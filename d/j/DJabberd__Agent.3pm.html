NOM

DJabberd::Agent - Classe de base abstraite représentant un agent logiciel qui communique via XMPP

SYNOPSIS

Les nouveaux agents sont créés en faisant une sous-classe de cette classe. Les méthodes "set_config_..." peuvent être fournies pour ajouter des options de configuration, qui seront ensuite prises en charge à la fois sur le constructeur de cette classe et dans un fichier de configuration lors de l'ajout de votre agent à un VHost en tant que plugin de livraison.

package MyAgent;

use base qw(DJabberd::Agent);

sub handles_destination {
    my ($self, $to_jid, $vhost) = @_;

    return ($to_jid->domain eq 'example.com' && $to_jid->node eq 'blah') ? 1 : 0;
}

sub handle_message {
    my ($self, $vhost, $stanza) = @_;
    my $response = $stanza->make_response();
    my $message = $self->{message} || "Hello, world!";
    $response->set_raw("<body>".DJabberd::Util::exml($message)."</body>");
    $response->deliver($vhost);
}

sub set_config_message {
    my ($self, $message) = @_;
    $self->{message} = $message;
}

L'exemple suivant montre comment vous pourriez charger la classe d'agent ci-dessus en tant que plugin :

<Plugin MyAgent>
    Message Kumquats are groovy!
</Plugin>

Il est également possible d'utiliser directement une instance en tant qu'objet, pour déléguer le traitement des stanzas à un autre plugin de livraison :

my $agent = MyAgent->new(
    message => "Kumquats are groovy!",
);
$agent->handle_stanza($vhost, $stanza);

Dans ce cas, l'appelant devra gérer lui-même les rappels de l'accroche de livraison de manière appropriée, mais on peut supposer qu'un appel à "handle_stanza" "livrera" toujours la stanza dans un certain sens.

DESCRIPTION

Ce module est la base de plusieurs autres classes DJabberd de niveau supérieur qui fournissent une API pour créer des agents logiciels qui communiquent via XMPP. Cela inclut les composants qui desservent un domaine entier (voir DJabberd::Component) et les nœuds de type bot qui ne répondent qu'à un nom de nœud spécifique dans un domaine (voir DJabberd::Agent::Node).

Il est peu probable que d'autres classes héritent directement de cette classe. La plupart des utilisateurs devraient hériter de l'une des sous-classes de niveau supérieur en fonction du type d'agent qu'ils souhaitent créer. Cette classe fournit le mécanisme de base pour le traitement des stanzas que tous les agents peuvent utiliser.

API

L'API de cette classe est normalement utilisée en redéfinissant certaines méthodes dans une sous-classe. Dans de nombreux cas, il est utile que ces méthodes redéfinies appellent les versions de la classe de base pour obtenir certaines fonctionnalités par défaut utiles.

La méthode "handles_destination" est la plus importante pour les héritiers à redéfinir, car les stanzas entrantes ne seront livrées à votre classe que si cette méthode renvoie vrai pour le JID de destination donné.

On suppose que si une valeur vraie est renvoyée par cette méthode, vous traiterez la stanza entrante d'une manière ou d'une autre ; cela implique que dans la plupart des cas, vous devriez répondre par un type de message d'erreur si la stanza est d'une manière ou d'une autre inacceptable.

Les sous-classes abstraites plus spécialisées de cette classe implémenteront généralement "handles_destination" d'une manière appropriée à leur rôle, de sorte que les utilisateurs de ces sous-classes n'auront pas besoin de redéfinir cette méthode.

handle_stanza($self, $vhost, $stanza)

Cette méthode est le « point d'entrée » de cette classe, et est appelée lorsqu'une stanza est reçue que cet agent a exprimé le désir de traiter. L'implémentation par défaut la distribue à l'une des méthodes de niveau supérieur "handle_..." en fonction du type de stanza reçue. Actuellement, seules les stanzas IQ, Message et Presence sont prises en charge.

Les héritiers peuvent redéfinir cette méthode pour effectuer un traitement bas niveau des stanzas, mais à moins que la version de cette classe ne soit invoquée, les méthodes de traitement de niveau supérieur cesseront de fonctionner.

Les appelants qui utilisent une instance d'agent directement en tant qu'objet plutôt que de l'avoir attachée à un VHost en tant que plugin appelleront généralement cette méthode directement pour déléguer le traitement des stanzas. Dans ce cas, il est de la responsabilité de l'appelant de s'assurer que la stanza convient à cet agent ; par exemple, l'appelant pourrait faire un appel à "handles_destination" pour déterminer si le JID de destination de la stanza convient.

handles_destination($self, $to_jid, $vhost)

Lorsqu'une stanza entrante est potentiellement destinée à être livrée à votre instance, cette méthode sera appelée pour savoir si votre agent est responsable du JID de destination.

Cette méthode est principalement utilisée dans le cas où l'agent est ajouté directement à un VHost en tant que plugin. Si une valeur vraie est renvoyée, le serveur supposera que votre agent traitera la stanza et appellera "handle_stanza". Si une valeur fausse est renvoyée, le serveur continuera à chercher un autre plugin de livraison approprié pour accepter la stanza.

handle_message($self, $vhost, $stanza)

Lorsque l'implémentation par défaut de "handle_stanza" est utilisée, cette méthode sera appelée pour traiter les stanzas « message » entrantes. L'objet $stanza passé sera une instance de DJabberd::Message.

L'implémentation par défaut de cette méthode ne fait rien.

handle_presence($self, $vhost, $stanza)

Lorsque l'implémentation par défaut de "handle_stanza" est utilisée, cette méthode sera appelée pour traiter les stanzas « presence » entrantes. L'objet $stanza passé sera une instance de DJabberd::Presence.

L'implémentation par défaut de cette méthode ne fait rien.

handle_iq($self, $vhost, $stanza)

Lorsque l'implémentation par défaut de "handle_stanza" est utilisée, cette méthode sera appelée pour traiter les stanzas « iq » entrantes. L'objet $stanza passé sera une instance de DJabberd::IQ.

L'implémentation par défaut de cette méthode fournit une prise en charge intégrée pour la découverte de service de base et les requêtes vcard, et provoque également l'appel de tous les gestionnaires IQ enregistrés lorsque c'est approprié.

Dans la plupart des cas, il vaut mieux ne pas redéfinir complètement cette méthode, mais plutôt enregistrer un gestionnaire IQ pour la signature IQ particulière qui vous intéresse en utilisant "register_iq_handler".

$self->register_iq_handler($signature, $handler)

Contrairement à la plupart des méthodes de cette classe, cette méthode n'est pas destinée à être redéfinie par les sous-classes. À la place, les sous-classes devraient appeler cette méthode pour enregistrer un gestionnaire pour un type particulier de stanza IQ. L'implémentation par défaut de "handle_iq" appellera alors les gestionnaires enregistrés lorsqu'une stanza appropriée est reçue.

$signature est une chaîne contenant la signature IQ utilisant le format de signature IQ standard de DJabberd. Cela consiste en le type IQ ("get", "set", etc) suivi d'un tiret, puis l'espace de noms de l'élément IQ entre accolades suivi du nom de l'élément. Par exemple, la signature pour une requête get vCard est "{vcard-temp}vCard".

$handler doit être une référence CODE qui accepte comme arguments "($vhost, $stanza")>, où $stanza sera une instance de DJabberd::IQ.

Si un gestionnaire est fourni pour une signature pour laquelle cette classe a une prise en charge intégrée, le gestionnaire fourni remplacera le gestionnaire intégré.

vcard($self, $requester_jid)

Appelé par l'implémentation vCard intégrée de cette classe pour obtenir le contenu de la vCard de cet agent. Les sous-classes doivent surcharger cette méthode et retourner une chaîne contenant le XML représentant le corps de la vCard à retourner, sans l'élément "vCard" conteneur.

L'implémentation par défaut retourne simplement une vCard vide. C'est préférable à ne retourner aucune réponse du tout, car certains clients font des choses sous-optimales si une requête de vCard échoue.

features($self, $requester_jid)

Appelé par l'implémentation Service Discovery intégrée de cette classe pour obtenir une liste des « features » (fonctionnalités) prises en charge par cet agent. Les sous-classes doivent surcharger cette méthode et retourner une référence à un tableau (ARRAY ref) contenant une liste de chaînes contenant les URI des fonctionnalités.

L'implémentation par défaut retourne les URI de fonctionnalités correctes pour indiquer la prise en charge des vCards et de la Service Discovery. Il est suggéré que les méthodes surchargées appellent initialement la classe parente pour obtenir la liste par défaut et ajoutent ensuite leurs propres fonctionnalités à la liste selon les besoins.

identities($self, $requester_jid)

Appelé par l'implémentation Service Discovery intégrée de cette classe pour obtenir une liste des « identities » (identités) exposées par cet agent. Les sous-classes doivent surcharger cette méthode et retourner une référence à un tableau (ARRAY ref) contenant une liste de références à des tableaux de la forme "[$category,$type,$name]", où ces valeurs correspondent aux attributs de même nom dans la spécification Service Discovery (XEP-0030).

Par exemple, il peut être approprié qu'un agent fournissant une salle de conférence multi-utilisateurs retourne l'identité "["conference","text","General Discussion"]".

L'implémentation par défaut retourne actuellement une liste vide. Il est suggéré que les méthodes surchargées appellent initialement la classe parente pour obtenir la liste par défaut et ajoutent ensuite leurs propres fonctionnalités à la liste selon les besoins. Bien que la liste retournée par cette classe soit actuellement vide, les sous-classes abstraites de niveau supérieur peuvent ajouter leurs propres identités à cette liste.

child_services($self, $requester_jid)

Appelé par l'implémentation Service Discovery intégrée de cette classe pour obtenir une liste des services enfants référencés par cet agent. Les sous-classes doivent surcharger cette méthode et retourner une référence à un tableau (ARRAY ref) contenant une liste de références à des tableaux de la forme "[$jid,$name]", où ces valeurs correspondent aux attributs de même nom dans la spécification Service Discovery (XEP-0030).

L'implémentation par défaut retourne actuellement une liste vide. Il est suggéré que les méthodes surchargées appellent initialement la classe parente pour obtenir la liste par défaut et ajoutent ensuite leurs propres fonctionnalités à la liste selon les besoins. Bien que la liste retournée par cette classe soit actuellement vide, les sous-classes abstraites de niveau supérieur peuvent ajouter leurs propres services enfants à cette liste.
