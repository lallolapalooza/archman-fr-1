DESCRIPTION

debuginfod_begin() crée un handle de connexion debuginfod_client qui doit être utilisé avec tous les autres appels. debuginfod_end() doit être appelé sur le handle client pour libérer tout état et stockage une fois terminé.

debuginfod_find_debuginfo(), debuginfod_find_executable(), et debuginfod_find_source() interrogent les serveurs debuginfod dont les URL sont contenues dans $DEBUGINFOD_URLS (voir ci-dessous) pour les informations de débogage, l'exécutable ou le fichier source avec le build_id donné. build_id doit être un pointeur vers une chaîne hexadécimale en minuscules se terminant par un octet nul ou un blob binaire. Si build_id est donné sous forme de chaîne hexadécimale, build_id_len doit être 0. Sinon, build_id_len doit être le nombre d'octets dans le blob binaire.

debuginfod_find_source() nécessite également un filename afin de spécifier un fichier source particulier. filename doit être un chemin absolu incluant le répertoire de compilation de l'unité de compilation (CU) associée au fichier source. Les chemins relatifs apparaissent couramment dans le répertoire source du fichier DWARF, mais ces chemins sont relatifs aux chemins AT_comp_dir de chaque unité de compilation, et un exécutable est composé de plusieurs CU. Par conséquent, pour désambiguïser, debuginfod attend que les requêtes de source préfixent les noms de chemins relatifs avec le répertoire de compilation de la CU, suivi d'un "/" obligatoire.

Note : l'appelant peut ou non élider les composants de chemin tels que ../, /./ ou des /// superflus dans les noms de répertoire. debuginfod accepte les deux formes. Spécifiquement, debuginfod canonise les noms de chemins conformément à la section 5.2.4 de la RFC3986 (Supprimer les segments de point), plus la réduction de tout // à / dans le chemin.

debuginfod_find_section() interroge les URL de serveur debuginfod contenues dans $DEBUGINFOD_URLS pour le contenu binaire d'une section ELF/DWARF contenue dans un fichier d'informations de débogage ou exécutable avec le build_id donné. section doit être le nom de la section ELF/DWARF souhaitée. Si un serveur ne prend pas en charge les requêtes de section, debuginfod_find_section peut interroger le serveur pour les informations de débogage et/ou l'exécutable avec build_id afin de récupérer et d'extraire la section.

debuginfod_find_metadata() interroge toutes les URL de serveur debuginfod contenues dans $DEBUGINFOD_URLS pour les métadonnées de toutes les correspondances d'une requête clé/valeur donnée avec les fichiers de leurs index. Le fichier résultant est un document JSON. Voir la page man debuginfod-find(1) pour des exemples des types de requêtes clé/valeur pris en charge et leurs résultats JSON.

Si path n'est pas NULL et que la requête réussit, path est défini sur le chemin du fichier dans le cache. L'appelant doit libérer (free()) cette valeur.

Les URL dans $DEBUGINFOD_URLS peuvent être interrogées en parallèle. Dès qu'un serveur debuginfod commence à transférer le fichier cible, toutes les connexions vers les autres serveurs sont fermées.

Un handle client ne doit être utilisé que par un seul fil d'exécution à la fois. Un handle peut être réutilisé pour une série de recherches, ce qui peut améliorer les performances grâce à la rétention des connexions et des caches.

VALEUR DE RETOUR

debuginfod_begin renvoie le handle debuginfod_client à utiliser avec tous les autres appels. En cas d'erreur, NULL sera renvoyé et errno sera défini.

Si une fonction de la famille find réussit, le fichier résultant est enregistré dans le cache client et un descripteur de fichier vers ce fichier est renvoyé. Le descripteur de fichier pointe vers le début du fichier. L'appelant doit fermer (close()) ce descripteur. Sinon, un code d'erreur négatif est renvoyé.

FONCTIONS OPTIONNELLES

Un petit nombre de fonctions optionnelles sont disponibles pour affiner ou interroger le fonctionnement du client debuginfod.

RAPPEL DE PROGRÈS

Comme les fonctions debuginfod_find_*() peuvent bloquer pendant des secondes ou plus, une fonction de rappel de progression est appelée périodiquement, si elle est configurée avec debuginfod_set_progressfn(). Cette fonction définit une nouvelle fonction de rappel de progression (ou NULL) pour le handle client.

La fonction de rappel donnée est appelée depuis le contexte de chaque fil d'exécution qui invoque l'une des autres fonctions de recherche. Elle reçoit deux paramètres numériques qui, considérés comme un numérateur a et un dénominateur b, représentent ensemble une fraction d'achèvement a/b. Le dénominateur peut être zéro initialement, jusqu'à ce qu'une quantité telle qu'une taille de téléchargement exacte soit connue.

La fonction de rappel de progression est également le moyen pris en charge pour interrompre l'opération de téléchargement. (La bibliothèque ne modifie ni ne déclenche de signaux.) La fonction de rappel de progression doit renvoyer 0 pour continuer le travail, ou toute autre valeur pour arrêter le travail dès que possible. Par conséquent, la fonction debuginfod_find_*() renverra probablement une erreur, mais pourrait toujours réussir.

SORTIE VERBOSE

Les fonctions debuginfod_find_*() peuvent utiliser plusieurs techniques pour récupérer les fichiers demandés, via le cache ou via un ou plusieurs serveurs ou URL de fichiers. Pour montrer comment une requête est traitée, debuginfod_set_verbose_fd() peut être utilisé pour définir un descripteur de fichier particulier sur lequel une sortie détaillée est donnée concernant les étapes de la requête et les erreurs éventuelles rencontrées.

HTTP

Avant que chaque fonction de recherche ne soit initiée, une application cliente peut ajouter des en-têtes de requête HTTP. Ceux-ci sont réinitialisés après chaque fonction de recherche. debuginfod_add_http_header() peut être appelée avec des chaînes de la forme "En-tête: valeur". Ces chaînes sont copiées par la bibliothèque. Une valeur de retour nulle indique le succès, mais des conditions de manque de mémoire peuvent entraîner une valeur non nulle -ENOMEM. Si la chaîne est sous la mauvaise forme, -EINVAL sera

retournée.

$DEBUGINFOD_HEADERS_FILE spécifie un fichier fournissant des en-têtes aux requêtes sortantes. Chaque ligne non vide de ce fichier est traitée comme si debuginfod_add_http_header() était appelée sur son

contenu.

Notez que l'implémentation actuelle de la bibliothèque debuginfod-client utilise libcurl, mais vous ne devriez pas vous reposer sur ce fait. N'utilisez pas cette fonction pour remplacer des en-têtes standards, à l'exception du User-Agent mentionné ci-dessous. Vous pouvez utiliser cette fonction pour ajouter des informations d'autorisation pour le contrôle d'accès, ou pour fournir des en-têtes optionnels au serveur à des fins de

journalisation.

Par défaut, la bibliothèque ajoute un User-Agent: descriptif aux requêtes sortantes. Si l'application cliente ajoute un en-tête avec le même nom, cette valeur par défaut est

supprimée.

Pendant ou après une recherche, une application cliente peut appeler debuginfod_get_headers() pour rassembler le sous-ensemble des en-têtes de réponse HTTP reçus du serveur debuginfod actuel ou le plus récent. Seuls les en-têtes préfixés par X-DEBUGINFOD (insensible à la casse) sont conservés. Ils sont retournés sous la forme d'une chaîne unique, avec chaque "en-tête: valeur" terminée par un \n (et no

n \r\n comme en HTTP). Elle peut être NULL. La chaîne résultante appartient à la b

aîne retournée si elle est nécessaire au-delà de la libération de l'objet client.

CACH

E

Avant chaque requête, la bibliothèque client debuginfod vérifie la nécessité de nettoyer le cache. S'il est temps de nettoyer, la bibliothèque parcourt le répertoire de cache et supprimees téléchargés liés au debuginfo et les répertoires devenus vides, s'ils n'ont pas été accédés

récemment.

Les fichiers de contrôle se situent directement sous le répertoire de cache. Ils contiennent des nombres décimaux simples pour définir les paramètres de configuration liés au cache. Si les fichiers n'existent pas, la bibliothèque client crée les fichiers avec les valeurs de paramètres par défaut comme

contenu.

Après chaque requête, la bibliothèque client de debuginfod dépose les fichiers nouvellement reçus dans un répertoire et un fichier dont le nom est basé sur le build-id. Une requête échouée est également mise en cache par un fichier spécial. La convention de nommage utilisée pour ces artefacts est délibérément non docume
