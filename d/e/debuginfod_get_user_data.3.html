NOM

debuginfod_find_debuginfo - demande des informations de débogage à debuginfod

SYNOPSIS

#include <elfutils/debuginfod.h>
Lier avec -ldebuginfod.

DESCRIPTION

debuginfod_begin() crée une poignée de connexion debuginfod_client qui doit être utilisée avec tous les autres appels. debuginfod_end() doit être appelée sur la poignée client pour libérer tout l'état et le stockage lorsque vous avez terminé.

debuginfod_find_debuginfo(), debuginfod_find_executableet debuginfod_find_source() interrogent les URL des serveurs debuginfod contenues dans $DEBUGINFOD_URLS (voir ci-dessous) pour obtenir le fichier d'informations de débogage, l'exécutable ou le fichier source correspondant à build_iddonné. build_id doit être un pointeur vers soit une chaîne hexadécimale en minuscules terminée par un caractère nul, soit un bloc binaire. Si build_id est donné sous forme de chaîne hexadécimale, build_id_len doit être 0. Sinon, build_id_len doit être le nombre d'octets du bloc binaire.

debuginfod_find_source() requiert également un filename afin de spécifier un fichier source particulier. filename doit être un chemin absolu incluant le répertoire de compilation de l'unité de compilation (CU) associée au fichier source. Les chemins relatifs apparaissent couramment dans le répertoire source du fichier DWARF, mais ces chemins sont relatifs aux chemins AT_comp_dir des unités de compilation individuelles, alors qu'un exécutable est composé de plusieurs CU. Par conséquent, pour lever l'ambiguïté, debuginfod attend que les requêtes de source préfixent les chemins relatifs par le répertoire de compilation de la CU, suivi d'un "/" obligatoire.

Remarque : l'appelant peut ou non omettre ../ ou /./ ou des composants de chemin superflus /// dans les noms de répertoires. debuginfod accepte les deux formes. Plus précisément, debuginfod canonifie les noms de chemin conformément à la section 5.2.4 de la RFC3986 (Remove Dot Segments), et réduit également tout // à / dans le chemin.

debuginfod_find_section() interroge les URL des serveurs debuginfod contenues dans $DEBUGINFOD_URLS pour obtenir le contenu binaire d'une section ELF/DWARF contenue dans un fichier d'informations de débogage ou un exécutable avec le build_iddonné. section doit être le nom de la section ELF/DWARF souhaitée. Si un serveur ne prend pas en charge les requêtes de section, debuginfod_find_section peut interroger le serveur pour le fichier d'informations de débogage et/ou l'exécutable avec build_id afin de récupérer et d'extraire la section.

debuginfod_find_metadata() interroge toutes les URL des serveurs debuginfod contenues dans $DEBUGINFOD_URLS pour obtenir les métadonnées de toutes les correspondances d'une requête clé/valeur donnée sur les fichiers de leurs index. Le fichier résultant est un document JSON. Voir la page man debuginfod-find(1) pour des exemples des types de requêtes clé/valeur pris en charge et de leurs résultats JSON.

Si path n'est pas NULL et que la requête réussit, path est défini sur le chemin du fichier dans le cache. L'appelant doit free() cette valeur.

Les URL dans $DEBUGINFOD_URLS peuvent être interrogées en parallèle. Dès qu'un serveur debuginfod commence à transférer le fichier cible, toutes les connexions aux autres serveurs sont fermées.

Une poignée client ne doit être utilisée que par un seul thread à la fois. Une poignée peut être réutilisée pour une série de recherches, ce qui peut améliorer les performances grâce à la conservation des connexions et des caches.

VALEUR RENVOYÉE

debuginfod_begin renvoie la poignée debuginfod_client à utiliser avec tous les autres appels. En cas d'erreur, NULL sera renvoyé et errno sera défini.

Si une fonction de la famille find réussit, le fichier résultant est enregistré dans le cache du client et un descripteur de fichier vers ce fichier est renvoyé. Le descripteur de fichier pointe vers le début du fichier. L'appelant doit close() ce descripteur. Sinon, un code d'erreur négatif est renvoyé.

FONCTIONS FACULTATIVES

Un petit nombre de fonctions facultatives sont disponibles pour régler ou interroger le fonctionnement du client debuginfod.

RAPPEL DE PROGRESSION

Comme les fonctions debuginfod_find_*() peuvent bloquer pendant des secondes ou plus, une fonction de rappel de progression est appelée périodiquement, si elle est configurée avec debuginfod_set_progressfn(). Cette fonction définit une nouvelle fonction de rappel de progression (ou NULL) pour la poignée client.

La fonction de rappel donnée est appelée depuis le contexte de chaque thread qui invoque l'une des autres fonctions de recherche. Elle reçoit deux paramètres numériques qui, si on les considère comme un numérateur a et un dénominateur b, représentent ensemble une fraction d'achèvement a/b. Le dénominateur peut être zéro au départ, jusqu'à ce qu'une quantité telle que la taille exacte du téléchargement devienne connue.

La fonction de rappel de progression est également le moyen pris en charge pour interrompre l'opération de téléchargement. (La bibliothèque ne modifie pas ou ne déclenche pas de signaux.) Le rappel de progression doit renvoyer 0 pour continuer le travail, ou toute autre valeur pour arrêter le travail dès que possible. Par conséquent, la fonction debuginfod_find_*() renverra probablement une erreur, mais pourrait tout de même réussir.

SORTIE VERBEUSE

Les fonctions debuginfod_find_*() peuvent utiliser plusieurs techniques pour récupérer les fichiers demandés, via le cache ou via un ou plusieurs serveurs ou URL de fichiers. Pour montrer comment une requête est traitée, debuginfod_set_verbose_fd() peut être utilisé pour définir un descripteur de fichier particulier sur lequel une sortie verbeuse est donnée concernant les étapes de la requête et les éventuelles erreurs rencontrées.

POINTEUR DE DONNÉES UTILISATEUR

Un unique pointeur void * associé à la poignée de connexion peut être défini à tout moment via debuginfod_set_user_data(), et récupéré via debuginfod_get_user_data(). La valeur est indéfinie si elle n'est pas définie.

<

URL

L'URL du téléchargement sortant actuel ou le plus récent, s'il est connu, peut être récupéré via debuginfod_get_url() depuis le callback progressfn, ou après. Il peut être NULL. La chaîne résultante appartient à la bibliothèque et ne doit pas être modifiée ou libérée. L'appelant doit la copier si elle est nécessaire au-delà de la libération de l'objet client.

EN-TÊTE HTTP

Avant l'initiation de chaque fonction de recherche, une application cliente peut ajouter des en-têtes de requête HTTP. Ceux-ci sont réinitialisés après chaque fonction de recherche. debuginfod_add_http_header() peut être appelé avec des chaînes de la forme "En-tête: valeur". Ces chaînes sont copiées par la bibliothèque. Une valeur de retour nulle indique le succès, mais des conditions de manque de mémoire peuvent entraîner un -ENOMEM non nul. Si la chaîne est dans le mauvais format, -EINVAL sera retourné.

$DEBUGINFOD_HEADERS_FILE spécifie un fichier pour fournir des en-têtes aux requêtes sortantes. Chaque ligne non vide de ce fichier est traitée comme si debuginfod_add_http_header() avait été appelé sur son contenu.

Notez que l'implémentation actuelle de la bibliothèque debuginfod-client utilise libcurl, mais vous ne devriez pas vous fier à ce fait. N'utilisez pas cette fonction pour remplacer des en-têtes standard, sauf pour le User-Agent mentionné ci-dessous. Vous pouvez utiliser cette fonction pour ajouter des informations d'autorisation pour le contrôle d'accès, ou pour fournir des en-têtes optionnels au serveur à des fins de journalisation.

Par défaut, la bibliothèque ajoute un en-tête descriptif User-Agent: aux requêtes sortantes. Si l'application cliente ajoute un en-tête du même nom, cette valeur par défaut est supprimée.

Pendant ou après une recherche, une application cliente peut appeler debuginfod_get_headers() pour collecter le sous-ensemble des en-têtes de réponse HTTP reçus du serveur debuginfod actuel ou le plus récent. Seuls les en-têtes préfixés par X-DEBUGINFOD (insensible à la casse) sont conservés. Ils sont retournés sous forme d'une seule chaîne, chaque "en-tête: valeur" étant terminé par un \n (pas \r\n comme en HTTP). Il peut être NULL. La chaîne résultante appartient à la bibliothèque et ne doit pas être modifiée ou libérée. L'appelant doit copier la chaîne retournée si elle est nécessaire au-delà de la libération de l'objet client.

MACROS

DEBUGINFOD_SONAME

Défini sur la chaîne qui pourrait être passée à dlopen(3) si la bibliothèque est chargée à l'exécution, par exemple


void *debuginfod_so = dlopen(DEBUGINFOD_SONAME, RTLD_LAZY);

SÉCURITÉ

Si des signatures IMA sont disponibles à partir des RPM contenant les fichiers demandés, debuginfod extraira ces signatures dans des en-têtes de réponse, et debuginfod_find_*() effectuera une vérification sur les fichiers. La politique de validation est contrôlée via des balises insérées dans $DEBUGINFOD_URLS. Par défaut, debuginfod_find_*() agit en mode ignoré.

Si l'accès se fait via HTTP plutôt que HTTPS, le réseau doit être digne de confiance. Les informations d'authentification via la bibliothèque interne libcurl ne sont actuellement pas activées, à l'exception du style basique en texte clair http[s]://userid:password@hostname/. (Le serveur debuginfod n'effectue pas d'authentification, mais un serveur proxy frontal pourrait le faire.)

ERREURS

La liste suivante n'est pas exhaustive. Des codes d'erreur peuvent également provenir d'appels à diverses fonctions de la bibliothèque C.

EACCESS
Accès refusé à la ressource située à l'URL.
ECONNREFUSED
Impossible de se connecter à l'hôte distant. Également retourné lorsqu'une connexion HTTPS n'a pas pu être vérifiée (certificat invalide).
ECONNRESET
Impossible d'envoyer ou de recevoir des données réseau.
EHOSTUNREACH
Impossible de résoudre l'hôte distant.
EINVAL
Un ou plusieurs arguments sont mal formatés. build_id peut être trop long (supérieur à 256 caractères), filename peut ne pas être un chemin absolu ou une URL debuginfod est malformée.
EIO
Impossible d'écrire les données reçues du serveur dans le fichier local.
EMLINK
Trop de redirections HTTP.
ENETUNREACH
Impossible d'initialiser la connexion réseau.
ENOENT
Impossible de trouver la ressource située à l'URL. Souvent, ce code d'erreur indique qu'un serveur debuginfod a été contacté avec succès mais que le serveur n'a pas pu trouver le fichier cible.
ENOMEM
Le système ne peut pas allouer de ressources.
ENOSYS
$DEBUGINFOD_URLS n'est pas défini.
ETIME
La requête a échoué en raison d'un délai d'attente. $DEBUGINFOD_TIMEOUT et $DEBUGINFOD_MAXTIME contrôlent cela.
EF2BIG
La requête a été abandonnée car le fichier demandé est trop volumineux. Le $DEBUGINFOD_MAXSIZE contrôle cela.
EBADMSG
Le contenu du fichier n'a pas réussi la vérification IMA par rapport à un certificat de signature connu.
ENOKEY
Le contenu du fichier n'a pas réussi la vérification IMA en raison d'un certificat de signature manquant.
ENODATA
Le contenu du fichier n'a pas réussi la vérification IMA en raison d'une signature manquante.

VARIABLES D'ENVIRONNEMENT

$TMPDIR
Cette variable d'environnement pointe vers un système de fichiers à utiliser pour les fichiers temporaires. La valeur par défaut est /tmp.
$DEBUGINFOD_URLS
Cette variable d'environnement contient une liste de préfixes d'URL pour les instances debuginfod fiables. Les préfixes d'URL alternatifs sont séparés par un espace. Cette variable d'environnement peut être définie par des scripts /etc/profile.d lisant les fichiers /etc/debuginfod/*.urls.

Cette variable d'environnement peut également contenir des politiques définissant des balises qui dictent la politique de réponse pour la vérification des signatures IMA par fichier dans les RPM. Alors que la liste séparée par des espaces est lue de gauche à droite, lors de la rencontre d'une balise, les URL suivantes jusqu'à la prochaine balise seront traitées en utilisant cette politique spécifiée. Toutes les URL avant la première balise utiliseront la politique par défaut, ima:ignore. Par exemple :


DEBUGINFOD_URLS="https://foo.com ima:enforcing https://bar.ca http://localhost:8002/ ima:ignore https://baz.org"

Où foo.com et baz.org utilisent la politique par défaut ignore et bar.ca et localhost utilisent une politique enforcing. La balise de politique peut être l'une des suivantes :

ima:enforcing Chaque fichier téléchargé nécessite une signature valide, protégeant entièrement l'intégrité.
ima:ignore Ignore complètement la vérification, ne fournissant aucune protection.

Les alertes en cas d'échec de validation seront dirigées comme spécifié dans $DEBUGINFOD_VERBOSE.

$DEBUGINFOD_CACHE_PATH
Cette variable d'environnement régit l'emplacement du cache où les fichiers téléchargés et les fichiers de contrôle de cache sont conservés. Le répertoire par défaut est choisi en fonction d'autres variables d'environnement, voir ci-dessous.
$DEBUGINFOD_PROGRESS
Cette variable d'environnement régit la fonction de progression par défaut. Si définie, et si une fonction de progression n'est pas explicitement définie, la bibliothèque configurera une fonction de progression par défaut. Cette fonction ajoutera un message de progression simple périodiquement à stderr. Par défaut, aucune sortie de fonction de progression n'est générée.
$DEBUGINFOD_VERBOSE
Cette variable d'environnement régit le descripteur de fichier par défaut pour la sortie détaillée. Si définie, et si un descripteur de fichier détaillé n'est pas explicitement défini, la sortie détaillée sera produite sur STDERR_FILENO.
$DEBUGINFOD_RETRY_LIMIT
Cette variable d'environnement régit la limite par défaut des tentatives de nouvelle connexion. Si une requête échoue avec un errno autre que ENOENT, plusieurs tentatives seront initiées dans la limite.
$DEBUGINFOD_TIMEOUT
Cette variable d'environnement régit le délai d'attente de commencement du téléchargement pour chaque connexion HTTP debuginfod. Un serveur qui ne parvient pas à fournir au moins 100 Ko de données dans ce nombre de secondes est ignoré. La valeur par défaut est 90 secondes. (Zéro ou négatif signifie "pas de délai d'attente".)
$DEBUGINFOD_MAXTIME
Cette variable d'environnement détermine combien de temps le client attendra pour compléter le téléchargement d'un fichier trouvé sur un serveur, en secondes. Il est préférable de l'utiliser pour s'assurer qu'un fichier est téléchargé rapidement ou rejeté. La valeur par défaut est 0 (temps infini).
$DEBUGINFOD_MAXSIZE
Cette variable d'environnement détermine la taille maximale d'un fichier à télécharger en octets. Il est préférable de l'utiliser si l'utilisateur souhaite s'assurer que seuls de petits fichiers sont téléchargés. Une valeur de 0 n'entraîne aucune prise en compte de la taille, et le client peut tenter de télécharger un fichier de n'importe quelle taille. La valeur par défaut est 0 (taille infinie).
$DEBUGINFOD_HEADERS_FILE
Cette variable d'environnement pointe vers un fichier qui fournit des en-têtes aux requêtes HTTP sortantes, un par ligne. Les lignes d'en-tête ne doivent pas se terminer par CRLF, sauf si telle est la convention de nouvelle ligne du système. Les lignes contenant uniquement des espaces sont ignorées.
$DEBUGINFOD_IMA_CERT_PATH
Cette variable d'environnement contient une liste de chemins de répertoires absolus contenant des certificats X.509 pour la vérification IMA par fichier des RPM. Les chemins alternatifs sont séparés par des deux-points.

CACHE

Avant chaque requête, la bibliothèque cliente debuginfod vérifie si un nettoyage du cache est nécessaire. S'il est temps de nettoyer, la bibliothèque parcourt le répertoire du cache et supprime

s téléchargés liés au debuginfo et les répertoires devenus vides, s'ils n'ont pas été accédés récemment.

Les fichiers de contrôle sont situés directement sous le répertoire de cache. Ils contiennent des nombres décimaux simples pour définir les paramètres de configuration liés au cache. Si les fichiers n'existent pas, la bibliothèque client du cache crée les fichiers avec les valeurs par défaut des paramètres comme contenu.

Après chaque requête, la bibliothèque client de debuginfod dépose les fichiers nouvellement reçus dans un répertoire et un fichier dont le nom est basé sur le build-id. Une requête échouée est également mise en cache par un fichier spécial. La convention de nommage utilisée pour ces artefacts est délibérément non documentée.

$XDG_CACHE_HOME/debuginfod_client/
Répertoire de cache par défaut, si $XDG_CACHE_HOME est défini.
$HOME/.cache/debuginfod_client/
Répertoire de cache par défaut, si $XDG_CACHE_HOME n'est pas défini.
$HOME/.debuginfod_client_cache/
Répertoire de cache obsolète, utilisé uniquement s'il existe déjà.
cache_clean_interval_s
Ce fichier de contrôle donne l'intervalle entre les cycles de nettoyage du cache, en secondes. La valeur par défaut est 86400, un jour. 0 signifie « immédiatement ».
max_unused_age_s
Ce fichier de contrôle définit la durée de conservation des fichiers liés au debuginfo non accédés, en secondes. La valeur par défaut est 604800, une semaine. 0 signifie « immédiatement ».
cache_miss_s
Ce fichier de contrôle définit la durée de mémorisation d'un échec de requête, en secondes. Les nouvelles requêtes pour les mêmes artefacts dans cette fenêtre de temps sont court-circuitées (retournant un échec immédiat au lieu d'envoyer une nouvelle requête aux serveurs). Cela accélère les requêtes qui échoueraient probablement encore. La valeur par défaut est 600, 10 minutes. 0 signifie « oublier immédiatement ».
metadata_retention_s
Ce fichier de contrôle définit la durée de mémorisation des résultats d'une requête de métadonnées. Les nouvelles requêtes pour les mêmes artefacts dans cette fenêtre de temps sont court-circuitées (en répétant les mêmes résultats). Cela accélère les requêtes qui auraient probablement les mêmes résultats. La valeur par défaut est 3600, 1 heure. 0 signifie « ne pas conserver ».
