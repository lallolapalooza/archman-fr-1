DESCRIPTIO

N

DECLARE permet à un utilisateur de créer des curseurs, qui peuvent être utilisés pour récupérer un petit nombre de lignes à la fois à partir d'une requête plus large. Une fois le curseur créé, les lignes sont extraites à l'aide de FETCH

.

Note

Cette page décrit l'utilisation des curseurs au niv

eau de la commande SQL. Si vous essayez d'utiliser
des curseurs à l'intérieur d'une fonction PL/pgSQL,
les règles sont différentes — voir la section 41.7.

S

no

m
Le nom du curseur à créer. Il doit être différent de tout autre nom de curseur actif dans la
session.

BINAR

Y
Fait que le curseur retourne les données en binaire plutôt qu'en format
texte.

ASENSITIVE
INSENSITIV

E
La sensibilité du curseur détermine si les modifications des données sous-jacentes au curseur, effectuées dans la même transaction après la déclaration du curseur, sont visibles dans le curseur. INSENSITIVE signifie qu'elles ne sont pas visibles, ASENSITIVE signifie que le comportement dépend de l'implémentation. Un troisième comportement, SENSITIVE, signifiant que de telles modifications sont visibles dans le curseur, n'est pas disponible dans PostgreSQL. Dans PostgreSQL, tous les curseurs sont insensibles ; ces mots-clés n'ont donc aucun effet et ne sont acceptés que pour des raisons de compatibilité avec le standard SQL.

Spécifier INSENSITIVE conjo

intement avec FOR UPDATE o
u FOR SHARE est une erreur.

SCROLL
NO

SCROLL
SCROLL spécifie que le curseur peut être utilisé pour récupérer des lignes de manière non séquentielle (par ex., à l'envers). Selon la complexité du plan d'exécution de la requête, spécifier SCROLL peut imposer une pénalité de performance sur le temps d'exécution de la requête. NO SCROLL spécifie que le curseur ne peut pas être utilisé pour récupérer des lignes de manière non séquentielle. Par défaut, le défilement est autorisé dans certains cas ; ce n'est pas la même chose que spécifier SCROLL. Voir les Notes ci-dessous pour plus de
détails.

WITH HOLD
WITHOUT

HOLD
WITH HOLD spécifie que le curseur peut continuer à être utilisé après que la transaction qui l'a créé a été validée avec succès. WITHOUT HOLD spécifie que le curseur ne peut pas être utilisé en dehors de la transaction qui l'a créé. Si ni WITHOUT HOLD ni WITH HOLD n'est spécifié, WITHOUT HOLD est la valeur par
défaut.

requêt

NOTE

S

Les curseurs normaux retournent les données en format texte, comme le ferait un SELECT. L'option BINARY spécifie que le curseur doit retourner les données en format binaire. Cela réduit l'effort de conversion tant pour le serveur que pour le client, au prix d'un effort de programmation plus important pour gérer les formats de données binaires dépendants de la plateforme. Par exemple, si une requête retourne la valeur un à partir d'une colonne entière, vous obtiendriez une chaîne de 1 avec un curseur par défaut, alors qu'avec un curseur binaire vous obtiendriez un champ de 4 octets contenant la représentation interne de la valeur (dans l'ordre des octets big-endian)

.

Les curseurs binaires doivent être utilisés avec précaution. De nombreuses applications, y compris psql, ne sont pas préparées à gérer des curseurs binaires et s'attendent à ce que les données reviennent en format

texte.

Note

Lorsque l'application cliente utilise le protocole de « requête étendue » pour émettre une commande FETCH, le message de protocole Bind spécifie si les données doivent être récupérées en format texte ou binaire. Ce choix prévaut sur la manière dont le curseur est défini

. Le concept de curseur binaire comme tel est donc obsolète lors de l'utilisation du prot
ocole de requête étendue — n'importe quel curseur peut être traité comme texte ou binaire.

Sauf si WITH HOLD est spécifié, le curseur créé par cette commande ne peut être utilisé qu'à l'intérieur de la transaction en cours. Ainsi, DECLARE sans WITH HOLD est inutile en dehors d'un bloc de transaction : le curseur ne survivrait qu'à l'exécution de l'instruction. Par conséquent, PostgreSQL signale une erreur si une telle commande est utilisée en dehors d'un bloc de transaction. Utilisez BEGIN et COMMIT (ou ROLLBACK) pour définir un bloc de

transaction.

Si WITH HOLD est spécifié et que la transaction qui a créé le curseur est validée avec succès, le curseur peut continuer à être accessible par les transactions suivantes dans la même session. (Mais si la transaction créatrice est annulée, le curseur est supprimé.) Un curseur créé avec WITH HOLD est fermé lorsqu'une commande CLOSE explicite est émise sur lui, ou lorsque la session se termine. Dans l'implémentation actuelle, les lignes représentées par un curseur conservé sont copiées dans un fichier temporaire ou une zone mémoire afin qu'elles restent disponibles pour les transactions

suivantes.

WITH HOLD ne peut pas être spécifié lorsque la requête inclut FOR UPDATE ou FOR

SHARE.

L'option SCROLL doit être spécifiée lors de la définition d'un curseur qui sera utilisé pour des extractions vers l'arrière. Cela est requis par le standard SQL. Cependant, pour des raisons de compatibilité avec les versions précédentes, PostgreSQL autorisera les extractions vers l'arrière sans SCROLL, si le plan de requête du curseur est suffisamment simple pour ne nécessiter aucune surcharge supplémentaire pour le prendre en charge. Cependant, il est conseillé aux développeurs d'applications de ne pas compter sur l'utilisation d'extractions vers l'arrière à partir d'un curseur qui n'a pas été créé avec SCROLL. Si NO SCROLL est spécifié, les extractions vers l'arrière sont interdites dans tous les

cas.

Les extractions vers l'arrière sont également interdites lorsque la requête inclut FOR UPDATE ou FOR SHARE ; par conséquent, SCROLL ne peut pas être spécifié dans ce

cas.

Attention

Les curseurs défilables peuvent donner des résultats inattendus s'ils invoquent des fonctions volatiles (voir la section 36.7). Lorsqu'une ligne précédemment extraite est ré-extrait, les fonctions peuvent être ré-exécutées, ce qui peut conduire à des ré

sultats différents de la première fois. Il est préférable de spécifier NO SCROLL pour une requête impliquant des fonctions volatiles. Si cela n'est pas pratique, une solution de contournement consiste à déclarer le curseur SCROLL WITH HOLD et à valider
la transaction avant de lire quoi que ce soit à partir de celui-ci. Cela forcera la sortie complète du curseur à être matérialisée dans un stockage temporaire, de sorte que les fonctions volatiles soient exécutées exactement une fois pour chaque ligne.

Si la requête du curseur inclut FOR UPDATE ou FOR SHARE, les lignes retournées sont verrouillées au moment où elles sont extraites pour la première fois, de la même manière que pour une commande SELECT régulière avec ces options. De plus, les lignes retournées seront les versions les plus à

jour.

Attention

Il est généralement recommandé d'utiliser FOR UPDATE si le curseur est destiné à être utilisé avec UPDATE ... WHERE CURRENT OF ou DELETE ... WHERE CURRENT OF. L'utilisation de FOR UPDATE empêche les autres sessions de modifier les lignes entre le moment où elles sont extraites et le moment où elles sont mises à jour. Sans FOR UPDATE, une commande WHERE CURRENT OF ultérieure n'aura aucun effet si la ligne a été modifiée depuis la création du

curseur.

Une autre raison d'utiliser FOR UPDATE est que sans lui, un WHERE CURRENT OF ultérieur pourrait échouer si la requête du curseur ne respecte pas les règles du standard SQL pour être « simplement mise à jour » (en particulier, le curseur doit référencer une seule table et ne pas utiliser de regroupement ni d'ORDER BY). Les curseurs qui ne sont pas simplement mis à jour peuvent fonctionner, ou non, selon les détails du choix de plan ; ainsi, dans le pire des cas, une application pourrait fonctionner en test puis échouer en production. Si FOR UPDATE est spécifié, le curseur est garanti d'être mis à

jour.

La principale raison de ne pas utiliser FOR UPDATE avec WHERE CURRENT OF est si vous avez besoin que le cu

rseur soit défilable, ou isolé des mises à jour concurrentes (c'est-à-dire qu'il continue d'afficher les an
ciennes données). Si c'est une exigence, veuillez tenir compte attentivement des avertissements ci-dessus.

Le standard SQL ne prévoit des curseurs que dans le SQL embarqué. Le serveur PostgreSQL n'implémente pas d'instruction OPEN pour les curseurs ; un curseur est considéré comme ouvert lorsqu'il est déclaré. Cependant, ECPG, le préprocesseur SQL embarqué pour PostgreSQL, prend en charge les conventions de curseurs SQL standard, y compris celles impliquant les instructions DECLARE et OPEN

.

La structure de données du serveur sous-jacente à un curseur ouvert est appelée un portail. Les noms de portails sont exposés dans le protocole client : un client peut extraire des lignes directement d'un portail ouvert, s'il connaît le nom du portail. Lors de la création d'un curseur avec DECLARE, le nom du portail est le même que celuisor

name.

COMPATIBILIT

É

Le standard SQL n'autorise les curseurs que dans le SQL embarqué et dans les modules. PostgreSQL permet d'utiliser les curseurs de manière

interactive.

Selon le standard SQL, les modifications apportées aux curseurs insensibles par les instructions UPDATE ... WHERE CURRENT OF et DELETE ... WHERE CURRENT OF sont visibles dans ce même curseur. PostgreSQL traite ces instructions comme toutes les autres instructions de modification de données, c'est-à-dire qu'elles ne sont pas visibles dans les curseurs

insensibles.
