DESCRIPTIO

N

NOTE : Ce module est un hack de Devel::SmallProf par Ted Ashton. Il a été modifié par Leon Brocard pour produire une sortie pour GraphViz, mais autrement, la seule chose que j'ai faite est de changer le nom. J'espère voir mes correctifs intégrés au code principal de Devel::SmallProf éventuellement, ou alternativement lire la sortie de Devel::SmallProf. Quoi qu'il en soit, la documentation normale, que vous pouvez probablement ignorer,

suit.

Le profileur Devel::GraphVizProf est centré sur le temps pris par l'exécution d'un programme ligne par ligne. Il est destiné à être aussi « petit » que possible en termes d'impact sur la vitesse et l'utilisation de la mémoire du programme profilé, et aussi en termes de simplicité d'utilisation. Ces statistiques sont placées dans le fichier smallprof.out au format suivant

: 
<num> <time> <ctime> <line>:
<text>

où <num> est le nombre de fois que la ligne a été exécutée, <time> est la quantité de « temps écoulé » (temps selon l'horloge murale vs. le temps CPU) passée à l'exécuter, <ctime> est la quantité de temps CPU dépensée pour elle et <line> et <text> sont le numéro de ligne et le texte réel de la ligne exécutée (lu depuis le fichier)

.

Le paquet utilise les crochets de débogage en Perl et a donc besoin du commutateur -d, donc pour profiler test.pl, utilisez la commande

: 
perl5 -d:GraphVizProf test.
pl

Une fois le script terminé, les statistiques dans smallprof.out peuvent être triées pour montrer quelles lignes ont pris le plus de temps. La sortie peut être triée pour trouver quelles lignes prennent le plus de temps, soit avec la commande sort

: 
sort -k 2nr,2 smallprof.out |
less

ou avec un script perl

: 
open(PROF,"smallprof.out");
@sorted = sort {(split
(/\s+/,$b))[2] <=> (split(/\s+/,$a
))[2]} <PROF>; close PROF; print join('',@sorted);

REMARQUE

S
  • Les mesures de « temps écoulé » proviennent de Time::HiRes et sont raisonnablement utiles, du moins sur mon système. Les temps CPU proviennent de la fonction interne 'times' et la granularité n'est pas nécessairement aussi fine qu'avec le temps écoulé. Sur certains systèmes, cette colonne peut être utile. Sur d'autres, elle peut ne pas
    • l'être.
  • GraphVizProf tente de compenser ses défauts en soustrayant une petite quantité à chaque mesure (compensation du temps nul). Cela devrait aider un peu pour la
    • précision.
  • GraphVizProf dépend du paquet Time::HiRes pour se
    • s mesures de temps. Il déclare nécessiter l
a version 1.20, mais peut fonctionner avec des ve
rsions antérieures, selon votre plateforme.

OPTION

S

GraphVizProf a 3 variables qui peuvent être utilisées pendant votre script pour affecter ce qui est

profilé.
  • Si vous ne souhaitez pas voir les lignes qui n'ont jamais été appelées, définissez la variable "$DB::drop_zeros = 1". Avec "drop_zeros" défini, GraphVizProf peut être utilisé pour une analyse de couverture
    • basique.
  • Pour désactiver le profilage pendant un moment, insérez un "$DB::profile = 0" dans votre code (le profilage peut être réactivé avec "$DB::profile = 1"). Tout le temps entre la désactivation et la réactivation du profilage sera regroupé et rapporté sur la ligne "$DB::profile = 0". Cela peut être utilisé pour résumer un appel de sous-routine ou un bloc de
    • code.
  • Pour ne profiler que le code dans un certain paquet, définissez le tableau %DB::packages. Par exemple, pour voir seulement le code dans les paquets "main" et "Test1", faites ceci : 
    %DB::packages = ( 'main' => 1, 'Test1' =>
    • 1 );
  • Ces variables peuvent être placées dans un fichier appelé .smallprof dans le répertoire courant. Par exemple, un .smallprof contenant 
    $DB::drop_zeros = 1;
$DB::profile
    = 0;

    définira GraphVizProf pour ne pas rapporter les lignes

    qui ne sont jamais touchées pour tout fichier p
    • rofilé dans ce répertoire et définira le profilage
désactivé initialement (probablement pour être act
ivé seulement pour une petite portion de code).

BOGUE

S

Les appels de sous-routines ne sont actuellement pas sous le contrôle de %DB::packages. Cela ne devrait pas être un grand inconvénient en

général.

La gestion des evals est mauvaise. Cela est dû à la gestion des evals par Perl sous le drapeau -d. Pour certains evals, caller() renvoie '(eval n)' pour le nom de fichier et pour d'autres non. Pour certains de ceux pour lesquels il le fait, le tableau "@{'_<filename'}" contient le code de l'eval. Pour d'autres, non. Un jour, quand j'aurai un ou deux tuits de plus, je comprendrai pourquoi et comment je peux compenser

cela.

. Si vous voyez des choses inefficaces dans ce module et a
vez une meilleure façon, s'il vous plaît faites-le moi savoir.
