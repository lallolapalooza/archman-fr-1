DESCRIPTION

debuginfod_begin() crée un gestionnaire de connexion debuginfod_client qui doit être utilisé avec tous les autres appels. debuginfod_end() doit être appelé sur le gestionnaire client pour libérer tout état et stockage une fois terminé.

debuginfod_find_debuginfo(), debuginfod_find_executable() et debuginfod_find_source() interrogent les serveurs debuginfod aux URL contenues dans $DEBUGINFOD_URLS (voir ci-dessous) pour les informations de débogage, l'exécutable ou le fichier source avec le build_id donné. build_id doit être un pointeur vers une chaîne hexadécimale se terminant par un caractère nul et en minuscules, ou un blob binaire. Si build_id est fourni sous forme de chaîne hexadécimale, build_id_len doit être 0. Sinon, build_id_len doit être le nombre d'octets dans le blob binaire.

debuginfod_find_source() nécessite également un filename afin de spécifier un fichier source particulier. filename doit être un chemin absolu incluant le répertoire de compilation de l'unité de compilation (CU) associée au fichier source. Les chemins relatifs apparaissent couramment dans le répertoire source du fichier DWARF, mais ces chemins sont relatifs aux chemins AT_comp_dir individuels des unités de compilation, et un exécutable est composé de plusieurs CU. Par conséquent, pour désambiguïser, debuginfod attend que les requêtes source préfixent les noms de chemins relatifs par le répertoire de compilation de la CU, suivi d'un caractère "/" obligatoire.

Remarque : l'appelant peut omettre ou non les composants de chemin tels que ../, /./ ou les /// superflus dans les noms de répertoires. debuginfod accepte les deux formes. Spécifiquement, debuginfod canonise les noms de chemins conformément à la section 5.2.4 de la RFC3986 (Remove Dot Segments), plus la réduction de tout // à / dans le chemin.

debuginfod_find_section() interroge les serveurs debuginfod aux URL contenues dans $DEBUGINFOD_URLS pour le contenu binaire d'une section ELF/DWARF contenue dans un fichier d'informations de débogage ou exécutable avec le build_id donné. section doit être le nom de la section ELF/DWARF souhaitée. Si un serveur ne prend pas en charge les requêtes de section, debuginfod_find_section peut interroger le serveur pour les informations de débogage et/ou l'exécutable avec build_id afin de récupérer et extraire la section.

debuginfod_find_metadata() interroge toutes les URL de serveur debuginfod contenues dans $DEBUGINFOD_URLS pour les métadonnées de toutes les correspondances d'une requête clé/valeur donnée par rapport aux fichiers de leurs index. Le fichier résultant est un document JSON. Voir la page de manuel de debuginfod-find(1) pour des exemples des types de requêtes clé/valeur pris en charge et de leurs résultats JSON.

Si path n'est pas NULL et que la requête réussit, path est défini sur le chemin du fichier dans le cache. L'appelant doit utiliser free() pour libérer cette valeur.

Les URL dans $DEBUGINFOD_URLS peuvent être interrogées en parallèle. Dès qu'un serveur debuginfod commence à transférer le fichier cible, toutes les connexions aux autres serveurs sont fermées.

Un gestionnaire client ne doit être utilisé que par un seul thread à la fois. Un gestionnaire peut être réutilisé pour une série de recherches, ce qui peut améliorer les performances grâce à la rétention des connexions et des caches.

VALEUR DE RETOUR

debuginfod_begin renvoie le gestionnaire debuginfod_client à utiliser avec tous les autres appels. En cas d'erreur, NULL sera renvoyé et errno sera défini.

Si une fonction de la famille find réussit, le fichier résultant est enregistré dans le cache du client et un descripteur de fichier vers ce fichier est renvoyé. Le descripteur de fichier pointe vers le début du fichier. L'appelant doit utiliser close() pour fermer ce descripteur. Sinon, un code d'erreur négatif est renvoyé.

FONCTIONS OPTIONNELLES

Un petit nombre de fonctions optionnelles sont disponibles pour ajuster ou interroger le fonctionnement du client debuginfod.

RAPPEL DE PROGRESSION

Comme les fonctions debuginfod_find_*() peuvent bloquer pendant des secondes ou plus, une fonction de rappel de progression est appelée périodiquement, si elle est configurée avec debuginfod_set_progressfn(). Cette fonction définit une nouvelle fonction de rappel de progression (ou NULL) pour le gestionnaire client.

La fonction de rappel donnée est appelée depuis le contexte de chaque thread qui invoque l'une des autres fonctions de recherche. Elle reçoit deux paramètres numériques qui, considérés comme un numérateur a et un dénominateur b, représentent ensemble une fraction d'achèvement a/b. Le dénominateur peut être zéro initialement, jusqu'à ce qu'une quantité telle qu'une taille de téléchargement exacte soit connue.

La fonction de rappel de progression est également le moyen pris en charge pour *interrompre* l'opération de téléchargement. (La bibliothèque ne modifie ni ne déclenche de signaux.) La fonction de rappel de progression doit renvoyer 0 pour continuer le travail, ou toute autre valeur pour arrêter le travail dès que possible. Par conséquent, la fonction debuginfod_find_*() renverra probablement une erreur, mais pourrait quand même réussir.

SORTIE VERBEUSE

Les fonctions debuginfod_find_*() peuvent utiliser plusieurs techniques pour récupérer les fichiers demandés, via le cache ou via un ou plusieurs serveurs ou URL de fichiers. Pour montrer comment une requête est traitée, debuginfod_set_verbose_fd() peut être utilisé pour définir un descripteur de fichier particulier sur lequel une sortie verbeuse est donnée concernant les étapes de la requête et les éventuelles erreurs rencontrées.

POINTEUR DE DONNÉES UTILISATEUR

Un seul pointeur void * associé au gestionnaire de connexion peut être défini à tout moment via debuginfod_set_user_data() et récupéré via debuginfod_get_user_data(). La valeur est indéfinie si elle n'est pas définie.

URL DU SERVEUR

debuginfod_get_url() renvoie l'URL du serveur actuellement interrogé. La chaîne renvoyée est un pointeur vers une chaîne statique et ne doit pas être modifiée ni libérée.

AJOUTER UN EN-TÊTE HTTP

debuginfod_add_http_header() ajoute un en-tête HTTP personnalisé à chaque requête HTTP effectuée par ce client. L'appelant est responsable de s'assurer que l'en-tête est correctement formaté. Les en-têtes multiples avec le même nom sont autorisés.

debuginfod_get_headers() renvoie une chaîne contenant tous les en-têtes HTTP personnalisés ajoutés via debuginfod_add_http_header(). La chaîne est terminée par un caractère nul et contient chaque en-tête sur une ligne séparée. La chaîne renvoyée est un pointeur vers une chaîne statique et ne doit pas être modifiée ni libérée.

ENVIRONNEMENT

Le comportement de ces fonctions est affecté par la variable d'environnement suivante :

$DEBUGINFOD_URLS
Une liste d'URL de serveurs debuginfod séparées par des espaces ou des virgules, ou par des nouvelles lignes. Les URL peuvent être préfixées par un nom pour le serveur, suivi de deux-points, par exemple: myarchive:http://archive.example.com/debuginfod. Si ce n'est pas défini, alors les URL par défaut suivantes sont utilisées: https://debuginfod.elfutils.org.
$DEBUGINFOD_MAX_RETRIES
Le nombre maximal de nouvelles tentatives à effectuer pour une requête donnée. La valeur par défaut est 10.
$DEBUGINFOD_CLIENT_TIMEOUT
Délai d'attente en secondes pour les requêtes HTTP. La valeur par défaut est 30.
$DEBUGINFOD_CACHE_DIR
Le répertoire à utiliser pour la mise en cache des fichiers téléchargés. Si ce n'est pas défini, le répertoire par défaut est utilisé (typiquement $HOME/.cache/debuginfod).
$DEBUGINFOD_NB_THREADS
Le nombre de threads à utiliser pour les requêtes parallèles. La valeur par défaut est 4.

HTTP

Avant chaque fonction de recherche, une application client peut ajouter des en-têtes de requête HTTP. Ceux-ci sont réinitialisés après chaque fonction de recherche. debuginfod_add_http_header() peut être appelée avec des chaînes de la forme "Header: value". Ces chaînes sont copiées par la bibliothèque. Une valeur de retour nulle indique le succès, mais des conditions de manque de mémoire peuvent entraîner une valeur non nulle -ENOMEM. Si la chaîne est sous la mauvaise forme -EINVAL sera

retourné.

$DEBUGINFOD_HEADERS_FILE spécifie un fichier fournissant des en-têtes aux requêtes sortantes. Chaque ligne non blanche de ce fichier est traitée comme si debuginfod_add_http_header() était appelée sur son

contenu.

Notez que l'implémentation actuelle de la bibliothèque debuginfod-client utilise libcurl, mais vous ne devriez pas vous fier à ce fait. N'utilisez pas cette fonction pour remplacer des en-têtes standards, à l'exception du User-Agent mentionné ci-dessous. Vous pouvez utiliser cette fonction pour ajouter des informations d'autorisation pour le contrôle d'accès, ou pour fournir des en-têtes optionnels au serveur à des fins de

journalisation.

Par défaut, la bibliothèque ajoute un User-Agent: descriptif aux requêtes sortantes. Si l'application client ajoute un en-tête du même nom, cette valeur par défaut est

supprimée.

Pendant ou après une recherche, une application client peut appeler debuginfod_get_headers() pour recueillir le sous-ensemble des en-têtes de réponse HTTP reçus du serveur debuginfod actuel ou le plus récent. Seuls les en-têtes préfixés par X-DEBUGINFOD (insensible à la casse) sont conservés. Ils sont retournés sous forme d'une chaîne unique, chaque "header: value" étant terminé par un \n (et non \r\n

comme dans HTTP). Elle peut être NULL. La chaîne résultante appartient à la bibl

CACH

E

Avant chaque requête, la bibliothèque client debuginfod vérifie s'il est nécessaire de nettoyer le cache. S'il est temps de nettoyer, la bibliothèque parcourt le répertoire de cache et supprime les téléchargementsed debuginfo-related artifacts and newly empty directories, if they have not been accessed

recently.

Les fichiers de contrôle sont situés directement dans le répertoire de cache. Ils contiennent des nombres décimaux simples pour définir les paramètres de configuration liés au cache. Si les fichiers n'existent pas, la bibliothèque client crée les fichiers avec les valeurs par défaut des paramètres comme

contenu.

Après chaque requête, la bibliothèque client debuginfod dépose les fichiers nouvellement reçus dans un répertoire et un fichier dont le nom est basé sur le build-id. Une requête échouée est également mise en cache par un fichier spécial. La convention de nommage utilisée pour ces artefacts est délibérément non docume
