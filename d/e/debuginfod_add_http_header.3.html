DESCRIPTIO

N

debuginfod_begin() crée un debuginfod_client pointeur de connexion qui doit être utilisé avec tous les autres appels. debuginfod_end() doit être appelé sur le pointeur client pour libérer tout l'état et le stockage lorsque vous avez

terminé.

debuginfod_find_debuginfo(), debuginfod_find_executable() et debuginfod_find_source() interrogent les URL des serveurs debuginfod contenues dans $DEBUGINFOD_URLS (voir ci-dessous) pour le debuginfo, l'exécutable ou le fichier source avec le build_id donné. build_id doit être un pointeur vers soit une chaîne hexadécimale minuscule terminée par un caractère nul, soit un bloc binaire. Si build_id est donné sous forme de chaîne hexadécimale, build_id_len doit être 0. Sinon build_id_len doit être le nombre d'octets du bloc

binaire.

debuginfod_find_source() exige également un filename afin de spécifier un fichier source particulier. filename doit être un chemin absolu qui inclut le répertoire de compilation de l'unité de compilation (CU) associée au fichier source. Les chemins relatifs apparaissent couramment dans le répertoire source du fichier DWARF, mais ces chemins sont relatifs aux chemins AT_comp_dir des unités de compilation individuelles, et pourtant un exécutable est composé de plusieurs CU. Par conséquent, pour lever l'ambiguïté, debuginfod attend que les requêtes de source préfixent les chemins relatifs par le répertoire de compilation de la CU, suivi d'un "/"

obligatoire.

Remarque : l'appelant peut ou non omettre ../ ou /./ ou des composants de chemin /// superflus dans les noms de répertoires. debuginfod accepte les deux formes. Plus précisément, debuginfod canonifie les noms de chemin selon la section 5.2.4 de la RFC3986 (Remove Dot Segments), et réduit également tout // en / dans le

chemin.

debuginfod_find_section() interroge les URL des serveurs debuginfod contenues dans $DEBUGINFOD_URLS pour le contenu binaire d'une section ELF/DWARF contenue dans un fichier debuginfo ou exécutable avec le build_id donné. section doit être le nom de la section ELF/DWARF souhaitée. Si un serveur ne prend pas en charge les requêtes de section, debuginfod_find_section peut interroger le serveur pour le debuginfo et/ou l'exécutable avec build_id afin de récupérer et d'extraire la

section.

debuginfod_find_metadata() interroge toutes les URL des serveurs debuginfod contenues dans $DEBUGINFOD_URLS pour les métadonnées de toutes les correspondances d'une requête clé/valeur donnée sur les fichiers de leurs index. Le fichier résultant est un document JSON. Voir la page man debuginfod-find(1) pour des exemples des types de requêtes clé/valeur pris en charge et de leurs résultats

JSON.

Si path n'est pas NULL et que la requête réussit, path est défini sur le chemin du fichier dans le cache. L'appelant doit free() cette

valeur.

Les URL dans $DEBUGINFOD_URLS peuvent être interrogées en parallèle. Dès qu'un serveur debuginfod commence à transférer le fichier cible, toutes les connexions aux autres serveurs sont

fermées.

Un pointeur client ne doit être utilisé que par un seul thread à la fois. Un pointeur peut être réutilisé pour une sé

rie de recherches, ce qui peut améliorer les performance
s grâce à la conservation des connexions et des caches.

VALEUR DE

RETOUR

debuginfod_begin retourne le pointeur debuginfod_client à utiliser avec tous les autres appels. En cas d'erreur NULL sera retourné et errno sera

défini.

Si une fonction de la famille find réussit, le fichier résultant est enregistré dans le cache du client et un descripteur de fichier vers ce fichier est retourné. Le descripteur de fichier pointe vers le début du fichier. L'appelant doit close() ce descripteur. Sinon, un co

de d'erreur nég
atif est retourné.

FONCTIONS

FACULTATIVES

Un petit nombre de fonctions facultatives sont disponibles pour régler ou interroger le fonctionnement du client

debuginfod.

RAPPEL DE

PROGRESSION

Comme les fonctions debuginfod_find_*() peuvent bloquer pendant des secondes ou plus, une fonction de rappel de progression est appelée périodiquement, si configurée avec debuginfod_set_progressfn(). Cette fonction définit une nouvelle fonction de rappel de progression (ou NULL) pour le pointeur

client.

La fonction de rappel donnée est appelée depuis le contexte de chaque thread qui invoque l'une des autres fonctions de recherche. Elle reçoit deux paramètres numériques qui, si on les considère comme un numérateur a et un dénominateur b, représentent ensemble une fraction d'achèvement a/b. Le dénominateur peut être zéro au début, jusqu'à ce qu'une quantité telle qu'une taille de téléchargement exacte devienne

connue.

La fonction de rappel de progression est également la manière prise en charge d' interrompre l'opération de téléchargement. (La bibliothèque ne modifie pas ou ne déclenche pas de signaux.) Le rappel de progression doit retourner 0 pour continuer le travail, ou toute autre valeur pour arrêter le travail dès que possible. Par conséquent, la fonction debuginfod_find_*() retournera probablement a

vec une erreur, mais p
ourrait quand même réussir.

SORTIE

VERBEUSE

Les fonctions debuginfod_find_*() peuvent utiliser plusieurs techniques pour récupérer les fichiers demandés, via le cache ou via un ou plusieurs serveurs ou URL de fichiers. Pour montrer comment une requête est traitée, la fonction debuginfod_set_verbose_fd() peut être utilisée pour définir un descripteur de fichier particulier sur lequel u

ne sortie verbeuse est donnée concernant les étapes
de la requête et les erreurs éventuelles rencontrées.

EN-TÊTE

HTTP

Avant que chaque fonction de recherche ne soit initiée, une application client peut ajouter des en-têtes de requête HTTP. Ceux-ci sont réinitialisés après chaque fonction de recherche. debuginfod_add_http_header() peut être appelée avec des chaînes de la forme "Header: value". Ces chaînes sont copiées par la bibliothèque. Une valeur de retour nulle indique le succès, mais des conditions de manque de mémoire peuvent entraîner une valeur non nulle -ENOMEM. Si la chaîne est sous la mauvaise forme -EINVAL sera

renvoyé.

$DEBUGINFOD_HEADERS_FILE spécifie un fichier servant à fournir des en-têtes aux requêtes sortantes. Chaque ligne non blanche de ce fichier est traitée comme si debuginfod_add_http_header() était appelée sur son

contenu.

Notez que l'implémentation actuelle de la bibliothèque debuginfod-client utilise libcurl, mais vous ne devriez pas vous fier à ce fait. N'utilisez pas cette fonction pour remplacer des en-têtes standards, à l'exception de User-Agent mentionné ci-dessous. Vous pouvez utiliser cette fonction pour ajouter des informations d'autorisation pour le contrôle d'accès, ou pour fournir des en-têtes optionnels au serveur à des fins de

journalisation.

Par défaut, la bibliothèque ajoute un User-Agent: descriptif aux requêtes sortantes. Si l'application client ajoute un en-tête portant le même nom, cette valeur par défaut est

supprimée.

Pendant ou après une recherche, une application client peut appeler debuginfod_get_headers() pour recueillir le sous-ensemble des en-têtes de réponse HTTP reçus du serveur debuginfod actuel ou le plus récent. Seuls les en-têtes préfixés par X-DEBUGINFOD (insensible à la casse) sont conservés. Ils sont renvoyés sous forme d'une chaîne unique, chaque "header: value" étant terminée par un \n (et non \r

\n comme dans HTTP). Elle peut être NULL. La chaîne résultante appartient à la b
ibliothèque et ne doit pas être modifiée ni libérée. L'appelant doit copier la ch
aîne renvoyée si elle est nécessaire au-delà de la libération de l'objet client.

SÉCURIT

É

Si des signature(s) IMA sont disponibles à partir des RPM contenant les fichiers demandés, alors debuginfod extraira ces signatures dans les en-têtes de réponse, et debuginfod_find_*() effectuera la vérification sur les fichiers. La politique de validation est contrôlée via des balises insérées dans $DEBUGINFOD_URLS. Par défaut, debuginfod_find_*() agit en mode

ignore.

Si l'accès se fait via HTTP plutôt que HTTPS, le réseau devrait être digne de confiance. L'authentification via la bibliothèque interne libcurl n'est actuellement pas activée, à l'exception du style basique en texte clair http[s]://userid:password@hostname/. (Le serveur debuginfod n'effectue pas d'

authentification, mais un serveur proxy d
e premier niveau pourrait le faire.)

Cette variable d'environnement contient une liste de préfixes d'URL pour les instances debuginfod de confiance. Les préfixes d'URL alternatifs sont séparés par des espaces. Cette variable d'environnement peut être définie par des scripts /etc/profile.d lisant les fichiers /etc/debuginfod/*.urls.

org"

CACH

E

Avant chaque requête, la bibliothèque client debuginfod vérifie la nécessité de nettoyer le cache. S'il est temps de nettoyer, la bibliothèque parcourt le répertoire de cache et supprimeves téléchargés liés au debuginfo et les répertoires devenus vides, s'ils n'ont pas été accédés

récemment.

Les fichiers de contrôle sont situés directement sous le répertoire de cache. Ils contiennent des nombres décimaux simples pour définir les paramètres de configuration liés au cache. Si les fichiers n'existent pas, la bibliothèque client crée les fichiers avec les valeurs de paramètres par défaut comme

contenu.

Après chaque requête, la bibliothèque client debuginfod dépose les fichiers nouvellement reçus dans un répertoire et un fichier dont le nom est basé sur le build-id. Une requête échouée est également mise en cache par un fichier spécial. La convention de nommage utilisée pour ces artefacts est délibérément non docume

ntée.
