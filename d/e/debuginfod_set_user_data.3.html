NOM

debuginfod_find_debuginfo - demander des informations de débogage à debuginfod

SYNOPSIS

#include <elfutils/debuginfod.h>
Lier avec -ldebuginfod.

DESCRIPTION

debuginfod_begin() crée un handle de connexion debuginfod_client qui doit être utilisé avec tous les autres appels. debuginfod_end() doit être appelé sur le handle client pour libérer tout état et stockage lorsque vous avez terminé.

debuginfod_find_debuginfo(), debuginfod_find_executable() et debuginfod_find_source() interrogent les serveurs debuginfod dont les URLs sont contenues dans $DEBUGINFOD_URLS (voir ci-dessous) pour les informations de débogage, l'exécutable ou le fichier source avec le build_id donné. build_id doit pointer soit vers une chaîne hexadécimale binaire se terminant par null, soit vers un blob binaire. Si build_id est donné sous forme de chaîne hexadécimale, build_id_len doit être 0. Sinon, build_id_len doit être le nombre d'octets dans le blob binaire.

debuginfod_find_source() nécessite également un filename afin de spécifier un fichier source particulier. filename doit être un chemin absolu incluant le répertoire de compilation de l'unité de compilation (CU) associée au fichier source. Les chemins relatifs apparaissent couramment dans le répertoire source du fichier DWARF, mais ces chemins sont relatifs aux chemins AT_comp_dir individuels des unités de compilation, et pourtant un exécutable est composé de plusieurs CU. Par conséquent, pour désambiguïser, debuginfod attend que les requêtes de sources préfixent les noms de chemins relatifs avec le répertoire de compilation de la CU, suivi d'un "/" obligatoire.

Note : l'appelant peut ou non élider les composants de chemin tels que ../ ou /./ ou /// superflus dans les noms de répertoires. debuginfod accepte les deux formes. Spécifiquement, debuginfod canonise les noms de chemins conformément à la RFC3986 section 5.2.4 (Supprimer les segments de points), plus la réduction de tout // à / dans le chemin.

debuginfod_find_section() interroge les URLs des serveurs debuginfod contenues dans $DEBUGINFOD_URLS pour les contenus binaires d'une section ELF/DWARF contenue dans un fichier de débogage ou exécutable avec le build_id donné. section doit être le nom de la section ELF/DWARF désirée. Si un serveur ne prend pas en charge les requêtes de sections, debuginfod_find_section peut interroger le serveur pour les informations de débogage et/ou l'exécutable avec build_id afin de récupérer et d'extraire la section.

debuginfod_find_metadata() interroge toutes les URLs des serveurs debuginfod contenues dans $DEBUGINFOD_URLS pour les métadonnées de toutes les correspondances d'une requête clé/valeur donnée contre les fichiers dans leurs index. Le fichier résultant est un document JSON. Voir la page man debuginfod-find(1) pour des exemples des types de requêtes clé/valeur pris en charge et de leurs résultats JSON.

Si path n'est pas NULL et que la requête réussit, path est défini sur le chemin du fichier dans le cache. L'appelant doit libérer cette valeur avec free().

Les URLs dans $DEBUGINFOD_URLS peuvent être interrogées en parallèle. Dès qu'un serveur debuginfod commence à transférer le fichier cible, toutes les connexions aux autres serveurs sont fermées.

Un handle client ne doit être utilisé que par un seul fil d'exécution à la fois. Un handle peut être réutilisé pour une série de recherches, ce qui peut améliorer les performances en raison de la conservation des connexions et des caches.

VALEUR DE RETOUR

debuginfod_begin retourne le handle debuginfod_client à utiliser avec tous les autres appels. En cas d'erreur, NULL sera retourné et errno sera défini.

Si une fonction de la famille find réussit, le fichier résultant est sauvegardé dans le cache du client et un descripteur de fichier vers ce fichier est retourné. Le descripteur de fichier pointe vers le début du fichier. L'appelant doit fermer ce descripteur avec close(). Sinon, un code d'erreur négatif est retourné.

FONCTIONS OPTIONNELLES

Un petit nombre de fonctions optionnelles sont disponibles pour ajuster ou interroger le fonctionnement du client debuginfod.

CALLEBACK DE PROGRÈS

Comme les fonctions debuginfod_find_*() peuvent bloquer pendant des secondes ou plus, une fonction de rappel de progression est appelée périodiquement, si elle est configurée avec debuginfod_set_progressfn(). Cette fonction définit une nouvelle fonction de rappel de progression (ou NULL) pour le handle client.

La fonction de rappel donnée est appelée depuis le contexte de chaque fil d'exécution qui invoque l'une des autres fonctions de recherche. Elle reçoit deux paramètres numériques qui, considérés comme un numérateur a et un dénominateur b, représentent ensemble une fraction d'achèvement a/b. Le dénominateur peut être zéro initialement, jusqu'à ce qu'une quantité telle qu'une taille de téléchargement exacte soit connue.

La fonction de rappel de progression est également la manière prise en charge pour *interrompre* l'opération de téléchargement. (La bibliothèque ne modifie ni ne déclenche de signaux.) La fonction de rappel de progression doit retourner 0 pour continuer le travail, ou toute autre valeur pour arrêter le travail dès que possible. Par conséquent, la fonction debuginfod_find_*() retournera probablement avec une erreur, mais pourrait encore réussir.

SORTIE VERBEUSE

Les fonctions debuginfod_find_*() peuvent utiliser plusieurs techniques pour récupérer les fichiers demandés, via le cache ou via un ou plusieurs serveurs ou URLs de fichiers. Pour montrer comment une requête est traitée, debuginfod_set_verbose_fd() peut être utilisé pour définir un descripteur de fichier particulier sur lequel des sorties verbeuses sont fournies concernant les étapes de la requête et les erreurs éventuelles rencontrées.

POINTEUR DONNÉES UTILISATEUR

Un unique pointeur void * associé au handle de connexion peut être défini à tout moment via debuginfod_set_user_data(), et récupéré via debuginfod_get_user_data(). La valeur n'est pas définie si elle n'est pas définie.

URL ACTUELLE

La fonction debuginfod_get_url() retourne l'URL du serveur debuginfod qui a été utilisé pour la requête la plus récente. Si aucune URL n'a été trouvée, elle retourne NULL.

EN-TÊTE HTTP

La fonction debuginfod_add_http_header() ajoute un en-tête HTTP personnalisé à chaque requête HTTP envoyée par le client debuginfod. Ceci est utile pour passer des informations d'authentification ou d'autres métadonnées au serveur debuginfod. Les en-têtes ajoutés sont ensuite accessibles via debuginfod_get_headers(), qui retourne un chemin vers un fichier contenant tous les en-têtes envoyés.

VARIABLE D'ENVIRONNEMENT

La variable d'environnement $DEBUGINFOD_URLS peut être utilisée pour spécifier une liste d'URLs de serveurs debuginfod à interroger. Les URLs doivent être séparées par des espaces. Si cette variable n'est pas définie, une liste d'URLs par défaut est utilisée.

URL

L'URL du téléchargement sortant en cours ou le plus récent, si connu, peut être récupéré via debuginfod_get_url() à partir de la fonction de rappel de progression (progressfn), ou après. Il peut être NULL. La chaîne résultante appartient à la bibliothèque et ne doit pas être modifiée ou libérée. L'appelant doit la copier si elle est nécessaire au-delà de la libération de l'objet client.

EN-TÊTE HTTP

Avant chaque fonction de recherche, une application cliente peut ajouter des en-têtes de requête HTTP. Ceux-ci sont réinitialisés après chaque fonction de recherche. debuginfod_add_http_header() peut être appelée avec des chaînes de la forme "En-tête : valeur". Ces chaînes sont copiées par la bibliothèque. Une valeur de retour nulle indique le succès, mais les conditions de manque de mémoire peuvent entraîner un -ENOMEM non nul. Si la chaîne est mal formée, -EINVAL sera retourné.

$DEBUGINFOD_HEADERS_FILE spécifie un fichier pour fournir des en-têtes aux requêtes sortantes. Chaque ligne non blanche de ce fichier est traitée comme si debuginfod_add_http_header() avait été appelée sur son contenu.

Notez que l'implémentation actuelle de la bibliothèque debuginfod-client utilise libcurl, mais vous ne devriez pas vous fier à ce fait. N'utilisez pas cette fonction pour remplacer des en-têtes standard, à l'exception de l'User-Agent mentionné ci-dessous. Vous pouvez utiliser cette fonction pour ajouter des informations d'authentification pour le contrôle d'accès, ou pour fournir des en-têtes facultatifs au serveur à des fins de journalisation.

Par défaut, la bibliothèque ajoute un en-tête descriptif User-Agent: aux requêtes sortantes. Si l'application cliente ajoute un en-tête du même nom, cette valeur par défaut est supprimée.

Pendant ou après une recherche, une application cliente peut appeler debuginfod_get_headers() pour collecter le sous-ensemble des en-têtes de réponse HTTP reçus du serveur debuginfod actuel ou le plus récent. Seuls les en-têtes préfixés par X-DEBUGINFOD (insensible à la casse) sont conservés. Ils sont retournés sous forme d'une seule chaîne, chaque "en-tête : valeur" étant terminé par un \n (et non \r\n comme en HTTP). Il peut être NULL. La chaîne résultante appartient à la bibliothèque et ne doit pas être modifiée ou libérée. L'appelant doit copier la chaîne retournée si elle est nécessaire au-delà de la libération de l'objet client.

MACROS

DEBUGINFOD_SONAME

Défini à la chaîne qui pourrait être passée à dlopen(3) si la bibliothèque est chargée à l'exécution, par exemple


void *debuginfod_so = dlopen(DEBUGINFOD_SONAME, RTLD_LAZY);

SÉCURITÉ

Si des signatures IMA sont disponibles à partir des RPM qui contiennent les fichiers demandés, alors debuginfod extraira ces signatures dans des en-têtes de réponse, et debuginfod_find_*() effectuera une vérification sur les fichiers. La politique de validation est contrôlée via des balises insérées dans $DEBUGINFOD_URLS. Par défaut, debuginfod_find_*() fonctionne en mode d'ignorance.

Si l'accès se fait via HTTP plutôt que HTTPS, le réseau doit être digne de confiance. Les informations d'authentification via la bibliothèque interne libcurl ne sont actuellement pas activées, à l'exception du style de base en texte brut http[s]://userid:password@hostname/. (Le serveur debuginfod n'effectue pas d'authentification, mais un serveur proxy frontal pourrait le faire.)

ERREURS

La liste suivante n'est pas exhaustive. Des codes d'erreur peuvent également provenir d'appels à diverses fonctions de la bibliothèque C.

EACCESS
Accès refusé à la ressource située à l'URL.
ECONNREFUSED
Impossible de se connecter à l'hôte distant. Également retourné lorsqu'une connexion HTTPS n'a pas pu être vérifiée (certificat incorrect).
ECONNRESET
Impossible d'envoyer ou de recevoir des données réseau.
EHOSTUNREACH
Impossible de résoudre l'hôte distant.
EINVAL
Un ou plusieurs arguments sont mal formatés. build_id peut être trop long (supérieur à 256 caractères), filename peut ne pas être un chemin absolu ou une URL debuginfod est mal formée.
EIO
Impossible d'écrire les données reçues du serveur dans le fichier local.
EMLINK
Trop de redirections HTTP.
ENETUNREACH
Impossible d'initialiser la connexion réseau.
ENOENT
Impossible de trouver la ressource située à l'URL. Souvent, ce code d'erreur indique qu'un serveur debuginfod a été contacté avec succès mais que le serveur n'a pas trouvé le fichier cible.
ENOMEM
Le système ne parvient pas à allouer de ressources.
ENOSYS
$DEBUGINFOD_URLS n'est pas défini.
ETIME
La requête a échoué en raison d'un délai d'attente. $DEBUGINFOD_TIMEOUT et $DEBUGINFOD_MAXTIME contrôlent cela.
EF2BIG
La requête a été abandonnée car le fichier demandé était trop volumineux. Le $DEBUGINFOD_MAXSIZE contrôle cela.
EBADMSG
Le contenu du fichier n'a pas réussi la vérification IMA par rapport à un certificat de signataire connu.
ENOKEY
Le contenu du fichier n'a pas réussi la vérification IMA en raison d'un certificat de signataire manquant.
ENODATA
Le contenu du fichier n'a pas réussi la vérification IMA en raison d'une signature manquante.

VARIABLES D'ENVIRONNEMENT

$TMPDIR
Cette variable d'environnement pointe vers un système de fichiers à utiliser pour les fichiers temporaires. La valeur par défaut est /tmp.
$DEBUGINFOD_URLS
Cette variable d'environnement contient une liste de préfixes d'URL pour les instances debuginfod de confiance. Les préfixes d'URL alternatifs sont séparés par un espace. Cette variable d'environnement peut être définie par des scripts /etc/profile.d lisant les fichiers /etc/debuginfod/*.urls.

Cette variable d'environnement peut également contenir des politiques définissant des balises qui dictent la politique de réponse pour la vérification des signatures IMA par fichier dans les RPM. Comme la liste séparée par des espaces est lue de gauche à droite, lors de la rencontre d'une balise, les URL suivantes jusqu'à la prochaine balise seront traitées en utilisant cette politique spécifiée. Toutes les URL avant la première balise utiliseront la politique par défaut, ima:ignore. Par exemple :


DEBUGINFOD_URLS="https://foo.com ima:enforcing https://bar.ca http://localhost:8002/ ima:ignore https://baz.org"

Où foo.com et baz.org utilisent la politique par défaut ignore et bar.ca et localhost utilisent une politique enforcing. La balise de politique peut être l'une des suivantes :

ima:enforcing Chaque fichier téléchargé nécessite une signature valide, protégeant entièrement l'intégrité.
ima:ignore Ignore complètement la vérification, ne fournissant aucune protection.

Les alertes en cas d'échec de validation seront dirigées comme spécifié dans $DEBUGINFOD_VERBOSE.

$DEBUGINFOD_CACHE_PATH
Cette variable d'environnement régit l'emplacement du cache où sont conservés les fichiers téléchargés et les fichiers de contrôle de cache. Le répertoire par défaut est choisi en fonction d'autres variables d'environnement, voir ci-dessous.
$DEBUGINFOD_PROGRESS
Cette variable d'environnement régit la fonction de progression par défaut. Si elle est définie, et si une fonction de progression (progressfn) n'est pas explicitement définie, alors la bibliothèque configurera une fonction de progression par défaut. Cette fonction ajoutera périodiquement un message de progression simple à stderr. La valeur par défaut est aucune sortie de fonction de progression.
$DEBUGINFOD_VERBOSE
Cette variable d'environnement régit le descripteur de fichier par défaut pour la sortie verbeuse. Si elle est définie, et si un descripteur de fichier verbeux n'est pas explicitement défini, alors la sortie verbeuse sera produite sur STDERR_FILENO.
$DEBUGINFOD_RETRY_LIMIT
Cette variable d'environnement régit la limite par défaut des tentatives de nouvelle connexion. Si une requête a échoué avec un errno autre que ENOENT, plusieurs tentatives seront effectuées dans la limite.
$DEBUGINFOD_TIMEOUT
Cette variable d'environnement régit le délai d'attente de commencement du téléchargement pour chaque connexion HTTP debuginfod. Un serveur qui ne parvient pas à fournir au moins 100 Ko de données dans ce nombre de secondes est ignoré. La valeur par défaut est 90 secondes. (Zéro ou négatif signifie "pas de délai d'attente".)
$DEBUGINFOD_MAXTIME
Cette variable d'environnement dicte combien de temps le client attendra pour terminer le téléchargement d'un fichier trouvé sur un serveur, en secondes. Il est préférable de l'utiliser pour s'assurer qu'un fichier est téléchargé rapidement ou rejeté. La valeur par défaut est 0 (temps infini).
$DEBUGINFOD_MAXSIZE
Cette variable d'environnement dicte la taille maximale d'un fichier à télécharger en octets. Ceci est préférable si l'utilisateur souhaite s'assurer que seuls de petits fichiers sont téléchargés. Une valeur de 0 n'entraîne aucune prise en compte de la taille, et le client peut tenter de télécharger un fichier de n'importe quelle taille. La valeur par défaut est 0 (taille infinie).
$DEBUGINFOD_HEADERS_FILE
Cette variable d'environnement pointe vers un fichier qui fournit des en-têtes aux requêtes HTTP sortantes, un par ligne. Les lignes d'en-tête ne doivent pas se terminer par CRLF, sauf si c'est la convention de nouvelle ligne du système. Les lignes contenant uniquement des espaces sont ignorées.
$DEBUGINFOD_IMA_CERT_PATH
Cette variable d'environnement contient une liste de chemins de répertoires absolus contenant des certificats X.509 pour la vérification IMA par fichier des RPM. Les chemins alternatifs sont séparés par des deux-points.

CACHE

Avant chaque requête, la bibliothèque cliente debuginfod vérifie s'il est nécessaire de nettoyer le cache. S'il est temps de nettoyer, la bibliothèque parcourt le répertoire du cache et supprime

s téléchargés liés au debuginfo et les répertoires devenus vides, s'ils n'ont pas été accédés

récemment.

Les fichiers de contrôle sont situés directement sous le répertoire de cache. Ils contiennent de simples nombres décimaux pour définir les paramètres de configuration liés au cache. Si les fichiers n'existent pas, la bibliothèque client du cache crée les fichiers avec les valeurs par défaut des paramètres comme

contenu.

Après chaque requête, la bibliothèque client de debuginfod dépose les fichiers nouvellement reçus dans un répertoire et un fichier dont le nom est basé sur le build-id. Une requête échouée est également mise en cache par un fichier spécial. La convention de nommage utilisée pour ces artefacts est délibérément non docume

ntée.
