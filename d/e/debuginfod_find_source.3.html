DESCRIPTIO

N

debuginfod_begin() crée un debuginfod_client pointeur de connexion qui doit être utilisé avec tous les autres appels. debuginfod_end() doit être appelé sur le pointeur client pour libérer tout l'état et le stockage lorsque vous avez

terminé.

debuginfod_find_debuginfo(), debuginfod_find_executable() et debuginfod_find_source() interrogent les URL des serveurs debuginfod contenues dans $DEBUGINFOD_URLS (voir ci-dessous) pour le fichier debuginfo, exécutable ou source avec le build_id donné. build_id doit être un pointeur vers soit une chaîne hexadécimale en minuscules terminée par un caractère nul, soit un bloc binaire. Si build_id est donné sous forme de chaîne hexadécimale, build_id_len doit être 0. Sinon build_id_len doit être le nombre d'octets du bloc

binaire.

debuginfod_find_source() nécessite également un filename afin de spécifier un fichier source particulier. filename doit être un chemin absolu qui inclut le répertoire de compilation de l'unité de compilation (CU) associée au fichier source. Les noms de chemins relatifs apparaissent couramment dans le répertoire source du fichier DWARF, mais ces chemins sont relatifs aux chemins AT_comp_dir des unités de compilation individuelles, alors qu'un exécutable est composé de plusieurs CU. Par conséquent, pour lever l'ambiguïté, debuginfod attend que les requêtes de source préfixent les noms de chemins relatifs par le répertoire de compilation de la CU, suivi d'un "/"

obligatoire.

Remarque : l'appelant peut ou non omettre ../ ou /./ ou des composants de chemin /// superflus dans les noms de répertoires. debuginfod accepte les deux formes. Plus précisément, debuginfod canonifie les noms de chemins selon la section 5.2.4 de la RFC3986 (Remove Dot Segments), plus la réduction de tout // en / dans le

chemin.

debuginfod_find_section() interroge les URL des serveurs debuginfod contenues dans $DEBUGINFOD_URLS pour le contenu binaire d'une section ELF/DWARF contenue dans un fichier debuginfo ou exécutable avec le build_id donné. section doit être le nom de la section ELF/DWARF souhaitée. Si un serveur ne prend pas en charge les requêtes de section, debuginfod_find_section peut interroger le serveur pour le debuginfo et/ou l'exécutable avec build_id afin de récupérer et d'extraire la

section.

debuginfod_find_metadata() interroge toutes les URL des serveurs debuginfod contenues dans $DEBUGINFOD_URLS pour les métadonnées de toutes les correspondances d'une requête clé/valeur donnée sur les fichiers de leurs index. Le fichier résultant est un document JSON. Voir la page man debuginfod-find(1) pour des exemples des types de requêtes clé/valeur pris en charge et de leurs résultats

JSON.

Si path n'est pas NULL et que la requête réussit, path est défini sur le chemin du fichier dans le cache. L'appelant doit free() cette

valeur.

Les URL dans $DEBUGINFOD_URLS peuvent être interrogées en parallèle. Dès qu'un serveur debuginfod commence à transférer le fichier cible, toutes les connexions aux autres serveurs sont

fermées.

Un pointeur client ne doit être utilisé que par un seul thread à la fois. Un pointeur peut être réutilisé pour une sé

rie de recherches, ce qui peut améliorer les performance
s grâce à la conservation des connexions et des caches.

FONCTIONS

FACULTATIVES

Un petit nombre de fonctions facultatives sont disponibles pour régler ou interroger le fonctionnement du client

debuginfod.

RAPPEL DE

PROGRESSION

Étant donné que les fonctions debuginfod_find_*() peuvent bloquer pendant des secondes ou plus, une fonction de rappel de progression est appelée périodiquement, si configurée avec debuginfod_set_progressfn(). Cette fonction définit une nouvelle fonction de rappel de progression (ou NULL) pour le pointeur

client.

La fonction de rappel donnée est appelée depuis le contexte de chaque thread qui invoque l'une des autres fonctions de recherche. Elle reçoit deux paramètres numériques qui, si on les considère comme un numérateur a et un dénominateur b, représentent ensemble une fraction de progression a/b. Le dénominateur peut être zéro au début, jusqu'à ce qu'une quantité telle qu'une taille de téléchargement exacte devienne

connue.

La fonction de rappel de progression est également la manière prise en charge pour interrompre l'opération de téléchargement. (La bibliothèque ne modifie pas ou ne déclenche pas de signaux.) Le rappel de progression doit renvoyer 0 pour continuer le travail, ou toute autre valeur pour arrêter le travail dès que possible. Par conséquent, la fonction debuginfod_find_*() renverra probablement

une erreur, mais pou
rrait quand même réussir.

VERBEUSE

Pour montrer comment une requête est traitée, debuginfod_set_verbose_fd() peut être utilisé pour définir un descripteur de fichier particulier sur leque

l une sortie verbeuse est donnée sur les étapes de
la requête et les éventuelles erreurs rencontrées.

UTILISATEUR

Un seul pointeur void * associé au pointeur de connexion peut être défini à tout moment via debuginfod_set_user_data(), et récupéré via debuginfod_get_user_data(). La valeur est indéfinie

si elle n'es

URL

URL

L'URL du téléchargement sortant actuel ou le plus récent, s'il est connu, peut être récupéré via debuginfod_get_url() à partir du rappel progressfn, ou après. Il peut être NULL. La chaîne résultante appartient à la bibliothèque et ne doit pas être modifiée ou libérée. L'appelant doit la copier si elle est nécessaire au-delà de la libération de l'objet client.

EN-TÊTE HTTP

Avant que chaque fonction de recherche ne soit initiée, une application cliente peut ajouter des en-têtes de requête HTTP. Ceux-ci sont réinitialisés après chaque fonction de recherche. debuginfod_add_http_header() peut être appelé avec des chaînes de la forme "En-tête: valeur". Ces chaînes sont copiées par la bibliothèque. Une valeur de retour nulle indique le succès, mais des conditions de manque de mémoire peuvent entraîner un -ENOMEM non nul. Si la chaîne est dans la mauvaise forme, -EINVAL sera retourné.

$DEBUGINFOD_HEADERS_FILE spécifie un fichier pour fournir des en-têtes aux requêtes sortantes. Chaque ligne non blanche de ce fichier est traitée comme si debuginfod_add_http_header() avait été appelé sur son contenu.

Notez que l'implémentation actuelle de la bibliothèque debuginfod-client utilise libcurl, mais vous ne devriez pas vous fier à ce fait. N'utilisez pas cette fonction pour remplacer des en-têtes standard, à l'exception de l'User-Agent mentionné ci-dessous. Vous pouvez utiliser cette fonction pour ajouter des informations d'authentification pour le contrôle d'accès, ou pour fournir des en-têtes optionnels au serveur à des fins de journalisation.

Par défaut, la bibliothèque ajoute un en-tête descriptif User-Agent: aux requêtes sortantes. Si l'application cliente ajoute un en-tête du même nom, cette valeur par défaut est supprimée.

Pendant ou après une recherche, une application cliente peut appeler debuginfod_get_headers() pour collecter le sous-ensemble d'en-têtes de réponse HTTP reçus du serveur debuginfod actuel ou le plus récent. Seuls les en-têtes préfixés par X-DEBUGINFOD (insensible à la casse) sont conservés. Ils sont retournés sous forme d'une seule chaîne, chaque "en-tête: valeur" étant terminé par un \n (pas \r\n comme en HTTP). Il peut être NULL. La chaîne résultante appartient à la bibliothèque et ne doit pas être modifiée ou libérée. L'appelant doit copier la chaîne retournée si elle est nécessaire au-delà de la libération de l'objet client.

MACROS

DEBUGINFOD_SONAME

Défini avec la chaîne qui pourrait être passée à dlopen(3) si la bibliothèque est chargée à l'exécution, par exemple


void *debuginfod_so = dlopen(DEBUGINFOD_SONAME, RTLD_LAZY);

SÉCURITÉ

Si des signatures IMA sont disponibles à partir des RPM contenant les fichiers demandés, alors debuginfod extraira ces signatures dans des en-têtes de réponse, et debuginfod_find_*() effectuera une vérification sur les fichiers. La politique de validation est contrôlée via des balises insérées dans $DEBUGINFOD_URLS. Par défaut, debuginfod_find_*() agit en mode d'ignorance.

Si l'accès se fait via HTTP plutôt que HTTPS, le réseau doit être digne de confiance. Les informations d'authentification via la bibliothèque interne libcurl ne sont pas actuellement activées, à l'exception du style basique en texte clair http[s]://userid:password@hostname/. (Le serveur debuginfod n'effectue pas d'authentification, mais un serveur proxy frontal pourrait le faire.)

ERREURS

La liste suivante n'est pas exhaustive. Des codes d'erreur peuvent également provenir d'appels à diverses fonctions de la bibliothèque C.

EACCESS
Accès refusé à la ressource située à l'URL.
ECONNREFUSED
Impossible de se connecter à l'hôte distant. Retourné également lorsqu'une connexion HTTPS n'a pas pu être vérifiée (certificat invalide).
ECONNRESET
Impossible d'envoyer ou de recevoir des données réseau.
EHOSTUNREACH
Impossible de résoudre l'hôte distant.
EINVAL
Un ou plusieurs arguments sont mal formatés. build_id peut être trop long (supérieur à 256 caractères), filename peut ne pas être un chemin absolu ou une URL debuginfod est mal formée.
EIO
Impossible d'écrire les données reçues du serveur dans le fichier local.
EMLINK
Trop de redirections HTTP.
ENETUNREACH
Impossible d'initialiser la connexion réseau.
ENOENT
Impossible de trouver la ressource située à l'URL. Souvent, ce code d'erreur indique qu'un serveur debuginfod a été contacté avec succès mais que le serveur n'a pas trouvé le fichier cible.
ENOMEM
Le système est incapable d'allouer des ressources.
ENOSYS
$DEBUGINFOD_URLS n'est pas défini.
ETIME
La requête a échoué en raison d'un délai d'attente. $DEBUGINFOD_TIMEOUT et $DEBUGINFOD_MAXTIME contrôlent cela.
EF2BIG
La requête a été interrompue car le fichier demandé était trop volumineux. Le $DEBUGINFOD_MAXSIZE contrôle cela.
EBADMSG
Le contenu du fichier a échoué à la vérification IMA par rapport à un certificat signataire connu.
ENOKEY
Le contenu du fichier a échoué à la vérification IMA en raison d'un certificat signataire manquant.
ENODATA
Le contenu du fichier a échoué à la vérification IMA en raison d'une signature manquante.

VARIABLES D'ENVIRONNEMENT

$TMPDIR
Cette variable d'environnement pointe vers un système de fichiers à utiliser pour les fichiers temporaires. La valeur par défaut est /tmp.
$DEBUGINFOD_URLS
Cette variable d'environnement contient une liste de préfixes d'URL pour les instances debuginfod de confiance. Les préfixes d'URL alternatifs sont séparés par un espace. Cette variable d'environnement peut être définie par des scripts /etc/profile.d lisant les fichiers /etc/debuginfod/*.urls.

Cette variable d'environnement peut également contenir une politique définissant des balises qui dictent la politique de réponse pour la vérification des signatures IMA par fichier dans les RPM. Comme la liste séparée par des espaces est lue de gauche à droite, lors de la rencontre d'une balise, les URL suivantes jusqu'à la prochaine balise seront traitées en utilisant cette politique spécifiée. Toutes les URL avant la première balise utiliseront la politique par défaut, ima:ignore. Par exemple :


DEBUGINFOD_URLS="https://foo.com ima:enforcing https://bar.ca http://localhost:8002/ ima:ignore https://baz.org"

Où foo.com et baz.org utilisent la politique par défaut ignore et bar.ca et localhost utilisent une politique enforcing. La balise de politique peut être l'une des suivantes :

ima:enforcing Chaque fichier téléchargé nécessite une signature valide, protégeant ainsi pleinement l'intégrité.
ima:ignore Ignore complètement la vérification, n'offrant aucune protection.

Les alertes d'échec de validation seront dirigées comme spécifié dans $DEBUGINFOD_VERBOSE.

$DEBUGINFOD_CACHE_PATH
Cette variable d'environnement régit l'emplacement du cache où sont conservés les fichiers téléchargés et les fichiers de contrôle de cache. Le répertoire par défaut est choisi en fonction d'autres variables d'environnement, voir ci-dessous.
$DEBUGINFOD_PROGRESS
Cette variable d'environnement régit la fonction de progression par défaut. Si elle est définie, et si une fonction de progression n'est pas explicitement définie, alors la bibliothèque configurera une fonction de progression par défaut. Cette fonction ajoutera périodiquement un message de progression simple à stderr. Par défaut, aucune sortie de fonction de progression n'est générée.
$DEBUGINFOD_VERBOSE
Cette variable d'environnement régit le descripteur de fichier par défaut pour la sortie détaillée. Si elle est définie, et si un descripteur de fichier détaillé n'est pas explicitement défini, alors la sortie détaillée sera produite sur STDERR_FILENO.
$DEBUGINFOD_RETRY_LIMIT
Cette variable d'environnement régit la limite par défaut des tentatives de réessai. Si une requête échoue avec un errno autre que ENOENT, plusieurs tentatives seront initiées dans la limite.
$DEBUGINFOD_TIMEOUT
Cette variable d'environnement régit le délai d'attente de démarrage du téléchargement pour chaque connexion HTTP debuginfod. Un serveur qui ne parvient pas à fournir au moins 100 Ko de données dans ce nombre de secondes est ignoré. La valeur par défaut est de 90 secondes. (Zéro ou négatif signifie "pas de délai d'attente".)
$DEBUGINFOD_MAXTIME
Cette variable d'environnement détermine combien de temps le client attendra pour terminer le téléchargement d'un fichier trouvé sur un serveur, en secondes. Il est préférable de l'utiliser pour s'assurer qu'un fichier est téléchargé rapidement ou rejeté. La valeur par défaut est 0 (temps infini).
$DEBUGINFOD_MAXSIZE
Cette variable d'environnement détermine la taille maximale d'un fichier à télécharger en octets. Il est préférable de l'utiliser si l'utilisateur souhaite s'assurer que seuls des fichiers de petite taille sont téléchargés. Une valeur de 0 ne tient pas compte de la taille, et le client peut tenter de télécharger un fichier de n'importe quelle taille. La valeur par défaut est 0 (taille infinie).
$DEBUGINFOD_HEADERS_FILE
Cette variable d'environnement pointe vers un fichier qui fournit des en-têtes pour les requêtes HTTP sortantes, un par ligne. Les lignes d'en-tête ne doivent pas se terminer par CRLF, à moins que ce ne soit la convention de nouvelle ligne du système. Les lignes contenant uniquement des espaces sont ignorées.
$DEBUGINFOD_IMA_CERT_PATH
Cette variable d'environnement contient une liste de chemins de répertoires absolus contenant des certificats X.509 pour la vérification IMA par fichier des RPM. Les chemins alternatifs sont séparés par des deux-points.

NAME

debuginfod_find_source, debuginfod_find_debuginfo — retrieve debug information and source files from debuginfod servers

LIBRARY

debuginfod client library (libdebuginfod, -ldebuginfod)

SYNOPSIS

#include <debuginfod.h>

char *
debuginfod_find_source(const char *build_id, size_t build_id_len);

char *
debuginfod_find_debuginfo(const char *build_id, size_t build_id_len);

DESCRIPTION

The <code>debuginfod</code> client library is used to download debug information and source files from remote servers.

The library uses a cache directory to store downloaded files. The cache directory is determined by the environment variables <code>$XDG_CACHE_HOME</code> and <code>$HOME</code>. If <code>$XDG_CACHE_HOME</code> is set, the cache directory is <code>$XDG_CACHE_HOME/debuginfod_client/</code>. Otherwise, it is <code>$HOME/.cache/debuginfod_client/</code>. A deprecated cache directory <code>$HOME/.debuginfod_client_cache/</code> is also supported if it already exists.

The library can be configured using control files in the cache directory. These files contain simple decimal numbers to set cache-related configuration parameters.

The cache directory is cleaned periodically to remove old and unused files. The cleaning process removes downloaded debuginfo-related artifacts and newly empty directories, if they have not been accessed recently.

Control files are located directly under the cache directory. They contain simple decimal numbers to set cache-related configuration parameters. If the files do not exist, the client library creates the files with the default parameter values as content.

After each query, the debuginfod client library deposits newly received files into a directory & file that is named based on the build-id. A failed query is also cached by a special file. The naming convention used for these artifacts is deliberately undocumented.

$XDG_CACHE_HOME/debuginfod_client/
Default cache directory, if $XDG_CACHE_HOME is set.
$HOME/.cache/debuginfod_client/
Default cache directory, if $XDG_CACHE_HOME is not set.
$HOME/.debuginfod_client_cache/
Deprecated cache directory, used only if preexisting.
cache_clean_interval_s
This control file gives the interval between cache cleaning rounds, in seconds. The default is 86400, one day. 0 means "immediately".
max_unused_age_s
This control file sets how long unaccessed debuginfo-related files are retained, in seconds. The default is 604800, one week. 0 means "immediately".
cache_miss_s
This control file sets how long to remember a query failure, in seconds. New queries for the same artifacts within this time window are short-circuited (returning an immediate failure instead of sending a new query to servers). This accelerates queries that probably would still fail. The default is 600, 10 minutes. 0 means "forget immediately".
metadata_retention_s
This control file sets how long to remember the results of a metadata query. New queries for the same artifacts within this time window are short-circuited (repeating the same results). This accelerates queries that probably would probably have the same results. The default is 3600, 1 hour. 0 means "do not retain".

RETURN VALUE

On success, both functions return a pointer to a newly allocated string containing the path to the downloaded file. The caller is responsible for freeing this string using free(3).

On failure, both functions return NULL, and errno is set appropriately.
