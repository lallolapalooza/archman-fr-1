DESCRIPTIO

N

Ce module fournit des métriques de couverture de code pour Perl. Les métriques de couverture de code décrivent dans quelle mesure les tests exercent le code. En utilisant Devel::Cover, vous pouvez découvrir les zones de code non exercées par vos tests et déterminer quels tests créer pour augmenter la couverture. La couverture de code peut être considérée comme une mesure indirecte de la

qualité.

Devel::Cover est désormais assez stable et fournit de nombreuses des fonctionnalités que l'on attend d'un outil de couverture

utile.

Les informations de couverture des instructions, des branches, des conditions, des sous-routines et du pod sont rapportées. Les données de couverture des instructions et des sous-routines devraient être précises. Les données de couverture des branches et des conditions devraient être également en grande partie précises, bien que pas toujours ce que l'on pourrait s'attendre initialement. La couverture du pod provient de Pod::Coverage. Si Pod::Coverage::CountParents est disponible, il sera utilisé à la

place.

Le programme cover peut être utilisé pour générer des rapports de couverture. Devel::Cover est livré avec un certain nombre de rapports, y compris divers types de sorties HTML, des rapports textuels, un rapport pour afficher la couverture manquante dans le même format que les erreurs de compilation et un rapport pour afficher les informations de couverture dans l'éditeur

Vim.

Il est possible d'ajouter des annotations aux rapports, par exemple vous pouvez ajouter une colonne à un rapport HTML montrant qui a changé une ligne en dernier, tel que déterminé par git blame. Certains modules d'annotation sont livrés avec Devel::Cover et vous pouvez facilement créer les

vôtres.

Le programme gcov2perl peut être utilisé pour convertir les fichiers gcov en bases de données "Devel::Cover". Cela vous permet d'afficher la couverture de votre code C ou XS avec votre couverture Perl, ou d'utiliser n'importe lequel des rapports Devel::Cover pour afficher vos données de couverture

C.

Les données de couverture de code sont collectées en remplaçant les opérations perl par des fonctions qui comptent combien de fois les opérations sont exécutées. Ces données sont ensuite mappées à la réalité en utilisant les modules compilateurs B. Il existe également une fonctionnalité de profilage des instructions qui ne doit pas être utilisée de manière fiable. Pour un profilage approprié, utilisez Devel::NYTProf. Les versions précédentes de Devel::Cover collectaient les données de couverture en remplaçant la fonction runops de perl. Il est toujours possible de basculer dans ce mode de fonctionnement, mais il est désormais peu testé et sera probablement bientôt supprimé. Vous ne vous souciez probablement de rien de tout

cela.

La liste de diffusion la plus appropriée pour discuter de ce module serait perl-qa. Voir https://lists.perl.org/list

/perl-qa.html.

Vous pouvez spécifier des options pour certains critères de couverture. Pour le moment, seule la couverture du pod prend des options. SÉLECTION DES FICHIERS À

COUVRIR

Vous pouvez sélectionner les fichiers pour lesquels vous souhaitez collecter les données de couverture à l'aide des options select, ignore et inc. Le système utilise la procédure suivante pour décider si un fichier sera inclus dans les rapports de couverture

:
  • Si le fichier correspond à une expression rationnelle (RE) donnée en tant qu'option select, il sera
    • inclus
  • Sinon, s'il correspond à une RE donnée en tant qu'option ignore, il ne sera pas
    • inclus
  • Sinon, s'il se trouve dans l'un des répertoires inc, il ne sera pas
    • inclus
  • Sinon,
    • il sera
inclus

Vous pouvez ajouter des RE à la sélection en utilisant +select, ou vous pouvez réinitialiser les sélections en utilisant -select. Le même principe s'applique aux RE à

ignorer.

Les répertoires inc sont initialement remplis avec le contenu du tableau @INC de perl. Vous pouvez réinitialiser ces répertoires en utilisant -inc, ou y ajouter des éléments en utilisant

+inc.

Bien que ces options prennent des expressions rationnelles, vous ne devez pas entourer la RE de // ou de tout autre caractère de

délimitation.

Les options -coverage, [+-]select, [+-]ignore et [+-]inc peuvent être spécifiées plusieurs fois, mais elles

peuvent aussi prendre plusieurs arguments séparés par des virgules. Dans tous les cas, vous ne devez pas
ajouter d'espace après la virgule, sauf si vous voulez que l'argument commence par cet espace littéral.

CRITÈRES NON

COUVRABLES

Parfois, vous avez du code qui n'est pas couvrable pour une raison quelconque. Peut-être s'agit-il d'une clause else qui ne peut pas être atteinte, ou d'une vérification d'une condition d'erreur qui ne devrait jamais se produire. Vous pouvez indiquer à Devel::Cover que certains critères ne sont pas couvrables, et alors ils ne sont pas comptés comme des erreurs lorsqu'ils ne sont pas exercés. En fait, ils sont comptés comme des erreurs s'ils sont

exercés.

Cette fonctionnalité ne devrait être utilisée qu'en dernier recours. Idéalement, vous trouveriez un moyen d'exercer tout votre code. Mais si vous avez analysé votre code et déterminé que vous ne pourrez pas l'exercer, il peut être préférable d'enregistrer ce fait de manière formelle et d'empêcher Devel::Cover de s'en plaindre, afin que les vrais problèmes ne se perdent pas dans le

bruit.

Si vous avez des critères non couvrables, je suggère de ne pas utiliser le rapport HTML par défaut (qui utilise actuellement html_minimal) car cela montre parfois des points non couvrables comme non couverts. À la place, vous devriez utiliser le rapport html_basic pour la sortie HTML, qui devrait se comporter correctement à cet

égard.

Il existe deux façons de spécifier une construction comme non couvrable, l'une invasive et l'autre non

invasive.

Spécification

invasive

Vous pouvez utiliser des commentaires spéciaux dans votre code pour spécifier les critères non couvrables. Les commentaires sont de la forme

: 
# uncoverable <criterion>
[details]

Le mot-clé "uncoverable" doit être le premier texte du commentaire. Il doit être suivi du nom du critère de couverture qui n'est pas couvrable. Il peut y avoir ensuite d'autres informations selon la nature de la construction non

couvrable.

Dans tous les cas, un attribut de classe peut être inclus dans les détails. Actuellement, un seul attribut de classe est reconnu : ignore_covered_err. Normalement, une erreur est signalée si du code marqué comme non couvrable est couvert. Lorsque l'attribut ignore_covered_err est spécifié, de telles erreurs ne seront pas signalées. C'est une méthode plus précise pour signaler de telles exceptions que l'option globale -ignore_covered_err du programme

cover.

Il existe également un attribut note qui peut aussi être inclus dans les détails. Cela devrait être le dernier attribut et consommera tout le texte restant. Actuellement, cet attribut n'est pas utilisé, mais il est destiné à servir de forme de documentation pour les données non

couvrables.

Exemple

: 
# uncoverable branch true count:1..3 class:ignore_covered_err note:error
chk

Instruction

s

Le commentaire "uncoverable" doit apparaître soit sur la même ligne que l'instruction, soit sur la ligne précédente

: 
$impossible++;  # uncoverable statement
# uncoverable statement
it_has_all_gone_horribly_wrong()
;

S'il y a plusieurs instructions (ou tout autre critère) sur une ligne, vous pouvez spécifier quelle instruction n'est pas couvrable en utilisant l'attribut "count", count:n, qui indique que l'instruction non couvrable est la n-ième instruction de la

ligne. 
# uncoverable statement count:1
# uncoverable statement count:2
cannot_run_this(); or_this()
;

Branche

s

Le commentaire "uncoverable" doit spécifier si la branche "true" ou "false" n'est pas

couvrable. 
# uncoverable branch true
if (pi ==
3)

Les deux branches peuvent être non couvrables

: 
# uncoverable branch true
# uncoverable branch false
if (impossible_thing_happened_one_way()) {
  handle_it_one_way();      # uncoverable statement
} else {
  handle_it_another_way();  # uncoverable statement
}

S'il y a un elsif dans la branche, il peut être adressé comme la deuxième branche de la ligne en utilisant l'attribut "count". Les elsif suivants sont les troisième et quatrième valeurs de "count", et ainsi de suite

: 
# uncoverable branch false count:2
if ($thing == 1) {
  handle_thing_being_one();
} elsif ($thing == 2) {
  handle_thing_being_tow();
} else {
  die "thing can only be one or two, not $thing"; # uncoverable statement
}

Condition

s

En raison de la manière dont Perl interrompt les opérations booléennes, il existe trois façons dont de tels conditionnels peuvent être non couvrables. Dans le cas de " $x && $y" par exemple, l'opérande de gauche peut ne jamais être vrai, l'opérande de droite peut ne jamais être vrai, et l'opération entière peut ne jamais être fausse. Ces conditions peuvent être modélisées ainsi

: 
# uncoverable branch true
# uncoverable condition left
# uncoverable condition false
if ($x && !$y) {
  $x++;  # uncoverable statement
}
# uncoverable branch true
# uncoverable condition right
# uncoverable condition false
if (!$x && $y) {
}

Les conditionnels "Or" sont traités de manière similaire (TODO - fournir quelques exemples) mais les conditionnels "xor" ne sont pas encore correctement

gérés.

Comme pour les branches, la valeur "count" peut être utilisée soit pour les conditions dans les conditionnels elsif, soit pour les conditions

complexes.

Sous-routine

s

Une sous-routine doit être marquée comme non couvrable au point où la première instruction est marquée comme non couvrable. Idéalement, tous les autres critères de la sous-routine seraient automatiquement marqués comme non couvrables, mais ce n'est pas le cas

actuellement. 
sub z {
  # uncoverable
subroutine $y++; #
uncoverable statement }

Spécification non

invasive

Si vous ne pouvez pas, ou ne voulez pas ajouter des commentaires de couverture à votre code, vous pouvez spécifier les informations non couvrables dans un fichier séparé. Par défaut, les fichiers PWD/.uncoverable et HOME/.uncoverable sont vérifiés. Si vous utilisez le paramètre -uncoverable_file, alors le fichier que vous fournissez est vérifié en plus de ces deux

fichiers.

L'interface pour gérer ce fichier est le programme cover, et les options sont

: 
-uncoverable_file
-add_uncoverable_point
-delete_uncoverable_point   **NON IMPLÉMENTÉ**

IMPLÉMENTÉ**

Le paramètre de -add_uncoverable_point est une chaîne composée d'au plus sept éléments séparés par des espaces : "$file $criterion $line $count $type $class $note"

Variables

utilisateur

L'option -silent est activée lorsque Devel::Cover est invoqué via $HARNESS_PERL_SWITCHES ou $PERL5OPT. Devel::Cover essaie de faire la bonne chose lorsque $MOD_PERL est défini. $DEVEL_COVER_OPTIONS est ajouté à toutes les options transmises à Devel::

Cover.

Notez que lorsque Devel::Cover est invoqué via une variable d'environnement, les modules spécifiés sur la ligne de commande, comme via l'optio

n -Mmodule, ne seront pas couverts. C'est parce que les variables d'environnement sont traitées après la ligne de commande et que tout code à
couvrir doit apparaître après que Devel::Cover a été chargé. Pour contourner cela, Devel::Cover peut aussi être spécifié sur la ligne de commande.

Variables

développeur

Lors de l'exécution de la suite de tests de Devel::Cover, $DEVEL_COVER_DEBUG active les informations de débogage, $DEVEL_COVER_GOLDEN_VERSION remplace l'idée propre à Devel::Cover des résultats de référence (golden) contre lesquels il devrait tester, et $DEVEL_COVER_NO_COVERAGE exécute les tests sans collecter la couverture. $DEVEL_COVER_DB_FORMAT peut être défini à "Sereal", "JSON" ou "Storable" pour remplacer le choix par défaut du format de la base de données (Sereal, puis JSON si l'un ou l'autre est disponible, sinon Storable). $DEVEL_COVER_IO_OPTIONS fournit un contrôle fin sur le format de la base de données. Par exemple, le définir à "pretty" lorsque le format est JSON stockera la base de données dans un format JSON lisible. $DEVEL_COVER_CPUS remplace la détection

automatique du nombre
de CPU à utiliser lors
des tests parallèles.

LIMITATION

S

Il existe des choses que Devel::Cover ne peut pas

couvrir.

Absence de dépendances

partagées

Perl garde une trace des modules qui ont été chargés (pour éviter de les recharger). À cause de cela, il n'est pas possible d'obtenir la couverture pour un chemin où un import à l'exécution échoue si le module importé est un de ceux que Devel::Cover utilise en interne. Par exemple, supposez que votre programme a cette fonction

: 
sub foo {
  eval { require Storable };
  if ($@) {
      carp "Can't find Storable";
      return;
  }
  # ...
}

Vous pourriez écrire un test pour le mode d'échec

comme 
BEGIN { @INC = () }
foo();
# check for error
message

Parce que Devel::Cover utilise Storable en interne, l'import réussira (et le test échouera) lors d'une exécution avec

couverture.
