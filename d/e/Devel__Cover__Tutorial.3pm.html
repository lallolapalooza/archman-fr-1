Voici une partie d'un message que j'ai envoyé à perl-qa concernant les métriques de couverture de

code.

1.0

Introduction

Il est sage de se souvenir de la citation suivante de Dijkstra, qui a dit

: 
Les tests ne prouvent jamais l'absence de fautes, ils ne font que montrer leur
présence.

En particulier, la couverture de code n'est qu'une arme dans l'arsenal de test de l'ingénieur

logiciel.

Toute discussion sur les métriques de couverture de code est entravée par le fait que de n

ombreux auteurs utilisent des termes différents pour décrire le même type de couverture. Ic
i, je ne fournirai qu'une brève introduction à certaines des métriques les plus courantes.

2.0

Métr
iques

2.1 Couverture des

instructions

C'est la forme de base de la couverture de code. Une instruction est couverte si elle est exécutée. Notez que instruction ≠ ligne de code. Plusieurs instructions sur une seule ligne peuvent embrouiller les choses - le rapport, sinon rien

d'autre.

Lorsqu'il y a des séquences d'instructions sans branches, il n'est pas nécessaire de compter l'exécution de chaque instruction, une seule suffira, mais les gens aiment souvent que le compte de chaque ligne soit rapporté, en particulier dans les statistiques résumées. Cependant, il n'est pas clair pour moi que cela soit réellement

utile.

Ce type de couverture est assez faible en ce que même avec une couverture d'instructions à 100 %, il peut encore y avoir de sérieux problèmes dans un programme qui pourraient être découverts par d'autres types de

métriques.

Il peut être assez difficile d'atteindre une couverture d'instructions de 100 %. Il peut y avoir des sections de code conçues pour gérer des conditions d'erreur, ou des événements rarement survenus tels qu'un signal reçu pendant une certaine section de code. Il peut aussi y avoir du code qui ne devrait jamais être exécuté

: 
if ($param > 20) {
  die "This should never happen!";
}

Il peut être utile de marquer un tel code de quelque manière et de signaler une erreur s'il est

exécuté.

La couverture des instructions, ou quelque chose de très similaire, peut être appelée exécuti

on d'instructions, lignes, blocs, blocs de base ou couverture de segments. J'ai tendance à fa
voriser la couverture de blocs qui n'essaie pas d'étendre ses résultats à chaque instruction.

2.2 Couverture des

branches

Le but de la couverture des branches est de s'assurer que chaque fois qu'un programme peut sauter, il saute vers toutes les destinations possibles. L'exemple le plus simple est une instruction if complète

: 
if ($x) {
  print "a";
} else {
  print "b";
}

Dans un exemple aussi simple, la couverture des instructions est aussi puissante, mais la couverture des branches devrait aussi permettre le cas où la partie else est manquante

: 
if ($x) {
  print "a";
}

La couverture complète n'est obtenue ici que si $x est vrai à une occasion et faux à une

autre.

Une couverture des branches à 100 % implique une couverture des instructions à 100

%.

La couverture des branches est

aussi appelée couverture des déc
isions ou de toutes les arêtes.

2.3 Couverture des

chemins

Il existe des classes d'erreurs que la couverture des branches ne peut pas détecter, telles que

: 
$h = undef;
if ($x) {
  $h = { a => 1 };
} if ($y) {
  print $h->{a};
}

Une couverture des branches à 100 % peut être atteinte en définissant ($x, $y) à (1, 1) puis à (0, 0). Mais si nous avons (0, 1), alors les choses

explosent.

Le but de la couverture des chemins est de s'assurer que tous les chemins à travers le programme sont empruntés. Dans un programme de taille raisonnable, il y aura un nombre énorme de chemins à travers le programme et donc en pratique les chemins peuvent être limités à une seule sous-routine, si la sous-routine n'est pas trop grande, ou simplement à deux branches

consécutives.

Dans l'exemple ci-dessus, il y a quatre chemins qui correspondent à la table de vérité pour $x et $y. Pour atteindre une couverture des chemins de 100 %, ils doivent tous être empruntés. Notez que les else manquants comptent comme des

chemins.

Dans certains cas, il peut être impossible d'atteindre une couverture des chemins de 100 %

: 
a if $x;
b;
c if
$x;

50 % de couverture des chemins est le meilleur que vous puissiez obtenir

ici.

Les boucles contribuent aussi aux chemins, et posent leurs propres problèmes que j'ignorerai pour

l'instant.

Une couverture des chemins de 100 % implique une couverture des branches de 100

%.

La couverture des chemins et certaines de ses cousines proches

sont aussi connues sous les noms de couverture des prédicats,
des chemins de base et LCSAJ (Linear Code Sequence and Jump).

2.4 Couverture des

expressions

Lorsqu'une expression booléenne est évaluée, il peut être utile de s'assurer que tous les termes de l'expression sont exercés. Par exemple

: 
a if $x ||
$y

L'expression devrait être exercée avec ($x, $y) défini à (0, 0) (requis pour la couverture des branches), (0, 1) et (1, 0) (pour s'assurer que $x et $y sont indépendants) et éventuellement avec (1, 1)

.

La couverture des expressions devient compliquée, et difficile à atteindre, à mesure que l'expression se

complique.

Les expressions qui ne font pas directement partie d'un construct de branchement devraient aussi être couvertes

: 
$z = $x || $y;
a if
$z;

La couverture des expressions est aussi connu

e sous les noms de couverture des conditions,
condition-décision et de décisions multiples.

3.0 Autres

considérations

Pour que les gens utilisent réellement la couverture de code, elle doit être simple à utiliser. Il devrait aussi être simple de comprendre les résultats et de corriger les problèmes soulevés. Enfin, si la surcharge est trop importante, elle ne sera pas non plus

utilisée.

Voilà donc un tutoriel de base sur la couverture

de code, ou du moins ma version. La saisie de q
uelques-uns de ces termes dans Google fournira p
robablement une base pour de futures recherches.
