NOM

deb-src-symbols - Fichier modèle étendu de bibliothèques partagées Debian

SYNOPIS

debian/paquet.symbols.arch, debian/symbols.arch, debian/paquet.symbols, debian/symbols

DESCRIPTION

Les modèles de fichiers symboles sont livrés dans les paquets source Debian, et leur format est un sur-ensemble des fichiers symboles livrés dans les paquets binaires, voir deb-symbols(5).

Commentaires

Les commentaires sont pris en charge dans les fichiers modèles de symboles. Toute ligne commençant par ‘#’ comme premier caractère est un commentaire, sauf si elle commence par ‘#include’ (voir la section "Utilisation des inclusions"). Les lignes commençant par ‘#MISSING:’ sont des commentaires spéciaux documentant les symboles qui ont disparu.

Utilisation de la substitution #PACKAGE#

Dans certains cas rares, le nom de la bibliothèque varie selon les architectures. Pour éviter de coder en dur le nom du paquet dans le fichier symboles, vous pouvez utiliser le marqueur #PACKAGE#. Il sera remplacé par le nom réel du paquet lors de l'installation des fichiers symboles. Contrairement au marqueur #MINVER#, #PACKAGE# n'apparaîtra jamais dans un fichier symboles à l'intérieur d'un paquet binaire.

Utilisation des tags de symboles

Le marquage des symboles est utile pour identifier les symboles qui sont spéciaux d'une manière ou d'une autre. Tout symbole peut avoir un nombre arbitraire de tags qui lui sont associés. Bien que tous les tags soient analysés et stockés, seuls certains d'entre eux sont compris par dpkg-gensymbols et déclenchent un traitement spécial des symboles. Voir la sous-section "Tags de symboles standard" pour la référence de ces tags.

La spécification du tag précède le nom du symbole (aucun espace n'est autorisé entre les deux). Elle commence toujours par une parenthèse ouvrante (, se termine par une parenthèse fermante ) et doit contenir au moins un tag. Plusieurs tags sont séparés par le caractère |. Chaque tag peut éventuellement avoir une valeur, séparée du nom du tag par le caractère =. Les noms de tags et les valeurs peuvent être des chaînes arbitraires, à condition qu'ils ne contiennent aucun des caractères spéciaux ) | =. Les noms de symboles suivant une spécification de tag peuvent éventuellement être entourés de guillemets simples ' ou doubles " pour permettre les espaces. Cependant, s'il n'y a pas de tags spécifiés pour le symbole, les guillemets sont traités comme faisant partie du nom du symbole, qui se poursuit jusqu'au premier espace.

(tag1=i am marked|tag name with space)"tagged quoted symbol"@Base 1.0
(optional)tagged_unquoted_symbol@Base 1.0 1
untagged_symbol@Base 1.0

Le premier symbole dans l'exemple est nommé tagged quoted symbol et a deux tags : tag1 avec la valeur i am marked et tag name with space qui n'a pas de valeur. Le deuxième symbole nommé tagged_unquoted_symbol est uniquement tagué avec le tag nommé optional. Le dernier symbole est un exemple de symbole normal non tagué.

Étant donné que les tags de symboles sont une extension du format deb-symbols(5), ils ne peuvent faire partie que des fichiers symboles utilisés dans les paquets source (ces fichiers doivent alors être considérés comme des modèles utilisés pour construire les fichiers symboles incorporés dans les paquets binaires). Lorsque dpkg-gensymbols est appelé sans l'option -t, il produira des fichiers symboles compatibles avec le format deb-symbols(5) : il traite entièrement les symboles conformément aux exigences de leurs tags standard et supprime tous les tags de la sortie. En revanche, en mode modèle (-t), tous les symboles et leurs tags (connus et inconnus) sont conservés dans la sortie et sont écrits sous leur forme d'origine telle qu'ils ont été chargés.

Tags de symboles standard

optional
Un symbole marqué comme optionnel peut disparaître de la bibliothèque à tout moment et cela ne fera jamais échouer dpkg-gensymbols. Cependant, les symboles optionnels disparus apparaîtront continuellement comme MISSING dans le diff à chaque nouvelle révision de paquet. Ce comportement sert de rappel au mainteneur qu'un tel symbole doit être supprimé du fichier symboles ou réajouté à la bibliothèque. Lorsque le symbole optionnel, précédemment déclaré comme MISSING, réapparaît soudainement dans la révision suivante, il sera reclassé en statut "existant" sans que sa version minimale ne soit modifiée.

Ce tag est utile pour les symboles qui sont privés, dont la disparition ne provoque pas de rupture d'ABI. Par exemple, la plupart des instanciations de modèles C++ entrent dans cette catégorie. Comme tout autre tag, celui-ci peut également avoir une valeur arbitraire : il pourrait être utilisé pour indiquer pourquoi le symbole est considéré comme optionnel.

arch=liste-architectures
arch-bits=bits-architecture
arch-endian=boutisme-architecture
Ces tags permettent de restreindre l'ensemble des architectures où le symbole est censé exister. Les tags arch-bits et arch-endian sont pris en charge depuis dpkg 1.18.0. Lorsque la liste des symboles est mise à jour avec les symboles découverts dans la bibliothèque, tous les symboles spécifiques à une architecture qui ne concernent pas l'architecture hôte actuelle sont traités comme s'ils n'existaient pas. Si un symbole spécifique à une architecture correspondant à l'architecture hôte actuelle n'existe pas dans la bibliothèque, les procédures normales pour les symboles manquants s'appliquent et cela peut entraîner l'échec de dpkg-gensymbols. D'autre part, si le symbole spécifique à une architecture est trouvé alors qu'il n'était pas censé exister (car l'architecture hôte actuelle n'est pas listée dans le tag ou ne correspond pas au boutisme et aux bits), il est rendu neutre en architecture (c'est-à-dire que les tags arch, arch-bits et arch-endian sont supprimés et le symbole apparaîtra dans le diff en raison de ce changement), mais il n'est pas considéré comme nouveau.

En mode normal non-modèle, parmi les symboles spécifiques à une architecture, seuls ceux qui correspondent à l'architecture hôte actuelle sont écrits dans le fichier symboles. Au contraire, tous les symboles spécifiques à une architecture (y compris ceux d'architectures étrangères) sont toujours écrits dans le fichier symboles lors du fonctionnement en mode modèle.

Le format de liste-architectures est le même que celui utilisé dans le champ Build-Depends de debian/control (à l'exception des crochets [] encadrants). Par exemple, le premier symbole de la liste ci-dessous ne sera considéré que sur les architectures arm64, any-amd64 et riscv64, le second uniquement sur les architectures linux, tandis que le troisième n'importe où sauf sur armel.

(arch=arm64 any-amd64 riscv64)arch_specific_symbol@Base 1.0
(arch=linux-any)linux_specific_symbol@Base 1.0
(arch=!armel)symbol_armel_does_not_have@Base 1.0

Les bits-architecture sont soit 32, soit 64.

(arch-bits=32)32bit_specific_symbol@Base 1.0
(arch-bits=64)64bit_specific_symbol@Base 1.0

Le boutisme-architecture est soit little, soit big.

(arch-endian=little)little_endian_specific_symbol@Base 1.0
(arch-endian=big)big_endian_specific_symbol@Base 1.0

Plusieurs restrictions peuvent être chaînées.

(arch-bits=32|arch-endian=little)32bit_le_symbol@Base 1.0
allow-internal
dpkg-gensymbols possède une liste de symboles internes qui ne devraient pas apparaître dans les fichiers symboles car ils ne sont généralement que des effets secondaires des détails d'implémentation de la chaîne d'outils (depuis dpkg 1.20.1). Si, pour une raison quelconque, vous souhaitez réellement qu'un de ces symboles soit inclus dans le fichier symboles, vous devez le taguer avec allow-internal. Cela peut être nécessaire pour certaines bibliothèques de chaîne d'outils de bas niveau comme “libgcc”.
ignore-blacklist
Un alias obsolète pour allow-internal (depuis dpkg 1.20.1, pris en charge depuis dpkg 1.15.3).

Utilisation des motifs de

symbole

Contrairement à une spécification de symbole standard, un motif peut couvrir plusieurs symboles réels de la bibliothèque. dpkg-gensymbols essaiera de faire correspondre chaque motif à chaque symbole réel qui n'a pas de contrepartie de symbole spécifique définie dans le fichier de symboles. Dès que le premier motif correspondant est trouvé, toutes ses balises et propriétés seront utilisées comme spécification de base du symbole. Si aucun des motifs ne correspond, le symbole sera considéré comme

nouveau.

Un motif est considéré comme perdu s'il ne correspond à aucun symbole de la bibliothèque. Par défaut, cela déclenchera un échec de dpkg-gensymbols avec -c1 ou un niveau supérieur. Cependant, si l'échec n'est pas souhaité, le motif peut être marqué avec la balise optional. Alors, si le motif ne correspond à rien, il apparaîtra seulement dans le diff comme MISSING. De plus, comme tout symbole, le motif peut être limité aux architectures spécifiques avec la balise arch. Veuillez vous référer à la sous-section « Balises de symboles standard » ci-dessus pour plus

d'informations.

Les motifs sont une extension du format deb-symbols(5) et ne sont donc valides que dans les modèles de fichiers de symboles. La syntaxe de spécification d'un motif n'est pas différente de celle d'un symbole spécifique. Cependant, la partie nom de symbole de la spécification sert d'expression à faire correspondre avec name@version du symbole réel. Afin de distinguer les différents types de motifs, un motif sera généralement marqué avec une balise

spéciale.

Pour le moment, dpkg-gensymbols prend en charge trois types de motifs de base

:
c+
+
Ce motif est désigné par la balise c++. Il ne correspond qu'aux symboles C++ par leur nom de symbole démanglé (tel qu'émis par l'utilitaire c++filt(1)). Ce motif est très pratique pour faire correspondre des symboles dont les noms manglés peuvent varier d'une architecture à l'autre alors que leurs noms démanglés restent les mêmes. Un groupe de tels symboles est les thunks non virtuels qui ont des décalages spécifiques à l'architecture intégrés dans leurs noms manglés. Un cas courant de cette situation est un destructeur virtuel qui, sous héritage en diamant, nécessite un symbole de thunk non virtuel. Par exemple, même si _ZThn8_N3NSB6ClassDD1Ev@Base sur les architectures 32 bits sera probablement _ZThn16_N3NSB6ClassDD1Ev@Base sur les 64 bits, il peut être fait correspondre avec un seul motif c++ : 
libdummy.so.1 libdummy1 #MINVER#
 [...]
 (c++)"non-virtual thunk to NSB::ClassD::~ClassD()@Base" 1.0
[...]

Le nom démanglé ci-dessus peut être obtenu en exécutant la commande

suivante : 
$ echo '_ZThn8_N3NSB6ClassDD1Ev@Base' |
c++filt

Veuillez noter que si le nom manglé est unique dans la bibliothèque par définition, ce n'est pas nécessairement le cas des noms démanglés. Plusieurs symboles réels distincts peuvent avoir

le même nom démanglé. Par exemple, c'est le cas des symboles de thunk non virtuel dans des configurations d'héritage complexes ou avec la plupart des constructeurs et destructeurs (car
g++ génère généralement deux symboles réels pour eux). Cependant, comme ces collisions se produisent au niveau de l'ABI, elles ne devraient pas dégrader la qualité du fichier de symboles.
symv
er
Ce motif est désigné par la balise symver. Les bibliothèques bien entretenues ont des symboles versionnés où chaque version correspond à la version amont où le symbole a été ajouté. Si c'est le cas, vous pouvez utiliser un motif symver pour faire correspondre tout symbole associé à la version spécifique. Par exemple : 
libc.so.6 libc6 #MINVER#
 (symver)GLIBC_2.0 2.0
 [...]
 (symver)GLIBC_2.7 2.7
 access@GLIBC_2.
0 2.2

Tous les symboles associés aux versions GLIBC_2.0 et GLIBC_2.7 mèneront à une version minimale de 2.0 et 2.7 respectivement, à l'exception du symbole access@GLIBC_2.0. Ce dernier mènera à une dépendance minimale sur la version 2.2 de libc6 bien qu'il soit dans la portée du motif « (symver)GLIBC_2.0 » car les symboles spécifiques priment sur les

motifs.

Veuillez noter que si les motifs génériques à l'ancien style (désignés par "*@version" dans le champ nom de symbole)

sont toujours pris en charge, ils ont été dépréciés par la nouvelle syntaxe « (symver|optional)version ». Par exempl
e, « *@GLIBC_2.0 2.0 » devrait être écrit « (symver|optional)GLIBC_2.0 2.0 » si le même comportement est nécessaire.
reg
ex
Les motifs d'expression régulière sont désignés par la balise regex. Ils correspondent par l'expression régulière perl spécifiée dans le champ nom de symbole. Une expression régulière est telle quelle, n'oubliez donc pas de la commencer par le caractère ^ ou elle pourrait correspondre à n'importe quelle partie de la chaîne name@version du symbole réel. Par exemple : 
libdummy.so.1 libdummy1 #MINVER#
 (regex)"^mystack_.*@Base$" 1.0
 (regex|optional)"private"
1.0

Des symboles comme « mystack_new@Base », « mystack_push@Base », « mystack_pop@Base », etc., seront faits correspondre par le premier motif alors que « ng_mystack_new@Base » ne le sera pas. Le second motif correspondra à tous les symboles ayant la chaîne « private » dans leurs noms et les correspondances hériteront de la balise opt

ional
du m
otif.

Les motifs de base listés ci-dessus peuvent être combinés là où c'est pertinent. Dans ce cas, ils sont traités dans l'ordre où les balises sont spécifiées. Par exemple, les deux

: 
(c++|regex)"^NSA::ClassA::Private::privmethod\d\(int\)@Base" 1.0
(regex|c++)N3NSA6ClassA7Private11privmethod\dEi@Base 1.
0

feront correspondre les symboles « _ZN3NSA6ClassA7Private11privmethod1Ei@Base » et « _ZN3NSA6ClassA7Private11privmethod2Ei@Base ». Lors de la correspondance du premier motif, le symbole brut est d'abord démanglé en symbole C++, puis le nom démanglé est comparé à l'expression régulière. D'autre part, lors de la correspondance du second motif, l'expression régulière est comparée au nom brut du symbole, puis le symbole est testé s'il est C++ en essayant de le démangler. L'échec de n'importe quel motif de base entraînera l'échec du motif entier. Par conséquent, par exemple, « __N3NSA6ClassA7Private11privmethod\dEi@Base » ne correspondra à aucun des motifs car ce n'est pas un symbole C++

valide.

En général, tous les motifs sont divisés en deux groupes : les alias (les motifs de base c++ et symver) et les motifs génériques (regex, toutes les combinaisons de motifs de base multiples). La correspondance des motifs de base basés sur les alias est rapide (O(1)) alors que les motifs génériques sont O(N) (N - nombre de motifs génériques) pour chaque symbole. Il est donc recommandé de ne pas abuser des motifs

génériques.

Quand plusieurs motifs correspondent au même symbole réel, les alias (d'abord c++, puis symver) sont préférés aux motifs génériques. Les motifs génériques sont comparés dans l'ordre où ils sont trouvés dans le modèle de fichier de symboles jusqu'au premier succès. Veuillez noter cependant que le réordonnement manuel des entrées du fichier modèle n'est pas recommandé car dpkg-gensymbols génère des diffs basés s

ur l'ordre alphanumé
rique de leurs noms.

Utilisation des

includes

Quand l'ensemble des symboles exportés diffère entre les architectures, l'utilisation d'un seul fichier de symboles peut devenir inefficace. Dans ces cas, une directive include peut s'avérer utile de plusieurs manières

:
  • Vous pouvez factoriser la partie commune dans un fichier externe et inclure ce fichier dans votre package.symbols.arch en utilisant une directive include comme celle-ci : 
    #include "I<
    packages>.sym
    • bols.common"
  • La directive include peut aussi être balisée comme n'importe quel symbole : 
    (tag|...|tagN)#include
    "file-to-include"

    En conséquence, tous les symboles inclus depuis file-to-include seront considérés comme balisés avec tag ... tagN par défaut. Vous pouvez utiliser cette fonctionnalité pour créer un fichier package.symbols commun qui inclut des fichiers de symboles spécifiques à

    l'architecture : 
     common_symbol1@Base 1.0
(arch-bits=6
    4)#include "package.symbols.64-bit"
    • (arch-bits=32)#include "package.symb
ols.32-bit" common_symbol2@Base 1.0

Les fichiers de symboles sont lus ligne par ligne, et les directives include sont traitées dès qu'elles sont rencontrées. Cela signifie que le contenu du fichier inclus peut remplacer tout contenu qui est apparu avant la directive include et que tout contenu après la directive peut remplacer tout ce que contient le fichier inclus. N'importe quel symbole (ou même une autre directive #include) dans le fichier inclus peut spécifier des balises supplémentaires ou remplacer les valeurs des balises héritées dans sa spécification de balises. Cependant, il n'y a aucun moyen pour un symbole de supprimer l'une des balises

héritées.

Un fichier inclus peut répéter la ligne d'en-tête contenant le SONAME de la bibliothèque. Dans ce cas, il remplace toute ligne d'en-tête lue précédemment. Cependant, en général, il vaut mieux éviter de dupliquer les lignes d'en-tête. Une façon de faire est la suivante

: 
#include "libsomet
hing1.symbols.com
mon" arch_specific_symbol@Base 1.0
