DESCRIPTIO

N

L'utilitaire dcm2img lit une image DICOM, convertit les données de pixels selon les options de traitement d'image sélectionnées et écrit une image dans l'un des formats d'image génériqu

es suivants : BMP, PGM/PPM, PNG, TIFF, JPEG ou JPEG-LS. Cet utilitaire prend en charge
les images DICOM non compressées ainsi que celles compressées en JPEG, JPEG-LS et RLE.

options de contournement pour les codages incorrects (images compressées JPEG uniquement) :
  +w6   --workaround-pred6
          active le contournement pour les images JPEG sans perte
          avec débordement dans le prédicteur 6
  # Des images DICOM avec 16 bits/pixel ont été observées "dans la nature"
  # qui sont compressées avec du JPEG sans perte et nécessitent une gestion
  # spéciale car l'encodeur a produit un débordement d'entier 16 bits dans le
  # prédicteur 6, qui doit être compensé (reproduit) lors de la décompression.
  # Ce drapeau permet une décompression correcte de telles images défectueuses,
  # mais causera en même temps une décompression incorrecte d'images correctement
  # compressées. À utiliser avec précaution.
  +wi   --workaround-incpl
          active le contournement pour les données JPEG incomplètes
  # Cette option fait que dcm2img ignore les données JPEG incomplètes
  # à la fin d'un fragment compressé et commence à décompresser
  # la trame suivante à partir du fragment suivant (s'il y en a un). Cela permet
  # de décoder des images avec des données JPEG incomplètes.
  +wc   --workaround-cornell
          active le contournement pour les images JPEG sans perte 16 bits
  # Cornell avec débordement de table de Huffman
  # L'une des premières implémentations open-source de la compression JPEG
  # sans perte, la bibliothèque "Cornell", a un bug bien connu qui entraîne
  # des valeurs invalides dans la table de Huffman lorsque des images avec
  # 16 bits/échantillon sont compressées. Ce drapeau active un contournement qui
  # permet de décoder correctement de telles images.

JOURNALISATI

ON

Le niveau de journalisation des différentes outils en ligne de commande et des bibliothèques sous-jacentes peut être spécifié par l'utilisateur. Par défaut, seules les erreurs et les avertissements sont écrits sur le flux d'erreur standard. En utilisant l'option --verbose , des messages informatifs tels que les détails de traitement sont également rapportés. L'option --debug peut être utilisée pour obtenir plus de détails sur l'activité interne, par exemple à des fins de débogage. D'autres niveaux de journalisation peuvent être sélectionnés à l'aide de l'option --log-level . En mode --quiet , seules les erreurs fatales sont rapportées. En cas d'erreur très grave, l'application se terminera généralement. Pour plus de détails sur les différents niveaux de journalisation, voir la documentation du module « oflog »

.

Si la sortie de journalisation doit être écrite dans un fichier (avec rotation optionnelle du fichier journal), dans syslog (Unix) ou dans le journal d'événements (Windows), l'option --log-config peut être utilisée. Ce fichier de configuration permet également de diriger uniquement certains messages vers un flux de sortie particulier et de filtrer certains messages en fonction du module ou de l'application où ils sont générés. Un exemple de fichier de configuration est fourni dans <etcdir>/l

ogger
.cfg.

LIGNE DE

COMMANDE

Tous les outils en ligne de commande utilisent la notation suivante pour les paramètres : les crochets entourent les valeurs facultatives (0-1), trois points de suite indiquent que plusieurs valeurs sont autorisées (1-n), une combinaison des deux signifie de 0 à n

valeurs.

Les options de ligne de commande se distinguent des paramètres par un signe '+' ou '-' en tête, respectivement. Habituellement, l'ordre et la position des options de ligne de commande sont arbitraires (c'est-à-dire qu'elles peuvent apparaître n'importe où). Cependant, si des options sont mutuellement exclusives, la dernière occurrence la plus à droite est utilisée. Ce comportement est conforme aux règles d'évaluation standard des shells Unix

courants.

De plus, un ou plusieurs fichiers de commandes peuvent être spécifiés en utilisant un signe '@' comme préfixe du nom de fichier (par exemple @command.txt ). Un tel argument de commande est remplacé par le contenu du fichier texte correspondant (plusieurs espaces blancs sont traités comme un seul séparateur s'ils n'apparaissent pas entre deux guillemets) avant toute autre évaluation. Veuillez noter qu'un fichier de commandes ne peut pas contenir un autre fichier de commandes. Cette approche simple mais efficace permet de résumer des combinaisons courantes d'options/paramètres et évite des lignes de commande longues et déroutantes (un exemple est fourni dans le fichier <datadir>/dumppat.txt

)
.

ENVIRONNEMEN

T

L'utilitaire dcm2img essaiera de charger les dictionnaires de données DICOM spécifiés dans la variable d'environnement DCMDICTPATH . Par défaut, c'est-à-dire si la variable d'environnement DCMDICTPATH n'est pas définie, le fichier <datadir>/dicom.dic sera chargé, sauf si le dictionnaire est intégré à l'application (par défaut sous Windows)

.

Le comportement par défaut doit être préféré et la variable d'environnement DCMDICTPATH ne doit être utilisée que lorsque des dictionnaires de données alternatifs sont nécessaires. La variable d'environnement DCMDICTPATH a le même format que la variable PATH du shell Unix en ce sens qu'un deux-points (« : ») sépare les entrées. Sur les systèmes Windows, un point-virgule (« ; ») est utilisé comme séparateur. Le code du dictionnaire de données essaiera de charger chaque fichier spécifié dans la variable d'environnement DCMDICTPATH . C'est une erreur si aucun di

ctionnaire de données
ne peut être chargé.
