DESCRIPTIO

N

L'utilitaire dcmcjpls lit une image DICOM non compressée (dcmfile-in), effectue une compression JPEG-LS (c'est-à-dire une conversion vers une syntaxe de transfert DICOM encapsulée) et écrit l'image convertie dans un fichier de sortie (dcmfil

NOTE

S

L'utilitaire dcmcjpls compresse les images DICOM de toutes les classes SOP. Il traite tous les éléments Pixel Data (7fe0,0010) du jeu de données, c'est-à-dire que la compression est également effectuée sur une image d'icône. Cependant, dcmcjpls ne tente pas de s'assurer que l'image compressée respecte toujours toutes les restrictions de l'IOD de

l'objet.

L'utilisateur est responsable de s'assurer que les images compressées qu'il crée sont conformes à la norme DICOM. En cas de doute, l'utilitaire dcmcjpls permet de convertir une image en capture secondaire - cette c

lasse SOP ne pose pas de restriction
s comme celles mentionnées ci-dessus.

JOURNALISATI

ON

Le niveau de journalisation des différentes outils en ligne de commande et des bibliothèques sous-jacentes peut être spécifié par l'utilisateur. Par défaut, seules les erreurs et les avertissements sont écrits sur le flux d'erreur standard. En utilisant l'option --verbose, des messages informatifs tels que les détails de traitement sont également rapportés. L'option --debug peut être utilisée pour obtenir plus de détails sur l'activité interne, par exemple à des fins de débogage. D'autres niveaux de journalisation peuvent être sélectionnés à l'aide de l'option --log-level. En mode --quiet, seules les erreurs fatales sont rapportées. Dans de tels cas d'erreur très grave, l'application se terminera généralement. Pour plus de détails sur les différents niveaux de journalisation, voir la documentation du module

"oflog".

Si la sortie de journalisation doit être écrite dans un fichier (avec rotation des fichiers journal optionnellement), dans syslog (Unix) ou dans le journal des événements (Windows), l'option --log-config peut être utilisée. Ce fichier de configuration permet également de diriger uniquement certains messages vers un flux de sortie particulier et de filtrer certains messages en fonction du module ou de l'application où ils sont générés. Un exemple de fichier de configuration est fourni dans <etcdir>/l

ogger
.cfg.

LIGNE DE

COMMANDE

Tous les outils en ligne de commande utilisent la notation suivante pour les paramètres : les crochets enclos des valeurs optionnelles (0-1), trois points de suite indiquent que plusieurs valeurs sont autorisées (1-n), une combinaison des deux signifie de 0 à n

valeurs.

Les options de ligne de commande se distinguent des paramètres par un signe '+' ou '-' en tête, respectivement. Habituellement, l'ordre et la position des options de ligne de commande sont arbitraires (c'est-à-dire qu'elles peuvent apparaître n'importe où). Cependant, si les options sont mutuellement exclusives, l'apparence la plus à droite est utilisée. Ce comportement est conforme aux règles d'évaluation standard des shells Unix

courants.

De plus, un ou plusieurs fichiers de commande peuvent être spécifiés en utilisant un signe '@' comme préfixe du nom de fichier (par exemple @command.txt). Un tel argument de commande est remplacé par le contenu du fichier texte correspondant (plusieurs espaces blancs sont traités comme un seul séparateur à moins qu'ils n'apparaissent entre deux guillemets) avant toute autre évaluation. Veuillez noter qu'un fichier de commande ne peut pas contenir un autre fichier de commande. Cette approche simple mais efficace permet de résumer des combinaisons courantes d'options/paramètres et évite des lignes de commande longues et déroutantes (un exemple est fourni dans le fichier <datadir>/du

mppat
.txt).

ENVIRONNEMEN

T

L'utilitaire dcmcjpls essaiera de charger les dictionnaires de données DICOM spécifiés dans la variable DCMDICTPATH. Par défaut, c'est-à-dire si la variable DCMDICTPATH n'est pas définie, le fichier <datadir>/dicom.dic sera chargé à moins que le dictionnaire ne soit intégré à l'application (par défaut sous Windows)

.

Le comportement par défaut devrait être préféré et la variable DCMDICTPATH ne devrait être utilisée que lorsque des dictionnaires de données alternatifs sont nécessaires. La variable DCMDICTPATH a le même format que la variable PATH du shell Unix en ce sens qu'un deux-points (":") sépare les entrées. Sur les systèmes Windows, un point-virgule (";") est utilisé comme séparateur. Le code du dictionnaire de données essaiera de charger chaque fichier spécifié dans la variable DCMDICTPATH. C'est une erreur si aucun dicti

onnaire de données ne
peut être chargé.
