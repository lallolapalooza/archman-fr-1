NOTES

L'utilitaire dcmcjpeg compresse les images DICOM de toutes les classes SOP. Il traite tous les éléments Pixel Data (7fe0,0010) du jeu de données, c'est-à-dire que la compression est également effectuée sur une image icône. Une gestion spéciale a été mise en œuvre pour les images CT (où la transformation de modalité est nécessaire pour créer des unités Hounsfield) et les classes SOP XA/RF/Biplane (où la transformation de modalité a une sémantique « inversée »). Cependant, dcmcjpeg n'essaie pas de garantir que l'image compressée reste conforme à toutes les restrictions de l'IOD de l'objet.

Quelques exemples :

  • Les images MR sont requises avec BitsAllocated=16.
  • Les images NM ne peuvent être encodées qu'avec une interprétation photométrique MONOCHROME2 ou PALETTE COLOR, mais pas avec RGB ou YBR_FULL (ce qui empêche effectivement la compression).
  • Les images Hardcopy Color doivent avoir un modèle couleur RGB, ce qui pose problème si une compression avec perte doit être effectuée.

L'utilisateur est responsable de s'assurer que les images compressées qu'il crée sont conformes à la norme DICOM. En cas de doute, l'utilitaire dcmcjpeg permet de convertir une image en capture secondaire - cette classe SOP n'impose pas les restrictions mentionnées ci-dessus.

Avec la version DCMTK 3.5.4, un nouvel encodeur pour la compression JPEG véritablement sans perte a été ajouté ( --true-lossless). Par rapport à l'ancien encodeur ( --pseudo-lossless), qui crée des images légèrement avec perte dues aux conversions internes d'espace couleur, au fenêtrage, etc., il y a quelques points à considérer :

  • Seules les images sources avec 8 ou 16 bits alloués sont prises en charge.
  • Les options de conversion d'espace couleur, de fenêtrage ou de mise à l'échelle des pixels sont ignorées ou remplacées.
  • Les interprétations photométriques YBR_FULL_422, YBR_PARTIAL_422, YBR_PARTIAL_420, YBR_ICT, YBR_RCT ne sont pas prises en charge.
  • L'encodeur change automatiquement la configuration planaire de 1 à 0 si nécessaire.
  • Le taux de compression peut être inférieur à celui du mode --pseudo-lossless.

Cependant, lors de l'utilisation du nouvel encodeur (par défaut), vous pouvez être sûr que la compression n'affecte pas la qualité de l'image.

Pour être sûr, le drapeau de compression avec perte est toujours défini sur « 01 » et un nouvel UID d'instance SOP est attribué (par défaut) pour l'ancien encodeur pseudo-sans perte. La sortie des anciens et nouveaux encodeurs sans perte peut également être distinguée par la description de dérivation dans l'image DICOM résultante, qui contient le terme « Compression JPEG sans perte » pour le nouveau et « Compression JPEG pseudo-sans perte » pour l'ancien encodeur.

JOURNALISATI

ON

Le niveau de journalisation des différentes outils en ligne de commande et des bibliothèques sous-jacentes peut être spécifié par l'utilisateur. Par défaut, seules les erreurs et les avertissements sont écrits sur le flux d'erreur standard. En utilisant l'option --verbose, des messages informatifs tels que les détails de traitement sont également rapportés. L'option --debug peut être utilisée pour obtenir plus de détails sur l'activité interne, par exemple à des fins de débogage. D'autres niveaux de journalisation peuvent être sélectionnés à l'aide de l'option --log-level. En mode --quiet, seules les erreurs fatales sont rapportées. Dans de tels événements d'erreur très graves, l'application se terminera généralement. Pour plus de détails sur les différents niveaux de journalisation, voir la documentation du module

"oflog".

Si la sortie de journalisation doit être écrite dans un fichier (avec rotation des fichiers journal éventuellement), dans syslog (Unix) ou dans le journal des événements (Windows), l'option --log-config peut être utilisée. Ce fichier de configuration permet également de diriger uniquement certains messages vers un flux de sortie particulier et de filtrer certains messages en fonction du module ou de l'application où ils sont générés. Un exemple de fichier de configuration est fourni dans <etcdir>/l

ogger
.cfg.

LIGNE DE

COMMANDE

Tous les outils en ligne de commande utilisent la notation suivante pour les paramètres : les crochets enclos des valeurs optionnelles (0-1), trois points de suite indiquent que plusieurs valeurs sont autorisées (1-n), une combinaison des deux signifie de 0 à n

valeurs.

Les options de ligne de commande sont distinguées des paramètres par un signe '+' ou '-' en tête, respectivement. Habituellement, l'ordre et la position des options de ligne de commande sont arbitraires (c'est-à-dire qu'elles peuvent apparaître n'importe où). Cependant, si les options sont mutuellement exclusives, l'apparence la plus à droite est utilisée. Ce comportement est conforme aux règles d'évaluation standard des shells Unix

courants.

En outre, un ou plusieurs fichiers de commandes peuvent être spécifiés en utilisant le signe '@' comme préfixe du nom de fichier (par exemple @command.txt). Un tel argument de commande est remplacé par le contenu du fichier texte correspondant (plusieurs espaces blancs sont traités comme un seul séparateur sauf s'ils apparaissent entre deux guillemets) avant toute autre évaluation. Veuillez noter qu'un fichier de commande ne peut pas contenir un autre fichier de commande. Cette approche simple mais efficace permet de résumer des combinaisons courantes d'options/paramètres et évite des lignes de commande longues et déroutantes (un exemple est fourni dans le fichier <datadir>/du

mppat
.txt).

ENVIRONNEMEN

T

L'utilitaire dcmcjpeg tentera de charger les dictionnaires de données DICOM spécifiés dans la variable d'environnement DCMDICTPATH. Par défaut, c'est-à-dire si la variable d'environnement DCMDICTPATH n'est pas définie, le fichier <datadir>/dicom.dic sera chargé, sauf si le dictionnaire est intégré à l'application (par défaut sous Windows)

.

Le comportement par défaut devrait être préféré et la variable d'environnement DCMDICTPATH n'est utilisée que lorsque des dictionnaires de données alternatifs sont nécessaires. La variable d'environnement DCMDICTPATH a le même format que la variable PATH du shell Unix en ce sens qu'un deux-points (":") sépare les entrées. Sur les systèmes Windows, un point-virgule (";") est utilisé comme séparateur. Le code du dictionnaire de données tentera de charger chaque fichier spécifié dans la variable d'environnement DCMDICTPATH. C'est une erreur si

aucun dictionnaire de do
nnées ne peut être chargé.
