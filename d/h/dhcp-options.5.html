D'OPTIONS

À partir de la version 4.3.0, lorsque ISC ajoute de nouvelles définitions d'options, ces définitions seront incluses dans le code en fonction de la définition d'un argument pour la RFC qui définit l'option dans includes/site.h. Cela vous fournit une méthode pour remplacer les définitions ISC si nécessaire - par exemple si vous avez précédemment défini l'option avec un format différent en utilisant le mécanisme de DÉFINITION DE NOUVELLES OPTIONS

ci-dessous.

Par défaut, toutes les options sont activées. Afin de désactiver une option, vous devriez modifier le fichier includes/site.h et commenter la définition de la RFC appropriée. OPTIONS DHCPV4

option dhcp-client-identifier chaîne;

Cette option peut être utilisée pour spécifier un identifiant de client DHCP dans une déclaration d'hôte, afin que dhcpd puisse trouver l'enregistrement de l'hôte en faisant correspondre l'identifiant du client.

Veuillez noter que certains clients DHCP, lorsqu'ils sont configurés avec des identifiants clients sous forme de texte ASCII, ajoutent un zéro au début du texte ASCII. Vous devrez donc peut-être écrire :

	option dhcp-client-identifier "\0foo";
plutôt que :
	option dhcp-client-identifier "foo";

option dhcp-lease-time uint32;

Cette option est utilisée dans une requête client (DHCPDISCOVER ou DHCPREQUEST) pour permettre au client de demander une durée de bail pour l'adresse IP. Dans une réponse serveur (DHCPOFFER), un serveur DHCP utilise cette option pour spécifier la durée de bail qu'il est disposé à offrir.

Cette option n'est pas directement configurable par l'utilisateur dans le serveur ; voir les options serveur max-lease-time et default-lease-time dans dhcpd.conf(5).

option dhcp-max-message-size uint16;

Cette option, lorsqu'elle est envoyée par le client, spécifie la taille maximale de toute réponse que le serveur envoie au client. Lorsqu'elle est spécifiée sur le serveur, si le client n'a pas envoyé d'option dhcp-max-message-size, la taille spécifiée sur le serveur est utilisée. Cela fonctionne aussi bien pour les réponses BOOTP que DHCP.

option dhcp-message texte;

Cette option est utilisée par un serveur DHCP pour fournir un message d'erreur à un client DHCP dans un message DHCPNAK en cas d'échec. Un client peut utiliser cette option dans un message DHCPDECLINE pour indiquer pourquoi le client a refusé les paramètres offerts.

Cette option n'est pas configurable par l'utilisateur.

option dhcp-message-type uint8;

Cette option, envoyée par le client et le serveur, spécifie le type de message DHCP contenu dans le paquet DHCP. Les valeurs possibles (tirées directement de RFC2132) sont :

             1     DHCPDISCOVER
             2     DHCPOFFER
             3     DHCPREQUEST
             4     DHCPDECLINE
             5     DHCPACK
             6     DHCPNAK
             7     DHCPRELEASE
             8     DHCPINFORM

Cette option n'est pas configurable par l'utilisateur.

option dhcp-option-overload uint8;

Cette option est utilisée pour indiquer que les champs ´sname´ ou ´file´ du DHCP sont surchargés en les utilisant pour transporter des options DHCP. Un serveur DHCP insère cette option si les paramètres renvoyés dépassent l'espace habituel alloué aux options.

Si cette option est présente, le client interprète les champs supplémentaires spécifiés après avoir terminé l'interprétation des champs d'options standard.

Les valeurs légales pour cette option sont :

             1     le champ ´file´ est utilisé pour stocker des options
             2     le champ ´sname´ est utilisé pour stocker des options
             3     les deux champs sont utilisés pour stocker des options

Cette option n'est pas configurable par l'utilisateur.

option dhcp-parameter-request-list uint8 [, uint8... ];

Cette option, lorsqu'elle est envoyée par le client, spécifie quelles options le client souhaite que le serveur renvoie. Normalement, dans le client DHCP ISC, cela est fait à l'aide de la instruction request. Si cette option n'est pas spécifiée par le client, le serveur DHCP renvoie normalement toutes les options valides dans la portée et qui rentrent dans la réponse. Lorsque cette option est spécifiée sur le serveur, le serveur renvoie les options spécifiées. Cela peut être utilisé pour forcer un client à accepter des options qu'il n'a pas demandées, et cela peut également être utilisé pour adapter la réponse du serveur DHCP pour les clients qui peuvent avoir besoin d'un ensemble d'options plus limité que celles que le serveur renverrait normalement.

option dhcp-rebinding-time uint32;

Cette option spécifie le nombre de secondes à partir du moment où un client obtient une adresse jusqu'à ce que le client passe à l'état REBINDING.

Cette option est configurable par l'utilisateur, mais elle sera ignorée si la valeur est supérieure ou égale à la durée du bail.

Pour faciliter la migration DHCPv4+DHCPv6 à l'avenir, toute valeur configurée dans cette option est également utilisée comme temps DHCPv6 « T1 » (renouvellement).

option dhcp-renewal-time uint32;

Cette option spécifie le nombre de secondes à partir du moment où un client obtient une adresse jusqu'à ce que le client passe à l'état RENEWING.

Cette option est configurable par l'utilisateur, mais elle sera ignorée si la valeur est supérieure ou égale au temps de re-liaison ou à la durée du bail.

Pour faciliter la migration DHCPv4+DHCPv6 à l'avenir, toute valeur configurée dans cette option est également utilisée comme temps DHCPv6 « T2 » (re-liaison).

option dhcp-requested-address adresse-ip;

Cette option est utilisée par le client dans un DHCPDISCOVER pour demander qu'une adresse IP particulière soit attribuée.

Cette option n'est pas configurable par l'utilisateur.

option dhcp-server-identifier adresse-ip;

Cette option est utilisée dans les messages DHCPOFFER et DHCPREQUEST, et peut facultativement être incluse dans les messages DHCPACK et DHCPNAK. Les serveurs DHCP incluent cette option dans le DHCPOFFER afin de permettre au client de distinguer les offres de bail. Les clients DHCP utilisent le contenu du champ « identifiant du serveur » comme adresse de destination pour tous les messages DHCP envoyés en unicast au serveur DHCP. Les clients DHCP indiquent également quelle offre parmi plusieurs est acceptée en incluant cette option dans un message DHCPREQUEST.

La valeur de cette option est l'adresse IP du serveur.

Cette option n'est pas directement configurable par l'utilisateur. Voir l'option serveur server-identifier dans dhcpd.conf(5).

option domain-name texte;

Cette option spécifie le nom de domaine que le client doit utiliser lors de la résolution des noms d'hôtes via le système de noms de domaine.

option domain-name-servers adresse-ip [, adresse-ip... ];

option domain-search liste-de-domaines;

L'option domain-search spécifie une « liste de recherche » de noms de domaine à utiliser par le client pour localiser les noms de domaine non entièrement qualifiés. La différence entre cette option et l'utilisation historique de l'option domain-name pour les mêmes fins est que cette option est codée en labels compressés RFC1035 sur le réseau. Par exemple :

  option domain-search "example.com", "sales.example.com",
                       "eng.example.com";

OPTION RELAY AGENT INFORMATION

Un brouillon de l'IETF, draft-ietf-dhc-agent-options-11.txt, définit une série d'options encapsulées qu'un agent relais peut ajouter à un paquet DHCP lors de son transfert vers le serveur DHCP. Le serveur peut alors prendre des décisions d'allocation d'adresses (ou toute autre décision qu'il souhaite) basées sur ces options. Le serveur renvoie également ces options dans toutes les réponses qu'il envoie via l'agent relais, de sorte que l'agent relais puisse utiliser les informations de ces options à des fins de distribution ou de comptabilité.

Le brouillon actuel définit deux options. Pour référencer ces options dans le serveur dhcp, spécifiez le nom de l'espace d'options, "agent", suivi d'un point, suivi du nom de l'option. Il n'est normalement pas utile de définir des valeurs pour ces options dans le serveur, bien que cela soit autorisé. Ces options ne sont pas prises en charge dans le client.

option agent.circuit-id string;

La sous-option circuit-id encode un identifiant local à l'agent du circuit à partir duquel un paquet DHCP client-serveur a été reçu. Elle est destinée à être utilisée par les agents pour relayer les réponses DHCP vers le circuit approprié. Le format de cette option est actuellement défini comme dépendant du fournisseur, et le restera probablement, bien que le brouillon actuel permette la possibilité de standardiser le format à l'avenir.

option agent.remote-id string;

La sous-option remote-id encode des informations sur l'extrémité distante d'un circuit. Des exemples de ce qu'elle pourrait contenir incluent des informations d'identification de l'appelant, des informations d'identification utilisateur, une adresse ATM distante, un identifiant de modem câble et des éléments similaires. En principe, la signification n'est pas bien spécifiée, et elle doit généralement être considérée comme un objet opaque qui est garanti administrativement d'être unique à une extrémité distante particulière d'un circuit.

option agent.DOCSIS-device-class uint32;

La sous-option DOCSIS-device-class est destinée à transmettre des informations sur le point d'extrémité hôte, le matériel et le logiciel, dont le système d'exploitation hôte ou le serveur DHCP pourraient ne pas avoir conscience autrement (mais que le relais est capable de distinguer). Ceci est implémenté sous la forme d'un champ de 32 bits (4 octets), chaque bit représentant un drapeau décrivant l'hôte d'une de ces manières. Jusqu'à présent, seul le bit zéro (le moins significatif) est défini dans la RFC3256. Si ce bit est défini à un, l'hôte est considéré comme un modem câble contrôlé par le CPE (CCCM). Tous les autres bits sont réservés.

option agent.link-selection ip-address;

La sous-option link-selection est fournie par les agents relais pour informer les serveurs du sous-réseau auquel le client est réellement connecté. Ceci est utile dans les cas où le giaddr (vers lequel les réponses doivent être envoyées à l'agent relais) n'est pas sur le même sous-réseau que le client. Lorsque cette option est présente dans un paquet d'un agent relais, le serveur DHCP utilisera son contenu pour trouver un sous-réseau déclaré dans la configuration, et de là, remonter d'une étape supplémentaire vers tout réseau partagé dans lequel le sous-réseau peut être défini ; le client peut se voir attribuer n'importe quelle adresse dans ce réseau partagé, comme il convient normalement.

SOUS-OPTIONS CLIENT FQDN

L'option Client FQDN, actuellement définie dans le brouillon Internet draft-ietf-dhc-fqdn-option-00.txt, n'est pas encore une norme, mais elle est déjà largement utilisée, c'est pourquoi nous l'avons implémentée. En raison de la complexité du format de l'option, nous l'avons implémentée comme un espace de sous-options plutôt qu'une seule option. En général, cette option ne doit pas être configurée par l'utilisateur ; elle doit plutôt être utilisée dans le cadre d'un système de mise à jour DNS automatique.

option fqdn.no-client-update flag;

Lorsque le client envoie ceci, si c'est vrai, cela signifie que le client ne tentera pas de mettre à jour son enregistrement A. Envoyé par le serveur au client, cela signifie que le client *ne doit pas* mettre à jour son propre enregistrement A.

option fqdn.server-update flag;

Lorsque le client envoie ceci au serveur, il demande que le serveur mette à jour son enregistrement A. Envoyé par le serveur, cela signifie que le serveur a mis à jour (ou est sur le point de mettre à jour) l'enregistrement A du client.

option fqdn.encoded flag;

Si vrai, cela indique que le nom de domaine inclus dans l'option est encodé au format filaire DNS, plutôt qu'en texte ASCII brut. Le client le définit normalement à false s'il ne prend pas en charge le format filaire DNS dans l'option FQDN. Le serveur doit toujours renvoyer la même valeur que celle envoyée par le client. Lorsque cette valeur est définie du côté configuration, elle contrôle le format dans lequel la sous-option *fqdn.fqdn* est encodée.

option fqdn.rcode1 flag;

option fqdn.rcode2 flag;

Ces options spécifient le résultat des mises à jour des enregistrements A et PTR, respectivement, et ne sont envoyées que par le serveur DHCP au client DHCP. Les valeurs de ces champs sont celles définies dans la spécification du protocole DNS.

option fqdn.fqdn text;

Spécifie le nom de domaine que le client souhaite utiliser. Il peut s'agir d'un nom de domaine entièrement qualifié, ou d'une seule étiquette. S'il n'y a pas de caractère point final ( . ) dans le nom, il n'est pas entièrement qualifié, et le serveur mettra généralement à jour ce nom dans un domaine défini localement.

option fqdn.hostname --never set--;

LES SOUS-OPTIONS FQDN

option fqdn.fqdn string;

Cette option ne doit jamais être définie, mais elle peut être lue à l'aide des opérateurs option et config-option dans une expression. Dans ce cas, elle renvoie le nom de domaine complet (FQDN) qui a été envoyé par le client. Par exemple, si le client envoie "foo.example.com.", alors fqdn.fqdn sera "foo.example.com.".

option fqdn.hostname --jamais définir--;

Cette option ne doit jamais être définie, mais elle peut être lue à l'aide des opérateurs option et config-option dans une expression. Dans ce cas, elle renvoie la première étiquette de la sous-option fqdn.fqdn. Par exemple, si la valeur de fqdn.fqdn est "foo.example.com.", alors fqdn.hostname sera "foo".

option fqdn.domainname --jamais définir--;

Cette option ne doit jamais être définie, mais elle peut être lue à l'aide des opérateurs option et config-option dans une expression. Dans ce cas, elle renvoie toutes les étiquettes après la première étiquette de la sous-option fqdn.fqdn. Par exemple, si la valeur de fqdn.fqdn est "foo.example.com.", alors fqdn.domainname sera "example.com.". Si la valeur de cette sous-option n'est pas définie, cela signifie qu'un nom non qualifié a été envoyé dans l'option fqdn, ou qu'aucune option fqdn n'a été envoyée du tout.

Si vous souhaitez utiliser l'une de ces sous-options, nous vous recommandons vivement de vous référer au brouillon de l'option FQDN client (ou à la norme, lorsqu'elle deviendra une norme) - la documentation ici est vague et incomplète en comparaison, et est uniquement destinée à être consultée par les personnes qui comprennent déjà la spécification de l'option FQDN client.

LES SOUS-OPTIONS NETWARE/IP

RFC2242 définit un ensemble d'options encapsulées pour les clients Novell NetWare/IP. Pour utiliser ces options dans le serveur dhcp, spécifiez le nom de l'espace d'options, "nwip", suivi d'un point, suivi du nom de l'option. Les options suivantes peuvent être spécifiées :

option nwip.nsq-broadcast flag;

Si vrai, le client doit utiliser la requête du serveur le plus proche de NetWare (Nearest Server Query) pour localiser un serveur NetWare/IP. Le comportement du client Novell si cette sous-option est fausse, ou absente, n'est pas spécifié.

option nwip.preferred-dss ip-address [, ip-address...];

Cette sous-option spécifie une liste de jusqu'à cinq adresses IP, chacune d'elles devant être l'adresse IP d'un serveur SAP/RIP NetWare Domain Service (DSS).

option nwip.nearest-nwip-server ip-address
[, ip-address...];

Cette sous-option spécifie une liste de jusqu'à cinq adresses IP, chacune d'elles devant être l'adresse IP d'un serveur NetWare IP le plus proche (Nearest NetWare IP server).

option nwip.autoretries uint8;

Spécifie le nombre de fois qu'un client NetWare/IP doit tenter de communiquer avec un serveur DSS donné au démarrage.

option nwip.autoretry-secs uint8;

Spécifie le nombre de secondes que le client Netware/IP doit attendre entre les tentatives lors de l'établissement de communications avec un serveur DSS au démarrage.

option nwip.nwip-1-1 uint8;

Si vrai, le client NetWare/IP doit supporter la compatibilité NetWare/IP version 1.1. Ceci n'est nécessaire que si le client doit contacter des serveurs Netware/IP version 1.1.

option nwip.primary-dss ip-address;

Spécifie l'adresse IP du serveur de service principal SAP/RIP de domaine (DSS) pour ce domaine NetWare/IP. L'utilitaire d'administration NetWare/IP utilise cette valeur comme DSS principal lors de la configuration d'un serveur DSS secondaire.

OPTIONS DHCPV6 STANDARD

Les options DHCPv6 diffèrent des options DHCPv4 partiellement en raison de l'utilisation de balises de code et de longueur sur 16 bits, mais les options de longueur nulle sont légalement possibles en DHCPv6, et plusieurs options sont traitées différemment. Alors qu'en DHCPv4 plusieurs options seraient concaténées pour former une seule option, en DHCPv6 elles sont attendues comme des instanciations individuelles. De manière compréhensible, de nombreuses options ne sont pas "autorisées" à avoir plusieurs instances dans un paquet - normalement, ce sont des options qui sont traitées par le logiciel du protocole DHCP, et non par les utilisateurs ou les applications.

option dhcp6.client-id string;

Cette option spécifie l'identifiant DUID du client. Les DUIDs sont similaires mais différentes des identifiants client DHCPv4 - il existe des types de DUID documentés :

duid-llt

ACCES AUX OPTIONS DE RELAIS DHCPV6

v6relay (relay-number, option) Cette option permet d'accéder à une option qui a été ajoutée à un paquet par un agent relais. La valeur de relay-number sélectionne le relais à examiner et option est l'option à trouver. Dans DHCPv6, chaque relais encapsule le message précédent entier dans une option, ajoute ses propres options (le cas échéant) et envoie le résultat. Le RFC spécifie une limite de 32 sauts. Un relay-number de 0 est une opération nulle et signifie ne pas examiner les relais. 1 est le relais le plus proche du client, 2 serait le suivant en provenance du client, et ainsi de suite. Toute valeur supérieure au nombre maximum de sauts est celle qui est la plus proche du serveur, indépendamment du nombre. Pour utiliser cette option dans une instruction de classe, vous auriez quelque chose comme ceci :

match if v6relay(1, option dhcp6.subscriber-id) = "client_1";

DEFINITION DE NOUVELLES OPTIONS

Le client et le serveur DHCP de l'Internet Systems Consortium offrent la possibilité de définir de nouvelles options. Chaque option DHCP a un nom, un code et une structure. Le nom est utilisé par vous pour faire référence à l'option. Le code est un nombre, utilisé par le serveur et le client DHCP pour faire référence à une option. La structure décrit à quoi ressemblent le contenu d'une option.

Pour définir une nouvelle option, vous devez choisir un nom pour celle-ci qui n'est pas déjà utilisé pour une autre option - par exemple, vous ne pouvez pas utiliser "host-name" car le protocole DHCP définit déjà une option host-name, qui est documentée plus loin dans cette page de manuel. Si un nom d'option n'apparaît pas dans cette page de manuel, vous pouvez l'utiliser, mais il est probablement judicieux de mettre une sorte de chaîne unique au début afin de pouvoir être sûr que les options futures ne prendront pas votre nom. Par exemple, vous pourriez définir une option, "local-host-name", en vous sentant confiant qu'aucun nom d'option DHCP officiel ne commencera jamais par "local".

Une fois que vous avez choisi un nom, vous devez choisir un code. Tous les codes compris entre 224 et 254 sont réservés comme options DHCP ´locales au site´, vous pouvez donc en choisir un parmi ceux-ci pour votre site (pas pour votre produit/application). Dans RFC3942, l'espace local au site a été déplacé de 128 à 224. En pratique, certains fournisseurs ont interprété le protocole de manière assez laxiste et ont utilisé eux-mêmes des valeurs de code d'option supérieures à 128. Il n'y a pas de véritable moyen d'éviter ce problème, et on pensait qu'il n'y aurait pas trop de problèmes en pratique. Si vous rencontrez un code d'option documenté par un fournisseur dans l'un ou l'autre des espaces locaux au site, veuillez contacter votre fournisseur et l'informer de rfc3942.

La structure d'une option est simplement le format dans lequel les données de l'option apparaissent. Le serveur ISC DHCP prend actuellement en charge quelques types simples, tels que les entiers, les booléens, les chaînes et les adresses IP, et il prend également en charge la capacité de définir des tableaux de types simples ou des tableaux de séquences fixes de types.

Les nouvelles options sont déclarées comme suit :

option nouveau-nom code nouveau-code = définition ;

Les valeurs de nouveau-nom et nouveau-code doivent être le nom que vous avez choisi pour la nouvelle option et le code que vous avez choisi. La définition doit être la définition de la structure de l'option.

Les définitions de types d'options simples suivantes sont prises en charge :

BOOLEAN

option nouveau-nom code nouveau-code = boolean ;

Une option de type booléen est un drapeau avec une valeur soit activée, soit désactivée (ou vrai, soit faux). Ainsi, un exemple d'utilisation du type booléen serait :

option use-zephyr code 180 = boolean;
option use-zephyr on;
INTEGER

option nouveau-nom code nouveau-code = signe integer largeur ;

Le jeton signe doit être vide, unsigned ou signed. La largeur peut être 8, 16 ou 32, et fait référence au nombre d'octets dans l'entier. Donc, par exemple, les deux lignes suivantes montrent une définition de l'option sql-connection-max et son utilisation :

option sql-connection-max code 192 = unsigned integer 16;
option sql-connection-max 1536;
IP-ADDRESS

option nouveau-nom code nouveau-code = ip-address ;

Une option dont la structure est une adresse IP peut être exprimée soit comme un nom de domaine, soit comme un quad pointé. Ainsi, l'exemple suivant est une utilisation du type ip-address :

option sql-server-address code 193 = ip-address;
option sql-server-address sql.example.com;
IP6-ADDRESS

option nouveau-nom code nouveau-code = ip6-address ;

Une option dont la structure est une adresse IPv6 doit être exprimée comme une adresse IPv6 valide. Ce qui suit est un exemple d'utilisation du type ip6-address :

option dhcp6.some-server code 1234 = array of ip6-address;
option dhcp6.some-server 3ffe:bbbb:aaaa:aaaa::1, 3ffe:bbbb:aaaa:aaaa::2;

TEXT

option nouveau-nom code nouveau-code = text ;

Une option dont le type est texte encodera une chaîne de texte ASCII. Par exemple :

option sql-default-connection-name code 194 = text;
option sql-default-connection-name "PRODZA";

DATA STRING

option nouveau-nom code nouveau-code = string ;

Une option dont le type est une chaîne de données est essentiellement juste une collection d'octets, et peut être spécifiée soit comme du texte entre guillemets, comme le type texte, soit comme une liste de contenus hexadécimaux séparés par des deux-points dont les valeurs doivent être comprises entre 0 et FF. Par exemple :

option sql-identification-token code 195 = string;
option sql-identification-token 17:23:19:a6:42:ea:99:7c:22;

DOMAIN-LIST

option nouveau-nom code nouveau-code = domain-list [compressed] ;

Une option dont le type est domain-list est une liste de noms de domaine formatée RFC1035 (sur le fil, "DNS Format"), séparés par des étiquettes racines. Le mot-clé facultatif compressed indique si l'option doit être compressée par rapport au début du contenu de l'option (pas du contenu du paquet).

En cas de doute, omettez le mot-clé compressed. Lorsque le logiciel reçoit une option compressée et que le mot-clé compressed est omis, il décompresse toujours l'option (par rapport au champ de contenu de l'option). Le mot-clé contrôle uniquement si les paquets transmis sont compressés ou non.

Notez que lorsque les options au format domain-list sont sorties sous forme de variables d'environnement vers dhclient-script(8), le mécanisme d'échappement DNS standard est utilisé : elles sont décimales. Ceci est approprié pour une utilisation directe dans par exemple /etc/resolv.conf.

ENCAPSULATION

option nouveau-nom code nouveau-code = encapsulate identificateur ;

Une option dont le type est encapsulate encapsulera le contenu de l'espace d'options spécifié dans identificateur. Des exemples d'options encapsulées dans le protocole DHCP tel qu'il existe actuellement incluent l'option vendor-encapsulated-options, l'option netware-suboptions et l'option relay-agent-information.

option space local;
option local.demo code 1 = text;
option local-encapsulation code 197 = encapsulate local;
option local.demo "demo";

ARRAYS

Les options peuvent contenir des tableaux de tous les types ci-dessus, à l'exception des types texte et chaîne de données, qui ne sont actuellement pas pris en charge dans les tableaux. Un exemple de définition de tableau est le suivant :

option kerberos-servers code 200 = array of ip-address;
option kerberos-servers 10.20.10.1, 10.20.11.1;
RECORDS

Les options peuvent également contenir des structures de données composées d'une séquence de types de données, ce qui est parfois appelé un type d'enregistrement. Par exemple :

option contrived-001 code 201 = { boolean, integer 32, text };
option contrived-001 on 1772 "contrivance";
Il est également possible d'avoir des options qui sont des tableaux d'enregistrements, par exemple : 
option new-static-routes code 201 = array of {
	ip-address, ip-address, ip-address, integer 8 };
option static-routes
	10.0.0.0 255.255.255.0 net-0-rtr.example.com 1,
	10.0.1.0 255.255.255.0 net-1-rtr.example.com 1,
	10.2.0.0 255.255.224.0 net-2-0-rtr.example.com 3;

OPTIONS ENCAPSULÉES PAR LE FABRICANT

Le protocole DHCP définit l'option vendor-encapsulated-options, qui permet aux fabricants de définir leurs propres options qui seront envoyées encapsulées dans une option DHCP standard. Il définit également l'option Vendor Identified Vendor Sub Options ("VIVSO"), et le protocole DHCPv6 définit l'option Vendor-specific Information Option ("VSIO"). Le format de toutes ces options est généralement une chaîne d'options interne, similaire aux autres options DHCP normales. Les options VIVSO et VSIO diffèrent en ce qu'elles contiennent des options correspondant aux numéros d'Enterprise-ID des fournisseurs (attribués par l'IANA), qui contiennent ensuite des options selon les spécifications de chaque fournisseur. Vous devrez vous référer à la documentation de votre fournisseur pour former des options selon ses spécifications.

La valeur de ces options peut être définie dans

de deux manières. La première consiste à spécifier directement les données, en utilisant une chaîne de texte ou une liste de valeurs hexadécimales séparées par des deux-points. Pour vous aider à formuler ces chaînes, veuillez consulter RFC2132 pour l'option DHCPv4 Vendor Specific Information Option, RFC3925 pour l'option DHCPv4 Vendor Identified Vendor Sub Options, ou RFC3315 pour l'option DHCPv6 Vendor-specific Information Option. Par exemple :

option vendor-encapsulated-options
    2:4:
	AC:11:41:1:
    3:12:
	73:75:6e:64:68:63:70:2d:73:65:72:76:65:72:31:37:2d:31:
    4:12:
	2f:65:78:70:6f:72:74:2f:72:6f:6f:74:2f:69:38:36:70:63;
option vivso
    00:00:09:bf:0E:
	01:0c:
	    48:65:6c:6c:6f:20:77:6f:72:6c:64:21;
option dhcp6.vendor-opts
    00:00:09:bf:
	00:01:00:0c:
	    48:65:6c:6c:6f:20:77:6f:72:6c:64:21;

La deuxième manière de définir la valeur de ces options est de faire en sorte que le serveur DHCP génère un tampon d'options spécifiques au fournisseur. Pour ce faire, vous devez faire quatre choses : définir un espace d'options, définir des options dans cet espace d'options, fournir des valeurs pour celles-ci et spécifier que cet espace d'options doit être utilisé pour générer l'option concernée.

Pour définir un nouvel espace d'options dans lequel les options du fournisseur peuvent être stockées, utilisez la déclaration option space :

option space name [ [ code width number ] [ length width number ] [ hash size number ] ] ;

Où les nombres suivant code width, length width, et hash size identifient respectivement le nombre d'octets utilisés pour décrire les codes d'options, les longueurs d'options, et la taille en buckets des tables de hachage pour conserver les options dans cet espace (la plupart des espaces d'options DHCPv4 utilisent des codes et des longueurs sur 1 octet, ce qui est la valeur par défaut, alors que la plupart des espaces d'options DHCPv6 utilisent des codes et des longueurs sur 2 octets).

Les largeurs de code et de longueur sont utilisées dans le protocole DHCP - vous devez configurer ces nombres pour qu'ils correspondent à l'espace d'options applicable que vous configurez. Ils valent chacun 1 par défaut. Les valeurs valides pour les largeurs de code sont 1, 2 ou 4. Les valeurs valides pour les largeurs de longueur sont 0, 1 ou 2. La plupart des espaces d'options DHCPv4 utilisent des codes et des longueurs sur 1 octet, ce qui est la valeur par défaut, alors que la plupart des espaces d'options DHCPv6 utilisent des codes et des longueurs sur 2 octets. Une longueur de zéro octet produit des options similaires à l'option DHCPv6 Vendor-specific Information Option - mais pas leur contenu !

Les valeurs par défaut de la taille du hachage dépendent de la code width sélectionnée, et peuvent être 254 ou 1009. Les valeurs valides vont de 1 à 65535. Notez que plus vous configurez cette valeur élevée, plus de mémoire sera utilisée. Il est considéré comme une bonne pratique de configurer une valeur légèrement supérieure au nombre estimé d'options que vous prévoyez de configurer dans l'espace. Dans les versions précédentes d'ISC DHCP (jusqu'à et y compris DHCP 3.0.*), cette valeur était fixée à 9973.

Le nom peut ensuite être utilisé dans les définitions d'options, comme décrit précédemment dans ce document. Par exemple :

option space SUNW code width 1 length width 1 hash size 3;
option SUNW.server-address code 2 = ip-address;
option SUNW.server-name code 3 = text;
option SUNW.root-path code 4 = text;
option space ISC code width 1 length width 1 hash size 3;
option ISC.sample code 1 = text;
option vendor.ISC code 2495 = encapsulate vivso-sample;
option vendor-class.ISC code 2495 = text;
option ISC.sample "configuration text here";
option vendor-class.ISC "vendor class here";
option space docsis code width 2 length width 2 hash size 17;
option docsis.tftp-servers code 32 = array of ip6-address;
option docsis.cablelabs-configuration-file code 33 = text;
option docsis.cablelabs-syslog-servers code 34 = array of ip6-address;
option docsis.device-id code 36 = string;
option docsis.time-servers code 37 = array of ip6-address;
option docsis.time-offset code 38 = signed integer 32;
option vsio.docsis code 4491 = encapsulate docsis;
Une fois que vous avez défini un espace d'options et le format de certaines options, vous pouvez mettre en place des portées qui définissent des valeurs pour ces options, et vous pouvez dire quand les utiliser. Par exemple, supposez que vous vouliez gérer deux classes différentes de clients. En utilisant la définition d'espace d'options montrée dans l'exemple précédent, vous pouvez envoyer différentes valeurs d'options à différents clients en fonction de l'option vendor-class-identifier que les clients envoient, comme suit : 
class "vendor-classes" {
  match option vendor-class-identifier;
}
subclass "vendor-classes" "SUNW.Ultra-5_10" {
  vendor-option-space SUNW;
  option SUNW.root-path "/export/root/sparc";
}
subclass "vendor-classes" "SUNW.i86pc" {
  vendor-option-space SUNW;
  option SUNW.root-path "/export/root/i86pc";
}
option SUNW.server-address 172.17.65.1;
option SUNW.server-name "sundhcp-server17-1";
option vivso-sample.sample "Hello world!";
option docsis.tftp-servers ::1;

Comme vous pouvez le voir dans l'exemple précédent, les règles de portée habituelles s'appliquent, vous pouvez donc définir des valeurs globales dans la portée globale, et définir uniquement des valeurs spécifiques à une classe particulière dans la portée locale. La vendor-option-space déclaration indique au serveur DHCP d' utiliser les options dans l'espace d'options SUNW pour construire l'option DHCPv4 vendor-encapsulated-options . C'est une limitation de cette option - les options DHCPv4 VIVSO et DHCPv6 VSIO peuvent avoir plusieurs définitions de fournisseurs à la fois (même transmises au même client), il n'est donc pas nécessaire de configurer cela.
