GROUP   DECLARATIONS


Group declarations are a way of managing groups of subnets or
    networks that share common configuration parameters. All group members
    inherit parameters from the group declaration. If a parameter is declared
    multiple times, the most specific declaration takes precedence. For example,
    if a parameter is declared in a group declaration and also in a subnet
    declaration within that group, the subnet declaration will be used.

POOLS   D'ADRESSES


Les déclarations pool et pool6 peuvent être utilisées
    pour spécifier un pool d'adresses qui sera traité différemment d'un autre
    pool d'adresses, même sur le même segment réseau ou sous-réseau. Par
    exemple, vous pourriez vouloir fournir un large ensemble d'adresses qui
    peuvent être assignées aux clients DHCP enregistrés auprès de votre serveur
    DHCP, tout en fournissant un plus petit ensemble d'adresses, potentiellement
    avec des baux de courte durée, disponibles pour les clients inconnus. Si vous
    avez un pare-feu, vous pourriez être en mesure de faire en sorte que les
    adresses d'un pool aient accès à Internet, tandis que les adresses d'un autre
    pool n'en aient pas, encourageant ainsi les utilisateurs à enregistrer leurs
    clients DHCP. Pour ce faire, vous mettriez en place une paire de déclarations
    de pools :


subnet 10.0.0.0 netmask 255.255.255.0 {
  option routers 10.0.0.254;
  # Les clients inconnus obtiennent ce pool.
  pool {
    option domain-name-servers bogus.example.com;
    max-lease-time 300;
    range 10.0.0.200 10.0.0.253;
    allow unknown-clients;
  }
  # Les clients connus obtiennent ce pool.
  pool {
    option domain-name-servers ns1.example.com, ns2.example.com;
    max-lease-time 28800;
    range 10.0.0.5 10.0.0.199;
    deny unknown-clients;
  }
}


Il est également possible de configurer des sous-réseaux
    entièrement différents pour les clients connus et inconnus - les pools
    d'adresses existent au niveau des réseaux partagés, de sorte que les plages
    d'adresses dans les déclarations de pools peuvent être sur des sous-réseaux
    différents.


Comme vous pouvez le voir dans l'exemple précédent, les pools
    peuvent avoir des listes d'autorisation qui contrôlent quels clients ont
    accès au pool et lesquels n'en ont pas. Chaque entrée dans la liste d'autorisation
    d'un pool est introduite par le mot-clé allow ou deny. Si un pool
    a une liste d'autorisation, alors seuls les clients qui correspondent à des
    entrées spécifiques sur la liste d'autorisation seront éligibles pour se voir
    assigner des adresses du pool. Si un pool a une liste de refus, alors seuls les
    clients qui ne correspondent à aucune entrée sur la liste de refus seront
    éligibles. Si des listes d'autorisation et de refus existent pour un pool,
    alors seuls les clients qui correspondent à la liste d'autorisation et qui ne
    correspondent pas à la liste de refus seront autorisés d'accès.


La déclaration pool6 est similaire à la déclaration
    pool. Actuellement, elle n'est autorisée qu'à l'intérieur d'une
    déclaration subnet6 et ne peut pas être incluse directement dans une
    déclaration de réseau partagé. En plus de l'instruction range6, elle
    permet d'inclure l'instruction prefix6. Vous pouvez inclure des
    instructions range6 pour NA et TA ainsi que des instructions
    prefix6 dans une seule instruction pool6.






ALLOCATION   DYNAMIQUE D'ADRESSES


L'allocation d'adresses n'est en fait effectuée que lorsqu'un client
    est à l'état INIT et a envoyé un message DHCPDISCOVER. Si le client pense
    avoir un bail valide et envoie un DHCPREQUEST pour initier ou renouveler ce
    bail, le serveur n'a que trois choix : il peut ignorer le DHCPREQUEST, envoyer
    un DHCPNAK pour dire au client qu'il doit cesser d'utiliser l'adresse, ou
    envoyer un DHCPACK, disant au client de continuer à utiliser l'adresse pendant un
    certain temps.


Si le serveur trouve l'adresse que le client demande, et que cette
    adresse est disponible pour le client, le serveur enverra un DHCPACK. Si
    l'adresse n'est plus disponible, ou si le client n'est pas autorisé à
    l'avoir, le serveur enverra un DHCPNAK. Si le serveur ne sait rien de
    l'adresse, il restera silencieux, à moins que l'adresse ne soit incorrecte pour
    le segment réseau auquel le client est attaché et que le serveur soit
    autoritaire pour ce segment réseau, auquel cas le serveur enverra un DHCPNAK
    même s'il ne connaît pas l'adresse.


Il peut y avoir une déclaration d'hôte correspondant à
    l'identification du client. Si cette déclaration d'hôte contient une
    déclaration fixed-address qui liste une adresse IP valide pour le segment
    réseau auquel le client est connecté, le serveur DHCP n'effectuera jamais
    d'allocation dynamique d'adresses. Dans ce cas, le client est obligé
    d'accepter l'adresse spécifiée dans la déclaration d'hôte. Si le client envoie
    un DHCPREQUEST pour une autre adresse, le serveur répondra par un DHCPNAK.


Lorsque le serveur DHCP alloue une nouvelle adresse à un client
    (rappelez-vous, cela ne se produit que si le client a envoyé un DHCPDISCOVER),
    il vérifie d'abord si le client a déjà un bail valide sur une adresse IP, ou
    s'il y a une ancienne adresse IP que le client avait auparavant et qui n'a pas
    encore été réattribuée. Dans ce cas, le serveur prendra cette adresse et la
    vérifiera pour voir si le client est toujours autorisé à l'utiliser. Si le
    client n'est plus autorisé à l'utiliser, le bail est libéré si le serveur pensait
    qu'il était toujours utilisé - le fait que le client ait envoyé un DHCPDISCOVER
    prouve au serveur que le client n'utilise plus le bail.


Si aucun bail existant n'est trouvé, ou si le client est interdit de
    recevoir le bail existant, alors le serveur recherchera dans la liste des pools
    d'adresses pour le segment réseau auquel le client est attaché un bail qui n'est
    pas utilisé et que le client est autorisé à avoir. Il parcourt chaque
    déclaration de pool en séquence (toutes les déclarations range qui
    apparaissent en dehors des déclarations de pools sont regroupées en un seul
    pool sans liste d'autorisation). Si la liste d'autorisation du pool permet
    d'allouer une adresse de ce pool au client, le pool est examiné pour voir si
    une adresse est disponible. Si c'est le cas, alors le client se voit
    tentativement assigner cette adresse. Sinon, le pool suivant est testé. Si aucune
    adresse n'est trouvée qui puisse être assignée au client, aucune réponse
    n'est envoyée au client.


Si une adresse est trouvée que le client est autorisé à avoir, et
    qui n'a jamais été assignée à aucun client auparavant, l'adresse est
    immédiatement allouée au client. Si l'adresse est disponible pour
    l'allocation mais a été précédemment assignée à un client différent, le
    serveur continuera à chercher dans l'espoir de trouver une adresse qui n'a
    jamais été assignée auparavant à un client.


Le serveur DHCP génère la liste des adresses IP disponibles à partir
    d'une table de hachage. Cela signifie que les adresses ne sont triées dans aucun
    ordre particulier, et il n'est donc pas possible de prédire l'ordre dans
    lequel le serveur DHCP allouera les adresses IP. Les utilisateurs des
    versions précédentes du serveur DHCP ISC peuvent s'être habitués à ce que le
    serveur DHCP alloue les adresses IP dans l'ordre croissant, mais ce n'est
    plus possible, et il n'y a aucun moyen de configurer ce comportement avec la
    version 3 du serveur DHCP ISC.






PRÉVENTION   DES CONFLITS D'ADRESSES IP


Le serveur DHCP vérifie si les adresses IP sont utilisées avant de les
    allouer aux clients. Il le fait en envoyant un message ICMP Echo request à
    l'adresse IP en cours d'allocation. Si aucune réponse ICMP Echo n'est reçue en
    une seconde, l'adresse est supposée être libre. Cela n'est fait que pour les
    baux spécifiés dans des instructions range, et uniquement lorsque le bail est
    supposé être libre par le serveur DHCP - c'est-à-dire que le serveur DHCP ou
    son pair de basculement n'a pas listé le bail comme étant utilisé.


Si une réponse est reçue à une requête ICMP Echo, le serveur DHCP
    suppose qu'il y a une erreur de configuration - l'adresse IP est utilisée par
    un hôte sur le réseau qui n'est pas un client DHCP. Il marque l'adresse comme
    abandonnée et ne l'assignera pas aux clients. Le bail restera abandonné pendant
    un minimum de abandon-lease-time secondes.


Si un client DHCP essaie d'obtenir une adresse IP, mais qu'aucune
    n'est disponible, mais qu'il y a des adresses IP abandonnées, alors le serveur
    DHCP tentera de récupérer une adresse IP abandonnée. Il marque une adresse IP
    comme libre, puis effectue la même vérification ICMP Echo request décrite
    précédemment. S'il n'y a pas de réponse à la requête ICMP Echo, l'adresse est
    assignée au client.


Le serveur DHCP ne parcourt pas les adresses IP abandonnées si la
    première adresse IP qu'il essaie de récupérer est libre. Au lieu de cela, lorsque
    le prochain DHCPDISCOVER arrive du client, il tentera une nouvelle allocation
    en utilisant la même méthode décrite ici, et essaiera typiquement une nouvelle
    adresse IP.






BASCULEMENT   DHCP


Cette version du serveur DHCP ISC prend en charge le protocole de
    basculement DHCP tel que documenté dans draft-ietf-dhc-failover-12.txt. Ce
    n'est pas un document de protocole final, et nous n'avons pas effectué de tests
    d'interopérabilité avec les implémentations de ce protocole d'autres vendeurs,
    vous ne devez donc pas supposer que cette implémentation est conforme à la
    norme. Si vous souhaitez utiliser le protocole de basculement, assurez-vous que
    les deux pairs de basculement exécutent la même version du serveur DHCP ISC.


Le protocole de basculement permet à deux serveurs DHCP (et pas plus
    de deux) de partager un pool d'adresses commun. Chaque serveur aura environ la
    moitié des adresses IP disponibles dans le pool à tout moment pour
    l'allocation. Si un serveur tombe en panne, l'autre serveur continuera à
    renouveler les baux du pool et allouera de nouvelles adresses à partir de la
    moitié environ des adresses disponibles qu'il avait lorsque les
    communications avec l'autre serveur ont été perdues.


Il est possible, lors d'une panne prolongée, d'indiquer au serveur
    restant que l'autre serveur est en panne, auquel cas le serveur restant
    récupérera (au fil du temps) toutes les adresses que l'autre serveur avait
    disponibles pour l'allocation, et commencera à les réutiliser. C'est ce qu'on
    appelle mettre le serveur dans l'état PARTNER-DOWN.


Vous pouvez mettre le serveur dans l'état PARTNER-DOWN soit en
    utilisant la commande omshell (1), soit en arrêtant le serveur, en
    modifiant la dernière déclaration d'état de basculement dans le fichier de
    baux et en redémarrant le serveur. Si vous utilisez cette dernière méthode,
    modifiez la ligne "my state" comme suit :


failover peer nom state {
my state partner-down;.
peer state état at date;
}


Il suffit de modifier "my state" comme indiqué ci-dessus.


Lorsque l'autre serveur revient en ligne, il devrait automatiquement
    détecter qu'il était hors ligne et demander une mise à jour complète au serveur
    qui fonctionnait en état PARTNER-DOWN, puis les deux serveurs reprendront le
    traitement ensemble.


Il est possible de se retrouver dans une situation dangereuse : si vous
    mettez un serveur dans l'état PARTNER-DOWN, et que *ce* serveur tombe ensuite
    en panne, et que l'autre serveur redémarre, l'autre serveur ne saura pas que
    le premier serveur était dans l'état PARTNER-DOWN, et pourrait attribuer des
    adresses précédemment attribuées par l'autre serveur à différents clients,
    entraînant des conflits d'adresses IP. Avant de mettre un serveur dans l'état

El protocolo de conmutación por error define un rol de servidor principal y un rol de servidor secundario. Existen algunas diferencias en la forma en que actúan los primarios y los secundarios, pero la mayoría de las diferencias simplemente tienen que ver con proporcionar una forma para que cada par se comporte de manera opuesta al otro. Por lo tanto, un servidor debe configurarse como principal y el otro como secundario, y no importa demasiado cuál sea cuál.

INICIO DE CONMUTACIÓN POR ERROR

Cuando un servidor se inicia que no ha comunicado previamente con su par de conmutación por error, debe establecer comunicaciones con su par de conmutación por error y sincronizarse con él antes de poder atender a los clientes. Esto puede ocurrir porque acaba de configurar sus servidores DHCP para realizar la conmutación por error por primera vez, o porque uno de sus servidores de conmutación por error ha fallado catastróficamente y ha perdido su base de datos.

El proceso de recuperación inicial está diseñado para garantizar que cuando un par de conmutación por error pierde su base de datos y luego se resincroniza, se respetarán todas las concesiones que el servidor fallido otorgó antes de fallar. Cuando el servidor fallido se inicia, nota que no tiene estado de conmutación por error guardado e intenta contactar a su par.

Cuando ha establecido el contacto, solicita al par una copia completa de la base de datos de concesiones de su par. El par luego envía su base de datos completa y envía un mensaje indicando que ha terminado. El servidor fallido luego espera hasta que haya pasado MCLT y, una vez que haya pasado MCLT, ambos servidores realizan la transición de regreso a la operación normal. Este período de espera garantiza que cualquier concesión que el servidor fallido haya podido otorgar mientras estaba fuera de contacto con su socio habrá expirado.

Mientras el servidor fallido se está recuperando, su socio permanece en el estado de socio inactivo, lo que significa que está sirviendo a todos los clientes. El servidor fallido no proporciona ningún servicio a los clientes DHCP hasta que haya realizado la transición a la operación normal.

En el caso en que ambos servidores detecten que nunca antes se han comunicado con su socio, ambos entran en este estado de recuperación y siguen el procedimiento que acabamos de describir. En este caso, no se proporcionará ningún servicio a los clientes DHCP hasta que expire MCLT.

CONFIGURACIÓN DE LA CONMUTACIÓN POR ERROR

Para configurar la conmutación por error, debe escribir una declaración de par que configure el protocolo de conmutación por error y debe escribir referencias de par en cada declaración de grupo para la que desee realizar la conmutación por error. No tiene que realizar la conmutación por error para todos los grupos en un segmento de red determinado. No debe indicar a un servidor que está realizando la conmutación por error en una agrupación de direcciones particular y al otro que no lo está. No debe tener ninguna agrupación de direcciones común en la que no esté realizando la conmutación por error. Una declaración de grupo que utiliza la conmutación por error se vería así:

pool {
	failover peer "foo";
	parámetros específicos del grupo
};

El servidor actualmente realiza muy pocas verificaciones de cordura, por lo que si lo configura mal, simplemente fallará de manera extraña. Por lo tanto, le recomiendo que realice la conmutación por error o que no la realice, pero que no realice agrupaciones mixtas. Además, utilice el mismo archivo de configuración maestro para ambos servidores y tenga un archivo separado que contenga la declaración del par e incluya el archivo maestro. Esto le ayudará a evitar discrepancias de configuración. A medida que nuestra implementación evolucione, esto será menos problemático. Un archivo dhcpd.conf de ejemplo básico para un servidor principal podría ser así:

failover peer "foo" {
  primary;
  address anthrax.rc.example.com;
  port 519;
  peer address trantor.rc.example.com;
  peer port 520;
  max-response-delay 60;
  max-unacked-updates 10;
  mclt 3600;
  split 128;
  load balance max seconds 3;
}
include "/etc/dhcpd.master";

Las declaraciones en la declaración del par son las siguientes:

Las declaraciones primary y secondary

[ primary | secondary ];

Esto determina si el servidor es principal o secundario, como se describió anteriormente en DHCP FAILOVER.

La declaración address

address dirección;

La declaración address declara la dirección IP o el nombre DNS en el que el servidor debe escuchar las conexiones de su par de conmutación por error, y también el valor que se utilizará para el identificador del servidor del Protocolo de Conmutación por Error DHCP. Dado que este valor se utiliza como identificador, no se puede omitir.

La declaración peer address

peer address dirección;

La declaración peer address declara la dirección IP o el nombre DNS al que el servidor debe conectarse para alcanzar su par de conmutación por error para los mensajes de conmutación por error.

La declaración port

port número de puerto;

La declaración port declara el puerto TCP en el que el servidor debe escuchar las conexiones de su par de conmutación por error. Esta declaración se puede omitir, en cuyo caso se utilizará el número de puerto 647 asignado por IANA por defecto.

La declaración peer port

peer port número de puerto;

La declaración peer port declara el puerto TCP al que el servidor debe conectarse para alcanzar su par de conmutación por error para los mensajes de conmutación por error. Esta declaración se puede omitir, en cuyo caso se utilizará el número de puerto 647 asignado por IANA por defecto.

La declaración max-response-delay

max-response-delay segundos;

La declaración max-response-delay indica al servidor DHCP cuántos segundos pueden pasar sin recibir un mensaje de su par de conmutación por error antes de asumir que la conexión ha fallado. Este número debe ser lo suficientemente pequeño como para que una falla de red transitoria que rompa la conexión no resulte en que los servidores estén fuera de comunicación durante mucho tiempo, pero lo suficientemente grande como para que el servidor no establezca y rompa conexiones constantemente. Este parámetro debe especificarse.

La declaración max-unacked-updates

max-unacked-updates conteo;

La declaración max-unacked-updates indica al servidor DHCP remoto cuántos mensajes BNDUPD puede enviar antes de recibir un BNDACK del sistema local. No tenemos suficiente experiencia operativa para decir cuál es un buen valor para esto, pero 10 parece funcionar. Este parámetro debe especificarse.

La declaración mclt

mclt segundos;

La declaración mclt define el Tiempo Máximo de Plazo para Clientes (Maximum Client Lead Time). Debe especificarse en el principal y no puede especificarse en el secundario. Este es el período de tiempo durante el cual una concesión puede ser renovada por cualquier par de conmutación por error sin contactar al otro. Cuanto más tiempo lo configure, más tiempo tardará el servidor en funcionamiento en recuperar las direcciones IP después de pasar al estado PARTNER-DOWN. Cuanto más corto lo configure, más carga experimentarán sus servidores cuando no se estén comunicando. Un valor de algo como 3600 es probablemente razonable, pero nuevamente, tenga en cuenta que no tenemos experiencia operativa real con esto.

La declaración split

split bits;

La declaración de división especifica la división entre el principal y el secundario a efectos de equilibrio de carga. Cada vez que un cliente realiza una solicitud DHCP, el servidor DHCP ejecuta un hash sobre la identificación del cliente, lo que resulta en un valor de 0 a 255. Esto se utiliza como índice en un campo de 256 bits. Si el bit en ese índice está configurado, el principal es responsable. Si el bit en ese índice no está configurado, el secundario es responsable. El valor split determina cuántos de los bits iniciales están configurados en uno. Por lo tanto, en la práctica, valores de división más altos harán que el principal atienda a más clientes que el secundario. Valores de división más bajos, lo contrario. Los valores legales están entre 0 y 256 inclusive, de los cuales el más razonable es 128. Tenga en cuenta que un valor de 0 hace que el secundario sea responsable de todos los clientes y un valor de 256 hace que el principal sea responsable de todos los clientes.

La declaración hba

hba lista-hexadecimal-separada-por-dos-puntos;

La declaración hba especifica la división entre el principal y el secundario como un mapa de bits en lugar de un corte, lo que teóricamente permite un control más granular. En la práctica, probablemente no sea necesario un control tan granular. Un ejemplo de declaración hba:

  hba ff:ff:ff:ff:ff:ff:ff:ff:ff:ff:ff:ff:ff:ff:ff:ff:
      00:00:00:00:00:00:00:00:00:00:00:00:00:00:00:00;

Esto es equivalente a una declaración split 128; y idéntico. Los dos ejemplos siguientes también son equivalentes a una split de 128, pero no son idénticos:

  hba aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:
      aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa;
  hba 55:55:55:55:55:55:55:55:55:55:55:55:55:55:55:55:
      55:55:55:55:55:55:55:55:55:55:55:55:55:55:55:55;

Son equivalentes, porque la mitad de los bits están configurados en 0, la mitad están configurados en 1 (0xa y 0x5 son 1010 y 0101 binarios respectivamente) y, en consecuencia, esto dividiría aproximadamente a los clientes por igual entre los servidores. No son idénticos, porque los pares reales a los que esto equilibraría la carga para cada servidor son diferentes para cada ejemplo.

Solo debe tener definido split o hba, nunca ambos. Para la mayoría de los casos, el control granular que ofrece hba no es necesario y se debe utilizar split.

La declaración load balance max seconds

load balance max seconds segundos;

Esta declaración le permite configurar un punto de corte después del cual se desactiva el equilibrio de carga. El punto de corte se basa en el número de segundos transcurridos desde que el cliente envió su primer mensaje DHCPDISCOVER o DHCPREQUEST, y solo funciona con clientes que implementan correctamente el campo secs; afortunadamente, la mayoría de los clientes lo hacen. Recomendamos establecer esto en algo como 3 o 5. El efecto de esto es que si uno de los pares de conmutación por error entra en un estado en el que está respondiendo a mensajes de conmutación por error pero no a algunas solicitudes de cliente, el otro par de conmutación por error asumirá automáticamente la carga de su cliente a medida que los clientes reintenten.

Es posible desactivar el equilibrio de carga entre pares estableciendo este valor en 0 en ambos pares. Tenga en cuenta que esto significa que ambos pares responderán a todos los DHCPDISCOVER o DHCPREQUEST.

La declaración auto-partner-down

auto-partner-down segundos;

Esta declaración instruye al servidor a iniciar un retraso temporizado al entrar en la comunicación

nications-interrupted state (any situation of being out-of-contact with the remote failover peer). At the conclusion of the timer, the server will automatically enter the partner-down state. This permits the server to allocate leases from the partner's free lease pool after an STOS+MCLT timer expires, which can be dangerous if the partner is in fact operating at the time (the two servers will give conflicting bindings)

.

Think very carefully before enabling this feature. The partner-down and communications-interrupted states are intentionally segregated because there do exist situations where a failover server can fail to communicate with its peer, but still has the ability to receive and reply to requests from DHCP clients. In general, this feature should only be used in those deployments where the failover servers are directly connected to one another, such as by a dedicated hardwired link ("a heartbeat cable")

.

A zero value disables the auto-partner-down feature (also the

default), and any positive value indicates the time in se
conds to wait before automatically entering partner-down.

Cette version du serveur DHCP évalue l'équilibrage des pools selon un calendrier, plutôt que sur demande lors de l'allocation des baux. La seconde approche s'est avérée légèrement maladroite lorsque le déséquilibre du pool atteignait la saturation totale — lorsqu'un serveur n'avait plus de baux à attribuer, il perdait également sa capacité à remarquer qu'il était à

sec.

Afin de comprendre l'équilibrage des pools, certains éléments de son fonctionnement doivent d'abord être définis. Tout d'abord, il y a les baux « free » et « backup ». Les deux sont désignés comme des « baux en état libre ». « free » et « backup » sont « les états libres » aux fins du présent document. La différence est que seul le primaire peut allouer à partir des baux « free » sauf dans des circonstances spéciales, et seul le secondaire peut allouer les baux « backup »

.

Lors de l'équilibrage d'un pool, la seule attente plausible est de fournir une répartition 50/50 des baux en état libre entre les deux serveurs. C'est parce que personne ne peut prédire quel serveur échouera, quelle que soit la charge relative placée sur les deux serveurs ; donner à chaque serveur la moitié des baux donne à tous les deux la même quantité de « résistance à la panne ». Par conséquent, il n'existe aucun moyen de configurer un comportement différent, en dehors de quelques fenêtres très petites que nous décrirons

bientôt.

La première chose calculée lors de chaque exécution de l'équilibrage d'un pool est une valeur appelée « lts », ou "Leases To Send" (Baux à envoyer). C'est, simplement, la différence entre le nombre de baux libres et de baux de sauvegarde, divisée par deux. Pour le secondaire, c'est la différence entre les baux de sauvegarde et les baux libres, divisée par deux. La valeur résultante est signée : si elle est positive, le serveur local est censé distribuer des baux pour maintenir un équilibre 50/50. Si elle est négative, le serveur distant devrait envoyer des baux pour équilibrer le pool. Une fois que la valeur lts atteint zéro, le pool est parfaitement équilibré (plus ou moins un baux dans le cas d'un nombre impair total de baux en état libre)

.

L'approche actuelle est toujours en quelque sorte un hybride de l'ancienne approche, marquée par la présence de la déclaration max-lease-misbalance . Ce paramètre configure ce qui était une valeur fixe de 10 % dans les versions précédentes : si lts est inférieur à free+backup * max-lease-misbalance percent, alors le serveur sautera l'équilibrage d'un pool donné (il ne se donnera pas la peine de déplacer des baux, même si certains baux « devraient » être déplacés). La signification de cette valeur est également quelque peu surchargée, car elle gouverne également l'estimation du moment où tenter d'équilibrer le pool (qui peut ensuite également être ignoré). Les baux les plus anciens dans les états libres et de sauvegarde sont examinés. Le temps qu'ils ont passé dans leurs files respectives est utilisé comme estimation pour indiquer combien de temps il est probable qu'il faudrait avant que les baux en haut de la liste soient consommés (et donc, combien de temps il faudrait pour utiliser tous les baux dans cet état). Ce pourcentage est directement multiplié par ce temps, et ajusté au calendrier s'il se situe dans les valeurs configurées min-balance et max-balance. L'heure de vérification planifiée du pool n'est déplacée que vers le bas, elle n'est jamais augmentée. Enfin, si le lts est plus du double de ce nombre dans la direction négative, le serveur local va « paniquer » et transmettre un message POOLREQ du protocole Failover, dans l'espoir que le système distant sera réveillé pour

agir.

Une fois que la valeur lts dépasse le max-lease-misbalance pourcentage du nombre total de baux en état libre comme décrit ci-dessus, les baux sont déplacés vers le serveur distant. Cela se fait en deux

passes.

Dans la première passe, seuls les baux dont le client lié le plus récemment aurait été servi par le serveur distant — selon l'algorithme de répartition de charge (voir ci-dessus les déclarations de configuration split et hba) — sont donnés au pair. Cette première passe continuera volontiers à donner des baux, en décrémentant la valeur lts de un pour chacun, jusqu'à ce que la valeur lts ait atteint le négatif du nombre total de baux multiplié par le max-lease-ownership pourcentage. C'est donc par cette valeur que vous pouvez permettre un petit déséquilibre des pools de baux — dans le but de donner au pair plus d'une part de 50 % des baux dans l'espoir que leurs clients puissent un jour revenir et être alloués par le pair (fonctionnant normalement). Ce processus est appelé « Affinité d'adresse MAC », mais c'est quelque peu mal nommé : il s'applique également aux options d'identifiant de client DHCP. Notez également que l'affinité s'applique aux baux lorsqu'ils entrent dans l'état « free » à partir de « expired » ou « released ». Dans ce cas également, les baux ne seront pas déplacés de free vers backup si le secondaire a déjà plus que sa

part.

La deuxième passe n'est entreprise que si la première passe échoue à réduire le lts en dessous du nombre total de baux en état libre multiplié par le max-lease-ownership pourcentage. Dans cette passe, les baux les plus anciens sont donnés au pair sans se soucier de l'algorithme de répartition de charge, et cela continue jusqu'à ce que le lts tombe sous cette valeur. De cette façon, le serveur local gardera également volontiers un petit pourcentage des baux qui se répartiraient normalement sur

lui-même.

Ainsi, la valeur max-lease-misbalance agit comme un seuil de comportement. Des valeurs plus petites feront transiter plus de baux d'un état à l'autre pour équilibrer les pools au fil du temps, des valeurs plus élevées réduiront la quantité de changement (mais peuvent conduire à une pénurie de pool s'il y a une ruée sur les baux)

.

La valeur max-lease-ownership permet un léger biais (pourcentage) dans l'équilibre des baux d'un pourcentage du nombre total de baux en état

libre.

Enfin, min-balance et max-balance font en sorte qu'un événement de rééquilibrage planifié se produise dans un délai raisonnable (pour ne pas être perturbé par, par exemple, un baux libre de 7 ans)

.

Les valeurs plausibles pour les pourcentages se situent entre 0 et 100, inclus, mais les valeurs supérieures à 50 sont indiscernables les unes des autres (une fois que lts dépasse 50 % des baux en état libre, un serveur doit donc avoir 100 % des baux dans son état libre respectif). Il est recommandé de sélectionner une valeur max-lease-ownership inférieure à la valeur sélectionnée pour max-lease-misbalance. max-lease-ownership a une valeur par défaut de 10, et max-lease-misbalance a une valeur par défaut de

15.

Les valeurs plausibles pour les temps min-balance et max-balance vont également de 0 à (2^32)-1 (ou la limite de votre valeur time_t loc

ale), mais ont par défaut les valeurs 60 et 36
00 respectivement (pour placer les événem
ents d'équilibrage entre 1 minute et 1 heure).

CLASSIFICATION DES

CLIENTS

Les clients peuvent être séparés en classes, et traités différemment selon la classe à laquelle ils appartiennent. Cette séparation peut se faire soit avec une instruction conditionnelle, soit avec une instruction match dans la déclaration de classe. Il est possible de spécifier une limite sur le nombre total de clients dans une classe ou sous-classe particulière qui peuvent détenir des baux à un moment donné, et il est possible de spécifier une sous-classification automatique basée sur le contenu du paquet

client.

La prise en charge de la classification pour les clients DHCPv6 a été ajoutée en 4.3.0. Elle suit les mêmes règles que pour DHCPv4, sauf que la prise en charge des classes de facturation n'a pas encore été

ajoutée.

Pour ajouter des clients à des classes basées sur une évaluation conditionnelle, vous pouvez spécifier une expression de correspondance dans la déclaration de classe

: 
class "ras-clients" {
  match if substring (option dhcp-client-identifier, 1, 3) = "RAS";
}

Veuillez noter que les valeurs utilisées dans les expressions de correspondance ne peuvent provenir que de données ou d'options qui font partie du paquet client. Il n'est pas possible d'utiliser des valeurs construites à travers une ou plusieurs instructions exécutables. Cela découle du fait que la classification des clients se produit avant l'exécution de toute instruction. Tenter de le faire produira des résultats

indéterminés.

Notez que que vous utilisiez des expressions de correspondance ou des instructions add (ou les deux) pour classifier les clients, vous devez toujours écrire une déclaration de classe pour toute classe que vous utilisez. S'il n'y a pas d'instruction match et pas d'instructions dans la portée pour une classe, la déclaration devrait ressembler à ceci

: 
class "ras-clients"
{
}

SOUS-CLASSE

S

En plus des classes, il est possible de déclarer des sous-classes. Une sous-classe est une classe avec le même nom qu'une classe régulière, mais avec une expression de sous-correspondance spécifique qui est hachée pour une correspondance rapide. C'est essentiellement un hack de vitesse — la principale différence entre cinq classes avec des expressions de correspondance et une classe avec cinq sous-classes est qu'il sera plus rapide de trouver les sous-classes. Les sous-classes fonctionnent comme suit

: 
class "allocation-class-1" {
  match pick-first-value (option dhcp-client-identifier, hardware);
}
class "allocation-class-2" {
  match pick-first-value (option dhcp-client-identifier, hardware);
}
subclass "allocation-class-1" 1:8:0:2b:4c:39:ad;
subclass "allocation-class-2" 1:8:0:2b:a9:cc:e3;
subclass "allocation-class-1" 1:0:0:c4:aa:29:44;
subnet 10.0.0.0 netmask 255.255.255.0 {
  pool {
    allow members of "allocation-class-1";
    range 10.0.0.11 10.0.0.50;
  }
  pool {
    allow members of "allocation-class-2";
    range 10.0.0.51 10.0.0.100;
  }
}

Les données suivant le nom de la classe dans la déclaration de sous-classe sont une valeur constante à utiliser pour faire correspondre l'expression de correspondance de la classe. Lorsque la correspondance de classe est effectuée, le serveur évaluera l'expression de correspondance et recherchera ensuite le résultat dans la table de hachage. S'il trouve une correspondance, le client est considéré comme membre à la fois de la classe et de la

sous-classe.

Les sous-classes peuvent être déclarées avec ou sans portée. Dans l'exemple ci-dessus, le seul but de la sous-classe est de permettre à certains clients l'accès à un pool d'adresses, tandis que d'autres clients se voient accéder à l'autre pool ; ces sous-classes sont donc déclarées sans portée. Si une partie du but de la sous-classe était de définir des valeurs de paramètres différentes pour certains clients, vous pourriez vouloir déclarer certaines sous-classes avec des

portées.

Dans l'exemple ci-dessus, si vous aviez un client unique nécessitant certains paramètres de configuration, alors que la plupart n'en ont pas besoin, vous pourriez écrire la déclaration de sous-classe suivante pour ce client

: 
subclass "allocation-class-2" 1:08:00:2b:a1:11:31 {
  option root-path "samsara:/var/diskless/alphapc";
  filename "/tftpboot/netbsd.alphapc-diskless";
}

Dans cet exemple, nous avons utilisé la sous-classification comme moyen de contrôler l'allocation d'adresses par client. Cependant, il est également possible d'utiliser la sous-classification de manière non spécifique aux clients - par exemple, pour utiliser la valeur de l'option vendor-class-identifier afin de déterminer quelles valeurs envoyer dans l'option vendor-encapsulated-options. Un exemple de cela est présenté sous l'en-tête VENDOR ENCAPSULATED OPTIONS dans la page de manuel

dhcp-op
tions(5).

CLASSES DE GÉNÉRATION

(SPAWNING)

Il est possible de déclarer une classe de génération. Une classe de génération est une classe qui produit automatiquement des sous-classes en fonction de ce que le client envoie. La raison pour laquelle les classes de génération ont été créées était de rendre possible la création de classes à limites de baux à la volée. L'application envisagée est un environnement de modem câble où le FAI souhaite fournir aux clients d'un site particulier plus d'une adresse IP, mais ne souhaite pas fournir à ces clients leur propre sous-réseau, ni leur donner un nombre illimité d'adresses IP à partir du segment réseau auquel ils sont

connectés.

De nombreux systèmes de tête de réseau de modem câble peuvent être configurés pour ajouter une option Relay Agent Information aux paquets DHCP lors de leur relais vers le serveur DHCP. Ces systèmes ajoutent généralement une option circuit ID ou remote ID qui identifie de manière unique le site du client. Pour tirer parti de cela, vous pouvez écrire une déclaration de classe comme suit

: 
class "customer" {
  spawn with option agent.circuit-id;
  lease limit 4;
}

Désormais, chaque fois qu'une requête provient d'un site client, l'option circuit ID sera vérifiée par rapport à la table de hachage de la classe. Si une sous-classe correspondant au circuit ID est trouvée, le client sera classé dans cette sous-classe et traité en conséquence. Si aucune sous-classe correspondant au circuit ID n'est trouvée, une nouvelle sera créée et enregistrée dans le fichier dhcpd.leases, et le client sera classé dans cette nouvelle classe. Une fois que le client a été classé, il sera traité selon les règles de la classe, y compris, dans ce cas, être soumis à la limite de quatre baux par

site.

L'utilisation du mécanisme de génération de sous-classes n'

est pas restreinte aux options d'agent relais - cet exempl
e particulier n'est donné que parce qu'il est assez simple.

MISES À JOUR DYNAMIQUES DU

DNS

Le serveur DHCP a la capacité de mettre à jour dynamiquement le système de noms de domaine (Domain Name System). Dans les fichiers de configuration, vous pouvez définir la manière dont vous souhaitez que le système de noms de domaine soit mis à jour. Ces mises à jour sont conformes à la RFC 2136, de sorte que tout serveur DNS prenant en charge la RFC 2136 devrait pouvoir accepter les mises à jour du serveur

DHCP.

Deux schémas DNS sont implémentés. L'option interim est basée sur des révisions de projet des documents DDNS, tandis que l'option standard est basée sur les RFC concernant l'interaction DHCP-DNS et les DHCIDs. Une troisième option, ad-hoc, a été dépréciée et a maintenant été retirée de la base de code. Le cadre de base des deux schémas est similaire, la différence matérielle principale étant qu'un enregistrement DHCID RR est utilisé dans la version standard, tandis que la version interim utilise un enregistrement TXT RR. Dans ces deux schémas, le serveur DHCP ne met pas nécessairement toujours à jour à la fois les enregistrements A et PTR. L'option FQDN inclut un drapeau qui, lorsqu'il est envoyé par le client, indique que le client souhaite mettre à jour son propre enregistrement A. Dans ce cas, le serveur peut être configuré soit pour respecter les intentions du client, soit pour les ignorer. Cela se fait avec l'instruction allow client-updates; ou l'instruction ignore client-updates;. Par défaut, les mises à jour par le client sont

autorisées.

Si le serveur est configuré pour autoriser les mises à jour par le client, alors si le client envoie un nom de domaine entièrement qualifié dans l'option FQDN, le serveur utilisera ce nom envoyé par le client dans l'option FQDN pour mettre à jour l'enregistrement PTR. Par exemple, supposons que le client soit un visiteur du domaine "radish.org", dont le nom d'hôte est "jschmoe". Le serveur est pour le domaine "example.org". Le client DHCP indique dans l'option FQDN que son FQDN est "jschmoe.radish.org.". Il indique également qu'il souhaite mettre à jour son propre enregistrement A. Le serveur DHCP n'essaie donc pas de créer un enregistrement A pour le client, mais crée un enregistrement PTR pour l'adresse IP qu'il attribue au client, pointant vers jschmoe.radish.org. Une fois que le client DHCP a une adresse IP, il peut mettre à jour son propre enregistrement A, en supposant que le serveur DNS de "radish.org" l'autorisera à le

faire.

Si le serveur est configuré pour ne pas autoriser les mises à jour par le client, ou si le client ne souhaite pas effectuer sa propre mise à jour, le serveur choisira simplement un nom pour le client. Par défaut, le serveur choisira parmi les trois valeurs suivantes

Il utilisera son propre nom de domaine pour le client. Il mettra ensuite à jour à la fois les enregistrements A et PTR, en utilisant le nom qu'il a choisi pour le client. AUTORISER ET REFUSER DANS LES DÉCLARATIONS DE POOL

Les utilisations des mots-clés autoriser et refuser présentées dans la section précédente fonctionnent pratiquement de la même manière, que le client envoie un message DHCPDISCOVER ou DHCPREQUEST : une adresse sera allouée au client (soit l'ancienne adresse qu'il demande, soit une nouvelle adresse), puis cette adresse sera testée pour déterminer s'il est acceptable de la laisser au client. Si le client l'a demandée et que ce n'est pas acceptable, le serveur enverra un message DHCPNAK. Sinon, le serveur ne répondra tout simplement pas au client. S'il est acceptable de donner l'adresse au client, le serveur enverra un message DHCPACK.

La principale motivation derrière les déclarations de pool est d'avoir des pools d'allocation d'adresses dont les politiques d'allocation sont différentes. Un client peut se voir refuser l'accès à un pool, mais être autorisé à accéder à un autre pool sur le même segment réseau. Pour que cela fonctionne, le contrôle d'accès doit être effectué lors de l'allocation d'adresse, et non après.

Lorsqu'un message DHCPREQUEST est traité, l'allocation d'adresse consiste simplement à rechercher l'adresse demandée par le client et à vérifier si elle est toujours disponible pour le client. Si c'est le cas, le serveur DHCP vérifie à la fois les listes d'autorisation des pools d'adresses et les déclarations autoriser et refuser pertinentes dans la portée pour voir s'il est acceptable d'accorder le bail au client. Dans le cas d'un message DHCPDISCOVER, le processus d'allocation se fait comme décrit précédemment dans la section ALLOCATION D'ADRESSES.

Lors de la déclaration de listes d'autorisation pour les pools d'allocation d'adresses, les syntaxes suivantes sont reconnues après les mots-clés autoriser ou refuser :


clients-connus ;

Si spécifiée, cette déclaration autorise ou empêche l'allocation à partir de ce pool pour tout client ayant une déclaration d'hôte (c'est-à-dire qu'il est connu). Un client est connu s'il a une déclaration d'hôte dans n'importe quelle portée, pas seulement la portée actuelle.


clients-inconnus ;

Si spécifiée, cette déclaration autorise ou empêche l'allocation à partir de ce pool pour tout client n'ayant pas de déclaration d'hôte (c'est-à-dire qu'il n'est pas connu).


membres de « classe » ;

Si spécifiée, cette déclaration autorise ou empêche l'allocation à partir de ce pool pour tout client membre de la classe nommée.


clients bootp dynamiques ;

Si spécifiée, cette déclaration autorise ou empêche l'allocation à partir de ce pool pour tout client bootp.


clients authentifiés ;

Si spécifiée, cette déclaration autorise ou empêche l'allocation à partir de ce pool pour tout client authentifié à l'aide du protocole d'authentification DHCP. Ceci n'est pas encore pris en charge.


clients non authentifiés ;

Si spécifiée, cette déclaration autorise ou empêche l'allocation à partir de ce pool pour tout client non authentifié à l'aide du protocole d'authentification DHCP. Ceci n'est pas encore pris en charge.


tous les clients ;

Si spécifiée, cette déclaration autorise ou empêche l'allocation à partir de ce pool pour tous les clients. Cela peut être utilisé lorsque vous souhaitez écrire une déclaration de pool pour une raison quelconque, mais la garder en réserve, ou lorsque vous souhaitez renommer rapidement votre réseau, et ainsi forcer le serveur à faire en sorte que tous les clients qui se sont vu attribuer des adresses à partir de ce pool en obtiennent de nouvelles immédiatement lors de leur prochain renouvellement.


après temps ;

Si spécifiée, cette déclaration autorise ou empêche l'allocation à partir de ce pool après une date donnée. Cela peut être utilisé lorsque vous souhaitez déplacer des clients d'un pool à un autre. Le serveur ajuste la durée normale du bail de sorte que la dernière heure d'expiration soit à l'heure donnée + durée minimale du bail. Une durée minimale de bail courte impose un changement brutal, tandis qu'une durée minimale de bail plus longue permet un changement progressif. temps est soit en secondes depuis l'époque, soit une chaîne de temps UTC par exemple 4 2007/08/24 09:14:32, soit une chaîne avec un décalage horaire en secondes par exemple 4 2007/08/24 11:14:32 -7200

La déclaration durée-bail-abandonné

Lorsque le nombre de baux alloués au sein d'un pool dépasse le pourcentage indiqué dans cette déclaration, le serveur DHCP réduit la durée du bail pour les nouveaux clients de ce pool à durée-minimale-bail secondes. L'instruction dhcp-cache-threshold prend un paramètre entier avec des valeurs autorisées comprises entre 0 et 100. La valeur par défaut est 25 (25 % de la durée du bail). L'instruction do-forward-updates

do-forward-updates flag;

L'instruction do-forward-updates indique au serveur DHCP s'il doit tenter de mettre à jour l'enregistrement A d'un client DHCP lorsque le client acquiert ou renouvelle un bail. Cette instruction n'a aucun effet sauf si les mises à jour DNS sont activées. Les mises à jour directes sont activées par défaut. Si cette instruction est utilisée pour désactiver les mises à jour directes, le serveur DHCP ne tentera jamais de mettre à jour l'enregistrement A du client, et ne tentera de mettre à jour l'enregistrement PTR du client que si le client fournit un FQDN qui doit être placé dans l'enregistrement PTR à l'aide de l'option fqdn. Si les mises à jour directes sont activées, le serveur DHCP honorera toujours le paramètre de l'indicateur client-updates.

L'instruction dont-use-fsync

dont-use-fsync flag;

L'instruction dont-use-fsync indique au serveur DHCP s'il doit appeler fsync() lors de l'écriture des baux dans le fichier de baux. Par défaut et si l'indicateur est défini sur false, le serveur appellera fsync(). Supprimer l'appel à fsync() peut améliorer les performances du serveur, mais il existe également un risque qu'un bail ne soit pas correctement écrit sur le disque après avoir été émis à un client et avant que le serveur ne s'arrête. Cela peut entraîner l'émission de baux en double à différents clients. L'utilisation de cette option n'est pas recommandée.

L'instruction dynamic-bootp-lease-cutoff

dynamic-bootp-lease-cutoff date;

L'instruction dynamic-bootp-lease-cutoff définit la date de fin de tous les baux attribués dynamiquement aux clients BOOTP. Comme les clients BOOTP n'ont aucun moyen de renouveler leurs baux et ne savent pas que leurs baux pourraient expirer, par défaut, dhcpd attribue des baux infinis à tous les clients BOOTP. Cependant, il peut être judicieux dans certaines situations de définir une date limite pour tous les baux BOOTP - par exemple, la fin d'un semestre scolaire, ou l'heure la nuit où une installation est fermée et où toutes les machines doivent être éteintes.

Date doit être la date à laquelle tous les baux BOOTP attribués expireront. La date est spécifiée sous la forme :


J AAAA/MM/JJ HH:MM:SS

J est le jour de la semaine exprimé par un nombre de zéro (dimanche) à six (samedi). AAAA est l'année, y compris le siècle. MM est le mois exprimé par un nombre de 1 à 12. JJ est le jour du mois, en comptant à partir de 1. HH est l'heure, de zéro à 23. MM est la minute et SS est la seconde. L'heure est toujours en Temps Universel Coordonné (UTC), pas en heure locale.

L'instruction dynamic-bootp-lease-length

dynamic-bootp-lease-length longueur;

L'instruction dynamic-bootp-lease-length est utilisée pour définir la durée des baux attribués dynamiquement aux clients BOOTP. Dans certains sites, il peut être possible de supposer qu'un bail n'est plus utilisé si son détenteur n'a pas utilisé BOOTP ou DHCP pour obtenir son adresse dans un certain laps de temps. La période est spécifiée dans longueur comme un nombre de secondes. Si un client redémarre en utilisant BOOTP pendant la période de temporisation, la durée du bail est réinitialisée à longueur, de sorte qu'un client BOOTP qui démarre suffisamment fréquemment ne perdra jamais son bail. Il va sans dire que ce paramètre doit être ajusté avec une extrême prudence.

Les instructions host avec des clauses fixed-address existent dans une certaine mesure pour servir cet objectif, mais parce que les instructions host sont destinées à approximer la « configuration statique », elles souffrent du fait de ne pas être référencées dans une multitude d'autres services du serveur, tels que le DNS dynamique, le basculement, les « événements on » et ainsi de suite.

Si

un bail dynamique standard, comme celui de n'importe quelle instruction range, est marqué « réservé », alors le serveur n'allouera ce bail qu'au client identifié (que ce soit par l'identifiant du client ou l'adresse matérielle).

En

pratique, cela signifie que le bail suit le moteur d'états normal, entre dans l'état ACTIF lorsque le client y est lié, expire ou est libéré, et que tous les événements ou services qui seraient normalement fournis lors de ces événements sont traités normalement, comme pour tout autre bail dynamique. La seule différence est que les serveurs de basculement traitent les baux réservés comme spéciaux lorsqu'ils entrent dans les états LIBRE ou SAUVEGARDE - chaque serveur applique le bail dans l'état à partir duquel il peut allouer - et que les baux ne sont pas placés sur la file d'attente pour une allocation à d'autres clients. À la place, ils peuvent seulement être « trouvés » par l'identité du client. Le résultat est que le bail n'est

proposé

qu'au client de retour. Il convient probablement de veiller à ce que le client n'ait qu'un seul bail dans un sous-réseau donné

pour
