DESCRIPTIO

N

Le serveur DHCP du Internet Systems Consortium, dhcpd, implémente le protocole de configuration dynamique d'hôte (DHCP) et le protocole d'

amorçage Internet (BOOTP). DHCP permet aux hôtes d'un réseau TCP/IP de demander et d'obtenir des adresses IP, et également de découvri
r des informations sur le réseau auquel ils sont rattachés. BOOTP fournit des fonctionnalités similaires, avec certaines restrictions.

FONCTIONNEMEN

T

Le protocole DHCP permet à un hôte inconnu de l'administrateur réseau d'obtenir automatiquement une nouvelle adresse IP à partir d'un pool d'adresses IP pour son réseau. Pour que cela fonctionne, l'administrateur réseau alloue des pools d'adresses dans chaque sous-réseau et les saisit dans le fichier dhcpd.conf(5)

.

Il existe deux versions du protocole DHCP, DHCPv4 et DHCPv6. Au démarrage, le serveur peut être lancé pour l'une ou l'autre via les arguments -4

ou

-6. Au démarrage, dhcpd lit le fichier dhcpd.conf et stocke en mémoire une liste des adresses disponibles sur chaque sous-réseau. Lorsqu'un client demande une adresse à l'aide du protocole DHCP, dhcpd lui alloue une adresse. Chaque client se voit attribuer un bail, qui expire après une durée choisie par l'administrateur (par défaut, un jour). Avant l'expiration des baux, les clients auxquels des baux sont attribués doivent les renouveler afin de continuer à utiliser les adresses. Une fois qu'un bail a expiré, le client au quel ce bail a été attribué n'est plus autorisé à utiliser l'adresse IP

louée.

Afin de suivre les baux à travers les redémarrages du système et les redémarrages du serveur, dhcpd conserve une liste des baux qu'il a attribués dans le fichier dhcpd.leases(5). Avant que dhcpd n'accorde un bail à un hôte, il enregistre le bail dans ce fichier et s'assure que le contenu du fichier est écrit sur le disque. Cela garantit que même en cas de crash du système, dhcpd n'oubliera pas un bail qu'il a attribué. Au démarrage, après avoir lu le fichier dhcpd.conf, dhcpd lit le fichier dhcpd.leases pour rafraîchir sa mémoire sur les baux qui ont été

attribués.

Les nouveaux baux sont ajoutés à la fin du fichier dhcpd.leases. Afin d'empêcher le fichier de devenir arbitrairement volumineux, de temps à autre dhcpd crée un nouveau fichier dhcpd.leases à partir de sa base de données de baux en mémoire. Une fois que ce fichier a été écrit sur le disque, l'ancien fichier est renommé dhcpd.leases~ et le nouveau fichier est renommé dhcpd.leases. Si le système plante au milieu de ce processus, quel que soit le fichier dhcpd.leases restant, il contiendra toutes les informations de baux, il n'y a donc pas besoin de processus spécial de récupération après

crash.

Ce serveur fournit également la prise en charge de BOOTP. Contrairement à DHCP, le protocole BOOTP ne fournit pas de protocole pour récupérer les adresses attribuées dynamiquement une fois qu'elles ne sont plus nécessaires. Il est toujours possible d'attribuer dynamiquement des adresses aux clients BOOTP, mais un certain processus administratif pour récupérer les adresses est requis. Par défaut, les baux sont accordés aux clients BOOTP à perpétuité, bien que l'administrateur réseau puisse définir une date de coupure plus précoce ou une durée de bail plus courte pour les baux BOOTP si cela a du

sens.

Les clients BOOTP peuvent également être servis à l'ancienne façon standard, qui consiste simplement à fournir une déclaration dans le fichier dhcpd.conf pour chaque client BOOTP, attribuant définitivement une adresse à chaque

client.

Chaque fois que des modifications sont apportées au fichier dhcpd.conf, dhcpd doit être redémarré. Pour redémarrer dhcpd, envoyez un SIGTERM (signal 15) à l'identifiant de processus contenu dans RUNDIR/dhcpd.pid, puis réinvitez dhcpd. Parce que la base de données du serveur DHCP n'est pas aussi légère qu'une base de données BOOTP, dhcpd ne se redémarre pas automatiquement lorsqu'il détecte une modification du fichier dhcpd.

conf.

PORT

S

Lors de ses opérations, le serveur peut utiliser plusieurs ports UDP et TCP pour fournir différentes fonctions. Les ports qui sont ouverts dépendent à la fois de la façon dont vous avez compilé votre code et de la configuration que vous fournissez. Ce qui suit devrait vous donner une idée des ports qui peuvent être

utilisés.

Normalement, un serveur DHCPv4 ouvrira un socket UDP brut pour recevoir et envoyer la plupart des paquets DHCPv4. Il ouvre aussi un socket UDP de secours pour l'envoi de paquets unicast. Normalement, ces deux utiliseront le numéro de port bien connu pour

BOOTPS.

Pour chaque pair de basculement DHCPv4 que vous listez dans le fichier de configuration, il y aura un socket TCP écoutant pour les connexions sur les ports spécifiés dans le fichier de configuration. Lorsque le pair se connecte, il y aura un autre socket pour la connexion établie. Pour la connexion établie, le côté (primaire ou secondaire) qui ouvre la connexion utilisera un port

aléatoire.

Pour DHCPv6, le serveur ouvre un socket UDP sur le port bien connu

dhcpv6-server.

Le serveur ouvre un socket icmp pour effectuer des requêtes ping afin de vérifier si des adresses sont

utilisées.

Si vous avez inclus une instruction omapi-port dans votre fichier de configuration, le serveur ouvrira un socket TCP sur ce port pour écouter les connexions OMPAI. Lorsque quelque chose se connecte, un autre port sera utilisé pour la connexion

établie.

Lorsque DDNS est activé à la compilation (voir includes/site.h), le serveur ouvrira à la fois un

socket UDP v4 et un socket v6 sur des ports aléatoires, sauf si les mises à jour DDNS sont glo
balement désactivées en définissant ddns-update-style sur none dans le fichier de configuration.

Sous-résea

ux

dhcpd doit connaître les numéros de sous-réseau et les masques de sous-réseau de tous les sous-réseaux pour lesquels il fournira son service. De plus, afin d'allouer dynamiquement des adresses, il doit lui être assigné un ou plusieurs plages d'adresses sur chaque sous-réseau qu'il pourra à son tour assigner aux hôtes clients lorsqu'ils démarrent. Ainsi, une configuration très simple fournissant un support DHCP pourrait ressembler à ceci

: 
subnet 239.252.197.0 netmask 255.255.255.0 {
  range 239.252.197.10 239.252.197.250;
}

Plusieurs plages d'adresses peuvent être spécifiées comme ceci

: 
subnet 239.252.197.0 netmask 255.255.255.0 {
  range 239.252.197.10 239.252.197.107;
  range 239.252.197.113 239.252.197.250;
}

Si un sous-réseau ne recevra qu'un service BOOTP et aucune

attribution dynamique d'adresses, la clause range peut être omi
se complètement, mais l'instruction subnet doit apparaître.

Durées de

bail

Les bails DHCP peuvent être assignés pour presque n'importe quelle durée, de zéro seconde à l'infini. La durée de bail qui a du sens pour un sous-réseau donné, ou pour une installation donnée, variera en fonction des types d'hôtes qui sont

desservis.

Par exemple, dans un environnement de bureau où des systèmes sont ajoutés de temps en temps et retirés de temps en temps, mais bougent relativement peu fréquemment, il pourrait avoir du sens de permettre des durées de bail d'un mois ou plus. Dans un environnement de test final sur un plancher de fabrication, il pourrait être plus judicieux d'assigner une durée de bail maximale de 30 minutes - assez de temps pour passer à travers une procédure de test simple sur un appareil réseau avant de l'emballer pour la

livraison.

Il est possible de spécifier deux durées de bail : la durée par défaut qui sera assignée si un client ne demande aucune durée de bail particulière, et une durée de bail maximale. Celles-ci sont spécifiées comme clauses de la commande subnet

: 
subnet 239.252.197.0 netmask 255.255.255.0 {
  range 239.252.197.10 239.252.197.107;
  default-lease-time 600;
  max-lease-time 7200;
}

Cette déclaration de sous-réseau particulière spécifie une durée de bail par défaut de 600 secondes (dix minutes), et une durée de bail maximale de 7200 secondes (deux heures). D'autres valeurs courantes seraient 86400 (un jour), 604800 (une semaine) et 2592000 (30 jours)

.

Chaque sous-réseau n'a pas besoin d'avoir le même bail—dans le cas d'un environnement de bureau et d'

un environnement de fabrication desservis par le même serveur DHCP, il pourrait avoir du sens d'avoir
des valeurs très différentes pour les durées de bail par défaut et maximales sur chaque sous-réseau.

Support

BOOTP

Chaque client BOOTP doit être déclaré explicitement dans le fichier dhcpd.conf. Une déclaration de client très basique spécifiera l'adresse matérielle de l'interface réseau du client et l'adresse IP à assigner à ce client. Si le client doit être capable de charger un fichier d'amorçage depuis le serveur, le nom de ce fichier doit être spécifié. Une déclaration de client bootp simple pourrait ressembler à ceci

: 
host haagen {
  hardware ethernet 08:00:2b:4c:59:23;
  fixed-address 239.252.197.9;
  filename "/tftpboot/haagen.boot";
}

OMAP

I

Le serveur DHCP fournit la capacité de modifier certaines de ses configurations pendant qu'il s'exécute, sans l'arrêter, modifier ses fichiers de base de données, et le redémarrer. Cette capacité est actuellement fournie en utilisant OMAPI - une API pour manipuler des objets distants. Les clients OMAPI se connectent au serveur en utilisant TCP/IP, s'authentifient, et peuvent alors examiner l'état actuel du serveur et y apporter des

changements.

Plutôt que d'implémenter directement le protocole OMAPI sous-jacent, les programmes utilisateur devraient utiliser l'API dhcpctl ou OMAPI elle-même. Dhcpctl est un enveloppe (wrapper) qui gère certaines des tâches de ménage qu'OMAPI ne fait pas automatiquement. Dhcpctl et OMAPI sont documentés dans dhcpctl(3) et omapi(

3).

OMAPI exporte des objets, qui peuvent ensuite être examinés et modifiés. Le serveur DHCP exporte les objets suivants : lease, ho

st, failover-state et group. Chaque objet a un certain nombre de méthodes qui sont fournies : lookup, create, et destroy. De
plus, il est possible d'examiner des attributs qui sont stockés sur les objets, et dans certains cas de modifier ces attributs.

NAME

dhcpd - Internet Systems Consortium DHCP server

SYNOPSIS

dhcpd [-p port] [-f logfile] [-d] [-q] [-t] [-T] [-s {local|remote}] [-cf config-file] [-lf lease-file] [-pf pid-file] [-tf trap-file] [interface...]

DESCRIPTION

The Internet Systems Consortium DHCP server, dhcpd, is a server daemon that implements the Dynamic Host Configuration Protocol (DHCP) specified in RFC2131. It is designed to permit the dynamic allocation of IP addresses to hosts on a network.

It is also capable of supporting the BOOTP protocol, as specified in RFC951.

This server can be configured to support a large number of clients. It can also be configured to provide addresses for more than one network, and can be configured with static mappings for particular hosts.

OPERATION

The dhcpd server listens for DHCP and BOOTP protocol requests on one or more network interfaces. When a request is received, it consults its configuration file and lease database to determine how to respond. It can allocate IP addresses to clients, provide configuration parameters like default gateway, DNS servers, domain name, etc., and manage the lease times for allocated addresses.

The server uses a lease database file to keep track of which addresses have been leased to which clients, and when those leases expire. This file is typically located in /var/lib/dhcp/dhcpd.leases.

A pid file is created which contains the process ID of the running server. This file is typically located in /var/run/dhcpd.pid.

The server can be instructed to perform failover over a pair of connections between two servers.

COMMAND LINE

The dhcpd server can be started with a number of command-line options, which are described below. It is usually started at boot time by a system script.

COMMAND LINE OPTIONS

-p port
Listen on the specified UDP port instead of the default port 67.
-f logfile
Log to the specified file instead of the standard error output.
-d
Run in the foreground and log to standard error. This is useful for debugging.
-q
Do not dump the core file when the server crashes.
-t
Test the configuration file for syntax errors, but do not start the server.
-T
Test the configuration file for syntax errors and start the server in debugging mode (implies -d).
-s {local|remote}
If failover is configured, this option specifies whether this server is the primary (local) or secondary (remote) server.
-cf config-file
Use the specified configuration file instead of the default /etc/dhcpd.conf.
-lf lease-file
Use the specified lease database file instead of the default /var/lib/dhcp/dhcpd.leases.
-pf pid-file
Use the specified PID file instead of the default /var/run/dhcpd.pid.
-tf trap-file
Use the specified trap file instead of the default /var/lib/dhcp/dhcpd.leases~.
interface...
One or more network interfaces on which to listen for DHCP requests. If no interfaces are specified, the server will attempt to discover all network interfaces on the system.

PORTS

The DHCP server listens on UDP port 67. It sends replies to clients on UDP port 68.

CONFIGURATION

The behavior of the dhcpd server is controlled by the configuration file, which is typically named dhcpd.conf and is located in /etc/dhcpd.conf.

The configuration file consists of a series of declarations and statements. The configuration file can include other files using the include statement.

The following are the most common declarations:

subnet network-declaration { ... }

Defines a subnet for which the server will provide addresses.

host name { ... }

Defines a specific host with a static IP address and other parameters.

group { ... }

Defines a group of hosts that share common parameters.

shared-network name { ... }

Defines a shared network, which is a network that is served by more than one subnet.

failover peer-name { ... }

Defines a failover peer relationship with another DHCP server.

server-identifier address;

Specifies the IP address of the server.

ddns-update-style style;

Specifies the style of DDNS updates to be performed. Valid styles are none, ad-hoc, and internal.

default-lease-time time;

Specifies the default lease time in seconds.

max-lease-time time;

Specifies the maximum lease time in seconds.

authoritative;

Declares the server to be authoritative for the network.

use-host-decl-names boolean;

If true, host declarations will be used to determine the DNS name of the host.

log-facility facility;

Specifies the facility to use for logging.

lease lease-file;

Specifies the lease database file.

pid-file pid-file;

Specifies the PID file.

trap-file trap-file;

Specifies the trap file.

Subnets

A subnet declaration specifies the network address and netmask for a subnet, and can also specify the range of addresses to be leased out to clients, default lease times, and other parameters.

Example:

subnet 192.168.1.0 netmask 255.255.255.0 {
  range 192.168.1.10 192.168.1.200;
  option routers 192.168.1.1;
  option domain-name-servers 192.168.1.5;
  default-lease-time 600;
  max-lease-time 7200;
}

Lease Lengths

The default-lease-time and max-lease-time statements specify the default and maximum lease times in seconds.

BOOTP Support

The dhcpd server can also provide BOOTP services. For BOOTP clients, the server must be configured with static mappings for each client. This is done using the host declaration.

Example:

host client0 {
  hardware ethernet 00:c0:4f:4b:4c:4d;
  fixed-address 192.168.1.100;
}

Options

The dhcpd server can provide a wide variety of DHCP options to clients. The most common options are:

routers

The default gateway for the client.

domain-name-servers

The IP addresses of the DNS servers.

domain-name

The domain name for the client.

subnet-mask

The subnet mask for the client.

time-offset

The time offset from UTC in seconds.

ntp-servers

The IP addresses of the NTP servers.

OMAPI

The dhcpd server supports the OMAPI (On-line Management Interface Protocol) which allows remote administration of the DHCP server. This is typically used by tools like omshell(1m).

To enable OMAPI, you need to add an omapi-port statement to the configuration file, and possibly an omapi-key statement.

Example:

omapi-port 7000;
omapi-key hostname identity key \"my-secret-key\";
