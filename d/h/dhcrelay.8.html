DESCRIPTIO

N

L'agent relais DHCP de l'Internet Systems Consortium, dhcrelay, fournit un moyen de relayer les requêtes D

HCP et BOOTP depuis un sous-réseau auquel aucun serveur DHCP n'est directement connecté vers un ou plusie
urs serveurs DHCP sur d'autres sous-réseaux. Il prend en charge les protocoles DHCPv4/BOOTP et DHCPv6.

FONCTIONNEMEN

T

L'agent relais DHCP écoute les requêtes DHCPv4 ou DHCPv6 provenant de clients ou d'autres agents relais sur une ou plusieur

s interfaces, et les transmet aux serveurs ou agents relais « amont » tels que spécifiés en ligne de commande. Lorsqu'u
ne réponse est reçue de l'amont, elle est diffusée en multicast ou unicast en aval, vers la source de la requête originale.

6

4
Exécute dhcrelay en tant qu'agent relais DHCPv4/BOOTP. C'est le mode de fonctionnement par défaut, l'argument n'est donc pas nécessaire, mais il peut être spécifié pour plus de clarté. Incompatible avec -6

Spécification des serveurs

DHCPv4/BOOTP

En mode DHCPv4, une liste d'une ou plusieurs adresses de serveurs doit être spécifiée en ligne de commande, vers lesquelles les requêtes DHCP/BOOTP doivent être

relayées.

Options disponibles uniquement en mode DHCPv4

:
-
a
Ajoute un champ d'option d'agent à chaque requête avant de la transmettre au serveur. Les champs d'option d'agent dans les réponses envoyées par les serveurs aux clients seront supprimés avant de transmettre ces réponses au client. Le champ d'option d'agent contiendra deux options d'agent : la sous-option Circuit ID et la sous-option Remote ID. Actuellement, le Circuit ID sera le nom imprimable de l'interface sur laquelle la requête du client a été reçue. Le client prend également en charge l'inclusion d'une sous-option Remote ID, mais celle-ci n'est pas utilisée par
défaut.
-A leng
th
Spécifie la taille maximale du paquet à envoyer à un serveur DHCPv4/BOOTP. Cela peut être fait pour permettre un espace suffisant pour l'ajout d'options d'agent relais tout en restant dans la taille MTU
Ethernet.
-
D
Rejette les paquets provenant des serveurs amont s'ils contiennent des options d'information de l'agent relais indiquant qu'ils ont été générés en réponse à une requête arrivée via un autre agent relais. Si cette option n'est pas spécifiée, de tels paquets seront relayés quand
même.
-g ipad
dr
Lorsqu'un paquet est renvoyé au client, remplace l'adresse IP de la passerelle (giaddr) par l' ipaddr donnée. Cela peut être utilisé comme solution de contournement pour des clients défectueux comme Solaris 11 grub, qui utilisent la giaddr au lieu du routeur annoncé (3) pour configurer sa route par
défaut.
-i ifna
me
Écoute le trafic DHCPv4/BOOTP sur l'interface ifname. Plusieurs interfaces peuvent être spécifiées en utilisant plus d'une option -i. Si aucune interface n'est spécifiée en ligne de commande, dhcrelay identifiera toutes les interfaces réseau, en éliminant les interfaces non broadcast si possible, et essaiera d'écouter sur
toutes.
-iu ifna
me
Spécifie une interface réseau amont : une interface à partir de laquelle les réponses des serveurs et des autres agents relais seront acceptées. Plusieurs interfaces peuvent être spécifiées en utilisant plus d'une option -iu. Cet argument est
destiné à être utilisé en conjonction avec un ou plusieurs arguments -i ou
-id.
-id ifna
me
Spécifie une interface réseau aval : une interface à partir de laquelle les requêtes des clients et des autres agents relais seront acceptées. Plusieurs interfaces peuvent être spécifiées en utilisant plus d'une option -id. Cet argument est destiné à être utilisé en conjonction avec un ou plusieurs arguments -i ou
-iu.
-m append|replace|forward|disca
rd
Contrôle le traitement des paquets DHCPv4 entrants qui contiennent déjà des options d'agent relais. Si un tel paquet n'a pas giaddr défini dans son en-tête, la norme DHCP exige que le paquet soit rejeté. Cependant, si giaddr est défini, l'agent relais peut gérer la situation de quatre manières : il peut ajouter son propre ensemble d'options de relais au paquet, en laissant le champ d'option fourni intact ; il peut remplacer le champ d'option d'agent existant ; il peut transmettre le paquet inchangé ; ou, il peut le reje
ter.
-U ifna
me
Permet l'ajout d'une sous-option de sélection de lien conforme à la RFC 3527 pour les clients directement connectés au relais. Cette RFC permet à un relais de spécifier deux adresses IP différentes : l'une pour que le serveur l'utilise lors de la communication avec le relais (giaddr), l'autre pour choisir le sous-réseau du client (la sous-option). Cela peut être utile si le serveur est incapable d'envoyer des paquets au relais via l'adresse utilisée pour le sous-réseau.

Lorsqu'elle est activée, dhcrelay ajoutera une option d'agent (comme pour -a ci-dessus) incluant la sous-option de sélection de lien au paquet transmis. Cela ne sera fait que pour les paquets reçus de clients directement connectés au relais (c'est-à-dire que giaddr est à zéro). L'adresse utilisée dans la sous-option sera celle du lien sur lequel le paquet entrant a été reçu (qui serait autrement utilisé pour giaddr). La valeur de giaddr sera définie sur celle de l'interface ifnam

e.

Une seule interface devrait être marquée de cette manière. Actuellement, l'activation de cette option sur une interface fait que le relais traite tout le trafic DHCP de manière similaire à l' option -i ; à l'avenir, nous pourrions séparer les deux plus

complètement.

Cette option est désactivée par défaut. Notez que l'activation de cette option active automatiquement l' option

-a.

Gardez à l'esprit que l'utilisation d'options telles que -m replace ou -m discardb> sur les relais en amont à partir d'un -U peut poser des problèmes. Le relais en amont effacera l'option agent initiale

contenant la sélection de lien tout en la
issant la valeur giaddr réutilisée en
place, ce qui fait que les paquets se perdent.

Options disponibles uniquement en mode DHCPv6

:
-
I
Force l'utilisation de l'option Interface-ID de DHCPv6. Cette option est automatiquement envoyée lorsqu'il y a deux interfaces aval ou plus en usage, pour les distinguer entre elles. L' -I option fait envoyer à dhcrelay l'option même s'il n'y a qu'une seule interface
aval.
-s
subscriber-id
Ajoute une option avec l'identifiant subscriber-id spécifié dans le paquet. Cette fonctionnalité est destinée aux tests plutôt qu'à la production car elle placera le même subscriber-id dans le paquet pour tous les
clients.
-l [address%]ifname[#inde
x]
Spécifie l'interface réseau « inférieure » (lower) pour le mode relais DHCPv6 : l' interface sur laquelle les requêtes seront reçues des clients ou d'autres agents relais. Au moins une -l option doit être incluse dans la ligne de commande lors de l'exécution en mode DHCPv6. Le nom d'interface ifname est un paramètre obligatoire. L'adresse de lien peut être spécifiée par address% ; si ce n'est pas le cas, dhcrelay utilisera la première adresse non link-local configurée sur l'interface. Le paramètre optionnel #index spécifie l'index de
l'interface.
-u [address%]ifna
me
Spécifie l'interface réseau « supérieure » (upper) pour le mode relais DHCPv6 : l' interface vers laquelle les requêtes des clients et des autres agents relais doivent être transférées. Au moins une -u option doit être incluse dans la ligne de commande lors de l'exécution en mode DHCPv6. Le nom d'interface ifname est un paramètre obligatoire. L'adresse de destination unicast ou multicast peut être spécifiée par address% ; si elle n'est pas spécifiée, l'agent relais transférera vers l'adresse multicast DHCPv6 All_DHCP_Relay_Ag
ents_and_
Servers.

Il est possible de spécifier la même interface avec différentes adresse

s plus d'une fois, et même, lorsque le système le prend en charge, d'utilise
r la même interface à la fois comme interface supérieure et inférieure.
