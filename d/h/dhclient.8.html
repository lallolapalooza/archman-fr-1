Le protocole DHCP fournit également un mécanisme par lequel un client peut apprendre des détails importants sur le réseau auquel il est connecté, comme l'emplacement d'un routeur par défaut, l'emplacement d'un serveur de noms, etc. Il existe deux versions du protocole DHCP : DHCPv4 et DHCPv6. Au démarrage, le client peut être démarré pour

ou l'autre via les -4 ou -6 options. Au démarrage, dhclient lit le fichier dhclient.conf pour les instructions de configuration. Il obtient ensuite une liste de

toutes

les interfaces réseau qui sont configurées sur le système actuel. Pour chaque interface, il tente de configurer l'interface à l'aide du protocole DHCP. Afin de suivre les baux à travers les redémarrages du système et les redémarrages du serveur, dhclient conserve une liste des

baux

qui lui ont été attribués dans le fichier dhclient.leases. Au démarrage, après avoir lu le fichier dhclient.conf, dhclient lit le fichier dhclient.leases pour rafraîchir sa mémoire sur les baux qui lui ont été attribués. Lorsqu'un nouveau bail est acquis, il est ajouté à la fin du fichier dhclient.leases. Afin d'empêcher le fichier de

devenir

arbitrairement volumineux, de temps en temps dhclient crée un nouveau fichier dhclient.leases à partir de sa base de données de baux en mémoire. L'ancienne version du fichier dhclient. leases est conservée sous le nom dhclient.leases~ jusqu'à la prochaine fois que dhclient réécrit la base de données. Les anciens baux sont conservés au cas où le serveur DHCP serait indisponible lorsque dhclient est invoqué pour la

première

fois (généralement lors du processus de démarrage initial du système). Dans ce cas, les anciens baux du fichier dhclient.leases qui ne sont pas encore expirés sont testés, et s'ils sont déterminés comme valides, ils sont utilisés jusqu'à ce qu'ils expirent ou que le serveur DHCP devienne disponible. Un hôte mobile qui peut parfois avoir besoin d'accéder à un réseau sur lequel aucun serveur

DHCP

n'existe peut être préchargé avec un bail pour une adresse fixe sur ce réseau. Lorsque toutes les tentatives de contacter un serveur DHCP ont échoué, dhclient essaiera de valider le bail statique, et s'il réussit, utilisera ce bail jusqu'à ce qu'il soit redémarré. Un hôte mobile peut également se rendre sur des réseaux sur lesquels DHCP n'est pas

disponible

mais où BOOTP l'est. Dans ce cas, il peut être avantageux de s'arranger avec l'administrateur réseau pour une entr

la liste des anciens baux. LIGNE DE COMMANDE Les noms des interfaces réseau que dhclient devrait tenter de

-p numéro-de-port
Le numéro de port UDP sur lequel le client DHCP doit écouter et transmettre. S'il n'est pas spécifié, dhclient utilise le port par défaut 68. Ceci est principalement utile à des fins de débogage. Si un port différent est spécifié sur lequel le client doit écouter et transmettre, le client utilisera également un port de destination différent - un de moins que le port spécifié.
-s adresse-serveur
Spécifie l'adresse IP du serveur ou le nom de domaine complet à utiliser comme destination pour les messages du protocole DHCP avant que dhclient n'ait acquis une adresse IP. Normalement, dhclient transmet ces messages à 255.255.255.255 (l'adresse de diffusion limitée IP). Le remplacement de ceci est principalement utile à des fins de débogage. Cette fonctionnalité n'est pas supportée en mode DHCPv6 (-6).
-g relais
Définit le champ giaddr de tous les paquets à l'adresse IP de relais, simulant un agent relais. Ceci est uniquement à des fins de test et ne doit pas être considéré comme fonctionnel de manière cohérente ou utile.
-i
Utilise un DUID avec les clients DHCPv4. Si aucun DUID n'est disponible dans le fichier de bail, un sera construit et sauvegardé. Le DUID sera utilisé pour construire un identifiant client de style RFC4361 qui sera inclus dans les messages du client. Cet identifiant client peut être remplacé en définissant un identifiant client dans le fichier de configuration. Le remplacement de l'identifiant client de cette manière est déconseillé.
-I
Utilise le schéma DDNS standard des RFC 4701 et 4702.
--decline-wait-time secondes
Spécifie le temps (en secondes) que le client IPv4 doit attendre après avoir décliné une adresse avant d'émettre une découverte. La valeur par défaut est 10 secondes, comme recommandé par la RFC 2131, section 3.1.5. Une valeur de zéro équivaut à aucune attente.

--version Affiche le numéro de version et quitte.

Options disponibles pour le mode DHCPv6 :

-S
Utilise une requête d'information pour obtenir uniquement des paramètres de configuration sans état (c'est-à-dire sans adresse). Ceci implique -6. Cela ne réécrit pas non plus la base de données des baux.
-T
Demande des adresses temporaires IPv6, un ensemble par drapeau -T. Ceci implique -6 et désactive également la requête d'adresse normale. Voir -N pour la restaurer.
-P
Active la délégation de préfixe IPv6. Ceci implique -6 et désactive également la requête d'adresse normale. Voir -N pour la restaurer. Plusieurs préfixes peuvent être demandés avec plusieurs drapeaux -P. Notez qu'une seule interface demandée est autorisée.
-R
Exige que les réponses incluent tous les éléments demandés par les options -N, -T ou -P. Normalement, même si la ligne de commande inclut un certain nombre de ces options, le client acceptera le meilleur bail qu'il peut obtenir, même si le bail n'inclut pas tous les éléments demandés. Cette option fait en sorte que le client n'accepte que les baux qui incluent tous les éléments demandés.

Attention : l'activation de ceci peut empêcher le client d'utiliser les baux qu'il reçoit si les serveurs ne sont pas configurés pour fournir tous les éléments.

-D LL ou LLT
Remplace la valeur par défaut lors de la sélection du type de DUID à utiliser. Par défaut, dhclient DHCPv6 crée un identifiant basé sur l'adresse de la couche de liaison (DUID-LL) s'il s'exécute en mode sans état (avec -S, ne demandant pas d'adresse), ou il crée un identifiant basé sur l'adresse de la couche de liaison plus un horodatage (DUID-LLT) s'il s'exécute en mode avec état (sans -S, demandant une adresse). Lorsque DHCPv4 est configuré pour utiliser un DUID via l'option -i, la valeur par défaut est d'utiliser un DUID-LLT. -D remplace ces valeurs par défaut, avec une valeur de LL ou LLT.
-N
Restaure la requête d'adresse normale pour IPv6. Ceci implique -6. Il est utilisé pour restaurer le fonctionnement normal après avoir utilisé -T ou -P. Plusieurs adresses peuvent être demandées avec plusieurs drapeaux -N.
--address-prefix-len longueur
Spécifie la longueur du préfixe pour les adresses IPv6. Cette valeur est transmise par dhclient au script client via la variable d'environnement, ip6_prefixlen, lors de la liaison des adresses IPv6. La valeur par défaut est 128. Alternativement, vous pouvez modifier la valeur par défaut lors de la compilation en définissant DHCLIENT_DEFAULT_PREFIX_LEN dans includes/site.h.
--dad-wait-time secondes
Spécifie le temps maximum (en secondes) que le client doit attendre la fin de la détection d'adresse en double (DAD) sur une interface. Cette valeur est propagée au script dhclient dans une variable d'environnement dad_wait_time. Si l'une des adresses IPv6 sur l'interface est temporaire (DAD est en cours), le script attendra le nombre de secondes spécifié pour que le DAD se termine. Si le script ignore cette variable, le paramètre n'a aucun effet.
--prefix-len-hint longueur
Lorsqu'il est utilisé conjointement avec -P, il indique au client d'utiliser la longueur donnée pour un indice de préfixe de "::/longueur", lors de la demande de nouveaux préfixes.

Modification des emplacements de fichiers par défaut : Les options suivantes peuvent être utilisées pour modifier les emplacements que le client utilise pour ses fichiers. Elles peuvent être particulièrement utiles si, par exemple, DBDIR ou RUNDIR n'ont pas été montés au démarrage du client DHCP.

-cf fichier-de-configuration
Chemin d'accès au fichier de configuration du client. S'il n'est pas spécifié, le fichier par défaut ETCDIR/dhclient.conf est utilisé. Voir dhclient.conf(5) pour une description de ce fichier.
-df fichier-de-bail-duid
Chemin d'accès à un fichier de bail secondaire. Si le fichier de bail principal ne contient pas de DUID, ce fichier sera recherché. Le DUID lu à partir du fichier secondaire sera écrit dans le fichier principal. Cette option peut être utilisée pour permettre à une instance IPv4 du client de partager un DUID avec une instance IPv6. Après avoir démarré l'une des instances, la seconde peut être démarrée avec cette option pointant vers le fichier de bail de la première instance. Il n'y a pas de valeur par défaut. Si aucun fichier n'est spécifié, aucune recherche de DUID ne sera effectuée s'il n'est pas trouvé dans le fichier de bail principal.
-lf fichier-de-bail
Chemin d'accès au fichier de base de données des baux. S'il n'est pas spécifié, le fichier par défaut DBDIR/dhclient.leases est utilisé. Voir dhclient.leases(5) pour une description de ce fichier.
-pf fichier-pid
Chemin d'accès au fichier de l'ID du processus. S'il n'est pas spécifié, le fichier par défaut RUNDIR/dhclient.pid est utilisé.
--no-pid
Option pour désactiver l'écriture des fichiers pid. Par défaut, le programme écrira un fichier pid. Si le programme est invoqué avec cette option, il n'essaiera pas de tuer les processus clients existants, même s'il est invoqué avec -r ou -x.
-sf fichier-script
Chemin d'accès au script de configuration réseau appelé par dhclient lorsqu'il obtient un bail. S'il n'est pas spécifié, le fichier par défaut CLIENTBINDIR/dhclient-script est utilisé. Voir dhclient-script(8) pour une description de ce fichier.

PORTS

Pendant les opérations, le client peut utiliser plusieurs ports UDP pour fournir différentes fonctions. Les ports qui sont ouverts dépendent à la fois de la manière dont vous avez compilé votre code et de la configuration que vous fournissez. Ce qui suit devrait vous donner une idée des ports qui peuvent être en cours d'utilisation.

Normalement, un client DHCPv4 ouvrira une socket UDP brute pour recevoir et envoyer la plupart des paquets DHCPv4. Il ouvrira également une socket UDP de secours pour l'envoi de paquets unicast. Normalement, les deux utiliseront le numéro de port bien connu pour BOOTPC.

Pour DHCPv6, le client ouvre une socket UDP sur le port client bien connu et une socket UDP de secours sur un port aléatoire pour l'envoi de messages unicast. Contrairement à DHCPv4, la socket bien connue n'a pas besoin d'être ouverte en mode brut.

Si vous avez inclus une instruction de port omapi dans votre fichier de configuration, le client ouvrira une socket TCP sur ce port pour écouter les connexions OMAPI. Lorsqu'une connexion s'établit, un autre port sera utilisé pour la connexion établie.

Lorsque DDNS est activé au moment de la compilation (voir includes/site.h), le client ouvrira une socket UDP v4 et une socket UDP v6 sur des ports aléatoires. Ces ports ne seront pas ouverts avant que le client ne tente d'effectuer une mise à jour. Si le client n'est pas configuré pour effectuer des mises à jour, les ports ne seront jamais ouverts.

CONFIGURATION

La syntaxe du fichier dhclient.conf(5) est discutée séparément.

OMAPI

Le client DHCP offre une certaine capacité à le contrôler pendant qu'il est en cours d'exécution, sans l'arrêter. Cette capacité est fournie à l'aide d'OMAPI, une API pour manipuler des objets distants. Les clients OMAPI se connectent au client via TCP/IP, s'authentifient, et peuvent ensuite examiner l'état actuel du client et y apporter des modifications.

Plutôt que d'implémenter directement le protocole OMAPI sous-jacent, les programmes utilisateur doivent utiliser l'API dhcpctl ou OMAPI elle-même. Dhcpctl est un wrapper qui gère certaines des tâches de maintenance qu'OMAPI ne fait pas automatiquement. Dhcpctl et OMAPI sont documentés dans dhcpctl(3) et omapi(3). La plupart des choses que vous voudriez faire avec le client peuvent être faites directement en utilisant la commande omshell(1), plutôt que d'avoir à écrire un programme spécial.

L'OBJET DE CONTRÔLE

L'OBJET DE CONTRÔLE

L'objet de contrôle vous permet d'arrêter le client, en libérant tous les baux qu'il détient et en supprimant tout enregistrement DNS qu'il aurait pu ajouter. Il vous permet également de mettre le client en pause - cela désconfigure toutes les interfaces que le client utilise. Vous pouvez ensuite le redémarrer, ce qui le fait reconfigurer ces interfaces. Vous mettriez normalement le client en pause avant d'entrer en hibernation ou en veille sur un ordinateur portable. Vous le reprendriez ensuite une fois l'alimentation rétablie. Cela permet de mettre les cartes PC en veille pendant que l'ordinateur est en hibernation ou en veille, puis de les réinitialiser à leur état précédent une fois que l'ordinateur sort de l'hibernation ou de la

veille.

L'objet de contrôle a un seul attribut - l'attribut d'état. Pour arrêter le client, définissez

son attribut d'état à 2. Il effectuera automatiquement un DHCPRELEASE. Pour le mettre en pause,
définissez son attribut d'état à 3. Pour le reprendre, définissez son attribut d'état à 4.

La version actuelle doit beaucoup aux améliorations Linux d'Elliot, mais a été substantiellement réorganisée et partiellement réécrite par Ted Lemon afin d'utiliser le
