DESCRIPTIO

N

dlopen(

)

La fonction dlopen() charge le fichier objet partagé dynamique (bibliothèque partagée) nommé par la chaîne terminée par un caractère nul chemin et retourne un « handle » opaque pour l'objet chargé. Ce handle est utilisé avec d'autres fonctions de l'API dlopen, telles que dlsym(3), dladdr(3), dlinfo(3), et dlclose

().

Si chemin est NULL, alors le handle retourné correspond au programme principal. Si chemin contient une barre oblique ("/"), alors il est interprété comme un chemin de fichier (relatif ou absinut). Sinon, l'éditeur de liens dynamique recherche l'objet comme suit (voir ld.so(8) pour plus de détails)

:
•
(ELF uniquement) Si l'objet appelant (c'est-à-dire la bibliothèque partagée ou l'exécutable à partir duquel dlopen() est appelé) contient une balise DT_RPATH, et ne contient pas de balise DT_RUNPATH, alors les répertoires listés dans la balise DT_RPATH sont
recherchés.
•
Si, au moment où le programme a été démarré, la variable d'environnement LD_LIBRARY_PATH était définie pour contenir une liste de répertoires séparés par des deux-points, alors ceux-ci sont recherchés. (En guise de mesure de sécurité, cette variable est ignorée pour les programmes set-user-ID et set-group-ID.
)
•
(ELF uniquement) Si l'objet appelant contient une balise DT_RUNPATH, alors les répertoires listés dans cette balise sont
recherchés.
•
Le fichier cache /etc/ld.so.cache (maintenu par ldconfig(8)) est vérifié pour voir s'il contient une entrée pour chemi
n.
•
Les répertoires /lib et /usr/lib sont recherchés
(dans cet
ordre).

Si l'objet spécifié par chemin a des dépendances sur d'autres objets partagés, alors ceux-ci sont également chargés automatiquement par l'éditeur de liens dynamique en utilisant les mêmes règles. (Ce processus peut se produire de manière récursive, si ces objets ont à leur tour des dépendances, et ainsi de suite.

)

L'une des deux valeurs suivantes doit être incluse dans drapeau

x :

ZY

(La liaison paresseuse n'est effectuée que pour les références de fonctions ; les références aux variables sont toujours liées immédiatement lorsque l'objet partagé est chargé.) Depuis glibc 2.1.1, ce drapeau est remplacé par l'effet de la variable d'environnement
LD_BIND_NOW.

Ne pas charger l'objet partagé. Cela peut être utilisé pour tester si l'objet est déjà résident (dlopen() retourne NULL s'il ne l'est pas, ou le handle de l'objet s'il est résident). Ce drapeau peut également être utilisé pour promouvoir les drapeaux sur un objet partagé qui est déjà chargé. Par exemple, un objet partagé qui a été chargé précédemment avec RTLD_LOCAL peut être rouvert avec RTLD_NOLOAD | RTL

symboles globaux portant le même nom contenus dans des objets qui ont déjà été chargés.

Si chemin est NULL, alors le handle retourné correspond au programme principal. Lorsqu'il est donné à dlsym(3), ce handle provoque la recherche d'un symbole dans le programme principal, puis de tous les objets partagés chargés au démarrage du programme, puis de tous les objets partagés chargés par dlopen() avec le drapeau RTLD_GLOBAL

.

Les références de symboles dans l'objet partagé sont résolues en utilisant (dans l'ordre) : les symboles dans la table de liens des objets chargés pour le programme principal et ses dépendances ; les symboles dans les objets partagés (et leurs dépendances) qui ont été ouverts précédemment avec dlopen() en utilisant le drapeau RTLD_GLOBAL ; et les définitions dans l'objet partagé lui-même (et toute dépendance qui a été chargée pour cet objet)

.

Tous les symboles globaux dans l'exécutable qui ont été placés dans sa table de symboles dynamiques par ld(1) peuvent également être utilisés pour résoudre les références dans un objet partagé chargé dynamiquement. Les symboles peuvent être placés dans la table de symboles dynamiques soit parce que l'exécutable a été lié avec le drapeau "-rdynamic" (ou, de manière synonyme, "--export-dynamic"), ce qui provoque le placement de tous les symboles globaux de l'exécutable dans la table de symboles dynamiques, soit parce que ld(1) a noté une dépendance sur un symbole dans un autre objet pendant la liaison

statique.

Si le même objet partagé est ouvert à nouveau avec dlopen(), le même handle d'objet est retourné. L'éditeur de liens dynamique maintient des compteurs de référence pour les handles d'objet, de sorte qu'un objet partagé chargé dynamiquement n'est pas désalloué tant que dlclose() n'a pas été appelé dessus autant de fois que dlopen() a réussi dessus. Les constructeurs (voir ci-dessous) sont appelés uniquement lorsque l'objet est réellement chargé en mémoire (c'est-à-dire lorsque le compteur de référence passe à 1)

.

Un appel dlopen() ultérieur qui charge le même objet partagé avec RTLD_NOW peut forcer la résolution de symboles pour un objet partagé chargé précédemment avec RTLD_LAZY. De même, un objet qui a été ouvert précédemment avec RTLD_LOCAL peut être promu à RTLD_GLOBAL dans un dlopen() ulté

rieur.

retourne NULL.

dlmopen(

)

Cette fonction effectue la même tâche que dlopen()—les arguments chemin et drapeaux, ainsi que la valeur de retour, sont les mêmes, à l'exception des différences notées

ci-dessous.

La fonction dlmopen() diffère de dlopen() principalement en ce qu'elle accepte un argument supplémentaire, lmid, qui spécifie la liste de table de liens (également appelée espace de noms) dans lequel l'objet partagé doit être chargé. (Par comparaison, dlopen() ajoute l'objet partagé chargé dynamiquement au même espace de noms que l'objet partagé à partir duquel l'appel dlopen() est fait.) Le type Lmid_t est un handle opaque qui fait référence à un espace de

noms.

L'argument lmid est soit l'identifiant d'un espace de noms existant (qui peut être obtenu en utilisant la requête dlinfo(3) RTLD_DI_LMID ) soit l'une des valeurs spéciales suivantes

:
LM_ID_BA
SE
Charger l'objet partagé dans l'espace de noms initial (c'est-à-dire l'espace de noms de l'application)
.
LM_ID_NEW
LM
Crée un nouvel espace de noms et charge l'objet partagé dans cet espace de noms
. L'objet doit avoir été correctement lié pour référencer tous les autres objets
partagés dont il a besoin, car le nouvel espace de noms est initialement vide.

Si path est NULL, alors la seule valeur autorisée pour lmid est LM_ID_BAS

E
.

dlclose(

)

La fonction dlclose() décrémente le compteur de références de l'objet partagé chargé dynamiquement référencé par handle

.

Si le compteur de références de l'objet tombe à zéro et que les symboles de cet objet ne sont pas nécessaires à d'autres objets, alors l'objet est déchargé après avoir appelé les éventuels destructeurs définis pour l'objet. (Les symboles de cet objet peuvent être nécessaires à un autre objet parce que cet objet a été ouvert avec l'indicateur RTLD_GLOBAL et que l'un de ses symboles a satisfait une relocation dans un autre objet.

)

Tous les objets partagés qui ont été chargés automatiquement lorsque dlopen() a été invoqué sur l'objet référencé par handle sont fermés récursivement de la même

manière.

Un retour réussi de dlclose() ne garantit pas que les symboles associés à handle sont retirés de l'espace d'adressage de l'appelant. En plus des références résultant d'appels explicites à dlopen(), un objet partagé peut avoir été chargé implicitement (et comptabilisé dans les références) en raison d

es dépendances dans d'autres objets partagés. Ce n'est
que lorsque toutes les références ont été libérées que l
'objet partagé peut être retiré de l'espace d'adressage.

VALEUR

RENVOYÉE

En cas de succès, dlopen() et dlmopen() renvoient un handle non NULL pour l'objet chargé. En cas d'erreur (fichier introuvable, non lisible, de mauvais format, ou provoquant des erreurs lors du chargement), ces fonctions renvoient

NULL.

En cas de succès, dlclose() renvoie 0 ; en cas d'erreur, elle renvoie une valeur non

nulle.

Les erreurs de ces fonctions peuvent être diagnostiquées à l'aide de dlerro

r(
3).

NOTE

S

dlmopen() et espaces de

noms

Une liste de liens de correspondance définit un espace de noms isolé pour la résolution des symboles par l'éditeur de liens dynamique. Au sein d'un espace de noms, les objets partagés dépendants sont chargés implicitement selon les règles habituelles, et les références aux symboles sont de même résolues selon les règles habituelles, mais cette résolution est confinée aux définitions fournies par les objets qui ont été chargés (explicitement et implicitement) dans l'espace de

noms.

La fonction dlmopen() permet l'isolation du chargement d'objets—la capacité de charger un objet partagé dans un nouvel espace de noms sans exposer le reste de l'application aux symboles rendus disponibles par le nouvel objet. Notez que l'utilisation de l'indicateur RTLD_LOCAL n'est pas suffisante à cette fin, car il empêche les symboles d'un objet partagé d'être disponibles à tout autre objet partagé. Dans certains cas, nous pouvons vouloir rendre les symboles fournis par un objet partagé chargé dynamiquement disponibles à (un sous-ensemble d') autres objets partagés sans exposer ces symboles à l'ensemble de l'application. Cela peut être réalisé en utilisant un espace de noms séparé et l'indicateur RTLD_GLOBAL

.

La fonction dlmopen() peut également être utilisée pour fournir une meilleure isolation que l'indicateur RTLD_LOCAL. En particulier, les objets partagés chargés avec RTLD_LOCAL peuvent être promus en RTLD_GLOBAL s'ils sont des dépendances d'un autre objet partagé chargé avec RTLD_GLOBAL. Ainsi, RTLD_LOCAL est insuffisant pour isoler un objet partagé chargé, sauf dans le (rare) cas où l'on a un contrôle explicite sur toutes les dépendances des objets

partagés.

Les utilisations possibles de dlmopen() sont les greffons (plugins) où l'auteur du framework de chargement de greffons ne peut pas faire confiance aux auteurs des greffons et ne souhaite pas que les symboles non définis du framework de greffons soient résolus vers les symboles du greffon. Une autre utilisation est de charger le même objet plus d'une fois. Sans l'utilisation de dlmopen(), cela nécessiterait la création de copies distinctes du fichier d'objet partagé. En utilisant dlmopen(), cela peut être réalisé en chargeant le même fichier d'objet partagé dans différents espaces de

noms.

L'implémentation de glibc

prend en charge un maxim
um de 16 espaces de noms.

Fonctions d'initialisation et de

finalisation

Les objets partagés peuvent exporter des fonctions à l'aide des attributs de fonction __attribute__((constructor)) et __attribute__((destructor)). Les fonctions constructeurs sont exécutées avant que dlopen() ne retourne, et les fonctions destructeurs sont exécutées avant que dlclose() ne retourne. Un objet partagé peut exporter plusieurs constructeurs et destructeurs, et des priorités peuvent être associées à chaque fonction pour déterminer l'ordre dans lequel elles sont exécutées. Voir les pages d'info gcc (sous « Function attributes ») pour plus

d'informations.

Une méthode plus ancienne pour (partiellement) obtenir le même résultat est via l'utilisation de deux symboles spéciaux reconnus par l'éditeur de liens : _init et _fini. Si un objet partagé chargé dynamiquement exporte une routine nommée _init(), alors ce code est exécuté après le chargement d'un objet partagé, avant que dlopen() ne retourne. Si l'objet partagé exporte une routine nommée _fini(), alors cette routine est appelée juste avant que l'objet ne soit déchargé. Dans ce cas, on doit éviter de lier contre les fichiers de démarrage du système, qui contiennent des versions par défaut de ces fichiers ; cela peut être fait en utilisant l'option de ligne de commande gcc(1) -nostartfiles

.

L'utilisation de _init et _fini est désormais obsolète au profit des constructeurs et destructeurs susmentionnés, qui, entre autres avantages, permettent de définir plusieurs fonctions d'initialisation et de

finalisation.

Depuis glibc 2.2.3, atexit(3) peut être utilisé pour enregistrer un gestionnaire de sortie

qui est automatiquement appelé lors
que un objet partagé est déchargé.

S

gé dans un espace de noms autre
que l'espace de noms initial.

S

Le programme ci-dessous charge la bibliothèque mathématique (glibc), recherche l'adresse de la fonction cos(3), et affiche le cosinus de 2.0. Voici un exemple de construction et d'exécution du programme

: 


$ cc dlopen_demo.c -ldl;
$ ./a.out;

Source du

programme 
#include <dlfcn.h>
#include <stdio.h>
#include <stdlib.h>
#include <gnu/lib-names.h>  /* Définit LIBM_SO (qui sera une
                               chaîne telle que "libm.so.6") */
int
main(void)
{
    void *handle;
    typeof(double (double)) *cosine;
    char *error;
    handle = dlopen(LIBM_SO, RTLD_LAZY);
    if (!handle) {
        fprintf(stderr, "%s\n", dlerror());
        exit(EXIT_FAILURE);
    }
    dlerror();    /* Efface toute erreur existante */
    cosine = (typeof(double (double)) *) dlsym(handle, "cos");
    /* Selon la norme ISO C, le casting entre pointeurs de
       fonction et 'void *', comme fait ci-dessus, produit des résultats
       indéfinis. POSIX.1-2001 et POSIX.1-2008 ont accepté cet état de fait et
       proposé le contournement suivant :
           *(void **) &cosine = dlsym(handle, "cos");
       Ce cast (maladroit) est conforme à la norme ISO C et évitera
       les avertissements de compilateur.
       Le Corrigendum Technique 2013 à POSIX.1-2008 a amélioré les choses
       en exigeant que les implémentations conformes supportent le casting
       de 'void *' en pointeur de fonction.  Néanmoins, certains compilateurs
       (par ex., gcc avec l'option '-pedantic') peuvent se plaindre du
       cast utilisé dans ce programme.  */
    error = dlerror();
    if (error != NULL) {
        fprintf(stderr, "%s\n", error);
        exit(EXIT_FAILURE);
    }
    printf("%f\n", (*cosine)(2.0));
    dlclose(handle);
    exit(EXIT_SUCCESS)
;
}
