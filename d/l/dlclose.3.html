dlopen(3) Manuel des fonctions de bibliothèque dlopen(3)

NOM

dlclose, dlopen, dlmopen - ouvrir et fermer un objet partagé

BIBLIOTHÈQUE

Bibliothèque de liaison dynamique (libdl, -ldl)

SYNTAXE

#include <dlfcn.h>
void *dlopen(const char *path, int flags);
int dlclose(void *handle);
#define _GNU_SOURCE
#include <dlfcn.h>
void *dlmopen(Lmid_t lmid, const char *path, int flags);

DESCRIPTION

dlopen()

La fonction dlopen() charge le fichier d'objet partagé dynamique (bibliothèque partagée) nommé par la chaîne terminée par un caractère nul path et renvoie un « handle » opaque pour l'objet chargé. Ce handle est utilisé avec d'autres fonctions de l'API dlopen, telles que dlsym(3), dladdr(3), dlinfo(3) et dlclose().

Si path est NULL, le handle retourné correspond au programme principal. Si path contient une barre oblique ("/"), elle est interprétée comme un nom de chemin (relatif ou absolu). Sinon, le lieur dynamique recherche l'objet comme suit (voir ld.so(8) pour plus de détails) :

•
(ELF uniquement) Si l'objet appelant (c'est-à-dire la bibliothèque partagée ou l'exécutable à partir duquel dlopen() est appelé) contient une balise DT_RPATH, et ne contient pas de balise DT_RUNPATH, alors les répertoires listés dans la balise DT_RPATH sont recherchés.
•
Si, au moment du démarrage du programme, la variable d'environnement LD_LIBRARY_PATH était définie pour contenir une liste de répertoires séparés par des deux-points, alors ceux-ci sont recherchés. (Par mesure de sécurité, cette variable est ignorée pour les programmes set-user-ID et set-group-ID.)
•
(ELF uniquement) Si l'objet appelant contient une balise DT_RUNPATH, alors les répertoires listés dans cette balise sont recherchés.
•
Le fichier cache /etc/ld.so.cache (maintenu par ldconfig(8)) est vérifié pour voir s'il contient une entrée pour path.
•
Les répertoires /lib et /usr/lib sont recherchés (dans cet ordre).

Si l'objet spécifié par path a des dépendances sur d'autres objets partagés, ceux-ci sont également chargés automatiquement par le lieur dynamique en utilisant les mêmes règles. (Ce processus peut se produire récursivement, si ces objets ont à leur tour des dépendances, et ainsi de suite.)

L'une des deux valeurs suivantes doit être incluse dans flags :

RTLD_LAZY
Effectue la liaison paresseuse. Résout les symboles uniquement lorsque le code qui les référence est exécuté. Si le symbole n'est jamais référencé, il n'est jamais résolu. (La liaison paresseuse n'est effectuée que pour les références de fonctions ; les références aux variables sont toujours liées immédiatement lors du chargement de l'objet partagé.) Depuis glibc 2.1.1, ce drapeau est outrepassé par l'effet de la variable d'environnement LD_BIND_NOW.
RTLD_NOW
Si cette valeur est spécifiée, ou si la variable d'environnement LD_BIND_NOW est définie sur une chaîne non vide, tous les symboles non définis dans l'objet partagé sont résolus avant que dlopen() ne renvoie. Si cela ne peut pas être fait, une erreur est renvoyée.

Zéro ou plusieurs des valeurs suivantes peuvent également être ORées dans flags :

RTLD_GLOBAL
Les symboles définis par cet objet partagé seront rendus disponibles pour la résolution de symboles des objets partagés chargés ultérieurement.
RTLD_LOCAL
C'est le contraire de RTLD_GLOBAL, et le comportement par défaut si aucun drapeau n'est spécifié. Les symboles définis dans cet objet partagé ne sont pas rendus disponibles pour résoudre les références dans les objets partagés chargés ultérieurement.
RTLD_NODELETE (depuis glibc 2.2)
Ne pas décharger l'objet partagé lors de dlclose(). Par conséquent, les variables statiques et globales de l'objet ne sont pas réinitialisées si l'objet est rechargé avec dlopen() ultérieurement.
RTLD_NOLOAD (depuis glibc 2.2)
Ne pas charger l'objet partagé. Ceci peut être utilisé pour tester si l'objet est déjà résident (dlopen() renvoie NULL s'il ne l'est pas, ou le handle de l'objet s'il est résident). Ce drapeau peut également être utilisé pour promouvoir les drapeaux d'un objet partagé déjà chargé. Par exemple, un objet partagé qui a été précédemment chargé avec RTLD_LOCAL peut être rouvert avec RTLD_NOLOAD | RTLD_GLOBAL.
RTLD_DEEPBIND (depuis glibc 2.3.4)
Placer la portée de recherche des symboles dans cet objet partagé avant la portée globale. Cela signifie qu'un objet autonome utilisera ses propres symboles de préférence aux symboles globaux portant le même nom contenus dans des objets qui ont déjà été chargés.

Si path est NULL, le handle retourné correspond au programme principal. Lorsqu'il est donné à dlsym(3), ce handle provoque une recherche d'un symbole dans le programme principal, suivi de tous les objets partagés chargés au démarrage du programme, puis de tous les objets partagés chargés par dlopen() avec le drapeau RTLD_GLOBAL.

Les références de symboles dans l'objet partagé sont résolues en utilisant (dans l'ordre) : les symboles dans le plan de liaison des objets chargés pour le programme principal et ses dépendances ; les symboles dans les objets partagés (et leurs dépendances) qui ont été précédemment ouverts avec dlopen() en utilisant le drapeau RTLD_GLOBAL ; et les définitions dans l'objet partagé lui-même (et toute dépendance chargée pour cet objet).

Tous les symboles globaux de l'exécutable qui ont été placés dans sa table de symboles dynamique par ld(1) peuvent également être utilisés pour résoudre les références dans un objet partagé chargé dynamiquement. Les symboles peuvent être placés dans la table de symboles dynamique soit parce que l'exécutable a été lié avec le drapeau "-rdynamic" (ou, de manière synonyme, "--export-dynamic"), ce qui fait que tous les symboles globaux de l'exécutable sont placés dans la table de symboles dynamique, soit parce que ld(1) a noté une dépendance sur un symbole d'un autre objet lors de la liaison statique.

Si le même objet partagé est ouvert à nouveau avec dlopen(), le même handle d'objet est renvoyé. Le lieur dynamique maintient des comptes de référence pour les handles d'objets, de sorte qu'un objet partagé chargé dynamiquement n'est pas désalloué tant que dlclose() n'a pas été appelé sur lui autant de fois que dlopen() a réussi sur lui. Les constructeurs (voir ci-dessous) ne sont appelés que lorsque l'objet est effectivement chargé en mémoire (c'est-à-dire lorsque le compte de référence passe à 1).

Un appel ultérieur à dlopen() qui charge le même objet partagé avec RTLD_NOW peut forcer la résolution de symboles pour un objet partagé précédemment chargé avec RTLD_LAZY. De même, un objet qui a été précédemment ouvert avec RTLD_LOCAL peut être promu en RTLD_GLOBAL dans un appel dlopen() ultérieur.

Si dlopen() échoue pour une raison quelconque, il renvoie NULL.

dlmopen()

Cette fonction effectue la même tâche que dlopen()—les arguments path et flags, ainsi que la valeur de retour, sont les mêmes, à l'exception des différences notées ci-dessous.

La fonction dlmopen() diffère de dlopen() principalement en ce qu'elle accepte un argument supplémentaire, lmid, qui spécifie la liste des plans de liaison (également appelée *espace de noms*) dans laquelle l'objet partagé doit être chargé. (En comparaison, dlopen() ajoute l'objet partagé chargé dynamiquement dans le même espace de noms que l'objet partagé à partir duquel l'appel dlopen() est effectué.) Le type Lmid_t est un handle opaque qui fait référence à un espace de noms.

L'argument lmid est soit l'ID d'un espace de noms existant (qui peut être obtenu en utilisant la requête RTLD_DI_LMID de dlinfo(3)) soit l'une des valeurs spéciales suivantes :

LM_ID_BASE
Charge l'objet partagé dans l'espace de noms initial (c'est-à-dire l'espace de noms de l'application).

LM_ID_NEW
LM
Crée un nouvel espace de noms et charge l'objet partagé dans cet espace de noms
. L'objet doit avoir été correctement lié pour référencer tous les autres objets partagés dont il a besoin, car le nouvel espace de noms est initialement vide.

Si path est NULL, alors la seule valeur autorisée pour lmid est LM_ID_BAS

E.

dlclose(

)

La fonction dlclose() décrémente le compteur de références de l'objet partagé chargé dynamiquement référencé par handle

.

Si le compteur de références de l'objet tombe à zéro et qu'aucun symbole de cet objet n'est requis par d'autres objets, alors l'objet est déchargé après avoir d'abord appelé tous les destructeurs définis pour l'objet. (Les symboles dans cet objet peuvent être requis dans un autre objet parce que cet objet a été ouvert avec l'indicateur RTLD_GLOBAL et que l'un de ses symboles a satisfait une relocalisation dans un autre objet.

)

Tous les objets partagés qui ont été chargés automatiquement lorsque dlopen() a été invoqué sur l'objet référencé par handle sont fermés récursivement de la même

manière.

Un retour réussi de dlclose() ne garantit pas que les symboles associés à handle sont retirés de l'espace d'adressage de l'appelant. En plus des références résultant des appels explicites à dlopen(), un objet partagé peut avoir été chargé implicitement (et comptabilisé en références) à cause des d

épendances dans d'autres objets partagés. Ce n'est que
lorsque toutes les références ont été libérées que l'objet partagé peut être retiré de l'espace d'adressage.

VALEUR

RENVOYÉE

En cas de succès, dlopen() et dlmopen() renvoient un handle non NULL pour l'objet chargé. En cas d'erreur (le fichier n'a pas pu être trouvé, n'était pas lisible, avait le mauvais format, ou a causé des erreurs lors du chargement), ces fonctions renvoient

NULL.

En cas de succès, dlclose() renvoie 0 ; en cas d'erreur, elle renvoie une valeur non

nulle.

Les erreurs de ces fonctions peuvent être diagnostiquées en utilisant dlerro

r(
3).

NOTE

S

dlmopen() et les espaces de

noms

Une liste de liens de correspondance définit un espace de noms isolé pour la résolution des symboles par l'éditeur de liens dynamique. Au sein d'un espace de noms, les objets partagés dépendants sont chargés implicitement selon les règles habituelles, et les références aux symboles sont de même résolues selon les règles habituelles, mais cette résolution est confinée aux définitions fournies par les objets qui ont été chargés (explicitement et implicitement) dans l'espace de

noms.

La fonction dlmopen() permet l'isolation au chargement des objets—la capacité de charger un objet partagé dans un nouveau espace de noms sans exposer le reste de l'application aux symboles rendus disponibles par le nouvel objet. Notez que l'utilisation de l'indicateur RTLD_LOCAL n'est pas suffisante à cette fin, car il empêche les symboles d'un objet partagé d'être disponibles pour tout autre objet partagé. Dans certains cas, nous pouvons vouloir rendre les symboles fournis par un objet partagé chargé dynamiquement disponibles pour (un sous-ensemble de) d'autres objets partagés sans exposer ces symboles à toute l'application. Cela peut être réalisé en utilisant un espace de noms séparé et l'indicateur RTLD_GLOBAL

.

La fonction dlmopen() peut aussi être utilisée pour fournir une meilleure isolation que l'indicateur RTLD_LOCAL. En particulier, les objets partagés chargés avec RTLD_LOCAL peuvent être promus en RTLD_GLOBAL s'ils sont des dépendances d'un autre objet partagé chargé avec RTLD_GLOBAL. Ainsi, RTLD_LOCAL est insuffisant pour isoler un objet partagé chargé sauf dans le cas (peu courant) où l'on a un contrôle explicite sur toutes les dépendances des objets

partagés.

Les utilisations possibles de dlmopen() sont les plugins où l'auteur du framework de chargement de plugins ne peut pas faire confiance aux auteurs des plugins et ne souhaite pas que des symboles indéfinis du framework de plugins soient résolus vers des symboles de plugin. Une autre utilisation est de charger le même objet plus d'une fois. Sans l'utilisation de dlmopen(), cela nécessiterait la création de copies distinctes du fichier d'objet partagé. En utilisant dlmopen(), cela peut être réalisé en chargeant le même fichier d'objet partagé dans différents espaces de

noms.

L'implémentation de gli

bc supporte un maximum
de 16 espaces de noms.

Fonctions d'initialisation et de

finalisation

Les objets partagés peuvent exporter des fonctions en utilisant les attributs de fonction __attribute__((constructor)) et __attribute__((destructor)). Les fonctions constructeurs sont exécutées avant que dlopen() ne retourne, et les fonctions destructeurs sont exécutées avant que dlclose() ne retourne. Un objet partagé peut exporter plusieurs constructeurs et destructeurs, et des priorités peuvent être associées à chaque fonction pour déterminer l'ordre dans lequel elles sont exécutées. Voir les pages info de gcc (sous « Function attributes ») pour plus

d'informations.

Une méthode plus ancienne pour (partiellement) obtenir le même résultat est via l'utilisation de deux symboles spéciaux reconnus par l'éditeur de liens : _init et _fini. Si un objet partagé chargé dynamiquement exporte une routine nommée _init(), alors ce code est exécuté après le chargement d'un objet partagé, avant que dlopen() ne retourne. Si l'objet partagé exporte une routine nommée _fini(), alors cette routine est appelée juste avant que l'objet ne soit déchargé. Dans ce cas, on doit éviter de lier contre les fichiers de démarrage du système, qui contiennent des versions par défaut de ces fichiers ; cela peut être fait en utilisant l'option de ligne de commande -nostartfiles de gcc(1)

.

L'utilisation de _init et _fini est maintenant dépréciée au profit des constructeurs et destructeurs susmentionnés, qui, entre autres avantages, permettent de définir plusieurs fonctions d'initialisation et de

finalisation.

Depuis glibc 2.2.3, atexit(3) peut être utilisé pour enregistrer un gestionnaire de sort

ie qui est automatiquement appelé qu
and un objet partagé est déchargé.

EXEMPLE

S

Le programme ci-dessous charge la bibliothèque mathématique (glibc), cherche l' adresse de la fonction cos(3), et affiche le cosinus de 2.0. Le qui suit est un exemple de construction et d'exécution du programme

: 


$ cc dlopen_demo.c -ldl;
$ ./a.out;
-0.
416147

Source du

programme 
#include <dlfcn.h>
#include <stdio.h>
#include <stdlib.h>
#include <gnu/lib-names.h>  /* Définit LIBM_SO (qui sera une
                               chaîne telle que "libm.so.6") */
int
main(void)
{
    void *handle;
    typeof(double (double)) *cosine;
    char *error;
    handle = dlopen(LIBM_SO, RTLD_LAZY);
    if (!handle) {
        fprintf(stderr, "%s\n", dlerror());
        exit(EXIT_FAILURE);
    }
    dlerror();    /* Efface toute erreur existante */
    cosine = (typeof(double (double)) *) dlsym(handle, "cos");
    /* Selon la norme ISO C, le cast entre pointeurs de fonction
       et 'void *', comme fait ci-dessus, produit des résultats indéfinis.
       POSIX.1-2001 et POSIX.1-2008 ont accepté cet état de fait et
       proposé le contournement suivant :
           *(void **) &cosine = dlsym(handle, "cos");
       Ce cast (maladroit) est conforme à la norme ISO C et évitera
       tout avertissement de compilateur.
       Le Corrigendum Technique 2013 à POSIX.1-2008 a amélioré les choses
       en exigeant que les implémentations conformes supportent le cast
       de 'void *' vers un pointeur de fonction. Néanmoins, certains compilateurs
       (par ex., gcc avec l'option '-pedantic') peuvent se plaindre du
       cast utilisé dans ce programme.  */
    error = dlerror();
    if (error != NULL) {
        fprintf(stderr, "%s\n", error);
        exit(EXIT_FAILURE);
    }
    printf("%f\n", (*cosine)(2.0));
    dlclose(handle);
    exit(EXIT_SUCCESS)
;
}

NOM

dlclose — fermer une bibliothèque partagée chargée dynamiquement

BIBLIOTHÈQUE

Bibliothèque de lien dynamique : libc.so.6
Chemin de lien : ld-linux.so.2

SYNTAXE

#include <dlfcn.h>
int dlclose(void *handle);

DESCRIPTION

La fonction dlclose ferme un objet de bibliothèque partagée qui a été précédemment ouvert par un appel à dlopen(3). Le paramètre handle est une poignée retournée par un appel réussi à dlopen(3).

Le comportement de dlclose est défini par la comptabilité de référence des objets de bibliothèque. Chaque fois qu'un objet de bibliothèque est ouvert, son compteur de références est incrémenté. dlclose décrémente le compteur de références de l'objet de bibliothèque ; si le compteur atteint zéro, l'objet de bibliothèque est déchargé de l'espace d'adressage du processus.

Le déchargement d'un objet de bibliothèque peut avoir des effets secondaires, tels que l'appel des fonctions de destruction enregistrées par la bibliothèque (voir dlsym(3) ; dladdr(3) ; dlerror(3) ; dlopen(3) ; rtld-audit(7) ; ld.so(8) ; ldconfig(8)).

VALEUR RENVOYÉE

En cas de succès, dlclose renvoie 0. En cas d'échec, elle renvoie une valeur non nulle et définit un indicateur d'erreur qui peut être interrogé avec dlerror(3).

Pour une explication des termes utilisés dans cette section, voir attributes(7).

dlclose Multi-threadé

NORMES

La fonction dlclose est conforme à la norme POSIX.1-2008.

HISTORIQUE

La fonction dlclose est apparue pour la première fois dans la version 2 de la spécification ABI des bibliothèques partagées de System V Release 4.

NOTES

Si la poignée handle ne correspond pas à une bibliothèque ouverte avec succès, ou si elle a déjà été fermée, le comportement est indéfini.

Si plusieurs appels à dlopen(3) ouvrent la même bibliothèque, plusieurs appels à dlclose sont nécessaires pour décharger la bibliothèque.

BOGUES

Les bogues connus et les problèmes potentiels sont souvent liés à la façon dont les bibliothèques sont chargées et déchargées, et à la gestion des symboles et des dépendances entre les bibliothèques. La documentation détaillée sur les bogues et les problèmes est généralement trouvée dans la documentation spécifique à l'implémentation du chargeur dynamique, comme ld.so(8) et rtld-audit(7).
