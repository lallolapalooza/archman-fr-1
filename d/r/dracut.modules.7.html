NOM

dracut.modules - modules dracut

DESCRIPTION

dracut utilise un système modulaire pour construire et étendre l'image initramfs. Tous les modules sont situés dans /usr/lib/dracut/modules.d ou dans <git-src>/modules.d. Le module dracut le plus basique est 80base. Dans 80base, le script shell initial init est défini, qui est exécuté par le noyau après le chargement de l'initramfs. Bien que vous puissiez remplacer init par votre propre version de 80base, ce n'est pas recommandé. Au lieu de cela, vous devriez utiliser, si possible, les hooks de dracut. Tous les hooks, et le moment où ils sont exécutés, sont décrits dans PHASES_DU_PROCESSUS_DE_DÉMARRAGE.

Le script principal, qui crée l'initramfs, est dracut lui-même. Il analyse tous les arguments et configure le répertoire dans lequel tout est installé. Il exécute ensuite tous les scripts check, install, installkernel trouvés dans les modules qui doivent être traités. Après que tout soit installé, le répertoire d'installation est archivé et compressé pour former l'image initramfs finale. Toutes les fonctions d'aide utilisées par les scripts check, install et installkernel se trouvent dans le fichier dracut-functions. Ces fonctions shell sont disponibles pour tous les scripts d'installation de modules (install, installkernel), sans avoir besoin de sourcer dracut-functions.

Un module peut vérifier les préconditions pour install et installkernel avec le script check. Les dépendances peuvent également être exprimées avec check. Si un module a passé check, install et installkernel seront appelés pour installer tous les fichiers nécessaires au module. Pour séparer les parties relatives au noyau et les parties non relatives au noyau de l'installation, toutes les parties liées aux modules du noyau doivent se trouver dans installkernel. Tous les autres fichiers trouvés dans un répertoire de module sont spécifiques au module et sont principalement des scripts de hook et des règles udev.

PHASES_DU_PROCESSUS_DE_DÉMARRAGE

Les modules dracut peuvent insérer des scripts personnalisés à divers points pour contrôler le processus de démarrage. Ces hooks sont des répertoires simples contenant des scripts shell se terminant par ".sh", qui sont sourcés par init. Les fonctions couramment utilisées se trouvent dans dracut-lib.sh, qui peuvent être sourcées par n'importe quel script.

Hook : cmdline

Le hook cmdline est un endroit pour insérer des scripts afin d'analyser la ligne de commande du noyau et de préparer les actions ultérieures, telles que la configuration des règles udev et des fichiers de configuration.

Dans ce hook, la variable d'environnement la plus importante est définie : root. La deuxième est rootok, qui indique qu'un module a prétendu être capable d'analyser la racine définie. Ainsi, par exemple, root=iscsi:.... sera revendiqué par le module dracut iscsi, qui définit alors rootok.

Hook: pre-udev

Ce hook est exécuté juste après le hook cmdline et une vérification si root et rootok ont été définis. Ici, les modules peuvent agir avec la racine finale et avant que udev n'ait été exécuté.

Démarrage d'Udev

Maintenant, udev est démarré et la journalisation pour udev est mise en place.

Hook: pre-trigger

Dans ce hook, vous pouvez définir des variables d'environnement udev avec udevadm control --property=KEY=valeur ou contrôler l'exécution ultérieure d'udev avec udevadm.

Déclenchement d'Udev

udev est déclenché en appelant udevadm trigger, qui envoie des événements d'ajout pour tous les périphériques et sous-systèmes.

Boucle principale

La boucle principale de dracut boucle jusqu'à ce qu'udev soit stabilisé et que tous les scripts dans initqueue/finished aient retourné true. Dans cette boucle, il y a trois hooks où des scripts peuvent être insérés en appelant /sbin/initqueue.

Initqueue

Ce hook est exécuté chaque fois qu'un script y est inséré, quel que soit l'état d'udev.

Initqueue stabilisé

Ce hook (initqueue/settled) est exécuté chaque fois qu'udev est stabilisé.

Délai d'attente d'Initqueue

Ce hook (initqueue/timeout) est exécuté lorsque le compteur de la boucle principale atteint la moitié du compteur rd.retry.

Initqueue en ligne

Ce hook (initqueue/online) est exécuté chaque fois qu'une interface réseau est mise en ligne (c'est-à-dire, une fois qu'elle est active et configurée par le module réseau configuré).

Initqueue terminé

Ce hook (initqueue/finished) est appelé après la stabilisation d'udev et si tous les scripts ici retournent 0, la boucle principale se terminera. Des scripts arbitraires peuvent être ajoutés ici, pour boucler dans l'initqueue jusqu'à ce que quelque chose se produise, ce qui est attendu par un module dracut.

Hook: pre-mount

Avant que le périphérique racine ne soit monté, tous les scripts du hook pre-mount sont exécutés. Dans certains cas (par exemple, NFS), le périphérique racine réel est déjà monté, cependant.

Hook : mount

Ce hook sert principalement à monter le périphérique racine réel.

Hook: pre-pivot

Ce hook est appelé avant le hook cleanup. C'est un bon endroit pour les actions autres que les nettoyages qui doivent être appelées avant le pivot.

Hook : cleanup

Ce hook est le dernier hook et est appelé avant que init ne bascule finalement la racine vers le périphérique racine réel. C'est un bon endroit pour nettoyer et tuer les processus qui ne sont plus nécessaires.

Nettoyage et switch_root

Init (ou systemd) tue tous les processus udev, nettoie l'environnement, configure les arguments pour le processus init réel et appelle enfin switch_root. switch_root supprime toute la hiérarchie des fichiers de l'initramfs, chroot() vers le périphérique racine réel et appelle /sbin/init avec les arguments spécifiés.

Pour garantir que tous les fichiers de la hiérarchie initramfs puissent être supprimés, tous les processus encore en cours d'exécution depuis l'initramfs ne doivent plus avoir de descripteurs de fichiers ouverts.

ÉCRIRE UN MODULE

Un exemple de module simple est 90kernel-modules, qui fait un modprobe d'un module noyau après que udev se soit stabilisé et que les pilotes de périphériques de base aient été chargés.

Toutes les informations d'installation du module se trouvent dans le fichier module-setup.sh.

Les variables shell suivantes sont les plus couramment utilisées dans les modules dracut. Ces variables shell sont toujours déclarées et ont des valeurs assignées (la valeur assignée peut être une chaîne vide). Il existe une promesse de compatibilité pour ces variables entre les versions de dracut. Les modules ne devraient que lire (et non écrire) ces variables. * $hostonly (peut être une chaîne vide) * $hostonly_mode (peut être une chaîne vide) * $hostonly_cmdline (pas une chaîne vide) * $moddir (pas une chaîne vide)

Tout d'abord, nous créons une fonction check(), qui se termine simplement par 0, indiquant que ce module doit être inclus par défaut.

check():

return 0

Ensuite, nous créons la fonction install(), qui installe un hook cmdline avec le numéro de priorité 20 appelé parse-insmodpost.sh. Elle installe également le script insmodpost.sh dans /sbin.

install():

inst_hook cmdline 20 "$moddir/parse-insmodpost.sh"
inst_simple "$moddir/insmodpost.sh" /sbin/insmodpost.sh

Le parse-instmodpost.sh analyse la ligne de commande du noyau pour un argument rd.driver.post, met en liste noire le module pour qu'il ne soit pas chargé automatiquement et installe le hook insmodpost.sh dans initqueue/sett

led.

parse-insmodpost.sh:

for p in $(getargs rd.driver.post=); do
    echo "blacklist $p" >> /run/modprobe.d/initramfsblacklist.conf
    _do_insmodpost=1
done
[ -n "$_do_insmodpost" ] && /sbin/initqueue --settled --unique --onetime /sbin/insmodpost.sh
unset _do_insmodpost

insmodpost.sh, qui est appelé dans le initqueue/settled hook fera simplement modprobe les modules du noyau spécifiés dans tous les paramètres rd.driver.post de la ligne de commande du noyau. Il s'exécute après que udev s'est stabilisé et n'est appelé qu'une seule fois (--onetime).

insmodpost.sh:

. /lib/dracut-lib.sh
for p in $(getargs rd.driver.post=); do
    modprobe $p
done

module-setup.sh: check()

check() est appelé par dracut pour évaluer l'inclusion d'un module dracut dans l'initramfs.

$hostonly

Si la variable $hostonly est définie, alors la fonction check() du module doit être en mode « hostonly », ce qui signifie que check() ne doit retourner 0 que si le module est réellement nécessaire pour démarrer cet hôte spécifique.

Évitez de prendre des décisions à l'intérieur de cette fonction basées sur la valeur de la variable $hostonly_mode. Ce principe garantit l'inclusion des mêmes modules dracut à la fois en mode sloppy et en mode strict.

check() doit retourner :

0

Inclure le module dracut dans l'initramfs.

1

Ne pas inclure le module dracut. Les prérequis ne sont pas remplis (outils manquants, etc.)

255

Inclure le module dracut uniquement si un autre module en dépend ou s'il est explicitement spécifié dans le fichier de configuration ou sur la liste d'arguments.

module-setup.sh: depends()

La fonction depends() doit écho tous les autres noms de modules dracut dont le module dépend.

module-setup.sh: cmdline()

Cette fonction doit afficher les options de la ligne de commande du noyau nécessaires pour démarrer la configuration de la machine actuelle. Elle doit commencer par un espace et ne doit pas afficher un retour à la ligne.

module-setup.sh: install()

La fonction install() est appelée pour installer tout ce qui n'est pas lié au noyau. Pour installer des binaires, des scripts et d'autres fichiers, vous pouvez utiliser les fonctions mentionnées dans [creation].

Pour référencer un fichier dans le répertoire du module actuel, utilisez la variable "$moddir".

module-setup.sh: installkernel()

Dans installkernel(), tous les fichiers liés au noyau doivent être installés. Vous pouvez utiliser toutes les fonctions mentionnées dans [creation] pour installer des fichiers.

Fonctions de création

inst_dir <dir>

installe un répertoire <dir> (mais pas son contenu) au même endroit dans l'image initramfs.

inst [-H] <src> [<dst>]

inst_binary <src> [<dst>]

inst_script <src> [<dst>]

installe un fichier <src> soit au même endroit dans l'initramfs soit vers une destination <dst> optionnelle, ainsi que ses dépendances et son fichier .hmac (s'il existe). inst avec plus de deux arguments est traité de la même manière que inst_multiple, tous les arguments sont traités comme des fichiers à installer et aucun comme destination d'installation.

options :

-H

journalise tous les fichiers installés dans /lib/dracut/hostonly-files, afin qu'ils puissent être supprimés si rd.hostonly est passé sur la ligne de commande du noyau.

inst_simple [-H] <src> [<dst>]

installe un fichier <src> soit au même endroit dans l'initramfs soit vers une destination <dst> optionnelle, mais sans installer ses dépendances ni son fichier .hmac.

options :

-H

journalise tous les fichiers installés dans /lib/dracut/hostonly-files, afin qu'ils puissent être supprimés si rd.hostonly est passé sur la ligne de commande du noyau.

inst_multiple [-H] [-o] <file> [ <file> ...]

installe plusieurs binaires et fichiers. Si des exécutables sont spécifiés sans chemin, dracut cherchera le binaire dans le chemin PATH=/usr/sbin:/sbin:/usr/bin:/bin.

options :

-H

journalise tous les fichiers installés dans /lib/dracut/hostonly-files, afin qu'ils puissent être supprimés si rd.hostonly est passé sur la ligne de commande du noyau.

-o

optionnel, un fichier manquant ne provoque pas d'erreur.

inst_hook <hookdir> <prio> <src>

installe un exécutable/script <src> dans le hook dracut <hookdir> avec la priorité <prio>.

inst_rules <udevrule> [ <udevrule> ...]

installe une ou plusieurs règles udev. Les règles udev inexistantes sont signalées, mais ne font pas échouer dracut.

inst_libdir_dir <dir> [<dir>...]

installe plusieurs répertoires (mais pas leur contenu) situés dans un répertoire de bibliothèque dans l'image initramfs.

inst_libdir_file [-n <pattern>] [-o] <file> [<file>...]

installe plusieurs fichiers situés dans un répertoire de bibliothèque dans l'image initramfs.

options :

-n <pattern>

installe toutes les bibliothèques correspondant à un motif.

-o

optionnel, une bibliothèque manquante ne provoque pas d'erreur.

instmods [-c] [-s] <kernelmodule> [ <kernelmodule> ... ]

instmods ne doit être utilisé que dans la fonction installkernel().

instmods installe un ou plusieurs modules du noyau dans l'initramfs. <kernelmodule> peut aussi être un sous-système entier, s'il est préfixé par un "=", comme "=drivers/net/team".

instmods n'installera pas le module du noyau si $hostonly est défini et que le module du noyau n'est actuellement requis par aucun /sys/.../uevent MODALIAS. Pour installer un module du noyau quel que soit le mode hostonly, utilisez la forme :

hostonly='' instmods <kernelmodule>

un motif courant pour appeler instmods est d'utiliser la forme suivante :

`hostonly=$(optional_hostonly) instmods <kernelmodule>`

Cette instruction installe le module du noyau dans l'une des conditions suivantes : * en mode non-hostonly (quel que soit l'état de l'hôte) * en mode sloppy hostonly (quel que soit l'état de l'hôte) * en mode hostonly si le module du noyau est déjà chargé sur l'hôte

options :

-c

vérifie que les modules du noyau existent et peuvent être installés (c'est-à-dire, non optionnels).

-s

réduit la verbosité.
