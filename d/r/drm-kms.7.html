Nom

drm-kms - Kernel Mode-Setting

Synopsis

#include <xf86drm.h>

#include <xf86drmMode.h>

Description

Chaque périphérique DRM fournit l'accès à la gestion des moniteurs et des écrans actuellement utilisés et des images à afficher. Cette tâche est appelée Kernel Mode-Setting (KMS). Historiquement, cela était fait en espace utilisateur et appelé User-space Mode-Setting (UMS). Presque tous les pilotes open-source fournissent maintenant l'API du noyau KMS pour cela, cependant, de nombreux pilotes binaires non open-source de différents fournisseurs ne le supportent toujours pas. Vous pouvez utiliser drmModeSettingSupported(3) pour vérifier si votre pilote supporte cela. Pour comprendre le fonctionnement de KMS, nous devons introduire 5 objets : CRTCs, Planes, Encodeurs, Connecteurs et Framebuffers.

CRTCs
Un CRTC (acronyme de CRT Controller) est une abstraction représentant une partie de la puce qui contient un pointeur vers un tampon de balayage. Par conséquent, le nombre de CRTC disponibles détermine combien de tampons de balayage indépendants peuvent être actifs à tout moment. La structure CRTC contient plusieurs champs pour supporter cela : un pointeur vers une mémoire vidéo (abstraite sous forme d'objet framebuffer), une liste de connecteurs pilotés, un mode d'affichage et un décalage (x, y) dans la mémoire vidéo pour supporter le panoramique ou les configurations où une pièce de mémoire vidéo s'étend sur plusieurs CRTC. Un CRTC est le point central où la configuration des écrans se produit. Vous sélectionnez quels objets utiliser, quels modes et quels paramètres, puis configurez chaque CRTC via drmModeCrtcSet(3) pour piloter les périphériques d'affichage.
Planes
Un plan (plane) représente une source d'image qui peut être mélangée ou superposée à un CRTC pendant le processus de balayage. Les plans sont associés à un framebuffer pour rogner une partie de la mémoire d'image (source) et éventuellement la redimensionner à une taille de destination. Le résultat est ensuite mélangé ou superposé sur un CRTC. Les plans ne sont pas fournis par tous les matériels et le nombre de plans disponibles est limité. Si les plans ne sont pas disponibles ou si des plans insuffisants sont disponibles, l'utilisateur devrait se rabattre sur le mélange logiciel normal (via GPU ou CPU).
Encodeurs
Un encodeur prend des données de pixels d'un CRTC et les convertit dans un format adapté à tous les connecteurs attachés. Sur certains périphériques, il peut être possible qu'un CRTC envoie des données à plus d'un encodeur. Dans ce cas, les deux encodeurs recevraient des données du même tampon de balayage, résultant en une configuration d'affichage clonée sur les connecteurs attachés à chaque encodeur.
Connecteurs
Un connecteur est la destination finale des données de pixels sur un périphérique, et se connecte généralement directement à un périphérique d'affichage externe comme un moniteur ou un écran de portable. Un connecteur ne peut être attaché qu'à un seul encodeur à la fois. Le connecteur est également la structure où les informations sur l'écran attaché sont conservées, il contient donc des champs pour les données d'affichage, les données EDID, le DPMS et le statut de connexion, ainsi que des informations sur les modes supportés par les écrans attachés.
Framebuffers
Les Framebuffers sont des objets mémoire abstraits qui fournissent une source de données de pixels à balayer vers un CRTC. Les applications demandent explicitement la création de framebuffers et peuvent contrôler leur comportement. Les framebuffers s'appuient sur le gestionnaire mémoire sous-jacent pour les opérations mémoire de bas niveau. Lors de la création d'un framebuffer, les applications passent un handle mémoire via l'API qui est utilisé comme stockage de sauvegarde. Le framebuffer lui-même n'est qu'un objet abstrait sans données. Il fait simplement référence à des tampons mémoire qui doivent être créés avec l'API de drm-memory(7).

Mode-Setting

Avant que le mode-setting puisse être effectué, une application doit appeler drmSetMaster(3) pour devenir le DRM-Master. Elle a alors un accès exclusif à l'API KMS. Un appel à drmModeGetResources(3) renvoie une liste de CRTCs, Connecteurs, Encodeurs et Planes.

La procédure normale comprend maintenant : Premièrement, vous sélectionnez les connecteurs que vous souhaitez utiliser. Les utilisateurs sont principalement intéressés par le moniteur ou l'écran actif, vous devez donc vous assurer de les organiser dans le bon ordre logique et de sélectionner ceux à utiliser. Pour chaque connecteur, vous devez trouver un CRTC pour piloter ce connecteur. Si vous souhaitez cloner la sortie vers deux ou plusieurs connecteurs, vous pouvez utiliser un seul CRTC pour tous les connecteurs clonés (si le matériel le supporte). Pour trouver un CRTC approprié, vous devez parcourir la liste des encodeurs disponibles pour chaque connecteur. Chaque encodeur contient une liste de CRTC avec lesquels il peut fonctionner et vous sélectionnez simplement l'un de ces CRTC. Si vous programmez plus tard le CRTC pour contrôler un connecteur, il sélectionne automatiquement le meilleur encodeur. Cependant, cette procédure est nécessaire pour que votre CRTC ait au moins un encodeur fonctionnel pour le connecteur sélectionné. Voir la section Exemples ci-dessous pour plus d'informations.

Tous les modes valides pour un connecteur peuvent être récupérés avec un appel à drmModeGetConnector(3). Vous devez sélectionner le mode que vous souhaitez utiliser et l'enregistrer. Le premier mode de la liste est le mode par défaut avec la résolution la plus élevée possible et souvent un choix approprié.

Une fois que vous avez une combinaison connecteur+CRTC+mode fonctionnelle, vous devez créer un framebuffer qui sera utilisé pour le balayage. L'allocation du tampon mémoire dépend du pilote et est décrite dans drm-memory(7). Vous devez créer un tampon suffisamment grand pour votre mode sélectionné. Vous pouvez maintenant créer un objet framebuffer qui utilise votre tampon mémoire comme tampon de balayage. Vous pouvez le faire avec drmModeAddFB(3) et drmModeAddFB2(3).

Comme dernière étape, vous voudrez programmer votre CRTC pour piloter votre connecteur sélectionné. Vous pouvez le faire avec un appel à drmModeSetCrtc(3).

Retournement de page

Un appel à drmModeSetCrtc(3) est exécuté immédiatement et force le CRTC à utiliser le nouveau tampon de balayage. Si vous souhaitez des transitions fluides sans déchirures, vous utilisez probablement la double mise en mémoire tampon. Vous devez créer un objet framebuffer pour chaque tampon que vous utilisez. Vous pouvez ensuite appeler drmModeSetCrtc(3) sur le tampon suivant pour effectuer le retournement. Si vous souhaitez synchroniser vos retournements avec les synchronisations verticales (vblanks), vous pouvez utiliser drmModePageFlip(3) qui planifie votre retournement de page pour le prochain vblank.

Plans

Les plans sont contrôlés indépendamment des CRTCs. C'est-à-dire qu'un appel à drmModeSetCrtc(3) n'affecte pas les plans. Au lieu de cela, vous devez appeler drmModeSetPlane(3) pour configurer un plan. Cela nécessite l'ID du plan, un CRTC, un framebuffer et les décalages dans le framebuffer du plan et le framebuffer du CRTC. Le CRTC mélange ensuite le contenu du plan sur le tampon du framebuffer du CRTC pendant le balayage. Comme cela n'implique aucun mélange logiciel, c'est beaucoup plus rapide que le mélange traditionnel. Cependant, les ressources des plans sont limitées. Voir drmModeGetPlaneResources(3) pour plus d'informations.

Curseurs

Similaire aux plans, de nombreux matériels supportent également les curseurs. Un curseur est un très petit tampon avec une image qui est mélangée par-dessus le framebuffer du CRTC. Vous pouvez définir un curseur différent pour chaque CRTC avec drmModeSetCursor(3) et le déplacer à l'écran avec drmModeMoveCursor(3). Cela permet de déplacer le curseur à l'écran sans le ré-rendre. Si aucun curseur matériel n'est supporté, vous devez le ré-rendre pour chaque image où le curseur est déplacé.

Sélection CRTC/Encodeur

Si vous avez récupéré toutes les informations de configuration d'affichage via drmModeGetResources(3) en tant que drmModeRes *res, sélectionné un connecteur dans la liste de res->connectors et récupéré les informations du connecteur en tant que drmModeConnector *conn via drmModeGetConnector(3), cet exemple montre comment trouver un identifiant CRTC approprié pour piloter ce connecteur. Cette fonction prend un descripteur de fichier pour le périphérique DRM (voir drmOpen(3)) en tant que fd, un pointeur vers les ressources récupérées en tant que res et un pointeur vers le connecteur sélectionné en tant que conn. Elle renvoie un entier inférieur à 0 en cas d'échec, sinon, un identifiant CRTC valide est renvoyé.

static int modeset_find_crtc(int fd, drmModeRes *res, drmModeConnector *conn)
{
    drmModeEncoder *enc;
    unsigned int i, j;
    /* itérer sur tous les encodeurs de ce connecteur */
    for (i = 0; i < conn->count_encoders; ++i) {
        enc = drmModeGetEncoder(fd, conn->encoders[i]);
        if (!enc) {
            /* impossible de récupérer l'encodeur, on ignore... */
            continue;
        }
        /* itérer sur tous les CRTC globaux */
        for (j = 0; j < res->count_crtcs; ++j) {
            /* vérifier si ce CRTC fonctionne avec l'encodeur */
            if (!(enc->possible_crtcs & (1 << j)))
                continue;
            /* Ici, vous devez vérifier qu'aucun autre connecteur
             * n'utilise actuellement le CRTC avec l'identifiant "crtc". Si vous avez l'intention
             * de piloter un seul connecteur, alors vous pouvez sauter cette
             * étape. Sinon, analysez simplement votre liste de connecteurs et CRTC configurés
             * pour voir si ce CRTC est déjà utilisé. S'il l'est, continuez simplement la recherche ici. */
            if (res->crtcs[j] "n'est pas utilisé") {
                drmModeFreeEncoder(enc);
                return res->crtcs[j];
            }
        }
        drmModeFreeEncoder(enc);
    }
    /* impossible de trouver un CRTC approprié */
    return -ENOENT;
}
