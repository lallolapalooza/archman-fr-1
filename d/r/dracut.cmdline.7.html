Le périphérique racine utilisé par le noyau est spécifié dans le fichier de configuration de démarrage sur la ligne de commande du noyau, comme

toujours.

La spécification de périphérique traditionnelle root=/dev/sda1 est autorisée, mais non recommandée. Le périphérique racine devrait plutôt être identifié par LABEL ou UUID. Si une étiquette est utilisée, comme dans root=LABEL=<label_of_root> l'initramfs recherchera tous les périphériques disponibles pour un système de fichiers avec l'étiquette appropriée, et montera ce périphérique comme système de fichiers racine. root=UUID=<uuidnumber> montera la partition avec cet UUID comme système de fichiers

racine.

Dans ce qui suit, tous les paramètres de la ligne de commande du noyau, qui sont traités par dracut, sont

décrits.

Les paramètres "rd.*" mentionnés sans "=" sont des paramètres booléens. Ils peuvent être activés/désactivés en les définissant à {0|1}. Si l'affectation avec "=" est manquante, "=1" est implicite. Par exemple rd.info peut être désactivé avec rd.info=0 ou activé avec rd.info=1 ou rd.info. La dernière valeur dans la ligne de commande du noyau est la valeur qui est

respectée.

crypto LUKS - key on removable device

support

NB: If systemd is included in the dracut initrd, dracut’s built in removable device keying support won’t work. systemd will prompt for a password from the console even if you’ve supplied rd.luks.key. You may be able to use standard systemd man:fstab[5,external] syntax to get the same effect. If you do need rd.luks.key to work, you will have to exclude the "systemd" dracut module and any modules that depend on it. See man:dracut.conf[5] and https://bugzilla.redhat.com/show_bug.cgi?id=905683 for more

information.

rd.luks.key=<keypath>[:<keydev>[:<luksdev>]

]
<keypath> is the pathname of a key file, relative to the root of the filesystem on some device. It’s REQUIRED. When <keypath> ends with .gpg it’s considered to be key encrypted symmetrically with GPG. You will be prompted for the GPG password on boot. GPG support requires the crypt-gpg dracut module, which needs to be added explicitly.

<keydev> identifies the device on which the key file resides. It may be the kernel name of the device (should start with "/dev/"), a UUID (prefixed with "UUID=") or a label (prefix with "LABEL="). You don’t have to specify a full UUID. Just its beginning will suffice, even if its ambiguous. All matching devices will be probed. This parameter is recommended, but not required. If it’s not present, all block devices will be probed, which may significantly increase boot

time.

If <luksdev> is given, the specified key will only be used for the specified LUKS device. Possible values are the same as for <keydev>. Unless you have several LUKS devices, you don’t have to specify this parameter. The simplest usage

is:

Exampl

e 
rd.luks.
key=/foo
/bar.key

As you see, you

can skip colons
in such a case.

Note

Your LUKS partition must match your key

file.

dracut provides keys to cryptsetup with -d (an older alias for --key-file). This uses the entire binary content of the key file as part of the secret. If you pipe a password into cryptsetup without -d or --key-file, it will be treated as text user input, and only characters before the first newline will be used. Therefore, when you’re creating an encrypted partition for dracut to mount, and you pipe a key into cryptsetup luksFormat,you must use -d

-.

Here is an example for a key encrypted with GPG (warning: --batch-mode will overwrite the device without asking for confirmation)

: 
gpg --quiet --decrypt rootkey.gpg |
\ cryptsetup --batch-mode --key-file
- \ luksFormat /dev/sda47

If you use unencrypted key files, just use the key file pathname instead of the standard input. For a random key with 256 bits of entropy, you might

use: 
head -32c /dev/urandom > rootkey.key
cr
yptsetup --batch-mode --key-file rootkey
.key \ luksFormat /dev/sda47

You can also use regular key files on an encrypted keydev

.

Compared to using GPG encrypted keyfiles on an unencrypted device this provides the following

advantages:
•you can unlock your disk(s) using multiple
passphrases
•better security by not losing the key stretching
mechanism

To use an encrypted keydev you must ensure that it becomes available by using the keyword keysource, e.g. rd.luks.uuid=keysource:aaaa aaaa being the uuid of the encrypted keydev

.

Example

You want to unlock A and B using keyfile keyfile.
The unlocked volumes be A', B' and C' with the uuids AAAA, BBBB and CCCC.
keyfile is saved on C' as /keyfile

One luks keyslot of each A, B and C is setup with a passphrase.
Another luks keyslot of each A and B is setup with keyfichier

(lecture seule) Remarque —

Il

existe 3 types de superposition distincts disponibles : •Instantanés device-mapper (l'offre d'origine)

,

•Instantanés de provisionnement fin device-mapper

(voir
rd.live.overlay.thin , une offre ultérieure), et •Montages
de superposition basés sur OverlayFS (une offre plus
récente)
. En utilisant l'une de ces technologies, le système fournira unesuperposition inscriptible pour
le
système de fichiers racine SquashFS de base en lecture seule.
Ces

méthodes permettent un démarrage relativement rapide et une utilisation moindre de la RAM. Avec la superposition d'instantané device-mapper d'origine, les utilisateurs doivent faire attention à ne pas écrire

trop

de blocs dans le périphérique d'instantané. Une fois que les blocs de la superposition d'instantané sont épuisés, tout le système de fichiers racine devient en lecture seule, entraînant des échecs d'application. Le périphérique de superposition d'instantané est marqué Overflow (débordement), et une récupération difficile est nécessaire pour réparer et agrandir la superposition hors ligne. Quand rd.live.overlay= n'est pas spécifié pour

un

stockage de superposition persistant, ou le fichier spécifié est introuvable ou non inscriptible, un instantané device-mapper basé non persistant ou temporaire est automatiquement créé en tant que fichier creux dans la RAM de l'initramfs. Ce fichier ne consommera de l'espace de contenu qu'à mesure que les blocs nécessaires sont alloués. Cette superposition basée sur un instantané a par défaut une taille apparente de 32 Gio en RAM, et peut être ajustée avec l'option de ligne de commande du noyau rd.live.overlay.size= . Ce fichier est caché (et apparaît comme supprimé) lorsque le processus de démarrage quitte l'initramfs pour le système de fichiers racine principal, mais sa boucle de périphérique reste connectée à l'instantané device-mapper. Même avec de grands

fichiers

de superposition device-mapper pour l'espace d'écriture, la capacité disponible du système de fichiers racine est limitéey la taille totale allouée du système de fichiers racine de base, qui fournit souvent seulement quelques Gigaoctets d'espace libre.

Cette pénurie pourrait être résolue en construisant le système de fichiers racine avec plus d'espace libre alloué, ou la méthode de montage superposé basée sur OverlayFS peut être utilisée.

Lorsque l'option rd.live.overlay.overlayfs est spécifiée ou lorsque rd.live.overlay= pointe vers un répertoire approprié avec une sœur à /../ovlwork, alors un montage superposé basé sur OverlayFS est utilisé. Un tel superposition OverlayFS persistante peut étendre le stockage du système de fichiers racine disponible jusqu'à la capacité du périphérique disque LiveOS.

Pour les superpositions OverlayFS non persistantes, le répertoire /run/overlayfs dans le tmpfs /run est utilisé pour le stockage temporaire. Ce système de fichiers est généralement dimensionné à la moitié de la RAM totale du système.
La commande : mount -o remount,size=<nbytes> /run redimensionnera ce système de fichiers virtuel après le démarrage.

La structure interne de SquashFS est traditionnellement attendue pour être :

squashfs.img          |  SquashFS de l'ISO LiveCD
   !(montage)
   /LiveOS
       |- rootfs.img  |  Généralement une image de système de fichiers ext4 à monter en lecture seule
            !(montage)
            /bin      |  Système de fichiers racine de base Live
            /boot     |
            /dev      |
            ...       |

Pour les superpositions de montage OverlayFS, la structure interne de SquashFS peut être une compression directe du système de fichiers racine :

squashfs.img          |  SquashFS de l'ISO LiveCD
   !(montage)
   /bin               |  Système de fichiers racine de base Live
   /boot              |
   /dev               |
   ...                |

Dracut utilise par défaut l'une des méthodes de superposition de démarrage en direct. Aucune option de ligne de commande supplémentaire n'est requise autre que root=live:<chemin vers le périphérique bloc> ou root=live:<URL> pour spécifier l'emplacement de votre système de fichiers racine compressé.

•L'image SquashFS compressée peut être copiée pendant le démarrage vers la RAM à l'emplacement /run/initramfs/squashed.img en utilisant l'option rd.live.ram=1.
•Un périphérique avec une superposition persistante peut être démarré en lecture seule en utilisant l'option rd.live.overlay.readonly sur la ligne de commande du noyau. Cela provoquera l'empilement d'une superposition temporaire et inscriptible sur un instantané en lecture seule du système de fichiers racine, ou le montage OverlayFS utilisera une couche inférieure supplémentaire avec le système de fichiers racine.

Image de système de fichiers live non compressée

Lorsque le système live a été installé avec l'option --skipcompress du script d'installation livecd-iso-to-disk pour les périphériques Live USB, l'image du système de fichiers racine, rootfs.img, est développée lors de l'installation et aucun SquashFS n'est impliqué pendant le démarrage.
•Si rd.live.ram=1 est utilisé dans cette situation, le système de fichiers racine complet et non compressé est copié pendant le démarrage vers /run/initramfs/rootfs.img dans le tmpfs /run.
•Si rd.live.overlay=none est fourni comme option de ligne de commande du noyau, une cible Device-mapper linéaire et inscriptible est créée au démarrage sans superposition.

Image de système de fichiers inscriptible

Le système récupérera une image de système de fichiers compressée, l'extraira dans /run/initramfs/fsimg/rootfs.img, la connectera à un périphérique de boucle, créera une cible Device-mapper linéaire et inscriptible à l'adresse /dev/mapper/live-rw, et montera ce dernier comme un volume inscriptible à l'adresse /. Plus de RAM est nécessaire pendant le démarrage, mais le système de fichiers live est plus facile à gérer s'il est plein. Les utilisateurs peuvent créer une image de système de fichiers de n'importe quelle taille, et cette taille sera maintenue au démarrage du système. Il n'y a pas de persistance des modifications du système de fichiers racine entre les démarrages avec cette option.

La structure du système de fichiers est attendue pour être :

rootfs.tgz            |  Tarball compressé contenant l'image du système de fichiers
   !(décompression)
   /rootfs.img        |  Image du système de fichiers dans /run/initramfs/fsimg/
      !(montage)
      /bin            |  Système de fichiers Live
      /boot           |
      /dev            |
      ...             |

Pour utiliser cette option de démarrage, assurez-vous que rd.writable.fsimg=1 se trouve sur votre ligne de commande du noyau et ajoutez root=live:<URL> pour spécifier l'emplacement de votre tarball d'image de système de fichiers compressé ou de votre image SquashFS.

rd.writable.fsimg=1

Active la prise en charge des systèmes de fichiers inscriptibles. Le système démarrera avec un système de fichiers entièrement inscriptible (mais non persistant) sans instantanés (voir les notes ci-dessus concernant les options de démarrage live disponibles). Vous pouvez utiliser l'option rootflags pour définir également les options de montage pour le système de fichiers live (voir la documentation sur rootflags dans la section section Standard ci-dessus). Cela implique que toute l'image est copiée en RAM avant que le démarrage ne se poursuive.

Note

Il doit y avoir suffisamment de RAM libre disponible pour contenir l'image complète.

Cette méthode est très adaptée aux démarrages sans disque.

rd.minmem=<mégaoctets>

Spécifie la RAM libre minimale en Mo après la copie d'une image disque live en mémoire. La valeur par défaut est 1024.

Ce paramètre s'applique uniquement conjointement avec les paramètres rd.writable.fsimg ou rd.live.ram.

root=live:<url>

Démarre une image live récupérée depuis <url>. Nécessite le module livenet de dracut. Gestionnaires valides : http, https, ftp, torrent, tftp.

Exemples

root=live:http://example.com/liveboot.img
root=live:ftp://ftp.example.com/liveboot.img
root=live:torrent://example.com/liveboot.img.torrent

rd.live.debug=1

Active la sortie de débogage du processus de démarrage live.

rd.live.dir=<chemin>

Spécifie le répertoire dans le périphérique de démarrage où se trouve squashfs.img ou rootfs.img. Par défaut, il s'agit de /LiveOS.

rd.live.squashimg=<nom_fichier_image_SquashFS>

Spécifie le nom du fichier pour une image SquashFS du système de fichiers racine. Par défaut, il s'agit de squashfs.img.

rd.live.ram=1

Copie l'image complète en RAM et l'utilise pour le démarrage. Ceci est utile lorsque l'image réside sur, par exemple, un DVD qui doit être éjecté plus tard.

rd.live.overlay={<devspec>[:{<pathspec>|auto}]|none}

Gère l'utilisation d'une superposition persistante.
•<devspec> spécifie le chemin vers un périphérique avec un système de fichiers montable.
•<pathspec> est un chemin dans le système de fichiers <devspec> vers
•un fichier (qui est monté en boucle pour une superposition Device-mapper) ou
•un répertoire (qui est symboliquement lié à /run/overlayfs pour une superposition de montage OverlayFS). (Un répertoire sœur requis /<pathspec>/../ovlwork est automatiquement créé.)
•none (le mot lui-même) spécifie qu'aucune superposition ne sera utilisée, par exemple lorsqu'un système de fichiers racine live non compressé et inscriptible est disponible.

La méthode ci-dessus doit être utilisée pour persister les modifications apportées au système de fichiers racine spécifié dans le
périphérique root=live:<chemin vers le périphérique bloc> ou root=live:<url>.

Le pathspec par défaut, lorsque :auto ou aucun :<pathspec> n'est donné, est /<rd.live.dir>/overlay-<label>-<uuid>, où <label> et <uuid> sont le LABEL et l'UUID du système de fichiers spécifié par le périphérique root=live:<path|url>.

Si une superposition persistante est détectée au chemin standard de LiveOS, et que rd.live.overlay.overlayfs n'est pas défini sur 1, le type de superposition (Device-mapper ou OverlayFS) sera détecté et utilisé.

Exemples

rd.live.overlay=/dev/sdb1:/persistent-overlay.img
rd.live.overlay=UUID=99440c1f-8daa-41bf-b965-b7240a8996f4

rd.live.overlay.cowfs=[btrfs|ext4|xfs]

Spécifie le système de fichiers à utiliser lors du formatage de la partition de superposition. Le système de fichiers par défaut est ext4.

rd.live.overlay.size=<taille_MiB>

Spécifie une taille de superposition Device-mapper non persistante en MiB. La valeur par défaut est 32768.

rd.live.overlay.readonly=1

Ceci est utilisé pour démarrer en mode lecture seule avec une superposition persistante normalement inscriptible. Avec cette option,
•les superpositions Device-mapper auront une superposition d'instantané supplémentaire, non persistante et inscriptible, empilée sur un instantané en lecture seule (/dev/mapper/live‑ro) du système de fichiers racine de base et de la superposition persistante, ou
•pour les images rootfs.img inscriptibles, ce qui précède par-dessus un périphérique de boucle en lecture seule, ou
•un montage OverlayFS liera le répertoire de superposition persistant à l'adresse /run/overlayfs‑r comme couche inférieure supplémentaire en lecture seule empilée sur le système de fichiers racine de base, et /run/overlayfs deviendra le répertoire supérieur temporaire et inscriptible de la superposition, pour compléter le système de fichiers racine amorçable.

rd.live.overlay.nouserconfirmprompt=

Supprime l'invite bloquante Utilisation d'une superposition temporaire qui demande une confirmation utilisateur avant de continuer le démarrage. Cela permet au processus de démarrage de se poursuivre jusqu'à la fin sans interaction utilisateur.

rd.live.overlay.reset=1

Spécifie qu'une superposition persistante doit être réinitialisée au démarrage. Toutes les modifications précédentes du système de fichiers racine sont annulées par cette action.

rd.live.overlay.thin=1

Active l'utilisation d'instantanés fins au lieu d'instantanés dm classiques. L'avantage des instantanés fins est qu'ils prennent en charge les rejets (discards), et libéreront les blocs qui ne sont pas revendiqués par le système de fichiers. Dans ce cas d'utilisation, cela signifie que la mémoire est rendue au noyau lorsque le système de fichiers ne la revendique plus.

rd.live.overlay.overlayfs=1

Active l'utilisation du module noyau OverlayFS, si disponible, pour fournir une union en copie sur écriture (copy-on-write) répertoire pour le système de fichiers racine. Les superpositions OverlayFS sont des répertoires contenant les fichiers modifiés sur le système de fichiers de base (inférieur) en lecture seule. Le système de fichiers racine est fourni par un montage de type overlay spécial qui fusionne au moins deux répertoires, désignés comme inférieur et supérieur. Si un répertoire supérieur OverlayFS n'est pas présent sur le périphérique de démarrage, un répertoire tmpfs sera créé dans /run/overlayfs pour fournir un stockage temporaire. Un stockage persistant peut être fourni sur des périphériques formatés vfat ou msdos en fournissant le répertoire supérieur OverlayFS dans un système de fichiers embarqué qui prend en charge la création d'attributs étendus trusted.* et fournit un d_type valide dans les réponses de readdir, comme avec btrfs, ext4, f2fs et xfs. Sur les périphériques non formatés vfat, une superposition OverlayFS persistante peut étendre le stockage du système de fichiers racine disponible jusqu'à la capacité du périphérique de disque LiveOS. Nécessite le module dracut overlayfs.

L'option rd.live.overlay.readonly, qui permet à une superposition overlayfs persistante d'être montée en lecture seule à travers un répertoire de superposition transitoire de niveau supérieur, a été implémentée grâce à la fonctionnalité de couches inférieures multiples d'OverlayFS.
