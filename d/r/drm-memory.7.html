Presque tous les pilotes matériels DRM du noyau prennent en charge une API appelée Dumb-Buffers. Cette API permet de créer des tampons de taille arbitraire qui peuvent être utilisés pour le scanout. Ces tampons peuvent être mappés en mémoire via mmap(2) afin que vous puissiez y effectuer du rendu sur le CPU. Cependant, l'accès GPU à ces tampons est souvent impossible. Par conséquent, ils conviennent à des tâches simples mais ne sont pas adaptés

aux

compositions et rendus complexes. L' ioctl DRM_IOCTL_MODE_CREATE_DUMB peut être utilisé pour créer un tampon bête. Le noyau renverra un handle 32 bits qui peut être utilisé pour gérer le tampon avec l'API DRM. Vous pouvez créer des tampons de trame avec drmModeAddFB(3) et l'utiliser pour le réglage de mode et le scanout. Pour accéder au tampon, vous devez d'abord récupérer l'offset du tampon. GEM est conçu pour gérer la mémoire graphique, contrôler l'accès au contexte d'exécution du périphérique graphique et gérer essentiellement l'environnement NUMA unique au matériel graphique moderne. GEM permet à plusieurs applications de partager les ressources du périphérique graphique sans avoir à recharger constamment toute la carte graphique. Les données peuvent être partagées entre plusieurs applications, GEM veillant à ce que la synchronisation mémoire appropriée se produise. GEM fournit des mécanismes simples pour gérer les

données

graphiques et contrôler le flux d'exécution au sein du sous-système DRM de Linux. Cependant, GEM n'est pas un framework entièrement indépendant du pilote. Au lieu de cela, il fournit de nombreuses fonctions partagées entre de nombreux pilotes, mais chaque pilote doit implémenter la plupart de la gestion de la mémoire avec des ioctls dépendant du pilote. Cette page manuel essaie de décrire la sémantique (et, le cas échéant, la syntaxe) partagée entre tous les pilotes qui utilisent GEM. Toutes les API GEM sont définies comme des

ioctl(2)

sur le descripteur de fichier DRM. Une application doit être autorisée via drmAuthMagic(3) par le DRM-Master actuel pour accéder au sous-système GEM. Un pilote qui ne prend pas en charge GEM renverra ENODEV pour toutes ces ioctls. Les handles d'objets invalides renvoient EINVAL et les noms d'objets invalides renvoient ENOENT. GEM fournit des primitives de gestion d

e

mémoire explicites. Des pages système sont allouées lorsque l'objet est créé, soit comme stockage fondamental pour le matériel où la mémoire système est utilisée directement par le processeur graphique, soit comme magasin de sauvegarde pour la mémoire résidente du processeur graphique. Les objets sont

référencés

depuis l'espace utilisateur à l'aide de handles. Ceux-ci sont, à toutes fins pratiques, équivalents aux descripteurs de fichier mais évitent la surcharge. Les pilotes de noyau plus récents prennent également en charge l'infrastructure drm-prime (7) qui peut renvoyer de véritables descripteurs de fichier pour les handles GEM en utilisant l'API DMA-BUF de Linux. Les objets peuvent être publiés avec un nom afin que d'autres applications et processus puissent y accéder. Le nom reste valide tant que l'objet existe. Les objets GEM sont comptés par références dans le noyau. L'objet n'est détruit que lorsque tous les handles de l'espace

utilisateur

ont été fermés. Les tampons GEM ne peuvent pas être créés avec une API générique. Chaque pilote fournit sa propre API pour créer des tampons GEM. Voir par exemple DRM_I915_GEM_CREATE, DRM_NOUVEAU_GEM_NEW ou DRM_RADEON_GEM_CREATE. Chacune de ces ioctls renvoie un handle GEM qui peut être passé à différentes ioctls génériques. La bibliothèque libgbm de la distribution mesa3D essaie de fournir une API indépendante du pilote pour créer des tampons GBM et récupérer un handle GBM pour ceux-ci. Elle permet de créer des tampons pour différents cas d'utilisation, y compris le scanout, le rendu, les curseurs et l'accès CPU. Voir la bibliothèque libgbm pour plus d'informations ou consulter les pages manuelles dépendant du pilote (par exemple drm-i

ntel(7)

ou drm-radeon(7)). Les tampons GEM peuvent être fermés avec drmCloseBufferHandle(3). Elle prend comme argument le handle GEM à fermer. Après cet appel, le handle GEM ne peut plus être utilisé par ce processus et peut être réutilisé pour de nouveaux

objets

GEM par l'API GEM. Si vous souhaitez partager des objets GEM entre différents processus, vous pouvez créer un nom pour ceux-ci et passer ce nom à d'autres processus qui peuvent alors ouvrir cet objet GEM. Les noms sont actuellement des ID entiers de 32 bits et n'ont pas de protection particulière. C'est-à-dire que si vous mettez un nom sur votre objet GEM, tout autre client ayant accès au périphérique DRM et authentifié via drmAuthMagic(3) par le DRM-Master actuel, peut nom et ouvrir ou accéder à l'objet GEM. Si vous souhaitez un contrôle d'accès plus fin, vous pouvez utiliser la nouvelle API drm-prime(7) pour récupérer des descripteurs de fichiers pour les handles GEM. Pour créer un nom pour un handle GEM, vous utilisez l' ioctl DRM_IOCTL_GEM_FLINK. Elle prend comme argument une structure de type struct drm_gem_

flink :

Vous pouvez maintenant passer ce nom à d'autres processus qui peuvent alors importer le nom avec l' ioctl DRM_IOCTL_GEM_OPEN. Elle prend comme argument une structure de type struct drm_gem

struct drm_gem_open {
    __u32 name;

Vous devez remplir le champ name avec le nom de l' objet GEM que vous souhaitez ouvrir. Le noyau remplira les champs handle et size avec le nouveau handle et la nouvelle taille de l'objet GEM. Vous pouvez maintenant accéder à l'objet GEM via le handle comme si vous l'aviez créé avec l' API

GEM.

En dehors de la gestion générique des tampons, l'API GEM ne fournit aucun accès générique. Chaque pilote implémente sa propre fonctionnalité au-dessus de cette API. Cela inclut les tampons d'exécution, la gestion GTT, la création de contextes, l'accès CPU, les E/S GPU et plus encore. L'API de niveau supérieur suivante est OpenGL. Donc si vous souhaitez utiliser plus de fonctionnalités GPU, vous devriez utiliser la bibliothèque mesa3D pour créer des contextes OpenGL sur les périphériques DRM. Cela ne nécessite aucun système de fenêtrage comme X11, mais peut également être fait sur des périphériques DRM bruts. Cependant, cela dépasse le cadre de cette page de manuel. Vous pouvez jeter un œil à d'autres pages de manuel mesa3D, y compris libgbm et libEGL. Le rendu logiciel 2D (rendu avec le CPU) peut être réalisé avec l'API dumb-buffer de manière indépendante du pilote, cependant, pour un rendu 2D ou 3D accéléré par le matériel, vous devez utiliser OpenGL. Toute autre API qui tente d'abstraire les détails internes du pilote pour accéder aux tampons d'exécution GEM et aux autres détails internes du GPU réinventerait simplement OpenGL, elle n'est donc pas fournie. Mais si vous avez besoin d'informations plus détaillées pour un pilote spécifique, vous pouvez jeter un œil aux pages de manuel des pilotes, y compris drm-intel(7), drm-radeon(7) et drm-nouveau(7). Cependant, l' infrastructure drm-prime(7) et l'API GEM générique décrite ici permettent aux gestionnaires d'affichage de gérer les tampons graphiques et les clients de rendu sans aucun

e connaissance approfondie du GPU utilisé. De plus, cela permet de déplacer d
es objets entre GPU et d'implémenter des serveurs d'affichage complexes qui ne fon
t aucun rendu par eux-mêmes. Voir sa page de manuel pour plus d'informations.

Tampons stupides

(Dumb-Buffers)

Cet exemple montre comment créer un dumb-buffer via l'API DRM générique. C'est indépendant du pilote (tant que le pilote prend en charge les dumb-buffers) et fournit des tampons mappés en mémoire qui peuvent être utilisés pour l'affichage (scanout). Cet exemple crée un tampon Full HD 1920x1080 avec 32 bits par pixel et une profondeur de couleur de 24 bits. Le tampon est ensuite lié à un framebuffer qui peut être utilisé pour l'affichage avec l'API KMS (voir drm-kms(7))
