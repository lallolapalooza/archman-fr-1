NOM

dpkg-gensymbols - génère des fichiers de symboles (informations de dépendance de bibliothèques partagées)

SYNTAXE

dpkg-gensymbols [option...]

DESCRIPTION

dpkg-gensymbols analyse un arbre de construction temporaire (debian/tmp par défaut) à la recherche de bibliothèques et génère un fichier de symboles les décrivant. Ce fichier, s'il n'est pas vide, est ensuite installé dans le sous-répertoire DEBIAN de l'arbre de construction afin qu'il soit inclus dans les informations de contrôle du paquet.

Lors de la génération de ces fichiers, il utilise comme entrée des fichiers de symboles fournis par le mainteneur. Il recherche les fichiers suivants (et utilise le premier trouvé) :

  • debian/package.symbols.arch
  • debian/symbols.arch
  • debian/package.symbols
  • debian/symbols

L'intérêt principal de ces fichiers est de fournir la version minimale associée à chaque symbole fourni par les bibliothèques. Habituellement, cela correspond à la première version de ce paquet qui fournissait le symbole, mais cela peut être augmenté manuellement par le mainteneur si l'ABI du symbole est étendue sans rompre la compatibilité ascendante. Il incombe au mainteneur de garder ces fichiers à jour et précis, mais dpkg-gensymbols y aide.

Lorsque les fichiers de symboles générés diffèrent de ceux fournis par le mainteneur, dpkg-gensymbols affichera une différence entre les deux versions. De plus, si la différence est trop significative, il échouera (vous pouvez personnaliser l'ampleur de la différence acceptable, voir l'option -c).

Ce programme a été introduit dans dpkg 1.14.8.

MAINTENANCE DES FICHIERS DE SYMBOLES

Le format d'échange de base du fichier de symboles est décrit dans deb-symbols(5), qui est utilisé par les fichiers de symboles inclus dans les paquets binaires. Ceux-ci sont générés à partir de fichiers de symboles modèles avec un format basé sur le précédent, décrit dans deb-src-symbols(5) et inclus dans les paquets sources.

Les fichiers de symboles ne sont vraiment utiles que s'ils reflètent l'évolution du paquet à travers plusieurs versions. Ainsi, le mainteneur doit les mettre à jour chaque fois qu'un nouveau symbole est ajouté afin que sa version minimale associée corresponde à la réalité.

Les différences contenues dans les journaux de construction peuvent servir de point de départ, mais le mainteneur doit, en outre, s'assurer que le comportement de ces symboles n'a pas changé d'une manière qui empêcherait quoi que ce soit utilisant ces symboles et lié à la nouvelle version, de fonctionner avec l'ancienne version.

Dans la plupart des cas, la différence s'applique directement au fichier debian/package.symbols. Cela dit, des ajustements supplémentaires sont généralement nécessaires : il est recommandé, par exemple, de supprimer la révision Debian de la version minimale afin que les backports avec un numéro de version inférieur mais la même version upstream satisfont toujours les dépendances générées. Si la révision Debian ne peut pas être supprimée car le symbole a réellement été ajouté par un changement spécifique à Debian, alors il convient de suffixer la version avec ‘~’.

Avant d'appliquer une modification au fichier de symboles, le mainteneur doit vérifier attentivement qu'elle est saine. Les symboles publics ne sont pas censés disparaître, le patch ne devrait donc idéalement qu'ajouter de nouvelles lignes.

Notez que vous pouvez insérer des commentaires dans les fichiers de symboles.

N'oubliez pas de vérifier si les anciennes versions de symboles doivent être augmentées. Il n'y a aucun moyen pour dpkg-gensymbols de vous prévenir à ce sujet. Appliquer aveuglément le diff ou supposer qu'il n'y a rien à changer s'il n'y a pas de diff, sans vérifier de tels changements, peut entraîner des paquets avec des dépendances lâches qui prétendent pouvoir fonctionner avec d'anciens paquets avec lesquels ils ne peuvent pas fonctionner. Cela introduira des bugs difficiles à trouver lors de mises à niveau (partielles).

Bonne gestion des bibliothèques

Une bibliothèque bien maintenue présente les caractéristiques suivantes :

  • son API est stable (les symboles publics ne sont jamais supprimés, seuls de nouveaux symboles publics sont ajoutés) et les changements incompatibles ne se produisent que lorsque le SONAME change ;
  • idéalement, elle utilise le versionnement des symboles pour obtenir une stabilité de l'ABI malgré les changements internes et les extensions d'API ;
  • elle n'exporte pas de symboles privés (de tels symboles peuvent être marqués comme optionnels comme solution de contournement).

Tout en maintenant le fichier de symboles, il est facile de remarquer l'apparition et la disparition de symboles. Mais il est plus difficile de détecter un changement incompatible de l'API et de l'ABI. Ainsi, le mainteneur doit lire attentivement le journal des modifications amont à la recherche de cas où les règles de bonne gestion des bibliothèques ont été enfreintes. Si des problèmes potentiels sont découverts, l'auteur amont devrait être informé car une correction amont est toujours préférable à une solution de contournement spécifique à Debian.

OPTIONS

-Prépertoire-construction-paquet
Analyser répertoire-construction-paquet au lieu de debian/tmp.
-ppaquet
Définir le nom du paquet. Requis si plus d'un paquet binaire est listé dans debian/control (ou s'il n'y a pas de fichier debian/control).
-vversion
Définir la version du paquet. Par défaut, prend la version extraite de debian/changelog. Requis si appelé en dehors d'un arbre de paquet source.
-efichier-bibliothèque
Analyser uniquement les bibliothèques explicitement listées au lieu de trouver toutes les bibliothèques publiques. Vous pouvez utiliser des motifs shell utilisés pour les expansions de chemin (voir la page de manuel de File::Glob pour plus de détails) dans fichier-bibliothèque pour faire correspondre plusieurs bibliothèques avec un seul argument (sinon vous avez besoin de plusieurs -e).
-lrépertoire
Ajouter répertoire au début de la liste des répertoires à rechercher pour les bibliothèques partagées privées (depuis dpkg 1.19.1). Cette option peut être utilisée plusieurs fois.

Note : Utilisez cette option au lieu de définir LD_LIBRARY_PATH, car cette variable d'environnement est utilisée pour contrôler le lieur d'exécution et son abus pour définir les chemins des bibliothèques partagées au moment de la construction peut être problématique lors de la compilation croisée, par exemple.

-Inom-de-fichier
Utiliser nom-de-fichier comme fichier de référence pour générer le fichier de symboles qui est intégré au paquet lui-même.
-O[nom-de-fichier]
Afficher le fichier de symboles généré sur la sortie standard ou dans nom-de-fichier s'il est spécifié, plutôt que dans debian/tmp/DEBIAN/symbols (ou répertoire-construction-paquet/DEBIAN/symbols si -P a été utilisé). Si nom-de-fichier existe déjà, son contenu est utilisé comme base pour le fichier de symboles généré. Vous pouvez utiliser cette fonctionnalité pour mettre à jour un fichier de symboles afin qu'il corresponde à une version amont plus récente de votre bibliothèque.
-t
Écrire le fichier de symboles en mode modèle plutôt qu'au format compatible avec deb-symbols(5). La principale différence est qu'en mode modèle, les noms et les balises de symboles sont écrits sous leur forme d'origine, contrairement aux noms de symboles post-traités avec les balises supprimées en mode compatible. De plus, certains symboles peuvent être omis lors de l'écriture d'un fichier deb-symbols(5) standard (selon les règles de traitement des balises) tandis que tous les symboles sont toujours écrits dans le modèle de fichier de symboles.
-c[0-4]
Définir les vérifications à effectuer lors de la comparaison du fichier de symboles généré avec le fichier modèle utilisé comme point de départ. Par défaut, le niveau est 1. Les niveaux croissants effectuent plus de vérifications et incluent toutes les vérifications des niveaux inférieurs.
Niveau 0
Ne jamais échouer.
Niveau 1
Échoue si des symboles ont disparu.
Niveau 2
Échoue si de nouveaux symboles ont été introduits.
Niveau 3
Échoue si des bibliothèques ont disparu.
Niveau 4
Échoue si des bibliothèques ont été introduites.

Cette valeur peut être remplacée par la variable d'environnement DPKG_GENSYMBOLS_CHECK_LEVEL.

-q
Se taire et ne jamais générer de diff entre le fichier de symboles généré et le fichier modèle utilisé comme point de départ, ni afficher d'avertissements sur les bibliothèques nouvelles/perdues ou les symboles nouveaux/perdus. Cette option désactive seulement la sortie informationnelle, mais pas les vérifications elles-mêmes (voir l'option -c).
-aarch
Supposer que arch est l'architecture hôte lors du traitement des fichiers de symboles. Utiliser cette option pour générer un fichier de symboles ou un diff pour n'importe quelle architecture à condition que ses binaires soient déjà disponibles.
-d
Activer le mode débogage. De nombreux messages sont affichés pour expliquer ce que fait dpkg-gensymbols.
-V
Activer le mode verbeux. Le fichier de symboles généré contient les symboles obsolètes en tant que commentaires. De plus, en mode modèle, les symboles de motif sont suivis de commentaires listant les symboles réels qui ont correspondu au modèle.
-?, --help
Afficher le message d'utilisation et quitter.
--version
Afficher la version et quitter.

ENVIRONNEMENT

DEB_HOST_ARCH
Définit l'architecture hôte si l'option --arch n'a pas été spécifiée.
DPKG_GENSYMBOLS_CHECK_LEVEL
Remplace le niveau de vérification de la commande, même si l'argument de ligne de commande -c a été donné (notez que cela va à l'encontre de la convention habituelle selon laquelle les arguments de ligne de commande ont la priorité sur les variables d'environnement).
DPKG_COLORS
Définit le mode couleur (depuis dpkg 1.18.5). Les valeurs actuellement acceptées sont : auto (par défaut), always et never.
DPKG_NLS
Si définie, elle sera utilisée pour décider si l'on active le support des langues natives, également connu sous le nom d'internationalisation (ou i18n) (depuis dpkg 1.19.0). Les valeurs acceptées sont : 0 et 1 (par défaut).
