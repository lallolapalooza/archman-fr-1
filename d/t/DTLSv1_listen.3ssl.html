DESCRIPTIO

N

SSL_stateless() écoute sans état les nouvelles connexions TLSv1.3 entrantes. DTLSv1_listen() écoute sans état les nouvelles connexions DTLS entrantes. Si un ClientHello est reçu qui ne contient pas de cookie, alors il répond par une demande de nouveau ClientHello contenant un cookie. Si un ClientHello est reçu avec un cookie qui est vérifié, alors la fonction retourne afin de permettre la complétion de la négociation (par exemple en utilisant SSL_acc

ept
()).

NOTE

S

Certains protocoles de transport (comme UDP) peuvent être vulnérables aux attaques par amplification. Contrairement à TCP, il n'y a pas de mise en place initiale de connexion dans UDP qui valide que le client peut réellement recevoir des messages sur son adresse source annoncée. Un attaquant pourrait forger son adresse IP source et ensuite envoyer des messages d'initiation de négociation au serveur. Le serveur enverrait alors sa réponse à l'adresse IP source forgée. Si les messages de réponse sont plus grands que le message original, alors l'attaque par amplification a

réussi.

Si DTLS est utilisé sur UDP (ou tout protocole basé sur des datagrammes qui ne valide pas l'adresse IP source), alors il est vulnérable à ce type d'attaque. TLSv1.3 est conçu pour fonctionner sur un protocole de transport basé sur un flux (comme TCP). Si TCP est utilisé, il n'est pas nécessaire d'utiliser SSL_stateless(). Cependant, certains protocoles de transport basés sur un flux (par exemple QUIC) peuvent ne pas valider l'adresse source. Dans ce cas, une application TLSv1.3 serait vulnérable à cette

attaque.

En guise de contre-mesure à ce problème, TLSv1.3 et DTLS incluent un mécanisme de cookie sans état. L'idée est que lorsqu'un client tente de se connecter à un serveur, il envoie un message ClientHello. Le serveur répond avec un HelloRetryRequest (dans TLSv1.3) ou un HelloVerifyRequest (dans DTLS) qui contient un cookie unique. Le client renvoie ensuite le ClientHello, mais cette fois-ci il inclut le cookie dans le message, prouvant ainsi que le client est capable de recevoir les messages envoyés à cette adresse. Tout cela peut être fait par le serveur sans allouer d'état, et donc sans consommer de ressources

coûteuses.

OpenSSL implémente cette capacité via les fonctions SSL_stateless() et DTLSv1_listen(). Le paramètre ssl doit être un objet SSL nouvellement alloué avec ses BIOs de lecture et d'écriture configurés, de la même manière que pour un appel à SSL_accept(). Typiquement, pour DTLS, le BIO de lecture sera dans un état « non connecté » et donc capable de recevoir des messages de n'importe quel

pair.

Lorsqu'un ClientHello est reçu contenant un cookie qui a été vérifié, alors ces fonctions retourneront avec le paramètre ssl mis à jour dans un état où la négociation peut être continuée par un appel à (par exemple) SSL_accept(). De plus, pour DTLSv1_listen(), le BIO_ADDR pointé par peer sera rempli avec les détails du pair qui a envoyé le ClientHello. Si le BIO sous-jacent est incapable d'obtenir le BIO_ADDR du pair (par exemple parce que le BIO ne le supporte pas), alors *peer sera effacé et la famille définie à AF_UNSPEC. Typiquement, le code utilisateur est censé « connecter » le socket sous-jacent au pair et continuer la négociation dans un état

connecté.

Avertissement : Il est essentiel que le code appelant connecte le socket sous-jacent au pair après avoir utilisé DTLSv1_listen(). Dans le cas typique où BIO_s_datagram(3) est utilisé, l'adresse du pair est mise à jour lors de la réception d'un datagramme sur un socket non connecté. Si le socket n'est pas connecté, il peut recevoir des datagrammes de n'importe quel hôte sur le réseau, ce qui fera que les datagrammes sortants transmis ultérieurement par DTLS seront transmis à cet hôte. En d'autres termes, ne pas appeler BIO_connect() ou une fonction similaire spécifique à l'OS sur un socket signifie que n'importe quel hôte sur le réseau peut faire rediriger le trafic DTLS sortant vers lui en envoyant un datagramme au socket en question. Cela ne rompt pas les protections cryptographiques de DTLS mais peut faciliter une attaque par déni de service ou permettre à un attaquant d'apprendre des informations non chiffrées dans la négociation DTLS. Cela est dû à la conception historique de BIO_s_datagram(3) ; voir BIO_s_datagram(3) pour plus de détails sur ce

problème.

Une fois qu'un socket a été connecté, BIO_ctrl_set_connected(3) devrait être utilisé pour informer le BIO que le socket doit être utilisé en mode

connecté.

Avant d'appeler DTLSv1_listen(), le code utilisateur doit s'assurer que les rappels de génération et de vérification de cookie ont été configurés en utilisant SSL_CTX_set_cookie_generate_cb(3) et SSL_CTX_set_cookie_verify_cb(3) respectivement. Pour SSL_stateless(), SSL_CTX_set_stateless_cookie_generate_cb(3) et SSL_CTX_set_stateless_cookie_verify_cb(3) doivent être utilisés à la

place.

Étant donné que DTLSv1_listen() opère entièrement sans état lors du traitement des ClientHellos entrants, il est incapable de traiter les messages fragmentés (puisque cela nécessiterait l'allocation d'état). Une implication de cela est que DTLSv1_listen() ne supporte que les ClientHellos qui tiennent dans un seul

datagramme.

Pour SSL_stateless(), si un message ClientHello entier ne peut pas être lu sans que le BIO de « lecture » ne devienne vide, alors l'appel à SSL_stateless() échouera. C'est à l'application de s'assurer que les données lues depuis le BIO de « lecture » lors d'un seul appel à SSL_stateless() proviennent toutes du même

pair.

SSL_stateless() échouera (avec une valeur de retour 0) si une version de TLS inférieure à TLSv1.3 est

utilisée.

À la fois SSL_stateless() et DTLSv1_listen() effaceront la file d'erreurs lorsqu'ils

démarrent.

SSL_stateless() ne peut pas être utilisé avec des objets SSL

QUIC et retourne une erreur s'i
l est appelé sur un tel objet.

VALEURS

RETOURNÉES

Pour SSL_stateless(), une valeur de retour de 1 indique le succès et l'objet ssl sera configuré prêt à continuer la négociation. Une valeur de retour de 0 ou -1 indique un échec. Si la valeur est 0, alors un HelloRetryRequest a été envoyé. Une valeur de -1 indique toute autre erreur. Le code utilisateur peut réessayer l'appel à SSL_statele

ss().

Pour DTLSv1_listen(), une valeur de retour >= 1 indique le succès. L'objet ssl sera configuré prêt à continuer la négociation. La valeur peer sera également

remplie.

Une valeur de retour de 0 indique une erreur non fatale. Cela pourrait (par exemple) être dû à une E/S non bloquante, ou à la réception d'un message invalide d'un pair. Des erreurs peuvent être placées sur la file d'erreurs OpenSSL avec des informations supplémentaires si approprié. Typiquement, le code utilisateur est censé réessayer l'appel à DTLSv1_listen() en cas d'erreur non

fatale.

Une valeur de retour < 0 indique une erreur fatale. Cela pourrait (par exemple) être dû à un échec d'allocation de mémoire suffisante pour

l'opération.

Pour DTLSv1_listen(), avant OpenSSL 1.1.0, les erreurs fatales et non fatales produisaient toutes deux des codes de retour <= 0 (dans les implémen

tations typiques, le code utilisateur traite toutes les erreurs comme n
on fatales), tandis que les codes de retour > 0 indiquaient le succès.
