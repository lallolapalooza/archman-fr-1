Généralement, l'arbre de travail contient à la fois des fichiers qui devraient être sous contrôle de version (comme le code source) et des fichiers que Darcs devrait ignorer (comme les exécutables compilés à partir du code source). La commande `darcs whatsnew` liste les changements non enregistrés dans l'arbre de travail. Si vous spécifiez un ensemble de fichiers et de répertoires, seuls les changements non enregistrés de ces fichiers et répertoires sont listés.

Avec l'option `--summary`, les changements sont condensés en une ligne par fichier, avec des mnémoniques pour indiquer la nature et l'étendue du changement. L'option `--look-for-adds` inclut les candidats pour `darcs add` dans la sortie résumée. Les mnémoniques de résumé sont les suivantes

:


* `A f` et `A d/` signifient respectivement un fichier ou un répertoire ajouté.
* `R f` et `R d/` signifient respectivement un fichier ou un répertoire supprimé.
* `M f -N +M rP` signifie un fichier modifié, avec `N` lignes supprimées, `M`
lignes ajoutées, et `P` remplacements lexicaux.
* `f -> g` signifie un fichier ou un répertoire déplacé.
* `a f` et `a d/` signifient respectivement un fichier ou un
répertoire nouveau, mais non ajouté, lors de l'utilisation de `--look-for-adds`.
* Un point d'exclamation (!) comme dans `R! foo.c`, signifie que le changement
entre en conflit avec un changement dans un patch antérieur. L'expression `duplicated`
signifie que le changement est identique à un changement dans un patch

antérieur.

L'option `--machine-readable` implique `--summary` tout en le rendant plus facile à analyser. Les fichiers modifiés ne sont affichés que comme `M f`, et les déplacements sont affichés sur deux lignes : `F f` et `T g` (comme dans 'From f To g' - de f à g)

Par défaut, `darcs whatsnew` utilise le format interne de Darcs pour les changements. Pour voir un peu de contexte (lignes inchangées) autour de chaque changement, utilisez l'option `--unified`. (Cette option n'a aucun effet en mode interactif.) darcs record [fichier|répertoire]..

La commande `darcs record` est utilisée pour créer un patch à partir de changements dans l'arbre de travail. Si vous spécifiez un ensemble de fichiers et de répertoires, les changements des autres fichiers seront ignorés.

Chaque patch a un nom, une description facultative, un auteur et une

date.

Darcs lancera un éditeur de texte (voir `darcs help environment`) après la sélection interactive, pour vous permettre de saisir le nom du patch (première ligne) et la description du patch (lignes suivantes)

.

Vous pouvez fournir le nom du patch à l'avance avec l'option `-m`, auquel cas aucun éditeur de texte n'est lancé, sauf si vous utilisez `--edit-long-comment`

.

La description du patch est un bloc facultatif de texte libre. Elle est utilisée pour fournir des informations supplémentaires qui ne tiennent pas dans le nom du patch. Par exemple, elle pourrait inclure une justification du POURQUOI le changement était

nécessaire.

Une différence technique entre le nom du patch et la description du patch est que la correspondance avec l'option `-p` n'est effectuée que sur les noms de

patch.

Enfin, l'option `--logfile` vous permet de fournir un fichier qui contient déjà le nom et la description du patch. C'est utile si un enregistrement précédent a échoué et a laissé un fichier `_darcs/patch_description.

txt`.

Chaque patch est attribué à son auteur, généralement par adresse e-mail (par exemple, `Fred Bloggs <fred@example.net>`). Darcs cherche cette chaîne d'auteur à plusieurs endroits : l'option `--author`, les fichiers `_darcs/prefs/author` (dans le dépôt) et `~/.darcs/author` (dans votre répertoire personnel), et les variables d'environnement `$DARCS_EMAIL` et `$EMAIL`. Si aucun de ceux-ci n'existe, Darcs vous demandera une chaîne d'auteur et l'écrira dans `~/.darcs/author`. Notez que si vous avez plus d'une adresse e-mail, vous pouvez les mettre toutes dans `~/.darcs/author`, un auteur par ligne. Darcs vous demandera toujours un auteur, mais cela vous permet de sélectionner dans la liste ou de saisir une

alternative.

Si vous souhaitez définir manuellement des dépendances explicites pour votre patch, vous pouvez utiliser l'option `--ask-deps`. Certaines dépendances peuvent être automatiquement déduites du contenu du patch et ne peuvent pas être supprimées. Un patch avec des dépendances spécifiques peut être

vide.

La date du patch est générée automatiquement. Elle ne peut être falsifiée qu'en utilisant l'option

`--pipe`.

Si vous exécutez record avec l'option `--pipe`, il vous sera demandé la date du patch, l'auteur et le commentaire long. Le commentaire long s'étendra jusqu'à la fin du fichier ou de l'entrée standard (stdin). darcs clone <dépôt> [<répertoi

re>]
Clone crée une copie d'un dépôt. Le second argument optionnel spécifie un répertoire de destination pour la nouvelle copie ; s'il est omis, il est déduit de l'emplacement de la source.

Par défaut, Darcs copiera chaque patch du dépôt original. Si vous vous attendez à ce que le dépôt original reste accessible, vous pouvez utiliser `--lazy` pour éviter de copier les patchs jusqu'à ce qu'ils soient nécessaires ('copie à la demande'). C'est particulièrement utile lors de la copie d'un dépôt distant avec un long historique auquel vous ne tenez

pas.

Lors d'un clonage local, Darcs utilise automatiquement les liens physiques (hard links) là où c'est possible. En plus d'économiser du temps et de l'espace, cela permet de déplacer ou de supprimer le dépôt original sans affecter la copie. Les liens physiques nécessitent que la copie soit sur le même système de fichiers que le dépôt original, et que le système de fichiers supporte les liens physiques. Cela inclut NTFS, HFS+ et tous les systèmes de fichiers Unix polyvalents (comme ext, UFS et ZFS). FAT ne supporte pas les liens

physiques.

Lors d'un clonage depuis un emplacement distant, Darcs cherchera et essaiera d'utiliser les paquets créés par `darcs optimize http` dans le dépôt distant. Les paquets sont de gros fichiers uniques qui peuvent être téléchargés plus rapidement que de nombreux petits

fichiers.

Darcs clone ne copiera pas les changements non enregistrés de l'arbre de travail du dépôt

source.

Vous pouvez copier un dépôt vers une URL ssh, auquel cas le nouveau dépôt sera toujours

complet.

Il est souvent souhaitable de faire une copie d'un dépôt qui exclut certains patchs. Par exemple, si les versions sont étiquetées, `darcs clone --tag .` ferait une copie du dépôt telle qu'à la dernière version. Un état de dépôt non étiqueté peut toujours être identifié de manière non ambiguë par un fichier de contexte, tel que généré par `darcs log --context`. Étant donné le nom d'un tel fichier, l'option `--context` créera un dépôt qui n'inclut que les patchs de ce contexte. Lorsqu'un utilisateur signale un bogue dans une version non publiée de votre projet, la manière recommandée de déterminer exactement la version qu'il utilisait est de lui demander d'inclure un fichier de contexte dans le rapport de bogue. Vous pouvez également faire une copie d'un état non étiqueté en utilisant les options `--to-patch` ou `--to-match`, qui excluent les patchs *après* le premier patch correspondant. Parce que ces options traitent l'ensemble des patchs comme une séquence ordonnée, vous pouvez obtenir différents résultats après un réordonnancement avec `darcs optimize

reorder`.

L'option `--set-scripts-executable` rend les scripts exécutables dans l'arbre de travail. Un script est tout fichier qui commence par un shebang ("#!")

.

L'option --inherit-default est destinée à prendre en charge un flux de travail où vous avez différentes branches du même dépôt amont et voulez que toutes vos branches aient le même dépôt amont comme defaultrepo. Elle est surtout utile lorsqu'elle est activée globalement en ajoutant 'ALL --inherit-default' à votre fichier `~/darcs/defaults`

.

Pour la commande clone, cela signifie ce qui suit : Si le dépôt source a déjà un defaultrepo défini (soit parce que vous l'avez cloné, soit parce que vous avez explicitement utilisé l'option --set-default), et que la source et la cible sont des chemins localement valides sur le même hôte, alors le dépôt cible obtiendra le même defaultrepo que le dépôt source. Sinon, le dépôt cible obtient le dépôt source lui-même comme defaultrepo, c'est-à-dire que nous revenons au comportement par défaut (--no-inherit-default)

.

Les commandes `initialize` et `clone` créent les fichiers de préférences dans le répertoire `_darcs/prefs/` du dépôt nouvellement créé. Avec l'option `--with-prefs-templates`, les fichiers de préférences `boring` et `binaries` seront remplis avec les modèles par défaut. Si vous souhaitez laisser ces fichiers vides, utilisez l'option `--no-prefs-templates`. Si vous préférez conserver les paramètres pertinents globalement, il est pratique d'ajouter 'ALL no-prefs-templates' à votre fichier `~/darcs/defaults

`

darcs pull [dépôt]..

.
Pull est utilisé pour intégrer des correctifs créés dans un autre dépôt dans le dépôt actuel (c'est-à-dire celui du répertoire courant, ou celui spécifié avec l'option `--repodir`). Pull accepte des arguments, qui sont des URL à partir desquelles tirer, et lorsqu'il est appelé sans argument, pull utilisera le dépôt spécifié dans `_darcs/prefs/defaultrepo`.

Le comportement par défaut (`--union`) est de tirer tous les correctifs présents dans n'importe lequel des dépôts spécifiés. Si vous spécifiez le drapeau `--intersection`, darcs ne tirera que les correctifs présents dans tous les dépôts source. Si vous spécifiez le drapeau `--complement`, darcs ne tirera que les éléments du premier dépôt qui n'existent dans aucun des dépôts restants.

Si `--reorder` est fourni, l'ensemble des correctifs qui existent uniquement dans le dépôt actuel est placé en haut de l'historique actuel. Cela fonctionnera même s'il n'y a pas de nouveaux correctifs à tirer.

L'option --inherit-default est conçue pour prendre en charge un flux de travail où vous avez différentes branches du même dépôt source et souhaitez que toutes vos branches aient le même dépôt source que le defaultrepo. Elle est particulièrement utile lorsqu'elle est activée globalement en ajoutant 'ALL --inherit-default' à votre fichier ~/darcs/defaults.

Pour les commandes push, pull et send, cela signifie : Change la signification de l'option --set-default de sorte qu'elle définisse le defaultrepo (local) sur le defaultrepo du dépôt distant, au lieu du dépôt distant lui-même. Cela se produit uniquement si le dépôt distant a un defaultrepo défini et que les dépôts local et distant sont des chemins locaux valides sur le même hôte, sinon il revient au comportement par défaut (--no-inherit-default).

Voir `darcs help apply` pour une description détaillée de nombreuses options.

darcs push [dépôt]

Push est l'inverse de pull. Push vous permet de copier des correctifs du dépôt actuel dans un autre dépôt.

L'option --reorder-patches fonctionne de la même manière que pour pull et apply : au lieu de placer les nouveaux correctifs (provenant de votre dépôt local) par-dessus (c'est-à-dire après) les correctifs existants (distants), elle place les correctifs propres au dépôt distant par-dessus ceux que vous poussez. Cela peut être utile, par exemple, si vous avez enregistré un tag localement et souhaitez que ce tag soit propre dans le dépôt distant après le push.

Si vous utilisez le drapeau `--apply-as`, darcs utilisera `sudo` pour appliquer les correctifs en tant qu'utilisateur différent. Cela peut être utile si vous souhaitez configurer un système où plusieurs utilisateurs peuvent modifier le même dépôt, mais que vous ne souhaitez pas leur accorder un accès complet en écriture. Ce n'est pas sécurisé contre des attaquants malveillants expérimentés, mais cela peut au moins protéger votre dépôt contre des utilisateurs maladroits, incompétents ou paresseux.

`darcs push` compressera les données des correctifs avant de les envoyer vers un emplacement distant via ssh. Cela fonctionne tant que le darcs distant n'est pas plus ancien que la version 2.5. Si vous obtenez des erreurs indiquant un paquet de correctifs corrompu, vous devriez réessayer avec l'option `--no-compress`.

L'option --inherit-default est conçue pour prendre en charge un flux de travail où vous avez différentes branches du même dépôt source et souhaitez que toutes vos branches aient le même dépôt source que le defaultrepo. Elle est particulièrement utile lorsqu'elle est activée globalement en ajoutant 'ALL --inherit-default' à votre fichier ~/darcs/defaults.

Pour les commandes push, pull et send, cela signifie : Change la signification de l'option --set-default de sorte qu'elle définisse le defaultrepo (local) sur le defaultrepo du dépôt distant, au lieu du dépôt distant lui-même. Cela se produit uniquement si le dépôt distant a un defaultrepo défini et que les dépôts local et distant sont des chemins locaux valides sur le même hôte, sinon il revient au comportement par défaut (--no-inherit-default).

Préparation des correctifs avant l'enregistrement :

darcs move <source> ... <destination>

Darcs ne peut pas distinguer de manière fiable entre la suppression d'un fichier et l'ajout d'un nouveau, et le déplacement d'un fichier. Par conséquent, Darcs suppose toujours le premier cas, et fournit la commande `darcs mv` pour informer Darcs lorsque vous souhaitez le second. Cette commande déplacera également le fichier dans l'arbre de travail (contrairement à `darcs remove`), sauf s'il a déjà été déplacé.

Darcs ne renommera pas un fichier si un autre fichier dans le même répertoire a le même nom, sauf pour la casse. L'option `--case-ok` remplace ce comportement. Windows et OS X utilisent généralement des systèmes de fichiers qui ne permettent pas à des fichiers d'un même répertoire d'avoir le même nom, sauf pour la casse (par exemple, `ReadMe` et `README`). Si `--case-ok` est utilisé, le dépôt pourrait être inutilisable sur ces systèmes !

darcs remove <fichier|répertoire> ...

La commande `darcs remove` existe principalement par symétrie avec `darcs add`, car la manière normale de supprimer un fichier du contrôle de version est simplement de le supprimer de l'arbre de travail. Cette commande n'est utile que dans le cas inhabituel où l'on souhaite enregistrer un correctif de suppression SANS supprimer la copie dans l'arbre de travail (qui peut être rajoutée).

Notez que l'application d'un correctif de suppression à un dépôt (par exemple, en tirant le correctif) affectera TOUJOURS l'arbre de travail de ce dépôt.

darcs replace <ancien> <nouveau> <fichier> ...

En plus des correctifs basés sur les lignes, Darcs prend en charge une forme limitée de substitution lexicale. Les fichiers sont traités comme des séquences de mots, et chaque occurrence du mot ancien est remplacée par le mot nouveau. Ceci est destiné à fournir un moyen propre de renommer une fonction ou une variable. De tels renommages affectent généralement des lignes tout au long du code source, de sorte qu'un correctif traditionnel basé sur les lignes serait très susceptible de confluer avec d'autres branches, nécessitant une fusion manuelle.

Les fichiers sont tokenisés selon une règle simple : les mots sont des chaînes de caractères token valides, et tout ce qui se trouve entre eux (ponctuation et espaces) est ignoré. Par défaut, les caractères token valides sont les lettres, les chiffres et le trait de soulignement (c'est-à-dire `[A-Za-z0-9_]`). Cependant, si le token ancien et/ou nouveau contient un trait d'union ou un point, LE trait d'union ET le point sont traités comme valides (c'est-à-dire `[A-Za-z0-9_.-]`).

L'ensemble des caractères valides peut être personnalisé à l'aide de l'option `--token-chars`. L'argument doit être entouré de crochets. Si un trait d'union se trouve entre deux caractères de l'ensemble, il est traité comme une plage de l'ensemble. Par exemple, dans la plupart des locales, `[A-Z]` désigne toutes les lettres majuscules. Si le premier caractère est un accent circonflexe, les tokens valides sont considérés comme le complément des caractères restants. Par exemple, `[^:0` pourrait être utilisé pour faire correspondre des champs dans passwd(5), où les enregistrements et les champs sont séparés par des sauts de ligne et des deux-points respectivement.

Si vous choisissez d'utiliser `--token-chars`, il est FORTEMENT recommandé de le faire de manière cohérente. Les conséquences de l'utilisation de plusieurs correctifs de remplacement avec différents arguments `--token-chars` sur le même fichier ne sont ni bien testées ni bien comprises.

Par défaut, Darcs refusera d'effectuer un remplacement si le nouveau token est déjà utilisé, car les remplacements ne seraient pas distinguables des tokens existants. Ce comportement peut être remplacé en fournissant l'option `--force`, mais une tentative de `darcs rollback` du correctif résultant affectera ces tokens existants.

Limitations :

Le tokeniseur traite les fichiers comme des chaînes d'octets, il n'est donc pas possible pour `--token-chars` d'inclure des caractères multi-octets, tels que les parties non ASCII de UTF-8. De même, essayer de remplacer un caractère « bit élevé » d'un encodage unioctet entraînera également le remplacement du même octet dans des fichiers avec des encodages différents. Par exemple, un a accent aigu de l'ISO 8859-1 correspondra également à un alpha de l'ISO 8859-7.

En raison des limitations du format de fichier des correctifs, les arguments `--token-chars` ne peuvent pas contenir d'espaces blancs littéraux. Par exemple, `[^ 0t]` ne peut pas être utilisé pour déclarer tous les caractères sauf l'espace, la tabulation et le saut de ligne comme valides dans un mot, car il contient un espace littéral.

Contrairement aux expressions régulières POSIX (7) entre crochets, les classes de caractères (telles que `[[:alnum:]]`) NE sont PAS prises en charge par `--token-chars`, et seront silencieusement traitées comme un simple ensemble de caractères.

darcs log [fichier|répertoire]...

La commande `darcs log` liste les correctifs du dépôt actuel ou, avec `--repo`, d'un dépôt distant. Sans options ni arguments, TOUS les correctifs seront listés.

Lorsqu'elle reçoit des chemins de fichiers ou de répertoires comme arguments, seuls les correctifs qui affectent ces chemins sont listés. Cela inclut les correctifs qui ont affecté des fichiers avant qu'ils ne soient déplacés ou renommés.

Quatre formats de sortie existent. Le défaut est `--human-readable`. Le format légèrement différent `--machine-readable` permet de voir les dépendances des correctifs en mode non interactif. Vous pouvez également choisir `--context`, qui est un format interne qui peut être relu par Darcs (par exemple, `darcs clone --context`).

Enfin, il y a `--xml-output`, qui produit du XML valide... à moins que les métadonnées du correctif (auteur, nom ou description) ne contiennent un caractère non ASCII et n'aient été enregistrées dans une locale non UTF8.

darcs test [[initialisation] commande

Exécute le test sur l'état actuellement enregistré du dépôt. Sans arguments, il utilise le test par défaut du dépôt (voir `darcs setpref`). Avec un argument, il le traite comme une commande de test. Avec deux arguments, le premier est une commande d'initialisation et le second est le test (signifiant que le code de sortie de la première commande n'est pas pris en compte pour déterminer la réussite du test). Si on lui donne les indicateurs `--linear` ou `--bisect`, il essaie de trouver la version la plus récente du dépôt qui passe le test.

`--linear` fait une recherche linéaire à partir de la tête, en s'éloignant de la tête. Cette stratégie est la meilleure lorsque le test s'exécute très rapidement ou le patch que vous cherchez est proche de la

tête.

`--bisect` fait une recherche binaire. Cette stratégie est la meilleure lorsque le test s'exécute très lentement ou le patch que vous cherchez se trouve probablement dans le passé lointain du

dépôt.

`--backoff` commence la recherche à partir de la tête, en sautant de plus en plus loin dans le passé jusqu'à ce que le test réussisse. Il fait ensuite une recherche binaire sur un sous-ensemble de ces patchs sautés. Cette stratégie fonctionne bien sauf si le patch que vous cherchez se trouve dans le passé lointain du

dépôt.

Sous l'hypothèse que l'échec est monotone, `--linear` et `--bisect` produisent le même résultat. (Monotone signifie que lorsqu'on s'éloigne de la tête, le résultat du test ne change qu'une seule fois de « échec » à « ok ».) Si l'échec n'est pas monotone, l'un des patchs qui cassent le test est trouvé au

hasard.

Si la commande de test renvoie un code de sortie de 125, l'état du dépôt est traité comme « non testable » - par exemple, vous pouvez lui faire faire cela pour une erreur de compilation ou un autre résultat qui n'est pas le problème réel que vous voulez trouver. Cela peut conduire à ce que plusieurs patchs soient signalés comme la source de

l'échec.

Par exemple, si le patch 1 introduit une erreur de compilation, le patch 2 casse un test dans une partie non liée du code, et le patch 3 répare l'erreur de compilation, alors les patchs 1, 2 et 3 seraient identifiés comme causant

l'échec.

L'option `--shrink-failures`, activée par défaut, ajoute une étape de post-traitement pour réordonner les patchs afin d'essayer de délimiter un échec plus précisément. Dans l'exemple ci-dessus, il est probable que le patch 2 pourrait être déplacé avant le patch 1 ou après le patch 3, permettant de l'identifier comme la seule cause de

l'échec.

La commande `darcs rebase' est utilisée pour éditer une collection de patches darcs.

L'idée de base est que vous pouvez suspendre des patches à la fin d'un dépôt. Ces patches ne font plus partie de l'historique et n'ont aucun effet sur l'arbre de travail. Les patches suspendus sont invisibles pour les commandes qui accèdent au dépôt de l'extérieur, comme push, pull, clone, send,

etc.

La séquence de patches suspendus peut être manipulée de manières qui ne sont pas autorisées pour les patches normaux. Par exemple, `darcs rebase obliterate` vous permet de supprimer un patch dans cette séquence, même si d'autres patches suspendus en dépendent. Ces autres patches deviendront alors en

conflit.

Vous pouvez aussi opérer sur les patches normaux de la manière habituelle. Si vous ajoutez ou supprimez des patches normaux, les patches suspendus seront automatiquement adaptés pour s'appliquer toujours à l'état pristine, devenant possiblement en conflit au

passage.

Notez que dès qu'un patch est suspendu, il perdra irrévocablement son identité. Cela signifie que suspendre un patch est soumis aux avertissements habituels concernant l'édition de l'historique de votre

projet.

L'opposé de suspendre un patch est de le réactiver. Cela le retransforme en patch normal. Si le patch est en conflit à la suite d'opérations précédentes sur les patches normaux ou les patches suspendus, la réactivation créera un balisage de conflit approprié. Notez cependant que le patch réactivé lui-même NE SERA PAS EN CONFLIT. Cela signifie qu'il n'y a aucun moyen de régénérer le balisage de conflit. Une fois que vous l'avez supprimé, en éditant des fichiers ou en utilisant `darcs revert`, toute information sur le conflit est

perdue.

ENVIRONNEMENT

HOME et APPDATA

Les préférences par utilisateur sont définies dans $HOME/.darcs (sur Unix) ou %APPDATA%/darcs (sous Windows). C'est également l'emplacement par défaut du cache.

DARCS_EDITOR, VISUAL, et EDITOR

Pour éditer la description d'un patch ou un commentaire par e-mail, Darcs invoquera un éditeur externe. Votre éditeur préféré peut être défini dans n'importe laquelle des variables d'environnement $DARCS_EDITOR, $VISUAL ou $EDITOR. Si aucune de ces variables n'est définie, nano est utilisé. Si nano plante ou n'est pas trouvé dans votre PATH, vi, emacs, emacs -nw et (sous Windows) edit sont essayés successivement.

DARCS_PAGER et PAGER

Darcs invoquera un pager si la sortie de certaines commandes dépasse 20 lignes. Darcs utilisera le pager spécifié par $DARCS_PAGER ou $PAGER. Si aucune des deux n'est définie, `less` sera utilisé. Définissez $DARCS_PAGER - ou $PAGER si le premier n'est pas défini - à une chaîne vide pour ne pas utiliser de pager.

DARCS_DONT_COLOR, DARCS_ALWAYS_COLOR, et DARCS_ALTERNATIVE_COLOR

Si le terminal comprend les séquences d'échappement de couleur ANSI, darcs mettra en surbrillance certains mots-clés et délimiteurs lors de l'impression des patchs, et imprimera également les lignes de hunks en couleur selon qu'elles sont supprimées ou ajoutées. Ceci peut être désactivé en définissant la variable d'environnement DARCS_DONT_COLOR à 1. Si vous utilisez un pager qui comprend les couleurs ANSI, comme `less -R`, darcs peut être forcé à toujours mettre en surbrillance la sortie en définissant DARCS_ALWAYS_COLOR à 1. Si vous ne voyez pas les couleurs, vous pouvez définir DARCS_ALTERNATIVE_COLOR à 1, et darcs utilisera les codes ANSI pour le gras et l'inversion vidéo au lieu des couleurs.

DARCS_DONT_ESCAPE_TRAILING_SPACES et DARCS_DONT_ESCAPE_TRAILING_CR

Par défaut, darcs échappera (en mettant en surbrillance si possible) tout type d'espaces à la fin des lignes lors de l'affichage du contenu des patchs. Si vous ne voulez pas de cela, vous pouvez le désactiver en définissant DARCS_DONT_ESCAPE_TRAILING_SPACES à 1. Un cas particulier existe pour les retours chariot uniquement : DARCS_DONT_ESCAPE_TRAILING_CR

DARCS_DONT_ESCAPE_ANYTHING, DARCS_DONT_ESCAPE_EXTRA, DARCS_ESCAPE_EXTRA, DARCS_DONT_ESCAPE_ISPRINT, et DARCS_ESCAPE_8BIT

Darcs a besoin d'échapper certains caractères lors de l'affichage du contenu des patchs dans un terminal, en fonction de l'encodage spécifié dans vos paramètres régionaux.

Par défaut, darcs suppose que l'encodage de vos paramètres régionaux est compatible ASCII. Cela inclut UTF-8 et certains encodages 8 bits comme ISO/IEC-8859 (y compris ses variantes). Comme ASCII contient des caractères de contrôle comme le backspace (qui pourrait masquer le contenu du patch à l'utilisateur lorsqu'il est imprimé littéralement dans le terminal), et même ceux qui peuvent introduire des risques de sécurité tels que la redirection de commandes vers le shell, darcs a besoin d'échapper de tels caractères. Ils sont imprimés comme `^<lettre de contrôle>` ou `<code hexadécimal>`. Darcs utilise également un marquage spécial pour les fins de ligne précédées d'espaces blancs, car ces espaces blancs ne seraient pas autrement reconnaissables.

Si vous utilisez un encodage qui n'est pas compatible ASCII, les choses sont un peu moins fluides. Ces encodages incluent UTF-16 et UTF-32, ainsi que bon nombre des encodages qui sont devenus obsolètes avec unicode. Dans ce cas, vous avez deux options : vous pouvez définir DARCS_DONT_ESCAPE_ANYTHING à 1. Alors tout ce qui ne modifie pas les jeux de codes fonctionnera, ainsi que toutes les cloches et sifflets de votre terminal. Cette variable d'environnement peut également être utile si vous redirigez la sortie vers un pager ou un filtre externe qui sait mieux que darcs comment gérer votre encodage. Notez que tout l'échappement, y compris l'échappement spécial de tous les espaces de fin de ligne, sera désactivé par ce réglage.

Une autre possibilité est de dire explicitement à darcs de ne pas échapper ou d'échapper certains octets, en utilisant DARCS_DONT_ESCAPE_EXTRA et DARCS_ESCAPE_EXTRA. Leurs valeurs doivent être des chaînes composées des octets bruts en question. Les échappements 'do' ont la priorité sur les échappements 'dont'. Les espaces sont toujours échappés en fin de ligne, cependant. La variable d'environnement spéciale DARCS_DONT_ESCAPE_TRAILING_CR désactive l'échappement des retours chariot en fin de ligne (style DOS).

Pour des raisons historiques, darcs prend également en charge DARCS_DONT_ESCAPE_ISPRINT et DARCS_USE_ISPRINT (qui sont des synonymes). Ceux-ci n'ont de sens que pour les encodages 8 bits comme ISO-8859 et ne sont plus nécessaires puisque darcs fait désormais la bonne chose par défaut.

Enfin, si vous êtes dans une situation de sécurité très sensible (ou juste paranoïaque pour d'autres raisons), vous pouvez définir DARCS_ESCAPE_8BIT à 1. Cela fera en sorte que darcs échappe chaque octet non ASCII en plus des caractères de contrôle ASCII.

DARCS_TMPDIR et TMPDIR

Darcs crée souvent des répertoires temporaires. Par exemple, la commande `darcs diff` crée deux arbres de travail à comparer. Par défaut, les répertoires temporaires sont créés dans /tmp, ou s'il n'existe pas, dans _darcs (dans le dépôt actuel). Ceci peut être outrepassé en spécifiant un autre répertoire dans le fichier _darcs/prefs/tmpdir ou la variable d'environnement $DARCS_TMPDIR ou $TMPDIR.

DARCS_KEEP_TMPDIR

Si la variable d'environnement DARCS_KEEP_TMPDIR est définie, darcs ne supprimera pas les répertoires temporaires qu'il crée. Ceci est principalement destiné au débogage de Darcs lui-même, mais peut également être utile, par exemple, pour déterminer pourquoi votre préférence de test (voir `darcs setpref`) échoue lorsque vous exécutez `darcs record`, mais fonctionne lorsqu'elle est exécutée manuellement.

DARCS_EMAIL et EMAIL

Chaque patch est attribué à son auteur, généralement par adresse e-mail (par exemple, `Fred Bloggs <fred@example.net>`). Darcs recherche cet auteur dans plusieurs endroits : l'option `--author`, les fichiers `_darcs/prefs/author` (dans le dépôt) et `~/.darcs/author` (dans votre répertoire personnel), et les variables d'environnement $DARCS_EMAIL et $EMAIL. Si aucune de ces options n'existe, Darcs vous demandera une chaîne d'auteur et l'écrira dans `~/.darcs/author`. Notez que si vous avez plus d'une adresse e-mail, vous pouvez les mettre toutes dans `~/.darcs/author`, un auteur par ligne. Darcs vous demandera toujours un auteur, mais cela vous permettra de choisir dans la liste ou de saisir une alternative.

SENDMAIL

Sur Unix, la commande `darcs send` s'appuie sur sendmail(8). La variable d'environnement `--sendmail-command` ou $SENDMAIL peut être utilisée pour fournir un chemin explicite vers ce programme ; sinon, les emplacements standard /usr/sbin/sendmail et /usr/lib/sendmail seront essayés.

DARCS_SLOPPY_LOCKS

Si sur certains systèmes de fichiers vous obtenez une erreur du type :


darcs: takeLock [...]: atomic_create [...]: unsupported operation

vous pourriez vouloir essayer d'exporter DARCS_SLOPPY_LOCKS=True.

DARCS_SSH

Les dépôts de la forme [user@]host:[dir] sont considérés comme des dépôts distants, auxquels Darcs accède avec le programme externe ssh(1).

La variable d'environnement $DARCS_SSH peut être utilisée pour spécifier un client SSH alternatif. Des arguments peuvent être inclus, séparés par des espaces. La valeur n'est pas interprétée par un shell, donc les constructions de shell ne peuvent pas être utilisées ; en particulier, il n'est pas possible que le nom du programme contienne des espaces en utilisant des guillemets ou des échappements.

DARCS_SCP et DARCS_SFTP

Lors de la lecture à partir d'un dépôt distant, Darcs tentera d'exécuter `darcs transfer-mode` sur l'hôte distant. Cela échouera si l'hôte distant n'a que Darcs 1 installé, n'a pas du tout Darcs installé, ou n'autorise que SFTP.

Si transfer-mode échoue, Darcs se rabattra sur scp(1) et sftp(1). Les commandes invoquées peuvent être personnalisées avec les variables d'environnement $DARCS_SCP et $DARCS_SFTP respectivement, qui se comportent comme $DARCS_SSH. Si l'extrémité distante n'autorise que sftp, essayez de définir DARCS_SCP=sftp.

scp est également utilisé par `darcs clone` si la destination est un répertoire ssh distant. Cette opération peut être rendue beaucoup plus rapide en définissant DARCS_SCP=rsync.

SSH_PORT

Si cette variable d'environnement est définie, elle sera utilisée comme numéro de port pour tous les appels SSH effectués par Darcs (lors de l'accès à des dépôts distants via SSH). Ceci est utile si votre serveur SSH ne fonctionne pas sur le port par défaut, et que votre client SSH ne prend pas en charge ssh_config(5). Les utilisateurs d'OpenSSH préféreront probablement mettre quelque chose comme `Host *.example.net Port 443` dans leur fichier ~/.ssh/config.

DARCS_CONNECTION_TIMEOUT

Définit le temps maximum en secondes que darcs autorise pour une connexion. Si la variable n'est pas spécifiée, le défaut est de 30 secondes. Cette option ne fonctionne qu'avec curl.
