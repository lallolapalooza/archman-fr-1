DESCRIPTIO

N

Ceci est une classe utilitaire pour DateTime::Format::Builder qui gère la création de parseurs. C'est ici que « Builder » délègue la plupart de ses

responsabilités
.

MÉTHODE

S

Il existe deux types de méthodes dans cette classe. Celles utilisées par les implémentations de parseurs et celles utilisées par « Builder ». Il est généralement peu probable que l'utilisateur veuille en utiliser une

quelconque.

Elles sont présentées, groupées selon leur

utilisation.

Paramètres Gestion (implémentations

)

Ces méthodes permettent aux implémentations d'avoir une validation de leurs arguments de manière standard et en raison de l'implémentation de « Parser », ces méthodes permettent également à « Parser » de déterminer quelle implémentation

utiliser.

Fonction interne qui renvoie simplement à quelle classe un paramètre est unique. S'il n'est pas unique, renvoie « und

Organisation et création de

parseurs

create_single_parse

r

Cela prend une spécification unique et renvoie une référence de code qui est un parseur adapté à cette spécification. C'est la fin de la chaîne pour toutes les méthodes de création de parseurs. Elle ne délègue plus

rien.

Si une référence de code est spécifiée, alors cette référence de code est immédiatement renvoyée (on suppose qu'elle est appropriée)

.

La spécification unique (si ce n'est pas une référence de code) peut être soit une référence de hachage, soit un hachage. Les clés et les valeurs doivent être conformes à la

spécification.

C'est ici que les tableaux de rappels sont unifiés. C'est aussi ici que les implémentations de parseurs sont utilisées. Avec la spécification donnée, les clés sont examinées et le module qui est le premier à avoir une clé unique dans la spécification est celui à qui la spécification est

donnée.

Remarque : veuillez déclarer un argument « valid_params » avec une lettre majuscule. Par exemple, si vous écrivez « DateTime::Format::Builder::Parser::Fnord », déclarez un paramètre appelé « Fnord ». De même, « DTFBP::Strptime » devrait avoir « Strptime » et « DTFBP::Regex » devrait avoir « Regex ». Ces deux derniers ne l'ont pas pour des raisons de rétrocompatibilité

.

Le parseur renvoyé renverra soit un objet « DateTime » soit « undef »

.

merge_callback

s

Produit soit undef, soit une référence de code unique à

partir de undef, d'un tableau vide, d'une référen
ce de code unique ou d'un tableau de références de code

create_multiple_parser

s

Étant donné le bloc d'options (comme créé par « create_parser ») et une liste de spécifications de parseurs uniques, cela renvoie une référence de code qui renvoie soit l'objet « DateTime » résultant, soit « undef »

.

Elle trie d'abord les spécifications en utilisant « sort_parsers » puis crée la foncti

on en fonction de ce
que cela a renvoyé.

sort_parser

s

Cela prend la liste des spécifications et les trie tout en transformant les spécifications en parseurs. Elle renvoie deux valeurs : la première est une référence de hachage contenant tous les parseurs basés sur la longueur. La seconde est un tableau contenant tous les autres

parseurs.

Si l'une des spécifications n'est pas une référence de code ou de hachage, alors elle appellera « croak »

.

Les références de code sont placées directement dans le tableau « other ». Toute référence de hachage sans clé length est passée à « create_single_parser » et le parseur résultant est placé dans le tableau « other »

.

Les références de hachage avec clés length sont passées à « create_single_parser », mais le parseur résultant est utilisé comme valeur dans la référence de hachage de longueur avec la longueur étant la clé. Si deux parseurs ou plus ont la même longueur spécifiée, alors

une erre
ur est levée.

create_parse

r

« create_class » est principalement un wrapper autour de « create_parser » qui fait des boucles et des trucs et appelle « create_parser » pour créer les parseurs

réels.

« create_parser » prend les spécifications de parseurs (qu'il s'agisse de spécifications uniques ou multiples) et renvoie une référence de code anonyme appropriée pour être utilisée comme méthode. La référence de code appellera « croak » dans le cas où elle est incapable d'analyser la chaîne unique qu'elle attend en

entrée.

L'entrée la plus simple est celle d'une spécification unique, présentée simplement comme un hachage brut, pas une référence de hachage. Celle-ci est passée directement à « create_single_parser » avec la valeur de retour de celle-ci enveloppée dans une fonction qui lui permet de « croak » en cas d'échec, ce wrapper étant

renvoyé.

Si le premier argument à « create_parser » est une référence de tableau, alors celle-ci est considérée comme un bloc d'options (comme pour la spécification de parseur multiple documentée précédemment)

.

Tout argument supplémentaire doit être soit une référence de hachage, soit une référence de code. Si le premier argument après la référence de tableau optionnelle n'est pas une référence de hachage ou de code alors cet argument et tous les arguments restants sont transmis à « create_single_parser » directement. Si le premier argument est une référence de hachage ou de code, alors celui-ci et les arguments restants sont transmis à « create_multiple_parsers »

.

La référence de code résultante de l'appel à l'une des méthodes de création est ensuite enveloppée dans une fonction qui appelle « croak » en cas d'échec ou renvoie l'objet « DateTime »

en ca
s de s
uccès.

RECHERCHE D'IMPLÉMENTATION

S

« Parser » charge automatiquement toutes les classes de parseurs dans @INC

.

Pour être chargé automatiquement, vous devezst être un "DateTime::Format::Builder::Parser::XXX"

module.

Pour être invisible et ne pas être chargé,

commencez votre classe par une lettre de
classe minuscule. Celles-ci sont ignorées.

ÉCRIRE UNE IMPLÉMENTATION

D'ANALYSEUR

Nommer votre

analyseur

Créez un module et nommez-le sous la forme "DateTime::Format::Builder::Parser::XXX" où XXX est ce que vous voulez, à condition qu'il ne commence pas par une lettre

minuscule.

Alternativement, appelez-le complètement différemment si vous ne dérangez pas que les utilisateurs chargent explicitement votre

module.

Je recommanderais de rester dans l'espace de noms "DateTime::Format::Builder" cependant --- au moment de la rédaction, je n'ai pas réfléchi à ce q

ue devraient être appelés ceux qui ne sont pas aut
o chargés. Des idées, envoyez-moi un courriel.

Déclarer les arguments de

spécification

Appelez "<DateTime::Format::Builder::Parser-"valid_params>> avec des arguments de style "Params::Validate". Par exemple

: 
DateTime::Format::Builder::Parser->valid_params(
    params => { type => ARRAYREF },
    Regex  => {
        type      => SCALARREF,
        callbacks => {
            'is a regex' => sub { ref(shift) eq 'Regexp' }
        }
    }
)
;

Commencez l'un des noms de clés par une lettre majuscule. Idéalement, cette clé devrait correspondre au XXX précédent. Cela sera utilisé pour aider à identifier à quel module une spécification d'analyseur doit être

donnée.

Les noms de clés on_match, on_fail, postprocess, preprocess, label et length sont prédéfinis. Il est recommandé de les utiliser. Vous pouvez ignorer length car "sort_parsers"

s'en
charge.

Définir

create_parser

Une méthode de classe nommée "create_parser" qui fait ce qui suit

:

Ses arguments sont ceux d'une méthode normale (c'est-à-dire la classe comme premier argument). Les autres arguments sont le résultat d'un appel à "Params::Validate" selon votre spécification (le "valid_params" précédent), c'est-à-dire un hachage de nom d'argument et de

valeur.

La valeur de retour devrait être une référence de code qui prend une chaîne de date comme premier argument et renvoie soit un objet "DateTime" soit "und

ef
".

le placement approprié
des appels aux rappels.
