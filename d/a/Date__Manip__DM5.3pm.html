Normalement, il n'est pas nécessaire d'appeler explicitement Date_Init. La première fois que l'une des autres routines est appelée, Date_Init sera appelé pour tout configurer. Si pour une raison quelconque vous souhaitez modifier la configuration de Date::Manip, vous pouvez passer la chaîne ou les chaînes appropriées à Date_Init pour réinitialiser les

choses.

Les chaînes à passer sont de la forme "VAR=VAL". Un nombre quelconque peut être inclus et ils peuvent être dans n'importe quel ordre. VAR peut être n'importe quelle variable de configuration. Une liste de toutes les variables de configuration est donnée dans la section PERSONNALISER DATE::MANIP ci-dessous. VAL est toute valeur autorisée pour cette variable. Par exemple, pour passer de l'anglais au français et utiliser le format non-US (de sorte que 12/10 soit le 12 oct.), faites ce

qui suit : 
Date_Init("Language=French","DateFormat=non-US")
;

Si Date_Init est appelé dans un contexte de liste, il renverra une liste de toutes les variables de configuration et de leurs val

eurs, adaptées pour être passées à Date_Init afin de ramener Date::Manip à l'état actuel. Le seul problème possible est qu
e par défaut, les jours fériés ne seront pas effacés, vous devrez donc peut-être préfixer l'élément "EraseHolidays=1" à la liste.
ParseDa
te 
$date = ParseDate(\@args);
$date = ParseDate($string);
$date = ParseDate(\$string)
;

Cela prend un tableau ou une chaîne contenant une date et la analyse. Lorsque la date est incluse sous forme de tableau (par exemple, les arguments d'un programme), le tableau doit contenir une date valide dans le premier ou les premiers éléments (les éléments suivant une date valide sont ignorés). Les éléments contenant une date valide sont décalés du tableau. Le plus grand nombre possible d'éléments pouvant être correctement interprétés comme une date valide est toujours utilisé. Si une chaîne est saisie plutôt qu'un tableau, cette chaîne est testée pour une date valide. La chaîne n'est pas modifiée, même si elle est passée par

référence.

Le vrai travail est effectué dans la routine

ParseDateString.

La routine ParseDate est principalement utilisée pour gérer les arguments de la ligne de commande. Si vous avez une commande où vous souhaitez saisir une date en tant qu'argument de la ligne de commande, vous pouvez utiliser Date::Manip pour faire fonctionner quelque chose comme ce

qui suit : 
mycommand -date Dec 10 1997 -arg
-arg2

Plus besoin de lire les pages man pour découvrir quel format de date est requis dans une page

man.

Note historique : c'est à l'origine la raison pour laquelle les routines de Date::Manip ont été écrites (bien avant qu'elles ne soient publiées en tant que module Date::Manip). J'utilisais un tas

de programmes (principalement des gestionnaires de file d'attente par lots) où les dates et les heures étaient saisies en tant qu'options de ligne de commande et je m'énervais beaucoup des nombreus
es façons différentes (mais non compatibles) de les saisir. Date::Manip consistait à l'origine en fondamentalement 1 routine à laquelle je pouvais passer "@ARGV" et qui retirait une date du début.
ParseDateStr
ing 
$date = ParseDateString($string)
;

Cette routine est appelée par ParseDate, mais elle peut aussi être appelée directement pour gagner un peu de temps (un montant négligeable)

.

REMARQUE : L'une des questions les plus fréquemment posées que j'ai reçues est la façon d'analyser les secondes depuis l'époque. ParseDateString ne peut pas simplement analyser un nombre comme les secondes depuis l'époque (cela entre en conflit avec certains formats de date ISO-8601). Il y a deux façons d'obtenir cette information. D'abord, vous pouvez faire ce

qui suit : 
$secs = ...         # secondes depuis Jan 1, 1970  00:00:00 GMT
$date = DateCalc("Jan 1, 1970  00:00:00 GMT","+
$secs");

Ensuite, vous pouvez l'appeler directement

comme suit : 
$date = ParseDateString("epoch $secs")
;

Pour aller en arrière, utilisez simplement le format "%s" de

UnixDate : 
$secs = UnixDate($date,
"%s");

Une date complète inclut en réalité 2 parties : la date et l'heure. Une heure doit inclure les heures et les minutes et peut optionnellement inclure les secondes, les secondes fractionnaires, une chaîne de type am/pm et un fuseau horaire. Par

exemple : 
[at] HH:MN              [Zone]
[at] HH:MN         [am] [Zone]
[at] HH:MN:SS      [am] [Zone]
[at] HH:MN:SS.SSSS [am] [Zone]
[at] HH            am
[Zone]

Les heures peuvent être écrites avec 1 ou 2 chiffres, mais la forme à un seul chiffre ne peut être utilisée que lorsqu'aucune ambiguïté n'est introduite (c'est-à-dire lorsqu'elle n'est pas immédiatement précédée d'un

chiffre).

Une heure est généralement saisie en mode 24 heures, mais le mode 12 heures peut également être utilisé si AM/PM sont saisis (AM peut être saisi comme AM ou A.M. ou d'autres variantes selon la

langue).

Les secondes fractionnaires sont également prises en charge lors de l'analyse, mais la partie fractionnaire est jetée (AUCUN arrondi n'a

lieu).

Les fuseaux horaires apparaissent toujours immédiatement après l'heure. Un certain nombre de formes différentes sont prises en charge (voir la section FUSEAUX HORAIRES ci-dessous)

.

Par ailleurs, l'heure est retirée de la date avant que celle-ci ne soit analysée, de sorte que l'heure peut apparaître avant ou après la date, ou entre n'importe quels deux éléments de la

date.

** Notez que les formats « dimanche semaine 22 » et « 22ème dimanche » donnent des comportements très différents. « dimanche semaine 22 » renvoie le dimanche de la 22ème semaine de l'année basé sur la façon dont la semaine 1 est définie. semaine.

Notez que certains mots tels que « in », « at », « of », etc. qui apparaissent couramment dans une date ou une heure sont ignorés. De plus, l'année est toujours

Quelques points à

noter :

Toutes les chaînes sont insensibles à la casse. « December » et « DEceMBer » fonctionnent tous

les deux.

Lorsqu'une partie de la date n'est pas donnée, des valeurs par défaut sont utilisées : l'année par défaut est l'année en cours ; les heures, minutes, secondes

à 00.

L'année peut être saisie avec 2 ou 4 chiffres. Si elle est saisie avec 2 chiffres, elle sera convertie en une année à 4 chiffres. Il y a plusieurs façons de faire cela basées sur la valeur de la variable YYtoYYYY (décrite ci-dessous). Le comportement par défaut est de forcer l'année à 2 chiffres à être dans la période de 100 ans CurrYear-89 à CurrYear+10. Ainsi en 1996, la plage est [1907 à 2006], et l'année à 2 chiffres 05 se référerait à 2005 mais 07 se référerait à 1907. Voir PERSONNALISER DATE::MANIP ci-dessous pour des informations sur YYtoYYYY pour d'autres

méthodes.

Les dates sont toujours vérifiées pour s'assurer qu'elles sont

valides.

Dans tous les formats, le jour de la semaine (« vendredi ») peut être saisi n'importe où dans la date et il sera vérifié pour l'exactitude. En d'autres termes,
« Tue Jul 16 1996 13:17:00 » fonctionnera mais
« Jul 16 1996 Wednesday 13:17:00 » ne fonctionnera pas (car le 16 juillet 1996 est un mardi, pas un mercredi). Notez que selon l'endroit où se trouve le jour de la semaine, cela peut donner des résultats inattendus lorsqu'il est utilisé dans un contexte tableau (avec ParseDate). Par exemple, la date ("Jun","25","Sun","1990") renverrait le 25 juin de l'année en cours car le 25 juin 1990 n'est pas un

dimanche.

Les heures « 12:00 am », « 12:00 pm » et « midnight » ne sont pas bien définies. Pour le meilleur ou pour le pire, j'utilise la convention suivante dans Date::Manip :
midnight = 12:00am = 00:00:00
noon = 12:00pm = 12:00:00 et la journée va de 00:00:00 à 23:59:59. En d'autres termes, midnight est le début d'une journée plutôt que la fin d'une journée. L'heure 24:00:00 est également autorisée (bien qu'elle soit automatiquement transformée en 00:00:00 du jour

suivant).

Le format de la date renvoyée est AAAAMMJJHH:MM:SS. L'avantage de ce format d'heure est que deux heures peuvent être comparées en utilisant des comparaisons de chaînes simples pour déterminer laquelle est la plus tardive. De plus, il est facilement compréhensible par un humain. Des formes alternatives peuvent être utilisées si c'est plus pratique. Voir Date_Init ci-dessous et la variable de configuration

Internal.

NOTE : Le format de la date va changer à un moment donné dans le futur pour AAAAMMJJHH:MN:SS+HHMN*FLAGS. Afin de maintenir

la compatibilité, vous devriez utiliser UnixDate pour extraire des informations d'une date, et Date_Cmp pour comp
arer deux dates. La comparaison de chaînes simples ne fonctionnera que pour des dates dans le même fuseau horaire.

NOTE

1 :

Le format ls (%l) s'applique aux dates dans les 6 mois passés OU futurs

!

NOTE

2 :

Les %U, %W, %L, %G, et %J formats sont utilisés pour prendre en charge le format ISO-8601 : YYYY-wWW-D. Dans ce format, une date est écrite comme une année, la semaine de l'année, et le jour de la semaine. Techniquement, la semaine peut être considérée comme commençant n'importe quel jour de la semaine, mais dimanche et lundi sont les deux choix courants, donc les deux sont pris en

charge.

Les %W et %G formats retournent la semaine-de-l'année et l'année en traitant les semaines comme commençant le

lundi.

Les %U et %L formats retournent la semaine-de-l'année et l'année en traitant les semaines comme commençant le

dimanche.

Si $mode est 1, le calcul est fait en utilisant un mode approximatif où un delta est renvoyé en utilisant aussi des années et des mois. La partie année et mois est calculée d'abord suivie du reste. Par exemple, les deux dates "Mar 12 1995" et "Apr 13 1995" auraient un delta exact de "31 days" mais en mode approximatif, il serait renvoyé comme "1 month 1 day". De même, "Mar 31" et "Apr 30" auraient des deltas de "30 days" ou "1 month" (puisqu'Apr 31 n'existe pas, cela redescend à Apr 30). Le mode approximatif est une façon plus humaine de voir les choses (vous diriez 1 mois et 2 jours plus souvent que 33 jours), mais il est moins significatif en termes de temps absolu. En mode approximatif $d1 et $d2 doivent être des dates. Si l'un ou les deux est un delta, le calcul est fait en mode

exact.

Si $mode est 2, un mode business est utilisé. C'est-à-dire que le calcul est fait en utilisant des jours ouvrables, en ignorant les jours fériés, les week-ends, etc. Afin d'utiliser correctement ce mode, un fichier de configuration doit exister qui contient la section définissant les jours fériés (voir la documentation sur le fichier de configuration ci-dessous). Le fichier de configuration peut aussi définir la semaine de travail et les heures de la journée de travail, il est donc possible d'avoir différents fichiers de configuration pour différentes

entreprises.

Par exemple, si un fichier de configuration définit la journée de travail de 08:00 à 18:00, une semaine de travail consistant en Mon-Sat, et les jours fériés standard (américains), alors de mardi à 12:00 jusqu'au lundi suivant à 14:00 est 5 jours et 2 heures. Si la "fin" de la journée est atteinte dans un calcul, cela bascule automatiquement au jour suivant. Ainsi, mardi à 12:00 plus 6 heures est mercredi à 08:00 (à condition que Wed ne soit pas un jour férié). De même, une date qui n'est pas pendant une journée de travail devient automatiquement le début de la prochaine journée de travail. Ainsi, dimanche 12:00 et lundi à 03:00 deviennent tous deux automatiquement lundi à 08:00 (à condition que lundi ne soit pas un jour férié). En mode business, toute combinaison de date et de delta peut être saisie, mais un delta ne devrait pas contenir un champ année ou mois (les semaines sont cependant acceptables)

.

Voir Date::Manip::Calc pour des commentaires supplémentaires sur les calculs en mode

business.

Notez qu'une semaine de business est traitée de la même manière qu'une semaine exacte (c.-à-d. de mardi à mardi, indépendamment des jours fériés). Puisque cela signifie que la relation entre les jours et les semaines n'est PAS non ambiguë, lorsqu'un delta est produit à partir de deux dates, il sera en termes de d/h/mn/s (c.-à-d. pas de champ

semaine).

Si $mode est 3 (ce qui ne s'applique que lorsque deux dates sont passées), un mode business exact est utilisé. Dans ce cas, il renvoie un delta comme un nombre exact de jours/heures/etc. de business entre les deux. Les semaines, mois et années sont

ignorés.

Toute autre valeur non nulle de $mode est traitée comme $mode=1 (mode approximatif)

.

Le mode peut être défini automatiquement dans les dates/deltas passées en incluant un mot-clé quelque part dedans. Par exemple, en anglais, si le mot "approximately" est trouvé dans l'un ou l'autre des arguments date/delta, le mode approximatif est forcé. DateFormat
Différents pays considèrent la date 12/10 comme le 10 décembre ou le 12 octobre. Aux États-Unis, la première est la plus courante, mais ce n'est certainement pas le cas pour les autres pays. Définir DateFormat à "US" force le premier comportement (10 décembre). Définir DateFormat à n'importe quelle autre valeur force le second comportement (12 octobre).
TZ
Si défini, cela définit le fuseau horaire local. Voir la section TIME ZONES ci-dessus pour des informations sur son format.
ConvTZ
Toutes les comparaisons et calculs de dates doivent être effectués dans un seul fuseau horaire pour qu'ils fonctionnent correctement. Ainsi, lorsqu'une date est analysée, elle doit être convertie dans un fuseau horaire spécifique. Cela permet de comparer et de manipuler facilement les dates comme si elles étaient toutes dans un seul fuseau horaire.

La variable ConvTZ détermine dans quel fuseau horaire les dates doivent être stockées. Si elle est laissée vide, toutes les dates sont converties dans le fuseau horaire local (voir la variable TZ ci-dessus). Si elle est définie sur l'un des fuseaux horaires listés ci-dessus, toutes les dates sont converties dans ce fuseau horaire. Enfin, si elle est définie sur la chaîne "IGNORE", toutes les informations de fuseau horaire sont ignorées lors de la lecture des dates (dans ce cas, les deux dates "1/1/96 12:00 GMT" et "1/1/96 12:00 EST" seraient traitées comme identiques).

Internal
Lorsqu'une date est analysée avec ParseDate, cette date est stockée dans un format interne compris par les routines Date::Manip UnixDate et DateCalc. À l'origine, le format utilisé pour stocker la date internement était : 
YYYYMMDDHH:MN:SS

Il a été suggéré que je supprime les deux-points (:) pour raccourcir ceci en :

YYYYMMDDHHMNSS

Le principal avantage est que certaines bases de données utilisent le deux-points comme délimiteur, ce qui rend le stockage d'une date provenant de Date::Manip fastidieux.

Afin de maintenir la rétrocompatibilité, la variable Internal a été introduite. Définissez-la à 0 (pour utiliser l'ancien format) ou 1 (pour utiliser le nouveau format).

FirstDay
Il est parfois nécessaire de savoir quel jour de la semaine est considéré comme le premier. Par défaut, il est défini à lundi, mais de nombreux pays et personnes préféreront dimanche (et dans quelques cas, un autre jour peut être souhaité). Définissez la variable FirstDay sur le premier jour de la semaine (1=lundi, 7=dimanche). Lundi devrait être choisi pour se conformer à la norme ISO 8601.
WorkWeekBeg, WorkWeekEnd
Le premier et le dernier jour de la semaine de travail. Par défaut, lundi et vendredi. WorkWeekBeg doit précéder WorkWeekEnd numériquement. Les jours sont numérotés de 1 (lundi) à 7 (dimanche).

Il n'y a aucun moyen de gérer une semaine de travail irrégulière de jeudi à lundi par exemple, ou 10 jours de travail, 4 jours de repos.

WorkDay24Hr
Si cette variable est non-nulle, une journée de travail est considérée comme d'une durée de 24 heures. Les variables WorkDayBeg et WorkDayEnd sont ignorées dans ce cas.
WorkDayBeg, WorkDayEnd
Les heures de début et de fin de la journée de travail. WorkDayBeg doit précéder WorkDayEnd (c'est-à-dire qu'il n'y a aucun moyen de gérer le travail de nuit où la journée de travail commence un jour et se termine le lendemain). De plus, la journée de travail DOIT durer plus d'une heure (bien sûr, si ce n'est pas le cas, faites-le moi savoir... je veux un emploi là-bas !).

Périodiquement, si un jour n'est pas un jour ouvrable, nous devons trouver le jour ouvrable le plus proche. Par défaut, nous chercherons d'abord "demain", mais si cette variable est définie à 0, nous chercherons d'abord "hier". Cela n'est utilisé que dans Date_NearestWorkDay et peut facilement être remplacé (voir la documentation de cette fonction).
DeltaSigns
Avant la version 5.07 de Date::Manip, un delta négatif mettait des signes négatifs devant chaque composante (c'est-à-dire "0:0:-1:-3:0:-4"). Par défaut, 5.07 change ce comportement pour n'imprimer qu'un ou deux signes devant les éléments année et jour (même si ces éléments peuvent être à zéro) et le signe pour année/mois et jour/heure/minute/secondes est le même. Définir cette variable à une valeur non nulle force les deltas à être stockés avec un signe devant chaque élément (y compris les éléments égaux à 0).
Jan1Week1
La norme ISO 8601 indique que la première semaine de l'année est celle qui contient le 4 janvier (c'est-à-dire qu'elle est la première semaine dans laquelle la plupart des jours de cette semaine tombent dans cette année). Cela signifie que les 3 premiers jours de l'année peuvent être traités comme appartenant à la dernière semaine de l'année précédente. Si cela est défini à une valeur non nulle, la norme ISO 8601 sera ignorée et la première semaine de l'année contiendra le 1er janvier.

Par défaut, une année à 2 chiffres est considérée comme tombant dans la période de 100 ans de CURR-89 à CURR+10. YYtoYYYY peut être défini à n'importe quel entier N pour forcer une année à 2 chiffres dans la période CURR-N à CURR+(99-N). Une valeur de 0 force l'année à être l'année en cours ou ultérieure. Une valeur de 99 force l'année à être l'année en cours ou antérieure. Puisque je n'effectue aucune vérification sur la valeur de YYtoYYYY, vous pouvez en fait lui donner n'importe quelle valeur positive ou négative pour la forcer dans le siècle de votre choix.

Elle peut aussi être définie sous la forme "C####" pour la forcer dans une période de 100 ans spécifique. C1950 fait référence à 1950-2049.

non :-)

Problèmes
Si vous utilisez Date::Manip pour trier un certain nombre de dates, vous devez appeler Date_Init soit explicitement, soit par l'intermédiaire d'une autre routine de Date::Manip avant qu'il ne soit utilisé dans le tri. Par exemple, le code suivant échoue : 
use Date::Manip;
# Date_Init;
sub sortDate {
    my($date1, $date2);
    $date1 = ParseDate($a);
    $date2 = ParseDate($b);
    return (Date_Cmp($date1,$date2));
}
@dates = ("Fri 16 Aug 96",
         "Mon 19 Aug 96",
         "Thu 15 Aug 96");
@i=sort sortDate
@dates;

mais si vous décommentez la ligne Date_Init, cela fonctionne. La raison en est que la première fois que vous appelez Date_Init, il initialise un certain nombre d'éléments utilisés par Date::Manip. Certains d'entre eux doivent être triés (des expressions régulières triées par longueur pour garantir la correspondance la plus longue). Il s'avère que Perl a un bug qui n'autorise pas un tri dans un tri. À un moment donné, cela devrait être corrigé, mais pour l'instant, la meilleure chose à faire est d'appeler Date_Init explicitement. Le bug existe dans toutes les versions jusqu'à la 5.005 (je n'ai pas encore testé la

5.6.0).

REMARQUE : C'est une façon EXTRÊMEMENT inefficace de trier des données (mais lisez la 2e note ci-dessous pour une façon simple de corriger cela). À la place, vous devriez analyser les dates avec ParseDate, les trier en utilisant une comparaison de chaîne normale, puis les reconvertir vers le format souhaité en utilisant

UnixDate.

REMARQUE : On m'a signalé que vous pouvez toujours utiliser ParseDate pour trier des dates de cette manière, et être assez efficace grâce à l'utilisation de Memoize. Ajoutez simplement les lignes suivantes à

votre code : 
use Date::Manip;
use Memoize;
memoize('ParseDate');
...
@i=sort sortDate
@dates;

Puisque sortDate appellerait ParseDate avec les mêmes données encore et encore, c'est une application parfaite pour le module Memoize. Ainsi, le tri avec ParseDate n'est plus lent pour

le
tri.

Heure d'été (Daylight Saving
Time)
Date::Manip 5.xx ne gère pas l'heure d'été, bien qu'il gère les fuseaux horaires dans une certaine mesure. La conversion de l'EST vers le PST fonctionne bien. Le passage de l'EST au PDT est peu fiable.

Les exemples suivants sont exécutés en hiver sur la côte est des États-Unis (c'est-à-dire dans le fuseau

horaire EST). 
print UnixDate(ParseDate("6/1/97 noon"),"%u"),"\n";
=> Sun Jun  1 12:00:00 EST
1997

Le 1er juin EST n'existe pas. Le 1er juin est pendant l'EDT. Il devrait

afficher : 
=> Sun Jun  1 00:00:00 EDT
1997

Même l'ajout explicite du fuseau horaire ne corrige pas les choses (si quelque chose, cela les

aggrave) : 
print UnixDate(ParseDate("6/1/97 noon EDT"),"%u"),"\n";
=> Sun Jun  1 11:00:00 EST
1997

Date::Manip convertit tout vers le fuseau horaire actuel (l'EST dans ce

cas).

Des problèmes similaires surviennent lorsqu'on essaie d'effectuer des calculs de dates au-delà d'un changement de fuseau horaire. Ces calculs peuvent être décalés d'une

heure.

De plus, si vous exécutez un script qui utilise Date::Manip sur une période qui commence dans un fuseau horaire et se termine dans un autre (c'est-à-dire qu'il passe de l'heure d'été à l'heure standard ou vice versa), beaucoup de choses peuvent être fausses (en particulier le temps

écoulé).

Ces problèmes ne seront pas cor

rigés dans Date::Manip 5.xx.
