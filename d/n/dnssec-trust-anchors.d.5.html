DESCRIPTIO

N

Les fichiers de configuration des ancres de confiance DNSSEC définissent les ancres de confiance positives et négatives sur lesquelles systemd-resolved.service(8) fond

e ses preuves d'i
ntégrité DNSSEC.

ANCRES DE CONFIANCE

POSITIVES

Les fichiers de configuration des ancres de confiance positives contiennent des définitions d'enregistrements de ressources DNSKEY et DS à utiliser comme base pour les preuves d'intégrité DNSSEC. Voir RFC 4035, Section 4.4[1] pour plus d'informations sur les ancres de confiance

DNSSEC.

Les ancres de confiance positives sont lues depuis des fichiers avec le suffixe .positive situés dans /etc/dnssec-trust-anchors.d/, /run/dnssec-trust-anchors.d/ et /usr/lib/dnssec-trust-anchors.d/. Ces répertoires sont parcourus dans l'ordre spécifié, et un fichier d'ancre de confiance de même nom dans un chemin antérieur remplace un fichier d'ancre de confiance dans un chemin ultérieur. Pour désactiver un fichier d'ancre de confiance fourni dans /usr/lib/dnssec-trust-anchors.d/, il suffit de fournir un fichier portant le même nom dans /etc/dnssec-trust-anchors.d/ ou /run/dnssec-trust-anchors.d/ qui est soit vide, soit un lien symbolique vers /dev/null (« masqué »)

.

Les fichiers d'ancres de confiance positives sont de simples fichiers texte ressemblant à des fichiers de zones DNS, comme documenté dans RFC 1035, Section 5[2]. Un seul DS ou enregistrement de ressource DNSKEY peut être listé par ligne. Les lignes vides et les lignes commençant par « # » ou « ; » sont ignorées, ce qui peut être utilisé pour des commentaires. Un enregistrement de ressource DS est spécifié comme dans l'exemple suivant

: 
. IN DS 19036 8 2 49aac11d7b6f6446702e54a1607371607a1a41855200fd2ce1cdde32f24e8f
b
5

Le premier mot spécifie le domaine, utilisez « . » pour le domaine racine. Le domaine peut être spécifié avec ou sans point final, ce qui est considéré comme équivalent. Le deuxième mot doit être « IN », le troisième mot « DS ». Les mots suivants spécifient le tag de clé, l'algorithme de signature, l'algorithme de digest, suivis de l'empreinte de clé encodée en hexadécimal. Voir RFC 4034, Section 5[3] pour les détails sur la syntaxe précise et la signification de ces

champs.

Alternativement, des enregistrements de ressource DNSKEY peuvent être utilisés pour définir des ancres de confiance, comme dans l'exemple suivant

: 
. Le premier mot spécifie à nouveau le domaine, le deuxième mot doit être « IN », suivi de « DNSKEY ». Les mots suivants encodent les champs d'indicateurs, de protocole et d'algorithme de la DNSKEY, suivis des données de clé encodées en Base64. Voir RFC 4034, Section 2[4] pour les détails sur la syntaxe précise et la signification de ces

champs.

Si plusieurs DS ou enregistrements DNSKEY sont définis pour le même domaine (éventuellement même dans différents fichiers d'ancres de confiance), toutes les clés sont utilisées et sont considérées comme équivalentes comme base pour les preuves

DNSSEC.

Notez que systemd-resolved utilisera automatiquement une clé d'ancre de confiance intégrée pour le domaine racine de l'Internet si aucune ancre de confiance positive n'est définie pour le domaine racine. Dans la plupart des cas, il est donc inutile de définir une clé explicite avec des fichiers d'ancres de confiance. La clé intégrée est désactivée dès qu'au moins une clé d'ancre de confiance pour le domaine racine est définie dans les fichiers d'ancres de

confiance.

Il est généralement recommandé d'encoder les ancres de confiance dans des enregistrements de ressources DS, plutôt que dans des enregistrements de ressources

DNSKEY.

Si une ancre de confiance spécifiée via un enregistrement DS est trouvée révoquée, elle est automatiquement supprimée de la base de données des ancres de confiance pour l'exécution en cours. Voir RFC 5011[5] pour les détails sur les ancres de confiance révoquées. Notez que systemd-resolved ne mettra pas à jour sa base de données d'ancres de confiance à partir de serveurs DNS automatiquement. À la place, il est recommandé de mettre à jour le logiciel de résolution ou de mettre à jour la nouvelle ancre de confiance en l'ajoutant dans de nouveaux fichiers d'ancres de

confiance.

L'ancre de confiance DNSSEC actuelle pour le domaine racine de l'Internet est disponible sur la page IANA Trust Anch

or and
Keys[6].

ANCRES DE CONFIANCE

NÉGATIVES

Les ancres de confiance négatives définissent les domaines pour lesquels la validation DNSSEC doit être désactivée. Les fichiers d'ancres de confiance négatives se trouvent aux mêmes emplacements que les fichiers d'ancres de confiance positives, et suivent les mêmes règles de remplacement. Ce sont des fichiers texte avec le suffixe .negative. Les lignes vides et les lignes dont le premier caractère est « ; » sont ignorées. Chaque ligne spécifie un nom de domaine qui est la racine d'un sous-arbre DNS pour lequel la validation doit être désactivée. Par exemple

: 
# Correspondances IPv4 inversées
10.in-addr.ar
pa 16.172.in-addr.arpa 168.192.in-addr.arpa .
.. # Quelques domaines personnalisés prod stag

Les ancres de confiance négatives sont utiles pour prendre en charge des sous-arbres DNS privés qui ne sont pas référencés depuis la hiérarchie DNS de l'Internet, et qui ne sont pas

signés.

RFC 7646[7] pour les détails sur les ancres de confiance

négatives.

Si aucun fichier d'ancres de confiance négatives n'est configuré, un ensemble intégré de domaines de zones DNS privées bien connus est utilisé comme ancres de confiance

négatives.

Il est également possible de définir des ancres de confiance négatives par interface en utilisant le paramètre DNSSECNegativeTrustAnchors= dans les fichiers systemd.ne

twor
k(5).
