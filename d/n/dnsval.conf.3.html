En dehors des options de configuration spécifiques à la zone, il est également possible de configurer des options globales pour la validation dans dnsval.conf. Les options globales peuvent être spécifiées à l'aide de la construction ci-dessous.

global-options 
    keyowrd1 value1
    keyword2 value2
    ...
;

Il ne peut y avoir qu'une seule construction global-options définie pour dnsval.conf. Si plusieurs constructions sont définies, seule la première est utilisée.

Les mots-clés suivants sont définis pour global-options dans dnsval.conf

trust-local-answers
Cette option est obsolète. Utilisez trust-oob-answers à la place.
trust-oob-answers
Si la valeur associée à cette option est yes, alors, pour toutes les réponses renvoyées en utilisant un mécanisme hors bande (par exemple, un magasin de fichiers tel que /etc/hosts), la valeur renvoyée par la fonction val_istrusted() (voir libval(3)) est supérieure à un.
edns0-size
Lors de l'interrogation de divers serveurs de noms, libsres tentera également plusieurs tailles EDNS0, terminant par une requête où EDNS0 est désactivé (c'est-à-dire sans bit CD défini). Les tailles EDNS0 suivantes sont essayées par défaut : 4096, 1492, 512. Le bouton de politique « edns0-size » peut être utilisé pour modifier la taille EDNS0 la plus grande qui est tentée.
env-policy
Cette option permet à l'administrateur de dnsval.conf de contrôler si libval utilise les valeurs spécifiées par l'utilisateur dans les variables d'environnement lors de la détermination de la politique libval et des cibles de journalisation. Voir la section ci-dessous sur la substitution des politiques dnsval.conf pour plus de détails sur cette option.
app-policy
Cette option permet à l'administrateur du fichier dnsval.conf de contrôler si libval recherche automatiquement une politique de validation avec une étiquette égale au nom de l'application dans dnsval.conf. Voir la section ci-dessous sur la substitution des politiques dnsval.conf pour plus de détails sur cette option.
closest-ta-only
Le comportement de validation par défaut consiste à rechercher toute chaîne d'authentification qui se valide avec succès. Ainsi, s'il existe des ancres de confiance pour example.com et test.example.com, le validateur renverra un succès si la chaîne d'authentification peut être ancrée à l'ancre de confiance example.com, même si l'ancre de confiance pour test.example.com ne correspond pas. Dans les cas où ce n'est pas souhaitable, l'option closest-ta-only peut être utilisée.

Si cette option est définie sur yes, l'algorithme de validation se termine à l' TA la plus proche.

rec-fallback
Cette option est utilisée pour contrôler si libval tentera de recourir à une recherche récursive du nom si la réponse du serveur de noms en cache a renvoyé une erreur. Par défaut, cette option est définie sur yes ; elle peut être désactivée en définissant cette option sur no.
max-refresh
Cette option est utilisée conjointement avec le drapeau de requête VAL_QUERY_SKIP_CACHE. Lorsque les requêtes ont ce drapeau activé, elles ignorent normalement les entrées mises en cache. Cependant, max-refresh peut limiter la fréquence à laquelle les requêtes sont réellement envoyées sur le fil. Lorsque cette option est définie sur une valeur positive, une nouvelle requête n'est envoyée que si la valeur mise en cache a été stockée il y a plus de (la valeur spécifiée par) max-refresh secondes. Si max-refresh est 0, alors le cache est toujours ignoré. Si la valeur est -1, le cache n'est jamais ignoré. La valeur par défaut pour max-refresh est de 60 secondes. Cela signifie que deux requêtes envoyées avec le drapeau VAL_QUERY_SKIP_CACHE défini à moins d'une minute d'intervalle ne résulteront qu'en une seule requête vue sur le fil.
proto
Cette option est utilisée pour contrôler le protocole réseau que libval utilise pour envoyer des requêtes à divers serveurs de noms. Si la valeur est définie sur ipv6, libval n'utilise que IPv6 ; si elle est définie sur ipv4, libval n'utilise que IPv4. La valeur par défaut est any, ce qui amène libval à envoyer sur n'importe lequel des protocoles disponibles pour le serveur de noms donné.
timeout
Cette option remplace la valeur de délai d'attente du résolveur par défaut par la valeur fournie.
retry
Cette option remplace la valeur de nouvelle tentative du résolveur par défaut par la valeur fournie.
log
Cette option contrôle le niveau de journalisation et la cible de journalisation pour libval. La valeur attendue pour cette option est la même que celle spécifiée pour val_add_log_optarg (voir libval(3)).

Un exemple de construction global-options est donné ci-dessous :

global-options
    trust-oob-answers yes
    edns0-size 4096
    env-policy enable
    app-policy enable
    log 5:stderr
;

SUBSTITUTION DES POLITIQUES RESOLV.CONF

libval recherche d'abord les options du résolveur présentes dans le fichier resolv.conf spécifié au moment de l'exécution de configure. Si ce fichier est absent, libval recherche dans le fichier /etc/resolv.conf les options du résolveur.

Cela permet aux utilisateurs de substituer facilement les politiques du résolveur. Le resolv.conf spécifique au système peut rester inchangé, tandis que toute politique supplémentaire qui pourrait devoir être spécifiée pour libval peut être utilisée dans le fichier resolv.conf fourni par configure.

SUBSTITUTION DES POLITIQUES DNSVAL.CONF

libval fournit trois méthodes pour adapter les politiques dnsval.conf à un environnement donné.

Fichiers include multiples
libval permet d'inclure des fichiers dnsval.conf supplémentaires dans un fichier dnsval.conf donné. L'option est spécifiée comme suit : 
include /chemin/vers/surcharge/fichier/dnsval.conf

Les fichiers sont lus en largeur. Les politiques sont évaluées de manière à donner à la dernière politique définie plus de priorité que les précédentes. Par conséquent, un administrateur peut fournir un dnsval.conf avec des politiques par défaut incluant un autre fichier du répertoire personnel de l'utilisateur. Le fichier inclus peut être utilisé pour substituer les politiques spécifiées dans le fichier dnsval.conf de base.

Politiques basées sur le nom d'application
Si l'option globale app-policy n'est pas désactivée, libval recherche automatiquement une politique dans dnsval.conf avec une valeur d'étiquette construite à partir du nom de l'application. Par exemple, dnsval.conf peut être défini avec des politiques de validation pour l'étiquette foo. L'application foo, lorsqu'elle est exécutée, utilisera la politique définie pour l'étiquette foo lors de son opération de validation.
Politiques via l'environnement
Si l'option globale env-policy n'est pas désactivée, libval examine les variables d'environnement VAL_CONTEXT_LABEL et VAL_LOG_TARGET afin de déterminer l'étiquette de politique du validateur et la cible de journalisation.
Priorité des étiquettes de validateur
Il existe effectivement quatre types d'étiquettes de politique qui peuvent être appliquées par libval : les politiques basées sur le nom d'application, les politiques via VAL_CONTEXT_LABEL, et les étiquettes spécifiées par l'application (NULL ou non-NULL). La priorité d'application de ces étiquettes est définie par les règles suivantes :

1. Si env-policy est « override », utilisez l'étiquette spécifiée dans la variable d'environnement VAL_CONTEXT_LABEL (si elle est définie).

2. Si env-policy est « enable » et que la politique spécifiée par l'application est NULL, utilisez l'étiquette spécifiée dans la variable d'environnement VAL_CONTEXT_LABEL (si elle est définie).

3. Si app-policy est « override », utilisez l'étiquette générée à partir du nom de l'application. Si cette étiquette de politique n'existe pas dans le système de configuration, utilisez la politique par défaut.

4. Si app-policy est « enable » et que la politique spécifiée par l'application est NULL, utilisez l'étiquette générée à partir du nom de l'application.

5. Si pol

icy spécifiée par l'application n'est pas NULL, utilisez cette
