Commande Clean

Commande : clean

Effectue le nettoyage des fichiers temporaires conservés pour les dépôts. Cela inclut toutes les données de ce type laissées par des dépôts désactivés ou supprimés, ainsi que pour les différentes versions de distribution.

dnf clean dbcache
Supprime les fichiers de cache générés à partir des métadonnées du dépôt. Cela force DNF à régénérer les fichiers de cache lors de sa prochaine exécution.
dnf clean expire-cache
Marque les métadonnées du dépôt comme expirées. DNF revalidera le cache pour chaque dépôt lors de sa prochaine utilisation.
dnf clean metadata
Supprime les métadonnées du dépôt. Il s'agit des fichiers que DNF utilise pour déterminer la disponibilité des paquets à distance. L'utilisation de cette option fera que DNF téléchargera toutes les métadonnées lors de sa prochaine exécution.
dnf clean packages
Supprime tous les paquets en cache du système.
dnf clean all
Fait tout ce qui est ci-dessus.

Met à niveau, rétrograde ou conserve les paquets installés sélectionnés pour qu'ils correspondent à la dernière version disponible dans tout dépôt activé. Si aucun paquet n'est spécifié, tous les paquets installés sont considérés.

Commande Group

Commande : group
Alias : grp
Alias obsolètes : groups, grouplist, groupinstall, groupupdate, groupremove, grouperase, groupinfo

Les groupes sont des collections virtuelles de paquets. DNF garde la trace des groupes que l'utilisateur a sélectionnés (« marqués ») pour l'installation et peut manipuler les paquets qui les composent avec des commandes simples.

dnf [options] group [summary] <group-spec>
Affiche un aperçu du nombre de groupes installés et disponibles. Avec une spécification, limite la sortie aux groupes correspondants. summary est la sous-commande de groupes par défaut.
dnf [options] group info <group-spec>
Affiche les listes de paquets d'un groupe. Montre quels paquets sont installés ou disponibles depuis un dépôt quand -v est utilisé.
dnf [options] group install [--with-optional] <group-spec>...
Marque le groupe spécifié comme installé et installe les paquets qu'il contient. Inclut également les paquets optionnels du groupe si --with-optional est spécifié. Tous les paquets obligatoires et par défaut seront installés chaque fois que c'est possible. Les paquets conditionnels sont installés s'ils satisfont leur exigence. Si le groupe est déjà (partiellement) installé, la commande installe les paquets manquants du groupe. Selon la valeur de l'option de configuration obsoletes <#obsoletes-conf-option-label>, l'installation de groupe tient compte des paquets obsolètes.
dnf [options] group list <group-spec>...
Liste tous les groupes correspondants, qu'ils soient parmi les groupes installés ou disponibles. Si rien n'est spécifié, liste tous les groupes connus. --installed et --available réduisent la liste demandée. Les enregistrements sont ordonnés par la balise display_order définie dans le fichier comps.xml. Fournit une liste de tous les groupes cachés en utilisant l'option --hidden. Fournit les identifiants de groupe quand les options -v ou --ids sont utilisées.
dnf [options] group remove <group-spec>...
Marque le groupe comme supprimé et supprime du système les paquets de ce groupe qui n'appartiennent pas à un autre groupe installé et qui n'ont pas été installés explicitement par l'utilisateur.
dnf [options] group upgrade <group-spec>...
Met à niveau les paquets du groupe et met à niveau le groupe lui-même. Ce dernier comprend l'installation des paquets qui ont été ajoutés au groupe par la distribution et la suppression des paquets qui ont été retirés du groupe, pour autant qu'ils n'aient pas été installés explicitement par l'utilisateur.

Les groupes peuvent aussi être marqués comme installés ou supprimés sans manipuler physiquement aucun paquet :

dnf [options] group mark install <group-spec>...
Marque le groupe spécifié comme installé. Aucun paquet ne sera installé par cette commande, mais le groupe est alors considéré comme installé.
dnf [options] group mark remove <group-spec>...
Marque le groupe spécifié comme supprimé. Aucun paquet ne sera supprimé par cette commande.

Voir aussi Politique de remplacement des fichiers de configuration.

Commande History

Commande : history
Alias : hist

La commande history permet à l'utilisateur de voir ce qui s'est passé lors des transactions passées et d'agir en fonction de cette information (en supposant que l'option de configuration history_record est définie).

dnf history [list] [--reverse] [<spec>...]
L'action history par défaut est de lister les informations sur les transactions données dans un tableau. Chaque <spec> peut être soit un <transaction-spec>, qui spécifie directement une transaction, soit un <transaction-spec>..<transaction-spec>, qui spécifie une plage de transactions, soit un <package-name-spec>, qui spécifie une transaction par un paquet qu'elle a manipulé. Quand aucune transaction n'est spécifiée, liste toutes les transactions connues.

Notez que les transactions transitoires (voir --transient) seront listées même si elles ne font pas de changements persistants aux fichiers sous /usr ni à la base de données RPM.

La colonne « Action(s) » liste chaque type d'action effectuée lors de la transaction. Les valeurs possibles sont :

  • Install (I) : un nouveau paquet a été installé sur le système
  • Downgrade (D) : une version plus ancienne d'un paquet a remplacé la version précédemment installée
  • Obsolete (O) : un paquet obsolète a été remplacé par un nouveau paquet
  • Upgrade (U) : une version plus récente du paquet a remplacé la version précédemment installée
  • Remove (E) : un paquet a été supprimé du système
  • Reinstall (R) : un paquet a été réinstallé avec la même version
  • Reason change (C) : un paquet a été conservé sur le système mais sa raison d'installation a changé

La colonne « Altered » liste le nombre d'actions effectuées dans chaque transaction, éventuellement suivi d'un ou deux des symboles suivants :

  • >: La base de données RPM a été modifiée, en dehors de DNF, après la transaction
  • <: La base de données RPM a été modifiée, en dehors de DNF, avant la transaction
  • *: La transaction a été interrompue avant son achèvement
  • #: La transaction s'est terminée, mais avec un statut non nul
  • E: La transaction s'est terminée avec succès, mais a produit des avertissements/erreurs
--reverse
L'ordre de la sortie de history list est imprimé en ordre inverse.
dnf history info [<spec>...]
Décrit les transactions données. La signification de <spec> est la même que dans la Commande History List. Quand aucune transaction n'est spécifiée, décrit ce qui s'est passé lors de la dernière transaction.
dnf history redo <transaction-spec>|<package-file-spec>
Répète la transaction spécifiée. Utilise la dernière transaction (avec l'identifiant le plus élevé) si plus d'une transaction est trouvée pour le <package-file-spec> donné. S'il n'est pas possible de répéter certaines opérations en raison de l'état actuel de la base de données RPM, la transaction ne sera pas répétée.
<a class="permalink" href="#dnf~27">dnf history replay [--ignore-installed] [--ignore-extras] [--skip-unavailable] <filename>
Rejouer une transaction stockée dans le fichier <filename> par la commande History Store. Le rejouement effectuera exactement les mêmes opérations sur les paquets que dans la transaction d'origine et renverra une erreur en cas de différences dans les paquets installés ou leurs versions. Voir aussi la spécification du format JSON de transaction <#transaction-json-label> du format de fichier.
--ignore-installed
Ne pas vérifier que les paquets installés sont dans le même état que ceux enregistrés dans la transaction. Par exemple, s'il y a une mise à niveau foo-1.0 -> foo-2.0 enregistrée dans la transaction, mais qu'il y a foo-1.1 installé sur le système cible.
--ignore-extras
Ne pas vérifier les paquets supplémentaires ajoutés à la transaction sur le système cible. Par exemple, le système cible peut ne pas avoir certaines dépendances qui étaient installées sur le système source. Le rejouement échoue par défaut dans ce cas, car la transaction ne serait pas la même.
--skip-unavailable
Si certains paquets enregistrés dans la transaction ne sont pas disponibles sur le système cible, les ignorer plutôt que d'échouer.
dnf history rollback <transaction-spec>|<package-file-spec>
Annuler toutes les transactions effectuées après la transaction spécifiée. Utilise la dernière transaction (avec l'ID le plus élevé) si plus d'une transaction est trouvée pour une <package-file-spec> donnée. S'il n'est pas possible d'annuler certaines transactions en raison de l'état actuel de la RPMDB, aucune transaction ne sera annulée.
dnf history store [--output <output-file>] <transaction-spec>
Enregistrer la transaction spécifiée par <transaction-spec>. La transaction peut être rejouée plus tard par la commande History Replay.

Avertissement : le format de transaction enregistré est considéré comme instable et peut changer à tout moment. Il fonctionnera si la même version de dnf est utilisée pour enregistrer et rejouer (ou entre les versions tant qu'il reste le même).

-o <output-file>, --output=<output-file> Enregistrer la transaction sérialisée dans <output-file. Par défaut, c'est transaction.json.

dnf history undo <transaction-spec>|<package-file-spec>
Effectuer l'opération opposée à toutes les opérations effectuées dans la transaction spécifiée. Utilise la dernière transaction (avec l'ID le plus élevé) si plus d'une transaction est trouvée pour une <package-file-spec> donnée. S'il n'est pas possible d'annuler certaines opérations en raison de l'état actuel de la RPMDB, la transaction ne sera pas annulée.
dnf history userinstalled
Afficher tous les paquets installés par l'utilisateur, installés depuis un groupe ou un profil de module, et les paquets installés en dehors de DNF. C'est-à-dire, il liste les paquets qui resteront sur le système lorsque la commande Autoremove ou la commande Remove avec clean_requirements_on_remove l'option de configuration définie à True est exécutée. Notez que les mêmes résultats peuvent être obtenus avec dnf repoquery --userinstalled, et la commande repoquery est plus puissante pour le formatage de la sortie.

Cette commande ne force pas par défaut une synchronisation des métadonnées expirées, sauf pour les sous-commandes redo, rollback et undo. Voir aussi Synchronisation des métadonnées et Politique de remplacement des fichiers de configuration.

Commande Install

Commande : install
Alias : in
Alias pour la correspondance NEVRA explicite : install-n, install-na, install-nevra
Alias obsolètes : localinstall
dnf [options] install <spec>...
S'assurer que les paquets donnés et leurs dépendances sont installés sur le système. Chaque <spec> peut être soit un <package-spec>, soit un @<module-spec>, soit un @<group-spec>. Voir Exemples d'installation. Si un paquet ou une fourniture donnée ne peut pas être installé (et n'est pas déjà installé), le code de sortie sera non nul. Si le <spec> correspond à la fois à un @<module-spec> et à un @<group-spec>, seul le module est installé.

Lorsqu'un <package-spec> spécifiant la version exacte du paquet est donné, DNF installera la version souhaitée, quelle que soit la version du paquet déjà installée. L'ancienne version du paquet sera supprimée dans le cas d'un paquet non installonly.

D'un autre côté, si <package-spec> ne spécifie qu'un nom, DNF prend également en compte les paquets qui le rendent obsolète lors du choix du paquet à installer. Ce comportement est spécifique à la commande install. Notez que cela peut entraîner des résultats apparemment inattendus si un paquet a plusieurs versions et qu'une version plus ancienne est rendue obsolète. Cela crée une division dans le chemin de mise à niveau et les deux voies sont considérées comme correctes, le paquet résultant est simplement choisi par ordre lexicographique.

Il existe aussi quelques commandes d'installation spécifiques install-n, install-na et install-nevra qui permettent la spécification d'un argument exact au format NEVRA. Par conséquent, <spec> ne sera pas mis en correspondance avec les fournitures et les fournitures de fichiers.

Voir aussi Politique de remplacement des fichiers de configuration.

Exemples d'installation

dnf install tito
Installer le paquet tito (tito est le nom du paquet).
dnf install ~/Downloads/tito-0.6.2-1.fc22.noarch.rpm
Installer un fichier rpm local tito-0.6.2-1.fc22.noarch.rpm depuis le répertoire ~/Downloads/.
dnf install tito-0.5.6-1.fc22
Installer le paquet avec une version spécifique. Si le paquet est déjà installé, il essaiera automatiquement de rétrograder ou de mettre à niveau vers la version spécifique.
dnf --best install tito
Installer la dernière version disponible du paquet. Si le paquet est déjà installé, il essaiera de le mettre à niveau automatiquement vers la dernière version. Si la dernière version du paquet ne peut pas être installée, l'installation échouera.
dnf install vim
DNF reconnaîtra automatiquement que vim n'est pas un nom de paquet, mais cherchera et installera un paquet qui fournit vim avec toutes les dépendances requises. Remarque : La correspondance du nom de paquet a la priorité sur la correspondance de la fourniture du paquet.
dnf install https://kojipkgs.fedoraproject.org//packages/tito/0.6.0/1.fc22/noarch/tito-0.6.0-1.fc22.noarch.rpm
Installer un paquet directement depuis une URL.
dnf install '@docker'
Installer tous les profils par défaut du module 'docker' et leurs RPM. Les flux de module sont activés en conséquence.
dnf install '@Web Server'
Installer le groupe environnemental 'Web Server'.
dnf install /usr/bin/rpmsign
Installer un paquet qui fournit le fichier /usr/bin/rpmsign.
dnf -y install tito --setopt=install_weak_deps=False
Installer le paquet tito (tito est le nom du paquet) sans les dépendances faibles. Les dépendances faibles ne sont pas requises pour la fonctionnalité de base du paquet, mais elles améliorent le paquet d'origine (comme la documentation étendue, les plugins, les fonctions supplémentaires, etc.).
dnf install --advisory=FEDORA-2018-b7b99fe852 \*
Installer tous les paquets qui appartiennent à l'avis de sécurité "FEDORA-2018-b7b99fe852".

Commande Module

Commande : module

Attention :

La modularité est dépréciée et ses fonctionnalités seront supprimées dans une future version de DNF5.

La vue d'ensemble de la modularité est disponible dans la page de manuel dnf.modularity(7) <#modularity-label>. Les sous-commandes de module acceptent des arguments <module-spec>... qui spécifient des modules ou des profils.

dnf [options] module install <module-spec>...
Installe les profils de module, y compris leurs paquets. Dans le cas où aucun profil n'est fourni, tous les profils par défaut sont installés. Les flux de modules sont activés en conséquence.

Cette commande ne peut pas être utilisée pour changer les flux de modules. Utilisez la commande dnf module switch-to pour cela.

dnf [options] module update <module-spec>...
Met à jour les paquets associés à un flux de modules actif, éventuellement limité à un profil. Si le profile_name est fourni, seuls les paquets référencés par ce profil seront mis à jour.
dnf [options] module switch-to <module-spec>...
Passe à ou active un flux de modules, change les versions des paquets installés vers les versions fournies par le nouveau flux, et supprime les paquets de l'ancien flux qui ne sont plus disponibles. Il met également à jour les profils installés s'ils sont disponibles pour le nouveau flux. Lorsqu'un profil a été fourni, il installe ce profil et ne met à jour aucun profil déjà installé.

Cette commande peut être utilisée comme une version plus puissante de la commande dnf module enable, qui non seulement active les modules, mais effectue également une distrosync sur tous les paquets modulaires des modules activés.

Elle peut également être utilisée comme une version plus puissante de la commande dnf module install, mais elle nécessite de spécifier les profils qui doivent être installés, car la commande switch-to n'utilise pas les profils par défaut. La commande switch-to n'installe pas seulement des profils, elle effectue également une distrosync sur tous les paquets modulaires du module installé.

dnf [options] module remove <module-spec>...
Supprime les profils de module installés, y compris les paquets qui ont été installés avec la commande dnf module install. Ne supprimera pas les paquets requis par d'autres profils de module installés ou par d'autres paquets installés par l'utilisateur. Dans le cas où aucun profil n'est fourni, tous les profils installés sont supprimés.
dnf [options] module remove --all <module-spec>...
Supprime les profils de module installés, y compris les paquets qui ont été installés avec la commande dnf module install. Avec l'option --all, elle supprime en plus tous les paquets dont les noms sont fournis par les modules spécifiés. Les paquets requis par d'autres profils de module installés et les paquets dont les noms sont également fournis par un autre module ne sont pas supprimés.
dnf [options] module enable <module-spec>...
Active un flux de modules et rend les RPM du flux disponibles dans l'ensemble des paquets.

Les dépendances modulaires sont résolues, les dépendances vérifiées et également activées récursivement. En cas de problème de dépendance modulaire, l'opération sera rejetée. Pour effectuer l'action quand même, veuillez utiliser l'option --skip-broken.

Cette commande ne peut pas être utilisée pour changer les flux de modules. Utilisez la commande dnf module switch-to pour cela.

dnf [options] module disable <module-name>...
Désactive un module. Tous les flux de modules associés deviendront indisponibles. Par conséquent, tous les profils installés seront supprimés et les RPM du module deviendront indisponibles dans l'ensemble des paquets. En cas de problème de dépendance modulaire, l'opération sera rejetée. Pour effectuer l'action quand même, veuillez utiliser l'option --skip-broken.
dnf [options] module reset <module-name>...
Réinitialise l'état du module afin qu'il ne soit plus activé ni désactivé. Par conséquent, tous les profils installés seront supprimés et seuls les RPM du flux par défaut seront disponibles dans l'ensemble des paquets.
dnf [options] module provides <package-name-spec>...
Liste tous les paquets modulaires correspondant à <package-name-spec> de tous les modules (y compris désactivés), ainsi que les modules et flux auxquels ils appartiennent.
dnf [options] module list [--all] [module_name...]
Liste tous les flux de modules, leurs profils et leurs états (activé, désactivé, par défaut).
dnf [options] module list --enabled [module_name...]
Liste les flux de modules qui sont activés.
dnf [options] module list --disabled [module_name...]
Liste les flux de modules qui sont désactivés.
dnf [options] module list --installed [module_name...]
Liste les flux de modules avec les profils installés.
dnf [options] module info <module-spec>...
Affiche des informations détaillées sur le flux de modules donné.
dnf [options] module info --profile <module-spec>...
Affiche des informations détaillées sur les profils de modules donnés.
dnf [options] module repoquery <module-spec>...
Liste tous les paquets disponibles appartenant aux modules sélectionnés.
dnf [options] module repoquery --available <module-spec>...
Liste tous les paquets disponibles appartenant aux modules sélectionnés.
dnf [options] module repoquery --installed <module-spec>...
Liste tous les paquets installés portant le même nom que les paquets appartenant aux modules sélectionnés.

Commande Provides

Commande : provides
Alias : prov, whatprovides, wp
dnf [options] provides <provide-spec>
Trouve les paquets qui fournissent le <provide-spec> donné. Ceci est utile lorsqu'on connaît un nom de fichier et que l'on veut trouver quel paquet (instal
activé ou non) fournit ce fichier. Le <provide-spec> est recherché progressivement aux emplacements suivants :
1.
Le <provide-spec> est comparé à toutes les fournitures de fichiers de tous les paquets disponibles :
$ dnf provides /usr/bin/gzip
gzip-1.9-9.fc29.x86_64 : The GNU data compression program
Matched from:
Filename    : /usr/bin/gzip
2.
Ensuite, toutes les fournitures de tous les paquets disponibles sont recherchées :
$ dnf provides "gzip(x86-64)"
gzip-1.9-9.fc29.x86_64 : The GNU data compression program
Matched from:
Provide     : gzip(x86-64) = 1.9-9.fc29
3.
DNF suppose que le <provide-spec> est une commande système, lui préfixe /usr/bin/, /usr/sbin/ (un à la fois) et relance la recherche des fournitures de fichiers. Pour des raisons de compatibilité (paquets qui n'ont pas effectué UsrMove), les préfixes /bin et /sbin sont également recherchés :
$ dnf provides zless
gzip-1.9-9.fc29.x86_64 : The GNU data compression program
Matched from:
Filename    : /usr/bin/zless
4.
Si cette dernière étape échoue également, DNF renvoie « Error: No Matches found ».

Cette commande ne force pas par défaut la synchronisation des métadonnées expirées. Voir aussi Synchronisation des métadonnées.

Commande Remove

Commande : remove
Alias : rm
Alias pour la correspondance NEVRA explicite : remove-n, remove-na, remove-nevra

dnf [options] remove <package-spec>...
Supprime les paquets spécifiés du système ainsi que tous les paquets dépendant des paquets supprimés. Chaque <spec> peut être soit un <package-spec>, qui spécifie directement un paquet, soit un @<group-spec>, qui spécifie un groupe (d'environnement) qui le contient. Si clean_requirements_on_remove est activé (par défaut), supprime également toutes les dépendances qui ne sont plus nécessaires.
dnf [options] remove --duplicates
Supprime les anciennes versions des paquets en double. Pour assurer l'intégrité du système, il réinstalle le paquet le plus récent. Dans certains cas, la commande ne peut pas résoudre les conflits. Dans de tels cas, la commande shell dnf avec les sous-commandes remove --duplicates et upgrade de dnf-shell pourrait aider.

Supprime les anciens paquets installonly, en ne conservant que les versions les plus récentes et la version du noyau en cours d'exécution.

Il existe également quelques commandes remove spécifiques remove-n, remove-na et remove-nevra qui permettent de spécifier un argument exact au format NEVRA. Par conséquent, <spec> ne sera pas comparé aux fournitures ni aux fournitures de fichiers.

Commande Updateinfo

Commande : updateinfo
Alias : upif
Alias obsolètes : list-updateinfo, list-security, list-sec, info-updateinfo, info-security, info-sec, summary-updateinfo

Affiche les informations sur les avis de mise à jour.

Selon le type de sortie, DNF affiche soit simplement le nombre de types d'avis (omis ou --summary), la liste des avis (--list) ou des informations détaillées (--info). L'option -v étend la sortie. Lorsqu'elle est utilisée avec --info, les informations sont encore plus détaillées. Lorsqu'elle est utilisée avec --list, une colonne supplémentaire avec la date de la dernière mise à jour de l'avis est ajoutée.

Si spécifié, et si ni l'ID, ni le type (bugfix, enhancement, security/sec) ni le nom d'un paquet d'un avis ne correspond à <spec>, l'avis n'est pas pris en compte. La correspondance est sensible à la casse et, dans le cas des ID d'avis et des noms de paquets, le globbing est pris en charge.

SPÉCIFICATION DES PAQUETS

De nombreuses commandes prennent un paramètre <package-spec> qui sélectionne un paquet pour l'opération. L'argument <package-spec> est comparé aux NEVRAs des paquets, aux provides et aux file provides.

<package-file-spec> est similaire à <package-spec>, sauf que la correspondance des provides n'est pas effectuée. Par conséquent, <package-file-spec> n'est comparé qu'aux NEVRAs et aux file provides.

<package-name-spec> n'est comparé qu'aux NEVRAs.

Globs

La spécification de paquet prend en charge la même correspondance de motifs glob que le shell, dans les trois cas mentionnés ci-dessus, elle correspond aux NEVRAs, aux provides et aux file provides.

Les motifs suivants sont pris en charge :

*
Correspond à un nombre quelconque de caractères.
?
Correspond à un seul caractère.
[]
Correspond à l'un des caractères inclus. Une paire de caractères séparés par un tiret représente une expression de plage ; tout caractère compris entre ces deux caractères, inclus, correspond. Si le premier caractère après le [ est un ! ou un ^ , alors tout caractère non inclus correspond.

Note : Les accolades ({}) ne sont pas prises en charge. Vous pouvez toujours les utiliser dans les shells qui les prennent en charge et laisser le shell faire l'expansion, mais s'ils sont entre guillemets ou échappés, dnf ne les expandera pas.

Correspondance NEVRA

Lors de la correspondance avec les NEVRAs, la correspondance partielle est prise en charge. DNF essaie de faire correspondre la spec avec la liste suivante de formes de NEVRA (dans l'ordre décroissant de priorité) :

  • name-[epoch:]version-release.arch
  • name.arch
  • name
  • name-[epoch:]version-release
  • name-[epoch:]version

Notez que name peut en général contenir des tirets (par ex. package-with-dashes).

La première forme qui correspond à des paquets est utilisée et les formes restantes ne sont pas essayées. Si aucune des formes ne correspond à des paquets, une tentative est faite de faire correspondre le <package-spec> avec les NEVRAs complets des paquets. Cela n'est pertinent que si des globs sont présents dans le <package-spec>.

<package-spec> correspond aux NEVRAs de la même manière que <package-name-spec> , mais si la correspondance avec les NEVRAs échoue, il essaie également de faire correspondre les provides et les file provides des paquets.

Vous pouvez spécifier des globs comme partie de n'importe lequel des cinq composants du NEVRA. Vous pouvez également spécifier un motif glob pour correspondre sur plusieurs composants du NEVRA (en d'autres termes, pour correspondre à travers les séparateurs du NEVRA). Dans ce cas, cependant, vous devez écrire la spec pour qu'elle corresponde aux NEVRAs complets des paquets, car il n'est pas possible de diviser une telle spec en formes de NEVRA.

Spécification explicite de la correspondance NEVRA

Certaines commandes (autoremove, install, remove et repoquery) ont également des alias avec les suffixes -n, -na et -nevra qui permettent de spécifier explicitement comment analyser les arguments :

  • Commande install-n ne correspond qu'à name.
  • Commande install-na ne correspond qu'à name.arch.
  • Commande install-nevra ne correspond qu'à name-[epoch:]version-release.arch.

SPÉCIFICATION DES PROVIDES

<provide-spec> dans les descriptions de commandes signifie que la commande opère sur les paquets fournissant la spec donnée. Cela peut être soit un provide explicite, un provide implicite (c'est-à-dire le nom du paquet) ou un file provide. La sélection est sensible à la casse et le globbing est pris en charge.

Spécification des file provides

Si une spec commence par / ou */, elle est considérée comme un file provide potentiel.

SPÉCIFICATION DES GROUPES

<group-spec> permet de sélectionner les groupes (d'environnement) sur lesquels une opération particulière doit travailler. C'est une chaîne insensible à la casse (supportant les caractères de globbing) qui est comparée à l'ID d'un groupe, au nom canonique et au nom traduit dans la locale LC_MESSAGES actuelle (si possible).

SPÉCIFICATION DES MODULES

<module-spec> permet de sélectionner les modules ou les profils sur lesquels une opération particulière doit travailler.

Il est de la forme NAME:STREAM:VERSION:CONTEXT:ARCH/PROFILE et les formes partielles prises en charge sont les suivantes :

  • NOM
  • NOM:FLUX
  • NOM:FLUX:VERSION
  • NOM:FLUX:VERSION:CONTEXTE
  • toutes les combinaisons ci-dessus avec ::ARCH (par ex. NOM::ARCH)
  • NOM:FLUX:VERSION:CONTEXTE:ARCH
  • toutes les combinaisons ci-dessus avec /PROFIL (par ex. NOM/PROFIL)

Si le flux n'est pas spécifié, le flux activé ou le flux par défaut est utilisé, dans cet ordre. Si le profil n'est pas spécifié, le profil par défaut du système ou le profil « default » est utilisé.

SPÉCIFICATION DES TRANSACTIONS

<transaction-spec> peut prendre plusieurs formes. S'il s'agit d'un entier, il spécifie un identifiant de transaction. Spécifier last est équivalent à spécifier l'identifiant de la transaction la plus récente. La dernière forme est last-<offset>, où <offset> est un entier positif. Elle spécifie la transaction précédant la plus récente d'un décalage donné.

FILTRAGE DES PAQUETS

Le filtrage des paquets exclut des paquets de l'ensemble des paquets disponibles, les rendant invisibles pour la plupart des commandes dnf. Ils ne peuvent pas être utilisés dans une transaction. Les paquets peuvent être filtrés soit par le filtrage par exclusion, soit par le filtrage modulaire.

Filtrage par exclusion

Le filtrage par exclusion est un mécanisme utilisé par un utilisateur ou par un greffon DNF pour modifier l'ensemble des paquets disponibles. Le filtrage par exclusion peut être modifié par les options de configuration includepkgs <#include-label> ou excludepkgs <#exclude-label> dans les fichiers de configuration <#conf-ref-label>. L'option de ligne de commande --disableexcludes peut être utilisée pour annuler les exclusions provenant des fichiers de configuration. En plus des exclusions configurées par l'utilisateur, les greffons peuvent également étendre l'ensemble des paquets exclus. Pour désactiver les exclusions d'un greffon DNF, vous pouvez utiliser l'option de ligne de commande --disableplugin.

Pour désactiver toutes les exclusions, par ex. pour la commande install, vous pouvez utiliser la combinaison suivante d'options de ligne de commande :

dnf --disableexcludes=all --disableplugin="*" install bash

Filtrage modulaire

Veuillez consulter la documentation sur la modularité <#modularity-label> pour plus de détails sur le fonctionnement du filtrage modulaire.

Avec la modularité, seuls les paquets RPM provenant des flux de modules actifs sont inclus dans l'ensemble des paquets disponibles. Les paquets RPM provenant des flux de modules inactifs , ainsi que les paquets non modulaires portant le même nom ou fournissant les mêmes éléments qu'un paquet d'un flux de modules actif , sont filtrés. Le filtrage modulaire n'est pas appliqué aux paquets ajoutés depuis la ligne de commande, aux paquets installés, ni aux paquets des dépôts ayant module_hotfixes=true dans leur fichier .repo .

La désactivation du filtrage modulaire n'est pas recommandée, car elle pourrait mettre le système dans un état instable. Pour désactiver le filtrage modulaire pour un dépôt particulier, spécifiez module_hotfixes=true dans le fichier .repo ou utilisez --setopt=<repo_id>.module_hotfixes=true.

Pour découvrir le module qui contient un paquet exclu, utilisez dnf module provides.

SYNCHRONISATION DES MÉTADONNÉES

Le bon fonctionnement de DNF dépend de l'accès à des données à jour provenant de tous les dépôts activés, mais contacter les miroirs distants à chaque opération le ralentit considérablement et consomme de la bande passante à la fois pour le client et le fournisseur du dépôt. L'option de configuration du dépôt metadata_expire <#metadata-expire-label> (voir dnf.conf(5)) est utilisée par DNF pour déterminer si une copie locale particulière des données du dépôt doit être resynchronisée. Il est crucial que les fournisseurs de dépôts définissent correctement cette option, à savoir à une valeur garantissant que si des métadonnées particulières étaient disponibles à temps T sur le serveur, alors tous les paquets qu'elles référencent seront toujours disponibles pour le téléchargement depuis le serveur à temps T + metadata_expire.

Pour réduire davantage la charge sur la bande passante, certaines des commandes pour lesquelles des métadonnées à jour ne sont pas critiques (par ex. la commande list ) ne vérifient pas si un dépôt est expiré et, chaque fois qu'une version quelconque en est localement disponible pour le compte de l'utilisateur, elle sera utilisée. Pour une utilisation en tant que non-root, voir aussi l'option --cacheonly . Notez que dans toutes les situations, l' utilisateur peut forcer la synchronisation de tous les dépôts activés avec l'option --refresh .

POLITIQUE DE REMPLACEMENT DES FICHIERS DE CONFIGURATION

Les paquets mis à jour pourraient remplacer les anciens fichiers de configuration modifiés par les nouveaux ou conserver les anciens fichiers. Aucun des fichiers n'est effectivement remplacé. Pour les fichiers en conflit, RPM ajoute un suffixe au nom d'origine. Quel fichier doit conserver le vrai nom après la transaction n'est pas contrôlé par le gestionnaire de paquets mais est spécifié par chaque paquet lui-même, en suivant les directives d'empaquetage.
