DESCRIPTIO

N

Les sources d'événements de dispatch peuvent être utilisées pour surveiller divers objets et événements système, y compris les descripteurs de fichiers, les ports mach, les processus, les nœuds de système de fichiers virtuel, la livraison de signaux et les

minuteurs.

Lorsqu'un changement d'état se produit, la source de dispatch soumettra son bloc de gestionnaire d'événements à sa file d'attente

cible.

La fonction dispatch_source_create() crée un nouvel objet source de dispatch qui peut être conservé et libéré à l'aide des appels à dispatch_retain() et dispatch_release() respectivement. Le paramètre queue spécifie la file d'attente cible du nouvel objet source ; elle sera conservée par l'objet source. Passez la constante DISPATCH_TARGET_QUEUE_DEFAULT pour utiliser la file d'attente cible par défaut (la file d'attente concurrentielle globale de priorité par défaut)

.

Les sources nouvellement créées le sont dans un état suspendu. Après que la source a été configurée en définissant un gestionnaire d'événements, un gestionnaire d'annulation, un gestionnaire d'enregistrement, un contexte, etc., la source doit être activée par un appel à dispatch_resume() avant que des événements soient

livrés.

Les sources de dispatch peuvent être de l'un des types suivants

Les arguments handle et mask de dispatch_source_create() ainsi que les valeurs de retour des fonctions dispatch_source_get_handle(), dispatch_source_get_mask() et dispatch_source_get_data() doivent être interprétés en fonction du type de la source de

dispatch.

La fonction dispatch_source_get_handle() renvoie le descripteur sous-jacent de la source de dispatch (c'est-à-dire le descripteur de fichier, le port mach, l'identifiant de processus, etc.). Le résultat de cette fonction peut être converti directement vers le type

sous-jacent.

La fonction dispatch_source_get_mask() renvoie l'ensemble des drapeaux qui ont été spécifiés lors de la création de la source via l'argument mask

La fonction dispatch_source_get_data() renvoie les données actuellement en attente pour la source de dispatch. Cette fonction ne doit être appelée que depuis le gestionnaire d'événements de la source. Le résultat de l'appel de cette fonction depuis tout autre contexte est

indéfini.

SOURCE GESTIONNAIRES

D'ÉVÉNEMENTS

Afin de recevoir des événements de la source de dispatch, un gestionnaire d'événements doit être spécifié via dispatch_source_set_event_handler(). Le bloc du gestionnaire d'événements est soumis à la file d'attente cible de la source lorsque l'état du descripteur système sous-jacent change, ou lorsqu'un événement se produit. Si une source est reprise sans qu'aucun bloc de gestionnaire d'événements ne soit défini, les événements seront silencieusement ignorés. Si le bloc du gestionnaire d'événements est modifié pendant que la source est suspendue, ou depuis un bloc s'exécutant sur une file d'attente sérielle qui est la file d'attente cible de la source, alors la prochaine invocation du gestionnaire d'événements utilisera le nouveau

bloc.

Les sources de dispatch peuvent être suspendues ou reprises indépendamment de leur file d'attente cible à l'aide de dispatch_suspend() et dispatch_resume() sur la source de dispatch directement. Les données décrivant les événements qui se produisent pendant qu'une source est suspendue sont regroupées et délivrées une fois la source

reprise.

Le bloc de gestionnaire n'a pas besoin d'être réentrant, car il n'est pas soumis à nouveau à la cible tant que toute invocation précédente pour cette source de dispatch n'est pas terminée. Lorsque le gestionnaire est défini, la source de dispatch va effectuer un Block_copy() sur le bloc de gestio

nnaire.

Pour annuler le gestionnaire d'événements, appelez dispatch_source_set_event_handler_f() et passez NULL comme fonction. Cela annule le gestionnaire d'événements que le gestionnaire soit un pointeur de fonction ou un bloc. Les gestionnaires d'enregistrement e

t d'annulation (voir ci-dessous) peuvent être annulés de la même manière,
mais comme indiqué ci-dessous, un gestionnaire d'annulation peut être requis.

ENREGISTREMEN

T

Lorsque dispatch_resume() est appelé sur une source suspendue ou nouvellement créée, il peut y avoir un court délai avant que la source soit prête à recevoir des événements du gestionnaire de système sous-jacent. Pendant ce délai, le gestionnaire d'événements ne sera pas invoqué et des événements seront

manqués.

Une fois que la source de dispatch est enregistrée avec le système sous-jacent et est prête à traiter tous les événements, son gestionnaire d'enregistrement optionnel sera soumis à sa file cible. Ce gestionnaire d'enregistrement peut être spécifié via dispatch_source_set_registrat

ion_handler().

Le gestionnaire d'événements ne sera pas appelé avant la fin du gestion

naire d'enregistrement. Si la source est annulée (voir ci-dessous) avant d'
être enregistrée, son gestionnaire d'enregistrement ne sera pas appelé.

ANNULATIO

N

La fonction dispatch_source_cancel() annule de manière asynchrone la source de dispatch, empêchant toute invocation ultérieure de son bloc de gestionnaire d'événements. L'annulation n'interrompt pas un bloc de gestionnaire en cours d'exécution (non préemptive). Si une source est annulée avant la première fois qu'elle est reprise, son gestionnaire d'événements ne sera jamais appelé. (Dans ce cas, notez que la source doit être reprise avant de pouvoir être libérée.

)

La fonction dispatch_source_testcancel() peut être utilisée pour déterminer si la source spécifiée a été annulée. Une valeur non nulle sera retournée si la source est

annulée.

Lorsqu'une source de dispatch est annulée, son gestionnaire d'annulation optionnel sera soumis à sa file cible. Le gestionnaire d'annulation peut être spécifié via dispatch_source_set_cancel_handler(). Ce gestionnaire d'annulation n'est invoqué qu'une seule fois, et seulement comme conséquence directe de l'appel à dispatch_source_c

ancel().

Important : un gestionnaire d'annulation est requis pour les sources basées sur des descripteurs de fichier et des ports mach afin de fermer le descripteur ou de détruire le port en toute sécurité. Fermer le descripteur ou le port avant que le gestionnaire d'annulation s'exécute peut entraîne

r une condition de course : si un nouveau descripteur est alloué avec la même valeur que le descripteur récemment fermé alors que le gestionnaire
d'événements de la source est toujours en cours d'exécution, le gestionnaire d'événements peut lire/écrire des données dans le mauvais descripteur.

La section suivante contient un résumé des types d'événements de dispatch pris en charge et l'interprétation de leurs paramètres et des données

DISPATCH_SOURCE_TYPE_DATA_ADD, DISPATCH_SOURCE_TYPE_DATA_OR, DISPATCH_SOURCE_TYPE_DATA_REPLAC

E

Les sources de ce type permettent aux applications de déclencher manuellement le gestionnaire d'événements de la source via un appel à dispatch_source_merge_data(). Les données seront fusionnées avec les données en attente de la source via un ajout atomique ou un OU bit à bit atomique, ou un remplacement direct (selon le type de la source), et le bloc de gestionnaire d'événements sera soumis à la file cible de la source. Les données sont définies par l'application. Ces sources n'ont pas de handle ni de mask et zéro doit être

utilisé.

Le bloc de gestionnaire d'événements sera soumis à la file cible lorsqu'un message sur le port mach attend d'être

D

Les sources de ce type surveillent les descripteurs de fichier pour des données en attente. Le handle est le descripteur de fichier (int) à surveiller et le mask n'est pas utilisé et doit être

Les données retournées par dispatch_source_get_data() sont un nombre estimé d'octets disponibles pour être lus depuis le descripteur. Cette estimation doit être traitée comme une taille de tampon de lecture minimale suggérée. Il n'y a aucune garantie qu'une lecture complète de cette taille sera

Il est fortement recommandé aux utilisateurs de ce type de source d'effectuer des entrées/sorties non bloquantes et de gérer toute lecture tronquée ou condition d'erreur qui peut survenir. fichier.
