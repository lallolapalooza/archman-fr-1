distcc(1) Manuel des commandes générales distcc(1)

NOM

distcc - compilateur C/C++/ObjC distribué avec extensions distcc-pump

SYNOPSIS

distcc <compilateur> [OPTIONS COMPILATEUR]

distcc [OPTIONS COMPILATEUR]

<compilateur> [OPTIONS COMPILATEUR]

distcc [OPTIONS DISTCC]

DESCRIPTION

distcc distribue la compilation du code C sur plusieurs machines d'un réseau. distcc devrait toujours produire les mêmes résultats qu'une compilation locale, il est simple à installer et à utiliser, et il est souvent beaucoup plus rapide qu'une compilation locale.

Cette version intègre le distcc simple ainsi qu'une amélioration appelée mode pompe ou distcc-pump.

Pour chaque tâche, distcc en mode simple envoie le code source pré-traité complet et les arguments du compilateur sur le réseau, du client vers un serveur de compilation. En mode pompe, distcc envoie le code source et les fichiers d'en-tête inclus récursivement (à l'exception de ceux des répertoires d'en-têtes système par défaut), de sorte que le pré-traitement et la compilation puissent avoir lieu sur les serveurs de compilation. Cela accélère la livraison des compilations jusqu'à un ordre de grandeur par rapport au distcc simple.

La compilation est pilotée par une machine cliente, qui est typiquement le poste de travail ou l'ordinateur portable du développeur. Le client distcc s'exécute sur cette machine, tout comme make, le préprocesseur (si le mode pompe de distcc n'est pas utilisé), l'éditeur de liens, et d'autres étapes du processus de construction. Un nombre quelconque de machines volontaires agissent comme serveurs de compilation et aident le client à construire le programme, en exécutant le démon distccd(1), le compilateur C et l'assembleur selon les besoins.

distcc peut fonctionner via des sockets TCP (par défaut sur le port 3632), ou via une commande de tunnel comme ssh(1). Pour les connexions TCP, les volontaires doivent exécuter le démon distccd(1) directement ou depuis inetd. Pour les connexions SSH, distccd doit être installé mais ne doit **pas** écouter les connexions.

Les connexions TCP ne doivent être utilisées que sur des réseaux sécurisés car il n'y a pas d'authentification utilisateur ni de protection du code source ou objet. Les connexions SSH sont plus lentes.

distcc est conçu pour être utilisé avec l'option -j de GNU Make, qui exécute plusieurs processus de compilation simultanément. distcc répartit les tâches entre les CPU locaux et distants. Parce que distcc est capable de distribuer la plupart du travail sur le réseau, un niveau de concurrence plus élevé peut être utilisé que pour les constructions locales. En règle générale, la valeur de -j doit être définie à environ deux fois le nombre total de CPU serveur disponibles, mais sous réserve des limitations du client. Ce réglage permet une entrelacement maximal des tâches bloquées en attendant des E/S disque ou réseau. Notez que distcc peut également fonctionner avec d'autres outils de contrôle de construction, tels que SCons, où des réglages de concurrence similaires doivent être ajustés.

Le réglage -j, en particulier pour les grandes valeurs de -j, doit tenir compte de la charge CPU du client. Des mesures supplémentaires peuvent être nécessaires pour limiter la charge du client. Par exemple, la liaison concurrente doit être sévèrement limitée à l'aide de verrous auxiliaires. L'effet d'autres activités de construction, comme la compilation Java lors de la construction de code mixte, doit être pris en compte. Le paramètre --localslots_cpp est par défaut défini à 8. Cela limite le nombre de processus concurrents qui effectuent le pré-traitement en mode distcc simple (non-pompe). Par conséquent, des valeurs de -j supérieures à 8 peuvent être utilisées sans surcharger un client à CPU unique en raison du pré-traitement. De telles valeurs élevées peuvent accélérer les parties de la construction qui n'impliquent pas de compilations C, mais elles peuvent ne pas être utiles à l'efficacité de distcc en mode simple.

En revanche, en utilisant le mode pompe et disons 40 serveurs, un réglage de -j80 ou plus peut être approprié même pour les clients à CPU unique.

Il est fortement recommandé d'installer la même version du compilateur sur toutes les machines participant à une construction. Des compilateurs incompatibles peuvent entraîner des erreurs de compilation ou de liaison mystérieuses.

DÉMARRAGE RAPIDE

1
Pour chaque machine, téléchargez distcc, décompressez et installez.
2
Sur chacun des serveurs, exécutez distccd --daemon avec des options --allow pour restreindre l'accès.
3
Mettez les noms des serveurs dans votre environnement :
$ export DISTCC_HOSTS='localhost red green blue'
4
Construisez !
$ make -j8 CC=distcc

DÉMARRAGE RAPIDE POUR LE MODE DISTCC-PUMP

Procédez comme ci-dessus, mais à l'étape 3, spécifiez que les hôtes distants doivent supporter la charge du pré-traitement et que les fichiers envoyés sur le réseau doivent être compressés :

$ export DISTCC_HOSTS='--randomize localhost red,cpp,lzo green,cpp,lzo blue,cpp,lzo'

L'option --randomize impose une utilisation uniforme des serveurs de compilation. Bien que vous bénéficiiez du mode pompe de distcc avec seulement quelques serveurs, vous obtenez un bénéfice croissant avec plus de CPU serveur (jusqu'à des centaines !). Encapsulez votre construction dans la commande pump, en supposant ici 10 serveurs :

$ pump make -j20 CC=distcc

DÉMARRAGE RAPIDE POUR LE MODE DISTCC-GSSAPI

Procédez comme pour le DÉMARRAGE RAPIDE mais à l'étape 3, spécifiez que les hôtes distants doivent s'authentifier mutuellement auprès du client :

$ export DISTCC_HOSTS='--randomize localhost red,auth green,auth blue,auth'

Si distccd s'exécute sous un nom de principal spécifique, exécutez la commande suivante avant l'étape 4 :

export DISTCC_PRINICIPAL=<nom>

COMMENT FONCTIONNE LE DISTCC SIMPLE (NON-POMPE)

distcc n'exécute jamais que le compilateur et l'assembleur à distance. Avec le distcc simple, le préprocesseur doit toujours s'exécuter localement car il a besoin d'accéder à divers fichiers d'en-tête sur la machine locale qui pourraient ne pas être présents, ou ne pas être les mêmes, sur le volontaire. L'éditeur de liens a de même besoin d'examiner les bibliothèques et les fichiers objets, et doit donc s'exécuter localement.

Le compilateur et l'assembleur prennent un seul fichier d'entrée (la source pré-traitée) et produisent une seule sortie (le fichier objet). distcc expédie ces deux fichiers sur le réseau et peut donc exécuter le compilateur/assembleur à distance.

Heureusement, pour la plupart des programmes, l'exécution du préprocesseur est relativement peu coûteuse, et l'éditeur de liens est appelé relativement peu fréquemment, de sorte que la majeure partie du travail peut être distribuée.

distcc examine sa ligne de commande pour déterminer quelles de ces phases sont invoquées, et si la tâche peut être distribuée.

COMMENT FONCTIONNE LE MODE DISTCC-PUMP

En mode pompe, distcc exécute également le préprocesseur à distance. Pour ce faire, le préprocesseur doit avoir accès à tous les fichiers auxquels il aurait eu accès s'il s'était exécuté localement. En mode pompe, par conséquent, distcc rassemble tous les en-têtes inclus récursivement, à l'exception de ceux qui sont des en-têtes système par défaut, et les envoie avec le fichier source au serveur de compilation.

En mode distcc-pump, le serveur décompresse l'ensemble de tous les fichiers source dans un répertoire temporaire, qui contient une arborescence de répertoires qui reflète la partie du système de fichiers pertinente pour le pré-traitement, y compris les liens symboliques.

Le compilateur est ensuite exécuté à partir du chemin dans le répertoire temporaire qui correspond au répertoire de travail actuel sur le client. Pour trouver et transmettre les centaines de fichiers qui font souvent partie d'une seule compilation, le mode pompe utilise un algorithme d'analyse des inclusions incrémentielle. Le serveur d'inclusions est un programme Python qui implémente cet algorithme. La commande pump démarre le serveur d'inclusions afin que tout au long de la construction, il puisse répondre aux requêtes d'inclusions des commandes distcc.

Le serveur d'inclusions utilise une analyse statique du langage macro pour gérer la compilation conditionnelle et les inclusions calculées. Il utilise la propriété que lorsqu'un fichier d'en-tête donné a déjà été analysé pour les inclusions, il n'est pas nécessaire de le faire à nouveau si toutes les options d'inclusion (-I) sont inchangées (ainsi que d'autres conditions).

Pour les grandes constructions, les fichiers d'en-tête sont inclus, en moyenne, des centaines de fois chacun. Avec le mode distcc-pump, chaque fichier de ce type n'est analysé que quelques fois, peut-être une seule fois, au lieu d'être pré-traité des centaines de fois. De plus, chaque fichier source ou d'en-tête est maintenant co

pressé seulement une fois, car le serveur d'inclusion met en cache les fichiers compressés. Par conséquent, le temps utilisé pour préparer les compilations peut diminuer d'un ordre de grandeur par rapport au prétraitement de distcc

standard.

Étant donné que distcc en mode pump est capable d'envoyer des fichiers envi

ron dix fois plus vite, la vitesse de construction peut augmenter de 3 fois ou plus pour les grandes compilations par rapport au mode distcc standard.

RESTRICTIONS POUR LE MODE

PUMP

L'utilisation du mode pump nécessite que le client et les serveurs utilisent la version 3.0 ou ultérieure de distcc et distccd (respectivement)

.

L'analyse incrémentale des inclusions du mode distcc-pump repose sur l'hypothèse fondamentale que les fichiers source et d'en-tête ne changent pas pendant le processus de construction. Quelques systèmes de construction complexes, comme celui du noyau Linux 2.6, ne satisfont pas tout à fait cette exigence. Pour surmonter ces problèmes, ainsi que d'autres cas particuliers tels que les chemins de fichiers absolus dans les inclusions, voir la page de manuel include_server(1)

.

Une autre hypothèse importante est que la configuration des inclusions de toutes les machines doit être identique. Ainsi, les en-têtes sous le chemin système par défaut doivent être les mêmes sur tous les serveurs et tous les clients. Si une installation standard du compilateur GNU est utilisée, alors cette exigence s'applique à toutes les bibliothèques dont les fichiers d'en-tête sont installés sous /usr/include ou /usr/local/include/. Notez que l'installation de paquets logiciels conduit souvent à ce que des fichiers d'en-tête supplémentaires soient placés dans des sous-répertoires de l'un ou

l'autre.

Si cette hypothèse ne tient pas, il est possible de casser des compilations avec le mode distcc-pump, ou pire, d'obtenir de mauvais résultats sans avertissement. Actuellement, cette condition n'est pas vérifiée, et il figure sur notre liste TODO de traiter ce

problème.

Une manière simple de garantir que les configurations d'inclusions sont identiques est d'utiliser un compilateur croisé qui définit un chemin de recherche système par défaut restreint aux répertoires de l'installation du

compilateur.

Voir le manuel include_server(1) pour plus d'informations sur les symptôme

s et les causes des violations de
s hypothèses du mode distcc-pump.

INSTALLATION DE

DISTCC

Il existe trois façons différentes d'appeler distcc, pour s'adapter à différentes circonstances

:

distcc peut être installé sous le nom du compilateur réel, pour intercepter les appels à celui-ci et les exécuter à distance. Ce compilateur « déguisé » a la plus large compatibilité avec les arbres de sources existants, et est pratique lorsque vous souhaitez utiliser distcc pour toutes les compilations. Le fait que distcc soit utilisé est transparent pour les

makefiles.

distcc peut être préfixé aux lignes de commande du compilateur, comme "distcc cc -c hello.c" ou CC="distcc gcc". C'est pratique lorsque vous souhaitez utiliser distcc pour seulement certaines compilations ou pour l'essayer, mais cela peut causer des problèmes avec certains makefiles ou des versions de libtool qui supposent que $CC ne contient pas

d'espace.

Enfin, distcc peut être utilisé directement comme compilateur. "cc" est toujours utilisé comme nom d

u compilateur réel dans ce mode « implicite ». Cela peut être pratique pour un usage interactif lorsq
ue le mode « explicite » ne fonctionne pas, mais n'est pas vraiment recommandé pour un nouvel usage.

Rappelez-vous que vous ne devriez pas utiliser deux méthodes pour appeler distcc en même temps. Si vous utilisez un répertoire d

e déguisement, ne changez pas CC et/ou CXX, mettez simplement le répertoire tôt dans votre PATH. Si vous n'utilisez pas de répe
rtoire de déguisement, vous devrez soit changer CC et/ou CXX, soit modifier le(s) makefile(s) pour appeler distcc explicitement.

DÉGUISEMEN

T

L'idée de base est de créer un « répertoire de déguisement » qui contient des liens du nom du compilateur réel vers le binaire distcc. Ce répertoire est inséré tôt dans le PATH, de sorte que les appels au compilateur sont interceptés et que distcc est exécuté à la place. distcc se retire ensuite du PATH pour trouver le compilateur

réel.

Par exemple

: 
# mkdir /usr/lib/distcc/bin
# cd /usr/lib/distcc/bin
# ln -s
../../../bin/distcc gcc # ln -s ../../../bin/distcc cc # l
n -s ../../../bin/distcc g++ # ln -s ../../../bin/distcc c++

Ensuite, pour utiliser distcc, un utilisateur n'a besoin que de placer le répertoire /usr/lib/distcc/bin tôt dans le PATH, et d'avoir défini une liste d'hôtes dans DISTCC_HOSTS ou un fichier. distcc s'occupera du

reste.

Pour découvrir automatiquement les compilateurs et créer des liens de déguisement, exécutez le script fourni update-distcc-symlinks

.

Notez que ce répertoire de déguisement doit apparaître sur le PATH avant le répertoire qui contient les compilateurs réels des mêmes noms, et que tous les programmes auxiliaires que ces compilateurs appellent (comme as ou ld) doivent également être trouvés sur le PATH dans un répertoire situé après le répertoire de déguisement, car distcc appelle le compilateur réel avec une valeur de PATH dont tous les répertoires jusqu'à et y compris le répertoire de déguisement ont été

supprimés.

Il est possible d'obtenir une « erreur de récursion » en mode déguisement, ce qui signifie que distcc se retrouve d'une manière ou d'une autre, et non le compilateur réel. Cela peut indiquer que vous avez deux répertoires de déguisement sur le PATH, possiblement parce que vous avez deux installations de distcc à des emplacements différents. Cela peut aussi indiquer que vous essayez de mélanger les opérations « déguisée » et « explicite »

.

Les erreurs de récursion peuvent être évitées en utilisant des scripts shell au lieu de liens. Par exemple, dans /usr/lib/distcc/bin, créez un fichier cc qui contient

e localiser le vrai gcc en examinant la variable PATH. À la

SPÉCIFICATIONS DES

HÔTES

Une « liste d'hôtes » indique à distcc quelles machines utiliser pour la compilation. Dans l'ordre, distcc cherche dans la variable d'environnement $DISTCC_HOSTS, le fichier $DISTCC_DIR/hosts de l'utilisateur, et le fichier d'hôtes système. Si aucune liste d'hôtes ne peut être trouvée, distcc émet un avertissement et compile

localement.

La liste d'hôtes est une simple liste d'espaces blancs de spécifications d'hôtes. La forme la plus simple et la plus courante est un nom d'hôte,

comme
localhost red green blue

distcc préfère les hôtes situés en début de liste, de sorte que les machines doivent être répertoriées dans l'ordre décroissant de leur vitesse. En particulier, lorsqu'une seule compilation peut être exécutée (par exemple, à partir d'un script de configuration), la première machine listée est utilisée (mais voir --randomize ci-dessous).

Placer localhost au bon endroit dans la liste est important pour obtenir de bonnes performances. Étant donné que la surcharge liée à l'exécution de travaux localement est faible, localhost devrait normalement être en première position. Cependant, il est important que le client dispose de suffisamment de cycles libres pour exécuter les travaux locaux et le client distcc. Si le client est plus lent que les volontaires, ou s'il y a de nombreux volontaires, alors le client doit être placé plus loin dans la liste, voire pas du tout. En règle générale, si la vitesse CPU globale du client est inférieure à un cinquième de la totale, alors le client doit être retiré de la liste.

Si vous avez un grand cluster de construction partagé et un seul fichier d'hôtes partagé, les règles ci-dessus entraîneront l'essai des premières machines du fichier d'hôtes en premier, même si elles sont probablement plus occupées que les machines plus loin dans la liste. Pour éviter cela, placez le mot-clé --randomize dans la liste des hôtes. Cela permettra de randomiser la liste des hôtes, ce qui devrait légèrement améliorer les performances pour les grands clusters de construction.

Il existe deux noms d'hôte spéciaux --localslots et --localslots_cpp qui sont utiles pour ajuster la charge sur la machine locale. L'hôte --localslots spécifie combien de travaux ne pouvant pas être exécutés à distance peuvent être exécutés simultanément sur la machine locale, tandis que --localslots_cpp contrôle combien de préprocesseurs s'exécuteront en parallèle sur la machine locale. L'ajustement de ces valeurs peut améliorer les performances. La mise en liaison sur de grands projets peut consommer beaucoup de mémoire. L'exécution de liaisons parallèles, qui ne peuvent pas être exécutées à distance, peut forcer la machine à swapper, ce qui réduit les performances par rapport à l'exécution des travaux en séquence sans swapper. Obtenir le bon nombre de préprocesseurs parallèles vous permet d'utiliser des facteurs parallèles plus importants avec make, car la machine locale dispose désormais d'un mécanisme pour mesurer l'utilisation des ressources locales.

Enfin, il y a l'entrée d'hôte

Les performances dépendent des détails des sources et des makefiles utilisés pour le projet, ainsi que de la vitesse des machines et du réseau. Expérimenter avec différents réglages pour la liste des hôtes et le facteur -j peut améliorer les performances.

La syntaxe est

  DISTCC_HOSTS = HOSTSPEC ...
  HOSTSPEC = LOCAL_HOST | SSH_HOST | TCP_HOST | OLDSTYLE_TCP_HOST
                        | GLOBAL_OPTION
                        | ZEROCONF
  LOCAL_HOST = localhost[/LIMIT]
             | --localslots=<int>
             | --localslots_cpp=<int>
  SSH_HOST = [USER]@HOSTID[/LIMIT][:COMMAND][OPTIONS]
  TCP_HOST = HOSTID[:PORT][/LIMIT][OPTIONS]
  OLDSTYLE_TCP_HOST = HOSTID[/LIMIT][:PORT][OPTIONS]
  HOSTID = HOSTNAME | IPV4 | IPV6
  OPTIONS = ,OPTION[OPTIONS]
  OPTION = lzo | cpp | auth[=AUTH_NAME]
  GLOBAL_OPTION = --randomize
  ZEROCONF = +zeroconf

Voici quelques exemples individuels de la syntaxe :

localhost
Le mot littéral "localhost" est interprété spécialement pour entraîner l'exécution directe des compilations, plutôt que leur passage à un démon sur la machine locale. Si vous souhaitez vous connecter à un démon sur la machine locale pour des tests, alors utilisez l'adresse IP ou le nom d'hôte réel de la machine. (Ce sera plus lent.)
IPV6
Une adresse IPv6 littérale entre crochets, telle que [::1]
IPV4
Une adresse IPv4 littérale, telle que 10.0.0.1
HOSTNAME
Un nom d'hôte à rechercher à l'aide du résolveur.
:PORT
Se connecter à un numéro de port décimal spécifié, plutôt qu'à celui par défaut de 3632.
@HOSTID
Se connecter à l'hôte via SSH, plutôt que via TCP. Les options pour la connexion SSH peuvent être définies dans ~/.ssh/config
USER@
Se connecter à l'hôte via SSH en tant qu'utilisateur spécifié.
:COMMAND
Se connecter via SSH et utiliser un chemin spécifié pour trouver le serveur distccd. Ceci n'est normalement nécessaire que si, pour une raison quelconque, vous ne pouvez pas installer distccd dans un répertoire du PATH par défaut pour les connexions SSH. Utilisez ceci si vous obtenez des erreurs telles que "distccd: command not found" en mode SSH.
/LIMIT
Une limite décimale peut être ajoutée à toute spécification d'hôte pour restreindre le nombre de travaux que ce client enverra à la machine. La limite est par défaut de quatre par hôte (deux pour localhost), mais peut être restreinte davantage par le serveur. Vous ne devriez avoir besoin de l'augmenter que pour les serveurs ayant plus de deux processeurs.
,lzo
Active la compression LZO pour cet hôte TCP ou SSH.
,cpp
Active le mode distcc-pump pour cet hôte. Note : la commande de construction doit être encapsulée dans le script pump afin de démarrer le serveur d'inclusion.
,auth
Active l'authentification mutuelle basée sur GSSAPI pour cet hôte.
AUTH_NAME
Le nom "canonique" à utiliser pour le nom du principal du service au lieu de HOSTNAME (ou son FQDN correspondant). Cette option est utile en cas d'accès à un serveur authentifié via le transfert de port SSH, auquel cas le HOSTNAME est 127.0.0.1.
--randomize
Randomiser l'ordre de la liste des hôtes avant l'exécution.
+zeroconf
Cette option n'est disponible que si distcc a été compilé avec le support Avahi activé lors de la configuration. Lorsque cette entrée spéciale est présente dans la liste des hôtes, distcc utilise la découverte de services DNS (DNS-SD) d'Avahi Zeroconf pour localiser tous les serveurs distccd disponibles sur le réseau local. Cela évite d'avoir à répertorier explicitement les noms d'hôtes ou les adresses IP des machines serveur distcc. Les serveurs distccd doivent avoir été démarrés avec l'option "--zeroconf" pour distccd. Une remarque importante est que dans l'implémentation actuelle, le mode pump (",cpp") et la compression (",lzo") ne seront jamais utilisés pour les hôtes localisés via zeroconf.

Voici un exemple démontrant quelques possibilités :

localhost/2 @bigman/16:/opt/bin/distccd oldmachine:4200/1
# cartman est en panne
distant/3,lzo

Les commentaires sont autorisés dans les spécifications d'hôtes. Les commentaires commencent par un signe dièse (#) et vont jusqu'à la fin de la ligne.

Si un hôte de la liste n'est pas joignable, distcc émettra un avertissement et ignorera cet hôte pendant environ une minute.

COMPRESSION

L'option d'hôte lzo spécifie que la compression LZO doit être utilisée pour le transfert de données, y compris le code source pré-traité, le code objet et les messages d'erreur. La compression est généralement économique sur les réseaux plus lents que 100 Mbps, mais les résultats peuvent varier en fonction du réseau, des processeurs et de l'arborescence des sources.

L'activation de la compression augmente l'utilisation du CPU par le client et le serveur distcc, mais réduit le trafic réseau. Le temps CPU supplémentaire est négligeable pour le mode pump. Le taux de compression est typiquement de 4:1 pour les sources et de 2:1 pour le code objet.

L'utilisation de la compression nécessite que le client et le serveur utilisent au moins la version 2.9 de distcc. Aucune configuration du serveur n'est requise : le serveur répond toujours avec des réponses compressées aux requêtes compressées.

Le mode pump nécessite que les serveurs aient l'option d'hôte lzo activée.

CHEMINS DE RECHERCHE

Si le nom du compilateur est un chemin absolu, il est transmis tel quel au serveur et le compilateur est exécuté à partir de ce répertoire. Par exemple :

distcc /usr/local/bin/gcc-3.1415 -c hello.c

Si le nom du compilateur n'est pas absolu, ou pas entièrement qualifié, le PATH de distccd est recherché. Lorsque distcc est exécuté à partir d'un répertoire de masquerade, seul le nom de base du compilateur est utilisé. Le PATH du client n'est utilisé que pour exécuter le préprocesseur et n'a aucun effet sur le chemin du serveur.

TEMPS DE CONNEXION

Le client et le serveur distcc imposent des délais d'attente sur le transfert de données sur le réseau. Ceci est destiné à détecter les hôtes qui sont en panne ou inaccessibles, et à empêcher les compilations de rester bloquées indéfiniment si un serveur est déconnecté pendant son utilisation. Si un délai d'attente côté client expire, le travail sera réexécuté localement.

Le délai de transfert n'est pas configurable actuellement. Le délai qui détecte les travaux distribués obsolètes est configurable via la variable d'environnement DISTCC_IO_TIMEOUT.

DIAGNOSTICS

Les messages d'erreur ou les avertissements des compilateurs locaux ou distants sont transmis à la sortie de diagnostic sur le client.

distcc peut fournir des informations de débogage étendues lorsque l'option verbeuse est utilisée. Ceci est contrôlé par la variable d'environnement DISTCC_VERBOSE sur le client, et l'option --verbose sur le serveur. Pour le dépannage, examinez les messages d'erreur du client et du serveur.

distcc fait la distinction entre les erreurs "authentiques" telles qu'une erreur de syntaxe dans la source, et les erreurs "accidentelles" telles qu'un problème de réseau lors de la connexion à un volontaire. En cas d'erreurs accidentelles, distcc retentera la compilation localement, sauf si l'option DISTCC_FALLBACK a été désactivée.

Si le compilateur se termine avec un signal, distcc renvoie un code de sortie de 128 plus le numéro du signal.

BUGS

In distcc-pump mode, the server may generate object files that are not bytewise identical to what would have been produced by compiling on the local client (due to different padding, etc), they should be functionally identical.

In distcc-pump mode, the include server is unable to handle certain very complicated computed includes as found in parts of the Boost library. The include server will time out and distcc will revert to plain mode.

In distcc-pump mode, certain assumptions are made that source and header files do not change during the build. See discussion in section DISTCC DISCREPANCY SYMPTOMS of include_server(1).

Other known bugs may be documented on http://code.google.com/p/distcc/
