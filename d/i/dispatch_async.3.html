dispatch_async(3) Manuel des fonctions de bibliothèque dispatch_async(3)

NOM

dispatch_async, dispatch_sync — planifier des blocs pour exécution

SYNTAXE

#include <dispatch/dispatch.h>

void
dispatch_async(dispatch_queue_t queue, void (^block)(void));

void
dispatch_sync(dispatch_queue_t queue, void (^block)(void));

void
dispatch_async_f(dispatch_queue_t queue, void *context, void (*function)(void *));

void
dispatch_sync_f(dispatch_queue_t queue, void *context, void (*function)(void *));

DESCRIPTION

Les fonctions dispatch_async() et dispatch_sync() planifient des blocs pour une exécution concurrente au sein du framework dispatch(3). Les blocs sont soumis à une file d'attente qui dicte la politique de leur exécution. Voir dispatch_queue_create(3) pour plus d'informations sur la création de files d'attente de dispatch.

Ces fonctions prennent en charge la synchronisation temporelle efficace, la concurrence en arrière-plan et la concurrence au niveau des données. Ces mêmes fonctions peuvent également être utilisées pour la notification efficace de l'achèvement des blocs asynchrones (également appelés callbacks).

SYNCHRONISATION TEMPORELLE

La synchronisation est souvent requise lorsque plusieurs threads d'exécution accèdent simultanément à des données partagées. La forme la plus simple de synchronisation est l'exclusion mutuelle (un verrou), par laquelle différents sous-systèmes s'exécutent en parallèle jusqu'à ce qu'une section critique partagée soit atteinte. Dans la famille des procédures pthread(3), la synchronisation temporelle est accomplie comme suit :

int r = pthread_mutex_lock(&my_lock);
assert(r == 0);

// section critique

r = pthread_mutex_unlock(&my_lock);
assert(r == 0);

La fonction dispatch_sync() peut être utilisée avec une file d'attente série pour accomplir le même style de synchronisation. Par exemple :

dispatch_sync(my_queue, ^{
	// section critique
});

En plus de fournir une expression plus concise de la synchronisation, cette approche est moins sujette aux erreurs car la section critique ne peut pas être quittée accidentellement sans restaurer la file d'attente dans un état réentrant.

La fonction dispatch_async() peut être utilisée pour implémenter des sections critiques différées lorsque le résultat du bloc n'est pas nécessaire localement. Les sections critiques différées ont les mêmes propriétés de synchronisation que le code ci-dessus, mais elles sont non bloquantes et donc plus efficaces à exécuter. Par exemple :

dispatch_async(my_queue, ^{
	// section critique
});

CONCURRENCE EN ARRIÈRE-PLAN

La fonction dispatch_async() peut être utilisée pour exécuter des tâches triviales en arrière-plan sur une file d'attente globale concurrente. Par exemple :

dispatch_async(dispatch_get_global_queue(DISPATCH_QUEUE_PRIORITY_DEFAULT,0), ^{
	// opération en arrière-plan
});

Cette approche est un remplacement efficace pour pthread_create(3).

CALLBACKS D'ACHÈVEMENT

Les callbacks d'achèvement peuvent être réalisés via des appels imbriqués à la fonction dispatch_async(). Il est important de se souvenir de conserver la référence à la file d'attente de destination avant le premier appel à dispatch_async(), et de relâcher cette file d'attente à la fin du callback d'achèvement pour s'assurer que la file d'attente de destination n'est pas désallouée pendant que le callback d'achèvement est en attente. Par exemple :

void
async_read(object_t obj,
	void *where, size_t bytes,
	dispatch_queue_t destination_queue,
	void (^reply_block)(ssize_t r, int err))
{
	// Il existe de meilleures façons de faire de l'I/O asynchrone.
	// Ceci est juste un exemple de blocs imbriqués.

	dispatch_retain(destination_queue);

	dispatch_async(obj->queue, ^{
		ssize_t r = read(obj->fd, where, bytes);
		int err = errno;

		dispatch_async(destination_queue, ^{
			reply_block(r, err);
		});
		dispatch_release(destination_queue);
	});
}

VERROUS RÉCURSIFS

Bien que dispatch_sync() puisse remplacer un verrou, il ne peut pas remplacer un verrou récursif. Contrairement aux verrous, les files d'attente prennent en charge les opérations asynchrones et synchrones, et ces opérations sont ordonnées par définition. Un appel récursif à dispatch_sync() provoque un simple interblocage car le bloc en cours d'exécution attend que le bloc suivant se termine, mais le bloc suivant ne démarrera pas tant que le bloc en cours d'exécution ne sera pas terminé.

Alors que le framework dispatch était conçu, nous avons étudié les verrous récursifs. Nous avons constaté que la grande majorité des verrous récursifs sont déployés rétroactivement lorsque des hiérarchies de verrous mal définies sont découvertes. En conséquence, l'adoption de verrous récursifs transforme souvent des bugs évidents en bugs obscurs. Cette étude a également révélé une idée : si la réentrance est inévitable, alors les verrous lecteur/rédacteur sont préférables aux verrous récursifs. Une utilisation disciplinée des verrous lecteur/rédacteur permet la réentrance uniquement lorsque la réentrance est sûre (le côté « lecture » du verrou).

Néanmoins, si cela est absolument nécessaire, voici une manière imparfaite d'implémenter des verrous récursifs en utilisant le framework dispatch :

void
sloppy_lock(object_t object, void (^block)(void))
{
	if (object->owner == pthread_self()) {
		return block();
	}
	dispatch_sync(object->queue, ^{
		object->owner = pthread_self();
		block();
		object->owner = NULL;
	});
}

L'exemple ci-dessus ne résout pas le cas où la file A s'exécute sur le thread X qui appelle dispatch_sync() contre la file B qui s'exécute sur le thread Y qui appelle récursivement dispatch_sync() contre la file A, ce qui bloque les deux exemples. Ceci est compatible bug pour bug avec une utilisation non triviale de pthread. En fait, la réentrance non triviale est impossible à prendre en charge dans les verrous récursifs une fois que le niveau ultime de réentrance est déployé (IPC ou RPC).

REFERENCES IMPLICITES

Les fonctions synchrones dans le framework dispatch conservent une référence implicite sur la file d'attente cible. Autrement dit, la fonction synchrone emprunte la référence de la fonction appelante (ce qui est valide car la fonction appelante est bloquée en attente du résultat de la fonction synchrone, et ne peut donc pas modifier le nombre de références de la file d'attente cible avant que la fonction synchrone ne soit retournée). Par exemple :

queue = dispatch_queue_create("com.example.queue", NULL);
assert(queue);
dispatch_sync(queue, ^{
	do_something();
	//dispatch_release(queue); // PAS SÛR -- dispatch_sync() utilise toujours 'queue'
});
dispatch_release(queue); // Équilibré SÛREMENT en dehors du bloc fourni à dispatch_sync()

Ceci est en contraste avec les fonctions asynchrones qui doivent conserver la référence du bloc et de la file d'attente cible pendant la durée de l'opération asynchrone (car la fonction appelante peut immédiatement abandonner son intérêt pour ces objets).
