Format de sortie binaire de diff

Dans la locale POSIX, si un ou les deux fichiers comparés ne sont pas des fichiers texte, il est défini par l'implémentation si diff utilise le format de sortie pour fichier binaire ou les autres formats spécifiés ci-dessous. Le format de sortie pour fichier binaire doit contenir les noms de chemin des deux fichiers comparés et la chaîne "differ".

Si les deux fichiers comparés sont des fichiers texte, selon les options spécifiées, l'un des formats suivants doit être utilisé pour écrire les différences.

Format de sortie par défaut de diff

La sortie par défaut (sans les options -e, -f, -c, -C, -u, ou -U ) de l'utilitaire diff doit contenir des lignes de ces formes :

"%da%d\n", <num1>, <num2>
"%da%d,%d\n", <num1>, <num2>, <num3>
"%dd%d\n", <num1>, <num2>
"%d,%dd%d\n", <num1>, <num2>, <num3>
"%dc%d\n", <num1>, <num2>
"%d,%dc%d\n", <num1>, <num2>, <num3>
"%dc%d,%d\n", <num1>, <num2>, <num3>
"%d,%dc%d,%d\n", <num1>, <num2>, <num3>, <num4>

Ces lignes ressemblent à des sous-commandes ed pour convertir file1 en file2. Les numéros de ligne avant les lettres d'action doivent se rapporter à file1; ceux après doivent se rapporter à file2. Ainsi, en échangeant a avec d et en lisant la ligne à l'envers, on peut aussi déterminer comment convertir file2 en file1. Comme dans ed, les paires identiques (où num1= num2) sont abrégées en un seul nombre.

Après chacune de ces lignes, diff doit écrire sur la sortie standard toutes les lignes affectées dans le premier fichier en utilisant le format :

"< %s", <line>

et toutes les lignes affectées dans le second fichier en utilisant le format :

"> %s", <line>

S'il y a des lignes affectées à la fois dans file1 et file2 (comme avec la sous-commande c ), les changements sont séparés par une ligne composée de trois caractères <hyphen-minus> :

"---\n"

Format de sortie de diff -e

Avec l'option -e , un script doit être produit qui, lorsqu'il est fourni en entrée à ed, avec une commande w (write) ajoutée à la fin, convertit file1 en file2. Seules les commandes a (append), c (change), d (delete), i (insert), et s (substitute) de ed doivent être utilisées dans ce script. Les lignes de texte, sauf celles consistant en le caractère unique <period> ('.'), doivent être produites telles qu'elles apparaissent dans le fichier.

Format de sortie de diff -f

Avec l'option -f , un format de script alternatif doit être produit. Il est similaire à celui produit par -e, avec les différences suivantes :

1.
Il est exprimé en séquence inversée ; la sortie de -e ordonne les changements de la fin du fichier vers le début ; celle de -f du début vers la fin.
2.
La forme de commande <lignes> <lettre_commande> utilisée parlines> <command-letter> utilisée par -e est inversée. Par exemple, 10c avec -e deviendrait c10 avec -f.
3.
La forme utilisée pour les plages de numéros de ligne est séparée par des <space>, plutôt que par des <comma>.

Format de sortie de diff -c ou -C

Avec les options -c ou -C , le format de sortie doit consister de lignes affectées ainsi que des lignes de contexte environnantes. Les lignes affectées doivent montrer lesquelles doivent être supprimées ou changées dans file1, et celles ajoutées depuis file2. Avec l'option -c , trois lignes de contexte, si disponibles, doivent être écrites avant et après les lignes affectées. Avec l'option -C , l'utilisateur peut spécifier combien de lignes de contexte sont écrites. Le format exact suit.

Le nom et l'heure de dernière modification de chaque fichier doivent être produits dans le format suivant :

"*** %s %s\n", file1, <file1 timestamp>
"--- %s %s\n", file2, <file2 timestamp>

Chaque champ <file> doit être le nom de chemin du fichier correspondant comparé. Le nom de chemin écrit pour l'entrée standard n'est pas spécifié.

Dans la locale POSIX, chaque champ <timestamp> doit être équivalent à la sortie de la commande suivante :

date "+%a %b %e %T %Y"

sans le <newline> final, exécutée au moment de la dernière modification du fichier correspondant (ou à l'heure actuelle, si le fichier est l'entrée standard).

Ensuite, les formats de sortie suivants doivent être appliqués à chaque ensemble de changements.

D'abord, une ligne doit être écrite dans le format suivant :

"***************\n"

Ensuite, la plage de lignes dans file1 doit être écrite dans le format suivant si la plage contient deux lignes ou plus :

"*** %d,%d ****\n", <beginning line number>, <ending line number>

et le format suivant sinon :

"*** %d ****\n", <ending line number>

Le numéro de ligne de fin d'une plage vide doit être le numéro de la ligne précédente, ou 0 si la plage est au début du fichier.

Ensuite, les lignes affectées ainsi que les lignes de contexte (lignes non affectées) doivent être écrites. Les lignes non affectées doivent être écrites dans le format suivant :

"  %s", <unaffected_line>

Les lignes supprimées doivent être écrites comme :

"- %s", <deleted_line>

Les lignes changées doivent être écrites comme :

"! %s", <changed_line>

Ensuite, la plage de lignes dans file2 doit être écrite dans le format suivant si la plage contient deux lignes ou plus :

"--- %d,%d ----\n", <beginning line number>, <ending line number>

et le format suivant sinon :

"--- %d ----\n", <ending line number>

Ensuite, les lignes de contexte et les lignes changées doivent être écrites comme décrit dans les formats précédents. Les lignes ajoutées depuis file2 doivent être écrites dans le format suivant :

"+ %s", <added_line>

Format de sortie de diff -u ou -U

Les options -u ou -U se comportent comme les options -c ou -C , sauf que les lignes de contexte ne sont pas répétées ; à la place, les lignes de contexte, supprimées et ajoutées sont montrées ensemble, entrelacées. Le format exact suit.

Le nom et l'heure de dernière modification de chaque fichier doivent être produits dans le format suivant :

"--- %s\t%s%s %s\n", file1, <file1 timestamp>, <file1 frac>, <file1 zone>
"+++ %s\t%s%s %s\n", file2, <file2 timestamp>, <file2 frac>, <file2 zone>

Chaque champ <file> doit être le nom de chemin du fichier correspondant comparé, ou le caractère unique '-' si l'entrée standard est comparée. Cependant, si le nom de chemin contient un <tab> ou un <newline>, ou s'il ne consiste pas entièrement en des caractères pris du jeu de caractères portable, le comportement est défini par l'implémentation.

Chaque champ <timestamp> doit être équivalent à la sortie de la commande suivante :

date '+%Y-%m-%d %H:%M:%S'

sans le <newline> final, exécutée au moment de la dernière modification du fichier correspondant (ou à l'heure actuelle, si le fichier est l'entrée standard).

Chaque champ <frac> doit être soit vide, soit un point décimal suivi d'au moins un chiffre décimal, indiquant la partie fraction de seconde (le cas échéant) de l'horodatage du fichier. Le nombre de chiffres fractionnaires doit être au moins le nombre nécessaire pour représenter l'horodatage du fichier sans perte d'information.

Chaque champ <zone> doit être de la forme "shhmm", où "shh" est un nombre décimal signé à deux chiffres dans l'intervalle -24 à +25, et "mm" est un nombre décimal non signé à deux chiffres dans l'intervalle 00 à 59. Il représente le fuseau horaire de l'horodatage comme le nombre d'heures (hh) et de minutes (mm) à l'est (+) ou à l'ouest (-) de l'UTC pour l'horodatage. Si les heures et les minutes sont toutes deux à zéro, le signe doit être '+'. Cependant, si le fuseau horaire n'est pas un nombre entier de minutes par rapport à l'UTC, le champ <zone> est défini par l'implémentation.

Ensuite, les formats de sortie suivants doivent être appliqués à chaque ensemble de changements.

D'abord, la plage de lignes dans chaque fichier doit être écrite dans le format suivant :

"@@ -%s +%s @@", <file1 range>, <file2 range>

Chaque champ <range> doit être de la forme :

"%1d", <beginning line number>

ou :

"%1d,1", <beginning line number>

si la plage contient exactement une ligne, et :

"%1d,%1d", <beginning line number>, <number of lines>

sinon. Si une plage est vide, son numéro de ligne de début doit être le numéro de la ligne juste avant la plage, ou 0 si la plage vide commence le fichier.

Ensuite, les lignes affectées ainsi que les lignes de contexte doivent être écrites. Chaque ligne non affectée non vide doit être écrite dans le format suivant :

" %s", <unaffected_line>

où le contenu de la ligne non affectée doit être pris depuis file1. Il est défini par l'implémentation si une ligne non affectée vide est écrite comme une ligne vide ou une ligne contenant un seul caractère <space>. Cette ligne représente aussi la même ligne de file2, même si file2's line may peuvent contenir des contenus différents en raison de la -b . Les lignes supprimées doivent être écrites comme suit

Les implémentations historiques emploient des algorithmes qui ne produisent pas toujours une liste minimale de différences ; le langage actuel concernant le fait de faire tous les efforts possibles est le mieux que ce volume de POSIX.1‐2017 puisse faire, car il n'existe pas de métrique qui puisse être employée pour juger la qualité des implémentations par rapport à n'importe quel contenu de fichier. L'énoncé « Cette liste devrait être minimale » implique clairement que l'on ne s'attend pas à ce que les implémentations fournissent la sortie suivante lors de la comparaison de deux fichiers de 100 lignes

qui ne diffèrent que par un seul caractère sur une seule ligne :

1,100c1,100 all 100 lines from file1 preceded with "< " --- all 100 lines from file2 preceded with "> " Les messages « Only in » requis lorsque

Ils sont autorisés ici mais ne sont pas requis car ils rapportent quelque chose qui est identique, ne rapportent pas une différence, et ne sont pas nécessaires pour mettre à jour une hiérarchie cible. L'option -c [[80]], qui écrit la sortie dans un format utilisant des lignes de contexte, a été incluse. Le format est utile pour diverses raisons, notamment une lisibilité nettement améliorée et la capacité à comprendre les changements de différences lorsque le fichier cible a des numéros de ligne différents d'une autre copie similaire, mais légèrement différente.

L'utilitaire

patch est le plus précieux lorsqu'il travaille avec des listes de différences utilisant un format de contexte. La version BSD de -c prend un argument optionnel spécifiant la quantité de contexte. Plutôt que de surcharger -c et de violer les Directives de syntaxe des utilitaires pourdiff , les développeurs de la norme ont décidé d'ajouter une option distincte pour spécifier un diff de contexte avec une quantité de contexte spécifiée ( -C ). De plus, le format pour les diffs de contexte a été légèrement étendu en 4.3 BSD pour permettre à plusieurs changements qui se trouvent à quelques lignes de contexte les uns des autres d'être fusionnés. Le format de sortie contient quatre caractères <astérisque> supplémentaires après la plage de lignes affectées dans le premier nom de fichier. Cela servait à fournir un indicateur pour les anciens programmes

(comme les anciennes versions de

patch ) qui ne comprennent que l'ancien format de contexte. La version de contexte décrite ici ne requiert pas que plusieurs changements dans les lignes de contexte soient fusionnés, mais ne le proscrit pas non plus. L'extension est compatible ascendante, de sorte que tout fournisseur qui souhaite conserver l'ancienne version de diff peut le faire en ajoutant les quatre caractères <astérisque> supplémentaires (c'est-à-dire, les utilitaires qui utilisent actuellement diff et comprennent le nouveau format fusionné comprendront également l'ancien format non fusionné, mais pas l'inverse ). Les options -u et -U de GNU diff ont été incluses. Leur format de sortie, conçu par Wayne Davison, prend moins de place que le

format

-c et -C [[111]], et dans de nombreux cas est plus facile à lire. Les horodatages du format ne varient pas selon la locale, donc LC_TIM

E

ne l'affecte pas. Les numéros de ligne du format sont rendus avec le format %1d [[115]], et non %d [[117]], car les règles de notation du format de fichier permettraient l'apparition de caractères <espace> supplémentaires autour des nombres. La commande de substitution a été ajoutée comme format supplémentaire pour

l'option

-e [[120]]. Cela a été ajouté pour fournir aux implémentations un moyen de corriger le bug classique du « point seul sur une ligne » présent dans de nombreuses versions de diff . Comme de nombreuses implémentations ont corrigé ce bug, les développeurs de la norme ont décidé de ne pas standardiser un comportement défectueux, mais plutôt de fournir l'outil nécessaire pour corriger le bug. Une façon de corriger ce bug est de produire deux points chaque fois qu'un point unique est nécessaire, puis de terminer la commande d'ajout avec un point, et ensuite d'utiliser la commande de substitution pour convertir les deux points en un point. L'option -r issue de BSD a été ajoutée pour fournir un mécanisme permettant d'utiliser

diff

pour comparer deux arbres de fichiers. Ce comportement est utile, est une pratique standard sur tous les systèmes dérivés de BSD, et n'est pas facilement reproductible avec l'utilitaire find . L'exigence selon laquelle dif

f

ne compare pas les fichiers dans certaines circonstances, même s'ils ont le même nom, est basée sur la sortie réelle des implémentations historiques. Le comportement spécifié prévient les problèmes résultant de la rencontre avec des FIFO et d'autres fichiers qui feraient diff se bloquer en attendant une entrée sans aucune indication à l'utilisateur que

diff

était bloqué. Une version antérieure de cette norme spécifiait le format de sortie plus précisément, mais en pratique cette exigence a été largement ignorée et l'avantage de la standardisation semblait faible, elle est donc maintenant non spécifiée. Dans la plupart

des usages courants,
