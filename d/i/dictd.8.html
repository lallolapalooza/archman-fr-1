DESCRIPTIO

N

dictd est un serveur pour le protocole de serveur de dictionnaire (DICT), un protocole de requête/réponse basé sur des transactions TCP qui permet à un client d'accéder aux définitions d'un dictionnaire à partir d'un ensemble de bases de données de dictionnaires de langues

naturelles.

Pour des raisons de sécurité, dictd abandonne les privilèges de root après le démarrage. Si l'utilisateur dictd existe sur le système, le démon s'exécutera en tant que cet utilisateur, groupe dictd, sinon il s'exécutera en tant qu'utilisateur nobody, groupe nobody ou nogroup (selon la distribution du système d'exploitation)

.

Étant donné que le temps de démarrage est important, le serveur est conçu pour s'exécuter en continu, et ne devrait pas être exécuté depuis inetd(8). (Cependant, avec un processeur rapide, il est faisable de le faire.

)

Les bases de données sont distribuées séparément du

serveur.

Par défaut, dictd suppose que les fichiers d'index sont triés par ordre alphabétique, et que seuls les caractères alphanumériques du jeu de caractères ASCII 7 bits sont utilisés pour la recherche. Ce comportement par défaut peut être surchargé par un en-tête dans le fichier de données. Les seules fonctionnalités de ce type implémentées à ce stade sont les en-têtes « 00-database-allchars » qui indique à dictd que des caractères non alphanumériques peuvent également être utilisés pour la recherche, l'en-tête « 00-database-utf8 » qui indique que la base de donn

ées utilise l'encodage utf8, et « 00-database-8bit-new » qui indique que la
base de données est encodée et triée selon une locale utilisant un encodage 8 bits.

CONTEXT

E

Pendant de nombreuses années, la communauté Internet s'est appuyée sur le protocole « webster » pour accéder aux définitions de langues naturelles. Le protocole webster prend en charge l'accès à un seul dictionnaire et (facultativement) à un seul thésaurus. Au cours des dernières années, le nombre de serveurs webster publiquement disponibles sur Internet a considérablement

diminué.

Heureusement, plusieurs dictionnaires et lexiques librement distribuables sont récemment devenus disponibles sur Internet. Cependant, ces bases de données librement distribuables ne sont pas accessibles via une interface uniforme, et ne sont pas accessibles depuis un seul site. Elles sont souvent petites et incomplètes individuellement, mais fourniraient collectivement une base de données intéressante et utile de mots anglais. Des exemples incluent le fichier Jargon, la base de données WordNet, la version de MICRA du Webster's Revised Unabridged Dictionary de 1913, et le Free Online Dictionary of Computing. (Voir la spécification du protocole DICT (RFC) pour les références.) Les dictionnaires de traduction et non anglais deviennent également disponibles (par exemple, le dictionnaire FOLDOC est en cours de traduction en espagnol)

.

Le protocole webster n'est pas adapté pour fournir l'accès à un grand nombre de bases de données de dictionnaires distinctes, et les extensions au protocole webster actuel n'ont pas été considérées comme une solution élégante au problème des bases de données de

dictionnaires.

Le protocole DICT est conçu pour fournir l'accès à plusieurs bases de données. Les définitions de mots peuvent être demandées, l'index des mots peut être recherché (en utilisant un ensemble d'algorithmes facilement extensible), des informations sur le serveur peuvent être fournies (par exemple, quelles stratégies de recherche d'index sont prises en charge, ou quelles bases de données sont disponibles), et des informations sur une base de données peuvent être fournies (par exemple, des informations de copyright, de citation ou de distribution). De plus, le protocole DICT possède des points d'extension qui peuvent être utilisés pour restreindre l'accès à certaines ou à toutes les bases de

données.

dictd(8) est un serveur qui implémente le protocole DICT. Bret Martin a implémenté un autre serveur,

et plusieurs personnes (y compris Bret et moi-mê
me) ont implémenté des clients dans divers langages.

Spécification
d'accès
Les spécifications d'accès peuvent apparaître dans la section d'accès ou dans la section de base de données. La spécification d'accès sera décrite ici.

Pour allow, deny et authonly, une étoile (*) peut être utilisée comme un caractère générique qui correspond à un nombre quelconque de caractères. Un point d'interrogation (?) peut être utilisé comme un caractère générique qui correspond à un seul caractère. Par exemple, 10.0.0.* et *.edu sont des chaînes

valides.

De plus, une plage d'adresses IP et une adresse IP suivie d'un masque de réseau peuvent être spécifiées. Par exemple, 10.0.0.0:10.0.0.255, 10.0.0.0/24, et 10.0.0.* spécifient tous la même plage de numéros IP. Les notations ne peuvent pas être combinées sur la même ligne. Si la notation n'a pas de sens, l'accès sera refusé par défaut. Utilisez l' option --debug auth pour déboguer les problèmes

associés.

Notez que ces spécifications ne prennent qu'une chaîne par ligne de spécification. Cependant, vous pouvez avoir plusieurs lignes de chaque

type.

site_no_banner booléen
Par défaut, la commande SHOW SERVER affiche des informations sur la version de dictd et le type de système d'exploitation. Cette option désactive cela.
site_no_uptime booléen
Par défaut, la commande SHOW SERVER affiche des informations sur le temps de fonctionnement de dictd, le nombre de forks depuis le démarrage et les forks par heure. Cette option désactive cela.

Par défaut, la commande SHOW SERVER affiche des informations internes sur les bases de données, telles que le nombre de têtes de mots, la taille de l'index, etc. Cette option désactive cela.
delay nombre
Spécifie le nombre de secondes pendant lesquelles un client peut être inactif avant que le serveur ne ferme la connexion. Le temps d'inactivité est défini comme le temps pendant lequel le serveur attend une entrée et n'inclut pas le temps que le serveur passe à rechercher dans la base de données. La valeur par défaut est de 0 seconde (aucune limite), mais peut être modifiée dans le fichier defs.h au moment de la compilation (DICT_DEFAULT_DELAY).
NOTE : La définition de l'option delay désactive l'option limit_time. Une seule des deux (la dernière spécifiée dans dictd.conf) est effective.

NOTE : Les connexions sont fermées sans avertissement car aucune disposition pour la terminaison prématurée des connexions n'est spécifiée dans le protocole DICT RFC.

depth nombre
Spécifie la longueur de la file d'attente pour listen(2). Spécifie le nombre de connexions socket en attente qui sont mises en file d'attente par le système d'exploitation. Certains systèmes d'exploitation peuvent limiter silencieusement cette valeur à 5 (anciens systèmes BSD) ou 128 (Linux). La valeur par défaut est 10 mais peut être modifiée dans le fichier defs.h au moment de la compilation (DICT_QUEUE_DEPTH).
limit_childs nombre
Spécifie le nombre de démons qui peuvent s'exécuter simultanément. Chaque démon gère une seule connexion. Si la limite est dépassée, une connexion (série) sera établie par le processus serveur, et un code de réponse 420 (serveur temporairement indisponible) sera envoyé au client. Ce paramètre doit être ajusté pour éviter que la machine serveur ne soit surchargée par les clients dict, mais ne doit pas être réglé trop bas de sorte que de nombreux clients se voient refuser des connexions utiles. La valeur par défaut est 100, mais peut être modifiée dans le fichier defs.h au moment de la compilation (DICT_DAEMON_LIMIT_CHILDS).
limit nombre
Synonyme de limit_childs. Pour la compatibilité ascendante uniquement.
limit_matches nombre
Spécifie le nombre maximum de correspondances qui peuvent être retournées par une requête MATCH. Zéro signifie aucune limite. La valeur par défaut est 2000.
limit_definitions nombre
Spécifie le nombre maximum de définitions qui peuvent être retournées par une requête DEFINE. Zéro signifie aucune limite. La valeur par défaut est 200.
limit_time nombre
Spécifie le nombre de secondes pendant lesquelles un client peut communiquer avec le serveur avant que le serveur ne ferme la connexion. La valeur par défaut est 600 secondes (10 minutes), mais peut être modifiée dans le fichier defs.h au moment de la compilation (DICT_DEFAULT_LIMIT_TIME).

NOTE : La définition de l'option limit_time désactive l'option delay. Une seule des deux (la dernière spécifiée dans dictd.conf) est effective.

NOTE : Les connexions sont fermées sans avertissement car aucune disposition pour la terminaison prématurée des connexions n'est spécifiée dans le protocole DICT RFC.

limit_queries nombre
Spécifie le nombre de requêtes (MATCH, DEFINE, SHOW DB, etc.) qu'un client peut envoyer au serveur avant que le serveur ne ferme la connexion. Zéro signifie aucune limite. La valeur par défaut est 2000, mais peut être modifiée dans le fichier defs.h au moment de la compilation (DICT_DEFAULT_LIMIT_QUERIES).
timestamp nombre
À quelle fréquence un horodatage doit être enregistré (en minutes). (Ceci n'est effectif que si la journalisation a été activée avec l'option -s ou -L, ou avec une option de débogage.)
log_option option
Spécifie une option de journalisation. Ceci n'est effectif que si la journalisation a été activée avec l'option -s ou -L ou dans le fichier de configuration, ou si la journalisation vers la console a été activée avec une option de débogage (par exemple, --debug nodetach. Une seule option peut être définie à chaque invocation de cette option ; cependant, plusieurs invocations de cette option peuvent être faites dans le fichier de configuration ou sur la ligne de commande de dictd. Par exemple :

est une ligne de commande valide, et définit trois options de journalisation.

Pour faciliter la localisation des informations intéressantes dans le fichier journal, les entrées sont marquées par des lettres initiales indiquant la classe de la ligne enregistrée :

E
Messages d'erreur.
C
Informations sur les commandes CLIENT.
D
Définitions trouvées dans les bases de données recherchées.
M
Correspondances trouvées dans la base de données recherchée.
N
Correspondances qui n'ont pas été trouvées dans les bases de données recherchées.
T
Traçage de la ligne exacte envoyée par le client.

Informations d'authentification.

DÉTERMINATION DU NIVEAU D'ACCÈS

Lorsqu'un client se connecte, la spécification d'accès globale est parcourue, dans l'ordre, jusqu'à ce qu'une spécification corresponde. Si aucune spécification d'accès n'existe, tout accès est autorisé (par exemple, l'action est la même que si "allow * " était le seul élément de la spécification). Pour chaque élément, le nom d'hôte et l'adresse IP sont vérifiés. Par exemple, considérez la spécification d'accès suivante :

allow 10.42.*
authonly *.edu
deny *
Avec cette spécification, tous les clients du réseau 10.42 seront autorisés à accéder aux bases de données sans restriction ; tous les clients des sites *.edu seront autorisés à s'authentifier, mais se verront refuser l'accès à toutes les bases de données, même celles qui ne sont pas autrement restreintes ; et tous les autres clients verront leur connexion immédiatement terminée. Les clients du réseau 10.42 peuvent envoyer une commande AUTH et obtenir l'accès aux bases de données restreintes. Les clients *.edu doivent envoyer une commande AUTH pour accéder à n'importe quelle base de données, restreinte ou non restreinte.

Lorsque la commande AUTH est envoyée, la liste d'accès de chaque base de données est parcourue, dans l'ordre, de la même manière que la liste d'accès globale est parcourue. Cependant, après l'authentification, le client a un nom d'utilisateur associé. Par exemple, considérez la spécification d'accès suivante :

user u1
deny *.com
user u2
allow *
Si le client s'est authentifié en tant que u1, alors le client aura accès à cette base de données, même si le client provient d'un site *.com. En revanche, si le client s'est authentifié en tant que u2, le client n'aura accès que s'il ne provient pas d'un site *.com. Dans ce cas, "user u2" est redondant, car ce client correspondrait également à "allow *".

Attention : Des vérifications sont effectuées pour les noms de domaine et pour les adresses IP. Cependant, si la résolution DNS inverse pour un site spécifique ne fonctionne pas, il est possible qu'un nom de domaine ne soit pas disponible pour vérification. Assurez-vous que tous les refus utilisent des adresses IP. (Et considérez une future amélioration : si un nom de domaine n'est pas disponible, les refus qui dépendent d'un nom de domaine devraient-ils correspondre à quelque chose ? C'est le point de vue le plus conservateur, mais il n'est actuellement pas implémenté.)

ALGORITHMES DE RECHERCHE

La norme DICT spécifie quelques algorithmes de recherche qui doivent être implémentés, et permet à d'autres d'être pris en charge de manière dépendante du serveur. Les stratégies de recherche suivantes sont prises en charge par ce serveur. Notez que toutes les stratégies ne tiennent pas compte de la casse. La plupart ignorent les caractères non alphanumériques et non blancs.

exact
Correspondance exacte. Cet algorithme utilise une recherche binaire et est l'un des algorithmes de recherche les plus rapides disponibles.
lev
L'algorithme de Levenshtein (distance d'édition de chaîne d'un). Cet algorithme recherche tous les mots qui sont à une distance d'édition de un du mot cible. Une "édition" signifie une insertion, une suppression ou une transposition. C'est un algorithme rapide pour corriger les erreurs d'orthographe, car de nombreuses erreurs d'orthographe sont à une distance de Levenshtein d'un du mot d'origine.
prefix
Correspondance de préfixe. Cet algorithme utilise également une recherche binaire et est très rapide.
nprefix
Comme prefix mais retourne la plage spécifiée de correspondances. Par exemple, lorsque la stratégie prefix retourne 1000 correspondances, vous pouvez en obtenir seulement 100 en sautant les 800 premières correspondances. Ceci est réalisé en spécifiant ces limites dans une requête comme suit : 800#100#app, où 800 est le nombre de sauts, 100 est le nombre de correspondances que vous souhaitez obtenir et "app" est votre requête. Cette stratégie permet d'implémenter un client DICT avec une autocomplétion rapide (bien que ce ne soit pas trivial) tout comme le font de nombreux programmes de dictionnaire autonomes.
NOTE : Si vous accédez au dictionnaire "*" (ou virtuel) avec la stratégie nprefix, la même plage est définie pour chaque base de données qu'il contient, mais globalement pour toutes les correspondances trouvées dans toutes les bases de données.
NOTE : Dans le cas où vous accédez à un dictionnaire non anglais, les correspondances retournées peuvent être (et le seront majoritairement) NON ordonnées alphabétiquement.
re
Recherche d'expressions régulières POSIX 1003.2 (modernes). Les expressions régulières modernes sont celles utilisées par egrep(1). Ces expressions régulières autorisent les classes de caractères prédéfinies (par exemple, [[:alnum:]], [[:alpha:]], [[:digit:]], et [[:xdigit:]] sont utiles pour cette application) ; utilise * pour faire correspondre une séquence de 0 ou plusieurs correspondances de l'atome précédent ; utilise + pour faire correspondre une séquence de 1 ou plusieurs correspondances de l'atome précédent ; utilise ? pour faire correspondre une séquence de 0 ou 1 correspondance de l'atome précédent ; utilise ^ pour faire correspondre le début d'un mot, utilise $ pour faire correspondre la fin d'un mot, et autorise les sous-expressions imbriquées et l'alternance avec () et |. Par exemple, "(foo|bar)" correspond à tous les mots contenant soit "foo", soit "bar". Pour faire correspondre ces caractères spéciaux, ils doivent être mis entre guillemets avec deux barres obliques inverses (en raison des caractéristiques de mise entre guillemets du serveur). Attention : Les correspondances d'expressions régulières peuvent prendre 10 à 300 fois plus de temps que les correspondances de sous-chaînes. Sur un serveur très sollicité, avec de nombreuses bases de données, cela peut nécessiter plus de 5 minutes d'attente, en fonction de la complexité de l'expression régulière.
regexp
Expressions régulières anciennes (de base). Ces expressions régulières ne prennent pas en charge |, +, ni ?. Les groupes utilisent des parenthèses échappées. Bien que les expressions régulières modernes soient généralement plus faciles à utiliser, les expressions régulières de base ont une fonctionnalité de référence arrière. Celle-ci peut être utilisée pour faire correspondre une deuxième occurrence de quelque chose qui a déjà été trouvé. Par exemple, l'expression suivante trouve tous les mots qui commencent et se terminent par les mêmes trois lettres :
    ^\\(...\\).*\\1$

Notez l'utilisation des doubles barres obliques inverses pour échapper les caractères spéciaux. Ceci est requis par le protocole DICT pour la spécification des chaînes (une seule barre oblique inverse met entre guillemets le caractère suivant -- nous en utilisons deux pour transmettre une seule barre oblique inverse au moteur d'expressions régulières). Attention : Notez que l'utilisation de la récursion arrière est encore plus lente que l'utilisation d'expressions régulières générales.

soundex
L'algorithme Soundex, un algorithme classique pour trouver des mots qui sonnent similairement les uns aux autres. L'algorithme encode chaque mot en utilisant la première lettre du mot et jusqu'à trois chiffres. Comme la première lettre est connue, cette recherche est relativement rapide, et elle est parfois bonne pour corriger les erreurs d'orthographe lorsque l'algorithme de Levenshtein n'aide pas.
substring
Correspondance d'une sous-chaîne n'importe où dans le mot-clé. Cette stratégie de recherche utilise un algorithme modifié de Boyer-Moore-Horspool. Comme elle doit rechercher dans tout le fichier d'index, elle n'est pas aussi rapide que les correspondances exactes et de préfixe.
suffix
Correspondance de suffixe. Cette stratégie de recherche utilise également un algorithme modifié de Boyer-Moore-Horspool, et est aussi rapide que la recherche de sous-chaîne. Si le fichier optionnel index_suffix est listé dans le fichier de configuration, cette recherche est beaucoup plus rapide.
word
Correspond à n'importe quel mot unique, même s'il fait partie d'une entrée multi-mots. Si le fichier optionnel index_word est listé dans le fichier de configuration, cette stratégie de recherche fonctionne beaucoup plus rapidement.
first
Correspond au premier mot qui commence une entrée multi-mots.
last
Correspond au dernier mot qui termine une entrée multi-mots. Si le fichier optionnel index_suffix est listé dans le fichier de configuration, cette stratégie de recherche fonctionne beaucoup plus rapidement.

FORMAT DE LA BASE DE DONNÉES

dictd(8) — Documentation Linux

NOM

dictd, dictd - serveur de dictionnaire de réseau

SYNTAXE

dictd [-d] [-p port] [-c configfile]

DESCRIPTION

dictd est un serveur de dictionnaire de réseau qui implémente le protocole DICT (RFC 2229). Il sert des bases de données de dictionnaires aux clients DICT.

ARRIÈRE-PLAN

Le serveur dictd est une implémentation du serveur de dictionnaire de réseau qui utilise un format de base de données particulier. Ce format est conçu pour des recherches rapides et efficaces.

OPTIONS

-d
Mode démon. Lance dictd en arrière-plan.
-p port
Spécifie le numéro de port sur lequel écouter. La valeur par défaut est 2628.
-c configfile
Spécifie le fichier de configuration à utiliser. La valeur par défaut est /etc/dict/dictd.conf.

FICHIER DE CONFIGURATION

Le fichier de configuration peut spécifier le répertoire des bases de données, les bases de données à charger, les stratégies de recherche autorisées, ainsi que d'autres paramètres de fonctionnement.

DÉTERMINATION DU NIVEAU D'ACCÈS

Le niveau d'accès est déterminé par les informations fournies dans le fichier de configuration et par les autorisations du système de fichiers.

ALGORITHMES DE RECHERCHE

dictd prend en charge plusieurs algorithmes de recherche, notamment la recherche par mot-clé, la recherche par expression régulière et la recherche par préfixe.

FORMAT DE BASE DE DONNÉES

Les bases de données pour dictd sont distribuées séparément. Une base de données se compose de deux fichiers. L'un est un fichier texte brut, l'autre est l'index.

Le fichier texte brut contient les entrées du dictionnaire (ou toute autre donnée appropriée), et l'index contient des tuples délimités par des tabulations composés du mot-clé, du décalage d'octets auquel cette entrée commence dans le fichier texte brut, et de la longueur de l'entrée en octets. Le décalage et la longueur sont encodés en base 64 en utilisant le sous-ensemble de 64 caractères de l'alphabet international IA5 discuté dans la RFC 1421 (encodage imprimable) et la RFC 1522 (base64 MIME). L'encodage des décalages en base 64 permet d'économiser considérablement de l'espace par rapport à l'encodage habituel en base 10, tout en permettant d'utiliser des caractères de tabulation (ASCII 9) pour délimiter les champs d'un enregistrement. Chaque enregistrement se termine par un saut de ligne (ASCII 10), de sorte que le fichier d'index est lisible par l'homme.

Certains mots-clés sont utilisés par dictd spécialement

00-database-info Contient les informations sur la base de données qui sont renvoyées par la commande SHOW INFO, sauf si elles sont spécifiées dans le fichier de configuration.

00-database-short Contient le nom court de la base de données qui est renvoyé par la commande SHOW DB, sauf si elle est spécifiée dans le fichier de configuration. Voir dictfmt -s.

00-database-url URL d'où ont été obtenues les sources originales du dictionnaire. Voir dictfmt -u. Ce mot-clé n'est pas utilisé par dictd

00-database-utf8 Indique si le dictionnaire est encodé en utilisant UTF-8. Voir dictfmt --utf8

00-database-8bit-new Indique si le dictionnaire est encodé en utilisant un jeu de caractères 8 bits (pas ASCII et pas UTF8). Voir dictfmt --locale.

Le fichier texte brut peut être compressé en utilisant gzip(1) (non recommandé) ou dictzip(1) (fortement recommandé). La vitesse optimale sera obtenue en utilisant un fichier non compressé. Cependant, l'algorithme de compression gzip fonctionne très bien sur du texte brut et peut entraîner des économies d'espace typiquement comprises entre 60 et 80%. L'utilisation d'un fichier compressé avec gzip(1) n'est cependant pas recommandée, car un accès aléatoire au fichier ne peut être effectué qu'en décompressant séquentiellement tout le fichier, un processus prohibitivement lent. dictzip(1) utilise le même algorithme de compression et le même format de fichier que gzip(1), mais fournit une table qui peut être utilisée pour accéder aléatoirement aux blocs compressés dans le fichier. L'utilisation de blocs de 50-64 Ko pour la compression dégrade généralement la compression de moins de 10%, tout en maintenant des capacités d'accès aléatoire acceptables pour toutes les données du fichier. Comme avantage supplémentaire, les fichiers compressés avec dictzip(1) peuvent être décompressés avec gzip(1) ou zcat(1). (Note : recompacter un fichier dictzip'd en utilisant, par exemple, znew(1) détruira les caractéristiques d'accès aléatoire du fichier. Toujours compresser les fichiers de données avec dictzip(1).)

SIGNALS

SIGHUP fait relire le fichier de configuration à dictd et réinitialiser les bases de données.

SIGUSR1 fait décharger les bases de données par dictd. Ensuite, dictd renvoie le statut 420 (au lieu de 220). Pour recharger les bases de données, envoyez le signal SIGHUP. Comme les fichiers de base de données sont mmap'és(2), il est impossible de les mettre à jour pendant que dictd est en cours d'exécution. Donc, si vous devez mettre à jour les fichiers de base de données et relire le fichier de configuration, envoyez d'abord le signal SIGUSR1 à dictd pour décharger les bases de données, mettez à jour les fichiers, puis envoyez le signal SIGHUP pour les recharger.

Les recherches par expressions régulières n'ignorent pas les caractères non blancs et non alphanumériques comme le font les autres recherches. En pratique, ce n'est pas un gros problème.

WARNINGS

La conformité des expressions régulières (utilisées par les stratégies de recherche 're' et 'regexp') à ERE et BRE dépend de la bibliothèque avec laquelle vous compilez dictd. Que les stratégies 're' et 'regex' prennent en charge utf8 dépend de la bibliothèque avec laquelle vous compilez dictd.
