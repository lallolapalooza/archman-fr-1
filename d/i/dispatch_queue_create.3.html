DESCRIPTION

Les files d'attente sont le mécanisme fondamental pour la planification de l'exécution des blocs dans le framework dispatch(3).

Tous les blocs soumis aux files d'attente de dispatch sont dépilés dans l'ordre FIFO. Les files d'attente créées avec l'attribut DISPATCH_QUEUE_SERIAL attendent que le bloc dépilé précédemment soit terminé avant de dépiler le bloc suivant. Une file d'attente avec ce comportement d'achèvement FIFO est généralement simplement décrite comme une "file d'attente série". Toutes les écritures de mémoire effectuées par un bloc distribué à une file d'attente série sont garanties d'être visibles par les blocs ultérieurs distribués à la même file d'attente. Les files d'attente ne sont liées à aucun fil d'exécution spécifique et les blocs soumis à des files d'attente indépendantes peuvent s'exécuter de manière concurrente.

Les files d'attente créées avec l'attribut DISPATCH_QUEUE_CONCURRENT peuvent exécuter les blocs dépilés de manière concurrente et prennent en charge les blocs barrières soumis avec l'API de dispatch barrière.

CRÉATION

Les files d'attente sont créées avec la fonction dispatch_queue_create(). Les files d'attente, comme tous les objets de dispatch, sont comptées par référence et les nouvelles files d'attente ont un compteur de référence de un.

L'argument facultatif label est utilisé pour décrire le but de la file d'attente et est utile lors du débogage et de l'analyse des performances. Si une étiquette est fournie, elle est copiée. Par convention, les clients doivent fournir une étiquette de style DNS inversé. Par exemple :

ma_queue = dispatch_queue_create("com.example.sous_systeme.tacheXYZ",
				 DISPATCH_QUEUE_SERIAL);

L'argument attr spécifie le type de file d'attente à créer et doit être soit DISPATCH_QUEUE_SERIAL soit DISPATCH_QUEUE_CONCURRENT.

La fonction dispatch_queue_get_label() renvoie l'étiquette fournie lors de la création de la queue donnée (ou une chaîne C vide si aucune étiquette n'a été fournie lors de la création). Passer la constante DISPATCH_CURRENT_QUEUE_LABEL à dispatch_queue_get_label() renvoie l'étiquette de la file d'attente actuelle.

SUSPENSION

Les files d'attente peuvent être temporairement suspendues et reprises avec les fonctions dispatch_suspend() et dispatch_resume() respectivement. La suspension est vérifiée avant l'exécution du bloc et n'est pas préemptive.

FILE PRINCIPALE

Le framework de dispatch fournit une file d'attente série par défaut pour que l'application l'utilise. Cette file d'attente est accessible via la fonction dispatch_get_main_queue().

Les programmes doivent appeler dispatch_main() à la fin de main() afin de traiter les blocs soumis à la file d'attente principale. (Voir la section COMPATIBILITÉ pour les exceptions.) La fonction dispatch_main() ne retourne jamais.

FILES D'ATTENTE GLOBALES CONCURRENTES

Contrairement à la file d'attente principale ou aux files d'attente allouées avec dispatch_queue_create(), les files d'attente globales concurrentes planifient les blocs dès que des threads deviennent disponibles (ordre d'achèvement non FIFO).

  • DISPATCH_QUEUE_PRIORITY_HIGH
  • DISPATCH_QUEUE_PRIORITY_DEFAULT
  • DISPATCH_QUEUE_PRIORITY_LOW
  • DISPATCH_QUEUE_PRIORITY_BACKGROUND

La priorité d'une file d'attente globale concurrente contrôle la priorité de planification des threads créés par le système pour invoquer les blocs soumis à cette file d'attente. Les files d'attente globales de priorité inférieure seront planifiées pour exécution après que toutes les files d'attente globales de priorité supérieure aient été planifiées. De plus, les éléments de la file d'attente globale de priorité d'arrière-plan s'exécuteront sur des threads avec un état d'arrière-plan tel que décrit dans setpriority(2) (c'est-à-dire que les E/S disque sont limitées et que la priorité de planification du thread est définie à la valeur la plus basse).

Utilisez la fonction dispatch_get_global_queue() pour obtenir la file d'attente globale de la priorité donnée. L'argument flags est réservé pour une utilisation future et doit être zéro. Passer une valeur autre que zéro peut entraîner une valeur de retour NULL.

FILE CIBLE

La fonction dispatch_set_target_queue() met à jour la file d'attente cible du dispatch object donné. La file d'attente cible d'un objet est responsable du traitement de l'objet.

La nouvelle file d'attente cible est conservée par l'objet donné avant que la file d'attente cible précédente ne soit libérée. Le nouveau réglage de la file d'attente cible prendra effet entre les exécutions de blocs sur l'objet, mais pas au milieu des exécutions de blocs existantes (non préemptif).

La file d'attente cible par défaut de tous les objets de dispatch créés par l'application est la file d'attente globale concurrente de priorité par défaut. Pour réinitialiser la file d'attente cible d'un objet à la valeur par défaut, passez la constante DISPATCH_TARGET_QUEUE_DEFAULT à dispatch_set_target_queue().

La priorité d'une file d'attente de dispatch est héritée de sa file d'attente cible. Pour modifier la priorité d'une file d'attente créée avec dispatch_queue_create(), utilisez la fonction dispatch_get_global_queue() pour obtenir une file d'attente cible de la priorité désirée.

Les blocs soumis à une file d'attente série dont la file d'attente cible est une autre file d'attente série ne seront pas invoqués de manière concurrente avec les blocs soumis à la file d'attente cible ou à toute autre file d'attente ayant la même file d'attente cible.

La file d'attente cible d'une source de dispatch spécifie où ses blocs de gestionnaire d'événements et de gestionnaire d'annulation seront soumis. Voir dispatch_source_create(3) pour plus d'informations sur les sources de dispatch.

dispatch_get_current_queue() renvoie toujours une file valide. Lorsqu'elle est appelée depuis un bloc soumis à une file de dispatch, cette file sera renvoyée. Si cette fonction est appelée depuis le thread principal avant dispatch_main() est appelée, alors le résultat de dispatch_get_main_queue() est renvoyé. Dans tous les autres cas, la file cible par défaut sera

renvoyée.

L'utilisation de dispatch_get_current_queue() est fortement déconseillée, sauf à des fins de débogage et de journalisation. Le code ne doit faire aucune hypothèse sur la file renvoyée, à moins qu'il ne s'agisse de l'une des files globales ou d'une file créée par le code lui-même. La file renvoyée peut avoir des politiques arbitraires qui peuvent surprendre le code qui essaie de planifier du travail avec la file. La liste des politiques comprend, sans s'y limiter, la largeur de la file (c'est-à-dire sérielle vs. concurrente), la priorité de planification, les identifiants de sécurité ou la configuration du système de fichiers. Cette fonction est obsolète et sera supprimée dans une version

future.

Il est tout aussi risqué pour le code de supposer que l'exécution synchrone sur une file est sûre contre les blocages si cette file n'est pas celle renvoyée par dispatch_get_curren

t_queue().

Le résultat de dispatch_get_main_queue() peut ou non être égal au résultat de dispatch_get_current_queue() lorsqu'elle est appelée sur le thread principal. Comparer les deux n'est pas une manière valide de tester si le code est en cours d'exécution sur le thread principal. Les programmes Foundation/AppKit doivent utiliser [NSThread isMainThread]. Les programmes POSIX peuvent utiliser pthread_main_

Bien qu'une telle file continue d' exister jusqu'à ce que tous les blocs soumis à elle aient terminé, tenter de la conserver est interdit et déclenchera une assertion. Si le comptage de références automatique d'Objective-C est activé, toute utilisation de l'objet renvoyé par dispatch_get_current_queue() entraînera la génération automatique d'appels de rétention, l'utilisation de dispatch_get_current_queue() pour quelque raison que ce soit dans du cod

COMPATIBILIT

É

Les applications Cocoa n'ont pas besoin d'appeler dispatch_main(). Les blocs soumis à la file principale seront exécutés dans le cadre des « modes communs » du NSRunLoop ou CFRunLoop principal de l'application. Cependant, les blocs soumis à la file principale dans les applications utilisant dispatch_main() ne sont pas garantis de s'exécuter sur le thread

principal.

Le framework dispatch est une API pure C. En conséquence, il ne rattrape pas les exceptions générées par des langages de haut niveau tels qu'Objective-C ou C++. Les applications DOIVENT rattraper toutes les exceptions avant de retourner d'un bloc soumis à une file de dispatch ; sinon le processus sera terminé avec une exception non

rattrapée.

Le framework dispatch gère la relation entre les files de dispatch et les threads d'exécution. En conséquence, les applications NE DOIVENT PAS supprimer ou muter des objets qu'elles n'ont pas créés. Les interfaces suivantes NE DOIVENT PAS être appelées par des blocs soumis à une file de dispatch

:

    • h()

    • ()

:

  • pthread_setcanceltyp
    • e()

    • m()

Bien que le résultat de pthread_self() puisse changer entre les invocations de blocs, la valeur ne changera pas pendant l'exécution d'un seul bloc. Comme le thread sous-jacent peut changer entre les invocations de blocs sur une seule file, l'utilisation de données par thread comme valeur de retour hors bande est source d'erreurs. En d'autres termes, le résultat de l'appel à pthread_setspecific() et pthread_getspecific() est bien défini dans un seul bloc, mais pas à travers plusieurs blocs. De plus, on ne peut faire aucune hypothèse sur le moment où le destructeur passé à pthread_key_create() est appelé. Le destructeur peut être appelé entre l'invocation de blocs sur la même file, ou pendant l' état de veille d'un

processus.

L'exemple de code suivant gère correctement les valeurs de retour par thread

: 
__block int r;
__block int e;
dispatch_sync(queue, ^{
	r = kill(1, 0);
	// Copier la valeur de retour par thread vers le thread appelant
	e = errno;
});
printf("kill(1,0) returned %d and errno %d0, r,
e)
;

Notez que dans l'exemple ci-dessus errno est une variable par thread et doit être copiée explicitement car le bloc peut être invoqué sur un thread d'exécution différent de celui de l'appelant. Un autre exemple de données par thread qui devraient être copiées est l'utilisation de getpwnam() au lieu de getpwnam_

r().

En tant qu'optimisation, dispatch_sync() invoque le bloc sur le thread courant lorsque c'est possible. Dans ce cas, les données spécifiques au thread telles que errno peuvent persister depuis le bloc jusqu'au retour vers l'appelant. Une grande pru

dence doit être prise pour ne pas s'appuy
er accidentellement sur cet effet secondaire.
