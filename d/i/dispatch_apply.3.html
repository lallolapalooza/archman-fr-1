NOM

dispatch_apply — planifie des blocs pour une exécution itérative

SYNTAXE

#include <dispatch/dispatch.h>

void
dispatch_apply(size_t iterations, dispatch_queue_t queue, void (^block)(size_t));

void
dispatch_apply_f(size_t iterations, dispatch_queue_t queue, void *context, void (*function)(void *, size_t));

DESCRIPTION

La fonction dispatch_apply() fournit une concurrence au niveau des données grâce à une primitive similaire à une boucle "for (;;)" :

size_t iterations = 10;

// 'idx' est indexé à partir de zéro, tout comme :
// for (idx = 0; idx < iterations; idx++)

dispatch_apply(iterations, DISPATCH_APPLY_AUTO, ^(size_t idx) {
	printf("%zu\n", idx);
});

Bien que n'importe quelle file d'attente puisse être utilisée, il est fortement recommandé d'utiliser DISPATCH_APPLY_AUTO comme argument queue pour dispatch_apply() et dispatch_apply_f(), comme montré dans l'exemple ci-dessus, car cela permet au système d'utiliser automatiquement des threads de travail qui correspondent au mieux à la configuration du thread actuel. Aucune supposition ne doit être faite quant à la file d'attente concurrente globale qui sera utilisée.

Comme une boucle "for (;;)", la fonction dispatch_apply() est synchrone. Si un comportement asynchrone est désiré, encapsulez l'appel à dispatch_apply() avec un appel à dispatch_async() vers une autre file d'attente.

Parfois, lorsque le bloc passé à dispatch_apply() est simple, l'utilisation de la strided peut optimiser les performances. Calculer la stride optimale est préférable de laisser à l'expérimentation. Commencez avec une stride de un et augmentez jusqu'à obtenir les performances souhaitées (peut-être en utilisant une recherche de puissance de deux) :

#define STRIDE 3

dispatch_apply(count / STRIDE, DISPATCH_APPLY_AUTO, ^(size_t idx) {
	size_t j = idx * STRIDE;
	size_t j_stop = j + STRIDE;
	do {
		printf("%zu\n", j++);
	} while (j < j_stop);
});

size_t i;
for (i = count - (count % STRIDE); i < count; i++) {
	printf("%zu\n", i);
}

REFERENCES IMPLICITES

Les fonctions synchrones dans le framework dispatch détiennent une référence implicite sur la file d'attente cible. En d'autres termes, la fonction synchrone emprunte la référence de la fonction appelante (ceci est valide car la fonction appelante est bloquée en attendant le résultat de la fonction synchrone, et ne peut donc pas modifier le compteur de références de la file d'attente cible avant le retour de la fonction synchrone).

Ceci contraste avec les fonctions asynchrones qui doivent conserver à la fois le bloc et la file d'attente cible pendant la durée de l'opération asynchrone (car la fonction appelante peut immédiatement cesser son intérêt pour ces objets).

FONDAMENTAUX

dispatch_apply() et dispatch_apply_f() tentent de créer rapidement suffisamment de threads de travail pour itérer efficacement le travail en parallèle. Par contraste, une boucle qui passe des éléments de travail individuellement à dispatch_async() ou dispatch_async_f() entraînera plus de surcharge et n'exprimera pas les sémantiques d'exécution parallèle souhaitées au système, donc pourrait ne pas créer un nombre optimal de threads de travail pour une charge de travail parallèle. Pour cette raison, préférez utiliser dispatch_apply() ou dispatch_apply_f() lorsque l'exécution parallèle est importante.

La fonction dispatch_apply() est un wrapper autour de dispatch_apply_f().

CAVEATS

Contrairement à dispatch_async(), un bloc soumis à dispatch_apply() est censé être soit indépendant, soit dépendant seulement du travail déjà effectué dans les invocations d'indice inférieur du bloc. Si la dépendance d'indice du bloc n'est pas linéaire, il est recommandé d'utiliser une boucle for autour des invocations de dispatch_async().
