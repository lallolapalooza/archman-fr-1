OPTIONS

-m <module>/<module-version>
Le nom du module et la version du module sur lesquels vous souhaitez opérer. La partie -m de cette option est facultative et peut être omise dans pratiquement toutes les circonstances.
-v <module-version>
La version du module sur laquelle exécuter l'action spécifiée. Cette option ne doit être spécifiée que si vous passez une option -m sans composant <module-version> propre.
-k <kernel-version>/<arch>
Le noyau et l'architecture sur lesquels effectuer l'action. Vous pouvez spécifier plusieurs paires de versions de noyau/architectures sur la ligne de commande en répétant l'argument -k avec une version de noyau et une architecture différentes. Cependant, toutes les actions ne prennent pas en charge plusieurs versions de noyau (cela générera une erreur dans ce cas). La partie architecture peut être omise, et DKMS supposera que vous voulez qu'elle corresponde à l'architecture du système en cours d'exécution.
-a, --arch
L'architecture du système sur laquelle effectuer l'action. Elle est facultative si vous la passez dans le cadre de l'option -k. Si elle n'est pas spécifiée, elle suppose l'architecture du système en cours d'exécution ( uname -m ). Vous pouvez spécifier plusieurs arguments d'architecture sur la même ligne de commande en répétant l'argument -a avec un nom d'architecture différent. Lorsque plusieurs architectures sont spécifiées, il doit y avoir une relation 1:1 entre les arguments -k et les arguments -a. DKMS supposera alors que le premier argument -a correspond au premier -k et ainsi de suite pour le deuxième, le troisième, etc.

Par exemple, si vous spécifiez : -k noyau1 -k noyau2 -a i386 -k noyau3 -a i686 -a x86_64 , DKMS traitera cela comme : noyau1-i386 , noyau2-i686 , noyau3-x86_64.

-q, --quiet
Silencieux.
-V, --version
Affiche la version actuellement installée de DKMS et quitte.
-h, --help
-c <dkms.conf-location>
L'emplacement du fichier dkms.conf. Ceci est nécessaire pour l'action add et si non spécifié, il est supposé être situé dans /usr/src/<module>-<module-version>/ . Voir ci-dessous pour plus d'informations sur le format de dkms.conf.
--config <kernel-include/config/auto.conf-location>
Lors d'une build, cette option est utilisée pour spécifier un emplacement alternatif pour le fichier de configuration du noyau include/config/auto.conf qui contient cette configuration du noyau. Normalement, dkms est capable de dériver l'emplacement du fichier de configuration du système de fichiers, mais s'il y a un problème de détection, vous devrez indiquer à dkms où trouver le fichier include/config/auto.conf (ou le fichier hérité .config) nécessaire afin que votre noyau puisse être correctement préparé pour la construction du module.
--archive <tarball-location>
Cette option est utilisée lors d'une action ldtarball pour spécifier l'emplacement du tarball que vous souhaitez charger dans votre arbre DKMS. Vous n'avez à spécifier la partie --archive de cette option que si <tarball-location> n'existe pas déjà en tant que fichier.
--templatekernel <kernel-version>
Cette option est requise pour l'action : match. Match examinera le noyau template spécifié et installera toutes les mêmes combinaisons module/version sur l'autre noyau.
--force
Cette option peut être utilisée conjointement avec build, install et ldtarball pour forcer l'écrasement des fichiers existants.
--force-version-override
Cette option ignore les vérifications pour savoir si la version du module qui va être installée est plus récente que la version déjà installée.
--binaries-only
Cette option peut être utilisée conjointement avec mktarball afin de créer un tarball DKMS qui ne contient pas les sources du module à l'intérieur. Cela peut être utile pour réduire la taille du tarball si vous savez que le système sur lequel ce tarball sera chargé possède déjà les sources installées. Pour charger un tarball créé en mode "binaries-only", vous devez avoir les sources du module dans l'arbre DKMS de ce système. Sinon, DKMS refusera de charger un tarball "binaries-only".
--source-only
Cette option peut être utilisée conjointement avec mktarball mais si vous ne voulez pas que le tarball que vous créez contienne des modules précompilés, passer cette option empêchera son tarball DKMS interne de contenir des modules précompilés.
--all
Cette option peut être utilisée pour spécifier automatiquement tous les noyaux/architectures pertinents pour un module/une version de module. Cela peut être utilisé pour des actions telles que remove, unbuild et uninstall. Cela évite d'avoir à spécifier explicitement -k noyau1 -a arch1 -k noyau2 -a arch2 pour chaque noyau pour lequel vous avez construit votre module.
--no-depmod
Cette option empêche DKMS d'exécuter la commande depmod pendant install et uninstall, ce qui évitera (re)calculer les dépendances des modules et ainsi gagner du temps.
--modprobe-on-install
Cette option exécute modprobe sur les modules après une installation réussie.
--kernelsourcedir <kernel-source-directory-location>
En utilisant cette option, vous pouvez spécifier l'emplacement de votre répertoire source du noyau. Il est fort probable que vous n'aurez pas besoin de définir cela si votre source du noyau est accessible via /usr/lib/modules/$kernel_version/build.
--directive <"cli-directive=cli-value">
En utilisant cette option, vous pouvez spécifier des directives supplémentaires depuis la ligne de commande. L'option --directive peut être utilisée plusieurs fois sur la même ligne de commande pour spécifier plusieurs directives de ligne de commande supplémentaires.
--rpm_safe_upgrade
Ce drapeau doit être utilisé lors de l'empaquetage de modules activés par DKMS dans des RPM. Il doit être spécifié pendant les actions add et remove dans le spec RPM pour garantir que DKMS et RPM se comportent correctement dans tous les scénarios lors de la mise à niveau entre différentes versions d'un package RPM de module activé par DKMS.
--dkmstree path/to/place
Fournit un arbre de destination pour construire et installer des modules. Utile dans les cas où vous ne voulez pas contaminer un système lorsque vous l'utilisez uniquement pour la construction.
--sourcetree path/to/place
Fournit un emplacement pour construire un package DKMS. Utile pour les systèmes où vous n'avez peut-être pas d'accès root, mais où vous aimeriez quand même pouvoir construire des packages DKMS.
--installtree path/to/place
Fournit un emplacement pour placer les modules lorsqu'une commande dkms install est émise.
-j nombre
Exécute au plus nombre tâches en parallèle ; voir l'option -j de make(1). Par défaut, le nombre de processeurs du système, détecté par nproc(1). Spécifiez 0 pour ne pas imposer de limite au nombre de tâches parallèles.
--verbose
Active la sortie détaillée des commandes externes exécutées dans DKMS.

MODULES ORIGINAUX

Lors de la première installation d'un module pour un <kernelversion>, dkms recherche dans /usr/lib/modules/<kernelversion> un module préexistant du même nom. S'il en trouve un, il sera automatiquement sauvegardé en tant que "module_original" afin que si le module plus récent est ultérieurement supprimé, dkms remette le module original à sa place. Actuellement, DKMS recherche ces modules originaux en donnant la priorité aux modules situés dans /usr/lib/modules/<kernelversion>/updates/ suivi de $DEST_MODULE_LOCATION (tel que spécifié dans dkms.conf ). Si aucun ne peut être trouvé dans l'un ou l'autre emplacement, une recherche sera utilisée pour en trouver un pour ce noyau. Si aucun n'est trouvé, alors lors d'une désinstallation ultérieure, votre noyau n'aura pas ce module remplacé.

Si plus d'un est trouvé, alors le premier trouvé (selon la préférence indiquée ci-dessus) sera considéré comme le "module_original". De plus, toutes les copies du module portant le même nom seront supprimées de votre arbre de noyaux et placées dans /var/lib/dkms/<module>/original_module/$kernelver/collisions afin qu'elles puissent être accessibles *manuellement* plus tard. DKMS ne fera jamais rien avec les modules trouvés sous le répertoire /collisions, et ils y seront stockés jusqu'à ce que vous les supprimiez manuellement.

DKMS.CONF

Lors de l'exécution d'une commande add, un fichier dkms.conf approprié doit être trouvé. Un fichier de configuration correctement formaté est essentiel pour communiquer à DKMS comment et où le module doit être installé. Bien que toutes les directives ne soient pas obligatoires, en fournir autant que possible permet de limiter toute ambiguïté. Notez que

at dkms.conf est en réalité un script shell de définitions de variables qui sont ensuite importées par le exécutable dkms (au format, DIRECTIVE="texte de la directive va ici" ). De plus, les directives sont sensibles à la casse et doivent être écrites EN

MAJUSCULES.

Il est important de comprendre que bon nombre de directives DKMS sont des tableaux dont les valeurs d'index sont liées entre elles. Ces associations de tableaux peuvent être considérées comme des familles, et il existe actuellement trois familles de telles familles de directives de tableaux. MAKE[#] et MAKE_MATCH[#] forment une famille. PATCH[#] et PATCH_MATCH[#] forment la deuxième famille. La troisième et la plus grande famille se compose de BUILT_MODULE_NAME[#] , BUILT_MODULE_LOCATION[#] , DEST_MODULE_NAME[#] , DEST_MODULE_LOCATION[#] et STRIP[#] . Lors de l'indexation de ces tableaux lors de la création de votre dkms.conf , chaque famille doit commencer à la valeur d'index

0.

=
Par défaut, strip est considéré comme "yes". S'il est défini à "no", DKMS n'exécutera pas strip -g sur votre module construit pour en retirer les symboles de débogage. STRIP[0] est utilisé comme valeur par défaut pour toute entrée non définie dans le tableau S

MAKE[#]
=
Le tableau de directives MAKE indique à DKMS quelle commande make doit être utilisée pour construire votre module. La commande make par défaut doit être placée dans MAKE[0]. Les autres entrées du tableau MAKE ne seront utilisées que si leur entrée correspondante dans MAKE_MATCH[#] correspond, en tant qu'expression régulière (à l'aide de grep -E), au noyau pour lequel le module est construit. Remarquez que si aucune valeur n'est placée dans MAKE_MATCH[#] pour un MAKE[#] où # > 0, alors cette directive MAKE est ignorée. MAKE_MATCH[0] est facultatif et, s'il est renseigné, il sera utilisé pour déterminer si MAKE[0] doit être utilisé pour construire le module pour ce noyau. Si plusieurs directives MAKE_MATCH correspondent au noyau pour lequel la construction est faite, le dernier MAKE[#] correspondant sera utilisé pour construire votre module. Si aucune directive MAKE n'est spécifiée ou si aucun MAKE_MATCH ne correspond au noyau pour lequel la construction est faite, DKMS essaiera d' utiliser une commande make générique pour construire votre module.

KERNELRELEASE=$kernelver -j$parallel_jobs sera automatiquement ajouté à MAKE[#]. Si vous souhaitez supprimer ce comportement,

vous pouvez mettre la commande
make entre guillemets : 'make'.

Voir l'entrée ci-dessus sur les directives MAKE[#]. Ce tableau doit être rempli d'expressions régulières qui, lorsqu'elles correspondent au noyau pour lequel la construction est faite, indiqueront à DKMS d'utiliser la commande make correspondante dans le tableau de directives MAKE[#] pour construire votre

La fonctionnalité des modules faibles a été conçue pour éliminer la nécessité de reconstruire les modules du noyau lors des mises à niveau du noyau et repose sur les symboles au sein du kABI. Les valeurs valides sont "yes" ou "no".

L'interface de module du noyau kABI est actuellement prise en charge sur Red

PATCH[#]
=
Utilisez le tableau de directives PATCH pour spécifier les correctifs qui doivent être appliqués à vos sources avant qu'une construction n'ait lieu. Tous les correctifs doivent être au format -p1 et sont appliqués avec la commande patch -p1. Chaque directive doit spécifier le nom de fichier du correctif à appliquer, et tous les correctifs doivent se trouver dans le sous-répertoire patches de votre répertoire source ( /usr/src/<module>-<module-version>/patches/ ). Si un correctif ne peut pas être appliqué, la construction sera interrompue et les rejets pourront être examinés dans /var/lib/dkms/<module>/<module-version>/build/. Si un correctif ne doit être appliqué que de manière conditionnelle, le tableau PATCH_MATCH[#] doit être utilisé, et une expression régulière correspondante doit être placée dans PATCH_MATCH[#] qui avertira dkms d'utiliser ce PATCH[#] uniquement si l'expression régulière correspond au noyau pour lequel le module est actuellement en cours de
construction.
PATCH_MATCH[#]
=
Voir la description ci-dessus pour les directives PATCH[#]. Si vous souhaitez qu'un correctif soit appliqué uniquement dans certains scénarios, le tableau PATCH_MATCH doit être utilisé en donnant une expression régulière qui correspond aux noyaux auxquels vous souhaitez que le PATCH[#] correspondant soit appliqué avant la construction de ce

DKMS.CONF DIRECTIVES

ADD_MODULE=
A space separated list of modules to add. This is typically used in a package's dkms.conf file to add the module to the DKMS tree.
AUTO_NAME_MODULES=
If this directive is set to yes, DKMS will attempt to auto-name your modules. This is used when you have multiple modules within a package and wish for DKMS to determine the module name from the files present in the source tree.
BUILTIN=
A space separated list of modules that should be built as part of the kernel and not as loadable modules. This is an optional directive.
BUILD_DEPENDS=
A space separated list of modules that this module depends on. DKMS will ensure these modules are installed and built before attempting to build this module. Note that this directive is not implemented yet.
BUILD_EXCLUSIVE_KERNEL=
This optional directive allows you to specify a regular expression which defines the subset of kernels which DKMS is allowed to build your module for. If the kernel being built for does not match against this regular expression (or does not the satisfy the constraints of any other BUILD_EXCLUSIVE_* directive), the build will error out with exit code 77. Note that dkms autoinstall will ignore this type of error condition and simply skip the respective modules. For example, if you set it as ="^2.4.*", your module would not be built for 2.6 or later kernels.
BUILD_EXCLUSIVE_KERNEL_MIN=
and BUILD_EXCLUSIVE_KERNEL_MAX= These optional directives allow one to specify the minimal and maximal kernel versions supported by the module. If one (or both) of these are defined, the module will not be built for kernels outside the specified version limits. For example, if you set BUILD_EXCLUSIVE_KERNEL_MIN as "=3.5", your module would be built for e.g. "3.5-rc2", "3.6.18" or other later versions but not for "3.4.999" or earlier kernels. Similarly, if you set BUILD_EXCLUSIVE_KERNEL_MAX as ="4.12", your module would be built for e.g. "4.11.999", "3.9-rc5" or other earlier versions, but not for "4.12-rc1" or later kernels.
BUILD_EXCLUSIVE_ARCH=
This optional directive functions very similarly to BUILD_EXCLUSIVE_KERNEL except that it matches against the kernel architecture. For example, if you set it to ="i.86", your module would not be built for ia32e, x86_64, amd64, s390, etc.
BUILD_EXCLUSIVE_CONFIG=
This optional directive allows you to specify a space separated list of kernel configuration options ("CONFIG_FOO") that must be enabled in the targeted kernels ".config" file (either to be compiled in or to be built as a module) or absent (if prefixed with an exclamation mark, e.g. "!CONFIG_BAR") in order to build the module. For example, if you set it as ="CONFIG_PCI !CONFIG_PREEMPT_RT", your module would only be built for kernels that have PCI enabled, but the RT patchset disabled.
BUILD_EXCLUSIVE_KERNEL[#]=, BUILD_EXCLUSIVE_KERNEL_MIN[#]=, BUILD_EXCLUSIVE_KERNEL_MAX[#]=, BUILD_EXCLUSIVE_ARCH[#]=, BUILD_EXCLUSIVE_CONFIG[#]=
These optional per-module directives function identically to their global counterparts but apply only to the specific module at the given index. They allow you to specify different BUILD_EXCLUSIVE constraints for each module in a multi-module package. The global BUILD_EXCLUSIVE directives are still checked for backward compatibility, and if any module fails either the global or its specific per-module constraints, the build will be excluded.

For example, if you have two modules in your package: BUILD_EXCLUSIVE_KERNEL[0]="^5..*" BUILD_EXCLUSIVE_KERNEL[1]="^6..*" Module 0 would only be built for kernel 5.x, while module 1 would only be built for kernel 6.x.

BUILD_DEPENDS_REBUILD=
If this directive is set to yes then the module which has BUILD_DEPENDS being set, will get rebuilt every time a dependency changes version. This is usually provided in a specific /etc/dkms/<module>.conf on a per installation basis.

To keep track of the dependency change, the version of the module that was used at build time is recorded in the file /var/lib/dkms/<module>/<kernel_version>-<arch>/.dep_<dependency>. As soon as the module version changes, this is compared and the dependent module is rebuilt. With the parameter --force the dependency is not tracked.

CLEAN=
The command to run to clean up the module build. This is optional.
DEST_MODULE_LOCATION=
This directive specifies where the modules will be installed. The default is /lib/modules/%k/misc. It can be overridden with the --targetdirs parameter.
MAKE=
The make command to use when building the module. This defaults to "make". It is essential to include the full path to make, e.g. MAKE="/usr/bin/make". You can also specify arguments to make, e.g. MAKE="make all INCLUDEDIR=/usr/src/linux-%k/include".
MAKE_TARGET=
The make target to use when building the module. This defaults to "all".
MODULES=
A space separated list of modules that DKMS should build. This is mandatory.
PACKAGE_NAME=
The name of the package. This is mandatory. If not specified, DKMS will attempt to determine it from the directory name.
PACKAGE_VERSION=
The version of the package. This is mandatory. If not specified, DKMS will attempt to determine it from the directory name.
POST_ADD=
The name of the script to be run after an add is performed. The path should be given relative to the root directory of your source.
POST_BUILD=
The name of the script to be run after a build is performed. The path should be given relative to the root directory of your source.
POST_INSTALL=
The name of the script to be run after an install is performed. The path should be given relative to the root directory of your source.
POST_REMOVE=
The name of the script to be run after a remove is performed. The path should be given relative to the root directory of your source.
PRE_BUILD=
The name of the script to be run before a build is performed. The path should be given relative to the root directory of your source.
PRE_INSTALL=
The name of the script to be run before an install is performed. The path should be given relative to the root directory of your source. If the script exits with a non-zero value, the install will be aborted. This is typically used to perform a custom version comparison.
REMOVE_MODULE=
A space separated list of modules to remove. This is typically used in a package's dkms.conf file to remove the module from the DKMS tree.
SIGN_MODULE=
If this directive is set to yes, DKMS will attempt to sign the module after building it. This is useful for modules that need to be signed with a specific key, e.g. for Secure Boot.
source=
This directive specifies the location of the source code for the module. It can be an absolute path or a path relative to /usr/src. If not specified, DKMS will assume the source code is located in /usr/src/<package_name>-<package_version>.

DKMS.CONF VARIABLES

Within your DKMS configuration file, you can use certain variables which will be replaced at run-time with their values.

$kernelver
This variable can be used within a directive definition and during use, the actual kernel version in question will be substituted in its place. This is especially useful in MAKE commands when specifying which INCLUDE statements should be used when compiling your module (eg. MAKE="make all INCLUDEDIR=/usr/lib/modules/${kernelver}/build/include").
$kernel_source_dir
This variable holds the value of the location of your kernel source directory. Usually, this will be /usr/lib/modules/$kernelver/build, unless otherwise specified with the --kernelsourcedir option.

DKMS.CONF OVERRIDES

You can override directives provided in the module-provided dkms.conf files. Every time after a dkms.conf file is read, dkms will look for and read the following files in order:

/etc/dkms/<module>.conf
/etc/dkms/<module>-<module-version>.conf
/etc/dkms/<module>-<module-version>-<kernel>.conf
/etc/dkms/<module>-<module-version>-<kernel>-<arch>.conf

You can use these files to override settings in the module-provided dkms.conf file.

FRAMEWORK.CONF MAIN CONFIGURATION

The /etc/dkms/framework.conf configuration file controls how the overall DKMS framework handles. It is sourced in every time the dkms command is run. Mainly it can currently be used to set different default values for the variables.

The file contains descriptions for each directive it supports.

Additionally to /etc/dkms/framework.conf , any file matching the glob /etc/dkms/framework.conf.d/*.conf will be loaded as well.

dkms_tree, source_tree, install_tree, tmp_location
Control which folders DKMS uses for components and artifacts.
verbose
Can be set to anything but a null value to enable verbose output of external commands executed in DKMS.
symlink_modules
Controls whether binary modules are copied to /usr/lib/modules or if only symlinks are created there. Note that these variables can also be manipulated on the command line with --dkmstree , --sourcetree , --installtree and --symlink-modules options.
autoinstall_all_kernels
Used by the common postinst for DKMS modules. It controls if the build should be done for all installed kernels or only for the current and latest installed kernel. It has no command line equivalent.
sign_file
This is the path of the sign-file kernel binary that is used to sign the kernel modules. The variable $kernelver can be used in path to represent the target kernel version. The path for the binary depends on the distribution.
mok_signing_key, mok_certificate
Location of the key and certificate files used for Secure boot. The variable $kernelver can be used in path to represent the target kernel version.

NOTE: If any of the files specified by mok_signing_key and mok_certificate are non-existant, dkms will re-create both files.

mok_signing_key can also be a "pkcs11:..." string for PKCS#11 engine, as long as the sign-file program supports it.

modprobe_on_install
Automatically load the built modules upon successful installation.
parallel_jobs
Run no more than this number of jobs in parallel.
compress_gzip_opts, compress_xz_opts, compress_zstd_opts
Control how modules are compressed. By default, the highest available level of compression is used.
build_environment
If the directive is set to any non null-value, when building modules, the exported variables that are in the file will be imported into the DKMS build environment.

post_transaction
Si la directive est définie à une valeur non nulle, le contenu de la directive sera exécuté avec toute commande qui modifie le contenu du dossier des modules du noyau, c'est-à-dire dkms autoinstall, dkms install et dkms remove/unbuild/uninstall. Peut être utilisé pour déclencher une reconstruction globale de initrd ou pour appeler un script qui effectue d'autres tâches (appel de kexec, déclenchement du redémarrage de services non contenus dans un paquet DKMS, etc.). La commande est construite avec l'interne du shell eval et la variable $kernelver peut être utilisée pour représenter la version du noyau cible. Quelques exemples:

Régénérer le disque de démarrage pour le noyau cible: post_transaction="dracut --force --kver $kernelver" (style Red Hat) ou post_transaction="update-initramfs -k $kernelver" (style Debian).

Lancer un script arbitraire: post_transaction="/path/to/script.sh"

Redémarrer un service: post_transaction="systemctl restart something.service"

Régénérer le disque de démarrage pour tous les noyaux installés, en ignorant la version du noyau passée en paramètre: post_transaction="dracut --force --regenerate-all" (style Red Hat) ou post_transaction="update-initramfs -k all" (style Debian).

DKMS AUTOINSTALLER

Le service d'installation automatique DKMS (qui peut être dkms_autoinstaller ou dkms.service selon votre distribution) est un service au démarrage qui installe automatiquement tout module pour lequel AUTOINSTALL="yes" est défini dans son fichier dkms.conf. Le service fonctionne de manière assez simple et s'il y a plusieurs versions d'un module dans l'arbre DKMS de votre système, il ne fera rien et expliquera à la place que une intervention manuelle est requise.
