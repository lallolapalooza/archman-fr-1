NOM

podman-machine-init - Initialise une nouvelle machine virtuelle

SYNOPSIS

podman machine init [options] [nom]

DESCRIPTION

Initialise une nouvelle machine virtuelle pour Podman.

Le nom de machine par défaut est podman-machine-default. Si un nom de machine n'est pas spécifié en argument, la nouvelle machine sera nommée podman-machine-default.

Uniquement sans racine.

Podman sur macOS et Windows nécessite une machine virtuelle. C'est parce que les conteneurs sont Linux - les conteneurs ne s'exécutent sur aucun autre système d'exploitation car la fonctionnalité de base des conteneurs est liée au noyau Linux. La machine Podman doit être utilisée pour gérer les machines macOS et Windows, mais peut être utilisée de manière facultative sur Linux.

podman machine init initialise une nouvelle machine virtuelle Linux où les conteneurs sont exécutés. Les clés SSH sont automatiquement générées pour accéder à la VM, et des connexions système au compte root et à un compte utilisateur à l'intérieur de la VM sont ajoutées.

Par défaut, la distribution de la VM est une image Fedora CoreOS personnalisée poussée vers quay.io/podman/machine-os (construite dans https://github.com/containers/podman-machine-os). WSL est une exception et est basée sur une image Fedora personnalisée.

Pour vérifier s'il y a une mise à jour disponible pour votre système d'exploitation de machine, vous pouvez exécuter la commande suivante :

$ podman machine ssh 'sudo rpm-ostree upgrade --check'

Si une mise à jour est disponible, vous pouvez réexécuter la commande ci-dessus et retirer le --check et votre système d'exploitation sera mis à jour. Après la mise à jour, vous devez arrêter et démarrer votre machine avec podman machine stop && podman machine start pour que celle-ci prenne effet.

Le mécanisme ci-dessus n'est utilisé que pour mettre à jour les versions de correctif (Z) de podman. Pour les mises à jour vers de nouvelles versions majeures et mineures (X.Y), utilisez la commande podman machine os apply , voir la documentation pour plus d'informations.

Remarque : La mise à jour comme décrit ci-dessus peut entraîner des incompatibilités de version entre Podman sur l'hôte et Podman dans la machine. L'exécution de podman info devrait révéler les versions des deux. Une configuration où les versions de Podman de l'hôte et de la machine diffèrent n'est pas prise en charge.

Pour mettre à jour l'image WSL, vous devez exécuter dnf update à l'intérieur, utilisez la commande suivante :

$ podman machine ssh dnf update

Les paramètres par défaut de la machine Podman peuvent être définis via la section [machine] du fichier containers.conf(5).

OPTIONS

--cpus=nombre

Nombre de CPU.

--disk-size=nombre

Taille du disque pour la VM invitée en Gio.

--help

Affiche l'énoncé d'utilisation.

--ignition-path

Chemin entièrement qualifié du fichier ignition.

Si un fichier ignition est fourni, le fichier est copié dans le CONF_DIR de l'utilisateur et renommé. De plus, aucune clé SSH n'est générée, ni aucune connexion système n'est établie. On suppose que l'utilisateur fait ces choses manuellement ou les gère autrement.

--image

Registre, chemin ou URL entièrement qualifiés vers une image VM. La cible du registre doit être sous la forme de docker://registre/dépôt/image:version.

Remarque : Seules les images fournies par podman seront prises en charge.

--memory, -m=nombre

Mémoire (en Mio). Remarque : 1024Mio = 1Gio.

--now

Démarre la machine virtuelle immédiatement après son initialisation.

--playbook

Ajoute le playbook Ansible fourni à la machine et l'exécute après le premier démarrage.

Remarque : Le playbook sera exécuté avec les mêmes privilèges accordés à l'utilisateur dans la machine virtuelle. Le playbook fourni ne peut pas inclure d'autres fichiers du système hôte, car ils ne seront pas copiés. L'utilisation de l'option --playbook nécessitera que l'image inclue Ansible. L'image par défaut fournie inclura Ansible.

--rootful

Indique si cette machine préfère l'exécution de conteneurs avec racine (true) ou sans racine (false). Cette option détermine la valeur par défaut de la connexion distante s'il n'existe pas de configuration de connexion distante existante.

Le transfert d'API, si disponible, suit ce paramètre.

--swap, -s=nombre

Espace d'échange (en Mio). Remarque : 1024Mio = 1Gio.

Génère un fichier zram-generator.conf avec zram-size défini à la valeur passée à --swap

--timezone

Définit le fuseau horaire pour la machine et les conteneurs. Les valeurs valides sont local ou un fuseau horaire tel que America/Chicago. La valeur local, qui est la valeur par défaut, signifie utiliser le fuseau horaire de la machine hôte.

Le paramètre de fuseau horaire n'est pas utilisé avec WSL. WSL définit automatiquement le fuseau horaire identique à celui du système d'exploitation Windows hôte.

--tls-verify

Exige HTTPS et vérifie les certificats lors de la connexion aux registres (par défaut : true). S'il est explicitement défini à true, la vérification TLS est utilisée. S'il est défini à false, la vérification TLS n'est pas utilisée. Si non spécifié, la vérification TLS est utilisée sauf si le registre cible est répertorié comme registre non sécurisé dans containers-registries.conf(5)

--usb=bus=nombre,devnum=nombre ou vendor=hexadécimal,product=hexadécimal

Assigne un périphérique USB de l'hôte à la VM via le transfert USB. Uniquement pris en charge pour les machines QEMU.

Le périphérique doit avoir les permissions appropriées afin d'être transféré à la machine. Cela signifie que le périphérique doit être sous votre groupe utilisateur.

Notez que l'utilisation du bus et du numéro de périphérique est plus simple mais les valeurs peuvent changer à chaque démarrage ou lorsque le périphérique est débranché.

Lors de la spécification d'un USB à l'aide des identifiants vendeur et produit, si plus d'un périphérique a le même identifiant vendeur et produit, le premier périphérique disponible est assigné.

--user-mode-networking

Cette option ne peut être utilisée que pour le fournisseur WSL sur Windows. Sur toutes les autres plateformes, cette option est ignorée et le réseau en mode utilisateur sera toujours true car ces fournisseurs dépendent toujours de gvproxy (notre outil de réseau en mode utilisateur pour les VM)

En revanche, l'arrière-plan Windows/WSL a pour valeur par défaut falseet suit la configuration réseau standard de WSL. Le changement de ce paramètre en true sur Windows/WSL indique à Podman de remplacer la configuration réseau WSL au démarrage de cette instance de machine par une distribution de réseau en mode utilisateur. Comme WSL partage le même noyau entre les distributions, toutes les autres distributions en cours d'exécution réutilisent ce réseau. De même, lorsque la dernière instance de machine avec un paramètre true s'arrête, la configuration réseau d'origine est restaurée.

Dans certaines configurations VPN, le VPN peut bloquer le trafic provenant d'interfaces réseau alternatives, y compris les périphériques réseau des VM. En activant le réseau en mode utilisateur, les VPN observent tout le trafic podman machine comme provenant de l'hôte, contournant le problème.

--username

Nom d'utilisateur à utiliser pour exécuter des commandes dans la VM distante. La valeur par défaut est core pour FCOS et user pour Fedora (par défaut sur les hôtes Windows). Doit correspondre à celui utilisé à l'intérieur de l'image VM résultante.

--volume, -v=source:cible[:options]

Monte un volume de la source vers la cible.

Crée un montage. Si /host-dir:/machine-dir est spécifié comme *source:cible*, Podman monte host-dir sur l'hôte vers machine-dir dans la machine Podman.

Des options supplémentaires peuvent être spécifiées sous forme de chaîne séparée par des virgules. Les options reconnues sont : * ro: monter le volume en lecture seule * rw: monter le volume en lecture/écriture (par défaut) * security_model=[modèle]: spécifier le modèle de sécurité 9p (voir ci-dessous)

Remarque : Les destinations suivantes sont interdites pour les volumes : /bin, /boot, /dev, /etc, /home, /proc, /root, /run, /sbin, /sys, /tmp, /usr, et /var. Les sous-répertoires de ces destinations sont autorisés mais les utilisateurs doivent être prudentserful de ne pas monter vers des répertoires importants car des résultats inattendus peuvent survenir.

Le modèle de sécurité 9p [détermine] https://wiki.qemu.org/Documentation/9psetup#Starting_the_Guest_directly si et comment le système de fichiers 9p traduit certaines opérations de fichiers avant le stockage réel sur l'hôte.

Afin de permettre aux liens symboliques de fonctionner, sur MacOS le modèle de sécurité par défaut est
none.

La valeur de mapped-xattr spécifie que 9p stocke les liens symboliques et certains attributs de fichiers sous forme d'attributs étendus sur l'hôte. Cela est adapté lorsque l'hôte et l'invité n'ont pas besoin d'interopérer sur le système de fichiers partagé, mais comporte des réserves pour un accès partagé réel ; notamment, les liens symboliques sur l'hôte ne sont pas utilisables sur l'invité et vice versa. Si l'interopérabilité est requise, choisissez plutôt none , mais gardez à l'esprit que l'invité n'est pas capable de faire des choses que l'utilisateur exécutant la machine virtuelle ne peut pas faire, par ex. créer des fichiers appartenant à un autre utilisateur. Utiliser none est presque certainement le meilleur choix pour les volumes en lecture seule.

Exemple : -v "$HOME/git:$HOME/git:ro,security_model=none"

Les montages de volumes par défaut sont définis dans containers.conf. Sauf indication contraire, la valeur par défaut est $HOME:$HOME.

Note sur le Windows Subsystem for Linux (WSL) Étant donné que tous les lecteurs sont montés dans /mnt au démarrage par défaut dans WSL, passer --volume est redondant et n'a aucun effet. Le répertoire personnel de l'hôte pour un lecteur C: sera monté dans /mnt/c/Users/<mon nom d'utilisateur>.

EXEMPLES

Initialiser la machine Podman par défaut, en tirant le contenu depuis internet.

$ podman machine init

Initialiser une machine Podman pour le nom spécifié en tirant le contenu depuis internet.

$ podman machine init myvm

Initialiser et démarrer une nouvelle machine Podman en une seule étape.

podman machine init --now

Initialiser la machine Podman par défaut en tirant le contenu depuis internet en mode rootful par défaut. Le mode par défaut est rootless.

$ podman machine init --rootful

Initialiser la machine Podman par défaut en ignorant la surcharge de la taille de son disque, en tirant le contenu depuis internet.

$ podman machine init --disk-size 50

Initialiser la machine Podman spécifiée en ignorant la taille de sa mémoire, en tirant le contenu depuis internet.

$ podman machine init --memory=1024 myvm

Initialiser la machine Podman par défaut avec le répertoire de l'hôte /Users monté dans la machine virtuelle à /Users.

$ podman machine init -v /Users:/Users

Initialiser la machine Podman par défaut avec un transfert de périphérique usb spécifié avec des options. Pris en charge uniquement pour les machines QEMU.

$ podman machine init --usb vendor=13d3,product=5406

Initialiser la machine Podman par défaut avec un transfert de périphérique usb spécifié avec des options. Pris en charge uniquement pour les machines QEMU.

$ podman machine init --usb bus=1,devnum=3
