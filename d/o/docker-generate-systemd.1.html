podman-generate-systemd(1) Manuel des commandes générales podman-generate-systemd(1)

NOM

podman-generate-systemd - [OBSOLÈTE] Générer un ou plusieurs fichiers d'unité systemd pour un conteneur ou un pod

SYNTAXE

podman generate systemd [options] conteneur|pod

DESCRIPTION

OBSOLÈTE : Note : podman generate systemd est obsolète. Nous recommandons d'utiliser les fichiers [Quadlet] lors de l'exécution de conteneurs ou de pods Podman sous systemd. Il n'est pas prévu de supprimer cette commande. Elle recevra des corrections de bugs urgents mais pas de nouvelles fonctionnalités.

podman generate systemd crée un fichier d'unité systemd qui peut être utilisé pour contrôler un conteneur ou un pod. Par défaut, la commande affiche le contenu des fichiers d'unité sur stdout.

La génération de fichiers d'unité pour un pod nécessite que le pod ait été créé avec un conteneur d'infrastructure (voir --infra=true). Un conteneur d'infrastructure s'exécute pendant toute la durée de vie d'un pod et est donc nécessaire pour que systemd gère le cycle de vie de l'unité principale du pod.

  • Note : Lors de l'utilisation de cette commande avec le client distant, y compris les machines Mac et Windows (à l'exception de WSL2), placez les unités générées sur le système distant. De plus, assurez-vous que la variable d'environnement XDG_RUNTIME_DIR est définie. Si elle n'est pas définie, définissez-la via export XDG_RUNTIME_DIR=/run/user/$(id -u).
  • Note : La commande podman run générée contient une option --sdnotify dont la valeur est prise du conteneur. Si le conteneur n'a pas de valeur explicitement définie ou si la valeur est définie sur ignore, la valeur conmon est utilisée. La raison de remplacer la valeur par défaut container est que presque aucune charge de travail de conteneur n'envoie de messages de notification. Systemd attend un message prêt qui n'arrive jamais, si la valeur container est utilisée pour un conteneur qui n'envoie pas de messages de notification. L'utilisation de la valeur par défaut a pu être involontaire de la part de l'utilisateur, d'où la valeur par défaut remplacée.

Intégration Kubernetes

Un fichier YAML Kubernetes peut être exécuté dans systemd via le modèle systemd podman-kube@.service. L'argument du modèle est le chemin vers le fichier YAML. Étant donné un fichier workload.yaml dans le répertoire personnel, il peut être exécuté comme suit :

$ échappé=$(systemd-escape ~/workload.yaml)
$ systemctl --user start podman-kube@$échappé.service
$ systemctl --user is-active podman-kube@$échappé.service
active

OPTIONS

--after=nom_dépendance

Ajoute l'option d'unité systemd after (After=), qui établit des dépendances d'ordonnancement entre la liste des dépendances et ce service. Cette option peut être spécifiée plusieurs fois.

Les dépendances définies par l'utilisateur sont ajoutées au fichier d'unité généré, mais toute option existante nécessaire ou définie par défaut (par exemple, online.target) n'est pas supprimée ou remplacée.

--container-prefix=préfixe

Définit le préfixe du nom de l'unité systemd pour les conteneurs. Le préfixe par défaut est container.

--env, -e=env

Définit des variables d'environnement dans les fichiers d'unité systemd.

Si une variable d'environnement est spécifiée sans valeur, Podman vérifie l'environnement hôte pour une valeur et définit la variable uniquement si elle est définie sur l'hôte. Comme cas spécial, si une variable d'environnement se terminant par * est spécifiée sans valeur, Podman recherche dans l'environnement hôte des variables commençant par le préfixe et ajoute ces variables aux fichiers d'unité systemd.

--files, -f

Génère des fichiers au lieu d'afficher sur stdout. Les fichiers générés sont nommés {container,pod}-{ID,nom}.service et sont placés dans le répertoire de travail courant.

Note : Sur un système avec SELinux activé, les fichiers générés héritent des contextes du répertoire de travail courant. Selon la configuration SELinux, des modifications des fichiers générés à l'aide de restorecon, chcon ou semanage peuvent être nécessaires pour permettre à systemd d'accéder à ces fichiers. Alternativement, utilisez l'option -Z lors de l'exécution de mv ou cp.

--format=format

Affiche les unités créées dans le format spécifié (json). Si --files est spécifié, les chemins vers les fichiers créés sont affichés au lieu du contenu de l'unité.

--name, -n

Utilise le nom du conteneur pour le démarrage, l'arrêt et la description dans le fichier d'unité.

--new

Cette option produit des fichiers d'unité qui ne s'attendent pas à l'existence de conteneurs et de pods. Au lieu de cela, de nouveaux conteneurs et pods sont créés en fonction de leurs fichiers de configuration. Les fichiers d'unité sont créés au mieux et peuvent nécessiter une édition supplémentaire ; veuillez examiner attentivement les fichiers générés avant de les utiliser en production.

Notez que --new ne fonctionne que sur les conteneurs et les pods créés directement via Podman (c'est-à-dire podman [container] {create,run} ou podman pod create). Il ne fonctionne pas sur les conteneurs ou les pods créés via l'API REST ou via podman kube play. Pour podman kube play, utilisez plutôt le modèle systemd podman-kube@.service.

--no-header

Ne génère pas l'en-tête incluant les métadonnées telles que la version de Podman et l'horodatage.

--pod-prefix=préfixe

Définit le préfixe du nom de l'unité systemd pour les pods. Le préfixe par défaut est pod.

--requires=nom_dépendance

Définit l'option systemd requires (Requires=). Semblable à wants, mais déclare une dépendance plus forte.

--restart-policy=politique

Définit la politique de redémarrage de systemd. La politique de redémarrage doit être l'une des suivantes : "no", "on-success", "on-failure", "on-abnormal", "on-watchdog", "on-abort", ou "always". La politique par défaut est on-failure sauf si le conteneur a été créé avec une politique de redémarrage personnalisée.

Notez que la génération d'une unité sans --new sur un conteneur avec une politique de redémarrage personnalisée peut entraîner des problèmes à l'arrêt ; systemd tente d'arrêter l'unité pendant que Podman essaie de la redémarrer. Il est recommandé de créer le conteneur sans --restart et d'utiliser l'option --restart-policy lors de la génération du fichier d'unité.

--restart-sec=temps

Définit la valeur restartsec du service systemd. Configure le temps d'attente avant de redémarrer un service (tel que configuré avec restart-policy). Prend une valeur en secondes.

--separator=séparateur

Définit le séparateur du nom de l'unité systemd entre le nom/ID d'un conteneur/pod et le préfixe. Le séparateur par défaut est -.

--start-timeout=valeur

Remplace le délai d'attente de démarrage par défaut pour le conteneur avec la valeur donnée en secondes.

--stop-timeout=valeur

Remplace le délai d'attente d'arrêt par défaut pour le conteneur avec la valeur donnée en secondes.

--template

Ajoute des spécificateurs de modèle pour exécuter plusieurs services à partir du fichier d'unité systemd.

Notez que si --new n'a pas été défini sur true, il est défini sur true par défaut. Cependant, la commande échoue si --new est explicitement défini sur false.

--wants=nom_dépendance

Ajoute l'option systemd wants (Wants=) de l'unité, dont ce service dépend (faiblement). Cette option peut être spécifiée plusieurs fois. Cette option n'influence pas l'ordre dans lequel les services sont démarrés ou arrêtés.

Les dépendances définies par l'utilisateur sont ajoutées au fichier d'unité généré, mais toute option existante nécessaire ou définie par défaut (par exemple, online.target) n'est pas supprimée ou remplacée.

EXEMPLES

Générer et afficher un fichier d'unité systemd pour un conteneur

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

r un conteneur

Génère un fichier unité systemd pour un conteneur exécutant nginx avec une always politique de redémarrage et un délai d'attente de 1 seconde vers stdout. Notez que l'option RequiresMountsFor dans la section Unit garantit que le stockage du conteneur pour le GraphRoot et le RunRoot est monté avant le démarrage du service. Pour les systèmes dont le stockage des conteneurs se trouve sur des disques tels que iSCSI ou d'autres protocoles de blocs distants, cela garantit que Podman n'est pas exécuté avant que les opérations de stockage nécessaires ne soient disponibles.

$ podman create --name nginx nginx:latest
$ podman generate systemd --restart-policy=always -t 1 nginx
# container-de1e3223b1b888bc02d0962dd6cb5855eb00734061013ffdd3479d225abacdc6.service
# autogenerated by Podman 1.8.0
# Wed Mar 09 09:46:45 CEST 2020
[Unit]
Description=Podman container-de1e3223b1b888bc02d0962dd6cb5855eb00734061013ffdd3479d225abacdc6.service
Documentation=man:podman-generate-systemd(1)
Wants=network-online.target
After=network-online.target
RequiresMountsFor=/var/run/container/storage
[Service]
Restart=always
ExecStart=/usr/bin/podman start de1e3223b1b888bc02d0962dd6cb5855eb00734061013ffdd3479d225abacdc6
ExecStop=/usr/bin/podman stop   
        -t 1 de1e3223b1b888bc02d0962dd6cb5855eb00734061013ffdd3479d225abacdc6
KillMode=none
Type=forking
PIDFile=/run/user/1000/overlay-containers/de1e3223b1b888bc02d0962dd6cb5855eb00734061013ffdd3479d225abacdc6/userdata/conmon.pid
[Install]
WantedBy=default.target

Générer un fichier unité systemd pour un conteneur avec le drapeau --new drapeau

Le drapeau --new génère des fichiers unités systemd qui créent et suppriment des conteneurs lors des commandes de démarrage et d'arrêt du service (voir les actions de service ExecStartPre et ExecStopPost). De tels fichiers unités ne sont pas liés à une seule machine et peuvent facilement être partagés et utilisés sur d'autres machines.

$ sudo podman generate systemd --new --files --name bb310a0780ae
# container-busy_moser.service
# autogenerated by Podman 1.8.3
# Fri Apr  3 09:40:47 EDT 2020
[Unit]
Description=Podman container-busy_moser.service
Documentation=man:podman-generate-systemd(1)
Wants=network-online.target
After=network-online.target
RequiresMountsFor=/var/run/container/storage
[Service]
Environment=PODMAN_SYSTEMD_UNIT=%n
Restart=on-failure
ExecStartPre=/bin/rm -f %t/%n-pid %t/%n-cid
ExecStart=/usr/local/bin/podman run   
        --conmon-pidfile %t/%n-pid   
	--cidfile %t/%n-cid   
	--cgroups=no-conmon   
	-d   
	-dit alpine
ExecStop=/usr/local/bin/podman stop   
        --ignore   
        --cidfile %t/%n-cid -t 10
ExecStopPost=/usr/local/bin/podman rm   
        --ignore   
        -f   
	--cidfile %t/%n-cid
PIDFile=%t/%n-pid
KillMode=none
Type=forking
[Install]
WantedBy=default.target

Générer des fichiers unités systemd pour un pod avec deux conteneurs alpine simples

Note systemctl ne doit être utilisé que sur l'unité du pod et non pour démarrer ou arrêter les conteneurs individuellement. Les conteneurs sont gérés par le service du pod avec le conteneur infra interne.

Utilisez systemctl status ou journalctl pour examiner les fichiers unités des conteneurs ou du pod.

$ podman pod create --name systemd-pod
$ podman create --pod systemd-pod alpine top
$ podman create --pod systemd-pod alpine top
$ podman generate systemd --files --name systemd-pod
/home/user/pod-systemd-pod.service
/home/user/container-amazing_chandrasekhar.service
/home/user/container-jolly_shtern.service

Installation des fichiers unités systemd générés.

Les fichiers unités générés par Podman incluent une section [Install] qui contient des informations d'installation pour l'unité. Elle est utilisée par les commandes enable et disable de systemctl(1) lors de l'installation.

Une fois le fichier unité systemd généré, installez-le dans /etc/systemd/system pour qu'il soit exécuté par l'utilisateur root, ou dans $HOME/.config/systemd/user pour l'installer en tant qu'utilisateur non-root. Activez le fichier unité copié ou les fichiers copiés en utilisant systemctl enable.

Note : Copier les fichiers unités dans /etc/systemd/system et les activer marque le fichier unité pour qu'il soit démarré automatiquement au démarrage. De même, copier un fichier unité dans $HOME/.config/systemd/user et l'activer marque le fichier unité pour qu'il soit démarré automatiquement à la connexion de l'utilisateur.

# Generated systemd files.
$ podman pod create --name systemd-pod
$ podman create --pod systemd-pod alpine top
$ podman generate systemd --files --name systemd-pod
# Copy all the generated files.
$ sudo cp pod-systemd-pod.service container-great_payne.service /etc/systemd/system
$ systemctl enable pod-systemd-pod.service
Created symlink /etc/systemd/system/multi-user.target.wants/pod-systemd-pod.service → /etc/systemd/system/pod-systemd-pod.service.
Created symlink /etc/systemd/system/default.target.wants/pod-systemd-pod.service → /etc/systemd/system/pod-systemd-pod.service.
$ systemctl is-enabled pod-systemd-pod.service
enabled

Pour exécuter les services utilisateur placés dans $HOME/.config/systemd/user lors de la première connexion de cet utilisateur, activez le service avec le drapeau --user.

$ systemctl --user enable <.service>

L'instance utilisateur de systemd est tuée après la fermeture de la dernière session de l'utilisateur. L'instance utilisateur de systemd peut être démarrée au démarrage du système et rester en cours d'exécution même après la déconnexion de l'utilisateur en activant lingering en utilisant

$ loginctl enable-linger <username>

Utilisez systemctl pour effectuer des opérations sur les fichiers unités installés générés.

Créez et activez des fichiers unités systemd pour un pod en utilisant les exemples ci-dessus comme référence et utilisez systemctl pour effectuer des opérations.

Comme systemctl utilise par défaut l'utilisateur root, toutes les modifications effectuées avec systemctl peuvent être vues en ajoutant sudo aux commandes de la ligne de commande podman. Pour effectuer des actions systemctl en tant qu'utilisateur non-root, utilisez le drapeau --user lors de l'interaction avec systemctl.

Note : Si les conteneurs ou pods créés précédemment utilisent des ressources partagées, comme des ports, assurez-vous de les supprimer avant de démarrer les unités systemd générées.

$ systemctl --user start pod-systemd-pod.service
$ podman pod ps
POD ID         NAME          STATUS    CREATED          # OF CONTAINERS   INFRA ID
0815c7b8e7f5   systemd-pod   Running   29 minutes ago   2                 6c5d116f4bbe
$ sudo podman ps # 0 Number of pods on root.
CONTAINER ID  IMAGE  COMMAND  CREATED  STATUS  PORTS  NAMES
$ systemctl stop pod-systemd-pod.service
$ podman pod ps
POD ID         NAME          STATUS   CREATED          # OF CONTAINERS   INFRA ID
272d2813c798   systemd-pod   Exited   29 minutes ago   2                 6c5d116f4bbe

Créez un conteneur alpine simple et générez le fichier unité systemd avec le drapeau --new drapeau. Activez le service et contrôlez les opérations à l'aide des commandes systemctl.

Note : Lors du démarrage du conteneur avec systemctl start plutôt que de modifier le conteneur déjà en cours d'exécution, cela lance un conteneur « nouveau » avec une configuration similaire.

# Enable the service.
$ sudo podman ps -a
CONTAINER ID  IMAGE                            COMMAND  CREATED        STATUS     PORTS  NAMES
bb310a0780ae  docker.io/library/alpine:latest  /bin/sh  2 minutes ago  Created           busy_moser
$ sudo systemctl start container-busy_moser.service
$ sudo podman ps -a
CONTAINER ID  IMAGE                            COMMAND  CREATED        STATUS        PORTS      NAMES
772df2f8cf3b  docker.io/library/alpine:latest  /bin/sh  1 second ago   Up 1 second              distracted_albattani
bb310a0780ae  docker.io/library/alpine:latest  /bin/sh  3 minutes ago  Created                  busy_moser
