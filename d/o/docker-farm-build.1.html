podman farm build Construit une image sur tous les nœuds d'une ferme et les regroupe dans une liste de manifestes. Il exécute

la commande

podman build sur les nœuds de la ferme avec le Containerfile fourni. Une fois les images construites sur tous les nœuds de la ferme, les images seront poussées vers le registre donné via l'indicateur --tag. Une fois toutes les images poussées, une liste de manifestes sera créée localement et poussée vers le registre également. La liste de manifestes contiendra une image par type d'architecture natif présent dans la

ferme.

La fonction principale de cette commande est de créer des compilations multi-architectures qui seront plus rapides que de le faire via l'émulation en

utilisant

podman build --arch --platform. Si aucune ferme n'est spécifiée, la compilation sera envoyé

e à tous les nœuds connus par

podman system connection. Remarque : Comme les images construites sont directement poussées vers un registre, l'utilisateur doit fournir un nom d'image complet en utilisant

l'option

--memory, -m=nombre[unité]

Limite de mémoire. Une unité peut être b (octets), k (kibioctets), m (mébioctets), ou g (gibioctets).

Permet de contraindre la mémoire disponible pour un conteneur. Si l'hôte prend en charge la mémoire swap, le réglage de mémoire -m peut être supérieur à la RAM physique. Cette option n'est pas prise en charge sur les systèmes sans racine cgroups V1.

--network=mode, --net

Définit la configuration des espaces de noms réseau lors du traitement des instructions RUN.

Les valeurs de mode valides sont :

  • none : pas de réseau.
  • host : utilise la pile réseau de l'hôte Podman. Note : le mode host donne au conteneur un accès complet aux services système locaux tels que D-bus et est donc considéré comme non sécurisé.
  • ns:chemin : chemin vers un espace de noms réseau à rejoindre.
  • private : crée un nouvel espace de noms pour le conteneur (par défaut)
  • <nom_réseau|ID> : rejoint le réseau avec le nom ou l'ID donné, par exemple, utilisez --network monreseau pour rejoindre le réseau nommé monreseau. Uniquement pris en charge pour les utilisateurs rootful.
  • slirp4netns[:OPTIONS,...] : utilise slirp4netns(1) pour créer une pile réseau utilisateur. Il est possible de spécifier ces options supplémentaires, elles peuvent également être définies avec network_cmd_options dans containers.conf :
  • allow_host_loopback=true|false : autorise slirp4netns à atteindre l'IP de boucle locale de l'hôte (par défaut 10.0.2.2 ou la deuxième IP du sous-réseau CIDR de slirp4netns lorsqu'il est modifié, voir l'option cidr ci-dessous). La valeur par défaut est false.
  • mtu=MTU : spécifie la MTU à utiliser pour ce réseau. (Par défaut 65520).
  • cidr=CIDR : spécifie la plage d'IP à utiliser pour ce réseau. (Par défaut 10.0.2.0/24).
  • enable_ipv6=true|false : active l'IPv6. Par défaut, true. (Requis pour outbound_addr6).
  • outbound_addr=INTERFACE : spécifie l'interface sortante sur laquelle slirp se lie (trafic ipv4 uniquement).
  • outbound_addr=IPv4 : spécifie l'adresse ipv4 sortante sur laquelle slirp se lie.
  • outbound_addr6=INTERFACE : spécifie l'interface sortante sur laquelle slirp se lie (trafic ipv6 uniquement).
  • outbound_addr6=IPv6 : spécifie l'adresse ipv6 sortante sur laquelle slirp se lie.
•
pasta[:OPTIONS,...] : utilise pasta(1) pour créer une pile réseau en mode utilisateur.
C'est la valeur par défaut pour les conteneurs sans racine et uniquement prise en charge en mode sans racine.
Par défaut, les adresses et routes IPv4 et IPv6, ainsi que le nom de l'interface du pod, sont copiés de l'hôte. Si le transfert de ports n'est pas configuré, les ports sont transférés dynamiquement lorsque des services sont liés des deux côtés (espace de noms d'initialisation ou espace de noms du conteneur). Le transfert de ports préserve l'adresse IP source d'origine. Les options décrites dans pasta(1) peuvent être spécifiées comme arguments séparés par des virgules.
En termes d'options de pasta(1), --config-net est donné par défaut, afin de configurer le réseau lorsque le conteneur est démarré, et --no-map-gw est également supposé par défaut, pour éviter l'accès direct du conteneur à l'hôte en utilisant l'adresse de la passerelle. Ce dernier peut être remplacé en passant --map-gw dans les options spécifiques à pasta (malgré le fait qu'il ne s'agisse pas d'une véritable option de pasta(1)).
De plus, -t none et -u none sont passés pour désactiver le transfert automatique de ports basé sur les ports liés. De même, -T none et -U none sont donnés pour désactiver la même fonctionnalité du conteneur vers l'hôte.
Quelques exemples :
  • pasta:--map-gw : permet au conteneur d'atteindre directement l'hôte en utilisant l'adresse de la passerelle.
  • pasta:--mtu,1500 : spécifie une MTU de 1500 octets pour l'interface tap dans le conteneur.
  • pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp, équivalent aux options par défaut de slirp4netns(1) : désactive l'IPv6, attribue 10.0.2.0/24 à l'interface tap0 dans le conteneur, avec une passerelle 10.0.2.3, active le relais DNS joignable à 10.0.2.3, définit la MTU à 1500 octets, désactive NDP, DHCPv6 et DHCP.
  • pasta:-I,tap0,--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,--no-ndp,--no-dhcpv6,--no-dhcp, équivalent aux options par défaut de slirp4netns(1) avec les remplacements de Podman : identique à ce qui précède, mais laisse la MTU à 65520 octets
  • pasta:-t,auto,-u,auto,-T,auto,-U,auto : active le transfert automatique de ports basé sur les ports liés observés des deux côtés (hôte et conteneur)
  • pasta:-T,5201 : active le transfert du port TCP 5201 du conteneur vers l'hôte, en utilisant l'interface de boucle locale au lieu de l'interface tap pour améliorer les performances

--no-cache

N'utilise pas les images mises en cache existantes pour la construction du conteneur. Construit à partir du début avec un nouvel ensemble de couches mises en cache.

--no-hostname

Ne crée pas le fichier /etc/hostname dans les conteneurs.

Par défaut, Podman gère le fichier /etc/hostname, en ajoutant le propre nom d'hôte du conteneur. Lorsque l'option --no-hostname est définie, le fichier /etc/hostname de l'image sera conservé sans modification s'il existe.

--no-hosts

Ne modifie pas le fichier /etc/hosts dans le conteneur.

Podman prend le contrôle du fichier /etc/hosts du conteneur par défaut et ajoute des entrées pour le nom du conteneur (voir l'option --name) et le nom d'hôte (voir l'option --hostname), les hôtes internes host.containers.internal et host.docker.internal, ainsi que tout nom d'hôte ajouté à l'aide de l'option --add-host. Se référer à l'option --add-host pour plus de détails. Passer --no-hosts désactive cela, de sorte que le fichier /etc/hosts de l'image est conservé sans modification. La même chose peut être obtenue globalement en définissant no_hosts=true dans containers.conf.

Cette option est en conflit avec --add-host.

--omit-history

Omet les informations d'historique de construction dans l'image construite. (par défaut false).

Cette option est utile dans les cas où les utilisateurs finaux souhaitent explicitement définir --omit-history pour omettre l'historique facultatif des images construites ou lors de la manipulation d'images construites à l'aide d'outils de construction qui n'incluent pas les informations d'historique dans leurs images.

--os-feature=feature

Définit le nom d'une fonctionnalité du système d'exploitation requise pour l'image en cours de construction. Par défaut, si l'image n'est pas basée sur scratch, la liste des fonctionnalités OS requises de l'image de base est conservée, si l'image de base en a spécifié. Cette option n'est généralement significative que lorsque le système d'exploitation de l'image est Windows.

Par défaut, si l'image n'est pas basée sur scratch, la version de l'OS requise de l'image de base est conservée, si l'image de base en a spécifié une. Cette option n'est généralement significative que lorsque le système d'exploitation de l'image est Windows, et est généralement définie dans les images de base Windows, donc l'utilisation de cette option est généralement inutile.

--pull=policy

Politique de téléchargement de l'image. La valeur par défaut est missing.

  • always : Télécharge toujours l'image et génère une erreur si le téléchargement échoue.
  • missing : Ne télécharge l'image que lorsqu'elle n'existe pas dans le stockage local des conteneurs. Génère une erreur si aucune image n'est trouvée et que le téléchargement échoue.
  • never : Ne télécharge jamais l'image mais utilise celle du stockage local des conteneurs. Génère une erreur lorsqu'aucune image n'est trouvée.
  • newer : Télécharge si l'image du registre est plus récente que celle du stockage local des conteneurs. Une image est considérée comme plus récente lorsque ses digests sont différents. La comparaison des horodatages est sujette à erreurs. Les erreurs de téléchargement sont supprimées si une image locale a été trouvée.

--sbom-merge-strategy=méthode

Si plusieurs valeurs de --sbom-scanner-command sont utilisées, utilise la méthode spécifiée pour fusionner la sortie des commandes ultérieures avec la sortie des commandes antérieures. Les valeurs reconnues incluent :

  • cat
    Concatène les fichiers.
  • merge-cyclonedx-by-component-name-and-version
    Fusionne les champs "component" des documents JSON, en ignorant les valeurs des
    documents lorsque la combinaison de leurs valeurs "name" et "version" est
    déjà présente. Les documents sont traités dans l'ordre où ils sont
    générés, c'est-à-dire l'ordre dans lequel les commandes qui les génèrent
    ont été spécifiées.
  • merge-spdx-by-package-name-and-versioninfo
    Fusionne les champs "package" des documents JSON, en ignorant les valeurs des
    documents lorsque la combinaison de leurs valeurs "name" et "versionInfo" est
    déjà présente. Les documents sont traités dans l'ordre où ils sont
    générés, c'est-à-dire l'ordre dans lequel les commandes qui les génèrent
    ont été spécifiées.

Génère des SBOMs en exécutant la commande spécifiée à partir de l'image du scanner. Si plusieurs commandes sont spécifiées, elles sont exécutées dans l'ordre dans lequel elles sont spécifiées. Ces substitutions de texte sont effectuées :

- {CONTEXT}

- {OUTPUT}

--secret=id=id[,src=envOuFichier][,env=ENV][,type=fichier | env]

Transmet des informations secrètes à utiliser dans le Containerfile pour construire des images de manière sécurisée, afin qu'elles ne soient pas stockées dans l'image finale, ni visibles dans d'autres étapes. La valeur du secret sera lue à partir d'une variable d'environnement ou d'un fichier nommé par l'option "id", ou nommé par l'option "src" si elle est spécifiée, ou à partir d'une variable d'environnement spécifiée par l'option "env". Voir EXEMPLES ⟨#examples⟩. Le secret sera monté dans le conteneur sur /run/secrets/id par défaut.

Pour utiliser ultérieurement le secret, utilisez l'indicateur --mount dans une instruction RUN au sein d'un Containerfile :

RUN --mount=type=secret,id=monsecret cat /run/secrets/monsecret

L'emplacement du secret dans le conteneur peut être remplacé en utilisant l'option "target", "dst" ou "destination" de l'indicateur RUN --mount.

RUN --mount=type=secret,id=monsecret,target=/run/secrets/monautresecret cat /run/secrets/monautresecret

Remarque : la modification du contenu des fichiers secrets ne déclenchera pas de reconstruction des couches qui utilisent ces secrets.

  • label=level:LEVEL : Définit le niveau de label pour les processus du conteneur
  • label=filetype:TYPE : Définit le type de fichier de label pour les fichiers du conteneur
  • label=disable : Désactive la séparation des labels pour le conteneur
  • no-new-privileges : Empêche les processus du conteneur d'acquérir des privilèges supplémentaires
  • seccomp=unconfined : Désactive le confinement seccomp pour le conteneur
  • seccomp=profile.json : Fichier JSON à utiliser comme filtre seccomp pour le conteneur.

--shm-size=nombre[unité]

Taille de /dev/shm. Une unité peut être b (octets), k (kibioctets), m (mébioctets) ou g (gibioctets). Si l'unité est omise, le système utilise les octets. Si la taille est omise, la valeur par défaut est

64m. Lorsque la taille est de 0, il n'y a aucune limite à la quantité de mémoire utilisée pour l'IPC par le conteneur. Cette option est en conflit avec --ipc=host.

--skip-unused-stages

Ignore les étapes des builds multi-étapes qui n'affectent pas l'étape cible. (Par défaut : true).

--source-date-epoch=secondes

Définit l'horodatage de "création" de l'image construite sur ce nombre de secondes depuis l'époque (Unix time 0, c'est-à-dire 00:00:00 UTC le 1er janvier 1970) (par défaut, utilise la valeur définie dans la variable d'environnement SOURCE_DATE_EPOCH, ou l'heure actuelle si elle n'est pas définie).

L'horodatage de "création" est écrit dans la configuration et le manifeste de l'image lors de la validation de l'image, de sorte que l'exécution de la même construction deux fois différentes produira normalement des images avec des hachages sha256 différents, même si aucun autre changement n'a été apporté au Containerfile et au contexte de construction.

Lorsque ce drapeau est défini, un argument de construction SOURCE_DATE_EPOCH fournira sa valeur pour une étape dans laquelle il est déclaré.

Lorsque ce drapeau est défini, l'horodatage "créé" de la configuration de l'image est toujours défini sur l'heure spécifiée, ce qui devrait permettre de construire des images identiques à différents moments en utilisant le même ensemble d'entrées.

Lorsque ce drapeau est défini, la sortie écrite comme spécifié dans l'option --output portera exactement l'horodatage spécifié.

En conflit avec l'option similaire --timestamp, qui définit également l'heure spécifiée sur le contenu des nouvelles couches.

--squash

Fusionne toutes les nouvelles couches de l'image en une seule nouvelle couche ; les couches préexistantes ne sont pas fusionnées.

--squash-all

Fusionne toutes les couches de la nouvelle image (y compris celles héritées d'une image de base) en une seule nouvelle couche.

--ssh=default | id=socket>

Socket de l'agent SSH ou clés à exposer à la construction. Le chemin du socket peut être laissé vide pour utiliser la valeur de default=$SSH_AUTH_SOCK

Pour utiliser plus tard l'agent ssh, utilisez l'option --mount dans une instruction RUN au sein d'un Containerfile :

RUN --mount=type=ssh,id=id mycmd

--tag, -t=nomImage

Définit le nom qui est attribué à l'image résultante si le processus de construction se termine avec succès. Si nomImage n'inclut pas de nom de registre, le nom de registre localhost est préfixé au nom de l'image.

--target=nomEtape

Définit l'étape de construction cible à construire. Lors de la construction d'un Containerfile avec plusieurs étapes de construction, --target peut être utilisé pour spécifier une étape de construction intermédiaire par son nom comme étape finale pour l'image résultante. Les commandes après l'étape cible sont ignorées.

--timestamp=secondes

Définit l'horodatage de création sur les secondes depuis l'époque pour permettre des constructions déterministes (par défaut, l'heure actuelle). Par défaut, l'horodatage de création est modifié et écrit dans le manifeste de l'image à chaque validation, provoquant une différence dans le hachage sha256 de l'image même si les sources sont exactement les mêmes autrement. Lorsque --timestamp est défini, l'horodatage de création est toujours défini sur l'heure spécifiée et donc inchangé, permettant au hachage sha256 de l'image de rester le même. Tous les fichiers validés dans les couches de l'image sont créés avec cet horodatage.

Si la seule instruction dans un Containerfile est FROM, ce drapeau n'a aucun effet.

--tls-verify

Exige HTTPS et vérifie les certificats lors du contact avec les registres (par défaut : true). S'il est explicitement défini sur true, la vérification TLS est utilisée. S'il est défini sur false, la vérification TLS n'est pas utilisée. Si non spécifié, la vérification TLS est utilisée sauf si le registre cible est répertorié comme registre non sécurisé dans containers-registries.conf(5)

--ulimit=type=limite-douce[:limite-stricte]

Spécifie les limites de ressources à appliquer aux processus lancés lors du traitement des instructions RUN. Cette option peut être spécifiée plusieurs fois. Les types de ressources reconnus incluent :
"core" : taille maximale du dump core (ulimit -c)
"cpu" : temps CPU maximal (ulimit -t)
"data" : taille maximale du segment de données d'un processus (ulimit -d)
"fsize" : taille maximale des nouveaux fichiers (ulimit -f)
"locks" : nombre maximal de verrous de fichiers (ulimit -x)
"memlock" : quantité maximale de mémoire verrouillée (ulimit -l)
"msgqueue" : quantité maximale de données dans les files d'attente de messages (ulimit -q)
"nice" : ajustement de la courtoisie (nice -n, ulimit -e)
"nofile" : nombre maximal de fichiers ouverts (ulimit -n)
"nproc" : nombre maximal de processus (ulimit -u)
"rss" : taille maximale de la mémoire résidente d'un processus (ulimit -m)
"rtprio" : priorité d'ordonnancement temps réel maximale (ulimit -r)
"rttime" : temps d'exécution temps réel maximal entre les appels système bloquants
"sigpending" : nombre maximal de signaux en attente (ulimit -i)
"stack" : taille maximale de la pile (ulimit -s)

Supprime l'annotation de l'image, ce qui empêche l'annotation d'être héritée de l'image de base.

--unsetenv=env

Supprime les variables d'environnement de l'image finale.

--unsetlabel=label

Supprime le label de l'image, ce qui empêche le label d'être hérité de l'image de base.

--userns=how

Définit la configuration des espaces de noms utilisateur lors du traitement des instructions RUN. La valeur configurée peut être "" (chaîne vide) ou "container" pour indiquer qu'un nouvel espace de noms utilisateur est créé, elle peut être "host" pour indiquer que l'espace de noms utilisateur dans lequel podman lui-même est exécuté est réutilisé, ou elle peut être le chemin vers un espace de noms utilisateur déjà utilisé par un autre processus.

--userns-gid-map=mapping

Spécifie directement une cartographie GID à utiliser pour définir la propriété, au niveau du système de fichiers, du contenu du conteneur de travail. Les commandes exécutées lors du traitement des instructions RUN sont exécutées par défaut dans leurs propres espaces de noms utilisateur, configurés à l'aide des cartographies UID et GID.

Les entrées de cette cartographie prennent la forme d'un ou plusieurs triplets : un GID de départ dans le conteneur, un GID de départ correspondant au niveau de l'hôte, et le nombre d'ID consécutifs que représente l'entrée de la cartographie.

Cette option remplace le paramètre remap-gids dans la section options de /etc/containers/storage.conf.

Si cette option n'est pas spécifiée, mais qu'un paramètre global --userns-gid-map est fourni, les paramètres de l'option globale sont utilisés.

Si aucun de --userns-uid-map-user, --userns-gid-map-group, ou --userns-gid-map n'est spécifié, mais que --userns-uid-map est spécifié, la cartographie GID est définie pour utiliser les mêmes valeurs numériques que la cartographie UID.

--userns-gid-map-group=groupe

Spécifie qu'une cartographie GID à utiliser pour définir la propriété, au niveau du système de fichiers, du contenu du conteneur de travail, peut être trouvée dans les entrées du fichier /etc/subgid correspondant au groupe spécifié. Les commandes exécutées lors du traitement des instructions RUN sont exécutées par défaut dans leurs propres espaces de noms utilisateur, configurés à l'aide des cartographies UID et GID. Si --userns-uid-map-user est spécifié, mais --userns-gid-map-group n'est pas spécifié, podman suppose que le nom d'utilisateur spécifié est également un nom de groupe approprié à utiliser comme paramètre par défaut pour cette option.

NOTE : Lorsque cette option est spécifiée par un utilisateur sans privilèges (rootless), les cartographies spécifiées sont relatives à l'espace de noms utilisateur sans privilèges dans le conteneur, plutôt que relatives à l'hôte comme c'est le cas lorsqu'il est exécuté avec des privilèges.

Les commandes exécutées lors du traitement des instructions RUN sont exécutées par défaut dans leurs propres espaces de noms utilisateur, configurés à l'aide des cartographies UID et GID.

Les entrées de cette cartographie prennent la forme d'un ou plusieurs triplets : un UID de départ dans le conteneur, un UID de départ correspondant au niveau de l'hôte, et le nombre d'ID consécutifs que représente l'entrée de la cartographie.

Changement de propriétaire des points de montage de

volumes

Par défaut, Podman ne modifie pas le propriétaire et le groupe des répertoires sources des volumes montés. Lors de l'exécution avec des espaces de noms d'utilisateurs, l'UID et le GID à l'intérieur de l'espace de noms peuvent correspondre à un autre UID et GID sur

l'hôte.

Le suffixe :U indique à Podman d'utiliser l'UID et le GID de l'hôte corrects, basés sur l'UID et le GID au sein de l'espace de noms, pour changer récursivement le propriétaire et le groupe du volume

source.

Avertissement : utilisez avec précaution car cela modifie le système de fichiers de

l'hôte.

Étiquetage des points de montage de

volumes

Les systèmes d'étiquetage comme SELinux exigent que des étiquettes appropriées soient placées sur le contenu des volumes montés dans un conteneur. Sans étiquette, le système de sécurité peut empêcher les processus s'exécutant à l'intérieur du conteneur d'utiliser le contenu. Par défaut, Podman ne modifie pas les étiquettes définies par le système

d'exploitation.

Pour changer une étiquette dans le contexte du conteneur, ajoutez l'un de ces deux suffixes :z ou :Z au point de montage du volume. Ces suffixes indiquent à Podman de réétiqueter les objets de fichiers sur les volumes partagés. L'option z indique à Podman que deux conteneurs partagent le contenu du volume. En conséquence, Podman étiquette le contenu avec une étiquette de contenu partagé. Les étiquettes de volume partagées permettent à tous les conteneurs de lire/écrire le contenu. L'option Z indique à Podman d'étiqueter le contenu avec une étiquette privée non partagée. Seul le conteneur actuel peut utiliser un volume

privé.

Remarque : ne réétiquetez pas les fichiers et répertoires du système. La réétiquetage du contenu système peut provoquer la défaillance d'autres services confinés sur la machine hôte. Pour ce type de conteneurs, il est recommandé de désactiver la séparation SELinux. L'option --security-opt label=disable désactive la séparation SELinux pour le conteneur. Par exemple, si un utilisateur souhaite monter l'intégralité de son répertoire personnel dans les conteneurs de construction, il doit désactiver la séparation

SELinux. 
$ podman build --security-opt label=disable -v $HOME:/home/user
.

Points de montage

Overlay

L'indicateur :O indique à Podman de monter le répertoire de l'hôte comme stockage temporaire en utilisant le système de fichiers Overlay. Les conteneurs des commandes RUN sont autorisés à modifier le contenu du point de montage et celui-ci est stocké dans le stockage du conteneur dans un répertoire séparé. En termes Overlay FS, le répertoire source est le niveau inférieur (lower) et le répertoire de stockage du conteneur est le niveau supérieur (upper). Les modifications du point de montage sont détruites lorsque la commande RUN a fini de s'exécuter, de manière similaire à un point de montage

tmpfs.

Toute exécution ultérieure de commandes RUN voit le contenu du répertoire source original, les modifications des commandes RUN précédentes n'existent

plus.

Un cas d'utilisation du montage overlay est le partage du cache de paquets de l'hôte vers le conteneur afin d'accélérer les

constructions.

    • fonctionne.

Par défaut, les volumes montés par liaison sont privés. Cela signifie que les montages effectués à l'intérieur des conteneurs ne sont pas visibles sur l'hôte et inversement. Ce comportement peut être modifié en spécifiant une propriété de propagation du montage de

volume.

Lorsque la politique de propagation du montage est définie sur shared, tout montage effectué à l'intérieur du conteneur sur ce volume est visible à la fois par l'hôte et le conteneur. Lorsque la politique de propagation du montage est définie sur slave, la propagation de montage unidirectionnelle est activée et tout montage effectué sur l'hôte pour ce volume n'est visible qu'à l'intérieur du contrôleur. Pour contrôler la propriété de propagation du montage d'un volume, utilisez l'indicateur de propagation :[r]shared, :[r]slave ou :[r]private. Pour que la propagation du montage fonctionne, le point de montage source (le point de montage sur lequel le répertoire source est monté) doit avoir les propriétés de propagation appropriées. Pour les volumes partagés, le point de montage source doit être partagé. Et pour les volumes esclaves (slave), le montage source doit être soit partagé, soit esclave. [1]

⟨#Footnote1⟩

Utilisez df <source-dir> pour déterminer le montage source et puis utilisez findmnt -o TARGET,PROPAGATION <source-mount-dir> pour déterminer les propriétés de propagation du montage source. Si l'utilitaire findmnt n'est pas disponible, le point de montage source peut être déterminé en examinant l'entrée de montage dans /proc/self/mountinfo. Regardez les champs optionnels et voyez si des propriétés de propagation sont spécifiées. shared:X signifie que le montage est shared, master:X signifie que le montage est slave et s'il n'y a rien, cela signifie que le montage est private.
