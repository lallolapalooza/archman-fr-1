podman-pod-create(1) Manuel des commandes générales podman-pod-create(1)

NOM

podman-pod-create - Crée un nouveau pod

SYNTAXE

podman pod create [options] [nom]

DESCRIPTION

Crée un pod vide, ou unité de plusieurs conteneurs, et le prépare à recevoir des conteneurs. Le pod peut être créé avec un nom spécifique. Si aucun nom n'est donné, un nom aléatoire est généré. L'ID du pod est affiché sur STDOUT. Vous pouvez ensuite utiliser podman create --pod <id_pod|nom_pod> ... pour ajouter des conteneurs au pod, et podman pod start <id_pod|nom_pod> pour démarrer le pod.

L'opérateur peut identifier un pod de trois manières : identifiant long UUID (“f78375b1c487e03c9438c729345e54db9d20cfa2ac1fc3494b6eb60872e74778”) identifiant court UUID (“f78375b1c487”) Nom (“jonah”)

Podman génère un UUID pour chaque pod, et si aucun nom n'est assigné au conteneur avec --name, un nom de chaîne aléatoire lui est généré. Ce nom est utile pour identifier un pod.

Note : les indicateurs liés aux limites de ressources fonctionnent en définissant explicitement les limites dans le cgroup parent du pod pour tous les conteneurs rejoignant le pod. Un conteneur peut outrepasser les limites de ressources lors de son ajout au pod. Par exemple, si un pod a été créé via podman pod create --cpus=5, spécifier podman container create --pod=<id_pod|nom_pod> --cpus=4 fait que le conteneur utilise la limite la plus basse. De plus, les conteneurs qui spécifient leur propre cgroup, tel que --cgroupns=host, ne reçoivent PAS les ressources cgroup assignées au niveau du pod.

OPTIONS

--add-host=nom_hote[;nom_hote[;...]]:ip

Ajoute un mappage personnalisé hôte-IP au fichier /etc/hosts du pod.

L'option prend un ou plusieurs noms d'hôtes séparés par des points-virgules à mapper à une seule adresse IPv4 ou IPv6, séparés par un deux-points. Elle peut également être utilisée pour écraser les adresses IP des noms d'hôtes que Podman ajoute à /etc/hosts par défaut (voir aussi les options --name et --hostname). Cette option peut être spécifiée plusieurs fois pour ajouter des mappages supplémentaires à /etc/hosts. Elle entre en conflit avec l'option --no-hosts et avec no_hosts=true dans containers.conf.

Au lieu d'une adresse IP, le drapeau spécial host-gateway peut être donné. Cela se résout en une adresse IP que le conteneur peut utiliser pour se connecter à l'hôte. L'adresse IP choisie dépend de votre configuration réseau, il n'y a donc aucune garantie que Podman puisse déterminer automatiquement l'adresse host-gateway, ce qui entraînera une erreur Podman. Vous pouvez écraser cette adresse IP en utilisant l'option host_containers_internal_ip dans containers.conf.

L'adresse host-gateway est également utilisée par Podman pour ajouter automatiquement les noms d'hôtes host.containers.internal et host.docker.internal à /etc/hosts. Vous pouvez l'empêcher soit en donnant l'option --no-hosts, soit en définissant host_containers_internal_ip="none" dans containers.conf. Si aucune adresse host-gateway n'a été configurée manuellement et que Podman ne parvient pas à déterminer l'adresse IP automatiquement, Podman omettra silencieusement l'ajout de ces noms d'hôtes internes à /etc/hosts. Si Podman s'exécute dans une machine virtuelle à l'aide de podman machine (ce qui inclut les hôtes Mac et Windows), Podman omettra silencieusement l'ajout des noms d'hôtes internes à /etc/hosts, à moins qu'une adresse IP n'ait été configurée manuellement ; les noms d'hôtes internes sont résolus par le résolveur DNS de gvproxy à la place.

Podman utilisera par défaut le fichier /etc/hosts de l'hôte comme base, c'est-à-dire que tout nom d'hôte présent dans ce fichier sera également présent dans le fichier /etc/hosts du conteneur. Un fichier de base différent peut être configuré en utilisant la configuration base_hosts_file dans containers.conf.

Le fichier /etc/hosts est partagé entre tous les conteneurs du pod.

--blkio-weight=poids

Poids relatif pour les entrées/sorties bloc. Le poids est une valeur comprise entre 10 et 1000.

Cette option n'est pas prise en charge sur les systèmes sans privilèges (rootless) utilisant cgroups V1.

--blkio-weight-device=périphérique:poids

Poids relatif du périphérique pour les entrées/sorties bloc.

--cgroup-parent=chemin

Chemin vers les cgroups sous lequel le cgroup pour le pod est créé. Si le chemin n'est pas absolu, il est considéré comme relatif au chemin des cgroups du processus d'initialisation. Les cgroups sont créés s'ils n'existent pas déjà.

--cpu-shares, -c=parts

Parts CPU (poids relatif).

Par défaut, tous les conteneurs obtiennent la même proportion de cycles CPU. Cette proportion peut être modifiée en changeant le poids partagé du CPU du conteneur par rapport au poids combiné de tous les conteneurs en cours d'exécution. Le poids par défaut est 1024.

La proportion ne s'applique que lorsque des processus gourmands en CPU sont en cours d'exécution. Lorsque les tâches dans un conteneur sont inactives, d'autres conteneurs peuvent utiliser le temps CPU restant. La quantité réelle de temps CPU varie en fonction du nombre de conteneurs en cours d'exécution sur le système.

Par exemple, considérons trois conteneurs, l'un ayant une part CPU de 1024 et les deux autres un réglage de part CPU de 512. Lorsque les processus de tous les trois conteneurs tentent d'utiliser 100% du CPU, le premier conteneur reçoit 50% du temps CPU total. Si un quatrième conteneur est ajouté avec une part CPU de 1024, le premier conteneur n'obtient que 33% du CPU. Les conteneurs restants reçoivent respectivement 16,5%, 16,5% et 33% du CPU.

Sur un système multi-cœurs, les parts de temps CPU sont distribuées sur tous les cœurs CPU. Même si un conteneur est limité à moins de 100% du temps CPU, il peut utiliser 100% de chaque cœur CPU individuel.

Par exemple, considérons un système avec plus de trois cœurs. Si le conteneur C0 est démarré avec --cpu-shares=512 exécutant un processus, et un autre conteneur C1 avec --cpu-shares=1024 exécutant deux processus, cela peut entraîner la division suivante des parts CPU :

PID conteneur CPU Part CPU
100 C0 0 100% du CPU0
101 C1 1 100% du CPU1
102 C1 2 100% du CPU2

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non-root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans privilèges (rootless) utilisant cgroups V1.

--cpus=quantité

Définit le nombre total de CPU délégués au pod. Par défaut, 0.000, ce qui indique qu'il n'y a pas de limite à la puissance de calcul.

--cpuset-cpus=numéro

CPU dans lesquels autoriser l'exécution. Peut être spécifié sous forme de liste séparée par des virgules (par ex. 0,1), de plage (par ex. 0-3), ou de toute combinaison (par ex. 0-3,7,11-15).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non-root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans privilèges (rootless) utilisant cgroups V1.

--cpuset-mems=nœuds

Nœuds mémoire (MEMs) dans lesquels autoriser l'exécution (0-3, 0,1). Uniquement efficace sur les systèmes NUMA.

S'il y a quatre nœuds mémoire sur le système (0-3), utilisez --cpuset-mems=0,1, puis les processus du conteneur n'utilisent que la mémoire des deux premiers nœuds mémoire.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non-root. Pour plus de détails, voir https://github.com /containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

--device=périphérique-hôte[:périphérique-conteneur][:permissions]

Ajoute un périphérique hôte au pod. Le paramètre optionnel permissions peut être utilisé pour spécifier les permissions du périphérique en combinant r pour lire, w pour écrire et m pour mknod(2).

Exemple : --device=/dev/sdc:/dev/xvdc:rwm.

Remarque : si périphérique-hôte est un lien symbolique, il est d'abord résolu. Le pod ne stocke que les numéros majeur et mineur du périphérique hôte.

Podman peut charger les modules du noyau requis pour utiliser le périphérique spécifié. Les périphériques pour lesquels Podman charge des modules si nécessaire sont : /dev/fuse.

En mode sans root, le nouveau périphérique est monté en bind dans le conteneur depuis l'hôte plutôt que Podman ne le crée dans l'espace du conteneur. Comme le montage en bind conserve son label SELinux sur les systèmes SELinux, le conteneur peut recevoir une erreur de permission lors de l'accès au périphérique monté. Modifiez les paramètres SELinux pour autoriser les conteneurs à utiliser tous les labels de périphérique via la commande suivante :

$ sudo setsebool -P container_use_devices=true

Remarque : le pod implémente les périphériques en stockant la configuration initiale passée par l'utilisateur et en recréant le périphérique à chaque conteneur ajouté au pod.

--device-read-bps=chemin:taux

Limite le taux de lecture (en octets par seconde) d'un périphérique (par ex. --device-read-bps=/dev/sda:1mo).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

--device-write-bps=chemin:taux

Limite le taux d'écriture (en octets par seconde) vers un périphérique (par ex. --device-write-bps=/dev/sda:1mo).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

--dns=adresse-ip

Définit des serveurs DNS personnalisés dans le fichier /etc/resolv.conf qui est partagé entre tous les conteneurs du pod. Une option spéciale, "none", est autorisée et désactive la création de /etc/resolv.conf pour le pod.

--dns-option=option

Définit des options DNS personnalisées dans le fichier /etc/resolv.conf qui est partagé entre tous les conteneurs du pod.

--dns-search=domaine

Définit des domaines de recherche DNS personnalisés dans le fichier /etc/resolv.conf qui est partagé entre tous les conteneurs du pod.

--exit-policy=continue | stop

Définit la politique de sortie du pod lorsque le dernier conteneur s'arrête. Les politiques prises en charge sont :

Politique de sortie Description
continue Le pod continue de s'exécuter, en maintenant son conteneur infra actif, lorsque le dernier conteneur s'arrête. Utilisé par défaut.
stop Le pod (y compris son conteneur infra) s'arrête lorsque le dernier conteneur s'arrête. Utilisé dans kube play et les quadlets.

--gidmap=gid-pod:gid-hôte:montant

Map GID pour l'espace utilisateur. L'utilisation de ce drapeau exécute tous les conteneurs du pod avec l'espace utilisateur activé. Il entre en conflit avec les drapeaux --userns et --subgidname.

--gpus=ENTREE

Périphériques GPU à ajouter au conteneur ('all' pour passer tous les GPU). Actuellement, seuls les périphériques Nvidia sont pris en charge.

--help, -h

Affiche l'énoncé d'utilisation.

--hostname=nom

Définit le nom d'hôte du pod à l'intérieur de tous les conteneurs.

Le nom d'hôte fourni est également ajouté au fichier /etc/hosts en utilisant l'adresse IP principale du conteneur (voir également l'option --add-host).

--hosts-file=chemin | none | image

Fichier de base pour créer le fichier /etc/hosts à l'intérieur du conteneur. Il doit s'agir soit d'un chemin absolu vers un fichier sur le système hôte, soit de l'un des drapeaux spéciaux suivants :
"" Utiliser le fichier de base base_hosts_file dans containers.conf (par défaut)
none Ne pas utiliser de fichier de base (c'est-à-dire commencer avec un fichier vide)
image Utiliser le fichier /etc/hosts de l'image du conteneur comme fichier de base

--infra

Crée un conteneur infra et l'associe au pod. Un conteneur infra est un conteneur léger utilisé pour coordonner l'espace de noms du noyau partagé d'un pod. Défaut : true.

--infra-command=commande

La commande exécutée pour démarrer le conteneur infra. Défaut : "/pause".

--infra-conmon-pidfile=fichier

Écrit le PID du processus conmon du conteneur infra dans un fichier. Comme conmon s'exécute dans un processus séparé de Podman, cela est nécessaire lors de l'utilisation de systemd pour gérer les conteneurs et les pods Podman.

--infra-image=image

L'image personnalisée utilisée pour le conteneur infra. Sauf spécification contraire, Podman construit une image locale personnalisée qui ne nécessite pas de téléchargement d'image.

--infra-name=nom

Le nom utilisé pour le conteneur infra du pod.

--ip=ipv4

Spécifie une adresse IPv4 statique pour le pod, par exemple 10.88.64.128. Cette option ne peut être utilisée que si le pod est joint à un seul réseau - c'est-à-dire que --network=nom-réseau est utilisé au plus une fois - et si le pod ne rejoint pas l'espace de noms réseau d'un autre conteneur via --network=container:id. L'adresse doit se trouver dans le pool d'adresses IP du réseau (par défaut 10.88.0.0/16).

Pour spécifier plusieurs adresses IP statiques par pod, définissez plusieurs réseaux en utilisant l'option --network avec une adresse IP statique spécifiée pour chacun en utilisant le mode ip pour cette option.

--ip6=ipv6

Spécifie une adresse IPv6 statique pour le pod, par exemple fd46:db93:aa76:ac37::10. Cette option ne peut être utilisée que si le pod est joint à un seul réseau - c'est-à-dire que --network=nom-réseau est utilisé au plus une fois - et si le pod ne rejoint pas l'espace de noms réseau d'un autre conteneur via --network=container:id. L'adresse doit se trouver dans le pool d'adresses IPv6 du réseau.

Pour spécifier plusieurs adresses IPv6 statiques par pod, définissez plusieurs réseaux en utilisant l'option --network avec une adresse IPv6 statique spécifiée pour chacun en utilisant le mode ip6 pour cette option.

--label, -l=clé=valeur

Ajoute des métadonnées à un pod.

--label-file=fichier

Lit un fichier de labels délimité par des sauts de ligne.

--mac-address=adresse

Adresse MAC de l'interface réseau du pod (par ex. 92:d0:c6:0a:29:33). Cette option ne peut être utilisée que si le pod est joint à un seul réseau - c'est-à-dire que --network=nom-réseau est utilisé au plus une fois - et si le pod ne rejoint pas l'espace de noms réseau d'un autre conteneur via --network=container:id.

N'oubliez pas que l'adresse MAC dans un réseau Ethernet doit être unique. L'adresse link-local IPv6 est basée sur l'adresse MAC du périphérique conformément à la RFC4862.

Pour spécifier plusieurs adresses MAC statiques par pod, définissez plusieurs réseaux en utilisant l'option --network avec une adresse MAC statique spécifiée pour chacun en utilisant le mode mac pour cette option.

--memory, -m=nombre[unité]

Limite de mémoire. Une unité peut être o (octets), k (kibioctets), m (mebioctets) ou g (gibioctets).

Permet de contraindre la mémoire disponible pour un conteneur. Si l'hôte prend en charge la mémoire swap, le réglage mémoire -m peut être supérieur à la RAM physique. Si une limite de 0 est spécifiée (sans utiliser -m), la mémoire du conteneur n'est pas limitée. La limite réelle peut être arrondie à un multiple de la taille de page du système d'exploitation (la valeur est très grande, c'est des millions de trillions).

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

--memory-swap=nombre[unité]

Une valeur limite égale à la mémoire plus le swap. Une unité peut être o (octets), k (kibioctets), m (mebioctets) ou g (gibioctets).

Doit être utilisé avec le drapeau -m (--memory). La valeur de l'argument doit être supérieure à celle de
-m (--memory). Par défaut, elle est définie sur le double de la valeur de --memory.

Définissez nombre sur -1 pour activer le swap illimité.

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

--name, -n=nom

Attribue un nom au pod.

--network=mode, --net

Définit le mode réseau pour le pod.

Les valeurs valides pour mode sont :

•
bridge[:OPTIONS,...] : Crée une pile réseau sur le pont par défaut. C'est le mode par défaut pour les conteneurs rootful. Il est possible de spécifier les options supplémentaires suivantes :
  • alias=nom : Ajoute un alias dans l'espace réseau pour le conteneur.
    • ip=IPv4 : Spécifiez une adresse IPv4 statique pour ce conteneur.
    • ip6=IPv6 : Spécifiez une adresse IPv6 statique pour ce conteneur.
    • mac=MAC : Spécifiez une adresse MAC statique pour ce conteneur.
    • interface_name=name : Spécifiez un nom pour l'interface réseau créée à l'intérieur du conteneur.
    • host_interface_name=name : Spécifiez un nom pour l'interface réseau créée à l'extérieur du conteneur.
Toute autre option sera transmise à netavark sans validation. Ceci peut être utile pour passer des arguments aux plugins netavark.

Par exemple, pour définir une adresse IPv4 statique et une adresse MAC statique, utilisez --network bridge:ip=10.88.0.10,mac=44:33:22:11:00:99.

  • <nom ou ID du réseau>[:OPTIONS,...] : Connectez-vous à un réseau défini par l'utilisateur ; il s'agit du nom ou de l'ID du réseau créé par podman network create. Il est possible de spécifier les mêmes options que celles décrites ci-dessus pour le mode bridge. Utilisez l'option --network plusieurs fois pour spécifier des réseaux supplémentaires.
    Pour des raisons de compatibilité ascendante, il est également possible de spécifier des réseaux séparés par des virgules sur le premier argument --network, mais cela vous empêche d'utiliser les options décrites dans la section bridge ci-dessus.
  • none : Créez un espace de noms réseau pour le conteneur mais ne configurez pas d'interfaces réseau pour celui-ci, de sorte que le conteneur n'ait aucune connectivité réseau.
  • container:id : Réutilisez la pile réseau d'un autre conteneur.
  • host : Utilisez l'espace de noms réseau de l'hôte pour le conteneur au lieu d'en créer un isolé. Attention : Cela donne au conteneur un accès complet aux sockets Unix abstraits et aux sockets TCP/UDP liés à localhost. Comme ces mécanismes sont souvent utilisés pour empêcher l'accès à des services système sensibles, en les isolant de l'accès par des entités externes, l'utilisation de cette option peut être considérée comme une vulnérabilité de sécurité.
  • ns:path : Chemin vers un espace de noms réseau à rejoindre.
  • private : Créez un nouvel espace de noms pour le conteneur. Ceci utilise le mode bridge pour les conteneurs rootful et slirp4netns pour les conteneurs rootless.
  • slirp4netns[:OPTIONS,...] : utilisez slirp4netns(1) pour créer une pile réseau utilisateur. Il est possible de spécifier ces options supplémentaires, qui peuvent également être définies avec network_cmd_options dans containers.conf :
  • allow_host_loopback=true|false : Autorise slirp4netns à atteindre l'IP de la boucle locale de l'hôte (par défaut 10.0.2.2 ou la deuxième IP du sous-réseau CIDR de slirp4netns lorsqu'il est modifié, voir l'option cidr ci-dessous). La valeur par défaut est false.
  • mtu=MTU : Spécifiez l'MTU à utiliser pour ce réseau. (Par défaut : 65520).
  • cidr=CIDR : Spécifiez la plage d'adresses IP à utiliser pour ce réseau. (Par défaut : 10.0.2.0/24).
  • enable_ipv6=true|false : Active l'IPv6. Par défaut : true. (Requis pour outbound_addr6).
  • outbound_addr=INTERFACE : Spécifiez l'interface sortante sur laquelle slirp se lie (trafic IPv4 uniquement).
  • outbound_addr=IPv4 : Spécifiez l'adresse IPv4 sortante sur laquelle slirp se lie.
  • outbound_addr6=INTERFACE : Spécifiez l'interface sortante sur laquelle slirp se lie (trafic IPv6 uniquement).
  • outbound_addr6=IPv6 : Spécifiez l'adresse IPv6 sortante sur laquelle slirp se lie.
  • port_handler=rootlesskit : Utilise rootlesskit pour le transfert de ports. Par défaut.
    Note : Rootlesskit modifie l'adresse IP source des paquets entrants vers une adresse IP de l'espace de noms réseau du conteneur, généralement 10.0.2.100. Si l'application nécessite la véritable adresse IP source, par exemple pour les journaux du serveur web, utilisez le gestionnaire de ports slirp4netns. Le gestionnaire de ports rootlesskit est également utilisé pour les conteneurs rootless connectés à des réseaux définis par l'utilisateur.
  • port_handler=slirp4netns : Utilise le transfert de ports slirp4netns, il est plus lent que rootlesskit mais préserve la bonne adresse IP source. Ce gestionnaire de ports ne peut pas être utilisé pour les réseaux définis par l'utilisateur.
•
pasta[:OPTIONS,...] : utilisez pasta(1) pour créer une pile réseau en mode utilisateur.
C'est la valeur par défaut pour les conteneurs rootless et uniquement prise en charge en mode rootless.
Par défaut, les adresses et routes IPv4 et IPv6, ainsi que le nom de l'interface pod, sont copiés de l'hôte. Le transfert de ports préserve l'adresse IP source d'origine. Les options décrites dans pasta(1) peuvent être spécifiées comme arguments séparés par des virgules.
En termes d'options de pasta(1), --config-net est donné par défaut, afin de configurer le réseau lorsque le conteneur démarre, et --no-map-gw est également supposé par défaut, pour éviter l'accès direct du conteneur à l'hôte en utilisant l'adresse de la passerelle. Ce dernier peut être remplacé en passant --map-gw dans les options spécifiques à pasta (bien que ce ne soit pas une option réelle de pasta(1)).
Pour une meilleure intégration avec la gestion du DNS, --dns-forward 169.254.1.1 est passé, et cette adresse est ajoutée à resolv.conf(5) en tant que premier résolveur. Il est possible de passer --dns-forward explicitement dans le cas où une adresse IP différente devrait être utilisée. Pour que l'entrée host.containers.internal dans /etc/hosts fonctionne et permette les connexions à l'hôte, --map-guest-addr 169.254.1.2 est passé. Encore une fois, cela peut être défini explicitement pour choisir une adresse IP différente.
De plus, -t none et -u none sont passés si, respectivement, aucun transfert de port TCP ou UDP de l'hôte vers le conteneur n'est configuré (via --publish de Podman ou en passant directement les options pasta -t/-u), afin de désactiver le transfert de ports automatique basé sur les ports liés. De même, -T none et -U none sont donnés pour désactiver la même fonctionnalité du conteneur vers l'hôte.
Toutes les options peuvent également être définies dans containers.conf(5) ; voir la clé pasta_options dans la section network de ce fichier.
Quelques exemples :
  • pasta:--map-gw : Autorise le conteneur à atteindre directement l'hôte en utilisant l'adresse de la passerelle.
  • pasta:--mtu,1500 : Spécifie une MTU de 1500 octets pour l'interface tap dans le conteneur.
  • pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp, équivalent aux options par défaut de slirp4netns(1) : désactive l'IPv6, attribue 10.0.2.0/24 à l'interface tap0 dans le conteneur, avec une passerelle 10.0.2.3, active le relais DNS joignable à 10.0.2.3, définit l'MTU à 1500 octets, désactive NDP, DHCPv6 et DHCP.

Par exemple, si l'on souhaite monter en liaison le répertoire source /foo, on peut faire mount --bind /foo /foo et mount --make-private --make-shared /foo. Cela convertit /foo en un point de montage partagé. Alternativement, on peut changer directement les propriétés de propagation du montage source. Disons que / est le montage source pour /foo, alors utilisez mount --make-shared / pour convertir / en un montage partagé.

Remarque : si l'utilisateur n'a des droits d'accès que via un groupe, l'accès au volume depuis l'intérieur d'un pod sans racine échoue.

Montage avec mappage d'identifiants

Si idmap est spécifié, crée un montage avec mappage d'identifiants vers l'espace de noms d'utilisateur cible dans le conteneur. L'option idmap prend en charge un mappage personnalisé qui peut différer de l'espace de noms d'utilisateur utilisé par le conteneur. Le mappage peut être spécifié après l'option idmap comme suit : idmap=uids=0-1-10#10-11-10;gids=0-100-10. Pour chaque triplet, la première valeur est le début des identifiants du système de fichiers sous-jacents qui sont mappés vers la deuxième valeur sur l'hôte. La longueur de ce mappage est donnée dans la troisième valeur. Plusieurs plages sont séparées par #.

--volumes-from=CONTAINER[:OPTIONS]

Monte les volumes du/des conteneur(s) spécifié(s). Utilisé pour partager des volumes entre des conteneurs et des pods. Les options sont une liste séparée par des virgules avec les éléments disponibles suivants :

  • rw|ro
  • z

Monte les volumes déjà montés d'un conteneur source sur un autre pod. CONTAINER peut être un nom ou un ID. Pour partager un volume, utilisez l'option --volumes-from lors de l'exécution du conteneur cible. Les volumes peuvent être partagés même si le conteneur source n'est pas en cours d'exécution.

Par défaut, Podman monte les volumes dans le même mode (lecture-écriture ou lecture-seule) que celui dans lequel ils sont montés dans le conteneur source. Cela peut être modifié en ajoutant une ro ou rw option.

Les systèmes d'étiquetage comme SELinux exigent que des étiquettes appropriées soient placées sur le contenu des volumes montés dans un pod. Sans étiquette, le système de sécurité peut empêcher les processus s'exécutant à l'intérieur du conteneur d'utiliser le contenu. Par défaut, Podman ne modifie pas les étiquettes définies par le système d'exploitation.

Pour changer une étiquette dans le contexte du pod, ajoutez z au montage du volume. Ce suffixe indique à Podman de réétiqueter les objets de fichiers sur les volumes partagés. L'option z indique à Podman que deux entités partagent le contenu du volume. En conséquence, Podman étiquette le contenu avec une étiquette de contenu partagé. Les étiquettes de volume partagées permettent à tous les conteneurs de lire/écrire le contenu.

Si l'emplacement du volume du conteneur source chevauche des données résidant sur un pod cible, alors le volume masque ces données sur la cible.

EXEMPLES

Crée un pod nommé.

$ podman pod create --name test

Crée un pod nommé.

$ podman pod create mypod

Crée un pod sans conteneur d'infrastructure.

$ podman pod create --infra=false

Crée un pod nommé avec une commande de conteneur d'infrastructure à exécuter.

$ podman pod create --infra-command /top toppod

Crée un pod avec des ports publiés sur l'hôte.

$ podman pod create --publish 8443:443

Crée un pod avec la configuration réseau spécifiée.

$ podman pod create --network slirp4netns:outbound_addr=127.0.0.1,allow_host_loopback=true

Crée un pod avec le réseau spécifié.

$ podman pod create --network pasta

Crée un pod sur deux réseaux.

$ podman pod create --network net1:ip=10.89.1.5 --network net2:ip=10.89.10.10

Crée un pod avec des limites de CPU et de mémoire partagées pour tous les conteneurs.

$ podman pod create --cpus=2 --memory=512m mypod

Crée un pod avec des montages de volumes partagés accessibles à tous les conteneurs.

$ podman pod create --volume /host/path:/container/path:Z mypod

Crée un pod avec des limites de ressources et des montages de volumes partagés pour tous les conteneurs.

$ podman pod create --volume /data:/data:Z --volume /config:/etc/config:ro --cpus=1.5 --memory=1g --cpu-shares=512 mypod

Crée un pod avec un accès partagé aux périphériques et des limites de ressources.

$ podman pod create --device /dev/sda:/dev/sda:rw --cpus=4 --memory=2g --blkio-weight=500 mypod

Crée un pod avec des limites d'ensemble de CPU partagées et des volumes provenant d'un autre conteneur qui seront partagés avec tous les conteneurs du pod.

$ podman pod create --cpuset-cpus=0,2 --volumes-from=source-container --memory=1g mypod

Crée un pod avec des ressources partagées et y ajoute des conteneurs.

$ podman pod create --cpus=2 --memory=1g --volume /data:/data:Z mypod
$ podman create --pod mypod nginx
$ podman create --pod mypod redis
