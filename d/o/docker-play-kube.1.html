DESCRIPTIO

N

podman kube play lit un fichier structuré de YAML Kubernetes. Il recrée les conteneurs, les pods ou les volumes décrits dans le YAML. Les conteneurs au sein d'un pod sont ensuite démarrés, et l'ID du nouveau Pod ou le nom du nouveau Volume est affiché. Si le fichier YAML est spécifié comme "-", alors podman kube play lit le fichier YAML depuis stdin. L'entrée peut également être une URL pointant vers un fichier YAML tel que https://podman.io/demo.yml. podman kube play lit le YAML depuis l'URL et crée des pods et des conteneurs à partir de

celui-ci.

En utilisant l'option de ligne de commande --down, il est également capable de détruire les pods créés lors d'une exécution précédente de podman kube

play.

En utilisant l'option de ligne de commande --replace, il détruit les pods (le cas échéant) créés lors d'une exécution précédente de podman kube play et recrée les pods avec le fichier YAML

Kubernetes.

Idéalement, le fichier d'entrée est créé par la commande Podman (voir podman-kube-generate(1)). Cela garantit une importation fluide et des résultats

attendus.

Pods ou Deployments

Kubernetes

Seuls cinq types de volumes sont pris en charge par kube play : les types de volumes hostPath, emptyDir, configMap, persistentVolumeClaim, et image

.
  • Lors de l'utilisation du type de volume hostPath, seuls les sous-types par défaut (vide), DirectoryOrCreate, Directory, FileOrCreate, File, Socket, CharDevice et BlockDevice sont pris en charge. Podman interprète la valeur de hostPath path comme un chemin de fichier lorsqu'elle contient au moins une barre oblique, sinon Podman traite la valeur comme le nom d'un volume
    • nommé.
  • Lors de l'utilisation d'un persistentVolumeClaim, la valeur de claimName est le nom du volume nommé
    • Podman.
  • Lors de l'utilisation d'un volume emptyDir, Podman crée un volume anonyme qui est attaché aux conteneurs s'exécutant à l'intérieur du pod et qui est supprimé une fois le pod
    • retiré.
  • Lors de l'utilisation d'un volume configMap, Podman crée un volume anonyme qui est attaché aux conteneurs s'exécutant à l'intérieur du pod et qui est supprimé une fois le pod
    • retiré.
  • Lors de l'utilisation d'un volume image, Podman crée un volume d'image en lecture seule avec un sous-chemin vide (l'image entièr
    • e est montée). L'image doit déjà exister localeme
nt. Elle n'est prise en charge qu'en mode rootful.

Remarque : La politique de redémarrage par défaut des conteneurs est always. Vous pouvez changer la valeur par défaut en définissant le champ restartPolicy dans le

spec.

Remarque : Lors de la lecture d'un YAML kube avec des conteneurs d'initialisation, le conteneur d'initialisation est créé avec la valeur de type d'initialisation once. Pour changer le type par défaut, utilisez l'annotation io.podman.annotations.init.container.type pour définir le type sur always

.

Remarque : Les types de volumes hostPath créés par kube play se voient attribuer un label SELinux partagé (z), les montages de liens ne sont pas relabellisés (utilisez chcon -t container_file_t -R <répertoire>)

.

Remarque : Pour définir le userns d'un pod, utilisez l'annotation io.podman.annotations.userns dans la définition du pod/deployment. Par exemple, l'annotation io.podman.annotations.userns=keep-id indique à Podman de créer un espace de noms d'utilisateur où le UID:GID de l'utilisateur rootless actuel est mappé vers les mêmes valeurs dans le conteneur. Cela peut être remplacé par l'indicateur --userns

.

Remarque : Utilisez l'annotation io.podman.annotations.volumes-from pour monter en liaison les volumes d'un conteneur vers un autre. Vous pouvez monter les volumes de plusieurs conteneurs sources vers un conteneur cible. Les conteneurs sources appartenant au même pod doivent être définis avant le conteneur source dans le YAML kube. Le format de l'annotation est io.podman.annotations.volumes-from/targetContainer: "sourceContainer1:mo

untOpts1;sourceContainer2:mountOpts2".

Remarque : Si le tag :latest est utilisé, Podman tente de tirer l'image depuis un registre. Si l'image a été construite localement avec Podman ou Buildah, elle a localhost comme domaine, dans ce cas, Podman utilise l'image du stockage local même si elle a le tag :late

st.

Remarque : La commande podman play kube est un alias de podman kube play, et effectue la même

fonction.

Remarque : La commande podman kube down peut être utilisée pour arrêter et supprimer des pods ou des conteneurs basés sur le même fichier YAML Kubernetes utilisé par podman kube play pour les

créer.

Remarque : Pour personnaliser le nom du conteneur d'infrastructure créé lors de podman kube play, utilisez l'annotation io.podman.annotations.infra.name dans la définition du pod. Cette annotation est automatiquement définie lors de la génération d'un kube yaml à partir d'un pod qui a été créé avec l'indicateur --infra-name

défini.

Remarque : Utilisez l'annotation io.podman.annotations.pids-limit/$ctrname pour configurer la limite de pids du

pod.

Remarque : Utilisez l'annotation io.podman.annotations.cpuset/$ctrname pour restreindre l'exécution d'un conteneur à un ensemble spécifique de cœurs de CPU. Cela équivaut à l'option --cpuset-cpus=nombre dans podman-run(1)

Remarque : Utilisez l'annotation io.podman.annotations.memory-nodes/$ctrname pour restreindre les allocations mémoire d'un conteneur à un ensemble spécifique de nœuds mémoire sur les systèmes NUMA. Cela équivaut à l'option --cpuset-mems=nœuds dans podman-run(1)

ConfigMap

Kubernetes

Un ConfigMap Kubernetes peut être référencé comme source de variables d'environnement ou de volumes dans les Pods ou Deployments. Les ConfigMaps ne sont pas un objet autonome dans Podman ; à la place, lorsqu'un conteneur utilise un ConfigMap, Podman crée des variables d'environnement ou des volumes selon les

besoins.

Par exemple, le document YAML suivant définit un ConfigMap et l'utilise ensuite dans un Pod

: 
apiVersion: v1
kind: ConfigMap
metadata:
  name: foo
data:
    FOO: bar
---
apiVersion: v1
kind: Pod
metadata:
  name: foobar
spec:
  containers:
  - name: container-1
    image: foobar
    envFrom:
    - configMapRef:
        name: foo
        optional: false

et en conséquence la variable d'environnement FOO est définie à bar pour le conteneur container-1.

Secret Kubernetes

Un secret Kubernetes représente un secret nommé Podman. Le secret Kubernetes est sauvegardé dans son intégralité et peut être référencé comme source de variables d'environnement ou de volumes dans les Pods ou les Déploiements.

Par exemple, le document YAML suivant définit un Secret puis l'utilise dans un Pod :

kind: Secret
apiVersion: v1
metadata:
  name: foo
data:
  foo: YmFy # base64 pour bar
---
apiVersion: v1
kind: Pod
metadata:
  name: foobar
spec:
  containers:
  - name: container-1
    image: foobar
    env:
    - name: FOO
      valueFrom:
        secretKeyRef:
          name: foo
          key: foo

et en conséquence la variable d'environnement FOO est définie à bar pour le conteneur container-1.

Montage automatique de volumes (obsolète)

Note : L'annotation de montage automatique est obsolète. Kubernetes prend en charge nativement les volumes d'image et cela devrait être utilisé plutôt que cette annotation spécifique à Podman.

Une image peut être montée automatiquement dans un conteneur si l'annotation io.podman.annotations.kube.image.automount/$ctrname est fournie. Les règles suivantes s'appliquent :

  • L'image doit déjà exister localement.
  • L'image doit avoir au moins 1 directive de volume.
  • Le chemin indiqué par la directive de volume sera monté depuis l'image dans le conteneur. Par exemple, une image avec un volume dans /test/test_dir aura /test/test_dir dans l'image monté sur /test/test_dir dans le conteneur.
  • Plusieurs images peuvent être spécifiées. Si plusieurs images ont un volume à un chemin spécifique, la dernière image spécifiée prévaut.
  • Les images sont toujours montées en lecture seule.
  • Les images à monter sont définies dans l'annotation "io.podman.annotations.kube.image.automount/$ctrname" sous forme de liste séparée par des points-virgules. Elles sont montées dans un seul conteneur du pod, pas dans tout le pod. L'annotation peut être spécifiée pour des conteneurs supplémentaires si des montages supplémentaires sont requis.

OPTIONS

--annotation=clé=valeur

Ajoute une annotation au conteneur ou au pod. Cette option peut être définie plusieurs fois.

Note : Pour podman kube play, le drapeau --annotation ajoute des annotations spécifiques à Podman aux conteneurs et aux pods créés par Podman, et non au fichier YAML Kubernetes lui-même. Ces annotations peuvent être utilisées pour configurer des fonctionnalités spécifiques à Podman telles que les espaces de noms utilisateur (io.podman.annotations.userns), volumes-from (io.podman.annotations.volumes-from), et d'autres comportements de conteneur.

--authfile=chemin

Chemin du fichier d'authentification. Par défaut, il s'agit de ${XDG_RUNTIME_DIR}/containers/auth.json sous Linux, et de $HOME/.config/containers/auth.json sous Windows/macOS. Le fichier est créé par podman login. Si l'état d'autorisation n'y est pas trouvé, $HOME/.docker/config.json est vérifié, ce qui est défini à l'aide de docker login.

Note : Il existe également une option pour remplacer le chemin par défaut du fichier d'authentification en définissant la variable d'environnement REGISTRY_AUTH_FILE. Cela peut être fait avec export REGISTRY_AUTH_FILE=chemin.

--build

Construit les images même si elles sont trouvées dans le stockage local. Utilisez --build=false pour désactiver complètement les constructions. (Cette option n'est pas disponible avec le client Podman distant)

Note : Vous pouvez également remplacer le type d'isolation par défaut en définissant la variable d'environnement BUILDAH_ISOLATION. export BUILDAH_ISOLATION=oci. Voir podman-build.1.md pour plus d'informations.

--cert-dir=chemin

Utilise les certificats dans chemin (*.crt, *.cert, *.key) pour se connecter au registre. (Par défaut : /etc/containers/certs.d) Pour plus de détails, voir containers-certs.d(5). (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (à l'exception de WSL2))

--configmap=chemin

Utilise le fichier YAML de configuration Kubernetes à l'emplacement spécifié pour fournir une source pour les valeurs des variables d'environnement dans les conteneurs du pod. (Cette option n'est pas disponible avec le client Podman distant)

Note : L'option --configmap peut être utilisée plusieurs fois ou une liste de chemins séparés par des virgules peut être utilisée pour passer plusieurs fichiers YAML de configuration Kubernetes. Le fichier YAML peut être au format YAML multi-documents. Mais il ne doit contenir que des configmaps.

--context-dir=chemin

Utilise chemin comme répertoire de contexte de construction pour chaque image. Nécessite que l'option --build soit vraie. (Cette option n'est pas disponible avec le client Podman distant)

--creds=[nom d'utilisateur[:mot de passe]]

Le [nom d'utilisateur[:mot de passe]] à utiliser pour s'authentifier auprès du registre, si nécessaire. Si une ou deux valeurs ne sont pas fournies, une invite apparaît et la valeur peut être entrée. Le mot de passe est entré sans écho.

Notez que les identifiants spécifiés sont uniquement utilisés pour s'authentifier auprès des registres cibles. Ils ne sont pas utilisés pour les miroirs ou lorsque le registre est réécrit (voir containers-registries.conf(5)) ; pour s'authentifier auprès de ceux-ci, envisagez d'utiliser un fichier containers-auth.json(5).

--network=mode, --net

Définit le mode réseau pour le pod.

Les valeurs valides pour mode sont :

•
bridge[:OPTIONS,...] : Crée une pile réseau sur le pont par défaut. C'est le comportement par défaut pour les conteneurs rootful. Il est possible de spécifier les options supplémentaires suivantes :
  • alias=nom : Ajoute un alias à portée réseau pour le conteneur.
  • ip=IPv4 : Spécifie une adresse IPv4 statique pour ce conteneur.
  • ip6=IPv6 : Spécifie une adresse IPv6 statique pour ce conteneur.
  • mac=MAC : Spécifie une adresse MAC statique pour ce conteneur.
  • interface_name=nom : Spécifie un nom pour l'interface réseau créée à l'intérieur du conteneur.
  • host_interface_name=nom : Spécifie un nom pour l'interface réseau créée à l'extérieur du conteneur.
Toutes les autres options seront transmises à netavark sans validation. Cela peut être utile pour passer des arguments aux plugins netavark.

Par exemple, pour définir une adresse ipv4 statique et une adresse mac statique, utilisez --network bridge:ip=10.88.0.10,mac=44:33:22:11:00:99.

  • <nom ou ID de réseau>[:OPTIONS,...] : Se connecte à un réseau défini par l'utilisateur ; il s'agit du nom ou de l'ID du réseau créé par podman network create.     Podman alloue des plages uniques d'UID et de GID à partir des identifiants d'utilisateurs subordonnés de containers. La taille des plages est basée sur le nombre d'UID requis dans l'image. Le nombre d'UID et de GID peut être remplacé avec l'option size

    L'option --userns=keep-id utilise tous les subuids et subgids de l'utilisateur. L'option --userns=nomap utilise tous les subuids et subgids de l'utilisateur sauf son propre identifiant. L'utilisation de --userns=auto lors du démarrage de nouveaux conteneurs ne fonctionne pas tant que des conteneurs existent qui ont été démarrés avec --userns=nomap ou --userns=keep-id sans limiter la taille de l'espace de noms

    utilisateur.

    Les valeurs autotions:

    • gidmapping=CONTAINER_GID:HOST_GID:TAILLE : pour forcer un mappage GID à être présent dans l'espace de noms utilisateur.
    • size=TAILLE : pour spécifier une taille explicite pour l'espace de noms utilisateur automatique. Par exemple, --userns=auto:size=8192. Si size n'est pas spécifié, auto estime une taille pour l'espace de noms utilisateur.
    • uidmapping=CONTAINER_UID:HOST_UID:TAILLE : pour forcer un mappage UID à être présent dans l'espace de noms utilisateur.

    L'UID et le GID de l'hôte dans gidmapping et uidmapping peuvent éventuellement être précédés du symbole @. Dans ce cas, podman recherchera l'ID intermédiaire correspondant à l'ID de l'hôte et mappera l'ID intermédiaire trouvé à l'ID du conteneur. Pour plus de détails, voir --uidmap.

    container:id : rejoint l'espace de noms utilisateur du conteneur spécifié.

    host ou "" (chaîne vide) : s'exécute dans l'espace de noms utilisateur de l'appelant. Les processus s'exécutant dans le conteneur ont les mêmes privilèges sur l'hôte que tout autre processus lancé par l'utilisateur appelant.

    keep-id : crée un espace de noms utilisateur où les UID :GID de l'utilisateur actuel sont mappés aux mêmes valeurs dans le conteneur. Pour les conteneurs créés par root, le mappage actuel est créé dans un nouvel espace de noms utilisateur.

    De plus, le processus d'initialisation à l'intérieur du conteneur s'exécutera sous l'UID de l'utilisateur actuel. Ce comportement remplace l'instruction USER de l'image, sauf si vous définissez explicitement --user.

    Options keep-id valides :

    • uid=UID : remplace l'UID à l'intérieur du conteneur qui est utilisé pour mapper l'utilisateur actuel.
    • gid=GID : remplace le GID à l'intérieur du conteneur qui est utilisé pour mapper l'utilisateur actuel.
    • size=TAILLE : remplace la taille de l'espace de noms utilisateur configuré. Il est utile de ne pas saturer tous les IDs disponibles. Non pris en charge lors de l'exécution en tant que root.

    nomap : crée un espace de noms utilisateur où les UID :GID de l'utilisateur rootless actuel ne sont pas mappés dans le conteneur. Cette option n'est pas autorisée pour les conteneurs créés par l'utilisateur root.

    ns:namespace : exécute le pod dans l'espace de noms utilisateur existant donné.

    --wait, -w

    Exécute les pods et les conteneurs au premier plan. La valeur par défaut est false.

    À tout moment, vous pouvez exécuter podman pod ps dans un autre terminal pour afficher la liste des pods et conteneurs en cours d'exécution.

    Lorsqu'il est attaché en mode tty, vous pouvez tuer les pods et les conteneurs en appuyant sur Ctrl-C ou en recevant tout autre signal d'interruption.

    Tous les pods, conteneurs et volumes créés avec podman kube play sont supprimés à la sortie.
