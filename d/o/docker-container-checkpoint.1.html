NOM

podman-container-checkpoint - Mettre en checkpoint un ou plusieurs conteneurs en cours d'exécution

SYNOPSIS

podman container checkpoint [options] conteneur [conteneur ...]

DESCRIPTION

podman container checkpoint met en checkpoint tous les processus dans un ou plusieurs conteneurs. Un conteneur peut être restauré à partir d'un checkpoint avec podman-container-restore. Les identifiants de conteneur ou les noms sont utilisés en entrée.

IMPORTANT : Si le conteneur utilise systemd comme point d'entrée , la mise en checkpoint du conteneur pourrait ne pas être possible.

OPTIONS

--all, -a

Mettre en checkpoint tous les conteneurs en cours d'exécution. conteneurs.
La valeur par défaut est false.
IMPORTANT : Cette OPTION n'a pas besoin d'un nom ou d'un identifiant de conteneur comme argument d'entrée.

--compress, -c=zstd | none | gzip

Spécifier l'algorithme de compression utilisé pour l'archive de checkpoint créée avec l' OPTION --export, -e . Les algorithmes possibles sont zstd, none et gzip.
Une raison possible d'utiliser none est de permettre une création plus rapide des archives de checkpoint. Ne pas compresser l'archive de checkpoint peut entraîner une création plus rapide de l'archive de checkpoint.
La valeur par défaut est zstd.

--create-image=image

Créer une image de checkpoint à partir d'un conteneur en cours d'exécution. Il s'agit d'une image OCI standard créée dans le magasin d'images local. Elle se compose d'une seule couche qui contient tous les fichiers de checkpoint. Le contenu de cette couche d'image est dans le même format qu'un checkpoint créé avec --export. Une image de checkpoint peut être poussée vers un registre de conteneurs standard et tirée sur un autre système pour permettre la migration de conteneurs. De plus, l'image peut être exportée avec podman image save et inspectée avec podman inspect. L'inspection d'une image de checkpoint affiche des informations supplémentaires, stockées sous forme d'annotations, sur l'environnement hôte utilisé pour effectuer le checkpoint :

  • io.podman.annotations.checkpoint.name: Nom lisible par l'humain du conteneur d'origine.
  • io.podman.annotations.checkpoint.rawImageName: Nom non traité de l'image utilisée pour créer le conteneur d'origine (tel que spécifié par l'utilisateur).
  • io.podman.annotations.checkpoint.rootfsImageID: Identifiant de l'image utilisée pour créer le conteneur d'origine.
  • io.podman.annotations.checkpoint.rootfsImageName: Nom de l'image utilisée pour créer le conteneur d'origine.
  • io.podman.annotations.checkpoint.podman.version: Version de Podman utilisée pour créer le checkpoint.
  • io.podman.annotations.checkpoint.criu.version: Version de CRIU utilisée pour créer le checkpoint.
  • io.podman.annotations.checkpoint.runtime.name: Environnement d'exécution de conteneur (par ex. runc, crun) utilisé pour créer le checkpoint.
  • io.podman.annotations.checkpoint.runtime.version: Version de l'environnement d'exécution de conteneur utilisé pour créer le checkpoint.
  • io.podman.annotations.checkpoint.conmon.version: Version de conmon utilisée avec le conteneur d'origine.
  • io.podman.annotations.checkpoint.host.arch: Architecture CPU de l'hôte sur lequel le checkpoint a été créé.
  • io.podman.annotations.checkpoint.host.kernel: Version du noyau Linux de l'hôte où le checkpoint a été créé.
  • io.podman.annotations.checkpoint.cgroups.version: Version de cgroup utilisée par l'hôte où le checkpoint a été créé.
  • io.podman.annotations.checkpoint.distribution.version: Version de la distribution de l'hôte sur laquelle le checkpoint a été créé.
  • io.podman.annotations.checkpoint.distribution.name: Nom de la distribution de l'hôte sur laquelle le checkpoint a été créé.

--export, -e=archive

Exporter le checkpoint vers une archive. Le type d'archive est spécifié avec --compress. Le checkpoint exporté peut être utilisé pour importer le conteneur sur un autre système, permettant ainsi la migration à chaud des conteneurs. Cette archive de checkpoint inclut également toutes les modifications du système de fichiers racine du conteneur , si cela n'est pas explicitement désactivé avec --ignore-rootfs.

--file-locks

Mettre en checkpoint un conteneur avec des verrous de fichiers. Si une application s'exécutant dans le conteneur utilise des verrous de fichiers, cette OPTION est requise lors de la mise en checkpoint et de la restauration. Sinon, la mise en checkpoint de conteneurs avec des verrous de fichiers échouera. Si des verrous de fichiers ne sont pas utilisés, cette option est ignorée.
La valeur par défaut est false.

--ignore-rootfs

Si un checkpoint est exporté vers une archive, il est possible, à l'aide de --ignore-rootfs , de désactiver explicitement l'inclusion des modifications du système de fichiers racine dans le fichier d'archive de checkpoint.
La valeur par défaut est false.
IMPORTANT : Cette OPTION ne fonctionne qu'en combinaison avec --export, -e.

--ignore-volumes

Cette OPTION doit être utilisée en combinaison avec l' OPTION --export, -e . Lorsque cette OPTION est spécifiée, le contenu des volumes associés au conteneur n'est pas inclus dans l'archive de checkpoint.
La valeur par défaut est false.

--keep, -k

Conserver tous les fichiers de log et de statistiques temporaires créés par CRIU lors de la mise en checkpoint. Ces fichiers ne sont pas supprimés si la mise en checkpoint échoue, pour un débogage ultérieur. Si la mise en checkpoint réussit, ces fichiers ne sont théoriquement pas nécessaires, mais si ces fichiers sont nécessaires, Podman peut les conserver pour une analyse ultérieure.
La valeur par défaut est false.

--latest, -l

Au lieu de fournir l' identifiant de conteneur ou le nom, utiliser le dernier conteneurcréé. La valeur par défaut est false. IMPORTANT : Cette OPTION n'est pas disponible avec le client Podman distant, y compris sur les machines Mac et Windows (à l'exclusion de WSL2). Cette OPTION n'a pas besoin d'un nom ou d'un identifiant de conteneur comme argument d'entrée.

--leave-running, -R

Laisser le conteneur en cours d'exécution après la mise en checkpoint au lieu de l'arrêter.
La valeur par défaut est false.

--pre-checkpoint, -P

Ne faire un dump que des informations mémoire du conteneur , en laissant le conteneur en cours d'exécution. Les opérations ultérieures remplacent les dumps précédents.
La valeur par défaut est false.

La fonctionnalité qui consiste à ne mettre en checkpoint que la mémoire du conteneur et, lors d'un second checkpoint, à n'écrire que les pages mémoire modifiées depuis le premier checkpoint repose sur le bit soft-dirty du noyau Linux, qui n'est pas disponible sur tous les systèmes car il dépend de l'architecture du système et de la configuration du noyau Linux. Podman vérifie si le système actuel prend en charge cette fonctionnalité et renvoie une erreur si le système actuel ne la prend pas en charge.

--print-stats

Afficher des statistiques sur la mise en checkpoint du/des conteneur(s). La sortie est rendue sous forme de tableau JSON et contient des informations sur le temps nécessaire aux différentes opérations de checkpoint. Beaucoup des statistiques de checkpoint sont créées par CRIU et simplement transmises à Podman. Les informations suivantes sont fournies dans le tableau JSON :

  • podman_checkpoint_duration: Temps total (en microsecondes) nécessaire pour créer tous les checkpoints.
  • runtime_checkpoint_duration: Temps (en microsecondes) que l'environnement d'exécution du conteneur a mis pour créer le checkpoint.
  • freezing_time: Temps (en microsecondes) que CRIU a mis pour mettre en pause (geler) tous les processus dans le conteneur (mesuré par CRIU).
  • frozen_time: Temps (en microsecondes) pendant lequel tous les processus dans le conteneur ont été mis en pause (mesuré par CRIU).
  • memdump_time: Temps (en microsecondes) nécessaire pour extraire toutes les pages mémoire requises de tous les processus du conteneur (mesuré par CRIU).
  • memwrite_time: Temps (en microsecondes) nécessaire pour écrire toutes les pages mémoire requises dans les fichiers d'image de checkpoint correspondants (mesuré par CRIU).
  • pages_scanned: Nombre de pages mémoire scannées pour déterminer si elles doivent être mises en checkpoint (mesuré par CRIU).
  • pages_written: Nombre de pages mémoire effectivement écridix fois la taille des fichiers d'image de point de contrôle (mesurée par CRIU).

La valeur par défaut est false.

--tcp-established

Crée un point de contrôle d'un conteneur avec des connexions TCP établies. Si l'image du point de contrôle contient des connexions TCP établies, cette OPTION est requise lors de la restauration. Par défaut, les conteneurs avec des connexions TCP établies ne sont pas inclus dans le point de contrôle.
La valeur par défaut est false.

--with-previous

Récupère le conteneur avec les fichiers d'image criu précédents lors du pre-dump. Cela ne fonctionne qu'avec runc 1.0-rc3 ou supérieur.
La valeur par défaut est false.
IMPORTANT : Cette OPTION n'est pas disponible avec --pre-checkpoint.

Cette option nécessite que l'option --pre-checkpoint ait été utilisée auparavant sur le même conteneur. Sans un pré-point de contrôle existant, cette option échoue.

Voir également --pre-checkpoint pour des informations supplémentaires sur la disponibilité de --pre-checkpoint sur différents systèmes.

EXEMPLES

Crée un point de contrôle pour le conteneur « mywebserver ».

# podman container checkpoint mywebserver

Crée une image de point de contrôle pour le conteneur « mywebserver ».

# podman container checkpoint --create-image mywebserver-checkpoint-1 mywebserver

Dump les informations mémoire du dernier conteneur dans une archive.

# podman container checkpoint -P -e pre-checkpoint.tar.zst -l

Conserve les informations mémoire d'un dump plus ancien et ajoute les informations mémoire du nouveau conteneur.

# podman container checkpoint --with-previous -e checkpoint.tar.zst -l

Dump les informations mémoire du dernier conteneur dans une archive avec la méthode de compression spécifiée.

# podman container checkpoint -l --compress=none --export=dump.tar
# podman container checkpoint -l --compress=gzip --export=dump.tar.gz
