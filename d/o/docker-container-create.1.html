Vous pouvez fournir des options supplémentaires pour chaque montage par liaison après un deux-points supplémentaire. Un suffixe :ro ou :rw monte un volume en mode lecture seule ou lecture-écriture respectivement. Par défaut, les volumes sont montés en mode lecture-écriture. Vous pouvez également spécifier l'exigence de cohérence pour le montage, soit :consistent (par défaut), :cached , ou :delegated . Les options multiples sont séparées par des virgules, par exemple :ro,cached . Les systèmes d'étiquetage comme SELinux exigent que des étiquettes appropriées soient placées sur le contenu du volume monté dans un conteneur. Sans étiquette, le système de sécurité peut empêcher les processus s'exécutant dans le conteneur d'utiliser le contenu. Par défaut, Docker ne modifie pas les étiquettes définies par le système d'exploitation. Pour modifier une étiquette dans le contexte du conteneur, vous pouvez ajouter l'un des deux suffixes :z ou :Z au montage du volume. Ces suffixes indiquent à Docker de réétiqueter les objets de fichiers sur les volumes partagés. L'option z

indique à Docker que deux conteneurs partagent le contenu du volume. En conséquence, Docker étiquette le contenu avec une étiquette de contenu partagé. Les étiquettes de volume partagées permettent à tous les conteneurs de lire/écrire le contenu. L'option Z indique à Docker d'étiqueter le contenu avec une étiquette privée non partagée. Seul le conteneur actuel peut utiliser un volume privé. Par défaut, les volumes montés par liaison sont privés . Cela signifie que les montages effectués dans le conteneur ne seront pas visibles sur l'hôte et vice versa. On peut changer ce comportement en spécifiant une propriété de propagation du montage du volume. En rendant un volume partagé , les montages effectués sous ce volume dans le conteneur seront visibles sur l'hôte et vice versa. En rendant un volume esclave , on ne permet qu'une propagation de montage unidirectionnelle, c'est-à-dire que les montages effectués sur l'hôte sous ce volume seront visibles dans le conteneur mais pas l'inverse. Pour contrôler la propriété de propagation du montage d'un volume, on peut utiliser le drapeau de propagation :[r]shared , :[r]

slave

ou :[r]private . La propriété de propagation ne peut être spécifiée que pour les volumes montés par liaison et non pour les volumes internes ou les volumes nommés. Pour que la propagation de montage fonctionne, le point de montage source (le point de montage où le répertoire source est monté) doit avoir les bonnes propriétés de propagation. Pour les volumes partagés, le point de montage source doit être partagé. Et pour les volumes esclaves, le montage source doit être soit partagé soit esclave. Utilisez df <chemin-répertoire-source

>

pour déterminer le montage source, puis utilisez findmnt -o TARGET,PROPAGATION <chemin-répertoire-source> pour déterminer les propriétés de propagation du montage source. Si l'utilitaire
findmnt n'est pas disponible, on peut examiner l'entrée de montage du point de montage source dans /proc/self/mountinfo . Examinez les champs optionnels et voyez si des propriétés de propagation sont spécifiées. shared:X signifie que le montage est partagé , master:X signifie que le montage est esclave et s'il n'y a rien, cela signifie que le montage

est privé

. Pour changer les propriétés de propagation d'un point de montage, utilisez la commande

mount

. Par exemple, si l'on souhaite monter par liaison le répertoire source /foo , on peut faire mount --bind /foo /foo et mount --make-private --make-shared /foo . Cela convertira /foo en un point de montage partagé . Alternativement, on peut modifier directement les propriétés de propagation du montage source. Disons que /

est le montage source pour /foo , utilisez alors mount --make-shared

/

pour convertir / en un montage partagé . Remarqu

e

: Lors de l'utilisation de systemd pour gérer le démarrage et l'arrêt du démon Docker, dans le fichier d'unité systemd, il existe une option pour contrôler la propagation du montage pour le démon Docker lui-même, appelée MountFlags . La valeur de ce paramètre peut empêcher Docker de voir les changements de propagation de montage effectués sur le point de montage. Par exemple, si cette valeur est slave , vous risquez de ne pas pouvoir utiliser la propagation shared ou rshared sur un volume. Pour désactiver la copie automatique des données du chemin du conteneur vers le volume, utilisez le drapeau nocopy . Le drapeau nocopy peut être défini sur les volumes nommés, et ne s'applique pas aux montages par liaison. EXEMPLE

### Spécifier la technologie d'isolation pour le conteneur (--isolation)
Cette option est utile dans les situations où vous exécutez des conteneurs Docker sur
Windows. L'option `--isolation=<valeur>` définit la technologie d'isolation
d'un conteneur. Sur Linux, la seule valeur prise en charge est l'option `default` qui utilise
les espaces de noms Linux. Sur Microsoft Windows, vous pouvez spécifier ces valeurs :
* `default` : Utiliser la valeur spécifiée par l'option `--exec-opt` du démon Docker. Si le `daemon` ne spécifie pas de technologie d'isolation, Microsoft Windows utilise `process` comme valeur par défaut.
* `process` : Isolation par espace de noms uniquement.
* `hyperv` : Isolation basée sur la partition de l'hyperviseur Hyper-V.
### Gestion des périphériques créés dynamiquement (--device-cgroup-rule)
Les périphériques disponibles pour un conteneur sont assignés au moment de sa création. Les périphériques assignés seront ajoutés au fichier cgroup.allow et créés dans le conteneur une fois qu'il est exécuté. Cela pose un problème lorsqu'un nouveau périphérique doit être ajouté à un conteneur en cours d'exécution.
L'une des solutions consiste à ajouter une règle plus permissive à un conteneur
lui permettant d'accéder à une gamme plus large de périphériques. Par exemple, en supposant
que notre conteneur ait besoin d'accéder à un périphérique de caractère avec le majeur `42`
et n'importe quel numéro mineur (ajouté au fur et à mesure que de nouveaux périphériques apparaissent), la
régler suivante serait ajoutée :
```console
$ docker create --device-cgroup-rule='c 42:* rmw' --name my-container my-image

Ensuite, un utilisateur pourrait demander à udev d'exécuter un script qui exécuterait docker exec my-container mknod newDevX c 42 <mineur> pour créer le périphérique requis lorsqu'il est ajouté.

REMARQUE : les périphériques initialement présents doivent toujours être ajoutés explicitement à la commande create/run

```
