NOM

docker-build - Construit une image à partir d'un Dockerfile

SYNOPIS

docker build [--add-host[=[]]] [--build-arg[=[]]] [--cache-from[=[]]] [-c|--cpu-shares[=0]] [--cgroup-parent[=CGROUP-PARENT]] [--help] [--iidfile[=IIDFILE]] [-f|--file[=CHEMIN/Dockerfile]] [--squash] Expérimental [--force-rm] [--isolation[=default]] [--label[=[]]] [--no-cache] [--pull] [--compress] [-q|--quiet] [--rm[=true]] [-t|--tag[=[]]] [-m|--memory[=MEMORY]] [--memory-swap[=LIMIT]] [--network[="default"]] [--shm-size[=SHM-SIZE]] [--cpu-period[=0]] [--cpu-quota[=0]] [--cpuset-cpus[=CPUSET-CPUS]] [--cpuset-mems[=CPUSET-MEMS]] [--target[=[]]] [--ulimit[=[]]] CHEMIN | URL | -

DESCRIPTION

Ceci lira le Dockerfile depuis le répertoire spécifié par CHEMIN. Il envoie également tous les autres fichiers et répertoires trouvés dans le répertoire courant au démon Docker. Le contenu de ce répertoire sera utilisé par les commandes ADD trouvées dans le Dockerfile.

Attention, cela enverra beaucoup de données au démon Docker en fonction du contenu du répertoire courant. La construction est exécutée par le démon Docker, pas par la CLI, donc tout le contexte doit être transféré au démon. La CLI Docker affiche "Sending build context to Docker daemon" lorsque le contexte est envoyé au démon.

Lorsque l'URL d'une archive tar ou d'un seul Dockerfile est donnée, aucun contexte n'est envoyé du client au démon Docker. Dans ce cas, le Dockerfile à la racine de l'archive et le reste de l'archive seront utilisés comme contexte de construction. Lorsqu'un dépôt Git est défini comme URL, le dépôt est cloné localement puis envoyé comme contexte.

OPTIONS

-f, --file CHEMIN/Dockerfile
Chemin vers le Dockerfile à utiliser. Si le chemin est un chemin relatif et que vous
construisez à partir d'un répertoire local, alors le chemin doit être relatif à ce
répertoire. Si vous construisez à partir d'une URL distante pointant vers une archive
tar ou un dépôt Git, alors le chemin doit être relatif à la racine du contexte distant.
Dans tous les cas, le fichier doit se trouver dans le contexte de construction.
Par défaut, c'est Dockerfile.

--squash true|false
Expérimental uniquement
Une fois l'image construite, écrase les nouvelles couches en une nouvelle image avec
une seule nouvelle couche. L'écrasement ne détruit aucune image existante, mais crée une nouvelle
image avec le contenu des couches écrasées. Cela donne l'impression que toutes les commandes
du Dockerfile ont été créées avec une seule couche. Le cache de construction est préservé
avec cette méthode.

Remarque : l'utilisation de cette option signifie que la nouvelle image ne pourra pas
profiter du partage de couches avec d'autres images et pourrait utiliser considérablement plus
d'espace.

Remarque : l'utilisation de cette option peut entraîner une utilisation significativement plus importante de l'espace due à
le stockage de deux copies de l'image, une pour le cache de construction avec toutes les couches
de cache intactes, et une pour la version écrasée.

--add-host []
Ajouter une cartographie personnalisée hôte-IP (hôte=ip, ou hôte:ip)

Ajoute une ligne à /etc/hosts. Le format est nomhôte=ip, ou nomhôte:ip.
L'option --add-host peut être définie plusieurs fois.

--build-arg variable
Nom et valeur d'un buildarg.

Par exemple, si vous voulez passer une valeur pour http_proxy, utilisez
--build-arg=http_proxy="http://some.proxy.url"

Les utilisateurs passent ces valeurs au moment de la construction. Docker utilise les
buildargs comme contexte d'environnement pour les commandes exécutées via l'instruction RUN du Dockerfile
ou pour l'expansion de variables dans d'autres instructions Dockerfile. Ceci n'est pas destiné
à passer des valeurs secrètes. Lire plus sur l'instruction buildargs ⟨https://docs.docker.com/engine/reference/builder/#arg⟩

--cache-from ""
Définit l'image qui sera utilisée comme source du cache de construction.

--force-rm true|false
Supprime toujours les conteneurs intermédiaires, même après des constructions échouées. Par défaut, c'est false.

--isolation "default"
L'isolation spécifie le type de technologie d'isolation utilisé par les conteneurs.

--label label
Définit des métadonnées pour une image

--no-cache true|false
N'utilise pas le cache lors de la construction de l'image. Par défaut, c'est false.

--iidfile ""
Écrit l'ID de l'image dans le fichier

--help
Affiche le message d'utilisation

--pull true|false
Tente toujours de télécharger une version plus récente de l'image. Par défaut, c'est false.

--compress true|false
Compresse le contexte de construction en utilisant gzip. Par défaut, c'est false.

-q, --quiet true|false
Supprime la sortie de construction et affiche l'ID de l'image en cas de succès. Par défaut, c'est false.

--rm true|false
Supprime les conteneurs intermédiaires après une construction réussie. Par défaut, c'est true.

-t, --tag ""
Noms de dépôts (et éventuellement avec des tags) à appliquer à l'image résultante en
cas de succès. Référez-vous à docker-tag(1) pour plus d'informations
sur les noms de tags valides.

-m, --memory MEMORY
Limite de mémoire

--memory-swap number[S]
Limite combinée mémoire plus swap ; S est un suffixe optionnel qui peut être l'un des
suivants : b (octets), k (kilooctets), m (mégaoctets), ou g (gigaoctets).
Cette option ne peut être utilisée qu'en combinaison avec --memory. L'argument doit toujours être supérieur à celui de --memory. Par défaut, il est le double de la valeur de
--memory. Définir à -1 pour activer le swap illimité.

--network type
Définit le mode réseau pour les instructions RUN pendant la construction. Les valeurs standard prises en charge
sont : none, bridge, host et container:<nom|id>. Toute autre valeur
est considérée comme le nom ou l'ID d'un réseau personnalisé auquel ce conteneur doit se connecter.

Sous Linux, par défaut, c'est bridge.

--shm-size SHM-SIZE
Taille de /dev/shm. Le format est <nombre><unité>. Le nombre doit être supérieur à 0.
L'unité est optionnelle et peut être b (octets), k (kilooctets), m (mégaoctets), ou g (gigaoctets). Si vous omettez l'unité, le système utilise les octets.
Si vous omettez complètement la taille, le système utilise 64m.

-c, --cpu-shares 0
Partages CPU (poids relatif).

Par défaut, tous les conteneurs obtiennent la même proportion de cycles CPU.
Les partages CPU sont un 'poids relatif', par rapport à la valeur par défaut de 1024.
Cette valeur par défaut est définie ici :

   cat /sys/fs/cgroup/cpu/cpu.shares
   1024

Vous pouvez modifier cette proportion en ajustant le poids CPU du conteneur par rapport au poids de tous les autres conteneurs en cours d'exécution.

Pour modifier la proportion par rapport à la valeur par défaut de 1024, utilisez l'option
-c ou --cpu-shares pour définir le poids à 2 ou plus.

  Conteneur   Partage CPU    Option
  {C0}        60% du CPU  --cpu-shares 614 (614 est 60% de 1024)
  {C1}        40% du CPU  --cpu-shares 410 (410 est 40% de 1024)

La proportion n'est appliquée que lorsque des processus intensifs en CPU sont en cours d'exécution.
Lorsque les tâches dans un conteneur sont inactives, les autres conteneurs peuvent utiliser le
temps CPU restant. La quantité réelle de temps CPU utilisée varie en fonction du
nombre de conteneurs en cours d'exécution sur le système.

Par exemple, considérez trois conteneurs, dont l'un a --cpu-shares 1024 et
deux autres ont --cpu-shares 512. Lorsque les processus dans les trois
conteneurs tentent d'utiliser 100

% du CPU, le premier conteneur recevrait
50% du temps CPU total. Si vous ajoutez un quatrième conteneur avec --cpu-shares 1024,
le premier conteneur ne reçoit que 33% du CPU. Les conteneurs restants
reçoivent 16,5%, 16,5% et 33% du

CPU. 
  Conteneur   Part CPU   Drapeau              Temps CPU
  {C0}        100%        --cpu-shares 1024   33%
  {C1}        50%         --cpu-shares 512    16,5%
  {C2}        50%         --cpu-shares 512    16,5%
  {C4}        100%        --cpu-shares 1024
33%

Sur un système multi-cœurs, les parts de temps CPU sont distribuées à travers les
cœurs CPU. Même si un conteneur est limité à moins de 100% du temps CPU, il peut
utiliser 100% de chaque cœur CPU

individuel.

Par exemple, considérez un système avec plus de trois cœurs. Si vous démarrez un
conteneur {C0} avec --cpu-shares 512 exécutant un processus, et un autre conteneur
{C1} avec --cpu-shares 1024 exécutant deux processus, cela peut entraîner la division suivante
des parts de CPU

: 
  PID    conteneur   CPU    Part CPU
  100    {C0}         0      100% de CPU0
  101    {C1}         1      100% de CPU1
  102    {C1}         2      100% de
CPU2

--cpu-period 0
Limite la période CFS (Completely Fair Scheduler) du

CPU.

Limite l'utilisation du CPU du conteneur. Ce drapeau force le noyau à restreindre l'utilisation
du CPU du conteneur à la période que vous

spécifiez.

--cpu-quota 0
Limite le quota CFS (Completely Fair Scheduler) du

CPU.

Par défaut, les conteneurs s'exécutent avec la ressource CPU complète. Ce drapeau force le noyau à restreindre l'utilisation du CPU du conteneur au quota que vous

spécifiez.

--cpuset-cpus CPUSET-CPUS
CPUs sur lesquels autoriser l'exécution (0-3, 0,1)

.

--cpuset-mems CPUSET-MEMS
Nœuds mémoire (MEMs) sur lesquels autoriser l'exécution (0-3, 0,1). Uniquement efficace sur les
systèmes

NUMA.

Par exemple, si vous avez quatre nœuds mémoire sur votre système (0-3), utilisez --cpuset-mems 0,1 pour vous assurer que les processus dans votre conteneur Docker n'utilisent que la mémoire des deux premiers nœuds

mémoire.

--cgroup-parent CGROUP-PARENT
Chemin vers les cgroups sous lesquels le cgroup du conteneur est

créé.

Si le chemin n'est pas absolu, le chemin est considéré comme relatif au chemin cgroups du processus init. Les cgroups sont créés s'ils n'existent pas

déjà.

--target ""
Définit le nom de l'étape de build

cible.

--ulimit []
Options

ulimit

Pour plus d'informations sur ulimit, voir Définir les ulimits dans un conteneur ⟨https://docs.docker.com/engine/reference/commandline/run/#set-ulimits-in-container---ulimi

t⟩

Construire une image en utilisant un Dockerfile situé dans le répertoire

courant

Les images Docker peuvent être construites en utilisant la commande build et un Dockerfile

: 
docker build
.

Pendant le processus de build, Docker crée des images intermédiaires. Pour les conserver, vous devez définir explicitement --rm fa

lse. 
docker build --rm false
.

Une bonne pratique consiste à créer un sous-répertoire avec un nom lié et à créer le Dockerfile dans ce répertoire. Par exemple, un répertoire appelé mongo peut contenir un Dockerfile pour créer une image Docker MongoDB. De même, un autre répertoire appelé httpd peut être utilisé pour stocker des Dockerfiles pour des images de serveur web

Apache.

C'est également une bonne pratique d'ajouter les fichiers requis pour l'image au sous-répertoire. Ces fichiers seront ensuite spécifiés avec les instructions COPY ou ADD dans le Dockerfile

.

Remarque : Si vous incluez un fichier tar (une bonne pratique), Docker extraira automatiquement le contenu du fichier tar spécifié dans l'instruction ADD vers la ci

ble spé
cifiée.

Construire une image et nommer cette

image

Une bonne pratique consiste à donner un nom à l'image que vous construisez. Notez que seuls a-z0-9-_ devraient être utilisés pour la cohérence. Il n'y a pas de règles strictes ici, mais il est préférable de réfléchir aux

noms.

Le drapeau -t/--tag est utilisé pour renommer une image. Voici quelques exemples

:

Bien que ce ne soit pas une bonne pratique, les noms d'images peuvent être arbitraires

: 
docker build -t myimage
.

Une meilleure approche consiste à fournir un dépôt, un nom et une étiquette entièrement qualifiés et significatifs (où l'étiquette dans ce contexte signifie le qualificatif après le ":"). Dans cet exemple, nous construisons une image JBoss pour le dépôt Fedora et lui donnons la version 1.0

: 
docker build -t fedora/jboss:1.0
.

L'exemple suivant est pour le dépôt utilisateur "whenry" et utilise Fedora et JBoss en lui donnant la version 2.1

: 
docker build -t whenry/fedora-jboss:v2.1
.

Si vous ne fournissez pas d'étiquette de version, Docker assignera lates

t : 
docker build -t whenry/fedora-jboss
.

Lorsque vous listez les images, l'image ci-dessus aura l'étiquette latest

.

Vous pouvez appliquer plusieurs étiquettes à une image. Par exemple, vous pouvez appliquer l'étiquette latest à une image nouvellement construite et ajouter une autre étiquette qui fait référence à une version spécifique. Par exemple, pour étiqueter une image à la fois comme whenry/fedora-jboss:latest et whenry/fedora-jboss:v2.1, utilisez ce qui suit

: 
docker build -t whenry/fedora-jboss:latest -t whenry/fedora-jboss:v2.1
.

Ainsi, renommer une image est arbitraire, mais il convient de réfléch

ir à une convention utile qui a du sens pour les consommateurs et qui doit
également prendre en compte les conventions de la communauté Docker.

Construire une image en utilisant une

URL

Cela clonera le dépôt GitHub spécifié depuis l'URL et l'utilisera comme contexte. Le Dockerfile à la racine du dépôt est utilisé comme Dockerfile. Cela ne fonctionne que si le dépôt GitHub est un dépôt

dédié. 
docker build github.com/scollier/purpletes
t

Remarque : Vous pouvez définir un dépôt Git arbitraire via le schéma

git
://.

Construire une image en utilisant une URL vers un contexte compressé en

tarball

Cela enverra l'URL elle-même au démon Docker. Le démon récupérera l'archive tarball, la décompressera et utilisera son contenu comme contexte de build. Le Dockerfile à la racine de l'archive et le reste de l'archive seront utilisés comme contexte du build. Si vous passez également une option -f PATH/Dockerfile, le système cherchera ce fichier à l'intérieur du contenu du

tarball. 
docker build -f dev/Dockerfile https://10.10.10.1/docker/context.tar.
gz

Remarque : les formats de compression pr

is en charge sont 'xz', 'bzip2', 'gzip'
et 'identity' (aucune compression).

Spécifier la technologie d'isolation pour le conteneur

(--isolation)

Cette option est utile dans les situations où vous exécutez des conteneurs Docker sur Windows. L'option --isolation <value> définit la technologie d'isolation d'un conteneur. Sur Linux, la seule prise en charge est l'option default qui utilise les espaces de noms Linux. Sur Microsoft Windows, vous pouvez spécifier ces valeurs

:
  • default : utiliser la valeur spécifiée par l'option --exec-opt du démon Docker. Si le démon ne spécifie pas de technologie d'isolation, Microsoft Windows utilise process comme valeur par
    • défaut.
  • process : isolation par espace de noms
    • uniquement.
  • hyperv : isolation basée su
    • r la partitio
n de l'hypervi
seur Hyper-V.
