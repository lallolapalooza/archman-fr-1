podman-kube-play(1) Manuel des commandes générales podman-kube-play(1)

NOM

podman-kube-play - Créer des conteneurs, des pods et des volumes basés sur des fichiers YAML Kubernetes

SYNTAXE

podman kube play [options] fichier.yml|-|https://website.io/fichier.yml

DESCRIPTION

podman kube play lit un fichier structuré de YAML Kubernetes. Il recrée les conteneurs, les pods ou les volumes décrits dans le YAML. Les conteneurs au sein d'un pod sont ensuite démarrés, et l'ID du nouveau Pod ou le nom du nouveau Volume est affiché. Si le fichier YAML est spécifié comme "-", alors podman kube play lit le fichier YAML depuis l'entrée standard. L'entrée peut également être une URL pointant vers un fichier YAML tel que https://podman.io/demo.yml. podman kube play lit le YAML depuis l'URL et crée des pods et des conteneurs à partir de celui-ci.

En utilisant l'option de ligne de commande --down, il est également capable de démanteler les pods créés par une précédente exécution de podman kube play.

En utilisant l'option de ligne de commande --replace, il démonte les pods (s'il y en a) créés par une précédente exécution de podman kube play et recrée les pods avec le fichier YAML Kubernetes.

Idéalement, le fichier d'entrée est créé par la commande Podman (voir podman-kube-generate(1)). Cela garantit une importation fluide et des résultats attendus.

Actuellement, les types Kubernetes pris en charge sont :

  • Pod
  • Deployment
  • PersistentVolumeClaim
  • ConfigMap
  • Secret
  • DaemonSet
  • Job

Pods ou Déploiements Kubernetes

Seulement cinq types de volumes sont pris en charge par kube play : les volumes de type hostPath, emptyDir, configMap, persistentVolumeClaim et image.

  • Lors de l'utilisation du type de volume hostPath, seuls les sous-types défaut (vide), DirectoryOrCreate, Directory, FileOrCreate, File, Socket, CharDevice et BlockDevice sont pris en charge. Podman interprète la valeur de hostPath path comme un chemin de fichier si elle contient au moins une barre oblique, sinon Podman traite la valeur comme le nom d'un volume nommé.
  • Lors de l'utilisation d'un persistentVolumeClaim, la valeur de claimName est le nom du volume nommé Podman.
  • Lors de l'utilisation d'un volume emptyDir, Podman crée un volume anonyme qui est attaché aux conteneurs exécutés à l'intérieur du pod et est supprimé une fois le pod supprimé.
  • Lors de l'utilisation d'un volume configMap, Podman crée un volume anonyme qui est attaché aux conteneurs exécutés à l'intérieur du pod et est supprimé une fois le pod supprimé.
  • Lors de l'utilisation d'un volume image, Podman crée un volume d'image en lecture seule avec un sous-chemin vide (l'image entière est montée). L'image doit déjà exister localement. Elle est prise en charge en mode rootful uniquement.

Note : La politique de redémarrage par défaut pour les conteneurs est always. Vous pouvez changer la valeur par défaut en définissant le champ restartPolicy dans le spec.

Note : Lors de la lecture d'un fichier kube YAML contenant des init containers, l'init container est créé avec la valeur de type d'init once. Pour changer la valeur par défaut, utilisez l'annotation io.podman.annotations.init.container.type pour définir le type à always.

Note : Les types de volumes hostPath créés par kube play reçoivent un label partagé SELinux (z), les montages bind ne sont pas reétiquetés (utilisez chcon -t container_file_t -R <répertoire>).

Note : Pour définir les espaces utilisateurs (userns) d'un pod, utilisez l'annotation io.podman.annotations.userns dans la définition du pod/déploiement. Par exemple, l'annotation io.podman.annotations.userns=keep-id indique à Podman de créer un espace utilisateur où le UID:GID de l'utilisateur rootless courant sont mappés aux mêmes valeurs dans le conteneur. Ceci peut être remplacé par le drapeau --userns.

Note : Utilisez l'annotation io.podman.annotations.volumes-from pour monter des volumes d'un conteneur à un autre. Vous pouvez monter des volumes depuis plusieurs conteneurs sources vers un conteneur cible. Les conteneurs sources qui appartiennent au même pod doivent être définis avant le conteneur source dans le fichier YAML kube. Le format de l'annotation est io.podman.annotations.volumes-from/conteneurCible: "conteneurSource1:optionsMontage1;conteneurSource2:optionsMontage2".

Note : Si le tag :latest est utilisé, Podman tente de tirer l'image d'un registre. Si l'image a été construite localement avec Podman ou Buildah, son domaine est localhost, dans ce cas, Podman utilise l'image du magasin local même si elle a le tag :latest.

Note : La commande podman play kube est un alias de podman kube play et effectue la même fonction.

Note : La commande podman kube down peut être utilisée pour arrêter et supprimer des pods ou conteneurs basés sur le même fichier YAML Kubernetes utilisé par podman kube play pour les créer.

Note : Pour personnaliser le nom du conteneur d'infrastructure (infra container) créé pendant podman kube play, utilisez l'annotation io.podman.annotations.infra.name dans la définition du pod. Cette annotation est automatiquement définie lors de la génération d'un fichier kube à partir d'un pod créé avec le drapeau --infra-name défini.

Note : Utilisez l'annotation io.podman.annotations.pids-limit/$nomCtr pour configurer la limite de pids du pod.

Note : Utilisez l'annotation io.podman.annotations.cpuset/$nomCtr pour restreindre l'exécution d'un conteneur à un ensemble spécifique de cœurs CPU. Ceci est équivalent à l'option --cpuset-cpus=nombre dans podman-run(1).

Note : Utilisez l'annotation io.podman.annotations.memory-nodes/$nomCtr pour restreindre les allocations mémoire d'un conteneur à un ensemble spécifique de nœuds mémoire sur les systèmes NUMA. Ceci est équivalent à l'option --cpuset-mems=nœuds dans podman-run(1).

PersistentVolumeClaims Kubernetes

Un PersistentVolumeClaim Kubernetes représente un volume nommé Podman. Seul le nom du PersistentVolumeClaim est requis par Podman pour créer un volume. Les annotations Kubernetes peuvent être utilisées pour exploiter les options disponibles pour les volumes Podman.

  • volume.podman.io/driver
  • volume.podman.io/device
  • volume.podman.io/type
  • volume.podman.io/uid
  • volume.podman.io/gid
  • volume.podman.io/mount-options
  • volume.podman.io/import-source
  • volume.podman.io/image

Utilisez volume.podman.io/import-source pour importer le contenu de l'archive (.tar, .tar.gz, .tgz, .bzip, .tar.xz, .txz, .tar.zst) spécifié dans la valeur de l'annotation dans le volume Podman créé.

Kube play est capable de construire des images à la volée étant donné la bonne disposition de répertoires et les Containerfiles. Cette option n'est pas encore disponible pour les clients distants, y compris les machines Mac et Windows (à l'exception de WSL2). Considérez l'extrait suivant d'un fichier YAML :

apiVersion: v1
kind: Pod
metadata:
...
spec:
  containers:
  - name: conteneur
    image: foobar
...

S'il existe un répertoire nommé foobar dans le répertoire courant avec un fichier nommé Containerfile ou Dockerfile, Podman kube play construit cette image et la nomme foobar. Une structure de répertoire exemple pour cet exemple ressemble à :

|- mesfichierskube
    |- monfichierplay.yaml
    |- foobar
         |- Containerfile

La construction considère foobar comme le répertoire de contexte pour la construction. S'il existe une image dans le stockage local appelée foobar, l'image n'est pas construite sauf si le drapeau --build est utilisé. Utilisez --build=false pour désactiver complètement les constructions.

Kube play prend en charge les sélecteurs de périphériques CDI (Container Device Interface) pour partager les périphériques hôtes (par exemple, les GPU) avec les conteneurs. Le format de configuration suit la gestion des ressources étendues de Kubernetes :

apiVersion: v1
kind: Pod
spec:
  containers:
  - name: conteneur
    resources:
      limits:
        nvidia.com/gpu=all: 1

Pour activer le partage des périphériques hôtes, de manière analogue à l'utilisation du drapeau --device, Podman kube prend en charge un sélecteur CDI personnalisé : podman.io/device=<chemin du périphérique hôte>.

ConfigMap Kubernetes

Un ConfigMap Kubernetes peut être référencé comme source de variables d'environnement ou de volumes dans les Pods ou les Déploiements. Les ConfigMaps ne sont pas un objet autonome dans Podman ; au lieu de cela, lorsqu'un conteneur utilise un ConfigMap, Podman crée les variables d'environnement ou les volumes selon les besoins.

Par exemple, le document YAML suivant définit un ConfigMap puis l'utilise dans un Pod :

apiVersion: v1
kind: ConfigMap
metadata:
  name: foo
data:
    FOO: bar
---
apiVersion: v1
kind: Pod
metadata:
  name: foobar
spec:
  containers:
  - name: conteneur-1
    image: fooba
r envFrom: - configMapRef: name: foo optional: false

et en conséquence la variable d'environnement FOO est définie à bar pour le conteneur container-1

.

Secret

Kubernetes

Le Secret Kubernetes représente un secret nommé Podman. Le Secret Kubernetes est enregistré en entier et peut être référencé comme source de variables d'environnement ou de volumes dans les Pods ou les

Deployments.

Par exemple, le document YAML suivant définit un Secret puis l'utilise dans un Pod

: 
kind: Secret
apiVersion: v1
metadata:
  name: foo
data:
  foo: YmFy # base64 for bar
---
apiVersion: v1
kind: Pod
metadata:
  name: foobar
spec:
  containers:
  - name: container-1
    image: foobar
    env:
    - name: FOO
      valueFrom:
        secretKeyRef:
          name: foo
          key:
foo

et en conséquence la variable d'environnement FOO est définie à bar pour le conteneur container-1

.

Lorsque l'option --no-hostname est définie, le fichier /etc/hostname de l'image sera préservé sans modification s'il existe. .SS --no-hosts .PP Ne modifie pas le fichier /etc/hosts dans le pod. .PP Podman prend le contrôle du fichier /etc/hosts du pod par défaut et ajoute des entrées pour le nom du conteneur (voir l'option --name) et le nom d'hôte (voir l'option --hostname), les hôtes internes host.containers.internal et host.docker.internal, ainsi que tout nom d'hôte ajouté à l'aide de l'option --add-host. Référez-vous à l'option --add-host pour plus de détails. Passer --no-hosts désactive cette fonction, de sorte que le fichier /etc/hosts de l'image est conservé sans modification. La même chose peut être réalisée globalement en définissant no_hosts=true dans containers.conf. .PP Cette option entre en conflit avec les hôtes ajoutés dans le YAML Kubernetes. .SS --no-pod-prefix .PP Ne préfixe pas le nom du conteneur avec le nom du pod. .SS --publish=[[ip:][hostPort]:]containerPort[/protocol] .PP Définit ou remplace une définition de port dans le fichier YAML. .PP Les listes de ports dans le fichier YAML et sur la ligne de commande sont fusionnées. La correspondance est effectuée en utilisant le champ containerPort. Si containerPort existe à la fois dans le fichier YAML et dans l'option, cette dernière a la priorité. .SS --publish-all .PP Définir cette option sur true exposera tous les ports à l'hôte, même s'ils ne sont spécifiés que via containerPort dans le YAML K8. En ce qui concerne le port qui sera exposé, --publish a une priorité plus élevée que hostPort, a une priorité plus élevée que containerPort. .PP Si défini sur false (ce qui est la valeur par défaut), seuls les ports définis via hostPort ou --publish sont publiés sur l'hôte. .SS --quiet, -q .PP Supprime les informations de sortie lors du téléchargement des images. .SS --replace .PP Démonte les pods créés par une exécution précédente de kube play et recrée les pods. Cette option est utilisée pour maintenir les pods existants à jour en fonction du YAML Kubernetes. .SS --seccomp-profile-root=path .PP Chemin du répertoire des profils seccomp (par défaut : "/var/lib/kubelet/seccomp"). (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (à l'exception de WSL2)). .SS --start .PP Démarre le pod après sa création, défini sur false pour seulement le créer. .SS --tls-verify .PP Exige HTTPS et vérifie les certificats lors du contact avec les registres (par défaut : true). S'il est explicitement défini sur true, la vérification TLS est utilisée. S'il est défini sur false, la vérification TLS n'est pas utilisée. S'il n'est pas spécifié, la vérification TLS est utilisée sauf si le registre cible est répertorié comme un registre non sécurisé dans containers-registries.conf(5). .SS --userns=mode .PP Définit le mode espace utilisateur pour le conteneur. .PP Si --userns n'est pas défini, la valeur par défaut est déterminée comme suit. - Si --pod est défini, --userns est ignoré et l'espace utilisateur du pod est utilisé. - Si la variable d'environnement PODMAN_USERNS est définie, sa valeur est utilisée. - Si userns est spécifié dans containers.conf, cette valeur est utilisée. - Sinon, --userns=host est supposé. .PP --userns="" (c'est-à-dire une chaîne vide) est un alias pour --userns=host. .PP Cette option est incompatible avec --gidmap, --uidmap, --subuidname et --subgidname. .PP Mappages des clés pour l'utilisateur sans privilèges --userns : .TS lb | l | l . lb Clé Utilisateur hôte Utilisateur conteneur l auto $UID nil (L'UID de l'utilisateur hôte n'est pas mappé dans le conteneur.) l host $UID 0 (Le compte utilisateur par défaut est mappé à l'utilisateur root dans le conteneur.) l keep-id $UID $UID (Mappe le compte utilisateur au même UID dans le conteneur.) l keep-id:uid=200,gid=210 $UID 200:210 (Mappe le compte utilisateur à l'UID spécifié, valeur GID dans le conteneur.) l nomap $UID nil (L'UID de l'utilisateur hôte n'est pas mappé dans le conteneur.) .TE .PP Les valeurs valides pour mode sont : .PP auto[:OPTIONS,...] : crée automatiquement un espace utilisateur unique. .TP mode rootful : l'option --userns=auto nécessite que le nom d'utilisateur containers soit spécifié dans les fichiers /etc/subuid et /etc/subgid, avec une plage inutilisée d'identifiants d'utilisateurs subordonnés que Podman peut allouer aux conteneurs. Exemple : containers:2147483647:2147483648. .TP mode rootless : la plage d'utilisateurs des fichiers /etc/subuid et /etc/subgid sera utilisée. Notez que l'exécution d'un seul conteneur sans utiliser --userns=auto utilisera la plage complète d'UID et n'autorisera pas de subdivision ultérieure. Voir subuid(5). .IP Podman alloue des plages uniques d'UID et de GID à partir des identifiants d'utilisateurs subordonnés containers. La taille des plages est basée sur le nombre d'UID requis dans l'image. Le nombre d'UID et de GID peut être remplacé par l'option size. .PP L'option --userns=keep-id utilise tous les subuids et subgids de l'utilisateur. L'option --userns=nomap utilise tous les subuids et subgids de l'utilisateur, à l'exception de l'ID de l'utilisateur lui-même. Utiliser --userns=auto lors du démarrage de nouveaux conteneurs ne fonctionne pas tant qu'il existe des conteneurs démarrés avec --userns=nomap ou --userns=keep-id sans limiter la taille de l'espace utilisateur. .PP Les options auto

    OPTIONS

    --container-lifetime
    The value can be one of the following:
    remove
    Remove the containers when the pod is removed.
    keep
    Do not remove the containers when the pod is removed. This is the default.
    --down
    Tear down the pod and containers described in the specified host YAML file.
    --ignore-stdin
    Ignore stdin, even when it is attached. Default is false.
    --network network
    Join a container to a specific network. This option can be used multiple times for multiple networks. The network name can be prefixed with <network_name>:, followed by network options, separated by commas. The available network options are:
    ip=IP
    Assign a static IP address to the container on the specified network.
    ipv6=IPv6
    Assign a static IPv6 address to the container on the specified network.
    link-local-ip=LinkLocalIP
    Assign a static link-local IP address to the container on the specified network.
    --quiet, -q
    Suppress informational output. Default is false.
    --resource-exclusive
    Ensure that the pod and its containers are the only ones running on the node. This option is only available for rootful containers.
    --service-account-token-dir path
    The directory containing the service account token that will be mounted into the pod. This directory must contain the following files:
    ca.crt
    The CA certificate.
    namespace
    The namespace of the service account.
    token
    The service account token.
    --skip-ready-info
    Skip the ready information messages. Default is false.
    --skip-mounts
    Skip mounting volumes specified in the YAML file. Default is false.
    --userns userns
    Join a container to a user namespace. The user namespace is created from the parent user namespace. The namespace is created from the parent user namespace.

    The value can be one of the following:

    gidmapping=CONTAINER_GID:HOST_GID:SIZE
    to force a GID mapping to be present in the user namespace.
    size=SIZE
    to specify an explicit size for the automatic user namespace. e.g. --userns=auto:size=8192. If size is not specified, auto estimates a size for the user namespace.
    uidmapping=CONTAINER_UID:HOST_UID:SIZE
    to force a UID mapping to be present in the user namespace.

    The host UID and GID in gidmapping and uidmapping can optionally be prefixed with the @ symbol. In this case, podman will look up the intermediate ID corresponding to host ID and it will map the found intermediate ID to the container id. For details see --uidmap.

    container:id
    join the user namespace of the specified container.
    host or "" (empty string)
    run in the user namespace of the caller. The processes running in the container have the same privileges on the host as any other process launched by the calling user.
    keep-id
    creates a user namespace where the current user's UID:GID are mapped to the same values in the container. For containers created by root, the current mapping is created into a new user namespace.

    In addition, the init process within the container will run under the current user's UID. This behavior overrides the image's USER instruction unless you explicitly set --user.

    Valid keep-id options:

    uid=UID
    override the UID inside the container that is used to map the current user to.
    gid=GID
    override the GID inside the container that is used to map the current user to.
    size=SIZE
    override the size of the configured user namespace. It is useful to not saturate all the available IDs. Not supported when running as root.
    nomap
    creates a user namespace where the current rootless user's UID:GID are not mapped into the container. This option is not allowed for containers created by the root user.
    ns:namespace
    run the pod in the given existing user namespace.
    --wait, -w
    Run pods and containers in the foreground. Default is false.

    At any time you can run podman pod ps in another shell to view a list of the running pods and containers.

    When attached in the tty mode, you can kill the pods and containers by pressing Ctrl-C or receiving any other interrupt signals.

    All pods, containers, and volumes created with podman kube play is removed upon exit.
