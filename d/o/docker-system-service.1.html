DESCRIPTIO

N

La commande podman system service crée un service en écoute qui répond aux appels d'API pour Podman. La commande est disponible sur les systèmes Linux et est généralement exécutée dans des services systemd. La commande n'est pas disponible lorsque la commande Podman est exécutée directement sur un hôte Windows ou macOS ou dans d'autres situations où la commande Podman accède à un service d'API Podman

distant.

L'API REST fournie par podman system service est divisée en deux parties : une couche de compatibilité offrant une prise en charge de l'API Docker v1.40 et une couche Libpod native à Podman. La documentation pour cette dernière est disponible à l'adresse https://docs.podman.io/en/latest/_static/api.html. Les deux API sont versionnées, mais le serveur ne rejette pas les requêtes dont la version définie n'est pas prise en

charge.

Exécuter la commande dans un service

systemd

La commande podman system service prend en charge l'activation par socket systemd. Lorsque la commande est exécutée dans un service systemd, le service d'API peut donc être fourni à la demande. Si le service systemd n'est pas déjà en cours d'exécution, il sera activé dès qu'un client se connecte au socket en écoute. Systemd exécute alors la commande podman system service. Après un certain temps d'inactivité, défini par l'option --time, la commande se termine. Systemd définit l'état de podman.service comme inactif. À ce stade, aucun processus podman system service n'est en cours d'exécution. Aucune ressource de calcul inutile n'est gaspillée. Dès qu'un autre client se connecte, systemd active à nouveau le service

systemd.

Exécuter la commande

directement

Pour prendre en charge l'exécution d'un service d'API sans utiliser un service systemd, la commande accepte également un argument d'endpoint facultatif pour l'API sous forme d'URI. Par exemple, unix:///tmp/foobar.sock ou tcp://localhost:8080. Si aucun endpoint n'est fourni, la valeur par défaut est utilisée. L'endpoint par défaut pour un service avec privilèges (rootful) est unix:///run/podman/podman.sock et sans privilèges (rootless) est unix://$XDG_RUNTIME_DIR/podman/podman.sock (par exemple unix:///run/user/100

Sécurit

é

Veuillez noter que l'API accorde un accès complet à toutes les fonctionnalités de Podman, et permet donc l'exécution de code arbitraire en tant que l'utilisateur exécutant l'API, sans possibilité de limiter ou d'auditer cet accès. Le modèle de sécurité de l'API repose sur l'accès via un socket Unix avec un accès restreint via les permissions de fichiers standard, garantissant que seul l'utilisateur exécutant le service pourra y accéder. TLS peut être utilisé pour sécuriser ce socket en exigeant que les clients présentent un certificat signé par une autorité de certification ("CA") de confiance, ainsi que pour permettre au client de vérifier l'identité de l'API. Nous recommandons fortement de ne pas rendre le socket de l'API disponible via le réseau (c'est-à-dire en liant le service à une URL tcp) sans activer le TLS mutuel pour authentifier le client. Même l'accès via Localhost comporte des risques - toute personne ayant accès au système pourra accéder à l'API. Si un accès distant est requis, nous recommandons plutôt de transférer le socket de l'API via SSH et de limiter l'accès sur la machine distante autant que possible. Si une URL tcp doit être utilisée sans TLS, l'utilisation de l'option --cors est recommand
