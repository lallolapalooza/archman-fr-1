Créer un fournisseur de points de trace est la première étape de l'utilisation

de

liblttng-ust . Les étapes suivantes sont

:
•Instrumenter votre application avec des appels lttng_ust_tracepoint() [[492]
]
•Construire votre application avec le support de LTTng-UST,ther statiquement ou dynamiquement.

Un fournisseur de points de trace est un objet compilé contenant les sondes d'événement correspondant à vos définitions de points de trace personnalisés. Un fournisseur de points de trace contient le code permettant d'obtenir la taille d'un événement et de le sérialiser, entre autres.

Pour créer un fournisseur de points de trace, commencez avec le suivant en-tête de fournisseur de points de trace modèle :

#undef LTTNG_UST_TRACEPOINT_PROVIDER
#define LTTNG_UST_TRACEPOINT_PROVIDER my_provider
#undef LTTNG_UST_TRACEPOINT_INCLUDE
#define LTTNG_UST_TRACEPOINT_INCLUDE "./tp.h"
#if !defined(_TP_H) || \
    defined(LTTNG_UST_TRACEPOINT_HEADER_MULTI_READ)
#define _TP_H
#include <lttng/tracepoint.h>
/*
 * LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(),
 * LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(),
 * LTTNG_UST_TRACEPOINT_LOGLEVEL(), and `LTTNG_UST_TRACEPOINT_ENUM()`
 * are used here.
 */
#endif /* _TP_H */
#include <lttng/tracepoint-event.h>

Dans ce modèle, le fournisseur de points de trace est nommé my_provider (définition LTTNG_UST_TRACEPOINT_PROVIDER ). Le fichier doit porter le nom de la définition LTTNG_UST_TRACEPOINT_INCLUDE (tp.h dans ce cas). Entre #include <lttng/tracepoint.h> et #endif vont les invocations des macros LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(), LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(), LTTNG_UST_TRACEPOINT_LOGLEVEL(), et LTTNG_UST_TRACEPOINT_ENUM() .


Remarque

Vous pouvez éviter d'écrire le prologue et l'épilogue répétitifs dans le fichier modèle ci-dessus en utilisant l'outil lttng-gen-tp(1) fourni avec LTTng-UST.

Le fichier d'en-tête du fournisseur de points de trace doit être inclus dans un fichier source qui ressemble à ceci :

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#include "tp.h"

Ensemble, ces deux fichiers (appelons-les tp.h et tp.c) forment les sources du fournisseur de points de trace, prêtes à être compilées.

Vous pouvez créer plusieurs fournisseurs de points de trace à utiliser dans une seule application, mais chacun doit avoir son propre fichier d'en-tête.

La section d'utilisation de LTTNG_UST_TRACEPOINT_EVENT() ci-dessous montre comment utiliser la macro LTTNG_UST_TRACEPOINT_EVENT() pour définir les points de trace réels dans le fichier d'en-tête du fournisseur de points de trace.

Voir la section EXEMPLE ci-dessous pour un exemple complet.

Utilisation de LTTNG_UST_TRACEPOINT_EVENT()

La macro LTTNG_UST_TRACEPOINT_EVENT() est utilisée dans un fichier d'en-tête de fournisseur modèle (voir la section Création d'un fournisseur de points de trace ci-dessus) pour définir des points de trace LTTng-UST.

Le modèle d'utilisation de LTTNG_UST_TRACEPOINT_EVENT() est le suivant :

LTTNG_UST_TRACEPOINT_EVENT(
    /* Tracepoint provider name */
    my_provider,
    /* Tracepoint/event name */
    my_tracepoint,
    /* List of tracepoint arguments (input) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* List of fields of eventual event (output) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

La macro LTTNG_UST_TP_ARGS() contient les arguments d'entrée du point de trace. Ces arguments peuvent être utilisés dans les expressions d'argument des champs de sortie définis dans LTTNG_UST_TP_FIELDS().

Le format des paramètres de LTTNG_UST_TP_ARGS() est : type C, puis nom de l'argument ; répétez au besoin, jusqu'à dix fois. Par exemple :

LTTNG_UST_TP_ARGS(
    int, my_int,
    const char *, my_string,
    FILE *, my_file,
    double, my_float,
    struct my_data *, my_data
)

La macro LTTNG_UST_TP_FIELDS() contient les champs de sortie du point de trace, c'est-à-dire les données réelles qui peuvent être enregistrées dans le charge utile d'un événement émis par ce point de trace.

La macro LTTNG_UST_TP_FIELDS() contient une liste de macros lttng_ust_field_*() NON séparées par des virgules. Les macros disponibles sont documentées dans la section sur les macros de type de champ lttng_ust_field_*() disponibles ci-dessous.

Expression C résultant en la valeur du champ. Cette expression peut utiliser un ou plusieurs arguments passés au point de trace. Les arguments d'un point de trace donné sont définis dans la macro LTTNG_UST_TP_ARGS() (voir la section Création d'un fournisseur de points de trace ci-dessus).

Nom du champ d'événement (syntaxe d'identifiant C, PAS une chaîne littérale).

Type C flottant (float ou double). La taille de ce type détermine la taille du champ du nombre en virgule flottante.

int_type

Type C entier. La taille de ce type détermine la taille du champ entier/énumération.

Expression C résultant en la longueur de la séquence. Cette expression peut utiliser un ou plusieurs arguments passés au point de trace.

len_type

Type C entier non signé de la longueur de la séquence.

Traçage des constructeurs et destructeurs C/C++

Si l'une des conditions suivantes est vraie :

•Vous compilez votre application C++ avec GCC ≤ 4.8.
•Vous compilez votre application C/C++ avec un compilateur C++ et définissez LTTNG_UST_ALLOCATE_COMPOUND_LITERAL_ON_HEAP.

Alors LTTng ne tracera pas :

•Les constructeurs et destructeurs C dans l'application elle-même ou dans les archives liées statiquement.
•Certains constructeurs et destructeurs C++ dans l'application elle-même ou dans les archives liées statiquement.

Dans ce cas, les constructeurs et destructeurs C++ exacts qui ne seront pas tracés dépendent de l'ordre d'initialisation au sein de chaque unité de traduction et entre toutes les unités de traduction lorsqu'elles sont liées ensemble.

Liaison statique du fournisseur de points de trace

Avec la méthode de liaison statique, les fournisseurs de points de trace compilés sont copiés dans l'application cible.

Définissez LTTNG_UST_TRACEPOINT_DEFINE sous la définition LTTNG_UST_TRACEPOINT_CREATE_PROBES dans la source du fournisseur de points de trace :

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#define LTTNG_UST_TRACEPOINT_DEFINE
#include "tp.h"

Créez le fichier objet du fournisseur de points de trace :

$ cc -c -I. tp.c

Note

Bien qu'une application instrumentée avec des points de trace LTTng-UST puisse être compilée avec un compilateur C++, les sondes de points de trace doivent être compilées avec un compilateur C.

À ce stade, vous pouvez archiver ce fichier objet du fournisseur de points de trace, éventuellement avec d'autres fichiers objets de votre application ou avec d'autres fichiers objets de fournisseurs de points de trace, sous forme de bibliothèque statique :

$ ar rc tp.a tp.o

L'utilisation d'une bibliothèque statique a l'avantage de centraliser les objets des fournisseurs de points de trace afin qu'ils puissent être partagés entre plusieurs applications. Ainsi, lorsque le fournisseur de points de trace est modifié, les changements du code source n'ont pas besoin d'être patchés dans l'arborescence du code source de chaque application. Les applications doivent être relinkées après chaque modification, mais n'ont pas besoin d'être recompilées autrement (sauf si l'API du fournisseur de points de trace change).

Ensuite, liez votre application avec ce fichier objet (ou avec la bibliothèque statique qui le contient) et avec liblttng-ust et libdl (libc sur un système BSD) :

$ cc -o app tp.o app.o -llttng-ust -ldl

Chargement dynamique du fournisseur de points de trace

La deuxième approche pour empaqueter le fournisseur de points de trace est d'utiliser le chargeur dynamique : la bibliothèque et ses fonctions membres sont recherchées explicitement, chargées à l'exécution.

Dans ce scénario, le fournisseur de points de trace est compilé en tant qu'objet partagé.

Le processus de création de l'objet partagé du fournisseur de points de trace est quasiment le même que la méthode de liaison statique, à ceci près que :

•Puisque le fournisseur de points de trace ne fait pas partie de l'application, LTTNG_UST_TRACEPOINT_DEFINE doit être défini, pour chaque fournisseur de points de trace, dans un seul fichier source de l' application.
•LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE doit être défini à côté de LTTNG_UST_TRACEPOINT_DEFINE.

Concernant LTTNG_UST_TRACEPOINT_DEFINE et LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE, la pratique recommandée est d'utiliser un fichier source C distinct dans votre application pour les définir, puis d'inclure les fichiers d'en-tête du fournisseur de points de trace par la suite. Par exemple, comme tp-define.c :

#define LTTNG_UST_TRACEPOINT_DEFINE
#define LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE
#include "tp.h"

Le fichier objet du fournisseur de points de trace utilisé pour créer la bibliothèque partagée est construit comme avec la méthode de liaison statique, mais avec l'option -fpic :

$ cc -c -fpic -I. tp.c

Il est ensuite lié en tant que bibliothèque partagée comme suit :

$ cc -shared -Wl,--no-as-needed -o tp.so tp.o -llttng-ust

Cet objet partagé du fournisseur de points de trace n'est pas lié à l'application utilisateur : il doit être chargé manuellement. C'est pourquoi l'application est construite sans mention de ce fournisseur de points de trace, mais nécessite quand même libdl :

$ cc -o app app.o tp-define.o -ldl

Il existe deux façons de charger dynamiquement l'objet partagé du fournisseur de points de trace :

•Le charger manuellement depuis l'application en utilisant dlopen(3)
•Faire en sorte que le chargeur dynamique le charge avec la variable d'environnement LD_PRELOAD (voir ld.so(8))

Si l'application ne charge pas dynamiquement l'objet partagé du fournisseur de points de trace en utilisant l'une des méthodes ci-dessus, le traçage est désactivé pour cette application, et les événements ne sont pas listés dans la sortie de lttng-list(1).

Notez qu'il n'est pas sûr d'utiliser dlclose(3) sur un objet partagé de fournisseur de points de trace qui est activement utilisé pour le traçage, en raison d'un manque de comptage de références de LTTng-UST vers l'objet partagé.

Par exemple, lier statiquement un fournisseur de points de trace à un objet partagé qui doit être chargé dynamiquement par une application (un plugin, par exemple) n'est pas sûr : l'objet partagé, qui contient le fournisseur de points de trace, pourrait être fermé dynamiquement (dlclose(3)) à tout moment par l'application.

Pour instrumenter un objet partagé, soit :

•Lier statiquement le fournisseur de points de trace à l'application, soit
•Construire le fournisseur de points de trace en tant qu'objet partagé (en suivant la procédure décrite dans cette section), et le précharger lorsque le traçage est nécessaire en utilisant la variable d'environnement LD_PRELOAD.

Utilisation de LTTng-UST avec les démons

Des précautions supplémentaires sont nécessaires lors de l'utilisation de liblttng-ust avec des applications démons qui appellent fork(2), clone(2), ou le rfork(2) de BSD sans un appel système suivant de la famille exec(3). La bibliothèque liblttng-ust-fork.so doit être préchargée avant de démarrer l'application avec la variable d'environnement LD_PRELOAD (voir ld.so(8)).

Pour utiliser liblttng-ust avec une application démon qui ferme des descripteurs de fichiers qui n'ont pas été ouverts par elle, préchargez la bibliothèque liblttng-ust-fd.so avant de démarrer l'application. Les cas d'utilisation typiques incluent les démons fermant tous les descripteurs de fichiers après fork(2), et les applications buggées effectuant des "doubles fermetures".

Détecter si LTTng-UST est chargé

Pour détecter si liblttng-ust est chargé à partir d'une application :

1.Définissez le symbole faible lttng_ust_loaded globalement : 
int lttng_ust_loaded __attribute__((weak));

Ce symbole faible est défini par le constructeur de liblttng-ust.

2.Testez lttng_ust_loaded là où c'est nécessaire : 
/* ... */
if (lttng_ust_loaded) {
    /* LTTng-UST est chargé */
} else {
    /* LTTng-UST N'EST PAS chargé */
}
/* ... */

#include <stdlib.h>
#include <stdio.h>
#include "tp.h"
#include "app.h"
static int array_of_ints[] = {
    100, -35, 1, 23, 14, -6, 28, 1001, -3000,
};
int main(int argc, char* argv[])
{
    FILE *stream;
    struct app_struct app_struct;
    lttng_ust_tracepoint(my_provider, simple_event, argc, argv[0]);
    stream = fopen("/tmp/app.txt", "w");
    if (!stream) {
        fprintf(stderr,
                "Error: Cannot open /tmp/app.txt for writing\n");
        return EXIT_FAILURE;
    }
    if (fprintf(stream, "0123456789") != 10) {
        fclose(stream);
        fprintf(stderr, "Error: Cannot write to /tmp/app.txt\n");
        return EXIT_FAILURE;
    }
    lttng_ust_tracepoint(my_provider, big_event, 35,
                         "hello tracepoint", stream, -3.14,
                         array_of_ints);
    fclose(stream);
    app_struct.b = argc;
    app_struct.c = "[the string]";
    lttng_ust_tracepoint(my_provider, event_instance1, 23,
                         &app_struct);
    app_struct.b = argc * 5;
    app_struct.c = "[other string]";
    lttng_ust_tracepoint(my_provider, event_instance2, 17,
                         &app_struct);
    app_struct.b = 23;
    app_struct.c = "nothing";
    lttng_ust_tracepoint(my_provider, event_instance3, -52,
                         &app_struct);
    return EXIT_SUCCESS;
}

VARIABLES D'ENVIRONNEMENT

LTTNG_HOME

Répertoire personnel alternatif de l'utilisateur. Cette variable est utile lorsque l'utilisateur exécutant l'application instrumentée a un répertoire personnel non inscriptible. Ce chemin est l'endroit où se trouvent les sockets Unix pour la communication avec le démon de session par utilisateur.

LTTNG_UST_ABORT_ON_CRITICAL

Si défini, arrête l'application instrumentée en cas de message d'erreur critique.

LTTNG_UST_ALLOW_BLOCKING

Si défini, permet à l'application de retenter le traçage d'événements lorsqu'il n'y a plus d'espace pour l'enregistrement de l'événement dans le sous-buffer, bloquant ainsi effectivement l'application jusqu'à ce que de l'espace soit disponible ou que le délai d'attente configuré soit atteint.

Pour permettre à une application de se bloquer pendant le traçage, vous devez également spécifier un délai d'attente de blocage lorsque vous créez un canal avec l'option --blocking-timeout de la commande lttng-enable-channel(1).

Cette option peut être utile dans les charges de travail générant un très grand débit de données de trace, où le blocage de l'application est un compromis acceptable pour éviter de rejeter les enregistrements d'événements.


Attention
La définition de cette variable d'environnement peut affecter de manière significative les timings de l'application.

LTTNG_UST_APP_PATH

Chemin du répertoire où le démon de session LTTng est censé placer les fichiers suivants pour recevoir les requêtes de connexion des applications instrumentées :
•Le socket Unix d'enregistrement de l'application.
•Les fichiers de mémoire partagée "wait" pour réveiller les applications instrumentées qui attendent le démarrage d'un démon de session.
•Le fichier du port de l'agent.

Ce fichier contient le port TCP auquel les agents doivent se connecter pour activer le traçage LTTng.

Ce répertoire doit exister au démarrage de l'application pour que le traçage LTTng soit activé.

Lorsque LTTNG_UST_APP_PATH est défini, liblttng-ust :

•Ne considère que ce chemin pour se connecter à un démon de session.
•Ne se connectera pas aux démons de session root et/ou utilisateur comme d'habitude.

Voir la variable d'environnement correspondante LTTNG_UST_CTL_PATH de lttng-sessiond(8).

LTTNG_UST_CLOCK_PLUGIN

Chemin vers l'objet partagé qui agit comme le plugin de remplacement d'horloge. Un exemple d'un tel plugin peut être trouvé dans la documentation de LTTng-UST sous examples/clock-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/clock-override.

LTTNG_UST_DEBUG

Si défini, active la sortie de débogage et les messages d'erreur de liblttng-ust.

LTTNG_UST_GETCPU_PLUGIN

Chemin vers l'objet partagé qui sert de plugin de remplacement getcpu() . Un exemple d'un tel plugin se trouve dans la documentation de LTTng-UST sous examples/getcpu-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/getcpu-override.

LTTNG_UST_MAP_POPULATE_POLICY

Si défini, remplace la politique utilisée pour remplir les pages de mémoire partagée au sein de l'application.

Les valeurs possibles sont :

none (par défaut)

Ne pré-remplit aucune page : provoque des défauts mineurs lors du premier accès pendant la traçabilité.

cpu_possible

Pré-remplit les pages pour tous les processeurs possibles du système, comme indiqué dans /sys/devices/system/cpu/possible.

LTTNG_UST_REGISTER_TIMEOUT

Temps d'attente pour la commande registration done du démon de session avant de procéder à l'exécution du programme principal (millisecondes).

La valeur 0 signifie ne pas attendre. La valeur -1 signifie attendre indéfiniment. Définir cette variable d'environnement à 0 est recommandé pour les applications ayant des contraintes de temps sur le temps de démarrage du processus.

Par défaut : 3000.

LTTNG_UST_WITHOUT_BADDR_STATEDUMP

Si défini, empêche liblttng-ust d'effectuer un instantané d'état de l'adresse de base (voir la section Instantané d'état LTTng-UST ci-dessus).

LTTNG_UST_WITHOUT_PROCNAME_STATEDUMP

Si défini, empêche liblttng-ust d'effectuer un instantané d'état du procname (voir la section d'instantané d'état LTTng-UST ci-dessus).
