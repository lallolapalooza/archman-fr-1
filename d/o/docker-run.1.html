DESCRIPTIO

N

Exécute un processus dans un nouveau conteneur. docker run démarre un processus avec son propre système de fichiers, sa propre mise en réseau et son propre arbre de processus isolé. L'IMAGE qui démarre le processus peut définir des valeurs par défaut relatives au processus qui sera exécuté dans le conteneur, au réseau à exposer, et plus encore, mais docker run donne le contrôle final à l'opérateur ou à l'administrateur qui démarre le conteneur à partir de l'image. Pour cette raison docker run a plus d'options que n'importe quelle autre commande

Docker.

Si l'IMAGE n'est pas déjà chargée, alors docker run va récupérer l'IMAGE et toutes les dépendances de l'image depuis le dépôt de la même manière que l'exécution de docker pull IMAGE, avant de démarrer le con

teneur à part
ir de cette image.

OPTION

-a, --attach=[]
Se connecte à STDIN, STDOUT ou

STDERR.

En mode premier plan (par défaut quand -d n'est pas spécifié), docker run peut démarrer le processus dans le conteneur et attacher la console à l'entrée standard, la sortie standard et l'erreur standard du processus. Il peut même se faire passer pour un TTY (c'est ce que la plupart des exécutables en ligne de commande attendent) et transmettre les signaux. L'option -a peut être définie pour chacun de stdin, stdout et

stderr.

L'option --add-host peut être définie plusieurs

fois.

-c, --cpu-shares=0
Parts CPU (poids

relatif)

Par défaut, tous les conteneurs reçoivent la même proportion de cycles CPU. Cette proportion peut être modifiée en changeant le poids de part CPU du conteneur par rapport au poids de tous les autres conteneurs en cours

d'exécution.

Pour modifier la proportion par rapport à la valeur par défaut de 1024, utilisez les drapeaux -c ou --cpu-shares pour définir le poids à 2 ou

supérieur.

La proportion ne s'appliquera que lorsque des processus gourmands en CPU sont en cours d'exécution. Lorsque les tâches d'un conteneur sont inactives, d'autres conteneurs peuvent utiliser le temps CPU restant. Le montant réel du temps CPU variera en fonction du nombre de conteneurs en cours d'exécution sur le

système.

Par exemple, considérez trois conteneurs, l'un a une part CPU de 1024 et les deux autres ont un paramètre de part CPU de 512. Lorsque les processus des trois conteneurs tentent d'utiliser 100 % du CPU, le premier conteneur recevrait 50 % du temps CPU total. Si vous ajoutez un quatrième conteneur avec une part CPU de 1024, le premier conteneur ne reçoit que 33 % du CPU. Les conteneurs restants reçoivent 16,5 %, 16,5 % et 33 % du

CPU.

Sur un système multi-cœur, les parts de temps CPU sont réparties sur tous les cœurs CPU. Même si un conteneur est limité à moins de 100 % du temps CPU, il peut utiliser 100 % de chaque cœur CPU

individuel.

Par exemple, considérez un système avec plus de trois cœurs. Si vous démarrez un conteneur {C0} avec -c=512 exécutant un processus, et un autre conteneur {C1} avec -c=1024 exécutant deux processus, cela peut entraîner la répartition suivante des parts CPU

: 
PID    conteneur	CPU	Part CPU
100    {C0}		0	100 % de CPU0
101    {C1}		1	100 % de CPU1
102    {C1}		2	100 % de
CPU2

Cette option vous permet de remplacer le point d'entrée par défaut de l'image qui est défini dans le Dockerfile. Le ENTRYPOINT d'une image est similaire à une COMMAND car il spécifie quel exécutable lancer lorsque le conteneur démarre, mais il est (volontairement) plus difficile à remplacer. Le ENTRYPOINT donne au conteneur sa nature ou son comportement par défaut, de sorte que lorsque vous définissez un ENTRYPOINT, vous pouvez exécuter le conteneur comme s'il s'agissait de ce binaire, avec les options par défaut, et vous pouvez passer plus d'options via la COMMAND. Mais, parfois, un opérateur peut vouloir exécuter autre chose à l'intérieur du conteneur, vous pouvez donc remplacer le ENTRYPOINT par défaut à l'exécution en utilisant un --entrypoint et une chaîne pour spécifier le nouveau

--mount type=TYPE,OPTION-SPECIFIQUE-TYPE[,...]
Attacher un montage de système de fichiers au conteneur

Les TYPES de montage actuellement pris en charge sont bind, volume et tmpfs.

Par exemple :

type=bind,source=/path/on/host,destination=/path/in/container

type=volume,source=my-volume,destination=/path/in/container,volume-label="color=red",volume-label="shape=round"

type=tmpfs,tmpfs-size=512M,destination=/path/in/container

Options communes :

  • src, source : spécification de la source du montage pour bind et volume. Obligatoire pour bind.
  • dst, destination, target : spécification de la destination du montage.
  • ro, readonly : true ou false (par défaut).

Note : la définition de readonly pour un montage bind peut ne pas rendre ses sous-montages en lecture seule en fonction de la version du noyau. Voir aussi bind-recursive.

Options spécifiques à bind :

  • bind-propagation : shared, slave, private, rshared, rslave ou rprivate (par défaut). Voir aussi mount(2).
  • consistency : consistent (par défaut), cached ou delegated. Actuellement, uniquement effectif pour Docker for Mac.
  • bind-recursive : enabled (par défaut), disabled, writable ou readonly :
    Si défini sur enabled, les sous-montages sont montés en bind récursivement et on tente de les rendre récursivement en lecture seule.
    Si défini sur disabled, les sous-montages ne sont pas montés en bind récursivement.
    Si défini sur writable, les sous-montages sont montés en bind récursivement mais ne sont pas rendus récursivement en lecture seule.
    Si défini sur readonly, les sous-montages sont montés en bind récursivement et forcés d'être rendus récursivement en lecture seule.

Options spécifiques à volume :

  • volume-driver : Nom du plugin de pilote de volume.
  • volume-label : Métadonnées personnalisées.
  • volume-nocopy : true (par défaut) ou false. Si défini sur false, le moteur copie les fichiers et répertoires existants sous le chemin de montage dans le volume, permettant à l'hôte d'y accéder.
  • volume-opt : spécifique à un pilote de volume donné.

Options spécifiques à tmpfs :

  • tmpfs-size : Taille du montage tmpfs en octets. Illimité par défaut sous Linux.
  • tmpfs-mode : Mode de fichier du tmpfs en octal. (par exemple, 700 ou 0700.) Par défaut à 1777 sous Linux.

Attribuer un nom au conteneur

L'opérateur peut identifier un conteneur de trois manières :

Type d'identifiant Valeur d'exemple
Identifiant long UUID "f78375b1c487e03c9438c729345e54db9d20cfa2ac1fc3494b6eb60872e74778"
Identifiant court UUID "f78375b1c487"

Les identifiants UUID proviennent du démon Docker, et si aucun nom n'est attribué au conteneur avec --name, le démon générera également un nom de chaîne aléatoire. Le nom est utile lors de la définition de liens (voir --link) (ou dans tout autre endroit où vous avez besoin d'identifier un conteneur). Cela fonctionne pour les conteneurs Docker en arrière-plan et en premier plan.

--network=type
Définir le mode réseau pour le conteneur. Les valeurs prises en charge sont :

Valeur Description
none Pas de réseau dans le conteneur.
bridge Connecter le conteneur au pont Docker par défaut via des interfaces veth.
host Utiliser la pile réseau de l'hôte à l'intérieur du conteneur.
container:nom|id Utiliser la pile réseau d'un autre conteneur, spécifié via son nom ou son id.
nom-réseau|id-réseau Connecter le conteneur à un réseau créé par l'utilisateur (en utilisant la commande docker network create)

La valeur par défaut est bridge.

Mapper les ports pour une utilisation

externe

Le port exposé d'une application peut être mappé vers un port hôte à l'aide de l'option -p. Par exemple, un port httpd 80 peut être mappé vers le port hôte 8080 en utilisant ce qui suit

: 
# docker run -p
8080:80 -d -i
-t fedora/httpd

Créer et monter un conteneur de volume de

données

De nombreuses applications nécessitent le partage de données persistantes entre plusieurs conteneurs. Docker vous permet de créer un conteneur de volume de données que d'autres conteneurs peuvent monter. Par exemple, créez un conteneur nommé qui contient les répertoires /var/volume1 et /tmp/volume2. L'image devra contenir ces répertoires, donc quelques instructions RUN mkdir pourraient être nécessaires pour votre image fedora-data

: 
# docker run --name=data -v /var/volume1 -v /tmp/volume2 -i -t fedora-data true
# docker run --volumes-from=data --name=fedora-container1 -i -t fedora
bash

Plusieurs paramètres --volumes-from rassembleront plusieurs volumes de données provenant de plusieurs conteneurs. Et il est possible de monter les volumes qui proviennent du conteneur DATAiner dans un autre conteneur via le conteneur intermédiaire fedora-container1, permettant d'abstraire la source de données réelle des utilisateurs de ces données:

# docker run --volumes-from=fedora-container1 --name=fedora-container2 -i -t fedora bash

Montage de volumes externes

Pour monter un répertoire hôte en tant que volume de conteneur, spécifiez le chemin absolu du répertoire et le chemin absolu du répertoire du conteneur séparés par un deux-points:

# docker run -v /var/db:/data1 -i -t fedora bash

Lors de l'utilisation de SELinux, sachez que l'hôte n'a aucune connaissance de la politique SELinux du conteneur. Par conséquent, dans l'exemple ci-dessus, si la politique SELinux est appliquée, le répertoire /var/db n'est pas inscriptible par le conteneur. Un message « Permission Denied » apparaîtra, ainsi qu'un message avc: dans le syslog de l'hôte.

Pour contourner ce problème, au moment de la rédaction de cette page de manuel, la commande suivante doit être exécutée afin que le type d'étiquette de politique SELinux approprié soit attaché au répertoire hôte:

# chcon -Rt svirt_sandbox_file_t /var/db

Maintenant, l'écriture dans le volume /data1 dans le conteneur sera autorisée et les modifications seront également reflétées sur l'hôte dans /var/db.

Utilisation d'un étiquetage de sécurité alternatif

Vous pouvez remplacer le schéma d'étiquetage par défaut pour chaque conteneur en spécifiant l'indicateur --security-opt . Par exemple, vous pouvez spécifier le niveau MCS/MLS, une exigence pour les systèmes MLS. La spécification du niveau dans la commande suivante vous permet de partager le même contenu entre les conteneurs.

# docker run --security-opt label=level:s0:c100,c200 -i -t fedora bash

Un exemple MLS pourrait être:

# docker run --security-opt label=level:TopSecret -i -t rhel7 bash

Pour désactiver l'étiquetage de sécurité pour ce conteneur au lieu de l'exécuter avec l'indicateur --permissive , utilisez la commande suivante:

# docker run --security-opt label=disable -i -t fedora bash

Si vous souhaitez une politique de sécurité plus stricte sur les processus à l'intérieur d'un conteneur, vous pouvez spécifier un type alternatif pour le conteneur. Vous pourriez exécuter un conteneur autorisé uniquement à écouter sur les ports Apache en exécutant la commande suivante:

# docker run --security-opt label=type:svirt_apache_t -i -t centos bash

Note:

Vous devriez écrire une politique définissant un type svirt_apache_t.

Définition du poids du périphérique

Si vous souhaitez définir le poids du périphérique /dev/sda à 200, vous pouvez spécifier le poids du périphérique avec l'indicateur --blkio-weight-device . Utilisez la commande suivante:

# docker run -it --blkio-weight-device "/dev/sda:200" ubuntu

Spécifier la technologie d'isolation pour le conteneur (--isolation)

Cette option est utile dans les situations où vous exécutez des conteneurs Docker sur Microsoft Windows. L'option --isolation <valeur> définit la technologie d'isolation d'un conteneur. Sous Linux, la seule prise en charge est l'option default qui utilise les espaces de noms Linux. Ces deux commandes sont équivalentes sous Linux:

$ docker run -d busybox top
$ docker run -d --isolation default busybox top

Sur Microsoft Windows, peut prendre l'une des valeurs suivantes:

  • default: Utilise la valeur spécifiée par --exec-opt du démon Docker. Si le démon ne spécifie pas de technologie d'isolation, Microsoft Windows utilise process comme valeur par défaut.
  • process: Isolation par espaces de noms uniquement.
  • hyperv: Isolation basée sur les partitions de l'hyperviseur Hyper-V.

En pratique, lors de l'exécution sur Microsoft Windows sans option de démon définie, ces deux commandes sont équivalentes:

$ docker run -d --isolation default busybox top
$ docker run -d --isolation process busybox top

Si vous avez défini l'option --exec-opt isolation=hyperv sur le démon Docker, l'une de ces commandes aboutit également à une isolation hyperv:

$ docker run -d --isolation default busybox top
$ docker run -d --isolation hyperv busybox top

Définition des paramètres noyau en espace de noms (Sysctls)

L'option --sysctl définit les paramètres noyau en espace de noms (sysctls) dans le conteneur. Par exemple, pour activer le transfert IP dans l'espace de noms réseau du conteneur, exécutez cette commande:

$ docker run --sysctl net.ipv4.ip_forward=1 someimage

Note:

Tous les sysctls ne sont pas en espace de noms. Docker ne prend pas en charge la modification des sysctls à l'intérieur d'un conteneur qui modifie également le système hôte. Au fur et à mesure que le noyau évolue, nous prévoyons que davantage de sysctls deviendront en espace de noms.

Voir la définition de l'option --sysctl ci-dessus pour la liste actuelle des sysctls pris en charge.
