DESCRIPTIO

N

Podman (Pod Manager) est un moteur de conteneurs complet qui est un outil simple sans démon. Podman fournit une ligne de commande comparable à celle de Docker, ce qui facilite la transition depuis d'autres moteurs de conteneurs et permet la gestion des pods, des conteneurs et des images. En résumé : alias docker=podman. La plupart des commandes Podman peuvent être exécutées en tant qu'utilisateur régulier, sans nécessiter de privilèges supplémentaires

.

Podman utilise Buildah(1) en interne pour créer des images de conteneurs. Les deux outils partagent le stockage des images (mais pas des conteneurs), chacun pouvant donc utiliser ou manipuler les images (mais pas les conteneurs) créées par

l'autre.

Les paramètres par défaut des drapeaux sont définis dans containers.conf. La plupart des paramètres pour les connexions distantes utilisent le containers.conf du serveur, sauf si documenté dans les pages

man.

--hooks-dir=chemi

n

Chaque fichier *.json dans le chemin configure un hook pour les conteneurs Podman. Pour plus de détails sur la syntaxe des fichiers JSON et la sémantique de l'injection de hooks, voir oci-hooks(5). Podman et libpod prennent actuellement en charge les schémas de hooks 1.0.0 et 0.1.0, bien que le schéma 0.1.0 soit

déprécié.

Cette option peut être définie plusieurs fois ; les chemins des options ultérieures ont une priorité plus élevée (oci-hooks(5) discute de la priorité des répertoires)

.

Pour les conditions d'annotation, libpod utilise toutes les annotations définies dans la configuration OCI

générée.

Pour les conditions de montage par liaison, seuls les montages explicitement demandés par l'appelant via --volume sont considérés. Les montages par liaison que libpod insère par défaut (par exemple /dev/shm) ne sont pas

considérés.

Si --hooks-dir n'est pas défini pour les appelants root, Podman et libpod utilisent actuellement par défaut /usr/share/containers/oci/hooks.d et /etc/containers/oci/hooks.d par ordre de priorité croissante. L'utilisation de ces valeurs par défaut est dépréciée. Migrez vers la définition explicite de --hooks-dir

.

Podman et libpod prennent actuellement en charge un état supplémentaire precreate qui est appelé avant l'opération create du runtime. Contrairement aux autres étapes, qui reçoivent l'état du conteneur sur leur entrée standard, les hooks precreate reçoivent la configuration runtime proposée sur leur entrée standard. Ils peuvent modifier cette configuration comme bon leur semble et écrire la forme modifiée sur leur sortie

standard.

AVERTISSEMENT : le hook precreate permet des modifications puissantes de se produire, comme l'ajout de montages supplémentaires à la configuration runtime. Ce pouvoir rend aussi facile de casser des choses. Avant de signaler des erreurs de libpod, essayez de lancer un conteneur avec les hooks precreate désactivés pour voir

si le problème est
dû à l'un des hooks.

Codes de

sortie

Le code de sortie de podman donne des informations sur la raison pour laquelle le conteneur n'a pas pu s'exécuter ou pourquoi il s'est terminé. Lorsque les commandes podman se terminent avec un code non nul, les codes de sortie suivent la norme chroot, voir ci-dessous

:

125 L'erreur provient de podman lui-même

$ podman run --foo busybox; echo $?
Error: unknown flag: --foo
125

126 Exécution d'une commande de conteneur et la commande ne peut pas être

invoquée 
$ podman run busybox /etc; echo $?
Error: container_linux.go:346: starting container process caused "exec: \"/etc\": permission denied": OCI runtime error
126

127 Exécution d'une commande de conteneur et la commande ne peut pas être

trouvée 
$ podman run busybox foo; echo $?
Error: container_linux.go:346: starting container process caused "exec: \"foo\": executable file not found in $PATH": OCI runtime error
127

Sinon, pour le code de sortie, podman renvoie le code de sortie de la commande du

conteneur 
$ podman run busybox /bin/sh -c 'exit 3'; echo $?
3

Mode sans racine

(Rootless)

Podman peut également être utilisé en tant qu'utilisateur non root. Lorsque podman s'exécute en mode sans racine, un espace de noms d'utilisateure est automatiquement créé pour l'utilisateur, défini dans /etc/subuid et /etc/subgid.

Les conteneurs créés par un utilisateur non-root ne sont pas visibles par les autres utilisateurs et ne sont pas vus ou gérés par Podman exécuté en tant que root.

Il est nécessaire d'avoir plusieurs UID/GID définis pour un utilisateur. Assurez-vous que l'utilisateur est présent dans les fichiers /etc/subuid et /etc/subgid.

Exécutez les commandes suivantes pour ajouter les plages aux fichiers

$ sudo usermod --add-subuids 10000-75535 NOMUTILISATEUR
$ sudo usermod --add-subgids 10000-75535 NOMUTILISATEUR

Ou ajoutez simplement le contenu manuellement.

$ echo NOMUTILISATEUR:10000:65536 >> /etc/subuid
$ echo NOMUTILISATEUR:10000:65536 >> /etc/subgid

Voir les pages de manuel subuid(5) et subgid(5) pour plus d'informations.

Note : les espaces blancs dans n'importe quelle ligne de /etc/subuid ou /etc/subgid, y compris les blancs de fin, peuvent entraîner des échecs de non-inscription.

Les images sont téléchargées sous XDG_DATA_HOME lorsqu'il est spécifié, sinon dans le répertoire personnel de l'utilisateur sous .local/share/containers/storage.

Actuellement, slirp4netns ou pasta doit être installé pour créer un périphérique réseau, sinon les conteneurs sans root doivent s'exécuter dans l'espace de noms réseau de l'hôte.

Dans certains environnements comme le HPC (High Performance Computing), les utilisateurs ne peuvent pas tirer parti des UID et GID supplémentaires des systèmes /etc/subuid et /etc/subgid. Cependant, dans cet environnement, Podman sans root peut fonctionner avec un seul UID. Pour que cela fonctionne, définissez l'option ignore_chown_errors dans le fichier containers-storage.conf(5). Cette option indique à Podman, lors du téléchargement d'une image, d'ignorer les erreurs de chown lors de la tentative de modification d'un fichier dans une image de conteneur pour qu'il corresponde à l'UID non-root de l'image. Cela signifie que tous les fichiers sont sauvegardés avec l'UID de l'utilisateur. Notez que cela peut causer des problèmes lors de l'exécution du conteneur.

NOTE : Systèmes de fichiers non pris en charge en mode sans root

Le système de fichiers Overlay (OverlayFS) n'est pas pris en charge avec les noyaux antérieurs à 5.12.9 en mode sans root. Le paquet fuse-overlayfs est un outil qui fournit la fonctionnalité d'OverlayFS dans l'espace de noms utilisateur, ce qui permet de monter des systèmes de fichiers dans des environnements sans root. Il est recommandé d'installer le paquet fuse-overlayfs. En mode sans root, Podman utilise automatiquement le programme fuse-overlayfs comme mount_program s'il est installé, tant que le fichier $HOME/.config/containers/storage.conf n'a pas été créé précédemment. Si storage.conf existe dans le répertoire personnel, ajoutez mount_program = "/usr/bin/fuse-overlayfs" sous [storage.options.overlay] pour activer cette fonctionnalité.

Le système de fichiers réseau (NFS) et d'autres systèmes de fichiers distribués (par exemple : Lustre, Spectrum Scale, le General Parallel File System (GPFS)) ne sont pas pris en charge lors de l'exécution en mode sans root, car ces systèmes de fichiers ne comprennent pas l'espace de noms utilisateur. Cependant, Podman sans root peut utiliser un répertoire personnel NFS en modifiant $HOME/.config/containers/storage.conf pour que l'option graphroot pointe vers un répertoire stocké sur un stockage local (non NFS).
