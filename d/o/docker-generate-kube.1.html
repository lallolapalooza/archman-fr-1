Les types de volume hostPath sont nommés selon le chemin sur la machine hôte, en remplaçant les barres obliques par des tirets, sans les barres obliques initiales et finales. Le cas particulier de la racine du système de fichiers, / [[50]], se traduit par le nom root [[52]]. De plus, le nom est suffixé par -host pour éviter les conflits de noms avec les volumes persistentVolumeClaim [[56]]. Chaque type de

volume

persistentVolumeClaim utilise le nom de son volume nommé associé suffixé par -pvc [[60]]. Notez que si un conteneur d'initialisation est créé avec le type once et que le pod a été démarré, il n'apparaît pas dans le kube YAML généré car les conteneurs d'initialisation de type once sont supprimés après leur exécution. Si le pod a seulement été créé et non démarré, il est présent dans le kube YAML généré. Les conteneurs d'initialisation créés avec le type always sont toujours générés dans le kube YAML car ils ne sont jamais supprimés, même après s'être

exécutés jusqu'à la fin.

Note : Lors de l'utilisation de volumes et de la génération d'un YAML Kubernetes pour un conteneur podman non privilégié et sans racine sur un système avec SELinux activé [[71]], l'une des options suivantes doit être appliquée : * Ajouter l'option "privileged: true" à la spécification du

pod

* Ajouter type: spc_t sous securityContext seLinuxOptions
dans la spécification du pod * Relier le volume via la commande en ligne de commande chcon -t container_file_t -R <répertoire>
Une fois cela fait, les permissions correctes sont en place pour accéder au volume lorsque le pod/conteneur est créé dans un cluster Kubernetes. Notez que le fichier YAML Kubernetes généré peut être utilisé pour relancer le déploiement via podman-play-kube(1).
