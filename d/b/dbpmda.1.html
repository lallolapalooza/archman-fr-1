NOM

dbpmda - débogueur pour les PMDA de Performance Co-Pilot

SYNOPSIS

dbpmda [-D debug] [-efiv?] [-n pmnsfile] [-q timeout] [-U username]

DESCRIPTION

dbpmda est une interface interactive pour les interactions entre un Agent de Domaine de Métriques de Performance (PMDA(3)) et le Collecteur de Métriques de Performance (pmcd(1)). Cela permet d'attacher, d'initialiser et d'exercer des PMDA pour tester leur bon fonctionnement.

dbpmda invite l'utilisateur à entrer des commandes de manière interactive, dont beaucoup émulent les Unités de Données de Protocole (PDU) qui peuvent être envoyées par un pmcd(1) . Après avoir lancé dbpmda, saisissez la commande help pour obtenir une liste des commandes disponibles. La section d'exemple ci-dessous illustre une session utilisant dbpmda pour tester un PMDA.

Pour simplifier les tests répétitifs d'un PMDA, le fichier .dbpmdarc dans le répertoire de travail courant peut contenir une liste de commandes qui seront exécutées par dbpmda au démarrage, avant que l'utilisateur ne soit invité à entrer d'autres commandes de manière interactive. Lors du traitement du fichier .dbpmdarc , le mode interactif et l'écho des commandes sont activés puis réinitialisés à la fin du fichier .dbpmdarc (voir les options de ligne de commande -i et -e ci-dessous).

L'option de ligne de commande -f empêche le traitement au démarrage d'un fichier .dbpmdarc (s'il existe).

Si le système prend en charge readline(3) , celui-ci sera utilisé pour lire les commandes lorsque l'entrée provient d'un périphérique tty, permettant ainsi l'historique et l'édition de la ligne de commande.

Comme il n'y a pas de contraintes de délai d'expiration pour un PMDA lors de l'utilisation de dbpmda (par rapport à pmcd(1)), un autre débogueur comme gdb(1) peut être utilisé sur le processus du PMDA une fois qu'il a été attaché à dbpmda.

OPTIONS

Les options de ligne de commande disponibles sont :

-e, --echo-input
Faire l'écho de l'entrée vers stdout. C'est utile lorsque l'entrée est redirigée depuis un fichier.
-f, --norc
Ne pas traiter le fichier .dbpmdarc .
-i, --interactive
Émuler un comportement interactif et demander de nouvelles commandes, même si l'entrée standard n'est pas un périphérique tty.
-n pmnsfile, --namespace=pmnsfile
Charger un Espace de Noms de Métriques de Performance (PMNS(5)) alternatif depuis le fichier pmnsfile.
-q timeout, --creds-timeout=timeout
Le protocole d'échange de version pmcd vers agent (nouveau dans PCP 2.0 - introduit pour assurer la compatibilité ascendante) utilise ce délai d'expiration pour spécifier combien de temps dbpmda doit attendre avant de supposer qu'aucune réponse de version ne viendra de l'agent. Si ce délai est atteint, l'agent est supposé être un agent qui ne comprend pas le protocole PCP 2.0. L'intervalle de délai par défaut est de trois secondes, mais l'option -q permet de spécifier un intervalle de délai alternatif (qui doit être supérieur à zéro). L'unité de temps est la seconde.
-U username, --username=username
Compte utilisateur sous lequel exécuter dbpmda.
-v, --valgrind
Utile lors de l'exécution de dbpmda sous le contrôle de valgrind(1) pour trier les problèmes dans un PMDA DSO. Si l'option -v est utilisée, alors dbpmda n'appellera pas dlclose(3) avant de se terminer, ce qui permet à valgrind(1)] d'accéder à la table de symboles du PMDA DSO lors du rapport, ce qui facilite grandement le débogage.
-?, --help
Afficher le message d'utilisation et quitter.

EXEMPLES

Voici une session dbpmda utilisant le PMDA simple . Un fichier .dbpmdarc est utilisé pour définir l'option de débogage, ouvrir le PMDA et afficher l'état actuel du débogueur :

$ cat .dbpmdarc
debug libpmda
open dso pmda_simple.so simple_init 253
status

Lorsque dbpmda est exécuté, les commandes du fichier .dbpmdarc sont exécutées en premier :

$ dbpmda

[Fri Sep 19 10:19:55] dbpmda(11651) Info: num indom   = 1
[Fri Sep 19 10:19:55] dbpmda(11651) Info: direct map  = 1

Pour examiner les métadonnées des métriques et des domaines d'instances, les commandes desc et instance peuvent être utilisées. Les métriques peuvent être identifiées soit par leur nom, soit en utilisant la notation numérique « pointillée » pour spécifier les champs domain, cluster et item d'un PMID. Les domaines d'instances doivent être identifiés en utilisant une notation numérique « pointillée » pour spécifier les champs domain et serial. La syntaxe de la plupart des commandes sera affichée si la commande est donnée sans aucun argument :

dbpmda> desc 253.0.0
PMID: 253.0.0
    Data Type: 32-bit unsigned int  InDom: PM_INDOM_NULL 0xffffffff
    Semantics: instant  Units: none
dbpmda> instance
instance indom# [ number | name | "name" ]
dbpmda> instance 253.0
pmInDom: 253.0
[  0] inst: 0 name: "red"
[  1] inst: 1 name: "green"
[  2] inst: 2 name: "blue"

Pour tester la composante la plus importante d'un PMDA, le fetch, il est souvent utile de déterminer le temps que met le PMDA à répondre. Le timer peut être activé avant de donner un fetch:

dbpmda> timer on
dbpmda> fetch simple.numfetch 253.0.1
PMID(s): 253.0.0 253.0.1
pmResult dump from 0x100078e0 timestamp: 0.000000 11:00:00.000 numpmid: 2
  253.0.0 (simple.numfetch): numval: 1 valfmt: 0 vlist[]:
   value 1 1.4012985e-45 0x1
  253.0.1 (simple.color): numval: 3 valfmt: 0 vlist[]:
    inst [0 or ???] value 1 1 1.4012985e-45 0x1
    inst [1 or ???] value 101 1.4153114e-43 0x65
    inst [2 or ???] value 201 2.8166099e-43 0xc9
Timer: 0.003921 seconds
dbpmda> timer off

Les traductions entières, en virgule flottante et en hexadécimal des valeurs dans la structure pmResult sont affichées si getdesc est défini à off (par défaut). Si getdesc est défini à on , cela récupère également les métadonnées de la métrique (ou pmDesc) et cela résulterait en l'affichage de valeurs uniquement entières dans le fetch ci-dessus car les métadonnées de la métrique décrivent le type de la métrique comme étant des entiers non signés sur 32 bits.

De même, le paramètre getiname contrôle la recherche des noms d'instances externes pour les métriques avec un domaine d'instances associé. Quand il est off (par défaut), la sortie est comme ci-dessus. Quand il est on , les « noms » d'instances ??? sont traduits en leurs noms d'instances externes par le PMDA et rapportés comme ci-dessous :

dbpmda> getiname on
dbpmda> fetch simple.color
PMID(s): 253.0.1
pmResult dump from 0x100078e0 timestamp: 0.000000 11:00:00.000 numpmid: 1
  253.0.1 (simple.color): numval: 3 valfmt: 0 vlist[]:
    inst [0 or "red"] value 4
    inst [1 or "green"] value 104
    inst [2 or "blue"] value 204

Parce que les métadonnées de la métrique sont nécessaires pour faire la recherche du nom d'instance, définir getiname à on définit implicitement getdesc à on.

Notez que si getdesc ou getiname sont définis à on , alors chaque fetch implique des appels supplémentaires sur le PMDA. Pour un PMDA en développement, cela peut ne pas être une bonne idée, c'est pourquoi les deux paramètres sont définis par défaut à off.

Le PMDA simple supporte également l'opération store qui peut être testée avec des commandes fetch subséquentes :

dbpmda> store simple.numfetch "42"
PMID: 253.0.0
Getting description...
Getting Result Structure

NAME


dbpmda - Performance Metrics Data Accessor (PMDA) debug utility






SYNOPSIS


dbpmda [-D debug_options] [-l logfile] [-h]






DESCRIPTION


The dbpmda utility is a tool for debugging Performance Co-Pilot (PCP)
    Performance Metrics Data Accessors (PMDAs). It allows direct interaction with a
    PMDA, bypassing the Performance Co-Pilot Data Collector Daemon (PMCD). This
    can be useful for testing PMDA functionality, debugging PMDA code, and
    understanding PMDA behavior.


When dbpmda is started, it can optionally launch a PMDA (or
    attach to an existing one) and then enter an interactive command-driven mode.


The following commands are supported:



  
open pmda_path [pmda_args] | pipe pmda_path [pmda_args]

  
Launches the specified PMDA. The pipe keyword indicates that the PMDA
      should be launched as a child process, communicating via pipes. Without
      pipe, dbpmda may attempt to use fork(2) and exec(2)
      to launch the PMDA. pmda_path is the path to the PMDA executable,
      and pmda_args are any command-line arguments for the PMDA.

  
attach pmda_path [pmda_args]

  
Attaches to a running PMDA. This is typically used when the PMDA is already
      running and listening for connections (e.g., via TCP/IP). Requires the PMDA
      to support the appropriate connection mechanism.

  
dump

  
Dumps the current state of the PMDA, including internal data structures and
      configuration.

  
fetch pmid[,pmid...]

  
Fetches performance metric values for the specified Performance Metric
      Identifiers (PMIDs).

  
store pmid value

  
Stores a new value for a performance metric. The value must be a
      string enclosed in single or double quotes.

  
profile indom [ all | none | add instance | delete instance ]

  
Manages the instance profile for a given instance domain (indom). This
      allows specifying which instances are included or excluded for metric
      retrieval.

  
watch filename

  
Opens an xterm window to tail the specified log file.

  
wait seconds

  
Pauses execution for the specified number of seconds (equivalent to
      sleep(1)).

  
children metric_name

  
Lists the direct descendants of a node within a dynamic PMNS subtree.

  
traverse metric_name

  
Lists all leaf nodes in the PMNS subtree below the specified node.

  
pmid metric_name

  
Translates a metric name to its corresponding PMID.

  
name pmid

  
Translates a PMID to its corresponding metric name.

  
attr attribute_name value

  
Passes connection attributes to the PMDA, mimicking PMCD behavior for
      authenticated connections. This is useful for testing PMDA integration
      with client authentication mechanisms (requires PMDA_INTERFACE_6 or
      later).

  
debug debug_options

  
Enables or disables specific debugging output from PCP libraries linked
      with the PMDA. Options can be prefixed with '-' to disable. 'all' enables
      all options, 'none' disables all options.

  
help [command]

  
Displays help information for available commands or a specific command.

  
quit

  
Exits the dbpmda utility.








OPTIONS



  
-D debug_options

  
Enable debugging output. debug_options is a comma-separated list
      of debugging keywords. Use `pmdbg -l` to see available options.

  
-l logfile

  
Specify a log file for debugging output.

  
-h

  
Display a help message and exit.

The watch command (usage: watch filename )
    opens an xterm window which tails the specified log file. This window must
    be closed by the user when no longer required.


The wait command is equivalent to sleep(1) and takes
    a single integer argument (wait time in seconds).


The introduction of dynamic subtrees in the PMNS and
    PMDA_INTERFACE_4 in libpcp_pmda has led to additional commands being
    supported in dbpmda to exercise the associated dynamic PMNS services.
    The examples below are based on the sample PMDA.


$ dbpmda
dbpmda> open pipe /var/lib/pcp/pmdas/sample/pmdasample -d 29
Start pmdasample PMDA: /var/lib/pcp/pmdas/sample/pmdasample -d 29
dbpmda> children sample.secret
Metric: sample.secret
   non-leaf foo
       leaf bar
dbpmda> traverse sample.secret.foo
Metric: sample.secret.foo
   sample.secret.foo.bar.max.redirect
   sample.secret.foo.one
   sample.secret.foo.two
   sample.secret.foo.bar.three
   sample.secret.foo.bar.four
   sample.secret.foo.bar.grunt.five
   sample.secret.foo.bar.grunt.snort.six
   sample.secret.foo.bar.grunt.snort.huff.puff.seven
dbpmda> pmid sample.secret.foo.bar.four
Metric: sample.secret.foo.bar.four
   29.0.1004
dbpmda> name 29.0.1006
PMID: 29.0.1006
   sample.secret.foo.bar.grunt.snort.six



The children command returns the next name component for
    all the direct descendants of a node within a dynamic subtree of the PMNS.
    The related traverse command returns the full metric names for all
    leaf nodes in the PMNS below the specified non-leaf node in a dynamic
    subtree of the PMNS.


The name and pmid commands exercise the translation
    of metric names to PMIDs (and vice versa) for metrics within a dynamic
    subtree of the PMNS.


If the commands children, traverse, pmid or
    name are used with a PMDA that is not using PMDA_INTERFACE_4
    or with performance metric names that are not part of a dynamic subtree of
    the PMNS, then the PMDA would be expected to return errors (PM_ERR_NAME or
    PM_ERR_PMID) to reflect the fact that the operation is in error (outside a
    dynamic subtree of the PMNS it is pmcd(1) and not the PMDA that is
    responsible for implementing these functions).


Client authentication mechanisms have been incorporated into the
    PMCS, providing per-user (and per-connection) information that is available
    to PMDAs. A PMDA using PMDA_INTERFACE_6 or later in libpcp_pmda is
    able to make use of the "attribute" method to gain visibility into
    these authenticated connections, with access to information including user
    and group identifiers, user name, and so on. The need to exercise and debug
    this interface has led to a new dbpmda command. The following example
    is based on the sample PMDA.


$ dbpmda
dbpmda> open pipe pmdasample -D AUTH -l logfile
Start pmdasample PMDA: pmdasample -D AUTH -l logfile
dbpmda> attr "username" "tanya"
Attribute: username=tanya
Success
dbpmda> attr 11 "0"
Attribute: userid=0
Success
dbpmda>


The attr command passes connection attributes
    (PCP_ATTR_XXXX keys) and their values into a PMDA in much the same way that
    PMCD would for a client connection. dbpmda always passes a client
    context identifier of zero, and while no validity checking on values is
    performed only recognised attributes can be set.


In the example above the AUTH debugging option is set for
    the PMDA, which uses this in its attribute callback and records each
    attribute and value pair sent to it in its logfile.


Note that authentication checks have already been performed by
    PMCD by the time a PMDA is presented with these attributes, so no further
    verification is necessary by the PMDA.


The debug command takes one or more debug options separated
    by whitespace or a comma. This can be used to selectively enable debugging
    output from various modules of the PCP libraries that the PMDA will be
    linked with. If the option is prefixed by a minus ``-'' the corresponding
    debugging option is disabled. The options are the same debug names as
    reported by the -l option to pmdbg(1) and/or their deprecated
    equivalent numeric values as reported by the -ol options to
    pmdbg(1). The special ``option'' none turns all debugging off
    and the special ``option'' all enables all the debugging options.






CAVEATS


A value cannot be stored into metrics of type
    PM_TYPE_AGGREGATE or PM_TYPE_EVENT.


dbpmda uses fork(2) and exec(2) to attach to
    daemon PMDAs. dbpmda makes no attempt to detect the termination of
    the daemon PMDA process, so it is possible for a PMDA to exit unexpectedly
    without any notification. However, any further communication attempts with
    the PMDA will result in errors which will indicate that the PMDA is no
    longer responding.






FILES



  
./.dbpmdarc

  
List of commands to do on startup.








PCP   ENVIRONMENT


Environment variables with the prefix PCP_ are used to
    parameterize the file and directory names used by PCP. On each installation,
    the file /etc/pcp.conf contains the local values for these variables.
    The $PCP_CONF variable may be used to specify an alternative
    configuration file, as described in pcp.conf(5).


For environment variables affecting PCP tools, see
    pmGetOptions(3).






DEBUGGING   OPTIONS


The -D or --debug option enables the output of
    additional diagnostics on stderr to help triage problems, although
    the information is sometimes cryptic and primarily intended to provide
    guidance for developers rather end-users. debug is a comma separated
    list of debugging options; use pmdbg(1) with the -l option to
    obtain a list of the available debugging options and their meaning.
