DESCRIPTIO

N

dbus-daemon est le démon de bus de messages D-Bus. Voir https://www.freedesktop.org/wiki/Software/dbus/ pour plus d'informations sur la vue d'ensemble. D-Bus est d'abord une bibliothèque qui fournit une communication un-à-un entre n'importe deux applications ; dbus-daemon est une application qui utilise cette bibliothèque pour implémenter un démon de bus de messages. Plusieurs programmes se connectent au démon de bus de messages et peuvent échanger des messages entre

eux.

Il existe deux instances standard de bus de messages : le bus de messages système (installé sur de nombreux systèmes comme le service init « messagebus ») et le bus de messages par session de connexion utilisateur (démarré à chaque fois qu'un utilisateur se connecte). dbus-daemon est utilisé pour ces deux instances, mais avec un fichier de configuration

différent.

L'option --session est équivalente à « --config-file=/usr/share/dbus-1/session.conf » et l'option --system est équivalente à « --config-file=/usr/share/dbus-1/system.conf ». En créant des fichiers de configuration supplémentaires et en utilisant l'option --config-file, des démons de bus de messages supplémentaires à usage spécifique pourraient être

créés.

Le démon système est normalement lancé par un script d'init, traditionnellement appelé simplement « messagebus »

.

Le démon système est largement utilisé pour diffuser des événements système, tels que les modifications de la file d'attente d'impression, ou l'ajout/suppression de

périphériques.

Le démon par session est utilisé pour diverses communications inter-processus entre applications de bureau (cependant, il n'est lié ni à X ni à l'interface graphique d'aucune manière)

.

SIGHUP fera recharger PARTIELLEMENT son fichier de configuration au démon D-Bus et videra ses caches d'informations utilisate

ur/groupe. Certaines modifications de configuration nécessiteraient de déconnecter toutes les applications du bus ; elles
ne prendront donc effet que si vous redémarrez le démon. Les modifications de politique devraient prendre effet avec SIGHUP.

FICHIER DE

CONFIGURATION

Un démon de bus de messages a un fichier de configuration qui l'adapte à une application particulière. Par exemple, un fichier de configuration pourrait configurer le bus de messages comme un bus de messages système, tandis qu'un autre pourrait le configurer comme un bus par session de connexion

utilisateur.

Le fichier de configuration établit également les limites de ressources, les paramètres de sécurité, et ainsi de

suite.

Le fichier de configuration ne fait partie d'aucune spécification d'interopérabilité et sa rétrocompatibilité n'est pas garantie ; ce document est de la documentation, pas une

spécification.

Les configurations standard du bus de messages système et par session sont configurées dans les fichiers « /usr/share/dbus-1/system.conf » et « /usr/share/dbus-1/session.conf ». Ces fichiers incluent normalement (<include>) un system-local.conf ou session-local.conf dans /etc/dbus-1 ; vous pouvez mettre des surcharges locales dans ces fichiers pour éviter de modifier les fichiers de configuration

principaux.

Le bus système standard lit normalement des fichiers XML supplémentaires depuis /usr/share/dbus-1/system.d. Les paquets tiers devraient installer les politiques par défaut nécessaires au bon fonctionnement dans ce répertoire, ce qui est pris en charge depuis dbus 1.10 (publié en 2015)

.

Le bus système standard lit également normalement des fichiers XML depuis /etc/dbus-1/system.d, qui devraient être utilisés par les administrateurs système s'ils souhaitent remplacer les politiques par

défaut.

Les paquets tiers installaient historiquement des fichiers XML dans /etc/dbus-1/system.d, mais cette pratique est maintenant considérée comme obsolète : ce répertoire devrait être traité comme réservé à l'administrateur

système.

Le fichier de configuration est un document XML. Il doit avoir la déclaration de type de document (doctype) suivante

: 
   <!DOCTYPE busconfig PUBLIC "-//freedesktop//DTD D-Bus Bus Configuration 1.0//EN"
    "http://www.freedesktop.org/sta
ndards/dbus/1.0/
busconfig.dtd">

Les éléments suivants peuvent être présents dans le fichier de

configuration.
•<busconfig
>

Élément

racine.
•<type
>

Le type bien connu du bus de messages. Les valeurs actuellement connues sont « system » et « session » ; si d'autres valeurs sont définies, elles devraient soit être ajoutées à la spécification D-Bus, soit être espacées de noms (namespaced). Le dernier élément <type> « gagne » (les valeurs précédentes sont ignorées). Cet élément ne contrôle que quelles variables d'environnement spécifiques au bus de messages sont définies dans les clients activés. La plupart de la politique qui distingue un bus de session d'un bus bus est contrôlé par les autres éléments du fichier de configuration.

Si le type bien connu du bus de messages est « session », alors la variable d'environnement DBUS_STARTER_BUS_TYPE sera définie sur « session » et la variable d'environnement DBUS_SESSION_BUS_ADDRESS sera définie sur l'adresse du bus de session. De même, si le type du bus de messages est « system », alors la variable d'environnement DBUS_STARTER_BUS_TYPE sera définie sur « system » et la variable d'environnement DBUS_SYSTEM_BUS_ADDRESS sera définie sur l'adresse du bus système (qui est normalement bien connue de toute façon).

Exemple : <type>session</type>

•<include>

Inclut un fichier <include>nom_fichier.conf</include> à cet endroit. Si le nom de fichier est relatif, il est localisé par rapport au fichier de configuration qui fait l'inclusion.

<include> possède un attribut optionnel « ignore_missing=(oui|non) » qui vaut « non » par défaut s'il n'est pas fourni. Cet attribut contrôle si l'absence du fichier inclus constitue une erreur fatale.

•<includedir>

Inclut tous les fichiers du répertoire <includedir>foo.d</includedir> à cet endroit. Les fichiers du répertoire sont inclus dans un ordre indéfini. Seuls les fichiers se terminant par « .conf » sont inclus.

Ceci est destiné à permettre l'extension du bus système par des paquets particuliers. Par exemple, si CUPS souhaite pouvoir envoyer des notifications de changements dans la file d'attente des imprimantes, il pourrait installer un fichier dans /usr/share/dbus-1/system.d qui permettrait à toutes les applications de recevoir ce message et autoriserait l'utilisateur du démon d'imprimante à l'envoyer.

•<user>

Le compte utilisateur sous lequel le démon doit s'exécuter, sous forme de nom d'utilisateur ou d'UID. Si le démon ne peut pas passer à cet UID au démarrage, il se terminera. Si cet élément est absent, le démon ne changera pas son UID et ne s'en souciera pas.

La dernière entrée <user> dans le fichier « gagne », les autres sont ignorées.

L'utilisateur est changé après que le bus a terminé son initialisation. Ainsi, les sockets, etc. seront créés avant le changement d'utilisateur, mais aucune donnée ne sera lue des clients avant le changement d'utilisateur. Cela signifie que les sockets et les fichiers PID peuvent être créés dans un emplacement qui nécessite des privilèges root pour l'écriture.

•<fork>

S'il est présent, le démon de bus devient un vrai démon (se détache en arrière-plan, etc.). Ceci est généralement utilisé plutôt que l'option de ligne de commande --fork.

•<keep_umask>

S'il est présent, le démon de bus conserve son umask d'origine lors du détachement. Ceci peut être utile pour éviter d'affecter le comportement des processus enfants.

•<syslog>

S'il est présent, le démon de bus enregistrera dans syslog. Les options de ligne de commande --syslog, --syslog-only et --nosyslog priment sur ce réglage.

•<pidfile>

S'il est présent, le démon de bus écrira son pid dans le fichier spécifié. L'option de ligne de commande --nopidfile prime sur ce réglage.

•<allow_anonymous>

S'il est présent, les connexions qui se sont authentifiées en utilisant le mécanisme ANONYMOUS seront autorisées à se connecter. Cette option n'a aucun effet pratique à moins que le mécanisme ANONYMOUS n'ait également été activé en utilisant l'élément <auth>, décrit ci-dessous.

L'utilisation de cette directive dans la configuration du bus système bien connu ou du bus de session bien connu rendra ce bus non sécurisé et ne devrait jamais être faite. De même, sur des types de bus personnalisés, l'utilisation de cette directive rendra généralement le bus personnalisé non sécurisé, à moins que sa configuration n'ait été spécifiquement conçue pour empêcher les utilisateurs anonymes de causer des dommages ou d'escalader leurs privilèges.

•<listen>

Ajoute une adresse sur laquelle le bus doit écouter. L'adresse est au format standard D-Bus qui contient un nom de transport plus des paramètres/options possibles.

Sur les plateformes autres que Windows, les transports basés sur Unix (unix, systemd, launchd) sont par défaut pour le bus système bien connu et le bus de session bien connu, et sont fortement recommandés.

Sur Windows, les transports basés sur Unix ne sont pas disponibles, donc des transports basés sur TCP doivent être utilisés. Similairement à X11 à distance, les transports tcp et nonce-tcp n'ont aucune protection d'intégrité ou de confidentialité, donc ils ne devraient normalement être utilisés que sur l'interface de boucle locale, par exemple en utilisant une adresse comme tcp:host=127.0.0.1 ou nonce-tcp:host=localhost. En particulier, configurer le bus système bien connu ou le bus de session bien connu pour écouter sur une adresse TCP non-boucle est non sécurisé.

Les développeurs sont parfois tentés d'utiliser TCP à distance comme outil de débogage. Cependant, si cette fonctionnalité est laissée activée dans les produits finis, le résultat sera dangereusement non sécurisé. Au lieu d'utiliser TCP à distance, les développeurs devraient relais les connexions via Secure Shell ou un protocole similaire[1].

Les connexions TCP à distance étaient historiquement parfois utilisées pour partager un seul bus de session entre les sessions de connexion du même utilisateur sur différentes machines au sein d'un réseau local de confiance, en conjonction avec X11 à distance non chiffré, un répertoire personnel partagé par NFS et l'authentification NIS (YP). Ceci n'est pas sécurisé contre un attaquant sur le même réseau local et devrait être considéré comme fortement déconseillé ; plus précisément, il n'est pas sécurisé de la même manière et pour les mêmes raisons que X11 à distance non chiffré et NFSv2/NFSv3. Les mainteneurs de D-Bus recommandent d'utiliser un bus de session séparé par paire (utilisateur, machine), accessible uniquement depuis cette machine.

Exemple : <listen>unix:path=/tmp/foo</listen>

Exemple : <listen>tcp:host=localhost,port=1234</listen>

S'il y a plusieurs éléments <listen>, le bus écoute sur plusieurs adresses. Le bus passera son adresse aux services démarrés ou à d'autres parties intéressées en commençant par la dernière adresse donnée dans <listen>. C'est-à-dire que les applications essaieront de se connecter à la dernière adresse <listen> en premier.

Les sockets tcp peuvent accepter des adresses IPv4, des adresses IPv6 ou des noms d'hôtes. Si un nom d'hôte résout plusieurs adresses, le serveur se liera à toutes. Les options family=ipv4 ou family=ipv6 peuvent être utilisées pour forcer la liaison à un sous-ensemble d'adresses.

Exemple : <listen>tcp:host=localhost,port=0,family=ipv4</listen>

Un cas particulier est l'utilisation d'un numéro de port zéro (ou l'omission du port), ce qui signifie choisir un port disponible sélectionné par le système d'exploitation. Le numéro de port choisi peut être obtenu avec le paramètre de ligne de commande --print-address et sera présent dans d'autres cas où le serveur rapporte sa propre adresse, comme lorsque DBUS_SESSION_BUS_ADDRESS est défini.

Exemple : <listen>tcp:host=localhost,port=0</listen>

Les adresses tcp/nonce-tcp permettent également une option bind=hostname, utilisée dans une adresse écoutable pour configurer l'interface sur laquelle le serveur écoutera : soit le nom d'hôte est l'adresse IP de l'une des interfaces de la machine locale (le plus souvent 127.0.0.1), un nom DNS qui résout vers l'une de ces adresses IP, '0.0.0.0' pour écouter simultanément sur toutes les interfaces IPv4, ou '::' pour écouter simultanément sur toutes les interfaces IPv4 et IPv6 (si pris en charge par le système d'exploitation). Si non spécifié, la valeur par défaut est la même que "host".

Exemple : <listen>tcp:host=localhost,bind=0.0.0.0,port=0</listen>

•<auth>

Liste les mécanismes d'autorisation autorisés. Si cet élément n'existe pas, tous les mécanismes connus sont autorisés. S'il y a plusieurs éléments <auth>, tous les mécanismes listés sont autorisés. L'ordre dans lequel les mécanismes sont listés n'a pas de signification.

Sur les systèmes d'exploitation non Windows, il est fortement recommandé d'autoriser uniquement le mécanisme d'authentification EXTERNAL. C'est le défaut pour le bus système bien connu et pour le bus de session bien connu.

Exemple : <auth>EXTERNAL</auth>

Exemple : <auth>DBUS_COOKIE_SHA1</auth>

•<servicedir>

Ajoute un répertoire pour rechercher les fichiers .service, qui indiquent au dbus-daemon comment démarrer un programme pour fournir un nom de bus bien connu particulier. Voir la spécification D-Bus pour plus de détails sur le contenu des fichiers .service.

Si un service particulier est trouvé dans plusieurs <servicedir>, le premier répertoire listé dans le fichier de configuration prime. Si deux fichiers de service fournissant le même nom de bus bien connu sont trouvés dans le même répertoire, il est arbitraire de savoir lequel sera choisi (cela ne peut arriver que si au moins un des fichiers de service n'a pas le nom recommandé, qui est son nom de bus bien connu suivi de ".service").

•<standard_session_servicedirs/>

<standard_session_servicedirs/> demande un ensemble standard de répertoires de services de session. Son effet est similaire à la spécification d'une série d'éléments <servicedir/> pour chacun des répertoires de données, dans l'ordre indiqué ici. Ce n'est pas exactement équivalent, car il n'y a actuellement aucun moyen de désactiver la surveillance des répertoires ou d'appliquer un nommage strict des fichiers de service pour un <servicedir/>.

Comme avec les éléments <servicedir/>, si un service particulier est trouvé dans plusieurs répertoires de service, le premier répertoire prime. Si deux fichiers de service fournissant le même nom de bus bien connu sont trouvés dans le même répertoire, il est arbitraire de savoir lequel sera choisi (cela ne peut arriver que si au moins un des fichiers de service n'a pas le nom recommandé, qui est son nom de bus bien connu suivi de ".service").

Sur Unix, les répertoires de services de session standard sont :

•$XDG_RUNTIME_DIR/dbus-1/services, si XDG_RUNTIME_DIR est défini (voir la spécification XDG Base Directory pour les détails de XDG_RUNTIME_DIR) : cet emplacement convient aux services transitoires créés à l'exécution par les générateurs systemd (voir systemd.generator(7)), les gestionnaires de session ou d'autres infrastructures de session. C'est une extension fournie par l'implémentation de référence de dbus-daemon, et elle n'est pas standardisée dans la spécification D-Bus.

Contrairement aux autres répertoires de services de session standard, ce répertoire applique un nommage strict pour les fichiers de service : le nom de fichier doit être exactement le nom de bus bien connu du service, suivi de ".service".

Également contrairement aux autres répertoires de services de session standard, ce répertoire n'est jamais surveillé avec inotify(7) ou des API similaires. On s'attend à ce que les programmes qui créent des fichiers de service dans ce répertoire pendant qu'un dbus-daemon est en cours d'exécution appellent la méthode ReloadConfig() du dbus-daemon après avoir effectué des modifications.

•$XDG_DATA_HOME/dbus-1/services, où XDG_DATA_HOME vaut par défaut ~/.local/shar
e (voir la spécification XDG Base Directory) : cet emplacement est spécifié par la spécification D-Bus et convient aux logiciels installés localement, par
utilisateur.
•directory/dbus-1/services pour chaque répertoire dans XDG_DATA_DIRS, où XDG_DATA_DIRS vaut par défaut /usr/local/share:/usr/share (voir la spécification XDG Base Directory) : ces emplacements sont spécifiés par la spécification D-Bus. Les valeurs par défaut conviennent aux logiciels installés localement par un administrateur système (/usr/local/share) ou aux logiciels installés à partir de paquets du système d'exploitation (/usr/share). Une configuration par utilisateur ou système qui définit la variable d'environnement XDG_DATA_DIRS peut étendre ce chemin de recherche pour couvrir les installations dans d'autres emplacements, par exemple ~/.local/share/flatpak/exports/share/ et /var/lib/flatpak/exports/share/ lorsque flatpak(1) est
utilisé.
•${datadir}/dbus-1/services pour le ${datadir} qui a été spécifié lorsque dbus a été compilé, généralement /usr/share : cet emplacement est une extension fournie par l'implémentation de référence dbus-daemon, et convient aux piles logicielles installées aux côtés de
dbus-daemon.

La « XDG Base Directory Specification » peut être trouvée à http://freedesktop.org/wiki/Standards/basedir-spec si elle n'a pas bougé, sinon essayez votre moteur de recherche

préféré.

:
•%CommonProgramFiles%/dbus-1/services si %CommonProgramFiles% est défini : cet emplacement convient aux paquets logiciels installés à l'échelle du
système
•Un répertoire share/dbus-1/services trouvé dans la même hiérarchie de répertoires (préfixe) que dbus-daemon : cet emplacement convient aux piles logicielles installées aux côtés de
dbus-daemon

L'option <standard_session_servicedirs/> n'est pertinente que pour le démon de bus de session par utilisateur défini dans /etc/dbus-1/session.conf. La placer dans un autre fichier de configuration serait probablement du

non-sens.

<standard_system_servicedirs/> spécifie les répertoires d'activation système standard dans lesquels les fichiers de service doivent être recherchés. Comme pour les services de session, le premier répertoire listé a la priorité la plus

Sur Unix, les répertoires de services système standard sont

•/etc/dbus-1/system-services : cet emplacement est spécifié par la spécification D-Bus, et convient aux logiciels installés localement par l'administrateur système, ou par un gestionnaire de déploiement déployant des services qui ne font pas partie du système d'exploitation (peut-être lorsque /usr/ est en lecture

•/usr/local/share/dbus-1/system-services : cet emplacement est spécifié par la spécification D-Bus, et convient aux logiciels installés localement par l'administrateur

•/usr/share/dbus-1/system-services : cet emplacement est spécifié par la spécification D-Bus, et convient aux logiciels installés par des paquets du système
d'exploitation
•${datadir}/dbus-1/system-services pour le ${datadir} qui a été spécifié lorsque dbus a été compilé, généralement /usr/share : cet emplacement est une extension fournie par l'implémentation de référence dbus-daemon, et convient aux piles logicielles installées aux côtés de
dbus-daemon
•/lib/dbus-1/system-services : cet emplacement est spécifié par la spécification D-Bus, et était destiné aux logiciels installés par des paquets du système d'exploitation et utilisés pendant le démarrage précoce (mais il devrait être considéré comme obsolète, car l'implémentation de référence de dbus-daemon n'est pas conçue pour être disponible pendant le démarrage
précoce)

L'option <standard_system_servicedirs/> n'est pertinente que pour le démon de bus système défini dans /usr/share/dbus-1/system.conf. La placer dans un autre fichier de configuration serait probablement du

non-sens.

L'élément <policy> définit une politique de sécurité à appliquer à un ensemble particulier de connexions au bus. Une politique est composée d'éléments <allow> et <deny>. Les attributs de l'élément <deny> déterminent si le déni « correspond » à une action particulière. S'il correspond, l'action est refusée (sauf si des règles ultérieures du fichier de configuration l'autorisent)

.

Les règles comportant un ou plusieurs attributs de la famille send_* sont vérifiées dans l'ordre lorsqu'une connexion tente d'envoyer un message. La dernière règle qui correspond au message détermine s'il peut être envoyé. Le bus de session connu autorise normalement l'envoi de n'importe quel message. Le bus système connu autorise normalement l'envoi de n'importe quel signal, les appels de méthode sélectionnés vers le dbus-daemon, et exactement une réponse à chaque appel de méthode envoyé précédemment (succès ou erreur). L'un ou l'autre peut être remplacé par la configuration ; sur le bus système, les services qui recevront des appels de méthode doivent installer une configuration qui leur permet de le faire, généralement via des règles de la forme <policy context="default"><allow send_destination="..."/><policy>

.

Les règles comportant un ou plusieurs attributs de la famille receive_*, ou avec l'attribut eavesdrop et aucun autre, sont vérifiées pour chaque destinataire d'un message (il peut y avoir plus d'un destinataire si le message est une diffusion ou si une connexion est en écoute). La dernière règle qui correspond au message détermine s'il peut être reçu. Le bus de session connu autorise normalement la réception de n'importe quel message, y compris l'écoute. Le bus système connu autorise normalement la réception de tout message qui n'a pas été écouté (tout message unicast adressé au destinataire, et tout message de diffusion)

.

Les attributs eavesdrop, min_fds et max_fds sont des modificateurs qui peuvent être appliqués aux règles send_* ou receive_*, et sont documentés

ci-dessous.

Les règles send_destination et receive_sender signifient que les messages ne peuvent pas être envoyés à ou reçus du *propriétaire* du nom donné, et non qu'ils ne peuvent pas être envoyés *à ce nom*. C'est-à-dire, si une connexion possède les services A, B, C, et que l'envoi à A est refusé, l'envoi à B ou C ne fonctionnera pas non plus. Comme cas particulier, send_destination="*" correspond à tout message (qu'il ait une destination spécifiée ou non), et receive_sender="*" correspond de même à tout

message.

Une règle send_destination_prefix ouvre ou ferme l'ensemble de l'espace de noms pour l'envoi. Elle signifie que les messages peuvent ou non être envoyés à la propriétaire de tout nom correspondant au préfixe, qu'il s'agisse du propriétaire principal ou en attente. En d'autres termes, pour la règle <allow send_destination_prefix="a.b"/> et les noms "a.b", "a.b.c", et "a.b.c.d" présents sur le bus, cela fonctionne comme si trois règles distinctes : <allow send_destination="a.b"/>, <allow send_destination="a.b.c"/>, et <allow send_destination="a.b.c.d"/> avaient été définies. Les règles pour la correspondance des noms sont les mêmes que dans own_prefix (voir ci-dessous) : un préfixe de "a.b" correspond aux noms "a.b" ou "a.b.c" ou "a.b.c.d", mais pas à "a.bc" ou "a.c". L'attribut send_destination_prefix ne peut pas être combiné avec l'attribut send_destination dans la même

règle.

Les règles avec send_broadcast="true" correspondent aux messages de signal sans destination (diffusions). Les règles avec send_broadcast="false" sont l'inverse : elles correspondent à toute destination unicast (signaux unicast, ainsi que tous les appels de méthode, réponses et erreurs) mais ne correspondent pas aux messages sans destination (diffusions). Ceci n'est pas la même chose que send_destination="*", qui correspond à tout message envoyé, qu'il ait une destination ou

non.

Les autres attributs send_* et receive_* sont des correspondances purement textuelles/valeur contre le champ donné dans l'en-tête du message, sauf que pour les attributs où c'est autorisé, * correspond à tout message (qu'il ait le champ d'en-tête pertinent ou non). Par exemple, send_interface="*" correspond à tout message envoyé, même s'il ne contient pas de champ d'en-tête d'interface. Des correspondances globales plus complexes telles que foo.bar.* ne sont pas

autorisées.

L'« écoute » se produit lorsqu'une application reçoit un message qui était explicitement adressé à un nom que l'application ne possède pas, ou qui est une réponse à un tel message. L'écoute ne s'applique donc qu'aux messages adressés aux services et aux réponses à ces messages (c'est-à-dire qu'elle ne s'applique pas aux signaux)

.

Pour <allow>, eavesdrop="true" indique que la règle correspond même en cas d'écoute. eavesdrop="false" est la valeur par défaut et signifie que la règle n'autorise les messages à aller que vers leur destinataire spécifié. Pour <deny>, eavesdrop="true" indique que la règle ne correspond que lors de l'écoute. eavesdrop="false" est la valeur par défaut pour <deny> également, mais ici cela signifie que la règle s'applique toujours, même sans écoute. L'attribut eavesdrop peut uniquement être combiné avec les règles send et receive (avec les attributs send_* et receive_*)

.

L'attribut [send|receive]_requested_reply fonctionne de manière similaire à l'attribut eavesdrop. Il contrôle si le <deny> ou <allow> correspond à une réponse attendue (correspond à un message d'appel de méthode précédent). Cet attribut n'a de sens que pour les messages de réponse (erreurs et retours de méthode), et est ignoré pour les autres types de

messages.

Pour <allow>, [send|receive]_requested_reply="true" est la valeur par défaut et indique que seules les réponses demandées sont autorisées par la règle. [send|receive]_requested_reply="false" signifie que la règle autorise toute réponse même si

inattendue.

Pour <deny>, [send|receive]_requested_reply="false" est la valeur par défaut mais indique que la règle ne correspond que lorsque la réponse n'a pas été demandée. [send|receive]_requested_reply="true" indique que la règle s'applique toujours, quel que soit l'état de la réponse en

attente.

Les attributs min_fds et max_fds modifient les règles send_* ou receive_*. Une règle avec l'attribut min_fds ne correspond aux messages que s'ils ont au moins ce nombre de descripteurs de fichier Unix attachés. Inversement, une règle avec l'attribut max_fds ne correspond aux messages que s'ils n'ont pas plus que ce nombre de descripteurs de fichier attachés. En pratique, les règles avec ces attributs prendront le plus souvent la forme <allow send_destination="..." max_fds="0"/>, <deny send_destination="..." min_fds="1"/> ou <deny receive_sender="*" min_fds="1"/>

.

Les règles avec l'attribut user ou group sont vérifiées lorsqu'une nouvelle connexion au bus de messages est établie, et contrôlent si la connexion peut continuer. Chacun de ces attributs ne peut pas être combiné avec un autre attribut. Comme cas particulier, user="*" et group="*" correspondent à toute connexion. S'il n'y a pas de règles de cette forme, la valeur par défaut est d'autoriser les connexions du même identifiant utilisateur que celui qui possède le dbus-daemon. Le bus de session connu utilise normalement ce comportement par défaut, tandis que le bus système connu autorise normalement toute

connexion.

Les règles avec l'attribut own ou own_prefix sont vérifiées lorsqu'une connexion tente de posséder un nom de bus connu. Comme cas particulier, own="*" correspond à tout nom de bus connu. Le bus de session connu autorise normalement toute connexion à posséder n'importe quel nom, tandis que le bus système connu n'autorise normalement aucune connexion à posséder n'importe quel nom, sauf si cela est autorisé par une configuration supplémentaire. Les services système qui posséderont un nom doivent installer une configuration qui leur permet de le faire, généralement via des règles de la forme <policy user="some-system-user"><allow own="..."/></policy>

.

<allow own_prefix="a.b"/> vous permet de posséder le nom "a.b" ou tout nom dont les premiers éléments séparés par des points sont "a.b" : en particulier, vous pouvez posséder "a.b.c" ou "a.b.c.d", mais pas "a.bc" ou "a.c". C'est utile lorsque des services comme Telepathy et ReserveDevice définissent une signification pour les sous-arbres de noms connus, tels que org.freedesktop.Telepathy.ConnectionManager.(anything) et org.freedesktop.ReserveDevice1.(anything)

.

Il n'a pas de sens de refuser un utilisateur ou un groupe à l'intérieur d'un <policy> pour un utilisateur ou un groupe ; les refus utilisateur/groupe ne peuvent se trouver que dans des politiques context="default" ou context="mandatory"

.

Une seule règle <deny> peut spécifier des combinaisons d'attributs tels que send_destination et send_interface et send_type. Dans ce cas, le déni ne s'applique que si les deux attributs correspondent au message refusé. p. ex. <deny send_interface="foo.bar" send_destination="foo.blah"/> refuserait les messages avec l'interface donnée ET le nom de bus donné. Pour obtenir un effet OU, vous spécifiez plusieurs règles <deny>

.

Vous ne pouvez pas inclure à la fois des attributs send_ et receive_ sur la même règle, car « si le message peut être envoyé » et « s'il peut être reçu » sont évalués

séparément.

Soyez prudent avec send_interface/receive_interface, car le champ d'interface dans les messages est facultatif. En particulier, ne spécifiez PAS <deny send_interface="org.foo.Bar"/> ! Cela bloquera les messages sans interface pour tous les services, ce qui n'est presque certainement pas ce que vous vouliez. Utilisez toujours des règles de la forme : <deny send_interface="org.foo.Bar" send_destination="org.foo.

SELINU

X

Voir http://www.nsa.gov/selinux/ pour les détails complets sur SELinux. Quelques extraits utiles

:

Chaque sujet (processus) et objet (par exemple fichier, socket, objet IPC, etc.) du système se voit attribuer un ensemble d'attributs de sécurité, connu sous le nom de contexte de sécurité. Un contexte de sécurité contient tous les attributs de sécurité associés à un sujet ou objet particulier qui sont pertinents pour la politique de

sécurité.

Afin de mieux encapsuler les contextes de sécurité et de fournir une plus grande efficacité, le code d'application de la politique de SELinux manipule généralement des identifiants de sécurité (SIDs) plutôt que des contextes de sécurité. Un SID est un entier qui est mappé par le serveur de sécurité à un contexte de sécurité à

l'exécution.

Lorsqu'une décision de sécurité est requise, le code d'application de la politique transmet une paire de SIDs (généralement le SID d'un sujet et le SID d'un objet, mais parfois une paire de SIDs de sujets ou une paire de SIDs d'objets), et une classe de sécurité d'objet au serveur de sécurité. La classe de sécurité d'objet indique le type d'objet, par exemple un processus, un fichier régulier, un répertoire, un socket TCP,

etc.

Les décisions d'accès spécifient si une permission est accordée ou non pour une paire donnée de SIDs et une classe. Chaque classe d'objet a un ensemble de permissions associées définies pour contrôler les opérations sur les objets de cette

classe.

D-Bus effectue des vérifications de sécurité SELinux à deux

endroits.

Premièrement, chaque fois qu'un message est routé d'une connexion à une autre connexion, le démon de bus vérifiera les permissions avec le contexte de sécurité de la première connexion comme source, le contexte de sécurité de la deuxième connexion comme cible, la classe d'objet "dbus" et la permission demandée

"send_msg".

Si un contexte de sécurité n'est pas disponible pour une connexion (impossible lors de l'utilisation de sockets de domaine UNIX), alors le contexte cible utilisé est le contexte du démon de bus lui-même. Il n'y a actuellement aucun moyen de changer cette valeur par défaut, car nous supposons que seuls les sockets de domaine UNIX seront utilisés pour se connecter au bus système global. Si cela change, nous ajouterons probablement un moyen de définir le contexte de connexion par

défaut.

Deuxièmement, chaque fois qu'une connexion demande à posséder un nom, le démon de bus vérifiera les permissions avec le contexte de sécurité de la connexion comme source, le contexte de sécurité spécifié pour le nom dans le fichier de configuration comme cible, la classe d'objet "dbus" et la permission demandée

"acquire_svc".

Le contexte de sécurité pour un nom de bus est spécifié avec l'élément <associate> décri

t plus tôt dans ce document. Si un nom n'a pas de contexte de sécurité associé dans le
fichier de configuration, le contexte de sécurité du démon de bus lui-même sera utilisé.

APPARMO

R

Le contexte de confinement AppArmor est stocké lorsque les applications se connectent au bus. Le contexte de confinement consiste en une étiquette et un mode de confinement. Lorsqu'une décision de sécurité est requise, le démon utilise le contexte de confinement pour interroger la politique AppArmor afin de déterminer si l'action doit être autorisée ou refusée et si l'action doit être

Le démon effectue des vérifications de sécurité AppArmor à trois

endroits.

Premièrement, chaque fois qu'un message est routé d'une connexion à une autre connexion, le démon de bus vérifiera les permissions avec l'étiquette de la première connexion comme source, l'étiquette et/ou le nom de connexion de la deuxième connexion comme cible, ainsi que le nom de bus, le chemin, le nom d'interface et le nom du membre. Les messages de réponse, tels que les messages method_return et error, sont implicitement autorisés s'ils répondent à un message qui a déjà été

autorisé.

Deuxièmement, chaque fois qu'une connexion demande à posséder un nom, le démon de bus vérifiera les permissions avec l'étiquette de la connexion comme source, le nom demandé comme cible, ainsi que le nom de

bus.

Troisièmement, chaque fois qu'une connexion tente d'écouter, le démon de bus vérifiera les permissions avec l'étiquette de la connexion comme source, ainsi que le nom de

bus.

Les règles AppArmor pour la médiation du bus ne sont pas stockées dans les fichiers de configuration du bus. Elles sont stockées dans le profil AppArmor de l'application. Veuillez consulter apparmor.d(5) pour

plus de
détails.

DÉBOGAG

E ss="Pp">Si vous essayez de déterminer où vont vos messages ou pourquoi vous n'en recevez pas, il y a plusieurs choses que vous pouvez essayer.

N'oubliez pas que le bus système est très verrouillé et si vous n'avez pas installé de fichier de politique de sécurité pour autoriser votre message, cela ne fonctionnera pas. Pour le bus de session, ce n'est pas un problème.

Le moyen le plus simple de comprendre ce qui se passe sur le bus est d'exécuter le programme dbus-monitor, qui est fourni avec le package D-Bus. Vous pouvez également envoyer des messages de test avec dbus-send. Ces programmes ont leurs propres pages de manuel.

Si vous voulez savoir ce que le démon lui-même fait, vous pourriez envisager d'exécuter une copie séparée du démon pour tester. Cela vous permettra de mettre le démon sous un débogueur, ou de l'exécuter avec une sortie détaillée, sans perturber votre session réelle et les démons système.

Pour exécuter une copie de test séparée du démon, par exemple, vous pouvez ouvrir un terminal et taper:

  DBUS_VERBOSE=1 dbus-daemon --session --print-address

L'adresse du démon de test sera imprimée au démarrage du démon. Vous devrez copier-coller cette adresse et l'utiliser comme valeur de la variable d'environnement DBUS_SESSION_BUS_ADDRESS lors du lancement des applications que vous souhaitez tester. Cela amènera ces applications à se connecter à votre bus de test au lieu du DBUS_SESSION_BUS_ADDRESS de votre bus de session réel.

DBUS_VERBOSE=1 n'aura AUCUN EFFET à moins que votre copie de D-Bus n'ait été compilée avec le mode détaillé activé. Ceci n'est pas recommandé dans les builds de production en raison de l'impact sur les performances. Vous devrez peut-être reconstruire D-Bus si votre copie n'a pas été compilée avec le débogage à l'esprit. (DBUS_VERBOSE affecte également la bibliothèque D-Bus et donc les applications utilisant D-Bus ; il peut être utile de voir une sortie détaillée côté client et du démon.)

Si vous voulez être plus avancé, vous pouvez créer une configuration de bus personnalisée pour votre bus de test (voir les fichiers session.conf et system.conf qui définissent les deux configurations par défaut, par exemple). Cela vous permettrait de spécifier un répertoire différent pour les fichiers .service, par exemple.
