DBI::Profile - Profilage des performances et tests de performance

pour le DBI

SYN

OP
SIS

La façon la plus simple d'activer le profilage DBI est de définir la variable d'environnement DBI_PROFILE à 2 puis d'exécuter votre code

comme d'habitude :

DBI_PROFILE=2 prog.

pl 
Cela profilera votre programme puis produira un résumé textuel groupé par requête à la sortie du programme. Vous pouvez aussi activer le profilage en définissant l'attribut Profile de n'importe quel
handle DBI :

$dbh->{Profile} =

2; 
Le résumé sera alors imprimé lorsque le handle sera
détruit.

De nombreuses autres valeurs que sont possibles - voir « ACTIVER UN PROFIL »

ci-dessous.

DESC

RIP
TION

Le module DBI::Profile fournit une interface simple pour collecter et rapporter des données de performance et de tests de performance

depuis le DBI.

Pour une interface plus élaborée, adaptée aux programmes plus volumineux, voir DBI::ProfileDumper et dbiprof. Pour les applications Apache/mod_perl, voir DBI::ProfileDumper::

Apache.

AP

ER
ÇU

La collecte de données de performance pour le DBI est construite autour de plusieurs concepts qu'il est important de comprendre

clairement.

Dispatch des

méthodes
Chaque appel de méthode sur un handle DBI passe par une fonction unique de « dispatch » qui gère tous les aspects communs des appels de méthodes DBI, comme la
gestion de l'attribut RaiseError.
Collecte des
données
Si le profilage est activé pour un handle, le code de dispatch prend un horodatage haute résolution peu après son entrée. Ensuite, après avoir appelé la méthode appropriée et juste avant de retourner, il prend un autre horodatage haute résolution et appelle une fonction pour enregistrer les informations. Cette fonction reçoit les deux horodatages ainsi que le handle DBI et le nom de la méthode qui a
été appelée. Ces données concernant un seul appel de méthode DBI sont appelées un
échantillon de profil. Filtrage des
données
Si l'appel de méthode a été invoqué par le DBI ou par un pilote, l'appel est ignoré pour le profilage car le temps passé sera comptabilisé par l'appel « le plus
externe » d'origine de votre code.
Par exemple, les appels que la méthode

selectrow_arrayref() fait à prepare() et execute() etc. ne sont pas comptés individuellement car le temps passé dans ces méthodes sera alloué à la méthode selectrow_arrayref() lorsqu'elle retourne. Si cela n'était pas fait, il serait très facile de compter deux fois le temps passé à l'intérieur

du
DBI.
Arborescence de stockage des
données
Les données de profil sont accumulées sous forme de « feuilles sur un arbre ». Le « chemin » à travers les branches de l'arbre jusqu'à une feuille particulière est déterminé dynamiquement pour chaque échantillon. C'est une caractéristique clé du profilage DBI.

Pour chaque appel de méthode profilé, le DBI parcourt le Path et utilise chaque valeur du Path pour descendre dans et faire croître l'arbre

Data.

Par exemple, si le

Path est 
[ 'foo', 'bar',
'baz' ]

alors les nouvelles données d'échantillon de profil seront fusionnées dans

l'arbre à 
$h->{Profile}->{Data}->{foo}->{bar}->
{baz}

Mais il n'est pas très utile de fusionner toutes les données d'appel dans un seul nœud feuille (sauf pour obtenir un total global du « temps passé à l'intérieur du DBI »). Il est plus courant de vouloir que le Path inclue des valeurs dynamiques telles que le texte de la requête courante et/ou le nom de la méthode appelée pour montrer à quoi a servi le temps passé à l'intérieur du

DBI.

Le Path peut contenir des valeurs « magic cookie » qui sont automatiquement remplacées par les valeurs dynamiques correspondantes lorsqu'elles sont utilisées. Ces magic cookies commencent toujours par un caractère de

ponctuation.

Par exemple, une valeur de"!MethodName" dans le Path fait que l'entrée correspondante dans le Data sera le nom de la méthode qui a été appelée. Par exemple, si le Path

était : 
[ 'foo', '!MethodName',
'bar' ]

et que la méthode selectall_arrayref() a été appelée, alors les données d'échantillon de profil pour cet appel seront fusionnées dans

l'arbre à : 
$h->{Profile}->{Dat
a}->{foo}->{selecta
ll_arrayref}->{bar}
Données de
profil
Les données de profil sont stockées aux « feuilles » de l'arbre sous forme de références à un tableau de valeurs numériques. Par exemple : 
[
  106,                  # 0: nombre d'échantillons à ce nœud
  0.0312958955764771,   # 1: durée totale
  0.000490069389343262, # 2: première durée
  0.000176072120666504, # 3: durée la plus courte
  0.00140702724456787,  # 4: durée la plus longue
  1023115819.83019,     # 5: heure du premier échantillon
  1023115819.86576,     # 6: heure du dernier échantillon
]

Après le premier échantillon, les é

chantillons suivants mettent toujou
rs à jour les éléments 0, 1 et 6, et
peuvent mettre à jour 3 ou 4 selon
la durée de l'appel échantillonné.

ACTIVER UN

PROFIL

Le profilage est activé pour un handle en assignant à l'attribut Profile. Par exemple

: 
$h->{Profile} = DBI::Profile->new()
;

L'attribut Profile contient une référence bénie à un objet hash qui contient les données de profil et les attributs s'y

rapportant.

On attend de la classe dans laquelle l'objet Profile est béni qu'elle fournisse au moins une méthode DESTROY qui déversera les données de profil vers le fichier de trace DBI (STDERR par défaut)

.

Tous ces exemples ont le même effet les uns que les autres

: 
$h->{Profile} = 0;
$h->{Profile} = "/DBI::Profile";
$h->{Profile} = DBI::Profile->new();
$h->{Profile} = {};
$h->{Profile} = { Path => [] }
;

De même, ces exemples ont le même effet les uns que les autres

: 
$h->{Profile} = 6;
$h->{Profile} = "6/DBI::Profile";
$h->{Profile} = "!Statement:!MethodName/DBI::Profile";
$h->{Profile} = { Path => [ '!Statement', '!MethodName' ] }
;

Si une référence hash non bénie est donnée, le module DBI::Profile est automatiquement "require"'é et la référence est bénie dans cette

classe.

Si une chaîne est donnée, elle est traitée comme ceci

: 
($path, $module, $args) = split /\//, $string, 3
@path = split /:/, $path
@args = split /:/, $args
eval "require $module" if $module
$module ||= "DBI::Profile"
$module->new( Path => \@Path, @args
)

Ainsi, la première valeur est utilisée pour sélectionner le Path à utiliser (voir ci-dessous). La deuxième valeur, si présente, est utilisée comme nom d'un module qui sera chargé et sa méthode "new" sera appelée. Si elle n'est pas présente, la valeur par défaut est DBI::Profile. Toutes les autres valeurs sont passées en arguments à la méthode "new". Par exemple :"2/DBIx::OtherProfil

e/Foo:42".

Des nombres peuvent être utilisés comme raccourci pour activer des valeurs de Path courantes. La façon la plus simple d'expliquer comment les valeurs sont interprétées est de montrer le code

: 
push @Path, "DBI"           if $path_elem & 0x01;
push @Path, "!Statement"    if $path_elem & 0x02;
push @Path, "!MethodName"   if $path_elem & 0x04;
push @Path, "!MethodClass"  if $path_elem & 0x08;
push @Path, "!Caller2"      if $path_elem &
0x10;

Ainsi "2" est équivalent à "!Statement" et "6" (2+4) est équivalent à "!Statement:!Method". Ce sont les deux valeurs les plus couramment utilisées. L'utilisation d'un nombre négatif inversera le chemin. Ainsi "-6" groupera par nom de méthode puis par

requête.

La séparation et l'analyse des valeurs de chaîne assignées à l'attribut Profile peuvent sembler un peu étranges, mais il y a une bonne raison pour cela. Rappelez-vous que les attributs peuvent être intégrés dans la chaîne Data Source Name qui peut être passée à un script en paramètre. Par exemple

: 
dbi:DriverName(Profile=>2):dbname
dbi:DriverName(Profile=>{Username}:!Statement/MyProfiler/Foo:42):
dbname

Et aussi, si la variable d'environnement "DBI_PROFILE" est définie, le DBI arrange les choses pour que chaque handle pilote partage le même objet de profil. Lorsque perl se te

rmine, un seul résumé de profil sera généré qui reflète (aussi fidè
lement que possible) l'utilisation totale du DBI par l'application.

L'OBJET DE

PROFIL

Le noyau du DBI attend que la valeur de l'attribut Profile soit une référence hash et si les valeurs suivantes n'existent pas, il les créera au besoin.

Chemi

n

La valeur Path est une référence vers un tableau. Chaque élément contrôle la valeur à utiliser au niveau correspondant de l'arbre de données du

profil.

Si la valeur de Path est autre chose qu'une référence de tableau, elle est traitée comme si elle était

: 
[ '!Statement'
]

Les éléments du tableau Path peuvent être de l'un des types suivants

:

Constante

spéciale

!

Statement

Utilise le texte de l'instruction courante. Généralement, c'est la valeur de l'attribut Statement pour le descripteur avec lequel la méthode a été appelée. Certaines méthodes, comme commit() et rollback(), ne sont pas liées à une instruction particulière. Pour ces méthodes, !Statement enregistre une chaîne

vide.

Pour les descripteurs d'instruction, c'est toujours simplement la chaîne qui a été donnée à prepare() lorsque le descripteur a été créé. Pour les descripteurs de base de données, c'est la dernière instruction préparée ou exécutée sur ce descripteur de base de données. Cela peut entraîner un peu de « flou » car, par exemple, les appels à la méthode quote() pour construire une nouvelle instruction seront généralement associés à l'instruction précédente. En pratique, ce n'est pas un problème important et le mécanisme dynamique Path peut être utilisé pour configurer vos propres

règles.

!

MethodName

Utilise le nom de la méthode DBI à laquelle l'échantillon de profil se

rapporte.

!

MethodClass

Utilise le nom complètement qualifié de la méthode DBI, y compris le paquet, à laquelle l'échantillon de profil se rapporte. Cela vous montre où la méthode a été implémentée. Par exemple

: 
'DBD::_::db::selectrow_arrayref' =>
    0.022902s
'DBD::mysql::db::selectrow_arrayref' =>
    2.244521s / 99 = 0.022445s avg (first 0.022813s, min 0.022051s, max 0.
028932s)

Le "DBD::_::db::selectrow_arrayref" montre que le pilote a hérité de la méthode selectrow_arrayref fournie par la

DBI.

Mais vous remarquerez qu'il n'y a qu'un seul appel à DBD::_::db::selectrow_arrayref mais 99 autres à DBD::mysql::db::selectrow_arrayref. Actuellement, le premier appel n'enregistre pas la véritable localisation. Cela pourrait

changer.

!

Caller

Utilise une chaîne montrant le nom de fichier et le numéro de ligne du code appelant la

méthode.

!

Caller2

Utilise une chaîne montrant le nom de fichier et le numéro de ligne du code appelant la méthode, comme pour !Caller, mais inclut aussi le nom de fichier et le numéro de ligne du code qui a appelé celui-ci. Les appels provenant des paquets DBI:: et DBD:: sont

ignorés.

!

File

Identique à !Caller ci-dessus, sauf que seul le nom de fichier est inclus, pas le numéro de

ligne.

!

File2

Identique à !Caller2 ci-dessus, sauf que seuls les noms de fichiers sont inclus, pas les numéros de

ligne.

!

Time

Utilise la valeur courante de time(). Rarement utilisé. Voir l'option plus utile "!Time~N" ci-d

essous.

!

Time~N

Où "N" est un entier. Utilise la valeur courante de time() mais avec une précision réduite. La valeur utilisée est déterminée de cette manière

: 
int( time() / N ) *
N

C'est une manière utile de segmenter un profil en créneaux de temps. Par exemple

: 
[ '!Time~60', '!Statement'
]

Référence de

code

La sous-routine reçoit le descripteur sur lequel elle a été appelée et le nom de la méthode DBI. L'instruction courante est dans $_. La chaîne d'instruction ne doit pas être modifiée, donc la plupart des sous-routines commencent par "local $_ =

$_;".

La liste de valeurs qu'elle retourne est utilisée à ce point du chemin du profil. Toutes les valeurs indéfinies sont traitées comme la chaîne ""undef""

.

La sous-routine peut « veto » (rejeter) un échantillon de profil en incluant une référence vers undef ("\undef") dans la liste retournée. Cela peut être utile lorsque vous voulez profiler uniquement les instructions qui correspondent à un certain motif, ou profiler uniquement certaines

méthodes.

Spécificateur de

sous-routine

Un élément Path qui commence par '"&"' est traité comme le nom d'une sous-routine dans l'espace de noms DBI::ProfileSubs et remplacé par la référence de code

correspondante.

Actuellement, cela ne fonctionne que lorsque le Path est spécifié par la variable d'environnement

"DBI_PROFILE".

De plus, actuellement, la seule sous-routine dans l'espace de noms DBI::ProfileSubs est '&norm_std_n3'. C'est une sous-routine très pratique lors du profilage de code qui n'utilise pas de paramètres de substitution. Voir DBI::ProfileSubs pour plus

d'informations.

Spécificateur

d'attribut

Une chaîne entourée d'accolades, comme '"{Username}"', spécifie que la valeur courante de l'attribut de descripteur de base de données correspondant doit être utilisée à ce point du

Path.

Référence vers un

scalaire

Spécifie que la valeur courante du scalaire référencé doit être utilisée à ce point du Path. Cela fournit un moyen efficace d'obtenir des valeurs « contextuelles » dans votre

profil.

Autres

valeurs

Toutes les autres valeurs sont converties en chaînes et utilisées

littéralement.

(Les références et les va

leurs qui commencent par
des caractères de ponctua
tion sont réservées.)

Format du

rapport

Les données de profil accumulées actuellement peuvent être formatées et sorties en

utilisant 
print $h->{Profile}->
format;

Pour ignorer les données de profil et commencer à collecter de nouvelles données, vous pouvez faire

: 
$h->{Profile}->{Data} =
undef;

Le format de résultat par défaut ressemble à ceci

: 
DBI::Profile: 0.001015s 42.7% (5 calls) programname @ YYYY-MM-DD HH:MM:SS
'' =>
    0.000024s / 2 = 0.000012s avg (first 0.000015s, min 0.000009s, max 0.000015s)
'SELECT mode,size,name FROM table' =>
    0.000991s / 3 = 0.000330s avg (first 0.000678s, min 0.000009s, max 0.
000678s)

Ce qui montre le temps total passé à l'intérieur de la DBI, avec le décompte du nombre total d'appels de méthode et le nom du script en cours d'exécution, puis une version formatée de l'arbre de données du

profil.

Si les résultats sont formatés lorsque le processus perl se termine (ce qui est généralement le cas lorsque la variable d'environnement DBI_PROFILE est utilisée), alors le pourcentage de temps que le processus a passé dans la DBI est également affiché. Si le processus ne se termine pas, le pourcentage est calculé en utilisant le temps entre le premier et le dernier appel à la

DBI.

Dans l'exemple ci-dessus, les chemins dans l'arbre n'ont qu'un seul niveau de profondeur et utilisent le texte de l'instruction comme valeur (c'est le comportement par défaut)

.

Les données de profil fusionnées aux « feuilles » de l'arbre sont présentées comme temps total passé, décompte, temps moyen passé (qui est simplement le temps total divisé par le décompte), puis le temps passé lors du premier appel, le temps passé lors de l'appel le plus rapide, et enfin le temps passé lors de l'appel le plus

lent.

Les temps 'avg', 'first', 'min' et 'max' ne sont pas particulièrement utiles lorsque le chemin des données de profil ne contient que le texte de l'instruction. Voici un extrait d'un exemple plus détaillé utilisant à la fois le texte de l'instruction et le nom de la méthode dans le chemin

: 
'SELECT mode,size,name FROM table' =>
    'FETCH' =>
        0.000076s
    'fetchrow_hashref' =>
        0.036203s / 108 = 0.000335s avg (first 0.000490s, min 0.000152s, max 0.
002786s)

Ici, vous pouvez voir que les 'avg', 'first', 'min' et 'max' pour les 108 appels à fetchrow_hashref() deviennent plutôt plus intéressants. De plus, les données pour FETCH montrent juste une valeur de temps parce qu'il n'a été appelé qu'une

fois.

Actuellement, les données de profil sont triées par noms de branche

. Cela pourrait changer dans une version ultérieure pour que le
s nœuds feuilles soient triés par temps total par nœud feuille.

as_node_path_lis

t 
@ary = $dbh->{Profile}->as_node_path_list();
@ary = $dbh->{Profile}->as_node_path_list($node, $path)
;

Retourne les données collectées ($dbh->{Profile}{Data}) restructurées en une liste de références de tableau, une pour chaque nœud feuille dans l'arbre de données. Cette structure « plate » est souvent beaucoup plus simple pour les applications à

manipuler.

Le premier élément de chaque référence de tableau est une référence vers le nœud feuille. Les éléments restants sont le « chemin » à travers l'arbre de données jusqu'à ce

nœud.

Par exemple, étant donné un arbre de données comme ceci

: 
{key1a}{key2a}[node1]
{key1a}{key2b}[node2]
{key1b}{key2a}{key3a}
[node3]

La méthode as_node_path_list() retournera cette liste

: 
[ [node1], 'key1a', 'key2a' ]
[ [node2], 'key1a', 'key2b' ]
[ [node3], 'key1b', 'key2a', 'key3a'
]

Les nœuds sont ordonnés par clé, en profondeur

d'abord.

L'argument $noden be used to focus on a sub-tree. If not specified it defaults to $dbh->{Profile}{Data}

.

The $path argument can be used to specify a list of path elements that will be added to each

element of the returned list. If not spe
cified it defaults to a ref to an empty array.

as_tex

t 
@txt = $dbh->{Profile}->as_text();
$txt = $dbh->{Profile}->as_text({
    node      => undef,
    path      => [],
    separator => " > ",
    format    => '%1$s: %11$fs / %10$d = %2$fs avg (first %12$fs, min %13$fs, max %14$fs)'."\n";
    sortsub   => sub { ... },
)
;

Renvoie les données collectées ($dbh->{Profile}{Data}) reformatées en une liste de chaînes formatées. En contexte scalaire, la liste est retournée sous forme d'une chaîne unique

concaténée.

Un hashref peut être utilisé pour passer des arguments, les valeurs par défaut sont montrées dans l'exemple

ci-dessus.

The "node" and <path> arguments are passed to as_node_path_

list().

The "separator" argument is used to join the elements of the path for each leaf

node.

The "sortsub" argument is used to pass in a ref to a sub that will order the list. The subroutine will be passed a reference to the array returned by as_node_path_list() and should sort the contents of the array in place. The return value from the sub is ignored. For example, to sort the nodes by the second level key you could

use: 
sortsub => sub { my $ary=shift; @$ary = sort { $a->[2] cmp $b->[2] } @$ary
}

are: 
 1:  path to node, joined with the separator
 2:  average duration (
total duration/count) (3 thru 9 are currently unused) 10: cou
nt 11: total duration 12: first duration 13: smallest duration 14
: largest duration 15: time of first call 16: time of first call

MANIPULATION PERSONNALISÉE DES

DONNÉES

Rappelez-vous que "$h->{Profile}->{Data}" est une référence vers les données collectées. Soit vers un tableau 'leaf' (quand le Path est vide, c.-à-d. que la variable d'environnement DBI_PROFILE vaut 1), soit une référence vers un hash contenant des valeurs qui sont soit des références vers d'autres hashes, soit des références vers des tableaux

'leaf'.

Parfois il est utile de pouvoir résumer une partie ou la totalité des données collectées. La fonction dbi_profile_merge_nodes() peut être utilisée pour fusionner les valeurs des nœuds

'leaf'.

dbi_profile_merge_node

s 
use DBI qw(dbi_profile_merge_nodes);
$time_in_dbi = dbi_profile_merge_nodes(my $totals=[], @$leaves)
;

Fusionne un nœud de données de profil. Étant donné une référence vers un tableau de destination, et zéro ou plusieurs références vers des données de profil, fusionne les données de profil dans le tableau de destination. Par exemple

: 
$time_in_dbi = dbi_profile_merge_nodes(
    my $totals=[],
    [ 10, 0.51, 0.11, 0.01, 0.22, 1023110000, 1023110010 ],
    [ 15, 0.42, 0.12, 0.02, 0.23, 1023110005, 1023110009 ],
)
;

$totals contiendra

alors 
[ 25, 0.93, 0.11, 0.01, 0.23, 1023110000, 1023110010
]

et $time_in_dbi vaudra 0.93

;

Le second argument n'a pas besoin d'être seulement des nœuds 'leaf'. S'il reçoit une référence vers un hash, alors le hash est recherché récursivement pour trouver des nœuds 'leaf' et tous ceux trouvés sont

fusionnés.

Par exemple, pour obtenir le temps passé 'à l'intérieur' du DBI pendant une requête http, votre code de journalisation exécuté à la fin de la requête (c.-à-d. LogHandler de mod_perl) pourrait utiliser

: 
my $time_in_dbi = 0;
if (my $Profile = $dbh->{Profile}) { # if DBI profiling is enabled
    $time_in_dbi = dbi_profile_merge_nodes(my $total=[], $Profile->{Data});
    $Profile->{Data} = {}; # reset the profile data
}

Si le profilage a été activé alors $time_in_dbi contiendra le temps passé à l'intérieur du DBI pour ce handle (et tout autre handle qui partage les mêmes données de profil) depuis la dernière

requête.

Avant DBI 1.56, la fonction dbi_profile_merge_nodes() s'appelait dbi_profile_merge(). Ce

nom existe to
ujours comme
un alias.

The dbi_profile() function can be used to add extra sample data into the profile data tree. For

example: 
use DBI;
use DBI::Profile (dbi_profile dbi_time);
my $t1 = dbi_time(); # floating point high-resolution time
... execute code you want to profile here ...
my $t2 = dbi_time();
dbi_profile($h, $statement, $method, $t1, $t2)
;

The $h parameter is the handle the extra profile sample should be associated with. The $statement parameter is the string to use where the Path specifies !Statement. If $statement is undef then $h->{Statement} will be used. Similarly $method is the string to use if the Path specifies !MethodName. There is no default value for $method

.

The $h->{Profile}{Path} attribute is processed by dbi_profile() in the usual

way.

The $h parameter is usually a DBI handle but it can also be a reference to a hash, in which case the dbi_profile() acts on each defined value in the hash. This is an e

fficient way to update multiple prof
iles with a single sample, and is u
sed by the DashProfiler module.

AVERTISSEMEN

TS

Applications which generate many different statement strings (typically because they don't use placeholders) and profile with !Statement in the Path (the default) will consume memory in the Profile Data structure for each statement. Use a code ref in the Path to return an edited (simplified) form of the

statement.

If a method throws an exception itself (not via RaiseError) then it won't be counted in the

profile.

If a HandleError subroutine throws an exception (rather than returning 0 and letting RaiseError do it) then the method call won't be counted in the

profile.

Time spent in DESTROY is added to the profile of the parent

handle.

Time spent in DBI->*() methods is not counted. The time spent in the driver connect method, $drh->connect(), when it's called by DBI->connect is counted if the DBI_PROFILE environment variable is

set.

Time spent fetching tied variables, $DBI::errstr, is

counted.

Time spent in FETCH for $h->{Profile} is not counted, so getting the profile data doesn't alter

it.

DBI::PurePerl does not support profiling (though it could in theory)

.

For asynchronous queries, time spent while the query is running on the backend is not

counted.

A few platforms don't support the gettimeofday() high resolution time function used by the DBI (and available via the dbi_time() function). In which case you'll get integer resolution time which is mostly

useless.

On Windows platforms the dbi_time() function is limited to millisecond resolution. Which isn't sufficiently fine for our needs, but still much better than integer resolution. This limited resolution means that fast method calls will often register as taking 0 time. And timings in general will have much more 'jitter' depending on where within the 'current millisecond' the start and end timing was

taken.
