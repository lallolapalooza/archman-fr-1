NOM

DBD::SQLite::VirtualTable -- Tables virtuelles SQLite implémentées en Perl

SYNOPSIS

# register the virtual table module within sqlite
$dbh->sqlite_create_module(mod_name => "DBD::SQLite::VirtualTable::Subclass");
# create a virtual table
$dbh->do("CREATE VIRTUAL TABLE vtbl USING mod_name(arg1, arg2, ...)")
# use it as any regular table
my $sth = $dbh->prepare("SELECT * FROM vtbl WHERE ...");

Note : les sous-classes ou les instances de VirtualTable ne sont pas appelées directement depuis le code Perl ; tout se passe indirectement via des instructions SQL au sein de SQLite.

DESCRIPTION

Ce module est une classe abstraite pour implémenter des tables virtuelles SQLite, écrites en Perl. Ces tables ressemblent à des tables normales et sont accessibles via des instructions SQL normales et l'API DBI normale ; mais l'implémentation se fait par des appels cachés à une classe Perl. C'est la même idée que les variables liées (tied) de Perl, mais au niveau de SQLite.

La classe abstraite actuelle ne peut pas être utilisée directement, donc le synopsis ci-dessus est juste là pour donner une idée générale. Les classes concrètes et utilisables fournies avec la présente distribution sont :

  • DBD::SQLite::VirtualTable::FileContent : implémente une colonne virtuelle qui expose le contenu de fichiers. C'est particulièrement utile en conjonction avec un index plein texte ; voir DBD::SQLite::Fulltext_search.
  • DBD::SQLite::VirtualTable::PerlData : se lie à un tableau Perl au sein du programme Perl. Cela peut être utilisé pour des opérations simples d'import/export, à des fins de débogage, pour joindre des données de différentes sources, etc.

D'autres tables virtuelles Perl peuvent également être publiées séparément sur CPAN.

Les chapitres suivants documentent la structure de la classe abstraite et expliquent comment écrire de nouvelles sous-classes ; ceci est destiné aux auteurs de modules, pas aux utilisateurs finaux. Si vous avez juste besoin d'utiliser un module de table virtuelle, référez-vous à la documentation de ce module.

ARCHITECTURE

Classes

Un module de table virtuelle pour SQLite est implémenté à travers une paire de classes :

  • la classe table implémente des méthodes pour créer ou se connecter à une table virtuelle, pour la détruire, pour ouvrir de nouvelles recherches, etc.
  • la classe curseur implémente des méthodes pour exécuter une instruction SQL spécifique

Méthodes

La plupart des méthodes dans les deux classes ne sont pas appelées directement depuis le code Perl : ce sont plutôt des rappels (callbacks), appelés depuis le noyau sqlite. Conformément aux conventions Perl courantes, de telles méthodes ont des noms en majuscules.

MÉTHODES DE TABLE

Méthodes de classe pour enregistrer le module

CREATE_MODULE

$class->CREATE_MODULE($sqlite_module_name);

Appelé lorsque le code client invoque

$dbh->sqlite_create_module($sqlite_module_name => $class);

L'implémentation par défaut est vide.

DESTROY_MODULE

$class->DESTROY_MODULE();

Appelé automatiquement lorsque la connexion à la base de données est fermée. L'implémentation par défaut est vide.

Méthodes de classe pour créer une instance de table virtuelle

CREATE

$class->CREATE($dbh_ref, $module_name, $db_name, $vtab_name, @args);

Appelé lorsque sqlite reçoit une instruction

CREATE VIRTUAL TABLE $db_name.$vtab_name USING $module_name(@args)

L'implémentation par défaut appelle simplement "NEW".

CONNECT

$class->CONNECT($dbh_ref, $module_name, $db_name, $vtab_name, @args);

Appelé lors de la tentative d'accès à une table virtuelle qui avait été créée lors d'une connexion précédente à la base de données. Les arguments de création ont été stockés dans la base de données sqlite et sont passés à nouveau à la méthode CONNECT.

L'implémentation par défaut appelle simplement "NEW".

_PREPARE_SELF

$class->_PREPARE_SELF($dbh_ref, $module_name, $db_name, $vtab_name, @args);

Prépare la structure de données pour une instance de table virtuelle. @args est
simplement la collection de chaînes (séparées par des virgules) qui ont été données
dans l'instruction "CREATE VIRTUAL TABLE" ; chaque sous-classe devrait
décider quoi faire de cette information,

La méthode analyse @args pour différencier les options (chaînes de la forme $key=$value ou $key="$value", stockées dans "$self->{options}"), et les colonnes (les autres @args, stockées dans "$self->{columns}"). Elle crée un hashref avec les champs suivants :

"dbh_ref"
une référence faible à la $dbh connexion à la base de données (voir Scalar::Util pour une explication des références faibles).
"module_name"
nom du module tel que déclaré à sqlite (à ne pas confondre avec le nom de la classe Perl).
"db_name"
nom de la base de données (généralement 'main' ou 'temp'), mais cela peut aussi être une base de données attachée
"vtab_name"
nom de la table virtuelle
"columns"
arrayref des déclarations de colonnes
"options"
hashref des déclarations d'options

Cette méthode ne devrait pas être redéfinie, car elle effectue un travail général censé être utile pour toutes les sous-classes. À la place, les sous-classes peuvent redéfinir la méthode "NEW".

NEW

$class->NEW($dbh_ref, $module_name, $db_name, $vtab_name, @args);

Instancie une table virtuelle.

Méthodes d'instance appelées depuis le noyau sqlite

DROP

Appelé chaque fois qu'une table virtuelle est détruite depuis la base de données via l'instruction SQL "DROP TABLE" .

Juste après l'appel DROP() , l'instance Perl sera détruite (et appellera donc automatiquement la méthode DESTROY() si une telle méthode est présente).

L'implémentation par défaut de DROP est vide.

Note : cela correspond à la méthode "xDestroy" dans la documentation de SQLite ; ici, elle n'a pas été nommée "DESTROY", pour éviter toute confusion avec la méthode Perl standard "DESTROY" pour la destruction des objets.

DISCONNECT

Appelé pour chaque table virtuelle juste avant que la connexion à la base de données ne soit fermée.

Juste après l'appel DISCONNECT() , l'instance Perl sera détruite (et appellera donc automatiquement la méthode DESTROY() si une telle méthode est présente).

L'implémentation par défaut de DISCONNECT est vide.

VTAB_TO_DECLARE

Cette méthode est appelée automatiquement juste après "CREATE" ou "CONNECT", pour enregistrer les colonnes de la table virtuelle au sein du noyau sqlite. La méthode devrait retourner une chaîne contenant une instruction SQL "CREATE TABLE" ; mais seules les parties de déclaration des colonnes seront considérées. Les colonnes peuvent être déclarées avec le mot-clé spécial "HIDDEN", ce qui signifie qu'elles sont utilisées en interne pour l'implémentation de la table virtuelle et ne sont pas visibles par les utilisateurs -- voir http://sqlite.org/c3ref/declare_vtab.html et http://www.sqlite.org/vtab.html#hiddencol pour des explications détaillées.

L'implémentation par défaut retourne :

CREATE TABLE $self->{vtab_name}(@{$self->{columns}})

BEST_INDEX

my $index_info = $vtab->BEST_INDEX($constraints, $order_by)

C'est la méthode la plus complexe à redéfinir dans les sous-classes. Cette méthode sera appelée au début d'une nouvelle requête sur la table virtuelle ; le travail de la méthode consiste à assembler certaines informations qui seront utilisées

a)
par le noyau de sqlite pour décider de la meilleure stratégie de recherche
b)
par la méthode "FILTER" du curseur pour produire le sous-ensemble désiré de lignes de la table virtuelle.

En appelant cette méthode, le noyau SQLite indique à la table virtuelle qu'il doit accéder à un sous-ensemble des lignes de la table virtuelle et qu'il souhaite connaître la manière la plus efficace d'effectuer cet accès. La "BEST_INDEX" méthode répond avec des informations que le noyau SQLite peut ensuite utiliser pour effectuer une recherche efficace de la table virtuelle.

La méthode prend en entrée une liste de $constraints et une liste de $order_by instructions. Elle retourne un hashref de propriétés d'indexation, décrites ci-dessous ; de plus, la méthode ajoute des informations supplémentaires dans l'entrée $constraints. Des explications détaillées sont données dans http://sqlite.org/vtab.html#xbestindex.

Contraintes d'entrée

Les éléments du $constraints arrayref correspondent à des clauses spécifiques de la "WHERE ..." partie de la requête SQL. Chaque contrainte est un hashref avec les clés :

"col"
l'index entier de la colonne du côté gauche de la contrainte
"op"
l'opérateur de comparaison, exprimé sous forme de chaîne contenant '=', '>', '>=', '<', '<=' ou 'MATCH'.
"usable"
un booléen indiquant si cette contrainte est utilisable ; certaines contraintes peuvent ne pas être utilisables en raison de la manière dont les tables sont ordonnées dans une jointure.

Le $constraints arrayref est utilisé à la fois pour l'entrée et pour la sortie. Pendant l'itération sur le tableau, la méthode doit ajouter les clés suivantes dans les contraintes utilisables :

"argvIndex"
Un index dans le tableau @values qui sera passé à la méthode "FILTER" du curseur. En d'autres termes, si la contrainte courante correspond au fragment SQL "WHERE ... AND foo < 123 ...", et que le "argvIndex" correspondant prend la valeur 5, cela signifie que la "FILTER" méthode recevra 123 dans $values[5].
"omit"
Un booléen indiquant au noyau de sqlite qu'il peut omettre de revérifier en toute sécurité cette contrainte avant de retourner le jeu de résultats au programme appelant ; cela signifie que la méthode FILTER a accompli le travail de filtrage sur cette contrainte et qu'il n'est pas nécessaire d'effectuer d'autres vérifications.

La "BEST_INDEX" méthode ne recevra pas nécessairement toutes les contraintes de la clause SQL "WHERE" : par exemple, une contrainte comme "col1 < col2 + col3" ne peut pas être traitée à ce niveau. De plus, la "BEST_INDEX" pourrait décider d'ignorer certaines des contraintes reçues. C'est pourquoi un second passage sur les résultats sera effectué par le noyau de sqlite.

Informations d'entrée "order_by"

Le $order_by arrayref correspond aux clauses "ORDER BY" dans la requête SQL. Chaque entrée est un hashref avec les clés :

"col"
l'index entier de la colonne qui est ordonnée
"desc"
un booléen indiquant si l'ordre est DESCendant ou ascendant

Ces informations pourraient être utilisées par certaines sous-classes pour optimiser la stratégie de requête ; mais généralement le noyau de sqlite effectuera un autre passage de tri une fois que tous les résultats sont rassemblés.

Informations hashref retournées par BEST_INDEX

La méthode doit retourner un hashref avec les clés suivantes :

"idxNum"
Un entier arbitraire associé à cet index ; cette information sera transmise à "FILTER".
"idxStr"
Une chaîne arbitraire associée à cet index ; cette information sera transmise à "FILTER".
"orderByConsumed"
Un booléen indiquant au noyau de sqlite si les $order_by informations ont été prises en compte ou non.
"estimatedCost"
Un flottant qui devrait être défini sur le nombre estimé d'opérations d'accès au disque nécessaires pour exécuter cette requête sur la table virtuelle. Le noyau SQLite appellera souvent BEST_INDEX plusieurs fois avec différentes contraintes, obtiendra plusieurs estimations de coût, puis choisira le plan de requête qui donne la plus faible estimation.
"estimatedRows"
Un entier donnant le nombre estimé de lignes retournées par cette requête.

OPEN

Appelé pour instancier un nouveau curseur. L'implémentation par défaut ajoute "::Cursor" au nom de classe courant et appelle NEW() dans cette classe de curseur.

_SQLITE_UPDATE

C'est la méthode de dispatch implémentant le xUpdate() rappel pour les tables virtuelles. L'implémentation par défaut applique l'algorithme décrit dans http://sqlite.org/vtab.html#xupdate pour décider d'appeler "INSERT", "DELETE" ou "UPDATE" ; il n'y a donc pas de raison de redéfinir cette méthode dans les sous-classes.

INSERT

my $rowid = $vtab->INSERT($new_rowid, @values);

Cette méthode devrait être redéfinie dans les sous-classes pour implémenter l'insertion d'une nouvelle ligne dans la table virtuelle. La taille du @values tableau correspond au nombre de colonnes déclarées via "VTAB_TO_DECLARE". Le $new_rowid peut être explicitement donné, ou il peut être "undef", auquel cas la méthode doit calculer un nouvel id et le retourner comme résultat de l'appel de méthode.

DELETE

$vtab->INSERT($old_rowid);

Cette méthode devrait être redéfinie dans les sous-classes pour implémenter la suppression d'une ligne de la table virtuelle.

UPDATE

$vtab->UPDATE($old_rowid, $new_rowid, @values);

Cette méthode devrait être redéfinie dans les sous-classes pour implémenter une mise à jour de ligne au sein de la table virtuelle. Habituellement $old_rowid est égal à $new_rowid, ce qui est une mise à jour régulière ; cependant, le rowid pourrait être changé depuis une instruction SQL telle que

UPDATE table SET rowid=rowid+1 WHERE ...;

FIND_FUNCTION

$vtab->FIND_FUNCTION($num_args, $func_name);

Lorsqu'une fonction utilise une colonne d'une table virtuelle comme son premier argument, cette méthode est appelée pour voir si la table virtuelle souhaiterait surcharger la fonction. Les paramètres sont le nombre d'arguments de la fonction, et le nom de la fonction. Si aucun surchargement n'est souhaité, cette méthode devrait retourner faux. Pour surcharger la fonction, cette méthode devrait retourner un coderef vers l'implémentation de la fonction.

Chaque table virtuelle conserve un cache des résultats des appels à FIND_FUNCTION , donc la méthode ne sera appelée qu'une fois pour chaque paire "($num_args, $func_name)".

BEGIN_TRANSACTION

Appelé pour commencer une transaction sur la table virtuelle.

SYNC_TRANSACTION

Appelé pour signaler le début d'un commit en deux phases sur la table virtuelle.

SYNC_TRANSACTION

Appelé pour valider une transaction de table virtuelle.

ROLLBACK_TRANSACTION

Appelé pour annuler une transaction de table virtuelle.

RENAME

$vtab->RENAME($new_name)

Appelé pour renommer une table virtuelle.

SAVEPOINT

$vtab->SAVEPOINT($savepoint)

Appelé pour signaler à la table virtuelle de sauvegarder son état actuel au point de sauvegarde $savepoint (un entier).

ROLLBACK_TO

$vtab->ROLLBACK_TO($savepoint)

Appelé pour signaler à la table virtuelle de retourner à l'état $savepoint. Cela invalidera tous les points de sauvegarde avec des valeurs supérieures à $savepoint.

RELEASE

$vtab->RELEASE($savepoint)

Appelé pour invalider tous les points de sauvegarde avec des valeurs supérieures ou égales à $savepoint.

Méthodes utilitaires d'instance

Les méthodes de cette section sont en minuscules, car elles ne sont pas appelées directement depuis le noyau de sqlite ; ce sont des méthodes utilitaires à appeler depuis les autres méthodes décrites ci-dessus.

dbh

Cette méthode retourne le gestionnaire de base de données ($dbh) associé à la table virtuelle courante.

MÉTHODES DE CURSEUR

Méthodes de classe

NEW

my $cursor = $cursor_class->NEW($vtable, @args)

Instancie un nouveau curseur. L'implémentation par défaut retourne simplement un hashref béni avec les clés "vtable" et "args".

Méthodes d'instance

FILTER

$cursor->FILTER($idxNum, $idxStr, @values);

Cette méthode commence une recherche dans une table virtuelle.

Les arguments $idxNum et $idxStr correspondent aux valeurs retournées par "BEST_INDEX" pour l'index choisi. Les significations spécifiques de ces valeurs sont sans importance pour SQLite, tant que "BEST_INDEX" et "FILTER" sont d'accord sur ce que cette signification est.

La "BEST_INDEX" méthode a pu demander les valeurs de certaines expressions en utilisant les "argvIndex" valeurs de la liste $constraints . Ces valeurs sont passées à "FILTER" à travers le tableau @values .

Si la table virtuelle contient une ou plusieurs lignes correspondant aux critères de recherche, alors le curseur doit être laissé pointant sur la première ligne. Les appels suivants à "EOF" doivent renvoyer faux. S'il n'y a aucune ligne correspondante, alors le curseur doit être laissé dans un état qui fera renvoyer vrai par "EOF". Le moteur SQLite utilisera les méthodes "COLUMN" et "ROWID" pour accéder au contenu de cette ligne. La méthode "NEXT" sera utilisée pour passer à la ligne suivante.

EOF

Cette méthode doit renvoyer faux si le curseur pointe actuellement vers une ligne de données valide, ou vrai sinon. Cette méthode est appelée par le moteur SQL immédiatement après chaque invocation de "FILTER" et "NEXT".

NEXT

Cette méthode avance le curseur vers la ligne suivante d'un ensemble de résultats initié par "FILTER". Si le curseur pointe déjà vers la dernière ligne lorsque cette méthode est appelée, alors le curseur ne pointe plus vers des données valides et un appel subséquent à la méthode "EOF" doit renvoyer vrai. Si le curseur est avancé avec succès vers une autre ligne de contenu, alors les appels suivants à "EOF" doivent renvoyer faux.

COLUMN

my $value = $cursor->COLUMN($idxCol);

Le noyau SQLite invoque cette méthode afin de trouver la valeur pour la N-ième colonne de la ligne courante. N est basé sur zéro, donc la première colonne est numérotée 0.

ROWID

my $value = $cursor->ROWID;

Renvoie le rowid de la ligne vers laquelle le curseur est actuellement en train de pointer.

VOIR AUSSI

SQLite::VirtualTable est un autre module pour les tables virtuelles écrit en Perl, mais conçu pour le cas d'utilisation inverse : au lieu de démarrer un programme Perl et d'y intégrer la bibliothèque SQLite, l'utilisation prévue est de démarrer un programme sqlite, et d'y intégrer l'interpréteur Perl.
