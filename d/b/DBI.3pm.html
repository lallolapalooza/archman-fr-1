DESCRIPTION

DBI est un module d'accès aux bases de données pour le langage de programmation Perl. Il définit un ensemble de méthodes, de variables et de conventions qui fournissent une interface de base de données cohérente, indépendante de la base de données réellement utilisée.

Il est important de se rappeler que DBI n'est qu'une interface. DBI est une couche de « colle » entre une application et un ou plusieurs modules de pilote de base de données. Ce sont les modules de pilotes qui font la plupart du vrai travail. DBI fournit une interface et un cadre standard pour que les pilotes fonctionnent.

Ce document utilise souvent des termes comme références, objets, méthodes. Si vous n'êtes pas familier avec ces termes, ce serait une bonne idée de lire au moins les manuels perl suivants d'abord : perlreftut, perldsc, perllol et perlboot.

L'API, ou Application Programming Interface, définit l'interface d'appel et les variables pour les scripts Perl. L'API est implémentée par l'extension Perl DBI.

DBI « distribue » les appels de méthodes au pilote approprié pour l'exécution réelle. DBI est également responsable du chargement dynamique des pilotes, de la vérification et du traitement des erreurs, de la fourniture d'implémentations par défaut pour les méthodes, et de nombreuses autres tâches non spécifiques à une base de données.

Chaque pilote contient des implémentations des méthodes DBI utilisant les fonctions d'interface privées du moteur de base de données correspondant. Seuls les auteurs d'applications sophistiquées/multi-bases de données ou de fonctions de bibliothèque génériques doivent se soucier des pilotes.

Valeurs

NULL

Les valeurs indéfinies, ou "undef", sont utilisées pour indiquer les valeurs NULL. Vous pouvez insérer et mettre à jour des colonnes avec une valeur NULL comme vous le feriez avec une valeur non-NULL. Ces exemples insèrent et mettent à jour la colonne "age" avec une valeur NULL

: 
$sth = $dbh->prepare(qq{
  INSERT INTO people (fullname, age) VALUES (?, ?)
});
$sth->execute("Joe Bloggs", undef);
$sth = $dbh->prepare(qq{
  UPDATE people SET age = ? WHERE fullname = ?
});
$sth->execute(undef, "Joe Bloggs")
;

Cependant, il faut faire attention lorsqu'on essaie d'utiliser des valeurs NULL dans une clause "WHERE". Considérez

: 
SELECT fullname FROM people WHERE age =
?

Lier un "undef" (NULL) au placeholder ne sélectionnera pas les lignes qui ont un "age" NULL ! Du moins pour les moteurs de base de données qui se conforment au standard SQL. Consultez le manuel SQL de votre moteur de base de données ou n'importe quel livre SQL pour les raisons de cela. Pour sélectionner explicitement les NULL, vous devez dire ""WHERE age IS

NULL"".

Un problème courant est d'avoir un fragment de code qui gère une valeur qui peut être soit "defined" (définie) soit "undef" (non-NULL ou NULL) à l'exécution. Une technique simple consiste à préparer la déclaration appropriée au besoin et à substituer le placeholder pour les cas non-NULL

: 
$sql_clause = defined $age? "age = ?" : "age IS NULL";
$sth = $dbh->prepare(qq{
  SELECT fullname FROM people WHERE $sql_clause
});
$sth->execute(defined $age ? $age : ())
;

La technique suivante illustre la qualification d'une clause "WHERE" avec plusieurs colonnes, dont les valeurs associées ("defined" ou "undef") se trouvent dans un hachage %h

: 
for my $col ("age", "phone", "email") {
  if (defined $h{$col}) {
    push @sql_qual, "$col = ?";
    push @sql_bind, $h{$col};
  }
  else {
    push @sql_qual, "$col IS NULL";
  }
}
$sql_clause = join(" AND ", @sql_qual);
$sth = $dbh->prepare(qq{
    SELECT fullname FROM people WHERE $sql_clause
});
$sth->execute(@sql_bind)
;

ci-dessus.

Une meilleure solution est une seule clause "WHERE" qui supporte à la fois les comparaisons NULL et non-NULL. Sa déclaration SQL ne devrait avoir besoin d'être préparée qu'une seule fois pour tous les cas, améliorant ainsi les performances. Le gestionnaire de base de données en cache est remplacé par une nouvelle connexion s'il a été déconnecté ou si la méthode "ping" échoue. Notez que le

utile

dans certaines applications, mais cela peut aussi causer des problèmes, comme trop de connexions, et devrait donc être utilisé avec précaution. En particulier, évitez de modifier les attributs d'un gestionnaire de base de données créé via connect_cached() car cela affectera d'autres codes qui pourraient utiliser le même gestionnaire. plus,

}

"data_string_desc"

Renvoie une description informelle de la chaîne. Par exemple :

UTF8 off, ASCII, 42 characters 42 bytes

UTF8 on but INVALID encoding, non-ASCII, 4 characters 6 bytes

Le "UTF8" on/off initial fait référence au drapeau interne SvUTF8 de Perl. Si $string a le drapeau SvUTF8 défini mais que la séquence d'octets qu'il contient n'est pas une encodage UTF-8 valide, alors data_string_desc() signalera "UTF8 on but INVALID encoding".

La partie "ASCII" vs "non-ASCII" affiche "ASCII" si tous les caractères de la chaîne sont ASCII (ont des points de code <= 127).

La fonction data_string_desc() a été ajoutée dans DBI 1.46.

"data_string_diff"

$diff = data_string_diff($a, $b);

Renvoie une description informelle de la première différence de caractère entre les chaînes. Si à la fois $a et $b contiennent la même séquence de caractères, alors data_string_diff() renvoie une chaîne vide. Par exemple :

Params a & b     Result
------------     ------
'aaa', 'aaa'     ''
'aaa', 'abc'     'Strings differ at index 2: a[2]=a, b[2]=b'
'aaa', undef     'String b is undef, string a has 3 characters'
'aaa', 'aa'      'String b truncated after 2 characters'

Les caractères Unicode sont signalés au format "\x{XXXX}" . Les points de code Unicode dans la plage U+0800 à U+08FF sont non attribués et surviennent très probablement en raison d'un double encodage. Les caractères dans cette plage sont signalés comme "\x{08XX}='C'" où "C" est le caractère latin-1 correspondant.

La fonction data_string_diff() ne considère que les caractères logiques et non l'encodage sous-jacent. Voir "data_diff" pour une alternative.

La fonction data_string_diff() a été ajoutée dans DBI 1.46.

Par exemple, "data_diff("abc", "ab\x{263a}")" renverra :

"Callbacks"

Type : référence de hachage

Le mécanisme de rappel (callback) du DBI vous permet d'intercepter et, si vous le souhaitez, de remplacer tout appel de méthode sur une poignée DBI. À la limite, cela vous permet de devenir un marionnettiste, trompant l'application comme bon vous semble.

L'attribut "Callbacks" est une référence de hachage dont les clés sont des noms de méthodes DBI et les valeurs sont des références de code. Pour chaque clé nommant une méthode, le DBI exécutera la référence de code associée avant d'exécuter la méthode.

Les arguments de la référence de code seront les mêmes que ceux de la méthode, y compris l'invocant (une poignée de base de données ou une poignée d'instruction). Par exemple, supposons que vous souhaitiez un rappel vers du code lors d'un appel à prepare():

$dbh->{Callbacks} = {
    prepare => sub {
        my ($dbh, $query, $attrs) = @_;
        print "Preparing q{$query}\n"
    },
};

Le rappel serait alors exécuté lorsque vous appeliez la méthode prepare() :

$dbh->prepare('SELECT 1');

Et la sortie serait bien sûr :

Preparing q{SELECT 1}

Comme les rappels sont exécutés avant les méthodes auxquelles ils sont associés, vous pouvez modifier les arguments avant qu'ils ne soient transmis à l'appel de méthode. Par exemple, pour vous assurer que tous les appels à prepare() sont immédiatement préparés par DBD::Pg, ajoutez un rappel qui s'assure que l'attribut "pg_prepare_now" est toujours défini :

my $dbh = DBI->connect($dsn, $username, $auth, {
    Callbacks => {
        prepare => sub {
            $_[2] ||= {};
            $_[2]->{pg_prepare_now} = 1;
            return; # must return nothing
        },
    }
});

Notez que nous modifions directement le contenu de @_ . Dans ce cas, nous avons créé le hachage d'attributs s'il n'était pas passé à l'appel "prepare" .

Vous pouvez également empêcher la méthode associée de s'exécuter. Pendant l'exécution d'un rappel, $_ contient le nom de la méthode. (Cela permet à plusieurs rappels de partager la même référence de code tout en sachant quelle méthode a été appelée.) Pour empêcher la méthode de s'exécuter, il suffit de faire "undef $_". Par exemple, si vous souhaitiez désactiver les appels à ping(), vous pourriez faire ceci :

$dbh->{Callbacks} = {
    ping => sub {
        # tell dispatch to not call the method:
        undef $_;
        # return this value instead:
        return "42 bells";
    }
};

Comme pour les autres attributs, les Callbacks peuvent être spécifiés sur une poignée ou via les attributs de connect(). Les rappels peuvent également être appliqués à des méthodes d'instruction sur une poignée d'instruction. Par exemple :

$sth->{Callbacks} = {
    execute => sub {
        print "Executing ", shift->{Statement}, "\n";
    }
};

L'attribut "Callbacks" d'une poignée de base de données n'est pas copié vers les poignées d'instruction qu'elle crée. Ainsi, la définition de rappels pour une poignée d'instruction nécessite de définir l'attribut "Callbacks" sur la poignée d'instruction vous-même, comme dans l'exemple ci-dessus, ou d'utiliser la clé spéciale "ChildCallbacks" décrite ci-dessous.

Clés spéciales dans l'attribut Callbacks

En plus des noms de méthodes des poignées DBI, la référence de hachage "Callbacks" prend en charge quatre clés supplémentaires.

La première est la clé "ChildCallbacks" . Lorsqu'une poignée d'instruction est créée à partir d'une poignée de base de données, la clé "ChildCallbacks" de l'attribut "Callbacks" de la poignée de base de données, s'il existe, devient le nouvel attribut "Callbacks" de la poignée d'instruction. Cela vous permet de définir des rappels pour toutes les poignées d'instruction créées à partir d'une poignée de base de données. Par exemple, si vous souhaitiez compter le nombre de fois où "execute" a été appelé dans votre application, vous pourriez écrire :

my $exec_count = 0;
my $dbh = DBI->connect( $dsn, $username, $auth, {
    Callbacks => {
        ChildCallbacks => {
            execute => sub { $exec_count++; return; }
        }
    }
});
END {
    print "The execute method was called $exec_count times\n";
}

Les trois autres clés spéciales sont "connect_cached.new", "connect_cached.connected"et "connect_cached.reused". Ces clés définissent des rappels qui sont appelés lorsque connect_cached() est appelé, mais permettent des comportements différents selon qu'une nouvelle poignée est créée ou qu'une poignée est retournée. Le rappel est invoqué avec les arguments suivants : "$dbh, $dsn, $user, $auth, $attr".

Par exemple, certaines applications utilisent connect_cached() pour se connecter avec "AutoCommit" activé, puis désactivent "AutoCommit" temporairement pour les transactions. Si connect_cached() est appelé pendant une transaction, peut-être dans une méthode utilitaire, il pourrait sélectionner la même poignée mise en cache et forcer "AutoCommit" , ce qui provoquerait le commit de la transaction. Voir la documentation de "connect_cached" pour une façon de gérer cela. Ici, nous décrirons une approche alternative utilisant un rappel.

Comme les rappels "connect_cached.new" et "connect_cached.reused" sont invoqués avant que connect_cached() n'ait appliqué les attributs de connexion, vous pouvez les utiliser pour modifier les attributs qui seront appliqués. Pour empêcher qu'une poignée mise en cache ne fasse commit de ses transactions avant d'être retournée, vous pouvez éliminer l'attribut "AutoCommit" dans un rappel "connect_cached.reused" , comme ceci :

my $cb = {
    'connect_cached.reused' => sub { delete $_[4]->{AutoCommit} },
};
sub dbh {
    my $self = shift;
    DBI->connect_cached( $dsn, $username, $auth, {
        PrintError => 0,
        RaiseError => 1,
        AutoCommit => 1,
        Callbacks  => $cb,
    });
}

Le résultat est que les nouvelles poignées de base de données sont créées avec "AutoCommit" activé, tandis que les poignées de base de données mises en cache restent dans l'état de transaction dans lequel elles se trouvaient lorsqu'elles ont été récupérées du cache.

Notez que nous avons également utilisé une variable lexicale pour la référence de hachage des rappels. C'est parce que connect_cached() retourne une nouvelle poignée de base de données si l'un des attributs qui lui sont passés a changé. Si nous utilisions une référence de hachage en ligne, connect_cached() retournerait une nouvelle poignée de base de données à chaque fois, ce qui contrecarrerait plutôt l'objectif.

Une application plus courante des rappels est de définir l'état de la connexion uniquement lorsqu'une nouvelle connexion est établie (par connect() ou connect_cached()). Ajouter un rappel à la méthode connected (lors de l'utilisation de "connect") ou via "connect_cached.connected" (lors de l'utilisation de connect_cached()>) facilite cela. La méthode connected() est une opération vide par défaut (sauf si vous sous-classez le DBI et la modifiez). Le DBI l'appelle pour indiquer qu'une nouvelle connexion a été établie et que les attributs de connexion ont tous été définis. Vous pouvez lui donner un peu de fonctionnalité supplémentaire en lui appliquant un rappel. Par exemple, pour vous assurer que MySQL comprend le SQL conforme à ANSI de votre application, configurez-le ainsi :

my $dbh = DBI->connect($dsn, $username, $auth, {
    Callbacks => {
        connected => sub {
            shift->do(q{
                SET SESSION sql_mode='ansi,strict_trans_tables,no_auto_value_on_zero';
            });
            return;
        },
    }
});

Si vous utilisez connect_cached(), utilisez plutôt le rappel "connect_cached.connected" . C'est parce que connected() est appelé pour les nouvelles poignées de base de données ainsi que pour celles réutilisées, mais vous ne voulez exécuter un rappel que lorsqu'une nouvelle poignée de base de données est retournée. Par exemple, pour définir le fuseau horaire lors de la connexion à une base de données PostgreSQL, essayez ceci :

my $cb = {
    'connect_cached.connected' => sub {
        shift->do('SET timezone = UTC');
    }
};
sub dbh {
    my $self = shift;
    DBI->connect_cached( $dsn, $username, $auth, { Callbacks => $cb });
}

Une limitation importante des rappels est qu'il ne peut y en avoir qu'un par méthode par poignée. Cela signifie qu'il est facile pour une utilisation des rappels d'interférer avec, ou plus généralement de simplement écraser, une autre utilisation des rappels. Pour cette raison, les modules utilisant des rappels doivent documenter clairement ce fait afin que les auteurs d'applications puissent savoir si l'utilisation des rappels par le module entrera en conflit avec l'utilisation des rappels par l'application.

Vous pourriez contourner ce problème en prenant une copie du rappel original et en l'appelant dans le vôtre. Par exemple :

my $prev_cb = $h->{Callbacks}{method_name};
$h->{Callbacks}{method_name} = sub {
  if ($prev_cb) {
      my @result = $prev_cb->(@_);
      return @result if not $_; # $prev_cb vetoed call
  }
  ... your callback logic here ...
};

Avertissement à l'acheteur : Ce cache peut être utile dans certaines applications, mais il peut aussi causer des problèmes et doit être utilisé avec précaution. Voici un cas artificiel où le cache causerait un problème significatif

: 
my $sth = $dbh->prepare_cached('SELECT * FROM foo WHERE bar=?');
$sth->execute(...);
while (my $data = $sth->fetchrow_hashref) {
  # plus tard, dans un autre code appelé dans la boucle...
  my $sth2 = $dbh->prepare_cached('SELECT * FROM foo WHERE bar=?');
  $sth2->execute(...);
  while (my $data2 = $sth2->fetchrow_arrayref) {
    do_stuff(...);
  }
}

Dans cet exemple, puisque les deux descripteurs préparent exactement la même instruction, $sth2 ne sera pas son propre descripteur d'instruction, mais un duplicata de $sth retourné depuis le cache. Les résultats ne seront certainement pas ceux que vous attendez. Typiquement la boucle de récupération interne fonctionnera normalement, récupérant tous les enregistrements et se terminant quand il n'y en a plus, mais maintenant que $sth est le même que $sth2 la boucle de récupération externe se terminera

aussi.

Vous saurez que vous rencontrez ce problème parce que prepare_cached() générera un avertissement par défaut (quand $if_active est faux)

.

Le cache utilisé par prepare_cached() est indexé à la fois par l'instruction et par tous les attributs, vous pouvez donc aussi éviter ce problème en faisant quelque chose comme

$sth = $dbh->prepare_cached("...", { dbi_dummy => __FILE__.__LINE__ })
;

ce qui garantira que prepare_cached ne retourne que les instructions mises en cache par cette ligne de code dans ce fichier

source.

De plus, pour garantir que les attributs passés sont toujours les mêmes, évitez de passer des références en ligne. Par exemple, l'attribut Slice est spécifié comme une référence. Assurez-vous de la déclarer à l'extérieur de l'appel à prepare_cached(), de telle sorte qu'une nouvelle référence de hachage ne soit pas créée à chaque appel. Voir "connect_cached" pour plus de détails et

d'exemples.

"disconnect"

errstr;

Déconnecte la base de données du descripteur de base de données. "disconnect" n'est typiquement utilisé qu'avant de quitter le programme. Le descripteur est de peu d'utilité après la

déconnexion.

Le comportement transactionnel de la méthode "disconnect" est, hélas, indéfini. Certains systèmes de base de données (comme Oracle et Ingres) commitent automatiquement tout changement en attente, mais d'autres (comme Informix) annulent tout changement en attente. Les applications qui n'utilisent pas "AutoCommit" devraient appeler explicitement "commit" ou "rollback" avant d'appeler "disconnect"

La base de données est automatiquement déconnectée par la méthode "DESTROY" si elle est toujours connectée quand il n'y a plus aucune référence au descripteur. La méthode "DESTROY" de chaque pilote devrait appeler implicitement "rollback" pour annuler tout changement non commité. C'est un comportement vital pour garantir que des transactions incomplètes ne soient pas commitées simplement parce que Perl appelle "DESTROY" sur chaque objet avant de quitter. De plus, ne comptez pas sur l'ordre de destruction des objets pendant la "global destruction", car il est

indéfini.

Généralement, si vous voulez que vos changements soient commités ou annulés quand vous vous déconnectez, vous devriez appeler explicitement "commit" ou "rollback" avant de vous

déconnecter.

Si vous vous déconnectez d'une base de données alors que vous avez encore des descripteurs d'instruction actifs (par ex., des descripteurs d'instruction SELECT qui peuvent avoir plus de données à récupérer), vous obtiendrez un avertissement. actifs.

Méthodes du gestionnaire de

DBI définit les méthodes suivantes pour une utilisation sur les gestionnaires de requêtes DBI

"bind_param"

La méthode "bind_param" prend une copie de $bind_value et l'associe (le lie) à un espace réservé, identifié par $p_num, intégré dans la requête préparée. Les espaces réservés sont indiqués par le caractère point d'interrogation ("?"). Par exemple

: 
$dbh->{RaiseError} = 1;        # évite de devoir vérifier chaque appel de méthode
$sth = $dbh->prepare("SELECT name, age FROM people WHERE name LIKE ?");
$sth->bind_param(1, "John%");  # les espaces réservés sont numérotés à partir de 1
$sth->execute;
DBI::dump_results($sth)
;

Voir "Placeholders and Bind Values" pour plus

d'informations.

Types de données pour les espaces

réservés

Le paramètre "\%attr" peut être utilisé pour indiquer le type de données que l'espace réservé devrait avoir. C'est rarement nécessaire. En général, le pilote est seulement intéressé par le fait de savoir si l'espace réservé doit être lié comme un nombre ou une

chaîne. 
$sth->bind_param(1, $value, { TYPE => SQL_INTEGER })
;

Comme raccourci pour le cas courant, le type de données peut être passé directement, à la place de la référence de hachage "\%attr". Cet exemple est équivalent au précédent

: 
$sth->bind_param(1, $value, SQL_INTEGER)
;

La valeur "TYPE" indique le type standard (non spécifique au pilote) pour ce paramètre. Pour spécifier le type spécifique au pilote, le pilote peut prendre en charge un attribut spécifique au pilote, tel que "{ ora_type =>

97 }".

SQL_INTEGER et les autres constantes associées peuvent être importées en

utilisant

;

Voir "DBI Constants" pour plus

d'informations.

Le type de données est « collant » en ce sens que les valeurs de liaison passées à execute() sont liées avec le type de données spécifié par les appels bind_param() précédents, s'il y en a. Les applications portables ne doivent pas compter sur la possibilité de changer le type de données après le premier appel "bind_p

aram".

Perl n'a que les types de données scalaire chaîne et nombre. Tous les types de base de données qui ne sont pas des nombres sont liés comme des chaînes et doivent être dans un format que la base de données comprendra, sauf lorsque l'attribut TYPE de bind_param() spécifie un type qui implique un format particulier. Par exemple, étant donné

;

le pilote devrait s'attendre à ce que $value soit dans le format SQL_DATETIME standard ODBC, qui est 'AAAA-MM-JJ HH:MM:SS'. De même pour SQL_DATE, SQL_TIME,

etc.

: 
INSERT INTO price(code, price) VALUES (?, CONVERT(MONEY,?)

d'informations.

"bind_param_inout"

$rc = $sth->bind_param_inout($p_num, \$bind_value, $max_len)  or die $sth->errstr;
$rv = $sth->bind_param_inout($p_num, \$bind_value, $max_len, \%attr)     or ...
$rv = $sth->bind_param_inout($p_num, \$bind_value, $max_len, $bind_type) or ..
.

Cette méthode agit comme "bind_param", mais permet aussi de mettre à jour des valeurs par la requête. La requête est typiquement un appel à une procédure stockée. Le $bind_value doit être passé comme une référence à la valeur réelle à

utiliser.

Contrairement à "bind_param", notez que la variable $bind_value n'est pas copiée quand "bind_param_inout" est appelé. À la place, la valeur dans la variable est lue au moment où "execute" est

appelé.

Le paramètre supplémentaire $max_len spécifie la quantité minimale de mémoire à allouer pour $bind_value pour la nouvelle valeur. Si la valeur retournée par la base de données est trop grande pour tenir, alors l'exécution devrait échouer. Si vous n'êtes pas sûr de la valeur à utiliser, choisissez une longueur généreuse, c'est-à-dire une longueur supérieure à la valeur la plus longue qui pourrait jamais être retournée. Le seul coût d'utilisation d'une valeur plus grande que nécessaire est une mémoire

gaspillée.

Les valeurs indéfinies ou "undef" sont utilisées pour indiquer des valeurs nulles. Voir aussi "Placeholders and Bind Values" pour plus

d'informations.

"bind_param_array"

$rc = $sth->bind_param_array($p_num, $array_ref_or_value)
$rc = $sth->bind_param_array($p_num, $array_ref_or_value, \%attr)
$rc = $sth->bind_param_array($p_num, $array_ref_or_value,
$bind_type)

La méthode "bind_param_array" est utilisée pour lier un tableau de valeurs à un espace réservé intégré dans la requête préparée qui sera exécutée avec "execute_array". Par exemple

: 
$dbh->{RaiseError} = 1;        # évite de devoir vérifier chaque appel de méthode
$sth = $dbh->prepare("INSERT INTO staff (first_name, last_name, dept) VALUES(?, ?, ?)");
$sth->bind_param_array(1, [ 'John', 'Mary', 'Tim' ]);
$sth->bind_param_array(2, [ 'Booth', 'Todd', 'Robinson' ]);
$sth->bind_param_array(3, "SALES"); # le scalaire sera réutilisé pour chaque ligne
$sth->execute_array( { ArrayTupleStatus => \my @tuple_status } )
;

L'argument %attr ($bind_type) est le même que celui défini pour "bind_param". Reportez-vous à "bind_param" pour les détails généraux sur l'utilisation des espaces

réservés.

(Notez que bind_param_array() ne peut pas être utilisé pour développer un espace réservé en une liste de valeurs pour une requête telle que "SELECT foo WHERE bar IN (?)". Un espace réservé ne peut toujours représenter qu'une valeur par exécution.

)

Les valeurs scalaires, y compris "undef", peuvent aussi être liées par "bind_param_array". Dans ce cas, la même valeur sera utilisée pour chaque appel "execute". Les implémentations spécifiques au pilote peuvent se comporter différemment, par exemple, lors de la liaison à un appel de procédure stockée, certaines bases de données peuvent permettre de mélanger des scalaires et des tableaux comme

arguments.

L'implémentation par défaut fournie par DBI (pour les pilotes qui n'ont pas implémenté la liaison de tableaux) consiste à appeler "execute" de manière itérative pour chaque tuple de paramètres fourni dans les tableaux liés. Les pilotes peuvent fournir des implémentations plus optimisées en utilisant n'importe quelle prise en charge d'opérations groupées que l'API de la base de données fournit. Le comportement par défaut du pilote devrait correspondre au comportement par défaut de DBI, mais consultez toujours la documentation de votre pilote car il peut y avoir des problèmes spécifiques au pilote à

considérer.

Notez que l'implémentation par défaut ne prend actuellement en charge que les requêtes qui ne retournent pas de données (INSERT, UPDATE, mais pas SELECT). De plus, "bind_param_array" et "bind_param" ne peuvent pas être mélangés dans la même exécution de requête, et "bind_param_array" doit être utilisé avec "execute_array" ; utiliser "bind_param_array" n'aura aucun effet pour

"execute".

La méthode "bind_param_array" a été ajoutée dans DBI 1.

22.

"execute"

$rv = $sth->execute                or die $sth->errstr;
$rv = $sth->execute(@bind_values)  or die $sth->
errstr;

Effectue tout le traitement nécessaire pour exécuter la requête préparée. Un "undef" est retourné si une erreur se produit. Un "execute" réussi retourne toujours vrai quel que soit le nombre de lignes affectées, même si c'est zéro (voir ci-dessous). Il est toujours important de vérifier le statut de retour de "execute" (et de la plupart des autres méthodes DBI) pour les erreurs si vous n'utilisez pas

"RaiseError".

Pour une requête non"SELECT", "execute" retourne le nombre de lignes affectées, si connu. Si aucune ligne n'a été affectée, alors "execute" retourne"0E0", que Perl traitera comme 0 mais considérera comme vrai. Notez que ce n'est pas une erreur qu'aucune ligne ne soit affectée par une requête. Si le nombre de lignes affectées n'est pas connu, alors "execute" retourne

-1.

Pour les requêtes "SELECT", execute « démarre » simplement la requête au sein du moteur de base de données. Utilisez l'une des méthodes de récupération pour récupérer les données après avoir appelé "execute". La méthode "execute" ne retourne pas le nombre de lignes que la requête retournera (car la plupart des bases de données ne peuvent pas le dire à l'avance), elle retourne simplement une valeur

vraie.

Vous pouvez savoir si la requête était une requête "SELECT" en vérifiant si "$sth->{NUM_OF_FIELDS}" est supérieur à zéro après avoir appelé "execute"

.

Si des arguments sont donnés, alors "execute" appellera effectivement "bind_param" pour chaque valeur avant d'exécuter la requête. Les valeurs liées de cette manière sont généralement traitées comme des types "SQL_VARCHAR" sauf si le pilote peut déterminer le type correct (ce qui est rare), ou sauf si "bind_param" (ou "bind_param_inout") a déjà été utilisé pour spécifier le

type.

Notez que passer à "execute" un tableau vide revient à ne passer aucun argument du tout, ce qui exécutera la requête avec les valeurs liées précédemment.ce n'est probablement pas ce que vous voulez.

Si execute() est appelé sur un descripteur de requête qui est encore actif ($sth->{Active} est vrai), alors il devrait effectivement appeler finish() pour nettoyer les résultats de l'exécution précédente avant de commencer cette nouvelle exécution.

"execute_array"

$tuples = $sth->execute_array(\%attr) or die $sth->errstr;
$tuples = $sth->execute_array(\%attr, @bind_values) or die $sth->errstr;
($tuples, $rows) = $sth->execute_array(\%attr) or die $sth->errstr;
($tuples, $rows) = $sth->execute_array(\%attr, @bind_values) or die $sth->errstr;

Exécute la requête préparée une fois pour chaque tuple de paramètres (groupe de valeurs) fourni soit dans @bind_values, soit par des appels précédents à "bind_param_array", ou via une référence passée dans \%attr.

Lorsqu'elle est appelée en contexte scalaire, la méthode execute_array() renvoie le nombre de tuples exécutés, ou "undef" si une erreur s'est produite. Comme execute(), un execute_array() réussi renvoie toujours vrai quel que soit le nombre de tuples exécutés, même s'il est égal à zéro. S'il y a eu des erreurs, le tableau ArrayTupleStatus peut être utilisé pour découvrir quels tuples ont échoué et avec quelles erreurs.

Lorsqu'elle est appelée en contexte liste, la méthode execute_array() renvoie deux scalaires; $tuples est le même que l'appel de execute_array() en contexte scalaire et $rows est le nombre de lignes affectées pour chaque tuple, si disponible, ou -1 si le pilote ne peut pas le déterminer. NOTE, certains pilotes ne peuvent pas déterminer le nombre de lignes affectées par tuple mais peuvent fournir le nombre de lignes affectées pour le lot. Si vous effectuez une opération de mise à jour, le nombre de lignes affectées renvoyé peut ne pas être celui que vous attendez si, par exemple, un ou plusieurs des tuples ont affecté la même ligne plusieurs fois. Certains pilotes peuvent ne pas encore supporter le contexte liste, auquel cas $rows sera undef, ou peuvent ne pas être en mesure de fournir le nombre de lignes affectées lors de l'exécution de cette opération par lot, auquel cas $rows sera -1.

Les valeurs de liaison pour les tuples à exécuter peuvent être fournies ligne par ligne via un attribut "ArrayTupleFetch" , ou colonne par colonne dans l'argument @bind_values , ou colonne par colonne via des appels précédents à "bind_param_array".

Lorsque la liaison colonne par colonne est utilisée (via l'argument @bind_values ou des appels à bind_param_array()), le nombre maximal d'éléments dans l'un des tableaux de valeurs liées détermine le nombre de tuples exécutés. Les emplacements réservés ayant moins de valeurs dans leurs tableaux de paramètres sont traités comme s'ils étaient complétés par des valeurs undef (NULL).

Si une valeur scalaire est liée, au lieu d'une référence de tableau, elle est traitée comme un tableau à longueur variable dont tous les éléments ont la même valeur. Cela n'influence pas le nombre de tuples exécutés, donc si tous les tableaux liés ont zéro élément, zéro tuple sera exécuté. Si toutes les valeurs liées sont des scalaires, alors un tuple sera exécuté, faisant que execute_array() se comporte exactement comme execute().

L'attribut "ArrayTupleFetch" peut être utilisé pour spécifier une référence vers une sous-routine qui sera appelée pour fournir les valeurs de liaison pour chaque exécution de tuple. La sous-routine doit renvoyer une référence vers un tableau qui contient le nombre approprié de valeurs de liaison, ou renvoyer un undef s'il n'y a plus de données à exécuter.

Par commodité, l'attribut "ArrayTupleFetch" peut aussi être utilisé pour spécifier un descripteur de requête. Dans ce cas, la méthode fetchrow_arrayref() sera appelée sur le descripteur de requête donné afin de fournir les valeurs de liaison pour chaque exécution de tuple.

Les valeurs spécifiées via bind_param_array() ou le paramètre @bind_values peuvent être soit des scalaires, soit des références de tableau. Si des @bind_values sont données, alors "execute_array" appellera effectivement "bind_param_array" pour chaque valeur avant d'exécuter la requête. Les valeurs liées de cette manière sont généralement traitées comme des types "SQL_VARCHAR" sauf si le pilote peut déterminer le type correct (ce qui est rare), ou sauf si "bind_param", "bind_param_inout", "bind_param_array", ou "bind_param_inout_array" a déjà été utilisé pour spécifier le type. Voir "bind_param_array" pour plus de détails.

L'attribut "ArrayTupleStatus" peut être utilisé pour spécifier une référence vers un tableau qui recevra le statut d'exécution de chaque tuple de paramètres exécuté. Notez que l'attribut "ArrayTupleStatus" était obligatoire jusqu'à DBI 1.38.

Pour les tuples exécutés avec succès, l'élément à la même position ordinale dans le tableau de statut est le compte de lignes résultant (ou -1 si inconnu). Si l'exécution d'un tuple provoque une erreur, alors l'élément correspondant du tableau de statut sera défini à une référence vers un tableau contenant "err", "errstr" et "state" définis par l'exécution échouée.

Si une exécution de tuple renvoie une erreur, "execute_array" renverra "undef". Dans ce cas, l'application devrait inspecter le tableau de statut pour déterminer quels tuples de paramètres ont échoué. Certaines bases de données peuvent ne pas continuer à exécuter les tuples au-delà du premier échec. Dans ce cas, le tableau de statut contiendra soit moins d'éléments, soit les éléments au-delà de l'échec seront undef.

Si tous les tuples de paramètres sont exécutés avec succès, "execute_array" renvoie le nombre de tuples exécutés. Si aucun tuple n'a été exécuté, alors execute_array() renvoie "0E0", tout comme execute() le fait, ce que Perl traitera comme 0 mais considérera comme vrai.

Par exemple :

$sth = $dbh->prepare("INSERT INTO staff (first_name, last_name) VALUES (?, ?)");
my $tuples = $sth->execute_array(
    { ArrayTupleStatus => \my @tuple_status },
    \@first_names,
    \@last_names,
);
if ($tuples) {
    print "Successfully inserted $tuples records\n";
}
else {
    for my $tuple (0..@last_names-1) {
        my $status = $tuple_status[$tuple];
        $status = [0, "Skipped"] unless defined $status;
        next unless ref $status;
        printf "Failed to insert (%s, %s): %s\n",
            $first_names[$tuple], $last_names[$tuple], $status->[1];
    }
}

La prise en charge des requêtes retournant des données telles que SELECT est spécifique au pilote et susceptible de changer. Actuellement, l'implémentation par défaut fournie par DBI ne prend en charge que les requêtes ne retournant pas de données.

La sémantique des transactions lors de l'utilisation de la liaison par tableau est spécifique au pilote et à la base de données. Si "AutoCommit" est activé, l'implémentation par défaut de DBI fera en sorte que chaque tuple de paramètres soit individuellement validé (ou annulé en cas d'erreur). Si "AutoCommit" est désactivé, l'application est responsable de valider explicitement l'ensemble des tuples de paramètres liés. Notez que différents pilotes et bases de données peuvent avoir des comportements différents lorsque certains tuples de paramètres provoquent des échecs. Dans certains cas, le pilote ou la base de données peut automatiquement annuler l'effet de tous les tuples de paramètres précédents qui ont réussi dans la transaction; d'autres pilotes ou bases de données peuvent conserver l'effet des tuples de paramètres précédemment exécutés avec succès. Assurez-vous de vérifier votre pilote et votre base de données pour son comportement spécifique.

Notez que, en général, les performances seront généralement meilleures avec "AutoCommit" désactivé, et en utilisant une validation explicite "commit" après chaque "execute_array" appel.

La méthode "execute_array" a été ajoutée dans DBI 1.22, et ArrayTupleFetch a été ajouté dans 1.36.

"execute_for_fetch"

$tuples = $sth->execute_for_fetch($fetch_tuple_sub);
$tuples = $sth->execute_for_fetch($fetch_tuple_sub, \@tuple_status);
($tuples, $rows) = $sth->execute_for_fetch($fetch_tuple_sub);
($tuples, $rows) = $sth->execute_for_fetch($fetch_tuple_sub, \@tuple_status);

La méthode execute_for_fetch() est utilisée pour effectuer des opérations par lot et bien qu'elle soit le plus souvent utilisée via la méthode execute_array() vous pouvez l'utiliser directement. La principale différence entre execute_array et execute_for_fetch est que le premier effectue une liaison colonne par colonne ou ligne par ligne et le dernier utilise une liaison ligne par ligne.

La sous-routine de récupération, référencée par $fetch_tuple_sub, est censée renvoyer une référence vers un tableau (connu sous le nom de 'tuple') ou undef.

La méthode execute_for_fetch() appelle $fetch_tuple_sub, sans aucun paramètre, jusqu'à ce qu'elle renvoie une valeur fausse. Chaque tuple renvoyé est utilisé pour fournir des valeurs de liaison pour un appel $sth->execute(@$tuple).

En contexte scalaire, execute_for_fetch() renvoie "undef" s'il y a eu des erreurs et le nombre de tuples exécutés sinon. Comme execute() et execute_array() un zéro est renvoyé sous la forme "0E0" afin que execute_for_fetch() ne soit faux qu'en cas d'erreur. S'il y a eu des erreurs le tableau @tuple_status peut être utilisé pour découvrir quels tuples ont échoué et avec quelles erreurs.

Lorsqu'elle est appelée en contexte liste, execute_for_fetch() renvoie deux scalaires; $tuples est le même que l'appel de execute_for_fetch() en contexte scalaire et $rows est la somme du nombre de lignes affectées pour chaque tuple, si disponible, ou -1 si le pilote ne peut pas le déterminer. Si vous effectuez une opération de mise à jour, le nombre de lignes affectées renvoyé peut ne pas être celui que vous attendez si, par exemple, un ou plusieurs des tuples ont affecté la même ligne plusieurs fois. Certains pilotes peuvent ne pas encore supporter le contexte liste, auquel cas $rows sera undef, ou peuvent ne pas être en mesure de fournir le nombre de lignes affectées lors de l'exécution de cette opération par lot, auquel cas $rows sera -1.

Si \@tuple_status est passé, alors la méthode execute_for_fetch l'utilise pour renvoyer des informations de statut. Le tableau tuple_status contient un élément par tuple. Si le execute() correspondant n'a pas échoué, alors l'élément contient la valeur de retour de execute(), qui est généralement un compte de lignes. Si le execute() a échoué, alors l'élément contient une référence vers un tableau contenant ($sth->err, $sth->errstr, $sth->state).

Si le pilote détecte une erreur qu'il sait signifier que aucun autre tuple ne peut être exécuté, alors il peut renvoyer, avec unn statut d'erreur, même si $fetch_tuple_sub peut encore avoir plus de tuples à

exécuter.

Récupère toutes les lignes depuis $sth, appelle "DBI::neat_list" pour chaque ligne, et imprime les résultats vers $fh (par défaut "STDOUT") séparés par $lsep (par défaut "\n"). $fsep vaut par défaut ", " et $maxlen vaut par défaut

35.

Cette méthode est conçue comme une utilitaire pratique pour le prototypage et le test de

requêtes. Comme elle utilise "neat_list" pour formater et éditer la chaîne pour une lectu
re par des humains, elle n'est pas recommandée pour les applications de transfert de données.

"ParamTypes"

Type : hash ref, lecture seule

Renvoie un pointeur vers un hash contenant les informations de type actuellement liées aux paramètres. Renvoie undef si le pilote ne le prend pas en charge.

* Clés :

Voir "ParamValues" ci-dessus.

* Valeurs :

Les valeurs du hash sont des pointeurs vers des hash d'informations de type sous la même forme que celle passée aux différentes méthodes bind_param() (Voir "bind_param" pour le format et les valeurs).

Il est possible que les valeurs du hash renvoyé par "ParamTypes" ne soient pas exactement les mêmes que celles passées à bind_param() ou execute(). Les attributs de paramètre spécifiés sous la forme abrégée, comme ceci :

$sth->bind_param(1, SQL_INTEGER);

sont renvoyés sous la forme développée, comme s'ils étaient appelés ainsi :

$sth->bind_param(1, { TYPE => SQL_INTEGER });

Le pilote peut avoir modifié les informations de type d'une certaine manière en fonction des valeurs liées, d'autres indices fournis par la requête SQL prepare()'ée, ou des correspondances de type alternatives requises par le pilote ou le système de base de données cible. Le pilote peut également ajouter des clés privées (avec des noms commençant par le préfixe réservé au pilote, par exemple, odbc_xxx).

* Exemple :

Les clés et valeurs du hash renvoyé peuvent être passées aux différentes méthodes bind_param() pour reproduire efficacement une liaison de paramètre précédente. Par exemple :

# assuming $sth1 is a previously prepared statement handle
my $sth2 = $dbh->prepare( $sth1->{Statement} );
my $ParamValues = $sth1->{ParamValues} || {};
my $ParamTypes  = $sth1->{ParamTypes}  || {};
$sth2->bind_param($_, $ParamValues->{$_}, $ParamTypes->{$_})
  for keys %{ {%$ParamValues, %$ParamTypes} };
$sth2->execute();

L'attribut "ParamTypes" a été ajouté dans DBI 1.49. L'implémentation est la responsabilité des pilotes individuels ; l'implémentation par défaut de la couche DBI renvoie simplement undef.

Type : hash ref, lecture seule

Renvoie un pointeur vers un hash contenant les valeurs actuellement liées aux paramètres avec "execute_array" ou "bind_param_array". Les clés du hash sont les 'noms' des paramètres, généralement des entiers commençant à 1. Renvoie undef si le pilote ne le prend pas en charge ou si aucun tableau de paramètres n'est lié.

Chaque valeur de clé est un pointeur vers un tableau contenant une liste des paramètres liés pour cette colonne.

Le pilote peut avoir légèrement modifié les valeurs d'une certaine manière en fonction du TYPE avec lequel la valeur a été liée. Par exemple, une valeur en virgule flottante liée en tant que type SQL_INTEGER peut être renvoyée comme un entier.

Il est également possible que les clés du hash renvoyé par "ParamArrays" ne soient pas exactement les mêmes que celles impliquées par la requête préparée. Par exemple, DBD::Oracle traduit les paramètres '"?"' en '":pN"' où N est un numéro de séquence commençant à 1.

INFORMATIONS COMPLÉMENTAIRES

Méthodes de catalogue

Une application peut récupérer des métadonnées du SGBD en émettant des requêtes appropriées sur les vues du schéma d'information. Malheureusement, les vues "INFORMATION_SCHEMA" sont rarement prises en charge par le SGBD. Des méthodes spéciales (méthodes de catalogue) sont disponibles pour renvoyer des ensembles de résultats pour une petite mais importante partie de ces métadonnées :

column_info
foreign_key_info
primary_key_info
table_info
statistics_info

Toutes les méthodes de catalogue acceptent des arguments afin de restreindre les ensembles de résultats. Passer "undef" à un argument facultatif ne restreint pas la recherche pour cet argument. Cependant, une chaîne vide ('') est traitée comme un critère de recherche normal et ne correspondra qu'à une valeur vide.

Note: SQL/CLI et ODBC diffèrent dans le traitement des chaînes vides. Une chaîne vide ne restreindra pas l'ensemble des résultats dans SQL/CLI.

La plupart des arguments des méthodes de catalogue n'acceptent que des valeurs ordinaires, par exemple les arguments de primary_key_info(). De tels arguments sont traités comme une chaîne littérale, c'est-à-dire que la casse est significative et que les caractères de guillemets sont pris littéralement.

Certains arguments des méthodes de catalogue acceptent des motifs de recherche (chaînes contenant '_' et/ou '%'), par exemple l'argument $table de column_info(). Passer '%' est équivalent à laisser l'argument "undef".

Avertissement: Le soulignement ('_') est valide et souvent utilisé dans les identifiants SQL. Passer une telle valeur à un argument de motif de recherche peut renvoyer plus de lignes que prévu ! Pour inclure des caractères de motif littéraux, ils doivent être précédés d'un caractère d'échappement, ce qui peut être obtenu avec

$esc = $dbh->get_info( 14 );  # SQL_SEARCH_PATTERN_ESCAPE
$search_pattern =~ s/([_%])/$esc$1/g;

Les spécifications ODBC et SQL/CLI définissent un moyen de changer le comportement par défaut décrit ci-dessus : Tous les arguments (sauf les arguments de valeur de liste) sont traités comme des identifiants si l'attribut "SQL_ATTR_METADATA_ID" est défini à "SQL_TRUE". Les identifiants entre guillemets sont très similaires aux valeurs ordinaires, c'est-à-dire que leur corps (la chaîne entre les guillemets) est interprété littéralement. Les identifiants sans guillemets sont comparés en MAJUSCULES.

DBI (actuellement) ne prend pas en charge l'attribut "SQL_ATTR_METADATA_ID" , c'est-à-dire qu'il se comporte comme un pilote ODBC où "SQL_ATTR_METADATA_ID" est défini à "SQL_FALSE".

Transactions

Les transactions sont une partie fondamentale de tout système de base de données robuste. Elles protègent contre les erreurs et la corruption de la base de données en s'assurant que des ensembles de modifications liées à la base de données ont lieu dans des unités atomiques (indivisibles, tout ou rien).

Cette section s'applique aux bases de données qui prennent en charge les transactions et où "AutoCommit" est désactivé. Voir "AutoCommit" pour les détails de l'utilisation de "AutoCommit" avec différents types de bases de données.

La manière recommandée d'implémenter des transactions robustes dans les applications Perl est d'activer "RaiseError" et de capturer l'erreur qui est 'jetée' comme une exception. Par exemple, avec Try::Tiny :

use Try::Tiny;

$dbh->{AutoCommit} = 0;  # activer les transactions, si possible
$dbh->{RaiseError} = 1;
try {
    foo(...)        # faire beaucoup de travail ici
    bar(...)        # y compris les insertions
    baz(...)        # et les mises à jour
    $dbh->commit;   # valider les changements si nous arrivons jusque-là
} catch {
    warn "Transaction annulée car $_"; # Try::Tiny copie $@ dans $_
    # maintenant annuler pour défaire les changements incomplets
    # mais le faire dans un eval{} car cela peut aussi échouer
    eval { $dbh->rollback };
    # ajouter ici d'autres codes de nettoyage en cas d'erreur de l'application
}
;

Si l'attribut "RaiseError" n'est pas défini, alors les appels DBI devraient être vérifiés manuellement pour les erreurs, typiquement comme ceci

: 
$h->method(@args) or die $h->
errstr;

Avec "RaiseError" défini, le DBI va automatiquement "die" si un appel de méthode DBI sur ce gestionnaire (ou un gestionnaire enfant) échoue, donc vous n'avez pas besoin de tester la valeur de retour de chaque appel de méthode. Voir "RaiseError" pour plus de

détails.

Un avantage majeur de l'approche "eval" est que la transaction sera correctement annulée si n'importe quel code (pas seulement les appels DBI) dans l'application interne meurt pour une raison quelconque. Le principal avantage d'utiliser l'attribut "$h->{RaiseError}" est que tous les appels DBI seront vérifiés automatiquement. Les deux techniques sont fortement

recommandées.

Après avoir appelé "commit" ou "rollback", de nombreux pilotes ne vous permettront pas de récupérer depuis une instruction "SELECT" préalablement active qui est un enfant du même gestionnaire de base de données. Une façon typique de contourner cela est de se connecter à la base de données deux fois et d'utiliser une connexion pour les instructions "SELECT"

.

Voir "AutoCommit" et "disconnec

t" pour d'autres informations im
portantes sur les transactions.

Gestion des champs BLOB / LONG /

Memo

De nombreuses bases de données supportent les types de données "blob" (objets binaires volumineux), "long" ou similaires pour stocker des chaînes très longues ou de grandes quantités de données binaires dans un seul champ. Certaines bases de données supportent des valeurs longues de longueur variable dépassant 2 000 000 000

tampon.

Voir la description de "LongReadLen" pour plus

d'informations.

Lors de la tentative d'insertion de valeurs longues ou binaires, des paramètres de liaison devraient être utilisés car il y a souvent des limites sur la taille maximale d'une instruction "INSERT" et la méthode "quote" ne peut généralement pas gére

r les données binaires. Voir "

Threads et sécurité des

threads

Perl 5.7 et les versions suivantes supportent un nouveau modèle de threads appelé iThreads. (Les anciens threads "style 5.005" ne sont pas supportés par le DBI.

)

Dans le modèle iThreads, chaque thread a sa propre copie de l'interpréteur perl. Quand un nouveau thread est créé, l'interpréteur perl original est 'cloné' pour créer une nouvelle copie pour le nouveau

thread.

Si le DBI et les pilotes sont chargés et les gestionnaires créés avant que le thread ne soit créé, alors il obtiendra une copie clonée du DBI, des pilotes et des

gestionnaires.

Cependant, les données de pointeur interne au sein des gestionnaires référenceront le DBI et les pilotes dans l'interpréteur original. Utiliser ces gestionnaires dans le nouveau thread de l'interpréteur n'est pas sûr, donc le DBI détecte cela et émet une erreur fatale sur tout appel de méthode utilisant des gestionnaires qui n'appartiennent pas au thread actuel (sauf pour DESTROY)

.

En raison de cette restriction (éventuellement temporaire), les threads nouvellement créés doivent établir leurs propres connexions à la base de données. Les gestionnaires ne peuvent pas être partagés entre les

threads.

Mais ATTENTION, certaines API de base de données sous-jacentes (le code que le pilote DBD utilise pour communiquer avec la base de données, souvent fourni par le fournisseur de la base de données) ne sont pas sûres pour les threads. Si ce n'est pas sûr pour les threads, alors permettre à plus d'un thread d'entrer dans le code en même temps peut causer des problèmes subtils/graves. Dans certains cas, permettre à plus d'un thread d'entrer dans le code, même si ce n'est pas en même temps, peut causer des problèmes. Vous avez été

averti.

L'utilisation du DBI avec les threads perl n'est pas encore recommandée pour les environnements de production. Pour plus d'informations voir http://www.perlmonks.org/index.pl?

node_id=288022

Note : Il y a un bug dans perl 5.8.2 quand configuré avec les threads et le débogage activés (bug #24463) qui causerait l'échec de certains tests DBI. Ces tests ont été désactivés pour perl-5.8.2 et les versions

antérieures.

Les tests pour le cache de méthode interne sont désactivés pour perl-5.

Gestion des signaux et annulation des

opérations

[Ce qui suit ne s'applique qu'aux systèmes avec gestion de signaux de type unix. J'accueillerais des ajouts pour d'autres systèmes, en particulier Windows.

]

La première chose à dire est que la gestion des signaux dans les versions de Perl antérieures à 5.8 n'est pas sûre. Il y a toujours un petit risque que Perl plante et/ou génère un core dump quand, ou après, avoir traité un signal car le signal pourrait arriver et être traité pendant que les structures de données internes sont en cours de modification. Si le code de gestion du signal utilisait ces mêmes structures de données internes, cela pourrait causer toutes sortes de problèmes subtils et moins subtils. Le risque a été réduit avec 5.4.4 mais était encore présent dans toutes les versions de perl jusqu'à 5.8.

0.

À partir de perl 5.8.0, perl implémente une gestion de signaux 'sûre' si votre système a la routine POSIX sigaction(). Maintenant quand un signal est délivré, perl fait juste une note mais n'exécute pas le gestionnaire %SIG. Le traitement est 'différé' jusqu'à un moment

'sûr'.

Bien que ce changement ait rendu la gestion des signaux sûre, il a aussi conduit à un problème avec des signaux différés plus longtemps que vous ne le voudriez. Si un signal arrivait pendant l'exécution d'un appel système, comme l'attente de données sur une connexion réseau, le signal est noté puis l'appel système qui s'exécutait retourne avec un code d'erreur EINTR pour indiquer qu'il a été interrompu. Tout va bien

jusqu'ici.

Le problème vient quand le code qui a fait l'appel système voit le code EINTR et décide de le rappeler. Perl ne fait pas cela, mais le code de base de données le fait parfois. Si cela arrive, alors le gestionnaire de signal ne sera pas appelé jusqu'à plus tard. Peut-être beaucoup plus

tard.

Heureusement, il y a des moyens de contourner cela que nous discuterons ci-dessous. Malheureusement, ils rendent les signaux à nouveau non

sûrs.

Les deux utilisations les plus courantes des signaux en relation avec le DBI sont pour annuler des opérations quand l'utilisateur tape Ctrl-C (interrupt), et pour implémenter un délai d'attente en utilisant alarm() et $SIG{AL

RM}.
Annulat
ion
Le DBI fournit une méthode "cancel" pour les gestionnaires d'instructions. La méthode "cancel" devrait annuler l'opération en cours et est conçue pour être appelée depuis un gestionnaire de signal. Par exemple : 
$SIG{INT} = sub { $sth->cancel
};

Cependant, peu de pilotes implémentent cela (le DBI fournit une méthode par défaut qui retourne simplement "undef") et, même si c'est implémenté, il y a encore une possibilité que le gestionnaire d'instructions, et même le gestionnaire de base de données parent, ne seront pas utilisables par la

suite.

Si "cancel" retourne vrai, alors il a réussi à invoquer la fonction d'annulation du moteur de base de données. S'il retourne faux, alors "cancel" a échoué. S'il retourne "undef", alors le pilote de base de données n'a pas

implémenté la fonction d'an
nulation - très peu l'ont.
Délai
d'attente
La façon traditionnelle d'implémenter un délai d'attente est de définir $SIG{ALRM}n> pour référencer du code qui sera exécuté lorsqu'un signal ALRM arrive, puis pour appeler alarm($seconds) afin de planifier l'envoi d'un signal ALRM $seconds dans le futur. Par exemple : 
my $failed;
eval {
  local $SIG{ALRM} = sub { die "TIMEOUT\n" }; # N.B. \n requis
  eval {
    alarm($seconds);
    ... code à exécuter avec délai d'attente ici (qui peut mourir) ...
    1;
  } or $failed = 1;
  # l'eval externe attrape l'alarme qui pourrait se déclencher JUSTE avant cet alarm(0)
  alarm(0);  # annuler l'alarme (si le code s'est exécuté rapidement)
  die "$@" if $failed;
  1;
} or $failed = 1;
if ( $failed ) {
  if ( defined $@ and $@ eq "TIMEOUT\n" ) { ... }
  else { ... } # une autre erreur
}

Le premier (externe) eval est utilisé pour éviter la possibilité, bien que peu probable, que le "code à exécuter" meure et que l'alarme se déclenche avant d'être annulée. Sans l'eval externe, si cela se produisait, votre programme mourrait si vous n'avez pas de gestionnaire ALRM, ou un gestionnaire d'alarme non local serait appelé.

Malheureusement, comme décrit ci-dessus, cela ne fonctionnera pas toujours comme prévu, selon votre version de perl et le code de base de la base de données.

Avec Oracle par exemple (DBD::Oracle), si le système qui héberge la base de données est en panne, l'appel DBI->connect() restera bloqué pendant plusieurs minutes avant de retourner une erreur.

La solution sur ces systèmes est d'utiliser la routine POSIX::sigaction() pour obtenir un accès de bas niveau à la manière dont le gestionnaire de signal est installé.

Le code ressemblerait à quelque chose comme ceci (pour le connect()DBD-Oracle) :

use POSIX qw(:signal_h);
my $mask = POSIX::SigSet->new( SIGALRM ); # signaux à masquer dans le gestionnaire
my $action = POSIX::SigAction->new(
    sub { die "connect timeout\n" },        # la référence de code du gestionnaire
    $mask,
    # pas d'utilisation du commutateur 'safe' (perl 5.8.2 et ultérieur) ni de sa_flags
);
my $oldaction = POSIX::SigAction->new();
sigaction( SIGALRM, $action, $oldaction );
my $dbh;
my $failed;
eval {
   eval {
     alarm(5); # secondes avant le délai d'attente
     $dbh = DBI->connect("dbi:Oracle:$dsn" ... );
     1;
   } or $failed = 1;
   alarm(0); # annuler l'alarme (si la connexion a fonctionné rapidement)
   die "$@\n" if $failed; # la connexion est morte
   1;
} or $failed = 1;
sigaction( SIGALRM, $oldaction );  # restaurer le gestionnaire de signal original
if ( $failed ) {
  if ( defined $@ and $@ eq "connect timeout\n" ) {...}
  else { # la connexion est morte }
}

Voir l'exemple précédent pour la raison du double eval.

Des techniques similaires peuvent être utilisées pour annuler l'exécution d'une instruction.

Malheureusement, cette solution est quelque peu désordonnée, et elle ne fonctionne pas avec les versions de perl antérieures à perl 5.8 où POSIX::sigaction() semble être défectueux.

Pour une implémentation plus propre qui fonctionne avec toutes les versions de perl, voir le module Sys::SigAction de Lincoln Baxter à Sys::SigAction. La documentation de Sys::SigAction inclut une discussion plus longue sur ce problème, et un script de test DBD::Oracle.

Assurez-vous de lire toutes les sections sur la gestion des signaux du manuel perlipc.

Et enfin, deux autres points à garder fermement à l'esprit. Premièrement, rappelez-vous que ce que nous avons fait ici revient essentiellement à l'ancien style de gestion non sûre de ces signaux. Alors faites le moins possible dans le gestionnaire. Idéalement, juste die(). Deuxièmement, les descripteurs en cours d'utilisation au moment où le signal est traité peuvent ne pas être sûrs à utiliser par la suite.

Sous-classer le DBI

Le DBI peut être sous-classé et étendu comme n'importe quel autre module orienté objet. Avant de parler de la manière de le faire, il est important d'être clair sur les différentes classes DBI et comment elles fonctionnent ensemble.

Par défaut "$dbh = DBI->connect(...)" retourne un $dbh béni dans la classe "DBI::db" . Et la méthode "$dbh->prepare" retourne un $sth béni dans la classe "DBI::st" (en fait, elle change simplement les quatre derniers caractères de la classe du descripteur appelant pour être "::st").

Le '"DBI"' initial est connu comme la 'classe racine' et les '"::db"' ou '"::st"' supplémentaires sont les 'suffixes de type de descripteur'. Si vous voulez sous-classer le DBI, vous devrez mettre vos méthodes surchargées dans les classes appropriées. Par exemple, si vous voulez utiliser une classe racine de "MySubDBI" et surcharger les méthodes do(), prepare() et execute() , alors vos méthodes do() et prepare() devraient être dans la classe "MySubDBI::db" et la méthode execute() devrait être dans la classe "MySubDBI::st" .

Pour configurer la hiérarchie d'héritage, la variable @ISA dans "MySubDBI::db" devrait inclure "DBI::db" et la variable @ISA dans "MySubDBI::st" devrait inclure "DBI::st". La classe racine "MySubDBI" elle-même n'est actuellement utilisée pour rien de visible et donc, à part le fait de configurer @ISA pour inclure "DBI", elle peut rester vide.

Donc, après avoir mis vos méthodes surchargées dans les bonnes classes et configuré la hiérarchie d'héritage, comment faire pour que le DBI les utilise ? Vous avez deux choix, soit un appel de méthode statique utilisant le nom de votre sous-classe :

$dbh = MySubDBI->connect(...);

soit la spécification d'un attribut "RootClass" :

$dbh = DBI->connect(..., { RootClass => 'MySubDBI' });

Si les deux formes sont utilisées, l'attribut prend le dessus.

Les seules différences entre les deux sont que l'utilisation d'un attribut RootClass explicite fera a) que le DBI essaiera automatiquement de charger un module portant ce nom si la classe n'existe pas, et b) qu'il n'appellera pas votre méthode MySubDBI::connect() , si vous en avez une.

Lorsqu'une sous-classe est utilisée, après une nouvelle connexion réussie, la méthode DBI->connect appelle automatiquement :

$dbh->connected($dsn, $user, $pass, \%attr);

La méthode par défaut ne fait rien. L'appel est fait simplement pour simplifier toute configuration post-connexion que votre sous-classe voudrait effectuer. Les paramètres sont les mêmes que ceux passés à DBI->connect. Si votre sous-classe fournit une méthode connected, elle devrait faire partie du paquet MySubDBI::db.

Une autre chose à noter : vous devez laisser le DBI faire la création des descripteurs. Si vous voulez surcharger la méthode connect() dans votre classe *::dr alors elle doit quand même appeler SUPER::connect pour obtenir un $dbh avec lequel travailler. De même, une méthode prepare() surchargée dans *::db doit quand même appeler SUPER::prepare pour obtenir un $sth. Si vous essayez de créer vos propres descripteurs en utilisant bless() , vous découvrirez que le DBI les rejettera avec une erreur "is not a DBI handle (has no magic)".

Voici un bref exemple de sous-classe DBI. Un exemple plus complet peut être trouvé dans t/subclass.t dans la distribution DBI.

package MySubDBI;
use strict;
use DBI;
our @ISA = qw(DBI);
package MySubDBI::db;
our @ISA = qw(DBI::db);
sub prepare {
  my ($dbh, @args) = @_;
  my $sth = $dbh->SUPER::prepare(@args)
      or return;
  $sth->{private_mysubdbi_info} = { foo => 'bar' };
  return $sth;
}
package MySubDBI::st;
our @ISA = qw(DBI::st);
sub fetch {
  my ($sth, @args) = @_;
  my $row = $sth->SUPER::fetch(@args)
      or return;
  do_something_magical_with_row_data($row)
      or return $sth->set_err(1234, "The magic failed", undef, "fetch");
  return $row;
}

Lorsque vous appelez une méthode SUPER::method qui retourne un descripteur, soyez prudent et vérifiez la valeur de retour avant d'essayer de faire d'autres choses avec dans votre méthode surchargée. C'est particulièrement important si vous voulez définir un attribut de hachage sur le descripteur, car l'auto-vivification de Perl vous mordra en créant (in)convenablement une référence de hachage non bénie, que votre méthode retournera ensuite avec généralement des résultats déroutants plus tard, comme l'erreur "dbih_getcom handle HASH(0xa4451a8) is not a DBI handle (has no magic". Il est préférable de vérifier juste après l'appel et de retourner undef immédiatement en cas d'erreur, tout comme le DBI le ferait et tout comme l'exemple ci-dessus.

Si votre méthode doit enregistrer une erreur, elle devrait appeler la méthode set_err() avec le code d'erreur et la chaîne d'erreur, comme montré dans l'exemple ci-dessus. Le code d'erreur et la chaîne d'erreur seront enregistrés dans le descripteur et disponibles via "$h->err" et $DBI::errstr etc. La méthode set_err() retourne toujours undef ou une liste vide selon le cas. Puisque votre méthode devrait presque toujours retourner undef ou une liste vide dès qu'une erreur est détectée, il est pratique de simplement retourner ce que set_err() retourne, comme montré dans l'exemple ci-dessus.

Si le descripteur a "RaiseError", "PrintError", ou "HandleError" etc. défini, alors la méthode set_err() les respectera. Cela signifie que si "RaiseError" est défini, alors set_err() ne retournera pas de manière normale mais 'lèvera une exception' qui peut être attrapée avec un bloc "eval" .

Vous pouvez stocker des données privées dans les descripteurs DBI via "$h->{private_..._*}". Voir l'entrée sous "ATTRIBUTES COMMON TO ALL HANDLES" pour des informations et des mises en garde importantes.

Fuites de mémoire

Lors du suivi des fuites de mémoire à l'aide d'outils comme Devel::Leak, vous constaterez que certaines parties internes du DBI sont signalées comme 'fuyant' de la mémoire. C'est très peu probable que ce soit une vraie fuite. Le DBI a divers caches pour améliorer les performances et les fuites apparentes sont simplement le fonctionnement normal de ces caches.

Les sources les plus fréquentes des fuites apparentes sont "ChildHandles", "prepare_cached" et "connect_cached".

Par exemple http://stackoverflow.com/questions/13338308/perl-dbi-memory-leak

TRACAGE

Le DBI a un puissant mécanisme de tracageanisme intégré. Il vous permet de voir ce qui se passe « en coulisses », à la fois dans le DBI et dans les pilotes que vous utilisez.

Paramètres de traçage

Les détails écrits dans la sortie de traçage sont contrôlés par une combinaison d'un niveau de traçage, un entier de 0 à 15, et d'un ensemble de indicateurs de traçage qui sont soit activés, soit désactivés. Ensemble, ils sont connus comme les paramètres de traçage paramètres de traçage et sont stockés ensemble dans un entier unique. Pour une utilisation normale, vous n'avez besoin de définir que le niveau de traçage, et généralement seulement à une valeur comprise entre 1 et 4.

Chaque gestionnaire a ses propres paramètres de traçage, et le DBI aussi. Lorsque vous appelez une méthode, le DBI fusionne les paramètres du gestionnaire avec les siens pour la durée de l'appel : les indicateurs de traçage du gestionnaire sont combinés (OR) avec les indicateurs de traçage du DBI, et si le gestionnaire a un niveau de traçage plus élevé, le niveau de traçage du DBI est augmenté pour correspondre. Les paramètres de traçage précédents du DBI sont restaurés lorsque la méthode appelée se termine.

Niveaux de traçage

Les niveaux de traçage sont les suivants :

0 - Traçage désactivé.
1 - Trace les appels de méthodes DBI de premier niveau qui retournent des résultats ou des erreurs.
2 - Comme ci-dessus, en ajoutant le traçage de l'entrée des méthodes de premier niveau avec leurs paramètres.
3 - Comme ci-dessus, en ajoutant certaines informations de haut niveau du pilote
    et certaines informations internes du DBI.
4 - Comme ci-dessus, en ajoutant des informations plus détaillées du pilote.
    C'est le premier niveau qui trace toutes les lignes récupérées.
5 à 15 - Comme ci-dessus mais avec de plus en plus d'informations internes.

Le niveau de traçage 1 est le meilleur pour un aperçu simple de ce qui se passe. Les niveaux de traçage 2 à 4 sont un bon choix pour un traçage à usage général. Les niveaux 5 et supérieurs sont mieux réservés à l'investigation d'un problème spécifique, lorsque vous devez voir « à l'intérieur » du pilote et du DBI.

La sortie de traçage est détaillée et généralement très utile. Une grande partie de la sortie de traçage est formatée à l'aide de la fonction "neat", donc les chaînes dans la sortie de traçage peuvent être éditées et tronquées par cette fonction.

Indicateurs de traçage

Les indicateurs de traçage sont utilisés pour activer le traçage d'activités spécifiques au sein du DBI et des pilotes. Le DBI définit certains indicateurs de traçage et les pilotes peuvent en définir d'autres. Les noms d'indicateurs de traçage du DBI commencent par une lettre majuscule et les noms spécifiques aux pilotes commencent par une lettre minuscule, comme d'habitude.

Actuellement, le DBI définit ces indicateurs de traçage :

ALL - active tous les indicateurs du DBI et des pilotes (non recommandé)
SQL - trace les instructions SQL exécutées
      (pas encore implémenté dans le DBI mais implémenté dans certains DBD)
CON - trace le processus de connexion
ENC - trace l'encodage (traductions unicode etc.)
      (pas encore implémenté dans le DBI mais implémenté dans certains DBD)
DBD - trace uniquement les messages DBD
      (pas encore implémenté par tous les DBD)
TXN - trace les transactions
      (pas encore implémenté dans tous les DBD)

Les méthodes "parse_trace_flags" et "parse_trace_flag" sont utilisées pour convertir les noms d'indicateurs de traçage en indicateurs de bits entiers correspondants.

Activation du traçage

La "$h->trace" méthode définit les paramètres de traçage pour un gestionnaire et "DBI->trace" fait de même pour le DBI.

En plus de la méthode "trace", vous pouvez activer les mêmes informations de traçage et diriger la sortie vers un fichier en définissant la variable d'environnement "DBI_TRACE" avant de démarrer Perl. Voir "DBI_TRACE" pour plus d'informations.

Enfin, vous pouvez définir ou obtenir les paramètres de traçage d'un gestionnaire à l'aide de l'attribut "TraceLevel" .

Toutes ces méthodes utilisent parse_trace_flags() et vous permettent donc de définir à la fois le niveau de traçage et plusieurs indicateurs de traçage en utilisant une chaîne contenant le niveau de traçage et/ou les noms d'indicateurs séparés par une barre verticale (""|"") ou une virgule ("",""). Par exemple :

local $h->{TraceLevel} = "3|SQL|foo";

Sortie de traçage

Initialement, la sortie de traçage est écrite vers "STDERR". Les méthodes "$h->trace" et "DBI->trace" prennent un paramètre optionnel $trace_file , qui peut être soit le nom d'un fichier à ouvrir par le DBI en mode ajout, soit une référence à un gestionnaire de fichier existant accessible en écriture (possiblement en couches). Si $trace_file est un nom de fichier et peut être ouvert en mode ajout, ou si $trace_file est un gestionnaire de fichier accessible en écriture, alors toute la sortie de traçage (actuellement y compris celle des autres gestionnaires) est redirigée vers ce fichier. Un avertissement est généré si $trace_file ne peut pas être ouvert ou n'est pas accessible en écriture.

Les appels ultérieurs à trace() sans $trace_file ne modifient pas la destination de la sortie de traçage. Si $trace_file est indéfini, la sortie de traçage est envoyée à "STDERR" et, si le traçage précédent a été ouvert avec $trace_file comme nom de fichier, le fichier de traçage précédent est fermé ; si $trace_file était un gestionnaire de fichier, le gestionnaire de fichier n'est pas fermé.

NOTE: Si $trace_file est spécifié comme gestionnaire de fichier, le gestionnaire de fichier ne doit pas être fermé tant que toutes les opérations du DBI ne sont pas terminées, ou que l'application n'a pas réinitialisé le fichier de traçage via un autre appel à trace() qui change le fichier de traçage.

Traçage vers des gestionnaires de fichier en couches

NOTE:

  • Les gestionnaires de fichier liés (tied) ne sont actuellement pas pris en charge, car les opérations tie ne sont pas disponibles pour les méthodes PerlIO utilisées par le DBI.
  • La prise en charge des couches PerlIO nécessite Perl version 5.8 ou supérieure.

À partir de la version 5.8, Perl offre la possibilité d'empiler diverses "disciplines" sur un gestionnaire de fichier ouvert via le module PerlIO.

Un exemple simple d'utilisation des couches PerlIO est d'utiliser un scalaire comme sortie :

my $scalar = '';
open( my $fh, "+>:scalar", \$scalar );
$dbh->trace( 2, $fh );

Maintenant, toute la sortie de traçage est simplement ajoutée à $scalar.

Une application plus complexe du traçage vers un gestionnaire de fichier en couches est l'utilisation d'une couche personnalisée (Voir Perlio::via pour plus de détails sur la création de couches PerlIO personnalisées.). Considérez une application avec le module de journalisation suivant :

package MyFancyLogger;
sub new
{
    my $self = {};
    my $fh;
    open $fh, '>', 'fancylog.log';
    $self->{_fh} = $fh;
    $self->{_buf} = '';
    return bless $self, shift;
}
sub log
{
    my $self = shift;
    return unless exists $self->{_fh};
    my $fh = $self->{_fh};
    $self->{_buf} .= shift;
#
# DBI nous fournit des morceaux à la fois, donc accumuler une ligne complète
# avant de l'afficher
#
    print $fh "At ", scalar localtime(), ':', $self->{_buf}, "\n" and
    $self->{_buf} = ''
        if $self->{_buf}=~tr/\n//;
}
sub close {
    my $self = shift;
    return unless exists $self->{_fh};
    my $fh = $self->{_fh};
    print $fh "At ", scalar localtime(), ':', $self->{_buf}, "\n" and
    $self->{_buf} = ''
        if $self->{_buf};
    close $fh;
    delete $self->{_fh};
}
1;

Pour rediriger les traçages du DBI vers ce journal, il faut créer un paquet pour la couche :

package PerlIO::via::MyFancyLogLayer;
sub PUSHED
{
    my ($class,$mode,$fh) = @_;
    my $logger;
    return bless \$logger,$class;
}
sub OPEN {
    my ($self, $path, $mode, $fh) = @_;
    #
    # $path est en fait notre objet journal
    #
    $$self = $path;
    return 1;
}
sub WRITE
{
    my ($self, $buf, $fh) = @_;
    $$self->log($buf);
    return length($buf);
}
sub CLOSE {
    my $self = shift;
    $$self->close();
    return 0;
}
1;

L'application peut ensuite faire en sorte que les traçages du DBI soient acheminés vers le journal à l'aide de

use PerlIO::via::MyFancyLogLayer;
open my $fh, '>:via(MyFancyLogLayer)', MyFancyLogger->new();
$dbh->trace('SQL', $fh);

Maintenant, toute la sortie de traçage sera traitée par la méthode log() de MyFancyLogger.

Contenu du traçage

Beaucoup des valeurs intégrées dans la sortie de traçage sont formatées à l'aide de la fonction utilitaire neat() . Cela signifie qu'elles peuvent être entre guillemets, assainies, et possiblement tronquées si elles sont plus longues que $DBI::neat_maxlen. Voir "neat" pour plus de détails.

Conseils de traçage

Vous pouvez ajouter du traçage à votre propre code d'application à l'aide de la méthode "trace_msg".

Il peut parfois être utile de comparer des fichiers de traçage de deux exécutions différentes du même script. Cependant, l'utilisation d'un outil comme "diff" sur la sortie du journal d'origine ne fonctionne pas bien car le fichier de traçage est plein d'adresses d'objets qui peuvent différer à chaque exécution.

Le DBI inclut une utilitaire pratique appelé dbilogstrip qui peut être utilisé pour « normaliser » le contenu du journal. Il peut être utilisé comme un filtre comme ceci :

DBI_TRACE=2 perl yourscript.pl ...args1... 2>&1 | dbilogstrip > dbitrace1.log
DBI_TRACE=2 perl yourscript.pl ...args2... 2>&1 | dbilogstrip > dbitrace2.log
diff -u dbitrace1.log dbitrace2.log

Voir dbilogstrip pour plus d'informations.

Variables d'environnement du DBI

Le module DBI reconnaît un certain nombre de variables d'environnement, mais la plupart d'entre elles ne devraient pas être utilisées la plupart du temps. Il vaut mieux être explicite sur ce que vous faites pour éviter le besoin de variables d'environnement, en particulier dans un système de service web où les serveurs web sont avares sur les variables d'environnement disponibles.

DBI_DSN

La variable d'environnement DBI_DSN est utilisée par DBI->connect si vous ne spécifiez pas de source de données lorsque vous émettez la connexion. Elle doit avoir un format tel que "dbi:Driver:databasename".

DBI_DRIVER

La variable d'environnement DBI_DRIVER est utilisée pour remplir le nom du pilote de base de données dans DBI->connect si la chaîne de source de données commence par "dbi::" (omettant ainsi le piloteer). Si DBI_DSN omet le nom du pilote, DBI_DRIVER peut combler cette lacune.

DBI_AUTOPROXY

La variable d'environnement DBI_AUTOPROXY prend une valeur de chaîne qui commence par "dbi:Proxy:" et est généralement suivie de "hostname=...;port=...". Elle est utilisée pour modifier le comportement de DBI->connect. Pour plus de détails, voir la documentation de DBI::Proxy.

DBI_USER

La variable d'environnement DBI_USER prend une valeur de chaîne qui est utilisée comme nom d'utilisateur si l'appel DBI->connect reçoit undef (par opposition à une chaîne vide) comme argument nom d'utilisateur. Soyez prudent quant aux implications de sécurité de l'utilisation de cette variable.

DBI_PASS

La variable d'environnement DBI_PASS prend une valeur de chaîne qui est utilisée comme mot de passe si l'appel DBI->connect reçoit undef (par opposition à une chaîne vide) comme argument mot de passe. Soyez particulièrement prudent quant aux implications de sécurité de l'utilisation de cette variable.

DBI_DBNAME (obsolète)

La variable d'environnement DBI_DBNAME prend une valeur de chaîne qui est utilisée uniquement lorsque l'ancien style de DBI->connect (avec le nom du pilote comme quatrième paramètre) est utilisé, et lorsqu'aucune valeur n'est fournie pour le premier argument (nom de la base de données).

DBI_TRACE

La variable d'environnement DBI_TRACE spécifie les paramètres de trace par défaut globaux pour le DBI au démarrage. Elle peut également être utilisée pour diriger la sortie de trace vers un fichier. Lorsque le DBI est chargé, il effectue :

DBI->trace(split /=/, $ENV{DBI_TRACE}, 2) if $ENV{DBI_TRACE};

Ainsi, si "DBI_TRACE" contient un ""="" alors ce qui suit est utilisé comme nom du fichier auquel ajouter la trace.

la sortie est ajoutée à ce fichier. Si le nom commence par un nombre suivi d'un signe égal ("="), alors le nombre et le signe égal sont supprimés du nom, et le nombre est utilisé pour définir le niveau de trace. Par exemple :

DBI_TRACE=1=dbitrace.log perl your_test_script.pl

Sur les systèmes de type Unix utilisant un shell de type Bourne, vous pouvez faire cela facilement en ligne de commande :

DBI_TRACE=2 perl your_test_script.pl

Voir "TRACING" pour plus d'informations.

PERL_DBI_DEBUG (obsolète)

Une ancienne variable qui ne devrait plus être utilisée ; équivalente à DBI_TRACE.

DBI_PROFILE

La variable d'environnement DBI_PROFILE peut être utilisée pour activer le profilage des appels de méthodes DBI. Voir DBI::Profile pour plus d'informations.

DBI_PUREPERL

La variable d'environnement DBI_PUREPERL peut être utilisée pour activer l' utilisation de DBI::PurePerl. Voir DBI::PurePerl pour plus d'informations.

Erreurs Fatales

Can't call method "prepare" without a package or object reference
Le $dbh descripteur que vous utilisez pour appeler "prepare" est probablement indéfini car le "connect" précédent a échoué. Vous devriez toujours vérifier le statut de retour des méthodes DBI, ou utiliser l' attribut "RaiseError".
Can't call method "execute" without a package or object reference
Le $sth descripteur que vous utilisez pour appeler "execute" est probablement indéfini car le "prepare" précédent a échoué. Vous devriez toujours vérifier le statut de retour des méthodes DBI, ou utiliser l' attribut "RaiseError".
DBI/DBD internal version mismatch
Le module pilote DBD a été compilé avec une version de DBI différente de celle actuellement utilisée. Vous devriez recompiler le module DBD sous la version actuelle de DBI.

(Certaines plateformes rares nécessitent une "liaison statique". Sur ces plateformes, une ancienne version de DBI ou du pilote DBD peut être réellement intégrée à l'exécutable Perl utilisé.)

DBD driver has not implemented the AutoCommit attribute
L'implémentation du pilote DBD est incomplète. Consultez l'auteur.
Can't [sg]et %s->{%s}: unrecognised attribute
Vous avez tenté de définir ou d'obtenir un attribut inconnu d'un descripteur. Assurez-vous que vous avez correctement orthographié le nom de l'attribut ; la casse est significative (par exemple, "Autocommit" n'est pas la même chose que "AutoCommit").

DBI Pure-Perl

Une émulation pure-perl du DBI est incluse dans la distribution pour les personnes utilisant des pilotes pure-perl qui, pour une raison quelconque, ne peuvent pas installer le DBI compilé. Voir DBI::PurePerl.
