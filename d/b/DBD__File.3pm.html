DBD::File - Classe de base

pour écrire des pilotes
DBI basés sur des fichiers

SYNOPSI

S

Ce module est une classe de base pour écrire d'autres DBD. Il n'est pas destiné à fonctionn

er comme un DBD lui-même (bien que ce soit possible). Si vous voulez accéder à des fichiers
plats, utilisez DBD::AnyData, ou DBD::CSV (tous deux étant des sous-classes de DBD::File).

DESCRIPTIO

N

Le module DBD::File n'est pas un vrai pilote DBI, mais une classe de base abstraite pour en dériver des pilotes DBI concrets. L'implication est que ces pilotes travaillent avec des fichiers simples, par exemple des fichiers CSV ou des fichiers INI. Le module est basé sur le module SQL::Statement, un moteur SQL

simple.

Voir DBI pour les détails sur DBI, SQL::Statement pour les détails sur SQL::Statement et DBD::CSV, DBD::DBM ou DBD::AnyData pour des exemples de

pilotes.

Attributs spécifiques à DBD::

File

En plus des attributs DBI, vous pouvez utiliser les attributs dbh suivants

:

f_di

r

Cet attribut est utilisé pour définir le répertoire dans lequel les fichiers sont ouverts et il vaut par défaut le répertoire courant (.). Habituellement, vous le définissez sur le dbh mais il peut être remplacé par table (voir f_meta)

.

Lorsque la valeur de "f_dir" est un chemin relatif, il est converti en nom de chemin absolu approprié (basé sur le répertoire de travail courant) lorsque l'attribut dbh est

défini. 
f_dir => "/data/foo/csv"
,

Si "f_dir" est défini sur un emplacement inexistant, la connexion échouera. Voir CVE-2014-10401 pour la justification. En raison de cela, les dossiers à utiliser ne peuvent pas être créés après la connexion, mais doivent exister avant que la connexion soit

initiée.

Voir "BOGUES ET LIMITATIONS

CONNUES".

f_dir_searc

h

Cet attribut facultatif peut être défini pour passer une liste de dossiers où trouver également des tables existantes. Il ne sera pas utilisé pour créer de nouveaux

fichiers. 
f_dir_search => [ "/data/bar/csv", "/dump/blargh/data" ]
,

f_ex

t

Cet attribut est utilisé pour définir l'extension de fichier. Le format est

: 
extension{/flag
}

où /flag est facultatif et l'extension ne dépend pas de la casse. "f_ext" vous permet de spécifier une extension qui

: 
f_ext => ".
csv/r",
  • fait que DBD::File préfère table.extension à tabl
    • e.
  • fait que le nom de la t
    • able est le nom de fic
hier moins l'extension. 
DBI:CSV:f_dir=data;f_ext=.
csv

Dans l'exemple ci-dessus et lorsque "f_dir" contient à la fois table.csv et table, DBD::File ouvrira table.csv et la table sera nommée "table". Si table.csv n'existe pas mais que table existe, ce fichier est ouvert et la table est également appelée

"table".

Si "f_ext" n'est pas spécifié et que table.csv existe, il sera ouvert et la table sera appelée "table.csv", ce qui n'est probablement pas ce que vous

voulez.

NOTE : même si les extensions ne dépendent pas de la casse, les noms de tables en

dépendent. 
DBI:CSV:f_dir=data;f_ext=.
csv/r

Le flag "r" signifie que l'extension de fichier est requise et tout nom de fichier qui ne correspond pas à l'extension est

ignoré.

Habituellement, vous le définissez sur le dbh mais il peut être remplacé par table (voir f_meta)

.

f_schem

a

Cela définira le nom du schéma et vaut par défaut le propriétaire du répertoire dans lequel le fichier de table réside. Vous pouvez définir "f_schema" à "undef"

. 
my $dbh = DBI->connect ("dbi:CSV:", "", "", {
    f_schema => undef,
    f_dir    => "data",
    f_ext    => ".csv/r",
    }) or die $DBI::

En définissant le schéma, vous affectez les résultats de l'appel tables

:

# pas de f_schema

Définir "f_schema" à la chaîne vide est équivalent à le définir à "undef" de sorte que le DSN peut être "dbi:CSV:f_schema=;

f_dir=.".

f_loc

k

L'attribut "f_lock" est utilisé pour définir le mode de verrouillage sur les fichiers de table ouverts. Notez que toutes les plateformes ne prennent pas en charge le verrouillage. Par défaut, les tables sont ouvertes avec un verrou partagé pour la lecture, et avec un verrou exclusif pour l'écriture. Les modes pris en charge sont

: 
0 : Pas de verrouillage du tout.
1 : Des verrous partagés seront utilisés.
2 : Des verrous exclusifs seront
utilisés.

Mais voir BOGUES CONNUS

ci-dessous.

f_lockfil

e

le" :

Si vous souhaitez désactiver le verrouillage, définissez "f_lockfile" à 0

f_encodin

g

Avec cet attribut, vous pouvez définir l'encodage dans lequel le fichier est ouvert. Cela est implémenté en utilisant "binmode $fh, ":encoding(<

f_encoding>)"".

f_met

a

Zone de données privée aliasant "sql_meta" dans DBI::DBD::SqlEngine qui contient des informations sur les tables que ce module gère. Les métadonnées de table peuvent ne pas être disponibles jusqu'à ce que la table ait été accédée pour la première fois, par exemple en émettant un select dessus, mais il est possible de pré-initialiser des attributs pour chaque table que vous

utilisez.

DBD::File reconnaît les attributs (publics) "f_ext", "f_dir", "f_file", "f_encoding", "f_lock", "f_lockfile", "f_schema", en plus des attributs "sql_meta" dans DBI::DBD::SqlEngine déjà pris en charge. Soyez très prudent lorsque vous modifiez des attributs que vous ne connaissez pas, la conséquence pourrait être une table détruite ou

corrompue.

"f_file" est un attribut applicable uniquement aux métadonnées de table et vous ne trouverez pas d'attribut correspondant dans le dbh. Bien qu'il puisse être raisonnable d'avoir plusieurs tables avec les mêmes noms de colonnes, ce n'est pas le cas pour le même nom de fichier. Si vous avez besoin d'accéder au même fichier en utilisant différents noms de table, utilisez "SQL::Statement" comme moteur SQL et le mot-clé "AS"

: 
SELECT * FROM tbl AS t1, tbl AS t2 WHERE t1.id = t2.
id ass="Pp">"f_file" peut être un chemin absolu ou un chemin relatif, mais s'il est relatif, il est interprété comme étant relatif à l' "f_dir" des métadonnées de la table. Quand "f_file" est défini, DBD::File utilisera "f_file" tel que spécifié et n'essaiera pas de trouver une alternative pour "f_file" en utilisant le "nom de la table" et l'attribut "f

_ext".

Bien que "f_meta" soit un attribut privé et en lecture seule (ce qui signifie que vous ne pouvez pas modifier ses valeurs), les pilotes dérivés peuvent fournir un accès en écriture restreint via un autre attribut. Les accesseurs bien connus sont "csv_tables" pour DBD::CSV, "ad_tables" pour DBD::AnyData et "dbm_tables" pour DBD::

DBM.

opérations.

La méthode "data_sources" renvoie une liste des sous-répertoires du répertoire courant sous la forme "dbi:CSV:f_dir=$dirname"

BOGUES ET LIMITATIONS

CONNUS
  • Ce module utilise flock () en interne mais flock n'est pas disponible sur toutes les plateformes. Sur MacOS et Windows 95, il n'y a pas de verrouillage du tout (peut-être pas si important sur MacOS et Windows 95, car il n'y a qu'un seul utilisateur)
    • .
  • Le module stocke les détails sur les tables traitées dans une zone privée du descripteur de pilote ($drh). Cette zone de données n'est pas partagée entre différentes instances de pilote, donc plusieurs appels "DBI->connect ()" causeront différentes instances de tables et différentes zones de données privées.

    Cette zone de données est remplie pour la première fois quand une table est accédée, soit via une instruction SQL, soit via "table_info", et n'est pas détruite tant que la table n'est pas supprimée ou que le descripteur de pilote n'est pas libéré. La destruction manuelle est possible via

    f_clear_meta.
