DBI

Méthodes de classe

DBI

connect

Cette méthode crée un descripteur de base de données en se connectant à une base de données, et est l'équivalent DBI de la méthode "new". Pour se connecter à une base de données Postgres avec un minimum de paramètres, utilisez la syntaxe suivante

: 
$dbh = DBI->connect("dbi:Pg:dbname=$dbname", '', '', {AutoCommit => 0})
;

Cela se connecte à la base de données nommée dans la variable $dbname sur le port par défaut (généralement 5432) sans aucune authentification

utilisateur.

L'instruction connect suivante montre presque tous les paramètres possibles

: 
$dbh = DBI->connect("dbi:Pg:dbname=$dbname;host=$host;port=$port;options=$options",
                    $username,
                    $password,
                    {AutoCommit => 0, RaiseError => 1, PrintError => 0}
                   )
;

Les paramètres contenant des caractères inhabituels tels que des espaces peuvent être entourés de guillemets simples autour de la valeur, et les guillemets simples et les barres obliques inverses peuvent être échappés avec une barre oblique inversée, par ex. "dbi:Pg:dbname='\'spacey\' na

me';host=$host".

Si un paramètre n'est pas donné, la méthode connect() cherchera d'abord des variables d'environnement spécifiques, puis utilisera par défaut des valeurs codées en dur

: 
paramètre     variable d'environnement    valeur par défaut codée en dur
------------------------------------------------------
host         PGHOST                  socket de domaine local
hostaddr     PGHOSTADDR              socket de domaine local
port         PGPORT                  5432
dbname*      PGDATABASE              identifiant utilisateur actuel
username     PGUSER                  identifiant utilisateur actuel
password     PGPASSWORD              (aucun)
options      PGOPTIONS               (aucun)
service      PGSERVICE               (aucun)
sslmode      PGSSLMODE
(aucun)

* Peut également utiliser les alias "db" ou "database

"

Si les valeurs de nom d'utilisateur et de mot de passe passées via connect() sont indéfinies (par opposition à être simplement des chaînes vides), DBI utilisera les variables d'environnement DBI_USER et DBI_PASS si elles

existent.

Vous pouvez également vous connecter en utilisant un fichier de connexion de service. Les noms de service peuvent être définis dans un fichier de service par utilisateur ou dans un fichier système. Si le même nom de service existe à la fois dans le fichier utilisateur et le fichier système, le fichier utilisateur a la priorité. Par défaut, le fichier de service par utilisateur est nommé ~/.pg_service.conf. Sur Microsoft Windows, il est nommé %APPDATA% \postgresql\.pg_service.conf (où %APPDATA% fait référence au sous-répertoire Application Data du profil de l'utilisateur). Un nom de fichier différent peut être spécifié en définissant la variable d'environnement PGSERVICEFILE. Le fichier système est nommé pg_service.conf. L'emplacement de ce fichier peut être contrôlé en définissant la variable d'environnement PGSYSCONFDIR. Pour utiliser l'un des services nommés dans le fichier, définissez le nom en utilisant soit le paramètre service, soit la variable d'environnement PGSERVICE. Notez que lors de la connexion de cette manière, seuls les paramètres minimaux doivent être utilisés. Par exemple, pour se connecter à un service nommé "zephyr", vous pourriez utiliser

: 
$dbh = DBI->connect("dbi:Pg:service=zephyr", '', '')
;

Vous pourriez également définir $ENV{PGSERVICE} à "zephyr" et vous connecter comme ceci

: 
$dbh = DBI->connect("dbi:Pg:", '', '')
;

Le format du fichier pg_service.conf est simplement un nom de service entre crochets, suivi d'un paramètre par ligne au format nom=valeur. Par exemple

: 
[zephyr]
dbname=winds
user=wisp
password=W$2Hc00YSgP
port=6543

4  Une commande COPY IN est toujours en cours d'exécution.
5  Une réponse incorrecte a été reçue du backend.
6  Une erreur non fatale s'est produite (un message d'avis ou d'avertissement)

ATTRIBUTS COMMUNS À TOUS LES

GESTIONNAIRES

InactiveDestroy (booléen

)

Si défini à true, la méthode "disconnect" ne sera pas automatiquement appelée lorsque le gestionnaire de base de données sort de portée. Ceci est requis si vous utilisez fork, et même dans ce cas, vous devez procéder avec prudence et vous assurer que soit le parent, soit l'enfant (mais pas les deux !) gère tous les appels de base de données à partir de ce moment, afin que les messages en provenance du backend Postgres ne soient traités que par un des processus. Si vous ne configurez pas les choses correctement, vous verrez des messages tels que "server closed the connection unexpectedly" et "message type 0x32 arrived from server while idle". La meilleure solution est soit de faire reconnecter le processus enfant à la base de données avec un nouveau gestionnaire de base de données, soit de réécrire votre application pour ne pas utiliser fork. Voir la section sur "Asynchronous Queries" pour une façon de faire continuer votre script à fonctionner pendant que la base de données traite une

requête.

AutoInactiveDestroy (booléen

)

L'attribut InactiveDestroy, décrit ci-dessus, doit être explicitement défini dans le processus enfant après un fork. Si le code qui effectue le fork se trouve dans un module tiers tel que Sys::Syslog, cela peut poser un problème. Utilisez AutoInactiveDestroy pour contourner ce

problème.

RaiseError (booléen,

hérité)

Force les erreurs à toujours lever une exception. Bien qu'il soit désactivé par défaut, il est recommandé de l'activer, car l'alternative consiste à vérifier la valeur de retour de chaque méthode (prepare, execute, fetch, etc.) manuellement, ce qu'il est facile d'oublier de

faire.

PrintError (booléen,

hérité)

Force les erreurs de base de données à générer également des avertissements, qui peuvent ensuite être filtrés avec des méthodes telles que la redéfinition locale de $SIG{__WARN__} ou l'utilisation de modules tels que "CGI::Carp". Cet attribut est activé par

défaut.

ShowErrorStatement (booléen,

hérité)

Ajoute des informations sur l'instruction courante aux messages d'erreur. Si des informations sur les paramètres sont disponibles, les ajoute également. Par défaut à

false.

Notez que cela ne fonctionnera pas lors de l'utilisation de "do" sans aucun

argument.

Warn (booléen,

hérité)

Active les avertissements. C'est activé par défaut, et cela ne devrait être désactivé que localement dans un bloc, pour une courte durée, seulement lorsque c'est absolument

nécessaire.

Executed (booléen, lecture

seule)

Indique si un gestionnaire a été exécuté. Pour les gestionnaires de base de données, cette valeur est true après l'appel de la méthode "do", ou lorsque l'un des gestionnaires d'instructions enfants a émis un "execute". L'émission d'un "commit" ou d'un "rollback" réinitialise toujours l'attribut à false pour les gestionnaires de base de données. Pour les gestionnaires d'instructions, tout appel à "execute" ou à ses variantes passera la valeur à true pour la durée de vie du gestionnaire

d'instructions.

TraceLevel (entier,

hérité)

Définit le niveau de trace, similaire à la méthode "trace". Voir les sections sur "trace" et parse_trace_flag pour plus de

détails.

Active (booléen, lecture

seule)

Indique si un gestionnaire est actif ou non. Pour les gestionnaires de base de données, cela indique si la base de données a été déconnectée ou non. Pour les gestionnaires d'instructions, cela indique si toutes les données ont été récupérées ou non. L'utilisation de cet attribut n'est pas

encouragée.

Kids (entier, lecture

seule)

Renvoie le nombre de processus enfants créés pour chaque type de gestionnaire. Pour un gestionnaire de pilote, indique le nombre de gestionnaires de base de données créés. Pour un gestionnaire de base de données, indique le nombre de gestionnaires d'instructions créés. Pour les gestionnaires d'instructions, il renvoie toujours zéro, car les gestionnaires d'instructions ne créent pas

d'enfants.

Tente de retourner l'id de la dernière valeur insérée dans une table. Vous pouvez soit fournir un nom de séquence (préféré), soit fournir un nom de table avec un schéma optionnel, et DBD::Pg tentera de trouver la séquence lui-même. La valeur actuelle de la séquence est retournée par un appel à la fonction PostgreSQL CURRVAL(). Cela échouera si la séquence n'a pas encore été utilisée dans la connexion de base de données

last_insert_id.

Plus précisément, assurez-vous qu'elle est appelée immédiatement après l'insertion, et que l'insertion n'ajoute pas de valeur à la colonne qui utilise la séquence comme valeur par défaut. table_info

$sth = $dbh->table_info(undef, $schema, $table, $type)
;

Retourne toutes les tables et vues visibles par l'utilisateur courant. Les arguments schema et table effectueront une recherche "LIKE" si un signe pour cent ("%") ou un soulignement ("_") est détecté dans l'argument. L'argument $type accepte toute combinaison séparée par des virgules de "TABLE", "VIEW", "SYSTEM TABLE", "SYSTEM VIEW", "MATERIALIZED VIEW", "SYSTEM MATERIALIZED VIEW", "FOREIGN TABLE", "SYSTEM FOREIGN TABLE", ou "LOCAL TEMPORARY". (Utiliser tous est l'action par défaut.

)

Notez qu'un handle de requête est retourné, et non une liste directe de tables. Voir les exemples ci-dessous pour des façons de gérer

cela.

Les champs suivants sont retournés

:

TABLE_CAT : Le nom de la base de données contenant la table ou la vue (toujours la base de données courante)

.

TABLE_SCHEM : Le nom du schéma contenant la table ou la

vue.

TABLE_NAME : Le nom de la table ou de la

vue.

TABLE_TYPE : Le type d'objet retourné. Sera l'un de "TABLE", "VIEW", "MATERIALIZED VIEW", "SYSTEM VIEW", "SYSTEM MATERIALIZED VIEW", "SYSTEM TABLE", "FOREIGN TABLE", "SYSTEM FOREIGN TABLE", ou "LOCAL

TEMPORARY".

TABLE_SCHEM et TABLE_NAME seront mis entre guillemets via quote_ide

nt().

Quatre champs supplémentaires spécifiques à DBD::Pg sont retournés

:

pg_schema : le nom non entre guillemets du

schéma

pg_table : le nom non entre guillemets de la

table

pg_tablespace_name : le nom du tablespace où se trouve la

table

pg_tablespace_location : l'emplacement du tablespace où se trouve la

table

Les tables qui n'ont pas été assignées à un tablespace particulier (ou les vues) retourneront NULL ("undef") pour les deux champs

ci-dessus.

Les lignes sont retournées par ordre alphabétique, avec toutes les tables d'abord, puis toutes les

vues.

Exemples d'utilisation

## Afficher toutes les tables et vues dans le schéma public :

# Afficher le schéma de toutes les tables nommées 'foo' :

  print "Table name is $rel->{TABLE_SCHEM}.$rel->{TABLE_NAME}\n";

Pris en charge par DBD::Pg comme proposé par DBI. Selon la classification de DBI, PostgreSQL est une base de données dans laquelle une transaction doit être explicitement démarrée. Attribut spécifique à DBD::Pg. Indique si DBD::Pg doit tenter d'utiliser des requêtes préparées côté serveur. La valeur par défaut, true, indique que les requêtes préparées doivent être utilisées chaque fois que c'est possible. Voir la section sur la méthode "prepare" pour plus

Attribut spécifique à DBD::Pg. Indique quand DBD::Pg passera internement de l'utilisation de PQexecParams à PQexecPrepared. bind_param

$rv = $sth->bind_param($param_num, $bind_value);
$rv = $sth->bind_param($param_num, $bind_value, $bind_type);
$rv = $sth->bind_param($param_num, $bind_value, \%attr)
;

Permet à l'utilisateur de lier une valeur et/ou un type de données à un emplacement réservé. C'est particulièrement important lors de l'utilisation des préparations côté serveur. Voir la méthode "prepare" pour plus

d'informations.

La valeur de $param_num est un nombre si vous utilisez les emplacements réservés de style '?' ou '$1'. Si vous utilisez les emplacements réservés de style ":foo", le nom complet (par ex. ":foo") doit être donné. Pour les valeurs numériques, vous pouvez utiliser soit un nombre soit un littéral '$1'. Voir les exemples

ci-dessous.

L'argument $bind_value est assez auto-explicatif. Une valeur de "undef" liera un "NULL" à l'emplacement réservé. Utiliser "undef" est utile lorsque vous voulez changer seulement le type et que vous écraserez la valeur plus tard. (N'importe quelle valeur est en fait utilisable, mais "undef" est simple et efficace)

.

Le hachage "\%attr" est utilisé pour indiquer le type de données de l'emplacement réservé. La valeur par défaut est "varchar". Les types de données sont « collants » (sticky) : une fois qu'un type de données est défini pour un certain emplacement réservé (placeholder), il restera pour cet emplacement, à moins qu'il ne soit explicitement défini sur autre chose par la suite. Si l'instruction a déjà été préparée, et que vous changez le type de données pour autre chose, DBD::Pg re-préparera l'instruction pour vous avant d'effectuer l'exécution

suivante.

Exemples

: 
use DBI qw(:sql_types);
use DBD::Pg qw(:pg_types);
$SQL = "SELECT id FROM ptable WHERE size > ? AND title = ?";
$sth = $dbh->prepare($SQL);
## Les deux arguments ci-dessous sont liés aux emplacements réservés en tant que "varchar"
$sth->execute(123, "Merk");
## Réinitialise le type de données du premier emplacement réservé à un entier
$sth->bind_param(1, undef, SQL_INTEGER);
## Le "undef" lié ci-dessus n'est pas utilisé, car nous fournissons des paramètres à execute
$sth->execute(123, "Merk");
## Définit la valeur et le type de données du premier emplacement réservé
$sth->bind_param(1, 234, { pg_type => PG_TIMESTAMP });
## Définit la valeur et le type de données du deuxième emplacement réservé.
## Nous n'envoyons pas de troisième argument, donc le "varchar" par défaut est utilisé
$sth->bind_param('$2', "Zool");
## Nous réalisons que le mauvais type de données a été défini ci-dessus, donc nous le changeons :
$sth->bind_param('$1', 234, { pg_type => SQL_INTEGER });
## Nous avons aussi la mauvaise valeur, donc nous changeons celle-ci également.
## Comme le type de données est collant, nous n'avons pas besoin de le changer
$sth->bind_param(1, 567);
## Cela exécute l'instruction avec 567 (entier) et "Zool" (varchar)
$sth->execute()
;

bind_param_inout

$rv = $sth->bind_param_inout($param_num, \$scalar, 0)
;

Une prise en charge expérimentale de cette fonctionnalité est fourie. Le premier argument de bind_param_inout doit être un numéro d'emplacement réservé. Le deuxième argument doit être une référence à une variable scalaire dans votre script. Le troisième argument n'est pas utilisé et doit simplement être défini à 0. Notez que ce que cela fait réellement est d'affecter une colonne retournée à la variable, dans l'ordre dans lequel la colonne apparaît. Par exemple

: 
my $foo = 123;
$sth = $dbh->prepare("SELECT 1+?::int");
$sth->bind_param_inout(1, \$foo, 0);
$foo = 222;
$sth->execute(444);
$sth->
fetch;

Ce qui précèdera fera en sorte que $foo ait une nouvelle valeur de "223" après le dernier fetch. Notez que les variables liées de cette manière sont très collantes, et prévaudront sur toutes les valeurs passées à execute. C'est parce que la liaison est effectuée le plus tard possible, au stade execute(), ce qui permet de modifier la valeur entre le moment où elle a été liée et le moment où la requête est exécutée. Ainsi, l'exécution ci-dessus est la même que

: 
$sth->execute()
;

execute

$rv = $sth->execute(@bind_values)
;

Exécute une instruction préparée précédemment. En plus des "UPDATE", "DELETE", "INSERT", pour lesquels elle renvoie toujours le nombre de lignes affectées, la méthode "execute" peut également être utilisée pour les instructions "SELECT ... INTO

table".

Le processus "prepare/bind/execute" a considérablement changé pour les serveurs PostgreSQL 7.4 et ultérieurs : veuillez consulter les entrées prepare() et bind_param() pour beaucoup plus

d'informations.

Définir l'une des bind_values sur "undef" est l'équivalent de définir la valeur sur NULL dans la base de données. Définir la bind_value sur $DBDPG_DEFAULT est l'équivalent de l'envoi de la chaîne littérale 'DEFAULT' au backend. Notez que l'utilisation de cette option désactivera les préparations côté serveur jusqu'à ce que PostgreSQL prenne en charge l'utilisation de DEFAULT dans les instructions

préparées.

DBD::Pg prend également en charge le passage de tableaux à execute : passez simplement une référence de tableau (arrayref), et DBD::Pg l'aplatira en une chaîne adaptée à l'entrée sur le

backend.

Si vous utilisez Postgres version 8.2 ou supérieure, vous pouvez également utiliser n'importe laquelle des méthodes de récupération (fetch) pour récupérer les valeurs d'une clause "RETURNING" après avoir exécuté un "UPDATE", "DELETE", ou "INSERT". Par exemple

: 
$dbh->do(q{CREATE TABLE abc (id SERIAL, country TEXT)});
$SQL = q{INSERT INTO abc (country) VALUES (?) RETURNING id};
$sth = $dbh->prepare($SQL);
$sth->execute('France');
$countryid = $sth->fetch()->[0];
$sth->execute('New Zealand');
$countryid = $sth->fetch()->[0]
;

fetchrow_arrayref

$ary_ref = $sth->fetchrow_arrayref
;

Récupère la ligne de données suivante de la poignée de statement (statement handle) et renvoie une référence à un tableau contenant les valeurs des colonnes. Toutes les colonnes qui sont NULL sont renvoyées comme undef dans le

tableau.

S'il n'y a plus de lignes ou si une erreur se produit, alors cette méthode renvoie undef. Vous devriez vérifier "$sth->err" par la suite (ou utiliser l'attribut RaiseError) pour découvrir si le undef renvoyé était dû à une

erreur.

Notez que la même référence de tableau est renvoyée pour chaque fetch, donc ne stockez pas la référence puis ne l'utilisez pas après un fetch ultérieur. De plus, les éléments du tableau sont également réutilisés pour chaque ligne, donc soyez prudent si vous voulez prendre la référence d'un élément. Voir aussi

"bind_columns".

fetchrow_hashref

$hash_ref = $sth->fetchrow_hashref;
$hash_ref = $sth->fetchrow_hashref($name)
;

Récupère la ligne de données suivante et renvoie une référence de hachage (hashref) contenant le nom des colonnes comme clés et les données elles-mêmes comme valeurs. Toute valeur NULL est renvoyée comme une valeur

undef.

S'il n'y a plus de lignes ou si une erreur se produit, alors cette méthode renvoie undef. Vous devriez vérifier "$sth->err" par la suite (ou utiliser l'attribut RaiseError) pour découvrir si le undef renvoyé était dû à une

erreur.

L'argument optionnel $name doit être soit "NAME", "NAME_lc" ou "NAME_uc", et indique le type de transformation à effectuer sur les clés dans le

hachage.

$tbl_ary_ref = $sth->fetchall_arrayref();

Renvoie une référence à un tableau de tableaux contenant toutes les lignes restantes à récupérer depuis la poignée de statement. S'il n'y a plus de lignes, une référence de tableau vide sera renvoyée. Si une erreur se produit, les données lues jusqu'à présent seront renvoyées. En raison de cela, vous devriez toujours vérifier "$sth->err" après avoir appelé cette méthode, sauf si RaiseError a été

passée.

hachage.

complète.

dump_results

$rows = $sth->dump_results($maxlen, $lsep, $fsep, $fh)
;

Récupère toutes les lignes du gestionnaire de statement, appelle "DBI::neat_list" pour chaque ligne, et imprime les résultats vers $fh (qui vaut par défaut STDOUT). Les lignes sont séparées par $lsep (qui vaut par défaut un retour à la ligne). Les colonnes sont séparées par $fsep (qui vaut par défaut une virgule). Le $maxlen contrôle la largeur maximale de la sortie, et vaut par défaut

35.

Cette méthode est conçue comme une utilité pratique pour le prototypage et le test de requêtes. Comme elle utilise "neat_list" pour formater et éditer la chaîne pour une lecture par des humains, elle n'est pas recommandée pour les applications de transfert de

données.

blob_read

$blob = $sth->blob_read($id, $offset, $len)
;

Pris en charge par DBD::Pg. Cette méthode est implémentée par DBI mais n'est pas actuellement documentée par DBI, donc cette méthode pourrait

changer.

Cette méthode semble être fortement influencée par l'implémentation actuelle des blobs dans Oracle. Néanmoins, nous essayons d'être aussi compatibles que possible. Alors qu'Oracle souffre de la limitation que les blobs sont liés aux tables et que chaque table ne peut avoir qu'un seul blob (datatype LONG), PostgreSQL gère ses blobs indépendamment de toute table en utilisant les identifiants d'objet. Cela explique pourquoi la méthode "blob_read" est bénie dans le package STATEMENT et ne fait pas partie du package DATABASE. Ici, le paramètre field a été utilisé pour gérer cet identifiant d'objet. Les paramètres offset et len peuvent être mis à zéro, auquel cas le blob entier est récupéré en une seule

fois.

Voir aussi les fonctions spécifiques à PostgreSQL concernant les blobs, qui sont disponibles via l'interface "func"

.

Pour plus d'informations et d'exemples sur les blobs, veuillez lire le chapitre sur les objets volumineux (Large Objects) dans le Guide du programmeur PostgreSQL à http://www.postgresql.org/docs/current/stat

ic/largeobjects.html.

Renvoie un arrayref indiquant le type de données pour chaque colonne dans l'instruction. Cette méthode renvoie undef si elle est appelée avant execute

().

seule)

Renvoie un arrayref de valeurs entières pour chaque colonne renvoyée par l'instruction. Le nombre indique la précision pour les colonnes "NUMERIC" , la taille en nombre de caractères pour les colonnes "CHAR" et "VARCHAR" , et pour tous les autres types de colonnes, il renvoie le nombre de octets. Cette méthode renvoie undef si elle est appelée avant execute

Renvoie un arrayref de valeurs entières pour chaque colonne renvoyée par l'instruction. Le nombre indique l'échelle de cette colonne. Le seul type qui renverra une valeur est "NUMERIC" . Cette méthode renvoie undef si elle est appelée avant execute

().

seule)

Renvoie un arrayref de valeurs entières pour chaque colonne renvoyée par l'instruction. Le nombre indique si la colonne est nullable ou non. 0 = non nullable, 1 = nullable, 2 = inconnu. Cette méthode renvoie undef si elle est appelée avant execute

().

Database (dbh, lecture

seule)

Renvoie le gestionnaire de base de données à partir duquel ce gestionnaire de statement a été

créé.

ParamValues (hash ref, lecture

seule)

Renvoie une référence vers un hash contenant les valeurs actuellement liées aux marqueurs de position. Si le type de marqueurs de position "paramètres nommés" est utilisé (comme ":foo"), alors les clés du hash seront les noms des marqueurs de position (sans les deux-points). Si le type de marqueurs de position "signe dollar numéros" est utilisé, les clés du hash seront les numéros, sans les signes dollars. Si le type "point d'interrogation" est utilisé, des nombres entiers seront renvoyés, en commençant à un et en augmentant pour chaque marqueur de

position.

Si cette méthode est appelée avant "execute", les valeurs littérales passées sont renvoyées. Si elle est appelée après "execute", alors les versions entre guillemets des valeurs sont

renvoyées.

ParamTypes (hash ref, lecture

seule)

Renvoie une référence vers un hash contenant les noms de types actuellement liés aux marqueurs de position. Les clés sont les mêmes que celles renvoyées par la méthode ParamValues. Savepoint

PostgreSQL version 8.0 a introduit le concept de points de sauvegarde (savepoints), qui permet aux transactions d'être annulées jusqu'à un certain point sans affecter le reste de la transaction. DBD::Pg encourage l'utilisation des méthodes suivantes pour contrôler les points de sauvegarde

Asynchrones

Il est possible d'envoyer une requête au backend et de faire faire d'autres travaux à votre script pendant que la requête s'exécute sur le backend. Les requêtes envoyées par la méthode "do", et par la méthode "execute" peuvent être envoyées de manière asynchrone. L'utilisation de base est la suivante

    $res = $dbh->pg_result();
    print "Result of do(): $res\n";
  }
  print "Query is still running...\n";
  if (cancel_request_received) {
    $dbh->pg_cancel();
  }
  sleep 1;
  redo;
}
print "Async prepare/execute example:\n";
$sth = $dbh->prepare("SELECT long_running_query(1)", {pg_async => PG_ASYNC});
$sth->execute();
## Changed our mind, cancel and run again:
$sth = $dbh->prepare("SELECT 678", {pg_async => PG_ASYNC + PG_OLDQUERY_CANCEL});
$sth->execute();
do_something_else();
if (!$sth->pg_ready) {
  do_another_thing();
}
## We wait until it is done, and get the result:
$res = $dbh->pg_result()
;

Exemples

asynchrones

Voici quelques exemples fonctionnels de requêtes asynchrones. Notez que nous utiliserons la fonction pg_sleep pour simuler une requête de longue

durée. 
use strict;
use warnings;
use Time::HiRes 'sleep';
use DBD::Pg ':async';
my $dbh = DBI->connect('dbi:Pg:dbname=postgres', 'postgres', '', {AutoCommit=>0,RaiseError=>1});
## Lance une requête de longue durée sur la première base de données :
my $sth = $dbh->prepare("SELECT pg_sleep(?)", {pg_async => PG_ASYNC});
$sth->execute(5);
## Pendant que celle-ci s'exécute, faites d'autres choses
print "Votre requête est en cours de traitement. Merci de patienter\n";
check_on_the_kids(); ## Sous-routine coûteuse, prend au moins trois secondes.
while (!$dbh->pg_ready) {
  check_on_the_kids();
  ## Si la fonction ci-dessus retourne rapidement pour une raison quelconque, nous ajoutons un petit sleep
  sleep 0.1;
}
print "La requête est terminée. Récupération des résultats\n";
my $result = $sth->pg_result;
print "Résultat : $result\n";
my $info = $sth->fetchall_arrayref()
;

Sans les requêtes asynchrones, le script ci-dessus prendrait environ 8 secondes à s'exécuter : cinq secondes d'attente pour que l'exécution se termine, puis trois pour que la fonction check_on_the_kids() retourne. Avec les requêtes asynchrones, le script prend environ 6 secondes à s'exécuter, et effectue deux itérations de check_on_the_kids dans le

processus.

Voici un exemple montrant la possibilité d'annuler une requête de longue durée. Imaginez deux bases de données répliquées dans des emplacements géographiques différents sur un réseau lent. Vous avez besoin d'informations le plus rapidement possible, alors vous interrogez les deux à la fois. Quand vous obtenez une réponse, vous dites à l'autre d'arrêter de travailler sur votre requête, car vous n'en avez plus

besoin. 
use strict;
use warnings;
use Time::HiRes 'sleep';
use DBD::Pg ':async';
my $dbhrep1 = DBI->connect('dbi:Pg:dbname=postgres;host=replica1', 'postgres', '', {AutoCommit=>0,RaiseError=>1});
my $dbhrep2 = DBI->connect('dbi:Pg:dbname=postgres;host=replica2', 'postgres', '', {AutoCommit=>0,RaiseError=>1});
$SQL = "SELECT count(*) FROM largetable WHERE flavor='blueberry'";
my $sth1 = $dbhrep1->prepare($SQL, {pg_async => PG_ASYNC});
my $sth2 = $dbhrep2->prepare($SQL, {pg_async => PG_ASYNC});
$sth1->execute();
$sth2->execute();
my $winner;
while (!defined $winner) {
  if ($sth1->pg_ready) {
    $winner = 1;
  }
  elsif ($sth2->pg_ready) {
    $winner = 2;
  }
  Time::HiRes::sleep 0.05;
}
my $count;
if ($winner == 1) {
  $sth2->pg_cancel();
  $sth1->pg_result();
  $count = $sth1->fetchall_arrayref()->[0][0];
}
else {
  $sth1->pg_cancel();
  $sth2->pg_result();
  $count = $sth2->fetchall_arrayref()->[0][0];
}

Support de

COPY

DBD::Pg permet la lecture et le stockage rapide (en masse) de données en utilisant la commande COPY. Le processus de base consiste à utiliser "$dbh->do" pour émettre une commande COPY, puis soit à ajouter des lignes en utilisant "pg_putcopydata", soit à les lire en utilisant "pg_getcopydata"

.

La première étape consiste à mettre le serveur en mode "COPY". Cela se fait en envoyant une commande COPY complète au serveur, en utilisant la méthode "do". Par exemple

: 
$dbh->do("COPY foobar FROM STDIN")
;

Cela indiquerait au serveur d'entrer en mode COPY IN (oui, c'est déroutant, mais le mode est COPY IN à cause de la commande COPY FROM). Il est maintenant prêt à recevoir des informations via la méthode "pg_putcopydata". La syntaxe complète de la commande COPY est plus complexe et n'est pas documentée ici : la documentation canonique de PostgreSQL pour COPY peut être trouvée à l'adresse

:

http://www.postgresql.org/docs/current/static/sql-copy.

html

Une fois qu'une commande COPY a été émise, aucune autre commande SQL n'est autorisée jusqu'à ce que "pg_putcopyend" ait été émise (pour COPY FROM), ou que le dernier "pg_getcopydata" ait été appelé (pour COPY TO)

.

Note : Toutes les autres méthodes COPY (pg_putline, pg_getline, etc.) sont maintenant fortement déconseillées au profit des méthodes pg_getcopydata, pg_putcopydata et

pg_putcopyend.

pg_getcopydata

Utilisée pour récupérer des données d'une table après que le serveur a été mis en mode COPY OUT en appelant "COPY tablename TO STDOUT". Les données sont toujours retournées une ligne de données à la fois. Notez que le serveur ajoutera un saut de ligne à chaque ligne

retournée.

Le premier argument de pg_getcopydata est la variable dans laquelle les données seront stockées (cette variable ne doit pas être indéfinie, ou elle pourrait déclencher un avertissement, bien qu'elle puisse être une référence). La méthode pg_getcopydata retourne un nombre supérieur à 1 indiquant la nouvelle taille de la variable, ou -1 lorsque le COPY est terminé. Une fois qu'un -1 a été retourné, aucune autre action n'est nécessaire, car le mode COPY sera déjà terminé. Exemple

: 
$dbh->do("COPY mytable TO STDOUT");
my @data;
my $x=0;
1 while $dbh->pg_getcopydata($data[$x++]) >=
0;

Il existe également une variante de cette méthode appelée pg_getcopydata_async, qui, comme son nom l'indique, retourne immédiatement. La seule différence avec la méthode originale est que cette version peut retourner un 0, indiquant que la ligne n'est pas encore prête à être délivrée. Quand cela se produit, la variable n'a pas été modifiée, et vous devrez rappeler la méthode jusqu'à ce que vous obteniez un résultat non nul. (Les données sont toujours retournées une ligne de données à la fois.

)

pg_putcopydata

Utilisée pour insérer des données dans une table après que le serveur a été mis en mode COPY IN en appelant "COPY tablename FROM STDIN". Le seul argument sont les données que vous voulez insérer. Émettez une pg_putcopyend() quand vous avez ajouté toutes vos

lignes.

Le délimiteur par défaut est un caractère de tabulation, mais cela peut être changé dans la déclaration COPY. Retourne un 1 en cas de saisie réussie. Exemples

: 
## Exemple simple :
$dbh->do("COPY mytable FROM STDIN");
$dbh->pg_putcopydata("123\tPepperoni\t3\n");
$dbh->pg_putcopydata("314\tMushroom\t8\n");
$dbh->pg_putcopydata("6\tAnchovies\t100\n");
$dbh->pg_putcopyend();
## Cet exemple utilise des colonnes explicites et un délimiteur personnalisé
$dbh->do("COPY mytable(flavor, slices) FROM STDIN WITH DELIMITER '~'");
$dbh->pg_putcopydata("Pepperoni~123\n");
$dbh->pg_putcopydata("Mushroom~314\n");
$dbh->pg_putcopydata("Anchovies~6\n");
$dbh->pg_putcopyend()
;

pg_putcopyend

Quand vous avez terminé avec pg_putcopydata, appelez pg_putcopyend pour informer le serveur

que vous avez terminé, et il retournera à un état normal, non-COPY. Retourne un 1 en cas de s
uccès. Cette méthode échouera si elle est appelée alors que le mode COPY IN n'est pas actif.

Curseur

s

Bien que PostgreSQL prenne en charge les curseurs, ils n'ont pas été utilisés dans l'implémentation actuelle. Quand DBD::Pg a été créé, les curseurs dans PostgreSQL ne pouvaient être utilisés qu'à l'intérieur d'un bloc de transaction. Comme un seul bloc de transaction est autorisé à la fois, cela aurait impliqué la restriction de ne pas utiliser d'instructions imbriquées "SELECT". Par conséquent, la méthode "execute" récupère toutes les données en une fois dans des structures de données situées dans l'application côté client. Ce fait doit être pris en compte lors de la sélection de grandes quantités de données

!

Vous pouvez utiliser les curseurs dans votre application, mais vous devrez faire un peu de travail. D'abord, vous devez déclarer votre curseur. Maintenant, vous pouvez émettre des requêtes contre le curseur, puis sélectionner contre vos requêtes. Cela résulte généralement en une double boucle, comme ceci

: 
# WITH HOLD n'est pas nécessaire si AutoCommit est désactivé
$dbh->do("DECLARE csr CURSOR WITH HOLD FOR $sql");
while (1) { my $sth = $dbh->prepare("fetch 1000 from csr"); $sth->execute; last if 0 == $sth->rows; whi
le (my $row = $sth->fetchrow_hashref) { # Faire quelque chose avec les données. } } $dbh->do("CLOSE csr");

Type de données

bool

L'implémentation actuelle de PostgreSQL retourne 't' pour vrai et 'f' pour faux. Du point de vue de Perl, c'est un choix plutôt malheureux. DBD::Pg traduit donc le résultat pour le type de données "BOOL" à la manière Perl : 'f' devient le nombre 0 et 't' devient le nombre 1. De cette manière, l'application n'a pas à vérifier les valeurs retournées spécifiques à la base de données pour le type de données « BOOL » car Perl traite 0 comme faux et 1 comme vrai. Vous pouvez définir l'attribut pg_bool_tf à une valeur vraie pour ramener les valeurs à 't' et 'f' si vous le

souhaitez.

Les valeurs booléennes peuvent être transmises à PostgreSQL

sous la forme TRUE, 't', 'true', 'y', 'yes' ou '1' pour
vrai et FALSE, 'f', 'false', 'n', 'no' ou '0' pour faux.
