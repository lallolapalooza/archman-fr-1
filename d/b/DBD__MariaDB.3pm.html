NOM

DBD::MariaDB - Pilote MariaDB et MySQL pour l'interface de base de données Perl5 (DBI)

SYNOPSIS

use DBI;
my $dsn = "DBI:MariaDB:database=$database;host=$hostname;port=$port";
my $dbh = DBI->connect($dsn, $user, $password);
my $sth = $dbh->prepare(
    'SELECT id, first_name, last_name FROM authors WHERE last_name = ?'
) or die 'prepare statement failed: ' . $dbh->errstr();
$sth->execute('Eggers') or die 'execution failed: ' . $dbh->errstr();
print $sth->rows() . " rows found.\n";
while (my $ref = $sth->fetchrow_hashref()) {
    print "Found a row: id = $ref->{'id'}, fn = $ref->{'first_name'}\n";
}

EXEMPLE

#!/usr/bin/perl
use strict;
use warnings;
use DBI;
# Connect to the database.
my $dbh = DBI->connect('DBI:MariaDB:database=test;host=localhost',
                       'joe', q(joe's password),
                       { RaiseError => 1, PrintError => 0 });
# Drop table 'foo'. This may fail, if 'foo' doesn't exist
# Thus we put an eval around it.
eval {
    $dbh->do('DROP TABLE foo');
} or do {
    print 'Dropping foo failed: ' . $dbh->errstr() . "\n";
};
# Create a new table 'foo'. This must not fail, thus we don't
# catch errors.
$dbh->do('CREATE TABLE foo (id INTEGER, name VARCHAR(20))');
# INSERT some data into 'foo' using placeholders
$dbh->do('INSERT INTO foo VALUES (?, ?)', undef, 2, 'Jochen');
# now retrieve data from the table.
my $sth = $dbh->prepare('SELECT * FROM foo');
$sth->execute();
while (my $ref = $sth->fetchrow_hashref()) {
    print "Found a row: id = $ref->{'id'}, name = $ref->{'name'}\n";
}
# Disconnect from the database.
$dbh->disconnect();

DESCRIPTION

DBD::MariaDB est le pilote de l'interface de base de données Perl5 pour les bases de données MariaDB et MySQL. En d'autres termes : DBD::MariaDB est une interface entre le langage de programmation Perl et l'API de programmation MariaDB/MySQL qui accompagne le système de gestion de base de données relationnelle MariaDB/MySQL. La plupart des fonctions fournies par cette API de programmation sont prises en charge. Certaines fonctions rarement utilisées sont manquantes, principalement parce que personne ne les a jamais demandées. :-)

Dans ce qui suit, nous discutons d'abord de l'utilisation de DBD::MariaDB, car c'est ce dont vous aurez le plus besoin. Pour l'installation, consultez le document séparé DBD::MariaDB::INSTALL. Voir « EXEMPLE » ci-dessus pour un exemple simple.

Depuis perl, vous activez l'interface avec l'instruction

use DBI;

Après cela, vous pouvez vous connecter à plusieurs serveurs de bases de données MariaDB et MySQL et envoyer plusieurs requêtes à n'importe lequel d'entre eux via une interface orientée objet simple. Deux types d'objets sont disponibles : les descripteurs de base de données et les descripteurs d'instructions. Perl retourne un descripteur de base de données à la méthode connect comme ceci :

my $dbh = DBI->connect("DBI:MariaDB:database=$db;host=$host",
                       $user, $password,
                       { RaiseError => 1, PrintError => 0 });

Une fois que vous êtes connecté à une base de données, vous pouvez exécuter des instructions SQL avec :

$dbh->do('INSERT INTO foo VALUES (?, ?)', undef, $number, $name);

Voir la méthode do de DBI pour plus de détails. Voir aussi la méthode bind_param dans DBI. Voir « DESCRIPTEURS DE BASE DE DONNÉES » ci-dessous pour plus de détails sur les descripteurs de base de données.

Si vous souhaitez récupérer des résultats, vous devez créer un soi-disant descripteur d'instructions avec :

my $sth = $dbh->prepare('SELECT * FROM ' . $dbh->quote_identifier($table));
$sth->execute();

Ce descripteur d'instructions peut être utilisé pour plusieurs choses. Tout d'abord, vous pouvez récupérer une ligne de données :

my $row = $sth->fetchrow_hashref();

Si votre table a des colonnes "ID" et "NAME", alors $row sera une référence de hachage avec les clés "ID" et "NAME". Voir « DESCRIPTEURS D'INSTRUCTIONS » ci-dessous pour plus de détails sur les descripteurs d'instructions.

Mais maintenant pour une approche plus formelle :

Classe Méthodes

connect
use DBI;
my $dsn = "DBI:MariaDB:$database";
my $dsn = "DBI:MariaDB:database=$database;host=$hostname";
my $dsn = "DBI:MariaDB:database=$database;host=$hostname;port=$port";
my $dsn = "DBI:MariaDB:database=$database;mariadb_socket=$socket";
my $dbh = DBI->connect($dsn, $user, $password);

L'attribut database n'est pas obligatoire, mais veuillez noter que MariaDB et MySQL n'ont pas de concept de base de données par défaut. Si vous ne spécifiez pas la base de données au moment de la connexion, votre base de données active sera nulle et vous devrez préfixer vos tables avec le nom de la base de données ; c'est-à-dire "SELECT * FROM mydb.mytable".

Cela est similaire au comportement du client en ligne de commande "mariadb" ou "mysql" . De plus, "SELECT DATABASE()" retournera la base de données actuellement active pour le descripteur.

Le pilote DBD::MariaDB comprend tout attribut de connexion spécifié dans la section « DESCRIPTEURS DE BASE DE DONNÉES » qui est en lecture/écriture et également tout autre attribut décrit ci-dessous.

host
port
Le host, s'il n'est pas spécifié ou spécifié comme chaîne vide ou "localhost", sera par défaut un serveur MariaDB ou MySQL s'exécutant sur la machine locale en utilisant la valeur par défaut pour le socket UNIX. Pour vous connecter à un serveur MariaDB ou MySQL sur la machine locale via TCP, vous devez spécifier l'adresse IP de bouclage 127.0.0.1 comme host.

Si le serveur MariaDB ou MySQL s'exécute sur un numéro de port non standard, vous pouvez explicitement indiquer le "numéro de port" auquel se connecter dans l'argument host , en concaténant le "nom d'hôte" et le "numéro de port" ensemble, séparés par un caractère deux-points (":") ou en utilisant l'argument port .

Pour vous connecter à un serveur MariaDB ou MySQL sur localhost en utilisant TCP/IP, vous devez spécifier le host comme 127.0.0.1 avec le portoptionnel, par exemple 3306.

Lors de la connexion à un serveur MariaDB ou MySQL avec IPv6, une adresse IPv6 entre crochets doit être utilisée. Exemple de DSN :

my $dsn = 'DBI:MariaDB:;host=[1a12:2800:6f2:85::f20:8cf];port=3306';
mariadb_client_found_rows
Si VRAI (par défaut), définit le drapeau "CLIENT_FOUND_ROWS" lors de la connexion au serveur MariaDB ou MySQL. Cela fait que les instructions "UPDATE" retournent le nombre de lignes correspondantes, et non le nombre de lignes réellement modifiées.

Si vous souhaitez le nombre de lignes modifiées en réponse à une instruction "UPDATE" , spécifiez "mariadb_client_found_rows=0" dans le DSN.

mariadb_compression
Si votre DSN contient l'option "mariadb_compression=1", alors la communication entre le client et le serveur sera compressée.
mariadb_connect_timeout
Si votre DSN contient l'option "mariadb_connect_timeout=##", la requête de connexion au serveur expirera si elle n'a pas abouti après le nombre de secondes donné. Une valeur de zéro signifie un délai d'attente infini.
mariadb_write_timeout
Si votre DSN contient l'option "mariadb_write_timeout=##", l'opération d'écriture vers le serveur expirera si elle n'a pas abouti après le nombre de secondes donné. Une valeur de zéro signifie un délai d'attente infini.
mariadb_read_timeout
Si votre DSN contient l'option "mariadb_read_timeout=##", l'opération de lecture vers le serveurill timeout if it has not been successful after the given number of seconds. Zero value means infinite timeout.
mariadb_init_command
If your DSN contains the option "mariadb_init_command=SQL", then this "SQL" statement is executed when connecting to the MariaDB or MySQL server. It is automatically re-executed if reconnection occurs.
mariadb_skip_secure_auth
This option is for older MySQL databases that don't have secure auth set.
mariadb_read_default_file
mariadb_read_default_group
These options can be used to read a config file like /etc/my.cnf or ~/.my.cnf. By default MariaDB's and MySQL's C client library doesn't use any config files unlike the client programs (mysql, mysqladmin, ...) that do, but outside of the C client library. Thus you need to explicitly request reading a config file, as in 
my $dsn = 'DBI:MariaDB:test;mariadb_read_default_file=/home/joe/my.cnf';
my $dbh = DBI->connect($dsn, $user, $password);

If the config file specifies the password, you need to use "undef" in "connect", not just an empty string, to have it replaced by the config value. All other attributes replace even the empty string.

The option mariadb_read_default_group can be used to specify the default group in the config file: Usually this is the "client" group, but see the following example:

[client]
host=localhost
[perl]
host=perlhost

(Note the order of the entries! The example won't work, if you reverse the "[client]" and "[perl]" sections!)

If you read this config file, then you'll be typically connected to "localhost". However, by using

my $dsn = 'DBI:MariaDB:test;mariadb_read_default_group=perl;'
        . 'mariadb_read_default_file=/home/joe/my.cnf';
my $dbh = DBI->connect($dsn, $user, $password);

you'll be connected to "perlhost". Note that if you specify a default group and do not specify a file, then the default config files will all be read. See the documentation of the C function mysql_options() for details.

mariadb_socket
It is possible to choose the Unix socket that is used for connecting to the server. This is done, for example, with 
my $dsn = 'DBI:MariaDB:database=test;'
        . 'mariadb_socket=/var/run/mysqld/mysqld.sock';

Usually there's no need for this option, unless you are using another location for the socket than that built into the client.

mariadb_auth_plugin
Specify authentication method used during connection to MariaDB or MySQL server. MySQL protocol uses "mysql_native_password" authentication method and MySQL version 5.5.7 extended protocol and added support for using other authentication methods which can be provided to clients by plugins. MySQL version 8.0.4 changed the default authentication method to "caching_sha2_password".

Example how to use "caching_sha2_password" authentication method:

my $dsn = 'DBI:MariaDB:database=test;host=hostname;'
        . 'mariadb_auth_plugin=caching_sha2_password';
mariadb_ssl
A true value enforces SSL encryption when connecting to the MariaDB or MySQL server. A false value (which is default) disables SSL encryption with the MariaDB or MySQL server.

When enabling SSL encryption you should set also other SSL options, at least mariadb_ssl_ca_file or mariadb_ssl_ca_path.

my $dsn = 'DBI:MariaDB:database=test;host=hostname;port=3306;'
        . 'mariadb_ssl=1;mariadb_ssl_verify_server_cert=1;'
        . 'mariadb_ssl_ca_file=/path/to/ca_cert.pem';

This means that your communication with the server will be encrypted.

mariadb_ssl_ca_file
The path to a file in PEM format that contains a list of trusted SSL certificate authorities.

When set MariaDB or MySQL server certificate is checked that it is signed by some CA certificate in the list. Common Name value is not verified unless mariadb_ssl_verify_server_cert is enabled.

mariadb_ssl_ca_path
The path to a directory that contains trusted SSL certificate authority certificates in PEM format.

When set MariaDB or MySQL server certificate is checked that it is signed by some CA certificate in the list. Common Name value is not verified unless mariadb_ssl_verify_server_cert is enabled.

Please note that this option is supported only if your MariaDB or MySQL client was compiled with OpenSSL library, and not with default yaSSL library.

mariadb_ssl_verify_server_cert
Checks the server's Common Name value in the certificate that the server sends to the client. The client verifies that name against the host name the client uses for connecting to the server, and the connection fails if there is a mismatch. For encrypted connections, this option helps prevent man-in-the-middle attacks.

Verification of the host name is disabled by default.

mariadb_ssl_client_key
The name of the SSL key file in PEM format to use for establishing a secure connection.
mariadb_ssl_client_cert
The name of the SSL certificate file in PEM format to use for establishing a secure connection.
mariadb_ssl_cipher
A list of permissible ciphers to use for connection encryption. If no cipher in the list is supported, encrypted connections will not work. 
mariadb_ssl_cipher=AES128-SHA
mariadb_ssl_cipher=DHE-RSA-AES256-SHA:AES128-SHA
mariadb_ssl_optional
Setting mariadb_ssl_optional to true disables strict SSL enforcement and makes SSL connection optional. This option opens security hole for man-in-the-middle attacks. Default value is false which means that mariadb_ssl set to true enforces SSL encryption.

Due to The BACKRONYM http://backronym.fail/ and The Riddle https://riddle.link/ vulnerabilities in libmariadb and libmysqlclient libraries, enforcement of SSL encryption was not possible and therefore "mariadb_ssl_optional=1" was effectively set for old DBD::mysql driver prior DBD::MariaDB fork was created. DBD::MariaDB with "mariadb_ssl=1" could refuse connection to MariaDB or MySQL server if underlying libmariadb or libmysqlclient library is vulnerable. Option mariadb_ssl_optional can be used to make SSL connection vulnerable.

mariadb_local_infile
The "LOCAL" capability for "LOAD DATA" may be disabled in the MariaDB or MySQL client library by default. If your DSN contains the option "mariadb_local_infile=1", "LOAD DATA LOCAL" will be enabled. However, this option is ineffective if the server has also been configured to disallow "LOCAL".
mariadb_embedded_options
The option mariadb_embedded_options can be used to pass command line options to the embedded server. When you want to start and connect embedded server, use "host=embedded" in dsn as connection parameter.

Example:

use DBI;
my $datadir = '/var/lib/mysql/';
my $langdir = '/usr/share/mysql/';
my $dsn = 'DBI:MariaDB:host=embedded;database=test;'
        . "mariadb_embedded_options=--datadir=$datadir,'
        .                          '--language=$langdir,'
        .                          '--log-error=/dev/null";
my $dbh = DBI->connect($dsn, undef, undef);

This would start embedded server with language directory $langdir, database directory $datadir, drop error messages and connects to database "test". It is suggested to specify "--log-error=" option which defines location for warning messages because by default Embedded server prints its warning and error messages to "STDOUT" which is not expected by Perl or application. Embedded server does not have to be supported by configured MariaDB or MySQL library. In that case "DBI->connect()" returns an error.

mariadb_embedded_groups
The option mariadb_embedded_groups can be used to specify the groups in the config file (my.cnf) which will be used to get options for the embedded server. If not specified "[server]" and "[embedded]" groups will be used.

Example:

my $dsn = 'DBI:MariaDB:host=embedded;database=test;'
        . 'mariadb_embedded_groups=embedded_server,common';
mariadb_conn_attrs
The option mariadb_conn_attrs is a hash of attribute names and values which can be used to send custom connection attributes to tserveur. Certains attributs comme "_os", "_platform", "_client_name" et "_client_version" sont ajoutés par libmariadb ou libmysqlclient.

Vous pouvez ensuite lire ces attributs depuis les tables du schéma de performance, ce qui peut être très utile pour profiler votre base de données ou créer des statistiques. Vous devrez utiliser à la fois le serveur et le client, au moins en version MariaDB 10.0.5 ou MySQL 5.6, pour tirer parti de cette fonctionnalité. C'est une bonne idée de fournir l'attribut supplémentaire "program_name" .

my $dbh= DBI->connect($dsn, $user, $password, {
    AutoCommit => 0,
    mariadb_conn_attrs => {
        program_name => $0,
        foo => 'bar',
        wiz => 'bang'
    },
});

Vous pouvez maintenant sélectionner les résultats depuis les tables du schéma de performance. Vous pouvez le faire dans la même session, mais aussi ultérieurement. Cela peut être très utile pour répondre à des questions comme quel script a envoyé cette requête ?

my $results = $dbh->selectall_hashref(
    'SELECT * FROM performance_schema.session_connect_attrs',
    'ATTR_NAME'
);

data_sources

Renvoie une liste de toutes les bases de données au format dsn, adaptée à la méthode connect, gérées par le serveur MariaDB ou MySQL. Elle accepte tous les attributs de la méthode connect.

POIGNÉES DE BASE DE DONNÉES

Le pilote DBD::MariaDB prend en charge les attributs suivants des poignées de base de données (lecture seule) :

my $errno = $dbh->{'mariadb_errno'};
my $error = $dbh->{'mariadb_error'};
my $hostinfo = $dbh->{'mariadb_hostinfo'};
my $info = $dbh->{'mariadb_info'};
my $insertid = $dbh->{'mariadb_insertid'};
my $protoinfo = $dbh->{'mariadb_protoinfo'};
my $serverinfo = $dbh->{'mariadb_serverinfo'};
my $ssl_cipher = $dbh->{'mariadb_ssl_cipher'};
my $stat = $dbh->{'mariadb_stat'};
my $thread_id = $dbh->{'mariadb_thread_id'};

Ceux-ci correspondent respectivement à mysql_errno(), mysql_error(), mysql_get_host_info(), mysql_info(), mysql_insert_id(), mysql_get_proto_info(), mysql_get_server_info(), mysql_stat(), mysql_get_ssl_cipher() et mysql_thread_id() .

Les applications DBI portables ne devraient pas les utiliser. Elles devraient plutôt utiliser les méthodes DBI standard : "$dbh->err()" et "$dbh->errstr()" pour le numéro et la chaîne d'erreur, "$dbh->get_info($GetInfoType{SQL_SERVER_NAME})" pour le nom d'hôte du serveur, "$dbh->get_info($GetInfoType{SQL_DBMS_NAME})" et "$dbh->get_info($GetInfoType{SQL_DBMS_VER})" pour le nom et la version de la base de données du serveur, "$dbh->last_insert_id()" ou "$sth->last_insert_id()" pour l'identifiant d'insertion.

mariadb_clientinfo
mariadb_clientversion
Liste les informations de la bibliothèque client MariaDB ou MySQL contre laquelle DBD::MariaDB a été compilé : 
print "$dbh->{mariadb_clientinfo}\n";
5.2.0-MariaDB
print "$dbh->{mariadb_clientversion}\n";
50200

Les applications DBI portables ne devraient pas se soucier de la version de la bibliothèque client sous-jacente. DBD::MariaDB est là pour masquer toute incompatibilité possible et fonctionne correctement avec toute version disponible.

mariadb_serverversion
print "$dbh->{mariadb_serverversion}\n";
50200

Les applications DBI portables devraient plutôt utiliser "$dbh->get_info($GetInfoType{SQL_DBMS_NAME})" et "$dbh->get_info($GetInfoType{SQL_DBMS_VER})" pour le nom et la version de la base de données du serveur.

mariadb_ssl_cipher
Renvoie le chiffrement SSL utilisé pour la connexion donnée au serveur. Si le chiffrement SSL n'a pas été activé avec mariadb_ssl ou n'a pas été établi, renvoie "undef". 
my $ssl_cipher = $dbh->{mariadb_ssl_cipher};
if (defined $ssl_cipher) {
    print "Connection with server is encrypted with cipher: $ssl_cipher\n";
} else {
    print "Connection with server is not encrypted\n";
}
mariadb_dbd_stats
my $info_hashref = $dbh->{mariadb_dbd_stats};

DBD::MariaDB conserve certaines statistiques dans l'attribut mariadb_dbd_stats . Les statistiques suivantes sont maintenues :

auto_reconnects_ok
Le nombre de fois où DBD::MariaDB s'est reconnecté avec succès au serveur MariaDB ou MySQL.
auto_reconnects_failed
Le nombre de fois où DBD::MariaDB a tenté de se reconnecter à MariaDB ou MySQL mais a échoué.

Le pilote DBD::MariaDB prend également en charge les attributs suivants des poignées de base de données (lecture/écriture) :

mariadb_auto_reconnect
Cet attribut détermine si DBD::MariaDB se reconnectera automatiquement au serveur MariaDB ou MySQL si la connexion est perdue. Cette fonctionnalité est désactivée par défaut. Définir mariadb_auto_reconnect à 1 n'est pas conseillé si "LOCK TABLES" est utilisé, car si DBD::MariaDB se reconnecte à MariaDB ou MySQL, tous les verrous de tables seront perdus. Cet attribut est ignoré lorsque AutoCommit est désactivé, et lorsque AutoCommit est désactivé, DBD::MariaDB ne se reconnectera pas automatiquement au serveur.

Il est également possible de définir la valeur par défaut de l'attribut mariadb_auto_reconnect pour $dbh en le passant dans le hash "\%attr" pour "DBI->connect".

$dbh->{mariadb_auto_reconnect} = 1;

ou

my $dbh = DBI->connect($dsn, $user, $password, {
    mariadb_auto_reconnect => 1,
});

Notez que si vous utilisez un module ou un framework qui effectue les reconnexions pour vous (par exemple DBIx::Connector en mode fixup), cette valeur doit être définie à 0.

mariadb_use_result
Cet attribut force le pilote à utiliser mysql_use_result() plutôt que la fonction de bibliothèque mysql_store_result() . La première est plus rapide et consomme moins de mémoire, mais a tendance à bloquer les autres processus. mysql_store_result() est la valeur par défaut en raison du fait que le stockage du résultat est le comportement attendu avec la plupart des applications.

Il est possible de définir la valeur par défaut de l'attribut mariadb_use_result pour $dbh via le DSN :

my $dbh = DBI->connect('DBI:MariaDB:test;mariadb_use_result=1', $user, $pass);

Vous pouvez également le définir après la création de la poignée de base de données :

$dbh->{mariadb_use_result} = 0; # disable
$dbh->{mariadb_use_result} = 1; # enable

Vous pouvez également définir ou annuler le paramètre mariadb_use_result sur votre poignée d'instruction, lors de la création de la poignée d'instruction ou après sa création. Voir « POIGNÉES D'INSTRUCTION ».

Les fonctions de bibliothèque mysql_use_result() et mysql_store_result() ne sont pas utilisées pour les instructions préparées côté serveur, par conséquent cet attribut mariadb_use_result n'a aucun effet lorsque les instructions préparées côté serveur sont activées.

Notez que la fonction de bibliothèque mysql_use_result() ne fournit pas le nombre de lignes dans le jeu de résultats. Par conséquent, si cet attribut mariadb_use_result est activé, la variable DBI $DBI::rows et les méthodes d'instruction execute et rows renvoient -1 (ce qui signifie que le nombre de lignes est inconnu). Cependant, la méthode d'instruction rows renvoie le nombre correct de lignes après que toutes les lignes ont déjà été récupérées et qu'un appel fetch supplémentaire a été émis (dans ce cas spécial, le pilote sait qu'il a traité toutes les lignes et sait donc quel est leotal number of rows).

Activer mariadb_use_result l'attribut sur un handle de requête interdit l'utilisation de tous les autres handles de requêtes et de bases de données jusqu'à ce que toutes les lignes de données du handle de requête actif soient récupérées. Tenter d'utiliser d'autres handles de requêtes ou de bases de données alors qu'il y a un attribut mariadb_use_result actif sur un handle de requête provoque des erreurs imprévisibles.

Dans la plupart des cas, il n'y a aucun avantage à utiliser cet attribut mariadb_use_result

mariadb_bind_type_guessing
Cet attribut fait que le pilote (requêtes préparées émulées) tente de deviner si une valeur liée est une valeur numérique et, le cas échéant, ne met pas la valeur entre guillemets. Cela a été créé par Dragonchild et est une façon de gérer le problème de performance lié à l'utilisation de guillemets dans une requête qui insère ou met à jour une grande valeur numérique.

HANDLES DE REQUÊTES

Les handles de requêtes de DBD::MariaDB prennent en charge un certain nombre d'attributs. Vous y accédez en utilisant, par exemple,

my $numFields = $sth->{NUM_OF_FIELDS};

Notez que la plupart des attributs ne sont valides qu'après un execute réussi. Une valeur "undef" sera retournée sinon. La plus importante exception est l'attribut mariadb_use_result .

Pour définir l'attribut mariadb_use_result sur le handle de requête $sth, utilisez l'une des méthodes suivantes :

my $sth = $dbh->prepare($sql, { mariadb_use_result => 1});

ou

my $sth = $dbh->prepare($sql);
$sth->{mariadb_use_result} = 1;

Les attributs dépendant des colonnes, par exemple NAME, les noms de colonnes, sont retournés sous forme de référence à un tableau. Les indices du tableau correspondent aux indices des tableaux retournés par fetchrow et les méthodes similaires. Par exemple, le code suivant imprimera un en-tête des noms de tables avec toutes les lignes :

my $sth = $dbh->prepare('SELECT * FROM t')
    or die 'Error: ' . $dbh->errstr() . "\n";
$sth->execute()
    or die 'Error: ' . $sth->errstr() . "\n";
my $names = $sth->{NAME};
my $numFields = $sth->{'NUM_OF_FIELDS'} - 1;
for my $i ( 0..$numFields ) {
    printf('%s%s', $i ? ',' : '', $$names[$i]);
}
print "\n";
while (my $ref = $sth->fetchrow_arrayref()) {
    for my $i ( 0..$numFields ) {
        printf('%s%s', $i ? ',' : '', $$ref[$i]);
    }
    print "\n";
}

Pour des applications portables, vous devriez vous limiter aux attributs dont les noms sont en majuscules ou en casse mixte. Les noms d'attributs en minuscules sont privés à DBD::MariaDB. La liste des attributs comprend :

ChopBlanks
Cet attribut détermine si un fetchrow supprimera les espaces précédents et suivants des valeurs de colonnes. La suppression des espaces n'a pas d'impact sur l'attribut mariadb_max_length
mariadb_insertid
Si l'instruction que vous avez exécutée effectue un "INSERT", et qu'il y a une colonne "AUTO_INCREMENT" dans la table dans laquelle vous avez inséré, cet attribut contient la valeur stockée dans la colonne "AUTO_INCREMENT" , si cette valeur est générée automatiquement, en stockant "NULL" ou 0 ou a été spécifiée comme valeur explicite.

Typiquement, vous accédez à la valeur via "$sth->{mariadb_insertid}". La valeur peut également être accessible via "$dbh->{mariadb_insertid}" mais cela peut facilement produire des résultats incorrects dans le cas où un handle de base de données est partagé.

Les applications DBI portables ne devraient pas utiliser mariadb_insertid. À la place, elles devraient utiliser la méthode DBI "$dbh->last_insert_id()" ou la méthode DBI de requête "$sth->last_insert_id()". La méthode de requête a été introduite dans la version 1.642 de DBI, mais DBD::MariaDB l'implémente également pour les anciennes versions de DBI.

mariadb_is_blob
Référence à un tableau de valeurs booléennes ; La valeur logique vraie indique que la colonne respective est un blob.
mariadb_is_num
Référence vers un tableau de valeurs booléennes ; une valeur logique vraie indique que la colonne correspondante contient des valeurs numériques.
mariadb_is_pri_key
Référence vers un tableau de valeurs booléennes ; une valeur logique vraie indique que la colonne correspondante est une clé primaire.
mariadb_is_auto_increment
Référence vers un tableau de valeurs booléennes ; une valeur logique vraie indique que la colonne correspondante est une colonne "AUTO_INCREMENT" .
mariadb_length
mariadb_max_length
Une référence vers un tableau des tailles maximales des colonnes. Le mariadb_max_length est le maximum physiquement présent dans le tableau de résultats, tandis que mariadb_length donne le maximum théoriquement possible.

Pour les types de variables orientés chaînes (char, varchar, text et types similaires), les deux attributs retournent la valeur en octets. Si vous êtes intéressé par le nombre de caractères, utilisez plutôt mariadb_length utilisez "COLUMN_SIZE" via la méthode standard DBI column_info, et au lieu de mariadb_max_length exécutez la requête SQL "SELECT MAX(CHAR_LENGTH(...))". Exemple :

my $ci_sth = $dbh->column_info(undef, undef, $table, $column);
my $ci_ref = $ci_sth->fetchall_arrayref({});
my $mariadb_char_length = $ci_ref->[0]->{COLUMN_SIZE};
my $mariadb_char_max_length = $dbh->selectrow_array(sprintf(
                                  'SELECT MAX(CHAR_LENGTH(%s)) FROM %s',
                                  $dbh->quote_identifier($column),
                                  $dbh->quote_identifier($table),
                              ));
NOM
Une référence vers un tableau de noms de colonnes.
NULLABLE
Une référence vers un tableau de valeurs booléennes ; une valeur logique vraie indique que cette colonne peut contenir des "NULL".
NUM_OF_FIELDS
Nombre de champs retournés par une instruction "SELECT" . Vous pouvez utiliser ceci pour vérifier si une instruction a retourné un résultat : une valeur zéro indique une instruction non-"SELECT" comme "INSERT", "DELETE" ou "UPDATE".
mariadb_table
Une référence vers un tableau de noms de tables, utile dans un résultat "JOIN" .
TYPE
Une référence vers un tableau de types de colonnes. Les types de colonnes natifs du moteur sont mappés vers des types portables comme DBI::SQL_INTEGER() ou DBI::SQL_VARCHAR(), autant que possible. Tous les types natifs n'ont pas d'équivalent significatif. Si vous avez besoin des types de colonnes natifs, utilisez mariadb_type. Voir ci-dessous.
mariadb_type
Une référence vers un tableau des types de colonnes natifs de MySQL, par exemple DBD::MariaDB::TYPE_SHORT() ou DBD::MariaDB::TYPE_STRING(). Utilisez l'attribut TYPE si vous voulez des types portables comme DBI::SQL_SMALLINT() ou DBI::SQL_VARCHAR().
mariadb_type_name
Similaire à mariadb_type, mais ce sont les noms de types et non les numéros qui sont retournés. Chaque fois que c'est possible, le nom ANSI SQL est préféré.
mariadb_warning_count
Le nombre d'avertissements générés lors de l'exécution de l'instruction SQL. Cet attribut est disponible à la fois sur les gestionnaires d'instructions et les gestionnaires de bases de données.

SUPPORT UNICODE

Tous les types de variables orientés chaînes (char, varchar, text et types similaires) sont représentés par DBD::MariaDB comme des chaînes Unicode conformément au modèle Unicode standard de Perl. Cela signifie que les scalaires Perl contiennent des points de code Unicode et non des octets UTF-8. En interne, DBD::MariaDB utilise le jeu de caractères "utf8mb4" de MySQL pour la communication réseau avec les serveurs MariaDB et MySQL. Il transforme automatiquement le jeu de caractères réseau MySQL "utf8mb4" en scalaires Perl Unicode et vice-versa.

Le jeu de caractères MySQL "utf8mb4" pour la communication réseau est configuré par "MYSQL_SET_CHARSET_NAME" de l'API de la bibliothèque C libmariadb/libmysqlclient, ce qui est une condition préalable pour que la méthode quote fonctionne et pour un remplacement émulé des paramètres de liaison côté client.

N'essayez pas de changer le jeu de caractères réseau (par exemple via la commande SQL "SET NAMES" manuellement) pour quelque chose de différent de UTF-8, car cela confondrait la bibliothèque C sous-jacente et DBD::MariaDB se comporterait de manière incorrecte (par exemple, cela conduirait à une méthode quote cassée ou non sécurisée, ou à un remplacement émulé des paramètres de liaison côté client).

L'utilisation d'un jeu de caractères non UTF-8 pour une colonne, une table ou une base de données est acceptable car le serveur MariaDB ou MySQL transforme automatiquement le jeu de caractères de stockage vers le jeu de caractères utilisé par le protocole réseau ("utf8mb4"). Notez que lorsque DBD::MariaDB se connecte au serveur MariaDB ou MySQL, il appelle la commande SQL "SET character_set_server = 'utf8mb4'" pour s'assurer que le jeu de caractères par défaut pour les nouvelles bases de données sera UTF-8. Attention, le jeu de caractères par défaut pour les nouvelles tables est défini à partir du jeu de caractères de la base de données.

Dans le cas où le serveur MySQL ne supporte pas le jeu de caractères MySQL "utf8mb4" pour un protocole réseau, DBD::MariaDB essaierait d'utiliser le jeu de caractères MySQL "utf8" qui est un sous-ensemble de l'encodage UTF-8 restreint aux séquences UTF-8 de 3 octets. Le support du jeu de caractères MySQL "utf8mb4" a été introduit dans le serveur MySQL version 5.5.3.

TRAVAIL avec les données binaires

Les scalaires Perl ne distinguent pas entre les tampons orientés octets et les chaînes orientées Unicode . En Perl, c'est toujours à l'appelant et à l'appelé de définir dans son API si les fonctions et les méthodes attendent des tampons octets ou des chaînes Unicode . Il n'est pas possible (ou plutôt l'application Perl ne devrait pas essayer) de distinguer si un scalaire Perl contient un tampons octets ou une chaîne Unicode .

Lors de la récupération de données depuis les serveurs MariaDB et MySQL, DBD::MariaDB traite tous les champs marqués avec le jeu de caractères MySQL "utf8mb4" (et aussi "utf8") comme des chaînes Unicode . Tout le reste est traité comme des tampons orientés octets binaires. Par conséquent, la seule différence est que les champs UTF-8 sont automatiquement décodés en Unicode. Les champs blob binaires restent intacts et les scalaires Perl correspondants contiendront simplement des ordinaux 0..255 (séquence classique d'octets). Les scalaires de chaînes Unicode contiendront une séquence de points de code Unicode.

Il y a un petit problème avec les données d'entrée, plus précisément avec les instructions SQL et leurs paramètres de liaison. Par définition, une instruction SQL est une chaîne et par conséquent elle est attendue et traitée par DBD::MariaDB comme une chaîne Unicode (et non un tampons orienté octets ). Il n'y a aucun moyen de traiter une instruction SQL comme un binaire, mais ce n'est pas un problème. Toutes les commandes SQL sont encodées en ASCII et tous les caractères ASCII sont des invariants en UTF-8 (ont la même représentation qu'une séquence de points de code Unicode et aussi lorsqu'ils sont encodés en UTF-8 dans un tampon d'octets). Pour le reste d'une instruction SQL, des emplacements de réservation avec paramètres de liaison peuvent et doivent être utilisés.

Paramètres binaires

Malheureusement, ni le serveur MariaDB ni le serveur MySQL ne fournissent d'informations de type pour les instructions SQL préparées ; par conséquent, DBD::MariaDB n'a absolument aucun moyen de savoir si un paramètre de liaison particulier pour un emplacement de réservation doit être traité comme une chaîne Unicode ou comme un tampons orienté octets . Ainsi, les applications Perl qui utilisent DBD::MariaDB doivent fournir des informations sur le type correct.

De plus, l'API DBI pour do, execute et toutes les méthodes select* lie tous les paramètres comme de type "SQL_VARCHAR" . Actuellement, c'est une limitation de l'API qui ne permet pas de spécifier le type de liaison. Varchar est une chaîne et donc DBD::MariaDB les traite tous comme des chaînes Unicode .

La seule façon de spécifier un type en DBI est via la méthode bind_param. Son troisième argument prend une constante "SQL_*" qui définit un type pour le paramètre de liaison passé.

Les constantes de type suivantes sont traitées comme binaires par DBD::MariaDB : "SQL_BIT", "SQL_BLOB", "SQL_BINARY", "SQL_VARBINARY", "SQL_LONGVARBINARY".

Cette approche de la gestion des données binaires a été implémentée dans DBD::MariaDB car elle ne viole pas le fonctionnement du modèle Unicode de Perl, suit exactement la documentation de l'API DBI, et, plus important encore, est la façon dont les autres pilotes DBI (y compris DBD::Pg et DBD::SQLite) dans leurs versions récentes fonctionnent. Cela assure une bonne compatibilité pour les applications Perl qui utilisent plusieurs backends de bases de données et plusieurs pilotes DBI.

Veuillez noter que l'ancien pilote DBD::mysql en version 4.041 fonctionne différemment et a un support Unicode complètement cassé.

Pour illustrer l'utilisation, voir l'exemple suivant :

# Prepare statement
my $sth = $dbh->prepare(
    'INSERT INTO users (id, name, picture) VALUES (?, ?, ?)'
);
# Bind number, 7-bit ASCII values are always in Unicode and binary context
$sth->bind_param(1, 10);
# Bind name, may contains Unicode character, in this case U+00E9
$sth->bind_param(2, "Andr\x{E9}");
# Bind picture, it is a sequence of binary bytes, not Unicode code points
$sth->bind_param(3, "\x{D8}\x{A0}\x{39}\x{F8}", DBI::SQL_BINARY);
# Execute statement with bind parameters
$sth->execute();

Explication : Dans ce cas nombre 10 et name "Andr\x{E9}" seraient automatiquement encodés depuis les scalaires Unicode Perl vers le jeu de caractères réseau "utf8mb4" de MySQL et picture ne serait pas modifié car il était lié avec le type "DBI::SQL_BINARY" type. Notez que les valeurs ASCII 7 bits sont des invariants en UTF-8, elles ont les mêmes représentations en UTF-8, donc les opérations d'encodage et de décodage sont simplement des fonctions identité.

C'est la façon préférée et sûre de travailler avec les données binaires. Elle est également prise en charge par d'autres pilotes DBI, y compris DBD::Pg et DBD::SQLite (voir ci-dessus).

Dans DBD::MariaDB, il existe une autre façon spécifique de créer une instruction SQL avec des données binaires : appeler la méthode quote en spécifiant un type binaire. Cette méthode prend un paramètre de liaison et le quote + échappe correctement. Pour les types binaires, elle convertit l'argument en syntaxe HEX de MySQL ("X'...'") qui est du pur ASCII 7 bits et donc invariant pour UTF-8. Voir l'exemple suivant :

my $param1 = 10;
my $param2 = "Andr\x{E9}";
my $param3 = "\x{D8}\x{A0}\x{39}\x{F8}";
my $query = 'INSERT INTO users (id, name, picture) VALUES (' .
              $dbh->quote($param1) . ' ,' .
              $dbh->quote($param2) . ' ,' .
              $dbh->quote($param3, DBI::SQL_BINARY) .
            ')';
$dbh->do($query);

Les deux premiers paramètres sont quotés et échappés pour un encodage UTF-8 ultérieur (vers le jeu de caractères "utf8mb4" de MySQL) et le troisième paramètre est quoté et échappé comme un tampon binaire en syntaxe HEX de MySQL pour les blobs binaires.

Cette méthode n'est pas recommandée, car les méthodes de quoting, d'échappement et similaires peuvent facilement être écrites de manière incorrecte et conduire à des injections SQL et à d'autres problèmes de sécurité.

SUPPORT DES TRANSACTIONS

Le support des transactions fonctionne comme suit :

  • Par défaut, le mode AutoCommit est activé, conformément aux spécifications DBI.
  • Si vous exécutez 
    $dbh->{AutoCommit} = 0;

    ou

    $dbh->{AutoCommit} = 1;

    alors le pilote définira la variable de serveur MariaDB ou MySQL autocommit à 0 ou 1, respectivement. Le passage de 0 à 1 émettra également un "COMMIT", conformément aux spécifications DBI.

  • Les méthodes 
    $dbh->rollback();
$dbh->commit();

    émettront les commandes "ROLLBACK" et "COMMIT", respectivement. Un "ROLLBACK" sera également émis si le mode AutoCommit est désactivé et que la méthode DESTROY de la poignée de base de données est appelée. Encore une fois, cela suit les spécifications DBI.

Compte tenu de ce qui précède, vous devriez noter ce qui suit :

  • Vous ne devriez jamais changer manuellement la variable de serveur AutoCommit, sauf si vous ignorez le support des transactions de DBI.
  • Le changement du mode AutoCommit d'activé à désactivé ou inversement peut échouer. Vous devriez toujours vérifier les erreurs lors du changement du mode AutoCommit. La manière suggérée de le faire est d'utiliser le drapeau DBI RaiseError. Si vous n'aimez pas RaiseError, vous devez utiliser du code comme celui-ci : 
    $dbh->{AutoCommit} = 0;
if ($dbh->{AutoCommit}) {
    # An error occurred!
}
  • Si vous détectez une erreur lors du changement du mode AutoCommit, vous ne devriez plus utiliser la poignée de base de données. En d'autres termes, vous devriez vous déconnecter et vous reconnecter, car le mode de transaction est imprévisible. Vous pouvez également vérifier le mode de transaction en vérifiant la valeur de la variable de serveur autocommit. Cependant, un tel comportement n'est pas portable.
  • DBD::MariaDB a une fonctionnalité reconnect qui gère le fameux bug du matin de MySQL morning bug: Si le serveur s'est déconnecté, très probablement en raison d'un délai d'attente, alors par défaut le pilote se reconnectera et tentera d'exécuter à nouveau la même instruction SQL. Cependant, ce comportement est désactivé lorsque AutoCommit est désactivé : sinon l'état de la transaction serait complètement imprévisible après une reconnexion.
  • La fonctionnalité reconnect de DBD::MariaDB peut être activée ou désactivée en utilisant l'attribut mariadb_auto_reconnect . Ce comportement devrait être désactivé dans le code qui utilise LOCK TABLE, car si le serveur de base de données expire et que DBD::MariaDB se reconnecte, les verrous de table seront perdus sans aucune indication d'une telle perte.

JEUX DE RÉSULTATS MULTIPLES

DBD::MariaDB prend en charge les jeux de résultats multiples, grâce à Guy Harrison !

L'utilisation de base des jeux de résultats multiples est

do {
    while (my @row = $sth->fetchrow_array()) {
        do stuff;
    }
} while ($sth->more_results);

Un exemple serait :

$dbh->do('drop procedure if exists someproc')
    or print $DBI::errstr;
$dbh->do('create procedure someproc() deterministic
    begin
        declare a,b,c,d int;
        set a=1;
        set b=2;
        set c=3;
        set d=4;
        select a, b, c, d;
        select d, c, b, a;
        select b, a, c, d;
        select c, b, d, a;
    end'
) or die "$DBI::err: $DBI::errstr";
my $sth = $dbh->prepare('call someproc()')
    or die "$DBI::err: $DBI::errstr";
$sth->execute()
    or die "$DBI::err: $DBI::errstr";
my $i=0;
do {
    print "\nRowset ".++$i."\n---------------------------------------\n\n";
    foreach my $colno (0..$sth->{NUM_OF_FIELDS}-1) {
        print $sth->{NAME}->[$colno]."\t";
    }
    print "\n";
    while (my @row = $sth->fetchrow_array())  {
        foreach $field (0..$#row) {
            print $row[$field]."\t";
        }
        print "\n";
    }
} while ($sth->more_results);

Problèmes avec les jeux de résultats multiples

Veuillez noter qu'il pourrait y avoir des problèmes si vos jeux de résultats sont irréguliers, ce qui signifie que le nombre de colonnes de vos résultats varie. Des nombres de colonnes variables pourraient entraîner le plantage de votre script.

MULTITHREADING

Les capacités de multithreading de DBD::MariaDB dépendent complètement des bibliothèques C sous-jacentes. Les modules ne travaillent qu'avec les données des poignées, aucune variable globale n'est accédée et (à ma connaissance) aucune fonction non thread-safe n'est appelée. Ainsi, on croit que DBD::MariaDB est complètement thread-safe, si les bibliothèques C sont thread-safe et que vous ne partagez pas les poignées entre les threads.

La question évidente est : Les bibliothèques C sont-elles thread-safe ? Dans le cas de MySQL, la réponse est oui, depuis MySQL 5.5 elles le sont. Pour les versions plus anciennes, la bibliothèque C doit être compilée avec les options de configuration "--with-thread-safe-client" ou "--enable-thread-safe-client" .

REQUÊTES ASYNCHRONES

Vous pouvez effectuer une seule requête asynchrone par connexion MySQL ; cela vous permet de soumettre une requête longue au serveur et de faire informer une boucle d'événements lorsqu'elle est prête. Une requête asynchrone est démarrée soit en définissant l'attribut mariadb_async à une valeur vraie dans la méthode do ou dans la méthode prepare. Les instructions créées avec mariadb_async défini à vrai dans prepare exécutent toujours leurs requêtes de manière asynchrone lorsque execute est appelé. Le pilote propose également trois méthodes supplémentaires : mariadb_async_result(), mariadb_async_ready(), et mariadb_sockfd(). mariadb_async_result() renvoie ce que do ou execute aurait renvoyé ; c'est-à-dire le nombre de lignes affectées. mariadb_async_ready() renvoie vrai si mariadb_async_result() ne bloquera pas, et zéro sinon. Tous deux renvoient "undef" si cette poignée n'a pas été créée avec mariadb_async défini à vrai ou si une requête asynchrone n'a pas encore été démarrée. mariadb_sockfd() renvoie le numéro de descripteur de fichier pour la connexion MySQL ; vous pouvez l'utiliser dans une boucle d'événements.

Voici un exemple d'utilisation de l'interface de requête asynchrone :

use feature 'say';
$dbh->do('SELECT SLEEP(10)', { mariadb_async => 1 });
until($dbh->mariadb_async_ready()) {
    say 'not ready yet!';
    sleep 1;
}
my $rows = $dbh->mariadb_async_result();

Et un autre exemple :

my $fd = $dbh->mariadb_sockfd();
my $sth = $dbh->prepare('SELECT 1, SLEEP(10), t.id FROM t', { mariadb_async => 1 });
$sth->execute();
my $bits = '';
vec($bits, $fd, 1) = 1;
select($bits, undef, $bits, undef);
my $num_rows = $sth->mariadb_async_result();
print "num rows: $num_rows\n";
while (my @array = $sth->fetchrow_array()) {
    print "row:\n";
    print "\tvalue: $_\n" foreach @array;
}

À l'origine, il y avait un pilote non-DBI, Mysql, qui était très similaire aux pilotes PHP tels que mysql et mysqli. Le Mysql module a été écrit à l'origine par Andreas König (koenig@kulturbox.de) qui contribue encore, à ce jour, des correctifs à DBD::mysql. Une version émulée de Mysql a été fournie à DBD::mysql par Jochen Wiedmann, mais a finalement été dépréciée car c'était un autre ensemble de code à maintenir.

La première incarnation de DBD::mysql a été développée par Alligator Descartes, qui a également été aidé et soutenu par Gary Shea, Andreas König et Tim Bunce.

L'incarnation actuelle de DBD::mysql a été écrite par Jochen Wiedmann, puis de nombreuses modifications et corrections de bugs ont été ajoutées par Rudy Lippan. Ensuite, le support des instructions préparées a été ajouté par Patrick Galbraith et Alexy Stroganov (qui a également ajouté seul le support du serveur embarqué).

Depuis 2004, DBD::mysql est maintenu par Patrick Galbraith (patg@patg.net), et depuis 2013 avec l'aide précieuse de Michiel Beijen (michiel.beijen@gmail.com), ainsi que toute la communauté des développeurs Perl qui continuent d'envoyer des correctifs pour aider à améliorer DBD::mysql.

En 2018, la version non publiée 4.042_01 de DBD::mysql a été forkée et DBD::MariaDB a été créé pour corriger des bugs Unicode de longue date et le support de MariaDB. Le développement à cette époque a été soutenu par GoodData. Actuellement, il est hébergé sur Github dans le cadre du grand projet perl5-dbi et maintenu par Pali (pali@cpan.org).
