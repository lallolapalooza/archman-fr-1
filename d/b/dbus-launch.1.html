DESCRIPTIO

N

La commande dbus-launch est utilisée pour démarrer une instance de session de bus dbus-daemon depuis un script shell. Elle est normalement appelée depuis les scripts de connexion d'un utilisateur. Contrairement au démon lui-même, dbus-launch se termine, de sorte que les guillemets inversés ou la construction $() peuvent être utilisés pour lire les informations depuis dbus-launch

.

Sans arguments, dbus-launch lancera une instance de bus de session et imprimera l'adresse et le PID de cette instance sur la sortie

standard.

Vous pouvez spécifier un programme à exécuter ; dans ce cas, dbus-launch lancera une instance de bus de session, définira les variables d'environnement appropriées pour que le programme spécifié puisse trouver le bus, puis exécutera le programme spécifié avec les arguments spécifiés. Voir ci-dessous pour des

exemples.

Si vous lancez un programme, dbus-launch n'imprimera pas les informations sur le nouveau bus sur la sortie

standard.

Quand dbus-launch imprime les informations du bus sur la sortie standard, par défaut, elles sont au format simple de paires clé-valeur. Cependant, vous pouvez demander plusieurs syntaxes alternatives en utilisant les options --sh-syntax, --csh-syntax, --binary-syntax ou --auto-syntax. Plusieurs d'entre elles font que dbus-launch émet du code shell pour configurer l'environnement

.

Avec l'option --auto-syntax, dbus-launch examine la valeur de la variable d'environnement SHELL pour déterminer quelle syntaxe de shell doit être utilisée. Si SHELL se termine par "csh", du code compatible csh est émis ; sinon, du code Bourne shell est émis. Au lieu de passer --auto-syntax, vous pouvez explicitement en spécifier une en utilisant --sh-syntax pour la syntaxe Bourne, ou --csh-syntax pour la syntaxe csh. Dans les scripts, il est plus robuste d'éviter --auto-syntax et vous savez probablement dans quel shell votre script est

écrit.

Voir https://www.freedesktop.org/wiki/Software/dbus/ pour plus d'informations sur D-Bus. Voir aussi la page man pour dbus-daemo

n
.

EXEMPLE

S

Les distributions qui exécutent dbus-launch comme partie d'une session X standard devraient exécuter dbus-launch --exit-with-session après que le serveur X a démarré et est devenu disponible, comme un enveloppeur autour du client X "principal" (généralement un gestionnaire de session ou de fenêtre), comme dans ces exemples

:

dbus-launch --exit-with-session

gnome-session

dbus-launch --exit-with-session

openbox

dbus-launch --exit-with-session ~/.

xsession

Si votre distribution ne fait pas cela, vous pouvez obtenir des résultats similaires en exécutant votre session ou gestionnaire de fenêtres de la même manière dans un script exécuté par votre session X, comme ~/.xsession, ~/.xinitrc ou ~/.

Xclients.

Pour démarrer une session D-Bus dans une session en mode texte, n'utilisez pas dbus-launch. À la place, voir dbus-run-sess

ion(1).

LANCEMENT

AUTOMATIQUE

Si DBUS_SESSION_BUS_ADDRESS n'est pas défini pour un processus qui essaie d'utiliser D-Bus, par défaut, le processus essaiera d'invoquer dbus-launch avec l'option --autolaunch pour démarrer un nouveau bus de session ou trouver l'adresse du bus existant sur l'affichage X ou dans un fichier dans ~/.dbus/session-bus

/

Chaque fois qu'un lancement automatique se produit, l'application qui a dû démarrer un nouveau bus sera dans son propre petit monde ; elle peut finir par démarrer une toute nouvelle session si elle essaie d'utiliser beaucoup de services de bus. Cela peut être sous-optimal ou même totalement cassé, selon l'application et ce qu'elle essaie de

faire.

Il y a deux raisons courantes de lancement automatique. L'une est ssh vers une machine distante. L'idéal serait de transférer DBUS_SESSION_BUS_ADDRESS de la même manière que DISPLAY est transféré. En attendant, vous pouvez modifier le fichier de configuration session.conf pour que votre bus de session écoute sur TCP, et définir manuellement DBUS_SESSION_BUS_ADDRESS, si vous le

souhaitez.

La deuxième raison courante de lancement automatique est un su vers un autre utilisateur, et l'affichage d'applications X exécutées par le second utilisateur sur l'affichage appartenant au premier utilisateur. Peut-être que l'idéal dans ce cas serait de permettre au second utilisateur de se connecter au bus de session du premier utilisateur, tout comme il peut se connecter à l'affichage du premier utilisateur. Cependant, un mécanisme pour cela n'a pas été

codé.

Vous pouvez toujours éviter le lancement automatique en définissant manuellement DBUS_SESSION_BUS_ADDRESS. Le lancement automatique se produit parce que l'adresse par défaut si aucune n'est définie est "autolaunch:", donc si une autre adresse est définie, il n'y aura pas de lancement automatique. Vous pouvez cependant inclure autolaunch dans une adresse de bus de session explicite comme solution de repli, par exemple DBUS_SESSION_BUS_ADDRESS="something:,autolaunch:" - dans ce cas, si la première adresse ne fonctionne pas, les processus feront un lancement automatique. (La variable d'adresse de bus contient une liste d'adresses séparées par des virgules à essayer.

)

L'option --autolaunch est considérée comme un détail d'implémentation interne d

e libdbus, et en fait, il y a des plans pour la changer. Il n'y a aucune raiso
n réelle de l'utiliser en dehors de l'implémentation de libdbus de toute façon.

OPTION

S

Les options suivantes sont prises en charge

:

--auto-synta

x
Choisir --csh-syntax ou --sh-syntax en fonction de la variable d'environnement
SHELL.

--binary-synta

x
Écrire sur stdout une adresse de bus terminée par un nul, puis le PID du bus comme un entier binaire de taille sizeof(pid_t), puis l'ID de fenêtre X du bus comme un entier binaire de taille sizeof(long). Les entiers sont dans l'ordre des octets de la machine, pas dans l'ordre des octets réseau ou tout autre ordre d'octets
canonique.

--close-stder

r
Fermer le flux de sortie d'erreur standard avant de démarrer le démon D-Bus. C'est utile si vous voulez capturer les messages d'erreur de dbus-launch mais que vous ne voulez pas que dbus-daemon garde le flux ouvert vers votre
application.

--config-file=FILENAM

E
Passer --config-file=FILENAME au démon de bus, au lieu de lui passer l'argument --session. Voir la page man pour
dbus-daemon

--csh-synta

x
Émettre du code compatible csh pour configurer les variables d'environnement
.

--exit-with-x1

1
Si cette option est fournie, un processus persistant "babysitter" sera créé, et se connectera au serveur X. S'il ne peut pas le faire, le lancement échoue. Si le processus "babysitter" perd sa connexion X, il tue le démon de bus de messages, déconnectant tous ses clients (qui devraient se terminer en réponse). Cela évite d'avoir des processus démon résiduels d'une session X utilisateur, après que la session X s'est
terminée.

--exit-with-sessio

n
Si cette option est fournie, un processus persistant "babysitter" sera créé, comme pour --exit-with-x11. S'il ne peut pas se connecter au serveur X, il surveillera le terminal à partir duquel dbus-launch a été démarré à la place, et s'il reçoit un HUP sur stdin, le démon de bus de messages sera tué. Cette option n'est pas recommandée, car elle consommera l'entrée du terminal où elle a été démarrée ; elle est principalement fournie pour la rétrocompatibilité
.

--autolaunch=MACHINEI

D
Cette option implique que dbus-launch devrait scanner pour une session précédemment démarrée et réutiliser les valeurs trouvées là. Si aucune session n'est trouvée, elle démarrera une nouvelle session. L'option --exit-with-session est impliquée si --autolaunch est donné. Cette option est pour l'usage exclusif de libdbus, vous ne voulez pas l'utiliser manuellement. Elle peut changer dans le
futur.

--sh-synta

x
Émettre du code compatible Bourne-shell pour configurer les variables d'environnement
.

--versio

n
Imprimer la version de
dbus-launch

--hel

p
Imprimer les inf
ormations d'aid
e de dbus-launch on class="Sh">

NOTE

S

Si vous exécutez dbus-launch myapp (avec n'importe quelles autres options), dbus-daemon ne se terminera pas lorsque myapp se termine : c'est parce que myapp est supposé faire partie d'une session plu

s grande, plutôt qu'une
session à part entière.
