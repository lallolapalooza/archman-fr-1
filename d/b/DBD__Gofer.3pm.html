DESCRIPTION DBD::Gofer est un pilote de base de données DBI qui transmet les requêtes à un autre pilote DBI, généralement dans un processus séparé, souvent sur une machine séparée. Il essaie d'être aussi transparent que possible afin qu'il semble que vous utilisez directement le pilote distant. DBD::Gofer est très similaire à DBD::Proxy. La principale différence est qu'avec DBD::Gofer, aucun état n'est maintenu côté distant. Cela signifie que chaque requête contient toutes les informations nécessaires pour créer l'état requis. (Ainsi, par exemple, chaque requête inclut le DSN auquel se connecter.) Chaque requête peut être envoyée à n'importe quel serveur disponible. Le serveur exécute la requête et renvoie une seule réponse qui inclut toutes les données. C'est très similaire à la façon dont http fonctionne comme protocole sans état pour le web. Chaque requête de votre navigateur web peut être traitée par un processus de serveur web différent. Cas

d'utilisation

Cela peut sembler une surcharge inutile, mais il y a des situations où c'est très bien. Considérons un cas spécifique. Imaginez l'utilisation de DBD::Gofer avec un transport http. Votre application appelle connect() , prepare("select * from table where foo=?")

AVERTISSEMENTS POUR DES MÉTHODES SPÉCIFIQUES

last_insert_id

Pour activer l'utilisation de last_insert_id, vous devez indiquer à DBD::Gofer que vous souhaitez l'utiliser. Vous le faites en ajoutant un "go_last_insert_id_args" attribut aux do() ou prepare() appels de méthode. Par exemple :

$dbh->do($sql, { go_last_insert_id_args => [...] });

ou

$sth = $dbh->prepare($sql, { go_last_insert_id_args => [...] });

La référence de tableau doit contenir les arguments que vous souhaitez transmettre à la last_insert_id() méthode.

execute_for_fetch

Les méthodes de tableau bind_param_array() et execute_array() sont prises en charge. Quand execute_array() est appelée, les données sont sérialisées et exécutées en un seul aller-retour vers le serveur Gofer. Cela la rend très rapide, mais nécessite suffisamment de mémoire pour stocker toutes les données sérialisées.

La execute_for_fetch() méthode n'est actuellement pas optimisée, elle utilise le comportement de repli du DBI en exécutant chaque tuple individuellement. (Elle pourrait être implémentée comme un wrapper pour execute_array() - les patches sont les bienvenus.)

TRANSPORTS

DBD::Gofer ne se préoccupe pas du transport des requêtes et des réponses. Pour cela, il utilise des modules de transport Gofer spéciaux.

Les modules de transport Gofer viennent généralement par paires : un pour le pilote 'client' DBD::Gofer et un pour l'extrémité 'serveur' distante. Ils ont des noms très similaires :

DBD::Gofer::Transport::<foo>
DBI::Gofer::Transport::<foo>

Parfois, les transports des côtés DBD et DBI peuvent avoir des noms différents. Par exemple, DBD::Gofer::Transport::http est typiquement utilisé avec DBI::Gofer::Transport::mod_perl (les modules DBD::Gofer::Transport::http et DBI::Gofer::Transport::mod_perl font partie de la distribution GoferTransport-http).

Transports fournis

Plusieurs modules de transport sont fournis avec DBD::Gofer :

null

Le transport null est le plus simple de tous. Il ne transporte en fait la requête nulle part. Il sérialise simplement (gèle) la requête en une chaîne, puis la dégèle en une structure de données avant de la passer à DBI::Gofer::Execute pour exécution. Le même gel et dégel est appliqué aux résultats.

Le transport null est le meilleur moyen de tester si votre application fonctionnera avec Gofer. Réglez simplement la variable d'environnement DBI_AUTOPROXY sur ""dbi:Gofer:transport=null;policy=pedantic"" (voir "Utilisation de DBI_AUTOPROXY" ci-dessous) et lancez votre application, ou idéalement sa suite de tests, comme d'habitude.

Il ne prend aucun paramètre.

pipeone

Le transport pipeone lance un sous-processus pour chaque requête. Il transmet la requête et lit la réponse.

Le fait qu'un nouveau sous-processus soit démarré pour chaque requête garantit que le côté serveur est véritablement sans état. Bien que cela rende le transport très lent, il est utile comme moyen de tester que votre application ne dépend pas d'un état par connexion, comme des tables temporaires, persistant entre les requêtes.

Il est également utile à la fois comme preuve de concept et comme classe de base pour le pilote stream.

stream

Le pilote stream lance également un sous-processus et écrit des requêtes et lit des réponses, comme le transport pipeone. Dans ce cas, cependant, le sous-processus est censé gérer plus d'une requête. (Bien qu'il sera automatiquement redémarré s'il se termine.)

C'est le premier transport qui est véritablement utile car il peut lancer le sous-processus sur une machine distante en utilisant "ssh". Cela signifie que vous pouvez maintenant utiliser DBD::Gofer pour accéder facilement à toutes les bases de données accessibles depuis tout système sur lequel vous pouvez vous connecter. Vous obtenez également tous les avantages de ssh, y compris le chiffrement et la compression optionnelle.

Voir "Utilisation de DBI_AUTOPROXY" ci-dessous pour un exemple.

Autres transports

Implémenter un transport Gofer est très simple, et plus de transports sont très bienvenus. Jetez simplement un œil à des transports existants qui sont similaires à vos besoins.

http

Voir la distribution GoferTransport-http sur CPAN : http://search.cpan.org/dist/GoferTransport-http/

Gearman

Je sais qu'Ask Bjørn Hansen a implémenté un transport pour le "gearman" système de tâches distribuées, bien qu'il ne soit pas sur CPAN au moment de la rédaction de ceci.

CONNEXION

Simplement préfixez votre DSN existant avec ""dbi:Gofer:transport=$transport;dsn="" où $transport est le nom du transport Gofer que vous souhaitez utiliser (voir "TRANSPORTS"). Les "transport" et "dsn" attributs doivent être spécifiés et le "dsn" attribut doit être en dernier.

D'autres attributs peuvent être spécifiés dans le DSN pour configurer DBD::Gofer et/ou le module de transport Gofer utilisé. Les principaux attributs après "transport"sont "url" et "policy". Ceux-ci et d'autres attributs sont décrits ci-dessous.

Utilisation de DBI_AUTOPROXY

La façon la plus simple d'essayer DBD::Gofer est de régler la variable d'environnement DBI_AUTOPROXY. Dans ce cas, vous n'incluez pas la "dsn=" partie. Par exemple :

export DBI_AUTOPROXY="dbi:Gofer:transport=null"

ou, pour un exemple plus utile, essayez :

export DBI_AUTOPROXY="dbi:Gofer:transport=stream;url=ssh:user@example.com"

Attributs de connexion

Ces attributs peuvent être spécifiés dans le DSN. Ils peuvent également être transmis dans le paramètre \%attr de la méthode connect du DBI en ajoutant un ""go_"" au début du nom.

transport

Spécifie la classe de transport Gofer à utiliser. Requis. Voir "TRANSPORTS" ci-dessus.

Si la valeur n'inclut pas "::" alors ""DBD::Gofer::Transport::"" est préfixé.

L'objet transport peut être accessible via $h->{go_transport}.

dsn

Spécifie le DSN auquel le côté distant doit se connecter. Requis, et doit être en dernier.

url

Utilisé pour indiquer au transport où se connecter. La forme exacte de la valeur dépend du transport utilisé.

policy

Spécifie la politique à utiliser. Voir "CONFIGURATION DU COMPORTEMENT DE LA POLITIQUE".

Si la valeur n'inclut pas "::" alors ""DBD::Gofer::Policy"" est préfixé.

L'objet politique peut être accessible via $h->{go_policy}.

timeout

Spécifie un délai d'attente, en secondes, à utiliser en attendant les réponses du côté serveur.

retry_limit

Spécifie le nombre de fois qu'une requête échouée sera réessayée. La valeur par défaut est 0.

retry_hook

Spécifie une référence de code à appeler pour décider si une requête échouée doit être réessayée. La référence de code est appelée comme ceci :

$transport = $h->{go_transport};
$retry = $transport->go_retry_hook->($request, $response, $transport);

Si elle retourne vrai, la requête sera réessayée, jusqu'à la "retry_limit". Si elle retourne une valeur faible mais définie, la requête ne sera pas réessayée. Si elle retourne undef, alors le comportement par défaut sera utilisé, comme si "retry_hook" n'avait pas été spécifié.

Le comportement par défaut est de réessayer les requêtes où $request->is_idempotent est vrai, ou où le message d'erreur correspond à "/induced by DBI_GOFER_RANDOM/".

cache

Spécifie qu'un cache côté client doit être effectué. La valeur est le nom d'une classe de cache à utiliser.

Toute classe implémentant les méthodes get($key) et set($key, $value) peut être utilisée. Cela inclut un grand nombre de puissantes classes de cache sur CPAN, y compris les distributions Cache et Cache::Cache.

Vous pouvez utiliser ""cache=1"" comme raccourci pour ""cache=DBI::Util::CacheMemory"". Voir DBI::Util::CacheMemory pour une description de ce cache par défaut simple et rapide.

L'objet cache peut être accessible via $h->go_cache. Par exemple :

$dbh->go_cache->clear; # libérer la mémoire utilisée par le cache

Les clés du cache sont les requêtes gelées (sérialisées), et les valeurs sont les réponses gelées.

Le comportement par défaut est d'utiliser le cache uniquement pour les requêtes où $request->is_idempotent est vrai (c'est-à-dire, le dbh a l'attribut ReadOnly défini ou l'instruction SQL est manifestement un SELECT sans clause FOR UPDATE.)

Pour un contrôle encore plus grand, vous pouvez utiliser l' "go_cache" attribut pour transmettre un objet cache instancié. Des méthodes individuelles, y compris >prepare(), peut également spécifier des caches alternatifs via l'attribut "go_cache" . Par exemple, pour spécifier l'absence de mise en cache pour une requête particulière, vous pourriez utiliser

$sth = $dbh->prepare( $sql, { go_cache => 0 } );

Cela peut être utilisé pour implémenter différentes politiques de mise en cache pour différentes instructions.

Il est intéressant de noter que DBD::Gofer peut être utilisé pour ajouter une mise en cache côté client à n'importe quelle application (compatible gofer), sans modification de code et sans nécessiter de serveur gofer. Il suffit de définir la variable d'environnement DBI_AUTOPROXY comme ceci :

DBI_AUTOPROXY='dbi:Gofer:transport=null;cache=1'

CONFIGURATION DE LA POLITIQUE DE COMPORTEMENT

DBD::Gofer prend en charge un mécanisme de « politique » qui vous permet d'ajuster finement le nombre d'aller-retours vers le serveur Gofer. Les politiques sont regroupées en classes (qui peuvent être sous-classées) et référencées par le nom de la classe.

La classe DBD::Gofer::Policy::Base est la classe de base pour tous les paquets de politique et décrit toutes les politiques disponibles.

Trois paquets de politique sont fournis avec DBD::Gofer :

DBD::Gofer::Policy::pedantic est le plus « transparent » mais le plus lent car il effectue plus d'aller-retours vers le serveur Gofer.

DBD::Gofer::Policy::classic est un compromis raisonnable - c'est la politique par défaut.

DBD::Gofer::Policy::rush est le plus rapide, mais peut nécessiter des modifications de code dans vos applications.

En général, la politique par défaut "classic" convient. Lorsque vous testez pour la première fois une application existante avec Gofer, il est conseillé de commencer avec la politique "pedantic" et de passer ensuite à "classic" ou à une politique personnalisée, pour les tests finaux.
