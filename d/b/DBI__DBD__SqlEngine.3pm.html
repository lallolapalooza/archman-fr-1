DESCRIPTIO

N

DBI::DBD::SqlEngine abstrait l'utilisation des moteurs SQL du DBD. Les auteurs de DBD peuvent se concentrer sur la récupération des données qu'ils souhaitent

fournir.

Il est fortement recommandé de lire DBD::File::Developers et DBD::File::Roadmap, car une grande partie de l'API de DBD::File est fournie par DBI::DBD::

SqlEngine.

Actuellement, l'API de DBI::DBD::SqlEngine est expérimentale et changera probablement dans un futur proche pour fournir les bases des métadonnées de table comme DBD::

File.

DBI::DBD::SqlEngine s'attend à ce que tout pilote dans la chaîne d'héritage ait un préfixe

DBI.

sql_identifier_cas

e

Contient la manière dont DBI::DBD::SqlEngine traite les identifiants SQL non quotés

: 
* SQL_IC_UPPER (1) signifie que tous les identifiants sont convertis
    en interne en leurs équivalents en majuscules
* SQL_IC_LOWER (2) signifie que tous les identifiants sont convertis
    en interne en leurs équivalents en minuscules
* SQL_IC_MIXED (4) signifie que tous les identifiants sont tels
quels

Ces conversions se produisent si (et seulement si) aucun identifiant existant ne correspond. Une fois qu'un identifiant existant est utilisé, il est

connu.

Les classes d'exécution des instructions SQL n'ont pas à s'en soucier, n'attendez donc pas à ce que "sql_identifier_case" affecte les noms de colonnes dans des instructions

comme 
SELECT * FROM
foo

sql_quoted_identifier_cas

e

Contient la manière dont DBI::DBD::SqlEngine traite les identifiants SQL quotés (lecture seule). Il est fixé à SQL_IC_SENSITIVE (3), qui est interprété comme

SQL_IC_MIXED.

sql_flag

s

Contient des indicateurs supplémentaires pour instancier un SQL::Parser. Parce qu'un SQL::Parser n'est instancié qu'une seule fois, il est recommandé de définir cet indicateur avant l'exécution de toute

instruction.

sql_dialec

t

Contrôle le dialecte compris par SQL::Parser. Valeurs possibles (état de livraison de SQL::Statement)

: 
* ANSI
* CSV
*
AnyData

Par défaut "CSV". Parce qu'un SQL::Parser n'est instancié qu'une seule fois et que SQL::Parser ne permet pas de modifier le dialecte une fois instancié, il est fortement recommandé de définir cet indicateur avant l'exécution de toute instruction (le meilleur endroit est le hachage d'attributs de connexion)

.

sql_engine_in_gofe

r

Cette valeur est vraie dans le cas où ce pilote est opéré via DBD::Gofer. L'impact d'être opéré via Gofer est un pilote en lecture seule (pas des bases de données en lecture seule !), vous ne pouvez donc modifier aucun attribut plus tard - ni aucun paramètre de table. Mais vous n'obtiendrez pas d'erreur dans les cas où vous modifiez des attributs de table, veuillez donc surveiller attentivement "sql_engine_in_gofer"

.

sql_met

a

Zone de données privée qui contient des informations sur les tables gérées par ce module. Les métadonnées de table peuvent ne pas être disponibles jusqu'à ce que la table ait été accédée pour la première fois, par exemple en émettant un select dessus, mais il est possible de pré-initialiser des attributs pour chaque table que vous

utilisez.

DBI::DBD::SqlEngine reconnaît les attributs (publics) "col_names", "table_name", "readonly", "sql_data_source" et "sql_identifier_case". Soyez très prudent lorsque vous modifiez des attributs que vous ne connaissez pas, la conséquence pourrait être une table détruite ou

corrompue.

Bien que "sql_meta" soit un attribut privé et en lecture seule (ce qui signifie que vous ne pouvez pas modifier ses valeurs), les pilotes dérivés peuvent fournir un accès en écriture restreint via un autre attribut. Les accesseurs bien connus sont "csv_tables" pour DBD::CSV, "ad_tables" pour DBD::AnyData et "dbm_tables" pour DBD::

DBM.

Méthodes DBI par

défaut

data_source

s

La méthode "data_sources" renvoie une liste des sous-répertoires du répertoire courant sous la forme "dbi:CSV:f_dir=$dirname"

.

Si vous voulez lire les sous-répertoires d'un autre répertoire,

utilisez 
my ($drh)  = DBI->install_driver ("CSV");
my (@list) = $drh->data_sources (f_dir => "/usr/local/csv_data")
;

list_table

s

Cette méthode renvoie une liste de noms de fichiers à l'intérieur de $dbh->{f_dir}. Exemple

: 
my ($dbh)  = DBI->connect ("dbi:CSV:f_dir=/usr/local/csv_data");
my (@list) = $dbh->func ("list_tables")
;

Notez que la liste inclut tous les fichiers contenus dans le répertoire, même ceux qui ont des noms de tables non valides du point de vue de

SQL.

Méthodes

supplémentaires

Les méthodes suivantes ne sont disponibles que sous leur nom documenté lorsque DBI::DBD::SQlEngine est utilisé directement. Comme cela n'est raisonnable que pour des fins de test, les vrais noms doivent être utilisés à la place. Ces noms peuvent être calculés en remplaçant le "sql_" dans le nom de la méthode par le préfixe du

pilote.

sql_version

s

Signature

: 
sub sql_versions (;$) {
  my ($table_name) = @_;
  $table_name ||= ".";
  ...
}

Renvoie les versions du pilote, incluant la version de DBI, la version de Perl, la version de DBI::PurePerl (si DBI::PurePerl est actif) et la version du moteur SQL

utilisé. 
my $dbh = DBI->connect ("dbi:File:");
my $sql_versions = $dbh->func( "sql_versions" );
print "$sql_versions\n";
__END__
# DBI::DBD::SqlEngine  0.05 using SQL::Statement 1.402
# DBI                  1.623
# OS                   netbsd (6.99.12)
# Perl                 5.016002 (x86_64-netbsd-thread-multi
)

Appelé en contexte de liste, sql_versions renverra un tableau contenant chaque ligne comme entrée

unique.

Certains pilotes pourraient utiliser l'argument optionnel (nom de table) et modifier les informations de version liées à la table (par exemple, DBD::DBM fournit des informations sur le backend de stockage pour la table demandée, lorsqu'elle a un nom de table)

.

Extensibilit

DBI::DBD::SqlEngine::

TableSource

Fournit des sources de données et des informations sur les tables au niveau du pilote de base de données et du handle de base de

données. 
package DBI::DBD::SqlEngine::TableSource;
sub data_sources ($;$)
{
  my ( $class, $drh, $attrs ) = @_;
  ...
}
sub avail_tables
{
  my ( $class, $drh ) = @_;
  ...
}

La méthode "data_sources" est appelée lorsque l'utilisateur invoce l'une des commandes suivantes

: 
@ary = DBI->data_sources($driver);
@ary = DBI->data_sources($driver, \%attr);
@ary = $dbh->data_sources();
@ary = $dbh->data_sources(\%attr)
;

La méthode "avail_tables" est appelée lorsque l'utilisateur invoce l'une des commandes suivantes

: 
@names = $dbh->tables( $catalog, $schema, $table, $type );
$sth = $dbh->table_info( $catalog, $schema, $table, $type );
$sth = $dbh->table_info( $catalog, $schema, $table, $type, \%attr );
$dbh->func( "list_tables" )
;

Chaque fois qu'un argument "\%attr" peut être spécifié, l'attribut "sql_table_source" de cet objet "\%attr" est préféré à l'attribut $dbh ou à la valeur par défaut du pilote, par

exemple 
@ary = DBI->data_sources("dbi:CSV:", {
  f_dir => "/your/csv/tables",
  # note: this class doesn't comes with DBI
  sql_table_source => "DBD::File::Archive::Tar::TableSource",
  # scan tarballs instead of directories
})
;

Lorsque vous allez implémenter une telle classe DBD::File::Archive::Tar::TableSource, n'oubliez pas d'ajouter les attributs corrects (y compris "sql_table_source" et "sql_data_source") aux DSN

renvoyés.

DBI::DBD::SqlEngine::

DataSource

Fournit la fonctionnalité de base pour gérer les tables. Elle est principalement conçue pour permettre un accès transparent aux fichiers sur disque ou aux (flux de) fichiers déjà ouverts (par exemple pour DBD::CSV)

.

Les classes dérivées devraient également être restreintes à des fonctionnalités similaires (par exemple, ouvrir des flux depuis une archive, compresser/décompresser de manière transparente des fichiers de journal avant de les

analyser, 
package DBI::DBD::SqlEngine::DataSource;
sub complete_table_name ($$;$)
{
  my ( $self, $meta, $table, $respect_case ) = @_;
  ...
}

La méthode "complete_table_name" est appelée lors de la première configuration des informations méta pour une table

: 
"SELECT user.id, user.name, user.shell FROM user WHERE ...
"

résulte en l'ouverture de la table "user". La première étape du processus d'ouverture de la table est la complétion du nom. Imaginons que vous ayez un handle DBD::CSV avec les paramètres suivants

: 
$dbh->{sql_identifier_case} = SQL_IC_LOWER;
$dbh->{f_ext} = '.lst';
$dbh->{f_dir} = '/data/web/adrmgr'
;

Ces paramètres résulteront en la recherche de fichiers correspondant à "[Uu][Ss][Ee][Rr](\.lst)?$" dans "/data/web/adrmgr/". Le balayage du répertoire "/data/web/adrmgr/" et la vérification de correspondance du motif seront effectués dans "DBD::File::DataSource::File" par la méthode "complete_table_name"

.

Si vous avez l'intention de fournir d'autres sources de flux de données que des fichiers, en plus de fournir une méthode "complete_table_name" appropriée, une méthode pour ouvrir la ressource est requise

: 
package DBI::DBD::SqlEngine::DataSource;
sub open_data ($)
{
  my ( $self, $meta, $attrs, $flags ) = @_;
  ...
}

Après que la méthode "open_data" a été exécutée avec succès, les informations méta de la table sont dans un état qui permet aux méthodes d'accès aux donnée

s de la table de pouvoir récupérer/stocker les informations de ligne.
Les détails d'implémentation dépendent fortement de l'implémentation
de la table, dont la plus célèbre est sans doute DBD::File::Table.

MOTEURS

SQL

DBI::DBD::SqlEngine prend actuellement en charge deux moteurs SQL : SQL::Statement et DBI::SQL::Nano::Statement_. DBI::SQL::Nano prend en charge un sous-ensemble très limité d'instructions SQL, mais il pourrait être plus rapide pour certaines tâches très simples. SQL::Statement, en revanche, prend en charge un sous-ensemble beaucoup plus large d'ANSI

SQL.

Pour utiliser SQL::Statement, vous avez besoin d'au moins la version 1.401 de SQL::Statement et la variable d'environnement "DBI_SQL_NANO" ne doit pas être

définie à une
valeur vraie.
