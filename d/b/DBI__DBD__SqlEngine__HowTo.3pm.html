Comment les attributs arrivent-ils dans le DBD et comment peuvent-ils être récupérés par l'utilisateur ? Bonne question, mais vous devriez le savoir car vous avez lu

la

sub init_valid_attributes
{

    $dbh->SUPER::init_valid_attributes ();

        foo_version         => 1,   # contient la version de ce pilote
        foo_valid_attrs     => 1,   # contient les attributs valides des pilotes foo
        foo_readonly_attrs  => 1,   # contient les attributs immuables des pilotes foo
        foo_bar             => 1,   # contient l'attribut bar
        foo_baz             => 1,   # contient l'attribut baz
        foo_manager         => 1,   # contient le gestionnaire de l'instance de pilote
        foo_manager_type    => 1,   # contient la classe de gestionnaire de l'instance de pilote
    };

        foo_version         => 1,   # s'assurer que personne ne modifie la version du pilote
        foo_valid_attrs     => 1,   # ne pas permettre d'ajouter d'autres attributs valides ...
        foo_readonly_attrs  => 1,   # ... ou de rendre les immuables mutables

Jusqu'ici,

nous pouvons empêcher les utilisateurs d'utiliser notre pilote de base de données comme stockage de données pour n'impo

rte quoi et n'importe quoi d'autre. Nous ne nous soucions que des choses vraiment importantes pour la paix dans le
monde et des attributs similaires. Mais en fait, le pilote ne peut toujours rien faire. Il peut faire moins que rien -

entre-temps

,

ce n'est plus une zone de stockage stupide. Confort de l'utilisateur « DBI::DBD::SqlEngine » depuis 0.05 consolide toutes les métadonnées persistantes d'une table dans une seule structure stockée dans « $dbh->{sql_meta} ». Bien que DBI::DBD::SqlEngine ne fournit qu'un accès en

lecture

seule à cette structure, les modifications sont toujours autorisées. Principalement, DBI::DBD:: SqlEngine fournit l'accès via les accesseurs « new_sql_engine_meta », « get_sql_engine_meta », « get_single_table_meta », « set_single_table_meta », « set_sql_engine_meta » et « clear_sql_engine_meta ». Ces méthodes sont facilement accessibles par les utilisateurs via l'interface « $dbh->func () » fournie par DBI. Eh

bien, 
beaucoup d'utilisateurs ne se sentent pas
    à l'aise en appelant
# ne pas exiger d'extension pour les tables
cars

$dbh->func ("cars", "f_ext", ".csv", "set_sql_engine_meta"); DBI::DBD::SqlEngine injectera une méthode dans

votre 
pilote pour
    augmenter le confort de l'utilisateur et permettre :
# ne pas exiger
d'extension

pour les tables cars $dbh->foo_set_meta

("cars", 
"f_ext", ".csv");
Mieux, mais ici et là les utilisateurs aiment faire :
# ne pas exiger
d'extension

pour les tables cars $dbh->{foo_tables}->{cars}->{f_ext} = ".csv"; Cette interface est fournie lorsque les DBD dérivés définissent ce qui suit dans

« 
init_valid_attributes » (revoir
    « Gestion de vos propres attributs ») :
sub init_valid_attributes
{
    my $dbh = $_[0];
    $dbh->SUPER::init_valid_attributes ();
    $dbh->{foo_valid_attrs} = {
        foo_version         => 1,   # contient la version de ce pilote
        foo_valid_attrs     => 1,   # contient les attributs valides des pilotes foo
        foo_readonly_attrs  => 1,   # contient les attributs immuables des pilotes foo
        foo_bar             => 1,   # contient l'attribut bar
        foo_baz             => 1,   # contient l'attribut baz
        foo_manager         => 1,   # contient le gestionnaire de l'instance de pilote
        foo_manager_type    => 1,   # contient la classe de gestionnaire de l'instance de pilote
        foo_meta            => 1,   # contient l'interface publique pour modifier les attributs méta de table
    };
    $dbh->{foo_readonly_attrs} = {
        foo_version         => 1,   # s'assurer que personne ne modifie la version du pilote
        foo_valid_attrs     => 1,   # ne pas permettre d'ajouter d'autres attributs valides ...
        foo_readonly_attrs  => 1,   # ... ni de rendre l'immuable mutable
        foo_manager         => 1,   # le gestionnaire n'est défini qu'en interne
        foo_meta            => 1,   # s'assurer que l'interface publique pour modifier les attributs méta de la table est immuable
    };
    $dbh->{foo_meta} = "foo_tables";
    return $dbh;
}

Cela fournit un hachage lié dans "$dbh->{foo_tables}" et un hachage lié pour les métadonnées de chaque table dans "$dbh->{foo_tables}->{$table_name}". Les modifications des attributs méta de la table sont effectuées à l'aide des méthodes de table

: 
sub get_table_meta_attr { ... }
sub set_table_meta_attr { ...
}

Les deux méthodes peuvent ajuster le nom de l'attribut pour des raisons de compatibilité, par exemple lorsque les anciennes versions du DBD permettaient d'utiliser des noms différents pour le même drapeau

: 
my %compat_map = (
                   abc => 'foo_abc',
                   xyz => 'foo_xyz',
                 );
__PACKAGE__->register_compat_map( \%compat_map )
;

Si toute modification utilisateur sur un attribut méta nécessite la réinitialisation de la structure méta (dans le cas de "DBI::DBD::SqlEngine", il s'agit des attributs "f_file", "f_dir", "f_ext" et "f_lockfile"), informez DBI::DBD::SqlEngine en

faisant 
my %reset_on_modify = (
                        foo_xyz => "foo_bar",
                        foo_abc => "foo_bar",
                      );
__PACKAGE__->register_reset_on_modify( \%reset_on_modify )
;

Le prochain accès aux métadonnées de la table forcera DBI::DBD::SqlEngine à refaire l'ensemble du processus d'initialisation des

métadonnées.

Toute action supplémentaire qui doit être prise peut être gérée dans "table_meta_attr_c

hanged" : 
sub table_meta_attr_changed
{
    my ($class, $meta, $attrib, $value) = @_;
    ...
    $class->SUPER::table_meta_attr_changed ($meta, $attrib, $value);
}

Cela est fait avant que la nouvelle valeur ne soit définie dans $meta, de sorte que le gestionnaire de changement d'att

ribut puisse agir en fo
nction de l'ancienne valeur.
