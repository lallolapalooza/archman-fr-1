NOM

DBD::DBM - un pilote DBI pour les fichiers DBM et MLDBM

SYNOPSIS

use DBI;
$dbh = DBI->connect('dbi:DBM:');                    # par défaut SDBM_File
$dbh = DBI->connect('DBI:DBM(RaiseError=1):');      # par défaut SDBM_File
$dbh = DBI->connect('dbi:DBM:dbm_type=DB_File');    # par défaut DB_File
$dbh = DBI->connect('dbi:DBM:dbm_mldbm=Storable');  # MLDBM avec SDBM_File
# ou
$dbh = DBI->connect('dbi:DBM:', undef, undef);
$dbh = DBI->connect('dbi:DBM:', undef, undef, {
    f_ext              => '.db/r',
    f_dir              => '/chemin/vers/fichiers/db/',
    f_lockfile         => '.lck',
    dbm_type           => 'BerkeleyDB',
    dbm_mldbm          => 'FreezeThaw',
    dbm_store_metadata => 1,
    dbm_berkeley_flags => {
        '-Cachesize' => 1000, # définir un drapeau ::Hash
    },
});

et d'autres variations sur connect() comme indiqué dans la documentation DBI, les métadonnées de DBD::File et « Métadonnées » ci-dessous.

Utilisez les fonctions standard DBI prepare, execute, fetch, paramètres de substitution, etc. Voir « DÉMARRAGE RAPIDE » pour un exemple.

DESCRIPTION

DBD::DBM est un système de gestion de bases de données qui fonctionne immédiatement. Si vous avez une installation standard de Perl et DBI, vous pouvez commencer à créer, accéder et modifier de simples tables de bases de données sans aucun module supplémentaire. Vous pouvez ajouter d'autres modules (par ex. SQL::Statement, DB_File, etc.) pour améliorer les fonctionnalités.

Le module utilise une couche de stockage de fichiers DBM. Le stockage de fichiers DBM est courant sur de nombreuses plateformes et les fichiers peuvent être créés avec celui-ci dans de nombreux langages de programmation en utilisant différentes API. Cela signifie qu'en plus de créer des fichiers avec DBI/SQL, vous pouvez également utiliser DBI/SQL pour accéder et modifier des fichiers créés par d'autres modules et programmes DBM, et vice versa. Notez que dans ces cas, il peut être nécessaire d'utiliser un sous-ensemble commun des fonctionnalités fournies.

Les fichiers DBM sont stockés dans un format binaire optimisé pour une récupération rapide lors de l'utilisation d'un champ clé. Cette optimisation peut être utilisée avantageusement pour rendre les opérations SQL de DBD::DBM utilisant des champs clés très rapides. Il existe plusieurs « saveurs » différentes de DBM qui utilisent des formats de stockage différents pris en charge par des modules Perl tels que SDBM_File et MLDBM. Ce module prend en charge toutes les saveurs prises en charge par Perl et, lorsqu'il est utilisé avec MLDBM, prend en charge les tables avec un nombre quelconque de colonnes et l'insertion d'objets Perl dans les tables.

DBD::DBM a été testé avec les types DBM suivants : SDBM_File, NDBM_File, ODBM_File, GDBM_File, DB_File, BerkeleyDB. Chaque type a été testé avec et sans MLDBM et avec les sérialiseurs Data::Dumper, Storable, FreezeThaw, YAML et JSON en utilisant les moteurs DBI::SQL::Nano ou SQL::Statement.

DÉMARRAGE RAPIDE

DBD::DBM fonctionne comme tous les autres pilotes DBD - sa syntaxe et son fonctionnement de base sont spécifiés par DBI. Si vous n'êtes pas familier avec DBI, vous devriez commencer par lire DBI et les documents auxquels il fait référence, puis revenir et lire ce fichier. Si vous êtes familier avec DBI, vous connaissez déjà la plupart de ce que vous devez savoir pour utiliser ce module. Lancez-vous simplement et créez un script de test semblable à celui montré ci-dessous.

Vous devez savoir qu'il existe plusieurs options pour le moteur SQL sous-jacent à DBD::DBM, voir « Syntaxe SQL prise en charge ». Il existe également de nombreuses options pour la prise en charge DBM, voir notamment la section sur « Ajout de la prise en charge multi-colonnes avec MLDBM ».

Mais voici un exemple pour vous lancer.

use DBI;
my $dbh = DBI->connect('dbi:DBM:');
$dbh->{RaiseError} = 1;
for my $sql( split /;\n+/,"
    CREATE TABLE user ( user_name TEXT, phone TEXT );
    INSERT INTO user VALUES ('Fred Bloggs','233-7777');
    INSERT INTO user VALUES ('Sanjay Patel','777-3333');
    INSERT INTO user VALUES ('Junk','xxx-xxxx');
    DELETE FROM user WHERE user_name = 'Junk';
    UPDATE user SET phone = '999-4444' WHERE user_name = 'Sanjay Patel';
    SELECT * FROM user
"){
    my $sth = $dbh->prepare($sql);
    $sth->execute;
    $sth->dump_results if $sth->{NUM_OF_FIELDS};
}
$dbh->disconnect;

UTILISATION

Cette section expliquera certains cas d'utilisation plus en détail. Pour obtenir un aperçu des attributs disponibles, voir « Métadonnées ».

Spécification des fichiers et des répertoires

DBD::DBM fournira automatiquement une extension de fichier appropriée pour le type de DBM que vous utilisez. Par exemple, si vous utilisez SDBM_File, une table appelée « fruit » sera stockée dans deux fichiers appelés « fruit.pag » et « fruit.dir ». Vous ne devez jamais spécifier les extensions de fichier dans vos instructions SQL.

DBD::DBM reconnaît les extensions par défaut suivantes pour les types suivants :

.pag/r
Choisi pour dbm_type "SDBM_File", "ODBM_File" et "NDBM_File" lorsqu'une implémentation est détectée qui enveloppe "-ldbm" pour "NDBM_File" (par ex. Solaris, AIX, ...).

Pour ces types, l'extension ".dir" est également reconnue (pour être supprimée lors de la suppression d'une table).

.db/r
Choisi pour dbm_type "NDBM_File" lorsqu'une implémentation est détectée qui enveloppe BerkeleyDB 1.x pour "NDBM_File" (typiquement les BSD, Darwin).

"GDBM_File", "DB_File" et "BerkeleyDB" n'utilisent généralement pas d'extension de fichier.

Si votre type de DBM utilise une extension autre que l'une des extensions reconnues, vous devriez définir l'attribut f_ext sur l'extension et signaler un bogue comme décrit dans DBI avec le nom de l'implémentation et l'extension afin que nous puissions l'ajouter à DBD::DBM. Merci d'avance pour cela :-).

$dbh = DBI->connect('dbi:DBM:f_ext=.db');  # l'extension .db est utilisée
$dbh = DBI->connect('dbi:DBM:f_ext=');     # aucune extension n'est utilisée
# ou
$dbh->{f_ext}='.db';                       # réglage global
$dbh->{f_meta}->{'qux'}->{f_ext}='.db';    # réglage pour la table 'qux'

Par défaut, les fichiers sont supposés se trouver dans le répertoire de travail courant. Pour utiliser d'autres répertoires, spécifiez l'attribut f_dir soit dans la chaîne de connexion, soit en définissant l'attribut du gestionnaire de base de données.

Par exemple, cela cherchera le fichier /foo/bar/fruit (ou /foo/bar/fruit.pag pour les types de DBM qui utilisent cette extension)

my $dbh = DBI->connect('dbi:DBM:f_dir=/foo/bar');
# et cela aussi :
my $dbh = DBI->connect('dbi:DBM:');
$dbh->{f_dir} = '/foo/bar';
# mais ceci est recommandé
my $dbh = DBI->connect('dbi:DBM:', undef, undef, { f_dir => '/foo/bar' } );
# maintenant vous pouvez faire
my $ary = $dbh->selectall_arrayref(q{ SELECT x FROM fruit });

Vous pouvez également utiliser des identifiants délimités pour spécifier des chemins directement dans les instructions SQL. Cela cherche au même endroit que les deux exemples ci-dessus mais sans définir f_dir:

my $dbh = DBI->connect('dbi:DBM:');
my $ary = $dbh->selectall_arrayref(q{
    SELECT x FROM "/foo/bar/fruit"
});

Vous pouvez également indiquer à DBD::DBM d'utiliser un chemin spécifié pour une table spécifique :

$dbh->{dbm_tables}->{f}->{file} = q(/foo/bar/fruit);

Veuillez noter que vous ne pouvez pas spécifier cela lors de la connexion.

Si vous avez SQL::Statement installé, vous pouvez utiliser des alias de table :

my $dbh = DBI->connect('dbi:DBM:');
my $ary = $dbh->selectall_arrayref(q{
    SELECT f.x FROM "/foo/bar/fruit" AS f
});

Voir « PIÈGES ET AVERTISSEMENTS » pour l'utilisation de DROP sur les tables.

Verrouillage des tables et flock()

Le verrouillage des tables est accompli à l'aide d'un fichier de verrouillage qui a le même nom de base que le fichier de la table mais avec l'extension de fichier '.lck' (ou une extension de fichier de verrouillage que vous fournissez, voir ci-dessous). Ce fichier de verrouillage est créé avec la table lors d'un CREATE et supprimé lors d'un DROP. Chaque fois que la table elle-même est ouverte, le fichier de verrouillage est flocked(). Pour SELECT, il s'agit d'un verrou partagé. Pour toutes les autres opérations, il s'agit d'un verrou exclusif (sauf lorsque vous spécifiez autre chose en utilisant l'attribut f_lock ).

Puisque le verrouillage dépend de flock(), il ne fonctionne que sur les systèmes d'exploitation qui prennent en charge flock(). Dans les cas où flock() n'est pasest implémenté, DBD::DBM se comportera simplement comme si flock() s'était produit bien qu'aucun verrouillage réel n'ait lieu. Lisez la documentation de flock() pour plus d'informations. Même sur les systèmes qui prennent en charge flock() , le verrouillage est uniquement consultatif - comme c'est toujours le cas avec flock(

)

. Cela signifie que si un autre programme essaie d'accéder au fichier de table pendant que DBD::DBM a la table verrouillée, cet autre programme *réussira* à l'ouvrir à moins qu'il n'utilise également flock sur le fichier '.lck'. Par conséquent, le verrouillage de DBD::DBM ne s'applique réellement qu'aux autres programmes utilisant DBD::DBM ou aux autres programmes écrits pour coopérer avec le verrouillage de DBD::DBM. Spécification du type de DBM Chaque « variante » de DBM stocke ses fichiers dans un format différent et possède des capacités et des limitations différentes. Optimisation de l'utilisation des champs clés La plupart des « variantes » de DBM n'ont que deux colonnes physiques (mais peuvent contenir plusieurs colonnes logiques comme expliqué ci-dessus dans « Ajout de la prise en charge multi-colonnes avec MLDBM »). Elles fonctionnent de manière similaire à un hash Perl avec la première colonne servant de clé. Comme un hash Perl, les fichiers DBM vous permettent de faire des recherches rapides en spécifiant la clé et évitent ainsi de parcourir tous les enregistrements (pris en charge uniquement par DBI::SQL::Nano). Comme un hash Perl également, les clés doivent être uniques. Il est impossible de créer deux enregistrements avec la même clé. Pour le dire plus simplement et en termes SQL, la colonne clé fonctionne comme

la

CLÉ PRIMAIRE ou l'INDEX

UNIQUE.

Dans DBD::DBM, vous pouvez tirer parti de la rapidité des recherches par clé en utilisant DBI::SQL::Nano et une clause WHERE avec une seule comparaison d'égalité sur le champ clé. Par exemple, les instructions SQL suivantes sont optimisées pour la recherche

par
clé :

CREATE TABLE user ( user_name TEXT, phone TEXT); INSERT INTO user VALUES ('Fred Bloggs','233-7777'); # ... beaucoup d'autres insertions SELECT phone FROM user WHERE user_name='Fred

Bloggs';

La colonne "user_name" est la colonne clé car c'est la première colonne. L'instruction SELECT utilise la colonne clé dans une seule comparaison d'égalité - "user_name='Fred Bloggs'" - donc la recherche la trouvera très rapidement sans avoir à parcourir tous les noms qui ont été insérés dans la table. En revanche, ces recherches sur la même table ne sont pas optimisées

:

1. SELECT phone FROM user WHERE user_name < 'Fred'; 2. SELECT user_name FROM user WHERE phone =

'233-7777'; 
Dans #1, l'opération utilise une comparaison inférieur à (<) plutôt
    qu'une comparaison d'égalité, donc elle ne sera pas optimisée pour la recherche par clé. Dans
    #2, le champ clé "user_name" n'est pas spécifié dans la clause
    WHERE, et par conséquent la recherche devra parcourir toutes les lignes pour trouver
    la ou les lignes
demandées.

Note

z

que le stockage DBM sous-jacent doit parcourir toutes

les

Même si les recherches sont plus rapides d'environ 50 %, DBI::SQL::Nano et SQL::Statement peuvent bénéficier des optimisations du champ clé lors de la mise à jour et de la suppression de lignes - et ici, l'évaluation de clause where améliorée de SQL::Statement pourrait surpasser DBI::SQL::Nano chaque fois que la clause where contient non seulement le champ clé (ou plus d'un). DBD::DBM utilise un sous-ensemble de SQL. La robustesse de ce sous-ensemble dépend des

Par défaut, ce module hérite de sa prise en charge SQL de DBI::SQL::Nano qui est livré avec DBI. Nano est, comme son nom l'indique, un moteur SQL *très* petit. Bien que limité dans son champ d'application, il est plus rapide que l'option n° 2 pour certaines opérations (en particulier les recherches

par

:

Si vous installez le module CPAN pur Perl SQL::Statement, DBD::DBM l'utilisera à la place de Nano. Cela ajoute la prise en charge des alias de table, des fonctions, des jointures et bien plus encore. Si vous comptez utiliser DBD::DBM pour autre chose que des tables très simples, vousnd requêtes, vous devriez installer SQL::Statement. Vous n'avez pas à modifier DBD::DBM ou vos scripts d'aucune manière, l'installation de SQL::Statement vous donnera simplement des capacités SQL plus robustes sans casser les scripts écrits pour DBI::SQL::Nano. charge.

Les fichiers DBM n'ont pas de standard pour stocker les noms de colonnes. DBD::DBM contourne ce problème avec une méthode spécifique à DBD::DBM pour stocker les noms de

DBD::DBM stocke les noms de colonnes comme une ligne dans le fichier avec la

Cependant, si vous accédez au fichier avec autre chose que DBD::DBM, la ligne sera traitée comme une ligne de données

régulière. 
Si vous ne voulez pas que les noms de colonnes soient stockés comme une ligne de données dans la table, vous pouvez définir l'attribut dbm_store_metadat
a

à

0.

EXTENSIBILITÉ

"SQL::Statement"
Moteur SQL amélioré par rapport au DBI::SQL::Nano intégré - voir "Syntaxe SQL prise en charge".
"DB_File"
Berkeley DB version 1. Cette bibliothèque de base de données est disponible sur de nombreux systèmes sans installation supplémentaire et la plupart des systèmes sont pris en charge.
"GDBM_File"
Type dbm simple (comparable à "DB_File") sous licence GNU. Généralement non disponible (ou nécessitant une installation supplémentaire) sur les systèmes d'exploitation non-GNU.
"BerkeleyDB"
Berkeley DB version jusqu'à v4 (et peut-être plus) - nécessite une installation supplémentaire mais est plus facile que GDBM_File sur les systèmes non-GNU.

db4 est livré avec de nombreux outils permettant de réparer et de migrer des bases de données. C'est le type dbm recommandé pour une utilisation en production.

"MLDBM"
Wrapper de sérialisation pour prendre en charge plus d'une colonne pour les fichiers. Livré avec des sérialiseurs utilisant "Data::Dumper", "FreezeThaw" et "Storable".
"YAML::MLDBM"
Sérialiseur supplémentaire pour MLDBM. YAML est très portable entre les langages.
"MLDBM::Serializer::JSON"
Sérialiseur supplémentaire pour MLDBM. JSON est très portable entre les langages, probablement plus que YAML.

PIÈGES ET AVERTISSEMENTS

L'utilisation de la commande SQL DROP supprimera tout fichier portant le nom spécifié dans la commande avec l'ajout de '.pag' et '.dir', '.db' ou votre {f_ext}. Cela peut donc être dangereux si vous n'êtes pas sûr du fichier auquel cela fait référence :

$dbh->do(qq{DROP TABLE "/path/to/any/file"});

Chaque type DBM a des limitations. SDBM_File, par exemple, ne peut stocker que des valeurs de moins de 1 000 caractères. *Vous*, en tant qu'auteur du script, devez vous assurer de ne pas dépasser ces limites. Si vous essayez d'insérer une valeur plus grande que ce que DBM peut stocker, les résultats seront imprévisibles. Consultez la documentation du DBM que vous utilisez pour plus de détails.

Les différentes implémentations de DBM renvoient les enregistrements dans des ordres différents. Cela signifie que vous ne devez pas vous fier à l'ordre des enregistrements sauf si vous utilisez une clause ORDER BY.

Les fichiers de données DBM sont spécifiques à la plateforme. Pour les déplacer d'une plateforme à une autre, vous devrez faire quelque chose comme exporter vos données en CSV sur la plateforme n°1 puis importer depuis CSV vers DBM sur la plateforme n°2. DBD::AnyData et DBD::CSV peuvent vous aider pour cela. Il peut aussi y avoir des outils de conversion DBM pour vos plateformes qui seraient probablement plus rapides.

Lors de l'utilisation de MLDBM, il y a un sérialiseur très puissant - il vous permettra de stocker du code Perl ou des objets dans des colonnes de base de données. Lorsqu'ils sont désérialisés, ils peuvent être évalués (eval) - en d'autres termes, MLDBM (ou en fait Data::Dumper lorsqu'il est utilisé par MLDBM) peut prendre les valeurs et essayer de les exécuter en Perl. Évidemment, cela peut présenter des dangers, donc si vous ne savez pas ce qu'il y a dans un fichier, soyez prudent avant d'y accéder avec MLDBM activé !

Voir toute la section sur "Verrouillage des tables et flock()" pour les pièges et avertissements concernant l'utilisation de flock().

BOGUES ET LIMITATIONS

Ce module utilise les interfaces de hachage de deux bases de données de fichiers colonnes. Bien qu'aucun des moteurs SQL pris en charge ne prenne en charge les index, les instructions suivantes font réellement la même chose (même si elles signifient quelque chose de complètement différent) pour chaque type dbm qui ne prend pas en charge "EXISTS" :

$sth->do( "insert into foo values (1, 'hello')" );
# cette instruction fait ...
$sth->do( "update foo set v='world' where k=1" );
# ... la même chose que cette instruction
$sth->do( "insert into foo values (1, 'world')" );

C'est considéré comme un bogue et pourrait changer dans une version future.

Les types dbm connus comme affectés sont "ODBM_File" et "NDBM_File". Nous vous recommandons fortement d'utiliser un type dbm plus moderne tel que "DB_File".
