Gestion des ensembles de résultats

multiples

Le Transact SQL de Sybase a la capacité de retourner plusieurs ensembles de résultats à partir d'une seule instruction SQL. Par exemple, la requête

: 
select b.title, b.author, s.amount
  from books b, sales s
 where s.authorID = b.authorID
 order by b.author, b.title
compute sum(s.amount) by b.
author

qui liste les ventes par auteur et titre et calcule également le total des ventes par auteur retourne deux types de lignes. La spécification DBI ne gère pas vraiment cette situation, ni le cas plus

complexe 
exec my_proc @p1='this', @p2='that', @p3
out

où "my_proc" pourrait retourner un nombre quelconque d'ensembles de résultats (c'est-à-dire qu'il pourrait effectuer un nombre inconnu de instructions "s

elect".

J'ai décidé de gérer cela en retournant une ligne vide à la fin de chaque ensemble de résultats, et en définissant un attribut Sybase spécial dans $sth que vous pouvez vérifier pour voir s'il reste des données à récupérer. L'attribut est syb_more_results que vous devriez vérifier pour voir si vous devez redémarrer la boucle fetch()

.

Pour vous assurer que tous les résultats sont récupérés, la boucle "fetch" de base peut être écrite comme ceci

: 
{
    while($d = $sth->fetch) {
       ... faire quelque chose avec les données
    }
    redo if $sth->{syb_more_results};
}

Vous pouvez obtenir le type de l'ensemble de résultats courant avec $sth->{syb_result_type}. Cela retourne une valeur numérique, telle que définie dans $SYBASE/$SYBASE_OCS/include/cspublic.h

: 
#define CS_ROW_RESULT           (CS_INT)4040
#define CS_CURSOR_RESULT        (CS_INT)4041
#define CS_PARAM_RESULT         (CS_INT)4042
#define CS_STATUS_RESULT        (CS_INT)4043
#define CS_MSG_RESULT           (CS_INT)4044
#define CS_COMPUTE_RESULT       (CS_INT)
4045

En particulier, le statut de retour d'une procédure stockée est retourné en tant que CS_STATUS_RESULT (4043), et est normalement le dernier ensemble de résultats qui est retourné lors de l'exécution d'une procédure stockée, mais voir l'attribut syb_do_proc_status pour une autre façon de gérer ce type de résultat. Voir Exécution des procédures stockées ailleurs dans ce document pour plus

d'informations.

AutoCommit, Transactions et

Lorsque $h->{AutoCommit} est désactivé, toutes les instructions SQL de modification de données que vous émettez (insert/update/delete) ne prendront effet que si vous appelez $dbh->com

DBD::Sybase implémente cela via deux méthodes distinctes, selon le paramétrage de l'attribut $h->{syb_chained_txn} et la version du serveur qui est

Si $h->{syb_chained_txn} est désactivé, alors le pilote DBD::Sybase enverra un BEGIN TRAN avant le premier $dbh->prepare(), et après chaque appel à $dbh->commit() ou $dbh->rollback(). Cela fonctionne bien, mais causera l'échec de tout SQL contenant des instructions CREATE TABLE (ou d'autres DDL). Ces instructions CREATE TABLE peuvent être cachées dans une procédure stockée quelque part (par exemple, "sp_helprotect" crée deux tables temporaires lorsqu'il est exécuté). Vous pouvez contourner cette limitation en définissant l'option "ddl in tran" (au niveau de la base de données, via "sp_dboption".) Vous devez être conscient que cela peut avoir des effets graves sur les performances car cela provoque le maintien de verrous sur certaines tables système pendant toute la durée de la

transaction.

Si $h->{syb_chained_txn} est activé, alors DBD::Sybase définit l'option CHAINED, qui indique à Sybase de ne rien valider automatiquement. De nouveau, vous devrez appeler $dbh->commit() pour rendre les modifica

DBD::Sybase prend en charge l'utilisation des paramètres de substitution ? dans les instructions SQL tant que la bibliothèque sous-jacente et le moteur de base de données le supportent. Il le fait en utilisant ce que Sybase appelle SQL Dynamique. Les paramètres de substitution ? vous permettent d'écrire quelque chose comme

: 
 $sth = $dbh->prepare("select * from employee where empno = ?");
 # Récupérer les lignes de employee où empno == 1024 :
 $sth->execute(1024);
 while($data = $sth->fetch) {
     print "@$data\n";
 }
# Maintenant obtenir les lignes où empno = 2000 :

 $sth->execute(2000);
 while($data = $sth->fetch) {
     print "@$data\n";
}

Lorsque vous utilisez des paramètres de substitution ?, Sybase crée une procédure temporaire qui correspond à votre instruction SQL. Vous passez ensuite des variables à $sth->execute ou $dbh->do, qui sont insérées dans la requête, et les lignes sont

retournées.

DBD::Sybase utilise les appels d'API Sybase sous-jacents pour gérer les paramètres de substitution de style ?. Pour les instructions select/insert/update/delete, DBD::Sybase appelle la famille de fonctions ct_dynamic() de la Client Library, qui donne à DBD::Sybase des informations sur le type de données pour chaque paramètre de la

requête.

Vous ne pouvez utiliser des paramètres de substitution de style ? que pour les instructions qui retournent un seul jeu de résultats, et les paramètres de substitution ? ne peuvent apparaître que dans une clause WHERE, dans la clause SET d'une instruction UPDATE, ou dans la liste VALUES d'une instruction I

NSERT.

La documentation DBI mentionne ce qui suit concernant les valeurs NULL et les paramètres de substitution

:

les raisons de cela. Pour sélectionner explicitement les NULL, vous devez

  ... WHERE (product_code = ? OR (? IS NULL AND product_code IS NULL))

Cela ne fonctionnera pas avec un serveur de base de données Sybase. Si vous tentez la construction ci-dessus, vous obtiendrez l'erreur suivante

Le problème spécifique ici est que lorsque vous utilisez des paramètres de substitution ?, l'opération prepare() est envoyée au serveur de base de données pour la résolution des paramètres. Cela extrait les types de données de chacun des paramètres de substitution. Malheureusement, la construction "? is null" n'associe pas le paramètre de substitution ? à une colonne de table existante, donc le serveur de base de données ne peut pas trouver le type de données. Comme cette opération entière se produit à l'intérieur des bibliothèques Sybase, il n'y a pas de moyen facile pour DBD::Sybase de contourner

cela.

Notez que Sybase gérera normalement la construction "foo = NULL" de la même manière queems handle « foo est NULL », de sorte que la construction complexe décrite ci-dessus n'est pas nécessaire pour obtenir les résultats corrects lors de l'interrogation d'une base de données

Sybase.

L'API sous-jacente ne prend pas en charge les espaces réservés de style ? pour les procédures stockées, mais voir la section intitulée Procédures stockées et espaces réservés ailleurs dans ce

document.

Les espaces réservés de style ? peuvent NE PAS être utilisés pour passer des éléments de données TEXT ou IMAGE au serveur. Ceci est une limitation du protocole TDS, et non de DBD::

Sybase.

Il y a aussi un problème de performance : OpenClient crée des procédures stockées dans tempdb pour chaque appel prepare() qui inclut des espaces réservés ?. La création de ces objets nécessite la mise à jour des tables système dans la base de données tempdb, et peut donc créer un point de contention de performance si beaucoup de instructions prepare() provenant de plusieurs clients sont exécutées simultanément. Ce problème a été corrigé pour les serveurs Sybase 11.9.x et versions ultérieures, car ils créent des procédures stockées temporaires « légères » qui sont conservées dans le cache mémoire du serveur et n'affectent pas les tables système du

tout.

En général, cependant, je trouve que si votre application va s'exécuter contre Sybase, il est préférable d'écrire des procédures stockées ad-hoc plutôt que d'utiliser les espaces réservés ? dans le SQL

intégré.

Par curiosité, j'ai fait quelques mesures de temps simples pour voir quel était le surcoût de faire un prepare avec des espaces réservés ? par rapport à un prepare SQL direct et par rapport à un prepare de procédure stockée. Contre un serveur 11.0.3.3 (linux), le prepare avec espaces réservés est nettement plus lent, et vous devez faire ~30 appels execute() sur la statement préparée pour compenser le surcoût. Contre un serveur 12.0 (solaris), cependant, la situation était très différente, avec des appels prepare() avec espaces réservés légèrement plus rapides qu'un prepare SQL direct. C'est quelque chose que je ne comprends vraiment pas, mais les chiffres étaient assez

clairs.

Dans tous les cas, les appels prepare() de procédures stockées étaient nettement plus rapides, et de manière

constante.

Ce test n'a pas tenté d'évaluer les problèmes de concurrence,

cependant.

Il n'est pas possible de récupérer la dernière valeur IDENTITY après un insert effectué avec des espaces réservés de style ?. Ceci est une limitation/bug de Sybase, et non un problème de DBD::Sybase. Par exemple, en supposant que la table foo a une colonne identity

: 
$dbh->do("insert foo(col1, col2) values(?, ?)", undef, "string1", "string2");
$sth = $dbh->prepare('select @@identity') 
  || die "Can't prepare the SQL statement: $DBI::errstr";
$sth->execute || die "Can't execute the SQL statement: $DBI::errstr";
#Get the data back.
while (my $row = $sth->fetchrow_arrayref()) {
  print "IDENTITY value = $row->[0]\n";
}

retournera toujours une valeur identity de 0, ce qui est évidemment incorrect. Ce comportement est dû au fait que le traitement des espaces réservés de style ? est implémenté à l'aide de procédures stockées temporaires dans Sybase, et la valeur de @@identity est réinitialisée lorsque la procédure stockée a été exécutée. L'utilisation d'une procédure stockée explicite pour effectuer l'insert et la tentative de récupération de @@identity après son exécution donne le même

comportement.

Appel de procédures

stockées

DBD::Sybase gère les procédures stockées de la même manière que toute autre instruction Transact-SQL. La seule vraie différence est que les procédures stockées Sybase renvoient toujours un jeu de résultats supplémentaire avec le statut de retour de la proc qui correspond à l'instruction return dans le code de la procédure stockée. Ce jeu de résultats à une seule ligne est toujours renvoyé en dernier et a un type de résultat CS_STATUS_RESULT (4043)

.

Par défaut, ce jeu de résultats est renvoyé comme tout autre, mais vous pouvez demander à DBD::Sybase de le traiter en interne via l'attribut $h->{syb_do_proc_status}. Si cet attribut est défini, alors DBD::Sybase traitera lui-même le jeu de résultats CS_STATUS_RESULT, placera la valeur du statut de retour dans $sth->{syb_proc_status}, et pourra lever une erreur si le jeu de résultats est différent de 0. Notez qu'un statut de retour non-0 ne CAUSERA PAS que $sth->execute retourne un code d'échec si la proc a au moins un autre jeu de résultats qui a renvoyé des lignes (raison : les lignes sont renvoyées et récupérées avant que le statut de retour ne soit vu)

.

Procédures stockées et espaces

réservés

DBD::Sybase a la capacité d'utiliser des espaces réservés de style ? comme paramètres pour les appels de procédures stockées. Les exigences sont que l'appel de la procédure stockée soit initié avec un « exec » et qu'il soit la seule instruction dans le lot qui est prépar

é :

Par exemple, ceci prépare un appel de procédure stockée avec des paramètres nommés

: 
my $sth = $dbh->prepare("exec my_proc \@p1 = ?, \@p2 = ?");
$sth->execute('one', 'two')
;

Vous pouvez aussi utiliser des paramètres positionnels

: 
my $sth = $dbh->prepare("exec my_proc ?, ?");
$sth->execute('one', 'two')
;

Vous ne pouvez pas mélanger les paramètres positionnels et nommés dans le même

prepare.

Vous ne pouvez pas mélanger les paramètres avec espaces réservés et les paramètres codés en dur. Par

exemple 
$sth = $dbh->prepare("exec my_proc \@p1 = 1, \@p2 = ?")
;

ne fonctionnera pas - parce que le paramètre @p1 n'est pas analysé correctement et ne sera pas envoyé au

serveur.

Vous pouvez spécifier des paramètres OUTPUT de la manière habituelle, mais vous ne pouvez PAS utiliser bind_param_inout() pour obtenir le résultat de sortie - à la place, vous devez appeler fetch() et/ou $sth->func('syb_output_params')

: 
my $sth = $dbh->prepare("exec my_proc \@p1 = ?, \@p2 = ?, \@p3 = ? OUTPUT ");
$sth->execute('one', 'two', 'three');
my (@data) = $sth->syb_output_params()
;

DBD::Sybase n'essaie pas de déterminer le type de paramètre correct pour chaque paramètre (il serait possible de le faire pour la plupart des cas, mais il y a suffisamment d'exceptions pour que j'aie préféré éviter le problème pour le moment). DBD::Sybase définit tous les paramètres par défaut à SQL_CHAR, et vous devez utiliser bind_param() avec une valeur de type explicite pour définir cela à quelque chose de différent. Le type est ensuite mémorisé, donc vous n'avez besoin d'utiliser l'appel explicite qu'une fois pour chaque paramètre

: 
my $sth = $dbh->prepare("exec my_proc \@p1 = ?, \@p2 = ?");
$sth->bind_param(1, 'one', SQL_CHAR);
$sth->bind_param(2, 2.34, SQL_FLOAT);
$sth->execute;
....
$sth->execute('two', 3.456);
etc..
.

Notez qu'une fois qu'un type a été défini pour un paramètre, vous ne pouvez pas le

changer.

Lors de la liaison de données SQL_NUMERIC ou SQL_DECIMAL, vous pouvez obtenir des erreurs de conversion fatales si l'échelle ou la précision dépasse la taille de la définition du paramètre

Fonctionnalité Bulk-Load

expérimentale

NOTE : Cette fonctionnalité nécessite que la bibliothèque libblk.a soit disponible au moment de la compilation. Ce n'est pas toujours le cas si le SDK Sybase n'est pas installé. Vous pouvez tester l'attribut $dbh->{syb_has_blk} pour voir si les appels d'API BLK sont disponibles dans votre copie de DBD::

Sybase.

À partir de la version 1.04.2, DBD::Sybase a la capacité d'utiliser l'API BLK (chargement groupé) de Sybase pour effectuer des chargements de données rapides. L'utilisation de base est la suivante

: 
my $dbh = DBI->connect('dbi:Sybase:server=MY_SERVER;bulkLogin=1', $user, $pwd);
$dbh->begin_work;  # optional.
my $sth = $dbh->prepare("insert the_table values(?, ?, ?, ?, ?)",
                        {syb_bcp_attribs => { identity_flag => 0,
                                             identity_column => 0 }}});
while(<DATA>) {
  chomp;
  my @row = split(/\|/, $_);   # suppose un fichier délimité par des barres verticales...
  $sth->execute(@row);
}
$dbh->commit;
print "Sent ", $sth->rows, " to the server\n";
$sth->
finish;

Tout d'abord, vous devez spécifier le nouvel attribut bulkLogin dans la chaîne de connexion, ce qui active la propriété CS_BULK_LOGIN pour la connexion. Sans cette propriété, l'API BLK ne sera pas

fonctionnelle.

Vous appelez $dbh->prepare() avec une instruction INSERT régulière et l'attribut spécial syb_bcp_attribs pour activer le traitement BLK des données. Le sous-attribut identity_flag peut être défini à 1 si vos données source incluent les valeurs pour la colonne IDENTITY de la table cible. Si la table cible a une colonne IDENTITY mais que vous voulez que l'opération d'insertion génère une nouvelle valeur pour chaque ligne, laissez identity_flag à 0, mais définissez identity_col au numéro de la colonne de l'identité (c'est généralement la première colonne de la table, mais pas toujours)

.

Le nombre de marqueurs de position dans l'instruction INSERT doit correspondre au nombre de colonnes de la table, et les données d'entrée doivent être dans le même ordre que l'ordre physique des colonnes de la table. Toute liste de colonnes dans l'instruction INSERT (c'est-à-dire insert table(a, b, c,...) values(...) est

ignorée.

La valeur de AutoCommit est ignorée pour les opérations BLK - les lignes ne sont validées que lorsque vous appelez $dbh->com

mit.

Vous pouvez appeler $dbh->rollback pour annuler toutes les lignes non validées, mais cela annule également le reste de l'opération BLK : toute tentative de charger des lignes vers le serveur après un appel à $dbh->rollback()

échouera.

Si une ligne échoue au chargement en raison d'une erreur côté CLIENT (comme une erreur de conversion de données), alors $sth->execute() renverra un échec (c'est-à-dire faux) et $sth->errstr contiendra la raison de

l'erreur.

Si une ligne échoue côté SERVEUR (par exemple en raison d'une erreur de ligne en double), alors tout le lot (c'est-à-dire entre deux appels $dbh->commit()) échouera. C'est le comportement normal pour

BLK/bcp.

L'API de chargement par lots est très sensible aux problèmes de conversion de données, car toutes les conversions sont gérées côté client, et la ligne est pré-formatée avant d'être envoyée au serveur. Par défaut, toute conversion signalée par l'appel cs_convert() de Sybase entraînera une ligne en échec. Certaines de ces erreurs de conversion sont manifestement fatales (par exemple, convertir 'Feb 30 2001' en une valeur DATETIME...), tandis que d'autres sont discutables (par exemple, convertir 123.456 en NUMERIC(6,2) ce qui entraîne une perte de précision). Le comportement par défaut de faire échouer toute ligne contenant une erreur de conversion peut être modifié en utilisant un gestionnaire d'erreurs spécial. Le fait de renvoyer 0 depuis ce gestionnaire indique à DBD::Sybase de faire échouer cette ligne, et le fait de renvoyer 1 signifie que nous voulons toujours essayer d'envoyer la ligne au serveur (évidemment, le code interne de Sybase peut toujours faire échouer la ligne à ce moment-là.) Vous définissez le gestionnaire comme ceci

: 
DBD::Sybase::syb_set_cslib_cb(\&handler)
;

et un gestionnaire d'exemple

: 
sub cslib_handler {
  my ($layer, $origin, $severity, $errno, $errmsg, $osmsg, $blkmsg) = @_;

  print "Layer: $layer, Origin: $origin, Severity: $severity, Error: $errno\n";
  print $msg;
  print $osmsg if($osmsg);
  print $blkmsg if $blkmsg;
  return 1 if($errno == 36)
  return 0;
}

Veuillez consulter le script de test t/xblk.t pour quelques

exemples.

Utilisation de DBD::Sybase avec

MS-SQL

MS-SQL est parti de Sybase 4.2, et il existe encore de nombreuses similitudes entre Sybase et MS-SQL qui rendent possible l'utilisation de DBD::Sybase pour interroger un serveur de données MS-SQL en utilisant soit les bibliothèques Sybase OpenClient, soit les bibliothèques FreeTDS (voir http://www.freetds.org)

.

Cependant, l'utilisation des bibliothèques Sybase pour interroger un serveur MS-SQL comporte certaines limitations. En particulier, les marqueurs de position de style ? ne sont pas pris en charge (bien que la prise en charge lors de l'utilisation des bibliothèques FreeTDS soit possible dans une future version des bibliothèques), et certains attributs syb_ peuvent ne pas être pris en

charge.

Sybase définit l'attribut TEXTSIZE (alias LongReadLen) à 32k, mais MS-SQL 7 ne semble pas le faire correctement, ce qui entraîne de très grandes demandes de mémoire lors de l'interrogation de tables avec des colonnes de données TEXT/IMAGE. La solution de contournement consiste à définir TEXTSIZE à une valeur raisonnable via $dbh->{LongReadLen} (si cela fonctionne - je n'ai aucune confirmation que c'est le cas) ou via $dbh->do("set textsize <somesize>

")

@data = $dbh->syb_nsql($sql, $type, $callback, $options)

clés.
