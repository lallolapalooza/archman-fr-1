DESCRIPTIO

N

Introductio

n

SQLite est livré avec un module d'extension appelé "FTS" pour l'indexation plein texte. Les tables dotées de cette fonctionnalité peuvent être interrogées efficacement pour trouver des lignes contenant une ou plusieurs occurrences de mots spécifiés (appelés aussi "jetons"), dans n'importe quelle colonne, même si la table contient de nombreux documents

volumineux.

Les premiers modules de recherche plein texte pour SQLite étaient appelés "FTS1" et "FTS2" et sont désormais obsolètes. La dernière version est "FTS4", mais elle partage de nombreuses caractéristiques avec l'ancien module "FTS3", ce qui explique pourquoi certaines parties de l'API et de la documentation font encore référence à "FTS3" ; d'un point de vue client, les deux peuvent être considérés comme largement équivalents. Une documentation détaillée peut être trouvée à l'adresse http://www.sqlit

e.org/ft
s3.html.

Exemple

court

Voici un exemple très court d'utilisation de FTS

: 
$dbh->do(<<"") or die DBI::errstr;
CREATE VIRTUAL TABLE fts_example USING fts4(content)

my $sth = $dbh->prepare("INSERT INTO fts_example(content) VALUES (?)");
$sth->execute($_) foreach @docs_to_insert;

my $results = $dbh->selectall_arrayref(<<"");
SELECT docid, snippet(fts_example) FROM fts_example WHERE content MATCH
'foo'

Les points clés de cet exemple sont les suivants

:
  • La syntaxe pour créer des tables FTS est 
    CREATE VIRTUAL TABLE <table_name> USING fts4(<columns>
    )

    où "<columns>" est une liste de noms de colonnes. Les colonnes peuvent être typées, mais l'information de type est ignorée. Si aucune colonne n'est spécifiée, la valeur par défaut est une colonne unique nommée "content". De plus, les tables FTS ont une colonne implicite appelée "docid" (ou aussi "rowid") pour numéroter

    les docume
    • nts stockés.
  • Les instructions d'insertion, de mise à jour ou de suppression d'enregistrements utilisent la même syntaxe que pour les tables SQLite
    • ordinaires.
  • Les recherches plein texte sont spécifiées avec l'opérateur "MATCH", et un opérande qui peut être un mot unique, un préfixe de mot se terminant par '*', une liste de mots, une "requête de phrase" entre guillemets doubles, ou une combinaison booléenne des éléments
    • ci-dessus.
  • La fonction intégrée snippet(...) construit un extrait formaté du texte du document
    • , où les mots pertinents pour l
a requête sont mis en évidence.

Il y a beaucoup plus de détails pour la construction et la recherche dans les tables FTS, nous vous invitons donc fortement à lire la documentation complète à l'adresse http://www.sq

lite.o
rg/fts3
.html.

REQUÊTES

Voici quelques explications sur les requêtes FTS, empruntées à la documentation de

sqlite.

Requêtes sur un jeton ou un préfixe de

jeton

Une table FTS peut être interrogée pour tous les documents contenant un terme spécifié, ou pour tous les documents contenant un terme avec un préfixe spécifié. L'expression de requête pour un terme spécifique est simplement le terme lui-même. L'expression de requête utilisée pour rechercher un préfixe de terme est le préfixe lui-même auquel on ajoute un caractère '*'. Par exemple

: 
-- Virtual table declaration
CREATE VIRTUAL TABLE docs USING fts3(title, body);

-- Query for all documents containing the term "linux":
SELECT * FROM docs WHERE docs MATCH 'linux';

-- Query for all documents containing a term with the prefix "lin".
SELECT * FROM docs WHERE docs MATCH
'lin*';

Si un jeton de recherche (à droite de l'opérateur MATCH) commence par "^", alors ce jeton doit être le premier dans son champ du document : ainsi par exemple "^lin*" correspond à 'linux kernel changes ...' mais ne correspond pas à 'new linux

implementation'
.

Spécifications de

colonnes

Normalement, une requête sur un jeton ou un préfixe de jeton est comparée à la colonne de la table FTS spécifiée à droite de l'opérateur MATCH. Ou, si la colonne spéciale portant le même nom que la table FTS elle-même est spécifiée, à toutes les colonnes. Cela peut être remplacé en spécifiant un nom de colonne suivi du caractère ":" avant une requête de terme de base. Il peut y avoir un espace entre le ":" et le terme à rechercher, mais pas entre le nom de colonne et le caractère ":". Par exemple

: 
-- Query the database for documents for which the term "linux" appears in
-- the document title, and the term "problems" appears in either the title
-- or body of the document.
SELECT
* FROM docs WHERE docs MATCH 'title:linux problems'; -- Query the database for documents for which the term "linux" appears in -- the document title, and the term "driver" appears in
the body of the document -- ("driver" may also appear in the title, but this alone will not satisfy the. -- query criteria). SELECT * FROM docs WHERE body MATCH 'title:linux driver';

Requêtes de

phrase

Une requête de phrase est une requête qui récupère tous les documents contenant un ensemble de termes ou de préfixes de termes désignés dans un ordre spécifié, sans jetons intercalés. Les requêtes de phrase sont spécifiées en enfermant une séquence de termes ou de préfixes de termes séparés par des espaces entre guillemets doubles ("). Par exemple

: 
-- Query for all documents that contain the phrase "linux applications".
SELECT * FROM docs WHERE docs MATCH '"linux applicatio
ns"'; -- Query for all documents that contain a phrase that matches "lin* app*". -- As well as "linux applications", this will
match common phrases such -- as "linoleum appliances" or "link apprentice". SELECT * FROM docs WHERE docs MATCH '"lin* app*"';

Requêtes

NEAR.

Une requête NEAR est une requête qui retourne les documents contenant deux termes ou phrases désignés ou plus à une proximité spécifiée les uns des autres (par défaut avec 10 termes intercalés ou moins). Une requête NEAR est spécifiée en plaçant le mot-clé "NEAR" entre deux requêtes de phrase, de terme ou de préfixe. Pour spécifier une proximité autre que celle par défaut, un opérateur de la forme "NEAR/<N>" peut être utilisé, où <N> est le nombre maximum de termes intercalés autorisés. Par exemple

: 
-- Virtual table declaration.
CREATE VIRTUAL TABLE docs USING fts4();
-- Virtual table data.
INSERT INTO docs VALUES('SQLite is an ACID compliant embedded relational database management system');
-- Search for a document that contains the terms "sqlite" and "database" with
-- not more than 10 intervening terms. This matches the only document in
-- table docs (since there are only six terms between "SQLite" and "database" 
-- in the document).
SELECT * FROM docs WHERE docs MATCH 'sqlite NEAR database';
-- Search for a document that contains the terms "sqlite" and "database" with
-- not more than 6 intervening terms. This also matches the only document in
-- table docs. Note that the order in which the terms appear in the document
-- does not have to be the same as the order in which they appear in the query.
SELECT * FROM docs WHERE docs MATCH 'database NEAR/6 sqlite';
-- Search for a document that contains the terms "sqlite" and "database" with
-- not more than 5 intervening terms. This query matches no documents.
SELECT * FROM docs WHERE docs MATCH 'database NEAR/5 sqlite';
-- Search for a document that contains the phrase "ACID compliant" and the term
-- "database" with not more than 2 terms separating the two. This matches the
-- document stored in table docs.
SELECT * FROM docs WHERE docs MATCH 'database NEAR/2 "ACID compliant"';
-- Search for a document that contains the phrase "ACID compliant" and the term
-- "sqlite" with not more than 2 terms separating the two. This also matches
-- the only document stored in table docs.
SELECT * FROM docs WHERE docs MATCH '"ACID compliant" NEAR/2
sqlite';

Plus d'un opérateur NEAR peutapparaissent dans une seule requête. Dans ce cas, chaque paire de termes ou de phrases séparés par un opérateur NEAR doit apparaître à la proximité spécifiée l'un de l'autre dans le document. En utilisant la même table et les mêmes données que dans le bloc d'exemples ci-dessus

: 
-- La requête suivante sélectionne les documents contenant une instance du terme
-- "sqlite" séparée de deux termes ou moins d'une instance du terme "acid",
-- qui est à son tour séparée de deux termes ou moins d'une instance du terme
-- "relational".
SELECT * FROM docs WHERE docs MATCH 'sqlite NEAR/2 acid NEAR/2 relational';
-- Cette requête ne correspond à aucun document. Il existe une instance du terme "sqlite" avec
-- une proximité suffisante à une instance de "acid", mais elle n'est pas suffisamment proche
-- d'une instance du terme "relational".
SELECT * FROM docs WHERE docs MATCH 'acid NEAR/2 sqlite NEAR/2
relational';

Les requêtes de phrase et NEAR ne

peuvent pas s'étendre sur plusieurs
colonnes au sein d'une ligne.

Opérations sur les

ensembles

Les trois types de requêtes de base décrits ci-dessus peuvent être utilisés pour interroger l'index de texte intégré afin d'obtenir l'ensemble des documents correspondant aux critères spécifiés. En utilisant le langage d'expression de requête FTS, il est possible d'effectuer diverses opérations sur les ensembles à partir des résultats des requêtes de base. Il existe actuellement trois opérations prises en charge

:
  • L'opérateur AND détermine l'intersection de deux ensembles de
    • documents.
  • L'opérateur OR calcule l'union de deux ensembles de
    • documents.
  • L'opérateur NOT peut être utilisé pour
    • calculer le complément d'un ensemble
de documents par rapport à un autre.

Les opérateurs binaires sur les ensembles AND, OR et NOT doivent être saisis en lettres majuscules ; sinon, ils sont interprétés comme des requêtes de termes de base au lieu d'opérateurs sur les ensembles. Chacun des deux opérandes d'un opérateur peut être une requête FTS de base, ou le résultat d'une autre opération sur les ensembles AND, OR ou NOT. Les parenthèses peuvent être utilisées pour contrôler la précédence et le

groupement.

L'opérateur AND est implicite pour les requêtes de base adjacentes sans aucun opérateur explicite. Par exemple, l'expression de requête "implicit operator" est une version plus concise de "implicit AND

operator".

Les opérations booléennes telles que décrites ci-dessus correspondent à la soi-disant "syntaxe de requête améliorée" de sqlite ; c'est la version compilée avec "DBD::SQLite", à partir de la version 1.31. Une version antérieure, appelée la "syntaxe de requête standard", prenait en charge les jetons préfixés par les si

gnes '+' ou '-' (pour l'inclusion ou l'exclusion de jetons) ; si votre applicat
ion doit prendre en charge cette ancienne syntaxe, utilisez DBD::SQLite::FTS3Tr
ansitional (publié dans une distribution séparée) pour effectuer la conversion.

TOKENISATEUR

S

Concep

t

Le comportement des index de texte intégré dépend fortement de la manière dont les documents sont divisés en jetons ; par conséquent, les déclarations de tables FTS peuvent spécifier explicitement comment effectuer la tokenisation

: 
CREATE ... USING fts4(<columns>, tokenize=<tokenizer>
)

où "<tokenizer>" est une séquence de mots séparés par des espaces qui déclenche un tokenisateur spécifique. Les tokenisateurs p

euvent être des fonctions intégrées de SQLite, écrites en code C,
ou des tokenisateurs Perl. Les deux sont expliqués ci-dessous.

Tokenisateurs intégrés de

SQLite

SQLite est livré avec quelques tokenisateurs intégrés (voir http://www.sqlite.org/fts3.html#tokenizer)

:
simp
le
Avec le tokenisateur simple, un terme est une séquence contiguë de caractères éligibles, où les caractères éligibles sont tous les caractères alphanumériques, le caractère "_", et tous les caractères dont les points de code UTF sont supérieurs ou égaux à 128. Tous les autres caractères sont écartés lors de la division d'un document en termes. Ils servent uniquement à séparer les termes adjacents.

Tous les caractères en majuscules dans la plage ASCII (points de code UTF inférieurs à 128) sont trans

formés en leurs équivalents en minuscules dans le cadre du processus de tokenisation. Ainsi, les requ
êtes de texte intégré ne tiennent pas compte de la casse lors de l'utilisation du tokenisateur simple.
port
er
Le tokenisateur porter utilise les mêmes règles pour séparer le document d'entrée en termes, mais en plus de mettre tous les termes en minuscules, il utilise l'algorithme de stemming Porter pour réduire les mots de la langue anglaise liés à une racine
commune.
ic
u
Le tokenisateur icu utilise la bibliothèque ICU pour décider comment identifier les caractères de mot dans différentes langues ; cependant, cela nécessite que SQLite soit compilé avec le symbole de préprocesseur "SQLITE_ENABLE_ICU" défini. Ainsi, pour utiliser ce tokenisateur, vous devez modifier Makefile.PL pour ajouter ce drapeau dans @CC_DEFINE, puis recompiler "DBD::SQLite" ; bien entendu, le prérequis est d'avoir une bibliothèque ICU disponible sur votre
système.
unicode
61
Le tokenisateur unicode61 fonctionne de manière très similaire à "simple" sauf qu'il effectue une conversion de casse unicode complète selon les règles de la version 6.1 d'Unicode et qu'il reconnaît les caractères d'espace et de ponctuation unicode et les utilise pour séparer les jetons. En revanche, le tokenisateur simple ne fait la conversion de casse que des caractères ASCII et ne reconnaît que les caractères d'espace et de ponctuation ASCII comme séparateurs de jetons.

Par défaut, "unicode61" supprime également tous les diacritiques des caractères de l'alphabet latin. Ce comportement peut être modifié en ajoutant l'argument de tokenisateur "remove_diacritics=0". Par

exemple : 
-- Créer des tables qui suppriment les diacritiques des caractères de l'alphabet latin
-- dans le cadre de la tokenisation.
CREATE VIRTUAL TABLE txt1 USING fts4(tokenize=unicode61);
CREATE VIRTUAL TABLE txt2 USING fts4(tokenize=unicode61 "remove_diacritics=1");
-- Créer une table qui ne supprime pas les diacritiques des caractères de l'alphabet
-- latin dans le cadre de la tokenisation.
CREATE VIRTUAL TABLE txt3 USING fts4(tokenize=unicode61 "remove_diacritics=0")
;

Des options supplémentaires peuvent personnaliser l'ensemble des points de code que unicode61 traite comme caractères séparateurs ou comme caractères de jeton -- voir la documentation dans http://www.sqlite

.org/fts
3.html#un
icode61.

Si un algorithme de tokenisation plus complexe est requis, par exemple pour impléme

nter le stemming, écarter la ponctuation, ou reconnaître les mots composés, utilisez
le tokenisateur perl pour implémenter votre propre logique, comme expliqué ci-dessous.

Tokenisateurs

Perl

Déclarer un tokenisateur

perl

En plus des tokenisateurs intégrés de SQLite, "DBD::SQLite" implémente un tokenisateur perl, qui peut se connecter à n'importe quel algorithme de tokenisation écrit en Perl. Ceci est spécifié comme suit

: 
CREATE ... USING fts4(<columns>, tokenize=perl '<perl_function>
')

où "<perl_function>" est un nom de fonction Perl entièrement qualifié (c'est-à-dire préfixé par le nom du paquet dans lequel cette fonction est déclarée). Ainsi, par exemple, si la fonction est "my_func" dans le programme principal,

écrivez 
CREATE ... USING fts4(<columns>, tokenize=perl 'main::
my_func')

Écrire un tokenisateur perl à la

main

Cette fonction doit retourner une référence de code qui prend une chaîne comme argument unique, et retourne un itérateur (une autre fonction), qui retourne un tuple "($term, $len, $start, $end, $index)" pour chaque terme. Voici un exemple simple qui tokenise sur des mots selon la locale perl

actuelle 
sub locale_tokenizer {
  return sub {
    my $string = shift;
    use locale;
    my $regex      = qr/\w+/;
    my $term_index = 0;
    return sub { # closure
      $string =~ /$regex/g or return; # either match, or no more token
      my ($start, $end) = ($-[0], $+[0]);
      my $len           = $end-$start;
      my $term          = substr($string, $start, $len);
      return ($term, $len, $start, $end, $term_index++);
    }
  };
}

Il doit y avoir trois niveaux de sous-programmes, dans une sorte de structure de "poupées russes", parce que

:
  • le sous-programme externe, nommé, est appelé chaque fois qu'on accède à une table FTS avec ce
    • tokenisateur
  • le sous-programme interne, anonyme, est appelé chaque fois qu'une nouvelle chaîne doit être tokenisée (soit pour insérer un nouveau texte dans la table, soit pour analyser une requête)
    • .
  • le sous-programme le plus interne, anonyme,
    • est appelé à plusieurs reprises pour récupé
rer tous les termes dans cette chaîne.

Utiliser Search::

Tokenizer

Au lieu d'écrire des tokenisateurs à la main, vous pouvez en récupérer un de ceux déjà implémentés dans le module Search::Tokenizer. Par exemple, si vous voulez ignorer les différences entre les caractères accentués, vous pouvez écrire

: 
use Search::Tokenizer;
$dbh->do(<<"") or die DBI::errstr;
CREATE ... USING fts4(<columns>, 
                      tokenize=perl 'Search::Tokenizer::
unaccent')

Alternativement, vous pouvez utiliser "new" dans Search::Tokenizer pour construire votre propre tokenisateur. Voici un exemple qui traite les mots composés (mots avec un tiret ou un point interne) comme des jetons uniques

: 
sub my_tokenizer {
  return Search::Tokenizer->new(
    regex => qr{\p{Word}+(?:[-./]\p{Word}+)*},
   )
;
}

Fts4aux - Accès direct à l'index de texte

intégré

Le contenu d'un index de texte intégré peut être accédé à travers le module de table virtuelle "fts4aux". Par exemple, en supposant que notre base de données contient une table indexée en texte intégré nommée "ft", nous pouvons déclarer

: 
CREATE VIRTUAL TABLE ft_terms USING
fts4aux(ft)

puis interroger la table "ft_terms" pour accéder à la liste des termes, leur fréquence, etc. Des exemples sont documentés dans http://www.sqlite.or

g/fts3.htm
l#fts4aux.

Comment économiser de l'espace de base de

données

Par défaut, FTS stocke une copie complète des documents indexés, ainsi que l'index de texte intégré. Sur une grande collection de documents, cela peut consommer pas mal d'espace disque. Cependanter, FTS propose des options pour compresser les documents, ou même pour ne pas les stocker du tout -- voir http://www.sqlite.org/fts3.html#fts4_options

.

dans
