NOM

DBD::SQLite2 - SGBDR autonome dans un pilote DBI (sqlite 2.x)

SYNOPSIS

use DBI;
my $dbh = DBI->connect("dbi:SQLite2:dbname=dbfile","","");

DESCRIPTION

SQLite est un moteur de base de données SGBDR du domaine public que vous pouvez trouver sur http://www.sqlite.org/.

Plutôt que de vous demander d'installer SQLite d'abord, parce que SQLite est du domaine public, DBD::SQLite2 inclut l'intégralité de celui-ci dans la distribution. Ainsi, pour obtenir un SGBDR rapide et capable de transactions pour votre projet perl, vous n'avez simplement qu'à installer ce module, et rien d'autre.

Pour un usage réel, veuillez utiliser le pilote DBD::SQLite mis à jour avec le backend sqlite3 à jour. SQLite2 prend en charge les fonctionnalités suivantes :

Implémente une grande partie de SQL92
Voir http://www.sqlite.org/lang.html pour les détails.
Une base de données complète dans un seul fichier disque
Tout ce qui concerne votre base de données est stocké dans un seul fichier disque, ce qui rend le déplacement des données plus facile qu'avec DBD::CSV.
Validation et annulation atomiques
Oui, DBD::SQLite2 est petit et léger, mais il prend en charge les transactions complètes
Extensible
Des fonctions agrégées ou régulières définies par l'utilisateur peuvent être enregistrées avec l'analyseur SQL.

Il y a beaucoup plus à cela, veuillez donc consulter la documentation sur le site web de SQLite, listé ci-dessus, pour les détails SQL. Consultez également DBI pour les détails sur l'utilisation de DBI lui-même.

CONFORMITÉ À LA SPÉCIFICATION DBI

L'API fonctionne comme chaque module DBI. Veuillez voir DBI pour plus de détails sur les fonctionnalités de base.

Actuellement, de nombreux attributs de requête ne sont pas implémentés ou sont limités par la nature sans type de la base de données SQLite2.

ATTRIBUTS PRIVÉS DU PILOTE

Attributs du gestionnaire de base de données

sqlite_version
Renvoie la version de la bibliothèque SQLite utilisée par DBD::SQLite2, c'est-à-dire "2.8.15".
sqlite_encoding
Renvoie soit "UTF-8" soit "iso8859" pour indiquer comment la bibliothèque SQLite a été compilée.
sqlite_handle_binary_nulls
Définissez cet attribut à 1 pour gérer de manière transparente les octets nuls binaires dans les données entre guillemets et renvoyées.

NOTE : Cela entraînera le doublement de tous les caractères barre oblique inverse ("\") dans toutes les colonnes, que celles-ci contiennent ou non des données binaires. Cela peut casser votre base de données si vous l'utilisez depuis une autre application. Cela n'utilise pas les fonctions intégrées "sqlite_encode_binary" et "sqlite_decode_binary" , ce qui peut être considéré comme un bogue.

MÉTHODES PRIVÉES DU PILOTE

$dbh->func('last_insert_rowid')

Cette méthode renvoie le dernier rowid inséré. Si vous spécifiez une clé primaire INTEGER comme première colonne de votre table, c'est cette colonne qui est renvoyée. Sinon, il s'agit de la colonne ROWID cachée. Voir la documentation de sqlite pour les détails.

$dbh->func( $name, $argc, $func_ref, "create_function" )

Cette méthode enregistrera une nouvelle fonction qui pourra être utilisée dans une requête SQL. Les paramètres de la méthode sont :

$name
Le nom de la fonction. C'est le nom de la fonction tel qu'il sera utilisé depuis SQL.
$argc
Le nombre d'arguments pris par la fonction. Si ce nombre est -1, la fonction peut prendre un nombre quelconque d'arguments.
$func_ref
Cela devrait être une référence vers l'implémentation de la fonction.

Par exemple, voici comment définir une fonction now() qui renvoie le nombre actuel de secondes depuis l'époque :

$dbh->func( 'now', 0, sub { return time }, 'create_function' );

Après cela, elle pourrait être utilisée depuis SQL comme :

INSERT INTO mytable ( now() );

$dbh->func( $name, $argc, $pkg, 'create_aggregate' )

Cette méthode enregistrera une nouvelle fonction agrégée qui pourra ensuite être utilisée depuis SQL. Les paramètres de la méthode sont :

$name
Le nom de la fonction agrégée, c'est le nom sous lequel la fonction sera disponible depuis SQL.
$argc
C'est un entier qui indique à l'analyseur SQL combien d'arguments la fonction prend. Si ce nombre est -1, la fonction peut prendre un nombre quelconque d'arguments.
$pkg
C'est le paquet qui implémente l'interface d'agrégation.

L'interface d'agrégation consiste à définir trois méthodes :

new()
Cette méthode sera appelée une fois pour créer un objet qui devrait être utilisé pour agréger les lignes d'un groupe particulier. Les méthodes step() et finalize() seront appelées sur la référence renvoyée par la méthode.
step(@_)
Cette méthode sera appelée une fois pour chaque ligne de l'agrégat.
finalize()
Cette méthode sera appelée une fois que toutes les lignes de l'agrégat auront été traitées et elle devrait renvoyer le résultat de la fonction agrégée. Quand il n'y a pas de lignes dans l'agrégat, finalize() sera appelée juste après new().

Voici une fonction agrégée simple qui renvoie la variance (exemple adapté de pysqlite) :

package variance;
sub new { bless [], shift; }
sub step {
    my ( $self, $value ) = @_;
    push @$self, $value;
}
sub finalize {
    my $self = $_[0];
    my $n = @$self;
    # Variance is NULL unless there is more than one row
    return undef unless $n || $n == 1;
    my $mu = 0;
    foreach my $v ( @$self ) {
        $mu += $v;
    }
    $mu /= $n;
    my $sigma = 0;
    foreach my $v ( @$self ) {
        $sigma += ($x - $mu)**2;
    }
    $sigma = $sigma / ($n - 1);
    return $sigma;
}
$dbh->func( "variance", 1, 'variance', "create_aggregate" );

La fonction agrégée peut ensuite être utilisée comme :

SELECT group_name, variance(score) FROM results
GROUP BY group_name;

NOTES

Pour accéder à la base de données depuis la ligne de commande, essayez d'utiliser dbish qui est fourni avec le module DBI. Tapez simplement :

dbish dbi:SQLite:foo.db

Sur la ligne de commande pour accéder au fichier foo.db.

Alternativement, vous pouvez installer SQLite depuis le lien ci-dessus sans entrer en conflit avec DBD::SQLite2 et utiliser l'outil en ligne de commande "sqlite" fourni.

PERFORMANCE

SQLite est rapide, très rapide. J'ai récemment traité mon fichier journal de 72 Mo avec lui, en insérant les données (plus de 400 000 lignes) en utilisant des transactions et en ne validant que tous les 1000 lignes (sinon l'insertion est assez lente), puis en effectuant des requêtes sur les données.

Des requêtes comme count(*) et avg(bytes) ont mis des fractions de seconde à renvoyer, mais ce qui m'a le plus surpris est :

SELECT url, count(*) as count FROM access_log
  GROUP BY url
  ORDER BY count desc
  LIMIT 20

Pour découvrir les 20 URL les plus visitées du site (http://axkit.org), et cela est renvoyé en moins de 2 secondes. Je réfléchis sérieusement à faire migrer mon code d'analyse de journaux vers ce petit démon de la vitesse !

Oh oui, et cela était sans aucun index sur la table, sur un PIII à 400 MHz.

Pour de meilleures performances, soyez soyez sûr d'ajuster vos paramètres hdparm si vous utilisez Linux. Vous pourriez aussi vouloir définir :

PRAGMA default_synchronous = OFF

Cela empêchera sqlite d'effectuer des fsync lors des écritures (ce qui ralentit considérablement les écritures non transactionnelles) au prix d'un peu moins de tranquillité d'esprit. Essayez aussi de jouer avec la pragma cache_size.
