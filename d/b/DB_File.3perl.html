Paramètres par défaut


Il est possible d'omettre certains ou tous les 4 derniers paramètres dans l'appel à "tie" et de les laisser prendre des valeurs par défaut. Comme DB_HASH est le format de fichier le plus couramment utilisé, l'appel :


tie %A, "DB_File", "filename" ;


est équivalent à :


tie %A, "DB_File", "filename", O_CREAT|O_RDWR, 0666, $DB_HASH ;


Il est également possible d'omettre le paramètre filename, de sorte que l'appel :


tie %A, "DB_File" ;


est équivalent à :


tie %A, "DB_File", undef, O_CREAT|O_RDWR, 0666, $DB_HASH ;


Voir "In Memory Databases" pour une discussion sur l'utilisation de
    "undef" à la place d'un nom de fichier.






Bases de données en mémoire


Berkeley DB permet la création de bases de données en mémoire en utilisant NULL (c'est-à-dire un "(char *)0" en C) à la place du nom de fichier. DB_File utilise
    "undef" au lieu de NULL pour fournir cette fonctionnalité.








DB_HASH


Le format de fichier DB_HASH est probablement le plus couramment utilisé des trois formats de fichiers que DB_File prend en charge. Il est également très simple à utiliser.




Un exemple simple


Cet exemple montre comment créer une base de données, ajouter des paires clé/valeur à la base de données, supprimer des paires clé/valeur et enfin comment énumérer le contenu de la base de données.


use warnings ;
use strict ;
use DB_File ;
our (%h, $k, $v) ;
unlink "fruit" ;
tie %h, "DB_File", "fruit", O_RDWR|O_CREAT, 0666, $DB_HASH
    or die "Cannot open file 'fruit': $!\n";
# Add a few key/value pairs to the file
$h{"apple"} = "red" ;
$h{"orange"} = "orange" ;
$h{"banana"} = "yellow" ;
$h{"tomato"} = "red" ;
# Check for existence of a key
print "Banana Exists\n\n" if $h{"banana"} ;
# Delete a key/value pair.
delete $h{"apple"} ;
# print the contents of the file
while (($k, $v) = each %h)
  { print "$k -> $v\n" }
untie %h ;


voici la sortie :


Banana Exists
orange -> orange
tomato -> red
banana -> yellow


Notez que, comme pour les tableaux associatifs ordinaires, l'ordre des clés récupérées est apparemment aléatoire.








DB_BTREE


Le format DB_BTREE est utile lorsque vous souhaitez stocker des données dans un ordre donné. Par défaut, les clés seront stockées dans l'ordre lexicographique, mais comme vous le verrez dans l'exemple de la section suivante, il est très facile de définir votre propre fonction de tri.




Changer l'ordre de tri BTREE


Ce script montre comment remplacer l'algorithme de tri par défaut utilisé par BTREE. Au lieu d'utiliser l'ordre lexicographique normal, une fonction de comparaison insensible à la casse sera utilisée.


use warnings ;
use strict ;
use DB_File ;
my %h ;
sub Compare
{
    my ($key1, $key2) = @_ ;
    "\L$key1" cmp "\L$key2" ;
}
# specify the Perl sub that will do the comparison
$DB_BTREE->{'compare'} = \&Compare ;
unlink "tree" ;
tie %h, "DB_File", "tree", O_RDWR|O_CREAT, 0666, $DB_BTREE
    or die "Cannot open file 'tree': $!\n" ;
# Add a key/value pair to the file
$h{'Wall'} = 'Larry' ;
$h{'Smith'} = 'John' ;
$h{'mouse'} = 'mickey' ;
$h{'duck'}  = 'donald' ;
# Delete
delete $h{"duck"} ;
# Cycle through the keys printing them in order.
# Note it is not necessary to sort the keys as
# the btree will have kept them in order automatically.
foreach (keys %h)
  { print "$_\n" }
untie %h ;


Voici la sortie du code ci-dessus.


mouse
Smith
Wall


Il y a quelques points à garder à l'esprit si vous souhaitez changer l'ordre dans une base de données BTREE :



  
1.

  
La nouvelle fonction de comparaison doit être spécifiée lorsque vous créez la base de données.

  
2.

  
Vous ne pouvez pas changer l'ordre une fois la base de données créée. Vous devez donc utiliser la même fonction de comparaison à chaque fois que vous accédez à la base de données.

  
3.

  
Les clés en double sont entièrement définies par la fonction de comparaison. Dans l'exemple insensible à la casse ci-dessus, les clés : 'KEY' et 'key' seraient considérées comme des doublons, et l'affectation à la seconde écraserait la première. Si les doublons sont autorisés (avec le drapeau R_DUP discuté ci-dessous), une seule copie des clés en double est stockée dans la base de données --- donc (encore avec l'exemple ci-dessus) l'affectation de trois valeurs aux clés : 'KEY', 'Key', et 'key' ne laisserait que la première clé : 'KEY' dans la base de données avec trois valeurs. Dans certaines situations, cela entraîne une perte d'informations, il faut donc faire attention à fournir des fonctions de comparaison complètes lorsque c'est nécessaire. Par exemple, la routine de comparaison ci-dessus pourrait être modifiée pour comparer également de manière sensible à la casse si deux clés sont égales dans la comparaison insensible à la casse :
        
sub compare {
    my($key1, $key2) = @_;
    lc $key1 cmp lc $key2 ||
    $key1 cmp $key2;
}


    
Et maintenant, vous n'aurez des doublons que lorsque les clés elles-mêmes sont réellement identiques. (note : dans les versions de la bibliothèque db antérieures à environ novembre 1996, de telles clés en double étaient conservées, il était donc possible de récupérer les clés originales dans les ensembles de clés qui étaient considérées comme égales).

  








Gestion des clés en double


Le type de fichier BTREE permet éventuellement d'associer une clé unique à un nombre arbitraire de valeurs. Cette option est activée en définissant l'élément flags de $DB_BTREE à R_DUP lors de la création de la base de données.


Il y a quelques difficultés à utiliser l'interface de hachage lié si vous souhaitez manipuler une base de données BTREE avec des clés en double. Considérez ce code :


use warnings ;
use strict ;
use DB_File ;
my ($filename, %h) ;
$filename = "tree" ;
unlink $filename ;
# Enable duplicate records
$DB_BTREE->{'flags'} = R_DUP ;
tie %h, "DB_File", $filename, O_RDWR|O_CREAT, 0666, $DB_BTREE
    or die "Cannot open $filename: $!\n";
# Add some key/value pairs to the file
$h{'Wall'} = 'Larry' ;
$h{'Wall'} = 'Brick' ; # Note the duplicate key
$h{'Wall'} = 'Brick' ; # Note the duplicate key and value
$h{'Smith'} = 'John' ;
$h{'mouse'} = 'mickey' ;
# iterate through the associative array
# and print each key/value pair.
foreach (sort keys %h)
  { print "$_  -> $h{$_}\n" }
untie %h ;


Voici la sortie :


Smith   -> John
Wall    -> Larry
Wall    -> Larry
Wall    -> Larry
mouse   -> mickey


Comme vous pouvez le voir, 3 enregistrements ont été créés avec la clé
    "Wall" - le seul problème est que, lorsqu'ils sont récupérés depuis la base de données, ils semblent avoir la même valeur, à savoir
    "Larry". Le problème est causé par la manière dont fonctionne l'interface de tableau associatif. Fondamentalement, lorsque l'interface de tableau associatif est utilisée pour récupérer la valeur associée à une clé donnée, elle ne récupérera jamais que la première valeur.


Bien que cela ne soit pas immédiatement évident à partir du code ci-dessus, l'interface de tableau associatif peut être utilisée pour écrire des valeurs avec des clés en double, mais elle ne peut pas être utilisée pour les relire depuis la base de données.


La façon de contourner ce problème est d'utiliser la méthode de l'API Berkeley DB appelée "seq". Cette méthode permet un accès séquentiel aux paires clé/valeur. Voir "THE API INTERFACE" pour les détails sur la méthode "seq" et sur l'API en général.


Voici le script ci-dessus réécrit en utilisant la méthode d'API
    "seq" .


use warnings ;
use strict ;
use DB_File ;
my ($filename, $x, %h, $status, $key, $value) ;
$filename = "tree" ;
unlink $filename ;
# Enable duplicate records
$DB_BTREE->{'flags'} = R_DUP ;
$x = tie %h, "DB_File", $filename, O_RDWR|O_CREAT, 0666, $DB_BTREE
    or die "Cannot open $filename: $!\n";
# Add some key/value pairs to the file
$h{'Wall'} = 'Larry' ;
$h{'Wall'} = 'Brick' ; # Note the duplicate key
$h{'Wall'} = 'Brick' ; # Note the duplicate key and value
$h{'Smith'} = 'John' ;
$h{'mouse'} = 'mickey' ;
# iterate through the btree using seq
# and print each key/value pair.
$key = $value = 0 ;
for ($status = $x->seq($key, $value, R_FIRST) ;
     $status == 0 ;
     $status = $x->seq($key, $value, R_NEXT) )
  {  print "$key -> $value\n" }
undef $x ;
untie %h ;


qui affiche :


Smith   -> John
Wall    -> Brick
Wall    -> Brick
Wall    -> Larry
mouse   -> mickey


Cette fois, nous avons obtenu toutes les paires clé/valeur, y compris les multiples valeurs associées à la clé
    "Wall".


Pour faciliter la vie lors de la manipulation de clés en double,
    DB_File est livré avec quelques méthodes utilitaires.






La get_dup() Méthode


La "get_dup" méthode aide à lire les valeurs en double depuis les bases de données BTREE. La méthode peut prendre les formes suivantes :


$count = $x->get_dup($key) ;
@list  = $x->get_dup($key) ;
%list  = $x->get_dup($key, 1) ;


Dans un contexte scalaire, la méthode retourne le nombre de valeurs associées à la clé, $key>.


En contexte liste, elle retourne toutes les valeurs qui correspondent à
    $key. Notez que les valeurs seront retournées dans un
    ordre apparemment aléatoire.


En contexte liste, si le second paramètre est présent et évalue à
    VRAI, la méthode retourne un tableau associatif. Les clés du tableau
    associatif correspondent aux valeurs qui ont correspondu dans le BTREE et
    les valeurs du tableau sont le compte du nombre de fois que cette valeur
    particulière est apparue dans le BTREE.


En supposant donc la base de données créée ci-dessus, nous pouvons utiliser
    "get_dup" comme ceci :


use warnings ;
use strict ;
use DB_File ;
my ($filename, $x, %h) ;
$filename = "tree" ;
# Enable duplicate records
$DB_BTREE->{'flags'} = R_DUP ;
$x = tie %h, "DB_File", $filename, O_RDWR|O_CREAT, 0666, $DB_BTREE
    or die "Cannot open $filename: $!\n";
my $cnt  = $x->get_dup("Wall") ;
print "Wall occurred $cnt times\n" ;
my %hash = $x->get_dup("Wall", 1) ;
print "Larry is there\n" if $hash{'Larry'} ;
print "There are $hash{'Brick'} Brick Walls\n" ;
my @list = sort $x->get_dup("Wall") ;
print "Wall =>      [@list]\n" ;
@list = $x->get_dup("Smith") ;
print "Smith =>     [@list]\n" ;
@list = $x->get_dup("Dog") ;
print "Dog =>       [@list]\n" ;


et cela affichera :


Wall occurred 3 times
Larry is there
There are 2 Brick Walls
Wall =>     [Brick Brick Larry]
Smith =>    [John]
Dog =>      []






La find_dup() Méthode


$status = $X->find_dup($key, $value) ;


Cette méthode vérifie l'existence d'une paire clé/valeur spécifique.
    Si la paire existe, le curseur est laissé pointant vers la paire et la
    méthode retourne 0. Sinon, la méthode retourne une valeur non nulle.


En supposant la base de données de l'exemple précédent :


use warnings ;
use strict ;
use DB_File ;
my ($filename, $x, %h, $found) ;

$DB_BTREE->{'flags'} = R_DUP ;

$found = ( $x->find_dup("Wall", "Larry") == 0 ? "" : "not") ;
print "Larry Wall is $found there\n" ;
$found = ( $x->find_dup("Wall", "Harry") == 0 ? "" : "not") ;
print "Harry Wall is $found there\n" ;
undef $x ;
untie %h ;


affiche ceci


Larry Wall is  there
Harry Wall is not there

Correspondance   de Clés Partielles


L'interface BTREE possède une fonctionnalité qui permet de faire
    correspondre des clés partielles. Cette fonctionnalité est uniquement disponible lorsque la méthode
    "seq" est utilisée avec le
    drapeau R_CURSOR.


$x->seq($key, $value, R_CURSOR) ;


Voici la citation pertinente de la page man dbopen où elle
    définit l'utilisation du drapeau R_CURSOR avec seq :


Note, pour la méthode d'accès DB_BTREE, la clé retournée n'est pas
nécessairement une correspondance exacte pour la clé spécifiée. La clé
retournée est la plus petite clé supérieure ou égale à la clé spécifiée,
permettant les correspondances de clés partielles et les recherches de plage.


Dans le script d'exemple ci-dessous, la
    "match" sous-routine utilise cette fonctionnalité pour trouver et
    afficher la première paire clé/valeur correspondante à partir d'une clé
    partielle.


use warnings ;
use strict ;
use DB_File ;
use Fcntl ;
my ($filename, $x, %h, $st, $key, $value) ;
sub match
{
    my $key = shift ;
    my $value = 0;
    my $orig_key = $key ;
    $x->seq($key, $value, R_CURSOR) ;
    print "$orig_key\t-> $key\t-> $value\n" ;
}
$filename = "tree" ;
unlink $filename ;
$x = tie %h, "DB_File", $filename, O_RDWR|O_CREAT, 0666, $DB_BTREE
    or die "Cannot open $filename: $!\n";
# Add some key/value pairs to the file
$h{'mouse'} = 'mickey' ;
$h{'Wall'} = 'Larry' ;
$h{'Walls'} = 'Brick' ;
$h{'Smith'} = 'John' ;
$key = $value = 0 ;
print "IN ORDER\n" ;
for ($st = $x->seq($key, $value, R_FIRST) ;
     $st == 0 ;
     $st = $x->seq($key, $value, R_NEXT) )
  {  print "$key    -> $value\n" }
print "\nPARTIAL MATCH\n" ;
match "Wa" ;
match "A" ;
match "a" ;
undef $x ;
untie %h ;


Voici la sortie :


IN ORDER
Smith -> John
Wall  -> Larry
Walls -> Brick
mouse -> mickey
PARTIAL MATCH
Wa -> Wall  -> Larry
A  -> Smith -> John
a  -> mouse -> mickey








DB_RECNO


DB_RECNO fournit une interface aux fichiers texte plats. Les
    enregistrements de longueur variable et de longueur fixe sont pris en charge.


Afin de rendre RECNO plus compatible avec Perl, le décalage de tableau
    pour tous les tableaux RECNO commence à 0 plutôt qu'à 1 comme dans Berkeley DB.


Comme pour les tableaux Perl normaux, un tableau RECNO peut être
    accédé en utilisant des index négatifs. L'index -1 fait référence au
    dernier élément du tableau, -2 à l'avant-dernier, et ainsi de suite.
    Tenter d'accéder à un élément avant le début du tableau provoquera une
    erreur fatale d'exécution.




L'Option 'bval'


Le fonctionnement de l'option bval mérite quelques explications. Voici
    la définition de bval tirée de la page man recno de Berkeley DB 1.85 :


The delimiting byte to be used to mark  the  end  of  a
record for variable-length records, and the pad charac-
ter for fixed-length records.  If no  value  is  speci-
fied,  newlines  (``\n'')  are  used to mark the end of
variable-length records and  fixed-length  records  are
padded with spaces.


La deuxième phrase est fausse. En fait, bval ne prendra par défaut la
    valeur "\n" que lorsque le paramètre openinfo
    dans dbopen est NULL. Si un paramètre openinfo non-NULL est utilisé du
    tout, la valeur qui se trouve dans bval sera utilisée. Cela signifie que
    vous devez toujours spécifier bval lorsque vous utilisez l'une des options
    du paramètre openinfo. Cette erreur de documentation sera corrigée dans la
    prochaine version de Berkeley DB.


Cela clarifie la situation concernant Berkeley DB lui-même. Qu'en
    est-il de DB_File? Eh bien, le comportement défini dans la citation ci-dessus est
    assez utile, donc DB_File s'y conforme.


Cela signifie que vous pouvez spécifier d'autres options (par exemple
    cachesize) et avoir quand même bval par défaut à "\n" pour
    les enregistrements de longueur variable, et à l'espace pour les
    enregistrements de longueur fixe.


Notez également que l'option bval ne vous permet de spécifier qu'un
    seul octet comme délimiteur.

Un   Exemple -- le problème de la terminaison 
NULL.

Considérez le scénario suivant. Vous avez une base de données DBM tque vous
    devez partager avec une application tierce en C. L'application en C suppose
    que toutes les clés et les valeurs sont terminées par NULL. Malheureusement, lorsque Perl
    écrit dans les bases de données DBM, il n'utilise pas de terminaison NULL, votre application
    Perl devra donc gérer elle-même la terminaison NULL. Lorsque vous écrivez dans
    la base de données, vous devrez utiliser quelque chose comme ceci :


$hash{"$key\0"} = "$value\0" ;


De même, le NULL doit être pris en compte lorsque vous
    considérez la longueur des clés/valeurs existantes.


Il serait beaucoup mieux si vous pouviez ignorer le problème des terminaisons
    NULL dans le code principal de l'application et disposer d'un mécanisme qui ajouterait
    automatiquement le NULL de terminaison à toutes les clés et valeurs lorsque vous écrivez dans
    la base de données et qui les supprimerait lorsque vous lisez depuis la base de données. Comme je suis sûr
    que vous l'avez déjà deviné, c'est un problème que les Filtres DBM peuvent résoudre très
    facilement.


use warnings ;
use strict ;
use DB_File ;
my %hash ;
my $filename = "filt" ;
unlink $filename ;
my $db = tie %hash, 'DB_File', $filename, O_CREAT|O_RDWR, 0666, $DB_HASH
  or die "Cannot open $filename: $!\n" ;
# Install DBM Filters
$db->filter_fetch_key  ( sub { s/\0$//    } ) ;
$db->filter_store_key  ( sub { $_ .= "\0" } ) ;
$db->filter_fetch_value( sub { s/\0$//    } ) ;
$db->filter_store_value( sub { $_ .= "\0" } ) ;
$hash{"abc"} = "def" ;
my $a = $hash{"ABC"} ;
# ...
undef $db ;
untie %hash ;


On espère que le contenu de chacun des filtres devrait être
    auto-explicatif. Les deux filtres "fetch" suppriment le NULL
    de terminaison, et les deux filtres "store" ajoutent un NULL de terminaison.






Un   autre exemple -- La clé est un int C.


Voici un autre exemple de la vie réelle. Par défaut, lorsque Perl
    écrit dans une base de données DBM, il écrit toujours la clé et la valeur sous forme de chaînes. Ainsi
    lorsque vous utilisez ceci :


$hash{12345} = "something" ;


la clé 12345 sera stockée dans la base de données DBM sous la forme de la chaîne de 5 octets
    "12345". Si vous voulez réellement que la clé soit stockée dans la
    base de données DBM sous la forme d'un int C, vous devrez utiliser
    "pack" lors de l'écriture, et
    "unpack" lors de la lecture.


Voici un Filtre DBM qui le fait :


use warnings ;
use strict ;
use DB_File ;
my %hash ;
my $filename = "filt" ;
unlink $filename ;
my $db = tie %hash, 'DB_File', $filename, O_CREAT|O_RDWR, 0666, $DB_HASH
  or die "Cannot open $filename: $!\n" ;
$db->filter_fetch_key  ( sub { $_ = unpack("i", $_) } ) ;
$db->filter_store_key  ( sub { $_ = pack ("i", $_) } ) ;
$hash{123} = "def" ;
# ...
undef $db ;
untie %hash ;


Cette fois, seuls deux filtres ont été utilisés -- nous n'avons besoin que de
    manipuler le contenu de la clé, il n'était donc pas nécessaire d'installer des
    filtres de valeur.

Verrouillage :   Le problème avec fd


Jusqu'à la version 1.72 de ce module, la technique recommandée pour
    le verrouillage des bases de données DB_File consistait à appliquer flock sur le descripteur de fichier renvoyé par la
    fonction "fd". Malheureusement, cette technique s'est avérée
    fondamentalement défaillante (Merci à David Harris pour avoir identifié le problème). Utilisez-la
    à vos propres risques !


La technique de verrouillage fonctionnait comme ceci.


$db = tie(%db, 'DB_File', 'foo.db', O_CREAT|O_RDWR, 0644)
    || die "dbcreat foo.db $!";
$fd = $db->fd;
open(DB_FH, "+<&=$fd") || die "dup $!";
flock (DB_FH, LOCK_EX) || die "flock: $!";
...
$db{"Tom"} = "Jerry" ;
...
flock(DB_FH, LOCK_UN);
undef $db;
untie %db;
close(DB_FH);


En termes simples, voici ce qui se passe :



  
1.

  
Utiliser "tie" pour ouvrir la base de données.

  
2.

  
Verrouiller la base de données avec fd & flock.

  
3.

  
Lire & Écrire dans la base de données.

  
4.

  
Déverrouiller et fermer la base de données.




Voici le cœur du problème. Un effet secondaire de l'ouverture de la base de données
    DB_File à l'étape 2 est qu'un bloc initial de la base de données
    sera lu depuis le disque et mis en cache en mémoire.


Pour voir pourquoi c'est un problème, considérez ce qui peut se passer lorsque deux
    processus, disons "A" et "B", veulent tous les deux mettre à jour la même base de données
    DB_File en utilisant les étapes de verrouillage décrites ci-dessus. Supposons
    que le processus "A" ait déjà ouvert la base de données et ait un verrou d'écriture,
    mais qu'il n'ait pas encore réellement mis à jour la base de données (il a terminé l'étape 2, mais
    n'a pas encore commencé l'étape 3). Maintenant, le processus "B" essaie d'ouvrir la même
    base de données - l'étape 1 réussira, mais il sera bloqué à l'étape 2 jusqu'à ce que le processus
    "A" libère le verrou. L'important à noter ici est qu'à
    ce moment-là, les deux processus auront mis en cache des blocs initiaux identiques
    depuis la base de données.


Maintenant, le processus "A" met à jour la base de données et se trouve
    modifier certaines des données contenues dans le tampon initial. Le processus "A"
    se termine, vidant toutes les données mises en cache vers le disque et libérant le verrou de la base de données.
    À ce stade, la base de données sur le disque reflétera correctement les changements
    effectués par le processus "A".


Le verrou étant libéré, le processus "B" peut maintenant continuer. Il
    met également à jour la base de données et, malheureusement, il modifie aussi les données qui
    étaient dans son tampon initial. Une fois que ces données sont vidées sur le disque, elles
    écraseront certaines/toutes les modifications que le processus "A" a faites à la
    base de données.


Le résultat de ce scénario est au mieux une base de données qui ne
    contient pas ce que vous attendez. Au pire, la base de données sera corrompue.


Ce qui précède ne se produira pas à chaque fois que des processus concurrents mettent à jour la même
    base de données DB_File , mais cela illustre pourquoi cette technique
    ne devrait pas être utilisée.






Moyens   sûrs de verrouiller une base de données


À partir de la version 2.x, Berkeley DB a un support interne pour
    le verrouillage. Le module compagnon de celui-ci, BerkeleyDB
    https://metacpan.org/pod/BerkeleyDB, fournit une interface à cette
    fonctionnalité de verrouillage. Si vous prenez au sérieux le verrouillage des bases de données Berkeley DB
    , je vous recommande fortement d'utiliser BerkeleyDB
    https://metacpan.org/pod/BerkeleyDB.


Si l'utilisation de BerkeleyDB https://metacpan.org/pod/BerkeleyDB
    n'est pas une option, il existe un certain nombre de modules disponibles sur CPAN qui peuvent être
    utilisés pour implémenter le verrouillage. Chacun implémente le verrouillage différemment et a
    des objectifs différents en tête. Il est donc utile de connaître la différence, afin
    que vous puissiez choisir le bon pour votre application. Voici les trois
    enveloppes de verrouillage :



  
Tie::DB_Lock

  
Une enveloppe DB_File qui crée des copies du fichier de base de données pour
      l'accès en lecture, de sorte que vous ayez une sorte de système de lecture concurrente à
      versions multiples. Cependant, les mises à jour restent séquentielles. À utiliser pour les bases de données où les lectures
      peuvent être longues et où des problèmes de cohérence peuvent survenir.

  
Tie::DB_LockFile

  
Une enveloppe DB_File qui a la capacité de verrouiller et de déverrouiller la
      base de données pendant qu'elle est utilisée. Évite le problème du tie-avant-flock en
      simplement ré-appliquant tie sur la base de données lorsque vous obtenez ou relâchez un
      verrou. En raison de la
      flexibilité pour relâcher et ré-acquérir le verrou au milieu d'une
      session, cela peut être adapté pour fonctionner avec des mises à jour et/ou des lectures longues si l'application suit les indices dans la
      documentation POD.

  
DB_File::Lock

  
Une enveloppe DB_File extrêmement légère qui applique simplement flock sur un fichier de verrouillage avant d'appliquer tie sur la base de données et relâche le verrou après l'untie.
      Permet d'utiliser le même fichier de verrouillage pour plusieurs bases de données pour éviter
      les problèmes d'interblocage, si désiré. À utiliser pour les bases de données où les mises à jour et les lectures
      sont rapides et où une sémantique de verrouillage flock simple suffit.








Partage   des bases de données avec des applications C


Il n'y a aucune raison technique pour laquelle une base de données Berkeley DB ne puisse pas être
    partagée à la fois par une application Perl et une application C.


La grande majorité des problèmes signalés dans ce domaine se
    résument au fait que les chaînes C sont terminées par NULL, tandis que les chaînes Perl ne
    le sont pas. Voir "DBM FILTERS" pour une méthode générique de contournement de ce
    problème.


Voici un exemple réel. Netscape 2.0 conserve un enregistrement des
    lieux que vous visitez ainsi que l'heure de votre dernière visite dans une base de données
    DB_HASH. Ceci est généralement stocké dans le fichier ~/.netscape/history.db.
    Le champ de clé dans la base de données est la chaîne de l'emplacement et le champ de valeur est
    l'heure à laquelle l'emplacement a été visité pour la dernière fois, stockée sous la forme d'une valeur binaire de 4 octets.


Si vous ne l'avez pas déjà deviné, la chaîne de l'emplacement est stockée avec
    un NULL de terminaison. Cela signifie que vous devez faire attention lorsque vous accédez à la
    base de données.


Voici un extrait de code qui est librement basé sur le script
    "ggh" de Tom Christiansen (disponible depuis votre archive CPAN la plus proche
    dans authors/id/TOMC/scripts/nshist.gz).


use warnings ;
use strict ;
use DB_File ;
use Fcntl ;
my ($dotdir, $HISTORY, %hist_db, $href, $binary_time, $date) ;
$dotdir = $ENV{HOME} || $ENV{LOGNAME};
$HISTORY = "$dotdir/.netscape/history.db";
tie %hist_db, 'DB_File', $HISTORY
    or die "Cannot open $HISTORY: $!\n" ;;
# Dump the complete database
while ( ($href, $binary_time) = each %hist_db ) {
    # remove the terminating NULL
    $href =~ s/\x00$// ;
    # convert the binary time into a user friendly string
    $date = localtime unpack("V", $binary_time);
    print "$date $href\n" ;
}
# check for the existence of a specific key
# remember to add the NULL
if ( $binary_time = $hist_db{"http://mox.perl.com/\x00"} ) {
    $date = localtime unpack("V", $binary_time) ;
    print "Last visited mox.perl.com on $date\n" ;
}
else {
    print "Never visited mox.perl.com\n"
}
untie %hist_db ;






Le untie() Piège


Si vous utilisez l'API Berkeley DB, il est très fortement
    recommandé de lire "The untie Gotcha" dans perltie.


Même si vous n'utilisez actuellement pas l'interface API, il est
    toujours utile de la lire.


Voici un exemple qui illustre le problème du point de vue de
    DB_File :


use DB_File ;
use Fcntl ;
my %x ;
my $X ;
$X = tie %x, 'DB_File', 'tst.fil' , O_RDWR|O_TRUNC
    or die "Cannot tie first time: $!" ;
$x{123} = 456 ;
untie %x ;
tie %x, 'DB_File', 'tst.fil' , O_RDWR|O_CREAT
    or die "Cannot tie second time: $!" ;
untie %x ;


Lors de l'exécution, le script produira ce message d'erreur :


Cannot tie second time: Invalid argument at bad.file line 14.


Bien que le message d'erreur ci-dessus fasse référence à la deuxième tie()
    du script, la source du problème réside en réalité dans le
    untie() qui la précède.


Après avoir lu perltie, vous avez probablement déjà deviné que
    l'erreur est causée par la copie supplémentaire de l'objet lié stockée dans
    $X. Si ce n'est pas le cas, le problème se résume au
    fait que le destructeur DB_File , DESTROY, ne sera pas appelé
    tant que toutes les références à l'objet lié ne seront pas détruites. À la fois la
    variable liée, %x, et $X ci-dessus
    détiennent une référence à l'objet. L'appel à untie() détruira la
    première, mais $X détient toujours une référence valide, donc le
    destructeur ne sera pas appelé et le fichier de base de données tst.fil restera ouvert. Le fait que Berkeley DB signale ensuite la tentative
    d'ouverture d'une base de données déjà ouverte via le message générique
    "Invalid argument" n'aide pas.


Si vous exécutez le script avec l'option
    "-w" , le message d'erreur devient :


untie attempted while 1 inner references still exist at bad.file line 12.
Cannot tie second time: Invalid argument at bad.file line 14.


ce qui identifie le vrai problème. Enfin, le script peut maintenant être
    modifié pour résoudre le problème initial en détruisant l'objet API avant
    le untie :


...
$x{123} = 456 ;
undef $X ;
untie %x ;
$X = tie %x, 'DB_File', 'tst.fil' , O_RDWR|O_CREAT
...








QUESTIONS   FRÉQUENTES




Pourquoi y a-t-il du code Perl dans ma base de données ?


Si vous regardez le contenu d'un fichier de base de données créé par
    DB_File, il peut parfois y avoir une partie d'un script Perl inclus dedans.


Cela se produit parce que Berkeley DB utilise de la mémoire dynamique pour
    allouer des tampons qui seront ensuite écrits dans le fichier de base de
    données. Comme cette mémoire est dynamique, elle aurait pu être utilisée
    pour n'importe quoi avant que DB ne l'allocation. Comme Berkeley DB ne
    vide pas la mémoire une fois qu'elle a été allouée, les parties inutilisées
    contiendront des données aléatoires. Dans le cas où un script Perl est
    écrit dans la base de données, ces données aléatoires correspondront à une
    zone de mémoire dynamique qui a été utilisée lors de la compilation du
    script.


À moins que vous n'ayez de la peine à l'idée qu'une partie de vos scripts
    Perl soit intégrée dans un fichier de base de données, il n'y a rien à
  craindre.






Comment stocker des structures de données complexes avec DB_File ?


Bien que DB_File ne puisse pas le faire directement, il existe un module
    qui peut se superposer de manière transparente à DB_File pour accomplir cette
  fonctionnalité.


Consultez le module MLDBM, disponible sur CPAN dans le répertoire
    modules/by-module/MLDBM.






Que signifie "wide character in subroutine entry" ?


Vous obtiendrez généralement ce message si vous travaillez avec des
    données UTF-8 et que vous voulez les lire/écrire depuis/vers un fichier de
    base de données Berkeley DB.


La façon la plus simple de gérer ce problème est d'utiliser le filtre
    pré-défini "utf8" DBM_Filter (voir DBM_Filter) qui a été conçu pour
    gérer cette situation.


L'exemple ci-dessous montre ce dont vous avez besoin si à la fois la clé et la
    valeur sont censées être en UTF-8.


use DB_File;
use DBM_Filter;
my $db = tie %h, 'DB_File', '/tmp/try.db', O_CREAT|O_RDWR, 0666, $DB_BTREE;
$db->Filter_Key_Push('utf8');
$db->Filter_Value_Push('utf8');
my $key = "\N{LATIN SMALL LETTER A WITH ACUTE}";
my $value = "\N{LATIN SMALL LETTER E WITH ACUTE}";
$h{ $key } = $value;






Que signifie "Invalid Argument" ?


Vous obtiendrez ce message d'erreur lorsque l'un des paramètres dans
    l'appel à "tie" est incorrect. Malheureusement, il y a
    pas mal de paramètres qui peuvent être erronés, il peut donc être difficile
    de déterminer lequel est en cause.


Voici quelques possibilités :



  
1.

  
Tenter de rouvrir une base de données sans la fermer.

  
2.

  
Utiliser l'indicateur O_WRONLY.








Que signifie "Bareword 'DB_File' not allowed" ?


Vous rencontrerez ce message d'erreur particulier lorsque vous avez la
    pragma "strict 'subs'" (ou la pragma strict complète)
    dans votre script. Considérez ce script :


use warnings ;
use strict ;
use DB_File ;
my %x ;
tie %x, DB_File, "filename" ;


Son exécution produit l'erreur en question :


Bareword "DB_File" not allowed while "strict subs" in use


Pour contourner l'erreur, placez le mot
    "DB_File" entre guillemets simples ou doubles, comme ceci :


tie %x, "DB_File", "filename" ;


Bien que cela puisse sembler vraiment pénible, cela vaut vraiment la peine
    d'avoir un "use strict" dans tous
    vos scripts.

ANOMALIES


Certaines anciennes versions de Berkeley DB avaient des problèmes avec les
    enregistrements de longueur fixe utilisant le format de fichier RECNO. Ce
    problème a été corrigé depuis la version 1.85 de Berkeley DB.


Je suis sûr qu'il y a des anomalies dans le code. Si vous en trouvez
    une, ou si vous pouvez suggérer des améliorations, je serais heureux de
    recevoir vos commentaires.

DISPONIBILITÉ


DB_File est fourni avec la distribution standard de la source Perl.
    Cherchez dans le répertoire ext/DB_File. Étant donné le temps qui s'écoule entre
    les versions de Perl, la version fournie avec Perl est probablement
    obsolète, la version la plus récente peut donc toujours être trouvée sur
    CPAN (voir "CPAN" dans perlmodlib pour plus de détails), dans le répertoire
    modules/by-module/DB_File.


DB_File est conçu pour fonctionner avec n'importe quelle version de Berkeley
    DB, mais est limité aux fonctionnalités fournies par la version 1. Si vous
    voulez utiliser les nouvelles fonctionnalités disponibles dans Berkeley DB
    2.x ou supérieur, utilisez plutôt le module Perl BerkeleyDB https://metacpan.org/pod/BerkeleyDB
    .


Le site web officiel pour Berkeley DB est
    http://www.oracle.com/technology/products/berkeley-db/db/index.html.
    Toutes les versions de Berkeley DB y sont disponibles.


Alternativement, la version 1 de Berkeley DB est disponible dans votre
    archive CPAN la plus proche dans src/misc/db.1.85.tar.gz.
