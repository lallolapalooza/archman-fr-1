CRÉATION D'UN NOUVEAU

PILOTE

La première règle pour créer un nouveau pilote de base de données pour le Perl DBI est très simple : NE LE FAITES

PAS !

Il y a généralement déjà un pilote disponible pour la base de données que vous voulez utiliser, presque quel que soit le choix de votre base de données. Très souvent, la base de données fournira une interface de pilote ODBC, vous pouvez donc souvent utiliser DBD::ODBC pour accéder à la base de données. C'est généralement moins pratique sur une machine Unix que sur une machine Microsoft Windows, mais il existe de nombreuses options pour les gestionnaires de pilotes ODBC sur Unix également, et très souvent le pilote ODBC est fourni par le fournisseur de la base de

données.

Avant de décider que vous devez écrire un pilote, faites vos recherches pour vous assurer que vous ne gaspillez pas vos

énergies.

[En décembre 2002, le consensus était que si vous avez besoin d'un gestionnaire de pilotes ODBC sur Unix, alors le pilote unixODBC (disponible depuis http://www.unixodbc.org/) est la voie à suivre.

]

La deuxième règle pour créer un nouveau pilote de base de données pour le Perl DBI est également très simple : Ne le faites pas -- faites-le faire par quelqu'un d'autre

!

Néanmoins, il y a des occasions où il est nécessaire d'écrire un nouveau pilote, souvent pour utiliser un langage ou une API propriétaire pour accéder à la base de données plus rapidement, ou plus complètement, qu'un pilote ODBC ne le peut. Dans ce cas, vous devriez lire ce document très attentivement, mais avec un œil sceptique

approprié.

S'il y a quelque chose ici qui n'a aucun sens, questionnez-le. Vous pourriez avoir raison de penser que l'information est fausse, mais n'en tirez pas cette conclusion trop

rapidement.

Enregistrement d'un nouveau

pilote

Avant de passer par un processus officiel d'enregistrement, vous devrez établir qu'aucun pilote n'est déjà en cours de développement. Vous le ferez en demandant sur les listes de diffusion DBI s'il existe un tel pilote disponible, ou si quelqu'un travaille

dessus.

Lorsque vous obtiendrez le feu vert, vous devrez établir le nom du pilote et un préfixe pour le pilote. Typiquement, le nom est basé sur le nom du logiciel de base de données qu'il utilise, et le préfixe est une contraction de celui-ci. Ainsi, DBD::Oracle a le nom Oracle et le préfixe 'ora_'. Le préfixe doit être en minuscules et ne contenir de soulignés autres que celui à la

fin.

Cette information sera enregistrée dans le module DBI. En dehors des besoins de documentation, l'enregistrement est un prérequis pour installer des méthodes

privées.

Si vous écrivez un pilote qui ne sera pas distribué sur CPAN, alors vous devriez choisir un préfixe commençant par 'x_', pour éviter des collisions potentielles de préfixes avec des pilotes enregistrés à l'avenir. Ainsi, si vous avez écrit un pilote non distribué sur CPAN appelé DBD::CustomDB, le préfixe pourrait être 'x_cdb_'

.

Ce document suppose que vous écrivez un pilote appelé DBD::Driver, et que le préfixe 'drv_' est attrib

pilote.

Deux styles de pilotes de bases de

Il y a deux styles distincts de pilotes de bases de données qui peuvent être écrits pour fonctionner avec le Perl

DBI.

Votre pilote peut être écrit en Perl pur, sans nécessiter de compilateur C. Lorsque c'est faisable, c'est la meilleure solution, mais la plupart des bases de données ne sont pas écrites de manière à ce que cela puisse être fait. Quelques exemples de pilotes en Perl pur sont DBD::File et DBD::C

Alternativement, et le plus couramment, votre pilote

Version Perl pure de Makefile.

Vous commencez généralement par écrire Makefile.PL, un générateur de Makefile. Le contenu de ce fichier est décrit en détail dans les pages man d'ExtUtils::MakeMaker. C'est définitivement une bonne idée de commencer à les lire. D'une importance particulière pour les pilotes DBI est la méthode postamble de la page man d'ExtUtils::

Pour les utilisateurs d'Emacs, je recommande la méthode libscan, qui supprime les fichiers de sauvegarde d'Emacs (les noms de fichiers qui se terminent par un tilde '~') des listes de

Maintenant un exemple, j'utilise le mot "Driver" là où vous devriez insérer le nom de votre pilote

use ExtUtils::MakeMaker;
WriteMakefile(
    dbd_edit_mm_attribs( {
        'NAME'         => 'DBD::Driver',
        'VERSION_FROM' => 'Driver.pm',
        'INC'          => '',
        'dist'         => { 'SUFFIX'   => '.gz',
                            'COMPRESS' => 'gzip -9f' },
        'realclean'    => { FILES => '*.xsi' },
        'PREREQ_PM'    => '1.03',
        'CONFIGURE'    => sub {
            eval {require DBI::DBD;};
            if ($@) {
                warn $@;
                exit 0;
            }
            my $dbi_arch_dir = dbd_dbi_arch_dir();
            if (exists($opts{INC})) {
                return {INC => "$opts{INC} -I$dbi_arch_dir"};
            } else {
                return {INC => "-I$dbi_arch_dir"};
            }
        }
    },
    { create_pp_tests => 1})
);
package MY;
sub postamble { return main::dbd_postamble(@_); }
sub libscan {
    my ($self, $path) = @_;
    ($path =~ m/\~$/) ? undef : $path;
}

Notez les appels à dbd_edit_mm_attribs() et dbd_postamb

le().

La deuxième référence de hash dans l'appel à dbd_edit_mm_attribs() (contenant create_pp_tests()) est facultative ; vous ne devriez pas l'utiliser à moins que votre pilote ne soit un pilote Perl pur (c'est-à-dire qu'il n'utilise pas de code C et XS). PREREQ_PM indique à MakeMaker que DBI (version 1.03 dans ce cas) est requis pour ce module. Cela émettra un avertissement si DBI 1.03 est manquant lorsque quelqu'un tente d'installer votre DBD sans DBI 1.03. CONFIGURE est une sous-routine appelée par MakeMaker pendant "WriteMakefile". Comme nous sortons avec succès sans créer de Makefile lorsque DBI::DBD est manquant, les testeurs cpan ne signaleront pas d'échec. Cela peut sembler en contradiction avec PREREQ_PM, mais PREREQ_PM ne cause pas "WriteMakefile" d'échouer (à moins que vous ne spécifiiez aussi PREREQ_FATAL, ce qui est fortement découragé par MakeMaker), donc "WriteMakefile" continuerait d'appeler "dbd_dbi_arch_dir" et

échouerait.

Le constructeur du handle de base de

données

Le constructeur du handle de base de données est la méthode (d'où le changement de namespace) connect() du pilote

: 
sub connect
{
    my ($drh, $dr_dsn, $user, $auth, $attr) = @_;
    # Some database specific verifications, default settings
    # and the like can go here. This should only include
    # syntax checks or similar stuff where it's legal to
    # 'die' in case of errors.
    # For example, many database packages requires specific
    # environment variables to be set; this could be where you
    # validate that they are set, or default them if they are not set.
    my $driver_prefix = "drv_"; # the assigned prefix for this driver
    # Process attributes from the DSN; we assume ODBC syntax
    # here, that is, the DSN looks like var1=val1;...;varN=valN
    foreach my $var ( split /;/, $dr_dsn ) {
        my ($attr_name, $attr_value) = split '=', $var, 2;
        return $drh->set_err($DBI::stderr, "Can't parse DSN part '$var'")
            unless defined $attr_value;
        # add driver prefix to attribute name if it doesn't have it already
        $attr_name = $driver_prefix.$attr_name
            unless $attr_name =~ /^$driver_prefix/o;
        # Store attribute into %$attr, replacing any existing value.
        # The DBI will STORE() these into $dbh after we've connected
        $attr->{$attr_name} = $attr_value;
    }
    # Get the attributes we'll use to connect.
    # We use delete here because these no need to STORE them
    my $db = delete $attr->{drv_database} || delete $attr->{drv_db}
        or return $drh->set_err($DBI::stderr, "No database name given in DSN '$dr_dsn'");
    my $host = delete $attr->{drv_host} || 'localhost';
    my $port = delete $attr->{drv_port} || 123456;
    # Assume you can attach to your database via drv_connect:
    my $connection = drv_connect($db, $host, $port, $user, $auth)
        or return $drh->set_err($DBI::stderr, "Can't connect to $dr_dsn: ...");
    # create a 'blank' dbh (call superclass constructor)
    my ($outer, $dbh) = DBI::_new_dbh($drh, { Name => $dr_dsn });
    $dbh->STORE('Active', 1 );
    $dbh->{drv_connection} = $connection;
    return $outer;
}

C'est essentiellement la même chose que dans le constructeur du handle de pilote ci-dessus. Les arguments sont décrits dans

DBI.

Le constructeur DBI::_new_dbh() est appelé, retournant un handle de base de données. Le prototype du constructeur est

: 
($outer, $inner) = DBI::_new_dbh($drh, $public_attr, $private_attr)

avec des arguments similaires à ceux du constructeur du handle de pilote, sauf que le $class est remplacé par $drh. L' attribut Name est un attribut DBI standard (voir "Database Handle Attributes" dans DBI)

En contexte scalaire, seul le handle externe est

retourné.

Notez l'utilisation de la méthode STORE() pour définir les attributs du dbh. C'est parce que dans le code du pilote, le handle objet que vous avez est le handle 'interne' d'un hash lié, et non le handle externe que les utilisateurs de votre pilote

Parce que vous avez le handle interne, la magie de tie n'est pas invoquée lorsque vous lisez ou définissez des valeurs dans le hash. C'est souvent très pratique pour la vitesse lorsque vous voulez lire ou définir des attributs simples non spéciaux spécifiques au

pilote.

Cependant, certaines valeurs d'attributs, comme celles gérées par le DBI comme PrintError, n'existent pas réellement dans le hash et doivent être lues via "$h->FETCH($attrib)" et définies via "$h->STORE($attrib, $value)". En cas de doute, utilisez ces
