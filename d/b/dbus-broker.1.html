NOM

dbus-broker - Courtier de messages D-Bus

SYNOPSIS

dbus-broker [ OPTIONS ]
dbus-broker --version
dbus-broker --help

DESCRIPTION

dbus-broker est une implémentation de la Spécification du Bus de Messages D-Bus [1]. Chaque instance fournit un bus de messages unique auquel les clients peuvent se connecter et envoyer des messages. Le courtier s'occupe de la médiation des messages, du contrôle d'accès, des abonnements et du contrôle du bus, conformément à la spécification D-Bus.

dbus-broker est une implémentation pure , ce qui signifie qu'elle n'implémente que la médiation des messages. Elle a besoin d'un processus de contrôle qui effectue la configuration du bus et toute la communication externe. dbus-broker-launch(1) est un tel contrôleur visant une compatibilité parfaite avec dbus-daemon(1), l'implémentation de référence de D-Bus. Voir dbus-broker-launch(1) pour plus de détails sur la façon de lancer un bus de messages.

Cette page man documente l'interface entre dbus-broker et son contrôleur (par exemple, dbus-broker-launch(1)).

OPTIONS

Les options de ligne de commande suivantes sont prises en charge. Si une option est passée qui n'est pas listée ici, le courtier refusera de démarrer et sortira avec une erreur.

-h, --help
affiche les informations d'utilisation et sort immédiatement
--version
affiche la version de compilation et sort immédiatement
--audit
active la journalisation vers le sous-système d'audit Linux (sans effet si le support d'audit n'a pas été compilé ; Par défaut: désactivé)
--controller=FD
utilise le descripteur de fichier hérité avec le numéro donné comme socket de contrôle (voir la section CONTRÔLEUR ; cette option est obligatoire)
--logFD
utilise le descripteur de fichier hérité avec le numéro donné pour accéder au journal système (voir la section JOURNALISATION ; Par défaut: pas de journalisation)
--machine-id=ID
définit le machine-id à annoncer par le courtier via l'interface org.freedesktop.DBus (cette option est obligatoire et provient généralement de /etc/machine-id)
--max-bytes=BYTES
nombre maximum d'octets que chaque utilisateur peut allouer dans le courtier (Par défaut: 16 Mio)
--max-fds=FDS
nombre maximum de descripteurs de fichiers que chaque utilisateur peut allouer dans le courtier (Par défaut: 64)
--max-matches=MATCHES
nombre maximum de règles de correspondance que chaque utilisateur peut allouer dans le courtier (Par défaut: 16k)
--max-objects=OBJECTS
nombre total maximum de noms, pairs, réponses en attente, etc. que chaque utilisateur peut allouer dans le courtier (Par défaut: 16k)

CONTRÔLEUR

Chaque instance de dbus-broker hérite d'un socket unix(7) de son processus parent. Ce socket doit être spécifié via l'option --controller . Le courtier utilise ce socket pour accepter les commandes de contrôle de son processus parent (ou de quiconque possède l'autre bout de ce socket, également appelé le Contrôleur). Ce socket utilise la communication P2P D-Bus normale. Les interfaces fournies sur ce socket sont décrites dans la section API .

Par défaut, une instance de courtier est inerte. C'est-à-dire qu'après le fork et l'exécution d'un courtier, elle commence avec une liste vide de sockets de bus à gérer, ainsi qu'aucun moyen pour les clients de s'y connecter. Le contrôleur doit utiliser l'interface de contrôle pour créer des sockets d'écoute, spécifier la politique du bus, créer des noms activables et réagir aux événements du bus.

Le processus dbus-broker n'accède jamais à des ressources externes autres que celles qui lui sont passées via la ligne de commande ou les interfaces de contrôle. C'est-à-dire qu'aucun accès au système de fichiers, aucun appel à nss(5) , aucune communication avec un processus externe n'est effectuée par le courtier. Au contraire, le courtier n'accède jamais à d'autres ressources que les sockets qui lui sont fournis par le contrôleur. Ceci est garanti par l'implémentation. En même temps, cela implique que le contrôleur doit effectuer toutes les acquisitions de ressources externes et la communication au nom du courtier (si cela est nécessaire).

JOURNALISATION

Si un FD de journalisation est fourni via l'option de ligne de commande --log , le courtier journalisera certaines informations via ce FD. Deux types de journaux différents sont pris en charge :

1.
Si le FD est un socket unix(7) SOCK_STREAM , les informations sont journalisées sous forme de blocs lisibles par l'homme basés sur des lignes.
2.
Si le FD est un socket unix(7) SOCK_DGRAM , les informations sont journalisées sous forme de blocs de données annotés basés sur des paires clé/valeur. Le format est compatible avec celui utilisé par systemd-journal (bien qu'il ne dépende pas de systemd). Cette journalisation basée sur clé/valeur est beaucoup plus verbeuse que la journalisation basée sur flux. De nombreuses métadonnées sont fournies sous forme de clés distinctes, permettant un traçage et une interprétation précis des données journalisées.

Le courtier a des règles strictes lorsqu'il journalise des données. Il journalise lors du démarrage et de l'arrêt, un message chacun pour fournir des informations sur sa configuration et son environnement. Au cours de l'exécution, le courtier ne journalise que dans des situations inattendues. C'est-à-dire que chaque message que le courtier journalise au cours de l'exécution a été déclenché par un client défaillant. Si un système est correctement configuré, aucun message de journal d'exécution ne sera déclenché.

Les situations où le courtier journalise sont :

1.
Lors du démarrage et de l'arrêt, le courtier soumet un court message incluant des métadonnées sur son contrôleur, son environnement et sa configuration.
2.
Chaque fois qu'une requête de client est refusée par la politique, un message est journalisé incluant le client et les politiques concernés.
3.
Chaque fois qu'un client dépasse son quota de ressources, un message est journalisé avec des informations sur le client.

API

Les interfaces suivantes sont implémentées par le courtier sur les nœuds respectifs. Le contrôleur est libre de les appeler à tout moment. La connexion du contrôleur est considérée comme de confiance. Aucun comptage de ressources ni contrôle d'accès n'est effectué.

Le contrôleur lui-même doit également implémenter des interfaces à utiliser par le courtier. Voir la section ci-dessous pour une liste des interfaces sur le contrôleur.

nœud /org/bus1/DBus/Broker {
interface org.bus1.DBus.Broker {
# Crée un nouveau nom activable @name, comptabilisé sur l'utilisateur @uid. Le nom
# sera exposé par le contrôleur sous forme de @path (qui doit correspondre au
# gabarit /org/bus1/DBus/Name/%).
méthode AddName(o path, s name, u uid) -> ()
# Ajoute un socket d'écoute à ce bus. Le socket d'écoute doit être
# prêt en mode d'écoute et spécifié comme @socket. Dès que cet
# appel retourne, les tentatives de connexion entrantes des clients seront servies
# sur ce socket.
# L'écouteur est exposé par le contrôleur sous forme de @path (qui doit correspondre au
# gabarit /org/bus1/DBus/Listener/%).
# La politique pour tous les clients se connectant via ce socket est
# fournie comme @policy. Voir org.bus1.DBus.Listener.SetPolicy() pour
# plus de détails.
méthode AddListener(o path, h socket, v policy) -> ()
# Ce signal est émis selon les requêtes des clients de
# org.freedesktop.DBus.UpdateActivationEnvironment().
signal SetActivationEnvironment(a{ss} environment)
}
}
nœud /org/bus1/DBus/Listener/% {
interface org.bus1.DBus.Listener {
# Libère cet écouteur. Il sera immédiatement supprimé par le courtier
# et aucune autre connexion ne sera servie sur lui. Tous les clients connectés
# via cet écouteur sont déconnectés de force.
méthod Release() -> ()
# Change la politique de ce socket d'écoute en @policy. La syntaxe de
# la politique est encore susceptible de changer et n'est pas stable, pour l'instant.
méthode SetPolicy(v policy) -> ()
}
}
nœud /org/bus1/DBus/Name/% {
interface org.bus1.DBus.Name {
# Libère ce nom activable. Il sera retiré avec effet immédiat par le
# broker. Notez que le nom reste valide pour être acquis par les
# clients, bien qu'aucune fonctionnalité d'activation ne soit
# prise en charge pour ce nom.
méthode Release() -> ()
# Réinitialise l'état d'activation de ce nom. Toutes les requêtes
# d'activation en attente sont annulées. L'appel nécessite un numéro
# de série à transmettre. Il doit s'agir du numéro de série reçu lors
# du dernier événement d'activation sur ce nom. Les appels avec d'autres
# numéros de série sont ignorés silencieusement et considérés comme obsolètes.
# Une chaîne org.bus1.DBus.Name.Error est également transmise, donnant un
# indice sur la raison de la réinitialisation de l'activation. La liste est définie ci-dessous.
méthode Reset(t serial, s error) -> ()
# La requête d'activation a échoué : une requête de désactivation concurrente est déjà en cours
error org.bus1.DBus.Name.Error.DestructiveTransaction
# La requête d'activation a échoué : unité inconnue
error org.bus1.DBus.Name.Error.UnknownUnit
# La requête d'activation a échoué : l'unité est masquée
error org.bus1.DBus.Name.Error.MaskedUnit
# La requête d'activation a échoué : l'unité est invalide
error org.bus1.DBus.Name.Error.InvalidUnit
# Le travail d'activation de l'unité a réussi, mais l'unité a échoué par la suite
error org.bus1.DBus.Name.Error.UnitFailure
# Le travail de démarrage était valide, mais il a échoué pendant l'activation
error org.bus1.DBus.Name.Error.StartupFailure
# Le travail de démarrage était valide, mais il a été ignoré pendant l'activation
error org.bus1.DBus.Name.Error.StartupSkipped
# Requête d'activation annulée : le nom de bus a été libéré
error org.bus1.DBus.Name.Error.NameReleased
# Ce signal est envoyé chaque fois qu'un client demande l'activation de ce
# nom. Notez que les requêtes d'activation multiples sont regroupées par le
# broker. Le contrôleur peut annuler les requêtes en attente via la
# Reset() méthode.
# Le broker envoie un numéro de série avec l'événement. Ce numéro
# représente la requête d'activation et doit être utilisé lors de la réaction
# à la requête avec des méthodes comme Reset(). Le numéro de série est
# unique pour chaque événement et n'est jamais réutilisé. Un numéro de série de 0
# n'est jamais envoyé et est considéré comme invalide.
signal Activate(t serial)
}
}

Le contrôleur lui-même doit implémenter les interfaces suivantes sur les nœuds donnés. Ces interfaces sont appelées par le broker pour implémenter certaines parties de l'interface du pilote telles que définies par la spécification D-Bus.

Notez que tous les appels de méthode effectués par le broker sont toujours entièrement asynchrones. C'est-à-dire que, quelle que soit la durée de traitement de la requête, le broker reste pleinement opérationnel et peut même envoyer d'autres requêtes au contrôleur.

Un contrôleur est libre d'implémenter ces appels de manière bloquante. Cependant, il incombe au contrôleur de s'assurer de ne pas effectuer d' appels bloquants récursifs vers le broker (par quelque moyen que ce soit).

nœud /org/bus1/DBus/Controller {
interface org.bus1.DBus.Controller {
# Cette fonction est appelée pour chaque requête de client de
# org.freedesktop.DBus.ReloadConfig().
méthode ReloadConfig() -> ()
}
}
