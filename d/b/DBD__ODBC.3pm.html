AVERTISSEME

NT

Cette version de DBD::ODBC contient une correction significative pour l'unicode lors de l'insertion dans des colonnes CHAR/VARCHAR et il s'agit d'un changement de comportement par rapport à la version 1.45. Le changement ne s'applique qu'aux compilations unicode de DBD::ODBC (par défaut sous Windows mais vous pouvez aussi le compiler pour l'unicode sous unix) et aux colonnes char/varchar et non aux colonnes

nchar/nvarchar.

Avant cette version de DBD::ODBC, lorsque vous utilisiez la compilation unicode de DBD::ODBC et insériez des données dans des colonnes CHAR/VARCHAR à l'aide de paramètres, DBD::ODBC faisait ceci

:

1 si vous définissiez odbc_describe_parameters à 0, (empêchant ainsi DBD::ODBC
d'appeler SQLDescribeParam) les paramètres pour les colonnes CHAR/VARCHAR
étaient liés comme SQL_WVARCHAR ou SQL_WLONGVARCHAR (selon la
longueur du paramètre)

.

2 si vous définissiez odbc_force_bind_type alors tous les paramètres étaient liés comme vous
l'aviez

spécifié.

3 si vous surchargez le type de paramètre dans la méthode bind_param, le
type que vous aviez spécifié était

utilisé.

4 si le pilote ne prenait pas en charge SQLDescribeParam ou si SQLDescribeParam
était appelé et échouait, le type de liaison revenait au comportement par défaut comme en

1.

5 si rien de ce qui précède (et je suppose que c'est le cas normal pour la plupart
des gens) alors DBD::ODBC appelait SQLDescribeParam pour trouver le type du
paramètre. Cela renvoyait généralement SQL_CHAR ou SQL_VARCHAR pour les colonnes CHAR/VARCHAR,
ce qui n'est pas surprenant. Le paramètre était alors lié comme

SQL_VARCHAR.

Les points 1 à 4 s'appliquent toujours. Le point 5 a maintenant un comportement différent. Dans cette version, DBD::ODBC examine d'abord vos données liées avant d'utiliser le type renvoyé par SQLDescribeParam. Si vos données ressemblent à de l'unicode (c'est-à-dire si SvUTF8() est vrai), le paramètre est maintenant lié comme

SQL_WVARCHAR.

Que pourrait cela signifier pour vous

?

Si vous aviez des scalaires Perl liés à des colonnes CHAR/VARCHAR dans une insertion/mise à jour/suppression et que ces scalaires contenaient de l'unicode, DBD::ODBC passait en réalité les octets individuels de votre scalaire et non les caractères. Par exemple, si vous aviez le scalaire Perl "\x{20ac}" (le caractère unicode Euro) et que vous le liiez à un CHAR/VARCHAR, DBD::ODBC passerait 0xe2, 0x82, 0xc2 comme caractères séparés car ces octets étaient l'encodage UTF-8 de Perl pour un euro. Votre moteur de base de données les interpréterait probablement comme 3 caractères dans sa page de code actuelle. Si vous interrogiez votre base de données pour trouver la longueur des données insérées, vous obtiendriez probablement 3, et non

1.

Cependant, lorsque DBD::ODBC lisait cette colonne dans une instruction select, il liait la colonne comme SQL_WCHAR et vous obteniez 3 caractères avec l'octet utf8 activé (quels étaient ces caractères dépendait de la façon dont votre base de données ou votre pilote traduisait les caractères de la page de code en caractères larges)

.

Ce qui devrait se produire maintenant est que si vos paramètres liés sont unicode, DBD::ODBC les liera comme des caractères larges (unico

de) et votre pilote ou votre base de données tentera de les convertir dans la page de code qu'il utilise. Cela signifie que tant que
votre base de données peut stocker les données que vous insérez, lorsque vous les relisez, vous devriez obtenir ce que vous avez inséré.

odbc_default_bind_typ

Cette valeur vaut 0 par

Les anciennes versions de DBD::ODBC supposaient que le type de liaison de paramètre était 12 ("SQL_VARCHAR"). Les nouvelles versions tentent toujours d'appeler "SQLDescribeParam" pour trouver les types des paramètres mais si "SQLDescribeParam" est indisponible, DBD::ODBC revient à un type de liaison par défaut. Si vous définissez "odbc_default_bind_type" à une valeur autre que 0, vous surchargez la valeur interne par

odbc_force_bind_typ

e

Cette valeur vaut 0 par

défaut.

Si définie à une valeur autre que 0, cela forcera les paramètres liés à être liés comme ce type et "SQLDescribeParam" ne sera pas utilisé ; en d'autres termes, cela implique que "odbc_describe_parameters" est aussi défini à

faux.

Les anciennes versions de DBD::ODBC supposaient que le type de liaison de paramètre était 12 ("SQL_VARCHAR") et les nouvelles versions tentent toujours d'appeler "SQLDescribeParam" pour trouver les types des paramètres. Si votre pilote prend en charge "SQLDescribeParam" et que cela réussit, il peut quand même échouer à décrire les paramètres avec précision (MS SQL Server le fait parfois avec certaines requêtes SQL comme select myfunc(?) where 1 = 1). Gardez à l'esprit que si vous insérez des données unicode, vous voudrez probablement utiliser "SQL_WVARCHAR"/"SQL_WCHAR"/"SQL_WLONGVARCHAR" et non "SQL_VARCHAR"

Comme cet attribut a été créé pour contourner les pilotes ODBC bogués qui prennent en charge SQLDescribeParam mais décrivent incorrectement les paramètres, vous ferez probablement mieux de spécifier le type de liaison dans l'appel à "bind_param" au niveau de chaque instruction plutôt que de définir aveuglément "odbc_force_bind_type" pour toute une

connexion.

N.B. Si vous appelez la méthode "bind_param" avec un type SQL, cela annule tout ce qui

précède.

odbc_force_rebin

d

Cela permet de gérer des cas particuliers, notamment lors de l'utilisation de plusieurs ensembles de résultats. Définissez-le avant execute pour "forcer" DBD::ODBC à réobtenir le nombre de colonnes et les types de colonnes de l'ensemble de résultats pour chaque execute. Particulièrement utile pour appeler des procédures stockées qui peuvent retourner différents ensembles de résultats à chaque exécution. La seule pénalité de performance est lors de execute(), mais je ne voulais pas supporter cette pénalité dans toutes les circonstances. C'est probablement assez rare. Cet attribut sera automatiquement défini lorsque plusieurs ensembles de résultats sont déclenchés. La plupart des gens ne devraient pas avoir à s'en

soucier.

odbc_utf8_o

n

Définissez ce drapeau pour traiter toutes les chaînes retournées par le pilote ODBC (sauf les colonnes décrites comme SQL_BINARY ou SQL_TIMESTAMP et ses variations) comme encodées en UTF-8. Certains pilotes ODBC (comme Aster et peut-être PostgreSQL) retournent des données encodées en UTF-8 mais ne prennent pas en charge l'API unicode SQLxxxW. Activer ce drapeau fera que DBD::ODBC traitera les données retournées par le pilote comme encodées en UTF-8 et elles seront marquées comme telles dans

Perl.

Ne confondez pas cela avec le support unicode de DBD::ODBC. L'attribut "odbc_utf8_on" ne s'applique qu'aux compilations de DBD::ODBC non activées pour

unicode.

odbc_describe_parameter

s

Activé par défaut. Lorsqu'il est défini, cela permet à DBD::ODBC d'appeler SQLDescribeParam (si le pilote le prend en charge) pour récupérer des informations sur les

paramètres.

Lorsqu'il est désactivé/faux, DBD::ODBC n'appellera pas SQLDescribeParam et utilisera par défaut la liaison des paramètres en SQL_CHAR/SQL_WCHAR en fonction du type de compilation et du fait que vos données soient unicode ou

non.

Vous n'avez pas à désactiver odbc_describe_parameters juste parce que votre pilote ne prend pas en charge SQLDescribeParam, car DBD::ODBC le déterminera au démarrage via SQLGetFunctions

.

Notez : désactiver odbc_describe_parameters lorsque votre pilote prend en charge SQLDescribeParam peut empêcher DBD::ODBC de lier correctement les paramètres pour certains types de

colonnes.

Vous pouvez également définir cet attribut dans les attributs passés à la méthode

prepare.

Cet attribut a été ajouté pour qu'une personne passant de freeTDS (un pilote qui ne prend pas en charge SQLDescribeParam) à un pilote qui prend en cha

rge SQLDescribeParam puisse le faire sans changer quoi que ce soit en Perl. La situation était très spécifique car les dates étaient liées en tant que
dates lorsque SQLDescribeParam était appelé et en tant que caractères sinon, et le format de données n'était pas un format de date pris en charge.

odbc_taf_callbac

k

NOTE : ceci est expérimental jusqu'à ce que je voie au moins plus d'un pilote ODBC qui prenne en charge

TAF.

Le Transparent Application Failover (TAF) est une fonctionnalité d'OCI qui permet aux clients de se reconnecter automatiquement à une instance en cas de défaillance de celle-ci. La reconnexion se fait automatiquement à partir de la bibliothèque OCI (Oracle Call Interface)

.

TAF prend en charge une fonction de rappel (callback) qui, une fois enregistrée, est appelée par le pilote pour vous informer de ce qui se passe et qui vous permet, dans une certaine mesure, de contrôler la gestion du

basculement.

Vous devez d'abord configurer TAF sur votre instance et ce processus est hors du cadre de ce document. Une fois TAF activé, vous définissez simplement "odbc_taf_callback" sur une référence de code qui devrait ressembler à ceci

: 
sub taf_handler {
 my ($dbh, $event, $type) = @_;
 # faire quelque chose ici
}

DBD::ODBC transmettra le handle de connexion ($dbh), le type d'événement Oracle (OCI_FO_END, OCI_FO_ABORT, OCI_FO_REAUTH, OCI_FO_BEGIN, OCI_FO_ERROR) et le type Oracle (OCI_FO_NONE, OCI_FO_SESSION, OCI_FO_SELECT, OCI_FO_TXNAL). Consultez la documentation Oracle pour savoir ce que sont ces constantes. Vous pouvez importer ces constantes à l'aide du tag d'exportation :taf. Si votre instance n'a pas TAF activé, il est probable qu'une tentative d'enregistrement d'un callback échouera, mais cela dépend du pilote (tout ce que fait DBD::ODBC est d'effectuer un appel SQLSetConnectAttr et de fournir un wrapper C qui appelle votre sous-programme Perl)

.

Voici un exemple commenté

: 
my $h = DBI->connect('dbi:ODBC:oracle','xxx','yyy',
                     {RaiseError => 1,
                      odbc_taf_callback => \&taf_handler}) or die "connect";
while (1) {
    my $s = $h->selectall_arrayref(q/select 1 from dual/);
    sleep 5;
}
sub taf_handler {
   my ($dbh, $event, $type) = @_;
   #print "taf_handler $dbh, $event, $type\n";
   if ($event == OCI_FO_BEGIN) {
       print "Instance unavailable, stand by\n";
       print "Your TAF type is : ",
           ($type == OCI_FO_NONE ? "NONE" :
                ($type == OCI_FO_SESSION ? "SESSION" :
                     ($type == OCI_FO_SELECT ? "SELECT" : "?"))) , "\n";
       # start a counter and each time OCI_FO_ERROR is passed in we will
       # count down and abort the failover when we hit 0.
       $count = 10;
       return 0;
   } elsif ($event == OCI_FO_ERROR) {
       # We get an OCI_FO_ERROR each time the failover fails
       # sleep a while until the count hits 0
       if (--$count < 1) {
           print "Giving up\n";
           return 0;            # give up
       } else {
           print "Retrying...\n";
           sleep 1;
           return OCI_FO_RETRY; # tell Oracle to retry
       }
   } elsif ($event == OCI_FO_REAUTH) {
       print "Failed over user. Resuming Services\n";
   } elsif ($event == OCI_FO_END) {
       print "Failover ended - resuming\n";
   }
   return 0;
}

NOTE : L'exemple ci-dessus est destiné à être utilisé avec le pilote ODBC Oracle Easysoft. ODBC ne définit aucun moyen standard de prendre en charge TAF et donc différents pilotes peuvent utiliser différents attributs de connexion pour le configurer ou peuvent même passer des arguments différents au callback. Malheureusement, je n'ai accès à aucun autre pilote ODBC qui prenne en charge TAF. Tant que je n'en vois pas d'autres, je ne peux pas créer d'interface générique. J'accepterai volontiers des correctifs pour tout autre pilote ou si vous m'envoyez une copie fonctionnelle du pilote et la documentation, j'ajouterai la prise en

Pour votre information, MS Access qui ne supporte pas les tableaux de paramètres produit une erreur HY092, "Invalid attribute/option

identifier".

Cependant, il existe un petit nombre de différences entre l'utilisation du execute_for_fetch de DBD::ODBC et l'utilisation de l'implémentation par défaut du DBI (qui appelle simplement execute plusieurs fois, une fois par ligne). Les différences que vous pourriez voir sont

:

o comme le execute_for_fetch du DBI fait une ligne à la fois, le résultat de execute est pour une ligne et presque tous les pilotes ODBC peuvent rapporter le nombre de lignes affectées lorsque SQLRowCount est appelé par execute. Lorsque des lots de paramètres sont envoyés, le pilote peut toujours retourner le nombre de lignes affectées mais c'est généralement par lot plutôt que par ligne. Par conséquent, le tableau tuple_status que vous pourriez passer à execute_for_fetch (ou execute_array) montre généralement -1 (inconnu) pour chaque ligne bien que le total affecté retourné en contexte de tableau soit un total affecté

correct.

o tous les pilotes ODBC n'ont pas un support ODBC suffisant (on peut argumenter que c'est un bug) pour un support correct des diagnostics lors de l'utilisation de tableaux. DBI dicte que si une ligne dans le lot est en erreur, tuple_status contiendra l'état, le natif et le message d'erreur. Cependant, le lot peut générer plusieurs erreurs par ligne (ce dont DBI ne dit rien) et plus d'une ligne peut être en erreur. Dans ODBC, nous obtenons une liste d'erreurs mais pour associer chacune à une ligne particulière, nous devons appeler SQLGetDiagField pour SQL_DIAG_ROW_NUMBER et il devrait dire à quelle ligne du lot le diagnostic est associé. Certains pilotes ODBC ne supportent pas correctement SQL_DIAG_ROW_NUMBER et alors DBD::ODBC ne peut pas savoir à quelle ligne du lot une erreur se réfère. Dans ce cas, DBD::ODBC rapportera une erreur disant "failed to retrieve diags", avec un état de HY000 et un code natif de 1, donc vous verrez toujours une erreur mais pas nécessairement exactement celle-ci. De plus, lorsque plus d'un diagnostic est trouvé pour une ligne, DBD::ODBC choisit le premier (qui est généralement le plus pertinent) car il n'y a aucun moyen de rapporter plus d'un diagnostic par ligne dans le tuple_status. Si le premier problème de SQL_DIAG_ROW_NUMBER s'avère être un problème pour vous, la trace de DBD::ODBC montrera toutes les erreurs et vous pouvez aussi utiliser "odbc_getdiagrec"

vous-même.

o Lier des paramètres avec execute_array et execute_for_fetch ne permet pas de définir les types de paramètres. Unicode - Mises en

Pour le support Unicode sur n'importe quelle plateforme en Perl, vous aurez besoin d'au moins Perl 5.8.1 - désolé mais c'est ainsi que les choses sont avec

Perl.

Le support Unicode dans DBD::ODBC attend qu'un WCHAR fasse 2 octets (comme c'est le cas sur Windows et comme la spécification ODBC le suggère). Tant qu'ODBC ne spécifie pas un autre support Unicode, il n'est pas prévu que cela change. Sur UNIX, il y a quelques gestionnaires de pilotes ODBC différents. Je n'ai testé que le gestionnaire de pilotes unixODBC (http://www.unixodbc.org) avec le support Unicode et il a été construit avec des valeurs par défaut qui définissent WCHAR comme faisant 2

octets.

Je crois que le gestionnaire de pilotes iODBC attend que les caractères larges soient des types wchar_t (qui font généralement 4 octets) et par conséquent DBD::ODBC ne fonctionnera pas avec iODBC lorsqu'il est construit pour

unicode.

Le pilote ODBC doit attendre que les données unicode spécifiées dans SQLBindParameter et SQLBindCol soient en UTF-16 avec l'endianness locale. De même, dans les appels à SQLPrepareW, SQLDescribeColW et SQLDriverConnectW

.

Vous devez être conscient qu'une fois le support Unicode activé, il affecte un certain nombre de méthodes DBI (certaines auxquelles vous ne vous attendriez peut-être pas). Par exemple, lors de l'énumération des tables, colonnes etc., certains pilotes (p. ex. Microsoft SQL Server) signaleront les types de colonnes comme des types larges même si les chaînes correspondent en réalité à l'ASCII 7 bits. Par conséquent, il y a un surcoût pour récupérer les données de cette colonne car 2 octets par caractère seront transmis (contre 1 lorsque le support Unicode n'est pas activé) et ces chaînes seront converties en UTF-8 mais finiront par correspondre (dans la plupart des cas) à l'ASCII 7 bits, de sorte qu'une grande partie du travail de conversion a été effectué pour rien. Si vous n'avez pas de noms de tables et de colonnes Unicode ou de données de colonnes Unicode dans vos tables, il est préférable de désactiver le support

Unicode.

Je ne suis actuellement pas sûr que le traitement ChopBlanks sur les chaînes Unicode fonctionne correctement sur UNIX. À défaut, la construction L' ' dans dbdimp.c pourrait ne pas fonctionner avec tous les compilateurs UNIX. Les rapports de problèmes et les correctifs sont les

Implémentation Unicode dans DBD::

ODBC

DBD::ODBC utilise les versions à caractères larges de l'API ODBC et le type ODBC SQL_WCHAR pour prendre en charge Unicode dans

Perl.

Les caractères larges renvoyés par le pilote ODBC seront convertis en UTF-8 et les scalaires perl auront le drapeau utf8 défini (en utilisant sv_utf8_decode)

.

IMPORTAN

T

Les scalaires Perl qui sont en UTF-8 et qui sont envoyés via l'API ODBC seront convertis en UTF-16 et transmis aux API larges ODBC ou signalés comme SQL_WCHAR (p. ex., dans le cas des colonnes liées). Les données récupérées qui sont des caractères larges sont converties de UTF-16 en UTF-8. Cependant, vous devez réaliser que la plupart des pilotes ODBC ne prennent pas en charge UTF-16, ODBC parle seulement de caractères larges de 2 octets et UCS-2 et UTF-16 ne sont pas identiques. UCS-2 ne prend en charge que les caractères Unicode du premier plan (le plan multilingue de base ou BMP) (points de code U+0000 à U+FFFF), les caractères les plus fréquemment utilisés. Alors pourquoi DBD::ODBC encode-t-il actuellement en UTF-16 ? Pour environ 97% des caractères Unicode dans la plage 0-0xFFFF, UCS-2 et UTF-16 sont exactement les mêmes (et là où ils diffèrent, il n'y a pas de caractère Unicode valide car la plage U+D800 à U+DFFF est réservée à une utilisation uniquement en tant que paires de substituants). Comme l'API ODBC utilise actuellement UCS-2, elle ne prend pas en charge les caractères Unicode avec des points de code supérieurs à 0xFFFF (si vous en savez plus, j'aimerais avoir de vos nouvelles). Cependant, parce que DBD::ODBC utilise l'encodage UTF-16, vous pouvez toujours insérer des caractères Unicode supérieurs à 0xFFFF dans votre base de données et les récupérer correctement, mais ils peuvent ne pas être traités comme un seul caractère Unicode dans votre base de données, p. ex., un "select length(a_column) from table" avec un seul caractère Unicode supérieur à 0xFFFF peut renvoyer 2 et non 1, vous ne pouvez donc pas utiliser les fonctions de base de données sur ces données comme upper/lower/length etc. mais vous pouvez au moins sauver les données dans votre base de données et les

récupérer.

Lorsqu'il est compilé pour Unicode, DBD::ODBC appellera toujours SQLDriverConnectW (et non SQLDriverConnect) même si a) votre chaîne de connexion n'est pas Unicode b) vous n'avez pas un DBI postérieur à 1.607, car unixODBC nécessite que SQLDriverConnectW soit appelé si vous voulez appeler d'autres API ODBC Unicode plus tard. Par conséquent, si vous compilez pour Unicode et passez des chaînes ASCII à la méthode connect, elles seront converties en UTF-16 et transmises à SQLDriverConnectW. Cela ne devrait faire aucune différence réelle pour Perl n'utilisant pas de chaînes de connexion

Unicode.

Vous aurez besoin d'un DBI postérieur à 1.607 pour prendre en charge les chaînes de connexion Unicode car jusqu'à après 1.607, il n'y avait aucun moyen pour DBI de passer des chaînes Unicode au

DBD.
