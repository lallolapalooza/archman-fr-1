SSL_WRITE(3ssl) OpenSSL SSL_WRITE(3ssl)

NOM

SSL_write_ex2, SSL_write_ex, SSL_write, SSL_sendfile, SSL_WRITE_FLAG_CONCLUDE - écrire des octets dans une connexion TLS/SSL

SYNTAXE

#include <openssl/ssl.h>
#define SSL_WRITE_FLAG_CONCLUDE
ossl_ssize_t SSL_sendfile(SSL *s, int fd, off_t offset, size_t size, int flags);
int SSL_write_ex2(SSL *s, const void *buf, size_t num,
                  uint64_t flags,
                  size_t *written);
int SSL_write_ex(SSL *s, const void *buf, size_t num, size_t *written);
int SSL_write(SSL *ssl, const void *buf, int num);

DESCRIPTION

SSL_write_ex() et SSL_write() écrivent num octets du tampon buf dans la connexion ssl spécifiée. En cas de succès, SSL_write_ex() stockera le nombre d'octets écrits dans *écrit.

La fonction SSL_write_ex2() fonctionne de manière similaire à SSL_write_ex() mais peut également accepter des indicateurs optionnels qui modifient son comportement. Appeler SSL_write_ex2() avec un argument flags de 0 est exactement équivalent à appeler SSL_write_ex().

SSL_sendfile() écrit size octets à partir du décalage offset du descripteur de fichier fd vers la connexion SSL spécifiée s. Cette fonction offre des sémantiques efficaces de type zéro-copie. SSL_sendfile() n'est disponible que lorsque le TLS noyau est activé, ce qui peut être vérifié en appelant BIO_get_ktls_send(). Elle est fournie ici pour permettre aux utilisateurs de maintenir la même interface. La signification de flags dépend de la plateforme. Actuellement, sous Linux, elle est ignorée.

L'argument flags de SSL_write_ex2() peut accepter zéro ou plusieurs des indicateurs suivants. Notez que les indicateurs pris en charge dépendront du type d'objet SSL et du protocole sous-jacent utilisé :

SSL_WRITE_FLAG_CONCLUDE
Cet indicateur n'est pris en charge que sur les objets SSL de flux QUIC (ou les objets SSL de connexion QUIC avec un flux par défaut attaché).

Si cet indicateur est défini et que l'appel à SSL_write_ex2() réussit, et que toutes les données passées à l'appel ont été écrites (ce qui signifie que "*written == num"), la partie d'envoi du flux QUIC pertinent est conclue automatiquement comme si SSL_stream_conclude(3) avait été appelée (provoquant la transmission d'un FIN pour le flux).

Bien que l'utilisation de cet indicateur soit sémantiquement équivalente à l'appel de SSL_stream_conclude(3) après un appel réussi à cette fonction, l'utilisation de cet indicateur permet une efficacité accrue par rapport à la formulation de ces deux appels API séparément, car elle permet aux données de flux écrites et à l'indicateur FIN indiquant la fin du flux d'être planifiés dans le cadre du même cadre QUIC STREAM et du même paquet QUIC.

Définir cet indicateur ne conclut pas la partie d'envoi d'un flux si toutes les données passées à l'appel n'ont pas été consommées.

Un appel à SSL_write_ex2() échoue si un indicateur non pris en charge ou non compris par l'objet SSL donné est passé. Une application doit déterminer si un indicateur est pris en charge (par exemple, pour SSL_WRITE_FLAG_CONCLUDE, qu'un objet SSL de flux QUIC est utilisé) avant de tenter de l'utiliser.

NOTES

Dans les paragraphes ci-dessous, une "fonction d'écriture" est définie comme étant soit SSL_write_ex(), soit SSL_write().

Si nécessaire, une fonction d'écriture négociera une session TLS/SSL, si elle n'a pas déjà été explicitement effectuée par SSL_connect(3) ou SSL_accept(3). Si le pair demande une renégociation, elle sera effectuée de manière transparente pendant l'opération de la fonction d'écriture. Le comportement des fonctions d'écriture dépend du BIO sous-jacent.

Pour que la négociation transparente réussisse, le ssl doit avoir été initialisé en mode client ou serveur. Ceci est fait en appelant SSL_set_connect_state(3) ou SSL_set_accept_state() avant le premier appel à une fonction d'écriture.

Si le BIO sous-jacent est bloquant, les fonctions d'écriture ne reviendront qu'une fois que l'opération d'écriture sera terminée ou qu'une erreur se sera produite.

Si le BIO sous-jacent est non bloquant, les fonctions d'écriture reviendront également lorsque le BIO sous-jacent n'a pas pu satisfaire les besoins de la fonction pour continuer l'opération. Dans ce cas, un appel à SSL_get_error(3) avec la valeur de retour de la fonction d'écriture retournera SSL_ERROR_WANT_READ ou SSL_ERROR_WANT_WRITE. Comme à tout moment une renégociation est possible, un appel à une fonction d'écriture peut également provoquer des opérations de lecture ! Le processus appelant doit alors répéter l'appel après avoir pris les mesures appropriées pour satisfaire les besoins de la fonction d'écriture. L'action dépend du BIO sous-jacent. En utilisant un socket non bloquant, rien ne doit être fait, mais select() peut être utilisé pour vérifier la condition requise. En utilisant un BIO tamponné, comme une paire de BIO, des données doivent être écrites dans ou récupérées hors du BIO avant de pouvoir continuer.

Les fonctions d'écriture ne retourneront avec succès que lorsque le contenu complet de buf de longueur num aura été écrit. Ce comportement par défaut peut être modifié avec l'option SSL_MODE_ENABLE_PARTIAL_WRITE de SSL_CTX_set_mode(3). Lorsque cet indicateur est défini, les fonctions d'écriture retourneront également avec succès lorsqu'une écriture partielle aura été complétée avec succès. Dans ce cas, l'opération de la fonction d'écriture est considérée comme terminée. Les octets sont envoyés et un nouvel appel d'écriture avec un nouveau tampon (en ayant retiré les octets déjà envoyés) doit être démarré. Une écriture partielle est effectuée avec la taille d'un bloc de message, soit 16 Ko.

Lorsqu'utilisé avec un objet SSL QUIC, l'appel d'une fonction d'E/S telle que SSL_write() permet d'effectuer le traitement des événements réseau internes. Il est important que ce traitement soit effectué régulièrement. Si une application n'utilise pas le mode assisté par fil, elle doit s'assurer qu'une fonction d'E/S telle que SSL_write() est appelée régulièrement, ou alternativement s'assurer que SSL_handle_events() est appelée régulièrement. Voir openssl-quic(7) et SSL_handle_events(3) pour plus d'informations.

AVERTISSEMENTS

Lorsqu'un appel de fonction d'écriture doit être répété car SSL_get_error(3) a retourné SSL_ERROR_WANT_READ ou SSL_ERROR_WANT_WRITE, il doit être répété avec les mêmes arguments. Les données qui ont été passées peuvent avoir été partiellement traitées. Lorsque SSL_MODE_ACCEPT_MOVING_WRITE_BUFFER a été défini à l'aide de SSL_CTX_set_mode(3) le pointeur peut être différent, mais les données et la longueur doivent toujours être les mêmes.

Vous ne devez pas appeler SSL_write() avec num=0, cela renverra une erreur. SSL_write_ex() peut être appelé avec num=0, mais n'enverra pas de données d'application au pair.

VALEURS DE RETOUR

SSL_write_ex() et SSL_write_ex2() retournent 1 en cas de succès ou 0 en cas d'échec. Le succès signifie que tous les octets de données d'application demandés ont été écrits dans la connexion SSL ou, si SSL_MODE_ENABLE_PARTIAL_WRITE est utilisé, au moins 1 octet de données d'application a été écrit dans la connexion SSL. L'échec signifie que tous les octets demandés n'ont pas encore été écrits (si SSL_MODE_ENABLE_PARTIAL_WRITE n'est pas utilisé) ou qu'aucun octet n'a pu être écrit dans la connexion SSL (si SSL_MODE_ENABLE_PARTIAL_WRITE est utilisé). Les échecs peuvent être retentables (par exemple, le tampon d'écriture réseau est temporairement plein) ou non retentables (par exemple, une erreur réseau fatale). En cas d'échec, appelez SSL_get_error(3) pour connaître la raison qui indique si l'appel est retentable ou non.

Pour SSL_write(), les valeurs de retour suivantes peuvent se produire :

> 0
L'opération d'écriture a réussi, la valeur de retour est le nombre d'octets effectivement écrits dans la connexion TLS/SSL.
<= 0
L'opération d'écriture a échoué, soit parce que la connexion a été fermée, une erreur s'est produite, soit une action doit être entreprise par le processus appelant. Appelez SSL_get_error() avec la valeur de retour ret pour connaître la raison.

SSL_write(3ssl) — 3.6.0

NAME

SSL_write, SSL_write_ex, SSL_write_ex2, SSL_sendfile - write data to a TLS/SSL connection

SYNOPSIS

 #include <openssl/ssl.h>
 int SSL_write(SSL *ssl, const void *buf, int num);
 int SSL_write_ex(SSL *ssl, const void *buf, size_t num, size_t *written);
 int SSL_write_ex2(SSL *ssl, const void *buf, size_t num, size_t *written,
                   unsigned int flags);
 int SSL_sendfile(SSL *ssl, int fd, off_t offset, size_t size);

DESCRIPTION

The SSL_write() function writes up to num bytes from the buffer buf to the TLS/SSL connection specified by ssl. The function may write fewer bytes than requested; the caller may call SSL_write() again to transmit the rest of the data.

The SSL_write_ex() function is an enhanced version of SSL_write(). It writes up to num bytes from the buffer buf to the TLS/SSL connection specified by ssl. The number of bytes actually written is returned in the location pointed to by written. The function may write fewer bytes than requested; the caller may call SSL_write_ex() again to transmit the rest of the data.

The SSL_write_ex2() function is similar to SSL_write_ex(), but it also accepts a flags argument. Currently, the only valid flag is SSL_MODE_ENABLE_PARTIAL_WRITE, which enables partial writes. If this flag is set, then SSL_write_ex2() will try to write as much data as possible, even if it's less than the requested amount. If the flag is not set, then SSL_write_ex2() will behave like SSL_write_ex().

The SSL_sendfile() function writes data from the file specified by fd to the TLS/SSL connection ssl. The data to be written starts at offset and has a maximum length of size. This function can be more efficient than reading the file into a buffer and then calling SSL_write(), as it may be able to send the data directly from the file system's page cache.

NOTES

The actual amount of data sent over the network might be less than requested, even if the functions return success. This is because of buffering within the TLS/SSL library and the underlying transport protocol. For SSL_write() and SSL_write_ex(), the caller must check the return value and potentially retry the operation with the remaining data if a partial write occurred.

For SSL_sendfile(), the size parameter specifies the maximum number of bytes to send. The actual number of bytes sent may be less than size

The ssl argument must be a pointer to an SSL object. The buf argument points to the data to be written. The num argument is the number of bytes to write. The fd argument is a file descriptor from which to send data. The offset argument is the starting offset in the file. The size argument is the number of bytes to send from the file.

The behavior of partial writes depends on the SSL/TLS library's configuration and the underlying BIO. For more details, see SSL_CTX_set_mode(3) and BIO_ctrl(3).

WARNINGS

This function is not thread-safe. Callers must ensure that only one thread calls SSL_write() (or related functions) on the same SSL object at any given time.

If SSL_write() returns a positive value less than num, it indicates a partial write. The caller must handle this by retrying the write operation with the remaining data. Failure to do so may result in data loss.

RETURN VALUES

For SSL_write(), the following return values can occur:

1
The write operation was successful. The return value is the number of bytes written, which may be less than num. The caller must call SSL_write() again to transmit the remaining data if a partial write occurred.
0
The TLS/SSL handshake is incomplete. Call SSL_write() again.
< 0
An error occurred. Call SSL_get_error() with the return value to determine the reason.

For SSL_write_ex(), the following return values can occur:

1
The write operation was successful. The number of bytes written is returned in the location pointed to by written. The caller must call SSL_write_ex() again to transmit the remaining data if a partial write occurred.
0
The TLS/SSL handshake is incomplete. Call SSL_write_ex() again.
< 0
An error occurred. Call SSL_get_error() with the return value to determine the reason.

For SSL_write_ex2(), the following return values can occur:

1
The write operation was successful. The number of bytes written is returned in the location pointed to by written. The caller must call SSL_write_ex2() again to transmit the remaining data if a partial write occurred.
0
The TLS/SSL handshake is incomplete. Call SSL_write_ex2() again.
< 0
An error occurred. Call SSL_get_error() with the return value to determine the reason.

For SSL_sendfile(), the following return values can occur:

>= 0
The write operation was successful, the return value is the number of bytes of the file written to the TLS/SSL connection. The return value can be less than size for a partial write.
< 0
The write operation was not successful, because either the connection was closed, an error occurred or action must be taken by the calling process. Call SSL_get_error() with the return value to find out the reason.

HISTORY

The SSL_write_ex() function was added in OpenSSL 1.1.1. The SSL_sendfile() function was added in OpenSSL 3.0. The SSL_write_ex2() function was added in OpenSSL 3.3.
