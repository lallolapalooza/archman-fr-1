SSL_CTX_dane_enable(3ssl)

Paquet: openssl

Licences: Apache-2.0

SSL_CTX_DANE_ENABLE(3ssl) OpenSSL SSL_CTX_DANE_ENABLE(3ssl)

NOM

SSL_CTX_dane_enable, SSL_CTX_dane_mtype_set, SSL_dane_enable, SSL_dane_tlsa_add, SSL_get0_dane_authority, SSL_get0_dane_tlsa, SSL_CTX_dane_set_flags, SSL_CTX_dane_clear_flags, SSL_dane_set_flags, SSL_dane_clear_flags - activer l'authentification TLS DANE du serveur TLS distant dans le client TLS local

SYNTAXE

#include <openssl/ssl.h>
int SSL_CTX_dane_enable(SSL_CTX *ctx);
int SSL_CTX_dane_mtype_set(SSL_CTX *ctx, const EVP_MD *md,
                           uint8_t mtype, uint8_t ord);
int SSL_dane_enable(SSL *s, const char *basedomain);
int SSL_dane_tlsa_add(SSL *s, uint8_t usage, uint8_t selector,
                      uint8_t mtype, const unsigned char *data, size_t dlen);
int SSL_get0_dane_authority(SSL *s, X509 **mcert, EVP_PKEY **mspki);
int SSL_get0_dane_tlsa(SSL *s, uint8_t *usage, uint8_t *selector,
                       uint8_t *mtype, const unsigned char **data,
                       size_t *dlen);
unsigned long SSL_CTX_dane_set_flags(SSL_CTX *ctx, unsigned long flags);
unsigned long SSL_CTX_dane_clear_flags(SSL_CTX *ctx, unsigned long flags);
unsigned long SSL_dane_set_flags(SSL *ssl, unsigned long flags);
unsigned long SSL_dane_clear_flags(SSL *ssl, unsigned long flags);

DESCRIPTION

Ces fonctions implémentent le support de l'authentification par pairs DANE TLSA (RFC6698 et RFC7671).

SSL_CTX_dane_enable() doit être appelée en premier pour initialiser l'état partagé requis pour le support DANE. Les connexions individuelles associées au contexte peuvent ensuite activer le support DANE par connexion selon les besoins. L'authentification DANE est implémentée dans la fonction X509_verify_cert(3), et les applications qui redéfinissent X509_verify_cert(3) via SSL_CTX_set_cert_verify_callback(3) sont responsables d'authentifier la chaîne de pairs de la manière qu'elles jugent appropriée.

SSL_CTX_dane_mtype_set() peut ensuite être appelée zéro ou plusieurs fois pour ajuster les algorithmes de hachage supportés. Cela doit être fait avant que des handles SSL ne soient créés pour le contexte.

L'argument mtype spécifie un type de correspondance DANE TLSA et l'argument md spécifie le handle de l'algorithme de hachage associé. L'argument ord spécifie un ordinal de force. Les algorithmes avec un ordinal de force plus élevé sont considérés comme plus sécurisés. Les ordinaux de force sont utilisés pour implémenter l'agilité des algorithmes de hachage RFC7671. La spécification d'un algorithme de hachage NULL pour un type de correspondance désactive le support pour ce type de correspondance. Le type de correspondance Full(0) ne peut pas être modifié ou désactivé.

Par défaut, le type de correspondance "SHA2-256(1)" (voir RFC7218 pour les définitions des acronymes des paramètres DANE TLSA) est mappé à EVP_sha256() avec un ordinal de force de 1 et le type de correspondance "SHA2-512(2)" est mappé à EVP_sha512() avec un ordinal de force de 2.

SSL_dane_enable() doit être appelée avant que la négociation SSL ne soit initiée avec SSL_connect(3) si (et seulement si) vous souhaitez activer DANE pour cette connexion. (La connexion doit être associée à un contexte SSL activé pour DANE). L'argument basedomain spécifie le domaine de base TLSA RFC7671, qui sera l'identificateur de référence du pair par défaut pour les vérifications de nom de certificat. Des noms de serveur supplémentaires peuvent être spécifiés via SSL_add1_host(3). Le basedomain est utilisé comme indication SNI par défaut si aucun n'a encore été spécifié via SSL_set_tlsext_host_name(3).

SSL_dane_tlsa_add() peut ensuite être appelée une ou plusieurs fois, pour charger chacun des enregistrements TLSA qui s'appliquent au pair TLS distant. (Ceci doit également être fait avant le début de la négociation SSL). Les arguments spécifient les champs de l'enregistrement TLSA. Le champ data est fourni sous forme binaire (RDATA réseau), et non sous forme de présentation ASCII hexadécimale, avec une longueur explicite passée via dlen. La bibliothèque prend une copie du contenu du tampon data et l'appelant peut libérer le tampon data d'origine lorsque cela lui convient. Une valeur de retour de 0 indique que des enregistrements TLSA « inutilisables » (avec des paramètres invalides ou non supportés) ont été fournis. Une valeur de retour négative indique une erreur interne lors du traitement de l'enregistrement.

L'appelant est censé vérifier la valeur de retour de chaque appel SSL_dane_tlsa_add() et prendre les mesures appropriées si aucun n'est utilisable ou si une erreur interne est rencontrée lors du traitement de certains enregistrements.

Si aucun enregistrement TLSA n'est ajouté avec succès, l'authentification DANE n'est pas activée et l'authentification sera basée sur tous les ancres de confiance traditionnelles configurées ; le succès de l'authentification dans ce cas ne signifie pas que le pair a été authentifié par DANE.

SSL_get0_dane_authority() peut être utilisée pour obtenir des informations plus détaillées sur l'ancre de confiance DANE correspondante après l'achèvement réussi de la connexion. La valeur de retour est négative si la vérification DANE a échoué (ou n'était pas activée), 0 si un enregistrement TLSA EE a directement correspondu au certificat feuille, ou un nombre positif indiquant la profondeur à laquelle un enregistrement TA a correspondu à un certificat émetteur. La chaîne vérifiée complète peut être récupérée via SSL_get0_verified_chain(3). La valeur de retour est un indice dans cette chaîne vérifiée, plutôt que la liste des certificats envoyés par le pair telle que renvoyée par SSL_get_peer_cert_chain(3).

Si l'argument mcert n'est pas NULL et qu'un enregistrement TLSA a correspondu à un certificat de la chaîne, un pointeur vers le certificat correspondant est renvoyé via mcert. L'adresse renvoyée est une référence interne à court terme au certificat et ne doit pas être libérée par l'application. Les applications qui souhaitent conserver l'accès au certificat peuvent appeler X509_up_ref(3) pour obtenir une référence à long terme qui doit ensuite être libérée via X509_free(3) une fois qu'elle n'est plus nécessaire.

Si aucun enregistrement TLSA ne correspond directement à un élément de la chaîne de certificats, mais qu'un enregistrement DANE-TA(2) SPKI(1) Full(0) a fourni la clé publique qui a signé un élément de la chaîne, alors cette clé est renvoyée via l'argument mspki (si non NULL). Dans ce cas, la valeur de retour est la profondeur de l'élément le plus haut de la chaîne de certificats validée. Comme avec mcert, il s'agit d'une référence interne à court terme, et EVP_PKEY_up_ref(3) et EVP_PKEY_free(3) peuvent être utilisés pour acquérir et libérer respectivement des références à long terme.

SSL_get0_dane_tlsa() peut être utilisé pour récupérer les champs de l'enregistrement TLSA qui a correspondu à la chaîne de certificats du pair. La valeur de retour indique la profondeur de correspondance ou l'échec de correspondance, tout comme avec SSL_get0_dane_authority(). Lorsque la valeur de retour est non négative, le stockage pointé par les paramètres usage, selector, mtype et data est mis à jour avec les champs d'enregistrement TLSA correspondants. Le champ data est sous forme binaire réseau, et n'est donc pas terminé par NUL, sa longueur est renvoyée via le paramètre dlen. Si l'un de ces paramètres est NULL, le champ correspondant n'est pas renvoyé. Le paramètre data est défini sur une copie interne à court terme du champ de données associé et ne doit pas être libéré par l'application. Les applications qui ont besoin d'un accès à long terme à ce champ doivent copier le contenu.

SSL_CTX_dane_set_flags() et SSL_dane_set_flags() peuvent être utilisés pour activer des fonctionnalités de vérification DANE optionnelles. SSL_CTX_dane_clear_flags() et SSL_dane_clear_flags() peuvent être utilisés pour désactiver les mêmes fonctionnalités. L'argument flags est un masque de bits des fonctionnalités à activer ou désactiver. Les flags définis pour un contexte SSL_CTX sont copiés dans chaque handle SSL associé à ce contexte au moment où le handle est créé. Les changements ultérieurs dans les flags du contexte n'ont aucun effet sur les flags définis pour le handle.

Actuellement, la seule option disponible est DANE_FLAG_NO_DANE_EE_NAMECHECKS qui peut être utilisée pour désactiver les vérifications de nom de serveur lors de l'authentification via des enregistrements TLSA DANE-EE(3). Pour certaines applications, principalement les navigateurs web, il n'est pas sûr de désactiver les vérifications de nom en raison des attaques de « partage de clé inconnu », dans lesquelles un serveur malveillant peut convaincre un client qu'une connexion à un serveur victime est en fait une connexion sécurisée au serveur malveillant. Le serveur malveillant peut alors être en mesure de violer les restrictions de script inter-origines. Ainsi, malgré le texte de la RFC7671, les vérifications de nom sont activées par défaut

VALEURS DE RETOUR

Les fonctions SSL_CTX_dane_enable(), SSL_CTX_dane_mtype_set(), SSL_dane_enable() et SSL_dane_tlsa_add() renvoient une valeur positive en cas de succès. Les valeurs de retour négatives indiquent des problèmes de ressources (manque de mémoire, etc.) dans la bibliothèque SSL, tandis qu'une valeur de retour de 0 indique une utilisation incorrecte ou une entrée invalide, telle qu'une utilisation de certificat, un sélecteur ou un type de correspondance TLSA non pris en charge. Les entrées invalides incluent également des données malformées, soit une longueur de résumé qui ne correspond pas à l'algorithme de résumé, soit un certificat Full(0) (forme binaire ASN.1 DER) ou une clé publique qui échoue à l'analyse.

Les fonctions SSL_get0_dane_authority() et SSL_get0_dane_tlsa() renvoient une valeur négative lorsque l'authentification DANE a échoué ou n'était pas activée. Une valeur non négative indique la profondeur de la chaîne au niveau de laquelle l'enregistrement TLSA correspondait à un certificat de chaîne, ou la profondeur du certificat le plus en haut, lorsque l'enregistrement TLSA est une clé publique complète qui en est le signataire.

Les fonctions SSL_CTX_dane_set_flags(), SSL_CTX_dane_clear_flags(), SSL_dane_set_flags() et SSL_dane_clear_flags() renvoient les flags en vigueur avant leur appel.

EXEMPLES

Supposons que "smtp.example.com" soit l'hôte MX du domaine "example.com", et qu'il possède des enregistrements TLSA validés par DNSSEC. Les appels ci-dessous effectueront une authentification DANE et organiseront la correspondance soit du nom d'hôte MX, soit du nom de domaine de destination dans le certificat du serveur SMTP. Les jokers sont pris en charge, mais doivent correspondre à l'ensemble de l'étiquette. Le nom réel correspondant dans le certificat (qui peut être un joker) est récupéré et doit être copié par l'application s'il doit être conservé au-delà de la durée de vie de la connexion SSL.

SSL_CTX *ctx;
SSL *ssl;
int (*verify_cb)(int ok, X509_STORE_CTX *sctx) = NULL;
int num_usable = 0;
const char *nexthop_domain = "example.com";
const char *dane_tlsa_domain = "smtp.example.com";
uint8_t usage, selector, mtype;
if ((ctx = SSL_CTX_new(TLS_client_method())) == NULL)
    /* erreur */
if (SSL_CTX_dane_enable(ctx) <= 0)
    /* erreur */
if ((ssl = SSL_new(ctx)) == NULL)
    /* erreur */
if (SSL_dane_enable(ssl, dane_tlsa_domain) <= 0)
    /* erreur */
/*
 * Pour de nombreuses applications, il est sûr de sauter les vérifications de
 * nom DANE-EE(3). Ne désactivez les vérifications que si les attaques de type
 * "partage de clé inconnu" ne présentent aucun risque pour votre
 * application.
 */
SSL_dane_set_flags(ssl, DANE_FLAG_NO_DANE_EE_NAMECHECKS);
if (!SSL_add1_host(ssl, nexthop_domain))
    /* erreur */
SSL_set_hostflags(ssl, X509_CHECK_FLAG_NO_PARTIAL_WILDCARDS);
for (... chaque enregistrement TLSA ...) {
    unsigned char *data;
    size_t len;
    int ret;
    /* définir usage, selector, mtype, data, len */
    /*
     * Les clients TLS DANE opportunistes ne prennent en charge que DANE-TA(2) ou
     * DANE-EE(3). Ils traitent toutes les autres utilisations de certificat, et
     * en particulier PKIX-TA(0) et PKIX-EE(1), comme inutilisables.
     */
    switch (usage) {
    default:
    case 0:     /* PKIX-TA(0) */
    case 1:     /* PKIX-EE(1) */
        continue;
    case 2:     /* DANE-TA(2) */
    case 3:     /* DANE-EE(3) */
        break;
    }
    ret = SSL_dane_tlsa_add(ssl, usage, selector, mtype, data, len);
    /* libérer data de manière appropriée */
    if (ret < 0)
        /* gérer l'erreur interne de la bibliothèque SSL */
    else if (ret == 0)
        /* gérer l'enregistrement TLSA inutilisable */
    else
        ++num_usable;
}
/*
 * À ce stade, le mode de vérification est toujours le défaut SSL_VERIFY_NONE.
 * Les clients DANE opportunistes utilisent le TLS non authentifié lorsque tous les
 * enregistrements TLSA sont inutilisables, donc poursuivez la négociation même si
 * l'authentification échoue.
 */
if (num_usable == 0) {
    /* Journaliser tous les enregistrements inutilisables ? */
    /* Facultativement, définir verify_cb à une fonction de rappel non NULL appropriée. */
    SSL_set_verify(ssl, SSL_VERIFY_NONE, verify_cb);
} else {
    /* Au moins un enregistrement utilisable. Nous nous attendons à vérifier le pair */
    /* Facultativement, définir verify_cb à une fonction de rappel non NULL appropriée. */
    /*
     * Ci-dessous, nous choisissons d'échouer la négociation lorsque la vérification
     * du pair échoue. Alternativement, utilisez le mode de vérification permissif
     * SSL_VERIFY_NONE, terminez la négociation, vérifiez le statut de vérification et,
     * si non vérifié, déconnectez-vous gracieusement au niveau de la couche application,
     * surtout si le protocole d'application prend en charge l'information du serveur
     * que l'authentification a échoué.
     */
    SSL_set_verify(ssl, SSL_VERIFY_PEER, verify_cb);
}
/*
 * Charger toute session sauvegardée pour reprise, en s'assurant que la session
 * précédente appliquait les mêmes exigences de sécurité et d'authentification que
 * celles attendues d'une connexion fraîche.
 */
/* Effectuer la négociation SSL_connect() et gérer les erreurs ici */
if (SSL_session_reused(ssl)) {
    if (SSL_get_verify_result(ssl) == X509_V_OK) {
        /*
         * La session reprise a été initialement vérifiée, cette connexion est
         * authentifiée.
         */
    } else {
        /*
         * La session reprise n'a pas été initialement vérifiée, cette connexion n'est
         * pas authentifiée.
         */
    }
} else if (SSL_get_verify_result(ssl) == X509_V_OK) {
    const char *peername = SSL_get0_peername(ssl);
    EVP_PKEY *mspki = NULL;
    int depth = SSL_get0_dane_authority(ssl, NULL, &mspki);
    if (depth >= 0) {
        (void) SSL_get0_dane_tlsa(ssl, &usage, &selector, &mtype, NULL, NULL);
        printf("DANE TLSA %d %d %d ", usage, selector, mtype);
        if (SSL_get0_peer_rpk(ssl) == NULL)
            printf("%s certificate at depth %d\n",
                   (mspki != NULL) ? "signed the peer" :
                   mdpth ? "matched the TA" : "matched the EE", mdpth);
        else
            printf(bio, "matched the peer raw public key\n");
    }
    if (peername != NULL) {
        /* Les vérifications de nom étaient dans le scope et correspondaient au peername */
        printf("Verified peername: %s\n", peername);
    }
} else {
    /*
     * Non authentifié, probablement tous les enregistrements TLSA inutilisables, mais
     * potentiellement une fonction de rappel a supprimé la terminaison de la connexion
     * malgré la présence d'enregistrements TLSA utilisables dont aucun n'a
     * correspondu. Procédez comme il convient pour les nouvelles connexions non
     * authentifiées.
     */
}

NOTES

Il est prévu que la majorité des clients utilisant DANE TLS effectuent une "TLS DANE opportuniste" au sens de RFC7672 et RFC7435. C'est-à-dire qu'ils utiliseront l'authentification DANE lorsque des enregistrements TLSA validés par DNSSEC sont publiés pour un pair donné, et sinon utiliseront le TLS non authentifié ou même en clair.

Ces applications devraient généralement considérer tout enregistrement TLSA publié par le pair avec les utilisations PKIX-TA(0) et PKIX-EE(1) comme "inutilisable", et ne devraient pas les inclure parmi les enregistrements TLSA utilisés pour authentifier les connexions des pairs. De plus, certains enregistrements TLSA avec des utilisations prises en charge peuvent être "inutilisables" en raison de paramètres invalides ou non pris en charge.

Lorsqu'un pair possède des enregistrements TLSA, mais qu'aucun n'est "utilisable", une application opportuniste doit éviter le clairtext, mais ne peut pas authentifier le pair, et devrait donc généralement procéder avec une connexion non authentifiée. Les applications opportunistes doivent noter la valeur de retour de chaque appel à SSL_dane_tlsa_add(), et si tous renvoient 0 (en raison de paramètres invalides ou non pris en charge), désactiver l'authentification du pair en appelant SSL_set_verify(3) avec mode égal à SSL_VERIFY_NONE.

NOM

SSL_CTX_dane_enable, SSL_CTX_dane_enable_tls, SSL_CTX_dane_enable_tlsa, SSL_CTX_dane_enable_валидация, SSL_CTX_dane_enable_валидация_валидация — Activation de la découverte de certificat basée sur DNS (DANE)

SYNTAXE

```c
int SSL_CTX_dane_enable(SSL_CTX *ctx, int flags);
int SSL_CTX_dane_enable_tls(SSL_CTX *ctx);
int SSL_CTX_dane_enable_tlsa(SSL_CTX *ctx);
int SSL_CTX_dane_enable_валидация(SSL_CTX *ctx, int flags);
int SSL_CTX_dane_enable_валидация_валидация(SSL_CTX *ctx, int flags);
```

DESCRIPTION

La fonctionnalité DANE permet aux clients de découvrir les certificats d'un serveur via des enregistrements DNS, plutôt que de dépendre de l'infrastructure de clés publiques (PKI) classique.

SSL_CTX_dane_enable active la prise en charge de DANE pour le contexte SSL spécifié par ctx. Les flags peuvent être une combinaison des valeurs suivantes :

  • SSL_CTX_DANE_FLAG_DEFAULT : Utilise les paramètres par défaut pour DANE.
  • SSL_CTX_DANE_FLAG_NO_DOWNGRADE : Empêche la rétrogradation vers la PKI classique si DANE échoue.

SSL_CTX_dane_enable_tls active la prise en charge de DANE pour le protocole TLS.

SSL_CTX_dane_enable_tlsa active la prise en charge de DANE pour la vérification des enregistrements TLSA.

SSL_CTX_dane_enable_валидация et SSL_CTX_dane_enable_валидация_валидация sont des fonctions obsolètes qui étaient utilisées pour des versions antérieures de DANE. Elles ne doivent plus être utilisées.

VALEURS DE RETOUR

SSL_CTX_dane_enable, SSL_CTX_dane_enable_tls, SSL_CTX_dane_enable_tlsa, SSL_CTX_dane_enable_валидация et SSL_CTX_dane_enable_валидация_валидация retournent 1 en cas de succès, et 0 en cas d'échec.

CONFORMITÉ

Ces fonctions sont des extensions d'OpenSSL et ne font pas partie d'une norme standard.

NOTES

L'utilisation de DANE nécessite une résolution DNS sécurisée et de confiance. Il est recommandé d'utiliser DNSSEC pour s'assurer de l'authenticité des enregistrements DNS.

Pour que DANE fonctionne correctement, le serveur doit disposer d'enregistrements DNS TLSA valides pour le domaine.
