NOM

SSL_EXTENSION_SUPPORTED, SSL_custom_ext_add_cb_ex, SSL_custom_ext_free_cb_ex, SSL_custom_ext_parse_cb_ex, SSL_CTX_add_custom_ext, SSL_CTX_add_client_custom_ext, SSL_CTX_add_server_custom_ext, custom_ext_add_cb, custom_ext_free_cb, custom_ext_parse_cb - gestion des extensions TLS personnalisées

typedef int (*SSL_custom_ext_add_cb_ex)(SSL *s, unsigned int ext_type,

DESCRIPTION

SSL_CTX_add_custom_ext() ajoute une extension personnalisée pour un client ou serveur TLS/DTLS pour toutes les versions de protocole supportées avec le type d'extension ext_type et les callbacks add_cb, free_cb et parse_cb (voir la section "CALLBACKS D'EXTENSION" ci-dessous). La valeur context détermine quels messages et dans quelles conditions l'extension sera ajoutée/analysée (voir la section "CONTEXTES D'EXTENSION" ci-dessous).

SSL_CTX_add_client_custom_ext() ajoute une extension personnalisée pour un client TLS/DTLS avec le type d'extension ext_type et les callbacks add_cb, free_cb et parse_cb. Cette fonction est similaire à SSL_CTX_add_custom_ext(), sauf qu'elle ne s'applique qu'aux clients, utilise l'ancien style de callbacks, et définit implicitement la valeur context à :

SSL_EXT_TLS_1_2_AND_BELOW_ONLY | SSL_EXT_CLIENT_HELLO
| SSL_EXT_TLS_1_2_SERVER_HELLO | SSL_EXT_IGNORE_ON_RESUMPTION

SSL_CTX_add_server_custom_ext() ajoute une extension personnalisée pour un serveur TLS/DTLS avec le type d'extension ext_type et les callbacks add_cb, free_cb et parse_cb. Cette fonction est similaire à SSL_CTX_add_custom_ext(), sauf qu'elle ne s'applique qu'aux serveurs, utilise l'ancien style de callbacks, et définit implicitement la valeur context à la même valeur que pour SSL_CTX_add_client_custom_ext() ci-dessus.

Le paramètre ext_type correspond au champ extension_type de RFC5246 et suivants. Ce n'est pas un NID. Dans tous les cas, le type d'extension ne doit pas être géré en interne par OpenSSL, sinon une erreur se produit.

SSL_extension_supported() retourne 1 si l'extension ext_type est gérée en interne par OpenSSL, et 0 sinon.

CALLBACKS D'EXTENSION

Le callback add_cb est appelé pour envoyer des données d'extension personnalisées à inclure dans divers messages TLS. Le paramètre ext_type est défini sur le type d'extension qui sera ajouté et add_arg sur la valeur définie lors de l'ajout du gestionnaire d'extension. Lors de l'utilisation des nouveaux callbacks, le paramètre context indiquera quel message est actuellement construit, par exemple pour le ClientHello, il sera défini sur SSL_EXT_CLIENT_HELLO.

Si l'application souhaite inclure l'extension ext_type, elle doit définir *out sur les données de l'extension, définir *outlen sur la longueur des données de l'extension et retourner 1.

Si le add_cb ne souhaite pas inclure l'extension, il doit retourner 0.

Si add_cb retourne -1, une erreur de handshake fatale se produit en utilisant l'alerte TLS spécifiée dans *al.

Lors de la construction du ClientHello, si add_cb est défini sur NULL, une extension de longueur zéro est ajoutée pour ext_type. Pour tous les autres messages, si add_cb est défini sur NULL, aucune extension n'est ajoutée.

Lors de la construction d'un message Certificate, le callback sera appelé pour chaque certificat du message. Le paramètre x indiquera le certificat courant et le paramètre chainidx indiquera la position du certificat dans le message. Le premier certificat est toujours le certificat de l'entité finale et a une valeur chainidx de 0. Les certificats sont dans l'ordre où ils ont été reçus dans le message Certificate.

Pour tous les messages sauf ServerHello et EncryptedExtensions, tous les add_cb enregistrés sont toujours appelés pour voir si l'application souhaite ajouter une extension (tant que toutes les exigences du context spécifié sont remplies).

Pour les messages ServerHello et EncryptedExtension, tous les add_cb enregistrés sont appelés une fois si et seulement si les exigences du context spécifié sont remplies et l'extension correspondante a été reçue dans le ClientHello. C'est-à-dire, si aucune extension correspondante n'a été reçue dans le ClientHello, alors add_cb ne sera pas appelé.

Si une extension est ajoutée (c'est-à-dire que add_cb retourne 1), free_cb est appelé (s'il est défini) avec la valeur de out définie par le callback d'ajout. Il peut être utilisé pour libérer toute donnée d'extension dynamique définie par add_cb. Comme out est constant (pour permettre l'utilisation de données constantes dans add_cb), les applications peuvent avoir besoin de supprimer la constante pour libérer les données.

Le callback parse_cb reçoit des données pour les extensions TLS. Le callback n'est appelé que si l'extension est présente et pertinente pour le contexte (voir ci-dessous "CONTEXTES D'EXTENSION").

Les données de l'extension consistent en inlen octets dans le buffer in pour l'extension ext_type.

Si le message analysé est un message Certificate compatible TLSv1.3, alors parse_cb sera appelé pour chaque certificat contenu dans le message. Le paramètre x indiquera le certificat courant et le paramètre chainidx indiquera la position du certificat dans le message. Le premier certificat est toujours le certificat de l'entité finale et a une valeur chainidx de 0.

Si le parse_cb considère les données de l'extension comme acceptables, il doit retourner 1. S'il retourne 0 ou une valeur négative, une erreur de handshake fatale se produit en utilisant l'alerte TLS spécifiée dans *al.

Le buffer in est un buffer interne temporaire qui ne sera pas valide après le retour du callback.

CONTEXTES D'EXTENSION

Un contexte d'extension définit quels messages et dans quelles conditions une extension doit être ajoutée ou attendue. Le contexte est construit en effectuant un OU bit à bit de plusieurs valeurs prédéfinies ensemble. Les valeurs de contexte valides sont :

SSL
Cette extension est spécifique à TLS.
SSL_EXT_DTLS_ONLY
Cette extension est spécifique à DTLS.
SSL_EXT_ANY_VERSION
Cette extension peut être utilisée avec n'importe quelle version de TLS.
SSL_EXT_TLS1_0_ONLY
Cette extension est uniquement pour TLS 1.0.
SSL_EXT_TLS1_1_ONLY
Cette extension est uniquement pour TLS 1.1.
SSL_EXT_TLS1_2_ONLY
Cette extension est uniquement pour TLS 1.2.
SSL_EXT_TLS1_3_ONLY
Cette extension est uniquement pour TLS 1.3.
SSL_EXT_TLS1_2_AND_BELOW_ONLY
Cette extension est pour TLS 1.2 et les versions antérieures.
SSL_EXT_CLIENT_HELLO
L'extension est gérée dans le message ClientHello.
SSL_EXT_SERVER_HELLO
L'extension est gérée dans le message ServerHello.
SSL_EXT_ANY_OTHER_HELLO
L'extension est gérée dans n'importe quel autre message Hello (par exemple, NewSessionTicket).
SSL_EXT_SILENT
Si l'extension n'est pas présente, ne pas générer d'erreur.
SSL_EXT_OCSP_RESPONSE
L'extension est associée à la réponse OCSP.
SSL_EXT_SESSION_TICKET
L'extension est associée à un ticket de session.
SSL_EXT_CERTIFICATE_TYPE
L'extension est associée au type de certificat.
SSL_EXT_PRE_CERTIFICATE_HOOK
Appelé avant que les certificats ne soient envoyés. Le certificat est disponible dans le paramètre x.
SSL_EXT_POST_INSTALL_CERT_HOOK
Appelé après l'installation des certificats côté serveur. Le certificat est disponible dans le paramètre x.
SSL_EXT_TLS1_3_CLIENT_HELLO
L'extension est gérée dans le ClientHello TLS 1.3.
SSL_EXT_TLS1_3_ENCRYPTED_EXTENSIONS
L'extension est gérée dans le message EncryptedExtensions TLS 1.3.
SSL_EXT_TLS1_3_CERTIFICATE
L'extension est gérée dans le message Certificate TLS 1.3.
SSL_EXT_TLS1_3_KNOWLEDGE_REQUEST
L'extension est gérée dans le message KeyUpdate TLS 1.3.
SSL_EXT_TLS1_3_HELLO_RETRY_REQUEST
L'extension est gérée dans le message HelloRetryRequest TLS 1.3.
SSL_EXT_IGNORE_ON_RESUMPTION
L'extension doit être ignorée lors de la reprise d'une session.
SSL_EXT_GOAWAY
L'extension doit être ignorée lors de la reprise d'une session.

NOTES

L'utilisation de SSL_CTX_add_client_custom_ext et SSL_CTX_add_server_custom_ext est obsolète. Les applications devraient utiliser SSL_CTX_add_custom_ext à la place.

Les types d'extensions personnalisées peuvent être définis en utilisant des valeurs entières. Il n'y a pas de mécanisme standard pour allouer des types d'extensions personnalisées. Les applications doivent s'assurer que les types d'extensions qu'elles utilisent ne chevauchent pas les types d'extensions standard gérés par OpenSSL ou les types d'extensions utilisés par d'autres parties.

Les extensions gérées par OpenSSL incluent les certificats, les demandes de certificats, les greffons OCSP, SNI, ALPN, le cryptage et d'autres. Utiliser SSL_extension_supported() est un moyen de vérifier si une extension est déjà gérée.

Si une extension personnalisée est ajoutée, le callback add_cb sera appelé pour chaque certificat dans le chaîne de certificats lors de la construction du message Certificate. Le paramètre chainidx indiquera le certificat courant.

Pour les extensions TLS 1.3, SSL_CTX_add_custom_ext est utilisé. Les contextes suivants sont importants pour TLS 1.3 : SSL_EXT_TLS1_3_CLIENT_HELLO, SSL_EXT_TLS1_3_ENCRYPTED_EXTENSIONS, SSL_EXT_TLS1_3_CERTIFICATE, SSL_EXT_TLS1_3_KNOWLEDGE_REQUEST, SSL_EXT_TLS1_3_HELLO_RETRY_REQUEST.

RETOUR

SSL_CTX_add_custom_ext(), SSL_CTX_add_client_custom_ext() et SSL_CTX_add_server_custom_ext() retournent 1 en cas de succès, et 0 en cas d'échec.

SSL_extension_supported() retourne 1 si l'extension est supportée, et 0 sinon.

NAME

SSL_CTX_add_custom_ext, SSL_CTX_add_client_custom_ext, SSL_CTX_add_server_custom_ext, SSL_extension_supported - add custom extensions

SYNOPSIS

#include <openssl/ssl.h>
int SSL_CTX_add_custom_ext(SSL_CTX *ctx, int ext_type, unsigned int flags,
                           ssl_ext_init_cb init_cb,
                           ssl_ext_add_cb add_cb,
                           ssl_ext_free_cb free_cb,
                           ssl_ext_parse_cb parse_cb, void *user_data);
int SSL_CTX_add_client_custom_ext(SSL_CTX *ctx, int ext_type, unsigned int flags,
                                  ssl_ext_add_cb add_cb, void *user_data);
int SSL_CTX_add_server_custom_ext(SSL_CTX *ctx, int ext_type, unsigned int flags,
                                  ssl_ext_add_cb add_cb, void *user_data);
int SSL_extension_supported(int ext_type);

DESCRIPTION

These functions allow an application to define and handle custom extensions. Custom extensions are extensions that are not part of the standard TLS protocol, but are defined by a specific application. The extension type is identified by an integer ext_type.

The functions add a custom extension of type ext_type to the given SSL_CTX.

SSL_CTX_add_custom_ext() is the most general function. It allows defining callbacks for all phases of handling a custom extension: initialization (init_cb), adding the extension to messages (add_cb), freeing any associated data (free_cb), and parsing the extension when received (parse_cb). It also takes a flags argument that specifies when the extension is allowed, and arbitrary user_data that will be passed to the callbacks.

SSL_CTX_add_client_custom_ext() and SSL_CTX_add_server_custom_ext() are convenience functions that set up common flags for client and server extensions respectively. They only allow defining an add_cb callback and user_data. The flags are set to SSL_EXT_CLIENT_HELLO, SSL_EXT_TLS_IMPLEMENTATION_ONLY, and SSL_EXT_IGNORE_ON_RESUMPTION for client extensions, and SSL_EXT_TLS1_2_SERVER_HELLO, SSL_EXT_TLS1_3_SERVER_HELLO, SSL_EXT_TLS1_3_ENCRYPTED_EXTENSIONS, SSL_EXT_TLS1_3_HELLO_RETRY_REQUEST, SSL_EXT_TLS1_3_CERTIFICATE, SSL_EXT_TLS1_3_NEW_SESSION_TICKET, SSL_EXT_TLS1_3_CERTIFICATE_REQUEST, SSL_EXT_DTLS_ONLY, SSL_EXT_TLS_ONLY, SSL_EXT_TLS_IMPLEMENTATION_ONLY, and SSL_EXT_IGNORE_ON_RESUMPTION for server extensions.

SSL_extension_supported() returns 1 if the extension ext_type is handled internally by OpenSSL, and 0 otherwise. This can be used to check if an extension type is reserved or already in use.

The extension type ext_type should be an IANA-assigned extension number, or a value chosen by the application. OpenSSL reserves extension types 0 to 65535 for internal use. Applications should use values greater than 65535 for custom extensions to avoid collisions.

The flags argument specifies under which circumstances the extension is permitted. The allowed flags are:

SSL_EXT_TLS_ONLY
The extension is only allowed in TLS
SSL_EXT_DTLS_ONLY
The extension is only allowed in DTLS
SSL_EXT_TLS_IMPLEMENTATION_ONLY
The extension is allowed in DTLS, but there is only a TLS implementation available (so it is ignored in DTLS).
SSL_EXT_SSL3_ALLOWED
Extensions are not typically defined for SSLv3. Setting this value will allow the extension in SSLv3. Applications will not typically need to use this.
SSL_EXT_TLS1_2_AND_BELOW_ONLY
The extension is only defined for TLSv1.2/DTLSv1.2 and below. Servers will ignore this extension if it is present in the ClientHello and TLSv1.3 is negotiated.
SSL_EXT_TLS1_3_ONLY
The extension is only defined for TLS1.3 and above. Servers will ignore this extension if it is present in the ClientHello and TLSv1.2 or below is negotiated.
SSL_EXT_IGNORE_ON_RESUMPTION
The extension will be ignored during parsing if a previous session is being successfully resumed.
SSL_EXT_CLIENT_HELLO
The extension may be present in the ClientHello message.
SSL_EXT_TLS1_2_SERVER_HELLO
The extension may be present in a TLSv1.2 or below compatible ServerHello message.
SSL_EXT_TLS1_3_SERVER_HELLO
The extension may be present in a TLSv1.3 compatible ServerHello message.
SSL_EXT_TLS1_3_ENCRYPTED_EXTENSIONS
The extension may be present in an EncryptedExtensions message.
SSL_EXT_TLS1_3_HELLO_RETRY_REQUEST
The extension may be present in a HelloRetryRequest message.
SSL_EXT_TLS1_3_CERTIFICATE
The extension may be present in a TLSv1.3 compatible Certificate message.
SSL_EXT_TLS1_3_NEW_SESSION_TICKET
The extension may be present in a TLSv1.3 compatible NewSessionTicket message.
SSL_EXT_TLS1_3_CERTIFICATE_REQUEST
The extension may be present in a TLSv1.3 compatible CertificateRequest message.

The context must include at least one message value (otherwise the extension will never be used).

NOTES

The add_arg and parse_arg parameters can be set to arbitrary values which will be passed to the corresponding callbacks. They can, for example, be used to store the extension data received in a convenient structure or pass the extension data to be added or freed when adding extensions.

If the same custom extension type is received multiple times a fatal decode_error alert is sent and the handshake aborts. If a custom extension is received in a ServerHello/EncryptedExtensions message which was not sent in the ClientHello a fatal unsupported_extension alert is sent and the handshake is aborted. The ServerHello/EncryptedExtensions add_cb callback is only called if the corresponding extension was received in the ClientHello. This is compliant with the TLS specifications. This behaviour ensures that each callback is called at most once and that an application can never send unsolicited extensions.

RETURN VALUES

SSL_CTX_add_custom_ext(), SSL_CTX_add_client_custom_ext() and SSL_CTX_add_server_custom_ext() return 1 for success and 0 for failure. A failure can occur if an attempt is made to add the same ext_type more than once, if an attempt is made to use an extension type handled internally by OpenSSL or if an internal error occurs (for example a memory allocation failure).

SSL_extension_supported() returns 1 if the extension ext_type is handled internally by OpenSSL and 0 otherwise.
