NAME

SSL_set_max_early_data, SSL_CTX_set_max_early_data, SSL_get_max_early_data, SSL_CTX_get_max_early_data, SSL_set_recv_max_early_data, SSL_CTX_set_recv_max_early_data, SSL_get_recv_max_early_data, SSL_CTX_get_recv_max_early_data, SSL_SESSION_get_max_early_data, SSL_SESSION_set_max_early_data, SSL_write_early_data, SSL_read_early_data, SSL_get_early_data_status, SSL_allow_early_data_cb_fn, SSL_CTX_set_allow_early_data_cb, SSL_set_allow_early_data_cb - fonctions pour envoyer et recevoir des données précoces

DESCRIPTION

Ces fonctions sont utilisées pour envoyer et recevoir des données précoces lorsque TLSv1.3 a été négocié. Les données précoces peuvent être envoyées par le client immédiatement après son ClientHello initial sans avoir à attendre que le serveur achève la négociation. Les données précoces peuvent être envoyées si une session a préalablement été établie avec le serveur ou lors de l'établissement d'une nouvelle session à l'aide d'un PSK hors bande, et uniquement lorsque le serveur est connu pour les prendre en charge. De plus, ces fonctions peuvent être utilisées pour envoyer des données du serveur au client lorsque le client n'a pas encore terminé l'étape d'authentification de la négociation.

Les données précoces ont des propriétés de sécurité plus faibles que les autres données envoyées sur une connexion SSL/TLS. En particulier, les données n'ont pas de confidentialité persistante (forward secrecy). Il existe également des considérations supplémentaires concernant les attaques par rejeu (voir "PROTECTION CONTRE LES REJEUX" ci-dessous). Pour ces raisons, il convient d'exercer une extrême prudence lors de l'utilisation des données précoces. Pour plus de détails, consultez la spécification TLS 1.3.

Lorsqu'un serveur reçoit des données précoces, il peut choisir de répondre immédiatement en envoyant des données d'application au client. Les données envoyées par le serveur à ce stade le sont avant que la négociation complète ne soit terminée. Plus précisément, les messages d'authentification du client n'ont pas encore été reçus, c'est-à-dire que le client n'est pas authentifié à ce stade et il faut être prudent lors de l'utilisation de cette capacité.

Un serveur ou un client peut déterminer si la négociation complète est terminée ou non en appelant SSL_is_init_finished(3).

Du côté client, la fonction SSL_SESSION_get_max_early_data() peut être utilisée pour déterminer si une session établie avec un serveur peut être utilisée pour envoyer des données précoces. Si la session ne peut pas être utilisée, cette fonction retournera 0. Sinon, elle retournera le nombre maximum d'octets de données précoces qui peuvent être envoyés.

La fonction SSL_SESSION_set_max_early_data() définit le nombre maximum d'octets de données précoces qui peuvent être envoyés pour une session. Ceci serait typiquement utilisé lors de la création d'un fichier de session PSK (voir SSL_CTX_set_psk_use_session_callback(3)). Si vous utilisez un PSK basé sur un ticket, celui-ci est défini automatiquement sur la valeur fournie par le serveur.

Un client utilise la fonction SSL_write_early_data() pour envoyer des données précoces. Cette fonction est similaire à la fonction SSL_write_ex(3), mais avec les différences suivantes. Voir SSL_write_ex(3) pour des informations sur la manière d'écrire des octets dans la connexion sous-jacente, et sur la manière de gérer les erreurs qui pourraient survenir. Cette page décrit les différences entre SSL_write_early_data() et SSL_write_ex(3).

Lorsqu'elle est appelée par un client, SSL_write_early_data() doit être la première fonction d'E/S appelée sur une nouvelle connexion, c'est-à-dire qu'elle doit se produire avant tout appel à SSL_write_ex(3), SSL_read_ex(3), SSL_connect(3), SSL_do_handshake(3) ou d'autres fonctions similaires. Elle peut être appelée plusieurs fois pour diffuser des données au serveur, mais le nombre total d'octets écrits ne doit pas dépasser la valeur renvoyée par SSL_SESSION_get_max_early_data(). Une fois le premier appel à SSL_write_early_data() terminé avec succès, le client peut intercaler des appels à SSL_read_ex(3) et SSL_read(3) avec des appels à SSL_write_early_data() selon les besoins.

Si SSL_write_early_data() échoue, vous devez appeler SSL_get_error(3) pour déterminer la marche à suivre correcte, comme pour SSL_write_ex(3).

Lorsque le client ne souhaite plus envoyer de données précoces, il doit terminer la négociation en appelant une fonction telle que SSL_connect(3) ou SSL_do_handshake(3). Vous pouvez également appeler une fonction d'écriture standard telle que SSL_write_ex(3), qui complétera de manière transparente la connexion et écrira les données demandées.

Un serveur peut choisir d'ignorer les données précoces qui lui ont été envoyées. Une fois la connexion terminée, vous pouvez déterminer si le serveur a accepté ou rejeté les données précoces en appelant SSL_get_early_data_status(). Cette fonction renverra SSL_EARLY_DATA_ACCEPTED si les données ont été acceptées, SSL_EARLY_DATA_REJECTED si elles ont été rejetées ou SSL_EARLY_DATA_NOT_SENT si aucune donnée précoce n'a été envoyée. Cette fonction peut être appelée par le client ou le serveur.

Un serveur utilise la fonction SSL_read_early_data() pour recevoir des données précoces sur une connexion pour laquelle les données précoces ont été activées à l'aide de SSL_CTX_set_max_early_data() ou SSL_set_max_early_data(). Comme pour SSL_write_early_data(), cela doit être la première fonction d'E/S appelée sur une connexion, c'est-à-dire qu'elle doit se produire avant tout appel à SSL_write_ex(3), SSL_read_ex(3), SSL_accept(3), SSL_do_handshake(3), ou d'autres fonctions similaires.

SSL_read_early_data() est similaire à SSL_read_ex(3) avec les différences suivantes. Reportez-vous à SSL_read_ex(3) pour les détails complets.

SSL_read_early_data() peut renvoyer 3 valeurs possibles :

SSL_READ_EARLY_DATA_ERROR
Ceci indique qu'une erreur d'E/S ou une autre erreur s'est produite. Ceci doit être traité de la même manière qu'une valeur de retour 0 de SSL_read_ex(3).
SSL_READ_EARLY_DATA_SUCCESS
Ceci indique que des données précoces ont été lues avec succès. Ceci doit être traité de la même manière qu'une valeur de retour 1 de SSL_read_ex(3). Vous devriez continuer à appeler SSL_read_early_data() pour lire plus de données.
SSL_READ_EARLY_DATA_FINISH
Ceci indique qu'aucune donnée précoce supplémentaire ne peut être lue. Cela peut être renvoyé lors du premier appel à SSL_read_early_data() si le client n'a envoyé aucune donnée précoce, ou si les données précoces ont été rejetées.

Une fois le premier appel à SSL_read_early_data() terminé avec succès (c'est-à-dire qu'il a renvoyé SSL_READ_EARLY_DATA_SUCCESS ou SSL_READ_EARLY_DATA_FINISH), le serveur peut choisir d'écrire des données immédiatement au client non authentifié en utilisant SSL_write_early_data(). Si SSL_read_early_data() a renvoyé SSL_READ_EARLY_DATA_FINISH, alors dans certains cas (par exemple, si le client ne prend en charge que TLSv1.2) la négociation peut déjà être terminée et les appels à SSL_write_early_data() ne sont pas autorisés. Appelez SSL_is_init_finished(3) pour vérifier.

Les serveurs ne doivent pas appeler SSL_read_ex(3), SSL_read(3), SSL_write_ex(3) ou SSL_write(3) tant que SSL_read_early_data() n'a pas retourné SSL_READ_EARLY_DATA_FINISH. Une fois cela fait, la connexion avec le client doit toujours être terminée. Terminez la connexion en appelant une fonction telle que SSL_accept(3) ou SSL_do_handshake(3). Alternativement, vous pouvez appeler une fonction de lecture standard telle que SSL_read_ex(3), qui terminera transparentement la connexion et lira les données demandées. Notez qu'il est erroné de tenter de terminer la connexion avant que SSL_read_early_data() n'ait retourné SSL_READ_EARLY_DATA_FINISH.

Seuls les serveurs peuvent appeler SSL_read_early_data().

Les appels à SSL_read_early_data() peuvent, dans certaines circonstances, terminer la connexion immédiatement sans qu'il soit nécessaire d'appeler une fonction telle que SSL_accept(3). Cela peut se produire si le client utilise une version de protocole inférieure à TLSv1.3. Les applications peuvent vérifier cela en appelant SSL_is_init_finished(3). Alternativement, les applications peuvent choisir d'appeler SSL_accept(3) de toute façon. Un tel appel réussira immédiatement sans aucune action supplémentaire.

Lorsqu'une session est créée entre un serveur et un client, le serveur spécifie la quantité maximale de données anticipées qu'il acceptera lors de toutes les futures tentatives de connexion. Par défaut, le serveur n'accepte pas de données anticipées ; un serveur peut indiquer son support pour les données anticipées en appelant SSL_CTX_set_max_early_data() ou SSL_set_max_early_data() pour définir cela pour l'ensemble du SSL_CTX ou un objet SSL individuel respectivement. Le paramètre max_early_data spécifie la quantité maximale de données anticipées, en octets, autorisée à être envoyée sur une seule connexion. De même, les fonctions SSL_CTX_get_max_early_data() et SSL_get_max_early_data() peuvent être utilisées pour obtenir les paramètres actuels de données anticipées maximales pour les objets SSL_CTX et SSL respectivement. Généralement, une application serveur utilisera à la fois SSL_read_early_data() et SSL_CTX_set_max_early_data() (ou SSL_set_max_early_data()), ou aucun des deux, car il n'y a aucun avantage pratique à n'en utiliser qu'un. Si le paramètre de données anticipées maximales pour un serveur est différent de zéro, la protection contre la relecture est automatiquement activée (voir "PROTECTION CONTRE LA RELECTURE" ci-dessous).

Si le serveur rejette les données anticipées envoyées par un client, il ignorera les données envoyées. La quantité maximale de données anticipées reçues qui sont ignorées est contrôlée par le paramètre recv_max_early_data. Si un client envoie plus que cela, la connexion sera interrompue. Cette valeur peut être définie en appelant SSL_CTX_set_recv_max_early_data() ou SSL_set_recv_max_early_data(). La valeur actuelle pour ce paramètre peut être obtenue en appelant SSL_CTX_get_recv_max_early_data() ou SSL_get_recv_max_early_data(). La valeur par défaut pour ce paramètre est de 16 384 octets.

La valeur recv_max_early_data a également un impact sur les données anticipées qui sont acceptées. La quantité de données acceptées sera toujours la plus faible entre le max_early_data pour la session et le paramètre recv_max_early_data pour le serveur. Si un client envoie plus de données que cela, la connexion sera interrompue.

La valeur configurée pour max_early_data sur un serveur peut changer au fil du temps selon les besoins. Cependant, les clients peuvent avoir des tickets contenant la valeur max_early_data précédemment configurée. recv_max_early_data doit toujours être égal ou supérieur à toute valeur max_early_data récemment configurée afin d'éviter les connexions interrompues. recv_max_early_data ne doit jamais être inférieur à la valeur max_early_data actuellement configurée.

Certaines applications serveur peuvent souhaiter avoir plus de contrôle sur l'acceptation ou le rejet des données anticipées, par exemple pour atténuer les risques de relecture (voir "PROTECTION CONTRE LA RELECTURE" ci-dessous) ou pour refuser les données anticipées lorsque le serveur est très chargé. Les fonctions SSL_CTX_set_allow_early_data_cb() et SSL_set_allow_early_data_cb() définissent un rappel qui est appelé à un moment de la négociation, juste avant qu'une décision ne soit prise pour accepter ou rejeter les données anticipées. Le rappel reçoit un pointeur vers l'argument de données utilisateur qui a été fourni lors de la première définition du rappel. Retourner 1 à partir du rappel autorisera les données anticipées et retourner 0 les rejettera. Notez que la bibliothèque OpenSSL peut rejeter les données anticipées pour d'autres raisons, auquel cas ce rappel ne sera pas appelé. Notamment, la fonctionnalité intégrée de protection contre la relecture sera toujours utilisée même si un rappel est présent, à moins qu'elle n'ait été explicitement désactivée en utilisant l'option SSL_OP_NO_ANTI_REPLAY. Voir "PROTECTION CONTRE LA RELECTURE" ci-dessous.

Ces fonctions ne peuvent pas être utilisées actuellement avec les objets SSL QUIC. SSL_set_max_early_data(), SSL_set_recv_max_early_data(), SSL_write_early_data(), SSL_read_early_data(), SSL_get_early_data_status() et SSL_set_allow_early_data_cb() échouent si elles sont appelées sur un objet SSL QUIC.

NOTES

Le but principal des données anticipées est de permettre à un client de commencer à envoyer des données au serveur avant qu'un aller-retour complet de trafic réseau ne se soit produit. Les développeurs d'applications doivent s'assurer qu'ils prennent en compte l'optimisation du socket TCP sous-jacent pour obtenir une solution performante. Par exemple, l'algorithme de Nagle est couramment utilisé par les systèmes d'exploitation pour éviter de nombreux petits paquets TCP. Dans de nombreux scénarios, cela est bénéfique pour les performances, mais cela ne fonctionne pas bien avec la solution de données anticipées telle qu'implémentée dans OpenSSL. Dans l'algorithme de Nagle, le système d'exploitation met en tampon les données TCP sortantes si un paquet TCP a déjà été envoyé pour lequel nous n'avons pas encore reçu d'accusé de réception (ACK) du pair. Les données mises en tampon ne seront transmises que si suffisamment de données pour remplir un paquet TCP entier sont accumulées, ou si l'ACK est reçu du pair. Le ClientHello initial sera envoyé dans le premier paquet TCP, ainsi que toutes les données du premier appel à SSL_write_early_data(). Si la quantité de données écrites dépasse la taille d'un seul paquet TCP, ou s'il y a d'autres appels à SSL_write_early_data(), ces données supplémentaires seront envoyées dans des paquets TCP ultérieurs qui seront mis en tampon par le système d'exploitation et ne seront pas envoyés tant qu'un ACK n'est pas reçu pour le premier paquet contenant le ClientHello. Cela signifie que les données anticipées ne sont effectivement envoyées qu'une fois qu'un aller-retour complet avec le serveur s'est produit, ce qui va à l'encontre de l'objectif des données anticipées.

Dans de nombreux systèmes d'exploitation, l'option de socket TCP_NODELAY est disponible pour désactiver l'algorithme de Nagle. Si une application choisit de désactiver l'algorithme de Nagle, il convient d'envisager de le réactiver après la fin de la négociation, le cas échéant.

Dans de rares circonstances, il peut être possible qu'un client ait une session qui signale une valeur max early data supérieure à 0, mais où le serveur ne la supporte pas. Par exemple, cela peut se produire si la configuration d'un serveur a été modifiée pour accepter une valeur max early data inférieure, par exemple en appelant SSL_CTX_set_recv_max_early_data(). Un autre exemple est si un serveur utilisait TLSv1.3 mais a été rétrogradé à TLSv1.2. L'envoi de données anticipées à un tel serveur entraînera l'interruption de la connexion. Les clients qui rencontrent une connexion interrompue lors de l'envoi de données anticipées peuvent vouloir réessayer la connexion sans envoyer de données anticipées, car cela ne se produit pas automatiquement. Un client devra établir une nouvelle connexion de couche de transport avec le serveur et tenter à nouveau la connexion SSL/TLS, mais sans envoyer de données anticipées. Notez qu'il est déconseillé de réessayer avec une version de protocole maximale inférieure.

PROTECTION CONTRE LA RELECTURE

Lorsque des données anticipées sont utilisées, le protocole TLS ne fournit aucune garantie de sécurité que les mêmes données anticipées n'ont pas été relues sur plusieurs connexions. En guise de mitigation pour ce problème, OpenSSL active automatiquement la protection contre la relecture si le serveur est configuré avec une valeur de données anticipées maximale non nulle. Avec la protection contre la relecture activée, les sessions sont forcées d'être à usage unique uniquement. Si un client tente de réutiliser un ticket de session plus d'une fois, les deuxième et les tentatives suivantes se replieront sur une négociation complète (et toutes les données anticipées qui ont été soumises seront ignorées). Notez que les tickets à usage unique sont appliqués même si un client n'envoie aucune donnée anticipée.

Le mécanisme de protection contre la relecture repose sur le cache de sessions interne d'OpenSSL (voir SSL_CTX_set_session_cache_mode(3)). Lorsque la protection contre la relecture est utilisée, le serveur fonctionnera comme si l'option SSL_OP_NO_TICKET avait été sélectionnée (voir SSL_CTX_set_options(3)). Les sessions seront ajoutées au cache chaque fois qu'un ticket de session est émis. Lorsqu'un client tente de reprendre la session, OpenSSL vérifiera sa présence dans le cache interne. S'il existe, la reprise est autorisée et la session est supprimée du cache. S'il n'existe pas, la reprise n'est pas autorisée et une négociation complète aura lieu.

Notez que certaines applications peuvent maintenir un cache externe de sessions (voir SSL_CTX_sess_set_new_cb(3) et fonctions similaires). Il incombe à l'application de s'assurer que toutes les sessions du cache externe sont également remplies dans le cache interne et qu'une fois supprimées du cache interne, elles sont également supprimées du cache externe. Ne pas le faire pourrait rendre une application vulnérable aux attaques par relecture. Notez qu'OpenSSL verrouillera le cache interne pendant qu'une session est supprimée, mais ce verrou n'est pas maintenu lorsque le rappel de suppression de session (voir SSL_CTX_sess_set_remove_cb(3)) est appelé. Cela pourrait entraîner une courte période pendant laquelle la session a été supprimée du cache interne mais est toujours disponible dans le cache externe. Les applications doivent être conçues en tenant compte de cela afin de minimiser la possibilité d'attaques par relecture.

La protection contre la relecture d'OpenSSL ne s'applique pas aux clés pré-partagées externes (PSK) (par exemple, voir SSL_CTX_set_psk_find_session_callback(3)). Par conséquent, une extrême prudence doit être appliquée lors de la combinaison de PSK externes avec des données anticipées.

Certaines applications peuvent atténuer les risques de relecture par d'autres moyens. Pour ces applications, il est possible de désactiver la fonctionnalité intégrée de protection contre la relecture en utilisant l'option SSL_OP_NO_ANTI_REPLAY. Voir SSL_CTX_set_o

OPTIONS

Les options pour la gestion des données anticipées peuvent être configurées via SSL_CTX_set_options(3). Consultez SSL_CTX_set_options(3) pour plus de détails. Les applications peuvent également définir un rappel pour prendre des décisions concernant l'acceptation ou non des données anticipées. Consultez SSL_CTX_set_allow_early_data_cb() ci-dessus pour plus de détails.

VALEURS DE RETOUR

SSL_write_early_data() retourne 1 en cas de succès ou 0 en cas d'échec. En cas d'échec, appelez SSL_get_error(3) pour déterminer la marche à suivre correcte.

SSL_read_early_data() retourne SSL_READ_EARLY_DATA_ERROR en cas d'échec, SSL_READ_EARLY_DATA_SUCCESS en cas de succès avec des données supplémentaires à lire, et SSL_READ_EARLY_DATA_FINISH en cas de succès sans plus de données à lire. En cas d'échec, appelez SSL_get_error(3) pour déterminer la marche à suivre correcte.

SSL_get_max_early_data(), SSL_CTX_get_max_early_data() et SSL_SESSION_get_max_early_data() retournent le nombre maximum d'octets de données anticipées pouvant être envoyés.

SSL_set_max_early_data(), SSL_CTX_set_max_early_data() et SSL_SESSION_set_max_early_data() retournent 1 en cas de succès ou 0 en cas d'échec.

SSL_get_early_data_status() retourne SSL_EARLY_DATA_ACCEPTED si les données anticipées ont été acceptées par le serveur, SSL_EARLY_DATA_REJECTED si les données anticipées ont été rejetées par le serveur, ou SSL_EARLY_DATA_NOT_SENT si aucune donnée anticipée n'a été envoyée.
