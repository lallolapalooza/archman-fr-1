SSL_CTX_set_verify(3ssl)

SSL_CTX_SET_VERIFY(3ssl) OpenSSL SSL_CTX_SET_VERIFY(3ssl)

NOM

SSL_get_ex_data_X509_STORE_CTX_idx, SSL_CTX_set_verify, SSL_set_verify, SSL_CTX_set_verify_depth, SSL_set_verify_depth, SSL_verify_cb, SSL_verify_client_post_handshake, SSL_set_post_handshake_auth, SSL_CTX_set_post_handshake_auth - définir divers paramètres SSL/TLS pour la vérification des certificats homologues

SYNOPIS

#include <openssl/ssl.h>
typedef int (*SSL_verify_cb)(int preverify_ok, X509_STORE_CTX *x509_ctx);
void SSL_CTX_set_verify(SSL_CTX *ctx, int mode, SSL_verify_cb verify_callback);
void SSL_set_verify(SSL *ssl, int mode, SSL_verify_cb verify_callback);
SSL_get_ex_data_X509_STORE_CTX_idx(void);
void SSL_CTX_set_verify_depth(SSL_CTX *ctx, int depth);
void SSL_set_verify_depth(SSL *ssl, int depth);
int SSL_verify_client_post_handshake(SSL *ssl);
void SSL_CTX_set_post_handshake_auth(SSL_CTX *ctx, int val);
void SSL_set_post_handshake_auth(SSL *ssl, int val);

DESCRIPTION

SSL_CTX_set_verify() définit les indicateurs de vérification pour ctx à mode et spécifie la fonction verify_callback à utiliser. Si aucune fonction de rappel ne doit être spécifiée, le pointeur NULL peut être utilisé pour verify_callback. ctx NE DOIT PAS être NULL.

SSL_set_verify() définit les indicateurs de vérification pour ssl à mode et spécifie la fonction verify_callback à utiliser. Si aucune fonction de rappel ne doit être spécifiée, le pointeur NULL peut être utilisé pour verify_callback. Dans ce cas, le dernier verify_callback défini spécifiquement pour cet ssl reste. Si aucun callback spécial n'a été défini auparavant, le callback par défaut pour le ctx sous-jacent est utilisé, celui qui était valide au moment où ssl a été créé avec SSL_new(3). Dans la fonction de rappel, SSL_get_ex_data_X509_STORE_CTX_idx peut être appelée pour obtenir l'index des données de l'objet SSL actuel qui effectue la vérification.

En mode client, verify_callback peut également appeler la fonction SSL_set_retry_verify(3) sur l'objet SSL défini dans les données ex de x509_store_ctx (voir SSL_get_ex_data_X509_STORE_CTX_idx(3)) et retourner 1. Ceci serait typiquement fait dans le cas où la vérification du certificat n'a pas encore pu réussir. Cela suspend la négociation et rend le contrôle à l'application appelante avec SSL_ERROR_WANT_RETRY_VERIFY. L'application peut par exemple récupérer des certificats supplémentaires ou des informations de statut de certificat nécessaires à la vérification. L'appel de SSL_connect(3) à nouveau reprend la tentative de connexion en réessayant l'étape de vérification du certificat serveur. Ce processus peut même être répété si nécessaire. Notez que la négociation peut toujours être abandonnée si une invocation ultérieure du callback (par exemple, à une profondeur inférieure, ou pour une condition d'erreur distincte) retourne 0.

SSL_CTX_set_verify_depth() définit la profondeur maximale pour la vérification de la chaîne de certificats qui sera autorisée pour ctx.

SSL_set_verify_depth() définit la profondeur maximale pour la vérification de la chaîne de certificats qui sera autorisée pour ssl.

SSL_CTX_set_post_handshake_auth() et SSL_set_post_handshake_auth() activent l'extension d'authentification post-négociation pour être ajoutée au ClientHello afin que l'authentification post-négociation puisse être demandée par le serveur. Si val est 0, l'extension n'est pas envoyée, sinon elle l'est. Par défaut, l'extension n'est pas envoyée. Un rappel de certificat devra être défini via SSL_CTX_set_client_cert_cb() si aucun certificat n'est fourni lors de l'initialisation.

SSL_verify_client_post_handshake() provoque l'envoi d'un message CertificateRequest par un serveur sur la connexion ssl donnée. Le drapeau SSL_VERIFY_PEER doit être défini ; le drapeau SSL_VERIFY_POST_HANDSHAKE est facultatif.

NOTES

La vérification des certificats peut être contrôlée par un ensemble d'indicateurs mode logiquement combinés par OR :

SSL_VERIFY_NONE
Mode serveur : le serveur n'enverra pas de demande de certificat client au client, donc le client n'enverra pas de certificat.

Mode client : si aucun chiffrement anonyme n'est utilisé (désactivé par défaut), le serveur enverra un certificat qui sera vérifié. Le résultat du processus de vérification du certificat peut être vérifié après la négociation TLS/SSL en utilisant la fonction SSL_get_verify_result(3). La négociation continuera indépendamment du résultat de la vérification.

SSL_VERIFY_PEER
Mode serveur : le serveur envoie une demande de certificat client au client. Le certificat retourné (le cas échéant) est vérifié. Si le processus de vérification échoue, la négociation TLS/SSL est immédiatement terminée par un message d'alerte contenant la raison de l'échec de la vérification. Le comportement peut être contrôlé par les indicateurs supplémentaires SSL_VERIFY_FAIL_IF_NO_PEER_CERT, SSL_VERIFY_CLIENT_ONCE et SSL_VERIFY_POST_HANDSHAKE.

Mode client : le certificat serveur est vérifié. Si le processus de vérification échoue, la négociation TLS/SSL est immédiatement terminée par un message d'alerte contenant la raison de l'échec de la vérification. Si aucun certificat serveur n'est envoyé, car un chiffrement anonyme est utilisé, SSL_VERIFY_PEER est ignoré.

SSL_VERIFY_FAIL_IF_NO_PEER_CERT
Mode serveur : si le client n'a pas retourné de certificat, la négociation TLS/SSL est immédiatement terminée par une alerte de « échec de négociation ». Cet indicateur doit être utilisé avec SSL_VERIFY_PEER.

Mode client : ignoré (voir BUGS)

SSL_VERIFY_CLIENT_ONCE
Mode serveur : ne demande un certificat client qu'une seule fois pendant la connexion. Ne demande pas à nouveau un certificat client pendant la renégociation ou l'authentification post-négociation si un certificat a été demandé pendant la négociation initiale. Cet indicateur doit être utilisé avec SSL_VERIFY_PEER.

Mode client : ignoré (voir BUGS)

SSL_VERIFY_POST_HANDSHAKE
Mode serveur : le serveur n'enverra pas de demande de certificat client pendant la négociation initiale, mais enverra la demande via SSL_verify_client_post_handshake(). Cela permet à SSL_CTX ou SSL d'être configuré pour la vérification des homologues post-négociation avant que la négociation ne se produise. Cet indicateur doit être utilisé avec SSL_VERIFY_PEER. TLSv1.3 uniquement ; aucun effet sur les connexions pré-TLSv1.3.

Mode client : ignoré (voir BUGS)

Si le mode est SSL_VERIFY_NONE, aucun des autres indicateurs ne peut être défini.

Si les indicateurs de vérification ne sont pas modifiés explicitement par SSL_CTX_set_verify() ou SSL_set_verify(), la valeur par défaut sera SSL_VERIFY_NONE.

La procédure de vérification réelle est effectuée soit à l'aide de la procédure de vérification intégrée, soit à l'aide d'une autre fonction de vérification fournie par l'application et définie avec SSL_CTX_set_cert_verify_callback(3). Les descriptions suivantes s'appliquent dans le cas de la procédure intégrée. Une procédure fournie par l'application a également accès aux informations de profondeur de vérification et à la fonction verify_callback(), mais la manière dont ces informations sont utilisées peut différer.

SSL_CTX_set_verify_depth() et SSL_set_verify_depth() définissent une limite sur le nombre de certificats entre le certificat de l'entité finale et les certificats d'ancrage de confiance. Ni le certificat de l'entité finale, ni le certificat d'ancrage de confiance ne comptent dans la profondeur. Si la chaîne de certificats nécessaire pour atteindre un émetteur de confiance est plus longue que profondeur+2, X509_V_ERR_CERT_CHAIN_TOO_LONG sera émis. Le compte de profondeur est « niveau 0 : certificat homologue », « niveau 1 : certificat CA », « niveau 2 : certificat CA de niveau supérieur », et ainsi de suite. Définir la profondeur maximale à 2 autorise les niveaux 0, 1, 2 et 3 (0 étant l'entité finale et 3 l'ancrage de confiance). La limite de profondeur par défaut est de 100, permettant le certificat homologue, au plus 100 certificats CA intermédiaires et un certificat d'ancrage de confiance final.

La fonction verify_callback est utilisée pour contrôler le comportement lorsque l'indicateur SSL_VERIFY_PEER est défini. Elle doit être fournie par l'application et reçoit deux arguments : preverify_ok

indique, que la vérification du certificat en question a été réussie (preverify_ok=1) ou non (preverify_ok=0). x509_ctx est un pointeur vers le contexte complet utilisé pour la vérification de la chaîne de certificats.

La chaîne de certificats est vérifiée en commençant par le niveau d'imbrication le plus profond (le certificat de l'autorité de certification racine) et en remontant vers le certificat du pair. À chaque niveau, les signatures et les attributs de l'émetteur sont vérifiés. Chaque fois qu'une erreur de vérification est trouvée, le numéro d'erreur est stocké dans x509_ctx et verify_callback est appelé avec preverify_ok=0. En appliquant les fonctions X509_CTX_store_* , verify_callback peut localiser le certificat en question et effectuer des étapes supplémentaires (voir EXEMPLES). Si aucune erreur n'est trouvée pour un certificat, verify_callback est appelé avec preverify_ok=1 avant de passer au niveau suivant.

La valeur de retour de verify_callback contrôle la stratégie du processus de vérification ultérieur. Si verify_callback renvoie 0, le processus de vérification est immédiatement arrêté avec l'état « échec de la vérification ». Si SSL_VERIFY_PEER est défini, une alerte d'échec de vérification est envoyée au pair et la négociation TLS/SSL est terminée. Si verify_callback renvoie 1, le processus de vérification est poursuivi. Si verify_callback renvoie toujours 1, la négociation TLS/SSL ne sera pas terminée en ce qui concerne les échecs de vérification et la connexion sera établie. Le processus appelant peut cependant récupérer le code d'erreur de la dernière erreur de vérification en utilisant SSL_get_verify_result(3) ou en maintenant son propre stockage d'erreurs géré par verify_callback.

Si aucun verify_callback n'est spécifié, le callback par défaut sera utilisé. Sa valeur de retour est identique à preverify_ok, de sorte que tout échec de vérification entraînera la fin de la négociation TLS/SSL avec un message d'alerte, si SSL_VERIFY_PEER est défini.

Après avoir appelé SSL_set_post_handshake_auth(), le client devra ajouter un certificat ou un callback de certificat à sa configuration avant de pouvoir s'authentifier avec succès. Ceci doit être appelé avant SSL_connect().

SSL_verify_client_post_handshake() exige que les drapeaux de vérification aient été précédemment définis, et qu'un client ait envoyé l'extension d'authentification post-négociation. Lorsque le client renvoie un certificat, le callback de vérification sera appelé. Une opération d'écriture doit avoir lieu pour que la demande de certificat soit envoyée au client, cela peut être fait avec SSL_do_handshake() ou SSL_write_ex(). Une seule demande de certificat peut être en attente à la fois.

Lorsque l'authentification post-négociation a lieu, un message NewSessionTicket actualisé est envoyé au client.

L'authentification post-négociation ne peut pas être utilisée avec QUIC. SSL_set_post_handshake_auth() n'a aucun effet si elle est appelée sur un objet SSL QUIC.

BOGUES

En mode client, il n'est pas vérifié si l'indicateur SSL_VERIFY_PEER est défini, mais si des indicateurs autres que SSL_VERIFY_NONE sont définis. Cela peut entraîner un comportement inattendu si SSL_VERIFY_PEER et d'autres indicateurs ne sont pas utilisés comme requis.

VALEURS DE RETOUR

Les fonctions SSL*_set_verify*() ne fournissent pas d'informations de diagnostic.

La fonction SSL_verify_client_post_handshake() renvoie 1 si la demande a réussi, et 0 si la demande a échoué. La pile d'erreurs peut être examinée pour déterminer la raison de l'échec.

EXEMPLES

La séquence de code suivante réalise une fonction verify_callback exemple qui poursuivra toujours la négociation TLS/SSL quelle que soit l'échec de la vérification, si souhaité. Le callback réalise une limite de profondeur de vérification avec des sorties plus informatives.

Toutes les erreurs de vérification sont imprimées ; des informations sur la chaîne de certificats sont imprimées sur demande. L'exemple est réalisé pour un serveur qui autorise mais n'exige pas les certificats clients.

L'exemple utilise la technique ex_data pour stocker des données d'application dans/récupérer des données d'application de la structure SSL (voir CRYPTO_get_ex_new_index(3), SSL_get_ex_data_X509_STORE_CTX_idx(3)).

...
typedef struct {
  int verbose_mode;
  int verify_depth;
  int always_continue;
} mydata_t;
int mydata_index;
...
static int verify_callback(int preverify_ok, X509_STORE_CTX *ctx)
{
    char    buf[256];
    X509   *err_cert;
    int     err, depth;
    SSL    *ssl;
    mydata_t *mydata;
    err_cert = X509_STORE_CTX_get_current_cert(ctx);
    err = X509_STORE_CTX_get_error(ctx);
    depth = X509_STORE_CTX_get_error_depth(ctx);
    /*
     * Récupérer le pointeur vers le SSL de la connexion actuellement traitée
     * et les données spécifiques à l'application stockées dans l'objet SSL.
     */
    ssl = X509_STORE_CTX_get_ex_data(ctx, SSL_get_ex_data_X509_STORE_CTX_idx());
    mydata = SSL_get_ex_data(ssl, mydata_index);
    X509_NAME_oneline(X509_get_subject_name(err_cert), buf, 256);
    /*
     * Capturer une chaîne de certificats trop longue. La limite de profondeur définie à l'aide de
     * SSL_CTX_set_verify_depth() est intentionnellement définie à « limite+1 » de sorte que
     * chaque fois que la condition « depth>verify_depth » est remplie, nous
     * avons violé la limite et voulons enregistrer cette condition d'erreur.
     * Nous devons le faire ici, car l'erreur CHAIN_TOO_LONG ne serait pas
     * trouvée explicitement ; seules les erreurs introduites par la coupure des
     * certificats supplémentaires seraient enregistrées.
     */
    if (depth > mydata->verify_depth) {
        preverify_ok = 0;
        err = X509_V_ERR_CERT_CHAIN_TOO_LONG;
        X509_STORE_CTX_set_error(ctx, err);
    }
    if (!preverify_ok) {
        printf("verify error:num=%d:%s:depth=%d:%s\n", err,
               X509_verify_cert_error_string(err), depth, buf);
    } else if (mydata->verbose_mode) {
        printf("depth=%d:%s\n", depth, buf);
    }
    /*
     * À ce stade, err contient la dernière erreur de vérification. Nous pouvons l'utiliser
     * pour quelque chose de spécial
     */
    if (!preverify_ok && (err == X509_V_ERR_UNABLE_TO_GET_ISSUER_CERT)) {
        X509_NAME_oneline(X509_get_issuer_name(err_cert), buf, 256);
        printf("issuer= %s\n", buf);
    }
    if (mydata->always_continue)
        return 1;
    else
        return preverify_ok;
}
...
mydata_t mydata;
...
mydata_index = SSL_get_ex_new_index(0, "mydata index", NULL, NULL, NULL);
...
SSL_CTX_set_verify(ctx, SSL_VERIFY_PEER | SSL_VERIFY_CLIENT_ONCE,
                   verify_callback);
/*
 * Laisser le verify_callback intercepter l'erreur verify_depth afin que nous obtenions
 * une erreur appropriée dans le fichier journal.
 */
SSL_CTX_set_verify_depth(verify_depth + 1);
/*
 * Configurer les données spécifiques au SSL dans « mydata » et les stocker dans la structure SSL.
 */
mydata.verify_depth = verify_depth; ...
SSL_set_ex_data(ssl, mydata_index, &mydata);
...
SSL_accept(ssl);       /* vérification du succès omise pour plus de clarté */
if (peer = SSL_get_peer_certificate(ssl)) {
    if (SSL_get_verify_result(ssl) == X509_V_OK) {
        /* Le client a envoyé un certificat qui s'est vérifié correctement */
    }
}
