DESCRIPTION

SSL_CTX_new_ex() crée un nouvel objet SSL_CTX, qui contient diverses configurations et données pertinentes pour l'établissement de sessions SSL/TLS ou DTLS. Celles-ci sont ensuite héritées par l'objet SSL représentant une session active. Le paramètre method spécifie si le contexte sera utilisé pour le côté client ou serveur ou les deux - pour plus de détails, voir les "NOTES" ci-dessous. Le contexte de bibliothèque libctx (voir OSSL_LIB_CTX(3)) est utilisé pour fournir les algorithmes cryptographiques nécessaires à la session. Tous les algorithmes cryptographiques utilisés par les objets SSL créés à partir de ce SSL_CTX seront récupérés depuis libctx en utilisant la chaîne de requête de propriétés propq (voir "ALGORITHM FETCHING" dans crypto(7). Les paramètres libctx ou propq peuvent être NULL.

SSL_CTX_new() fait la même chose que SSL_CTX_new_ex(), sauf que le contexte de bibliothèque par défaut est utilisé et qu'aucune chaîne de requête de propriétés n'est spécifiée.

Un objet SSL_CTX est compté par référence. La création d'un objet SSL_CTX pour la première fois incrémente le compteur de références. La libération de l'SSL_CTX (en utilisant SSL_CTX_free) le décrémente. Lorsque le compteur de références tombe à zéro, toute mémoire ou ressource allouée à l'objet SSL_CTX est libérée. SSL_CTX_up_ref() incrémente le compteur de références pour une structure SSL_CTX existante.

Un objet SSL_CTX ne doit pas être modifié après avoir été utilisé pour créer des objets SSL ou par plusieurs threads simultanément, car l'implémentation ne fournit pas de sérialisation d'accès pour ces cas.

NOTES

Lors de l'établissement de la session, par défaut, aucune vérification des identifiants du pair n'est effectuée. Cela doit être explicitement demandé, typiquement en utilisant SSL_CTX_set_verify(3). Pour vérifier les certificats des pairs, de nombreuses options peuvent être définies à l'aide de diverses fonctions telles que SSL_CTX_load_verify_locations(3) et SSL_CTX_set1_param(3).

L'implémentation SSL/(D)TLS utilise la fonction X509_STORE_CTX_set_default(3) pour préparer les vérifications pour X509_PURPOSE_SSL_SERVER côté client et X509_PURPOSE_SSL_CLIENT côté serveur. La fonction X509_VERIFY_PARAM_set_purpose(3) peut être utilisée, également en conjonction avec SSL_CTX_get0_param(3), pour outrepasser le but par défaut de la session.

L'objet SSL_CTX utilise method comme méthode de connexion. Trois variantes de méthodes sont disponibles : une méthode générique (pour une utilisation client ou serveur), une méthode serveur uniquement et une méthode client uniquement.

Le paramètre method de SSL_CTX_new_ex() et SSL_CTX_new() peut être l'une des suivantes :

TLS_method(), TLS_server_method(), TLS_client_method()
Ce sont les méthodes SSL/TLS génériques à version flexible. La version réelle du protocole utilisée sera négociée à la version la plus élevée mutuellement prise en charge par le client et le serveur. Les protocoles pris en charge sont SSLv3, TLSv1, TLSv1.1, TLSv1.2 et TLSv1.3. Les applications doivent utiliser ces méthodes et éviter les méthodes spécifiques à une version décrites ci-dessous, qui sont dépréciées.
SSLv23_method(), SSLv23_server_method(), SSLv23_client_method()
Ces fonctions n'existent plus, elles ont été renommées en TLS_method(), TLS_server_method() et TLS_client_method() respectivement. Actuellement, les anciens appels de fonction sont renommés en leurs correspondants nouveaux par des macros préprocesseur, pour garantir que le code existant utilisant les anciens noms de fonction compile toujours. Cependant, l'utilisation des anciens noms de fonction est dépréciée et le nouveau code devrait plutôt appeler les nouvelles fonctions.
TLSv1_2_method(), TLSv1_2_server_method(), TLSv1_2_client_method()
Une connexion SSL/TLS établie avec ces méthodes ne comprendra que le protocole TLSv1.2. Ces méthodes sont dépréciées.
TLSv1_1_method(), TLSv1_1_server_method(), TLSv1_1_client_method()
Une connexion SSL/TLS établie avec ces méthodes ne comprendra que le protocole TLSv1.1. Ces méthodes sont dépréciées.
TLSv1_method(), TLSv1_server_method(), TLSv1_client_method()
Une connexion SSL/TLS établie avec ces méthodes ne comprendra que le protocole TLSv1. Ces méthodes sont dépréciées.
SSLv3_method(), SSLv3_server_method(), SSLv3_client_method()
Une connexion SSL/TLS établie avec ces méthodes ne comprendra que le protocole SSLv3. Le protocole SSLv3 est déprécié et ne doit pas être utilisé.
DTLS_method(), DTLS_server_method(), DTLS_client_method()
Ce sont les méthodes DTLS à version flexible. Les protocoles actuellement pris en charge sont DTLS 1.0 et DTLS 1.2.
DTLSv1_2_method(), DTLSv1_2_server_method(), DTLSv1_2_client_method()
Ce sont les méthodes spécifiques à la version pour DTLSv1.2. Ces méthodes sont dépréciées.
DTLSv1_method(), DTLSv1_server_method(), DTLSv1_client_method()
Ce sont les méthodes spécifiques à la version pour DTLSv1. Ces méthodes sont dépréciées.

SSL_CTX_new() initialise la liste des chiffrements, le réglage du cache de session, les rappels, les clés et certificats ainsi que les options à leurs valeurs par défaut.

TLS_method(), TLS_server_method(), TLS_client_method(), DTLS_method(), DTLS_server_method() et DTLS_client_method() sont les méthodes à version flexible. Toutes les autres méthodes ne prennent en charge qu'une seule version de protocole spécifique. Utilisez les méthodes à version flexible

ds au lieu de la méthode spécifique à la version.

Si vous souhaitez limiter les protocoles pris en charge pour les méthodes flexibles en fonction de la version, vous pouvez utiliser les fonctions SSL_CTX_set_min_proto_version(3), SSL_set_min_proto_version(3), SSL_CTX_set_max_proto_version(3) et SSL_set_max_proto_version(3). En utilisant ces fonctions, il est possible de choisir par exemple TLS_server_method() et d'être capable de négocier avec tous les clients possibles, mais de n'autoriser que les protocoles plus récents comme TLS 1.0, TLS 1.1, TLS 1.2 ou TLS 1.3.

La liste des protocoles disponibles peut également être limitée en utilisant les options SSL_OP_NO_SSLv3, SSL_OP_NO_TLSv1, SSL_OP_NO_TLSv1_1, SSL_OP_NO_TLSv1_3, SSL_OP_NO_TLSv1_2 et SSL_OP_NO_TLSv1_3 des fonctions SSL_CTX_set_options(3) ou SSL_set_options(3), mais cette approche n'est pas recommandée. Les clients doivent éviter de créer des « trous » dans l'ensemble des protocoles qu'ils prennent en charge. Lors de la désactivation d'un protocole, assurez-vous de désactiver également soit toutes les versions de protocole précédentes, soit toutes les versions suivantes. Chez les clients, lorsqu'une version de protocole est désactivée sans désactiver toutes les versions de protocole précédentes, l'effet est également de désactiver toutes les versions de protocole suivantes.

Le protocole SSLv3 est obsolète et ne devrait généralement pas être utilisé. Les applications devraient généralement utiliser SSL_CTX_set_min_proto_version(3) pour définir le protocole minimum à au moins TLS1_VERSION.

VALEURS DE RETOUR

Les valeurs de retour suivantes peuvent se produire :

NULL
La création d'un nouvel objet SSL_CTX a échoué. Vérifiez la pile d'erreurs pour déterminer la raison.
Pointeur vers un objet SSL_CTX
La valeur de retour pointe vers un objet SSL_CTX alloué.

SSL_CTX_up_ref() renvoie 1 en cas de succès et 0 en cas d'échec.

HISTORIQUE

La prise en charge de SSLv2 et des fonctions correspondantes SSLv2_method(), SSLv2_server_method() et SSLv2_client_method() a été supprimée dans OpenSSL 1.1.0.

SSLv23_method(), SSLv23_server_method() et SSLv23_client_method() ont été dépréciées et les fonctions préférées TLS_method(), TLS_server_method() et TLS_client_method() ont été ajoutées dans OpenSSL 1.1.0.

Toutes les méthodes spécifiques à la version ont été dépréciées dans OpenSSL 1.1.0.

SSL_CTX_new_ex() a été ajouté dans OpenSSL 3.0.
