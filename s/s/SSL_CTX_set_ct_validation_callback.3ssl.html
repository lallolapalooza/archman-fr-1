SSL_CTX_set_ct_validation_callback(3ssl)

Paquet: openssl

Licences: Apache-2.0

SSL_CTX_set_ct_validation_callback(3ssl) OpenSSL SSL_CTX_set_ct_validation_callback(3ssl)

NOM

ssl_ct_validation_cb, SSL_enable_ct, SSL_CTX_enable_ct, SSL_set_ct_validation_callback, SSL_CTX_set_ct_validation_callback, SSL_ct_is_enabled, SSL_CTX_ct_is_enabled - contrôle de la politique de transparence des certificats

SYNOPIS

#include <openssl/ssl.h>
typedef int (*ssl_ct_validation_cb)(const CT_POLICY_EVAL_CTX *ctx,
                                   const STACK_OF(SCT) *scts, void *arg);
int SSL_enable_ct(SSL *s, int validation_mode);
int SSL_CTX_enable_ct(SSL_CTX *ctx, int validation_mode);
int SSL_set_ct_validation_callback(SSL *s, ssl_ct_validation_cb callback,
                                   void *arg);
int SSL_CTX_set_ct_validation_callback(SSL_CTX *ctx,
                                       ssl_ct_validation_cb callback,
                                       void *arg);
void SSL_disable_ct(SSL *s);
void SSL_CTX_disable_ct(SSL_CTX *ctx);
int SSL_ct_is_enabled(const SSL *s);
int SSL_CTX_ct_is_enabled(const SSL_CTX *ctx);

DESCRIPTION

SSL_enable_ct() et SSL_CTX_enable_ct() activent le traitement des horodatages de certificats (SCT) pour une connexion SSL spécifique ou pour toutes les connexions partageant le contexte SSL donné, respectivement. Ceci est réalisé en établissant un rappel de validation prédéfini. Le comportement du rappel est déterminé par l'argument validation_mode, qui peut être SSL_CT_VALIDATION_PERMISSIVE ou SSL_CT_VALIDATION_STRICT, comme décrit ci-dessous.

Si validation_mode est égal à SSL_CT_VALIDATION_STRICT, alors dans une négociation TLS complète avec le mode de vérification SSL_VERIFY_PEER, si le côté opposé ne présente pas de SCT valides, la négociation sera abandonnée. Si le mode de vérification est SSL_VERIFY_NONE, la négociation continuera même s'il n'y a pas de SCT valides. Cependant, dans ce cas, si le statut de vérification avant le rappel était X509_V_OK, il sera défini sur X509_V_ERR_NO_VALID_SCTS après le rappel. Les applications peuvent appeler SSL_get_verify_result(3) pour vérifier le statut à la fin de la négociation, même après la reprise de session, car le statut de vérification fait partie de l'état de session enregistré.

Si validation_mode est égal à SSL_CT_VALIDATION_PERMISSIVE, la négociation continue et le statut de vérification n'est pas modifié, quel que soit le statut de validation de tout SCT. L'application peut toujours inspecter le statut de validation des SCT à la fin de la négociation. Remarque : avec la reprise de session, aucun SCT ne sera présenté pendant la négociation. Par conséquent, dans les applications qui choisissent de différer la politique des SCT à après la négociation, de telles vérifications différées ne doivent être effectuées que lorsque la session n'est pas reprise.

SSL_set_ct_validation_callback() et SSL_CTX_set_ct_validation_callback() enregistrent un rappel personnalisé qui peut implémenter une politique différente de celle décrite ci-dessus. Ce rappel peut examiner les SCT du côté opposé et déterminer s'ils sont suffisants pour permettre à la connexion de continuer. La négociation est abandonnée si le mode de vérification n'est pas SSL_VERIFY_NONE et que le rappel renvoie un résultat non positif.

Un argument de données arbitraire, arg, peut être transmis au rappel lors de la configuration du rappel. Il sera transmis à celui-ci lorsqu'il sera appelé. La propriété de ce contexte reste avec l'appelant.

S'il n'y a pas de rappel défini, aucun SCT ne sera demandé et aucune validation de transparence des certificats ne sera effectuée.

Aucun rappel ne sera appelé lorsque le côté opposé ne présente aucun certificat, par exemple, en utilisant un chiffrement anonyme (aNULL). Dans ce cas, la négociation se poursuivra comme si aucun rappel n'avait été demandé. Les rappels ne sont pas non plus appelés lorsque le jeu de certificats du côté opposé est invalide ou lorsqu'une vérification est effectuée avec des enregistrements TLSA DANE-TA(2) ou DANE-EE(3) utilisant une PKI X.509 privée, ou lorsqu'il n'y a pas de PKI X.509 du tout, respectivement. Les clients qui exigent des SCT s'attendent à ne pas avoir activé de chiffrements aNULL ni spécifié la vérification du serveur via les enregistrements TLSA DANE-TA(2) ou DANE-EE(3).

SSL_disable_ct() et SSL_CTX_disable_ct() désactivent le traitement CT, que ce soit via le rappel prédéfini ou le rappel personnalisé, en définissant un rappel nul. Ceux-ci peuvent être implémentés comme des macros.

SSL_ct_is_enabled() et SSL_CTX_ct_is_enabled() renvoient 1 si le traitement CT est activé via SSL_enable_ct() ou un rappel personnalisé non nul, et 0 sinon.

NOTES

Lorsque le traitement des SCT est activé, l'empilage OCSP sera activé. C'est parce qu'une source possible de SCT peut être la réponse OCSP d'un serveur.

L'heure renvoyée par SSL_SESSION_get_time_ex() sera utilisée pour évaluer si les SCT présentés ont des dates futures (et sont donc invalides).

RESTRICTIONS

La validation de la transparence des certificats ne peut pas être activée et par conséquent aucun rappel ne peut être défini si une extension client personnalisée pour la gestion des SCT (TLSEXT_TYPE_signed_certificate_timestamp) a été enregistrée.

VALEURS DE RETOUR

SSL_enable_ct(), SSL_CTX_enable_ct(), SSL_CTX_set_ct_validation_callback() et SSL_set_ct_validation_callback() renvoient 1 si le callback est défini avec succès. Ils renvoient 0 en cas d'erreur, par exemple, si un gestionnaire d'extension client personnalisé a été configuré pour gérer les SCT.

SSL_disable_ct() et SSL_CTX_disable_ct() ne renvoient pas de résultat.

SSL_CTX_ct_is_enabled() et SSL_ct_is_enabled() renvoient 1 si un rappel de validation CT non nul a été défini, ou 0 s'il n'y a pas de rappel (ou équivalent, un rappel nul).
