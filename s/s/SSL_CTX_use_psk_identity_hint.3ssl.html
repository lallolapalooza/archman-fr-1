SSL_CTX_use_psk_identity_hint(3ssl)

Licences: Apache-2.0

SSL_CTX_USE_PSK_IDENTITY_HINT(3ssl) OpenSSL SSL_CTX_USE_PSK_IDENTITY_HINT(3ssl)

NOM

SSL_psk_server_cb_func, SSL_psk_find_session_cb_func, SSL_CTX_use_psk_identity_hint, SSL_use_psk_identity_hint, SSL_CTX_set_psk_server_callback, SSL_set_psk_server_callback, SSL_CTX_set_psk_find_session_callback, SSL_set_psk_find_session_callback - définir l'indice d'identité PSK à utiliser

SYNTAXIS

#include <openssl/ssl.h>
typedef int (*SSL_psk_find_session_cb_func)(SSL *ssl,
                                            const unsigned char *identity,
                                            size_t identity_len,
                                            SSL_SESSION **sess);
void SSL_CTX_set_psk_find_session_callback(SSL_CTX *ctx,
                                           SSL_psk_find_session_cb_func cb);
void SSL_set_psk_find_session_callback(SSL *s, SSL_psk_find_session_cb_func cb);
typedef unsigned int (*SSL_psk_server_cb_func)(SSL *ssl,
                                               const char *identity,
                                               unsigned char *psk,
                                               unsigned int max_psk_len);
int SSL_CTX_use_psk_identity_hint(SSL_CTX *ctx, const char *hint);
int SSL_use_psk_identity_hint(SSL *ssl, const char *hint);
void SSL_CTX_set_psk_server_callback(SSL_CTX *ctx, SSL_psk_server_cb_func cb);
void SSL_set_psk_server_callback(SSL *ssl, SSL_psk_server_cb_func cb);

DESCRIPTION

Une application serveur souhaitant utiliser les PSK TLSv1.3 doit définir une fonction de rappel en utilisant soit SSL_CTX_set_psk_find_session_callback() soit SSL_set_psk_find_session_callback(), selon le cas.

La fonction de rappel reçoit un pointeur vers la connexion SSL dans ssl et une identité dans identity de longueur identity_len. La fonction de rappel doit identifier un objet SSL_SESSION qui fournit les détails du PSK et le stocker dans *sess. L'objet SSL_SESSION doit, au minimum, définir la clé maître, le chiffrement et la version du protocole. Voir SSL_CTX_set_psk_use_session_callback(3) pour plus de détails.

Il est également possible que la fonction de rappel réussisse mais ne fournisse pas de PSK. Dans ce cas, aucun PSK ne sera utilisé mais la négociation se poursuivra. Pour ce faire, la fonction de rappel doit réussir et s'assurer que *sess est NULL.

Les indices d'identité ne sont pas pertinents pour TLSv1.3. Une application serveur souhaitant utiliser des chiffrements PSK pour TLSv1.2 et inférieur peut appeler SSL_CTX_use_psk_identity_hint() pour définir l'indice d'identité PSK se terminant par NUL, hint, pour l'objet contexte SSL ctx. SSL_use_psk_identity_hint() définit l'indice d'identité PSK se terminant par NUL, hint, pour l'objet connexion SSL ssl. Si hint est NULL, l'indice actuel de ctx ou ssl est supprimé.

Dans le cas où l'indice d'identité PSK est NULL, le serveur n'envoie pas le message ServerKeyExchange au client.

Une application serveur souhaitant utiliser des PSK pour TLSv1.2 et inférieur doit fournir une fonction de rappel qui est appelée lorsque le serveur reçoit le message ClientKeyExchange du client. Le but de la fonction de rappel est de valider l'identité PSK reçue et de récupérer la clé pré-partagée utilisée pendant la phase de configuration de la connexion. La fonction de rappel est définie à l'aide des fonctions SSL_CTX_set_psk_server_callback() ou SSL_set_psk_server_callback(). La fonction de rappel reçoit la connexion dans le paramètre ssl, l'identité PSK se terminant par NUL envoyée par le client dans le paramètre identity, et un tampon psk de longueur max_psk_len où la clé pré-partagée doit être stockée.

La fonction de rappel pour une utilisation dans TLSv1.2 fonctionnera également dans TLSv1.3 bien qu'il soit recommandé d'utiliser SSL_CTX_set_psk_find_session_callback() ou SSL_set_psk_find_session_callback() à cette fin à la place. Si TLSv1.3 a été négocié, OpenSSL vérifiera d'abord si une fonction de rappel a été définie via SSL_CTX_set_psk_find_session_callback() ou SSL_set_psk_find_session_callback() et l'utilisera de préférence. Si aucune fonction de rappel de ce type n'est présente, il vérifiera si une fonction de rappel a été définie via SSL_CTX_set_psk_server_callback() ou SSL_set_psk_server_callback() et l'utilisera. Dans ce cas, le hachage de négociation sera par défaut SHA-256 pour tout PSK retourné. Les échanges de données précoces TLSv1.3 sont possibles dans les connexions PSK uniquement avec la fonction de rappel SSL_psk_find_session_cb_func, et ne sont pas possibles avec la fonction de rappel SSL_psk_server_cb_func.

Une connexion établie via un PSK TLSv1.3 apparaîtra comme si une reprise de session avait eu lieu, de sorte que SSL_session_reused(3) renverra vrai.

VALEURS DE RETOUR

SSL_CTX_use_psk_identity_hint() et SSL_use_psk_identity_hint() renvoient 1 en cas de succès, 0 sinon.

Les valeurs de retour de la fonction de rappel du serveur TLSv1.2 et inférieurs sont interprétées comme suit :

0
L'identité PSK n'a pas été trouvée. Un message d'alerte "unknown_psk_identity" sera envoyé et la configuration de la connexion échouera.
>0
L'identité PSK a été trouvée et la fonction de rappel du serveur a fourni avec succès le PSK dans le paramètre psk. La valeur de retour est la longueur de psk en octets. Il est erroné de renvoyer une valeur supérieure à max_psk_len.

Si l'identité PSK n'a pas été trouvée mais que la fonction de rappel demande au protocole de continuer quand même, la fonction de rappel doit fournir des données aléatoires à psk et renvoyer la longueur des données aléatoires, de sorte que la connexion échouera avec `decryption_error` avant d'être complètement terminée.

La fonction de rappel SSL_psk_find_session_cb_func doit renvoyer 1 en cas de succès ou 0 en cas d'échec. En cas d'échec, la configuration de la connexion échoue.

NOTES

Il n'y a pas de problèmes de sécurité connus liés au partage du même PSK entre TLSv1.2 (ou inférieur) et TLSv1.3. Cependant, la RFC contient la mise en garde suivante :

"Bien qu'il n'y ait aucun moyen connu par lequel le même PSK pourrait produire des sorties liées dans les deux versions, seule une analyse limitée a été effectuée. Les implémentations peuvent garantir la sécurité contre les sorties liées inter-protocoles en ne réutilisant pas les PSK entre TLS 1.3 et TLS 1.2."
