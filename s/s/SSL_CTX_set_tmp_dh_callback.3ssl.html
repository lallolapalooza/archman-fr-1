SSL_CTX_set_tmp_dh_callback(3ssl)

Paquet: openssl

Licences: Apache-2.0

SSL_CTX_SET_TMP_DH_CALLBACK(3ssl) OpenSSL SSL_CTX_SET_TMP_DH_CALLBACK(3ssl)

NOM

SSL_CTX_set_dh_auto, SSL_set_dh_auto, SSL_CTX_set0_tmp_dh_pkey, SSL_set0_tmp_dh_pkey, SSL_CTX_set_tmp_dh_callback, SSL_CTX_set_tmp_dh, SSL_set_tmp_dh_callback, SSL_set_tmp_dh - gérer les clés DH pour l'échange de clés éphémères

SYNTAXE

#include <openssl/ssl.h>
long SSL_CTX_set_dh_auto(SSL_CTX *ctx, int onoff);
long SSL_set_dh_auto(SSL *s, int onoff);
int SSL_CTX_set0_tmp_dh_pkey(SSL_CTX *ctx, EVP_PKEY *dhpkey);
int SSL_set0_tmp_dh_pkey(SSL *s, EVP_PKEY *dhpkey);

Les fonctions suivantes sont obsolètes depuis OpenSSL 3.0 et peuvent être entièrement masquées en définissant OPENSSL_API_COMPAT avec une valeur de version appropriée, voir openssl_user_macros(7):

void SSL_CTX_set_tmp_dh_callback(SSL_CTX *ctx,
                                 DH *(*tmp_dh_callback)(SSL *ssl, int is_export,
                                                        int keylength));
long SSL_CTX_set_tmp_dh(SSL_CTX *ctx, DH *dh);
void SSL_set_tmp_dh_callback(SSL *ctx,
                             DH *(*tmp_dh_callback)(SSL *ssl, int is_export,
                                                    int keylength));
long SSL_set_tmp_dh(SSL *ssl, DH *dh);

DESCRIPTION

Les fonctions décrites sur cette page ne concernent que les serveurs.

Certains jeux de chiffrements peuvent utiliser un échange de clés Diffie-Hellman (DH) éphémère. Dans ces cas, les données de session sont négociées à l'aide de la clé DH éphémère/temporaire et la clé fournie et certifiée par la chaîne de certificats n'est utilisée que pour la signature. Les chiffrements anonymes (sans clé serveur permanente) utilisent également des clés DH éphémères.

L'utilisation d'un échange de clés DH éphémère offre une confidentialité persistante (forward secrecy) car la connexion ne peut être décryptée que lorsque la clé DH est connue. En générant une clé DH temporaire à l'intérieur de l'application serveur qui est perdue lorsque l'application se termine, il devient impossible pour un attaquant de décrypter les sessions passées, même s'il obtient la clé normale (certifiée), car cette clé n'a été utilisée que pour la signature.

Pour effectuer un échange de clés DH, le serveur doit utiliser un groupe DH (paramètres DH) et générer une clé DH. Le serveur générera toujours une nouvelle clé DH lors de la négociation.

Comme la génération de paramètres DH est extrêmement coûteuse en temps, une application ne doit pas générer les paramètres à la volée. Les paramètres DH peuvent être réutilisés, car la clé réelle est générée nouveau pendant la négociation.

Généralement, les applications devraient utiliser des paramètres DH bien connus qui bénéficient d'un support intégré dans OpenSSL. Les macros SSL_CTX_set_dh_auto() et SSL_set_dh_auto() configurent OpenSSL pour utiliser les paramètres DH intégrés par défaut pour les objets SSL_CTX et SSL respectivement. Passer une valeur de 2 ou 1 dans le paramètre onoff l'active. Si le paramètre onoff est défini à 2, il forcera la taille de la clé DH à 1024 si le niveau de sécurité du SSL_CTX ou du SSL SSL_CTX_set_security_level(3) est 0 ou 1. Passer une valeur de 0 le désactive. Le réglage par défaut est désactivé.

Si les paramètres DH "auto" sont activés, les paramètres seront sélectionnés pour être cohérents avec la taille de la clé associée au certificat du serveur. S'il n'y a pas de certificat (par exemple, pour les jeux de chiffrements PSK), alors il sera cohérent avec la taille de la clé de chiffrement symétrique négociée.

Les applications peuvent fournir leurs propres paramètres DH au lieu d'utiliser les valeurs intégrées. Cette approche est déconseillée et les applications devraient préférer utiliser le support des paramètres intégrés décrit ci-dessus. Les applications souhaitant fournir leurs propres paramètres DH devraient appeler SSL_CTX_set0_tmp_dh_pkey() ou SSL_set0_tmp_dh_pkey() pour fournir les paramètres pour le SSL_CTX ou le SSL respectivement. Les paramètres devraient être fournis dans l'argument dhpkey sous forme d'un EVP_PKEY contenant des paramètres DH. La propriété de la valeur dhpkey est transmise à l'objet SSL_CTX ou SSL à la suite de cet appel, donc l'appelant ne devrait pas la libérer si l'appel de fonction réussit.

Les macros obsolètes SSL_CTX_set_tmp_dh() et SSL_set_tmp_dh() font la même chose que SSL_CTX_set0_tmp_dh_pkey() et SSL_set0_tmp_dh_pkey() sauf que les paramètres DH sont fournis dans un objet DH à la place dans l'argument dh, et la propriété de l'objet DH est conservée par l'application. Les applications devraient plutôt utiliser les paramètres "auto", ou appeler SSL_CTX_set0_tmp_dh_pkey() ou SSL_set0_tmp_dh_pkey() selon le cas.

Une application peut plutôt spécifier les paramètres DH via une fonction de rappel en utilisant les fonctions SSL_CTX_set_tmp_dh_callback() ou SSL_set_tmp_dh_callback() pour définir le rappel pour l'objet SSL_CTX ou SSL respectivement. Ces fonctions sont obsolètes. Les applications devraient plutôt utiliser les paramètres "auto", ou spécifier les paramètres via SSL_CTX_set0_tmp_dh_pkey() ou SSL_set0_tmp_dh_pkey() selon le cas.

Le rappel sera appelé lors d'une connexion lorsque des paramètres DH sont requis. L'objet SSL pour la connexion actuelle est fourni en argument. Les versions précédentes d'OpenSSL utilisaient les arguments is_export et keylength pour contrôler la génération des paramètres pour les jeux de chiffrements d'exportation et non d'exportation. Les versions modernes d'OpenSSL ne prennent pas en charge les jeux de chiffrements d'exportation et ces arguments sont donc inutilisés et peuvent être ignorés par le rappel. Le rappel devrait renvoyer les paramètres à utiliser dans un objet DH. La propriété de l'objet DH est conservée par l'application et devrait être libérée plus tard.

VALEURS DE RETOUR

Toutes ces fonctions/macros renvoient 1 en cas de succès ou 0 en cas d'erreur.
