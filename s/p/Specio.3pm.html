NOM

Specio - Contraintes de types et coercitions pour Perl

VERSION

version 0.53

SYNOPIS

package MyApp::Type::Library;
use Specio::Declare;
use Specio::Library::Builtins;
declare(
    'PositiveInt',
    parent => t('Int'),
    inline => sub {
        $_[0]->parent->inline_check( $_[1] )
            . ' && ( '
            . $_[1]
            . ' > 0 )';
    },
);
# ou ...
declare(
    'PositiveInt',
    parent => t('Int'),
    where  => sub { $_[0] > 0 },
);
declare(
    'ArrayRefOfPositiveInt',
    parent => t(
        'ArrayRef',
        of => t('PositiveInt'),
    ),
);
coerce(
    'ArrayRefOfPositiveInt',
    from  => t('PositiveInt'),
    using => sub { [ $_[0] ] },
);
any_can_type(
    'Duck',
    methods => [ 'duck_walk', 'quack' ],
);
object_isa_type('MyApp::Person');

DESCRIPTION

La distribution "Specio" fournit des classes pour représenter des contraintes de types et des coercitions, ainsi que des sucre syntaxiques pour les déclarer.

Notez qu'il ne s'agit pas d'un système de types propre pour Perl. Rien dans cette distribution ne fera magiquement que l'interpréteur Perl commence à vérifier le type d'une valeur lors de son affectation à une variable. En fait, il n'y a aucun moyen intégré d'appliquer un type à une variable.

Au lieu de cela, vous pouvez explicitement vérifier une valeur par rapport à un type et, éventuellement, contraindre des valeurs à ce type.

QU'EST-CE QU'UN TYPE ?

À la base, un type est simplement une contrainte. Une contrainte est du code qui vérifie une valeur et renvoie vrai ou faux. La plupart des contraintes sont représentées par des objets Specio::Constraint::Simple. Cependant, il existe d'autres classes de contraintes de types pour des types spécialisés de contraintes.

Les types peuvent être nommés ou anonymes, et chaque type peut avoir un type parent. La contrainte d'un type est facultative car parfois vous pourriez vouloir créer un sous-type nommé d'un type existant sans ajouter de contraintes supplémentaires.

Les contraintes peuvent être exprimées soit sous forme de référence de sous-routine simple, soit sous forme de référence de sous-routine génératrice en ligne. La première est plus facile à écrire, mais la seconde est préférée car elle permet une meilleure optimisation.

Un type peut également avoir une référence de sous-routine génératrice de message facultative. Vous pouvez l'utiliser pour fournir un message d'erreur plus intelligent lorsqu'une valeur ne passe pas la contrainte, bien que le message par défaut devrait suffire dans la plupart des cas.

Enfin, vous pouvez associer un ensemble de coercitions à un type. Une coercion est une référence de sous-routine (ou un générateur en ligne, comme les contraintes) qui prend une valeur d'un type et la transforme en une valeur qui correspond au type auquel la coercion appartient.

TYPES INTRODUITS

Cette distribution est livrée avec un ensemble de types intégrés représentant les types fournis par l'interpréteur Perl lui-même. Ils sont organisés dans une hiérarchie comme suit :

Item
    Bool
    Maybe (of `a)
    Undef
    Defined
        Value
            Str
                Num
                    Int
                ClassName
        Ref
            ScalarRef (of `a)
            ArrayRef (of `a)
            HashRef (of `a)
            CodeRef
            RegexpRef
            GlobRef
            FileHandle
            Object

Le type "Item" accepte tout et n'importe quoi.

Le type "Bool" n'accepte que "undef", 0, ou 1.

Le type "Undef" n'accepte que "undef".

Le type "Defined" accepte tout sauf "undef".

Les types "Num" et "Int" sont plus stricts concernant les nombres que Perl. Plus précisément, ils n'autorisent aucun espace dans le nombre, et n'acceptent pas non plus "Nan", "Inf" ou "Infinity".

La contrainte de type "ClassName" vérifie que le nom est valide *et* que la classe est chargée.

Le type "FileHandle" accepte soit un glob, un handle de fichier scalaire, soit tout ce qui est un IO::Handle.

Tous les types acceptent les objets surchargés qui supportent l'opération requise. Voir ci-dessous pour plus de détails.

Surcharge

La surcharge de Perl est horriblement cassée et n'a pas beaucoup de sens.

Cependant, contrairement à Moose, toutes les contraintes de type acceptent les objets surchargés lorsque cela a du sens.

Pour les types où la surcharge a du sens, nous vérifions explicitement que l'objet fournit la surcharge de type attendue. Nous n'essayons *pas* simplement d'utiliser l'objet comme type en question et d'espérer que cela fonctionne. Cela signifie que ces vérifications ignorent effectivement le paramètre "fallback" pour l'objet surchargé. En d'autres termes, un objet qui surcharge la stringification ne passera pas la vérification de type "Bool" à moins qu'il ne surcharge *également* la booléanisation.

La plupart des types ne vérifient pas que la méthode surchargée renvoie réellement quelque chose qui correspond à la contrainte. Cela pourrait changer à l'avenir.

Le type "Bool" accepte un objet qui implémente la surcharge "bool".

Le type "Str" accepte un objet qui implémente la surcharge de chaîne ("q{""}").

Le type "Num" accepte un objet qui implémente la surcharge numérique ("'0+'}"). Le type "Int" fait de même, mais il vérifiera que la surcharge renvoie un entier réel.

Le type "ClassName" acceptera un objet avec une surcharge de chaîne qui renvoie un nom de classe.

Pour rendre tout cela plus confus, le type "Value" n'acceptera *jamais* d'objet, même si certains de ses sous-types le font.

Les différents types de références acceptent tous des objets qui fournissent la surcharge appropriée. Le type "FileHandle" accepte un objet qui surcharge la globification tant que le glob renvoyé est un handle de fichier ouvert.

TYPES PARAMÉTRABLES

Tout type suivi d'un paramètre de type "of `a" dans la hiérarchie ci-dessus peut être paramétré. Le paramètre est lui-même un type, vous pouvez donc dire que vous voulez un "ArrayRef d'Int", ou même un "ArrayRef de HashRef de ScalarRef de ClassName".

Lorsqu'ils sont paramétrés, les types "ScalarRef" et "ArrayRef" vérifient que la ou les valeurs qu'ils référencent correspondent au paramètre de type. Pour le type "HashRef", le paramètre s'applique aux valeurs (les clés ne sont jamais vérifiées).

Maybe

Le type "Maybe" est un type paramétrable spécial. Il autorise soit "undef", soit une valeur. En soi, il est dénué de sens, car il est équivalent à "Maybe d'Item", ce qui est équivalent à Item. Lorsqu'il est paramétré, il accepte soit un "undef", soit le type de son paramètre.

Ceci est utile pour les attributs ou paramètres optionnels. Cependant, vous feriez probablement mieux de faire en sorte que votre code ne passe tout simplement pas le paramètre. Cela rend généralement une API plus simple.

REGISTRES ET IMPORTATION

Les types sont locaux à chaque paquet où ils sont utilisés. Lorsque vous "importez" des types d'une autre bibliothèque, vous faites en fait une copie de ce type.

Cela signifie qu'un type nommé "Foo" dans un paquet peut ne pas être le même que "Foo" dans un autre paquet. Cela a le potentiel de confusion, mais évite également l'action magique à

DISTANCE POLLUTION

La pollution de distance qui accompagne un système de noms global.

Le registre est géré en interne par les modules de la distribution Specio et n'est pas exposé à votre code. Pour accéder à un type, vous appelez toujours t('TypeName').

Cela renvoie le type nommé ou échoue s'il n'existe pas un tel type.

Puisque les types sont toujours copiés lors de l'importation, il est sûr de créer des coercitions sur n'importe quel type. Votre coercition de "Str" vers "Int" ne sera pas vue par aucun autre paquet, à moins que ce paquet n'importe explicitement votre type "Int".

Lorsque vous importez des types, vous importez tous les types définis dans le paquet que vous importez. Cependant, vous *pouvez* réécrire un type importé avec votre propre définition. Vous *ne pouvez pas* définir le même type deux fois en interne.

CREATION D'UNE BIBLIOTHEQUE DE TYPES

Par défaut, tous les types créés à l'intérieur d'un paquet ne sont pas visibles par d'autres paquets. Si vous souhaitez créer une bibliothèque de types, vous devez hériter de la classe Specio::Exporter:

package MyApp::Type::Library;
use parent 'Specio::Exporter';
use Specio::Declare;
use Specio::Library::Builtins;
declare(
    'Foo',
    parent => t('Str'),
    where  => sub { $_[0] =~ /foo/i },
);

Maintenant, le paquet MyApp::Type::Library exportera un seul type nommé "Foo". Il ne ré-exportera pas les types fournis par Specio::Library::Builtins.

Si vous souhaitez que votre bibliothèque ré-exporte d'autres types de bibliothèques, vous pouvez le demander explicitement:

package MyApp::Type::Library;
use parent 'Specio::Exporter';
use Specio::Declare;
use Specio::Library::Builtins -reexport;
declare( 'Foo, ... ');

Maintenant MyApp::Types::Library exportera tous les types que vous définissez vous-même, ainsi que tous les types définis dans Specio::Library::Builtins.

DECLARATION DES TYPES

Utilisez le module Specio::Declare pour déclarer des types. Il exporte un ensemble d'aides pour déclarer des types. Voir les détails de ces aides dans la documentation du module.

UTILISATION DE SPECIO AVEC Moose

Cela devrait fonctionner simplement. Utilisez un type Specio partout où vous spécifiez un type.

UTILISATION DE SPECIO AVEC Moo

Utiliser Specio avec Moo est facile. Vous pouvez passer des objets de contrainte Specio en tant que paramètres "isa" pour les attributs. Pour les coercions, appelez simplement "$type->coercion_sub".

package Foo;
use Specio::Declare;
use Specio::Library::Builtins;
use Moo;
my $str_type = t('Str');
has string => (
   is  => 'ro',
   isa => $str_type,
);
my $ucstr = declare(
    'UCStr',
    parent => t('Str'),
    where  => sub { $_[0] =~ /^[A-Z]+$/ },
);
coerce(
    $ucstr,
    from  => t('Str'),
    using => sub { return uc $_[0] },
);
has ucstr => (
    is     => 'ro',
    isa    => $ucstr,
    coerce => $ucstr->coercion_sub,
);

Les sous-routines retournées par Specio utilisent Sub::Quote en interne et conviennent à l'inlining.

Moose, MooseX::Types, et Specio

Ce module vise à remplacer à la fois le système de types de Moose (voir Moose::Util::TypeConstraints alias MUTC) et celui de MooseX::Types, qui tente de corriger certaines lacunes dans la conception des types de Moose.

Voici quelques différences notables:

  • Les noms de types sont des chaînes de caractères, mais pas globaux.

    Contrairement à Moose et MooseX::Types, les noms de types sont toujours locaux au paquet actuel. Il n'y a aucune possibilité de collision de noms entre différents modules, vous pouvez donc utiliser des noms courts sans inquiétude.

    Contrairement à MooseX::Types, les types sont des chaînes de caractères, il n'y a donc aucune possibilité de collision avec des noms de classes ou de sous-routines existants.

  • Aucune création automatique de type.

    Les types sont obtenus via la sous-routine t(). Si vous passez un nom inconnu à cette sous-routine, elle échoue. C'est différent de Moose et MooseX::Types, qui supposent que les noms inconnus sont des noms de classe.

  • Les types anonymes sont explicites.

    Avec Moose et MooseX::Types, la même sous-routine subtype() est utilisée pour déclarer des types nommés et anonymes. Avec Specio, declare() est utilisé pour les types nommés et anon() pour les types anonymes.

  • Les types de classes et d'objets sont distincts.

    Moose et MooseX::Types ont "class_type" et "duck_type". Le premier nécessite un objet, tandis que le second accepte un nom de classe ou un objet.

    Avec Specio, la distinction entre accepter un objet, un objet ou une classe est explicite. Il y a six aides de déclaration, "object_can_type", "object_does_type", "object_isa_type", "any_can_type", "any_does_type", et "any_isa_type".

  • Le support de la surcharge est intégré.

    La surcharge de Perl est mal implémentée, mais l'ignorer rend le système de types de Moose frustrant dans de nombreux cas.

  • Les types peuvent avoir une contrainte ou un générateur lié, mais pas les deux.

    Les types de Moose et MooseX::Types peuvent être définis avec une référence de sous-routine comme contrainte, un générateur lié ou les deux. Ceci est purement pour la compatibilité ascendante, ce qui rend les internes plus compliqués que nécessaire.

    Avec Specio, une contrainte peut avoir *soit* une sous-routine comme référence, *soit* un générateur lié, mais pas les deux.

  • Les coercions peuvent être liées.

    Je n'ai pas implémenté cela dans Moose.

  • Pas de fonctionnalités de coercition aussi extrêmes.

    Moose a des fonctionnalités inhabituelles (et principalement non documentées) liées aux coercions et aux types paramétrés. C'est une mauvaise caractéristique.

PREREQUIS OPTIONNELS

Il existe plusieurs prérequis optionnels qui, s'ils sont installés, amélioreront légèrement cette distribution.

  • Ref::Util

    L'installation de ceci accélérera plusieurs types de vérifications sur les types par défaut.

  • XString

    Si cela est installé, il sera chargé à la place du module B si vous avez Perl 5.10 ou plus. Ce module est beaucoup plus efficace en mémoire que de charger tout le module B.

  • Sub::Util ou Sub::Name

    Si l'un de ceux-ci est installé, les traces de pile se terminant dans le code de Specio auront des noms de sous-routines beaucoup plus jolis pour chaque frame.

FORCAGE DU MODE PERL PUR

Pour certains cas d'utilisation (notamment, le fatpacking d'un programme), vous pourriez vouloir forcer Specio à utiliser du code Perl pur au lieu du code XS. Cela peut être fait en définissant la variable d'environnement "SPECIO_IMPLEMENTATION" à "PP".

POURQUOI LE NOM ?

Cette distribution s'appelait à l'origine "Type", mais c'est un espace de noms trop générique. Specio est latin, signifie "voir" et "spec" est la racine du mot "species". C'est court, relativement facile à écrire et n'est pas utilisé par d'autres distributions.
