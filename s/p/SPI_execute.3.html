SPI_EXECUTE(3) Documentation PostgreSQL 18.1 SPI_EXECUTE(3)

NOM

SPI_execute - exécute une commande

SYNOPIS

int SPI_execute(const char * command, bool read_only, long count)

DESCRIPTION

SPI_execute exécute la commande SQL spécifiée pour count lignes. Si read_only est vrai, la commande doit être en lecture seule et les frais généraux d'exécution sont légèrement réduits.

Cette fonction ne peut être appelée que depuis une fonction C connectée.

Si count est zéro, la commande est exécutée pour toutes les lignes auxquelles elle s'applique. Si count est supérieur à zéro, pas plus de count lignes ne seront récupérées ; l'exécution s'arrête lorsque le compte est atteint, un peu comme l'ajout d'une clause LIMIT à la requête. Par exemple,

SPI_execute("SELECT * FROM foo", true, 5);

récupérera au plus 5 lignes de la table. Notez qu'une telle limite n'est effective que lorsque la commande retourne effectivement des lignes. Par exemple,

SPI_execute("INSERT INTO foo SELECT * FROM bar", false, 5);

insère toutes les lignes de bar, ignorant le paramètre count. Cependant, avec

SPI_execute("INSERT INTO foo SELECT * FROM bar RETURNING *", false, 5);

au plus 5 lignes seraient insérées, car l'exécution s'arrêterait après la récupération de la cinquième ligne de résultat RETURNING.

Vous pouvez passer plusieurs commandes dans une seule chaîne ; SPI_execute renvoie le résultat de la commande exécutée en dernier. La limite count s'applique séparément à chaque commande (même si seul le dernier résultat sera effectivement retourné). La limite n'est pas appliquée aux commandes cachées générées par les règles.

Lorsque read_only est faux, SPI_execute incrémente le compteur de commandes et calcule un nouveau "snapshot" avant d'exécuter chaque commande de la chaîne. Le "snapshot" ne change pas réellement si le niveau d'isolation de la transaction actuelle est SERIALIZABLE ou REPEATABLE READ, mais en mode READ COMMITTED, la mise à jour du "snapshot" permet à chaque commande de voir les résultats des transactions nouvellement validées des autres sessions. Ceci est essentiel pour un comportement cohérent lorsque les commandes modifient la base de données.

Lorsque read_only est vrai, SPI_execute ne met pas à jour le "snapshot" ni le compteur de commandes, et n'autorise que les commandes SELECT simples dans la chaîne de commandes. Les commandes sont exécutées en utilisant le "snapshot" préalablement établi pour la requête environnante. Ce mode d'exécution est quelque peu plus rapide que le mode lecture/écriture en raison de l'élimination des frais généraux par commande. Il permet également de créer des fonctions véritablement stables : puisque les exécutions successives utiliseront toutes le même "snapshot", il n'y aura aucun changement dans les résultats.

Il est généralement déconseillé de mélanger des commandes en lecture seule et en lecture/écriture au sein d'une même fonction utilisant SPI ; cela pourrait entraîner un comportement très déroutant, car les requêtes en lecture seule ne verraient pas les résultats des mises à jour de la base de données effectuées par les requêtes en lecture/écriture.

Le nombre réel de lignes pour lesquelles la (dernière) commande a été exécutée est retourné dans la variable globale SPI_processed. Si la valeur de retour de la fonction est SPI_OK_SELECT, SPI_OK_INSERT_RETURNING, SPI_OK_DELETE_RETURNING, SPI_OK_UPDATE_RETURNING, ou SPI_OK_MERGE_RETURNING, alors vous pouvez utiliser le pointeur global SPITupleTable *SPI_tuptable pour accéder aux lignes de résultat. Certaines commandes utilitaires (comme EXPLAIN) retournent également des ensembles de lignes, et SPI_tuptable conterra le résultat dans ces cas aussi. Certaines commandes utilitaires (COPY, CREATE TABLE AS) ne retournent pas d'ensemble de lignes, donc SPI_tuptable est NULL, mais elles retournent toujours le nombre de lignes traitées dans SPI_processed.

La structure SPITupleTable est définie comme suit :

typedef struct SPITupleTable
{
    /* Membres publics */
    TupleDesc   tupdesc;        /* descripteur de tuple */
    HeapTuple  *vals;           /* tableau de tuples */
    uint64      numvals;        /* nombre de tuples valides */
    /* Membres privés, non destinés aux appelants externes */
    uint64      alloced;        /* longueur allouée du tableau vals */
    MemoryContext tuptabcxt;    /* contexte mémoire de la table de résultats */
    slist_node  next;           /* lien pour la gestion interne */
    SubTransactionId subid;     /* sous-transaction dans laquelle tuptable a été créée */
} SPITupleTable;

Les champs tupdesc, vals et numvals peuvent être utilisés par les appelants SPI ; les autres champs sont internes. vals est un tableau de pointeurs vers les lignes. Le nombre de lignes est donné par numvals (pour des raisons historiques, ce compte est également retourné dans SPI_processed). tupdesc est un descripteur de ligne que vous pouvez passer aux fonctions SPI traitant les lignes.

SPI_finish libère toutes les SPITupleTables allouées pendant la fonction C actuelle. Vous pouvez libérer une table de résultats particulière plus tôt, si vous n'en avez plus besoin, en appelant SPI_freetuptable.

ARGUMENTS

const char * command

chaîne contenant la commande à exécuter

bool read_only

vrai pour exécution en lecture seule

long count

nombre maximum de lignes à retourner, ou 0 pour aucune limite

VALEUR RENVOYÉE

Si l'exécution de la commande a réussi, l'une des valeurs (non négatives) suivantes sera retournée :

SPI_OK_SELECT

si un SELECT (mais pas SELECT INTO) a été exécuté

SPI_OK_SELINTO

si un SELECT INTO a été exécuté

SPI_OK_INSERT

si un INSERT a été exécuté

SPI_OK_DELETE

si un DELETE a été exécuté

SPI_OK_UPDATE

si un UPDATE a été exécuté

SPI_OK_MERGE

si un MERGE a été exécuté

SPI_OK_INSERT_RETURNING

si un INSERT RETURNING a été exécuté

SPI_OK_DELETE_RETURNING

si un DELETE RETURNING a été exécuté

SPI_OK_UPDATE_RETURNING

si un UPDATE RETURNING a été exécuté

SPI_OK_MERGE_RETURNING

si un MERGE RETURNING a été exécuté

SPI_OK_UTILITY

si une commande utilitaire (par exemple, CREATE TABLE) a été exécutée

SPI_OK_REWRITTEN

si la commande a été réécrite en un autre type de commande (par exemple, UPDATE est devenu INSERT) par une règle.

En cas d'erreur, l'une des valeurs négatives suivantes est retournée :

SPI_ERROR_ARGUMENT

si command est NULL ou si count est inférieur à 0

SPI_ERROR_COPY

si COPY TO stdout ou COPY FROM stdin a été tenté

SPI_ERROR_TRANSACTION

si une commande de manipulation de transaction a été tentée (BEGIN, COMMIT, ROLLBACK, SAVEPOINT, PREPARE TRANSACTION, COMMIT PREPARED, ROLLBACK PREPARED, ou toute variante de ceux-ci)

SPI_ERROR_OPUNKNOWN

si le type de commande est inconnu (ne devrait pas arriver)

SPI_ERROR_UNCONNECTED

si appelée depuis une fonction C non connectée

NOTES

Toutes les fonctions d'exécution de requêtes SPI définissent à la fois SPI_processed et SPI_tuptable (juste le pointeur, pas le contenu de la structure). Sauvegardez ces deux variables globales dans des variables locales de fonction C si vous avez besoin d'accéder à la table de résultat de SPI_execute ou d'une autre fonction d'exécution de requête lors d'appels ultérieurs.
