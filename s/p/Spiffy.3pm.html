NOM

Spiffy - Spiffy Perl Interface Framework For You

SYNTAXE

package Keen;
use Spiffy -Base;
field 'mirth';
const mood => ':-)';
sub happy {
    if ($self->mood eq ':-(') {
        $self->mirth(-1);
        print "Cheer up!";
    }
    super;
}

DESCRIPTION

"Spiffy" est un framework et une méthodologie pour la programmation orientée objet (POO) en Perl. Spiffy combine les meilleures parties de Exporter.pm, base.pm, mixin.pm et SUPER.pm en une seule classe fondamentale magique. Il tente de corriger toutes les petites imperfections et les défauts de la POO traditionnelle en Perl, de manière propre, directe et (peut-être un jour) standard.

Spiffy emprunte des idées à d'autres langages POO comme Python, Ruby, Java et Perl 6. Il ajoute également quelques astuces personnelles.

Si vous jetez un œil sur CPAN, il existe une tonne de modules liés à la POO. Lorsque vous démarrez un nouveau projet, vous devez choisir l'ensemble de modules qui a le plus de sens, puis utiliser ces modules dans chacune de vos classes. Spiffy, en revanche, contient tout ce dont vous aurez probablement besoin dans un seul module, et vous n'avez besoin de l'utiliser qu'une seule fois dans l'une de vos classes. Si vous faites de Spiffy.pm la classe de base de la classe la plus basique de votre projet, Spiffy transmettra automatiquement toute sa magie à toutes vos sous-classes. Vous pourrez peut-être oublier que vous l'utilisez !

La différence la plus frappante entre Spiffy et les autres classes de base orientées objet Perl est sa capacité à exporter des éléments. Si vous créez une sous-classe de Spiffy, toutes les choses que Spiffy exporte seront automatiquement exportées par votre sous-classe, en plus de tout autre élément que vous souhaitez exporter. Et si quelqu'un crée une sous-classe de votre sous-classe, tout cela sera exporté automatiquement, et ainsi de suite. Pensez-y comme à une "Exportation Héritée", et cela utilise la syntaxe familière du spécificateur de Exporter.pm.

Pour utiliser Spiffy ou toute sous-classe de Spiffy comme classe de base de votre classe, vous spécifiez l'argument "-base" à la commande "use".

use MySpiffyBaseModule -base;

Vous pouvez également utiliser la syntaxe traditionnelle "use base 'MySpiffyBaseModule';" et tout fonctionnera exactement de la même manière. La seule réserve est que Spiffy.pm doit déjà être chargé. C'est parce que Spiffy réécrit base.pm à la volée pour faire toute la magie Spiffy.

Spiffy prend en charge les mixins de type Ruby avec les rôles de type Perl6. Tout comme pour "base", vous pouvez utiliser l'une des invocations suivantes :

use mixin 'MySpiffyBaseModule';
use MySpiffyBaseModule -mixin;

La seconde version ne fonctionnera que si la classe qui est mixée est une sous-classe de Spiffy. La première version fonctionnera dans tous les cas, tant que Spiffy a déjà été chargé.

Pour limiter les méthodes mixées, utilisez les rôles. (Indice : ils fonctionnent comme une liste Exporter) :

use MySpiffyBaseModule -mixin => qw(:basics x y !foo);

Dans la POO Perl, presque toutes les sous-routines sont des méthodes. Chaque méthode reçoit l'objet qui lui est passé comme premier argument. Cela signifie que pratiquement toutes les sous-routines commencent par la ligne :

my $self = shift;

Spiffy fournit un mécanisme de filtrage simple et optionnel pour insérer cette ligne pour vous, ce qui se traduit par un code plus propre. Si vous estimez qu'une méthode moyenne a 10 lignes de code, c'est 10% de votre code ! Pour activer cette option, utilisez simplement l'option "- Base" au lieu de l'option "-base", ou ajoutez l'option "-selfless". Si le filtrage de source vous met mal à l'aise, n'utilisez pas cette fonctionnalité. Je la trouve personnellement addictive dans ma quête d'un code propre, maintenable et scintillant.

Une fonctionnalité utile de Spiffy est qu'il exporte deux fonctions : "field" et "const" qui peuvent être utilisées pour déclarer les attributs de votre classe et générer automatiquement des méthodes d'accès pour eux. La seule différence entre les deux fonctions est que les attributs "const" ne peuvent pas être modifiés ; l'accesseur est donc beaucoup plus rapide.

Un aspect intéressant de la POO est lorsqu'une méthode appelle la même méthode d'une classe parente. Ceci est généralement connu sous le nom d'appel d'une méthode super. La facilité de Perl pour faire cela est terriblement laide :

sub cleanup {
    my $self = shift;
    $self->scrub;
    $self->SUPER::cleanup(@_);
}

Spiffy rend l'appel de méthodes super, euh, super facile. Vous utilisez simplement la fonction "super". Vous n'avez pas besoin de lui passer d'arguments car elle les transmet automatiquement pour vous. Voici la même fonction avec Spiffy :

sub cleanup {
    $self->scrub;
    super;
}

Spiffy dispose d'une méthode spéciale pour analyser les arguments appelée "parse_arguments", qu'il utilise également pour analyser ses propres arguments. Vous déclarez quels arguments sont booléens (singleton) et lesquels sont appariés, avec deux méthodes spéciales appelées "boolean_arguments" et "paired_arguments". Parse arguments extrait les booléens et les paires et les renvoie dans une hash anonyme, suivi d'une liste des arguments non appariés.

Enfin, Spiffy peut exporter quelques fonctions de débogage "WWW", "XXX", "YYY" et "ZZZ". Chacune d'elles produit un dump YAML de ses arguments. WWW avertit la sortie, XXX meurt avec la sortie, YYY imprime la sortie, et ZZZ avoue la sortie. Si YAML ne convient pas à vos besoins, vous pouvez passer tous les dumps au format Data::Dumper avec l'option "-dumper".

C'est Spiffy !

EXPORTATION

Spiffy implémente une idée complètement nouvelle en Perl. Les modules qui agissent à la fois comme des classes orientées objet et qui exportent des fonctions. Mais cela va plus loin que le concept de Exporter.pm ; il parcourt tout le chemin @ISA d'une classe et respecte les spécifications d'exportation de chaque module. Comme Spiffy fait appel au module Exporter pour ce faire, vous pouvez utiliser toutes les fonctionnalités de l'interface fantaisistes qu'Exporter a, y compris les balises et la négation.

Spiffy considère que tous les arguments qui ne commencent pas par un tiret composent la spécification d'exportation.

package Vehicle;
use Spiffy -base;
our $SERIAL_NUMBER = 0;
our @EXPORT = qw($SERIAL_NUMBER);
our @EXPORT_BASE = qw(tire horn);
package Bicycle;
use Vehicle -base, '!field';
$self->inflate(tire);

Dans ce cas, "Bicycle->isa('Vehicle')" et aussi toutes les choses que "Vehicle" et "Spiffy" exportent, iront dans "Bicycle", à l'exception de "field".

L'exportation peut être très utile lorsque vous avez conçu un système avec des centaines de classes, et que vous voulez qu'elles aient toutes accès à certaines fonctions ou constantes

ou variables. Il suffit de les exporter dans votre classe de base principale et chaque sous-classe

obtiendra les fonctions dont elle a besoin.

Vous pouvez faire presque tout ce que fait Exporter car Spiffy délègue le travail à Exporter (après avoir ajouté une magie Spiffy). Spiffy propose une variable @EXPORT_BASE qui est comme @EXPORT, mais uniquement pour les utilisations qui utilisent "-base".

MIXINS ET ROLES

Si vous avez beaucoup programmé en POO en Perl, vous avez probablement utilisé l'Héritage Multiple (HM), et si vous avez beaucoup utilisé l'HM, vous avez probablement rencontré des problèmes et des maux de tête étranges. Certains langages comme Ruby tentent de résoudre les problèmes de l'HM en utilisant une technique appelée mixins. Essentiellement, toutes les classes Ruby utilisent uniquement l'Héritage Simple (HS), puis *mixent* des fonctionnalités d'autres modules si elles en ont besoin.

Les mixins peuvent être considérés, à un niveau simpliste, comme l'*importation* des méthodes d'une autre classe dans votre sous-classe. Mais d'un point de vue implémentation, ce n'est pas la meilleure façon de faire. Spiffy fait ce que fait Ruby. Il crée une classe anonyme vide, y importe tout, puis enchaîne la nouvelle classe dans votre chemin d'héritage HS. En d'autres termes, si vous dites :

package AAA;
use BBB -base;
use CCC -mixin;
use DDD -mixin;

Vous vous retrouvez avec une chaîne d'héritage simple de classes comme celle-ci :

AAA << AAA-DDD << AAA-CCC << BBB;

MIXIN

"AAA-DDD" et "AAA-CCC" sont les noms de package réels des classes générées. L'avantage de ce style est que le mixin de CCC n'écrase aucune méthode dans AAA, et DDD n'entre pas en conflit avec AAA ou CCC. Si vous aviez mixé une méthode dans CCC qui était également dans AAA, vous pouvez toujours y accéder en utilisant "super".

Lorsque Spiffy mixe CCC, il importe toutes les méthodes de CCC qui ne commencent pas par un underscore. En fait, il va plus loin. Si CCC est une sous-classe, il importera toutes les méthodes que CCC "peut" faire par héritage. C'est très puissant, peut-être trop puissant.

Pour limiter ce que vous mixez, Spiffy emprunte le concept de Rôles à Perl6. Le terme rôle est utilisé de manière plus lâche dans Spiffy cependant. C'est beaucoup comme une liste d'importation que le module Exporter utilise, et vous pouvez utiliser des groupes (tags) et la négation. Si le premier élément de votre liste utilise la négation, Spiffy commencera avec toutes les méthodes que votre classe mixin peut faire.

use EEE -mixin => qw(:tools walk !run !:sharp_tools);

Dans cet exemple, "walk" et "run" sont des méthodes que EEE peut faire, et "tools" et "sharp_tools" sont des rôles de la classe EEE. Comment la classe EEE définit-elle ces rôles ? Elle définit très simplement des méthodes appelées "_role_tools" et "_role_sharp_tools" qui retournent des listes d'autres méthodes. (Et potentiellement d'autres rôles !) Ce qui est astucieux ici, c'est que comme les rôles sont juste des méthodes, ils peuvent aussi être hérités. Prenez ça, Perl6 !

FILTRAGE

En utilisant le drapeau "-Base" au lieu de "-base", vous n'avez jamais besoin d'écrire la ligne :

my $self = shift;

Cette instruction est ajoutée à chaque sous-routine de votre classe en utilisant un filtre source. La magie est simple et rapide, donc il y a peu de pénalité de performance pour la création de code propre à la hauteur de Ruby et Python.

package Example;
use Spiffy -Base;
sub crazy {
    $self->nuts;
}
sub wacky { }
sub new() {
    bless [], shift;
}

est exactement la même chose que :

package Example;
use Spiffy -base;
use strict;use warnings;
sub crazy {my $self = shift;
    $self->nuts;
}
sub wacky {my $self = shift; }
sub new {
    bless [], shift;
}
;1;

Notez que les parenthèses vides après la sous-routine "new" l'empêchent d'avoir un $self ajouté. Notez également que le code supplémentaire est ajouté aux lignes existantes pour garantir que les numéros de ligne ne sont pas modifiés.

"-Base" active également les pragmas strict et warnings, et ajoute cette ligne agaçante '1;' à votre module.

MÉTHODES PRIVÉES

Spiffy prend désormais en charge les méthodes privées lorsque vous utilisez le mécanisme de filtre '-Base'. Il vous suffit de déclarer les subs avec le mot-clé "my", et de les appeler avec un '$' devant. Comme ceci :

package Keen;
use SomethingSpiffy -Base;
# méthode publique normale
sub swell {
    $self->$stinky;
}
# méthode lexicale privée. Non appelable depuis l'extérieur de ce fichier.
my sub stinky {
    ...
}

DÉBOGAGE SPIFFY

La fonction XXX est très utile pour le débogage car vous pouvez l'insérer presque partout, et elle affichera vos données en YAML propre. Prenez l'instruction suivante :

my @stuff = grep { /keen/ } $self->find($a, $b);

Si vous avez un problème avec cette instruction, vous pouvez la déboguer de l'une des manières suivantes :

XXX my @stuff = grep { /keen/ } $self->find($a, $b);
my @stuff = XXX grep { /keen/ } $self->find($a, $b);
my @stuff = grep { /keen/ } XXX $self->find($a, $b);
my @stuff = grep { /keen/ } $self->find(XXX $a, $b);

XXX est facile à insérer et à supprimer. C'est aussi une tradition de marquer les zones de code incertaines avec XXX. Cela rendra les dumpers de débogage faciles à repérer si vous oubliez de les retirer.

WWW et YYY sont utiles car ils affichent leurs arguments puis renvoient les arguments. De cette façon, vous pouvez les insérer à plusieurs endroits et laisser le code s'exécuter comme avant. Utilisez ZZZ lorsque vous avez besoin de mourir avec un dump YAML et une trace de pile complète.

Les fonctions de débogage sont exportées par défaut si vous utilisez l'option "-base", mais seulement si vous avez précédemment utilisé l'option "-XXX". Pour exporter les 4 fonctions, utilisez le tag d'exportation :

use SomeSpiffyModule ':XXX';

Pour forcer les fonctions de débogage à utiliser Data::Dumper au lieu de YAML :

use SomeSpiffyModule -dumper;

FONCTIONS SPIFFY

Cette section décrit les fonctions exportées par Spiffy. Les fonctions "field", "const", "stub" et "super" ne sont exportées que lorsque vous utilisez les options "-base" ou "-Base".

field
Définit des méthodes d'accesseur pour un champ de votre classe : 
package Example;
use Spiffy -Base;
field 'foo';
field bar => [];
sub lalala {
    $self->foo(42);
    push @{$self->{bar}}, $self->foo;
}

Le premier paramètre passé à "field" est le nom de l'attribut en cours de définition. Les accesseurs peuvent recevoir une valeur par défaut optionnelle. Cette valeur sera retournée si aucune valeur pour le champ n'a été définie dans l'objet.

const
const bar => 42;

La fonction "const" est similaire à <field> sauf qu'elle est immuable. Elle ne stocke pas non plus de données dans l'objet. Vous voudrez probablement toujours donner une valeur par défaut à un "const", sinon la méthode générée sera quelque peu inutile.

stub
stub 'cigar';

La fonction "stub" génère une méthode qui mourra avec un message approprié. L'idée est que les sous-classes doivent implémenter ces méthodes afin que les méthodes stubs ne soient pas appelées.

super
Si cette fonction est appelée sans arguments, elle appellera la même méthode qu'elle-même, plus haut dans l'arbre ISA, en lui passant tous les mêmes arguments. Si elle est appelée avec des arguments, elle utilisera ces arguments avec $self en premier. En d'autres termes, cela fonctionne comme vous vous y attendez. 
sub foo {
    super;             # Équivalent à $self->SUPER::foo(@_);
    super('hello');    # Équivalent à $self->SUPER::foo('hello');
    $self->bar(42);
}
sub new() {
    my $self = super;
    $self->init;
    return $self;
}

"super" ne fera simplement rien s'il n'y a pas de méthode super. Enfin, "super" fait la bonne chose dans les sous-routines AUTOLOAD.

MÉTHODES

Cette section liste toutes les méthodes dont toute sous-classe de Spiffy hérite automatiquement.

mixin
Une méthode pour mixer une classe à l'exécution. Prend les mêmes arguments que "use mixin ...". Fait de la classe cible un mixin de l'appelant. 
$self->mixin('SomeClass');
$object->mixin('SomeOtherClass' => 'some_method');
parse_arguments
Cette méthode prend une liste d'arguments et les regroupe en paires. Elle permet des arguments booléens qui peuvent ou non avoir une valeur (par défaut à 1). La méthode retourne une référence de hachage de toutes les paires en tant que clés et valeurs dans le hachage. Tous les arguments qui ne peuvent pas être mis en paire sont retournés sous forme de liste. Voici un exemple : 
sub boolean_arguments { qw(-has_spots -is_yummy) }
sub paired_arguments { qw(-name -size) }
my ($pairs, @others) = $self->parse_arguments(
    'red', 'white',
    -name => 'Ingy',
    -has_spots =>
    -size => 'large',
    'black',
    -is_yummy => 0,
);

Après cet appel, $pairs contiendra :

{
    -name => 'Ingy',
    -has_spots => 1,
    -size => 'large',
    -is_yummy => 0,
}

et @others contiendra 'red', 'white', et 'black'.

boolean_arguments
Retourne la liste des arguments qui sont reconnus comme booléens. Remplacez cette méthode pour définir votre propre liste.
paired_arguments
Retourne la liste des arguments qui sont reconnus comme appariés. Remplacez cette méthode pour définir votre propre liste.

ARGUMENTS

Lorsque vous "use"z le module Spiffy ou une de ses sous-classes, vous pouvez lui passer une liste d'arguments. Ces arguments sont analysés en utilisant la méthode "parse_arguments" décrite ci-dessus. L'argument spécial "-base" est utilisé pour faire de l'empaquetage courant une sous-classe du module Spiffy utilisé.

Les paramètres non appariés agissent comme une liste d'importation normale ; tout comme ceux utilisés avec le module Exporter.

UTILISATION DE SPIFFY AVEC BASE.PM

La manière correcte d'utiliser un module Spiffy comme classe de base est avec le paramètre "-base" dans l'instruction "use". Cela diffère des modules typiques où vous voudriez "use base".

package Something;
use Spiffy::Module -base;
use base 'NonSpiffy::Module';

Maintenant, il peut être difficile de suivre ce qui est Spiffy et ce qui ne l'est pas. Par conséquent, Spiffy a été conçu pour fonctionner avec ba

UTILISER SPIFFY AVEC BASE.PM

La base.pm (fournie avec Perl) vous permet de déclarer une classe comme étant une classe de base pour votre classe.

Dans Spiffy, vous pouvez utiliser use base pour déclarer vos classes mères. Voici un exemple.

package Mon::Module;

use Spiffy;
use base 'Vraiment::Spiffy';
use base 'Aussi::Spiffy';

# Ou vous pouvez les mélanger avec des modules qui ne sont pas Spiffy
# Spiffy s'en chargera pour vous.
package QuelqueChose;
use base 'Spiffy::Module';
use base 'NonSpiffy::Module';

"use base" est également très utile lorsque votre classe n'est pas un module réel (un fichier séparé) mais juste un paquet dans un fichier déjà chargé. "base" fonctionnera que la classe soit un module ou non, tandis que la syntaxe "-base" ne peut pas fonctionner de cette manière, car "use" essaie toujours de charger un module.

base.pm Caveats

Pour faire fonctionner Spiffy avec base.pm, une astuce a été employée. Spiffy remplace "base::import" par sa propre version. Si les modules de base ne sont pas Spiffy, Spiffy appelle le base::import original. Si les modules de base sont Spiffy, alors Spiffy fait sa propre chose.

Il y a deux caveats.

Spiffy doit être chargé en premier.
Si Spiffy n'est pas chargé et que "use base" est appelé sur un module Spiffy, Spiffy mourra avec un message utile indiquant à l'auteur de lire cette documentation. C'est parce que Spiffy a besoin de faire le remplacement de l'importation au préalable.

Si vous obtenez cette erreur, mettez simplement une instruction comme celle-ci en tête de votre code :

use Spiffy ();
Pas de mélange
"base.pm" peut prendre plusieurs arguments. Et cela fonctionne avec Spiffy tant que toutes les classes de base sont Spiffy, ou qu'elles sont toutes non-Spiffy. Si elles sont mélangées, Spiffy mourra. Dans ce cas, utilisez simplement des instructions "use base" séparées.
