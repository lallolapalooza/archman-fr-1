La classe SoNode est la classe de base pour les nœuds utilisés dans les graphes de scène.

Coin est une bibliothèque de visualisation 3D en mode rémanent (basée sur la bibliothèque OpenGL en mode immédiat). Le terme « mode rémanent » implique qu'au lieu de transmettre directement des commandes pour dessiner les éléments primitifs graphiques à la sortie vidéo, on construit des structures de données qui sont rendues par la bibliothèque « à la demande ».

Les classes de nœuds sont les « primitives » principales pour construire ces structures de données. Dans Coin, on construit des hiérarchies d'arbres composées de différents types de nœuds : nœuds de groupe (pour la structure arborescente d'autres nœuds), nœuds d'apparence (pour configurer des matériaux, des textures, etc.), nœuds de forme (pour la géométrie réelle) et nœuds d'éclairage et de position de caméra.

Une des principales préoccupations des nouveaux utilisateurs de l'API est qu'ils ne doivent pas et ne peuvent pas utiliser l'opérateur de suppression sur les nœuds, car le destructeur est protégé. Ceci est dû au fait que les instances de nœuds utilisent une technique courante pour la gestion des ressources mémoire appelée « comptage de références ». Les nœuds sont supprimés (en réalité, ils se suppriment eux-mêmes) lorsque la méthode unref() est appelée et que le compteur de références descend à zéro.

Un effet important de cela est que les classes dérivées de SoNode ne doivent pas être allouées dynamiquement statiquement, ni en mémoire de module statique, ni sur la pile de fonctions. Les classes dérivées de SoNode doivent toujours être allouées dynamiquement depuis le tas mémoire avec l'opérateur new (sinon, le schéma d'auto-destruction lors du déréférencement à 0 ne fonctionnera pas).

Les développeurs d'applications ne manipulent rarement manuellement ref() et unref() des nœuds pour des raisons d'optimisation, car les nœuds sont passés directement à SoGroup::addChild() ou So@Gui@Viewer::setSceneGraph() ou quelque chose de similaire. Ces fonctions ref() et unref() incrémentent et décrémentent respectivement le compteur de références des nœuds.

Vous devez vous assurer que les nœuds dont vous avez des références ont été préalablement ref() pour éviter qu'ils ne soient accidentellement supprimés par un appel à unref() dans le code de la bibliothèque elle-même. Si vous n'avez pas appelé manuellement ref() sur un nœud racine de haut niveau, celui-ci sera supprimé automatiquement. Ce code montre comment faire :

SoSeparator * root = new SoSeparator; // le compteur de références de root commencera à 0
root->addChild(foo_node); // le compteur de références de foo_node est incrémenté de 1
root->addChild(bar_node); // le compteur de références de bar_node est incrémenté de 1
// incrémenter le compteur de références avant de passer le nœud à setScenegraph(), pour éviter la destruction prématurée
root->ref();
myviewer->setSceneGraph(root); // le compteur de références de root est incrémenté de 1, il est maintenant de 2
// [visualisation et traitement de modules]
// myviewer libérera sa référence au nœud root, diminuant son compteur de références de 1
myviewer->setSceneGraph(NULL);
// le compteur de références de root passe de +1 à 0, et il sera supprimé de manière contrôlée
root->unref();
// éviter un pointeur nul, au cas où "root" serait réutilisé (pas vraiment nécessaire, mais bon pour détecter les erreurs tôt)
root = NULL;

Pour des informations complètes et des tutoriels de style introduction aux problèmes de l'API, consultez la section « Références et Suppression » du Chapitre 3 pour en savoir plus sur les techniques de comptage de références.

Souvent, lors de l'utilisation de la bibliothèque Coin, on s'intéresse à l'étendre. Un sujet particulièrement intéressant est la configuration de nœuds d'extension, qui sont parcourus, rendus et utilisés de la même manière que d'autres nœuds internes à la bibliothèque.

Le fichier d'en-tête Coin Inventor/nodes/SoSubNode.h comprend un certain nombre de macros utilitaires pour la construction rapide et facile de nœuds d'extension. Voici un extrait de code complet montrant comment configurer un squelette de structure pour une classe de nœud d'extension :

#include <Inventor/nodes/SoWWWInline.h>
class MyWWWInline : public SoWWWInline {
  SO_NODE_HEADER(MyWWWInline);
public:
  static void initClass(void);
  MyWWWInline(void);
protected:
  virtual ~MyWWWInline();
};
SO_NODE_SOURCE(MyWWWInline);
MyWWWInline::MyWWWInline(void)
{
  SO_NODE_CONSTRUCTOR(MyWWWInline);
}
MyWWWInline::~MyWWWInline()
{
}
void
MyWWWInline::initClass(void)
{
  SO_NODE_INIT_CLASS(MyWWWInline, SoWWWInline, "SoWWWInline");
}
int
main(int argc, char ** argv)
{
  SoDB::init();
  MyWWWInline::initClass();
  // [...]
  return 0;
}

Vous pouvez par exemple remplacer la méthode GLRender() pour que votre nouvelle classe dessine une géométrie OpenGL différente de celle de sa classe parente.

void SoNode::setOverride (const SbBool state)

Définit le drapeau de substitution.

Si ce drapeau est TRUE, les valeurs de champ de ce nœud remplaceront les valeurs de champ d'autres nœuds de la même classe lors du parcours de l'arbre de scène.

Une utilisation courante pour les nœuds de "substitution" est de les placer en haut de l'arbre comme un moyen pratique de forcer, par exemple, un style de dessin commun dans tout l'arbre.

Le drapeau de substitution n'existe pas dans le format de fichier Inventor. Cela signifie que le drapeau n'est pas persistant et doit être défini par programme. La raison d'être de ce drapeau est que les spectateurs peuvent contrôler le style de rendu des modèles 3D, il ne serait donc pas judicieux que certaines parties de certains modèles ne respectent pas le mode du spectateur.

SoNode * SoNode::copy (SbBool copyconnections = FALSE) const [virtual]

Crée une copie de ce nœud et renvoie un pointeur vers la copie.

Si ce nœud est un nœud de groupe, les enfants sont également copiés et nous renvoyons un pointeur vers la racine d'une copie complète de la sous-graphe racine ici.

Si copyconnections est TRUE, nous copions également les connexions aux champs à l'intérieur de ce nœud (et ainsi de suite pour tous les enfants et leurs enfants).

Remarque : Cette fonction a été rendue virtuelle dans Coin, ce qui n'est pas le cas dans l'API originale d'Open Inventor. Nous pouvons ramener cette méthode à non virtuelle après celle-ci, car elle a été rendue virtuelle par erreur. Veuillez ne pas écrire de code d'application qui dépend de SoNode::copy() étant virtuel.

La raison pour laquelle cette méthode ne doit pas être virtuelle est qu'il ne s'agit pas de la fonction que le programmeur d'application doit redéfinir dans les nœuds d'extension s'il a besoin d'un comportement spécial pendant une copie (comme copier la valeur des données internes non exposées sous forme de champs).

À cette fin, redéfinissez la méthode copyContents(). Votre méthode redéfinie copyContents() doit *à la fois* copier les données internes et appeler la méthode copyContents() de la classe parente pour gérer automatiquement les champs et autres données communes.

SbBool SoNode::affectsState (void ) const [virtual]

Retourne TRUE si le nœud pourrait avoir un effet sur l'état pendant le parcours.

S'il renvoie FALSE, aucune donnée dans l'état de parcours ne changera de l'état avant le parcours à l'état après le parcours. Le nœud SoSeparator renverra FALSE, car ce qu'il fait est de passer et de quitter l'état avant et après le parcours de ses enfants. Tous les nœuds SoShape renverront également FALSE, car seules les données géométriques sont envoyées au moteur de rendu, mais elles n'affectent pas l'état de rendu réel.

La méthode par défaut renvoie TRUE, dans un principe plus sûr que "mieux vaut prévenir que guérir" (car elle est basée sur un principe meilleur).

Detailed Description

The SoNode class is the base class for all objects that can be part of an Inventor scene graph.

The scene graph is a directed acyclic graph (DAG) of nodes, where each node represents an object or an action to be performed during rendering or traversal. The scene graph is traversed from root to leaf during rendering. Each node can have children, which are accessed via an SoNodeList.

Nodes are divided into several categories:

  • Group nodes (subclasses of SoGroup) organize other nodes and define the structure of the scene graph.

  • Primitive nodes (subclasses of SoPrimitive) represent geometric objects like cubes, spheres, lines, etc.

  • Appearance nodes define the visual properties of primitives, such as color, shading, textures, etc. (e.g., SoMaterial, SoDrawStyle).

  • Transformation nodes modify the coordinate system for subsequent nodes (SoTransform, SoTranslation, etc.).

  • Light nodes define light sources for rendering (SoLight, SoPointLight, etc.).

  • Information nodes provide information about the rendering process or scene graph structure (SoLevelOfDetail, SoSwitch).

  • Callback nodes allow the application to register callbacks for events or traversals (SoEventCallback, SoNodeSensor).

All nodes are derived from SoBase and have a unique type ID (SoType) that can be used for runtime type checking and registration.

Nodes can have fields (SoField) that store their data and can be accessed and modified by the application. Fields are essential for defining the behavior and appearance of nodes.

The scene graph is managed by an SoNodekit (or SoAction) object, which traverses the graph and performs operations like rendering, picking, or searching.
