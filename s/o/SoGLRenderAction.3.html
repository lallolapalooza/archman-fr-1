Description détaillée

La classe SoGLRenderAction rend le graphe de scène avec des appels OpenGL.

Appliquer cette méthode à un nœud racine pour un graphe de scène, un chemin ou une liste de chemins, rendra toute la géométrie contenue dans cette instance dans la fenêtre OpenGL actuelle.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Documentation des énumérations des membres

enum SoGLRenderAction::TransparencyType

Divers réglages pour la manière de rendre les objets transparents dans la scène. Certains réglages offriront un rendu plus rapide, tandis que d'autres vous donneront un rendu de meilleure qualité.

Notez que le rendu correct de *plusieurs* objets transparents échoue souvent, car pour être correct à 100 %, tous les polygones doivent être rendus dans l'ordre trié, et les polygones ne peuvent pas s'intersecter. Dans un graphe de scène dynamique, il est souvent impossible de garantir qu'aucun polygone ne s'intersecte, et trouver un algorithme qui trie correctement les polygones pour tous les cas possibles est très difficile et prend beaucoup de temps.

Le mode de transparence de la plus haute qualité dans l'Open Inventor original de SGI / TGS est SoGLRenderAction::SORTED_OBJECT_BLEND, où tous les objets transparents sont rendus dans l'ordre trié lors d'une passe de rendu après tous les objets opaques. Cependant, ce mode ne trie pas les polygones, et si vous avez un objet où un polygone A est derrière un autre polygone B, la transparence ne sera correcte que si A est rendu avant B. Pour d'autres angles de caméra, où B est derrière A, la transparence ne sera pas correcte.

Dans Coin, nous avons un nouveau mode de transparence qui résout certains de ces problèmes : SoGLRenderAction::SORTED_OBJECT_SORTED_TRIANGLE_BLEND. En plus de trier les objets, tous les polygones à l'intérieur de chaque objet sont également triés de l'arrière vers l'avant lors du rendu. Mais, si vous avez des objets qui s'intersectent et/ou des polygones qui s'intersectent, même ce mode de transparence échouera. De plus, en raison du tri des polygones, ce mode de transparence est assez lent. Il est cependant possible d'accélérer les choses en utilisant le nœud SoTransparencyType, qui vous permet de définir différents modes de transparence pour différentes parties du graphe de scène. Si vous n'avez que quelques objets pour lesquels vous avez besoin de trier les polygones, vous pouvez utiliser SoGLRenderAction::SORTED_OBJECT_SORTED_TRIANGLE_BLEND pour ceux-ci, et par exemple SoGLRenderAction::SORTED_OBJECT_BLEND pour tous les autres objets transparents.

Le mode de transparence de la plus haute qualité dans Coin est SoGLRenderAction::SORTED_LAYERS_BLEND. C'est également le seul mode qui remplace tous les autres modes du graphe de scène.

(Une note importante concernant ce mode : nous avons eu des rapports d'utilisateurs indiquant que certains pilotes OpenGL - potentiellement certains systèmes Mac OS X - dégradent considérablement les performances de rendu. Soyez donc prudent et testez votre application sur une grande variété de systèmes d'exécution lorsque vous utilisez SoGLRenderAction::SORTED_LAYERS_BLEND.)

SoTransparencyType

Énumérateur

SCREEN_DOOR
Les triangles transparents sont rendus avec un motif de tramage. C'est un mode de transparence rapide (sur la plupart des cartes graphiques) mais pas de très haute qualité.

Une caractéristique particulière de ce mode est que vous êtes assuré qu'il rend toujours les parties transparentes de la scène correctement par rapport à l'ordre de profondeur interne des objets / polygones, ce qui n'est pas le cas pour les autres modes de transparence.

Les polygones rendus avec uniquement des textures transparentes ne sont pas affichés comme transparents lors de l'utilisation de ce mode. La raison est que le mode SoGLRenderAction::SCREEN_DOOR fonctionne sur les polygones, pas sur les pixels. Pour rendre des polygones avec un motif de tramage, un nœud matériel doit être inséré dans le graphe de scène avec son champ de transparence défini.

ADD
Les objets transparents sont rendus en utilisant un mélange alpha additif. Le mélange additif est probablement surtout utilisé pour créer des effets de transparence spéciaux. La nouvelle couleur du pixel est calculée comme la couleur du pixel actuel plus la couleur du pixel source multipliée par la valeur alpha du pixel source.
DELAYED_ADD
Les objets transparents sont rendus en utilisant un mélange alpha additif, dans une deuxième passe de rendu avec les mises à jour du tampon de profondeur désactivées.
SORTED_OBJECT_ADD
Les objets transparents sont rendus en utilisant un mélange alpha additif. Les objets opaques sont rendus en premier, et les objets transparents sont rendus de l'arrière vers l'avant avec les mises à jour du z-buffer désactivées.
BLEND
Les objets transparents sont rendus en utilisant un mélange alpha multiplicatif.

Le mélange alpha multiplicatif est le type de mélange le plus souvent utilisé pour rendre les objets transparents. La nouvelle valeur du pixel est calculée comme l'ancienne couleur du pixel multipliée par un moins la valeur alpha source, plus la couleur du pixel source multipliée par la valeur alpha source.

Nous vous recommandons d'utiliser ce mode de transparence si vous n'avez qu'un seul objet transparent dans votre scène, et que vous savez qu'il sera rendu après les objets opaques.

DELAYED_BLEND
Les objets transparents sont rendus en utilisant un mélange alpha multiplicatif, dans une deuxième passe de rendu avec les mises à jour du tampon de profondeur désactivées.

Utilisez ce type de transparence lorsque vous avez un objet transparent, ou plusieurs objets transparents dont vous savez qu'ils ne se chevaucheront jamais (lorsqu'ils sont projetés à l'écran). Puisque les objets transparents sont rendus après les objets opaques, vous n'aurez pas à vous soucier de placer les objets transparents à la fin de votre graphe de scène. Ce ne sera pas aussi rapide que le type de transparence SoGLRenderAction::BLEND, bien sûr, puisque le graphe de scène est parcouru deux fois.

SORTED_OBJECT_BLEND
Les objets transparents sont rendus en utilisant un mélange alpha multiplicatif, Les objets opaques sont rendus en premier, et les objets transparents sont rendus de l'arrière vers l'avant avec les mises à jour du z-buffer désactivées.

Utilisez ce mode de transparence lorsque vous avez plusieurs objets transparents dont vous savez qu'ils pourraient se chevaucher (lorsqu'ils sont projetés à l'écran). Cette méthode nécessitera 1 + nombre_d_objets_transparents passes de rendu. La traversée de chemin est utilisée lors du rendu des objets transparents, bien sûr, mais cela peut toujours être lent si vous avez beaucoup de changements d'état avant votre objet transparent. Lorsque vous utilisez ce mode, nous recommandons de placer les objets transparents aussi tôt que possible dans le graphe de scène pour minimiser la surcharge de traversée.

SORTED_OBJECT_SORTED_TRIANGLE_ADD
Ce type de transparence est une extension de Coin par rapport à l'API originale d'Open Inventor de SGI.

Les objets transparents sont rendus de l'arrière vers l'avant, et les triangles de chaque objet sont triés de l'arrière vers l'avant avant le rendu.

Voir la description de SoGLRenderAction::SORTED_OBJECT_SORTED_TRIANGLE_BLEND pour plus d'informations sur ce type de transparence.

SORTED_OBJECT_SORTED_TRIANGLE_BLEND
Ce type de transparence est une extension de Coin par rapport à l'API originale d'Open Inventor de SGI.

Les objets transparents sont rendus de l'arrière vers l'avant, et les triangles de chaque objet sont triés de l'arrière vers l'avant avant le rendu.

Utilisez ce type de transparence lorsque vous avez un (ou plusieurs) objet(s) transparent(s) où vous savez que les triangles peuvent se chevaucher à l'intérieur de l'objet. Ce type de transparence peut être très lent si vous avez un objet avec beaucoup de triangles, car tous les triangles doivent être triés avant le rendu, et une boucle de rendu non optimisée est utilisée lors du rendu. Les lignes et les points ne sont pas triés avant le rendu. Ils sont rendus comme dans le mode de transparence normal SoGLRenderAction::SORTED_OBJECT_BLEND.

Veuillez noter que ce mode de transparence ne garantit pas un rendu de transparence « correct ». Il est presque impossible de trouver un algorithme qui trie correctement les triangles dans tous les cas, et les triangles qui s'intersectent ne sont pas gérés. De plus, puisque chaque objet est traité séparément, deux objets qui s'intersectent entraîneront une transparence incorrecte.

NONE
Ce type de transparence est une extension de Coin par rapport à l'API Open Inventor.

Désactive la transparence pour les objets, même si la transparence est définie à l'aide d'un nœud SoMaterial.

Depuis

Coin 1.0
SORTED_LAYERS_BLEND
Ce type de transparence est une extension de Coin par rapport à l'API originale d'Open Inventor de SGI.

En utilisant ce type de transparence, le SoGLRenderAction rendra correctement les objets transparents normaux et qui s'intersectent, indépendamment de l'ordre de rendu. C'est le seul mode de rendu de type transparence qui garantit de le faire.

Ce mode est différent de tous les autres modes en ce sens qu'il remplace les nœuds SoTransparencyType dans le graphe de scène ; tous les objets sont dessinés en utilisant SoGLRenderAction::SORTED_LAYERS_BLEND.

Il existe actuellement deux chemins de code distincts pour ce mode. Les deux chemins sont fortement basés sur des extensions OpenGL. La première méthode est basée sur des extensions qui ne sont disponibles que sur les chipsets NVIDIA (GeForce3 et supérieur, sauf GeForce4 MX). Ces extensions sont GL_NV_texture_shader, GL_NV_texture_rectangle ou GL_EXT_texture_rectangle, GL_NV_register_combiners, GL_ARB_shadow et GL_ARB_depth_texture. Veuillez noter que ce type de transparence occupe les quatre unités de texture de la carte NVIDIA pour toutes les passes de rendu, sauf la première. Les surfaces texturées ne seront donc texturées que si elles ne sont pas occultées par une autre surface transparente.

La deuxième méthode utilise l'extension GL_ARB_fragment_program. Cette extension est actuellement prise en charge par la famille GeForceFX et la Radeon 9500 et

au-dessus. Cette technique est plus rapide que la méthode NVIDIA pure. La méthode de programme de fragment sera automatiquement choisie si possible. Veuillez noter qu'il faut faire attention à ne pas placer le plan proche trop près de la caméra en raison du manque de contrôle de précision des nombres à virgule flottante dans les programmes de fragment. Faire ainsi peut entraîner une perte de précision sur les bords et une apparence "dentelée" de la géométrie transparente.

La définition de la variable d'environnement COIN_SORTED_LAYERS_USE_NVIDIA_RC à '1' forcera l'utilisation de l'ancien chemin de code au lieu du dernier, même s'il est disponible.

Un contexte de rendu avec un tampon de profondeur de 24 bits ou plus et un canal alpha de 8 bits doit être le contexte de rendu actuel pour que ce mode de fusion soit réellement activé. Si la toile de rendu actuelle ne possède pas ces propriétés, Coin utilisera un mode de gestion de la transparence plus simple. Si vous utilisez l'une des bibliothèques de liaison du système de fenêtrage fournies par Kongsberg Oil & Gas Technologies, par exemple SoXt, SoQt ou SoWin, vous devrez l'activer explicitement dans votre visionneuse. Voir la documentation de l'API de la méthode setAlphaChannel() de SoXtGLWidget, SoQtGLWidget ou SoWinGLWidget.

La détection de si oui ou non le mode SoGLRenderAction::SORTED_LAYERS_BLEND peut être utilisé sera effectuée automatiquement par les internes de Coin. Si une ou plusieurs des conditions nécessaires listées ci-dessus sont indisponibles, SoGLRenderAction::SORTED_OBJECT_BLEND sera utilisé à la place du type de transparence.

Pour pouvoir rendre une transparence correcte indépendamment de l'ordre des objets, il faut rendre en plusieurs passes. Cette technique est basée sur le depth-peeling qui enlève des couches de profondeur à chaque passe successive. Le nombre de passes est donc une indication de la profondeur à laquelle les surfaces transparentes seront rendues avec transparence dans la scène. Un nombre plus élevé entraînera une fréquence d'images plus faible mais une qualité supérieure pour les scènes avec beaucoup de surfaces transparentes. Le nombre par défaut de passes est '4'. Ce nombre peut être spécifié en utilisant SoGLRenderAction::setSortedLayersNumPasses() ou en laissant la variable d'environnement COIN_NUM_SORTED_LAYERS_PASSES ou OIV_NUM_SORTED_LAYERS_PASSES spécifier le nombre de passes.

Une présentation plus détaillée de l'algorithme est écrite par Cass Everitt chez NVIDIA ;

"Interactive Order-Independent Transparency" https://www.nvidia.com/en-us/drivers/Interactive-Order-Transparency/

enum SoGLRenderAction::TransparentDelayedObjectRenderType

Énumère les types de rendu des objets transparents.

Énumérateur

ONE_PASS
Rendu normal en une seule passe. Cela peut causer des artefacts pour les objets non solides.
NONSOLID_SEPARATE_BACKFACE_PASS
Les objets non solides sont gérés dans une passe de rendu supplémentaire. Les faces arrière sont rendues dans la première passe, et les faces avant dans la seconde passe.

void SoGLRenderAction::setAbortCallback (SoGLRenderAbortCB *const func, void *const userdata)

Définit la fonction de rappel d'abandon. La fonction de rappel d'abandon est appelée par l'action pour chaque nœud pendant le parcours afin de vérifier les conditions d'abandon.

La méthode de rappel doit retourner l'une des valeurs de l'énumération SoGLRenderAction::AbortCode pour indiquer comment l'action doit se poursuivre.

Étant donné que la fonction de rappel SoGLRenderAbortCB du client n'a qu'un seul argument void* pour les données utilisateur, il faut faire un travail supplémentaire pour savoir pour quel nœud le rappel a été effectué. On peut le faire, par exemple, en passant le pointeur de l'action comme données utilisateur, puis en appelant la méthode SoGLRenderAction::getCurPath(). La queue du chemin sera alors le dernier nœud parcouru. Comme ceci :

// Mettre en place pour pouvoir abandonner ou intervenir autrement sur le parcours
// de rendu :
myRenderAction->setAbortCallback(MyRenderCallback, myRenderAction);
// [...]
SoGLRenderAction::AbortCode
MyRenderCallback(void * userdata)
{
  SoGLRenderAction * action = (SoGLRenderAction *)userdata;
  SoNode * lastnode = action->getCurPath()->getTail();
  // [...]
  return SoGLRenderAction::CONTINUE;
}

void SoGLRenderAction::addPreRenderCallback (SoGLPreRenderCB * func, void * userdata)

Ajoute un rappel qui est appelé juste avant de commencer la traversée de l'arbre de scène. Toutes les initialisations GL nécessaires sont effectuées ensuite (par exemple, la fenêtre d'affichage est correctement définie), et ce rappel peut être utile pour, par exemple, effacer la fenêtre d'affichage avant le rendu, ou dessiner un bitmap en arrière-plan avant le rendu, etc.

Le rappel n'est appelé qu'une seule fois (avant la première passe de rendu) lorsque le rendu multi-passe est activé.

Note : SoSceneManager ajoute généralement un rappel pour effacer les tampons GL dans SoSceneManager::render(). Par conséquent, si vous avez l'intention de dessiner une image dans le tampon de couleur à l'aide de ce rappel, vous devez vous assurer que le gestionnaire de scène n'efface pas le tampon. Cela peut être fait en appelant SoSceneManager::render() avec les deux arguments FALSE, ou, si vous utilisez l'une de nos bibliothèques d'interface graphique (SoXt/SoQt/SoGtk/SoWin), appelez setClearBeforeRender() sur l'observateur.

Cette méthode est une extension par rapport à l'API Open Inventor.

void SoGLRenderAction::setSortedObjectOrderStrategy (const SortedObjectOrderStrategy strategy, SoGLSortedObjectOrderCB * cb = NULL, void * closure = NULL)

Définit la stratégie utilisée pour trier les objets transparents.

La stratégie CUSTOM_CALLBACK permet à l'utilisateur de fournir un rappel qui est appelé pour chaque forme transparente. Cette stratégie peut être utilisée si les stratégies de tri intégrées ne sont pas suffisantes.

Le rappel doit retourner une valeur flottante à utiliser pour le tri des objets Coin. Cette valeur flottante est interprétée comme une distance à la caméra, et les objets avec des valeurs plus élevées sont triés derrière ceux avec des valeurs plus faibles.

Le rappel fournit l'instance SoGLRenderAction et le chemin actuel de l'objet peut être trouvé en utilisant SoAction::getCurPath().
