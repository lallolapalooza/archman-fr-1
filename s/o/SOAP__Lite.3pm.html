NOM

SOAP::Lite - Toolkit Perl pour les services Web

DESCRIPTION

SOAP::Lite est une collection de modules Perl qui fournit une interface simple et légère au protocole SOAP (Simple Object Access Protocol) côté client et côté serveur.

AVERTISSEMENT DE VERSION PERL

Depuis la version SOAP::Lite 1.05, les versions de Perl antérieures à 5.8 ne seront plus prises en charge.

La version 0.71 de SOAP::Lite sera la dernière à fonctionner sous Perl 5.005.

Les futures versions de SOAP::Lite nécessiteront au moins Perl 5.6.0.

Si vous n'avez pas eu le temps de mettre à jour votre Perl, vous devriez envisager de le faire maintenant.

MÉTHODES

Toutes les méthodes d'accès renvoient la valeur actuelle lorsqu'elles sont appelées sans paramètre, et renvoient l'objet référencé lorsqu'une nouvelle valeur lui est passée. Cela permet de chaîner les appels de définition d'attributs.

new( optionnel )
$client = SOAP::Lite->new(proxy => $endpoint)

Constructeur. Bon nombre des méthodes d'accès définies ici peuvent être initialisées lors de la création de l'objet en fournissant leur nom comme clé, suivi de la valeur souhaitée. L'exemple fournit la valeur pour l'élément proxy du client.

transport( objet de transport optionnel )
$transp = $client->transport( );

Obtient ou définit l'objet de transport utilisé pour envoyer/recevoir des messages SOAP.

Voir SOAP::Transport pour plus de détails.

serializer( objet de sérialiseur optionnel )
$serial = $client->serializer( )

Obtient ou définit l'objet de sérialiseur utilisé pour créer des messages XML.

Voir SOAP::Serializer pour plus de détails.

packager( objet de packager optionnel )
$packager = $client->packager( )

Fournit un accès à l'objet "SOAP::Packager" que le client utilise pour gérer l'utilisation des pièces jointes. Le packager par défaut est un packager MIME, mais aucun formatage MIME ne sera effectué si aucune pièce à envoyer n'est spécifiée.

Voir aussi : SOAP::Packager.

proxy( endpoint, arguments supplémentaires optionnels )
$client->proxy('http://soap.xml.info/ endPoint');

Le proxy est le serveur ou le point de terminaison auquel le client se connectera. Cette méthode permet de définir le point de terminaison, ainsi que toutes les informations supplémentaires dont l'objet de transport a besoin lors de l'envoi de la requête.

Cette méthode est en fait un alias de la méthode proxy de l'objet SOAP::Transport. C'est la même chose que d'écrire :

$client->transport( )->proxy(...arguments);

Des arguments supplémentaires peuvent être passés à proxy() - voir ci-dessous.

compress_threshold
Voir COMPRESSION dans HTTP::Transport.
Toutes les options d'initialisation de la couche de transport
Les options pour HTTP(S) sont les mêmes que celles de la méthode new() de LWP::UserAgent.

Une option courante consiste à instancier HTTP::Cookies et à la passer comme option cookie_jar :

my $cookie_jar = HTTP::Cookies->new()
$client->proxy('http://www.example.org/webservice',
   cookie_jar => $cookie_jar,
);

Par exemple, si vous souhaitez définir le délai d'attente HTTP pour un client SOAP::Lite à 5 secondes, utilisez le code suivant :

my $soap = SOAP::Lite
 ->uri($uri)
 ->proxy($proxyUrl, timeout => 5 );

Voir LWP::UserAgent.

endpoint( nouvelle adresse de point de terminaison optionnelle )
$client->endpoint('http://soap.xml.info/ newPoint')

Il est préférable de définir un nouveau point de terminaison sans le travail supplémentaire d'analyse de la nouvelle adresse pour les informations de protocole et de vérification que le code de support est chargé et disponible. Cette méthode permet à l'appelant de modifier le point de terminaison auquel le client est actuellement configuré pour se connecter, sans recharger le code de transport pertinent. Remarque : La méthode proxy doit avoir été appelée avant cette méthode.

service( URL du service )
$client->service('http://svc.perl.org/Svc.wsdl');

"SOAP::Lite" offre un certain support pour la création de stubs de méthodes à partir de descriptions de services. Actuellement, seul le support WSDL est pris en charge. Cette méthode charge le schéma WSDL spécifié et l'utilise comme base pour générer des stubs.

outputxml( booléen )
$client->outputxml('true');

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

">Lorsque défini sur une valeur vraie, le XML brut est renvoyé par l'appel à une méthode distante.

La valeur par défaut est de renvoyer un objet SOAP::SOM (faux).

autotype(booléen)
$client->autotype(0);

Cette méthode est un raccourci pour :

$client->serializer->autotype(booléen);

Par défaut, le sérialiseur essaie de déduire automatiquement les types pour les données envoyées dans un message. Définir une valeur fausse avec cette méthode désactive ce comportement.

readable(booléen)
$client->readable(1);

Cette méthode est un raccourci pour :

$client->serializer->readable(booléen);

Lorsque ceci est utilisé pour définir une valeur vraie pour cette propriété, le XML généré envoyé au point d'extrémité contient des caractères supplémentaires (espaces et nouvelles lignes) ajoutés pour rendre le XML plus lisible par des yeux humains (vraisemblablement pour le débogage). La valeur par défaut est de ne pas envoyer de caractères supplémentaires.

headerattr(hash référence d'attributs)
$obj->headerattr({ attr1 => 'value' });

Permet de définir des attributs arbitraires sur l'objet d'en-tête. Gardez à l'esprit que
tous les attributs non nativement connus de SOAP doivent être qualifiés par un espace de noms. Si vous utilisez $session->call ($method, $callData, $callHeader), SOAP::Lite sérialise les informations comme

<soap:Envelope>
  <soap:Header>
    <userId>xxxxx</userId>
    <password>yyyyy</password>
  </soap:Header>
  <soap:Body>
    <myMethod xmlns="http://www.someuri.com">
      <foo />
    </myMethod>
  </soap:Body>
</soap:Envelope>

Les attributs, donnés à headerattr, sont placés dans l'En-tête comme

<soap:Header attr1="value">
bodyattr(hash référence d'attributs)
$obj->bodyattr({ attr1 => 'value' });

Permet de définir des attributs arbitraires sur l'objet du corps. Gardez à l'esprit que
tous les attributs non nativement connus de SOAP doivent être qualifiés par un espace de noms. Voir headerattr.

default_ns($uri)
Définit l'espace de noms par défaut pour la requête à l'URI spécifié. Ceci remplace toute déclaration d'espace de noms précédente qui aurait pu être définie en utilisant un appel précédent à ns() ou default_ns(). Définir l'espace de noms par défaut fait que les éléments sont sérialisés sans préfixe d'espace de noms, comme ceci : 
<soap:Envelope>
  <soap:Body>
    <myMethod xmlns="http://www.someuri.com">
      <foo />
    </myMethod>
  </soap:Body>
</soap:Envelope>

Certains services Web .NET ont été rapportés comme nécessitant cet idiome d'espace de noms XML.

ns($uri,$prefix=indéfini)
Définit l'URI de l'espace de noms et éventuellement le préfixe de l'espace de noms pour la requête aux valeurs spécifiées. Ceci remplace toute déclaration d'espace de noms précédente qui aurait pu être définie en utilisant un appel précédent à ns() ou default_ns().

Si un préfixe n'est pas spécifié, un sera généré automatiquement pour vous. Définir l'espace de noms fait que les éléments sont sérialisés avec un préfixe d'espace de noms déclaré, comme ceci :

<soap:Envelope>
  <soap:Body>
    <my:myMethod xmlns:my="http://www.someuri.com">
      <my:foo />
    </my:myMethod>
  </soap:Body>
</soap:Envelope>
use_prefix(booléen)
Obsolète. Utilisez les méthodes ns() et "default_ns" décrites ci-dessus.

Raccourci pour "serializer->use_prefix()". Ceci vous permet d'activer/désactiver l'utilisation d'un préfixe d'espace de noms pour les enfants de l'élément /Envelope/Body. La valeur par défaut est 'true'.

Lorsque use_prefix est défini sur 'true', le XML sérialisé ressemblera à ceci :

<SOAP-ENV:Envelope ...attributs omis>
  <SOAP-ENV:Body>
    <namesp1:mymethod xmlns:namesp1="urn:MyURI" />
  </SOAP-ENV:Body>
</SOAP-ENV:Envelope>

Lorsque use_prefix est défini sur 'false', le XML sérialisé ressemblera à ceci :

<SOAP-ENV:Envelope ...attributs omis>
  <SOAP-ENV:Body>
    <mymethod xmlns="urn:MyURI" />
  </SOAP-ENV:Body>
</SOAP-ENV:Envelope>

Certains services Web .NET ont été rapportés comme nécessitant cet idiome d'espace de noms XML.

soapversion(optionnel valeur)
$client->soapversion('1.2');

Si aucun paramètre n'est donné, renvoie la version actuelle de SOAP utilisée par l'objet client pour encoder les requêtes. Si un paramètre est donné, la méthode tente de le définir comme la version de SOAP utilisée.

La valeur doit être 1.1 ou 1.2.

envprefix(QName)
$client->envprefix('env');

Cette méthode est un raccourci pour :

$client->serializer->envprefix(QName);

Obtient ou définit le préfixe d'espace de noms pour l'espace de noms SOAP. La valeur par défaut est SOAP.

Le préfixe lui-même n'a pas de signification, mais les applications peuvent souhaiter en choisir un explicitement pour désigner différentes versions de SOAP ou similaires.

encprefix(QName)
$client->encprefix('enc');

Cette méthode est un raccourci pour :

$client->serializer->encprefix(QName);

Obtient ou définit le préfixe d'espace de noms pour l'espace de noms des règles d'encodage. La valeur par défaut est SOAP-ENC.

Bien que cela puisse sembler une opération inutile de définir une valeur qui n'est pas pertinente pour le message, comme les étiquettes d'espace de noms pour les URN d'enveloppe et d'encodage, la possibilité de définir ces étiquettes explicitement peut s'avérer une aide précieuse pour distinguer et déboguer les messages côté serveur des opérations.

encoding(encodage URN)
$client->encoding($soap_12_encoding_URN);

Cette méthode est un raccourci pour :

$client->serializer->encoding(args);

Alors que la méthode précédente traitait de l'étiquette utilisée pour les attributs liés au schéma d'encodage SOAP, cette méthode définit réellement l'URN à spécifier comme schéma d'encodage pour le message. La valeur par défaut est de spécifier l'encodage pour SOAP 1.1, donc c'est pratique pour les applications qui doivent encoder selon les règles de SOAP 1.2.

typelookup
$client->typelookup;

Cette méthode est un raccourci pour :

$client->serializer->typelookup;

Donne à l'application accès à la table de recherche de types de l'objet sérialiseur. Voir la section sur SOAP::Serializer.

uri(spécificateur de service)
Obsolète - la sous-routine "uri" est obsolète afin de fournir une convention de nommage plus intuitive pour les sous-routines qui définissent les espaces de noms. À l'avenir, vous devrez utiliser soit les sous-routines ns() ou default_ns() au lieu de uri(). 
$client->uri($service_uri);

Cette méthode est un raccourci pour :

$client->serializer->uri(service);

L'URI associé à cet accesseur sur un objet client est le spécificateur de service pour la requête, souvent encodé pour les requêtes basées sur HTTP comme en-tête SOAPAction. Bien que les noms puissent sembler confus, cette méthode ne spécifie pas le point d'extrémité lui-même. Dans la plupart des circonstances, l'"uri" fait référence à l'espace de noms utilisé pour la requête.

Souvent, la valeur peut ressembler à une URL valide. Malgré cela, elle n'a pas besoin de pointer vers une ressource existante (et souvent ne le fait pas). Cette méthode définit et récupère cette valeur de l'objet. Notez qu'aucun code de transport n'est déclenché par cela car cela n'a pas d'effet direct sur le transport de l'objet.

multirefinplace(booléen)
$client->multirefinplace(1);

Cette méthode est un raccourci pour :

$client->serializer->multirefinplace(booléen);

Contrôle comment le sérialiseur gère les valeurs qui ont plusieurs références à elles. Rappelez-vous des chapitres SOAP précédents qu'une valeur peut être étiquetée avec un identifiant, puis référencée à plusieurs endroits. Lorsque c'est le cas pour une valeur, le sérialiseur place par défaut l'élément de données vers le haut du message, juste après la balise d'ouverture de la spécification de méthode. Il est sérialisé comme une entité autonome avec un ID qui est ensuite référencé aux endroits pertinents plus tard. Si cette méthode est utilisée pour définir une valeur vraie, le comportement est différent. Lorsque l'attribut multirefinplace est vrai, les données sont sérialisées à la première occurrence qui les référence, plutôt que comme un élément distinct plus haut dans le corps. C'est plus compact mais peut être plus difficile à lire ou à suivre dans un environnement de débogage.

parts( TABLEAU )
Utilisé pour spécifier un tableau d'entités MIME à joindre au message SOAP transmis. Les pièces jointes retournées dans une réponse peuvent être accessibles par SOAP::SOM::parts().
self
$ref = SOAP::Lite->self;

Renvoie une référence d'objet vers l'objet global par défaut que le package "SOAP::Lite" maintient. Ceci est l'objet qui traite plusieurs des arguments lorsqu'ils sont fournis sur la ligne d'utilisation.

La méthode suivante n'est pas un style d'accesseur o

f méthode, mais ni ne correspond-elle au groupe qui la suit immédiatement :

call(arguments)
$client->call($method => @arguments);

Comme cela a été illustré dans les chapitres précédents, les objets clients "SOAP::Lite" peuvent gérer les appels distants avec dispatch automatique en utilisant certaines des fonctionnalités les plus élaborées de Perl. call est utilisé lorsque l'application souhaite un plus grand contrôle sur les détails de l'appel lui-même. La méthode peut être construite à partir d'un objet SOAP::Data, afin de permettre un contrôle total de l'espace de noms associé à la balise, ainsi que d'autres attributs comme l'encodage. Ceci est également important pour appeler des méthodes qui contiennent des caractères non autorisés dans les noms de fonctions Perl, tels que A.B.C.

Les quatre méthodes suivantes utilisées dans la classe "SOAP::Lite" sont destinées à gérer les types d'événements qui peuvent survenir pendant le cycle de vie du message. Chacune d'elles configure un rappel pour l'événement en question :

on_action(callback)
$client->on_action(sub { qq("$_[0]") });

Déclenché lorsque l'objet de transport configure l'en-tête SOAPAction pour un appel basé sur HTTP. Par défaut, l'en-tête est défini sur la chaîne, uri#méthode, où URI est la valeur définie par la méthode uri décrite précédemment, et méthode est le nom de la méthode appelée. Lorsqu'elle est appelée, la routine référencée (ou la fermeture, si elle est spécifiée comme dans l'exemple) reçoit deux arguments, uri et méthode, dans cet ordre.

Les services Web .NET attendent généralement "/" comme séparateur pour "uri" et "méthode". Pour modifier le comportement de SOAP::Lite afin d'utiliser uri/méthode comme en-tête SOAPAction, utilisez le code suivant :

$client->on_action( sub { join '/', @_ } );
on_fault(callback)
$client->on_fault(sub { popup_dialog($_[1]) });

Déclenché lorsqu'un appel de méthode résulte en une réponse d'erreur (fault) du serveur. Lorsqu'elle est appelée, la liste des arguments contient d'abord l'objet client lui-même, suivi de l'objet qui encapsule l'erreur. Dans l'exemple, l'objet d'erreur est passé (sans l'objet client) à une fonction GUI hypothétique qui présente une boîte de dialogue d'erreur avec le texte de l'erreur extrait de l'objet (ce qui sera traité ultérieurement dans les méthodes SOAP::SOM).

on_nonserialized(callback)
$client->on_nonserialized(sub { die "$_[0]?!?" });

Occasionnellement, le sérialiseur peut recevoir des données qu'il ne peut pas transformer en XML compatible SOAP ; par exemple, si un bug du programme résulte en une référence de code ou quelque chose de similaire passé en tant que paramètre d'un appel de méthode. Lorsque cela se produit, ce rappel est activé, avec un argument. Cet argument est l'élément de données qui n'a pas pu être compris. Ce sera le seul argument. Si la routine retourne, la valeur de retour est insérée dans le message comme sérialisation. Généralement, une erreur est appropriée, et ce rappel permet de contrôler la signalisation de cette erreur.

on_debug(callback)
$client->on_debug(sub { print @_ });

Obsolète. Utilisez les installations globales +debug et +trace décrites dans SOAP::Trace

Notez que cette méthode ne fonctionnera pas comme prévu : Au lieu d'affecter le comportement de débogage de l'objet sur lequel elle est appelée, elle affectera globalement le comportement de débogage de tous les objets de cette classe.

ÉCRIRE UN CLIENT SOAP

Ce chapitre vous guide dans l'écriture d'un client SOAP par l'exemple.

Le service SOAP à accéder est une variation simple du programme bien connu "hello world". Il accepte deux paramètres, un nom et un prénom, et retourne "Bonjour $prénom $nom".

Nous utiliserons "Martin Kutter" comme nom pour l'appel, donc toutes les variantes afficheront le message suivant en cas de succès :

Bonjour Martin Kutter !

Styles de messages SOAP

Il existe trois variantes courantes (et une moins courante) des messages SOAP.

Celles-ci abordent le style du message (paramètres positionnels vs documents de message spécifiés) et l'encodage (tel quel vs typé).

Les différents styles de messages sont :

  • rpc/encoded

    Paramètres typés et positionnels. Largement utilisés dans les langages de script. Le type des arguments est inclus dans le message. Les tableaux et autres peuvent être encodés selon les règles d'encodage SOAP (ou d'autres).

  • rpc/literal

    Paramètres positionnels tel quel. Le type des arguments est défini par une interface pré-échangée.

  • document/encoded

    Message spécifié avec des éléments typés. Rarement utilisé.

  • document/literal

    Message spécifié avec des éléments tel quel. La spécification du message et les types d'éléments sont définis par une interface pré-échangée.

Depuis 2008, document/literal est devenu la variante dominante des messages SOAP. rpc/literal et rpc/encoded sont toujours utilisés, principalement avec les langages de script, tandis que document/encoded est très peu utilisé.

Vous verrez des clients pour les variantes SOAP rpc/encoded et document/literal dans cette section.

Implémentations d'exemple

RPC/ENCODED

Rpc/encoded est le plus populaire auprès des langages de script comme perl, php et python sans utiliser de WSDL. Les descriptions de méthodes habituelles ressemblent à ceci :

Méthode : sayHello(string, string)
Paramètres :
   name: string
   givenName: string

Une telle description signifie généralement que vous pouvez appeler une méthode nommée "sayHello" avec deux paramètres positionnels, "name" et "givenName", qui sont tous deux des chaînes de caractères.

Le message correspondant à cette description ressemble un peu à cela :

<sayHello xmlns="urn:HelloWorld">
  <s-gensym01 xsi:type="xsd:string">Kutter</s-gensym01>
  <s-gensym02 xsi:type="xsd:string">Martin</s-gensym02>
</sayHello>

N'importe quels noms de balises XML peuvent être utilisés à la place des "s-gensym01" - les paramètres sont positionnels, les noms de balises n'ont pas de signification.

Un client produisant un tel appel est implémenté comme suit :

use SOAP::Lite;
my $soap = SOAP::Lite->new( proxy => 'http://localhost:81/soap-wsdl-test/helloworld.pl');
$soap->default_ns('urn:HelloWorld');
my $som = $soap->call('sayHello', 'Kutter', 'Martin');
die $som->faultstring if ($som->fault);
print $som->result, "\n";

Vous pouvez bien sûr utiliser aussi une ligne de commande...

Parfois, les interfaces rpc/encoded sont décrites avec des définitions WSDL. Un WSDL acceptant des paramètres "nommés" avec rpc/encoded ressemble à cela :

<definitions xmlns:soap="http://schemas.xmlsoap.org/wsdl/soap/"
  xmlns:s="http://www.w3.org/2001/XMLSchema"
  xmlns:s0="urn:HelloWorld"
  targetNamespace="urn:HelloWorld"
  xmlns="http://schemas.xmlsoap.org/wsdl/">
  <types>
    <s:schema targetNamespace="urn:HelloWorld">
    </s:schema>
  </types>
  <message name="sayHello">
    <part name="name" type="s:string" />
    <part name="givenName" type="s:string" />
  </message>
  <message name="sayHelloResponse">
    <part name="sayHelloResult" type="s:string" />
  </message>
  <portType name="Service1Soap">
    <operation name="sayHello">
      <input message="s0:sayHello" />
      <output message="s0:sayHelloResponse" />
    </operation>
  </portType>
  <binding name="Service1Soap" type="s0:Service1Soap">
    <soap:binding transport="http://schemas.xmlsoap.org/soap/http"
        style="rpc" />
    <operation name="sayHello">
      <soap:operation soapAction="urn:HelloWorld#sayHello"/>
      <input>
        <soap:body use="encoded"
          encodingStyle="http://schemas.xmlsoap.org/soap/encoding/"/>
      </input>
      <output>
        <soap:body use="encoded"
          encodingStyle="http://schemas.xmlsoap.org/soap/encoding/"/>
      </output>
    </operation>
  </binding>
  <service name="HelloWorld">
    <port name="HelloWorldSoap" binding="s0:Service1Soap">
      <soap:address location="http://localhost:81/soap-wsdl-test/helloworld.pl" />
    </port>
  </service>
</definitions>

Le message correspondant à ce schéma ressemble à ceci :

<sayHello xmlns="urn:HelloWorld">
  <name xsi:type="xsd:string">Kutter</name>
  <givenName xsi:type="xsd:string">Martin</givenName>
</sayHello>

Un client de service Web utilisant ce schéma ressemble à ceci :

use SOAP::Lite;
my $soap = SOAP::Lite->service("file:say_hello_rpcenc.wsdl");
eval { my $result = $soap->sayHello('Kutter', 'Martin'); };
if ($@) {
    die $@;
}
print $som->result();

Vous pouvez bien sûr également utiliser la ligne de commande suivante :

perl -MSOAP::Lite -e 'print SOAP::Lite->service("file:say_hello_rpcenc.wsdl")\
  ->sayHello('Kutter', 'Martin'), "\n";'

Un client de service Web (sans description de service) ressemble à ceci.

use SOAP::Lite;
my $soap = SOAP::Lite->new( proxy => 'http://localhost:81/soap-wsdl-test/helloworld.pl');
$soap->default_ns('urn:HelloWorld');
my $som = $soap->call('sayHello',
   SOAP::Data->name('name')->value('Kutter'),
   SOAP::Data->name('givenName')->value('Martin')
);
die $som->faultstring if ($som->fault);
print $som->result, "\n";

RPC/LITERAL

Les services Web SOAP utilisant l'encodage de message document/literal sont généralement décrits par une définition de service Web. Notre service Web a la description WSDL suivante :

<definitions xmlns:soap="http://schemas.xmlsoap.org/wsdl/soap/"
  xmlns:s="http://w
<?xml version="1.0" encoding="utf-8"?> <definitions xmlns:soap="http://schemas.xmlsoap.org/wsdl/soap/" xmlns:s="http://www.w3.org/2001/XMLSchema" xmlns:s0="urn:HelloWorld" targetNamespace="urn:HelloWorld" xmlns="http://schemas.xmlsoap.org/wsdl/"> <types> <s:schema targetNamespace="urn:HelloWorld"> <s:complexType name="sayHello"> <s:sequence> <s:element minOccurs="0" maxOccurs="1" name="name" type="s:string" /> <s:element minOccurs="0" maxOccurs="1" name="givenName" type="s:string" nillable="1" /> </s:sequence> </s:complexType> <s:complexType name="sayHelloResponse"> <s:sequence> <s:element minOccurs="0" maxOccurs="1" name="sayHelloResult" type="s:string" /> </s:sequence> </s:complexType> </s:schema> </types> <message name="sayHello"> <part name="parameters" type="s0:sayHello" /> </message> <message name="sayHelloResponse"> <part name="parameters" type="s0:sayHelloResponse" /> </message> <portType name="Service1Soap"> <operation name="sayHello"> <input message="s0:sayHello" /> <output message="s0:sayHelloResponse" /> </operation> </portType> <binding name="Service1Soap" type="s0:Service1Soap"> <soap:binding transport="http://schemas.xmlsoap.org/soap/http" style="rpc" /> <operation name="sayHello"> <soap:operation soapAction="urn:HelloWorld#sayHello"/> <input> <soap:body use="literal" namespace="urn:HelloWorld"/> </input> <output> <soap:body use="literal" namespace="urn:HelloWorld"/> </output> </operation> </binding> <service name="HelloWorld"> <port name="HelloWorldSoap" binding="s0:Service1Soap"> <soap:address location="http://localhost:80//helloworld.pl" /> </port> </service> </definitions> ```

Le message XML (à l'intérieur de l'enveloppe SOAP) ressemble à ceci :

```xml <ns0:sayHello xmlns:ns0="urn:HelloWorld"> <parameters> <name>Kutter</name> <givenName>Martin</givenName> </parameters> </ns0:sayHello> <sayHelloResponse xmlns:ns0="urn:HelloWorld"> <parameters> <sayHelloResult>Hello Martin Kutter!</sayHelloResult> </parameters> </sayHelloResponse> ```

Voici l'implémentation SOAP::Lite pour le client du service Web :

```perl use SOAP::Lite +trace; my $soap = SOAP::Lite->new( proxy => 'http://localhost:80/helloworld.pl'); $soap->on_action( sub { "urn:HelloWorld#sayHello" }); $soap->autotype(0)->readable(1); $soap->default_ns('urn:HelloWorld'); my $som = $soap->call('sayHello', SOAP::Data->name('parameters')->value( \SOAP::Data->value([ SOAP::Data->name('name')->value( 'Kutter' ), SOAP::Data->name('givenName')->value('Martin'), ])) ); die $som->fault->{ faultstring } if ($som->fault); print $som->result, "\n"; ```

DOCUMENT/LITERAL

Les services Web SOAP utilisant le codage de message document/literal sont généralement décrits par une définition de service Web. Notre service Web a la description WSDL suivante :

```xml <definitions xmlns:soap="http://schemas.xmlsoap.org/wsdl/soap/" xmlns:s="http://www.w3.org/2001/XMLSchema" xmlns:s0="urn:HelloWorld" targetNamespace="urn:HelloWorld" xmlns="http://schemas.xmlsoap.org/wsdl/"> <types> <s:schema targetNamespace="urn:HelloWorld"> <s:element name="sayHello"> <s:complexType> <s:sequence> <s:element minOccurs="0" maxOccurs="1" name="name" type="s:string" /> <s:element minOccurs="0" maxOccurs="1" name="givenName" type="s:string" nillable="1" /> </s:sequence> </s:complexType> </s:element> <s:element name="sayHelloResponse"> <s:complexType> <s:sequence> <s:element minOccurs="0" maxOccurs="1" name="sayHelloResult" type="s:string" /> </s:sequence> </s:complexType> </s:element> </types> <message name="sayHelloSoapIn"> <part name="parameters" element="s0:sayHello" /> </message> <message name="sayHelloSoapOut"> <part name="parameters" element="s0:sayHelloResponse" /> </message> <portType name="Service1Soap"> <operation name="sayHello"> <input message="s0:sayHelloSoapIn" /> <output message="s0:sayHelloSoapOut" /> </operation> </portType> <binding name="Service1Soap" type="s0:Service1Soap"> <soap:binding transport="http://schemas.xmlsoap.org/soap/http" style="document" /> <operation name="sayHello"> <soap:operation soapAction="urn:HelloWorld#sayHello"/> <input> <soap:body use="literal" /> </input> <output> <soap:body use="literal" /> </output> </operation> </binding> <service name="HelloWorld"> <port name="HelloWorldSoap" binding="s0:Service1Soap"> <soap:address location="http://localhost:80//helloworld.pl" /> </port> </service> </definitions> ```

Le message XML (à l'intérieur de l'enveloppe SOAP) ressemble à ceci :

```xml <sayHello xmlns="urn:HelloWorld"> <name>Kutter</name> <givenName>Martin</givenName> </sayHello> <sayHelloResponse> <sayHelloResult>Hello Martin Kutter!</sayHelloResult> </sayHelloResponse> ```

Vous pouvez appeler ce service Web avec le code client suivant :

```perl use SOAP::Lite; my $soap = SOAP::Lite->new( proxy => 'http://localhost:80/helloworld.pl'); $soap->on_action( sub { "urn:HelloWorld#sayHello" }); $soap->autotype(0); $soap->default_ns('urn:HelloWorld'); my $som = $soap->call("sayHello", SOAP::Data->name('name')->value( 'Kutter' ), SOAP::Data->name('givenName')->value('Martin'), ); die $som->fault->{ faultstring } if ($som->fault); print $som->result, "\n"; ```

Différences entre les implémentations

Vous avez peut-être remarqué qu'il y a peu de différences entre l'implémentation rpc/encoded, rpc/literal et celle de document/literal. En fait, du point de vue de SOAP::Lite, les seules différences entre rpc/literal et document/literal sont que les paramètres sont toujours nommés.

Dans notre exemple, la variante rpc/encoded utilisait déjà des paramètres nommés (en utilisant deux messages), il n'y a donc aucune différence.

Vous avez peut-être remarqué l'idiome quelque peu étrange pour passer une liste de paramètres nommés dans l'exemple rpc/literal :

my $som = $soap->call('sayHello', SOAP::Data->name('parameters')->value(
   \SOAP::Data->value([
       SOAP::Data->name('name')->value( 'Kutter' ),
       SOAP::Data->name('givenName')->value('Martin'),
   ]))
);

Alors que SOAP::Data offre un contrôle total sur le XML généré, le passage de structures de type hash nécessite un codage supplémentaire.

FONCTIONNALITÉS

PIÈCES JOINTES

"SOAP::Lite" prend en charge la spécification SOAP with Attachments. Actuellement, SOAP::Lite ne prend en charge que les pièces jointes basées sur MIME. Les pièces jointes basées sur DIME ne sont pas encore entièrement fonctionnelles.

EXEMPLES

Client envoyant une pièce jointe

Les clients "SOAP::Lite" peuvent spécifier les pièces jointes à envoyer avec une requête en utilisant la méthode SOAP::Lite::parts(), qui prend en argument un TABLEAU d'"MIME::Entity".

use SOAP::Lite;
use MIME::Entity;
my $ent = build MIME::Entity
  Type        => "image/gif",
  Encoding    => "base64",
  Path        => "somefile.gif",
  Filename    => "saveme.gif",
  Disposition => "attachment";
my $som = SOAP::Lite
  ->uri($SOME_NAMESPACE)
  ->parts([ $ent ])
  ->proxy($SOME_HOST)
  ->some_method(SOAP::Data->name("foo" => "bar"));

Client récupérant une pièce jointe

Un client accédant aux pièces jointes retournées dans une réponse en utilisant l'accesseur SOAP::SOM::parts().

use SOAP::Lite;
use MIME::Entity;
my $soap = SOAP::Lite
  ->uri($NS)
  ->proxy($HOST);
my $som = $soap->foo();
foreach my $part (${$som->parts}) {
  print $part->stringify;
}

Serveur recevant une pièce jointe

Les serveurs, comme les clients, utilisent le module SOAP::SOM pour accéder aux pièces jointes qui leur sont transmises.

package Attachment;
use SOAP::Lite;
use MIME::Entity;
use strict;
use vars qw(@ISA);
@ISA = qw(SOAP::Server::Parameters);
sub someMethod {
  my $self = shift;
  my $envelope = pop;
  foreach my $part (@{$envelope->parts}) {
    print "AttachmentService: attachment found! (".ref($part).")\n";
  }
  # do something
}

Serveur répondant avec une pièce jointe

Les serveurs souhaitant retourner une pièce jointe au client appelant doivent simplement retourner des objets "MIME::Entity" en plus des éléments SOAP::Data, ou de toute autre donnée destinée à la réponse.

package Attachment;
use SOAP::Lite;
use MIME::Entity;
use strict;
use vars qw(@ISA);
@ISA = qw(SOAP::Server::Parameters);
sub someMethod {
  my $self = shift;
  my $envelope = pop;
  my $ent = build MIME::Entity
  'Id'          => "<1234>",
  'Type'        => "text/xml",
  'Path'        => "some.xml",
  'Filename'    => "some.xml",
  'Disposition' => "attachment";
  return SOAP::Data->name("foo" => "blah blah blah"),$ent;
}

CONFIGURATIONS PAR DÉFAUT

Bien que cette fonctionnalité puisse ressembler à autodispatch, elles n'ont (presque) rien en commun. Cette capacité vous permet de spécifier des configurations par défaut afin que tous les objets créés après ce moment soient initialisés avec les bonnes valeurs par défaut.

Si vous souhaitez fournir des configurations proxy() ou uri() communes à tous les objets "SOAP::Lite" de votre application, vous pouvez le faire comme suit:

use SOAP::Lite
  proxy => 'http://localhost/cgi-bin/soap.cgi',
  uri => 'http://my.own.com/My/Examples';
my $soap1 = new SOAP::Lite; # obtiendra le même proxy()/uri() que ci-dessus
print $soap1->getStateName(1)->result;
my $soap2 = SOAP::Lite->new; # la même chose que ci-dessus
print $soap2->getStateName(2)->result;
# ou vous pouvez remplacer toute configuration que vous souhaitez
my $soap3 = SOAP:: Lite->proxy('http://localhost/');
print $soap3->getStateName(1)->result;

Toute propriété "SOAP::Lite" peut être propagée ainsi. Les modifications apportées aux copies d'objets n'affecteront pas les configurations globales et vous pouvez toujours modifier les configurations globales en appelant "SOAP::Lite->self", qui renvoie une référence à l'objet global. Le paramètre fourni mettra à jour cet objet et vous pouvez même le définir sur "undef":

SOAP:: Lite->self(undef);

La syntaxe "use SOAP:: Lite" vous permet également de spécifier des gestionnaires par défaut pour votre code. Si vous avez différents objets "SOAP::Lite" et que vous souhaitez partager le même on_action() (ou on_fault() pour cet argument), vous pouvez spécifier on_action() lors de l'initialisation pour chaque objet, mais vous pouvez également faire:

use SOAP:: Lite
  on_action => sub {sprintf '%s#%s', @_};

et ce gestionnaire sera le gestionnaire par défaut pour tous vos objets "SOAP". Vous pouvez le remplacer si vous spécifiez un gestionnaire pour un objet particulier. Voir t/*.t pour un exemple de gestionnaire on_fault().

Gardez à l'esprit que, puisque "use ..." est exécuté au moment de la compilation, toutes les instructions "use" seront exécutées avant l'exécution du script, ce qui peut entraîner des résultats inattendus. Considérez le code:

use SOAP:: Lite proxy => 'http://localhost/';
print SOAP:: Lite->getStateName(1)->result;
use SOAP:: Lite proxy => 'http://localhost/cgi-bin/soap.cgi';
print SOAP:: Lite->getStateName(1)->result;

Les deux appels SOAP seront dirigés vers 'http://localhost/cgi-bin/soap.cgi'. Si vous souhaitez exécuter "use" au moment de l'exécution, placez-le dans un "eval":

eval "use SOAP:: Lite proxy => 'http://localhost/cgi-bin/soap.cgi'; 1" or die;

Ou alternativement:

SOAP:: Lite->self->proxy('http://localhost/cgi-bin/soap.cgi');

DÉFINITION DE LA TAILLE MAXIMALE DES MESSAGES

Une fonctionnalité de "SOAP:: Lite" est la capacité de contrôler la taille maximale d'un message qu'un serveur "SOAP:: Lite" autorisera à traiter. Pour contrôler cette fonctionnalité, définissez simplement $SOAP::Constants::MAX_CONTENT_SIZE dans votre code comme suit:

use SOAP:: Transport::HTTP;
use MIME:: Entity;
$SOAP::Constants::MAX_CONTENT_SIZE = 10000;
SOAP:: Transport::HTTP::CGI
  ->dispatch_to('TemperatureService')
  ->handle;

PARAMÈTRES D'ENTRÉE/SORTIE, DE SORTIE ET AUTOBINDING

"SOAP:: Lite" vous donne accès à tous les paramètres (entrée/sortie et sortie) et effectue également des travaux supplémentaires pour vous. Considérez l'exemple suivant:

<mehodResponse>
  <res1>name1</res1>
  <res2>name2</res2>
  <res3>name3</res3>
</mehodResponse>

Dans ce cas:

$result = $r->result; # vous donne 'name1'
$paramout1 = $r->paramsout;      # vous donne 'name2', en raison du contexte scalaire
$paramout1 = ($r->paramsout)[0]; # vous donne aussi 'name2'
$paramout2 = ($r->paramsout)[1]; # vous donne 'name3'

ou

@paramsout = $r->paramsout; # vous donne un ARRAY de paramètres de sortie
$paramout1 = $paramsout[0]; # vous donne 'res2', le même que ($r->paramsout)[0]
$paramout2 = $paramsout[1]; # vous donne 'res3', le même que ($r->paramsout)[1]

Généralement, si le serveur renvoie "return (1,2,3)" vous obtiendrez 1 comme résultat et 2 et 3 comme paramètres de sortie.

Si le serveur renvoie "return [1,2,3]" vous obtiendrez une référence à un ARRAY de résultats de result() et "undef" de paramsout().

Les résultats peuvent être des structures arbitrairement complexes: ils peuvent être des références à des tableaux, des objets, n'importe quoi et être renvoyés par result(). Si un seul paramètre est renvoyé, paramsout() renverra "undef".

De plus, si vous avez un paramètre de sortie portant la même signature (nom + type) que dans les paramètres d'entrée, ce paramètre sera automatiquement mappé à votre entrée. Par exemple:

Code du serveur:

sub mymethod {
  shift; # référence à l'objet/classe
  my $param1 = shift;
  my $param2 = SOAP:: Data->name('myparam' => shift() * 2);
  return $param1, $param2;
}

Code du client:

$a = 10;
$b = SOAP:: Data->name('myparam' => 12);
$result = $soap->mymethod($a, $b);

Après cela, "$result == 10 et $b->value == 24"! Magique? Un peu.

L'autobinding vous offre cela. Il fonctionnera également avec des objets avec une différence: vous n'avez pas besoin de vous soucier du nom et du type du paramètre objet. Considérez l'exemple "PingPong" (examples/My/PingPong.pm et examples/pingpong.pl):

Code du serveur:

package My::PingPong;
sub new {
  my $self = shift;
  my $class = ref($self) || $self;
  bless {_num=>shift} => $class;
}
sub next {
  my $self = shift;
  $self->{_num}++;
}

Code du client:

use SOAP:: Lite +autodispatch =>
  uri => 'urn:',
  proxy => 'http://localhost/';
my $p = My::PingPong->new(10); # $p->{_num} est 10 maintenant, objet réel renvoyé
print $p->next, "\n";          # $p->{_num} est 11 maintenant!, objet auto-lié

DÉPLOIEMENT STATIQUE ET DYNAMIQUE

Examinons le processus de déploiement. Lorsque vous concevez votre serveur SOAP, vous pouvez envisager deux types de déploiement: statique et dynamique. Pour les deux, vous devrez spécifier "MODULE", "MODULE::method", "method" ou "PATH/" lorsque vous utilisez "use" avec le module "SOAP:: Lite". La différence entre le déploiement statique et dynamique est qu'en cas de déploiement dynamique, tout module qui n'est pas présent sera chargé en temps réel. Voir la section "SÉCURITÉ" pour une description plus détaillée.

Lorsque vous déployez un serveur SOAP de manière statique, vous devez connaître tous les modules qui gèrent les requêtes SOAP à l'avance.

Le déploiement dynamique permet d'étendre l'interface de votre serveur SOAP en installant un autre module dans le chemin de dispatch_to (voir ci-dessous).

EXEMPLE DE DÉPLOIEMENT STATIQUE

use SOAP:: Transport::HTTP;
use My::Examples;           # le module est préchargé
SOAP:: Transport::HTTP::CGI
   # le module déployé doit être ici ou le client recevra 'accès refusé'
  -> dispatch_to('My::Examples')
  -> handle;

Pour le déploiement statique, vous devez spécifier directement le nom du module.

Vous devriez également utiliser le binding statique lorsque vous avez plusieurs classes différentes dans le même fichier et que vous souhaitez les rendre disponibles pour les appels SOAP.

EXEMPLE DE DÉPLOIEMENT DYNAMIQUE

use SOAP:: Transport::HTTP;
# nom inconnu, le module est chargé par défaut
SOAP:: Transport::HTTP::CGI
  # le module déployé doit être ici ou le client recevra 'accès refusé'
  -> dispatch_to('/Your/Path/To/Deployed/Modules', 'My::Examples')
  -> handle;

Pour le déploiement dynamique, vous pouvez spécifier le nom directement (auquel cas il sera appelé "require" sans restriction) ou indirectement avec un CHEMIN. Dans ce cas, le seul chemin disponible sera le CHEMIN spécifié dans la méthode dispatch_to(). Pour plus d'informations sur la gestion de cette situation, voir la section "SÉCURITÉ".

RÉSUMÉ

dispatch_to(
  # déploiement dynamique qui permet d'accéder à tous les modules dans un répertoire spécifique
  PATH/TO/MODULES
  # 1. spécifie le répertoire
  # -- ET --
  # 2. donne accès à tous les modules dans ce répertoire sans limites
  # déploiement statique qui permet d'accéder à toutes les méthodes d'un module spécifique
  MODULE
  # 1. donne accès à un module spécifique (toutes les méthodes disponibles)
  # PRÉREQUIS:
  #    le module doit être chargé manuellement (par exemple avec 'use ...')
  #    -- OU --
  #    vous pouvez toujours le spécifier dans PATH/TO/MODULES
  # déploiement statique qui permet d'accéder à une méthode spécifique uniquement
  MODULE::method
  # idem que MODULE, mais donne accès à une seule méthode spécifique, il n'y a donc pas beaucoup d'intérêt à utiliser à la fois MODULE et MODULE::method pour le même MODULE
);

En plus de cela, "SOAP:: Lite" prend également en charge une syntaxe expérimentale qui permet de lier une URL spécifique ou un SOAPAction à une CLASSE/MODULE ou un objet.

Par exemple:

dispatch_with({
  URI => MODULE,        # 'http://www.soaplite.com/' => 'My::Class',
  SOAPAction => MODULE, # 'http://www.soaplite.com/method' => 'Another::Class',
  URI => object,        # 'http://www.soaplite.com/obj' => My::Class->new,
})

"URI" est vérifié avant "SOAPAction". Vous pouvez utiliser à la fois dispatch_to() et dispatch_with() sur le même serveur, mais notez que dispatch_with() a un ordre de priorité plus élevé. dispatch_to() n'est vérifié qu'après que "URI" et "SOAPAction" ont été vérifiés.

Voir également: EXEMPLE D'UTILISATION DE Apache::Registry, "SÉCURITÉ"

COMPRESSION

La compression des messages SOAP peut être configurée de manière similaire. La syntaxe "use SOAP::Lite" vous permet également de spécifier des configurations de compression pour votre code.

COMPRESSION

"SOAP::Lite" vous offre la possibilité d'activer la compression transparente sur le réseau. La compression peut être activée en spécifiant une valeur seuil (en kilo-octets) pour la compression côté client et côté serveur :

Note : La compression ne fonctionne actuellement qu'avec les serveurs et clients basés sur HTTP.

Code client

print SOAP::Lite
  ->uri('http://localhost/My/Parameters')
  ->proxy('http://localhost/', options => {compress_threshold => 10000})
  ->echo(1 x 10000)
  ->result;

Code serveur

my $server = SOAP::Transport::HTTP::CGI
  ->dispatch_to('My::Parameters')
  ->options({compress_threshold => 10000})
  ->handle;

Pour plus d'informations, voir COMPRESSION dans HTTP::Transport.

SÉCURITÉ

Pour des raisons de sécurité, le chemin d'accès existant pour les modules Perl (@INC) sera désactivé une fois que vous aurez choisi le déploiement dynamique et spécifié votre propre "PATH/". Si vous souhaitez accéder à d'autres modules dans votre package inclus, vous avez plusieurs options :

1.
Passer au lien statique : 
use MODULE;
$server->dispatch_to('MODULE');

Ce qui peut également être utile lorsque vous souhaitez importer quelque chose de spécifique des modules déployés :

use MODULE qw(import_list);
2.
Changer "use" en "require". Le chemin n'est disponible que pendant la phase d'initialisation. Il est à nouveau disponible pendant l'exécution. Par conséquent, si vous utilisez "require" quelque part dans votre package, cela fonctionnera.
3.
Encapsuler "use" dans un bloc "eval" : 
eval 'use MODULE qw(import_list)'; die if $@;
4.
Définir votre chemin d'inclusion dans votre package, puis spécifier "use". N'oubliez pas de placer @INC dans un bloc "BEGIN{}", sinon cela ne fonctionnera pas. Par exemple, 
BEGIN { @INC = qw(my_directory); use MODULE }

INTEROPÉRABILITÉ

Client Microsoft .NET avec serveur SOAP::Lite

Pour utiliser un client .NET avec un serveur SOAP::Lite, assurez-vous d'utiliser des noms complètement qualifiés pour vos valeurs de retour. Par exemple :

return SOAP::Data->name('myname')
                 ->type('string')
                 ->uri($MY_NAMESPACE)
                 ->value($output);

Voir également le commentaire sur l'encodage par défaut dans les services Web .NET ci-dessous.

Client SOAP::Lite avec un serveur .NET

Si vous rencontrez des problèmes lors de l'utilisation d'un client SOAP::Lite pour appeler un service Web .NET, il est recommandé de vérifier ou de respecter toutes les recommandations suivantes :

Déclarer une soapAction appropriée dans votre appel
Par exemple, utilisez "on_action( sub { 'http://www.myuri.com/WebService.aspx#someMethod'; } )".
Désactiver la définition du jeu de caractères dans l'en-tête Content-type
Certains utilisateurs ont déclaré que Microsoft .NET préfère que la valeur de l'en-tête Content-type soit exclusivement un mimetype, mais SOAP::Lite spécifie un jeu de caractères en plus du mimetype. Cela entraîne une erreur similaire à : 
Server found request content type to be 'text/xml; charset=utf-8',
but expected 'text/xml'

Pour désactiver ce comportement, spécifiez le code suivant :

use SOAP::Lite;
$SOAP::Constants::DO_NOT_USE_CHARSET = 1;
# Le reste de votre code
Utiliser un nom complètement qualifié pour les paramètres de méthode
Par exemple, le code suivant est préférable : 
SOAP::Data->name(Query  => 'biztalk')
          ->uri('http://tempuri.org/')

Contrairement à :

SOAP::Data->name('Query'  => 'biztalk')
Placer la méthode dans l'espace de noms par défaut
Par exemple, le code suivant est préférable : 
my $method = SOAP::Data->name('add')
                       ->attr({xmlns => 'http://tempuri.org/'});
my @rc = $soap->call($method => @parms)->result;

Contrairement à :

my @rc = $soap->call(add => @parms)->result;
# -- OU --
my @rc = $soap->add(@parms)->result;
Désactiver l'utilisation de préfixes d'espaces de noms explicites
Certains utilisateurs ont signalé que .NET ne parse tout simplement pas les messages qui utilisent des préfixes d'espaces de noms sur autre chose que les éléments SOAP eux-mêmes. Par exemple, le XML suivant ne serait pas analysé : 
<SOAP-ENV:Envelope ...attributs omis>
  <SOAP-ENV:Body>
    <namesp1:mymethod xmlns:namesp1="urn:MyURI" />
  </SOAP-ENV:Body>
</SOAP-ENV:Envelope>

SOAP::Lite permet aux utilisateurs de désactiver l'utilisation d'espaces de noms explicites via la méthode use_prefix(). Par exemple, le code suivant :

$som = SOAP::Lite->uri('urn:MyURI')
                 ->proxy($HOST)
                 ->use_prefix(0)
                 ->myMethod();

Produira le XML suivant, plus acceptable par .NET :

<SOAP-ENV:Envelope ...attributs omis>
  <SOAP-ENV:Body>
    <mymethod xmlns="urn:MyURI" />
  </SOAP-ENV:Body>
</SOAP-ENV:Envelope>

SOAP::Lite utilise l'encodage SOAP (section 5 de la spécification soap 1.1), et la valeur par défaut pour les services Web .NET est d'utiliser un encodage littéral. Ainsi, les éléments de la requête sont non qualifiés, mais votre service s'attend à ce qu'ils soient qualifiés. Les services Web .Net ont un moyen de changer le format de message attendu, ce qui devrait vous permettre de faire fonctionner votre interopérabilité. En haut de votre classe dans le fichier asmx, ajoutez cet attribut (pour la Beta 1) :

[SoapService(Style=SoapServiceStyle.RPC)]

Une autre source a dit que cela pourrait être cet attribut (pour la Beta 2) :

[SoapRpcService]

Le texte complet du service Web peut ressembler à ceci :

<%@ WebService Language="C#" Class="Test" %>
using System;
using System.Web.Services;
using System.Xml.Serialization;
[SoapService(Style=SoapServiceStyle.RPC)]
public class Test : WebService {
  [WebMethod]
  public int add(int a, int b) {
    return a + b;
  }
}

Un autre exemple de Kirill Gavrylyuk <kirillg@microsoft.com> :

"Vous pouvez insérer l'attribut [SoapRpcService()] sur votre classe ou au niveau de l'opération".

 <%@ WebService Language=CS class="DataType.StringTest"%>
 namespace DataType {
   using System;
   using System.Web.Services;
   using System.Web.Services.Protocols;
   using System.Web.Services.Description;
  [SoapRpcService()]
  public class StringTest: WebService {
    [WebMethod]
    [SoapRpcMethod()]
    public string RetString(string x) {
      return(x);
    }
  }
}

Exemple de Yann Christensen <yannc@microsoft.com> :

using System;
using System.Web.Services;
using System.Web.Services.Protocols;
namespace Currency {
  [WebService(Namespace="http://www.yourdomain.com/example")]
  [SoapRpcService]
  public class Exchange {
    [WebMethod]
    public double getRate(String country, String country2) {
      return 122.69;
    }
  }
}

DÉPANNAGE

SOAP::Lite sérialise "18373" comme un entier, mais je veux que ce soit une chaîne !
SOAP::Lite devine les types de données à partir du contenu fourni, en utilisant un ensemble de règles de bon sens. Ces règles ne sont pas fiables à 100 %, bien qu'elles conviennent à la plupart des données.

Vous pouvez forcer le type en passant un objet SOAP::Data avec un type spécifié :

my $proxy = SOAP::Lite->proxy('http://www.example.org/soapservice');
my $som = $proxy->myMethod(
    SOAP::Data->name('foo')->value(12345)->type('string')
);

Vous pouvez également modifier la priorité des règles de devinette de type. Notez que cela implique de modifier les internes de SOAP::Lite - cela pourrait ne pas fonctionner comme prévu dans les versions futures.

L'exemple ci-dessus force tout à être encodé comme une chaîne (c'est parce que le test de chaîne est normalement le dernier et retourne toujours vrai) :

my @list = qw(-1 45 foo bar 3838);
my $proxy = SOAP::Lite->uri($uri)->proxy($proxyUrl);
my $lookup = $proxy->serializer->typelookup;
$lookup->{string}->[0] = 0;
$proxy->serializer->typelookup($lookup);
$proxy->myMethod(\@list);

Voir SOAP::Serializer pour plus de détails.

"+autodispatch" ne fonctionne pas dans Perl 5.8
Il y a un bug dans la fonctionnalité "UNIVERSAL::AUTOLOAD" de Perl 5.8 qui empêche la fonctionnalité "+autodispatch" de fonctionner correctement. La solution consiste à utiliser "dispatch_from" à la place. Là où vous feriez normalement quelque chose comme ceci : 
use Some::Module;
use SOAP::Lite +autodispatch =>
    uri => 'urn:Foo'
    proxy => 'http://...';

Vous feriez quelque chose comme ceci :

use SOAP::Lite dispatch_from(Some::Module) =>
    uri => 'urn:Foo'
    proxy => 'http://...';

Can't load '/usr/local/lib/perl5/site_perl/.../XML/Parser/Expat/Expat.so'

<IfModule mod_env.c>

L'utilisation de "SOAP::Lite" (ou XML::Parser::Expat) en combinaison avec mod_perl provoque des segfaults aléatoires dans les processus httpd. Pour corriger cela, essayez de configurer Apache avec ce qui suit : 
RULE_EXPAT=no

Si vous utilisez Apache 1.3.20 et versions ultérieures, essayez de configurer Apache avec l'option suivante :

./configure --disable-rule=EXPAT

Le parseur SAX Java ne parvient pas à analyser le message composé par SOAP::Lite
Dans certains cas, les messages SOAP créés par "SOAP::Lite" peuvent ne pas être analysés correctement par un analyseur XML SAX2/Java. Ceci est dû à un bug connu dans "org.xml.sax.helpers.ParserAdapter". Ce bug se manifeste lorsqu'un attribut dans un élément XML apparaît avant la déclaration d'espace de noms XML dont il dépend. Cependant, selon la spécification XML, l'ordre de ces attributs n'est pas significatif.

PERFORMANCE

Traitement des fragments encodés en XML
"SOAP::Lite" est basé sur XML::Parser, qui est essentiellement un wrapper autour du parseur expat de James Clark. Le comportement d'Expat pour l'analyse des chaînes encodées en XML peut affecter le traitement des messages qui contiennent beaucoup d'entités encodées, comme des fragments XML, encodés sous forme de chaînes. Pour fournir des détails de bas niveau, le parseur appellera le rappel char() pour chaque partie du flux traité, mais individuellement pour chaque entité ou nouvelle ligne traitée. Cela peut entraîner de nombreux appels et des dépenses supplémentaires du gestionnaire de mémoire, même pour de petits messages. En revanche, les messages XML encodés en base64Binary n'ont pas ce problème et la différence de temps de traitement peut être significative. Pour une chaîne encodée en XML comportant environ 20 lignes et 30 balises, le nombre d'appels pourrait être d'environ 100 au lieu d'un pour la même chaîne encodée en base64Binary.

Comme il s'agit d'une fonctionnalité du parseur, il n'y a PAS de correction pour ce comportement (faites-moi savoir si vous en trouvez une), d'autant plus que vous devez analyser le message que vous avez déjà reçu (et que vous ne pouvez pas contrôler le contenu de ce message). Cependant, si vous êtes responsable des deux extrémités du traitement, vous pouvez passer l'encodage à base64 côté expéditeur. Cela fonctionnera certainement avec SOAP::Lite et cela pourrait fonctionner avec d'autres toolkits/implémentations, mais évidemment je ne peux pas le garantir.

Si vous souhaitez encoder une chaîne spécifique en base64, faites simplement "SOAP::Data->type(base64 => $string)" côté client ou côté serveur. Si vous souhaitez modifier le comportement pour une instance spécifique de SOAP::Lite, vous pouvez créer une sous-classe de "SOAP::Serializer", remplacer la méthode as_string() qui est responsable de l'encodage des chaînes (regardez as_base64Binary()) et spécifier la nouvelle classe de sérialiseur pour votre objet SOAP::Lite avec :

my $soap = new SOAP::Lite
  serializer => My::Serializer->new,
  ..... autres paramètres

ou côté serveur :

my $server = new SOAP::Transport::HTTP::Daemon # ou tout autre serveur
  serializer => My::Serializer->new,
  ..... autres paramètres

Si vous souhaitez modifier ce comportement pour toutes les instances de SOAP::Lite, remplacez simplement la méthode as_string() par as_base64Binary() quelque part dans votre code après "use SOAP::Lite" et avant le traitement/envoi réel :

*SOAP::Serializer::as_string = \&SOAP::XMLSchema2001::Serializer::as_base64Binary;

Attention, les deux dernières méthodes affecteront toutes les chaînes et les convertiront en base64 encodé. Cela ne fait aucune différence pour SOAP::Lite, mais cela pourrait faire une différence pour d'autres toolkits.

BOGUES ET LIMITATIONS

  • Aucun support pour les tableaux multidimensionnels, partiellement transmis et épars (cependant, les tableaux de tableaux sont pris en charge, ainsi que toute autre structure de données, et vous pouvez ajouter votre propre implémentation avec SOAP::Data).
  • Support limité pour le schéma WSDL.
  • XML::Parser::Lite repose sur le support Unicode dans Perl et ne fait pas de décodage d'entités.
  • Support limité pour les attributs mustUnderstand et Actor.
