Description détaillée

La classe SoGroup est un nœud qui gère d'autres instances de nœuds.

Les structures de données internes du système de scène dans Coin sont gérées comme des graphes orientés. Les graphes sont construits en configurant une hiérarchie à l'aide de nœuds de groupe (soit de ce type, soit dérivés de SoSeparator), puis ils sont parcourus lorsque des actions sont appliquées (comme SoGLRenderAction).

Les nœuds SoGroup, SoSeparator et autres classes dérivées de SoGroup sont les « outils » que le programmeur d'application utilise lors de la création de la disposition de la hiérarchie de scène.

Une question fréquemment posée concernant les nœuds SoGroup est : « Pourquoi n'y a-t-il pas de méthode getParent() dans SoGroup ? » La réponse est que les nœuds de la hiérarchie de scène peuvent avoir plusieurs parents, donc une simple méthode getParent() ne serait pas appropriée. Si vous souhaitez supprimer un nœud de la hiérarchie de scène, vous devez le faire à l'aide d'une SoSearchAction pour trouver tous les chemins menant à ce nœud, puis appeler SoGroup::removeChild() à partir de tous les parents trouvés.

La fonction pourrait ressembler à ceci :

void getParents(SoNode * node, SoNode * root, SoPathList & parents)
{
  SoSearchAction sa;
  sa.setNode(node);
  sa.setInterest(SoSearchAction::ALL);
  sa.apply(root);
  parents = sa.getPaths();
}

Ou si vous savez que votre nœud d'intérêt n'a qu'un seul parent :

SoGroup * getParent(SoNode * node, SoNode * root)
{
  SoSearchAction sa;
  sa.setNode(node);
  sa.setInterest(SoSearchAction::FIRST);
  sa.apply(root);
  SoPath * p = sa.getPath();
  assert(p && "not found");
  if (p->getLength() < 2) { return NULL; } // pas de parent
  return (SoGroup *)p->getNodeFromTail(1);
}

Une note importante sur un problème potentiel lors de l'utilisation de nœuds SoGroup, qui n'est pas courant mais peut rendre la recherche d'erreurs difficile : vous ne devez pas modifier la structure de la hiérarchie de scène pendant un parcours d'action, car cela n'est pas autorisé dans le code interne de Coin. C'est-à-dire que vous ne devez pas utiliser addChild(), removeChild(), insertChild() ou replaceChild() à partir d'un rappel qui est déclenché directement ou indirectement à la suite d'un parcours d'action. La façon la plus courante d'être victime de cette erreur serait quelque chose comme l'exemple suivant (simplifié) :

#include <Inventor/Qt/SoQt.h>
#include <Inventor/Qt/viewers/SoQtExaminerViewer.h>;
#include <Inventor/nodes/SoEventCallback.h>;
#include <Inventor/nodes/SoSeparator.h>;
#include <Inventor/nodes/SoCone.h>;
#include <Inventor/manips/SoPointLightManip.h>;
#include <Inventor/events/SoMouseButtonEvent.h>;
SoPointLightManip * global_pointlightmanip;
SoSeparator * global_root;
// Supprimer la lumière ponctuelle lors du clic droit.
static void
mySelectionC(void * ud, SoEventCallback * n)
{
  const SoMouseButtonEvent * mbe = (SoMouseButtonEvent*) n->getEvent();
  if ((mbe->getButton() == SoMouseButtonEvent::BUTTON2) &&
      (mbe->getState() == SoButtonEvent::DOWN)) {
    if (global_pointlightmanip) {
      global_root->removeChild(global_pointlightmanip);
      global_pointlightmanip = NULL;
    }
  }
}
int
main(int argc, char ** argv)
{
  QWidget * window = SoQt::init(argv[0]);
  global_root = new SoSeparator;
  global_root->ref();
  SoEventCallback * ecb = new SoEventCallback;
  ecb->addEventCallback(SoMouseButtonEvent::getClassTypeId(), mySelectionC, 0);
  global_root->addChild(ecb);
  global_root->addChild(new SoCone);
  global_pointlightmanip = new SoPointLightManip;
  global_root->addChild(global_pointlightmanip);
  SoQtExaminerViewer * viewer = new SoQtExaminerViewer(window);
  viewer->setSceneGraph(global_root);
  viewer->show();
  SoQt::show(window);
  SoQt::mainLoop();
  global_root->unref();
  delete viewer;
  return 0;
}

Ce qui se passe dans le cas précédent est le suivant : lorsque vous cliquez avec le bouton droit de la souris, SoQtExaminerViewer convertit l'événement Qt en un événement Coin, qui est envoyé à travers la hiérarchie de scène avec une SoHandleEventAction. Le parcours d'action atteint le nœud SoSeparator nommé global_root, où il constate qu'il doit parcourir 3 nœuds enfants (d'abord SoEventCallback, puis SoCone, puis SoPointLightManip). Lors du parcours de SoEventCallback, la fonction mySelectionC() est appelée, qui supprime le dernier enfant. Cependant, le SoHandleEventAction continuera à parcourir comme si le nœud global_root avait 3 enfants — et le code planterait.

(Cet exemple exact pourrait être facile à gérer en interne dans Coin, mais il existe d'autres façons de modifier la structure de la hiérarchie de scène qui sont difficiles à gérer correctement. Par conséquent, en général, la modification de la structure pendant un parcours d'action n'est pas autorisée.)

Que faire dans ces cas ? Il est préférable de modifier le code dans le rappel pour ne pas effectuer d'opérations qui modifient immédiatement la structure de la hiérarchie de scène, mais de les reporter à après le parcours. Cela peut être fait, par exemple, en utilisant un capteur Coin.

NAME

SoGroup - group node of a scenegraph

SYNOPSIS

#include <Inventor/nodes/SoGroup.h>

Inheritance diagram for SoGroup:

All inherited members

SoNode  SoBase  SoInternal 

Detailed Description

A SoGroup is a node that contains a list of child nodes, which it in turn manages.

A SoGroup is also an SoNode, and therefore inherits all of the node-related functionality such as:

  • Scene graph traversal.
  • Node kits.
  • Field access.
  • Node actions.

The group node specifically adds the ability to manage a list of child nodes.

A SoGroup instance can contain any number of child nodes. The children are traversed in the order they are added to the group, and the group's methods (such as GLRenderAction, RayPickAction, etc.) will invoke the corresponding methods on its children.

Children can be added, removed, or reordered at any time, even during traversal. The SoGroup takes ownership of the children it manages. This means that when a SoGroup is destroyed, it will also destroy all of its children.

The SoGroup class itself is intended to be abstract. You should typically subclass it to create nodes that behave like groups. For example, SoSeparator, SoSwitch, and SoInfoGroup are all subclasses of SoGroup.

The Coin library provides a base group class, SoNode, which is implicitly a group node (all nodes are implicitly groups). If you want to build a node that is a group, you do not need to subclass SoGroup. Instead, you should subclass SoNode and add child nodes to it by using the addChild() and removeChild() methods.

However, if you want to implement a custom group node type, you'll likely want to subclass SoGroup.
