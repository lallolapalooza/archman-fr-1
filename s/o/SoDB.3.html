Description détaillée

La classe SoDB gère les données globales internes.

•
!

Cette classe rassemble diverses méthodes pour initialiser, définir et accéder aux données globales communes de la bibliothèque Coin.

Toutes les méthodes de SoDB sont statiques.

Assurez-vous d'appeler SoDB::init() (directement ou indirectement via la méthode init() de la bibliothèque d'interface graphique) avant d'utiliser les autres classes Coin.

Documentation des typedef de membre

typedef SbBool SoDB::ProgressCallbackType(const SbName &itemid, float fraction, SbBool interruptible, void *userdata)

Les fonctions de rappel de progression du code client doivent être des fonctions statiques de ce type.

L'argument itemid est un identifiant textuel unique qui indique ce qui est traité (utilisez-le pour tout texte informatif de barre de progression de l'interface graphique), et fraction est une valeur dans l'intervalle [0, 1] qui indique où en est le processus. Si la tâche est annulée avec succès, la fonction de rappel sera appelée une dernière fois avec fraction défini à -1.0.

La valeur de retour est un indicateur d'interruption du code client. Notez que le processus en cours ne peut être interrompu que si le drapeau interruptible est défini.

Voir SoDB::addProgressCallback() pour une documentation complète sur le fonctionnement du mécanisme de notification de progression.

void SoDB::init (void ) [static]

Initialise le système Coin. Ceci doit être fait comme première chose avant de commencer à utiliser la bibliothèque, sinon vous risquez un crash prématuré.

void SoDB::finish (void ) [static]

Invoquez cette méthode comme dernier appel du code de l'application, pour déclencher un nettoyage de toutes les ressources statiques utilisées par la bibliothèque Coin.

Ce n'est généralement pas nécessaire pour les applications exécutables autonomes, car le système d'exploitation se chargera du nettoyage après la sortie du processus.

Il peut cependant être nécessaire d'invoquer cette méthode pour éviter les fuites dans des environnements d'exécution « spéciaux », par exemple si la bibliothèque Coin est utilisée comme plug-in de navigateur, ou un autre type de composant pouvant être démarré, arrêté et redémarré plusieurs fois.

SoSeparator * SoDB::readAll (SoInput * in) [static]

Lit tous les graphes à partir de in et les retourne sous un nœud SoSeparator. Si le fichier ne contient qu'un seul graphe sous un nœud SoSeparator (ce qui est la manière la plus courante de construire et d'exporter des graphes de scène), aucun nœud racine supplémentaire SoSeparator ne sera créé, mais le nœud racine retourné sera le nœud le plus haut du fichier.

Le compteur de références du séparateur racine retourné par cette méthode sera à zéro. Les autres nœuds du graphe de scène retourné auront des compteurs de références conformes au nombre de relations parent-enfant, comme d'habitude.

La disposition courante pour charger, travailler avec, puis enfin détruire et retourner les ressources mémoire des graphes de scène se présente généralement comme suit :

// [snip]
SoInput in;
if (!in.openFile(filename)) { exit(1); }
SoSeparator * root = SoDB::readAll(&in);
if (!root) { exit(1); }
// le nœud racine retourné par SoDB::readAll() a un compte
// de références initial à zéro, donc référencez-le avant de commencer à l'utiliser pour
// éviter une destruction prématurée.
root->ref();
// [faites votre chose ici -- attachez la scène à un visualiseur ou autre chose]
// ramenez le compte de références du nœud racine à zéro pour provoquer la
// destruction de la scène.
root->unref();
// (Lors de sa propre autodestruction, le nœud racine dés-référencera également
// ses nœuds enfants, donc ils s'autodétruiront également, et ainsi de suite
// récursivement dans la hiérarchie du graphe de scène jusqu'à ce que le graphe
// de scène complet se soit autodétruit et ait ainsi retourné toutes les
// ressources mémoire qu'il utilisait.)

Retourne NULL en cas d'erreur.

Astuce : une opération courante à effectuer après l'importation d'un graphe de scène est de récupérer les pointeurs mémoire d'un ou plusieurs des nœuds importés pour une manipulation ultérieure. Cela peut être accompli en utilisant soit la fonction SoNode::getByName() (qui est l'approche la plus simple), soit en utilisant une instance de la classe SoSearchAction (qui est l'approche la plus complexe mais aussi la plus flexible).

SbBool SoDB::registerHeader (const SbString & headerstring, SbBool isbinary, float ivversion, SoDBHeaderCB * precallback, SoDBHeaderCB * postcallback, void * userdata = NULL) [static]

Enregistre une chaîne d'en-tête qui doit être reconnue par SoInput lors de l'importation de fichiers. C'est un moyen pratique pour les utilisateurs de bibliothèques d'enregistrer leurs propres formats de fichiers dérivés de VRML ou de Coin.

Définissez isbinary à TRUE si le fichier doit être lu comme des données binaires, et définissez ivversion pour indiquer quelle version de la bibliothèque Coin est nécessaire pour lire le fichier.

Les rappels precallback et postcallback seront appelés avant et après l'importation du format personnalisé.

Si headerstring ne peut pas être accepté comme un en-tête de format de fichier valide pour les fichiers Coin, FALSE sera retourné. Un en-tête valide **doit** commencer par un caractère '#', et ne pas dépasser 80 caractères.

Ceci est un wrapper autour de l'appel POSIX select(). Il est fourni afin que vous puissiez effectuer des entrées/sorties synchrones pendant que Coin continue de gérer les événements de capteur, le rendu, etc. Les paramètres sont les mêmes que pour select(), consultez donc la documentation de votre système sur la façon de les utiliser.

void SoDB::addProgressCallback (ProgressCallbackType * func, void * userdata) [static]

Le concept derrière les informations de progression dans Coin est que tout processus qui peut prendre du temps à se terminer (comme par exemple l'importation de fichiers pour des scènes volumineuses) peut transmettre des informations de progression en rappelant une fonction de rappel de progression définie par le code de l'application cliente.

La signature de la fonction de rappel de progression du client doit correspondre à SoDB::ProgressCallbackType.

Le mécanisme fonctionne en imposant que toutes les notifications de progression provenant de Coin doivent

1.
Utiliser un identifiant textuel unique pour identifier le processus qui fournit des informations de progression (par exemple, "Importation de fichier" pour la lecture de fichiers SoDB::readAll() / SoInput, "Exportation de fichier" pour SoOutput / SoWriteAction, etc.). C'est le nom de l' itemid passé à la fonction de rappel de progression.
2.
La première invocation de la fonction de rappel utilisateur sera effectuée avec une valeur de fraction exacte de 0.0.
3.
La dernière invocation sera effectuée avec une valeur de fraction exacte de 1.0.
4.
Une exception à ce dernier point est que si le processus est interrompu, une dernière invocation avec une valeur de fraction de -1.0 sera effectuée.

Une chose importante à noter à propos du mécanisme est que les processus avec des fonctions de rappel de progression peuvent s'exécuter dans d'autres processus utilisant la fonctionnalité de rappel de progression. Les informations de progression devront alors être considérées comme "empilées", et le code client doit en être conscient et les traiter correctement.

Cette fonction est une extension pour Coin, et elle n'est pas disponible dans l'API originale SGI Open Inventor v2.1.

void SoDB::readlock (void ) [static]

Place un verrou de lecture sur le mutex global SoDB. Ceci peut être utilisé pour synchroniser entre les threads qui lisent/écrivent des graphes de scène Coin.

Si vous appelez cette fonction, vous devez vous assurer que vous appelez également SoDB::readunlock(). Si vous omettez de le faire, vous pourriez constater que votre application se bloque.

Toutes les actions Coin appliquent un verrou de lecture sur le mutex global SoDB pendant le parcours du graphe de scène.

Detailed Description

The SoDB class is the central database for the Coin scene graph. It keeps track of all the nodes, their fields, and the connections between them. It also handles reading and writing scene graph files, managing node IDs, and registering new node classes.

The SoDB class is a singleton, meaning there is only one instance of it in the application. You can access this instance using the static methods of the class.
