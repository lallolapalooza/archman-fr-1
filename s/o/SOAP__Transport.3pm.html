SOAP::Transport(3) Documentation Perl contribuée par l'utilisateur SOAP::Transport(3)

NOM

SOAP::Transport - une classe abstraite étendue par des modules de transport plus spécialisés

DESCRIPTION

Les objets de la classe SOAP::Transport gèrent deux rôles : ils gèrent à la fois les paramètres liés au transport tels que définis via l'objet SOAP::Lite parent, et ils abstraient la sélection et le chargement d'un module de transport approprié. Ceci est fait avec une fonction AUTOLOAD dans la classe qui intercepte toutes les méthodes au-delà des deux définies ci-dessous et les redirige vers le code d'implémentation du transport sous-jacent.

MÉTHODES

new
$trans = SOAP::Transport->new;

C'est le constructeur, qui n'est généralement pas appelé directement par une application. Une application peut l'utiliser pour créer un nouvel objet SOAP::Transport, qui peut être installé en utilisant la méthode SOAP::Lite->transport définie précédemment. Aucun argument n'est reconnu.

proxy(optionnel chaîne URL)
$trans->proxy('http://www.blackperl.com/SOAP');

Récupère ou définit le proxy (point d'extrémité). Cette méthode doit être appelée avant toute autre méthode. Le code de transport approprié est chargé en fonction du schéma spécifié par l'URL elle-même (http, jabber, etc.). Jusqu'à ce que cette méthode soit appelée pour la première fois avec une chaîne URL, le code sous-jacent n'a pas encore été chargé et les méthodes ne sont pas disponibles. Lors de la récupération du proxy actuel (appel sans paramètres), la valeur retournée est une référence à l'objet client créé à partir de la classe de protocole qui correspond au point d'extrémité, et non au point d'extrémité lui-même.

SOAP Classes filles de Transport

Étant donné que la majeure partie du travail est effectuée au sein du module "SOAP::Lite" lui-même, nombre de modules de niveau transport sont très simples dans leurs implémentations. Les modules de transport sont censés définir des classes client et serveur au sein de leurs fichiers. Si un module ne définit qu'un seul des types, il est supposé que le protocole de transport lui-même ne prend en charge que ce côté de la conversation. Un exemple est SOAP::Transport::FTP, qui ne fournit qu'une classe "SOAP::Transport::FTP::Client".

"SOAP::Transport::FTP" - Classe client uniquement

"SOAP::Transport::HTTP" - Classes client et serveur pour CGI, FCGI, Daemon et mod_perl

"SOAP::Transport::IO" - Classe serveur uniquement

"SOAP::Transport::JABBER" - Classes serveur et client

"SOAP::Transport::LOCAL" - Classe client uniquement

"SOAP::Transport::MAILTO" - Classe client uniquement

"SOAP::Transport::MQ" - Classes serveur et client

"SOAP::Transport::POP3" - Classe serveur uniquement

"SOAP::Transport::TCP" - Classes serveur et client

MÉTHODES

Chaque sous-classe SOAP::Transport est censée définir (ou hériter, si elle hérite d'une autre classe de transport) au moins deux méthodes. Toutes les classes de transport nouvellement développées doivent également adhérer à cette interface. Les clients sont censés implémenter les méthodes "new" et "send_receive", et les serveurs sont censés implémenter les méthodes "new" et "handle". Les voici :

new(optionnel paires clé/valeur)
$object = $class->new(%params);

Crée une nouvelle instance d'objet et la retourne. Comme les constructeurs des classes "SOAP::Lite" et SOAP::Server, tous les arguments passés sont traités comme des paires clé/valeur, où la clé est censée être l'une des méthodes prises en charge par la classe, et la valeur est l'argument (ou la référence à une liste d'arguments) de la méthode.

send_receive(paires clé/valeur)
$client->send_recieve(%hash_table);

(Requis pour les classes client uniquement) Lorsque les objets SOAP::Lite tentent d'envoyer des requêtes, le moyen de le faire est de tenter d'appeler cette méthode sur l'objet contenu dans l'objet SOAP::Transport contenu dans le client lui-même. Tous les clients sont censés fournir cela, et l'appel à cette méthode passe toujours quatre valeurs pour les clés de hachage :

action
L'URI spécifiant l'action en cours, généralement le résultat du hook on_action sur l'objet client.
encodage
L'URI du schéma d'encodage qui régit le message envoyé.
point_d_extremite
L'URI spécifiant le point d'extrémité auquel le message est envoyé.
enveloppe
Le contenu XML du message à envoyer. C'est généralement la valeur de retour de la méthode envelope de l'instance de l'objet SOAP::Serializer que l'objet client maintient.
parties
Pièces jointes à ajouter à la requête. Actuellement, cela ne prend en charge qu'un tableau d'objets MIME::Entity, mais en théorie, cela pourrait prendre en charge des pièces jointes de n'importe quel format.
handle
$server->handle;

(Requis pour les classes serveur uniquement.) Cette méthode est le point central pour que les différentes classes serveur fournissent une interface pour gérer les requêtes. L'ensemble exact et la nature des paramètres varient généralement en fonction des classes elles-mêmes.

SOAP::Transport::HTTP

Le module de transport le plus couramment utilisé est l'implémentation HTTP. Il est chargé chaque fois qu'un point d'extrémité est donné qui commence par les caractères http:// ou https://. C'est également le module de transport le plus complexe, définissant non seulement une classe client mais aussi plusieurs classes serveur différentes.

PARAMÈTRES DE PROXY HTTP

Étant donné que "SOAP::Client" hérite de "LWP::UserAgent", vous pouvez utiliser tous les paramètres de proxy de "LWP::UserAgent". Par exemple :

SOAP::Lite->proxy("http://endpoint.server/",
                  proxy => ["http" => "http://my.proxy.server"]);

ou

$soap->transport->proxy("http" => "http://my.proxy.server");

Les exemples de code ci-dessus devraient spécifier un serveur proxy pour vous. Et si vous utilisez "HTTP_proxy_user" et "HTTP_proxy_pass" pour l'autorisation proxy, "SOAP::Lite" s'en chargera correctement.

AUTHENTIFICATION BASIQUE HTTP

L'authentification basique HTTP est réalisée en surchargeant la sous-routine get_basic_credentials dans "LWP::UserAgent" (dont "SOAP::Transport::HTTP::Client" est une sous-classe) :

BEGIN {
  sub SOAP::Transport::HTTP::Client::get_basic_credentials {
    return 'username' => 'password';
  }
}

AUTHENTIFICATION BASÉE SUR LES COOKIES

use HTTP::Cookies;
my $cookies = HTTP::Cookies->new(ignore_discard => 1);
# vous pouvez également ajouter 'file' si vous voulez les conserver entre les sessions
my $soap = SOAP::Lite->proxy('http://localhost/');
$soap->transport->cookie_jar($cookies);

Ou, alternativement, vous pouvez faire ce qui précède en une seule ligne :

$soap->proxy('http://localhost/',
             cookie_jar => HTTP::Cookies->new(ignore_discard => 1));

Les cookies seront pris à partir de la réponse et fournis à la requête. Vous pouvez accéder et manipuler les cookies reçus, ainsi qu'ajouter vos propres cookies en utilisant les interfaces "HTTP::Cookies".

AUTHENTIFICATION PAR CERTIFICAT SSL

L'implémentation SSL par défaut pour la bibliothèque client HTTP LWP::UserAgent utilisée par SOAP::Lit

e es IO::Socket::SSL.

Pour activer l'authentification basée sur les certificats, vous devrez passer votre certificat et votre clé comme options supplémentaires à la méthode proxy() comme suit :

$soap->proxy( $url, ssl_opts => {
    SSL_cert_file => 'client-cert.pem',
    SSL_key_file  => 'client-key.pem'
});

Ou vous pouvez les définir plus tard comme ceci :

$soap->transport->ssl_opts(
    SSL_cert_file => 'client-cert.pem',
    SSL_key_file  => 'client-key.pem'
);

Si vous utilisez Crypt::SSLeay, ce qui suit s'applique :

Pour que l'authentification basée sur les certificats fonctionne, vous devez définir trois variables d'environnement : "HTTPS_CERT_FILE", "HTTPS_KEY_FILE" et éventuellement "HTTPS_CERT_PASS". Cela peut être fait soit en ligne de commande, soit directement dans votre script Perl en utilisant la variable $ENV :

$ENV{HTTPS_CERT_FILE} = 'client-cert.pem';
$ENV{HTTPS_KEY_FILE}  = 'client-key.pem';

Ces réglages s'appliquent à "Crypt::SSLeay". D'autres réglages (par exemple, la vérification des certificats des pairs) peuvent être spécifiés de manière similaire. Voir la documentation de Crypt::SSLeay pour plus d'informations.

Note : Bien que l'utilisation de "Crypt::SSLeay" ne soit pas recommandée car elle n'effectue pas la vérification du nom d'hôte, "LWP::UserAgent" utilise par défaut "IO::Socket::SSL". Voir également https://metacpan.org/pod/Crypt::SSLeay#DO-YOU-NEED-Crypt::SSLeay.

Les utilisateurs souhaitant utiliser des clés cryptées peuvent trouver utile la discussion suivante dans le groupe de newsgroups de SOAP::Lite :

http://groups.yahoo.com/group/soaplite/message/729

COMPRIMÉ

SOAP::Lite vous offre la possibilité d'activer la compression dans le transmetteur HTTP *uniquement* dans les contextes serveur et client, à condition que Compress::Zlib soit installé. La compression et la décompression sont effectuées de manière transparente pour votre application.

Un serveur ne répondra avec un message encodé ou compressé que si le client a déclaré qu'il acceptait ce type de message (indiqué par un en-tête HTTP "Accept-Encoding" avec la valeur 'deflate' ou '*').

Si le serveur ne comprend pas le type de compression spécifié (c'est-à-dire "Content-Encoding: deflate") et renvoie le code HTTP approprié (415 NOT ACCEPTABLE), le client réitérera la requête sans utiliser de compression. Le client mettra ce serveur en cache pour la session, de sorte que toutes les requêtes ultérieures à ce serveur seront transmises sans compression.

La compression est activée côté client en spécifiant l'option "compress_threshold", et si la taille de la requête actuelle dépasse ce seuil.

Exemple de code client

print SOAP::Lite
  ->uri('http://localhost/My/Parameters')
  ->proxy('http://localhost/', options => {compress_threshold => 10000})
  ->echo(1 x 10000)
  ->result;

Les serveurs répondront avec un message compressé si "compress_threshold" a été spécifié, si la taille du message de réponse actuel dépasse ce seuil, et si le client a transmis le bon en-tête HTTP "Accept-Encoding".

Exemple de code serveur

my $server = SOAP::Transport::HTTP::CGI
  ->dispatch_to('My::Parameters')
  ->options({compress_threshold => 10000})
  ->handle;

Voir aussi : Compress::Zlib.

SOAP::Transport::HTTP::Client

Hérite de : SOAP::Client, LWP::UserAgent (du dossier LWP)

Avec cette classe, les clients peuvent utiliser HTTP pour envoyer des messages. Cette classe ne fournit que les méthodes de base "new" et "send_receive". Les objets de cette classe comprennent l'option "compress_threshold" et l'utilisent si le serveur auquel ils communiquent la comprend également.

CHANGEMENT DE CLASSE USERAGENT PAR DÉFAUT

Par défaut, "SOAP::Transport::HTTP::Client" hérite de "LWP::UserAgent". Cependant, dans certains cas, un utilisateur peut souhaiter changer la classe de UserAgent par défaut pour gérer les connexions persistantes ou pour "LWP::UserAgent::ProxyAny", qui a une meilleure interopérabilité avec Win32/Internet Explorer.

Vous pouvez utiliser l'exemple suivant pour changer la classe de UserAgent par défaut :

use SOAP::Lite;
use SOAP::Transport::HTTP;
$SOAP::Transport::HTTP::Client::USERAGENT_CLASS = "My::UserAgent";
my $client = SOAP::Lite->proxy(..)->uri(..);
my $som = $client->myMethod();

Cependant, il y a une mise en garde : la classe UserAgent que vous utilisez doit également être une sous-classe de "LWP::UserAgent". Sinon, "SOAP::Lite" générera l'erreur suivante : "Could not load UserAgent class <USERAGENT CLASS>."

HTTP-KEEP-ALIVE, TIMEOUTS, ET PLUS

Étant donné que "SOAP::Transport::HTTP::Client" hérite de "LWP::UserAgent", toutes les méthodes disponibles dans "LWP::UserAgent" sont également disponibles pour vos clients SOAP. Par exemple, les en-têtes HTTP keep alive dans "LWP::UserAgent" sont implémentés avec le code suivant :

my $ua = LWP::UserAgent->new(
      keep_alive => 1,
      timeout    => 30
);

Par conséquent, les paramètres d'initialisation que vous passeriez à "LWP::UserAgent" peuvent également être passés à votre client SOAP "proxy" comme suit :

my $soap = SOAP::Lite
   ->uri($uri)
   ->proxy($proxyUrl,
       timeout => 30,
       keep_alive => 1,
     );

Ceci est valable pour tous les paramètres et méthodes de "LWP::UserAgent".

MÉTHODES

http_request
Cette méthode vous donne accès à un prototype de l'objet de requête HTTP qui sera envoyé à un SOAP::Server. L'objet de requête utilisé est une copie de l'objet.
http_response
Cette méthode vous donne accès à l'objet de réponse HTTP qui sera ou a été envoyé à un SOAP Server. Elle renvoie un objet HTTP::Response.

SOAP::Transport::HTTP::Server

Hérite de : SOAP::Server.

Ceci est l'implémentation la plus basique d'un serveur HTTP. Elle fournit les méthodes de base "new" et "handle". Le comportement de la méthode "handle" est défini ici, ainsi que d'autres méthodes spécifiques à cette classe. Le rôle de cette classe est d'agir comme superclasse pour d'autres classes de serveurs HTTP.

handle
$server->handle;

Attend que la méthode de requête HTTP ait été utilisée pour associer un objet HTTP::Request à l'objet serveur avant d'être appelée. Cette méthode obtient la référence de l'objet pour obtenir la requête en cours de traitement.

request(valeur facultative)
$server->request($req_object)

Obtient ou définit la référence à l'objet HTTP::Request que le serveur traitera dans la méthode "handle".

response(valeur facultative)
$server->response(HTTP::Response->new(...));

Obtient ou définit la référence à l'objet HTTP::Response que le serveur a préparé pour l'envoi au client.

make_response(code, body)
$server->make_response(200, $body_xml);

Crée et renvoie un objet de type HTTP::Response, en utilisant le code de réponse et le contenu fournis.

make_fault(arguments de faute)
$server->response($server->make_fault(@data));

Crée une référence à l'objet HTTP::Response en utilisant un code de réponse par défaut pour indiquer qu'une erreur s'est produite. Les arguments sont les mêmes que ceux de la méthode "make_fault" de la classe SOAP::Server).

product_tokens
Cette méthode n'accepte aucun argument et renvoie simplement une chaîne identifiant les éléments de la classe du serveur. Elle est similaire aux méthodes "product_tokens" dans les classes HTTP::Daemon et Apache).

SOAP::Transport::HTTP::CGI

Hérite de : SOAP::Transport::HTTP::Server.

Cette classe est une sous-classe directe de SOAP::Transport::HTTP::Server et ne définit aucune méthode supplémentaire. Elle inclut une logique dans son implémentation de la méthode "handle" qui gère les en-têtes et paramètres spécifiques à l'environnement CGI.

EXEMPLE D'UTILISATION CGI

Le code suivant est un service web basé sur CGI qui convertit les degrés Celsius en Fahrenheit :

#!/usr/bin/perl
use SOAP::Transport::HTTP;
SOAP::Transport::HTTP::CGI
  ->dispatch_to('C2FService')
  ->handle;
BEGIN {
  package C2FService;
  use vars qw(@ISA);
  @ISA = qw(Exporter SOAP::Server::Parameters);
  use SOAP::Lite;
  sub c2f {
    my $self = shift;
    my $envelope = pop;
    my $temp = $envelope->dataof("//c2f/temperature");
    return SOAP::Data->name('convertedTemp' => (((9/5)*($temp->value)) + 32));
  }
}

EXEMPLE D'UTILISATION DE Apache::REGISTRY

L'utilisation d'un service web basé sur CGI présente certains inconvénients en termes de performances. L'exécution du même CGI sous le système Apache::Registry offre certains gains de performance.

httpd.conf

Alias /mod_perl/ "/Your/Path/To/Deployed/Modules"
<Location /mod_perl>
  SetHandler perl-script
  PerlHandler Apache::Registry
  PerlSendHeader On
  Options +ExecCGI
</Location>

soap.cgi

use SOAP::Transport::HTTP;
SOAP::Transport::HTTP::CGI
  ->dispatch_to('/Your/Path/To/Deployed/Modules', 'Module::Name', 'Module::method')
  ->handle;

AVERTISSEMENT : Déploiement dynamique avec Apache::Registry

L'utilisation de "Apache::Registry" pour le déploiement dynamique échouera, car le module ne sera chargé dynamiquement que la première fois.

Les appels ultérieurs produiront des erreurs d'"accès refusé" car une fois le module déjà en mémoire "SOAP::Lite" contournera le déploiement dynamique. Pour contourner ce problème, spécifiez simplement le CHEMİN complet ET le nom du MODULE dans dispatch_to() et le module sera chargé dynamiquement, mais fonctionnera alors comme sous un déploiement statique. Voir examples/server/soap.mod_cgi comme exemple.

SOAP::Transport::HTTP::Daemon

Hérite de : SOAP::Transport::HTTP::Server.

La classe SOAP::Transport::HTTP::Daemon encapsule une référence à un objet de la classe HTTP::Daemon (du paquet LWP). La classe intercepte les méthodes qui ne sont pas fournies localement ou par la superclasse et tente de les appeler sur l'objet HTTP::Daemon. Ainsi, toutes les méthodes définies dans la documentation de cette classe sont également disponibles pour cette classe. Celles qui entrent en conflit avec les méthodes de SOAP::Transport::HTTP::Server (comme product_tokens) vont à la superclasse. De plus, le comportement de la méthode handle est spécifique à cette classe :

handle
Lorsqu'elle est invoquée, cette méthode entre dans la boucle d'acceptation typique dans laquelle elle attend une requête sur le socket que l'objet daemon maintient et traite le contenu de la requête. Lorsque toutes les requêtes de la connexion retournées par la méthode accept de l'objet HTTP::Daemon ont été traitées, cette méthode retourne.

RÉUTILISATION DES SOCKETS AU REDÉMARRAGE

Souvent, lors de l'implémentation d'un daemon HTTP, les sockets sont bloqués lorsque vous essayez de redémarrer le serveur daemon. Cela empêche le serveur de redémarrer. Souvent, les utilisateurs voient une erreur comme "Impossible de démarrer le serveur : port déjà utilisé". Pour contourner cela, demandez à SOAP::Lite de réutiliser les sockets ouverts à l'aide de "Reuse => 1" :

my $daemon = SOAP::Transport::HTTP::Daemon
                -> new (LocalPort => 80000, Reuse => 1)

EXEMPLE DE DAEMON SERVEUR

use SOAP::Transport::HTTP;
# changez LocalPort à 81 si vous voulez le tester avec soapmark.pl
my $daemon = SOAP::Transport::HTTP::Daemon
  -> new (LocalAddr => 'localhost', LocalPort => 80)
  # spécifiez la liste des objets-par-référence ici
  -> objects_by_reference(qw(My::PersistentIterator My::SessionIterator My::Chat))
  # spécifiez le chemin vers My/Examples.pm ici
  -> dispatch_to('/Votre/Chemin/Vers/Modules/Déployés', 'Module::Nom', 'Module::méthode')
;
print "Contactez le serveur SOAP à ", $daemon->url, "\n";
$daemon->handle;

SOAP::Transport::HTTP::Apache

Hérite de : SOAP::Transport::HTTP::Server.

Cette classe fournit une intégration de la classe de base SOAP::Server avec l'extension mod_perl pour Apache. Pour fonctionner comme gestionnaire d'emplacement, le paquet fournit une méthode appelée handler, pour laquelle handle est aliasée. La méthode new n'est pas fonctionnellement différente de la superclasse. Voici les autres méthodes fournies par cette classe :

handler(requête Apache)
$server->handler($r)

Définit la base d'un gestionnaire d'emplacement à la manière de mod_perl. La méthode attend un objet de requête Apache comme paramètre, à partir duquel elle extrait le corps de la requête et appelle la méthode handle de la superclasse.

Notez que dans cette classe, la méthode locale nommée handle est aliasée à cette méthode.

configure(requête Apache)
$server->configure(Apache->request);

Les informations de configuration par emplacement peuvent être fournies à l'objet serveur à l'aide de la directive DirConfig d'Apache et en appelant cette méthode sur l'objet lui-même. Lors de son invocation, la méthode lit les informations de configuration de répertoire d'Apache et recherche des lignes de la forme :

method => param

Chaque ligne qui correspond au modèle est considérée comme une méthode potentielle à appeler sur l'objet serveur, le reste du jeton étant pris comme paramètre de la méthode. Les méthodes qui prennent des références de hachage comme arguments peuvent être spécifiées comme suit :

method => key => param, key => param

Les paires clé/valeur seront transformées en une référence de hachage à la demande. Si l'objet serveur ne reconnaît pas la méthode nommée comme valide, il ignore la ligne.

EXEMPLE DE SERVEUR APACHE MOD_PERL

Voir examples/server/Apache.pm et Apache::SOAP pour plus d'informations.

httpd.conf

<Location /soap>
  SetHandler perl-script
  PerlHandler SOAP::Apache
  PerlSetVar options "compress_threshold => 10000"
</Location>

SOAP::Apache.pm

package SOAP::Apache;
use SOAP::Transport::HTTP;
my $server = SOAP::Transport::HTTP::Apache
  ->dispatch_to('/Votre/Chemin/Vers/Modules/Déployés', 'Module::Nom', 'Module::méthode');
sub handler { $server->handler(@_) }
1;

Voir aussi Apache::SOAP.

SOAP::Transport::HTTP::FCGI

Hérite de : SOAP::Transport::HTTP::CGI.

Il s'agit d'une extension de SOAP::Transport::HTTP::CGI qui implémente les différences nécessaires pour le protocole FastCGI. Aucune des méthodes n'est fonctionnellement différente.

SOAP::Transport::IO

La classe basée sur SOAP::Transport::IO permet une sorte de proxy I/O en permettant à l'application de configurer les fichiers ou les descripteurs de fichiers qui sont utilisés. Ce module fournit uniquement une classe serveur.

SOAP::Transport::IO::Server

Hérite de : SOAP::Server.

La classe serveur définie ici hérite de toutes les méthodes de SOAP::Server, et ajoute deux méthodes supplémentaires spécifiques à la nature de la classe :

in
$server->in(IO::File->new($file));

Obtient ou définit le descripteur de fichier actuel utilisé comme source d'entrée.

out
$server->out(\*STDERR);

Obtient ou définit le descripteur de fichier utilisé comme destination de sortie.

SOAP::Transport::LOCAL

Le module SOAP::Transport::LOCAL est conçu pour fournir une classe client sans transport pour le traçage et le débogage du trafic de communication. Il relie SOAP::Client et SOAP::Server de sorte que le même objet qui "envoie" la requête la "reçoit" également.

SOAP::Transport::LOCAL::Client

Hérite de : SOAP::Client, SOAP::Server. Les implémentations des méthodes new et send_receive ne sont pas sensiblement différentes dans leur interface. Leur comportement mérite cependant une description :

new
Lorsque le constructeur crée un nouvel objet de cette classe, il met en place quelques éléments au-delà de la disposition habituelle de SOAP::Client. La méthode is_success est définie à une valeur par défaut de 1. La méthode dispatch_to héritée de SOAP::Server est appelée avec la valeur actuelle du tableau global @INC, permettant au client d'appeler toutes les méthodes qui peuvent être trouvées dans le chemin de recherche valide actuel. Et comme avec la plupart des constructeurs de ce module, les paires clé/valeur optionnelles sont traitées comme des noms de méthode et des paramètres.
send_receive
L'implémentation de cette méthode passe simplement la partie enveloppe des données d'entrée à la méthode handle de SOAP::Server. Bien qu'aucun trafic réseau n'en résulte (directement), cela permet d'envoyer des signaux de débogage via le système SOAP::Trace.

SOAP::Transport::MAILTO

Cette classe de transport gère l'envoi de messages basés sur SMTP du point de vue du client. Elle ne fournit pas de classe serveur. La classe est sélectionnée lorsqu'un objet client passe une URI à proxy ou un point de terminaison qui commence par les caractères, mailto:.

SOAP::Transport::MAILTO::Client

Hérite de : SOAP::Client.

La classe client pour ce protocole ne définit aucune nouvelle méthode. Le constructeur fonctionne de la même manière que les constructeurs des autres classes. La fonctionnalité de la méthode send_receive est cependant légèrement différente des autres classes.

Lorsqu'elle est invoquée, la méthode send_receive utilise le paquet MIME::Lite pour encapsuler et transmettre le message. Comme les messages électroniques sont des communications unidirectionnelles (la réponse étant un processus distinct), il n'y a pas de message de réponse à retourner par la méthode. Au lieu de cela, tous les attributs liés au statut (code, message, statut, is_success) sont définis, et aucune valeur n'est explicitement retournée.

SOAP::Transport::POP3

Le support POP3 est limité à une implémentation serveur. Tout comme la classe MAILTO décrite précédemment fonctionne en envoyant des requêtes sans s'attendre à traiter une réponse, le serveur décrit ici accepte les messages de requête et les distribue sans se soucier d'envoyer une réponse autre que celle que POP3 définit pour la livraison réussie d'un message.

SOAP::Transport::POP3::Server

Hérite de : SOAP::Server.

La méthode new de cette classe crée un objet de la classe Net::POP3 à utiliser en interne pour interroger un serveur POP3 spécifié pour les messages entrants. Lorsqu'un objet de cette classe est créé, il s'attend à ce qu'un point de terminaison soit spécifié avec une URI qui commence par les caractères pop:// et inclut des informations d'identifiant utilisateur et de mot de passe ainsi que l'hôte lui-même.

La méthode handle prend les messages présents dans la boîte aux lettres distante et les passe (un par un) à la méthode handle de la superclasse. Chaque message est supprimé après avoir été routé. Tous les messages de la boîte aux lettres POP3 sont présumés être des messages SOAP.

Les méthodes de l'objet Net::POP3 sont détectées et routées correctement, permettant des opérations telles que $server->ping( ).

Cela signifie que la chaîne de point de terminaison n'a pas besoin de fournir l'identifiant utilisateur et le mot de passe car la méthode login de l'API POP3 peut être utilisée directement.
