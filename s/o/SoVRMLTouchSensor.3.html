Description Détaillée

La classe SoVRMLTouchSensor suit la position du pointeur et envoie des événements basés sur l'interaction de l'utilisateur.

La documentation détaillée de la classe est reprise mot pour mot de la norme VRML97 (ISO/IEC 14772-1:1997). Elle est la propriété du Web3D Consortium, et est utilisée avec la permission du Consortium :

TouchSensor {
  exposedField SFBool  enabled TRUE
  eventOut     SFVec3f hitNormal_changed
  eventOut     SFVec3f hitPoint_changed
  eventOut     SFVec2f hitTexCoord_changed
  eventOut     SFBool  isActive
  eventOut     SFBool  isOver
  eventOut     SFTime  touchTime
}

Un nœud TouchSensor suit la position et l'état du dispositif de punter et détecte quand l'utilisateur pointe vers la géométrie contenue par le groupe parent du nœud TouchSensor. Un nœud TouchSensor peut être activé ou désactivé en lui envoyant un événement enabled avec la valeur TRUE ou FALSE. Si le nœud TouchSensor est désactivé, il ne suit pas les entrées de l'utilisateur ni n'envoie d'événements.

Le TouchSensor génère des événements lorsque le dispositif de punter pointe vers des nœuds de géométrie qui sont descendants du groupe parent du TouchSensor. Voir 4.6.7.5, Activation et manipulation des capteurs (http://www.web3d.org/documents/specifications/14772/V2.0/part1/concepts.html#4.6.7.5), pour plus de détails sur l'utilisation du dispositif de punter pour activer le TouchSensor.

Le champ eventOut isOver reflète l'état du dispositif de punter quant à savoir s'il pointe vers la géométrie du nœud TouchSensor ou non. Lorsque le dispositif de punter passe d'une position telle que sa portée n'intersecte aucune géométrie du nœud TouchSensor à une position où il intersecte la géométrie, un événement isOver TRUE est généré. Lorsque le dispositif de punter passe d'une position où sa portée intersecte la géométrie à une position où il n'intersecte plus la géométrie, ou qu'une autre géométrie obstrue la géométrie du nœud TouchSensor, un événement isOver FALSE est généré. Ces événements ne sont générés que lorsque le dispositif de punter a bougé et changé d'état 'over'. Aucun événement n'est généré si la géométrie elle-même s'anime et se déplace sous le dispositif de punter.

Pendant que l'utilisateur déplace la portée sur la géométrie du nœud TouchSensor, le point d'intersection (le cas échéant) entre la portée et la géométrie est déterminé. Chaque mouvement du dispositif de punter, pendant que isOver est TRUE, génère les événements hitPoint_changed, hitNormal_changed et hitTexCoord_changed. Les événements hitPoint_changed contiennent le point 3D sur la surface de la géométrie sous-jacente, donné dans le système de coordonnées du nœud TouchSensor. Les événements hitNormal_changed contiennent le vecteur normal de surface au hitPoint. Les événements hitTexCoord_changed contiennent les coordonnées de texture de cette surface au hitPoint. Les valeurs des événements hitTexCoord_changed et hitNormal_changed sont calculées de manière appropriée pour la forme associée.

Si isOver est TRUE, l'utilisateur peut activer le dispositif de punter pour provoquer la génération d'événements isActive par le nœud TouchSensor (par exemple, en appuyant sur le bouton principal de la souris). Lorsque le nœud TouchSensor génère un événement isActive TRUE, il capture tous les événements de mouvement ultérieurs du dispositif de punter jusqu'à ce qu'il soit relâché et génère un événement isActive FALSE (d'autres capteurs de dispositif de punter ne généreront pas d'événements pendant ce temps). Le mouvement du dispositif de punter pendant que isActive est TRUE est appelé un "glisser". Si un dispositif de punter 2D est utilisé, les événements isActive reflètent l'état du bouton principal associé au dispositif (c'est-à-dire que isActive est TRUE lorsque le bouton principal est pressé et FALSE lorsqu'il est relâché). Si un dispositif de punter 3D est utilisé, les événements isActive refléteront généralement si le dispositif de punter se trouve dans (ou en contact avec) la géométrie du nœud TouchSensor.

Le champ eventOut touchTime est généré lorsque les trois conditions suivantes sont réunies :

  • Le dispositif de punter pointait vers la géométrie lorsqu'il a été initialement activé (isActive est TRUE).
  • Le dispositif de punter pointe actuellement vers la géométrie (isOver est TRUE).
  • Le dispositif de punter est désactivé (un événement isActive FALSE est également généré).

Plus d'informations sur ce comportement sont décrites dans 4.6.7.3, Capteurs de dispositif de punter (http://www.web3d.org/documents/specifications/14772/V2.0/part1/concepts.html#4.6.7.3), 4.6.7.4, Capteurs de glisser (http://www.web3d.org/documents/specifications/14772/V2.0/part1/concepts.html#4.6.7.4), et 4.6.7.5, Activation et manipulation des capteurs (http://www.web3d.org/documents/specifications/14772/V2.0/part1/concepts.html#4.6.7.5).

Le reste de cette documentation de classe n'est pas tiré de la documentation des normes VRML97, mais a été rédigé spécifiquement pour la documentation de l'API Coin3D.


Voici un petit exemple qui montre l'utilisation de SoVRMLTouchSensor. Cliquez sur la SoVRMLSphere pour allumer la SoVRMLPointLight :

#VRML V2.0 utf8
Group {
   children [
      Transform {
         children [
            DEF light PointLight {
               intensity 1
               on FALSE
            }
            Transform {
               translation -2 0 -2
               children [
                  Shape {
                     appearance Appearance {
                        material Material {
                           diffuseColor 1 0 1
                           specularColor 1 1 1
                           shininess 0.9
                        }
                     }
                     geometry Sphere { }
                  }
                  DEF touchsensor TouchSensor { }
               ]
            }
         ]
      }
   ]
   ROUTE touchsensor.isActive TO light.set_on
}

SbBool SoVRMLTouchSensor::affectsState (void ) const [virtual]

Renvoie TRUE si le nœud peut avoir un effet sur l'état pendant le parcours.

S'il renvoie FALSE, aucune donnée dans l'état de parcours ne changera de l'état pré-parcours à l'état post-parcours. Le nœud SoSeparator, par exemple, renverra FALSE, car il pousse et dépile l'état avant et après le parcours de ses enfants. Tous les nœuds SoShape renverront également FALSE, car le simple envoi de données géométriques au moteur de rendu n'affectera pas l'état de rendu réel.

La méthode par défaut renvoie TRUE, selon la philosophie "mieux vaut prévenir que guérir".
