Description Détaillée

La classe SoVRMLScript est utilisée pour contrôler la scène à l'aide de scripts.

La documentation détaillée de la classe est tirée littéralement de la norme VRML97 (ISO/IEC 14772-1:1997). Elle est la propriété du Web3D Consortium et est utilisée avec la permission du Consortium :

Script {
  exposedField MFString url           []
  field        SFBool   directOutput  FALSE
  field        SFBool   mustEvaluate  FALSE
  # Et un nombre quelconque de :
  eventIn      eventType eventName
  field        fieldType fieldName initialValue
  eventOut     eventType eventName
}

Le nœud Script est utilisé pour programmer le comportement dans une scène. Les nœuds Script

  • signalent un changement ou une action utilisateur ;
  • reçoivent des événements d'autres nœuds ;
  • contiennent un module de programme qui effectue un calcul ;
  • provoquent un changement ailleurs dans la scène en envoyant des événements.

Chaque nœud Script a un code de langage de programmation associé, référencé par le champ url, qui est exécuté pour accomplir la fonction du nœud Script. Ce code est appelé le "script" dans le reste de cette description. Les détails sur le champ url se trouvent dans 4.5, VRML et le World Wide Web (http://www.web3d.org/documents/specifications/14772/V2.0/part1/concepts.html#4.5).

Les navigateurs ne sont pas obligés de supporter un langage spécifique. Des informations détaillées sur les langages de script sont décrites dans 4.12, Scripting (http://www.web3d.org/documents/specifications/14772/V2.0/part1/concepts.html#4.12).

Les navigateurs supportant un langage de script pour lequel une liaison de langage est spécifiée doivent adhérer à cette liaison de langage. Avant qu'un script ne reçoive le premier événement, il doit être initialisé (toute initialisation() spécifique au langage ou définie par l'utilisateur est effectuée).

Le script est capable de recevoir et de traiter les événements qui lui sont envoyés. Chaque événement pouvant être reçu doit être déclaré dans le nœud Script en utilisant la même syntaxe que celle utilisée dans une définition de prototype :

eventIn type name

Le type peut être l'un des champs VRML standards (tels que définis dans 5, Référence des champs et des événements). Le nom doit être un identifiant unique pour ce nœud Script.

Le nœud Script est capable de générer des événements en réponse aux événements entrants. Chaque événement pouvant être généré doit être déclaré dans le nœud Script en utilisant la syntaxe suivante :

eventOut type name

À l'exception du champ url, les exposedFields ne sont pas autorisés dans les nœuds Script.

Si le champ mustEvaluate du nœud Script est FALSE, le navigateur peut retarder l'envoi des événements d'entrée au script jusqu'à ce que ses sorties soient nécessaires par le navigateur. Si le champ mustEvaluate est TRUE, le navigateur doit envoyer les événements d'entrée au script dès que possible, indépendamment du fait que les sorties soient nécessaires ou non. Le champ mustEvaluate doit être réglé sur TRUE uniquement si le nœud Script a des effets qui ne sont pas connus du navigateur (tels que l'envoi d'informations sur le réseau). Sinon, de mauvaises performances peuvent en résulter.

Une fois que le script a accès à un nœud VRML (via une valeur SoSFNode ou SoMFNode soit dans l'un des champs du nœud Script, soit passé en tant qu'eventIn), le script est capable de lire le contenu des exposedFields de ce nœud.

Si le champ directOutput du nœud Script est TRUE, le script peut également envoyer des événements directement à n'importe quel nœud auquel il a accès, et peut établir ou rompre dynamiquement des routes.

Si directOutput est FALSE (par défaut), le script ne peut affecter le reste du monde que via les événements envoyés par ses eventOuts. Les résultats sont indéfinis si directOutput est FALSE et que le script envoie des événements directement à un nœud auquel il a accès.

Un script est capable de communiquer directement avec le navigateur VRML pour obtenir des informations telles que l'heure actuelle et l'URL du monde actuel. Ceci est strictement défini par l'API du langage de script spécifique utilisé. L'emplacement du nœud Script dans le graphe de scène n'a aucun effet sur son fonctionnement. Par exemple, si un parent d'un nœud Script est un nœud Switch dont whichChoice est réglé sur "-1" (c'est-à-dire ignorer ses enfants), le nœud Script continue de fonctionner comme spécifié (c'est-à-dire qu'il reçoit et envoie des événements).

Detailed Description

This node implements the VRML97 Script node. It allows the user to define a node which can dynamically alter the scene graph by executing JavaScript code.

In VRML97, the Script node is used to add interactivity to scenes. It defines a set of input and output fields, and a body of JavaScript code. When the scene graph is traversed by a suitable action (e.g. rendering, handling an event, etc.), the script code is executed.

The JavaScript code is interpreted by an embedded JavaScript engine. The engine can be provided by the application, or Coin can be compiled with an interpreter like the SpiderMonkey JavaScript engine.

To create and use a SoVRMLScript node:

1. Create an instance of the node:

    SoVRMLScript * script = new SoVRMLScript;

2. Define input and output fields. These can be any standard Coin field type:

    script->addEventIn("myInput", SO_EVENTIN_FIELD);
    script->addEventOut("myOutput", SO_EVENTOUT_FIELD);
    script->addExposedIn("myExposed", SO_EXPOSEDIN_FIELD);

3. Set the script code. This is a string containing the JavaScript code:

    script->set("function initialize() {\n  // Initialization code here\n}\n\nfunction myInput_changed(value) {\n  myOutput = value * 2;\n  browser.println(myOutput);\n}");

4. Add the node to the scene graph:

    mySceneGraph->addChild(script);

The script code can access and modify input and output fields. The standard VRML Script node functions like `initialize()`, `field_changed()`, `eventIn()`, `eventOut()`, and `browser` are available within the script context.

Note: Coin does not ship with an embedded JavaScript engine. You will need to provide one or compile Coin with an engine like SpiderMonkey for the script node to function.

void SoVRMLScript::copyContents (const SoFieldContainer * from, SbBool copyconnections) [protected], [virtual]

Makes a deep copy of all data of from into this instance, except external scene graph references if copyconnections is FALSE.

This is the method that should be overridden by extension node / engine / dragger / whatever subclasses which need to account for internal data that are not handled automatically.

For copying nodes from application code, you should not invoke this function directly, but rather call the SoNode::copy() function:

SoNode * mynewnode = templatenode->copy();

The same also goes for engines.

Make sure that when you override the copyContents() method in your extension class that you also make it call upwards to its parent superclass in the inheritance hierarchy, as copyContents() in for instance SoNode and SoFieldContainer does important work. It should go something like this:

void
MyCoinExtensionNode::copyContents(const SoFieldContainer * from,
                                  SbBool copyconnections)
{
  // let parent superclasses do their thing (copy fields, copy
  // instance name, etc.)
  SoNode::copyContents(from, copyconnections);
  // [..then copy internal data..]
}
