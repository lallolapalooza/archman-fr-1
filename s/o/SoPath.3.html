Description détaillée

La classe SoPath est une classe conteneur pour les descriptions de chemins de transit.

Les objets SoPath contiennent une liste de pointeurs vers SoNode et une liste d'indices d'enfants. Les indices sont nécessaires pour désambiguïser les situations où un nœud utilise plusieurs fois le même nœud comme enfant.

Les chemins peuvent être exportés et importés à partir de fichiers, comme d'autres objets dérivés de SoBase. Pour voir comment fonctionne le format de fichier, lisez la documentation de la fonction write().

Il est important de connaître la différence entre cette classe et SoFullPath lorsque l'on travaille avec des chemins. SoPath::getTail() retourne le premier nœud du chemin qui n'hérite pas de SoGroup, et getLength() retourne le nombre de nœuds à partir de ce nœud.

Si vous avez besoin de la longueur réelle du chemin ou du nœud final réel, vous devrez convertir le chemin en SoFullPath.

Retourne l'identification de type d'un objet dérivé d'une classe héritant de SoBase. Ceci est utilisé pour la vérification de type à l'exécution et le transtypage "descendant". Exemple d'utilisation:

Pour les programmeurs d'applications souhaitant étendre la bibliothèque avec de nouveaux nœuds, moteurs, kits de nœuds, draggers ou autres : cette méthode doit être surchargée dans toutes les sous-classes. SoNode * SoPath::getTail (void ) const

Cette méthode retourne le nœud de la queue du chemin. Veuillez noter que cette méthode ne considère que les nœuds de groupe sans enfants cachés (nœuds héritant de SoGroup) lors de la recherche de la queue.

Si vous souhaitez trouver le véritable nœud de la queue (également sous les kits de nœuds et les nœuds VRML avec des enfants cachés), vous devez utiliser SoFullPath::getTail(). void SoPath::write (SoWriteAction * action) [virtual]

Cette méthode est utilisée pour écrire le contenu d'un SoPath.

Un chemin est écrit comme suit :

Path {
  NOEUD_TETE_DU_SOUS-GRAPHE
  NOMBRE-D'INDEX
  INDEX0
  INDEX1
  ...
}

[Le reste de la documentation de cette méthode explique uniquement la raison d'une différence de comportement entre Open Inventor original et Coin. Ne la lisez pas si vous n'y portez pas un intérêt particulier. (Version courte : nous faisons l'exportation SoPath d'une manière quelque peu moins efficace pour éviter les bugs potentiels).]

Contrairement à Open Inventor, nous écrivons le sous-graphe complet sous le nœud de tête. Écrire uniquement les parties du sous-graphe affectant l'état des nœuds dans le chemin est sujet aux erreurs si un sous-graphe est exporté dans le cadre d'un chemin avant d'être exporté « correctement ». Considérez l'exportation d'un graphe de scène qui ressemble à ceci (en mémoire) :

DEF top_sep Separator {
  Cone { }
  DEF a_sphere Sphere { }
  Cube { }
}
DEF path_switch PathSwitch {
  path Path {
    ...chemin de « top_sep » à « a_sphere »...
  }
}

..si nous faisons maintenant :

SoSeparator * root = new SoSeparator;
root->addChild([ptr vers path_switch]);
root->addChild([ptr vers top_sep]);
SoWriteAction wa;
wa.apply(root);

..nous obtiendrions le graphe de scène exporté comme ceci :

Separator {
  DEF path_switch PathSwitch {
    path Path {
      DEF top_sep Separator {
        DEF a_sphere Sphere {
        }
      }
      1
      0
    }
  }
  USE top_sep
}

..et comme vous pouvez le voir, à la fois le Cone et le Cube ont disparu, car ils n'étaient pas importants pour la partie en soi, et n'ont pas été écrits dans le cadre de celle-ci.

C'est pourquoi nous faisons une exportation complète du sous-graphe pour les nœuds de tête dans les chemins.
