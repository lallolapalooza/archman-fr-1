Description Détaillée

La classe SoFieldContainer est une classe de base pour toutes les classes contenant des champs.

Les classes contenant des champs dans Coin sont les classes de nœud et de moteur, elles sont donc toutes des sous-classes de SoFieldContainer.

La classe SoFieldContainer fournit des méthodes pour lire, écrire, comparer l'égalité, effectuer des opérations de copie, etc. sur les champs.

SbBool SoFieldContainer::enableNotify (const SbBool enable)

Cette méthode définit si la notification sera propagée lorsque les valeurs des champs contenus sont modifiées. La valeur précédente du drapeau est retournée.

La notification par défaut est activée. Désactiver la notification automatique peut être utile pour optimiser les performances. Si de nombreuses mises à jour sont effectuées, on peut éviter la propagation des notifications lors de la modification de la valeur de chaque champ. Ceci est géré comme suit :

SbBool autonotify = node->enableNotify(FALSE);
// ...
// Effectuer des modifications sur les champs de "node" ici.
// ...
node->enableNotify(autonotify);
node->touch();

void SoFieldContainer::copyContents (const SoFieldContainer * from, SbBool copyconnections) [virtual]

Crée une copie profonde de toutes les données de from dans cette instance, sauf si copyconnections est FALSE et qu'aucun lien externe vers le graphe n'est effectué.

C'est la méthode qui doit être remplacée par les sous-classes de nœuds / moteurs / draggers / etc. qui ont besoin de gérer des données internes qui ne sont pas gérées automatiquement.

Pour copier des nœuds à partir du code de l'application, n'appelez pas directement cette méthode, mais utilisez la fonction SoNode::copy():

SoNode * mynewnode = templatenode->copy();

Il en va de même pour les moteurs.

Assurez-vous que lorsque vous surchargez la méthode copyContents() dans votre classe d'extension, vous l'appelez également vers le haut dans la hiérarchie des superclasses, car copyContents() dans par exemple SoNode et SoFieldContainer effectue des tâches importantes.

ork. Il devrait ressembler à ceci :

void
MyCoinExtensionNode::copyContents(const SoFieldContainer * from,
                                  SbBool copyconnections)
{
  // Laissons les superclasses parentales faire leur travail (copier les champs,
  // copier le nom de l'instance, etc.)
  SoNode::copyContents(from, copyconnections);
  // [..puis copier les données internes..]
}

Retourne une copie de orig.

Cette méthode exécutera également la méthode copyContents() sur la copie, si elle n'a pas déjà été exécutée. Notez que si vous appelez copyContents() sur la copie en dehors de cette méthode, cela passera inaperçu et le contenu de orig sera copié plusieurs fois dans sa copie.

Si copyContents() est appelé directement (au lieu d'utiliser copy()), on suppose que l'utilisateur ne souhaite copier que les valeurs des champs, et nous retournons simplement NULL ici. Ceci est fait pour correspondre à la manière dont cela est fait dans SGI Inventor.

void SoFieldContainer::getFieldsMemorySize (size_t & managed, size_t & unmanaged) const [virtual]

Retourne les tailles des tableaux de données des champs multiples enregistrés par SoFieldData. L'argument managed retourne la taille des champs pour lesquels Coin gère la mémoire, et l'argument unmanaged retourne la taille des données dans les champs multiples contrôlés par l'application via SoMField::setValuesPointer() que Coin ne supprimera pas.

Les données conservées dans le bloc mémoire de l'objet (qui est inclus lorsque vous faites sizeof(object)) ne sont pas incluses dans ces valeurs - seule la mémoire gérée dans des blocs mémoire supplémentaires à partir du bloc objet est retournée.

Les types de champs d'extension qui ne sont pas connus de la simple bibliothèque Coin ne sont pas pris en compte. Cette fonction est donc virtuelle, de sorte que de tels types de champs d'extension peuvent être ajoutés aux nombres pour les nœuds d'extension.

Cette méthode est utilisée à des fins de profilage mémoire.

SbBool SoFieldContainer::readInstance (SoInput * in, unsigned short flags) [protected], [virtual]

Cette méthode est principalement destinée à une utilisation interne lors des opérations d'importation de fichiers.

Elle lit la définition d'une instance à partir du flux d'entrée in. L'état du flux d'entrée pointe vers le début d'une représentation séquentielle / persistante d'une instance de ce type de classe.

TRUE ou FALSE est retourné, selon que l'instanciation et la configuration du nouvel objet de ce type de classe se sont bien déroulées ou non. Le processus d'importation doit être robuste et gérer les flux d'entrée corrompus en retournant FALSE.

flags est utilisé en interne lors de l'importation binaire lors de la lecture de nœuds d'extension utilisateur, de nœuds de groupe ou de moteurs.
