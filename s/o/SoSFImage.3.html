Description détaillée

La classe SoSFImage est utilisée pour stocker des images de pixels.

La classe SoSFImage fournit un espace pour des cartes d'image 2D en ligne. Les images dans Coin sont principalement utilisées pour le support de texturisation.

Les objets SoSFImage ont : leurs dimensions d'image (largeur et hauteur), le nombre d'octets utilisés pour décrire chaque pixel (nombre de composantes) et un tampon de pixels associé. La taille du tampon de pixels sera largeur*hauteur*composantes.

Pour les cartes de texturisation, la valeur des composantes / octets par pixel se traduit comme suit : utilisez 1 pour une carte en niveaux de gris, 2 pour gris + transparence (c.-à-d. valeur d'opacité), 3 pour RVB (1 octet chacun pour le rouge, le vert et le bleu) et 4 composantes signifie 3 octets pour le RVB + 1 octet de valeur de transparence (également appelé RVBA).

Ce champ est sérialisé dans le format Inventor / Coin comme suit :

FIELDNAME X Y C 0xRRGGBBAA 0xRRGGBBAA ...

"X" et "Y" sont les dimensions de l'image le long des axes donnés, "C" est le nombre de composantes dans l'image. Le nombre de spécifications de couleur 0xRRGGBBAA nécessaires pour correspondre au nombre exact de pixels, qui est en fait donné par X*Y. Chaque partie de la valeur de couleur du pixel est comprise entre 0x00 et 0xff (hexadécimal, 0 à 255 décimal).

Pour les images à 3 composantes, le format de pixel est 0xXXRRGGBB, où l'octet de la valeur de couleur du pixel marqué "XX" est ignoré et peut être omis.

Pour les images à 2 composantes, le format de pixel est 0xXXXXGGAA, où les octets des valeurs de couleur de pixel marquées "XX" sont ignorés et peuvent être omis. "GG" est la partie qui donne une valeur de transparence.

DESCRIPTION

This field contains an image. The image is represented by a pointer to an array of unsigned chars, the dimensions of the image and the number of components per pixel.

The image data are stored as unsigned bytes in the pixel buffer, ordered from the lower-left corner to the upper-right corner. The bytes are ordered as GGBB, where GG is the grayscale value and BB is the alpha value. If the image has 1 component, the pixel-format is 0xXXGG, where the bytes marked as "XX" are ignored and can be left out.

If an image has 3 components, the pixel-format is 0xRRFFEE, where RR is the red value, GG is the green value and BB is the blue value.

If an image has 4 components, the pixel-format is 0xRRFFEEAA, where RR is the red value, GG is the green value, BB is the blue value and AA is the alpha value.

For 1-component images, the pixel-format is 0xXXGG, where the bytes in the pixel color values marked as "XX" are ignored and can be left out.

The pixels are read as being ordered in rows along X (width) and columns along Y (height, bottom to top).

Here's a simple example of the file format serialization, for a 2x2 RGB-image inside an SoTexture2 node, as mapped onto an SoCube:

Initialize this field to size and nc.

\n

If pixels is not NULL, the image data is copied from\n pixels into this field. If pixels is NULL, the image data is\n cleared by setting all bytes to 0 (note that the behavior on passing a NULL\n pointer is specific for Coin, Open Inventor will crash if you try it).

The copypolicy argument makes it possible to share image\n data with SoSFImage without the data being copied (thereby using less\n memory resources). The default is to copy image data from the pixels\n source into an internal copy.
