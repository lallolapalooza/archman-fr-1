NOM

sd_journal_get_fd, sd_journal_get_events, sd_journal_get_timeout, sd_journal_process, sd_journal_wait, sd_journal_reliable_fd, SD_JOURNAL_NOP, SD_JOURNAL_APPEND, SD_JOURNAL_INVALIDATE - Interface de notification de changement du journal

SYNTAXE

#include <systemd/sd-journal.h>

int sd_journal_get_fd(sd_journal *j);

int sd_journal_get_events(sd_journal *j);

int sd_journal_get_timeout(sd_journal *j, uint64_t *timeout_usec);

int sd_journal_process(sd_journal *j);

int sd_journal_wait(sd_journal *j, uint64_t timeout_usec);

int sd_journal_reliable_fd(sd_journal *j);

DESCRIPTION

sd_journal_get_fd() renvoie un descripteur de fichier qui peut être interrogé de manière asynchrone dans une boucle d'événements externe et qui est signalé dès que le journal change, car de nouvelles entrées ou de nouveaux fichiers ont été ajoutés, une rotation a eu lieu, ou des fichiers ont été supprimés, etc. Le descripteur de fichier est adapté à une utilisation dans poll(2). Utilisez sd_journal_get_events() pour obtenir un masque d'événements à surveiller. L'appel prend un argument : l'objet de contexte du journal. Notez que tous les systèmes de fichiers ne sont pas capables de générer les événements nécessaires pour des réveils à partir de ce descripteur de fichier afin que les changements soient remarqués immédiatement. En particulier, les systèmes de fichiers réseau ne génèrent pas toujours des événements de changement de fichier appropriés. Ces cas peuvent être détectés avec sd_journal_reliable_fd(), ci-dessous. sd_journal_get_timeout() assurera dans ces cas que les réveils se produisent assez fréquemment pour que les changements soient remarqués, bien qu'avec une certaine latence.

sd_journal_get_events() renverra le masque poll() à attendre. Cette fonction retournera une combinaison de POLLIN et POLLOUT et similaires pour remplir le champ ".events" de struct pollfd.

sd_journal_get_timeout() renverra une valeur de délai d'attente à utiliser dans poll(). Elle renvoie une valeur en microsecondes depuis l'époque de CLOCK_MONOTONIC pour la mise en veille de poll() dans timeout_usec. Voir clock_gettime(2) pour les détails sur CLOCK_MONOTONIC. S'il n'y a pas de délai d'attente, cette fonction remplira (uint64_t) -1 à la place. Notez que poll() prend un délai d'attente relatif en millisecondes plutôt qu'un délai d'attente absolu en microsecondes. Pour convertir le 'us' absolu en 'ms' relatif, utilisez un code comme celui-ci :

uint64_t t;
int msec;
sd_journal_get_timeout(m, &t);
if (t == (uint64_t) -1)
  msec = -1;
else {
  struct timespec ts;
  uint64_t n;
  clock_gettime(CLOCK_MONOTONIC, &ts);
  n = (uint64_t) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
  msec = t > n ? (int) ((t - n + 999) / 1000) : 0;
}

Le code ci-dessus ne fait aucun contrôle d'erreur par souci de brièveté. L'entier msec calculé peut être passé directement en paramètre de délai d'attente de poll().

Après chaque réveil de poll(), sd_journal_process() doit être appelé pour traiter les événements. Cet appel indiquera également quel type de changement a été détecté (voir ci-dessous ; notez que les réveils inopinés sont possibles).

Une alternative synchrone à l'utilisation de sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout() et sd_journal_process() est sd_journal_wait(). Elle attendra de manière synchrone jusqu'à ce que le journal soit modifié. Le temps maximum pendant lequel cet appel dort peut être contrôlé avec le paramètre timeout_usec. Passez (uint64_t) -1 pour attendre indéfiniment. En interne, cet appel combine simplement sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout(), poll() et sd_journal_process() en un seul.

sd_journal_reliable_fd() peut être utilisé pour vérifier si les événements de réveil du descripteur de fichier renvoyé par sd_journal_get_fd() sont connus pour être déclenchés rapidement. Sur certains systèmes de fichiers où les événements de changement de fichier de l'OS ne sont pas disponibles (comme NFS), les changements doivent être sondés de manière répétée, et sont donc détectés avec une latence considérable. Cet appel renverra une valeur positive si les changements du journal sont détectés rapidement et zéro s'ils nécessitent d'être sondés. Notez qu'il n'est généralement pas nécessaire d'invoquer cette fonction directement car sd_journal_get_timeout() demandera de toute façon des délais d'attente appropriés.

Notez que toutes les interfaces de notification de changement ci-dessus ne signalent pas les changements instantanément. Des latences sont introduites pour plusieurs raisons : comme mentionné, certains backends de stockage nécessitent une interrogation basée sur le temps, dans d'autres cas les réveils sont optimisés en regroupant les événements, et l'OS introduit des latences supplémentaires de planification d'E/S/CPU.

VALEUR RENVOYÉE

sd_journal_get_fd() renvoie un descripteur de fichier valide en cas de succès ou un code d'erreur négatif de style errno.

sd_journal_get_events() renvoie une combinaison de POLLIN, POLLOUT et similaires en cas de succès ou un code d'erreur négatif de style errno.

sd_journal_reliable_fd() renvoie un entier positif si le descripteur de fichier renvoyé par sd_journal_get_fd() déclenchera immédiatement des réveils pour tous les changements du journal. Renvoie 0 s'il peut y avoir une latence impliquée.

sd_journal_process() et sd_journal_wait() renvoient un code d'erreur négatif de style errno, ou l'un de SD_JOURNAL_NOP, SD_JOURNAL_APPEND ou SD_JOURNAL_INVALIDATE en cas de succès :

•Si SD_JOURNAL_NOP est renvoyé, le journal n'a pas changé depuis la dernière invocation.
•Si SD_JOURNAL_APPEND est renvoyé, de nouvelles entrées ont été ajoutées à la fin du journal. Dans ce cas, il suffit de continuer à lire à l'ancienne position de fin du journal pour lire les entrées nouvellement ajoutées.
•Si SD_JOURNAL_INVALIDATE, des fichiers de journal ont été ajoutés ou supprimés de l'ensemble des fichiers de journal surveillés (par exemple, en raison d'une rotation ou d'un nettoyage), et par conséquent, des entrées peuvent être apparues ou disparues à des endroits arbitraires dans le flux de log, potentiellement avant ou après l'ancienne fin du flux de log. Si SD_JOURNAL_INVALIDATE est renvoyé, les interfaces utilisateur en visualisation directe qui souhaitent refléter à l'écran l'état précis des données de log sur le disque devraient probablement rafraîchir leur affichage complet (par rapport au curseur de l'entrée de log en haut de l'écran). Les programmes uniquement intéressés par un flux de données de log strictement séquentiel peuvent traiter SD_JOURNAL_INVALIDATE de la même manière que SD_JOURNAL_APPEND, ignorant ainsi toute modification de la vue du log antérieure à l'ancienne fin du flux de log.

SÉCURITÉ DES SIGNAUX

En général, sd_journal_get_fd(), sd_journal_get_events() et sd_journal_get_timeout() ne sont *pas* « async signal safe » au sens de signal-safety(7). Cependant, seul le premier appel à l'une de ces trois fonctions effectue des opérations non sûres, donc les appels ultérieurs *sont* sûrs.

sd_journal_process() et sd_journal_wait() ne sont pas sûrs. sd_journal_reliable_fd() est sûr.

NOTES

Toutes les fonctions décrites ici sont indépendantes des threads et un seul thread peut opérer sur un objet donné à un moment donné. Différents threads peuvent accéder au même objet à des moments différents. Plusieurs objets indépendants peuvent être utilisés à partir de différents threads en parallèle.

Les fonctions décrites ici sont disponibles sous forme de bibliothèque partagée, qui peut être compilée et liée avec le fichier libsystemd pkg-config(1).

SYNOPIS

DESCRIPTION

Cette fonction est utilisée pour obtenir le descripteur de lecture du journal systemd. Le descripteur est utilisé pour effectuer des opérations de lecture et d'écriture sur le journal.

VALEUR DE RETOUR

La fonction retourne le descripteur de lecture du journal systemd.

SÉCURITÉ DES SIGNAUX

Cette fonction est sûre en ce qui concerne les signaux.

NOTES

Note : Cette fonction ne gère pas les erreurs.

EXEMPLES

Exemple d'utilisation :


/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <poll.h>
#include <time.h>
#include <systemd/sd-journal.h>
int wait_for_changes(sd_journal *j) {
  uint64_t t;
  int msec;
  struct pollfd pollfd;
  sd_journal_get_timeout(j, &t);
  if (t == (uint64_t) -1)
    msec = -1;
  else {
    struct timespec ts;
    uint64_t n;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    n = (uint64_t) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
    msec = t > n ? (int) ((t - n + 999) / 1000) : 0;
  }
  pollfd.fd = sd_journal_get_fd(j);
  pollfd.events = sd_journal_get_events(j);
  poll(&pollfd, 1, msec);
  return sd_journal_process(j);
}
