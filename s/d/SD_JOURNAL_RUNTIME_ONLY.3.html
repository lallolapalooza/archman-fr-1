SD_JOURNAL_OPEN(3) sd_journal_open SD_JOURNAL_OPEN(3)

NOM

sd_journal_open, sd_journal_open_directory, sd_journal_open_directory_fd, sd_journal_open_files, sd_journal_open_files_fd, sd_journal_open_namespace, sd_journal_close, sd_journal, SD_JOURNAL_LOCAL_ONLY, SD_JOURNAL_RUNTIME_ONLY, SD_JOURNAL_SYSTEM, SD_JOURNAL_CURRENT_USER, SD_JOURNAL_OS_ROOT, SD_JOURNAL_ALL_NAMESPACES, SD_JOURNAL_INCLUDE_DEFAULT_NAMESPACE, SD_JOURNAL_TAKE_DIRECTORY_FD - Ouvre le journal système en lecture

SYNOPIS

#include <systemd/sd-journal.h>

int sd_journal_open(sd_journal ** ret, int flags);

int sd_journal_open_namespace(sd_journal ** ret, const char *namespace, int flags);

int sd_journal_open_directory(sd_journal ** ret, const char *path, int flags);

int sd_journal_open_directory_fd(sd_journal ** ret, int fd, int flags);

int sd_journal_open_files(sd_journal ** ret, const char *const *paths, int flags);

int sd_journal_open_files_fd(sd_journal ** ret, int fds[], unsigned n_fds, int flags);

void sd_journal_close(sd_journal *j);

DESCRIPTION

sd_journal_open() ouvre le journal système en lecture. Il recherchera automatiquement tous les fichiers journaux et les fusionnera lors de la lecture. Le premier argument attend un pointeur vers un pointeur sd_journal, qui, en cas de succès, contiendra un objet de contexte du journal. Le second argument est un champ de drapeaux, qui peut se composer des drapeaux suivants combinés par OR : SD_JOURNAL_LOCAL_ONLY garantit que seuls les fichiers journaux générés sur la machine locale sont ouverts. SD_JOURNAL_RUNTIME_ONLY garantit que seuls les fichiers journaux volatils sont ouverts, excluant ceux qui sont stockés sur un support persistant. SD_JOURNAL_SYSTEM entraînera l'ouverture des fichiers journaux des services système et du noyau (par opposition aux processus de session des utilisateurs). SD_JOURNAL_CURRENT_USER entraînera l'ouverture des fichiers journaux de l'utilisateur actuel. Si ni SD_JOURNAL_SYSTEM ni SD_JOURNAL_CURRENT_USER ne sont spécifiés, tous les types de fichiers journaux seront ouverts.

sd_journal_open_namespace() est similaire à sd_journal_open() mais prend un paramètre supplémentaire namespace qui spécifie l'espace de noms de journal sur lequel opérer. Si le paramètre est NULL, l'appel est identique à sd_journal_open(). S'il n'est pas NULL, seules les données de l'espace de noms identifié par le paramètre seront accessibles. Cet appel comprend deux drapeaux supplémentaires : si SD_JOURNAL_ALL_NAMESPACES est spécifié, le paramètre namespace est ignoré et tous les espaces de noms définis sont accessibles simultanément ; si SD_JOURNAL_INCLUDE_DEFAULT_NAMESPACE est spécifié, l'espace de noms spécifié et l'espace de noms par défaut sont accessibles, mais aucun autre (ce drapeau n'a aucun effet lorsque namespace est passé comme NULL). Pour plus de détails sur les espaces de noms de journaux, voir systemd-journald.service(8).

sd_journal_open_directory() est similaire à sd_journal_open() mais prend un chemin de répertoire absolu comme argument. Tous les fichiers journaux dans ce répertoire seront ouverts et fusionnés automatiquement. Cet appel prend également un argument de drapeaux. Les paramètres de drapeaux acceptés par cet appel sont SD_JOURNAL_OS_ROOT, SD_JOURNAL_SYSTEM et SD_JOURNAL_CURRENT_USER. Si SD_JOURNAL_OS_ROOT est spécifié, les fichiers journaux sont recherchés sous les chemins habituels /var/log/journal et /run/log/journal, au lieu d'être directement sous le chemin spécifié. Les deux autres drapeaux limitent les fichiers qui sont ouverts, de la même manière que dans sd_journal_open().

sd_journal_open_directory_fd() est similaire à sd_journal_open_directory(), mais prend un descripteur de fichier faisant référence à un répertoire dans le système de fichiers au lieu d'un chemin absolu. En plus des drapeaux acceptés par sd_journal_open_directory(), cette fonction accepte également SD_JOURNAL_TAKE_DIRECTORY_FD. Si SD_JOURNAL_TAKE_DIRECTORY_FD est spécifié, la fonction prendra la propriété du descripteur de fichier spécifié avec succès et le fermera avec sd_journal_close(), de sorte que l'appelant de la fonction ne doive pas fermer le descripteur. Lorsque le drapeau n'est pas spécifié, sd_journal_close() ne fermera pas le descripteur, de sorte que l'appelant doit le fermer après sd_journal_close().

sd_journal_open_files() est similaire à sd_journal_open() mais prend une liste de chemins de fichiers terminée par NULL comme argument. Tous les fichiers seront ouverts et fusionnés automatiquement. Cet appel prend également un argument de drapeaux, mais il doit être passé comme 0, car aucun drapeau n'est actuellement compris pour cet appel. Note : cette fonction est utile uniquement pour le débogage sur un journal en direct, car les fichiers journaux individuels peuvent être mis en rotation à tout moment, et l'ouverture de fichiers spécifiques est intrinsèquement sujette à des conditions de concurrence.

sd_journal_open_files_fd() est similaire à sd_journal_open_files() mais prend un tableau de descripteurs de fichiers qui doivent faire référence à des fichiers journaux, au lieu d'une liste de chemins de fichiers du système de fichiers. Passez le tableau de descripteurs comme deuxième argument, et le nombre d'entrées du tableau comme troisième. Le paramètre de drapeaux doit être passé comme 0.

Les objets sd_journal ne peuvent pas être utilisés dans le processus enfant après un fork. Les fonctions qui prennent un objet de journal comme argument (sd_journal_next() et autres) renverront -ECHILD après un fork.

sd_journal_close() fermera le contexte du journal alloué avec sd_journal_open() ou sd_journal_open_directory() et libérera ses ressources.

Lors de l'ouverture du journal, seuls les fichiers journaux accessibles à l'utilisateur qui appelle seront ouverts. Si les fichiers journaux ne sont pas accessibles à l'utilisateur, cela sera ignoré silencieusement.

Voir sd_journal_next(3) pour un exemple sur la façon d'itérer à travers le journal après l'avoir ouvert avec sd_journal_open().

L'objet de contexte du journal renvoyé par sd_journal_open() fait référence à une entrée de journal spécifique comme courante, similaire à un descripteur de fichier dans un système de fichiers classique, mais sans positions absolues. Il peut être modifié avec sd_journal_next(3) et sd_journal_seek_head(3) et les appels associés. La position d'entrée actuelle peut être exportée dans des chaînes de curseur, accessible via sd_journal_get_cursor(3). Les chaînes de curseur peuvent être utilisées globalement pour identifier de manière stable une entrée de journal spécifique, puis la rechercher (ou si l'entrée spécifique n'est pas disponible localement, son entrée la plus proche dans le temps) via sd_journal_seek_cursor(3).

La notification des changements du journal est disponible via sd_journal_get_fd() et les appels associés.

VALEUR RENVOYÉE

Les appels à sd_journal_open(), sd_journal_open_directory() et sd_journal_open_files() renvoient 0 en cas de succès ou un code d'erreur errno négatif. sd_journal_close() ne renvoie rien.

NOTES

Toutes les fonctions listées ici sont indépendantes des threads et seule une seule chaîne peut opérer sur un objet donné à la fois. Différents threads peuvent accéder au même objet à différents moments. Plusieurs objets indépendants peuvent être utilisés par différents threads en parallèle.

Les fonctions décrites ici sont disponibles en tant que bibliothèque partagée, qui peut être compilée et liée avec le fichier libsystemd pkg-config(1).

HISTORIQUE

sd_journal_open(), sd_journal_open_directory() et sd_journal_close() ont été ajoutés dans la version 187.

sd_journal_open_files() a été ajouté dans la version 205.

sd_journal_open_directory_fd() et sd_journal_open_files_fd() ont été ajoutés dans la version 230.

sd_journal_open_namespace() a été ajouté dans la version 245.
