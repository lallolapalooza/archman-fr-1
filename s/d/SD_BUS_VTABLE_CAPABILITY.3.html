DESCRIPTION

sd_bus_add_object_vtable() est utilisé pour déclarer des attributs pour le chemin d'objet path connecté à la connexion bus bus sous l'interface interface. La table vtable peut contenir des déclarations de propriétés utilisant SD_BUS_PROPERTY() ou SD_BUS_WRITABLE_PROPERTY(), des déclarations de méthodes utilisant SD_BUS_METHOD(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), ou SD_BUS_METHOD_WITH_NAMES_OFFSET(), et des déclarations de signaux utilisant SD_BUS_SIGNAL_WITH_NAMES() ou SD_BUS_SIGNAL(), voir ci-dessous. Le paramètre userdata contient un pointeur qui sera passé à diverses fonctions de rappel. Il peut être spécifié comme NULL si aucune valeur n'est nécessaire. Une interface peut avoir n'importe quel nombre de tables vtable qui lui sont attachées.

sd_bus_add_fallback_vtable() est similaire à sd_bus_add_object_vtable(), mais est utilisé pour enregistrer des attributs "de secours". Lors de la recherche d'une déclaration d'attribut, les chemins d'objets bus enregistrés avec sd_bus_add_object_vtable() sont vérifiés en premier. Si aucune correspondance n'est trouvée, les tables vtable de secours sont vérifiées pour chaque préfixe du chemin de l'objet bus, c'est-à-dire en supprimant successivement les derniers composants séparés par des barres obliques. Cela permet d'utiliser la table vtable pour un nombre arbitraire d'objets créés dynamiquement.

Le paramètre find est une fonction utilisée pour localiser l'objet cible en fonction du chemin de l'objet bus path. Elle doit retourner 1 et définir le paramètre de sortie ret_found si l'objet est trouvé, retourner 0 si l'objet n'a pas été trouvé, et retourner un code d'erreur négatif de style errno ou initialiser la structure d'erreur ret_error en cas d'erreur. Le pointeur passé dans ret_found sera utilisé comme paramètre userdata pour les fonctions de rappel (décalé par les décalages offset tels que spécifiés dans les entrées vtable).

sd_bus_add_object() attache un rappel directement au chemin d'objet path. Un chemin d'objet peut avoir n'importe quel nombre de rappels qui lui sont attachés. Chaque rappel est ajouté en tête de la liste des rappels qui sont toujours appelés dans l'ordre. sd_bus_add_fallback() est similaire à sd_bus_add_object() mais s'applique aux chemins de secours à la place.

sd_bus_add_filter() installe un rappel qui est invoqué pour chaque message D-Bus entrant. Les filtres peuvent être utilisés pour gérer la logique commune à tous les messages reçus par un service (par exemple, authentification ou autorisation).

Lorsqu'une requête est reçue, les rappels associés sont appelés séquentiellement jusqu'à ce qu'un rappel retourne un entier non nul. Retourner zéro d'un rappel pour donner à d'autres rappels la chance de traiter la requête. Les rappels sont appelés dans l'ordre suivant : d'abord, les rappels globaux installés avec sd_bus_add_filter() sont appelés. Deuxièmement, les rappels attachés directement au chemin de l'objet de la requête sont appelés, suivis par les rappels de méthodes D-Bus attachés au chemin de l'objet, à l'interface et au membre de la requête. Enfin, les rappels de propriétés attachés au chemin de l'objet, à l'interface et au membre de la requête sont appelés. Si le dernier rappel retourne zéro, une erreur

SD_BUS_METHOD_WITH_ARGS_OFFSET(), SD_BUS_METHOD_WITH_ARGS()

Define un método D-Bus con el nombre member, argumentos args y resultado result. args espera una secuencia de pares tipo/nombre envueltos en la macro SD_BUS_ARGS(). Los elementos en índices pares de esta lista describen los tipos de los argumentos del método. La firma del parámetro del método es la concatenación de todos los literales de cadena en índices pares de args. Si un método no tiene parámetros, pase SD_BUS_NO_ARGS a args. Los elementos en índices impares describen los nombres de los argumentos del método. result espera una secuencia de pares tipo/nombre envueltos en la macro SD_BUS_RESULT() en el mismo formato que SD_BUS_ARGS(). La firma del resultado del método es la concatenación de todos los literales de cadena en índices pares de result. Si un método no tiene resultado, pase SD_BUS_NO_RESULT a result. Tenga en cuenta que se espera que los tipos de los argumentos sean literales de cadena entre comillas y los nombres de los argumentos se espera que sean literales de cadena sin comillas. Vea a continuación un ejemplo completo.

La función de manejador handler debe ser de tipo sd_bus_message_handler_t. Se llamará para manejar los mensajes que invocan este método. Recibe un puntero que es el parámetro userdata pasado a la función de registro compensada por offset bytes. Esto puede usarse para pasar punteros a diferentes campos de la misma estructura a diferentes métodos de la misma vtable. Para enviar una respuesta desde handler, llame a sd_bus_reply_method_return(3) con el mensaje que invocó la devolución de llamada. El parámetro flags es una combinación de flags, vea a continuación.

SD_BUS_METHOD_WITH_NAMES_OFFSET(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), SD_BUS_METHOD()

Define un método D-Bus con el nombre member, firma de parámetro signature y resultado result. Los parámetros in_names y out_names especifican los nombres de los argumentos de entrada y salida en la firma de la función. in_names y out_names deben crearse usando la macro SD_BUS_PARAM(), vea a continuación. En otros aspectos, esta macro se comporta exactamente como SD_BUS_METHOD_WITH_ARGS_OFFSET().

SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET() y SD_BUS_METHOD() son variantes que especifican desplazamiento cero (userdata se pasa sin cambios), dejan los nombres sin definir (es decir, sin nombres de parámetros), o ambos.

Se prefiere usar SD_BUS_METHOD_WITH_ARGS_OFFSET() y SD_BUS_METHOD_WITH_ARGS() en lugar de estas macros, ya que permiten especificar tipos de argumento y nombres juntos, lo cual es menos inconveniente que especificar primero todos los tipos de argumento y luego todos los nombres de argumento.

SD_BUS_WRITABLE_PROPERTY(), SD_BUS_PROPERTY()

Define una propiedad D-Bus con el nombre member y firma de valor signature. Los parámetros get y set son los métodos de getter y setter. Se llaman con un puntero que es el parámetro userdata pasado a la función de registro compensada por offset bytes. Esto puede usarse para pasar punteros a diferentes campos de la misma estructura a diferentes setters y getters de la misma vtable. El parámetro flags es una combinación de flags, vea a continuación.

Los métodos de getter y setter pueden omitirse (especificados como NULL), si la propiedad es de uno de los tipos básicos o "as" en el caso de propiedades de solo lectura. En tales casos, los parámetros userdata y offset deben juntos apuntar a un valor válido del tipo correspondiente. Se proporcionan un setter y un getter por defecto, que simplemente copian el argumento entre esta variable y el mensaje.

SD_BUS_PROPERTY() se utiliza para definir una propiedad de solo lectura.

SD_BUS_PARAM()

Los nombres de los parámetros deben envolverse con esta macro, vea el ejemplo a continuación.

El parámetro flags se usa para especificar una combinación de anotaciones D-Bus[1].

SD_BUS_VTABLE_DEPRECATED

Marca esta entrada de vtable como obsoleta usando la anotación org.freedesktop.DBus.Deprecated en los datos de introspección. Si se especifica para SD_BUS_VTABLE_START(), la anotación se aplica a la interfaz que la contiene.

SD_BUS_VTABLE_HIDDEN

Marca esta entrada de vtable como oculta. No se mostrará en los datos de introspección. Si se especifica para SD_BUS_VTABLE_START(), todas las entradas de la lista están ocultas.

SD_BUS_VTABLE_METHOD_NO_REPLY

Marca esta entrada de vtable como un método que no devolverá una respuesta usando la anotación org.freedesktop.DBus.Method.NoReply en los datos de introspección.

SD_BUS_VTABLE_PROPERTY_CONST, SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE, SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION

Estas tres flags corresponden a diferentes valores de la anotación org.freedesktop.DBus.Property.EmitsChangedSignal, que especifica si se emite la señal org.freedesktop.DBus.Properties.PropertiesChanged cuando la propiedad cambia. SD_BUS_VTABLE_PROPERTY_CONST corresponde a const y significa que la propiedad nunca cambia durante la vida útil del objeto al que pertenece, por lo que no se necesita emitir ninguna señal. SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE corresponde a true y significa que se emite la señal. SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION corresponde a invalidates y significa que se emite la señal, pero el valor no se incluye en la señal.

SD_BUS_VTABLE_PROPERTY_EXPLICIT

Marca esta entrada de vtable de propiedad como que requiere una solicitud explícita para mostrar el valor (generalmente porque el valor es grande o lento de calcular). Esta entrada no puede combinarse con SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE, y no se mostrará en listas de propiedades por defecto (por ejemplo, busctl introspect). Esto corresponde a la anotación org.freedesktop.systemd1.Explicit en los datos de introspección.

SD_BUS_VTABLE_SENSITIVE

Marca esta entrada de vtable de método como que procesa datos sensibles. Cuando está establecido, los mensajes de invocación de método y sus mensajes de respuesta de salida se marcan como sensibles usando sd_bus_message_sensitive(3), por lo que se eliminan de la memoria cuando se liberan.

SD_BUS_VTABLE_ABSOLUTE_OFFSET

Marca esta entrada de vtable de método o propiedad como que los datos del usuario están en un desplazamiento fijo.

Si un callback fue invocado para manejar una solicitud que espera una respuesta y devuelve un valor negativo, el valor se interpreta como un código de error errno y se envía como un error D-Bus como si se hubiera llamado sd_bus_reply_method_errno(3). Además, todos los callbacks tienen un parámetro de salida slot que puede usarse para proporcionar información de error más detallada. Si ret_error se establece cuando el callback se completa, el error D-Bus correspondiente se envía como si se hubiera llamado sd_bus_reply_method_error(3). Cualquier error almacenado en ret_error tiene prioridad sobre cualquier valor negativo devuelto por el mismo callback al determinar qué error se debe enviar al llamador. Use sd_bus_error_set(3) o una de sus variantes para establecer ret_error y devolver un valor negativo de un callback con una sola llamada de función. Para enviar una respuesta de error después de que un callback ya haya finalizado, use sd_bus_reply_method_errno(3) o una de sus variantes.

Para todas las funciones, se crea una ranura de coincidencia internamente. Si el parámetro de salida slot es NULL, se crea un objeto de ranura "flotante", vea sd_bus_slot_set_floating(3). De lo contrario, se devuelve un puntero al objeto de ranura. En ese caso, la referencia al objeto de ranura debe ser destruida cuando la vtable ya no sea necesaria, vea sd_bus_slot_unref(3).

SD_BUS_VTABLE_CAPABILITY(capacité)

L'accès à cette entrée de vtable sera autorisé si le processus appelant possède la capacité capacité, comme décrit dans sd_bus_query_sender_privilege(3). Si utilisé pour SD_BUS_VTABLE_START(), fournit une valeur par défaut pour toutes les entrées du tableau. Si non spécifié, soit pour une entrée individuelle, soit pour tout le tableau, CAP_SYS_ADMIN est vérifié par défaut. Voir capabilities(7) pour des informations sur les capacités.

Notez que les entrées de vtable peuvent être marquées comme non privilégiées et l'ensemble du bus peut être marqué comme fiable, voir la discussion sur SD_BUS_VTABLE_UNPRIVILEGED ci-dessous.

SD_BUS_VTABLE_UNPRIVILEGED

Marque cette entrée de vtable comme non privilégiée. L'accès aux entrées privilégiées est limité aux utilisateurs ayant les capacités appropriées, comme décrit ci-dessus. En pratique, de nombreuses entrées de vtable sont marquées comme non privilégiées, et sont soit ouvertes à tous, soit la décision d'autoriser l'accès est prise plus tard, par exemple en déléguant à polkit[2].

L'ensemble du bus peut être marqué comme fiable, auquel cas les annotations au niveau de l'entrée sont ignorées, voir sd_bus_set_trusted(3).

Lorsque non spécifié, l'annotation org.freedesktop.systemd1.Privileged avec la valeur "true" sera affichée dans les données d'introspection.

SD_BUS_VTABLE_UNPRIVILEGED ne peut pas être appliqué aux propriétés en lecture seule, mais l'accès en lecture (aux propriétés en lecture seule et en écriture) est toujours illimité.

Notez que cette page décrit les contrôles implémentés dans le client D-Bus. Le serveur D-Bus a une politique supplémentaire qui peut autoriser ou refuser les connexions, voir "FICHIER DE CONFIGURATION" dans dbus-daemon(1).

EXEMPLES

Exemple 1. Créer un écouteur simple sur le bus

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <errno.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdlib.h>
#include <stdio.h>
#include <systemd/sd-bus.h>
#define _cleanup_(f) __attribute__((cleanup(f)))
typedef struct object {
  char *name;
  uint32_t number;
} object;
static int method(sd_bus_message *m, void *userdata, sd_bus_error *error) {
  int r;
  printf("Got called with userdata=%p\n", userdata);
  if (sd_bus_message_is_method_call(m,
                                    "org.freedesktop.systemd.VtableExample",
                                    "Method4"))
    return 1;
  const char *string;
  r = sd_bus_message_read(m, "s", &string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_message_read() failed: %s\n", strerror(-r));
    return 0;
  }
  r = sd_bus_reply_method_return(m, "s", string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_reply_method_return() failed: %s\n", strerror(-r));
    return 0;
  }
  return 1;
}
static const sd_bus_vtable vtable[] = {
        SD_BUS_VTABLE_START(0),
        SD_BUS_METHOD(
            "Method1", "s", "s", method, 0),
        SD_BUS_METHOD_WITH_NAMES_OFFSET(
            "Method2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            "s", SD_BUS_PARAM(returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_DEPRECATED),
        SD_BUS_METHOD_WITH_ARGS_OFFSET(
            "Method3",
            SD_BUS_ARGS("s", string, "o", path),
            SD_BUS_RESULT("s", returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_METHOD_WITH_ARGS(
            "Method4",
            SD_BUS_NO_ARGS,
            SD_BUS_NO_RESULT,
            method,
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_SIGNAL(
            "Signal1",
            "so",
            0),
        SD_BUS_SIGNAL_WITH_NAMES(
            "Signal2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            0),
        SD_BUS_SIGNAL_WITH_ARGS(
            "Signal3",
            SD_BUS_ARGS("s", string, "o", path),
            0),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticStringProperty", "s", NULL, NULL,
            offsetof(object, name),
            SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticIntegerProperty", "u", NULL, NULL,
            offsetof(object, number),
            SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION),
        SD_BUS_VTABLE_END
};
int main(int argc, char **argv) {
  _cleanup_(sd_bus_flush_close_unrefp) sd_bus *bus = NULL;
  int r;
  sd_bus_default(&bus);
  object object = { .number = 666 };
  object.name = strdup("name");
  if (!object.name) {
    fprintf(stderr, "OOM\n");
    return EXIT_FAILURE;
  }
  r = sd_bus_add_object_vtable(bus, NULL,
                               "/org/freedesktop/systemd/VtableExample",
                               "org.freedesktop.systemd.VtableExample",
                               vtable,
                               &object);
  if (r < 0) {
    fprintf(stderr, "sd_bus_add_object_vtable() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  r = sd_bus_request_name(bus,
                          "org.freedesktop.systemd.VtableExample",
                          0);
  if (r < 0) {
    fprintf(stderr, "sd_bus_request_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  for (;;) {
    r = sd_bus_wait(bus, UINT64_MAX);
    if (r < 0) {
      fprintf(stderr, "sd_bus_wait() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
    r = sd_bus_process(bus, NULL);
    if (r < 0) {
      fprintf(stderr, "sd_bus_process() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
  }
  r = sd_bus_release_name(bus, "org.freedesktop.systemd.VtableExample");
  if (r < 0) {
    fprintf(stderr, "sd_bus_release_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  free(object.name);
  return 0;
}

VALEUR DE RETOUR

En cas de succès, sd_bus_add_object_vtable() et sd_bus_add_fallback_vtable() renvoient un entier non négatif. En cas d'échec, ils renvoient un code d'erreur négatif de style errno.

Erreurs

Les erreurs renvoyées peuvent indiquer les problèmes suivants :

-EINVAL

L'un des paramètres requis est NULL ou invalide. Une interface D-Bus réservée a été passée en tant que paramètre interface.

-ENOPKG

Le bus ne peut pas être résolu.

-ECHILD

Le bus a été créé dans un processus, une bibliothèque ou une instance de module différent.

-ENOMEM

Erreur d'allocation mémoire.

-EPROTOTYPE

sd_bus_add_object_vtable() et sd_bus_add_fallback_vtable() ont tous deux été appelés pour le même chemin d'objet de bus, ce qui n'est pas autorisé.

-EEXIST

Cette vtable a déjà été enregistrée pour cette interface et ce chemin.

NOTES

Les fonctions décrites ici sont

disponible en tant que bibliothèque partagée, qui peut être compilée et liée avec le fichier pkg-config(1) de libsystemd.

Le code décrit ici utilise getenv(3), qui est déclaré comme n'étant pas sûr pour les threads multiples. Cela signifie que le code appelant les fonctions décrites ici ne doit pas appeler setenv(3) à partir d'un thread parallèle. Il est recommandé de n'appeler setenv() qu'à partir d'une phase précoce du programme, lorsqu'aucun autre thread n'a été démarré.
