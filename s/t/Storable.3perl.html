Storable(3perl) Manuel du programmeur Perl Storable(3perl)

NOM

Storable - persistance pour les structures de données Perl

SYNTAXE

use Storable;
store \%table, 'fichier';
$hashref = retrieve('fichier');
use Storable qw(nstore store_fd nstore_fd freeze thaw dclone);
# Ordre réseau
nstore \%table, 'fichier';
$hashref = retrieve('fichier');        # Pas de nretrieve()
# Stockage vers un fichier déjà ouvert
store_fd \@array, \*STDOUT;
nstore_fd \%table, \*STDOUT;
$aryref = fd_retrieve(\*SOCKET);
$hashref = fd_retrieve(\*SOCKET);
# Sérialisation en mémoire
$serialized = freeze \%table;
%table_clone = %{ thaw($serialized) };
# Clonage profond (récursif)
$cloneref = dclone($ref);
# Verrouillage consultatif
use Storable qw(lock_store lock_nstore lock_retrieve);
lock_store \%table, 'fichier';
lock_nstore \%table, 'fichier';
$hashref = lock_retrieve('fichier');

DESCRIPTION

Le module Storable fournit la persistance des structures de données Perl contenant des objets SCALAR, ARRAY, HASH ou REF, c'est-à-dire tout ce qui peut être stocké commodément sur disque et récupéré ultérieurement.

Il peut être utilisé de manière régulière en appelant "store" avec une référence à l'objet à stocker, ainsi que le nom du fichier où l'image doit être écrite.

La fonction retourne "undef" en cas de problèmes d'E/S ou d'erreurs internes, une valeur vraie sinon. Les erreurs graves sont propagées par une exception "die".

Pour récupérer des données stockées sur disque, utilisez "retrieve" avec un nom de fichier. Les objets stockés dans ce fichier sont recréés en mémoire pour vous, et une *référence* à l'objet racine est retournée. En cas d'erreur d'E/S lors de la récupération, "undef" est retourné. Les autres erreurs graves sont propagées par "die".

Étant donné que le stockage est effectué récursivement, il peut être utile de regrouper des références à des objets partageant un grand volume de données communes dans un seul tableau ou une table de hachage, puis de stocker cet objet. Ainsi, lors de la récupération de tout le contenu, les objets partageront toujours ce qu'ils partageaient à l'origine.

Malgré un petit surcoût en en-tête, vous pouvez stocker dans un fichier déjà ouvert en utilisant la routine "store_fd", et récupérer d'un fichier en utilisant "fd_retrieve". Ces noms ne sont pas importés par défaut, vous devrez donc le faire explicitement si vous avez besoin de ces routines. Le descripteur de fichier que vous fournissez doit déjà être ouvert, en lecture si vous voulez récupérer, et en écriture si vous voulez stocker.

store_fd(\%table, *STDOUT) || die "impossible de stocker vers stdout\n";
$hashref = fd_retrieve(*STDIN);

Vous pouvez également stocker des données au format réseau pour permettre un partage facile entre différentes plateformes, ou lorsque vous stockez sur une socket connue pour être connectée à distance. Les routines à appeler ont un préfixe "n" pour *réseau*, comme dans "nstore" et "nstore_fd". Lors de la récupération, vos données seront correctement restaurées, vous n'aurez donc pas besoin de savoir si vous récupérez des données natives ou réseau. Les nombres à virgule flottante sont stockés sous forme de chaînes pour garantir la portabilité, bien qu'avec le risque de perdre la précision sur les derniers chiffres décimaux.

Lorsque vous utilisez "fd_retrieve", les objets sont récupérés séquentiellement, un pour chaque "store_fd" associé (c'est-à-dire une racine d'objet récursive pour chaque associé).

Si vous êtes plus orienté objet, vous pouvez hériter de Storable et stocker vos objets en invoquant "store" comme méthode. La différence est que la racine de l'arbre à stocker étant une référence bénie (c'est-à-dire un objet) est traitée spécialement, de sorte que lors de la récupération, vous n'obtenez pas une référence à l'objet, mais la référence de l'objet lui-même (le référent béni). (Sinon, vous obtiendriez une référence à l'objet béni).

STOCKAGE EN MÉMOIRE

Le moteur Storable peut également stocker des données dans un scalaire Perl pour les récupérer ensuite. Ceci est principalement utilisé pour "geler" une structure complexe quelque part en mémoire compacte (d'où elle pourrait être envoyée à un autre processus via IPC, car geler la structure la sérialise également). Puis, probablement ailleurs, vous pouvez "dégeler" le scalaire Perl et recréer la structure originale en mémoire.

Heureusement, les routines à appeler s'appellent "freeze" et "thaw". Si vous souhaitez envoyer le scalaire gelé à un autre appareil, utilisez "nfreeze" pour obtenir une image portable.

Note : Geler une structure d'objets puis la dégeler réalise en fait un clonage profond de cette structure :

dclone(.) = thaw(freeze(.))

Storable vous fournit une interface "dclone" qui ne crée pas ce scalaire intermédiaire, mais gèle la structure dans un espace mémoire interne puis la dégèle.

VERROUILLAGE CONSEILLÉ

Les routines "lock_store" et "lock_nstore" sont équivalentes à "store" et "nstore", sauf qu'elles obtiennent un verrou exclusif sur le fichier avant d'écrire. De même, "lock_retrieve" fait la même chose que "retrieve", mais obtient également un verrou partagé sur le fichier avant de lire.

Comme tout système de verrouillage conseillé, la protection ne fonctionne que si vous utilisez systématiquement "lock_store" et "lock_retrieve". Si une partie de votre application utilise "store" tandis que l'autre utilise "lock_retrieve", vous n'aurez aucune protection.

Le verrouillage conseillé interne est implémenté en utilisant la routine flock() de Perl. Si votre système ne prend pas en charge une forme quelconque de flock(), ou si vous partagez vos fichiers sur NFS, vous pourriez vouloir utiliser d'autres types de verrouillage en utilisant des modules comme LockFile::Simple, qui verrouillent un fichier par un enregistrement du système de fichiers, au lieu de verrouiller le descripteur de fichier.

VITESSE

Le cœur de Storable est écrit en C pour une vitesse décente. Des optimisations supplémentaires ont été apportées au niveau de l'interne de Perl, sacrifiant l'encapsulation au profit de la vitesse.

REPRÉSENTATION CANONIQUE

Normalement, Storable stocke les éléments des tables dans l'ordre où Perl les stocke en interne, c'est-à-dire de manière pseudo-aléatoire. Si vous définissez $Storable::canonical à une valeur "VRAI", Storable stockera les tables avec les éléments triés par leurs clés. Cela permet de comparer des structures de données en comparant leurs représentations gelées (ou même leurs représentations compressées et gelées), ce qui peut être utile pour créer des tables de recherche pour des requêtes complexes.

La représentation canonique n'implique pas l'ordre réseau ; ce sont deux configurations orthogonales.

RÉFÉRENCES DE CODE

Depuis la version 2.05 de Storable, les références de code peuvent être sérialisées avec l'aide de B::Deparse. Pour activer cette fonctionnalité, définissez $Storable::Deparse à une valeur vraie. Pour activer la désérialisation, définissez $Storable::Eval à une valeur vraie. Vous devez être conscient que la désérialisation se fait par "eval", qui est dangereux si le fichier Storable contient des données malveillantes. Vous pouvez définir $Storable::Eval à une référence de sous-routine qui sera utilisée à la place de "eval". Voir l'exemple ci-dessous d'un environnement Safe pour désérialiser des références de code.

Si $Storable::Deparse et/ou $Storable::Eval sont définis à des valeurs fausses, la valeur de $Storable::forgive_me (voir ci-dessous) sera respectée lors de la sérialisation et de la désérialisation.

GESTION DES ERREURS

Storable utilise le paradigme de "l'exception", dans lequel il n'essaie pas de résoudre les échecs : si quelque chose de mal se produit, une exception est générée du point de vue de l'appelant (voir Carp et croak()). Utilisez eval {} pour capturer de telles exceptions.

Lorsque Storable fait un croak(), il tente de signaler l'erreur en utilisant la routine logcroak() de la classe "Log::Agent", si elle est disponible.

Les erreurs normales sont signalées par store() ou retrieve() en renvoyant "undef". De telles erreurs sont généralement des erreurs d'E/S (ou des erreurs de flux tronqué lors de la récupération).

Lorsque Storable génère l'erreur "Max. recursion depth with nested structures exceeded", nous sommes déjà en dehors de la pile. Cependant, dans certaines anciennes versions de Perl, le nettoyage d'une structure récursive s'appelle récursivement, ce qui peut provoquer des débordements de pile lors du nettoyage. Cette structure n'est pas nettoyée correctement et n'est détruite que lors de la destruction globale.

POUR LES SORCIERS SEULEMENT

Hooks

Toute classe peut définir des hooks qui seront appelés lors du processus de sérialisation et de désérialisation d'objets qui sont des instances de cette classe. Ces hooks peuvent redéfinir la manière dont la sérialisation est effectuée (et par conséquent, comment la désérialisation symétrique doit être effectuée).

Étant donné ce que nous avons mentionné ci-dessus :

dclone(.) = thaw(freeze(.))

tout ce que nous dirons sur les hooks devrait également s'appliquer au clonage profond. Cependant, les hooks savent si l'opération est juste une sérialisation ou un clonage.

Par conséquent, lorsque les hooks sont impliqués dans la sérialisation :

dclone(.) <> thaw(freeze(.))

Eh bien, nous pourrions les garder synchronisés, mais il n'y a aucune garantie qu'ils le soient toujours dans les classes écrites par d'autres. De plus, il n'y a pas grand-chose à y gagner : un hook de sérialisation pourrait ne conserver qu'une seule propriété d'un objet, ce qui n'est probablement pas ce qui devrait se passer lors d'un clonage profond du même objet.

Voici l'interface de hooking :

"STORABLE_freeze" obj, cloning
Le hook de sérialisation, appelé lors de la sérialisation de l'objet. Il peut être hérité ou défini dans la classe elle-même, comme n'importe quelle autre méthode.

Arguments : obj est l'objet à sérialiser, cloning est un indicateur indiquant si nous sommes dans un dclone() ou une sérialisation régulière via store() ou freeze().

Valeur de retour : Une LISTE "($serialized, $ref1, $ref2, ...)" où $serialized est la forme sérialisée à utiliser, et les $ref1, $ref2, etc. sont des références supplémentaires que vous souhaitez autoriser le moteur Storable à sérialiser.

Lors de la désérialisation, vous recevrez la même LISTE, mais toutes les références supplémentaires pointeront vers la structure désérialisée.

Si c'est la première fois que le hook s'exécute dans un flux de sérialisation, vous pouvez renvoyer une liste vide. Cela indiquera au moteur Storable de supprimer ce hook pour cette classe et, par conséquent, de revenir à la sérialisation par défaut des données Perl sous-jacentes. Le hook sera traité normalement lors de la prochaine sérialisation.

À moins que vous ne sachiez mieux, un hook de sérialisation devrait toujours dire :

sub STORABLE_freeze {
    my ($self, $cloning) = @_;
    return if $cloning;         # Sérialisation régulière par défaut
    ...
}

pour maintenir le sens approprié de dclone().

"STORABLE_thaw" obj, cloning, serialized, ...
Le hook de désérialisation appelé lors de la désérialisation de l'objet. Mais attendez : si nous désérialisons, il n'y a pas encore d'objet... est-ce le cas ?

Incorrect : le moteur Storable crée un objet vide pour vous. Si vous connaissez Eiffel, vous pouvez considérer "STORABLE_thaw" comme une routine de création alternative.

Cela signifie que le hook peut être hérité comme n'importe quelle autre méthode, et obj est votre référence "benie" pour cette instance particulière.

Les autres arguments doivent vous être familiers si vous connaissez "STORABLE_freeze" : cloning est vrai lorsque nous sommes dans une opération de clonage profond, serialized est la chaîne sérialisée que vous avez renvoyée au moteur dans "STORABLE_freeze", et il peut y avoir une liste optionnelle de références, dans le même ordre que vous les avez fournies lors de la sérialisation, pointant vers les objets désérialisés (qui ont été traités par le moteur Storable).

Si le moteur Storable ne trouve pas de routine "STORABLE_thaw", il essaie de charger la classe par référence dynamique (en utilisant le nom du package "benie"), puis essaie à nouveau. S'il ne parvient pas à localiser la routine à ce stade, le moteur fait un croak(). Notez que ce mécanisme échouera si vous définissez plusieurs classes dans le même fichier, mais perlmod vous avertira.

Il vous appartient d'utiliser ces informations pour remplir obj comme vous le souhaitez.

Valeur de retour : aucune.

"STORABLE_attach" class, cloning, serialized
While "STORABLE_freeze" and "STORABLE_thaw" are useful for classes where each instance is independent, this mechanism has difficulty (or is incompatible) with objects that exist as common process-level or system-level resources, such as singleton objects, database pools, caches, or memoized objects.

The alternative "STORABLE_attach" method provides a solution for these shared objects. Instead of "STORABLE_freeze" --> "STORABLE_thaw", you implement "STORABLE_freeze" --> "STORABLE_attach" instead.

Arguments : class est la classe à laquelle nous nous attachons, cloning est un indicateur indiquant si nous sommes dans un dclone() ou une désérialisation régulière via thaw(), et serialized est la chaîne stockée pour l'objet ressource.

Étant donné que ces objets ressources sont considérés comme la propriété de l'ensemble du processus/système, et non comme la propriété de l'objet en cours de sérialisation, ils ne devraient pas inclure de références dans la chaîne sérialisée. Par conséquent, dans n'importe quelle classe, vous ne devriez pas inclure de références dans la chaîne sérialisée.

Valeur de retour : aucune.

Implémente "STORABLE_attach", la méthode "STORABLE_freeze" ne peut pas retourner de références et "Storable" lèvera une erreur si "STORABLE_freeze" essaie de retourner des références.

Toutes les informations nécessaires pour ré-attacher l'objet partagé doivent être contenues uniquement dans la chaîne retournée par "STORABLE_freeze". Sinon, "STORABLE_freeze" se comporte comme d'habitude pour les classes "STORABLE_attach".

Parce que "STORABLE_attach" reçoit la classe (et non un objet), il retourne également l'objet directement, sans modifier l'objet passé.

Valeur retournée: objet de type "class"

Prédicats

Les prédicats ne sont pas exportables. Ils doivent être appelés avec le préfixe du package Storable.

"Storable::last_op_in_netorder"
Le prédicat Storable::last_op_in_netorder() indiquera si l'ordre réseau a été utilisé lors de la dernière opération de stockage ou de récupération. Si vous ne savez pas comment l'utiliser, ignorez-le simplement.
"Storable::is_storing"
Retourne vrai si vous êtes dans une opération de stockage (via le hook "STORABLE_freeze").
"Storable::is_retrieving"
Retourne vrai si vous êtes dans une opération de récupération (via le hook "STORABLE_thaw").

Récursion

Avec les hooks, vous obtenez le pouvoir de ré-appeler le moteur Storable. En fait, les hooks sont du code Perl régulier, et Storable est pratique pour sérialiser et désérialiser des choses, alors pourquoi ne pas l'utiliser pour gérer la chaîne de sérialisation ?

Bien qu'il y ait quelques points à connaître :

•
De Storable 3.05 à 3.13, nous testons la profondeur de la pile pour les références, tableaux et hachages jusqu'à un maximum d'environ 1200-35000, sinon nous pourrions tomber dans un dépassement de pile. Dans JSON::XS, cette limite est de 512. Avec des références ne référençant pas directement d'autres références, il n'y a pas de telle limite, vous pourriez donc tomber dans un dépassement de pile qui se résout par un segfault.

Ce test et ces vérifications que nous effectuons ont quelques limites :

  • La taille de la pile lors de la compilation peut être différente lors de l'exécution, par exemple, la taille de la pile peut avoir été modifiée avec ulimit(1). Si elle est plus grande lors de l'exécution, Storable pourrait échouer inutilement lors de freeze() ou thaw(). Si elle est plus grande lors de la compilation, Storable pourrait casser le segment lors du traitement d'une structure profonde lors de l'exécution.
  • La taille de la pile peut être différente dans les threads.
  • Les limites de profondeur des tableaux et des hachages sont comprimées séparément contre la même profondeur de récursion, un objet figé avec une grande séquence de tableaux à l'intérieur de multiples hachages profonds pourrait épuiser la pile du processeur sans déclencher la protection de récursion de Storable.

Par conséquent, ils ont maintenant des valeurs par défaut simples au lieu de tests lors de la compilation.

Vous pouvez contrôler la limite de profondeur des tableaux et des hachages en modifiant $Storable::recursion_limit et $Storable::recursion_limit_hash respectivement. Les deux peuvent être réglés à -1 pour empêcher toute vérification de profondeur, bien que cela ne soit pas recommandé.

Si vous voulez tester quelles sont les limites, l'outil stacksize est inclus dans la distribution de "Storable".

  • Si les objets sérialisés par freeze() (par exemple) pointent vers l'objet en cours de sérialisation dans le hook, vous pourriez créer des boucles infinies.
  • Les références partagées entre objets ne seront pas conservées partagées : si nous sérialisons la liste d'objets [A, C] où A et C font tous deux référence au même objet B, et s'il y a un hook de sérialisation dans A qui dit freeze(B), lors de la désérialisation, vous obtiendrez [A', C'] où A' référence B', mais C' référence D, un clone profond de B'. La topologie n'a pas été préservée.
  • La limite de récursion de pile maximale pour votre système est retournée par stack_depth() et stack_depth_hash(). La limite de hachage est généralement la moitié de la taille du tableau et de la limite de référence, car l'API Perl pour les hachages n'est pas optimale.

C'est pourquoi "STORABLE_freeze" vous permet de fournir une liste de références à sérialiser. Le moteur garantit qu'elles seront sérialisées dans le même contexte que les autres objets, de sorte que les objets partagés resteront partagés.

Dans l'exemple précédent [A, C], le hook "STORABLE_freeze" pourrait retourner :

("something", $self->{B})

et la partie B sera sérialisée par le moteur. Dans "STORABLE_thaw", vous obtiendrez la référence à l'objet B' désérialisé pour vous.

Par conséquent, la récursion doit normalement être évitée, mais elle est toujours prise en charge.

Clonage profond

Il existe un module Clone disponible sur CPAN qui implémente le clonage profond de manière native, c'est-à-dire sans geler la mémoire et dégeler le résultat. Il vise à remplacer un jour la méthode dclone() de Storable. Cependant, il ne met pas à jour le support des hooks de Storable pour redéfinir comment le clonage profond est effectué.

Magie de Storable

Oui, il y en a beaucoup :-) Mais plus précisément, sur les systèmes UNIX, il existe un utilitaire appelé "file" qui reconnaît les fichiers de données en fonction de leur contenu (généralement leurs premiers octets). Pour qu'il fonctionne, un fichier appelé magic doit être informé de la signature du contenu. L'emplacement de cette configuration dépend du style UNIX ; c'est souvent quelque chose comme /usr/share/misc/magic ou /etc/magic. Votre administrateur système doit mettre à jour le fichier magic. Les informations de signature sont affichées par défaut sur STDOUT lorsque vous appelez Storable::show_file_magic(). Notez que l'implémentation GNU de l'utilitaire "file", version 3.38 ou ultérieure, s'attend à ce qu'elle dispose d'un support pour reconnaître les fichiers Storable hors du goulot d'étranglement, en plus d'autres types de fichiers Perl.

Vous pouvez également utiliser les fonctions suivantes pour extraire les informations d'en-tête des fichiers Storable :

$info = Storable::file_magic( $filename )
Si le fichier donné est une image Storable, retourne un hash le décrivant. Si le fichier est lisible mais n'est pas une image Storable, retourne "undef". Si le fichier n'existe pas ou n'est pas lisible, provoque une erreur.

Le hash retourné a les éléments suivants :

"version"
Retourne la version du format du fichier. C'est une chaîne comme "2.7". Notez que ce numéro de version n'est pas le même que le numéro de version du module Storable. Par exemple, Storable v0.7 crée des fichiers au format v2.0 et Storable v2.15 au format v2.7. Le numéro de version du format de fichier n'augmente que lorsque des fonctionnalités supplémentaires sont ajoutées qui pourraient perturber les anciennes versions du module.
"version_nv"
Retourne la version du format du fichier sous forme de nombre. C'est une chaîne comme "2.007". Cette valeur est appropriée pour les comparaisons numériques.
"major", "minor"
Retourne également la version du format du fichier. Si la version est "2.7", major sera 2 et minor 7. L'élément minor est absent lorsque le major est inférieur à 2.
"hdrsize"
C'est le nombre d'octets que prend l'en-tête Storable.
"netorder"
Vaut TRUE si les données du fichier ont été stockées en ordre réseau. Cela signifie qu'il a été créé avec nstore() ou une commande similaire.
"byteorder"
N'est présent que lorsque "netorder" est FALSE. C'est la chaîne $Config{byteorder} du perl qui a créé cette image. C'est une chaîne comme "1234" (little-endian 32 bits) ou "87654321" (big-endian 64 bits). Cela doit correspondre au perl actuel pour que le fichier soit lisible par Storable.
"intsize", "longsize", "ptrsize", "nvsize"
Ceux-ci ne sont présents que lorsque "netorder" est FALSE. Ce sont les tailles de divers types de données C du perl qui a créé cette image. Celles-ci doivent correspondre au perl actuel pour que le fichier soit lisible par Storable.

L'élément "nvsize" n'est présent que pour les formats de fichiers v2.2 et supérieurs.

"file"
Le nom du fichier.
$info = Storable::read_magic( $buffer )
$info = Storable::read_magic( $buffer, $must_be_file )
Le $buffer doit être une image Storable ou les premiers octets de celle-ci. Si le $buffer commence par un en-tête Storable, un hash décrivant l'image est retourné, sinon "undef" est retourné.

Le hash a la même structure que celui retourné par Storable::file_magic(). L'élément "file" est TRUE si l'image est une image de fichier.

Si l'argument $must_be_file est fourni et est TRUE, "undef" est retourné à moins que l'image ne semble appartenir à un dump de fichier.

EXEMPLES

Voici quelques exemples de code montrant une utilisation possible de Storable :

use Storable qw(store retrieve freeze thaw dclone);
%color = ('Blue' => 0.1, 'Red' => 0.8, 'Black' => 0, 'White' => 1);
store(\%color, 'mycolors') or die "Impossible de stocker %a dans mycolors !\n";
$colref = retrieve('mycolors');
die "Impossible de récupérer depuis mycolors !\n" unless defined $colref;
printf "Blue est toujours %lf\n", $colref->{'Blue'};
$colref2 = dclone(\%color);
$str = freeze(\%color);
printf "La sérialisation de %%color fait %d octets de long.\n", length($str);
$colref3 = thaw($str);

Ce qui imprime (sur ma machine) :

Blue est toujours 0.100000
La sérialisation de %color fait 102 octets de long.

Sérialisation de références de code et désérialisation dans un environnement sécurisé :

use Storable qw(freeze thaw);
use Safe;
use strict;
my $safe = Safe->new;
        # en raison des opcodes utilisés par "use strict" :
$safe->permit(qw(:default require));
local $Storable::Deparse = 1;
local $Storable::Eval = sub { $safe->reval($_[0]) };
my $serialized = freeze(sub { 42 });
my $code = thaw($serialized);
$code->() == 42;

AVERTISSEMENT DE SÉCURITÉ

N'acceptez jamais de documents Storable provenant de sources non fiables ! Il n'y a aucun moyen de configurer Storable pour qu'il puisse être utilisé en toute sécurité pour traiter des données non fiables. Bien qu'il existe des options qui peuvent atténuer des problèmes spécifiques, elles ne constituent pas une protection complète pour l'utilisateur, et le traitement de données non fiables peut entraîner des plantages de segmentation, une exécution de code à distance ou une élévation de privilèges. Les points suivants répertorient certaines fonctionnalités connues qui posent des problèmes de sécurité que les utilisateurs doivent prendre en compte.

De manière plus évidente, la fonctionnalité facultative (désactivée par défaut) de sérialisation des références de code permet de transférer du code dans le processus de désérialisation. De plus, tout objet sérialisé amènera Storable à charger le module correspondant à la classe de l'objet dans le module de désérialisation. Pour les modules dont le nom est manipulé, cela peut charger presque n'importe quel code. Enfin, les destructeurs des objets désérialisés sont appelés lorsque les objets sont détruits dans le processus de désérialisation. Des documents Storable malveillants peuvent placer de tels objets dans la valeur d'une clé de hachage qui est écrasée par une autre paire clé/valeur dans la même hachage, provoquant l'exécution immédiate de leurs destructeurs.

Pour désactiver le 'blessing' d'objets lors de la désérialisation, supprimez le drapeau "BLESS_OK" = 2 de $Storable::flags ou définissez le deuxième argument de thaw/retrieve à 0.

Pour désactiver le 'tie' de données lors de la désérialisation, supprimez le drapeau "TIE_OK" = 4 de $Storable::flags ou définissez le deuxième argument de thaw/retrieve à 0.

Avec la valeur par défaut de $Storable::flags = 6, la création ou la destruction d'objets arbitraires, y compris des objets renommés, peut être contrôlée par un attaquant. Voir CVE-2015-1592 et son module metasploit.

Si votre application nécessite d'accepter des données provenant de sources non fiables, il est préférable d'utiliser une forme de sérialisation plus faible et plus susceptible d'être sécurisée. Si vos données sont suffisamment simples, Cpanel::JSON::XS ou Data::MessagePack sont des alternatives acceptables. Pour des structures de données plus complexes contenant des types de données Perl spécifiques tels que des expressions régulières ou des données alliées, Sereal est l'alternative la plus appropriée et offre une interopérabilité maximale. Notez que Sereal est par défaut non sécurisé, mais vous pouvez configurer l'encodeur et le décodeur pour atténuer tout problème de sécurité.

AVERTISSEMENT

Si vous utilisez des références comme clés dans vos tables de hachage, vous serez forcément déçu en récupérant vos données. En effet, Perl stringifie les références utilisées comme clés dans les tables de hachage. Si vous souhaitez ensuite accéder aux éléments via une autre référence stringifiée (c'est-à-dire en utilisant la même référence qui a été utilisée à l'origine pour enregistrer la valeur dans la table de hachage), cela fonctionnera, car les deux références se stringifieront en la même chaîne.

Cela ne fonctionnera pas dans une séquence d'opérations "store" et "retrieve", car les adresses dans les objets récupérés, qui font partie des références stringifiées, peuvent différer des adresses d'origine. La topologie de votre structure est préservée, mais pas la sémantique cachée.

Sur les plateformes où c'est important, assurez-vous d'appeler binmode() sur les descripteurs que vous passez aux fonctions de Storable.

Stocker des données de manière canonique contenant de grandes hachages peut être considérablement plus lent que de stocker les mêmes données normalement, car des tableaux temporaires doivent être alloués, remplis, triés et libérés pour stocker les clés de chaque hachage. Certains tests montrent une augmentation de 50 % de la vitesse de stockage, bien que le coût exact dépende de la complexité de vos données. Il n'y a aucun impact sur la vitesse de récupération des données.

EXPRESSIONS RÉGULIÈRES

Storable prend désormais en charge les expressions régulières de manière expérimentale, mais avec des limitations importantes :

  • Perl 5.8 ou version ultérieure est requis.
  • Les expressions régulières avec des blocs de code, c'est-à-dire "/(?{ ... })/" ou "/(??{ ... })/", lèveront une exception lors de la désérialisation.
  • La syntaxe et les indicateurs des expressions régulières ont changé au fil de l'histoire de Perl, de sorte qu'une expression régulière que vous avez figée dans une version de Perl peut ne pas se désérialiser correctement ou se comporter différemment dans une autre version.
  • Selon la version de Perl, les expressions régulières peuvent changer en fonction du contexte, mais les Perl les plus récents incorporeront ce comportement dans l'expression régulière.

Storable lèvera une exception si une expression régulière figée ne peut pas être désérialisée.

BOGUES

Vous ne pouvez pas stocker GLOB, FORMLINE, etc... Si vous pouvez définir la sémantique pour ces opérations, faites en sorte que Storable puisse les gérer.

Les fonctions de stockage lèveront "croak" si elles rencontrent de telles références, à moins que vous ne définissiez $Storable::forgive_me à une valeur "TRUE". Dans ce cas, le message d'erreur fatal deviendra un avertissement et une chaîne inutile sera stockée.

Définir $Storable::canonical ne garantit pas que les chaînes figées seront identiques en raison de la potentielle stringification des nombres. Lorsque la version chaîne d'un scalaire existe, c'est la forme stockée ; par conséquent, si vous utilisez vos nombres comme chaînes entre deux opérations de figement sur les mêmes données structurées, vous obtiendrez des résultats différents.

Lors du stockage de doubles en ordre réseau, leur valeur est stockée sous forme de texte. Cependant, vous devez également vous attendre à ce que des valeurs non numériques comme l'infini et "non un nombre" ne soient pas correctement transmises via une paire nstore()/retrieve().

Comme Storable ne connaît ni ne se soucie des jeux de caractères (bien qu'il sache que les caractères peuvent être plus de huit bits), toute différence dans l'interprétation des codes de caractères entre un hôte et un système cible est votre problème. En particulier, si l'hôte et le système cible utilisent des codes différents pour représenter les caractères dans la représentation textuelle des nombres à virgule flottante, vous ne pourrez pas échanger de données flottantes même avec nstore().

"Storable::drop_utf8" est un outil direct. Il n'y a aucune capacité à renvoyer toutes les chaînes sous forme de séquences UTF-8 ou à tenter de reconvertir des données UTF-8 en 8 bits et à croak() si la conversion échoue.

Avant Storable 2.01, il n'y avait pas de distinction entre les entiers signés et non signés lors du stockage. Par défaut, Storable préférait stocker la représentation chaîne d'un scalaire (s'il en avait une) pour éviter les problèmes. Cela ne causait des problèmes que lors du stockage d'entiers non signés qui n'avaient jamais été convertis en chaîne ou en virgule flottante. En d'autres termes, des valeurs générées par des opérations entières comme des opérations logiques et ensuite non utilisées dans un contexte chaîne ou arithmétique avant leur stockage.

Données 64 bits dans Perl 5.6.0 et 5.6.1

Cette section ne s'applique que si vous avez des données existantes écrites par Storable 2.02 ou des versions antérieures dans Perl 5.6.0 ou 5.6.1 sous Unix ou Linux configuré avec le support des entiers 64 bits (pas par défaut). Si vous avez obtenu un perl précompilé au lieu d'exécuter Configure pour construire votre propre perl à partir des sources, alors cela ne vous affecte probablement pas et vous pouvez arrêter de lire maintenant (sauf si vous êtes curieux). Si vous utilisez Perl sous Windows, cela ne vous concerne pas.

Storable écrit un en-tête de fichier qui contient la taille de divers types de langage C pour le compilateur qui a construit Storable (lorsqu'il n'écrit pas en ordre réseau), et refusera de charger des fichiers écrits par un Storable qui n'est pas sur la même architecture (ou une architecture compatible). Ceci est requis pour vérifier l'interprétation des champs de fichier et parce que les tailles des champs dans le fichier sont données par les tailles des types de langage C. Par conséquent, les fichiers écrits sur différentes architectures ne sont pas compatibles. Ce processus est effectué pour augmenter la vitesse. (Lors de l'écriture en ordre réseau, tous les champs sont écrits comme des longueurs standard, ce qui permet une interopérabilité complète, mais prend plus de temps à lire et à écrire).

Perl 5.6.x a introduit la capacité facultative de configurer l'interpréteur Perl pour utiliser le type C "long long" pour permettre aux scalaires de stocker des entiers 64 bits sur des systèmes 32 bits. Cependant, en raison de la manière dont le système de configuration de Perl générait les fichiers de configuration C sur les plateformes non Windows, et de la manière dont Storable génère son en-tête, rien dans l'en-tête de fichier de Storable ne reflétait si le perl écrivait en entier 32 ou 64 bits. Même si Storable stockait certaines données différemment dans le fichier, le fait que Storable stockait certaines données différemment n'affectait pas l'en-tête. Par conséquent, Storable exécuté sous Perl avec des entiers 64 bits lira l'en-tête d'un fichier écrit par un perl 32 bits, ne reconnaîtra pas que les données sont en réalité dans un format subalterne incompatible, puis se comportera mal (éventuellement en plantant) s'il rencontre un entier stocké. C'est une faille de conception.

Storable a maintenant été modifié.

to write out and read in a file header with information about the size of integers. It's impossible to detect whether an old file being read in was written with 32 or 64 bit integers (they have the same header) so it's impossible to automatically switch to a correct backwards compatibility mode. Hence this Storable defaults to the new, correct behaviour.

What this means is that if you have data written by Storable 1.x running on perl 5.6.0 or 5.6.1 configured with 64 bit integers on Unix or Linux then by default this Storable will refuse to read it, giving the error Byte order is not compatible. If you have such data then you should set $Storable::interwork_56_64bit to a true value to make this Storable read and write files with the old header. You should also migrate your data, or any older perl you are communicating with, to this current version of Storable.

If you don't have data written with specific configuration of perl described above, then you do not and should not do anything. Don't set the flag - not only will Storable on an identically configured perl refuse to load them, but Storable a differently configured perl will load them believing them to be correct for it, and then may well fail or crash part way through reading them.
