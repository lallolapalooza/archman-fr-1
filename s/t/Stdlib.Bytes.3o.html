val length : bytes -> int

Retourne la longueur (nombre d'octets) de l'argument.

val get : bytes -> int -> char

get s n retourne l'octet à l'index n dans l'argument s.

Lève Invalid_argument si n n'est pas un indice valide dans s.

val set : bytes -> int -> char -> unit

set s n c modifie s en place, remplaçant l'octet à l'index n par c.

Lève Invalid_argument si n n'est pas un indice valide dans s.

val create : int -> bytes

create n retourne une nouvelle séquence d'octets de longueur n. La séquence est non initialisée et contient des octets arbitraires.

Lève Invalid_argument si n < 0 ou n > Sys.max_string_length.

val make : int -> char -> bytes

make n c retourne une nouvelle séquence d'octets de longueur n, remplie avec l'octet c.

Lève Invalid_argument si n < 0 ou n > Sys.max_string_length.

val init : int -> (int -> char) -> bytes

init n f retourne une nouvelle séquence d'octets de longueur n, où le caractère i est initialisé par le résultat de f i (dans l'ordre croissant des indices).

Lève Invalid_argument si n < 0 ou n > Sys.max_string_length.

val sub : bytes -> int -> int -> bytes

sub s pos len retourne une nouvelle séquence d'octets de longueur len, contenant la sous-séquence de s qui commence à la position pos et a la longueur len.

Lève Invalid_argument si pos et len ne désignent pas une plage valide de s.

val fill : bytes -> int -> int -> char -> unit

fill s pos len c modifie s en place, remplaçant len caractères par c, en commençant à la position pos.

val blit : bytes -> int -> bytes -> int -> int -> unit

blit src src_pos dst dst_pos len copie len octets de la séquence d'octets src, en commençant à l'index src_pos, vers la séquence d'octets dst, en commençant à l'index dst_pos. Cela fonctionne correctement même si src et dst sont la même séquence d'octets, et si les intervalles source et destination se chevauchent.

Lève Invalid_argument si src_pos et len ne désignent pas une plage valide de src, ou si dst_pos et len ne désignent pas une plage valide de dst.

Conversions non sures (pour utilisateurs avancés)

Cette section décrit les fonctions de conversion non sures et de bas niveau entre bytes et string . Elles ne copient pas les données internes ; utilisées de manière inappropriée, elles peuvent briser l'invariant d'immutabilité des chaînes. Elles sont disponibles pour les auteurs de bibliothèques experts, mais pour la plupart des usages, vous devriez utiliser Bytes.to_string et Bytes.of_string , qui sont toujours correctes.

val unsafe_to_string : bytes -> string

Convertit de manière non sure une séquence d'octets en une chaîne.

Pour raisonner sur l'utilisation de unsafe_to_string , il est pratique de considérer une discipline « de possession ». Un morceau de code qui manipule des données en « possède » ; il existe plusieurs modes de possession disjoints, notamment :

- Possession unique : les données peuvent être accédées et modifiées

- Possession partagée : les données ont plusieurs propriétaires, qui ne peuvent y accéder, mais pas les modifier.

La possession unique est linéaire : passer les données à un autre morceau de code signifie abandonner la possession (nous ne pouvons plus écrire les données). Un propriétaire unique peut décider de rendre les données partagées (renonçant aux droits de modification), mais des données partagées ne peuvent pas redevenir possédées de manière unique.

unsafe_to_string s ne peut être utilisée que lorsque l'appelant possède la séquence d'octets s -- soit de manière unique, soit en tant que données immuables partagées. L'appelant abandonne la possession de s et acquiert la possession de la chaîne retournée.

Il existe deux cas d'utilisation valides qui respectent cette discipline de possession :

1. Créer une chaîne en initialisant et en modifiant une séquence d'octets qui n'est jamais modifiée après l'initialisation.

let string_init len f : string =
  let s = Bytes.create len in
  for i = 0 to len - 1 do Bytes.set s i (f i) done;
  Bytes.unsafe_to_string s

Cette fonction est sure car la séquence d'octets s ne sera jamais accédée ou modifiée après l'appel à unsafe_to_string . Le code string_init abandonne la possession de s et renvoie la possession de la chaîne résultante à son appelant.

Notez qu'il serait dangereux si s était passé comme paramètre supplémentaire à la fonction f car elle pourrait s'échapper de cette manière et être modifiée ultérieurement -- string_init abandonnerait la possession de s pour la passer à f , et ne pourrait pas appeler unsafe_to_string en toute sécurité.

Nous avons fourni les fonctions String.init , String.map et String.mapi pour couvrir la plupart des cas de construction de nouvelles chaînes. Vous devriez préférer celles-ci à to_string ou unsafe_to_string chaque fois que possible.

2. Donner temporairement la possession d'une séquence d'octets à une fonction qui attend une chaîne possédée de manière unique et rend la possession, afin que nous puissions à nouveau modifier la séquence après la fin de l'appel.

let bytes_length (s : bytes) =
  String.length (Bytes.unsafe_to_string s)

Dans ce cas d'utilisation, nous ne promettons pas que s ne sera jamais modifié après l'appel à bytes_length s . La fonction String.length emprunte temporairement la possession unique de la séquence d'octets (et la voit comme une string ), mais rend cette possession à l'appelant, qui peut supposer que s est toujours une séquence d'octets valide après l'appel. Notez que ceci n'est correct que parce que nous savons que String.length ne capture pas son argument -- il pourrait s'échapper par un canal secondaire tel qu'un combinateur de mémoïsation.

L'appelant ne peut pas modifier s pendant que la chaîne est empruntée (il a temporairement abandonné la possession). Cela affecte les programmes concurrents, mais aussi les fonctions d'ordre supérieur : si String.length renvoyait une fermeture à appeler plus tard, s ne devrait pas être modifié jusqu'à ce que cette fermeture soit entièrement appliquée et rende la possession.

val unsafe_of_string : string -> bytes

Convertit de manière non sure une chaîne partagée en une séquence d'octets qui ne doit pas être modifiée.

La même discipline de possession qui rend unsafe_to_string correcte s'applique à unsafe_of_string : vous pouvez l'utiliser si vous étiez le propriétaire de la valeur string , et vous posséderez les bytes retournés dans le même mode.

En pratique, la possession unique des valeurs de chaînes est extrêmement difficile à raisonner correctement. Vous devriez toujours supposer que les chaînes sont partagées, jamais possédées de manière unique.

Par exemple, les littéraux de chaîne sont implicitement partagés par le compilateur, donc vous ne les possédez jamais de manière unique.

let incorrect = Bytes.unsafe_of_string "hello"
let s = Bytes.of_string "hello"

La première déclaration est incorrecte, car le littéral de chaîne "hello" pourrait être partagé par le compilateur avec d'autres parties du programme, et modifier incorrect est un bug. Vous devez toujours utiliser la deuxième version, qui effectue une copie et est donc correcte.

Supposer la possession unique des chaînes qui ne sont pas des littéraux de chaîne, mais qui sont (en partie) construites à partir de littéraux de chaîne, est également incorrect. Par exemple, modifier unsafe_of_string ("foo" ^ s) pourrait modifier la chaîne partagée "foo" -- en supposant une représentation de type « corde » des chaînes. Plus généralement, les fonctions opérant sur les chaînes supposeront une possession partagée, elles ne préservent pas la possession unique. Il est donc incorrect de supposer la possession unique du résultat de unsafe_of_string .

Le seul cas pour lequel nous avons une confiance raisonnable qu'il est sûr est si le produit bytes est partagé -- utilisé comme une séquence d'octets immuable. Ceci est potentiellement utile pour la migration incrémentielle de programmes de bas niveau qui manipulent des séquences d'octets immuables (par exemple Marshal.from_bytes ) et utilisaient précédemment le type string pour ce but.

val split_on_char : char -> bytes -> bytes list

split_on_char sep s retourne la liste de toutes les sous-séquences (potentiellement vides) de s qui sont délimitées par le caractère sep. Si s est vide, le résultat est la liste singleton [vide].

La sortie de la fonction est spécifiée par les invariants suivants :

-La liste n'est pas vide.

-La concaténation de ses éléments en utilisant sep comme séparateur retourne une séquence d'octets égale à l'entrée ( Bytes.concat (Bytes.make 1 sep)
(Bytes.split_on_char sep s) = s ).

-Aucune séquence d'octets dans le résultat ne contient le caractère sep.

Encodage/décodage binaire d'entiers

Les fonctions de cette section encodent et décodent des entiers en binaire vers et depuis des séquences d'octets.

Toutes les fonctions suivantes lèvent Invalid_argument si l'espace nécessaire à l'indice i pour décoder ou encoder l'entier n'est pas disponible.

L'encodage little-endian (resp. big-endian) signifie que les octets de poids faible (resp. fort) sont stockés en premier. Big-endian est aussi connu sous le nom d'ordre des octets réseau. L'encodage native-endian est soit little-endian soit big-endian selon Sys.big_endian.

Les entiers 32 bits et 64 bits sont représentés par les types int32 et int64, qui peuvent être interprétés comme des nombres signés ou non signés.

Les entiers 8 bits et 16 bits sont représentés par le type int, qui a plus de bits que l'encodage binaire. Ces bits supplémentaires sont gérés comme suit :

-Les fonctions qui décodent des entiers signés (resp. non signés) de 8 ou 16 bits représentés par des valeurs int étendent le signe (resp. remplissent de zéros) leur résultat.

-Les fonctions qui encodent des entiers de 8 ou 16 bits représentés par des valeurs int tronquent leur entrée à leurs octets les moins significatifs.

Séquences d'octets et sécurité de la concurrence

Il faut être prudent lors de l'accès concurrent aux séquences d'octets depuis plusieurs domaines : l'accès à une séquence d'octets ne fera jamais planter un programme, mais des accès non synchronisés pourraient produire des résultats surprenants (non séquentiellement cohérents).

Atomicité

Toute opération sur séquence d'octets qui accède à plus d'un octet n'est pas atomique. Cela inclut l'itération et le balayage.

Par exemple, considérons le programme suivant :

let size = 100_000_000
let b = Bytes.make size  ' '
let update b f ()  =
  Bytes.iteri (fun i x -> Bytes.set b i (Char.chr (f (Char.code x)))) b
let d1 = Domain.spawn (update b (fun x -> x + 1))
let d2 = Domain.spawn (update b (fun x -> 2 * x + 1))
let () = Domain.join d1; Domain.join d2
la séquence d'octets b peut contenir un mélange non déterministe de valeurs '!' , 'A' , 'B' et 'C' .

Après exécution de ce code, chaque octet de la séquence b est soit '!' , soit 'A' , soit 'B' , soit 'C' . Si l'atomicité est requise, alors l'utilisateur doit implémenter sa propre synchronisation (par exemple, en utilisant Mutex.t).

Courses de données

Si deux domaines n'accèdent qu'à des parties disjointes d'une séquence d'octets, alors le comportement observé est équivalent à un certain entrelacement séquentiel des opérations des deux domaines.

Une course de données est dite se produire lorsque deux domaines accèdent au même octet sans synchronisation et qu'au moins un des accès est une écriture. En l'absence de courses de données, le comportement observé est équivalent à un certain entrelacement séquentiel des opérations de différents domaines.

Dans la mesure du possible, les courses de données doivent être évitées en utilisant la synchronisation pour arbitrer les accès aux éléments de la séquence.

En effet, en présence de courses de données, les programmes ne planteront pas, mais le comportement observé pourrait ne pas être équivalent à un quelconque entrelacement séquentiel des opérations de différents domaines. Néanmoins, même en présence de courses de données, une opération de lecture renverra la valeur d'une écriture antérieure à cet emplacement.

Accès de tailles mixtes

Un autre point subtil est que si une course de données implique des écritures et des lectures de tailles mixtes au même emplacement, l'ordre dans lequel ces écritures et lectures sont observées par les domaines n'est pas spécifié. Par exemple, le code suivant écrit séquentiellement un entier 32 bits et un char au même indice

let b = Bytes.make 10 '\000'
let d1 = Domain.spawn (fun () -> Bytes.set_int32_ne b 0 100; b.[0] <- 'd' )

Dans cette situation, un domaine qui observe l'écriture de 'd' à b. 0 n'est pas garanti d'observer également l'écriture aux indices 1 , 2 ou 3.
