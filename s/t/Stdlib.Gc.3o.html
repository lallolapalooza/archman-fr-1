Les compteurs de gestion de la mémoire sont retournés dans un enregistrement stat. Ces compteurs donnent des valeurs pour l'ensemble du programme.

La quantité totale de mémoire allouée par le programme depuis son démarrage est (en mots) minor_words + major_words - promoted_words. Multipliez par la taille du mot (4 sur une machine 32 bits, 8 sur une machine 64 bits) pour obtenir le nombre d'octets.

Les paramètres du GC sont donnés sous forme d'un enregistrement de control. Notez que ces paramètres peuvent également être initialisés en définissant la variable d'environnement OCAMLRUNPARAM. Voir la documentation de ocamlrun.

val stat : unit -> stat

Retourne les valeurs actuelles des compteurs de gestion de la mémoire dans un enregistrement stat qui représente les statistiques de mémoire totales du programme. Les métriques heap_chunks, free_blocks, largest_free et stack_size ne sont pas actuellement disponibles en OCaml 5 : leurs valeurs de champ retournées sont par conséquent 0. Cette fonction déclenche une collecte majeure complète.

val quick_stat : unit -> stat

Retourne un enregistrement avec les valeurs actuelles des compteurs de gestion de la mémoire, comme stat. Contrairement à stat, quick_stat n'effectue pas de collecte majeure complète et est donc beaucoup plus rapide. Cependant, quick_stat rapporte les compteurs échantillonnés lors de la dernière collecte mineure ou à la fin du dernier cycle de collecte majeure (selon la dernière événement). Par conséquent, les statistiques de mémoire retournées par quick_stat ne sont pas instantanément précises.

val counters : unit -> float * float * float

Retourne (minor_words, promoted_words, major_words) pour le domaine actuel ou potentiellement les domaines précédents. Cette fonction est aussi rapide que quick_stat.

val minor_words : unit -> float

Nombre de mots alloués dans le tas mineur par ce domaine ou potentiellement par des domaines précédents. Ce nombre est précis dans les programmes en code octet, mais seulement une approximation dans les programmes compilés en code natif.

En code natif, cette fonction n'alloue pas.

val get : unit -> control

Retourne les valeurs actuelles des paramètres du GC dans un enregistrement control.

Les champs major_heap_increment, max_overhead, allocation_policy et window_size ne sont pas actuellement disponibles en OCaml 5 : leurs valeurs de champ retournées sont donc 0.

Attention accès non synchronisé. Les paramètres du GC sont un état global mutable.

val set : control -> unit

set r modifie les paramètres du GC conformément à l'enregistrement control r. L'utilisation normale est : Gc.set { (Gc.get()) with Gc.verbose = 0x00d }

Les champs major_heap_increment, max_overhead, allocation_policy et window_size ne sont pas actuellement disponibles en OCaml 5 : leur modification n'a donc aucun effet.

Attention accès non synchronisé. Les paramètres du GC sont un état global mutable.

val minor : unit -> unit

Déclenche une collecte mineure.

val major_slice : int -> int

major_slice n Effectue une collecte mineure et une tranche de collecte majeure. n est la taille de la tranche : le GC effectuera suffisamment de travail pour libérer (en moyenne) n mots de mémoire. Si n = 0, le GC essaiera de faire suffisamment de travail pour que la prochaine tranche automatique n'ait rien à faire. Cette fonction retourne un entier non spécifié (actuellement : 0).

val major : unit -> unit

Effectue une collecte mineure et termine le cycle de collecte majeure en cours.

val full_major : unit -> unit

Effectue une collecte mineure, termine le cycle de collecte majeure en cours, et effectue un nouveau cycle complet. Cela collectera tous les blocs actuellement inaccessibles.

val compact : unit -> unit

Effectue une collecte majeure complète et compacte le tas. Notez que la compaction du tas est une opération longue.

val print_stat : out_channel -> unit

Imprime les valeurs actuelles des compteurs de gestion de la mémoire (sous forme lisible par l'homme) du programme total dans le canal argument.

val allocated_bytes : unit -> float

Retourne le nombre d'octets alloués par ce domaine et potentiellement par un domaine précédent. Il est retourné sous forme de float pour éviter les problèmes de dépassement avec int sur les machines 32 bits.

val get_minor_free : unit -> int

Retourne la taille actuelle de l'espace libre dans le tas mineur de ce domaine.

val finalise : ('a -> unit) -> 'a -> unit

finalise f v enregistre f comme fonction de finalisation pour v. v doit être alloué sur le tas. f sera appelée avec v comme argument à un moment donné entre la première fois où v devient inaccessible (y compris via des pointeurs faibles) et le moment où v est collecté par le GC. Plusieurs fonctions peuvent être enregistrées pour la même valeur, voire plusieurs instances de la même fonction. Chaque instance sera appelée une fois (ou jamais, si le programme se termine avant que v ne devienne inaccessible).

Le GC appellera les fonctions de finalisation dans l'ordre de désallocation. Lorsque plusieurs valeurs deviennent inaccessibles en même temps (c'est-à-dire pendant le même cycle GC), les fonctions de finalisation seront appelées dans l'ordre inverse des appels correspondants à finalise. Si finalise est appelée dans le même ordre que les valeurs sont allouées, cela signifie que chaque valeur est finalisée avant les valeurs dont elle dépend. Bien sûr, cela devient faux si des dépendances supplémentaires sont introduites par des affectations.

En présence de plusieurs threads OCaml, il faut supposer que n'importe quel finaliseur peut être exécuté dans n'importe lequel des threads.

Tout ce qui est accessible depuis la fermeture des fonctions de finalisation est considéré comme accessible, donc le code suivant ne fonctionnera pas comme prévu :

- let v = ... in Gc.finalise (fun _ -> ...v...) v

Au lieu de cela, vous devriez vous assurer que v n'est pas dans la fermeture de la fonction de finalisation en écrivant :

- let f = fun x -> ... let v = ... in Gc.finalise f v

La fonction f peut utiliser toutes les fonctionnalités d'OCaml, y compris les affectations qui rendent à nouveau la valeur accessible. Elle peut également boucler indéfiniment (dans ce cas, les autres fonctions de finalisation ne seront pas appelées pendant l'exécution de f, sauf si elle appelle finalise_release). Elle peut lever une exception ; dans ce cas, l'exception interrompra tout ce que le programme faisait lorsque la fonction a été appelée.

finalise lèvera Invalid_argument si v n'est pas garanti d'être alloué sur le tas. Quelques exemples de valeurs qui ne sont pas allouées sur le tas sont les entiers, les constructeurs constants, les booléens, le tableau vide, la liste vide, la valeur unitaire. La liste exacte de ce qui est alloué ou non sur le tas dépend de l'implémentation. Certaines valeurs constantes peuvent être allouées sur le tas mais jamais désallouées pendant la durée de vie du programme, par exemple une liste de constantes entières ; cela dépend également de l'implémentation. Notez que les valeurs de type float sont parfois allouées et parfois non, donc leur finalisation est dangereuse, et finalise lèvera également Invalid_argument pour elles. Les valeurs de type 'a Lazy.t (pour tout 'a) sont similaires aux float à cet égard, sauf que le compilateur les optimise parfois d'une manière qui empêche finalise de les détecter. Dans ce cas, elle ne lèvera pas Invalid_argument, mais vous devriez toujours éviter d'appeler finalise sur des valeurs paresseuses.

Les résultats des appels à String.make, Bytes.make, Bytes.create, Array.make et ref sont garantis d'être alloués sur le tas et non constants, sauf lorsque l'argument de longueur est 0.

val finalise_last : (unit -> unit) -> 'a -> unit

identique à Gc.finalise sauf que la valeur n'est pas fournie en argument. Vous ne pouvez donc pas utiliser la valeur fournie pour le calcul de la fonction de finalisation. L'avantage est que la fonction est appelée après que la valeur soit inaccessible pour la dernière fois au lieu de la première fois. Ainsi, contrairement à Gc.finalise, la valeur ne sera jamais à nouveau accessible ni réutilisée. En particulier, tous les pointeurs faibles et les éphémères qui contenaient cette valeur comme clé ou donnée sont désactivés avant d'exécuter la fonction de finalisation. De plus, les fonctions de finalisation attachées avec Gc.finalise sont toujours appelées avant les fonctions de finalisation attachées avec Gc.finalise_last.

val finalise_release : unit -> unit

Une fonction de finalisation peut appeler finalise_release pour indiquer au GC qu'il peut lancer la prochaine fonction de finalisation sans attendre que la fonction actuelle se termine.

type alarm

Une alarme est une donnée qui appelle une fonction utilisateur à la fin d'un cycle GC majeur. Les fonctions suivantes sont fournies pour créer et supprimer des alarmes.

val create_alarm : (unit -> unit) -> alarm

create_alarm f organisera l'appel de f à la fin des cycles GC majeurs, non causés par f elle-même, en commençant par le cycle actuel ou le suivant. f s'exécutera sur le même domaine qui a créé l'alarme, jusqu'à ce que le domaine se termine ou que delete_alarm soit appelé. Une valeur de type alarm est retournée que vous pouvez utiliser pour appeler delete_alarm.

Il n'est pas garanti que l'alarme GC s'exécute à la fin de chaque cycle GC majeur, mais il est garanti qu'elle s'exécutera éventuellement.

Par exemple, voici une façon rudimentaire d'interrompre une fonction si la consommation de mémoire du programme dépasse une limite donnée en Mo, adaptée à une utilisation dans le toplevel :

let run_with_memory_limit (limit : int) (f : unit -> 'a) : 'a =
  let limit_memory () =
    let mem = Gc.(quick_stat ()).heap_words in
    if mem / (1024 * 1024) > limit / (Sys.word_size / 8) then
      raise Out_of_memory
  in
  let alarm = Gc.create_alarm limit_memory in
  Fun.protect f ~finally:(fun () -> Gc.delete_alarm alarm ; Gc.compact ())

val delete_alarm : alarm -> unit

delete_alarm a arrêtera les appels à la fonction associée à a. Appeler à nouveau delete_alarm a n'a aucun effet.

val eventlog_pause : unit -> unit

Obsolète. Utilisez Runtime_events.pause à la place.

val eventlog_resume : unit -> unit

Obsolète. Utilisez Runtime_events.resume à la place.

module Memprof : sig end

Memprof est un moteur de profilage qui échantillonne de manière aléatoire les mots de mémoire alloués. Chaque mot alloué a une probabilité d'être échantillonné égale à un taux d'échantillonnage configurable. Une fois qu'un bloc est échantillonné, il devient suivi. Un bloc suivi déclenche une fonction de rappel définie par l'utilisateur dès qu'il est alloué, promu ou désalloué.

Comme les blocs sont composés de plusieurs mots

s, un bloc peut potentiellement être échantillonné plusieurs fois. Si un bloc est échantillonné plusieurs fois, alors chacun des callbacks est appelé une fois pour chaque événement de ce bloc : la multiplicité est donnée dans le champ n_samples de la structure allocation.

Ce moteur permet d'implémenter un profileur mémoire à faible surcharge comme une bibliothèque OCaml.

Note : cette API est EXPÉRIMENTALE. Elle peut changer sans préavis.

type suspended_collection_work

val ramp_up : (unit -> 'a) -> 'a * suspended_collection_work

En général, le GC OCaml suppose que le programme s'exécute dans un état "stable" où l'utilisation maximale de la mémoire reste constante : pour chaque travail nouvellement alloué, il suppose qu'un travail est devenu inaccessible et essaiera de le collecter lors de la prochaine tranche de GC.

Cette hypothèse est incorrecte aux points de l'exécution du programme où la mémoire vivante augmente au lieu de rester stable : l'hypothèse d'état stable fera travailler le GC plus dur sans bénéfice, car il ne trouvera pas plus de mémoire à collecter.

ramp_up f met le domaine courant dans une phase de "montée en puissance" (ramp-up) pendant la durée de l'évaluation de f () , faisant savoir au GC que l'hypothèse d'état stable ne tient pas ; il doit être utilisé lorsque vous savez que la mémoire vivante du programme augmentera de manière significative.

Pendant une phase de montée en puissance, le GC n'essaiera pas de travailler plus dur pour les nouvelles allocations : le travail de collecte correspondant est "suspendu". Le montant total du travail de collecte suspendu est renvoyé par ramp_up avec le résultat de la fonction.

Si l'utilisateur écarte ce travail suspendu (en n'en faisant rien), le GC n'accélérera jamais pour récupérer le montant correspondant de mémoire. C'est approprié si le travail de montée en puissance alloue de la mémoire de longue durée qui reste vivante jusqu'à la fin de l'exécution du programme.

Si l'utilisateur sait qu'à un certain point du programme la consommation de mémoire vivante a été réduite du montant correspondant -- généralement parce que la mémoire allouée pendant ramp_up est devenue inutilisée -- alors il doit appeler Gc.ramp_down ci-dessous pour que le GC "re prenne" ce travail de collecte.

Si f () lève une exception, la phase de montée en puissance se termine, le travail de collecte qui était suspendu est repris, et l'exception est relancée.

Si f () effectue un effet, l'effet n'est pas géré et une exception Effect.Unhandled est levée à la place.

val ramp_down : suspended_collection_work -> unit

Notifier le GC d'une certaine quantité de travail de collecte qui a été suspendue pendant une phase de montée en puissance, pour être reprise maintenant.
