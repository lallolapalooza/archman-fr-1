NAME

SELECT, TABLE, SET - récupérer des lignes d'une table ou d'une vue

SYNOPSIS

[ SET [ RÉCURSIF ] ensemble [, ...] ]
SELECT [ TOUT | DISTINCT [ SUR ( expression [, ...] ) ] ]
    [ { * | expression [ [ COMME ] nom_sortie ] } [, ...] ]
    [ DE ( element_de_from [, ...] ) ]
    [ OÙ condition ]
    [ GROUPER PAR ( elements_de_groupe [, ...] ) ]
    [ AYANT condition ]
    [ WINDOW nom_de_fenetre AS ( definition_de_fenetre ) [, ...] ]
    [ { UNION | INTERSECT | EXCEPT } [ TOUT | DISTINCT ] select ]
    [ ORDONNER PAR expression [ ASC | DESC | UTILISANT operateur ] [ NULLS { FIRST | LAST } ] [, ...] ]
    [ LIMIT { nombre | TOUT } ]
    [ OFFSET debut [ ROW | ROWS ] ]
    [ FETCH { FIRST | NEXT } [ nombre ] { ROW | ROWS } { ONLY | WITH TIES } ]
    [ FOR { UPDATE | NO KEY UPDATE | SHARE | SHARE ROW EXCLUSIVE } [ OF reference_de_from [, ...] ] [ NOWAIT | SKIP LOCKED ] [...] ]
où element_de_from peut être l'un des suivants :
    [ TOUT ] nom_table [ * ] [ [ COMME ] alias ( alias_colonne [, ...] ) ]
                [ TABLESAMPLE methode_echantillonage ( argument [, ...] ) [ REPEATABLE ( graine ) ] ]
    [ LATERAL ] ( select ) [ [ COMME ] alias ( alias_colonne [, ...] ) ]
    nom_ensemble [ [ COMME ] alias ( alias_colonne [, ...] ) ]
    [ LATERAL ] nom_fonction ( [ argument [, ...] ] )
                [ WITH ORDINALITY ] [ [ COMME ] alias ( definition_colonne [, ...] ) ]
    [ LATERAL ] nom_fonction ( [ argument [, ...] ] ) [ COMME ] alias ( definition_colonne [, ...] )
    [ LATERAL ] nom_fonction ( [ argument [, ...] ] ) AS ( definition_colonne [, ...] )
    [ LATERAL ] ROWS FROM( nom_fonction ( [ argument [, ...] ] ) [ AS ( definition_colonne [, ...] ) ] [, ...] )
                [ WITH ORDINALITY ] [ [ COMME ] alias ( alias_colonne [, ...] ) ]
    element_de_from type_jointure element_de_from { ON condition_jointure | USING ( colonne_jointure [, ...] ) [ AS alias_jointure ] }
    element_de_from NATURAL type_jointure element_de_from
    element_de_from CROSS JOIN element_de_from
et elements_de_groupe peut être l'un des suivants :
    ( )
    expression
    ( expression [, ...] )
    ROLLUP ( { expression | ( expression [, ...] ) } [, ...] )
    CUBE ( { expression | ( expression [, ...] ) } [, ...] )
    GROUPING SETS ( elements_de_groupe [, ...] )
et ensemble est :
    nom_ensemble [ ( nom_colonne [, ...] ) ] AS [ [ NO ] MATERIALIZED ] ( select | values | insert | update | delete | merge )
        [ SEARCH { BREADTH | DEPTH } FIRST BY nom_colonne [, ...] SET nom_col_col ]
        [ CYCLE nom_colonne [, ...] SET nom_col_cycle [ TO valeur_cycle DEFAULT valeur_par_defaut_cycle ] USING nom_col_cycle ]
TABLE [ TOUT ] nom_table [ * ]

DESCRIPTION

SELECT récupère des lignes d'une table ou d'une vue. Le traitement général de SELECT est le suivant :

1. Toutes les requêtes dans la liste WITH sont calculées. Elles agissent effectivement comme des tables temporaires ou des vues qui peuvent être référencées dans la liste FROM. Une requête WITH qui se référence plus d'une fois dans la liste FROM est calculée une seule fois, à moins qu'elle ne soit explicitement marquée comme NO MATERIALIZED. (Voir la section SET Clause.)
2. Tous les éléments dans la liste FROM sont calculés. (Chaque élément de la liste FROM est une table réelle ou virtuelle.) Si plus d'un élément est spécifié dans la liste FROM, ils sont joints en produit cartésien. (Voir la section JOIN Clause.)
3. Si la clause WHERE est spécifiée, les lignes qui ne satisfont pas la condition sont supprimées de la sortie. (Voir la section WHERE Clause.)
4. Si la clause GROUP BY est spécifiée, ou s'il y a des appels à des fonctions d'agrégation, la sortie est combinée en groupes de lignes qui correspondent sur une ou plusieurs valeurs, et les résultats des fonctions d'agrégation sont calculés. Si la clause HAVING existe, elle supprime les groupes qui ne satisfont pas la condition donnée. (Voir les sections GROUP BY Clause et HAVING Clause.) Bien que les colonnes de sortie de la requête SELECT soient calculées à l'étape suivante, elles peuvent également être référencées (par nom ou par numéro ordinal) dans la clause GROUP BY.
5. Les lignes de sortie réelles sont calculées en utilisant les expressions SELECT pour chaque ligne sélectionnée ou groupe de lignes. (Voir la section SELECT List.)
6. SELECT DISTINCT supprime les lignes dupliquées du résultat. SELECT DISTINCT ON supprime les lignes qui correspondent sur toutes les expressions spécifiées. SELECT ALL (par défaut) renvoie toutes les lignes candidates, y compris les doublons. (Voir la section DISTINCT Clause.)
7. En utilisant les opérateurs UNION, INTERSECT et EXCEPT, les résultats de plusieurs requêtes SELECT peuvent être combinés pour former un ensemble de résultats unique. L'opérateur UNION renvoie toutes les lignes qui se trouvent dans l'un ou l'autre des ensembles de résultats, ou dans les deux. L'opérateur INTERSECT renvoie toutes les lignes qui se trouvent strictement dans les deux ensembles de résultats. L'opérateur EXCEPT renvoie les lignes qui se trouvent dans le premier ensemble de résultats mais pas dans le second. Dans tous les cas, les lignes dupliquées sont supprimées, à moins que ALL ne soit spécifié. Le terme facultatif DISTINCT peut être ajouté explicitement pour spécifier la suppression des lignes dupliquées. Note : DISTINCT est le comportement par défaut ici, même si ALL est le comportement par défaut pour SELECT. (Voir les sections UNION Clause, INTERSECT Clause et EXCEPT Clause.)
8. Si la clause ORDER BY est spécifiée, les lignes renvoyées sont triées dans l'ordre spécifié. Si ORDER BY n'est pas spécifié, les lignes sont renvoyées dans l'ordre jugé le plus rapide à produire par le système. (Voir la section ORDER BY Clause.)
9. Si la clause LIMIT (ou FETCH FIRST) ou OFFSET est spécifiée, la requête SELECT ne renvoie qu'un sous-ensemble des lignes de résultat. (Voir la section LIMIT Clause.)
10. Si FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE ou FOR SHARE ROW EXCLUSIVE est spécifié, la requête SELECT verrouille les lignes sélectionnées contre les mises à jour concurrentes. (Voir la section LOCKING Clause.)

Vous devez avoir le privilège SELECT sur chaque colonne utilisée dans une requête SELECT. L'utilisation de FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE ou FOR SHARE ROW EXCLUSIVE nécessite également le privilège UPDATE (au moins sur une colonne de chaque table sélectionnée).

PARAMETRES

Clause WITH

La clause WITH permet de spécifier une ou plusieurs sous-requêtes qui peuvent être référencées par nom dans la requête principale. Les sous-requêtes agissent effectivement comme des tables temporaires ou des vues pendant la durée de la requête principale. Chaque sous-requête peut être un SELECT, TABLE, VALUES, INSERT, UPDATE, DELETE ou MERGE. Lors de l'écriture d'une instruction de modification de données (INSERT, UPDATE, DELETE ou MERGE) dans WITH, il est courant d'inclure une clause RETURNING. C'est le résultat de RETURNING, et non la table sous-jacente modifiée par l'instruction, qui forme la table temporaire lue par la requête principale. Si RETURNING n'est pas spécifié, l'instruction est exécutée, mais ne produit pas de sortie, elle ne peut donc pas être référencée comme une table par la requête principale.

Un nom (sans qualification de schéma) doit être spécifié pour chaque requête WITH. Optionnellement, des noms de colonnes peuvent être spécifiés ; si ceux-ci sont omis, les noms de colonnes sont inférés de la sous-requête.

Si RECURSIVE est spécifié, il permet à une sous-requête SELECT de se référencer elle-même par nom. De telles sous-requêtes doivent avoir la forme :

terme_non_recursif UNION [ ALL | DISTINCT ] terme_recursif

où la référence récursive auto-référente doit apparaître du côté droit de l'UNION. Une seule référence auto-référente est autorisée par requête. Les requêtes de modification de données ne sont pas supportées, mais les résultats d'une requête SELECT récursive peuvent être utilisés dans une instruction de modification de données. Voir la section 7.8 pour un exemple.

Un autre effet de RECURSIVE est que les requêtes WITH ne sont pas nécessaires à l'ordre : une requête peut en référencer une autre qui apparaît plus tard dans la liste. (Cependant, les références cycliques ou mutuelles ne sont pas implémentées.) Sans RECURSIVE, les requêtes WITH ne peuvent référencer que des requêtes WITH sœurs qui apparaissent plus tôt dans la liste WITH.

Lorsqu'il y a plusieurs requêtes dans la clause WITH, RECURSIVE ne doit être écrit qu'une seule fois, immédiatement après WITH. Il s'applique à toutes les requêtes de la clause WITH, bien qu'il n'affecte pas les requêtes qui n'utilisent pas de récursion ou de références vers l'avant.

La clause facultative SEARCH calcule une colonne de séquence de recherche qui peut être utilisée pour trier les résultats d'une requête récursive en ordre de largeur ou de profondeur. Le nom de la liste de colonnes spécifiée est la

row key qui doit être utilisé pour suivre les lignes visitées. Une colonne nommée search_seq_col_name sera ajoutée à la liste des colonnes de résultat de la requête WITH. Cette colonne peut être triée dans la requête externe pour obtenir le tri respectif. Voir la section 7.8.2.1 pour des exemples.

La clause optionnelle CYCLE est utilisée pour détecter les cycles dans les requêtes récursives. La liste des noms de colonnes fournie spécifie la clé de ligne à utiliser pour suivre les lignes visitées. Une colonne nommée cycle_mark_col_name sera ajoutée à la liste des colonnes de résultat de la requête WITH. Cette colonne sera définie à cycle_mark_value lorsqu'un cycle a été détecté, sinon à cycle_mark_default. De plus, le traitement de l'union récursive s'arrêtera lorsqu'un cycle aura été détecté. cycle_mark_value et cycle_mark_default doivent être des constantes et elles doivent être coercibles à un type de données commun, et le type de données doit avoir un opérateur d'inégalité. (La norme SQL exige qu'elles soient des constantes booléennes ou des chaînes de caractères, mais PostgreSQL ne l'exige pas.) Par défaut, TRUE et FALSE (de type booléen) sont utilisés. De plus, une colonne nommée cycle_path_col_name sera ajoutée à la liste des colonnes de résultat de la requête WITH. Cette colonne est utilisée en interne pour suivre les lignes visitées. Voir la section 7.8.2.2 pour des exemples.

Les clauses SEARCH et CYCLE ne sont valides que pour les requêtes WITH récursives. Le with_query doit être une UNION (ou UNION ALL) de deux commandes SELECT (ou équivalent) (pas d'UNION imbriquées). Si les deux clauses sont utilisées, la colonne ajoutée par la clause SEARCH apparaît avant les colonnes ajoutées par la clause CYCLE.

La requête principale et les requêtes WITH sont toutes (notionnellement) exécutées en même temps. Cela implique que les effets d'une instruction de modification de données dans WITH ne peuvent pas être vus par d'autres parties de la requête, sauf en lisant sa sortie RETURNING. Si deux instructions de modification de données tentent de modifier la même ligne, les résultats ne sont pas spécifiés.

Une propriété clé des requêtes WITH est qu'elles sont normalement évaluées une seule fois par exécution de la requête principale, même si la requête principale y fait référence plus d'une fois. En particulier, les instructions de modification de données sont garanties d'être exécutées une fois et une seule, que la requête principale lise tout ou partie de leur sortie.

Cependant, une requête WITH peut être marquée NOT MATERIALIZED pour supprimer cette garantie. Dans ce cas, la requête WITH peut être intégrée dans la requête principale, tout comme s'il s'agissait d'une simple sous-requête SELECT dans la clause FROM de la requête principale. Cela entraîne des calculs dupliqués si la requête principale fait référence à cette requête WITH plus d'une fois ; mais si chaque utilisation nécessite seulement quelques lignes de la sortie totale de la requête WITH, NOT MATERIALIZED peut permettre des économies nettes en permettant aux requêtes d'être optimisées conjointement. NOT MATERIALIZED est ignoré s'il est attaché à une requête WITH qui est récursive ou qui n'est pas sans effets de bord (c'est-à-dire qui n'est pas un simple SELECT ne contenant aucune fonction volatile).

Par défaut, une requête WITH sans effets de bord est intégrée dans la requête principale si elle est utilisée exactement une fois dans la clause FROM de la requête principale. Cela permet une optimisation conjointe des deux niveaux de requête dans des situations où cela devrait être sémantiquement invisible. Cependant, une telle intégration peut être empêchée en marquant la requête WITH comme MATERIALIZED. Cela pourrait être utile, par exemple, si la requête WITH est utilisée comme une barrière d'optimisation pour empêcher le planificateur de choisir un mauvais plan. Les versions de PostgreSQL antérieures à la v12 n'ont jamais effectué une telle intégration, de sorte que les requêtes écrites pour les versions antérieures peuvent reposer sur WITH pour agir comme une barrière d'optimisation.

Voir la section 7.8 pour des informations supplémentaires.

Clause FROM

La clause FROM spécifie une ou plusieurs tables sources pour le SELECT. Si plusieurs sources sont spécifiées, le résultat est le produit cartésien (jointure croisée) de toutes les sources. Mais généralement, des conditions de qualification sont ajoutées (via WHERE) pour restreindre les lignes retournées à un petit sous-ensemble du produit cartésien.

La clause FROM peut contenir les éléments suivants :

table_name

Le nom (éventuellement qualifié par un schéma) d'une table ou d'une vue existante. Si ONLY est spécifié avant le nom de la table, seule cette table est analysée. Si ONLY n'est pas spécifié, la table et toutes ses tables descendantes (le cas échéant) sont analysées. Optionnellement, * peut être spécifié après le nom de la table pour indiquer explicitement que les tables descendantes sont incluses.

alias

Un nom substitut pour l'élément FROM contenant l'alias. Un alias est utilisé pour la concision ou pour éliminer l'ambiguïté lors des auto-jointures (où la même table est analysée plusieurs fois). Lorsqu'un alias est fourni, il masque complètement le nom réel de la table ou de la fonction ; par exemple, étant donné FROM foo AS f, le reste du SELECT doit faire référence à cet élément FROM comme f et non comme foo. Si un alias est écrit, une liste d'alias de colonne peut également être écrite pour fournir des noms substituts pour une ou plusieurs colonnes de la table.

TABLESAMPLE sampling_method ( argument [, ...] ) [ REPEATABLE ( seed ) ]

Une clause TABLESAMPLE après un table_name indique que la sampling_method spécifiée doit être utilisée pour récupérer un sous-ensemble des lignes de cette table. Cet échantillonnage précède l'application de tout autre filtre tel que les clauses WHERE. La distribution PostgreSQL standard inclut deux méthodes d'échantillonnage, BERNOULLI et SYSTEM, et d'autres méthodes d'échantillonnage peuvent être installées dans la base de données via des extensions.

Les méthodes d'échantillonnage BERNOULLI et SYSTEM acceptent chacune un seul argument qui est la fraction de la table à échantillonner, exprimée en pourcentage entre 0 et 100. Cet argument peut être toute expression à valeur réelle. (D'autres méthodes d'échantillonnage peuvent accepter plus ou différents arguments.) Ces deux méthodes retournent un échantillon choisi au hasard de la table qui contiendra environ le pourcentage spécifié de lignes de la table. La méthode BERNOULLI analyse toute la table et sélectionne ou ignore les lignes individuelles indépendamment avec la probabilité spécifiée. La méthode SYSTEM effectue un échantillonnage au niveau des blocs, chaque bloc ayant une chance spécifiée d'être sélectionné ; toutes les lignes de chaque bloc sélectionné sont renvoyées. La méthode SYSTEM est significativement plus rapide que la méthode BERNOULLI lorsque de petits pourcentages d'échantillonnage sont spécifiés, mais elle peut renvoyer un échantillon moins aléatoire de la table en raison des effets de clustering.

La clause optionnelle REPEATABLE spécifie une graine (seed) numérique ou une expression à utiliser pour générer des nombres aléatoires au sein de la méthode d'échantillonnage. La valeur de la graine peut être toute valeur à virgule flottante non nulle. Deux requêtes spécifiant la même graine et les mêmes valeurs d'argument sélectionneront le même échantillon de la table, si la table n'a pas été modifiée entre-temps. Mais des valeurs de graine différentes produiront généralement des échantillons différents. Si REPEATABLE n'est pas donné, un nouvel échantillon aléatoire est sélectionné pour chaque requête, basé sur une graine générée par le système. Notez que certaines méthodes d'échantillonnage supplémentaires n'acceptent pas REPEATABLE et produiront toujours de nouveaux échantillons à chaque utilisation.

select

Une sous-requête SELECT peut apparaître dans la clause FROM. Cela agit comme si son résultat était créé sous forme de table temporaire pour la durée de cette seule commande SELECT. Notez que la sous-requête SELECT doit être entourée de parenthèses, et un alias peut être fourni de la même manière qu'une table. Une commande VALUES peut également être utilisée ici.

with_query_name

Une requête WITH est référencée en écrivant son nom, comme si le nom de la requête était un nom de table. (En fait, la requête WITH masque toute table réelle du même nom aux fins de la requête principale. Si nécessaire, vous pouvez faire référence à une table réelle du même nom en qualifiant le nom de la table par son schéma.) Un alias peut être fourni de la même manière qu'une table.

function_name

Des appels de fonction peuvent apparaître dans la clause FROM. (C'est particulièrement utile pour les fonctions qui renvoient des ensembles de résultats, mais toute fonction peut être utilisée.) Cela agit comme si le résultat de la fonction était créé sous forme de table temporaire pour la durée de cette seule commande SELECT. Si le type de résultat de la fonction est composé (y compris le cas d'une fonction avec plusieurs paramètres OUT), chaque attribut devient une colonne distincte dans la table implicite.

Lorsque la clause optionnelle WITH ORDINALITY est ajoutée à l'appel de fonction, une colonne supplémentaire de type bigint sera ajoutée aux colonnes de résultat de la fonction. Cette colonne numérote les lignes de l'ensemble de résultats de la fonction, en commençant par 1. Par défaut, cette colonne est nommée ordinality.

Un alias peut être fourni de la même manière qu'une table. Si un alias est écrit, une liste d'alias de colonnes peut également être écrite pour fournir des noms substituts pour un ou plusieurs attributs du type de retour composé de la fonction, y compris la colonne d'ordinalité si elle est présente.

Plusieurs appels de fonction peuvent être combinés en un seul élément de clause FROM en les entourant de ROWS FROM( ... ). Le résultat d'un tel élément est la concaténation de la première ligne de chaque fonction, puis de la deuxième ligne de chaque fonction, etc. Si certaines des fonctions produisent moins de lignes que d'autres, des valeurs null sont substituées pour les données manquantes, de sorte que le nombre total de lignes renvoyées est toujours le même que pour la fonction qui a produit le plus de lignes.

Si la fonction a été définie comme renvoyant le type de données record, alors un alias ou le mot-clé AS doit être présent, suivi d'une liste de définitions de colonnes sous la forme ( nom_colonne type_données [, ... ]). La liste des définitions de colonnes doit correspondre au nombre et aux types réels de colonnes renvoyées par la fonction.

Lors de l'utilisation de la syntaxe ROWS FROM( ... ), si l'une des fonctions nécessite une liste de définitions de colonnes, il est préférable de placer la liste de définitions de colonnes après l'appel de fonction à l'intérieur de ROWS FROM( ... ). Une liste de définitions de colonnes ne peut être placée après la construction ROWS FROM( ... ) que s'il n'y a qu'une seule fonction et aucune clause WITH ORDINALITY.

Pour utiliser ORDINALITY avec une liste de définitions de colonnes, vous devez utiliser la syntaxe ROWS FROM( ... ) et placer la liste de définitions de colonnes à l'intérieur de ROWS FROM( ... ).

join_type

L'un des suivants :
•[ INNER ] JOIN
•LEFT [ OUTER ] JOIN
•RIGHT [ OUTER ] JOIN
•FULL [ OUTER ] JOIN

Pour les types de jointure INNER et OUTER, une condition de jointure doit être spécifiée, à savoir exactement l'un des éléments ON join_condition, USING (join_column [, ...]), ou NATURAL. Voir ci-dessous pour la signification.

Une clause JOIN combine deux éléments FROM, que nous appellerons par commodité des « tables », bien qu'en réalité ils puissent être de n'importe quel type d'élément FROM. Utilisez des parenthèses si nécessaire pour déterminer l'ordre d'imbrication. En l'absence de parenthèses, les JOINs sont imbriqués de gauche à droite. Dans tous les cas, JOIN a une priorité plus forte que les virgules séparant les éléments de la liste FROM. Toutes les options de JOIN sont juste une notat

Clause WHERE

La clause facultative WHERE a la forme générale

WHERE condition

où condition est une expression quelconque qui s'évalue à un résultat de type booléen. Toute ligne qui ne satisfait pas cette condition sera supprimée du résultat final. Une ligne satisfait la condition si elle renvoie true lorsque les valeurs de la ligne réelle sont substituées dans toute référence de variable.

Clause GROUP BY

La clause facultative GROUP BY a la forme générale

GROUP BY [ ALL | DISTINCT ] grouping_element [, ...]

GROUP BY condense en une seule ligne toutes les lignes sélectionnées qui partagent les mêmes valeurs pour les expressions dans le groupe. Une expression utilisée dans un grouping_element peut être un nom de colonne d'entrée, ou le nom ou le numéro d'une colonne de sortie (élément de la liste SELECT), ou une expression arbitraire formée à partir de valeurs d'entrée. En cas d'ambiguïté, un nom GROUP BY sera interprété comme un nom de colonne d'entrée et non comme une colonne de sortie.

Si un élément de GROUPING SETS, ROLLUP ou CUBE est présent, la clause GROUP BY dans son ensemble définit un certain nombre de grouping sets. L'effet est équivalent à la construction d'un UNION ALL entre des sous-requêtes avec chacun des grouping sets comme leur clause GROUP BY. Le mot-clé DISTINCT facultatif supprime les ensembles dupliqués avant le traitement ; il ne transforme pas le UNION ALL en UNION DISTINCT. Pour plus de détails sur la gestion de GROUPING SETS, voir la section 7.2.4.

Les fonctions d'agrégation, si elles sont utilisées, sont calculées sur toutes les lignes formant chaque groupe, produisant une valeur distincte pour chaque groupe. (S'il y a des fonctions d'agrégation mais pas de clause GROUP BY, la requête est traitée comme si elle avait un seul groupe formé par toutes les lignes sélectionnées.) Les lignes envoyées à chaque fonction d'agrégation peuvent être filtrées davantage en ajoutant une clause FILTER à l'appel de la fonction d'agrégation ; voir la section 4.2.7 pour plus d'informations. Lorsqu'il y a une clause FILTER, seules les lignes qui y correspondent sont incluses dans l'entrée de cette fonction d'agrégation.

Lorsqu'il y a une clause GROUP BY, ou une fonction d'agrégation, il est invalide pour les expressions de la liste SELECT de faire référence à des colonnes non agrégées, sauf dans les fonctions d'agrégation ou lorsque la colonne non agrégée est fonctionnellement dépendante des colonnes agrégées, car sinon il y aurait plus d'une valeur possible pour une colonne non agrégée. Une dépendance fonctionnelle existe si les colonnes agrégées (ou un sous-ensemble d'entre elles) constituent la clé primaire de la table contenant la colonne non agrégée.

N'oubliez pas que toutes les fonctions d'agrégation sont évaluées avant l'évaluation de toute expression scalaire dans la clause HAVING ou dans la liste SELECT. Cela signifie, par exemple, qu'une expression CASE ne peut pas être utilisée pour sauter l'évaluation d'une fonction d'agrégation ; voir la section 4.2.14.

Actuellement, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE et FOR KEY SHARE ne peuvent pas être spécifiés avec GROUP BY.

Clause HAVING

La clause facultative HAVING a la forme générale

HAVING condition

où condition est la même que pour la clause WHERE.

HAVING supprime les lignes de groupe qui ne satisfont pas la condition. HAVING est distinct de WHERE : WHERE filtre les lignes individuelles avant d'appliquer GROUP BY, tandis que HAVING filtre les lignes de groupe créées par GROUP BY. Chaque colonne référencée dans condition doit se référer sans ambiguïté à une colonne de groupe, à moins que la référence n'apparaisse dans une fonction d'agrégation ou que la colonne non agrégée ne soit fonctionnellement dépendante des colonnes de groupe.

La présence de HAVING transforme une requête en une requête groupée même s'il n'y a pas de clause GROUP BY. C'est la même chose que lorsqu'une requête contient des fonctions d'agrégation mais pas de GROUP BY. Toutes les lignes sélectionnées sont considérées comme un seul groupe, et la liste SELECT et la clause HAVING ne peuvent faire référence qu'à des colonnes de table dans des fonctions d'agrégation. De telles requêtes produiront un seul enregistrement si la condition HAVING est vraie, et zéro enregistrement sinon.

Actuellement, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE et FOR KEY SHARE ne peuvent pas être spécifiés avec HAVING.

Clause WINDOW

La clause facultative WINDOW a la forme générale

WINDOW window_name AS ( window_definition ) [, ...]

où window_name est un nom qui peut être référencé à partir des clauses OVER ou des définitions de fenêtres ultérieures, et window_definition est

[ existing_window_name ]
[ PARTITION BY expression [, ...] ]
[ ORDER BY expression [ ASC | DESC | USING operator ] [ NULLS { FIRST | LAST } ] [, ...] ]
[ frame_clause ]

Si existing_window_name est spécifié, il doit faire référence à une entrée précédente dans la liste des fenêtres ; la nouvelle fenêtre copie sa clause de partition de cette entrée, ainsi que sa clause de tri si elle existe. Dans ce cas, la nouvelle fenêtre ne peut pas spécifier sa propre clause de partition, et elle peut spécifier ORDER BY seulement si la fenêtre copiée n'a pas de clause de tri. La nouvelle fenêtre utilise toujours sa propre clause de cadre ; la fenêtre copiée ne doit pas spécifier de clause de cadre.

Les éléments de la liste PARTITION BY sont interprétés de manière similaire aux éléments d'une clause GROUP BY, sauf qu'il s'agit d'expressions simples et ne sont jamais le nom ou le numéro d'une colonne de sortie. Une autre différence est que ces expressions peuvent contenir des appels à des fonctions d'agrégation, ce qui n'est pas autorisé dans une clause GROUP BY régulière. Ceux-ci sont autorisés ici car le venting s'exécute après le regroupement et l'agrégation.

Les éléments de la liste ORDER BY sont également interprétés de manière similaire aux éléments d'une clause ORDER BY de niveau de requête, sauf que les expressions sont toujours des expressions simples et ne sont jamais le nom ou le numéro d'une colonne de sortie.

La frame_clause facultative définit le cadre de la fenêtre pour les fonctions de fenêtre dépendantes du cadre (pas toutes le sont). Le cadre de la fenêtre est un ensemble de lignes liées pour chaque ligne de la requête (appelée la ligne courante). La frame_clause peut être l'un des éléments suivants

{ RANGE | ROWS | GROUPS } frame_start [ frame_exclusion ]
{ RANGE | ROWS | GROUPS } BETWEEN frame_start AND frame_end [ frame_exclusion ]

où frame_start et frame_end peuvent être l'un des éléments suivants

U

NBOUNDED PRECEDING

La valeur offset PRECEDING

NBOUNDED PRECEDING

et frame_exclusion peuvent être l'un des suivants :

EXCLUDE CURRENT ROW
EXCLUDE GROUP
EXCLUDE TIES
EXCLUDE NO OTHERS

Si frame_end est omis, la valeur par défaut est CURRENT ROW. Les contraintes sont que frame_start ne peut pas être UNBOUNDED FOLLOWING, frame_end ne peut pas être UNBOUNDED PRECEDING, et le frame_end ne peut pas apparaître plus tôt dans la liste de frame_start et frame_end que le frame_start. Par exemple, RANGE BETWEEN CURRENT ROW ET offset PRECEDING n'est pas autorisé.

L'option de cadre par défaut est RANGE UNBOUNDED PRECEDING, ce qui équivaut à RANGE BETWEEN UNBOUNDED PRECEDING ET CURRENT ROW; elle définit le cadre comme toutes les lignes depuis le début de la partition jusqu'à la dernière ligne de la ligne actuelle. En général, UNBOUNDED PRECEDING signifie que le cadre commence par la première ligne de la partition, et de même, UNBOUNDED FOLLOWING signifie que le cadre se termine par la dernière ligne de la partition, quel que soit le mode RANGE, ROWS ou GROUPS. En mode ROWS, CURRENT ROW signifie que le cadre commence ou se termine avec la ligne actuelle; mais en mode RANGE ou GROUPS, cela signifie que le cadre commence ou se termine avec le premier ou le dernier pair de la ligne actuelle dans l'ordre de la clause ORDER BY. Les options offset PRECEDING et offset FOLLOWING varient selon le mode de cadre. En mode ROWS, l'offset est un entier indiquant que le cadre commence ou se termine tant de lignes avant ou après la ligne actuelle. En mode GROUPS, l'offset est un entier indiquant que le cadre commence ou se termine tant de groupes de pairs avant ou après la ligne de pairs actuelle, où un groupe de pairs est un groupe de lignes équivalentes selon la clause ORDER BY de la fenêtre. En mode RANGE, l'utilisation d'une option offset nécessite qu'il y ait exactement une colonne ORDER BY dans la définition de la fenêtre. Ensuite, le cadre contient les lignes dont la valeur de la colonne de tri est inférieure ou égale à offset (pour PRECEDING) ou supérieure à (pour FOLLOWING) la valeur de la colonne de tri de la ligne actuelle. Dans ces cas, le type de l'expression offset dépend du type de la colonne de tri. Pour les colonnes de tri numériques, il est généralement du même type que la colonne de tri; mais pour les colonnes de tri de type datetime, il s'agit d'un intervalle. Dans tous ces cas, la valeur de offset ne doit pas être nulle et être non négative. De plus, bien que l'offset n'ait pas besoin d'être une valeur constante simple, il ne peut pas contenir de variables, de fonctions d'agrégation ou de fonctions de fenêtre.

L'option frame_exclusion permet d'exclure des lignes autour de la ligne actuelle du cadre, même si elles seraient incluses selon les options de début et de fin du cadre. EXCLUDE CURRENT ROW exclut la ligne actuelle du cadre. EXCLUDE GROUP exclut la ligne actuelle et ses pairs de tri du cadre. EXCLUDE TIES exclut tous les pairs de la ligne actuelle du cadre, mais pas la ligne actuelle elle-même. EXCLUDE NO OTHERS spécifie simplement explicitement le comportement par défaut de ne pas exclure la ligne actuelle ou ses pairs.

Étant donné que le mode ROWS peut produire des résultats inattendus si le tri des lignes par ORDEN BY ne trie pas les lignes de manière unique, les modes RANGE et GROUPS sont conçus pour garantir que les lignes qui sont des pairs dans le tri de ORDEN BY soient traitées de manière égale : toutes les lignes d'un groupe de pairs seront dans le cadre ou en seront exclues.

Le but d'une clause WINDOW est de spécifier le comportement des fonctions de fenêtre qui apparaissent dans la liste SELECT d'une requête ou dans la clause ORDER BY. Ces fonctions peuvent faire référence aux entrées de la clause WINDOW par leur nom dans leurs clauses OVER. Une entrée de clause WINDOW n'a pas besoin d'être référencée quelque part, mais si elle n'est pas utilisée dans la requête, elle est simplement ignorée. Il est possible d'utiliser des fonctions de fenêtre sans aucune clause WINDOW, car un appel de fonction de fenêtre peut spécifier directement sa définition de cadre dans sa clause OVER. Cependant, la clause WINDOW permet de conserver le typage lorsque la même définition de cadre est nécessaire pour plus d'une fonction de fenêtre.

Actuellement, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE et FOR KEY SHARE ne peuvent pas être spécifiés avec WINDOW.

Les fonctions de fenêtre sont décrites en détail dans le Chapitre 3.5, le Chapitre 4.2.8 et le Chapitre 7.2.5.

SELECT List

La liste SELECT (entre les mots-clés SELECT et FROM) spécifie les expressions qui forment les lignes de sortie de l'instruction SELECT. Les expressions peuvent (et le font normalement) faire référence à des colonnes calculées dans la clause FROM.

De manière similaire à une table, chaque colonne de sortie d'un SELECT a un nom. Dans un SELECT simple, ce nom est utilisé uniquement pour étiqueter la colonne pour l'affichage, mais lorsque le SELECT est une sous-requête d'une requête plus grande, le nom est vu comme le nom de la table virtuelle produite par la sous-requête dans la requête plus grande. Pour spécifier le nom à utiliser pour une colonne de sortie, écrivez output_name après l'expression de la colonne. (Vous pouvez omettre AS, mais seulement si le nom souhaité pour la sortie ne correspond à aucun mot-clé de PostgreSQL (voir App. C). Pour vous protéger contre d'éventuels ajouts futurs de mots-clés, il est conseillé d'écrire AS ou de doubler le mot-clé de sortie.) Si vous ne spécifiez pas de nom de colonne, un nom est automatiquement choisi par PostgreSQL. Si l'expression de la colonne est une référence simple à une colonne, le nom choisi est le même que le nom de la colonne. Dans des cas plus complexes, vous pouvez utiliser un nom de fonction ou de type, ou le système peut revenir à un nom généré comme ?column?.

Le nom de la colonne de sortie peut faire référence à la valeur de la colonne dans les clauses ORDER BY et GROUP BY, mais pas dans les clauses WHERE ou HAVING; là, vous devez écrire l'expression explicitement.

Au lieu d'une expression, * peut être écrit dans la liste de sortie comme un raccourci pour toutes les colonnes des lignes sélectionnées. Vous pouvez également écrire table_name.* comme un raccourci pour les colonnes de cette seule table. Dans ces cas, vous ne pouvez pas spécifier de nouveaux noms avec AS; les noms des colonnes de sortie seront les mêmes que les noms des colonnes de la table.

Selon la norme SQL, les expressions de la liste de sortie doivent être calculées avant d'appliquer DISTINCT, ORDER BY ou LIMIT. Ceci est évidemment nécessaire lorsque DISTINCT est utilisé, car sinon on ne sait pas quelles valeurs sont rendues distinctes. Cependant, dans de nombreux cas, il est souhaitable que les expressions de sortie soient calculées après ORDER BY et LIMIT, surtout si la liste de sortie contient des fonctions volatiles ou coûteuses. Avec ce comportement, l'ordre d'évaluation des fonctions est plus intuitif et il n'y aura pas d'évaluations correspondant à des lignes qui n'apparaissent jamais dans la sortie. PostgreSQL évaluera les expressions de sortie après le tri et la limitation, à condition que ces expressions ne fassent pas référence à DISTINCT, ORDER BY ou GROUP BY. (À titre d'exemple, SELECT f(x) FROM tab ORDER BY 1 doit évaluer f(x) avant de trier.) Les expressions de sortie contenant des fonctions retournant des ensembles sont évaluées après le tri et avant la limitation, de sorte que LIMIT agira pour couper la sortie d'une fonction retournant des ensembles.


Note

Les versions de PostgreSQL antérieures à 9.6 ne garantissaient pas le moment de l'évaluation des expressions de sortie par rapport au tri et à la limitation. Cela dépendait de la forme du plan de requête choisi.

DISTINCT Clause

Si SELECT DISTINCT est spécifié, toutes les lignes dupliquées sont supprimées du résultat (une ligne est conservée de chaque groupe de doublons). SELECT ALL spécifie le contraire : toutes les lignes sont conservées; c'est le comportement par défaut.

SELECT DISTINCT ON ( expression [, ...] ) ne conserve que la première ligne de chaque groupe de lignes où les expressions données évaluent à des valeurs égales. Les expressions de DISTINCT ON sont interprétées en utilisant les mêmes règles que pour ORDER BY (voir ci-dessus). Bien que la "première ligne" de chaque groupe soit imprévisible, vous ne devez pas utiliser ORDER BY pour garantir que la ligne souhaitée apparaisse en premier. Par exemple :

SELECT DISTINCT ON (location) location, time, report
    FROM weather_reports
    ORDER BY location, time DESC;

recueille le rapport météorologique le plus récent pour chaque emplacement. Mais si nous n'avions pas utilisé ORDER BY pour forcer le tri descendant des valeurs de temps pour chaque emplacement, nous aurions obtenu un rapport d'une heure imprévisible pour chaque emplacement.

Les expressions de DISTINCT ON doivent correspondre aux expressions les plus à gauche de la clause ORDER BY. La clause ORDER BY contient généralement des expressions supplémentaires qui déterminent la priorité souhaitée des lignes au sein de chaque groupe DISTINCT ON.

Actuellement, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE et FOR KEY SHARE ne peuvent pas être spécifiés avec DISTINCT.

UNION Clause

La clause UNION a ce format général :

select_statement UNION [ ALL | DISTINCT ] select_statement

select_statement est tout SELECT sans clause ORDER BY, LIMIT, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE ou FOR KEY SHARE. (ORDEN BY et LIMIT peuvent être joints à une sous-expression si elle est enfermée entre parenthèses. Sans parenthèses, ces clauses s'appliqueront au résultat de l'union, pas à son expression de droite.)

L'opérateur UNION calcule l'union des lignes retournées par les instructions SELECT impliquées. Une ligne est dans l'ensemble union de deux résultats de requête si elle apparaît dans au moins l'un d'eux. Les deux instructions SELECT qui représentent les opérandes directs de l'UNION doivent produire le même nombre de colonnes, et les colonnes correspondantes doivent être de types compatibles.

Le résultat de UNION ne contient aucune ligne dupliquée, sauf si ALL est spécifié. ALL évite la suppression des doublons. (Par conséquent, UNION ALL est généralement significativement plus rapide que UNION; utilisez ALL quand vous le pouvez.) DISTINCT peut être écrit pour spécifier explicitement le comportement par défaut de suppression des doublons.

Les unions multiples dans la même instruction SELECT sont évaluées de gauche à droite, à moins qu'elles ne soient explicitement indiquées par des parenthèses.

Actuellement, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE et FOR KEY SHARE ne peuvent pas être spécifiés non plus pour le résultat d'une union, ni pour aucune entrée d'une union.

INTERSECT Clause

La clause INTERSECT a ce format général :

select_statement INTERSECT [ ALL | DISTINCT ] select_statement

select_statement est tout SELECT

Clause EXCEPT

La clause EXCEPT a cette forme générale:

select_statement EXCEPT [ ALL | DISTINCT ] select_statement

select_statement est un SELECT sans clause ORDER BY, LIMIT, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE ou FOR KEY SHARE.

L'opérateur EXCEPT calcule l'ensemble des lignes qui sont dans le résultat du SELECT de gauche mais pas dans le résultat de droite.

Le résultat de EXCEPT ne contient aucune ligne dupliquée, à moins que l'option ALL ne soit spécifiée. Avec ALL, une ligne qui a m doublons dans la table de gauche et n dans la table de droite apparaîtra min(m, n) fois dans le résultat. DISTINCT peut être écrit pour spécifier explicitement le comportement par défaut de suppression des lignes dupliquées.

Les opérateurs EXCEPT multiples dans un même SELECT sont évalués de gauche à droite, à moins que des parenthèses n'indiquent le contraire. EXCEPT est appliqué avec une priorité plus forte qu'UNION. C'est-à-dire que A UNION B INTERSECT C sera interprété comme A UNION (B INTERSECT C).

Actuellement, les clauses FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE et FOR KEY SHARE ne peuvent être spécifiées ni pour le résultat d'un EXCEPT, ni pour aucune entrée d'un EXCEPT.

Clause ORDER BY

La clause ORDER BY est facultative et a cette forme générale:

ORDER BY expression [ ASC | DESC | USING operator ] [ NULLS { FIRST | LAST } ] [, ...]

La clause ORDER BY provoque le tri des lignes résultantes selon les expressions spécifiées. Si deux lignes sont égales selon la première expression, elles sont comparées selon la suivante, et ainsi de suite. Si elles sont égales selon toutes les expressions spécifiées, elles sont renvoyées dans un ordre implicite.

Chaque expression peut être le nom ou le numéro d'une colonne de sortie (élément de la liste SELECT), ou une expression arbitraire formée à partir de valeurs de colonnes d'entrée.

Le numéro ordinal fait référence à la position (de gauche à droite) de la colonne de sortie. Cette caractéristique permet de définir un tri basé sur une colonne qui n'a pas de nom unique. Ceci est toujours facultatif, car il est toujours possible de nommer une colonne de sortie en utilisant la clause AS.

Il est également possible d'utiliser des expressions arbitraires dans la clause ORDER BY, y compris des colonnes qui n'apparaissent pas dans la liste de sortie du SELECT. Par conséquent, la déclaration suivante est valide:

SELECT name FROM distributors ORDER BY code;

Une limitation de cette caractéristique est qu'une clause ORDER BY appliquée au résultat d'une UNION, INTERSECT ou EXCEPT ne peut spécifier que le nom ou le numéro d'une colonne de sortie, pas une expression.

Si une expression ORDER BY est un nom simple qui correspond à la fois au nom d'une colonne de sortie et au nom d'une colonne d'entrée, ORDER BY l'interprétera comme le nom de la colonne de sortie. C'est le contraire de ce que GROUP BY ferait dans la même situation. Cette incohérence a été introduite pour être compatible avec la norme SQL.

Facultativement, le mot-clé ASC (ascendant) ou DESC (descendant) peut être ajouté après toute expression de la clause ORDER BY. Si rien n'est spécifié, ASC est supposé par défaut. Alternativement, un opérateur de tri peut être spécifié dans la clause USING. Un opérateur de tri doit être membre d'une famille d'opérateurs B-tree. ASC est généralement équivalent à USING < et DESC est généralement équivalent à USING >. (Mais le créateur d'un type de données personnalisé peut définir exactement quel est l'ordre de tri par défaut, et il pourrait correspondre à des opérateurs portant d'autres noms.)

Si NULLS LAST est spécifié, les valeurs nulles sont triées après toutes les valeurs non nulles; si NULLS FIRST est spécifié, les valeurs nulles sont triées avant toutes les valeurs non nulles. Si rien n'est spécifié, le comportement par défaut est NULLS LAST lorsque ASC est utilisé, ou NULLS FIRST lorsque DESC est utilisé (ainsi, le comportement par défaut est que les valeurs nulles sont supérieures aux valeurs non nulles). Lorsque USING est spécifié, le comportement par défaut des valeurs nulles dépend de si l'opérateur est un opérateur de moindre ou de plus grande valeur.

Note: Les options de tri ne s'appliquent qu'à l'expression qui suit; par exemple, ORDER BY x, y DESC ne signifie pas la même chose que ORDER BY x DESC, y DESC.

Les données textuelles sont triées selon la collation applicable à la colonne triée. Cela peut être redéfini en incluant une clause COLLATE dans l'expression, par exemple, ORDER BY mycolumn COLLATE "en_US". Pour plus d'informations, voir Section 4.2.10 et Section 23.2.

Clause LIMIT

La clause LIMIT comprend deux sous-clauses indépendantes:

LIMIT { count | ALL }
OFFSET start

Le paramètre count spécifie le nombre maximum de lignes à retourner, tandis que start spécifie le nombre de lignes à ignorer avant de commencer à retourner des lignes. Lorsque les deux sont spécifiés, start lignes sont ignorées avant de commencer à compter count lignes à retourner.

Si l'expression count évalue à NULL, elle est considérée comme LIMIT ALL, c'est-à-dire sans limite. Si start évalue à NULL, il est considéré de la même manière qu'OFFSET 0.

SQL:2008 a introduit une syntaxe différente pour obtenir le même résultat, qui est également prise en charge par PostgreSQL. Elle est:

OFFSET start { ROW | ROWS }
FETCH { FIRST | NEXT } [ count ] { ROW | ROWS } { ONLY | WITH TIES }

Dans cette syntaxe, la valeur start ou count est obligatoire selon la norme et doit être une valeur constante, un paramètre ou un nom de variable; en tant qu'extension de PostgreSQL, d'autres expressions sont autorisées, mais elles doivent généralement être entourées de parenthèses pour éviter toute ambiguïté. Si count est omis dans une clause FETCH, la valeur par défaut est 1. L'option WITH TIES est utilisée pour retourner toutes les lignes supplémentaires qui se classent comme dernières dans l'ensemble de résultats selon la clause ORDER BY; ORDER BY est obligatoire dans ce cas, et SKIP LOCKED n'est pas autorisé. Les mots-clés ROW et ROWS, ainsi que FIRST et NEXT, sont également utilisés, mais ils n'affectent pas les effets de ces clauses. Selon la norme, la clause OFFSET doit précéder la clause FETCH si les deux sont présentes; mais PostgreSQL est plus flexible et autorise n'importe quel ordre.

Lorsque LIMIT est utilisé, il est conseillé d'utiliser une clause ORDER BY qui restreint les lignes résultantes à un seul ordre. Sinon, vous obtiendrez un sous-ensemble imprévisible des lignes de la requête, par exemple, les dixième à vingtième lignes, mais dans quel ordre? Vous ne le saurez pas, tant que vous n'aurez pas spécifié ORDER BY.

Le planificateur de requêtes prend en compte LIMIT lors de la génération d'un plan de requête, vous obtiendrez donc probablement des plans différents (qui donnent des ordres de lignes différents) en fonction de ce que vous utilisez pour LIMIT et OFFSET. Par conséquent, utiliser différentes valeurs de LIMIT et OFFSET pour sélectionner différents sous-ensembles de résultats d'une requête produira des résultats incohérents à moins que vous n'ayez exécuté un tri prédictif avec ORDER BY. Ce n'est pas une erreur; c'est une conséquence inhérente du fait que SQL ne garantit pas l'ordre des résultats d'une requête, à moins qu'ORDER BY ne soit utilisé pour restreindre l'ordre.

Il est même possible que des exécutions répétées de la même requête avec LIMIT renvoient des sous-ensembles de lignes distincts d'une table, s'il n'y a pas de clause ORDER BY pour garantir la sélection d'un sous-ensemble déterministe. Ce n'est pas une erreur; la déterminisme des résultats n'est tout simplement pas garanti dans un tel cas.

La Clause de Verrouillage

FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE et FOR KEY SHARE sont des clauses de verrouillage; elles affectent la manière dont SELECT verrouille les lignes lorsqu'il les obtient de la table.

La clause de verrouillage a la forme générale:

FOR lock_strength [ OF from_reference [, ...] ] [ NOWAIT | SKIP LOCKED ]

où lock_strength peut être l'un des éléments suivants:

UPDATE
NO KEY UPDATE
SHARE
KEY SHARE

from_reference doit être un alias de table ou un nom de table non masqué référencé dans la clause FROM. Pour plus d'informations sur chaque niveau de verrouillage de ligne, voir Section 13.3.2.

Pour empêcher l'opération d'attendre que d'autres transactions soient validées, utilisez soit l'option NOWAIT, soit SKIP LOCKED. Avec NOWAIT, l'instruction signale une erreur, au lieu d'attendre, si une ligne sélectionnée ne peut pas être verrouillée immédiatement. Avec SKIP LOCKED, toute ligne sélectionnée qui ne peut pas être verrouillée immédiatement est ignorée. Ignorer les lignes verrouillées donne une vision incohérente des données, ce n'est donc pas adapté aux tâches générales, mais peut être utilisé pour éviter les conflits de verrouillage avec plusieurs consommateurs accédant à une table similaire à une file d'attente. Note: NOWAIT et SKIP LOCKED ne s'appliquent qu'aux verrous de ligne; le verrouillage de table au niveau de la ligne (requis) est toujours pris de manière normale (voir Chapitre 13). Vous pouvez utiliser LOCK avec l'option NOWAIT en premier, si vous avez besoin d'acquérir le verrouillage de table sans attendre.

Si des tables spécifiques sont spécifiées dans une clause de verrouillage, alors seules les lignes provenant de ces tables sont verrouillées; toute autre table utilisée dans le SELECT est lue normalement. Une clause de verrouillage sans liste de table affecte toutes les tables utilisées dans l'instruction. Si une clause de verrouillage s'applique à une vue ou une sous-requête, elle affecte toutes les tables utilisées dans la vue ou la sous-requête. Cependant, ces clauses ne s'appliquent pas aux requêtes WITH référencées par la requête principale. Si vous souhaitez que le verrouillage de ligne se produise dans une requête WITH, spécifiez une clause de verrouillage à l'intérieur de la requête WITH.

Plusieurs clauses de verrouillage peuvent être écrites:

even if it is necessary to specify different locking behavior for different tables. If the same table is mentioned (or implicitly affected) by more than one locking clause, then it is processed as if it was only specified by the strongest one. Similarly, a table is processed as NOWAIT if that is specified in any of the clauses affecting it. Otherwise, it is processed as SKIP LOCKED if that is specified in any of the clauses affecting it.

Les clauses de verrouillage ne peuvent pas être utilisées dans des contextes où les lignes renvoyées ne peuvent pas être clairement identifiées par des lignes de table individuelles ; par exemple, elles ne peuvent pas être utilisées avec une agrégation.

Lorsqu'une clause de verrouillage apparaît au niveau supérieur d'une requête SELECT, les lignes verrouillées sont exactement celles qui sont renvoyées par la requête ; dans le cas d'une requête de jointure, les lignes verrouillées sont celles qui contribuent aux lignes de jointure renvoyées. De plus, les lignes qui satisfaisaient les conditions de la requête au moment de l'instantané de la requête seront verrouillées, bien qu'elles ne soient pas renvoyées si elles ont été mises à jour après l'instantané et ne satisfont plus les conditions de la requête. Si une clause LIMIT est utilisée, le verrouillage s'arrête une fois que suffisamment de lignes ont été renvoyées pour satisfaire la limite (mais notez que les lignes ignorées par OFFSET seront verrouillées). De même, si une clause de verrouillage est utilisée dans la requête d'un curseur, seules les lignes effectivement récupérées ou passées par le curseur seront verrouillées.

Lorsqu'une clause de verrouillage apparaît dans une sous-requête SELECT, les lignes verrouillées sont celles renvoyées à la requête externe par la sous-requête. Cela peut impliquer moins de lignes que l'inspection de la sous-requête seule ne le suggérerait, car les conditions de la requête externe peuvent être utilisées pour optimiser l'exécution de la sous-requête. Par exemple,

SELECT * FROM (SELECT * FROM mytable FOR UPDATE) ss WHERE col1 = 5;

verrouillera uniquement les lignes ayant col1 = 5, même si cette condition ne se trouve pas textuellement dans la sous-requête.

Les versions précédentes n'ont pas réussi à préserver un verrou qui est mis à niveau par un point de sauvegarde ultérieur. Par exemple, ce code :

BEGIN;
SELECT * FROM mytable WHERE key = 1 FOR UPDATE;
SAVEPOINT s;
UPDATE mytable SET ... WHERE key = 1;
ROLLBACK TO s;

n'aurait pas réussi à préserver le verrou FOR UPDATE après le ROLLBACK TO. Ceci a été corrigé dans la version 9.3.


Attention

Il est possible qu'une commande SELECT exécutée au niveau d'isolation de transaction READ COMMITTED et utilisant ORDER BY et une clause de verrouillage renvoie des lignes dans le désordre. Cela est dû au fait que ORDER BY est appliqué en premier. La commande trie le résultat, mais peut ensuite bloquer en essayant d'obtenir un verrou sur une ou plusieurs des lignes. Une fois que le SELECT est débloqué, certaines des valeurs des colonnes de tri peuvent avoir été modifiées, ce qui peut amener ces lignes à apparaître dans le désordre (bien qu'elles soient dans l'ordre par rapport aux valeurs des colonnes d'origine). Cela peut être contourné au besoin en plaçant la clause FOR UPDATE/SHARE dans une sous-requête, par exemple

SELECT * FROM (SELECT * FROM mytable FOR UPDATE) ss ORDER BY column1;

Notez que cela entraînera le verrouillage de toutes les lignes de mytable, alors que FOR UPDATE au niveau supérieur ne verrouillerait que les lignes effectivement renvoyées. Cela peut entraîner une différence de performance significative, en particulier si ORDER BY est combiné avec LIMIT ou d'autres restrictions. Cette technique n'est donc recommandée que si des mises à jour simultanées des colonnes de tri sont attendues et qu'un résultat strictement trié est requis.

Aux niveaux d'isolation de transaction REPEATABLE READ ou SERIALIZABLE, cela entraînerait un échec de sérialisation (avec un SQLSTATE de '40001'), il n'y a donc aucune possibilité de recevoir des lignes dans le désordre sous ces niveaux d'isolation.

Commande TABLE

La commande

TABLE name

est équivalente à

SELECT * FROM name

Elle peut être utilisée comme commande de niveau supérieur ou comme variante syntaxique d'économie d'espace dans des parties de requêtes complexes. Seules les clauses WITH, UNION, INTERSECT, EXCEPT, ORDER BY, LIMIT, OFFSET, FETCH et FOR de verrouillage peuvent être utilisées avec TABLE ; la clause WHERE et toute forme d'agrégation ne peuvent pas être utilisées.

EXEMPLES

Pour joindre la table films et la table distributeurs :

SELECT f.title, f.did, d.name, f.date_prod, f.kind
    FROM distributors d JOIN films f USING (did);
       title       | did |     name     | date_prod  |   kind
-------------------+-----+--------------+------------+----------
 The Third Man     | 101 | British Lion | 1949-12-23 | Drama
 The African Queen | 101 | British Lion | 1951-08-11 | Romantic
 ...

Pour sommer la colonne len de tous les films et regrouper les résultats par kind :

SELECT kind, sum(len) AS total FROM films GROUP BY kind;
   kind   | total
----------+-------
 Action   | 07:34
 Comedy   | 02:58
 Drama    | 14:28
 Musical  | 06:42
 Romantic | 04:38

Pour sommer la colonne len de tous les films, regrouper les résultats par kind et afficher les totaux de groupe inférieurs à 5 heures :

SELECT kind, sum(len) AS total
    FROM films
    GROUP BY kind
    HAVING sum(len) < interval '5 hours';
   kind   | total
----------+-------
 Comedy   | 02:58
 Romantic | 04:38

Les deux exemples suivants sont des moyens identiques de trier les résultats individuels en fonction du contenu de la deuxième colonne (name) :

SELECT * FROM distributors ORDER BY name;
SELECT * FROM distributors ORDER BY 2;

-----+------------------

 110 | Bavaria Atelier
 101 | British Lion
 107 | Columbia
 102 | Jean Luc Godard
 113 | Luso films
 104 | Mosfilm
 103 | Paramount
 106 | Toho
 105 | United Artists

 112 | Warner Bros.
 108 | Westward

L'exemple suivant montre comment obtenir l'union des tables distributors et actors, en limitant les résultats à ceux qui commencent par la lettre W dans chaque table. Seules les lignes distinctes sont souhaitées, donc le mot-clé ALL est omis.

distributors:               actors:
 did |     name              id |     name
-----+--------------        ----+----------------
 108 | Westward               1 | Woody Allen
 111 | Walt Disney            2 | Warren Beatty
 112 | Warner Bros.           3 | Walter Matthau
 ...                         ...
SELECT distributors.name
    FROM distributors
    WHERE distributors.name LIKE 'W%'
UNION
SELECT actors.name
    FROM actors
    WHERE actors.name LIKE 'W%';
      name
----------------
 Walt Disney

 Warner Bros.
 Warren Beatty
 Westward

Cet exemple montre comment utiliser une fonction dans la clause FROM, avec et sans liste de définition de colonnes :

CREATE FUNCTION distributors(int) RETURNS SETOF distributors AS $$
    SELECT * FROM distributors WHERE did = $1;
$$ LANGUAGE SQL;
SELECT * FROM distributors(111);
 did |    name
-----+-------------
 111 | Walt Disney
CREATE FUNCTION distributors_2(int) RETURNS SETOF record AS $$
    SELECT * FROM distributors WHERE did = $1;
$$ LANGUAGE SQL;
SELECT * FROM distributors_2(111) AS (f1 int, f2 text);
 f1  |     f2
-----+-------------
 111 | Walt Disney

Voici un exemple de fonction avec une colonne d'ordinalité ajoutée :

SELECT * FROM unnest(ARRAY['a','b','c','d','e','f']) WITH ORDINALITY;
 unnest | ordinality
--------+----------
 a      |        1
 b      |        2
 c      |        3
 d      |        4
 e      |        5
 f      |        6
(6 rows)

Cet exemple montre comment utiliser une clause WITH simple :

WITH t AS (
    SELECT random() as x FROM generate_series(1, 3)
  )
SELECT * FROM t
UNION ALL
SELECT * FROM t;
         x
--------------------
  0.534150459803641
  0.520092216785997
 0.0735620250925422
  0.534150459803641
  0.520092216785997
 0.0735620250925422

Notez que la requête WITH a été évaluée une seule fois, de sorte que nous avons obtenu deux ensembles des mêmes trois valeurs aléatoires.

Cet exemple utilise WITH RECURSIVE pour trouver tous les subordonnés (directs ou indirects) de l'employé Mary, et leur niveau d'indirectivité, à partir d'une table qui montre uniquement les subordonnés directs :

WITH RECURSIVE employee_recursive(distance, employee_name, manager_name) AS (
    SELECT 1, employee_name, manager_name
    FROM employee
    WHERE manager_name = 'Mary'
  UNION ALL
    SELECT er.distance + 1, e.employee_name, e.manager_name
    FROM employee_recursive er, employee e
    WHERE er.employee_name = e.manager_name
  )
SELECT distance, employee_name FROM employee_recursive;

Notez la forme typique des requêtes récursives : une condition initiale, suivie de UNION, suivie de la partie récursive de la requête. Assurez-vous que la partie récursive de la requête ne renverra finalement aucun tuple, sinon la requête bouclera indéfiniment. (Voir la section 7.8 pour d'autres exemples.)

Cet exemple utilise LATERAL pour appliquer une fonction renvoyant un ensemble get_product_names() pour chaque ligne de la table manufacturers :

SELECT m.name AS mname, pname
FROM manufacturers m, LATERAL get_product_names(m.id) pname;

Les fabricants n'ayant actuellement aucun produit n'apparaîtraient pas dans le résultat, car il s'agit d'une jointure interne. Si nous souhaitions inclure les noms de tels fabricants dans le résultat, nous pourrions faire ceci :

SELECT m.name AS mname, pname
FROM manufacturers m LEFT JOIN LATERAL get_product_names(m.id) pname ON true;

COMPATIBILITÉ

Bien sûr, l'instruction SELECT est compatible avec la norme SQL. Mais il y a quelques extensions et quelques fonctionnalités manquantes.

Clauses FROM omises

PostgreSQL permet d'omettre la clause FROM. Son utilisation est simple pour calculer les résultats d'expressions simples :

SELECT 2+2;
 ?column?
----------
        4

Certaines autres bases de données SQL ne peuvent pas le faire, sauf en introduisant une table factice d'une seule ligne à partir de laquelle effectuer le SELECT.

Listes SELECT vides

La liste des expressions de sortie après SELECT peut être vide, produisant une table de résultats à zéro colonne. Ce n'est pas une syntaxe valide selon la norme SQL. PostgreSQL l'autorise pour être cohérent avec l'autorisation de tables à zéro colonne. Cependant, une liste vide n'est pas autorisée lorsque DISTINCT est utilisé.

Omission du mot-clé AS

Dans la norme SQL, le mot-clé facultatif A

S peut être omis avant un nom de colonne de sortie chaque fois que le nouveau nom de colonne est un nom de colonne valide (c'est-à-dire, pas le même qu'un mot-clé réservé). PostgreSQL est légèrement plus restrictif : AS est requis si le nouveau nom de colonne correspond à un mot-clé, réservé ou non. Il est recommandé d'utiliser AS ou de mettre entre guillemets doubles les noms de colonnes de sortie, afin d'éviter tout conflit potentiel avec de futurs mots-clés ajoutés.

Dans les éléments FROM, le standard et PostgreSQL autorisent tous deux AS à être omis avant un alias qui est un mot-clé non réservé. Mais cela est impraticable pour les noms de colonnes de sortie, en raison d'ambiguïtés syntaxiques.

Omission des alias de sous-SELECT dans FROM

Selon la norme SQL, un sous-SELECT dans la liste FROM doit avoir un alias. Dans PostgreSQL, cet alias peut être omis.

ONLY et Héritage

La norme SQL exige des parenthèses autour du nom de table lors de l'écriture de ONLY, par exemple SELECT * FROM ONLY (tab1), ONLY (tab2) WHERE .... PostgreSQL considère ces parenthèses comme facultatives.

PostgreSQL autorise un * en fin de chaîne pour spécifier explicitement le comportement non-ONLY consistant à inclure les tables enfants. La norme ne le permet pas.

(Ces points s'appliquent de manière égale à toutes les commandes SQL prenant en charge l'option ONLY.)

Restrictions sur la clause TABLESAMPLE

La clause TABLESAMPLE n'est actuellement acceptée que sur les tables régulières et les vues matérialisées. Selon la norme SQL, il devrait être possible de l'appliquer à tout élément FROM.

Appels de fonctions dans FROM

PostgreSQL autorise un appel de fonction à être écrit directement comme membre de la liste FROM. Dans la norme SQL, il serait nécessaire d'encapsuler un tel appel de fonction dans un sous-SELECT ; c'est-à-dire que la syntaxe FROM func(...) alias est approximativement équivalente à FROM LATERAL (SELECT func(...)) alias. Notez que LATERAL est considéré comme implicite ; cela est dû au fait que la norme exige des sémantiques LATERAL pour un élément UNNEST() dans FROM. PostgreSQL traite UNNEST() de la même manière que les autres fonctions renvoyant des ensembles.

Espace de noms disponible pour GROUP BY et ORDER BY

Dans la norme SQL-92, une clause ORDER BY ne peut utiliser que des noms de colonnes de sortie ou des nombres, tandis qu'une clause GROUP BY ne peut utiliser que des expressions basées sur des noms de colonnes d'entrée. PostgreSQL étend chacune de ces clauses pour permettre également l'autre choix (mais il utilise l'interprétation du standard en cas d'ambiguïté). PostgreSQL permet également aux deux clauses de spécifier des expressions arbitraires. Notez que les noms apparaissant dans une expression seront toujours considérés comme des noms de colonnes d'entrée, et non comme des noms de colonnes de sortie.

SQL:1999 et les versions ultérieures utilisent une définition légèrement différente qui n'est pas entièrement compatible avec SQL-92. Dans la plupart des cas, cependant, PostgreSQL interprétera une expression ORDER BY ou GROUP BY de la même manière que SQL:1999.

Dépendances fonctionnelles

PostgreSQL reconnaît la dépendance fonctionnelle (permettant d'omettre des colonnes de GROUP BY) uniquement lorsque la clé primaire d'une table est incluse dans la liste GROUP BY. La norme SQL spécifie des conditions supplémentaires qui devraient être reconnues.

LIMIT et OFFSET

Les clauses LIMIT et OFFSET sont des syntaxes spécifiques à PostgreSQL, également utilisées par MySQL. La norme SQL:2008 a introduit les clauses OFFSET ... FETCH {FIRST|NEXT} ... pour la même fonctionnalité, comme indiqué ci-dessus dans la clause LIMIT. Cette syntaxe est également utilisée par IBM DB2. (Les applications écrites pour Oracle utilisent fréquemment une solution de contournement impliquant la colonne générée automatiquement rownum, qui n'est pas disponible dans PostgreSQL, pour implémenter les effets de ces clauses.)

FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE, FOR KEY SHARE

Bien que FOR UPDATE apparaisse dans la norme SQL, la norme ne l'autorise qu'en tant qu'option de DECLARE CURSOR. PostgreSQL l'autorise dans toute requête SELECT ainsi que dans les sous-SELECT, mais il s'agit d'une extension. Les variantes FOR NO KEY UPDATE, FOR SHARE et FOR KEY SHARE, ainsi que les options NOWAIT et SKIP LOCKED, n'apparaissent pas dans la norme.

Instructions de modification de données dans WITH

PostgreSQL autorise INSERT, UPDATE, DELETE et MERGE à être utilisées comme requêtes WITH. Ceci ne se trouve pas dans la norme SQL.

Clauses non standard

DISTINCT ON ( ... ) est une extension de la norme SQL.

ROWS FROM( ... ) est une extension de la norme SQL.

Les options MATERIALIZED et NOT MATERIALIZED de WITH sont des extensions de la norme SQL.
