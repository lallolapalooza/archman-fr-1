SET ROLE(7) Documentation PostgreSQL 18.1 SET ROLE(7)

NOM

SET_ROLE - définit l'identifiant utilisateur actuel de la session actuelle

SYNTAXE

SET [ SESSION | LOCAL ] ROLE nom_du_role
SET [ SESSION | LOCAL ] ROLE NONE
RESET ROLE

DESCRIPTION

Cette commande définit l'identifiant utilisateur actuel de la session SQL actuelle sur nom_du_role. Le nom du rôle peut être écrit en tant qu'identifiant ou littéral de chaîne. Après SET ROLE, la vérification des permissions pour les commandes SQL est effectuée comme si le rôle nommé était celui qui s'est connecté à l'origine. Notez que SET ROLE et SET SESSION AUTHORIZATION font exception ; les vérifications de permissions pour celles-ci continuent d'utiliser l'utilisateur de session actuel et l'utilisateur de session initial (l'utilisateur authentifié), respectivement.

L'utilisateur de session actuel doit avoir l'option SET pour nom_du_role spécifié, soit directement, soit indirectement via une chaîne d'appartenances avec l'option SET. (Si l'utilisateur de session est un superutilisateur, n'importe quel rôle peut être sélectionné.)

Les modificateurs SESSION et LOCAL agissent de la même manière que pour la commande SET normale.

SET ROLE NONE définit l'identifiant utilisateur actuel sur l'identifiant utilisateur de session actuel, tel que renvoyé par session_user. RESET ROLE définit l'identifiant utilisateur actuel sur le réglage spécifié lors de la connexion par les options de ligne de commande, ALTER ROLE ou ALTER DATABASE, si de tels réglages existent. Sinon, RESET ROLE définit l'identifiant utilisateur actuel sur l'identifiant utilisateur de session actuel. Ces formes peuvent être exécutées par n'importe quel utilisateur.

NOTES

En utilisant cette commande, il est possible soit d'ajouter des privilèges, soit de restreindre ses propres privilèges. Si le rôle utilisateur de session s'est vu accorder des appartenances AVEC INHERIT TRUE, il possède automatiquement tous les privilèges de chaque rôle de ce type. Dans ce cas, SET ROLE supprime effectivement tous les privilèges sauf ceux que le rôle cible possède directement ou hérite. D'un autre côté, si le rôle utilisateur de session s'est vu accorder des appartenances AVEC INHERIT FALSE, les privilèges des rôles accordés ne peuvent pas être accessibles par défaut. Cependant, si le rôle a été accordé AVEC SET TRUE, l'utilisateur de session peut utiliser SET ROLE pour supprimer les privilèges attribués directement à l'utilisateur de session et acquérir à la place les privilèges disponibles pour le rôle nommé. Si le rôle a été accordé AVEC INHERIT FALSE, SET FALSE alors les privilèges de ce rôle ne peuvent être exercés ni avec ni sans SET ROLE.

SET ROLE a des effets comparables à SET SESSION AUTHORIZATION, mais les vérifications de privilèges impliquées sont assez différentes. De plus, SET SESSION AUTHORIZATION détermine quels rôles sont autorisés pour les futures commandes SET ROLE, tandis que le changement de rôles avec SET ROLE ne modifie pas l'ensemble des rôles autorisés pour un futur SET ROLE.

SET ROLE ne traite pas les variables de session comme spécifié par les réglages ALTER ROLE du rôle ; cela ne se produit que lors de la connexion.

SET ROLE ne peut pas être utilisé dans une fonction SECURITY DEFINER.

EXEMPLES

SELECT SESSION_USER, CURRENT_USER;
 session_user | current_user
--------------+--------------
 peter        | peter
SET ROLE 'paul';
SELECT SESSION_USER, CURRENT_USER;
 session_user | current_user
--------------+--------------
 peter        | paul

COMPATIBILITE

PostgreSQL autorise la syntaxe d'identifiant ("nom_du_role"), tandis que la norme SQL exige que le nom du rôle soit écrit sous forme de littéral de chaîne. SQL n'autorise pas cette commande pendant une transaction ; PostgreSQL n'impose pas cette restriction car il n'y a aucune raison de le faire. Les modificateurs SESSION et LOCAL sont une extension PostgreSQL, tout comme la syntaxe RESET.
