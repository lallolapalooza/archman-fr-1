Safe(3perl) Guide de référence du programmeur Perl Safe(3perl)

NOM

Safe - Compiler et exécuter du code dans des compartiments restreints

SYNTAXE

use Safe;
$compartiment = new Safe;
$compartiment->permit(qw(time sort :browse));
$resultat = $compartiment->reval($code_non_securise);

DESCRIPTION

Le module d'extension Safe permet la création de compartiments dans lesquels du code perl peut être évalué. Chaque compartiment possède

un nouvel espace de noms
La "racine" de l'espace de noms (c'est-à-dire "main::") est changée pour un paquet différent et le code évalué dans le compartiment ne peut pas référencer des variables en dehors de cet espace de noms, même avec des recherches globales à l'exécution et d'autres astuces.

Le code qui est compilé en dehors du compartiment peut choisir de placer des variables dans (ou de *partager* des variables avec) l'espace de noms du compartiment et seules ces données seront visibles par le code évalué dans le compartiment.

Par défaut, les seules variables partagées avec les compartiments sont les variables "underscore" $_ et @_ (et, techniquement, les moins utilisées %_, le descripteur de fichier _ et ainsi de suite). Ceci est nécessaire car sinon les opérateurs perl qui utilisent $_ par défaut ne fonctionneront pas, pas plus que l'affectation d'arguments à @_ lors de l'entrée dans une sous-routine.

un masque d'opérateurs
Chaque compartiment a un "masque d'opérateurs" associé. Rappelez-vous que le code perl est compilé dans un format interne avant exécution. L'évaluation de code perl (par exemple via "eval" ou "do 'fichier'") provoque la compilation du code dans un format interne, puis, en l'absence d'erreur de compilation, son exécution. Le code évalué dans un compartiment est compilé en fonction du masque d'opérateurs du compartiment. Tenter d'évaluer du code dans un compartiment qui contient un opérateur masqué provoquera un échec de compilation avec une erreur. Le code ne sera pas exécuté.

Le masque d'opérateurs par défaut pour un compartiment nouvellement créé est la balise d'option ':default'.

Il est important de lire la documentation du module Opcode pour plus d'informations, notamment pour les définitions détaillées des noms d'opérateurs, des balises d'option et des ensembles d'options.

Puisque c'est uniquement au stade de la compilation que le masque d'opérateurs s'applique, un accès contrôlé à des opérations potentiellement dangereuses peut être réalisé en ayant une référence à une sous-routine enveloppante (écrite en dehors du compartiment) placée dans le compartiment. Par exemple,

$cpt = new Safe;
sub wrapper {
  # Valider les arguments et effectuer des opérations potentiellement dangereuses
}
$cpt->share('&wrapper');

AVERTISSEMENT

Le module Safe n'implémente pas un bac à sable efficace pour l'évaluation de code non fiable avec l'interpréteur perl.

Les bugs dans l'interpréteur perl qui pourraient être exploités pour contourner les restrictions de Safe ne sont pas considérés comme des vulnérabilités. Voir perlsecpolicy pour des informations supplémentaires.

Les auteurs ne donnent aucune garantie, implicite ou autre, quant à l'adéquation de ce logiciel à des fins de sécurité.

Vos résultats peuvent varier. En cas de doute, ne l'utilisez pas.

MÉTHODES

Pour créer un nouveau compartiment, utilisez

$cpt = new Safe;

L'argument optionnel est (ESPACE_NOM), où ESPACE_NOM est l'espace de noms racine à utiliser pour le compartiment (par défaut "Safe::Root0", incrémenté pour chaque nouveau compartiment).

Notez que la version 1.00 du module Safe supportait un second paramètre optionnel, MASQUE. Cette fonctionnalité a été retirée en attendant une réflexion plus approfondie. Utilisez les méthodes permit et deny décrites ci-dessous.

Les méthodes suivantes peuvent ensuite être utilisées sur l'objet compartiment retourné par le constructeur ci-dessus. L'objet argument est implicite dans chaque cas.

permit (OP, ...)

Autorise les opérateurs listés à être utilisés lors de la compilation du code dans le compartiment ( *en plus* de tout autre opérateur déjà autorisé).

Vous pouvez lister des codes d'opération par leur nom, ou utiliser un nom de balise ; voir "Balises d'opérateurs prédéfinies" dans Opcode.

permit_only (OP, ...)

Autorise *uniquement* les opérateurs listés à être utilisés lors de la compilation du code dans le compartiment (*aucun* autre opérateur n'est autorisé).

deny (OP, ...)

Interdit l'utilisation des opérateurs listés lors de la compilation du code dans le compartiment (d'autres opérateurs peuvent toujours être autorisés).

deny_only (OP, ...)

Interdit *uniquement* les opérateurs listés lors de la compilation du code dans le compartiment (*tous* les autres opérateurs seront autorisés, vous ne voudrez donc probablement pas utiliser cette méthode).

trap (OP, ...), untrap (OP, ...)

Les méthodes trap et untrap sont des synonymes de deny et permit respectivement.

share (NOM, ...)

Ceci partage la ou les variables de la liste d'arguments avec le compartiment. C'est presque identique à l'exportation de variables en utilisant le module Exporter.

Chaque NOM doit être le *nom* d'une variable non lexicale, typiquement avec l'identifiant de type initial inclus. Un mot nu est traité comme un nom de fonction.

Des exemples de noms légaux sont '$foo' pour un scalaire, '@foo' pour un tableau, '%foo' pour une table de correspondance (hash), '&foo' ou 'foo' pour une sous-routine et '*foo' pour un glob (c'est-à-dire toutes les entrées de la table des symboles associées à "foo", y compris les scalaires, tableaux, tables de correspondance, sous-routines et descripteurs de fichiers).

Chaque NOM est supposé être dans le paquet appelant. Voir share_from pour une méthode alternative (que "share" utilise).

share_from (PACKAGE, ARRAYREF)

Cette méthode est similaire à share() mais vous permet de nommer explicitement le paquet à partir duquel les symboles doivent être partagés. Les noms de symboles (y compris les caractères de type) sont fournis sous forme de référence de tableau.

$safe->share_from('main', [ '$foo', '%bar', 'func' ]);

Les noms peuvent inclure des noms de paquets, qui sont relatifs au PACKAGE spécifié. Ainsi, ces deux appels ont le même effet :

$safe->share_from('Scalar::Util', [ 'reftype' ]);
$safe->share_from('main', [ 'Scalar::Util::reftype' ]);

varglob (VARNAME)

Ceci retourne une référence glob pour l'entrée de la table des symboles de VARNAME dans le paquet du compartiment. VARNAME doit être le *nom* d'une variable sans aucun marqueur de type initial. Par exemple :

${$cpt->varglob('foo')} = "Bonjour le monde";

a le même effet que :

$cpt = new Safe 'Root';
$Root::foo = "Bonjour le monde";

mais évite d'avoir à connaître le nom du paquet de $cpt.

reval (STRING, STRICT)

Ceci évalue STRING comme du code perl à l'intérieur du compartiment.

Le code ne peut voir que l'espace de noms du compartiment (tel que retourné par la méthode root). Le paquet racine du compartiment apparaît comme le paquet "main::" pour le code à l'intérieur du compartiment.

Toute tentative par le code dans STRING d'utiliser un opérateur qui n'est pas autorisé par le compartiment provoquera une erreur (à l'exécution du programme principal mais à la compilation pour le code dans STRING). L'erreur est de la forme "'%s' piégé par le masque d'opération...".

Si une opération est piégée de cette manière, le code dans STRING ne sera pas exécuté. Si une telle op piégée

RISQUES

Cette section résume certaines des actions qu'un programme à l'intérieur d'une "sandbox" (intentionnellement ou non) peut effectuer et qui pourraient avoir un effet en dehors de la sandbox.

Mémoire
Consommer toute (ou presque toute) la mémoire disponible.
CPU
Créer des boucles infinies, etc.
Espionnage
Copier des informations privées de votre système. Même quelque chose comme votre nom d'utilisateur a de la valeur pour d'autres. Beaucoup d'informations utiles pourraient être obtenues de vos variables d'environnement, par exemple.
Signaux
Générer des signaux (en particulier SIGFPE et SIGALARM) qui affectent votre processus.

La configuration d'un gestionnaire de signaux nécessite soin et contrôle. Quel est le masque de signaux actif lors de l'appel d'un gestionnaire de signaux ? Si un utilisateur peut obtenir une fonction importée qui génère une exception et appelle le gestionnaire de signaux de l'utilisateur, le masque de signaux de l'utilisateur est-il réinstallé avant l'appel du gestionnaire ? Le gestionnaire importé est-il appelé avec son masque d'origine ou avec celui de l'utilisateur ?

Changements d'état
Des opérations comme chdir affectent le processus en général, pas seulement le code dans la sandbox. Des opérations comme rand et srand ont un effet similaire mais plus subtil.
