Sub::Exporter(3) Documentation Perl fournie par l'utilisateur Sub::Exporter(3)

NOM

Sub::Exporter - un exportateur sophistiqué pour des routines personnalisées

VERSION

version 0.991

SYNOPIS

Sub::Exporter doit être utilisé à deux endroits. D'abord, dans un module exportateur :

# dans le module exportateur :
package Text::Tweaker;
use Sub::Exporter -setup => {
  exports => [
    qw(squish titlecase), # fonctionne toujours de la même manière
    reformat => \&build_reformatter, # générateur pour construire la fonction exportée
    trim     => \&build_trimmer,
    indent   => \&build_indenter,
  ],
  collectors => [ 'defaults' ],
};

Ensuite, dans un module importateur :

# dans le module importateur :
use Text::Tweaker
  'squish',
  indent   => { margin => 5 },
  reformat => { width => 79, justify => 'full', -as => 'prettify_text' },
  defaults => { eol => 'CRLF' };

Avec cette configuration, le module importateur se retrouve avec trois routines : "squish", "indent", et "prettify_text". Ces deux dernières ont été construites selon les spécifications de l'importateur -- ce ne sont pas juste des copies du code du package exportateur.

DESCRIPTION

ATTENTION ! Si vous ne connaissez pas Exporter ou l'exportation, lisez d'abord Sub::Exporter::Tutorial !

Pourquoi des générateurs ?

Le principal avantage de Sub::Exporter par rapport aux exportateurs existants (y compris l'omniprésent Exporter.pm) est sa capacité à construire de nouveaux réf de code à exporter, plutôt que de simplement exporter du code identique à celui trouvé dans le package exportateur.

Si les consommateurs de votre module obtiennent une routine qui fonctionne comme ceci :

use Data::Analyze qw(analyze);
my $value = analyze($data, $tolerance, $passes);

et qu'ils passent constamment seulement une ou deux ensembles de valeurs différentes pour les arguments non-$data, votre code peut bénéficier de Sub::Exporter. En écrivant un simple générateur, vous pouvez leur permettre de faire ceci, à la place :

use Data::Analyze
  analyze => { tolerance => 0.10, passes => 10, -as => analyze10 },
  analyze => { tolerance => 0.15, passes => 50, -as => analyze50 };
my $value = analyze10($data);

Le package avec le générateur pour cela ressemblerait à ceci :

package Data::Analyze;
use Sub::Exporter -setup => {
  exports => [
    analyze => \&build_analyzer,
  ],
};
sub build_analyzer {
  my ($class, $name, $arg) = @_;
  return sub {
    my $data      = shift;
    my $tolerance = shift || $arg->{tolerance};
    my $passes    = shift || $arg->{passes};
    analyze($data, $tolerance, $passes);
  }
}

L'utilisateur de votre module a maintenant moins de travail à faire pour en bénéficier -- et rappelez-vous, vous êtes souvent votre propre utilisateur ! Investir dans des sous-routines personnalisées est un investissement dans la paresse future.

Cela évite également une forme courante de laideur observée dans de nombreux modules : la configuration au niveau du package. C'est-à-dire, vous avez peut-être vu quelque chose comme ce qui précède implémenté ainsi :

use Data::Analyze qw(analyze);
$Data::Analyze::default_tolerance = 0.10;
$Data::Analyze::default_passes    = 10;

Cela peut économiser du temps, jusqu'à ce que vous ayez plusieurs modules utilisant Data::Analyze. Comme il n'y a qu'une seule configuration globale, ils se marchent sur les pieds et votre code commence à avoir des erreurs mystérieuses.

Les générateurs peuvent également vous permettre d'exporter des méthodes de classe à appeler comme des sous-routines :

package Data::Methodical;
use Sub::Exporter -setup => { exports => { some_method => \&_curry_class } };
sub _curry_class {
  my ($class, $name) = @_;
  return sub { $class->$name(@_); };
}

En raison de la manière dont les exportateurs et Sub::Exporter fonctionnent, tout package qui hérite de Data::Methodical peut hériter de son exportateur et remplacer sa "some_method". Si un utilisateur importe "some_method" de ce package, il recevra une sous-routine qui appelle la méthode sur la sous-classe, plutôt que sur Data::Methodical lui-même. Gardez à l'esprit que si vous reconfigurez Sub::Exporter dans un package qui hérite de Data::Methodical, vous remplacerez bien sûr entièrement l'exportateur de Data::Methodical. "import" est une méthode, et est cachée de la même manière que toute autre méthode.

Autres personnalisations

La construction de routines personnalisées avec des générateurs n'est pas la seule façon dont Sub::Exporters permet au code importateur d'affiner son utilisation des routines exportées. Elles peuvent également être renommées pour éviter les collisions de noms.

Considérez le code suivant :

# ce programme détermine à quel cercle de l'enfer vous serez condamné
use Morality qw(sin virtue); # pour calculer la viciousité
use Math::Trig qw(:all);     # pour traiter les cercles

Le programmeur a accidentellement importé deux routines "sin". La solution, dans les modules basés sur Exporter.pm, serait d'en importer une seule et ensuite d'appeler l'autre par son nom entièrement qualifié. Alternativement, l'importateur pourrait écrire une routine qui le ferait, ou pourrait jouer avec les typeglobs.

Combien plus facile est-il d'écrire :

# ce programme détermine à quel cercle de l'enfer vous serez condamné
use Morality qw(virtue), sin => { -as => 'offense' };
use Math::Trig -all => { -prefix => 'trig_' };

et d'avoir à sa disposition "offense" et "trig_sin" -- sans parler de "trig_cos" et "trig_tan".

VERSION PERL

Cette bibliothèque devrait fonctionner sur des versions de Perl même très anciennes. Elle devrait fonctionner sur n'importe quelle version de perl publiée au cours des cinq dernières années.

Bien qu'elle puisse fonctionner sur des versions plus anciennes de perl, aucune garantie n'est faite que la version minimale requise ne sera pas augmentée. La version peut être augmentée pour quelque raison que ce soit, et il n'y a aucune promesse que des correctifs seront acceptés pour abaisser la version minimale requise de perl.

CONFIGURATION EXPORTER

Vous pouvez configurer un exportateur pour votre package en utilisant Sub::Exporter comme ceci :

package Tools;
use Sub::Exporter
  -setup => { exports => [ qw(function1 function2 function3) ] };

C'est la manière la plus simple d'utiliser l'exportateur, et elle équivaut essentiellement à ceci :

package Tools;
use base qw(Exporter);
our @EXPORT_OK = qw(function1 function2 function3);

Toute utilisation basique de Sub::Exporter ressemblera à ceci :

package Tools;
use Sub::Exporter -setup => \%config;

Les clés suivantes sont valides dans %config :

exports - une liste de routines à fournir pour l'exportation ; chaque routine peut être
          suivie d'un générateur
groups  - une liste de groupes à fournir pour l'exportation ; chacun doit être suivi par
          soit (a) une liste d'exportations, éventuellement avec des arguments pour chaque
          exportation, soit (b) un générateur
collectors - une liste de noms dans lesquels les valeurs sont collectées pour être utilisées dans
             la génération de routines ; chaque nom peut être suivi d'un validateur

En plus des options de base ci-dessus, quelques options plus avancées peuvent être passées :

into_level - combien d'appels vers le haut de la pile d'appels rechercher une cible (par défaut 0)
into       - une cible explicite (package) dans laquelle exporter les routines

En d'autres termes : Sub::Exporter installe une routine "import" qui, lorsqu'elle est appelée, exporte des routines vers l'espace de noms appelant. Les options "into" et "into_level" modifient l'endroit où ces routines exportées sont installées.

generator  - un rappel utilisé pour produire le code qui sera installé
             défaut: Sub::Exporter::default_generator
installer  - un rappel utilisé pour installer le code produit par le générateur
             défaut: Sub::Exporter::default_installer

Pour savoir comment ces rappels sont utilisés, consultez la documentation de "default_generator" et "default_installer".

{ exports => [ qw(foo bar baz), quux => \&quux_generator ] }
{ exports =>
  { foo => undef, bar => undef, baz => undef, quux => \&quux_generator } }

Les générateurs sont du code qui renvoie des références de code. Ils sont appelés avec quatre paramètres :

 $class - la classe dont la méthode d'exportation a été appelée (la classe exportatrice)
 $name  - le nom de l'export pour lequel la routine est construite
\%arg   - les arguments passés pour cet export
\%col   - les collections pour cette importation

Compte tenu de la configuration dans le "SYNOPSIS", la déclaration "use" suivante :

use Text::Tweaker
  reformat => { -as => 'make_narrow', width => 33 },
  defaults => { eol => 'CR' };

entraînerait l'appel suivant à &build_reformatter :

my $code = build_reformatter(
  'Text::Tweaker',
  'reformat',
  { width => 33 }, # notez que -as n'est pas passé
  { defaults => { eol => 'CR' } },
);

La référence de code retournée ($code) serait alors installée sous le nom "make_narrow" dans le package appelant.

Au lieu de fournir une référence de code dans la configuration, une référence au nom d'une méthode peut être fournie. Cette méthode sera alors appelée sur l'invocant de la méthode "import". (Dans ce cas, nous ne passons pas le paramètre $class, car il serait redondant.)

Configuration des groupes

La liste "groups" peut être passée dans les mêmes formes que "exports". Les groupes doivent avoir des valeurs pour être significatifs, qui peuvent soit lister les exports qui composent le groupe (éventuellement avec des arguments), soit fournir un moyen de construire le groupe.

Le cas le plus simple est le premier : une définition de groupe est une liste d'exports. Voici l'exemple qui pourrait aller dans l'exportateur du "SYNOPSIS".

groups  => {
  default    => [ qw(reformat) ],
  shorteners => [ qw(squish trim) ],
  email_safe => [
    'indent',
    reformat => { -as => 'email_format', width => 72 }
  ],
},

Les groupes sont importés en spécifiant leur nom préfixé par un tiret ou deux-points. Cette ligne de code importerait le groupe "shorteners" :

use Text::Tweaker qw(-shorteners);

Les arguments passés à un groupe lors de l'importation sont fusionnés avec les options du groupe et passés à tout générateur pertinent. Les groupes peuvent contenir d'autres groupes, mais les structures de groupes en boucle sont ignorées.

L'autre valeur possible pour une définition de groupe, une référence de code, permet à un générateur de construire plusieurs routines exportables simultanément. Ceci est utile lorsque plusieurs routines doivent partager des variables lexicales encapsulées. La référence de code doit retourner une référence de hachage. Les clés seront utilisées comme noms d'export et les valeurs sont les subs qui seront exportées.

Cet exemple montre une utilisation simple du générateur de groupe.

package Data::Crypto;
use Sub::Exporter -setup => { groups => { cipher => \&build_cipher_group } };
sub build_cipher_group {
  my ($class, $group, $arg) = @_;
  my ($encode, $decode) = build_codec($arg->{secret});
  return { cipher => $encode, decipher => $decode };
}

Les routines "cipher" et "decipher" sont construites dans un groupe car elles sont construites ensemble par du code qui encapsule leur secret dans leur environnement.

Groupes par défaut

Si un module qui utilise Sub::Exporter est "use"d sans arguments, il essaiera d'exporter le groupe nommé "default". Si ce groupe n'a pas été spécifiquement configuré, il sera vide, et rien ne se passera.

Un autre groupe est également créé s'il n'est pas défini : "all". Le groupe "all" contient tous les exports de la liste des exports.

Configuration des collecteurs

L'entrée "collectors" dans la configuration de l'exportateur donne des noms qui, lorsqu'ils sont trouvés dans l'appel d'importation, ont leurs valeurs collectées et passées à chaque générateur.

Par exemple, le générateur "build_analyzer" que nous avons vu plus haut pourrait être réécrit comme suit :

sub build_analyzer {
  my ($class, $name, $arg, $col) = @_;
  return sub {
    my $data      = shift;
    my $tolerance = shift || $arg->{tolerance} || $col->{defaults}{tolerance};
    my $passes    = shift || $arg->{passes}    || $col->{defaults}{passes};
    analyze($data, $tolerance, $passes);
  }
}

Cela permettrait à l'importateur de spécifier des valeurs par défaut globales pour ses importations :

use Data::Analyze
  'analyze',
  analyze  => { tolerance => 0.10, -as => analyze10 },
  analyze  => { tolerance => 0.15, passes => 50, -as => analyze50 },
  defaults => { passes => 10 };
my $A = analyze10($data);     # équivalent à analyze($data, 0.10, 10);
my $C = analyze50($data);     # équivalent à analyze($data, 0.15, 50);
my $B = analyze($data, 0.20); # équivalent à analyze($data, 0.20, 10);

Si des valeurs sont fournies dans la liste "collectors" lors de la configuration de l'exportateur, elles doivent être des références de code, et sont utilisées pour valider les valeurs de l'importateur. Le validateur est appelé lorsque la collection est trouvée, et s'il renvoie faux, une exception est levée. Nous pourrions nous assurer que personne n'essaie de définir une valeur de données globale facilement :

collectors => { defaults => sub { return (exists $_[0]->{data}) ? 0 : 1 } }

Les références de code des collecteurs peuvent également être utilisées comme des crochets pour effectuer des actions arbitraires avant que quoi que ce soit ne soit exporté.

Lorsque la référence de code est appelée, elle reçoit la valeur de la collection et une référence de hachage contenant les entrées suivantes :

name        - le nom du collecteur
config      - la configuration de l'exportateur (référence de hachage)
import_args - les arguments passés à l'exportateur, sans les collections (référence d'tableau)
class       - le package sur lequel l'importateur a été appelé
into        - le package dans lequel les exports seront exportés

Les collecteurs dont les noms sont entièrement en majuscules (c'est-à-dire composés de _ ou de lettres majuscules de A à Z) sont réservés à un usage spécial. Le seul collecteur spécial actuellement implémenté est "INIT", dont le crochet (s'il est présent dans la configuration de l'exportateur) est toujours exécuté avant tout autre crochet.

APPEL DE L'EXPORTATEUR

Les arguments de l'exportateur (c'est-à-dire les arguments après le nom du module dans une déclaration "use") sont analysés comme suit :

Premièrement, les collecteurs rassemblent toutes les collections trouvées dans les arguments. Tout type de référence peut être donné comme valeur pour un collecteur. Pour chaque collection donnée dans les arguments, son validateur (le cas échéant) est appelé.

Ensuite, les groupes sont développés. Si le groupe est implémenté par un générateur de groupe, le générateur est appelé. Il y a deux arguments spéciaux qui, s'ils sont donnés à un groupe, ont une signification spéciale :

-prefix - une chaîne à préfixer à tout export importé de ce groupe
-suffix - une chaîne à suffixer à tout export importé de ce groupe

Enfin, les générateurs d'exports individuels sont appelés et toutes les subs, générées ou autrement, sont installées dans le package appelant. Il n'y a qu'un seul argument spécial pour les générateurs d'exports :

-as     - où installer la sub exportée

Normalement, "-as" contiendra un nom alternatif pour la routine. Il peut, cependant, contenir une référence à un scalaire. Si c'est le cas, une référence à la routine générée sera placée dans le scalaire référencé par "-as". Elle ne sera pas installée dans le package appelant.

Arguments spéciaux de l'exportateur

L'exportateur généré accepte certaines options spéciales, qui peuvent être passées comme premier argument, dans une référence de hachage.

Ces options sont :

into_level
into
generator
installer

Ces options remplacent les options de configuration du même nom décrites dans "EXPORTER CONFIGURATION".

SOUS-ROUTINES

setup_exporter

Cette routine construit et installe une routine "import". Elle est appelée avec un seul argument, une référence de hachage contenant la configuration de l'exportateur. En utilisant cela, elle construit un exportateur et l'installe dans le package appelant sous le nom "import." En plus de la configuration normale de l'exportateur, quelques arguments nommés peuvent être passés dans la référence de hachage :

into       - dans quel package l'exportateur doit-il être installé
into_level - jusqu'à quel niveau de la pile l'exportateur doit-il être installé
as         - quel nom doit porter l'exportateur installé

Par défaut, l'exportateur est installé sous le nom "import" dans l'appelant immédiat de "setup_exporter". Autrement dit, si votre package appelle "setup_exporter" sans fournir aucun des trois arguments ci-dessus, il aura une routine "import" installée.

Fournir à la fois "into" et "into_level" provoquera une exception.

L'exportateur est construit par "build_exporter".

build_exporter

Étant donné une configuration standard d'exportateur, cette routine construit et renvoie un exportateur, c'est-à-dire une sous-routine qui peut être installée en tant que méthode de classe pour effectuer l'exportation sur demande.

Habituellement, cette méthode est appelée par "setup_exporter", qui installe ensuite l'exportateur comme routine d'importation d'un package.

default_generator

C'est le générateur par défaut de Sub::Exporter. Il prend des morceaux de configuration qui ont été rassemblés lors de l'importation et les transforme en une référence de code qui peut être installée.

my $code = default_generator(\%arg);

Les arguments passés sont :

class - la classe sur laquelle la méthode d'importation a été appelée
name  - le nom de l'export généré
