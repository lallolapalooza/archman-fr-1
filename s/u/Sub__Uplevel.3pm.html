NOM

Sub::Uplevel - apparemment exécuter une fonction dans une trame de pile supérieure

VERSION

version 0.2800

SYNTAXE

use Sub::Uplevel;
sub foo {
    print join " - ", caller;
}
sub bar {
    uplevel 1, \&foo;
}
#line 11
bar();    # main - foo.plx - 11

DESCRIPTION

Comme la fonction uplevel() de Tcl, mais pas tout à fait aussi dangereuse. L'idée est simplement de tromper caller(). Toutes les parties vraiment répréhensibles de uplevel() de Tcl sont évitées.

CE N'EST PAS LE TYPE DE CHOSE QUE VOUS VOULEZ FAIRE TOUS LES JOURS

uplevel
uplevel $nb_trames, \&func, @args;

Fait croire à la fonction donnée qu'elle est exécutée $nb_trames niveaux plus haut que le niveau de pile actuel. Ainsi, lorsqu'ils utilisent caller($frames), cela donnera en réalité caller($frames + $nb_trames) pour eux.

"uplevel(1, \&some_func, @_)" est effectivement "goto &some_func" mais vous ne quittez pas immédiatement la sous-routine actuelle. Donc, bien que vous ne puissiez pas faire ceci :

sub wrapper {
    print "Avant\n";
    goto &some_func;
    print "Après\n";
}

vous pouvez faire ceci :

sub wrapper {
    print "Avant\n";
    my @out = uplevel 1, &some_func;
    print "Après\n";
    return @out;
}

"uplevel" a la capacité d'émettre un avertissement si $nb_trames est supérieur à la profondeur actuelle de la pile d'appels, bien que cet avertissement soit désactivé et compilé par défaut car la vérification est relativement coûteuse.

Pour activer la vérification pour le débogage ou les tests, vous devez définir le global $Sub::Uplevel::CHECK_FRAMES sur true avant de charger Sub::Uplevel pour la première fois comme suit :

#!/usr/bin/perl

BEGIN {
    $Sub::Uplevel::CHECK_FRAMES = 1;
}
use Sub::Uplevel;

Définir ou changer le global après que le module ait été chargé n'aura aucun effet.

EXEMPLE

La principale raison pour laquelle j'ai écrit ce module est de pouvoir écrire des wrappers autour de fonctions et qu'elles ne sachent pas qu'elles ont été enveloppées.

use Sub::Uplevel;
my $original_foo = \&foo;
*foo = sub {
    my @output = uplevel 1, $original_foo;
    print "foo() a retourné :  @output";
    return @output;
};

Si ce code vous effraie, vous ne devriez pas utiliser ce module.

BOGUES et CAVEATS

Eh bien, la mauvaise nouvelle est que uplevel() est environ 5 fois plus lent qu'un appel de fonction normal. Une implémentation XS, quelqu'un ? Il ralentit également chaque invocation de caller(), que uplevel() soit en effet ou non.

Sub::Uplevel remplace temporairement CORE::GLOBAL::caller pour la portée de chaque appel uplevel. Il fait de son mieux pour fonctionner avec tout CORE::GLOBAL::caller existant précédemment (à la fois lors du chargement de Sub::Uplevel et au sein de chaque appel uplevel) comme ceux de Contextual::Return ou Hook::LexWrap.

Cependant, si vous utilisez régulièrement plusieurs modules qui remplacent CORE::GLOBAL::caller, vous vous exposez probablement à des problèmes.

Vous devriez charger Sub::Uplevel aussi tôt que possible dans votre programme. Comme avec tous les surcharges de CORE::GLOBAL, la surcharge n'affectera pas les modules qui ont déjà été compilés avant la surcharge. Un module qui est souvent chargé de manière inévitable avant Sub::Uplevel est Exporter. Pour recompiler de force Exporter (et Exporter::Heavy) après avoir chargé Sub::Uplevel, utilisez-le avec le tag ":aggressive" :

use Sub::Uplevel qw/:aggressive/;

La fonction privée Sub::Uplevel::_force_reload() peut recevoir une liste de modules supplémentaires à recharger si ":aggressive" n'est pas assez agressif. Recharger des modules peut casser des choses, utilisez donc cela comme dernier recours.

À partir de la version 0.20, Sub::Uplevel nécessite Perl 5.6 ou supérieur.
