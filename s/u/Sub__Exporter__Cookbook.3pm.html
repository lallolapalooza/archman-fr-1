NOM

Sub::Exporter::Cookbook - astuces utilisables, démonstratives ou stupides de Sub::Exporter

VERSION

version 0.991

APERÇU

Sub::Exporter est un outil assez simple et peut être utilisé pour accomplir quelques objectifs très simples. Son comportement de base et son application de base (c'est-à-dire l'exportation traditionnelle de fonctions) sont décrits dans Sub::Exporter::Tutorial et Sub::Exporter. Ce document présente des applications qui ne sont pas immédiates ou qui peuvent démontrer comment certaines fonctionnalités peuvent être utilisées (pour le meilleur ou pour le pire).

VERSION PERL

Cette bibliothèque devrait fonctionner dans des versions de Perl sorties même il y a longtemps. Elle devrait fonctionner dans n'importe quelle version de Perl sortie il y a cinq ans.

Bien qu'elle puisse fonctionner dans des versions anciennes de Perl, il n'est pas garanti que la version minimale requise n'augmente pas. La version peut être augmentée pour quelque raison que ce soit, et il n'est pas garanti que des correctifs soient acceptés pour réduire la version minimale requise de Perl.

LES RECETTES

Exporter des méthodes comme des routines

Alors que les modules d'exportation exportent généralement des fonctions à appeler comme des fonctions, il est facile d'utiliser Sub::Exporter pour exporter des fonctions qui peuvent être appelées comme des méthodes sur le paquet d'importation ou ses objets.

Voici un exemple simple (et naïf) :

package Mixin::DumpObj;
use Data::Dumper;
use Sub::Exporter -setup => {
  exports => [ qw(dump) ]
};
sub dump {
  my ($self) = @_;
  return Dumper($self);
}

Lorsque nous écrivons notre propre classe objet, nous pouvons importer dump en tant que méthode, appelée comme suit :

$object->dump;

En supposant que le paquet d'importation fournira une interface spécifique, un module d'exportation de méthodes peut être utilisé comme un simple plugin :

package Number::Plugin::Upto;
use Sub::Exporter -setup => {
  into    => 'Number',
  exports => [ qw(upto) ],
  groups  => [ default => [ qw(upto) ] ],
};
sub upto {
  my ($self) = @_;
  return 1 .. abs($self->as_integer);
}

La ligne "into" dans la configuration indique que ce plugin exportera par défaut dans le paquet "Number", et non dans le paquet qui utilise "use". Il peut être exporté de toute façon, mais cela fonctionne tant que la destination fournit une méthode "as_integer" comme prévu. Pour l'importer vers une destination différente, il suffit d'écrire :

use Number::Plugin::Upto { into => 'Quantity' };

Mélanger un comportement externe complexe

Lorsque nous exportons des fonctions à utiliser comme méthodes (voir ci-dessus), une option très puissante est d'exporter des méthodes qui maintiennent une fermeture capturant le module de l'exportateur. Cela permet à un utilisateur d'importer une seule méthode qui est implémentée en termes d'un paquet complet et bien structuré.

Voici un très petit exemple :

package Data::Analyzer;
use Sub::Exporter -setup => {
  exports => [ analyze => \'_generate_analyzer' ],
};
sub _generate_analyzer {
  my ($mixin, $name, $arg, $col) = @_;
  return sub {
    my ($self) = @_;
    my $values = [ $self->values ];
    my $analyzer = $mixin->new($values);
    $analyzer->perform_analysis;
    $analyzer->aggregate_results;
    return $analyzer->summary;
  };
}

S'il est importé par un paquet fournissant une méthode "values", ce plugin fournira une seule méthode "analyze" qui agit comme une interface simple à un ensemble de comportements plus complexes.

Plus important encore, comme la valeur $mixin sera l'invocateur sur lequel "import" a été appelé, vous pouvez hériter d'une classe "Data::Analyzer" et ne remplacer que des parties individuelles du comportement complexe, ce qui facilite l'écriture d'outils complexes et héritables avec des points d'entrée simples pour les interfaces externes.

Exporter des constantes

Bien que Sub::Exporter ne soit pas dans le métier d'exporter des constantes, il est facile d'exporter des constantes en utilisant l'un de ses modules frères, Package::Generator.

package Important::Constants;

use Sub::Exporter -setup => {
  collectors => [ constants => \'_set_constants' ],
};

sub _set_constants {
  my ($class, $value, $data) = @_;

  Package::Generator->assign_symbols(
    $data->{into},
    [
      MEANING_OF_LIFE => \42,
      ONE_TRUE_BASE   => \13,
      FACTORS         => [ 6, 9 ],
    ],
  );
  return 1;
}

Ensuite, quelqu'un peut écrire :

use Important::Constants 'constants';

print "Les facteurs @FACTORS produisent $MEANING_OF_LIFE dans $ONE_TRUE_BASE.";

(Les constantes doivent être exportées via un collecteur, car elles modifient effectivement le paquet d'importation d'une manière différente de l'installation de fonctions.)

Modifier le @ISA de l'importateur

Il est simple de créer un collecteur qui modifie l'héritage d'un paquet d'importation :

use Sub::Exporter -setup => {
  collectors => { -base => \'_make_base' },
};
sub _make_base {
  my ($class, $value, $data) = @_;
  my $target = $data->{into};
  push @{"$target\::ISA"}, $class;
}

Ensuite, l'utilisateur de votre classe peut écrire :

use Some::Class -base;

et il devient une sous-classe. Cela peut être très utile pour construire, par exemple, un module qui aide à construire des plugins. Nous pourrions vouloir importer des utilitaires, mais nous voulons aussi hériter du comportement d'une classe de plugin de base ;

package Framework::Util;
use Sub::Exporter -setup => {
  exports    => [ qw(log global_config) ],
  groups     => [ _plugin => [ qw(log global_config) ]
  collectors => { '-plugin' => \'_become_plugin' },
};
sub _become_plugin {
  my ($class, $value, $data) = @_;
  my $target = $data->{into};
  push @{"$target\::ISA"}, $class->plugin_base_class;
  push @{ $data->{import_args} }, '-_plugin';
}

Maintenant, vous pouvez écrire un plugin comme ceci :

package Framework::Plugin::AirFreshener;
use Framework::Util -plugin;

in

Vous ne devriez probablement pas faire cela en production. C'est offert davantage comme une démonstration qu'une suggestion.

sub exporter_upgrade {
  my ($pkg) = @_;
  my $new_pkg = "$pkg\::UsingSubExporter";
  return $new_pkg if $new_pkg->isa($pkg);
  Sub::Exporter::setup_exporter({
    as      => 'import',
    into    => $new_pkg,
    exports => [ @{"$pkg\::EXPORT_OK"} ],
    groups  => {
      %{"$pkg\::EXPORT_TAG"},
      default => [ @{"$pkg\::EXPORTS"} ],
    },
  });
  @{"$new_pkg\::ISA"} = $pkg;
  return $new_pkg;
}

Cette routine, étant donné le nom d'un package existant configuré pour utiliser Exporter.pm, renvoie le nom d'un nouveau package avec une routine "import" alimentée par Sub::Exporter. Cela vous permet d'importer "Toolkit::exported_sub" dans le package courant avec le nom "foo" en écrivant :

BEGIN {
  require Toolkit;
  exporter_upgrade('Toolkit')->import(exported_sub => { -as => 'foo' })
}

Si vous vous sentez particulièrement malicieux, cette routine aurait pu être déclarée dans le package UNIVERSAL, ce qui signifie que vous pourriez écrire :

BEGIN {
  require Toolkit;
  Toolkit->exporter_upgrade->import(exported_sub => { -as => 'foo' })
}

Le nouveau package aura la même configuration d'exportateur que l'original, mais supportera le renommage d'exportation et de groupe, y compris l'exportation dans des références scalaires. De plus, comme Sub::Exporter utilise "can" pour trouver la routine exportée, le nouveau package peut être sous-classé et certains de ses exports remplacés.
