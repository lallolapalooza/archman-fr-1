NOM

SVN::Ra - Fonctions d'accès distant Subversion

SYNOPIS

use SVN::Core;
use SVN::Ra;
my $ra = SVN::Ra->new('file:///tmp/svntest');
print $ra->get_latest_revnum;

DESCRIPTION

SVN::Ra encapsule les fonctions orientées objet "svn_ra_plugin_t", fournissant un accès à un dépôt Subversion via une URL, en utilisant le module d'accès au dépôt approprié.

SVN::Ra

SVN::Ra->new(...)

Le constructeur crée un objet RA et appelle "open" pour celui-ci. Ses paramètres sont soit une table de hachage d'options, soit une seule valeur contenant l'URL du dépôt. Les options valides sont :

url
L'URL du dépôt.
auth
Un "auth_baton" peut être donné à l'objet SVN::RA. Par défaut, c'est un "auth_provider" avec un "username_provider". Voir SVN::Client pour créer un "auth_baton".
pool
Le pool que la session RA doit utiliser. Les fonctions membres seront également appelées avec ce pool. Par défaut, c'est un pool racine nouvellement créé.
config
La table de hachage de configuration qui peut être obtenue en appelant SVN::Core::config_get_config(undef).
callback
L'espace de noms "ra_callback" à utiliser. Par défaut, SVN::Ra::Callbacks.

Les exemples suivants feront tous deux la même chose, avec tous les arguments optionnels prenant leurs valeurs par défaut :

my $ra = SVN::Ra->new('file:///tmp/repos');
my $ra = SVN::Ra->new(url => 'file:///tmp/repos');

MÉTHODES

Veuillez consulter la section svn_ra.h de l'API Subversion. Les fonctions membres de "svn_ra_plugin_t" peuvent être appelées en tant que méthodes des objets SVN::Ra, avec les arguments "session_baton" et "pool" omis.

$ra->change_rev_prop($revnum, $name, $value)
Définit la propriété de révision (non versionnée) $name à $value sur la révision $revnum, ou supprime la propriété si $value est indéfini. 
$ra->change_rev_prop(123, 'svn:log', 'Nouveau message de log.');

Bien sûr, cela ne fonctionnera que s'il existe un hook "pre-revprop-change" disponible.

$ra->check_path($path, $revnum)
Type de nœud à $path dans la révision $revnum. Un nombre qui correspond à l'une des constantes suivantes : $SVN::Node::none, $SVN::Node::file, $SVN::Node::dir, $SVN::Node::unknown.
$ra->do_diff($revision, $target, $recurse, $ignore_ancestry, $versus_url, $editor)
$ra->do_diff2($revision, $target, $recurse, $ignore_ancestry, $text_deltas, $versus_url, $editor)
Ces deux méthodes retournent un SVN::Ra::Reporter avec lequel vous pouvez décrire une copie de travail. Il appellera ensuite des méthodes sur $editor pour indiquer les différences entre le dépôt et la copie de travail.

La méthode "do_diff2" a été ajoutée dans Subversion 1.4. Elle ajoute l'option $text_deltas, qui, si elle est fausse, désactive la génération de deltas de texte sur l'éditeur. Avec "do_diff", les deltas de texte sont toujours générés.

my $reporter = $ra->do_diff(1, '', 1, 0, $repos_url,
                            MyEditor->new);
$reporter->set_path(...);
$reporter->finish_report;
$ra->do_status($target, $revision, $recurse, $editor)
Retourne un SVN::Ra::Reporter auquel vous pouvez décrire le statut d'une copie de travail. Il appellera ensuite des méthodes sur $editor pour décrire le statut actuel de la copie de travail par rapport au dépôt.
$ra->do_switch($revnum, $target, $recurse, $repos_url, $editor)
Retourne un SVN::Ra::Reporter avec lequel vous pouvez décrire une copie de travail. Il appellera ensuite des méthodes sur $editor pour indiquer comment ajuster la copie de travail pour la basculer vers la révision $revnum de $repos_url.
$ra->do_update($revision_to_update_to, $target, $recurse, $editor)
Retourne un objet SVN::Ra::Reporter. Appelez des méthodes sur le reporter pour décrire l'état actuel de votre copie de travail (ou de ce que vous mettez à jour). Après avoir appelé la méthode finish_report() du reporter, Subversion générera des appels à votre $editor pour décrire les différences entre ce que vous avez déjà et l'état du dépôt dans $revision_to_update_to.

Pour mettre à jour vers la dernière révision, passez $SVN::Core::INVALID_REVNUM comme premier argument.

$target doit être le chemin vers la partie du dépôt qui vous intéresse. Vous n'obtiendrez pas d'informations sur les changements en dehors de ce chemin. Si vous voulez tout, passez une chaîne vide.

Si $recurse est vrai et que la cible est un répertoire, mettez à jour récursivement ; sinon, mettez à jour seulement la cible et ses entrées immédiates, mais pas ses sous-répertoires (le cas échéant).

Tous les chemins sont relatifs à l'URL utilisée pour ouvrir $ra.

L'appelant ne peut pas effectuer d'opérations RA en utilisant $ra avant d'avoir terminé le rapport, et ne peut pas effectuer d'opérations RA en utilisant $ra depuis les opérations d'édition de $editor.

Cet exemple montre la mise à jour la plus simple, où le client indique au reporter qu'il n'a rien à commencer :

my $reporter = $ra->do_update($revnum, '', 1, MyEditor->new);
$reporter->set_path('', 0, 1, undef);
$reporter->finish_report;
$ra->get_commit_editor($logmsg, $callback, $callback_baton, $lock_tokens, $keep_locks)
$ra->get_commit_editor2($logmsg, $callback, $callback_baton, $lock_tokens, $keep_locks)
Retourne un objet éditeur opaque pour commiter une nouvelle révision dans le dépôt. Les valeurs retournées doivent être passées au constructeur SVN::Delta::Editor pour créer un objet éditeur que vous pouvez réellement utiliser. Par exemple : 
my $editor = SVN::Delta::Editor->new(
    $ra->get_commit_editor(
        "Je vais commiter des changements depuis mon code Perl.",
        \&commit_callback, undef, {}, 0));

Maintenant que vous avez votre éditeur, vous pouvez appeler des méthodes dessus pour décrire les changements dans l'arborescence que vous voulez effectuer, comme ajouter des répertoires, modifier le contenu des fichiers, etc. Voir SVN::Delta pour la documentation de l'interface éditeur.

La fonction $callback sera appelée pendant votre appel à la méthode "$ed->close_edit()", après que le commit ait réussi. Elle ne sera pas appelée s'il n'y avait pas de changements à commiter. Si vous n'en avez pas besoin, passez undef au lieu d'une référence de fonction.

"get_commit_editor2" est identique à "get_commit_editor", à l'exception des informations passées à la fonction de rappel. La nouvelle version, ajoutée dans Subversion 1.4, passera au rappel une seule valeur (TODO : Je ne peux pas tester cela, mais c'est probablement un objet ou une table de hachage) qui contient toutes les informations. Elle inclut également le message d'erreur du script de hook post-commit, qui n'est pas disponible avec "get_commit_editor".

Le rappel pour la version originale recevra trois arguments :

  • Le numéro de la nouvelle révision.
  • La date et l'heure auxquelles la révision a été committée, qui seront exactement la même valeur que sa propriété de révision "svn:date".

    • L'undef dans la liste des arguments de l'exemple ci-dessus est le "baton" qui est censé être passé au callback de commit, mais il ne l'est pas. Ce n'est pas un problème car vous pouvez fournir une fermeture (closure) comme callback afin qu'elle puisse accéder aux variables dont vous avez besoin.

    La valeur $logmsg doit être une chaîne de caractères qui sera stockée dans la propriété de révision "svn:log". Si undef est passé à la place, la nouvelle révision n'aura pas de propriété "svn:log".

    $lock_tokens doit être une référence vers une table de hachage associant les chemins aux jetons de verrouillage à utiliser pour ceux-ci. Il semble qu'avec Subversion 1.2, cela soit requis, donc si vous n'utilisez aucun verrou, passez simplement "{}". Dans Subversion 1.3.1 cependant, il semble nécessaire de *ne pas* passer cet argument du tout.

    Si $keep_locks est vrai, les verrous sur les fichiers validés ne seront pas libérés par la validation.

    La méthode get_commit_editor() elle-même retourne une liste de deux éléments, dont le premier (un objet "_p_svn_delta_editor_t") est l'éditeur réel. Le second est le "baton" de l'éditeur. Aucun des deux n'est utile sans encapsuler la paire dans un SVN::Delta::Editor.

    $ra->get_dir($path, $revnum)
    $ra->get_dir2($path, $revnum, $dirent_fields)
    Récupère les entrées du répertoire et les propriétés du répertoire à $path dans la révision $revnum.

    Une liste de trois valeurs est retournée. La première est une référence vers une table de hachage d'entrées de répertoire. Les clés sont les noms de tous les fichiers et répertoires dans $path (pas les chemins complets, juste les noms de fichiers). Les valeurs sont des objets _p_svn_dirent_t, avec tous leurs champs remplis. Le troisième paramètre de "get_dir2" vous permet de sélectionner des champs particuliers. À FAIRE : Je ne pense pas que les constantes que vous utiliseriez pour construire la valeur de $dirent_fields soient fournies dans l'API Perl.

    La seconde valeur est un nombre, qui n'est valide que si $revnum est $SVN::Core::INVALID_REVNUM. Si c'est le cas, la dernière révision sera récupérée, et le numéro de révision (la révision HEAD) sera retourné comme seconde valeur. Sinon, le numéro de révision retourné sera complètement arbitraire.

    La troisième valeur retournée sera une référence vers une table de hachage de toutes les propriétés du répertoire. Cela signifie *toutes* les propriétés : pas seulement celles contrôlées par l'utilisateur et stockées dans le système de fichiers du dépôt, mais aussi celles qui ne peuvent pas être modifiées et sont générées par le système SCM lui-même (par exemple, 'wcprops', 'entryprops', etc.).

    my ($dirents, undef, $props) = $ra->get_dir('trunk/dir', 123);
my ($dirents, $fetched_revnum, $props) = $ra->get_dir(
    'trunk/dir', $SVN::Core::INVALID_REVNUM);
    $ra->get_file($path, $revnum, $fh)

    Notez que $path ne peut pas se terminer par un slash sauf s'il s'agit juste de '/'.

    $ra->get_log(\@paths, $start, $end, $limit, $discover_changed_paths, $strict_node_history, \&callback)
    Pour $limit révisions de $start à $end, appelle le récepteur callback() avec des informations sur les changements effectués dans la révision (message de log, heure, etc.).

    L'appelant ne peut pas invoquer d'opérations RA en utilisant $ra depuis la fonction de rappel. Elles peuvent fonctionner dans certaines situations, mais ce n'est pas garanti.

    Le premier argument peut être soit une chaîne de caractères unique, soit une référence vers un tableau de chaînes de caractères. Chacun de ceux-ci indique un chemin dans le dépôt qui vous intéresse. Les révisions qui ne modifient aucun de ces chemins (ou les fichiers en dessous) seront ignorées. Passez simplement '' si vous ne souhaitez pas limiter par chemin.

    $start et $end doivent être des numéros de révision. Si $start a une valeur inférieure à $end, les révisions seront produites dans l'ordre croissant (r1, r2, ...), sinon dans l'ordre décroissant. Si $start est $SVN::Core::INVALID_REVNUM, il prend par défaut la dernière révision.

    À FAIRE - la phrase précédente devrait également s'appliquer à $end, mais faire cela génère un message d'erreur dans Subversion 1.3.

    $limit est un nombre indiquant le nombre maximum de fois où le récepteur callback() doit être appelé. S'il est de 0, il n'y aura pas de limite.

    Si $discover_changed_paths est vrai, alors les informations sur les changements effectués sur les chemins sont passées au callback().

    Si $strict_node_history est vrai, l'historique des copies ne sera pas parcouru (s'il existe) lors de la collecte des logs de révision pour chaque chemin.

    La fonction de rappel recevra les arguments suivants :

    • Une référence vers une table de hachage des chemins modifiés par la révision. Uniquement passée si $discover_changed_paths est vrai, sinon undef est passé à la place.

      Les clés de la table de hachage sont les chemins complets vers les fichiers et répertoires modifiés. Les valeurs sont des objets _p_svn_log_changed_path_t.

    • Numéro de révision.
    • Nom de l'utilisateur qui a effectué le changement, ou undef s'il n'est pas connu.
    • Date et heure de validation de la révision.
    • Message de log sous forme de chaîne de caractères unique, ou undef.
    • Un objet pool.

    Cet exemple affiche certaines des informations reçues dans un format simple, montrant quels chemins ont été modifiés dans chaque révision, pour toutes les révisions à partir de la première :

    $ra->get_log('', 1, $ra->get_latest_revnum, 0, 1, 0,
             \&log_callback);
sub log_callback
{
    my ($paths, $revnum, $user, $datetime, $logmsg) = @_;
    print "$datetime - $user - r$revnum\n";
    while (my ($path, $changes) = each %$paths) {
        print $changes->action, " $path\n";
        if ($changes->copyfrom_path) {
            print " from ", $changes->copyfrom_path,
                  " r", $changes->copyfrom_rev, "\n"
        }
    }
    print "\n";
}

    SVN::Ra::Reporter

    Les méthodes "do_diff", "do_status", "do_switch" et "do_update" de SVN::Ra renvoient toutes un objet SVN::Ra::Reporter, qui peut être utilisé pour décrire la copie de travail (ou d'autres données disponibles) que le client possède. Subversion l'utilise pour déterminer quelles nouvelles informations doivent être fournies via un éditeur de delta d'arbre.

    Les objets de cette classe sont en fait des wrappers simples autour des objets sous-jacents "svn_ra_reporter2_t" et de leur bâton associé.

    METHODES

    $reporter->set_path($path, $revision, $start_empty, $lock_token, $pool)
    Décrit une copie de travail $path comme étant à une $revision particulière.

    Si $start_empty est vrai et que $path est un répertoire, l'implémenteur doit supposer que le répertoire ne contient aucune entrée ni propriété.

    Cela *remplacera* tous les appels set_path() précédents effectués sur les chemins parents. $path est relatif à l'URL spécifiée dans "SVN::Ra->open()" ou "SVN::Ra->new()".

    Si $lock_token n'est pas undef, il s'agit du jeton de verrouillage pour $path dans la WC.

    Toutes les allocations temporaires sont effectuées dans $pool.

    $reporter->delete_path($path, $pool)
    Décrit une copie de travail $path comme étant manquante.

    Toutes les allocations temporaires sont effectuées dans $pool.

    $reporter->link_path($path, $url, $revision, $start_empty, $lock_token, $pool)
    Similaire à set_path(), mais diffère en ce que $path dans la copie de travail (relatif à la racine du pilote de rapport) n'est pas un reflet de $path dans le dépôt (relatif à l'URL spécifiée lors de l'ouverture de la couche RA), mais est plutôt un reflet d'un autre dépôt $url à la $revision.

    Si $start_empty est vrai et que $path est un répertoire, l'implémenteur doit supposer que le répertoire ne contient aucune entrée ni propriété.

    Si $lock_token n'est pas undef, il s'agit du jeton de verrouillage pour $path dans la WC.

    Toutes les allocations temporaires sont effectuées dans $pool.

    $reporter->finish_report($pool)
    Appelez ceci lorsque le rapport d'état est terminé ; tous les répertoires ou fichiers qui ne sont pas explicitement 'set' sont supposés être à la révision de base initialement passée à do_update(). Aucune autre fonction de reporting, y compris abort_report(), ne doit être appelée après avoir appelé cette fonction.
    $reporter->abort_report($pool)
    Si une erreur se produit pendant un rapport, cette méthode doit provoquer l'abandon et le nettoyage de la transaction du système de fichiers. Aucune autre méthode de reporting ne doit être appelée après avoir appelé cette méthode.

    SVN::Ra::Callbacks

    C'est la classe wrapper pour "svn_ra_callback_t". Pour fournir des callbacks personnalisés à SVN::Ra, héritez de cette classe et remplacez les fonctions membres.
