NOM

Smokeping::probes::IRTT - une sonde SmokePing pour IRTT https://github.com/peteheist/irtt

SYNOPSIS

*** Sondes ***
+IRTT
binary = /usr/local/bin/irtt # obligatoire
forks = 5
offset = 50%
step = 300
timeout = 15
tmpdir = /tmp/smokeping-irtt
# Les variables suivantes peuvent être redéfinies dans chaque section de cible
/^influx_.+/ = influx_location = Dans le sous-sol
dscp = 46
extraargs = --ttl=32
fill = rand
hmac = opensesame
interval = 1.5
ipversion = 6
length = 172
localaddr = 192.168.1.10:63814
metric = rtt
pings = 5
readfrom = irtt1
readfrompollinterval = 2
serverfill = rand
sleep = 0.5
writeto = irtt1
# [...]
*** Cibles ***
probe = IRTT # si c'est la sonde par défaut
# [...]
+ ma_cible
# probe = IRTT # si la sonde par défaut est autre chose
host = mon.hote
/^influx_.+/ = influx_location = Dans le sous-sol
dscp = 46
extraargs = --ttl=32
fill = rand
hmac = opensesame
interval = 1.5
ipversion = 6
length = 172
localaddr = 192.168.1.10:63814
metric = rtt
pings = 5
readfrom = irtt1
readfrompollinterval = 2
serverfill = rand
sleep = 0.5
writeto = irtt1

DESCRIPTION

Cette sonde SmokePing utilise IRTT https://github.com/peteheist/irtt pour enregistrer le temps de trajet aller-retour réseau https://fr.wikipedia.org/wiki/Latence_(informatique), le délai unidirectionnel https://fr.wikipedia.org/wiki/D%C3%A9lai_de_bout_en_bout ou la variation de délai des paquets IPDV https://fr.wikipedia.org/wiki/Variation_du_d%C3%A9lai_des_paquets (gigue), en fonction de la valeur de la variable metric.

De plus, la sonde propose une fonctionnalité de partage de résultats, qui permet d'utiliser les résultats d'une seule exécution IRTT pour enregistrer plusieurs métriques pour un hôte donné en même temps. Une cible est définie avec la variable writeto activée, ce qui sélectionne le nom d'un fichier temporaire pour enregistrer la sortie IRTT. Des cibles supplémentaires sont définies avec la variable readfrom activée avec la même valeur, qui, au lieu d'exécuter IRTT, attendent que la sortie de la cible principale soit disponible, puis l'analysent pour enregistrer la métrique choisie à partir des mêmes données. Voir les variables writeto et readfrom pour plus d'informations.

ATTENTION

La fonctionnalité de partage de résultats (variables writeto et readfrom) nécessite que le nombre de forks pour la sonde IRTT soit au moins égal au nombre total de cibles IRTT définies (indépendamment du fait qu'elles aient writeto et readfrom activés). Sinon, il peut y avoir un interblocage pendant que les cibles readfrom attendent l'achèvement de leur cible writeto correspondante, qui pourrait ne jamais démarrer.

VARIABLES

Variables spécifiques à la sonde prises en charge :

binary
L'emplacement de votre binaire irtt.

Exemple de valeur : /usr/local/bin/irtt

Valeur par défaut : /usr/bin/irtt

Ce paramètre est obligatoire.

forks
Exécuter ce nombre de processus concurrents maximum.

Exemple de valeur : 5

Valeur par défaut : 5

offset
Si vous exécutez plusieurs sondes simultanément, vous voudrez peut-être éviter qu'elles ne frappent votre réseau en même temps. En utilisant le paramètre d'offset spécifique à la sonde, vous pouvez modifier le moment où chaque sonde sera exécutée. L'offset est spécifié en % de l'intervalle total, ou alternativement comme 'random', et l'offset de la section 'General' est utilisé si rien n'est spécifié ici. Notez que cela n'influence PAS les RRD eux-mêmes, il s'agit simplement d'une question de moment où l'acquisition des données est initiée. (Cette variable n'est applicable que si la variable 'concurrentprobes' est définie dans la section 'General'.)

Exemple de valeur : 50%

step
Durée de l'intervalle de base que cette sonde doit utiliser, si elle est différente de celle spécifiée dans la section 'Database'. Notez que l'étape dans les fichiers RRD est fixe lors de leur génération initiale, et si vous modifiez le paramètre d'étape par la suite, vous devrez supprimer les anciens fichiers RRD ou les convertir d'une manière ou d'une autre. (Cette variable n'est applicable que si la variable 'concurrentprobes' est définie dans la section 'General'.)

Exemple de valeur : 300

timeout
Combien de temps prend un 'ping' unique au maximum.

Exemple de valeur : 15

Valeur par défaut : 5

tmpdir
Un répertoire temporaire dans lequel placer les fichiers pour writeto/readfrom.

Valeur par défaut : /tmp/smokeping-irtt

Variables spécifiques à la cible prises en charge :

/^influx_.+/
Ceci est une étiquette (tag) qui sera envoyée à influxdb et n'a aucun impact sur la mesure de la sonde. Le nom de l'étiquette sera envoyé sans le préfixe "influx_", qui sera remplacé par "tag_" à la place. Les étiquettes peuvent être utilisées pour le filtrage.

Exemple de valeur : influx_location = Dans le sous-sol

dscp
La valeur DSCP https://fr.wikipedia.org/wiki/DiffServ du paquet à utiliser ("irtt client --dscp"). C'est la même chose que le champ IP ToS d'un octet classique, mais sur l'Internet moderne, seuls les 6 bits inférieurs sont généralement utilisés, et cela s'appelle la valeur DSCP. Les deux bits supérieurs sont réservés à ECN https://fr.wikipedia.org/wiki/Explicit_Congestion_Notification. L'hexadécimal peut être utilisé s'il est préfixé par "0x".

Exemple de valeur : 46

extraargs
Arguments supplémentaires pour "irtt client" (voir irtt-client(1)). Faites attention avec les arguments supplémentaires, car certains peuvent corrompre les résultats.

Exemple de valeur : --ttl=32

fill
Le remplissage à utiliser dans la charge utile pour le paquet client vers serveur ("irtt client --fill"). La variable length doit être suffisamment grande pour qu'il y ait une charge utile à remplir. Utilisez rand pour un remplissage aléatoire, ou voir irtt-client(1) pour plus d'options.

Exemple de valeur : rand

hmac
La clé HMAC https://fr.wikipedia.org/wiki/HMAC à utiliser lors de l'envoi de paquets au serveur ("irtt client --hmac").

Exemple de valeur : opensesame

interval
L'intervalle entre les requêtes successives, en secondes ("irtt client -i", mais l'unité est toujours secondes (s)).

ATTENTION

Si interval est augmenté à plus de 5 secondes, le timeout (qui par défaut est pings * 5 secondes + 1) doit être modifié afin que SmokePing ne tue pas la sonde prématurément. De plus, interval ne doit pas être augmenté de telle sorte que pings * interval soit supérieur à step. Par exemple, avec step=300 et pings=20, interval ne doit pas être supérieur à 15 secondes, mais devrait de préférence être inférieur pour tenir compte des temps de négociation et d'attente des paquets.

Exemple de valeur : 1.5

Valeur par défaut : 1

ipversion
La version IP à utiliser pour les paquets (4 ou 6, correspondant à "irtt client -4" ou "irtt client -6"). Par défaut, la version IP est choisie en fonction de l'hôte fourni.

Exemple de valeur : 6

length
La longueur (taille) du paquet ("irtt client -l"). La longueur comprend les en-têtes IRTT, mais pas les en-têtes IP ou UDP. La longueur réelle du paquet est augmentée pour accueillir les en-têtes IRTT, si nécessaire.

NAME

Smokeping_probes_IRTT - IRTT probe for smokeping

SYNOPSIS

use "Smokeping_probes_IRTT"

\@average

sequence

step

pings

timeout

interval

length

dscp

localaddr

serverfill

fill

sleeptime

readfrom

writeto

readfrompollinterval

metric

ipversion

hmac

extraargs

loraw

DESCRIPTION

This probe uses the IRTT utility to measure network latency. IRTT is a very precise network latency measuring tool. See http://www.irtt.speculate.org/ for more details on IRTT itself.

This probe runs IRTT in client mode. IRTT can do monotonic as well as wall clock measurements. The probe defaults to using monotonic clock measurements, which are unaffected by NTP adjustments to the system clock.

Note that IRTT needs to be installed on both the smokeping server and the target machine.

This probe requires the use of IRTT's special UDP packets. You may need to configure your firewall to allow these packets.

See the smokeping_config(5) man page for details on how to configure the targets.

The results are stored in files in the directory specified by tmpdir in smokeping's configuration. By default this is /var/tmp/smokeping.

This probe requires the IRTT utility to be installed and accessible in the PATH.

VARIABLES

interval
The interval between probes. See smokeping_config(5) for details.
pings
How many pings should be sent to each target, if different from the global value specified in the Database section. Note that the number of pings in the RRD files is fixed when they are originally generated, and if you change this parameter afterwards, you'll have to delete the old RRD files or somehow convert them.

Example value: 5

length
The length of the UDP packets to send. Default is 100 bytes. The minimum is 28 bytes (1480 bytes for IPV6). Maximum is 1472 bytes for IPV4 (1452 for IPV6).

Example value: 1472

dscp
The DSCP value to set on the outgoing packets. Defaults to 46 (EF) if available, otherwise 0. See https://en.wikipedia.org/wiki/Differentiated_Services_Code_Point for more information.

Example value: 46

loraw
The IRTT header size as of IRTT 0.9.0 as used in SmokePing is 48 bytes when writeto is set (since both monotonic and wall clock values are requested) and 40 bytes otherwise.

Example value: 172

localaddr
The local address to bind to when sending packets ("irtt client --local"). See irtt-client(1) Host formats for valid syntax.

Example value: 192.168.1.10:63814

metric
The metric to record, one of:
  • rtt: round-trip time https://en.wikipedia.org/wiki/Round-trip_delay_time
  • send: one-way send delay https://en.wikipedia.org/wiki/End-to-end_delay (requires external time synchronization)
  • receive: one-way receive delay https://en.wikipedia.org/wiki/End-to-end_delay (requires external time synchronization)
  • ipdv: IPDV https://en.wikipedia.org/wiki/Packet_delay_variation (instantaneous packet delay variation, or jitter)
  • send_ipdv: IPDV for sent packets
  • receive_ipdv: IPDV for received packets

Note that the "send" and "receive" metrics require accurate external system clock synchronization, otherwise the values from one will be abnormally high and the other will be abnormally low or even negative, in which case the value 0 will be given SmokePing. It is recommended to install ntp on both the SmokePing client and IRTT server. Properly configured NTP may be able to synchronize time to within a few milliseconds, which is usually enough to provide useful results. PTP over a LAN may achieve microsecond-level accuracy. For best results between geographically remote hosts, GPS receivers may be used. Since "send_ipdv" and "receive_ipdv" measure the variation in times between successive packets, and since "rtt" and "ipdv" use monotonic clock values on the client side only, external time synchronization is not required for these metrics.

Default value: rtt

readfrom
The name of a file to read results from, instead of running IRTT. Use in combination with writeto to use the results from one IRTT run to record multiple metrics. The value will become the name of a file in tmpdir, and must be the same as another target's setting for writeto. Multiple targets may use the same value for readfrom, but writeto and readfrom may not be both set for a given target. When readfrom is set, any variables that affect "irtt client" are ignored because IRTT is not being invoked, including: dscp, extraargs, fill, hmac, interval, ipversion, length, localaddr and serverfill. These values are only relevant in the corresponding writeto target.

Note that the host variable must still be defined for targets that define readfrom, otherwise the target won't be used.

When using this feature, be sure to have at least as many forks for the IRTT probe as you have total IRTT targets defined. See the "DESCRIPTION" section for more information.

Example value: irtt1

readfrompollinterval
The integer interval in seconds on which to poll for results when readfrom is set. Lower numbers will allow readfrom to see the results a bit sooner, at the cost of higher CPU usage. Polling does not begin until the soonest time at which the IRTT client could have terminated normally.

Example value: 2

Default value: 5

serverfill
The fill to use in the payload for the server to client packet ("irtt client --sfill"). The length variable must be large enough to accommodate a payload. Use "rand" for random fill, or see irtt-client(1) for more options.

Example value: rand

sleep
The amount of time to sleep before starting requests or processing results (a float in seconds). This may be used to avoid CPU spikes caused by invoking multiple instances of IRTT at the same time.

Example value: 0.5

writeto
The name of a file to write results to after running IRTT. Use in combination with readfrom to use the results from this IRTT run to record multiple metrics. The value will become the name of a file in tmpdir, and any targets with readfrom set to the same value will use this target's results. There must be only one target with writeto set for a given file, and writeto and readfrom may not be both set for a given target.

When using this feature, be sure to have at least as many forks for the IRTT probe as you have total IRTT targets defined. See the "DESCRIPTION" section for more information.

Example value: irtt1
