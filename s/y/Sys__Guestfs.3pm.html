NOM

Sys::Guestfs - Bindings Perl pour libguestfs

SYNOPIS

use Sys::Guestfs;
my $g = Sys::Guestfs->new ();
$g->add_drive_opts ('guest.img', format => 'raw');
$g->launch ();
$g->mount ('/dev/sda1', '/');
$g->touch ('/hello');
$g->shutdown ();
$g->close ();

DESCRIPTION

Le module "Sys::Guestfs" fournit un binding XS Perl à l'API libguestfs pour examiner et modifier des images disque de machines virtuelles.

Parmi les choses utiles, on trouve : la modification par lots des invités, l'obtention de statistiques d'utilisation/d'espace disque (voir aussi : virt-df), la migration entre systèmes de virtualisation (voir aussi : virt-p2v), la réalisation de sauvegardes partielles, la réalisation de clones partiels d'invités, le clonage d'invités et la modification des informations de registre/UUID/nom d'hôte, et bien plus encore.

Libguestfs utilise le code du noyau Linux et de qemu, et peut accéder à tout type de système de fichiers invité que Linux et qemu peuvent utiliser, y compris, mais sans s'y limiter : ext2/3/4, btrfs, FAT et NTFS, LVM, de nombreux schémas de partitions disque différents, qcow, qcow2, vmdk.

Libguestfs fournit des moyens d'énumérer le stockage invité (par exemple, partitions, LVs, quel système de fichiers se trouve dans chaque LV, etc.). Il peut également exécuter des commandes dans le contexte de l'invité. Vous pouvez également accéder aux systèmes de fichiers via FUSE.

ERREURS

Toutes les erreurs entraînent des appels à "croak" (voir Carp(3)).

La chaîne d'erreur de libguestfs est directement disponible dans $@. Utilisez la méthode "last_errno" si vous souhaitez obtenir l'errno.

MÉTHODES

$g = Sys::Guestfs->new ([environment => 0,] [close_on_exit => 0]);
Crée un nouveau handle guestfs.

Si l'argument optionnel "environment" est faux, alors le drapeau "GUESTFS_CREATE_NO_ENVIRONMENT" est défini.

Si l'argument optionnel "close_on_exit" est faux, alors le drapeau "GUESTFS_CREATE_NO_CLOSE_ON_EXIT" est défini.

$g->close ();
Ferme explicitement le handle guestfs.

Note : Vous ne devriez généralement pas appeler cette fonction. Le handle sera fermé implicitement lorsque son compteur de références atteint zéro (par exemple, lorsqu'il sort de portée ou que le programme se termine). Cet appel n'est requis que dans certains cas exceptionnels, comme lorsque le programme peut contenir des références mises en cache au handle 'quelque part' et que vous devez absolument que la fermeture se produise immédiatement. Après avoir appelé "close", le programme ne doit appeler aucune méthode (y compris "close") sur le handle (mais l'appel implicite à "DESTROY" qui se produit lorsque la référence finale est nettoyée est correct).

$event_handle = $g->set_event_callback (\&cb, $event_bitmask);
Enregistre "cb" comme fonction de rappel pour tous les événements dans $event_bitmask (un ou plusieurs drapeaux "$Sys::Guestfs::EVENT_*" mis en logique OU).

Cette fonction retourne un handle d'événement qui peut être utilisé pour supprimer le rappel en utilisant "delete_event_callback".

La fonction de rappel reçoit 4 paramètres :

&cb ($event, $event_handle, $buf, $array)
$event
L'événement qui s'est produit (égal à l'un des "$Sys::Guestfs::EVENT_*").
$event_handle
Le handle d'événement.
$buf
Pour certains types d'événements, il s'agit d'un tampon de message (c'est-à-dire une chaîne).
$array
Pour certains types d'événements (notamment les événements de progression), il s'agit d'un tableau d'entiers.

Vous devriez lire attentivement la documentation de "guestfs_set_event_callback" dans guestfs(3) avant d'utiliser cette fonction.

$g->delete_event_callback ($event_handle);
Cela supprime le rappel qui a été précédemment enregistré à l'aide de "set_event_callback".
$str = Sys::Guestfs::event_to_string ($events);
$events est soit un seul événement, soit un masque d'événements. Ceci retourne une chaîne imprimable, utile pour le débogage.

Notez qu'il s'agit d'une fonction de classe, pas d'une méthode.

$errnum = $g->last_errno ();
Ceci retourne le dernier numéro d'erreur (errno) qui s'est produit sur le handle $g.

En cas de succès, un entier errno différent de zéro est retourné.

Si aucun numéro d'erreur n'est disponible, ceci retourne 0. Voir "guestfs_last_errno" dans guestfs(3) pour plus de détails sur la raison pour laquelle cela peut se produire.

Vous pouvez utiliser le module standard Perl Errno(3) pour comparer l'erreur numérique retournée par cet appel avec des errnos symboliques :

$g->mkdir ("/foo");
if ($g->last_errno() == Errno::EEXIST()) {
  # mkdir a échoué car le répertoire existe déjà.
}

$g->set_acl ($filename, $acl);
This function sets the Access Control List (ACL) for the file or directory named "filename" to the new ACL specified by "acl".

This function is only available if the underlying filesystem supports ACLs and if the libguestfs library was compiled with ACL support.

If the specified "filename" does not exist, an error is returned. If "filename" is a directory, the function will fail. This function is intended to be used only on regular files.

The "acl" parameter is the new ACL in either "long text form" or "short text form" (see acl(5)). The new ACL completely replaces any previous ACL on the file. The ACL must contain the full Unix permissions (eg. "u::rwx,g::rx,o::rx").

If you are specifying individual users or groups, then the mask field is also required (eg. "m::rwx"), followed by the "u:ID:..." and/or "g:ID:..." field(s). A full ACL string might therefore look like this:

u::rwx,g::rwx,o::rwx,m::rwx,u:500:rwx,g:500:rwx
\ Unix permissions / \mask/ \      ACL        /

You should use numeric UIDs and GIDs. To map usernames and groupnames to the correct numeric ID in the context of the guest, use the Augeas functions (see "$g->aug_init").

This function depends on the feature "acl". See also "$g->feature-available".

$nrdisks = $g->add_domain ($dom [, libvirturi => $libvirturi] [, readonly => $readonly] [, iface => $iface] [, live => $live] [, allowuuid => $allowuuid] [, readonlydisk => $readonlydisk] [, cachemode => $cachemode] [, discard => $discard] [, copyonread => $copyonread]);
Cette fonction ajoute le(s) disque(s) attaché(s) au domaine libvirt nommé "dom". Elle fonctionne en se connectant à libvirt, en demandant le domaine et le XML du domaine à libvirt, en l'analysant pour trouver les disques, et en appelant "$g->add_drive_opts" sur chacun d'eux.

Le nombre de disques ajoutés est retourné. Cette opération est atomique : si une erreur est retournée, aucun disque n'est ajouté.

Cette fonction effectue des vérifications minimales pour s'assurer que le domaine libvirt n'est pas en cours d'exécution (sauf si "readonly" est vrai). Dans une version future, nous essaierons d'acquérir le verrou libvirt sur chaque disque.

Les disques doivent être accessibles localement. Cela signifie souvent que l'ajout de disques depuis une connexion libvirt distante (voir https://libvirt.org/remote.html) échouera à moins que ces disques ne soient également accessibles via le même chemin de périphérique localement.

Le paramètre optionnel "libvirturi" définit l'URI libvirt (voir https://libvirt.org/uri.html). S'il n'est pas défini, nous nous connectons à l'URI libvirt par défaut (ou à celle définie par une variable d'environnement, voir la documentation libvirt pour plus de détails).

Le drapeau optionnel "live" est ignoré dans libguestfs ≥ 1.48.

Si le drapeau "allowuuid" est vrai (par défaut faux), alors un UUID *peut* être passé à la place du nom du domaine. La chaîne "dom" est traitée comme un UUID d'abord et recherchée, et si cette recherche échoue, nous traitons "dom" comme un nom comme d'habitude.

Le paramètre optionnel "readonlydisk" contrôle ce que nous faisons pour les disques marqués <readonly/> dans le XML libvirt. Les valeurs possibles sont :

readonlydisk = "error"
Si "readonly" est faux :

L'appel entier est avorté avec une erreur si un disque avec le flag <readonly/> est trouvé.

Si "readonly" est vrai :

Les disques avec le flag <readonly/> sont ajoutés en lecture seule.

readonlydisk = "read"
Si "readonly" est faux :

Les disques avec le flag <readonly/> sont ajoutés en lecture seule. Les autres disques sont ajoutés en lecture/écriture.

Si "readonly" est vrai :

Les disques avec le flag <readonly/> sont ajoutés en lecture seule.

readonlydisk = "write" (par défaut)
Si "readonly" est faux :

Les disques avec le flag <readonly/> sont ajoutés en lecture/écriture.

Si "readonly" est vrai :

Les disques avec le flag <readonly/> sont ajoutés en lecture seule.

readonlydisk = "ignore"
Si "readonly" est vrai ou faux :

Les disques avec le flag <readonly/> sont ignorés.

Si présent, la valeur de l'attribut "logical_block_size" de la balise <blockio/> dans le XML libvirt sera passée comme paramètre "blocksize" à "$g->add_drive_opts".

Les autres paramètres optionnels sont passés directement à "$g->add_drive_opts".

$g->add_drive ($filename [, readonly => $readonly] [, format => $format] [, iface => $iface] [, name => $name] [, label => $label] [, protocol => $protocol] [, server => $server] [, username => $username] [, secret => $secret] [, cachemode => $cachemode] [, discard => $discard] [, copyonread => $copyonread] [, blocksize => $blocksize]);
Cette fonction ajoute une image disque appelée filename au handle. filename peut être un fichier hôte régulier ou un périphérique hôte.

Lorsque cette fonction est appelée avant "$g->launch" (cas le plus fréquent), la première fois que vous appelez cette fonction, le disque apparaît dans l'API sous le nom /dev/sda, la deuxième fois sous /dev/sdb, et ainsi de suite.

Vous n'avez pas nécessairement besoin d'être root pour utiliser libguestfs. Cependant, vous avez évidemment besoin des permissions suffisantes pour accéder au nom de fichier pour les opérations que vous souhaitez effectuer (c'est-à-dire un accès en lecture si vous souhaitez seulement lire l'image ou un accès en écriture si vous souhaitez modifier l'image).

Cet appel vérifie que filename existe.

filename peut être la chaîne spéciale "/dev/null". Voir "NULL DISKS" dans guestfs(3).

Les arguments optionnels sont :

"readonly"
Si vrai, l'image est traitée comme étant en lecture seule. Les écritures sont toujours autorisées, mais elles sont stockées dans une superposition d'instantané temporaire qui est supprimée à la fin. Le disque que vous ajoutez n'est pas modifié.
"format"
Ceci force le format de l'image. Si vous omettez ceci (ou utilisez "$g->add_drive" ou "$g->add_drive_ro"), le format est détecté automatiquement. Les formats possibles incluent "raw" et "qcow2".

La détection automatique du format vous expose à une faille de sécurité potentielle lors du traitement d'images non fiables au format brut. Voir CVE-2010-3851 et RHBZ#642934. La spécification du format ferme cette faille de sécurité.

"iface"
Cette option rarement utilisée permet d'émuler le comportement de l'appel obsolète "$g->add_drive_with_if" (voir).
"name"
Ce champ était auparavant passé comme indication pour l'inspection de l'invité, mais il n'est plus utilisé.
"label"
Donne un label au disque. Le label doit être une chaîne courte et unique utilisant uniquement des caractères ASCII "[a-zA-Z]". En plus de son nom habituel dans l'API (tel que /dev/sda), le lecteur sera également nommé /dev/disk/guestfs/label.

Voir "DISK LABELS" dans guestfs(3).

"protocol"
L'argument optionnel protocol peut être utilisé pour sélectionner un protocole source alternatif.

Voir aussi : "REMOTE STORAGE" dans guestfs(3).

"protocol = "file""
filename est interprété comme un fichier ou un périphérique local. C'est le défaut si le paramètre optionnel protocol est omis.
"protocol = "ftp"|"ftps"|"http"|"https""
Se connecte à un serveur FTP ou HTTP distant. Le paramètre "server" doit également être fourni - voir ci-dessous.

Voir aussi : "FTP AND HTTP" dans guestfs(3)

"protocol = "iscsi""
Se connecte au serveur iSCSI. Le paramètre "server" doit également être fourni - voir ci-dessous. Le paramètre "username" peut être fourni. Voir ci-dessous. Le paramètre "secret" peut être fourni. Voir ci-dessous.

Voir aussi : "ISCSI" dans guestfs(3).

"protocol = "nbd""
Se connecte au serveur Network Block Device. Le paramètre "server" doit également être fourni - voir ci-dessous.

Voir aussi : "NETWORK BLOCK DEVICE" dans guestfs(3).

"protocol = "rbd""
Se connecte au serveur Ceph (librbd/RBD). Le paramètre "server" doit également être fourni - voir ci-dessous. Le paramètre "username" peut être fourni. Voir ci-dessous. Le paramètre "secret" peut être fourni. Voir ci-dessous.

Voir aussi : "RBD" dans guestfs(3).

"server"
Utilisé avec les protocoles distants (voir ci-dessus). Pour "ftp" et "http", c'est le nom d'hôte du serveur. Pour "iscsi", c'est le nom de l'initiateur iSCSI. Pour "nbd", c'est le nom d'hôte du serveur NBD. Pour "rbd", c'est le nom du serveur Ceph (par exemple, "mycephcluster") ou le chemin vers le fichier de configuration Ceph (par exemple, "/etc/ceph/ceph.conf").

Le nom du serveur peut être précédé d'une chaîne de connexion libvirt (par exemple, "qemu:///system?uri=..."). Ceci est utilisé pour forcer l'utilisation d'une connexion libvirt particulière.

"username"
Le nom d'utilisateur pour l'authentification. Utilisé avec "iscsi" et "rbd".
"secret"
Le mot de passe ou le secret pour l'authentification. Utilisé avec "iscsi" et "rbd".
"cachemode"
Définit le mode de mise en cache du disque. Les valeurs possibles sont "none", "writeback", "writethrough", "unsafe". Le comportement par défaut est de ne pas spécifier de mode de cache, ce qui permet à l'hyperviseur de choisir le mode par défaut.
"discard"
Si vrai, le passage de défausse des blocs non utilisés est activé. Cela est pris en charge par le pilote de périphérique sous-jacent (par exemple, le pilote de périphérique virtio-scsi). Les valeurs possibles sont "unmap" (envoi de commandes UNMAP/TRIM) ou "discard" (envoi de commandes de défausse plus anciennes). L'activation de cette option peut améliorer les performances et l'utilisation de l'espace sur les périphériques de stockage qui prennent en charge la défausse, tels que les SSD.
"copyonread"
Si vrai, le pilote de périphérique utilise l'option copy-on-read pour les images. Ceci est une optimisation pour les images qui sont rarement modifiées. Lorsque cette option est activée, l'hyperviseur peut directement écrire sur la page de données sans avoir besoin de la copier au préalable. Notez que cela peut rendre l'image moins résiliente en cas de crash.
"blocksize"
Définit la taille des blocs du périphérique disque. La taille est spécifiée en octets. Si elle n'est pas spécifiée, la taille par défaut est de 512 octets.
"CEPH" dans guestfs(3).

"protocol = "ssh""
Se connecter au serveur Secure Shell (ssh).

Le paramètre "server" doit être fourni. Le paramètre "username" peut être fourni. Voir ci-dessous.

Voir aussi : "SSH" dans guestfs(3).

"server"
Pour les protocoles qui nécessitent l'accès à un serveur distant, il s'agit d'une liste de serveurs. 
Protocole       Nombre de serveurs requis
--------       --------------------------
file           La liste doit être vide ou le paramètre non utilisé du tout
ftp|ftps|http|https  Exactement un
iscsi          Exactement un
nbd            Exactement un
rbd            Zéro ou plus
ssh            Exactement un

Chaque élément de la liste est une chaîne spécifiant un serveur. La chaîne doit être dans l'un des formats suivants :

hostname
hostname:port
tcp:hostname
tcp:hostname:port
unix:/chemin/vers/socket

Si le numéro de port est omis, le numéro de port standard pour le protocole est utilisé (voir /etc/services).

"username"
Pour les protocoles "ftp", "ftps", "http", "https", "iscsi", "rbd" et "ssh", ceci spécifie le nom d'utilisateur distant.

S'il n'est pas fourni, le nom d'utilisateur local est utilisé pour "ssh", et aucune authentification n'est tentée pour ceph. Mais notez que cela peut parfois donner des résultats inattendus, par exemple lors de l'utilisation du backend libvirt et si le backend libvirt est configuré pour démarrer l'appliance qemu sous un utilisateur spécial comme "qemu.qemu". En cas de doute, spécifiez le nom d'utilisateur distant souhaité.

"secret"
Pour le protocole "rbd" uniquement, ceci spécifie le 'secret' à utiliser lors de la connexion au périphérique distant. Il doit être encodé en base64.

S'il n'est pas fourni, un secret correspondant au nom d'utilisateur donné sera recherché dans les emplacements par défaut de la chaîne de clés, ou si aucun nom d'utilisateur n'est donné, aucune authentification ne sera utilisée.

"cachemode"
Choisir si libguestfs respectera ou non les opérations de synchronisation (sûr mais lent) ou non (dangereux mais rapide). Les valeurs possibles pour cette chaîne sont :
"cachemode = "writeback""
C'est la valeur par défaut.

Les opérations d'écriture dans l'API ne retournent pas avant qu'un appel write(2) ne soit terminé sur l'hôte [mais notez que cela n'implique pas que quoi que ce soit soit écrit sur le disque].

Les opérations de synchronisation dans l'API, y compris les synchronisations implicites dues à la journalisation du système de fichiers, ne retourneront pas avant qu'un appel fdatasync(2) ne soit terminé sur l'hôte, indiquant que les données ont été validées sur le disque.

"cachemode = "unsafe""
Dans ce mode, il n'y a aucune garantie. Libguestfs peut mettre en cache n'importe quoi et ignorer les demandes de synchronisation. Ceci convient uniquement aux disques temporaires ou à usage unique.
"discard"
Activer ou désactiver le support de discard (alias trim ou unmap) sur ce lecteur. S'il est activé, les opérations telles que "$g->fstrim" pourront éliminer / rendre fin / percer des trous dans le fichier ou le périphérique hôte sous-jacent.

Les paramètres discard possibles sont :

"discard = "disable""
Désactiver le support de discard. C'est la valeur par défaut.
"discard = "enable""
Activer le support de discard. Échouer si discard n'est pas possible.
"discard = "besteffort""
Activer le support de discard si possible, mais ne pas échouer s'il n'est pas pris en charge.

Comme tous les backends et tous les systèmes sous-jacents ne prennent pas en charge discard, c'est un bon choix si vous voulez utiliser discard si possible, mais que cela ne vous dérange pas s'il ne fonctionne pas.

"copyonread"
Le paramètre booléen "copyonread" active la prise en charge de la copie à la lecture. Ceci n'affecte que les formats de disque qui ont des fichiers de sauvegarde, et permet aux lectures d'être stockées dans la couche de superposition, accélérant ainsi les lectures multiples de la même zone de disque.

La valeur par défaut est false.

"blocksize"
Ce paramètre définit la taille de secteur du disque. Les valeurs possibles sont 512 (la valeur par défaut si le paramètre est omis) ou 4096. Utilisez 4096 lors de la manipulation d'un disque "Advanced Format" qui utilise une taille de secteur de 4 Ko (https://en.wikipedia.org/wiki/Advanced_Format).

Seul un sous-ensemble des backends prend en charge ce paramètre (actuellement seuls les backends libvirt et direct le font).

$g->add_drive_opts ($filename [, readonly => $readonly] [, format => $format] [, iface => $iface] [, name => $name] [, label => $label] [, protocol => $protocol] [, server => $server] [, username => $username] [, secret => $secret] [, cachemode => $cachemode] [, discard => $discard] [, copyonread => $copyonread] [, blocksize => $blocksize]);
Ceci est un alias de "add_drive".
$g->add_drive_ro ($filename);
Cette fonction est l'équivalent de l'appel "$g->add_drive_opts" avec le paramètre optionnel "GUESTFS_ADD_DRIVE_OPTS_READONLY" défini à 1, de sorte que le disque est ajouté en lecture seule, avec le format détecté automatiquement.
$g->add_drive_ro_with_if ($filename, $iface);
Ceci est identique à "$g->add_drive_ro" mais permet de spécifier l'émulation d'interface QEMU à utiliser au moment de l'exécution. Les backends direct et libvirt ignorent "iface".

Cette fonction est obsolète. Dans un nouveau code, utilisez l'appel "add_drive" à la place.

Les fonctions obsolètes ne seront pas supprimées de l'API, mais le fait qu'elles soient obsolètes indique qu'il y a des problèmes avec l'utilisation correcte de ces fonctions.

$g->add_drive_scratch ($size [, name => $name] [, label => $label] [, blocksize => $blocksize]);
Cette commande ajoute un disque temporaire de secours à la poignée. Le paramètre "size" est la taille virtuelle (en octets). Le disque de secours est initialement vierge (toutes les lectures renvoient des zéros jusqu'à ce que vous commenciez à y écrire). Le disque est supprimé lorsque la poignée est fermée.

Les arguments optionnels "name", "label" et "blocksize" sont transmis à "$g->add_drive_opts".

$g->add_drive_with_if ($filename, $iface);
Ceci est identique à "$g->add_drive" mais permet de spécifier l'émulation d'interface QEMU à utiliser au moment de l'exécution. Les backends direct et libvirt ignorent "iface".

    La raison est que nous ne savons pas quels groupes sont pris en charge par l'appliance/le démon tant qu'il n'est pas en cours d'exécution et qu'il peut être interrogé.

$g->parse_environment_list (\@environment);
Analyse la liste de chaînes de caractères de l'argument "environment" et définit les indicateurs dans le handle en conséquence. Par exemple, si "LIBGUESTFS_DEBUG=1" est une chaîne dans la liste, alors l'indicateur "verbose" est défini dans le handle.

C'est la même chose que "$g->parse_environment", sauf qu'il analyse une liste explicite de chaînes au lieu de l'environnement du programme.

$g->part_add ($device, $prlogex, $startsect, $endsect);
Cette commande ajoute une partition à "device". S'il n'y a pas de table de partitions sur le périphérique, appelez d'abord "$g->part_init".

Le paramètre "prlogex" est le type de partition. Normalement, vous devriez y passer "p" ou "primary", mais les tables de partitions MBR prennent également en charge les types de partitions "l" (ou "logical") et "e" (ou "extended").

Les "startsect" et "endsect" sont le début et la fin de la partition en secteurs. "endsect" peut être négatif, ce qui signifie qu'il compte à rebours à partir de la fin du disque (-1 est le dernier secteur).

La création d'une partition qui couvre tout le disque n'est pas si facile. Utilisez "$g->part_disk" pour cela.

$g->part_del ($device, $partnum);
Cette commande supprime la partition numérotée "partnum" sur "device".

Notez que dans le cas du partitionnement MBR, la suppression d'une partition étendue supprime également toutes les partitions logiques qu'elle contient.

$g->part_disk ($device, $parttype);
Cette commande est simplement une combinaison de "$g->part_init" suivie de "$g->part_add" pour créer une seule partition primaire couvrant tout le disque.

Le "parttype" est le type de table de partitions, généralement "mbr" ou "gpt", mais d'autres valeurs possibles sont décrites dans "$g->part_init".

DISPONIBILITÉ

De temps en temps, nous ajoutons de nouvelles API libguestfs. De plus, certaines API libguestfs ne seront pas disponibles dans toutes les versions de libguestfs (la version Fedora est complète, mais d'autres versions peuvent désactiver des fonctionnalités). Comment tester si les API dont votre programme Perl a besoin sont disponibles dans la version de "Sys::Guestfs" que vous utilisez ?

Pour tester si une fonction particulière est disponible dans la classe "Sys::Guestfs", utilisez la méthode Perl UNIVERSAL can(METHOD) (voir perlobj(1)). Par exemple :

use Sys::Guestfs;
if (defined (Sys::Guestfs->can ("set_verbose"))) {
  print "\$g->set_verbose est disponible\n";
}

Pour tester si des fonctionnalités particulières sont prises en charge par la version actuelle, utilisez la méthode "feature_available" comme dans l'exemple ci-dessous. Notez que l'appliance doit être lancée d'abord.

$g->feature_available ( ["augeas"] );

Pour plus d'informations à ce sujet, reportez-vous à la section "AVAILABILITY" de guestfs(3).

STOCKAGE DES DONNÉES DANS LE HANDLE

Le handle retourné par "new" est une référence de hachage. Le hachage contient normalement quelques éléments :

{
  _g => [données privées utilisées par libguestfs],
  _flags => [indicateurs fournis lors de la création du handle]
}

Les appelants peuvent ajouter d'autres éléments à ce hachage pour stocker des données à leurs propres fins. Les données persistent pendant toute la durée de vie du handle.

Tous les champs dont le nom commence par un trait de soulignement sont réservés à un usage privé par libguestfs. Nous pourrions en ajouter d'autres à l'avenir.

Il est recommandé que les appelants préfixent le nom de leur(s) champ(s) par une chaîne unique, afin d'éviter les conflits avec d'autres utilisateurs.
