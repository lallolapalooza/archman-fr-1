POE::Loop(3) Documentation Perl contribuée par l'utilisateur POE::Loop(3)

NOM

POE::Loop - documentation de l'interface du pont de boucle d'événements de POE

SYNOPIS

$kernel->loop_initialize();
$kernel->loop_finalize();
$kernel->loop_do_timeslice();
$kernel->loop_run();
$kernel->loop_halt();
$kernel->loop_watch_signal($signal_name);
$kernel->loop_ignore_signal($signal_name);
$kernel->loop_attach_uidestroy($gui_window);
$kernel->loop_resume_time_watcher($next_time);
$kernel->loop_reset_time_watcher($next_time);
$kernel->loop_pause_time_watcher();
$kernel->loop_watch_filehandle($handle, $mode);
$kernel->loop_ignore_filehandle($handle, $mode);
$kernel->loop_pause_filehandle($handle, $mode);
$kernel->loop_resume_filehandle($handle, $mode);

DESCRIPTION

POE::Loop est une classe de base virtuelle qui définit une interface de boucle d'événements standard. Les sous-classes de POE::Loop se mélangent à POE::Kernel et implémentent les fonctionnalités nécessaires pour gérer les boucles d'événements sous-jacentes de manière cohérente. Cette documentation couvre l'interface, qui est partagée par toutes les sous-classes.

Au chargement de POE::Kernel, celui-ci recherche dans %INC les modules de boucle d'événements. POE::Kernel charge la sous-classe POE::Loop la plus appropriée pour la boucle d'événements qu'il trouve. La sous-classe insère ses méthodes dans POE::Kernel, complétant ainsi la classe au moment du chargement. POE et POE::Kernel fournissent des moyens d'indiquer la boucle d'événements souhaitée au cas où la détection automatique ferait une erreur ou si le développeur préfère être explicite. Voir "Utiliser POE avec d'autres boucles d'événements" dans POE::Kernel pour des instructions sur la façon d'utiliser réellement POE avec d'autres boucles d'événements, les conventions de nommage des boucles d'événements et d'autres détails.

Des sous-classes de POE::Loop existent pour de nombreuses boucles d'événements prises en charge par Perl : select(), IO::Poll, WxWindows, EV, Glib, Event, etc. Voir CPAN pour une liste complète.

NOTES GENERALES

Comme précédemment noté, les sous-classes de POE::Loop fournissent des méthodes supplémentaires à POE::Kernel et ne sont pas des objets à part entière en elles-mêmes.

Chaque sous-classe de POE::Loop définit d'abord son propre espace de noms et sa version à l'intérieur. De cette façon, CPAN et d'autres peuvent suivre sa version. Elles basculent ensuite vers le paquet POE::Kernel pour définir leurs méthodes supplémentaires.

POE::Loop est conçu comme une classe de mixage car Perl imposait une pénalité de performance pour l'héritage de méthodes au moment de la conception de la classe. Cela pourrait être modifié à l'avenir, mais cela nécessitera des changements en cascade dans plusieurs autres classes.

Voici un squelette d'une sous-classe de POE::Loop :

use strict;
# Pont de votre toolkit pour POE::Kernel;
package POE::Loop::VotreToolkit;
use vars qw($VERSION);
$VERSION = '1.000'; # NOTE - Doit être #.### (trois décimales)
package POE::Kernel;
# Définir les données lexicales privées ici.
# Implémenter l'interface POE::Loop ici.
1;
__END__

... la documentation va ici ...
=cut

INTERFACE PUBLIQUE

L'interface publique de POE::Loop est divisée en quatre parties : méthodes administratives, méthodes de gestion des signaux, méthodes de gestion du temps et méthodes de surveillance des descripteurs de fichiers. Chaque groupe et ses membres seront décrits en détail sous peu.

Les sous-classes de POE::Loop utilisent des variables lexicales pour garder une trace des choses. L'implémentation exacte est laissée à l'auteur de la sous-classe. POE::Loop::Select conserve ses vecteurs de bits pour les appels select() dans des variables lexicales vues de la classe (statiques). POE::Loop::Gtk suit un seul moniteur de temps et plusieurs moniteurs de fichiers.

Les ponts utilisent souvent des méthodes privées comme rappels depuis leurs boucles d'événements. Les ponts Event, Gtk et Tk font cela. Les noms des rappels privés doivent commencer par "_loop_" pour éviter les collisions avec d'autres méthodes.

Les développeurs devraient examiner les ponts existants pour se faire une idée des choses. Le drapeau "-m" pour perldoc affichera un module dans son intégralité.

perldoc -m POE::Loop::Select
perldoc -m POE::Loop::Gtk
...

Méthodes administratives

Ces méthodes initialisent et finalisent une boucle d'événements, exécutent la boucle pour traiter les événements et l'arrêtent.

loop_initialize

Initialise la boucle d'événements. Les kits d'outils graphiques nécessitent particulièrement un appel ou une séquence d'initialisation pour la configuration. Par exemple, Tk nécessite qu'un widget soit créé avant que les événements ne soient traités, et l'interface utilisateur du programme sera considérée comme détruite si ce widget est fermé.

sub loop_initialize {
  my $self = shift;
  $poe_main_window = Tk::MainWindow->new();
  die "impossible de créer une fenêtre principale Tk" unless defined $poe_main_window;
  $self->signal_ui_destroy($poe_main_window);
}

POE::Loop::Select initialise ses vecteurs de bits select().

sub loop_initialize {
  @loop_vectors = ( '', '', '' );
  vec($loop_vectors[MODE_RD], 0, 1) = 0;
  vec($loop_vectors[MODE_WR], 0, 1) = 0;
  vec($loop_vectors[MODE_EX], 0, 1) = 0;
}

loop_finalize

Finalise la boucle d'événements. La plupart des boucles d'événements ne nécessitent rien ici puisqu'elles se sont déjà arrêtées au moment où loop_finalize() est appelée. Cependant, c'est un bon endroit pour vérifier qu'un pont n'a pas divulgué de mémoire ou de données. Cet exemple provient de POE::Loop::Event.

sub loop_finalize {
  my $self = shift;
  foreach my $fd (0..$#fileno_watcher) {
    next unless defined $fileno_watcher[$fd];
    foreach my $mode (MODE_RD, MODE_WR, MODE_EX) {
      POE::Kernel::_warn(
        "Mode $mode watcher pour fileno $fd est défini pendant la finalisation de la boucle"
      ) if defined $fileno_watcher[$fd]->[$mode];
    }
  }
  $self->loop_ignore_all_signals();
}

loop_do_timeslice

Attend que le temps passe ou que de nouveaux événements se produisent, et distribue les événements qui arrivent à échéance. Si la boucle d'événements sous-jacente le fait via des rappels, alors loop_do_timeslice() fournira une colle minimale ou ne fera rien.

Par exemple, loop_do_timeslice() pour POE::Loop::Select configure et appelle select(). Si des fichiers ou d'autres ressources deviennent actifs, elle met en file d'attente des événements pour eux. Enfin, elle déclenche la distribution pour tous les événements qui sont dus.

D'autre part, la boucle d'événements Gtk gère tout cela, donc loop_do_timeslice() est vide pour le pont Gtk.

Une implémentation échantillon de loop_do_timeslice() n'est pas présentée ici car elle serait soit assez grande, soit vide. Voir chaque POE::Loop::IO_Poll ou Select pour les grandes. Event et Gtk sont vides.

Les ponts pour Poll et Select pour les grandes. Ceux pour Event et Gtk sont vides, et celui de Tk (dans POE::Loop::TkCommon) est plutôt petit.

loop_run

Exécute une boucle d'événements jusqu'à ce que POE n'ait plus de sessions à traiter. Cette méthode a tendance à être très petite, et elle est souvent implémentée en termes de loop_do_timeslice(). Par exemple, POE::Loop::IO_Poll l'implémente :

sub loop_run {
  my $self = shift;
  while ($self->_data_ses_count()) {
    $self->loop_do_timeslice();
  }
}

Cette méthode est encore plus triviale lorsqu'une boucle d'événements la gère. Ceci provient du pont Gtk :

sub loop_run {
  unless (defined $_watcher_timer) {
    $_watcher_timer = Gtk->idle_add(\&_loop_resume_timer);
  }
  Gtk->main;
}

loop_halt

loop_halt() fait ce qu'elle dit : elle arrête la boucle d'événements sous-jacente de POE. Elle a tendance à être soit triviale pour les boucles d'événements externes, soit vide pour celles qui sont implémentées dans le pont lui-même (IO_Poll, Select).

Par exemple, la méthode loop_run() dans le pont Poll se termine lorsque les sessions sont épuisées, donc sa méthode loop_halt() est vide :

sub loop_halt {
  # ne fait rien
}

Gtk, cependant, doit être arrêté car il ne sait pas quand POE est terminé.

sub loop_halt {
  Gtk->main_quit();
}

Méthodes de gestion des signaux

Ces méthodes activent et désactivent les moniteurs de signaux. Elles sont utilisées par POE::Resource::Signals pour gérer les moniteurs de signaux d'une boucle d'événements.

La plupart des boucles d'événements utilisent le %SIG de Perl pour surveiller les signaux. C'est tellement courant que POE::Loop::PerlSignals implémente l'interface pour le compte d'autres sous-classes.

loop_watch_signal NOM_DU_SIGNAL

Surveille un NOM_DU_SIGNAL donné. NOM_DU_SIGNAL est la version trouvée dans %SIG, qui a tendance à être le nom du signal du système avec le préfixe "SIG" supprimé.

L'implémentation de POE::Loop::PerlSignals ajoute des rappels à %SIG, à l'exception de CHLD/CL

Alarmes et Gestion du Temps

Ces méthodes permettent d'activer et de désactiver un minuteur ou une alarme dans la boucle d'événements sous-jacente. POE n'en nécessite qu'un seul, qui est réutilisé ou recréé si nécessaire.

La plupart des boucles d'événements déclenchent des rappels lorsque le temps est écoulé. Il incombe au pont de s'enregistrer et de se désinscrire d'un rappel selon les besoins. Lorsqu'il est appelé, le rappel doit déclencher les événements arrivés et éventuellement définir un nouveau rappel pour le prochain événement à déclencher.

Les méthodes de gestion du temps peuvent accepter NEXT_EVENT_TIME. C'est le moment où le prochain événement sera dû, en temps universel époque (temps époque UNIX). NEXT_EVENT_TIME est un nombre réel et peut avoir une précision inférieure à la seconde. Il incombe au pont de convertir cette valeur en ce que la boucle d'événements sous-jacente requiert.

loop_resume_time_watcher NEXT_EVENT_TIME

Reprendre un minuteur déjà actif. Utilisé avec loop_pause_time_watcher() pour fournir un basculement plus économique pour les cas fréquents. Comme mentionné précédemment, NEXT_EVENT_TIME est en temps universel époque et peut avoir une précision inférieure à la seconde.

loop_resume_time_watcher() est utilisé par les ponts qui définissent leurs minuteurs dans la boucle d'événements sous-jacente. Par exemple, POE::Loop::Gtk l'implémente ainsi :

sub loop_resume_time_watcher {
  my ($self, $next_time) = @_;
  $next_time -= time();
  $next_time *= 1000;
  $next_time = 0 if $next_time < 0;
  $_watcher_timer = Gtk->timeout_add(
    $next_time, \&_loop_event_callback
  );
}

Cette méthode est généralement vide dans les ponts qui implémentent leurs propres boucles d'événements.

loop_reset_time_watcher NEXT_EVENT_TIME

Réinitialiser un minuteur, souvent en arrêtant ou en détruisant un minuteur existant et en en créant un nouveau à la place. C'est généralement un wrapper pour loop_resume_time_watcher() qui détruit d'abord un minuteur existant. Par exemple, l'implémentation de POE::Loop::Gkt :

sub loop_reset_time_watcher {
  my ($self, $next_time) = @_;
  Gtk->timeout_remove($_watcher_timer);
  undef $_watcher_timer;
  $self->loop_resume_time_watcher($next_time);
}

loop_pause_time_watcher

Suspendre un minuteur sans le détruire, si la boucle d'événements sous-jacente le supporte. POE::Loop::Event le supporte :

sub loop_pause_time_watcher {
  $_watcher_timer or return;
  $_watcher_timer->stop();
}

Gestion de l'activité des fichiers

Ces méthodes permettent d'activer et de désactiver les surveillants d'activité de fichiers. Il existe quatre méthodes : loop_watch_filehandle(), loop_ignore_filehandle(), loop_pause_filehandle() et loop_resume_filehandle(). Les méthodes "pause" et "resume" sont des versions légères de "ignore" et "watch" respectivement.

Toutes les méthodes prennent les deux mêmes paramètres : un descripteur de fichier HANDLE et un MODE d'accès. Les MODES peuvent être MODE_RD, MODE_WR ou MODE_EX. Ces constantes sont définies par POE::Kernel et correspondent aux significations des méthodes select_read(), select_write() et select_expedite() de POE::Kernel.

POE appelle MODE_EX "expéditif" car il signale généralement qu'un fichier est prêt pour des informations hors bande. Toutes les boucles d'événements ne gèrent pas MODE_EX. Par exemple, Tk :

sub loop_watch_filehandle {
  my ($self, $handle, $mode) = @_;
  my $fileno = fileno($handle);
  my $tk_mode;
  if ($mode == MODE_RD) {
    $tk_mode = 'readable';
  }
  elsif ($mode == MODE_WR) {
    $tk_mode = 'writable';
  }
  else {
    # Le document Tk implique par défaut que les fichiers expéditifs ne sont pas gérés. Ceci est la première partie de deux.
    confess "Tk ne supporte pas les fichiers expéditifs";
  }
  # ... le reste omis ....
}

loop_watch_filehandle FILE_HANDLE, IO_MODE

Surveiller l'activité d'un descripteur de fichier HANDLE dans un MODE d'E/S spécifié. Selon la boucle d'événements sous-jacente, un surveillant ou un rappel sera enregistré pour le descripteur de fichier HANDLE. L'activité dans le MODE spécifié (lecture, écriture ou hors bande) déclenchera l'émission de l'événement correspondant dans l'espace d'application.

POE::Loop::Select définit le bit fileno() dans le vecteur de bits select() correspondant. Il maintient également le compte des descripteurs de fichiers actifs.

sub loop_watch_filehandle {
  my ($self, $handle, $mode) = @_;
  my $fileno = fileno($handle);
  vec($loop_vectors[$mode], $fileno, 1) = 1;
  $loop_filenos{$fileno} |= (1<<$mode);
}

loop_ignore_filehandle FILE_HANDLE, IO_MODE

Arrêter la surveillance du descripteur de fichier HANDLE dans un MODE d'E/S spécifié. Arrête (et potentiellement détruit) le surveillant correspondant au descripteur de fichier HANDLE et au MODE.

Le loop_ignore_filehandle() de POE::Loop::IO_Poll gère les bits de descripteur/mode pour sa méthode _poll() ici. Il effectue également un nettoyage si un descripteur n'est plus surveillé après cet appel d'ignorance.

sub loop_ignore_filehandle {
  my ($self, $handle, $mode) = @_;
  my $fileno = fileno($handle);
  my $type = mode_to_poll($mode);
  my $current = $poll_fd_masks{$fileno} || 0;
  my $new = $current & ~$type;
  if (TRACE_FILES) {
    POE::Kernel::_warn(
      sprintf(
        "<fh> Ignorer $fileno: " .
        ": Masque actuel: 0x%02X - suppression 0x%02X = 0x%02X\n",
        $current, $type, $new
      )
    );
  }
  if ($new) {
    $poll_fd_masks{$fileno} = $new;
  }
  else {
    delete $poll_fd_masks{$fileno};
  }
}

loop_pause_filehandle FILE_HANDLE, IO_MODE

Ceci est une version légère de loop_ignore_filehandle(). Elle est utilisée en conjonction avec loop_resume_filehandle() pour changer temporairement l'état d'un surveillant sur un descripteur de fichier HANDLE dans un MODE spécifique.

Certaines boucles d'événements, comme Event.pm, prennent en charge la désactivation et la réactivation de leurs surveillants sans avoir à détruire et recréer les objets surveillants.

sub loop_pause_filehandle {
  my ($self, $handle, $mode) = @_;
  my $fileno = fileno($handle);
  $fileno_watcher[$fileno]->[$mode]->stop();
}

En comparaison, la méthode loop_ignore_filehandle() d'Event annule et détruit l'objet surveillant.

sub loop_ignore_filehandle {
  my ($self, $handle, $mode) = @_;
  my $fileno = fileno($handle);
  if (defined $fileno_watcher[$fileno]->[$mode]) {
    $fileno_watcher[$fileno]->[$mode]->cancel();
    undef $fileno_watcher[$fileno]->[$mode];
  }
}

Ignorer et recréer les surveillants est relativement coûteux, c'est pourquoi les méthodes select_pause_read() et select_resume_read() de POE::Kernel (et les méthodes correspondantes pour l'écriture et l'expédition) utilisent les versions les plus rapides.

loop_resume_filehandle FILE_HANDLE, IO_MODE

Ceci est une version légère de loop_watch_filehandle(). Elle est utilisée en conjonction avec loop_pause_filehandle() pour changer temporairement l'état d'un surveillant sur un descripteur de fichier HANDLE dans un MODE spécifique.

Comment POE trouve les ponts de boucle d'événements

Ceci est un récapitulatif de "Utilisation de POE avec d'autres boucles d'événements" dans POE::Kernel.

Premièrement, si une sous-classe de POE::Loop est chargée manuellement avant POE::Kernel, alors elle sera utilisée. Fin de l'histoire.

Si aucune n'est chargée, POE::Kernel recherche un module de boucle d'événements externe dans %INC. Pour chaque module dans %INC, les sous-classes correspondantes de POE::XS::Loop et POE::Loop sont essayées.

Par exemple, si IO::Poll est chargé, POE::Kernel essaie :

use POE::XS::Loop::IO_Poll;
use POE::Loop::IO_Poll;

Ceci est relativement coûteux, mais garantit que POE::Kernel peut trouver de nouvelles sous-classes de POE::Loop sans les définir dans un registre central.

POE::Loop::Select est la boucle d'événements de dernier recours. Elle est chargée si aucune autre boucle d'événements n'est disponible dans %INC.

On ne saurait trop insister sur le fait que les boucles d'événements doivent être chargées avant POE::Kernel. Sinon, elles ne seront pas présentes dans %INC et POE::Kernel ne les détectera pas.

NAME

POE::Loop - the POE event loop

SYNOPSIS

use POE::Loop;

POE::Loop::load($driver, $options);
POE::Loop::run();
POE::Loop::stop();

DESCRIPTION

POE is an event-driven application framework. It provides a way to write high-performance, asynchronous applications. POE::Loop is the core of POE, managing the event loop and dispatching events to the appropriate objects.

It is not intended to be used directly by end users. Instead, it is called by other POE modules and by POE applications.

The event loop can be implemented by various drivers, such as POE::Loop::Select (using select(2)), POE::Loop::Poll (using poll(2)), or POE::Loop::Epoll (using epoll(7)) on Linux systems.

GENERAL NOTES

POE::Loop is a part of the POE framework and is not meant to be used directly. The event loop is typically started with POE::Kernel::run, which in turn calls POE::Loop::run.

If you are writing a POE application, you should refer to the documentation for POE(3) and related modules.

PUBLIC INTERFACE

The public interface for POE::Loop is minimal and primarily used internally by POE itself. It includes:

POE::Loop::load($driver, $options)
Loads and initializes the specified event loop driver. $driver is the name of the driver module (e.g., POE::Loop::Select). $options are driver-specific.
POE::Loop::run()
Starts the event loop. This function blocks until the loop is stopped.
POE::Loop::stop()
Stops the event loop.

HOW POE FINDS EVENT LOOP BRIDGES

POE searches for available event loop drivers in the following order:

  1. Explicitly specified driver: If a driver is specified during the kernel's initialization (e.g., via configuration or explicitly in code), that driver will be used.
  2. Environment variables: POE checks for environment variables like POE_LOOP_DRIVER.
  3. System capabilities: POE attempts to load the most efficient driver available for the system. This typically means trying POE::Loop::Epoll on Linux, then POE::Loop::Poll, and finally POE::Loop::Select.

The chosen driver is then loaded using POE::Loop::load.

SEE ALSO

POE(3), POE::Kernel(3), POE::Loop::Select(3), POE::Loop::Poll(3), POE::Loop::Epoll(3).

Authors of POE distributions are encouraged to use the tests for their own distributions.

BUGS

None known.
