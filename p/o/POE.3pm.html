Nom

POE - Framework portable de multitâche et de réseau pour tout cycle d'événements

Syntaxe

#!/usr/bin/perl
use warnings;
use strict;
use POE;  # Inclut automatiquement POE::Kernel et POE::Session.
sub handler_start {
  my ($kernel, $heap, $session) = @_[KERNEL, HEAP, SESSION];
  print "Session ", $session->ID, " a démarré.\n";
  $heap->{count} = 0;
  $kernel->yield('increment');
}
sub handler_increment {
  my ($kernel, $heap, $session) = @_[KERNEL, HEAP, SESSION];
  print "Session ", $session->ID, " a atteint ", ++$heap->{count}, ".\n";
  $kernel->yield('increment') if $heap->{count} < 10;
}
sub handler_stop {
  print "Session ", $_[SESSION]->ID, " s'est arrêtée.\n";
}
for (1..10) {
  POE::Session->create(
    inline_states => {
      _start    => \&handler_start,
      increment => \&handler_increment,
      _stop     => \&handler_stop,
    }
  );
}
POE::Kernel->run();
exit;

Description

POE est un framework pour la multitâche et le réseau coopératifs, basés sur les événements, en Perl. D'autres langages ont des frameworks similaires. Python a Twisted. TCL a "le cycle d'événements".

POE fournit une interface unifiée à divers cycles d'événements, y compris select(), IO::Poll, Glib, Gtk, Tk, Wx et Gtk2. Beaucoup de ces interfaces de cycle d'événements ont été écrites par d'autres, avec le soutien de POE::Test::Loops. Vous les trouverez sur CPAN.

POE atteint son haut degré de portabilité vers différents systèmes d'exploitation et versions de Perl en étant entièrement écrit en Perl. CPAN héberge des modules Perl OPTIONNELS de POE si la vitesse est plus importante que la portabilité.

POE est conçu en couches. Chaque couche s'appuie sur les couches inférieures. Les programmes peuvent utiliser POE à n'importe quel niveau d'abstraction et peuvent être mélangés et utilisés de manière transparente au sein d'un même programme. N'oubliez pas, cependant, que les niveaux supérieurs nécessitent souvent plus de ressources que les niveaux inférieurs. Les commodités qu'ils offrent ne sont pas gratuites.

Les couches visibles de l'iceberg POE sont le bord d'un iceberg en croissance. Sprocket, POE::Stage et d'autres distributions CPAN s'appuient sur ce travail. Nous vous encourageons à explorer.

Même si vous allez aussi loin que possible, tout se résume à des appels à POE::Kernel. Ainsi, le code terrestre peut coopérer facilement avec les systèmes qui sont en l'air.

Couche 1 : Noyau et Sessions

La couche la plus basse est composée de POE::Kernel, POE::Session et d'autres types de sessions.

POE::Kernel effectue la majeure partie du travail. Il fournit une interface portable pour la détection d'activité sur des descripteurs de fichiers ouverts, des minuteries multiples, la gestion des signaux et d'autres fonctions moins courantes.

POE::Session et ses classes dérivées encapsulent le concept d'une tâche basée sur les événements. Elles personnalisent également la répartition des événements pour une convention d'appel spécifique. POE::NFA, par exemple, est davantage une machine à états correcte. D'autres classes de sessions CPAN existent également.

Tout se résume à ces classes ou aux concepts qu'elles implémentent. Si vous manquez de temps, ce que vous devriez lire en plus de cette section est POE::Kernel et POE::Session.

Couche 2 : Roues, Filtres et Pilotes

Les objets POE::Wheel sont des mixins dynamiques pour les instances de POE::Session. Ces "roues" effectuent des tâches très communes et génériques de manière très réutilisable et personnalisable. POE::Wheel::ReadWrite, par exemple, implémente des E/S non bloquantes avec mise en mémoire tampon. Ce dont presque tout le monde a besoin, alors pourquoi le réinventer à la main ?

Les objets POE::Filter personnalisent les roues de manière modulaire. Les filtres agissent comme des couches d'E/S, transformant les flux bruts en données structurées et sérialisant les structures en quelque chose d'approprié pour les flux. Il y en a aussi plusieurs sur CPAN.

Les pilotes sont l'endroit où les roues rencontrent la route. Dans ce cas, la route est une sorte de descripteur de fichier. Les pilotes effectuent la lecture et l'écriture de manière standard, de sorte que les roues n'ont pas besoin de connaître la différence entre send() et syswrite().

Les objets POE::Driver sont ce qui est donné aux moins, mais fréquemment, le plus commun, POE::Driver::SysRW, est universel et également celui par défaut, donc la plupart des gens n'auront jamais à le spécifier.

Couche 3 : Composants

Les classes POE::Component sont des classes Perl de base qui utilisent POE pour effectuer des tâches de manière non bloquante ou coopérative. C'est une définition très large, et les composants POE sont présents partout sur la carte des abstractions.

De nombreux composants, tels que POE::Component::Server::SMTP, encapsulent les détails généraux d'une application entière. D'autres effectuent des tâches assez spécifiques, comme POE::Component::DirWatch::Object.

Les composants POE sont souvent juste des objets Perl normaux. L'objet susmentionné, POE::Component::DirWatch::Object, utilise Moose. D'autres frameworks d'objets et méta-objets sont pris en charge.

Il convient également de mentionner POE::Component::Generic, qui permet de créer un composant POE à partir de n'importe quel module bloquant.

Il existe un bon nombre de composants sur CPAN. <

Couche 4 et au-delà : Frameworks et Métaphores d'Objets

Il est possible d'abstraire complètement POE derrière un framework distinct. En fait, nous vous invitons à écrire des abstractions spécifiques à un domaine qui masquent complètement POE si vous en avez besoin. L'avantage est qu'même à ces niveaux d'abstraction élevés, les choses continueront à être échangées à partir du niveau 1.

Deux exemples d'abstractions de niveau ultra-élevé sont Sprocket, un framework réseau qui fait son propre truc, et POE::Stage, la tentative de formaliser et de standardiser les composants POE faite par le créateur de POE.

Il est également possible de communiquer entre des processus POE. Cela s'appelle IKC, pour Inter-Kernel Communication. Il existe quelques composants IKC sur CPAN <

Couche 0 : Internes de POE

L'architecture en couches de POE se poursuit au-delà de la surface. Les entrailles de POE sont divisées en classes spécifiques POE::Loop pour chaque cycle d'événements pris en charge. Les fonctions internes sont divisées par type, donnant des classes POE::Resource pour les alias, les contrôles, les événements, les extrefs, les gestionnaires de fichiers, les SIDs, les sessions et les signaux.

Les API de POE::Kernel peuvent être étendues à l'aide de classes mixin POE::API. Quelques personnes courageuses ont même publié de nouvelles API sur CPAN, comme POE::API::Peek (qui vous donne accès à certaines des fonctions internes de POE::Resource).

Par conception, il est possible d'implémenter de nouvelles parties de POE::Kernel en créant une autre classe POE::Resource. Une fois que vous le faites, vous pouvez exposer la fonctionnalité avec une nouvelle classe mixin POE::API.

DESCRIPTION

POE is an event-driven programming system. It is designed to make it easier to write complex, interactive programs such as IRC bots, game servers, and network daemons.

POE is not a framework in the sense that it enforces a specific application structure. Rather, it's a library that provides a collection of tools that may be used to create event-driven programs.

The core of POE is its event loop. A POE program consists of one or more "sessions" that are run by the event loop. When an event occurs, the event loop dispatches it to the appropriate session. A session might be something as simple as a loop that waits for input from a terminal, or something as complex as a web server.

A POE program may consist of one or more sessions. Each session typically has its own state, its own event handlers, and its own set of resources. Sessions may communicate with each other through events.

POE is designed to be portable. It is written in "Plain Perl" and does not require any nonstandard libraries to run. Most POE programs will run on any system that has a modern version of Perl installed.

POE is highly extensible. It is easy to write new POE components and to integrate existing Perl modules into POE programs. The POE::Wheel interface, in particular, is designed to make it easy to wrap existing blocking modules into POE-compatible components.

Core Concepts Document Common Features

POE::Session, POE::Event, and POE::State document the core concepts of POE. These are the fundamental building blocks of any POE program, and it is essential to understand them before proceeding.

POE::Loop documents the event loop. This is the heart of POE, and it is responsible for dispatching events to the appropriate sessions. There are several different implementations of POE::Loop, each with its own strengths and weaknesses.

POE::Kernel is the main interface to the POE event loop. It is used to create sessions, send events, and otherwise control the execution of the program.

Session Types

POE provides a number of different session types, each designed for a specific purpose. These include:

  • POE::Session::Simple - A basic session type that is suitable for simple programs.
  • POE::Session::Reusable - A session type that can be reused multiple times.
  • POE::Session::NonBlocking - A session type that is designed for non-blocking operations.

In addition to these standard session types, you can also create your own custom session types. This is done by subclassing POE::Session and implementing the necessary methods.

Driver Types

POE drivers are responsible for handling input and output for sessions. They provide a portable interface to underlying operating system features such as sockets, pipes, and ttys.

POE provides a number of different driver types, including:

  • POE::Driver::Stream - A general-purpose driver that can be used with sockets, pipes, and ttys.
  • POE::Driver::TCP - A driver specifically for TCP sockets.
  • POE::Driver::UDP - A driver specifically for UDP sockets.

You can also create your own custom driver types by subclassing POE::Driver and implementing the necessary methods.

Filters

POE filters are used to process data as it passes through a session. They can be used for tasks such as protocol parsing, data serialization, and character encoding conversion.

POE provides a number of built-in filter types, including:

  • POE::Filter::Line - A filter that processes data line by line.
  • POE::Filter::IRCD - A filter for parsing IRC protocol messages.
  • POE::Filter::Reference - A filter that serializes and deserializes Perl data structures.

You can also create your own custom filter types by subclassing POE::Filter and implementing the necessary methods.

Components

POE components are higher-level abstractions that provide common functionality. They are typically implemented as a set of sessions and filters that work together to provide a specific service.

POE includes a number of built-in components, such as:

  • POE::Component::IRC - A component for interacting with IRC servers.
  • POE::Component::WWW::Mechanize - A component for web scraping.
  • POE::Component::Resolver - A component for DNS lookups.

You can also create your own custom component types by subclassing POE::Component and implementing the necessary methods.

POE::Component::Server::TCP and POE::Component::Server::HTTP are examples of how to create server components. The POE::Wheel interface, and other session types often do it differently.

Base Classes Document Common Features

The POE::Wheel, POE::Driver, POE::Filter, and POE::Component base classes describe what's common among each class. It's a good idea to at least skim the base class documentation since the subclasses tend not to rehash the common things.

POE::Queue, POE::Resource, and POE::Loop document the concepts and sometimes the standard interfaces behind multiple subclasses. You're encouraged to have a look.

Helper Classes

POE includes some helper classes for portability. POE::Pipe, and its subclasses POE::Pipe::OneWay and POE::Pipe::TwoWay are portable pipes.

Event Loop Bridges

POE::Loop documents and specifies the interface for all of POE's event loop bridges. The individual classes may document specific details, but generally they adhere to the spec strongly enough that they don't need to.

Many of the existing POE::Loop bridges provided in POE's base distribution will move out to separate distributions shortly. The documentation will probably remain the same, however.

POE::Queue and POE::Queue::Array

POE's event queue is basically a priority heap implemented as an ordered array. POE::Queue documents the standard interface for POE event queues, and POE::Queue::Array implements the ordered array queue. Tony Cook has released POE::XS::Queue::Array, which is a drop-in C replacement for POE::Queue::Array. You might give it a try if you need more performance. POE's event queue is some of the hottest code in the system.

SYSTEM REQUIREMENTS

POE's basic requirements are rather light. Most are included with modern versions of Perl, and the rest (if any) should be generally portable by now.

Time::HiRes is highly recommended, even for older Perls that don't include it. POE will work without it, but alarms and other features will be much more accurate if it's included. POE::Kernel will use Time::HiRes automatically if it's available.

POE::Filter::Reference needs a module to serialize data for transporting it across a network. It will use Storable, FreezeThaw, YAML, or some other package with freeze() and thaw() methods. It can also use Compress::Zlib to conserve bandwidth and reduce latency over slow links, but it's not required.

If you want to write web servers, you'll need to install libwww-perl, which requires libnet. This is a small world of modules that includes HTTP::Status, HTTP::Request, HTTP::Date, and HTTP::Response. They are generally good to have, and modern versions of Perl even include them.

Programs that use POE::Wheel::Curses will of course require the Curses module, which in turn requires some sort of curses library.

If you're using POE with Tk, you'll need Tk installed.

And other obvious things. Let us know if we've overlooked a non-obvious detail.

COMPATIBILITY ISSUES

One of POE's design goals is to be as portable as possible. That's why it's written in "Plain Perl". XS versions of POE modules are available as third-party distributions. Parts of POE that require nonstandard libraries are optional, and not having those libraries should not prevent POE from installing.

Despite Chris Williams' efforts, we can't test POE everywhere. Please see the GETTING HELP section if you run into a problem.

POE is expected to work on most forms of UNIX, including FreeBSD, MacOS X, Linux, Solaris. Maybe even AIX and QNX, but we're not sure.

POE is also tested on Windows XP, using the latest version of ActiveState, Strawberry and Cygwin Perl. POE is fully supported with Strawberry Perl, as it's included in the Strawberry distribution.

OS/2 and MacOS 9 have been reported to work in the past, but nobody seems to be testing there anymore. Reports and patches are still welcome.

Past versions of POE have been tested with Perl versions as far back as 5.6.2 and as recent as "blead", today's development build. We can no longer guarantee each release will work everywhere, but we will be happy to work with you if you need special support for a really old system. You can always use older POE releases that works on your version, please check BackPAN http://backpan.perl.org/authors/id/R/RC/RCAPUTO/.

POE's quality is due in large part to the fine work of Chris Williams and the other CPAN testers. They have dedicated resources towards ensuring CPAN distributions pass their own tests, and we watch their reports religiously. You can, too. The latest POE test reports can be found at http://cpantesters.org/distro/P/POE.html.

Thanks also go out to Benjamin Smith and the 2006 Google Summer of Code. Ben was awarded a grant to improve POE's test suite, which he did admirably.

Windows Issues

POE seems to work very nicely with Perl compiled for Cygwin. If you must use ActiveState Perl, please use the absolute latest version. ActiveState Perl's compatibility fluctuates from one build to another, so we tend not to support older releases.

Windows and ActiveState Perl are considered an esoteric platform due to the complex interactions between various versions. POE therefore relies on user feedback and support here.

A number of people have helped bring POE's Windows support this far, through contributions of time, patches, and other resources. Some of them are: Sean Puckett, Douglas Couch, Andrew Chen, Uhlarik Ondoej, Nick Williams, and Chris Williams (no relation).

POE's developers take pride in its quality. If you encounter a problem, please let us know.

POE's Request Tracker

You're welcome to e-mail questions and bug reports to <bug-POE@rt.cpan.org>. This is not a realtime support channel, though. If you need a more immediate response, try one of the methods below.

POE's Mailing List

POE has a dedicated mailing list where developers and users discuss the software and its use. You're welcome to join us. Send an e-mail to <poe-help@perl.org> for subscription instructions. The subject and message body are ignored.

Reporting Bugs

If you find a bug in POE, please report it to the POE Request Tracker. You can find it at http://rt.cpan.org/NoAuth/ReportBug.html?Queue=POE.

When reporting a bug, please include the following information:

  • The version of POE you are using.
  • The version of Perl you are using.
  • Your operating system and version.
  • A small, self-contained program that demonstrates the bug.
  • The output of the program, including any error messages.

The more information you can provide, the easier it will be for us to diagnose and fix the bug.
