NAME

POE::Roue::ReadWrite - module de lecture/écriture non bloquant pour POE::Session

SYNOPSIS

#!perl
use warnings;
use strict;
use IO::Socket::INET;
use POE qw(Wheel::ReadWrite);
POE::Session->create(
  inline_states => {
    _start => sub {
      # Note : IO::Socket::INET bloquera. POE::Wheel::SocketFactory ou POE::Component::Client::TCP sont recommandés si le blocage est indésirable.
      $_[HEAP]{client} = POE::Wheel::ReadWrite->new(
        Handle => IO::Socket::INET->new(
          PeerHost => 'www.yahoo.com',
          PeerPort => 80,
        ),
        InputEvent => 'on_remote_data',
        ErrorEvent => 'on_remote_error',
      );
      print "Connecté. Envoi de la requête...\n";
      $_[HEAP]{client}->put(
        "GET / HTTP/0.9",
        "Host: www.yahoo.com",
        "",
      );
    },
    on_remote_data => sub {
      print "Reçu : $_[ARG0]\n";
    },
    on_remote_error => sub {
      print "La connexion a échoué ou a été terminée. Fermeture...\n";
      delete $_[HEAP]{client};
    },
  },
);
POE::Kernel->run();
exit;

DESCRIPTION

POE::Roue::ReadWrite encapsule un modèle de conception commun : la gestion des E/S bufferisées et événementielles non bloquantes.

Le modèle se déroule comme suit :

Étant donné un descripteur de fichier, il observe les données entrantes. Lorsqu'il est notifié de données entrantes, il lit, bufferise et analyse selon un protocole de bas niveau (comme ligne par ligne). Il déclenche des événements de plus haut niveau « voici les lignes », un pour chaque ligne traitée.

Dans l'autre sens, il accepte des blocs de données entiers (comme des lignes) pour la sortie. Il les re-formate selon un protocole de bas niveau (comme l'ajout de retours à la ligne), et bufferise les données pour la sortie. Il vide le tampon lorsque le descripteur est prêt pour la transmission.

MÉTHODES PUBLIQUES

Constructeur

Les sous-classes de POE::Wheel effectuent généralement une grande quantité de configuration pour les rendre plus légères et plus rapides. Le constructeur de POE::Roue::ReadWrite ne fait pas exception.

new

new() crée et retourne un nouvel objet POE::Roue::ReadWrite. Dans la plupart des cas, la roue continuera à lire/écrire sur un ou plusieurs descripteurs jusqu'à ce qu'elle soit détruite.

Handle

Handle spécifie le descripteur de fichier que l'objet POE::Roue::ReadWrite lira et écrira. L'exemple SYNOPSIS inclut une utilisation de Handle.

Un objet POE::Roue::ReadWrite peut lire depuis et écrire sur différents descripteurs. Voir « InputHandle » pour plus d'informations et un exemple.

InputHandle

InputHandle et OutputHandle peuvent être utilisés pour spécifier différents descripteurs pour l'entrée et la sortie. Par exemple, l'entrée peut provenir de STDIN et la sortie peut aller à STDOUT :

$_[HEAP]{console} = POE::Wheel::ReadWrite->new(
  InputHandle => \*STDIN,
  OutputHandle => \*STDOUT,
  InputEvent => "console_input",
);

InputHandle et OutputHandle ne peuvent pas être utilisés avec Handle.

OutputHandle

InputHandle et OutputHandle peuvent être utilisés pour spécifier différents descripteurs pour l'entrée et la sortie. Voir « InputHandle » pour plus d'informations et un exemple.

Driver

Driver spécifie comment POE::Roue::ReadWrite lira et écrira sur son/ses descripteur(s). Driver doit être un objet qui hérite de POE::Driver.

POE::Driver::SysRW, qui implémente sysread() et syswrite(), est la valeur par défaut. Il est utilisé dans presque tous les cas, il n'est donc pas nécessaire de le spécifier.

Filter

Filter est l'analyseur que POE::Roue::ReadWrite utilisera pour reconnaître les données entrantes et le sérialiseur qu'il utilise pour préparer les données à écrire. Par défaut, il s'agit d'une nouvelle instance de POE::Filter::Line, car de nombreux protocoles réseau sont basés sur des lignes.

InputFilter

InputFilter et OutputFilter peuvent être utilisés pour spécifier différents filtres pour l'entrée et la sortie.

OutputFilter

InputFilter et OutputFilter peuvent être utilisés pour spécifier différents filtres pour l'entrée et la sortie. Voir « InputFilter » pour plus d'informations et un exemple.

InputEvent

InputEvent spécifie le nom de l'événement qui sera envoyé pour chaque unité d'entrée complète (telle qu'analysée par InputFilter ou Filter).

Chaque événement d'entrée inclut deux paramètres :

"ARG0" contient l'unité d'entrée analysée, et "ARG1" contient l'identifiant unique de l'objet POE::Roue::ReadWrite qui a généré l'événement.

InputEvent est facultatif. S'il est omis, l'objet POE::Roue::ReadWrite n'observera pas son Handle ou InputHandle pour l'entrée, et aucun événement d'entrée ne sera généré.

Un exemple de gestionnaire d'InputEvent :

sub handle_input {
  my ($heap, $input, $wheel_id) = @_[HEAP, ARG0, ARG1];
  print "Écho de l'entrée du wheel $wheel_id : $input\n";
  $heap->{wheel}->put($input); # Remettre... l'entrée... !
}

FlushedEvent

FlushedEvent spécifie l'événement qui sera déclenché par un objet POE::Roue::ReadWrite lorsque son tampon de sortie passe d'un état contenant des données à un état vide.

FlushedEvent est livré avec un seul paramètre : "ARG0" contient l'identifiant unique de l'objet POE::Roue::ReadWrite qui a généré l'événement. Ceci peut être utilisé pour associer l'événement à un wheel particulier.

Les événements "Flushed" sont courants pour fermer les E/S après qu'un message d'« au revoir » a été envoyé. Par exemple, le input_handler() suivant répond à "quit" en demandant au wheel de dire "Goodbye." puis de déclencher un événement "shutdown" lorsque cela a été envoyé à la connexion.

sub handle_input {
  my ($input, $wheel_id) = @_[ARG0, ARG1];
  my $wheel = $_[HEAP]{wheel}{$wheel_id};
  if ($input eq "quit") {
    $wheel->event( FlushedEvent => "shutdown" );
    $wheel->put("Goodbye.");
  }
  else {
    $wheel->put("Echo: $input");
  }
}

Voici le gestionnaire de fermeture. Il détruit simplement le wheel pour terminer la connexion :

sub handle_flushed {
  my $wheel_id = $_[ARG0];
  delete $_[HEAP]{wheel}{$wheel_id};
}

ErrorEvent

ErrorEvent nomme l'événement qu'un objet POE::Roue::ReadWrite déclenchera lorsqu'une erreur se produit. Chaque ErrorEvent inclut quatre paramètres :

"ARG0" décrit ce qui a échoué, soit "read" ou "write". Il ne nomme pas une fonction spécifique car POE::Roue::ReadWrite délègue la lecture et l'écriture à un objet POE::Driver.

"ARG1" et "ARG2" contiennent les valeurs numériques et textuelles de $! au moment de l'échec. Le code de l'application ne peut pas tester $! directement car sa valeur peut avoir changé entre le moment de l'échec et le moment où l'événement d'erreur est déclenché.

"ARG3" contient l'identifiant unique du wheel. L'identifiant du wheel est utilisé pour différencier plusieurs wheels gérés par une seule session.

ErrorEvent peut également indiquer une fin de fichier d'entrée en renvoyant l'opération "read" avec une erreur de 0. Pour les sockets, cela signifie que le côté distant a fermé la connexion.

Un exemple de gestionnaire d'ErrorEvent :

sub error_state {
  my ($operation, $errnum, $errstr, $id) = @_[ARG0..ARG3];
  if ($operation eq "read" and $errnum == 0) {
    print "EOF depuis le wheel $id\n";
  }
  else {
    warn "Le wheel $id a eu une erreur $operation $errnum : $errstr\n";
  }
  delete $_[HEAP]{wheels}{$id}; # ferme ce wheel
}

HighEvent

HighEvent et LowEvent sont utilisés conjointement avec HighMark et LowMark pour contrôler le débit de données sortantes en mode streaming.

Un HighEvent est déclenché lorsqu'un tampon de sortie d'un objet POE::Roue::ReadWrite dépasse une taille donnée (le "niveau maximum" ou HighMark). Cela signale à une application d'arrêter d'envoyer des données. POE et Perl ne se soucient pas vraiment si l'application continue, mais le processus risque de manquer de mémoire si le tampon grossit sans limite.

Un objet POE::Roue::ReadWrite continuera à remplir son tampon même après qu'une application ait cessé d'envoyer des données, jusqu'à ce que le tampon soit vide. Certaines applications de streaming pourraient nécessiter que le tampon soit toujours rempli de données. Par exemple, un serveur multimédia rencontrerait un problème.

put RECORDS

put() accepte une liste de RECORDS, qui seront sérialisés par le filtre de la roue et stockés et écrits par son driver.

put() retourne true si un HighMark a été défini et que le buffer de sortie du driver a atteint ou dépassé la limite. False est retourné si le HighMark n'a pas été défini, ou si le buffer du driver est inférieur à cette limite.

put() retourne sa valeur à titre indicatif ; une application peut continuer à stocker des données après le HighMark, mais cela peut entraîner le dépassement des limites de mémoire du processus. N'utilisez pas la syntaxe "<1 while not $wheel-"put()<<" si le HighMark n'a pas été défini : l'application échouera de manière spectaculaire !

event EVENT_TYPE => EVENT_NAME, ...

event() permet à une application de modifier les événements émis par un objet POE::Wheel::ReadWrite. Tous les paramètres du constructeur qui se terminent par "Event" peuvent être modifiés à l'exécution : "InputEvent", "FlushedEvent", "ErrorEvent", "HighEvent", et "LowEvent".

Définir un événement à undef désactive le code à l'intérieur de la roue qui génère l'événement. Par exemple, désactiver InputEvent arrêtera également la lecture à partir du filehandle. "pause_input" et "resume_input" peuvent être une méthode plus appropriée pour gérer les événements d'entrée, bien que moins explicite.

set_filter POE_FILTER

set_filter() modifie la façon dont un objet POE::Wheel::ReadWrite analyse l'entrée et sérialise la sortie. Toutes les données en attente qui n'ont pas encore été envoyées à l'application seront analysées avec le nouveau POE_FILTER. Les données qui ont été mises en put() mais pas encore en flush() ne seront pas resérialisées.

set_filter() effectue la même action que l'appel à set_input_filter() et set_output_filter() avec le même POE::Filter.

La modification des filtres peut être délicate. Veuillez consulter la discussion sur get_pending() dans POE::Filter. Certains filtres peuvent ne pas pouvoir être chargés ou désactivés dynamiquement.

set_input_filter POE_FILTER

set_input_filter() modifie le filtre d'entrée d'un objet POE::Wheel::ReadWrite tout en laissant le filtre de sortie inchangé. Cela modifie la façon dont les données d'entrée sont analysées sans affecter la façon dont elles sont sérialisées pour la sortie.

set_output_filter POE_FILTER

set_output_filter() modifie la façon dont la sortie d'un objet POE::Wheel::ReadWrite est sérialisée, mais n'affecte pas la façon dont les données sont analysées.

get_input_filter

get_input_filter() retourne l'objet POE::Filter actuellement utilisé par un objet POE::Wheel::ReadWrite pour analyser les données d'entrée. L'objet retourné peut être inspecté ou modifié via ses propres méthodes.

Il n'y a pas de méthode get_filter() car il n'y a pas de valeur de retour sensée lorsque les filtres d'entrée et de sortie sont différents.

get_output_filter

get_output_filter() retourne l'objet POE::Filter actuellement utilisé par un objet POE::Wheel::ReadWrite pour sérialiser les données de sortie. L'objet retourné peut être inspecté ou modifié via ses propres méthodes.

Il n'y a pas de méthode get_filter() car il n'y a pas de valeur de retour sensée lorsque les filtres d'entrée et de sortie sont différents.

set_high_mark HIGH_MARK_OCTETS

Définit le seuil haut --- le nombre d'octets qui désigne un "buffer suffisamment plein". Un objet POE::Wheel::ReadWrite émettra un HighEvent lorsque son buffer de sortie se développera pour atteindre ce point. Tous les appels à put() retourneront true lorsque le buffer de sortie sera égal ou supérieur à HIGH_MARK_OCTETS.

Les deux, HighEvent et put(), indiquent qu'il est dangereux de continuer à écrire lorsque le buffer de sortie atteint au moins HIGH_MARK_OCTETS.

set_low_mark LOW_MARK_OCTETS

Définit le seuil bas --- le nombre d'octets qui désigne un "buffer suffisamment vide". Cet événement permet à une application de savoir qu'il est sûr de recommencer à écrire.

Les objets POE::Wheel::ReadWrite émettront un LowEvent lorsque leur buffer de sortie se contractera à LOW_MARK_OCTETS après avoir atteint HIGH_MARK_OCTETS.

ID

ID() retourne l'identifiant unique d'un objet POE::Wheel::ReadWrite. ID() est généralement appelé après la création de l'objet, afin que l'objet puisse être stocké par son ID. Les événements générés par l'objet POE::Wheel::ReadWrite incluront l'ID de l'objet, permettant ainsi de les associer à leurs sources.

pause_input

pause_input() demande à un objet POE::Wheel::ReadWrite d'arrêter de surveiller les entrées et donc d'arrêter les événements InputEvent. C'est plus efficace que de détruire l'objet directement, surtout si l'application a l'intention d'utiliser resume_input() plus tard.

resume_input

resume_input() réactive la surveillance des entrées d'un objet POE::Wheel::ReadWrite. Elle est utilisée pour reprendre la surveillance des entrées et donc reprendre les événements InputEvent. pause_input() et resume_input() implémentent une sorte de contrôle de flux d'entrée, piloté par l'application elle-même.

get_input_handle

get_input_handle() retourne le filehandle surveillé pour les entrées.

La manipulation de filehandles gérés par POE peut causer des effets secondaires indésirables, qui peuvent varier d'une version de POE à l'autre. Veuillez faire preuve de prudence.

get_output_handle

get_output_handle() retourne le filehandle surveillé pour les sorties.

La manipulation de filehandles gérés par POE peut causer des effets secondaires indésirables, qui peuvent varier d'une version de POE à l'autre. Veuillez faire preuve de prudence.

shutdown_input

Appelle shutdown($fh,0) sur le filehandle d'entrée d'un objet POE::Wheel::ReadWrite. Cela ne fonctionne que pour les sockets ; rien ne sera fait pour les autres types de filehandles.

Parfois, l'objet POE::Wheel::ReadWrite cessera de surveiller son filehandle d'entrée pour de nouvelles données. Cela se produit quel que soit le type de filehandle.

shutdown_output

Appelle shutdown($fh,1) sur le filehandle de sortie d'un objet POE::Wheel::ReadWrite. Cela ne fonctionne que pour les sockets ; rien ne sera fait pour les autres types de filehandles.

Parfois, l'objet POE::Wheel::ReadWrite cessera de surveiller son filehandle de sortie pour de nouvelles données. Cela se produit quel que soit le type de filehandle.

get_driver_out_octets

Les objets POE::Driver contiennent des buffers de sortie qui sont vidés de manière asynchrone. get_driver_out_octets() retourne le nombre d'octets restants dans le buffer de sortie du driver de la roue.

get_driver_out_messages

Les buffers de sortie des objets POE::Driver peuvent être basés sur des messages. Chaque appel à put() peut être stocké individuellement. get_driver_out_messages() retournera le nombre de messages put() en attente qui n'ont pas encore été envoyés.

Les drivers basés sur des messages retourneront 1 s'il y a des données en attente d'envoi. C'est parce qu'ils fonctionnent avec un message potentiellement volumineux.

flush

flush() tente de vider manuellement le buffer de sortie d'une roue de manière synchrone. Ceci peut être utilisé pour vider de petits messages. Cependant, un vidage complet n'est pas garanti ; pour ce faire, on pourrait utiliser une boucle de flush() :

$wheel->flush() while $wheel->get_driver_out_octets();

Cependant, il serait prudent de vérifier également les erreurs. Un flush() échoué peut être permanent, et une boucle infinie serait probablement inappropriée.
