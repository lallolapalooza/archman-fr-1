POE::Component::Client::HTTP(3) Documentation Perl fournie par l'utilisateur POE::Component::Client::HTTP(3)

NOM

POE::Component::Client::HTTP - un composant client HTTP

VERSION

version 0.949

SYNOPSIS

use POE qw(Component::Client::HTTP);
POE::Component::Client::HTTP->spawn(
  Agent     => 'SpiffCrawler/0.90',   # par défaut, quelque chose de long
  Alias     => 'ua',                  # par défaut 'weeble'
  From      => 'spiffster@perl.org',  # par défaut undef (pas d'en-tête)
  Protocol  => 'HTTP/0.9',            # par défaut 'HTTP/1.1'
  Timeout   => 60,                    # par défaut 180 secondes
  MaxSize   => 16384,                 # par défaut réponse entière
  Streaming => 4096,                  # par défaut 0 (désactivé)
  FollowRedirects => 2,               # par défaut 0 (désactivé)
  Proxy     => "http://localhost:80", # par défaut variable d'environnement HTTP_PROXY
  NoProxy   => [ "localhost", "127.0.0.1" ], # par défaut variable d'environnement NO_PROXY
  BindAddr  => "12.34.56.78",         # par défaut INADDR_ANY
);
$kernel->post(
  'ua',        # envoie à l'alias 'ua'
  'request',   # envoie à l'état 'request' de ua
  'response',  # quel état recevra la réponse
  $request,    # un objet HTTP::Request
);
# Ceci est la sous-routine appelée lorsque la session reçoit un
# événement 'response'.
sub response_handler {
  my ($request_packet, $response_packet) = @_[ARG0, ARG1];
  # HTTP::Request
  my $request_object  = $request_packet->[0];
  # HTTP::Response
  my $response_object = $response_packet->[0];
  my $stream_chunk;
  if (! defined($response_object->content)) {
    $stream_chunk = $response_packet->[1];
  }
  print(
    "*" x 78, "\n",
    "*** ma requête:\n",
    "-" x 78, "\n",
    $request_object->as_string(),
    "*" x 78, "\n",
    "*** leur réponse:\n",
    "-" x 78, "\n",
    $response_object->as_string(),
  );
  if (defined $stream_chunk) {
    print "-" x 40, "\n", $stream_chunk, "\n";
  }
  print "*" x 78, "\n";
}

DESCRIPTION

POE::Component::Client::HTTP est un agent utilisateur HTTP pour POE. Il permet à d'autres sessions de s'exécuter pendant que les transactions HTTP sont traitées, et permet le traitement parallèle de plusieurs transactions HTTP.

Il prend en charge la persistance des connexions (keep-alive) via POE::Component::Client::Keepalive, qui utilise à son tour POE::Component::Resolver pour la résolution asynchrone des noms IPv4 et IPv6.

Les composants clients HTTP ne sont pas de vrais objets. Au lieu d'être créés, comme la plupart des objets, ils sont "lancés" comme des sessions distinctes. Pour éviter la confusion (et espérons-le, ne pas en causer d'autre), ils doivent être lancés avec une méthode "spawn", et non créés avec une méthode "new".

CONSTRUCTEUR

spawn

La méthode "spawn" de PoCo::Client::HTTP prend quelques paramètres nommés :

Agent => $chaine_agent_utilisateur
Agent => \@liste_des_agents
Si aucun en-tête UserAgent n'est présent dans la requête HTTP::Request, un en-tête aléatoire sera utilisé parmi ceux spécifiés par le paramètre "Agent". Si aucun n'est fourni, POE::Component::Client::HTTP s'auto-annoncera au serveur.

"Agent" peut contenir une référence à une liste d'agents utilisateurs. Si c'est le cas, PoCo::Client::HTTP en choisira un au hasard pour chaque requête.

Alias => $alias_de_session
"Alias" définit le nom par lequel la session sera connue. Si aucun alias n'est donné, le composant utilise par défaut "weeble". L'alias permet à plusieurs sessions d'interagir avec des composants HTTP sans conserver (ni même connaître) des références directes vers eux. Il est possible de lancer plusieurs composants HTTP avec des noms différents.
ConnectionManager => $poco_client_keepalive
"ConnectionManager" définit le gestionnaire de pool de connexions de ce composant. Il attend que le gestionnaire de connexion soit une référence à un objet POE::Component::Client::Keepalive. Le composant client HTTP appellera allocate() sur le gestionnaire de connexion lui-même, donc vous ne devriez pas l'avoir fait auparavant. 
my $pool = POE::Component::Client::Keepalive->new(
  keep_alive    => 10, # secondes pour maintenir les connexions ouvertes
  max_open      => 100, # connexions concurrentes max - total
  max_per_host  => 20, # connexions concurrentes max - par hôte
  timeout       => 30, # temps max (secondes) pour établir une nouvelle connexion
);
POE::Component::Client::HTTP->spawn(
  # ...
  ConnectionManager => $pool,
  # ...
);

Voir POE::Component::Client::Keepalive pour plus d'informations, y compris comment modifier la configuration du résolveur du gestionnaire de connexion (par exemple, pour forcer l'IPv6 ou le préférer avant l'IPv4).

CookieJar => $jar_de_cookies
"CookieJar" définit le gestionnaire de cookies du composant. Il attend que le gestionnaire de cookies soit une référence à un objet HTTP::Cookies.
From => $adresse_admin
"From" contient une adresse e-mail où l'administrateur et/ou le responsable du client peuvent être contactés. Il vaut par défaut undef, ce qui signifie qu'aucun en-tête From ne sera inclus dans les requêtes.
MaxSize => OCTETS
"MaxSize" spécifie la plus grande réponse à accepter d'un serveur. Le contenu des réponses plus volumineuses sera tronqué à OCTETS octets. Ceci a été utilisé pour retourner la section <head></head> des pages Web sans avoir besoin de parcourir <body></body>.
NoProxy => [ $hôte_1, $hôte_2, ..., $hôte_N ]
NoProxy => "hôte1,hôte2,hôteN"
"NoProxy" spécifie une liste d'hôtes serveurs qui ne seront pas proxifiés. C'est utile pour les hôtes locaux et les hôtes qui ne supportent pas correctement le proxy. Si NoProxy n'est pas spécifié, une liste sera extraite de la variable d'environnement NO_PROXY. 
NoProxy => [ "localhost", "127.0.0.1" ],
NoProxy => "localhost,127.0.0.1",
BindAddr => $ip_locale
Spécifiez "BindAddr" pour lier toutes les sockets client à une adresse locale particulière. La valeur de BindAddr sera passée via POE::Component::Client::Keepalive à POE::Wheel::SocketFactory (en tant que "bind_address"). Voir la documentation de ce module pour les détails d'implémentation. 
BindAddr => "12.34.56.78"
Protocol => $chaine_protocole_http
"Protocol" annonce le protocole que le client souhaite utiliser. Dans des circonstances normales, il doit être laissé à sa valeur par défaut : "HTTP/1.1".
Proxy => [ $hôte_proxy, $port_proxy ]
Proxy => $url_proxy
Proxy => $url_proxy,$url_proxy,...
"Proxy" spécifie un ou plusieurs hôtes proxy par lesquels les requêtes seront passées. Si non spécifié, les serveurs proxy seront pris à partir de la variable d'environnement HTTP_PROXY (ou http_proxy). Aucun proxy ne sera utilisé à moins que Proxy ne soit défini ou que l'une des variables d'environnement n'existe.

Le proxy peut être spécifié soit comme hôte et port, soit comme une ou plusieurs URL. Les URL de proxy doivent spécifier le port du proxy, même s'il s'agit de 80.

Proxy => [ "127.0.0.1", 80 ],
Proxy => "http://127.0.0.1:80/",

"Proxy" peut spécifier plusieurs proxys séparés par des virgules. PoCo::Client::HTTP choisira les proxys dans cette lis

Streaming => OCTETS
"Streaming" est utilisé pour la remise des réponses volumineuses. Lorsque "Streaming" est défini, les réponses du serveur sont envoyées par morceaux de la taille spécifiée (en octets). La réponse entière n'est pas mise en mémoire tampon avant d'être livrée. Ce paramètre est utile pour les réponses qui peuvent être traitées au fur et à mesure de leur réception. Lorsque le contenu n'est pas disponible (c'est-à-dire lorsque le streaming est activé), le second élément du paquet de réponse contiendra le fragment de données.
Timeout => SECONDS
"Timeout" est le nombre de secondes d'attente pour les réponses du serveur. Si le temps imparti est dépassé, un événement "timeout" sera envoyé à la session du client.

TRAITEMENT DES ÉVÉNEMENTS

Lorsque vous publiez une requête sur un composant client HTTP, vous devez créer un état pour gérer les événements que le composant vous renvoie. Les événements que vous pourriez recevoir sont:

response
Cet événement est envoyé au gestionnaire d'état spécifié dans votre appel à post(). Il est envoyé une fois que le composant client HTTP a reçu une réponse complète du serveur. Deux objets sont passés à cet état : le premier est une référence à l'objet HTTP::Request original et le second est une référence à l'objet HTTP::Response reçu.
error
Cet événement est envoyé si une erreur se produit. Il est envoyé au gestionnaire d'état par défaut de votre session. Deux arguments sont passés à cet état : un message d'erreur et une référence à l'objet HTTP::Request original. Le composant client HTTP tentera d'envoyer l'événement "error" à votre gestionnaire de réponse par défaut.
timeout
Cet événement est envoyé lorsque le délai d'attente spécifié dans le paramètre "Timeout" est dépassé. Il est envoyé à la session du client. Il y a deux arguments passés : un message d'erreur et une référence à l'objet HTTP::Request original.
streaming_chunk
Cet événement est envoyé lorsque le paramètre "Streaming" est défini et qu'un morceau de la réponse est prêt. Il est envoyé à votre gestionnaire de réponse par défaut. Deux arguments sont passés : une référence à l'objet HTTP::Request original et une chaîne de données du morceau de réponse.

REQUÊTES ET RÉPONSES

Les requêtes sont passées au composant client HTTP sous forme d'objets HTTP::Request. Les réponses sont renvoyées sous forme d'objets HTTP::Response.

La requête la plus simple est une requête GET. Elle est créée comme suit:

    use HTTP::Request;
    my $request = HTTP::Request->new( GET => 'http://example.com/' );

Les requêtes POST, PUT, DELETE, etc. sont créées de manière similaire. Voir la documentation de HTTP::Request pour plus d'informations.

Le composant client HTTP enverra ses réponses sous forme de paquets contenant les objets requête et réponse. Ces paquets sont envoyés aux états de la session qui s'est abonnée à l'alias du composant client HTTP.

    # dans le noyau POE
    $kernel->post( $ua_alias, 'request', $response_state, $request_object );
    # dans l'état de la session
    sub request_handler {
        my ($args)=@_;
        my ($req, $resp)=@$args;
        # faire quelque chose avec $req et $resp
    }

Si le paramètre "Streaming" est défini, la réponse sera envoyée en plusieurs morceaux. Le premier paquet de réponse contiendra l'objet requête et l'objet réponse, mais le champ "content" de l'objet réponse sera vide. Les morceaux de données suivants seront envoyés en tant qu'arguments supplémentaires au paquet de réponse.

    # dans le noyau POE
    $kernel->post( $ua_alias, 'request', $response_state, $request_object );
    # dans l'état de la session
    sub request_handler {
        my ($args)=@_;
        my ($req, $resp)=@$args;
        my ($chunk_data) = @_; # L'argument suivant sera le morceau de données
        # faire quelque chose avec $req et $resp
        if ( defined $chunk_data ) {
            # faire quelque chose avec $chunk_data
        }
    }

COOKIES

Si vous souhaitez que le composant client HTTP gère les cookies, vous pouvez fournir un objet HTTP::Cookies lors de l'appel à "spawn".

use HTTP::Cookies;
my $cookie_jar = HTTP::Cookies->new(
    file     => '/path/to/cookies.txt',
    autosave => 1,
);
POE::Component::Client::HTTP->spawn(
    # ...
    CookieJar => $cookie_jar,
    # ...
);

Le composant client HTTP utilisera le cookie jar fourni pour stocker et renvoyer automatiquement les cookies appropriés avec les requêtes.

Streaming => OCTETS
"Streaming" modifie la manière dont Client::HTTP retourne le contenu volumineux en morceaux (de OCTETS octets chacun) au lieu de combiner tout le contenu en un seul objet HTTP::Response.

Par défaut, Client::HTTP lit tout le contenu d'une réponse en mémoire avant de retourner un objet HTTP::Response. Ceci est évidemment problématique pour des applications comme les clients de streaming MP3, car ils récupèrent souvent des chansons qui ne finissent jamais. Oui, elles continuent, mon ami.

Lorsque "Streaming" est défini à une valeur non nulle, le gestionnaire de réponse reçoit des morceaux allant jusqu'à OCTETS octets chacun. Le gestionnaire de réponse accepte des paramètres légèrement différents dans ce cas. ARG0 est également un objet HTTP::Response mais il ne contient pas le contenu de la réponse, et ARG1 contient un morceau de contenu brut de la réponse, ou undef si le flux est terminé.

sub streaming_response_handler {
  my $response_packet = $_[ARG1];
  my ($response, $data) = @$response_packet;
  print SAVED_STREAM $data if defined $data;
}
FollowRedirects => $nombre_de_sauts_à_suivre
"FollowRedirects" spécifie combien de redirections (par exemple, 302 déplacé) suivre. Si non spécifié, la valeur par défaut est 0, et donc aucune redirection n'est suivie. Ceci maintient la compatibilité avec le comportement précédent, qui était de ne pas suivre les redirections du tout.

Si les redirections sont suivies, une chaîne de réponses doit être construite et peut être accessible via $response_object->previous(). Voir HTTP::Response pour plus de détails.

Timeout => $timeout_de_requête
"Timeout" définit combien de temps POE::Component::Client::HTTP a pour traiter la requête d'une application, en secondes. "Timeout" a une valeur par défaut de 180 (trois minutes) si non spécifié.

Il est important de noter que le délai commence lorsque le composant reçoit une requête de l'application, et non lorsqu'il tente de se connecter au serveur web.

Les dépassements de délai peuvent résulter de l'envoi trop de requêtes simultanément au composant. Chaque requête devrait être reçue et suivie. Considérez ceci :

$_[KERNEL]->post(component => request => ...) for (1..15_000);

15 000 requêtes sont mises en file d'attente en un seul gros bloc. Le composant les recevrait et les initialiserait dans l'ordre. La première activité de socket n'arriverait que lorsque la 15 000ème requête serait configurée. Si cela prenait plus de temps que "Timeout", alors les requêtes qui ont attendu trop longtemps échoueraient.

"ConnectionManager"'s own délai d'attente et limites de concurrence affectent également le nombre de requêtes qui peuvent être traitées simultanément. Par exemple, la plupart des 15 000 requêtes attendraient dans le pool du gestionnaire de connexions jusqu'à ce que des sockets deviennent disponibles. Pendant ce temps, le "Timeout" continuerait à décompter.

Les applications peuvent choisir de contrôler la concurrence en dehors du "Timeout" du composant. Elles peuvent le faire de plusieurs manières.

La manière la plus simple est de limiter le nombre initial de requêtes à quelque chose de plus gérable. Au fur et à mesure que les réponses arrivent, l'application doit les traiter et démarrer de nouvelles requêtes. Ceci limite la concurrence au nombre initial de requêtes.

Une application peut également externaliser le limitation des tâches vers un autre module, tel que POE::Component::JobQueue.

Dans tous les cas, "Timeout" et "ConnectionManager" peuvent être ajustés pour maximiser les délais d'attente et les limites de concurrence. Ceci peut aider dans certains cas. Les développeurs doivent être conscients que cela augmentera l'utilisation de la mémoire. POE::Component::Client::HTTP et KeepAlive suivent les requêtes en mémoire, tandis que les applications peuvent garder les requêtes en attente sur disque.

ÉVÉNEMENTS ACCEPTÉS

Les sessions communiquent de manière asynchrone avec PoCo::Client::HTTP. Elles lui envoient des requêtes, et il renvoie des réponses.

requête

Les requêtes sont envoyées à l'état « request » du composant. Elles incluent un objet HTTP::Request qui définit la requête. Par exemple :

$kernel->post(
  'ua', 'request',            # alias de session http & état
  'response',                 # mon état pour recevoir les réponses
  GET('http://poe.perl.org'), # une requête http simple
  'id unique',                # une étiquette pour identifier la requête
  'progress',                 # un événement pour indiquer la progression
  'http://1.2.3.4:80/'        # proxy à utiliser pour cette requête
);

Les requêtes incluent l'état auquel les réponses seront envoyées. Dans l'exemple précédent, le gestionnaire pour un état « response » sera appelé pour chaque réponse HTTP. Le gestionnaire « progress » est facultatif et s'il est installé, le composant fournira des métriques de progression (voir l'exemple de gestionnaire ci-dessous). Le paramètre « proxy » est facultatif et s'il n'est pas défini, un proxy par défaut sera utilisé s'il est configuré. Aucun proxy ne sera utilisé si ni un proxy par défaut ni un paramètre « proxy » n'est défini.

nombre_requêtes_en_attente

Il existe également un état pending_requests_count qui retourne le nombre de requêtes en cours de traitement. Pour recevoir la valeur de retour, il doit être appelé avec $kernel->call().

my $count = $kernel->call('ua' => 'pending_requests_count');

NOTE : Parfois, le compte peut ne pas être celui attendu, car les réponses sont actuellement dans la file d'attente de POE et vous ne les avez pas encore traitées. Cela pourrait se produire si vous configurez la concurrence du "ConnectionManager" à une valeur suffisamment élevée.

annuler

Annuler une requête HTTP spécifique. Nécessite une référence à la requête originale (blessée ou linéarisée) afin de savoir laquelle annuler. Voir le « gestionnaire de progression » ci-dessous pour des notes sur l'annulation des requêtes en streaming.

Pour annuler une requête basée sur son objet HTTP::Request blessé :

$kernel->post( component => cancel => $http_request );

Pour annuler une requête basée sur son objet HTTP::Request linéarisé :

$kernel->post( component => cancel => "$http_request" );

arrêter

Répond à toutes les requêtes en attente avec 408 (délai d'attente de la requête), puis arrête le composant et tous ses sous-composants.

ÉVÉNEMENTS ENVOYÉS

gestionnaire_réponse

En plus de tous les paramètres POE habituels, les réponses HTTP sont fournies avec deux références de liste :

my ($request_packet, $response_packet) = @_[ARG0, ARG1];

$request_packet contient une référence à l'objet HTTP::Request original. Ceci est utile pour faire correspondre les réponses aux requêtes qui les ont générées.

my $http_request_object = $request_packet->[0];
my $http_request_tag    = $request_packet->[1]; # depuis le post 'request'

$response_packet contient une référence à l'objet HTTP::Response résultant.

my $http_response_object = $response_packet->[0];

Veuillez consulter les pages de manuel de HTTP::Request et HTTP::Response pour plus d'informations.

gestionnaire_progression

L'exemple de gestionnaire de progression montre comment calculer un pourcentage d'achèvement du téléchargement.

sub progress_handler {
  my $gen_args  = $_[ARG0];    # arguments passés à tous les appels
  my $call_args = $_[ARG1];    # arguments spécifiques à l'appel
  my $req = $gen_args->[0];    # objet HTTP::Request en cours de traitement
  my $tag = $gen_args->[1];    # étiquette d'identification de la requête.
  my $got = $call_args->[0];   # nombre d'octets récupérés jusqu'à présent.
  my $tot = $call_args->[1];   # nombre total d'octets à récupérer.
  my $oct = $call_args->[2];   # morceau d'octets bruts reçus cette fois-ci.
  my $percent = $got / $tot * 100;
  printf(
    "-- %.0f%% [%d/%d]: %s\n", $percent, $got, $tot, $req->uri()
  );
  # Pour annuler la requête:
  # $_[KERNEL]->post( component => cancel => $req );
}

AVERTISSEMENT DE DÉPRÉCIATION

Le troisième argument de retour (les octets bruts reçus) a été déprécié. Au lieu de cela, utilisez le paramètre Streaming pour obtenir des morceaux de contenu dans le gestionnaire de réponse.

CALLBACKS DE REQUÊTE

L'objet HTTP::Request passé à l'événement request peut contenir une référence de code sous forme de "content". Ceci permet d'envoyer de gros fichiers sans gaspiller de mémoire. Votre callback doit retourner un morceau de données chaque fois qu'il est appelé, et une chaîne vide une fois terminé. N'oubliez pas de définir correctement l'en-tête Content-Length. Exemple :

my $request = HTTP::Request->new( PUT => 'http://...' );
my $file = '/chemin/vers/gros_fichier';
open my $fh, '<', $file;
my $upload_cb = sub {
  if ( sysread $fh, my $buf, 4096 ) {
    return $buf;
  }
  else {
    close $fh;
    return '';
  }
};
$request->content_length( -s $file );
$request->content( $upload_cb );
$kernel->post( ua => request, 'response', $request );

ENCODAGE ET COMPRESSION DU CONTENU

Le décodage transparent du contenu a été désactivé depuis la version 0.84. Ceci supprime également le support de la requête gzip transparente et de la décompression.

Pour réactiver la compression gzip, spécifiez l'encodage de contenu gzip et utilisez la méthode decoded_content() de HTTP::Response plutôt que content() :

my $request = HTTP::Request->new(
  GET => "http://www.yahoo.com/", [
    'Accept-Encoding' => 'gzip'
  ]
);
# ... le temps passe ...
my $content = $response->decoded_content();
