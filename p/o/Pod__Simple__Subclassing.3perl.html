NOM

Pod::Simple::Subclassing -- écrire un formateur en tant que sous-classe de Pod::Simple

SYNTAXE

package Pod::SomeFormatter;
use Pod::Simple;
@ISA = qw(Pod::Simple);
$VERSION = '1.01';
use strict;
sub _handle_element_start {
  my($parser, $element_name, $attr_hash_r) = @_;
  ...
}
sub _handle_element_end {
  my($parser, $element_name, $attr_hash_r) = @_;
  # NOTE: $attr_hash_r est seulement présent lorsque $element_name est "over" ou "begin"
  # Les extraits de code restants ignoreront principalement ce $attr_hash_r, car il est
  # largement inutile. Il est documenté là où les événements "over-*" et "begin" sont
  # documentés.
  ...
}
sub _handle_text {
  my($parser, $text) = @_;
  ...
}
1;

DESCRIPTION

Ce document concerne l'utilisation de Pod::Simple pour écrire un processeur de Pod, généralement un formateur de Pod. Si vous souhaitez simplement savoir comment utiliser un formateur de Pod existant, consultez plutôt sa documentation et également la documentation de Pod::Simple.

La étape zéro dans l'écriture d'un formateur de Pod est de s'assurer qu'il n'en existe pas déjà un décent sur CPAN. Voir http://search.cpan.org/ et effectuez une recherche sur le nom du format que vous souhaitez rendre. Pensez également à rejoindre la liste Pod People http://lists.perl.org/showlist.cgi?name=pod-people et demandez si quelqu'un a un formateur pour ce format - peut-être que quelqu'un en a bricolé un mais ne l'a pas encore publié.

La première étape dans l'écriture d'un processeur de Pod est de lire perlpodspec, qui contient des informations sur l'écriture d'un analyseur de Pod (qui a été largement pris en charge par Pod::Simple), mais aussi de nombreuses exigences et recommandations pour l'écriture d'un formateur.

La deuxième étape consiste à réellement apprendre le format dans lequel vous prévoyez de formater - ou du moins autant que vous avez besoin de savoir pour représenter le Pod, ce qui n'est probablement pas beaucoup.

La troisième étape consiste à choisir quelle interface de Pod::Simple vous souhaitez utiliser :

Pod::Simple
L'interface de base de Pod::Simple qui utilise _handle_element_start(), _handle_element_end() et _handle_text().
Pod::Simple::Methody
L'interface Pod::Simple::Methody est basée sur les événements, similaire à celle de HTML::Parser ou des "Handlers" de XML::Parser.
Pod::Simple::PullParser
Pod::Simple::PullParser fournit une interface de flux de jetons, un peu comme l'interface de HTML::TokeParser.
Pod::Simple::SimpleTree
Pod::Simple::SimpleTree fournit une interface d'arbre simple, plutôt comme l'interface "Tree" de XML::Parser. Les utilisateurs familiers avec la manipulation XML se sentiront à l'aise avec cette interface. Les utilisateurs intéressés par la sortie d'XML, devraient examiner les modules qui produisent une représentation XML du flux de Pod, notamment Pod::Simple::XMLOutStream ; vous pouvez alimenter la sortie d'une telle classe avec le système d'analyse XML avec lequel vous êtes le plus à l'aise.

La dernière étape consiste à écrire votre code en fonction de la façon dont les événements (ou les jetons, ou les nœuds d'arbre, ou le XML, ou quelle que soit la méthode d'analyse) seront mappés aux constructions du format de sortie. Assurez-vous également de considérer comment échapper les nœuds de texte contenant du texte arbitraire, et quoi faire avec les nœuds de texte qui représentent du texte préformaté (provenant de sections verbatim).

Dans la section suivante, nous utilisons XML pour représenter la structure d'événements associée à une construction particulière. C'est-à-dire qu'une balise ouvrante représente le début de l'élément, les attributs de cette balise ouvrante sont les attributs donnés au callback, et la balise fermante représente la fin de l'élément.

Trois méthodes de callback doivent être fournies par une classe étendant Pod::Simple pour recevoir l'événement correspondant :

"$parser->_handle_element_start( nom_element, hash_ref_attributs )"
"$parser->_handle_element_end( nom_element )"
"$parser->_handle_text( chaîne_texte )"

Voici la liste complète des valeurs que vous pouvez attendre en tant que nom_element dans votre implémentation de "_handle_element_start" et "_handle_element_end" ::

événements avec un nom_element de Document
L'analyse d'un document produit cette structure d'événements : 
<Document start_line="543">
  ...tous les événements...
</Document>

La valeur de l'attribut start_line sera le numéro de ligne de la première directive Pod dans le document.

S'il n'y a pas de Pod dans le document donné, la structure d'événements sera la suivante :

<Document contentless="1" start_line="543">
</Document>

Dans ce cas, la valeur de l'attribut start_line ne sera pas significative ; dans les implémentations actuelles, elle correspondra probablement au numéro de la dernière ligne du fichier.

événements avec un nom_element de Para
L'analyse d'un paragraphe simple (non-verbatim, non-directive, non-data) dans un document Pod produit cette structure d'événements : 
<Para start_line="543">
  ...tous les événements de ce paragraphe...
</Para>

La valeur de l'attribut start_line sera le numéro de ligne du début du paragraphe.

Par exemple, l'analyse de ce paragraphe Pod :

The value of the I<start_line> attribute will be the
line number of the start of the paragraph.

produit cette structure d'événements :

<Para start_line="129">
  The value of the
  <I>
    start_line
  </I>
  attribute will be the line number of the first Pod directive
  in the document.
</Para>
événements avec un nom_element de B, C, F, ou I.
L'analyse d'un code de formatage B<...> (ou bien sûr de l'une de ses variantes syntaxiques sémantiquement identiques B<< ... >>, ou B<<<< ... >>>>, etc.) produit cette structure d'événements : 
<B>
  ...contenu...
</B>

Actuellement, aucun attribut n'est transmis.

L'analyse des codes C, F ou I produit la même structure, avec simplement un nom d'élément différent.

Si votre objet analyseur a été configuré pour accepter d'autres codes de formatage, ils seront présentés comme ces codes B/C/F/I - c'est-à-dire sans attributs.

événements avec un nom_element de S
Normalement, l'analyse d'une séquence S<...> produit cette structure d'événements, comme s'il s'agissait d'un code B/C/F/I : 
<S>
  ...contenu...
</S>

Cependant, Pod::Simple (et présumablement tous les analyseurs dérivés) offre l'option "nbsp_for_S" qui, si elle est activée, supprimera tous les événements S et remplacera tous les espaces dans le contenu par des espaces insécables. Ceci est destiné aux formateurs qui sortent vers un format qui n'a pas de code signifiant la même chose que S<...>, mais qui a un code/caractère signifiant un espace insécable.

événements avec un nom_element de X
Normalement, l'analyse d'une séquence X<...> produit cette structure d'événements, comme s'il s'agissait d'un code B/C/F/I : 
<X>
  ...contenu...
</X>

Cependant, Pod::Simple (et présumablement tous les analyseurs dérivés) offre l'option "nix_X_codes" qui, si elle est activée, supprimera tous les événements X et ignorera leur contenu. Pour les formateurs/processeurs qui n'utilisent pas les événements X, cela est présumablement très utile.

événements avec un nom_element de L
Étant donné que L<...> est la construction la plus complexe du langage, il ne devrait pas vous surprendre que les événements qu'elle génère soient les plus compl
ex dans la langue. La plupart de la complexité est cachée dans les valeurs des attributs, donc pour ceux qui écrivent un formatteur de Pod qui produit un format non hypertextuel, ils peuvent ignorer les attributs et traiter une structure d'événement L comme un élément de format qui (vraisemblablement) ne produit pas de changement de format. C'est-à-dire, le contenu de la structure d'événement L (contrairement à ses attributs) sera toujours ce qui doit être affiché comme du texte.

Il existe, au départ, trois types de liens L : URL, man et pod.

Lors de l'analyse d'un code L<some_url>, cette structure d'événement est produite :

<L content-implicit="yes" raw="that_url" to="that_url" type="url">
  that_url
</L>

L'attribut "type="url"" est toujours spécifié pour ce type de code L.

Par exemple, ce code Pod :

L<http://www.perl.com/CPAN/authors/>

produit cette structure d'événement :

<L content-implicit="yes" raw="http://www.perl.com/CPAN/authors/" to="http://www.perl.com/CPAN/authors/" type="url">
  http://www.perl.com/CPAN/authors/
</L>

Lors de l'analyse d'un code L<manpage(section)> (et ceux-ci sont assez rares et pas très utiles), cette structure d'événement est produite :

<L content-implicit="yes" raw="manpage(section)" to="manpage(section)" type="man">
  manpage(section)
</L>

L'attribut "type="man"" est toujours spécifié pour ce type de code L.

Par exemple, ce code Pod :

L<crontab(5)>

produit cette structure d'événement :

<L content-implicit="yes" raw="crontab(5)" to="crontab(5)" type="man">
  crontab(5)
</L>

Dans les cas raisonnables où une liaison de page de manuel a une section spécifiée, le texte apparaît dans l'attribut section. Par exemple, ce code Pod :

L<crontab(5)/"ENVIRONMENT">

génère cette structure d'événement :

<L content-implicit="yes" raw="crontab(5)/&quot;ENVIRONMENT&quot;" section="ENVIRONMENT" to="crontab(5)" type="man">
  "ENVIRONMENT" dans crontab(5)
</L>

Dans les cas raisonnables où le document Pod a du code comme L<sometext|manpage(section)>, le texte sometext apparaîtra comme contenu de l'élément, tandis que le texte manpage(section) apparaîtra uniquement comme valeur de l'attribut to, et il n'y aura pas d'attribut "content-implicit="yes"" (sa présence indique que l'analyseur Pod a dû inférer quel texte devait apparaître comme texte du lien, par opposition aux cas où cet attribut n'est pas présent, indiquant que l'analyseur Pod n'a pas eu à inférer le texte du lien, car le code L a explicitement spécifié un texte de lien).

Par exemple, ce code Pod :

L<enfer lui-même !|crontab(5)>

génère cette structure d'événement :

<L raw="hell itself!|crontab(5)" to="crontab(5)" type="man">
  hell itself!
</L>

Le dernier type de structure d'événement L concerne les liens vers/dans les documents Pod. C'est le plus complexe, car il peut avoir un attribut to, ou un attribut section, ou les deux. L'attribut "type="pod"" est toujours spécifié pour ce type de code L.

Dans le cas le plus courant, la structure d'événement simple de L<podpage> génère cette structure d'événement :

<L content-implicit="yes" raw="podpage" to="podpage" type="pod">
  podpage
</L>

Par exemple, ce code Pod :

L<Net::Ping>

génère cette structure d'événement :

<L content-implicit="yes" raw="Net::Ping" to="Net::Ping" type="pod">
  Net::Ping
</L>

Dans les cas où le texte du lien est spécifié explicitement, il se trouvera dans le contenu de l'élément (et non dans les attributs), comme dans le cas de L<sometext|manpage(section)> discuté précédemment. Par exemple, ce code Pod :

L<Messages d'erreur Perl|perldiag>

génère cette structure d'événement :

<L raw="Perl Error Messages|perldiag" to="perldiag" type="pod">
  Perl Error Messages
</L>

Dans les cas de liens vers une section du document actuel, il y a un attribut section au lieu d'un attribut to. Par exemple, ce code Pod :

L</"Member Data">

génère cette structure d'événement :

<L content-implicit="yes" raw="/\"Member Data\"" section="Member Data" type="pod">
  "Member Data"
</L>

Autre exemple, ce code Pod :

L<les divers attributs|/"Member Data">

génère cette structure d'événement :

<L raw="the various attributes|/\"Member Data\"" section="Member Data" type="pod">
  the various attributes
</L>

Dans les cas de liens vers une section d'un autre document Pod, il y a à la fois les attributs section et to. Par exemple, ce code Pod :

L<perlsyn/"Basic BLOCKs and Switch Statements">

génère cette structure d'événement :

<L content-implicit="yes" raw="perlsyn/\"Basic BLOCKs and Switch Statements\"" section="Basic BLOCKs and Switch Statements" to="perlsyn" type="pod">
  "Basic BLOCKs and Switch Statements" dans perlsyn
</L>

Autre exemple, ce code Pod :

L<instructions SWITCH|perlsyn/"Basic BLOCKs and Switch Statements">

génère cette structure d'événement :

<L raw="SWITCH statements|perlsyn/\"Basic BLOCKs and Switch Statements\"" section="Basic BLOCKs and Switch Statements" to="perlsyn" type="pod">
  SWITCH statements
</L>

Bien qu'en fait, vous remarquerez que nous ne faisons pas de distinction entre ces syntaxes :

L</"Member Data">
L<"Member Data">
L</Member Data>
L<Member Data>    [syntaxe obsolète]

C'est-à-dire que toutes produisent la même structure d'événement (en général), à savoir :

<L content-implicit="yes" raw="$depends_on_syntax" section="Member Data" type="pod">
  &#34;Member Data&#34;
</L>

L'attribut raw dépend du contenu d'origine de la balise "L<>", donc la structure d'événement est généralement la même.

Si vous ne l'avez pas encore déduit, l'attribut raw contient le contenu d'origine non échappé de la balise de format "L<>". En plus des exemples ci-dessus, prêtez attention à la structure d'événement suivante générée par le code de format "L<>" suivant :

L<cliquez ICI B<ici>|page/À propos du commutateur C<-M>>
<L raw="click B<here>|page/About the C<-M> switch" section="About the -M switch" to="page" type="pod">
  click B<here>
</L>

Il est également important de noter que les codes de format des événements sont présents et non échappés dans l'attribut raw.

Il existe un bug connu dans l'attribut raw où tout espace blanc autour est condensé en un seul espace. Par exemple, étant donné L< lien>, l'attribut raw sera " lien".

événements avec un element_name de E ou Z
Bien qu'il existe des codes Pod E<...> et Z<>, ceux-ci *ne* produisent *pas* d'événements E ou Z -- c'est-à-dire qu'il n'existe pas de tels événements E ou Z.
événements avec un element_name de Verbatim
Lorsqu'un paragraphe verbatim Pod (alias "bloc de code") est analysé, il produit cette structure d'événement : 
<Verbatim start_line="543" xml:space="preserve">
  ...texte...
</Verbatim>

La valeur de l'attribut start_line sera le numéro de ligne de la première ligne de ce bloc verbatim. L'attribut xml:space est toujours présent, et a toujours la valeur "preserve".

Le contenu textuel aura les tabulations déjà développées.

événements avec un element_name de head1 .. head4
Lorsqu'une directive "=head1 ..." est analysée, elle produit cette structure d'événement : 
<head1>
  ...contenu...
</head1>

Par exemple, une directive composée de ceci :

=head1 Options pour C<new> et al.

produira cette structure d'événement :

<head1 start_line="543">
  Options pour
  <C>
    new
  </C>
  et al.
</head1>

Les directives "=head2" à "=head4" sont identiques, à l'exception des noms d'éléments dans la structure d'événement.

événements avec un element_name de encoding
Dans le cas par défaut, les événements correspondant aux directives "=encoding" ne sont pas émis. Ils sont émis si "keep_encoding_directive" est vrai. Dans ce cas, ils produisent des structures d'événement telles que "événements avec un element_name de head1 .. head4" ci-dessus.
événements avec un element_name de over-bullet
Lorsqu'un bloc "=over ... =back" est analysé où les éléments sont une liste à puces, il produira cette structure d'événement : 
<over-bullet indent="4" start_line="543">
  <item-bullet start_line="545">
    ...Contenu...
  </item-bullet>
  ...plus d'item-bullets...
</over-bullet fake-closer="1">

L'attribut fake-closer est présent uniquement s'il a une valeur vraie ; il n'est pas présent s'il a une valeur fausse. Il est montré dans l'exemple ci-dessus pour illustrer où se trouve l'attribut (dans le)

balise de fermeture). Il signifie que "=over" n'avait pas de correspondance "=back", et que Pod::Simple a donc dû créer un faux fermeur.

Par exemple, cette source Pod :

=over
=item *
Something
=back

Produirait une structure d'événement qui n'a **pas** l'attribut fake-closer, alors que cette source Pod :

=over
=item *
Gasp! An unclosed =over block!

le ferait. Le reste des exemples over-* ne démontreront pas cet attribut, mais ils peuvent tous l'avoir. Voir la source de Pod::Checker pour un exemple d'utilisation de cet attribut.

La valeur de l'attribut indent est la valeur qui suit la directive "=over", comme dans "=over 8". Si aucune valeur de ce type n'est spécifiée dans la directive, alors l'attribut indent a la valeur "4".

Par exemple, cette source Pod :

=over
=item *
Stuff
=item *
Bar I<baz>!
=back

Produit cette structure d'événement :

<over-bullet indent="4" start_line="10">
  <item-bullet start_line="12">
    Stuff
  </item-bullet>
  <item-bullet start_line="14">
    Bar <I>baz</I>!
  </item-bullet>
</over-bullet>
événements avec un nom_élément égal à over-number
Lorsqu'un bloc "=over ... =back" est analysé où les éléments sont une liste numérotée, il produira cette structure d'événement : 
<over-number indent="4" start_line="543">
  <item-number number="1" start_line="545">
    ...Stuff...
  </item-number>
  ...plus d'item-number...
</over-bullet>

Ceci est similaire à la structure d'événement "over-bullet" ; mais notez que les contenus sont "item-number" au lieu de "item-bullet", et notez qu'ils auront un attribut "number", que certains formateurs/processeurs peuvent ignorer (car, par exemple, il n'est pas nécessaire en HTML pour produire une structure "<UL><LI>...</LI>...</UL>"), mais que tout processeur peut utiliser.

Notez que les valeurs des attributs number des éléments "item-number" dans une zone "over-number" donnée *commenceront* à 1 et augmenteront de un à chaque fois. Si la source Pod ne suit pas cet ordre (même si elle le devrait vraiment !), les nombres qu'elle contient seront ignorés (les valeurs correctes seront mises dans les attributs number), et un message d'erreur pourrait être émis à l'utilisateur.

événements avec un nom_élément égal à over-text
Ces événements sont quelque peu différents des autres structures over-*, en ce qui concerne leur contenu. Lorsqu'un bloc "=over ... =back" est analysé où les éléments sont une liste de "sous-titres" textuels, il produira cette structure d'événement : 
<over-text indent="4" start_line="543">
  <item-text>
    ...stuff...
  </item-text>
  ...stuff (généralement des éléments Para ou Verbatim)...
  <item-text>
  ...plus d'item-text et/ou de stuff...
</over-text>

Les attributs indent et fake-closer sont comme pour les autres événements over-*.

Par exemple, cette source Pod :

=over
=item Foo
Stuff
=item Bar I<baz>!
Quux
=back

Produit cette structure d'événement :

<over-text indent="4" start_line="20">
  <item-text start_line="22">
    Foo
  </item-text>
  <Para start_line="24">
    Stuff
  </Para>
  <item-text start_line="26">
    Bar
      <I>
        baz
      </I>
    !
  </item-text>
  <Para start_line="28">
    Quux
  </Para>
</over-text>
événements avec un nom_élément égal à over-block
Ces événements sont quelque peu différents des autres structures over-*, en ce qui concerne leur contenu. Lorsqu'un bloc "=over ... =back" est analysé où il n'y a pas d'éléments, il produira cette structure d'événement : 
<over-block indent="4" start_line="543">
  ...stuff (généralement des éléments Para ou Verbatim)...
</over-block>

Les attributs indent et fake-closer sont comme pour les autres événements over-*.

Par exemple, cette source Pod :

=over
For cutting off our trade with all parts of the world
For transporting us beyond seas to be tried for pretended offenses
He is at this time transporting large armies of foreign mercenaries to
complete the works of death, desolation and tyranny, already begun with
circumstances of cruelty and perfidy scarcely paralleled in the most
barbarous ages, and totally unworthy the head of a civilized nation.
=back

Produira cette structure d'événement :

<over-block indent="4" start_line="2">
  <Para start_line="4">
    For cutting off our trade with all parts of the world
  </Para>
  <Para start_line="6">
    For transporting us beyond seas to be tried for pretended offenses
  </Para>
  <Para start_line="8">
    He is at this time transporting large armies of [...more text...]
  </Para>
</over-block>
événements avec un nom_élément égal à over-empty
Note : Ces événements ne sont déclenchés que si parse_empty_lists() est défini sur une valeur vraie.

Ces événements sont quelque peu différents des autres structures over-*, en ce qui concerne leur contenu. Lorsqu'un bloc "=over ... =back" est analysé où il n'y a pas de contenu, il produira cette structure d'événement :

<over-empty indent="4" start_line="543">
</over-empty>

Les attributs indent et fake-closer sont comme pour les autres événements over-*.

Par exemple, cette source Pod :

=over
=over
=back
=back

Produira cette structure d'événement :

<over-block indent="4" start_line="1">
  <over-empty indent="4" start_line="3">
  </over-empty>
</over-block>

Notez que le "=over" extérieur est un bloc car il n'a pas d'"=item"s mais a toujours du contenu : l'"=over" intérieur. L'"=over" intérieur, à son tour, est complètement vide et est traité comme tel.

événements avec un nom_élément égal à item-bullet
Voir "événements avec un nom_élément égal à over-bullet", ci-dessus.
événements avec un nom_élément égal à item-number
Voir "événements avec un nom_élément égal à over-number", ci-dessus.

Voir "événements avec un nom_élément égal à over-text", ci-dessus.

Plus de méthodes Pod::Simple

Pod::Simple fournit de nombreuses méthodes qui ne sont généralement pas intéressantes pour l'utilisateur final d'un formateur Pod existant, mais dont certaines pourraient vous être utiles pour écrire un formateur Pod. Elles sont listées ci-dessous. Les premières méthodes (les méthodes accept_*) servent à déclarer les capacités de votre analyseur, notamment les sections "=for nom_cible" qui l'intéressent, les codes N<...> supplémentaires qu'il accepte au delà de ceux décrits dans perlpod.

"$parser->accept_targets( VALEUR )"
Lorsque l'analyseur rencontre des sections comme : 
=for html  <img src="fig1.jpg">

ou

=begin html
  <img src="fig1.jpg">
=end html

... l'analyseur ignorera ces sections sauf si votre sous-classe a spécifié qu'elle veut voir les sections ciblées pour "html" (ou quel que soit le nom du formateur).

Si vous voulez traiter toutes les sections, même si elles ne vous sont pas destinées, appelez ceci avant de commencer l'analyse :

$parser->accept_targets('*');
"$parser->accept_targets_as_text( VALEUR )"
Ceci est similaire à accept_targets, sauf que cela spécifie également que le contenu des sections pour cette cible doit être traité comme du texte Pod, même si le nom de la cible dans "=for nom_cible" ne commence pas par un ":".

Au moment de la rédaction, je ne pense pas que vous ayez besoin de l'utiliser.

"$parser->accept_codes( NomCode, NomCode... )"
Ceci indique à l'analyseur que vous acceptez des codes de formatage supplémentaires, au-delà des codes standard (I B C L F S X, plus les deux codes étranges que vous ne voyez pas réellement dans l'arbre d'analyse, Z et E). Par exemple, pour accepter également les codes "N", "R" et "W" : 
$parser->accept_codes( qw( N R W ) );

"$parser->accept_directive_as_data( nom_directive )"
"$parser->accept_directive_as_verbatim( nom_directive )"
"$parser->accept_directive_as_processed( nom_directive )"
Dans le cas improbable où vous auriez besoin d'indiquer à l'analyseur que vous acceptez des directives supplémentaires (choses de type "=foo"), vous devez d'abord définir l'analyseur pour qu'il traite son contenu comme des données (c'est-à-dire, pas vraiment traité), ou comme du verbatim (principalement juste l'expansion des tabulations), ou comme du texte traité (analyse des codes de formatage comme B<...>).

Par exemple, pour accepter une nouvelle directive "=method", vous utiliseriez probablement :

$parser->accept_directive_as_processed("method");

afin que vous puissiez avoir des lignes Pod comme :

=method I<$whatever> thing B<um>

Créer vos propres directives brise la compatibilité avec d'autres formateurs Pod, d'une manière qui utiliser "=for cible ..."

Pod::Simple::DumpAsXML -- pour générer du XML indenté à partir de documents Pod avec chaque événement sur une ligne distincte

Pod::Simple::XMLOutStream -- génère un document Pod au format XML (sans introduire d'espace supplémentaire comme dans Pod::Simple::DumpAsXML)

Pod::Simple::DumpAsText -- pour générer du texte indenté à partir de documents Pod avec chaque événement sur une ligne distincte

Pod::Simple::LinkSection -- classe pour les objets représentant les valeurs des attributs TODO et TODO des éléments L<...>

Pod::Escapes -- le module que Pod::Simple utilise pour évaluer le contenu de E<...>

Pod::Simple::Text -- un simple formateur de texte brut pour Pod

Pod::Simple::TextContent -- similaire à Pod::Simple::Text, mais n'essaie pas d'indenter ou d'aligner le texte formé
