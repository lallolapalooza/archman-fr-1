NOM

POE::Component::IKC::Responder - Gestionnaire d'état pour POE IKC

SYNOPIS

use POE;
use POE::Component::IKC::Responder;
create_ikc_responder();
...
$kernel->post('IKC', 'post', $to_state, $state);
$ikc->publish('my_name', [qw(state1 state2 state3)]);

DESCRIPTION

Ce module implémente le traitement d'état pour POE IKC. Le gestionnaire envoie des états à des noyaux externes et appelle des états dans le noyau local à la demande des noyaux externes.

Il y a deux interfaces pour le gestionnaire. Soit en envoyant des états à la session 'IKC', soit via l'interface objet. Bien que la seconde soit plus rapide, la plus bien élevée, puisque POE est un système coopératif.

ÉTATS/MÉTHODES

"spawn"

POE::Component::IKC::Responder->spawn();

Cette fonction crée la session du gestionnaire et l'objet. Normalement, POE::Component::IKC::Client ou POE::Component::IKC::Server le fait pour vous. Cependant, dans certaines applications, vous voulez vous assurer que le gestionnaire est actif avant qu'il ne le fasse.

"post"

Envoie une requête d'état à un noyau externe. Renvoie une valeur booléenne si l'état a été envoyé et une autre booléenne si la requête n'a pas pu être envoyée au noyau externe. Cela ne signifie pas nécessairement que le noyau externe a pu publier l'état, bien que ce soit le cas. Les paramètres sont les suivants :

"foreign_state"
Miroir pour l'état du noyau externe. Voir POE::Component::IKC::Specifier.
"parameters"
Une référence à tout ce que vous voulez que l'état externe obtienne en tant qu'ARG0. Si vous voulez spécifier plusieurs paramètres, utilisez une référence de tableau et laissez l'état externe les déréférencer. 
$kernel->post('IKC', 'post',
    {kernel=>'Syslog', session=>'logger', state=>'log'},
    [$faculty, $priority, $message];

ou

$ikc->post('poe://Syslog/logger/log', [$faculty, $priority, $message]);

Ceci enregistre un état avec un logger hypothétique.

Voir le "PROXY SENDER" ci-dessous.

"call"

Ceci est identique à "post", sauf qu'il a un troisième paramètre qui décrit quel état recevra la valeur retournée par le noyau externe.

$kernel->post('IKC', 'call',
            'poe://Pulse/timeserver/time', '',
            'poe:get_time');

ou

$ikc->call({kernel=>'Pulse', session=>'timeserver', state=>'time'},
            '', 'poe://me/get_time');

Ceci interroge le noyau externe 'Pulse' pour connaître l'heure. L'état 'get_time' de la session actuelle est publié avec ce que le noyau externe a retourné.

Vous n'avez pas à publier les messages de retour, car ils sont publiés temporairement. Combien de temps ? Ils ne peuvent être publiés qu'une seule fois par un noyau externe. C'est, bien sûr, un problème car quelqu'un pourrait publier avant le retour. C'est la vie.

"foreign_state"
Identique au paramètre "post".
"parameters"
Identique au paramètre "post".
"rsvp"
Identifiant d'événement pour le retour. C'est-à-dire, cet état sera appelé avec la valeur retournée par l'état externe. Il peut s'agir d'un miroir de "foreign_state" ou simplement du nom d'un état dans la session actuelle.
$kernel->call('IKC', 'post',
    {kernel=>'e-comm', session=>'CC', state=>'check'},
    {CC=>$cc, expiry=>$expiry}, folder=>$holder},
    'is_valid');
# ou
$ikc->call('poe://e-comm/CC/check',
    {CC=>$cc, expiry=>$expiry}, folder=>$holder},
    'poe://me/is_valid');

Ceci demande au serveur e-comm de vérifier si un numéro de carte de crédit est "valide". Oui, ce serait probablement un abus d'utilisation.

L'état "rsvp" n'a pas besoin d'être publié. IKC s'occupe d'enregistrer l'état " rsvp" et permet au noyau externe de publier dessus.

Voir le "PROXY SENDER" ci-dessous.

"default"

Définit le noyau externe par défaut. Vous devez d'abord être connecté au noyau externe.

Le seul paramètre est le nom du noyau externe.

Renvoie une valeur booléenne en cas de succès.

"register"

Enregistre les noms de noyaux externes auprès du gestionnaire. Ceci est fait pendant la phase de négociation d'IKC et est normalement géré par POE::Component::IKC::Channel. Il définira le noyau par défaut s'il n'y en a pas de précédent.

Le premier paramètre est un nom de noyau unique. Le second paramètre est une référence de tableau d'alias de noyau à enregistrer.

"unregister"

Désenregistre les noms de noyaux externes auprès du gestionnaire. Ceci est fait lorsque le noyau externe se déconnecte par POE::Component::IKC::Channel. S'il s'agit du noyau par défaut, il n'y a plus de noyau par défaut.

Le premier paramètre est un nom de noyau ou un alias. Le second paramètre est une référence de tableau d'alias de noyau à désenregistrer. Le second paramètre est un peu stupide, car si vous désenregistrez un noyau distant, tous ses alias sont également désenregistrés.

"register_local"

Enregistre de nouveaux alias locaux auprès du gestionnaire. Ceci est fait interne par POE::Component::IKC::Server et POE::Component::IKC::Client. Il ne définira pas le noyau par défaut.

Le premier et unique paramètre est une référence de tableau d'alias de noyau à enregistrer.

"publish"

Indique à IKC que certains états de la session actuelle sont disponibles pour être utilisés par des sessions externes.

"session"
Un alias de session par lequel les sessions externes appelleront. L'alias doit déjà être enregistré auprès du noyau local.
"states"
Référence de tableau des états qui peuvent être publiés par des sessions externes. 
$kernel->post('IKC', 'publish', 'me', [qw(foo bar baz)]);
# ou
$ikc->publish('me', [qw(foo bar baz)]);

"retract"

Indique à IKC que certains états ne doivent plus être utilisés par des sessions externes. Vous n'avez pas à désactiver tous les états publiés.

"session"
Identique au paramètre "session" dans "publish"
"states"
Identique au paramètre "states" dans "publish". S'il n'est pas spécifié, *tous* les états publiés sont retirés. 
$kernel->post('IKC', 'retract', 'me', [qw(foo mibble dot)]);
# ou
$ikc->retract('me', [qw(foo)]);

"published"

$list=$kernel->call(IKC=>'published', $session);

Renvoie une liste de tous les états publiés.

$hash=$kernel->call(IKC=>'published');

Renvoie une référence de hachage, indexée par les identifiants de session. Les valeurs sont des références de tableau des états publiés par cette session.

"session"
Un alias de session pour lequel vous souhaitez obtenir la liste des états.

"subscribe"

S'abonne aux sessions ou états externes.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

"unsubscribe"

L'inverse de la méthodologie de souscription. Cependant, elle n'est pas bien documentée actuellement.

"ping"

Répond avec 'PONG'. Elle est auto-publiée, donc elle peut être appelée à partir de noyaux distants pour voir si le noyau local est toujours actif. En fait, je ne vois pas d'autre utilité à cela.

$kernel->post('poe://remote/IKC', 'ping', 'some_state');
$kernel->delay('some_state', 60);   # timeout

sub some_state
{
    my($pong)=$_[ARG0];
    return if $pong;            # todo todo todo

    # YOW! Le noyau distant a expiré. COURREZ EN CRIANT!
}

"shutdown"

On s'attend à ce que cela provoque le dépérissement d'IKC et de toutes les sessions périphériques dans un nuage de fumée. Au pire, toute session restante sera sans rapport avec IKC ou à peine vivante (c'est-à-dire qu'elle n'aura que des alias pour éviter la collecte de miettes).

"monitor"

Permet à une session de surveiller l'état des noyaux distants. Actuellement, une session est informée lorsqu'un noyau distant s'enregistre, se désenregistre, s'abonne ou se désabonne. Vous devez vous assurer que l'alias IKC existe avant de surveiller. Cela peut être fait en appelant POE::Component::IKC::Responder->spawn ou dans un callback on_connect.

$kernel->post('IKC', 'monitor', $remote_kernel_id, $states);
$remote_kernel_id
Nom ou alias ou spécificateur IKC du noyau distant que vous souhaitez surveiller. Vous pouvez également spécifier *&* pour surveiller tous les noyaux distants. Si vous le faites, votre moniteur sera appelé plusieurs fois pour un noyau donné. En effet, un noyau a un ID unique et plusieurs alias. Par exemple, un noyau distant aura un ID unique au sein du noyau local, un nom (passé à ou généré par create_ikc_{kernel,client}) et un ID global attribué par le noyau distant via $kernel->ID. Cela surprend certains, mais consultez la note courte après l'explication des paramètres des callbacks.
$states
Un hashref spécifiant quels callbacks appeler lorsque quelque chose d'intéressant se produit. Si $state est vide ou undef, la session cessera de surveiller le noyau distant donné.

États des callbacks

Les états suivants peuvent être surveillés :

"channel"
Appelé lorsqu'un canal devient prêt ou se ferme. ARG3 est soit "ready", soit "close". ARG4 est l'ID de session numérique du canal. Voir "CHANNELS" ci-dessous.
"register"
Appelé lorsqu'un noyau ou un alias est enregistré. Ceci est équivalent à la fin de la phase de connexion.
"unregister"
Appelé lorsqu'un noyau ou un alias est désenregistré. Ceci est équivalent à la déconnexion du noyau distant.
"subscribe"
Appelé lorsque IKC réussit à s'abonner à une session distante. ARG3 est un IKC::Specifier de ce à quoi il s'est abonné. Utilisez-le pour publier sur la session proxy.
"unsubscribe"
Appelé lorsque IKC réussit à se désabonner d'une session distante.
"shutdown"
Signalé lorsqu'une tentative de fermeture normale d'IKC et de toutes les sessions périphériques est effectuée. Ceci n'est appelé qu'une seule fois, après que quelqu'un ait publié un événement IKC/shutdown.
"error"
Les erreurs sur les noyaux locaux et distants sont signalées. ARG3 est l'opération qui a échoué. ARG4 est le message d'erreur. Voir "ERRORS" ci-dessous.
"data"
Une donnée (peut être scalaire ou une référence) qui est passée au callback. Cela permet plus de magie.

Les états de callback sont appelés avec les paramètres suivants :

"ARG0"
Nom du noyau qui a été passé à poe://*/IKC/monitor
"ARG1"
ID ou alias du noyau distant du point de vue d'IKC.
"ARG2"
Un drapeau. S'il est vrai, alors ARG1 est l'ID unique du noyau distant, s'il est faux, alors ARG1 est un alias. Ceci est principalement utile lorsque vous surveillez *&*, et c'est en fait un peu un point d'achoppement.
"ARG3"
"$state->{data}" c'est-à-dire toute donnée que vous souhaitez.
"ARG4" ... "ARGN"
Paramètres spécifiques au callback. Voir ci-dessus.

La plupart du temps, ARG0 et ARG1 seront identiques. Les exceptions sont si vous surveillez *&* ou si vous avez fourni un spécificateur d'événement IKC complet à IKC/monitor au lieu d'un simple nom de noyau.

Note courte sur la surveillance de tous les noyaux avec "*"

Il y a deux raisons pour lesquelles vous pourriez vouloir surveiller tous les noyaux distants : connaître les noms à l'avance et ne pas connaître les noms à l'avance.

Si vous connaissez les noms des noyaux à l'avance, vous pourriez préférer surveiller un nom donné. Cependant, vous pourriez préférer faire une comparaison similaire avec ARG1 (en utilisant des regex, par exemple). Ce serait utile pour le clustering, où plusieurs noyaux redondants pourraient suivre une convention de nommage comme [application]-[hôte], de sorte que vous pourriez comparer "ARG1" avec "/^credit-/" pour voir si vous voulez configurer des choses spécifiques pour ce noyau.

Sans connaître le nom d'un noyau à l'avance, vous pourriez effectuer une sorte de découverte automatique ou simplement surveiller pour le débogage, la journalisation ou la comptabilité. Vous ne voudrez clairement pas effectuer une découverte automatique pour chaque alias de chaque noyau, mais uniquement pour le nom canonique, d'où la nécessité d'ARG2.

Note courte la deuxième

Vous pouvez utiliser les mêmes états de callback lorsque vous surveillez plusieurs noyaux. Dans ce cas, vous trouverez ARG0 utile pour les différencier.

$kernel->post('IKC', 'monitor', '*', 
                {register=>'remote_register',
                 unregister=>'remote_unregister',
                 subscribe=>'remote_subscribe',
                 unsubscribe=>'remote_unsubscribe',
                 data=>'magic box'});

Maintenant, remote_{register,unregister,subscribe,unsubscribe} sera appelé pour n'importe quel noyau distant.

$kernel->post('IKC', 'monitor', 'Pulse', {register=>'pulse_connected'});

"pulse_connected" sera appelé dans la session actuelle lorsque vous vous serez connecté avec succès à un noyau nommé 'Pulse'.

$kernel->post('IKC', 'monitor', '*');

La session ne surveille plus tous les noyaux, mais seulement 'Pulse'.

$kernel->post('IKC', 'monitor', 'Pulse', {});

Maintenant, nous ne nous soucions plus de 'Pulse' ;

POE::Component::IKC::Responder(3pm) — Arch manual pages

NAME

POE::Component::IKC::Responder - an IKC responder

SYNOPSIS

    use POE::Component::IKC::Responder;
    
    my $responder = POE::Component::IKC::Responder->spawn(
        Alias => 'my_responder',
        Remote => 'poe://remote_kernel/some/state',
        Args => [ $arg1, $arg2 ],
        Callback => sub { ... },
    );
    
    # or if you want to spawn a responder for a remote kernel that
    # does not use aliases
    my $responder = POE::Component::IKC::Responder->spawn(
        Remote => 'poe://192.168.1.1:1234/some/state',
        Args => [ $arg1, $arg2 ],
        Callback => sub { ... },
    );
    
    # or if you want to spawn a responder for a remote kernel that
    # knows about you
    my $responder = POE::Component::IKC::Responder->spawn(
        Remote => 'poe://remote_kernel_id',
        Args => [ $arg1, $arg2 ],
        Callback => sub { ... },
    );
    
    # you can also specify the port and protocol
    my $responder = POE::Component::IKC::Responder->spawn(
        Remote => 'poe://remote_kernel/some/state',
        Port => 1234,
        Protocol => 'tcp',
        Args => [ $arg1, $arg2 ],
        Callback => sub { ... },
    );
    
    # you can also make the responder listen for incoming connections
    my $responder = POE::Component::IKC::Responder->spawn(
        Listen => 1,
        Port => 1234,
        Protocol => 'tcp',
        Alias => 'my_responder',
        Args => [ $arg1, $arg2 ],
        Callback => sub { ... },
    );

DESCRIPTION

POE::Component::IKC::Responder is used to respond to requests from remote POE kernels. Normally a kernel will make a request to another kernel via the POE::Component::IKC::Client interface. This component allows you to implement the code that runs on the other side.

The responder listens for incoming connections, or makes a connection to a remote kernel. It then waits for a request to arrive. When a request arrives, it calls the code that you specified in the Callback parameter.

The Callback will be called with arguments that are passed to it by the remote kernel. The Callback is also passed a reference to the current POE::Component::IKC::Responder object.

The remote kernel will be waiting for a response. The response can be sent back via the Responder object's post_response method.

You can also use the Responder to post events that are not directly tied to a request. This is done by setting the Args parameter to undef and calling post_response with no arguments.

STATES/METHODS

All arguments to spawn are session state variables. See POE::Component for more information.

Alias
The alias that this responder will register itself with in the local kernel.
Remote
The destination kernel and state. This can be a hostname, an IP address, or an alias that the kernel has registered itself with.
Port
The port number to connect to or listen on. Defaults to POE::Component::IKC::default_port.
Protocol
The protocol to use, ie. tcp or udp. Defaults to tcp.
Args
An array reference of arguments to send along with the request. If this is undef, then no arguments will be sent, and the responder will be listening for incoming requests rather than making a request.
Callback
The coderef to call when a request is received. The coderef will be called with the Responder object as the first argument, followed by any arguments sent with the request.
Listen
A boolean value indicating whether the responder should listen for incoming connections. Defaults to false.
post_response

The post_response method is used to send a response back to the remote kernel. It takes a list of arguments to send back.

sub post_response {
    my( $self, @args ) = @_;
    $poe_kernel->post( $self->{SENDER}, 'response', @args );
}

If the Args parameter was set to undef when spawning the responder, then post_response can be called with no arguments. In this case, it will simply acknowledge receipt of the request.

CHANNELS

IKC uses POE::Component::IKC::Channel to manage the underlying network connections. Each channel is managed by a POE::Component::IKC::Channel object.

The Responder object holds a hash of channels, keyed by the remote kernel's kernel ID. You can access these channels via the channel method:

my $channel = $responder->channel( $rkernel );

The channel object has a close method:

sub close_channel {
    my( $self, $rkernel ) = @_[ OBJECT, ARG0 ];
    # tell the channel to close
    $poe_kernel->post( $self->{channel}{ $rkernel } => 'shutdown' );
}

ERRORS

Previous versions of IKC did not adequately allow you to monitor for errors on a connection. With 0.2400 we started monitoring errors.

There are 2 step during which you can have errors: when opening the connection and during message exchange. These 2 steps are handled diffrently.

You use "on_error" in POE::Component::IKC::Client and "on_error" in POE::Component::IKC::Server to receive errors while a connection is being opened. Note that this includes the initial IKC handshake.

sub on_error 
{
    my( $op, $errnum, $errstr ) = @_;
    # Handle this like you would any POE socket error
    # But remember you can't rely on your session being active
}

You use "monitor" on error to receive errors during message exchange. ARG3 is the name of the operation. ARG4 is the error message. Current operations are:

remote-request
Remote kernel was unable to parse a request that was sent from the local kernel.
remote-check
Remote kernel has not published an event that was sent from the local kernel.
remote-resolve
Remote kernel could not find a session that could handle the request.
remote-invocation
Remote kernel had an error when it tried to invoke the request handler. Please note this will not catch errors in the request handler, but only errors in the thunk.
local-request
local-check
local-resolve
local-invocation
These 4 operations are the local equivalent of the previous 4. They are intented for logging. In general no actions are required.

Note that 'local' and 'remote' refer to where the operation happened, not where the request originated. As an example, kernel A sends a poe://B/foo/bar request to kernel B. Kernel B has not published that event. Monitors on kernel A will see remote-check. Monitors on kernel B will see local-check.

channel-error
Receive channel errors during message exchange. Channel errors are equivalent to POE wheel errors. The message will be "[$errnum] $errstr".
subscribe
Failure to subscribe to a remote session.
fork
POE::Component::IKC::Server failed to fork.
resolve
Error when trying to find a remote kernel or session.

Example monitor for error events:

sub monitor_error
{   
    my( $self, $rid, $kernel, $real, $data, $op, $message ) = 
            @_[ OBJECT, ARG0 ... $#_ ];
    if( $op =~ /^channel-/ and $message =~ /\[(\d+)\] (.*)/ ) {
        return unless $real;
        my( $errnum, $errstr ) = ( $1, $2 );
        if( $op eq 'channel-read' and $errnum == 0 ) {
            warn "Connection closed";
            return;
        }
    }
    warn "Error during $op: $message";
}

In particular, you will note we don't do anything when we detect the channel closed. Instead, it is recommended to attempt reconnection in the "unregister" event.

PROXY SENDER

Event handlers invoked via IKC will have a proxy SENDER session. You may use it to post back to the remote session.

$poe_kernel->post( $_[SENDER], 'response', @args );

Normally this proxy session is available during the invocation of the event handler. You may claim it for longer by setting an external reference:

$heap->{remote} = $_[SENDER]->ID;
$poe_kernel->refcount_increment( $heap->{remote}, 'MINE' );

POE::Component::IKC will detect this and create a new proxy session for future calls. It will then be UP TO YOU to free the session:

$poe_kernel->refcount_decrement( $heap->{remote}, 'MINE' );

Note that you will have to publish any events that will be posted back.

BUGS

Sending session references and coderefs to a foreign kernel is a bad idea. At some point it would be desirable to recurse through the paramerters and and turn any session references into state specifiers.

The "rsvp" state in call is a bit problematic. IKC allows it to be posted to once, but doesn't check to see if the foreign kernel is the right one.

"retract" does not currently tell foreign kernels that have subscribed to a session/state about the retraction.

call()ing a state in a proxied foreign session doesn't work, for obvious reasons.
