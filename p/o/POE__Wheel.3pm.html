POE::Wheel(3) Documentation Perl Contribuée par l'Utilisateur POE::Wheel(3)

NOM

POE::Wheel - mixins événementiels pour POE::Session

SYNOPIS

Cette classe de base n'a pas de synopsis. Veuillez consulter l'une des sous-classes à la place.

DESCRIPTION

Un objet POE::Wheel encapsule un ensemble de gestionnaires d'événements qui effectuent une tâche spécifique. Il gère également les observateurs d'événements qui déclenchent ces gestionnaires.

La durée de vie des objets est très importante pour les roues POE. Lors de la création, la plupart des roues ajouteront des gestionnaires d'événements anonymes à la session active. En d'autres termes, la session qui a créé la roue est modifiée pour gérer de nouveaux événements. Des observateurs d'événements peuvent également être initialisés si nécessaire pour déclencher les nouveaux gestionnaires. Ces observateurs d'événements sont également détenus par la session qui a créé la roue.

Les sessions ne doivent pas exposer leurs roues à d'autres sessions. Le faire causera probablement des problèmes car les roues sont étroitement intégrées aux sessions qui les ont créées. Par exemple, appeler put() sur une instance de POE::Wheel::ReadWrite peut activer un observateur de type "écriture autorisée". Le gestionnaire de cet observateur est déjà défini dans le propriétaire de la roue. Appeler put() en dehors de cette session activera l'observateur "écriture autorisée" dans la mauvaise session, et l'événement ne sera jamais géré.

De même, les roues doivent être détruites depuis les sessions qui les ont créées. Sinon, des erreurs se produiront lorsque les méthodes DESTROY des roues tenteront de désenregistrer les gestionnaires d'événements et les observateurs des mauvaises sessions. Pour simplifier les choses, il est recommandé de stocker les instances de POE::Wheel dans les tas des sessions qui les ont créées.

Par exemple, la création d'un objet POE::Wheel::FollowTail enregistrera un gestionnaire d'événements qui interroge périodiquement un fichier pour de nouvelles informations. Il démarrera également le minuteur qui déclenche l'interrogation périodique.

use POE;
use POE::Wheel::FollowTail;
my @files_to_tail = qw( messages maillog security );
foreach my $filename (@files_to_tail) {
  POE::Session->create(
    inline_states => {
      _start => sub {
        push @{$_[HEAP]{messages}}, POE::Wheel::FollowTail->new(
          Filename   => "/var/log/$filename",
          InputEvent => "got_input",
        );
      },
      got_input => sub {
        print "$filename: $_[ARG0]\n";
      },
    }
  );
}
POE::Kernel->run();
exit;

Comme illustré dans l'exemple précédent, il est possible (parfois recommandé) de créer plus d'une POE::Wheel d'un type particulier dans la même session. Une session avec plusieurs roues peut mieux évoluer que des sessions séparées avec une roue chacune. En cas de doute, faites des benchmarks.

Contrairement aux composants (ou au fromage), les roues ne sont pas autonomes. Chaque roue doit être créée par une session afin d'enregistrer des observateurs et des gestionnaires d'événements dans cette session. Les roues sont donc étroitement couplées à leurs sessions créatrices et ne peuvent pas être transmises à d'autres sessions.

FILTRES, ET PILOTES

De nombreuses roues effectuent des opérations de transfert de données sur des descripteurs de fichiers (qui, comme vous le savez probablement, incluent les sockets, les tuyaux et à peu près tout ce qui peut stocker ou transférer des données).

Pour éviter les "subclass hell", les objets POE::Wheel peuvent être personnalisés lors de la création en incluant d'autres objets des espaces de noms POE::Filter et POE::Driver.

Filtres

Les "filtres" POE implémentent des analyseurs et des sérialiseurs de données. Par exemple, POE::Filter::Line analyse les flux en enregistrements séparés par une chaîne donnée (par défaut, le saut de ligne réseau traditionnel). Le filtre Line ajoute également des séparateurs d'enregistrement aux données en sortie.

POE::Filter::HTTPD est un exemple plus complexe. Il implémente un sous-ensemble du côté serveur du protocole HTTP. Les flux d'entrée sont analysés en requêtes HTTP et encapsulés dans des objets HTTP::Request. Le code serveur renvoie des objets HTTP::Response au client, qui sont sérialisés afin de pouvoir être envoyés à un socket.

La plupart des roues utilisent POE::Filter::Line par défaut.

Pilotes

Les "pilotes" POE implémentent des stratégies pour envoyer des données à un descripteur de fichier et en recevoir. Une seule classe POE::Wheel peut interagir avec des fichiers, des tuyaux, des sockets ou des périphériques en utilisant le pilote approprié.

POE::Driver::SysRW est le seul pilote fourni avec POE. sysread() et syswrite() peuvent gérer presque tous les types d'interactions de flux, donc il n'y a pas eu beaucoup de demande pour un autre type de pilote.

MÉTHODES

POE::Wheel définit une interface commune que la plupart des sous-classes utilisent. Les sous-classes peuvent implémenter d'autres méthodes, notamment pour aider à accomplir leurs tâches uniques. Si quelque chose d'utile n'est pas documenté ici, consultez la sous-classe avant d'implémenter une fonctionnalité.

Méthodes requises

Ces méthodes sont requises par toutes les sous-classes.

new LOTS_OF_STUFF

new() instancie et initialise un nouvel objet roue et le retourne. La nouvelle roue continuera à fonctionner tant qu'elle existera, bien que d'autres méthodes puissent modifier son fonctionnement.

Une partie de la construction de chaque roue est l'enregistrement de gestionnaires d'événements anonymes pour effectuer des tâches spécifiques à la roue. Les observateurs d'événements sont également démarrés pour déclencher les gestionnaires lors d'activités pertinentes.

Chaque roue a un objectif différent et nécessite des paramètres de constructeur différents, donc LOTS_OF_STUFF est documenté dans chaque sous-classe particulière.

DESTROY

DESTROY est le vieux destructeur d'objets Perl. Lorsque la dernière référence forte à la roue est abandonnée, DESTROY déclenche le nettoyage de la roue. L'objet se retire de la session qui l'a créé : les observateurs d'événements actifs sont arrêtés et les gestionnaires d'événements anonymes sont désenregistrés.

event TYPE_ÉVÉNEMENT, NOM_ÉVÉNEMENT [, TYPE_ÉVÉNEMENT, NOM_ÉVÉNEMENT, ....]

event() change les événements qu'une roue émettra. Ses paramètres sont une ou plusieurs paires de TYPE_ÉVÉNEMENT et de NOM_ÉVÉNEMENT à émettre lorsque chaque type d'événement se produit. Si un NOM_ÉVÉNEMENT est indéfini, alors la roue cessera d'émettre ce type d'événement. Ou la roue peut déclencher une erreur si le type d'événement est requis.

Les TYPE_ÉVÉNEMENT varient pour chaque roue et correspondent aux paramètres du constructeur qui correspondent à /.*Event$/. Par exemple, POE::Wheel::ReadWrite peut émettre jusqu'à cinq types d'événements différents : InputEvent, ErrorEvent, FlushedEvent, HighEvent, LowEvent. Le nom de chaque événement émis peut être modifié à l'exécution.

Cet exemple modifie les événements à émettre lors d'une nouvelle entrée et lorsque la sortie est vidée. Il empêche la roue d'émettre des événements en cas d'erreur.

$wheel->event(
  InputEvent   => 'new_input_event',
  ErrorEvent   => undef,
  FlushedEvent => 'new_flushed_event',
);

Méthodes E/S

Les roues qui effectuent des entrées et sorties peuvent implémenter une partie ou la totalité de ces méthodes. La méthode put() est souvent omise. Les roues qui n'effectuent pas de sortie n'ont pas de méthodes put().

put ENREGISTREMENT [, ENREGISTREMENT [, ....]]

put() envoie un ou plusieurs ENREGISTREMENTS à la roue pour transmission. Chaque ENREGISTREMENT est sérialisé par le POE::Filter associé à la roue afin qu'il soit prêt à être transmis. Le flux sérialisé peut être transmis immédiatement par l'objet POE::Driver de la roue, ou il peut être mis en tampon dans le POE::Driver jusqu'à ce qu'il puisse être vidé vers le descripteur de fichier de sortie.

La plupart des roues utilisent POE::Filter::Line et POE::Driver::SysRW par défaut, il n'est donc pas nécessaire de les spécifier dans la plupart des cas.

Fonctions statiques de classe

Ces fonctions exposent des informations communes à toutes les roues. Ce ne sont pas des méthodes, elles ne doivent donc pas être appelées comme des méthodes.

my $new_wheel_id = POE::Wheel::allocate_wheel_id();
POE::Wheel::free_wheel_id($new_wheel_id);

allocate_wheel_id

Ce n'est pas une méthode de classe.

Chaque roue a un identifiant unique. allocate_wheel_id() renvoie le prochain identifiant de roue unique disponible. Les constructeurs de roues l'utilisent pour définir leurs identifiants en interne.

package POE::Wheel::Example;
use base qw(POE::Wheel);
sub new {
  # ... entre autres choses ...
  $self->[MY_WHEEL_ID] = POE::Wheel::allocate_wheel_id();
  return $self;
}

Les identifiants de roue sont souvent utilisés pour stocker un état local à la roue dans le tas d'une session.

sub handle_error {
  my $wheel_id = $_[ARG3];
  print "La roue $wheel_id a attrapé une erreur. Fermeture.";
  delete $_[HEAP]{wheels}{$wheel_id};
}

Il est essentiel que les roues libèrent leurs identifiants alloués lorsqu'elles sont détruites. La classe POE::Wheel suit les identifiants de roue alloués pour éviter les collisions, et ils resteront en mémoire jusqu'à leur libération. Voir free_wheel_id().

free_wheel_id WHEEL_ID

Ce n'est pas une méthode de classe.

free_wheel_id() désalloue un identifiant de roue afin qu'il cesse de consommer de la mémoire et puisse être réutilisé ultérieurement. Ceci est souvent appelé depuis le destructeur d'une roue.

package POE::Wheel::Example;
use base qw(POE::Wheel);
sub DESTROY {
  my $self = shift;
  # ... entre autres choses ...
  POE::Wheel::free_wheel_id($self->[MY_WHEEL_ID]);
}

Les identifiants de roue peuvent être réutilisés, bien que cela n'ait jamais été signalé. Cependant, deux roues actives ne partageront jamais le même identifiant.

ID

Ceci est généralement implémenté dans la sous-classe !

La méthode ID() renvoie l'identifiant unique d'une roue. Elle est couramment utilisée pour faire correspondre les événements avec les roues qui les ont générés.

Encore une fois, cette méthode n'est pas implémentée dans cette classe ! Si elle est manquante dans la sous-classe, veuillez aller importuner cet auteur de module - merci !

VOIR AUSSI

La section VOIR AUSSI de POE contient une table des matières couvrant toute la distribution POE.

POE::Driver - Une classe de base pour les pilotes d'accès aux fichiers que POE::Wheel peut utiliser.

POE::Filter - Une classe de base pour les analyseurs et les sérialiseurs de données que POE::Wheel peut utiliser.

POE::Wheel::Curses - Entrée non bloquante pour Curses.

POE::Wheel::FollowTail - Surveillance non bloquante de fichiers et de FIFO.

POE::Wheel::ListenAccept - Serveur non bloquant pour les sockets existants.

POE::Wheel::ReadLine - Entrée console non bloquante, avec prise en charge complète de readline.

POE::Wheel::ReadWrite - E/S de flux non bloquantes.

POE::Wheel::Run - Création et gestion de processus non bloquantes.

POE::Wheel::SocketFactory - Création de sockets non bloquantes, prenant en charge la plupart des protocoles et des modes.

BOGUES

Il serait bien que les roues soient plus semblables à de vrais flux Unix.
