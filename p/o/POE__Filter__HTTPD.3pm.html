NOM

POE::Filter::HTTPD - analyse les requêtes HTTP simples et sérialise les réponses HTTP::Response

SYNOPHIS

#!perl
use warnings;
use strict;
use POE qw(Component::Server::TCP Filter::HTTPD);
use HTTP::Response;
POE::Component::Server::TCP->new(
  Port         => 8088,
  ClientFilter => 'POE::Filter::HTTPD',  ### <-- ICI NOUS SOMMES!
  ClientInput => sub {
    my $request = $_[ARG0];
    # C'est une réponse pour le client s'il y a eu un problème.
    if ($request->isa("HTTP::Response")) {
      my $response = $request;
      $request = $response->request;
      warn "ERREUR: ", $request->message if $request;
      $_[HEAP]{client}->put($response);
      $_[KERNEL]->yield("shutdown");
      return;
    }
    my $request_fields = '';
    $request->headers()->scan(
      sub {
        my ($header, $value) = @_;
        $request_fields .= (
          "<tr><td>$header</td><td>$value</td></tr>"
        );
      }
    );
    my $response = HTTP::Response->new(200);
    $response->push_header( 'Content-type', 'text/html' );
    $response->content(
      "<html><head><title>Votre Requête</title></head>" .
      "<body>Détails de votre requête:" .
      "<table border='1'>$request_fields</table>" .
      "</body></html>"
    );
    $_[HEAP]{client}->put($response);
    $_[KERNEL]->yield("shutdown");
  }
);
print "Pointez votre navigateur vers le port 8088 de cette machine.\n";
POE::Kernel->run();
exit;

DESCRIPTION

POE::Filter::HTTPD interprète les flux d'entrée comme des requêtes HTTP 0.9, 1.0 ou 1.1. Il retourne un objet HTTP::Request lors de l'analyse réussie d'une requête.

En cas d'échec, il retourne un objet HTTP::Response décrivant l'échec. L'intention est que le code applicatif remarque l'objet HTTP::Response et le renvoie sans traitement supplémentaire. L'objet de requête erroné est parfois disponible via la méthode "$r->request" dans HTTP::Response. Ceci est illustré dans le "SYNOPSIS".

Pour la sortie, POE::Filter::HTTPD accepte des objets HTTP::Response et retourne leurs flux correspondants.

Veuillez consulter HTTP::Request et HTTP::Response pour plus de détails sur l'utilisation de ces objets.

Les en-têtes HTTP ne sont pas autorisés à contenir de caractères UTF-8; ils doivent être en ISO-8859-1. POE::Filter::HTTPD convertira tout UTF-8 en son équivalent encodé MIME. Il utilise "utf8::is_utf8" pour la détection et Email::MIME::RFC2047::Encoder pour la conversion. Si utf8 n'est pas installé, aucune conversion n'a lieu. Si Email::MIME::RFC2047::Encoder n'est pas installé, "utf8::downgrade" est utilisé à la place. Dans ce dernier cas, vous verrez un avertissement si vous essayez d'envoyer des en-têtes UTF-8.

METHODES DU FILTRE PUBLIQUES

POE::Filter::HTTPD implémente l'interface POE::Filter de base.

new

new() accepte une liste de paramètres nommés.

"MaxBuffer" définit la quantité maximale de données que le filtre conservera en mémoire. Par défaut, 512 Mo (536870912 octets). Comme POE::Filter::HTTPD copie toutes les données en mémoire, définir ce nombre à une valeur élevée permettrait à un client HTTPD malveillant de remplir toute la mémoire et le swap du serveur.

"MaxContent" définit la taille maximale du contenu d'une requête HTTP. Par défaut, 1 Mo (1038336 octets). Comme POE::Filter::HTTPD copie toutes les données en mémoire, définir ce nombre à une valeur élevée permettrait à un client HTTPD malveillant de remplir toute la mémoire et le swap du serveur. Ignoré si "Streaming" est activé.

"Streaming" active le mode de flux de requêtes. Par défaut, il est désactivé. En mode flux, ce filtre retournera soit un objet HTTP::Request, soit un bloc de contenu. Le contenu de l'objet HTTP::Request sera vide. Les blocs de contenu seront des parties du corps de la requête, jusqu'à la taille spécifiée par Content-Length. Vous distinguez les objets de requête des blocs de contenu en utilisant "Scalar::Util/bless" (Voir "Requête en flux" ci-dessous). Cette option remplace "MaxContent".

MISE EN GARDE

Certaines versions de libwww sont connues pour générer du code HTTP invalide. Par exemple, ce code (adapté de la documentation de HTTP::Request::Common) provoquera une erreur dans un démon POE::Filter::HTTPD :

NOTE : L'utilisation de ce test avec libwww-perl/5.834 a montré qu'il ajoutait les données HTTP/1.1 appropriées ! Nous ne sommes pas sûrs de la version de LWP qui a corrigé cela. Cet exemple est valide pour les anciennes installations LWP, attention !

use HTTP::Request::Common;
use LWP::UserAgent;
my $ua = LWP::UserAgent->new();
$ua->request(POST 'http://example.com', [ foo => 'bar' ]);

Par défaut, HTTP::Request est agnostique à la version HTTP. Il ne fait aucune tentative pour ajouter un en-tête de version HTTP à moins que vous ne déclariez explicitement un protocole en utilisant "$request->protocol('HTTP/1.0')".

Selon la RFC 1.0 de HTTP (1945), en l'absence d'un en-tête de version HTTP, l'analyseur doit utiliser HTTP/0.9 par défaut. POE::Filter::HTTPD suit cette convention. Dans la transaction détaillée ci-dessus, le démon basé sur Filter::HTTPD retournera une erreur 400 car POST n'est pas un type de requête HTTP/0.9 valide.

Lors de la gestion d'une erreur de requête, il est plus rapide et plus fiable de répondre avec l'erreur et de fermer la connexion. Les requêtes HTTP invalides peuvent corrompre le flux de requêtes. Par exemple, l'absence d'un en-tête Content-Length signale qu'une requête n'a pas de contenu. Les requêtes avec du contenu mais sans cet en-tête seront décomposées en une requête sans contenu et des données invalides. Les données invalides peuvent également ressembler à une requête ! L'hilarité suivra, éventuellement de manière répétée, jusqu'à ce que le filtre puisse trouver la prochaine requête valide. En fermant la connexion au premier signe d'erreur, le client peut réessayer sa requête avec une connexion et un filtre propres.

Requête en flux

Normalement, POE::Filter::HTTPD lit l'intégralité du contenu de la requête en mémoire avant de retourner l'objet HTTP::Request à votre code. En mode flux, il retournera le contenu séparément, sous forme de scalaires non bénis. Le contenu peut être divisé en blocs de tailles variables, en fonction des contraintes du système d'exploitation et du transport. Votre code peut distinguer l'objet de requête des blocs de contenu en utilisant "blessed" dans Scalar::Util.

use Scalar::Util;
use POE::Wheel::ReadWrite;
use POE::Filter:HTTPD;
$heap->{wheel} = POE::Wheel::ReadWrite->new( 
                    InputEvent => 'http_input',
                    Filter => POE::Filter::HTTPD->new( Streaming => 1 ),
                    # ....
            );
sub http_input_handler
{
    my( $heap, $req_or_data ) = @_[ HEAP, ARG0 ];
    if( blessed $req_or_data ) {
        my $request = $req_or_data;
        if( $request->isa( 'HTTP::Response') ) {
            # Erreur HTTP
            $heap->{wheel}->put( $request );
        }
        else {
            # Requête HTTP
            # ....
        }
    }
    else {
        my $data = $req_or_data;
        # ....
    }
}

Vous pouvez trivialement créer un bug de déni de service si vous conservez tout le contenu en mémoire sans imposer de Content-Length maximum. Un attaquant pourrait envoyer "Content-Length: 1099511627776" (soit 1 To) et continuer à envoyer des données jusqu'à ce que toute la mémoire et le swap de votre système soient remplis.

Content-Length a été assaini par POE::Filter::HTTPD, donc sa vérification est triviale :

if( $request->headers( 'Content-Length' ) > 1024*1024 ) {
    my $resp = HTTP::Response->new( RC_REQUEST_ENTITY_TOO_LARGE ), 
                                         "Tellement de contenu !" ) 
    $heap->{wheel}->put( $resp );
    return;
}

Si vous souhaitez gérer de grandes quantités de données, vous devriez enregistrer le contenu dans un fichier avant de le traiter. Vous devez toujours vérifier Content-Length ou un attaquant pourrait remplir la partition.

use File::Temp qw(tempfile);
if( blessed $_[ARG0] ) {
    $heap->{request} = $_[ARG0];
    if( $heap->{request}->method eq 'GET' ) {
        handle_get( $heap );
        delete $heap->{request};
        return;
    }
    my( $fh, $file ) = tempfile( "httpd-XXXXXXXX", TMPDIR=>1 );
    $heap->{content_file} = $file;
    $heap->{content_fh} = $fh;
    $heap->{content_size} = 0;
}
else {
    return unless $heap->{request};
    $heap->{content_size} += length

Réponse en flux

Il est possible d'utiliser POE::Filter::HTTPD pour diffuser du contenu en flux, mais une application peut l'utiliser pour envoyer des en-têtes, puis passer à POE::Filter::Stream.

Depuis le gestionnaire d'entrée (le gestionnaire InputEvent si vous utilisez des roues, ou ClientInput pour POE::Component::Server::TCP) :

my $response = HTTP::Response->new(200);
$response->push_header('Content-type', 'audio/x-mpeg');
$_[HEAP]{client}->put($response);
$_[HEAP]{client}->set_output_filter(POE::Filter::Stream->new());

Ensuite, le gestionnaire de sortie vidée (FlushEvent pour POE::Wheel::ReadWrite, ou ClientFlushed pour POE::Component::Server::TCP) peut appeler put() des morceaux du flux selon les besoins.

my $bytes_read = sysread(
  $_[HEAP]{file_to_stream}, my $buffer = '', 4096
);
if ($bytes_read) {
  $_[HEAP]{client}->put($buffer);
}
else {
  delete $_[HEAP]{file_to_stream};
  $_[KERNEL]->yield("shutdown");
}

BOGUES

De nombreux aspects de HTTP 1.0 et supérieur ne sont pas pris en charge, tels que la connexion persistante (keep-alive). Un simple filtre d'E/S ne peut pas prendre en charge la connexion persistante, par exemple. Un certain nombre de serveurs HTTP POE plus riches en fonctionnalités sont disponibles sur CPAN. Voir <http://search.cpan.org/search?query=POE+http+server&mode=dist>
