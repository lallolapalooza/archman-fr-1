NOM

POE::Kernel - un noyau d'application événementiel en Perl

SYNOPSIS

use POE; # inclut automatiquement POE::Kernel et POE::Session
POE::Session->create(
  inline_states => {
    _start => sub { $_[KERNEL]->yield("next") },
    next   => sub {
      print "tick...\n";
      $_[KERNEL]->delay(next => 1);
    },
  },
);
POE::Kernel->run();
exit;

Dans l'esprit de Perl, il existe de nombreuses autres façons d'utiliser POE.

DESCRIPTION

POE::Kernel est le cœur de POE. Il fournit les fonctionnalités de plus bas niveau : l'I/O multiplexé non bloquant, les timers et les watchers de signaux sont les plus significatifs. Tout le reste est construit sur cette base.

POE::Kernel n'est pas une boucle d'événements en soi. Pour cela, il utilise l'un des plusieurs modules d'interface POE::Loop disponibles. Voir CPAN pour les modules dans l'espace de noms POE::Loop.

La documentation de POE suppose que le lecteur comprend les constantes de décalage de @_ (KERNEL, HEAP, ARG0, etc.). Le lecteur curieux ou confus trouvera des explications plus détaillées dans POE::Session.

UTILISATION DE POE

Utilisation littérale de POE

POE.pm n'est guère plus qu'un chargeur de classes. Il implémente une magie pour réduire le travail de configuration.

Les paramètres de "use POE" ne sont pas traités comme des importations normales. Plutôt, ce sont des modules abréviés à inclure avec POE.

use POE qw(Component::Client::TCP).

Comme vous pouvez le voir, le préfixe "POE::" peut être omis ainsi.

POE.pm inclut également POE::Kernel et POE::Session par défaut. Ces deux modules sont utilisés par presque tous les programmes basés sur POE. Ainsi, l'exemple ci-dessus est en fait l'équivalent de :

use POE;
use POE::Kernel;
use POE::Session;
use POE::Component::Client::TCP;

Utilisation de POE::Kernel

POE::Kernel doit savoir quel boucle d'événements vous voulez utiliser. Ceci est pris en charge de trois manières différentes :

La première façon est d'utiliser un module de boucle d'événements avant d'utiliser POE::Kernel (ou POE, qui charge POE::Kernel pour vous) :

use Tk; # ou l'un de plusieurs autres
use POE::Kernel.

POE::Kernel scanne la liste des modules déjà chargés et charge un adaptateur POE::Loop approprié s'il trouve une boucle d'événements connue.

La manière suivante est de charger explicitement la classe POE::Loop que vous voulez :

use POE qw(Loop::Gtk);

Enfin, l'import() de POE::Kernel prend en charge une configuration plus conviviale pour le programmeur :

use POE::Kernel { loop => "Gtk" };
use POE::Session;

Anatomie d'une application basée sur POE

Les programmes utilisant POE fonctionnent comme n'importe quels autres. Ils chargent les modules requis, effectuent une configuration, exécutent du code et finissent par se terminer. Sous réserve du problème de blocage.

Une application basée sur POE charge des modules, configure une ou plusieurs sessions, exécute le code de ces sessions et finit par se terminer.

use POE;
POE::Session->create( ... mapper les événements au code ici ... );
POE::Kernel->run();
exit;

Singleton de POE::Kernel

Le POE::Kernel est un objet singleton ; il ne peut y avoir qu'une seule instance de POE::Kernel dans un processus. Cela permet à de nombreuses méthodes d'objet d'être également des méthodes de paquet.

Sessions

POE implémente des compartiments isolés appelés sessions. Les sessions jouent le rôle de tâches ou de threads au sein de POE. POE::Kernel agit comme le planificateur de tâches de POE, distribuant des tranches de temps à chaque session en invoquant des rappels en leur sein.

Les rappels ne sont pas préemptifs. Tant qu'un est en cours d'exécution, aucun autre ne sera distribué. C'est ce qu'on appelle le multitâche coopératif. Chaque session doit coopérer en retournant au noyau de dispatching central.

Le multitâche coopératif simplifie grandement le partage de données, puisque deux morceaux de code ne peuvent pas modifier les données en même temps.

Une session peut également prendre le contrôle exclusif du temps d'un programme, si nécessaire, en ne revenant tout simplement pas dans un délai raisonnable. Il est même possible d'écrire des programmes complètement bloquants qui utilisent POE comme une machine à états plutôt qu'un répartiteur coopératif.

Chaque application basée sur POE nécessite au moins une session. Le code ne peut pas s'exécuter dans POE sans faire partie d'une session. De même, un programme multi-thread a toujours un "thread zéro".

Les sessions dans POE::Kernel ne doivent pas être confondues avec POE::Session, même si les deux sont inextricablement associés. POE::Session adapte le répartiteur de POE::Kernel à une convention d'appel particulière. D'autres classes POE::Session existent sur CPAN. Certaines modifient radicalement la façon dont les gestionnaires d'événements sont appelés. http://search.cpan.org/search?query=poe+session.

Ressources

Les ressources sont des événements et des choses qui peuvent créer de nouveaux événements, tels que des timers, des watchers d'E/S et même d'autres sessions.

POE::Kernel suit les ressources pour le compte de ses sessions actives. Il génère des événements correspondant à l'activité de ces ressources, notifiant les sessions lorsqu'il est temps de faire des choses.

La conversation ressemble à ceci :

Session: Fais-moi une faveur, Kernel, et fais-moi savoir quand quelqu'un clique
         sur ce widget. Merci beaucoup !
[LE TEMPS PASSE] [SFX: CLIC DE SOURIS]
Kernel: Très bien. Quelqu'un a cliqué sur votre widget.
        Voici.

De plus, comme le Kernel suit tout ce que font les sessions, il sait quand une session n'a plus de tâches à accomplir. Lorsque cela se produit, le Kernel émet un événement "_stop" à la session moribonde afin qu'elle puisse se nettoyer et s'arrêter.

Kernel: Veuillez éteindre les lumières et fermer à clé ; il est temps de partir.

De même, si une session s'arrête d'elle-même et qu'il reste des watchers de ressources ouverts, le Kernel en est conscient et les nettoie pour le compte de la session. POE excelle dans les services de longue durée car il suit et nettoie méticuleusement les ressources.

POE::Resources et les classes POE::Resource implémentent chaque type de ressource, qui sont résumés ici et couverts plus en détail plus tard.

Événements.
Un événement est un message à une session. Poster un événement maintient à la fois l'expéditeur et le destinataire en vie jusqu'après que l'événement ait été distribué. Ceci n'est garanti que si l'expéditeur et le destinataire sont dans le même processus. Les modules complémentaires de passage de messages inter-Kernel peuvent avoir d'autres garanties. Veuillez consulter leur documentation pour plus de détails.

La raison est que l'événement est en jeu, donc le destinataire doit rester actif pour qu'il soit distribué. L'expéditeur reste en vie au cas où le destinataire souhaiterait renvoyer une réponse.

Les événements postés ne peuvent pas être annulés de manière préemptive. Ils ont tendance à être de courte durée en pratique, donc ce n'est généralement pas un problème.

Timers.
Les timers permettent à une application d'envoyer un message au futur. Une fois défini, un timer maintiendra la session de destination active jusqu'à ce qu'il se déclenche et que l'événement résultant soit distribué.
Alias.
Les alias de session sont un moyen contrôlé par l'application pour s'adresser à une session. Les alias agissent comme des watchers d'événements passifs. Tant qu'une session a un alias, une autre session peut lui envoyer des événements par ce nom. Les alias maintiennent les sessions en vie tant qu'un processus a des sessions actives.

Si les seules sessions restantes sont maintenues en vie uniquement par leurs alias, POE::Kernel leur enverra un signal terminal "IDLE" (inactif). Dans la plupart des cas, cela terminera les sessions restantes et permettra au programme de se terminer. Si les sessions restent en mémoire sans se réveiller au signal "IDLE", POE::Kernel leur envoie un signal "ZOMBIE" non masquable. Elles sont alors supprimées de force, et le programme se terminera enfin.

Watchers d'E/S.
Une session restera active tant qu'une session surveillera

Durées de vie de session

Durées de vie de session

"Session" en tant que terme est un peu ambigu. Il existe deux concepts connexes qui partagent le même nom. Premièrement, il y a la classe POE::Session, et les objets créés avec elle ou des classes apparentées. Deuxièmement, il y a une structure de données au sein de POE::Kernel qui suit les objets POE::Session en cours d'utilisation et les ressources que chacun possède.

La façon dont fonctionne le ramasse-miettes de POE est qu'un objet de session est remis à POE::Kernel au moment de sa création. Le Kernel conserve ensuite cet objet tant qu'il existe des ressources qui nécessitent que la session reste active. Lorsque toutes ces ressources sont détruites ou libérées, l'objet de session n'a plus rien à activer. POE::Kernel en informe l'objet via lui-même, et nettoie son contexte interne de session. L'objet de session est libéré, et est normalement libéré de la manière Perl.

Les sessions peuvent être arrêtées même si elles ont des ressources actives. Par exemple, une session peut échouer à gérer un signal terminal. Dans ce cas, POE::Kernel force l'arrêt de la session, et toutes les ressources associées à la session sont préalablement libérées.

Événements

Un événement est un message envoyé d'une partie de l'application POE à une autre. Un événement se compose du nom de l'événement, de paramètres spécifiques à l'événement et d'informations OOB. Un événement peut être envoyé par le noyau, par un rotor ou par une session.

Une application crée un événement avec "post", "yield", "call" ou même "signal". POE::Kernel crée des événements en réponse à des stimuli externes (signaux, select, etc.).

Gestionnaires d'événements

Un événement est géré par une fonction appelée gestionnaire, qui est un code désigné pour être appelé lorsqu'un événement spécifique est déclenché. Voir "Gestion des gestionnaires d'événements" et POE::Session.

Le terme état est souvent utilisé à la place de gestionnaire, en particulier lorsqu'il s'agit de sessions en tant que machines à états pilotées par événements.

Les gestionnaires sont toujours appelés dans un contexte scalaire pour les événements asynchrones (c'est-à-dire via post()). Les événements synchrones, invoqués avec call(), sont gérés dans le même contexte que celui dans lequel call() a été appelé.

Les gestionnaires ne peuvent pas renvoyer de références à des objets dans l'espace de noms "POE". POE::Kernel les stringifie pour éviter les problèmes d'exécution avec la destruction de certains objets. Par exemple, ce gestionnaire d'erreur provoquerait des erreurs car un rotor supprimé ne serait pas détruit comme on pourrait s'y attendre:

sub handle_error {
  warn "Got an error";
  delete $_[HEAP]{wheel};
}

L'appel delete() renvoie le membre supprimé du rotor, qui est ensuite renvoyé implicitement par handle_error().

Utilisation de POE avec d'autres boucles d'événements

POE::Kernel prend en charge n'importe quel nombre de boucles d'événements. Deux sont incluses dans la distribution de base. Historiquement, POE incluait d'autres boucles mais les a déplacées vers une distribution séparée. Vous pouvez les trouver ainsi que d'autres boucles sur CPAN.

Les interfaces publiques de POE restent les mêmes, quelle que soit la boucle d'événements utilisée. Les principales bibliothèques graphiques incluant certains types de boucles d'événements, le code backend doit être portable sur toutes.

La coopération de POE avec d'autres boucles d'événements permet d'intégrer POE dans d'autres logiciels. La boucle d'événements commune sous-jacente contrôle à la fois l'application et POE. Par exemple, en utilisant POE::Component::Client::HTTP (et tout le reste), on peut intégrer POE dans Vim, irssi et d'autres. Les scripts d'application peuvent tirer parti de POE::Component::Client::HTTP (et de tout le reste) pour effectuer des travaux à grande échelle sans bloquer le reste du programme.

Comme il s'agit de Perl, il existe plusieurs façons de charger une boucle d'événements alternative. La méthode la plus simple consiste à charger la boucle d'événements avant de charger POE::Kernel.

use Gtk;
use POE;

N'oubliez pas que POE charge POE::Kernel en interne.

POE::Kernel examine les modules chargés avant lui et détecte que Gtk a été chargé. Si POE::Loop::Gtk est disponible, POE le charge et le connecte automatiquement à POE::Kernel.

Il est moins mystérieux de charger directement la classe correspondante de POE::Loop. Son nom suit le format "POE::Loop::$loop_module_name", où $loop_module_name est le nom du module de boucle après que chaque "::" ait été remplacé par un trait d'union. Il peut être abrégé en utilisant la magie du chargeur de POE.

use POE qw( Loop::Event_Lib );

POE reconnaît également les boucles XS, qui se trouvent dans l'espace de noms "POE::XS::Loop::$loop_module_name". Les utiliser peut améliorer les performances de votre plateforme, car les boucles d'événements sont parmi les codes les plus sollicités du système. Comme toujours, testez votre application avec plusieurs boucles pour voir laquelle convient le mieux à votre charge et à votre plateforme.

use POE qw( XS::Loop::EPoll );

Ne chargez pas les modules de boucle directement, car POE n'aura pas la possibilité d'initialiser ses structures internes. Le code écrit ainsi générera des erreurs au démarrage. Bien que cela puisse ressembler à un bug dans POE, c'est simplement la façon dont POE est conçu.

use POE::Loop::IO_Poll;
use POE;

POE::Kernel prend également en charge les directives de configuration dans sa propre ligne "use". Une boucle spécifiée de cette manière remplacera la logique de recherche.

use POE::Kernel { loop => "Glib" };

Enfin, vous pouvez spécifier la classe de la boucle via la variable d'environnement POE_EVENT_LOOP. Ce mécanisme a été ajouté pour les tests qui nécessitent de spécifier la boucle à distance.

BEGIN { $ENV{POE_EVENT_LOOP} = "POE::XS::Loop::Poll" }
use POE;

Clairement, cela peut également être défini depuis votre shell :

% export POE_EVENT_LOOP='POE::XS::Loop::Poll'
% make test

De nombreuses boucles d'événements externes prennent en charge leurs propres mécanismes de rappel. Les méthodes postback() et callback() de POE::Session renvoient du code Perl simple qui génère des événements POE lorsqu'il est appelé. Les applications peuvent passer ces références de code aux boucles d'événements pour les utiliser comme rappels.

La distribution POE inclut deux interfaces de boucles d'événements. CPAN en propose plusieurs autres :

POE::Loop::Select (inclus)

Par défaut, POE utilise sa boucle select() pour gérer son système d'événements. Cela peut être le plus inefficace, mais aussi le plus portable. POE optimise pour la correction dans tout ce qu'il peut.

POE::Loop::IO_Poll (inclus)

La boucle IO::Poll fournit une alternative qui, théoriquement, est plus évolutive que select().

POE::Loop::Event (séparé)

Cette boucle d'événements assure l'interopérabilité avec les modules utilisant Event. Elle peut également améliorer les performances car Event est écrit dans un langage compilé. Cependant, cela rend Event moins portable que le select() intégré de Perl.

POE::Loop::Gtk (séparé)

Cette boucle d'événements permet aux programmes de fonctionner sous la bibliothèque graphique Gtk.

POE::Loop::Tk (séparé)

Cette boucle d'événements permet aux programmes de fonctionner sous la bibliothèque graphique Tk. Tk a quelques restrictions qui obligent POE à agir de manière inhabituelle.

La boucle d'événements Tk ne s'exécutera pas tant qu'au moins un widget n'aura pas été créé. Par conséquent, POE doit créer un tel widget avant de pouvoir s'exécuter. POE::Kernel expose $poe_main_window pour que le développeur de l'application puisse utiliser le widget (qui est une fenêtre principale), puisque POE n'en a pas besoin pour autre chose que pour déclencher des événements.

La création et l'utilisation d'une fenêtre principale différente ont généralement un résultat indésirable.

POE::Loop::EV (séparé)

POE::Loop::EV permet aux programmes basés sur POE d'utiliser la bibliothèque EV avec peu ou pas de modifications.

POE::Loop::Glib (séparé)

POE::Loop::Glib permet aux programmes basés sur POE d'utiliser Glib avec peu ou pas de modifications. Il prend également en charge l'intégration de programmes basés sur POE dans des applications utilisant déjà Glib. Par exemple, on rapporte que POE a pu être intégré dans Vim, irssi et xchat via cette boucle.

POE::Loop::Kqueue (séparé)

POE::Loop::Kqueue permet aux programmes basés sur POE d'utiliser de manière transparente la bibliothèque d'événements kqueue des systèmes qui la prennent en charge.

POE::Loop::Prima (séparé)

POE::Loop::Prima permet aux programmes basés sur POE d'utiliser la boucle Prima avec peu ou pas de modifications. Elle permet aux bibliothèques POE d'être utilisées dans des applications Prima.

POE::Loop::Wx (séparé)

POE::Loop::Wx permet aux programmes basés sur POE d'utiliser la boucle Wx avec peu ou pas de modifications. Elle permet aux bibliothèques POE d'être utilisées dans des applications Wx, comme Padre.

POE::XS::Loop::EPoll (séparé)

POE::XS::Loop::EPoll permet aux composants POE d'utiliser de manière transparente la bibliothèque EPoll des systèmes qui la prennent en charge.

POE::XS::Loop::Poll (séparé)

POE::XS::Loop::Poll est une boucle d'événements plus rapide basée sur C. Elle remplace une partie du code Perl sollicité par du C pour améliorer les performances.

Autres boucles d'événements (séparées)

POE peut être étendu pour gérer d'autres boucles d'événements. Les développeurs sont invités à collaborer avec nous pour prendre en charge leurs boucles préférées.

MÉTODOS PÚBLICOS

POE::Kernel encapsula una gran cantidad de características. La documentación para cada conjunto de características se agrupa por propósito.

Gestión y Acceso del Kernel

ID

ID() actualmente devuelve el identificador único de POE::Kernel. Cada instancia de Kernel se asigna un identificador único globalmente al nacer. has_forked() altera este identificador para que cada proceso hijo tenga uno único.

% perl -wl -MPOE -e 'print $poe_kernel->ID'
macbookpoe.local-4d5305de-0000e6b8-00000001

El contenido de estos identificadores puede cambiar con el tiempo. Tu código no debe depender del formato actual.

Advertencia de Deprecación 2011-02-09

Tu código no debe depender de que ID() permanezca único. La unicidad será eliminada en una futura versión de POE. Si necesitas identificadores únicos, consulta uno de los módulos de CPAN con GUID o UUID:

http://search.cpan.org/search?query=GUID&mode=dist
http://search.cpan.org/search?query=UUID&mode=dist

POE no requiere identificadores globales o universales de kernel. La creación y mantenimiento de estos identificadores añade sobrecarga al método has_forked() de POE::Kernel. Otros módulos lo hacen mejor, bajo demanda, sin incurrir en sobrecarga para quienes no lo necesitan.

run

run() ejecuta el despachador de eventos de POE::Kernel. No retornará hasta que todas las sesiones hayan terminado. run() es un método de clase, por lo que no se necesita una referencia a POE::Kernel para iniciar la ejecución de un programa.

use POE;
POE::Session->create( ... ); # una o más
POE::Kernel->run();          # inician todas las sesiones
exit;

POE implementa el patrón Reactor en su núcleo. Los eventos se envían a funciones y métodos mediante callbacks. El código detrás de run() espera y dispara eventos.

run() no retornará hasta que todas las sesiones hayan terminado. Esto incluye sesiones creadas durante el tiempo que run() esté ejecutándose.

POE::Kernel imprimirá un mensaje fuerte si un programa crea sesiones pero no llama a run(). Antes de este aviso, recibimos muchos informes de errores como "mi programa POE no hace nada". Esto se debió a que las personas olvidaron iniciar un despachador de eventos, por lo que los eventos nunca se envían.

Si no se llama a run(), es intencional, posiblemente porque otro bucle de eventos ya tiene el control, puedes evitar el mensaje llamando a run() antes de crear una sesión. run() en ese momento inicia POE y retorna inmediatamente. POE::Kernel sentirá que run() fue llamado, aunque POE no haya tomado realmente el control del bucle de eventos.

use POE;
POE::Kernel->run(); # silenciar el aviso
POE::Session->create( ... );
exit;

Sin embargo, esta variación depende del bucle de eventos. Si una implementación específica de POE::Loop no lo soporta, probablemente sea un error. Por favor, envía un informe de error al propietario del módulo correspondiente de POE::Loop.

run_one_timeslice

run_one_timeslice() dispara cualquier evento que deba ser enviado. Estos eventos incluyen temporizadores, mensajes asíncronos que deban ser enviados, señales que requieren manejo y notificaciones de archivos con I/O pendiente. No debes depender demasiado del orden de los eventos. run_one_timeslice() está definido por el bucle de eventos subyacente, y su tiempo puede variar.

run() se implementa de forma similar a:

run_one_timeslice() while $session_count > 0;

run_one_timeslice() puede usarse para mantener ejecutando el despachador de POE::Kernel mientras emulas comportamiento bloqueante. El patrón se implementa con un flag que se establece cuando ocurre un evento asíncrono. Un bucle llama a run_one_timeslice() hasta que ese flag esté establecido. Por ejemplo:

my $done = 0;
sub handle_some_event {
  $done = 1;
}
$kernel->run_one_timeslice() while not $done;

Debes tener cuidado. El ejemplo anterior se ejecutará en un bucle infinito si POE::Kernel está terminado pero $done nunca se establece. El bucle nunca terminará, aunque no haya nada más que establezca $done.

run_while SCALAR_REF

run_while() es una versión experimental de run_one_timeslice() que solo retorna cuando no hay más sesiones activas, o el valor del escalar referenciado se vuelve falso.

Aquí hay un ejemplo de run_one_timeslice() usando run_while():

my $job_count = 3;
sub handle_some_event {
  $job_count--;
}
$kernel->run_while(\$job_count);

has_forked

my $pid = fork();
die "Unable to fork" unless defined $pid;
unless( $pid ) {
    $poe_kernel->has_forked;
}

Informa al kernel que ahora está ejecutándose en un nuevo proceso. Esto permite al kernel restablecer algunos datos internos para ajustarse al nuevo estado.

has_forked() debe ser llamado en el proceso hijo si quieres ejecutar el mismo kernel. Sin embargo, si deseas que el proceso hijo tenga un nuevo kernel, debes llamar a stop en su lugar.

Nota: Las internas de POE detectarán si un fork ocurrió antes de run() y llamarán has_forked() automáticamente. Si no estás seguro de si debes llamarlo o no, activa ASSERT_USAGE y POE emitirá una advertencia si es necesario.

stop

stop() hace que run() de POE::Kernel retorne anticipadamente. Lo hace vaciando la cola de eventos, liberando recursos utilizados y deteniendo todas las sesiones activas. stop() no debe usarse a la ligera. Presta atención.

Advertencias:

La sesión que llama a stop() no será completamente destruida hasta que retorne. Invocar un manejador de eventos en la sesión requiere una referencia a esa sesión, y en POE se prohíben las referencias débiles por razones de compatibilidad. Por lo tanto, la última sesión no será recolectada de inmediato.

Las sesiones no son notificadas de su destrucción. Si algo depende de que se envíe _stop, fallará o dejará de liberar memoria.

stop() sigue siendo experimental. Fue añadido para mejorar el soporte de fork() en POE::Wheel::Run. Si es inutilizable, será eliminado sin previo aviso.

stop() es magia avanzada. Se invita a los programadores que sientan la necesidad de usarlo a familiarizarse con su código fuente.

Ver "Uso de POE::Kernel en el hijo" en POE::Wheel::Run para un ejemplo de cómo usar esta función.

Mensajes Asíncronos (Eventos FIFO)

Los mensajes asíncronos son eventos que se envían en el orden en que se pusieron en cola (primero en entrar, primero en salir, conocido como FIFO). Estos métodos ponen en cola nuevos mensajes para ser enviados. La acción de poner en cola un mensaje mantiene vivo al remitente del mensaje al menos hasta que el mensaje sea enviado.

post DESTINATION, EVENT_NAME [, PARAMETER_LIST]

post() pondrá en cola un mensaje para ser enviado a una sesión DESTINATION específica. El mensaje será procesado por el código asociado con EVENT_NAME. Si se incluye un PARAMETER_LIST, sus valores también se pasarán.

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[KERNEL]->post( $_[SESSION], "event_name", 0 );
    },
    event_name => sub {
      print "$_[ARG0]\n";
      $_[KERNEL]->post( $_[SESSION], "event_name", $_[ARG0] + 1 );
    },
  }
);

post() devuelve un valor booleano que indica si el mensaje se puso en cola correctamente. Si post() devuelve falso, $! se establece para explicar el fallo:

ESRCH ("No such process") - La sesión DESTINATION no existía en el momento de la llamada a post().

yield EVENT_NAME [, PARAMETER_LIST]

yield() es una forma corta de post() donde la sesión DESTINATION es la misma que la remitente. Este ejemplo es equivalente al de post():

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[KERNEL]->yield( "event_name", 0 );
    },
    event_name => sub {
      print "$_[ARG0]\n";
      $_[KERNEL]->yield( "event_name", $_[ARG0] + 1 );
    },
  }
);

Como con post(), yield() devuelve inmediatamente, y el evento EVENT_NAME puesto en cola se dispara más tarde. Esto puede ser confuso si ya estás familiarizado con los hilos.

yield() siempre debe tener éxito, por lo que no devuelve un valor significativo.

Mensajes Síncronos

A veces es necesario invocar código inmediatamente. Por ejemplo, algunos recursos deben ser atendidos inmediatamente o de lo contrario informarán su preparación como una serie de eventos duplicados. Estos informes aparecerían como un flujo de eventos duplicados. Los eventos asíncronos también pueden evitar que los datos sean stale entre el momento en que un evento se pone en cola y el momento en que se envía.

Los manejadores de eventos asíncronos priorizan la cola de eventos de POE, por lo que deben realizar tareas simples de duración limitada. Los eventos asíncronos que necesiten más que solo atender un recurso deben pasar información sobre el recurso a un manejador asíncrono. De lo contrario, las operaciones asíncronas ocurren en orden inverso a los eventos asíncronos. Es muy fácil tener conflictos de tiempo o romper la causalidad de esta manera, así que evita hacerlo, a menos que estés dispuesto a las consecuencias.

POE ofrece estas formas de invocar manejadores de mensajes inmediatamente.

call DESTINATION, EVENT_NAME [, PARAMETER_LIST]

call() tiene semánticas casi idénticas a post(). call() invoca el manejador de una sesión DESTINATION asociado con EVENT_NAME. Se pasa un LISTA de parámetros opcional al manejador del mensaje. La diferencia es que el manejador se invoca inmediatamente, incluso antes de que call() devuelva su valor.

call() devuelve el valor devuelto por el manejador de EVENT_NAME. Esto es posible porque el manejador se invoca antes de que call() devuelva su valor. Por lo tanto, call() puede usarse como un accesor, aunque hay mejores formas de lograr un comportamiento de accesor simple.

POE::Session->create(
  inline_states => {
    _start => sub {
      print "Got: ", $_[KERNEL]->call($_[SESSION], "do_now"), "\n";
    },
    do_now => sub {
      return "some value";
    }
  }
);

call() peut échouer de la même manière et pour les mêmes raisons que post(). En cas d'échec, $! est défini sur une valeur non nulle indiquant la raison. Étant donné que call() peut retourner undef de manière habituelle, il est recommandé de vérifier $! pour la condition d'erreur ainsi que son explication.

ESRCH ("No such process") - La session DESTINATION n'existait pas au moment de l'appel à post().

Événements de Timer (Messages Différés)

Il est souvent utile d'attendre une période spécifique ou jusqu'à ce qu'un certain moment soit passé. POE le supporte avec des événements qui sont programmés pour s'exécuter après un temps absolu ("alarms") ou après une certaine durée ("delays").

Les interfaces de timer sont divisées en deux groupes. L'un identifie les timers par les noms de leurs événements associés. L'autre identifie les timers par un identifiant unique retourné par les constructeurs de timer. Techniquement, les deux sont basés sur le nom, mais les timers basés sur des identifiants fournissent un second niveau de gestion plus spécifique pour identifier des timers individuels.

Les timers ne peuvent être configurés que pour la session actuelle. Cette conception était basée sur alarm() et SIGALRM, qui n'affectent que le processus UNIX actuel. Chaque session a son propre espace de noms de timers. Les méthodes de timer appelées dans une session n'affectent pas les timers des autres sessions. Comme vous l'avez peut-être remarqué, une grande partie de l'API de POE est conçue pour empêcher les sessions d'interférer les unes avec les autres.

La meilleure façon de simuler des messages différés échangés entre sessions est d'envoyer un message immédiat qui amène la destination à définir un timer. Le timer de la destination diffère alors l'action demandée. Cette approche est préférée car le temps nécessaire pour communiquer la demande entre les sessions peut ne pas être négligeable, surtout si les sessions sont séparées par un réseau. La session peut déterminer combien de temps il reste avant que le timer demandé ne s'exécute et ajuster son délai d'attente en conséquence.

Timers Basés sur le Nom

Les timers basés sur le nom sont identifiés par les noms d'événements utilisés pour les créer. Il est possible que différentes sessions utilisent le même nom d'événement, car chaque session est un espace de noms séparé avec son propre espace de noms de timers. Il est possible qu'une session ait plusieurs timers pour un événement donné, mais les résultats peuvent être surprenants. Il faut veiller à utiliser correctement les méthodes de timer.

Les méthodes de timer basées sur le nom sont alarm(), alarm_add(), delay() et delay_add().

alarm EVENT_NAME [, EPOCH_TIME [, PARAMETER_LIST] ]

alarm() supprime tous les timers existants dans la même session avec le même EVENT_NAME. Il définit ensuite un nouveau timer, avec le même nom EVENT_NAME, qui se déclenchera lorsque EPOCH_TIME sera atteint. Un paramètre OPTIONNEL peut être passé au gestionnaire de timer.

Omettre EPOCH_TIME et les paramètres suivants fait que alarm() supprime les timers EVENT_NAME dans la même session sans en définir de nouveau.

EPOCH_TIME est le temps epoch UNIX. C'est-à-dire, le nombre de secondes depuis 00:00 le 1er janvier 1970. POE utilise Time::HiRes::time(), ce qui permet à EPOCH_TIME d'être (ou d'inclure) des secondes fractionnaires.

POE supporte les secondes fractionnaires, mais la précision diminue rapidement après 1/100 de seconde. La dégradation variera en fonction de votre vitesse de CPU et de la résolution du système d'exploitation.

Assurez-vous d'utiliser Time::HiRes::time() au lieu de la fonction intégrée time() de Perl si la précision sub-seconde est importante. La fonction intégrée time() retourne le floor() de Time::HiRes::time(), qui est presque toujours une fraction de seconde dans le passé. Par exemple, l'heure haute résolution pourrait être 1200941422.89996. Au même instant, time() serait 1200941422. Une alarme pour time() + 0.5 serait 0.39996 secondes dans le passé, elle serait donc déclenchée immédiatement (voire plus tôt).

La file d'attente d'événements de POE est triée par heure, donc un timer dû avant time() sera délivré avant d'autres événements mais pas avant les timers dont l'heure d'échéance est plus ancienne. Par conséquent, un alarm() avec un EPOCH_TIME antérieur à time() sera déclenché au début de la file d'attente.

Tous les timers sont implémentés de manière identique, quelle que soit la méthode de configuration. alarm() se comportera donc de manière non souciée en supprimant les timers définis par d'autres moyens.

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[KERNEL]->alarm( tick => time() + 1, 0 );
    },
    tick => sub {
      print "tick $_[ARG0]\n";
      $_[KERNEL]->alarm( tock => time() + 1, $_[ARG0] + 1 );
    },
    tock => sub {
      print "tock $_[ARG0]\n";
      $_[KERNEL]->alarm( tick => time() + 1, $_[ARG0] + 1 );
    },
  }
);

alarm() retourne 0 en cas de succès ou une valeur vraie en cas d'échec. Généralement EINVAL pour un paramètre invalide, comme un événement EVENT_NAME invalide.

alarm_add EVENT_NAME, EPOCH_TIME [, PARAMETER_LIST]

alarm_add() est utilisé pour ajouter un nouveau timer d'alarme nommé EVENT_NAME sans supprimer les timers existants. EPOCH_TIME est un paramètre obligatoire. Sinon, la signification est identique à alarm().

Un programme peut utiliser alarm_add() sans utiliser préalablement alarm().

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[KERNEL]->alarm_add( tick => time() + 1.0, 1_000_000 );
      $_[KERNEL]->alarm_add( tick => time() + 1.5, 2_000_000 );
    },
    tick => sub {
      print "tick $_[ARG0]\n";
      $_[KERNEL]->alarm_add( tock => time() + 1, $_[ARG0] + 1 );
    },
    tock => sub {
      print "tock $_[ARG0]\n";
      $_[KERNEL]->alarm_add( tick => time() + 1, $_[ARG0] + 1 );
    },
  }
);

alarm_add() retourne 0 en cas de succès ou EINVAL si EVENT_NAME ou EPOCH_TIME est indéfini.

delay EVENT_NAME [, DURATION_SECONDS [, PARAMETER_LIST] ]

delay() supprime tous les timers existants dans la même session avec le même EVENT_NAME. Il définit ensuite un nouveau timer, avec le même nom EVENT_NAME, qui se déclenchera lorsque DURATION_SECONDS se seront écoulés à partir de maintenant. Un paramètre OPTIONNEL peut être passé au gestionnaire de timer.

Omettre DURATION_SECONDS et les paramètres suivants fait que delay() supprime les timers EVENT_NAME dans la même session sans en définir de nouveau.

DURATION_SECONDS peut être ou inclure des secondes fractionnaires. Comme pour tous les timers POE, la précision diminue rapidement après 1/100 de seconde. La dégradation variera en fonction de votre vitesse de CPU et de la résolution du système d'exploitation.

La file d'attente d'événements de POE est triée par heure, donc un timer dû avant time() sera délivré avant d'autres événements mais pas avant les timers dont l'heure d'échéance est plus ancienne. Par conséquent, un delay () avec une DURATION_SECONDS de 0 ou négative sera déclenché au début de la file d'attente.

delay() peut être considéré comme un raccourci pour alarm(), mais il existe des différences subtiles en matière de chronométrage. Ce code est à peu près équivalent à l'exemple alarm().

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[KERNEL]->delay( tick => 1, 0 );
    },
    tick => sub {
      print "tick $_[ARG0]\n";
      $_[KERNEL]->delay( tock => 1, $_[ARG0] + 1 );
    },
    tock => sub {
      print "tock $_[ARG0]\n";
      $_[KERNEL]->delay( tick => 1, $_[ARG0] + 1 );
    },
  }
);

delay() retourne 0 en cas de succès ou un motif d'échec : EINVAL si EVENT_NAME est indéfini.

delay_add EVENT_NAME, DURATION_SECONDS [, PARAMETER_LIST]

delay_add() est utilisé pour ajouter un nouveau timer de délai nommé EVENT_NAME sans supprimer les timers existants. DURATION_SECONDS est un paramètre obligatoire. Sinon, la signification est identique à delay().

Un programme peut utiliser delay_add() sans utiliser préalablement delay().

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[KERNEL]->delay_add( tick => 1.0, 1_000_000 );
      $_[KERNEL]->delay_add( tick => 1.5, 2_000_000 );
    },
    tick => sub {
      print "tick $_[ARG0]\n";
      $_[KERNEL]->delay_add( tock => 1, $_[ARG0] + 1 );
    },
    tock => sub {
      print "tock $_[ARG0]\n";
      $_[KERNEL]->delay_add( tick => 1, $_[ARG0] + 1 );
    },
  }
);

delay_add() retourne 0 en cas de succès ou EINVAL si EVENT_NAME ou DURATION_SECONDS est indéfini.

Timers Basés sur l'Identifiant

Une autre façon de gérer les timers est par le biais des identifiants. Définir une alarme ou un délai avec les méthodes d'"identifiant" permet à un programme de manipuler plusieurs timers portant le même nom dans la même session. Bien que couvert dans alarm() et delay(), il est possible de mélanger les appels aux timers nommés et identifiés, mais les conséquences ne sont pas toujours attendues.

alarm_set EVENT_NAME, EPOCH_TIME [, PARAMETER_LIST]

alarm_set() définit une alarme, retournant un identifiant unique qui peut être utilisé pour ajuster ou supprimer l'alarme plus tard. Bien que alarm() ne supprime pas les timers portant le même EVENT_NAME au préalable, la signification est identique à alarm().

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[HEAP]{alarm_id} = $_[KERNEL]->alarm_set(
        party => time() + 1999
      );
      $_[KERNEL]->delay(raid => 1);
    },
    raid => sub {
      $_[KERNEL]->alarm_remove( delete $_[HEAP]{alarm_id} );
    },
  }
);

alarm_set() retourne false en cas d'échec et définit $! avec l'explication. $! sera EINVAL si EVENT_NAME ou TIME est indéfini.

alarm_adjust ALARM_ID, DELTA_SECONDS

alarm_adjust() ajuste l'heure d'échéance d'un timer existant de DELTA_SECONDS, qui peut être positif ou négatif. Il peut même être zéro, bien que ce ne soit pas très utile. En cas de succès, il retourne la nouvelle heure d'échéance depuis le début de l'epoch UNIX.

Il est possible d'ajuster les timers créés avec delay_set() et alarm_set().

Cet exemple déplace une alarme 10 secondes plus tôt.

use POSIX qw(strftime);
POE::Session->create(
  inline_states => {
    _start => sub {
      $_[HEAP]{alarm_id} = $_[KERNEL]->alarm_set(
        party => time() + 1999
      );
      $_[KERNEL]->delay(postpone => 1);
    },
    postpone => sub {
      my $new_time = $_[KERNEL]->alarm_adjust(
        $_[HEAP]{alarm_id}, -10
      );
      print(
        "Now we're gonna party like it's ",
        strftime("%F %T", gmtime($new_time)), "\n"
      );
    },
  }
);

alarm_adjust() retourne un booléen false en cas d'échec, définissant $! avec la raison. $! peut être EINVAL si ALARM_ID ou DELTA_SECONDS est indéfini. Il peut également être ESRCH si ALARM_ID ne fait plus référence à un timer en attente. $! peut également contenir EPERM si ALARM_ID est valide mais appartient à une autre session.

alarm_remove ALARM_ID

alarm_remove() supprime l'alarme identifiée par ALARM_ID. ALARM_ID provient d'un appel précédent à alarm_set() ou delay_set().

En cas de succès, alarm_remove() renvoie une valeur vraie en fonction de son contexte. Dans un contexte de liste, il renvoie trois choses : le nom de l'événement de l'alarme supprimée, l'heure UNIX à laquelle elle devait se déclencher, et une référence à la PARAMETER_LIST (le cas échéant) assignée au minuteur lors de sa création. Si nécessaire, le minuteur peut être reconfiguré avec ces informations.

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[HEAP]{alarm_id} = $_[KERNEL]->alarm_set(
        party => time() + 1999
      );
      $_[KERNEL]->delay(raid => 1);
    },
    raid => sub {
      my ($name, $time, $param) = $_[KERNEL]->alarm_remove(
        $_[HEAP]{alarm_id}
      );
      print(
        "Alarme supprimée pour l'événement $name prévu à $time avec @$param\n"
      );
      # Ou le réinitialiser, si vous le souhaitez. Peut-être après modification.
      $_[KERNEL]->alarm_set($name, $time, @$param);
    },
  }
);

Dans un contexte scalaire, il renvoie une référence à une liste des trois éléments ci-dessus.

# Supprimer et réinitialiser une alarme.
my $alarm_info = $_[KERNEL]->alarm_remove( $alarm_id );
my $new_id = $_[KERNEL]->alarm_set(
  $alarm_info[0], $alarm_info[1], @{$alarm_info[2]}
);

Cependant, en cas d'échec, alarm_remove() renvoie une valeur fausse booléenne et définit $! avec la raison de l'échec de l'appel :

EINVAL ("Argument invalide") indique un problème avec un ou plusieurs paramètres, généralement un ALARM_ID indéfini.

ESRCH ("Aucun processus de ce type") indique que ALARM_ID ne faisait pas référence à une alarme en attente.

EPERM ("Opération non autorisée"). Une session ne peut pas supprimer une alarme dont elle n'est pas propriétaire.

alarm_remove_all

alarm_remove_all() supprime tous les minuteurs en attente pour la session courante, indépendamment de la méthode de création ou du type. Cette méthode ne prend aucun argument. Elle renvoie des informations sur les alarmes qui ont été supprimées, soit sous forme de liste d'alarmes, soit sous forme de référence de liste selon que alarm_remove_all() est appelée dans un contexte scalaire ou de liste.

Les informations de chaque alarme supprimée sont identiques au format expliqué dans alarm_remove().

sub some_event_handler {
  my @removed_alarms = $_[KERNEL]->alarm_remove_all();
  foreach my $alarm (@removed_alarms) {
    my ($name, $time, $param) = @$alarm;
    ...;
  }
}

delay_set EVENT_NAME, DURATION_SECONDS [, PARAMETER_LIST]

delay_set() définit un minuteur pour DURATION_SECONDS dans le futur. Le minuteur sera envoyé au code associé à EVENT_NAME dans la session courante. Une PARAMETER_LIST optionnelle sera transmise au gestionnaire. Il renvoie les mêmes types de valeurs que alarm_set().

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[KERNEL]->delay_set("later", 5, "hello", "world");
    },
    later => sub {
      print "@_[ARG0..#$_]\n";
    }
  }
);

delay_adjust ALARM_ID, SECONDS_FROM_NOW

delay_adjust() modifie l'heure de déclenchement d'un minuteur pour qu'elle soit SECONDS_FROM_NOW. Il est utile pour rafraîchir les minuteurs de type "watchdog" ou "timeout". En cas de succès, il renvoie la nouvelle heure UNIX absolue à laquelle le minuteur sera déclenché.

Il est possible pour delay_adjust() d'ajuster les minuteurs créés par alarm_set() ainsi que par delay_set().

use POSIX qw(strftime);
POE::Session->create(
  inline_states => {
    # Configuration.
    # ... omise.
    got_input => sub {
      my $new_time = $_[KERNEL]->delay_adjust(
        $_[HEAP]{input_timeout}, 60
      );
      print(
        "Timeout d'entrée rafraîchi. Le prochain pourrait survenir à ",
        strftime("%F %T", gmtime($new_time)), "\n"
      );
    },
  }
);

En cas d'échec, il renvoie une valeur booléenne fausse et définit $! avec une raison de l'échec. Voir l'explication de $! pour alarm_adjust().

delay_remove n'est pas nécessaire

Il n'y a pas de delay_remove(). Les minuteurs sont tous identiques en interne, donc alarm_remove() fonctionnera avec les ID de minuteur retournés par delay_set().

delay_remove_all n'est pas nécessaire

Il n'y a pas de delay_remove_all(). Les minuteurs sont tous identiques en interne, donc alarm_remove_all() les efface tous, quelle que soit la manière dont ils ont été créés.

Identifiants de Session (IDs et Alias)

Une session peut être référencée par ses références d'objet (soit blessées, soit stringifiées), un ID de session, ou un ou plusieurs noms symboliques que nous appelons alias.

Chaque session est représentée par un objet, donc les références de session sont assez simples. POE::Kernel peut référencer ces objets. Par exemple, post() peut utiliser $_[SENDER] comme destination :

POE::Session->create(
  inline_states => {
    _start => sub { $_[KERNEL]->alias_set("echoer") },
    ping => sub {
      $_[KERNEL]->post( $_[SENDER], "pong", @_[ARG0..$#_] );
    }
  }
);

POE reconnaît également les objets de session stringifiés pour plus de commodité et comme une forme de référence faible. Ici, $_[SENDER] est entouré de guillemets pour le stringifier :

POE::Session->create(
  inline_states => {
    _start => sub { $_[KERNEL]->alias_set("echoer") },
    ping => sub {
      $_[KERNEL]->post( "$_[SENDER]", "pong", @_[ARG0..$#_] );
    }
  }
);

Chaque session se voit attribuer un ID unique au moment de sa création. Aucune session active ne partagera le même ID, mais les IDs peuvent être réutilisés au fil du temps. La combinaison d'un ID de noyau et d'un ID de session devrait être suffisante comme identifiant unique global.

POE::Session->create(
  inline_states => {
    _start => sub { $_[KERNEL]->alias_set("echoer") },
    ping => sub {
      $_[KERNEL]->delay(
        pong_later => rand(5), $_[SENDER]->ID, @_[ARG0..$#_]
      );
    },
    pong_later => sub {
      $_[KERNEL]->post( $_[ARG0], "pong", @_[ARG1..$#_] );
    }
  }
);

Les noyaux maintiennent également un espace de noms ou un dictionnaire global de sessions qui peut être utilisé pour mapper un alias symbolique à une session. Une fois qu'une association d'alias a été créée, cet alias peut être utilisé pour référencer la session partout où une session peut être spécifiée.

Dans les exemples précédents, chaque service d'écho a défini un alias "echoer". Une autre session peut poster une requête de ping à la session d'écho en utilisant cet alias plutôt qu'une référence de session ou un ID. Par exemple :

POE::Session->create(
  inline_states => {
    _start => sub { $_[KERNEL]->post(echoer => ping => "whee!" ) },
    pong => sub { print "@_[ARG0..$#_]\n" }
  }
);

Une session avec un alias ne s'arrêtera pas tant que toute autre activité n'aura pas cessé. Les alias sont traités comme une sorte de spectateur d'événements. Les événements proviennent de sessions actives. Les alias deviennent donc inutiles lorsqu'il n'y a plus de sessions actives. Plutôt que de laisser le programme s'exécuter dans un état "zombie", POE détecte cette condition de blocage et déclenche un nettoyage. Voir "Classes de signaux" pour plus d'informations.

alias_set ALIAS

alias_set() mappe un ALIAS dans le dictionnaire de POE::Kernel à la session courante. L'ALIAS peut ensuite être utilisé presque partout où une référence de session, une référence stringifiée ou un ID est attendue.

Les sessions peuvent avoir plus d'un alias. Chaque alias doit être défini dans un appel séparé à alias_set(). Un alias unique ne peut pas faire référence à plus d'une session.

Des exemples d'alias multiples sont donnés ci-dessus.

alias_set() renvoie 0 en cas de succès, ou un indicateur d'échec non nul : EEXIST ("Fichier existant") indique que l'alias est déjà attribué à une autre session.

alias_remove ALIAS

alias_remove() supprime un ALIAS pour la session courante du dictionnaire de POE::Kernel. L'ALIAS ne fera plus référence à la session courante. Cela n'affecte pas négativement les événements déjà postés dans la file d'attente de POE. La résolution d'alias se produit au moment de post(), pas au moment de la livraison.

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[KERNEL]->alias_set("short_window");
      $_[KERNEL]->delay(close_window => 1);
    },
    close_window => {
      $_[KERNEL]->alias_remove("short_window");
    }
  }
);

alias_remove() renvoie 0 en cas de succès ou un code d'échec non nul : ESRCH ("Aucun processus de ce type") indique que l'ALIAS n'est pas actuellement dans le dictionnaire de POE::Kernel. EPERM ("Opération non autorisée") signifie que la session courante ne peut pas supprimer l'ALIAS car il est utilisé par une autre session.

alias_resolve ALIAS

alias_resolve() renvoie une référence de session correspondant à un ALIAS donné. En fait, l'ALIAS peut être une référence de session stringifiée, un ID de session, ou un alias enregistré précédemment par alias_set().

Une utilisation de alias_resolve() est de détecter si une autre session a disparu :

unless (defined $_[KERNEL]->alias_resolve("Elvis")) {
  print "Elvis a quitté le bâtiment.\n";
}

Comme mentionné précédemment, alias_resolve() renvoie une référence de session ou undef en cas d'échec. L'échec définit également $! à ESRCH ("Aucun processus de ce type") lorsque l'ALIAS n'est pas actuellement dans le dictionnaire de POE::Kernel.

alias_list [SESSION_REFERENCE]

alias_list() renvoie une liste d'alias associés à une SESSION spécifique, ou à la session courante si SESSION est omis. alias_list() renvoie une liste vide si la SESSION demandée n'a pas d'alias.

SESSION peut être une référence de session (blessée ou stringifiée), un ID de session, ou un alias de session.

POE::Session->create(
  inline_states => {
    $_[KERNEL]->alias_set("mi");
    print(
      "Les noms dont je m'appelle : ",
      join(", ", $_[KERNEL]->alias_list()),
      "\n"
    );
  }
);

ID_id_to_session SESSION_ID

ID_id_to_session() traduit un ID de session en référence de session. C'est un sous-ensemble spécifique de alias_re

solve(), ce qui le rend un peu plus rapide et quelque peu moins flexible.

unless (defined $_[KERNEL]->ID_id_to_session($session_id)) {
  print "La session $session_id n'existe pas.\n";
}

ID_id_to_session() renvoie undef si une recherche a échoué. $! sera défini sur ESRCH ("Aucun processus de ce type").

ID_session_to_id SESSION_REFERENCE

ID_session_to_id() convertit une SESSION_REFERENCE, qu'elle soit bénite ou chaînée, en un ID de session. C'est plus pratique pour les références chaînées, car les programmes peuvent appeler la méthode ID() de POE::Session sur celles qui sont bénies. Ces instructions sont équivalentes :

$id = $_[SENDER]->ID();
$id = $_[KERNEL]->ID_session_to_id($_[SENDER]);
$id = $_[KERNEL]->ID_session_to_id("$_[SENDER]");

Comme pour les autres méthodes de recherche de POE::Kernel, ID_session_to_id() renvoie undef en cas d'échec, en définissant $! sur ESRCH ("Aucun processus de ce type").

Surveillants I/O (Selects)

Aucun système d'événements ne serait complet sans la capacité de surveiller de manière asynchrone les événements I/O. POE::Kernel implémente les surveillants de plus bas niveau, appelés "selects" car ils étaient historiquement implémentés à l'aide de la fonction intégrée de Perl select(2) .

Les applications gèrent les événements de préparation I/O en effectuant une activité sur le descripteur de fichier sous-jacent. La préparation à la lecture peut être gérée en lisant depuis le descripteur. La préparation à l'écriture en y écrivant.

Tous les événements des surveillants I/O incluent deux paramètres. "ARG0" contient le descripteur qui est prêt pour le travail. "ARG1" contient un entier décrivant ce qui est prêt.

sub handle_io {
  my ($handle, $mode) = @_[ARG0, ARG1];
  print "Le fichier $handle est prêt pour ";
  if ($mode == 0) {
    print "lecture";
  }
  elsif ($mode == 1) {
    print "écriture";
  }
  elsif ($mode == 2) {
    print "lecture hors bande";
  }
  else {
    die "mode inconnu $mode";
  }
  print "\n";
  # ... faire quelque chose ici
}

Les paramètres restants, @_[ARG2..$%_], contiennent des paramètres supplémentaires qui ont été passés à la méthode de POE::Kernel qui a créé le surveillant.

POE::Kernel conditionne les descripteurs de fichiers pour qu'ils soient propres en 8 bits et non bloquants. Les programmes qui ont besoin qu'ils soient conditionnés différemment devraient les configurer après avoir lancé les surveillants I/O de POE. Si vous utilisez une version de Perl antérieure à 5.8.1 et que vous utilisez des descripteurs de fichiers liés (tied), vous devez définir vous-même le mode non bloquant car IO::Handle ne fonctionne pas bien. Voir https://rt.cpan.org/Ticket/Display.html?id=67545 pour plus d'informations.

Les surveillants I/O empêcheront les sessions de s'arrêter.

select_read FILE_HANDLE [, EVENT_NAME [, PARAMÈTRES_ADDITIONNELS] ]

select_read() démarre ou arrête la surveillance de la session actuelle pour les données entrantes sur un FILE_HANDLE donné. Le surveillant est démarré si EVENT_NAME est spécifié, ou arrêté s'il ne l'est pas. PARAMÈTRES_ADDITIONNELS, s'ils sont spécifiés, seront passés au gestionnaire EVENT_NAME en tant que @_[ARG2..$#_].

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[HEAP]{socket} = IO::Socket::INET->new(
        PeerAddr => "localhost",
        PeerPort => 25,
      );
      $_[KERNEL]->select_read( $_[HEAP]{socket}, "got_input" );
      $_[KERNEL]->delay(timed_out => 1);
    },
    got_input => sub {
      my $socket = $_[ARG0];
      while (sysread($socket, my $buf = "", 8192)) {
        print $buf;
      }
    },
    timed_out => sub {
      $_[KERNEL]->select_read( delete $_[HEAP]{socket} );
    },
  }
);

select_read() ne renvoie rien de significatif.

select_write FILE_HANDLE [, EVENT_NAME [, PARAMÈTRES_ADDITIONNELS] ]

select_write() suit la même sémantique que select_read(), mais elle démarre ou arrête un surveillant qui recherche la préparation à l'écriture. Autrement dit, lorsque EVENT_NAME est délivré, cela signifie que FILE_HANDLE est prêt à être écrit.

select_write() ne renvoie rien de significatif.

select_expedite FILE_HANDLE [, EVENT_NAME [, PARAMÈTRES_ADDITIONNELS] ]

select_expedite() fait quelque chose de similaire à select_read() et select_write(), mais elle surveille un FILE_HANDLE pour les données hors bande prêtes à être entrées depuis un FILE_HANDLE. Presque personne n'utilise cela, mais cela existe pour des raisons de complétude.

Un événement EVENT_NAME sera délivré chaque fois que le FILE_HANDLE peut être lu hors bande. Les données hors bande sont considérées comme "accélérées" car elles précèdent souvent les données normales d'une socket.

select_expedite() ne renvoie rien de significatif.

select_pause_read FILE_HANDLE

select_pause_read() est un moyen léger de mettre en pause un surveillant d'entrée de FILE_HANDLE sans effectuer toute la gestion des appels de select_read(). Il est utilisé avec select_resume_read() pour implémenter le contrôle de flux d'entrée.

L'entrée qui se produit sur FILE_HANDLE sera mise en mémoire tampon dans les tampons du système d'exploitation jusqu'à ce que select_resume_read() soit appelée.

Un effet secondaire du contournement de la gestion de select_read() est qu'un FILE_HANDLE mis en pause n'arrêtera pas prématurément la session en cours.

select_pause_read() ne renvoie rien de significatif.

select_resume_read FILE_HANDLE

select_resume_read() reprend un surveillant d'entrée de FILE_HANDLE qui a été précédemment mis en pause par select_pause_read(). Voir select_pause_read() pour plus de détails sur le contrôle de flux d'entrée léger.

Les données mises en mémoire tampon dans le système d'exploitation en raison d'un appel à select_pause_read() seront disponibles après l'appel à select_resume_read().

select_resume_read() ne renvoie rien de significatif.

select_pause_write FILE_HANDLE

select_pause_write() met en pause un surveillant de sortie de FILE_HANDLE de la même manière que select_pause_read() le fait pour l'entrée. Veuillez consulter select_pause_read() pour plus d'informations.

select_resume_write FILE_HANDLE

select_resume_write() reprend un surveillant de sortie de FILE_HANDLE de la même manière que select_resume_read() le fait pour l'entrée. Voir select_resume_read() pour plus d'informations.

select FILE_HANDLE [, EV_READ [, EV_WRITE [, EV_EXPEDITE [, ARGS] ] ] ]

La méthode select() de POE::Kernel configure ou efface les surveillants de lecture, d'écriture et d'accélération d'un FILE_HANDLE en une seule fois. C'est un peu plus coûteux que d'appeler select_read(), select_write() et select_expedite() manuellement, mais c'est beaucoup plus pratique.

Les noms d'événements définis activent leurs surveillants correspondants, et les noms d'événements indéfinis les désactivent. Ceci désactive tous les surveillants pour un FILE_HANDLE :

sub stop_io {
  $_[KERNEL]->select( $_[HEAP]{file_handle} );
}

Cette instruction :

$_[KERNEL]->select( $file_handle, undef, "write_event", undef, @stuff );

est équivalente à :

$_[KERNEL]->select_read( $file_handle );
$_[KERNEL]->select_write( $file_handle, "write_event", @stuff );
$_[KERNEL]->select_expedite( $file_handle );

Il ne faut pas confondre la méthode select() de POE::Kernel avec la fonction intégrée select() de Perl.

Comme pour les autres méthodes de surveillance I/O, select() ne renvoie pas de valeur significative.

Gestion des Sessions

Les sessions sont dynamiques. Elles peuvent être créées et détruites au cours de la vie d'un programme. Lorsqu'une session est créée, elle devient l'"enfant" de la session courante. Le créateur -- la session courante -- devient sa session "parente". Ceci est vaguement inspiré des processus UNIX.

La gestion de session la plus courante consiste à créer de nouvelles sessions et à les laisser éventuellement s'arrêter.

Chaque session a un parent, même la toute première session créée. Les sessions sans parents évidents sont des enfants de l'instance POE::Kernel du programme.

Les sessions enfants maintiendront leurs parents actifs. Voir "Durées de vie des sessions" pour en savoir plus sur la raison pour laquelle les sessions restent actives.

L'arborescence des relations parent/enfant régit également la manière dont de nombreux signaux sont distribués. Voir "Distribution commune des signaux" pour plus d'informations à ce sujet.

Événements de gestion de session (_start, _stop, _parent, _child)

POE::Kernel fournit quatre événements de gestion de session : _start, _stop, _parent et _child. Ils sont appelés de manière synchrone chaque fois qu'une session est nouvellement créée ou sur le point d'être détruite.

_start
_start devrait vous être familier maintenant. POE déclenche l'événement _start pour initialiser une session après qu'elle ait été enregistrée auprès de POE::Kernel. Ce qui n'est pas immédiatement évident, cependant, c'est qu'il est appelé avant que le constructeur de POE::Session ne renvoie.

Dans le gestionnaire _start, l'expéditeur de l'événement est la session qui a créé la nouvelle session. Autrement dit, le *parent* de la nouvelle session. Les sessions créées avant l'appel à POE::Kernel->run() seront des descendants du singleton POE::Kernel du programme.

La valeur de retour du gestionnaire _start est passée à la session parente dans un événement _child, avec la notification que le nouvel enfant du parent a été créé avec succès. Voir la discussion sur _child pour plus de détails.

POE::Session->create(
  inline_states => { _start=> \&_start },
  args => [ $some, $args ]
);
sub _start {
  my ( $some, $args ) = @_[ ARG0, ARG1 ];
  # ....
}
_stop
_stop est un peu plus mystérieux. POE appelle un gestionnaire _stop lorsqu'une session est irrévocablement sur le point d'être détruite. Une partie de la destruction de la session est la récupération forcée de ses ressources (événements, minuteries, événements de messages, etc.), il n'est donc pas possible de post() un message depuis le gestionnaire de _stop. Un programme est libre d'essayer, mais l'événement sera détruit avant qu'il n'ait la possibilité d'être distribué.

La valeur de retour du gestionnaire _stop est passée à l'événement _child du parent. Voir _child pour plus de détails.

_stop est généralement appelé lorsqu'une session n'a plus de raison d'être, bien que les signaux puissent la faire s'arrêter plus tôt.

Le gestionnaire _child correspondant est appelé de manière synchrone juste après le retour de _stop.

_parent
_parent est utilisé pour notifier une session enfant lorsque son parent a changé. Cela se produit généralement lors de la création initiale d'une session. Cela peut également se produire lorsqu'une session enfant est détachée de son parent. Voir detach_child et "detach_myself".

Événements de gestion de session

Les événements de gestion de session sont des notifications envoyées à une session pour la tenir informée de la manière dont les sessions parentes et enfants sont gérées.

_parent
_parent notifie une session lorsque le parent d'une autre session a changé. ARG0 contient l'ancien parent de la session, et ARG1 contient son nouveau parent.

sub _parent {
  my ( $old_parent, $new_parent ) = @_[ ARG0, ARG1 ];
  print(
    "Session ", $_[SESSION]->ID,
    " parent changed from session ", $old_parent->ID,
    " to session ", $new_parent->ID,
    "\n"
  );
}
_child
_child notifie une session lorsqu'une session enfant a été créée, détruite ou réattribuée à ou depuis un autre parent. Il est généralement envoyé lors de la création ou de la destruction de sessions. Il peut également se produire lorsqu'une session est détachée de son parent.

_child inclut des informations dans la partie "arguments" de @_. Typiquement ARG0, ARG1 et ARG2, mais ceux-ci peuvent être remplacés par une classe POE::Session différente :

ARG0 contient une chaîne décrivant ce qui est arrivé à l'enfant. La chaîne peut être 'create' (la session enfant a été créée), 'gain' (l'enfant a été cédé par une autre session), ou 'lose' (la session enfant a été arrêtée ou cédée).

Dans tous les cas, ARG1 contient une référence à la session enfant.

Dans le cas de 'create', ARG2 contient la valeur retournée par le gestionnaire _start de la session enfant. De même, ARG2 contient la valeur de retour du gestionnaire _stop pour le cas 'lose'.

sub _child {
  my( $reason, $child ) = @_[ ARG0, ARG1 ];
  if( $reason eq 'create' ) {
    my $retval = $_[ ARG2 ];
  }
  # ...
}

Les événements sont livrés dans des ordres spécifiques.

Lorsqu'une nouvelle session est créée :

1.
Le constructeur de la session est appelé.
2.
La session est mise en jeu. C'est-à-dire que POE::Kernel enregistre la session dans sa comptabilité.
3.
La nouvelle session reçoit _start.
4.
La session parente reçoit _child ('create'), la référence à la nouvelle session, et la valeur de retour de _start de la nouvelle session.
5.
Le constructeur de la session retourne.

Lorsqu'une ancienne session s'arrête :

1.
Si la session a ses propres enfants, ils sont cédés au parent de la session. Cela déclenche un ou plusieurs événements _child ('gain') chez le parent, et un _parent chez chaque enfant.
2.
Une fois dépouillée de ses enfants, la session qui s'arrête reçoit un événement _stop.
3.
Le parent de la session qui s'arrête reçoit un événement _child ('lose') avec la référence de l'enfant partant et la valeur de retour de son gestionnaire _stop.
4.
La session arrêtée est retirée de la mise en jeu, ainsi que toutes ses ressources restantes.
5.
Le parent de la session est vérifié pour l'inactivité. Si c'est le cas, le garbage collection commencera sur celui-ci, et il sera également arrêté.

Lorsqu'une session est détachée de son parent :

1.
Le parent de la session détachée est notifié par un événement _child ('lose'). La valeur de retour du gestionnaire _stop est undef car l'enfant ne s'arrête pas réellement.
2.
La session détachée est notifiée par un événement _parent que son nouveau parent est POE::Kernel lui-même.
3.
Les données de comptabilité de POE::Kernel sont ajustées pour refléter le changement de parenté.
4.
L'ancien parent de la session est vérifié pour l'inactivité. Si c'est le cas, le garbage collection commencera sur celui-ci, et il sera également arrêté.

Méthodes de gestion de session

Ces méthodes permettent de détacher des sessions de leurs parents dans les cas rares où la relation parent/enfant devient gênante.

detach_child CHILD_SESSION

detach_child() détache une CHILD_SESSION particulière de la session courante. En cas de succès, la CHILD_SESSION deviendra un enfant de l'instance POE::Kernel, et detach_child() retournera vrai. En cas d'échec, cependant, detach_child() retourne faux et définit $! pour expliquer la nature de l'échec :

ESRCH ("No such process").
La CHILD_SESSION n'est pas une session valide.
EPERM ("Operation not permitted").
La CHILD_SESSION existe, mais elle n'est pas un enfant de la session courante.

detach_child() générera des événements "_parent" et/ou "_child" aux sessions appropriées. Voir Événements de gestion de session pour une explication détaillée de ces événements. Voir ci-dessus pour l'ordre dans lequel les événements sont générés.

detach_myself

detach_myself() détache la session courante de son parent courant. Le nouveau parent sera l'instance POE::Kernel en cours d'exécution. Elle retourne vrai en cas de succès. En cas d'échec, elle retourne faux et définit $! pour expliquer la nature de l'échec :

EPERM ("Operation not permitted").
La session courante est déjà un enfant de POE::Kernel, elle ne peut donc pas être détachée.

detach_child() générera des événements "_parent" et/ou "_child" aux sessions appropriées. Voir Événements de gestion de session pour une explication détaillée de ces événements. Voir ci-dessus pour l'ordre dans lequel les événements sont générés.

Signaux

POE::Kernel fournit des méthodes par lesquelles un programme peut s'enregistrer pour l'intérêt des signaux qui arrivent, peut envoyer ses propres signaux sans recourir à des appels système, et peut indiquer que des signaux ont été gérés afin que les comportements par défaut ne soient pas nécessaires.

Les signaux sont par nature une *action à distance*, et leur mise en œuvre nécessite une synchronisation généralisée entre les sessions (et la réentrance dans le dispatcher, mais c'est un détail d'implémentation). Perfectionner la sémantique s'est avéré difficile, mais POE essaie de faire la *bonne chose* chaque fois que possible.

POE n'enregistre pas de gestionnaires %SIG pour les signaux tant que sig() n'est pas appelé pour les surveiller. Par conséquent, le comportement par défaut d'un signal se produit pour les signaux non gérés. Autrement dit, SIGINT arrêtera un programme sans ménagement, SIGWINCH ne fera rien, SIGTSTP mettra un programme en pause, etc.

Classes de signaux

Il existe trois classes de signaux. Chaque classe définit un comportement par défaut pour le signal et si ce défaut peut être outrepassé. Elles sont :

Signaux bénins, consultatifs ou informatifs

Ce sont trois noms pour la même classe de signal. Les signaux de cette classe notifient une session d'un événement mais ne terminent pas la session s'ils ne sont pas gérés.

Il est possible qu'une application crée ses propres signaux bénins. Voir "signal" ci-dessous.

Signaux terminaux

Les signaux terminaux tueront les sessions s'ils ne sont pas gérés par un appel "sig_handled"(). Les signaux du système d'exploitation qui tuent ou dumpent généralement un processus sont considérés comme terminaux dans POE, mais ils ne déclenchent jamais de coredump. Ce sont : HUP, INT, QUIT et TERM.

Il existe deux signaux terminaux créés par et utilisés au sein de POE :

DIE
"DIE" notifie les sessions qu'une exception Perl s'est produite. Voir "Gestion des exceptions" pour les détails.
IDLE
Le signal "IDLE" est utilisé pour notifier les sessions restantes qu'un programme n'a plus rien à faire.

Signaux non masquables

Les signaux non masquables sont terminaux, que sig_handled() soit appelé ou non. Le terme vient de "NMI", l'interruption CPU non masquable généralement générée par une exception matérielle irrécupérable.

Les sessions qui reçoivent un signal non masquable s'arrêteront inévitablement. POE implémente deux signaux non masquables :

ZOMBIE
Ce signal non masquable est déclenché si un programme a reçu un signal "IDLE" mais n'a ni redémarré ni quitté. Le programme est devenu un zombie (c'est-à-dire qu'il n'est ni mort ni vivant, et n'existe que pour consommer des cerveeeeaux... euh... de la mémoire). Le signal "ZOMBIE" agit comme un coup de batte de cricket sur la tête, abattant le zombie, pour de bon.
UIDESTROY
Ce signal non masquable indique que l'interface utilisateur d'un programme a été fermée, et que le programme devrait également comprendre l'indice de l'utilisateur et disparaître. Il est généralement généré lorsqu'un widget GUI particulier est fermé.

Distribution commune des signaux

La plupart des signaux ne sont pas distribués à une seule session. La lignée des sessions de POE (parents et enfants) forme une sorte d'arbre généalogique. Lorsqu'un signal est envoyé à une session, il traverse d'abord tous les enfants (et les petits-enfants, etc.) qui s'intéressent également au signal.

Dans le cas des signaux terminaux, si l'une des sessions à travers laquelle un signal passe appelle "sig_handled"(), alors le signal est considéré comme pris en charge. Cependant, si aucune d'entre elles ne le fait, l'ensemble de l'arbre de sessions enraciné à la session de destination est terminé. Par exemple, considérons cet arbre de sessions :

POE::Kernel
  Session 2
    Session 4
    Session 5
  Session 3
    Session 6
    Session 7

POE::Kernel est le parent des sessions 2 et 3. La session 2 est le parent des sessions 4 et 5. Et la session 3 est le parent des 6 et 7.

Un signal envoyé à la Session 2 peut également être distribué aux sessions 4 et 5 car ce sont les enfants de 2. Les sessions 4 et 5 ne recevront le signal que si elles ont enregistré le watcher approprié. Si le signal est terminal, et qu'aucun des watchers de signal dans les sessions 2, 4 et 5 n'a appelé sig_handled(), les 3 sessions seront terminées.

L'instance POE::Kernel du programme est considérée comme une session aux fins de la distribution des signaux. Ainsi, tout signal envoyé à POE::Kernel se propagera à travers chaque session intéressée de l'ensemble du programme. C'est en fait ainsi que les signaux du système d'exploitation sont gérés : un gestionnaire de signaux global est enregistré pour transférer le signal à POE::Kernel.

Sémantique des signaux

Tous les signaux sont livrés avec le nom du signal dans ARG0. Le nom du signal est tel qu'il apparaît dans %SIG, avec une exception : les signaux des processus enfants sont toujours "CHLD" même si le système d'exploitation courant les reconnaît comme "CLD".

Certains signaux ont une sémantique spéciale :

SIGCHLD

SIGCLD

À la fois "SIGCHLD" et "SIGCLD" indiquent qu'un processus enfant s'est terminé ou a été terminé par un signal. Le nom réel du signal varie selon les systèmes d'exploitation, mais POE utilise toujours "CHLD".

L'intérêt pour "SIGCHLD" est enregistré via la méthode "sig_child". La méthode "sig"() fonctionne également, mais elle n'est pas aussi pratique.

L'événement "SIGCHLD" comprend trois paramètres :

ARG0
"ARG0" contient la chaîne 'CHLD' (même si le système l'appelle SIGCLD, SIGMONKEY, ou quelque chose comme ça).
ARG1
"ARG1" contient l'identifiant du processus enfant terminé.
ARG2
Et "ARG2" contient la valeur de $? pour le processus terminé.

Exemple :

sub sig_CHLD {
  my( $name, $PID, $exit_val ) = @_[ ARG0, ARG1, ARG2 ];
  # ...
}

SIGPIPE

SIGPIPE est rarement utilisé, car POE fournit des événements qui font le même travail. Cependant, il peut être utilisé si nécessaire. Contrairement à la plupart des événements, SIGPIPE est envoyé directement à la session active lorsqu'il est capturé. Sauf en cas de conditions de concurrence, la session active devrait avoir provoqué l'envoi du signal en premier lieu.

Le signal SIGPIPE continuera à se propager aux sessions filles.

ARG0 est "PIPE". Aucune information supplémentaire n'est associée à ce signal.

SIGWINCH

Les redimensionnements de fenêtre peuvent générer un très grand nombre de signaux très rapidement. Cela peut ne pas poser de problème lors de l'utilisation de Perl 5.8.0 ou versions ultérieures, mais les anciennes versions peuvent ne pas tolérer cette utilisation. Vous avez été prévenu.

ARG0 est "WINCH". Aucune information supplémentaire n'est associée à ce signal.

Gestion des exceptions

POE::Kernel ne fournit qu'un seul type de gestion des exceptions : le signal "DIE".

Lorsque la gestion des exceptions est active (par défaut), POE::Kernel encapsule l'appel d'état dans "eval{}". Si le gestionnaire d'événements génère une exception, généralement avec "die", POE::Kernel enverra un signal "DIE" à la session de destination.

"ARG0" est le nom du signal, "DIE".

"ARG1" est un hashref décrivant l'exception :

error_str
Le texte de l'exception. En d'autres termes, $@.
dest_session
L'objet de session de l'état qui a lancé l'exception. En d'autres termes, $_[SESSION] dans la fonction qui est tombée.
event
Le nom de l'événement qui est tombé.
source_session
L'objet de session qui a envoyé l'événement d'origine. C'est-à-dire, $_[SENDER] dans la fonction qui est tombée.
from_state
L'état à partir duquel l'événement d'origine a été envoyé. C'est-à-dire, $_[CALLER_STATE] dans la fonction qui est tombée.
file
Le nom du fichier de l'événement qui a été envoyé. C'est-à-dire, $_[CALLER_FILE] dans la fonction qui est tombée.
line
Le numéro de ligne de l'événement qui a été envoyé. C'est-à-dire, $_[CALLER_LINE] dans la fonction qui est tombée.

Notez que la discussion précédente suppose que vous utilisez les sémantiques d'appel de POE::Session.

Notez que le signal "DIE" est envoyé à la session qui a lancé l'exception, pas à la session qui a envoyé l'événement qui a provoqué l'exception.

sub _start {
  $poe_kernel->sig( DIE => 'sig_DIE' );
  $poe_kernel->yield( 'some_event' );
}
sub some_event {
  die "I didn't like that!";
}
sub sig_DIE {
  my( $sig, $ex ) = @_[ ARG0, ARG1 ];
  # $sig est 'DIE'
  # $ex est le hash de l'exception
  warn "$$: error in $ex->{event}: $ex->{error_str}";
  $poe_kernel->sig_handled();
  # Envoyer le signal à la session qui a envoyé l'événement d'origine.
  if( $ex->{source_session} ne $_[SESSION] ) {
    $poe_kernel->signal( $ex->{source_session}, 'DIE', $sig, $ex );
  }
}

La gestion intégrée des exceptions de POE::Kernel peut être désactivée en définissant la constante "POE::Kernel::CATCH_EXCEPTIONS" à 0. Comme avec d'autres constantes de configuration de compilation, vous devez la définir avant de compiler POE::Kernel :

BEGIN {
  package POE::Kernel;
  use constant CATCH_EXCEPTIONS => 0;
}
use POE;

ou

sub POE::Kernel::CATCH_EXCEPTIONS () { 0 }
use POE;

Méthodes de surveillance des signaux

Et enfin, les méthodes elles-mêmes.

sig SIGNAL_NAME [, EVENT_NAME [, LIST] ]

sig() enregistre ou désenregistre un événement EVENT_NAME pour un SIGNAL_NAME donné, avec une LIST de paramètres qui seront passés au gestionnaire du signal, après toute donnée associée au signal.

Si EVENT_NAME est défini, le gestionnaire est enregistré. Sinon, il est désenregistré.

Chaque session ne peut enregistrer qu'un seul gestionnaire par SIGNAL_NAME. Les enregistrements ultérieurs remplaceront les précédents. Plusieurs sessions peuvent surveiller le même signal.

Les SIGNAL_NAME sont généralement les mêmes que les membres de %SIG, à deux exceptions près. Premièrement, "CLD" est un alias de "CHLD" (bien que voir "sig_child"). Et deuxièmement, il est possible d'envoyer et de gérer des signaux créés par le programme, sans base sur le système d'exploitation.

sub handle_start {
  $_[KERNEL]->sig( INT => "event_ui_shutdown" );
  $_[KERNEL]->sig( bat => "holy_searchlight_batman" );
  $_[KERNEL]->sig( signal => "main_screen_turn_on" );
}

Le système d'exploitation ne sera peut-être jamais en mesure de générer les deux derniers signaux, mais une session peut utiliser la méthode "signal"() de POE::Kernel pour les envoyer.

Plus tard, la session peut décider de ne plus gérer les signaux :

sub handle_ui_shutdown {
  $_[KERNEL]->sig( "INT" );
  $_[KERNEL]->sig( "bat" );
  $_[KERNEL]->sig( "signal" );
}

Plus d'une session peut enregistrer un intérêt pour le même signal, et une session peut supprimer ses propres surveillances de signal sans affecter celles des autres sessions.

sig() ne renvoie pas de valeur significative.

sig_child PROCESS_ID [, EVENT_NAME [, LIST] ]

sig_child() est un moyen pratique d'envoyer un événement EVENT_NAME lorsqu'un processus spécifique a terminé. Une LIST de paramètres optionnels est passée au gestionnaire du signal après les informations de waitpid().

Le surveillant peut être nettoyé en appelant sig_child() avec uniquement le PROCESS_ID.

Une session peut enregistrer autant de gestionnaires sig_child() que nécessaire, mais elle ne peut en avoir qu'un par PROCESS_ID.

Les surveillants sig_child() sont temporaires. Ils se désenregistrent automatiquement après l'envoi de l'événement. Il n'y a aucun intérêt à continuer à surveiller un signal qui ne se produira plus. Les autres gestionnaires de signaux persistent jusqu'à ce qu'ils soient nettoyés.

Les surveillants sig_child() maintiennent une session active tant qu'ils sont actifs. C'est une caractéristique unique parmi les surveillants de signaux de POE.

Les programmes qui souhaitent réclamer des processus de manière fiable doivent s'assurer d'appeler sig_child() avant de retourner du gestionnaire qui a bifurqué le processus. Sinon, POE::Kernel pourrait avoir la possibilité d'appeler waitpid() avant qu'un surveillant approprié n'ait été enregistré.

Les programmes qui réclament des processus avec waitpid() doivent nettoyer les surveillants POE pour les mêmes identifiants de processus, sinon POE attendra indéfiniment des processus qui n'enverront jamais de signaux.

sig_child() ne renvoie pas de valeur significative.

sub forked_parent {
  my( $heap, $pid, $details ) = @_[ HEAP, ARG0, ARG1 ];
  $poe_kernel->sig_child( $pid, 'sig_child', $details );
}
sub sig_child {
  my( $heap, $sig, $pid, $exit_val, $details ) = @_[ HEAP, ARG0..ARG3 ];
  my $details = delete $heap->{ $pid };
  warn "$$: Child $pid exited"
  # ... de plus, $details a été passé depuis forked_parent() par sig_child()
}

sig_handled

sig_handled() informe POE::Kernel que le signal actuellement distribué a été géré par la session active. Si le signal est terminal, l'appel à sig_handled() empêche POE::Kernel d'arrêter les sessions qui ont reçu le signal.

Un même signal peut être distribué à plusieurs sessions. Une seule doit appeler sig_handled() pour éviter que l'ensemble du groupe ne s'arrête. Si aucune d'entre elles ne l'appelle, cependant, elles s'arrêteront ensemble.

sig_handled() ne renvoie pas de valeur significative.

sub _start {
  $_[KERNEL]->sig( INT => 'sig_INT' );
}
sub sig_INT {
  warn "$$ SIGINT";
  $_[KERNEL]->sig_handled();
}

signal SESSION, SIGNAL_NAME [, ARGS_LIST]

signal() envoie un signal SIGNAL_NAME à une session spécifique avec une ARGS_LIST optionnelle qui est passée à tous les gestionnaires intéressés. Comme mentionné précédemment, le signal peut être livré aux enfants, petits-enfants, et ainsi de suite. Et si SESSION est POE::Kernel lui-même, toutes les sessions intéressées recevront le signal.

Il est possible d'envoyer un signal qui n'existe pas sur le système d'exploitation dans POE. signal() l'envoie directement dans la file d'attente des événements de POE comme s'il venait du système d'exploitation, mais il n'est pas limité aux signaux reconnus par kill(). POE utilise certains de ces signaux fictifs pour des notifications globales.

Par exemple :

sub some_event_handler {
  # Active tous les écrans principaux.
  $_[KERNEL]->signal( $_[KERNEL], "signal" );
}

signal() renvoie true en cas de succès. En cas d'échec, il renvoie false après avoir défini $! pour expliquer le type d'échec :

ESRCH ("No such process")
La session n'existe pas.

Étant donné que toutes les sessions sont des enfants de POE::Kernel, l'envoi d'un signal au noyau propagera le signal à toutes les sessions. C'est une forme économique de multiplexage.

$_[KERNEL]->signal( $_[KERNEL], 'shutdown' );

signal_ui_destroy WIDGET_OBJECT

class="Pp">signal_ui_destroy() associe la destruction d'un WIDGET_OBJECT à la destruction complète de l'interface utilisateur du programme. Lorsque le WIDGET_OBJECT est détruit, POE::Kernel émet le signal UIDESTROY, qui désactive rapidement toutes les sessions actives. POE::Kernel->run() revient brièvement après. 
sub setup_ui {
  $_[HEAP]{main_widget} = Gtk->new("toplevel");
  # ... peuplez le widget principal ici ...
  $_[KERNEL]->signal_ui_destroy( $_[HEAP]{main_widget} );
}

La détection de la destruction d'un widget est spécifique à chaque toolkit.

Gestion des gestionnaires d'événements

Les méthodes de gestion des gestionnaires d'événements permettent aux sessions de modifier leurs gestionnaires d'événements en temps réel. Par exemple, les objets POE::Wheel utilisent state() pour mélanger leurs propres gestionnaires d'événements dans les sessions qu'ils créent.

Ces méthodes n'affectent que la session actuelle ; il serait grossier de modifier les gestionnaires d'autres sessions.

Il n'y a qu'une seule méthodologie dans cette catégorie. Comme elle peut être appelée de plusieurs manières, il peut être plus facile à comprendre si chacune est documentée séparément.

state EVENT_NAME [, CODE_REFERNCE]

state() définit ou supprime un gestionnaire pour EVENT_NAME dans la session actuelle. La fonction référencée par CODE_REFRENCE est appelée chaque fois que des événements EVENT_NAME sont envoyés à la session actuelle. Si CODE_REFRENCE est omis, le gestionnaire pour EVENT_NAME est supprimé.

Une session ne peut avoir qu'un seul gestionnaire pour un EVENT_NAME donné. Les tentatives ultérieures pour définir un gestionnaire pour EVENT_NAME remplaceront les gestionnaires précédents du même nom.

# Arrêter l'écoute des entrées. Jusqu'à ce que le message soit envoyé, aucune écoute ne doit être effectuée. Une connexion doit être fermée lorsque le message est envoyé.
sub send_final_response {
  $_[HEAP]{wheel}->put("KTHXBYE");
  $_[KERNEL]->state( 'on_client_input' );
  $_[KERNEL]->state( on_flush => \&close_connection );
}

state EVENT_NAME [, OBJECT_REFERENCE [, OBJECT_METHOD_NAME] ]

Définit ou supprime un gestionnaire pour EVENT_NAME dans la session actuelle. Si un OBJECT_REFERENCE est fourni, cet objet gérera l'événement. Un OBJECT_METHOD_NAME optionnel peut être fourni. Si le nom de la méthode n'est pas fourni, POE recherchera une méthode qui correspond à EVENT_NAME. Si OBJECT_REFERENCE est omis, le gestionnaire pour EVENT_NAME est supprimé.

Une session ne peut avoir qu'un seul gestionnaire pour un EVENT_NAME donné. Les tentatives ultérieures pour définir un gestionnaire pour EVENT_NAME remplaceront les gestionnaires précédents du même nom.

$_[KERNEL]->state( 'some_event', $self );
$_[KERNEL]->state( 'other_event', $self, 'other_method' );

state EVENT_NAME [, CLASS_NAME [, CLASS_METHOD_NAME] ]

Cette forme d'appel de state() est pratiquement identique à la forme objet.

Définit ou supprime un gestionnaire pour EVENT_NAME dans la session actuelle. Si un CLASS_NAME est fourni, cette classe gérera l'événement. Un CLASS_METHOD_NAME optionnel peut être fourni. Si le nom de la méthode n'est pas fourni, POE recherchera une méthode qui correspond à EVENT_NAME. Si CLASS_NAME est omis, le gestionnaire pour EVENT_NAME est supprimé.

Une session ne peut avoir qu'un seul gestionnaire pour un EVENT_NAME donné. Les tentatives ultérieures pour définir un gestionnaire pour EVENT_NAME remplaceront les gestionnaires précédents du même nom.

$_[KERNEL]->state( 'some_event', __PACKAGE__ );
$_[KERNEL]->state( 'other_event', __PACKAGE__, 'other_method' );

Compteurs de références publics

Les méthodes de cette section manipulent les compteurs de références dans la session actuelle ou dans une autre session.

Chaque session possède un espace de noms pour les compteurs de références gérés par l'utilisateur. Ces espaces de noms sont associés à l'ID_SESSION cible des méthodes de compteur de références, et non à l'appelant. Actuellement, il est impossible d'empêcher une session de décrémenter un compteur de références qui a été incrémenté par une autre, mais ce comportement n'est pas garanti. Pour l'instant, il appartient aux utilisateurs de ces fonctions de choisir des noms de compteur obscurs pour éviter les collisions.

La comptabilisation des références est une partie importante de la magie de POE. Divers objets (principalement des observateurs d'événements et des composants) maintiennent des références aux sessions qui les possèdent. "Vie des sessions" explique ce concept plus en détail.

La capacité de maintenir une session en vie peut être utile dans un programme ou une bibliothèque. Par exemple, un composant peut conserver une référence publique à une autre session pendant qu'il traite une requête de cette session. De cette façon, le composant s'assure que le demandeur est toujours présent lorsque la réponse est préparée. Conserver une référence à l'objet de la session est insuffisant. POE::Kernel a ses propres mécanismes internes de comptabilité des références.

refcount_increment SESSION_ID, COUNTER_NAME

refcount_increment() incrémente la valeur de COUNTER_NAME dans le compteur de références de la session identifiée par un SESSION_ID. Pour éviter les références orphelines aux sessions, refcount_increment() doit spécifier l'ID de session comme cible.

La session cible ne s'arrêtera pas tant que la valeur de n'importe lequel et de tous ses COUNTER_NAME dans le compteur de références ne sera pas zéro. (En fait, elle pourrait s'arrêter dans certains cas, comme un échec dans la gestion d'un signal terminal.)

Les compteurs de références négatifs sont valides. Ils doivent être ré-incrémentés à zéro avant qu'une session ne soit en mesure de s'arrêter.

sub handle_request {
  # Entre autres, maintient un compteur de références sur l'expéditeur.
  $_[KERNEL]->refcount_increment( $_[SENDER]->ID, "pending request");
  $_[HEAP]{requesters}{$request_id} = $_[SENDER]->ID;
}

Pour que cela fonctionne, la session doit avoir un moyen de se souvenir de l'ID de $_[SENDER]->ID pour une requête donnée. Généralement, la session génère un ID de requête et l'utilise pour suivre la requête jusqu'à ce qu'elle soit satisfaite.

refcount_increment() renvoie le résultat du compteur de références (peut être zéro) en cas de succès. En cas d'échec, elle renvoie undef et définit $! comme raison de l'erreur.

ESRCH : L'ID_SESSION ne fait pas référence à une session active actuellement.

refcount_decrement SESSION_ID, COUNTER_NAME

refcount_decrement() décrémente la valeur de COUNTER_NAME dans le compteur de références de la session identifiée par un SESSION_ID. C'est le pendant de refcount_increment(). Veuillez consulter refcount_increment() pour plus de contexte.

sub finally_send_response {
  # Entre autres, libère le compteur de références du demandeur.
  my $requester_id = delete $_[HEAP]{requesters}{$request_id};
  $_[KERNEL]->refcount_decrement( $requester_id, "pending request");
}

L'ID de $_[SENDER]->ID du demandeur est conservé et retiré du heap (pour éviter les fuites de mémoire). Il est utilisé pour décrémenter le compteur de références qui avait été incrémenté au début de la requête.

refcount_decrement() renvoie le résultat du compteur de références (peut être zéro) en cas de succès. En cas d'échec, elle renvoie undef et définit $! comme raison de l'erreur :

ESRCH : L'ID_SESSION ne fait pas référence à une session active actuellement.

Il n'est pas possible de découvrir les références publiques actuelles. Voir POE::API::Peek.

Accesseurs d'état du noyau

POE::Kernel fournit quelques accesseurs dans son cerveau massif afin que les développeurs de bibliothèques puissent avoir un accès pratique aux données nécessaires sans dépendre de leurs appelants pour les fournir.

Ces accesseurs exposent des moyens de briser l'encapsulation de la session. Veuillez les utiliser avec modération et prudence.

get_active_session

get_active_session() renvoie une référence à la session qui est actuellement en cours d'exécution, ou une référence à l'objet POE::Kernel du programme s'il n'y a pas de session active pour le moment. La valeur est équivalente à $_[SESSION] de POE::Session.

Cette méthode a été ajoutée pour les bibliothèques qui ont besoin de $_[SESSION] mais ne veulent pas l'inclure comme paramètre dans leurs API.

sub some_housekeeping {
  my( $self ) = @_;
  my $session = $poe_kernel->get_active_session;
  # faire quelques nettoyages sur $session
}

get_active_event

get_active_event() renvoie le nom de l'événement en cours de dispatch. Elle renvoie une chaîne vide lorsqu'elle est appelée en dehors d'un dispatch d'événement. La valeur est équivalente à $_[STATE] de POE::Session.

sub waypoint {
  my( $message ) = @_;
  my $event = $poe_kernel->get_active_event;
  print STDERR "$$:$event:$mesage\n";
}

get_event_count

get_event_count() renvoie le nombre d'événements en attente dans la file d'attente d'événements de POE. Exposé pour les auteurs de classes POE::Loop. Pourrait être obsolète à l'avenir.

get_next_event_time

get_next_event_time() renvoie l'heure à laquelle le prochain événement doit se produire, dans un format compatible avec la fonction UNIX time(). Exposé pour les auteurs de classes POE::Loop. Pourrait être obsolète à l'avenir.

poe_kernel_loop

poe_kernel_loop() renvoie le nom de la classe POE::Loop qui est utilisée pour détecter et dispatcher les événements.

Méthodes d'aide de session

Les méthodes de cette catégorie exposent des fonctionnalités pour les auteurs de classes POE::Session.

session_alloc SESSION_OBJECT [, START_ARGS]

session_alloc() alloue un contexte de session au sein de POE::Kernel pour un nouveau SESSION_OBJECT. Une liste d'arguments START_ARGS optionnels est transmise à la session dans le cadre de l'événement "_start".

Le SESSION_OBJECT est censé suivre un sous-ensemble de l'interface POE::Session.

Il n'y a pas de session_free(). POE::Kernel détermine quand la session doit s'arrêter et effectue le nettoyage nécessaire après que la session a reçu l'événement "_stop".

Méthodes diverses

On ne sait pas où classer les méthodes de cette section.

new

Il n'est pas nécessaire d'appeler la méthode new() de POE::Kernel. Le faire renverra l'objet singleton POE::Kernel du programme, cependant.

Variables exportées publiques

POE::Kernel exporte deux variables pour être utilisées dans le code : $poe_kernel et $poe_main_window. POE::Kernel est utilisé implicitement par POE

Mantén toda la estructura del archivo.

En más detalle:

$poe_kernel

$poe_kernel contiene una referencia al objeto singleton POE::Kernel de la sesión actual. Su uso principal es acceder a métodos de POE::Kernel desde lugares donde $_[KERNEL] no está disponible. Es más comúnmente utilizado en bibliotecas de ayuda.

$poe_main_window

$poe_main_window se usa por bibliotecas gráficas que requieren al menos una widget antes de que sus bucles de eventos estén funcionales. Esto se actualiza actualmente solo en Tk.

POE::Loop::Tk crea una ventana principal para satisfacer el bucle de eventos de Tk. La ventana es dada a la aplicación ya que POE no tiene otra utilidad para ella.

$poe_main_window es indefinido en bibliotecas que no requieren una widget para desencadenar eventos.

En un apartado relacionado, POE se detendrá si la widget en $poe_main_window es destruida. Esto puede cambiarse con el método POE::Kernel::signal_ui_destroy.

DÉBOGAGE DE POE ET DES PROGRAMMES L'UTILISANT

POE inclut beaucoup de code de débogage, sous forme d'assertions et de traces d'exécution. Celles-ci peuvent avoir été activées à la compilation, mais il n'y a aucun moyen de les activer à l'exécution. Cela a été fait pour éviter des pénalités à l'exécution dans les programmes où le débogage n'est pas nécessaire. C'est-à-dire, dans les cas de production.

Les traces sont des rappels verbaux de ce qui se passe à l'intérieur de POE. Chacune est précédée d'un champ de quatre caractères décrivant le sous-système POE qui a généré le message.

Les assertions sont coûteuses mais mortelles, à la fois en termes de performance (elles ont un impact significatif sur le temps d'exécution) et parce qu'elles provoquent des erreurs mortelles lorsqu'elles sont déclenchées.

Les assertions et les traces sont utiles pour développer des programmes avec POE, mais elles ont été initialement ajoutées pour déboguer POE lui-même.

Chaque groupe d'assertions et de traces est activé en définissant une constante dans l'espace de noms POE::Kernel à une valeur vraie.

BEGIN {
  package POE::Kernel;
  use constant ASSERT_DEFAULT => 1;
}
use POE;

Ou la manière plus ancienne (plus courte) de la "constante subroutine". Celle-ci n'a pas besoin du bloc BEGIN{} car les définitions de sous-routines sont effectuées au moment de la compilation.

sub POE::Kernel::ASSERT_DEFAULT () { 1 }
use POE;

Les commutateurs doivent être définis comme des constantes avant que POE::Kernel ne soit chargé. Sinon, le compilateur Perl ne verra pas les constantes lors de la compilation de POE::Kernel et les fonctions n'auront pas été activées correctement.

Les assertions et les traces peuvent également être activées en définissant des variables d'environnement shell. Les variables d'environnement sont nommées d'après les constantes de POE::Kernel avec un préfixe POE_.

POE_ASSERT_DEFAULT=1 POE_TRACE_DEFAULT=1 ./my_poe_program

Par ordre alphabétique:

ASSERT_DATA

ASSERT_DATA active les vérifications d'intégrité des données à l'exécution dans POE::Kernel et les classes qui s'y mélangent. POE::Kernel suit un grand nombre de données interconnectées, et ce groupe d'assertions garantit qu'elles sont cohérentes.

Préfixe: <dt>

Variable d'environnement: POE_ASSERT_DATA

ASSERT_DEFAULT

ASSERT_DEFAULT spécifie la valeur par défaut pour les assertions non explicitement activées ou désactivées. C'est une méthode rapide et fiable pour s'assurer que toutes les assertions sont activées.

ASSERT_DEFAULT n'est pas utilisé directement dans les assertions, et ce drapeau n'a pas de préfixe de sortie correspondant.

Active toutes les assertions sauf ASSERT_EVENTS:

sub POE::Kernel::ASSERT_DEFAULT () { 1 }
sub POE::Kernel::ASSERT_EVENTS  () { 0 }
use POE::Kernel;

Préfixe: (aucun)

Variable d'environnement: POE_ASSERT_DEFAULT

ASSERT_EVENTS

ASSERT_EVENTS se concentre sur la détection des tentatives de déclenchement d'événements sur des sessions inexistantes. Cette assertion peut aider à déboguer des cas étranges et silencieux où les gestionnaires d'événements ne sont pas appelés.

Préfixe: <ev>

Variable d'environnement: POE_ASSERT_EVENTS

ASSERT_FILES

ASSERT_FILES active quelques vérifications à l'exécution sur les moniteurs de fichiers de POE et le code qui les gère.

Préfixe: <fh>

Variable d'environnement: POE_ASSERT_FILES

ASSERT_RETVALS

ASSERT_RETVALS transforme les codes de retour des méthodes de POE::Kernel de consultatifs à mortels. La plupart des programmeurs ne vérifient pas les valeurs de retour de ces méthodes, donc ASSERT_RETVALS est une méthode rapide pour valider l'hypothèse que tout va bien.

Préfixe: <rv>

Variable d'environnement: POE_ASSERT_RETVALS

ASSERT_USAGE

ASSERT_USAGE est le pendant de ASSERT_RETVALS. Il active les vérifications à l'exécution qui garantissent que les paramètres des méthodes de POE::Kernel sont corrects. C'est une méthode rapide (mais pas parfaite) pour vérifier l'utilisation de POE dans un programme.

Préfixe: <us>

Variable d'environnement: POE_ASSERT_USAGE

TRACE_DEFAULT

TRACE_DEFAULT spécifie la valeur par défaut pour les traces non explicitement activées ou désactivées. C'est une méthode rapide et fiable pour s'assurer que votre programme génère une sortie abondante dans le fichier spécifié par TRACE_FILENAME ou dans STDERR.

Pour activer toutes les traces sauf une paire plus verbeuses:

sub POE::Kernel::TRACE_DEFAULT () { 1 }
sub POE::Kernel::TRACE_EVENTS  () { 0 }
use POE::Kernel;

Préfixe: (aucun)

Variable d'environnement: POE_TRACE_DEFAULT

TRACE_DESTROY

TRACE_DESTROY fait en sorte que chaque objet POE::Session dépose le contenu de $_[HEAP] lorsque Perl le détruit. Cette trace a été ajoutée pour aider les développeurs à trouver des fuites de mémoire dans leurs programmes.

Préfixe: Une ligne indiquant "----- Session $self Leak Check -----".

Variable d'environnement: POE_TRACE_DESTROY

TRACE_EVENTS

TRACE_EVENTS active les messages liés à la boucle d'événements de POE. Lorsqu'ils sont mis en file d'attente, déclenchés ou discutés, etc. C'est excellent pour déterminer où vont les événements et quand. Bien sûr, c'est l'une des traces les plus verbeuses de POE.

Préfixe: <ev>

Variable d'environnement: POE_TRACE_EVENTS

TRACE_FILENAME

TRACE_FILENAME spécifie le nom d'un fichier dans lequel les traces et les messages de débogage de POE devraient être écrits. C'est utile si vous souhaitez générer des messages mais que vous avez d'autres plans pour STDERR, où les messages vont par défaut.

Les tests de POE utilisent ceci afin que le code de trace et de débogage puisse être instrumenté pendant le test sans que les messages ne s'envolent dans le terminal.

Préfixe: (aucun)

Variable d'environnement: POE_TRACE_FILENAME

TRACE_FILES

TRACE_FILES active ou désactive les traces sur les moniteurs de fichiers de POE et sur la classe POE::Loop qui implémente le multiplexeur de fichiers bas niveau. Cela peut être utile lorsque l'on recherche un comportement étrange lié aux fichiers.

Préfixe: <fh>

Variable d'environnement: POE_TRACE_FILES

TRACE_REFCNT

TRACE_REFCNT contrôle si POE::Kernel tracera les compteurs de références des sessions. Comme discuté dans "Durées de vie des sessions", POE effectue un grand nombre de comptages de références, et l'état actuel des compteurs de références d'une session détermine si la session vit ou meurt. Il est courant que les développeurs se demandent pourquoi une session s'arrête trop tôt ou reste active trop longtemps. TRACE_REFCNT peut aider à expliquer pourquoi.

Préfixe: <rc>

Variable d'environnement: POE_TRACE_REFCNT

TRACE_RETVALS

TRACE_RETVALS peut déclencher une alerte lorsqu'une méthode de POE::Kernel est sur le point de échouer. C'est une forme non fatale mais plus verbeuse de ASSERT_RETVALS.

Préfixe: <rv>

Variable d'environnement: POE_TRACE_RETVALS

TRACE_SESSIONS

TRACE_SESSIONS active les messages de trace liés à la gestion des sessions. Vous serez informé de la création ou de la destruction des sessions, et lorsque le statut parent ou enfant d'une session change.

Préfixe: <ss>

Variable d'environnement: POE_TRACE_SESSIONS

TRACE_SIGNALS

TRACE_SIGNALS active les traces dans le système de gestion des signaux de POE. Le déploiement des signaux est l'un des aspects les plus complexes de POE, et les traces peuvent aider les développeurs à comprendre la propagation et le timing des signaux.

Préfixe: <sg>

Variable d'environnement: POE_TRACE_SIGNALS

USE_SIGCHLD

Utiliser $SIG{CHLD} ou effectuer un sondage à intervalles réguliers?

Ce drapeau est activé par défaut dans Perl >= 5.8.1, car il prend en charge les signaux sûrs. Veuillez consulter perlipc pour plus de détails.

Vous pourriez vouloir le désactiver si vous utilisez une version de Perl connue pour avoir une mauvaise gestion des signaux, ou si un module intermédiaire perturbe $SIG{CHLD}. Un module connu pour faire cela est Apache.

L'activation de ce drapeau entraînera la reprise des fils d'exécution presque immédiatement, plutôt qu'une fois par "CHILD_POLLING_INTERVAL".

DÉBOGAGE DE POE ET DES PROGRAMMES L'UTILISANT

Les tests de POE sont charmants, sombres et profonds. Ces variables d'environnement permettent aux testeurs de prendre des chemins moins fréquentés.

CHILD_POLLING_INTERVAL

L'intervalle auquel "wait" est appelé pour déterminer si des processus enfants doivent être supprimés et si le signal "CHLD" doit être émulé.

Par défaut, 1 seconde.

USE_SIGNAL_PIPE

La seule façon sûre de gérer les signaux est d'implémenter un modèle sans partage. POE construit un tube de signaux qui communique entre les gestionnaires de signaux et la boucle du noyau POE de manière sûre et atomique. Le tube de signaux est implémenté avec POE::Pipe::OneWay, utilisant un conduit "pipe" sur Unix. Malheureusement, le tube de signaux n'est pas compatible avec Windows et n'est pas utilisé sur cette plateforme.

Si vous souhaitez revenir au comportement de signal précédent non sûr, vous devez définir "USE_SIGNAL_PIPE" à 0, ou la variable d'environnement "POE_USE_SIGNAL_PIPE".

CATCH_EXCEPTIONS

Si POE doit exécuter le code du gestionnaire d'événements dans un eval { } et délivrer le signal "DIE" en cas d'erreur.

Voir "Gestion des exceptions".

VARIABLES D'ENVIRONNEMENT POUR LES TESTS

Les tests de POE sont charmants, sombres et profonds. Ces variables d'environnement permettent aux testeurs de prendre des routes moins fréquentées.

POE_DANTIC

Windows et les Perls conçus pour lui ont tendance à être médiocres pour faire des choses à la UNIX, bien qu'ils essaient. POE, étant très à la UNIX, doit sauter beaucoup de tests sous Windows. La variable d'environnement POE_DANTIC, lorsqu'elle est vraie, activera tous ces tests. Elle est destinée à être utilisée de temps en temps pour voir si Windows s'est amélioré dans certains domaines.
