NOM

Pod::POM - Modèle Objet de Pod

SYNOPSIS

use Pod::POM;
my $parser = Pod::POM->new(\%options);
# analyser à partir d'une chaîne de texte
my $pom = $parser->parse_text($text)
    || die $parser->error();
# analyser à partir d'un fichier spécifié par nom ou descripteur de fichier
my $pom = $parser->parse_file($file)
    || die $parser->error();
# analyser à partir de texte ou de fichier 
my $pom = $parser->parse($text_or_file)
    || die $parser->error();
# examiner les avertissements émis
foreach my $warning ($parser->warnings()) {
    warn $warning, "\n";
}
# imprimer la table des matières en utilisant chaque titre =head1
foreach my $head1 ($pom->head1()) {
    print $head1->title(), "\n";
}
# imprimer chaque section
foreach my $head1 ($pom->head1()) {
    print $head1->title(), "\n";
    print $head1->content();
}
# imprimer l'intégralité du document en HTML
use Pod::POM::View::HTML;
print Pod::POM::View::HTML->print($pom);
# créer une vue personnalisée
package My::View;
use parent qw( Pod::POM::View::HTML );
sub view_head1 {
    my ($self, $item) = @_;
    return '<h1>', 
           $item->title->present($self), 
           "</h1>\n",
           $item->content->present($self);
}

package main;
print My::View->print($pom);

DESCRIPTION

Ce module implémente un analyseur pour convertir les documents Pod en une forme de modèle objet simple, appelée ci-après le Modèle Objet de Pod. Le modèle objet est généré sous forme d'arbre hiérarchique de nœuds, chacun représentant un élément différent du document original. L'arbre peut être parcouru manuellement et les nœuds examinés, imprimés ou manipulés d'une autre manière. De plus, Pod::POM prend en charge et fournit des objets de vue qui peuvent parcourir automatiquement l'arbre, ou une partie de celui-ci, et générer une représentation de sortie sous une forme ou une autre.

Examinons un document Pod typique à titre d'exemple.

=head1 NOM
My::Module - juste un autre My::Module
=head1 DESCRIPTION
Ceci est My::Module, un morceau de code Perl profondément funky.
=head2 MÉTHODES
My::Module implémente les méthodes suivantes
=over 4
=item new(\%config)
C'est la méthode constructeur. Elle accepte les options de
configuration suivantes :
=over 4
=item nom
Le nom de la chose.
=item couleur
La couleur de la chose.
=back
=item print()
Ceci imprime la chose.
=back
=head1 AUTEUR
My::Module a été écrit par moi E<lt>moi@ici.orgE<gt>

Ce document contient 3 sections principales, NOM, DESCRIPTION et AUTEUR, chacune étant délimitée par une balise d'ouverture "=head1". NOM et AUTEUR contiennent chacun une seule ligne de texte, mais DESCRIPTION est plus intéressant. Il contient une ligne de texte suivie de la sous-section "=head2", MÉTHODES. Celle-ci contient une ligne de texte et une liste allant de "=over 4" à la "=back" finale juste avant que la section AUTEUR ne commence. La liste contient 2 éléments, new(\%config), qui contient lui-même du texte et une liste de 2 éléments, et print().

Présenté sous forme de texte brut et utilisant l'indentation pour indiquer l'imbrication des éléments, le modèle ressemble alors à ceci :

NOM
    My::Module - juste un autre My::Module
DESCRIPTION
    Ceci est My::Module, un morceau de code Perl profondément funky.
    MÉTHODES
        My::Module implémente les méthodes suivantes
        * new(\%config)
            C'est la méthode constructeur. Elle accepte les 
            options de configuration suivantes :
            * nom
                Le nom de la chose.
            * couleur
                La couleur de la chose.
        * item print()
            Ceci imprime la chose.
AUTEUR
    My::Myodule a été écrit par moi <moi@ici.org>

Ceux d'entre vous qui connaissent le XML préféreront peut-être le visualiser de la manière suivante :

<pod>
  <head1 title="NOM">
    <p>My::Module - juste un autre My::Module</p>
  </head1>
  <head1 title="DESCRIPTION">
    <p>Ceci est My::Module, un morceau de code Perl 
       profondément funky.</p>
    <head2 title="MÉTHODES">
      <p>My::Module implémente les méthodes suivantes</p>
      <over indent=4>
        <item title="item new(\%config)">
          <p>C'est la méthode constructeur. Elle accepte
             les options de configuration suivantes :</p>
          <over indent=4>
            <item title="nom">
              <p>Le nom de la chose.</p>
            </item>
            <item title="couleur">
              <p>La couleur de la chose.</p>
            </item>
          </over>
        </item>
        <item title="print()">
          <p>Ceci imprime la chose.</p>
        </item>
      </over>
    </head2>
  </head1>
  <head1 title="AUTEUR">
    <p>My::Myodule a été écrit par moi &lt;moi@ici.org&gt;
  </head1>
</pod>

Notez comment nous pouvons faire certaines suppositions sur divers éléments. Par exemple, nous pouvons supposer que toute section "=head1" que nous trouvons commence une nouvelle section et termine implicitement toute section précédente. De même, nous pouvons supposer qu'un "=item" se termine lorsque le suivant commence, et ainsi de suite. En termes d'exemple XML présenté ci-dessus, nous disons que nous sommes assez intelligents pour ajouter un élément "</head1>" pour terminer tout "<head1>" précédemment ouvert lorsque nous trouvons une nouvelle balise "=head1" dans le document d'entrée.

Quelle que soit la manière dont vous visualisez le contenu, tout se ramène au même modèle sous-jacent. Le travail du module Pod::POM est de lire un document Pod d'entrée et de construire un modèle objet pour le représenter sous cette forme structurée.

Chaque nœud de l'arbre (c'est-à-dire un élément du document) est représenté par un objet Pod::POM::Node::*. Ceux-ci encapsulent les attributs d'un élément (tel que le titre d'une balise "=head1") et servent également de conteneurs pour d'autres objets Pod::POM::Node::* représentant le contenu de l'élément. Tout en bas, aux nœuds feuilles, nous avons des types d'objets simples pour représenter des paragraphes de texte formaté et verbatim, ainsi que d'autres éléments de base.

Analyse de Pod

Le module Pod::POM implémente les méthodes parse_file($file), parse_text($text) et parse($file_or_text) pour analyser des fichiers Pod et du texte d'entrée. Elles renvoient un objet Pod::POM::Node::Pod pour représenter la racine du Modèle Objet de Pod, c'est-à-dire effectivement l'élément "<pod>" dans l'arbre XML présenté ci-dessus.

use Pod::POM;
my $parser = Pod::POM->new();
my $pom = $parser->parse_file($filename)
    || die $parser->error();

Les méthodes parse(), parse_text() et parse_file() renvoient undef en cas d'erreur. La méthode error() peut être appelée pour récupérer le message d'erreur généré. L'analyse d'un document peut également générer des avertissements non fatals. Ceux-ci peuvent être récupérés via la méthode warnings() qui renvoie une référence à une liste dans un contexte scalaire ou une liste d'avertissements dans un contexte de liste.

foreach my $warn ($parser->warnings()) {
    warn $warn, "\n";
}

Alternativement, l'option de configuration 'warn' peut être définie pour que les avertissements soient automatiquement déclenchés via warn() dès qu'ils sont rencontrés.

my $parser = Pod::POM->new( warn => 1 );

Parcourir le modèle objet

Après avoir analysé un document en un modèle objet, nous pouvons alors sélectionner divers éléments à partir de celui-ci. Chaque nœud implémente des méthodes (via AUTOLOAD) qui correspondent aux attributs et aux éléments de contenu autorisés à l'intérieur.

Pour récupérer la liste des sections '=head1' dans notre document analysé, nous ferions ceci :

my $sections = $pom->head1();

Des méthodes comme celle-ci renverront une liste d'autres objets Pod::POM::Node::* lorsqu'elles sont appelées dans un contexte de liste ou une référence à une liste dans un contexte scalaire. Dans ce dernier cas, la liste est bénie dans la classe Pod::POM::Node::Content, ce qui lui confère certaines propriétés magiques (plus à ce sujet plus tard).

Étant donné la liste d'objets Pod::POM::Node::Head1 retournée par ce qui précède, nous pouvons imprimer les attributs de titre de chacun comme suit :

foreach my $s (@$sections) {
    print $s->title();
}

Regardons la deuxième section, DESCRIPTION.

my $desc = $sections->[1];

Nous pouvons imprimer le titre de chacune de ses sous-sections :

foreach my $ss ($desc->head2()) {
    print $s

Contenu des éléments

Tout cela est bien beau si vous connaissez la structure exacte d'un document à l'avance. Pour les cas plus courants où ce n'est pas le cas, chaque nœud pouvant contenir d'autres nœuds fournit une méthode 'content' pour retourner une liste complète de tous les autres nœuds qu'il contient. La méthode 'type' peut être appelée sur n'importe quel nœud pour retourner son type d'élément (par exemple, 'head1', 'head2', 'over', 'item', etc.).

foreach my $item ($pom->content()) {
    my $type = $item->type();
    if ($type eq 'head1') {
        ...
    }
    elsif ($type eq 'head2') {
        ...
    }
    ...
}

Le contenu d'un élément est représenté par une référence à une liste, bénie dans la classe Pod::POM::Node::Content. Cela fournit une magie sous la forme d'un opérateur de stringification surchargé qui imprimera automatiquement le contenu de la liste si vous imprimez l'objet lui-même. En langage simple, ou plutôt, en Perl simple, cela signifie que vous pouvez faire des choses comme ce qui suit :

foreach my $head1 ($pom->head1()) {
    print '<h1>', $head1->title(), "</h1>\n\n";
    print $head1->content();
}
# imprimer tout le contenu racine
foreach my $item ($pom->content()) {
    print $item;
}
# identique à ci-dessus
print $pom->content();

En fait, tous les objets Pod::POM::Node::* fournissent cette même magie, et tenteront de faire le nécessaire pour se présenter de manière appropriée lorsqu'ils sont imprimés. Ainsi, les éléments suivants sont tous valides.

print $pom;                 # document entier
print $pom->content;        # contenu du document
print $pom->head1->[0];     # juste la première section
print $pom->head1;          # imprimer toutes les sections
foreach my $h1 ($pom->head1()) {
    print $h1->head2();     # imprimer toutes les sous-sections
}

Vues de sortie

Pour comprendre comment les différents éléments se présentent « de la manière appropriée », nous devons introduire le concept de vue. Une vue est simplement une manière particulière de regarder le modèle. Concrètement, nous pouvons penser à une vue comme étant une sorte de type de sortie généré par un convertisseur pod2whatever. Notionnellement, nous pouvons penser à lire un document d'entrée, à construire un Pod Object Model, puis à générer une vue HTML du document, et/ou une vue LaTeX, une vue en texte brut, etc.

Une vue est représentée dans ce cas par une classe d'objet qui contient des méthodes pour afficher chacun des différents types d'éléments qui pourraient être rencontrés dans n'importe quel document Pod. Il existe une méthode pour afficher les sections "=head1" (view_head1()), une autre méthode pour afficher les sections "=head2" (view_head2()), une pour "=over" (view_over()), une autre pour "=item" (view_item()) et ainsi de suite.

Si nous avons une référence à un $node et que nous savons que c'est un nœud 'head1', alors nous pouvons appeler directement la bonne méthode de vue pour qu'il soit affiché correctement :

$view = 'Pod::POM::View::HTML';
$view->view_head1($node);

Ainsi, notre exemple précédent peut être modifié pour être *légèrement* moins laborieux et *marginalement* plus flexible.

foreach my $node ($pom->content) {
    my $type = $node->type();
    if ($type eq 'head1') {
        print $view->view_head1($node);
    }
    elsif ($type eq 'head2') {
        print $view->view_head2($node);
    }
    ...
}

Cependant, c'est toujours loin d'être idéal. Pour nous faciliter la vie, chaque classe Pod::POM::Node::* hérite (ou redéfinit éventuellement) une méthode present($view) de la classe de base Pod::POM::Node. Cette méthode attend une référence à un objet vue passé en argument, et elle appelle simplement la méthode view_xxx() appropriée sur l'objet vue, se renvoyant elle-même comme argument. En jargon objet, cela s'appelle « double dispatch ». La beauté réside dans le fait que vous n'avez pas besoin de savoir quel type de nœud vous avez pour pouvoir l'imprimer. Vous lui passez simplement un objet vue et il se charge du reste.

foreach my $node ($pom->content) {
    print $node->present($view);
}

Si $node est un objet Pod::POM::Node::Head1, alors la méthode view_head1($node) est appelée sur l'objet $view. Sinon, s'il s'agit d'un objet Pod::POM::Node::Head2, alors la méthode view_head2($node) est appelée. Et ainsi de suite, chaque nœud sachant ce qu'il est et où il va, comme s'il était déterminé par un instinct génétique pré-programmé. Remplissant leur destin, pour ainsi dire.

Le double dispatch nous permet de nous passer de toutes les vérifications de type explicites et autres absurdités, et de laisser les objets nœuds eux-mêmes se soucier de la manière dont ils doivent être acheminés. Au prix d'un appel de méthode supplémentaire par nœud, nous obtenons une commodité pour le programmeur, et c'est généralement une bonne chose.

Jetons un coup d'œil à la manière dont les classes de vue et de nœud pourraient être implémentées.

package Pod::POM::View::HTML;
sub view_pod {
    my ($self, $node) = @_;
    return $node->content->present($self);
}
sub view_head1 {
    my ($self, $node) = @_;
    return "<h1>", $node->title->present($self), "</h1>\n\n"
         . $node->content->present($self);
}
sub view_head2 {
    my ($self, $node) = @_;
    return "<h2>", $node->title->present($self), "</h2>\n\n"
         . $node->content->present($self);
}
...
package Pod::POM::Node::Pod;
sub present {
    my ($self, $view) = @_;
    $view->view_pod($self);
}
package Pod::POM::Node::Head1;
sub present {
    my ($self, $view) = @_;
    $view->view_head1($self);
}
package Pod::POM::Node::Head2;
sub present {
    my ($self, $view) = @_;
    $view->view_head2($self);
}
...

Certaines méthodes view_xxx font des appels aux objets nœuds pour afficher leurs attributs et/ou leur contenu. Ceci est montré, par exemple, dans la méthode view_head1() ci-dessus, où la méthode imprime le titre de la section dans les balises "<h1>"..."<h1>", suivi du contenu restant de la section.

Notez que l'attribut title() est imprimé en appelant sa méthode present(), en transmettant la référence à la vue actuelle. De même, la méthode present() du contenu est appelée, lui donnant une chance de faire le nécessaire pour se présenter correctement via l'objet vue.

Il y a de fortes chances que l'attribut titre soit du texte ordinaire, nous pourrions donc être tentés de simplement imprimer le titre plutôt que d'appeler sa méthode present.

sub view_head1 {
    my ($self, $node) = @_;
    # non recommandé, préférez $node->title->present($self)
    return "<h1>", $node->title(), "</h1>\n\n", ...
}

Cependant, il est entièrement valide pour les titres et autres attributs d'éléments, ainsi que pour les blocs de texte réguliers et formatés, de contenir des séquences de code, telles que "B<this>" et "I<this>". Celles-ci sont utilisées pour indiquer différents styles de balisage, marquer des références externes ou des éléments d'index, etc. De plus, elles peuvent être "B<imbriquées I<indéfiniment>>". Pod::POM prend en charge tout cela en analysant ce texte, ainsi que toutes les séquences incorporées, en un Autre Arbre Encore, dont le nœud racine est un objet Pod::POM::Node::Text, contenant éventuellement d'autres objets Pod::POM::Node::Sequence. Lorsque le texte est présenté, l'arbre est automatiquement parcouru et les rappels pertinents sont effectués sur la vue pour les différents types de séquences. Les méthodes appelées sur la vue sont toutes préfixées par 'view_seq_', par exemple 'view_seq_bold', 'view_seq_italic'.

Maintenant, la vraie magie entre en jeu. Vous pouvez définir une vue pour rendre le texte gras/italique dans un style :

package My::View::Text;
use parent qw( Pod::POM::View::Text );
sub view_seq_bold {
    my ($self, $text) = @_;
    return "*$text*";
}
sub view_seq_italic {
    my ($self, $text) = @_;
    return "_$text_";
}

Et une autre vue pour le rendre dans un style différent :

package My::View::HTML;
use parent qw( Pod::POM::View::HTML );
sub view_seq_bold {
    my ($self, $text) = @_;
    return "<b>$text</b>";
}
sub view_seq_italic {
    my ($self, $text) = @_;
    return "<i>$text</i>";
}

Ensuite, vous pouvez facilement visualiser un Pod Object Model dans l'un ou l'autre style :

my $text = 'My::View::Text';
my $html = 'My::View::HTML';
print $pom->present($text);
print $pom->present($html);

Et vous pouvez appliquer cette technique à n'importe quel nœud de l'objet modèle.

print $pom->head1->[0]->present($text);
print $pom->head1->[0]->present($html);

Dans ces exemples, la vue passée à la méthode present() était un nom de classe. Ainsi, les méthodes view_xxx sont appelées en tant que méthodes de classe, comme si elles étaient écrites :

My::View::Text->view_head1(...);

Si votre vue a besoin de maintenir un état, vous pouvez créer un objet vue et le passer à la méthode present().

my $view = My::View->new();
$node->present($view);

Dans ce cas, les méthodes view_xxx sont appelées en tant que méthodes d'objet.

sub view_head1 {
    my ($self, $node) = @_;
    my $title = $node->title();
    if ($title eq 'NAME' && ref $self) {
        $self->{ title } = $title();
    }
    $self->SUPER::view_head1($node);
}

Chaque fois que vous imprimez un objet Pod::POM::Node::*, ou que vous faites quoi que ce soit pour que Perl le transforme en chaîne (comme l'inclure dans une autre chaîne entre guillemets "comme $this"), sa méthode present() est automatiquement appelée. Lorsqu'elle est appelée sans argument de vue, la méthode present() utilise la vue par défaut spécifiée dans $Pod::POM::DEFAULT_VIEW, qui est, par défaut, 'Pod::POM::View::Pod'. Cette vue régénère le document Pod original, bien qu'il convient de noter que la sortie générée peut ne pas être exactement la même que l'entrée. Le parseur est suffisamment intelligent pour détecter certaines erreurs courantes (par exemple, ne pas terminer un "=over" par un "=back") et les corriger automatiquement. Ainsi, vous pourriez trouver un "=back" correctement placé dans la sortie, même si vous avez oublié de l'ajouter à l'entrée. De telles corrections génèrent des avertissements non critiques qui peuvent ensuite être examinés via la méthode warnings().

Vous pouvez mettre à jour la variable de paquetage $Pod::POM::DEFAULT_VIEW pour définir la v

d'affichage par défaut, ou appelez la méthode default_view(). La méthode default_view() chargera automatiquement tout paquet que vous spécifiez. Si vous définissez la variable de paquet directement, vous devez vous assurer que tous les paquets requis ont été préchargés.

use My::View::HTML;
$Pod::POM::DEFAULT_VIEW = 'My::View::HTML';

ou

Pod::POM->default_view('My::View::HTML');

Vues Template Toolkit

L'une des motivations pour écrire ce module était de faciliter la personnalisation de la documentation Pod pour qu'elle corresponde à votre propre apparence ou à vos conventions de formatage locales. En séparant clairement le contenu (représenté par le Pod Object Model) du style de présentation (représenté par une ou plusieurs vues), il devient beaucoup plus facile d'y parvenir.

La dernière version de Template Toolkit (2.06 au moment de la rédaction) fournit un plugin Pod pour l'interface avec ce module. Elle implémente également une nouvelle directive VIEW (mais expérimentale) qui peut être utilisée pour construire différents styles de présentation pour convertir le Pod en d'autres formats. Template Toolkit est disponible sur CPAN :

http://www.cpan.org/modules/by-module/Template/

Les vues Template Toolkit sont similaires aux objets Pod::POM::View décrits ci-dessus, sauf qu'elles permettent d'écrire le style de présentation pour chaque composant Pod sous forme de fichier modèle ou de bloc plutôt que de méthode d'objet. La syntaxe et la structure précises de la directive VIEW sont susceptibles de changer (étant donné qu'elle est encore expérimentale), mais à l'heure actuelle, elle peut être utilisée pour définir une vue ressemblant à ceci :

[% VIEW myview %]
   [% BLOCK view_head1 %]
      <h1>[% item.title.present(view) %]</h1>
      [% item.content.present(view) %]
   [% END %]

   [% BLOCK view_head2 %]
      <h2>[% item.title.present(view) %]</h2>
      [% item.content.present(view) %]
   [% END %]
   ...
[% END %]

Un plugin est fourni pour l'interface avec le module Pod::POM :

[% USE pod %]
[% pom = pod.parse('/path/to/podfile') %]

L'instance Pod Object Model retournée peut alors être parcourue et présentée via la vue de presque toutes les manières imaginables :

<h1>Table des matières</h1>
<ul>
[% FOREACH section = pom.head1 %]
   <li>[% section.title.present(view) %]
[% END %]
</ul>
<hr>
[% FOREACH section = pom.head1 %]
   [% section.present(myview) %]
[% END %]

Vous pouvez soit passer une référence à la VUE (myview) à la méthode present() d'un nœud Pod::POM :

[% pom.present(myview) %]       # présente le document entier

Ou alternativement, appeler la méthode print() de la VUE, en passant le nœud Pod::POM comme argument :

[% myview.print(pom) %]

En interne, la vue appelle la méthode present() sur le nœud, en se passant elle-même comme argument. Elle est donc équivalente à l'exemple précédent.

Le nœud Pod::POM et la vue conspirent pour « Faire ce qu'il faut » pour traiter le bon bloc de modèle pour le nœud. Une référence au nœud est disponible dans le modèle sous la variable 'item'.

[% BLOCK view_head2 %]
   <h2>[% item.title.present(view) %]</h2>
   [% item.content.present(view) %]
[% END %]

La documentation de Template Toolkit contient des informations supplémentaires sur la définition et l'utilisation des vues. Cependant, comme noté ci-dessus, cela peut être sujet à changement ou incomplet en attendant le développement ultérieur de la directive VIEW.

MÉTHODES

new(\%config)

Méthode de constructeur qui instancie et retourne un nouvel objet analyseur Pod::POM.

use Pod::POM;
my $parser = Pod::POM->new();

Une référence à un tableau associatif d'options de configuration peut être passée comme argument.

my $parser = Pod::POM->new( { warn => 1 } );

Par souci de commodité, les options de configuration peuvent également être passées sous forme de liste de paires (clé => valeur).

my $parser = Pod::POM->new( warn => 1 );

Les options de configuration suivantes sont définies :

code
Cette option peut être définie pour que toutes les parties non-Pod du document d'entrée soient stockées dans le modèle d'objet sous forme d'éléments 'code', représentés par des objets de la classe Pod::POM::Node::Code. Elle est désactivée par défaut et les sections de code sont ignorées. 
my $parser = Pod::POM->new( code => 1 );
my $podpom = $parser->parse(\*DATA);
foreach my $code ($podpom->code()) {
    print "<pre>$code</pre>\n";
}
__DATA__
Ceci est du code de programme.
=head1 NOM
...

Cela générera la sortie suivante :

<pre>Ceci est du code de programme.</pre>

Notez que les éléments de code sont stockés dans l'élément POM dans lequel ils sont rencontrés. Par exemple, l'élément de code ci-dessous intégré entre des sections Pod est stocké dans le tableau qui peut être récupéré en appelant "$podpom->head1->[0]->code()".

=head1 NOM
Mon::Module::Nom;
=cut
Du code de programme intégré dans Pod.
=head1 SYNOPSIS
...
warn
Les avertissements non fatals rencontrés lors de l'analyse d'un document Pod sont stockés en interne et disponibles par la suite via la méthode warnings(). 
my $parser = Pod::POM->new();
my $podpom = $parser->parse_file($filename);
foreach my $warning ($parser->warnings()) {
    warn $warning, "\n";
}

L'option 'warn' peut être définie pour que les avertissements soient automatiquement déclenchés via warn() dès qu'ils sont rencontrés.

my $parser = Pod::POM->new( warn => 1 );
my $podpom = $parser->parse_file($filename);

Si la valeur de configuration est spécifiée comme une référence de sous-routine, le code sera appelé chaque fois qu'un avertissement est déclenché, en passant le message d'avertissement comme argument.

sub my_warning {
    my $msg = shift;
    warn $msg, "\n";
};
my $parser = Pod::POM->new( warn => \&my_warning );
my $podpom = $parser->parse_file($filename);
meta
L'option 'meta' peut être définie pour autoriser les balises "=meta" dans le document Pod. 
my $parser = Pod::POM->new( meta => 1 );
my $podpom = $parser->parse_file($filename);

Il s'agit d'une fonctionnalité expérimentale qui ne fait pas partie du POD standard. Par exemple :

=meta author Andy Wardley

Celles-ci sont rendues disponibles en tant qu'éléments de métadonnées dans le nœud racine du POM analysé.

my $author = $podpom->metadata('author');

Voir la section METADATA ci-dessous pour plus d'informations.

parse_file($file)

Analyse le fichier spécifié par son nom ou par une référence à un descripteur de fichier. Retourne une référence à un objet Pod::POM::Node::Pod qui représente le nœud racine du modèle d'objet Pod en cas de succès. En cas d'erreur, undef est retourné et le message d'erreur généré peut être récupéré en appelant error().

my $podpom = $parser->parse_file($filename)
    || die $parser->error();
my $podpom = $parser->parse_file(\*STDIN)
    || die $parser->error();

Tous les avertissements rencontrés peuvent être examinés en appelant la méthode warnings().

foreach my $warn ($parser->warnings()) {
    warn $warn, "\n";
}

parse_text($text)

Analyse la chaîne de texte Pod passée en argument en un modèle d'objet Pod, comme pour parse_file().

parse($texte_ou_$fichier)

Méthode d'usage général qui tente de faire ce qu'il faut en appelant parse_file() ou parse_text() en fonction de l'argument passé.

Une référence de hachage peut être passée comme argument, contenant une clé 'text' ou 'file' et la valeur correspondante.

my $podpom = $parser->parse({ file => $filename })
    || die $parser->error();

Sinon, l'argument peut être une référence à un descripteur d'entrée qui est passé à parse_file().

my $podpom = $parser->parse(\*DATA)
    || die $parser->error();

Si l'argument est une chaîne de texte qui ressemble à du texte Pod (c'est-à-dire qu'elle contient '=' au début d'une ligne), elle est passée à parse_text().

my $podpom = $parser->parse($podtext)
    || die $parser->error();

Sinon, elle est supposée être un nom de fichier et est passée à parse_file().

my $podpom = $parser->parse($podfile)
    || die $parser->error();

TYPES DE NŒUDS, ATTRIBUTS ET ÉLÉMENTS

Cette section liste les différents nœuds qui peuvent être présents dans un Pod Object Model. Ceux-ci sont implémentés comme des instances d'objets Pod::POM::Node::* (par exemple, head1 => Pod::POM::Node::Head1). Pour présenter un nœud, une vue doit implémenter une méthode qui correspond au nom du nœud précédé de 'view_' (par exemple, head1 => view_head1()).

pod
Le nœud "pod" est utilisé pour représenter le nœud racine du Pod Object Model.

Éléments de contenu : head1, head2, head3, head4, over, begin, for, verbatim, text, code.

head1
Un nœud "head1" contient le contenu Pod à partir d'une balise "=head1" jusqu'à la prochaine balise "=head1" ou la fin du fichier.

Attributs : title

Éléments de contenu : head2, head3, head4, over, begin, for, verbatim, text, code.

head2
Un nœud "head2" contient le contenu Pod à partir d'une balise "=head2" jusqu'à la prochaine balise "=head1" ou "=head2" ou la fin du fichier.

Attributs : title

Éléments de contenu : head3, head4, over, begin, for, verbatim, text, code.

Un nœud "head3" contient le contenu Pod à partir d'une balise "=head3"

NAME

Pod::POM - Parse Pod into an Object Model

SYNOPSIS

 use Pod::POM;

 my $parser = Pod::POM->new();
 my $pom    = $parser->parse_file($filename);

 # Traverse the model...
 foreach my $node ( $pom->nodes() ) {
     # ... do something ...
 }

 # ... or use a formatter (view) object ...
 use Pod::POM::View::Text;
 my $formatter = Pod::POM::View::Text->new( width => 78 );
 print $formatter->process($pom);

DESCRIPTION

Pod::POM provides an object-oriented representation of a Pod document. The document is parsed into a tree of nested objects, where each object represents a specific element of the Pod document, such as a section, a paragraph, a list, etc. This object model can then be traversed and processed by 'formatter' or 'view' objects, which can render the Pod document in various formats (e.g. plain text, HTML, etc.).

The primary benefits of using Pod::POM are:

  • Flexibility: The object model can be processed in many different ways, making it easy to create custom formatters.

  • Extensibility: New Pod elements or formatting directives can be added to the model and processed by custom formatters.

  • Structure: Provides a clear and well-defined representation of the Pod document structure.

The core of the module consists of the Pod::POM parser class itself, and a set of classes representing the various nodes within the Pod Object Model (POM).

METHODS

new
Constructor for the Pod::POM parser. Takes an optional hash of configuration options:
 my $parser = Pod::POM->new(
     perl_code  => 1, # Process =begin code /=end code blocks
     meta       => 1, # Process =meta tags
 );
parse_string( $string )
Parses the given string containing Pod content and returns a Pod::POM object representing the document.
parse_file( $filename )
Parses the given file containing Pod content and returns a Pod::POM object representing the document.
parse_fh( $filehandle )
Parses the content from the given filehandle and returns a Pod::POM object representing the document.

The Pod::POM object itself is a node and can be traversed like any other node (see NODE_TYPES, ATTRIBUTES AND ELEMENTS below).

NODE TYPES, ATTRIBUTES AND ELEMENTS

The Pod::POM object model is composed of a tree of nodes. The root node is the Pod::POM object itself. Each node type represents a specific Pod construct and may contain other nodes as its content.

head1
A "head1" node contains the Pod content from a "=head1" tag up to the next "=head1" tag or the end of the file.

Attributes: title

Content elements: head2, head3, head4, over, begin, for, verbatim, text, code.

head2
A "head2" node contains the Pod content from a "=head2" tag up to the next "=head1", "=head2" tag or the end of the file.

Attributes: title

Content elements: head3, head4, over, begin, for, verbatim, text, code.

head3
A "head3" node contains the Pod content from a "=head3" tag up to the next "=head1", "=head2" or "=head3" tag or the end of the file.

Attributes: title

Content elements: head4, over, begin, for, verbatim, text, code.

head4
A "head4" node contains the Pod content from a "=head4" tag up to the next "=head1", "=head2", "=head3" or "=head4" tag or the end of the file.

Attributes: title

Content elements: over, begin, for, verbatim, text, code.

over
The "over" node encloses the Pod content in a list starting at an "=over" tag and continuing up to the matching "=back" tag. Lists may be nested indefinitely.

Attributes: indent (default: 4)

Content elements: over, item, begin, for, verbatim, text, code.

item
The "item" node encloses the Pod content in a list item starting at an "=item" tag and continuing up to the next "=item" tag or a "=back" tag which terminates the list.

Attributes: title (default: *)

Content elements: over, begin, for, verbatim, text, code.

begin
A "begin" node encloses the Pod content in a conditional block starting with a "=begin" tag and continuing up to the next "=end" tag.

Attributes: format

Content elements: verbatim, text, code.

for
A "for" node contains a single paragraph containing text relevant to a particular format.

Attributes: format, text

verbatim
A "verbatim" node contains a verbatim text paragraph which is prefixed by whitespace in the source Pod document (i.e. indented).

Attributes: text

text
A "text" node contains a regular text paragraph. This may include embedded inline sequences.

Attributes: text

code
A "code" node contains Perl code which is by default, not considered to be part of a Pod document. The "code" configuration option must be set for Pod::POM to generate code blocks, otherwise they are ignored.

Attributes: text

INLINE SEQUENCES

Embedded sequences are permitted within regular text blocks (i.e. not verbatim) and title attributes. To present these sequences, a view should implement methods corresponding to the sequence name, prefixed by 'view_seq_' (e.g. bold => view_seq_bold()).

code
Code extract, e.g. C<my code>
bold
Bold text, e.g. B<bold text>
italic
Italic text, e.g. I<italic text>
link
A link (cross reference), e.g. L<My::Module>
space
Text contains non-breaking space, e.g.S<Buffy The Vampire Slayer>
file
A filename, e.g. F</etc/lilo.conf>
index
An index entry, e.g. X<Angel>
zero
A zero-width character, e.g. Z<>
entity
An entity escape, e.g. E<lt>

BUNDLED MODULES AND TOOLS

The Pod::POM module distribution includes a number of sample view objects for rendering Pod Object Models into particular formats. These are incomplete and may require some further work, but serve at present to illustrate the principal and can be used as the basis for your own view objects.

Pod::POM::View::Pod
Regenerates the model as Pod.
Pod::POM::View::Text
Presents the model as plain text.
Pod::POM::View::HTML
Presents the model as HTML.

A script is provided for converting Pod documents to other format by using the view objects provided. The "pom2" script should be called with two arguments, the first specifying the output format, the second the input filename. e.g.

$ pom2 text My/Module.pm > README
$ pom2 html My/Module.pm > ~/public_html/My/Module.html

You can also create symbolic links to the script if you prefer and leave it to determine the output format from its own name.

$ ln -s pom2 pom2text       
$ ln -s pom2 pom2html
$ pom2text My/Module.pm > README
$ pom2html My/Module.pm > ~/public_html/My/Module.html

The distribution also contains a trivial script, "podlint" (previously "pomcheck"), which checks a Pod document for well-formedness by simply parsing it into a Pod Object Model with warnings enabled. Warnings are printed to STDERR.

$ podlint My/Module.pm

The "-f" option can be set to have the script attempt to fix any problems it encounters. The regenerated Pod output is printed to STDOUT.

$ podlint -f My/Module.pm > newfile

METADATA

This module includes support for an experimental new "=meta" tag. This is disabled by default but can be enabled by loading Pod::POM with the "meta" option.

use Pod::POM qw( meta );

Alternately, you can specify the "meta" option to be any true value when you instantiate a Pod::POM parser:

my $parser = Pod::POM->new( meta => 1 );
my $pom    = $parser->parse_file($filename);

Any "=meta" tags in the document will be stored as metadata items in the root node of the Pod model created.

For example:

=meta module Foo::Bar
=meta author Andy Wardley

You can then access these items via the metadata() method.

print "module: ", $pom->metadata('module'), "\n";
print "author: ", $pom->metadata('author'), "\n";

or

my $metadata = $pom->metadata();
print "module: $metadata->{ module }\n";
print "author: $metadata->{ author }\n";

Please note that this is an experimental feature which is not supported by other POD processors and is therefore likely to be most incompatible. Use carefully.
