NOM

POE::NFA - une machine à états asynchrone (automate fini non déterministe)

SYNOPSIS

use POE::Kernel;
use POE::NFA;
use POE::Wheel::ReadLine;
# Démarrer une machine NFA et entrer dans son état initial.
POE::NFA->spawn(
  inline_states => {
    initial => {
      setup => \&setup_stuff,
    },
    state_login => {
      on_entry => \&login_prompt,
      on_input => \&save_login,
    },
    state_password => {
      on_entry => \&password_prompt,
      on_input => \&check_password,
    },
    state_cmd => {
      on_entry => \&command_prompt,
      on_input => \&handle_command,
    },
  },
)->goto_state(initial => "setup")
;
POE::Kernel->run();
exit;
sub setup_stuff {
  $_[RUNSTATE]{io} = POE::Wheel::ReadLine->new(
    InputEvent => 'on_input',
  );
  $_[MACHINE]->goto_state(state_login => "on_entry");
}
sub login_prompt { $_[RUNSTATE]{io}->get('Login: '); }
sub save_login {
  $_[RUNSTATE]{login} = $_[ARG0];
  $_[MACHINE]->goto_state(state_password => "on_entry");
}
sub password_prompt { $_[RUNSTATE]{io}->get('Password: '); }
sub check_password {
  if ($_[RUNSTATE]{login} eq $_[ARG0]) {
    $_[MACHINE]->goto_state(state_cmd => "on_entry");
  }
  else {
    $_[MACHINE]->goto_state(state_login => "on_entry");
  }
}
sub command_prompt { $_[RUNSTATE]{io}->get('Cmd: '); }
sub handle_command {
  $_[RUNSTATE]{io}->put("  <<$_[ARG0]>>");
  if ($_[ARG0] =~ /^(?:quit|stop|exit|halt|bye)$/i) {
    $_[RUNSTATE]{io}->put('Bye!');
    $_[MACHINE]->stop();
  }
  else {
    $_[MACHINE]->goto_state(state_cmd => "on_entry");
  }
}

DESCRIPTION

POE::NFA implémente une variante de POE::Session : une machine à états non déterministe (automate fini). Décomposons cela.

Un automate fini est une machine à états avec un nombre limité d'états et de transitions. Techniquement, les objets POE::NFA peuvent se modifier eux-mêmes à l'exécution, ils ne sont donc pas vraiment « finis ». La modification à l'exécution n'est actuellement pas prise en charge par l'API, donc l'inutilisabilité plausible est maintenue.

Les machines à états déterministes sont celles pour lesquelles toutes les transitions possibles sont connues au moment de la compilation. POE::NFA est « non déterministe » car les transitions peuvent changer en fonction des conditions d'exécution.

Cependant, plus simplement, POE::NFA est comme POE::Session mais avec des gestionnaires d'événements qui peuvent changer en fonction de l'état d'exécution de la machine. Considérez l'exemple SYNOPSIS, qui a des gestionnaires d'événements « on_entry » et « on_input » qui effectuent des tâches différentes selon l'état d'exécution. POE::Wheel::ReadLine va déclencher « on_input », mais des choses différentes se produiront selon que la session est dans son état « login », « password » ou « command ».

POE::NFA hérite fortement de POE::Session, ce document se concentrera donc sur les différences. Veuillez consulter POE::Session pour les sujets similaires.

MÉTHODES PUBLIQUES

Ce document se concentre principalement sur les différences avec POE::Session.

get_current_state

Chaque état de la machine a un nom. get_current_state() renvoie le nom de l'état actuel de la machine. get_current_state() est principalement utilisé pour récupérer l'état d'une autre machine. Il est plus facile (et plus rapide) d'utiliser $_[STATE] dans les gestionnaires d'événements propres à une machine.

get_runstate

get_runstate() renvoie l'état d'exécution de la machine. L'état d'exécution est équivalent aux heaps de POE::Session, donc cette méthode est très similaire à get_heap() de POE::Session. Il est plus facile (et plus rapide) d'utiliser $_[RUNSTATE] dans les gestionnaires d'événements propres à une machine, bien qu'un peu plus lent.

spawn STATE_NAME => HANDLERS_HASHREF[, ...]

spawn() est le constructeur de POE::NFA. Le nom reflète le concept que de nouvelles machines à états sont créées comme des threads ou des processus, plutôt que comme des objets.

La machine elle-même est définie comme une liste de noms d'états et de hachages qui mappent des événements à des gestionnaires dans chaque état.

my %states = (
  state_1 => {
    event_1 => \&handler_1,
    event_2 => \&handler_2,
  },
  state_2 => {
    event_1 => \&handler_3,
    event_2 => \&handler_4,
  },
);

Un événement peut être géré par plusieurs états. Le bon gestionnaire est appelé en fonction de l'état actuel de la machine. Par exemple, si "event_1" est envoyé alors que la machine est dans "state_2", alors handler_3() sera appelé pour gérer l'événement. Le mappage état - événement - gestionnaire est ainsi :

$machine{state_2}{event_1} = \&handler_3;

Au lieu de "inline_states", "object_states" ou "package_states" peuvent être utilisés. Ceux-ci mappent les événements d'un état à un objet ou une méthode de package respectivement.

object_states => {
  state_1 => [
    $object_1 => [qw(event_1 event_2)],
  ],
  state_2 => [
    $object_2 => {
      event_1 => method_1,
      event_2 => method_2,
    }
  ]
}

Dans l'exemple ci-dessus, si "event_1" arrive alors que la machine est dans "state_1", la méthode "event_1" sur $object_1 sera appelée. Si la machine est dans "state_2", la méthode "method_1" sur $object_2 sera appelée.

Les "package_states" sont très similaires, mais au lieu d'utiliser un $object, un "Package::Name" est passé.

Le paramètre "runstate" permet d'initialiser différemment "RUNSTATE" au moment de la création. "RUNSTATE", comme les heaps, sont généralement des hachages anonymes, mais "runstate" peut les définir comme des références de tableaux ou même des objets.

Les transitions d'état ne sont pas exécutées par défaut. Elles sont plutôt mises dans la file d'événements POE derrière tout événement en attente actuel. L'activation de l'option "immediate" fait que les transitions d'état s'exécutent immédiatement, indépendamment de tout événement en attente.

goto_state NEW_STATE[, ENTRY_EVENT[, EVENT_ARGS]]

goto_state() place la machine dans un nouvel état. Si un ENTRY_EVENT est spécifié, alors cet événement sera déclenché après que la machine ait entré dans le nouvel état. EVENT_ARGS, s'ils sont inclus, seront transmis au gestionnaire de l'événement d'entrée via "ARG0..$#_".

# Passer à l'état suivant.
$_[MACHINE]->goto_state( 'next_state' );
# Passer à l'état suivant, et appeler un point d'entrée spécifique.
$_[MACHINE]->goto_state( 'next_state', 'entry_event' );
# Passer à l'état suivant ; appeler un point d'entrée avec quelques valeurs.
$_[MACHINE]->goto_state( 'next_state', 'entry_event', @parameters );

stop

stop() force l'arrêt d'une machine. La machine arrêtera également son exécution gracieusement si elle n'a plus rien à faire, comme POE::Session.

stop() est assez explicite. Il forcera le nettoyage des ressources. Cependant, les références circulaires dans le "RUNSTATE" de la machine ne sont pas sous la responsabilité de POE et peuvent causer des fuites de mémoire.

$_[MACHINE]->stop();

POE::NFA est une machine à états implémentée en Perl. Elle permet la création et la gestion de machines à états avec divers événements et états.

MÉTHODES PUBLIQUES

POE::NFA fournit des méthodes publiques pour la gestion des machines à états. Ces méthodes permettent les transitions entre états, la gestion des événements et le contrôle de l'état de la machine.

CHAMPS D'ÉVÉNEMENTS PRÉDÉFINIS

Les champs d'événements prédéfinis de POE::NFA sont les mêmes que ceux de POE::Session, à l'exception des trois suivants.

MACHINE

"MACHINE" est équivalent au champ "SESSION" de POE::Session. Il contient une référence à la machine à états actuelle et est utile pour appeler ses méthodes.

RUNSTATE

"RUNSTATE" est équivalent au champ "HEAP" de POE::Session. Il contient une référence à une table de hachage anonyme que POE est garanti de ne pas toucher. Les données stockées dans "RUNSTATE" persisteront entre les invocations de gestionnaires.

STATE

"STATE" contient le nom de l'état actuel de la machine. Il n'est équivalent à rien de POE::Session.

EVENT

"EVENT" est équivalent au champ "STATE" de POE::Session. Il contient le nom de l'événement qui a invoqué le gestionnaire actuel. Voir le champ "STATE" de POE::Session pour plus d'informations.

NOMS D'ÉVÉNEMENTS PRÉDÉFINIS

POE::NFA définit quatre événements qui lui sont propres. Ces événements sont utilisés en interne et ne peuvent pas être outrepassés par le code de l'application.

Voir la section "NOMS D'ÉVÉNEMENTS PRÉDÉFINIS" de POE::Session pour plus d'informations sur les autres événements prédéfinis.

Les événements sont : "poe_nfa_goto_state", "poe_nfa_push_state", "poe_nfa_pop_state", "poe_nfa_stop".

Oui, tous les événements internes commencent par "poe_nfa_". D'autres pourraient être ajoutés à l'avenir, mais ils commenceront toujours de la même manière. Par conséquent, veuillez ne pas définir d'événements commençant par "poe_nfa_".

VOIR AUSSI

Bon nombre des fonctionnalités de POE::NFA sont directement tirées de POE::Session. Veuillez consulter POE::Session pour plus d'informations.

La section SEE ALSO dans POE contient une table des matières couvrant l'intégralité de la distribution POE.

BOGUES

Voir la documentation de POE::Session.

POE::NFA n'est pas aussi complet en termes de fonctionnalités que POE::Session. Vos commentaires sont appréciés.
