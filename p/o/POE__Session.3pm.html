NOM

POE::Session - une tâche générique d'événements

SYNOPSIS

use POE; # inclut automatiquement POE::Kernel et POE::Session
POE::Session->create(
  inline_states => {
    _start => sub { $_[KERNEL]->yield("next") },
    next   => sub {
      print "tick...\n";
      $_[KERNEL]->delay(next => 1);
    },
  },
);
POE::Kernel->run();
exit;

POE::Session peut également appeler des méthodes d'objets et de classes via les callbacks "object_states" et "package_states".

DESCRIPTION

POE::Session et ses sous-classes convertissent les événements de POE::Kernel en les conventions d'appel appropriées pour le code des applications. Dans le langage des patrons de conception, POE::Session sont des adaptateurs entre POE::Kernel et le code des applications.

Les sessions gérées par POE::Kernel sont plutôt des structures de tâches génériques. Heureusement, ces deux concepts sont presque identiques dans leur nom.

Une précision sur la nomenclature

Ce document fera référence aux gestionnaires d'événements comme des "états" dans certains cas inévitables. Les sessions étaient à l'origine conçues comme des machines à états événementiels, mais leur but a évolué avec le temps. Certains des anciens termes sont maintenus dans l'API pour des raisons de compatibilité ascendante.

De manière confuse, POE::NFA est une classe pour implémenter réellement des machines à états événementiels. Sa documentation utilise "état" dans le sens propre.

UTILISATION DE POE::Session

POE::Session a deux objectifs principaux. Premièrement, il associe des noms d'événements à du code qui les gère. Deuxièmement, il associe une interface de distribution d'événements cohérente aux gestionnaires.

Considérez l'exemple de la "SYNOPSIS". Une instance de POE::Session est créée avec deux "inline_states", chacun associant un nom d'événement ("_start" et "next") à une sous-routine inline. POE::Session s'assure que "$_[KERNEL]" et ainsi de suite ont du sens dans un gestionnaire d'événements.

Les gestionnaires d'événements peuvent également être des méthodes d'objets ou de classes, en utilisant respectivement "object_states" et "package_states". Le format de "create()" est différent de celui de "inline_states", mais la convention d'appel est presque identique.

Notez que l'objet créé de POE::Session n'a pas été sauvegardé dans une variable. Le nouvel objet POE::Session est donné à POE::Kernel, qui le gère ensuite et utilise toutes ses ressources.

Il est possible de conserver des références aux nouveaux objets POE::Session, mais ce n'est généralement pas nécessaire. Si un programme ne fait pas attention à la clôture de ces références, des références circulaires seront créées, qui seront perdues lorsque POE::Kernel détruira normalement l'objet POE::Session. Il est recommandé de conserver plutôt l'identifiant de la session.

Convention d'appel de POE::Session

Le plus grand obstacle syntaxique que la plupart des gens rencontrent avec POE est la convention d'appel inhabituelle de POE::Session. Par exemple :

sub handle_event {
  my ($kernel, $heap, $parameter) = @_[KERNEL, HEAP, ARG0];
  ...;
}

Ou l'utilisation de "$_[KERNEL]", "$_[HEAP]" et "$_[ARG0]" inline, comme c'est fait dans la plupart des exemples.

Ce qui se passe ici est assez basique. En Perl, les paramètres sont passés aux sous-routines ou méthodes en utilisant le tableau @_ . Les constantes "KERNEL", "HEAP", "ARG0" et d'autres sont exportées par POE::Session (incluses gratuitement lorsque vous utilisez POE). Voici pourquoi c'est utilisé :

1.
Dans le cas courant, passer des paramètres dans @_ est plus rapide que de passer des références de hachage ou de tableau, puis de les déréférencer dans le gestionnaire.
2.
Les erreurs dans les listes de paramètres basées sur des hachages sont soit des erreurs d'exécution douces, soit elles nécessitent une vérification constante à l'exécution. Les constantes sont soit connues à la compilation, soit elles provoquent des erreurs claires à la compilation.
3.
L'accès aux indices de @_ avec des constantes permet de déplacer les paramètres dans le futur sans casser le code des applications.
4.
Les gestionnaires d'événements n'ont pas besoin de tous les éléments de @_. Les slices permettent aux gestionnaires d'utiliser uniquement les paramètres qui les intéressent.

Paramètres de POE::Session

Les gestionnaires d'événements reçoivent la majeure partie de leur contexte d'exécution via jusqu'à neuf paramètres de rappel. POE::Kernel en fournit beaucoup.

"$_[OBJECT]"

"$_[OBJECT]" est "$self" pour les gestionnaires d'événements qui sont des méthodes d'objet. C'est le nom de la classe (paquet) pour les gestionnaires d'événements basés sur une classe. C'est undef pour les callbacks de code plat, qui n'ont pas de valeur spéciale "$self".

"OBJECT" est toujours zéro, car "$_[0]" est toujours "$self" ou "$class" dans les méthodes d'objet et de classe. Les callbacks de code plat ont un placeholder "undef" à "$_[0]" afin que les autres indices restent valides.

Il est utile pour les gestionnaires basés sur des méthodes d'appeler d'autres méthodes du même objet. "$_[OBJECT]" aide à y parvenir.

sub ui_update_everything {
  my $self = $_[OBJECT];
  $self->update_menu();
  $self->update_main_window();
  $self->update_status_line();
}

Vous pouvez également utiliser l'héritage de méthodes. Ici, nous appelons "$self->a_method(@_)". Comme l'opérateur "->" en Perl ajoute "$self" au début de @_, nous devons d'abord déplacer une copie pour conserver les positions des paramètres POE :

sub a_method {
  my $self = shift;
  $self->SUPER::a_method( @_ );
  # ... plus de travail ...
}

"$_[SESSION]"

"$_[SESSION]" est une référence à l'objet de session actuel. Cela permet aux gestionnaires d'accéder aux méthodes de leur session. Les programmes peuvent également comparer "$_[SESSION]" à "$_[SENDER]" pour vérifier que les événements de session internes ne proviennent pas d'autres sessions.

"$_[SESSION]" peut également être utilisé comme cible pour les événements internes de "post()" et "call()". "yield()" est légèrement plus pratique et plus efficace que "post($_[SESSION], ...)" cependant.

Il est mal vu d'accéder directement à une autre session. La méthode recommandée est de manipuler une session via un gestionnaire d'événements.

sub enable_trace {
  my $previous_trace = $_[SESSION]->option( trace => 1 );
  my $id = $_[SESSION]->ID;
  if ($previous_trace) {
    print "Session $id: dispatch trace is still on.\n";
  }
  else {
    print "Session $id: dispatch trace has been enabled.\n";
  }
}

"$_[KERNEL]"

"$_[KERNEL]" est toujours une référence à l'unique instance POE::Kernel du programme d'application. Il est le plus souvent utilisé pour appeler des méthodes de POE::Kernel depuis des gestionnaires d'événements.

# Définir un minuteur de 10 secondes.
$_[KERNEL]->delay( time_is_up => 10 );

"$_[HEAP]"

Chaque objet POE::Session contient son propre espace de noms de variables, connu sous le nom de "HEAP" de sa session. Il est modélisé et nommé d'après les tas de mémoire du processus (pas de priorité). Les tas sont par défaut des références de hachage anonymes, mais peuvent être initialisés dans "create()" pour être presque n'importe quoi. POE::Session lui-même n'utilise jamais "$_[HEAP]", bien que certains composants de POE le fassent.

Les tas ne se chevauchent pas entre les sessions, bien que le paramètre "heap" de "create()" puisse être utilisé pour le faire.

Utilisation de POE::Session avec des Objets

Une session peut gérer des événements dans plusieurs objets. Ou, d'un autre point de vue, plusieurs objets peuvent être combinés en une seule session. Et, que diriez-vous ? Introduisons aussi quelques bouts de code en ligne !

POE::Session->create(
  object_states => [
    $object_1 => { event_1a => "method_1a" },
    $object_2 => { event_2a => "method_2a" },
  ],
  inline_states => {
    event_3 => \&piece_of_code,
  },
);

Cependant, un seul des gestionnaires peut être affecté à un nom d'événement donné. Les doublons écrasent les précédents.

event_1a est géré en appelant "$object_1->method_1a(...)". "$_[OBJECT]" est "$object_1" dans ce cas. "$_[HEAP]" appartient à la session, ce qui signifie que toutes les données stockées ici seront disponibles pour tout autre gestionnaire d'événement, quel que soit l'objet.

event_2a est géré en appelant "$object_2->method_2a(...)". Dans ce cas, "$_[OBJECT]" est "$object_2". "$_[HEAP]" est le même hashref anonyme qui a été passé au gestionnaire d'event_1a, bien que les méthodes soient résolues au moment où l'événement est géré (liaison tardive).

event_3 est géré en appelant "piece_of_code(...)". "$_[OBJECT]" est "undef" ici, car il n'y a pas d'objet. Et, encore une fois, "$_[HEAP]" est le même hashref partagé que les gestionnaires d'event_1a et d'event_2a ont vu.

Fait intéressant, il n'y a aucune raison technique pour qu'un seul objet ne puisse pas gérer les événements de plus d'une session :

for (1..2) {
  POE::Session->create(
    object_states => [
      $object_4 => { event_4 => "method_4" },
    ]
  );
}

Maintenant, "$object_4->method_4(...)" peut être appelé pour gérer les événements d'une de deux sessions. Dans les deux cas, "$_[OBJECT]" sera "$object_4", mais "$_[HEAP]" stockera des données spécifiques à une session particulière.

Il en va de même pour les états en ligne. Une sous-routine peut gérer des événements de plusieurs sessions. "$_[SESSION]" et "$_[HEAP]" peuvent être utilisés dans le gestionnaire pour accéder facilement au contexte de la session dans laquelle l'événement est traité.

MÉTHODES PUBLIQUES

POE::Session n'a que quelques méthodes publiques.

create LOTS_OF_STUFF

create() lance une nouvelle session. Renvoie un nouvel objet POE::Session en cas de succès, bien que la plupart des applications n'auront pas besoin de le conserver.

create() appelle le gestionnaire _start de la session nouvellement lancée avant de la renvoyer.

create() passe également le nouvel objet POE::Session au POE::Kernel. Le noyau POE conserve l'objet pour distribuer les événements. L'objet sera libéré lorsque le noyau détectera que l'objet est devenu mourant. Cela devrait provoquer la destruction de l'objet par Perl si le code d'application ne l'a pas conservé.

create() accepte plusieurs paramètres nommés, dont la plupart sont facultatifs. Cependant, ces paramètres ne sont pas contenus dans un hashref.

args => ARRAYREF

Le paramètre "args" accepte une référence à une liste de paramètres qui seront passés au gestionnaire _start de la session aux positions "ARG0" à "$#_" (la fin de " @_ ").

Cet exemple affichera "arg0 arg1 etc." :

POE::Session->create(
  inline_states => {
    _start => sub {
      print "Session started with arguments: @_[ARG0..$#_]\n";
    },
  },
  args => [ 'arg0', 'arg1', 'etc.' ],
);

heap => ANYTHING

Le paramètre "heap" permet d'initialiser le tas d'une session différemment lors de son instanciation. Les tas sont généralement des hashrefs anonymes, mais "heap" peut les définir comme des références de tableau ou même des objets.

Cet exemple affichera "tree" :

POE::Session->create(
  inline_states => {
    _start => sub {
      print "Slot 0 = $_[HEAP][0]\n";
    },
  },
  heap => [ 'tree', 'bear' ],
);

Vous devez être prudent lors de l'initialisation du tas avec autre chose qu'un comportement de hashref. Certaines bibliothèques supposent un comportement de hashref et échoueront si le tas ne se comporte pas ainsi.

inline_states => HASHREF

"inline_states" mappe les noms d'événements aux sous-routines qui les géreront. Sa valeur est un hashref qui mappe les noms d'événements aux références de code de leurs gestionnaires correspondants :

POE::Session->create(
  inline_states => {
    _start => sub {
      print "arg0=$_[ARG0], arg1=$_[ARG1], etc.=$_[ARG2]\n";
    },
    _stop  => \&stop_handler,
  },
  args => [qw( arg0 arg1 etc. )],
);

Le terme "inline" vient du fait que les références de code peuvent être dans des sous-routines anonymes.

Soyez très prudent avec les fermetures, cependant. "Méfiez-vous des références circulaires".

object_states => ARRAYREF

"object_states" associe un ou plusieurs objets à une session et mappe les noms d'événements aux méthodes des objets qui les géreront. Sa valeur est un arrayref ; les hashrefs ne seraient pas valides.

Ici, _start est géré par "$object->_session_start()" et _stop déclenche "$object->_session_stop()" :

POE::Session->create(
  object_states => [
    $object => {
      _start => '_session_start',
      _stop  => '_session_stop',
    }
  ]
);

POE::Session prend également en charge une forme courte où les noms d'événements et de méthodes sont identiques. Ici, _start invoque "$object->_start()" et _stop déclenche "$object->_stop()" :

POE::Session->create(
  object_states => [
    $object => [ '_start', '_stop' ],
  ]
);

Les méthodes sont vérifiées lors de la création de la session, mais sont également résolues au moment où le gestionnaire est appelé (liaison tardive). La plupart du temps, une méthode ne changera pas, mais dans certains cas, comme l'héritage dynamique, elle pourrait résoudre à une sous-routine différente.

options => HASHREF

Les sessions POE::Session prennent en charge un petit nombre d'options, qui peuvent être initialisées avec le paramètre constructeur "option" et modifiées à l'exécution avec la méthode "option()|/option".

"option" prend un hashref avec des paires option => valeur :

POE::Session->create(
  ... set up h
ndlers ..., options => { trace => 1, debug => 1 }, );

Ceci est équivalent à l'exemple précédent :

POE::Session->create(
  ... configuration des gestionnaires ...,
)->option( trace => 1, debug => 1 );

Les options et valeurs prises en charge sont documentées avec la méthode "option()|/option".

package_states => ARRAYREF

"package_states" associe une ou plusieurs classes à une session et mappe les noms d'événements aux méthodes de classe qui les géreront. Sa fonction est analogue à "object_states", mais ce sont des noms de paquetages qui sont spécifiés plutôt que des objets.

En fait, la documentation suivante est une copie de la description de "object_states" avec quelques substitutions de mots.

La valeur de "package_states" est un ARRAYREF pour être cohérent avec "object_states", même si les noms de classes (également connus sous le nom de noms de paquets) sont déjà des chaînes de caractères, il n'est donc pas nécessaire d'éviter de les convertir en chaînes.

Ici, _start est géré par "$class_name->_session_start()" et _stop déclenche "$class_name->_session_stop()" :

POE::Session->create(
  package_states => [
    $class_name => {
      _start => '_session_start',
      _stop  => '_session_stop',
    }
  ]
);

POE::Session prend également en charge une forme courte où le nom de l'événement et le nom de la méthode sont identiques. Ici, _start invoque "$class_name->_start()", et _stop déclenche "$class_name->_stop()" :

POE::Session->create(
  package_states => [
    $class_name => [ '_start', '_stop' ],
  ]
);

ID

ID() renvoie l'identifiant unique de l'instance de session. Il s'agit d'un entier qui commence à 1 et augmente indéfiniment, ou jusqu'à ce que le nombre revienne à zéro.

Il est théoriquement possible qu'un ID de session ne soit pas unique, mais cela nécessite la création d'au moins 4,29 milliards de sessions au cours de la durée de vie d'un programme. POE garantit cependant qu'aucune session n'aura le même ID en même temps ; votre ordinateur n'a pas assez de mémoire pour stocker 4,29 milliards d'objets de session.

L'ID d'une session est unique dans un processus en cours d'exécution, mais plusieurs processus auront probablement les mêmes ID de session. Si un ID global est requis, il devra inclure à la fois "$_[KERNEL]->ID" et "$_[SESSION]->ID".

option NOM_OPTION [, VALEUR_OPTION [, NOM_OPTION, VALEUR_OPTION]... ]

option() définit et/ou récupère les valeurs de diverses options de session. Les options en question sont implémentées par POE::Session et n'ont aucune signification particulière ailleurs.

Elle peut être appelée avec un seul NOM_OPTION pour récupérer la valeur de cette option.

my $trace_value = $_[SESSION]->option('trace');

option() définit la valeur d'une option lorsqu'elle est appelée avec une seule paire NOM_OPTION, VALEUR_OPTION. Dans ce cas, option() renvoie la valeur précédente de l'option.

my $previous_trace = $_[SESSION]->option(trace => 1);

option() peut également être utilisé pour définir les valeurs de plusieurs options à la fois. Dans ce cas, option() renvoie les valeurs précédentes de toutes les options spécifiées dans un hashref anonyme :

my $previous_values = $_[SESSION]->option(
  trace => 1,
  debug => 1,
);
print "Previous option values:\n";
while (my ($option, $old_value) = each %$previous_values) {
  print "  $option = $old_value\n";
}

POE::Session prend actuellement en charge trois options :

L'option "debug".

L'option "debug" est destinée à activer des avertissements supplémentaires lorsque des choses étranges se produisent au sein de POE::Session. À l'heure actuelle, il n'y a qu'un seul avertissement supplémentaire :

•
La redéfinition d'un gestionnaire d'événements ne provoque généralement pas d'avertissement, mais elle le fera lorsque l'option "debug" sera définie.

L'option "default".

L'activation de l'option "default" transforme les événements inconnus en avertissements, s'il n'y a pas de gestionnaire _default pour les intercepter.

Le drapeau de classe "POE::Session::ASSERT_STATES" est implémenté en activant l'option "default" sur toutes les nouvelles sessions.

L'option "trace".

Activez l'option "trace" pour enregistrer toutes les événements distribués à une session particulière. Il s'agit d'une option de trace spécifique à la session qui permet de déboguer des sessions individuelles.

Le traçage au niveau de la session indique également lorsque les événements sont redirigés vers _default. Cela peut être utilisé pour découvrir des erreurs de nommage d'événements.

Options définies par l'utilisateur.

option() ne vérifie pas si les NOMS_OPTION sont connus, donc option() peut être utilisé pour stocker et récupérer des informations définies par l'utilisateur.

Choisissez les noms d'options avec prudence. Il n'y a pas de convention établie pour éviter les collisions d'espaces de noms entre les options définies par l'utilisateur et les futures options internes.

postback NOM_EVENEMENT, PARAMETRES_EVENEMENT

postback() fabrique des rappels qui publient des événements POE. Il renvoie une référence de code anonyme qui publiera NOM_EVENEMENT à la session cible, avec des PARAMETRES_EVENEMENT optionnels dans une référence de tableau dans ARG0. Les paramètres passés au rappel seront envoyés dans une référence de tableau dans ARG1.

En d'autres termes, ARG0 permet au créateur du postback de transmettre un contexte à travers le postback. ARG1 permet à l'appelant de renvoyer des informations.

Cet exemple crée une référence de code qui, lorsqu'elle est appelée, publie "ok_button" sur $some_session avec ARG0 contenant "[ 8, 6, 7 ]".

my $postback = $some_session->postback( "ok_button", 8, 6, 7 );

Voici un exemple de gestionnaire d'événements pour "ok_button".

sub handle_ok_button {
  my ($creation_args, $called_args) = @_[ARG0, ARG1];
  print "Postback created with (@$creation_args).\n";
  print "Postback called with (@$called_args).\n";
}

Appeler $postback->(5, 3, 0, 9) effectuerait l'équivalent de...

$poe_kernel->post(
  $some_session, "ok_button",
  [ 8, 6, 7 ],
  [ 5, 3, 0, 9 ]
);

Ceci serait affiché lorsque "ok_button" serait distribué à handle_ok_button() :

Postback created with (8 6 7).
Postback called with (5 3 0 9).

Les postbacks détiennent des références à leurs sessions cibles. Par conséquent, les sessions ayant des postbacks en attente resteront actives. Sous tous les boucles d'événements sauf Tk, les postbacks sont bénis afin que DESTROY puisse être appelé lorsque leurs utilisateurs ont terminé. Cela déclenche une décrémentation de leurs compteurs de références, permettant aux sessions de s'arrêter.

Les postbacks ont une méthode, weaken(), qui peut être utilisée pour réduire leur compteur de références sur demande. weaken() renvoie le postback, vous pouvez donc faire :

my $postback = $session->postback("foo")->weaken();

Les postbacks ont été créés comme un adaptateur léger entre les bibliothèques de rappels et POE. Le problème en question était de savoir comment transformer les rappels des widgets de la boîte à outils graphique de Tk en événements POE sans sous-classer plusieurs classes Tk. La solution consistait à fournir à Tk des rappels ordinaires qui publiaient des événements POE.

Puisque postback() et callback() sont des méthodes de session, elles peuvent être appelées sur $_[SESSION] ou $_[SENDER], selon les besoins particuliers. Il existe généralement de meilleures façons d'interagir entre les sessions que d'abuser des postbacks, cependant.

Voici un bref exemple d'attachement d'un bouton Gtk2 à un gestionnaire d'événements POE :

my $btn = Gtk2::Button->new("Clear");
$btn->signal_connect( "clicked", $_[SESSION]->postback("ev_clear") );

Points à retenir : La session restera active tant que $btn existera et détiendra une copie du postback de $_[SESSION]. Tous les paramètres passés par le bouton Gtk2 seront dans ARG1.

callback NOM_EVENEMENT, PARAMETRES_EVENEMENT

callback() fabrique des rappels qui utilisent "$poe_kernel->call()" pour délivrer des événements POE plutôt que "$poe_kernel->post()". Il est identique à postback() à tous les autres égards.

callback() a été créé pour éviter les conditions de concurrence qui surviennent lorsque des bibliothèques externes supposent que les rappels s'exécuteront de manière synchrone. File::Find en est un exemple évident (mais pas nécessairement approprié). Il fournit beaucoup d'informations dans des variables locales qui cessent d'être valides après le rappel. Les informations ne seraient plus disponibles au moment où un événement post()é serait distribué.

get_heap

get_heap() renvoie une référence au tas d'une session. C'est la même valeur que $_[HEAP] pour la session cible. get_heap() est destiné à être utilisé avec $poe_kernel et get_active_session() de POE::Kernel afin que les bibliothèques n'aient pas besoin que ces trois valeurs courantes leur soient explicitement passées.

C'est-à-dire qu'il évite le besoin de :

sub some_helper_function {
  my ($kernel, $session, $heap, @specific_parameters) = @_;
  ...;
}

Plutôt, les fonctions d'aide peuvent utiliser :

use POE::Kernel; # exporte $poe_kernel
sub some_helper_function {
  my (@specific_parameters) = @_;
  my $session = $poe_kernel->get_active_session();
  my $heap = $session->get_heap();
}

Ce n'est pas très pratique pour les personnes qui écrivent des bibliothèques, mais cela rend les bibliothèques beaucoup plus pratiques à utiliser.

L'utilisation de get_heap() pour casser l'encapsulation d'une autre session est fortement déconseillée.

instantiate CREATE_PARAMETERS

instantiate() crée et retourne un objet POE::Session vide. Il est appelé avec les CREATE_PARAMETERS dans une référence de hachage juste avant que create() ne les traite. Les modifications apportées aux CREATE_PARAMETERS affecteront la manière dont create() initialise la nouvelle session.

Les sous-classes peuvent redéfinir instantiate() pour modifier la structure de la session sous-jacente. Elles peuvent étendre instantiate() pour ajouter de nouveaux paramètres à create().

Tous les paramètres non reconnus par create() doivent être supprimés des CREATE_PARAMETERS avant que instantiate() ne retourne. create() plantera s'il découvre des paramètres inconnus.

Assurez-vous de retourner $self depuis instantiate.

sub instantiate {
  my ($class, $create_params) = @_;
  # La classe de base instancie la nouvelle session.
  my $self = $class->SUPER::instantiate($create_parameters);
  # Étendre les paramètres reconnus par create().
  my $new_option = delete $create_parameters->{new_option};
  if (defined $new_option) {
    # ... personnaliser $self ici ...
  }
  return $self;
}

try_alloc START_ARGS

try_alloc() appelle session_alloc() de POE::Kernel pour allouer une structure de session et commencer à gérer la session au sein du noyau de POE. Il est appelé à la fin de create() de POE::Session. Il retourne $self.

C'est un crochet de sous-classement pour la personnalisation tardive de la session avant que create() ne retourne. Il peut également affecter le contenu de @_[ARG0..$#_] qui est passé au gestionnaire _start de la session.

sub try_alloc {
  my ($self, @start_args) = @_;
  # Initialisation tardive.
  # ...
  # Donner $self à POE::Kernel.
  return $self->SUPER::try_alloc(@args);
}

ÉVÉNEMENTS DE POE::Session

Veuillez ne pas définir de nouveaux événements commençant par un trait d'union au début. POE revendique les événements commençant par /^_/ comme étant les siens.

POE::Session ne génère qu'un seul événement, _default. Tous les autres événements internes de POE sont générés par (et documentés dans) POE::Kernel.

_default

_default est l'équivalent de "AUTOLOAD" pour les gestionnaires d'événements. Si POE::Session ne trouve pas de gestionnaire au moment de la distribution, il tente de rediriger l'événement vers le gestionnaire de _default à la place.

S'il n'y a pas de gestionnaire _default, POE::Session supprimera silencieusement l'événement, sauf si l'option "default" est définie.

Pour préserver les informations originales, l'événement original est légèrement modifié avant d'être redirigé vers le gestionnaire _default : les paramètres originaux de l'événement sont déplacés dans une référence de tableau dans ARG1, et le nom de l'événement original est passé à _default dans ARG0.

sub handle_default {
  my ($event, $args) = @_[ARG0, ARG1];
  print(
    "La session ", $_[SESSION]->ID,
    " a intercepté l'événement non géré $event avec (@$args).\n"
  );
}

_default est très flexible. Il peut être utilisé pour le débogage, ou pour gérer des noms d'événements générés dynamiquement sans pré-définir leurs gestionnaires. En ce sens, _default fonctionne de manière analogue à "AUTOLOAD" de Perl.

_default peut également être utilisé comme clause par défaut ou "autrement" d'une instruction switch. Considérez un gestionnaire d'entrée qui déclenche des événements basés sur un nom de commande :

sub parse_command {
  my ($command, @parameters) = split /\s+/, $_[ARG0];
  $_[KERNEL]->post( "cmd_$command", @parameters );
}

Un gestionnaire _default peut être utilisé pour émettre des erreurs pour des commandes inconnues :

sub handle_default {
  my $event = $_[ARG0];
  return unless $event =~ /^cmd_(\S+)/;
  warn "Commande inconnue : $1\n";
}

Le comportement _default est implémenté dans POE::Session, il peut donc être différent pour d'autres types de sessions.

Fonctionnalités de débogage de POE::Session

POE::Session contient une assertion de débogage, pour le moment.

ASSERT_STATES

Définir ASSERT_STATES à vrai fait que chaque session émet un avertissement lorsqu'on lui demande de gérer des événements inconnus. Session.pm implémente les fonctionnalités d'ASSERT_STATES en définissant l'option "default" à vrai au lieu de faux. Voir la méthode option() plus tôt dans ce document pour plus de détails sur l'option "default".

BOGUES

Il y a une possibilité que les ID de session entrent en collision après que la valeur entière de Perl ait débordé. Cela peut se produire après aussi peu que 4,29 milliards de sessions.

Attention aux références circulaires

Comme vous le savez probablement déjà, une référence circulaire est lorsque une variable fait partie d'une chaîne de références qui finit par se référer à elle-même. Perl ne récupérera pas la mémoire impliquée dans une telle chaîne de références tant que la chaîne ne sera pas manuellement rompue.

Ici, une POE::Session est créée qui se réfère à elle-même via un scalaire externe. Les gestionnaires d'événements importent $session via des fermetures qui sont ensuite stockées dans $session. Même si cette session s'arrête, les références circulaires resteront.

my $session;
$session = POE::Session->create(
  inline_states => {
    _start => sub {
      $_[HEAP]->{todo} = [ qw( step1 step2 step2a ) ],
      $_[KERNEL]->post( $session, 'next' );
    },
    next => sub {
      my $next = shift @{ $_[HEAP]->{todo} };
      return unless $next;
      $_[KERNEL]->post( $session, $next );
    }
    # ....
  }
);

Réduit à l'essentiel :

my %event_handlers;
$event_handler{_start} = sub { \%event_handlers };

Notez également qu'une sous-routine anonyme crée une fermeture sur toutes les variables lexicales dans la portée où elle a été définie, même si elle n'y fait pas référence. $session est toujours détenue dans une référence circulaire ici :

my $self = $package->new;
my $session;
$session = POE::Session->create(
  inline_state => {
    _start => sub { $self->_start( @_[ARG0..$#_] ) }
  }
);

Pour éviter cela, une session peut définir un alias pour elle-même. D'autres parties du programme peuvent alors y faire référence par alias. Dans ce cas, il n'est pas nécessaire de suivre la session soi-même (POE::Kernel s'en chargera de toute façon).

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[HEAP]->{todo} = [ qw( step1 step2 step2a ) ],
      $_[KERNEL]->alias_set('step_doer');
      $_[KERNEL]->post( 'step_doer', 'next' );
    },
    next => sub {
      my $next = shift @{ $_[HEAP]->{todo} };
      return unless $next;
      $_[KERNEL]->post( 'step_doer', $next );
    }
    # ....
  }
);

Les alias ne sont même pas nécessaires dans l'exemple précédent car la session se réfère à elle-même. On pourrait plutôt utiliser la méthode yield() de POE::Kernel pour renvoyer l'événement à la session actuelle :

next => sub {
  my $next = shift @{ $_[HEAP]->{todo} };
  return unless $next;
  $_[KERNEL]->yield( $next );
}

Ou le paramètre "$_[SESSION]" passé à chaque gestionnaire d'événements, mais yield() est plus efficace.

next => sub {
  my $next = shift @{ $_[HEAP]->{todo} };
  return unless $next;
  $_[KERNEL]->post( $_[SESSION], $next );
}

Dans la même veine que "$_[SESSION]", une session peut répondre à l'expéditeur d'un événement en postant à "$_[SENDER]". C'est idéal pour répondre aux requêtes.

Si un programme doit conserver une sorte de référence de session dynamique, il est recommandé d'utiliser l'ID numérique de la session plutôt que l'objet lui-même. Un ID de session peut être reconverti en son objet, mais post() accepte les ID de session ainsi que les objets et les alias :

my $session_id;
$session_id = POE::Session->create(
  inline_states => {
    _start => sub {
      $_[HEAP]->{todo} = [ qw( step1 step2 step2a ) ],
      $_[KERNEL]->post( $session_id, 'next' );
    },
    # ....
  }
)->ID;
