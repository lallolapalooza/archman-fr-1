POE::Wheel::Run(3) Documentation Perl fournie par l'utilisateur POE::Wheel::Run(3)

NOM

POE::Wheel::Run - exécute de manière portable du code bloquant et des programmes dans des sous-processus

SYNOPSIS

#!/usr/bin/perl
use warnings;
use strict;
use POE qw( Wheel::Run );
POE::Session->create(
  inline_states => {
    _start           => \&on_start,
    got_child_stdout => \&on_child_stdout,
    got_child_stderr => \&on_child_stderr,
    got_child_close  => \&on_child_close,
    got_child_signal => \&on_child_signal,
  }
);
POE::Kernel->run();
exit 0;
sub on_start {
  my $child = POE::Wheel::Run->new(
    Program => [ "/bin/ls", "-1", "/" ],
    StdoutEvent  => "got_child_stdout",
    StderrEvent  => "got_child_stderr",
    CloseEvent   => "got_child_close",
  );
  $_[KERNEL]->sig_child($child->PID, "got_child_signal");
  # Les événements du Wheel incluent l'ID du wheel.
  $_[HEAP]{children_by_wid}{$child->ID} = $child;
  # Les événements de signal incluent l'ID du processus.
  $_[HEAP]{children_by_pid}{$child->PID} = $child;
  print(
    "Enfant pid ", $child->PID,
    " démarré comme wheel ", $child->ID, ".\n"
  );
}
# Événement de Wheel, incluant l'ID du wheel.
sub on_child_stdout {
  my ($stdout_line, $wheel_id) = @_[ARG0, ARG1];
  my $child = $_[HEAP]{children_by_wid}{$wheel_id};
  print "pid ", $child->PID, " STDOUT: $stdout_line\n";
}
# Événement de Wheel, incluant l'ID du wheel.
sub on_child_stderr {
  my ($stderr_line, $wheel_id) = @_[ARG0, ARG1];
  my $child = $_[HEAP]{children_by_wid}{$wheel_id};
  print "pid ", $child->PID, " STDERR: $stderr_line\n";
}
# Événement de Wheel, incluant l'ID du wheel.
sub on_child_close {
  my $wheel_id = $_[ARG0];
  my $child = delete $_[HEAP]{children_by_wid}{$wheel_id};
  # Peut avoir été récupéré par on_child_signal().
  unless (defined $child) {
    print "wid $wheel_id a fermé tous les pipes.\n";
    return;
  }
  print "pid ", $child->PID, " a fermé tous les pipes.\n";
  delete $_[HEAP]{children_by_pid}{$child->PID};
}
sub on_child_signal {
  print "pid $_[ARG1] a terminé avec le statut $_[ARG2].\n";
  my $child = delete $_[HEAP]{children_by_pid}{$_[ARG1]};
  # Peut avoir été récupéré par on_child_close().
  return unless defined $child;
  delete $_[HEAP]{children_by_wid}{$child->ID};
}

DESCRIPTION

POE::Wheel::Run exécute un programme ou un bloc de code dans un sous-processus, créé de la manière habituelle : en utilisant fork(). Le processus parent peut échanger des informations avec l'enfant via les flux de fichiers STDIN, STDOUT et STDERR de l'enfant.

Dans le processus parent, l'objet POE::Wheel::Run représente le processus enfant. Il dispose de méthodes telles que PID() et kill() pour interroger et gérer le processus enfant.

La méthode put() de POE::Wheel::Run envoie des données au STDIN de l'enfant. La sortie de l'enfant sur STDOUT et STDERR peut être dispatchée sous forme d'événements dans le parent, si demandé.

POE::Wheel::Run peut également notifier le parent lorsque l'enfant a fermé ses flux de fichiers de sortie. Certains programmes restent actifs, mais ils ferment leurs flux de fichiers de sortie pour indiquer qu'ils ont terminé l'écriture.

Une manière plus fiable de détecter la sortie de l'enfant est d'utiliser la méthode sig_child() de POE::Kernel pour attendre que le processus du wheel soit récupéré. Il est en fait essentiel d'utiliser sig_child() dans toutes les circonstances car sans cela, POE n'essaiera pas de récupérer les processus enfants.

Le fait de ne pas utiliser sig_child() a par le passé conduit à des machines bloquées. Les programmes de longue durée ont laissé fuir des processus, consommant éventuellement toutes les places disponibles dans la table des processus et nécessitant des redémarrages.

Étant donné que les fuites de processus sont si graves, POE::Kernel vérifiera cette condition à la sortie et affichera un avis s'il constate que des processus fuient. Les développeurs doivent tenir compte de ces avertissements.

POE::Wheel::Run communique par défaut avec le processus enfant sur une base ligne par ligne. Les programmes peuvent outrepasser cela en spécifiant un autre objet POE::Filter dans "StdinFilter", "StdoutFilter", "StdioFilter" et/ou "StderrFilter".

MÉTHODES PUBLIQUES

Constructeur

Les sous-classes de POE::Wheel ont tendance à effectuer beaucoup de configurations afin qu'elles s'exécutent plus légèrement et plus rapidement. Le constructeur de POE::Wheel::Run ne fait pas exception.

new

new() crée et retourne un nouvel objet POE::Wheel::Run. S'il réussit, l'objet représentera un processus enfant avec certaines qualités spécifiées. Il fournit également une interface orientée objet et événementielle pour interagir de manière asynchrone avec le processus.

Conduit

Conduit spécifie le mécanisme de communication inter-processus qui sera utilisé pour passer des données entre le processus parent et enfant. Conduit peut être l'une des valeurs "pipe", "socketpair", "inet", "pty", ou "pty-pipe". POE::Wheel::Run utilisera le Conduit le plus approprié pour le système d'exploitation au moment de l'exécution (pas au moment de la compilation), mais cela varie d'un OS à l'autre.

En interne, POE::Wheel::Run passe le type de Conduit à POE::Pipe::OneWay et POE::Pipe::TwoWay. Ces classes d'aide ont été créées pour rendre l'IPC portable et réutilisable. Elles ne nécessitent pas le reste de POE.

Trois types de Conduit utilisent des pipes ou des communications inter-processus de type pipe : "pipe", "socketpair" et "inet". Ils déterminent si l'IPC interne utilise pipe(), socketpair() ou des sockets Internet. Ces valeurs de Conduit sont transmises à POE::Pipe::OneWay ou POE::Pipe::TwoWay en interne.

Le type de conduit "pty" exécute le processus enfant sous un pseudo-tty, qui est créé par IO::Pty. Les pseudo-ttys (ptys) persuadent les processus enfants qu'ils interagissent avec des terminaux plutôt qu'avec des pipes. Cela peut être utilisé pour tromper des programmes comme ssh en leur faisant croire qu'il est sûr de demander un mot de passe, bien que les identités sans phrase secrète puissent être meilleures pour cela.

Le conduit "pty" ne peut pas séparer STDERR de STDOUT, mais le mode "pty-pipe" le peut.

Le conduit "pty-pipe" utilise un pty pour STDIN et STDOUT et un pipe unidirectionnel pour STDERR. Le pipe supplémentaire maintient la sortie STDERR séparée de STDOUT.

Le module IO::Pty n'est chargé que si "pty" ou "pty-pipe" est utilisé. Ce n'est une dépendance que lorsqu'il est réellement nécessaire.

Winsize

Winsize définit la taille du terminal du processus enfant. Sa valeur doit être un tableau référencé avec quatre éléments. Les deux premiers éléments doivent être respectivement le nombre de lignes et de colonnes pour la fenêtre du terminal de l'enfant. La paire d'éléments suivante décrit les dimensions X et Y du terminal en pixels. Si la dernière paire est manquante, elles seront calculées à partir des lignes et des colonnes en utilisant une taille de cellule de 9x16.

$_[HEAP]{child} = POE::Wheel::Run->new(
  # ... entre autres choses ...
  Winsize => [ 25, 80, 720, 400 ],
);

Winsize n'est valide que pour les conduits qui utilisent des pseudo-ttys : "pty" et "pty-pipe". Les autres conduits ne simulent pas de terminaux, ils n'ont donc pas de tailles de fenêtre.

Winsize est par défaut la taille de fenêtre du processus parent, en supposant que le processus parent a un terminal à interroger.

CloseOnCall

CloseOnCall, lorsqu'il est vrai, active l'émulation close-on-exec pour les sous-processus qui n'appellent pas réellement exec(). Il s'agirait des cas où l'enfant exécute un bloc de code plutôt que d'exécuter un programme externe. Par exemple :

$_[HEAP]{child} = POE::Wheel::Run->new(
  # ... entre autres choses ...
  CloseOnCall => 1,
  Program => \&some_function,
);

CloseOnCall est désactivé (0) par défaut.

CloseOnCall fonctionne en fermant tous les descripteurs de fichiers supérieurs à $^F dans le processus enfant avant d'appeler le code de l'application. Pour plus de détails, veuillez consulter la discussion sur $^F dans perlvar.

StdioDriver

StdioDriver spécifie un seul objet POE::Driver à utiliser pour STDIN et STDOUT. C'est équivalent à définir "StdinDriver" et "StdoutDriver" sur le même objet POE::Driver.

POE::Wheel::Run créera et utilisera un pilote POE::Driver::SysRW si aucun n'est spécifié. C'est de loin le cas d'utilisation le plus courant, c'est donc le défaut.

StdinDriver

"StdinDriver" définit le POE::Driver utilisé pour écrire dans le conduit IPC STDIN du processus enfant. Il n'est presque jamais nécessaire. L'omettre permettra à POE::Wheel::Run d'utiliser un objet POE::Driver::SysRW créé en interne.

StdoutDriver

"StdoutDriver" définit l'objet POE::Driver qui sera utilisé pour lire à partir du STDOUT du processus enfant.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

conduit. Il n'est presque jamais nécessaire. S'il est omis, POE::Wheel::Run créera et utilisera en interne un objet POE::Driver::SysRW.

StderrDriver

"StderrDriver" définit le pilote qui sera utilisé pour lire depuis le conduit STDERR du processus enfant. Comme avec "StdoutDriver", il est presque toujours préférable de laisser POE::Wheel::Run instancier son propre pilote.

CloseEvent

CloseEvent contient le nom d'un événement que la roue émettra lorsque le processus enfant fermera son dernier descripteur de sortie ouvert. C'est une notification cohérente que l'enfant a fini d'envoyer des sorties. Veuillez noter que cela ne signale pas la sortie du processus enfant. Les programmes devraient utiliser sig_child() pour le détecter.

Bien qu'il soit impossible que ErrorEvent ou StdoutEvent se produisent après CloseEvent, il n'y a aucune garantie pour CHLD, qui peut se produire avant ou après CloseEvent.

En plus des paramètres POE habituels, chaque CloseEvent est livré avec l'un des siens :

"ARG0" contient l'identifiant unique de la roue. Ceci peut être utilisé pour séparer plusieurs processus enfants lorsqu'ils sont gérés par la même session.

Un exemple de gestionnaire d'événement de fermeture :

sub close_state {
  my ($heap, $wheel_id) = @_[HEAP, ARG0];
  my $child = delete $heap->{child}->{$wheel_id};
  print "L'enfant ", $child->PID, " a terminé.\n";
}

ErrorEvent

ErrorEvent contient le nom d'un événement à émettre si quelque chose échoue. Il est facultatif ; s'il est omis, la roue ne notifiera pas sa session si des erreurs se produisent. Cependant, POE::Wheel::Run->new() lèvera toujours une exception en cas d'échec.

"ARG0" contient le nom de l'opération qui a échoué. Il peut s'agir de 'read', 'write', 'fork', 'exec' ou du nom d'une autre fonction ou tâche. Les valeurs réelles ne sont pas encore définies. Elles ne correspondront probablement pas aussi neatly aux noms des fonctions intégrées de Perl.

"ARG1" et "ARG2" contiennent des valeurs numériques et textuelles pour $!, respectivement. "$!" sera égal à "" pour une erreur de lecture 0 (le processus enfant a fermé le descripteur de fichier).

"ARG3" contient l'identifiant unique de la roue.

"ARG4" contient le nom du descripteur de fichier enfant qui présente l'erreur. Il peut s'agir de "STDIN", "STDOUT", ou "STDERR". Le sens de "ARG0" sera l'opposé de ce à quoi vous pourriez normalement vous attendre pour ces descripteurs. Par exemple, POE::Wheel::Run signalera une erreur de "lecture" sur "STDOUT" car il a essayé de lire des données depuis le STDOUT de l'enfant.

Un exemple de gestionnaire d'événement d'erreur :

sub error_state {
  my ($operation, $errnum, $errstr, $wheel_id) = @_[ARG0..ARG3];
  $errstr = "l'autre extrémité a été fermée" if $operation eq "read" and !$errnum;
  warn "La roue $wheel_id a généré une erreur $operation $errnum: $errstr\n";
}

Notez que sauf si vous désactivez le tuyau de signal, vous pourriez également voir une erreur "EIO" (5) lors des opérations de lecture.

StdinEvent

StdinEvent contient le nom d'un événement que Wheel::Run émet chaque fois que tout ce qui est mis en file d'attente par sa méthode put() a été envoyé au descripteur STDIN de l'enfant. C'est l'équivalent de l'événement FlushedEvent de POE::Wheel::ReadWrite.

StdinEvent ne vient qu'avec un paramètre supplémentaire : "ARG0" contient l'identifiant unique de la roue qui a envoyé l'événement.

StdoutEvent

StdoutEvent contient le nom d'un événement que Wheel::Run émet chaque fois que le processus enfant écrit quelque chose sur son descripteur STDOUT. En d'autres termes, quoi que l'enfant imprime sur STDOUT, le parent reçoit un StdoutEvent --- à condition que l'enfant imprime quelque chose de compatible avec le StdoutFilter du parent.

StdoutEvent vient avec deux paramètres. "ARG0" contient les informations que l'enfant a écrites sur STDOUT. "ARG1" contient l'identifiant unique de la roue qui a lu la sortie.

sub stdout_state {
  my ($heap, $input, $wheel_id) = @_[HEAP, ARG0, ARG1];
  print "Le processus enfant dans la roue $wheel_id a écrit sur STDOUT : $input\n";
}

StderrEvent

StderrEvent se comporte exactement comme StdoutEvent, sauf pour les données que le processus enfant écrit sur son descripteur STDERR.

StderrEvent vient avec deux paramètres. "ARG0" contient les informations que l'enfant a écrites sur STDERR. "ARG1" contient l'identifiant unique de la roue qui a lu la sortie.

sub stderr_state {
  my ($heap, $input, $wheel_id) = @_[HEAP, ARG0, ARG1];
  print "Le processus enfant dans la roue $wheel_id a écrit sur STDERR : $input\n";
}

RedirectStdout

Il s'agit d'un descripteur de fichier ou d'un nom de fichier vers lequel la sortie standard sera redirigée. Il est erroné d'utiliser cette option en même temps que StdoutEvent. Ceci est utile au cas où votre programme a besoin d'avoir des entrées/sorties standard, mais ne se soucie pas réellement que leur contenu soit visible pour le parent.

RedirectStderr

Tout comme RedirectStdout, mais avec la sortie d'erreur standard. Il est erroné de l'utiliser avec StderrEvent.

RedirectStdin

Il s'agit d'un descripteur de fichier ou d'un nom de fichier que le processus enfant utilisera comme entrée standard. Il est erroné d'utiliser cette option avec StdinEvent.

RedirectOutput

Ceci redirigera stderr et stdout vers le même descripteur de fichier. C'est équivalent à faire quelque chose comme

$ quelque chose > /chemin/vers/sortie 2>&1

dans un shell bourne.

NoStdin

Alors que les descripteurs de fichiers de sortie seront fermés s'il n'y a pas d'événements à recevoir sur eux, stdin est ouvert par défaut - car l'absence d'un gestionnaire d'événements ne signifie pas nécessairement qu'il n'y a pas de flux d'entrée souhaité. Cette option désactive explicitement la création d'un conduit stdin IPC.

StdioFilter

StdioFilter, s'il est utilisé, doit contenir une instance d'une sous-classe de POE::Filter. Ce filtre décrit comment le parent formatera les données put() pour le STDIN de l'enfant, et comment le parent analysera le STDOUT de l'enfant.

Si STDERR doit également être analysé, alors un StderrFilter séparé sera également nécessaire.

StdioFilter est par défaut une instance de POE::Filter::Line, mais seulement si StdinFilter et StdoutFilter ne sont pas spécifiés. Si StdinFilter ou StdoutFilter est utilisé, alors StdioFilter est illégal.

StdinFilter

StdinFilter peut être utilisé pour spécifier un sérialiseur STDIN particulier différent du parseur STDOUT. S'il est spécifié, il entre en conflit avec StdioFilter. La valeur de StdinFilter, si spécifiée, doit être une instance d'une sous-classe de POE::Filter.

Sans StdinEvent, StdinFilter est illégal.

StdoutFilter

StdoutFilter peut être utilisé pour spécifier un parseur STDOUT particulier différent du sérialiseur STDIN. S'il est spécifié, il entre en conflit avec StdioFilter. La valeur de StdoutFilter, si spécifiée, doit être une instance d'une sous-classe de POE::Filter.

Sans StdoutEvent, StdoutFilter est illégal.

StderrFilter

StderrFilter peut être utilisé pour spécifier un filtre pour la sortie STDERR d'un processus enfant. S'il est omis, POE::Wheel::Run créera et utilisera sa propre instance POE::Filter::Line, mais seulement si un StderrEvent est spécifié.

Sans StderrEvent, StderrFilter est illégal.

Group

Group contient un identifiant de groupe numérique dans lequel le processus enfant doit s'exécuter. Par défaut, le processus enfant s'exécutera dans le même groupe que le parent.

Group n'est pas entièrement portable. Il peut ne pas fonctionner sur les systèmes qui n'ont pas de concept de groupes d'utilisateurs. De plus, le processus parent peut avoir besoin de s'exécuter avec des privilèges élevés pour que l'enfant puisse changer de groupe.

User

User contient un identifiant d'utilisateur numérique qui devrait posséder le processus enfant. Par défaut, le processus enfant s'exécutera en tant que le même utilisateur que le parent.

User n'est pas entièrement portable. Il peut ne pas fonctionner sur les systèmes qui n'ont pas de concept d'utilisateurs. De plus, le processus parent peut avoir besoin de s'exécuter avec des privilèges élevés pour que l'enfant puisse changer d'utilisateur.

NoSetSid

Si vrai, NoSetSid désactive setsid() dans le processus enfant. Par défaut, setsid() est appelé dans le processus enfant afin qu'il puisse s'exécuter dans une session UNIX distincte.

Cette option est obsolète. Comme IO::Pty utilise setsid(), ce module n'a aucun contrôle sur son invocation ou non.

NoSetPgrp

Si vrai, NoSetPgrp désactive setprgp() dans le processus enfant. Par défaut, le processus enfant appelle setpgrp() pour changer son groupe de processus, si le système d'exploitation le prend en charge.

setsid() est utilisé à la place de setpgrp() si Conduit est pty ou pty-pipe. Voir "NoSetSid".

Priority

Priority ajuste le niveau de "niceness" ou de priorité du processus enfant, en fonction de ce que le système d'exploitation sous-jacent supporte (le cas échéant). Priority contient un décalage numérique qui sera ajouté à la priorité du parent pour déterminer celle de l'enfant.

Le décalage de priorité peut être négatif, ce qui en UNIX représente une priorité plus élevée. Cependant, UNIX nécessite des privilèges élevés pour augmenter la priorité d'un processus.

Program

Program spécifie le programme à exec() ou le bloc de code à exécuter dans le processus enfant. Le type de Program est significatif.

Si Program contient un scalaire, sa valeur sera exécutée comme exec($program). Les métacaractères du shell sont significatifs, selon la sémantique de exec(SCALAR).

Si Program contient une référence de tableau, elle sera exécutée comme exec(@$program). Comme pour exec(ARRAY), les métacaractères du shell ne seront pas significatifs.

Si Program contient une référence de code, ce code sera appelé dans le processus enfant. Ce mode permet à POE::Wheel::Run d'exécuter du code interne de longue durée de manière asynchrone, tandis que les modes habituels exécutent des programmes externes. Le processus enfant se terminera après l'exécution de ce code, de manière à éviter l'exécution des blocs DESTROY et END. Voir "Effets secondaires de l'exécution de Coderef" pour plus de détails.

perlfunc contient plus d'informations sur exec() et les différentes manières de l'appeler.

Veuillez éviter d'appeler exit() explicitement lors de l'exécution d'une sous-routine. Le processus enfant hérite de tous les objets du parent, y compris ceux qui peuvent effectuer des effets secondaires. POE::Wheel::Run prend un soin particulier pour éviter les destructeurs d'objets et les blocs END dans le processus enfant, mais l'appel de exit() les déclenchera.

ProgramArgs

S'il est spécifié, ProgramArgs devrait faire référence à une liste de paramètres pour le programme en cours d'exécution.

my @parameters = qw(foo bar baz);  # seront passés à Program
ProgramArgs => \@parameters;

event EVENT_TYPE => EVENT_NAME, ...

event() permet aux programmes de changer les événements émis par $wheel lorsque certaines activités se produisent. EVENT_TYPE peut être l'un des paramètres d'événement décrits dans le constructeur de POE::Wheel::Run.

Cet exemple change les événements émis par $wheel pour l'activité STDIN et STDOUT :

$wheel->event(
  StdinEvent  => 'new-stdin-event',
  StdoutEvent => 'new-stdout-event',
);

Les EVENT_NAMEs non définis désactivent les événements.

put RECORDS

put() met en file d'attente une liste de RECORDS à envoyer au flux d'entrée du processus enfant. Ces RECORDS seront d'abord sérialisés selon le filtre d'entrée de la roue. Les RECORDS sérialisés seront envoyés de manière asynchrone une fois que le gestionnaire d'événements actuel sera retourné.

get_stdin_filter

get_stdin_filter() renvoie l'objet POE::Filter actuellement utilisé pour sérialiser les RECORDS de put() pour le flux d'entrée du processus enfant. L'objet renvoyé peut être utilisé selon sa propre interface.

get_stdout_filter

get_stdout_filter() renvoie l'objet POE::Filter actuellement utilisé pour parser ce que le processus enfant écrit sur STDOUT.

get_stderr_filter

get_stderr_filter() renvoie l'objet POE::Filter actuellement utilisé pour parser ce que le processus enfant écrit sur STDERR.

set_stdio_filter FILTER_OBJECT

Définit StdinFilter et StdoutFilter sur un nouvel objet FILTER_OBJECT. Les données non parsées de STDOUT seront ensuite parsées par le nouvel objet FILTER_OBJECT. Cependant, les données déjà mises en file d'attente par put() resteront sérialisées par l'ancien filtre.

set_stdin_filter FILTER_OBJECT

Définit StdinFilter sur un nouvel objet FILTER_OBJECT. Les données déjà mises en file d'attente par put() resteront sérialisées par l'ancien filtre.

set_stdout_filter FILTER_OBJECT

Définit StdoutFilter sur un nouvel objet FILTER_OBJECT. Les données non parsées de STDOUT seront ensuite parsées par le nouvel objet FILTER_OBJECT.

set_stderr_filter FILTER_OBJECT

Définit StderrFilter sur un nouvel objet FILTER_OBJECT. Les données non parsées de STDERR seront ensuite parsées par le nouvel objet FILTER_OBJECT.

pause_stdout

Met en pause la lecture de STDOUT du processus enfant. Le processus enfant peut se bloquer si le tampon de STDOUT de l'IPC est plein. La lecture peut être reprise avec resume_stdout().

pause_stderr

Met en pause la lecture de STDERR du processus enfant. Le processus enfant peut se bloquer si le tampon de STDERR de l'IPC est plein. La lecture peut être reprise avec resume_stderr().

resume_stdout

Reprend la lecture depuis le flux de sortie du processus enfant. Ceci n'est pertinent que si pause_stdout() a été appelé et reste en vigueur.

resume_stderr

Reprend la lecture depuis le flux d'erreur du processus enfant. Ceci n'est pertinent que si pause_stderr() a été appelé et reste en vigueur.

shutdown_stdin

shutdown_stdin() ferme le flux d'entrée du processus enfant et arrête la roue de signaler StdinEvent. C'est très utile pour exécuter des utilitaires qui attendent EOF sur STDOUT avant de répondre.

ID

ID() renvoie l'identifiant unique de la roue. Chaque événement généré par un objet POE::Wheel::Run inclut un identifiant de roue afin qu'il puisse être comparé à la roue qui l'a émis. Cela permet de gérer plusieurs roues sans confusion quant à quel événement a généré quoi.

ID() n'est pas identique à PID().

PID

PID() renvoie l'identifiant du processus enfant représenté par l'objet POE::Wheel::Run. Il est souvent utilisé comme argument dans sig_child().

PID() n'est pas identique à ID().

kill SIGNAL

La méthode kill() de POE::Wheel::Run envoie un SIGNAL au processus enfant représenté par l'objet. kill() est souvent utilisé pour forcer la fin d'un programme. SIGNAL est l'un des noms de signal présents dans %SIG.

kill() renvoie le nombre de processus correctement signalés : 1 en cas de succès, ou 0 en cas d'échec, car l'objet POE::Wheel::Run n'affecte qu'un seul processus.

kill() envoie SIGTERM si SIGNAL est indéfini ou omis.

get_driver_out_messages

get_driver_out_messages() renvoie le nombre de RECORDS put() qui sont toujours dans la file d'attente de sortie dans la file d'attente de sortie POE::Driver de POE::Wheel::Run. Il est souvent utilisé pour savoir si la roue a d'autres entrées pour le processus enfant.

Dans la plupart des cas, StdinEvent peut être utilisé pour déclencher l'événement lorsque toutes les données ont été envoyées au processus enfant.

get_driver_out_octets

get_driver_out_octets() renvoie le nombre d'octets sérialisés qui sont encore dans la file d'attente de sortie de POE::Wheel::Run. Il est souvent utilisé pour savoir si la roue a d'autres entrées pour le processus enfant.

ASTUCES ET CONSEILS

Support MSWin32

Avant que POE::Wheel::Run ne prenne en charge MSWin32, les utilisateurs devaient utiliser des solutions de contournement personnalisées. Puis Chris Williams (BINGOS) est arrivé et a résolu le problème avec son module POE::Wheel::Run::Win32. Après quelques tests, il a été décidé d'intégrer le code win32 dans POE::Wheel::Run. Tout le monde était content !

Cependant, après quelques recherches, Apocalypse (APOCAL) a découvert que dans certains cas, cela ne fonctionnait toujours pas correctement. La cause première était que le chemin d'accès win32 dans POE::Wheel::Run ne se fermait pas correctement. Cela signifie que les blocs DESTROY et END s'exécutaient ! Après avoir discuté avec plus de monde, la solution n'a pas été très élégante.

Le problème est qu'il n'y a pas d'équivalent à POSIX::_exit() sur MSWin32. Nous espérons que dans une future version de Perl, cela pourra être corrigé ! En attendant, POE::Wheel::Run utilisera CORE::kill() pour terminer le processus enfant. Cependant, cela a un inconvénient : environ 1 Ko sera perdu à chaque exécution. Le code a été amélioré pour réduire la probabilité de cela.

Actuellement, la manière la plus fiable de déclencher cela est d'exécuter un binaire invalide. La définition d'un "binaire invalide" dépend de divers facteurs, mais cela signifie que l'appel à Win32::Job->spawn() a échoué. Cela forcera POE::Wheel::Run à utiliser le travail de redirection pour quitter le processus enfant. Si cela se produit, un gros message sera imprimé sur STDERR du processus enfant et le processus parent recevra le message.

Si vous êtes un hacker Perl MSWin32, veuillez aider à résoudre cette situation ! Consultez le bug rt.cpan.org #56417 et discutez avec nous/p5p pour voir comment vous pouvez contribuer.

Merci de votre patience pendant que nous améliorons POE::Wheel::Run sur MSWin32 !

kill() et ClosedEvent sous Windows

Windows échoue souvent à signaler EOF sur les pipes lorsque les processus enfants sont terminés. La solution consiste à intercepter le signal dans le processus enfant et à quitter normalement :

my $child = POE::Wheel::Run->new(
  Program => sub {
    $SIG{INT} = sub { exit };
    ...;
  },
  ...,
);

Assurez-vous de kill() le processus enfant en utilisant le même signal qu'il intercepte et quitte normalement. N'oubliez pas que tous les signaux ne peuvent pas être interceptés par du code utilisateur.

$child->kill("INT");

Environnement d'Exécution

Il est courant de nettoyer l'environnement du processus du processus enfant, afin que seules les valeurs nécessaires et sûres soient présentes. Cela se traduit par la suppression du contenu de %ENV et sa repeuplement.

Le nettoyage de l'environnement est facile lorsque le processus enfant exécute une sous-routine, mais ce n'est pas aussi facile lorsqu'un programme externe est exécuté.

La façon dont nous procédons est d'exécuter une petite sous-routine dans le processus enfant qui effectue l'appel exec() pour nous.

Program => \&exec_with_scrubbed_env,
sub exec_with_scrubbed_env {
  delete @ENV{keys @ENV};
  $ENV{PATH} = "/bin";
  exec(@program_and_args);
}

Ceci supprime tout de l'environnement et définit un PATH simple et sûr avant d'exécuter un programme.

Effets de Bord de l'Exécution des Références de Code

Le processus enfant est créé via fork(), qui duplique le processus parent, y compris une copie de POE::Kernel, toutes les instances de Session, les événements dans la file d'attente, les observateurs, les flux d'entrée/sortie ouverts, et ainsi de suite.

Lorsqu'un programme externe est exécuté, l'appel UNIX exec() remplace la copie du parent par un tout nouveau programme.

Cependant, lorsqu'on exécute des références internes, nous devons préserver le code et toute mémoire à laquelle il pourrait se référer. Cela entraîne quelques effets potentiels.

POE::Wheel::Run(3pm)

NAME

POE::Wheel::Run - A wheel for running child processes.

SYNOPSIS

 use POE::Wheel::Run;

 # Construct a new wheel.
 my $wheel = POE::Wheel::Run->new(
    Program     => [ 'ls', '-l' ], # The program to run
    CloseOnExit => 0,            # Close pipes when child exits?
    StdinFilter => 'Line',       # Filter for child's STDIN
    StdoutFilter=> 'Line',       # Filter for child's STDOUT
    StderrFilter=> 'Line',       # Filter for child's STDERR
    ErrorHandle => \&my_error_handler, # Handle errors
    );

 # Send input to the child.
 $wheel->send_input("some text\n");

 # When the wheel is no longer needed, call its destructor.
 # $wheel->detach; # Optional: let the wheel run in the background
 # $wheel->kill;   # Optional: kill the child process

 # Or, let POE's garbage collection handle it.

DESCRIPTION

POE::Wheel::Run is a subclass of POE::Wheel. It allows a POE application to run another program as a child process, and communicate with it via its standard input, output, and error.

The wheel handles the creation of the child process, and the management of the pipes that connect to its standard streams. It also provides methods for sending input to the child and for receiving output from it.

PUBLIC METHODS

TIPS AND TRICKS

Exiting from a Child Process

When a child process is forked, the parent's file descriptors and other resources are copied into the child. When the child exits normally, any DESTROY and END blocks are executed there. Later, when the parent exits, they may run again.

POE::Wheel::Run takes steps to avoid running DESTROY and END blocks in the child process. It uses POSIX::_exit() to bypass them. If that fails, it may even kill() itself.

If an application needs to exit explicitly, for example to return an error code to the parent process, then please use POSIX::_exit() rather than Perl's core exit().

POE::Kernel's run() method was never called

This warning is displayed from POE::Kernel's DESTROY method. It's a side effect of calling exit() in a child process that was started before "POE::Kernel->run()" could be called. The child process receives a copy of POE::Kernel where run() wasn't called, even if it was called later in the parent process.

The most direct solution is to call POSIX::_exit() rather than exit(). This will bypass POE::Kernel's DESTROY, and the message it emits.

Running POE::Kernel in the Child

Calling "POE::Kernel->run()" in the child process effectively resumes the copy of the parent process. This is rarely (if ever) desired.

More commonly, an application wants to run an entirely new POE::Kernel instance in the child process. This is supported by first stop()ping the copied instance, starting one or more new sessions, and calling run() again. For example:

Program => sub {
  # Wipe the existing POE::Kernel clean.
  $poe_kernel->stop();
  # Start a new session, or more.
  POE::Session->create(
    ...
  );
  # Run the new sessions.
  POE::Kernel->run();
}

Strange things are bound to happen if the program does not call "stop" in POE::Kernel before "run" in POE::Kernel. However this is vaguely supported in case it's the right thing to do at the time.

CAVEATS & TODOS

POE::Wheel::Run's constructor should emit proper events when it fails. Instead, it just dies, carps or croaks. This isn't necessarily bad; a program can trap the death in new() and move on.

Priority is a delta, not an absolute niceness value.

It might be nice to specify User by name rather than just UID.

It might be nice to specify Group by name rather than just GID.

POE::Pipe::OneWay and Two::Way don't require the rest of POE. They should be spun off into a separate distribution for everyone to enjoy.

If StdinFilter and StdoutFilter seem backwards, remember that it's the filters for the child process. StdinFilter is the one that dictates what the child receives on STDIN. StdoutFilter tells the parent how to parse the child's STDOUT.
