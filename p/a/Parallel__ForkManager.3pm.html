Nom

Parallel::ForkManager - Un gestionnaire de processus parallèle simple

Version

version 2.04

Syntaxe

use Parallel::ForkManager;
my $pm = Parallel::ForkManager->new($MAX_PROCESSES);
DATOS:
foreach my $data (@all_data) {
  # Crée un processus enfant et renvoie son PID :
  my $pid = $pm->start y next DATOS;
  ... effectuer le travail avec $data dans le processus enfant ...
  $pm->finish; # Termine le processus enfant
}

Description

Ce module est conçu pour être utilisé dans des opérations qui peuvent être effectuées en parallèle où le nombre de processus à créer doit être limité. Une utilisation typique est un téléchargeur qui récupérera des centaines/des milliers de fichiers.

Le code d'un téléchargeur ressemblerait à ceci :

use LWP::Simple;
use Parallel::ForkManager;
...
my @links=(
  ["http://www.foo.bar/rulez.data", "rulez_data.txt"],
  ["http://new.host/more_data.doc", "more_data.doc"],
  ...
);
...
# Maximum 30 processus pour le téléchargement parallèle
my $pm = Parallel::ForkManager->new(30);
DATOS:
foreach my $linkarray (@links) {
  $pm->start y next DATOS; # Faire le fork
  my ($link, $fn) = @$linkarray;
  warn "Impossible d'obtenir $fn depuis $link"
    if getstore($link, $fn) != RC_OK;
  $pm->finish; # Quitter le processus enfant
}
$pm->wait_all_children;

Vous devez d'abord instancier le ForkManager avec le constructeur « new ». Vous devez spécifier le nombre maximum de processus à créer. Si vous spécifiez 0 (zéro), aucun processus enfant ne sera créé. Ceci est utile à des fins de débogage.

Ensuite, utilisez $pm->start pour effectuer le fork. $pm renvoie 0 pour le processus enfant et le PID du processus parent (voir également « fork » dans perlfunc). Le « y next » saute la boucle interne dans le processus parent. REMARQUE : $pm->start échoue si le fork échoue.

$pm->finish termine le processus enfant (en supposant qu'un fork a été effectué dans le « start »).

REMARQUE : Vous ne pouvez pas utiliser $pm->start si vous êtes déjà dans un processus enfant. Si vous souhaitez gérer un autre ensemble de processus enfants dans le processus enfant, vous devez instancier un autre objet Parallel::ForkManager !

Méthodes

Le préfixe « # » indique où la méthode doit être exécutée. P pour parent, C pour enfant.

new $processus
Crée un nouvel objet Parallel::ForkManager. Vous devez spécifier le nombre maximum de processus à créer. Si vous spécifiez 0 (zéro), aucun processus enfant ne sera créé. Ceci est utile à des fins de débogage.

Le paramètre optionnel $tempdir n'est utilisé que si vous souhaitez que les enfants renvoient une référence à certaines données (voir RETRIEVING DATASTRUCTURES ci-dessous). S'il n'est pas spécifié, il est défini par un appel à File::Temp::tempdir().

La méthode new se comporte comme une erreur si le répertoire temporaire n'existe pas ou n'est pas un répertoire.

À partir de la version 2.00, le constructeur peut également être appelé dans le style typique de Moo/Moose. Par exemple :

my $fm = Parallel::ForkManager->new(
    max_proc => 4,
    tempdir => '...',
    child_role => 'Parallel::ForkManager::CustomChild',
);
child_role
Renvoie le nom du rôle que le gestionnaire de processus enfant consomme. Par défaut, il s'agit de Parallel::ForkManager::Child et peut être modifié via le constructeur.
start [ $identifiant_processus ]
Cette méthode effectue le fork. Elle renvoie le PID du processus enfant au parent, et 0 au processus enfant. Si le paramètre $processus du constructeur est 0, en supposant que vous êtes dans le processus enfant, $pm->start renvoie simplement 0.

Un paramètre optionnel $identifiant_processus peut être fourni à cette méthode... Il est utilisé par le callback « run_on_finish » (voir CALLBACKS) pour identifier le processus terminé.

start_child [ $identifiant_processus, ] \&callback
Comme la méthode « start », mais exécute le callback en tant qu'enfant. Si le callback renvoie quelque chose, il sera transmis comme données à la mère via « finish() ».
finish [ $code_de_sortie [, $reference_structure_donnees ] ]
Ferme le processus enfant en sortant et accepte un code de sortie optionnel (le code de sortie par défaut est 0), qui peut être récupéré dans le parent via le callback. Si le second paramètre est fourni, l'enfant tente d'envoyer ses données à la mère. Si utilisé en mode débogage ($processus == 0), cette méthode appelle simplement le callback.

Si $reference_structure_donnees est fournie, elle est sérialisée et transmise au processus parent. Voir RETRIEVING DATASTRUCTURES pour plus d'informations.

set_max_procs $processus
Permet de définir un nouveau nombre maximum de processus à maintenir.
wait_all_children
Peut être appelée pour attendre tous les processus qui ont été forkés. Il s'agit d'une attente bloquante.
reap_finished_children
Un appel non bloquant pour récupérer les enfants terminés et exécuter les callbacks indépendamment des appels à « start » ou « wait_all_children ». Utilisez ceci dans des situations où « start » est rarement appelé mais où vous souhaitez exécuter les callbacks rapidement.
is_parent
Renvoie « vrai » si dans le parent ou « faux » si dans l'enfant.
is_child
Renvoie « vrai » si dans l'enfant ou « faux » si dans le parent.
max_procs
Renvoie le nombre maximum de processus que le gestionnaire va créer.
running_procs
Renvoie les PID des processus qui sont surveillés par Parallel::ForkManager. Vous devez noter que les enfants sont toujours signalés comme en cours d'exécution jusqu'à ce que le gestionnaire de processus effectue un appel à « start » ou « wait_all_children ». 
my @pids = $pm->running_procs;
my $nbr_children = $pm->running_procs;
running_procs_with_identifiers
Renvoie une liste de paires. Les clés sont les PID des processus créés (tels que renvoyés par « running_procs »), et les valeurs sont les identifiants donnés à ces PID par « start ». Si aucun identifiant n'a été fourni pour un processus, la valeur pour ce PID sera indéfinie.
wait_for_available_procs( $n )
Attend jusqu'à ce que $n slots de processus soient disponibles. Si $n n'est pas spécifié, la valeur par défaut de 1 est utilisée.
waitpid_blocking_sleep
Renvoie la période de sommeil, en secondes, des appels pseudo-bloquants. La période de sommeil peut être une fraction de seconde.

Renvoie 0 si désactivé.

La valeur par défaut est de 1 seconde.

Voir « BLOCKING CALLS » pour plus de détails.

set_waitpid_blocking_sleep $secondes
Définit la période de sommeil, en secondes, des appels pseudo-bloquants. Définir à 0 pour désactiver.

Voir « BLOCKING CALLS » pour plus de détails.

CALLBACKS

Pour spécifier une sous-routine à exécuter après qu'un enfant ait terminé, vous pouvez utiliser le constructeur pour spécifier une sous-routine et une sous-routine optionnelle pour les processus terminés.

my $pm = Parallel::ForkManager->new(10, undef, undef, \&my_callback);
...
sub my_callback {
  my ($pid, $exit_code, $arg_ref) = @_;
  if ($arg_ref and ref $arg_ref eq 'ARRAY') {
    my ($identifiant, $filename) = @$arg_ref;
    print "Child $pid with identifier $identifiant exited with code $exit_code and processed $filename.\n";
  } else {
    print "Child $pid exited with code $exit_code.\n";
  }
}

Le paramètre $arg_ref est le troisième paramètre de la méthode "finish".

Pour spécifier des sous-routines distinctes pour la terminaison d'enfants et les données des enfants, utilisez la syntaxe de style Moo/Moose :

my $pm = Parallel::ForkManager->new(
    max_proc       => 4,
    run_on_finish  => \&my_finish_callback,
    get_child_data => \&my_child_data_callback,
);
...
sub my_finish_callback {
    my ($pid, $exit_code, $child_ident) = @_;
    print "Child $pid exited with code $exit_code.\n";
    # $child_ident est le 3ème arg de $pm->finish
}
sub my_child_data_callback {
    my ($pid, $child_data, $child_ident) = @_;
    # $child_data est la structure de données retournée par l'enfant
    print "Child $pid returned data. Identifier: $child_ident.\n";
    return $child_data; # Obligatoire si vous voulez utiliser les données
}

Les sous-routines de rappel sont exécutées dans l'ordre suivant :

  1. La sous-routine "run_on_finish" est exécutée.
  2. Si des données ont été retournées par le processus enfant et qu'une sous-routine "get_child_data" a été spécifiée, celle-ci est appelée. Le résultat de cette sous-routine est renvoyé par la méthode "wait_all_children" comme une liste de paires (child_ident, child_data).

La sous-routine "run_on_finish" peut également retourner des données qui seront utilisées par la méthode "wait_all_children".

Les sous-routines de rappel sont appelées dans le processus parent.

Il existe également une sous-routine "on_thread_error" qui est appelée en cas d'erreur lors de la création de threads. Elle est transmise aux arguments du thread.

RETRANSMISSION

Les structures de données peuvent être transmises des enfants aux parents en utilisant la méthode "finish". Les données doivent être sérialisables et désérialisables à l'aide de Storable.

use Storable qw(freeze thaw);
...
my $pm = Parallel::ForkManager->new(4);
$pm->run_on_finish( \&print_results );
DATOS:
foreach my $file (@files_to_process) {
  my $pid = $pm->start and next DATOS;
  # ... traitement du fichier ...
  my $results = { # structure de données à renvoyer
    original_file => $file,
    processed_size => -s $file,
    checksum => compute_checksum($file)
  };
  $pm->finish( 0, $results ); # 0 = code de sortie, $results = structure de données
}

Le processus parent reçoit la structure de données dé-sérialisée.

sub print_results {
  my ($pid, $exit_code, $ident) = @_;
  my $results = $pm->get_child_data($ident); # Récupère les données de l'enfant
  if ($results) {
    print "File: $results->{original_file}, Size: $results->{processed_size}, Checksum: $results->{checksum}\n";
  } else {
    print "Child $pid finished with code $exit_code\n";
  }
}

Notez que vous devez appeler $pm->get_child_data($ident) pour récupérer les données de l'enfant.

Si vous n'utilisez pas de sous-routine de rappel, mais que vous voulez récupérer les données, vous pouvez appeler wait_all_children.

my @children_results = $pm->wait_all_children;
for my $child_result (@children_results) {
  my $pid = $child_result->{pid};
  my $exit_code = $child_result->{code};
  my $data = $child_result->{data};
  print "Child $pid ($exit_code) returned: $data\n";
}

Le tableau @children_results contiendra une liste de hachages contenant les PID, les codes de sortie et les données retournées par les enfants.

APPELS BLOQUANTS

Dans un monde normal, la méthode wait_all_children attendrait l'achèvement de tous les enfants.

Cependant, si la méthode wait_all_children est appelée dans un scénario où il n'y a qu'un seul enfant, alors le comportement par défaut est de ne pas vraiment attendre.

Si la gestion des signaux est importante, vous pourriez souhaiter modifier le comportement de la méthode wait_all_children.

En définissant "waitpid_blocking_sleep" à un nombre différent de 1, vous pouvez modifier la façon dont le programme attend les enfants. Par exemple, si vous définissez "waitpid_blocking_sleep" à 0, alors il ne fera pas d'attente du tout.

Si vous définissez "waitpid_blocking_sleep" à une valeur plus grande, par exemple 5, alors l'attente sera plus longue.

Dans le cas où vous utilisez la méthode reap_finished_children, vous pouvez également spécifier une valeur pour reap_finished_children à la place.

my $pm = Parallel::ForkManager->new(10);
$pm->set_waitpid_blocking_sleep(5); # Attend 5 secondes entre chaque vérification
# Ou
$pm->set_reap_finished_children(5); # Fait des vérifications toutes les 5 secondes

DÉBOGAGE

Si vous souhaitez déboguer le comportement de votre code avec Parallel::ForkManager, vous pouvez instancier le gestionnaire avec 0 processus. Cela désactivera le fork et exécutera simplement le code dans le processus parent.

my $pm = Parallel::ForkManager->new(0); # Désactive le fork
DATOS:
foreach my $data (@all_data) {
  # my $pid = $pm->start y next DATOS; # N'est pas appelé
  ... effectuer le travail avec $data ...
  # $pm->finish; # N'est pas appelé
}

Cela vous permet de tester le code qui s'exécute dans le processus enfant sans avoir à vous soucier du comportement du fork.

CALLBACKS'>CALLBACKS

Vous pouvez définir des rappels dans le code, qui sont appelés lors d'événements tels que le démarrage d'un processus ou à son achèvement. Déclarez-les avant le premier appel à start().

Les rappels peuvent être définis avec les méthodes suivantes :

run_on_finish $code [, $pid ]
Vous pouvez définir une sous-routine qui est appelée lorsqu'un enfant est terminé. Elle est appelée dans le processus parent.

Les paramètres de $code sont les suivants :

- PID du processus terminé
- Code de sortie du programme
- Identification du processus (si fournie dans la méthode "start")
- Signal de sortie (0-127 : nom du signal)
- Core dump (1 s'il y a eu un core dump à la sortie)
- Référence de structure de données ou undef (voir RÉCUPÉRATION DES STRUCTURES DE DONNÉES)
run_on_start $code
Vous pouvez définir une sous-routine qui est appelée lorsqu'un enfant est démarré. Elle est appelée après le démarrage réussi d'un enfant dans le processus parent.

Les paramètres de $code sont les suivants :

- PID du processus qui a été démarré
- Identification du processus (si fournie dans la méthode "start")
run_on_wait $code, [$period]
Vous pouvez définir une sous-routine qui est appelée lorsque le processus enfant doit attendre le démarrage. Si $period n'est pas défini, alors un appel est effectué par enfant. Si $period est défini, alors $code est appelé périodiquement et le module attend $period secondes entre les deux appels. Notez que $period peut également être un nombre fractionnaire. La durée exacte de « $period secondes » n'est pas garantie ; les signaux peuvent la raccourcir et le planificateur de processus peut l'allonger (sur les systèmes chargés).

Le $code est également appelé dans les méthodes "start" et "wait_all_children".

Aucun paramètre n'est passé à $code lors de l'appel.

APPELS BLOQUANTS

Lorsqu'il s'agit d'attendre la terminaison des processus enfants, "Parallel::ForkManager" se trouve entre le marteau et l'enclume (si vous me pardonnez ce terrible jeu de mots). La fonction Perl sous-jacente "waitpid" sur laquelle le module s'appuie peut bloquer jusqu'à ce qu'un processus spécifique ou n'importe quel processus enfant se termine, mais pas pour un processus faisant partie d'un groupe donné.

Cela signifie que le module peut faire l'une des deux choses suivantes lorsqu'il attend qu'un de ses processus enfants se termine :

Attendre uniquement ses propres processus enfants
Ceci est fait via une boucle utilisant un appel non bloquant "waitpid" et une instruction sleep. Le code fait quelque chose comme : 
while(1) {
    if ( un des processus enfants de P::FM est terminé ) {
        return son pid
    }
    sleep $sleep_period
}

C'est le comportement par défaut que le module utilisera. Ce n'est pas la manière la plus efficace d'attendre les processus enfants, mais c'est la manière la plus sûre de garantir que "Parallel::ForkManager" n'interférera pas avec toute autre partie du code.

La période de sommeil est définie via la méthode "set_waitpid_blocking_sleep".

Bloquer jusqu'à ce que n'importe quel processus se termine
Alternativement, "Parallel::ForkManager" peut appeler "waitpid" de manière à bloquer jusqu'à ce que n'importe quel processus enfant se termine. Si le processus enfant n'était pas l'un des sous-processus surveillés, l'attente reprendra. C'est plus efficace, mais cela signifie que "P::FM" peut capturer (et ignorer) la notification de terminaison qu'une autre partie du code pourrait attendre.

Si c'est une condition de concurrence qui ne s'applique pas à votre base de code, vous pouvez définir la période waitpid_blocking_sleep à 0, ce qui activera l'appel bloquant "waitpid".

my $pm = Parallel::ForkManager->new( 4 );
$pm->set_waitpid_blocking_sleep(0);  # appels bloquants réels activés
for ( 1..100 ) {
    $pm->start and next;
    ...; # faire le travail
    $pm->finish;
}

RECUPÉRATION DES STRUCTURES DE DONNÉES depuis les processus enfants

La capacité du parent à récupérer des structures de données est nouvelle depuis la version 0.7.6.

Chaque processus enfant peut éventuellement envoyer 1 structure de données au parent. Par structure de données, nous entendons une référence à une chaîne, une table de hachage ou un tableau. Le contenu de la structure de données est écrit dans des fichiers temporaires sur disque en utilisant la méthode store() du module Storable. La référence est ensuite récupérée depuis le code que vous envoyez à la fonction de rappel run_on_finish.

La structure de données peut être n'importe quelle structure de données scalaire Perl qui a du sens : une chaîne, une valeur numérique ou une référence à un tableau, une table de hachage ou un objet.

Il y a 2 étapes impliquées dans la récupération des structures de données :

1) Une référence à la structure de données que l'enfant souhaite renvoyer au parent est fournie comme deuxième argument à l'appel finish(). Il appartient à l'enfant de décider s'il souhaite renvoyer quelque chose au parent ou non.

2) La référence de la structure de données est récupérée à l'aide du rappel fourni dans la méthode run_on_finish().

Gardez à l'esprit que la récupération de structures de données n'est pas la même chose que le retour d'une structure de données à partir d'un appel de méthode. Ce n'est pas ce qui se passe réellement. La structure de données référencée dans un processus enfant donné est sérialisée et écrite dans un fichier par Storable. Le fichier est ensuite relu en mémoire et une nouvelle structure de données appartenant au processus parent est créée. Veuillez tenir compte de la pénalité de performance que cela peut impliquer, alors essayez de garder la structure retournée petite.

EXEMPLES

Obtention parallèle

Ce petit exemple peut être utilisé pour obtenir des URL en parallèle.

use Parallel::ForkManager;
use LWP::Simple;
my $pm = Parallel::ForkManager->new(10);
LIENS:
for my $link (@ARGV) {
  $pm->start and next LIENS;
  my ($fn) = $link =~ /^.*\/(.*?)$/;
  if (!$fn) {
    warn "Impossible de déterminer le nom de fichier à partir de $fn\n";
  } else {
    $0 .= " " . $fn;
    print "Obtention de $fn à partir de $link\n";
    my $rc = getstore($link, $fn);
    print "$link téléchargé. code de réponse : $rc\n";
  };
  $pm->finish;
};

Callbacks

Exemple d'un programme utilisant des rappels pour obtenir les codes de sortie des enfants :

use strict;
use Parallel::ForkManager;
my $max_procs = 5;
my @names = qw( Fred Jim Lily Steve Jessica Bob Dave Christine Rico Sara );
# hachage pour associer les PID aux informations spécifiques de l'enfant
my $pm = Parallel::ForkManager->new($max_procs);
# Configuration d'un rappel pour lorsqu'un enfant se termine afin que nous puissions
# obtenir son code de sortie
$pm->run_on_finish( sub {
    my ($pid, $exit_code, $ident) = @_;
    print "** $ident vient de quitter la pool " .
      "avec le PID $pid et le code de sortie : $exit_code\n";
});
$pm->run_on_start( sub {
    my ($pid, $ident)=@_;
    print "** $ident démarré, pid : $pid\n";
});
$pm->run_on_wait( sub {
    print "** Je dois attendre un enfant...\n"
  },
  0.5
);
NOMS:
foreach my $child ( 0 .. $#names ) {
  my $pid = $pm->start($names[$child]) and next NOMS;
  # Ce code est le processus enfant
  print "Ceci est $names[$child], Enfant numéro $child\n";
  sleep ( 2 * $child );
  print "$names[$child], L'enfant $child est sur le point de sortir...\n";
  sleep 1;
  $pm->finish($child); # passer un code de sortie à finish
}
print "Attente des enfants...\n";
$pm->wait_all_children;
print "Tout le monde a quitté la pool !\n";

Récupération de structure de données

Dans cet exemple simple, chaque enfant renvoie une référence de chaîne.

use Parallel::ForkManager 0.7.6;
use strict;
my $pm = Parallel::ForkManager->new(2, '/server/path/to/temp/dir/');
# récupération et gestion des structures de données
$pm -> run_on_finish ( # appelé AVANT le premier appel à start()
  sub {
    my ($pid, $exit_code, $ident, $exit_signal, $core_dump, $data_structure_reference) = @_;
    # récupérer la structure de données de l'enfant
    if (defined($data_structure_reference)) {  # les enfants ne sont pas obligés d'envoyer quoi que ce soit
      my $string = ${$data_structure_reference};  # l'enfant a passé une référence de chaîne
      print "$string\n";
    }
    else {  # les problèmes survenant pendant le stockage ou la récupération généreront un avertissement
      print qq|Aucun message reçu du processus enfant $pid!\n|;
    }
  }
);
# préparer des composants d'instructions aléatoires
my @foods = ('chocolat', 'crème glacée', 'beurre de cacahuète', 'cornichons', 'pizza', 'bacon', 'pancakes', 'spaghetti', 'cookies');
my @preferences = ('adore', 'ne supporte pas', 'en veut toujours plus', 'marchera 100 miles pour', 'ne mange que', 'préférerait mourir plutôt que de manger');
# exécuter les processus parallèles
PERSONNES:
foreach my $person (qw(Fred Wilma Ernie Bert Lucy Ethel Curly Moe Larry)) {
  $pm->start() and next PERSONNES;
  # générer une déclaration aléatoire sur les préférences alimentaires
  my $statement = $person . ' ' . $preferences[int(rand @preferences)] . ' ' . $foods[int(rand @foods)];
  # le renvoyer au processus parent
  $pm->finish(0, \$statement);  # noter que c'est une référence scalaire, pas le scalaire lui-même
}
$pm->wait_all_children;

Un deuxième exemple de récupération de structure de données montre comment les enfants décident s'il faut envoyer quelque chose en retour, quoi envoyer et comment le parent doit traiter ce qui est récupéré.

use Parallel::ForkManager 0.7.6;
use Data::Dumper;  # pour afficher les structures de données récupérées.
use strict;
my $pm = Parallel::ForkManager->new(20);  # en utilisant le répertoire temporaire du système $L<File::Temp::tempdir()
# récupération et gestion des structures de données
my %retrieved_responses = ();  # pour collecter les réponses
$pm -> run_on_finish (
  sub {
    my ($pid, $exit_code, $ident, $exit_signal, $core_dump, $data_structure_reference) = @_;
    # voir ce que l'enfant nous a envoyé, s'il y en a
    if (defined($data_structure_reference)) {  # tester plutôt que supposer que l'enfant a envoyé quelque chose
      my $reftype = ref($data_structure_reference);
      print qq|l'identifiant "$ident" a retourné une référence de type "$reftype"|;
e.

|;
      if (1) {  # simple on/off switch to display the contents
        print &Dumper($data_structure_reference) . qq|fin de la structure envoyée "$ident"\n\n|;
      }
      # we can also collect retrieved data structures for processing after all children have exited
      $retrieved_responses{$ident} = $data_structure_reference;
    } else {
      print qq|l'identifiant "$ident" n'a rien envoyé.\n\n|;
    }
  }
);
# generate a list of instructions
my @instructions = (  # a unique identifier and what the child process should send
  {'name' => 'Clés %ENV sous forme de chaîne', 'send' => 'keys'},
  {'name' => 'N\'envoyer rien'},  # not instructing the child to send anything back to the parent
  {'name' => '%ENV des enfants', 'send' => 'all'},
  {'name' => 'L\'enfant choisit aléatoirement', 'send' => 'random'},
  {'name' => 'Instructions d\'envoi invalides', 'send' => 'Na Na Nana Na'},
  {'name' => 'Valeurs ENV dans un tableau', 'send' => 'values'},
);
INSTRUCTS:
foreach my $instruction (@instructions) {
  $pm->start($instruction->{'name'}) and next INSTRUCTS;  # this time we are using an explicit, unique child process identifier
  # last step in child processing
  $pm->finish(0) unless $instruction->{'send'};  # no data structure is sent unless this child is told what to send.
  if ($instruction->{'send'} eq 'keys') {
    $pm->finish(0, \join(', ', keys %ENV));
  } elsif ($instruction->{'send'} eq 'values') {
    $pm->finish(0, [values %ENV]);  # kinda useless without knowing which keys they belong to...
  } elsif ($instruction->{'send'} eq 'all') {
    $pm->finish(0, \%ENV);  # remember, we are not "returning" anything, just copying the hash to disc
  # demonstrate clearly that the child determines what type of reference to send
  } elsif ($instruction->{'send'} eq 'random') {
    my $string = q|Je ne suis qu'une chaîne.|;
    my @array = qw(Je suis un tableau);
    my %hash = (type => 'tableau associatif', synonym => 'hash', cool => 'très :)');
    my $return_choice = ('string', 'array', 'hash')[int(rand 3)];  # randomly choose return data type
    $pm->finish(0, \$string) if ($return_choice eq 'string');
    $pm->finish(0, \@array) if ($return_choice eq 'array');
    $pm->finish(0, \%hash) if ($return_choice eq 'hash');
  # as a responsible child, inform parent that their instruction was invalid
  } else {
    $pm->finish(0, \qq|Instructions invalides: "$instruction->{'send'}".|);  # ordinarily I wouldn't include invalid input in a response...
  }
}
$pm->wait_all_children;  # blocks until all forked processes have exited
# post fork processing of returned data structures
for (sort keys %retrieved_responses) {
  print qq|Post traitement de "$_"...\n|;
}

UTILISATION DE RAND() DANS LES PROCESSUS FORKÉS

Une mise en garde à noter est que tous les processus forkés utiliseront la même graine aléatoire, fournissant potentiellement les mêmes résultats (voir http://blogs.perl.org/users/brian_phillips/2010/06/when-rand-isnt-random.html). Si vous utilisez rand() et souhaitez que chaque enfant forké utilise une graine différente, vous pouvez ajouter ceci à votre programme :

$pm->run_on_start(sub { srand });

EXTENSION

À partir de la version 2.0.0, "Parallel::ForkManager" utilise Moo en coulisses. Lorsqu'un processus est forgé à partir de l'objet parent, l'instance forgée de l'objet sera modifiée pour consommer le rôle Parallel::ForkManager::Child. Tout cela rend l'extension de Parallel::ForkManager pour implémenter n'importe quel mécanisme de stockage/récupération ou tout autre comportement assez facile.

Exemple : stocker et récupérer des données via un service web

{
    package Parallel::ForkManager::Web;
    use HTTP::Tiny;
    use Moo;
    extends 'Parallel::ForkManager';
    has ua => (
        is => 'ro',
        lazy => 1,
        default => sub {
            HTTP::Tiny->new;
        }
    );
    sub store {
        my( $self, $data ) = @_;
        $self->ua->post( "http://.../store/$$", { body => $data } );
    }
    sub retrieve {
        my( $self, $kid_id ) = @_;
        $self->ua->get( "http://.../store/$kid_id" )->{content};
    }
}
my $fm = Parallel::ForkManager::Web->new(2);
$fm->run_on_finish(sub{
    my $retrieved = $_[5];
    print "reçu ", $retrieved, "\n";
});
$fm->start_child(sub {
    return $_**2;
}) for 1..3;
$fm->wait_all_children;

Exemple : faire sortir les processus enfants différemment

use Parallel::ForkManager;
package Parallel::ForkManager::Child::PosixExit {
    use Moo::Role;
    with 'Parallel::ForkManager::Child';
    sub finish  { POSIX::_exit() };
}
my $fm = Parallel::ForkManager->new(
    max_proc   => 1,
    child_role => 'Parallel::ForkManager::Child::PosixExit'
);

SÉCURITÉ

Parallel::ForkManager utilise des fichiers temporaires lorsqu'un processus enfant renvoie des informations à son processus parent. Les noms de fichiers sont basés sur le processus du parent et des enfants, ils sont donc assez faciles à deviner. Ainsi, si la sécurité est une préoccupation dans votre environnement, assurez-vous que le répertoire utilisé par Parallel::ForkManager est restreint à l'utilisateur actuel uniquement (le comportement par défaut est de créer un répertoire, via "tempdir" de File::Temp, ce qui le fait).

DÉPANNAGE

PerlIO::gzip et Parallel::ForkManager ne jouent pas bien ensemble

Si vous utilisez PerlIO::gzip dans vos processus enfants, vous pourriez vous retrouver avec des fichiers corrompus. Ce n'est pas vraiment la faute de P::FM, mais plutôt un problème entre PerlIO::gzip et fork() (voir https://rt.cpan.org/Public/Bug/Display.html?id=114557).

Heureusement, il semble qu'il existe une solution simple au problème en ajoutant la couche "unix" ? C'est-à-dire,

open(IN, '<:unix:gzip', ...

BOGUES ET LIMITATIONS

N'utilisez pas Parallel::ForkManager dans un environnement où d'autres processus enfants peuvent affecter l'exécution du programme principal ; l'utilisation de ce module n'est pas recommandée dans un environnement où fork() / wait() est déjà utilisé.

Si vous souhaitez utiliser plusieurs copies de Parallel::ForkManager, vous devez vous assurer que tous les processus enfants sont terminés avant d'utiliser le second objet dans le programme principal.

Vous êtes libre d'utiliser une nouvelle copie de Parallel::ForkManager dans les processus enfants, bien que je ne pense pas que cela ait de sens.
