NOM

Path::IsDev - Déterminer si un chemin donné est un répertoire de développement

VERSION

version 1.001003

SYNOPSIS

use Path::IsDev qw(is_dev);
if( is_dev('/some/path') ) {
    ...
} else {
    ...
}

DESCRIPTION

Ce module est plus ou moins un ensemble d'heuristiques pour déterminer si un chemin donné est la racine d'un répertoire de développement.

Il a de nombreuses applications utiles, en particulier celles qui nécessitent des comportements différents pour les modules « installés » et ceux qui sont encore « en développement ».

FONCTIONS

debug

Callback de débogage.

Pour activer le débogage :

export PATH_ISDEV_DEBUG=1

"is_dev"

En utilisant un "import"'ed "is_dev" :

if( is_dev( $path ) ) {
}

Cependant, les heuristiques réelles utilisées dépendent de la manière dont l'"import" a été appelée.

De plus, vous pouvez appeler

Path::IsDev::is_dev

sans rien importer, et ce sera exactement la même chose que si vous aviez importé en utilisant

use Path::IsDev qw( is_dev );

Autrement dit, aucune "set" n'est appliquée, donc vous n'obtiendrez que le "défaut".

COMPRENDRE ET DÉBOGUER CE MODULE

Comprendre comment fonctionne ce module est crucial pour comprendre où vous pouvez l'utiliser et les conséquences de son utilisation.

Ce module fonctionne à un niveau très simple, et il est facile d'avoir des faux positifs.

Il existe deux types d'heuristiques, les Heuristiques Positives et les Heuristiques Négatives.

Les Heuristiques Positives et Négatives sont basées uniquement sur la présence de fichiers marqueurs spécifiques dans un répertoire ou de répertoires marqueurs spéciaux.

Par exemple, les fichiers

- "META.yml", "Makefile.PL" et "Build.PL" sont des marqueurs d'Heuristique Positive, car leur présence indique généralement une "racine" de répertoire de développement.

Et par exemple, les répertoires

- "t/", "xt/" et ".git/" sont également des marqueurs d'Heuristique Positive, car ces structures sont courantes dans "perl" et rares dans les structures d'installation.

Cependant, ces marqueurs peuvent être trompeurs, par exemple, considérez que vous avez une installation de "local::lib" ou "perlbrew" dans $HOME

$HOME/
$HOME/lib/
$HOME/perl5/perls/perl-5.19.3/lib/site_perl/

Et ainsi de suite.

Dans des conditions normales, ni $HOME ni ces 3 chemins ne sont considérés comme des "dev".

Cependant, ce qui provoque un faux positif, c'est lorsqu'une personne installe un répertoire "t" ou "xt" ou un fichier marqueur dans l'un de ces répertoires, afin que path_isdev($dir) renvoie vrai.

Ce n'est pas un problème, du moins jusqu'à ce que vous utilisiez "Path::FindDev" qui combine "Path::IsDev" avec une traversée récursive des niveaux supérieurs.

$HOME/
$HOME/lib/
$HOME/perl5/perls/perl-5.19.3/lib/site_perl/
find_dev('$HOME/perl5/perls/perl-5.19.3/lib/site_perl/') # retourne false, car ce n'est pas dans un répertoire de développement
mkdir $HOME/t
find_dev('$HOME/perl5/perls/perl-5.19.3/lib/site_perl/') # retourne $HOME, car $HOME/t existe.

Et c'est ce genre de problèmes qui surprend généralement les utilisateurs.

PATH_ISDEV_DEBUG=1 \
    perl -Ilib -MPath::FindDev=find_dev \
    -E "say find_dev(q{/home/kent/perl5/perlbrew/perls/perl-5.19.3/lib/site_perl})" 
...
[Path::IsDev=0] + ::Tool::Dzil => 0 : dist.ini n'existe pas
[Path::IsDev=0] + ::Tool::MakeMaker => 0 : Makefile.PL n'existe pas
[Path::IsDev=0] + ::Tool::ModuleBuild => 0 : Build.PL n'existe pas
[Path::IsDev=0] + ::META => 0 : META.json n'existe pas
[Path::IsDev=0] + ::META => 1 : META.yml existe
[Path::IsDev=0] + ::META => 1 : /home/kent/perl5/META.yml est un fichier
[Path::IsDev=0] + ::META correspond à /home/kent/perl5

Hé !

[Path::IsDev=0] + ::META => 1 : META.yml existe
[Path::IsDev=0] + ::META => 1 : /home/kent/perl5/META.yml est un fichier

Pourquoi pas ?

rm /home/kent/perl5/META.yml
PATH_ISDEV_DEBUG=1 \
    perl -Ilib -MPath::FindDev=find_dev \
    -E "say find_dev(q{/home/kent/perl5/perlbrew/perls/perl-5.19.3/lib/site_perl})"

[Path::IsDev=0] Correspondance /home/kent/perl5
...
[Path::IsDev=0] + ::TestDir => 0 : xt n'existe pas
[Path::IsDev=0] + ::TestDir => 1 : t existe
[Path::IsDev=0] + ::TestDir => 1 : /home/kent/perl5/t est un répertoire
[Path::IsDev=0] + ::TestDir correspond à /home/kent/perl5

Deux « Hé ! »

[Path::IsDev=0] + ::TestDir => 1 : /home/kent/perl5/t est un répertoire

Vous pouvez continuer à faire cela jusqu'à ce que vous supprimiez toutes les heuristiques négatives dans votre arborescence.

Ou, vous pourriez utiliser une heuristique négative.

[Path::IsDev=0] - ::IsDev::IgnoreFile exclut le chemin /home/kent/perl5
[Path::IsDev=0] aucune correspondance trouvée
...
[Path::IsDev=0] Correspondance /
...
[Path::IsDev=0] aucune correspondance trouvée

Succès !

    UTILISATION AVANCÉE

    Ensembles personnalisés

    "Path::IsDev" dispose d'un système d'"ensembles" d'heuristiques, afin de permettre des types d'heuristiques interchangeables et flexibles.

    Cependant, pour la grande majorité des cas, cela n'est pas nécessaire.

    use Path::IsDev is_dev => { set => 'Basic' };
use Path::IsDev is_dev => { set => 'SomeOtherSet' , -as => 'is_dev_other' };

    Remplacer l'ensemble par défaut

    Si, pour une raison quelconque, l'ensemble "Basic" est insuffisant, ou s'il génère de faux positifs sur votre système pour une raison quelconque, l'ensemble "par défaut" peut être remplacé.

    export PATH_ISDEV_DEFAULT_SET="SomeOtherSet"
...
use Path::IsDev qw( is_dev );
is_dev('/some/path') # utilise SomeOtherSet

    Cependant, cela ne prendra la priorité que si l'ensemble n'est pas spécifié lors de l'"import".

    Si cela pose un problème de sécurité pour l'utilisateur, alors ce trou de sécurité peut être éliminé en déclarant l'ensemble souhaité dans le code :

    export PATH_ISDEV_DEFAULT_SET="SomeOtherSet"
...
use Path::IsDev  is_dev => { set => 'Basic' };
is_dev('/some/path') # utilise Basic, indépendamment de ENV

    SÉCURITÉ

    Il est concevable qu'un utilisateur malveillant puisse construire un ensemble malveillant, contenant du code arbitraire et vulnérable, et éventuellement cacher cet ensemble malveillant dans le @INC d'un utilisateur privilégié mal sécurisé.

    Et s'ils parvenaient à y parvenir, s'ils pouvaient empoisonner la variable %ENV de l'utilisateur privilégié, ils pourraient tromper l'utilisateur privilégié pour qu'il exécute du code arbitraire.

    Cependant, il est vrai que si vous pouvez faire l'une ou l'autre de ces 2 choses, vous êtes probablement déjà vulnérable en matière de sécurité, et il est vrai que si vous pouviez faire l'une ou l'autre de ces choses, vous pourriez faire beaucoup plus de choses malveillantes en faisant ce qui suit :

    export PERL5OPT="-MEvil::Module"

    Donc, en tenant compte de cela, dire que l'utilité par défaut de ce module est "non sécurisée" est largement un argument fallacieux.

    Et à cet égard, ce module ne fait rien pour "verrouiller" ce mécanisme, et ce module vous encourage à NE PAS forcer un ensemble, sauf si vous en avez BESOIN, et suggère fortement que forcer un ensemble dans le but de la sécurité n'apportera aucune amélioration réelle en matière de sécurité, tout en réduisant simultanément l'utilité.
