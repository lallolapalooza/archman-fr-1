NOM

Parse::RecDescent - Générer des analyseurs récursifs descendants

VERSION

Ce document décrit la version 1.967015 de Parse::RecDescent publiée le 4 avril 2017.

SYNOPSIS

use Parse::RecDescent;
# Génère un analyseur à partir de la spécification dans $grammar :
    $parser = new Parse::RecDescent ($grammar);
# Génère un analyseur à partir de la spécification dans $othergrammar
    $anotherparser = new Parse::RecDescent ($othergrammar);
# Analyse $text en utilisant la règle 'startrule' (qui doit être
# définie dans $grammar) :
   $parser->startrule($text);
# Analyse $text en utilisant la règle 'otherrule' (qui doit également
# être définie dans $grammar) :
    $parser->otherrule($text);
# Change le motif de préfixe de jeton universel
# avant de construire une grammaire
# (la valeur par défaut est : '\s*') :
   $Parse::RecDescent::skip = '[ \t]+';
# Remplace les productions de règles existantes (ou en crée de nouvelles)
# par les productions définies dans $newgrammar :
   $parser->Replace($newgrammar);
# Étend les règles existantes (ou en crée de nouvelles)
# en ajoutant des productions supplémentaires définies dans $moregrammar :
   $parser->Extend($moregrammar);
# Indicateurs globaux (utiles comme arguments de ligne de commande avec -s) :
   $::RD_ERRORS       # sauf si indéfini, signale les erreurs fatales
   $::RD_WARN         # sauf si indéfini, signale également les problèmes non fatals
   $::RD_HINT         # si défini, suggère également des remèdes
   $::RD_TRACE        # si défini, trace également le comportement des analyseurs
   $::RD_AUTOSTUB     # si défini, génère des "stubs" pour les règles non définies
   $::RD_AUTOACTION   # si défini, ajoute l'action spécifiée aux productions

DESCRIPTION

Vue d'ensemble

Parse::RecDescent génère de manière incrémentale des analyseurs récursifs descendants de type yacc à partir de spécifications de grammaire simples. Il fournit :

  • Des expressions régulières ou des chaînes littérales comme terminaux (jetons),
  • Des productions multiples (non contiguës) pour toute règle,
  • Des sous-règles répétées et optionnelles au sein des productions,
  • Un accès complet à Perl dans les actions spécifiées dans la grammaire,
  • Un rapport d'erreurs automatisé simple lors de la génération de l'analyseur et de l'analyse,
  • La possibilité de s'engager, de se désengager ou de rejeter des productions particulières pendant une analyse,
  • La possibilité de passer des données vers le haut et vers le bas de l'arbre d'analyse ("vers le bas" via les listes d'arguments des sous-règles, "vers le haut" via les valeurs de retour des sous-règles)
  • L'extension incrémentale de la grammaire d'analyse (même pendant une analyse),
  • La précompilation des objets analyseurs,
  • La résolution des conflits réduire-réduire définissable par l'utilisateur via la "notation" des productions correspondantes.

Utilisation de "Parse::RecDescent"

Les objets analyseurs sont créés en appelant "Parse::RecDescent::new", en passant une spécification de grammaire (voir les sous-sections suivantes). Si la grammaire est correcte, "new" retourne une référence bénéficiée qui peut ensuite être utilisée pour initier l'analyse via n'importe quelle règle spécifiée dans la grammaire d'origine. Une séquence typique ressemble à ceci :

$grammar = q {
    # SPÉCIFICATION DE GRAMMAIRE ICI
     };
$parser = new Parse::RecDescent ($grammar) or die "Mauvaise grammaire !\n";
# acquérir $text
defined $parser->startrule($text) or print "Mauvais texte !\n";

La règle par laquelle l'analyse est initiée doit être explicitement définie dans la grammaire (c'est-à-dire pour l'exemple ci-dessus, la grammaire doit inclure une règle de la forme : "startrule: <sous-règles>".

Si la règle de départ réussit, sa valeur (voir ci-dessous) est retournée. L'échec de la génération de l'analyseur d'origine ou l'échec de la correspondance d'un texte est indiqué par le retour de "undef". Notez qu'il est facile de configurer des grammaires qui peuvent réussir, mais qui retournent une valeur de 0, "0" ou "". Ne soyez donc pas tenté d'écrire :

$parser->startrule($text) or print "Mauvais texte !\n";

Normalement, l'analyseur n'a aucun effet sur le texte d'origine. Donc, dans l'exemple précédent, la valeur de $text serait inchangée après avoir été analysée.

Si, cependant, le texte à faire correspondre est passé par référence :

$parser->startrule(\$text)

alors tout texte consommé pendant la correspondance sera retiré du début de $text.

Règles

Dans la grammaire à partir de laquelle l'analyseur est construit, les règles sont spécifiées en donnant un identifiant (qui doit satisfaire /[A-Za-z]\w*/), suivi d'un deux-points sur la même ligne, suivi d'une ou plusieurs productions, séparées par des barres verticales simples. La disposition des productions est entièrement libre :

regle1:  production1
 |  production2 |
production3 | production4

À tout moment de la grammaire, les règles précédemment définies peuvent être étendues avec des productions supplémentaires. Ceci est réalisé en redéclarant la règle avec les nouvelles productions. Ainsi :

regle1: a | b | c
regle2: d | e | f
regle1: g | h

est exactement équivalent à :

regle1: a | b | c | g | h
regle2: d | e | f

Chaque production d'une règle se compose de zéro ou plusieurs éléments, chacun pouvant être : le nom d'une autre règle à faire correspondre (une "sous-règle"), un motif ou une chaîne littérale à faire correspondre directement (un "jeton"), un bloc de code Perl à exécuter (une "action"), une directive spéciale pour l'analyseur (une "directive"), ou un commentaire Perl standard (qui est ignoré).

Une règle correspond à un texte si l'une de ses productions correspond. Une production correspond si chacun de ses éléments correspond à des sous-chaînes consécutives du texte. Les productions d'une règle à faire correspondre sont essayées dans le même ordre qu'elles apparaissent dans la grammaire d'origine, et la première production correspondante termine la tentative de correspondance (avec succès). Si toutes les productions sont essayées et qu'aucune ne correspond, la tentative de correspondance échoue.

Notez que ce comportement est très différent du comportement de "préférer la correspondance la plus longue" de yacc. Par exemple, si yacc analysait la règle :

seq : 'A' 'B'
| 'A' 'B' 'C'

en faisant correspondre "AB", il regarderait si un 'C' est suivant et, si c'est le cas, il ferait correspondre la deuxième production de préférence à la première. En d'autres termes, yacc essaie effectivement toutes les productions d'une règle en largeur d'abord en parallèle, et sélectionne la "meilleure" correspondance, où "meilleure" signifie la plus longue (notez que c'est une simplification grossière du comportement réel de yacc, mais cela suffit pour nos besoins).

En revanche, "Parse::RecDescent" essaie chaque production en profondeur d'abord séquentiellement, et sélectionne la "meilleure" correspondance, où "meilleure" signifie la première. C'est la différence fondamentale entre l'analyse "ascendante" et "récursive descendante".

Chaque élément de production correspondant avec succès se voit attribuer une valeur, qui peut être accessible dans les actions ultérieures au sein de la même production (ou, dans certains cas, comme valeur de retour d'un appel de sous-règle réussi). Les éléments infructueux n'ont pas de valeur associée, car l'échec d'un élément provoque l'échec immédiat de toute la production entourante. Les sections suivantes décrivent les différents types d'éléments et leurs valeurs de succès.

Sous-règles

Une sous-règle qui apparaît dans une production est une instruction à l'analyseur pour tenter de faire correspondre la règle nommée à cet endroit du texte analysé. Si la sous-règle nommée n'est pas définie lorsqu'elle est demandée, la production qui la contient échoue immédiatement (sauf si elle était "autostubée" - voir Autostubbing).

Une règle peut (récursivement) s'appeler elle-même comme sous-règle, mais pas comme élément le plus à gauche dans aucune de ses productions (car de telles récursions sont généralement non terminantes).

La valeur associée à une sous-règle est la valeur associée à sa variable $return (voir "Actions" ci-dessous), ou au dernier élément correspondant avec succès dans la correspondance de la sous-règle.

Les sous-règles peuvent également être spécifiées avec un spécificateur de répétition final, indiquant qu'elles doivent être mises en correspondance (avidement) le nombre de fois spécifié. Les spécificateurs disponibles sont :

sousregle(?)  # Correspond une ou zéro fois
sousregle(s)  # Correspond une ou plusieurs fois
sousregle(s?) # Correspond zéro ou plusieurs fois
sousregle(N)  # Correspond exactement N fois pour un entier N > 0
sousregle(N..M)   # Correspond entre N et M fois
sousregle(..M)    # Correspond entre 1 et M fois
sousregle(N..) # Correspond N fois ou plus

Notez que si une sous-règle avec un spécificateur de répétition échoue, l'échec est traité comme s'il s'agissait d'une sous-règle sans spécificateur. La seule exception est que si une répétition est spécifiée (par exemple, "s" pour une ou plusieurs fois), mais que le nombre de correspondances réussies est de zéro, alors la production entière échoue.

De plus, les sous-règles peuvent être indiquées comme étant optionnelles ou répétitives en plaçant un "?" ou un "*" après le nom de la règle. L'utilisation de "?" correspond à une ou zéro occurrence, et "*" correspond à zéro ou plusieurs occurrences.

Tokens

Les jetons sont les unités de base de l'analyse syntaxique. Ils peuvent être soit des chaînes littérales entre guillemets simples ou doubles, soit des expressions régulières entre barres obliques.

Par exemple:

    "{"      # Correspond à la chaîne littérale '{'
    'mot'    # Correspond à la chaîne littérale 'mot'
    / [A-Z] /  # Correspond à n'importe quelle lettre majuscule
    / \d+ /    # Correspond à une ou plusieurs chiffres

Lorsqu'un jeton est trouvé, il est consommé du texte d'entrée et sa valeur est définie comme étant la chaîne de caractères qui a été mise en correspondance.

Par défaut, tout espace blanc avant un jeton est ignoré. Vous pouvez changer cela en modifiant la variable globale $Parse::RecDescent::skip.

Actions

Une action est un bloc de code Perl qui est exécuté lorsqu'il est rencontré dans une production. Les actions sont délimitées par des accolades et sont traitées comme n'importe quel autre élément d'une production.

Par exemple:

rule: "a" { print "Found an A!\n"; } "b" { $value = "AB"; }

Dans cet exemple, lorsque la production correspond, le code dans la première action est exécuté, puis la sous-règle "b" est analysée. Si "b" réussit, le code dans la deuxième action est exécuté. La valeur retournée par une action est la valeur de la dernière expression évaluée dans le bloc.

Les valeurs des éléments précédents de la production sont disponibles via des variables spéciales. La valeur du jeton ou de la sous-règle immédiatement précédente est disponible dans la variable $item. La valeur de tous les éléments précédents dans la production est disponible dans le tableau @items.

La valeur renvoyée par une production entière peut être explicitement définie en assignant une valeur à la variable spéciale $return dans une action. Si $return n'est pas explicitement défini, la valeur retournée par la production est la valeur du dernier élément qui a été mis en correspondance.

Directives

Les directives sont des commandes spéciales qui contrôlent le comportement de l'analyseur. Elles sont précédées d'un signe deux-points.

Les directives disponibles sont :

:skip
Définit le motif de décalage pour le reste de la production.
:commit
Si la production correspond, ne pas essayer d'autres productions pour cette règle. Utile pour l'optimisation ou pour résoudre les conflits de réduction.
:reject
Faire échouer cette production immédiatement. Utile pour exclure des motifs particuliers ou pour résoudre les conflits de réduction.

Les directives peuvent également être utilisées pour définir des actions automatiques. Si une directive est suivie d'un nom de règle ou d'un motif, et que ce dernier est rencontré dans une production, l'action spécifiée est automatiquement ajoutée à la production.

Commentaires

Les commentaires commencent par un dièse (#) et se poursuivent jusqu'à la fin de la ligne. Ils sont ignorés par l'analyseur.

Gestion des erreurs

Parse::RecDescent fournit une gestion simple des erreurs. Si une erreur d'analyse se produit, l'analyseur tentera de signaler la nature de l'erreur et l'emplacement dans le texte où elle s'est produite.

Les indicateurs globaux $::RD_ERRORS, $::RD_WARN et $::RD_HINT peuvent être utilisés pour contrôler le niveau de détail des messages d'erreur.

Autostubbing

Si l'indicateur $::RD_AUTOSTUB est défini, et qu'une production fait référence à une règle qui n'est pas encore définie, Parse::RecDescent générera automatiquement un "stub" pour cette règle. Ce stub agira comme s'il était défini, mais échouera toujours. Cela peut être utile pour construire des grammaires de manière incrémentale.

Autocomplétion

Si l'indicateur $::RD_AUTOACTION est défini, et qu'une production fait référence à un jeton ou à une sous-règle, une action automatique sera générée pour affecter la valeur de cet élément à la variable $return. Cela peut simplifier l'écriture des grammaires.

Extension incrémentale

Vous pouvez étendre une grammaire existante en utilisant les méthodes Replace et Extend. Replace remplace les productions d'une règle par de nouvelles productions, tandis que Extend ajoute de nouvelles productions aux productions existantes.

Conflits de réduction

Parse::RecDescent peut rencontrer des conflits de réduction-réduction lorsqu'une entrée peut être analysée de plusieurs manières. Ces conflits peuvent être résolus en utilisant des directives comme :commit ou :reject, ou en fournissant une fonction de scoring personnalisée.

EXEMPLES

Voici un exemple simple d'utilisation de Parse::RecDescent pour analyser une expression arithmétique simple :

use Parse::RecDescent;
my $grammar = q {
    expr: term (('+' | '-') term)*
    term: factor (('*' | '/') factor)*
    factor: NUMBER
          | '(' expr ')'
    };
my $parser = new Parse::RecDescent($grammar);
my $text = "3 + 4 * 2";
my $result = $parser->expr($text);
if ($result) {
    print "Analyse réussie : $result\n";
} else {
    print "Erreur d'analyse.\n";
}

Cet exemple définira un analyseur pour les expressions arithmétiques qui peut gérer l'addition, la soustraction, la multiplication et la division, ainsi que les parenthèses pour contrôler la précédence.

Les sous-règles répétées continuent à correspondre jusqu'à ce que la sous-règle échoue à correspondre, ou qu'elle ait correspondu au nombre minimal de fois mais échoue à consommer une partie du texte analysé (cette deuxième condition empêche la sous-règle de correspondre indéfiniment dans certains cas).

Étant donné qu'une sous-règle répétée peut correspondre à de nombreuses instances de la sous-règle elle-même, la valeur qui lui est associée n'est pas un scalaire simple, mais plutôt une référence à une liste de scalaires, chacun étant la valeur associée à chaque correspondance de sous-règle individuelle. En d'autres termes, dans la règle :

program: statement(s)

la valeur associée à la sous-règle répétée "statement(s)" est une référence à un tableau contenant les valeurs correspondant à chaque appel de la sous-règle individuelle "statement".

Les modificateurs de répétition peuvent inclure un motif séparateur :

program: statement(s /;/)

spécifiant une séquence de caractères à ignorer entre chaque répétition. Ceci est en réalité juste un raccourci pour la directive <leftop:...> (voir ci-dessous).

Tokens

Si une chaîne délimitée par des guillemets ou une expression régulière Perl apparaît dans une production, l'analyseur tente de faire correspondre cette chaîne ou ce motif à cet endroit du texte. Par exemple :

typedef: "typedef" typename identifier ';'
identifier: /[A-Za-z_][A-Za-z0-9_]*/

Comme dans Perl normal, une chaîne à guillemets simples n'est pas interpolée, tandis qu'une chaîne à guillemets doubles ou un motif est interpolé (au moment de la correspondance, *pas* lors de la construction de l'analyseur). Par conséquent, il est possible de définir des règles dans lesquelles les tokens peuvent être définis à l'exécution :

typedef: "$::typedefkeyword" typename identifier ';'
identifier: /$::identpat/

Notez que, puisque chaque règle est implémentée dans un espace de noms spécial appartenant à son analyseur, il est nécessaire de quantifier explicitement les variables du paquet principal.

Les tokens d'expression régulière peuvent être spécifiés en utilisant simplement des barres obliques comme délimiteurs ou avec la syntaxe explicite "m<delimiter>......<delimiter>" :

typedef: "typedef" typename identifier ';'
typename: /[A-Za-z_][A-Za-z0-9_]*/
identifier: m{[A-Za-z_][A-Za-z0-9_]*}

Une expression régulière de l'un ou l'autre type peut également avoir des paramètres finaux valides (c'est-à-dire n'importe lesquels de [cgimsox]) :

typedef: "typedef" typename identifier ';'
identifier: / [a-z_]        # LETTRE OU UNDERSCORE MAJUSCULE/MINUSCULE
      [a-z0-9_]*    # PUIS CHIFFRES AUTORISÉS AUSSI
    /ix     # IGNORER MAJUSCULES/MINUSCULES / ESPACE / COMMENTAIRE

La valeur associée à tout token correspondant avec succès est une chaîne contenant le texte réel qui a été correspondant par le token.

Il est important de se rappeler que, puisque chaque grammaire est spécifiée dans une chaîne Perl, toutes les instances du caractère d'échappement universel '\' au sein d'une grammaire doivent être "doublées", de sorte qu'elles s'interpolent en simples '\' lors de la compilation de la chaîne. Par exemple, pour utiliser la grammaire :

word:       /\S+/ | backslash
line:       prefix word(s) "\n"
backslash:  '\\'

le code suivant est requis :

$parser = new Parse::RecDescent (q{
    word:   /\\S+/ | backslash
    line:   prefix word(s) "\\n"
    backslash:  '\\\\\\'
});

Sous-règles anonymes

Les parenthèses introduisent une portée imbriquée qui ressemble beaucoup à un appel à une sous-règle anonyme. Elles sont donc utiles pour "intégrer" des appels de sous-routines et d'autres types de regroupement. Par exemple, au lieu de :

word:       /\S+/ | backslash
line:       prefix word(s) "\n"

vous pourriez écrire :

line:       prefix ( /\S+/ | backslash )(s) "\n"

et obtenir exactement les mêmes effets.

Les parenthèses sont également utilisées pour collecter des alternances non répétées au sein d'une seule production.

secret_identity: "Mr" ("Incredible"|"Fantastic"|"Sheen") ", Esq."

Séparateurs de terminaux

Aux fins de correspondance, chaque terminal d'une production est considéré comme précédé d'un "préfixe" - un motif qui doit correspondre avant qu'une tentative de correspondance de token ne soit effectuée. Par défaut, le préfixe est un espace blanc facultatif (qui correspond toujours, au moins trivialement), mais ce défaut peut être réinitialisé dans n'importe quelle production.

La variable $Parse::RecDescent::skip stocke le préfixe universel, qui est le défaut pour toutes les correspondances de terminaux dans tous les analyseurs construits avec "Parse::RecDescent".

Si vous souhaitez modifier le préfixe universel en utilisant $Parse::RecDescent::skip, veillez à le définir *avant* de créer l'objet de grammaire, car il est appliqué statiquement (lorsqu'une grammaire est construite) plutôt que dynamiquement (lorsqu'une grammaire est utilisée). Alternativement, vous pouvez fournir une directive globale "<skip:...>" dans votre grammaire avant toute règle (décrit plus tard).

Le préfixe d'une production individuelle peut être modifié en utilisant la directive "<skip:...>" (décrite plus tard). Définir cette directive dans la règle de niveau supérieur est une approche alternative à la définition de $Parse::RecDescent::skip avant de créer l'objet, mais dans ce cas, vous n'obtenez pas le comportement de saut souhaité si vous invoquez directement des méthodes autres que la règle de niveau supérieur.

Actions

Une action est un bloc de code Perl qui doit être exécuté (comme bloc d'une instruction "do") lorsque l'analyseur atteint ce point dans une production. L'action s'exécute dans un espace de noms spécial appartenant à l'analyseur actif, il faut donc prendre soin de qualifier correctement les noms de variables (voir aussi "Actions de démarrage" ci-dessous).

L'action est considérée comme réussie si la valeur finale du bloc est définie (c'est-à-dire si l'instruction "do" implicite évalue à une valeur définie - *même une qui serait traitée comme "fausse"*). Notez que la valeur associée à une action réussie est également la valeur finale du bloc.

Une action *échouera* si sa dernière valeur évaluée est "undef". C'est étonnamment facile à faire par accident. Par exemple, voici un cas frustrant d'action qui fait échouer sa production, mais seulement lorsque le débogage *n'est pas* activé :

description: name rank serial_number
    { print "Got $item[2] $item[1] ($item[3])\n"
    if $::debugging
    }

Si $debugging est faux, aucune instruction du bloc n'est exécutée, donc la valeur finale est "undef", et toute la production échoue. La solution est :

description: name rank serial_number
    { print "Got $item[2] $item[1] ($item[3])\n"
    if $::debugging;
      1;
    }

Dans une action, un certain nombre de variables utiles au moment de l'analyse sont disponibles dans l'espace de noms spécial de l'analyseur (d'autres variables sont également accessibles, mais leur modification risque de casser votre analyseur. En règle générale, si vous évitez de faire référence à des variables non qualifiées - en particulier celles commençant par un underscore - à l'intérieur d'une action, les choses devraient bien se passer) :

@item et %item
La tranche de tableau @item[1..$#item] stocke la valeur associée à chaque élément (c'est-à-dire chaque sous-règle, token ou action) dans la production actuelle. L'analogie est avec $1, $2, etc. dans une grammaire yacc. Notez que, pour des raisons évidentes, @item ne contient que les valeurs des éléments *avant* le point actuel de l'analyse.

Le premier élément ($item[0]) stocke le nom de la règle en cours de correspondance.

@item est un tableau Perl standard, il peut donc également être indexé avec des nombres négatifs, représentant le nombre d'éléments *en arrière* par rapport à la position actuelle dans l'analyse :

stuff: /various/ bits 'and' pieces "then" data 'end'
    { print $item[-2] }  # IMPRIME data
         # (PLUS FACILE QUE : $item[6])

Le hash %item complète le tableau <@item>, fournissant un accès nommé aux mêmes valeurs d'éléments :

stuff: /various/ bits 'and' pieces "then" data 'end'
    { print $item{data}  # IMPRIME data
         # (ENCORE PLUS FACILE QUE D'UTILISER @item)

Les résultats des sous-règles nommées sont stockés dans le hash sous le nom de chaque sous-règle (y compris le spécificateur de répétition, le cas échéant), tandis que tous les autres éléments sont stockés sous une clé "nom positionnel" qui indique leur position ordinale au sein de leur type d'élément : __STRINGn__, __PATTERNn__, __DIRECTIVEn__, __ACTIONn__ :

stuff: /various/ bits 'and' pieces "then" data 'end' { save }
    { print $item{__PATTERN1__}, # IMPRIME 'various'
    $item{__STRING2__},  # IMPRIME 'then'
    $item{__ACTION1__},  # IMPRIME LA VALEUR DE RETOUR
             # DE save
    }

Si vous souhaitez un accès nommé approprié aux motifs ou aux littéraux, vous devez les transformer en règles séparées :

stuff: various bits 'and' pieces "then" data 'end'
    { print $item{various}  # IMPRIME various
    }
various: /various/

L'entrée spéciale $item{__RULE__} stocke le nom de la règle actuelle (c'est-à-dire la même valeur que $item[0].

L'avantage d'utiliser %item, au lieu de @items, est qu'il élimine le besoin de suivre les positions des éléments qui peuvent changer à mesure qu'une grammaire évolue. Par exemple, l'ajout d'une directive d'action "<skip>" intermédiaire peut ruiner silencieusement une action finale, en décalant un élément @item "vers le bas" dans le tableau d'une place. En revanche, l'entrée nommée de %item n'est pas affectée par une telle insertion.

Une limitation du hash %item est qu'il n'enregistre que la *dernière* valeur d'une sous-règle particulière. Par exemple :

range: '(' number '..' number )'
    { $return = $item{number} }

ne retournera que la valeur correspondant à la *deuxième* correspondance de la sous-règle "number". En d'autres termes, les appels successifs à une sous-règle écrasent l'entrée correspondante dans %item. Encore une fois, la solution est de renommer chaque sous-règle dans sa propre règle :

range: '(' from_num '..' to_num ')'
    { $return = $item{from_num
{
  "from_num": "número",
  "to_num": "número"
}
```
@arg y %arg
Le tableau @arg et la table associative %arg stockent tous les arguments passés à une règle depuis une autre règle (voir « Liste d'arguments des sous-règles »). Les modifications apportées aux éléments de ces variables ne se propagent pas à la règle appelante (la valeur peut être passée d'une sous-règle via la variable $return – voir le point suivant).
$return
Si une valeur est assignée à $return dans une action, cette valeur est retournée si la production contenant l'action réussit. Il faut noter que la définition de $return ne provoque *pas* la réussite de la production actuelle. Elle indique simplement à la production quelle valeur elle retournera si elle *réussit*. Par conséquent, $return est analogue à $$ dans une grammaire yacc.

Si $return n'est pas assigné dans une production, la valeur du dernier composant de la production (c'est-à-dire : $item[$#item]) est retournée si la production est satisfaite.

$commit
L'état actuel d'engagement dans la production actuelle (voir « Directives » ci-dessous).
$skip
Le préfixe terminal actuel (voir « Directives » ci-dessous).
$text
Le texte restant (non traité). Les modifications de $text ne se propagent *pas* en dehors des productions qui échouent, mais elles survivent aux productions qui réussissent. Il est donc possible de modifier dynamiquement le texte en cours d'analyse – par exemple, pour fournir une fonctionnalité de type "#include" : 
hash_include: '#include' filename
    { $text = ::loadfile($item[2]) . $text }
filename: '<' /[a-z0-9._-]+/i '>'  { $return = $item[2] }
| '"' /[a-z0-9._-]+/i '"'  { $return = $item[2] }
$thisline et $prevline
$thisline stocke le numéro de la ligne actuelle en cours d'analyse (commençant à 1). $prevline stocke le numéro de ligne du dernier caractère qui a été correctement analysé (ceci sera différent de $thisline à la fin de chaque ligne).

Pour des raisons d'efficacité, $thisline et $prevline sont en fait liés à des tables associatives et ne recalculent le numéro de ligne que lorsque la valeur de la variable est utilisée.

Assigner une valeur à $thisline ajuste le compteur de lignes, de sorte qu'il considère que le numéro de ligne actuel est la valeur qui a été assignée. Notez que cet ajustement sera reflété dans tous les calculs de numéros de ligne ultérieurs.

La modification de la valeur de la variable $text (comme dans l'exemple précédent de "hash_include") peut perturber le mécanisme de comptage des lignes. Pour éviter cela, vous devez appeler Parse::RecDescent::LineCounter::resync($thisline) *immédiatement* après toute assignation à la variable $text (ou, au moins, avant la prochaine tentative d'utilisation de $thisline).

Notez que si une production échoue après avoir assigné ou synchronisé $thisline, le mécanisme de comptage de lignes de l'analyseur est généralement corrompu.

Vous verrez également l'entrée pour @itempos.

Le numéro de ligne peut être défini à des valeurs autres que 1 en appelant la règle de départ avec un second argument. Par exemple :

$parser = new Parse::RecDescent ($grammar);
$parser->input($text, 10);  # COMMENCE LE NUMÉROTAGE DES LIGNES À 10
$thiscolumn et $prevcolumn
$thiscolumn stocke le numéro de colonne actuel dans la ligne en cours d'analyse (commençant à 1). $prevcolumn stocke le numéro de colonne du dernier caractère qui a été correctement analysé. Normalement, "$prevcolumn == $thiscolumn-1", mais pas à la fin des lignes.

Pour des raisons d'efficacité, $thiscolumn et $prevcolumn sont en fait liés à des tables associatives et ne recalculent le numéro de colonne que lorsque la valeur de la variable est utilisée.

Assigner une valeur à $thiscolumn ou $prevcolumn est une erreur fatale.

La modification de la valeur de la variable $text (comme dans l'exemple précédent de "hash_include") peut perturber le mécanisme de comptage des colonnes.

Notez que $thiscolumn renvoie le numéro de colonne *avant* tout espace qui pourrait être sauté avant la lecture d'un jeton. Par conséquent, si vous voulez savoir où un jeton a commencé (et s'est terminé), utilisez quelque chose comme ceci :

rule: token1 token2 startcol token3 endcol token4
    { print "token3: colonnes $item[3] à $item[5]"; }
startcol: '' { $thiscolumn }    # NÉCESSITE LE '' POUR PASSER LE SEPARATOR
endcol:  { $prevcolumn }

Vous verrez également l'entrée pour @itempos.

$thisoffset et $prevoffset
$thisoffset stocke le décalage actuel de la position d'analyse dans le texte complet en cours d'analyse (commençant à 0). $prevoffset stocke le décalage du dernier caractère qui a été correctement analysé. Dans tous les cas, "$prevoffset == $thisoffset-1".

Pour des raisons d'efficacité, $thisoffset et $prevoffset sont en fait liés à des tables associatives et ne recalculent le décalage que lorsque la valeur de la variable est utilisée.

Assigner une valeur à $thisoffset ou <$prevoffset> est une erreur fatale.

La modification de la valeur de la variable $text n'affecte pas le mécanisme de comptage des décalages.

Vous verrez également l'entrée pour @itempos.

@itempos
Le tableau @itempos stocke une référence vers une table associative correspondant à chaque élément de @item. Les éléments de la table associative fournissent les informations suivantes : 
$itempos[$n]{offset}{from}  # VALEUR DE $thisoffset AVANT $item[$n]
$itempos[$n]{offset}{to}    # VALEUR DE $prevoffset APRÈS $item[$n]
$itempos[$n]{line}{from}    # VALEUR DE $thisline AVANT $item[$n]
$itempos[$n]{line}{to}  # VALEUR DE $prevline APRÈS $item[$n]
$itempos[$n]{column}{from}  # VALEUR DE $thiscolumn AVANT $item[$n]
$itempos[$n]{column}{to}    # VALEUR DE $prevcolumn APRÈS $item[$n]

Notez que les diverses valeurs "$itempos[$n]...{from}" enregistrent la valeur appropriée *après* avoir sauté tout préfixe de jeton.

Ainsi, au lieu d'écrire quelque chose comme :

rule: startcol token1 endcol
  startcol token2 endcol
  startcol token3 endcol
    { print "token1: colonnes $item[1]
          à $item[3]
     token2: colonnes $item[4]
          à $item[6]
     token3: colonnes $item[7]
          à $item[9]" }
startcol: '' { $thiscolumn }    # NÉCESSITE LE '' POUR PASSER LE SEPARATOR
endcol:  { $prevcolumn }

il est possible d'écrire :

rule: token1 token2 token3
    { print "token1: colonnes $itempos[1]{column}{from}
          à $itempos[1]{column}{to}
     token2: colonnes $itempos[2]{column}{from}
          à $itempos[2]{column}{to}
     token3: colonnes $itempos[3]{column}{from}
          à $itempos[3]{column}{to}" }

Cependant, malgré ce qui précède (dans l'implémentation actuelle), l'utilisation de @itempos n'importe où dans la grammaire implique que des informations de positionnement des éléments sont collectées *à chaque endroit* pendant l'analyse. Cela peut être prohibitivement coûteux en fonction du graphe de grammaire et de la taille du texte à analyser. Par conséquent, dans certains cas, il est préférable d'utiliser explicitement $thisline, $thiscolumn, etc.

$thisparser
Une référence à la classe "Parse::RecDescent" à travers laquelle l'analyse a été initiée.
$thisrule
Une référence à la classe "Parse::RecDescent::Rule" correspondant à la règle actuelle qui est comparée.
$thisprod
Une référence à la classe "Parse::RecDescent::Production" correspondant à la production actuelle qui est comparée.
$score et $score_return
$score stocke le meilleur score de production jusqu'à présent, comme spécifié par une directive "<score:...>" précédente. $score_return stocke la valeur correspondante de la production réussie.

Avertissement : l'analyseur dépend des informations contenues dans les objets de type "this..." de manière non évidente. En modifiant les autres membres de ces objets, vous provoquerez probablement de mauvaises choses, à moins que vous ne sachiez *vraiment* ce que vous faites. La seule exception à ce conseil est que l'utilisation de "$this...->{local}" est toujours sûre.

Actions de démarrage

Toute action qui apparaît *avant* la première définition de règle dans une grammaire est traitée comme une *action de démarrage*. Chaque action de ce type est dépouillée de ses parenthèses externes et évaluée (dans l'espace de noms spécial de l'analyseur) avant que les règles de la grammaire ne soient compilées.

L'utilisation principale des actions de démarrage est de déclarer des variables locales dans l'espace de noms spécial de l'analyseur :

{ my $lastitem = '???'; }
list: item(s)   { $return = $lastitem }
item: book  { $lastitem = 'book'; }
  bell  { $lastitem = 'bell'; }
  candle    { $lastitem = 'candle'; }

mais les actions de démarrage peuvent être utilisées pour exécuter *toute* action Perl valide.

Actions automatiques

Il est parfois souhaitable de spécifier une action par défaut à la fin de chaque production (par exemple, pour construire facilement un arbre d'analyse). Si la variable $::RD_AUTOACTION est définie lors de l'appel à Parse::RecDescent::new(), le contenu de cette variable est traité comme une spécification d'une action qui est ajoutée à chaque production dans la grammaire correspondante.

Alternativement, vous pouvez coder l'action automatique directement dans une grammaire, en utilisant la directive <autoaction:...>.

Ainsi, par exemple, pour construire un arbre d'analyse simple, vous pourriez écrire :

$::RD_AUTOACTION = q { [@item] };
parser = Parse::RecDescent->new(q{
expression: and_expr '||' expression | and_expr
and_expr:   not_expr '&&' and_expr   | not_expr
not_expr:   '!' brack_expr       | brack_expr
brack_expr: '(' expression ')'       | identifier
identifier: /[a-z]+/i
});

ou :

parser = Parse::RecDescent->new(q{
<autoaction: { [@item] } >
expression: and_expr '||' expression | and_expr
and_expr:   not_expr '&&' and_expr   | not_expr
not_expr:   '!' brack_expr       | brack_expr
brack_expr: '(' expression ')'       | identifier
identifier: /[a-z]+/i
});

L'un ou l'autre de ces exemples est équivalent à :

parser = new Parse::RecDescent (q{
expression: and_expr '||' expression
    { [@item] }
  | and_expr
    { [@item] }
and_expr:   not_expr '&&' and_expr
    { [@item] }
|   not_expr
    { [@item] }
not_expr:   '!' brack_expr
    { [@item] }
|   brack_expr
    { [@item] }
brack_expr: '(' expression ')'
    { [@item] }
  | identifier
    { [@item] }
identifier: /[a-z]+/i
    { [@item] }
});

Alternativement, nous pourrions adopter une approche orientée objet, utiliser différentes classes pour chaque nœud (et également supprimer les nœuds intermédiaires redondants) :

$::RD_AUTOACTION = q
  { $#item==1 ? $item[1] : "$item[0]_node"->new(@item[1..$#item]) };
parser = Parse::RecDescent->new(q{
    expression: and_expr '||' expression | and_expr
    and_expr:   not_expr '&&' and_expr   | not_expr
    not_expr:   '!' brack_expr           | brack_expr
    brack_expr: '(' expression ')'       | identifier
    identifier: /[a-z]+/i
});

ou :

parser = Parse::RecDescent->new(q{
    <autoaction:
      $#item==1 ? $item[1] : "$item[0]_node"->new(@item[1..$#item])
    >
    expression: and_expr '||' expression | and_expr
    and_expr:   not_expr '&&' and_expr   | not_expr
    not_expr:   '!' brack_expr           | brack_expr
    brack_expr: '(' expression ')'       | identifier
    identifier: /[a-z]+/i
});

qui sont équivalents à :

parser = Parse::RecDescent->new(q{
    expression: and_expr '||' expression
        { "expression_node"->new(@item[1..3]) }
    | and_expr
    and_expr:   not_expr '&&' and_expr
        { "and_expr_node"->new(@item[1..3]) }
    |   not_expr
    not_expr:   '!' brack_expr
        { "not_expr_node"->new(@item[1..2]) }
    |   brack_expr
    brack_expr: '(' expression ')'
        { "brack_expr_node"->new(@item[1..3]) }
    | identifier
    identifier: /[a-z]+/i
        { "identifer_node"->new(@item[1]) }
});

Remarque : Si une production se termine déjà par une action, une action automatique ne lui sera pas ajoutée. Par exemple, dans cette version :

$::RD_AUTOACTION = q
  { $#item==1 ? $item[1] : "$item[0]_node"->new(@item[1..$#item]) };
parser = Parse::RecDescent->new(q{
    expression: and_expr '&&' expression | and_expr
    and_expr:   not_expr '&&' and_expr   | not_expr
    not_expr:   '!' brack_expr           | brack_expr
    brack_expr: '(' expression ')'       | identifier
    identifier: /[a-z]+/i
        { 'terminal_node'->new($item[1]) }
});

chaque correspondance de "identifier" produit un objet "terminal_node", *pas* un objet "identifier_node".

Un avertissement de niveau 1 est émis chaque fois qu'une action automatique est ajoutée à une production.

Arbres automatiques

Une action automatique couramment nécessaire est celle qui construit un arbre d'analyse. Il est quelque peu compliqué de mettre en place une telle action (qui doit traiter les terminaux différemment des non-terminaux), Parse::RecDescent simplifie donc le processus en offrant la directive <autotree>.

Si cette directive apparaît au début de la grammaire, elle amène Parse::RecDescent à insérer des actions automatiques à la fin de toute règle, sauf celles qui se terminent déjà par une action. L'action insérée dépend de si la production est une règle intermédiaire (avec deux éléments ou plus) ou un terminal de la grammaire (c'est-à-dire un élément unique de type motif ou chaîne).

Ainsi, par exemple, la grammaire suivante :

<autotree>
file    : command(s)
command : get | set | vet
get : 'get' ident ';'
set : 'set' ident 'to' value ';'
vet : 'check' ident 'is' value ';'
ident   : /\w+/
value   : /\d+/

est équivalente à :

file    : command(s)        { bless \%item, $item[0] }
command : get       { bless \%item, $item[0] }
| set           { bless \%item, $item[0] }
| vet           { bless \%item, $item[0] }
get : 'get' ident ';'   { bless \%item, $item[0] }
set : 'set' ident 'to' value ';'    { bless \%item, $item[0] }
vet : 'check' ident 'is' value ';'  { bless \%item, $item[0] }
ident   : /\w+/  { bless {__VALUE__=>$item[1]}, $item[0] }
value   : /\d+/  { bless {__VALUE__=>$item[1]}, $item[0] }

Remarque : Chaque nœud de l'arbre est "blessé" dans une classe du même nom que la règle. Cela facilite la construction de processeurs orientés objet pour les arbres d'analyse produits par la grammaire. Remarquez également que les deux dernières règles produisent des objets spéciaux avec la seule propriété __VALUE__. C'est parce qu'ils ne consistent qu'en un seul terminal.

Cette grammaire auto-actionnée produirait un arbre d'analyse dans une structure de données comme celle-ci :

{
  file => {
    command => {
     [ get => {
        identifier => { __VALUE__ => 'a' },
          },
       set => {
        identifier => { __VALUE__ => 'b' },
        value      => { __VALUE__ => '7' },
          },
       vet => {
        identifier => { __VALUE__ => 'b' },
        value      => { __VALUE__ => '7' },
          },
      ],
       },
  }
}

(à l'exception, en fait, que chaque hash imbriqué est également "blessé" dans la classe correspondante).

Vous pouvez également spécifier une classe de base pour la directive <autotree>. Le préfixe fourni sera précédé du nom des règles lors de la création des nœuds d'arbre. Les éléments suivants sont équivalents :

<autotree:MyBase::Class>
<autotree:MyBase::Class::>

Et produiront un nœud racine "blessé" dans la classe "MyBase::Class::file" de l'exemple ci-dessus.

Bouchonnage automatique

Normalement, si une sous-règle apparaît dans une production, mais qu'aucune règle de ce nom n'est définie dans la grammaire, la production faisant référence à la sous-règle inexistante échoue immédiatement. Cela se produit généralement à la suite d'erreurs de frappe, et c'est une occurrence suffisamment fréquente pour qu'un avertissement soit généré à ce sujet.

Cependant, lors du prototypage d'une grammaire, il est souvent utile de pouvoir utiliser des sous-règles avant qu'une spécification complète de celles-ci ne soit réellement possible. Par exemple, une grammaire pourrait inclure une section comme celle-ci :

function_call: identifier '(' arg(s?) ')'
identifier: /[a-z]\w*/i

où le format possible d'un argument est suffisamment complexe pour qu'il ne soit pas rentable de le spécifier dans son intégralité tant que la syntaxe générale de l'appel de fonction n'a pas été déboguée. Dans cette situation, il est pratique de laisser la règle réelle "arg" indéfinie et d'introduire simplement un "substitut" (ou "bouchon") :

arg: 'arg'

afin que la syntaxe de l'appel de fonction puisse être testée avec des entrées fictives telles que :

f0()
f1(arg)
f2(arg arg)
f3(arg arg arg)

etc.

Au cours de la phase de prototypage, de nombreux "bouchons" de ce type peuvent être nécessaires, "Parse::RecDescent" fournit donc un moyen d'automatiser leur définition. Si la variable $::RD_AUTOSTUB est définie lors de la construction d'un analyseur, une référence de sous-règle à une règle inexistante (par exemple, "subrule") entraînera la génération automatique d'une règle "bouchon" dans l'analyseur généré. Si $::RD_AUTOSTUB est '1' ou faux, une règle de type sera générée :

subrule: 'subrule'

Si la valeur de $::RD_AUTOSTUB est '1', vous pouvez utiliser la commande perl -s avec -RD_AUTOSTUB sans générer "subrule: '1'" comme indiqué ci-dessus. Si $::RD_AUTOSTUB est vrai, une règle de type sera générée :

subrule: $::RD_AUTOSTUB

La variable $::RD_AUTOSTUB doit contenir un élément de production valide, aucune vérification n'est effectuée. Il n'y a pas d'évaluation différée de $::RD_AUTOSTUB, elle est évaluée au moment de la génération de l'analyseur.

Par conséquent, avec $::RD_AUTOSTUB défini, il est possible de spécifier partiellement une grammaire, puis de "simuler" les correspondances des règles non spécifiées (sous-règles) en introduisant simplement leur nom, ou une valeur littérale qui a été attribuée à $::RD_AUTOSTUB.

Avance d'analyse

Si une sous-règle, un jeton ou une action est précédé de "...", il est traité comme une demande d'avance d'analyse. Cela signifie que la production actuelle peut (comme d'habitude) réussir uniquement si l'élément spécifié correspond, mais que cette correspondance *ne consomme pas* le texte en cours d'analyse. Ceci est très similaire à la construction de l'expression Perl "/(?=...)/".

Ainsi, la règle :

inner_word: word ...word

correspondra à ce à quoi la sous-règle "word" correspond, à condition que la correspondance soit suivie d'un texte supplémentaire auquel la sous-règle "word" correspondrait également (même si cette seconde sous-chaîne n'est pas réellement consommée par "inner_word").

De même, une demande de "...! " précédée d'une sous-règle :

...!

Directives

Les directives sont des actions spéciales prédéfinies qui peuvent être utilisées pour modifier le comportement de l'analyseur. Il existe actuellement vingt-trois directives : "<commit>", "<uncommit>", "<reject>", "<score>", "<autoscore>", "<skip>", "<resync>", "<error>", "<warn>", "<hint>", "<trace_build>", "<trace_parse>", "<nocheck>", "<rulevar>", "<matchrule>", "<leftop>", "<rightop>", "<defer>", "<nocheck>", "<perl_quotelike>", "<perl_codeblock>", "<perl_variable>", et "<token>".

Commit et uncommit
Les directives "<commit>" et "<uncommit>" permettent de tronquer (ou "couper") pour l'efficacité l'arbre d'analyse de la grammaire. Au sein d'une règle, une directive "<commit>" demande à la règle d'ignorer les productions suivantes si la production actuelle échoue. Par exemple : 
command: 'find' <commit> filename
   | 'open' <commit> filename
   | 'move' filename filename

Clairement, si le premier token 'find' correspond dans la première production, mais que cette production échoue pour une autre raison, alors les productions restantes ne peuvent pas correspondre. La présence de la directive "<commit>" fait échouer immédiatement la règle "command" si une commande "find" invalide est rencontrée, et de même si une commande "open" invalide est rencontrée.

Il est également possible de révoquer un commit précédent. Par exemple :

if_statement: 'if' <commit> condition
    'then' block <uncommit>
    'else' block
    | 'if' <commit> condition
    'then' block

Dans ce cas, un échec pour trouver un bloc "else" dans la première production ne doit pas empêcher les productions restantes d'être essayées, mais un échec pour trouver une "condition" le devrait certainement.

Comme cas spécial, toute production dans laquelle le premier élément est un "<uncommit>" révoque immédiatement un engagement précédent "<commit>" (bien que la production ne soit pas réellement tentée). Par exemple, dans la règle :

request: 'explain' expression
       | 'explain' <commit> keyword
       | 'save'
       | 'quit'
       | <uncommit> term '?'

si le texte correspondant était "explain?", et que les deux premières productions échouaient, alors le "<commit>" dans la deuxième production ferait omettre les productions 3 et 4, mais le "<uncommit>" dans la production 5 permettrait à cette production de tenter une correspondance.

Notez dans l'exemple précédent que le "<commit>" était uniquement dans la production 2. Si la production 1 était :

request: 'explain' <commit> expression

alors la production 2 serait (inappropriément) omise si un "explain..." était détecté.

Les deux directives "<commit>" et "<uncommit>" réussissent toujours et leur valeur est toujours 1.

Rejet d'une production
La directive "<reject>" force immédiatement la production actuelle à échouer (elle est exactement équivalente mais plus évidente que l'action "{undef}"). Un "<reject>" est utile lorsque l'on souhaite obtenir les effets secondaires d'une production, sans préjuger d'une correspondance pour une autre production ultérieure dans la règle. Par exemple, pour insérer du code de traçage dans l'analyse : 
complex_rule: { print "In complex rule...\n"; } <reject>
complex_rule: simple_rule '+' 'i' '*' simple_rule
    | 'i' '*' simple_rule
    | simple_rule

Il est également possible de spécifier un rejet conditionnel, en utilisant la forme "<reject:condition>", qui rejette uniquement si la condition spécifiée est vraie. Cette forme de rejet est exactement équivalente à l'action "{(condition)?undef:1}>". Par exemple :

command: save_command
   | restore_command
   | <reject: defined $::tolerant> { exit }
   | <error: Unknown command. Ignored.>

Une directive "<reject>" ne réussit jamais (et n'a donc pas de valeur associée). Un rejet conditionnel peut réussir (si sa condition n'est pas remplie), auquel cas sa valeur est 1.

En tant qu'optimisation supplémentaire, "Parse::RecDescent" ignore toute production commençant par une directive "<reject>", car une telle production ne peut jamais correspondre ou avoir des effets secondaires utiles. Un avertissement de niveau 1 est émis dans tous ces cas.

Notez que les productions commençant par des directives conditionnelles "<reject:...>" ne sont jamais optimisées ainsi, même si elles garantissent toujours l'échec (par exemple : "<reject:1>").

Étant donné que les grammaires sont analysées différemment, il existe une contrainte mineure sur la condition d'une directive conditionnelle "<reject:...>" : elle ne peut pas contenir de caractères bruts '<' ou '>'. Par exemple :

line: cmd <reject: $thiscolumn > max> data

produit une erreur lors de la construction d'un analyseur à partir de cette grammaire (car l'analyseur ne peut pas savoir si le premier > est un 'inférieur à' ou la fin du "<reject:...>".

Pour surmonter ce problème, placez la condition dans un bloc do{} :

line: cmd <reject: do{$thiscolumn > max}> data

Notez que le même problème peut survenir dans d'autres directives qui acceptent des arguments. La solution est la même dans tous les cas.

Ignorer entre les terminaux
La directive "<skip>" permet de modifier le préfixe terminal utilisé dans une production. Par exemple :

OneLiner: Command <skip:'[ \t]*'> Arg(s) /;/

entraîne l'ignorance des seuls espaces et tabulations avant les terminaux dans la sous-règle "Arg" (et toutes ses sous-règles) et également avant le terminal final "/;/". Une fois la production terminée, le préfixe terminal précédent est réinstallé. Notez que cela implique que des productions distinctes d'une règle doivent réinitialiser leurs préfixes terminaux individuellement.

La directive "<skip>" évalue à son préfixe terminal précédent, il est donc facile de réinitialiser un préfixe plus tard dans une production :

Command: <skip:","> CSV(s) <skip:$item[1]> Modifier

La valeur spécifiée après le deux-points est interpolée dans un modèle, donc tous les éléments suivants sont équivalents (bien que leur efficacité augmente dans la liste) :

<skip: "$colon|$comma">   # EN SUPPOSANT QUE LES VARIABLES CONTiennent LES VALEURS ÉVIDENTES
<skip: ':|,'>
<skip: q{[:,]}>
<skip: qr/[:,]/>

Il n'y a pas de moyen direct de définir le préfixe pour une règle entière, sauf comme suit :

Rule: <skip: '[ \t]*'> Prod1
    | <skip: '[ \t]*'> Prod2a Prod2b
    | <skip: '[ \t]*'> Prod3

ou, mieux encore :

Rule: <skip: '[ \t]*'>
(
    Prod1
  | Prod2a Prod2b
  | Prod3
)

Le modèle de saut est passé aux sous-règles, donc la définition du saut pour la règle supérieure comme décrit actuellement définit réellement le préfixe pour toute la grammaire (sauf si seule la méthode correspondant à la règle supérieure est appelée). Alternativement, ou si vous avez plus d'une règle supérieure dans votre grammaire, vous pouvez fournir une directive globale "<skip>" avant de définir toute règle dans la grammaire. Ce sont les alternatives préférées à la configuration de $Parse::RecDescent::skip.

Ajoute...

La directive "<skip>" permet d'avoir un comportement de saut dynamique complet. Par exemple :

Rule_with_dynamic_skip: <skip: $::skip_pattern> Rule

Vous pouvez définir $::skip_pattern avant d'invoquer "Rule_with_dynamic_skip" et ainsi sauter ce que vous avez spécifié.

Note : Jusqu'à la version 1.51 de Parse::RecDescent, un mécanisme différent était utilisé pour spécifier les préfixes terminaux. La méthode actuelle n'est pas rétrocompatible avec cette ancienne approche. La méthode actuelle est stable et ne changera jamais.

Note : La directive globale "<skip>" ajoutée dans la version 1.967_004 n'interpolait pas l'argument du motif, mais plaçait plutôt le motif entre apostrophes, puis l'interpolait. Ce comportement a été modifié dans la version 1.967_010, de sorte que le comportement de toutes les directives "<skip>" soit similaire.

Resynchronisation
La directive "<resync>" fournit un moyen visuellement distinctif de consommer une partie du texte en cours d'analyse, souvent pour sauter une entrée erronée. Dans sa forme la plus simple, "<resync>" consomme le texte jusqu'à la prochaine nouvelle ligne ("\n") incluse, et ne réussit que si la nouvelle ligne est trouvée, auquel cas la règle qui l'entoure retourne 0.

Autrement dit, un "<resync>" est exactement équivalent au token "/[^\n]*\n/" suivi de l'action "{ $return = 0 }" (bien que les règles commençant par "<resync>" soient ignorées lors de la génération des messages d'erreur). Un usage typique pourrait être :

script : command(s)
command: save_command
   | restore_command
   | <resync> # ESSAYER LA LIGNE SUIVANTE, SI POSSIBLE

Il est également possible de spécifier explicitement un motif de resynchronisation, en utilisant la variante "<resync:motif>". Cette version ne réussit que si le motif spécifié correspond (et consomme) le texte analysé. Autrement dit, "<resync:motif>" est exactement équivalent au token "/motif/" (suivi d'une action "{ $return = 0 }"). Par exemple, si les commandes se terminaient par des nouvelles lignes ou des points-virgules :

command: save_command
   | restore_command
   | <resync:[^;\n]*[;\n]>

La valeur d'une directive "<resync>" correctement correspondante (de quelque type que ce soit) est le texte qui a été consommé. Cependant, notez qu'elle définit également $return, donc une production composée d'un seul "<resync>" réussi mais retourne la valeur 0 (ce qu'une règle appelée peut trouver utile pour distinguer les correspondances « vraies » des correspondances « tolérantes »). Rappelez-vous qu'une valeur de retour de 0 indique que la règle a réussi (puisque seul un "undef" indique un échec dans les analyseurs "Parse::RecDescent").

Gestion des erreurs
La directive "<error>" permet la génération automatique ou définie par l'utilisateur de messages d'erreur pendant une analyse. Dans sa forme la plus simple, "<error>" prépare un message d'erreur basé sur la différence entre le dernier élément attendu et le texte qui le cause. Par exemple, étant donné la règle :

McCoy: curse ',' name ', I'm a doctor, not a' a_profession '!'
 | pronoun 'dead,' name '!'
 | <error>

les chaînes de caractères suivantes produiraient les messages suivants :

"Amen, Jim!"
ERREUR (ligne 1): McCoy invalide : Attendu curse ou pronoun non trouvé
"Dammit, Jim, I'm a doctor!"
ERREUR (ligne 1): McCoy invalide : Attendu ", I'm a doctor, not a"
    mais trouvé ", I'm a doctor!" à la place
"He's dead,\n"
ERREUR (ligne 2): McCoy invalide : Attendu name non trouvé
"He's alive!"
ERREUR (ligne 1): McCoy invalide : Attendu 'dead,' mais trouvé "alive!" à la place
"Dammit, Jim, I'm a doctor, not a pointy-eared Vulcan!"
ERREUR (ligne 1): McCoy invalide : Attendu a profession mais trouvé "pointy-eared Vulcan!" à la place

Notez que, lors de la génération automatique de messages d'erreur, tous les traits d'union dans les noms de règles utilisés dans un message sont remplacés par des espaces simples (par exemple, « a_production » devient « a production »). Un choix judicieux des noms de règles peut considérablement améliorer la lisibilité des messages d'erreur automatiques (ainsi que la maintenabilité de la grammaire d'origine).

Si le message d'erreur généré automatiquement n'est pas suffisant, il est possible de fournir un message explicite dans le cadre de la directive d'erreur. Par exemple :

Spock: "Fascinating ',' (name | 'Captain') '.'
 | "Highly illogical, doctor."
 | <error: He never said that!>

ce qui aurait pour résultat que *tous* les échecs d'analyse d'une sous-règle « Spock » afficheraient le message suivant :

ERREUR (ligne <N>): Spock invalide : He never said that!

Le message d'erreur est traité comme une chaîne « qq{...} » et est interpolé lorsque l'erreur est générée (et *non* lors de la spécification de la directive !). Par conséquent :

<error: Mystical error near "$text">

corrigerait correctement le texte environnant qui a causé l'erreur.

Il existe deux autres formes de directive d'erreur : "<error?>" et "<error?: msg>". Celles-ci se comportent exactement comme "<error>" et "<error: msg>", sauf qu'elles ne génèrent d'erreur que si, au moment de leur rencontre, la règle est "engagée". Par exemple :

Scotty: "Ya kenna change the Laws of Phusics," <commit> name
  | name <commit> ',' 'she's goanta blaw!'
  | <error?>

ne générerait une erreur que pour une chaîne commençant par « Ya kenna change the Laws o' Phusics, » ou un nom valide, mais qui ne correspond pas encore à la production correspondante. Ainsi, "$parser->Scotty(\"Aye, Cap'ain\")" échouerait silencieusement (car aucune des deux productions n'est engagée sur cette entrée), tandis que "$parser->Scotty(\"Mr Spock, ah jest kenna do'ut!")" échouerait avec le message d'erreur :

ERREUR (ligne 1): Scotty invalide : attendu 'she's goanta blaw!'
    mais trouvé 'I jest kenna do'ut!' à la place.

car dans ce cas, la deuxième production s'est engagée après avoir fait correspondre le nom initial.

Notez que pour permettre ce comportement, toutes les directives "<error>" qui sont le premier élément d'une production désengagent automatiquement la règle juste assez pour tenter sa production (c'est-à-dire que si sa production échoue, l'engagement est rétabli afin que les productions suivantes puissent être tentées).

Pour désengager la règle avant de générer un message d'erreur, il faut explicitement placer une directive "<uncommit>" avant "<error>". Par exemple :

line: 'Kirk:'  <commit> Kirk
| 'Spock:' <commit> Spock
| 'McCoy:' <commit> McCoy
| <uncommit> <error?> <reject>
| <resync>

Les messages d'erreur générés par les diverses directives "<error...>" ne sont pas affichés immédiatement. Ils sont plutôt stockés dans un tampon et affichés uniquement lorsque l'analyse échoue finalement. De plus, les directives "<error...>" qui provoquent l'échec d'une production d'une règle sont automatiquement retirées de la file des messages si une autre production ultérieure provoque la réussite complète de la règle. Cela signifie que vous pouvez placer des directives "<error...>" partout où elles sont utiles pour le diagnostic, et seules celles associées aux échecs de l'analyseur seront affichées. Voir aussi « PIÈGES ».

En règle générale, les diagnostics les plus utiles sont généralement générés au niveau le plus bas de la grammaire ou au niveau le plus élevé. Un bon critère est d'identifier les sous-règles qui consistent principalement (ou entièrement) en des terminaux, puis de placer une directive "<error...>" à la fin de toute règle qui appelle une ou plusieurs de ces sous-règles.

Il existe un autre cas dans lequel la sortie des différents types de directives d'erreur est supprimée ; c'est-à-dire lorsque la règle qui les contient est analysée dans le cadre d'une « anticipation » (voir « Anticipation »). Dans ce cas, la directive d'erreur provoquera toujours l'échec de la règle, mais le fera silencieusement.

Une directive "<error>" inconditionnelle échoue toujours (et n'a donc aucune valeur associée). Cela signifie que la rencontre d'une telle directive provoque toujours l'échec de la production qui la contient. Par conséquent, une directive "<error>" sera toujours le dernier élément (utile) d'une règle (un avertissement de niveau 3 est émis si une production contient des éléments après une directive "<error>" inconditionnelle).

Une directive "<error?:>" réussit (c'est-à-dire qu'elle n'échoue pas) si la règle actuelle n'est pas engagée lorsque la directive est rencontrée. Dans ce cas, la valeur associée est 0. Par conséquent, ce type de directive peut être utilisé avant la fin d'une production. Par exemple :

command: 'do' <commit> something
   | 'report' <commit> something
   | <error?: Syntax error> <error: Unknown command>

Attention :

La directive "<error?>" ne signifie pas "échouer toujours (mais le faire silencieusement sauf si validé)". Elle signifie en fait "échouer (et signaler) uniquement si validé, sinon réussir". Pour obtenir la sémantique "échouer silencieusement si non validé", il est nécessaire d'utiliser :

rule: item <commit> item(s)
| <error?> <reject>  # ÉCHOUER SILENCIEUSEMENT SAUF SI VALIDÉ

Cependant, comme les gens semblent s'attendre à ce qu'une directive isolée "<error?>" fonctionne comme suit :

rule: item <commit> item(s)
| <error?: Message d'erreur si validé>
| <error:  Message d'erreur si non validé>

Parse::RecDescent ajoute automatiquement une directive "<reject>" si la directive "<error?>" est le seul élément d'une production. Un avertissement de niveau 2 (voir ci-dessous) est émis lorsque cela se produit.

Le niveau de rapport d'erreurs lors de la construction de l'analyseur et lors de l'analyse est contrôlé par la présence ou l'absence de quatre variables globales : $::RD_ERRORS, $::RD_WARN, $::RD_HINT et <$::RD_TRACE>. Si $::RD_ERRORS est définie (et, par défaut, elle l'est) alors les erreurs fatales sont signalées.

Chaque fois que $::RD_WARN est définie, certains problèmes non fatals sont également signalés.

Les avertissements ont un "niveau" associé : 1, 2 ou 3. Plus le niveau est élevé, plus l'avertissement est grave. La valeur de la variable globale correspondante ($::RD_WARN) détermine le *plus bas* niveau d'avertissement à afficher. Par conséquent, pour voir *tous* les avertissements, définissez $::RD_WARN à 1. Pour ne voir que les avertissements les plus graves, définissez $::RD_WARN à 3. Par défaut, $::RD_WARN est initialisée à 3, garantissant que les erreurs graves mais non fatales sont automatiquement signalées.

Il existe également une directive de grammaire pour activer les avertissements depuis la grammaire : "<warn>". Elle prend un argument optionnel, qui spécifie le niveau d'avertissement : "<warn: 2>".

Voir "DIAGNOSTICS" pour une liste des divers messages d'erreur et d'avertissement que Parse::RecDescent génère lorsque ces deux variables sont définies.

La définition de l'une des variables restantes (qui ne sont pas définies par défaut) augmente encore la quantité d'informations rapportées. La définition de $::RD_HINT amène le générateur d'analyseur à proposer des analyses et des indices plus détaillés sur les erreurs et les avertissements. Notez que la définition de $::RD_HINT à n'importe quel moment définit automatiquement $::RD_WARN à 1. Il existe également une directive "<hint>", qui peut être codée en dur dans une grammaire.

La définition de $::RD_TRACE amène le générateur d'analyseur et l'analyseur à rapporter leur progression à STDERR avec une extrême précision (bien que, sans indices à moins que $::RD_HINT ne soit défini séparément). Ce détail peut être modéré d'une seule manière : si $::RD_TRACE a une valeur entière (N) supérieure à 1, seuls les N caractères du "contexte d'analyse en cours" (c'est-à-dire, où nous sommes dans la chaîne d'entrée à un moment donné de l'analyse) sont rapportés à chaque fois.

$::RD_TRACE est principalement utile pour déboguer une grammaire qui ne se comporte pas comme prévu. À cette fin, si $::RD_TRACE est défini lors de la construction d'un analyseur, tout code d'analyseur réel généré est également écrit dans un fichier nommé "RD_TRACE" dans le répertoire local.

Il existe deux directives associées à la variable $::RD_TRACE. Si une grammaire contient une directive "<trace_build>" n'importe où dans sa spécification, $::RD_TRACE est activé pendant la phase de construction de l'analyseur. Si une grammaire contient une directive "<trace_parse>" n'importe où dans sa spécification, $::RD_TRACE est activé pendant toute analyse effectuée par l'analyseur.

Notez que les quatre variables appartiennent au package "main", ce qui les rend plus faciles à référencer dans le code contrôlant l'analyseur, et facilite également leur transformation en options de ligne de commande ("-RD_ERRORS", "-RD_WARN", "-RD_HINT", "-RD_TRACE") sous perl -s.

Les directives correspondantes sont utiles pour "coder en dur" les différentes fonctionnalités de débogage dans une grammaire particulière (plutôt que d'avoir à définir et réinitialiser des variables externes).

Redirection des diagnostics
Les diagnostics fournis par le mécanisme de traçage vont toujours à STDERR. Si vous avez besoin qu'ils aillent ailleurs, localisez et rouvrez STDERR avant l'analyse.

Par exemple :

{
    local *STDERR = IO::File->new(">$filename") or die $!;
    my $result = $parser->startrule($text);
}
Vérifications de cohérence
Chaque fois qu'un analyseur est construit, Parse::RecDescent effectue un certain nombre de vérifications de cohérence (potentiellement coûteuses). Celles-ci incluent : la vérification que la grammaire n'est pas récursive à gauche et qu'aucune règle n'a été laissée indéfinie.

Ces vérifications sont des garde-fous importants pendant le développement, mais constituent une surcharge inutile lorsque la grammaire est stable et prête à être déployée. Parse::RecDescent fournit donc une directive pour les désactiver : "<nocheck>".

Si une grammaire contient une directive "<nocheck>" n'importe où dans sa spécification, les vérifications supplémentaires à la compilation sont ignorées.

Spécification de variables locales
Il est parfois pratique de spécifier des variables qui sont locales à une seule règle. Cela peut être réalisé en incluant une directive "<rulevar:...>" n'importe où dans la règle. Par exemple : 
markup: <rulevar: $tag>
markup: tag {($tag=$item[1]) =~ s/^<|>$//g} body[$tag]

L'exemple de directive "<rulevar: $tag>" provoque la déclaration d'une variable "my" nommée $tag au début de la sous-routine implémentant la règle "markup" (c'est-à-dire, *avant* la première production, quelle que soit la position de la directive dans la règle).

Spécifiquement, toute directive de la forme : "<rulevar:texte>" provoque l'ajout d'une ligne de la forme "my texte;" au début de la sous-routine de la règle, immédiatement après les définitions des variables locales suivantes :

$thisparser $commit
$thisrule   @item
$thisline   @arg
$text   %arg

Cela signifie que les directives "<rulevar>" suivantes fonctionnent comme prévu :

<rulevar: $count = 0 >
<rulevar: $firstarg = $arg[0] || '' >
<rulevar: $myItems = \@item >
<rulevar: @context = ( $thisline, $text, @arg ) >
<rulevar: ($name,$age) = $arg{"name","age"} >

Si une variable qui est également visible par les sous-règles est requise, elle doit être "local"isée, et non "my"isée. "rulevar" est par défaut "my", mais si "local" est explicitement spécifié :

<rulevar: local $count = 0 >

alors une variable "local"isée est déclarée à la place, et sera disponible dans les sous-règles.

Notez cependant que, puisque toutes ces variables sont des variables "my", leurs valeurs *ne persistent pas* entre les tentatives de correspondance sur une règle donnée. Pour conserver les valeurs entre les tentatives de correspondance, les valeurs peuvent être stockées dans le membre "local" de l'objet $thisrule :

countedrule: { $thisrule->{"local"}{"count"}++ }
     <reject>
   | subrule1
   | subrule2
   | <reject: $thisrule->{"local"}{"count"} == 1>
     subrule3

Lors de la correspondance d'une règle, chaque directive "<rulevar>" est traitée comme une directive "<reject>" inconditionnelle (c'est-à-dire, elle provoque l'échec immédiat de la correspondance de la production dans laquelle elle apparaît). Pour cette raison (et pour améliorer la lisibilité), il est habituel de spécifier toute directive "<rulevar>" dans une production séparée au début de la règle (cela a l'avantage ajouté de permettre à "Parse::RecDescent" d'optimiser de telles productions, tout comme il le fait pour la directive "<reject>").

Règles mises en correspondance dynamiquement
Étant donné que les regex et les chaînes entre guillemets doubles sont interpolées, il est relativement facile de spécifier des productions avec des jetons "sensibles au contexte". Par exemple : 
command:  keyword  body  "end $item[1]"

ce qui garantit qu'un bloc de commande est délimité par une paire "<mot-clé>...end <même mot-clé>".

La construction de productions dans lesquelles les sous-règles sont sensibles au contexte est également possible, via la directive "<matchrule:...>". Cette directive se comporte de manière identique à un élément de sous-règle, sauf que la règle qui est invoquée pour la faire correspondre est déterminée par la chaîne spécifiée après le deux-points. Par exemple, nous pourrions réécrire la règle "command" comme suit :

command:  keyword  <matchrule:body>  "end $item[1]"

Tout ce qui apparaît après le deux-points dans la directive est traité comme une chaîne interpolée (c'est-à-dire, comme s'il apparaissait dans l'opérateur "qq{...}") et la valeur de cette chaîne interpolée est le nom de la sous-règle à faire correspondre.

Bien sûr, le simple fait de placer une chaîne constante comme "body" dans une directive "<matchrule:...>" présente peu d'intérêt ou d'avantage. La puissance de la directive

Cuando se use
Una cadena que se interpola a algo interesante, se ve una vez que se utiliza. Por ejemplo:

command:    keyword <matchrule:$item[1]_body> "end $item[1]"
keyword:    'while' | 'if' | 'function'
while_body: condition block
if_body:    condition block ('else' block)(?)
function_body:  arglist block

Ahora, la regla "command" selecciona cómo proceder según la palabra clave que se encuentre. Es como si "command" fuera declarado:

command:    'while'    while_body    "end while"
   |    'if'       if_body   "end if"
   |    'function' function_body "end function"
Cuando se use una <matchrule:...> directiva
Como subregla repetida, el nombre de la regla a llamar es "late-bound". Es decir, el nombre de la regla a llamar se re-evalúa *cada vez* que se realiza un intento de coincidencia. Por lo tanto, la siguiente gramática:

{ $::species = 'dogs' }
pair:   'two' <matchrule:$::species>(s)
dogs:   /dogs/ { $::species = 'cats' }
cats:   /cats/

seguirá coincidiendo completamente con el texto "two dogs cats cats", mientras que solo coincidirá con el texto "two dogs dogs dogs" hasta el octavo carácter. Si el nombre de la regla fuera "early bound" (es decir, evaluado solo la primera vez que se encuentra la directiva en una producción), se esperaría el comportamiento inverso.

Nota que la directiva "matchrule" trata una cadena que se usa como nombre de una regla, *no* como invocación de una regla. Es decir, es como una referencia simbólica en Perl, no como un "eval". Así como puedes decir:

$subname = 'foo';
# y luego...
&{$foo}(@args);

pero no:

$subname = 'foo(@args)';
# y luego...
&{$foo};

similarmente puedes decir:

$rulename = 'foo';
# y en la gramática...
<matchrule:$rulename>[@args]

pero no:

$rulename = 'foo[@args]';
# y en la gramática...
<matchrule:$rulename>
Acciones diferidas
La directiva "<defer:...>" se usa para especificar una acción a realizar cuando (y solo cuando) la producción actual finalmente es exitosa.
Cuando aparece una directiva "<defer:...>", el código que especifica se convierte en un cierre (una referencia a una subrutina anónima) que se coloca en el objeto de parseo activo. Nota que, porque el código diferido se convierte en un cierre, los valores de cualquier variable local (como $text, <@item>, etc.) se preservan hasta que el código diferido se ejecute realmente.
Si el parse finalmente es exitoso y la producción en la cual la directiva "<defer:...>" fue evaluada formó parte del parseo exitoso, entonces el código diferido se ejecuta inmediatamente antes de que el parse se devuelva. Si, sin embargo, la producción que asignó la acción diferida falla, o una de las reglas de nivel superior que llamó a esa producción falla, entonces la acción diferida se quita de la cola y no se ejecuta.
Ejemplo, dada la gramática:
sentence: noun trans noun
| noun intrans
noun:     'the dog'
    { print "$item[1]\t(noun)\n" }
|     'the meat'
    { print "$item[1]\t(noun)\n" }
trans:    'ate'
    { print "$item[1]\t(transitive)\n" }
intrans:  'ate'
    { print "$item[1]\t(intransitive)\n" }
   |  'barked'
    { print "$item[1]\t(intransitive)\n" }
entonces el parse del texto "the dog ate" producirá la salida:
the dog  (noun)
ate  (transitive)
the dog  (noun)
ate  (intransitive)
Esto es porque, aunque la primera producción de "sentence" finalmente falla, sus subreglas "noun" y "trans" coinciden, y por eso ejecutan sus acciones asociadas. Luego, la segunda producción de "sentence" es exitosa, causando que las acciones de las subreglas "noun" y "intrans" se ejecuten también.
En cambio, si las acciones fueran reemplazadas por directivas "<defer:...>":
sentence: noun trans noun
| noun intrans
noun:     'the dog'
    <defer: print "$item[1]\t(noun)\n" >
|     'the meat'
    <defer: print "$item[1]\t(noun)\n" >
trans:    'ate'
    <defer: print "$item[1]\t(transitive)\n" >
intrans:  'ate'
    <defer: print "$item[1]\t(intransitive)\n" >
   |  'barked'
    <defer: print "$item[1]\t(intransitive)\n" >
la salida sería:
the dog  (noun)
ate  (intransitive)
ya que las acciones diferidas solo se ejecutan si fueron evaluadas en una producción que finalmente contribuye al parseo exitoso.
En este caso, aunque la primera producción de "sentence" causó que las subreglas "noun" y "trans" coincidieran, esa producción finalmente falló y así las acciones diferidas de esas subreglas fueron descartadas. La segunda producción luego fue exitosa, causando que el parse completo se completara, y así se ejecutan las acciones diferidas de la (segunda) coincidencia de la subregla "noun" y la siguiente coincidencia de "intrans".
Las acciones diferidas proporcionan un medio para mejorar el rendimiento de un parser, ejecutando solo aquellas acciones que forman parte del árbol de parseo final de los datos de entrada.
O bien, las acciones diferidas pueden verse como un mecanismo para construir (y ejecutar) una subrutina personalizada correspondiente a los datos de entrada, de manera similar a cómo las acciones auto-generadas (ver "Autoactions") pueden utilizarse para construir una estructura personalizada para un tipo específico de entrada.
Independientemente de si la acción especificada se ejecuta o no, una directiva "<defer:...>" siempre se realiza con éxito, devolviendo el número de acciones diferidas actualmente guardadas en ese momento.
Parseo de Perl
Parse::RecDescent proporciona soporte limitado para parsear subconjuntos de Perl, es decir: operadores de cita, variables Perl y bloques de código completos.
La directiva "<perl_quotelike>" puede usarse para parsear cualquier operador de cita Perl: 'a string', "m/a pattern/", "tr{ans}{lation}", etc. Esto lo hace llamando a Text::Balanced::quotelike().
Si se encuentra un operador de cita, se devuelve una referencia a un array de ocho elementos. Estos elementos son idénticos a los últimos ocho elementos devueltos por Text::Balanced::extract_quotelike() en un contexto de array, es decir:
[0]
el nombre del operador de cita - 'q', 'qq', 'm', 's', 'tr' - si el operador fue nombrado; de lo contrario "undef",
[1]
el delimitador izquierdo del primer bloque de la operación,
[2]
el texto del primer bloque de la operación (es decir, el contenido de una cita, el patrón de una coincidencia, la sustitución o la lista de destino de una traducción),
[3]
el delimitador derecho del primer bloque de la operación,
[4]
el delimitador izquierdo del segundo bloque de la operación si existe (es decir, si es un "s", "tr" o "y"); de lo contrario "undef",
[5]
el texto del segundo bloque de la operación si existe (es decir, la sustitución de una sustitución o la lista de destino de una traducción); de lo contrario "undef",
[6]
el delimitador derecho del segundo bloque de la operación (si existe); de lo contrario "undef",
[7]
los modificadores al final de la operación (si existen); de lo contrario "undef".
Si no se encuentra una expresión de tipo de cita, la directiva falla con el valor usual "undef".
La directiva "<perl_variable>" puede usarse para parsear cualquier variable Perl: $scalar, @array, %hash, $ref->{field}[$index], etc. Esto lo hace llamando a Text::Balanced::extract_variable().
Si la directiva coincide con el texto que representa una especificación válida de variable Perl, devuelve ese texto. De lo contrario, falla con el valor usual "undef".
La directiva "<perl_codeblock>" puede usarse para parsear un bloque de código entre llaves Perl, como: { $a = 1; f() =~ m/pat/; }. Esto lo hace llamando a Text::Balanced::extract_codeblock().
Si la directiva coincide con el texto que representa un bloque de código válido Perl, devuelve ese texto. De lo contrario, falla con el valor usual "undef".
Usted también puede indicar qué tipo de llaves usar como delimitadores externos. Por ejemplo:
arglist: <perl_codeblock ()>
causando que un arglist coincida con un bloque de código Perl cuyos delimitadores externos sean "(...)" (en lugar de los por defecto "{...}").
Construyendo tokens
Finalmente, Parse::RecDescent podrá parsear entrada tokenizada, así como cadenas ordinarias. Para prepararse para este día feliz, se ha proporcionado la directiva "<token:...>". Esta directiva crea un token que será adecuado para la entrada de un parser Parse::RecDescent (cuando finalmente se soporte la entrada tokenizada).
El texto del token es el valor de la expresión inmediatamente siguiente.
Mantén toda la estructura del archivo.
"<token:...>"

La directiva "<token:...>" siempre tiene un valor de retorno que es la referencia a un hash que es el nuevo token. También establece el valor de retorno para la producción a esa referencia de hash.

La directiva "<token:...>" hace que sea fácil construir un lexer compatible con Parse::RecDescent en Parse::RecDescent:

my $lexer = new Parse::RecDescent q
{
 lex:    token(s)
 token:  /a\b/          <token:INDEF>
     |  /the\b/        <token:DEF>
     |  /fly\b/        <token:NOUN,VERB>
     |  /[a-z]+/i { lc $item[1] }  <token:ALPHA>
     |  <error: Unknown token>
};

que eventualmente será usado con una gramática regular de Parse::RecDescent:

my $parser = new Parse::RecDescent q
{
 startrule: subrule1 subrule 2
# ETC...
};

con o sin una fase de pre-lexing:

$parser->startrule( $lexer->lex($data) );

o con un enfoque de lex-on-demand:

$parser->startrule( sub{$lexer->token(\$data)} );

pero actualmente solo la directiva "<token:...>" está implementada. El resto es vaporware.

"<leftop:...>"

La directiva "<leftop:...>" proporciona un método más fácil para especificar operaciones binarias. Usando "<leftop:...>", los ejemplos anteriores se convierten en:

disjunction:    <leftop: conjunction 'or' conjunction>
conjunction:    <leftop: atom 'and' atom>

La directiva "<leftop:...>" especifica un operador binario asociativo a la izquierda. Es especificada alrededor de tres otros elementos de la gramática (generalmente subreglas o terminales), que coinciden con el operando izquierdo, el operador mismo y el operando derecho respectivamente.

Una directiva como:

disjunction:    <leftop: conjunction 'or' conjunction>

se convierte en:

disjunction:    ( conjunction ('or' conjunction)(s?)
{ $return = [ $item[1], @{$item[2]} ] } )

En otras palabras, una directiva "<leftop:...>" coincide con el operando izquierdo seguido de cero o más repeticiones del operador y el operando derecho. Luego, se aplanan los elementos coincidentes en un array anónimo que se convierte en el valor (único) de la directiva "<leftop:...>".

Por ejemplo, una directiva "<leftop:...>" como:

output:  <leftop: ident '<<' expr >

cuando se le da un string como:

cout << var << "str" << 3

equivale a:

output:  ident          { $return = [$item[1]]   }
      |  ident '<<' expr        { $return = [@item[1,3]]     }
      |  ident '<<' expr '<<' expr      { $return = [@item[1,3,5]]   }
      |  ident '<<' expr '<<' expr '<<' expr    { $return = [@item[1,3,5,7]] }
      #  ...etc...

similarmente, la directiva "<rightop:...>" toma un operando izquierdo, un operador y un operando derecho:

assign:  <rightop: var '=' expr >

y se convierte en:

assign:  ( (var '=' {$return=$item[1]})(s?) expr
{ $return = [ @{$item[1]}, $item[2] ] } )

equivalente a un operador asociativo a la derecha:

assign:  expr       { $return = [$item[1]]       }
      |  var '=' expr       { $return = [@item[1,3]]     }
      |  var '=' var '=' expr   { $return = [@item[1,3,5]]   }
      |  var '=' var '=' var '=' expr   { $return = [@item[1,3,5,7]] }
      #  ...etc...

Nota: Para ambas directivas "<leftop:...>" y "<rightop:...>", la directiva no devuelve normalmente el operador mismo, sino una lista de operandos involucrados. Esto es especialmente útil para especificar listas:

list: '(' <leftop: list_item ',' list_item> ')'
{ $return = $item[2] }

Sin embargo, hay un problema: a veces el operador mismo es significativo. Por ejemplo, en una lista Perl, tanto una coma como un "=>" son separadores válidos, pero el "=>" tiene semánticas de stringificación adicionales. Por lo tanto, es importante saber qué se usó en cada caso.

Para resolver este problema, las directivas "<leftop:...>" y "<rightop:...>" *sí* devuelven los operadores, bajo dos circunstancias. La primera es cuando el operador se especifica como una subregla. En ese caso, lo que el operador coincide es devuelto (asumiendo que si el operador es importante lo suficiente para tener su propia subregla, es importante lo suficiente para devolver).

La segunda circunstancia es cuando el operador se especifica como una expresión regular. En ese caso, si el primer subpatrón del regular se coincide, el valor de coincidencia es devuelto (esto es similar al comportamiento de la función Perl "split").

En otras palabras, dada la entrada:

( a=>1, b=>2 )

las especificaciones:

list:      '('  <leftop: list_item separator list_item>  ')'
separator: ',' | '=>'

o:

list:      '('  <leftop: list_item /(,|=>)/ list_item>  ')'

causan que los separadores de la lista estén mezclados con los operandos en el array anónimo en $item[2]:

[ 'a', '=>', '1', ',', 'b', '=>', '2' ]

pero la siguiente versión:

list:      '('  <leftop: list_item /,|=>/ list_item>  ')'

devuelve solo los operadores:

[ 'a', '1', 'b', '2' ]

De hecho, ninguna de las especificaciones anteriores maneja el caso de una lista vacía, ya que las directivas "<leftop:...>" y "<rightop:...>" requieren al menos un operando derecho o izquierdo para coincidir. Para especificar que el operador puede coincidir de forma trivial, es necesario agregar un cualificador "(s?)" a la directiva:

list:      '('  <leftop: list_item /,|=>/ list_item>(s?)  ')'

Nota: En casi todos los ejemplos anteriores, los primeros y terceros argumentos de la directiva "<leftop:...>" eran los mismos subreglas. Esto se debe a que las directivas "<leftop:...>" se utilizan frecuentemente para especificar listas separadas de la misma clase de elemento. Para hacer más fácil la especificación de tales listas, se utiliza la siguiente sintaxis:

list:   element(s /,/)

que es exactamente equivalente a:

list:   <leftop: element /,/ element>

Nota: El separador debe especificarse como un patrón raw (es decir, no como una cadena o subregla).

"Scored"

Por defecto, las reglas de gramática de Parse::RecDescent siempre aceptan la primera producción que coincide con la entrada. Sin embargo, si varias producciones pueden potencialmente coincidir con la misma entrada, elegir la primera que lo hace no es necesariamente óptimo.

Por ejemplo, si estás analizando la oración "time flies like an arrow", podrías usar una regla así:

sentence: verb noun preposition article noun { [@item] }
| adjective noun verb article noun { [@item] }
| noun verb preposition article noun { [@item] }

cada una de estas reglas coincide con la oración, pero la tercera es la interpretación más probable. Sin embargo, si la oración fuera "fruit flies like a banana", la segunda regla sería probablemente la adecuada.

Para adaptarse a situaciones como esta, se puede usar la directiva "<score:...>". La directiva es equivalente a una directiva "<reject>" incondicional, excepto que permite especificar un "score" para la producción actual. Si ese score es numéricamente mayor que el mejor score de cualquier producción precedente, la producción actual se cacheará para consideración posterior. Si no hay producción posterior que coincida, la producción cacheada se trata como si hubiera coincidido, y el valor del ítem inmediatamente antes de su directiva "<score:...>" se devuelve como resultado.

En otras palabras, poniendo una directiva "<score:...>" al final de cada producción, puedes elegir la producción que coincide usando criterios distintos de la especificación del orden. Por ejemplo:

sentence: verb noun preposition article noun { [@item] } <score: sensible(@item)>
| adjective noun verb article noun   { [@item] } <score: sensible(@item)>
| noun verb preposition article noun { [@item] } <score: sensible(@item)>

ahora, cuando cada producción alcanza su respectiva directiva "<score:...>", se llama a la subrutina "sensible" para evaluar...

Mantener la estructura del archivo.

La variable $score conserve toujours la valeur la plus élevée de toute production, et la variable $score_return conserve la valeur de retour correspondante.

À titre d'exemple supplémentaire, la grammaire suivante correspond à des lignes séparées par des virgules, des points ou des points-virgules. Cela peut prêter à confusion si une ligne séparée par des points-virgules contient également des virgules, ou vice versa. La grammaire résout l'ambiguïté en sélectionnant la règle qui génère le plus petit nombre de champs :

line: seplist[sep=>','] <score: -@{$item[1]}>
| seplist[sep=>':'] <score: -@{$item[1]}>
| seplist[sep=>" "] <score: -@{$item[1]}>
seplist: <skip:""> <leftop: /[^$arg{sep}]*/ "$arg{sep}" /[^$arg{sep}]*/>

Note : La négation est utilisée à l'intérieur de la "<score:...>" pour garantir que la liste de séparation comportant le plus d'éléments obtienne le score le plus bas.

Comme le montrent les exemples ci-dessus, il est courant que toutes les productions d'une règle utilisent exactement la même "<score:...>" dans chaque production. Il est fastidieux de répéter cette directive identique dans chaque production, Parse::RecDescent fournit donc également la directive "<autoscore:...>".

Si une directive "<autoscore:...>" apparaît dans une production d'une règle, le code qu'elle spécifie est utilisé comme code de score pour chaque production de cette règle, à l'exception de celles qui se terminent déjà par une directive "<score:...>" explicite. Par conséquent, les règles ci-dessus pourraient être réécrites comme suit :

line: <autoscore: -@{$item[1]}>
line: seplist[sep=>',']
| seplist[sep=>':']
| seplist[sep=>" "]
sentence: <autoscore: sensible(@item)>
| verb noun preposition article noun { [@item] }
| adjective noun verb article noun   { [@item] }
| noun verb preposition article noun { [@item] }

Note : La directive "<autoscore:...>" agit comme un "<reject>" conditionnel et (similaire à la directive "<rulevar:...>") est supprimée lors de la compilation.

Se passer des vérifications de grammaire
Au cours du processus de compilation d'un analyseur, Parse::RecDescent effectue un petit nombre de vérifications sur la grammaire qu'il reçoit. Plus précisément, il vérifie que la grammaire n'est pas récursive, qu'il n'y a pas de constructions « insatiables » de la forme :

rule: subrule(s) subrule

et qu'il n'y a pas de règles manquantes (c'est-à-dire référencées mais jamais définies).

Ces vérifications sont importantes pendant le développement, mais peuvent ralentir la construction de l'analyseur dans du code stable. C'est pourquoi Parse::RecDescent fournit la directive , qui peut apparaître avant la première définition de règle et désactive complètement les vérifications pour le reste de la grammaire actuelle.

Généralement, cette directive est ajoutée une fois que l'analyseur a été entièrement testé et est prêt à être diffusé.

Listes d'arguments de sous-règle

Il est parfois utile de passer des données à une sous-règle qui est appelée. Par exemple, considérez le fragment de grammaire suivant :

classdecl: keyword decl
keyword:   'struct' | 'class';
decl:      # WHATEVER

La règle "decl" pourrait souhaiter savoir laquelle des deux mots-clés a été utilisée (car cela pourrait affecter certains aspects de la façon dont la déclaration suivante est interprétée). "Parse::RecDescent" permet de passer des données à une règle en les plaçant dans une *liste d'arguments* (c'est-à-dire entre parenthèses) immédiatement après tout élément de sous-règle dans une production. Par conséquent, nous pourrions passer le mot-clé à "decl" comme suit :

classdecl: keyword decl[ $item[1] ]
keyword:   'struct' | 'class';
decl:      # WHATEVER

La liste d'arguments peut contenir n'importe quel nombre (y compris zéro !) d'expressions séparées par des virgules. En d'autres termes, elle ressemble exactement à une référence de tableau anonyme en Perl. Par exemple, nous pourrions passer le mot-clé, le nom de la règle environnante et la chaîne 'keyword' à "decl" comme suit :

classdecl: keyword decl[$item[1],$item[0],'keyword']
keyword:   'struct' | 'class';
decl:      # WHATEVER

À l'intérieur de la règle à laquelle les données sont transmises (dans cet exemple "decl"), les données sont disponibles sous forme d'éléments d'une variable locale @arg. Ainsi, "decl" pourrait exprimer son intention comme suit :

classdecl: keyword decl[$item[1],$item[0],'keyword']
keyword:   'struct' | 'class';
decl:      { print "Declaring $arg[0] (a $arg[2])\n";
     print "(this rule called by $arg[1])" }

Les listes d'arguments de sous-règles peuvent également être interprétées comme des hachages, en changeant simplement la variable locale @arg en %arg. Nous pourrions donc réécrire l'exemple précédent comme suit :

classdecl: keyword decl[keyword => $item[1],
    caller => $item[0],
    type => 'keyword']
keyword:   'struct' | 'class';
decl:      { print "Declaring $arg{keyword} (a $arg{type})\n";
     print "(this rule called by $arg{caller})" }

Les deux @arg et %arg sont toujours disponibles, de sorte que le concepteur de la grammaire peut choisir l'une ou l'autre des conventions (ou des combinaisons) qui lui conviennent le mieux.

Les listes d'arguments de sous-règles sont également utiles pour créer des « modèles de règles » (surtout lorsqu'elles sont utilisées avec la directive "<matchrule:...>"). Par exemple, la sous-règle :

list:     <matchrule:$arg{rule}> /$arg{sep}/ list[%arg]
    { $return = [ $item[1], @{$item[3]} ] }
|     <matchrule:$arg{rule}>
    { $return = [ $item[1]] }

est un bon modèle pour le problème courant de correspondance d'une liste séparée. Par exemple :

function: 'func' name '(' list[rule=>'param',sep=>';'] ')'
param:    list[rule=>'name',sep=>';'] ':' typename
name:     /\w+/
typename: name

Lorsqu'une liste d'arguments de sous-règle est utilisée avec une sous-règle répétée, la liste d'arguments est évaluée *avant* le spécificateur de répétition :

list:   /some|many/ thing[ $item[1] ](s)

La liste d'arguments est « liée tardivement ». Autrement dit, elle est réévaluée chaque fois que la sous-règle répétée est tentée. Cela signifie que chaque tentative répétée de faire correspondre la sous-règle peut passer un ensemble d'arguments différent, si la valeur de l'expression dans la liste d'arguments change entre les tentatives. Ainsi, par exemple, la grammaire :

{ $::species = 'dogs' }
pair:   'two' animal[$::species](s)
animal: /$arg[0]/ { $::species = 'cats' }

correspondra entièrement à la chaîne « two dogs cats cats », alors qu'elle ne fera correspondre que « two dogs dogs dogs » jusqu'au huitième caractère. Si la valeur de la liste d'arguments était « liée tôt » (c'est-à-dire évaluée uniquement lors de la première tentative d'une correspondance répétée), on s'attendrait à ce que les actions de correspondance soient inversées.

Bien qu'il soit possible de « lier tôt » efficacement de telles listes d'arguments, cela peut être fait en leur passant une valeur qui ne change pas à chaque tentative. Par exemple :

{ $::species = 'dogs' }
pair:   'two' { $::species } animal[$item[2]](s)
animal: /$arg[0]/ { $::species = 'cats' }

Les arguments peuvent également être transmis à la règle de départ, simplement en les ajoutant à la liste d'arguments avec laquelle la règle de départ est appelée ( *après* le paramètre « numéro de ligne »). Par exemple, étant donné :

$parser = new Parse::RecDescent ( $grammar );
$parser->data($text, 1, "str", 2, \@arr);
#         ^^^^^  ^  ^^^^^^^^^^^^^^^
#       |    |     |
# TEXT TO BE PARSED  |     |
# STARTING LINE NUMBER     |
# ELEMENTS OF @arg WHICH IS PASSED TO RULE data

alors, dans les productions de la règle "data", le tableau @arg contiendra "("str", 2, \@arr)".

Alternances

Les alternances sont des règles implicites (sans nom) définies dans le cadre d'une production. Une alternance est définie comme une séquence de productions séparées par | à l'intérieur d'une paire de parenthèses. Par exemple :

character: 'the' ( good | bad | ugly ) /dude/

Chaque alternance définit implicitement une nouvelle sous-règle, dont le nom généré automatiquement indique son origine : « _alternation_<I>_of_production_<P>_of_rule<R> » pour les valeurs respectives de <I>, <P> et <R>. Un appel à cette sous-règle implicite est inséré à sa place entre parenthèses. Par conséquent, l'exemple ci-dessus n'est qu'un raccourci pratique pour :

character: 'the'
   _alternation_1_of_production_1_of_rule_character
   /dude/
_alternation_1_of_production_1_of_rule_character:
   good | bad | ugly

Étant donné que les alternances sont traitées récursivement par le générateur d'analyseurs, n'importe quel type d'élément peut apparaître dans une alternance. Par exemple :

character: 'the' ( 'high' "plains"  # Silent, avec poncho
     | /no[- ]name/ # Silent, sans poncho
     | vengeance_seeking    # Poncho facultatif
     | <error>
     ) drifter

Dans ce cas, si une erreur se produit, le message généré automatiquement serait :

ERROR (line <N>): Invalid implicit subrule: Expected
      'high' or /no[- ]name/ or generic,
      but found "pacifist" instead

Étant donné que chaque alternance a un nom, il est même possible de les étendre ou de les remplacer :

parser->Replace("_alternation_1_of_production_1_of_rule_character:
    'generic Eastwood'");

Important, étant donné que les alternances sont un type de sous-règle, elles peuvent avoir des spécificateurs de répétition :

character: 'the' ( good | bad | ugly )(?) /dude/

Analyse incrémentale

Parse::RecDescent fournit deux méthodes — "Extend" et "Replace" — qui peuvent être utilisées pour modifier la grammaire qui correspond à un analyseur. Ces deux méthodes prennent le même argument que "Parse::RecDescent".

ent::new", à savoir une chaîne de spécification grammaticale

"Parse::RecDescent::Extend" interprète la spécification grammaticale et ajoute les productions qu'il trouve à la fin des règles pour lesquelles elles sont spécifiées. Par exemple :

$add = "name: 'Jimmy-Bob' | 'Bobby-Jim'\ndesc: colour /necks?/";
parser->Extend($add);

ajoute deux productions à la règle « name » (en la créant si nécessaire) et une production à la règle « desc ».

"Parse::RecDescent::Replace" est identique, sauf qu'il réinitialise d'abord chaque règle spécifiée dans la grammaire supplémentaire, supprimant toutes les productions existantes. Par conséquent, après :

$add = "name: 'Jimmy-Bob' | 'Bobby-Jim'\ndesc: colour /necks?/";
parser->Replace($add);

il n'y a que des noms valides et la seule description possible.

Une utilisation plus intéressante des méthodes "Extend" et "Replace" est de les appeler à l'intérieur de l'action d'un analyseur en cours d'exécution. Par exemple :

typedef: 'typedef' type_name identifier ';'
       { $thisparser->Extend("type_name: '$item[3]'") }
   | <error>
identifier: ...!type_name /[A-Za-z_]w*/

ce qui empêche automatiquement les noms de type d'être déclarés avec « typedef », ou :

command: 'map' key_name 'to' abort_key
       { $thisparser->Replace("abort_key: '$item[2]'") }
   | 'map' key_name 'to' key_name
       { map_key($item[2],$item[4]) }
   | abort_key
       { exit if confirm("abort?") }
abort_key: 'q'
key_name: ...!abort_key /[A-Za-z]/

ce qui permet à l'utilisateur de modifier la liaison de la touche d'abandon, mais pas de la désactiver.

L'utilisation judicieuse de telles constructions permet de reconfigurer un analyseur en cours d'exécution, éliminant ainsi le besoin de rétroaction sémantique en fournissant une rétroaction syntaxique à la place. Cependant, tel qu'implémenté actuellement, Replace() et Extend() doivent régénérer et ré-evaluer l'ensemble de l'analyseur chaque fois qu'ils sont appelés. Cela les rend assez lents pour les grammaires volumineuses.

Dans de tels cas, l'utilisation judicieuse d'une expression régulière interpolée sera probablement beaucoup plus efficace :

typedef: 'typedef' type_name/ identifier ';'
       { $thisparser->{local}{type_name} .= "|$item[3]" }
   | <error>
identifier: ...!type_name /[A-Za-z_]w*/
type_name: /$thisparser->{local}{type_name}/

Précompilation des analyseurs

Normalement, Parse::RecDescent construit un analyseur à partir d'une grammaire au moment de l'exécution. Cette approche simplifie la conception et l'implémentation du code d'analyse, mais présente l'inconvénient de ralentir le processus d'analyse - il faut attendre que Parse::RecDescent construise l'analyseur à chaque exécution du programme. Les grammaires longues ou complexes peuvent être particulièrement lentes à construire, entraînant des retards inacceptables au démarrage.

Pour surmonter cela, le module fournit un moyen de « pré-construire » un objet analyseur et de le sauvegarder dans un module séparé. Ce module peut ensuite être utilisé pour créer des clones de l'analyseur d'origine.

Une grammaire peut être précompilée à l'aide de la méthode de classe "Precompile". Par exemple, pour précompiler une grammaire stockée dans le scalaire $grammar, et produire une classe nommée PreGrammar dans un fichier de module nommé PreGrammar.pm, vous pouvez utiliser :

use Parse::RecDescent;
Parse::RecDescent->Precompile([$options_hashref], $grammar, "PreGrammar", ["RuntimeClass"]);

Le premier argument requis est la chaîne de grammaire, le second est le nom de la classe à construire. Le nom du fichier de module est généré automatiquement en ajoutant « .pm » au dernier élément du nom de la classe. Ainsi :

Parse::RecDescent->Precompile($grammar, "My::New::Parser");

produirait un fichier de module nommé Parser.pm.

Après le nom de la classe, vous pouvez spécifier le nom de la classe runtime appelée par l'analyseur précompilé. Voir « Runtimes précompilés » pour plus de détails.

Une référence de hachage optionnelle peut être fournie comme premier argument à "Precompile". Cet argument est actuellement EXPÉRIMENTAL et peut changer dans une future version de Parse::RecDescent. L'unique option actuellement supportée est "-standalone", voir « Analyseurs précompilés autonomes ».

Il est quelque peu fastidieux de devoir écrire un petit programme Perl juste pour générer une classe de grammaire précompilée, Parse::RecDescent dispose donc d'une magie spéciale qui vous permet de faire le travail directement depuis la ligne de commande.

Si votre grammaire est spécifiée dans un fichier nommé grammar, vous pouvez générer une classe nommée Yet::Another::Grammar comme ceci :

> perl -MParse::RecDescent - grammar Yet::Another::Grammar [Runtime::Class]

Cela produirait un fichier nommé Grammar.pm contenant la définition complète d'une classe appelée Yet::Another::Grammar. Bien sûr, pour utiliser cette classe, vous devrez placer le fichier Grammar.pm dans un répertoire nommé Yet/Another, quelque part dans votre chemin d'inclusion Perl.

Une fois la nouvelle classe créée, il est très facile de l'utiliser pour construire un analyseur. Vous faites simplement « use » le nouveau module, puis vous appelez sa méthode "new" pour créer un objet analyseur. Par exemple :

use Yet::Another::Grammar;
my $parser = Yet::Another::Grammar->new();

L'effet de ces deux lignes est exactement le même que :

use Parse::RecDescent;
open GRAMMAR_FILE, "grammar" or die;
local $/;
my $grammar = <GRAMMAR_FILE>;
my $parser = Parse::RecDescent->new($grammar);

seulement considérablement plus rapide.

Notez cependant que les analyseurs produits par l'une ou l'autre approche sont exactement les mêmes, donc bien que la précompilation ait un effet sur la vitesse de configuration, elle n'a aucun effet sur la vitesse d'analyse. RecDescent 2.0 remédiera à ce problème.

Analyseurs précompilés autonomes

Jusqu'à la version 1.967003 de Parse::RecDescent, les modules analyseurs construits avec "Precompile" dépendaient de Parse::RecDescent. Les futures versions de Parse::RecDescent avec des implémentations internes différentes casseraient les analyseurs précompilés existants.

La version 1.967_005 a ajouté la possibilité pour Parse::RecDescent de s'inclure dans le fichier .pm résultant si vous passez l'option booléenne "-standalone" à "Precompile" :

Parse::RecDescent->Precompile({ -standalone => 1, },
    $grammar, "My::New::Parser");

Parse::RecDescent est inclus en tant que $class::_Runtime afin d'éviter les conflits entre une version installée de Parse::RecDescent et d'autres analyseurs autonomes précompilés créés avec Parse::RecDescent. Le nom de cette classe peut être modifié avec l'option "-runtime_class" de Precompile. Ce renommage est expérimental et susceptible d'être modifié dans les futures versions.

Les analyseurs précompilés restent dépendants de Parse::RecDescent par défaut, car cette fonctionnalité est toujours considérée comme expérimentale. À l'avenir, les analyseurs autonomes deviendront la norme.

Runtimes précompilés

Les analyseurs précompilés autonomes incluent chacun une copie de Parse::RecDescent. Pour les utilisateurs qui ont une famille d'analyseurs précompilés liés, c'est très inefficace. "Precompile" prend maintenant en charge l'option expérimentale "-runtime_class". Pour construire un analyseur précompilé avec un nom de runtime différent, appelez :

Parse::RecDescent->Precompile({
        -standalone => 1,
        -runtime_class => "My::Runtime",
    },
    $grammar, "My::New::Parser");

L'analyseur autonome résultant contiendra une copie de Parse::RecDescent, renommée en « My::Runtime ».

Pour construire un ensemble d'analyseurs qui « use » un runtime au nom personnalisé, sans inclure ce runtime dans la sortie, construisez simplement ces analyseurs avec "-runtime_class" et sans "-standalone" :

Parse::RecDescent->Precompile({
        -runtime_class => "My::Runtime",
    },
    $grammar, "My::New::Parser");

Le runtime lui-même doit également être généré, afin qu'il puisse être « use » par My::New::Parser. Pour générer le fichier runtime, utilisez l'un des deux appels suivants :

Parse::RecDescent->PrecompiledRuntime("My::Runtime");
Parse::RecDescent->Precompile({
        -standalone => 1,
        -runtime_class => "My::Runtime",
    },
    '', # grammaire vide
    "My::Runtime");

PIÈGES

Cette section décrit les erreurs courantes que les auteurs de grammaires semblent commettre régulièrement.

1. S'attendre à ce qu'une erreur invalide toujours une analyse

Une erreur courante lors de l'utilisation des messages d'erreur est d'écrire la grammaire comme suit :

file: line(s)
line: line_type_1
| line_type_2
| line_type_3
| <error>

L'attente semble être que toute ligne qui n'est pas de type 1, 2 ou 3 invoquera la directive "<error>" et provoquera ainsi l'échec de l'analyse.

Malheureusement, cela ne se produit que si l'erreur survient dans la toute première ligne. La première règle stipule qu'un "file" est mis en correspondance par une ou plusieurs lignes, donc si même une seule ligne réussit, la première règle est complètement satisfaite et l'analyse dans son ensemble réussit. Cela signifie que tous les messages d'erreur générés par les échecs ultérieurs dans la règle "line" sont silencieusement ignorés.

Généralement, ce qui est vraiment nécessaire est ceci :

file: line(s) eofile    { $return = $item[1] }
line: line_type_1
| line_type_2
| line_type_3
| <error>
eofile: /^\Z/

L'ajout de la sous-règle "eofile" à la première production signifie qu'un fichier ne correspond à une série de correspondances de "line" réussies qui consomment le texte d'entrée complet. Si du texte d'entrée reste après que les lignes aient été mises en correspondance, il doit y avoir eu une erreur dans la dernière "line". Dans ce cas, la règle "eofile" échouera, entraînant l'échec de l'ensemble de la règle "file".

Notez également que "eofile" doit correspondre à "/^\Z/" (fin de texte), pas &quo

2. Utiliser un « return » dans une action

Une action est semblable à un bloc de code "do" dans la sous-routine qui implémente la règle englobante. Ainsi, si vous placez une instruction "return" dans une action :

range: '(' start '..' end )'
    { return $item{end} }
   /\s+/

cette sous-routine s'arrêtera immédiatement, sans vérifier les éléments restants de la production actuelle (par exemple, le "/\s+/") et sans définir les structures de données nécessaires pour indiquer que la règle s'est terminée avec succès.

La méthode correcte pour définir une valeur de retour dans une action est de définir la variable $return :

range: '(' start '..' end )'
            { $return = $item{end} }
       /\s+/

2. Définir $Parse::RecDescent::skip au moment de l'analyse

Si vous souhaitez modifier le comportement par défaut de suppression (voir « Séparateurs Terminaux » et la directive "<skip:...>") à l'aide de la variable $Parse::RecDescent::skip, vous devez vous rappeler de définir cette variable *avant* de créer l'objet de règle.

Par exemple, vous pourriez vouloir ignorer tous les commentaires Perl avec cette expression régulière :

my $skip_spaces_and_comments = qr/
      (?mxs:
         \s+         # ou des espaces
         | \# .*?$   # ou un dièse et ce qui suit jusqu'à la fin de ligne
      )*             # répété dans n'importe quel ordre
   /;

Puis :

my $parser1 = Parse::RecDescent->new($grammar);
$Parse::RecDescent::skip = $skip_spaces_and_comments;
my $parser2 = Parse::RecDescent->new($grammar);
$parser1->parse($text); # celui-ci ne gère pas les commentaires
$parser2->parse($text); # celui-ci gère correctement les commentaires

Les deux analyseurs se comportent différemment car le comportement de suppression spécifié par $Parse::RecDescent::skip est stocké dans l'objet de règle lors de sa construction, et non lors de l'analyse.

DIAGNOSTICS

Les diagnostics sont conçus pour être auto-explicatifs (en particulier si vous utilisez -RD_HINT (sous perl -s) ou si vous définissez $::RD_HINT dans votre programme).

"Parse::RecDescent" diagnostique actuellement les éléments suivants :

  • Expressions régulières invalides utilisées comme motifs terminaux (erreur fatale).
  • Code Perl invalide dans des blocs de code (erreur fatale).
  • Utilisation incorrecte ou incohérente de l'aperçu (lookahead) (erreur fatale).
  • Récursion gauche évidente (erreur fatale).
  • Composants manquants ou étranges dans les directives "<leftop>" ou "<rightop>" (erreur fatale).
  • Composants non reconnus dans la spécification de la grammaire (erreur fatale).
  • Composants de règle spécifiés avant la première règle (erreur fatale) ou après une directive "<error>" (avertissement de niveau 3).
  • Définitions de règles manquantes (génère seulement un avertissement de niveau 3, car elles peuvent être fournies plus tard via Parse::RecDescent::Extend()).
  • Instances où le comportement de répétition gourmand peut rendre une production non réalisable (un avertissement de niveau 3 - voir « PROBLÈMES EN COURS ET DIRECTIONS FUTURES » ci-dessous).
  • Tentatives de définir des règles nommées 'Replace' ou 'Extend', qui ne peuvent pas être appelées directement via l'objet analyseur en raison de la signification par défaut de "Parse::RecDescent::Replace" et "Parse::RecDescent::Extend". (génère seulement un avertissement de niveau 2, car de telles règles peuvent toujours être utilisées comme sous-règles).
  • Productions constituées d'une seule directive "<error?>" et qui peuvent donc réussir de manière inattendue (un avertissement de niveau 2, car cela pourrait être l'effet souhaité).
  • Constructions d'aperçu consécutives (un avertissement de niveau 1 uniquement, car leurs effets s'accumulent simplement).
  • Productions commençant par une directive "<reject>" ou "<rulevar:...>". Celles-ci sont optimisées (un avertissement de niveau 1).
  • Règles générées sous $::AUTOSTUB (un avertissement de niveau 1).

BOGUES ET IRRITATIONS

Il y a des problèmes sérieux qui pourraient être cachés dans ce code, donc le plaisir est grand ! Les plaintes, les cas de test et autres commentaires sont les bienvenus.

Les problèmes récurrents comprennent :

  • Aucun support pour l'analyse d'un flux d'entrée directement. Si et quand les dieux de Perl nous accorderaient des expressions régulières sur un flux, cela devrait être simple (ah, mais ne le faites pas !)
  • Le générateur d'analyseur peut être induit en erreur si les actions ne sont pas correctement délimitées ou si elles contiennent des erreurs de syntaxe Perl particulièrement mal implémentées (en particulier des parenthèses non équilibrées).
  • Le générateur ne détecte que la forme la plus évidente de récursion gauche (récursion sur la première sous-règle d'une règle). Les formes plus complexes de récursion gauche (par exemple, une sous-règle avec un match « zéro » de répétition « zéro ou plus » sur le deuxième élément d'une règle, ou après un match de sous-règle avec une production vide) ne sont pas détectées.
  • Au lieu de critiquer la récursion gauche, le générateur devrait silencieusement transformer la grammaire pour l'éliminer. N'attendez pas cette fonctionnalité trop tôt, car elle nécessiterait une approche plus compliquée pour la génération de l'analyseur.
  • Les analyseurs générés n'exécutent pas toujours aussi vite que souhaité.
  • L'analyseur méta devrait être construit à l'aide de "Parse::RecDescent" :-)

PROBLÈMES EN COURS ET DIRECTIONS FUTURES

1.
Les répétitions sont « gourmandes sans correction » car elles consommeront tout ce qu'elles peuvent et ne reviendront pas en arrière si ce comportement fait échouer une production. Par exemple : 
rule: subrule(s) subrule

ne peut jamais être satisfait, car la répétition consommera toutes les sous-règles qu'elle trouve, n'en laissant aucune pour correspondre au deuxième élément. De telles constructions sont relativement rares (et "Parse::RecDescent::new" génère un avertissement lorsqu'elles se produisent) de sorte que cela pourrait ne pas être un problème, d'autant plus que le comportement incontrôlable peut être contourné « manuellement » en écrivant :

rule: penultimate_subrule(s) subrule
penultimate_subrule: subrule ...subrule

Le problème est que cette construction est exactement deux fois plus coûteuse que l'originale, tandis que le backtracking ajouterait seulement 1/N au coût (pour correspondre à N répétitions de "subrule"). J'aimerais beaucoup avoir des commentaires sur la nécessité du backtracking ; en particulier dans les cas où son absence rend la performance de l'analyse problématique.

2.
En ouvrant cette boîte de Pandore, il faut également considérer si une forme de répétition non gourmande est nécessaire. Bien qu'il soit possible (à un certain coût) de fournir manuellement la fonctionnalité requise : 
rule: nongreedy_subrule(s) othersubrule
nongreedy_subrule: subrule ...!othersubrule

En général, le problème est de savoir si le bénéfice de cette fonctionnalité supplémentaire l'emporte sur les inconvénients de compliquer davantage (actuellement minimale) la syntaxe de la spécification de la grammaire et (pire) d'introduire une charge supplémentaire sur les analyseurs générés.

3.
Une directive "<autocommit>" serait géniale. Elle serait utile pour pouvoir dire : 
command: <autocommit>
command: 'find' name
   | 'find' address
   | 'do' command 'at' time 'if' condition
   | 'do' command 'at' time
   | 'do' command
   | unusual_command

et que le générateur travaille à la « élaguer » comme ceci :

command: 'find' name
   | 'find' <commit> address
   | 'do' <commit> command <uncommit>
    'at' time
    'if' <commit> condition
   | 'do' <commit> command <uncommit>
    'at' <commit> time
   | 'do' <commit> command
   | unusual_command

Il y a plusieurs problèmes ici. Premièrement, le "<autocommit>" devrait-il automatiquement installer un "<uncommit>" au début de la dernière production (pour la raison que la "command" ne sait pas si une "unusual_command" pourrait commencer par "find" ou "do") ou devrait-il analyser le sous-graphe "unusual_command" (pour voir s'il pourrait être réalisable après un "find" ou "do") ?

La deuxième question est de savoir comment les expressions régulières devraient être traitées. La manière la plus simple serait simplement de désactiver le "commit" avant elles (pour la raison qu'elles *pourraient* correspondre). Une plus grande efficacité serait obtenue en analysant tous les jetons littéraux précédents pour déterminer si le motif pourrait y correspondre.

En général, les problèmes sont : une approche automatique de « l'élagage » peut-elle aborder un problème manuel ?
