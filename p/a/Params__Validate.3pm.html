Params::Validate(3pm) Documentation Perl fournie par l'utilisateur Params::Validate(3pm)

NOM

Params::Validate - Valider les paramètres de méthode/fonction

VERSION

version 1.31

SYNOPSIS

use Params::Validate qw(:all);
# prend des paramètres nommés (hash ou hashref)
sub foo {
    validate(
        @_, {
            foo => 1,    # obligatoire
            bar => 0,    # optionnel
        }
    );
}
# prend des paramètres positionnels
sub bar {
    # les deux premiers sont obligatoires, le troisième est optionnel
    validate_pos( @_, 1, 1, 0 );
}
sub foo2 {
    validate(
        @_, {
            foo =>
                # spécifier un type
                { type => ARRAYREF },
            bar =>
                # spécifier une interface
                { can => [ 'print', 'flush', 'frobnicate' ] },
            baz => {
                type      => SCALAR,     # un scalaire ...
                                         # ... qui est un entier simple ...
                regex     => qr/^\d+$/,
                callbacks => {           # ... et plus petit que 90
                    'less than 90' => sub { shift() < 90 },
                },
            }
        }
    );
}
sub callback_with_custom_error {
    validate(
        @_,
        {
            foo => {
                callbacks => {
                    'is an integer' => sub {
                        return 1 if $_[0] =~ /^-?[1-9][0-9]*$/;
                        die "$_[0] is not a valid integer value";
                    },
                },
            }
        }
    );
}
sub with_defaults {
    my %p = validate(
        @_, {
            # obligatoire
            foo => 1,
            # $p{bar} sera 99 si bar n'est pas donné. bar est maintenant
            # optionnel.
            bar => { default => 99 }
        }
    );
}
sub pos_with_defaults {
    my @p = validate_pos( @_, 1, { default => 99 } );
}
sub sets_options_on_call {
    my %p = validate_with(
        params => \@_,
        spec   => { foo => { type => SCALAR, default => 2 } },
        normalize_keys => sub { $_[0] =~ s/^-//; lc $_[0] },
    );
}

DESCRIPTION

Je vous recommande de considérer l'utilisation de Params::ValidationCompiler à la place. Ce module, bien que pur Perl, est significativement plus rapide que celui-ci, au prix d'une adoption d'un système de types tel que Specio, Type::Tiny, ou celui fourni avec Moose.

Ce module vous permet de valider les paramètres d'appel de méthode ou de fonction à un niveau de spécificité arbitraire. Au niveau le plus simple, il est capable de valider que les paramètres requis ont été fournis et qu'aucun paramètre supplémentaire non spécifié n'a été passé.

Il est également capable de déterminer qu'un paramètre est d'un type spécifique, qu'il s'agit d'un objet d'une certaine hiérarchie de classes, qu'il possède certaines méthodes, ou d'appliquer des callbacks de validation aux arguments.

EXPORT

Le module exporte toujours les fonctions validate() et validate_pos().

Il dispose également d'une fonction supplémentaire disponible pour l'exportation, "validate_with", qui peut être utilisée pour valider tout type de paramètres et définir diverses options sur une base par invocation.

De plus, il peut exporter les constantes suivantes, utilisées dans le cadre de la vérification de type. Ce sont "SCALAR", "ARRAYREF", "HASHREF", "CODEREF", "GLOB", "GLOBREF", et "SCALARREF", "UNDEF", "OBJECT", "BOOLEAN", et "HANDLE". Celles-ci sont expliquées dans la section sur la validation de type.

Les constantes sont disponibles via la balise d'exportation ":types". Il existe également une balise ":all" qui inclut toutes les constantes ainsi que la fonction validation_options().

VALIDATION DES PARAMÈTRES

Les mécanismes de validation fournis par ce module peuvent gérer les paramètres nommés ou positionnels. Pour la plupart, les mêmes fonctionnalités sont disponibles pour chacun. La plus grande différence réside dans la manière dont la spécification de validation est fournie à la sous-routine correspondante. L'autre différence concerne les messages d'erreur générés en cas d'échec des vérifications de validation.

Lors de la gestion des paramètres nommés, le module accepte soit une hash, soit une référence de hash.

Les sous-routines attendant des paramètres nommés doivent appeler la sous-routine validate() comme suit :

validate(
    @_, {
        parametre1 => spec de validation,
        parametre2 => spec de validation,
        ...
    }
);

Les sous-routines attendant des paramètres positionnels doivent appeler la sous-routine validate_pos() comme suit :

validate_pos( @_, { spec de validation }, { spec de validation } );

Paramètres Obligatoires/Optionnels

Si vous voulez simplement spécifier que certains paramètres sont obligatoires et d'autres optionnels, cela peut être fait très simplement.

Pour une sous-routine attendant des paramètres nommés, vous feriez ceci :

validate( @_, { foo => 1, bar => 1, baz => 0 } );

Cela signifie que les paramètres "foo" et "bar" sont obligatoires et que le paramètre "baz" est optionnel. La présence de tout autre paramètre provoquera une erreur.

Pour une sous-routine attendant des paramètres positionnels, vous feriez ceci :

validate_pos( @_, 1, 1, 0, 0 );

Cela signifie que vous attendez au moins 2 et pas plus de 4 paramètres. Si vous avez une sous-routine qui a un nombre minimum de paramètres mais peut en accepter un nombre maximum quelconque, vous pouvez faire ceci :

validate_pos( @_, 1, 1, (0) x (@_ - 2) );

Ceci sera toujours valide tant qu'au moins deux paramètres sont donnés. Une construction similaire pourrait être utilisée pour les paramètres de validation plus complexes décrits plus loin.

Veuillez noter que ceci :

validate_pos( @_, 1, 1, 0, 1, 1 );

n'a absolument aucun sens, ne le faites donc pas. Tous les zéros doivent venir à la fin de la spécification de validation.

De plus, si vous spécifiez qu'un paramètre peut avoir une valeur par défaut, alors il est considéré comme optionnel.

Validation de Type

Ce module prend en charge les types simples suivants, qui peuvent être exportés sous forme de constantes :

  • SCALAR

    Un scalaire qui n'est pas une référence, tel que 10 ou 'hello'. Un paramètre non défini n'est pas traité comme un scalaire. Si vous voulez autoriser les valeurs non définies, vous devrez spécifier "SCALAR | UNDEF".

  • ARRAYREF

    Une référence de tableau telle que "[1, 2, 3]" ou "\@foo".

  • HASHREF

    Une référence de hash telle que "{ a => 1, b => 2 }" ou "\%bar".

  • CODEREF

    Une référence de sous-routine telle que "\&foo_sub" ou "sub { print "hello" }".

  • GLOB

    Celui-ci est un peu délicat. Un glob serait quelque chose comme *FOO, mais pas "\*FOO", qui est une référence de glob. Il faut noter que cette astuce :

    my $fh = do { local *FH; };

    fait de $fh un glob, pas une référence de glob. D'un autre côté, la valeur de retour de "Symbol::gensym" est une référence de glob. L'un ou l'autre peut être utilisé comme descripteur de fichier ou de répertoire.

  • GLOBREF

    Une référence de glob telle que "\*FOO". Voir l'entrée GLOB ci-dessus pour plus de détails.

  • SCALARREF

    Une référence à un scalaire telle que "\$x".

  • UNDEF

    Une valeur indéfinie

    Types

    The following types are supported:

    • OBJECT: Une référence bénie.

    • BOOLEAN: Il s'agit d'une option spéciale, et c'est juste un raccourci pour "UNDEF | SCALAR".

    • HANDLE: Cette option est également spéciale, et c'est juste un raccourci pour "GLOB | GLOBREF". Cependant, il semble probable que la plupart des personnes intéressées par les globs ou les références de globs soient probablement intéressées par le fait que le paramètre en question puisse être un descripteur de fichier ou de répertoire valide.

    Pour spécifier qu'un paramètre doit être d'un type donné lors de l'utilisation de paramètres nommés, faites ceci:

    validate(
    @_, {
        foo => { type => SCALAR },
        bar => { type => HASHREF }
    }
);

    Si un paramètre peut être de plusieurs types, utilisez simplement l'opérateur OU bit à bit ("|") pour les combiner.

    validate( @_, { foo => { type => GLOB | GLOBREF } );

    Pour les paramètres positionnels, cela peut être spécifié comme suit:

    validate_pos( @_, { type => SCALAR | ARRAYREF }, { type => CODEREF } );

Validation d'interface

Pour spécifier qu'un paramètre est censé avoir un certain ensemble de méthodes, nous pouvons faire ce qui suit:

   validate(
       @_, {
           foo =>
               # juste doit être capable de ->bar
               { can => 'bar' }
       }
   );
... ou ...
   validate(
       @_, {
           foo =>
               # doit être capable de ->bar et ->print
               { can => [qw( bar print )] }
       }
   );

Validation de classe

Un mot d'avertissement. Lors de la construction de vos interfaces externes, il est probablement préférable de spécifier les méthodes que vous attendez d'un objet plutôt que sa classe (ou une classe enfant). Cela rendra votre API beaucoup plus flexible.

Cela étant dit, si vous souhaitez valider qu'un paramètre entrant appartient à une classe (ou une classe enfant) ou à des classes, faites:

   validate(
       @_,
       { foo => { isa => 'My::Frobnicator' } }
   );
... ou ...
   validate(
       @_,
       # doit être les deux, pas l'un ou l'autre !
       { foo => { isa => [qw( My::Frobnicator IO::Handle )] } }
   );

Validation Regex

Si vous souhaitez spécifier qu'un paramètre donné doit correspondre à une expression régulière spécifique, cela peut être fait avec la clé de spécification "regex". Par exemple:

validate(
    @_,
    { foo => { regex => qr/^\d+$/ } }
);

La valeur de la clé "regex" peut être une chaîne de caractères ou une regex pré-compilée créée via "qr".

Si la valeur vérifiée par rapport à une regex est indéfinie, la regex est explicitement vérifiée par rapport à la chaîne vide ('') afin d'éviter les avertissements "Utilisation d'une valeur non initialisée".

Le module "Regexp::Common" sur CPAN est une excellente source d'expressions régulières adaptées à la validation des entrées.

Validation par rappel

Si rien de ce qui précède ne suffit, il est possible de passer un ou plusieurs rappels pour valider le paramètre. Le rappel recevra la valeur du paramètre comme premier argument. Son deuxième argument sera tous les paramètres, sous forme de référence à un hash ou à un tableau. Les rappels sont spécifiés comme des références de hash. La clé est un identifiant pour le rappel (utilisé dans les messages d'erreur) et la valeur est une référence de sous-routine, telle que:

validate(
    @_,
    {
        foo => {
            callbacks => {
                'plus petit qu'une boîte à pain' => sub { shift() < $breadbox },
                'vert ou bleu'           => sub {
                    return 1 if $_[0] eq 'green' || $_[0] eq 'blue';
                    die "$_[0] n'est pas vert ou bleu !";
                }
            }
        }
    }
);
validate(
    @_, {
        foo => {
            callbacks => {
                'plus grand que baz' => sub { $_[0] > $_[1]->{baz} }
            }
        }
    }
);

Le rappel doit renvoyer une valeur vraie si la valeur est valide. Sinon, il peut renvoyer faux ou mourir. Si vous renvoyez faux, un message d'erreur générique sera levé par "Params::Validate".

Si votre rappel meurt à la place, vous pouvez fournir un message d'erreur personnalisé. Si le rappel meurt avec une chaîne de caractères simple, cette chaîne sera ajoutée à un message d'exception généré par "Params::Validate". Si le rappel meurt avec une référence (bénie ou non), alors celle-ci sera relancée telle quelle par "Params::Validate".

Détaché

Si vous souhaitez que les valeurs soient détachées, définissez la clé "untaint" dans une spécification de hash à une valeur vraie, comme ceci:

my %p = validate(
    @_, {
        foo => { type => SCALAR, untaint => 1 },
        bar => { type => ARRAYREF }
    }
);

Cela détachera le paramètre "foo" si les paramètres sont valides.

Notez que le détachement n'est effectué que si tous les paramètres sont valides. De plus, seules les valeurs de retour sont détachées, pas les valeurs d'origine passées à la fonction de validation.

Demander le détachement d'une valeur de référence ne fera rien, car "Params::Validate" tentera uniquement de détacher la référence elle-même.

Obligatoire/Facultatif revisité

Si vous souhaitez spécifier quelque chose comme le type ou l'interface, plus le fait qu'un paramètre peut être facultatif, faites ceci:

validate(
    @_, {
        foo => { type => SCALAR },
        bar => { type => ARRAYREF, optional => 1 }
    }
);

ou ceci pour les paramètres positionnels:

validate_pos(
    @_,
    { type => SCALAR },
    { type => ARRAYREF, optional => 1 }
);

Par défaut, les paramètres sont considérés comme obligatoires sauf indication contraire.

Dépendances

Il est également possible de spécifier qu'un paramètre optionnel donné dépend de la présence d'un ou plusieurs autres paramètres optionnels.

validate(
    @_, {
        cc_number => {
            type     => SCALAR,
            optional => 1,
            depends  => [ 'cc_expiration', 'cc_holder_name' ],
        },
        cc_expiration  => { type => SCALAR, optional => 1 },
        cc_holder_name => { type => SCALAR, optional => 1 },
    }
);

Dans ce cas, "cc_number", "cc_expiration" et "cc_holder_name" sont tous facultatifs. Cependant, si "cc_number" est fourni, alors "cc_expiration" et "cc_holder_name" doivent également être fournis.

Cela vous permet de regrouper des ensembles de paramètres qui doivent tous être fournis ensemble.

La version validate_pos() des dépendances est légèrement différente, en ce que vous ne pouvez dépendre que d'un seul autre paramètre. De plus, si, par exemple, le deuxième paramètre 2 dépend du quatrième paramètre, cela implique une dépendance vis-à-vis du troisième paramètre également. En effet, si le quatrième paramètre est requis, l'utilisateur doit également fournir un troisième paramètre afin qu'il y ait quatre paramètres au total.

"Params::Validate" mourra si vous essayez de dépendre d'un paramètre non déclaré dans votre spécification de paramètre.

Spécification des valeurs par défaut

Si les fonctions validate() ou validate_pos() sont appelées dans un contexte de liste, elles renverront un hash ou un tableau contenant les paramètres d'origine plus les valeurs par défaut indiquées par la spécification de validation.

Si la fonction n'est pas appelée dans un contexte scalaire, fournir une valeur par défaut dans la spécification de validation indique toujours que le paramètre est facultatif.

Le hash ou le tableau renvoyé par la fonction sera toujours une copie des paramètres d'origine, afin de laisser @_ intact pour la fonction appelante.

Des exemples simples de valeurs par défaut seraient:

my %p = validate( @_, { foo => 1, bar => { default => 99 } } );
my @p = validate_pos( @_, 1, { default => 99 } );

En contexte scalaire, une référence de hash ou une référence de tableau sera renvoyée, le cas échéant.

NOTES D'UTILISATION

Échec de la validation

Par défaut, lorsque la validation échoue, "Params::Validate" appelle Carp::confess(). Cela peut être remplacé en définissant l'option "on_fail", qui est décrite dans la section OPTIONS GLOBALES.

Appels de méthodes

Lors de l'utilisation de ce module pour valider les paramètres passés à un appel de méthode, vous voudrez probablement supprimer la classe/l'objet de la liste des paramètres avant d'appeler validate() ou validate_pos(). Si votre méthode attend des paramètres nommés, alors ceci est nécessaire pour que la fonction validate() fonctionne réellement, sinon @_ ne pourra pas être utilisé comme un hash, car il contiendra d'abord votre objet (ou classe) suivi d'un ensemble de clés et de valeurs.

Ainsi, l'utilisation idiomatique de validate() dans un appel de méthode ressemblera à ceci:

sub method {
    my $self = shift;
    my %params = validate(
        @_, {
            foo => 1,
            bar => { type => ARRAYREF },
        }
    );
}

Accélérer la validation

Dans la plupart des cas, la spécification de validation restera la même pour chaque appel à une sous-routine. Dans ce cas, vous pouvez accélérer la validation en définissant la spécification de validation une seule fois, plutôt qu'à chaque appel à la sous-routine:

my %spec = ( ... );
sub foo {
    my %params = validate( @_, \%spec );
}

Vous pouvez également u

utilisez la fonctionnalité "state" pour ce faire :

use feature 'state';
sub foo {
    state $spec = { ... };
    my %params = validate( @_, $spec );
}

OPTIONS "GLOBALES"

Étant donné que l'API des fonctions validate() et validate_pos() ne permet pas de spécifier d'autres options que la spécification de validation, il est possible de définir certaines options comme des pseudo-'globales'. Celles-ci vous permettent de spécifier, par exemple, si la validation des paramètres nommés doit être sensible à la casse.

Ces options sont appelées pseudo-'globales' car ces paramètres sont **uniquement appliqués aux appels provenant du package qui définit les** **options**.

En d'autres termes, si je suis dans le package "Foo" et que j'appelle validation_options(), ces options ne sont effectives que lorsque j'appelle validate() depuis le package "Foo".

Bien que cela soit très différent de la manière dont la plupart des autres modules fonctionnent, je pense que cela est nécessaire pour permettre à un module/application d'utiliser Params::Validate tout en utilisant d'autres modules qui utilisent également Params::Validate, potentiellement avec des options différentes.

L'inconvénient est que si vous écrivez une application avec un style d'appel standard pour toutes les fonctions, et que votre application comporte dix modules, **chaque** **module doit inclure un appel à** **validation_options()**. Vous pourriez bien sûr écrire un module que tous vos modules utilisent et qui utilise diverses astuces pour faire cela lors de l'importation.

Options

  • normalize_keys => $callback

    Cette option n'est pertinente que lorsqu'il s'agit de paramètres nommés.

    Ce callback sera utilisé pour transformer les clés de hachage des paramètres et de la spécification des paramètres lorsque validate() ou validate_with() sont appelés.

    Toutes les modifications apportées par ce callback seront reflétées dans le hachage de paramètres renvoyé par la fonction de validation. Par exemple :

    sub foo {
    return validate_with(
        params => \@_,
        spec   => { foo => { type => SCALAR } },
        normalize_keys =>
            sub { my $k = shift; $k =~ s/^-//; return uc $k },
    );
}
%p = foo( foo => 20 );
# $p{FOO} vaut maintenant 20
%p = foo( -fOo => 50 );
# $p{FOO} vaut maintenant 50

    Le callback doit renvoyer une valeur définie.

    Si un callback est fourni, les options obsolètes "ignore_case" et "strip_leading" sont ignorées.

  • allow_extra => $boolean

    Si vrai, la routine de validation autorisera des paramètres supplémentaires non nommés dans la spécification de validation. Dans le cas des paramètres positionnels, cela autorise un nombre illimité de paramètres maximum (bien qu'un minimum puisse toujours être défini). La valeur par défaut est faux.

  • on_fail => $callback

    Si elle est fournie, cette fonction de rappel sera appelée chaque fois qu'une vérification de validation échouera. Elle sera appelée avec un seul paramètre, qui sera une chaîne décrivant l'échec. C'est utile si vous souhaitez que ce module lève des exceptions sous forme d'objets plutôt que de chaînes, par exemple.

    Ce callback est censé appeler die() en interne. S'il ne le fait pas, la validation se poursuivra, avec des résultats imprévisibles.

    Par défaut, la fonction confess() du module Carp est utilisée.

  • stack_skip => $number

    Ceci indique à Params::Validate combien de cadres de pile ignorer lors de la recherche d'un nom de sous-routine à utiliser dans les messages d'erreur. Par défaut, il examine un cadre en arrière, l'appelant immédiat de validate() ou validate_pos(). Si cette option est définie, le nombre de cadres indiqué est ignoré à la place.

  • ignore_case => $boolean

    OBSOLÈTE

    Ceci n'est pertinent que lorsqu'il s'agit de paramètres nommés. S'il est vrai, le code de validation ignorera la casse des noms de paramètres. La valeur par défaut est faux.

  • strip_leading => $characters

    OBSOLÈTE

    Ceci aussi n'est pertinent que lorsqu'il s'agit de paramètres nommés. S'il est fourni, tout paramètre commençant par ces caractères sera considéré comme équivalent à des paramètres sans eux. Par exemple, si cela est spécifié comme '-', alors "-foo" et "foo" seraient considérés comme identiques.

OPTIONS PAR INVOCATION

La fonction validate_with() peut être utilisée pour définir les options listées ci-dessus sur une base par invocation. Par exemple :

my %p = validate_with(
    params => \@_,
    spec   => {
        foo => { type    => SCALAR },
        bar => { default => 10 }
    },
    allow_extra => 1,
);

En plus des options listées ci-dessus, il est également possible de définir l'option "called", qui devrait être une chaîne de caractères. Cette chaîne sera utilisée dans tous les messages d'erreur dus à un échec de la spécification de validation.

Cette sous-routine validera les paramètres nommés comme un hachage si le paramètre "spec" est une référence de hachage. S'il s'agit d'une référence de tableau, les paramètres sont supposés être positionnels.

my %p = validate_with(
    params => \@_,
    spec   => {
        foo => { type    => SCALAR },
        bar => { default => 10 }
    },
    allow_extra => 1,
    called      => 'Le constructeur de classe Quux::Baz',
);
my @p = validate_with(
    params => \@_,
    spec   => [
        { type    => SCALAR },
        { default => 10 }
    ],
    allow_extra => 1,
    called      => 'Le constructeur de classe Quux::Baz',
);

DÉSACTIVATION DE LA VALIDATION

Si la variable d'environnement "PERL_NO_VALIDATION" est définie sur une valeur vraie, alors la validation est désactivée. Cela peut être utile si vous souhaitez uniquement utiliser ce module pendant le développement mais que vous ne voulez pas de ralentissement en production.

La seule erreur qui sera détectée sera lorsqu'un nombre impair de paramètres est passé à une fonction/méthode qui attend un hachage.

Si vous souhaitez activer et désactiver sélectivement la validation à l'exécution, vous pouvez directement définir la variable globale $Params::Validate::NO_VALIDATION. Il est **fortement** recommandé de **localiser** toute modification de cette variable, car d'autres modules que vous utilisez peuvent s'attendre à ce que la validation soit activée lorsqu'ils s'exécutent. Par exemple :

{
    local $Params::Validate::NO_VALIDATION = 1;
    # pas d'erreur
    foo( bar => 2 );
}
# erreur
foo( bar => 2 );
sub foo {
    my %p = validate( @_, { foo => 1 } );
    ...;
}

Mais si vous voulez vous tirer une balle dans le pied et la désactiver, allez-y !

SPÉCIFICATION D'UNE IMPLÉMENTATION

Ce module est fourni avec deux implémentations équivalentes, une en XS et une en Perl pur. Par défaut, il essaiera de charger la version XS et se rabattra sur l'implémentation Perl pur si nécessaire. Si vous souhaitez demander une version spécifique, vous pouvez définir la variable d'environnement "PARAMS_VALIDATE_IMPLEMENTATION" sur "XS" ou "PP". Si l'implémentation demandée ne peut pas être chargée, ce module mourra lors de son chargement.

MODE TAINT

L'implémentation XS de ce module a quelques problèmes en mode Taint avec les versions de Perl antérieures à 5.14. Si la validation **échoue**, au lieu d'obtenir le message d'erreur attendu, vous obtiendrez un message tel que "Insecure dependency in eval_sv". Cela peut être contourné en désinfectant vous-même les arguments, en utilisant l'implémentation Perl pur, ou en mettant à jour votre Perl.

LIMITATIONS

Actuellement, il n'y a aucun moyen (sans utiliser une fonction de rappel) de spécifier que quelque chose doit être d'une des classes d'une liste, ou qu'il doit posséder une des méthodes d'une liste. Si cela est souhaité, cela pourrait être ajouté à l'avenir.

Idéalement, il n'y aurait qu'une seule fonction de validation. Si quelqu'un trouve comment faire cela, faites-le moi savoir.
