NOM Documentation Perl contribuée par l'utilisateur PAR::Packer::Dépannage(3)

NOM

PAR::Packer::Dépannage - Problèmes courants lors du paquetage de scripts avec pp

SYNOP

Explique certains problèmes et solutions courants lors du paquetage de scripts avec pp.

DESCRIPTION

Modules_manquants

Lors de l'exécution de l'exécutable généré, celui-ci plante avec un message semblable à :

Can't locate Foo/Bar.pm in @INC (you may need to install the Foo::Bar module) 
  (@INC contains: ...) at script/pp5yBDq.pl line 1.
BEGIN failed--compilation aborted at script/pp5yBDq.pl line 1.

Votre script "require" le module "Foo::Bar" (probablement indirectement depuis un autre module), mais pp ne l'a pas inclus dans l'exécutable. pp utilise Module::ScanDeps pour parcourir récursivement votre script afin de trouver les modules "require" nécessaires. Parfois, cette recherche peut être incomplète en raison des nombreuses façons dont Perl permet d'exprimer son désir de charger un module.

Essayez de compiler avec les options --compile ou --execute pour résoudre le problème. Si cela échoue, ajoutez explicitement le module avec l'option -M, c'est-à-dire :

% pp -M Foo::Bar ...

Il peut être nécessaire de répéter l'ajout de modules, les variantes de -M avec * peuvent être utiles ici.

DLLs_natives_manquantes

L'exécutable généré fonctionne bien sur la machine où il a été généré, mais il plante avec un message similaire au suivant lorsqu'il est exécuté sur une autre machine (qui n'a peut-être pas Perl installé).

Can't load 'C:\Users\myuser\AppData\Local\Temp\3\par-74686f6b65\temp-1772\inc\lib/auto/Net/SSLeay/SSLeay.dll' for module Net::SSLeay:
  load_file: The specified module could not be found at <embedded>/DynaLoader.pm line 206.
Compilation failed at <embedded>/PAR/Heavy.pm line 95.

Ici, la partie du module XS (Net::SSLeay) (.../auto/Net/SSLeay/SSLeay.dll) qui a la partie DLL (lib/ssl*.dll) a été compressée, mais elle est liée à une DLL native qui n'a pas été compressée. La DLL native est clairement présente sur la machine où elle a été compressée, mais pas sur l'autre machine. Notez que pp (ou plutôt Module::ScanDeps) ne détecte pas une telle dépendance non-Perl et ne compressera donc pas la DLL native ; vous devrez l'ajouter manuellement (en utilisant l'option --link).

TL;DR Utilisez pp_autolink de "App::PP::Autolink" pour automatiser la compression des DLL natives et en finir avec cela, ou lisez plus sur les détails concernant les oiseaux.

Inspecter .../auto/Net/SSLeay/SSLeay.dll (en utilisant des outils comme objdump) montre qu'il est lié aux DLL natives libssl*.dll et libcrypto*.dll. Ces DLL proviennent d'*OpenSSL*. Notez les * dans les noms ci-dessus, ils représentent des versions. Une fois que vous avez les noms exacts, vous pouvez ajouter ces DLL à la ligne de commande de pp avec "--link ...". Mais ce n'est pas fini : libcrypto*.dll est généralement lié à libz*.dll, vous devez donc ajouter "--link ..." pour celle-ci. Notez que cet exemple utilise le suffixe Windows ".dll", mais le problème existe aussi sous Linux ou macOS.

"Essayer_de_réinstaller..._aborté._Compilation_échouée_à_require..."

Plusieurs scénarios peuvent provoquer l'émission de "Essayer de réinstaller... aborté. Compilation échouée à require..." : c'est juste un indicateur qu'une précédente instruction "require" de quelque chose a échoué, mais l'erreur a été supprimée et ensuite quelque chose a été réactivé. La raison originale de l'erreur serait indiquée, mais ce n'est pas le cas.

Voici un exemple, foo.pl.

use strict;
use warnings;
use feature qw( say state );
eval {
    say "premier Foo";
    require Foo;
};
#say "échec de require : $@" if $@;   # <---
say "Text::ParseWords ...";
require Text::ParseWords;
say "deuxième Foo";
require Foo;

Maintenant, exécutez :

% echo "use Bar; 1;" > Foo.pm
% echo "use Quux; 1;" > Bar.pm
% perl -I. foo.pl
premier Foo
Text::ParseWords ...
deuxième Foo
Essayer de réinstaller Foo.pm aborté.
Compilation échouée à require dans foo.pl ligne 28.

Décommentez la ligne avec le pointeur pour voir la vraie raison : "Impossible de trouver Quux.pm dans @INC ... à Bar.pm ligne 1.", c'est-à-dire que Quux.pm est absent. Notez que le message original ne mentionne pas "Quux.pm".

Essayez maintenant ceci :

% echo "{" > Quux.pm        # oui, c'est une erreur de syntaxe
% perl -I. foo.pl 
premier Foo
Text::ParseWords ...
deuxième Foo
Essayer de réinstaller Foo.pm aborté.
Compilation échouée à require dans foo.pl ligne 28.

Résultat similaire au précédent. Encore une fois, décommentez la ligne avec le pointeur pour voir la vraie raison : "Crochet ou accolade manquant dans Quux.pm ligne 1 ... erreur de syntaxe dans Quux.pm ligne 1, fin.". Donc, Quux.pm existe, mais ne peut pas être chargé en raison d'une erreur de syntaxe. Il existe d'autres raisons pour lesquelles un module pourrait ne pas se charger, par exemple les "DLLs_natives_manquantes".

Voici une recette pour réduire le problème. Ajoutez ce qui suit avant la première instruction Perl de foo.pl :

BEGIN {
    my $required;
    unshift @INC, sub {
        (undef, $required) = @_;
        my (undef, $filename, $line) = caller();
        print STDERR "requiring $required from ${filename}:${line}\n";
        return;
    };
    push @INC, sub { print STDERR "MISSING $required\n"; return; };
}

Cela enregistre toute tentative de "require" de quelque chose, y compris le site appelant. Il ne peut pas enregistrer si le "require" a réussi ou l'erreur en cas d'échec. Mais si l'échec est juste un module manquant, il affichera "MISSING quelque chose".

Essayez maintenant les deux variantes à nouveau. Voici le cas de "MISSING quelque chose" (affiche uniquement "stderr") :

requiring strict.pm from foo.pl:14
requiring warnings.pm from foo.pl:15
requiring feature.pm from foo.pl:16
requiring Foo.pm from foo.pl:22
requiring Bar.pm from Foo.pm:1
requiring Quux.pm from Bar.pm:1
MISSING Quux.pm
requiring Text/ParseWords.pm from foo.pl:27
requiring Exporter.pm from /usr/lib/x86_64-linux-gnu/perl-base/Text/ParseWords.pm:8
Essayer de réinstaller Foo.pm aborté.
Compilation échouée à require dans foo.pl ligne 28.

et le cas de "ne peut pas charger" :

requiring strict.pm from foo.pl:14
requiring warnings.pm from foo.pl:15
requiring feature.pm from foo.pl:16
requiring Foo.pm from foo.pl:22
requiring Bar.pm from Foo.pm:1
requiring Quux.pm from Bar.pm:1
requiring Text/ParseWords.pm from foo.pl:27
requiring Exporter.pm from /usr/lib/x86_64-linux-gnu/perl-base/Text/ParseWords.pm:8
Essayer de réinstaller Foo.pm aborté.
Compilation échouée à require dans foo.pl ligne 28.

La stratégie pour trouver la cause de "Essayer de réinstaller quelque chose" est la suivante :

  • Trouvez la première occurrence de "requiring quelque chose" dans la sortie.
  • Avancez dans la chaîne d'appels de "require" imbriqués, en restant "sous" quelque chose. Le coupable est généralement le dernier module mentionné dans une ligne de "requiring ... from ...".
  • Si la ligne suivante est "MISSING quelque chose", alors c'est un cas de "Modules_manquants" avec quelque chose comme coupable. Sinon, c'est une erreur de chargement, probablement "DLLs_natives_manquantes".

Dans l'exemple ci-dessus, la chaîne d'appels est :

foo.pl -> Foo.pm -> Bar.pm -> Quux.pm

(Text/ParseWords.pm est "require" de foo.pl, donc "au-dessus" est Foo.pm). Cela impliquerait Quux.pm. Notez que la chaîne d'appels n'a pas besoin d'être régulière, ce n'est que le cas si tous les "require" proviennent de "use" qui sont exécutés au moment de la compilation. L'image peut être faussée si des "require" sont utilisés au moment de l'exécution.
