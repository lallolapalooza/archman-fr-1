PPIx::Regexp(3) Documentation Perl fournie par l'utilisateur PPIx::Regexp(3)

NOM

PPIx::Regexp - Représenter une expression régulière quelconque

SYNOPSIS

use PPIx::Regexp;
use PPIx::Regexp::Dumper;
my $re = PPIx::Regexp->new( 'qr{foo}smx' );
PPIx::Regexp::Dumper->new( $re )
    ->print();

AVIS DE DÉPRÉCATION

L'argument "postderef" pour new() est retiré, et les déréférencements postfixes seront toujours reconnus.

À partir de la version 0.074_01, la première utilisation de cet argument a provoqué un avertissement. Avec la version 0.079_01, toutes les utilisations ont provoqué un avertissement. Avec la version 0.080_01, toutes les utilisations sont devenues fatales. Avec la version 0.084_01, toute mention de cet argument a été supprimée, à l'exception de cet avis.

HÉRITAGE

"PPIx::Regexp" est un PPIx::Regexp::Node.

"PPIx::Regexp" n'a pas de descendants.

DESCRIPTION

Le but du paquetage PPIx-Regexp est d'analyser les expressions régulières d'une manière similaire à la façon dont le paquetage PPI analyse Perl. Cette classe forme la racine de l'arbre d'analyse, jouant un rôle similaire à celui de PPI::Document.

Ce paquetage partage avec PPI la propriété d'être sûr pour l'aller-retour. C'est-à-dire,

my $expr = 's/ ( \d+ ) ( \D+ ) /$2$1/smxg';
my $re = PPIx::Regexp->new( $expr );
print $re->content() eq $expr ? "yes\n" : "no\n"

devrait imprimer 'yes' pour toute expression régulière valide.

La navigation est similaire à celle fournie par PPI. C'est-à-dire que des choses comme "children", "find_first", "next_sibling" et ainsi de suite fonctionnent à peu près de la même manière qu'en PPI.

La hiérarchie des classes est également similaire à PPI. À l'exception de certaines classes utilitaires (le dumper, le lexer et le tokenizer), toutes les classes descendent de PPIx::Regexp::Element, qui fournit la navigation de base. Les jetons descendent de PPIx::Regexp::Token, qui fournit le contenu. Tous les conteneurs descendent de PPIx::Regexp::Node, qui fournit des enfants, et tous les éléments structurels descendent de PPIx::Regexp::Structure, qui fournit des délimiteurs de début et de fin, et un type.

Il existe deux fonctionnalités de PPI que ce paquetage ne fournit pas : la mutabilité et la surcharge d'opérateurs. Il n'y a pas de projets de mutabilité sérieuse, bien que quelque chose comme la fonctionnalité "prune" de PPI puisse être envisagée. De même, il n'y a pas de projets de surcharge d'opérateurs, ce qui représente pour l'auteur un impact sur les performances pour un gain tangible minime.

AVIS

L'auteur tentera de préserver l'interface documentée, mais si l'interface doit changer pour corriger une décision de conception ou une implémentation manifestement mauvaise, alors elle changera. Tout changement incompatible passera par un cycle de dépréciation.

L'objectif de ce paquetage est d'analyser correctement les expressions régulières bien formées. Un objectif secondaire est de ne pas planter sur des expressions régulières mal formées. L'identification et la caractérisation correctes des expressions régulières mal formées ne sont pas un objectif de ce paquetage, pas plus que l'analyse cohérente des expressions régulières mal formées d'une version à l'autre.

Cette politique tente de suivre les fonctionnalités des versions de développement ainsi que des versions publiques. Cependant, les fonctionnalités ajoutées dans une version de développement puis supprimées avant la prochaine version de production ne seront pas suivies, et toute fonctionnalité liée à de telles fonctionnalités sera supprimée. Le problème ici est la réutilisation potentielle (avec une sémantique différente) de syntaxes qui n'ont pas été intégrées dans la version de production.

De temps en temps, le moteur d'expressions régulières de Perl change d'une manière qui modifie l'analyse d'une expression régulière donnée. Lorsque ces changements se produisent, "PPIx::Regexp" sera modifié pour produire l'analyse plus moderne. Les exemples connus incluent :

Le $ ne s'interpole plus à partir de Perl 5.005, selon "perl5005delta".
Les versions plus récentes de Perl semblent analyser ceci comme "qr{$}" (c'est-à-dire une assertion de fin de chaîne ou de nouvelle ligne) suivie d'une parenthèse ouvrante, et c'est ce que fait "PPIx::Regexp".
$) et $| semblent également être analysés comme l'assertion "$"
suivie du métacaractère pertinent, bien que je n'aie pas de référence documentaire pour cela.
"@+" et "@-" ne s'interpollent plus à partir de Perl 5.9.4
selon "perl594delta". Les versions ultérieures de Perl traitent "@+" comme un littéral quantifié et "@-" comme deux littéraux, et c'est ce que fait "PPIx::Regexp". Notez que les références indexées à ces tableaux s'interpollent bien, et sont donc analysées par "PPIx::Regexp".
Seulement l'espace et la tabulation horizontale sont des espaces blancs à partir de Perl 5.23.4
à l'intérieur d'une classe de caractères entre crochets à l'intérieur d'une classe de caractères étendue entre crochets, selon "perl5234delta". Auparavant, tout caractère d'espacement était analysé comme un espace blanc. Cette modification dans "PPIx::Regexp" sera revertie si la modification dans Perl n'est pas intégrée dans Perl 5.24.0.
Les crochets gauches littéraux non échappés
Ils sont supprimés dans les positions où les quantificateurs sont légaux, afin qu'ils puissent être utilisés pour de nouvelles fonctionnalités. Certains d'entre eux ont disparu dans 5.25.1, d'autres seront supprimés dans une future version de Perl. Dans les situations où ils ont été supprimés, perl_version_removed() renverra la version dans laquelle ils ont été supprimés. Lorsque la nouvelle fonctionnalité apparaîtra, l'analyse produite par ce logiciel reflétera la nouvelle fonctionnalité.

NOTE que la situation avec un crochet gauche littéral après un caractère littéral est compliquée. Elle est devenue une erreur dans Perl 5.25.1, et est restée ainsi dans toutes les versions 5.26, mais est redevenue un avertissement dans 5.27.1 en raison de son utilisation dans GNU Autoconf. Qu'elle redevienne un jour illégale ne m'est pas clair sur la base du contenu de perl5271delta. Pour le moment, perl_version_removed() renvoie "undef", mais évidemment ce n'est pas toute l'histoire, et les méthodes accepts_perl() et requirements_for_perl() ont été introduites pour gérer cette complication.

"\o{...}"
est analysé comme l'équivalent octal de "\x{...}". C'est son sens à partir de perl 5.13.2. Avant 5.13.2, c'était simplement le littéral 'o' et ainsi de suite.
"x{,3}"
(avec le premier compte omis) est autorisé comme quantificateur à partir de Perl 5.33.6. L'analyse précédente en faisait des littéraux.
"x{ 0 , 3 }"
(avec des espaces à l'intérieur mais adjacents aux accolades, ou autour de la virgule le cas échéant) est autorisé comme quantificateur à partir de Perl 5.33.6. L'analyse précédente en faisait des littéraux.

Il existe très probablement d'autres exemples de cela. Lorsqu'ils seront connus, il sera documenté qu'ils produisent l'analyse moderne, et le code sera modifié pour produire cette analyse si nécessaire.

MÉTHODES

Cette classe fournit les méthodes publiques suivantes. Les méthodes non documentées ici sont privées et non prises en charge dans le sens où l'auteur se réserve le droit de les modifier ou de les supprimer sans préavis.

new

my $re = PPIx::Regexp->new('/foo/');

Cette méthode instancie un objet "PPIx::Regexp" à partir d'une chaîne, d'un PPI::Token::QuoteLike::Regexp, d'un PPI::Token::Regexp::Match, ou d'un PPI::Token::Regexp::Substitute. Honnêtement, tout PPI::Element fonctionnera, mais seules les trois classes Regexp mentionnées précédemment feront probablement quelque chose d'utile.

Quelle que soit la forme de l'argument, il est supposé consister entièrement en une chaîne de correspondance, de substitution ou de "qr<>" valide.

Optionnellement, vous pouvez passer une ou plusieurs paires nom/valeur après l'expression régulière. Les options possibles sont :

NOM

PPIx::Regexp - analyse les expressions régulières Perl

SYNOPSIS

  use PPIx::Regexp;

  # Créer un objet PPIx::Regexp à partir d'une chaîne de caractères
  my $re = PPIx::Regexp->new( 'm/(foo)/x' );

  # Créer un objet PPIx::Regexp à partir d'un élément PPI
  my $element = ... ; # Un élément PPI, par exemple un appel de méthode
  my $re = PPIx::Regexp->new( $element );

  # Créer un objet PPIx::Regexp à partir d'un fichier
  my $doc = PPI::Document->new( $path );
  my @res = PPIx::Regexp->extract_regexps( $doc );

  # Récupérer le contenu de l'expression régulière
  print $re->content(), "\n";

  # Récupérer les noms des captures
  foreach my $name ( $re->capture_names() ) {
      print "Capture name '$name'\n";
  }

  # Récupérer les délimiteurs
  my ( $re_delim, $sub_delim ) = $re->delimiters();

  # Récupérer les échecs d'analyse
  print "Parse failures: ", $re->failures(), "\n";

  # Récupérer le numéro de capture maximal
  print "Max capture number: ", $re->max_capture_number(), "\n";

  # Récupérer les modificateurs
  print $re->modifier()->content(), "\n";

  # Récupérer l'élément source original
  my $source_element = $re->source();

  # Récupérer l'objet d'expression régulière interne
  my $internal_re = $re->regular_expression();

DESCRIPTION

La classe PPIx::Regexp est une sous-classe de PPI::Element qui représente une expression régulière Perl. Elle fournit une interface pour accéder aux différentes parties d'une expression régulière, comme les délimiteurs, les captures, les modificateurs, etc.

Elle utilise le module PPIx::Regexp::Tokenizer pour analyser la chaîne de caractères de l'expression régulière et la transformer en une structure de données analysable.

new

  my $re = PPIx::Regexp->new( $string_or_element, \%options );
  my $re = PPIx::Regexp->new( $string_or_element, $option_name => $option_value, ... );

Constructeur de la classe PPIx::Regexp. Il prend comme premier argument soit une chaîne de caractères représentant une expression régulière Perl, soit un objet PPI::Element qui contient l'expression régulière. Il peut également prendre des options pour affiner l'analyse.

Options

default_modifiers array_reference
Cette option spécifie une référence à un tableau de modificateurs par défaut à appliquer à l'expression régulière en cours d'analyse. Chaque modificateur est spécifié sous forme de chaîne de caractères. Tous les modificateurs réels trouvés remplacent les valeurs par défaut.

Lors de l'application des valeurs par défaut, '?' et '/' sont complètement ignorés, et '^' est ignoré sauf s'il apparaît au début du modificateur. Le premier trait d'union ('-') entraîne la négation des modificateurs subsquents.

Ainsi, par exemple, si vous souhaitez produire un objet "PPIx::Regexp" représentant l'expression régulière dans

use re '/smx';
{
   no re '/x';
   m/ foo /;
}

vous feriez (après un peu d'aide de PPI pour trouver les instructions pertinentes), quelque chose comme

my $re = PPIx::Regexp->new( 'm/ foo /',
    default_modifiers => [ '/smx', '-/x' ] );
encoding name
Cette option spécifie l'encodage de l'expression régulière. Ceci est passé au tokenizer, qui va "décoder" la chaîne de l'expression régulière avant de la tokeniser. Par exemple : 
my $re = PPIx::Regexp->new( '/foo/',
    encoding => 'iso-8859-1',
);
index_locations Boolean
Cette option booléenne spécifie si les emplacements des éléments dans l'expression régulière doivent être indexés.

Si elle n'est pas spécifiée ou si elle est spécifiée comme "undef", une valeur par défaut est utilisée. Cette valeur par défaut est vraie si l'argument est un PPI::Element ou si l'option "location" a été spécifiée. Sinon, la valeur par défaut est fausse.

location array_reference
Cette option spécifie l'emplacement du nouvel objet dans le document d'où il a été créé. C'est une référence à un tableau de cinq éléments compatible avec celui retourné par la méthode location() de PPI::Element.

Si elle n'est pas spécifiée, l'emplacement de la chaîne originale est utilisé si elle a été spécifiée comme un PPI::Element.

Si aucun emplacement ne peut être déterminé, les différentes méthodes location() retourneront "undef".

postderef Boolean
CET ARGUMENT EST DÉPRÉCIÉ. Voir la NOTICE DE DÉPRÉCIATION ci-dessus pour les détails.

Cette option est transmise au tokenizer, où elle spécifie si les déréférences postfixées sont reconnues dans les interpolations et le code. Cette fonctionnalité expérimentale a été introduite dans Perl 5.19.5.

À partir de la version 0.074_01, la valeur par défaut est vraie. Jusqu'à la version 0.074, la valeur par défaut était celle de $PPIx::Regexp::Tokenizer::DEFAULT_POSTDEREF, qui était vraie. Lors de son introduction initiale, elle était fausse, mais il était documenté qu'elle deviendrait vraie lorsque la déréférence postfixée deviendrait courante. L'intention de la rendre courante a été annoncée avec Perl 5.23.1, et est devenue officielle (pour ainsi dire) avec Perl 5.24.0, donc la valeur par défaut est devenue vraie avec PPIx::Regexp 0.049_01.

Notez que si PPI commence à reconnaître inconditionnellement les déréférences postfixées, cet argument sera immédiatement ignoré, et subira un cycle de dépréciation puis sera supprimé.

strict Boolean
Cette option est transmise au tokenizer et au lexer, où elle spécifie si l'analyse doit supposer que "use re 'strict'" est en vigueur.

Le pragma 'strict' a été introduit dans Perl 5.22, et sa documentation indique qu'il est expérimental et qu'il n'y a aucun engagement de compatibilité ascendante. Il en va de même pour l'analyse produite lorsque cette option est activée. De plus, la mise en garde habituelle s'applique : si "use re 'strict'" finit par être rétracté, cette option et toute la fonctionnalité associée le seront également.

Compte tenu de la nature de "use re 'strict'", vous devriez vous attendre à ce que si vous activez cette option, des expressions régulières qui s'analysaient auparavant sans erreur puissent ne plus le faire. Si un élément finit par être déclaré erroné parce que cette option est définie, sa perl_version_introduced() sera la version de Perl à laquelle "use re 'strict'" a commencé à rejeter ces éléments.

La valeur par défaut est fausse.

trace number
Si supérieur à zéro, cette option provoque une sortie de trace de l'analyse. L'auteur se réserve le droit de modifier ou d'éliminer ceci sans préavis.

Passer des entrées optionnelles autres que celles ci-dessus n'est pas une erreur, mais ce n'est pas non plus supporté.

new_from_cache

  my $re = PPIx::Regexp->new_from_cache( $element );

Cette méthode statique encapsule "new" dans un mécanisme de mise en cache. Un seul objet sera généré pour un PPI::Element donné, quelle que soit la fréquence à laquelle cette méthode est appelée. Les appels après le premier pour un PPI::Element donné retournent simplement le même objet "PPIx::Regexp".

Lorsque l'objet "PPIx::Regexp" est retourné depuis le cache, les valeurs des arguments optionnels sont ignorées.

Les appels à cette méthode avec l'expression régulière sous forme de chaîne de caractères plutôt que de PPI::Element ne seront pas mis en cache.

Avertissement : Cette méthode est fournie pour du code comme Perl::Critic qui pourrait instancier le même objet plusieurs fois. Le cache persistera jusqu'à ce que "flush_cache" soit appelé.

flush_cache

  $re->flush_cache();            # Supprimer $re du cache
  PPIx::Regexp->flush_cache();   # Vider le cache

Cette méthode vide le cache utilisé par "new_from_cache". Si elle est appelée comme méthode statique sans arguments, le cache entier est vidé. Sinon, tous les objets spécifiés sont supprimés du cache.

capture_names

  foreach my $name ( $re->capture_names() ) {
      print "Capture name '$name'\n";
  }

Cette méthode de commodité retourne les noms des captures trouvés dans l'expression régulière.

Cette méthode est équivalente à

  $self->regular_expression()->capture_names();

sauf que si "$self->regular_expression()" retourne "undef" (signifiant que quelque chose s'est terriblement mal passé avec l'analyse), cette méthode retournera simplement une liste vide.

content

  my $content = $re->content();

Retourne la chaîne de caractères de l'expression régulière originale.

delimiters

  print join("\t", PPIx::Regexp->new('s/foo/bar/')->delimiters());
  # Affiche '//	//'

Lorsqu'elle est appelée en contexte de liste, cette méthode retourne soit une, soit deux chaînes, selon que l'expression analysée a une chaîne de remplacement. Dans le cas de substitutions non entourées d'accolades, le délimiteur de début de la chaîne de remplacement est considéré comme étant le même que son délimiteur de fin, comme l'illustre l'exemple ci-dessus.

Lorsqu'elle est appelée en contexte scalaire, vous obtenez les délimiteurs de l'expression régulière ; c'est-à-dire l'élément 0 du tableau qui est retourné en contexte de liste.

Optionnellement, vous pouvez passer un indice et les délimiteurs correspondants seront retournés ; l'indice 0 représente les délimiteurs de l'expression régulière, et l'indice 1 représente les délimiteurs de la chaîne de remplacement, qui peut être undef. Par exemple,

  print PPIx::Regexp->new('s{foo}<bar>')->delimiters(1);
  # Affiche '<>'

Si l'objet n'a pas été initialisé avec une regexp valide d'une sorte ou d'une autre, les résultats de cette méthode sont indéfinis.

errstr

Cette méthode statique retourne la chaîne d'erreur de la tentative la plus récente d'instanciation d'une "PPIx::Regexp". Elle sera "undef" si la tentative la plus récente a réussi.

extract_regexps

  my $doc = PPI::Document->new( $path );
  $doc->index_locations();
  my @res = PPIx::Regexp->extract_regexps( $doc )

Cette méthode statique de commodité (enfin, plus ou moins) prend comme argument un objet PPI::Document et retourne des objets "PPIx::Regexp" correspondant à toutes les expressions régulières trouvées dans celui-ci, dans l'ordre où elles apparaissent dans le document. Vous devrez conserver une référence à l'objet PPI::Document original si vous souhaitez pouvoir récupérer les objets PPI::Element originaux via la méthode source() de PPIx::Regexp.

failures

  print "There were ", $re->failures(), " parse failures\n";

Cette méthode retourne le nombre d'échecs d'analyse. C'est un compte du nombre de jetons inconnus plus le nombre de structures non terminées plus le nombre de crochets droits non appariés de quelque sorte que ce soit.

max_capture_number

  print "Highest used capture number ",
      $re->max_capture_number(), "\n";

Cette méthode de commodité retourne le numéro de capture le plus élevé utilisé par l'expression régulière. S'il n'y a pas de captures, le retour sera 0.

Cette méthode est équivalente à

  $self->regular_expression()->max_capture_number();

sauf que si "$self->regular_expression()" retourne "undef" (signifiant que quelque chose s'est terriblement mal passé avec l'analyse), cette méthode le fera aussi.

modifier

  my $re = PPIx::Regexp->new( 's/(foo)/${1}bar/smx' );
  print $re->modifier()->content(), "\n";
  # Affiche 'smx'.

Cette méthode récupère le modificateur de l'objet. Il provient de la fin de la chaîne ou de l'objet d'initialisation et sera un PPIx::Regexp::Token::Modifier.

Note que cet objet représente les modificateurs réels présents sur la regexp, et ne prend pas en compte ceux qui ont pu être appliqués par défaut (c'est-à-dire via l'option "

modifiers

  my @modifiers = $re->modifiers();
  my $modifier_obj = $re->modifiers( 's' );

Lorsqu'elle est appelée sans arguments, cette méthode retourne un tableau de tous les objets PPIx::Regexp::Token::Modifier correspondant aux modificateurs présents dans l'expression régulière.

Si un argument est passé, il doit s'agir d'une chaîne de caractères représentant un modificateur. La méthode retournera le premier objet PPIx::Regexp::Token::Modifier correspondant, ou undef s'il n'est pas trouvé.

quote_context

  my $context = $re->quote_context();

Retourne le contexte de citation de l'expression régulière. Il peut s'agir de "normal", "interpolated", ou "none".

regular_expression

  my $internal_re = $re->regular_expression();

Retourne l'objet d'expression régulière interne (un objet Regexp::Parse::Grammar::Regex) qui a été utilisé pour analyser l'expression régulière. Ceci est principalement utile pour accéder aux fonctionnalités fournies par Regexp::Parse elle-même.

Si l'analyse a échoué pour une raison quelconque, cette méthode retournera "undef".

source

  my $element = $re->source();

Retourne l'élément source original à partir duquel l'objet PPIx::Regexp a été créé. Cela peut être une chaîne de caractères ou un objet PPI::Element.

TO_STRING

  print $re->string(), "\n";

Méthode de conversion en chaîne de caractères. Retourne la chaîne de caractères de l'expression régulière.

default_modifiers

my $re = PPIx::Regexp->new( '/ . /',
    default_modifiers => [ 'smx' ] );
print $re->modifier_asserted( 'x' ) ? "yes\n" : "no\n";

Cette méthode renvoie true si le modificateur donné est affirmé pour l'expression régulière, soit explicitement, soit par les modificateurs passés dans l'argument "default_modifiers".

Depuis la version 0.036_01, si l'argument est un modificateur d'un seul caractère suivi d'un astérisque (censé être un caractère joker), le retour est le nombre de fois que ce modificateur apparaît. Dans ce cas, une exception sera lancée si un modificateur multi-caractères (par exemple, 'ee*'') est spécifié, ou si l'un des modes de sémantique de correspondance (par exemple, 'a*'') est spécifié.

modifier_asserted

my $re = PPIx::Regexp->new( 's/(foo)/${1}bar/smx' );
print $re->modifier_asserted( 'x' ) ? "yes\n" : "no\n";
# prints 'yes'.

Cette méthode renvoie true si le modificateur donné est affirmé pour l'expression régulière, soit explicitement, soit par les modificateurs passés dans l'argument "default_modifiers".

Depuis la version 0.036_01, si l'argument est un modificateur d'un seul caractère suivi d'un astérisque (censé être un caractère joker), le retour est le nombre de fois que ce modificateur apparaît. Dans ce cas, une exception sera lancée si un modificateur multi-caractères (par exemple, 'ee*'') est spécifié, ou si l'un des modes de sémantique de correspondance (par exemple, 'a*'') est spécifié.

regular_expression

my $re = PPIx::Regexp->new( 's/(foo)/${1}bar/smx' );
print $re->regular_expression()->content(), "\n";
# prints '/(foo)/'.

Cette méthode renvoie la partie de l'objet qui représente réellement une expression régulière.

replacement

my $re = PPIx::Regexp->new( 's/(foo)/${1}bar/smx' );
print $re->replacement()->content(), "\n";
# prints '${1}bar/'.

Cette méthode renvoie la partie de l'objet qui représente la chaîne de remplacement. Ce sera "undef" sauf si l'expression régulière a une chaîne de remplacement. Les délimiteurs seront inclus, mais il n'y aura pas de délimiteur de début, à moins que l'expression régulière ne soit délimitée.

source

my $source = $re->source();

Cette méthode renvoie l'objet ou la chaîne qui a été utilisé pour instancier l'objet.

type

my $re = PPIx::Regexp->new( 's/(foo)/${1}bar/smx' );
print $re->type()->content(), "\n";
# prints 's'.

Cette méthode renvoie le type de l'objet. Ceci provient du début de la chaîne ou de l'objet utilisé pour instancier l'objet, et sera un PPIx::Regexp::Token::Structure dont le "content" est l'un de 's', 'm', 'qr' ou ''.

RESTRICTIONS

Compte tenu de la nature de ce module, il ne sera jamais capable de faire les choses correctement. De nombreux domaines de problèmes connus impliquent des interpolations d'une manière ou d'une autre.

Ambiguous Syntax

Les expressions régulières Perl contiennent des cas où la syntaxe est ambiguë. Un exemple particulièrement grave est une interpolation suivie de crochets de type carré ou de type cercle, par exemple $foo[...]. Il n'y a rien dans la syntaxe pour dire si le programmeur voulait interpoler un élément de la liste @foo, ou s'il voulait interpoler un scalaire $foo, puis continuer avec une classe de caractères.

Le document perlop note qu'en ce cas, ce que Perl fait est de deviner. C'est-à-dire qu'il utilise diverses heuristiques dans le code pour tenter de déterminer ce que le programmeur voulait. Ces heuristiques sont documentées comme non documentées (!) et peuvent être modifiées sans préavis. Comme exemple des problèmes rencontrés même par perl lors de l'analyse de Perl, voir https://github.com/perl/perl5/issues/16478).

Étant donné cette situation, les chances que ce module reproduise l'interprétation de chaque expression régulière de chaque version de Perl sont pratiquement nulles. Ce qu'il fait actuellement est de supposer que les crochets dans un texte contenant uniquement un nombre entier ou une interpolation représentent un indice ; sinon, ils représentent une classe de caractères. De même, les crochets dont le contenu est uniquement un mot-clé ou une interpolation représentent un indice ; sinon, une quantification.

Changes in Syntax

Parfois, l'introduction de nouveaux changements de syntaxe modifie la façon dont une expression régulière est analysée. Par exemple, le caractère "\v" a été introduit dans Perl 5.9.5. Cependant, il ne représentait pas une erreur de syntaxe avant cette version, il était simplement analysé comme "v". Donc

$ perl -le 'print "v" =~ m/\v/ ? "yes" : "no"'

affiche "yes" sous Perl 5.8.9, mais "no" sous 5.10.0. "PPIx::Regexp" suppose généralement l'analyse la plus moderne dans de tels cas.

Equivocation

Parfois, une construction est supprimée puis réintroduite. Dans ce cas, le plan est que perl_version_introduced() renvoie la version la plus ancienne où la construction est apparue, et perl_version_removed() renvoie la version après la dernière où elle est apparue (qu'elle ait été en production ou en développement), ou "undef" si elle est dans la version la plus élevée de Perl.

Les constructions impliquées dans ce cas sont :

Un crochet gauche non échappé après un crochet droit littéral

C'est-à-dire, quelque chose comme "qr<x{>".

Cela a été considéré comme une erreur en 5.25.1, et était une erreur en 5.26.0. Mais cela est redevenu un avertissement en 5.27.1. Le perl5271delta dit qu'il a été réintégré car les changements ont cassé GNU Autoconf, et le message d'avertissement dit qu'il sera supprimé dans Perl 5.30.

Par conséquent, perl_version_introduced() renvoie 5.0. Maintenant, perl_version_removed() renvoie '5.025001'. Mais s'il est présent avec ou sans avertissement en 5.28, perl_version_removed() deviendra "undef". Si vous avez besoin d'une résolution plus précise que cela, consultez les méthodes accepts_perl() et requirements_for_perl() des classes PPIx::Regexp::Element.

Static Parsing

Il est bien connu que Perl ne peut pas être analysé statiquement. C'est-à-dire que vous ne pouvez pas analyser complètement un morceau de code Perl sans exécuter ce code lui-même.

Cependant, cette classe tente d'analyser les expressions régulières statiquement. La principale difficulté est qu'il n'y a aucun moyen de savoir ce qui est interpolé dans l'expression régulière par une variable interpolée. C'est un problème car la valeur interpolée peut changer l'interprétation des éléments voisins.

Ce module traite de ce problème en faisant des hypothèses sur le contenu d'une variable interpolée. Ces hypothèses ne sont pas énumérées ici, mais en général, le principe est de supposer que la valeur interpolée ne change pas l'interprétation de l'expression régulière. Par exemple,

my $foo = 'a-z]';
my $re = qr{[$foo};

est accepté par l'interpréteur Perl, mais confond le module dans ce cas. Similairement et plus utilement, quelque chose comme

my $mods = 'i';
my $re = qr{(?$mods:foo)};

ou peut-être

my $mods = 'i';
my $re = qr{(?$mods)$foo};

définit probablement un modificateur d'une sorte, et c'est ainsi que ce module l'interprète. Si l'interpolation ne concerne pas les modificateurs, ce module l'interprétera incorrectement. Un autre exemple semi-bénin est

my $foo = $] >= 5.010 ? '?<foo>' : '';
my $re = qr{($foo\w+)};

qui est analysé, mais ce module ne reconnaîtra jamais qu'il pourrait s'agir d'une capture nommée.

Non-Standard Syntax

Il existe des modules extérieurs qui altèrent la syntaxe de Perl. Si la syntaxe d'une expression régulière est altérée, ce module ne peut pas comprendre qu'elle a été altérée, ni s'adapter à l'altération. Les modules suivants sont connus pour causer des problèmes :

Acme::PerlML, qui rend Perl en XML.

"Data::PostfixDeref", qui fait que Perl interprète les crochets suffixés comme une déréférencement de ce qui les suit. Ce module, par Ben Morrow ("BMORROW"), semble avoir été retiré.

Filter::Trigraph, qui reconnaît les trigraphes ANSI C, permettant d'écrire Perl dans le jeu de caractères ISO 646.

Perl6::Pugs. C'est dit.

Perl6::Rules, qui réimporte une partie de la syntaxe des expressions régulières de Perl 6 vers Perl 5.

Regexp::Extended, qui étend les expressions régulières de plusieurs manières, dont certaines semblent être en conflit avec Perl 5.010.

SEE ALSO

Regexp::Parsertron, qui utilise Marpa::R2 pour analyser l'expression régulière, et Tree pour naviguer. Contrairement à "PPIx::Regexp|PPIx::Regexp", Regexp::Parsertron prend en charge la modification de l'arbre d'analyse.

Regexp::Parser, qui analyse une expression régulière de base (sans envol "qr{}", "m//", ou autre) et utilise un modèle de navigation différent. Après une longue pause, ce module a été adopté et le support est en cours de refonte.

YAPE::Regex, qui fournit l'arbre d'analyse et possède un mécanisme d'héritage des classes d'éléments pour la personnalisation. La dernière version date de 2011, mais les résultats des tests CPAN sont tous au vert. Le module compagnon YAPE::Regex::Explain explique ce que fait chaque partie d'une expression régulière, bien que les constructions ajoutées dans perl 5.10 et ultérieures ne soient pas prises en charge. Je ne sais pas comment j'ai manqué cette information lors de la recherche initiale de parsers d'"Regexp".

PPR, qui reconnaît Perl de tous types, y compris les expressions régulières, mais ne fournit pas d'analyse réelle des constructions reconnues.
