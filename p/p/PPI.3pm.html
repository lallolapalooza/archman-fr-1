PPI(3) Documentation Perl Contribuée par l'Utilisateur PPI(3)

NOM

PPI - Analyse, Syntaxe et Manipulation de Perl (sans perl)

SYNTAXE

use PPI;

# Crée un nouveau document vide
my $Document = PPI::Document->new;

# Crée un document à partir d'une source
$Document = PPI::Document->new(\'print "Bonjour le monde!\n"');

# Charge un Document depuis un fichier
$Document = PPI::Document->new('Module.pm');

# Contient-il du POD ?
if ( $Document->find_any('PPI::Token::Pod') ) {
    print "Le module contient du POD\n";
}

# Obtient le nom du paquet principal
$pkg = $Document->find_first('PPI::Statement::Package')->namespace;

# Supprime toute cette documentation inutile
$Document->prune('PPI::Token::Pod');
$Document->prune('PPI::Token::Comment');

# Sauvegarde le fichier
$Document->save('Module.pm.stripped');

DESCRIPTION

À propos de ce Document

Ceci est le manuel de PPI. Il décrit sa raison d'être, sa structure générale, son utilisation, un aperçu de son API, et fournit quelques exemples d'implémentation.

Contexte

La capacité de lire et de manipuler Perl (le langage) de manière programmatique, autre qu'avec perl (l'application), a longtemps posé difficulté.

La cause de ce problème résidait dans la grammaire complexe et dynamique de Perl. Bien qu'il n'y ait généralement pas une énorme diversité dans la grammaire de la plupart des codes Perl, certains problèmes causent de gros problèmes lorsqu'il s'agit d'analyser.

En effet, très tôt dans l'histoire de Perl, Tom Christiansen a introduit dans la communauté Perl la citation "Rien d'autre que Perl ne peut analyser Perl", ou comme on le dit plus souvent maintenant comme une vérité première :

"Seul Perl peut analyser Perl"

Un exemple des types de choses qui empêchent Perl d'être facilement analysé est celui des signatures de fonctions, comme démontré par ce qui suit.

@result = (dothis $foo, $bar);

# À quoi cela équivaut-il ?
@result = (dothis($foo), $bar);
@result = dothis($foo, $bar);

La première ligne ci-dessus peut être interprétée de deux manières différentes, selon que la fonction &dothis attend un argument, deux, ou plusieurs.

Un "analyseur de code" (quelque chose qui analyse dans le but d'exécution) tel que perl a besoin d'informations qui ne se trouvent pas à proximité immédiate de l'instruction analysée.

L'information peut ne pas se trouver ailleurs dans le fichier, elle peut même ne pas être dans le même fichier du tout. Il se peut aussi qu'il ne soit pas possible de déterminer cette information sans l'exécution préalable d'un bloc "BEGIN {}", ou le chargement et l'exécution d'un ou plusieurs modules externes. Ou pire, la fonction &dothis peut même ne pas avoir encore été écrite.

Lors de l'analyse de Perl en tant que code, vous devez également l'exécuter.

Même perl lui-même ne comprend jamais vraiment la structure du code source après et même pendant qu'il le traite, et en ce sens ne "parse" pas le code source Perl en quelque chose de remotement ressemblant à un document structuré. Cela le rend inutile pour toute tâche qui consiste à traiter le code source comme un document, et ce de manière fiable et robuste.

Pour plus d'informations sur les raisons pour lesquelles il est impossible d'analyser Perl, consultez la réponse séminale de Randal Schwartz à la question "Pourquoi ne pouvez-vous pas analyser Perl".

http://www.perlmonks.org/index.pl?node_id=44722

Le but de PPI n'est pas d'analyser du code Perl, mais des documents Perl. En traitant le problème de cette manière, nous sommes capables d'analyser un fichier unique contenant du code source Perl "isolé" de toute autre ressource, telle que les bibliothèques dont le code peut dépendre, et sans avoir besoin d'exécuter une instance de perl à côté ou à l'intérieur de l'analyseur.

Historiquement, l'utilisation d'un analyseur perl intégré était largement considérée comme la voie la plus probable pour trouver une solution à l'analyse de Perl. Elle a été étudiée de temps en temps, mais les tentatives ont généralement échoué ou ont souffert de cas limites suffisamment mauvais pour qu'elles soient abandonnées.

Que signifie PPI ?

"PPI" est un acronyme du nom de module original plus long "Parse::Perl::Isolated". Et dans l'esprit des jeux d'acronymes idiots joués par certains projets Open Source sans nom dont vous avez peut-être entendu parler, c'est aussi un rétroacronyme de "I Parse Perl".

Bien sûr, je pourrais simplement mentir et avoir inventé cette seconde partie 10 minutes avant la sortie de PPI 1.000. D'ailleurs, tous les paquets Perl cool ont des TLAs (Three Letter Acronyms - Acronymes de Trois Lettres). C'est une règle ou quelque chose comme ça.

Pourquoi ne pas simplement y penser comme à l'Interface d'Analyse Perl pour simplifier.

Le nom original a été raccourci pour éviter à l'auteur (et à vous, les utilisateurs) de contracter des TMS (Troubles Musculo-Squelettiques) en ayant à taper des choses folles comme "Parse::Perl::Isolated::Token::QuoteLike::Backtick" 100 fois par jour.

En reconnaissance du fait que quelqu'un pourrait un jour trouver une solution valide au problème de la grammaire, il a été décidé au début du projet de laisser l'espace de noms "Parse::Perl" libre pour tout effort de ce type.

Depuis lors, j'ai pu prouver à ma propre satisfaction qu'il est vraiment impossible d'analyser précisément Perl à la fois comme code et comme document. Pour les universitaires, l'analyse de Perl souffre du "Problème de l'Arrêt".

Pourquoi analyser Perl ?

Une fois que l'on peut accepter que nous ne serons jamais capables d'analyser Perl suffisamment bien pour satisfaire les standards de ceux qui traitent Perl comme du code, il vaut la peine de réexaminer pourquoi nous voulons "analyser" Perl.

Quelles sont les choses pour lesquelles les gens pourraient vouloir un "analyseur Perl" ?

Documentation
Analyser le contenu d'un document Perl pour générer automatiquement de la documentation, parallèlement à, ou en remplacement de, la documentation POD.

Permettre à un indexeur de localiser et de traiter tous les commentaires et la documentation du code pour des applications de "recherche plein texte".

Analyse Structurelle et de Qualité
Déterminer la qualité ou d'autres métriques sur un corps de code, et identifier des situations relatives à des phrases, techniques ou emplacements particuliers.

Indexer les fonctions, variables et paquets dans le code Perl, et effectuer des analyses de recherche et de graphes (au sens nœud/arc) sur de grandes bases de code.

Perl::Critic, basé sur PPI, est un outil vaste et florissant pour la détection d'erreurs et l'analyse de style du code Perl.

Refactorisation
Apporter des changements structurels, syntaxiques ou autres au code de manière automatisée, soit indépendamment, soit en assistance à un éditeur. Cette liste de tâches comprend le backporting, le forward porting, l'évaluation partielle, "l'amélioration" du code, ou autre. Tout ce que vous attendriez d'un Perl::Editor.
Mise en page
Modifier la mise en page du code sans en changer le sens. Cela inclut des techniques telles que le nettoyage (comme perltidy), l'obfuscation, la compression et le "squishing", ou la mise en œuvre de préférences ou de politiques de formatage.
Présentation
Cela inclut des méthodes d'amélioration de la présentation du code, sans changer le contenu du code. Modifier, améliorer, coloriser la syntaxe, etc. la présentation d'un document Perl. Génération de fonctions de type "IntelliText".

Si nous considérons cela comme une base pour les types de choses sur lesquelles nous devrons construire par-dessus Perl, alors il devient possible d'identifier un standard pour la qualité d'un analyseur Perl nécessaire.

Quelle qualité est suffisamment bonne(TM)

PPI vise à être suffisamment bon pour réaliser toutes les tâches ci-dessus, ou pour fournir une API suffisamment bonne sur laquelle permettre à d'autres d'implémenter des modules dans ces domaines et des domaines connexes.

Internationalisation

PPI fournit un support partiel pour l'internationalisation et la localisation.

Plus précisément, il permet l'utilisation de caractères de l'ensemble de caractères Latin-1 dans les guillemets, les commentaires et le POD. Cela couvre en premier lieu les langues d'Europe et d'Amérique du Sud.

PPI ne fournit actuellement aucun support pour l'ensemble de caractères Unicode. Si vous avez besoin de support pour l'ensemble de caractères Unicode et souhaitez aider, veuillez contacter l'auteur. (détails de contact ci-dessous)

Round Trip Safe

Lorsque PPI analyse un fichier, il construit l'intégralité dans le modèle, y compris les espaces blancs. Ceci est nécessaire pour rendre le document totalement "Round Trip" sûr.

L'idée générale derrière un analyseur "Round Trip" est qu'il sait ce qu'il analyse, ce qui le rend parfois "attentif" à obtenir des choses mauvaises. Dans les cas où il analyse du code incorrectement, l'arbre est re-sérialisé dans la même chaîne de code qu'il a lue, réparant ainsi le faux pas tout en retournant au fichier.

Le résultat final est que si vous analysez un fichier et le re-sérialisez sans modifier l'arbre, vous êtes garanti d'obtenir le même fichier avec lequel vous avez commencé. PPI y parvient correctement et de manière fiable dans 100 % des cas connus.

Ce qui entre, sort. À chaque fois.

La seule petite exception pour le moment est que si les fins de ligne de votre fichier sont incorrectes (c'est-à-dire qu'elles ne correspondent pas au format de fin de ligne du système), PPI se localisera pour vous. (Ce n'est pas pour être à l'aise, supporter n'importe quel format de fin de ligne rendrait une partie du code plus compliquée)

Le contrôle du type de fin de ligne est sur la liste de souhaits, et toute personne intéressée à aider est invitée à contacter l'auteur.

IMPLÉMENTATION

General Layout

PPI est construit sur deux composants d'analyse principaux, PPI::Tokenizer et PPI::Lexer, et un grand arbre d'environ 70 classes qui implémentent le modèle objet de document Perl (PDOM).

Le PDOM est conceptuellement similaire en style et en objectif aux DOM standards ou à d'autres arbres de syntaxe abstraite (AST), mais il présente quelques différences pour gérer des cas spécifiques à Perl et pour aider à traiter le code comme un document. Il convient de noter qu'il ne s'agit pas d'une implémentation du modèle objet de document Perl standard, mais de quelque chose d'assez similaire.

Au-dessus du Tokenizer, du Lexer et des classes PDOM, il existe plusieurs classes conçues pour vous faciliter la vie lors de la manipulation de l'arbre PDOM.

Les deux composants d'analyse principaux ont été codés à la main à partir de zéro avec uniquement du code Perl et quelques petits modules utilitaires. Il n'y a pas de grammaires ni de langages de modèles réduits, ni d'outils comme YACC ou LEX, et il n'y a qu'un nombre limité d'expressions régulières.

C'est principalement dû au volume d'ordures dans Perl. Même Perl lui-même ne peut pas analyser les documents Perl (rappelez-vous, il ne fait que l'analyser et l'exécuter comme du code).

En conséquence, PPI a dû être plus "ordurier" que Perl. Vous pouvez vous sentir assez stupide à ce stade, et espérer que vous n'aurez jamais à comprendre le code du Tokenizer. D'ailleurs...

The Tokenizer

Le Tokenizer prend le code source et le transforme en une série de tokens. Il le fait par un processus lent mais détaillé, caractère par caractère, plutôt que d'utiliser un système de modèles ou des expressions régulières complexes.

Ou du moins, il le fait conceptuellement. Si vous vous étiez donné la peine, vous auriez constaté qu'il ne s'agit pas vraiment caractère par caractère en raison d'un certain nombre d'expressions régulières et d'optimisations dans le code. Cela permet au Tokenizer de "sauter" lorsqu'il peut trouver des accélérations, ce qui lui fait parfois sauter autour d'une ligne de manière assez incontrôlée.

En pratique, le nombre de fois que le Tokenizer déplace son propre curseur de caractère est supérieur d'environ 5 % à 10 % au nombre de tokens contenus dans le fichier. Cela le rend aussi optimal que possible sans l'implémenter dans autre chose que Perl.

En 2001, lorsque PPI a été lancé, cette structure rendait PPI très lent, et il n'était vraiment pas adapté aux tâches interactives. Cette situation s'est considérablement améliorée avec des processeurs multi-gigahertz, mais peut encore être gênante lors du traitement de fichiers volumineux.

Le taux d'analyse souhaité pour PPI est d'environ 5000 lignes par gigacycle. On pense actuellement qu'il est d'environ 1500, et le principal moyen d'atteindre le taux souhaité est maintenant PPI::XS, un accélérateur XS de PPI.

Comme PPI::XS n'en est qu'à ses débuts et qu'il s'agit d'une preuve de concept, cela pourrait prendre un peu de temps. Si vous êtes intéressé à aider avec PPI::XS, vous êtes fortement encouragé à contacter l'auteur. En fait, la conception de PPI::XS permet de porter une fonction à la fois de manière sûre et fiable. Donc, chaque petit peu aidera.

The Lexer

Le Lexer prend un flux de tokens et les transforme en un arbre lexical. Parce que nous analysons des **documents** de code Perl, cela inclut les espaces blancs, les commentaires et toutes sortes de choses qui n'ont aucune pertinence lorsque le code est exécuté.

Une instance de PPI::Lexer consomme des objets PPI::Tokenizer et produit des objets PPI::Document. Cependant, nous vous recommandons de ne jamais travailler directement avec le Lexer. Vous devriez pouvoir créer des objets PPI::Document et travailler directement avec eux.

The Perl Document Object Model

Le PDOM est une collection structurée de classes de données qui forment ensemble un modèle correct et évolutif pour les documents qui suivent la syntaxe standard de Perl.

Les trois classes les plus importantes parmi celles-ci sont PPI::Document, PPI::Statement et PPI::Structure.

The Document, Statement and Structure

Au sommet de tous les arbres PDOM complets se trouve un objet PPI::Document. Celui-ci représente un fichier de code source Perl tel que vous pourriez le trouver sur le disque.

Il existe quelques types spécialisés de documents, tels que PPI::Document::File et PPI::Document::Normalized, mais aux fins du PDOM, ils sont tous considérés de la même manière.

Chaque document contiendra un certain nombre d'États, de Structures et de Tokens.

Un PPI::Statement est toute séquence de Tokens et de Structures traitée comme un seul état continu par perl. Vous devez noter qu'un État est ce qui se rapproche le plus de ce que PPI peut "analyser" le code dans le sens où perl lui-même analyse le code Perl lorsqu'il construit son arbre d'opérations (arbre d'op).

En raison de l'isolement et de la syntaxe de Perl, il est mathématiquement impossible pour PPI de déterminer avec précision la précedence des opérateurs ou quels jetons sont des arguments implicites à un appel de sous-routine.

Ainsi, plutôt que de vous donner une mauvaise estimation qui a de fortes chances d'être erronée, PPI n'essaie pas du tout de déterminer la précedence ou les paramètres de sous-routines.

À un niveau fondamental, il sait seulement que cette série d'éléments représente une seule instruction telle que Perl la voit, mais il peut le faire avec suffisamment de certitude pour qu'elle soit fiable.

Cependant, pour des types spécifiques d'instructions, le PDOM est capable de dériver des informations utiles supplémentaires sur leur signification. Pour le meilleur exemple, le plus utile et le plus utilisé, voir PPI::Statement::Include.

Une PPI::Structure est toute série de jetons contenus dans des accolades correspondantes. Cela inclut les blocs de code, les conditions, les accolades d'arguments de fonction, les constructeurs d'arrays et de hashs anonymes, les listes, les accolades de portée et toutes les autres structures syntaxiques représentées par une paire d'accolades correspondante, y compris (bien que cela ne semble pas évident au premier abord) les accolades "<READLINE>".

Chaque Structure contient zéro, un, ou plusieurs Jetons et Structures (les règles pour lesquels varient selon les différentes sous-classes de Structure).

Selon les règles de structure du PDOM, une Instruction ne peut jamais directement contenir une autre Instruction enfant, une Structure ne peut jamais directement contenir une autre Structure enfant, et un Document ne peut jamais contenir un autre Document n'importe où dans l'arbre.

En dehors de ces trois règles, l'arbre PDOM est extrêmement flexible.

Le PDOM en Action

Pour démontrer le PDOM en action, commençons par un exemple montrant à quoi pourrait ressembler l'arbre pour le fragment de code Perl suivant.

#!/usr/bin/perl
print( "Hello World!" );
exit();

Traduit en arbre PDOM, il aurait la structure suivante (tel que montré via le PPI::Dumper inclus).

PPI::Document
  PPI::Token::Comment                '#!/usr/bin/perl\n'
  PPI::Token::Whitespace             '\n'
  PPI::Statement

Veuillez noter que dans cet exemple, les chaînes ne sont listées que pour le véritable PPI::Token qui contient cette chaîne. Les structures sont listées avec le type de caractères d'accolades qu'elles représentent.

Le module PPI::Dumper peut être utilisé pour générer vous-même des arbres similaires.

Nous pouvons rendre ce dump PDOM un peu plus facile à lire en retirant tous les espaces blancs. Le voici à nouveau, sans les jetons d'espace blanc distrayants.

  PPI::Statement

    PPI::Token::Word                 'exit'
    PPI::Structure::List             ( ... )
    PPI::Token::Structure            ';'

Comme vous pouvez le constater, l'arbre peut devenir assez profond à certains moments, surtout lorsque chaque jeton isolé dans une accolade devient sa propre instruction. Ceci est nécessaire pour permettre à tout élément de l'arbre de croître. Cela rend également les algorithmes de recherche et d'analyse beaucoup plus flexibles.

En raison de la profondeur et de la complexité des arbres PDOM, un grand nombre de méthodes très faciles à utiliser ont été ajoutées dans la mesure du possible pour aider les personnes travaillant avec des arbres PDOM à effectuer des tâches courantes de manière relativement rapide et efficace.

Aperçu des Classes Principales

Les principales classes PPI, et les liens vers leur propre documentation, sont listées ici par ordre alphabétique.

PPI::Document
L'objet Document, la racine du PDOM.
PPI::Document::Fragment
Un fragment cohérent d'un Document plus grand. Bien qu'il n'ait pas d'utilité actuelle réelle, il est nécessaire pour certains algorithmes internes de manipulation d'arbres.

Par exemple, pour faire des choses comme copier/coller, etc. Très similaire à un PPI::Document, mais possède des méthodes supplémentaires et ne représente pas une limite de portée lexicale.

Un fragment de document n'est pas non plus sérialisable, et ne peut donc pas être sauvegardé dans un fichier.

PPI::Dumper
Une classe simple pour afficher des versions de débogage lisibles des structures PDOM, comme dans la démonstration ci-dessus.
PPI::Element
La classe Element est la classe de base abstraite pour tous les objets du PDOM.
PPI::Find
Implémente une forme d'objet instanciable pour la recherche dans un arbre PDOM.
PPI::Lexer
Le Lexer PPI. Convertit les flux de jetons en arbres PDOM.
PPI::Node
L'objet Node, la classe de base abstraite pour tous les objets PDOM qui peuvent contenir d'autres Éléments, tels que les objets Document, Statement et Structure.
PPI::Statement
La classe de base pour toutes les instructions Perl. Les instructions génériques "évaluer pour effets secondaires" sont de ce type réel. D'autres types d'instructions plus intéressantes appartiennent à l'une de ses classes enfants.

Voir sa propre documentation pour une description plus longue et une liste de tous les différents types d'instructions et sous-classes.

PPI::Structure
La classe de base abstraite pour toutes les structures. Une Structure est une construction de langage composée d'accolades correspondantes contenant un ensemble d'autres éléments.

Voir la documentation de PPI::Structure pour une description et une liste de tous les différents types de structures et sous-classes.

PPI::Token
Un jeton est l'unité de base du contenu. Dans sa forme la plus basique, un Jeton est juste une chaîne de caractères taguée avec des métadonnées (sa classe et quelques indicateurs supplémentaires dans certains cas).
PPI::Token::_QuoteEngine
Les classes PPI::Token::Quote et PPI::Token::QuoteLike fournissent des classes de base abstraites pour les nombreux et variés types de guillemets et choses similaires aux guillemets en Perl. Cependant, une grande partie de la logique de guillemets réelle est implémentée dans un moteur de guillemets séparé, basé à PPI::Token::_QuoteEngine.

Les classes qui héritent de PPI::Token::Quote, PPI::Token::QuoteLike et PPI::Token::Regexp ne sont généralement analysées que par le Moteur de Guillemets.

PPI::Tokenizer
Le Tokenizer PPI. Un Tokenizer consomme un bloc de texte et fournit un accès à un flux d'objets PPI::Token.

Le Tokenizer est très, très compliqué, au point même que l'auteur progresse prudemment lorsqu'il travaille avec.

La plupart de la complication résulte d'optimisations qui ont triplé la vitesse de tokenisation, au détriment de la maintenabilité. Nous gérons ce "spaghetti" en commentant abondamment tout.

PPI::Transform
L'API de Transformation de Documents Perl. Fournit une interface standard et une classe de base abstraite pour les objets et classes qui manipulent les Documents.

INSTALLATION

La distribution PPI principale est en pur Perl et a été maintenue aussi compacte que possible et avec aussi peu de dépendances que possible.

Elle devrait se télécharger et s'installer normalement sur n'importe quelle plateforme depuis les applications CPAN et CPANPLUS, ou directement en utilisant la tarball de distribution. Si vous installez manuellement, vous pourrez avoir besoin d'installer quelques petits modules utilitaires au préalable. Ceux exacts dépendront de votre version de perl.

Il n'y a pas d'instructions d'installation spéciales pour PPI, et les instructions normales de "Perl Makefile.PL", "make", "make test", "make install" s'appliquent.

EXTENSION

L'espace de noms PPI lui-même est réservé à l'usage de PPI. Il est recommandé d'utiliser l'espace de noms PPIx:: pour les modifications ou prototypes spécifiques à PPI, ou Perl:: pour les modules qui fournissent des fonctions générales liées au langage Perl.

Si ce que vous souhaitez implémenter semble correspondre à l'espace de noms PPIx::, vous devriez envisager de contacter les mainteneurs de PPI sur GitHub au préalable, car ce que vous voulez pourrait déjà être en cours, ou vous pourriez vouloir envisager de contribuer à PPI lui-même.

- Création d'un document Tutoriel PPI

- Ajout de nombreuses fonctions clés supplémentaires à PPI::XS

- Nous pouvons toujours écrire des tests unitaires plus nombreux et meilleurs

- Achèvement de l'implémentation complète de ->literal (1.200)

- Compréhension complète de la portée (prévue pour 1.300)

SUPPORT

La version la plus récente de PPI est disponible à l'adresse suivante.

https://metacpan.org/pod/PPI

La source de PPI est maintenue dans un dépôt GitHub à l'adresse suivante.

https://github.com/Perl-Critic/PPI

Les contributions via des pull requests GitHub sont les bienvenues.

Les corrections de bugs sous forme de pull requests ou les rapports de bugs avec de nouveaux tests unitaires (en échec) ont les meilleures chances d'être traités par des mainteneurs occupés, et sont fortement encouragés.

Si vous ne pouvez pas fournir de test ou de correction, ou si vous n'avez pas le temps de

do so, alors les rapports de bugs réguliers sont toujours acceptés et appréciés via le dépôt de bugs GitHub.

https://github.com/Perl-Critic/PPI/issues

L'utilitaire "ppidump" qui fait partie de la distribution Perl::Critic est un outil utile pour démontrer comment PPI analyse (ou analyse mal) de petits extraits de code, et pour fournir des informations pour les rapports de bugs.

Pour d'autres problèmes, questions, ou demandes commerciales ou médiatiques, contactez l'auteur.
