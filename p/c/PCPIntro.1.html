NOM

PCPINTRO - Introduction au Performance Co-Pilot (PCP)

INTRODUCTIONS

Le Performance Co-Pilot (PCP) est une collection d'outils conçus pour surveiller et gérer les performances du système. Ces services sont distribués et évolutifs pour s'adapter aux configurations système et aux problèmes de performance les plus complexes.

PCP prend en charge différentes plateformes, y compris (mais sans s'y limiter) Linux, macOS, Solaris et Windows. D'un point de vue général, PCP peut être considéré comme contenant deux types d'utilitaires:

Collecteurs PCP
Ce sont les parties de PCP qui collectent et extraient les données de performance de diverses sources, par exemple le noyau du système d'exploitation.
Moniteurs PCP
Ce sont les parties de PCP qui affichent les données collectées à partir d'hôtes (ou de fichiers d'historique) sur lesquels le Collecteur PCP est installé. De nombreux outils de surveillance sont disponibles dans le cadre de la distribution standard de PCP, tandis que d'autres (généralement des outils graphiques) sont disponibles dans le paquet GUI de PCP.

Ce document de manuel décrit les caractéristiques et les options communes à la plupart des utilitaires PCP disponibles sur toutes les plateformes.

VUE D'ENSEMBLE

L'architecture PCP est distribuée dans le sens où tout outil PCP peut être exécuté à distance. Sur l'hôte (ou les hôtes) surveillé(s), chaque domaine de métriques de performance, qu'il s'agisse du noyau du système, d'un niveau de service, d'un système de gestion de base de données, d'un serveur web, d'un programme, etc., nécessite un Agent de Domaine de Mesure de Performance (PMDA) responsable de la collecte des mesures de performance de ce domaine. Tous les PMDA sont contrôlés par le Serveur Collecteur de Mesures de Performance (pmcd(1)) sur le même hôte.

Les applications clientes (les outils de surveillance) se connectent à pmcd(1), qui agit comme un routeur pour les requêtes, transmettant les requêtes aux PMDA correspondants et renvoyant les réponses aux clients. Les clients peuvent également accéder aux données de performance à partir des fichiers d'archivage PCP (créés avec pmlogger(1)) pour une analyse rétroactive.

SÉCURITÉ

PCP redistribue une quantité considérable d'informations de performance au sein de l'hôte et sur ses réseaux. La philosophie de sécurité sous-jacente repose sur plusieurs paramètres par défaut qui contrôlent la quantité d'informations envoyées et reçues.

Par défaut, les informations exposées par PMCD sur un hôte sont à peu près du même niveau de confidentialité que celles disponibles pour un utilisateur non privilégié sur cet hôte. Par conséquent, les données de performance qui peuvent être lues librement sur une machine peuvent être exposées par PMCD sur le réseau.

Cependant, l'hôte exécutant PMCD et son réseau ne sont pas supposés être uniquement peuplés d'applications conviviales. Par conséquent, les opérations d'écriture, y compris depuis l'hôte lui-même, ne sont pas autorisées par défaut.

Ces paramètres par défaut peuvent être modifiés (élargis ou restreints) de plusieurs manières, notamment en spécifiant des listes de contrôle d'accès dans pmcd.conf, en activant des PMDA non par défaut, ou en utilisant des connexions PMCD qui transmettent les identifiants de l'utilisateur. Par exemple, certains PMDA fournissent automatiquement des informations supplémentaires aux utilisateurs ou aux groupes spécifiques disposant d'identifiants.

APPLICATIONS

Les outils de surveillance des performances suivants sont principalement de type console, généralement exécutés directement depuis la ligne de commande, et ne représentent qu'une petite partie des outils disponibles dans le paquet de base de PCP.

Chaque outil ou commande est entièrement documenté dans sa propre page de manuel.

pmstat
Imprime un résumé ASCII de haut niveau des performances du système.
pmie
Un moteur d'inférence qui évalue des règles prédicat-action pour déclencher des alarmes et automatiser les tâches de gestion du système.
pminfo
Interroge des métriques de performance spécifiques et les métadonnées qui les décrivent.
pmlogger
Génère des fichiers d'archivage de métriques de performance compatibles avec la plupart des outils PCP.
pmrep
Un générateur de rapports de métriques de performance hautement personnalisable avec prise en charge de plusieurs modes de sortie.
pmval
Rapporte périodiquement certaines ou toutes les instances d'une métrique de performance, avec un contrôle optionnel du temps de magnétoscope.

Si le paquet GUI de PCP a été installé, les outils supplémentaires suivants peuvent être utilisés.

pmchart
Visualise les tendances dans le temps des métriques de performance sélectionnées arbitrairement à partir d'un ou plusieurs hôtes.
pmtime
Un utilitaire de synchronisation qui coordonne le temps entre plusieurs outils (y compris pmchart et pmval).
pmdumptext
Génère des rapports ASCII pour des combinaisons arbitraires de métriques de performance.

COMMANDES LIGNE PAR DÉFAUT

Il existe un ensemble de commandes ligne qui sont utilisées de manière cohérente par la plupart des outils PCP.

-a archive, --archive=archive
Les informations de métriques de performance sont obtenues de manière rétroactive à partir de l'ensemble d'archives PCP identifié par archive, précédemment généré par pmlogger(1). Voir LOGIMPORT(3) et LOGARCHIVE(5) pour plus d'informations sur la création de fichiers d'archives et la documentation du format.

archive est une liste séparée par des virgules de noms de fichiers, dont chacun peut être le nom d'un répertoire contenant une ou plusieurs archives, le nom de base commun à tous les fichiers physiques créés par une instance de pmlogger(1), ou n'importe lequel des fichiers physiques, par exemple /chemin/vers/mesarchives (répertoire) ou monarchive (nom de base) ou monarchive.meta (le fichier de métadonnées) ou monarchive.index (l'index temporel) ou monarchive.0 (le premier volume de données de archive) ou monarchive.0.bz2 ou monarchive.0.bz (le premier volume de données compressé avec bzip2(1)) ou monarchive.0.gz ou monarchive.0.Z ou monarchive.0.z (le premier volume de données compressé avec gzip(1)), monarchive.1 ou monarchive.3.bz2 ou monarchive.42.gz etc.

-h hôte, --host=hôte
À moins qu'un autre hôte ne soit spécifié par l'option -h (ou --host), ou qu'un ensemble d'archives ne soit spécifié par l'option -a (ou --archive), la source des métriques de performance sera le Serveur Collecteur de Mesures de Performance (PMCD) sur l'hôte local. Voir la section SPÉCIFICATION DE L'HÔTE PMCD plus loin pour plus de détails sur les nombreuses options disponibles lors de la formation de la spécification de l'hôte, ainsi qu'une description détaillée de la connexion par défaut de l'hôte local. Les options -a (ou --archive) et -h (ou --host) sont mutuellement exclusives.
-s échantillons, --samples=échantillons
L'argument échantillons définit le nombre d'échantillons à récupérer et à rapporter. Si échantillons est 0 ou si -s (ou --samples) n'est pas spécifié, l'application échantillonnera et rapportera en continu (en mode temps réel) ou jusqu'à la fin de la série d'archives PCP (en mode archive).
-z, --hostzone
Change l'heure d'affichage à la zone horaire de l'hôte source des métriques de performance, identifiée par l'option -h (ou --host) ou -a (ou --archive)
-Z fuseau horaire
Change l'heure d'affichage au fuseau horaire spécifié par fuseau horaire de l'hôte source des métriques de performance, identifiée par l'option -h (ou --host) ou -a (ou --archive)
-D spécification_debug, --debug=spécification_debug
Définit les options de débogage PCP à spécification_debug pour activer les diagnostics et le traçage qui sont les plus utiles pour les développeurs ou lors de la tentative de diagnostic du mauvais comportement d'une application PCP. spécification_debug doit être une liste séparée par des virgules de nom(s) d'option(s) de débogage et/ou d'entiers décimaux, voir pmdbg(1) pour une description des noms et valeurs d'options pris en charge.

En l'absence d'une source de métriques en direct ou archivée, une recherche heuristique d'archives pour l'hôte local peut être invoquée via l'option -O (ou --origin). Lors de l'utilisation de cette option sans source explicite de métriques, les outils de surveillance tentent d'utiliser les archives d'un emplacement d'archives système tel que $PCP_LOG_DIR/pmlogger/`hostname`. Référez-vous à la section SPÉCIFICATION DE FENÊTRE DE TEMPS ci-dessous pour plus de détails sur la syntaxe acceptable pour l'option d'origine, mais une invocation typique dans ce mode serait -O today ou --origin yesterday.

SPÉCIFICATION DE L'INTERVALLE ET ALIGNEMENT

La plupart des outils PCP fonctionnent avec un échantillonnage ou une génération de rapports périodiques, et les options -t (ou --interval) et -A (ou --align) peuvent être utilisées pour contrôler la durée de l'intervalle d'échantillonnage et l'alignement des heures d'échantillonnage.

-t intervalle, --interval=intervalle
Définit l'intervalle de mise à jour ou de rapport.

L'argument intervalle est spécifié comme une séquence d'un ou plusieurs éléments de la forme

nombre[unités]
où nombre est une constante entière ou flottante (analysée à l'aide de strtod(3)) et unités facultatif est l'une des suivantes : seconds, second, secs, sec, s, minutes, minute, mins, min, m, hours, hour, h, days, day et d. Si l'unité est vide, second est supposé.

De plus, la version en majuscules (ou mixtes) de l'un des éléments ci-dessus est également acceptable.

Les espaces n'importe où dans l'intervalle sont ignorés, donc 4 days 6 hours 30 minutes, 4day6hour30min, 4d6h30m et 4d6.5h sont tous équivalents.

Les spécifications multiples sont additives, par exemple ``1hour 15mins 30secs'' est interprété comme 3600+900+30 secondes.

-A alignement, --align=alignement
Par défaut, les échantillons ne sont pas nécessairement alignés sur une unité de temps naturelle. L'option -A ou --align peut être utilisée pour forcer le premier échantillon à être aligné sur la frontière d'une unité de temps naturelle. Par exemple, -A 1sec, -A 30min et --align 1hour spécifient un alignement sur les secondes entières, les demi-heures et les heures entières respectivement.

L'argument alignement suit la syntaxe d'un argument intervalle décrit ci-dessus pour l'option -t ou --interval.

Notez que l'alignement se produit en avançant le temps si nécessaire, et que -A (ou --align) agit comme un modificateur pour avancer à la fois le début de la fenêtre de temps (voir la section suivante) et l'heure d'origine (si l'option -O ou --origin est spécifiée).

SPÉCIFICATION DE FENÊTRE DE TEMPS

De nombreux outils PCP sont conçus pour fonctionner dans une fenêtre de temps d'intérêt, par exemple pour définir une heure de fin pour la surveillance en temps réel ou pour définir une heure de début et de fin dans un ensemble d'archives PCP.

En l'absence des options -O (ou --origin) et -A (ou --align) pour spécifier une origine de temps d'échantillonnage initiale et un alignement temporel (voir ci-dessus), l'application PCP récupérera le premier échantillon au début de la fenêtre de temps.

Les options suivantes peuvent être utilisées pour spécifier une fenêtre de temps d'intérêt.

-S heure_début, --start=heure_début
Par défaut, la fenêtre de temps commence immédiatement en mode temps réel, ou coïncide avec l'heure de début de l'ensemble des archives PCP en mode archive. L'option -S ou --start peut être utilisée pour spécifier une heure ultérieure pour le début de la fenêtre de temps.

Le paramètre heure_début peut être donné sous l'une des trois formes (intervalle est le même que pour l'option -t ou --interval décrit ci-dessus, datetime est décrit ci-dessous) :

intervalle
Pour spécifier un décalage par rapport à l'heure actuelle (en mode temps réel) ou au début d'un ensemble d'archives PCP (en mode archive), spécifiez simplement l'intervalle de temps comme argument. Par exemple, -S 30min définira le début de la fenêtre de temps exactement 30 minutes à partir de maintenant en mode temps réel, ou exactement 30 minutes à partir du début d'un ensemble d'archives PCP.
-intervalle
Pour spécifier un décalage par rapport à la fin d'un ensemble d'archives PCP, préfixez l'argument intervalle par un signe moins. Dans ce cas, le début de la fenêtre de temps précède l'heure de fin de l'ensemble des archives de l'intervalle donné. Par exemple, -S -1hour définira le début de la fenêtre de temps exactement une heure avant l'heure du dernier échantillon dans un ensemble d'archives PCP.
@datetime
Pour spécifier la date et l'heure du calendrier (heure locale dans le fuseau horaire de reporting) pour le début de la fenêtre de temps, utilisez la syntaxe datetime précédée d'un signe arobase. Reportez-vous à la description de datetime ci-dessous pour des informations détaillées.
-T heure_fin, --finish=heure_fin
Par défaut, la fin de la fenêtre de temps est illimitée (en mode temps réel) ou alignée sur l'heure de fin d'un ensemble d'archives PCP (en mode archive). L'option -T ou --finish peut être utilisée pour spécifier une heure antérieure pour la fin de la fenêtre de temps.

Le paramètre heure_fin peut être donné sous l'une des trois formes (intervalle est le même que pour l'option -t ou --interval décrit ci-dessus, datetime est décrit ci-dessous) :

intervalle
Pour spécifier un décalage par rapport au début de la fenêtre de temps, utilisez simplement l'intervalle de temps comme argument. Par exemple, -T 2h30m définira la fin de la fenêtre de temps à 2 heures et 30 minutes après le début de la fenêtre de temps.
-intervalle
Pour spécifier un décalage par rapport à l'heure de fin d'un ensemble d'archives PCP, préfixez l'argument intervalle par un signe moins. Par exemple, -T -90m définira la fin de la fenêtre de temps à 90 minutes avant l'heure du dernier échantillon dans un ensemble d'archives PCP.
@datetime
Pour spécifier la date et l'heure du calendrier (heure locale dans le fuseau horaire de reporting) pour la fin de la fenêtre de temps, utilisez la syntaxe datetime précédée d'un signe arobase. Reportez-vous à la description de datetime ci-dessous pour des informations détaillées.
-O origine, --origin=origine
Par défaut, les échantillons sont extraits du début de la fenêtre de temps (voir la description de l'option -S ou --start) jusqu'à la fin de la fenêtre de temps (voir la description de l'option -T ou --finish). L'option -O ou --origin permet de spécifier une origine dans la fenêtre de temps à utiliser comme heure d'échantillonnage initiale. Ceci est utile pour une utilisation interactive d'un outil PCP avec la facilité de lecture de magnétoscope pmtime(1).

L'argument origine accepté par -O (ou --origin) est conforme à la même syntaxe et sémantique que l'argument heure_début pour l'option -T (ou --finish).

Par exemple, --origin -0 spécifie que la position initiale doit être à la fin de la fenêtre de temps ; ceci est le plus utile lorsque l'on souhaite rejouer ``à l'envers'' dans la fenêtre de temps.

L'argument datetime pour les options -O (ou --origin), -S (ou --start) et -T (ou --finish) se compose de :
date heure fuseau_horaire jour relatif
Une date peut être l'une des suivantes : AA-MM-JJ, MM/JJ/AA, JJ Mois AAAA, ou Mois JJ AAAA. Une heure peut être l'une des suivantes : HH:MM:SS, HH:MM. HH:MM peut utiliser soit le format 12 heures (via un suffixe am ou pm) soit le format 24 heures. Un jour de la semaine peut être un jour de la semaine épelé, éventuellement précédé d'un numéro ordinal tel que le deuxième mardi. Une zone est une valeur de fuseau horaire telle que spécifiée par la commande tzselect(8). Un temps relatif peut être une unité de temps qui est : précédée d'un nombre cardinal tel que 1 an ou 2 mois, précédée de l'un des mots temps this ou last, ou suivie du mot temps ago. Un temps relatif peut également être l'un des mots temps : yesterday, today, tomorrow, now. Des exemples de chaînes datetime sont : 1996-03-04 13:07:47 EST Mon, 1996-03-05 14:07:47 EST -1hour, Mon Mar 4 13:07:47 1996, Mar 4 1996, Mar 4, Mar, 13:07:50 ou 13:08.

Pour tous les champs de faible ordre manquants, la valeur par défaut de 0 est supposée pour les heures, les minutes et les secondes, 1 pour le jour du mois et Jan pour les mois. Par conséquent, les éléments suivants sont équivalents : --start '@ Mar 1996' et --start '@ Mar 1 00:00:00 1996'.

Si des champs de haute ordre sont manquants, ils sont remplis en commençant par l'année, le mois et le jour de l'heure actuelle (mode temps réel) ou de l'heure de début de l'ensemble des archives PCP (mode archive) et en avançant l'heure jusqu'à ce qu'elle corresponde aux champs spécifiés. Ainsi, par exemple, si la fenêtre de temps commence par défaut à ``Mon Mar 4 13:07:47 1996'', alors --start @13:10 correspond à 13:10:00 le Lun Mar 4, 1996, tandis que --start @10:00 correspond à 10:00:00 le Mar 5, 1996 (notez que c'est le jour suivant).

Pour une précision supérieure à celle offerte par datetime(3), le se

conds peut être un nombre à virgule flottante.

Si un fuseau horaire n'est pas inclus dans un *datetime*, plusieurs interprétations sont disponibles en fonction des autres options de ligne de commande utilisées. Par défaut, le fuseau horaire local du système où l'outil PCP est exécuté est utilisé. Une option -Z ou --timezone spécifie un fuseau horaire explicite, sinon une option -z ou --hostzone change le fuseau horaire pour le fuseau horaire local de l'hôte qui est la source des métriques de performance.

MÉTRIQUES DE PERFORMANCE - IDENTIFIANTS, NOMS, VALEURS

Le nombre de noms de métriques de performance pris en charge par PCP sur la plupart des plateformes varie de plusieurs centaines à plusieurs milliers. Les bibliothèques et applications PCP utilisent un schéma d'identification interne qui associe sans ambiguïté un entier unique à chaque métrique de performance connue. Cet entier est connu sous le nom d'identifiant de métrique de performance, ou PMID. Bien que ce ne soit pas une exigence, les PMID ont tendance à avoir une cohérence globale sur tous les systèmes, de sorte qu'une métrique de performance particulière a généralement le même PMID.

Pour tous les utilisateurs et la plupart des applications, l'utilisation directe des PMID serait inappropriée (cela limiterait la gamme de métriques accessibles, rendrait le code difficile à maintenir, obligerait l'interface utilisateur à être particulièrement baroque, etc.). Par conséquent, un espace de noms de métriques de performance (PMNS) est utilisé pour fournir des noms externes et une classification hiérarchique pour les métriques de performance. Un PMNS est représenté comme un arbre, chaque nœud ayant une étiquette, un pointeur vers un PMID (pour les nœuds feuilles) ou un ensemble de nœuds descendants dans le PMNS (pour les nœuds non feuilles).

Une étiquette de nœud doit commencer par un caractère alphabétique, suivi de zéro ou plusieurs caractères tirés de l'alphabet, des chiffres et du caractère « _ » (souligné). Pour les caractères alphabétiques dans une étiquette de nœud, la casse majuscule et minuscule est distinguée.

Par convention, le nom d'une métrique de performance est construit par concaténation des étiquettes des nœuds sur un chemin à travers le PMNS de la racine à un nœud feuille, avec un « . » comme séparateur. Le nœud racine dans le PMNS n'est pas étiqueté, de sorte que tous les noms commencent par l'étiquette associée à l'un des nœuds descendants sous le nœud racine du PMNS, par exemple *kernel.percpu.syscall*. Typiquement (bien que ce ne soit pas une exigence), il y aurait au plus un nom pour chaque PMID dans un PMNS. Par exemple, *kernel.all.cpu.idle* et *disk.dev.read* sont les noms uniques de deux métriques de performance distinctes, chacune avec un PMID unique.

Des groupes de PMID liés peuvent être nommés en nommant un nœud non feuille dans l'arbre PMNS, par exemple *disk*.

Le PMNS local par défaut utilisé par pmcd est situé dans $PCP_VAR_DIR/pmns/root, cependant la variable d'environnement PMNS_DEFAULT peut être définie sur le chemin complet d'un PMNS différent qui sera alors utilisé comme PMNS local par défaut.

La plupart des applications n'utilisent pas directement le PMNS local, mais importent plutôt des parties du PMNS selon les besoins à partir du même endroit d'où sont récupérées les métriques de performance, c'est-à-dire de pmcd(1) pour la surveillance en direct ou d'un ensemble d'archives PCP pour la surveillance rétrospective.

Pour explorer le PMNS, utilisez pminfo(1), ou si le package GUI PCP est installé, les fenêtres New Chart et Metric Search dans pmchart(1).

Certaines métriques de performance ont une valeur singulière. Par exemple, la mémoire disponible ou le nombre de changements de contexte ont une valeur par source de métrique de performance, c'est-à-dire une valeur par hôte. Le descripteur de métrique (métadonnées) de chaque métrique informe les applications qui traitent les valeurs de ces métriques à valeur unique.

Certaines métriques de performance ont un ensemble de valeurs ou d'*instances* dans chaque domaine de métrique de performance implémentant. Par exemple, une valeur pour chaque disque, une valeur pour chaque processus, une valeur pour chaque CPU, ou une valeur pour chaque activation d'une application donnée. Lorsqu'une métrique a plusieurs instances, le PMNS ne le représente pas dans les noms de métriques ; plutôt, une seule métrique peut avoir un ensemble de valeurs associé. Les valeurs multiples sont associées aux membres d'un *domaine d'instances*, de sorte que chaque instance a un identifiant d'instance unique au sein du domaine d'instances associé. Par exemple, le domaine d'instances « par CPU » peut utiliser les identifiants d'instance 0, 1, 2, 3, etc. pour identifier les processeurs configurés dans le système. En interne, les identifiants d'instance sont encodés sous forme de valeurs binaires, mais chaque domaine de métrique de performance prend également en charge des chaînes correspondantes en tant que noms externes pour les identifiants d'instance, et ces noms sont utilisés dans l'interface utilisateur des utilitaires PCP.

Plusieurs métriques de performance peuvent être associées à un seul domaine d'instance. Par exemple, les métriques par processus sous *proc* partagent toutes le même domaine d'instance.

PCP organise les informations décrivant les domaines d'instance pour qu'elles soient exportées des domaines de métriques de performance vers les applications qui nécessitent ces informations. Les applications peuvent également choisir de récupérer les valeurs pour toutes les instances d'une métrique de performance, ou un sous-ensemble arbitraire des instances disponibles.

Les noms de métriques et le concept de domaine d'instance fournissent deux dimensions pour la modélisation des métriques de performance. C'est un modèle clair et simple, cependant, dans certains cas, il ne suffit pas. Par exemple, une métrique peut vouloir représenter des données de dimension supérieure telles que des compteurs « par CPU » pour chaque processus en cours d'exécution. Dans ces cas, il est courant de créer une instance composée, où le nom est composé de chaque composant avec un séparateur entre eux (par exemple, « 87245::cpu7 » pourrait être utilisé pour séparer l'ID du processus de l'ID du CPU) pour créer des noms d'instance aplaties. De plus, de tels cas bénéficient de l'utilisation d'étiquettes d'instances de métriques pour montrer explicitement les composants séparés (en poursuivant l'exemple ci-dessus, des étiquettes « {\"pid\":87245,\"cpu\":7} » pourraient être utilisées).

SPÉCIFICATIONS DES MÉTRIQUES DE PERFORMANCE

Dans les fichiers de configuration et (dans une moindre mesure) les options de ligne de commande, les spécifications de métriques respectent les règles de syntaxe suivantes par la plupart des outils. Voir les pages de manuel spécifiques à l'outil pour la syntaxe exacte prise en charge.

Si la source des métriques de performance est en temps réel à partir de pmcd(1), alors la syntaxe acceptée est
hôte:métrique[instance1,instance2,...]

Si la source des métriques de performance est un ensemble d'archives PCP, alors la syntaxe acceptée est
archive/métrique[instance1,instance2,...]

Les composantes hôte:, archive/ et [instance1,instance2,...] sont toutes facultatives.

Le délimiteur , dans la liste des noms d'instance peut être remplacé par des espaces blancs.

Les caractères spéciaux dans les noms d'*instance* peuvent être échappés en entourant le nom de guillemets doubles ou en faisant précéder le caractère d'une barre oblique inverse.

Les espaces blancs sont ignorés partout sauf dans un nom d'*instance* entre guillemets.

Une *instance* vide est ignorée silencieusement, et en particulier « [] » équivaut à aucune *instance*, tandis que « [one,,,two] » est analysé comme spécifiant uniquement les deux instances « one » et « two ».

À titre de cas spécial, si l'*hôte* est le caractère unique « @ » alors cela fait référence à une source PM_CONTEXT_LOCAL, voir pmNewContext(3).

CONNEXIONS SÉCURISÉES À PMCD

Depuis la version 3.6.11 de PCP, un moniteur peut demander explicitement une connexion sécurisée à un hôte collecteur exécutant pmcd(1) ou pmproxy(1) en utilisant le drapeau de contexte PM_CTXFLAG_SECURE. Si l'hôte collecteur PCP prend en charge cette fonctionnalité - référez-vous à la métrique pmcd.feature.secure pour confirmer cela - une connexion TLS/SSL (Transport Layer Security ou Secure Sockets Layer) peut être établie qui utilise la cryptographie à clé publique et des techniques connexes. Ces fonctionnalités visent à empêcher l'écoute clandestine et la falsification de données par un tiers malveillant, ainsi qu'à fournir une authentification côté serveur (identification certaine d'un serveur par un client) qui peut être utilisée pour se prémunir contre les attaques de type man-in-the-middle.

Une connexion sécurisée à pmcd nécessite l'utilisation de l'authentification par certificat. Les fonctionnalités de sécurité offertes par pmcd et pmproxy sont implémentées à l'aide des API et utilitaires OpenSSL. L'outil openssl(1) peut être utilisé pour créer des certificats appropriés pour établir la confiance entre le moniteur PCP et les hôtes collecteurs.

Une description complète dépasse le cadre de ce document, référez-vous aux sections ENVIRONNEMENT PCP, FICHIERS et VOIR AUSSI pour des informations détaillées. Cela inclut des liens vers des tutoriels sur les étapes nécessaires à la mise en place des fonctionnalités de sécurité disponibles.

SPÉCIFICATION DE L'HÔTE PMCD

En l'absence de spécification explicite du nom d'hôte, la plupart des outils utiliseront par défaut l'hôte local en mode de mise à jour en direct. Dans les versions de PCP depuis la 3.8.4, cela entraîne la sélection d'un protocole local efficace - généralement un socket de domaine Unix. Si cette option est utilisée (ce qui peut également être demandé explicitement via la spécification d'hôte *unix:* décrite ci-dessous), il est important de noter que toutes les connexions seront automatiquement authentifiées. En d'autres termes, les informations d'identification de l'utilisateur qui invoque un outil client seront automatiquement mises à disposition de pmcd(1) et de tous ses PMDA, pour le compte de l'utilisateur, afin que les résultats puissent être personnalisés aux niveaux de privilèges des utilisateurs individuels.

Les noms d'hôtes distants exécutant le démon pmcd(1) peuvent bien sûr également être fournis pour demander l'utilisation d'un hôte distant. La forme la plus basique d'une spécification d'hôte pmcd est un simple nom d'hôte, éventuellement incluant le nom de domaine si nécessaire. Cependant, cela peut être étendu de plusieurs manières pour affiner davantage les attributs de la connexion établie à pmcd.

Le numéro de port pmcd ainsi que le nom d'hôte pmproxy(1) optionnel et son numéro de port, peuvent être donnés dans le cadre de la spécification d'hôte, depuis la version 3.0 de PCP. Ceux-ci remplacent (et outrepassent) les anciennes variables d'environnement PMCD_PORT, PMPROXY_HOST et PMPROXY_PORT.

Les spécifications d'hôtes suivantes sont valides et spécifient des connexions à pmcd sur l'hôte nas1.acme.com avec/sans liste de ports, avec/sans un pmproxy(1) connexion via un pare-feu, et avec des adresses IPv6 et IPv4 comme indiqué.


$ pcp --host nas1.acme.com:44321,4321@firewall.acme.com:44322
$ pcp --host nas1.acme.com:44321@firewall.acme.com:44322
$ pcp --host nas1.acme.com:44321@firewall.acme.com
$ pcp --host nas1.acme.com@firewall.acme.com
$ pcp --host nas1.acme.com:44321
$ pcp --host [fe80::2ad2:44ff:fe88:e4f1%p2p1]
$ pcp --host 192.168.0.103

De plus, des ``attributs de connexion'' peuvent également être spécifiés. Ceux-ci incluent le nom d'utilisateur, le mot de passe (peut être fourni interactivement et peut dépendre du mécanisme d'authentification utilisé), s'il faut cibler un conteneur en cours d'exécution spécifique, s'il faut utiliser un protocole sécurisé (crypté) ou natif (nu), etc. Les exemples précédents utilisent tous par défaut le protocole natif, et n'utilisent aucune authentification. Cela peut être modifié, comme dans les exemples suivants.


$ pcp --host pcps://app2.acme.com?container=cae8e6edc0d5
$ pcp --host pcps://nas1.acme.com:44321?username=tanya&method=gssapi
$ pcp --host pcps://nas2.acme.com@firewalls.r.us?method=plain
$ pcp --host pcp://nas3.acme.com
$ pcp --host 192.168.0.103?container=cae8e6edc0d5,method=scram-sha-256
$ pcp --host unix:
$ pcp --host local:

Le choix de la méthode d'authentification, et d'autres paramètres résultants tels que le nom d'utilisateur, le mot de passe optionnel, etc., dépend de la configuration SASL2 utilisée par chaque pmcd (distant). Des tutoriels sont disponibles spécifiant divers aspects de la configuration des modules d'authentification utilisés ; ces détails fins sont hors de la portée de ce document.

Dans toutes les situations, les noms d'hôtes peuvent être utilisés de manière interchangeable avec l'adressage IPv4 ou IPv6 (directement), comme montré ci-dessus. Dans le cas d'une adresse IPv6, l'adresse complète doit être entourée de crochets et la portée (interface) doit également être spécifiée.

Le dernier exemple local: est maintenant le défaut pour la plupart des outils. Cette connexion est une connexion locale automatiquement authentifiée sur toutes les plateformes qui supportent les sockets de domaine Unix. Aucun mot de passe n'est requis et l'authentification est automatique. C'est aussi le canal de communication le plus efficace (le plus faible surcoût).

La différence entre unix: et local: est que le premier est une spécification stricte de socket de domaine Unix (la connexion échoue si elle ne parvient pas à se connecter de cette manière), tandis que le second a un mécanisme de repli plus tolérant vers l'utilisation de localhost (c'est-à-dire qu'une connexion socket Inet régulière est utilisée lorsque les connexions par socket de domaine Unix sont indisponibles).

Contient des répertoires de fichiers de configuration pour plusieurs outils PCP.

Script local pour contrôler les actions de démarrage, d'arrêt et de redémarrage de PCP.
$PCP_VAR_DIR/pmns
Répertoire contenant l'ensemble des fichiers PMNS pour tous les PMDA installés.
$PCP_VAR_DIR/pmns/root
Le fichier PMNS(5) ASCII exporté par défaut par pmcd(1). Ce PMNS est le sur-ensemble de tous les autres fichiers PMNS installés dans $PCP_VAR_DIR/pmns.

Fichier de contrôle pour les instances de pmlogger(1) lancées depuis $PCP_RC_DIR/pmlogger et/ou gérées par pmlogger_check(1) et pmlogger_daily(1) dans le cadre d'une configuration de collecte d'archives PCP de production.

ENVIRONNEMENT

En plus de l'environnement d'exécution de PCP et des variables de configuration décrites dans la section ENVIRONNEMENT D'EXÉCUTION PCP ci-dessous, les variables d'environnement suivantes s'appliquent à toutes les installations.

Notez que la plupart des utilisations de ces variables d'environnement sont optimisées pour vérifier l'environnement uniquement lors de la première utilisation potentielle de la variable. Comme l'environnement n'est généralement pas vérifié à nouveau, la seule stratégie sûre est de s'assurer que toutes les variables d'environnement liées à PCP sont définies avant le premier appel à l'une des bibliothèques PCP.

PCP_ALLOW_BAD_CERT_DOMAIN
Lorsqu'elle est définie, permet aux clients d'accepter des certificats avec des noms de domaine non concordants sans invite lorsqu'ils sont envoyés par pmcd ou d'autres composants serveur. Voir PCP_SECURE_SOCKETS.
PCP_ALLOW_SERVER_SELF_CERT
Lorsqu'elle est définie, permet aux clients d'accepter des certificats auto-signés sans invite lorsqu'ils sont envoyés par pmcd ou d'autres composants serveur. Voir PCP_SECURE_SOCKETS.
PCP_CONSOLE
Lorsqu'elle est définie, modifie la console par défaut de /dev/tty (sur Unix) ou CON: (sur Windows) pour être la console spécifiée. La valeur spéciale de none peut être utilisée pour indiquer qu'aucune console n'est disponible pour l'utilisation. Ceci est utilisé dans les cas où les outils basés sur la console doivent interagir avec l'utilisateur, et en particulier lorsqu'une authentification est en cours d'exécution.
PCP_DEBUG
Lorsqu'elle est définie, cette variable fournit une alternative à l'option de ligne de commande -D décrite ci-dessus pour initialiser les options de diagnostic et de débogage pour les applications qui utilisent pmGetOptions(3) pour traiter les options et arguments de ligne de commande. La valeur de $PCP_DEBUG est la même que pour l'option de ligne de commande -D, à savoir une liste séparée par des virgules de noms d'options de débogage, et/ou d'entiers décimaux, voir pmdbg(1) pour une description des noms et valeurs d'options pris en charge.
PCP_DERIVED_CONFIG
Lorsqu'elle est définie, cette variable définit une liste séparée par des deux-points de fichiers et/ou de répertoires (la syntaxe est la même que pour la variable $PATH de sh(1)). Les composants sont développés en une liste de fichiers comme suit : si un composant de $PCP_DERIVED_CONFIG est un fichier, alors ce fichier est ajouté à la liste, sinon si un composant est un répertoire alors une descente récursive est utilisée pour énumérer tous les fichiers sous ce répertoire et ceux-ci sont ajoutés à la liste.

Chaque fichier de la liste résultante est supposé contenir des définitions de métriques dérivées selon la syntaxe décrite dans pmLoadDerivedConfig(3), et celles-ci sont chargées dans l'ordre.

Les métriques dérivées peuvent être utilisées pour étendre les métriques disponibles avec de nouvelles métriques (dérivées) en utilisant des expressions arithmétiques simples.

Si PCP_DERIVED_CONFIG est définie, les définitions de métriques dérivées sont traitées automatiquement à chaque établissement d'une nouvelle source de métriques de performance (c'est-à-dire chaque fois qu'une fonction pmNewContext(3) est appelée) ou lorsque des requêtes sont faites sur le PMNS.

Tout composant de la liste $PCP_DERIVED_CONFIG ou de la liste étendue de fichiers qui n'est pas un fichier, ou n'est pas un répertoire, ou n'est pas accessible (en raison des permissions ou d'un lien symbolique défectueux) sera silencieusement ignoré.

pcp.env(5)

Performance Co-Pilot Environment Variables

NAME

pcp.env - Performance Co-Pilot environment variables

DESCRIPTION

Many of the Performance Co-Pilot (PCP) tools and applications use environment variables to control their behavior. The primary mechanism for controlling the configuration of PCP applications is via the pcp.conf(5) file, but a range of environment variables can be used to override these settings or provide additional configuration for specific invocations.

Details of the environment variables that are used by PCP applications are provided in the files listed in the FILES section below.

FILES

The primary PCP configuration file, used by PCP daemons and clients, is /etc/pcp.conf. The PCP utilities use a set of environment variables to control their behavior. These are described in:

  • pcp.conf(5) for general configuration and client connection parameters.
  • pmcd.conf(5) for controlling the PCP collector daemon (pmcd(1)).
  • pmlogger.conf(5) for controlling the PCP archive logger daemon (pmlogger(1)).
  • pmie.conf(5) for controlling the PCP inference engine daemon (pmie(1)).
  • pmtrap.conf(5) for controlling the PCP event trap daemon (pmtrap(1)).
  • pmdumptext(1) for controlling the formatting of output from the pmdumptext(1) utility.
  • pmrep(1) for controlling the output format of the pmrep(1) utility.
  • pmval(1) for controlling the output format of the pmval(1) utility.
  • pmchart(1) for controlling the graphical output of the pmchart(1) utility.
  • pmtime(1) for controlling the time selection dialogue of the pmtime(1) utility.
  • pminfo(1) for controlling the output of the pminfo(1) utility.
  • pmtrace(1) for controlling the output of the pmtrace(1) utility.
  • pcp.pidfile(5) for the format of PID files.
  • pcp.kopt(5) for controlling the kernel metric reporting.

ENVIRONMENT

The following environment variables are supported by PCP:

$PCP_CONF
If set, this variable specifies the location of the PCP configuration file. By default, this is /etc/pcp.conf.
$PCP_HOST
If set, this variable specifies the default host to connect to when accessing performance metrics. If not set, PCP will default to using the local host.
$PCP_USER
If set, this variable specifies the user account under which PCP daemons (e.g., pmcd(1), pmlogger(1)) should run. This is typically only used when starting PCP services as root.
$PCP_DATADIR
The directory for runtime data files, including archives and process information.
$PCP_LOGDIR
The directory for log files generated by PCP daemons.
$PCP_RUNTIMEDIR
The directory for runtime control files, such as PID files and sockets.
$PCP_DEMODIR
The directory for example configuration and metric files.
$PCP_SYSCONFDIR
The directory for system-wide configuration files.
$PCP_LOCALEDIR
The directory for locale-specific message catalogs.
$PCP_TMPDIR
A directory for temporary files.

Some PCP tools may also consult environment variables that are used by the underlying C library, such as TZ for time zone information.

PCP ENVIRONMENT

The PCP utilities may be configured via environment variables. These variables are often used to override defaults or to provide specific settings for individual tool invocations. The following are commonly used:

$PCP_HOST
This environment variable is used by many PCP clients to specify the Performance Metrics Domain (PMD) host to connect to. If this variable is not set, the default is to connect to the local host. For example:

$ export PCP_HOST=remote.example.com

$PCP_PMCD_PORT
Specifies the TCP port number for the pmcd(1) daemon. The default is 44321.
$PCP_PMCD_LOCAL
If set to a non-empty value, this environment variable causes PCP clients to attempt to connect to a local pmcd(1) instance, bypassing any pmcd.conf(5) or $PCP_HOST settings. This is useful for testing or when you are certain that a local pmcd(1) is running.
$PCP_DEBUG
If set to a non-empty value, this environment variable enables verbose debugging output from many PCP tools. The level of debugging can sometimes be controlled by appending a number (e.g., $PCP_DEBUG=1).
$PCP_TEXT_OUTPUT
This environment variable influences the default output format for tools like pmval(1) and pmrep(1). If set, it typically forces plain text output rather than the default graphical or more structured formats.
$PCP_DATE_FORMAT
Allows customization of how dates and times are displayed. For example, you might set it to display dates in ISO 8601 format. Consult the documentation for the specific tool for details on supported formats.
$PCP_TIMEOUT
Sets a timeout value in seconds for network operations, such as waiting for a response from pmcd(1).
$PCP_METRIC_PATH
Specifies a colon-separated list of directories to search for metric description files (PMNS files). This overrides the default search path.
$PCP_ARCHIVE
Used by tools that process PCP archives to specify the directory where archives are stored. By default, this is often /var/log/pcp/pmlogger/.
$PCP_USE_ARCHIVE
When set, this environment variable enables the use of PCP archives for data retrieval, even if a live connection to pmcd(1) is available. This is useful for replaying historical data.

The file /etc/pcp.conf contains the local values for these variables. The $PCP_CONF variable may be used to specify an alternative configuration file, as described in pcp.conf(5).

For environment variables affecting PCP tools, see pmGetOptions(3).
