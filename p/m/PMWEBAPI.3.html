NOM

PMWEBAPI - Introduction à l'API Web des Métriques de Performance Coeur

SYNTAXE HTTP

GET /metrics
GET /series/...
GET /search/...
GET /pmapi/...
POST /logger/...

SYNTAXE C

#include <pcp/pmwebapi.h>

... routines diverses ...

cc ... -lpcp_web -lpcp

DESCRIPTION

PMWEBAPI est une collection d'interfaces qui fournissent des services de métriques Performance Coeur pour les applications web. Elle inclut des API pour les applications web interrogeant et analysant les données de métriques en temps réel et historiques, ainsi que des API utilisées par les serveurs web.

Les règles des paramètres HTTP standard s'appliquent et les requêtes REST PMWEBAPI suivent toujours la convention :

/api/endpoint?parametre1=valeur1&parametre2=valeur2

Les exemples dans les sections suivantes utilisent l'utilitaire curl(1) avec un serveur local pmproxy(1) écoutant sur le port 44322 (port par défaut). L'utilitaire pmjson(1) est utilisé pour formater proprement toute sortie JSON, par opposition au format compact (avec un minimum d'espaces blancs) par défaut. Les exemples dans la section des séries temporelles évolutives utilisent des données historiques enregistrées par le service pmlogger(1), couplé à un serveur local clé-valeur.

OPEN METRICS ET OPEN TELEMETRY

L'exportation des métriques en temps réel au format Open Metrics (https://openmetrics.io) ou au format Open Telemetry (https://opentelemetry.io) est disponible.

Toutes les requêtes sont effectuées sur l'hôte du serveur web par défaut, à moins qu'un paramètre hostspec ne soit spécifié.

GET /metrics

Paramètres Type Explication
names chaîne Liste des noms de métriques séparés par des virgules
filter chaîne Liste des noms de métriques exclus séparés par des virgules
match chaîne Mode de correspondance (exact, glob, ou regex)
times booléen Inclure les horodatages d'échantillons (millisecondes depuis l'époque)
hostspec chaîne Schéma d'hôte tel que décrit dans PCPIntro(1)

Récupère les valeurs actuelles et les métadonnées pour toutes les métriques, ou seulement celles indiquées par une liste de names séparés par des virgules.

Pour toutes les métriques avec un préfixe numérique NAME, crée un format de sortie texte ouvert qui donne sa valeur actuelle et ses métadonnées associées.

Le choix du format de sortie est sélectionné via l'en-tête HTTP Accept. Sans en-tête, le format par défaut est le texte Open Metrics. L'utilisation de l'en-tête avec la valeur application/json modifie la réponse au format JSON d'Open Telemetry.

En mode de réponse Open Telemetry, les horodatages d'échantillons sont toujours inclus et rapportés avec précision en nanosecondes.

$ curl -H Accept:application/json -s http://localhost:44322/metrics?names=disk.dev,filesys | pmjson
{
    "resourceMetrics": [
        {
            "resource": {
                "attributes": [ ... ]
            },
            "scopeMetrics": [
                {
                    "scope": { ... },
                    "metrics": [
                        {
                            "name": "disk.dev.total.bytes",
                            "description": "compteur par disque des octets lus et écrits",
                            "unit": "KiBy",
                            "sum": {
                                "aggregationTemporality": "CUMULATIVE",
                                "isMonotonic": true,
                                "dataPoints": [
                                    {
                                        "attributes": [ ... ]
                                        "timeUnixNano": "1753934255798173",
                                        "asInt": "68927569"
                                    }
                                ]
                            }
                        },
                        ...

En mode de réponse Open Metrics, les métadonnées natives de la métrique (nom, type, indom, sémantique et unités) sont affichées en premier pour chaque métrique avec le préfixe # PCP. Les métadonnées rapportées sont de la forme décrite dans pmTypeStr(3), pmInDomStr(3), pmSemStr(3) et pmUnitsStr(3) respectivement. Si la chaîne d'unités pmUnitsStr(3) est vide, none est affiché. La chaîne de métadonnées d'unités peut contenir des espaces et s'étend jusqu'à la fin de la ligne.

Les noms de métriques PCP sont mappés de telle sorte que les séparateurs . soient échangés contre des _ (: en mode compatibilité, où # PCP est le suffixe de ligne identifiant). Les étiquettes de métriques et les instances sont représentées comme des étiquettes Open Metrics, avec les noms d'instances externes entre guillemets et la hiérarchie d'étiquetage PCP déployée avec chaque valeur.

Lors de la correspondance des noms de métriques en utilisant l'option filter, le mode par défaut est la correspondance par joker (glob). L'option match peut être utilisée pour demander un filtrage basé sur regex ou une correspondance exacte des métriques.

$ curl -s http://localhost:44322/metrics?names=proc.nprocs,kernel.pernode.cpu.intr,filesys.blocksize
# PCP5 proc.nprocs 3.8.99 u32 PM_INDOM_NULL instant none
# HELP proc_nprocs instantaneous number of processes
# TYPE proc_nprocs gauge
proc_nprocs {hostname="app1"} 7
# PCP5 kernel.pernode.cpu.intr 60.0.66 u64 60.19 counter millisec
# HELP kernel_pernode_cpu_intr total interrupt CPU [...]
# TYPE kernel_pernode_cpu_intr counter
kernel_pernode_cpu_intr{hostname="app1",instname="node0"} 25603
# PCP5 filesys.blocksize 60.5.9 u32 60.5 instant byte
# HELP filesys_blocksize Size of each block on mounted file[...]
# TYPE filesys_blocksize gauge
filesys_blocksize{hostname="app1",instname="/dev/sda1"} 4096
filesys_blocksize{hostname="app1",instname="/dev/sda2"} 4096

SERIES TEMPORELLES ÉVOLUTIVES

Les capacités de requête de séries temporelles rapides et évolutives fournies par l'utilitaire pmseries(1) sont également accessibles via une API REST. Ces requêtes permettent d'accéder aux données de métriques (métadonnées et valeurs) de plusieurs hôtes simultanément, dans un style adapté à une récupération efficace par un nombre quelconque d'applications web.

Toutes les requêtes de ce groupe peuvent être accompagnées d'un paramètre optionnel client. La valeur passée dans la requête est renvoyée dans la réponse - toutes les réponses seront au format objet JSON dans ce cas, avec les champs de niveau supérieur client et result.

Les clients de l'API REST peuvent optionnellement envoyer une chaîne de requête URL-encodée dans le corps de la requête HTTP, sauf indication contraire. Dans ce cas, la méthode POST doit être utilisée au lieu de la méthode GET.

GET /series/ping

Un simple test de fonctionnement pour que les clients vérifient si le serveur est opérationnel et prend en charge l'API /series.

Effectue une requête de séries en temps réel pour des identifiants de séries ou pour des identifiants de séries avec des valeurs horodatées.

La requête est au format décrit dans pmseries(1) et est passée au serveur via le paramètre expr (HTTP GET) ou via le corps de la requête (HTTP POST).

Lorsqu'on interroge uniquement des séries temporelles, aucune option de fenêtre temporelle n'est spécifiée et les identifiants de séries sont renvoyés dans un tableau JSON.

$ curl -s 'http://localhost:44322/series/query?expr=disk.dev.read*' | pmjson
[
  "9d8c7fb51ce160eb82e3669aac74ba675dfa8900",
  "ddff1bfe286a3b18cebcbadc1678a68a964fbe9d",

]

GET /series/values - pmSeriesValues(3)

Paramètres Type Explication
series string Liste séparée par des virgules d'identifiants de séries
client string Identifiant de requête renvoyé avec la réponse
samples number Nombre d'échantillons à renvoyer
interval string Intervalle entre les échantillons consécutifs
start string Date de début de la fenêtre d'échantillons
finish string Date de fin de la fenêtre d'échantillons
offset string Décalage de la fenêtre d'échantillons
align string Alignement temporel des échantillons
zone string Fuseau horaire de la fenêtre d'échantillons

Récupère les valeurs pour un ou plusieurs identifiants de séries. La réponse au format JSON contient les mêmes informations que l'option pmseries-q/--query en utilisant l'un des paramètres de fenêtre temporelle décrits dans pmseries(1). Si aucun paramètre de fenêtre temporelle n'est spécifié, la dernière valeur observée est renvoyée.

$ curl -s http://localhost:44322/series/values?series=605fc77742cd0317597291329561ac4e50c0dd12 | pmjson
[
  {
    "series": "605fc77742cd0317597291329561ac4e50c0dd12",
    "timestamp": 1317633022959.959241041,
    "value": "71660"
  }
]

GET /series/labels - pmSeriesLabels(3), pmSeriesLabelValues(3)

Paramètres Type Explication
series string Liste séparée par des virgules d'identifiants de séries
match string Modèle de chaîne à faire correspondre dans toutes les étiquettes
name string Rechercher toutes les valeurs d'étiquette connues pour un nom donné
names string Liste séparée par des virgules de noms d'étiquettes
client string Identifiant de requête renvoyé avec la réponse

Cette commande fonctionne dans l'un des trois modes. Elle peut effectuer une recherche d'étiquettes pour un ou plusieurs identifiants de séries, lorsque le paramètre series est fourni. Elle peut également produire une liste de tous les noms d'étiquettes connus, sans les paramètres name, names ou series. Les réponses JSON dans ces modes contiennent les mêmes informations que l'option pmseries-l/--labels.

Alternativement, elle peut produire une liste de toutes les valeurs connues d'une étiquette donnée ou de names. La réponse JSON dans ce mode contient les mêmes informations que l'option pmseries-v/--values.

    "labels": {
      "agent": "linux",
      "domainname": "acme.com",
      "groupid": 1000,
      "hostname": "www.acme.com",
      "latitude": -25.28496,
      "longitude": 152.87886,
      "machineid": "295b16e3b6074cc8bdbda8bf96f6930a",
      "platform": "dev",
      "userid": 1000
    }
  }
]

Alternativement, sans les paramètres name, names ou series, renvoie la liste de tous les noms d'étiquettes connus.

$ curl -s http://localhost:44322/series/labels | pmjson
[
    "agent",
    "appversion",

    "groupid",
    "hostname",
    "jobid",
    "latitude",
    "longitude",
    "machineid",
    "platform",
    "userid"
]

Utilisez les paramètres name ou names pour trouver toutes les valeurs possibles d'étiquette pour les noms donnés.

$ curl -s http://localhost:44322/series/labels?names=hostname,domainname | pmjson
{
    "hostname": [ "app", "nas" ],
    "domainname": [ "acme.com" ]
}

RECHERCHE TEXTUELLE

Les capacités de recherche textuelle fournies par la commande pmsearch(1) sont également disponibles via une API REST. Ces requêtes donnent accès à un index sur les noms de métriques de performance, les instances, les domaines d'instances et le texte d'aide, adapté pour un moteur de recherche de métriques, et d'une manière appropriée pour une requête efficace par un nombre quelconque d'applications web.

Afin d'utiliser cette fonctionnalité, le module facultatif ValkeySearch doit être chargé dans le serveur clé-valeur au moment où pmproxy est démarré, de sorte que les métriques, instances et textes d'aide qu'il découvre puissent être indexés automatiquement.

GET /search/text - pmSearchTextQuery(3)

Paramètres Type Explication
query string Chaîne de requête au format pmsearch(1)
highlight fields Inclure le balisage correspondant dans les champs de réponse
offset number Curseur de décalage des résultats pour la pagination
limit number Nombre maximum de résultats à inclure dans la réponse
field fields Champs interrogeables (par défaut, tous)
return fields Champs à renvoyer réellement (par défaut, tous)
type types Types d'entités à filtrer (par défaut, tous)

Effectue une recherche textuelle sur les métriques et les domaines d'instances - toutes les formes de noms et textes d'aide.

La chaîne de recherche obligatoire est décrite plus en détail dans pmsearch(1) et est passée au serveur via le paramètre query (HTTP GET).

$ curl -s http://localhost:44322/search/text?query=halt | pmjson
{
  "total": 2,
  "offset": 0,
  "limit": 10,
  "elapsed": 0.000504,
  "results": [
    {
      "name": "kvm.halt_exits",
      "type": "metric",
      "indom": "95.0.4",
      "oneline": "Nombre de sorties de l'invité dues à des appels halt.",
      "helptext": "Ce type de sortie est généralement observé lorsqu'un invité est inactif."
    },
    {
      "name": "kvm.halt_wakeup",
      "type": "metric",
      "indom": "95.0.6",
      "oneline": "Nombre de réveils après un halt.",
    }
  ]
}

Les types d'entités de recherche disponibles sont metric, indom et instance. Les paramètres de requête highlight et field acceptent name, oneline et helptext.

Le paramètre de requête return accepte name, type, oneline, helptext, indom. Il y a généralement à la fois un nom et un texte d'aide associés aux métriques. Les contenus de ceux-ci sont ensuite mis en correspondance avec query. Un domaine d'instance a un texte d'aide et un identifiant numérique, tandis que les instances ont un nom seulement (qui peut être recherché).

GET /search/suggest - pmSearchTextSuggest(3)

Paramètres Type Explication
query string Requête de recherche pour le moteur de recherche
limit number Nombre maximum de résultats à inclure dans la réponse

Fournit des suggestions de requêtes de recherche, c'est-à-dire des noms de métriques et d'instances.

La chaîne de recherche obligatoire est décrite plus en détail dans pmsearch(1) et est passée au serveur via le paramètre query (HTTP GET).

$ curl -s http://localhost:44322/search/suggest?query=disk&limit=4 | pmjson
[
    "disk.all.avactive",
    "disk.all.aveq",
    "disk.all.blkread",
    "disk.all.blktotal"
]

GET /search/indom - pmSearchTextInDom(3)

Paramètres Type Explication
query string Indom cible pour le moteur de recherche

PMAPI HOST SERVICES

Les installations de collecte de performances en direct disponibles à partir de pmcd(1) peuvent également être accessibles via une API REST.

Toutes les requêtes sont effectuées sur l'hôte du serveur web par défaut, sauf si un paramètre hostspec ou context est fourni. hostname peut être utilisé à la place de hostspec.

Les identifiants de contexte sont utilisés comme moyen persistant de se référer aux contextes PMAPI à travers des requêtes web connexes. Ces contextes expirent après une période configurable de non-utilisation, et sont soit explicitement alloués à l'aide de l'interface /pmapi/context, soit implicitement alloués à l'aide d'autres interfaces.

L'intervalle de délai d'attente est configurable au moment de la création du contexte, et à ce titre, le paramètre polltimeout peut être utilisé partout où hostspec est spécifié. Il définit le délai d'attente du contexte en termes de durée d'inactivité. L'unité de la valeur du délai d'attente est en secondes et la valeur par défaut est 5.

Pour spécifier un contexte existant spécifique dans toute requête web PMAPI, les points d'extrémité peuvent être accédés avec le paramètre context ou intégrés dans l'URL du point d'extrémité lui-même, tel que /pmapi/[nombre]/fetch.

GET /pmapi/context - pmNewContext(3)

Paramètres Type Explication
hostspec chaîne Spécification d'hôte telle que décrite dans PCPIntro(1)
polltimeout nombre Secondes d'inactivité avant fermeture du contexte
client chaîne Identifiant de requête renvoyé avec la réponse

Pour créer un contexte d'échantillonnage en direct, un client web peut accéder à n'importe quelle URL /pmapi (en utilisant éventuellement le paramètre hostspec ou context). Si aucun contexte n'existe, un nouveau sera créé pour ce client web, et son identifiant sera renvoyé pour les accès futurs.

Cependant, /pmapi/context est fourni comme une URL dédiée aux applications souhaitant créer explicitement les contextes qu'elles utilisent.

En cas de succès, le serveur répond avec un code HTTP 200 (OK) et un corps de message JSON de la forme :

$ curl -s http://localhost:44322/pmapi/context?hostspec=www.acme.com&polltimeout=0.5 | pmjson

    "machineid": "295b7623b6074cc8bdbda8bf96f6930a"

Dans le cas d'un hostspec contenant des informations d'authentification, telles qu'un nom d'utilisateur, le serveur suivra le protocole HTTP Basic Authentication pour obtenir les détails d'authentification nécessaires de l'utilisateur, offrant à l'application web client une opportunité de les demander à l'utilisateur.

WEBHOOK D'ARCHIVAGE - LOGARCHIVE(5)

La fonctionnalité de push d'archive à distance est disponible via les utilitaires pmlogger(1) et pmlogpush(1). Ceci est réalisé par une série d'opérations HTTP POST sur les points d'API décrits ici.

Toutes les requêtes de ce groupe peuvent être accompagnées d'un paramètre client optionnel. La valeur passée dans la requête sera renvoyée dans la réponse - toutes les réponses sont sous forme d'objet JSON et incluront un champ de niveau supérieur supplémentaire "client".

GET /logger/ping

Test de base de disponibilité pour que les clients vérifient si le serveur est opérationnel et prend en charge l'API /logger.

POST /logger/label

Le corps de cette API est la représentation binaire (sur disque) indépendante de la machine d'une étiquette d'archive PCP telle que décrite dans LOGARCHIVE(5). Les versions 2 et 3 sont acceptées, et le champ volume de cette structure sera ignoré - un appel API suffit pour tous les volumes d'une archive, pmproxy assure que le contenu correct est écrit pour chacun.

Cette API renvoie un jeton numérique (LOGID) qui doit être utilisé dans toutes les interactions API ultérieures pour cette archive, comme décrit ci-dessous.

POST /logger/meta/LOGID

Le corps de la requête contient des enregistrements de fichiers de métadonnées tels que décrits dans LOGARCHIVE.

POST /logger/index/LOGID

Le corps de la requête contient des enregistrements d'index temporels tels que décrits dans LOGARCHIVE.

POST /logger/volume/VOLID/LOGID

Le corps de la requête contient des échantillons de valeurs de métriques horodatées, tels que décrits dans LOGARCHIVE. Le volume numérique (VOLID) auquel ces enregistrements doivent être écrits est une partie obligatoire du point d'API.

NOTES

Pour les API REST, les erreurs entraînent généralement des réponses d'erreur au niveau HTTP. Dans la mesure du possible, toute chaîne d'erreur PMAPI sera également fournie dans un message accompagnant la réponse.

Toutes les réponses seront renvoyées en utilisant le protocole HTTP 1.1 et avec un encodage segmenté utilisé pour diffuser les réponses plus volumineuses qu'une taille maximale configurée. La compression sera utilisée sur les réponses chaque fois que le client indiquera un support approprié.

Un en-tête Access-Control-Allow-Origin: * est ajouté à toutes les réponses de l'API REST.
