PMAPI(3) Manuel des fonctions de bibliothèque PMAPI(3)

NOM

PMAPI - Introduction à l'interface de programmation d'applications de métriques de performance

SYNTAXE C

#include <pcp/pmapi.h>

... diverses routines ...

cc ... -lpcp

DESCRIPTION

Dans le cadre du Performance Co-Pilot (PCP), les applications clientes sont développées en utilisant l'interface de programmation d'applications de métriques de performance (PMAPI) qui définit une interface procédurale avec des services adaptés au développement d'applications particulièrement intéressées par les métriques de performance.

Cette description présente un aperçu de la PMAPI et du contexte dans lequel les applications PMAPI sont exécutées. La PMAPI est décrite plus en détail dans le Guide du programmeur du Performance Co-Pilot, et dans les pages de manuel des routines individuelles de la PMAPI.

MÉTRIQUES DE PERFORMANCE - NOMS ET IDENTIFIANTS

Pour une description de l'espace de noms des métriques de performance (PMNS) et des termes et concepts associés, voir PCPIntro(1).

Tous les PMID n'ont pas besoin d'être représentés dans le PMNS de chaque application. Par exemple, une application qui surveille le trafic disque utilisera probablement un espace de noms qui ne référence que les PMID pour les statistiques d'E/S.

Les applications qui utilisent la PMAPI peuvent avoir des versions indépendantes d'un PMNS, construites à partir d'un fichier d'initialisation au démarrage de l'application ; voir pmLoadASCIINameSpace(3), pmLoadNameSpace(3), et PMNS(5).

En interne (sous la PMAPI), l'implémentation du système de collecte de métriques de performance (PMCS) utilise uniquement les PMID, et un PMNS fournit un mappage externe d'une taxonomie hiérarchique de noms vers des PMID qui est pratique dans le contexte d'un système particulier ou d'une utilisation particulière de la PMAPI. Pour le programmeur d'applications, les routines pmLookupName(3) et pmNameID(3) effectuent la traduction entre les noms dans un PMNS et les PMID, et vice versa. Le PMNS peut être parcouru en utilisant pmGetChildren(3) et pmTraversePMNS. Les fonctions pmFetchGroup(3) combinent les opérations de recherche de noms de métriques, de récupération et de conversion.

CONTEXTE PMAPI

Une application utilisant la PMAPI peut manipuler plusieurs contextes simultanés, chacun associé à une source de métriques de performance, par exemple pmcd(1) sur un hôte donné, ou un ensemble d'archives de métriques de performance telles que créées par pmlogger(1).

Les contextes sont identifiés par un « handle », une petite valeur entière qui est retournée lors de la création du contexte ; voir pmNewContext(3) et pmDupContext(3). Certaines fonctions de la PMAPI nécessitent un « handle » explicite pour identifier le contexte correct, mais plus communément la fonction PMAPI est exécutée dans le contexte « courant ». Le contexte courant peut être découvert en utilisant pmWhichContext(3) et modifié en utilisant pmUseContext(3).

Si un contexte PMAPI n'a pas été explicitement établi (ou si le contexte courant précédent a été fermé en utilisant pmDestroyContext(3)), alors le contexte PMAPI courant est indéfini.

En plus de la source des métriques de performance, le contexte inclut également le profil d'instance et le temps de collecte (tous deux décrits ci-dessous) qui contrôle la quantité d'informations retournées, et quand les informations ont été collectées.

DOMAINES D'INSTANCES

Lorsque les valeurs des métriques de performance sont retournées via la PMAPI à une application demandeuse, il peut y avoir plusieurs valeurs pour une métrique particulière. Des valeurs multiples, ou instances, pour une seule métrique résultent généralement de l'instrumentation implémentée pour chaque instance d'un ensemble de composants ou services similaires dans un système, par exemple des compteurs indépendants pour chaque CPU, ou chaque processus, ou chaque disque, ou chaque type d'appel système, etc. Cette multiplicité de valeurs n'est pas énumérée dans l'espace de noms mais, lorsque les métriques de performance sont délivrées via la PMAPI par pmFetch(3), le format du résultat prend en compte les valeurs pour une ou plusieurs instances, avec un couple instance-valeur codant la valeur de la métrique pour une instance particulière.

Les instances sont identifiées par un identifiant interne attribué par l'agent responsable de l'instanciation des valeurs pour la métrique de performance associée. Chaque identifiant d'instance a un nom d'identifiant d'instance externe correspondant (une chaîne ASCII). Les routines pmGetInDom(3), pmLookupInDom(3) et pmNameInDom(3) peuvent être utilisées pour énumérer tous les identifiants d'instance, et pour traduire entre les identifiants d'instance internes et externes.

Tous les identifiants d'instance pour une métrique de performance particulière sont collectivement appelés un domaine d'instance. Plusieurs métriques de performance peuvent partager le même domaine d'instance.

Si une seule instance est jamais disponible pour une métrique de performance particulière, l'identifiant d'instance dans le résultat de pmFetch(3) prend la valeur spéciale PM_IN_NULL et peut être ignoré par l'application, et un seul couple instance-valeur apparaît dans le résultat pour cette métrique. Dans ces circonstances, le domaine d'instance associé (tel que retourné via pmLookupDesc(3)) est défini sur PM_INDOM_NULL pour indiquer que les valeurs pour cette métrique sont singulières.

La question difficile des métriques de performance transitoires (par exemple, les informations par système de fichiers, les modules matériels remplaçables à chaud, etc.) implique que des requêtes répétées pour le même PMID peuvent retourner un nombre différent de valeurs, et/ou des changements dans les identifiants d'instance particuliers retournés. Cela signifie que les applications doivent être conscientes que l'instanciation des métriques n'est garantie d'être valide qu'au moment de la collecte. Des règles similaires s'appliquent aux sémantiques transitoires des valeurs de métriques associées. En général, cependant, il est attendu que la majorité des métriques de performance auront des sémantiques d'instanciation qui sont fixes pendant la durée d'exécution de tout client PMAPI.

LE TYPE DES VALEURS DE MÉTRIQUES

La PMAPI prend en charge un large éventail d'encodages de format et de type pour les valeurs des métriques de performance, à savoir les entiers signés et non signés, les nombres à virgule flottante, les encodages 32 bits et 64 bits de tous les éléments ci-dessus, les chaînes ASCII (style C, terminées par un octet NULL), et les agrégats arbitraires de données binaires.

Le champ type dans la structure pmDesc retournée par pmLookupDesc(3) identifie le format et le type des valeurs pour une métrique de performance particulière dans un contexte PMAPI particulier.

Notez que l'encodage des valeurs pour une métrique de performance particulière peut être différent pour différents contextes PMAPI, en raison des différences dans l'implémentation sous-jacente pour différents contextes. Cependant, il est attendu que la grande majorité des métriques de performance auront un encodage de valeur cohérent sur toutes les versions de toutes les implémentations, et donc sur tous les contextes PMAPI.

La PMAPI prend en charge des routines pour automatiser la gestion des divers formats et types de valeurs, en particulier pour le cas courant où une conversion vers un format canonique est souhaitée, voir pmExtractValue(3) et pmPrintValue(3).

LA DIMENSIONALITÉ ET L'ÉCHELLE DES VALEURS DE MÉTRIQUES

Indépendamment de la façon dont la valeur est encodée, la valeur d'une métrique de performance est supposée provenir d'un ensemble de valeurs qui peuvent être décrites en termes de leur dimensionalité et de leur échelle par un codage compact comme suit. La dimensionalité est définie par une puissance, ou un indice, dans chacune des 3 dimensions orthogonales, à savoir Espace, Temps et Compte (ou Événements, qui sont sans dimension). Par exemple, le débit d'E/S pourrait être représenté comme Espace/Temps, tandis que le total courant des appels système est Compte, l'allocation mémoire est Espace et le temps de service moyen est Temps/Compte. LA DIMENSIONALITÉ ET L’ÉCHELLE DES VALEURS DE MESURE

There are a number of common scale values that may be used to better encode ranges that might otherwise exhaust the precision of a 32-bit value. This information is encoded in the pmUnits structure which is embedded in the pmDesc structure returned from pmLookupDesc(3).

The routine pmConvScale(3) is provided to convert values in conjunction with the pmUnits structures that defines the dimensionality and scale of the values for a particular performance metric as returned from pmFetch(3), and the desired dimensionality and scale of the value the PMAPI client wishes to manipulate. Alternatively, the pmFetchGroup(3) functions can perform data format and unit conversion operations, specified by textual descriptions of desired unit / scales.

PROFIL D’INSTANCE

The set of instances for performance metrics returned from a pmFetch(3) call may be filtered or restricted using an instance profile. There is one instance profile for each PMAPI context the application creates, and each instance profile may include instances from one or more instance domains.

The routines pmAddProfile(3) and pmDelProfile(3) may be used to dynamically adjust the instance profile.

TEMPS DE COLLECTE

For each set of values for performance metrics returned via pmFetch(3) there is an associated ``timestamp'' that serves to identify when the performance metric values were collected; for metrics being delivered from a real-time source (i.e. pmcd(1) on some host) this would typically be not long before they were exported across the PMAPI, and for metrics being delivered from a set of archives, this would be the time when the metrics were written into the archive.

There is an issue here of exactly when individual metrics may have been collected, especially given their origin in potentially different Performance Metric Domains, and variability in the metric updating frequency at the lowest level of the Performance Metric Domain. The PMCS opts for the pragmatic approach, in which the PMAPI implementation undertakes to return all of the metrics with values accurate as of the timestamp, to the best of our ability. The belief is that the inaccuracy this introduces is small, and the additional burden of accurate individual timestamping for each returned metric value is neither warranted nor practical (from an implementation viewpoint).

Of course, in the case of collection of metrics from multiple hosts the PMAPI client must assume the sanity of the timestamps is constrained by the extent to which clock synchronization protocols are implemented across the network.

A PMAPI application may call pmSetMode(3) to vary the requested collection time, e.g. to rescan performance metrics values from the recent past, or to ``fast-forward'' through a set of archives.

PROBLÈMES GÉNÉRAUX DU STYLE DE PROGRAMMATION PMAPI

Across the PMAPI, all arguments and results involving a ``list of something'' are declared to be arrays with an associated argument or function value to identify the number of elements in the list. This has been done to avoid both the varargs(3) approach and sentinel-terminated lists.

Where the size of a result is known at the time of a call, it is the caller's responsibility to allocate (and possibly free) the storage, and the called function will assume the result argument is of an appropriate size. Where a result is of variable size and that size cannot be known in advance (e.g. for pmGetChildren(3), pmGetInDom(3), pmNameInDom(3), pmNameID(3), pmLookupLabels(3), pmLookupText(3) and pmFetch(3)) the PMAPI implementation uses a range of dynamic allocation schemes in the called routine, with the caller responsible for subsequently releasing the storage when no longer required. In some cases this simply involves calls to free(3), but in others (most notably for the result from pmFetch(3)), special routines (e.g. pmFreeResult(3) and pmFreeLabelSets(3)) should be used to release the storage.

As a general rule, if the called routine returns an error status then no allocation will have been done, and any pointer to a variable sized result is undefined.

DIAGNOSTICS

Where error conditions may arise, the functions that comprise the PMAPI conform to a single, simple error notification scheme, as follows;

+
the function returns an integer
+
values >= 0 indicate no error, and perhaps some positive status, e.g. the number of things really processed
+
values < 0 indicate an error, with a global table of error conditions and error messages

The PMAPI routine pmErrStr(3) translates error conditions into error messages. By convention, the small negative values are assumed to be negated versions of the Unix error codes as defined in <errno.h> and the strings returned are as per strerror(3). The larger, negative error codes are PMAPI error conditions.

One error, common to all PMAPI routines that interact with pmcd(1) on some host is PM_ERR_IPC, which indicates the communication link to pmcd(1) has been lost.

APPLICATIONS MULTITHREADÉES

The original design for PCP was based around single-threaded applications, or more strictly applications in which only one thread was ever expected to call the PCP libraries. This restriction has been relaxed for libpcp to allow the most common PMAPI routines to be safely called from any thread in a multi-threaded application.

However the following groups of functions and services in libpcp are still restricted to being called from a single-thread, and this is enforced by returning PM_ERR_THREAD when an attempt to call the routines in each group from more than one thread is detected.

1.
Any use of a PM_CONTEXT_LOCAL context, as the DSO PMDAs that are called directly from libpcp may not be thread-safe.

ENVIRONNEMENT PCP

Most environment variables are described in PCPIntro(1). In addition, environment variables with the prefix PCP_ are used to parameterize the file and directory names used by PCP. On each installation, the file /etc/pcp.conf contains the local values for these variables. The $PCP_CONF variable may be used to specify an alternative configuration file, as described in pcp.conf(5). Values for these variables may be obtained programmatically using the pmGetConfig(3) function.
