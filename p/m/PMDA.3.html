PMDA(3) Manuel des fonctions de bibliothèque PMDA(3)

NOM

PMDA - introduction à la bibliothèque de support des agents de domaine de métriques de performance

SYNTAXE C

#include <pcp/pmapi.h>
#include <pcp/pmda.h>

... diverses routines ...

cc ... -lpcp_pmda -lpcp

DESCRIPTION

Pour aider au développement des agents de domaine de métriques de performance (PMDAs) pour le Collecteur de performance (PCP), une interface procédurale est fournie qui étend la bibliothèque de l'interface de programmation d'applications de métriques de performance (PMAPI(3)). Ces procédures sont conçues pour permettre à un programmeur de construire rapidement un PMDA qui peut ensuite être testé et affiné. Cependant, cela implique également qu'un PMDA a une structure particulière qui peut ne pas convenir à toutes les implémentations de PMDA.

Une fois que vous êtes familiarisé avec les frameworks PCP et PMDA, vous pouvez rapidement implémenter un nouveau PMDA avec seulement quelques structures de données et fonctions. Ceci est couvert de manière beaucoup plus détaillée dans le Guide du programmeur du Collecteur de performance.

Un PMDA est responsable d'un ensemble de métriques de performance, dans le sens où il doit répondre aux demandes de pmcd(1) concernant les informations sur les métriques de performance, les domaines d'instances et les valeurs instanciées.

Cette page de manuel contient des sections du PMDA simple qui est situé dans $PCP_PMDAS_DIR/simple.

COMMUNICATION AVEC PMCD

Deux approches peuvent être utilisées pour connecter un PMDA à un processus pmcd(1). Un objet partagé dynamique (DSO) peut être attaché par pmcd(1) en utilisant dlopen(3) lorsque le processus pmcd(1) est démarré. Une interface procédurale référencée via une structure de données partagée est utilisée pour gérer les requêtes de pmcd(1) vers le PMDA.

L'approche préférée est qu'un processus séparé (démon) communique avec pmcd(1) en utilisant le protocole de communication inter-processus (IPC) des Unités de Données de Performance (PDU).

Tous les PMDA sont lancés et contrôlés par le processus pmcd(1) sur l'hôte local. Les requêtes des clients sont reçues par pmcd(1) et transmises aux PMDA appropriés. Les réponses, lorsqu'elles sont nécessaires, sont renvoyées via pmcd(1) aux clients. Les requêtes (PDU) qui peuvent être envoyées à un PMDA depuis pmcd(1) sont PDU_FETCH, PDU_PROFILE, PDU_INSTANCE_REQ, PDU_DESC_REQ, PDU_TEXT_REQ et PDU_RESULT. Si le PMDA implémente des métriques dynamiques, il peut également recevoir les PDU PDU_PMNS_CHILD, PDU_PMNS_IDS, PDU_PMNS_NAMES et PDU_PMNS_TRAVERSE.

CALLBACKS PAR DÉFAUT POUR LA GESTION DES PDU

Pour permettre un framework cohérent, pmdaMain(3) peut être utilisé par un PMDA démon pour gérer le protocole de communication en utilisant les mêmes callbacks qu'un PMDA DSO. La structure pmdaInterface est utilisée pour transmettre l'interface procédurale commune et les informations d'état utilisées par pmcd(1) et un PMDA. Ces informations d'état incluent des tables décrivant les métriques et les domaines d'instances pris en charge.

Comme la plupart de l'interface procédurale est identique pour tous les PMDA, elles sont fournies dans le cadre de cette bibliothèque de support (pmdaProfile(3), pmdaFetch(3), pmdaInstance(3), pmdaDesc(3), pmdaText(3) et pmdaStore(3)). Cependant, ces routines nécessitent l'accès aux informations d'état de pmdaInterface, elles doivent donc être correctement initialisées à l'aide de pmdaConnect(3), pmdaDaemon(3), pmdaOpenLog(3), pmdaDSO(3), pmdaGetOpt(3) et pmdaInit(3).

INSTANCES ET DOMAINES D'INSTANCES

Trois structures sont déclarées dans /usr/include/pcp/pmda.h qui fournissent un cadre pour la déclaration des métriques et des instances prises en charge par le PMDA.

Chaque instance nécessite un identifiant entier unique et un nom unique, tels que définis par la structure pmdaInstid :

/*
 * Description de l'instance : index et nom
 */
typedef struct {
    int         i_inst;        /* identifiant interne de l'instance */
    char        *i_name;       /* identifiant externe de l'instance */
} pmdaInstid;

Un domaine d'instance nécessite sa propre identification unique (pmInDom), le nombre d'instances que le domaine représente, et un pointeur vers un tableau de descriptions d'instances. Ceci est défini dans la structure pmdaIndom :

/*
 * Description du domaine d'instance : identifiant d'instance unique,
 * nombre d'instances dans ce domaine et la liste des
 * instances (non terminées par null).
 */
typedef struct {
    pmInDom     it_indom;       /* indom, rempli */
    int         it_numinst;     /* nombre d'instances */
    pmdaInstid  *it_set;        /* identifiants d'instance */
} pmdaIndom;

Le PMDA simple a un domaine d'instance pour simple.color avec trois instances (red, green et blue), et un second domaine d'instance pour simple.now avec des instances qui peuvent être spécifiées à l'exécution. Ces domaines d'instances sont définis comme suit :

static pmdaInstid _color[] = {
    { 0, "red" }, { 1, "green" }, { 2, "blue" }
};
static pmdaInstid *_timenow = NULL;
static pmdaIndom indomtab[] = {
#define COLOR_INDOM	0
    { COLOR_INDOM, 3, _color },
#define NOW_INDOM 1
    { NOW_INDOM, 0, NULL },
};

Les macros préprocesseur COLOR_INDOM et NOW_INDOM sont utilisées dans la table de description des métriques pour identifier les domaines d'instances des métriques individuelles. Celles-ci correspondent à la valeur serial dans la structure du domaine d'instance pmInDom (le champ domain est défini par pmdaInit(3) à l'exécution). La valeur de série doit être unique pour chaque domaine d'instance au sein du PMDA.

Le tableau indom montré ci-dessus qui est généralement passé à pmdaInit(3) n'a pas besoin d'être créé si l'on souhaite écrire ses propres fonctions Fetch et Instance. Voir pmdaInit(3) pour plus de détails.

ESPACE DE NOMS

Chaque PMDA a son propre espace de noms unique utilisant le format défini dans PMNS(5). En résumé, l'espace de noms associe les noms des métriques à l'identifiant unique. Le PMDA simple définit cinq métriques : simple.numfetch, simple.color, simple.time.user, simple.time.sys et simple.now. L'espace de noms pour ces métriques est défini dans $PCP_PMDAS_DIR/simple/pmns et est installé comme suit :

simple {
    numfetch    253:0:0
    color       253:0:1
    time
    now         253:2:4
}
simple.time {
    user        253:1:2
    sys         253:1:3
}

Le numéro de domaine 253 est obtenu à partir de $PCP_VAR_DIR/pmns/stdpmid. Les nouveaux PMDA doivent spécifier un numéro de domaine unique dans ce fichier et obtenir le numéro lors de l'installation. Cela permet au numéro de domaine de changer en modifiant uniquement le fichier $PCP_VAR_DIR/pmns/stdpmid.

Les métriques simple.time et simple.now sont définies dans des clusters séparés des autres métriques, ce qui permet à un PMDA de prendre en charge plus de 1024 métriques, ainsi que de regrouper des métriques similaires. Par conséquent, les numéros d'éléments d'un nouveau cluster peuvent être identiques aux numéros d'éléments d'autres clusters. Le PMDA simple continue d'incrémenter les numéros d'éléments pour permettre un mappage direct (voir pmdaInit(3)).

Le fichier d'espace de noms doit être installé et supprimé avec l'agent en utilisant pmnsadd(1) et pmnsdel(1). Voir les sections ultérieures sur INSTALLATION et SUPPRESSION.

Un espace de noms ASCII simple peut être construit en créant un fichier similaire à $PCP_PMDAS_DIR/simple/root :

/*
 * Faux "root" pour valider le sous-arbre PMNS local
 */
#include "$PCP_VAR_DIR/pmns/stdpmid"

DESCRIPTIONS DE METRIQUES

Chaque métrique nécessite une description (pmDesc), qui contient son identifiant de métrique PCP (PMID), les spécifications du type de données, le domaine d'instances, la sémantique et les unités (voir pmLookupDesc(3)). Un handle pour des informations spécifiques à l'application est également fourni dans la structure pmdaMetric :

/*
 * Description de métrique : handle pour étendre la description,
 * et la description.
 */
typedef struct {
    void*       m_user;         /* pour une utilisation externe par l'utilisateur */
    pmDesc      m_desc;         /* description de métrique */
} pmdaMetric;

Le PMDA simple définit les métriques comme suit :

static pmdaMetric metrictab[] = {
/* numfetch */
    { (void *)0,
      { PMDA_PMID(0,0), PM_TYPE_U32, PM_INDOM_NULL, PM_SEM_INSTANT,
        { 0,0,0,0,0,0 } }, },
/* color */
    { (void *)0,
      { PMDA_PMID(0,1), PM_TYPE_32, COLOR_INDOM, PM_SEM_INSTANT,
        { 0,0,0,0,0,0 } }, },
/* time.user */
    { (void*)0,
      { PMDA_PMID(1,2), PM_TYPE_DOUBLE, PM_INDOM_NULL, PM_SEM_COUNTER,
      	{ 0, 1, 0, 0, PM_TIME_SEC, 0 } }, },
/* time.sys */
    { (void*)0,
      { PMDA_PMID(1,3), PM_TYPE_DOUBLE, PM_INDOM_NULL, PM_SEM_COUNTER,
      	{ 0, 1, 0, 0, PM_TIME_SEC, 0 } }, },
/* now */
    { NULL,
      { PMDA_PMID(2,4), PM_TYPE_U32, NOW_INDOM, PM_SEM_INSTANT,
        { 0,0,0,0,0,0 } }, },
};

La macro PMDA_PMID (définie dans /usr/include/pcp/pmda.h) est utilisée pour spécifier les champs cluster et item du pmID associé. Comme pour les domaines d'instance, le domaine est défini par pmdaInit(3) à l'exécution, bien que la valeur par défaut soit le domaine défini par le PMDA dans la macro MYDOMAIN.

Le tableau des métriques montré ci-dessus, qui est généralement passé à pmdaInit(3), n'a pas besoin d'être créé si vous écrivez votre propre fonction Fetch et Descriptor. Voir pmdaInit(3) pour plus de détails.

PMDA DSO

Un PMDA exécuté en tant que DSO est ouvert par pmcd(1) via dlopen(3). pmcd(1) appellera la fonction d'initialisation du PMDA spécifiée dans $PCP_PMCDCONF_PATH. Cette fonction reçoit un pointeur vers une structure pmdaInterface qui doit être complétée. Tous les callbacks autres que les callbacks par défaut de la bibliothèque de support du PMDA doivent être spécifiés dans la structure pmdaInterface.

Le PMDA simple utilise son propre store et fetch callback. simple_fetch() appelle pmdaFetch(3), qui nécessite qu'un callback soit défini avec pmdaSetFetchCallBack(3), comme on peut le voir dans $PCP_PMDAS_DIR/simple/simple.c.

Le flag _isDSO est utilisé pour déterminer si le PMDA est un démon ou un DSO, ainsi la routine d'initialisation correspondante, pmdaDaemon(3) ou pmdaDSO(3), est appelée.

PMDA Démon

Un PMDA exécuté en tant que démon est forké et exécuté par pmcd(1). Par conséquent, contrairement à un PMDA DSO, le point de départ d'un PMDA démon est main(). L'agent doit analyser les arguments de la ligne de commande, créer un fichier log et initialiser certaines structures de données que pmcd(1) initialiserait pour un agent DSO.

La structure pmdaInterface doit être entièrement définie par le PMDA démon. La fonction pmdaDaemon(3) peut être appelée au début de main() pour définir presque tous les champs. L'analyse des commandes peut être simplifiée en utilisant pmdaGetOpt(3), similaire à getopt(2), mais qui extrait un ensemble commun d'options dans la structure pmdaInterface. stderr peut être mappé à un fichier log en utilisant pmdaOpenLog(3) pour simplifier le débogage et les messages d'erreur. La connexion avec pmcd(1) peut être faite avec pmdaConnect(3), et la boucle qui gère les PDUs, pmdaMain(3), doit être la dernière fonction appelée. Ceci peut être vu dans $PCP_PMDAS_DIR/simple/simple.c.

La routine simple_init() est commune à un agent qui peut s'exécuter à la fois comme démon et comme PMDA DSO.

TEXTE D'AIDE

Chaque PMDA doit être capable de fournir à pmcd(1) le texte d'aide pour chaque métrique. Les PMDAs les plus courants utilisent des fichiers spécialisés avec des index pour permettre une récupération efficace de ce texte d'aide. Des outils sont fournis avec PCP pour créer des fichiers texte d'aide au format approprié. Voir newhelp(1).

INSTALLATION ET RETRAIT

Une série de procédures shell définies dans $PCP_SHARE_DIR/lib/pmdaproc.sh simplifient considérablement l'installation et le retrait d'un PMDA.

Les scripts d'installation Install de la plupart des PMDAs doivent seulement spécifier le nom du PMDA dans iam, appeler pmdaSetup qui définit quelques valeurs par défaut, vérifie les permissions (il faut être root pour installer ou retirer un PMDA), vérifie que vous êtes dans le bon répertoire (celui qui se termine par /pmdas/$iam), génère éventuellement les fichiers PMNS (Performance Metrics Name Space) et le domaine du PMDA pour les PMDAs Perl ou Python, vérifie que le numéro de domaine du PMDA est valide, etc., spécifie les protocoles de communication, puis appelle pmdaInstall pour effectuer tout le travail de mise à jour du PMNS, de mise à jour du fichier de configuration de pmcd(1), de notification ou de redémarrage de pmcd(1).

Au-delà de pmdaSetup et pmdaInstall, une autre routine optionnelle est pmdaChooseConfigFile qui peut être utilisée pour interagir de manière interactive pour sélectionner ou créer un fichier de configuration spécifique au PMDA, par exemple pmdalogger(1).

Les scripts de retrait Remove sont encore plus simples car il n'est pas nécessaire de définir les protocoles de communication, donc on définit le nom du PMDA dans iam, puis on appelle pmdaSetup suivi d'un appel à pmdaRemove.

Plus d'informations se trouvent dans le fichier $PCP_SHARE_DIR/lib/pmdaproc.sh et dans la section suivante.

Optionnellement, un PMDA peut fournir un script Upgrade en plus de Install et Remove. S'il est présent, ce script sera utilisé par le processus de démarrage de pmcd pour s'assurer que les corrections préalables ont été effectuées avant que le PMDA ne soit exécuté. Des exemples de telles corrections incluent les mises à jour de pmcd.conf lorsqu'un script ou un binaire de PMDA a été renommé, lorsque le PMDA supporte un nouveau format de son fichier de configuration, ou s'il y a un problème latent d'une installation précédente (par exemple, certains PMDAs peuvent avoir besoin d'introduire l'utilisation du mot-clé notready dans pmcd.conf, comme décrit ci-dessous).

RAFFINEMENTS D'INSTALLATION

Comme décrit ci-dessous, plusieurs variables peuvent être définies dans le script d'installation Install d'un PMDA pour influencer le comportement des procédures d'installation. Ces variables sont généralement définies avant l'appel à pmdaInstall, mais dans certains cas (comme $iam et les cas spécifiques signalés ci-dessous), avant l'appel à pmdaSetup.

Les variables suivantes contrôlent les options de communication entre le PMDA et pmcd(1). Au moins une des variables $daemon_opt, $dso_opt, $perl_opt ou $python_opt doit être définie pour spécifier les modes de communication supportés. Si plus d'une de ces options est définie, l'utilisateur sera invité lors de l'exécution du script d'installation à faire un choix.

daemon_opt
Nous sommes disposés à installer le PMDA en tant que démon.
Valeur par défaut : true
dso_opt
Nous sommes disposés à installer le PMDA en tant que DSO, de sorte que pmcd(1) utilisera le chargeur dynamique pour lier le PMDA à l'exécution et la communication de pmcd(1) avec le PMDA et vice versa utilisera des appels procéduraux, pas un canal IPC.
Valeur par défaut : false
dso_entry
Pour un PMDA DSO, il s'agit du nom de la routine d'initialisation du PMDA.
Valeur par défaut : ${iam}_init
dso_name
Pour un PMDA DSO, il s'agit du chemin d'accès complet au fichier DSO du PMDA.
Valeur par défaut : $PCP_PMDAS_DIR/$iam/pmda_$iam.$dso_suffix
pipe_opt
Pour un PMDA démon, le canal IPC par défaut est-il via un pipe(2) ?
Valeur par défaut : spécifié par le système d'exploitation, donc true pour la plupart, mais false pour Windows
perl_opt
Nous sommes disposés à installer le PMDA en tant que script Perl et pmcd(1) utilisera l'interpréteur perl(1) pour exécuter le PMDA.
Valeur par défaut : false
pmda_dir
Le chemin d'accès complet au répertoire où se trouveront les fichiers d'installation du PMDA (exécutable, script, source PMNS, source du texte d'aide, etc.).
Valeur par défaut : sortie de pwd(1)

Si défini, cela doit être fait avant l'appel à pmdaSetup.

pmda_name
Pour un PMDA démon, il s'agit du nom de l'exécutable du PMDA par rapport au répertoire $pmda_dir.
Valeur par défaut : pmda$iam
python_opt
Nous sommes disposés à installer le PMDA en tant que script Python et pmcd(1) utilisera l'interpréteur python(1) pour exécuter le PMDA.
Valeur par défaut : false
ipc_prot
Pour un PMDA démon, cela peut être défini sur binary ou text. La valeur par défaut est binary et text est rarement utilisé. De plus, un canal IPC optionnel peut être spécifié avec pipe(2)...

Si défini, cela doit être fait avant l'appel à pmdaSetup.

ameter notready peut être utilisé pour signifier que le PMDA démarrera dans l'état notready, par exemple ipc_prot="binary notready". Notez que les guillemets sont requis. Les paramètres IPC d'un PMDA apparaissent dans pmcd.conf dans la colonne IPC Params. Pour plus de détails, voir pmcd(1) mais en gros, pmcd n'émettra aucune requête à un PMDA qui a démarré dans l'état notready jusqu'à ce que le PMDA envoie une PDU PM_ERR_PMDAREADY. Cela permet aux PMDA ayant des temps de démarrage longs de s'initialiser correctement sans dépasser le délai imparti. Pour plus de détails, voir pmdaSendError(3) et pmcd(1). Lorsqu'un PMDA est dans l'état notready, toute requête client envoyée à pmcd pour le domaine PMDA retournera avec l'erreur PM_ERR_PMDANOTREADY.
socket_inet_def
Pour un PMDA démon utilisant un socket(2) comme canal IPC, le numéro de port Internet ou le nom de service par défaut (s'il est connu).
Par défaut : ""
socket_opt
Pour un PMDA démon, s'agit-il du canal IPC par défaut via un socket(2) ?
Par défaut : Spécifique à la plateforme, donc false pour la plupart, mais true pour Windows

Les variables suivantes contrôlent les options PMNS.

pmns_dupok
La plupart des PMDA n'ont pas de noms dupliqués pour le même PMID dans leur PMNS. Mais si ce n'est pas le cas, pmns_dupok doit être défini sur true.
Par défaut : false
pmns_name
Chaque PMDA ajoutera un ou plusieurs nœuds non-feuilles en haut du PMNS. Le cas le plus courant est que toutes les métriques d'un PMDA seront placées sous le nœud nommé $iam. Si ce n'est pas le cas, et en particulier lorsque le PMDA ajoute plus d'un nœud non-feuille en haut du PMNS, pmns_name doit être défini sur la liste des noms de nœuds (séparés par des espaces blancs), par exemple pour pmdaproc(1), pmns_name est défini sur "proc cgroup hotproc".
Par défaut : $iam

Il est très important que si pmns_name est défini sur une valeur non défaut dans le script Install, il doit également être défini sur la même valeur dans le script Remove.

pmns_source
Le nom du fichier source PMNS du PMDA. Par défaut, le nom est interprété comme un chemin relatif depuis le répertoire $pmda_dir.
Par défaut : pmns

Les variables suivantes fournissent diverses options supplémentaires associées à l'installation d'un PMDA.

args
Arguments de ligne de commande supplémentaires pour le PMDA. Ceux-ci seront ajoutés à la ligne de contrôle du PMDA dans $PCP_PMCDCONF_PATH.
Par défaut : ""
check_delay
Délai (en secondes) après l'achèvement de l'installation (ou de la suppression) du PMDA avant de vérifier la disponibilité des métriques du PMDA. Peut devoir être augmenté si le PMDA a une procédure de démarrage longue.
Par défaut : 0.3
signal_delay
Délai (en secondes) après la notification de pmcd(1) avec un signal. Requis pour permettre à pmcd(1) de terminer le traitement avant de passer à l'étape suivante de l'installation (ou de la suppression).
Par défaut : 1
configdir
Détermine le répertoire dans lequel le fichier de configuration d'un PMDA sera stocké. Utilisé par pmdaChooseConfigFile, il doit donc être défini avant d'appeler cette procédure.
Par défaut : $PCP_VAR_DIR/config/$iam
configfile
Fichier de configuration préféré pour le PMDA. Utilisé par pmdaChooseConfigFile, il doit donc être défini avant d'appeler cette procédure.
Par défaut : ""
default_configfile
Fichier de configuration par défaut pour le PMDA. Utilisé par pmdaChooseConfigFile, il doit donc être défini avant d'appeler cette procédure.
Par défaut : ""
dso_suffix
Suffixe standard pour un DSO. Ne devrait pas nécessiter de modification dans des circonstances normales.
Par défaut : Spécifique à la plateforme, donc 'so' pour Linux, 'dylib' pour macOS, 'dll' pour Windows, etc.

Si défini, cela doit être fait avant l'appel à pmdaSetup.

help_source
Le nom du fichier source du texte d'aide qui doit être utilisé comme entrée pour pmnewhelp(1). Par défaut, le nom est interprété comme un chemin relatif depuis le répertoire $pmda_dir.
Par défaut : help
python_name
Chemin d'accès complet du script Python pour un PMDA Python.
Par défaut : $pmda_dir/pmda$iam.python ou $pmda_dir/pmda$iam.py

Les procédures shell dans $PCP_SHARE_DIR/lib/pmdaproc.sh manipulent un certain nombre de fichiers temporaires en utilisant la variable $tmp comme préfixe pour le nom des fichiers temporaires. $tmp est un répertoire qui est créé, utilisé et supprimé en interne dans les procédures de $PCP_SHARE_DIR/lib/pmdaproc.sh mais peut également être utilisé comme préfixe pour les fichiers temporaires nécessaires aux scripts Install ou Remove d'un PMDA. Lorsqu'il est utilisé de cette manière, $tmp doit être suivi d'un « / » puis d'un suffixe, par exemple $tmp/myfoo. Les scripts Install et Remove ne doivent pas utiliser d'autres préfixes de noms de fichiers temporaires ni utiliser de instructions trap de sh(1) pour nettoyer les fichiers temporaires, car tout cela est géré dans $PCP_SHARE_DIR/lib/pmdaproc.sh.

MISE EN GARDE

Omettre de remplir l'une des structures de données ou d'appeler l'une des routines de bibliothèque dans le désordre peut entraîner un comportement inattendu dans le PMDA.

En raison des modifications apportées aux API PMAPI(3) et PMDA(3) dans la version 2.0 de PCP, comme décrit dans les notes de publication du produit, les PMDA construits à l'aide de PCP 2.0 doivent spécifier PMDA_INTERFACE_2 ou une version ultérieure et être liés avec libpcp_pmda.so.2 et libpcp.so.2. Les PMDA démon préexistants spécifiant PMDA_INTERFACE_1 continueront de fonctionner en utilisant les bibliothèques rétrocompatibles libpcp_pmda.so.1 et libpcp.so.1 et peuvent être recompilés en utilisant les en-têtes installés dans /usr/include/pcp1.x/ sans aucune modification. Ces en-têtes et bibliothèques rétrocompatibles sont contenus dans le sous-système pcp.sw.compat.

DIAGNOSTICS

Tout PMDA qui utilise cette bibliothèque peut activer l'option de contrôle de débogage PMAPI(3) libpmda (avec -Dlibpmda sur la ligne de commande ou via 3pmSetDebug(3)) pour afficher des informations de débogage qui peuvent être utiles pendant le développement (voir pmdbg(1)).

Le champ status de la structure pmdaInterface doit être zéro après l'appel de pmdaDaemon, pmdaDSO, pmdaGetOpt, pmdaConnect et pmdaInit. Une valeur inférieure à zéro indique que l'initialisation a échoué.

Certains messages d'erreur courants à la plupart des fonctions de cette bibliothèque sont les suivants :

Version de l'interface PMDA interface non prise en charge
La plupart des fonctions exigent que le champ comm.version de la structure pmdaInterface soit défini sur PMDA_INTERFACE_2 ou une version ultérieure. PMDA_INTERFACE_2 ou PMDA_INTERFACE_3 implique que les champs version.two sont correctement initialisés, tandis que PMDA_INTERFACE_4 implique que les champs version.four sont correctement initialisés (voir pmdaDaemon(3) et pmdaDSO(3)).

ENVIRONNEMENT PCP

Les variables d'environnement avec le préfixe PCP_ sont utilisées pour paramétrer les noms de fichiers et de répertoires utilisés par PCP. Lors de chaque installation, le fichier /etc/pcp.conf contient les valeurs locales pour ces variables. La variable $PCP_CONF peut être utilisée pour spécifier un fichier de configuration alternatif, comme décrit dans pcp.conf(5). Les valeurs de ces variables peuvent être obtenues par programme en utilisant la fonction pmGetConfig(3).
