PHYSFS_EnumerateCallback

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'elle peut renvoyer un résultat de rappel : par exemple, si vous recherchez quelque chose de spécifique, une fois trouvé, vous pouvez dire à PhysicsFS d'arrêter l'énumération. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir correctement implémenté. :)

Paramètres

data Un pointeur de données personnalisé, passé par l'API qui a finalement appelé la fonction de rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé l'énumération, passé dans la fonction de rappel pour votre commodité.
fname Le nom du fichier qui est énuméré. Il ne sera pas trié par ordre alphabétique par rapport à d'autres fonctions de rappel qui ont été appelées, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retour

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

Définition de void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonctions de rappel qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; cela vous donne plus de contrôle sur le processus.

Celles-ci sont utilisées pour signaler une liste d'entrées de répertoire à un appelant d'origine, une entrée par appel de fonction de rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire des chaînes.

Ces fonctions de rappel sont utilisées, depuis PhysicsFS 1.1, comme alternative aux fonctions qui renvoient des listes qui doivent être libérées avec PHYSFS_freeList(). L'appel de fonction de rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes à l'avance.

Assurez-vous que le tri des données promis dans les versions de liste n'est pas nécessaire dans les versions de fonction de rappel. Vérifiez la documentation des API spécifiques, mais les chaînes ne seront pas nécessairement triées comme vous vous y attendez et vous pourriez recevoir des chaînes dupliquées.

enum PHYSFS_ErrorCode

Valeurs représentant des causes spécifiques d'échec. La plupart du temps, vous ne devriez vous soucier que si une opération a échoué, mais il y a des cas où vous prévoyez de gérer gracieusement une situation d'échec spécifique, c'est pourquoi nous fournissons des codes d'erreur spécifiques.

La plupart de ces erreurs sont un peu vagues, et la plupart ne sont pas des choses que vous pouvez corriger... s'il y a une erreur de permission, par exemple, la seule chose que vous pouvez faire est de transmettre cette information à l'utilisateur et de le laisser trouver comment la gérer. Dans la plupart de ces cas, votre programme devrait simplement se soucier d'avoir échoué à atteindre ses objectifs, et ne pas se soucier spécifiquement de pourquoi.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Plie" un point de code Unicode vers son équivalent en minuscules. (Ceci est pour un usage limité et avancé. Si vous ne voyez pas immédiatement un besoin pour cela, vous pouvez l'ignorer pour toujours.)

Il convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux sans équivalent en minuscules seront retournés sans conversion.

Note : Il peut y avoir plusieurs points de code retournés ! Par exemple, le caractère allemand eszett sera converti en deux points de code en minuscules, 's'. La théorie est que si vous fusionnez deux chaînes, l'une avec l'eszett et l'autre avec "SS", elles correspondront.

Attention

Quiconque a étudié Unicode connaît le problème du "i turc". Cette API ne le gère pas. Elle suppose que chaque lettre Unicode se comportera de manière "normale". Si vous ne savez pas de quoi il s'agit, vous pouvez ignorer ce problème pour la plupart du monde, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Le tampon où les valeurs des points de code pliés seront stockées. Il doit pointer vers un espace pour au moins 3 emplacements PHYSFS_uint32.

Retour

Le nombre de points de code qui ont été pliés. Sera entre 1 et 3.

int PHYSFS_close (PHYSFS_File * handle)

Ferme un descripteur de fichier PhysicsFS. Cet appel peut échouer si le système d'exploitation était en train de mettre en cache des écritures sur le support physique et qu'il a maintenant forcé ces écritures sur le support physique, mais qu'il ne peut pas stocker les données pour une raison quelconque. Dans ce cas, le descripteur reste ouvert. Un programme bien écrit devrait toujours vérifier la valeur de retour de l'appel à close() en plus de chaque appel à write() !

Paramètres

handle Le descripteur retourné par PHYSFS_open*().

Retour

Non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_deinit (void )

Désinitialise la bibliothèque PhysicsFS. Elle ferme tous les fichiers ouverts par PhysicsFS, vide les chemins de recherche et d'écriture, libère la mémoire et invalide tous les descripteurs de fichiers.

Note : Cet appel peut échouer s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent était en train de mettre en cache des écritures vers un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur a échoué, etc.). Il est généralement préférable de fermer tous les descripteurs en écriture avant d'appeler cette fonction afin de gérer une défaillance spécifique en douceur.

Une fois correctement désinitialisée, PHYSFS_init() peut être appelée à nouveau pour redémarrer le système. Tous les états par défaut de l'API sont restaurés à ce stade, à l'exception de tout allocateur personnalisé que vous auriez spécifié, qui survit entre les initialisations.

Retour

Non nul en cas de succès, zéro en cas d'erreur. Les détails de l'erreur peuvent être obtenus via PHYSFS_getLastError(). En cas d'erreur, l'état de PhysFS est indéterminé et probablement corrompu.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtener una lista de archivos de una carpeta de la ruta de búsqueda, utilizando una función de callback definida por el usuario, con errores reportados. Internamente, PHYSFS_enumerateFiles() solo llama a esta función y luego construye una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica, salvo cómo se presenta la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve un array, sino que llama a una función definida por el solicitante una vez por cada elemento en la ruta de búsqueda:

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Los elementos que se pasan a la función de callback no están garantizados en ningún orden específico. No se realiza ningún ordenamiento a este nivel, y si lo necesita, debe usar PHYSFS_enumerateFiles(), que garantiza el orden alfabético. Esta forma informa lo que se encuentra en cada archivo antes de pasar al siguiente. Incluso dentro de un solo archivo, no podemos garantizar el orden en que se descubren los datos. Cualquier orden que encuentre en estas devoluciones de llamada es pura suerte. No dependa de ello. Dado que recorre todos los archivos, puede recibir nombres de archivo duplicados.

Esta API y las funciones de callback son capaces de reportar errores. Antes de esta API, las funciones de callback tenían que aceptar cada elemento enumerado, incluso si solo buscaban un elemento específico y querían detenerse después, o si tenían un error grave y no podían notificar a nadie. Además, si PhysicsFS tenía un problema (error de disco o lo que fuera), no podía informarlo a la aplicación que lo llamaba, sino que simplemente omitía elementos o detenía la enumeración, y el llamador no sabría que se habían perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto completo de datos, y si quiere detener la enumeración temprano, su callback tiene el control. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su callback.

Parámetros

dir Carpeta, en notación independiente del sistema operativo, a enumerar.
c Función de callback para notificar sobre elementos de la ruta.
d Datos definidos por el solicitante que se pasan a la función de callback. Puede ser NULL.

Retorno

Distinto de cero en caso de éxito, cero en caso de error. Utilice PHYSFS_getLastErrorCode() para obtener el error específico. Si la función de callback devuelve PHYSFS_ENUM_STOP para detenerse temprano, esto se considera un éxito. Las funciones de callback que devuelven PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezca el código de error en PHYSFS_ERR_APP_CALLBACK.

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);

* We've got [y.sav].
* We've got [z.sav].

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añadir un archivo o directorio a la ruta de búsqueda. Si es un duplicado, el registro no se agrega de nuevo, incluso si el función es exitosa. No puedes añadir el mismo archivo a dos puntos de montaje diferentes: el control de duplicados se hace contra el archivo y no el punto de montaje.

Cuando montas un archivo, se lo añade a un sistema de archivos virtual... todos los archivos de todos los archivos montados se interpolan en una única jerarquía de archivos. Dos archivos montados en el mismo lugar (o un archivo con archivos que superponen otro punto de montaje) pueden tener archivos superpuestos: en ese caso, el archivo más antiguo en la ruta de búsqueda se selecciona, y los otros archivos no son accesibles por la aplicación. Esto permite usar archivos para reemplazar revisiones previas; puedes usar el mecanismo de montaje para colocar archivos en un punto específico en el árbol de archivos y prevenir superposiciones; es útil para mods descargables que puedan pisar datos de aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montar, lo cual es diferente de lo que se espera de los usuarios familiarizados con el concepto Unix de "montar". Además, más de un archivo puede ser montado en el mismo punto de montaje, o los puntos de montaje y los contenidos de los archivos pueden superponerse... el mecanismo de interpolación sigue funcionando así.

Se permite especificar un enlace simbólico a un archivo o directorio, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esta función solo se enfoca en enlaces simbólicos dentro del directorio o archivo montado.

mountPoint ubicación en el árbol interpolado donde se montará este archivo, en notación independiente de la plataforma. NULL o "" es equivalente a "/".
appendToPath no cero para appendear a la ruta de búsqueda, cero para preponer.

Retorna

No cero si se agregó a la ruta, cero en error (archivo inválido, directorio no encontrado, etc). Usa PHYSFS_getLastErrorCode() para obtener el error específico.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archivés contiennent des fichiers qui ne sont que des références à d'autres fichiers. Lors de l'ouverture d'un tel lien dans le système physique, le fichier auquel il fait référence sera ouvert de manière transparente.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous faire sortir des chemins de lecture et d'écriture, compromettant la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Remarque : ceci est davantage destiné au sandboxing des langages de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une bonne raison de créer un lien symbolique, vous ne devriez donc pas le désactiver, à moins que vous ne ressentiez un danger spécifique.

Les liens symboliques seront explicitement suivis lorsqu'il s'agit de noms de fichiers dans une notation indépendante du système d'exploitation. C'est-à-dire, lorsque vos chemins de recherche et d'écriture, etc., sont définis, les liens symboliques ne seront jamais suivis.

L'autorisation des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

int PHYSFS_setRoot(const char * archive, const char * subdir)

Make a subdirectory of an archive its root directory. This lets you narrow down the accessible files in a specific archive. For example, if you have x.zip with a file in y/z.txt, mounted to /a, if you call PHYSFS_setRoot("x.zip", "/y"), then the call PHYSFS_openRead("/a/z.txt") will succeed.

You can change an archive's root at any time, altering the interpolated file tree (depending on where paths shift, a different archive may be providing various files). If you set the root to NULL or "/", the archive will be treated as if no special root was set (as if the archive was just mounted normally).

Changing the root only affects future operations on pathnames; a file that was opened from a path that changed due to a setRoot will not be affected.

Setting a new root is not limited to archives in the search path; you may set one on the write dir, too, which might be useful if you have files open for write and thus can't change the write dir at the moment.

It is not an error to set a subdirectory that does not exist to be the root of an archive; however, no files will be visible in this case. If the missing directories end up getting created (a mkdir to the physical filesystem, etc) then this will be reflected in the interpolated tree.

archive dir/archive on which to change root.
subdir new subdirectory to make the root of this archive.

nonzero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error.

int PHYSFS_setSaneConfig(const char * organization, const char * appName, const char * archiveExt, int includeCdRoms, int archivesFirst)

Set up sane, default paths. Helper function.

The write dir will be set to the pref dir returned by

PHYSFS_getPrefDir(organization, appName)

, which is created if it doesn't exist.

The above is sufficient to make sure your program's configuration directory is separated from other clutter, and platform-independent.

The search path will be:

  • The Write Dir (created if it doesn't exist)
  • The Base Dir (PHYSFS_getBaseDir())
  • All found CD-ROM dirs (optionally)

These directories are then searched for files ending with the extension (archiveExt), which, if they are valid and supported archives, will also be added to the search path. If you specified "PKG" for (archiveExt), and there's a file named data.PKG in the base dir, it'll be checked. Archives can either be appended or prepended to the search path in alphabetical order, regardless of which directories they were found in. All archives are mounted in the root of the virtual file system ("/")

All of this can be accomplished from the application, but this just does it all for you. Feel free to add more to the search path manually, too.

Parameters

organization Name of your company/group/etc to be used as a dirname, so keep it small, and no-frills.
appName Program-specific name of your program, to separate it from other programs using PhysicsFS.

Do not specify the '.' char; If you want to look for ZIP files, specify "ZIP" and not ".ZIP" ... the archive search is case-insensitive.

You may want to specify zero and handle the disc setup yourself.
archivesFirst Non-zero to prepend the archives to the search path. Zero to append them. Ignored if !(archiveExt).

nonzero on success, zero on error. Use PHYSFS_getLastErrorCode() to obtain the specific error.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convertit une chaîne Latin1 en chaîne UTF-8. Les chaînes Latin1 ont 8 bits par caractère : un encodage "high ASCII" populaire.

Pour s'assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon dont la taille est le double de la taille du tampon source. UTF-8 étend les points de code Latin1 supérieurs à 127 de 1 à 2 octets, la chaîne peut donc s'agrandir dans certains cas.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Veuillez noter que nous ne fournissons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer la plupart des points de code Unicode. C'est un encodage hérité ; vous devriez toujours vous en éloigner.

dst Tampon pour stocker la chaîne UTF-8 convertie.
