PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'elle peut retourner un résultat depuis le callback : notamment, si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous avons espérons bien fait cette fois-ci. :)

Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent des fichiers.

Attention

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; il vous donne plus de contrôle sur le processus.

Ils sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de ces chaînes.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le cas dans les versions de callback. Vérifiez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous l'attendez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data Pointeur de données défini par l'utilisateur, transmis depuis l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être dans un ordre alphabétique par rapport aux autres callbacks qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

typedef void(* physfs_StringCallback) (void *data, const char *str)

Signature de fonction pour les callbacks qui rapportent des chaînes. Ils sont utilisés pour signaler une liste de chaînes à un appelant d'origine, une chaîne par callback. int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenez une liste de fichiers du répertoire du chemin de recherche, en utilisant un rappel défini par l'application, avec des erreurs signalées. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique, sauf pour la façon dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés au rappel ne sont garantis dans aucun ordre. Il n'y a pas de tri effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme rapporte ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons pas garantir l'ordre dans lequel les données seront découvertes. Tout tri que vous trouverez dans ces rappels est purement un hasard. N'y comptez pas. Comme cela parcourt toute la liste des archives, vous pourriez recevoir des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble de données complet, et son rappel a le contrôle s'il veut que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement de votre rappel.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées au rappel. Peut être NULL.

Retourne

non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel retourne PHYSFS_ENUM_STOP pour s'arrêter tôt, cela sera considéré comme un succès. Les rappels retournant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

char **PHYSFS_enumerateFiles (const char * dir)

Obtenez une liste de fichiers du répertoire du chemin de recherche.

Attention

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction retournait autant d'éléments que possible face à une condition d'échec (manque de mémoire, erreur d'entrée/sortie disque, etc.). Puisque cela impliquait que les applications ne pouvaient pas distinguer entre un succès complet et un échec partiel, et comme la fonction pouvait toujours retourner NULL pour signaler des échecs catastrophiques de toute façon, dans PhysicsFS 2.1 la politique de cette fonction a changé : elle retournera soit une liste de résultats complets, soit NULL pour tout échec de quelque nature que ce soit, afin que nous puissions garantir que l'énumération s'est déroulée jusqu'à son terme et n'a pas de lacunes dans ses résultats.

Les répertoires correspondants sont interpolés. C'est-à-dire, si "C:\mydir" se trouve dans le chemin de recherche et contient un répertoire "savegames" qui contient "x.sav", "y.sav", et "z.sav", et qu'il y a aussi un "C:\userdir" dans le chemin de recherche qui a un sous-répertoire "savegames" avec "w.sav", alors le code suivant :

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi
N'hésitez pas à trier la liste comme bon vous semble. Cependant, les données retournées ne contiendront jamais de doublons et seront toujours triées par ordre alphabétique (ou plutôt, Unicode sensible à la casse) pour vous.
N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur de retour de cette fonction lorsque vous avez terminé.

void PHYSFS_permitSymbolicLinks(int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné à la mise en bac à sable du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lorsqu'il s'agit de noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés via cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

int PHYSFS_registerArchiveLayer(PHYSFS_Archiver *archives)

Enregistre une nouvelle couche d'archive. PhysicsFS est une bibliothèque de systèmes de fichiers virtuels. Les archives sont des fichiers qui contiennent d'autres fichiers. Ces archives sont souvent liées à des formats spécifiques (par exemple, les fichiers .zip, .lha, etc.). PhysicsFS peut lire ces formats via des "couches d'archives". Les couches d'archives sont essentiellement des bibliothèques dynamiques qui implémentent l'interface PHYSFS_Archiver. La fonction PHYSFS_registerArchiveLayer() enregistre ces couches. Il est important de noter que PhysicsFS n'essaie de charger les archives qu'une fois par chemin de recherche. Si vous avez plusieurs archives du même type, seul le premier sera réellement chargé.

Ceci est une fonction interne à PhysicsFS et ne devrait généralement pas être appelée par le code de l'application. Cependant, si vous implémentez votre propre système de fichiers pour PhysicsFS, vous voudrez peut-être le faire.

Paramètres

archives un tableau de pointeurs vers des structures PHYSFS_Archiver. Le dernier élément du tableau doit être un pointeur NULL.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 expands latin1 codepoints over 127 from 1 to 2 bytes, so the string may grow in some cases.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-8 sequence at the end. If the buffer length is 0, this function does nothing.

Please note that we do not supply a UTF-8 to Latin1 converter, since Latin1 can't express most Unicode codepoints. It's a legacy encoding; you should be converting away from it at all times.

int PHYSFS_utf8stricmp (const char * str1, const char * str2)

Case-insensitive compare of two UTF-8 strings. This is a strcasecmp/stricmp replacement that expects both strings to be in UTF-8 encoding. It will do "case folding" to decide if the Unicode codepoints in the strings match.

If both strings are exclusively low-ASCII characters, this will do the right thing, as that is also valid UTF-8. If there are any high-ASCII chars, this will not do what you expect!

It will report which string is "greater than" the other, but be aware that this doesn't necessarily mean anything: 'a' may be "less than" 'b', but a Japanese kuten has no meaningful alphabetically relationship to a Greek lambda, but being able to assign a reliable "value" makes sorting algorithms possible, if not entirely sane. Most cases should treat the return value as "equal" or "not equal".

Like stricmp, this expects both strings to be NULL-terminated.

Parameters

str1 First string to compare.
str2 Second string to compare.

Returns

-1 if str1 is "less than" str2, 1 if "greater than", 0 if equal.

Convertit une chaîne UTF-8 en une chaîne UTF-16.

Attention

Cette fonction ne signalera pas d'erreur s'il y a des séquences UTF-8 invalides dans la chaîne source. Elle les remplacera par un caractère '?' et continuera.

Les chaînes UTF-16 ont 16 bits par caractère (sauf certains caractères, qui ont 32 bits) : TCHAR sous Windows, lors de la compilation avec le support Unicode. src Chaîne source terminée par null au format UTF-8.
