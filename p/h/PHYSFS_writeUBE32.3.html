Signature de fonction pour les callbacks qui énumèrent des fichiers.

Attention

Depuis PhysicsFS 2.1, utilisez plutôt PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; cela vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de la chaîne.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme une alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions avec listes n'est pas nécessairement le cas dans les versions avec callback. Vérifiez la documentation des APIs spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des doublons de chaînes.

int PHYSFS_caseFold(const PHYSFS_uint32 from, PHYSFS_uint32 *to)

"Fold" a Unicode codepoint to a lowercase equivalent. (This is for limited, hardcore use. If you don't immediately see a need for it, you can probably ignore this forever.)

This will convert a Unicode codepoint into its lowercase equivalent. Bogus codepoints and codepoints without a lowercase equivalent will be returned unconverted.

Note that you might get multiple codepoints in return! The German Eszett, for example, will fold down to two lowercase latin 's' codepoints. The theory is that if you fold two strings, one with an Eszett and one with "SS" down, they will match.

Warning

Anyone that is a student of Unicode knows about the "Turkish I" problem. This API does not handle it. Assume this one letter in all of Unicode will definitely fold sort of incorrectly. If you don't know what this is about, you can probably ignore this problem for most of the planet, but perfection is impossible.

Parameters

from The codepoint to fold.
to Buffer to store the folded codepoint values into. This should point to space for at least 3 PHYSFS_uint32 slots.

Returns

The number of codepoints the folding produced. Between 1 and 3.

int PHYSFS_deinit(void)

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). It is usually best to close all write handles yourself before calling this function, so that you can gracefully handle a specific failure.

Once successfully deinitialized, PHYSFS_init() can be called again to restart the subsystem. All default API states are restored at this point, with the exception of any custom allocator you might have specified, which survives between initializations.

Returns

nonzero on success, zero on error. Specifics of the error can be gleaned from PHYSFS_getLastError(). If failure, state of PhysFS is undefined, and probably badly screwed up.

int PHYSFS_delete(const char *filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

Chances are, the bits that make up the file still exist, they are just made available to be written over at a later point. Don't consider this a security method or anything. :)

Parameters

filename Filename to delete.

Returns

nonzero on success, zero on error. Use PHYSFS_getLastErrorCode() to obtain the specific error.

int PHYSFS_deregisterArchiver(const char *ext)

Remove an archiver from the system. If for some reason, you only need your previously-registered archiver to live for a portion of your app's lifetime, you can remove it from the system once you're done with it through this function.

This fails if there are any archives still open that use this archiver.

This function can also remove internally-supplied archivers, like .zip support or whatnot. int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers d'un répertoire du chemin de recherche, en utilisant un rappel défini par l'application, avec signalement des erreurs. Internement, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique sauf pour la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés au rappel ne sont garantis dans aucun ordre que ce soit. Il n'y a pas de tri effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel elle découvrira les données. Tout tri que vous trouverez dans ces appels de fonction n'est que de la pure chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pourriez recevoir des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'une chose spécifique et voulaient s'arrêter après cela, ou s'ils avaient une erreur sérieuse et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération purement et simplement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr qu'il a obtenu un ensemble de données complet, et son rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour plus de détails sur la manière dont votre rappel doit se comporter.

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées au rappel. Peut être NULL.

Retourne

non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel retourne PHYSFS_ENUM_STOP pour s'arrêter tôt, cela sera considéré comme un succès. int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute un fichier ou un répertoire à la liste de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée même si la fonction réussit. Vous ne pouvez pas ajouter le même fichier à deux points de montage différents : le contrôle des doublons est effectué par rapport au fichier et non par rapport au point de montage.

Lors du montage d'un fichier, il est ajouté à un système de fichiers virtuel... tous les fichiers de tous les fichiers montés sont entrelacés dans un seul arbre hiérarchique. Deux fichiers montés au même endroit (ou un fichier avec des fichiers qui se chevauchent un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans ce cas, le fichier le plus proche dans la liste de recherche est sélectionné, et les autres fichiers ne sont pas accessibles par l'application. Cela permet d'utiliser des fichiers comme remplacements pour des révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des fichiers à un endroit spécifique dans l'arborescence des fichiers et empêcher le chevauchement ; ceci est utile pour les modifications téléchargées qui peuvent transplanter sur des données de l'application ou les unes sur les autres, par exemple.

Il est permis de spécifier un lien symbolique vers un fichier ou un répertoire, indépendamment du fait que PHYSFS_permitSymbolicLinks() soit activé ou non. Cette fonction ne traite que les liens symboliques à l'intérieur du répertoire ou du fichier monté.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce à quoi s'attendent ceux qui connaissent le concept Unix de « montage ». De plus, plus d'un fichier peut être monté au même point de montage, ou les points de montage et le contenu des fichiers peuvent se chevaucher... le mécanisme d'entrelacement continue de fonctionner comme ça.

mountPoint emplacement dans l'arborescence entrelacée où ce fichier sera « monté », en notation indépendante du système. NULL ou « » équivaut à « / ».
appendToPath non nul pour ajouter à la fin de la liste de recherche, zéro pour ajouter au début.

Non nul si ajouté à la liste, zéro en cas d'erreur (fichiers invalides, répertoires manquants, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (transparentement) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre différent de zéro. Notez que ceci est davantage destiné à isoler le langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, donc à moins que vous ne ressentiez un danger spécifique à leur autorisation, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow différent de zéro pour autoriser les liens symboliques, zéro pour refuser le lien.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Définit un sous-répertoire d'une archive comme répertoire racine. Cela permet de restreindre les fichiers accessibles à une archive spécifique. Par exemple, si vous avez x.zip avec un fichier à y/z.txt monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel à PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer le répertoire racine d'une archive à tout moment, en modifiant l'arborescence de fichiers interpolée (selon l'endroit où les chemins se déplacent, une archive différente peut fournir des fichiers différents). Si vous définissez le répertoire racine à NULL ou "/", l'archive sera traitée comme si aucun répertoire spécial n'avait été spécifié (comme si l'archive était montée normalement).

Changer le répertoire racine n'affecte que les opérations futures sur les chemins de fichiers ; un fichier qui a été ouvert à partir d'un chemin qui a changé en raison d'un setRoot ne sera pas affecté.

Définir un nouveau répertoire racine n'est pas limité aux fichiers dans le chemin de recherche ; vous pouvez le définir dans le répertoire d'écriture également, ce qui peut être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez pas changer le répertoire d'écriture au moment voulu.

Il n'est pas erroné de définir un sous-répertoire qui n'existe pas comme répertoire racine d'une archive, mais dans ce cas, aucun fichier ne sera visible. Si les répertoires manquants finissent par être créés (un mkdir dans le système de fichiers physique, etc.), cela sera reflété dans l'arborescence interpolée.

Paramètres

archive Le répertoire/fichier dont le répertoire racine doit être changé.
subdir Le nouveau sous-répertoire à définir comme racine de l'archive.

Retour

non zéro en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

Toutes les archives seront montées à la racine du système de fichiers virtuel ("/") .

archiveExt L'extension utilisée par votre programme pour spécifier une archive. Par exemple, Quake 3 utilise "pk3", bien qu'il s'agisse simplement de fichiers zip. Spécifiez NULL pour ne pas rechercher automatiquement les archives. Ne spécifiez pas le point '.' ; si vous voulez rechercher les fichiers ZIP, spécifiez "ZIP" et non ".ZIP" ... la recherche d'archives ne tient pas compte de la casse.

Vous pouvez spécifier zéro et gérer la configuration du disque vous-même.
archivesFirst Non nul pour préfixer les archives à la recherche. Zéro pour les suffixer. Ignoré si !(archiveExt).

non zéro en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.
