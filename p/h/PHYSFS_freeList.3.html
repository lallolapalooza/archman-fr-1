PHYSFS_EnumerateCallback

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du callback : à savoir : si vous cherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être en ordre alphabétique par rapport aux autres callbacks qui ont été appelés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retours

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent des fichiers.

Attention

Depuis PhysicsFS 2.1, utilisez plutôt PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; il vous donne plus de contrôle sur le processus.

Ils sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire d'une chaîne.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes au préalable.

Sachez que l'ordre des données promis dans les versions avec liste n'est pas nécessairement le même dans les versions avec callback. Consultez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous l'attendez et vous pourriez obtenir des doublons.

Paramètres

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être en ordre alphabétique par rapport aux autres callbacks qui ont été appelés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Obtenir une liste de fichiers d'un répertoire d'un chemin de recherche, en utilisant une fonction de rappel définie par l'utilisateur, avec signalement d'erreurs. En interne, PHYSFS_enumerateFiles() appelle uniquement cette fonction, puis construit une liste avant de la retourner à l'application. La fonctionnalité est donc identique, sauf pour la manière dont les informations sont présentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois pour chaque élément du chemin de recherche :

{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donne-moi plus de données, s'il te plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments passés à la fonction de rappel ne sont pas garantis d'être dans un ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un ordre alphabétique. Cette forme signale ce qui est trouvé dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout tri que vous trouvez dans ces rappels n'est que de la pure chance. N'en dépendez pas. Comme cela parcourt toute la liste des archives, vous pourriez recevoir des noms de fichiers en double.

Cette API et les fonctions de rappel elles-mêmes peuvent signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même si elles ne recherchaient qu'un objet spécifique et voulaient s'arrêter après cela, ou s'il y avait une erreur grave et qu'elles ne pouvaient en avertir personne. De plus, si PhysicsFS lui-même avait un problème (disque défectueux ou autre), il ne pouvait pas le signaler à l'application appelante ; il se contenterait d'ignorer des éléments ou d'arrêter l'énumération, et l'appel ne saurait pas qu'il avait perdu des données en cours de route.

Désormais, l'appelant peut être sûr d'avoir obtenu un ensemble complet de données, et s'il souhaite arrêter l'énumération prématurément, sa fonction de rappel a le contrôle. Voir la documentation de PHYSFS_EnumerateCallback pour plus de détails sur la façon dont votre fonction de rappel doit se comporter.

dir Répertoire, en notation indépendante du système, à énumérer.
c Fonction de rappel pour être notifié des éléments du chemin.
d Données définies par l'application qui sont passées à la fonction de rappel. Peut être NULL.

Retourne

Non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers chevauchant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser les archives pour remplacer les versions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer les archives à un endroit spécifique dans l'arborescence des fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou les uns les autres, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept Unix de "montage" peuvent s'attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

Spécifier un lien symbolique vers une archive ou un répertoire est autorisé ici, indépendamment de l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne concerne que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

newDir répertoire ou archive à ajouter au chemin, en notation spécifique à la plateforme.
mountPoint Emplacement dans l'arborescence interpolée où cette archive sera "montée", en notation indépendante de la plateforme. NULL ou "" est équivalent à "/".
appendToPath Non nul pour ajouter au chemin de recherche, zéro pour préfixer.

Ce handle contient toutes les données de l'archive et est utilisé à la place d'un fichier réel dans le système de fichiers physique. Le PHYSFS_File peut être basé sur un fichier réel dans le système de fichiers physique, mais ce n'est pas nécessairement le cas. L'utilisation la plus courante est probablement de monter des archives stockées à l'intérieur d'autres archives.

(newDir) doit être une chaîne unique pour identifier cette archive. Elle est utilisée pour optimiser la sélection de l'archiveur (si vous la nommez XXXXX.zip, nous pourrions essayer l'archiveur ZIP en premier, par exemple, ou choisir directement un archiveur qui ne peut faire confiance à la validité des données que par l'extension du nom de fichier). Il n'est pas nécessaire qu'il fasse référence à un fichier réel. Si l'extension du nom de fichier n'est pas utile, le système essaiera tous les archiveurs jusqu'à ce qu'un fonctionne ou qu'aucun ne fonctionne. Ce nom de fichier doit être unique, car le système ne vous permettra pas d'avoir deux archives du même nom.

void PHYSFS_permitSymbolicLinks (int allow)

Activez ou désactivez le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné à la mise en quarantaine du langage de script d'un programme, au cas où des scripts non approuvés tenteraient de compromettre le système. De manière générale, un utilisateur pourrait très bien avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne ressentiez un danger spécifique à leur autorisation, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lorsque l'on traite des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans tous les cas pas suivi. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser les liens.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Hace que un subdirectorio de un archivo sea su directorio raíz. Esto le permite limitar los archivos accesibles dentro de un archivo específico. int PHYSFS_ucs4stricmp (const PHYSFS_uint32 * str1, const PHYSFS_uint32 * str2)

Comparaison insensible à la casse de deux chaînes au format UCS-4. Ceci est un remplacement de strcasecmp/stricmp qui s'attend à ce que les deux chaînes soient au format UCS-4 (également connu sous le nom de UTF-32). Il indique quelle chaîne est "plus grande" que l'autre, mais gardez à l'esprit que cela ne signifie pas nécessairement grand-chose : 'a' peut être "plus petit" que 'b', mais un caractère japonais n'a pas de relation significative avec un lambda grec en termes alphabétiques. Dans la plupart des cas, vous devriez traiter la valeur renvoyée comme "égal" ou "pas égal".

Comme stricmp, il s'attend à ce que les deux chaînes soient terminées par NULL.

Paramètres

str1 Première chaîne à comparer.
str2 Deuxième chaîne à comparer.

Retour

-1 si str1 est "plus petit" que str2, 1 s'il est "plus grand", 0 s'ils sont égaux.

Les chaînes UTF-16 ont 16 bits par caractère (sauf certains caractères qui font 32 bits) : TCHAR sous Windows, lors de la compilation avec le support Unicode. Les versions modernes de Windows utilisent UTF-16. Les versions de Windows antérieures à 2000 utilisaient TCHAR, mais ne géraient que UCS-2. UTF-16 est UCS-2, à l'exception des caractères qui font 4 octets, lesquels ne sont de toute façon pas représentables en UCS-2. Si vous n'êtes pas sûr, vous devriez utiliser UTF-16 à ce stade sur Windows.

Pour s'assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon de double la taille du tampon source. UTF-8 n'utilise jamais plus de 32 bits par caractère, donc bien qu'il puisse réduire une chaîne UTF-16, il peut aussi l'étendre.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

dst Tampon pour stocker la chaîne UTF-8 convertie.

int PHYSFS_utf8stricmp (const char * str1, const char * str2)

Comparaison insensible à la casse de deux chaînes UTF-8. Ceci est un remplacement de strcasecmp/stricmp qui attend que les deux chaînes soient en encodage UTF-8. Il effectuera un "repliement de casse" pour déterminer si les points de code Unicode dans les chaînes correspondent.

Si les deux chaînes sont exclusivement des caractères ASCII bas, cela fonctionnera correctement, car c'est aussi un UTF-8 valide. S'il y a des caractères ASCII hauts, cela ne fera pas ce que vous attendez !

Il indiquera quelle chaîne est "supérieure à" l'autre, mais soyez conscient que cela n'a pas forcément de sens : 'a' peut être "inférieur à" 'b', mais un kuten japonais n'a pas de relation alphabétique significative avec un lambda grec, mais pouvoir attribuer une "valeur" fiable rend les algorithmes de tri possibles, même s'ils ne sont pas entièrement sains. Dans la plupart des cas, vous devriez considérer la valeur de retour comme "égal" ou "différent".

Comme stricmp, ceci attend que les deux chaînes soient terminées par un caractère nul.

Paramètres

str1 Première chaîne à comparer.
str2 Deuxième chaîne à comparer.

Retourne

-1 si str1 est "inférieur à" str2, 1 si "supérieur à", 0 si égal.
