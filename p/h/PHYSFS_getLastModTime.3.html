PHYSFS_EnumerateCallback

PHYSFS_enumerate

Ceci est identique à PHYSFS_EnumFilesCallback de PhysicsFS 2.0, à moins qu'il ne retourne un résultat depuis le callback : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez indiquer à PhysicsFS d'arrêter l'énumération. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons que vous avez obtenu correctement. :)

Paramètres

data pointeur vers une PHYSFS_Version à initialiser.
origdir chaîne avec le chemin complet, en notation indépendante du système, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire dans lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname nom du fichier en cours d'énumération. Il ne sera pas trié par ordre alphabétique par rapport aux autres callbacks qui ont été appelés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies; ne les utilisez pas.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() pour plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, une entrée par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire de toute chaîne.

Ces callbacks sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui retournent des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le callback indique que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes précédemment.

Notez que le tri des données promis dans les versions de liste n'est pas nécessairement le cas dans les versions de callback. Vérifiez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendriez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data pointeur vers des données définies par l'utilisateur, passé via l'API qui a finalement appelé le callback.
origdir chaîne avec le chemin complet, en notation indépendante du système, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire dans lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname nom du fichier en cours d'énumération. Il ne sera pas trié par ordre alphabétique par rapport aux autres callbacks qui ont été appelés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

int PHYSFS_mount(const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés en un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers chevauchant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer des révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner les uns les autres, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que les personnes familières avec le concept Unix de "montage" pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

Spécifier un lien symbolique vers une archive ou un répertoire est autorisé ici, quel que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

Cette fonction fonctionne comme PHYSFS_mount(), mais prend un handle PHYSFS_File au lieu d'un nom de chemin. Ce handle contient toutes les données de l'archive et est utilisé à la place d'un vrai fichier dans le système de fichiers physique. Le PHYSFS_File peut être basé sur un vrai fichier dans le système de fichiers physique, mais ce n'est pas nécessairement le cas. L'utilisation la plus courante à cette fin est probablement de monter des archives stockées à l'intérieur d'autres archives.

(newDir) doit être une chaîne de caractères unique pour identifier cette archive. Elle est utilisée pour optimiser la sélection de l'archiveur (si vous la nommez XXXXX.zip, nous pourrions essayer l'archiveur ZIP en premier, par exemple, ou choisir directement un archiveur qui ne peut faire confiance à la validité des données que par son extension de nom de fichier). Il n'est pas nécessaire qu'il fasse référence à un vrai fichier. Si l'extension du nom de fichier n'est pas utile, le système essaiera chaque archiveur jusqu'à ce qu'un fonctionne ou qu'aucun d'entre eux ne le fasse. Ce nom de fichier doit être unique, car le système ne vous permettra pas d'avoir deux archives portant le même nom.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, ouvrir un tel lien ouvrira (transparence) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné à l'encapsulation d'un langage de script de programme, au cas où des scripts non fiables tenteraient de compromettre le système. De manière générale, un utilisateur pourrait très bien avoir une raison légitime de créer un lien symbolique, donc à moins que vous ne ressentiez un danger spécifique à leur autorisation, vous devriez les permettre.

Les liens symboliques ne sont explicitement vérifiés que lors de la manipulation de noms de fichiers en notation indépendante de la plateforme. C'est-à-dire lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission de lien symbolique peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour interdire les liens.

Vous ne pouvez appeler cette fonction qu'avant PHYSFS_init() ; si la bibliothèque est initialisée, elle rejettera vos tentatives de modification de l'algorithme d'allocation en cours de route. Vous pouvez appeler cette fonction après PHYSFS_deinit() si vous êtes prêt à arrêter la bibliothèque et à la redémarrer avec un nouvel algorithme d'allocation ; c'est une opération sûre et prise en charge. L'algorithme reste intact entre les appels de désinitialisation/initialisation. Si vous souhaitez revenir à l'algorithme par défaut du système, passez un NULL ici.

Paramètres

allocator Structure contenant les points d'entrée de votre algorithme d'allocation.

Retour

Zéro en cas d'erreur, non-zéro en cas de succès. Cet appel échouera uniquement entre PHYSFS_init() et PHYSFS_deinit().

int PHYSFS_utf8stricmp (const char * str1, const char * str2)

Comparaison insensible à la casse de deux chaînes UTF-8. Il s'agit d'un remplacement de strcasecmp/stricmp qui attend que les deux chaînes soient en encodage UTF-8. Elle effectuera un "repliement de casse" pour décider si les points de code Unicode dans les chaînes correspondent.

Si les deux chaînes sont exclusivement des caractères ASCII bas, cela fonctionnera correctement, car c'est aussi du UTF-8 valide. S'il y a des caractères ASCII hauts, cela ne fera pas ce que vous attendez !

Elle indiquera quelle chaîne est "supérieure" à l'autre, mais sachez que cela ne signifie pas nécessairement quelque chose : 'a' peut être "inférieur à" 'b', mais un kuten japonais n'a pas de relation alphabétique significative avec un lambda grec, mais pouvoir assigner une "valeur" fiable rend les algorithmes de tri possibles, bien que pas entièrement sains. La plupart des cas devraient traiter la valeur de retour comme "égal" ou "non égal".

Comme stricmp, elle attend que les deux chaînes soient terminées par un caractère nul.

Paramètres

str1 Première chaîne à comparer.
str2 Deuxième chaîne à comparer.

Retourne

-1 si str1 est "inférieur à" str2, 1 si "supérieur à", 0 si égal.
