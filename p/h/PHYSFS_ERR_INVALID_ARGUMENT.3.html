typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature des fonctions de rappel qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() pour avoir plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, une entrée par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire des chaînes.

Ces rappels sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui renvoient des listes qui doivent être libérées avec PHYSFS_freeList(). Le rappel indique que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes.

Notez que l'ordre des données dans les versions de liste n'est pas nécessairement garanti dans les versions de rappel. Vérifiez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendiez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data pointeur vers des données définies par l'utilisateur, passé via l'API qui a finalement appelé le rappel.
origdir chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire dans lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname le nom du fichier qui est énuméré. Il ne sera pas nécessairement dans l'ordre alphabétique par rapport à d'autres rappels qui ont été appelés, et ne contiendra pas le chemin complet. Vous pouvez reconstruire le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

enum PHYSFS_ErrorCode

Valeurs représentant des causes spécifiques d'échec. La plupart du temps, vous ne devez vous soucier que d'une opération a échoué ou non, mais il peut y avoir des occasions où vous prévoyez de gérer un cas d'échec spécifique avec élégance, nous offrons donc des codes d'erreur spécifiques.

La plupart de ces erreurs sont un peu vagues et ne sont pas toujours des choses que vous pouvez corriger... s'il y a une erreur de permission, par exemple, tout ce que vous pouvez faire est de transmettre cette information à l'utilisateur et de le laisser gérer comment la traiter. Dans la plupart de ces cas, votre programme ne devrait se soucier que du fait qu'il n'a pas atteint ses objectifs, et non pas spécifiquement pourquoi.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers d'un répertoire du chemin de recherche, en utilisant un rappel défini par l'application, avec signalement des erreurs. Interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique sauf la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas de tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons trouvé [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés au rappel ne sont garantis dans aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons pas garantir l'ordre dans lequel les données seront découvertes. Tout tri que vous trouverez dans ces rappels est purement un hasard. N'en dépendez pas. Comme cela parcourt toute la liste des archives, vous pourriez recevoir des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur sérieuse et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération directement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr qu'il a obtenu un ensemble de données complet, et son rappel a le contrôle s'il souhaite que l'énumération s'arrête tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement attendu de votre rappel.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées au rappel. Peut être NULL.

Retourne

Non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel renvoie PHYSFS_ENUM_STOP pour s'arrêter tôt, cela sera considéré comme un succès. Les rappels renvoyant PHYSFS_ENUM_ERROR feront que cette fonction retournera zéro et définira le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

Comme cela empêchait les applications de distinguer le succès complet de l'échec partiel, et comme la fonction pouvait toujours retourner NULL pour signaler des échecs catastrophiques de toute façon, dans PhysicsFS 2.1, la politique de cette fonction a changé : elle retournera soit une liste de résultats complets, soit NULL pour tout échec de quelque nature que ce soit, afin que nous puissions garantir que l'énumération s'est déroulée jusqu'à son terme et qu'il n'y a pas de lacunes dans ses résultats.

* Nous avons trouvé [y.sau].

* Nous avons trouvé [w.sau]..fi

const char * PHYSFS_getLastError (void )

Obtenez des informations sur la dernière erreur lisibles par l'homme.

Obsolète

Utilisez plutôt PHYSFS_getLastErrorCode() et PHYSFS_getErrorByCode().

Attention

Depuis PhysicsFS 2.1, cette fonction a été affaiblie. Avant PhysicsFS 2.1, cette fonction était le seul moyen d'obtenir des détails sur les erreurs au-delà de la valeur de retour de base d'une fonction donnée. Il était censé s'agir d'une chaîne lisible par l'homme dans l'une des plusieurs langues, et n'était pas utile pour l'analyse par les applications. C'était un problème, car le développeur et non l'utilisateur choisissait la langue au moment de la compilation, et les mainteneurs de PhysicsFS devaient (mal) maintenir une quantité importante de travail de localisation. L'application ne pouvait pas analyser les chaînes, même si elle comptait sur une langue spécifique, car certaines étaient générées dynamiquement. Dans la version 2.1 et ultérieures, cela retourne toujours une chaîne statique en anglais ; vous pouvez l'utiliser comme chaîne clé pour vos propres localisations si vous le souhaitez, car nous nous engageons à ne pas modifier les chaînes d'erreur existantes. De plus, si votre application souhaite examiner des erreurs spécifiques, nous offrons maintenant une meilleure option : utilisez plutôt PHYSFS_getLastErrorCode().

Obtenez le dernier message d'erreur PhysicsFS sous forme de chaîne de caractères lisible par l'homme et terminée par NULL. Cela retournera NULL s'il n'y a pas eu d'erreur depuis le dernier appel à cette fonction. Le pointeur retourné par cet appel pointe vers un tampon interne. void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et architectures contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. En ouvrant un lien symbolique physique, celui-ci ouvrira en transparence le fichier auquel il pointe.

Par défaut, PhysicsFS vérifiera si un fichier est réellement un lien symbolique lors des appels d'ouverture et échouera si c'est le cas. Si cette fonction n'est pas activée, le lien pourrait vous amener en dehors des chemins de lecture et d'écriture, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Notez que ceci est davantage destiné au sandboxing d'un langage de script de programme, au cas où des scripts non fiables tenteraient de compromettre le système. En général, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas les désactiver sauf si vous ressentez un danger spécifique.

Les liens symboliques ne seront vus que lors de la manipulation de noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire que lorsque vous définissez vos chemins de recherche et d'écriture, etc., les liens symboliques ne seront jamais vus.

Note : PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. S'il n'est pas autorisé par cette fonction, PHYSFS_stat() ignorera le lien et le traitera comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désactiver le lien.

int PHYSFS_setBuffer (PHYSFS_File * handle, int bufsize)

Set the buffering behavior of a file handle. This function can also be used to enable or disable buffering, and to resize an existing buffer.

If bufsize is greater than zero, then a buffer of that size (in bytes) will be allocated for the file handle. If the file handle already has a buffer, it will be flushed and destroyed, and a new one allocated. If bufsize is zero, any existing buffer will be flushed and destroyed, and the file handle will be unbuffered.

Note that any outstanding I/O on the handle will implicitly cause a flush...check your return values!

Seeking, etc transparently accounts for buffering.

You can resize an existing buffer by calling this function more than once on the same file. Setting the buffer size to zero will free an existing buffer.

PhysicsFS file handles are unbuffered by default.

Please check the return value of this function! Failures can include not being able to seek backwards in a read-only file when removing the buffer, not being able to allocate the buffer, and not being able to flush the buffer to disk, among other unexpected problems.

handle handle returned from PHYSFS_open*().
bufsize size, in bytes, of buffer to allocate.

Returns

nonzero if successful, zero on error.

Faire d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de restreindre les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt, monté sur /a, alors l'appel PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer la racine d'une archive à tout moment, modifiant l'arborescence de fichiers interpolée (en fonction de l'endroit où les chemins changent, une archive différente peut fournir divers fichiers). Si les répertoires manquants finissent par être créés (un mkdir sur le système de fichiers physique, etc.), cela se reflétera dans l'arbre interpolé.

archive répertoire/archive sur lequel changer la racine.
subdir nouveau sous-répertoire à faire de la racine de cette archive.

Retours

non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.
