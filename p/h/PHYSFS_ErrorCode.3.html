Documentation des définitions de macro

#define PHYSFS_file PHYSFS_File

Compatibilité API 1.0. physfs_file est identique à PHYSFS_File. Ce #define est là pour la compatibilité avec l'API 1.0, qui avait une convention de casse incohérente dans ce cas. Le nouveau code devrait utiliser PHYSFS_File, car ce #define peut être supprimé.

#define PHYSFS_VERSION( x)

Valeur :

{ \
    (x)->major = PHYSFS_VER_MAJOR; \
    (x)->minor = PHYSFS_VER_MINOR; \
    (x)->patch = PHYSFS_VER_PATCH; \
}

Macro pour déterminer avec quelle version de PhysicsFS votre programme est compilé. Cette macro remplit une structure PHYSFS_Version avec les valeurs de la version.

Documentation des macros

#define PHYSFS_VERSION_MAJOR

Major version number of the library you compiled against. This is determined by what header the compiler uses. Note that if you dynamically linked the library, you might have a slightly newer or older version at runtime. That version can be determined with PHYSFS_getLinkedVersion(), which, unlike PHYSFS_VERSION, is not a macro.

Parameters

x A pointer to a PHYSFS_Version struct to initialize.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au contraire, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

    printf(" * Nous avons obtenu [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...

Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme rapporte ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données seront découvertes. Tout tri que vous trouvez dans ces rappels est de la pure chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération immédiatement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble de données complet, et son rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement de votre rappel.

Obtenir une liste de fichiers d'un répertoire de chemin de recherche.

Attention

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction retournait autant d'éléments que possible face à une condition d'échec (manque de mémoire, erreur d'entrée/sortie disque, etc.). Les répertoires correspondants sont interpolés. C'est-à-dire que si "C:\mydir" est dans le chemin de recherche et contient un répertoire "savegames" qui contient "x.sav", "y.sav", et "z.sav", et qu'il y a aussi un "C:\userdir" dans le chemin de recherche qui a un sous-répertoire "savegames" avec "w.sav", alors le code suivant :

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Nous avons obtenu [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi
N'hésitez pas à trier la liste comme vous le souhaitez. Cependant, les données retournées ne contiendront jamais de doublons et seront toujours triées par ordre alphabétique (ou plutôt, Unicode sensible à la casse) pour vous.
N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur de retour de cette fonction lorsque vous en avez terminé.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archivés contiennent des fichiers qui sont de simples pointeurs vers d'autres fichiers. Lors de l'ouverture d'un lien symbolique sur un système physique, le fichier pointé est ouvert de manière transparente.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous amener en dehors des chemins de lecture et d'écriture, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Notez que cela est davantage destiné au wrapper d'un langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas les désactiver, à moins que vous ne pensiez qu'il existe un danger spécifique.

Les liens symboliques ne sont considérés que lorsqu'il s'agit de noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire, lorsque vos chemins de recherche et d'écriture, etc., sont définis, les liens symboliques ne sont jamais suivis.

Note : PHYSFS_stat() examine toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traite la requête comme si le chemin n'existait pas.

La permissibilité des liens symboliques peut être activée ou désactivée après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow une valeur non nulle pour autoriser les liens symboliques, zéro pour désactiver le suivi.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Définit un sous-répertoire d'une archive comme répertoire racine. Cela vous permet de réduire les fichiers accessibles à une archive spécifique. Vous pouvez changer le répertoire racine d'une archive à tout moment, altérant l'arborescence interpolée (selon l'endroit où les chemins sont résolus, un fichier différent pourrait fournir différents fichiers). Définir un nouveau répertoire racine n'est pas limité aux archives dans le chemin de recherche ; vous pouvez aussi le définir sur le répertoire d'écriture, ce qui peut être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez pas changer le répertoire d'écriture à ce moment-là.

Il est acceptable de définir un sous-répertoire qui n'existe pas comme répertoire racine d'une archive ; cependant, aucun fichier ne sera visible dans ce cas. archive Répertoire/archive dont le répertoire racine sera changé.
subdir Nouveau sous-répertoire à définir comme répertoire racine de cette archive.

Retour

Différent de zéro en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convertir une chaîne UTF-8 en une chaîne de Latin1. Les chaînes de Latin1 ont 8 bits par caractère : un "encodage ASCII étendu" populaire.

Pour garantir que le tampon de destination soit suffisamment grand pour la conversion, veuillez allouer un tampon de taille double par rapport au tampon source. UTF-8 étend les codes Latin1 supérieurs à 127 de 1 à 2 octets, donc la chaîne peut parfois s'agrandir.

Convert a UTF-8 string to a UCS-4 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UCS-4 strings are 32-bits per character. This is the preferred format for Unicode on many platforms.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UCS-4 always uses four bytes per character, so an entirely low-ASCII string will double in size!
