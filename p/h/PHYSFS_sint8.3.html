typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; cela vous donne plus de contrôle sur le processus.

Ils sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de ces chaînes.

Ces rappels sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions avec liste n'est pas nécessairement le même dans les versions avec rappel. Vérifiez la documentation sur les API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes en double.

int PHYSFS_caseFold(const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Replie" un point de code Unicode vers un équivalent en minuscules. (Ceci est pour un usage limité et intense. Si vous ne voyez pas immédiatement la nécessité de l'utiliser, vous pouvez probablement l'ignorer pour toujours.)

Ceci convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux n'ayant pas d'équivalent en minuscules seront retournés sans conversion.

Notez que vous pourriez obtenir plusieurs points de code en retour ! L'Eszett allemand, par exemple, sera replié en deux points de code latins 's' en minuscules. La théorie est que si vous repliez deux chaînes, l'une avec un Eszett et l'autre avec "SS", elles correspondront.

Attention

Toute personne étudiant Unicode connaît le problème du "I turc". Cette API ne le gère pas. Supposez que cette seule lettre dans tout Unicode sera repliée de manière plus ou moins incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la plupart des cas, mais la perfection est impossible.

Paramètres

from Le point de code à replier.
to Tampon pour stocker les valeurs des points de code repliés. Il doit pointer vers un espace pour au moins 3 emplacements PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le repliement. Entre 1 et 3.

int PHYSFS_deinit(void )

Désinitialise la bibliothèque PhysicsFS. Cela ferme tous les fichiers ouverts via PhysicsFS, efface les chemins de recherche/écriture, libère la mémoire et invalide tous vos descripteurs de fichiers.

Notez que cet appel peut ÉCHOÜER s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures sur un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur a échoué, etc.). Il est généralement préférable de fermer tous les descripteurs d'écriture vous-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois désinitialisé avec succès, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états d'API par défaut sont restaurés à ce moment-là, à l'exception de tout allocateur personnalisé que vous auriez pu spécifier, qui survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les détails de l'erreur peuvent être obtenus auprès de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini, et probablement très perturbé.

int PHYSFS_delete(const char *filename)

Supprime un fichier ou un répertoire. (filename) est spécifié dans une notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, et non ce vers quoi il pointe, indépendamment du fait que vous ayez "permis les liens symboliques" ou non.

Donc, si vous avez défini le répertoire d'écriture sur "C:\monjeu\repertoire_ecriture" et que vous appelez PHYSFS_delete("telechargements/cartes/niveau1.map"), alors le fichier "C:\monjeu\repertoire_ecriture\telechargements\cartes\niveau1.map" est supprimé du système de fichiers physique, s'il existe et si le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont un descripteur de fichier ouvert sur celui-ci (y compris votre programme) ne l'auront pas fermé.

Obtient une liste de fichiers à partir du dossier d'un répertoire de chemin de recherche, en utilisant un rappel défini par l'utilisateur, avec des erreurs signalées. En interne, PHYSFS_enumerateFiles() n'appelle que cette fonction, puis construit une liste avant de la retourner à l'application, de sorte que la fonctionnalité est identique sauf quant à la manière dont l'information est présentée à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par le demandeur une fois pour chaque élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // Donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments passés au rappel ne sont garantis d'être dans aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un tri alphabétique. Cette forme signale ce qui est trouvé dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout tri que vous trouvez dans ces rappels est purement un hasard. Ne vous y fiez pas. Comme cela parcourt toute la liste des fichiers, vous pourriez recevoir des noms de fichiers en double.

Cette API et les rappels eux-mêmes peuvent signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'un objet spécifique et voulaient s'arrêter après cela, ou s'il y avait une erreur grave et qu'ils ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque, etc.), il ne pouvait pas le signaler au demandeur, il sautait simplement des éléments ou arrêtait l'énumération, et l'appelant ne savait pas qu'il avait perdu des données en cours de route.

Maintenant, l'appelant peut être assuré qu'il a obtenu un ensemble complet de données, et s'il le souhaite, son rappel a le contrôle sur la question de savoir s'il faut arrêter l'énumération prématurément. Voir la documentation de PHYSFS_EnumerateCallback pour plus de détails sur la façon dont votre rappel doit se comporter.

d Données définies par le demandeur qui sont passées au rappel. Peut être NULL.

Non zéro en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel retourne PHYSFS_ENUM_STOP, cela est considéré comme un succès. int PHYSFS_mount(const char *newDir, const char *mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers se chevauchant avec un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer des révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un endroit spécifique de l'arborescence de fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner des données d'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que peuvent attendre ceux qui connaissent le concept de « montage » Unix. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

La spécification d'un lien symbolique vers une archive ou un répertoire est autorisée ici, indépendamment de l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

Paramètres

newDir répertoire ou archive à ajouter au chemin, en notation dépendante de la plateforme.
mountPoint Emplacement dans l'arbre interpolé où cette archive sera « montée », en notation indépendante de la plateforme. NULL ou « » équivaut à « / ».
appendToPath non-zéro pour ajouter au chemin de recherche, zéro pour insérer au début.

Retourne

non-zéro si ajouté au chemin, zéro en cas d'échec (archive invalide, répertoire manquant, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre différent de zéro. Notez que cela est davantage destiné à l'isolation d'un langage de script de programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne ressentiez un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques sont uniquement vérifiés explicitement lors de la manipulation des noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow différent de zéro pour autoriser les liens symboliques, zéro pour refuser les liens.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Fait d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de restreindre les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier y/z.txt monté sur /a, et que vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel à PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer le répertoire racine d'une archive à tout moment, modifiant ainsi l'arborescence de fichiers interpolée (selon où les chemins sont déplacés, un fichier différent peut fournir plusieurs fichiers). archive le répertoire/l'archive dont le répertoire racine est changé.

Convertit une chaîne Latin1 en une chaîne UTF-8. Les chaînes Latin1 utilisent 8 bits par caractère : un encodage populaire de type "high ASCII".

Pour s'assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon dont la taille est le double de celle du tampon source. UTF-8 développe les points de code latin1 supérieurs à 127 de 1 à 2 octets, la chaîne peut donc grossir dans certains cas.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Veuillez noter que nous ne fournissons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer la plupart des points de code Unicode. C'est un encodage hérité ; vous devriez toujours vous en éloigner.

Advertencia

Esta función no reportará un error si hay secuencias UTF-16 inválidas en la cadena de entrada. Reemplazará estas secuencias con un carácter '?' y continuará.
