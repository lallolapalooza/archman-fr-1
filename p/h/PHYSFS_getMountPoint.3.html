PHYSFS_EnumerateCallback

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du callback : à savoir, si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois :)

Paramètres

data Pointeur de données défini par l'utilisateur, transmis depuis l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, transmis dans le callback pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être en ordre alphabétique par rapport aux autres callbacks qui ont été déclenchés, et il ne contenir pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent des fichiers.

Attention

À partir de PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; il vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de la chaîne.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme une alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le cas dans les versions de callback. Vérifiez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers d'un répertoire du chemin de recherche, en utilisant un rappel défini par l'application, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique sauf la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Elle appelle plutôt une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons trouvé [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés au rappel ne sont garantis dans aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel elle découvrira les données. Tout tri que vous trouverez dans ces rappels n'est que de la pure chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération de manière abrupte, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble de données complet, et son rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Consultez la documentation de PHYSFS_EnumerateCallback pour plus de détails sur le comportement de votre rappel.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées au rappel. Peut être NULL.

Retourne

non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel retourne PHYSFS_ENUM_STOP pour s'arrêter tôt, cela sera considéré comme un succès. Les rappels retournant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Nous avons trouvé [%s].\n", *i);

* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter un fichier ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter le même fichier à deux points de montage différents : la vérification des doublons se fait par rapport au fichier, pas par rapport au point de montage.

Lors du montage d'un fichier, celui-ci est ajouté à un système de fichiers virtuel... tous les fichiers de tous les fichiers montés sont interpolés dans un seul arbre de répertoires hiérarchique. Deux fichiers montés au même endroit (ou un fichier avec des fichiers qui se chevauchent avec un point de montage) peuvent avoir des fichiers qui se chevauchent : dans ce cas, le fichier le plus proche dans le chemin de recherche est sélectionné, et les autres fichiers ne sont pas accessibles à l'application. Cela permet d'utiliser les fichiers pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des fichiers à un endroit spécifique dans l'arborescence des répertoires et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient remplacer les données de l'application ou les fichiers les uns des autres, par exemple.

Ajoute une archive, contenue dans un descripteur PHYSFS_File, au chemin de recherche.

Attention

Les archives dans les archives peuvent être très lentes ! Bien qu'un PHYSFS_File puisse se déplacer (seek) même lorsque les données sont compressées, il peut le faire en revenant au début et en décompressant tout avant le point de déplacement. L'utilisation normale d'archive peut effectuer de nombreux déplacements en coulisses. En tant que tel, vous pourriez trouver l'utilisation normale d'archive extrêmement pénible si elle est montée de cette manière. Prévoyez en conséquence : si vous avez, par exemple, un fichier .zip auto-extractible, et que vous souhaitez monter quelque chose à l'intérieur, compressez le contenu de l'archive interne et assurez-vous que le fichier .zip externe ne compresse pas l'archive interne.

Cette fonction opère comme PHYSFS_mount(), mais prend un descripteur PHYSFS_File au lieu d'un nom de chemin. L'utilisation la plus courante pour cela est probablement de monter des archives stockées à l'intérieur d'autres archives.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive la sécurité des liens symboliques. Certains systèmes de fichiers physiques et architectures contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, celui-ci ouvrira de manière transparente le fichier vers lequel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins de lecture et d'écriture, compromettant la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Ceci est principalement destiné à l'isolation des langages de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. En général, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas les désactiver, à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser.

Les liens symboliques ne seront vus que lorsqu'il s'agira de noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire, lorsque vos chemins de recherche et d'écriture, etc., sont définis, les liens symboliques ne seront jamais vus.

Note : PHYSFS_stat() vérifiera toujours le chemin spécifié ; s'il s'agit d'un lien symbolique, il ne sera dans aucun cas suivi. S'il n'est pas autorisé par cette fonction, PHYSFS_stat() ignorera le lien et traitera la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désactiver le lien.

Ajoute un nouvel archiveur au système.

Attention

C'est du matériel avancé et hardcore. Vous n'en avez pas besoin à moins de savoir vraiment ce que vous faites. La plupart des applications n'en auront pas besoin.

Si vous souhaitez fournir votre propre archiveur (par exemple, un format de fichier d'archive personnalisé, ou quelque chose de virtuel que vous souhaitez faire ressembler à un système de fichiers accessible via les API PhysicsFS habituelles), c'est par où commencer. Convert a UTF-8 string to a UCS-4 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UCS-4 strings are 32-bits per character. This is a direct mapping of UTF-8 to UCS-4, where each character's code point is preserved.

The destination buffer should be large enough to hold the converted string. Each UTF-8 character requires between one and four bytes, while each UCS-4 character requires four bytes. void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. If you aren't sure, you should be using UTF-16 at this point on Windows.

UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.
