Documentation des définitions de macro

#define PHYSFS_file PHYSFS_File

Redéfinition de compatibilité API 1.0. PHYSFS_file est identique à PHYSFS_File. Cette directive #define est ici pour la compatibilité ascendante avec l'API 1.0, qui avait une convention de capitalisation incohérente dans ce cas. Le nouveau code doit utiliser PHYSFS_File, car cette directive #define pourrait disparaître un jour.

Version Information

PHYSFS_VERSION

A macro that defines the version of the library you compiled against.

This is determined by what header the compiler uses. Note that if you dynamically linked the library, you might have a slightly newer or older version at runtime. That version can be determined with PHYSFS_getLinkedVersion(), which, unlike PHYSFS_VERSION, is not a macro.

Parameters

x A pointer to a PHYSFS_Version struct to initialize.

typedef PHYSFS_EnumerateCallbackResult(* physfs_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Possible return values from PHYSFS_EnumerateCallback. Function signature for callbacks that enumerate and return results.

These values dictate if an enumeration callback should continue to fire, or stop (and why it is stopping).

See also

PHYSFS_EnumerateCallback

PHYSFS_enumerate

This is the same thing as PHYSFS_EnumFilesCallback from PhysicsFS 2.0, except it can return a result from the callback: namely: if you're looking for something specific, once you find it, you can tell PhysicsFS to stop enumerating further. int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers d'un répertoire du chemin de recherche, en utilisant un rappel défini par l'application, avec signalement des erreurs. Internement, PHYSFS_enumerateFiles() appelle cette fonction puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique sauf pour la façon dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés au rappel ne sont garantis dans aucun ordre quelconque. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme rapporte tout ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une seule archive, nous ne pouvons pas garantir l'ordre dans lequel les données seront découvertes. *Tout tri que vous trouvez dans ces rappels est purement de la chance. Ne vous y fiez pas.* Comme cette fonction parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération purement et simplement, et l'appelant ne saurait pas qu'il avait perdu des données en cours de route.

Maintenant, l'appelant peut être sûr qu'il a obtenu un ensemble de données complet, et son rappel a le contrôle s'il veut que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur la façon dont votre rappel doit se comporter.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées au rappel. Peut être NULL.

Retourne

Non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel retourne PHYSFS_ENUM_STOP pour arrêter plus tôt, cela sera considéré comme un succès. Les rappels retournant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

Obtenir une liste de fichiers d'un répertoire du chemin de recherche.

Attention

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction retournait autant d'éléments que possible face à une condition d'échec (manque de mémoire, erreur d'E/S disque, etc.). char **rc = PHYSFS_enumerateFiles("savegames");

for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);

* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi

Attention

À moins d'avoir un besoin spécial et de bas niveau, vous devriez utiliser PHYSFS_mount() à la place.

Les archives dans les archives peuvent être très lentes ! Bien qu'un PHYSFS_File puisse se déplacer même lorsque les données sont compressées, il peut le faire en revenant au début et en décompressant tout avant le point de déplacement. L'utilisation normale d'archives peut impliquer beaucoup de déplacements en arrière-plan. Ainsi, vous pourriez trouver l'utilisation normale d'archives extrêmement pénible si elles sont montées de cette manière. Prévoyez en conséquence : si vous avez, par exemple, un fichier .zip auto-extractible et que vous souhaitez y monter quelque chose, compressez le contenu de l'archive interne et assurez-vous que le fichier .zip externe ne compresse pas l'archive interne également.

Cette fonction opère comme PHYSFS_mount(), mais prend un descripteur PHYSFS_File au lieu d'un chemin d'accès. Ce descripteur contient toutes les données de l'archive et est utilisé à la place d'un fichier réel dans le système de fichiers physique. Le PHYSFS_File peut être basé sur un fichier réel dans le système de fichiers physique, mais ce n'est pas nécessairement le cas. L'utilisation la plus courante à cette fin est probablement de monter des archives stockées à l'intérieur d'autres archives.

(newDir) doit être une chaîne de caractères unique pour identifier cette archive. Elle est utilisée pour optimiser la sélection de l'archiveur (si vous la nommez XXXXX.zip, nous pourrions essayer l'archiveur ZIP en premier, par exemple, ou choisir directement un archiveur qui ne peut valider les données qu'en fonction de l'extension du nom de fichier). Elle n'a pas besoin de correspondre à un fichier réel. Si l'extension du nom de fichier n'est pas utile, le système essaiera tous les archiveurs jusqu'à ce qu'un fonctionne ou qu'aucun ne fonctionne. Ce nom de fichier doit être unique, car le système ne vous permettra pas d'avoir deux archives portant le même nom.

(file) doit rester valide jusqu'à ce que l'archive soit démontée. Lorsque l'archive est démontée, le système appellera PHYSFS_close(file). Si vous avez besoin que ce descripteur survive, vous devrez l'encapsuler dans un PHYSFS_Io et utiliser PHYSFS_mountIo() à la place.

Si cette fonction échoue, PHYSFS_close(file) n'est pas appelée.

newDir Nom de fichier qui peut représenter ce flux.

appendToPath différent de zéro pour ajouter au chemin de recherche, zéro pour le précéder.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des références à d'autres fichiers. L'ouverture d'un lien symbolique physique ouvrira de manière transparente le fichier auquel il fait référence.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins de lecture et d'écriture, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Notez que ceci est davantage destiné à limiter un langage de programmation de script, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur peut avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas les désactiver, à moins que vous ne ressentiez un danger spécifique.

Les liens symboliques ne sont vérifiés que lors du traitement des noms de fichiers dans une notation indépendante du système. C'est-à-dire, lorsque vos chemins de recherche et d'écriture, etc., sont définis, les liens symboliques ne sont jamais vérifiés.

Notez que PHYSFS_stat() vérifie toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traite la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée à tout moment après l'appel de PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désactiver le lien.

Comparaison insensible à la casse de deux chaînes UTF-8. C'est un remplacement de strcasecmp/stricmp qui s'attend à ce que les deux chaînes soient encodées en UTF-8. Il effectuera un "repliement de casse" pour déterminer si les points de code Unicode dans les chaînes correspondent.

Si les deux chaînes ne contiennent que des caractères ASCII de bas niveau, cela fonctionnera correctement, car c'est aussi un UTF-8 valide. S'il y a des caractères ASCII de haut niveau, cela ne fera pas ce que vous attendez !

La plupart des cas devraient traiter la valeur de retour comme "égal" ou "inégal".

Comme stricmp, ceci s'attend à ce que les deux chaînes soient terminées par un caractère nul.

Paramètres

str1 Première chaîne à comparer.
str2 Deuxième chaîne à comparer.

Retourne

-1 si str1 est "inférieur à" str2, 1 si "supérieur à", 0 si égal.

Convert a UTF-8 string to a UCS-4 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UCS-4 strings are 32-bits per character. They are equivalent to 'wchar_t' on Linux/Unix systems when 'wchar_t' is 32 bits. If you are on Windows, you should be using PHYSFS_utf8ToUtf16() instead.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

Detailed Description

These functions are convenience wrappers around PHYSFS_write(3). They handle the byte-swapping required to convert an unsigned integer from the platform's native byte order to either bigendian or littleendian, and then write the result to the specified file.

These functions are useful for writing data files that need to maintain a specific endianness, irrespective of the host system.
