Informations sur la version

Pour déterminer la version de la bibliothèque avec laquelle vous avez compilé, vous pouvez comparer les valeurs des macros PHYSFS_VERSION et PHYSFS_getLinkedVersion(). La première, PHYSFS_VERSION, vous donne la version de l'en-tête que le compilateur utilise. Ceci est déterminé par l'en-tête que le compilateur utilise. Notez que si vous avez lié dynamiquement la bibliothèque, vous pourriez avoir une version légèrement plus récente ou plus ancienne au moment de l'exécution. Cette version peut être déterminée à l'aide de PHYSFS_getLinkedVersion(), qui, contrairement à PHYSFS_VERSION, n'est pas une macro.

Paramètres

x Un pointeur vers une structure PHYSFS_Version à initialiser.

typedef void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez plutôt PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; il vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de ces chaînes.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme une alternative aux fonctions qui retourneraient des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le même dans les versions de callback. Vérifiez la documentation sur les API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes en double.

Paramètres

data Pointeur de données défini par l'utilisateur, transmis depuis l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé une énumération, passé dans le callback pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être en ordre alphabétique par rapport à d'autres callbacks qui ont été appelés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers d'un répertoire du chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de la renvoyer à l'application, de sorte que la fonctionnalité est identique, sauf la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons trouvé [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/mon/chemin", printDir, NULL);

Il n'est pas garanti que les éléments envoyés à la fonction de rappel soient dans un ordre quelconque. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale tout ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre de découverte des données. Tout tri que vous trouverez dans ces rappels est purement un coup de chance. Ne vous y fiez pas. Comme cette fonction parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers en double.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter une fois celle-ci trouvée, ou s'ils avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement sauter des éléments ou arrêter l'énumération, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Désormais, l'appelant peut être assuré qu'il a obtenu un ensemble de données complet, et sa fonction de rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour plus de détails sur le comportement attendu de votre fonction de rappel.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

Retourne

Non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel renvoie PHYSFS_ENUM_STOP pour s'arrêter tôt, cela sera considéré comme un succès. Les fonctions de rappel renvoyant PHYSFS_ENUM_ERROR feront que cette fonction retournera zéro et définira le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

Obtient une liste de fichiers d'un répertoire du chemin de recherche.

Avertissement

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction renvoyait autant d'éléments que possible face à une condition d'échec (manque de mémoire, erreur d'E/S disque, etc.). Comme cela empêchait les applications de distinguer un succès complet d'un échec partiel, et comme la fonction pouvait toujours renvoyer NULL pour signaler des échecs catastrophiques, la politique de cette fonction a changé dans PhysicsFS 2.1 : elle renvoie soit une liste de résultats complets, soit NULL en cas de tout type d'échec, afin que nous puissions garantir que l'énumération s'est déroulée jusqu'à son terme et qu'il n'y a pas de lacunes dans ses résultats.

Les répertoires correspondants sont interpolés. C'est-à-dire, si "C:\mondossier" se trouve dans le chemin de recherche et contient un répertoire "sauvegardes" qui contient "x.sav", "y.sav", et "z.sav", et s'il y a également un répertoire "C:\monutilisateur" dans le chemin de recherche qui a un sous-répertoire "sauvegardes" avec "w.sav", alors le code suivant :

char **rc = PHYSFS_enumerateFiles("sauvegardes");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Nous avons trouvé [%s].\n", *i);
PHYSFS_freeList(rc);
* Nous avons trouvé [x.sav].
* Nous avons trouvé [y.sav].
* Nous avons trouvé [z.sav].
* Nous avons trouvé [w.sav]..fi
N'hésitez pas à trier la liste comme bon vous semble. Cependant, les données renvoyées ne contiendront jamais de doublons et seront toujours triées par ordre alphabétique (ou plus précisément : ordre Unicode sensible à la casse) pour vous.
N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur de retour de cette fonction lorsque vous avez terminé.

const char *PHYSFS_getPrefDir (const char * org, const char * app)

Obtenir le chemin du répertoire spécifié où les fichiers peuvent être écrits. Fonction d'aide.

Obtenez le "pref dir". Ceci est utilisé pour que les utilisateurs puissent écrire des fichiers personnels (préférences et sauvegardes de jeux, etc.) spécifiques à votre application. Ce répertoire est unique par utilisateur et par application.

Cette fonction décidera de l'emplacement approprié sur le système de fichiers natif, créera le répertoire s'il n'existe pas, et renverra une chaîne en notation dépendante du système de fichiers, adaptée pour être passée à PHYSFS_setWriteDir().

Sous Windows, cela pourrait ressembler à : "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name"

Sous Linux, cela pourrait ressembler à : "/home/bob/.local/share/My Program Name"

Sous Mac OS X, cela pourrait ressembler à : "/Users/bob/Library/Application Support/My Program Name"

(etc.)

Vous devriez utiliser le pref dir pour votre chemin d'écriture et le placer également au début de votre liste de recherche. Les anciennes versions de PhysicsFS ne proposaient que PHYSFS_getUserDir() et laissaient votre application trouver le chemin d'écriture. Ceci trouve le bon emplacement pour n'importe quelle plateforme, qui change non seulement entre les systèmes d'exploitation, mais aussi entre les versions du même système d'exploitation.

Spécifiez le nom de votre organisation (s'il ne s'agit pas d'une organisation réelle, votre nom ou un domaine que vous possédez peut faire l'affaire) et le nom de votre application. Ce devraient être des noms appropriés.

Les deux (org) et (app) peuvent faire partie d'un nom de répertoire, alors suivez ces règles :

  • Utilisez la même chaîne (sensibilité à la casse incluse) pour toutes vos applications qui utilisent cette fonction.
  • Utilisez une chaîne unique pour chaque application et assurez-vous qu'elle ne change pas une fois décidée.
  • Les caractères Unicode sont valides tant qu'ils sont encodés en UTF-8, mais...
  • ... utilisez uniquement des lettres, des chiffres et des espaces. Évitez d'utiliser des points comme dans "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" suffit.

Le pointeur renvoyé par cette fonction reste valide jusqu'à ce que vous l'appeliez à nouveau ou que vous appeliez PHYSFS_deinit(). Ce n'est pas nécessairement un appel rapide, vous devriez donc l'appeler une fois au démarrage et copier la chaîne si vous en avez besoin.

Vous devez supposer que le chemin renvoyé par cette fonction est le seul endroit sûr pour écrire des fichiers (et que PHYSFS_getUserDir() et PHYSFS_getBaseDir(), bien qu'ils puissent être accessibles en écriture, ou même parents du chemin renvoyé, ne sont pas là où vous devriez écrire).

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et d'archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, celui-ci sera ouvert de manière transparente vers le fichier auquel il se réfère.

Par défaut, PhysicsFS vérifiera si un fichier est réellement un lien symbolique lors des appels d'ouverture et échouera si c'est le cas. Sinon, le lien pourrait vous faire sortir des chemins de lecture et d'écriture, compromettant la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Ceci est davantage destiné au sandboxing d'un langage de script du programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une raison valable de créer un lien symbolique, il ne devrait donc pas le désactiver, à moins que vous ne ressentiez un danger spécifique à l'autoriser.

Les liens symboliques ne sont vérifiés que lors du traitement des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire que lorsque vos chemins de recherche et d'écriture, etc., sont définis, les liens symboliques ne sont jamais vérifiés.

Remarque : PHYSFS_stat() vérifie toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si le lien symbolique n'est pas autorisé par cette fonction, PHYSFS_stat() l'ignorera et traitera la requête comme si le chemin n'existait pas.

L'autorisation des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désautoriser le lien.

Convertir une chaîne UTF-8 en une chaîne UCS-4.

Attention

Cette fonction ne signalera pas d'erreur s'il y a des séquences UTF-8 invalides dans la chaîne source. Elle les remplacera par un caractère '?' et continuera.

Les chaînes UCS-4 (également appelées UTF-32) font 32 bits par caractère : wchar_t sous Unix.

Pour garantir que le tampon de destination soit assez grand pour la conversion, veuillez allouer un tampon quatre fois plus grand que le tampon source. void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convertit une chaîne UTF-8 en une chaîne UTF-16.

Attention

Cette fonction ne signalera pas d'erreur s'il y a des séquences UTF-8 invalides dans la chaîne source. Elle les remplacera par un caractère '?' et continuera.

Les chaînes UTF-16 ont 16 bits par caractère (sauf pour certains caractères, qui en ont 32) : TCHAR sous Windows, lors de la compilation avec la prise en charge Unicode. Les versions modernes de Windows utilisent UTF-16. Les versions de Windows antérieures à 2000 utilisaient TCHAR, mais ne géraient que l'UCS-2. UTF-16 est UCS-2, à l'exception des caractères qui prennent 4 octets, qui ne sont de toute façon pas représentables en UCS-2. En cas de doute, vous devriez utiliser UTF-16 à ce stade sur Windows.

Pour vous assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon de double la taille du tampon source. UTF-8 utilise de un à quatre octets par caractère, mais UTF-16 en utilise toujours de deux à quatre, donc une chaîne entièrement ASCII bas verra sa taille doubler ! Les caractères UTF-16 qui prendraient quatre octets prennent également quatre octets en UTF-8, vous n'avez donc pas besoin d'allouer 4x l'espace par précaution : doubler suffira.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais une paire de substitution UTF-16 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Paramètres

src Chaîne source terminée par un caractère nul au format UTF-8.
dst Tampon pour stocker la chaîne UTF-16 convertie.
len Taille, en octets, du tampon de destination.

PHYSFS_sint64 PHYSFS_writeBytes (PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Écrit des données dans un descripteur de fichier PhysicsFS. Le fichier doit être ouvert en écriture.

Veuillez noter que bien que (len) soit un entier non signé de 64 bits, vous êtes limité à 63 bits (9223372036854775807 octets), nous pouvons donc retourner une valeur négative en cas d'erreur. Si la longueur est supérieure à 0x7FFFFFFFFFFFFFFF, cette fonction échouera immédiatement. Pour les systèmes n'ayant pas de type de données 64 bits, vous êtes limité à 31 bits (0x7FFFFFFF, soit 2147483647 octets). Nous supposons que la plupart des choses n'auront pas besoin de faire plusieurs gigaoctets d'E/S en un seul appel, mais pourquoi limiter les choses ?

nombre d'octets écrits. Cela peut être inférieur à (len) ; en cas d'erreur, le système peut essayer d'écrire autant d'octets que possible, une écriture incomplète peut donc se produire.
