typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonctions de rappel qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() plutôt que PHYSFS_EnumFilesCallback ; il offre plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, une entrée par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire des chaînes.

Ces rappels sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournent des listes qui doivent être libérées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin de conserver une liste complète et toutes les chaînes.

Notez que l'ordre des données promis dans les versions de liste n'est pas nécessairement garanti dans les versions de rappel. Vérifiez la documentation des API spécifiques, mais les chaînes ne seront pas nécessairement triées comme vous l'attendiez et vous pourriez obtenir des doublons.

Paramètres

data pointeur vers des données définies par l'utilisateur, passé par l'API qui a finalement appelé le rappel.
origdir chaîne avec le chemin complet, en notation indépendante du système d'exploitation, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire dans lequel vous avez demandé l'énumération, passé au rappel pour votre commodité.
fname le nom du fichier en cours d'énumération. Il peut ne pas être dans l'ordre alphabétique par rapport à d'autres rappels qui ont été appelés, et ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

enum PHYSFS_EnumerateCallbackResult

Énumérateur des résultats des rappels d'énumération.

PHYSFS_ENUM_ERROR
Arrêter l'énumération, signaler une erreur à l'application.
PHYSFS_ENUM_STOP
Arrêter l'énumération, signaler le succès à l'application.
PHYSFS_ENUM_OK
Continuer l'énumération, sans problème.

enum PHYSFS_ErrorCode

Valeurs représentant des causes spécifiques d'échec. Dans la plupart des cas, vous ne devriez vous soucier que si une opération a échoué, mais il y a des moments où vous prévoyez de gérer gracieusement une situation spécifique, nous offrons donc des codes d'erreur spécifiques.

La plupart de ces erreurs sont un peu vagues et ne sont pas des choses que vous pouvez corriger... s'il y a une erreur de permission, par exemple, la seule chose que vous pourriez faire est de transmettre cette information à l'utilisateur et de le laisser gérer la façon de le traiter. Dans la plupart de ces cas, votre programme ne devrait se soucier que du fait qu'il n'a pas atteint ses objectifs, et non de la raison pour laquelle.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenez une liste de fichiers à partir d'un répertoire d'un chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec des erreurs signalées. Internement, PHYSFS_enumerateFiles() appelle cette fonction, puis construit une liste avant de la retourner à l'application, donc la fonctionnalité est identique, sauf la façon dont l'information est présentée à l'application.

Bien que PHYSFS_enumerateFiles() ne retourne pas un tableau, cette fonction appelle une fonction spécifiée par l'application une fois pour chaque élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont pas garantis dans un ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un tri alphabétique. Cette forme signale ce qui est découvert dans chaque archiveur avant de passer au suivant. Même si au sein d'un même archiveur, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout tri que vous trouvez dans ces rappels est purement un hasard. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les fonctions de rappel elles-mêmes sont capables de signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'un objet spécifique et souhaitaient s'arrêter après cela, ou s'ils avaient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur disque ou similaire), il ne pourrait pas le signaler à l'application appelante, il sauterait simplement des éléments ou arrêterait l'énumération, et l'appelant ne saurait pas qu'il avait perdu des données en cours de route.

Maintenant, l'appelant peut s'assurer qu'il a obtenu un ensemble complet de données, et s'il veut arrêter l'énumération plus tôt, sa fonction de rappel aura le contrôle. Voir la documentation de PHYSFS_EnumerateCallback pour plus de détails sur le comportement attendu de votre fonction de rappel.

Paramètres

dir Répertoire, en notation indépendante du système d'exploitation, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin.
d Données définies par l'application transmises à la fonction de rappel. Peut être NULL.

Retour

Une valeur non nulle en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel retourne PHYSFS_ENUM_STOP, cela est considéré comme un succès. Les fonctions de rappel retournant PHYSFS_ENUM_ERROR feront que cette fonction retourne zéro et définira le code d'erreur comme PHYSFS_ERR_APP_CALLBACK.

char **rc = PHYSFS_enumerateFiles("savegames");

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive dont les fichiers chevauchent un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer des révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence de fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

void PHYSFS_permitSymbolicLinks (int allow)

Enable or disable following of symbolic links. Some physical filesystems and archives contain files that are just pointers to other files. On the physical filesystem, opening such a link will (transparently) open the file that is pointed to.

By default, PhysicsFS will check if a file is really a symlink during open calls and fail if it is. Otherwise, the link could take you outside the write and search paths, and compromise security.

If you want to take that risk, call this function with a non-zero parameter. Note that this is more for sandboxing a program's scripting language, in case untrusted scripts try to compromise the system. Generally speaking, a user could very well have a legitimate reason to set up a symlink, so unless you feel there's a specific danger in allowing them, you should permit them.

Symlinks are only explicitly checked when dealing with filenames in platform-independent notation. That is, when setting up your search and write paths, etc, symlinks are never checked for.

Please note that PHYSFS_stat() will always check the path specified; if that path is a symlink, it will not be followed in any case. If symlinks aren't permitted through this function, PHYSFS_stat() ignores them, and would treat the query as if the path didn't exist at all.

Symbolic link permission can be enabled or disabled at any time after you've called PHYSFS_init(), and is disabled by default.

Parameters

allow nonzero to permit symlinks, zero to deny linking.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Faire d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de restreindre les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt, monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer la racine d'une archive à tout moment, modifiant l'arbre de fichiers interpolé (selon où les chemins changent, une archive différente peut fournir divers fichiers). archive répertoire/archive sur lequel changer la racine.
subdir nouveau sous-répertoire à faire de la racine de cette archive.

non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_ucs4stricmp (const PHYSFS_uint32 * str1, const PHYSFS_uint32 * str2)

Comparaison insensible à la casse de deux chaînes UCS-4. C'est un remplacement pour strcasecmp/stricmp qui s'attend à ce que les deux chaînes soient encodées en UCS-4 (alias UTF-32). Il effectuera un « pliage de casse » pour décider si les points de code Unicode dans les chaînes correspondent.

Il indiquera quelle chaîne est « supérieure à » l'autre, mais sachez que cela ne signifie pas nécessairement grand-chose : 'a' peut être « inférieur à » 'b', mais un kuten japonais n'a pas de relation alphabétique significative avec un lambda grec, mais pouvoir attribuer une « valeur » fiable rend les algorithmes de tri possibles, bien que pas entièrement logiques.
