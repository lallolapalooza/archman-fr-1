Valeurs de retour possibles de PHYSFS_EnumerateCallback. Signature de fonction pour les rappels qui énumèrent et retournent des résultats.

Ces valeurs dictent si un rappel d'énumération doit continuer à être déclenché, ou s'arrêter (et pourquoi il s'arrête).

PHYSFS_EnumerateCallback

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'elle peut retourner un résultat du rappel : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être dans un ordre alphabétique par rapport à d'autres rappels qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

PHYSFS_EnumerateCallbackResult

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent les fichiers.

Avertissement

À partir de PhysicsFS 2.1, utilisez plutôt PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; cela vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire d'une chaîne.

Ces rappels sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retourneraient des listes nécessitant d'être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le cas dans les versions de rappel. Consultez la documentation sur les API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être dans un ordre alphabétique par rapport à d'autres rappels qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers à partir d'un répertoire dans un chemin de recherche, en utilisant un callback défini par l'utilisateur, avec des erreurs signalées. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de renvoyer à l'application, donc la fonctionnalité est identique sauf la façon dont les informations sont présentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'utilisateur une fois pour chaque élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés au callback ne sont pas garantis d'être dans un ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit l'ordre alphabétique. Cette forme signale ce qui se trouve dans chaque fichier archivé avant de passer au suivant. Même à l'intérieur d'un fichier archivé, nous ne pouvons pas garantir l'ordre dans lequel les données sont découvertes. Tout ordre que vous pourriez trouver dans ces callbacks est de la pure chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des fichiers, vous pourriez recevoir des noms de fichiers dupliqués.

Cette API et les callbacks eux-mêmes sont capables de signaler des erreurs. Avant cette API, les callbacks devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'un élément spécifique et voulaient s'arrêter après, ou s'il y avait une erreur grave et qu'ils ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, mais sautait simplement des éléments ou arrêtait l'énumération, et l'appelant ne savait pas qu'il avait perdu des données en cours de route.

Maintenant, l'appelant peut être assuré d'avoir obtenu un ensemble complet de données, et son callback a le contrôle sur l'arrêt anticipé de l'énumération. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur la façon dont votre callback devrait se comporter.

dir Répertoire, en notation indépendante du système d'exploitation, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application transmises au rappel. Peut être NULL.

Retour

Non nul en cas de succès, nul en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel renvoie PHYSFS_ENUM_STOP pour s'arrêter tôt, cela est considéré comme un succès. Les rappels renvoyant PHYSFS_ENUM_ERROR feront que cette fonction renvoie nul et définira le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

char **rc = PHYSFS_enumerateFiles("savegames");

for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);

* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav].

Attention

Depuis PhysicsFS 2.1, cette fonction a été déclarée obsolète. Avant PhysicsFS 2.1, c'était le seul moyen d'obtenir des détails d'erreur au-delà de la valeur de retour d'une fonction spécifique. int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter un répertoire ou un fichier au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, bien que la fonction réussisse. Vous ne pouvez pas ajouter le même répertoire à deux points de montage différents : le contrôle des doublons est effectué par rapport au répertoire, pas par rapport au point de montage.

Lorsque vous montez un répertoire, il est ajouté à un système de fichiers virtuel... tous les fichiers de tous les répertoires montés sont interpolés dans une arborescence de répertoires unique. Deux répertoires montés au même endroit (ou un répertoire avec des fichiers qui chevauchent un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans ce cas, le fichier le plus proche dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des répertoires pour remplacer les versions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des répertoires à un endroit spécifique de l'arborescence des fichiers et éviter les chevauchements ; ceci est utile pour les modes téléchargeables qui peuvent écraser les données de l'application ou les leurs.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que l'on attend des systèmes Unix avec le concept familier de « montage ». De plus, plus d'un répertoire peut être monté au même point de montage, ou les points de montage et le contenu des répertoires peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours normalement.

Il est permis de spécifier un lien symbolique vers un répertoire ou un fichier, indépendamment de l'état de PHYSFS_permitSymbolicLinks(). Cette fonction se concentre uniquement sur les liens symboliques dans le répertoire ou le fichier monté.

Paramètres

newDir répertoire ou répertoire à ajouter au chemin, dans une notation système.
mountPoint emplacement dans l'arborescence interpolée où ce répertoire sera monté, dans une notation indépendante. NULL ou « » équivaut à « / ».
appendToPath non nul pour ajouter au chemin, zéro pour préfixer.

Retourne

Non nul si ajouté au chemin, zéro en cas d'erreur (fichier invalide, répertoire décédé, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

PHYSFS_mountIo

Ajoute un fichier, contenu dans un PHYSFS_File handle, à la liste de recherche.

Attention

N'utilisez pas PHYSFS_mount() à moins d'avoir un besoin spécial de bas niveau.

Les fichiers dans les archives peuvent être très lents ! Bien qu'un PHYSFS_File puisse faire un seek même lorsque les données sont compressées, il peut le faire en soustrayant du début et en décompressant tout avant le point de seek. L'utilisation normale des fichiers peut entraîner un grand nombre de seeks en arrière-plan. Ainsi, vous pourriez trouver l'utilisation normale des fichiers extrêmement gênante si elle est montée de cette façon. Planifiez en conséquence : si vous avez, par exemple, un fichier .zip auto-extractible et que vous souhaitez monter quelque chose à l'intérieur, compressez le contenu du fichier intérieur et assurez-vous que le fichier extérieur ne compresse pas trop l'intérieur.

Cette fonction opère exactement comme PHYSFS_mount(), mais prend un PHYSFS_File handle au lieu d'un chemin. Ce handle contient toutes les données du fichier et est utilisé à la place d'un fichier réel sur le système de fichiers physique. Le PHYSFS_File peut être basé sur un fichier réel sur le système de fichiers physique, mais ce n'est pas nécessairement le cas. L'utilisation la plus courante est de monter des fichiers qui se trouvent à l'intérieur d'autres fichiers.

(newDir) doit être une chaîne de caractères unique pour identifier ce fichier. Elle est utilisée pour optimiser la sélection de l'archiveur (si vous le nommez XXXXX.zip, nous pourrions essayer l'archiveur ZIP, par exemple, ou choisir directement un archiveur qui ne repose que sur l'extension du nom). Il n'est pas nécessaire qu'il fasse référence à un fichier réel. Si l'extension du nom n'est pas utile, le système essaiera chaque archiveur jusqu'à ce que l'un fonctionne ou qu'aucun ne fonctionne. Ce nom doit être unique, car le système n'autorisera pas deux fichiers portant le même nom.

(file) doit rester jusqu'à ce que le fichier soit démonté. Lorsque le fichier est démonté, le système appellera PHYSFS_close(file). Si vous souhaitez que ce handle survive, vous devrez l'encapsuler dans un PHYSFS_Io et utiliser PHYSFS_mountIo() à la place.

Si cette fonction échoue, PHYSFS_close(file) n'est pas appelé.

file Le handle PHYSFS_File qui contient les données du fichier.
newDir Le nom de fichier qui peut représenter ce flux.
mountPoint L'emplacement dans l'arborescence interpolée où ce fichier sera "monté", en notation indépendante de la plateforme. NULL ou "" équivaut à "/".
appendToPath Non nul pour ajouter à la liste de recherche, nul pour préfixer.

Retour

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, ouvrir un tel lien ouvrira (transparentement) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous voulez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné au sandboxing du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. De manière générale, un utilisateur pourrait très bien avoir une raison légitime de créer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger particulier à les autoriser, vous devriez les autoriser.

Les liens symboliques sont uniquement explicitement vérifiés lors du traitement des noms de fichiers dans la notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser les liens.

Convertit une chaîne UTF-8 en chaîne UTF-16.

Attention

Cette fonction ne signalera pas d'erreur s'il y a des séquences UTF-8 invalides dans la chaîne source. Elles seront remplacées par un caractère '?' et la conversion se poursuivra.

Les chaînes UTF-16 comportent 16 bits par caractère (sauf pour certains caractères qui en utilisent 32) : TCHAR sous Windows, lors de la compilation avec le support Unicode. Les versions modernes de Windows utilisent UTF-16. Les versions de Windows antérieures à 2000 utilisaient TCHAR, mais ne prenaient en charge qu'UCS-2.
