int PHYSFS_addToSearchPath (const char * newDir, int appendToPath)

Ajoute un répertoire ou un fichier au chemin de recherche.

Obsolète

Depuis PhysicsFS 2.0, utilisez PHYSFS_mount() à la place. Cette fonction n'est qu'un wrapper pour celle-ci.

Cette fonction est équivalente à :

PHYSFS_mount(newDir, NULL, appendToPath);

Vous devriez utiliser cette fonction plutôt que PHYSFS_mount si la compatibilité binaire avec PhysicsFS 1.0 est importante (ce qui pourrait ne pas être le cas pour de nombreux utilisateurs).

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenez une liste de fichiers dans le répertoire d'un chemin de recherche, en utilisant une fonction de rappel définie par l'utilisateur, avec des erreurs signalées. En interne, PHYSFS_enumerateFiles() appelle cette fonction, puis construit une liste avant de la retourner à l'application, donc la fonctionnalité est identique, sauf la manière dont les informations sont présentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction définie par l'application une fois pour chaque élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont pas garantis d'être dans un ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un ordre alphabétique. Cette approche signale ce qui est trouvé dans chaque archive avant de passer à la suivante. Même au sein d'une seule archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout ordre que vous pourriez trouver dans ces fonctions de rappel est pure coïncidence. Ne vous y fiez pas. Comme cela parcourt toute la liste des fichiers, vous pourriez recevoir des noms de fichiers en double.

Cette API et les fonctions de rappel elles-mêmes peuvent signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même si elles ne recherchaient qu'un élément spécifique et voulaient s'arrêter là, ou si elles rencontraient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application ; il sautait simplement des éléments ou détaillait l'énumération, et l'appelant ne saurait pas qu'il manquait des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble complet de données, et sa fonction de rappel a le contrôle sur l'arrêt prématuré de l'énumération. Consultez la documentation de PHYSFS_EnumerateCallback pour plus de détails sur la façon dont votre fonction de rappel doit se comporter.

Paramètres

dir Le répertoire à énumérer, en notation indépendante de la plateforme.
c La fonction de rappel pour notifier les éléments du chemin.
d Les données définies par l'application passées à la fonction de rappel. Peut être NULL.

Retour

Non zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel retourne PHYSFS_ENUM_STOP, cela sera considéré comme un succès. Les fonctions de rappel retournant PHYSFS_ENUM_ERROR feront que cette fonction retourne zéro et définira le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

Remarque

Depuis PhysicsFS 2.1, cette fonction a été « coupée ». Avant PhysicsFS 2.1, c'était le seul moyen d'obtenir des détails d'erreur au-delà de la valeur de retour de base d'une fonction. Il s'agissait intentionnellement d'une chaîne dans plusieurs langues, et non utile pour l'analyse par application. C'était un problème, car le développeur ne choisissait pas la langue au moment de la compilation, et les mainteneurs de PhysicsFS devaient (mal) maintenir une grande quantité de travail de localisation. L'application ne pouvait pas analyser les chaînes, même si elles étaient dans une langue spécifique, car certaines étaient générées dynamiquement. Depuis la version 2.1 et ultérieures, elle renvoie toujours une chaîne statique en anglais ; vous pouvez l'utiliser comme clé pour votre propre localisation, car nous nous sommes engagés à ne pas modifier les chaînes existantes. De plus, si votre application souhaite voir des erreurs spécifiques, nous offrons maintenant une meilleure option : utilisez PHYSFS_getLastErrorCode().

Le pointeur renvoyé pointe vers un tampon interne. Chaque thread a un état d'erreur unique associé, mais chaque fois qu'un nouveau message d'erreur est défini, il écrase le précédent associé à ce thread. Il est sûr d'appeler cette fonction à tout moment, même avant PHYSFS_init().

PHYSFS_getLastError() et PHYSFS_getLastErrorCode() réinitialisent tous deux le même état d'erreur spécifique au thread. Appeler l'un effacera les données de l'autre. Si vous avez besoin des deux, appelez PHYSFS_getLastErrorCode(), puis passez cette valeur à PHYSFS_getErrorByCode().

Depuis PhysicsFS 2.1, cette fonction ne présente que du texte en anglais, mais les chaînes sont statiques, vous pouvez donc les utiliser comme clés dans votre propre dictionnaire de localisation. Ces chaînes sont destinées à être passées directement à l'utilisateur.

Généralement, les applications ne se soucient que de savoir si une fonction a échoué ; cependant, si votre code nécessite plus de spécificités, vous devriez utiliser PHYSFS_getLastErrorCode() à la place de cette fonction.

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Obtenir le chemin spécifique à l'utilisateur et à l'application où les fichiers peuvent être écrits. Fonction d'assistance.

Obtenir le "répertoire de préférences". Ceci est destiné à être l'endroit où les utilisateurs peuvent écrire des fichiers personnels (préférences et sauvegardes de jeux, etc.) spécifiques à votre application. Ce répertoire est unique par utilisateur, par application.

Sous Linux, cela pourrait ressembler à : "/home/bob/.local/share/My Program Name"

Sous Mac OS X, cela pourrait ressembler à : "/Users/bob/Library/Application Support/My Program Name"

(etc.)

Vous devriez probablement utiliser le répertoire de préférences comme répertoire d'écriture, et également le placer près du début de votre chemin de recherche. int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers qui se chevauchent avec un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser les archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce à quoi les personnes familières avec le concept Unix de "montage" pourraient s'attendre. void PHYSFS_permitSymbolicLinks (int allow)

Activez ou désactivez le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (transparencement) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné au sandboxing du langage de script d'un programme, au cas où des scripts non fiables essaieraient de compromettre le système. D'une manière générale, un utilisateur pourrait très bien avoir une raison légitime de créer un lien symbolique, donc à moins que vous ne ressentiez un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lorsque l'on traite des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire que lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser les liens.

Convert a UTF-8 string to a UCS-4 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UCS-4 strings are 32-bits per character. UTF-8 uses from one to four bytes per character. If you need to convert from UTF-8 to UCS-4, you should allocate a buffer that is quadruple the size of the source buffer. This is because a single character in UTF-8 could be four bytes long, while in UCS-4 it is always four bytes long.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UCS-4 sequence at the end. If the buffer length is 0, this function does nothing.

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UCS-4 string.
len Size, in bytes, of destination buffer.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. If you aren't sure, you should be using UTF-16 at this point on Windows.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
len Size, in bytes, of destination buffer.

Veuillez noter que bien que (len) soit un entier non signé de 64 bits, vous êtes limité à 63 bits (9223372036854775807 octets), nous pouvons donc retourner une valeur négative en cas d'erreur.
