C'est le même que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il renvoie un résultat de rappel : si vous cherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter l'énumération. Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate(); cela vous donne plus de contrôle sur le processus.

Celles-ci sont utilisées pour signaler une liste d'entrées de répertoire à un appelant d'origine, une entrée par appel de fonction de rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire d'aucune chaîne.

Notez que l'ordre promis dans les versions basées sur des listes n'est pas nécessairement respecté dans les versions basées sur des rappels. Consultez la documentation spécifique des API, mais les chaînes ne seront pas nécessairement dans l'ordre attendu et vous pourriez obtenir des chaînes en double.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Fold" a Unicode codepoint to a lowercase equivalent. (This is for limited, hardcore use. If you don't immediately see a need for it, you can probably ignore this forever.)

This will convert a Unicode codepoint into its lowercase equivalent. Bogus codepoints and codepoints without a lowercase equivalent will be returned unconverted.

Note that you might get multiple codepoints in return! The German Eszett, for example, will fold down to two lowercase latin 's' codepoints. The theory is that if you fold two strings, one with an Eszett and one with "SS" down, they will match.

Warning

Anyone that is a student of Unicode knows about the "Turkish I" problem. This API does not handle it. Assume this one letter in all of Unicode will definitely fold sort of incorrectly. If you don't know what this is about, you can probably ignore this problem for most of the planet, but perfection is impossible.

Parameters

from The codepoint to fold.
to Buffer to store the folded codepoint values into. This should point to space for at least 3 PHYSFS_uint32 slots.

Returns

The number of codepoints the folding produced. Between 1 and 3.

int PHYSFS_deinit (void )

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). It is usually best to close all write handles yourself before calling this function, so that you can gracefully handle a specific failure.

Once successfully deinitialized, PHYSFS_init() can be called again to restart the subsystem. All default API states are restored at this point, with the exception of any custom allocator you might have specified, which survives between initializations.

Returns

nonzero on success, zero on error. Specifics of the error can be gleaned from PHYSFS_getLastError(). If failure, state of PhysFS is undefined, and probably badly screwed up.

int PHYSFS_delete (const char * filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

Chances are, the bits that make up the file still exist, they are just made available to be written over at a later point. Don't consider this a security method or anything. :)

Parameters

filename Filename to delete.

Returns

nonzero on success, zero on error. Use PHYSFS_getLastErrorCode() to obtain the specific error.

int PHYSFS_deregisterArchiver (const char * ext)

Remove an archiver from the system. If for some reason, you only need your previously-registered archiver to live for a portion of your app's lifetime, you can remove it from the system once you're done with it through this function.

This fails if there are any archives still open that use this archiver.

This function can also remove internally-supplied archivers, like .zip support or whatnot. This could be useful in some situations, like disabling support for them outright or overriding them with your own implementation. Once an internal archiver is disabled like this, PhysicsFS provides no mechanism to recover them, short of calling PHYSFS_deinit() and PHYSFS_init() again.

PHYSFS_deinit() will automatically désenregistrer tous les archiveurs, donc vous n'avez pas besoin de désenregistrer explicitement le vôtre si vous arrêtez proprement par ailleurs.

Paramètres

ext Extension de nom de fichier que l'archiveur gère.

Retourne

Zéro en cas d'erreur, non-zéro en cas de succès.

De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération purement et simplement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons est effectuée sur l'archive et non sur le point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés en un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers chevauchant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept Unix de "montage" pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

La spécification d'un lien symbolique vers une archive ou un répertoire est autorisée ici, quelle que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que des liens symboliques à l'intérieur du répertoire ou de l'archive montée.

newDir répertoire ou archive à ajouter au chemin, en notation dépendante de la plateforme.
mountPoint Emplacement dans l'arbre interpolé où cette archive sera "montée", en notation indépendante de la plateforme. NULL ou "" équivaut à "/".
appendToPath Non nul pour ajouter au chemin de recherche, zéro pour précéder.

Retourne

Non nul si ajouté au chemin, zéro en cas d'échec (archive bidon, répertoire manquant, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_permitSymbolicLinks (int allow)

Permet ou interdit le suivi des liens symboliques. Certains systèmes de fichiers physiques et d'archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, celui-ci sera ouvert de manière transparente vers le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est effectivement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous faire sortir des chemins de lecture et d'écriture, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Remarque : ceci est davantage destiné au sandboxing d'un langage de script du programme, au cas où des scripts non fiables tenteraient de compromettre le système. En général, un utilisateur pourrait avoir une raison valable de définir un lien symbolique, vous ne devriez donc pas le désactiver, à moins que vous ne ressentiez un danger spécifique.

Les liens symboliques ne seront pris en compte que lors de la manipulation de noms de fichiers dans une notation indépendante de la plateforme. Autrement dit, lorsque vous configurez vos chemins de recherche et d'écriture, etc., les liens symboliques ne seront jamais pris en compte.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne le suivra en aucun cas. Si les liens symboliques ne sont pas autorisés via cette fonction, PHYSFS_stat() les ignorera et traitera la requête comme si le chemin n'existait pas.

L'autorisation des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désactiver le lien.

Paramètres

str1 Première chaîne à comparer.
str2 Deuxième chaîne à comparer.

Retour

-1 si str1 est "inférieur" à str2, 1 si il est "supérieur", 0 s'ils sont égaux.

Pour garantir que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon de double la taille du tampon source. UTF-8 étend les points de code Latin1 supérieurs à 127 de 1 à 2 octets, donc la chaîne peut grossir dans certains cas.
