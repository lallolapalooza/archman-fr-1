PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du rappel : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent des fichiers.

Attention

Depuis PhysicsFS 2.1, utilisez plutôt PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; cela vous donne plus de contrôle sur le processus.

Ils sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire d'une chaîne.

Ces rappels sont utilisés, à partir de PhysicsFS 1.1, comme une alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes au préalable.

Soyez conscient que l'ordre promis des données dans les versions de liste n'est pas nécessairement le cas dans les versions de rappel. Vérifiez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, transmis dans le rappel pour votre commodité.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Plie" un point de code Unicode vers son équivalent en minuscules. (Ceci est pour une utilisation limitée et avancée. Si vous ne voyez pas immédiatement un besoin pour cela, vous pouvez probablement l'ignorer pour toujours.)

Ceci convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux qui n'ont pas d'équivalent en minuscules seront retournés sans conversion.

Notez que vous pourriez obtenir plusieurs points de code en retour ! Le s é scharf allemand, par exemple, sera plié en deux points de code latins minuscules 's'. La théorie est que si vous pliez deux chaînes, l'une avec un s é scharf et l'autre avec "SS" vers le bas, elles correspondront.

Attention

Toute personne étudiant Unicode connaît le problème du "I turc". Cette API ne le gère pas. Supposez que cette seule lettre dans tout Unicode sera pliée d'une manière ou d'une autre incorrectement. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la plupart du monde, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Tampon pour stocker les valeurs des points de code pliés. Il doit pointer vers un espace d'au moins 3 emplacements PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialise la bibliothèque PhysicsFS. Cela ferme tous les fichiers ouverts via PhysicsFS, vide les chemins de recherche/écriture, libère la mémoire et invalide toutes vos poignées de fichiers.

Notez que cet appel peut ÉCHOIR s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures sur un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur est tombé en panne, etc.). Il est généralement préférable de fermer toutes les poignées d'écriture vous-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois désinitialisé avec succès, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états par défaut de l'API sont restaurés à ce stade, à l'exception de tout allocateur personnalisé que vous auriez pu spécifier, qui survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les détails de l'erreur peuvent être obtenus à partir de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini, et probablement très endommagé.

int PHYSFS_delete (const char * filename)

Supprime un fichier ou un répertoire. (filename) est spécifié en notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, pas ce à quoi il pointe, que vous ayez "autorisé les liens symboliques" ou non.

Donc, si vous avez défini le répertoire d'écriture sur "C:\mygame\writedir" et que vous appelez PHYSFS_delete("downloads/maps/level1.map") alors le fichier "C:\mygame\writedir\downloads\maps\level1.map" est supprimé du système de fichiers physique, s'il existe et si le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont une poignée de fichier ouverte sur celui-ci (y compris votre programme) ne fermeront pas leurs poignées.

Il y a de fortes chances que les bits qui composent le fichier existent toujours, ils sont juste rendus disponibles pour être écrasés plus tard. Ne considérez pas cela comme une méthode de sécurité ou quoi que ce soit. :)

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

const char *PHYSFS_getPrefDir (const char * org, const char * app)

Obtenir la ruta de directori específica per escriure fitxers, utilitzada per l'usuari i l'aplicació. Funció auxiliar.

Obtenir el "pref dir". És perquè els usuaris escriguin fitxers personals (preferències i jocs desats, etc.) específics de la vostra aplicació. Aquest directori és únic per usuari i per aplicació.

Aquesta funció decideix la ubicació adequada al sistema de fitxers natiu, crea el directori si cal i retorna una cadena en notació del sistema, adequada per passar a PHYSFS_setWriteDir().

A Windows, pot semblar així: "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name"

A Linux, pot semblar així: "/home/bob/.local/share/My Program Name"

A Mac OS X, pot semblar així: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

Hauríeu d'utilitzar el pref dir per a la vostra ruta d'escriptura i també posar-lo al principi de la vostra ruta de cerca. Les versions antigues de PhysicsFS només oferien PHYSFS_getUserDir() i us deixaven decidir on havien d'estar els fitxers sota aquest arbre. Aquesta troba el lloc correcte per a qualsevol plataforma, que no només canvia entre sistemes operatius, sinó també entre versions del mateix sistema operatiu.

Especifiqueu el nom de la vostra organització (si no és una organització real, el vostre nom o un domini d'Internet que posseïu podria servir) i el nom de la vostra aplicació. Aquests han de ser noms correctes.

Tant les cadenes (org) com (app) es poden convertir en part d'un nom de directori, així que seguiu aquestes regles:

  • Intenteu utilitzar la mateixa cadena d'organització (inclosa la sensibilitat a majúscules/minúscules) per a totes les vostres aplicacions que utilitzen aquesta funció.
  • Utilitzeu sempre una cadena d'aplicació única per a cadascuna, i assegureu-vos que no canviï per a una aplicació un cop decidida.
  • Els caràcters Unicode són vàlids, sempre que estiguin codificats com a UTF-8, però...
  • ...només utilitzeu lletres, números i espais. Eviteu caràcters com "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" n'és suficient.

El punter retornat per aquesta funció roman vàlid fins que la truqueu de nou o truqueu PHYSFS_deinit(). No és necessàriament una trucada ràpida, així que hauríeu de trucar-la una vegada a l'inici i copiar la cadena si la necessiteu.

Hauríeu d'assumir que la ruta retornada per aquesta funció és l'únic lloc segur per escriure fitxers (i que PHYSFS_getUserDir() i PHYSFS_getBaseDir(), tot i que puguin ser escriptibles, o fins i tot pares de la ruta retornada, no són on heu d'escriure).

Paràmetres

org nom de la vostra organització.
app nom de la vostra aplicació.

Retorna

cadena de només lectura de la ruta de directori de l'usuari en notació del sistema. NULL si hi ha un problema (creació de directori fallida, etc.).

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons est effectuée par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés en un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers chevauchant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer les versions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; ceci est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou s'écraser mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que les personnes familières avec le concept Unix de "montage" pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

Spécifier un lien symbolique vers une archive ou un répertoire est autorisé ici, quel que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne concerne que les liens symboliques à l'intérieur du répertoire ou de l'archive monté.

Paramètres

newDir répertoire ou archive à ajouter au chemin, en notation spécifique à la plateforme.
mountPoint Emplacement dans l'arbre interpolé où cette archive sera "montée", en notation indépendante de la plateforme. NULL ou "" équivaut à "/".
appendToPath non nul pour ajouter au chemin de recherche, zéro pour préfixer.

Retourne

non nul si ajouté au chemin, zéro en cas d'échec (archive invalide, répertoire manquant, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et architectures contiennent des fichiers qui ne sont que des références à d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, celui-ci sera ouvert de manière transparente pour ouvrir le fichier auquel il fait référence.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous mener hors des chemins de recherche et d'écriture, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Notez que ceci est davantage destiné au sandboxing d'un langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une bonne raison de créer un lien symbolique, vous ne devriez donc pas les désactiver, à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser.

Les liens symboliques ne seront pris en compte que lors de l'utilisation de noms de fichiers dans une notation indépendante du système. Autrement dit, lorsque vous configurez vos chemins de recherche et d'écriture, etc., les liens symboliques ne seront jamais pris en compte.

Note : PHYSFS_stat() vérifie toujours le chemin spécifié ; si ce chemin est un lien symbolique, il sera ignoré dans tous les cas. S'il n'est pas autorisé via cette fonction, PHYSFS_stat() ignorera le lien et traitera la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désactiver le lien.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Fait d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de restreindre les fichiers accessibles dans une archive spécifique. Vous pouvez changer la racine d'une archive à tout moment, modifiant l'arborescence de fichiers interpolée (selon l'endroit où les chemins changent, une archive différente peut fournir divers fichiers). Définir une nouvelle racine n'est pas limité aux archives dans le chemin de recherche ; vous pouvez en définir une sur le répertoire d'écriture, ce qui pourrait être utile si vous avez des fichiers ouverts en écriture et ne pouvez donc pas changer le répertoire d'écriture pour le moment.

NAME

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 — convert and write an unsigned integer in a specific endianness

#include <physfs.h>

DESCRIPTION

These functions convert an unsigned integer from the platform's native byte order to the specified endianness (big-endian or little-endian) and write it to the specified file.

These are convenience functions. You can achieve the same result by using PHYSFS_writeLE16(), PHYSFS_writeBE16(), PHYSFS_writeLE32(), PHYSFS_writeBE32(), PHYSFS_writeLE64(), and PHYSFS_writeBE64() directly.
