PHYSFS_EnumerateCallback

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du rappel : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé une énumération, passé dans le rappel pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport aux autres rappels qui se sont déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

PHYSFS_EnumerateCallbackResult

typedef void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez plutôt PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; cela vous donne plus de contrôle sur le processus.

Ils sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire d'une chaîne.

Ces rappels sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le même dans les versions de rappel. Consultez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé une énumération, passé dans le rappel pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport aux autres rappels qui se sont déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

enum PHYSFS_ErrorCode

Valeurs qui représentent des causes spécifiques d'échec. La plupart du temps, vous ne devriez vous préoccuper que de savoir si une opération donnée a échoué ou non, mais il peut y avoir des occasions où vous prévoyez de gérer gracieusement un cas d'échec spécifique, nous fournissons donc des codes d'erreur spécifiques.

La plupart de ces erreurs sont un peu vagues, et la plupart ne sont pas des choses que vous pouvez corriger... s'il y a une erreur de permission, par exemple, tout ce que vous pouvez vraiment faire est de transmettre cette information à l'utilisateur et de le laisser trouver comment la gérer. Dans la plupart de ces cas, votre programme ne devrait se soucier que de l'échec de l'accomplissement de ses objectifs, et pas spécifiquement de la raison.

Désinitialise la bibliothèque PhysicsFS. Cela ferme tous les fichiers ouverts via PhysicsFS, vide les chemins de recherche/écriture, libère la mémoire et invalide tous vos handles de fichier.

Un répertoire doit être vide avant que cet appel puisse le supprimer.

La suppression d'un lien symbolique supprime le lien, pas ce vers quoi il pointe, que vous ayez « autorisé les symlinks » ou non.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers d'un répertoire du chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec rapport des erreurs. Interne­ment, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique sauf la manière dont l'information est représentée à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons trouvé [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis dans aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale tout ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une seule archive, nous ne pouvons garantir l'ordre de découverte des données. Tout tri que vous trouvez dans ces appels est pure chance. Ne vous y fiez pas. Comme cette fonction parcourt toute la liste des archives, vous pourriez recevoir des noms de fichiers en double.

Cette API et les fonctions de rappel elles-mêmes sont capables de signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même si elles ne recherchaient qu'un élément spécifique et voulaient s'arrêter après, ou si elles avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération immédiatement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Désormais, l'appelant peut être sûr d'avoir obtenu un ensemble complet de données, et sa fonction de rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation pour PHYSFS_EnumerateCallback pour plus de détails sur le comportement attendu de votre fonction de rappel.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

Retourne

Non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel retourne PHYSFS_ENUM_STOP pour arrêter prématurément, cela sera considéré comme un succès. Les fonctions de rappel retournant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

Obtenir une liste de fichiers d'un répertoire du chemin de recherche.

Attention

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction retournait autant d'éléments que possible face à une condition d'échec (manque de mémoire, erreur d'E/S disque, etc.). Comme cela empêchait les applications de distinguer un succès complet d'un échec partiel, et comme la fonction pouvait toujours retourner NULL pour signaler des échecs catastrophiques de toute façon, dans PhysicsFS 2.1 la politique de cette fonction a changé : elle retournera soit une liste complète de résultats, soit NULL en cas d'échec de quelque nature que ce soit, nous garantissons ainsi que l'énumération s'est déroulée jusqu'à son terme et n'a pas de lacunes dans ses résultats.

Les répertoires correspondants sont interpolés. C'est-à-dire que si "C:\mydir" se trouve dans le chemin de recherche et contient un répertoire "savegames" qui contient "x.sav", "y.sav", et "z.sav", et qu'il y a aussi un répertoire "C:\userdir" dans le chemin de recherche qui a un sous-répertoire "savegames" avec "w.sav", alors le code suivant :

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Nous avons trouvé [%s].\n", *i);
PHYSFS_freeList(rc);
* Nous avons trouvé [x.sav].
* Nous avons trouvé [y.sav].
* Nous avons trouvé [z.sav].
* Nous avons trouvé [w.sav]..fi
N'hésitez pas à trier la liste comme vous le souhaitez. Cependant, les données retournées ne contiendront jamais de doublons, et seront toujours triées par ordre alphabétique (ou plutôt : sensible à la casse Unicode).
N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur retournée par cette fonction lorsque vous avez terminé.

dir répertoire en notation indépendante de la plateforme à énumérer.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons est effectuée par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive dont les fichiers chevauchent un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser les archives pour remplacer les versions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer les archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce à quoi peuvent s'attendre ceux qui connaissent le concept de "montage" Unix. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou des points de montage et des contenus d'archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

void PHYSFS_permitSymbolicLinks (int allow)

Enables or disables the following of symbolic links. Some physical and archive file systems contain files that are simply references to other files. When opening such a link on a physical file system, the file it refers to will be opened automatically.

By default, PhysicsFS checks if a file is actually a symbolic link during open calls and fails if it is. Otherwise, the link might lead you outside of the read and write paths, compromising security.

If you want to take that risk, call this function with a non-zero value. Note that this is mostly for sandboxing scripting languages in programs, in case untrusted scripts try to compromise the system. Generally, a user might have a legitimate reason to set up a symbolic link, so you should not permit it, unless you feel there's a specific danger in allowing them.

Symbolic links are only checked when dealing with platform-independent path notation. That is, when setting up your search and write paths, etc., symbolic links are never checked.

Note: PHYSFS_stat() always checks the specified path; if it's a symbolic link, it will not be followed under any circumstances. If not permitted via this function, PHYSFS_stat() will ignore the link and treat the query as if the path didn't exist.

Symbolic link permission can be enabled or disabled at any time after PHYSFS_init() has been called, and it is disabled by default.

Parameters

allow non-zero to permit symbolic links, zero to disallow them.

int PHYSFS_utf8stricmp (const char * str1, const char * str2)

Comparaison insensible à la casse de deux chaînes UTF-8. C'est un remplacement de strcasecmp/stricmp qui attend que les deux chaînes soient en encodage UTF-8. Il effectuera un « pliage de casse » pour déterminer si les points de code Unicode dans les chaînes correspondent.

Si les deux chaînes sont exclusivement des caractères ASCII bas, cela fonctionnera correctement, car c'est aussi du UTF-8 valide. S'il y a des caractères ASCII élevés, cela ne fera pas ce que vous attendez !

Il indiquera quelle chaîne est « supérieure » à l'autre, mais soyez conscient que cela ne signifie pas nécessairement quelque chose : 'a' peut être « inférieur » à 'b', mais un kuten japonais n'a aucune relation alphabétique significative avec un lambda grec, mais pouvoir attribuer une « valeur » fiable permet des algorithmes de tri, même s'ils ne sont pas entièrement sains. Dans la plupart des cas, vous devriez traiter la valeur de retour comme « égal » ou « pas égal ».

Comme stricmp, cela attend que les deux chaînes soient terminées par un caractère nul.

Paramètres

str1 Première chaîne à comparer.
str2 Deuxième chaîne à comparer.

Retourne

-1 si str1 est « inférieur » à str2, 1 si « supérieur », 0 si égal.

Convert a UTF-8 string to a UCS-4 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UCS-4 strings are 32-bits per character. UTF-8 strings use one to four bytes per character.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is quadruple the size of the source buffer. This is because a single UTF-8 character could take up to 4 bytes, and each UCS-4 character is 4 bytes. UTF-8 uses from one to four bytes per character, but UCS-4 always uses four bytes per character.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 *dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. If you aren't sure, you should be using UTF-16 at this point on Windows.

UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
