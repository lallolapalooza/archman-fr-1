Possible return values of PHYSFS_EnumerateCallback. Function signature for callbacks that enumerate and return results.

These values determine if an enumeration callback should continue or stop (and why).

PHYSFS_EnumerateCallback

PHYSFS_enumerate

This is the same as PhysicsFS 2.0's PHYSFS_EnumFilesCallback, except that it can return a result from the callback: i.e., if you are searching for something specific, once you find it, you can tell PhysicsFS to stop enumerating. This is used with PHYSFS_enumerate(), which hopefully you've gotten correctly. :)

Parameters

data User-supplied data pointer, passed in by the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory that contains this file. In most cases, this is the directory you asked to enumerate, passed into the callback for your convenience.
fname The filename being enumerated. It might not be in alphabetical order compared to other callbacks that have been called, and it will not contain the full path. You can recreate the full path with $origdir/$fname ... The file might be a subdirectory, a file, a symlink, etc.

Returns

A value of PHYSFS_EnumerateCallbackResult. All other values are (currently) undefined; do not use them.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

Since PhysicsFS 2.1, use PHYSFS_EnumerateCallback with PHYSFS_enumerate() for more control over the process.

These are used to report a list of directory entries to an original caller, one entry per callback. All strings are UTF-8 encoded. The functions should not attempt to modify or free the memory of any strings.

These callbacks are used, since PhysicsFS 1.1, as an alternative to functions that return lists that must be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate a full list and all the strings at once.

You should be aware that the order promised in list-based versions is not necessarily the same in callback-based versions. Check the documentation of specific APIs, but strings are not necessarily sorted alphabetically and you might get duplicates.

data User-supplied data pointer, passed in by the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory that contains this file. In most cases, this is the directory you asked to enumerate, passed into the callback for your convenience.
fname The filename being enumerated. It might not be in alphabetical order compared to other callbacks that have been called, and it will not contain the full path. You can recreate the full path with $origdir/$fname ... The file might be a subdirectory, a file, a symlink, etc.

enum PHYSFS_ErrorCode

Values that represent specific reasons for failure. Most of the time, you should only care whether an operation failed, but there are occasions where you plan to handle a specific failure case gracefully, so we offer specific error codes.

Most of these errors are a bit vague and aren't things you can fix... if there's a permissions error, for example, all you can really do is pass that information up to the user and let them figure out how to handle it. In most of these cases, your program should just worry that it failed to meet its goals, and not care specifically why.

Obtenir une liste de fichiers d'un répertoire d'un chemin de recherche, en utilisant un callback défini par l'application, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de la retourner à l'application, donc la fonctionnalité est identique, à l'exception de la manière dont les informations sont présentées à l'application.

Différente de PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois pour chaque élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // Donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés au callback ne sont garantis dans aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un tri alphabétique. Cette forme signale ce qui est trouvé dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout tri que vous trouvez dans ces callbacks est juste de la pure chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les callbacks eux-mêmes sont capables de signaler des erreurs. Avant cette API, les callbacks devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'un objet spécifique et souhaitaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application, il pouvait simplement ignorer les éléments ou arrêter l'énumération et l'appelant ne saurait pas qu'il manquait des données.

Maintenant, l'appelant peut s'assurer d'avoir obtenu un ensemble complet de données, et son callback contrôle s'il veut arrêter l'énumération plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur la manière dont votre callback doit se comporter.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive dont les fichiers chevauchent un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un endroit spécifique dans l'arborescence des fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient écraser des données d'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept de « montage » Unix pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archivés contiennent des fichiers qui ne sont que des références à d'autres fichiers. L'ouverture d'un lien symbolique physique ouvrira transparentement le fichier auquel il fait référence.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Faire d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de restreindre les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt, monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer la racine d'une archive à tout moment, modifiant l'arborescence de fichiers interpolée (selon où les chemins changent, une archive différente peut fournir divers fichiers). Définir une nouvelle racine n'est pas limité aux archives dans le chemin de recherche ; vous pouvez en définir une sur le répertoire d'écriture également, ce qui peut être utile si vous avez des fichiers ouverts en écriture et ne pouvez donc pas changer le répertoire d'écriture pour le moment.

Il n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme racine d'une archive ; cependant, aucun fichier ne sera visible dans ce cas. Si les répertoires manquants finissent par être créés (un mkdir sur le système de fichiers physique, etc.), cela sera reflété dans l'arbre interpolé.

archive répertoire/archive dont changer la racine.
subdir nouveau sous-répertoire à faire de la racine de cette archive.

non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.
