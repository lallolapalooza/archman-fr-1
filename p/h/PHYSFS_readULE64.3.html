#define PHYSFS_VERSION

The version of the library you compiled against. This is a combined integer, where the major version is the high byte, the minor version is the middle byte, and the patch version is the low byte. For example, if you compiled against PhysicsFS 2.0.1, then PHYSFS_VERSION would be 0x020001.

Note

This macro is only useful for compile-time checks. At runtime, you may dynamically link against a slightly newer or older version of the library than the one your header files were compiled against. The runtime version can be determined with PHYSFS_getLinkedVersion().

int PHYSfs_init (const char *argv0)

Initialise the PhysicsFS library. This function should be called before any other PhysicsFS function. It is safe to call this multiple times; it will simply return a non-zero value if PhysicsFS has already been initialized.

The argv0 parameter is used to determine the location of user-defined preferences and the current working directory. Ideally, it should be the path to the executable. If you don't have this, you can pass NULL, but be aware that some functionality might not work correctly.

Parameters

argv0 The path to the executable, used for determining configuration file locations and the current working directory.

Returns Non-zero on success, zero on failure.

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du rappel : à savoir : si vous cherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous avons espérons bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, transmis depuis l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être en ordre alphabétique par rapport à d'autres rappels qui se sont déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers, physiques et archivés, contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Lorsque vous ouvrez un lien symbolique physique, il sera ouvert de manière transparente vers le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait pointer vers un endroit en dehors de la portée d'écriture et de recherche, compromettant la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Ceci est davantage destiné au sandboxing d'un langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une raison valable de définir un lien symbolique, vous ne devriez donc pas les désactiver, à moins que vous ne ressentiez un danger spécifique.

Les liens symboliques ne seront explicitement suivis que lorsqu'il s'agit de noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire lorsque vos chemins de recherche et d'écriture, etc., sont définis, les liens symboliques ne seront jamais examinés pour vérification.

La permissibilité des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Configure buffering for a file handle.

By default, PhysicsFS uses buffered I/O. This means that reads and writes are not necessarily synchronous.

If you set a buffer size, PhysicsFS will allocate memory for it. Any read or write operation on this file handle will use this buffer. A call to PHYSFS_flush() is required to force the buffer to be written to disk. If you don't explicitly call PHYSFS_flush(), the buffer will be written to disk automatically when the file is closed, but this may not happen at the time you expect.

If you set bufsize to zero, any existing buffer for this file handle will be freed, and all read and write operations will be performed synchronously. This means that disk I/O will happen immediately.

  • Setting a buffer size of zero can fail if the file handle is opened for read-only access and the buffer cannot be flushed to disk.
  • Allocating memory for the buffer might fail.
  • Flushing the buffer to disk might fail.

The seeking operations are transparently buffered. A seek will always be possible, regardless of whether buffering is enabled or disabled.

You can resize an existing buffer by calling this function more than once on the same file handle. Setting the buffer size to zero will free an existing buffer.

PhysicsFS file handles are unbuffered by default.

Please check the return value of this function! Failures can include not being able to seek backwards in a read-only file when removing the buffer, not being able to allocate the buffer, and not being able to flush the buffer to disk, among other unexpected problems.

PHYSFS_sint64 PHYSFS_writeBytes (PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Écrire des données dans un fichier PhysicsFS. Le fichier doit être ouvert en écriture.

Remarque : bien que (len) soit un entier non signé de 64 bits, vous êtes limité à 63 bits (9223372036854775807 octets), nous pouvons donc retourner une valeur négative en cas d'erreur. Si la longueur est supérieure à 0x7FFFFFFFFFFFFFFF, cette fonction échouera immédiatement. Pour les systèmes sans type 64 bits, vous êtes limité à 31 bits (0x7FFFFFFF, soit 2147483647 octets). Nous supposons que presque personne n'aura besoin de faire plusieurs gigaoctets d'E/S en un seul appel, mais pourquoi limiter les choses ?
