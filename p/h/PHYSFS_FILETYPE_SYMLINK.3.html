PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du callback : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent des fichiers.

Attention

À partir de PhysicsFS 2.1, utilisez plutôt PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; cela vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de ces chaînes.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre promis des données dans les versions de liste n'est pas nécessairement le cas dans les versions de callback. Vérifiez la documentation sur les API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé une énumération, transmis dans le callback pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être dans un ordre alphabétique par rapport aux autres callbacks qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Valeurs qui représentent des causes spécifiques d'échec. La plupart du temps, vous ne devriez vous soucier que de savoir si une opération donnée a échoué ou non, mais il peut y avoir des occasions où vous prévoyez de gérer gracieusement un cas d'échec spécifique, nous fournissons donc des codes d'erreur spécifiques.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Plier" un point de code Unicode vers son équivalent en minuscules. (C'est pour un usage limité et très spécifique. Si vous ne voyez pas immédiatement un besoin pour cela, vous pouvez probablement ignorer cette fonction pour toujours.)

Ceci convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux n'ayant pas d'équivalent en minuscules seront retournés sans être modifiés.

Notez que vous pourriez obtenir plusieurs points de code en retour ! L'Eszett allemand, par exemple, sera plié en deux points de code latins en minuscules 's'. La théorie est que si vous pliez deux chaînes, l'une avec un Eszett et l'autre avec "SS", elles correspondront.

Attention

Quiconque est étudiant en Unicode connaît le problème du "I turc". Cette API ne le gère pas. Supposez que cette seule lettre dans tout Unicode sera pliée d'une manière quelque peu incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la majeure partie de la planète, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Tampon pour stocker les valeurs de points de code pliés. Il doit pointer vers un espace pour au moins 3 emplacements PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialiser la bibliothèque PhysicsFS. Cela ferme tous les fichiers ouverts via PhysicsFS, efface les chemins de recherche/écriture, libère la mémoire et invalide tous vos descripteurs de fichiers.

Notez que cet appel peut ÉCHOUEE s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures vers un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur est tombé en panne, etc.). Il est généralement préférable de fermer tous les descripteurs d'écriture vous-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois avec succès désinitialisé, PHYSFS_init() peut être rappelé pour redémarrer le sous-système. Tous les états par défaut de l'API sont restaurés à ce moment-là, à l'exception de tout allocateur personnalisé que vous auriez pu spécifier, qui survit entre les initialisations.

Retourne

une valeur non nulle en cas de succès, zéro en cas d'erreur. Les détails de l'erreur peuvent être obtenus auprès de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini et probablement gravement endommagé.

int PHYSFS_delete (const char * filename)

Supprimer un fichier ou un répertoire. (nom de fichier) est spécifié dans une notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, pas ce qu'il pointe, que vous ayez ou non "autorisé les liens symboliques".

Donc, si vous avez défini le répertoire d'écriture sur "C:\monjeu\repertoires_ecriture" et appelez PHYSFS_delete("telechargements/cartes/niveau1.carte") alors le fichier "C:\monjeu\repertoires_ecriture\telechargements\cartes\niveau1.carte" est supprimé du système de fichiers physique, s'il existe et si le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont un descripteur de fichier ouvert pour celui-ci (y compris votre programme) ne fermeront pas leurs descripteurs.

Il y a de fortes chances que les bits qui composent le fichier existent toujours, ils sont simplement rendus disponibles pour être écrasés plus tard. Ne considérez pas cela comme une méthode de sécurité ou quoi que ce soit. :)

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtener una lista de archivos en una carpeta de ruta de búsqueda, usando un callback definido por el usuario, con errores reportados. Internamente, PHYSFS_enumerateFiles() solo llama a esta función y luego construye una lista antes de devolver a la aplicación, así que la funcionalidad es idéntica, excepto por cómo la información se presenta a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve un array. En cambio, llama a una función especificada por el aplicativo una vez por cada elemento de la ruta de búsqueda:

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSfs_ENUM_OK;  // dar más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Los items enviados al callback no están garantizados para estar en ningún orden. No se realiza ningún ordenamiento en este nivel, y si necesitas eso, deberías usar PHYSFS_enumerateFiles(), que garantiza el orden alfabético. Esta forma reporta lo que se encuentra en cada arco de datos antes de moverse a la siguiente. Even within one archive, we can't guarantee the order in which data is discovered. Any sorting you find in these callbacks is just pure luck. Do not rely on it. Como esta camina por toda la lista de arcos, puedes recibir nombres de archivos duplicados.

Esta API y los callbacks mismos son capaces de reportar errores. Antes de esta API, los callbacks tenían que aceptar cada elemento enumerado, incluso si solo buscaban un elemento específico y querían detenerse allí, o tenían un error serio y no podían notificar a nadie. Además, si PhysicsFS mismo tenia un problema (error de disco o lo que sea), no podría reportarlo a la aplicación, simplemente pasaría a los elementos o detendría la enumeración, y el llamador no sabería que perdió datos durante el proceso.

Ahora el llamador puede asegurarse de que obtuvo un conjunto de datos completo, y su callback puede controlar si quiere detener la enumeración temprano. Ve la documentación para PHYSFS_EnumerateCallback para detalles de cómo debería comportarse su callback.

c Función de callback para notificar sobre elementos de ruta.
d Datos definidos por el aplicativo pasado a la callback. Puede ser NULL.

No cero en éxito, cero en fallo. Usa PHYSFS_getLastErrorCode() para obtener el error específico. Si el callback devuelve PHYSFS_ENUM_STOP para detener temprano, esto se considera éxito. This function will decide the appropriate location in the native filesystem, create the directory if necessary, and return a string in platform-dependent notation, suitable for passing to PHYSFS_setWriteDir().

On Windows, this might look like: "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name"

On Linux, this might look like: "/home/bob/.local/share/My Program Name"

On Mac OS X, this might look like: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

You should probably use the pref dir for your write dir, and also put it near the beginning of your search path. Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left you to figure out where the files should go under that tree. This finds the correct location for whatever platform, which not only changes between operating systems, but also versions of the same operating system.

You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might do) and the name of your application. These should be proper names.

Both the (org) and (app) strings may become part of a directory name, so please follow these rules:

  • Try to use the same org string (including case-sensitivity) for all your applications that use this function.
  • Always use a unique app string for each one, and make sure it never changes for an app once you've decided on it.
  • Unicode characters are legal, as long as it's UTF-8 encoded, but...
  • ...only use letters, numbers, and spaces. Avoid punctuation like "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" is sufficient.

The pointer returned by this function remains valid until you call this function again, or call PHYSFS_deinit(). This is not necessarily a fast call, though, so you should call this once at startup and copy the string if you need it.

You should assume the path returned by this function is the only safe place to write files (and that PHYSFS_getUserDir() and PHYSFS_getBaseDir(), while they might be writable, or even parents of the returned path, aren't where you should be writing things).

app The name of your application.

Figure out where in the search path a file resides. The file is specified in platform-independent notation. The returned filename will be the element of the search path where the file was found, which may be a directory, or an archive. Even if there are multiple matches in different parts of the search path, only the first one found is used, just like when opening a file.

So, if you look for "maps/level1.map", and C:\mygame is in your search path and C:\mygame\maps\level1.map exists, then "C:\mygame" is returned.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendsWithPath)

Ajouter une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons est effectuée par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers chevauchant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un endroit spécifique de l'arborescence des fichiers et éviter les chevauchements ; ceci est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou les uns les autres, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept de montage Unix pourraient attendre. De plus, plusieurs archives peuvent être montées au même point de montage, ou des points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

Spécifier un lien symbolique vers une archive ou un répertoire est autorisé ici, quelle que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

Prévoyez en conséquence : si vous avez, par exemple, un fichier .zip auto-extractible et que vous souhaitez monter quelque chose à l'intérieur, compressez le contenu de l'archive interne et assurez-vous que le fichier .zip externe ne compresse pas l'archive interne.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes et archives physiques contiennent des fichiers qui ne sont que des références à d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, le lien ouvrira de manière transparente le fichier auquel il fait référence.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Autrement, le lien pourrait vous faire sortir du répertoire de lecture et d'écriture, compromettant ainsi la sécurité.

Si vous souhaitez assumer ce risque, appelez cette fonction avec une valeur non nulle. Notez que cela concerne davantage le sandboxing d'un langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. En général, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas les désactiver, à moins que vous ne pensiez qu'il existe un risque spécifique.

Les liens symboliques ne seront explicitement vus que lors de la manipulation de noms de fichiers dans une notation indépendante du système. Autrement dit, lorsque vos répertoires de recherche et d'écriture, etc., sont définis, les liens symboliques ne seront jamais vus.

Notez que PHYSFS_stat() vérifie toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. S'il n'est pas autorisé via cette fonction, PHYSFS_stat() ignorera le lien et traitera la requête comme si le chemin n'existait pas.

Convertit une chaîne UTF-8 en une chaîne Latin1. Les chaînes Latin1 sont de 8 bits par caractère : un encodage populaire de type "high ASCII".

Pour s'assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon de double la taille du tampon source. UTF-8 étend les points de code Latin1 supérieurs à 127 de 1 à 2 octets, donc la chaîne peut grossir dans certains cas.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Veuillez noter que nous ne fournissons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer la plupart des points de code Unicode. C'est un encodage hérité ; vous devriez toujours vous en éloigner.

src Chaîne source terminée par un caractère nul au format Latin1.
dst Tampon pour stocker la chaîne UTF-8 convertie.
len Taille, en octets, du tampon de destination.
