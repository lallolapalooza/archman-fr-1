typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent des fichiers.

Attention

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() pour avoir plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, une entrée par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire de quelque chaîne que ce soit.

Ces callbacks sont utilisés, depuis PhysicsFS 1.1, comme une alternative aux fonctions qui retournent des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes au début.

Notez que l'ordre promis des données dans les versions de liste n'est pas nécessairement le cas dans les versions de callback. Consultez la documentation spécifique des API, mais les chaînes peuvent ne pas être triées comme vous l'attendriez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data pointeur vers des données définies par l'utilisateur, transmis via l'API qui a finalement appelé le callback.
origdir une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire pour lequel vous avez demandé l'énumération, transmis au callback pour votre commodité.
fname le nom du fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport à d'autres callbacks qui ont été appelés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

« Plier » un point de code Unicode vers son équivalent en minuscule. (Ceci est pour un usage limité et avancé. Si vous ne voyez pas immédiatement un besoin pour cela, vous pouvez probablement ignorer cette fonction pour toujours.)

Ceci convertira un point de code Unicode en son équivalent en minuscule. Les points de code invalides et ceux n'ayant pas d'équivalent en minuscule seront retournés sans conversion.

Notez que vous pourriez obtenir plusieurs points de code en retour ! L'Eszett allemand, par exemple, sera réduit à deux points de code en minuscule 's'. La théorie est que si vous réduisez deux chaînes, l'une avec un Eszett et l'autre avec "SS", elles correspondront.

Attention

Toute personne étudiant Unicode connaît le problème de l'"I turc". Cette API ne le gère pas. Supposez que cette seule lettre dans tout Unicode sera pliée de manière plutôt incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la majeure partie de la planète, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Tampon pour stocker les valeurs des points de code pliés. Il doit pointer vers un espace pour au moins 3 emplacements de PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialiser la bibliothèque PhysicsFS. Ceci ferme tous les fichiers ouverts via PhysicsFS, efface les chemins de recherche/écriture, libère la mémoire et invalide toutes vos poignées de fichier.

Notez que cet appel peut ÉCHOUE si un fichier ouvert en écriture refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures sur un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur est tombé en panne, etc.). Il est généralement préférable de fermer toutes les poignées d'écriture vous-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois désinitialisé avec succès, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états par défaut de l'API sont restaurés à ce stade, à l'exception de tout allocateur personnalisé que vous auriez pu spécifier, qui survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les détails de l'erreur peuvent être obtenus à partir de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini, et probablement très perturbé.

int PHYSFS_delete (const char * filename)

Supprimer un fichier ou un répertoire. (filename) est spécifié dans une notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, et non ce vers quoi il pointe, indépendamment du fait que vous ayez « autorisé les liens symboliques » ou non.

Donc, si vous avez défini le répertoire d'écriture sur "C:\mygame\writedir" et que vous appelez PHYSFS_delete("downloads/maps/level1.map"), alors le fichier "C:\mygame\writedir\downloads\maps\level1.map" est supprimé du système de fichiers physique, s'il existe et si le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont une poignée de fichier ouverte dessus (y compris votre programme) ne fermeront pas leurs poignées.

Il y a de fortes chances que les bits qui composent le fichier existent toujours, ils sont juste rendus disponibles pour être écrasés plus tard. Ne considérez pas cela comme une méthode de sécurité ou autre. :)

Paramètres

filename Nom du fichier à supprimer.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_deregisterArchiver (const char * ext)

Supprimer un archiveur du système. Si pour une raison quelconque, vous n'avez besoin que de votre archiveur précédemment enregistré qu'une partie de la durée de vie de votre application, vous pouvez le retirer du système une fois que vous avez terminé avec lui via cette fonction.

Ceci échouera s'il y a encore des archives ouvertes qui utilisent cet archiveur.

Cette fonction peut également supprimer des archiveurs fournis en interne, tels que le support .zip ou autre. Ceci pourrait être utile dans certaines situations, comme désactiver complètement leur support ou les remplacer par votre propre implémentation. Une fois qu'un archiveur interne est désactivé ainsi, PhysicsFS ne fournit aucun mécanisme pour les récupérer, à part appeler PHYSFS_deinit() et PHYSFS_init() à nouveau.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir una lista de archivos de un directorio de una ruta de búsqueda, utilizando un callback definido por la aplicación, con errores reportados. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego construye una lista antes de devolver a la aplicación, por lo que la funcionalidad es idéntica excepto por cómo la información se presenta a la aplicación.

Diferentemente de PHYSFS_enumerateFiles(), esta función no devuelve un array. En cambio, llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSfs_ENUM_OK;  // me da más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Los elementos enviados al callback no están garantizados en ningún orden específico. No hay ordenamiento realizado en este nivel, y si necesitas ese, deberías usar PHYSFS_enumerateFiles(), que garantiza el orden alfabético. Esta forma reporta lo que se encuentra en cada archivo archivado antes de moverse a la siguiente. Even within one archive, we can't guarantee the order in which data is discovered. Any sorting you find in these callbacks is just pure luck. Do not rely on it. Como esta camina por toda la lista de archivos, puedes recibir nombres de archivos duplicados.

Esta API y los callbacks mismos pueden reportar errores. Antes de esta API, los callbacks tenían que aceptar cada elemento enumerado, incluso si solo buscaban un objeto específico y querían detenerse allí, o si tenía un error grave y no podía alertar a nadie. Además, si PhysicsFS mismo tenía un problema (error de disco o algo así), no podía reportarla a la aplicación llamante, simplemente pasaría a omitir elementos o detener la enumeración completamente, y la llamante no sabría que había perdido algunos datos durante el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto completo de datos, y si quiere detener la enumeración tempranamente, su callback tiene control. Consulta la documentación para PHYSFS_EnumerateCallback sobre cómo debe comportarse su callback.

Parámetros

dir Director, en notación independiente de la plataforma, a enumerar.
c Función de callback para notificar sobre elementos de la ruta.
d Datos definidos por el aplicador que se pasan al callback. Puede ser NULL.

Retorno

No cero en éxito, cero en falla. Usa PHYSFS_getLastErrorCode() para obtener el error específico. Si el callback devuelve PHYSFS_ENUM_STOP, este se considera éxito. Los callbacks devolviendo PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezca el código de error en PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtener una lista de archivos de un directorio de una ruta de búsqueda.

Advertencia

En versiones de PhysicsFS anteriores a 2.1, esta función devolvería tantos elementos como fuera posible en caso de una condición de error (error de memoria, error de I/O de disco, etc). Ya que esto hacía que los aplicadores no distinguieran entre éxito completo y falla parcial, y ya que la función podía siempre devolver NULL para reportar fallos catastróficos, en PhysicsFS 2.1 esta política cambió: devolverá un listado de resultados completos o NULL en caso de cualquier falla, así garantizando que la enumeración se completó y que no hay huecos en sus resultados.

Directorios que coinciden se interpolan. Es decir, si "C:\\mydir" está en la ruta de búsqueda y contiene un directorio "savegames" que contiene "x.sav", "y.sav" y "z.sav", y hay también un "C:\\userdir" en la ruta de búsqueda que tenga un directorio "savegames" con "w.sav", entonces el siguiente código:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
 * We've got [x.sav].
 * We've got [y.sav].
 * We've got [z.sav].
 * We've got [w.sav]..
Libremente puedes ordenar la lista como quieras. Sin embargo, el dato devuelto siempre contendrá sin duplicados y siempre estarán ordenados alfabéticamente (aunque sea ordenado en Unicode mayúsculas). No olvides llamar a PHYSFS_freeList() con el valor devuelto de esta función cuando hayas terminado con él.

Obsolète

Attention

Depuis PhysicsFS 2.1, cette fonction a été obscurcie. Avant PhysicsFS 2.1, c'était le seul moyen d'obtenir des détails d'erreur en dehors de l'évaluation de base d'une fonction. C'était destiné à être une chaîne de texte en plusieurs langues et n'était pas utile pour l'analyse par les applications. C'était un problème, car le développeur et non l'utilisateur choisit la langue au moment de la compilation, et les mainteneurs de PhysicsFS devaient (mal) maintenir un travail de localisation énorme. L'application ne pouvait pas analyser les chaînes, même si elle disposait d'une langue spécifique, car certaines étaient générées dynamiquement. int PHYSFS_setRoot (const char * archive, const char * subdir)

Fait d'un sous-répertoire d'une archive son répertoire racine. Ceci vous permet de restreindre les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt, monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer la racine d'une archive à tout moment, modifiant l'arbre de fichiers interpolé (selon où les chemins changent, une archive différente peut fournir divers fichiers). Si vous définissez la racine sur NULL ou "/", l'archive sera traitée comme si aucune racine spéciale n'était définie (comme si l'archive était simplement montée normalement).

Changer la racine n'affecte que les opérations futures sur les noms de chemin ; un fichier qui a été ouvert à partir d'un chemin qui a changé en raison d'un setRoot ne sera pas affecté.

Définir une nouvelle racine ne se limite pas aux archives dans le chemin de recherche ; vous pouvez en définir une sur le répertoire d'écriture, ce qui pourrait être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez donc pas changer le répertoire d'écriture pour le moment.

Il n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme racine d'une archive ; cependant, aucun fichier ne sera visible dans ce cas. Si les répertoires manquants finissent par être créés (un mkdir vers le système de fichiers physique, etc.), cela sera reflété dans l'arbre interpolé.

archive répertoire/archive sur laquelle changer la racine.
subdir nouveau sous-répertoire à faire la racine de cette archive.

Retourne

non-zero en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.
