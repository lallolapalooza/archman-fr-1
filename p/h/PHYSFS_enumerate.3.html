typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent les fichiers.

Attention

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; cela vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de toute chaîne.

Ces rappels sont utilisés, à partir de PhysicsFS 1.1, comme une alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions en liste n'est pas nécessairement le cas dans les versions par rappel. Consultez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous l'attendez et vous pourriez obtenir des chaînes dupliquées.

origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, transmis dans le rappel pour votre commodité.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Plie" un point de code Unicode vers un équivalent en minuscules. (Ceci est pour une utilisation limitée et avancée. Si vous ne voyez pas immédiatement une utilité, vous pouvez probablement ignorer ceci pour toujours.)

Ceci convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux n'ayant pas d'équivalent en minuscules seront retournés sans conversion.

Notez que vous pourriez obtenir plusieurs points de code en retour ! Le Eszett allemand, par exemple, sera plié en deux points de code 's' minuscules. La théorie est que si vous pliez deux chaînes, l'une avec un Eszett et l'autre avec "SS", elles correspondront.

Attention

Quiconque étudiant Unicode connaît le problème du "I turc". Cette API ne le gère pas. Supposons que cette seule lettre dans tout Unicode sera pliée de manière incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la majeure partie de la planète, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Tampon pour stocker les valeurs des points de code pliés. Ceci doit pointer vers un espace d'au moins 3 emplacements de PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialise la bibliothèque PhysicsFS. Ceci ferme tous les fichiers ouverts via PhysicsFS, efface les chemins de recherche/écriture, libère la mémoire et invalide tous vos handles de fichier.

Notez que cet appel peut ÉCHOUMER s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures sur un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur est tombé en panne, etc.). Il est généralement préférable de fermer tous les handles d'écriture vous-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois désinitialisé avec succès, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états API par défaut sont restaurés à ce stade, à l'exception de tout allocateur personnalisé que vous auriez pu spécifier, qui survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les spécificités de l'erreur peuvent être obtenues à partir de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini, et probablement très dégradé.

int PHYSFS_delete (const char * filename)

Supprime un fichier ou un répertoire. (filename) est spécifié dans une notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, et non ce vers quoi il pointe, que vous ayez ou non "permis les liens symboliques".

Donc, si vous avez défini le répertoire d'écriture sur "C:\mygame\writedir" et appelez PHYSFS_delete("downloads/maps/level1.map"), le fichier "C:\mygame\writedir\downloads\maps\level1.map" sera supprimé du système de fichiers physique, s'il existe et si le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont un handle de fichier ouvert sur celui-ci (y compris votre programme) ne fermeront pas leurs handles.

Il y a de fortes chances que les bits qui composent le fichier existent toujours, ils sont simplement rendus disponibles pour être écrasés plus tard. Ne considérez pas cela comme une méthode de sécurité ou quoi que ce soit. :)

Paramètres

filename Nom du fichier à supprimer.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

Supprime un archiveur du système. Si pour une raison quelconque, vous n'avez besoin que de votre archiveur précédemment enregistré qu'une partie de la durée de vie de votre application, vous pouvez le supprimer du système une fois que vous avez terminé grâce à cette fonction.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers d'un répertoire d'un chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec des erreurs signalées. En interne, PHYSFS_enumerateFiles() appelle uniquement cette fonction, puis construit une liste avant de la renvoyer à l'application, de sorte que la fonctionnalité est identique, à l'exception de la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois pour chaque élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // Donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis d'être dans aucun ordre spécifique. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit le tri alphabétique. Cette forme signale ce qui se trouve dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout tri que vous trouvez dans ces fonctions de rappel est purement dû au hasard. Ne vous y fiez pas. Comme il parcourt la liste entière des archives, vous pourriez recevoir des noms de fichiers en double.

Cette API et les fonctions de rappel elles-mêmes peuvent signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même si elles ne recherchaient qu'un objet spécifique et souhaitaient s'arrêter là, ou si elles rencontraient une erreur grave et ne pouvaient en alerter personne. De plus, si PhysicsFS lui-même rencontrait un problème (erreur de disque ou autre), il ne pourrait pas le signaler à l'application, il arrêterait simplement l'énumération et l'appelant ne saurait pas s'il manquait des données.

Désormais, l'appelant peut être assuré d'avoir obtenu un ensemble complet de données, et sa fonction de rappel contrôle s'il souhaite arrêter l'énumération plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour plus de détails sur la façon dont votre fonction de rappel doit se comporter.

const char * PHYSFS_getLastError (void )

Obtient des informations d'erreur lisibles par l'homme.

Avertissement

Utilisez PHYSFS_getLastErrorCode() et PHYSFS_getErrorByCode() à la place.

Remarque

Depuis PhysicsFS 2.1, cette fonction a été obscurcie. Avant la version 2.1, c'était le seul moyen d'obtenir des détails d'erreur en dehors de l'évaluation booléenne d'une fonction. C'était une chaîne pour afficher le message d'erreur lisible par l'homme dans diverses langues, mais ce n'était pas utile pour l'analyse d'applications. En dehors de l'exception, le développeur ne choisissait pas la langue, et les mainteneurs de PhysicsFS devaient (maladroitement) maintenir une grande quantité de travail de localisation. L'application ne pouvait pas analyser les messages, même si elle disposait d'une langue spécifique, car certains étaient générés dynamiquement. Dans la version 2.1 et ultérieures, elle renvoie toujours une chaîne statique en anglais ; vous pouvez l'utiliser comme une chaîne clé pour votre propre localisation, bien que vous ne puissiez pas changer les messages existants. De plus, si votre application souhaite obtenir des erreurs spécifiques, nous offrons une meilleure option : utilisez PHYSFS_getLastErrorCode().

Le pointeur renvoyé pointe vers un tampon interne. Chaque thread a un état d'erreur unique associé, mais chaque fois qu'un nouveau message d'erreur est défini, il écrase l'état précédent associé à ce thread. Il est sûr d'appeler cette fonction à tout moment, même avant PHYSFS_init().

Depuis PhysicsFS 2.1, cette fonction ne présente que du texte en anglais, mais les chaînes sont statiques, vous pouvez donc les utiliser comme clés dans votre propre dictionnaire de localisation. Ces chaînes sont destinées à être passées directement à l'utilisateur.

Généralement, les programmes se soucient uniquement de savoir si une fonction a échoué ; cependant, si votre code nécessite plus de détails, vous devriez utiliser PHYSFS_getLastErrorCode() à la place de cette fonction.

Sous Linux, cela pourrait ressembler à : "/home/bob/.local/share/My Program Name"

Sous Mac OS X, cela pourrait ressembler à : "/Users/bob/Library/Application Support/My Program Name"

(etc.)

  • Utilisez toujours une chaîne d'application unique pour chaque application, et assurez-vous qu'elle ne change jamais pour une application une fois que vous avez décidé de son nom.

int PHYSFS_mount(const char *newDir, const char *mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Returns

nonzero if added to path, zero on failure (bogus archive, dir missing, etc). Use PHYSFS_getLastErrorCode() to obtain the specific error.

void PHYSFS_permitSymbolicLinks (int allow)

Permet ou refuse le suivi des liens symboliques. Certains systèmes de fichiers physiques et architectures contiennent des fichiers qui ne sont que des références à d'autres fichiers. En ouvrant un lien symbolique physique, le fichier auquel il fait référence sera automatiquement ouvert.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous conduire en dehors des chemins de lecture et d'écriture, compromettant la sécurité.

Si vous souhaitez assumer le risque, appelez cette fonction avec une valeur non nulle. Notez que ceci est davantage destiné au sandboxing d'un langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur peut avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas les désactiver à moins que vous ne ressentiez un risque spécifique.

Les liens symboliques ne seront vérifiés que lorsque des noms de fichiers en notation indépendante de la plateforme sont traités. Autrement dit, lorsque vous configurez vos chemins de recherche et d'écriture, etc., les liens symboliques ne seront jamais vérifiés.

Notez que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera pas suivi dans tous les cas. S'il n'est pas autorisé par cette fonction, PHYSFS_stat() ignorera le lien et traitera la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

int PHYSFS_setBuffer (PHYSFS_File * handle, unsigned int bufsize)

Set the buffering mode for a file handle.

This can be used to enable or disable buffering, or to change the size of an existing buffer.

If bufsize is non-zero, a buffer of that size (in bytes) will be allocated for the file handle. If the handle already has a buffer, it will be freed and replaced. If the buffer cannot be allocated, the function will fail. Note that enabling buffering implicitly causes a flush...check your return values!

Seeking, etc transparently accounts for buffering.

You can resize an existing buffer by calling this function more than once on the same file. Setting the buffer size to zero will free an existing buffer.

PhysicsFS file handles are unbuffered by default.

bufsize size, in bytes, of buffer to allocate.

Faites d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de restreindre les fichiers accessibles dans une archive spécifique. void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convertit une chaîne UTF-8 en une chaîne Latin1. Les chaînes Latin1 sont de 8 bits par caractère : un encodage populaire "high ASCII".

Pour s'assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon de double la taille du tampon source. UTF-8 étend les points de code Latin1 supérieurs à 127 de 1 à 2 octets, la chaîne peut donc croître dans certains cas.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Veuillez noter que nous ne fournissons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer la plupart des points de code Unicode. C'est un encodage hérité ; vous devriez toujours vous en éloigner.

Paramètres

src Chaîne source terminée par un caractère nul au format Latin1.
dst Tampon pour stocker la chaîne UTF-8 convertie.
len Taille, en octets, du tampon de destination.

void PHYSFS_utf8ToUcs4 (const char * src, PHYSFS_uint32 dst[], PHYSFS_uint64 len)

Convert a UTF-8 string to a UCS-4 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UCS-4 strings are 32-bits per character. Most modern OSes use UTF-16. You'll only want to use UCS-4 if you're doing things like dealing with data from older systems, or if you specifically need it for some reason.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UCS-4 always uses four, so an entirely low-ASCII string will double in size!

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UCS-4 sequence at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UCS-4 string.
len Size, in bytes, of destination buffer.

PHYSFS_writeUBE32() and PHYSFS_writeULE32() write unsigned 32-bit values.
