PHYSFS_enumerate

C'est le même que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat depuis le rappel : si vous cherchez quelque chose de spécifique, une fois trouvé, vous pouvez dire à PhysicsFS d'arrêter l'énumération. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois. :)

Paramètres

data Pointeur de données personnalisé, passé par l'API qui a finalement appelé le rappel.
origdir Une chaîne avec le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire pour lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname Le nom du fichier qui est énuméré. Il se peut qu'il ne soit pas dans l'ordre alphabétique par rapport à d'autres rappels qui ont été appelés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonctions de rappel qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; cela vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, une entrée par rappel. Toutes les chaînes sont au format UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire des chaînes.

Ces rappels sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui retournent des listes qui doivent être libérées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes au début.

Vous devez être conscient que les ordres promis dans les versions de liste ne sont pas nécessairement ainsi dans les versions de rappel. Vérifiez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes en double.

origdir Une chaîne avec le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire pour lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname Le nom du fichier qui est énuméré. Il se peut qu'il ne soit pas dans l'ordre alphabétique par rapport à d'autres rappels qui ont été appelés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers d'un répertoire d'un chemin de recherche, en utilisant un callback défini par l'utilisateur, avec des erreurs signalées. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de la retourner à l'application, donc la fonctionnalité est identique, sauf la manière dont l'information est présentée à l'application.

Bien que PHYSFS_enumerateFiles() ne retourne pas un tableau, cette fonction appelle une fonction spécifiée par l'utilisateur une fois pour chaque élément du chemin de recherche :

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSfs_ENUM_OK;  // Donne-moi plus de données, s'il te plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés au callback ne sont garantis pour être dans aucun ordre spécifique. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit l'ordre alphabétique. Cette forme signale ce qu'elle trouve dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel elle découvrira les données. Tout ordre que vous trouvez dans ces callbacks est pure chance. Ne vous y fiez pas. Comme cela parcourt toute la liste de fichiers, vous pouvez recevoir des noms de fichiers en double.

Cette API et les callbacks eux-mêmes peuvent signaler des erreurs. Avant cette API, les callbacks devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'un objet spécifique et voulaient s'arrêter là, ou s'ils avaient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou quelque chose de similaire), il ne pouvait pas le signaler à l'application, il suffisait de sauter des éléments ou d'arrêter l'énumération, et l'appelant ne saurait pas qu'il avait manqué des données en cours de route.

Maintenant, l'appelant peut s'assurer qu'il a obtenu un ensemble de données complet, et s'il veut arrêter l'énumération plus tôt, son callback le contrôle. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur la façon dont votre callback doit se comporter.

Paramètres

dir Répertoire à énumérer, en notation indépendante du système d'exploitation.
c Fonction de rappel pour notifier les éléments du chemin.
d Données définies par l'utilisateur transmises au callback. Peut être NULL.

Retourne

Non-zéro en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le callback retourne PHYSFS_ENUM_STOP, cela est considéré comme un succès. Les callbacks retournant PHYSFS_ENUM_ERROR feront que cette fonction retourne zéro et définiront le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtient une liste de fichiers d'un répertoire d'un chemin de recherche.

Avertissement

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction retournait autant d'éléments que possible en cas de condition d'erreur (erreur mémoire, erreur disque, etc.). Par conséquent, les applications ne pouvaient pas faire la différence entre un succès complet et un échec partiel. De plus, elle pouvait déjà retourner NULL pour signaler des échecs catastrophiques, donc dans PhysicsFS 2.1, cette politique a changé : elle retournera une liste complète de résultats ou retournera NULL en cas d'échec, nous pouvons donc garantir que l'énumération a été terminée et que les résultats ne comportent pas de trous.

Les répertoires correspondants sont interpolés. C'est-à-dire que si "C:\mydir" est dans le chemin de recherche et contient un répertoire "savegames" contenant "x.sav", "y.sav" et "z.sav", et qu'il y a aussi un "C:\userdir" dans le chemin de recherche qui contient un répertoire "savegames" avec "w.sav", alors le code suivant :

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi
Vous pouvez trier la liste comme vous le souhaitez. Cependant, les données retournées ne contiennent jamais de doublons et sont toujours triées par ordre alphabétique (plus précisément : triées d'une manière sensible à Unicode). N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur retournée par cette fonction lorsque vous avez terminé avec elle.

Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive, et non par rapport au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont entrelacés dans une seule hiérarchie de répertoires. void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné à la mise en bac à sable du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers dans la notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés via cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

Convertir une chaîne UTF-8 en une chaîne UCS-2.

Avertissement

Il est presque certain que vous devriez utiliser PHYSFS_utf8ToUtf16(), disponible depuis PhysicsFS 2.1, à moins que vous ne sachiez ce que vous faites.

Cette fonction ne signalera pas d'erreur si des séquences invalides sont présentes dans la chaîne source UTF-8. Elle les remplacera par '?' et poursuivra la conversion.

Les chaînes UCS-2 sont codées sur 16 bits par caractère : TCHAR sous Windows lorsque compilé avec le support Unicode. Veuillez noter que les versions modernes de Windows utilisent UTF-16, qui est un format étendu d'UCS-2, mais ce n'est pas UCS-2 en soi. Pour vous assurer que le buffer de destination est suffisamment grand pour la conversion, veuillez allouer un buffer deux fois plus grand que le buffer source. L'UTF-8 utilise de 1 à 4 octets par caractère, mais UCS-2 utilise toujours 2 octets, donc une chaîne ASCII basique doublera de taille !

void PHYSFS_utf8ToUcs4(const char * src, PHYSFS_uint32 **dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UCS-4 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UCS-4 strings are 32-bits per character. UTF-8 strings can use one to four bytes per character.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is four times the size of the source buffer. A null character in UTF-8 takes one byte, but will take four bytes in UCS-4. Any other character in UTF-8 will take between two and twelve bytes, but will take four bytes in UCS-4.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UCS-4 sequence at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UCS-4 string.
len Size, in bytes, of destination buffer.

void PHYSFS_utf8ToUtf16(const char * src, PHYSFS_uint16 *dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. If you aren't sure, you should be using UTF-16 at this point on Windows.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
len Size, in bytes, of destination buffer.
