Cette structure détermine la version de la bibliothèque avec laquelle vous avez compilé. Ceci est déterminé par l'en-tête que le compilateur utilise. typedef void(* PHYSfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent les fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; il vous donne plus de contrôle sur le processus.

Ils sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire d'une chaîne.

Ces rappels sont utilisés, depuis PhysicsFS 1.1, comme une alternative aux fonctions qui renvoyaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes auprès.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le cas dans les versions de rappel. Vérifiez la documentation sur les API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Plie" un point de code Unicode vers un équivalent en minuscules. (Ceci est pour une utilisation limitée et hardcore. Si vous ne voyez pas immédiatement un besoin pour cela, vous pouvez probablement l'ignorer pour toujours.)

Ceci convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux sans équivalent en minuscules seront retournés sans conversion.

Notez que vous pourriez obtenir plusieurs points de code en retour ! L'Eszett allemand, par exemple, sera plié en deux points de code latins minuscules 's'. La théorie est que si vous pliez deux chaînes, l'une avec un Eszett et l'autre avec "SS", elles correspondront.

Attention

Quiconque est étudiant en Unicode connaît le problème de "i turc". Cette API ne le gère pas. Supposez que cette seule lettre dans tout Unicode sera pliée de manière quelque peu incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la majeure partie de la planète, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Tampon pour stocker les valeurs de points de code pliés. Ceci devrait pointer vers de l'espace pour au moins 3 emplacements PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialise la bibliothèque PhysicsFS. Ceci ferme tous les fichiers ouverts via PhysicsFS, vide les chemins de recherche/écriture, libère la mémoire et invalide tous vos handles de fichiers.

Notez que cet appel peut ÉCHOUER s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures sur un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur a échoué, etc.). Il est généralement préférable de fermer tous les handles d'écriture vous-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois désinitialisé avec succès, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états par défaut de l'API sont restaurés à ce moment-là, à l'exception de tout allocateur personnalisé que vous pourriez avoir spécifié, lequel survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les détails de l'erreur peuvent être obtenus à partir de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini, et probablement gravement corrompu.

int PHYSFS_delete (const char * filename)

Supprime un fichier ou un répertoire. (filename) est spécifié en notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel ne puisse le supprimer.

La suppression d'un lien symbolique retire le lien, pas ce vers quoi il pointe, que vous ayez ou non "permis les liens symboliques".

Donc, si vous avez défini le répertoire d'écriture sur "C:\monjeu\dossier_ecriture" et appelez PHYSFS_delete("telechargements/cartes/niveau1.map"), alors le fichier "C:\monjeu\dossier_ecriture\telechargements\cartes\niveau1.map" est supprimé du système de fichiers physique, s'il existe et que le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont un handle de fichier ouvert dessus (y compris votre programme) ne fermeront pas leurs handles.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers d'un répertoire du chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique, sauf la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Elle appelle plutôt une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis dans aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme rapporte tout ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre de découverte des données. *Tout tri que vous trouverez dans ces callbacks est purement le fruit du hasard. Ne vous y fiez pas.* Comme cette fonction parcourt toute la liste des archives, vous pourriez recevoir des noms de fichiers dupliqués.

Cette API et les callbacks eux-mêmes sont capables de signaler des erreurs. Avant cette API, les callbacks devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur sérieuse et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement sauter des éléments ou arrêter l'énumération, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Désormais, l'appelant peut être sûr qu'il a obtenu un ensemble complet de données, et son callback a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement attendu de votre callback.

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées au callback. Peut être NULL.

Retourne

non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le callback retourne PHYSFS_ENUM_STOP pour s'arrêter plus tôt, cela sera considéré comme un succès. Les callbacks retournant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

Obtient une liste de fichiers d'un répertoire du chemin de recherche.

Attention

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction retournait autant d'éléments que possible face à une condition d'échec (manque de mémoire, erreur d'E/S disque, etc.). Comme cela empêchait les applications de distinguer un succès complet d'un échec partiel, et comme la fonction pouvait toujours retourner NULL pour signaler des échecs catastrophiques de toute façon, dans PhysicsFS 2.1, la politique de cette fonction a changé : elle retournera soit une liste de résultats complets, soit NULL en cas d'échec de quelque nature que ce soit, afin que nous puissions garantir que l'énumération s'est déroulée jusqu'au bout et qu'il n'y a pas de lacunes dans ses résultats.

Les répertoires correspondants sont interpolés. C'est-à-dire que si "C:\mydir" se trouve dans le chemin de recherche et contient un répertoire "savegames" qui contient "x.sav", "y.sav", et "z.sav", et qu'il y a aussi un répertoire "C:\userdir" dans le chemin de recherche qui a un sous-répertoire "savegames" avec "w.sav", alors le code suivant :

char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Nous avons [%s].\n", *i);
PHYSFS_freeList(rc);

* Nous avons [y.sav].
* Nous avons [z.sav].
* Nous avons [w.sav]..fi

N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur de retour de cette fonction lorsque vous avez terminé.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons est effectuée par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers chevauchant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser les archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence de fichiers et éviter les chevauchements ; cela est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept de « montage » Unix pourraient attendre. De plus, plus d'une archive peut être montée sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

Spécifier un lien symbolique vers une archive ou un répertoire est autorisé ici, quel que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que des liens symboliques à l'intérieur du répertoire ou de l'archive monté.

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné à la mise en bac à sable du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans tous les cas pas suivi. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour interdire le lien.

Faire d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de réduire les fichiers accessibles dans une archive spécifique. Vous voudrez peut-être spécifier zéro et gérer vous-même la configuration du disque.
archivesFirst Non nul pour préfixer les archives au chemin de recherche. Zéro pour les ajouter. Ignoré si !(archiveExt).
