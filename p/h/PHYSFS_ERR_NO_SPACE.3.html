PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il retourne un résultat depuis le callback : si vous cherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter l'énumération. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons que vous avez correctement obtenu. :)

Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonctions de callback qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() pour avoir plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, une entrée par callback. Toutes les chaînes de caractères sont encodées en UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire des chaînes de caractères.

Ces callbacks sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui retournent des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes de caractères d'avance.

Vous devez être conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le même dans les versions de callback. Vérifiez la documentation des API spécifiques, mais les chaînes de caractères peuvent ne pas être triées comme vous l'attendez et vous pourriez obtenir des chaînes de caractères dupliquées.

Paramètres

data pointeur vers des données définies par l'utilisateur, passé via l'API qui a finalement appelé le callback.
origdir chaîne de caractères contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire pour lequel vous avez demandé l'énumération, transmis dans le callback pour votre commodité.
fname nom de fichier en cours d'énumération. Il peut ne pas être classé par ordre alphabétique par rapport aux autres callbacks qui ont été appelés, et n'inclura pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers d'un répertoire du chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec les erreurs signalées. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de la retourner à l'application, donc la fonctionnalité est identique, sauf la manière dont l'information est présentée à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois pour chaque élément du répertoire de recherche :

static physFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis dans aucun ordre spécifique. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit l'ordre alphabétique. Cette forme signale ce qui est trouvé dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons pas garantir l'ordre dans lequel les données sont découvertes. Tout tri que vous trouvez dans ces fonctions de rappel est purement le fruit du hasard. Ne vous y fiez pas. Comme cette méthode parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les fonctions de rappel elles-mêmes sont capables de signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même si elles ne recherchaient qu'un élément spécifique et voulaient s'arrêter ensuite, ou si elles rencontraient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même rencontrait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il passait simplement aux éléments suivants ou terminait l'énumération, et l'appelant ne saurait pas qu'il avait perdu des données en cours de route.

Désormais, l'appelant peut être assuré d'avoir obtenu un ensemble complet de données, et s'il souhaite arrêter l'énumération plus tôt, sa fonction de rappel a le contrôle. Consultez la documentation de PHYSFS_EnumerateCallback pour savoir comment votre fonction de rappel doit se comporter.

dir Répertoire, en notation indépendante du système, à énumérer.
c Fonction de rappel pour signaler les éléments du chemin.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

Retourne

Non nul en cas de succès, nul en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel retourne PHYSFS_ENUM_STOP pour s'arrêter tôt, cela est considéré comme un succès. Les fonctions de rappel retournant PHYSFS_ENUM_ERROR feront que cette fonction retournera nul et définira le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

* We've got [z.sav].

Sous Mac OS X, cela pourrait ressembler à : "/Users/bob/Library/Application Support/Mon Nom de Programme"

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un duplicata, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la détection de doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive dont les fichiers chevauchent un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Ceci permet d'utiliser les archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et empêcher les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient écraser les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce à quoi ceux qui connaissent le concept Unix de "montage" peuvent s'attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

Spécifier un lien symbolique vers une archive ou un répertoire est autorisé ici, quel que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que des liens symboliques à l'intérieur du répertoire ou de l'archive montée.

newDir répertoire ou archive à ajouter au chemin, en notation dépendante de la plateforme.
mountPoint Emplacement dans l'arbre interpolé où cette archive sera "montée", en notation indépendante de la plateforme. NULL ou "" est équivalent à "/".
appendToPath non-zéro pour ajouter au chemin de recherche, zéro pour ajouter au début.

non-zéro si ajouté au chemin, zéro en cas d'échec (archive invalide, répertoire manquant, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous emmener en dehors des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné à l'encapsulation du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. De manière générale, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, donc à moins que vous ne ressentiez un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques sont explicitement vérifiés uniquement lorsqu'il s'agit de noms de fichiers en notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour les refuser.

-1 si str1 est "inférieur" à str2, 1 si "supérieur", 0 si égal.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convertit une chaîne UTF-8 en une chaîne Latin1. Les chaînes Latin1 ont 8 bits par caractère : une codification populaire du "high ASCII".

Pour vous assurer que le buffer de destination est suffisamment grand pour la conversion, veuillez allouer un buffer dont la taille est le double de celle du buffer source. L'UTF-8 étend les codes Latin1 supérieurs à 127 en 1 ou 2 octets, de sorte que la chaîne peut s'agrandir dans certains cas.

Les chaînes qui ne rentrent pas dans le buffer de destination seront tronquées, mais seront toujours terminées par un caractère nul et ne contiendront jamais une séquence UTF-8 incomplète à la fin. Si la taille du buffer est de 0, cette fonction ne fait rien.

Note : Nous ne fournissons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer de nombreux codes Unicode. C'est une ancienne codification ; vous devriez toujours vous convertir à partir de celle-ci.

Paramètres

src Chaîne source au format Latin1, terminée par un caractère nul.
dst Buffer de destination pour la chaîne UTF-8 convertie.
len Taille en octets du buffer de destination.

void PHYSFS_utf8FromUtf16 (const PHYSFS_uint16 * src, char * dst, PHYSFS_uint64 len)

Convertit une chaîne UTF-16 en une chaîne UTF-8.

Avertissement

Cette fonction ne signalera pas d'erreur s'il y a des séquences UTF-16 invalides dans la chaîne source. Elle les remplacera par un caractère '?' et continuera.

Les chaînes UTF-16 (également appelées UCS-2) ont 16 bits par caractère (à l'exception de certains caractères qui font 32 bits) : TCHAR sous Windows, lorsqu'elles sont compilées avec le support Unicode. Les versions modernes de Windows utilisent UTF-16. Les anciennes versions de Windows avant 2000 utilisaient TCHAR, mais ne prenaient en charge que UCS-2. UTF-16 *est* UCS-2, à l'exception des caractères à 4 octets, qui ne peuvent pas du tout être représentés en UCS-2. Si vous n'êtes pas sûr, vous devriez utiliser UTF-16 sous Windows maintenant.

Pour vous assurer que le buffer de destination est suffisamment grand pour la conversion, veuillez allouer un buffer dont la taille est le double de celle de la source. L'UTF-8 n'utilise jamais plus de 32 bits par caractère, donc bien qu'il puisse réduire une chaîne UTF-16, il peut aussi l'agrandir.

Les chaînes qui ne rentrent pas dans le buffer de destination seront tronquées, mais seront toujours terminées par un caractère nul et ne contiendront jamais une séquence UTF-8 incomplète à la fin. Si la taille du buffer est de 0, cette fonction ne fait rien.

Comparaison insensible à la casse de deux chaînes UTF-8. C'est un remplacement pour strcasecmp/stricmp qui s'attend à ce que les deux chaînes soient au format UTF-8. Elle effectuera un "pliage de casse" pour décider si les codes Unicode dans les chaînes correspondent.

Si les deux chaînes ne contiennent que des caractères ASCII bas, cela fonctionnera correctement, car c'est également du UTF-8 valide. S'il y a des caractères ASCII hauts, cela ne fera pas ce que vous attendez !

Elle indiquera quelle chaîne est "supérieure à" l'autre, mais vous devez garder à l'esprit que cela ne signifie pas nécessairement quelque chose : 'a' peut être "inférieur à" 'b', mais un kuten japonais n'a pas de relation alphabétique significative avec un lambda grec, mais être capable d'attribuer une valeur fiable rend les algorithmes de tri possibles, même s'ils ne sont pas totalement rationnels. La plupart des cas devraient traiter la valeur renvoyée comme "égale" ou "non égale".

Comme stricmp, elle s'attend à ce que les deux chaînes soient terminées par un caractère nul.

Paramètres

str1 Chaîne à comparer.
str2 Chaîne à comparer.

Retourne

-1 si str1 est "inférieur à" str2, 1 si "supérieur à", 0 si égaux.
