typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent des fichiers.

Attention

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() pour avoir plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste de répertoires d'entrée à un appelant d'origine, une entrée par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire des chaînes.

Ces callbacks sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui retournent des listes qui doivent être libérées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes.

Notez que l'ordre des données promis dans les versions de liste n'est pas nécessairement le même dans les versions de callback. Vérifiez la documentation des API spécifiques, mais les chaînes ne seront pas nécessairement triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data pointeur vers des données définies par l'utilisateur, passé par l'API qui a finalement appelé le callback.
origdir une chaîne avec le chemin complet, en notation indépendante du système d'exploitation, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire dans lequel vous avez demandé l'énumération, passé par le callback pour votre commodité.
fname le nom du fichier qui est énuméré. Il pourrait ne pas être dans l'ordre alphabétique comparé à d'autres callbacks qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retour

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir una lista de fichiers à partir du répertoire d'un chemin de recherche, en utilisant un rappel défini par l'utilisateur, avec des erreurs signalées. En interne, PHYSFS_enumerateFiles() n'appelle que cette fonction, puis construit la liste avant de la retourner à l'application, de sorte que la fonctionnalité est identique, sauf la manière dont les informations sont présentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'utilisateur une fois pour chaque élément du chemin de recherche :

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSfs_ENUM_OK;  // donner plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments transmis au rappel ne sont pas garantis d'être dans un ordre spécifique. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit l'ordre alphabétique. Cette forme retourne ce qui est trouvé dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout ordre que vous pourriez trouver dans ces rappels est purement fortuit. Ne comptez pas dessus. Comme cette fonction parcourt toute la liste des fichiers, vous pourriez recevoir des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes peuvent signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'un élément spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il se contenterait de sauter des éléments ou d'arrêter l'énumération, et l'appelant ne saurait pas qu'il avait perdu des données en cours de route.

Désormais, l'appelant peut être assuré qu'il a obtenu un ensemble complet de données, et son rappel contrôlera s'il souhaite arrêter l'énumération plus tôt. Consultez la documentation de PHYSFS_EnumerateCallback pour connaître les détails sur la manière dont votre rappel doit se comporter.

dir Répertoire à énumérer en notation indépendante du système d'exploitation.
c Fonction de rappel pour notifier les éléments du chemin.
d Données définies par l'application transmises au rappel. Peut être NULL.

Retourne

Non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel retourne PHYSFS_ENUM_STOP, cela est considéré comme un succès. Les rappels retournant PHYSFS_ENUM_ERROR feront que cette fonction retournera zéro et définira le code d'erreur comme PHYSFS_ERR_APP_CALLBACK.

char **rc = PHYSFS_enumerateFiles("savegames");

for (i = rc; *i != NULL; i++)

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Obtenir le chemin spécifique à l'utilisateur et à l'application où les fichiers peuvent être écrits. Fonction d'assistance.

Sous Mac OS X, cela pourrait ressembler à : "/Users/bob/Library/Application Support/My Program Name"

(etc.)

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés en un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive dont les fichiers chevauchent un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser les archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que les personnes familières avec le concept de "montage" Unix pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

Spécifier un lien symbolique vers une archive ou un répertoire est autorisé ici, quelle que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

Paramètres

newDir répertoire ou archive à ajouter au chemin, en notation spécifique à la plateforme.
mountPoint Emplacement dans l'arbre interpolé où cette archive sera "montée", en notation indépendante de la plateforme. NULL ou "" équivaut à "/".
appendToPath une valeur non nulle pour ajouter au chemin de recherche, zéro pour ajouter au début.

une valeur non nulle si elle a été ajoutée au chemin, zéro en cas d'échec (archive invalide, répertoire manquant, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

Par conséquent, vous pourriez trouver l'utilisation normale des dossiers très pénible si vous montez de cette manière. Planifiez en conséquence : si, par exemple, vous avez un fichier ZIP auto-extractible et que vous souhaitez monter quelque chose à l'intérieur, compressez les contenus internes et assurez-vous que le fichier externe ne comprime pas trop l'interne.

Cette fonction se comporte exactement comme PHYSFS_mount(), mais elle prend un handle PHYSFS_File au lieu d'un nom de fichier. Ce handle contient toutes les données du dossier et est utilisé à la place d'un fichier réel sur le système de fichiers physique. Le PHYSFS_File peut être soutenu par un fichier réel sur le système de fichiers physique, mais ce n'est pas nécessairement le cas. L'utilisation la plus courante est de monter des dossiers stockés dans d'autres dossiers.

(newDir) doit être une chaîne unique pour identifier ce dossier. Elle est utilisée pour optimiser la sélection des archiveurs (si elle est nommée XXXXX.zip, elle pourrait tenter l'archiveur ZIP, par exemple, ou choisir directement un archiveur qui ne s'appuie que sur l'extension du nom). Il n'est pas nécessaire qu'elle fasse référence à un fichier réel. Si l'extension du nom n'est pas utile, le système essaiera tous les archiveurs jusqu'à ce que l'un d'eux fonctionne ou qu'aucun d'eux ne fonctionne. Cette chaîne doit être unique, car le système n'autorisera pas deux dossiers ayant le même nom.

(file) doit être conservé jusqu'à ce que le dossier soit démonté. Lorsque le dossier sera démonté, le système appellera PHYSFS_close(file). Si vous avez besoin que ce handle survive, vous devrez l'envelopper dans un PHYSFS_Io et utiliser PHYSFS_mountIo().

Si cette fonction échoue, PHYSFS_close(file) n'est pas appelée.

newDir Le nom de fichier qui peut représenter ce flux.

appendToPath Non nul pour ajouter au chemin de recherche, nul pour préfixer.

Retour

Non nul si ajouté au chemin, nul en cas d'erreur (mauvais dossier, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné à la mise en bac à sable du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, donc sauf si vous estimez qu'il y a un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques sont uniquement vérifiés explicitement lors du traitement des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

L'autorisation des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser les liens.

Fait d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de réduire les fichiers accessibles dans une archive spécifique. -1 si str1 est "inférieur à" str2, 1 si "supérieur à", 0 si égal.
