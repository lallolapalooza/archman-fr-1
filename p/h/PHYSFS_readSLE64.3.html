int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Plie" un point de code Unicode vers un équivalent en minuscules. (Ceci est pour une utilisation limitée et intensive. Si vous ne voyez pas immédiatement un besoin pour cela, vous pouvez probablement ignorer cela pour toujours.)

Ceci convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux sans équivalent en minuscules seront retournés inchangés.

Notez que vous pourriez obtenir plusieurs points de code en retour ! Le caractère allemand Eszett, par exemple, sera plié en deux points de code 's' minuscules. La théorie est que si vous pliez deux chaînes, l'une avec un Eszett et l'autre avec "SS", elles correspondront.

Attention

Quiconque a étudié Unicode connaît le problème du "I turc". Cette API ne le gère pas. Supposons que cette lettre unique dans tout Unicode sera pliée de manière incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la plupart de la planète, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Tampon pour stocker les valeurs des points de code pliés. Il doit pointer vers de l'espace pour au moins 3 emplacements PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialise la bibliothèque PhysicsFS. Cela ferme tous les fichiers ouverts via PhysicsFS, efface les chemins de recherche/écriture, libère la mémoire et invalide tous vos handles de fichier.

Notez que cet appel peut ÉCHOIR s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures sur un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur a échoué, etc.). Il est généralement préférable de fermer tous les handles d'écriture vous-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois désinitialisé avec succès, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états par défaut de l'API sont restaurés à ce stade, à l'exception de tout allocateur personnalisé que vous auriez pu spécifier, qui survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les détails de l'erreur peuvent être obtenus à partir de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini et probablement gravement endommagé.

int PHYSFS_delete (const char * filename)

Supprime un fichier ou un répertoire. (filename) est spécifié dans une notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel ne puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, pas ce qu'il pointe, indépendamment du fait que vous ayez "autorisé les liens symboliques" ou non.

Donc, si vous avez le répertoire d'écriture défini sur "C:\monjeu\repertoireecriture" et appelez PHYSFS_delete("telechargements\cartes\niveau1.map") alors le fichier "C:\monjeu\repertoireecriture\telechargements\cartes\niveau1.map" est supprimé du système de fichiers physique, s'il existe et si le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont un handle de fichier ouvert dessus (y compris votre programme) ne fermeront pas leurs handles.

Il y a de fortes chances que les bits qui composent le fichier existent toujours, ils sont juste rendus disponibles pour être écrasés plus tard. Ne considérez pas cela comme une méthode de sécurité ou autre. :)

Paramètres

filename Nom du fichier à supprimer.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_deregisterArchiver (const char * ext)

Supprime un archiveur du système. Si pour une raison quelconque, vous n'avez besoin que de votre archiveur précédemment enregistré qu'une partie de la durée de vie de votre application, vous pouvez le supprimer du système une fois que vous avez terminé à l'aide de cette fonction.

Cela échoue s'il y a encore des archives ouvertes qui utilisent cet archiveur.

Cette fonction peut également supprimer des archiveurs fournis en interne, tels que le support .zip ou autre. Cela pourrait être utile dans certaines situations, comme désactiver complètement leur support ou les remplacer par votre propre implémentation. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis crée une liste avant de la renvoyer à l'application, de sorte que la fonctionnalité est identique, sauf pour la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

{
    printf(" * Nous avons obtenu [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis dans aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale tout ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une seule archive, nous ne pouvons pas garantir l'ordre dans lequel les données seront découvertes. Tout tri que vous trouvez dans ces rappels est purement le hasard. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers en double.

Cette API et les fonctions de rappel elles-mêmes sont capables de signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr qu'il a obtenu un ensemble complet de données, et sa fonction de rappel a le contrôle s'il veut que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement attendu de votre fonction de rappel.

int PHYSFS_mount(const char *newDir, const char *mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers se chevauchant avec un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser les archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer les archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que les personnes familières avec le concept Unix de « montage » pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier pointé.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que c'est surtout pour l'encapsulation du langage de scripting d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser, vous devriez les permettre.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers dans la notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Note

Si vous voulez fournir votre propre archiveur (par exemple, un format de fichier personnalisé ou quelque chose de virtuel que vous voulez faire ressembler à un système de fichiers auquel vous pouvez accéder via les API standard de PhysicsFS), c'est par où vous commencez. Une fois que cette fonction retourne avec succès, PhysicsFS sera capable de prendre en charge les fichiers de ce type jusqu'à ce que vous désenregistriez l'archiveur.

int PHYSFS_setAllocator (const PHYSFS_Allocator * allocator)

Injectez vos propres routines d'allocation dans PhysicsFS. (Ceci est pour une utilisation limitée et intensive. Si vous ne voyez pas immédiatement un besoin pour cela, vous pouvez l'ignorer pour toujours.)

Par défaut, PhysicsFS utilisera ce qui est le plus raisonnable pour gérer la mémoire dynamique sur une plateforme (généralement malloc/realloc/free ANSI C, mais certains systèmes peuvent utiliser autre chose). L'allocateur reste le même entre les appels de désinitialisation/initialisation. Si vous voulez revenir à l'allocateur par défaut de la plateforme, passez NULL ici.

Si vous n'êtes pas sûr de ce qu'il faut faire avec cette fonction, vous pouvez l'ignorer complètement.

allocator La structure contenant les points d'entrée de votre allocateur.

Retour

int PHYSFS_setBuffer (PHYSFS_File * handle, PHYSFS_uint64 bufsize)

Configure la mise en mémoire tampon pour un descripteur de fichier PhysicsFS. Définit une mise en mémoire tampon d'E/S pour un descripteur de fichier. Un bloc de mémoire de (bufsize) octets sera alloué et associé à (handle).

Pour les fichiers ouverts en lecture, jusqu'à (bufsize) octets seront lus depuis (handle) et stockés dans le tampon interne. Les appels à PHYSFS_read() extrairont du tampon jusqu'à ce qu'il soit vide, puis rempliront le tampon pour une lecture ultérieure. Notez que les fichiers compressés, tels que les archives ZIP, sont décompressés pendant la mise en mémoire tampon, ce qui peut être utile pour décaler les opérations gourmandes en CPU. Le tampon n'est pas rempli tant que vous n'effectuez pas votre prochaine lecture.

Pour les fichiers ouverts en écriture, les données seront écrites en mémoire jusqu'à ce que le tampon soit plein ou qu'une opération de vidage soit effectuée. La fermeture d'un descripteur de fichier doit assurer que le tampon est vidé.

void PHYSFS_setErrorCode (PHYSFS_ErrorCode code)

Définit le code d'erreur du thread courant. Ceci vous permet de définir la valeur qui sera retournée par le prochain appel à PHYSFS_getLastErrorCode(). Cela remplacera tout code d'erreur existant, qu'il ait été défini par votre application ou en interne par PhysicsFS.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Définit un sous-répertoire d'une archive comme répertoire racine. Ceci vous permet de limiter les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier à y/z.txt monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel à PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez modifier le répertoire racine d'une archive à tout moment, ce qui modifiera l'arborescence de fichiers interpolée (selon l'endroit où les chemins sont déplacés, une archive différente pourrait fournir des fichiers différents). Si vous définissez le répertoire racine à NULL ou à "/", l'archive sera traitée comme si aucun répertoire racine n'avait été spécifié.

La modification du répertoire racine n'affecte que les opérations futures sur les chemins de fichiers ; une archive ouverte à partir d'un chemin qui a été modifié par un appel à setRoot ne sera pas affectée.

La définition d'un nouveau répertoire racine n'est pas limitée aux archives du répertoire de recherche ; vous pouvez également la définir sur le répertoire d'écriture, ce qui pourrait être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez pas modifier le répertoire d'écriture pour le moment.

Ce n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme racine d'une archive ; cependant, aucun fichier ne sera trouvé dans ce cas. Si les répertoires manquants finissent par être créés (un mkdir vers le système de fichiers physique, etc.), cela se reflétera dans l'arborescence interpolée.

Paramètres

archive Répertoire/archive dans lequel définir le répertoire racine.
subdir Nouveau sous-répertoire à définir comme racine de cette archive.

Retourne

non zéro en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_setSaneConfig (const char * organization, const char * appName, const char * archiveExt, int includeCdRoms, int archivesFirst)

Définit des chemins et des répertoires de recherche par défaut raisonnables. Fonction d'aide.

Le répertoire d'écriture sera défini sur le répertoire préfixe retourné par

PHYSFS_getPrefDir(organization, appName)

,

qui est créé s'il n'existe pas.

La partie ci-dessus est suffisante pour garantir que le répertoire de configuration de votre programme est séparé des autres désordres et qu'il est indépendant de la plateforme.

Le chemin de recherche sera :

  • Répertoire d'écriture (créé s'il n'existe pas)
  • Répertoire de base (PHYSFS_getBaseDir())
  • Tous les répertoires CD-ROM trouvés (optionnel)

Ces répertoires sont recherchés pour des fichiers portant une extension (archiveExt), qui, s'ils sont valides et pris en charge, sont également ajoutés à la liste de recherche. Si vous avez spécifié "PKG" pour (archiveExt), et qu'il existe un fichier nommé data.PKG dans le répertoire de base, il sera vérifié. Les archives peuvent être ajoutées au début ou à la fin de la liste de recherche par ordre alphabétique, indépendamment de l'endroit où elles ont été trouvées. Toutes les archives sont montées à la racine du système de fichiers virtuel ("/")

Tout ce qui précède peut être fait à partir du programme, mais ceci fait tout pour vous. Vous pouvez également ajouter manuellement d'autres éléments à la liste de recherche.

Paramètres

organization Nom de votre entreprise/groupe/etc. à utiliser comme nom de répertoire, donc gardez-le court et simple.
appName Nom spécifique de votre programme, pour le distinguer des autres programmes utilisant PhysicsFS.
archiveExt Extension utilisée par votre programme pour spécifier une archive. Par exemple, Quake 3 utilise "pk3", même s'il s'agit simplement de fichiers zip. Spécifiez NULL pour ne pas rechercher automatiquement les archives. Ne spécifiez pas le point '.' ; si vous voulez rechercher les fichiers ZIP, spécifiez "ZIP" et non ".ZIP"... la recherche d'archives est insensible à la casse.
includeCdRoms Non nul pour inclure les CD-ROM dans la liste de recherche, et (si (archiveExt) != NULL) rechercher des archives dans ceux-ci. Cela peut causer des délais importants lors de l'accès aux disques, et s'il n'y a pas de disques dans le lecteur (ou même pas montés sur les systèmes Unix), ils ne seront pas disponibles. Vous pouvez spécifier zéro et gérer la configuration du disque par vous-même.
archivesFirst Non nul pour préfixer les archives dans la liste de recherche. Zéro pour les suffixer. Ignoré si !(archiveExt).

Retourne

non zéro en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.
