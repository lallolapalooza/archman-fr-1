C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'elle peut renvoyer un résultat du rappel : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. typedef void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent des fichiers.

Attention

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; cela vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de ces chaînes.

Ces rappels sont utilisés, à partir de PhysicsFS 1.1, comme une alternative aux fonctions qui renverraient des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Sachez que l'ordre promis des données dans les versions de liste n'est pas nécessairement le cas dans les versions par rappel. Consultez la documentation sur les API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data Pointeur de données défini par l'utilisateur, transmis depuis l' API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport à d'autres rappels qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

enum PHYSFS_ErrorCode

Valeurs qui représentent des causes spécifiques d'échec. La plupart du temps, vous ne devriez vous préoccuper que de savoir si une opération donnée a échoué ou non, mais il peut y avoir des occasions où vous prévoyez de gérer un cas d'échec spécifique avec élégance, nous fournissons donc des codes d'erreur spécifiques.

La plupart de ces erreurs sont un peu vagues, et la plupart ne sont pas des choses que vous pouvez corriger... s'il y a une erreur de permission, par exemple, tout ce que vous pouvez vraiment faire est de transmettre cette information à l'utilisateur et de le laisser trouver comment la gérer. Dans la plupart de ces cas, votre programme ne devrait se soucier que du fait qu'il n'a pas réussi à atteindre ses objectifs, et pas spécifiquement pourquoi.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Plie" un point de code Unicode vers un équivalent en minuscules. (Ceci est pour un usage limité et hardcore. Si vous ne voyez pas immédiatement un besoin pour cela, vous pouvez probablement ignorer ceci pour toujours.)

Ceci convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux qui n'ont pas d'équivalent en minuscules seront retournés sans conversion.

Notez que vous pourriez obtenir plusieurs points de code en retour ! L'Eszett allemand, par exemple, se pliera en deux points de code 's' minuscules. La théorie est que si vous pliez deux chaînes, l'une avec un Eszett et l'autre avec "SS" vers le bas, elles correspondront.

Attention

Quiconque est étudiant en Unicode connaît le problème de la "I turque". Cette API ne le gère pas. Supposez que cette lettre unique dans tout Unicode se pliera de manière incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la plupart de la planète, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Buffer pour stocker les valeurs des points de code pliés. Ceci devrait pointer vers un espace pour au moins 3 emplacements PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_close (PHYSFS_File * handle)

Ferme un handle de fichier PhysicsFS. Cet appel peut échouer si le système d'exploitation mettait en mémoire tampon les écritures sur le média physique et, forcé maintenant d'écrire ces changements sur le média physique, ne peut pas stocker les données pour une raison quelconque. Paramètres

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

non nul en cas de succès, zéro en cas d'erreur. Les spécificités de l'erreur peuvent être obtenues auprès de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini et probablement très endommagé.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers d'un chemin de recherche, en utilisant un rappel défini par l'utilisateur, avec des erreurs signalées. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de la renvoyer à l'application, de sorte que la fonctionnalité est identique, sauf la manière dont les informations sont présentées à l'application.

Différent de PHYSFS_enumerateFiles(), cette fonction ne renvoie pas de tableau, mais appelle une fonction spécifiée par l'utilisateur une fois pour chaque élément du chemin de recherche :

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSfs_ENUM_OK;  // donne-moi plus de données, s'il te plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés au rappel ne sont garantis d'être dans aucun ordre. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un ordre alphabétique. Cette forme signale ce qui se trouve dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout ordre que vous trouvez dans ces rappels est de la pure chance. Vous ne devriez pas en dépendre. Comme cela parcourt toute la liste de fichiers, vous pourriez recevoir des noms de fichiers en double.

Cette API et les rappels eux-mêmes peuvent signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'un objet spécifique et voulaient s'arrêter ensuite, ou s'ils avaient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou similaire), il ne pourrait pas le signaler à l'application appelante, il devrait simplement sauter des éléments ou s'arrêter complètement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr qu'il a obtenu un ensemble complet de données, et s'il le souhaite, son rappel a le contrôle de savoir s'il faut arrêter l'énumération prématurément. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur la façon dont votre rappel doit se comporter.

Paramètres

dir Répertoire en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées au rappel. Peut être NULL.

Retourne

Non zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel renvoie PHYSFS_ENUM_STOP pour s'arrêter prématurément, cela est considéré comme un succès. Les rappels renvoyant PHYSFS_ENUM_ERROR feront que cette fonction renverra zéro et définira le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute un fichier ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'élément n'est pas ajouté à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter le même fichier à deux points de montage différents : la vérification des doublons se fait par rapport au fichier et non par rapport au point de montage.

Lors du montage d'un fichier, celui-ci est ajouté à un système de fichiers virtuel... tous les fichiers de tous les fichiers montés sont interpolés en une seule arborescence de répertoires. Deux fichiers montés au même endroit (ou un fichier dont les fichiers chevauchent un point de montage) peuvent avoir des fichiers qui se chevauchent : dans ce cas, le fichier le plus précoce dans le chemin de recherche est sélectionné, et les autres fichiers ne sont pas accessibles à l'application. Cela permet d'utiliser des fichiers pour remplacer des versions antérieures ; vous pouvez utiliser le mécanisme de montage pour placer des fichiers à un endroit spécifique dans l'arborescence des fichiers et empêcher les chevauchements ; ceci est utile pour les modes téléchargeables qui peuvent écraser les données de l'application ou eux-mêmes, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui diffère de ce que l'on attend du concept Unix de « montage » familier aux utilisateurs. De plus, plusieurs fichiers peuvent être montés sur le même point de montage, ou les points de montage et le contenu des fichiers peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours normalement.

Il est permis de spécifier un lien symbolique vers un fichier ou un répertoire, indépendamment de l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que les liens symboliques au sein du répertoire ou du fichier monté.

mountPoint emplacement dans l'arborescence interpolée où ce fichier sera « monté », dans une notation indépendante de la plateforme. NULL ou « » équivaut à « / ».

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins de sauvegarde et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné au sandbox d'un langage de script de programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne sentiez qu'il y a un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et de sauvegarde, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés via cette fonction, PHYSFS_stat() les ignore, et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Fait d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de restreindre les fichiers accessibles dans une archive spécifique. UTF-16 est UCS-2, sauf pour les caractères qui font 4 octets, qui ne peuvent pas être entièrement représentés en UCS-2. Si vous n'êtes pas sûr, vous devriez utiliser UTF-16 à ce stade sous Windows.

Pour garantir que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon dont la taille est le double de celle du tampon d'entrée. UTF-8 utilise de 1 à 4 octets par caractère, mais UTF-16 utilise toujours 2 à 4 octets, donc une chaîne purement ASCII bas de gamme doublera sa taille ! Les caractères UTF-16 qui nécessitent 4 octets nécessiteront également 4 octets en UTF-8, vous n'avez donc pas besoin d'allouer le double de l'espace qui ne serait nécessaire qu'en cas d'erreur : le double sera suffisant.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un nul et n'auront jamais de paires de substitution incomplètes à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Paramètres

src Chaîne d'entrée en UTF-8 terminée par un nul.
dst Tampon pour stocker la chaîne UTF-16 convertie.
len Taille en octets du tampon de destination.

NAME

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 – write native-endian integers to a file

LIBRARY

PhysicsFS Library (libphysfs, on -lphysfs)

SYNOPSIS

int
PHYSFS_writeUBE16(PHYSFS_File *file, PHYSFS_uint16 val);

int
PHYSFS_writeUBE32(PHYSFS_File *file, PHYSFS_uint32 val);

int
PHYSFS_writeUBE64(PHYSFS_File *file, PHYSFS_uint64 val);

int
PHYSFS_writeULE16(PHYSFS_File *file, PHYSFS_uint16 val);

int
PHYSFS_writeULE32(PHYSFS_File *file, PHYSFS_uint32 val);

int
PHYSFS_writeULE64(PHYSFS_File *file, PHYSFS_uint64 val);

DESCRIPTION

These functions provide convenient ways to write integer values to a PHYSFS_File (*file). They handle the conversion from the platform's native byte order to the specified endianness (big-endian or little-endian) before writing.

  • PHYSFS_writeUBE16: Writes an unsigned 16-bit big-endian value.
  • PHYSFS_writeUBE32: Writes an unsigned 32-bit big-endian value.
  • PHYSFS_writeUBE64: Writes an unsigned 64-bit big-endian value.
  • PHYSFS_writeULE16: Writes an unsigned 16-bit little-endian value.
  • PHYSFS_writeULE32: Writes an unsigned 32-bit little-endian value.
  • PHYSFS_writeULE64: Writes an unsigned 64-bit little-endian value.

PARAMETERS

file
A pointer to the PHYSFS_File handle to which the data will be written.
val
The unsigned integer value to be converted and written.

RETURNS

These functions return a non-zero value on success and zero on failure. If an error occurs, you can obtain more information by calling PHYSFS_getLastErrorCode.

Warning: On platforms without native 64-bit support, PHYSFS_uint64 may only be 32 bits wide.
