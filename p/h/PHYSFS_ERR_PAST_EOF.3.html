PHYSFS_enumerate

Ceci est le même que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat de rappel : si vous cherchez quelque chose de spécifique, une fois qu'il est trouvé, vous pouvez dire à PhysicsFS d'arrêter l'itération. PHYSFS_EnumerateCallbackResult

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonctions de rappel qui énumèrent des fichiers.

Note

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() pour avoir plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, une entrée par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire d'une chaîne.

Ces rappels sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui renvoient des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le rappel indique que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes au préalable.

Notez que les promesses de tri des données dans les versions de liste ne sont pas nécessairement tenues dans les versions de rappel. Vérifiez la documentation des API spécifiques, mais les chaînes ne seront pas nécessairement triées comme vous l'attendez et vous pourriez obtenir des chaînes dupliquées.

Obtenir une liste de fichiers à partir d'un répertoire d'un chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec des erreurs signalées. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de la retourner à l'application, donc la fonctionnalité est identique, sauf si les informations sont présentées à l'application dans un ordre différent.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas un tableau. Au lieu de cela, elle appelle une fonction spécifique définie par l'application une fois pour chaque élément dans le chemin de recherche :

static physFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donne-moi plus de données, s'il te plaît.
}
// ...

Les éléments passés au rappel ne sont garantis dans aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit l'ordre alphabétique. Cette forme signale ce qu'elle trouve dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données sont trouvées. Tout ordre que vous trouvez dans ces rappels est pure coïncidence. Vous ne devriez pas vous y fier. Comme cela parcourt toutes les archives, vous pourriez recevoir des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes peuvent signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'un élément spécifique et voulaient s'arrêter là, ou s'ils rencontraient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application, il devait simplement ignorer des éléments ou s'arrêter complètement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Désormais, l'appelant peut être assuré d'avoir obtenu un ensemble complet de données, et s'il souhaite arrêter l'énumération plus tôt, son rappel a le contrôle. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement de votre rappel.

    printf(" * We've got [%s].\n", *i);

* We've got [y.sav].

const char *PHYSFS_getPrefDir(const char *org, const char *app)

Obtenir le chemin spécifique à l'utilisateur et à l'application où les fichiers peuvent être écrits. Fonction d'assistance.

Obtenir le « répertoire des préférences ». Ceci est destiné à être l'endroit où les utilisateurs peuvent écrire des fichiers personnels (préférences et sauvegardes de jeux, etc.) spécifiques à votre application. Ce répertoire est unique par utilisateur, par application.

Cette fonction déterminera l'emplacement approprié dans le système de fichiers natif, créera le répertoire si nécessaire et retournera une chaîne en notation dépendante de la plateforme, adaptée à être passée à PHYSFS_setWriteDir().

Sous Linux, cela pourrait ressembler à : « /home/bob/.local/share/Mon Nom de Programme »

Sous Mac OS X, cela pourrait ressembler à : « /Users/bob/Library/Application Support/Mon Nom de Programme »

(etc.)

Vous devriez probablement utiliser le répertoire des préférences pour votre répertoire d'écriture, et également le placer près du début de votre chemin de recherche.   • Utilisez toujours une chaîne app unique pour chacune, et assurez-vous qu'elle ne change jamais pour une application une fois que vous l'avez décidée.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés en un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers chevauchant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser les archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un endroit spécifique de l'arborescence des fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept Unix de « montage » pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et architectures contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Lors de l'ouverture d'un lien symbolique sur un système physique, cela est effectué de manière transparente, en ouvrant le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous faire sortir des chemins de lecture et d'écriture, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Notez que cela concerne davantage le sandboxing d'un langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une raison valable de créer un lien symbolique, vous ne devriez donc pas les désactiver à moins de ressentir un danger spécifique.

Les liens symboliques seront explicitement vérifiés lorsqu'il s'agit de noms de fichiers dans une notation indépendante du système d'exploitation. Autrement dit, lors de la définition de vos chemins de recherche et d'écriture, etc., les liens symboliques ne seront jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifie toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne le suivra dans aucun cas. S'il n'est pas autorisé par cette fonction, PHYSFS_stat() ignore les liens symboliques et traiterait la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nulle pour autoriser les liens symboliques, nulle pour désactiver le lien.

Il indiquera quelle chaîne est "supérieure à" l'autre, mais gardez à l'esprit que cela n'a pas nécessairement de sens : 'a' peut être "inférieur à" 'b', mais un kuten japonais n'a pas de relation alphabétique significative avec un lambda grec, mais pouvoir attribuer une "valeur" fiable rend les algorithmes de tri possibles, bien que pas entièrement sensés. Dans la plupart des cas, vous devriez traiter la valeur de retour comme "égal" ou "non égal".

Comme stricmp, cela attend que les deux chaînes soient terminées par un caractère nul.

Paramètres

str1 Première chaîne à comparer.
str2 Seconde chaîne à comparer.

Retourne

-1 si str1 est "inférieur à" str2, 1 s'il est "supérieur à", 0 s'ils sont égaux.

Attention
