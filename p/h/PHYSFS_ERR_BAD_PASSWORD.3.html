typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent des fichiers.

Attention

À partir de PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; cela vous donne plus de contrôle sur le processus.

Ils sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de toute chaîne.

Ces rappels sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le cas dans les versions de rappel. Consultez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes en double.

enum PHYSFS_ErrorCode

Valeurs qui représentent des causes spécifiques d'échec. La plupart du temps, vous ne devriez vous préoccuper que de savoir si une opération donnée a échoué ou non, mais il peut y avoir des occasions où vous prévoyez de gérer gracieusement un cas d'échec spécifique, c'est pourquoi nous fournissons des codes d'erreur spécifiques.

La plupart de ces erreurs sont un peu vagues, et la plupart ne sont pas des choses que vous pouvez corriger... s'il y a une erreur de permission, par exemple, tout ce que vous pouvez vraiment faire est de transmettre cette information à l'utilisateur et de le laisser trouver comment la gérer. Dans la plupart de ces cas, votre programme ne devrait se soucier que de l'échec de l'accomplissement de ses objectifs, et pas spécifiquement de la raison pour laquelle.

int physFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

« Plier » un point de code Unicode vers son équivalent en minuscules. (Ceci est pour une utilisation limitée et hardcore. Si vous ne voyez pas immédiatement une utilité, vous pouvez l'ignorer pour toujours.)

Convertira un point de code Unicode vers son équivalent en minuscules. Les points de code sans équivalent en minuscules ou qui ne peuvent pas être pliés seront retournés sans modification.

Note: Il peut y avoir plusieurs points de code en retour ! L'« Eszett » allemand se convertira en deux points de code « s » minuscules. La théorie est que si vous pliez deux chaînes, l'une avec un Eszett et l'autre avec un « SS », elles correspondront.

Avertissement

Quiconque qui étudie Unicode connaît le problème du « i turc ». Cette API ne le gère pas. Elle suppose que chaque lettre de l'Unicode se comportera de manière incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez l'ignorer pour la majorité de la planète, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Le tampon où les valeurs de point de code pliées seront stockées. Il doit pointer vers de l'espace pour au moins 3 emplacements PHYSFS_uint32.

Retourne

Le nombre de points de code pliés. Entre 1 et 3.

int physFS_deinit (void )

Désinitialiser la bibliothèque PhysicsFS. Cela ferme tous les fichiers ouverts via PhysicsFS, vide les chemins de recherche/écriture, libère la mémoire et invalide tous les handles de fichiers que vous possédez.

Note : Cet appel peut échouer s'il y a un fichier ouvert en écriture qui n'a pas été fermé (par exemple, le système d'exploitation mettait en mémoire tampon des écritures vers un système de fichiers réseau, et le serveur de fichiers s'est arrêté ou un disque dur a échoué, etc.). Il est généralement préférable de fermer tous les handles d'écriture vous-même avant d'appeler cette fonction, afin de gérer gracieusement un échec spécifique.

Une fois correctement désinitialisée, PHYSFS_init() peut être appelée à nouveau pour redémarrer le sous-système. Tous les états par défaut de l'API sont restaurés à ce moment-là, à l'exception des allocateurs spécifiés personnellement, qui survivent entre les initialisations.

Retourne

Une valeur non nulle en cas de succès, zéro en cas d'erreur. Les spécifications de l'erreur peuvent être obtenues à partir de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini et probablement corrompu.

int physFS_delete (const char * filename)

Supprimer un fichier ou un répertoire. (filename) est spécifié en notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant de pouvoir être supprimé.

La suppression d'un lien symbolique supprimera le lien, pas ce vers quoi il pointe, que les liens symboliques soient autorisés ou non.

Ainsi, si vous avez défini le répertoire d'écriture sur « C:\mygame\writedir » et que vous appelez PHYSFS_delete("downloads/maps/level1.map"), alors le fichier « C:\mygame\writedir\downloads\maps\level1.map » sera supprimé du système de fichiers physique, s'il existe et que le système d'exploitation autorise la suppression.

Note : Sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel n'est pas supprimé tant que tous les processus qui ont un handle ouvert dessus (y compris votre programme) ne ferment pas leurs handles.

Les bits restants possibles du fichier existent toujours, mais sont disponibles pour être écrasés à l'avenir. Ne vous y fiez pas comme méthode de sécurité ou quoi que ce soit.

Paramètres

filename Le nom du fichier à supprimer.

Retourne

Une valeur non nulle en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int physFS_deregisterArchiver (const char * ext)

Supprimer un archiveur du système. Si pour une raison quelconque vous ne souhaitez que votre archiveur précédent soit actif que pendant une partie de la vie de votre application, vous pouvez le supprimer du système en utilisant cette fonction une fois que vous en avez terminé.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers d'un répertoire du chemin de recherche, à l'aide d'une fonction de rappel définie par l'application, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de la renvoyer à l'application, de sorte que la fonctionnalité est identique, sauf la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas un tableau. Elle appelle plutôt une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Il n'est garanti aucun ordre particulier pour les éléments envoyés à la fonction de rappel. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une seule archive, nous ne pouvons garantir l'ordre dans lequel elle découvrira les données. Tout tri que vous trouverez dans ces rappels est de la pure chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers en double.

Cette API et les fonctions de rappel elles-mêmes sont capables de signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même si elles ne recherchaient qu'une chose spécifique et voulaient s'arrêter après cela, ou avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération directement, et l'appelant ne saurait pas qu'il avait perdu des données en cours de route.

Maintenant, l'appelant peut être sûr qu'il a obtenu un ensemble complet de données, et sa fonction de rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour plus de détails sur le comportement de votre fonction de rappel.

Retourne

Non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel renvoie PHYSFS_ENUM_STOP pour s'arrêter plus tôt, cela sera considéré comme un succès. This function is used to query the currently installed memory allocator. This can be useful for debugging, or for dynamic library extensions that need to use the same memory allocation strategy as the main application.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : les doublons sont vérifiés par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers chevauchant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser les archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et empêcher le chevauchement ; ceci est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept de "montage" Unix pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

La spécification d'un lien symbolique vers une archive ou un répertoire est autorisée ici, indépendamment de l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

appendToPath Non nul pour ajouter au chemin de recherche, zéro pour ajouter au début.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous emmener en dehors des chemins de recherche et d'écriture, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné à la mise en bac à sable du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. De manière générale, un utilisateur pourrait très bien avoir une raison légitime de créer un lien symbolique, donc sauf si vous estimez qu'il existe un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors de la manipulation des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire que lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés via cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Faire d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de limiter les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt, monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer la racine d'une archive à tout moment, modifiant l'arbre de fichiers interpolé (en fonction de l'endroit où les chemins changent, une archive différente peut fournir divers fichiers). Si vous définissez la racine à NULL ou "/", l'archive sera traitée comme si aucune racine spéciale n'était définie (comme si l'archive était simplement montée normalement).

Changer la racine n'affecte que les opérations futures sur les noms de chemins ; un fichier qui a été ouvert à partir d'un chemin qui a changé en raison d'un setRoot ne sera pas affecté.

La définition d'une nouvelle racine n'est pas limitée aux archives dans le chemin de recherche ; vous pouvez en définir une sur le répertoire d'écriture, trop, ce qui pourrait être utile si vous avez des fichiers ouverts en écriture et ne pouvez donc pas changer le répertoire d'écriture pour le moment.

Il n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme racine d'une archive ; cependant, aucun fichier ne sera visible dans ce cas. Si les répertoires manquants finissent par être créés (un mkdir sur le système de fichiers physique, etc.) alors cela sera reflété dans l'arbre interpolé.

archive répertoire/archive sur laquelle changer la racine.
subdir nouveau sous-répertoire à faire de la racine de cette archive.

non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.
