PHYSFS_enumerate

Este es el mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado desde el callback: si estás buscando algo específico, una vez lo encuentres, puedes indicar a PhysicsFS que detenga la enumeración. Esto se utiliza con PHYSFS_enumerate(), que esperamos haber obtenido correctamente. :)

Parámetros

data puntero de datos usuario, pasado a través del API que finalmente llamó al callback.
origdir cadena que contiene el camino completo, en notación independiente del sistema operativo, del directorio que contiene este archivo. En la mayoría de los casos, es el directorio en el cual pediste la enumeración, pasado al callback para tu conveniencia.
fname el nombre del archivo que está siendo enumerado. Puede no estar ordenado alfabéticamente comparado con otros callbacks que hayan sido ejecutados, y no contendrá el camino completo. Puedes recrear el camino completo con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un symlink, etc.

Retorna

Un valor desde PHYSFS_EnumerateCallbackResult. Todos otros valores son (actualmente) no definidos; no los uses.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de función para callbacks que enumeran archivos.

Advertencia

Desde PhysicsFS 2.1, use PHYSFS_EnumerateCallback con PHYSFS_enumerate() para tener más control sobre el proceso.

Estos se utilizan para reportar una lista de entradas de directorio a un llamador original, una entrada de archivo/dir/symlink por callback. Todos los strings son codificados en UTF-8. Las funciones no deben intentar modificar o liberar el memoria de los strings.

Estos callbacks se utilizan, comenzando en PhysicsFS 1.1, como alternativa a funciones que devuelven listas que deben ser limpiadas con PHYSFS_freeList(). El callback significa que la librería no necesita alojar un listado completo y todas las strings al frente.

Tenga en cuenta que el orden prometido en las versiones de lista no necesariamente es el mismo en las versiones de callback. Verifique la documentación de los APIs específicos, pero los strings pueden no estar ordenados como lo esperas y podrías obtener strings duplicados.

Parámetros

data puntero de datos usuario, pasado a través del API que finalmente llamó al callback.
origdir cadena que contiene el camino completo, en notación independiente del sistema operativo, del directorio que contiene este archivo. En la mayoría de los casos, es el directorio en el cual pediste la enumeración, pasado al callback para tu conveniencia.
fname el nombre del archivo que está siendo enumerado. Puede no estar ordenado alfabéticamente comparado con otros callbacks que hayan sido ejecutados, y no contendrá el camino completo. Puedes recrear el camino completo con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un symlink, etc.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de fallo. La mayoría de las veces, deberías preocuparte solo si una operación falló, pero podría haber ocasiones donde planees manejar un caso específico de fallo con elegancia, así que ofrecemos códigos específicos de error.

La mayoría de estos errores son un poco vagos y no siempre son cosas que puedas corregir... si hay un error de permisos, por ejemplo, lo único que podrías hacer es pasar esa información a los usuarios y dejar que ellos se encarguen de cómo manejarlo. En la mayoría de estos casos, tu programa debería solo preocuparse por que falló al lograr sus metas, y no importar específicamente por qué.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers d'un répertoire depuis le chemin de recherche, en utilisant un callback défini par l'utilisateur, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit la liste avant de la retourner à l'application, donc la fonctionnalité est identique, sauf la manière dont l'information est présentée à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Elle appelle plutôt une fonction spécifiée par l'application une fois pour chaque élément du chemin de recherche :

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons [%s] dans [%s].\n", fname, origdir);
    return PHYSfs_ENUM_OK;  // donne-moi plus de données, s'il te plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés au callback ne sont garantis dans aucun ordre spécifique. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un ordre alphabétique. Cette forme signale ce qui est trouvé dans chaque archiveur avant de passer au suivant. Même au sein d'une archive, nous ne pouvons pas garantir l'ordre dans lequel les données sont découvertes. *Quel que soit l'ordre que vous trouvez dans ces callbacks est purement fortuit. Ne comptez jamais dessus.* Comme cette fonction parcourt la liste des archiveurs, vous pouvez recevoir des noms de fichiers en double.

Cette API et les callbacks eux-mêmes peuvent signaler des erreurs. Avant cette API, les callbacks devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'un objet spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque, etc.), il ne pouvait pas le signaler à l'application, il sautait simplement des éléments ou arrêtait l'énumération, et l'appelant ne savait pas qu'il avait perdu des données en chemin.

Maintenant, l'appelant peut être assuré d'avoir obtenu un ensemble complet de données, et s'il veut arrêter l'énumération plus tôt, son callback a le contrôle. Consultez la documentation de PHYSFS_EnumerateCallback pour plus de détails sur la manière dont votre callback doit se comporter.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées au rappel. Peut être NULL.

Retourne

Non zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel retourne PHYSFS_ENUM_STOP pour s'arrêter tôt, cela sera considéré comme un succès. Les rappels qui retournent PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

Obtenir une liste de fichiers d'un répertoire à partir du chemin de recherche.

Avertissement

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction retournait autant d'éléments que possible en cas d'échec (erreur de mémoire, erreur d'E/S disque, etc.). Comme cela empêchait les applications de distinguer entre succès complet et échec partiel, et comme la fonction pouvait retourner NULL pour signaler des échecs catastrophiques, dans PhysicsFS 2.1, la politique de cette fonction a changé : elle retournera une liste de résultats complets ou retournera NULL en cas d'échec de quelque type que ce soit, afin que nous puissions garantir que l'énumération s'est terminée et qu'il n'y a pas de lacunes dans vos résultats.

char **rc = PHYSFS_enumerateFiles("sauvegardes");
char **i;
for (i = rc; *i != NULL; i++)

PHYSFS_freeList(rc);

* Nous avons [y.sau].
* Nous avons [z.sau].
* Nous avons [w.sau].

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers se chevauchant avec un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer des révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et empêcher les chevauchements ; ceci est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept Unix de "montage" pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

La spécification d'un lien symbolique vers une archive ou un répertoire est autorisée ici, quel que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

int PHYSFS_mountHandle (PHYSFS_File * file, const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive, contenue dans un descripteur PHYSFS_File, au chemin de recherche.

Attention

Sauf si vous avez un besoin spécial et de bas niveau, vous devriez utiliser PHYSFS_mount() à la place.

Les archives dans les archives peuvent être très lentes ! Bien qu'un PHYSFS_File puisse effectuer un seek même lorsque les données sont compressées, il peut le faire en revenant au début et en décompressant tout avant le point de seek. L'utilisation normale d'une archive peut effectuer de nombreux seeks en arrière-plan. Par conséquent, vous pourriez trouver l'utilisation normale d'une archive extrêmement pénible si elle est montée de cette manière. Prévoyez en conséquence : si vous avez, par exemple, un fichier .zip auto-extractible et que vous souhaitez monter quelque chose à l'intérieur, compressez le contenu de l'archive interne et assurez-vous que le fichier .zip externe ne compresse pas l'archive interne.

Cette fonction fonctionne comme PHYSFS_mount(), mais prend un descripteur PHYSFS_File au lieu d'un chemin. Ce descripteur contient toutes les données de l'archive et est utilisé à la place d'un fichier réel dans le système de fichiers physique. Le PHYSFS_File peut être basé sur un fichier réel dans le système de fichiers physique, mais ce n'est pas nécessairement le cas. L'utilisation la plus courante pour cela est probablement de monter des archives stockées à l'intérieur d'autres archives.

(newDir) doit être une chaîne unique pour identifier cette archive. Elle est utilisée pour optimiser la sélection de l'archiveur (si vous la nommez XXXXX.zip, nous pourrions essayer l'archiveur ZIP en premier, par exemple, ou choisir directement un archiveur qui ne peut faire confiance à la validité des données que par l'extension du nom de fichier). Elle n'a pas besoin de faire référence à un fichier réel. Si l'extension du nom de fichier n'est pas utile, le système essaiera tous les archiveurs jusqu'à ce qu'un fonctionne ou qu'aucun d'entre eux ne fonctionne. Ce nom de fichier doit être unique, car le système ne vous permettra pas d'avoir deux archives avec le même nom.

(file) doit rester jusqu'à ce que l'archive soit démontée. Lorsque l'archive est démontée, le système appellera PHYSFS_close(file). Si vous avez besoin que ce descripteur survive, vous devrez l'encapsuler dans un PHYSFS_Io et utiliser PHYSFS_mountIo() à la place.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des références à d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, celui-ci sera ouvert de manière transparente vers le fichier auquel il se réfère.

Par défaut, PhysicsFS vérifiera si un fichier est réellement un lien symbolique lors des appels d'ouverture et échouera s'il l'est. Sinon, le lien pourrait pointer en dehors des chemins de lecture et d'écriture, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Notez que cela concerne davantage le sandboxing d'un langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur peut avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas les désactiver, sauf si vous estimez qu'il existe un danger spécifique à les autoriser.

Les liens symboliques ne sont vérifiés que lorsqu'il s'agit de noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire que lorsque votre chemin de recherche et d'écriture, etc., est défini, les liens symboliques ne sont jamais vérifiés.

Notez que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne le suivra dans aucun cas. S'il n'est pas autorisé par cette fonction, PHYSFS_stat() ignore le lien et traite la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée après l'appel à PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désactiver le lien.

Pour s'assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon dont la taille est le double de celle du tampon source. UTF-8 n'utilise jamais plus de 32 bits par caractère, donc bien qu'il puisse réduire la taille d'une chaîne UTF-16, il peut aussi l'agrandir.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais une séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

int PHYSFS_utf8stricmp (const char * str1, const char * str2)

Compare deux chaînes UTF-8 sans tenir compte de la casse. Il s'agit d'un remplacement de strcasecmp/stricmp qui attend que les deux chaînes soient encodées en UTF-8. Il effectuera un "repli de casse" pour décider si les points de code Unicode des chaînes correspondent.

Dans la plupart des cas, la valeur de retour doit être traitée comme "égale" ou "non égale".

Comme stricmp, cela attend que les deux chaînes soient terminées par un caractère nul.

str1 Première chaîne à comparer.
str2 Deuxième chaîne à comparer.

Retourne

-1 si str1 est "inférieur à" str2, 1 s'il est "supérieur à", 0 s'ils sont égaux.

PHYSFS_writeBE16, PHYSFS_writeBE32, PHYSFS_writeBE64, PHYSFS_writeLE16, PHYSFS_writeLE32, PHYSFS_writeLE64 — write integers in specific byte orders

Detailed Description

These functions are convenience wrappers around PHYSFS_write() that handle the conversion of integer types from the platform's native byte order to either big-endian or little-endian byte order, and then write the result to the specified file.

The following macros are available for convenience:

PHYSFS_writeBE16
Writes an unsigned 16-bit integer in big-endian format.
PHYSFS_writeBE32
Writes an unsigned 32-bit integer in big-endian format.
PHYSFS_writeBE64
Writes an unsigned 64-bit integer in big-endian format.
PHYSFS_writeLE16
Writes an unsigned 16-bit integer in little-endian format.
PHYSFS_writeLE32
Writes an unsigned 32-bit integer in little-endian format.
PHYSFS_writeLE64
Writes an unsigned 64-bit integer in little-endian format.
