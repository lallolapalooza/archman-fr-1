Documentation des Définitions de Macros

#define PHYSFS_file PHYSFS_File

Définit de compatibilité avec l'API 1.0. PHYSFS_file est identique à PHYSFS_File. Ce #define est présent pour la compatibilité ascendante avec l'API 1.0, qui avait une convention de capitalisation incohérente dans ce cas. Le nouveau code doit utiliser PHYSFS_File, car ce #define pourrait disparaître un jour.

    (x)->minor = PHYSFS_VER_MINOR; \
    (x)->patch = PHYSFS_VER_PATCH; \

Macro pour déterminer la version de PhysicsFS avec laquelle le programme a été compilé. Cette macro remplit une structure PHYSFS_Version

avec la version de la bibliothèque contre laquelle vous avez compilé. Ceci est déterminé par l'en-tête que le compilateur utilise. Notez que si vous avez lié dynamiquement la bibliothèque, vous pourriez avoir une version légèrement plus récente ou plus ancienne à l'exécution. Cette version peut être déterminée avec PHYSFS_getLinkedVersion(), qui, contrairement à PHYSFS_VERSION, n'est pas une macro.

typedef PHYSFS_EnumerateCallbackResult(* PHYSFS_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Valeurs de retour possibles pour PHYSFS_EnumerateCallback. Signature de fonction pour les rappels qui énumèrent et retournent des résultats.

Ces valeurs dictent si un rappel d'énumération doit continuer à être déclenché, ou s'arrêter (et pourquoi il s'arrête).

PHYSFS_EnumerateCallback

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du rappel : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, transmis par l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport aux autres rappels qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers d'un répertoire du chemin de recherche, en utilisant un rappel défini par l'application, avec des erreurs signalées. Interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique sauf la façon dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas de tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés au rappel ne sont garantis dans aucun ordre particulier. Il n'y a pas de tri effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme rapporte ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel elle découvrira les données. Tout tri que vous trouvez dans ces rappels est purement dû au hasard. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient en alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble de données complet, et son rappel a le contrôle s'il souhaite que l'énumération s'arrête tôt. Voir la documentation de PHYSFS_EnumerateCallback pour plus de détails sur le comportement attendu de votre rappel.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées au rappel. Peut être NULL.

Retourne

Non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel retourne PHYSFS_ENUM_STOP pour s'arrêter tôt, cela sera considéré comme un succès. Les rappels retournant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

char **rc = PHYSFS_enumerateFiles("sauvegardes");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Nous avons [%s].\n", *i);
PHYSFS_freeList(rc);
* Nous avons [x.sav].
* Nous avons [y.sav].
* Nous avons [z.sav].
* Nous avons [w.sav]..fi

int PHYSFS_setBuffer (PHYSFS_File * handle, PHYSFS_uint64 bufsize)

Définit le tampon de lecture/écriture pour un descripteur de fichier PhysicsFS. Définit un tampon d'E/S pour un descripteur de fichier. Un bloc de mémoire de (bufsize) octets sera alloué et associé à (handle).

Pour les fichiers ouverts en écriture, les données seront stockées en mémoire jusqu'à ce que le tampon soit plein ou qu'un vidage soit effectué. La fermeture d'un descripteur déclenchera un vidage.

void PHYSFS_setBuffer (PHYSFS_File * handle, size_t bufsize)

Le dice a PhysicsFS que almacene en búfer las operaciones de E/S para este archivo. Esto puede mejorar drásticamente el rendimiento, ya que las llamadas al sistema operativo son costosas. Establecer el tamaño del búfer a cero se considerará un error (el tamaño mínimo del búfer es 1, o PHYSFS_ OSError si es 0).

Por defecto, las operaciones de E/S para los archivos no se almacenan en búfer. Esto significa que cada llamada a PHYSFS_read() o PHYSFS_write() resultará en una llamada al sistema operativo. Esto también significa que cada llamada a PHYSFS_write() forzará un PHYSFS_flush(3), que implícitamente causa un flush... ¡compruebe los valores de retorno!

El seeking, etc. maneja transparentemente el búfer.
