Signature de fonction pour les rappels qui énumèrent des fichiers.

Attention

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; cela vous donne plus de contrôle sur le processus.

Ils sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de ces chaînes.

Ces rappels sont utilisés, à partir de PhysicsFS 1.1, comme une alternative aux fonctions qui renvoyaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions liste ne l'est pas nécessairement dans les versions rappel. Consultez la documentation sur les API spécifiques, mais les chaînes peuvent ne pas être triées comme vous l'attendez et vous pourriez obtenir des chaînes en double.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

« Plie » un point de code Unicode vers son équivalent en minuscules. (Ceci est pour une utilisation limitée et avancée. Si vous ne voyez pas immédiatement un besoin, vous pouvez probablement ignorer cela pour toujours.)

Cela convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux n'ayant pas d'équivalent en minuscules seront renvoyés sans conversion.

Notez que vous pourriez obtenir plusieurs points de code en retour ! La lettre allemande Eszett, par exemple, sera pliée en deux points de code latins minuscules « s ». La théorie est que si vous pliez deux chaînes, l'une avec un Eszett et l'une avec « SS », elles correspondront.

Attention

Quiconque étudiant Unicode connaît le problème du « I turc ». Cette API ne le gère pas. Supposez que cette seule lettre dans tout Unicode sera pliée de manière quelque peu incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la plupart de la planète, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Tampon pour stocker les valeurs de points de code pliés. Cela doit pointer vers un espace pour au moins 3 emplacements de PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialise la bibliothèque PhysicsFS. Cela ferme tous les fichiers ouverts via PhysicsFS, efface les chemins de recherche/écriture, libère la mémoire et invalide toutes vos poignées de fichier.

Notez que cet appel peut ÉCHOUEUR s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures sur un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur a échoué, etc.). Il est généralement préférable de fermer toutes les poignées d'écriture vous-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois correctement désinitialisé, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états par défaut de l'API sont restaurés à ce moment-là, à l'exception de tout allocateur personnalisé que vous auriez pu spécifier, qui survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les détails de l'erreur peuvent être obtenus à partir de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini, et probablement très corrompu.

int PHYSFS_delete (const char * filename)

Supprime un fichier ou un répertoire. (filename) est spécifié dans une notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, pas ce qu'il pointe, que vous ayez « autorisé les liens symboliques » ou non.

Donc, si vous avez le répertoire d'écriture défini sur "C:\monjeu\rep_ecriture" et que vous appelez PHYSFS_delete("telechargements/cartes/niveau1.carte"), alors le fichier "C:\monjeu\rep_ecriture\telechargements\cartes\niveau1.carte" est supprimé du système de fichiers physique, s'il existe et si le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont une poignée de fichier ouverte dessus (y compris votre programme) ne fermeront pas leurs poignées.

Il y a de fortes chances que les bits qui composent le fichier existent toujours, ils sont simplement rendus disponibles pour être écrasés plus tard. Ne considérez pas cela comme une méthode de sécurité ou quoi que ce soit. :)

Paramètres

filename Nom du fichier à supprimer.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_enumerate(const char *dir, PHYSFS_EnumerateCallback c, void *d)

Obtiene una lista de archivos de una ruta de búsqueda, usando una función de callback definida por el usuario, con errores reportados. Internamente, PHYSFS_enumerateFiles() solo llama a esta función y luego construye una lista antes de devolver a la aplicación, así que la funcionalidad es idéntica, pero la información se presenta de forma diferente a la aplicación.

Diferente de PHYSFS_enumerateFiles(), esta función no retorna un array. En lugar de eso, llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Los elementos enviados a la callback no están garantizados para estar en ningún orden específico. No hay ordenamiento hecho a este nivel, y si lo necesitas, deberías usar PHYSFS_enumerateFiles(), que garantiza el orden alfabético. Esta forma reporta lo que encuentra en cada archive antes de moverse al siguiente. Incluso dentro de un archive, no podemos garantizar el orden en que se descubren los datos. Cualquier ordenamiento que encuentres en estas callbacks es solo pura suerte. No confíes en él. Como esta camina toda la lista de archives, puedes recibir nombres de archivos duplicados.

Esta API y las funciones de callback son capaces de reportar errores. Antes de esta API, las funciones de callback tenían que aceptar cada elemento enumerado, incluso si solo buscaban un objeto específico y querían detenerse después, o tenían un error grave y no podían notificar a nadie. Además, si PhysicsFS mismo tenía un problema (error de disco o lo que sea), no podría reportarlo a la aplicación que llama, simplemente tendría que saltar los elementos o detener la enumeración, y la que llama no sabría que había perdido algunos datos en el camino.

Ahora la que llama puede estar segura de haber obtenido un conjunto completo de datos, y si quiere detener la enumeración temprano, su callback tiene control. Ver la documentación para PHYSFS_EnumerateCallback para detalles sobre cómo debe comportarse su callback.

c Función de callback para notificar sobre elementos de la ruta de búsqueda.
d Datos definidos por la aplicación para pasar a la callback. Puede ser NULL.

Retorno

No cero en éxito, cero en error. Usa PHYSFS_getLastErrorCode() para obtener el error específico. Si la callback devuelve PHYSFS_ENUM_STOP para detener temprano, este se considera éxito. Las callbacks que devuelven PHYSFS_ENUM_ERROR harán que esta función retorne cero y establecerá el código de error a PHYSFS_ERR_APP_CALLBACK.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive dont les fichiers chevauchent un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Ceci permet d'utiliser des archives pour remplacer les versions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; ceci est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que les personnes familières avec le concept Unix de « montage » pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

Spécifier un lien symbolique vers une archive ou un répertoire est autorisé ici, quel que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

Paramètres

newDir répertoire ou archive à ajouter au chemin, en notation spécifique à la plateforme.
mountPoint Emplacement dans l'arbre interpolé où cette archive sera « montée », en notation indépendante de la plateforme. NULL ou «  » équivaut à « / ».
appendToPath une valeur non nulle pour ajouter au chemin de recherche, zéro pour ajouter au début.

Retourne

une valeur non nulle si ajouté au chemin, zéro en cas d'échec (archive invalide, répertoire manquant, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et architectures contiennent des fichiers qui ne sont que des références à d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, cela se fera de manière transparente lors de l'ouverture du fichier auquel il se réfère.

Par défaut, PhysicsFS vérifiera si un fichier est réellement un lien symbolique lors des appels d'ouverture et échouera si c'est le cas. Sinon, le lien pourrait vous emmener en dehors des chemins de lecture et d'écriture, ce qui pourrait compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Notez que cela est davantage destiné au sandboxing d'un langage de programmation de script, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas les désactiver, à moins que vous ne ressentiez un danger spécifique.

Les liens symboliques ne seront considérés que lorsque des noms de fichiers sont manipulés dans une notation indépendante du système d'exploitation. Autrement dit, lorsque vos chemins de recherche et d'écriture, etc., sont définis, les liens symboliques ne seront jamais examinés pour vérification.

Notez que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne le suivra dans aucun cas. Si vous n'autorisez pas les liens symboliques via cette fonction, PHYSFS_stat() les ignorera et traitera la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée à tout moment après l'appel de PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désactiver le lien.

int PHYSFS_setBuffer (PHYSFS_File * handle, PHYSFS_uint64 bufsize)

Définit le tampon d'un handle de fichier PhysFS. Définit un tampon d'E/S pour un handle de fichier. Un bloc de mémoire de (bufsize) octets est alloué et associé à (handle).

Pour les fichiers ouverts en lecture, jusqu'à (bufsize) octets sont lus à partir de (handle) et stockés dans le tampon interne. Les appels à PHYSFS_read() extrairont du tampon jusqu'à ce qu'il soit vide, puis il sera rempli pour des lectures supplémentaires. Notez que les fichiers compressés, tels que les archives ZIP, sont décompressés lors de la mise en tampon, ce qui peut être utile pour décaler les opérations gourmandes en CPU. Le tampon ne sera pas rempli avant que vous n'effectuez votre prochaine lecture.

Pour les fichiers ouverts en écriture, les données seront mises en tampon en mémoire jusqu'à ce que le tampon soit plein ou qu'une opération de vidage soit effectuée. La fermeture d'un handle dissocie le tampon.

L'opération provoque implicitement un vidage... vérifiez les valeurs de retour !

La recherche, etc. s'occupe de la mise en mémoire tampon de manière transparente.

Vous pouvez redimensionner un tampon existant en appelant cette fonction plus d'une fois sur le même fichier. Définir la taille du tampon à zéro libérera un tampon existant.

Les descripteurs de fichiers PhysicsFS sont sans tampon par défaut.

Veuillez vérifier la valeur de retour de cette fonction ! Elle peut indiquer des problèmes inattendus tels que l'impossibilité de reculer dans un fichier en lecture seule lors de la suppression du tampon, l'impossibilité d'allouer le tampon, et l'impossibilité de vider le tampon sur disque, parmi d'autres problèmes inattendus.

Paramètres

handle descripteur renvoyé par PHYSFS_open*().
bufsize taille, en octets, du tampon à allouer.

Définir une nouvelle racine n'est pas limitée aux archives dans le chemin de recherche ; vous pouvez en définir une dans le répertoire d'écriture également, ce qui peut être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez pas changer le répertoire d'écriture pour le moment.

archive répertoire/archive sur lequel changer la racine.
subdir nouveau sous-répertoire à faire de la racine de cette archive.

Retourne

non zéro en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convertit une chaîne Latin1 en une chaîne UTF-8. Les chaînes Latin1 utilisent 8 bits par caractère : un encodage "ASCII étendu" populaire.

Pour garantir que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon de double la taille du tampon source. UTF-8 étend les points de code Latin1 supérieurs à 127 de 1 à 2 octets, la chaîne peut donc parfois s'agrandir.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Veuillez noter que nous ne fournissons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer la plupart des points de code Unicode. C'est un encodage hérité ; vous devriez toujours vous en éloigner.

Paramètres

src Chaîne source terminée par un caractère nul au format Latin1.
dst Tampon pour stocker la chaîne UTF-8 convertie.
len Taille, en octets, du tampon de destination.
