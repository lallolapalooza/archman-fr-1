Signature de fonctions de callbacks qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate(); cela permet plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, une entrée par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire des chaînes.

Ces callbacks sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui retournent des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes au préalable.

Notez que les garanties de tri dans les versions de liste ne sont pas nécessairement présentes dans les versions de callback. Vérifiez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme prévu et vous pourriez obtenir des doublons.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Fold" a Unicode codepoint to a lowercase equivalent. (This is for limited, hardcore use. If you don't immediately see a need for it, you can probably ignore this forever.)

This will convert a Unicode codepoint into its lowercase equivalent. Bogus codepoints and codepoints without a lowercase equivalent will be returned unconverted.

Note that you might get multiple codepoints in return! The German Eszett, for example, will fold down to two lowercase latin 's' codepoints. The theory is that if you fold two strings, one with an Eszett and one with "SS" down, they will match.

Warning

Anyone that is a student of Unicode knows about the "Turkish I" problem. This API does not handle it. Assume this one letter in all of Unicode will definitely fold sort of incorrectly. If you don't know what this is about, you can probably ignore this problem for most of the planet, but perfection is impossible.

Parameters

from The codepoint to fold.
to Buffer to store the folded codepoint values into. This should point to space for at least 3 PHYSFS_uint32 slots.

Returns

The number of codepoints the folding produced. Between 1 and 3.

int PHYSFS_deinit (void )

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). It is usually best to close all write handles yourself before calling this function, so that you can gracefully handle a specific failure.

Once successfully deinitialized, PHYSFS_init() can be called again to restart the subsystem. All default API states are restored at this point, with the exception of any custom allocator you might have specified, which survives between initializations.

Returns

nonzero on success, zero on error. Specifics of the error can be gleaned from PHYSFS_getLastError(). If failure, state of PhysFS is undefined, and probably badly screwed up.

int PHYSFS_delete (const char * filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné à l'isolation d'un langage de script de programme, au cas où des scripts non fiables essaieraient de compromettre le système. De manière générale, un utilisateur pourrait très bien avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne ressentiez un danger spécifique à leur autorisation, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lorsqu'il s'agit de noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire que lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

int PHYSFS_setRoot (const char * archive, const char * subdir)

Fait d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de restreindre les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier à y/z.txt, monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel à PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez modifier le répertoire racine d'une archive à tout moment, ce qui modifie l'arborescence de fichiers interpolée (selon l'endroit où les chemins sont déplacés, une archive différente peut fournir différents fichiers). La définition d'un nouveau répertoire racine n'est pas limitée aux archives dans le chemin de recherche ; vous pouvez également en définir une dans le répertoire d'écriture, ce qui pourrait être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez pas changer le répertoire d'écriture pour le moment.

Il n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme répertoire racine d'une archive, bien qu'aucun fichier ne soit affiché dans ce cas. archive le répertoire/fichier dont le répertoire racine sera changé.
subdir le nouveau sous-répertoire à définir comme répertoire racine de cette archive.

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convertir una cadena UTF-8 en una cadena UTF-16.

Aviso

Esta función no reportará un error si hay secuencias de UTF-8 inválidas en la cadena de entrada. Reemplazará las mismas con un carácter '?' y continuará.

Las cadenas UTF-16 tienen 16 bits por carácter (a excepción de algunos caracteres, que son 32 bits): TCHAR en Windows, cuando se compila con soporte Unicode. Las versiones modernas de Windows usan UTF-16. Las versiones antiguas de Windows antes de 2000 usaban TCHAR, pero solo manejaron UCS-2. UTF-16 es UCS-2, excepto para los caracteres que son 4 bytes, que no pueden representarse en UCS-2 por completo. Si no estás seguro, deberías estar usando UTF-16 en Windows en este punto.

Para asegurar que el buffer de destino sea lo suficientemente grande para la conversión, por favor allocate un buffer que sea el doble del tamaño del buffer de fuente. UTF-8 utiliza de 1 a 4 bytes por carácter, pero UTF-16 siempre utiliza 2 a 4, por lo que una cadena de ASCII completamente baja doblará en tamaño! Los caracteres UTF-16 que ocupan 4 bytes también ocupan 4 bytes en UTF-8, por lo que no necesitas alojar 4 veces el espacio, solo doblarás.

Las cadenas que no se ajustan al buffer de destino serán truncadas, pero siempre estarán terminadas con un carácter nulo y no tendrán un par de surrondados incompletos en la parte final. Si el tamaño del buffer es 0, esta función no hace nada.

dst Buffer para almacenar la cadena UTF-16 convertida.
