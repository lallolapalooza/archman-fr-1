PHYSFS_VERSION

PHYSFS_VERSION

A macro that describes the version of the PhysicsFS library. It's used to ensure that the version of the header file you're compiling against is compatible with the version of the library you're linking against.

Usage

To check that you have a compatible version of the library:

#if (PHYSFS_VERSION_MAJOR != 2) || (PHYSFS_VERSION_MINOR != 4) || (PHYSFS_VERSION_PATCH != 0)
#error "Your PhysicsFS header files are not compatible with the PhysicsFS library!"
#endif

If you are dynamically linking the library, you might also want to check the runtime version using PHYSFS_getLinkedVersion(). This is generally a good idea to prevent runtime crashes due to incompatible shared libraries.

See also

PHYSFS_getLinkedVersion()

PHYSFS_getLinkedVersion

const PHYSFS_Version* PHYSFS_getLinkedVersion(void);

Returns a pointer to a static PHYSFS_Version struct that describes the version of the dynamically linked PhysicsFS library.

This function is intended to be used to verify that the version of the PhysicsFS library that the application is dynamically linked against is compatible with the version of the library that the application was compiled against. This is important for preventing runtime errors caused by incompatible library versions.

The returned pointer points to a statically allocated PHYSFS_Version struct, so it should not be freed or modified.

Example

const PHYSFS_Version *ver = PHYSFS_getLinkedVersion();
if (ver->major > 2 || (ver->major == 2 && ver->minor > 4)) {
    fprintf(stderr, "Warning: PhysicsFS library version is newer than expected!\n");
}

int PHYSFS_init(const char *argv0);

Initialize the PhysicsFS library. This function must be called before any other PhysicsFS function is used.

The argv0 parameter is used to determine the platform-specific default directories where the library should look for archives and other data files. On Unix-like systems, this is typically the path to the executable. On Windows, it can be NULL.

If initialization is successful, the function returns 1. Otherwise, it returns 0.

Parameters

Returns

1 on success, 0 on failure.

PHYSFS_getSearchPath

char** PHYSFS_getSearchPath(void);

Returns a dynamically allocated array of strings, where each string is a path to a directory or archive that PhysicsFS will search for files.

The order of the paths in the array indicates the search precedence. The first element is the highest precedence, and the last element is the lowest.

This function is useful for debugging or for iterating through the search path to perform custom operations.

The returned array and its contents are dynamically allocated and must be freed using PHYSFS_freeList() when no longer needed.

Returns

A NULL-terminated array of strings representing the search path, or NULL if an error occurred.

PHYSFS_enumerateFilesCallback

typedef void(* PHYSFS_enumerateFilesCallback) (void *data, const char *origdir, const char *fname);

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

See also

PHYSFS_enumerate

int PHYSFS_enumerate(const char *dirname, PHYSFS_EnumerateCallback callback, void *data);

Enumerates the contents of a directory.

This function iterates through all the files and subdirectories within the specified directory (dirname) and calls the provided callback function (callback) for each entry found. The callback function receives a pointer to user-defined data (data), the full path of the directory containing the entry (origdir), and the name of the entry (fname).

The callback function can return one of the following values to control the enumeration process:

  • PHYSFS_ENUM_OK: Continue enumeration.
  • PHYSFS_ENUM_STOP: Stop enumeration and return success.
  • PHYSFS_ENUM_ERROR: Stop enumeration and return an error.

Parameters

dirname The directory to enumerate.
callback The callback function to be called for each entry.
data User-defined data to be passed to the callback function.

Returns

1 on success, 0 on failure.

int PHYSFS_registerMount(const char *mountName, const char *description, PHYSFS_MountCallback mountCallback, PHYSFS_UnmountCallback unmountCallback, void *data);

Registers a new mount point with PhysicsFS.

This function allows you to register a custom file system or archive format with PhysicsFS. When PhysicsFS needs to access a file within this mount point, it will call the provided mountCallback function.

The mountName is a unique identifier for the mount point (e.g., "zip"). The description is a human-readable description. The mountCallback is a function that will be called when the mount point is accessed. The unmountCallback is a function that will be called when the mount point is removed. The data is a pointer to user-defined data that will be passed to the callbacks.

Parameters

mountName The unique name of the mount point.
description A human-readable description of the mount point.
mountCallback The function to call when the mount point is accessed.
unmountCallback The function to call when the mount point is removed.
data User-defined data to be passed to the callbacks.

Returns

1 on success, 0 on failure.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenez une liste de fichiers d'un répertoire du chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec des rapports d'erreurs. Interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique sauf pour la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Plutôt, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons trouvé [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis d'être dans aucun ordre quelconque. Il n'y a pas de tri effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme rapporte ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une seule archive, nous ne pouvons pas garantir l'ordre de découverte des données. Tout tri que vous trouverez dans ces appels de fonction n'est que de la pure chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pourriez recevoir des noms de fichiers dupliqués.

Cette API et les fonctions de rappel elles-mêmes sont capables de signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après cela, ou s'ils avaient une erreur sérieuse et ne pouvaient en alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération purement et simplement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble complet de données, et sa fonction de rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement de votre fonction de rappel.

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel retourne PHYSFS_ENUM_STOP pour s'arrêter tôt, cela sera considéré comme un succès. Obtenir le chemin spécifique à l'utilisateur et à l'application où les fichiers peuvent être écrits. Fonction d'assistance.

Obtient le "répertoire de préférences". Il est destiné à être l'endroit où les utilisateurs peuvent écrire des fichiers personnels (préférences, sauvegardes, etc.) spécifiques à votre application. Ce répertoire est unique par utilisateur, par application.

Sous Linux, cela pourrait ressembler à : "/home/bob/.local/share/Mon Nom de Programme"

Sous Mac OS X, cela pourrait ressembler à : "/Users/bob/Library/Application Support/Mon Nom de Programme"

(etc.)

Vous devriez probablement utiliser le répertoire de préférences pour votre répertoire d'écriture, et également le placer près du début de votre chemin de recherche. int PHYSFS_mount (const char * archive, const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive, contenue dans un fichier PHYSFS_File, au chemin de recherche.

Avertissement

À moins que vous n'ayez un besoin spécial de bas niveau, vous devriez utiliser PHYSFS_mount() à la place.

Les archives dans les archives peuvent être très lentes ! Bien qu'un PHYSFS_File puisse chercher même lorsque les données sont compressées, il peut le faire en revenant au début et en décompressant tout avant le point de recherche. L'utilisation normale des archives peut effectuer de nombreuses recherches en arrière-plan. En tant que tel, vous pourriez trouver l'utilisation normale des archives extrêmement pénible si elles sont montées de cette manière. Prévoyez en conséquence : si vous avez, par exemple, un fichier .zip auto-extractible et que vous souhaitez monter quelque chose à l'intérieur, compressez le contenu de l'archive interne et assurez-vous que le fichier .zip externe ne compresse pas l'archive interne également.

Cette fonction fonctionne comme PHYSFS_mount(), mais prend un descripteur PHYSFS_File au lieu d'un chemin d'accès. Ce descripteur contient toutes les données de l'archive et est utilisé à la place d'un vrai fichier dans le système de fichiers physique. Le PHYSFS_File peut être sauvegardé par un vrai fichier dans le système de fichiers physique, mais ce n'est pas nécessairement le cas. L'utilisation la plus courante est probablement de monter des archives stockées à l'intérieur d'autres archives.

(newDir) doit être une chaîne unique pour identifier cette archive. Elle est utilisée pour optimiser la sélection de l'archiveur (si vous la nommez XXXXX.zip, nous pourrions essayer l'archiveur ZIP en premier, par exemple, ou choisir directement un archiveur qui ne peut garantir que les données sont valides que par l'extension du nom de fichier). Il n'a pas besoin de faire référence à un vrai fichier. Si l'extension du nom de fichier n'est pas utile, le système essaiera tous les archiveurs jusqu'à ce qu'un fonctionne ou qu'aucun d'entre eux ne fonctionne. Ce nom de fichier doit être unique, car le système ne vous permettra pas d'avoir deux archives portant le même nom.

(file) doit rester jusqu'à ce que l'archive soit démontée. Lorsque l'archive est démontée, le système appellera PHYSFS_close(file). Si vous avez besoin que ce descripteur survive, vous devrez l'encapsuler dans un PHYSFS_Io et utiliser PHYSFS_mountIo() à la place.

Si cette fonction échoue, PHYSFS_close(file) n'est pas appelée.

newDir Nom de fichier qui peut représenter ce flux.
mountPoint Emplacement dans l'arbre interpolé où cette archive sera « montée », dans une notation indépendante de la plateforme. NULL ou « » est équivalent à « / ».
appendToPath non nul pour ajouter au chemin de recherche, zéro pour précéder.

Retourne

non nul si ajouté au chemin, zéro en cas d'échec (archive invalide, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_autoriserSymbolicLinks (int allow)

Activer ou désactiver le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné au cloisonnement du langage de script d'un programme, au cas où des scripts non fiables essaieraient de compromettre le système. D'une manière générale, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne sentiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors de la manipulation de noms de fichiers en notation indépendante de la plateforme. C'est-à-dire que lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore, et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convertit une chaîne de caractères UTF-8 en une chaîne de Latin1. Les chaînes de Latin1 ont chaque caractère sur 8 bits : un "encodage ASCII élevé" populaire.

Pour garantir que le tampon de destination soit suffisamment grand pour la conversion, veuillez allouer un tampon de double taille par rapport au tampon source. L'UTF-8 étend les codes Latin1 supérieurs à 127 à 2 octets, donc la chaîne peut s'agrandir dans certains cas.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais une séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Note : aucun convertisseur UTF-8 vers Latin1 n'est fourni, car Latin1 ne peut pas exprimer de nombreux codes Unicode. C'est un vieil encodage ; vous devriez vous convertir à partir de celui-ci dans tous les cas.

Paramètres

src Chaîne Latin1 terminée par un caractère nul.
dst Tampon pour stocker la chaîne UTF-8 convertie.
len Taille en octets du tampon de destination.
