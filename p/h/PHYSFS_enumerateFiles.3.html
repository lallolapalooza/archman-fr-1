int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Plie" un point de code Unicode vers un équivalent en minuscules. (Ceci est pour une utilisation limitée et avancée. Si vous ne voyez pas immédiatement un besoin pour cela, vous pouvez probablement l'ignorer pour toujours.)

Ceci convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux sans équivalent en minuscules seront retournés inchangés.

Notez que vous pourriez obtenir plusieurs points de code en retour ! L'eszett allemand, par exemple, sera "plié" en deux points de code latins 's' en minuscules. La théorie est que si vous pliez deux chaînes, l'une avec un Eszett et l'autre avec "SS", elles correspondront.

Attention

Quiconque étudie l'Unicode connaît le problème du "I turc". Cette API ne le gère pas. Supposons que cette seule lettre dans tout Unicode sera certainement pliée de manière quelque peu incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la plupart des cas, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Tampon pour stocker les valeurs des points de code pliés. Il doit pointer vers un espace pour au moins 3 emplacements PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialise la bibliothèque PhysicsFS. Cela ferme tous les fichiers ouverts via PhysicsFS, efface les chemins de recherche/d'écriture, libère la mémoire et invalide toutes vos poignées de fichiers.

Notez que cet appel peut ÉCHOUE si un fichier ouvert en écriture refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures sur un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur est tombé en panne, etc.). Il est généralement préférable de fermer toutes les poignées d'écriture vous-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois désinitialisé avec succès, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états par défaut de l'API sont restaurés à ce stade, à l'exception de tout allocateur personnalisé que vous auriez pu spécifier, qui survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les détails de l'erreur peuvent être obtenus à partir de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini, et probablement très dégradé.

int PHYSFS_delete (const char * filename)

Supprime un fichier ou un répertoire. (filename) est spécifié dans une notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, pas ce à quoi il pointe, indépendamment du fait que vous ayez autorisé ou non les liens symboliques (`permitSymLinks`).

Donc, si vous avez défini le répertoire d'écriture sur "C:\monjeu\dossier_ecriture" et que vous appelez PHYSFS_delete("telechargements/cartes/niveau1.carte"), alors le fichier "C:\monjeu\dossier_ecriture\telechargements\cartes\niveau1.carte" est supprimé du système de fichiers physique, s'il existe et que le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont une poignée de fichier ouverte sur lui (y compris votre programme) ne fermeront pas leurs poignées.

Il y a de fortes chances que les bits qui composent le fichier existent toujours, ils sont juste rendus disponibles pour être écrasés plus tard. Ne considérez pas cela comme une méthode de sécurité ou autre. :)

Paramètres

filename Nom du fichier à supprimer.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_deregisterArchiver (const char * ext)

Supprime un archiveur du système. Si pour une raison quelconque vous n'avez besoin que de votre archiveur précédemment enregistré qu'il vive pendant une partie de la durée de vie de votre application, vous pouvez le supprimer du système une fois que vous avez terminé via cette fonction.

Cela échoue s'il y a des archives encore ouvertes qui utilisent cet archiveur.

Cette fonction peut également supprimer les archiveurs fournis en interne, tels que le support .zip ou autre. Cela pourrait être utile dans certaines situations, comme désactiver complètement le support pour eux ou les remplacer par votre propre implémentation. int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers d'un répertoire du chemin de recherche, en utilisant un rappel défini par l'application, avec des erreurs signalées. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique sauf quant à la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés au rappel ne sont garantis dans aucun ordre spécifique. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons pas garantir l'ordre de découverte des données. Tout tri que vous trouverez dans ces appels de rappel n'est que pure chance. N'en dépendez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient en alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération brutalement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr qu'il a obtenu un ensemble complet de données, et son rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement attendu de votre rappel.

d Données définies par l'application passées au rappel. Peut être NULL.

Retourne

Non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel retourne PHYSFS_ENUM_STOP pour s'arrêter tôt, cela sera considéré comme un succès. int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute un fichier ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter le même fichier à deux points de montage différents : la vérification des doublons se fait par rapport au fichier, et non par rapport au point de montage.

Lors du montage d'un fichier, celui-ci est ajouté à un système de fichiers virtuel... tous les fichiers de tous les fichiers montés sont intercalés dans un seul arbre hiérarchique. Deux fichiers montés au même endroit (ou un fichier avec des fichiers qui chevauchent un point de montage) peuvent avoir des fichiers qui se chevauchent : dans ce cas, le fichier le plus proche dans le chemin de recherche est choisi, et les autres fichiers ne sont pas accessibles à l'application. Cela permet d'utiliser des fichiers pour remplacer des révisions antérieures ; vous pouvez utiliser le mécanisme de montage pour placer des fichiers à un point spécifique dans l'arborescence du système et empêcher le chevauchement ; c'est utile pour les modes téléchargeables qui peuvent écraser des données d'application ou s'écraser mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui diffère de ce que les utilisateurs familiers avec le concept de « montage » sous Unix pourraient attendre. appendToPath Non nul pour ajouter au chemin de recherche, nul pour ajouter au début.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et architectures contiennent des fichiers qui ne sont que des références à d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, ce lien sera transparentement ouvert pour ouvrir le fichier auquel il fait référence.

Par défaut, PhysicsFS vérifiera si un fichier est en fait un lien symbolique lors des appels d'ouverture et échouera s'il l'est. Sinon, le lien pourrait vous amener en dehors des chemins de lecture et d'écriture, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Remarque : ceci est davantage destiné au sandboxing d'un langage de script du programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une bonne raison légitime de créer un lien symbolique, vous ne devriez donc pas le désactiver, sauf si vous sentez qu'il y a un danger spécifique à le permettre.

Les liens symboliques ne sont jamais vus lors de la manipulation de noms de fichiers dans la notation non physique. C'est-à-dire que lors de la définition de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vus pour la vérification.

Remarque : PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés par le biais de cette fonction, PHYSFS_stat() les ignorera et traitera la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Définit un sous-répertoire d'une archive comme répertoire racine. Cela vous permet de limiter les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel à PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer la racine d'une archive à tout moment, ce qui modifie l'arborescence de fichiers interpolée (selon l'endroit où les chemins sont déplacés, cela pourrait fournir des fichiers différents d'une archive différente). Si vous définissez la racine sur NULL ou "/", l'archive sera traitée comme si elle n'avait pas de racine spéciale (comme si l'archive était montée normalement).

Changer la racine n'affecte que les opérations futures sur les chemins de répertoires ; une archive qui a été ouverte à partir d'un chemin qui a changé en raison d'un setRoot ne sera pas affectée.

La définition d'une nouvelle racine n'est pas limitée aux archives dans le chemin de recherche ; vous pouvez en définir une dans le répertoire d'écriture, ce qui pourrait être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez pas changer le répertoire d'écriture pour le moment.

Il est inadmissible de définir un sous-répertoire qui n'existe pas comme racine d'une archive ; cependant, aucun fichier ne sera vu dans ce cas. Si les répertoires manquants finissent par être créés (un mkdir sur le système de fichiers physique, etc.), cela se reflétera dans l'arborescence interpolée.

Paramètres

archive répertoire/archive dont la racine sera changée.
subdir nouveau sous-répertoire à définir comme racine de cette archive.

Retour

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convertit une chaîne UTF-8 en une chaîne Latin1. Les chaînes Latin1 utilisent 8 bits par caractère : un encodage "high ASCII" populaire.

Pour garantir que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon dont la taille est le double de la taille du tampon source. L'UTF-8 étend les points de code Latin1 supérieurs à 127 de 1 à 2 octets, la chaîne peut donc augmenter dans certains cas.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Notez que nous ne fournissons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer la plupart des points de code Unicode. C'est un encodage hérité ; vous devriez toujours essayer de le convertir.

Paramètres

src Chaîne source terminée par un caractère nul en format Latin1.
dst Tampon pour stocker la chaîne UTF-8 convertie.
len Taille, en octets, du tampon de destination.
