PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du callback : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, transmis depuis l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, transmis dans le callback pour votre commodité.
fname Le nom du fichier qui est énuméré. Il pourrait ne pas être dans l'ordre alphabétique par rapport à d'autres callbacks qui ont été évalués, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent des fichiers.

Attention

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; cela vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire d'une chaîne.

Ces callbacks sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions par liste n'est pas nécessairement le cas dans les versions par callback. Vérifiez la documentation des API spécifiques, mais les chaînes pourraient ne pas être triées comme vous vous y attendez et vous pourriez obtenir des doublons.

Paramètres

data Pointeur de données défini par l'utilisateur, transmis depuis l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, transmis dans le callback pour votre commodité.
fname Le nom du fichier qui est énuméré. Il pourrait ne pas être dans l'ordre alphabétique par rapport à d'autres callbacks qui ont été évalués, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

En interne, PHYSFS_enumerateFiles() n'appelle que cette fonction puis construit une liste avant de la renvoyer à l'application, donc la fonctionnalité est identique, sauf la façon dont l'information est présentée à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'utilisateur une fois pour chaque élément dans le chemin de recherche :

{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // je veux plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments passés à la callback ne sont garantis d'être dans aucun ordre spécifique. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un ordre alphabétique. Cette forme signale ce qui est trouvé dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout tri que vous trouverez dans ces callbacks est purement un hasard. Ne vous y fiez pas. Comme cette fonction parcourt toute la liste des archives, vous pourriez recevoir des noms de fichiers dupliqués.

Cette API et les callbacks elles-mêmes peuvent signaler des erreurs. Avant cette API, les callbacks devaient accepter chaque élément énuméré, même si elles ne recherchaient qu'un objet spécifique et voulaient s'arrêter là, ou si elles avaient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pourrait pas le signaler à l'application appelante, il passerait simplement à l'élément suivant ou arrêterait l'énumération, et l'appelant ne saurait pas qu'il avait perdu des données en cours de route.

Maintenant, l'appelant peut être assuré qu'il a obtenu un ensemble complet de données, et s'il le souhaite, sa callback a le contrôle sur quand arrêter l'énumération. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur la façon dont votre callback doit se comporter.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il existe déjà, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans une seule structure d'arbre hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers qui se chevauchent avec un point de montage) peuvent avoir des fichiers qui se chevauchent : dans ce cas, le fichier le plus proche dans le chemin est sélectionné, et les autres fichiers ne sont pas accessibles à l'application. Cela permet d'utiliser des archives pour remplacer des versions antérieures ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un endroit spécifique de l'arborescence des fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargés qui pourraient écraser les données de l'application ou s'écraser mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce à quoi on s'attend avec le concept familier de « montage » Unix. De plus, plusieurs archives peuvent être montées au même endroit, ou les points de montage et les contenus des archives peuvent se chevaucher... le mécanisme d'interpolation continue de fonctionner ainsi.

Il est autorisé de spécifier un lien symbolique vers une archive ou un répertoire, indépendamment de l'état de PHYSFS_permitSymbolicLinks(). La fonction ne se concentre que sur les liens symboliques à l'intérieur du répertoire ou de l'archive monté(e).

Paramètres

newDir Le répertoire ou l'archive à ajouter au chemin, en notation dépendant de la plateforme.
mountPoint L'emplacement dans l'arborescence interpolée où cette archive sera montée, en notation indépendante. NULL ou «  » équivaut à « / ».
appendToPath Non nul pour ajouter à la fin du chemin, zéro pour ajouter au début.

Retourne

Non nul si ajouté au chemin, zéro en cas d'erreur (archive invalide, répertoire introuvable, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

L'utilisation normale des archives peut effectuer de nombreuses recherches en arrière-plan. En tant que tel, vous pourriez trouver l'utilisation normale des archives extrêmement pénible si elles sont montées de cette manière. Prévoyez en conséquence : si vous avez, par exemple, un fichier .zip auto-extractible, et que vous voulez monter quelque chose à l'intérieur, compressez le contenu de l'archive interne et assurez-vous que le fichier .zip externe ne compresse pas l'archive interne.

Cette poignée contient toutes les données de l'archive et est utilisée à la place d'un vrai fichier dans le système de fichiers physique. Le PHYSFS_File peut être basé sur un vrai fichier dans le système de fichiers physique, mais ce n'est pas nécessairement le cas. void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné au sandboxing du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait très bien avoir une raison légitime de configurer un lien symbolique, donc sauf si vous estimez qu'il y a un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lorsque l'on traite des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire que lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés via cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

Elle renverra quelle chaîne est "supérieure à" l'autre, mais vous devez garder à l'esprit que cela ne signifie pas nécessairement grand-chose : 'a' peut être "inférieur à" 'b', mais un kuten japonais n'a pas de relation alphabétique significative avec un lambda grec, mais pouvoir attribuer une valeur fiable permet des algorithmes de tri. Dans la plupart des cas, la valeur renvoyée sera considérée comme "égale" ou "inégale".

Comme avec stricmp, elle s'attend à ce que les deux chaînes soient terminées par un caractère nul.

Paramètres

str1 Première chaîne à comparer.
str2 Deuxième chaîne à comparer.

Retourne

-1 si str1 est "inférieure à" str2, 1 si elle est "supérieure à", 0 si elles sont égales.

Convertit une chaîne UTF-8 en une chaîne UCS-2.

Attention

Vous devriez presque certainement utiliser PHYSFS_utf8ToUtf16(), qui est devenu disponible dans PhysicsFS 2.1, à moins que vous ne sachiez ce que vous faites.

Cette fonction ne signalera pas d'erreur s'il y a des séquences UTF-8 invalides dans la source. Elle les remplacera par un caractère '?' et continuera.

void PHYSFS_utf8ToUtf16(const char *src, PHYSFS_uint16 *dst, PHYSFS_uint64 len)

Convertit une chaîne UTF-8 en une chaîne UTF-16.

Attention

Cette fonction ne signalera pas d'erreur s'il y a des séquences UTF-8 invalides dans la chaîne source. Elles seront remplacées par un caractère '?' et la fonction continuera.

Les chaînes UTF-16 utilisent 16 bits par caractère (sauf pour certains caractères, qui utilisent 32 bits) : TCHAR sous Windows, lors de la compilation avec le support Unicode. Les versions modernes de Windows utilisent UTF-16. Les versions de Windows antérieures à 2000 utilisaient TCHAR, mais ne géraient que l'UCS-2. src Chaîne source terminée par un caractère nul au format UTF-8.
dst Tampon pour stocker la chaîne UTF-16 convertie.
