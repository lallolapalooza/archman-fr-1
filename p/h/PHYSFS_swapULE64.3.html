#define PHYSFS_file PHYSFS_File

Define de compatibilité API 1.0. PHYSFS_file est identique à PHYSFS_File. Ce #define est là pour la compatibilité ascendante avec l'API 1.0, qui avait une convention de capitalisation incohérente dans ce cas. Le nouveau code doit utiliser PHYSFS_File, car ce #define pourrait disparaître un jour.

#define PHYSFS_VERSION

Indique la version de la bibliothèque contre laquelle vous avez compilé. Ceci est déterminé par l'en-tête que le compilateur utilise. Notez que si vous avez lié dynamiquement la bibliothèque, vous pourriez avoir une version légèrement plus récente ou plus ancienne à l'exécution. Cette version peut être déterminée avec PHYSFS_getLinkedVersion(), qui, contrairement à PHYSFS_VERSION, n'est pas une macro.

typedef PHYSFS_EnumerateCallbackResult(* physfs_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Valeurs de retour possibles de PHYSFS_EnumerateCallback. Signature de fonction pour les rappels qui énumèrent et retournent des résultats.

Ces valeurs dictent si un rappel d'énumération doit continuer à être déclenché ou s'arrêter (et pourquoi il s'arrête).

PHYSFS_EnumerateCallback

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du rappel : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez indiquer à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, transmis par l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, transmis dans le rappel pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport aux autres rappels qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenez une liste de fichiers d'un répertoire dans un chemin de recherche, en utilisant une fonction de rappel définie par l'utilisateur, avec des rapports d'erreurs. En interne, PHYSFS_enumerateFiles() n'appelle que cette fonction, puis construit une liste avant de la renvoyer à l'application, donc la fonctionnalité est identique sauf la manière dont les informations sont présentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas un tableau. Elle appelle plutôt une fonction spécifiée par l'application une fois par élément dans le chemin de recherche :

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // Donne-moi plus de données, s'il te plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments transmis à la fonction de rappel ne sont pas garantis dans un ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un tri alphabétique. Cette forme signale ce qui est trouvé dans chaque archive avant de passer à la suivante. Même au sein d'une seule archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout tri que vous trouverez dans ces callbacks est purement le fait du hasard. Ne vous y fiez pas. Comme elle parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers en double.

Cette API et les callbacks eux-mêmes peuvent signaler des erreurs. Avant cette API, les callbacks devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'un élément spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), nous ne pouvions pas le signaler à l'application, elle aurait simplement dû sauter des éléments ou arrêter complètement l'énumération, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être assuré d'avoir obtenu un ensemble complet de données, et s'il veut arrêter l'énumération plus tôt, son callback a le contrôle. Voir la documentation de PHYSFS_EnumerateCallback pour plus de détails sur le comportement attendu de votre callback.

Paramètres

dir Le répertoire, dans une notation indépendante du système d'exploitation, à énumérer.
c La fonction de rappel pour notifier les éléments du chemin de recherche.
d Les données définies par l'application transmises au callback. Peut être NULL.

Retourne

Non zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le callback renvoie PHYSFS_ENUM_STOP pour s'arrêter tôt, cela est considéré comme un succès. Les callbacks renvoyant PHYSFS_ENUM_ERROR feront que cette fonction renverra zéro et définira le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtenez une liste de fichiers d'un répertoire dans un chemin de recherche.

Avertissement

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction renvoyait autant d'éléments que possible en cas d'échec (erreur mémoire, erreur d'E/S disque, etc.). Comme cela empêchait les applications de distinguer un succès complet d'un échec partiel, et étant donné que la fonction pouvait toujours renvoyer NULL pour signaler des échecs catastrophiques, dans PhysicsFS 2.1 cette politique a changé : elle renverra une liste de résultats complets ou renverra NULL en cas d'échec de tout type, afin que nous puissions garantir que l'énumération a été effectuée et qu'il n'y a pas de lacunes dans vos résultats.

Les répertoires correspondants sont interpolés. C'est-à-dire que si "C:\mydir" se trouve dans le chemin de recherche et contient un répertoire "savegames" qui contient "x.sav", "y.sav" et "z.sav", et qu'il y a aussi un "C:\userdir" dans le chemin de recherche qui a un sous-répertoire "savegames" avec "w.sav", alors le code suivant :

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi
N'hésitez pas à trier la liste comme bon vous semble. Cependant, les données renvoyées ne contiendront jamais de doublons et seront toujours triées par ordre alphabétique (ou plutôt, sensible à la casse Unicode) pour vous.
N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur renvoyée par cette fonction lorsque vous avez terminé.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archivés contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, celui-ci sera transparentement ouvert vers le fichier auquel il se réfère.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous mener en dehors des chemins de lecture et d'écriture, compromettant la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Notez que cela est davantage destiné au sandboxing d'un langage de script, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas le désactiver à moins de ressentir une menace spécifique.

Les liens symboliques ne seront explicitement visibles que lorsque vous travaillez avec des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne seront jamais visibles pour vérification.

Note : PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. S'il n'est pas autorisé par cette fonction, PHYSFS_stat() ignorera le lien symbolique et traitera la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nulle pour permettre les liens symboliques, zéro pour désactiver le lien.

int PHYSFS_setRoot(const char * archive, const char * subdir)

Faire d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de restreindre les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt, monté sur /a, et que vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer la racine d'une archive à tout moment, modifiant l'arborescence de fichiers interpolée (selon où les chemins changent, une archive différente peut fournir divers fichiers). Si vous définissez la racine sur NULL ou "/", l'archive sera traitée comme si aucune racine spéciale n'était définie (comme si l'archive était simplement montée normalement).

La définition d'une nouvelle racine n'est pas limitée aux archives dans le chemin de recherche ; vous pouvez également en définir une sur le répertoire d'écriture, ce qui pourrait être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez donc pas changer le répertoire d'écriture pour le moment.

Il n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme racine d'une archive ; cependant, aucun fichier ne sera visible dans ce cas. Si les répertoires manquants finissent par être créés (un mkdir vers le système de fichiers physique, etc.), cela se reflétera dans l'arbre interpolé.

archive répertoire/archive sur lequel changer la racine.
subdir nouveau sous-répertoire à définir comme racine de cette archive.

non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

Comparaison insensible à la casse de deux chaînes UCS-4. Ceci est un remplacement de strcasecmp/stricmp qui attend que les deux chaînes soient en encodage UCS-4 (aka UTF-32). Il effectuera un "repliement de casse" pour déterminer si les points de code Unicode dans les chaînes correspondent.

Il indiquera quelle chaîne est "plus grande que" l'autre, mais soyez conscient que cela ne signifie pas nécessairement quelque chose : 'a' peut être "plus petit que" 'b', mais un kuten japonais n'a pas de relation alphabétique significative avec un lambda grec, mais pouvoir attribuer une "valeur" fiable rend les algorithmes de tri possibles, sinon entièrement sensés.
