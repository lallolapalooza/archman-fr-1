int PHYSFS_caseFold(const PHYSFS_uint32 from, PHYSFS_uint32 *to)

"Fold" a Unicode codepoint to a lowercase equivalent. (This is for limited, hardcore use. If you don't immediately see a need for it, you can probably ignore this forever.)

This will convert a Unicode codepoint into its lowercase equivalent. Bogus codepoints and codepoints without a lowercase equivalent will be returned unconverted.

Note that you might get multiple codepoints in return! The German Eszett, for example, will fold down to two lowercase latin 's' codepoints. The theory is that if you fold two strings, one with an Eszett and one with "SS" down, they will match.

Warning

Anyone that is a student of Unicode knows about the "Turkish I" problem. This API does not handle it. Assume this one letter in all of Unicode will definitely fold sort of incorrectly. If you don't know what this is about, you can probably ignore this problem for most of the planet, but perfection is impossible.

Parameters

from The codepoint to fold.
to Buffer to store the folded codepoint values into. This should point to space for at least 3 PHYSFS_uint32 slots.

Returns

The number of codepoints the folding produced. Between 1 and 3.

int PHYSFS_deinit(void)

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). It is usually best to close all write handles yourself before calling this function, so that you can gracefully handle a specific failure.

Once successfully deinitialized, PHYSFS_init() can be called again to restart the subsystem. All default API states are restored at this point, with the exception of any custom allocator you might have specified, which survives between initializations.

Returns

nonzero on success, zero on error. Specifics of the error can be gleaned from PHYSFS_getLastError(). If failure, state of PhysFS is undefined, and probably badly screwed up.

int PHYSFS_delete(const char *filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

Chances are, the bits that make up the file still exist, they are just made available to be written over at a later point. Don't consider this a security method or anything. :)

Parameters

filename Filename to delete.

Returns

nonzero on success, zero on error. Use PHYSFS_getLastErrorCode() to obtain the specific error.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers d'un répertoire du chemin de recherche, en utilisant un rappel défini par l'application, avec rapport d'erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique sauf pour la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons obtenu [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/chemin/quelconque", printDir, NULL);

Les éléments envoyés au rappel ne sont garantis dans aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme rapporte tout ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel elle découvrira les données. Tout tri que vous trouverez dans ces rappels est purement un hasard. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération carrément, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble de données complet, et son rappel a le contrôle s'il veut que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur la manière dont votre rappel doit se comporter.

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées au rappel. Peut être NULL.

Returns

Différent de zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel retourne PHYSFS_ENUM_STOP pour arrêter tôt, cela sera considéré comme un succès. Les rappels retournant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

Ajouter un répertoire ou un fichier au chemin de recherche. S'il s'agit d'un doublon, l'élément n'est pas ajouté à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter le même fichier à deux points de montage différents : la vérification des doublons se fait par rapport au fichier et non par rapport au point de montage.

Lors du montage d'un répertoire, celui-ci est ajouté à un système de fichiers virtuel... tous les fichiers de tous les répertoires montés sont interpolés en une seule arborescence de répertoires. Deux répertoires montés au même endroit (ou un répertoire avec des fichiers qui chevauchent un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers ne sont pas accessibles à l'application. Cela permet d'utiliser des répertoires pour remplacer des versions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des répertoires à un endroit précis dans l'arborescence des fichiers et empêcher le chevauchement ; ceci est utile pour les modes téléchargeables qui peuvent s'imposer sur les données de l'application ou sur eux-mêmes.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce à quoi on s'attend dans le concept Unix de « montage » pour les utilisateurs familiers. Ajoute une archive, contenue dans un descripteur PHYSFS_File, au chemin de recherche.

Attention

À moins d'avoir un besoin spécial de bas niveau, vous devriez utiliser PHYSFS_mount() à la place de cette fonction.

Les archives dans des archives peuvent être très lentes ! Bien qu'un PHYSFS_File puisse effectuer une recherche même lorsque les données sont compressées, il peut le faire en revenant au début et en décompressant tout ce qui précède le point de recherche. L'utilisation normale d'archives peut effectuer de nombreuses recherches en arrière-plan. Par conséquent, vous pourriez trouver l'utilisation normale d'archives extrêmement pénible si elles sont montées de cette manière. Prévoyez en conséquence : si vous avez, par exemple, un fichier .zip auto-extractible et que vous souhaitez monter quelque chose à l'intérieur, compressez le contenu de l'archive interne et assurez-vous que le fichier .zip externe ne compresse pas également l'archive interne.

Cette fonction opère de la même manière que PHYSFS_mount(), mais prend un descripteur PHYSFS_File au lieu d'un nom de chemin. Le PHYSFS_File peut être basé sur un fichier réel dans le système de fichiers physique, mais ce n'est pas nécessairement le cas. void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous amener en dehors des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela concerne davantage le sandboxing du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait très bien avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers dans la notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après l'appel à PHYSFS_init(), et elle est désactivée par défaut.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Hace un subdirectorio de un archivo su directorio raíz. Esto permite que puedas acotar los archivos accesibles en un archivo específico. Por ejemplo, si tienes x.zip con un archivo en y/z.txt montado a /a, si llamas a PHYSFS_setRoot("x.zip", "/y"), entonces la llamada a PHYSFS_openRead("/a/z.txt") será exitosa.

Puedes cambiar la raíz de un archivo en cualquier momento, alterando el árbol de archivos interpolado (dependiendo de dónde se desplacen las rutas, un archivo diferente podría proporcionar diversos archivos). Si estableces la raíz en NULL o "/", el archivo se tratará como si no hubiera raíz especial (como si el archivo fuera montado normalmente).

Cambiar la raíz solo afecta las operaciones futuras en rutas de archivos; un archivo que se abrió desde una ruta que cambió debido a un setRoot no será afectado.

Establecer una nueva raíz no está limitado a archivos en el directorio de búsqueda; puedes establecer una en el directorio de escritura, lo cual podría ser útil si tienes archivos abiertos para escribir y no puedes cambiar el directorio de escritura en este momento.

No es un error establecer un subdirectorio que no exista como raíz de un archivo, aunque no se vean archivos en ese caso. Si los directorios que faltan se crean (una mkdir en el sistema de archivos físico, etc), este se reflejará en el árbol interpolado.

Parámetros

archive directorio/archivo en el cual cambiar la raíz.
subdir subdirectorio nuevo que se convertirá en la raíz de este archivo.

Retorno

no cero si es exitoso, cero en error. Usa PHYSFS_getLastErrorCode() para obtener el error específico.
