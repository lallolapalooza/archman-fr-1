int PHYSFS_deinit(void)

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). int PHYSFS_delete(const char *filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

Chances are, the bits that make up the file still exist, they are just made available to be written over at a later point. Don't consider this a security method or anything. :)

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers à partir d'un répertoire d'un chemin de recherche, en utilisant un rappel défini par l'utilisateur, avec des erreurs rapportées. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de la renvoyer à l'application, de sorte que la fonctionnalité est identique, sauf que les informations sont présentées différemment à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois pour chaque élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // Donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés au rappel ne sont pas garantis d'être dans un ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un ordre alphabétique. Cette forme signale ce qui est trouvé dans chaque archive avant de passer à la suivante. Même dans une archive, nous ne pouvons pas garantir l'ordre dans lequel les données sont découvertes. Tout tri que vous trouvez dans ces rappels est purement de la chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers en double.

Cette API et les rappels eux-mêmes peuvent signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'un type spécifique et voulaient s'arrêter là, ou s'ils avaient une erreur grave et ne pouvaient en alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application, il devait simplement sauter des éléments ou cesser l'énumération, et l'appelant ne saurait pas qu'il avait perdu des données en cours de route.

Maintenant, l'appelant peut être assuré d'obtenir un ensemble complet de données, et son rappel a le contrôle s'il veut arrêter l'énumération plus tôt. Consultez la documentation de PHYSFS_EnumerateCallback pour connaître les détails sur la façon dont votre rappel doit se comporter.

Paramètres

dir Répertoire, en notation indépendante du système, à énumérer.
c Fonction de rappel pour notifier les éléments de chemin.
d Données définies par l'application passées au rappel. Peut être NULL.

Valeur de retour

non-zéro en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel renvoie PHYSFS_ENUM_STOP pour arrêter tôt, cela est considéré comme un succès. Les rappels renvoyant PHYSFS_ENUM_ERROR feront que cette fonction renverra zéro et définira le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtenir une liste de fichiers à partir d'un répertoire d'un chemin de recherche.

Avertissement

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction renvoyait autant d'éléments que possible en cas de condition d'échec (erreur de mémoire, erreur d'E/S disque, etc.). Par conséquent, les applications ne pouvaient pas faire la distinction entre un succès complet et un échec partiel, et la fonction pouvait toujours renvoyer NULL pour signaler des échecs catastrophiques. Dans PhysicsFS 2.1, la politique de cette fonction a changé : elle renverra une liste complète de résultats ou NULL en cas de problème, afin que nous puissions garantir que l'énumération s'est terminée correctement et qu'il n'y a pas de lacunes dans vos résultats.

Les répertoires correspondants sont interpolés. C'est-à-dire que si « C:\mydir » se trouve dans le chemin de recherche et contient un répertoire « savegames » qui contient « x.sav », « y.sav » et « z.sav », et qu'il existe également un « C:\userdir » dans le chemin de recherche qui possède un sous-répertoire « savegames » avec « w.sav », alors le code suivant :

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi
N'hésitez pas à trier la liste comme vous le souhaitez. Cependant, les données renvoyées ne contiendront toujours aucun doublon et seront toujours triées par ordre alphabétique (plutôt : ordre Unicode sensible à la casse) pour vous.
N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur renvoyée par cette fonction lorsque vous avez terminé.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers qui chevauchent un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient écraser les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce à quoi les personnes familières avec le concept Unix de "montage" pourraient s'attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

Spécifier un lien symbolique vers une archive ou un répertoire est autorisé ici, quelle que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que des liens symboliques à l'intérieur du répertoire monté ou de l'archive.

une valeur non nulle si ajouté au chemin, zéro en cas d'échec (archive invalide, répertoire manquant, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné au cloisonnement du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers en notation indépendante de la plateforme. Autrement dit, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission de lien symbolique peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Fait d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de vous rapprocher des fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier à y/z.txt monté sur /a, si vous appelez PHYSFS_setRoot() avec "x.zip" et "/y", alors l'appel à PHYSFS_openRead() avec "/a/z.txt" réussira.

Vous pouvez changer le répertoire racine d'une archive à tout moment, modifiant ainsi l'arborescence de fichiers interpolée (selon l'endroit où les chemins se déplacent, une archive différente pourrait fournir des fichiers différents). Si vous définissez le répertoire racine à NULL ou "/", l'archive sera traitée comme si elle n'avait pas été spécialement définie (comme si elle était montée normalement).

Définir un nouveau répertoire racine n'est pas limité aux archives dans le chemin de recherche ; vous pouvez également le définir dans le répertoire d'écriture, ce qui pourrait être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez pas changer le répertoire d'écriture pour le moment.

Ce n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme répertoire racine d'une archive ; cependant, aucun fichier ne sera affiché dans ce cas. archive Répertoire/archive dans lequel changer le répertoire racine.
subdir Nouveau sous-répertoire à faire le répertoire racine de cette archive.

non-zéro en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

Pour vous assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon dont la taille est le double de celle du tampon source. UTF-8 développe les points de code latin1 supérieurs à 127 de 1 à 2 octets, la chaîne peut donc dans certains cas s'allonger.

Veuillez noter que nous ne fournissons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer la plupart des points de code Unicode. C'est un encodage hérité ; vous devriez toujours vous en éloigner.
