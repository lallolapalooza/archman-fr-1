Signature de fonctions pour les callbacks qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez plutôt PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; cela vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, une entrée par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire de toutes les chaînes.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournent des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes par la suite.

Notez que l'ordre des données promis dans les versions de liste n'est pas nécessairement le même dans les versions de callback. Consultez la documentation des API spécifiques, mais les chaînes ne seront pas triées comme vous vous y attendez et vous pourriez obtenir des chaînes en double.

Paramètres

data pointeur vers des données définies par l'utilisateur, passé via l'API qui a finalement appelé le callback.
origdir chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire pour lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname nom du fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport à d'autres callbacks qui ont été appelés et ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données seront découvertes. *Tout tri que vous trouverez dans ces rappels est purement dû au hasard. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble de données complet, et son rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement de votre rappel.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. PHYSFS_mountIo(3)

Add an archive, contained in a PHYSFS_File handle, to the search path.

Warning

Unless you have some special, low-level need, you should be using PHYSFS_mount() instead of this.

Archives-in-archives may be very slow! While a PHYSFS_File can seek even when the data is compressed, it may do so by rewinding to the start and decompressing everything before the seek point. Normal archive usage may do a lot of seeking behind the scenes. As such, you might find normal archive usage extremely painful if mounted this way. Plan accordingly: if you, say, have a self-extracting .zip file, and want to mount something in it, compress the contents of the inner archive and make sure the outer .zip file doesn't compress the inner archive too.

This function operates just like PHYSFS_mount(), but takes a PHYSFS_File handle instead of a pathname. This handle contains all the data of the archive, and is used instead of a real file in the physical filesystem. The PHYSFS_File may be backed by a real file in the physical filesystem, but isn't necessarily. The most popular use for this is likely to mount archives stored inside other archives.

(newDir) must be a unique string to identify this archive. It is used to optimize archiver selection (if you name it XXXXX.zip, we might try the ZIP archiver first, for example, or directly choose an archiver that can only trust the data is valid by filename extension). It doesn't need to refer to a real file at all. If the filename extension isn't helpful, the system will try every archiver until one works or none of them do. This filename must be unique, as the system won't allow you to have two archives with the same name.

(file) must remain until the archive is unmounted. When the archive is unmounted, the system will call PHYSFS_close(file). If you need this handle to survive, you will have to wrap this in a PHYSFS_Io and use PHYSFS_mountIo() instead.

If this function fails, PHYSFS_close(file) is not called.

Parameters

file The PHYSFS_File handle containing archive data.
newDir Filename that can represent this stream.
mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier vers lequel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné au sandboxing du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait très bien avoir une raison légitime de créer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser, vous devriez les permettre.

Les liens symboliques ne sont explicitement vérifiés que lorsque vous traitez des noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

L'autorisation des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser la liaison.

Establece el tamaño del buffer para un handle de archivo dado.

Un tamaño de buffer de cero desactiva el buffering para el archivo dado, lo que significa que todas las operaciones de lectura y escritura se realizarán directamente en el archivo subyacente. Esto tiene implicaciones de rendimiento, ya que puede aumentar el número de llamadas al sistema.

Los handles de archivo de PhysicsFS no tienen búfer por defecto.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Hace de un subdirectorio de un archivo tu directorio raíz. Esto te permite restringir los archivos accesibles dentro de un archivo específico. Por ejemplo, si tienes x.zip con un archivo en y/z.txt montado en /a, si llamas a PHYSFS_setRoot("x.zip", "/y"), la llamada a PHYSFS_openRead("/a/z.txt") tendrá éxito.

Puedes cambiar la raíz de un archivo en cualquier momento, alterando así el árbol de archivos interpolado (dependiendo de dónde se muevan las rutas, un archivo diferente puede proporcionar archivos diferentes). Si estableces la raíz a NULL o "/", el archivo se tratará como si no tuviera raíz especial (como si el archivo se montara normalmente).

Cambiar la raíz solo afecta a las operaciones futuras sobre las rutas de los archivos; un archivo que se abrió a partir de una ruta que cambió debido a un setRoot no se verá afectado.

Establecer una nueva raíz no se limita a los archivos en el directorio de búsqueda; puedes establecer una en el directorio de escritura, lo que puede ser útil si tienes archivos abiertos para escritura y no puedes cambiar el directorio de escritura en este momento.

No es un error establecer un subdirectorio que no existe como raíz de un archivo; sin embargo, en ese caso, no se verán archivos. Si los directorios faltantes se crean eventualmente (una mkdir en el sistema de archivos físico, etc.), esto se reflejará en el árbol interpolado.

Parámetros

archive directorio/archivo en el cual cambiar la raíz.
subdir nuevo subdirectorio para hacer la raíz de este archivo.

Retorna

distinto de cero en caso de éxito, cero en caso de error. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

Paramètres

str1 Première chaîne à comparer.
str2 Deuxième chaîne à comparer.

Retour

-1 si str1 est "inférieur à" str2, 1 s'il est "supérieur à", 0 s'ils sont égaux.

Remarque : nous n'offrons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer la plupart des codes Unicode. C'est un code ancien ; vous devriez toujours vous convertir à partir de celui-ci.

src Chaîne Latin1 terminée par un caractère nul.
dst Tampon pour stocker la chaîne UTF-8 convertie.
len Taille en octets du tampon de destination.

Warning

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. If you aren't sure, you should be using UTF-16 at this point on Windows.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
len Size, in bytes, of destination buffer.

NAME

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 — écriture de valeurs d'entiers de taille fixe dans un fichier

SYNOPSIS

int PHYSFS_writeUBE16(PHYSFS_File *file, PHYSFS_uint16 val);
int PHYSFS_writeUBE32(PHYSFS_File *file, PHYSFS_uint32 val);
int PHYSFS_writeUBE64(PHYSFS_File *file, PHYSFS_uint64 val);

int PHYSFS_writeULE32(PHYSFS_File *file, PHYSFS_uint32 val);

DESCRIPTION

Ces fonctions écrivent des entiers non signés dans un fichier, en les convertissant dans l'ordre des octets spécifié.

Les fonctions « UBE » écrivent la valeur sous forme d'entier big-endian, tandis que les fonctions « ULE » écrivent la valeur sous forme d'entier little-endian. Les suffixes « 16 », « 32 » et « 64 » indiquent la taille de l'entier en bits.

Ces fonctions sont des fonctions de commodité. Elles convertissent une valeur entière de l'ordre des octets natif de la plateforme vers l'ordre des octets spécifié (big-endian ou little-endian) avant de l'écrire dans le fichier.
