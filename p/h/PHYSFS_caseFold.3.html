DESCRIPTION

This file contains the public API for the PhysicsFS library. It defines all the data structures, function prototypes, and constants needed to use PhysicsFS in your application.

The functions are grouped by their functionality:

Byte Swapping
Functions for swapping byte order for different integer sizes (16, 32, 64 bits) between little-endian and big-endian formats and the platform's native byte order.
Reading/Writing Integers
Functions for reading and writing integer values (16, 32, 64 bits) in specific endian formats (little-endian and big-endian) from/to PhysicsFS file handles.
Initialization and State
Functions to check if PhysicsFS is initialized, to set custom memory allocators, and to query or modify settings like symbolic link permissions.
Mounting and Search Path
Functions to add archives or directories to the search path (mount them), retrieve information about mounted directories, and remove them.
File Enumeration and Callback
Functions to enumerate files within directories using application-defined callbacks.
String Conversion and Manipulation
Functions for converting strings between different character encodings (UCS-4, UCS-2, UTF-8, Latin-1) and for performing case-insensitive string comparisons.
Archiver Registration
Functions to register and deregister custom archive format handlers.
File I/O
Functions for reading and writing raw bytes to and from PhysicsFS file handles, and for mounting archives from various sources like I/O interfaces, memory buffers, or existing file handles.
Error Handling
Functions to retrieve the last error code, get a human-readable error description, and set the current thread's error code.
Directory Management
Functions to get platform-specific preference directories and to set the root directory within an archive.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature des fonctions de rappel qui énumèrent les fichiers.

Note

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; il offre plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, une entrée par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire des chaînes.

Ces rappels sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui renvoient des listes qui doivent être libérées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin de pré-allouer une liste complète et toutes les chaînes.

Vous devez être conscient que les promesses de tri des données dans les versions de liste ne sont pas nécessairement les mêmes dans les versions de rappel. Vérifiez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

enum PHYSFS_ErrorCode

Valeurs représentant des causes spécifiques d'échec. La plupart du temps, vous ne devriez vous soucier que de savoir si une opération a échoué ou non, mais il peut y avoir des occasions où vous prévoyez de gérer gracieusement une situation d'échec spécifique, nous offrons donc des codes d'erreur spécifiques.

La plupart de ces erreurs sont un peu vagues, et la plupart ne sont pas des choses que vous pouvez corriger... s'il y a une erreur de permission, par exemple, la seule chose que vous pouvez faire est de transmettre cette information à l'utilisateur et de laisser l'utilisateur trouver comment la gérer. Dans la plupart de ces cas, votre programme ne devrait s'inquiéter que du fait qu'il n'a pas atteint ses objectifs, et ne pas se soucier spécifiquement du pourquoi.

Un répertoire doit être vide avant que cet appel ne puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, et non ce vers quoi il pointe, que vous ayez ou non activé "permitSymLinks".

Il y a de fortes chances que les bits qui composent le fichier existent toujours, ils sont simplement rendus disponibles pour être écrasés plus tard. Ne considérez pas cela comme une méthode de sécurité ou quoi que ce soit. :)

filename Nom du fichier à supprimer.

const char *physFS_getPrefDir (const char * org, const char * app)

Obtenir le chemin du répertoire spécifique pour écrire des fichiers, utilisé par l'utilisateur et l'application. Fonction d'aide.

Obtenez le "répertoire de préférences". C'est là que les utilisateurs peuvent écrire des fichiers personnels (préférences et sauvegardes de jeux, etc.) spécifiques à votre application. Ce répertoire est unique par utilisateur et par application.

Cette fonction détermine l'emplacement approprié sur le système natif, crée le répertoire si nécessaire et renvoie une chaîne en notation système, appropriée pour être passée à PHYSFS_setWriteDir().

Sous Linux, cela pourrait ressembler à ceci : "/home/bob/.local/share/My Program Name"

Sous Mac OS X, cela pourrait ressembler à ceci : "/Users/bob/Library/Application Support/My Program Name"

(etc.)

Vous devriez utiliser le répertoire de préférences pour votre chemin d'écriture, et également le placer près du début de votre liste de recherche. Les anciennes versions de PhysicsFS n'offraient que PHYSFS_getUserDir() et laissaient les utilisateurs trouver où les fichiers devaient se trouver sous cet arbre. Ceci trouve l'emplacement correct pour toute plateforme, qui non seulement varie entre les systèmes d'exploitation, mais aussi entre les versions du même système d'exploitation.

  • Utilisez la même chaîne (y compris la casse) pour toutes les applications qui utilisent cette fonction.
  • Utilisez une chaîne unique pour chaque application, en vous assurant qu'elle ne change pas pour une application une fois que vous l'avez décidée.
  • Les caractères Unicode sont valides, tant qu'ils sont encodés en UTF-8, mais...
  • ...n'utilisez que des lettres, des chiffres et des espaces. Évitez les caractères comme "Nom du jeu 2: La revanche du méchant !" ... "Nom du jeu 2" est suffisant.

Le pointeur renvoyé par cette fonction reste valide jusqu'à ce que vous l'appeliez à nouveau ou que vous appeliez PHYSFS_deinit(). Bien que ce ne soit pas rapide, vous devriez l'appeler une fois au démarrage et copier la chaîne si vous en avez besoin.

Vous devriez supposer que le chemin renvoyé par cette fonction est le seul endroit sûr pour écrire des fichiers (et que PHYSFS_getUserDir() et PHYSFS_getBaseDir(), bien qu'ils puissent être inscriptibles, ou même être les parents du chemin renvoyé, ne sont pas les bons endroits pour écrire).

Avertissement

À moins que vous n'ayez une raison très spécifique, vous devriez utiliser PHYSFS_mount() à la place.

Cette fonction opère exactement comme PHYSFS_mount(), mais elle prend un PHYSFS_Io au lieu d'un nom de fichier. Dans le système de fichiers sous-jacent, PHYSFS_mount() appelle cette fonction avec un PHYSFS_Io basé sur le système de fichiers physique.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous mener en dehors des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné au sandboxing du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne sentiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers dans la notation indépendante de la plateforme. C'est-à-dire que lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore, et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

Ceci vous permet de rediriger PhysicsFS pour utiliser vos propres routines d'allocation à la place. Vous ne pouvez appeler cette fonction qu'avant PHYSFS_init() ; si la bibliothèque est initialisée, elle rejettera vos tentatives de changer l'allocateur en cours de route. Vous pouvez appeler cette fonction après PHYSFS_deinit() si vous êtes prêt à arrêter la bibliothèque et à la redémarrer avec un nouvel allocateur ; ceci est une opération sûre et prise en charge. L'allocateur reste intact entre les appels de deinit/init. Si vous voulez revenir à l'allocateur par défaut de la plateforme, passez NULL ici.

Si vous ne savez pas immédiatement quoi faire avec cette fonction, vous pouvez l'ignorer sans risque.

Paramètres

allocator Structure contenant les points d'entrée de votre allocateur.

Retourne

zéro en cas d'échec, non-zéro en cas de succès. Cet appel échoue uniquement lorsqu'il est utilisé entre les appels à PHYSFS_init() et PHYSFS_deinit().

Cette fonction ne signalera pas d'erreur s'il y a des séquences invalides dans la chaîne source UTF-16. Elle les remplacera par un caractère '?' et continuera.

Les chaînes UTF-16 (également appelées UCS-2) sont 16 bits par caractère (à l'exception de certains caractères qui sont 32 bits) : TCHAR sous Windows lors de la compilation avec le support Unicode. Les versions modernes de Windows utilisent UTF-16. Les anciennes versions de Windows (avant 2000) utilisaient TCHAR, mais ne géraient que UCS-2. UTF-16 est UCS-2, à l'exception des caractères qui prennent 4 octets, qui ne peuvent pas du tout être représentés en UCS-2. Si vous n'êtes pas sûr, vous devriez utiliser UTF-16 sous Windows maintenant.

Pour assurer que le buffer de destination soit suffisamment grand pour la conversion, veuillez allouer un buffer de taille double par rapport au buffer source. L'UTF-8 n'utilise jamais plus de 32 bits par caractère, donc bien qu'il puisse réduire une chaîne UTF-16, il peut aussi l'étendre.

Les chaînes qui ne rentrent pas dans le buffer de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du buffer est de 0, cette fonction ne fait rien.

int PHYSFS_utf8stricmp (const char * str1, const char * str2)

Compare deux chaînes UTF-8 de manière insensible à la casse. C'est un remplacement pour strcasecmp/stricmp qui s'attend à ce que les deux chaînes soient encodées en UTF-8. Il effectuera un « pliage de casse » pour déterminer si les codes Unicode dans les chaînes correspondent.

Si les deux chaînes ne contiennent que des caractères ASCII bas, cela fera la bonne chose, car c'est également un UTF-8 valide. S'il y a des caractères ASCII hauts, cela ne fera pas ce que vous attendez !

Il indiquera quelle chaîne est « plus grande que » l'autre, mais gardez à l'esprit que cela ne signifie pas nécessairement quelque chose : 'a' peut être « plus petit que » 'b', mais un katakana japonais n'a aucune relation significative alphabétique avec un lambda grec, mais pouvoir assigner une valeur fiable permet aux algorithmes de tri de fonctionner, même s'ils ne sont pas entièrement rationnels. La plupart des cas devraient traiter la valeur renvoyée comme « égale » ou « non égale ».

Comme stricmp, celle-ci s'attend à ce que les deux chaînes soient terminées par un caractère nul.

Paramètres

str1 Première chaîne de comparaison.
str2 Seconde chaîne de comparaison.

Renvoie

-1 si str1 est « plus petit que » str2, 1 s'il est « plus grand que », 0 s'ils sont égaux.
