PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, à la différence qu'il peut retourner un résultat depuis le rappel : notamment : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; cela vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant originel, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire d'une chaîne.

Ces rappels sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions avec liste n'est pas nécessairement le cas dans les versions avec rappel. Vérifiez la documentation sur les API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé une énumération, passé dans le rappel pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être en ordre alphabétique par rapport aux autres rappels qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Signature de fonction pour les rappels qui rapportent des chaînes. Ceux-ci sont utilisés pour rapporter une liste de chaînes à un appelant originel, une chaîne par rappel. int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir una lista de archivos de la carpeta de un camino de búsqueda, usando un callback definido por la aplicación, con errores reportados. Internamente, PHYSFS_enumerateFiles() solo llama a esta función y luego construye una lista antes de devolver a la aplicación, así que la funcionalidad es idéntica, salvo cómo la información se presenta a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve un array. En cambio, llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSfs_ENUM_OK;  // me daría más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Los elementos enviados a la callback no están garantizados en ningún orden. No se realiza ningún ordenamiento en este nivel, y si lo necesitas, deberías usar PHYSFS_enumerateFiles(), que garantiza el orden alfabético. Esta forma reporta lo que se encuentra en cada archivo antes de pasar a la siguiente. Even within one archive, we can't guarantee the order in which data is discovered. Cualquier ordenamiento que encuentres en estos callbacks es pura suerte. No dejes de confiar en ello. Como esta camina por toda la lista de archivos, podrías recibir nombres de archivos duplicados.

Esta API y los callbacks mismos son capaces de reportar errores. Antes de esta API, los callbacks tenían que aceptar cada elemento enumerado, incluso si solo buscaban un tipo específico y querían detenerse después de eso, o tenían un error serio y no podían alertar a nadie. Además, si PhysicsFS mismo tenía un problema (error de disco o algo así), no podría reportarlo al aplicación, simplemente pasaría a los items o detendría la enumeración, y el llamador no estaría seguro de haber perdido datos.

Ahora el llamador puede estar seguro de haber obtenido un conjunto de datos completo, y si lo desea, su callback controla si detiene la enumeración temprano. Ve el documentación de PHYSFS_EnumerateCallback para detalles de cómo debe comportarse su callback.

Parámetros

dir Carpeta a enumerar en notación de plataforma independiente.
c Función de callback para notificar sobre elementos de la ruta.
d Datos definidos por la aplicación pasado a la callback. Puede ser NULL.

Devuelve

no cero si es exitoso, cero si hay un error. Usa PHYSFS_getLastErrorCode() para obtener el error específico. Si el callback devuelve PHYSFS_ENUM_STOP, esto se considera exitoso. Callbacks que devuelvan PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezca el código de error en PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtener una lista de archivos de la carpeta de un camino de búsqueda.

Advertencia

En versiones de PhysicsFS anteriores a 2.1, esta función devolvería tantos elementos como fuera posible en caso de falla (error de memoria, i/o de disco, etc). Como esto hacía que los aplicaciones no pudiesen diferenciar entre éxito completo y fracaso parcial, y que la función podía siempre devolver NULL para reportar fallos catastróficos, en PhysicsFS 2.1 esta política cambió: devolverá una lista completa de resultados o devolverá NULL en caso de cualquier fallo, por lo que podemos garantizar que la enumeración se completó y no tiene vacíos en sus resultados.

Las carpetas que coincidan se interpolan. Es decir, si "C:\mydir" está en la ruta de búsqueda y contiene una carpeta "savegames" que contiene "x.sav", "y.sav" y "z.sav", y hay también una carpeta "C:\userdir" en la ruta de búsqueda con una subcarpeta "savegames" que contiene "w.sav", entonces el siguiente código:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
resultará en:
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav].
Siente la libertad de ordenar la lista como quieras. Sin embargo, los datos devueltos siempre contendrán cero duplicados, y siempre estarán ordenados alfabéticamente (o más bien, sensible a mayúsculas y minúsculas Unicode) para ti.
No olvides llamar a PHYSFS_freeList() con el valor de retorno de esta función cuando hayas terminado con él.

dir carpeta a enumerar en notación de plataforma independiente.

Array de strings nulo-terminado de strings nulo-terminados, o NULL en caso de fallo.

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Obtenez le chemin spécifique à l'utilisateur et à l'application où les fichiers peuvent être écrits. Fonction d'assistance.

Obtenez le "répertoire de préférences". Il est destiné à être l'endroit où les utilisateurs peuvent écrire des fichiers personnels (préférences et sauvegardes de jeux, etc.) spécifiques à votre application. Ce répertoire est unique par utilisateur, par application.

Cette fonction décidera de l'emplacement approprié dans le système de fichiers natif, créera le répertoire si nécessaire, et retournera une chaîne en notation dépendante de la plateforme, adaptée pour être passée à PHYSFS_setWriteDir().

Sous Linux, cela pourrait ressembler à : "/home/bob/.local/share/My Program Name"

Sur Mac OS X, cela pourrait ressembler à : "/Users/bob/Library/Application Support/My Program Name"

(etc.)

Vous devriez probablement utiliser le répertoire de préférences pour votre répertoire d'écriture, et également le placer près du début de votre chemin de recherche. Ceci trouve l'emplacement correct pour n'importe quelle plateforme, qui change non seulement entre les systèmes d'exploitation, mais aussi entre les versions du même système d'exploitation.

  • Utilisez toujours une chaîne app unique pour chacune, et assurez-vous qu'elle ne change jamais pour une application une fois que vous l'avez décidée.

  • ...n'utilisez que des lettres, des chiffres et des espaces. Évitez la ponctuation comme "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" est suffisant.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés en un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers se chevauchant avec un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou les uns les autres, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept de "montage" Unix pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

La spécification d'un lien symbolique vers une archive ou un répertoire est autorisée ici, indépendamment de l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

Paramètres

newDir répertoire ou archive à ajouter au chemin, en notation dépendante de la plateforme.
mountPoint Emplacement dans l'arbre interpolé où cette archive sera "montée", en notation indépendante de la plateforme. NULL ou "" est équivalent à "/".
appendToPath non nul pour ajouter au chemin de recherche, zéro pour ajouter au début.

une valeur non nulle si ajouté au chemin, zéro en cas d'échec (archive invalide, répertoire manquant, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

Par conséquent, vous pourriez trouver l'utilisation normale d'archives extrêmement pénible si elles sont montées de cette manière. Prévoyez en conséquence : si vous avez, par exemple, un fichier .zip auto-extractible et que vous souhaitez monter quelque chose dedans, compressez le contenu de l'archive interne et assurez-vous que le fichier .zip externe ne compresse pas non plus l'archive interne.

void PHYSFS_permitSymbolicLinks (int allow)

Enables or disables following of symbolic links. Some physical and archive file systems contain files that are just pointers to other files. When opening a physical symbolic link, the system transparently opens the file it points to.

By default, PhysicsFS will check if a file is actually a symbolic link during open calls and fail if it is. Otherwise, the link might lead you outside of the read/write paths, compromising security.

If you wish to take that risk, call this function with a non-zero value. Note that this is mostly for sandboxing a scripting language in a program, in case untrusted scripts try to compromise the system. Generally, a user might have a legitimate reason to create a symbolic link, so you shouldn't disable them, unless you feel there is a specific danger.

Symbolic links will be explicitly skipped when handling filenames in a platform-independent notation. That is, when setting up your search and write paths, etc., symbolic links will never be followed.

Please note that PHYSFS_stat() will always check the specified path; if that path is a symbolic link, it will not follow it in any case. If symbolic links are disallowed via this function, PHYSFS_stat() will ignore them and treat the query as if the path didn't exist.

Symbolic link permission can be turned on or off at any time after you have called PHYSFS_init(), and it is off by default.

Parameters

allow non-zero to allow symbolic links, zero to disallow them.

Paramètres

str1 Première chaîne à comparer.
str2 Deuxième chaîne à comparer.

Retourne

-1 si str1 est "inférieur à" str2, 1 si "supérieur à", 0 si égal.
