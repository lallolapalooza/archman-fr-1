Documentation des macros

#define PHYSFS_VERSION_MAJOR

La version majeure de la bibliothèque que vous avez compilée.

#define PHYSFS_VERSION_MINOR

La version mineure de la bibliothèque que vous avez compilée.

#define PHYSFS_VERSION_PATCH

La version de correction de la bibliothèque que vous avez compilée.

#define PHYSFS_VERSION

La version complète de la bibliothèque que vous avez compilée.

Ceci est défini comme PHYSFS_VERSION_MAJOR.PHYSFS_VERSION_MINOR.PHYSFS_VERSION_PATCH. Par exemple, si vous avez compilé contre la version 2.0.1 de PhysicsFS, ceci sera défini comme 2.0.1.

Ce macro est utile pour vérifier la version de la bibliothèque qui a été utilisée pour compiler votre programme. Cela peut être important car différentes versions de la bibliothèque peuvent avoir des incompatibilités binaires. Lorsque vous reliez dynamiquement la bibliothèque, la version réelle de la bibliothèque au moment de l'exécution peut être légèrement différente. Cette version peut être obtenue avec PHYSFS_getLinkedVersion(), qui, contrairement à PHYSFS_VERSION, n'est pas une macro.

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat depuis le callback : à savoir : si vous cherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le callback.
origdir Une chaîne de caractères contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport aux autres callbacks qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent des fichiers.

Attention

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; cela vous donne plus de contrôle sur le processus.

Ils sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire d'une chaîne.

Ces callbacks sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes nécessitant d'être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes d'avance.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le cas dans les versions callback. Vérifiez la documentation sur les API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le callback.
origdir Une chaîne de caractères contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir una liste de fichiers d'un répertoire à partir d'un chemin de recherche, en utilisant une fonction de rappel définie par l'utilisateur, avec rapport d'erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de la retourner à l'application, donc la fonctionnalité est identique, mais la présentation des informations à l'application est différente.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'utilisateur une fois pour chaque élément du chemin de recherche :

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis dans aucun ordre spécifique. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit l'ordre alphabétique. Cette forme rapporte ce qui est découvert dans chaque fichier archivé avant de passer au suivant. Même à l'intérieur d'une archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout tri que vous trouverez dans ces rappels est purement le fruit du hasard. Ne vous y fiez pas. Comme cette fonction parcourt toute la liste des fichiers, vous pouvez recevoir des noms de fichiers en double.

Cette API et les fonctions de rappel elles-mêmes sont capables de signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même si elles ne cherchaient qu'un élément spécifique et voulaient s'arrêter après, ou si elles avaient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement sauter les éléments ou arrêter complètement l'énumération, et l'appelant ne saurait pas qu'il avait perdu des données en cours de route.

Désormais, l'appelant peut être assuré d'avoir obtenu un ensemble complet de données, et s'il veut arrêter l'énumération plus tôt, sa fonction de rappel a le contrôle. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement attendu de votre fonction de rappel.

non nul en cas de succès, nul en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. PHYSFS_Allocator

Structure defining custom memory allocation routines.

PhysicsFS provides a set of default memory allocation routines, but you can override these with your own routines by creating a PHYSFS_Allocator structure and passing it to PHYSFS_setAllocator. The structure looks like this:

typedef struct {
    void *(*Init) (void);
    void (*Destroy) (void *data);
    void *(*Malloc) (void *data, int size);
    void (*Free) (void *data, void *ptr);
    void *(*Realloc) (void *data, void *ptr, int size);
} PHYSfs_allocator;

Init: This is called once when PhysicsFS is initialized. It should return a pointer to a data structure that will be passed to the other functions, or NULL on failure.

Destroy: This is called once when PhysicsFS is deinitialized. It should free any memory allocated by Init.

Malloc: Called to allocate memory. Should behave like malloc(3). data is the pointer returned by Init, and size is the number of bytes to allocate.

Free: Called to free memory. Should behave like free(3). data is the pointer returned by Init, and ptr is the pointer to free.

Realloc: Called to reallocate memory. Should behave like realloc(3). data is the pointer returned by Init, ptr is the pointer to reallocate, and size is the new size in bytes.

The default allocators provided by PhysicsFS are simple wrappers around the C library's malloc, free, and realloc.

You can get a pointer to the currently used allocator by calling PHYSFS_getAllocator.

PHYSFS_getAllocator

Get a pointer to the current memory allocator.

This function returns a pointer to the `PHYSFS_Allocator` struct that PhysicsFS is currently using. This will either be the allocator that your application specified with `PHYSFS_setAllocator()`, or PhysicsFS's internal, default allocator if your application hasn't specified one yet. This can be useful for apps that want to access PhysicsFS's internal, default allocation routines, as well as for external code that wants to share the same allocator, even if the application specified their own.

This call is only valid between PHYSFS_init() and PHYSFS_deinit() calls; it will return NULL if the library isn't initialized. As we can't guarantee the state of the internal allocators unless the library is initialized, you shouldn't use any allocator returned here after a call to PHYSFS_deinit().

Do not call the returned allocator's Init() or Deinit() methods under any circumstances.

If you aren't immediately sure what to do with this function, you can safely ignore it altogether.

Returns

Current allocator, as set by PHYSFS_setAllocator(), or PhysicsFS's internal, default allocator if no application defined allocator is currently set. Will return NULL if the library is not initialized.

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Obtenir le chemin spécifique à l'utilisateur et à l'application où les fichiers peuvent être écrits. Fonction d'aide.

Obtenir le "répertoire de préférences". Il est destiné à être l'endroit où les utilisateurs peuvent écrire des fichiers personnels (préférences et sauvegardes de jeux, etc.) qui sont spécifiques à votre application. Ce répertoire est unique par utilisateur, par application.

Sous Linux, cela pourrait ressembler à : "/home/bob/.local/share/Mon Nom de Programme"

Sous Mac OS X, cela pourrait ressembler à : "/Users/bob/Library/Application Support/Mon Nom de Programme"

(etc.)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons est effectuée sur l'archive et non sur le point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés en un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers chevauchant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept de montage Unix pourraient attendre. Ajoute une archive, contenue dans un handle PHYSFS_File, au chemin de recherche.

Attention

À moins que vous n'ayez un besoin spécial de bas niveau, vous devriez utiliser PHYSFS_mount() à la place.

Les archives dans des archives peuvent être très lentes ! Bien qu'un PHYSFS_File puisse effectuer des recherches même lorsque les données sont compressées, il peut le faire en revenant au début et en décompressant tout avant le point de recherche. L'utilisation normale d'archive peut effectuer de nombreuses recherches en arrière-plan. Par conséquent, vous pourriez trouver l'utilisation normale d'archive extrêmement pénible si elle est montée de cette manière. Prévoyez en conséquence : si vous avez, par exemple, un fichier .zip auto-extractible et que vous souhaitez monter quelque chose à l'intérieur, compressez le contenu de l'archive interne et assurez-vous que le fichier .zip externe ne compresse pas l'archive interne.

Cette fonction opère comme PHYSFS_mount(), mais prend un handle PHYSFS_File au lieu d'un chemin. Ce handle contient toutes les données de l'archive et est utilisé à la place d'un fichier réel dans le système de fichiers physique. Le PHYSFS_File peut être basé sur un fichier réel dans le système de fichiers physique, mais ce n'est pas nécessairement le cas. L'utilisation la plus courante est probablement de monter des archives stockées à l'intérieur d'autres archives.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et d'archives contiennent des fichiers qui ne sont que des références à d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, celui-ci ouvrira de manière transparente le fichier auquel il fait référence.

Par défaut, PhysicsFS vérifiera si un fichier est effectivement un lien symbolique lors des appels open et échouera si c'est le cas. Sinon, le lien pourrait vous faire sortir du chemin de lecture et d'écriture, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Notez que cela est davantage destiné au sandboxing d'un langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur peut avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas le désactiver, à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser.

Les liens symboliques ne sont vérifiés que lorsque des noms de fichiers sont gérés en notation indépendante du système d'exploitation. C'est-à-dire lorsque vous configurez vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si vous n'autorisez pas les liens via cette fonction, PHYSFS_stat() les ignorera et traitera la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désactiver le lien.

If bufsize is zero, any existing buffer on this handle is freed.

All reads and writes to the file handle will be buffered. Any seek operations will be translated into reads and writes to make sure that the buffers are flushed, and that the seek is performed on the underlying file.

If the handle is opened for writing, or for read/write, PhysFS will attempt to flush the buffer to disk when the handle is closed, or when this function is called with bufsize=0.

PhysicsFS file handles are unbuffered by default.

Avertissement

Cette fonction ne signalera pas d'erreur s'il y a des séquences UTF-8 invalides dans la chaîne d'entrée. Elle remplacera ces séquences par un caractère '?' et continuera.

Les chaînes UTF-16 ont 16 bits par caractère (sauf pour certains caractères qui font 32 bits) : TCHAR sous Windows, lorsque le support Unicode est utilisé.
