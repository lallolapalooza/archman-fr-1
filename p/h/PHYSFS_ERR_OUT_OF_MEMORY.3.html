Signature de fonction pour les rappels qui énumèrent les fichiers.

Avertissement

À partir de PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; il vous donne plus de contrôle sur le processus.

Ils sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de ces chaînes.

Ces rappels sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le même dans les versions de rappel. Consultez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Plie" un point de code Unicode vers son équivalent en minuscules. (Ceci est pour une utilisation limitée et hardcore. Si vous ne voyez pas immédiatement un besoin pour cela, vous pouvez probablement ignorer cette fonction pour toujours.)

Cela convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux n'ayant pas d'équivalent en minuscules seront retournés sans modification.

Notez que vous pourriez obtenir plusieurs points de code en retour ! Le "Eszett" allemand, par exemple, sera transformé en deux points de code latins en minuscules 's'. La théorie est que si vous pliez deux chaînes, l'une avec un Eszett et l'autre avec "SS" en minuscules, elles correspondront.

Attention

Quiconque a étudié Unicode connaît le problème du "i turc". Cette API ne le gère pas. Supposez que cette lettre unique dans tout Unicode sera pliée de manière incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la majeure partie de la planète, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Tampon pour stocker les valeurs des points de code pliés. Ce pointeur doit référencer un espace pour au moins 3 emplacements de PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialise la bibliothèque PhysicsFS. Cela ferme tous les fichiers ouverts via PhysicsFS, vide les chemins de recherche/écriture, libère la mémoire et invalide tous vos handles de fichiers.

Notez que cet appel peut ÉCHOUEER s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures sur un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur est tombé en panne, etc.). Il est généralement préférable de fermer tous les handles d'écriture vous-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois correctement désinitialisé, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états par défaut de l'API sont restaurés à ce moment-là, à l'exception de tout allocateur personnalisé que vous auriez pu spécifier, qui survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les détails de l'erreur peuvent être obtenus à partir de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini, et probablement très perturbé.

int PHYSFS_delete (const char * filename)

Supprime un fichier ou un répertoire. (filename) est spécifié dans une notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, pas ce qu'il pointe, indépendamment du fait que vous ayez "autorisé les liens symboliques" ou non.

Donc, si vous avez défini le répertoire d'écriture sur "C:\monjeu\writedir" et que vous appelez PHYSFS_delete("telechargements/cartes/niveau1.carte") alors le fichier "C:\monjeu\writedir\telechargements\cartes\niveau1.carte" est supprimé du système de fichiers physique, s'il existe et si le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont un handle de fichier ouvert dessus (y compris votre programme) ne fermeront pas leurs handles.

Il y a de fortes chances que les bits qui composent le fichier existent toujours, ils sont juste rendus disponibles pour être écrasés plus tard. Ne considérez pas cela comme une méthode de sécurité ou quoi que ce soit. :)

Paramètres

filename Nom du fichier à supprimer.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'utilisateur une fois pour chaque élément dans le chemin de recherche :

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donne-moi plus de données, s'il te plaît.
}
// ...

Les éléments transmis à la fonction de rappel ne sont garantis dans aucun ordre spécifique. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit l'ordre alphabétique. Cette forme signale ce qu'elle trouve dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons pas garantir l'ordre dans lequel les données sont découvertes. Tout tri que vous trouvez dans ces fonctions de rappel est purement un hasard. Ne vous y fiez pas. Comme cela parcourt toute la liste des fichiers, vous pourriez recevoir des noms de fichiers en double.

Cette API et les fonctions de rappel elles-mêmes peuvent signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même si elles ne recherchaient qu'un seul objet spécifique et voulaient s'arrêter là, ou si elles avaient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (une erreur de disque ou quelque chose de similaire), il ne pourrait pas le signaler à l'application, il pourrait simplement sauter des éléments ou arrêter l'énumération complètement, et l'appelant ne saurait pas qu'il avait perdu certaines données en cours de route.

Maintenant, l'appelant peut s'assurer qu'il a obtenu un ensemble complet de données, et s'il souhaite arrêter l'énumération plus tôt, sa fonction de rappel aura le contrôle. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur la manière dont votre fonction de rappel doit se comporter.

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Get the user-and-app-specific path where files can be written. Helper function.

Get the "pref dir". This is meant to be where users can write personal files (preferences and save games, etc) that are specific to your application. This directory is unique per user, per application.

This function will decide the appropriate location in the native filesystem, create the directory if necessary, and return a string in platform-dependent notation, suitable for passing to PHYSFS_setWriteDir().

On Windows, this might look like: "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name"

On Linux, this might look like: "/home/bob/.local/share/My Program Name"

On Mac OS X, this might look like: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

You should probably use the pref dir for your write dir, and also put it near the beginning of your search path. Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left you to figure out where the files should go under that tree. This finds the correct location for whatever platform, which not only changes between operating systems, but also versions of the same operating system.

You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might do) and the name of your application. These should be proper names.

Both the (org) and (app) strings may become part of a directory name, so please follow these rules:

  • Try to use the same org string (including case-sensitivity) for all your applications that use this function.
  • Always use a unique app string for each one, and make sure it never changes for an app once you've decided on it.
  • Unicode characters are legal, as long as it's UTF-8 encoded, but...

Ajoute un fichier ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter le même fichier à deux points de montage différents : le contrôle des doublons se fait par rapport au fichier, pas par rapport au point de montage.

Lorsque vous montez un fichier, celui-ci est ajouté à un système de fichiers virtuel... tous les fichiers de tous les fichiers montés sont entrelacés dans une seule arborescence hiérarchique. Deux fichiers montés au même endroit (ou un fichier superposant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans ce cas, le fichier le plus proche dans le chemin de recherche est sélectionné, et les autres fichiers ne sont pas accessibles à l'application. Cela permet d'utiliser les fichiers pour remplacer des versions antérieures ; vous pouvez utiliser le mécanisme de montage pour placer des fichiers à un endroit spécifique dans l'arborescence des fichiers et empêcher les superpositions ; c'est utile pour les modes de téléchargement qui pourraient piétiner les données de l'application ou les unes les autres, par exemple.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive la sécurité des liens symboliques dans les fichiers. Certains systèmes de fichiers physiques et archivés contiennent des fichiers qui sont de simples références à d'autres fichiers. Lors de l'ouverture d'un tel lien, le système physique ouvre de manière transparente le fichier auquel il fait référence.

Par défaut, PhysicsFS vérifie si un fichier est un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait pointer en dehors des chemins de lecture et d'écriture, compromettant la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Notez que cela est davantage destiné au sandboxing d'un langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur peut avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas le désactiver, à moins que vous ne pensiez qu'il existe un risque spécifique à leur autorisation.

Les liens symboliques ne seront vus que lorsque des noms de fichiers sont traités dans une notation indépendante du système. C'est-à-dire que lorsque vos chemins de recherche et d'écriture, etc., sont définis, les liens symboliques ne seront jamais vus.

Remarque : PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne le suivra jamais dans tous les cas. S'il n'est pas autorisé par cette fonction, PHYSFS_stat() ignorera le lien et traitera la requête comme si le chemin n'existait pas.

L'autorisation des liens symboliques peut être activée ou désactivée à tout moment après l'appel de PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désactiver le lien.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convertit une chaîne UTF-8 en une chaîne Latin1. Les chaînes Latin1 sont codées sur 8 bits par caractère : un encodage "ASCII étendu" populaire.

Pour s'assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon de taille double par rapport au tampon source. UTF-8 étend les points de code Latin1 supérieurs à 127 de 1 à 2 octets, donc la chaîne peut s'agrandir dans certains cas.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais une séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Veuillez noter que nous ne fournissons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer la plupart des points de code Unicode. C'est un encodage hérité ; vous devriez toujours chercher à vous en éloigner.

Paramètres

src Chaîne source terminée par un caractère nul au format Latin1.
dst Tampon pour stocker la chaîne UTF-8 convertie.
len Taille, en octets, du tampon de destination.
