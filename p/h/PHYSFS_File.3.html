typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent les fichiers.

Attention

À partir de PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() pour avoir plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, une entrée par callback. Toutes les chaînes de caractères sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire des chaînes de caractères.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui renvoient des listes qui doivent être libérées avec PHYSFS_freeList(). Le callback indique que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes de caractères auparavant.

Notez que l'ordre promis dans les versions de liste n'est pas nécessairement le même dans les versions de callback. Voir la documentation spécifique des API, mais les chaînes de caractères peuvent ne pas être triées comme vous l'attendez et vous pourriez obtenir des chaînes de caractères en double.

Paramètres

data pointeur vers des données définies par l'utilisateur, passé via l'API qui a finalement appelé le callback.
origdir chaîne de caractères avec le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire pour lequel vous avez demandé l'énumération, passé en paramètre dans le callback pour votre commodité.
fname nom du fichier en cours d'énumération. Il peut ne pas être trié alphabétiquement par rapport à d'autres callbacks qui ont été appelés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

La suppression d'un lien symbolique supprimera le lien, pas ce à quoi il pointe, indépendamment du fait que vous ayez "autorisé les liens symboliques" ou non.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenez une liste de fichiers d'un répertoire du chemin de recherche, en utilisant un rappel défini par l'application, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de la renvoyer à l'application, donc la fonctionnalité est identique, sauf pour la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas de tableau. Elle appelle plutôt une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés au rappel ne sont garantis dans aucun ordre. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale tout ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre de découverte des données. Tout tri que vous trouvez dans ces rappels est pure chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers en double.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur sérieuse et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement sauter des éléments ou arrêter l'énumération franchement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble de données complet, et son rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement de votre rappel.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées au rappel. Peut être NULL.

Retourne

Non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel renvoie PHYSFS_ENUM_STOP pour s'arrêter plus tôt, cela sera considéré comme un succès. Les rappels renvoyant PHYSFS_ENUM_ERROR feront renvoyer zéro à cette fonction et définiront le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtenez une liste de fichiers d'un répertoire du chemin de recherche.

Attention

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction renvoyait autant d'éléments que possible face à une condition d'échec (manque de mémoire, erreur d'E/S disque, etc.). Comme cela signifiait que les applications ne pouvaient pas distinguer un succès complet d'un échec partiel, et comme la fonction pouvait toujours renvoyer NULL pour signaler des échecs catastrophiques de toute façon, dans PhysicsFS 2.1, la politique de cette fonction a changé : elle renverra soit une liste de résultats complets, soit NULL pour tout échec de quelque nature que ce soit, afin que nous puissions garantir que l'énumération s'est déroulée complètement et n'a pas de lacunes dans ses résultats.

Les répertoires correspondants sont interpolés. C'est-à-dire que si "C:\mydir" se trouve dans le chemin de recherche et contient un répertoire "savegames" qui contient "x.sav", "y.sav" et "z.sav", et qu'il y a aussi un répertoire "C:\userdir" dans le chemin de recherche qui a un sous-répertoire "savegames" avec "w.sav", alors le code suivant :

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Nous avons [%s].\n", *i);
PHYSFS_freeList(rc);
* Nous avons [x.sav].
* Nous avons [y.sav].
* Nous avons [z.sav].
* Nous avons [w.sav]..fi
N'hésitez pas à trier la liste comme vous le souhaitez. Cependant, les données renvoyées ne contiendront toujours aucun doublon et seront toujours triées par ordre alphabétique (plutôt : Unicode sensible à la casse) pour vous.
N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur de retour de cette fonction lorsque vous en avez terminé.
Paramètres
dir répertoire en notation indépendante de la plateforme à énumérer.

char **PHYSFS_getCdRomDirs(void)

Obtient un tableau de chemins vers les répertoires de CD-ROM disponibles. Les répertoires renvoyés dépendent du système (« D:\\ » sous Win32, « /cdrom » ou autre sous Unix). Les répertoires ne sont renvoyés que s'il y a un disque prêt et accessible dans le lecteur. Ainsi, si vous avez deux lecteurs (D: et E:), et que seul E: contient un disque, vous n'obtiendrez que le lecteur E:. Si l'utilisateur insère un disque dans D: et que vous appelez à nouveau cette fonction, vous obtiendrez les deux lecteurs. Sur un système Unix, si l'utilisateur démonte un disque et le remonte, le prochain appel à cette fonction reflétera ce changement. char **cds = PHYSFS_getCdRomDirs();

    printf("cdrom dir [%s] is available.\n", *i);

PHYSFS_freeList(cds);

Cet appel peut bloquer pendant que les lecteurs tournent. Soyez donc averti.

Lorsque vous avez terminé avec les informations renvoyées, vous pouvez libérer les ressources en appelant PHYSFS_freeList() avec le pointeur renvoyé.

void PHYSFS_permitSymbolicLinks (int allow)

Permettre ou interdire le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné à l'isolation du langage de script d'un programme, au cas où des scripts non fiables essaieraient de compromettre le système. De manière générale, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, donc à moins que vous ne pensiez qu'il existe un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers dans la notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans tous les cas pas suivi. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser les liens.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 expands latin1 codepoints over 127 from 1 to 2 bytes, so the string may grow in some cases.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-8 sequence at the end. If the buffer length is 0, this function does nothing.

Warning

This function will not report an error if there are invalid UTF-16 sequences in the source string. It will replace them with a '?' character and continue on.

int PHYSFS_utf8stricmp (const char * str1, const char * str2)

Case-insensitive compare of two UTF-8 strings. This is a strcasecmp/stricmp replacement that expects both strings to be in UTF-8 encoding. It will do "case folding" to decide if the Unicode codepoints in the strings match.

If both strings are exclusively low-ASCII characters, this will do the right thing, as that is also valid UTF-8. If there are any high-ASCII chars, this will not do what you expect!

It will report which string is "greater than" the other, but be aware that this doesn't necessarily mean anything: 'a' may be "less than" 'b', but a Japanese kuten has no meaningful alphabetically relationship to a Greek lambda, but being able to assign a reliable "value" makes sorting algorithms possible, if not entirely sane. Most cases should treat the return value as "equal" or "not equal".

Like stricmp, this expects both strings to be NULL-terminated.

Parameters

str1 First string to compare.
str2 Second string to compare.

Returns

-1 if str1 is "less than" str2, 1 if "greater than", 0 if equal.
