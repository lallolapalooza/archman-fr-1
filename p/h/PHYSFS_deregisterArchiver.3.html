PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du rappel : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter de chercher davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname Le nom du fichier qui est énuméré. Il pourrait ne pas être dans l'ordre alphabétique par rapport à d'autres rappels qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent des fichiers.

Avertissement

À partir de PhysicsFS 2.1, utilisez plutôt PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; il vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de ces chaînes.

Ces rappels sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre promis des données dans les versions basées sur des listes n'est pas nécessairement le même dans les versions basées sur des rappels. Vérifiez la documentation des API spécifiques, mais les chaînes pourraient ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers d'un répertoire du chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec rapport d'erreurs. En interne, PHYSFS_enumerateFiles() appelle cette fonction puis construit une liste avant de la retourner à l'application, donc la fonctionnalité est identique sauf la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Elle appelle plutôt une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons obtenu [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis dans aucun ordre. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme rapporte ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons pas garantir l'ordre dans lequel les données seront découvertes. Tout tri que vous trouverez dans ces rappels est purement de la chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pourriez recevoir des noms de fichiers en double.

Cette API et les fonctions de rappel elles-mêmes sont capables de signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'il y avait une erreur grave et qu'ils ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération directement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble de données complet, et sa fonction de rappel a le contrôle s'il veut que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement de votre fonction de rappel.

const char *physFS_getPrefDir (const char * org, const char * app)

Obtient le "répertoire des préférences". C'est l'endroit où les utilisateurs peuvent écrire des fichiers personnels (préférences et sauvegardes de jeux, etc.) spécifiques à votre application. Ce répertoire est unique pour chaque utilisateur et chaque application.

Sous Linux, cela pourrait ressembler à : "/home/bob/.local/share/My Program Name"

Sous Mac OS X, cela pourrait ressembler à : "/Users/bob/Library/Application Support/My Program Name"

(etc.)

  • Utilisez toujours une chaîne d'application unique pour chaque application, et assurez-vous qu'elle ne change pas pour une application une fois décidée.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : le contrôle des doublons est effectué par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés en un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers chevauchant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser les archives pour remplacer les versions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer les archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; ceci est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept de "montage" Unix pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

Spécifier un lien symbolique vers une archive ou un répertoire est autorisé ici, indépendamment de l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que des liens symboliques à l'intérieur du répertoire ou de l'archive montée.

Retour

Un handle de fichier physique valide en cas de succès, NULL en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

Voir aussi

Activer ou désactiver le suivi des liens symboliques. Certains systèmes de fichiers physiques et architectures contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, le fichier auquel il fait référence est ouvert de manière transparente.

Par défaut, PhysicsFS vérifie si un fichier est un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait pointer vers une destination en dehors des chemins de lecture et d'écriture, compromettant la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Ceci est surtout utile pour l'isolation d'un langage de script du programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas le désactiver à moins que vous ne ressentiez une menace spécifique.

Les liens symboliques ne seront spécifiquement vérifiés que lors du traitement des noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire, lorsque les chemins de recherche et d'écriture, etc., sont définis, les liens symboliques ne sont jamais vérifiés.

Note : PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si cette fonction n'est pas autorisée, PHYSFS_stat() ignorera le lien et traitera la requête comme si le chemin n'existait pas.

L'autorisation des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow différent de zéro pour autoriser les liens symboliques, zéro pour désactiver les liens.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Fait d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de réduire les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt, monté sur /a, alors l'appel PHYSFS_openRead("/a/z.txt") réussira si vous appelez PHYSFS_setRoot("x.zip", "/y").

Vous pouvez changer la racine d'une archive à tout moment, modifiant l'arborescence de fichiers interpolée (selon où les chemins changent, une archive différente peut fournir divers fichiers). La définition d'une nouvelle racine n'est pas limitée aux archives dans le chemin de recherche ; vous pouvez également en définir une sur le répertoire d'écriture, ce qui peut être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez donc pas changer le répertoire d'écriture pour le moment.

archive répertoire/archive dont changer la racine.

int PHYSFS_setSaneConfig (const char * organization, const char * appName, const char * archiveExt, int includeCdRoms, int archivesFirst)

Configure des chemins par défaut raisonnables. Fonction d'aide.

Le répertoire d'écriture sera défini sur le répertoire de préférences renvoyé par

PHYSFS_getPrefDir(organization, appName)

, qui est créé s'il n'existe pas.

Ce qui précède est suffisant pour s'assurer que le répertoire de configuration de votre programme est séparé des autres encombrements et indépendant de la plateforme.

Le chemin de recherche sera :

  • Le répertoire d'écriture (créé s'il n'existe pas)
  • Le répertoire de base (PHYSFS_getBaseDir())
  • Tous les répertoires de CD-ROM trouvés (facultatif)

Ces répertoires sont ensuite recherchés pour les fichiers se terminant par l'extension (archiveExt), qui, s'ils sont des archives valides et prises en charge, seront également ajoutés au chemin de recherche. Si vous avez spécifié "PKG" pour (archiveExt), et qu'il existe un fichier nommé data.PKG dans le répertoire de base, il sera vérifié. Les archives peuvent être ajoutées ou précédées au chemin de recherche par ordre alphabétique, quel que soit le répertoire dans lequel elles ont été trouvées. Toutes les archives sont montées à la racine du système de fichiers virtuel ("/").

Tout cela peut être accompli depuis l'application, mais ceci le fait simplement pour vous. N'hésitez pas à ajouter manuellement d'autres éléments au chemin de recherche.

Écrire des données dans un descripteur de fichier PhysicsFS. Le fichier doit être ouvert en écriture.

Veuillez noter que bien que (len) soit un entier non signé de 64 bits, vous êtes limité à 63 bits (9223372036854775807 octets), nous pouvons donc retourner une valeur négative en cas d'erreur. PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 — convert and write an unsigned N-bit number in big or little endian format to a PHYSFS archive

Detailed Description

These functions convert an unsigned integer from the platform's native byte order to big-endian or little-endian format, and then write it to the specified PHYSFS_openWrite (3) file handle.

These are convenience functions. They just call PHYSFS_writeLE16 (3) and friends internally.

Warning: PHYSFS_uint64 is only 32 bits on platforms without any sort of 64-bit support.
