PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut renvoyer un résultat à partir du rappel : par exemple, si vous recherchez quelque chose de spécifique, en le trouvant, vous pouvez dire à PhysicsFS d'arrêter l'énumération. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien obtenu. :)

Paramètres

data Un pointeur vers des données définies par l'utilisateur, transmises via l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante du système d'exploitation, du répertoire qui contient ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, transmis dans le rappel pour votre commodité.
fname Le nom du fichier en cours d'énumération. Il peut ne pas être dans l'ordre alphabétique par rapport à d'autres rappels qui ont été appelés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() pour avoir plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste de répertoires d'entrée à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire des chaînes.

Ces rappels sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui renvoient des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer la liste entière et toutes les chaînes à l'avance.

Notez que le tri promis dans les versions de liste n'est pas nécessairement le même dans les versions de rappel. Consultez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes en double.

Paramètres

data Un pointeur vers des données définies par l'utilisateur, transmis via l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante du système d'exploitation, du répertoire qui contient ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, transmis dans le rappel pour votre commodité.
fname Le nom du fichier en cours d'énumération. Il peut ne pas être dans l'ordre alphabétique par rapport à d'autres rappels qui ont été appelés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers d'un répertoire du chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec rapport d'erreurs. Internally, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique, sauf pour la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas de tableau. Elle appelle plutôt une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis d'aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme rapporte tout ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre de découverte des données. Tout tri que vous trouvez dans ces fonctions de rappel n'est que pure chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers en double.

Cette API et les fonctions de rappel elles-mêmes sont capables de signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même si elles ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou si elles avaient une erreur sérieuse et ne pouvaient en alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération complètement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr qu'il a obtenu un ensemble de données complet, et sa fonction de rappel a le contrôle s'il veut arrêter l'énumération plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement de votre fonction de rappel.

Parameters

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

Returns

non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel retourne PHYSFS_ENUM_STOP pour s'arrêter plus tôt, cela sera considéré comme un succès. Les fonctions de rappel retournant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

char **PHYSFS_enumerateFiles (const char * dir)

Obtenir une liste de fichiers d'un répertoire du chemin de recherche.

Warning

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction retournait autant d'éléments que possible face à une condition d'échec (manque de mémoire, erreur d'entrée/sortie disque, etc.). Comme cela signifiait que les applications ne pouvaient pas distinguer un succès complet d'un échec partiel, et comme la fonction pouvait toujours retourner NULL pour signaler des échecs catastrophiques de toute façon, dans PhysicsFS 2.1, la politique de cette fonction a changé : elle retournera soit une liste de résultats complets, soit NULL pour tout échec d'une sorte ou d'une autre, afin que nous puissions garantir que l'énumération s'est déroulée jusqu'à son terme et qu'il n'y a pas de lacunes dans ses résultats.

Les répertoires correspondants sont interpolés. C'est-à-dire que si "C:\monrep" est dans le chemin de recherche et contient un répertoire "sauvegardes" qui contient "x.sav", "y.sav" et "z.sav", et qu'il y a aussi un "C:\repuser" dans le chemin de recherche qui a un sous-répertoire "sauvegardes" avec "w.sav", alors le code suivant :

char **rc = PHYSFS_enumerateFiles("sauvegardes");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Nous avons [%s].\n", *i);
PHYSFS_freeList(rc);
* Nous avons [x.sav].
* Nous avons [y.sav].
* Nous avons [z.sav].
* Nous avons [w.sav]..fi
N'hésitez pas à trier la liste comme bon vous semble. Cependant, les données retournées ne contiendront toujours aucun doublon, et seront toujours triées par ordre alphabétique (ou plutôt, par ordre Unicode sensible à la casse) pour vous.
N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur de retour de cette fonction lorsque vous en aurez terminé.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers se chevauchant avec un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser les archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer les archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; ceci est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept de montage Unix peuvent attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

La spécification d'un lien symbolique vers une archive ou un répertoire est autorisée ici, quel que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne concerne que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

newDir répertoire ou archive à ajouter au chemin, en notation dépendant de la plateforme.
mountPoint Emplacement dans l'arbre interpolé où cette archive sera "montée", en notation indépendante de la plateforme. NULL ou "" est équivalent à "/".
appendToPath non nul pour ajouter au chemin de recherche, zéro pour précéder.

une valeur non nulle si ajouté au chemin, zéro en cas d'échec (archive invalide, répertoire manquant, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archivés contiennent des fichiers qui sont simplement des liens vers d'autres fichiers. Lors de l'ouverture d'un lien symbolique dans un système physique, cela est fait de manière transparente, en ouvrant le fichier pointé.

Par défaut, PhysicsFS vérifiera si un fichier est réellement un lien symbolique lors des appels d'ouverture et échouera si c'est le cas. Sinon, le lien pourrait vous amener en dehors des chemins de lecture et d'écriture, compromettant la sécurité.

Si vous souhaitez assumer ce risque, appelez cette fonction avec une valeur non nulle. Notez que cela concerne davantage le sandboxing des langages de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. En général, un utilisateur pourrait avoir une raison valable de créer un lien symbolique, vous ne devriez donc pas le désactiver, à moins que vous ne pensiez qu'il y ait un danger spécifique.

Les liens symboliques ne seront visibles que lorsqu'il s'agit de noms de fichiers dans une notation indépendante de la plateforme. Autrement dit, lorsque vous configurez vos chemins de recherche et d'écriture, etc., les liens symboliques ne seront jamais vus.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignorera et traitera la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désactiver le lien.

Définit le code d'erreur actuel du thread. Cela vous permet de définir la valeur qui sera retournée par le prochain appel à PHYSFS_getLastErrorCode(). Cela remplacera tout code d'erreur existant, qu'il ait été défini par votre application ou en interne par PhysicsFS.

Cette fonction ne se soucie pas de savoir si le code d'erreur est une valeur connue par PhysicsFS ou non (mais PHYSFS_getErrorByCode() retournera NULL pour les valeurs inconnues). La valeur sera rapportée sans modification par PHYSFS_getLastErrorCode().

int PHYSFS_setRoot (const char * archive, const char * subdir)

Crée un sous-répertoire d'une archive comme répertoire racine. Cela vous permet de restreindre les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier à y/z.txt, monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors un appel à PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer le répertoire racine d'une archive à tout moment, modifiant ainsi l'arborescence de fichiers interpolée (selon l'endroit où les chemins correspondent, une archive différente peut fournir des fichiers différents). Si vous définissez le répertoire racine sur NULL ou sur "/", l'archive sera traitée comme si elle n'avait pas été spécifiquement définie (comme si l'archive était montée normalement).

Changer le répertoire racine n'affecte que les opérations futures sur les chemins de fichiers ; un fichier ouvert à partir d'un chemin qui a changé en raison d'un setRoot ne sera pas affecté.

La définition d'un nouveau répertoire racine n'est pas limitée aux archives dans le chemin de recherche ; vous pouvez également le définir dans le répertoire d'écriture, ce qui pourrait être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez pas changer le répertoire d'écriture pour le moment.

Ce n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme répertoire racine d'une archive ; cependant, aucun fichier ne sera visible dans ce cas. Si les répertoires manquants finissent par être créés (un mkdir vers le système de fichiers physique, etc.), cela sera reflété dans l'arborescence interpolée.

Paramètres

archive Répertoire/archive dans lequel changer le répertoire racine.
subdir Nouveau sous-répertoire à définir comme répertoire racine de cette archive.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.
