PHYSFS_enumerate

C'est le même que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il retourne un résultat depuis le callback : par exemple, si vous cherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter l'énumération. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir obtenu correctement. :)

Paramètres

data Un pointeur vers un PHYSFS_Version pour initialiser.
origdir Une chaîne avec le chemin complet, en notation indépendante du système d'exploitation, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire dans lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport à d'autres callbacks qui ont été appelés, et ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonctions de callbacks qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() pour avoir plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, une entrée par callback. Toutes les chaînes sont codées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire des chaînes.

Ces callbacks sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui retournent des listes qui doivent être libérées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes au départ.

Notez que l'ordre promis dans les versions de liste n'est pas nécessairement le même dans les versions de callback. Vérifiez la documentation spécifique des API, mais les chaînes peuvent ne pas être triées comme vous l'attendez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data Un pointeur vers des données définies par l'utilisateur, passé via l'API qui a finalement appelé le callback.
origdir Une chaîne avec le chemin complet, en notation indépendante du système d'exploitation, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire dans lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport à d'autres callbacks qui ont été appelés, et ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

In PhysicsFS versions prior to 2.1, this function would return as many items as it could in the face of a failure condition (out of memory, disk i/o error, etc). const char *PHYSFS_getLastError (void )

Obtenir des informations d'erreur sous forme de chaîne de caractères lisible.

Obsolète

Utilisez PHYSFS_getLastErrorCode() et PHYSFS_getErrorByCode() à la place.

Note

Depuis PhysicsFS 2.1, cette fonction a été retirée. Avant PhysicsFS 2.1, c'était la seule façon d'obtenir des détails d'erreur au-delà de la valeur renvoyée par la fonction de base d'un processus donné. C'était intentionnellement une chaîne lisible dans plusieurs langues, et non utile pour l'analyse par les applications. C'était un problème, car le développeur, et non l'utilisateur, choisissait la langue au moment de la compilation, et les mainteneurs de PhysicsFS devaient (mal) maintenir un travail de localisation énorme. L'application ne pouvait pas analyser les chaînes, même si elles étaient dans une langue spécifique, car certaines étaient générées dynamiquement. Dans la version 2.1 et ultérieures, elle renvoie toujours une chaîne statique en anglais ; vous pouvez l'utiliser comme chaîne clé pour votre propre localisation, à condition que nous promettions de ne pas changer les chaînes d'erreur existantes. De plus, si votre application souhaite connaître les erreurs spécifiques, nous offrons maintenant une meilleure option : utilisez PHYSFS_getLastErrorCode().

Obtient le dernier message d'erreur de PhysicsFS sous forme de chaîne de caractères lisible et nulle-terminée. Cette fonction renverra NULL s'il n'y a pas eu d'erreur depuis le dernier appel à cette fonction. Le pointeur renvoyé pointe vers un tampon interne. Chaque thread a un état d'erreur unique qui lui est associé, mais chaque fois qu'un nouveau message d'erreur est défini, il écrase l'état précédent associé à ce thread. Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Warning

Unless you have some special, low-level need, you should be using PHYSFS_mount() instead of this.

Archives-in-archives may be very slow! While a PHYSFS_File can seek even when the data is compressed, it may do so by rewinding to the start and decompressing everything before the seek point. Normal archive usage may do a lot of seeking behind the scenes. As such, you might find normal archive usage extremely painful if mounted this way. Plan accordingly: if you, say, have a self-extracting .zip file, and want to mount something in it, compress the contents of the inner archive and make sure the outer .zip file doesn't compress the inner archive too.

This function operates just like PHYSFS_mount(), but takes a PHYSFS_File handle instead of a pathname. This handle contains all the data of the archive, and is used instead of a real file in the physical filesystem. The PHYSFS_File may be backed by a real file in the physical filesystem, but isn't necessarily. The most popular use for this is likely to mount archives stored inside other archives.

(newDir) must be a unique string to identify this archive. It is used to optimize archiver selection (if you name it XXXXX.zip, we might try the ZIP archiver first, for example, or directly choose an archiver that can only trust the data is valid by filename extension). It doesn't need to refer to a real file at all. If the filename extension isn't helpful, the system will try every archiver until one works or none of them do. This filename must be unique, as the system won't allow you to have two archives with the same name.

int PHYSFS_mountMemory (const void * buf, PHYSFS_uint64 len, void(* del )(void *), const char * newDir, const char * mountPoint, int appendToPath)

Add an archive, contained in a memory buffer, to the search path.

Warning

Unless you have some special, low-level need, you should be using PHYSFS_mount() instead of this.

This function operates just like PHYSFS_mount(), but takes a memory buffer instead of a pathname. This buffer contains all the data of the archive, and is used instead of a real file in the physical filesystem.

(newDir) must be a unique string to identify this archive. It is used to optimize archiver selection (if you name it XXXXX.zip, we might try the ZIP archiver first, for example, or directly choose an archiver that can only trust the data is valid by filename extension). It doesn't need to refer to a real file at all. If the filename extension isn't helpful, the system will try every archiver until one works or none of them do. This filename must be unique, as the system won't allow you to have two archives with the same name.

(ptr) must remain until the archive is unmounted. When the archive is unmounted, the system will call (del)(ptr), which will notify you that the system is done with the buffer, and give you a chance to free your resources. (del) can be NULL, in which case the system will make no attempt to free the buffer.

If this function fails, (del) is not called.

Parameters

buf Address of the memory buffer containing the archive data.
len Size of memory buffer, in bytes.
del A callback that triggers upon unmount. Can be NULL.
newDir Filename that can represent this stream.
mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Returns

nonzero if added to path, zero on failure (bogus archive, etc). Use PHYSFS_getLastErrorCode() to obtain the specific error.

void PHYSFS_permitSymbolicLinks (int allow)

Permite o deniega el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y arquitecturas contienen archivos que son simples referencias a otros archivos. Al abrir un enlace simbólico físico, este se abrirá transparentemente en el archivo al que se refiere.

Por defecto, PhysicsFS comprobará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de los caminos de lectura y escritura, comprometiendo la seguridad.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Hace que un subdirectorio de un archivo sea su directorio raíz. Esto le permite reducir los archivos accesibles en un archivo específico. Por ejemplo, si tiene x.zip con un archivo en y/z.txt montado en /a, si llama PHYSFS_setRoot("x.zip", "/y"), la llamada a PHYSFS_openRead("/a/z.txt") tendrá éxito.

Puede cambiar la raíz de un archivo en cualquier momento, alterando así el árbol de archivos interpolado (dependiendo de dónde se desplacen las rutas, puede que proporcione varios archivos de un archivo diferente). Si establece la raíz a NULL o a "/", el archivo se tratará como si no tuviera raíz especial (como si el archivo se hubiera montado normalmente).

Cambiar la raíz solo afecta a las operaciones futuras en las rutas de los archivos; un archivo que se abrió a partir de una ruta que cambió debido a un setRoot no se verá afectado.

Establecer una nueva raíz no se limita a los archivos de la lista de búsqueda; puede establecerla en el directorio de escritura también, lo que podría ser útil si tiene archivos abiertos para escribir y no puede cambiar el directorio de escritura ahora.

No es un error establecer un subdirectorio que no exista como raíz de un archivo, aunque no se mostrarán archivos en este caso. Si los directorios que se quieren crear (una mkdir en el sistema de archivos físico, etc.) se crean, esto se reflejará en el árbol interpolado.

Parámetros

archive directorio/archivo en el cual cambiar la raíz.
subdir nuevo subdirectorio para hacer la raíz de este archivo.

Devuelve

Pour garantir que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon deux fois plus grand que le tampon source. L'UTF-8 étend les points de code Latin1 supérieurs à 127 de 1 à 2 octets, donc la chaîne peut s'agrandir dans certains cas.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Veuillez noter que nous ne fournissons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer la plupart des points de code Unicode. C'est un encodage hérité ; vous devriez toujours vous en éloigner.

dst Tampon pour stocker la chaîne UTF-8 convertie.

UTF-16 est UCS-2, sauf pour les caractères qui font 4 octets, qui ne peuvent pas être entièrement représentés en UCS-2. Si vous n'êtes pas sûr, vous devriez utiliser UTF-16 sur Windows à ce stade.

Pour vous assurer que le buffer de destination est suffisamment grand pour la conversion, veuillez allouer un buffer deux fois plus grand que le buffer source. UTF-8 utilise un à quatre octets par caractère, mais UTF-16 utilise toujours deux à quatre octets, donc une chaîne de caractères ASCII basiques doublera sa taille ! Les caractères UTF-16 qui prendraient quatre octets prendraient aussi quatre octets en UTF-8, donc vous n'avez pas besoin d'allouer 4 fois l'espace, juste le double.

Les chaînes qui ne rentrent pas dans le buffer de destination seront tronquées, mais elles seront toujours terminées par un caractère nul et n'auront jamais de paire de substitution incomplète à la fin. Si la longueur du buffer est de zéro, cette fonction ne fait rien.

Paramètres

src Chaîne source terminée par un caractère nul au format UTF-8.
dst Buffer pour stocker la chaîne UTF-16 convertie.
len Taille en octets du buffer de destination.

Écrire des données dans un fichier PhysicsFS. Le fichier doit être ouvert en écriture.

Note : bien que (len) soit un entier non signé de 64 bits, vous êtes limité à 63 bits (9223372036854775807 octets), nous pouvons donc retourner une valeur négative en cas d'erreur.
