PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du callback : à savoir : si vous cherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous avons espérons bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, transmis depuis l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, transmis dans le callback pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être en ordre alphabétique par rapport aux autres callbacks qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent les fichiers.

Attention

À partir de PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; cela vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de ces chaînes.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes d'avance.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le même dans les versions de callback. Consultez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous l'attendez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data Pointeur de données défini par l'utilisateur, transmis depuis l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, transmis dans le callback pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être en ordre alphabétique par rapport aux autres callbacks qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de la renvoyer à l'application, donc la fonctionnalité est identique, sauf pour la manière dont l'information est présentée à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas un tableau. Elle appelle à la place une fonction spécifiée par l'application une fois pour chaque élément dans le chemin de recherche :

{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donne-moi plus de données, s'il te plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés au callback ne sont pas garantis d'être dans un ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un ordre alphabétique. Cette forme signale ce qui est trouvé dans chaque archive avant de passer à la suivante. Même au sein d'une seule archive, nous ne pouvons pas garantir l'ordre dans lequel les données sont découvertes. Tout tri que vous trouvez dans ces callbacks n'est que de la pure chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pourriez recevoir des noms de fichiers dupliqués.

Cette API et les callbacks eux-mêmes peuvent signaler des erreurs. Avant cette API, les callbacks devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'un élément spécifique et voulaient s'arrêter là, ou s'ils avaient une erreur sérieuse et ne pouvaient en alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante ; il se contentait d'ignorer des éléments ou d'arrêter l'énumération, et l'appelant n'aurait aucune idée qu'il avait perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble de données complet, et son callback a le contrôle s'il souhaite arrêter l'énumération plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur la façon dont votre callback doit se comporter.

dir Répertoire, en notation indépendante du système d'exploitation, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées au callback. Peut être NULL.

Retour

Non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le callback renvoie PHYSFS_ENUM_STOP pour s'arrêter plus tôt, cela sera considéré comme un succès. Les callbacks qui renvoient PHYSFS_ENUM_ERROR feront que cette fonction renvoie zéro et définira le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

Obtenir une liste de fichiers d'un répertoire d'un chemin de recherche.

Attention

Comme cela empêchait les applications de distinguer entre un succès complet et un échec partiel, et étant donné que la fonction pouvait toujours renvoyer NULL pour signaler des erreurs catastrophiques, dans PhysicsFS 2.1, cette politique a été modifiée : elle renverra une liste complète de résultats ou renverra NULL en cas de tout type d'échec, afin que nous puissions garantir que l'énumération s'est terminée correctement et qu'il n'y a pas de lacunes dans vos résultats.

Les répertoires correspondants sont interpolés. C'est-à-dire, si "C:\mydir" est dans le chemin de recherche et contient un répertoire "savegames" contenant "x.sav", "y.sav" et "z.sav", et qu'il y a également un répertoire "C:\userdir" dans le chemin de recherche qui a un sous-répertoire "savegames" avec "w.sav", alors le code suivant :

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi

N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur renvoyée par cette fonction lorsque vous avez terminé.

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Obtient le chemin spécifique à l'utilisateur et à l'application où les fichiers peuvent être écrits. Fonction d'aide.

Obtient le « répertoire de préférences ». Ceci est destiné à être l'endroit où les utilisateurs peuvent écrire des fichiers personnels (préférences et sauvegardes de jeux, etc.) spécifiques à votre application. Ce répertoire est unique par utilisateur, par application.

Cette fonction déterminera l'emplacement approprié dans le système de fichiers natif, créera le répertoire si nécessaire et retournera une chaîne en notation indépendante de la plateforme, adaptée pour être passée à PHYSFS_setWriteDir().

Sous Linux, cela pourrait ressembler à : "/home/bob/.local/share/Mon Nom de Programme"

Sous Mac OS X, cela pourrait ressembler à : "/Users/bob/Library/Application Support/Mon Nom de Programme"

(etc.)

Vous devriez probablement utiliser le répertoire de préférences pour votre répertoire d'écriture, et également le placer près du début de votre chemin de recherche. Les versions plus anciennes de PhysicsFS offraient uniquement PHYSFS_getUserDir() et vous laissaient deviner où les fichiers devaient aller sous cet arbre. Ceci trouve l'emplacement correct pour quelle que soit la plateforme, qui change non seulement entre les systèmes d'exploitation, mais aussi entre les versions du même système d'exploitation.

  • Essayez d'utiliser la même chaîne d'organisation (y compris la casse) pour toutes vos applications qui utilisent cette fonction.
  • Utilisez toujours une chaîne d'application unique pour chacune, et assurez-vous qu'elle ne change jamais pour une application une fois que vous l'avez décidée.
  • Les caractères Unicode sont autorisés, tant qu'ils sont encodés en UTF-8, mais...
  • ...n'utilisez que des lettres, des chiffres et des espaces. Évitez la ponctuation comme "Nom du Jeu 2: La Revanche du Méchant !" ... "Nom du Jeu 2" est suffisant.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers se chevauchant avec un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser les archives pour remplacer les versions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et empêcher les chevauchements ; ceci est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou les uns les autres, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui sont familiers avec le concept Unix de "montage" pourraient s'attendre. De plus, plusieurs archives peuvent être montées au même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

La spécification d'un lien symbolique vers une archive ou un répertoire est autorisée ici, quel que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

Paramètres

newDir répertoire ou archive à ajouter au chemin, en notation dépendante de la plateforme.
mountPoint Emplacement dans l'arborescence interpolée où cette archive sera "montée", en notation indépendante de la plateforme. NULL ou "" équivaut à "/".

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et architectures contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, il s'ouvrira de manière transparente vers le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous faire sortir des chemins de lecture et d'écriture, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Notez que ceci est plus destiné au sandboxing d'un langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas le désactiver, sauf si vous ressentez un danger spécifique.

Les liens symboliques ne seront vérifiés que lorsque des noms de fichiers seront manipulés dans une notation indépendante de la plateforme. C'est-à-dire, lorsque vos chemins de recherche et d'écriture, etc., seront définis, les liens symboliques ne seront jamais vérifiés.

Remarque : PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés par le biais de cette fonction, PHYSFS_stat() les ignore et traite la requête comme si le chemin n'existait pas.

La permissibilité des liens symboliques peut être activée ou désactivée après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désactiver le lien.

Detailed Description

Ces fonctions écrivent des valeurs entières de 16, 32 ou 64 bits sans signe dans un fichier, en s'assurant qu'elles sont dans l'ordre des octets spécifié.

Elles sont utiles pour écrire des données dans des formats de fichiers qui exigent un ordre des octets spécifique, indépendamment de l'architecture de la plateforme sur laquelle le programme s'exécute.
