Informations sur la version

PHYSFS_VERSION est une macro qui représente la version de la bibliothèque PhysFS à laquelle vous avez compilé votre projet. Elle est déterminée par l'en-tête que le compilateur utilise. Notez que si vous avez lié la bibliothèque dynamiquement, la version exécutée peut être légèrement plus récente ou plus ancienne. Cette version peut être déterminée à l'aide de PHYSFS_getLinkedVersion(), qui, contrairement à PHYSFS_VERSION, n'est pas une macro.

Paramètres

x Un pointeur vers une structure PHYSFS_Version à initialiser.

Signature de fonction pour les callbacks qui énumèrent des fichiers.

Avertissement

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de ces chaînes.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Plie" un point de code Unicode vers un équivalent en minuscules. (Ceci est pour un usage limité et avancé. Si vous ne voyez pas immédiatement l'utilité, vous pouvez probablement ignorer cela pour toujours.)

Ceci convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux sans équivalent en minuscules seront renvoyés sans modification.

Notez que vous pourriez obtenir plusieurs points de code en retour ! L'eszett allemand, par exemple, sera plié en deux points de code latins 's' en minuscules. La théorie est que si vous pliez deux chaînes, l'une avec un Eszett et l'autre avec "SS" vers le bas, elles correspondront.

Avertissement

Quiconque est étudiant de l'Unicode connaît le problème du "I turc". Cette API ne le gère pas. Supposez que cette une lettre dans tout l'Unicode sera pliée de manière plutôt incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la plupart de la planète, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Tampon pour stocker les valeurs de points de code pliés. Il doit pointer vers de l'espace pour au moins 3 emplacements de PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialise la bibliothèque PhysicsFS. Cela ferme tous les fichiers ouverts via PhysicsFS, efface les chemins de recherche/écriture, libère la mémoire et invalide tous vos handles de fichiers.

Notez que cet appel peut ÉCHOUEr s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en cache des écritures sur un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur a échoué, etc.). Il est généralement préférable de fermer tous les handles d'écriture vous-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois désinitialisé avec succès, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états par défaut de l'API sont restaurés à ce stade, à l'exception de tout allocateur personnalisé que vous pourriez avoir spécifié, qui survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les spécificités de l'erreur peuvent être obtenues à partir de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini et probablement très endommagé.

int PHYSFS_delete (const char * filename)

Supprime un fichier ou un répertoire. (filename) est spécifié dans une notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel ne puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, pas ce à quoi il pointe, que vous autorisiez ou non les symlinks.

Donc, si vous avez défini le répertoire d'écriture sur "C:\monjeu\rep_ecriture" et que vous appelez PHYSFS_delete("telechargements/cartes/niveau1.carte"), alors le fichier "C:\monjeu\rep_ecriture\telechargements\cartes\niveau1.carte" est supprimé du système de fichiers physique, s'il existe et si le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont un handle de fichier ouvert vers celui-ci (y compris votre programme) ne fermeront pas leurs handles.

Il est probable que les bits qui composent le fichier existent toujours, ils sont simplement rendus disponibles pour être écrasés à un moment ultérieur. Ne considérez pas cela comme une méthode de sécurité ou autre. :)

filename Nom du fichier à supprimer.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers d'un répertoire du chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis crée une liste avant de la retourner à l'application. La fonctionnalité est donc identique, à l'exception de la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons trouvé [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis dans aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une seule archive, nous ne pouvons pas garantir l'ordre dans lequel les données seront découvertes. Tout tri que vous trouverez dans ces rappels est purement un hasard. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers en double.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante ; il devait simplement ignorer des éléments ou arrêter l'énumération purement et simplement, et l'appelant ne saurait pas qu'il avait perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble de données complet, et sa fonction de rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur la façon dont votre fonction de rappel doit se comporter.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

Retourne

Non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel retourne PHYSFS_ENUM_STOP pour s'arrêter prématurément, cela sera considéré comme un succès. Les fonctions de rappel retournant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtient une liste de fichiers d'un répertoire du chemin de recherche.

Attention

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction retournait autant d'éléments que possible en cas de condition d'échec (manque de mémoire, erreur d'entrée/sortie disque, etc.). Comme cela empêchait les applications de distinguer un succès complet d'un échec partiel, et comme la fonction pouvait toujours retourner NULL pour signaler des échecs catastrophiques de toute façon, dans PhysicsFS 2.1, la politique de cette fonction a changé : elle retournera soit une liste de résultats complets, soit NULL en cas d'échec de quelque nature que ce soit, nous pouvons donc garantir que l'énumération s'est terminée et n'a pas de lacunes dans ses résultats.

Les répertoires correspondants sont interpolés. C'est-à-dire que si "C:\mydir" se trouve dans le chemin de recherche et contient un répertoire "savegames" qui contient "x.sav", "y.sav" et "z.sav", et qu'il y a aussi un répertoire "C:\userdir" dans le chemin de recherche qui a un sous-répertoire "savegames" avec "w.sav", alors le code suivant :

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Nous avons trouvé [%s].\n", *i);
PHYSFS_freeList(rc);
* Nous avons trouvé [x.sav].
* Nous avons trouvé [y.sav].
* Nous avons trouvé [z.sav].
* Nous avons trouvé [w.sav]..fi
N'hésitez pas à trier la liste comme vous le souhaitez. Cependant, les données retournées ne contiendront jamais de doublons et seront toujours triées par ordre alphabétique (ou plutôt : Unicode sensible à la casse) pour vous.
N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur de retour de cette fonction lorsque vous en avez terminé.

dir répertoire en notation indépendante de la plateforme à énumérer.

Tableau terminé par NULL de chaînes terminées par NULL, ou NULL en cas d'échec.

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Obtenir le chemin spécifique à l'utilisateur et à l'application où les fichiers peuvent être écrits. Fonction d'aide.

Obtenir le "répertoire des préférences". Il est destiné à être l'endroit où les utilisateurs peuvent écrire des fichiers personnels (préférences et sauvegardes, etc.) qui sont spécifiques à votre application. Ce répertoire est unique par utilisateur, par application.

Cette fonction déterminera l'emplacement approprié dans le système de fichiers natif, créera le répertoire si nécessaire, et retournera une chaîne en notation dépendante de la plateforme, adaptée à être passée à PHYSFS_setWriteDir().

Sous Windows, cela pourrait ressembler à : "C:\\Users\\bob\\AppData\\Roaming\\Ma Société\\Mon Nom de Programme"

Sous Linux, cela pourrait ressembler à : "/home/bob/.local/share/Mon Nom de Programme"

Sous Mac OS X, cela pourrait ressembler à : "/Users/bob/Library/Application Support/Mon Nom de Programme"

(etc.)

Vous devriez probablement utiliser le répertoire des préférences pour votre répertoire d'écriture, et aussi le placer près du début de votre chemin de recherche. Les anciennes versions de PhysicsFS ne proposaient que PHYSFS_getUserDir() et vous laissaient déterminer où devaient aller les fichiers sous cet arbre. Ceci trouve l'emplacement correct pour quelle que soit la plateforme, qui change non seulement entre les systèmes d'exploitation, mais aussi entre les versions du même système d'exploitation.

  • Essayez d'utiliser la même chaîne org (y compris la casse) pour toutes vos applications qui utilisent cette fonction.
  • Utilisez toujours une chaîne app unique pour chacune, et assurez-vous qu'elle ne change jamais pour une application une fois que vous l'avez choisie.
  • Les caractères Unicode sont légaux, tant qu'ils sont encodés en UTF-8, mais...
  • ...n'utilisez que des lettres, des chiffres et des espaces. Évitez la ponctuation comme "Nom du Jeu 2 : La Revanche du Méchant !"... "Nom du Jeu 2" est suffisant.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (transparentement) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné à la mise en bac à sable du langage de script d'un programme, au cas où des scripts non fiables essaieraient de compromettre le système. D'une manière générale, un utilisateur pourrait très bien avoir une raison légitime de créer un lien symbolique, donc à moins que vous ne ressentiez un danger spécifique à les autoriser, vous devriez les permettre.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission de lien symbolique peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour permettre les liens symboliques, zéro pour refuser les liens.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convertir un string Latin1 en un string UTF-8. Los strings Latin1 son de 8 bits por carácter: una codificación popular llamada "high ASCII".

Para asegurar que el buffer de destino sea lo suficientemente grande para la conversión, por favor asigna un buffer que sea el doble de grande que el buffer de origen. El UTF-8 expande los códigos Latin1 que son mayores a 127 de 1 a 2 bytes, por lo que el string podría crecer en algunos casos.

Los strings que no caben en el buffer de destino serán truncados, pero siempre estarán terminados por nulo y nunca tendrán una secuencia incompleta de UTF-8 al final. Si la longitud del buffer es 0, esta función no hace nada.

Nota: No se proporciona un conversor de UTF-8 a Latin1, ya que Latin1 no puede expresar muchos códigos Unicode. Es una codificación obsoleta; deberías alejarte de ella siempre.

src String Latin1 terminado por nulo.
dst Buffer para almacenar el string UTF-8 convertido.

Les chaînes UTF-16 utilisent 16 bits par caractère (sauf certains caractères, qui utilisent 32 bits) : TCHAR sous Windows, lors de la compilation avec le support Unicode. Les versions modernes de Windows utilisent UTF-16. Les versions de Windows antérieures à 2000 utilisaient TCHAR, mais ne supporteraient que UCS-2. UTF-16 *est* UCS-2, à l'exception des caractères qui font 4 octets, qui ne sont de toute façon pas représentables en UCS-2. Si vous n'êtes pas sûr, vous devriez utiliser UTF-16 à ce stade sous Windows.

Pour vous assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon de double taille par rapport au tampon source. UTF-8 utilise de un à quatre octets par caractère, mais UTF-16 utilise toujours deux à quatre, donc une chaîne entièrement en ASCII basique doublera de taille ! Les caractères UTF-16 qui nécessitent quatre octets prennent également quatre octets en UTF-8, vous n'avez donc pas besoin d'allouer 4x l'espace au cas où : le double suffira.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par null et ne contiendront jamais une paire de substitution UTF-16 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Paramètres

src Chaîne source terminée par null au format UTF-8.
dst Tampon pour stocker la chaîne UTF-16 convertie.
len Taille, en octets, du tampon de destination.

Écrit des données dans un descripteur de fichier PhysicsFS. Le fichier doit être ouvert en écriture.

Veuillez noter que bien que (len) soit un entier non signé de 64 bits, vous êtes limité à 63 bits (9223372036854775807 octets), nous pouvons donc renvoyer une valeur négative en cas d'erreur.
