Version Information

PHYSFS_VERSION

A macro that holds the version of the library you compiled against. This is determined by what header the compiler uses. Note that if you dynamically linked the library, you might have a slightly newer or older version at runtime. That version can be determined with PHYSFS_getLinkedVersion(), which, unlike PHYSFS_VERSION, is not a macro.

typedef void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

enum PHYSFS_ErrorCode

Values that represent specific causes of failure. Most of the time, you should only concern yourself with whether a given operation failed or not, but there may be occasions where you plan to handle a specific failure case gracefully, so we provide specific error codes.

Most of these errors are a little vague, and most aren't things you can fix...if there's a permission error, for example, all you can really do is pass that information on to the user and let them figure out how to handle it. In most these cases, your program should only care that it failed to accomplish its goals, and not care specifically why.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Plie" un point de code Unicode vers un équivalent en minuscules. (Ceci est pour une utilisation limitée et hardcore. Si vous ne voyez pas immédiatement un besoin pour cela, vous pouvez probablement l'ignorer pour toujours.)

Ceci convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et les points de code sans équivalent en minuscules seront renvoyés sans conversion.

Notez que vous pourriez obtenir plusieurs points de code en retour ! L'Eszett allemand, par exemple, sera plié en deux points de code latins minuscules en 's'. La théorie est que si vous pliez deux chaînes, l'une avec un Eszett et l'une avec "SS", elles correspondront.

Avertissement

Quiconque est étudiant en Unicode connaît le problème du "I turc". Cette API ne le gère pas. Supposons que cette seule lettre dans tout Unicode sera pliée de manière incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la plupart de la planète, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Tampon pour stocker les valeurs des points de code pliés. Ceci devrait pointer vers un espace pour au moins 3 emplacements PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialise la bibliothèque PhysicsFS. Ceci ferme tous les fichiers ouverts via PhysicsFS, vide les chemins de recherche/écriture, libère la mémoire et invalide toutes vos poignées de fichiers.

Notez que cet appel peut ÉCHOUMER s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures sur un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur a échoué, etc.). Il est généralement préférable de fermer toutes les poignées d'écriture vous-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois désinitialisé avec succès, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états par défaut de l'API sont restaurés à ce moment-là, à l'exception de tout allocateur personnalisé que vous auriez spécifié, qui survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les détails de l'erreur peuvent être obtenus à partir de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini et probablement très endommagé.

int PHYSFS_delete (const char * filename)

Supprime un fichier ou un répertoire. (filename) est spécifié dans une notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel ne puisse le supprimer.

La suppression d'un lien symbolique supprime le lien, et non ce à quoi il pointe, que vous ayez ou non activé "permitSymLinks".

Donc, si vous avez défini le répertoire d'écriture sur "C:\monjeu\repertoire_ecriture" et que vous appelez PHYSFS_delete("telechargements/cartes/niveau1.map"), alors le fichier "C:\monjeu\repertoire_ecriture\telechargements\cartes\niveau1.map" est supprimé du système de fichiers physique, s'il existe et que le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont une poignée de fichier ouverte dessus (y compris votre programme) ne fermeront pas leurs poignées.

Il y a de fortes chances que les bits qui composent le fichier existent toujours, ils sont juste rendus disponibles pour être écrasés plus tard. Ne considérez pas cela comme une méthode de sécurité ou quoi que ce soit. :)

Paramètres

filename Nom du fichier à supprimer.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_deregisterArchiver (const char * ext)

Supprime un archiveur du système. Si, pour une raison quelconque, vous n'avez besoin que de votre archiveur précédemment enregistré pour vivre pendant une partie de la durée de vie de votre application, vous pouvez le supprimer du système une fois que vous en avez terminé grâce à cette fonction.

Cela échoue s'il y a encore des archives ouvertes qui utilisent cet archiveur.

Cette fonction peut également supprimer les archiveurs fournis en interne, tels que le support .zip ou autre. Cela pourrait être utile dans certaines situations, comme désactiver complètement la prise en charge ou les remplacer par votre propre implémentation. Une fois qu'un archiveur interne est désactivé de cette manière, PhysicsFS ne fournit aucun mécanisme pour les récupérer, à part appeler PHYSFS_deinit() et PHYSFS_init() à nouveau.

PHYSFS_deinit() automatisera

ly déenregistrer tous archivistes, vous n'avez donc pas besoin de désenregistrer explicitement le vôtre si vous arrêtez proprement.

Paramètres

ext Extension de nom de fichier que l'archiviste gère.

Retourne

Zéro en cas d'erreur, non-zéro en cas de succès.

Cette forme signale ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons pas garantir l'ordre de découverte des données. Tout tri que vous trouvez dans ces rappels est purement de la chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers en double.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération directement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble de données complet, et son rappel a le contrôle s'il souhaite arrêter l'énumération plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement de votre rappel.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier vers lequel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné à la mise en bac à sable du langage de script d'un programme, au cas où des scripts non fiables essaieraient de compromettre le système. D'une manière générale, un utilisateur pourrait très bien avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Faire d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de limiter les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt, monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer la racine d'une archive à tout moment, modifiant l'arbre de fichiers interpolé (en fonction des chemins qui changent, une archive différente peut fournir divers fichiers). Il n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme racine d'une archive ; cependant, aucun fichier ne sera visible dans ce cas. void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convertit une chaîne Latin1 en chaîne UTF-8. Les chaînes Latin1 sont codées sur 8 bits par caractère : un encodage "high ASCII" populaire.

Pour garantir que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon dont la taille est le double de celle du tampon source. UTF-8 étend les points de code latin1 supérieurs à 127 de 1 à 2 octets, la chaîne peut donc augmenter dans certains cas.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Notez que nous ne fournissons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer la plupart des points de code Unicode. C'est un encodage hérité ; vous devriez toujours vous en éloigner.

Paramètres

src Chaîne source terminée par un caractère nul au format Latin1.
dst Tampon pour stocker la chaîne UTF-8 convertie.
len Taille, en octets, du tampon de destination.
