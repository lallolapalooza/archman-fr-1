typedef PHYSFS_EnumerateCallbackResult(* physFS_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Valeurs de retour possibles pour PHYSFS_EnumerateCallback. Signature de fonction pour les callbacks qui énumèrent et retournent des résultats.

Ces valeurs dictent si un callback d'énumération doit continuer à être déclenché, ou s'arrêter (et pourquoi il s'arrête).

PHYSFS_EnumerateCallback

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du callback : à savoir : si vous cherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être en ordre alphabétique par rapport à d'autres callbacks qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retours

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent des fichiers.

Attention

À partir de PhysicsFS 2.1, utilisez plutôt PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; il vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de ces chaînes.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le même dans les versions de callback. Consultez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous l'attendez et vous pourriez obtenir des chaînes en double.

Paramètres

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être en ordre alphabétique par rapport à d'autres callbacks qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

const char * PHYSFS_getLastError (void )

Obtient des informations d'erreur lisibles par l'homme.

Obsolète

Utilisez plutôt PHYSFS_getLastErrorCode() et PHYSFS_getErrorByCode().

Attention

Depuis PhysicsFS 2.1, cette fonction a été « enterrée ». Avant PhysicsFS 2.1, c'était la seule façon d'obtenir des détails d'erreur au-delà de la valeur de retour d'une fonction individuelle. C'était censé être un message lisible par l'homme dans l'une des nombreuses langues et pas utile pour l'analyse par les applications. C'était un problème, car le développeur ne choisissait pas la langue au moment de la compilation, et les mainteneurs de PhysicsFS devaient (mal) maintenir une grande quantité de travail de localisation. L'application ne pouvait pas analyser les messages, même si elle avait une langue spécifique, car certains étaient générés dynamiquement. Dans la version 2.1 et ultérieures, elle retourne toujours une chaîne statique en anglais ; vous pouvez l'utiliser comme clé de localisation dans votre propre système de localisation, car nous nous engageons à ne pas modifier les anciennes chaînes. De plus, si votre application souhaite examiner des erreurs spécifiques, nous proposons désormais une meilleure option : utilisez PHYSFS_getLastErrorCode().

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons est effectuée par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers chevauchant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer des versions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un endroit spécifique de l'arborescence des fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

(ptr) doit rester jusqu'à ce que l'archive soit démontée. void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné à isoler le langage de scripting d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne ressentiez un danger particulier à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors de la manipulation des noms de fichiers dans la notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés via cette fonction, PHYSFS_stat() les ignore, et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

Vous pouvez modifier la racine d'une archive à tout moment, ce qui modifiera l'arbre de fichiers interpolé (en fonction de l'endroit où les chemins changent, une archive différente peut fournir divers fichiers). Si vous définissez la racine sur NULL ou "/", l'archive sera traitée comme si aucune racine spéciale n'était définie (comme si l'archive était simplement montée normalement).

Le changement de racine n'affecte que les opérations futures sur les noms de chemins ; un fichier qui a été ouvert à partir d'un chemin qui a changé en raison d'un setRoot ne sera pas affecté.

La définition d'une nouvelle racine n'est pas limitée aux archives dans le chemin de recherche ; vous pouvez également en définir une sur le répertoire d'écriture, ce qui pourrait être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez donc pas changer le répertoire d'écriture pour le moment.

Ce n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme racine d'une archive ; cependant, aucun fichier ne sera visible dans ce cas. Si les répertoires manquants finissent par être créés (un mkdir sur le système de fichiers physique, etc.), cela sera reflété dans l'arbre interpolé.

Paramètres

archive répertoire/archive sur lequel changer la racine.
subdir nouveau sous-répertoire à faire de la racine de cette archive.

Retourne

non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

str1 chaîne à comparer.
str2 chaîne à comparer.

Retour

-1 si str1 est "plus petit" que str2, 1 si elle est "plus grande", 0 si elles sont égales.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a Latin1 string. Latin1 strings are 8-bits per character: a popular "high ASCII" encoding.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 expands latin1 codepoints over 127 from 1 to 2 bytes, so the string may grow in some cases.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-8 sequence at the end. If the buffer length is 0, this function does nothing.

Please note that we do not supply a UTF-8 to Latin1 converter, since Latin1 can't express most Unicode codepoints. It's a legacy encoding; you should be converting away from it at all times.

Parameters

src Null-terminated source string in Latin1 format.
dst Buffer to store converted UTF-8 string.
len Size, in bytes, of destination buffer.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. If you aren't sure, you should be using UTF-16 at this point on Windows.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
len Size, in bytes, of destination buffer.
