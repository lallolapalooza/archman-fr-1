Signature des fonctions de rappel qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() pour avoir plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, une entrée par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire des chaînes.

Ces rappels sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui retournent des listes devant être libérées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes à l'avance.

Notez que l'ordre promis dans les versions de liste n'est pas nécessairement le même dans les versions de rappel. Vous devriez examiner la documentation des API spécifiques, mais les chaînes ne sont pas nécessairement triées comme vous pourriez vous y attendre et vous pourriez obtenir des chaînes en double.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

« Plier » un point de code Unicode vers un équivalent en minuscules. (Ceci est pour un usage limité et avancé. Si vous ne voyez pas immédiatement l'utilité, vous pouvez probablement l'ignorer pour toujours.)

Ceci convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux sans équivalent en minuscules seront retournés sans conversion.

Notez que vous pourriez obtenir plusieurs points de code en retour ! L'Eszett allemand, par exemple, se pliera en deux points de code latins 's' en minuscules. La théorie est que si vous pliez deux chaînes, l'une avec un Eszett et l'autre avec « SS », elles correspondront.

Tous ceux qui ont étudié Unicode connaissent le problème de la « I turque ». Cette API ne le gère pas. Supposons que cette seule lettre de tout Unicode se pliera de manière incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la plupart des utilisateurs, mais la perfection est impossible.

to Tampon pour stocker les valeurs de points de code pliés. Ceci doit pointer vers un espace pour au moins 3 emplacements PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialiser la bibliothèque PhysicsFS. Cela ferme tous les fichiers ouverts via PhysicsFS, vide les chemins de recherche/écriture, libère la mémoire et invalide toutes vos poignées de fichiers.

Notez que cet appel peut ÉCHOIR s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures vers un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur a échoué, etc.). Il est généralement préférable de fermer toutes les poignées d'écriture vous-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois désinitialisé avec succès, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états par défaut de l'API sont restaurés à ce moment-là, à l'exception de tout allocateur personnalisé que vous auriez pu spécifier, qui survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les détails de l'erreur peuvent être obtenus à partir de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini et probablement très endommagé.

int PHYSFS_delete (const char * filename)

Supprimer un fichier ou un répertoire. (nom de fichier) est spécifié dans une notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, pas ce vers quoi il pointe, indépendamment du fait que vous ayez « autorisé les liens symboliques » ou non.

Donc, si vous avez défini le répertoire d'écriture sur « C:\mygame\writedir » et que vous appelez PHYSFS_delete (« downloads/maps/level1.map ») alors le fichier « C:\mygame\writedir\downloads\maps\level1.map » est supprimé du système de fichiers physique, s'il existe et si le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont une poignée de fichier ouverte vers celui-ci (y compris votre programme) ne fermeront pas leurs poignées.

Il est probable que les bits qui composent le fichier existent toujours, ils sont simplement rendus disponibles pour être écrasés ultérieurement. Ne considérez pas cela comme une méthode de sécurité ou quoi que ce soit. :)

Paramètres

filename Nom du fichier à supprimer.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Get a file listing of a search path's directory.

Warning

In PhysicsFS versions prior to 2.1, this function would return as many items as it could in the face of a failure condition (out of memory, disk i/o error, etc). Since this meant apps couldn't distinguish between complete success and partial failure, and since the function could always return NULL to report catastrophic failures anyway, in PhysicsFS 2.1 this function's policy changed: it will either return a list of complete results or it will return NULL for any failure of any kind, so we can guarantee that the enumeration ran to completion and has no gaps in its results.

Matching directories are interpolated. That is, if "C:\mydir" is in the search path and contains a directory "savegames" that contains "x.sav", "y.sav", and "z.sav", and there is also a "C:\userdir" in the search path that has a "savegames" subdirectory with "w.sav", then the following code:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);

* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..

Vous ne pouvez pas ajouter le même fichier à deux points de montage différents : la vérification des doublons se fait par rapport au fichier, et non par rapport au point de montage.

Lorsque vous montez un fichier, il est ajouté à un système de fichiers virtuel... tous les fichiers de tous les fichiers montés sont entrelacés dans un seul arbre de répertoires. Deux fichiers montés au même endroit (ou un fichier avec des fichiers qui chevauchent un point de montage) peuvent avoir des fichiers qui se chevauchent : dans ce cas, le fichier le plus ancien dans la liste de recherche est choisi, et les autres fichiers ne sont pas accessibles par l'application. Cela permet d'utiliser des fichiers pour remplacer les versions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des fichiers à un endroit spécifique dans l'arbre de répertoires et éviter les chevauchements ; c'est utile pour les modes téléchargeables qui peuvent écraser les données de l'application ou d'autres fichiers.

Ajoute une archive, contenue dans un descripteur PHYSFS_File, au chemin de recherche.

Attention

Sauf si vous avez un besoin spécifique et de bas niveau, vous devriez utiliser PHYSFS_mount() à la place de cette fonction.

Les archives dans les archives peuvent être très lentes ! Bien qu'un PHYSFS_File puisse se repositionner même lorsque les données sont compressées, il peut le faire en revenant au début et en décompressant tout avant le point de repositionnement. L'utilisation normale d'archives peut impliquer de nombreux repositionnements en arrière-plan. En tant que tel, vous pourriez trouver l'utilisation normale des archives extrêmement pénible si elles sont montées de cette façon. Prévoyez en conséquence : si vous avez, par exemple, un fichier .zip auto-extractible et que vous souhaitez y monter quelque chose, compressez le contenu de l'archive interne et assurez-vous que le fichier .zip externe ne compresse pas non plus l'archive interne.

Cette fonction opère de la même manière que PHYSFS_mount(), mais prend un descripteur PHYSFS_File au lieu d'un nom de chemin. Ce descripteur contient toutes les données de l'archive et est utilisé à la place d'un fichier réel dans le système de fichiers physique. Le PHYSFS_File peut être basé sur un fichier réel dans le système de fichiers physique, mais ce n'est pas nécessairement le cas. L'utilisation la plus courante est probablement de monter des archives stockées à l'intérieur d'autres archives.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (transparenmment) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné à l'isolation du langage de script d'un programme, au cas où des scripts non fiables essaieraient de compromettre le système. D'une manière générale, un utilisateur pourrait très bien avoir une raison légitime de créer un lien symbolique, donc à moins que vous ne sentiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lorsqu'il s'agit de noms de fichiers en notation indépendante de la plateforme. C'est-à-dire lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Convierte un subdirectorio de un archivo en su directorio raíz. Esto le permite acotar los archivos accesibles dentro de un archivo específico. Por ejemplo, si tiene x.zip con un archivo en y/z.txt, montado en /a, si llama a PHYSFS_setRoot("x.zip", "/y"), entonces la llamada a PHYSFS_openRead("/a/z.txt") tendrá éxito.

Puede cambiar el directorio raíz de un archivo en cualquier momento, alterando el árbol de archivos interpolado (dependiendo de dónde se desplacen las rutas, un archivo diferente podría proporcionar archivos diferentes). Establecer un nuevo directorio raíz no se limita a los archivos en el directorio de búsqueda; puede establecer uno en el directorio de escritura también, lo que podría ser útil si tiene archivos abiertos para escribir y no puede cambiar el directorio de escritura ahora.

archive El directorio/archivo en el que cambiar el directorio raíz.
subdir El nuevo subdirectorio que será el directorio raíz de este archivo.

Retorna

Distinto de cero si tiene éxito, cero en caso de error. Utilice PHYSFS_getLastErrorCode() para obtener el error específico.

  • Directorio base (PHYSFS_getBaseDir())
