Valeurs de retour possibles pour PHYSFS_EnumerateCallback. Signature de fonction pour les callbacks qui énumèrent et retournent des résultats.

Ces valeurs déterminent si un callback doit continuer ou s'arrêter (et pourquoi).

PHYSFS_EnumerateCallback

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il renvoie un résultat de callback : si vous recherchez quelque chose de spécifique, une fois trouvé, vous pouvez dire à PhysicsFS d'arrêter l'énumération. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir correctement acquis. :)

Paramètres

data pointeur vers un PHYSFS_Version à initialiser.
origdir chaîne contenant le chemin complet, en notation indépendante du système d'exploitation, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire pour lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname le nom du fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport à d'autres callbacks qui ont été appelés, et ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

PHYSFS_EnumerateCallbackResult

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent les fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() pour avoir plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, une entrée par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire de toute chaîne.

Ces callbacks sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui retournent des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes à l'avance.

Notez que l'ordre promis dans les versions de liste n'est pas nécessairement respecté dans les versions de callback. Vérifiez la documentation des API spécifiques, mais les chaînes ne seront pas nécessairement triées comme prévu et vous pourriez obtenir des chaînes en double.

Paramètres

data pointeur vers des données définies par l'utilisateur, passé via l'API qui a finalement appelé le callback.
origdir chaîne contenant le chemin complet, en notation indépendante du système d'exploitation, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire pour lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname le nom du fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport à d'autres callbacks qui ont été appelés, et ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

### Section: `char ** PHYSFS_enumerateFiles_(const_char_*_dir)`

Avertissement

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction renvoyait autant d'éléments que possible en cas d'erreur (même espace mémoire, erreur d'E/S disque, etc.). Par conséquent, les applications ne pouvaient pas faire la distinction entre un succès complet et un échec partiel. De plus, la fonction pouvait toujours retourner `NULL` pour signaler des échecs catastrophiques. Dans PhysicsFS 2.1, la politique de cette fonction a changé : elle renverra une liste complète de résultats ou `NULL` en cas d'erreur, garantissant que l'énumération est effectuée sans interruption.

Les répertoires correspondants sont interpolés. C'est-à-dire que si `C:\mydir` est dans le chemin de recherche et contient un répertoire `savegames` qui contient `x.sav`, `y.sav` et `z.sav`, et qu'il existe également un répertoire `C:\userdir` dans le chemin de recherche qui possède un sous-répertoire `savegames` avec `w.sav`, le code suivant :

char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
 * We've got [x.sav].
 * We've got [y.sav].
 * We've got [z.sav].
 * We've got [w.sav].

Obtenir le chemin d'écriture spécifique à l'utilisateur et à l'application. Fonction d'aide.

Obtenir le "pref dir". C'est une notion qui doit être utilisé pour écrire des fichiers spécifiques à votre application (préférences et sauvegardes de jeux, etc). Ce dossier est unique par utilisateur et par application.

Sur Linux, cela peut ressembler à : "/home/bob/.local/share/My Program Name"

Sur Mac OS X, cela peut ressembler à : "/Users/bob/Library/Application Support/My Program Name"

(etc.)

Vous devriez probablement utiliser ce chemin d'écriture pour votre dossier d'écriture, et aussi le placer au début de votre liste de recherche. int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añadir un directorio o archivo a la ruta de búsqueda. Si es un duplicado, el registro no se agrega de nuevo, incluso si el función éxito. No puedes agregar el mismo archivo a dos puntos de montaje diferentes: el control de duplicado se hace contra el archivo y no contra el punto de montaje.

Al montar un directorio, se lo agrega a un sistema de archivos virtual... todos los archivos de todos los directorios montados se interpolan en una única arborescencia jerárquica. Dos directorios montados en el mismo lugar (o un directorio con archivos que sobreponen un punto de montaje) pueden tener archivos sobreponiéndose: en ese caso, el archivo más cercano en la ruta de búsqueda se selecciona, y los otros archivos no son accesibles por la aplicación. El punto de montaje no necesita existir antes de montar, lo cual es diferente de lo que se espera en el concepto Unix de "montar" de los usuarios familiarizados. void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et architectures contiennent des fichiers qui ne sont que des références à d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, celui-ci ouvrira de manière transparente le fichier auquel il fait référence.

Par défaut, PhysicsFS vérifiera si un fichier est réellement un lien symbolique lors des appels d'ouverture et échouera si c'est le cas. Sinon, le lien pourrait vous emmener en dehors des chemins de lecture et d'écriture, compromettant la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Notez que ceci est davantage destiné au sandboxing des langages de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. En général, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, vous ne devriez donc pas les désactiver, à moins que vous ne sentiez qu'il existe un danger spécifique.

Les liens symboliques ne sont explicitement vérifiés que lorsque des noms de fichiers sont gérés dans une notation indépendante de la plateforme. C'est-à-dire que lorsque vous configurez vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignorera et traitera la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désactiver le lien.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Fait d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de réduire les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt, monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer la racine d'une archive à tout moment, en modifiant l'arbre de fichiers interpolé (en fonction de l'endroit où les chemins changent, une archive différente peut fournir divers fichiers). Si vous définissez la racine sur NULL ou "/", l'archive sera traitée comme si aucune racine spéciale n'était définie (comme si l'archive était simplement montée normalement).

Le changement de racine n'affecte que les opérations futures sur les noms de chemins ; un fichier qui était ouvert à partir d'un chemin qui a changé en raison d'un setRoot ne sera pas affecté.

La définition d'une nouvelle racine ne se limite pas aux archives du chemin de recherche ; vous pouvez également en définir une sur le répertoire d'écriture, ce qui peut être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez donc pas changer le répertoire d'écriture pour le moment.

Ce n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme racine d'une archive ; cependant, aucun fichier ne sera visible dans ce cas. Si les répertoires manquants finissent par être créés (un mkdir vers le système de fichiers physique, etc.), cela se reflétera dans l'arbre interpolé.

Paramètres

archive répertoire/archive dont on change la racine.
subdir nouveau sous-répertoire à faire devenir la racine de cette archive.

Retourne

une valeur non nulle en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. If you aren't sure, you should be using UTF-16 at this point on Windows.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
