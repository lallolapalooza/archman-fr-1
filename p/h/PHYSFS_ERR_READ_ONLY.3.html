typedef void(*physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent des fichiers.

Attention

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() pour avoir plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, une entrée par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire des chaînes.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui renvoient des listes qui doivent être libérées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes par la suite.

Notez que l'ordre promis dans les versions de liste n'est pas nécessairement respecté dans les versions de callback. Vérifiez la documentation des API spécifiques, mais les chaînes ne sont pas nécessairement triées comme vous pourriez vous y attendre et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data pointeur vers des données définies par l'utilisateur, passé par le biais de l'API qui a finalement appelé le callback.
origdir chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire dans lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname le nom du fichier en cours d'énumération. Il peut ne pas être dans l'ordre alphabétique par rapport à d'autres callbacks qui ont été appelés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retour

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Récupère une liste de fichiers à partir d'un chemin de recherche, en utilisant une fonction de rappel définie par l'utilisateur, avec des erreurs signalées. Interne, PHYSFS_enumerateFiles() appelle cette fonction puis construit une liste avant de la renvoyer à l'application, donc la fonctionnalité est identique, sauf la façon dont l'information est présentée à l'application.

Différent de PHYSFS_enumerateFiles(), cette fonction ne renvoie pas un tableau. Au lieu de cela, elle appelle une fonction définie par l'application une fois pour chaque élément dans le chemin de recherche :

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donne-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont pas garantis dans un ordre spécifique. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit l'ordre alphabétique. Cette forme renvoie ce qui est trouvé dans chaque architecture avant de passer à la suivante. Même au sein d'une seule architecture, je ne peux pas garantir l'ordre dans lequel les données seront découvertes. Tout ordre que vous trouverez dans ces rappels est une pure coïncidence. Ne comptez pas dessus. Comme cela parcourt toute la liste des architectures, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les fonctions de rappel elles-mêmes peuvent signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même si elles ne recherchaient qu'un élément spécifique et voulaient s'arrêter après cela, ou s'il y avait une erreur grave et qu'elles ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque, etc.), il ne pouvait pas le signaler à l'application, il pouvait simplement sauter des éléments ou arrêter complètement l'énumération, et l'appelant ne saurait pas qu'il avait perdu des données en cours de route.

Maintenant, l'appelant peut être assuré qu'il a obtenu un ensemble complet de données, et sa fonction de rappel peut contrôler si l'énumération s'arrête tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur la façon dont votre fonction de rappel doit se comporter.

dir Le répertoire à énumérer, en notation indépendante du système d'exploitation.
c La fonction de rappel à notifier des éléments du chemin de recherche.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

Retourne

Non nul en cas de succès, nul en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Les fonctions de rappel renvoyant PHYSFS_ENUM_ERROR feront que cette fonction renvoie nul et définira le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et architectures contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, le fichier auquel il pointe sera ouvert de manière transparente.

Par défaut, PhysicsFS vérifiera si un fichier est réellement un lien symbolique lors des appels d'ouverture et échouera si c'est le cas. Sinon, le lien pourrait vous faire sortir des chemins de lecture et d'écriture, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Notez que ceci est davantage destiné au sandboxing des langages de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. En général, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas le désactiver à moins de ressentir un danger spécifique.

Les liens symboliques ne seront explicitement visibles que lorsque vous travaillerez avec des noms de fichiers dans une notation non indépendante de la plateforme. Autrement dit, lorsque vous définissez vos chemins de recherche et d'écriture, etc., les liens symboliques ne seront jamais visibles.

Remarque : PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignorera et traitera la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désactiver le lien.

int PHYSFS_setBuffer(PHYSFS_File *handle, unsigned int bufsize)

Define a buffer for a file handle. This is used to make file I/O faster by reducing the number of system calls made.

If the buffer is set to a non-zero size, PhysicsFS will attempt to allocate a buffer of that size. If it fails, it will try to allocate a smaller buffer until it succeeds, or until it runs out of memory. If it fails to allocate any memory, the file will be unbuffered.

If the buffer is set to zero, any existing buffer will be freed. This effectively makes the file handle unbuffered.

Flushing a buffer is implicit when reading or seeking. Changing the buffer size implicitly causes a flush...check your return values!

Seeking, etc transparently accounts for buffering.

You can resize an existing buffer by calling this function more than once on the same file. Setting the buffer size to zero will free an existing buffer.

PhysicsFS file handles are unbuffered by default.

Please check the return value of this function! Failures can include not being able to seek backwards in a read-only file when removing the buffer, not being able to allocate the buffer, and not being able to flush the buffer to disk, among other unexpected problems.

handle handle returned from PHYSFS_open*().
bufsize size, in bytes, of buffer to allocate.

Returns

nonzero if successful, zero on error.

Si les deux strings sont exclusivement des caractères ASCII bas, cela fonctionnera correctement, car c'est aussi un UTF-8 valide. S'il y a des caractères ASCII élevés, cela ne fera pas ce que vous attendez !

Elle indiquera lequel des strings est "supérieur à" l'autre, mais vous devez être conscient que cela ne signifie pas nécessairement quelque chose : 'a' peut être "inférieur à" 'b', mais un kuten japonais n'a pas de relation alphabétique significative avec un lambda grec, mais la capacité d'attribuer une valeur "fiable" rend les algorithmes de tri possibles, même s'ils ne sont pas complètement rationnels. La plupart des cas devraient traiter la valeur de retour comme "égal" ou "non égal".

Comme stricmp, elle attend que les deux strings soient terminés par un caractère nul.

Paramètres

str1 Premier string à comparer.
str2 Deuxième string à comparer.

Retour

-1 si str1 est "inférieur à" str2, 1 s'il est "supérieur à", 0 s'ils sont égaux.

Convertir un string UTF-8 en un string UCS-2.

Avertissement

Vous devriez presque certainement utiliser PHYSFS_utf8ToUtf16(), qui est devenu disponible dans PhysicsFS 2.1, à moins de savoir ce que vous faites.

void PHYSFS_utf8ToUcs4 (const char * src, PHYSFS_uint32 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to UCS-4 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UCS-4 strings are 32-bits per character. They are the same as UTF-8 strings, except that UTF-8 strings use one to four bytes per character, and UCS-4 strings use exactly four bytes per character.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is four times the size of the source buffer. UTF-8 uses from one to four bytes per character, but UCS-4 always uses four bytes per character. So an entirely low-ASCII string will quadruple in size!

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UCS-4 sequence at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UCS-4 string.
len Size, in bytes, of destination buffer.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. If you aren't sure, you should be using UTF-16 at this point on Windows.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
len Size, in bytes, of destination buffer.
