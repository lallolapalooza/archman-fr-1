PHYSFS_EnumerateCallback

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il renvoie un résultat de rappel : si vous recherchez quelque chose de spécifique, une fois qu'il est trouvé, vous pouvez dire à PhysicsFS d'arrêter l'énumération. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons que vous avez correctement obtenu.

Paramètres

data pointeur vers une PHYSFS_Version à initialiser.
origdir chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire dans lequel vous avez demandé l'énumération, transmis dans le rappel pour votre commodité.
fname le nom du fichier qui est énuméré. Il n'est pas nécessairement en ordre alphabétique par rapport aux autres rappels qui ont été lancés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

PHYSFS_EnumerateCallbackResult

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonctions de rappel qui énumèrent des fichiers.

Attention

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() pour avoir plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, une entrée de fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire des chaînes.

Ces rappels sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui renvoient des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes à l'avance.

Notez que le tri des données promis dans les versions de liste ne se respecte pas nécessairement dans les versions de rappel. Vérifiez la documentation des API spécifiques, mais les chaînes ne sont pas nécessairement triées comme vous vous y attendriez et vous pourriez obtenir des chaînes en double.

Paramètres

data pointeur vers des données définies par l'utilisateur, passé via l'API qui a finalement appelé le rappel.
origdir chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire dans lequel vous avez demandé l'énumération, transmis dans le rappel pour votre commodité.
fname le nom du fichier qui est énuméré. Il n'est pas nécessairement en ordre alphabétique par rapport aux autres rappels qui ont été lancés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

enum PHYSFS_ErrorCode

Valeurs représentant des causes spécifiques d'échec. La plupart du temps, vous ne devriez vous soucier que de savoir si une opération a échoué ou non, mais il y a des cas où vous prévoyez de gérer gracieusement une situation d'erreur spécifique, c'est pourquoi nous fournissons des codes d'erreur spécifiques.

La plupart de ces erreurs sont un peu vagues et ne sont pas toujours des choses que vous pouvez corriger... par exemple, s'il y a une erreur de permission, la seule chose que vous pouvez faire est de transmettre cette information à l'utilisateur et de laisser l'utilisateur gérer comment le résoudre. Dans la plupart de ces cas, votre programme ne devrait que se soucier qu'il n'a pas réussi à atteindre ses objectifs, et non se soucier spécifiquement de pourquoi.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers d'un répertoire d'un chemin de recherche, en utilisant un callback défini par l'application, avec des erreurs signalées. En interne, PHYSFS_enumerateFiles() n'appelle que cette fonction, puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique, sauf la manière dont les informations sont présentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Elle appelle plutôt une fonction spécifiée par l'application une fois pour chaque élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donne-moi plus de données, s'il te plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés au callback ne sont garantis d'être dans aucun ordre spécifique. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit l'ordre alphabétique. Cette forme rapporte ce qui se trouve dans chaque fichier d'archive avant de passer au suivant. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout tri que vous trouvez dans ces callbacks n'est que de la pure chance. N'y comptez pas. Comme cela parcourt toute la liste des fichiers, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les callbacks eux-mêmes peuvent signaler des erreurs. Avant cette API, les callbacks devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'un élément spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient en alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement sauter des éléments ou arrêter complètement l'énumération, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être assuré d'avoir obtenu un ensemble complet de données, et s'il souhaite arrêter l'énumération prématurément, son callback aura le contrôle. Voir la documentation de PHYSFS_EnumerateCallback pour plus de détails sur le comportement attendu de votre callback.

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin.
d Données définies par l'application passées au callback. Peut être NULL.

Valeur de retour

Non nul en cas de succès, nul en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le callback renvoie PHYSFS_ENUM_STOP pour s'arrêter prématurément, cela sera considéré comme un succès. Les callbacks renvoyant PHYSFS_ENUM_ERROR feront que cette fonction renverra zéro et définira le code d'erreur comme PHYSFS_ERR_APP_CALLBACK.

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Get the user-and-app-specific path where files can be written. Helper function.

Get the "pref dir". This is meant to be where users can write personal files (preferences and save games, etc) that are specific to your application. This directory is unique per user, per application.

This function will decide the appropriate location in the native filesystem, create the directory if necessary, and return a string in platform-dependent notation, suitable for passing to PHYSFS_setWriteDir().

On Windows, this might look like: "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name"

On Linux, this might look like: "/home/bob/.local/share/My Program Name"

On Mac OS X, this might look like: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

You should probably use the pref dir for your write dir, and also put it near the beginning of your search path. Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left you to figure out where the files should go under that tree. This finds the correct location for whatever platform, which not only changes between operating systems, but also versions of the same operating system.

You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might do) and the name of your application. These should be proper names.

Both the (org) and (app) strings may become part of a directory name, so please follow these rules:

  • Try to use the same org string (including case-sensitivity) for all your applications that use this function.
  • Always use a unique app string for each one, and make sure it never changes for an app once you've decided on it.
  • Unicode characters are legal, as long as it's UTF-8 encoded, but...
  • ...only use letters, numbers, and spaces. Avoid punctuation like "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" is sufficient.

The pointer returned by this function remains valid until you call this function again, or call PHYSFS_deinit(). This is not necessarily a fast call, though, so you should call this once at startup and copy the string if you need it.

You should assume the path returned by this function is the only safe place to write files (and that PHYSFS_getUserDir() and PHYSFS_getBaseDir(), while they might be writable, or even parents of the returned path, aren't where you should be writing things).

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, ouvrir un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné à la mise en quarantaine du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. De manière générale, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers dans la notation indépendante de la plate-forme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans tous les cas pas suivi. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convertit une chaîne UTF-8 en une chaîne Latin1. Les chaînes Latin1 sont codées sur 8 bits par caractère : un encodage "ASCII élevé" populaire.

Pour s'assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon de double taille par rapport au tampon source. UTF-8 développe les points de code Latin1 supérieurs à 127 de 1 à 2 octets, la chaîne peut donc s'agrandir dans certains cas.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Veuillez noter que nous ne fournissons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer la plupart des points de code Unicode. C'est un encodage hérité ; vous devriez toujours vous en éloigner.

Paramètres

src Chaîne source terminée par un caractère nul au format Latin1.
dst Tampon pour stocker la chaîne UTF-8 convertie.
len Taille, en octets, du tampon de destination.

NAME

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 - write values in specific byte orders.

SYNOPSIS

int **PHYSFS_writeUBE16** (PHYSFS_File *file, PHYSFS_uint16 val)

int **PHYSFS_writeUBE32** (PHYSFS_File *file, PHYSFS_uint32 val)

int **PHYSFS_writeUBE64** (PHYSFS_File *file, PHYSFS_uint64 val)

int **PHYSFS_writeULE16** (PHYSFS_File *file, PHYSFS_uint16 val)

int **PHYSFS_writeULE32** (PHYSFS_File *file, PHYSFS_uint32 val)

int **PHYSFS_writeULE64** (PHYSFS_File *file, PHYSFS_uint64 val)

DESCRIPTION

These functions convert an unsigned integer from the platform's native byte order to the specified endianness (big-endian or little-endian) and write it to a file.

These are convenience functions. They will be slightly less efficient than writing the value directly, but they save you from having to do the byte swapping yourself.

PARAMETERS

file
A pointer to the PHYSFS_File object to write to.
val
The unsigned integer value to write.

RETURN VALUE

On success, these functions return a non-zero value. On failure, they return zero, and you can find out what went wrong from PHYSFS_getLastErrorCode().

Warning

Remember, PHYSFS_uint64 is only 32 bits on platforms without any sort of 64-bit support.
