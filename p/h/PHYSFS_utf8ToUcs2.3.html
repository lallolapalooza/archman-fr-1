Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() pour avoir plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, une entrée par callback. Toutes les chaînes sont au format UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire des chaînes.

Ces callbacks sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui renvoient des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes à l'avance.

Vous devez être conscient que l'ordre promis dans les versions de liste n'est pas nécessairement le cas dans les versions de callback. Vérifiez la documentation spécifique des API, mais les chaînes peuvent ne pas être triées comme vous l'attendez et vous pourriez obtenir des chaînes en double.

origdir chaîne contenant le chemin complet, en notation indépendante du système d'exploitation, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname nom du fichier en cours d'énumération. Il peut ne pas être trié par ordre alphabétique par rapport à d'autres callbacks qui ont été appelés, et ne contiendra pas le chemin complet. int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Plie" un point de code Unicode vers un équivalent en minuscules. (Ceci est pour une utilisation limitée et intensive. Si vous ne voyez pas immédiatement un besoin pour cela, vous pouvez probablement ignorer ceci pour toujours.)

Ceci convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux qui n'ont pas d'équivalent en minuscules seront retournés sans conversion.

Notez que vous pourriez obtenir plusieurs points de code en retour ! Le Eszett allemand, par exemple, sera plié en deux points de code latins minuscules 's'. La théorie est que si vous pliez deux chaînes, l'une avec un Eszett et l'autre avec "SS", elles correspondront.

Attention

Quiconque est étudiant en Unicode connaît le problème de "l'I turc". Cette API ne le gère pas. Supposons que cette seule lettre dans tout Unicode sera pliée de manière un peu incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la majeure partie de la planète, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Tampon pour stocker les valeurs des points de code pliés. Ceci devrait pointer vers un espace pour au moins 3 emplacements de type PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialise la bibliothèque PhysicsFS. Ceci ferme tous les fichiers ouverts via PhysicsFS, efface les chemins de recherche/écriture, libère la mémoire et invalide tous vos descripteurs de fichiers.

Notez que cet appel peut ÉCHOUEE s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures sur un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur a échoué, etc.). Il est généralement préférable de fermer tous les descripteurs d'écriture soi-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois correctement désinitialisé, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états par défaut de l'API sont restaurés à ce moment-là, à l'exception de tout allocateur personnalisé que vous auriez spécifié, qui survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les détails de l'erreur peuvent être obtenus à partir de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini et probablement gravement compromis.

int PHYSFS_delete (const char * filename)

Supprime un fichier ou un répertoire. (filename) est spécifié dans une notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel puisse le supprimer.

La suppression d'un lien symbolique supprime le lien, et non ce vers quoi il pointe, que vous ayez ou non autorisé les symlinks ("permitSymLinks").

Donc, si vous avez défini le répertoire d'écriture à "C:\monjeu\repd'ecriture" et appelez PHYSFS_delete("telechargements/cartes/niveau1.map") alors le fichier "C:\monjeu\repd'ecriture\telechargements\cartes\niveau1.map" est supprimé du système de fichiers physique, s'il existe et si le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont un descripteur de fichier ouvert pour celui-ci (y compris votre programme) ne fermeront pas leurs descripteurs.

Il y a de fortes chances que les bits qui composent le fichier existent toujours, ils sont juste rendus disponibles pour être écrasés plus tard. Ne considérez pas cela comme une méthode de sécurité ou quoi que ce soit. :)

Paramètres

filename Nom du fichier à supprimer.

Retourne

  • Essayez d'utiliser la même chaîne d'organisation (y compris la casse) pour toutes vos applications qui utilisent cette fonction.
  • Utilisez toujours une chaîne unique pour chaque application, et assurez-vous qu'elle ne change pas pour une application une fois que vous avez choisi la chaîne.
  • Les caractères Unicode sont valides, tant qu'ils sont encodés en UTF-8, mais...
  • ...utilisez uniquement des lettres, des chiffres et des espaces. Évitez d'utiliser des caractères tels que « Game Name 2: Bad Guy's Revenge! » ... « Game Name 2 » est suffisant.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

void PHYSFS_permitSymbolicLinks(int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (transparentement) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné au sandboxing du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. De manière générale, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, donc à moins que vous ne sentiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore, et traiterait la requête comme si le chemin n'existait pas du tout.

La permission de lien symbolique peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser les liens.

int PHYSFS_setRoot (const char * archive, const char * subdir)

  • Le répertoire de base (PHYSFS_getBaseDir())

Toutes les archives sont montées à la racine du système de fichiers virtuel ("/")

Spécifiez NULL pour ne pas rechercher automatiquement les archives. Vous pourriez vouloir spécifier zéro et gérer vous-même la configuration du disque.
archivesFirst Non nul pour préfixer les archives au chemin de recherche. Zéro pour les ajouter. Ignoré si !(archiveExt).

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convertit une chaîne Latin1 en une chaîne UTF-8. Les chaînes Latin1 sont codées sur 8 bits par caractère : un encodage populaire de "high ASCII".

Pour s'assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon de taille double de celle du tampon source. UTF-8 étend les points de code latin1 supérieurs à 127 de 1 à 2 octets, donc la chaîne peut grossir dans certains cas.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Veuillez noter que nous ne fournissons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer la plupart des points de code Unicode. C'est un encodage hérité ; vous devriez toujours vous en éloigner.

Paramètres

src Chaîne source terminée par un caractère nul au format Latin1.
dst Tampon pour stocker la chaîne UTF-8 convertie.
len Taille, en octets, du tampon de destination.

str1 Première chaîne à comparer.

Retourne

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. If you aren't sure, you should be using UTF-16 at this point on Windows.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
len Size, in bytes, of destination buffer.
