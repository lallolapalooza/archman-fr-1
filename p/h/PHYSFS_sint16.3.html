PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf que vous renvoyez un résultat depuis le callback : si vous cherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter l'énumération. typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent les fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; cela vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, une entrée par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de toute chaîne.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui renvoient des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes au début.

Vous devez être conscient que le tri des données promis dans les versions de liste n'est pas nécessairement vrai dans les versions de callback. Voir la documentation spécifique des API, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez recevoir des doublons.

Paramètres

data pointeur vers des données définies par l'utilisateur, passé via l'API qui a finalement appelé le callback.
origdir chaîne avec le chemin complet, en notation indépendante du système d'exploitation, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire pour lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname nom du fichier en cours d'énumération. Il peut ne pas être dans l'ordre alphabétique par rapport à d'autres callbacks qui ont été appelés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

PHYSFS_ENUM_OK

enum PHYSFS_ErrorCode

Valeurs représentant des causes spécifiques d'échec. Bien que la plupart du temps vous ne devriez vous soucier que de savoir si une opération a échoué, il y a des cas où vous prévoyez de gérer gracieusement une situation d'erreur spécifique, c'est pourquoi nous proposons des codes d'erreur spécifiques.

La plupart de ces erreurs sont un peu vagues et ne sont pas toujours des choses que vous pouvez corriger... s'il y a une erreur de permission, par exemple, la seule chose que vous pouvez faire est de transmettre cette information à l'utilisateur et de le laisser trouver par lui-même comment la gérer. Dans la plupart des cas, votre programme ne devrait se soucier que du fait qu'il n'a pas réussi à atteindre ses objectifs, et non spécifiquement pourquoi.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers d'un répertoire du chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de la renvoyer à l'application, de sorte que la fonctionnalité est identique, sauf la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas un tableau. Elle appelle plutôt une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis dans aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale tout ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une seule archive, nous ne pouvons pas garantir l'ordre de découverte des données. Tout tri que vous trouvez dans ces rappels est purement de la chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers en double.

Cette API et les fonctions de rappel elles-mêmes sont capables de signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même si elles ne recherchaient qu'une chose spécifique et souhaitaient s'arrêter après cela, ou avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble de données complet, et sa fonction de rappel a le contrôle s'il souhaite arrêter l'énumération plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour plus de détails sur le comportement de votre fonction de rappel.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

Retourne

non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel renvoie PHYSFS_ENUM_STOP pour arrêter tôt, cela sera considéré comme un succès. Les fonctions de rappel renvoyant PHYSFS_ENUM_ERROR feront que cette fonction retournera zéro et définira le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtenir une liste de fichiers d'un répertoire du chemin de recherche.

Attention

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction renvoyait autant d'éléments que possible face à une condition d'échec (manque de mémoire, erreur d'entrée/sortie disque, etc.). Comme cela empêchait les applications de distinguer un succès complet d'un échec partiel, et comme la fonction pouvait toujours renvoyer NULL pour signaler des échecs catastrophiques de toute façon, dans PhysicsFS 2.1, la politique de cette fonction a changé : elle renverra soit une liste de résultats complets, soit NULL pour tout échec, afin que nous puissions garantir que l'énumération s'est terminée et qu'il n'y a pas de lacunes dans ses résultats.

Les répertoires correspondants sont interpolés. C'est-à-dire que si "C:\mydir" se trouve dans le chemin de recherche et contient un répertoire "savegames" qui contient "x.sav", "y.sav" et "z.sav", et qu'il y a également un "C:\userdir" dans le chemin de recherche qui a un sous-répertoire "savegames" avec "w.sav", alors le code suivant :

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Nous avons [%s].\n", *i);
PHYSFS_freeList(rc);
* Nous avons [x.sav].
* Nous avons [y.sav].
* Nous avons [z.sav].
* Nous avons [w.sav]..fi
N'hésitez pas à trier la liste comme vous le souhaitez. Cependant, les données renvoyées ne contiendront jamais de doublons et seront toujours triées par ordre alphabétique (ou plutôt : insensible à la casse Unicode) pour vous.
N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur de retour de cette fonction lorsque vous avez terminé.
Paramètres
dir répertoire en notation indépendante de la plateforme à énumérer.

Tableau terminé par NULL de chaînes terminées par NULL, ou NULL en cas d'échec.

const char * PHYSFS_getLastError (void )

Obtenir des informations d'erreur lisibles par l'homme.

Obsolète

Utilisez plutôt PHYSFS_getLastErrorCode() et PHYSFS_getErrorByCode().

Avertissement

Depuis PhysicsFS 2.1, cette fonction a été dépréciée. Avant PhysicsFS 2.1, c'était la seule façon d'obtenir des détails d'erreur en dehors de la valeur de retour de base d'une fonction. Elle était censée être une chaîne lisible par l'homme dans plusieurs langues, mais n'était pas utile pour l'analyse par les applications. C'était un problème, car le développeur, et non l'utilisateur, sélectionnait la langue au moment de la compilation, et les mainteneurs de PhysicsFS devaient (maladroitement) maintenir une grande quantité de travail de localisation. L'application ne pouvait pas analyser les chaînes, même si elles étaient dans une langue spécifique, car certaines étaient générées dynamiquement. const char *physFS_getPrefDir (const char * org, const char * app)

Obtener la ruta de directorio específica para escribir archivos. Función de ayuda.

Obtener el "pref dir". Este es para que los usuarios puedan escribir archivos personales (preferencias y juegos salvados, etc) específicos de tu aplicación. Este directorio es único por usuario y por aplicación.

Esta función decidirá la ubicación adecuada en el sistema de archivos nativo, creará el directorio si es necesario y devolverá una cadena en notación de plataforma adecuada para pasar a PHYSFS_setWriteDir().

En Windows, podría parecer: "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name"

En Linux, podría parecer: "/home/bob/.local/share/My Program Name"

En Mac OS X, podría parecer: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

Tú deberías usar la ruta de directorio de pref para tu ruta de escritura, y también colócalo cerca del principio de tu lista de búsqueda. Versiones antiguas de PhysicsFS ofrecían solo PHYSFS_getUserDir() y dejaban que tú decidieras dónde poner los archivos bajo esa carpeta. Esta encuentra la ubicación correcta para cualquier plataforma, que no solo cambia entre sistemas operativos, sino también entre versiones del mismo sistema operativo.

Específicamente, especifica el nombre de tu organización (si no es una organización real, tu nombre o un dominio de internet que posees podría hacerlo), y el nombre de tu aplicación. Estos deberían ser nombres adecuados.

  • Intenta usar el mismo string de organización (incluso la sensibilidad de mayúsculas) para todas tus aplicaciones que usen esta función.
  • Usa siempre un string único de aplicación para cada una, y asegúrate de que no cambie para una aplicación una vez que hayas decidido usarlo.
  • Caracteres Unicode son válidos, siempre que estén codificados en UTF-8, pero...
  • ... úsalo solo letras, números y espacios. Evita caracteres como "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" es suficiente.

El puntero devuelto por esta función permanece válido hasta que lo llames nuevamente o llames PHYSFS_deinit(). Aunque no es rápido, deberías llamarlo una vez al inicio y copiar la cadena si la necesitas.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons est effectuée par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers se chevauchant avec un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser les archives pour remplacer les versions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer les archives à un point spécifique de l'arborescence des fichiers et empêcher les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept Unix de "montage" pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

Spécifier un lien symbolique vers une archive ou un répertoire est autorisé ici, quel que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne concerne que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

Ajouter une archive, contenue dans un descripteur PHYSFS_File, au chemin de recherche.

Avertissement

À moins d'avoir un besoin spécial de bas niveau, vous devriez utiliser PHYSFS_mount() à la place.

Les archives dans les archives peuvent être très lentes ! Bien qu'un PHYSFS_File puisse effectuer une recherche même lorsque les données sont compressées, il peut le faire en revenant au début et en décompressant tout avant le point de recherche. L'utilisation normale des archives peut effectuer de nombreuses recherches en arrière-plan. En tant que tel, vous pourriez trouver l'utilisation normale des archives extrêmement pénible si elles sont montées de cette manière. Prévoyez en conséquence : si vous avez, par exemple, un fichier .zip auto-extractible et que vous souhaitez y monter quelque chose, compressez le contenu de l'archive interne et assurez-vous que le fichier .zip externe ne compresse pas non plus l'archive interne.

Cette fonction fonctionne comme PHYSFS_mount(), mais prend un descripteur PHYSFS_File au lieu d'un nom de chemin. Ce descripteur contient toutes les données de l'archive et est utilisé à la place d'un fichier réel dans le système de fichiers physique. Le PHYSFS_File peut être basé sur un fichier réel dans le système de fichiers physique, mais ce n'est pas nécessairement le cas. L'utilisation la plus courante est probablement de monter des archives stockées à l'intérieur d'autres archives.

(newDir) doit être une chaîne de caractères unique pour identifier cette archive. Elle est utilisée pour optimiser la sélection de l'archiveur (si vous la nommez XXXXX.zip, nous pourrions essayer l'archiveur ZIP en premier, par exemple, ou choisir directement un archiveur qui ne peut faire confiance à la validité des données que par l'extension du nom de fichier). Il n'a pas besoin de faire référence à un fichier réel. Si l'extension du nom de fichier n'est pas utile, le système essaiera tous les archiveurs jusqu'à ce qu'un fonctionne ou qu'aucun ne fonctionne. Ce nom de fichier doit être unique, car le système ne vous permettra pas d'avoir deux archives portant le même nom.

(file) doit rester jusqu'à ce que l'archive soit démontée. Lorsque l'archive est démontée, le système appellera PHYSFS_close(file). Si vous avez besoin que ce descripteur survive, vous devrez l'encapsuler dans un PHYSFS_Io et utiliser PHYSFS_mountIo() à la place.

Si cette fonction échoue, PHYSFS_close(file) n'est pas appelée.

newDir Nom de fichier pouvant représenter ce flux.
mountPoint Emplacement dans l'arbre interpolé où cette archive sera "montée", en notation indépendante de la plateforme. NULL ou "" équivaut à "/".
appendToPath non nul pour ajouter au chemin de recherche, zéro pour ajouter au début.

Retourne

non nul si ajouté au chemin, zéro en cas d'échec (archive invalide, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier vers lequel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné à la mise en bac à sable du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait très bien avoir une raison légitime de créer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont vérifiés explicitement que lors de la manipulation de noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire que lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

int PHYSFS_setBuffer (PHYSFS_File * handle, unsigned int bufsize)

Set the buffering status of a file handle. By default, PhysicsFS file handles are unbuffered. This means that every call to PHYSFS_read() or PHYSFS_write() will result in a direct system call.

Buffering can significantly speed up I/O operations, especially when dealing with many small reads or writes. A buffer is allocated for the file handle, and reads and writes are performed against this buffer in memory, only touching the underlying file system when the buffer needs to be flushed (filled or emptied).

Calling this function on a file handle that is already buffered will result in the existing buffer being flushed and freed, and a new buffer of the requested size being allocated.

Setting the buffer size to zero will flush and free any existing buffer associated with the file handle, effectively returning it to an unbuffered state.

Note that PHYSFS_seek() and related functions transparently handle buffering. When you seek, PhysicsFS ensures that any buffered data is written to disk, and that the file pointer is correctly positioned.

PhysicsFS file handles are unbuffered by default.

Please check the return value of this function! Failures can include not being able to seek backwards in a read-only file when removing the buffer, not being able to allocate the buffer, and not being able to flush the buffer to disk, among other unexpected problems.

Parameters

handle handle returned from PHYSFS_open*().
bufsize size, in bytes, of buffer to allocate.

Returns

nonzero if successful, zero on error.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Définissez un sous-répertoire d'une archive comme répertoire racine. Cela vous permet de restreindre les fichiers accessibles dans une archive spécifique. int PHYSFS_ucs4stricmp (const PHYSFS_uint32 * str1, const PHYSFS_uint32 * str2)

Comparaison insensible à la casse de deux chaînes UCS-4. Ceci est un remplacement pour strcasecmp/stricmp qui s'attend à ce que les deux chaînes soient au format UCS-4 (également connu sous le nom de UTF-32). Il effectuera un "casse-calcul" pour déterminer si les codes de caractères Unicode dans les chaînes correspondent.

Il indiquera quelle chaîne est "supérieure" à l'autre, mais rappelez-vous que cela ne signifie pas nécessairement quelque chose : 'a' peut être "inférieur" à 'b', mais un kana japonais n'a pas de relation significative avec un lambda grec dans l'ordre alphabétique. PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 - write numbers in platform-independant byte order

#include <physfs.h>

Detailed Description

These functions are convenience functions to write unsigned integers to disk in a platform-independant byte order.

The PHYSFS_writeUBE16(), PHYSFS_writeUBE32() and PHYSFS_writeUBE64() functions convert an unsigned integer from the platform's native byte order to big-endian and write it to the specified file.

The PHYSFS_writeULE16(), PHYSFS_writeULE32() and PHYSFS_writeULE64() functions convert an unsigned integer from the platform's native byte order to little-endian and write it to the specified file.

These are convenience functions and not strictly necessary, but can make code easier to read.
