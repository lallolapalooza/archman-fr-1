#define PHYSFS_file PHYSFS_File

Définition de compatibilité API 1.0. PHYSFS_file est identique à PHYSFS_File. Ce #define existe pour la compatibilité descendante avec l'API 1.0, qui avait une convention de casse incohérente dans ce cas. Le nouveau code devrait utiliser PHYSFS_File, car ce #define pourrait disparaître un jour.

typedef PHYSFS_EnumerateCallbackResult(* physFS_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Valeurs de retour possibles de PHYSFS_EnumerateCallback. Signature de fonction pour les rappels qui énumèrent et renvoient des résultats.

Ces valeurs dictent si un rappel d'énumération doit continuer à être déclenché, ou s'arrêter (et pourquoi il s'arrête).

PHYSFS_EnumerateCallback

PHYSFS_enumerate

Ceci est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, à la différence qu'il peut renvoyer un résultat du rappel : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport à d'autres rappels qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent des fichiers.

Attention

À partir de PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; il vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de toute chaîne.

int PHYSFS_delete (const char * filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers dans le répertoire d'un chemin de recherche, en utilisant une fonction de rappel définie par l'utilisateur, avec rapport d'erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de la renvoyer à l'application, de sorte que la fonctionnalité est identique, sauf la façon dont les informations sont présentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas de tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'utilisateur une fois pour chaque élément du chemin de recherche :

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSfs_ENUM_OK;  // donne-moi plus de données, s'il te plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments transmis à la fonction de rappel ne sont garantis dans aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un ordre alphabétique. Cette forme signale ce qu'elle trouve dans chaque archive avant de passer à la suivante. Même au sein d'une seule archive, nous ne pouvons pas garantir l'ordre dans lequel les données sont découvertes. Tout tri que vous pourriez trouver dans ces rappels est purement fortuit. Ne vous y fiez pas. Comme cela parcourt toute la liste de fichiers, vous pourriez recevoir des noms de fichiers en double.

Cette API et les rappels eux-mêmes peuvent signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'un objet spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement sauter des éléments ou arrêter l'énumération, et l'appelant ne saurait pas qu'il avait perdu des données en cours de route.

Maintenant, l'appelant peut être sûr qu'il a obtenu un ensemble complet de données, et s'il veut arrêter l'énumération prématurément, sa fonction de rappel a le contrôle. Voir la documentation pour PHYSFS_EnumerateCallback pour les détails sur la façon dont votre fonction de rappel doit se comporter.

Paramètres

dir Répertoire, en notation indépendante du système d'exploitation, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin.
d Données définies par l'application transmises à la fonction de rappel. Peut être NULL.

Retourne

Non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel renvoie PHYSfs_ENUM_STOP pour arrêter prématurément, cela est considéré comme un succès. Les rappels qui renvoient PHYSfs_ENUM_ERROR feront que cette fonction renverra zéro et définira le code d'erreur sur PHYSfs_ERR_APP_CALLBACK.

Étant donné que cela empêchait les applications de distinguer entre un succès complet et un échec partiel, et étant donné que la fonction pouvait toujours renvoyer NULL pour signaler un échec catastrophique, dans PhysicsFS 2.1, cette politique a changé : elle renverra une liste complète de résultats ou renverra NULL en cas d'échec de quelque nature que ce soit, afin que nous puissions garantir que l'énumération est terminée et qu'il n'y a pas de lacunes dans vos résultats.

Les répertoires correspondants dans le chemin de recherche sont interpolés. C'est-à-dire que si « C:\mydir » se trouve dans le chemin de recherche et contient un répertoire « savegames » contenant « x.sav », « y.sav » et « z.sav », et qu'il y a également un répertoire « C:\userdir » dans le chemin de recherche qui a un sous-répertoire « savegames » avec « w.sav », alors le code suivant :

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi
Choisissez comment trier la liste comme vous le souhaitez. Cependant, les données renvoyées ne contiennent aucun doublon et seront toujours triées par ordre alphabétique (ou plus précisément : triées par casse sensible Unicode) pour vous.
N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur renvoyée par cette fonction lorsque vous avez terminé.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute un archive ou un répertoire au chemin de recherche. S'il s'agit d'un duplicata, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter le même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non par rapport au point de montage.

Lors du montage d'un archive, il est ajouté à un système de fichiers virtuel... tous les fichiers de tous les archives sont interpolés dans une seule arborescence de répertoires. Deux archives montés au même emplacement (ou un archive avec des fichiers qui chevauchent un point de montage) peuvent avoir des fichiers qui se chevauchent : dans ce cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles au programme. Cela permet d'utiliser des archives pour remplacer des versions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence de fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargés qui pourraient écraser les données de l'application ou se remplacer mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que l'on attend des utilisateurs familiers avec le concept Unix de « montage ». De plus, plus d'un archive peut être monté au même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours normalement.

La spécification d'un lien symbolique vers un archive ou un répertoire est autorisée ici, indépendamment de l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne gère que les liens symboliques à l'intérieur du répertoire ou de l'archive monté.

mountPoint emplacement dans l'arborescence interpolée où cet archive sera monté, dans une notation indépendante du système. NULL ou « » équivaut à « / ».
appendToPath non nul pour ajouter à la fin du chemin de recherche, nul pour ajouter au début.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné à la mise en quarantaine du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne pensiez qu'il existe un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers dans la notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

allow non nul pour autoriser les liens symboliques, zéro pour interdire les liens.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Fait d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de réduire les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt, monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer la racine d'une archive à tout moment, modifiant l'arborescence de fichiers interpolée (selon où les chemins changent, une archive différente peut fournir divers fichiers). Si vous définissez la racine sur NULL ou "/", l'archive sera traitée comme si aucune racine spéciale n'était définie (comme si l'archive était simplement montée normalement).

Changer la racine n'affecte que les opérations futures sur les noms de chemin ; un fichier qui a été ouvert à partir d'un chemin qui a changé en raison d'un setRoot ne sera pas affecté.

La définition d'une nouvelle racine n'est pas limitée aux archives du chemin de recherche ; vous pouvez en définir une sur le répertoire d'écriture, ce qui peut être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez donc pas changer le répertoire d'écriture pour le moment.

Ce n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme racine d'une archive ; cependant, aucun fichier ne sera visible dans ce cas. Si les répertoires manquants finissent par être créés (un mkdir vers le système de fichiers physique, etc.), cela sera reflété dans l'arborescence interpolée.

Paramètres

archive répertoire/archive sur lequel changer la racine.
subdir nouveau sous-répertoire à faire de la racine de cette archive.

Retourne

non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UTF-16 string.

Attention

Cette fonction ne signalera pas d'erreur s'il y a des séquences UTF-8 invalides dans la chaîne source. Elles seront remplacées par un caractère '?' et la conversion continuera.

Les chaînes UTF-16 utilisent 16 bits par caractère (sauf pour certains caractères qui en utilisent 32) : TCHAR sous Windows, lors de la compilation avec le support Unicode. Les versions modernes de Windows utilisent UTF-16. Les versions de Windows antérieures à 2000 utilisaient TCHAR, mais ne supportaient que l'UCS-2. L'UTF-16 est de l'UCS-2, à l'exception des caractères qui nécessitent 4 octets, qui ne sont de toute façon pas représentables en UCS-2. Si vous n'êtes pas sûr, vous devriez utiliser UTF-16 à ce stade sous Windows.

Pour garantir que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon de double la taille du tampon source. UTF-8 utilise de un à quatre octets par caractère, mais UTF-16 utilise toujours de deux à quatre octets, donc une chaîne entièrement en ASCII basique doublera de taille ! Les caractères UTF-16 qui nécessiteraient quatre octets prennent également quatre octets en UTF-8, vous n'avez donc pas besoin d'allouer 4 fois l'espace au cas où : le double suffira.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de paire de substitution UTF-16 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

src Chaîne source terminée par un caractère nul au format UTF-8.
