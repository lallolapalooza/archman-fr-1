int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Learns" a Unicode codepoint an equivalent lowercase one. (This is for limited, hardcore use. If you don't immediately see a use case, you can ignore this forever.)

Converts a Unicode codepoint to its lowercase equivalent. Unusual Unicode codepoints without a lowercase equivalent will be returned unchanged. Unicode codepoints are always 32 bits, but this API takes and returns them as 16-bit values for maximum compatibility with existing code that might not be ready for 32-bit Unicode.

You must be able to get multiple Unicode codepoints back! The German "Eszett", for example, will be converted into two lowercase 's' codepoints. The theory is that if you have two strings, one with Eszett and another with "SS", they should compare as equal.

Warning

Those who are students of Unicode are aware of the "Turkish I" problem. This API does not handle it. It assumes that every Unicode letter will behave as expected. If you don't know what this is, you can ignore it for most of the planet, but perfection is impossible.

Parameters

from The Unicode codepoint to convert.
to The buffer to store the converted Unicode codepoint values. Should point to space for at least 3 PHYSFS_uint32 slots.

Returns

The number of Unicode codepoints produced by the conversion. Between 1 and 3.

int PHYSFS_deinit (void )

Deinitializes the PhysicsFS library. It closes any open PhysicsFS files, clears out search paths and write directories, frees memory, and invalidates all file handles you have.

Note: This call can fail if there is an open file for writing that refuses to close (e.g., the OS was buffering writes to a network file system, and the file server has crashed, or a hard drive has failed, etc). It is usually best to close all write handles yourself before calling this function, so you can gracefully handle a specific failure.

Once deinitialized, you can call PHYSFS_init() again to reinitialize the system. All default API states are restored at this time, except for any custom allocators you may have specified, which survive between initializations.

Returns

non-zero on success, zero on error. Error details can be obtained from PHYSFS_getLastError(). If there is an error, PhysFS's state is indeterminate and probably messed up.

int PHYSFS_delete (const char * filename)

Deletes a file or directory. (filename) is specified in platform-independent notation relative to the write directory.

A directory must be empty before it can be deleted.

Deleting a symlink will delete the symlink itself, not what it points to, regardless of whether you allow symlinks or not.

So if you have the write directory set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map"), the file "C:\mygame\writedir\downloads\maps\level1.map" will be deleted from the physical filesystem, if it exists and the OS permits deletion.

Note: On Unix systems, deleting a file may succeed, but the actual file won't be deleted until all processes that have a file handle open to it (including your program) close their handles. Even though the bits that make up the file still exist, they are available to be written over in the future. Do not consider this a security measure or anything like it.

Parameters

filename The name of the file or directory to delete.

Returns

non-zero on success, zero on error. Use PHYSFS_getLastErrorCode() to get the specific error.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers d'un répertoire du chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec des erreurs signalées. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de la renvoyer à l'application, de sorte que la fonctionnalité est identique, sauf pour la façon dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis dans aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale tout ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une seule archive, nous ne pouvons garantir l'ordre de découverte des données. Tout tri que vous trouverez dans ces fonctions de rappel n'est que pure chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pourriez recevoir des noms de fichiers dupliqués.

Cette API et les fonctions de rappel elles-mêmes sont capables de signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter tous les éléments énumérés, même si elles ne recherchaient qu'une chose spécifique et souhaitaient s'arrêter après, ou avaient une erreur grave et ne pouvaient en alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération carrément, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr qu'il a obtenu un ensemble de données complet, et sa fonction de rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Consultez la documentation de PHYSFS_EnumerateCallback pour connaître les détails sur le comportement de votre fonction de rappel.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés en un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers chevauchant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que les personnes familières avec le concept Unix de "montage" pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et les contenus des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

Spécifier un lien symbolique vers une archive ou un répertoire est autorisé ici, quel que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

Paramètres

newDir répertoire ou archive à ajouter au chemin, en notation dépendante de la plateforme.
mountPoint Emplacement dans l'arbre interpolé où cette archive sera "montée", en notation indépendante de la plateforme. NULL ou "" équivaut à "/".
appendToPath non nul pour ajouter au chemin de recherche, zéro pour insérer au début.

Retourne

Non nul si ajouté au chemin, zéro en cas d'échec (archive invalide, répertoire manquant, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers et architectures contiennent des fichiers qui ne sont que des références à d'autres fichiers. Lors de l'ouverture d'un lien symbolique dans un système de fichiers, le fichier auquel il fait référence sera automatiquement ouvert.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait pointer vers une destination hors de la portée d'écriture et de recherche, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Note : Ceci est davantage destiné au sandboxing d'un langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas les désactiver, à moins que vous ne pensiez qu'il y ait un danger spécifique.

Les liens symboliques ne seront explicitement vus que lors du traitement des noms de fichiers dans une notation indépendante de la plateforme. Autrement dit, lors de la définition de vos chemins de recherche et d'écriture, etc., les liens symboliques ne seront jamais consultés pour vérification.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il sera ignoré dans tous les cas. Si les liens symboliques ne sont pas autorisés via cette fonction, PHYSFS_stat() les ignorera et traitera la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée à tout moment après l'appel de PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désactiver le suivi des liens.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Faites d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de réduire les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt, monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer la racine d'une archive à tout moment, modifiant l'arbre de fichiers interpolé (selon l'endroit où les chemins changent, une archive différente peut fournir divers fichiers). Si vous définissez la racine sur NULL ou "/", l'archive sera traitée comme si aucune racine spéciale n'était définie (comme si l'archive était simplement montée normalement).

Le changement de racine n'affecte que les opérations futures sur les noms de chemins ; un fichier qui a été ouvert à partir d'un chemin qui a changé en raison d'un setRoot ne sera pas affecté.

La définition d'une nouvelle racine n'est pas limitée aux archives dans le chemin de recherche ; vous pouvez également en définir une sur le répertoire d'écriture, ce qui peut être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez donc pas modifier le répertoire d'écriture pour le moment.

Ce n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme racine d'une archive ; cependant, aucun fichier ne sera visible dans ce cas. Si les répertoires manquants finissent par être créés (un mkdir sur le système de fichiers physique, etc.), cela sera reflété dans l'arbre interpolé.

archive répertoire/archive sur lequel changer la racine.
subdir nouveau sous-répertoire à faire de la racine de cette archive.

Retourne

non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

archivesFirst Non nul pour préfixer les archives au chemin de recherche. Zéro pour les ajouter. Ignoré si !(archiveExt).

Pour vous assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon dont la taille est le double de celle du tampon source. UTF-8 étend les points de code latin1 supérieurs à 127 de 1 à 2 octets, la chaîne peut donc s'agrandir dans certains cas.
