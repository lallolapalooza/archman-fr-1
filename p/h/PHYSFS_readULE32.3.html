The version of the library. Contains members for the major, minor, and patch levels.

unsigned short major
The major version number.
unsigned short minor

The version of the library is determined by the header files that you compile against. This is determined by what header the compiler uses. Note that if you dynamically linked the library, you might have a slightly newer or older version at runtime. typedef void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

enum PHYSFS_ErrorCode

Values that represent specific causes of failure. Most of the time, you should only concern yourself with whether a given operation failed or not, but there may be occasions where you plan to handle a specific failure case gracefully, so we provide specific error codes.

In most these cases, your program should only care that it failed to accomplish its goals, and not care specifically why.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Fold" a Unicode codepoint to a lowercase equivalent. (This is for limited, hardcore use. If you don't immediately see a need for it, you can probably ignore this forever.)

This will convert a Unicode codepoint into its lowercase equivalent. Bogus codepoints and codepoints without a lowercase equivalent will be returned unconverted.

Note that you might get multiple codepoints in return! The German Eszett, for example, will fold down to two lowercase latin 's' codepoints. The theory is that if you fold two strings, one with an Eszett and one with "SS" down, they will match.

Warning

Anyone that is a student of Unicode knows about the "Turkish I" problem. This API does not handle it. Assume this one letter in all of Unicode will definitely fold sort of incorrectly. If you don't know what this is about, you can probably ignore this problem for most of the planet, but perfection is impossible.

Parameters

from The codepoint to fold.
to Buffer to store the folded codepoint values into. This should point to space for at least 3 PHYSFS_uint32 slots.

Returns

The number of codepoints the folding produced. Between 1 and 3.

int PHYSFS_deinit (void )

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). It is usually best to close all write handles yourself before calling this function, so that you can gracefully handle a specific failure.

Once successfully deinitialized, PHYSFS_init() can be called again to restart the subsystem. All default API states are restored at this point, with the exception of any custom allocator you might have specified, which survives between initializations.

Returns

nonzero on success, zero on error. Specifics of the error can be gleaned from PHYSFS_getLastError(). If failure, state of PhysFS is undefined, and probably badly screwed up.

int PHYSFS_delete (const char * filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

Chances are, the bits that make up the file still exist, they are just made available to be written over at a later point. Don't consider this a security method or anything. :)

Parameters

filename Filename to delete.

Returns

nonzero on success, zero on error. Use PHYSFS_getLastErrorCode() to obtain the specific error.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers du répertoire du chemin de recherche, en utilisant un rappel défini par l'application, avec rapports d'erreurs. Interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique sauf la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas de tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés au rappel ne sont garantis dans aucun ordre quelconque. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons pas garantir l'ordre de découverte des données. Tout tri que vous trouverez dans ces rappels est purement de la chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération sans préavis, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers se chevauchant avec un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus tôt dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence de fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept Unix de "montage" pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné à la mise en bac à sable du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait très bien avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

allow non nul pour autoriser les liens symboliques, zéro pour les refuser.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Définit un sous-répertoire d'une archive comme répertoire racine. Cela vous permet de limiter les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt, monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer la racine d'une archive à tout moment, modifiant l'arborescence de fichiers interpolée (selon l'endroit où les chemins changent, une archive différente peut fournir divers fichiers). Si vous définissez la racine sur NULL ou "/", l'archive sera traitée comme si aucune racine spéciale n'était définie (comme si l'archive était simplement montée normalement).

Le changement de racine n'affecte que les opérations futures sur les chemins ; un fichier qui a été ouvert à partir d'un chemin qui a changé en raison d'un setRoot ne sera pas affecté.

La définition d'une nouvelle racine n'est pas limitée aux archives du chemin de recherche ; vous pouvez en définir une sur le répertoire d'écriture, également, ce qui pourrait être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez donc pas changer le répertoire d'écriture pour le moment.

Il n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme racine d'une archive ; cependant, aucun fichier ne sera visible dans ce cas. Si les répertoires manquants finissent par être créés (un mkdir vers le système de fichiers physique, etc.), cela se reflétera dans l'arbre interpolé.

Paramètres

archive répertoire/archive dont il faut changer la racine.
subdir nouveau sous-répertoire à définir comme racine de cette archive.

Retourne

non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

Le répertoire d'écriture sera défini sur le répertoire de préférences retourné par

Ce qui précède est suffisant pour garantir que le répertoire de configuration de votre programme est séparé des autres encombrements, et est indépendant de la plateforme.

  • Le répertoire d'écriture (créé s'il n'existe pas)
  • Le répertoire de base (PHYSFS_getBaseDir())
  • Tous les répertoires de CD-ROM trouvés (facultatif)

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convertit une chaîne Latin1 en chaîne UTF-8. Les chaînes Latin1 ont 8 bits par caractère : un encodage populaire de type "high ASCII".

Pour garantir que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon deux fois plus grand que le tampon source. L'UTF-8 étend les points de code Latin1 supérieurs à 127 de 1 à 2 octets, donc la chaîne peut s'agrandir dans certains cas.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Veuillez noter que nous ne fournissons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer la plupart des points de code Unicode. C'est un encodage hérité ; vous devriez toujours vous en éloigner.

Paramètres

src Chaîne source terminée par un caractère nul au format Latin1.
dst Tampon pour stocker la chaîne UTF-8 convertie.
len Taille, en octets, du tampon de destination.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convertir una cadena UTF-8 a una cadena UTF-16.

Advertencia

Esta función no reportará un error si hay secuencias UTF-8 inválidas en la cadena de entrada. Reemplazará estas secuencias con un carácter '?' y continuará.

Las cadenas UTF-16 tienen 16 bits por carácter (a excepción de algunos caracteres, que son 32 bits): TCHAR en Windows cuando se compila con soporte Unicode. Versiones modernas de Windows usan UTF-16. Las versiones antiguas de Windows antes de 2000 usaban TCHAR, pero solo manejan UCS-2. UTF-16 es UCS-2, excepto para los caracteres que son 4 bytes, que no se representan correctamente en UCS-2 al completo. Si no estás seguro, deberías estar usando UTF-16 en este punto en Windows.

Para asegurar que el buffer de destino sea suficientemente grande para la conversión, por favor asigna un buffer que sea el doble del tamaño del buffer de entrada. UTF-8 utiliza de 1 a 4 bytes por carácter, pero UTF-16 siempre utiliza 2 a 4 bytes, por lo que una cadena de ASCII completamente baja duplicará su tamaño! Los caracteres UTF-16 que tomarían 4 bytes también ocupan 4 bytes en UTF-8, por lo que no necesitas asignar el doble del espacio solo por seguridad: el doble bastará.

Las cadenas que no se ajustan al buffer de destino serán truncadas, pero siempre serán nulas y nunca tendrán una pareja de surrountes incompletas al final. Si el tamaño del buffer es 0, esta función no realiza ninguna acción.

Parámetros

src Cadena de entrada nula en formato UTF-8.
dst Buffer para almacenar la cadena UTF-16 convertida.
len Tamaño, en bytes, del buffer de destino.
