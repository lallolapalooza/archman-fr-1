typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent les fichiers.

Avertissement

À partir de PhysicsFS 2.1, utilisez plutôt PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; il vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de toute chaîne.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le cas dans les versions de callback. Consultez la documentation sur les API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

« Plie » un point de code Unicode vers son équivalent en minuscules. (Ceci est pour une utilisation limitée et intensive. Si vous ne voyez pas immédiatement un besoin pour cela, vous pouvez probablement ignorer cette fonction pour toujours.)

Ceci convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux sans équivalent en minuscules seront retournés sans conversion.

Notez que vous pourriez obtenir plusieurs points de code en retour ! Le Eszett allemand, par exemple, sera réduit à deux points de code latins « s » en minuscules. La théorie est que si vous pliez deux chaînes, l'une avec un Eszett et l'autre avec « SS », elles correspondront.

Attention

Toute personne qui étudie Unicode connaît le problème de « i turc ». Cette API ne le gère pas. Supposons que cette seule lettre dans tout Unicode sera pliée de manière quelque peu incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la plupart des gens, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Tampon pour stocker les valeurs des points de code pliés. Celui-ci doit pointer vers un espace pour au moins 3 emplacements de type PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialise la bibliothèque PhysicsFS. Cela ferme tous les fichiers ouverts via PhysicsFS, efface les chemins de recherche/écriture, libère la mémoire et invalide tous vos descripteurs de fichiers.

Notez que cet appel peut ÉCHOUEER s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures sur un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur a échoué, etc.). Il est généralement préférable de fermer tous les descripteurs d'écriture vous-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois correctement désinitialisé, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états par défaut de l'API sont restaurés à ce stade, à l'exception de tout allocateur personnalisé que vous auriez pu spécifier, qui survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les détails de l'erreur peuvent être obtenus à partir de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini et probablement très compromis.

int PHYSFS_delete (const char * filename)

Supprime un fichier ou un répertoire. (filename) est spécifié dans une notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, et non ce à quoi il pointe, indépendamment du fait que vous ayez activé ou non "permitSymLinks".

Donc, si vous avez le répertoire d'écriture défini sur "C:\mygame\writedir" et que vous appelez PHYSFS_delete("downloads/maps/level1.map"), alors le fichier "C:\mygame\writedir\downloads\maps\level1.map" est supprimé du système de fichiers physique, s'il existe et si le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont un descripteur de fichier ouvert vers celui-ci (y compris votre programme) ne fermeront pas leurs descripteurs.

Il est probable que les bits qui composent le fichier existent toujours, ils sont juste mis à disposition pour être écrasés ultérieurement. Ne considérez pas cela comme une méthode de sécurité ou quoi que ce soit. :)

Paramètres

filename Nom du fichier à supprimer.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

char **PHYSFS_enumerateFiles (const char * dir)

Get a file listing of a search path's directory.

Warning

In PhysicsFS versions prior to 2.1, this function would return as many items as it could in the face of a failure condition (out of memory, disk i/o error, etc). Since this meant apps couldn't distinguish between complete success and partial failure, and since the function could always return NULL to report catastrophic failures anyway, in PhysicsFS 2.1 this function's policy changed: it will either return a list of complete results or it will return NULL for any failure of any kind, so we can guarantee that the enumeration ran to completion and has no gaps in its results.

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)

PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers se chevauchant avec un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus tôt dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer des versions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept Unix de "montage" pourraient attendre. De plus, plus d'une archive peut être montée sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

La spécification d'un lien symbolique vers une archive ou un répertoire est autorisée ici, quel que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

mountPoint Emplacement dans l'arbre interpolé où cette archive sera "montée", en notation indépendante de la plateforme. NULL ou "" est équivalent à "/".
appendToPath une valeur non nulle pour ajouter au chemin de recherche, zéro pour ajouter au début.

une valeur non nulle si ajouté au chemin, zéro en cas d'échec (archive invalide, répertoire manquant, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (transparentement) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est plus destiné au cloisonnement du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait très bien avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne sentiez qu'il existe un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lorsqu'il s'agit de noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

Convertit une chaîne Latin1 en chaîne UTF-8. Les chaînes Latin1 ont 8 bits par caractère : un encodage "high ASCII" populaire.

Pour garantir que le tampon de destination soit suffisamment grand pour la conversion, veuillez allouer un tampon dont la taille est le double de celle du tampon source. UTF-8 étend les points de code latin1 supérieurs à 127 de 1 à 2 octets, la chaîne peut donc dans certains cas s'agrandir.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Veuillez noter que nous ne fournissons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer la plupart des points de code Unicode. C'est un encodage hérité ; vous devriez toujours vous en éloigner.

Paramètres

src Chaîne source terminée par un caractère nul au format Latin1.
dst Tampon pour stocker la chaîne UTF-8 convertie.
len Taille, en octets, du tampon de destination.
