PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du callback : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, passé par l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être dans un ordre alphabétique par rapport à d'autres callbacks qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent des fichiers.

Attention

Depuis PhysicsFS 2.1, utilisez plutôt PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; il vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire d'une chaîne.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre promis des données dans les versions liste n'est pas nécessairement le cas dans les versions callback. Consultez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes en double.

Paramètres

data Pointeur de données défini par l'utilisateur, passé par l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être dans un ordre alphabétique par rapport à d'autres callbacks qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers d'un répertoire du chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis crée une liste avant de la renvoyer à l'application, de sorte que la fonctionnalité est identique, sauf pour la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons trouvé [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis dans aucun ordre. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale tout ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons pas garantir l'ordre dans lequel les données seront découvertes. Tout tri que vous trouvez dans ces rappels est purement le fruit du hasard. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les fonctions de rappel elles-mêmes sont capables de signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'un élément spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération immédiatement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble complet de données, et sa fonction de rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour plus de détails sur le comportement de votre fonction de rappel.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

Retourne

Non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel renvoie PHYSFS_ENUM_STOP pour s'arrêter plus tôt, cela sera considéré comme un succès. Les fonctions de rappel renvoyant PHYSFS_ENUM_ERROR feront renvoyer zéro à cette fonction et définiront le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi

int PHYSFS_mount(const char *newDir, const char *mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Cette fonction opère comme PHYSFS_mount(), mais prend un tampon mémoire au lieu d'un chemin. Ce tampon contient toutes les données de l'archive et est utilisé à la place d'un vrai fichier dans le système de fichiers physique.

Ce nom de fichier doit être unique, car le système ne vous permettra pas d'avoir deux archives portant le même nom.

(ptr) doit rester jusqu'à ce que l'archive soit démontée. Lorsque l'archive est démontée, le système appellera (del)(ptr), ce qui vous informera que le système a fini avec le tampon et vous donnera une chance de libérer vos ressources. (del) peut être NULL, dans ce cas le système ne fera aucune tentative pour libérer le tampon.

Si cette fonction échoue, (del) n'est pas appelée.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné à l'isolation d'un langage de script de programme, au cas où des scripts non fiables tenteraient de compromettre le système. De manière générale, un utilisateur pourrait très bien avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lorsque l'on traite des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

Setting a new root is not limited to archives in the search path; you may set one on the write dir, too, which might be useful if you have files open for write and thus can't change the write dir at the moment.

It is not an error to set a subdirectory that does not exist to be the root of an archive; however, no files will be visible in this case. If the missing directories end up getting created (a mkdir to the physical filesystem, etc) then this will be reflected in the interpolated tree.

Returns

nonzero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error.

PHYSFS_sint64 PHYSFS_writeBytes (PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Écrit des données dans un descripteur de fichier PhysicsFS. Le fichier doit être ouvert en écriture.

Veuillez noter que bien que (len) soit un entier non signé de 64 bits, vous êtes limité à 63 bits (9223372036854775807 octets), nous pouvons donc retourner une valeur négative en cas d'erreur. Si la longueur est supérieure à 0x7FFFFFFFFFFFFFFF, cette fonction échouera immédiatement. Pour les systèmes sans type de données 64 bits, vous êtes limité à 31 bits (0x7FFFFFFF, soit 2147483647 octets). Nous faisons confiance au fait que la plupart des choses n'auront pas besoin d'effectuer plusieurs gigaoctets d'E/S en un seul appel, mais pourquoi limiter les choses ?

Paramètres

handle valeur de retour de PHYSFS_openWrite() ou PHYSFS_openAppend().
buffer tampon de (len) octets à écrire dans (handle).
len nombre d'octets à écrire dans (handle).

Retourne

nombre d'octets écrits. Ce nombre peut être inférieur à (len) ; en cas d'erreur, le système peut essayer d'écrire autant d'octets que possible, de sorte qu'une écriture incomplète puisse se produire. PHYSFS_getLastErrorCode() peut éclaircir la raison pour laquelle ce nombre pourrait être inférieur à (len). -1 en cas d'échec complet.

val Valeur à convertir et à écrire.
