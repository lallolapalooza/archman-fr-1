Définit de compatibilité avec l'API 1.0. PHYSFS_file est identique à PHYSFS_File. Ce #define est là pour la compatibilité ascendante avec l'API 1.0, qui avait une convention de capitalisation incohérente dans ce cas. typedef PHYSFS_EnumerateCallbackResult(* physfs_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Valeurs de retour possibles de PHYSFS_EnumerateCallback. Signature de fonction pour les callbacks qui énumèrent et retournent des résultats.

Ces valeurs dictent si un callback d'énumération doit continuer à être déclenché, ou s'arrêter (et pourquoi il s'arrête).

PHYSFS_EnumerateCallback

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'elle peut retourner un résultat du callback : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, transmis depuis l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé l'énumération, transmis dans le callback pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être dans un ordre alphabétique par rapport à d'autres callbacks qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent les fichiers.

Attention

À partir de PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; il vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de toute chaîne.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme une alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le cas dans les versions de callback. Vérifiez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data Pointeur de données défini par l'utilisateur, transmis depuis l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé l'énumération, transmis dans le callback pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être dans un ordre alphabétique par rapport à d'autres callbacks qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir una liste de fichiers d'un répertoire de la chaîne de recherche, en utilisant une fonction de rappel définie par l'utilisateur, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de la renvoyer à l'application, donc la fonction est identique à moins de la façon dont les informations sont présentées à l'application.

Différent de PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau, mais appelle une fonction spécifiée par l'utilisateur une fois pour chaque élément dans la chaîne de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons trouvé [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // Donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments passés à la fonction de rappel ne sont pas garantis d'être dans un ordre quelconque. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit l'ordre alphabétique. Cette forme rapporte ce qui est trouvé dans chaque fichier d'archive avant de passer au suivant. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout ordre que vous pourriez trouver dans ces fonctions de rappel est pure coïncidence. Ne comptez pas dessus. Comme cela parcourt toute la liste de fichiers, vous pouvez recevoir des noms de fichiers en double.

Cette API et les fonctions de rappel elles-mêmes peuvent signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même si elles ne recherchaient qu'un élément spécifique et voulaient s'arrêter après, ou si elles rencontraient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement sauter les éléments ou arrêter l'énumération, et l'appelant ne saurait pas qu'il avait manqué des données en cours de route.

Maintenant, l'appelant peut s'assurer qu'il a obtenu un ensemble complet de données, et s'il veut arrêter l'énumération tôt, sa fonction de rappel contrôle cela. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement attendu de votre fonction de rappel.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments de la chaîne de recherche.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

Retour

Non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel renvoie PHYSFS_ENUM_STOP pour s'arrêter tôt, cela sera considéré comme un succès. Les fonctions de rappel renvoyant PHYSFS_ENUM_ERROR feront que cette fonction renverra zéro et définira le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à différents points de montage : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers chevauchant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser les archives pour remplacer les versions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un endroit spécifique de l'arbre de fichiers et éviter les chevauchements ; ceci est utile pour les mods téléchargeables qui pourraient écraser les données de l'application ou se piétiner mutuellement, par exemple.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous amener en dehors des chemins de recherche et d'écriture, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné à la mise en sandbox du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. De manière générale, un utilisateur pourrait très bien avoir une raison légitime de créer un lien symbolique, donc à moins que vous ne sentiez qu'il y a un danger spécifique à les autoriser, vous devriez les permettre.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour interdire les liens.

UTF-16 est UCS-2, à l'exception des caractères qui nécessitent 4 octets, qui ne sont de toute façon pas représentables en UCS-2. Si vous n'êtes pas sûr, vous devriez utiliser UTF-16 à ce stade sous Windows.

Pour s'assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon deux fois plus grand que le tampon source. UTF-8 n'utilise jamais plus de 32 bits par caractère, donc bien qu'il puisse réduire la taille d'une chaîne UTF-16, il peut aussi l'augmenter.

Les chaînes qui ne tiennent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

src Chaîne source terminée par un caractère nul au format UTF-16.
dst Tampon pour stocker la chaîne UTF-8 convertie.

La plupart des cas devraient traiter la valeur de retour comme « égal » ou « inégal ».

Comme stricmp, cela suppose que les deux chaînes sont terminées par NULL.

str1 Première chaîne à comparer.

Retourne

-1 si str1 est « inférieur » à str2, 1 si « supérieur », 0 si égal.
