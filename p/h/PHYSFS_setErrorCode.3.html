typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature des fonctions de callback qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() pour avoir plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant original, une entrée fichier/répertoire/symbole par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire des chaînes.

Ces callbacks sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui retournent des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes à l'avance.

Notez que l'ordre des données promis dans les versions de liste n'est pas nécessairement le même dans les versions de callback. Vérifiez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pouvez obtenir des chaînes dupliquées.

Paramètres

data pointeur vers des données définies par l'utilisateur, passé via l'API qui a finalement appelé le callback.
origdir chaîne contenant le chemin complet, dans la notation indépendante du système d'exploitation, du répertoire qui contient ce fichier. Dans la plupart des cas, c'est le répertoire dans lequel vous avez demandé l'énumération, passé dans le callback pour votre commodité.
fname le nom du fichier en cours d'énumération. Il peut ne pas être dans l'ordre alphabétique par rapport à d'autres callbacks qui ont été appelés et ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Plie" un point de code Unicode vers un équivalent en minuscules. (Ceci est pour une utilisation limitée et intensive. Si vous ne voyez pas immédiatement un besoin pour cela, vous pouvez probablement l'ignorer pour toujours.)

Ceci convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et les points de code sans équivalent en minuscules seront renvoyés sans conversion.

Notez que vous pourriez obtenir plusieurs points de code en retour ! Le ligature allemande Eszett, par exemple, sera plié en deux points de code 's' latins minuscules. La théorie est que si vous pliez deux chaînes, l'une avec un Eszett et l'autre avec "SS", elles correspondront.

Attention

Toute personne qui étudie Unicode connaît le problème de l'« I turc ». Cette API ne le gère pas. Supposons que cette seule lettre dans tout Unicode sera pliée d'une manière ou d'une autre incorrectement. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la majeure partie de la planète, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Tampon pour stocker les valeurs des points de code pliés. Il doit pointer vers un espace pour au moins 3 emplacements PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialise la bibliothèque PhysicsFS. Cela ferme tous les fichiers ouverts via PhysicsFS, efface les chemins de recherche/écriture, libère la mémoire et invalide tous vos descripteurs de fichier.

Notez que cet appel peut ÉCHOUEr s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures sur un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur a échoué, etc.). Il est généralement préférable de fermer tous les descripteurs d'écriture vous-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois correctement désinitialisé, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états API par défaut sont restaurés à ce moment-là, à l'exception de tout allocateur personnalisé que vous auriez pu spécifier, qui survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les spécificités de l'erreur peuvent être obtenues auprès de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini, et probablement très endommagé.

int PHYSFS_delete (const char * filename)

Supprime un fichier ou un répertoire. (filename) est spécifié dans une notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, pas ce à quoi il pointe, indépendamment du fait que vous ayez "permis les liens symboliques" ou non.

Donc, si vous avez défini le répertoire d'écriture sur "C:\monjeu\rep_ecriture" et que vous appelez PHYSFS_delete("telechargements/cartes/niveau1.carte"), alors le fichier "C:\monjeu\rep_ecriture\telechargements\cartes\niveau1.carte" est supprimé du système de fichiers physique, s'il existe et si le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont un descripteur de fichier ouvert dessus (y compris votre programme) ne fermeront pas leurs descripteurs.

Il y a de fortes chances que les bits qui composent le fichier existent toujours, ils sont simplement rendus disponibles pour être écrasés ultérieurement. Ne considérez pas cela comme une méthode de sécurité ou quoi que ce soit. :)

Paramètres

filename Nom du fichier à supprimer.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_deregisterArchiver (const char * ext)

Supprime un archiveur du système. Si pour une raison quelconque, vous n'avez besoin de votre archiveur précédemment enregistré que pendant une partie de la durée de vie de votre application, vous pouvez le retirer du système une fois que vous avez terminé grâce à cette fonction.

Cela échoue s'il y a encore des archives ouvertes qui utilisent cet archiveur.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter un répertoire ou un fichier au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si l'opération réussit. Le même répertoire ne peut pas être ajouté à deux points de montage différents : la vérification des doublons se fait par rapport au répertoire et non par rapport au point de montage.

Lors du montage d'un répertoire, il est ajouté à un système de fichiers virtuel... tous les fichiers de tous les répertoires montés sont entrelacés dans un seul arborescence de répertoires. Deux répertoires montés au même endroit (ou un répertoire avec des fichiers superposés à un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus proche dans le chemin de recherche est sélectionné, et les autres fichiers ne sont pas accessibles à l'application. Cela permet aux répertoires d'être utilisés pour remplacer des versions antérieures ; vous pouvez utiliser le mécanisme de montage pour placer des répertoires à un endroit spécifique dans l'arborescence des fichiers et éviter les superpositions ; c'est utile pour les modes téléchargeables qui pourraient écraser les données de l'application ou se superposer les uns aux autres, par exemple.

Le point de montage n'a pas besoin d'exister au préalable, ce qui diffère de ce que l'on attend du concept de « montage » sur Unix. De plus, plus d'un répertoire peut être monté au même point de montage, ou les points de montage et le contenu des répertoires peuvent se chevaucher... les mécanismes d'entrelacement fonctionnent toujours.

Spécifier un lien symbolique vers un répertoire ou un fichier est autorisé ici, indépendamment de l'état de PHYSFS_permitSymbolicLinks(). La fonction ne gère que les liens symboliques à l'intérieur du répertoire ou du fichier monté.

Paramètres

newDir répertoire ou fichier à ajouter au chemin, en notation système.
mountPoint emplacement dans l'arborescence entrelacée où ce répertoire doit être monté, en notation système. NULL ou «  » équivaut à « / ».
appendToPath non nul pour ajouter au chemin de recherche, zéro pour précéder.

Retourne

Non nul si l'élément a été ajouté au chemin, zéro en cas d'erreur (fichiers invalides, répertoires manquants, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

Ajoute une archive, contenue dans un handle PHYSFS_File, au chemin de recherche.

Attention

Sauf si vous avez un besoin spécial et de bas niveau, vous devriez utiliser PHYSFS_mount() à la place.

Les archives dans les archives peuvent être très lentes ! Bien qu'un PHYSFS_File puisse se repositionner même lorsque les données sont compressées, il peut le faire en revenant au début et en décompressant tout avant le point de repositionnement. L'utilisation normale des archives peut effectuer de nombreux repositionnements en arrière-plan. En tant que tel, vous pourriez trouver l'utilisation normale des archives extrêmement pénible si elles sont montées de cette manière. Planifiez en conséquence : si vous avez, par exemple, un fichier .zip auto-extractible et que vous souhaitez y monter quelque chose, compressez le contenu de l'archive interne et assurez-vous que le fichier .zip externe ne compresse pas également l'archive interne.

Cette fonction fonctionne comme PHYSFS_mount(), mais prend un handle PHYSFS_File au lieu d'un nom de chemin. Ce handle contient toutes les données de l'archive et est utilisé à la place d'un fichier réel dans le système de fichiers physique. Le PHYSFS_File peut être basé sur un fichier réel dans le système de fichiers physique, mais ce n'est pas nécessairement le cas. L'utilisation la plus courante est probablement de monter des archives stockées à l'intérieur d'autres archives.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné à la mise en sandbox du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait très bien avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne pensiez qu'il existe un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors de la manipulation de noms de fichiers dans la notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Fait d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de restreindre les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt, monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer la racine d'une archive à tout moment, modifiant l'arbre de fichiers interpolé (en fonction de l'endroit où les chemins changent, une archive différente peut fournir divers fichiers). Si vous définissez la racine à NULL ou "/", l'archive sera traitée comme si aucune racine spéciale n'était définie (comme si l'archive était simplement montée normalement).

Changer la racine n'affecte que les opérations futures sur les noms de chemins ; un fichier qui a été ouvert à partir d'un chemin qui a changé en raison d'un setRoot ne sera pas affecté.

La définition d'une nouvelle racine n'est pas limitée aux archives du chemin de recherche ; vous pouvez également en définir une sur le répertoire d'écriture, ce qui pourrait être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez donc pas changer le répertoire d'écriture pour le moment.

Il n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme racine d'une archive ; cependant, aucun fichier ne sera visible dans ce cas. Si les répertoires manquants finissent par être créés (un mkdir vers le système de fichiers physique, etc.), cela se reflétera dans l'arbre interpolé.

Paramètres

archive répertoire/archive sur laquelle changer la racine.
subdir nouveau sous-répertoire à faire de la racine de cette archive.

Retourne

non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convertit une chaîne UTF-8 en chaîne Latin1. Les chaînes Latin1 ont 8 bits par caractère : un encodage populaire "high ASCII".

Pour garantir que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon deux fois plus grand que le tampon source. UTF-8 étend les points de code latin1 supérieurs à 127 de 1 à 2 octets, donc la chaîne peut grossir dans certains cas.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Veuillez noter que nous ne fournissons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer la plupart des points de code Unicode. C'est un encodage hérité ; vous devriez toujours vous en éloigner.

Paramètres

src Chaîne source terminée par un caractère nul au format Latin1.
dst Tampon pour stocker la chaîne UTF-8 convertie.
len Taille, en octets, du tampon de destination.
