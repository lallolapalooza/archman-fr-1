PHYSFS_EnumerateCallback

PHYSFS_enumerate

Ceci est le même que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat de rappel : par exemple, si vous cherchez quelque chose de spécifique, une fois trouvé, vous pouvez dire à PhysicsFS d'arrêter l'énumération. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait. :)

Paramètres

data Pointeur de données défini par l'utilisateur, transmis par l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire que vous avez demandé à énumérer, transmis dans le rappel pour votre commodité.
fname Le nom du fichier qui est énuméré. Il ne sera pas trié par ordre alphabétique par rapport à d'autres rappels qui ont été appelés, et ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature des fonctions de rappel qui énumèrent les fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; il offre plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, une entrée par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de toutes les chaînes.

Ces rappels sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui renvoient des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le rappel indique que la bibliothèque n'a pas besoin de réserver une liste complète et toutes les chaînes précédemment.

Vous devez être conscient que l'ordre promis dans les versions de liste n'est pas nécessairement le cas dans les versions de rappel. Vérifiez la documentation des API spécifiques, mais les chaînes ne seront pas nécessairement triées comme vous vous y attendez, et vous pourriez obtenir des chaînes dupliquées.

origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire que vous avez demandé à énumérer, transmis dans le rappel pour votre commodité.

int PHYSFS_deinit(void)

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). int PHYSFS_delete(const char *filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

Chances are, the bits that make up the file still exist, they are just made available to be written over at a later point. Don't consider this a security method or anything. :)

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers d'un répertoire du chemin de recherche, en utilisant un rappel défini par l'application, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de la retourner à l'application, donc la fonctionnalité est identique sauf la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas de tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons obtenu [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés au rappel ne sont garantis dans aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons pas garantir l'ordre dans lequel les données seront découvertes. Tout tri que vous trouverez dans ces appels de rappel est purement de la chance. Ne comptez pas dessus. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération tout simplement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr qu'il a obtenu un ensemble de données complet, et son rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation pour PHYSFS_EnumerateCallback pour les détails sur le comportement attendu de votre rappel.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées au rappel. Peut être NULL.

Retourne

Non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel retourne PHYSFS_ENUM_STOP pour s'arrêter plus tôt, cela sera considéré comme un succès. * Nous avons obtenu [w.sav]..fi

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute un fichier ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée même si la fonction réussit. Vous ne pouvez pas ajouter le même fichier à deux points de montage distincts : la vérification des doublons se fait par rapport au fichier et non par rapport au point de montage.

Lors du montage d'un fichier, il est ajouté à un système de fichiers virtuel... tous les fichiers de tous les fichiers montés sont entrelacés en un seul arbre de répertoires. Deux fichiers montés au même endroit (ou un fichier avec des fichiers se chevauchant un point de montage) peuvent avoir des fichiers qui se chevauchent : dans ce cas, le fichier qui apparaît en premier dans le chemin de recherche est choisi, et les autres fichiers ne sont pas accessibles par l'application. Elle est utilisée pour optimiser la sélection de l'archiveur (si vous la nommez XXXXX.zip, nous pourrions essayer l'archiveur ZIP en premier, par exemple, ou choisir directement un archiveur qui ne peut faire confiance à la validité des données que par l'extension du nom de fichier). Il n'est pas nécessaire qu'il fasse référence à un fichier réel. Si l'extension du nom de fichier n'est pas utile, le système essaiera chaque archiveur jusqu'à ce que l'un fonctionne ou qu'aucun d'entre eux ne fonctionne. Ce nom de fichier doit être unique, car le système ne vous permettra pas d'avoir deux archives portant le même nom.

(ptr) doit rester jusqu'à ce que l'archive soit démontée. Lorsque l'archive est démontée, le système appellera (del)(ptr), ce qui vous informera que le système a fini d'utiliser le tampon et vous donnera une chance de libérer vos ressources. (del) peut être NULL, auquel cas le système ne fera aucune tentative pour libérer le tampon.

Si cette fonction échoue, (del) n'est pas appelé.

Paramètres

buf Adresse du tampon mémoire contenant les données de l'archive.
len Taille du tampon mémoire, en octets.
del Une fonction de rappel qui se déclenche lors du démontage. Peut être NULL.
newDir Nom de fichier pouvant représenter ce flux.
mountPoint Emplacement dans l'arbre interpolé où cette archive sera « montée », dans une notation indépendante de la plateforme. NULL ou « » équivaut à « / ».
appendToPath non nul pour ajouter au chemin de recherche, nul pour préfixer.

Retourne

non nul si ajouté au chemin, nul en cas d'échec (archive invalide, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, ouvrir un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné à la mise en quarantaine du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait très bien avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne pensiez qu'il existe un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors de la manipulation des noms de fichiers dans la notation indépendante de la plateforme. C'est-à-dire que lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans tous les cas pas suivi. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Fait d'un sous-répertoire d'une archive son répertoire racine. Ceci vous permet de restreindre les fichiers accessibles dans une archive particulière. Par exemple, si vous avez x.zip avec un fichier à y/z.txt monté à /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer la racine d'une archive à tout moment, modifiant ainsi l'arborescence de fichiers interpolée (selon où les chemins se déplacent, une archive différente pourrait fournir des fichiers différents). Définir une nouvelle racine n'est pas limité aux archives dans le répertoire de recherche ; vous pouvez le définir dans le répertoire d'écriture également, ce qui peut être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez pas changer le répertoire d'écriture maintenant.

archive Le répertoire/archive dans lequel changer la racine.
subdir Le nouveau sous-répertoire à faire la racine de cette archive.

non zéro en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.
