Signature de fonction pour les rappels qui énumèrent des fichiers.

Avertissement

À partir de PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; cela vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de toute chaîne.

Ces rappels sont utilisés, à partir de PhysicsFS 1.1, comme une alternative aux fonctions qui renvoyaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions listes n'est pas nécessairement le même dans les versions rappel. Vérifiez la documentation sur les API spécifiques, mais les chaînes peuvent ne pas être triées comme vous l'attendez et vous pourriez obtenir des chaînes dupliquées.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

« Plie » un point de code Unicode vers un équivalent en minuscules. (Ceci est pour une utilisation limitée et avancée. Si vous ne voyez pas immédiatement un besoin pour cela, vous pouvez probablement l'ignorer à jamais.)

Ceci convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux sans équivalent en minuscules seront retournés sans conversion.

Notez que vous pourriez obtenir plusieurs points de code en retour ! L'Eszett allemand, par exemple, sera réduit à deux points de code « s » en minuscules. La théorie est que si vous réduisez deux chaînes, l'une avec un Eszett et l'autre avec « SS », elles correspondront.

Attention

Quiconque a étudié Unicode connaît le problème du « I turc ». Cette API ne le gère pas. Supposez que cette seule lettre dans tout Unicode ne sera probablement pas réduite correctement. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la plupart du monde, mais la perfection est impossible.

Paramètres

from Le point de code à réduire.
to Tampon pour stocker les valeurs de points de code réduits. Ceci devrait pointer vers un espace pour au moins 3 emplacements PHYSFS_uint32.

Retourne

Le nombre de points de code produits par la réduction. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialise la bibliothèque PhysicsFS. Cela ferme tous les fichiers ouverts via PhysicsFS, efface les chemins de recherche/écriture, libère la mémoire et invalide toutes vos poignées de fichier.

Notez que cet appel peut ÉCHOUEr s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures sur un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur a échoué, etc.). Il est généralement préférable de fermer toutes les poignées d'écriture soi-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois désinitialisé avec succès, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états API par défaut sont restaurés à ce moment-là, à l'exception de tout allocateur personnalisé que vous auriez pu spécifier, qui survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les détails de l'erreur peuvent être obtenus à partir de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini et probablement très perturbé.

int PHYSFS_delete (const char * filename)

Supprime un fichier ou un répertoire. (filename) est spécifié en notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, et non ce vers quoi il pointe, indépendamment du fait que vous ayez « autorisé les liens symboliques » ou non.

Ainsi, si vous avez défini le répertoire d'écriture sur "C:\mygame\writedir" et que vous appelez PHYSFS_delete("downloads/maps/level1.map"), alors le fichier "C:\mygame\writedir\downloads\maps\level1.map" est supprimé du système de fichiers physique, s'il existe et si le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont une poignée de fichier ouverte dessus (y compris votre programme) ne fermeront pas leurs poignées.

Il est probable que les bits qui composent le fichier existent toujours, ils sont juste rendus disponibles pour être écrasés ultérieurement. Ne considérez pas cela comme une méthode de sécurité ou quoi que ce soit. :)

Paramètres

filename Nom du fichier à supprimer.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers d'un répertoire du chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec signalement des erreurs. Interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique, sauf pour la façon dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas de tableau. Elle appelle plutôt une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons obtenu [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis dans aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale tout ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données seront découvertes. *Tout tri que vous trouverez dans ces appels de fonction est purement le fruit du hasard. Ne vous y fiez pas.* Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les fonctions de rappel elles-mêmes sont capables de signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même si elles ne recherchaient qu'un élément spécifique et voulaient s'arrêter après, ou si elles avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération purement et simplement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble de données complet, et sa fonction de rappel a le contrôle s'il souhaite arrêter l'énumération plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur la façon dont votre fonction de rappel doit se comporter.

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

Retourne

non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel retourne PHYSFS_ENUM_STOP pour arrêter tôt, cela sera considéré comme un succès. Les fonctions de rappel retournant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

const char * PHYSFS_getLastError (void )

Obtient des informations d'erreur lisibles par l'homme.

Obsolète

Utilisez PHYSFS_getLastErrorCode() et PHYSFS_getErrorByCode() à la place.

Depuis PhysicsFS 2.1, cette fonction a été « affaiblie ». Avant 2.1, c'était le seul moyen d'obtenir des détails sur les erreurs en dehors des valeurs retournées par une fonction individuelle. C'était un problème, car le développeur, et non l'utilisateur, choisissait la langue au moment de la compilation, et les mainteneurs de PhysicsFS devaient (très mal) maintenir un gros travail de localisation. L'application ne pouvait pas analyser les chaînes, même si elle dépendait d'une langue spécifique, car certaines étaient générées dynamiquement.   • Essayez d'utiliser la même chaîne d'organisation (y compris la casse) pour toutes vos applications qui utilisent cette fonction.
  • Utilisez toujours une chaîne d'application unique pour chacune, et assurez-vous qu'elle ne change jamais après avoir été décidée.
  • Les caractères Unicode sont légaux, tant qu'ils sont codés en UTF-8, mais...
  • ... utilisez uniquement des lettres, des chiffres et des espaces. Évitez les caractères tels que « Game Name 2: Bad Guy's Revenge! » ... « Game Name 2 » est suffisant.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers se chevauchant sur un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Ceci permet d'utiliser des archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence de fichiers et empêcher les chevauchements ; ceci est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se chevaucher mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que les personnes familières avec le concept Unix de "montage" pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

La spécification d'un lien symbolique vers une archive ou un répertoire est autorisée ici, indépendamment de l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que des liens symboliques à l'intérieur du répertoire ou de l'archive montée.

Paramètres

newDir répertoire ou archive à ajouter au chemin, en notation dépendante de la plateforme.
mountPoint Emplacement dans l'arbre interpolé où cette archive sera "montée", en notation indépendante de la plateforme. NULL ou "" équivaut à "/".
appendToPath non nul pour ajouter au chemin de recherche, zéro pour ajouter au début.

Retourne

une valeur non nulle si ajoutée au chemin, zéro en cas d'échec (archive invalide, répertoire manquant, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

Ajoute une archive, contenue dans un descripteur PHYSFS_File, au chemin de recherche.

Attention

Sauf si vous avez un besoin spécial de bas niveau, vous devriez utiliser PHYSFS_mount() à la place.

Les archives dans les archives peuvent être très lentes ! Bien qu'un PHYSFS_File puisse effectuer des recherches (seek) même lorsque les données sont compressées, cela peut impliquer de revenir au début et de décompresser tout ce qui précède le point de recherche. L'utilisation normale d'archive peut effectuer de nombreuses recherches en arrière-plan. En tant que tel, vous pourriez trouver l'utilisation normale des archives extrêmement pénible si elles sont montées de cette manière. Planifiez en conséquence : si vous avez, par exemple, un fichier .zip auto-extractible et que vous souhaitez monter quelque chose à l'intérieur, compressez le contenu de l'archive interne et assurez-vous que le fichier .zip externe ne compresse pas l'archive interne également.

Cette fonction fonctionne comme PHYSFS_mount(), mais prend un descripteur PHYSFS_File au lieu d'un chemin d'accès. Ce descripteur contient toutes les données de l'archive et est utilisé à la place d'un vrai fichier dans le système de fichiers physique. Le PHYSFS_File peut être basé sur un vrai fichier dans le système de fichiers physique, mais ce n'est pas nécessairement le cas. L'utilisation la plus courante pour cela est probablement de monter des archives stockées à l'intérieur d'autres archives.

Elle est utilisée pour optimiser la sélection de l'archiveur (si vous la nommez XXXXX.zip, nous pourrions essayer l'archiveur ZIP en premier, par exemple, ou choisir directement un archiveur qui ne peut faire confiance à la validité des données que par extension de nom de fichier). Il n'est pas nécessaire qu'elle fasse référence à un fichier réel. Si l'extension du nom de fichier n'est pas utile, le système essaiera tous les archiveurs jusqu'à ce qu'un fonctionne ou qu'aucun ne fonctionne. Ce nom de fichier doit être unique, car le système ne vous permettra pas d'avoir deux archives portant le même nom.

Si cette fonction échoue, PHYSFS_close(file) n'est pas appelée.

appendToPath différent de zéro pour ajouter au chemin de recherche, zéro pour précéder.

Ce qui précède est suffisant pour garantir que le répertoire de configuration de votre programme est séparé des autres encombrements et est indépendant de la plateforme.

Le chemin de recherche sera :

  • Le répertoire d'écriture (créé s'il n'existe pas)
  • Le répertoire de base (PHYSFS_getBaseDir())
  • Tous les répertoires de CD-ROM trouvés (facultatif)

Si vous avez spécifié "PKG" pour (archiveExt), et qu'il existe un fichier nommé data.PKG dans le répertoire de base, il sera vérifié. Toutes les archives sont montées à la racine du système de fichiers virtuel ("/").

Spécifiez NULL pour ne pas extraire automatiquement les archives. Ne spécifiez pas le caractère '.' ; si vous souhaitez rechercher des fichiers ZIP, spécifiez "ZIP" et non ".ZIP" ... la recherche d'archives est insensible à la casse.

Cela peut entraîner un blocage important lors de l'accès aux disques, et s'il n'y a pas de disques dans le lecteur (ou même pas montés sur les systèmes Unix), ils peuvent de toute façon ne pas être disponibles. Vous voudrez peut-être spécifier zéro et gérer la configuration du disque vous-même.
archivesFirst Valeur non nulle pour préfixer les archives au chemin de recherche. Zéro pour les ajouter. Ignoré si !(archiveExt).

Retourne

une valeur non nulle en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.
