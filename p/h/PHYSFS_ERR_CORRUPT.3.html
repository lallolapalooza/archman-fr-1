PHYSFS_enumerate

Ceci est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du rappel : à savoir : si vous cherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous avons, espérons-le, bien fait cette fois-ci. :)

Paramètres

origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.

Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent des fichiers.

Avertissement

À partir de PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; cela vous donne plus de contrôle sur le processus.

Ils sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de ces chaînes.

Ces rappels sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes au préalable.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le même dans les versions de rappel. Consultez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes en double.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers d'un répertoire du chemin de recherche, en utilisant un rappel défini par l'application, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis crée une liste avant de retourner à l'application, donc la fonctionnalité est identique sauf pour la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons trouvé [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés au rappel ne sont garantis dans aucun ordre que ce soit. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une seule archive, nous ne pouvons pas garantir l'ordre de découverte des données. Tout tri que vous trouverez dans ces rappels est purement de la chance. N'en dépendez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération directement, et l'appelant ne saurait pas qu'il a perdu des données en cours de chemin.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble de données complet, et son rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement attendu de votre rappel.

d Données définies par l'application passées au rappel. Peut être NULL.

Retourne

The returned filename will be the element of the search path where the file was found, which may be a directory, or an archive. int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons est effectuée par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers chevauchant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser les archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence de fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou s'écraser mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept de « montage » Unix pourraient s'attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

La spécification d'un lien symbolique vers une archive ou un répertoire est autorisée ici, indépendamment de l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que les liens symboliques à l'intérieur du répertoire monté ou archive.

mountPoint Emplacement dans l'arbre interpolé où cette archive sera « montée », en notation indépendante de la plateforme. NULL ou « » équivaut à « / ».
appendToPath un entier non nul pour ajouter au chemin de recherche, zéro pour ajouter en tête.

Un entier non nul si ajouté au chemin, zéro en cas d'échec (archive invalide, répertoire manquant, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

À moins d'avoir un besoin spécial et de bas niveau, vous devriez utiliser PHYSFS_mount() à la place.

Cette fonction fonctionne comme PHYSFS_mount(), mais prend un tampon mémoire au lieu d'un nom de chemin. Ce tampon contient toutes les données de l'archive et est utilisé à la place d'un fichier réel dans le système de fichiers physique.

(newDir) doit être une chaîne unique pour identifier cette archive. Elle est utilisée pour optimiser la sélection de l'archiveur (si vous la nommez XXXXX.zip, nous pourrions essayer l'archiveur ZIP en premier, par exemple, ou choisir directement un archiveur qui ne peut faire confiance à la validité des données que par extension de nom de fichier). Il n'a pas besoin de faire référence à un fichier réel. Si l'extension du nom de fichier n'est pas utile, le système essaiera tous les archiveurs jusqu'à ce qu'un fonctionne ou qu'aucun d'entre eux ne fonctionne. Ce nom de fichier doit être unique, car le système ne vous permettra pas d'avoir deux archives avec le même nom.

(ptr) doit rester jusqu'à ce que l'archive soit démontée. Lorsque l'archive est démontée, le système appellera (del)(ptr), ce qui vous informera que le système a terminé avec le tampon et vous donnera une chance de libérer vos ressources. (del) peut être NULL, auquel cas le système ne tentera pas de libérer le tampon.

Si cette fonction échoue, (del) n'est pas appelée.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné au sandbox d'un langage de script de programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers dans la notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans tous les cas pas suivi. Si les liens symboliques ne sont pas autorisés via cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser les liens.

Establece el código de error actual del hilo. Esto te permite establecer el valor que será devuelto por la próxima llamada a PHYSFS_getLastErrorCode(). Este código reemplazará cualquier código de error existente, ya sea establecido por tu aplicación o por PhysicsFS.

Crea un subdirectorio de un archivo como directorio raíz. Esto te permite limitar los archivos accesibles en un archivo específico. void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. If you aren't sure, you should be using UTF-16 at this point on Windows.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
len Size, in bytes, of destination buffer.
