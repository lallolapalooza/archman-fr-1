#define PHYSFS_file PHYSFS_File

Définition de compatibilité API 1.0. PHYSFS_file est identique à PHYSFS_File. Cette #define est présente pour la compatibilité descendante avec l'API 1.0, qui avait une convention de casse incohérente dans ce cas. typedef PHYSFS_EnumerateCallbackResult(* physfs_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Valeurs de retour possibles de PHYSFS_EnumerateCallback. Signature de fonction pour les rappels qui énumèrent et renvoient des résultats.

Ces valeurs dictent si un rappel d'énumération doit continuer à être déclenché, ou s'arrêter (et pourquoi il s'arrête).

Voir aussi

PHYSFS_EnumerateCallback

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du rappel : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez indiquer à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, transmis depuis l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être par ordre alphabétique par rapport à d'autres rappels qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers d'un répertoire spécifié, en utilisant une fonction de rappel définie par l'utilisateur, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de la retourner à l'application, de sorte que la fonctionnalité est identique, sauf pour la manière dont les informations sont présentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois pour chaque élément du répertoire :

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments passés à la fonction de rappel ne sont garantis dans aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit le tri par ordre alphabétique. Cette forme signale ce qui est trouvé dans chaque fichier, et même à l'intérieur d'un même fichier, nous ne pouvons garantir l'ordre dans lequel la donnée est découverte. Tout ordre trouvé dans ces rappels est de la pure chance. Ne comptez pas dessus. Comme cela parcourt toute la liste des fichiers, vous pourriez recevoir des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes peuvent signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'une donnée spécifique et voulaient s'arrêter là, ou s'ils avaient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application, il pouvait simplement ignorer des éléments ou arrêter l'énumération, et l'appelant ne saurait pas qu'il avait perdu des données en cours de route.

Maintenant, l'appelant peut être sûr qu'il a obtenu un ensemble complet de données, et s'il veut arrêter l'énumération plus tôt, son rappel contrôle cela. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement attendu de votre rappel.

Paramètres

dir Répertoire, en notation indépendante du système d'exploitation, à énumérer.
c Fonction de rappel pour notifier les éléments du répertoire.
d Données définies par l'application passées au rappel. Peut être NULL.

Retour

Non nul en cas de succès, nul en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel retourne PHYSFS_ENUM_STOP, cela est considéré comme un succès. Les rappels retournant PHYSFS_ENUM_ERROR feront que cette fonction retournera nul et définira le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait contre l'archive et non contre le point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers se chevauchant avec un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer des révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner des données d'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que les habitués du concept Unix de "montage" pourraient attendre. void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné à la mise en quarantaine du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors de la manipulation de noms de fichiers en notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore, et traiterait la requête comme si le chemin n'existait pas du tout.

La permission de lien symbolique peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

int PHYSFS_setSaneConfig (const char * organization, const char * appName, const char * archiveExt, int includeCdRoms, int archivesFirst)

Set up sane, default paths. Helper function.

The write dir will be set to the pref dir returned by

PHYSFS_getPrefDir(organization, appName)

, which is created if it doesn't exist.

The above is sufficient to make sure your program's configuration directory is separated from other clutter, and platform-independent.

The search path will be:

  • The Write Dir (created if it doesn't exist)
  • The Base Dir (PHYSFS_getBaseDir())
  • All found CD-ROM dirs (optionally)

These directories are then searched for files ending with the extension (archiveExt), which, if they are valid and supported archives, will also be added to the search path. If you specified "PKG" for (archiveExt), and there's a file named data.PKG in the base dir, it'll be checked. Archives can either be appended or prepended to the search path in alphabetical order, regardless of which directories they were found in. All archives are mounted in the root of the virtual file system ("/") .

All of this can be accomplished from the application, but this just does it all for you. Feel free to add more to the search path manually, too.

Parameters

organization Name of your company/group/etc to be used as a dirname, so keep it small, and no-frills.
appName Program-specific name of your program, to separate it from other programs using PhysicsFS.
archiveExt File extension used by your program to specify an archive. For example, Quake 3 uses "pk3", even though they are just zipfiles. Specify NULL to not dig out archives automatically. Do not specify the '.' char; If you want to look for ZIP files, specify "ZIP" and not ".ZIP" ... the archive search is case-insensitive.
includeCdRoms Non-zero to include CD-ROMs in the search path, and (if (archiveExt) != NULL) search them for archives.
