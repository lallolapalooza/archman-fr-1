typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent des fichiers.

Avertissement

À partir de PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; cela vous donne plus de contrôle sur le processus.

Ils sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire d'une chaîne.

Ces rappels sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le cas dans les versions par rappel. Vérifiez la documentation sur les API spécifiques, mais les chaînes peuvent ne pas être triées comme vous l'attendez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être en ordre alphabétique par rapport aux autres rappels qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

enum PHYSFS_ErrorCode

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Récupère la liste des fichiers d'un répertoire du chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec signalement des erreurs. Interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis crée une liste avant de retourner à l'application, donc la fonctionnalité est identique, sauf pour la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas de tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche : 

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons obtenu [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis dans aucun ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale tout ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une seule archive, nous ne pouvons garantir l'ordre dans lequel les données seront découvertes. Tout tri que vous pourriez trouver dans ces rappels n'est que pure chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les fonctions de rappel elles-mêmes sont capables de signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'il y avait une erreur sérieuse et qu'ils ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble de données complet, et sa fonction de rappel a le contrôle s'il souhaite arrêter l'énumération plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour plus de détails sur le comportement de votre fonction de rappel.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

Retour

Non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel renvoie PHYSFS_ENUM_STOP pour arrêter prématurément, cela sera considéré comme un succès. Les fonctions de rappel renvoyant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

Récupère la liste des fichiers d'un répertoire du chemin de recherche.

Attention

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction retournait autant d'éléments que possible face à une condition d'échec (manque de mémoire, erreur d'E/S disque, etc.). Comme cela empêchait les applications de distinguer un succès complet d'un échec partiel, et comme la fonction pouvait toujours retourner NULL pour signaler des échecs catastrophiques de toute façon, dans PhysicsFS 2.1, la politique de cette fonction a changé : elle retournera soit une liste de résultats complets, soit NULL en cas d'échec, afin que nous puissions garantir que l'énumération s'est terminée et qu'il n'y a pas de lacunes dans ses résultats.

Les répertoires correspondants sont interpolés. C'est-à-dire que si « C:\mydir » se trouve dans le chemin de recherche et contient un répertoire « savegames » contenant « x.sav », « y.sav » et « z.sav », et qu'il existe également un répertoire « C:\userdir » dans le chemin de recherche qui a un sous-répertoire « savegames » avec « w.sav », alors le code suivant : 

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Nous avons obtenu [%s].\n", *i);
PHYSFS_freeList(rc);
* Nous avons obtenu [x.sav].
* Nous avons obtenu [y.sav].
* Nous avons obtenu [z.sav].
* Nous avons obtenu [w.sav]..fi
N'hésitez pas à trier la liste comme vous le souhaitez. Cependant, les données renvoyées ne contiendront toujours aucun doublon et seront toujours triées par ordre alphabétique (ou plutôt, Unicode sensible à la casse) pour vous.
N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur de retour de cette fonction lorsque vous en avez terminé.

Get the user-and-app-specific path where files can be written. Helper function.

void PHYSFS_permitSymbolicLinks (int allow)

Activer ou désactiver le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (transparenmment) le fichier vers lequel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins de recherche et d'écriture, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné à l'isolement du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne ressentiez un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers dans la notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser les liens.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. If you aren't sure, you should be using UTF-16 at this point on Windows.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
len Size, in bytes, of destination buffer.

See also

PHYSFS_sint64 PHYSFS_writeBytes (PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Écrit des données dans un descripteur de fichier PhysicsFS. Le fichier doit être ouvert en écriture.

Veuillez noter que bien que (len) soit un entier non signé de 64 bits, vous êtes limité à 63 bits (9223372036854775807 octets), nous pouvons donc retourner une valeur négative en cas d'erreur. Si la longueur est supérieure à 0x7FFFFFFFFFFFFFFF, cette fonction échouera immédiatement. Pour les systèmes sans type de données 64 bits, vous êtes limité à 31 bits (0x7FFFFFFF, soit 2147483647 octets). Nous pensons que la plupart des choses n'auront pas besoin de faire plusieurs gigaoctets d'entrée/sortie en un seul appel, mais pourquoi limiter les choses ?

Paramètres

handle valeur de retour de PHYSFS_openWrite() ou PHYSFS_openAppend().
buffer tampon de (len) octets à écrire dans (handle).
len nombre d'octets à écrire dans (handle).

Retourne

nombre d'octets écrits. Cela peut être inférieur à (len) ; en cas d'erreur, le système peut essayer d'écrire autant d'octets que possible, de sorte qu'une écriture incomplète puisse se produire. PHYSFS_getLastErrorCode() peut éclairer la raison pour laquelle cela pourrait être inférieur à (len). -1 en cas d'échec complet.
