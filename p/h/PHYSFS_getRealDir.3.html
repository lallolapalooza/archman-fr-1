typedef PHYSFS_EnumerateCallbackResult(* physFS_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Possible return values from PHYSFS_EnumerateCallback. Function signature for callbacks that enumerate and return results.

These values dictate if an enumeration callback should continue to fire, or stop (and why it is stopping).

See also

PHYSFS_EnumerateCallback

PHYSFS_enumerate

This is the same thing as PHYSFS_EnumFilesCallback from PhysicsFS 2.0, except it can return a result from the callback: namely: if you're looking for something specific, once you find it, you can tell PhysicsFS to stop enumerating further. This is used with PHYSFS_enumerate(), which we hopefully got right this time. :)

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

Returns

A value from PHYSFS_EnumerateCallbackResult. All other values are (currently) undefined; don't use them.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

enum PHYSFS_ErrorCode

Values that represent specific causes of failure. Most of the time, you should only concern yourself with whether a given operation failed or not, but there may be occasions where you plan to handle a specific failure case gracefully, so we provide specific error codes.

Most of these errors are a little vague, and most aren't things you can fix...if there's a permission error, for example, all you can really do is pass that information on to the user and let them figure out how to handle it. In most these cases, your program should only care that it failed to accomplish its goals, and not care specifically why.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers d'un répertoire à partir d'un chemin de recherche, en utilisant une fonction de rappel définie par l'utilisateur, avec des erreurs rapportées. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de la retourner à l'application, de sorte que la fonctionnalité est identique, sauf pour la manière dont les informations sont présentées à l'application.

Différente de PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'utilisateur une fois pour chaque élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donne-moi plus de données, s'il te plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments passés à la fonction de rappel ne sont garantis dans aucun ordre. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un ordre alphabétique. Cette forme rapporte ce qui est trouvé dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout ordre que vous trouvez dans ces callbacks est de la pure chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des fichiers, vous pourriez recevoir des noms de fichiers dupliqués.

Cette API et les fonctions de rappel elles-mêmes peuvent rapporter des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même si elles ne cherchaient qu'un objet spécifique et voulaient s'arrêter ensuite, ou si elles avaient une erreur grave et ne pouvaient en avertir personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque, etc.), il ne pouvait pas le signaler à l'application, il devait simplement sauter des éléments ou cesser l'énumération, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut s'assurer qu'il a obtenu un ensemble complet de données, et s'il veut arrêter l'énumération plus tôt, sa fonction de rappel a le contrôle. Consultez la documentation de PHYSFS_EnumerateCallback pour connaître les détails sur la façon dont votre fonction de rappel doit se comporter.

Paramètres

dir Répertoire, en notation indépendante du système d'exploitation, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'utilisateur passées à la fonction de rappel. Peut être NULL.

Retour

Non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel renvoie PHYSFS_ENUM_STOP pour arrêter prématurément, cela sera considéré comme un succès. Les fonctions de rappel renvoyant PHYSFS_ENUM_ERROR feront en sorte que cette fonction retourne zéro et définisse le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

Depuis PhysicsFS 2.1, cette fonction a été renforcée. Avant PhysicsFS 2.1, c'était le seul moyen d'obtenir des détails d'erreur au-delà de la valeur de retour de base d'une fonction. C'était un problème, car le développeur, et non l'utilisateur, choisit la langue au moment de la compilation, et les mainteneurs de PhysicsFS devaient (mal) maintenir un travail de localisation important. L'application ne pouvait pas analyser les chaînes, même si elle dépendait d'une langue spécifique, car certaines étaient générées dynamiquement. En 2.1 et versions ultérieures, elle renvoie toujours une chaîne statique en anglais ; vous pouvez l'utiliser comme clé de chaîne pour votre propre localisation, bien que nous nous engagions à ne pas modifier les chaînes existantes. Depuis PhysicsFS 2.1, cette fonction ne présente que du texte en langue anglaise, mais les chaînes sont statiques, vous pouvez donc les utiliser comme clés dans votre propre dictionnaire de localisation. Ces chaînes sont destinées à être directement transmises à l'utilisateur.

En général, les applications ne se soucient que de savoir si une fonction a échoué ; cependant, si votre code nécessite plus de spécificités, vous devriez utiliser PHYSFS_getLastErrorCode() au lieu de cette fonction.

const char *physFS_getPrefDir (const char * org, const char * app)

Obtenir le chemin du répertoire spécifique à l'écriture des fichiers, utilisé par l'utilisateur et l'application. Fonction d'aide.

Obtenir le "pref dir". C'est l'endroit où les utilisateurs sont censés pouvoir écrire des fichiers personnels (préférences et sauvegardes de jeux, etc.) spécifiques à votre application. Ce dossier est unique par utilisateur et par application.

Cette fonction déterminera l'emplacement approprié sur le système de fichiers natif, créera le dossier si nécessaire, et retournera une chaîne en notation dépendante de la plateforme, appropriée pour être passée à PHYSFS_setWriteDir().

Sous Windows, cela pourrait ressembler à : "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name"

Sous Linux, à : "/home/bob/.local/share/My Program Name"

Sous Mac OS X, à : "/Users/bob/Library/Application Support/My Program Name"

(etc.)

Nous vous recommandons d'utiliser le pref dir comme répertoire d'écriture et de le placer au début de votre liste de recherche. Les anciennes versions de PhysicsFS n'offraient que PHYSFS_getUserDir() et laissaient à l'utilisateur le soin de décider où placer les fichiers sous cet arbre. Cette fonction trouve l'emplacement correct pour n'importe quelle plateforme, ce qui change non seulement entre les systèmes d'exploitation, mais aussi entre les versions du même système d'exploitation.

  • Essayez d'utiliser la même chaîne (y compris la casse) pour toutes vos applications qui utilisent cette fonction.
  • Utilisez toujours une chaîne unique pour chaque application, et assurez-vous qu'elle ne change pas une fois que vous avez décidé de la chaîne.
  • Les caractères Unicode sont autorisés tant qu'ils sont encodés en UTF-8, mais...
  • ... utilisez uniquement des lettres, des chiffres et des espaces. Évitez les caractères comme « NomDuJeu 2: La Revanche du Méchant ! » ... « NomDuJeu 2 » suffit.

int PHYSFS_mount (const char *newDir, const char *mountPoint, int appendToPath)

Añadir un directorio o un archivo a la lista de búsqueda. Si es un duplicado, el registro no se añade de nuevo, incluso si el función éxito. No puedes añadir el mismo directorio a dos diferentes puntos de montaje: el control de duplicado se hace contra el directorio y no el punto de montaje.

Cuando montas un directorio, se añade a un sistema de archivos virtual... todos los archivos de todos los directorios montados se interpolan en una única arboléctica jerárquica. Dos directorios montados en el mismo lugar (o un directorio que tiene archivos que superponen a otro punto de montaje) pueden tener archivos superpuestos: en ese caso, el archivo más antiguo en la lista de búsqueda se selecciona, y los otros archivos no están accesibles para la aplicación. Esto permite que los directorios se usen para reemplazar revisiones previas; puedes usar el mecanismo de montaje para colocar directorios en un punto específico en el árbol de archivos y evitar superposiciones; esto es útil para modulos descargables que puedan trampar sobre datos de aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montar, lo que es diferente de lo que se espera en el concepto Unix de "montar" de los usuarios familiares. Además, más de un directorio puede montarse en el mismo punto de montaje, o puntos de montaje y contenido de directorios pueden superponerse... el mecanismo de interpolación sigue funcionando.

Es permitido especificar un ligero a un directorio o un archivo, independientemente de si PHYSFS_permitSymbolicLinks() está en estado de activación o no. Esta función solo se enfoca en ligeros dentro del directorio o del directorio montado.

newDir directorio o directorio a añadir a la lista, en notación dependiente del sistema.
mountPoint ubicación en el árbol interpolado donde se montará este directorio, en notación independiente del sistema. NULL o "" es equivalente a "/".
appendToPath no cero para agregar al camino de búsqueda, cero para preponer.

Devuelve

No cero si se añadió al camino, cero en caso de error (archivos inválidos, directorios faltantes, etc). Usa PHYSFS_getLastErrorCode() para obtener el error específico.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (transparentement) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné au cloisonnement du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait très bien avoir une raison légitime de créer un lien symbolique, donc à moins que vous ne ressentiez un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire que lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission de lien symbolique peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

, qui est créé s'il n'existe pas.

Ce qui précède est suffisant pour garantir que le répertoire de configuration de votre programme est séparé des autres encombrements et est indépendant de la plateforme.

Le chemin de recherche sera :

  • Le Répertoire d'Écriture (créé s'il n'existe pas)
  • Le Répertoire de Base (PHYSFS_getBaseDir())
  • Tous les répertoires de CD-ROM trouvés (facultatif)

Ces répertoires sont ensuite recherchés pour les fichiers se terminant par l'extension (archiveExt), qui, s'ils sont valides et pris en charge par les archives, seront également ajoutés au chemin de recherche. Si vous avez spécifié "PKG" pour (archiveExt), et qu'il existe un fichier nommé data.PKG dans le répertoire de base, il sera vérifié. Les archives peuvent être ajoutées ou préfixées au chemin de recherche par ordre alphabétique, quelle que soit la manière dont elles ont été trouvées dans les répertoires. Toutes les archives sont montées à la racine du système de fichiers virtuel ("/").

Tout cela peut être accompli par l'application, mais ceci s'en charge pour vous. N'hésitez pas à ajouter manuellement d'autres éléments au chemin de recherche.

Paramètres

organization Nom de votre entreprise/groupe/etc à utiliser comme nom de répertoire, donc gardez-le court et simple.
appName Nom spécifique du programme, pour le distinguer des autres programmes utilisant PhysicsFS.
archiveExt Extension de fichier utilisée par votre programme pour spécifier une archive. Par exemple, Quake 3 utilise "pk3", même s'il s'agit simplement de fichiers zip. Spécifiez NULL pour ne pas rechercher automatiquement les archives. Ne spécifiez pas le caractère '.' ; Si vous souhaitez rechercher des fichiers ZIP, spécifiez "ZIP" et non ".ZIP" ... la recherche d'archives ne respecte pas la casse.
includeCdRoms Non nul pour inclure les CD-ROM dans le chemin de recherche, et (si (archiveExt) != NULL) les rechercher pour les archives. Cela peut entraîner un blocage important lors de l'accès aux disques, et s'il n'y a pas de disques dans le lecteur (ou même pas montés sur les systèmes Unix), ils peuvent ne pas être disponibles de toute façon. Vous pourriez vouloir spécifier zéro et gérer la configuration du disque vous-même.
archivesFirst Non nul pour préfixer les archives au chemin de recherche. Zéro pour les suffixer. Ignoré si !(archiveExt).

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

Les versions modernes de Windows utilisent UTF-16. Les versions de Windows antérieures à 2000 utilisaient TCHAR, mais ne géraient que UCS-2. UTF-16 est UCS-2, à l'exception des caractères qui nécessitent 4 octets, qui ne sont de toute façon pas représentables en UCS-2. Si vous n'êtes pas sûr, vous devriez utiliser UTF-16 à ce stade sur Windows.

Pour garantir que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon dont la taille est le double de celle du tampon source. UTF-8 utilise de un à quatre octets par caractère, mais UTF-16 en utilise toujours de deux à quatre ; une chaîne entièrement en ASCII basique doublera donc de taille ! Les caractères UTF-16 qui nécessiteraient quatre octets en nécessitent également quatre en UTF-8, vous n'avez donc pas besoin d'allouer 4 fois l'espace par précaution : le double suffira.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par null et ne comporteront jamais une paire de substitution UTF-16 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Paramètres

src Chaîne source terminée par null au format UTF-8.
dst Tampon pour stocker la chaîne UTF-16 convertie.
len Taille, en octets, du tampon de destination.
