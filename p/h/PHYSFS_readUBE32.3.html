int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Aplatir" un point de code Unicode vers un équivalent en minuscules. (Ceci est pour une utilisation limitée et hardcore. Si vous ne voyez pas immédiatement la nécessité, vous pouvez l'ignorer pour toujours.)

Convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides ou sans équivalent en minuscules seront retournés sans modification.

Note : Vous pourriez obtenir plusieurs points de code en réponse ! Le caractère eszett, par exemple, sera aplati en deux points de code minuscules 's' en latin. Le théorème est que si vous aplatissez deux chaînes, l'une avec un eszett et l'autre avec "SS", elles correspondront.

Avertissement

Quiconque étudiant Unicode connaît le problème du "i turc". Cette API ne le gère pas. Elle suppose que chaque lettre de l'ensemble Unicode se comportera de manière prévisible lors de l'aplatissement. Si vous ne savez pas de quoi il s'agit, vous pouvez ignorer ce problème pour la majeure partie du monde, mais la perfection est impossible.

Paramètres

from Le point de code à aplatir.
to Le tampon dans lequel les valeurs aplaties seront stockées. Il doit pointer vers un espace pour au moins 3 emplacements PHYSFS_uint32.

Retourne

Le nombre de points de code produits par l'aplatissement. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialiser la bibliothèque PhysicsFS. Ceci ferme tous les fichiers ouverts via PhysicsFS, vide les chemins de recherche/écriture, libère la mémoire et invalide tous vos handles de fichiers.

Note : Cet appel peut échouer s'il y a un fichier ouvert en écriture qui ne se ferme pas correctement (par exemple, le système d'exploitation mettait en mémoire tampon des écritures sur un système de fichiers réseau, et le serveur de fichiers est tombé en panne, ou un disque dur a échoué, etc.). Il est généralement préférable de fermer tous les handles d'écriture avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois désinitialisé avec succès, PHYSFS_init() peut être rappelé pour réinitialiser le sous-système. Tous les états par défaut de l'API sont réinitialisés à ce stade, à l'exception des allocateurs personnalisés que vous auriez spécifiés, qui sont conservés entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les détails de l'erreur peuvent être obtenus via PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS sera indéfini et probablement mal construit.

int PHYSFS_delete (const char * filename)

Supprimer un fichier ou un répertoire. (filename) est spécifié en notation indépendante du système par rapport au répertoire d'écriture.

Un répertoire doit être vide avant de pouvoir être supprimé.

La suppression d'un lien symbolique supprimera le lien, pas ce vers quoi il pointe, que les liens symboliques soient autorisés ou non.

Donc, si vous avez le répertoire d'écriture configuré sur "C:\mygame\writedir" et que vous appelez PHYSFS_delete("downloads/maps/level1.map"), alors le fichier "C:\mygame\writedir\downloads\maps\level1.map" sera supprimé du système de fichiers physique, s'il existe et que le système d'exploitation autorise la suppression.

Note : Sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier physique ne sera pas réellement supprimé tant que tous les processus qui ont un handle ouvert sur lui (y compris votre programme) ne l'auront pas fermé. Il est possible que les bits qui composent le fichier existent toujours, mais qu'ils puissent être écrasés dans le futur. Ne considérez pas cela comme une méthode de sécurité.

Paramètres

filename Le nom du fichier à supprimer.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenez une liste de fichiers d'un répertoire du chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique sauf la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis dans aucun ordre quelconque. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme rapporte ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une seule archive, nous ne pouvons pas garantir l'ordre de découverte des données. Tout tri que vous trouvez dans ces fonctions de rappel est purement de la chance. N'en dépendez pas. Comme cela parcourt toute la liste des archives, vous pourriez recevoir des noms de fichiers dupliqués.

Cette API et les fonctions de rappel elles-mêmes sont capables de signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'il y avait une erreur grave et qu'ils ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération purement et simplement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir un ensemble de données complet, et sa fonction de rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour plus de détails sur le comportement attendu de votre fonction de rappel.

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

Retour

Non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel retourne PHYSFS_ENUM_STOP pour s'arrêter plus tôt, cela sera considéré comme un succès. Les fonctions de rappel retournant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers chevauchant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus tôt dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et empêcher les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept Unix de "montage" pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

La spécification d'un lien symbolique vers une archive ou un répertoire est autorisée ici, indépendamment de l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Hace un subdirectorio de un archivo como directorio raíz. Esto te permite restringir los archivos accesibles en un archivo específico. Por ejemplo, si tienes x.zip con un archivo en y/z.txt montado a /a, si llamas PHYSFS_setRoot("x.zip", "/y"), entonces el llamado PHYSFS_openRead("/a/z.txt") será exitoso.

Puedes cambiar la raíz de un archivo en cualquier momento, alterando el árbol de archivos interpolado (dependiendo de dónde se muevan las rutas, un archivo diferente podría proporcionar archivos diversos). Establecer una nueva raíz no está limitado a archivos en el directorio de búsqueda; puedes establecer una raíz en el directorio de escritura, lo cual podría ser útil si tienes archivos abiertos para escritura y no puedes cambiar el directorio de escritura en el momento.

No es un error establecer un subdirectorio que no exista como raíz de un archivo, pero en ese caso no se mostrarán archivos. Si los directorios faltantes terminan siendo creados (una mkdir en el sistema de archivos físico, etc), esto se reflejará en el árbol interpolado.

archive directorio/archivo en el cual cambiar la raíz.
subdir subdirectorio nuevo a hacer la raíz de este archivo.

no cero en éxito, cero en error. Usa PHYSFS_getLastErrorCode() para obtener el error específico.
