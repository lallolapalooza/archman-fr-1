typedef PHYSFS_EnumerateCallbackResult(* physfs_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Possible return values from PHYSFS_EnumerateCallback. Function signature for callbacks that enumerate and return results.

These values dictate if an enumeration callback should continue to fire, or stop (and why it is stopping).

See also

PHYSFS_EnumerateCallback

PHYSFS_enumerate

This is the same thing as PHYSFS_EnumFilesCallback from PhysicsFS 2.0, except it can return a result from the callback: namely: if you're looking for something specific, once you find it, you can tell PhysicsFS to stop enumerating further. This is used with PHYSFS_enumerate(), which we hopefully got right this time. :)

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

Returns

A value from PHYSFS_EnumerateCallbackResult. All other values are (currently) undefined; don't use them.

typedef void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

enum PHYSFS_ErrorCode

Values that represent specific causes of failure. Most of the time, you should only concern yourself with whether a given operation failed or not, but there may be occasions where you plan to handle a specific failure case gracefully, so we provide specific error codes.

Most of these errors are a little vague, and most aren't things you can fix...if there's a permission error, for example, all you can really do is pass that information on to the user and let them figure out how to handle it. In most these cases, your program should only care that it failed to accomplish its goals, and not care specifically why.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir une liste de fichiers d'un répertoire d'un chemin de recherche, en utilisant un callback défini par l'application, avec rapport d'erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de la renvoyer à l'application, donc la fonctionnalité est identique, sauf la manière dont l'information est présentée à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas un tableau. Elle appelle plutôt une fonction spécifiée par l'application une fois pour chaque élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés au callback ne sont garantis dans aucun ordre. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un ordre alphabétique. Cette forme signale ce qui est trouvé dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout tri que vous trouvez dans ces callbacks est purement le fruit du hasard. Ne vous y fiez pas. Comme elle parcourt toute la liste des fichiers, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les callbacks eux-mêmes peuvent signaler des erreurs. Avant cette API, les callbacks devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'un élément spécifique et voulaient s'arrêter après, ou s'ils rencontraient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même rencontrait un problème (erreur de disque ou autre), il ne pourrait pas le signaler à l'application appelante, il devrait simplement ignorer les éléments ou arrêter l'énumération, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être assuré qu'il a obtenu un ensemble complet de données, et son callback contrôle s'il arrête l'énumération prématurément. Consultez la documentation de PHYSFS_EnumerateCallback pour plus de détails sur le comportement de votre callback.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin.
d Données définies par l'application passées au callback. Peut être NULL.

Retourne

Non zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le callback retourne PHYSFS_ENUM_STOP, cela est considéré comme un succès. Les callbacks retournant PHYSFS_ENUM_ERROR feront que cette fonction retournera zéro et définira le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

Avertissement

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction renvoyait autant d'éléments que possible en cas de problème (erreur de mémoire, erreur d'entrée/sortie disque, etc.). Pour cette raison, les applications ne pouvaient pas distinguer un succès complet d'un échec partiel, et comme la fonction pouvait renvoyer NULL pour signaler un échec catastrophique, dans PhysicsFS 2.1 cette politique a changé : elle renvoie une liste complète de résultats ou NULL en cas de problème, nous pouvons ainsi garantir que l'énumération a été complète et qu'il n'y a pas d'espaces dans vos résultats.

Les répertoires correspondants sont interpolés. char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Nous avons [%s].\n", *i);
PHYSFS_freeList(rc);

* Nous avons [y.sav].
* Nous avons [z.sav].
* Nous avons [w.sav]..fi

N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur renvoyée par cette fonction lorsque vous avez terminé.

L'application ne pouvait pas analyser les chaînes, même si elle comptait sur une langue spécifique, car certaines étaient générées dynamiquement. Dans les versions 2.1 et ultérieures, elle retourne toujours une chaîne statique en anglais ; vous pouvez l'utiliser comme chaîne clé pour vos propres localisations si vous le souhaitez, car nous nous engageons à ne pas modifier les chaînes d'erreur existantes. De plus, si votre application souhaite examiner des erreurs spécifiques, nous offrons maintenant une meilleure option : utilisez PHYSFS_getLastErrorCode() à la place.

Obtenir le dernier message d'erreur de PhysicsFS sous forme de chaîne de caractères lisible, terminée par NULL. Renverra NULL s'il n'y a pas eu d'erreur depuis le dernier appel à cette fonction. Le pointeur retourné par cet appel pointe vers un tampon interne. Chaque thread a un état d'erreur unique qui lui est associé, mais chaque fois qu'un nouveau message d'erreur est défini, il écrasera le précédent associé à ce thread. Il est sûr d'appeler cette fonction à tout moment, même avant PHYSFS_init().

Depuis PhysicsFS 2.1, cette fonction ne présente que du texte en langue anglaise, mais les chaînes sont statiques, vous pouvez donc les utiliser comme clés dans votre propre dictionnaire de localisation. Ces chaînes sont destinées à être transmises directement à l'utilisateur.

Généralement, les applications ne devraient se préoccuper que du fait qu'une fonction donnée a échoué ; cependant, si votre code nécessite plus de spécificités, vous devriez utiliser PHYSFS_getLastErrorCode() au lieu de cette fonction.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers chevauchant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser les archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; ceci est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui sont familiers avec le concept Unix de "montage" pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

La spécification d'un lien symbolique vers une archive ou un répertoire est autorisée ici, quel que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que les liens symboliques à l'intérieur du répertoire monté ou de l'archive.

void PHYSFS_permitSymbolicLinks(int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et architectures contiennent des fichiers qui ne sont que des références à d'autres fichiers. Lors de l'ouverture d'un lien symbolique sur un système physique, celui-ci sera ouvert de manière transparente pour ouvrir le fichier auquel il fait référence.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous mener en dehors des chemins de lecture et d'écriture, compromettant la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Vous devriez être conscient que ceci est davantage destiné au sandboxing d'un langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une raison légitime de définir un lien symbolique, vous ne devriez donc pas le désactiver à moins que vous ne ressentiez un danger spécifique.

Les liens symboliques ne sont explicitement vérifiés que lorsqu'ils traitent des noms de fichiers dans une notation indépendante du système. Autrement dit, lorsque vos chemins de recherche et d'écriture sont définis, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. S'il n'est pas autorisé par le biais de cette fonction, PHYSFS_stat() ignorera ces liens et traitera la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

int PHYSFS_setRoot(const char * archive, const char * subdir)

Définit un sous-répertoire d'une archive comme répertoire racine. Cela vous permet de restreindre les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt, monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez modifier la racine d'une archive à tout moment, ce qui modifie l'arborescence de fichiers interpolée (selon la façon dont les chemins changent, une archive différente peut fournir divers fichiers). Si vous définissez la racine sur NULL ou "/", l'archive sera traitée comme si aucune racine spéciale n'était définie (comme si l'archive était simplement montée normalement).

La modification de la racine n'affecte que les opérations futures sur les noms de chemins ; un fichier qui a été ouvert à partir d'un chemin qui a changé en raison d'un setRoot ne sera pas affecté.

La définition d'une nouvelle racine n'est pas limitée aux archives dans le chemin de recherche ; vous pouvez en définir une sur le répertoire d'écriture, ce qui peut être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez donc pas modifier le répertoire d'écriture pour le moment.

Ce n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme racine d'une archive ; cependant, aucun fichier ne sera visible dans ce cas. Si les répertoires manquants finissent par être créés (un mkdir vers le système de fichiers physique, etc.), cela sera reflété dans l'arbre interpolé.

archive répertoire/archive sur lequel changer la racine.
subdir nouveau sous-répertoire à définir comme racine de cette archive.

non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

  • Le répertoire de base (PHYSFS_getBaseDir())
  • Tous les répertoires de CD-ROM trouvés (facultatif)

Ces répertoires sont ensuite recherchés pour les fichiers se terminant par l'extension (archiveExt), qui, s'ils sont des archives valides et prises en charge, seront également ajoutés au chemin de recherche. Si vous avez spécifié "PKG" pour (archiveExt), et qu'il existe un fichier nommé data.PKG dans le répertoire de base, il sera vérifié. Les archives peuvent être ajoutées ou préfixées au chemin de recherche par ordre alphabétique, quelle que soit la manière dont elles ont été trouvées. Toutes les archives sont montées à la racine du système de fichiers virtuel ("/").

Tout cela peut être accompli par l'application, mais ceci le fait simplement pour vous. N'hésitez pas à ajouter manuellement d'autres éléments au chemin de recherche.

Paramètres

organization Nom de votre entreprise/groupe/etc. à utiliser comme nom de répertoire, donc gardez-le petit et sans fioritures.
appName Nom spécifique du programme pour votre programme, afin de le distinguer des autres programmes utilisant PhysicsFS.
archiveExt Extension de fichier utilisée par votre programme pour spécifier une archive. Par exemple, Quake 3 utilise "pk3", même s'il s'agit simplement de fichiers zip. Spécifiez NULL pour ne pas extraire automatiquement les archives. Ne spécifiez pas le caractère '.' ; si vous souhaitez rechercher des fichiers ZIP, spécifiez "ZIP" et non ".ZIP" ... la recherche d'archives ne tient pas compte de la casse.
includeCdRoms Non nul pour inclure les CD-ROM dans le chemin de recherche, et (si (archiveExt) != NULL) pour y rechercher des archives. Cela peut entraîner un blocage important lors de l'accès aux disques, et s'il n'y a pas de disques dans le lecteur (ou même pas montés sur les systèmes Unix), ils peuvent ne pas être disponibles de toute façon. Vous pourriez vouloir spécifier zéro et gérer vous-même la configuration du disque.
archivesFirst Non nul pour préfixer les archives au chemin de recherche. Zéro pour les ajouter. Ignoré si !(archiveExt).

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

Convertit une chaîne Latin1 en chaîne UTF-8. Les chaînes Latin1 sont codées sur 8 bits par caractère : un encodage populaire "high ASCII".

Pour s'assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon de taille double par rapport au tampon source. UTF-8 étend les points de code Latin1 supérieurs à 127 de 1 à 2 octets, la chaîne peut donc s'agrandir dans certains cas.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Veuillez noter que nous ne fournissons pas de convertisseur UTF-8 vers Latin1, car Latin1 ne peut pas exprimer la plupart des points de code Unicode. C'est un encodage hérité ; vous devriez toujours vous en éloigner.

Paramètres

src Chaîne source terminée par un caractère nul au format Latin1.
dst Tampon pour stocker la chaîne UTF-8 convertie.
len Taille, en octets, du tampon de destination.

UTF-8 utilise de un à quatre octets par caractère, mais UTF-16 en utilise toujours de deux à quatre, donc une chaîne entièrement ASCII basse doublera de taille ! Les caractères UTF-16 qui prendraient quatre octets prennent également quatre octets en UTF-8, vous n'avez donc pas besoin d'allouer 4 fois l'espace juste au cas où : le double suffira.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par null et n'auront jamais une paire de substitution UTF-16 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Paramètres

src Chaîne source terminée par null au format UTF-8.
dst Tampon pour stocker la chaîne UTF-16 convertie.
len Taille, en octets, du tampon de destination.
