PHYSFS_enumerate

Esto es lo mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado desde el callback: si estás buscando algo específico, una vez que lo encuentres, puedes indicar a PhysicsFS que detenga la enumeración. Esto se utiliza con PHYSFS_enumerate(), ¡que esperamos haber hecho correctamente esta vez! :)

Parámetros

data Un puntero de datos personalizado, pasado por la API que finalmente llamó al callback.
origdir Una cadena con el camino completo, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, es el directorio en el que solicitaste la enumeración, pasado en el callback para tu comodidad.
fname El nombre del archivo que se está enumerando. No estará ordenado alfabéticamente en comparación con otros callbacks que se hayan llamado, y no contendrá el camino completo. Puedes reconstruir el camino completo con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

Devolución

Un valor de PHYSFS_EnumerateCallbackResult. Todos los demás valores son (actualmente) indefinidos; no los uses.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de la función de callback que enumera archivos.

Advertencia

Desde PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate(); ofrece más control sobre el proceso.

Estos se utilizan para informar a un llamador original una lista de entradas de directorio, una entrada por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de las cadenas.

Estos callbacks se utilizan, desde PhysicsFS 1.1, como alternativa a funciones que devuelven listas que deben ser liberadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas previamente.

Ten en cuenta que la ordenación prometida en las versiones de lista no es necesariamente así en las versiones de callback. Consulta la documentación de APIs específicas, pero las cadenas no estarán necesariamente ordenadas como esperas y podrías obtener cadenas duplicadas.

data Un puntero de datos personalizado, pasado por la API que finalmente llamó al callback.
origdir Una cadena con el camino completo, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, es el directorio en el que solicitaste la enumeración, pasado en el callback para tu comodidad.
fname El nombre del archivo que se está enumerando. No estará ordenado alfabéticamente en comparación con otros callbacks que se hayan llamado, y no contendrá el camino completo. Puedes reconstruir el camino completo con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers d'un répertoire du chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique sauf la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * On a trouvé [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis d'être dans aucun ordre que ce soit. Il n'y a pas de tri effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit le tri alphabétique. Cette forme signale tout ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons pas garantir l'ordre dans lequel elle découvrira les données. Tout tri que vous trouverez dans ces appels de fonction est purement une coïncidence. Ne comptez pas dessus. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les fonctions de rappel elles-mêmes sont capables de signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération complètement, et l'appelant ne saurait pas qu'il avait perdu des données en cours de route.

Maintenant, l'appelant peut être sûr qu'il a obtenu un ensemble complet de données, et sa fonction de rappel a le contrôle s'il veut que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur la façon dont votre fonction de rappel doit se comporter.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

Retourne

Non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel retourne PHYSFS_ENUM_STOP pour s'arrêter tôt, cela sera considéré comme un succès. Les fonctions de rappel retournant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtient une liste de fichiers d'un répertoire du chemin de recherche.

Attention

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction retournait autant d'éléments que possible face à une condition d'échec (manque de mémoire, erreur d'E/S disque, etc.). Comme cela signifiait que les applications ne pouvaient pas distinguer un succès complet d'un échec partiel, et comme la fonction pouvait toujours retourner NULL pour signaler des échecs catastrophiques de toute façon, dans PhysicsFS 2.1, la politique de cette fonction a changé : elle retournera soit une liste de résultats complets, soit elle retournera NULL pour tout échec de quelque nature que ce soit, afin que nous puissions garantir que l'énumération s'est terminée et n'a pas de lacunes dans ses résultats.

Les répertoires correspondants sont interpolés. C'est-à-dire que si "C:\monrep" se trouve dans le chemin de recherche et contient un répertoire "saves" contenant "x.sav", "y.sav", et "z.sav", et qu'il existe également un "C:\repuser" dans le chemin de recherche qui a un sous-répertoire "saves" avec "w.sav", alors le code suivant :

char **rc = PHYSFS_enumerateFiles("saves");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * On a trouvé [%s].\n", *i);
PHYSFS_freeList(rc);
* On a trouvé [x.sav].
* On a trouvé [y.sav].
* On a trouvé [z.sav].
* On a trouvé [w.sav]..fi
N'hésitez pas à trier la liste comme vous le souhaitez. Cependant, les données retournées ne contiendront jamais de doublons et seront toujours triées par ordre alphabétique (ou plutôt : Unicode sensible à la casse) pour vous.
N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur de retour de cette fonction lorsque vous avez terminé.

dir répertoire en notation indépendante de la plateforme à énumérer.

Obtenir le chemin spécifique à l'utilisateur et à l'application où les fichiers peuvent être écrits. Fonction utilitaire.

Obtenir le « répertoire de préférences ». C'est là que les utilisateurs peuvent écrire des fichiers personnels (préférences et sauvegardes, etc.) spécifiques à votre application. Ce répertoire est unique par utilisateur, par application.

Sous Mac OS X, cela pourrait ressembler à : "/Users/bob/Library/Application Support/Mon Programme"

(etc.)

Vous devriez probablement utiliser le répertoire de préférences pour votre répertoire d'écriture, et également le placer près du début de votre chemin de recherche. void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archivés contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, le fichier référencé sera ouvert de manière transparente.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins de lecture et d'écriture, compromettant la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Ceci est davantage destiné aux conteneurs d'un langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une raison valable de créer un lien symbolique, vous ne devriez donc pas le désactiver, à moins que vous ne pensiez qu'il existe un danger spécifique à les autoriser.

Les liens symboliques ne seront visibles que lorsqu'il s'agira de noms de fichiers dans une notation indépendante du système. C'est-à-dire que lorsque vous définissez vos chemins de recherche et d'écriture, etc., les liens symboliques ne seront jamais visibles.

Note : PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera en aucun cas suivi. Si les liens symboliques ne sont pas autorisés via cette fonction, PHYSFS_stat() les ignorera et traitera la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée après l'appel de PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

Set the buffering on an open file handle. This is useful for improving performance on slow media or for reducing overhead. A buffer size of zero will disable buffering, effectively returning the file handle to its unbuffered state.

PhysicsFS file handles are unbuffered by default.

Convertit une chaîne UTF-16 en une chaîne UTF-8.

Attention

Cette fonction ne signalera pas d'erreur s'il y a des séquences UTF-16 invalides dans la chaîne source. Elle les remplacera par un caractère '?' et continuera.

Les chaînes UTF-16 ont 16 bits par caractère (sauf certains caractères, qui en ont 32) : TCHAR sous Windows, lors de la compilation avec le support Unicode. Les versions modernes de Windows utilisent UTF-16. Les versions de Windows avant 2000 utilisaient TCHAR, mais ne géraient que UCS-2. Si vous n'êtes pas sûr, vous devriez utiliser UTF-16 à ce stade sous Windows.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UTF-8 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

str2 Deuxième chaîne à comparer.

Retourne

-1 si str1 est "inférieur à" str2, 1 si "supérieur à", 0 si égal.

Convertir una cadena UTF-8 a una cadena UTF-16.

Advertencia

Esta función no reportará un error si hay secuencias UTF-8 inválidas en la cadena de entrada. Reemplazará estas secuencias con un carácter '?' y continuará procesando.
