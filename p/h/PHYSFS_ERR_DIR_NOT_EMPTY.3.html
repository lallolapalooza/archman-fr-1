PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du rappel : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être dans un ordre alphabétique par rapport aux autres rappels qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent des fichiers.

Avertissement

À partir de PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; il vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de chaînes.

Ces rappels sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le cas dans les versions de rappel. Consultez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

Obtient une liste de fichiers d'un répertoire spécifié, en utilisant une fonction de rappel définie par l'utilisateur, avec signalement d'erreurs. En interne, PHYSFS_enumerateFiles() n'appelle que cette fonction, puis construit une liste avant de la retourner à l'application. La fonctionnalité est donc identique, mais la manière dont les informations sont présentées à l'application diffère.

Bien que PHYSFS_enumerateFiles() ne retourne pas un tableau, cette fonction appelle une fonction spécifiée par l'utilisateur une fois pour chaque élément du répertoire :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donner plus d'informations, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments passés à la fonction de rappel ne sont pas garantis d'être dans un ordre spécifique. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un tri alphabétique. Cette méthode signale ce qui est trouvé dans chaque fichier avant de passer au suivant. Même à l'intérieur d'un fichier, nous ne pouvons pas garantir l'ordre dans lequel les données sont découvertes. Tout ordre que vous pourriez constater dans ces rappels est purement fortuit. Vous ne devez pas vous y fier. Comme cette fonction parcourt toute la liste des fichiers, vous pourriez recevoir des noms de fichiers en double.

Cette API et les fonctions de rappel elles-mêmes peuvent signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même si elles ne recherchaient qu'un objet spécifique et voulaient s'arrêter après, ou si elles rencontraient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application ; il pouvait simplement ignorer des éléments ou arrêter l'énumération, et l'appelant ne saurait pas qu'il avait perdu des données.

Désormais, l'appelant peut être assuré d'avoir obtenu un ensemble complet de données, et sa fonction de rappel contrôle si l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement attendu de votre fonction de rappel.

dir Répertoire, en notation indépendante du système, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

Retour

Non nul en cas de succès, nul en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel retourne PHYSFS_ENUM_STOP, cela est considéré comme un succès. Les fonctions de rappel retournant PHYSFS_ENUM_ERROR feront que cette fonction retournera zéro et définira le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

char **PHYSFS_enumerateFiles (const char * dir)

Obtient une liste de fichiers d'un répertoire à partir d'un chemin de recherche.

Avertissement

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction retournait autant d'éléments que possible en cas de condition d'échec (erreur de mémoire, E/S disque, etc.). Cela empêchait les applications de distinguer un succès complet d'un échec partiel, et étant donné que la fonction pouvait toujours retourner NULL pour signaler un échec catastrophique, dans PhysicsFS 2.1, la politique de cette fonction a changé : elle retournera une liste complète de résultats ou NULL en cas de tout échec, nous pouvons ainsi garantir que l'énumération a été effectuée de manière transparente dans ses résultats.

Les répertoires qui correspondent sont interpolés. Autrement dit, si "C:\mydir" est sur le chemin de recherche et qu'il contient un répertoire "savegames" contenant "x.sav", "y.sav", "z.sav" et qu'il y a également un répertoire "C:\userdir" sur le chemin de recherche qui contient un sous-répertoire "savegames" avec "w.sav", alors le code suivant :

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
produira la sortie :
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav].

Cela libère la liste afin que vous puissiez la trier comme vous le souhaitez. Cependant, les données retournées ne contiendront toujours aucun doublon et seront triées par ordre alphabétique (plus précisément : triées par Unicode sensible à la casse) pour vous.

N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur retournée par cette fonction lorsque vous avez terminé de l'utiliser.

dir répertoire en notation indépendante du système à énumérer.

(buf) doit rester valide jusqu'à ce que le fichier soit démonté. Lorsque le fichier sera démonté, le système appellera (del)(buf), ce qui vous donnera l'occasion de libérer vos ressources. (del) peut être NULL, auquel cas le système n'essaiera pas de libérer le buffer.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins de recherche et d'écriture, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné à la mise en bac à sable du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait très bien avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés via cette fonction, PHYSFS_stat() les ignore, et traiterait la requête comme si le chemin n'existait pas du tout.

La permission de lien symbolique peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Fait d'un sous-répertoire d'une archive le répertoire racine. Ceci vous permet de circonscrire les fichiers accessibles à une archive spécifique. Retour

Non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

UTF-8 utilise de un à quatre octets par caractère, mais UTF-16 utilise toujours de deux à quatre, donc une chaîne entièrement en ASCII basique doublera de taille ! Les caractères UTF-16 qui nécessiteraient quatre octets prennent également quatre octets en UTF-8, vous n'avez donc pas besoin d'allouer 4 fois l'espace par sécurité : le double suffira.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais une paire de substitution UTF-16 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Paramètres

src Chaîne source terminée par un caractère nul au format UTF-8.
dst Tampon pour stocker la chaîne UTF-16 convertie.
len Taille, en octets, du tampon de destination.
