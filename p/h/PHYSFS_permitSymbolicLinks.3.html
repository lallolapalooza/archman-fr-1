typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent les fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; il vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de quelque chaîne que ce soit.

Ces callbacks sont utilisés, depuis PhysicsFS 1.1, comme une alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes au préalable.

Soyez conscient que l'ordre des données promis dans les versions basées sur des listes n'est pas nécessairement le cas dans les versions basées sur des callbacks. Consultez la documentation des API spécifiques, mais les chaînes pourraient ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes en double.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

« Fold » un point de code Unicode vers un équivalent en minuscules. (Ceci est pour une utilisation limitée et hardcore. Si vous ne voyez pas immédiatement une nécessité de la part de votre application, vous pouvez l'ignorer pour toujours.)

Elle convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux qui n'ont pas d'équivalent en minuscules seront renvoyés sans modification.

Remarque : Vous pouvez obtenir plusieurs points de code en réponse ! Par exemple, le "Eszett" allemand sera transformé en deux points de code minuscules 's'. La théorie est que si vous transformez deux chaînes, l'une avec un Eszett et l'autre avec "SS", elles correspondront.

Avertissement

Ceux qui étudient Unicode connaissent le problème du « I » turc. Cette API ne le gère pas. Supposez que cette lettre dans tout Unicode sera mal transformée. Si vous ne savez pas de quoi il s'agit, vous pouvez ignorer ce problème pour la majorité de la planète, mais la perfection est impossible.

Paramètres

from Le point de code à transformer.
to Le tampon où les valeurs de points de code transformés sont stockées. Il doit pointer vers un espace pour au moins 3 emplacements PHYSFS_uint32.

Retour

Le nombre de points de code produits. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialise la bibliothèque PhysicsFS. Cela ferme tous les fichiers ouverts par PhysicsFS, efface les chemins de recherche/écriture, libère la mémoire et invalide tous les handles de fichiers que vous possédez.

Remarque : cet appel peut échouer s'il y a un fichier ouvert en écriture qui ne se ferme pas (par exemple, le système d'exploitation mettait en mémoire tampon des écritures vers un système de fichiers réseau, et le serveur de fichiers a échoué, ou un disque dur a échoué, etc.). Il est généralement préférable de fermer vous-même tous les handles d'écriture avant d'appeler cette fonction, afin de gérer gracieusement un échec spécifique.

Une fois correctement désinitialisé, vous pouvez appeler à nouveau PHYSFS_init() pour redémarrer le sous-système. Tous les états par défaut de l'API sont restaurés à ce stade, à l'exception des éventuels allocateurs personnalisés que vous avez spécifiés, qui survivent entre les initialisations.

Retour

Non nul en cas de succès, nul en cas d'erreur. Les détails de l'erreur peuvent être obtenus via PHYSFS_getLastError(). S'il y a eu un échec, l'état de PhysFS est indéterminé et probablement mal construit.

int PHYSFS_delete (const char * filename)

Supprime un fichier ou un répertoire. (filename) est spécifié dans une notation indépendante du système de fichiers par rapport au répertoire d'écriture.

Un répertoire doit être vide avant de pouvoir être supprimé.

La suppression d'un lien symbolique supprimera le lien symbolique, et non ce vers quoi il pointe, que ce soit autorisé ou non.

Donc, si vous avez le répertoire d'écriture configuré sur "C:\monjeu\writedir" et que vous appelez PHYSFS_delete("telechargements/cartes/niveau1.map"), le fichier "C:\monjeu\writedir\telechargements\cartes\niveau1.map" sera supprimé du système de fichiers physique, s'il existe et que le système d'exploitation le permet.

Remarque : Sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont un handle ouvert sur celui-ci (y compris votre programme) ne fermeront pas leurs handles.

Dans la plupart des cas, les bits qui composent le fichier existent toujours, mais sont disponibles pour être réécrits à l'avenir. Ne considérez pas cela comme une méthode de sécurité ou similaire.

Paramètres

filename Le nom du fichier à supprimer.

Retour

Non nul en cas de succès, nul en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_deregisterArchiver (const char * ext)

Supprime un archiveur du système. Si pour une raison quelconque vous n'avez besoin que de votre archiveur précédemment enregistré pendant une partie de la durée de vie de votre application, vous pouvez le retirer du système via cette fonction une fois que vous l'avez utilisé.

Cette fonction échoue s'il y a un archiveur ouvert qui utilise cet archiveur.

Cette fonction peut également retirer des archiveurs intégrés, tels que la prise en charge de .zip, et autres. Cela pourrait être utile dans certains cas, comme la désactivation de la prise en charge ou son remplacement par une implémentation personnalisée. Une fois qu'un archiveur intégré est désactivé de cette manière, PhysicsFS n'offre aucun mécanisme pour le récupérer, sauf en appelant PHYSFS_deinit() et PHYSFS_init() à nouveau.

PHYSFS_deinit() va

automatiquement désenregistrer tous les archiveurs, de sorte que vous n'avez pas besoin de désenregistrer explicitement le vôtre si vous arrêtez proprement.

Paramètres

ext Extension de nom de fichier que l'archiveur gère.

Retourne

Zéro en cas d'erreur, non-zéro en cas de succès.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas de tableau. Elle appelle plutôt une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons trouvé [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés au rappel ne sont pas garantis dans un ordre quelconque. Il n'y a pas de tri à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme rapporte ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons pas garantir l'ordre dans lequel elle découvrira les données. Tout tri que vous trouvez dans ces rappels n'est que de la pure chance. N'en dépendez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers en double.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient en alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération directement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr qu'il a obtenu un ensemble de données complet, et son rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation pour PHYSFS_EnumerateCallback pour les détails sur le comportement attendu de votre rappel.

d Données définies par l'application passées au rappel. Peut être NULL.

Retourne

non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel retourne PHYSFS_ENUM_STOP pour s'arrêter tôt, cela sera considéré comme un succès. Les rappels retournant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add a file or directory to the search path. If it is a duplicate, the archive is not added again, though the function will succeed. You may not add the same file to two different mount points: duplicate checking is done against the archive, not the mount point. When mounting an archive, it's added to a virtual filesystem...all files from all mounted archives are interpolated into a single file hierarchy. Two archives mounted at the same place (or an archive that has files that overlap a mount point) can have overlapping files: in such a case, the archive closest in the search path is chosen, and the other files are inaccessible to the application. This allows archives to replace previous revisions; you can use the mount mechanism to place files at a specific point in the file tree and avoid overlaps; this is useful for downloaded mods that can stomp on application data or themselves, for example.

The mount point does not need to exist before mounting, which is different from what is expected in the concept of "mounting" on Unix. Also, more than one archive can be mounted at the same mount point, or mount points and archive contents can overlap...the interpolation mechanics still work.

It is permitted to specify a symbolic link to an archive or directory, regardless of the state of PHYSFS_permitSymbolicLinks(). This function only concerns itself with symbolic links within the mounted archive or directory.

Parameters

newDir Directory or archive to add to the path, in system-dependent notation.
mountPoint Location in the interpolated tree where this archive will be mounted, in system-independent notation. NULL or "" is equivalent to "/".
appendToPath Non-zero to append to the search path, zero to prepend.

Returns

Non-zero on success, zero on error (invalid archive, directory not found, etc). Use PHYSFS_getLastErrorCode() to get the specific error.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné au sandboxing du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait très bien avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne ressentiez un danger spécifique à les autoriser, vous devriez les permettre.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers dans la notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

allow non nul pour autoriser les liens symboliques, zéro pour les interdire.

Convertit une chaîne UTF-8 en une chaîne UTF-16.

Attention

Cette fonction ne signalera pas d'erreur s'il y a des séquences UTF-8 invalides dans la chaîne source. Elles seront remplacées par un caractère '?' et la fonction continuera.

Les chaînes UTF-16 sont de 16 bits par caractère (sauf pour certains caractères, qui sont de 32 bits) : TCHAR sous Windows, lorsque vous compilez avec le support Unicode. Les versions modernes de Windows utilisent UTF-16. Les versions de Windows antérieures à 2000 utilisaient TCHAR, mais ne supportaient que UCS-2. UTF-16 est UCS-2, à l'exception des caractères qui font 4 octets, qui ne sont de toute façon pas représentables en UCS-2. Si vous n'êtes pas sûr, vous devriez utiliser UTF-16 à ce stade sous Windows.

Pour vous assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon dont la taille est le double de celle du tampon source. UTF-8 utilise de un à quatre octets par caractère, mais UTF-16 utilise toujours de deux à quatre, donc une chaîne entièrement ASCII bas doublera de taille ! Les caractères UTF-16 qui nécessiteraient quatre octets en nécessitent également quatre en UTF-8, vous n'avez donc pas besoin d'allouer 4x l'espace par précaution : le double suffira.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par null et ne contiendront jamais une paire de substitution UTF-16 incomplète à la fin. Si la taille du tampon est de 0, cette fonction ne fait rien.

Paramètres

src Chaîne source terminée par null au format UTF-8.
dst Tampon pour stocker la chaîne UTF-16 convertie.
len Taille, en octets, du tampon de destination.

Écrit des données dans un descripteur de fichier PhysicsFS. Le fichier doit être ouvert en écriture.

Veuillez noter que bien que (len) soit un entier non signé de 64 bits, vous êtes limité à 63 bits (9223372036854775807 octets), nous pouvons donc retourner une valeur négative en cas d'erreur. Pour les systèmes sans type de données 64 bits, vous êtes limité à 31 bits (0x7FFFFFFF, soit 2147483647 octets).
