Documentation des définitions de macros

#define PHYSFS_file PHYSFS_File

Définition de compatibilité API 1.0. PHYSFS_file est identique à PHYSFS_File. Cette #define est là pour la compatibilité ascendante avec l'API 1.0, qui avait une convention de capitalisation incohérente dans ce cas. Le nouveau code doit utiliser PHYSFS_File, car cette #define pourrait disparaître un jour.

#define PHYSFS_VERSION( x)

Valeur :

{ \
    (x)->major = PHYSFS_VER_MAJOR; \
    (x)->minor = PHYSFS_VER_MINOR; \
    (x)->patch = PHYSFS_VER_PATCH; \
}

Macro pour déterminer la version de PhysicsFS compilée avec le programme. Cette macro remplit une structure PHYSFS_Version.

avec la version de la bibliothèque contre laquelle vous avez compilé. Ceci est déterminé par l'en-tête que le compilateur utilise. Notez que si vous avez lié dynamiquement la bibliothèque, vous pourriez avoir une version légèrement plus récente ou plus ancienne à l'exécution. Cette version peut être déterminée avec PHYSFS_getLinkedVersion(), qui, contrairement à PHYSFS_VERSION, n'est pas une macro.

Paramètres

x Un pointeur vers une structure PHYSFS_Version à initialiser.

typedef PHYSFS_EnumerateCallbackResult(* PHYSFS_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Valeurs de retour possibles pour PHYSFS_EnumerateCallback. Signature de fonction pour les rappels qui énumèrent et retournent des résultats.

Ces valeurs dictent si un rappel d'énumération doit continuer à être déclenché, ou s'arrêter (et pourquoi il s'arrête).

Voir aussi

PHYSFS_EnumerateCallback

PHYSFS_enumerate

Ceci est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du rappel : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez indiquer à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être dans un ordre alphabétique par rapport à d'autres rappels qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent des fichiers.

Attention

À partir de PhysicsFS 2.1, utilisez plutôt PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; il vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire d'une chaîne.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers d'un répertoire du chemin de recherche, en utilisant un rappel défini par l'application, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique sauf pour la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons obtenu [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés au rappel ne sont garantis dans aucun ordre quelconque. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une seule archive, nous ne pouvons pas garantir l'ordre dans lequel elle découvrira les données. Tout tri que vous trouvez dans ces rappels est purement le fruit du hasard. Ne vous y fiez pas. Comme cette fonction parcourt toute la liste des archives, vous pourriez recevoir des noms de fichiers en double.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter tous les éléments énumérés, même s'ils ne recherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement sauter des éléments ou arrêter l'énumération, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr qu'il a obtenu un ensemble de données complet, et son rappel a le contrôle s'il veut que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur le comportement attendu de votre rappel.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées au rappel. Peut être NULL.

Retourne

Non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel retourne PHYSFS_ENUM_STOP pour s'arrêter tôt, cela sera considéré comme un succès. Les rappels retournant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur sur PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtient une liste de fichiers d'un répertoire du chemin de recherche.

Attention

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction retournait autant d'éléments que possible face à une condition d'échec (manque de mémoire, erreur d'E/S disque, etc.). Comme cela empêchait les applications de distinguer un succès complet d'un échec partiel, et comme la fonction pouvait toujours retourner NULL pour signaler des échecs catastrophiques de toute façon, dans PhysicsFS 2.1, la politique de cette fonction a changé : elle retournera soit une liste de résultats complets, soit elle retournera NULL pour tout échec, de quelque nature que ce soit, afin que nous puissions garantir que l'énumération s'est déroulée jusqu'à son terme et n'a pas de lacunes dans ses résultats.

Les répertoires correspondants sont interpolés. C'est-à-dire que si "C:\monrep" se trouve dans le chemin de recherche et contient un répertoire "sauvegardes" qui contient "x.sav", "y.sav", et "z.sav", et qu'il existe également un répertoire "C:\repuser" dans le chemin de recherche qui possède un sous-répertoire "sauvegardes" avec "w.sav", alors le code suivant :

char **rc = PHYSFS_enumerateFiles("sauvegardes");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Nous avons obtenu [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi
N'hésitez pas à trier la liste comme vous le souhaitez. Cependant, les données retournées ne contiendront toujours aucun doublon et seront toujours triées par ordre alphabétique (ou plus précisément : Unicode sensible à la casse).

const char * PHYSFS_getPrefDir(const char *org, const char *app)

Obtenir le chemin spécifique à l'utilisateur et à l'application où les fichiers peuvent être écrits. Fonction d'aide.

Obtenir le "répertoire de préférences". Ceci est destiné à être l'endroit où les utilisateurs peuvent écrire des fichiers personnels (préférences et sauvegardes, etc.) spécifiques à votre application. Ce répertoire est unique par utilisateur, par application.

Sous Linux, cela pourrait ressembler à : "/home/bob/.local/share/My Program Name"

Sous Mac OS X, cela pourrait ressembler à : "/Users/bob/Library/Application Support/My Program Name"

(etc.)

Vous devriez probablement utiliser le répertoire de préférences pour votre répertoire d'écriture, et également le placer près du début de votre chemin de recherche. Deux fichiers montés au même endroit (ou un fichier avec des fichiers se chevauchant sur un point de montage) peuvent avoir des fichiers qui se chevauchent : dans ce cas, le fichier le plus tôt dans le chemin de recherche est sélectionné, et les autres fichiers ne sont pas accessibles à l'application. Cela permet d'utiliser des fichiers pour remplacer des versions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des fichiers à un endroit spécifique de l'arborescence des fichiers et éviter les chevauchements ; ceci est utile pour les mods téléchargeables qui peuvent se chevaucher sur les données de l'application ou entre eux, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que l'on attend des utilisateurs familiers avec le concept Unix de « montage ». De plus, plusieurs fichiers peuvent être montés au même point de montage, ou les points de montage et le contenu des fichiers peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours normalement.

Il est permis de spécifier un lien symbolique vers un fichier ou un répertoire, indépendamment de l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne gère que les liens symboliques à l'intérieur du répertoire ou du fichier monté.

Ajoute une archive, contenue dans un descripteur PHYSFS_File, au chemin de recherche.

Attention

Les archives dans les archives peuvent être très lentes ! Bien qu'un PHYSFS_File puisse effectuer des recherches même lorsque les données sont compressées, il peut le faire en revenant au début et en décompressant tout avant le point de recherche. L'utilisation normale des archives peut effectuer de nombreuses recherches en arrière-plan. Par conséquent, vous pourriez trouver l'utilisation normale des archives extrêmement pénible si elles sont montées de cette manière. Planifiez en conséquence : si vous avez, par exemple, un fichier .zip auto-extractible et que vous souhaitez monter quelque chose à l'intérieur, compressez le contenu de l'archive interne et assurez-vous que le fichier .zip externe ne compresse pas l'archive interne.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (transparence) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous emmener en dehors des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné à l'isolation d'un langage de script de programme, au cas où des scripts non fiables essaieraient de compromettre le système. De manière générale, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors de la manipulation de noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés via cette fonction, PHYSFS_stat() les ignore, et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser les liens.

Pour s'assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon de double la taille du tampon source. UTF-8 développe les points de code latin1 supérieurs à 127 de 1 à 2 octets, donc la chaîne peut s'agrandir dans certains cas.

int PHYSFS_utf8stricmp (const char * str1, const char * str2)

Comparaison insensible à la casse de deux chaînes UTF-8. Ceci est un remplacement de strcasecmp/stricmp qui attend que les deux chaînes soient encodées en UTF-8. Il effectuera un « repliement de casse » pour déterminer si les points de code Unicode dans les chaînes correspondent.

Si les deux chaînes sont exclusivement des caractères ASCII bas, cela fonctionnera correctement, car c'est aussi du UTF-8 valide. S'il y a des caractères ASCII hauts, cela ne fera pas ce que vous attendez !

Il indiquera quelle chaîne est « supérieure » à l'autre, mais sachez que cela ne signifie pas nécessairement quelque chose : 'a' peut être « inférieur à » 'b', mais un kuten japonais n'a pas de relation alphabétique significative avec un lambda grec, mais pouvoir attribuer une « valeur » fiable rend les algorithmes de tri possibles, même s'ils ne sont pas entièrement sains. Dans la plupart des cas, il convient de traiter la valeur de retour comme « égal » ou « différent ».

Comme stricmp, ceci attend que les deux chaînes soient terminées par un caractère nul.

Paramètres

str1 Première chaîne à comparer.
str2 Seconde chaîne à comparer.

Retourne

-1 si str1 est « inférieur à » str2, 1 s'il est « supérieur à », 0 s'ils sont égaux.
