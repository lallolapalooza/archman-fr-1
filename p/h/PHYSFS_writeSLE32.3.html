int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Fold" a Unicode codepoint to a lowercase equivalent. (This is for limited, hardcore use. If you don't immediately see a need for it, you can probably ignore this forever.)

This will convert a Unicode codepoint into its lowercase equivalent. Bogus codepoints and codepoints without a lowercase equivalent will be returned unconverted.

Note that you might get multiple codepoints in return! The German Eszett, for example, will fold down to two lowercase latin 's' codepoints. The theory is that if you fold two strings, one with an Eszett and one with "SS" down, they will match.

Warning

Anyone that is a student of Unicode knows about the "Turkish I" problem. This API does not handle it. Assume this one letter in all of Unicode will definitely fold sort of incorrectly. If you don't know what this is about, you can probably ignore this problem for most of the planet, but perfection is impossible.

Parameters

from The codepoint to fold.
to Buffer to store the folded codepoint values into. This should point to space for at least 3 PHYSFS_uint32 slots.

Returns

The number of codepoints the folding produced. Between 1 and 3.

int PHYSFS_deinit (void )

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). It is usually best to close all write handles yourself before calling this function, so that you can gracefully handle a specific failure.

Once successfully deinitialized, PHYSFS_init() can be called again to restart the subsystem. All default API states are restored at this point, with the exception of any custom allocator you might have specified, which survives between initializations.

Returns

nonzero on success, zero on error. Specifics of the error can be gleaned from PHYSFS_getLastError(). If failure, state of PhysFS is undefined, and probably badly screwed up.

int PHYSFS_delete (const char * filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

Chances are, the bits that make up the file still exist, they are just made available to be written over at a later point. Don't consider this a security method or anything. :)

Parameters

filename Filename to delete.

Returns

nonzero on success, zero on error. Use PHYSFS_getLastErrorCode() to obtain the specific error.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtener una lista de archivos de una ruta de búsqueda, usando un callback definido por el usuario, con errores reportados. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego construye una lista antes de devolver a la aplicación, así que la funcionalidad es idéntica, salvo cómo la información se presenta a la aplicación.

Aunque PHYSFS_enumerateFiles() no devuelve un array, esta función llama a una función especificada por el aplicador una vez por cada elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // me pide más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Los elementos enviados al callback no están garantizados para estar en ningún orden específico. No se realiza ningún ordenamiento en este nivel, y si lo necesitas, deberías usar PHYSFS_enumerateFiles(), que garantiza el orden alfabético. Esta forma reporta lo que se descubre en cada archivo, antes de pasar a la siguiente. Even within one archive, we can't guarantee the order in which data is discovered. Cualquier orden que encuentres en estos callbacks es pura suerte. No dejes de confiar en ello. Como esta camina por toda la lista de archivos, puedes recibir nombres de archivos duplicados.

Esta API y los callbacks mismos pueden reportar errores. Antes de esta API, los callbacks tenían que aceptar cada elemento enumerado, incluso si solo buscaban un objeto específico y querían detenerse después, o tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS mismo tenía un problema (error de disco o lo que sea), no podría reportarlo a la aplicación que lo llama, simplemente ignoraría los elementos o detenería la enumeración, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de haber obtenido un conjunto completo de datos, y si quiere detener la enumeración temprano, su callback tiene control. Ver la documentación de PHYSFS_EnumerateCallback para detalles sobre cómo debe comportarse tu callback.

c Función de callback para notificar sobre elementos de la ruta de búsqueda.
d Datos definidos por el aplicador que se pasan al callback. Puede ser NULL.

Retorno

No cero en éxito, cero en error. Usa PHYSFS_getLastErrorCode() para obtener el error específico. Si el callback devuelve PHYSFS_ENUM_STOP, este se considera éxito. Callbacks devolviendo PHYSFS_ENUM_ERROR harán este función retornar cero y establecerá el código de error a PHYSFS_ERR_APP_CALLBACK.

* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav].

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Returns

nonzero if added to path, zero on failure (bogus archive, dir missing, etc). Use PHYSFS_getLastErrorCode() to obtain the specific error.

Ajoute une archive, contenue dans une poignée PHYSFS_File, au chemin de recherche.

Attention

Sauf si vous avez un besoin spécial de bas niveau, vous devriez utiliser PHYSFS_mount() à la place de ceci.

Les archives dans les archives peuvent être très lentes ! Bien qu'un PHYSFS_File puisse effectuer un seek même lorsque les données sont compressées, il peut le faire en revenant au début et en décompressant tout avant le point de seek. L'utilisation normale d'archives peut effectuer de nombreux seek en arrière-plan. Ainsi, vous pourriez trouver l'utilisation normale d'archives extrêmement pénible si elles sont montées de cette manière. Prévoyez en conséquence : si vous avez, par exemple, un fichier .zip auto-extractible, et que vous voulez monter quelque chose dedans, compressez le contenu de l'archive interne et assurez-vous que le fichier .zip externe ne compresse pas l'archive interne également.

Cette fonction opère comme PHYSFS_mount(), mais prend une poignée PHYSFS_File au lieu d'un nom de chemin. Cette poignée contient toutes les données de l'archive, et est utilisée à la place d'un vrai fichier dans le système de fichiers physique. Le PHYSFS_File peut être basé sur un vrai fichier dans le système de fichiers physique, mais ce n'est pas nécessaire. L'utilisation la plus courante pour ceci est probablement de monter des archives stockées à l'intérieur d'autres archives.

Elle est utilisée pour optimiser la sélection de l'archiveur (si vous le nommez XXXXX.zip, nous pourrions essayer l'archiveur ZIP en premier, par exemple, ou choisir directement un archiveur qui ne peut faire confiance à la validité des données que par l'extension du nom de fichier). Si cette fonction échoue, PHYSFS_close(file) n'est pas appelée.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, celui-ci sera ouvert de manière transparente pour ouvrir le fichier auquel il fait référence.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous mener en dehors des chemins de lecture et d'écriture, compromettant la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Notez que cela est davantage destiné au sandboxing d'un langage de script du programme, au cas où des scripts non fiables tenteraient de compromettre le système. En général, un utilisateur peut avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas les désactiver, à moins que vous ne pensiez qu'il y a un danger spécifique à les autoriser.

Les liens symboliques ne sont vérifiés que lorsqu'ils sont gérés par des noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire, lorsque vos chemins de recherche et d'écriture sont définis, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignorera et traitera la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désactiver le lien.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Fait d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de limiter les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt, monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer la racine d'une archive à tout moment, en modifiant l'arborescence de fichiers interpolée (selon où les chemins changent, une archive différente peut fournir divers fichiers). La définition d'une nouvelle racine n'est pas limitée aux archives dans le chemin de recherche ; vous pouvez également en définir une sur le répertoire d'écriture, ce qui pourrait être utile si vous avez des fichiers ouverts en écriture et ne pouvez donc pas changer le répertoire d'écriture pour le moment.

Ce n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme racine d'une archive ; cependant, aucun fichier ne sera visible dans ce cas. Si les répertoires manquants finissent par être créés (un mkdir sur le système de fichiers physique, etc.) alors cela sera reflété dans l'arbre interpolé.

archive répertoire/archive sur lequel changer la racine.
subdir nouveau sous-répertoire à faire la racine de cette archive.

Retourne

non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

Paramètres

file Handle de fichier PhysicsFS vers lequel écrire.
val Valeur à convertir et à écrire.

Retourne

Zéro en cas d'échec, non nul en cas de succès. En cas d'échec, vous pouvez trouver ce qui s'est passé en appelant PHYSFS_getLastErrorCode().

Attention

Rappelez-vous que PHYSFS_uint64 n'a que 32 bits sur les plateformes qui ne prennent pas en charge les 64 bits.
