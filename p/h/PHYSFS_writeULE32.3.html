PHYSFS_EnumerateCallback

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du callback: à savoir: si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, transmis depuis l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé l'énumération, transmis dans le callback pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport aux autres callbacks qui se sont déclenchés, et il ne conterra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies; ne les utilisez pas.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent les fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place; il vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de toute chaîne.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme une alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes d'avance.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le même dans les versions de callback. Vérifiez la documentation sur les API spécifiques, mais les chaînes peuvent ne pas être triées comme vous l'attendez et vous pourriez obtenir des doublons.

Paramètres

data Pointeur de données défini par l'utilisateur, transmis depuis l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé l'énumération, transmis dans le callback pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport aux autres callbacks qui se sont déclenchés, et il ne conterra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Signature de fonction pour les callbacks qui rapportent des chaînes. Ceux-ci sont utilisés pour rapporter une liste de chaînes à un appelant d'origine, une chaîne par callback. int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir una lista de archivos de una ruta de búsqueda, usando un callback definido por la aplicación, con errores reportados. Internamente, PHYSFS_enumerateFiles() solo llama a esta función y luego construye una lista antes de devolverse a la aplicación, así que la funcionalidad es idéntica excepto por cómo la información se presenta a la aplicación.

Diferente de PHYSFS_enumerateFiles(), esta función no devuelve un array. En cambio, llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSfs_ENUM_OK;  // me da más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Los items enviados al callback no son garantizados estar en ningún orden. No se realiza ningún ordenamiento en este nivel, y si necesitas eso, deberías usar PHYSFS_enumerateFiles(), que garantiza el orden alfabético. Esta forma reporta lo que se encuentra en cada archive antes de moverse a la siguiente. Even within one archive, we can't guarantee the order in which data is discovered. Any sorting you find in these callbacks is just pure luck. Do not rely on it. Como este camina por toda la lista de archivos, podrías recibir nombres de archivos duplicados.

Esta API y los callbacks mismos pueden reportar errores. Antes de esta API, los callbacks tenían que aceptar cada elemento enumerado, incluso si solo buscaban un objeto específico y querían parar después de eso, o tenían un error serio y no podían alertar a nadie. Además, si PhysicsFS mismo tenia un problema (error de disco o lo que fuera), no podría reportarlo al aplicativo, simplemente pasaría los items o detendría la enumeración, y el llamador no sabría que había perdido datos por el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto completo de datos, y su callback controla si quiere detener la enumeración temprano. Ve las documentaciones de PHYSFS_EnumerateCallback para detalles de cómo su callback debería comportarse.

dir Dirección, en notación independiente del sistema operativo, a enumerar.
c Función de callback a notificar sobre los elementos de la ruta.
d Datos definidos por el aplicativo que se pasan al callback. Puede ser NULL.

Retorno

No cero en caso de éxito, cero en caso de falla. Usa PHYSFS_getLastErrorCode() para obtener el error específico. Si el callback devuelve PHYSFS_ENUM_STOP, se considera éxito. Callbacks que devuelvan PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezca el código de error en PHYSFS_ERR_APP_CALLBACK.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y arquitecturas contienen archivos que son simplemente referencias a otros archivos. Al abrir un enlace simbólico físico, se abre automáticamente el archivo al que se refiere.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría llevarte fuera de las rutas de lectura y escritura, comprometiendo la seguridad.

Si quieres asumir ese riesgo, llama a esta función con un valor distinto de cero. Ten en cuenta que esto es más para el sandboxing de lenguajes de scripting de programas, en caso de que scripts no confiables intenten comprometer el sistema. En general, un usuario podría tener una razón legítima para establecer un enlace simbólico, por lo que no deberías deshabilitarlo a menos que sientas que existe un peligro específico.

Los enlaces simbólicos solo se verifican cuando se tratan nombres de archivos en notación independiente de plataforma. Es decir, cuando configures tus rutas de búsqueda y escritura, etc., los enlaces simbólicos nunca se verifican.

Nota: PHYSFS_stat() siempre verifica la ruta especificada; si es un enlace simbólico, no lo seguirá en ningún caso. Si no se permite a través de esta función, PHYSFS_stat() ignorará los enlaces simbólicos y tratará la consulta como si la ruta no existiera.

El permiso de enlaces simbólicos puede habilitarse o deshabilitarse después de haber llamado PHYSFS_init(), y está deshabilitado por defecto.

Parámetros

allow distinto de cero para permitir enlaces simbólicos, cero para deshabilitar el enlace.

str1 chaîne à comparer.

-1 si str1 est "plus petit" que str2, 1 si str1 est "plus grand" que str2, 0 si égal.

Convertit une chaîne UTF-8 en une chaîne UTF-16.

Attention

Cette fonction ne signalera pas d'erreur s'il y a des séquences UTF-8 invalides dans la chaîne source. Elle les remplacera par un caractère '?' et continuera.

Les chaînes UTF-16 ont 16 bits par caractère (sauf pour certains caractères qui en ont 32) : TCHAR sous Windows, lorsque compilé avec le support Unicode. Les versions modernes de Windows utilisent UTF-16. Les versions de Windows antérieures à 2000 utilisaient TCHAR, mais ne géraient que UCS-2. UTF-16 est UCS-2, à l'exception des caractères qui prennent 4 octets, qui ne sont de toute façon pas représentables en UCS-2. Si vous n'êtes pas sûr, vous devriez utiliser UTF-16 à ce stade sous Windows.

Pour s'assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon de taille double de celle du tampon source. UTF-8 utilise de un à quatre octets par caractère, mais UTF-16 en utilise toujours de deux à quatre, donc une chaîne entièrement en ASCII basique doublera de taille ! Les caractères UTF-16 qui prendraient quatre octets prennent également quatre octets en UTF-8, vous n'avez donc pas besoin d'allouer 4 fois l'espace au cas où : le double suffira.

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais une paire de substitution UTF-16 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.
