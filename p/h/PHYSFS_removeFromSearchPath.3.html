PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'elle peut retourner un résultat du rappel : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous avons espérons bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, transmis par l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé une énumération, transmis dans le rappel pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport aux autres rappels qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent des fichiers.

Avertissement

À partir de PhysicsFS 2.1, utilisez plutôt PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; cela vous donne plus de contrôle sur le processus.

Ils sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire d'une chaîne.

Ces rappels sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions listes n'est pas nécessairement le cas dans les versions par rappel. Vérifiez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data Pointeur de données défini par l'utilisateur, transmis par l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé une énumération, transmis dans le rappel pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport aux autres rappels qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

typedef void(* physfs_StringCallback) (void *data, const char *str)

Obtenir une liste de fichiers d'un répertoire à partir d'un chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec des erreurs signalées. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de la renvoyer à l'application, de sorte que la fonctionnalité est identique, sauf la manière dont les informations sont présentées à l'application.

Bien que PHYSFS_enumerateFiles() ne renvoie pas de tableau, cette fonction appelle une fonction spécifiée par l'application une fois pour chaque élément dans le chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donne-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments transmis à la fonction de rappel ne sont pas garantis d'être dans un ordre spécifique. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un ordre alphabétique. Cette forme signale ce qui est trouvé dans chaque fichier archivé avant de passer au suivant. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout ordre que vous trouverez dans ces rappels est de la pure chance. Ne vous y fiez pas. Comme cette fonction parcourt toute la liste des fichiers, vous pourriez recevoir des noms de fichiers en double.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'un élément spécifique et voulaient s'arrêter ensuite, ou s'ils avaient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque, etc.), il ne pourrait pas le signaler à l'application, il passerait simplement aux éléments ou arrêterait l'énumération, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être assuré d'avoir obtenu un ensemble complet de données, et s'il le souhaite, sa fonction de rappel a le contrôle de l'arrêt précoce de l'énumération. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur la façon dont votre fonction de rappel doit se comporter.

dir Répertoire en notation indépendante du système d'exploitation, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application transmises à la fonction de rappel. Peut être NULL.

Retour

Non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel renvoie PHYSFS_ENUM_STOP, cela est considéré comme un succès. Les rappels qui renvoient PHYSFS_ENUM_ERROR feront que cette fonction renvoie zéro et définiront le code d'erreur comme PHYSFS_ERR_APP_CALLBACK.

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Obtenir le chemin spécifique à l'utilisateur et à l'application où les fichiers peuvent être écrits. Fonction d'aide.

Obtenir le "répertoire des préférences". Il est destiné à être l'endroit où les utilisateurs peuvent écrire des fichiers personnels (préférences, sauvegardes, etc.) spécifiques à votre application. Ce répertoire est unique par utilisateur, par application.

Cette fonction déterminera l'emplacement approprié dans le système de fichiers natif, créera le répertoire si nécessaire, et retournera une chaîne en notation dépendante de la plateforme, utilisable pour PHYSFS_setWriteDir().

Sur Windows, cela pourrait ressembler à : "C:\\Users\\bob\\AppData\\Roaming\\Ma Société\\Mon Programme Nom"

Sur Linux, cela pourrait ressembler à : "/home/bob/.local/share/Mon Nom de Programme"

Sur Mac OS X, cela pourrait ressembler à : "/Users/bob/Library/Application Support/Mon Nom de Programme"

(etc.)

Vous devriez probablement utiliser le répertoire des préférences pour votre répertoire d'écriture, et le placer également près du début de votre chemin de recherche. Les versions plus anciennes de PhysicsFS ne proposaient que PHYSFS_getUserDir() et vous laissaient trouver où placer les fichiers sous cet arbre. Ceci trouve l'emplacement correct pour chaque plateforme, ce qui change non seulement entre les systèmes d'exploitation, mais aussi entre les versions du même système d'exploitation.

  • Essayez d'utiliser la même chaîne org (y compris la sensibilité à la casse) pour toutes vos applications qui utilisent cette fonction.
  • Utilisez toujours une chaîne app unique pour chacune, et assurez-vous qu'elle ne change jamais pour une application une fois que vous l'avez décidée.
  • Les caractères Unicode sont légaux, tant qu'ils sont encodés en UTF-8, mais...
  • ...n'utilisez que des lettres, des chiffres et des espaces. Évitez la ponctuation comme "Nom du Jeu 2 : La Vengeance du Méchant !" ... "Nom du Jeu 2" est suffisant.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers se chevauchant avec un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser les archives pour remplacer les versions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer les archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que les habitués au concept Unix de "montage" pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

La spécification d'un lien symbolique vers une archive ou un répertoire est autorisée ici, quel que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

Paramètres

newDir répertoire ou archive à ajouter au chemin, en notation propre à la plateforme.
mountPoint Emplacement dans l'arbre interpolé où cette archive sera "montée", en notation indépendante de la plateforme. NULL ou "" est équivalent à "/".
appendToPath non nul pour ajouter au chemin de recherche, zéro pour préfixer.

Retourne

non nul si ajouté au chemin, zéro en cas d'échec (archive invalide, répertoire manquant, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et architectures contiennent des fichiers qui ne sont que des références à d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, celui-ci sera ouvert de manière transparente sur le fichier auquel il fait référence.

Par défaut, PhysicsFS vérifiera si un fichier est réellement un lien symbolique lors des appels d'ouverture et échouera si c'est le cas. Sinon, le lien pourrait vous faire sortir des chemins de lecture et d'écriture, compromettant ainsi la sécurité.

Si vous souhaitez assumer ce risque, appelez cette fonction avec une valeur non nulle. Notez que cela concerne davantage le sandboxing d'un langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur peut avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas le désactiver, sauf si vous estimez qu'il y a un risque spécifique.

Les liens symboliques ne seront consultés que lors du traitement de noms de fichiers dans une notation indépendante du système d'exploitation. Autrement dit, lorsque vous définissez vos chemins de recherche et d'écriture, etc., les liens symboliques ne seront jamais consultés.

L'autorisation des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour interdire le lien.

Comme stricmp, cela attend que les deux chaînes soient terminées par un caractère nul.

str1 Première chaîne à comparer.
str2 Seconde chaîne à comparer.

Retourne

-1 si str1 est "inférieur à" str2, 1 si "supérieur à", 0 s'ils sont égaux.

void PHYSFS_utf8ToUcs4 (const char * src, PHYSFS_uint32 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UCS-4 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UCS-4 strings are 32-bits per character. UTF-8 uses from one to four bytes per character. The destination buffer should be sized with (number of UTF-8 characters * 4) bytes. If you have a string of N bytes in UTF-8, then it has at most N characters, and requires at most 4*N bytes in UCS-4. This function attempts to convert as many characters as possible. Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UCS-4 sequence at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UCS-4 string.
len Size, in bytes, of destination buffer.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. If you aren't sure, you should be using UTF-16 at this point on Windows.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
len Size, in bytes, of destination buffer.
