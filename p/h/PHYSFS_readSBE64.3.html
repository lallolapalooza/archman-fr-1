Documentation des types PHYSFS_EnumFilesCallback (void *data, const char *origdir, const char *fname)

Signature des fonctions de rappel qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() pour avoir plus de contrôle sur le processus.

Ils sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, une entrée par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire des chaînes.

Ces rappels sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui retournent des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le rappel indique que la bibliothèque n'a pas besoin de réserver une liste complète et toutes les chaînes au début.

Notez que les promesses d'ordre dans les versions de liste ne sont pas nécessairement respectées dans les versions de rappel. Consultez la documentation spécifique des API, mais les chaînes peuvent ne pas être triées comme prévu et vous pouvez obtenir des doublons.

Paramètres

data Pointeur vers des données définies par l'utilisateur, passé par l'API qui a finalement appelé le rappel.
origdir Une chaîne représentant le chemin complet, en notation indépendante du système d'exploitation, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire dans lequel vous avez demandé l'énumération, passé par le rappel pour votre commodité.
fname Le nom du fichier en cours d'énumération. Il n'est pas nécessairement trié par ordre alphabétique par rapport à d'autres rappels qui ont été appelés, et ne contient pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retour

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

« Plie » un point de code Unicode vers un équivalent en minuscules. (Ceci est pour une utilisation limitée et intensive. Si vous ne voyez pas immédiatement un besoin pour cela, vous pouvez probablement ignorer cela pour toujours.)

Ceci convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux n'ayant pas d'équivalent en minuscules seront retournés sans être modifiés.

Notez que vous pourriez obtenir plusieurs points de code en retour ! Le « Eszett » allemand, par exemple, sera plié en deux points de code latins en minuscules « s ». La théorie est que si vous pliez deux chaînes, l'une avec un Eszett et l'autre avec « SS » vers le bas, elles correspondront.

Avertissement

Quiconque est étudiant en Unicode connaît le problème de « l'I Turc ». Cette API ne le gère pas. Supposons que cette lettre unique dans tout Unicode sera pliée de manière quelque peu incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la plupart de la planète, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Tampon pour stocker les valeurs des points de code pliés. Ceci doit pointer vers de l'espace pour au moins 3 emplacements de PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialise la bibliothèque PhysicsFS. Cela ferme tous les fichiers ouverts via PhysicsFS, vide les chemins de recherche/écriture, libère la mémoire et invalide tous vos handles de fichiers.

Notez que cet appel peut ÉCHOUEr s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures sur un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur est tombé en panne, etc.). Il est généralement préférable de fermer tous les handles d'écriture vous-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois désinitialisé avec succès, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états par défaut de l'API sont restaurés à ce stade, à l'exception de tout allocateur personnalisé que vous auriez pu spécifier, qui survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les spécificités de l'erreur peuvent être obtenues à partir de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini et probablement très compromis.

int PHYSFS_delete (const char * filename)

Supprime un fichier ou un répertoire. (filename) est spécifié dans une notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, et non ce à quoi il pointe, que vous ayez « autorisé les liens symboliques » ou non.

Donc, si vous avez défini le répertoire d'écriture sur "C:\monjeu\repertoire_ecriture" et que vous appelez PHYSFS_delete("telechargements/cartes/niveau1.carte"), alors le fichier "C:\monjeu\repertoire_ecriture\telechargements\cartes\niveau1.carte" est supprimé du système de fichiers physique, s'il existe et si le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont un handle de fichier ouvert pour celui-ci (y compris votre programme) ne le fermeront pas.

Il est probable que les bits qui composent le fichier existent toujours, ils sont simplement rendus disponibles pour être écrasés ultérieurement. Ne considérez pas cela comme une méthode de sécurité ou autre. :)

Paramètres

filename Nom du fichier à supprimer.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_deregisterArchiver (const char * ext)

Supprime un archiveur du système. Si, pour une raison quelconque, vous n'avez besoin que de votre archiveur précédemment enregistré qu'une partie de la durée de vie de votre application, vous pouvez le supprimer du système une fois que vous avez terminé avec lui via cette fonction.

Cela échouera s'il reste des archives ouvertes qui utilisent cet archiveur.

Cette fonction peut également supprimer les archiveurs fournis en interne, tels que le support .zip ou autre. Cela pourrait être utile dans certaines situations, comme désactiver leur support complètement ou les remplacer par votre propre implémentation. Une fois qu'un archiveur interne est désactivé de cette manière, PhysicsFS ne fournit aucun mécanisme pour les récupérer, à moins d'appeler PHYSFS_deinit() et PHYSFS_init() à nouveau.

PHYSFS_deinit() retirera automatiquemy désenregistrer tous les archiveurs, vous n'avez donc pas besoin de désenregistrer explicitement le vôtre si vous arrêtez proprement par ailleurs.

Paramètres

ext Extension de nom de fichier gérée par l'archiveur.

Retourne

Zéro en cas d'erreur, non nul en cas de succès.

Interne­ment, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de la retourner à l'application. La fonctionnalité est donc identique, sauf pour la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas de tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * On a trouvé [%s] dans [%s].\n", fname, origdir);
    return physfs_ENUM_OK;  // Donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis dans aucun ordre particulier. Il n'y a pas de tri effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données seront découvertes. Tout tri que vous trouverez dans ces appels de fonction de rappel n'est que pure chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pourriez recevoir des noms de fichiers en double.

Cette API et les fonctions de rappel elles-mêmes sont capables de signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même si elles ne recherchaient qu'un élément spécifique et voulaient s'arrêter après, ou si elles avaient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération directement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble de données complet, et sa fonction de rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour plus de détails sur la manière dont votre fonction de rappel doit se comporter.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

Retourne

Non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel retourne PHYSFS_ENUM_STOP pour s'arrêter tôt, cela sera considéré comme un succès. Les fonctions de rappel retournant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, il sera ouvert de manière transparente pour ouvrir le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous conduire hors des chemins de lecture et d'écriture, compromettant la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Remarque : cela concerne davantage le sandboxing d'un langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas le désactiver à moins de sentir qu'il existe un danger spécifique à l'autoriser.

Les liens symboliques ne sont explicitement vérifiés que lorsqu'il s'agit de noms de fichiers dans une notation non indépendante du système d'exploitation. C'est-à-dire que lorsque vos chemins de recherche et d'écriture sont définis, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifie toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas.

  • All found CD-ROM dirs (optionally)
