Valeurs de retour possibles pour les callbacks PHYSFS_EnumerateCallback. Signature de fonction pour les callbacks qui énumèrent et retournent des résultats.

Ces valeurs dictent si un callback d'énumération doit continuer à être déclenché, ou s'arrêter (et pourquoi il s'arrête).

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'elle peut retourner un résultat du callback : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous avons j'espère bien fait cette fois-ci. :)

Paramètres

origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé une énumération, passé dans le callback pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport aux autres callbacks qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() à la place ; cela vous donne plus de contrôle sur le processus.

Ils sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire d'une chaîne.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions listes n'est pas nécessairement le cas dans les versions callback. Consultez la documentation sur les API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le callback.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé une énumération, passé dans le callback pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport aux autres callbacks qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

int PHYSFS_deinit (void )

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). It is usually best to close all write handles yourself before calling this function, so that you can gracefully handle a specific failure.

int PHYSFS_delete (const char * filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

Chances are, the bits that make up the file still exist, they are just made available to be written over at a later point. Don't consider this a security method or anything. :)

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenez une liste de fichiers à partir d'un chemin de recherche, à l'aide d'une fonction de rappel définie par l'utilisateur, avec des rapports d'erreurs. En interne, PHYSFS_enumerateFiles() ne fait qu'appeler cette fonction, puis construire la liste avant de la renvoyer à l'application, de sorte que la fonctionnalité est identique, bien que la manière dont les informations sont présentées soit différente.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne renvoie pas de tableau. Elle appelle plutôt une fonction spécifiée par l'utilisateur une fois pour chaque élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // S'il vous plaît, donnez-moi plus de données.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés à la fonction de rappel ne sont garantis dans aucun ordre spécifique. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un tri alphabétique. Cette forme de rapport dresse la liste de tout ce qui est trouvé dans chaque archive avant de passer à la suivante. Même au sein d'une seule archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout tri que vous trouvez dans ces fonctions de rappel n'est que de la pure chance. N'en dépendez pas. Comme cette fonction parcourt la liste de toutes les archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les fonctions de rappel elles-mêmes peuvent signaler des erreurs. Avant cette API, les fonctions de rappel devaient accepter chaque élément énuméré, même si elles ne cherchaient qu'un élément spécifique et voulaient s'arrêter après cela, ou si elles rencontraient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il passerait simplement aux éléments suivants ou arrêterait l'énumération, et l'appelant ne saurait pas qu'il avait perdu des données pendant le processus.

Désormais, l'appelant peut être assuré qu'il a obtenu un ensemble complet de données, et s'il le souhaite, sa fonction de rappel a le contrôle sur le moment d'arrêter l'énumération prématurément. Consultez la documentation de PHYSFS_EnumerateCallback pour connaître les détails du comportement attendu de votre fonction de rappel.

Paramètres

dir Le répertoire, en notation indépendante du système d'exploitation, à énumérer.
c La fonction de rappel pour notifier les éléments du chemin de recherche.
d Les données définies par l'application transmises à la fonction de rappel. Peut être NULL.

Retour

Non zéro en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel renvoie PHYSFS_ENUM_STOP pour s'arrêter prématurément, cela est considéré comme un succès. Les fonctions de rappel renvoyant PHYSFS_ENUM_ERROR entraîneront le retour de zéro de cette fonction et la définition du code d'erreur à PHYSFS_ERR_APP_CALLBACK.

Get the user-and-app-specific path where files can be written. Helper function.

(etc.)

Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left you to figure out where the files should go under that tree. This finds the correct location for whatever platform, which not only changes between operating systems, but also versions of the same operating system.

You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might do) and the name of your application. These should be proper names.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Par défaut, PhysicsFS vérifiera si un fichier est réellement un lien symbolique lors des appels d'ouverture et échouera si c'est le cas. Sinon, le lien pourrait vous faire sortir des chemins de lecture et d'écriture, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Vous devrez considérer que cela est davantage destiné au sandboxing d'un langage de script du programme, au cas où des scripts non fiables tenteraient de compromettre le système. En général, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas désactiver la permission si vous ne ressentez pas de danger spécifique.

Les liens symboliques seront explicitement vérifiés uniquement lors de la manipulation de noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire que lorsque vos chemins de recherche et d'écriture, etc., sont configurés, les liens symboliques ne seront jamais vérifiés.

Note : PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. S'il n'est pas autorisé par cette fonction, PHYSFS_stat() ignorera le lien et le traitera comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.
