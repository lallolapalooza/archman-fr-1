#define PHYSFS_file PHYSFS_File

Définition de compatibilité API 1.0. PHYSFS_file est identique à PHYSFS_File. Cette #define est là pour la compatibilité ascendante avec l'API 1.0, qui avait une convention de capitalisation incohérente dans ce cas. Le nouveau code devrait utiliser PHYSFS_File, car cette #define pourrait disparaître un jour.

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du rappel : notamment : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer plus loin. Ceci est utilisé avec PHYSFS_enumerate(), que nous avons, espérons-le, bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être en ordre alphabétique par rapport à d'autres rappels qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent des fichiers.

Attention

Depuis PhysicsFS 2.1, utilisez plutôt PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; il vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour rapporter une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire d'une chaîne.

Ces rappels sont utilisés, à partir de PhysicsFS 1.1, comme alternative aux fonctions qui retourneraient des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le cas dans les versions de rappel. Consultez la documentation sur les API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes en double.

data Pointeur de données défini par l'utilisateur, passé depuis l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname Le nom de fichier qui est énuméré. Il peut ne pas être en ordre alphabétique par rapport à d'autres rappels qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

int PHYSFS_delete(const char * filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Lister les fichiers d'un répertoire du chemin de recherche, en utilisant un rappel défini par l'utilisateur, avec des erreurs signalées. Interne, PHYSFS_enumerateFiles() appelle seulement cette fonction, puis construit une liste avant de la retourner à l'application, donc la fonction est identique sauf quant à la manière dont l'information est présentée à l'application.

Différent de PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois pour chaque élément du chemin de recherche :

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons obtenu [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donne-moi plus de données, s'il te plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments envoyés au rappel ne sont pas garantis dans un ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit un ordre alphabétique. Cette forme signale ce qui est trouvé dans chaque fichier archivé avant de passer au suivant. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. Tout tri que vous pourriez trouver dans ces rappels est purement le fruit du hasard. Ne comptez pas dessus. Puisque cela parcourt l'intégralité du listage archivé, vous pourriez recevoir des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'un élément spécifique et voulaient s'arrêter après, ou s'ils rencontraient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il ignorerait simplement les éléments ou arrêterait l'énumération, et l'appelant ne saurait pas qu'il avait perdu des données en cours de route.

Désormais, l'appelant peut être assuré d'avoir obtenu un ensemble complet de données, et s'il le souhaite, son rappel a le contrôle pour décider s'il arrête l'énumération prématurément. Consultez la documentation de PHYSFS_EnumerateCallback pour connaître les détails sur le comportement attendu de votre rappel.

Paramètres

dir Répertoire à énumérer, en notation indépendante du système.
c Fonction de rappel pour notifier les éléments du chemin.
d Données définies par l'application passées au rappel. Peut être NULL.

Retour

Non nul en cas de succès, nul en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel retourne PHYSFS_ENUM_STOP, cela est considéré comme un succès. Les rappels retournant PHYSFS_ENUM_ERROR feront que cette fonction retourne nul et définiront le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

Avertissement

C'était un problème, car le développeur, et non l'utilisateur, sélectionnait la langue de compilation, et les mainteneurs de PhysicsFS devaient (mal) maintenir un travail de localisation énorme. L'application ne pouvait pas analyser les chaînes, même si elles étaient dans une langue spécifique, car certaines étaient générées dynamiquement. Ajoute une archive, contenue dans une poignée PHYSFS_File, au chemin de recherche.

Attention

L'utilisation normale des archives peut effectuer de nombreuses recherches en coulisses. Par conséquent, vous pourriez trouver l'utilisation normale des archives extrêmement pénible si elles sont montées de cette manière. Planifiez en conséquence : si vous avez, par exemple, un fichier .zip auto-extractible, et que vous souhaitez monter quelque chose dedans, compressez le contenu de l'archive interne et assurez-vous que le fichier .zip externe ne compresse pas l'archive interne non plus.

Le PHYSFS_File peut être basé sur un fichier réel dans le système de fichiers physique, mais ce n'est pas nécessairement le cas. Si l'extension du nom de fichier n'est pas utile, le système essaiera chaque archiveur jusqu'à ce qu'un fonctionne ou qu'aucun d'entre eux ne le fasse. void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et architectures contiennent des fichiers qui ne sont que des références à d'autres fichiers. Lors de l'ouverture d'un lien symbolique sur un système physique, celui-ci est ouvert de manière transparente pour le fichier qu'il référence.

Par défaut, PhysicsFS vérifie si un fichier est un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous faire sortir des chemins de lecture et d'écriture, compromettant la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Vous devriez noter que cela est davantage destiné à la mise en bac à sable du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, vous ne devriez donc pas les désactiver, sauf si vous estimez qu'il existe un danger spécifique.

Les liens symboliques ne sont vérifiés explicitement que lors de la manipulation de noms de fichiers en notation indépendante de la plateforme. C'est-à-dire lorsque vous configurez vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Note : PHYSFS_stat() vérifie toujours le chemin spécifié ; s'il s'agit d'un lien symbolique, il ne sera en aucun cas suivi. S'il n'est pas autorisé via cette fonction, PHYSFS_stat() ignore les liens symboliques et traiterait la requête comme si le chemin n'existait pas.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désactiver le lien.

int PHYSFS_ucs4stricmp (const PHYSFS_uint32 * str1, const PHYSFS_uint32 * str2)

Comparaison insensible à la casse de deux chaînes UTF-32. C'est un remplaçant de strcasecmp/stricmp qui s'attend à ce que les deux chaînes soient en format UTF-32. Elle effectue un "case folding" pour déterminer si les codes Unicode dans les chaînes correspondent.

Elle renvoie la chaîne qui est "plus grande" que l'autre, mais gardez à l'esprit que cela ne signifie pas nécessairement quelque chose : 'a' peut être "plus petit" que 'b', mais un kana japonais n'a pas de relation significative avec un lambda grec en termes alphabétiques. La capacité d'attribuer une valeur fiable permet des algorithmes de tri, même s'ils ne sont pas nécessairement entièrement rationnels. Dans la plupart des cas, la valeur renvoyée sera traitée comme "égale" ou "non égale".

Comme stricmp, elle s'attend à ce que les deux chaînes soient terminées par NULL.

Paramètres

str1 Première chaîne à comparer.
str2 Deuxième chaîne à comparer.

Retourne

-1 si str1 est "plus petit" que str2, 1 si str1 est "plus grand" que str2, 0 s'ils sont égaux.

Elle indiquera quelle chaîne est "supérieure" à l'autre, mais sachez que cela ne signifie pas nécessairement quelque chose : 'a' peut être "inférieur à" 'b', mais un kuten japonais n'a pas de relation alphabétique significative avec un lambda grec, mais pouvoir attribuer une "valeur" fiable permet des algorithmes de tri, même s'ils ne sont pas entièrement sains. Dans la plupart des cas, il faut considérer la valeur de retour comme "égal" ou "non égal".

Comme stricmp, cela attend que les deux chaînes soient terminées par un caractère nul.

Paramètres

str1 Première chaîne à comparer.
str2 Deuxième chaîne à comparer.

Retourne

-1 si str1 est "inférieur à" str2, 1 si "supérieur à", 0 s'ils sont égaux.

Convertit une chaîne UTF-8 en une chaîne UCS-2.

Avertissement

vous devriez presque certainement utiliser PHYSFS_utf8ToUtf16(), qui est disponible depuis PhysicsFS 2.1, sauf si vous savez ce que vous faites.

Cette fonction ne signalera pas d'erreur s'il y a des séquences UTF-8 invalides dans la chaîne source. Elle les remplacera par un caractère '?' et continuera.

Les chaînes UCS-2 utilisent 16 bits par caractère : TCHAR sous Windows, lorsque compilé avec le support Unicode. Veuillez noter que les versions modernes de Windows utilisent UTF-16, qui est une forme étendue d'UCS-2, et non UCS-2 lui-même. Vous voulez presque certainement PHYSFS_utf8ToUtf16() à la place, mais vous devez comprendre comment cela change les choses aussi.

Pour vous assurer que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon de taille double par rapport au tampon source. L'UTF-8 utilise de un à quatre octets par caractère, mais UCS-2 utilise toujours deux, donc une chaîne entièrement ASCII bas doublera de taille !

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convertir una cadena UTF-8 en una cadena UTF-16.

Advertencia

Esta función no reportará un error si hay secuencias UTF-8 inválidas en la cadena de fuente. Las reemplazará con un carácter '?' y continuará.

Las cadenas UTF-16 son de 16 bits por carácter (a excepción de algunos caracteres, que son 32 bits): TCHAR en Windows, cuando se usa la soporte de Unicode. Las versiones modernas de Windows usan UTF-16. Las versiones antiguas de Windows antes de 2000 usaron TCHAR, pero solo manejaron UCS-2. UTF-16 es UCS-2, a menos que los caracteres sean de 4 bytes, que no pueden representarse en UCS-2 en su totalidad. Si no estás seguro, deberías estar usando UTF-16 en Windows en este punto.

Para asegurar que el buffer de destino sea lo suficientemente grande para la conversión, por favor reserva un buffer que sea el doble del tamaño del buffer de fuente. El UTF-8 usa de uno a cuatro bytes por carácter, pero el UTF-16 siempre usa de dos a cuatro bytes, ¡así que una cadena completamente en ASCII bajo duplicará su tamaño! Los caracteres UTF-16 que tomarían cuatro bytes también ocupan cuatro bytes en UTF-8, así que no necesitas reservar 4 veces el espacio, solo el doble.

Las cadenas que no caben en el buffer de destino se truncarán, pero siempre se anularán y nunca tendrán un par sustituto incompleto al final. Si el tamaño del buffer es 0, esta función no hace nada.

Parámetros

src Cadena de fuente con terminación nula en formato UTF-8.
dst Buffer para almacenar la cadena UTF-16 convertida.
len Tamaño en bytes del buffer de destino.
