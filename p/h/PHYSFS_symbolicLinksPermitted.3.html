Documentation des définitions de macros

#define PHYSFS_file PHYSFS_File

Définition de compatibilité de l'API 1.0. PHYSFS_file est identique à PHYSFS_File. Ce #define est là pour la compatibilité descendante avec l'API 1.0, qui avait une convention de capitalisation incohérente dans ce cas. Le nouveau code doit utiliser PHYSFS_File, car ce #define pourrait disparaître un jour.

#define PHYSFS_VERSION( x)

Valeur:

{ \
    (x)->major = PHYSFS_VER_MAJOR; \
    (x)->minor = PHYSFS_VER_MINOR; \
    (x)->patch = PHYSFS_VER_PATCH; \
}

Macro pour déterminer la version de PhysicsFS avec laquelle le programme a été compilé. Cette macro remplit une structure PHYSFS_Version.

structure avec la version de la bibliothèque à laquelle vous avez compilé. Ceci est déterminé par l'en-tête que le compilateur utilise. Notez que si vous avez lié dynamiquement la bibliothèque, vous pourriez avoir une version légèrement plus récente ou plus ancienne à l'exécution. Cette version peut être déterminée avec PHYSFS_getLinkedVersion(), qui, contrairement à PHYSFS_VERSION, n'est pas une macro.

Paramètres

x Un pointeur vers une structure PHYSFS_Version à initialiser.

typedef PHYSFS_EnumerateCallbackResult(* physFS_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Valeurs de retour possibles de PHYSFS_EnumerateCallback. Signature de fonction pour les rappels qui énumèrent et retournent des résultats.

Ces valeurs dictent si un rappel d'énumération doit continuer à être déclenché, ou s'arrêter (et pourquoi il s'arrête).

PHYSFS_EnumerateCallback

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du rappel : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez indiquer à PhysicsFS d'arrêter l'énumération. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois-ci. :)

Paramètres

Un répertoire doit être vide avant que cet appel ne puisse le supprimer.

La suppression d'un lien symbolique supprime le lien, pas ce qu'il pointe, indépendamment du fait que vous ayez "permis les liens symboliques" ou non.

Il y a de fortes chances que les bits qui composent le fichier existent toujours, ils sont simplement rendus disponibles pour être écrasés ultérieurement. Ne considérez pas cela comme une méthode de sécurité ou quoi que ce soit. :)

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtient une liste de fichiers d'un répertoire de chemin de recherche, en utilisant un rappel défini par l'application, avec des erreurs signalées. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de retourner à l'application, de sorte que la fonctionnalité est identique sauf pour la manière dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons trouvé [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Les éléments envoyés au rappel ne sont garantis dans aucun ordre quelconque. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme rapporte ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons pas garantir l'ordre dans lequel les données seront découvertes. Tout tri que vous trouverez dans ces rappels est purement un coup de chance. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur grave et ne pouvaient alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération franchement, et l'appelant ne saurait pas qu'il a perdu des données en cours de chemin.

Maintenant, l'appelant peut être sûr qu'il a obtenu un ensemble de données complet, et son rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur la manière dont votre rappel doit se comporter.

Paramètres

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées au rappel. Peut être NULL.

Retourne

non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel retourne PHYSFS_ENUM_STOP pour s'arrêter plus tôt, cela sera considéré comme un succès. Les rappels retournant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtient une liste de fichiers d'un répertoire de chemin de recherche.

Attention

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction retournait autant d'éléments que possible face à une condition d'échec (manque de mémoire, erreur d'entrée/sortie disque, etc.). Comme cela signifiait que les applications ne pouvaient pas distinguer un succès complet d'un échec partiel, et comme la fonction pouvait toujours retourner NULL pour signaler des échecs catastrophiques de toute façon, dans PhysicsFS 2.1 la politique de cette fonction a changé : elle retournera soit une liste de résultats complets, soit NULL pour tout échec, de sorte que nous puissions garantir que l'énumération s'est déroulée jusqu'à son terme et n'a pas de lacunes dans ses résultats.

Les répertoires correspondants sont interpolés. C'est-à-dire que si "C:\mydir" se trouve dans le chemin de recherche et contient un répertoire "savegames" qui contient "x.sav", "y.sav", et "z.sav", et qu'il y a aussi un "C:\userdir" dans le chemin de recherche qui a un sous-répertoire "savegames" avec "w.sav", alors le code suivant :

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Nous avons trouvé [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi
N'hésitez pas à trier la liste comme vous le souhaitez. Cependant, les données retournées ne contiendront jamais de doublons et seront toujours triées par ordre alphabétique (ou plutôt, sensible à la casse Unicode) pour vous.
N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur de retour de cette fonction lorsque vous avez terminé avec elle.

This function returns a pointer to the internal allocator structure used by PhysicsFS. int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arborescence de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers chevauchant un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser les archives pour remplacer les versions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer les archives à un point spécifique de l'arborescence de fichiers et éviter les chevauchements ; c'est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept Unix de "montage" pourraient attendre. De plus, plusieurs archives peuvent être montées au même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

La spécification d'un lien symbolique vers une archive ou un répertoire est autorisée ici, quelle que soit l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne traite que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (transparentement) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins de recherche et d'écriture, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné à la mise en bac à sable du langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, donc à moins que vous ne pensiez qu'il existe un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors de la manipulation de noms de fichiers dans la notation indépendante de la plateforme. C'est-à-dire que lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

Dans la plupart des cas, il faut considérer la valeur de retour comme "égal" ou "différent".

Comme stricmp, elle s'attend à ce que les deux chaînes soient terminées par un caractère nul.

Paramètres

str1 Première chaîne à comparer.
str2 Deuxième chaîne à comparer.

Retourne

-1 si str1 est "inférieur" à str2, 1 si "supérieur", 0 si égal.

void PHYSFS_utf8ToUcs2 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convertissez une chaîne UTF-8 en une chaîne UCS-2.

Attention

vous devriez presque certainement utiliser PHYSFS_utf8ToUtf16(), qui est devenu disponible dans PhysicsFS 2.1, sauf si vous savez ce que vous faites.

Cette fonction ne signalera pas d'erreur s'il y a des séquences UTF-8 invalides dans la chaîne source. Elle les remplacera par un caractère '?' et continuera.

Les chaînes UCS-2 sont de 16 bits par caractère : TCHAR sous Windows, lors de la compilation avec le support Unicode. Veuillez noter que les versions modernes de Windows utilisent UTF-16, qui est une forme étendue de UCS-2, et non UCS-2 lui-même. Vous voudrez presque certainement PHYSFS_utf8ToUtf16() à la place, mais vous devez comprendre comment cela change les choses également.

Pour garantir que le tampon de destination est suffisamment grand pour la conversion, veuillez allouer un tampon dont la taille est le double de celle du tampon source. UTF-8 utilise de un à quatre octets par caractère, mais UCS-2 en utilise toujours deux, de sorte qu'une chaîne entièrement ASCII de bas niveau doublera de taille !

Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et n'auront jamais de séquence UCS-2 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

Paramètres

src Chaîne source terminée par un caractère nul au format UTF-8.
dst Tampon pour stocker la chaîne UCS-2 convertie.
len Taille, en octets, du tampon de destination.
