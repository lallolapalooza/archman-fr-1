int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Plie" un point de code Unicode vers un équivalent en minuscules. (Ceci est pour un usage limité et extrême. Si vous ne voyez pas immédiatement l'utilité, vous pouvez probablement l'ignorer pour toujours.)

Ceci convertira un point de code Unicode en son équivalent en minuscules. Les points de code invalides et ceux qui n'ont pas d'équivalent en minuscules seront retournés sans conversion.

Notez que vous pourriez obtenir plusieurs points de code en retour ! L'eszett allemand, par exemple, sera plié en deux points de code latins minuscules 's'. La théorie est que si vous pliez deux chaînes, l'une avec un eszett et l'autre avec "SS", elles correspondront.

Attention

Quiconque est un étudiant de l'Unicode connaît le problème du "I turc". Cette API ne le gère pas. Supposez que cette lettre unique dans tout l'Unicode sera pliée de manière incorrecte. Si vous ne savez pas de quoi il s'agit, vous pouvez probablement ignorer ce problème pour la plupart des utilisateurs, mais la perfection est impossible.

Paramètres

from Le point de code à plier.
to Tampon pour stocker les valeurs des points de code pliés. Il doit pointer vers un espace pour au moins 3 emplacements de PHYSFS_uint32.

Retourne

Le nombre de points de code produits par le pliage. Entre 1 et 3.

int PHYSFS_deinit (void )

Désinitialise la bibliothèque PhysicsFS. Ceci ferme tous les fichiers ouverts via PhysicsFS, vide les chemins de recherche/écriture, libère la mémoire et invalide tous vos handles de fichiers.

Notez que cet appel peut ÉCHOIR s'il y a un fichier ouvert en écriture qui refuse de se fermer (par exemple, le système d'exploitation sous-jacent mettait en mémoire tampon les écritures sur un système de fichiers réseau, et le serveur de fichiers a planté, ou un disque dur a échoué, etc.). Il est généralement préférable de fermer tous les handles d'écriture vous-même avant d'appeler cette fonction, afin de pouvoir gérer gracieusement un échec spécifique.

Une fois correctement désinitialisé, PHYSFS_init() peut être appelé à nouveau pour redémarrer le sous-système. Tous les états par défaut de l'API sont restaurés à ce stade, à l'exception de tout allocateur personnalisé que vous auriez pu spécifier, qui survit entre les initialisations.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Les détails de l'erreur peuvent être obtenus à partir de PHYSFS_getLastError(). En cas d'échec, l'état de PhysFS est indéfini et probablement gravement compromis.

int PHYSFS_delete (const char * filename)

Supprime un fichier ou un répertoire. (nom de fichier) est spécifié dans une notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, et non ce qu'il pointe, indépendamment du fait que vous ayez activé "permitSymLinks" ou non.

Donc, si vous avez défini le répertoire d'écriture sur "C:\monjeu\repertoireecriture" et que vous appelez PHYSFS_delete("telechargements/cartes/niveau1.map"), alors le fichier "C:\monjeu\repertoireecriture\telechargements\cartes\niveau1.map" est supprimé du système de fichiers physique, s'il existe et si le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont un handle de fichier ouvert dessus (y compris votre programme) ne fermeront pas leurs handles.

Il est probable que les bits qui composent le fichier existent toujours, ils sont juste rendus disponibles pour être écrasés ultérieurement. Ne considérez pas cela comme une méthode de sécurité ou quoi que ce soit. :)

Paramètres

filename Nom du fichier à supprimer.

Retourne

non nul en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_deregisterArchiver (const char * ext)

Supprime un archiveur du système. Si pour une raison quelconque, vous n'avez besoin de votre archiveur précédemment enregistré que pendant une partie de la durée de vie de votre application, vous pouvez le supprimer du système une fois que vous en avez terminé via cette fonction.

Cela échoue s'il y a encore des archives ouvertes qui utilisent cet archiveur.

Cette fonction peut également supprimer des archiveurs fournis en interne, comme le support .zip ou autre. Cela pourrait être utile dans certaines situations, comme désactiver complètement leur prise en charge ou les remplacer par votre propre implémentation. Obtenir una lista de archivos de una carpeta de un camino de búsqueda, usando una función de callback definida por el usuario, con errores reportados. Internamente, PHYSFS_enumerateFiles() solo llama a esta función y luego construye la lista antes de devolver a la aplicación, así que la funcionalidad es idéntica, aunque la información se presenta de forma diferente.

Diferente de PHYSFS_enumerateFiles(), esta función no devuelve un array. En su lugar, llama a una función especificada por el aplicativo una vez por cada elemento de la ruta de búsqueda:

    printf(" * We've got [%s] in [%s].\n", fname, origdir);

}
// ...

Los elementos enviados a la callback no son garantizados para estar en ningún orden. No se realiza ningún ordenamiento en este nivel, y si lo necesitas, deberías usar PHYSFS_enumerateFiles(), que garantiza el orden alfabético. Esta forma reporta lo que se encuentra en cada arqueo antes de pasar a la siguiente. Incluso dentro de un mismo archivo, no podemos garantizar el orden en el que se descubren los datos. Cualquier ordenación que encuentres en estas callbacks es pura suerte. No debes depender de ella. Como esta camina por toda la lista de arqueos, podrías recibir nombres de archivos duplicados.

Esta API y las funciones de callback son capaces de reportar errores. Antes de esta API, las funciones de callback tenían que aceptar cada elemento enumerado, incluso si solo buscaban un cierto objeto y querían detenerse después de eso, o tenían un error serio y no podían alertar a nadie. Además, si PhysicsFS mismo tenía un problema (error de disco o lo que sea), no podría reportarlo a la aplicación que lo llama, simplemente pasaría a omitir los elementos o detener la enumeración, y la llamada no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede asegurarse de haber obtenido un conjunto de datos completo, y si quiere detener la enumeración temprano, su callback tendrá control. Ve la documentación para PHYSFS_EnumerateCallback para detalles sobre cómo debería comportarse tu callback.

const char * PHYSFS_getLastError (void )

Utilisez PHYSFS_getLastErrorCode() et PHYSFS_getErrorByCode() à la place.

Depuis PhysicsFS 2.1, cette fonction a été renforcée. Avant PhysicsFS 2.1, c'était le seul moyen d'obtenir des détails d'erreur au-delà de la valeur de retour de base d'une fonction. En dehors de ce contexte, le développeur ne choisit pas la langue, et les mainteneurs de PhysicsFS devaient (très mal) maintenir une énorme quantité de travail de localisation. L'application ne pouvait pas analyser les chaînes, même si elle dépendait d'une langue spécifique, car certaines étaient générées dynamiquement. Chaque thread a un état d'erreur unique associé, mais chaque fois qu'un nouveau message d'erreur est défini, il écrase l'état précédent associé à ce thread. En général, les applications ne se soucient que de savoir si une fonction a échoué ; cependant, si votre code nécessite plus de spécifications, vous devriez utiliser PHYSFS_getLastErrorCode() à la place de cette fonction.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajouter une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait contre l'archive et non contre le point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers se chevauchant avec un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arbre de fichiers et éviter les chevauchements ; ceci est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

Le point de montage n'a pas besoin d'exister avant le montage, ce qui est différent de ce que ceux qui connaissent le concept de "montage" Unix pourraient attendre. De plus, plusieurs archives peuvent être montées sur le même point de montage, ou les points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archivés contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Lors de l'ouverture d'un lien symbolique physique, le fichier auquel il fait référence sera ouvert de manière transparente.

Par défaut, PhysicsFS vérifie si un fichier est effectivement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait pointer vers une destination en dehors des chemins de lecture et de recherche, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Notez que ceci est principalement destiné au sandboxing d'un langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur pourrait avoir une raison légitime de créer un lien symbolique, vous ne devriez donc pas les désactiver, à moins que vous ne pensiez qu'il existe un danger spécifique à les autoriser.

Les liens symboliques ne sont vérifiés que lorsqu'il s'agit de noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire que lorsque vous définissez votre chemin de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Notez que PHYSFS_stat() vérifie toujours le chemin spécifié ; si ce chemin est un lien symbolique, il n'est en aucun cas suivi. Si les liens ne sont pas autorisés via cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas.

L'autorisation des liens symboliques peut être activée ou désactivée à tout moment après l'appel de PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour désactiver le lien.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Fait d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de restreindre les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt, monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel PHYSFS_openRead("/a/z.txt") réussira.

Vous pouvez changer la racine d'une archive à tout moment, modifiant l'arborescence de fichiers interpolée (selon les chemins qui changent, une archive différente peut fournir divers fichiers). Définir une nouvelle racine ne se limite pas aux archives dans le chemin de recherche ; vous pouvez en définir une sur le répertoire d'écriture, ce qui peut être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez donc pas changer le répertoire d'écriture pour le moment.

Il n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme racine d'une archive ; cependant, aucun fichier ne sera visible dans ce cas. Si les répertoires manquants finissent par être créés (un mkdir sur le système de fichiers physique, etc.), cela sera reflété dans l'arbre interpolé.

archive répertoire/archive sur lequel changer la racine.
subdir nouveau sous-répertoire à définir comme racine de cette archive.

une valeur non nulle en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.
