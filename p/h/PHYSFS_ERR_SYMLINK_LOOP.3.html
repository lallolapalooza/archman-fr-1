PHYSFS_EnumerateCallback

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il renvoie un résultat du rappel : si vous cherchez quelque chose de spécifique, une fois qu'il est trouvé, vous pouvez dire à PhysicsFS d'arrêter l'énumération. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien obtenu. :)

Paramètres

data pointeur vers une PHYSFS_Version à initialiser.
origdir chaîne contenant le chemin complet, en notation indépendante du système, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname le nom du fichier qui est énuméré. Il n'est pas nécessairement trié par ordre alphabétique par rapport à d'autres rappels qui ont été appelés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature des fonctions de rappel qui énumèrent des fichiers.

Remarque

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() pour avoir plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, une entrée par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire des chaînes.

Ces rappels sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions retournant des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes a priori.

Vous devez garder à l'esprit que l'ordre des données promis dans les versions de liste n'est pas nécessairement le cas dans les versions de rappel. Vérifiez la documentation des API spécifiques, mais les chaînes peuvent ne pas être triées comme vous l'attendez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data pointeur vers des données définies par l'utilisateur, passé via l'API qui a finalement appelé le rappel.
origdir chaîne contenant le chemin complet, en notation indépendante du système, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, passé dans le rappel pour votre commodité.
fname le nom du fichier qui est énuméré. Il n'est pas nécessairement trié par ordre alphabétique par rapport à d'autres rappels qui ont été appelés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenez une liste de fichiers d'un répertoire du chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec signalement des erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de la retourner à l'application, donc la fonctionnalité est identique, sauf pour la façon dont les informations sont représentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois par élément du chemin de recherche :

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Nous avons trouvé [%s] dans [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donnez-moi plus de données, s'il vous plaît.
}
// ...
PHYSFS_enumerate("/quelque/chemin", printDir, NULL);

Il n'y a aucune garantie quant à l'ordre des éléments envoyés à la fonction de rappel. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez probablement utiliser PHYSFS_enumerateFiles() à la place, qui garantit un tri alphabétique. Cette forme signale ce qui est découvert dans chaque archive avant de passer à la suivante. Même au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données seront découvertes. Tout tri que vous pourriez trouver dans ces rappels n'est que pure chance. Ne vous y fiez pas. Comme cette fonction parcourt toute la liste des archives, vous pourriez recevoir des noms de fichiers en double.

Cette API et les rappels eux-mêmes sont capables de signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne cherchaient qu'une chose spécifique et voulaient s'arrêter après, ou s'ils avaient une erreur sérieuse et ne pouvaient en alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur disque ou autre), il ne pouvait pas le signaler à l'application appelante, il devait simplement ignorer des éléments ou arrêter l'énumération directement, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble de données complet, et sa fonction de rappel a le contrôle s'il souhaite que l'énumération s'arrête plus tôt. Voir la documentation de PHYSFS_EnumerateCallback pour les détails sur la manière dont votre fonction de rappel doit se comporter.

Parameters

dir Répertoire, en notation indépendante de la plateforme, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application passées à la fonction de rappel. Peut être NULL.

Returns

Non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si la fonction de rappel retourne PHYSFS_ENUM_STOP pour s'arrêter tôt, cela sera considéré comme un succès. Les fonctions de rappel retournant PHYSFS_ENUM_ERROR feront retourner zéro à cette fonction et définiront le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

* We've got [z.sav].
* We've got [w.sav]..fi

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné à sandboxer le langage de script d'un programme, au cas où des scripts non fiables tenteraient de compromettre le système. De manière générale, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne ressentiez un danger spécifique à leur permettre, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lorsque l'on traite des noms de fichiers dans une notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

int PHYSFS_setRoot (const char * archive, const char * subdir)

PHYSFS_sint64 PHYSFS_writeBytes (PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Écrit des données dans un descripteur de fichier PhysicsFS. Le fichier doit être ouvert en écriture.

Veuillez noter que bien que (len) soit un entier non signé de 64 bits, vous êtes limité à 63 bits (9223372036854775807 octets), nous pouvons donc retourner une valeur négative en cas d'erreur. Si la longueur est supérieure à 0x7FFFFFFFFFFFFFFF, cette fonction échouera immédiatement. Pour les systèmes sans type de données 64 bits, vous êtes limité à 31 bits (0x7FFFFFFF, soit 2147483647 octets). Nous supposons que la plupart des choses n'auront pas besoin de plusieurs gigaoctets d'i/o en un seul appel, mais pourquoi limiter les choses ?

Paramètres

handle valeur de retour de PHYSFS_openWrite() ou PHYSFS_openAppend().
buffer tampon de (len) octets à écrire dans (handle).
len nombre d'octets à écrire dans (handle).

Retourne

nombre d'octets écrits. Il peut être inférieur à (len) ; en cas d'erreur, le système peut tenter d'écrire autant d'octets que possible, donc une écriture incomplète peut se produire. PHYSFS_getLastErrorCode() peut éclaircir la raison pour laquelle ce nombre pourrait être inférieur à (len). -1 en cas d'échec complet.
