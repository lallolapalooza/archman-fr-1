#define PHYSFS_file PHYSFS_File

Définit de compatibilité API 1.0. PHYSFS_file est identique à PHYSFS_File. Ce #define est là pour la compatibilité ascendante avec l'API 1.0, qui avait une convention de capitalisation incohérente dans ce cas. Le nouveau code devrait utiliser PHYSFS_File, car ce #define pourrait disparaître un jour.

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du callback : à savoir : si vous cherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous espérons avoir bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, transmis depuis l'API qui a éventuellement appelé le callback.
origdir Une chaîne de caractères contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, transmis dans le callback pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport aux autres callbacks qui ont été déclenchés, et il ne conterra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les callbacks qui énumèrent des fichiers.

Attention

À partir de PhysicsFS 2.1, utilisez plutôt PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; cela vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire d'une chaîne.

Ces callbacks sont utilisés, à partir de PhysicsFS 1.1, comme une alternative aux fonctions qui retourneraient des listes qui doivent être nettoyées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes au préalable.

Soyez conscient que l'ordre des données promis dans les versions de liste n'est pas nécessairement le cas dans les versions de callback. Vérifiez la documentation sur les API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

Paramètres

data Pointeur de données défini par l'utilisateur, transmis depuis l'API qui a éventuellement appelé le callback.
origdir Une chaîne de caractères contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, il s'agit du répertoire sur lequel vous avez demandé l'énumération, transmis dans le callback pour votre commodité.
fname Le nom du fichier qui est énuméré. Il peut ne pas être dans l'ordre alphabétique par rapport aux autres callbacks qui ont été déclenchés, et il ne conterra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Lister les fichiers d'un répertoire sur le chemin de recherche, en utilisant une fonction de rappel définie par l'utilisateur, avec rapports d'erreurs. En interne, PHYSFS_enumerateFiles() appelle simplement cette fonction, puis construit une liste avant de la retourner à l'application, donc la fonctionnalité est identique, à moins que les informations ne soient présentées différemment à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'utilisateur une fois pour chaque élément du chemin de recherche:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donne-moi plus de données, s'il te plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments passés à la fonction de rappel ne sont pas garantis d'être dans un ordre particulier. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit l'ordre alphabétique. Cette méthode signale ce qu'elle trouve dans chaque fichier archivé avant de passer au suivant. Même au sein d'une seule archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes. *Tout tri que vous trouvez dans ces rappels n'est que de la pure chance. Ne vous y fiez pas.* Comme elle parcourt toute la liste des fichiers, vous pouvez rencontrer des noms de fichiers dupliqués.

Cette API et les rappels eux-mêmes peuvent signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'un seul objet spécifique et voulaient s'arrêter ensuite, ou s'ils avaient une erreur grave et ne pouvaient en alerter personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pourrait pas le signaler à l'application appelante ; il devrait simplement sauter des éléments ou arrêter l'énumération, et l'appelant ne saurait pas qu'il a perdu des données en cours de route.

Désormais, l'appelant peut s'assurer qu'il a obtenu un ensemble complet de données, et s'il souhaite arrêter l'énumération plus tôt, son rappel a le contrôle. Voir la documentation de PHYSFS_EnumerateCallback pour plus de détails sur le comportement attendu de votre rappel.

Paramètres

dir Le répertoire, en notation indépendante du système d'exploitation, à énumérer.
c La fonction de rappel à notifier pour les éléments du chemin de recherche.
d Les données définies par l'application passées au rappel. Peut être NULL.

Valeur de retour

Non nul en cas de succès, nul en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel retourne PHYSFS_ENUM_STOP pour s'arrêter tôt, cela sera considéré comme un succès. Les rappels qui retournent PHYSFS_ENUM_ERROR feront en sorte que cette fonction retourne zéro et définissent le code d'erreur comme PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtenir une liste de fichiers d'un répertoire sur le chemin de recherche.

Avertissement

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction retournait autant d'éléments que possible en cas de condition d'erreur (erreur de mémoire, erreur d'E/S disque, etc.). Comme cela signifiait que les applications ne pouvaient pas distinguer un succès complet d'un échec partiel, et que la fonction pouvait toujours retourner NULL pour signaler une défaillance catastrophique, dans PhysicsFS 2.1, la politique de cette fonction a été modifiée : elle retournera une liste de résultats complète ou retournera NULL en cas de tout type d'erreur, afin que nous puissions garantir que l'énumération est terminée et qu'aucun élément ne manque dans vos résultats.

Les répertoires correspondants sont interpolés. C'est-à-dire que si « C:\mydir » est dans le chemin de recherche et contient un répertoire « savegames » qui contient « x.sav », « y.sav », « z.sav », et qu'il y a aussi un « C:\userdir » dans le chemin de recherche qui contient un sous-répertoire « savegames » avec « w.sav », alors le code suivant:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi

N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur retournée par cette fonction lorsque vous avez terminé.

void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que cela est davantage destiné à l'encapsulation d'un langage de script de programme, au cas où des scripts non fiables essaieraient de compromettre le système. De manière générale, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne pensiez qu'il y ait un danger spécifique à les autoriser, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire, lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié; si ce chemin est un lien symbolique, il ne sera suivi dans aucun cas. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser les liens.

Si les deux chaînes sont exclusivement des caractères ASCII bas, elle fera la bonne chose, car c'est aussi du UTF-8 valide. S'il y a des caractères ASCII étendus, elle ne fera pas ce que vous attendez !

Elle indiquera quelle chaîne est "plus grande" que l'autre, mais attention, cela ne signifie pas nécessairement grand-chose : 'a' peut être "inférieur à" 'b', mais un Kuten japonais n'a pas de relation significative avec un lambda grec, mais pouvoir attribuer une valeur fiable permet des algorithmes de tri, même s'ils ne sont pas entièrement rationnels. La plupart du temps, vous devriez traiter la valeur renvoyée comme "égal" ou "pas égal".

Comme stricmp, celle-ci attend que les deux chaînes soient terminées par un caractère nul.

Paramètres

str1 Chaîne à comparer.
str2 Chaîne à comparer.

Renvoie

-1 si str1 est "inférieur à" str2, 1 s'il est "supérieur à", 0 s'ils sont égaux.

Avertissement

vous devriez probablement utiliser PHYSFS_utf8ToUtf16(), qui est disponible depuis PhysicsFS 2.1, à moins que vous ne sachiez ce que vous faites.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convertit une chaîne UTF-8 en une chaîne UTF-16.

Attention

Cette fonction ne signalera pas d'erreur s'il y a des séquences UTF-8 invalides dans la chaîne source. Elles seront remplacées par un caractère '?' et la fonction continuera.

Les chaînes UTF-16 sont composées de 16 bits par caractère (sauf pour certains caractères qui en utilisent 32) : TCHAR sous Windows, lorsque compilé avec le support Unicode. Les versions modernes de Windows utilisent UTF-16. Les versions de Windows antérieures à 2000 utilisaient TCHAR, mais ne géraient que l'UCS-2. UTF-16 est UCS-2, à l'exception des caractères à 4 octets, qui ne sont de toute façon pas représentables en UCS-2. Si vous n'êtes pas sûr, vous devriez utiliser UTF-16 à ce stade sur Windows.

Pour garantir que le tampon de destination soit suffisamment grand pour la conversion, veuillez allouer un tampon dont la taille est le double de celle du tampon source. UTF-8 utilise de un à quatre octets par caractère, mais UTF-16 utilise toujours de deux à quatre, donc une chaîne entièrement en ASCII bas de gamme doublera de taille ! Les chaînes qui ne rentrent pas dans le tampon de destination seront tronquées, mais seront toujours terminées par un caractère nul et ne contiendront jamais une paire de substitution UTF-16 incomplète à la fin. Si la longueur du tampon est de 0, cette fonction ne fait rien.

src Chaîne source terminée par un caractère nul au format UTF-8.
dst Tampon pour stocker la chaîne UTF-16 convertie.
