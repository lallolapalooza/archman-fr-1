Définit de compatibilité API 1.0. PHYSFS_file est identique à PHYSFS_File. Ce #define est là pour la compatibilité ascendante avec l'API 1.0, qui avait une convention de capitalisation incohérente dans ce cas. Le nouveau code doit utiliser PHYSFS_File, car ce #define pourrait disparaître un jour.

PHYSFS_EnumerateCallback

PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'il peut retourner un résultat du rappel : à savoir : si vous recherchez quelque chose de spécifique, une fois que vous l'avez trouvé, vous pouvez dire à PhysicsFS d'arrêter d'énumérer davantage. Ceci est utilisé avec PHYSFS_enumerate(), que nous avons j'espère bien fait cette fois-ci. :)

Paramètres

data Pointeur de données défini par l'utilisateur, transmis par l'API qui a finalement appelé le rappel.
origdir Une chaîne contenant le chemin complet, en notation indépendante de la plateforme, du répertoire contenant ce fichier. Dans la plupart des cas, c'est le répertoire sur lequel vous avez demandé l'énumération, transmis dans le rappel pour votre commodité.
fname Le nom de fichier qui est en cours d'énumération. Il peut ne pas être dans l'ordre alphabétique par rapport aux autres rappels qui ont été déclenchés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retourne

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction pour les rappels qui énumèrent des fichiers.

Avertissement

À partir de PhysicsFS 2.1, utilisez plutôt PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; il vous donne plus de contrôle sur le processus.

Ils sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, un fichier/répertoire/lien symbolique par rappel. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas essayer de modifier ou de libérer la mémoire de toute chaîne.

Ces rappels sont utilisés, à partir de PhysicsFS 1.1, comme une alternative aux fonctions qui retournaient des listes qui devaient être nettoyées avec PHYSFS_freeList(). Le rappel signifie que la bibliothèque n'a pas besoin d'allouer une liste entière et toutes les chaînes à l'avance.

Soyez conscient que l'ordre des données promis dans les versions liste ne l'est pas nécessairement dans les versions rappel. Vérifiez la documentation sur les API spécifiques, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des chaînes dupliquées.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtiene una lista de archivos de una carpeta de ruta de búsqueda, utilizando una callback definida por el aplicativo, con errores reportados. Internamente, PHYSFS_enumerateFiles() solo llama a esta función y luego construye una lista antes de devolver a la aplicación, así que la funcionalidad es idéntica, excepto por cómo la información se presenta a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve un array. En cambio, llama a una función especificada por el aplicativo una vez por cada elemento de la ruta de búsqueda:

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSfs_ENUM_OK;  // dar más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Los elementos enviados a la callback no son garantizados para estar en ningún orden específico. No se realiza ningún ordenamiento a este nivel, y si lo necesitas, deberías usar PHYSFS_enumerateFiles(), que garantiza el orden alfabético. Esta forma reporta lo que se encuentra en cada archive antes de pasar al siguiente. Incluso dentro de un archive, no podemos garantizar el orden en el que se descubren los datos. Cualquier ordenamiento que encuentres en estas callbacks es solo pura suerte. No confíes en él. Como esta camina por toda la lista de archives, puedes recibir nombres de archivos duplicados.

Esta API y las callbacks mismas son capaces de reportar errores. Antes de esta API, las callbacks tenían que aceptar cada elemento enumerado, incluso si solo buscaban un objeto específico y querían detenerse después, o tenían un error grave y no podían notificar a nadie. Adicionalmente, si PhysicsFS mismo tenia un problema (error de disco o lo que sea), no podría reportarlo al aplicativo, simplemente ignoraría los elementos o detenería la enumeración, y el llamante no sabría que había perdido datos durante el camino.

Ahora el llamante puede estar seguro de haber obtenido un conjunto completo de datos, y si quiere detener la enumeración temprano, su callback tendrá control. Ver la documentación para PHYSFS_EnumerateCallback para detalles de cómo debe comportarse tu callback.

Parámetros

dir Carpeta, en notación independiente de plataforma, para enumerar.
c Función de callback para notificar sobre elementos de ruta.
d Datos definidos por el aplicativo pasados a la callback. Puede ser NULL.

Valor de retorno

No cero en éxito, cero en fallo. Usa PHYSFS_getLastErrorCode() para obtener el error específico. Si el callback devuelve PHYSFS_ENUM_STOP para detener temprano, esto se considera éxito. Callbacks que devuelvan PHYSFS_ENUM_ERROR harán este función devolver cero y establecerá el código de error a PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtiene una lista de archivos de una carpeta de ruta de búsqueda.

Advertencia

En versiones de PhysicsFS anteriores a 2.1, esta función devolvería tantos elementos como pudiera en caso de falla (error de memoria, error de i/o de disco, etc). Ya que esto hacía que los aplicativos no pudieran distinguir entre éxito completo y fracaso parcial, y ya que la función podía devolver NULL para reportar fallos catastróficos, en PhysicsFS 2.1 esta política cambió: devolverá una lista completa de resultados o NULL en caso de cualquier fallo, así que podemos garantizar que la enumeración terminó correctamente y no hay huecos en sus resultados.

Las carpetas que se matchen se interpolan. Es decir, si "C:\mydir" está en la ruta de búsqueda y contiene una carpeta "savegames" que contiene "x.sav", "y.sav" y "z.sav", y también hay una "C:\userdir" en la ruta de búsqueda que tiene una carpeta "savegames" con "w.sav", entonces el siguiente código:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..
Siéntete libre de ordenar la lista como quieras. Sin embargo, los datos devueltos nunca contendrán duplicados y siempre estarán ordenados alfabéticamente (o mejor dicho, sensible a mayúsculas/minúsculas en Unicode) para ti.
No olvides llamar a PHYSFS_freeList() con el valor de retorno de esta función cuando hayas terminado con él.
Parámetros
dir carpeta en notación independiente de plataforma para enumerar.
Valor de retorno
Arreglo de strings nulo-terminados, o NULL en caso de fallo.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Ajoute une archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter la même archive à deux points de montage différents : la vérification des doublons se fait par rapport à l'archive et non au point de montage.

Lorsque vous montez une archive, elle est ajoutée à un système de fichiers virtuel... tous les fichiers de toutes les archives sont interpolés dans un seul arbre de fichiers hiérarchique. Deux archives montées au même endroit (ou une archive avec des fichiers se chevauchant avec un autre point de montage) peuvent avoir des fichiers qui se chevauchent : dans un tel cas, le fichier le plus ancien dans le chemin de recherche est sélectionné, et les autres fichiers sont inaccessibles à l'application. Cela permet d'utiliser des archives pour remplacer les révisions précédentes ; vous pouvez utiliser le mécanisme de montage pour placer des archives à un point spécifique de l'arborescence des fichiers et éviter les chevauchements ; ceci est utile pour les mods téléchargeables qui pourraient piétiner les données de l'application ou se piétiner mutuellement, par exemple.

De plus, plusieurs archives peuvent être montées sur le même point de montage, ou des points de montage et le contenu des archives peuvent se chevaucher... le mécanisme d'interpolation fonctionne toujours comme d'habitude.

Spécifier un lien symbolique vers une archive ou un répertoire est autorisé ici, indépendamment de l'état de PHYSFS_permitSymbolicLinks(). Cette fonction ne concerne que les liens symboliques à l'intérieur du répertoire ou de l'archive montée.

(newDir) doit être une chaîne unique pour identifier cette archive. Elle est utilisée pour optimiser la sélection des archiveurs (si vous la nommez XXXXX.zip, nous pourrions essayer l'archiveur ZIP, par exemple, ou choisir directement un archiveur qui ne fait confiance qu'à l'extension du nom). Elle n'a pas besoin de faire référence à un fichier physique réel. Si l'extension du nom n'est pas utile, le système essaiera chaque archiveur jusqu'à ce que l'un fonctionne ou qu'aucun ne fonctionne. Cette chaîne doit être unique, car le système ne vous permettra pas d'avoir deux archives du même nom.

(ptr) doit rester valide jusqu'à ce que l'archive soit démontée. Lorsque l'archive sera démontée, le système appellera (del)(ptr), ce qui vous donnera l'occasion de libérer vos ressources. (del) peut être NULL, auquel cas le système n'essaiera pas de libérer le tampon.

Si cette fonction échoue, (del) n'est pas appelée.

Paramètres

newDir nom de fichier qui peut représenter cette chaîne.

Retour

différent de zéro si ajouté à la chaîne, zéro en cas d'échec (archive invalide, etc.). Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

void PHYSFS_permitSymbolicLinks(int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et architectures contiennent des fichiers qui ne sont que des références à d'autres fichiers. L'ouverture d'un lien symbolique dans un système physique ouvre automatiquement le fichier pointé.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue si c'est le cas. Sinon, le lien pourrait vous faire sortir des chemins de lecture et d'écriture, compromettant ainsi la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec une valeur non nulle. Notez que cela concerne davantage le sandboxing d'un langage de script du programme, au cas où des scripts non fiables tenteraient de compromettre le système. Généralement, un utilisateur peut avoir une justification légitime pour définir un lien symbolique, vous ne devriez donc pas les désactiver, sauf si vous ressentez un danger spécifique.

Les liens symboliques ne sont explicitement vérifiés que lors de la manipulation de noms de fichiers dans une notation indépendante du système. C'est-à-dire, lorsque vos chemins de recherche et d'écriture, etc., sont définis, les liens symboliques ne sont jamais vérifiés.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et elle est désactivée par défaut.

allow une valeur non nulle pour autoriser les liens symboliques, zéro pour refuser le lien.

Si vous définissez le répertoire racine à NULL ou à "/", l'archive sera traitée comme si aucun répertoire racine spécial n'avait été défini (comme si l'archive était montée normalement).

Le changement du répertoire racine n'affecte que les opérations futures sur les chemins de fichiers ; un fichier qui a déjà été ouvert à partir d'un chemin qui a changé en raison d'un setRoot ne sera pas affecté.

La définition d'un nouveau répertoire racine n'est pas limitée aux archives dans le chemin de recherche ; vous pouvez en définir une dans le répertoire d'écriture, ce qui peut être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez pas changer le répertoire d'écriture maintenant.

Ce n'est pas une erreur de définir un sous-répertoire qui n'existe pas comme répertoire racine d'une archive ; cependant, dans ce cas, aucun fichier ne sera visible. Si les répertoires manquants finissent par être créés (un mkdir sur le système de fichiers physique, etc.), cela se reflétera dans l'arbre interpolé.

Paramètres

archive Le répertoire/fichier dont le répertoire racine sera modifié.
subdir Le nouveau sous-répertoire qui deviendra le répertoire racine de cette archive.

Retour

Non nul en cas de succès, nul en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

Convertit une chaîne UTF-8 en une chaîne UTF-16.

Attention

Cette fonction ne signalera pas d'erreur s'il y a des séquences UTF-8 invalides dans la chaîne source. Elles seront remplacées par un caractère '?' et la conversion continuera.

Les chaînes UTF-16 ont 16 bits par caractère (sauf certains caractères qui en ont 32) : TCHAR sous Windows, lors de la compilation avec le support Unicode.
