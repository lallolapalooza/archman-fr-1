PHYSFS_enumerate

C'est la même chose que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, sauf qu'elle renvoie un résultat de callback : par exemple, si vous recherchez quelque chose de spécifique, une fois trouvé, vous pouvez dire à PhysicsFS d'arrêter l'énumération. Ceci est utilisé avec PHYSFS_enumerate(), qui, espérons-le, a été obtenu correctement.

Paramètres

data pointeur vers une PHYSFS_Version à initialiser.
origdir chaîne contenant le chemin complet, en notation indépendante du système, du répertoire qui contient ce fichier. Dans la plupart des cas, il s'agit du répertoire dans lequel vous avez demandé l'énumération, passé dans le callback par commodité.
fname le nom du fichier qui est énuméré. Il peut ne pas être dans un ordre alphabétique par rapport aux autres callbacks qui ont été appelés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

Retours

Une valeur de PHYSFS_EnumerateCallbackResult. Toutes les autres valeurs sont (actuellement) indéfinies ; ne les utilisez pas.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signature de fonction des callbacks qui énumèrent des fichiers.

Avertissement

Depuis PhysicsFS 2.1, utilisez PHYSFS_EnumerateCallback avec PHYSFS_enumerate() ; cela vous donne plus de contrôle sur le processus.

Ceux-ci sont utilisés pour signaler une liste d'entrées de répertoire à un appelant d'origine, une entrée par callback. Toutes les chaînes sont encodées en UTF-8. Les fonctions ne doivent pas tenter de modifier ou de libérer la mémoire de toute chaîne.

Ces callbacks sont utilisés, depuis PhysicsFS 1.1, comme alternative aux fonctions qui renvoient des listes qui doivent être libérées avec PHYSFS_freeList(). Le callback signifie que la bibliothèque n'a pas besoin d'allouer une liste complète et toutes les chaînes à l'avance.

Vous devez être conscient que l'ordre garanti des données dans les versions de liste n'est pas nécessairement maintenu dans les versions de callback. Vérifiez la documentation spécifique des API, mais les chaînes peuvent ne pas être triées comme vous vous y attendez et vous pourriez obtenir des doublons.

Paramètres

data pointeur vers des données définies par l'utilisateur, passé via l'API qui a finalement appelé le callback.
origdir chaîne contenant le chemin complet, en notation indépendante du système, du répertoire qui contient ce fichier. Dans la plupart des cas, il s'agit du répertoire dans lequel vous avez demandé l'énumération, passé dans le callback par commodité.
fname le nom du fichier qui est énuméré. Il peut ne pas être dans un ordre alphabétique par rapport aux autres callbacks qui ont été appelés, et il ne contiendra pas le chemin complet. Vous pouvez recréer le chemin complet avec $origdir/$fname ... Le fichier peut être un sous-répertoire, un fichier, un lien symbolique, etc.

int PHYSFS_delete (const char * filename)

Supprime un fichier ou un répertoire. (filename) est spécifié dans une notation indépendante de la plateforme par rapport au répertoire d'écriture.

Un répertoire doit être vide avant que cet appel puisse le supprimer.

La suppression d'un lien symbolique supprimera le lien, pas ce vers quoi il pointe, que vous ayez ou non "autorisé les liens symboliques".

Donc, si vous avez défini le répertoire d'écriture sur "C:\monjeu\repertoireecriture" et que vous appelez PHYSFS_delete("telechargements/cartes/niveau1.map") alors le fichier "C:\monjeu\repertoireecriture\telechargements\cartes\niveau1.map" est supprimé du système de fichiers physique, s'il existe et que le système d'exploitation autorise la suppression.

Notez que sur les systèmes Unix, la suppression d'un fichier peut réussir, mais le fichier réel ne sera pas supprimé tant que tous les processus qui ont un handle de fichier ouvert vers celui-ci (y compris votre programme) ne fermeront pas leurs handles.

Il y a de fortes chances que les bits qui composent le fichier existent toujours, ils sont simplement rendus disponibles pour être écrasés ultérieurement. Ne considérez pas cela comme une méthode de sécurité ou quoi que ce soit. :)

Paramètres

filename Nom du fichier à supprimer.

Retourne

une valeur non nulle en cas de succès, zéro en cas d'erreur. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenir una liste de fichiers à partir d'un chemin de recherche, en utilisant une fonction de rappel définie par l'application, avec des erreurs signalées. Internement, PHYSFS_enumerateFiles() appelle uniquement cette fonction, puis construit une liste avant de retourner à l'application, donc la fonctionnalité est identique à moins de la manière dont les informations sont présentées à l'application.

Contrairement à PHYSFS_enumerateFiles(), cette fonction ne retourne pas un tableau. Au lieu de cela, elle appelle une fonction spécifiée par l'application une fois pour chaque élément du chemin de recherche :

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // donne-moi plus de données, s'il te plaît.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Les éléments transmis à la fonction de rappel ne sont garantis dans aucun ordre spécifique. Aucun tri n'est effectué à ce niveau, et si vous en avez besoin, vous devriez utiliser PHYSFS_enumerateFiles(), qui garantit le tri alphabétique. Cette forme signale ce qui est trouvé dans chaque archive avant de passer à la suivante. Même si, au sein d'une archive, nous ne pouvons garantir l'ordre dans lequel les données sont découvertes, tout tri que vous trouverez dans ces rappels est purement le fruit du hasard. Ne vous y fiez pas. Comme cela parcourt toute la liste des archives, vous pouvez recevoir des noms de fichiers en double.

Cette API et les rappels eux-mêmes peuvent signaler des erreurs. Avant cette API, les rappels devaient accepter chaque élément énuméré, même s'ils ne recherchaient qu'un objet spécifique et voulaient s'arrêter ensuite, ou s'ils avaient une erreur grave et ne pouvaient en informer personne. De plus, si PhysicsFS lui-même avait un problème (erreur de disque ou autre), il ne pouvait pas le signaler à l'application, il ignorait simplement les éléments ou arrêtait l'énumération, et l'appelant ne saurait pas qu'il avait perdu des données en cours de route.

Maintenant, l'appelant peut être sûr d'avoir obtenu un ensemble complet de données, et s'il le souhaite, sa fonction de rappel a le contrôle de l'arrêt anticipé de l'énumération. Consultez la documentation de PHYSFS_EnumerateCallback pour savoir comment votre fonction de rappel doit se comporter.

Paramètres

dir Chemin du répertoire, en notation indépendante du système d'exploitation, à énumérer.
c Fonction de rappel pour notifier les éléments du chemin de recherche.
d Données définies par l'application transmises à la fonction de rappel. Peut être NULL.

Retourne

Non nul en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique. Si le rappel renvoie PHYSFS_ENUM_STOP, cela est considéré comme un succès. Les rappels qui renvoient PHYSFS_ENUM_ERROR feront que cette fonction renvoie zéro et définira le code d'erreur à PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtenir une liste de fichiers d'un répertoire d'un chemin de recherche.

Avertissement

Dans les versions de PhysicsFS antérieures à 2.1, cette fonction retournait autant d'éléments que possible en cas d'échec (comme une erreur de mémoire, une erreur d'E/S de disque, etc.). Comme cela rendait impossible pour les applications de distinguer entre un succès complet et un échec partiel, et comme la fonction pouvait toujours retourner NULL pour signaler des échecs catastrophiques, dans PhysicsFS 2.1 cette politique a changé : elle retournera une liste complète de résultats ou retournera NULL en cas de tout type d'échec, afin que nous puissions garantir que l'énumération est terminée et qu'elle ne contient pas de lacunes dans ses résultats.

Les dossiers correspondants sont interpolés. Autrement dit, si « C:\mydir » est dans le chemin de recherche et contient un dossier « savegames » qui contient « x.sav », « y.sav » et « z.sav », et qu'il y a aussi un « C:\userdir » dans le chemin de recherche qui a un sous-dossier « savegames » avec « w.sav », alors le code suivant :

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi
N'hésitez pas à trier la liste comme vous le souhaitez. Cependant, les données retournées ne contiendront toujours aucun doublon et seront toujours triées par ordre alphabétique (ou plutôt, ordre Unicode sensible à la casse) pour vous.
N'oubliez pas d'appeler PHYSFS_freeList() avec la valeur de retour de cette fonction lorsque vous en avez terminé.

dir répertoire en notation indépendante du système d'exploitation à énumérer.

Ajoute un archive ou un répertoire au chemin de recherche. S'il s'agit d'un doublon, l'entrée n'est pas ajoutée à nouveau, même si la fonction réussit. Vous ne pouvez pas ajouter le même archive à deux points de montage différents : le contrôle des doublons est effectué par rapport à l'archive et non au point de montage.

Lorsque vous montez un archive, il est ajouté à un système de fichiers virtuel... tous les fichiers de tous les archives sont entrelacés dans une seule hiérarchie de fichiers. void PHYSFS_permitSymbolicLinks (int allow)

Active ou désactive le suivi des liens symboliques. Certains systèmes de fichiers physiques et archives contiennent des fichiers qui ne sont que des pointeurs vers d'autres fichiers. Sur le système de fichiers physique, l'ouverture d'un tel lien ouvrira (de manière transparente) le fichier auquel il pointe.

Par défaut, PhysicsFS vérifie si un fichier est réellement un lien symbolique lors des appels d'ouverture et échoue s'il l'est. Sinon, le lien pourrait vous faire sortir des chemins d'écriture et de recherche, et compromettre la sécurité.

Si vous souhaitez prendre ce risque, appelez cette fonction avec un paramètre non nul. Notez que ceci est davantage destiné à l'isolation d'un langage de script de programme, au cas où des scripts non fiables tenteraient de compromettre le système. D'une manière générale, un utilisateur pourrait avoir une raison légitime de configurer un lien symbolique, donc à moins que vous ne ressentiez un danger spécifique à leur autorisation, vous devriez les autoriser.

Les liens symboliques ne sont explicitement vérifiés que lors du traitement des noms de fichiers en notation indépendante de la plateforme. C'est-à-dire que lors de la configuration de vos chemins de recherche et d'écriture, etc., les liens symboliques ne sont jamais vérifiés.

Veuillez noter que PHYSFS_stat() vérifiera toujours le chemin spécifié ; si ce chemin est un lien symbolique, il ne sera dans aucun cas suivi. Si les liens symboliques ne sont pas autorisés par cette fonction, PHYSFS_stat() les ignore et traiterait la requête comme si le chemin n'existait pas du tout.

La permission des liens symboliques peut être activée ou désactivée à tout moment après avoir appelé PHYSFS_init(), et est désactivée par défaut.

Paramètres

allow non nul pour autoriser les liens symboliques, zéro pour refuser le lien.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Faire d'un sous-répertoire d'une archive son répertoire racine. Cela vous permet de restreindre les fichiers accessibles dans une archive spécifique. Par exemple, si vous avez x.zip avec un fichier dans y/z.txt, monté sur /a, si vous appelez PHYSFS_setRoot("x.zip", "/y"), alors l'appel PHYSFS_openRead("/a/z.txt") réussira.

La définition d'une nouvelle racine ne se limite pas aux archives du chemin de recherche ; vous pouvez également en définir une sur le répertoire d'écriture, ce qui pourrait être utile si vous avez des fichiers ouverts en écriture et que vous ne pouvez donc pas changer le répertoire d'écriture pour le moment.

archive répertoire/archive sur lequel changer la racine.

non-zéro en cas de succès, zéro en cas d'échec. Utilisez PHYSFS_getLastErrorCode() pour obtenir l'erreur spécifique.
