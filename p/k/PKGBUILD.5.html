PKGBUILD(5) Manuel de Pacman PKGBUILD(5)

NOM

PKGBUILD - Fichier de description de construction de paquet

SYNTAXE

PKGBUILD

DESCRIPTION

Cette page de manuel décrit les règles générales relatives aux PKGBUILDs. Une fois qu'un PKGBUILD est écrit, le paquet réel sera construit à l'aide de makepkg et installé avec pacman.


Note

Un exemple de PKGBUILD, utile pour référence, se trouve dans /usr/share/pacman avec d'autres fichiers d'exemple comme un script d'installation. Vous pouvez copier le fichier PKGBUILD.proto fourni dans un nouveau répertoire de construction de paquet et apporter des modifications personnalisées selon vos besoins.

OPTIONS ET DIRECTIVES

La liste suivante présente les options et directives standard disponibles pour une utilisation dans un PKGBUILD. Celles-ci sont comprises et interprétées par makepkg, et la plupart d'entre elles sont transmises directement au paquet construit. Les entrées obligatoires pour un PKGBUILD fonctionnel minimum sont pkgname, pkgver, pkgrel et arch.

Si vous avez besoin de créer des variables personnalisées à utiliser dans le processus de construction du paquet, il est recommandé de faire précéder leur nom d'un trait de soulignement (_). Cela évite les conflits potentiels avec les variables internes de makepkg. Par exemple, pour stocker le numéro de version du noyau de base dans une variable, utilisez quelque chose comme $_basekernver.

pkgname (tableau)

Soit le nom du paquet, soit un tableau de noms de paquets pour les paquets fractionnés. Les caractères valides pour les membres de ce tableau sont alphanumériques et tout des caractères suivants : « @ . _ + - ». De plus, les noms ne peuvent pas commencer par un trait d'union ou un point.

pkgver

Il s'agit de la version du logiciel telle que publiée par l'auteur (par exemple, 2.7.1). Cette variable ne doit pas contenir de points, de barres obliques, de traits d'union ou d'espaces.

La variable pkgver peut être mise à jour automatiquement en fournissant une fonction pkgver() dans le PKGBUILD qui renvoie la nouvelle version du paquet. Celle-ci est exécutée après le téléchargement et l'extraction des fichiers sources et l'exécution de la fonction prepare() (si présente), elle peut donc utiliser ces fichiers pour déterminer la nouvelle pkgver. Ceci est plus utile lorsque vous utilisez des sources de contrôle de version (voir ci-dessous).

pkgrel

Il s'agit du numéro de version de publication spécifique à la distribution. Cela permet aux mainteneurs de mettre à jour les indicateurs de configuration du paquet, par exemple. Ceci est généralement défini à 1 pour chaque nouvelle version du logiciel amont et incrémenté pour les mises à jour intermédiaires de PKGBUILD. Cette variable est un entier positif, avec un niveau supplémentaire de sous-version spécifié par un entier positif séparé par un point (c'est-à-dire au format x.y).

epoch

Ceci est utilisé pour forcer le paquet à être considéré comme plus récent que toute version précédente avec un epoch inférieur, même si le numéro de version normal ne le ferait pas. Cette valeur est obligatoire et doit être un entier positif ; la valeur par défaut si elle n'est pas spécifiée est 0. Ceci est utile lorsque le schéma de numérotation de version d'un paquet change (ou est alphanumérique), rompant la logique normale de comparaison de version. Voir pacman(8) pour plus d'informations sur la comparaison de versions.

pkgdesc

Ceci devrait être une brève description du paquet et de sa fonctionnalité. Essayez de garder la description en un seul texte et de ne pas utiliser le nom du paquet.

url

Ceci est utilisé pour contenir une URL associée au logiciel en cours de paquetage. C'est typiquement le site web du projet.

license (tableau)

Ce champ spécifie les licences qui s'appliquent au paquet. Si plusieurs licences sont applicables, listez-les toutes : license=('GPL' 'FDL').

install

Spécifie un script d'installation spécial qui est inclus dans le paquet. Ce fichier doit résider dans le même répertoire que le PKGBUILD et est copié dans le paquet par makepkg. Il n'est pas nécessaire de l'inclure dans le tableau des sources (par exemple, install=$pkgname.install).

changelog

Spécifie un fichier de journal des modifications qui est inclus dans le paquet. Le fichier de journal des modifications doit se terminer par un seul saut de ligne. Ce fichier doit résider dans le même répertoire que le PKGBUILD et est copié dans le paquet par makepkg. Il n'est pas nécessaire de l'inclure dans le tableau des sources (par exemple, changelog=$pkgname.changelog).

source (tableau)

Un tableau de fichiers sources nécessaires pour construire le paquet. Les fichiers sources doivent résider dans le même répertoire que le PKGBUILD, ou être une URL complètement qualifiée que makepkg peut utiliser pour télécharger le fichier. Pour simplifier la maintenance des PKGBUILD, utilisez les variables $pkgname et $pkgver lors de la spécification de l'emplacement de téléchargement, si possible. Les fichiers compressés seront automatiquement extraits, à moins qu'ils ne soient listés dans le tableau noextract décrit ci-dessous.

Les fichiers dans le tableau source avec les extensions .sig, .sign ou .asc sont reconnus par makepkg comme des signatures PGP et sont utilisés automatiquement pour vérifier l'intégrité du fichier correspondant.

validpgpkeys (tableau)

Un tableau d'empreintes digitales PGP. Si ce tableau n'est pas vide, makepkg n'acceptera que les signatures des clés listées ici et ignorera les valeurs de confiance des clés du trousseau. Si le fichier source a été signé avec une sous-clé, makepkg utilisera toujours la clé principale pour la comparaison.

Seules les empreintes complètes sont acceptées. Elles doivent être en majuscules et ne pas contenir d'espaces.

noextract (tableau)

Un tableau de noms de fichiers correspondant à ceux de la liste source. Les fichiers listés ici ne seront pas extraits avec les autres fichiers sources. Ceci est utile pour les paquets qui utilisent directement des données compressées.

cksums (tableau)

Ce tableau contient les sommes de contrôle CRC pour chaque fichier source spécifié dans le tableau source (dans le même ordre). makepkg les utilisera pour vérifier l'intégrité des fichiers sources lors des futures constructions. Si la valeur SKIP est placée dans le tableau au lieu d'une somme de contrôle normale, la vérification d'intégrité pour ce fichier source sera ignorée. Pour générer facilement des sommes de contrôle, exécutez makepkg -g > PKGBUILD. Si vous le souhaitez, déplacez la ligne cksums à un endroit approprié. Il convient de noter que les sommes de contrôle générées par makepkg -g doivent être vérifiées à l'aide des valeurs de sommes de contrôle fournies par le développeur du logiciel.

md5sums, sha1sums, sha224sums, sha256sums, sha384sums, sha512sums, b2sums (tableaux)

Vérifications d'intégrité alternatives que makepkg prend en charge ; toutes sont similaires à l'option cksums décrite ci-dessus. Pour activer leur utilisation et leur génération, assurez-vous de configurer l'option INTEGRITY_CHECK dans makepkg.conf(5).

groups (tableau)

Un tableau de noms symboliques représentant des groupes de paquets, permettant l'installation de plusieurs paquets en demandant un seul objectif. Par exemple, on peut installer tous les paquets KDE en installant le groupe kde.

arch (tableau)

Définit sur quelles architectures le paquet donné est disponible (par exemple, arch=('i686' 'x86_64')). Les paquets ne contenant aucun fichier spécifique à l'architecture doivent utiliser arch=('any'). Les caractères valides pour les membres de ce tableau sont alphanumériques et le caractère _.

backup (tableau)

Un tableau de noms de fichiers, sans préfixe de chemin, qui doivent être conservés si le paquet est supprimé ou mis à jour. Ceci est couramment utilisé pour les paquets qui placent des fichiers de configuration dans /etc. Voir « Gestion des fichiers de configuration » dans pacman(8) pour plus d'informations.

depends (tableau)

Un tableau de paquets dont le paquet dépend. Par exemple, il dépend de libfoo et libbar.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

ages dont ce paquet dépend pour fonctionner. Les entrées de cette liste doivent être entourées d'apostrophes et contenir au moins le nom du paquet. Les entrées peuvent également inclure une exigence de version de la forme nom<>version, où <> est l'une des cinq comparaisons : >= (supérieur ou égal à), <= (inférieur ou égal à), = (égal à), > (supérieur à), ou < (inférieur à).

Si le nom de la dépendance semble être une bibliothèque (se termine par .so), makepkg essaiera de trouver un binaire qui dépend de la bibliothèque dans le paquet construit et ajoutera la version requise par le binaire. L'ajout de la version vous-même désactive la détection automatique.

Des dépendances supplémentaires spécifiques à l'architecture peuvent être ajoutées en ajoutant un trait d'union bas et le nom de l'architecture, par exemple depends_x86_64=().

makedepends (tableau)

Un tableau de paquets dont ce paquet dépend pour la construction, mais qui ne sont pas nécessaires à l'exécution. Les paquets de cette liste suivent le même format que depends.

Des dépendances de construction supplémentaires spécifiques à l'architecture peuvent être ajoutées en ajoutant un trait d'union bas et le nom de l'architecture, par exemple makedepends_x86_64=().

checkdepends (tableau)

Un tableau de paquets dont ce paquet dépend pour exécuter sa suite de tests, mais qui ne sont pas nécessaires à l'exécution. Les paquets de cette liste suivent le même format que depends. Ces dépendances ne sont prises en compte que lorsque la fonction check() est présente et doit être exécutée par makepkg.

Des dépendances de vérification supplémentaires spécifiques à l'architecture peuvent être ajoutées en ajoutant un trait d'union bas et le nom de l'architecture, par exemple checkdepends_x86_64=().

optdepends (tableau)

Un tableau de paquets (et les raisons associées) qui ne sont pas essentiels pour la fonctionnalité de base, mais qui peuvent être nécessaires pour tirer pleinement parti du contenu de ce paquet. Les optdepends sont actuellement à des fins d'information uniquement et ne sont pas utilisés par pacman lors de la résolution des dépendances. Les paquets de cette liste suivent le même format que depends, avec une description facultative ajoutée. Le format pour spécifier les descriptions d'optdepends est : 
optdepends=('python: pour les liaisons de bibliothèque')

Des dépendances optionnelles supplémentaires spécifiques à l'architecture peuvent être ajoutées en ajoutant un trait d'union bas et le nom de l'architecture, par exemple optdepends_x86_64=().

conflicts (tableau)

Un tableau de paquets qui entreront en conflit avec ce paquet (c'est-à-dire qu'ils ne peuvent pas être installés en même temps). Cette directive suit le même format que depends. Les conflits versionnés sont pris en charge à l'aide des opérateurs décrits dans depends.

Des conflits supplémentaires spécifiques à l'architecture peuvent être ajoutés en ajoutant un trait d'union bas et le nom de l'architecture, par exemple conflicts_x86_64=().

provides (tableau)

Un tableau de « provisions virtuelles » que ce paquet fournit. Cela permet à un paquet de fournir des dépendances autres que son propre nom de paquet. Par exemple, le paquet dcron peut fournir cron, ce qui permet aux paquets de dépendre de cron plutôt que de dcron OU fcron.

Les provisions versionnées sont également possibles, au format nom=version. Par exemple, dcron peut fournir cron=2.0 pour satisfaire la dépendance cron>=2.0 d'autres paquets. Les provisions impliquant les opérateurs > et < sont invalides car seules des versions spécifiques d'un paquet peuvent être fournies.

Si le nom de la provision semble être une bibliothèque (se termine par .so), makepkg essaiera de trouver la bibliothèque dans le paquet construit et d'ajouter la version correcte. L'ajout de la version vous-même désactive la détection automatique.

Des provisions supplémentaires spécifiques à l'architecture peuvent être ajoutées en ajoutant un trait d'union bas et le nom de l'architecture, par exemple provides_x86_64=().

replaces (tableau)

Un tableau de paquets que ce paquet doit remplacer. Cela peut être utilisé pour gérer les paquets renommés/combinés. Par exemple, si le paquet j2re est renommé en jre, cette directive permet aux futures mises à niveau de continuer comme prévu même si le paquet a été déplacé. Les remplacements versionnés sont pris en charge à l'aide des opérateurs décrits dans depends.

Sysupgrade est actuellement la seule opération pacman qui utilise ce champ. Une synchronisation ou une mise à niveau normale n'utilisera pas sa valeur.

Des remplacements supplémentaires spécifiques à l'architecture peuvent être ajoutés en ajoutant un trait d'union bas et le nom de l'architecture, par exemple replaces_x86_64=().

options (tableau)

Ce tableau vous permet de remplacer certains des comportements par défaut de makepkg lors de la construction de paquets. Pour définir une option, incluez simplement le nom de l'option dans le tableau options. Pour inverser le comportement par défaut, placez un « ! » au début de l'option. Spécifiez uniquement les options que vous souhaitez spécifiquement remplacer, les autres seront prises dans makepkg.conf(5). **NOTE :** force est une option maintenant supprimée en faveur de la variable epoch de niveau supérieur.

strip

Supprime les symboles des binaires et des bibliothèques. Si vous utilisez fréquemment un débogueur sur des programmes ou des bibliothèques, il peut être utile de désactiver cette option.

docs

Enregistre les répertoires de documentation. Si vous souhaitez supprimer les répertoires de documentation, spécifiez !docs dans le tableau.

libtool

Laisse les fichiers libtool (.la) dans les paquets. Spécifiez !libtool pour les supprimer.

staticlibs

Laisse les fichiers de bibliothèque statique (.a) dans les paquets. Spécifiez !staticlibs pour les supprimer (s'ils ont une contrepartie partagée).

emptydirs

Laisse les répertoires vides dans les paquets.

zipman

Compresse les pages de manuel et d'informations avec gzip.

ccache

Autorise l'utilisation de ccache pendant build(). Plus utile sous sa forme négative !ccache avec des paquets sélectionnés qui ont des problèmes de construction avec ccache.

distcc

Autorise l'utilisation de distcc pendant build(). Plus utile sous sa forme négative !distcc avec des paquets sélectionnés qui ont des problèmes de construction avec distcc.

buildflags

Autorise l'utilisation de buildflags spécifiques à l'utilisateur (CPPFLAGS, CFLAGS, CXXFLAGS, LDFLAGS) pendant build() comme spécifié dans makepkg.conf(5). Plus utile sous sa forme négative !buildflags avec des paquets sélectionnés qui ont des problèmes de construction avec des buildflags personnalisés.

makeflags

Autorise l'utilisation de makeflags spécifiques à l'utilisateur pendant build() comme spécifié dans makepkg.conf(5). Plus utile sous sa forme négative !makeflags avec des paquets sélectionnés qui ont des problèmes de construction avec des makeflags personnalisés tels que -j2 (ou supérieur).

debug

Ajoute les drapeaux de débogage spécifiés par l'utilisateur (DEBUG_CFLAGS, DEBUG_CXXFLAGS) à leurs drapeaux de construction correspondants comme spécifié dans makepkg.conf(5). Lorsqu'il est utilisé en combinaison avec l'option « strip », un paquet séparé contenant les symboles de débogage est créé.

lto

Active la construction de paquets utilisant l'optimisation au moment de la liaison. Ajoute -flto à CFLAGS et CXXFLAGS.

FONCTIONS DE CONDITIONNEMENT

En plus des directives ci-dessus, les PKGBUILDs nécessitent un ensemble de fonctions qui fournissent des instructions pour construire et installer le paquet. Au minimum, le PKGBUILD doit contenir une fonction package() qui installe tous les fichiers du paquet dans le répertoire de conditionnement, avec des fonctions facultatives prepare(), build(), et check() étant utilisées pour créer ces fichiers à partir des sources.

Ceci est directement sourcé et exécuté par makepkg, donc tout ce qui est disponible dans Bash ou le système est disponible ici. Assurez-vous que toutes les commandes exotiques utilisées sont couvertes par le tableau makedepends.

Si vous créez vos propres variables dans l'une de ces fonctions, il est recommandé d'utiliser le mot-clé local de Bash pour limiter la portée de la variable à l'intérieur de la fonction.

Fonction package()

La fonction package() est utilisée pour installer des fichiers dans le répertoire qui deviendra la racine du paquet construit et est exécutée après toutes les fonctions facultatives listées ci-dessous. L'étape de conditionnement est exécutée à l'aide de fakeroot pour garantir les autorisations de fichiers correctes dans le paquet résultant. Toutes les autres fonctions seront exécutées en tant qu'utilisateur appelant makepkg. Cette fonction est exécutée dans $srcdir.

Fonction verify()

Une fonction verify() facultative peut être spécifiée pour implémenter une authentification arbitraire des sources. La fonction doit retourner un code de sortie non nul lorsque la vérification échoue. Cette fonction est exécutée avant l'extraction des sources. Cette fonction est exécutée dans $startdir.

Fonction prepare()

Une fonction prepare() facultative peut être spécifiée dans laquelle les opérations pour préparer les sources à la construction, telles que l'application de correctifs, sont effectuées. Cette fonction est exécutée après l'extraction des sources et avant la fonction build(). La fonction prepare() est ignorée lorsque l'extraction des sources est ignorée. Cette fonction est exécutée dans $srcdir.

Fonction build()

La fonction build() facultative est utilisée pour compiler et/ou ajuster les fichiers sources en préparation à être installés par la fonction package(). Cette fonction est exécutée dans $srcdir.

Fonction check()

Une fonction check() facultative peut être spécifiée dans laquelle la suite de tests d'un paquet peut être exécutée. Cette fonction est exécutée entre les fonctions build() et package(). Assurez-vous que toutes les commandes exotiques utilisées sont couvertes par le tableau checkdepends. Cette fonction est exécutée dans $srcdir.

Toutes les variables ci-dessus telles que $pkgname et $pkgver sont disponibles pour être utilisées dans les fonctions de conditionnement. De plus, makepkg définit les variables suivantes :

srcdir

Ceci contient le répertoire où makepkg extrait ou copie tous les fichiers sources.

pkgdir

Ceci contient le répertoire où makepkg regroupe le paquet installé. Ce répertoire deviendra la racine de votre paquet construit. Cette variable ne doit être utilisée que dans la fonction package().

startdir

Ceci contient le chemin absolu vers le répertoire où se trouve le PKGBUILD, ce qui correspond généralement à la sortie de $(pwd) lorsque makepkg est démarré. L'utilisation de cette variable est obsolète et fortement déconseillée.

DIVISION DES PAQUETS

makepkg prend en charge la construction de plusieurs paquets à partir d'un seul PKGBUILD. Ceci est réalisé en assignant un tableau de noms de paquets à la directive pkgname. Chaque paquet divisé utilise une fonction de conditionnement correspondante nommée package_foo(), où foo est le nom du paquet divisé.

EXEMPLE

Voici un exemple de fichier PKGBUILD pour le paquet patch.

# Maintainer: Joe User <joe.user@example.com>
pkgname=patch
pkgver=2.7.1
pkgrel=1
pkgdesc="A utility to apply patch files to original files"
arch=('i686' 'x86_64')
url="https://www.gnu.org/software/patch/patch.html"
license=('GPL')
groups=('base-devel')
depends=('glibc')
makedepends=('ed')
optdepends=('ed: for "patch -e" functionality')
source=("ftp://ftp.gnu.org/gnu/$pkgname/$pkgname-$pkgver.tar.xz"{,.sig})
sha256sums=('9124ba46db0abd873d0995c2ca880e81252676bb6c03e0a37dfc5f608a9b0ceb'
            'SKIP')
build() {
        cd "$srcdir/$pkgname-$pkgver"
        ./configure --prefix=/usr
        make
}
package() {
        cd "$srcdir/$pkgname-$pkgver"
        make DESTDIR="$pkgdir/" install
}

BOGUES

Des bogues ? Vous plaisantez ; il n'y a pas de bogues dans ce logiciel.
