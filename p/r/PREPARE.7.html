NOM

PREPARE - préparer une requête pour exécution

SYNOPSIS

PREPARE nom [ ( type_donnees [, ...] ) ] AS requete

DESCRIPTION

PREPARE crée une requête préparée. Une requête préparée est un objet côté serveur qui peut être utilisé pour optimiser les performances. Lorsque la commande PREPARE est exécutée, la requête spécifiée est analysée, traitée et réécrite. Lorsqu'une commande EXECUTE est ensuite émise, la requête préparée est planifiée et exécutée. Cette division du travail évite les analyses répétitives, tout en permettant au plan d'exécution de dépendre des valeurs spécifiques des paramètres fournies.

Les requêtes préparées peuvent prendre des paramètres : des valeurs qui sont substituées dans la requête lors de son exécution. Lors de la création de la requête préparée, référez-vous aux paramètres par leur position, en utilisant $1, $2, etc. Une liste correspondante de types de données de paramètres peut facultativement être spécifiée. Lorsqu'un type de données de paramètre n'est pas spécifié ou est déclaré comme inconnu, le type est inféré du contexte dans lequel le paramètre est référencé pour la première fois (si possible). Lors de l'exécution de la requête, spécifiez les valeurs réelles de ces paramètres dans la commande EXECUTE. Référez-vous à EXECUTE(7) pour plus d'informations.

Les requêtes préparées n'existent que pendant la durée de la session de base de données actuelle. Lorsque la session se termine, la requête préparée est oubliée, elle doit donc être recréée avant d'être utilisée à nouveau. Cela signifie également qu'une seule requête préparée ne peut pas être utilisée par plusieurs clients de base de données simultanés ; cependant, chaque client peut créer sa propre requête préparée à utiliser. Les requêtes préparées peuvent être nettoyées manuellement à l'aide de la commande DEALLOCATE.

Les requêtes préparées ont potentiellement le plus grand avantage de performance lorsqu'une seule session est utilisée pour exécuter un grand nombre de requêtes similaires. La différence de performance sera particulièrement significative si les requêtes sont complexes à planifier ou à réécrire, par exemple si la requête implique une jointure de nombreuses tables ou nécessite l'application de plusieurs règles. Si la requête est relativement simple à planifier et à réécrire mais relativement coûteuse à exécuter, l'avantage de performance des requêtes préparées sera moins perceptible.

PARAMÈTRES

nom

Un nom arbitraire donné à cette requête préparée particulière. Il doit être unique au sein d'une seule session et est ensuite utilisé pour exécuter ou désallouer une requête préparée précédemment.

type_donnees

Le type de données d'un paramètre de la requête préparée. Si le type de données d'un paramètre particulier n'est pas spécifié ou est spécifié comme inconnu, il sera inféré du contexte dans lequel le paramètre est référencé pour la première fois. Pour faire référence aux paramètres dans la requête préparée elle-même, utilisez $1, $2, etc.

requete

Toute requête SELECT, INSERT, UPDATE, DELETE, MERGE ou VALUES.

NOTES

Une requête préparée peut être exécutée avec un plan générique ou un plan personnalisé. Un plan générique est le même pour toutes les exécutions, tandis qu'un plan personnalisé est généré pour une exécution spécifique en utilisant les valeurs des paramètres données lors de cet appel. L'utilisation d'un plan générique évite les frais de planification, mais dans certaines situations, un plan personnalisé sera beaucoup plus efficace à exécuter car le planificateur peut utiliser la connaissance des valeurs des paramètres. (Bien sûr, si la requête préparée n'a pas de paramètres, cela n'a pas d'importance et un plan générique est toujours utilisé.)

Par défaut (c'est-à-dire lorsque plan_cache_mode est réglé sur auto), le serveur choisira automatiquement s'il faut utiliser un plan générique ou personnalisé pour une requête préparée qui a des paramètres. La règle actuelle est que les cinq premières exécutions sont effectuées avec des plans personnalisés et le coût estimé moyen de ces plans est calculé. Ensuite, un plan générique est créé et son coût estimé est comparé au coût moyen des plans personnalisés. Les exécutions ultérieures utilisent le plan générique si son coût n'est pas tellement plus élevé que le coût moyen des plans personnalisés au point de rendre la replanification répétée préférable.

Cette heuristique peut être contournée, forçant le serveur à utiliser des plans génériques ou personnalisés, en réglant plan_cache_mode sur force_generic_plan ou force_custom_plan respectivement. Ce réglage est principalement utile si l'estimation du coût du plan générique est erronée pour une raison quelconque, permettant de le choisir même si son coût réel est bien supérieur à celui d'un plan personnalisé.

Pour examiner le plan de requête que PostgreSQL utilise pour une requête préparée, utilisez EXPLAIN, par exemple

EXPLAIN EXECUTE nom(valeurs_parametres);

Si un plan générique est utilisé, il contiendra les symboles de paramètre $n, tandis qu'un plan personnalisé aura les valeurs de paramètre fournies substituées.

Pour plus d'informations sur la planification des requêtes et les statistiques collectées par PostgreSQL à cette fin, consultez la documentation de ANALYZE(7).

Bien que l'objectif principal d'une requête préparée soit d'éviter l'analyse syntaxique et la planification répétitives de la requête, PostgreSQL forcera la ré-analyse et la replanification de la requête avant de l'utiliser chaque fois que les objets de base de données utilisés dans la requête ont subi des modifications de définition (DDL) ou que leurs statistiques de planification ont été mises à jour depuis la dernière utilisation de la requête préparée. De plus, si la valeur de search_path change d'une utilisation à l'autre, la requête sera réanalysée en utilisant le nouveau search_path. (Ce dernier comportement est nouveau depuis PostgreSQL 9.3.) Ces règles rendent l'utilisation d'une requête préparée sémantiquement presque équivalente à la soumission répétée du même texte de requête, mais avec un avantage de performance si aucune définition d'objet n'est modifiée, en particulier si le meilleur plan reste le même entre les utilisations. Un exemple de cas où l'équivalence sémantique n'est pas parfaite est que si la requête fait référence à une table par un nom non qualifié, puis qu'une nouvelle table du même nom est créée dans un schéma apparaissant plus tôt dans le search_path, aucune ré-analyse automatique ne se produira car aucun objet utilisé dans la requête n'a changé. Cependant, si un autre changement force une ré-analyse, la nouvelle table sera référencée dans les utilisations ultérieures.

Vous pouvez voir toutes les requêtes préparées disponibles dans la session en interrogeant la vue système pg_prepared_statements.

EXEMPLES

Créez une requête préparée pour une instruction INSERT, puis exécutez-la :

PREPARE fooplan (int, text, bool, numeric) AS
    INSERT INTO foo VALUES($1, $2, $3, $4);
EXECUTE fooplan(1, 'Hunter Valley', 't', 200.00);

Créez une requête préparée pour une instruction SELECT, puis exécutez-la :

PREPARE usrrptplan (int) AS
    SELECT * FROM users u, logs l WHERE u.usrid=$1 AND u.usrid=l.usrid
    AND l.date = $2;
EXECUTE usrrptplan(1, current_date);

Dans cet exemple, le type de données du deuxième paramètre n'est pas spécifié, il est donc inféré du contexte dans lequel $2 est utilisé.

COMPATIBILITÉ

La norme SQL inclut une instruction PREPARE, mais elle n'est utilisable que dans le SQL embarqué. Cette version de l'instruction PREPARE utilise également une syntaxe quelque peu différente.
