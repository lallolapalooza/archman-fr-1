Comment écrire un parser JSON en Pegex

Ce document détaille la création du module CPAN : Pegex::JSON, qui est un parser/décodeur JSON écrit en Perl à l'aide du framework de parsing Pegex. Le code est sur GitHub ici :

https://github.com/ingydotnet/pegex-json-pm

Tester d'abord

Regardez l'exemple de test :

https://github.com/ingydotnet/pegex-json-pm/blob/master/test/test.t

Ce test simple contient de nombreuses parties JSON et leurs équivalents YAML. Il est supposé que lors du décodage du JSON, cela correspondra au YAML.

Le test est écrit dans un langage de test connu sous le nom de TestML. TestML n'utilise que Pegex dans son compilateur. TestML et Pegex sont tous deux des frameworks Acmeist, c'est-à-dire qu'ils sont censés fonctionner dans plusieurs langages de programmation.

Vous pouvez exécuter le test normalement :

> prove -lv t/test.t

La grammaire Pegex JSON

La prochaine étape consiste à écrire la grammaire JSON dans le langage de grammaire Pegex. L'écriture de grammaires est le cœur et l'âme de l'utilisation de Pegex. Une grammaire est simplement une définition d'un langage qui spécifie ce qu'est quoi, et comment il doit être structuré.

Comme Pegex est Acmeist, j'ai placé la grammaire JSON dans son propre dépôt afin qu'elle puisse être partagée par de nombreux projets dans différents langages de programmation. Le fichier de grammaire est ici :

https://github.com/ingydotnet/json-pgx/blob/master/json.pgx

Examinons cette définition de langage petite mais complète en détail.

Le fichier commence par quelques commentaires. Les commentaires peuvent être utilisés librement dans Pegex et vont d'un '#' jusqu'à la fin d'une ligne. Comme on pourrait s'y attendre.

# Une grammaire simple pour le langage de données JSON.
# Pour les implémentations de parser utilisant cette grammaire, voir :
# * https://github.com/ingydotnet/pegex-json-pm

Ensuite, nous avons ce qu'on appelle la section méta de la grammaire.

%grammar json
%version 0.0.1

Les lignes de section méta ont le format :

%clé valeur

Votre grammaire doit avoir au moins un nom et une version.

Tout le reste dans la grammaire est un ensemble de choses appelées « règles ». Une règle a un nom et une définition. La première règle d'un langage est spéciale. Lorsque le parser commence à la parser, la règle numéro un est utilisée par défaut comme règle de départ (bien que cela puisse être remplacé).

Nous commençons par cette règle :

json: map | seq

Le nom de cette règle est « json ». Lorsque nous commençons à parser le JSON, nous disons que tout le texte doit correspondre à la règle « json ». Cela a beaucoup de sens.

Ce style de parsing est connu sous le nom de Top Down et de Recursive Descent. Pegex est les deux. Il faut noter que Pegex ne tokenise pas un texte avant de le parser. Les règles elles-mêmes forment une sorte de tokenizer, extrayant les segments de données souhaités au besoin.

Dans cette règle, nous disons qu'un document « json » est soit une « map » (aka mapping ou hash), soit une « seq » (aka sequence ou array), ce qui, en supposant que vous connaissez le JSON (autour de presque tout le monde), est la seule chose autorisée au niveau supérieur.

Dans cette règle, « map » et « seq » sont appelées « références de règles ». Elles pointent vers d'autres règles nommées que l'on s'attend à trouver dans la grammaire. Les références sont généralement juste le nom de la sous-règle, mais elles peuvent aussi être entourées d'accolades (bien que parfois nécessaires). Ainsi, la règle ci-dessus pourrait également être écrite comme ceci :

json: map | seq

On introduit également le OU, qui est un simple caractère Pipe. Il faut aussi noter qu'un DEUX-POINTS sépare le nom de la règle et sa définition.

La ligne suivante définit une nouvelle règle nommée « node » :

node: map | seq | scalar

Nous appelons « node » les types de structures générales que tout point de l'arbre de données JSON peut être. C'est simplement un mapping, une séquence ou un scalaire.

Ensuite, nous devons définir les règles décrivant « map », « seq » et « scalar ». Une grammaire est complète lorsque toutes ses références de règles sont définies.

Commençons par « map » :

map:
    /- LCURLY -/
    pair* % /- COMMA -/
    /- RCURLY -/

Cela ressemble à un peu plus compliqué, mais nous allons le décomposer, un par un. Ce que nous découvrirons, c'est que cette règle signifie qu'une map est '{' suivie de zéro ou plusieurs (paires clé/valeur) séparées par une virgule, puis terminée par '}'. Pendant ce processus, il peut également y avoir des espaces blancs intermittents. Le caractère '-' indique des espaces blancs, mais nous le verrons plus tard.

La première chose que nous remarquons, c'est qu'une définition de règle peut s'étendre sur plusieurs lignes. Une définition de règle se termine lorsque la règle suivante commence. Pegex permet effectivement plusieurs règles sur une ligne, mais elles doivent être séparées par un point-virgule, comme ceci :

rule1: a|b; rule2: c|d; rule3: e|f

La prochaine chose que je vois sont les caractères de barre oblique inverse. Tout comme en Perl et JavaScript, une paire de barres obliques inverses indique une expression régulière. Dans cette règle, nous avons trois expressions régulières.

C'est le bon moment pour signaler que les grammaires Pegex sont compilées dans une structure simple que vous pouvez exprimer en JSON ou en YAML. En fait, le dépôt contenant la grammaire Pegex que nous discutons contient également les formes compilées correspondantes. Voir :

https://github.com/ingydotnet/json-pgx/blob/master/json.pgx.yaml

Un coup d'œil rapide à ce fichier montre les mêmes définitions de règles, mais les expressions régulières sont très différentes.

C'est parce que Pegex essaie de rendre les expressions régulières lisibles et composables. Cela signifie que des expressions régulières complexes peuvent être définies comme de petites parties qui composent des parties plus grandes. Au moment de la compilation, elles peuvent être difficiles à comprendre.

Par exemple, si nous avions cette grammaire Pegex :

greeting: / hello COMMA - world /
hello: / (:'O' SPACE 'HAI' | 'Hey' SPACE 'there') /
world: / (:Earth|Mars|Venus) /

cela compilerait en :

greeting:
  .rgx: (?:O\ HAI|Hey\ there),\s*(?:Earth|Mars|Venus)

Remarque : les règles 'hello' et 'world' ont été supprimées, mais leurs définitions ont été incorporées dans la grande expression régulière pour 'greeting'.

Il y a également des références à des choses comme COMMA et SPACE. Ce sont des ATOMS Pegex, et il y a des atomes pour tous les caractères de ponctuation, les caractères d'espace et autres. La liste complète se trouve ici : Pegex::Grammar::Atoms.

Écrire 'SEMI' au lieu de ';' semble étrange au début, mais c'est ainsi que Pegex sépare facilement la métasyntaxe de ce qui doit être correspondant. Une fois que vous vous y habituez, c'est très lisible.

Les espaces blancs (et les commentaires) à l'intérieur d'une expression régulière sont complètement ignorés par Pegex. C'est pareil que le flag 'x' de Perl.

Le '-' est l'indicateur d'espace blanc de Pegex, et il se développe généralement en "\s*". En fait, il se développe en "ws1", qui se développe en "ws*", qui se développe en "WS*", qui se développe en "\s*" (à moins que vous ne remplaciez l'une de ces règles).

Revenons au JSON...

La règle que nous avons définie pour 'map' devrait maintenant être plus lisible. Regardons-la à nouveau, mais cette fois dans un format plus compact :

map: /- LCURLY -/   (pair* % /- COMMA -/)   /- RCURLY -/

J'ai compacté les expressions régulières (puisqu'elles ne signifient que des accolades et des virgules avec des espaces blancs), et j'ai ajouté des parenthèses au milieu pour indiquer que l'opérateur '%' a une liaison plus forte.

Qu'est-ce que l'opérateur '%' ? Il a été emprunté au langage de règles de Perl 6. Considérez :

a+ % b

Cela signifie une ou plusieurs 'a', séparées par 'b'. Simple. L'opérateur %% signifie la même chose, sauf qu'il indique qu'un 'b' final est acceptable.

Cette notation est utile pour les listes séparées par des virgules. (Exactement ce que nous utilisons ici.)

La règle ci-dessus signifie zéro ou plusieurs 'pair' séparés par des virgules. (Pas de virgule finale autorisée, ce qui est strictement correct en JSON).

C'est le bon moment pour mentionner les 'quantificateurs de règles'. Un quantificateur de règle est un suffixe à une référence de règle, et peut être l'un de ?, * ou +. Ces suffixes signifient la même chose qu'en expressions régulières.

Il existe deux autres suffixes de quantificateurs. '2+' est équivalent à la syntaxe d'expression régulière {2,} et 2-5 est équivalent à {2,5}. Lorsque vous utilisez l'un de ces deux formats, vous devez mettre la référence de règle entre crochets, sinon le nombre apparaît comme faisant partie du nom de la règle. Par exemple :

rule1: <rule2>5

-9 <règle3>29+

pas :

règle1: règle25-9 règle329+

Regardons cette règle après compilation par Pegex :

map:
  .all:
  - .rgx: \s*\{\s*
  - +min: 0
    .ref: pair
    .sep:
      .rgx: \s*,\s*
  - .rgx: \s*\}\s*

La règle pour 'map' indique que le texte doit correspondre à 3 choses : une expression régulière (une accolade ouvrante), zéro ou plusieurs occurrences d'une règle nommée 'pair' séparées par une expression régulière (une virgule), et enfin une autre expression régulière (une accolade fermante).

Une chose que nous avons implicitement couverte est l'opérateur ET. C'est parce qu'il n'y a pas de symbole d'opérateur pour cela. Considérons les règles :

a: b c+ /d/
b: c | d
c: d e | f % g

Le caractère PIPE entre 2 choses signifie OU. Aucun symbole entre 2 choses signifie ET. Un POURCENT signifie ALTERNATION. L'ALTERNATION est la plus prioritaire et le OU est le moins prioritaire, avec le ET au milieu. La précédence peut être désambiguïsée avec des parenthèses. Ainsi, la règle pour 'c' peut être reformulée :

c: ((d e) | (f % g))

OK. Je pense que nous avons couvert à peu près tout ce qui est nécessaire jusqu'à présent. C'était beaucoup d'apprentissage pour une seule règle, mais maintenant vous connaissez la plupart de Pegex !

Les trois règles suivantes ne nécessitent aucune nouvelle connaissance. Jetez un œil à celles-ci et voyez si vous pouvez les comprendre.

pair:
    string
    /- COLON -/
    node
seq:
    /- LSQUARE -/
    node* % /- COMMA -/
    /- RSQUARE -/
scalar:
    string |
    number |
    boolean |
    null

Une paire (vous savez... une clé/valeur de hachage), est une chaîne, deux points et un nœud. Une séquence est zéro ou plusieurs nœuds séparés par des virgules entre crochets. Un scalaire peut être l'une des 4 formes. Simple.

Un point intéressant qui vient d'être soulevé ici est l'utilisation de la récursion. Les règles pour 'pair' et 'seq' font toutes deux référence à la règle pour 'node'. Ainsi, la grammaire est une descente récursive. Elle commence par la règle de l'ensemble (c'est-à-dire 'json') et descend (récursivement) jusqu'à ce qu'elle corresponde à tous les caractères spécifiques.

Expressions Régulières Pegex en plus de détail

Ensuite, nous avons la définition d'une chaîne JSON :

# string et number sont des interprétations de http://www.json.org/
string: /
    DOUBLE
        (
            (:
                BACK (:       # Échappements par barre oblique inverse
                    [
                        DOUBLE      # Guillemet double
                        BACK        # Barre oblique inverse
                        SLASH       # Barre oblique
                        b           # Retour arrière
                        f           # Saut de page
                        n           # Nouvelle ligne
                        r           # Retour chariot
                        t           # Tabulation horizontale
                    ]
                |
                    u HEX{4}        # Paire d'octets Unicode
                )
            |
                [^ DOUBLE CONTROLS ]  # Tout le reste
            )*
        )
    DOUBLE
/

que Pegex compile en cette expression régulière (simple et évidente ;) :

/"((?:\\(?:["\\/bfnrt]|u[0-9a-fA-F]{4})|[^"\x00-\x1f])*)"/

Voyons ce qu'il y a de nouveau ici...

Tout d'abord, nous avons beaucoup d'espaces blancs et de commentaires. Cela devrait rendre assez facile d'avoir au moins une idée générale de ce qui est accompli.

Comprendre comment le texte entre une paire de caractères '/' est transformé en une vraie expression régulière est la clé pour vraiment comprendre Pegex.

Remarquez le '*', le '{4}', le '|', le '(...)', et le '^...'. Toute cette ponctuation est transmise telle quelle dans l'expression régulière compilée. Il n'y a que quelques exceptions. Couvrons-les en détail.

Tout ce qui se trouve à l'intérieur de "<quelque_référence_de_règle>" est remplacé par l'expression régulière à laquelle la référence pointe. Les références de règles à l'intérieur d'une expression régulière doivent pointer directement vers une autre référence, bien que ces règles puissent pointer vers encore plus de parties d'expression régulière.

Les caractères "-" sont remplacés par 'ws1', qui est ensuite remplacé par sa définition de règle. "+" est remplacé par "ws2" (qui se résout par défaut en "\s+").

Enfin, '(:' est remplacé par '(?:)'. C'est simplement pour rendre votre syntaxe de parenthèses non capturantes un peu plus jolie. En général, vous pouvez omettre '?' après un '(' et Pegex les ajoutera pour vous.

C'est tout. Tout le reste que vous mettez entre des barres obliques ira tel quel dans l'expression régulière.

Dans un certain sens, Pegex est juste une façon très bien organisée d'écrire un analyseur à partir d'expressions régulières. Pour être vraiment bon en Pegex, il faut une compréhension assez solide du fonctionnement des expressions régulières, mais étant donné que les expressions régulières sont si courantes, Pegex rend la tâche de les transformer en analyseur assez simple.

Capture de données

La prochaine chose à couvrir est la capture d'expressions régulières. Lorsque vous analysez des données, il est généralement important d'extraire certains morceaux de texte afin de pouvoir faire quelque chose avec eux.

Pegex a une seule façon très simple, directe et évidente de faire cela : toute parenthèse de capture dans n'importe quelle expression régulière capturera des données et les transmettra à l'objet receveur. Puisque Pegex est basé sur des expressions régulières, cela a du sens.

Nous parlerons des objets receveurs dans la section suivante. Pour l'instant, sachez simplement qu'un objet receveur est ce qui crée quelque chose à partir des données et des événements trouvés lors d'une analyse. Dans notre cas JSON ici, notre receveur créera une structure de données Perl qui correspond au JSON que nous analysons. Évident !

Dans la règle pour 'string' ci-dessus, nous capturons les caractères entre les guillemets doubles. Ce sont les données brutes qui seront transformées en un scalaire Perl.

Finaliser la grammaire JSON

Il ne reste que 5 règles simples nécessaires pour compléter la grammaire JSON Pegex :

number: /(
    DASH?
    (: 0 | [1-9] DIGIT* )
    (: DOT DIGIT* )?
    (: [eE] [ DASH PLUS ]? DIGIT+ )?
)/
boolean: true | false
true: /true/
false: /false/
null: /null/

Notez que la règle pour 'number' capture des données, mais les autres règles ne le font pas. C'est parce que tant que le receveur sait qu'une règle 'null' a été trouvée, il peut la transformer en un "undef" Perl. L'important n'est pas le texte correspondant réel (même si dans ce cas, il doit être exactement la chaîne 'null').

Pegex::JSON::Grammar - La classe de grammaire Pegex

La grammaire JSON Pegex que nous venons d'examiner en détail excrémentiel est compilée en une structure de données Perl puis intégrée dans une classe de grammaire. Un objet Pegex::Parser (ce qui fait l'analyse) nécessite un objet grammaire (ce qu'il faut chercher) et un objet receveur (ce qu'il faut faire quand on le trouve).

Il convient de noter que Pegex utilise Pegex pour analyser les grammaires Pegex. C'est-à-dire que cette grammaire : https://github.com/ingydotnet/pegex-pgx/blob/master/pegex.pgx est utilisée par Pegex pour analyser notre grammaire json.pgx (et oui, elle peut aussi analyser pegex.pgx).

On peut concevoir que chaque fois que nous voudrions analyser du JSON, nous pourrions d'abord analyser la grammaire json.pgx, mais ce serait une perte de temps. Nous mettons donc en cache le grand arbre de grammaire sous forme de structure de données Perl pure à l'intérieur de Pegex::JSON::Grammar.

Si pour une raison quelconque nous avions besoin de changer json.pgx, nous devrions la recompiler en Perl et la copier/coller dans notre module. Ce serait une corvée, il y a donc une commande spéciale pour le faire pour nous. Exécutez simplement ceci :

perl -Ilib -MPegex::JSON:Grammar=compile

Si vous êtes en mode développement intensif et que vous changez fréquemment la grammaire, vous pouvez simplement définir une variable d'environnement comme ceci :

export PERL_PEGEX_AUTO_COMPILE=Pegex::JSON::Grammar

et la recompilation se fera automatiquement. Ceci est possible grâce à cette ligne dans le module de grammaire :

use constant file => '../json-pgx/json.pgx';

Cette ligne n'est utilisée que pendant le développement et nécessite que le fichier de grammaire se trouve à cet endroit.
