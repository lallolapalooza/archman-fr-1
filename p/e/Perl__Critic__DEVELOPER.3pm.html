Perl::Critic::DEVELOPER(3pm) Documentation Perl contribuée Perl::Critic::DEVELOPER(3pm)

NOM

Perl::Critic::DEVELOPER - Comment écrire des modules Perl::Critic::Policy pour les développeurs.

DESCRIPTION

Pour les développeurs souhaitant créer des normes de codage personnalisées, ce qui suit explique comment écrire un module de Policy pour Perl::Critic. Bien que la distribution Perl::Critic inclue déjà plusieurs Policies basées sur les livres de Damian Conway, Perl Best Practices (qui seront référencés ici comme "PBP"), Perl::Critic ne se limite pas à ses guides et peut être utilisé pour faire respecter toutes les pratiques, préférences ou styles que vous souhaitez suivre. Vous pouvez même écrire des Policies pour faire respecter des guides contradictoires. La seule chose que vous avez à faire est d'écrire un module Perl::Critic::Policy correspondant, qui peut nécessiter aussi peu que 10 lignes de code.

CONTEXTE

Le cœur de Perl::Critic est PPI, un analyseur syntaxique et un lexer pour Perl. PPI transforme le code source Perl en un Modèle Objet Document (DOM). Chaque jeton dans le document est représenté par une classe PPI, telle que PPI::Token::Operator ou PPI::Token::Word, puis ils sont organisés en classes structurelles, telles que PPI::Statement::Expression et PPI::Structure::Subroutine. La racine de la hiérarchie est le nœud PPI::Document.

Le moteur Perl::Critic parcourt chaque nœud de l'arbre PPI::Document et appelle chaque classe Perl::Critic::Policy sur le nœud approprié. Le Policy peut inspecter le nœud, regarder les nœuds environnants et faire ce qu'il veut. Si le Policy décide qu'une norme de codage a été violée, il renvoie un ou plusieurs objets Perl::Critic::Violation. S'il n'y a pas de violations, il ne renvoie rien.

Les Policies sont souvent écrits sur la base de Policies existants, examinons donc un exemple pour voir comment cela fonctionne. Le Policy RequireBlockGrep.pm est relativement simple et illustre la plupart des problèmes importants. L'objectif de ce Policy est de faire en sorte que chaque appel à "grep" utilise un bloc comme premier argument et non une expression. Les raisons de ce Policy sont discutées en détail dans PBP.

EXEMPLE DE POLICY

Premièrement, le module de Policy doit avoir un nom. Perl::Critic utilise Module::Pluggable pour découvrir automatiquement tous les modules dans l'espace de noms "Perl::Critic::Policy". Nous avons également adopté la convention de regrouper les Policies dans des répertoires en fonction des chapitres de PBP. Étant donné que l'objectif de ce Policy est de faire respecter l'utilisation d'arguments de bloc pour "grep" et qu'il provient de la section "Fonctions intégrées" de PBP, nous nommons ce Policy "Perl::Critic::Policy::BuiltinFunctions::RequireBlockGrep".

package Perl::Critic::Policy::BuiltinFunctions::RequireBlockGrep;

Ensuite, nous définissons quelques pragmas et chargeons les modules dont nous avons besoin. Tous les modules de Policy héritent de la classe Perl::Critic::Policy, qui fournit des implémentations vides des méthodes de base. Notre tâche consiste à redéfinir ces méthodes pour qu'elles fassent quelque chose d'utile.

Techniquement, "use strict;" et "use warnings;" sont facultatifs, mais nous ne voulons pas que Perl::Critic soit hypocrite, n'est-ce pas ?.

use strict;
use warnings;
use Readonly;
use Perl::Critic::Utils qw{ :severities :classification :ppi };
use parent 'Perl::Critic::Policy';
our $VERSION = '1.05';

Ensuite, nous déclarons une description et une explication pour ce Policy. La description est toujours une chaîne de caractères qui dit essentiellement "voici ce qui ne va pas." L'explication peut être une chaîne de caractères avec plus de détails, ou une référence à un tableau d'entiers correspondant aux numéros de page dans PBP. Nous les rendons read-only car ils ne changent jamais. (Voir Perl::Critic::Policy::ValuesAndExpressions::ProhibitConstantPragma pour la raison pour laquelle nous n'utilisons pas "use constant".)

Readonly::Scalar my $DESC => q{Forme d'expression de "grep"};
Readonly::Scalar my $EXPL => [ 169 ];

La plupart des Policies courantes n'ont pas besoin de redéfinir la méthode initialize_if_enabled() fournie par Perl::Critic::Policy. Cependant, si votre Policy est configurable via .perlcriticrc, vous devez implémenter la méthode supported_parameters() et vous devez implémenter initialize_if_enabled() pour examiner la valeur de $config. Comme ce Policy n'est pas configurable, nous le déclarons en implémentant supported_parameters() qui renvoie une liste vide.

sub supported_parameters { return ()                  }

Ensuite, nous définissons la méthode default_severity(), qui doit renvoyer un entier indiquant la gravité de la violation de ce Policy. Les valeurs de gravité vont de 1 à 5, 5 étant le "plus grave". En général, le niveau 5 est réservé aux choses qui sont souvent mal utilisées et/ou qui causent des erreurs. Le niveau 1 est pour les choses très subjectives ou simplement esthétiques. Le paquet Perl::Critic::Utils exporte plusieurs constantes de gravité que vous pouvez utiliser ici via le tag ":severities".

sub default_severity     { return $SEVERITY_HIGH      }

De même, la méthode default_themes() renvoie une liste de noms de thèmes. Les thèmes sont intentionnellement des groupes de Policies. Tous les Policies livrés avec Perl::Critic ont un thème "core". Étant donné que l'utilisation de "grep" sans blocs cause souvent des erreurs, nous incluons un thème "bugs". Et comme ce Policy provient directement de PBP, ce Policy devrait appartenir au thème "pbp".

sub default_themes       { return qw( core bugs pbp ) }

En tant qu'auteur de Policy, vous pouvez attribuer n'importe quel thème à votre Policy. Si vous publiez une suite de Policies personnalisées, nous vous recommandons de créer un thème unique qui couvre tous les Policies de la distribution. De cette façon, les utilisateurs peuvent facilement activer ou désactiver tous vos Policies en même temps. Par exemple, tous les Policies de la distribution Perl::Critic::More ont un thème "more".

Ensuite, nous spécifions quels éléments de code ce Policy analysera, tels que des déclarations, des variables, des conditions ou des POD. Ces éléments sont spécifiés comme des classes PPI, telles que PPI::Statement, PPI::Token::Symbol, PPI::Structure::Conditional ou PPI::Token::Pod respectivement. La méthode applies_to() renvoie une liste de noms de packages PPI. (Vous pouvez obtenir cette liste de packages disponibles via "perldoc PPI".) Lorsque Perl::Critic parcourt le document, il appellera la méthode violates() de ce module lorsqu'il rencontrera l'un des types de PPI donnés ici. Dans ce cas, nous voulons seulement tester les appels à "grep". Comme le jeton "grep" est une classe PPI::Token::Word, nous renvoyons ce nom de package depuis la méthode applies_to().

sub applies_to           { return 'PPI::Token::Word'  }

Si votre Policy doit analyser plusieurs types d'éléments distincts, la méthode applies_to() peut renvoyer le nom de plusieurs packages PPI. Si votre Policy doit examiner le fichier dans son intégralité, alors la méthode applies_to() devrait renvoyer PPI::Document. Comme il n'y a qu'un seul élément PPI::Document disponible, votre Policy serait appelé une fois par fichier.

Vient maintenant la partie intéressante. La méthode violates() effectue tout le travail. Elle est toujours appelée avec deux arguments : une référence à l'élément PPI actuel que Perl::Critic parcourt, et une référence au document PPI complet. [Et comme c'est une méthode d'objet, il y aura un argument supplémentaire qui est une référence à cet objet ($self), mais vous le saviez déjà !]. Comme ce Policy n'a pas besoin d'accéder à l'ensemble du document, nous ignorons le dernier argument en l'assignant à "undef".

sub violates {
    my ( $self, $elem, undef ) = @_;

La méthode violates() effectue ensuite quelques tests pour s'assurer que nous avons le bon type d'élément. Dans notre exemple, nous savons que l'élément sera un PPI::Token::Word car c'est ce que nous avons spécifié dans la méthode applies_to(). Cependant, nous n'avons pas spécifié exactement quel "mot" nous recherchions. Évaluer un élément PPI dans un contexte de chaîne renvoie la forme littérale du code. (Vous pouvez également utiliser la méthode content().) Nous écrivons donc :

sub violates {
    my ( $self, $elem, undef ) = @_;

POLICY IMPLEMENTATION

This section delves into the practicalities of implementing a Perl::Critic Policy. We'll continue with the example of a Policy that requires the block form of the C<grep> function.

The violates() Method

The heart of any Policy is the violates() method. This method is called by Perl::Critic for every element in the document that matches the element types that the Policy is interested in. The method receives the element as its only argument.

    sub violates {
        my ( $self, $elem ) = @_;

The first thing that we must do is to ensure that the element is actually a call to the function we are interested in. If the element is not a call to "grep", then we don't need to do anything more. We can just return.

To start, we make sure that this element is, in fact, "grep". If it's not, then we don't need to bother examining it.

return if $elem ne 'grep';

The "PPI::Token::Word" class is also used for barewords and methods called on object references. It is possible for someone to declare a bareword hash key as "%hash = ( grep => 'foo')". We don't want to test those types of elements because they don't represent function calls to "grep". So we use one of handy utility functions from Perl::Critic::Utils to make sure that this "grep" is actually in the right context. (The is_function_call() subroutine is brought in via the ":classification" tag.)

return if ! is_function_call($elem);

Now that we know this element is a call to the "grep" function, we can look at the nearby elements to see what kind of arguments are being passed to it. In the following paragraphs, we discuss how to do this manually in order to explore PPI; after that, we'll show how this Policy actually uses facilities provided by Perl::Critic::Utils to get this done.

Every PPI element is linked to its siblings, parent, and children (if it has any). Since those siblings could just be whitespace, we use the snext_sibling() to get the next code-sibling (the "s" in "snext_sibling" stands for "significant").

my $sib = $elem->snext_sibling() or return;

In Perl, the parenthesis around argument lists are usually optional, and PPI packs the elements into a PPI::Structure::List object when parentheses are used. So if the sibling is a "PPI::Structure::List", we pull out the first (significant) child of that list. This child will be the first argument to "grep". If parentheses were not used, then the sibling itself is the first argument.

my $arg = $sib->isa('PPI::Structure::List') ? $sib->schild(0) : $sib;

In actuality, this sort of function argument lookup is common, so there is a "first_arg" in Perl::Critic::Utils subroutine available via the ":ppi" tag. So we use that instead.

my $arg = first_arg($elem);

Finally, we now have a reference to the first argument to "grep". If that argument is a block (i.e. something in curly braces), then it will be a PPI::Structure::Block, in which case our Policy is satisfied and we just return nothing.

return if !$arg;
return if $arg->isa('PPI::Structure::Block');

But if it is not a PPI::Structure::Block, then we know that this call to "grep" must be using the expression form, and that violates our Policy. So we create and return a new Perl::Critic::Violation object via the "violation" in Perl::Critic::Policy method, passing in the description, explanation, and a reference to the PPI element that caused the violation. And that's all there is to it!

    return $self->violation( $DESC, $EXPL, $elem );
}
1;

One last thing -- people are going to need to understand what is wrong with the code when your Policy finds a problem. It isn't reasonable to include all the details in your violation description or explanation. So please include a DESCRIPTION section in the POD for your Policy. It should succinctly describe the behavior and motivation for your Policy and include a few examples of both good and bad code. Here's an example:

=pod
=head1 NAME
Perl::Critic::Policy::BuiltinFunctions::RequireBlockGrep
=head1 DESCRIPTION
The expression forms of C<grep> and C<map> are awkward and hard to read.
Use the block forms instead.
    @matches = grep  /pattern/,    @list;        #not ok
    @matches = grep { /pattern/ }  @list;        #ok
    @mapped = map  transform($_),    @list;      #not ok
    @mapped = map { transform($_) }  @list;      #ok
=cut

When your policy has a section like this, users can invoke perlcritic with a "--verbose" parameter of 10 or 11 or with a "%d" escape to see it along with the rest of the output for violations of your policy.

MAKING YOUR POLICY CONFIGURABLE

Perl::Critic takes care of gathering configuration information for your Policy, from whatever source the user specifies. (See "CONFIGURATION" in Perl::Critic for the details of how a user specifies the values you're going to receive.) What your Policy ends up receiving for the value of a parameter is a string with leading and trailing whitespace removed. By default, you will need to handle conversion of that string to a useful form yourself. However, if you provide some metadata about your parameters, the parameter handling will be taken care of for you. (Additionally, tools that deal with Policies themselves can use this information to enhance their functionality. See the perlcritic "--profile-proto" option for an example.)

You can look at Perl::Critic::Policy::ControlStructures::ProhibitCascadingIfElse for a simple example of a configurable Policy and Perl::Critic::Policy::Documentation::RequirePodSections for a more complex one.

Do It All Yourself

The initialize_if_enabled() method for a Policy receives one argument: an instance of Perl::Critic::PolicyConfig. This method is only called if the user's configuration has enabled the policy. It returns a boolean stating whether the Policy should continue to be enabled. Generally, the only reason to return $FALSE is when some external requirement is missing. For example, Perl::Critic::Policy::CodeLayout::RequireTidyCode used to disable itself if Perl::Tidy was not installed (that is until we made it no longer optional for the Perl-Critic distribution).

A basic, do-nothing implementation of initialize_if_enabled() would be:

use Perl::Critic::Utils qw< :booleans >;
...
sub initialize_if_enabled {
    my ( $self, $config ) = @_;
    return $TRUE;
}

As stated above, what you get in $config are trimmed strings. For example, if the user's .perlcritic contains

[Your::Policy]
foo          = bar baz
factor   =     5.52
selections =   2 78 92

then $config will contain the equivalent of

my $config = {
    foo        => 'bar baz',
    factor     => '5.52',
    selections => '2 78 92',
};

To make this available to the violates() method, the values are usually put into $self under the name of the configuration item prefixed with an underscore. E.g.

sub initialize_if_enabled {
    my ( $self, $config ) = @_;
    $self->{_foo} = $config->get{foo};
    $self->{_factor} = $config->get{factor};
    $self->{_selections} = $config->get{selections};
    return $TRUE;
}

Often, you'll want to convert the configuration values into something more useful. In this example, "selections" is supposed to be a list of integers. Perl::Critic::Utils contains a number of functions that can help you with this. Assuming that violates() wants to have "selections" as an array, you'll want to have something like this:

use Perl::Critic::Utils qw{ :booleans :characters :data_conversion };
sub initialize_if_enabled {
    my ( $self, $config ) = @_;
    $self->{_foo} = $config->get{foo};
    $self->{_factor} = $config->get{factor};
    my $selections = $config->get{selections} // $EMPTY_STRING;
    $self->{_selections} = [ words_from_string($selections) ];
    return $TRUE;
}

Since "selections" contains numbers, it may be desirable to change the assignment to look like

$self->{_selections} = [ map { $_ + 0 } words_from_string($selections) ];

If violates() needs to quickly determine whether a particular value is in "selections", you would want to use a hash instead of an array, like this:

$self->{_selections} = { hashify( words_from_string($selections) ) };

For an example of a Policy that has some simple, but non-standard configuration handling, see Perl::Critic::Policy::CodeLayout::RequireTidyCode.

Note On Constructors

It used to be the case that Policies handled configuration by implementing a constructor. However, there was no requirement to call the base constructor; as long as the Policy ended up being a blessed hash reference, everything was fine. Unfortunately, this meant that Policies would be loaded and their prerequisites would be "use"d, even if the Policy wasn't enabled, slowing things down. Also, this severely restricted the core of Perl::Critic's ability to enhance things. Use of constructors is deprecated and is incompatible with supported_parameters() metadata below. Kindly use initialize_if_enabled(), instead, to do any sort of set up that you need.

Providing Basic Configuration Information Via supported_parameters()

As minimum for a well behaved Policy, you should implement supported_parameters() in order to tell the rest of "Perl::Critic" what configuration values the Policy looks for, even if it is only to say that the Policy is not configurable. In the simple form, this function returns a list of the names of the parameters the Policy supports. So, for a non-configurable Policy, as in the "RequireBlockGrep" example above, this looked like

sub supported_parameters { return ()                  }

For the example being used in the initialize_if_enabled() section above, this would be

sub supported_parameters { return qw< foo factor selections >; }

Given this information, "Perl::Critic" can tell the user when they have specified a parameter for a Policy which isn't valid, e.g. when they've misspelled the name of the parameter

, et peut émettre le paramètre dans le cadre d'un prototype .perlcriticrc.

Vous pouvez fournir encore plus d'informations sur la configuration de votre stratégie en donnant à chaque paramètre une description et une représentation textuelle de la valeur par défaut pour ce paramètre. Vous le faites en faisant en sorte que les valeurs de la liste retournée par supported_parameters() soient des références de hachage au lieu de chaînes de caractères, avec les clés "name", "description" et "default_string". Par exemple,

sub supported_parameters {
    return (
        {
            name           => 'allowed_values',
            description    =>
                'Valeurs individuelles et plages de valeurs autorisées, et/ou « all_integers ».',
            default_string => '0 1 2',
        },
        {
            name           => 'allowed_types',
            description    => 'Type de littéraux autorisés.',
            default_string => 'Float',
        },
    );
}

Notez que l'utilisation de constructeurs est incompatible avec la spécification de paramètres de cette manière.

Utilisation de supported_parameters() pour obtenir le résultat

La discussion ci-dessus sur supported_parameters() a montré comment vous pouviez aider les autres avec votre stratégie, mais n'a rien fait pour vous faciliter la vie en tant qu'auteur de stratégie ; vous devez toujours implémenter initialize_if_enabled() pour accéder à toute configuration que l'utilisateur a spécifiée. Pour que la configuration soit gérée automatiquement pour vous, vous devez déclarer comment vos paramètres agissent en spécifiant une valeur pour leur "behavior". Par exemple, ce qui suit déclare qu'un paramètre permet à l'utilisateur de choisir parmi cinq valeurs spécifiques et que l'utilisateur peut en sélectionner n'importe quelle combinaison :

sub supported_parameters {
    return (
        {
            name           => 'allowed_types',
            description    => 'Type de littéraux autorisés.',
            default_string => 'Float',
            behavior       => 'enumeration',
            enumeration_values => [ qw{ Binary Exp Float Hex Octal } ],
            enumeration_allow_multiple_values => 1,
        },
    );
}

Lorsque vous spécifiez un comportement, l'analyse et la validation des valeurs spécifiées par l'utilisateur et par défaut sont effectuées pour vous, et votre méthode violates() peut récupérer la valeur sous la clé du nom du paramètre précédée d'un trait de soulignement, par exemple, pour la déclaration ci-dessus, la valeur analysée et validée est accessible via "$self->{_allowed_types}".

Les comportements fournissent une fonctionnalité supplémentaire à "Perl::Critic" ; pour en savoir plus à ce sujet, voir Perl::Critic::PolicyParameter et Perl::Critic::PolicyParameter::Behavior.

Ce qui suit discute de chacun des comportements pris en charge et des options qu'ils prennent en charge. Pour connaître tous les détails d'un comportement, consultez la documentation de la classe d'implémentation.

"string"

Implémenté dans Perl::Critic::PolicyParameter::Behavior::String.

Le plus basique des comportements, la valeur du paramètre sera stockée dans la Stratégie sous forme de chaîne de caractères.

Ce comportement n'est pas configurable.

Exemple de supported_parameters()

sub supported_parameters {
    return (
        {
            name           => 'a_string',
            description    => 'Un exemple de chaîne.',
            default_string => 'blah blah blah',
            behavior       => 'string',
        },
    );
}

Exemple d'accès

sub violates {
    my ($self, $element, $document) = @_;
    ...
    my $string = $self->{_a_string};
    ...
}

"boolean"

Implémenté dans Perl::Critic::PolicyParameter::Behavior::Boolean.

La valeur du paramètre sera soit $TRUE soit $FALSE.

Ce comportement n'est pas configurable.

Exemple de supported_parameters()

sub supported_parameters {
    return (
        {
            name           => 'a_boolean',
            description    => 'Un exemple booléen.',
            default_string => '1',
            behavior       => 'boolean',
        },
    );
}

Exemple d'accès

sub violates {
    my ($self, $element, $document) = @_;
    ...
    my $is_whatever = $self->{_a_boolean};
    if ($is_whatever) {
        ...
    }
    ...
}

"integer"

Implémenté dans Perl::Critic::PolicyParameter::Behavior::Integer.

La valeur est validée par rapport à "m/ \A [-+]? [1-9] [\d_]* \z /xms" (avec une vérification spéciale pour « 0 »). Notez que cela signifie que les traits de soulignement sont autorisés dans les valeurs d'entrée, comme avec les littéraux numériques Perl.

Cela prend deux options, "integer_minimum" et "integer_maximum", qui spécifient les bornes d'une plage inclusive pour restreindre la valeur. L'une, aucune, ou les deux peuvent être spécifiées.

Exemple de supported_parameters()

sub supported_parameters {
    return (
        {
            name            => 'an_integer',
            description     => 'Un exemple d\'entier.',
            default_string  => '5',
            behavior        => 'integer',
            integer_minimum => 0,
            integer_maximum => 10,
        },
    );
}

Exemple d'accès

sub violates {
    my ($self, $element, $document) = @_;
    ...
    my $integer = $self->{_an_integer};
    if ($integer > $TURNING_POINT) {
        ...
    }
    ...
}

"string list"

Implémenté dans Perl::Critic::PolicyParameter::Behavior::StringList.

Les valeurs seront dérivées en divisant la chaîne d'entrée sur les espaces. (Voir « words_from_string » dans Perl::Critic::Utils.) Le paramètre sera stocké sous forme de référence à un hachage, les valeurs étant les clés.

Cela prend une option facultative, "list_always_present_values", d'une référence à un tableau de chaînes qui seront toujours incluses dans la valeur du paramètre, par exemple si la valeur de cette option est "[ qw{ a b c } ]" et que l'utilisateur spécifie une valeur de 'c d e', alors la valeur du paramètre contiendra 'a', 'b', 'c', 'd', et 'e'.

Exemple de supported_parameters()

sub supported_parameters {
    return (
        {
            name                  => 'a_string_list',
            description           => 'Un exemple de liste.',
            default_string        => 'red pink blue',
            behavior              => 'string list',
            list_always_present_values => [ qw{ green purple} ],
        },
    );
}

Exemple d'accès

sub violates {
    my ($self, $element, $document) = @_;
    ...
    my $list = $self->{_a_string_list};
    my @list = keys %{$list};
    ...
    return if not $list->{ $element->content() };
    ...
}

"enumeration"

Implémenté dans Perl::Critic::PolicyParameter::Behavior::Enumeration.

Les valeurs seront dérivées en divisant la chaîne d'entrée sur les espaces. (Voir « words_from_string » dans Perl::Critic::Utils.) Selon la valeur de l'option "enumeration_allow_multiple_values", le paramètre sera stocké sous forme de chaîne de caractères ou de référence à un hachage, les valeurs étant les clés.

Ce comportement prend une option requise et une optionnelle. Une valeur pour "enumeration_values", une référence à un tableau de chaînes valides, est requise. Une valeur vraie peut être spécifiée pour "enumeration_allow_multiple_values" pour permettre à l'utilisateur de choisir plusieurs valeurs, mais cela est désactivé par défaut.

Exemple de supported_parameters()

use Perl::Critic::Utils qw{ :characters };
sub supported_parameters {
    return (
        {
            name               => 'a_single_valued_enumeration',
            description        =>
                'Un exemple d\'énumération qui ne peut avoir qu\'une seule valeur.',
            default_string     => $EMPTY,
            behavior           => 'enumeration',
            enumeration_values => [ qw{ block statement pod operator } ],
            enumeration_allow_multiple_values => 0,
        },
        {
            name               => 'a_multi_valued_enumeration',
            description        =>
                'Un exemple d\'énumération qui peut avoir plusieurs valeurs.',
            default_string     => 'fe',
            behavior           => 'enumeration',
            enumeration_values => [ qw{ fe fi fo fum } ],
            enumeration_allow_multiple_values => 1,
        },
    );
}

Exemple d'accès

sub violates {
    my ($self, $element, $document) = @_;
    ...
    my $single_value = $self->{_a_single_valued_enumeration};
    ...
    my $multi_value = $self->{_a_multi_valued_enumeration};
    if ( $multi_value->{fum} ) {
        ...
    }
    ...
}

Utilisation d'un analyseur personnalisé

Si aucun des comportements ne fait exactement ce que vous voulez, vous pouvez fournir votre propre analyseur pour un paramètre. La raison de le faire par opposition à l'utilisation d'une implémentation de initialize_if_enabled() est qu'elle vous permet d'utiliser un comportement pour fournir sa fonctionnalité supplémentaire et qu'elle fournit un moyen pour un programme de configuration "Perl::Critic", par exemple un IDE qui intègre "Perl::Critic", de valider votre paramètre pendant que l'utilisateur modifie sa valeur.

La manière de déclarer que vous avez un analyseur personnalisé est d'inclure une référence à celui-ci dans la spécification du paramètre avec la clé "parser". Par exemple :

sub supported_parameters {
    return (
        {
            name           => 'file_name',
            description    => 'Un fichier pour lire une liste de valeurs.',
            default_string => undef,
            behavior       => 'string',
            parser         => \&_parse_file_name,
        },
    );
}

Un analyseur est une méthode sur une sous-classe de Perl::Critic::Policy qui prend deux paramètres : le Perl::Critic::PolicyParameter qui est spécifié et la chaîne de valeur fournie par l'utilisateur. La méthode est responsable de la gestion de toute valeur par défaut et de la sauvegarde de la valeur analysée pour une utilisation ultérieure par le

CONFIGURATION

supported_parameters()

To add configuration options to your Policy, you must override the supported_parameters() method. This method should return a reference to an array of hash references. Each hash reference represents a single configuration parameter that your Policy supports.

The keys in each hash reference are as follows:

- "name" (mandatory)
The name of the parameter. This is the name that the user will use in their .perlcriticrc file.
- "description" (optional)
A description of the parameter. This will be used when generating documentation for the Policy.
- "behavior" (optional)
The type of the parameter. Supported values are:
"boolean"
"enumeration"
"integer"
"string"
"string list"

If this is omitted, the parameter will be treated as a "string".

- "default_string" (optional)
A string representation of the default value of the parameter. This will be used if the user does not provide a value for the parameter.
- "parser" (optional)
A code reference to a custom parser for the parameter. This will be called with the string value of the parameter and should return the parsed value. If this is not provided, a default parser will be used based on the "behavior".

Additional keys are available for specific behaviors:

Enumerations

- "enumeration_values" (mandatory for "enumeration")
A reference to an array of strings that are the only valid values for the parameter.
- "enumeration_allow_multiple_values" (optional)
A boolean value indicating whether or not the user is allowed to provide multiple values for the parameter (separated by commas).

Integers

- "integer_minimum" (optional)
The minimum allowed value for the parameter, inclusive.
- "integer_maximum" (optional)
The maximum allowed value for the parameter, inclusive.

String lists

- "list_always_present_values" (optional)
A reference to an array of values that should always be included in the parameter's value, even if the user doesn't provide them. This is useful for ensuring that certain required elements are always present.

An example implementation:

sub supported_parameters {
    return [
        {
            name        => 'ignore_unless_condition',
            description => 'Whether to ignore unless condition is met',
            behavior    => 'boolean',
            default_string => '0',
        },
        {
            name        => 'severity_threshold',
            description => 'Minimum severity to report',
            behavior    => 'integer',
            integer_minimum => 1,
            integer_maximum => 5,
            default_string => '3',
        },
        {
            name        => 'allowed_protocols',
            description => 'Which protocols are allowed',
            behavior    => 'enumeration',
            enumeration_values => [ 'http', 'https', 'ftp' ],
            enumeration_allow_multiple_values => 1,
            default_string => 'http, https',
        },
        {
            name        => 'exclude_files',
            description => 'List of files to exclude',
            behavior    => 'string list',
            list_always_present_values => [ 'lib/auto/*' ],
        },
    ];
}

initialize_if_enabled()

Once the parameters have been parsed and validated, the initialize_if_enabled() method is called. This method is intended for any additional initialization that your Policy may need. The parsed parameter values are available via accessor methods on the Policy object itself (e.g. $self->ignore_unless_condition()). The original configuration string is also available via the $config parameter, though it is not generally recommended to use it.

Note that if the parameter value is invalid, an exception of type Perl::Critic::Exception::Configuration::Option::Policy::ParameterValue will be thrown. This allows Perl::Critic to collect all configuration errors into a single message. The parser for the parameter value will be responsible for calling the appropriate constructor for this exception type if the value is not valid. The example parser below shows how to use throw_policy_value().

An example parser (without enough error handling) for the above example declaration:

use Path::Tiny;
use Perl::Critic::Exception::Configuration::Option::Policy::ParameterValue
    qw{ throw_policy_value };
sub _parse_file_name {
    my ($self, $parameter, $config_string) = @_;
    my @thingies;
    if ($config_string) {
        if (not -r $config_string) {
            throw_policy_value
                policy         => $self->get_short_name(),
                option_name    => $parameter->get_name(),
                option_value   => $config_string,
                message_suffix => 'is not readable.';
        }
        @thingies = path($config_string)->slurp;
    }
    $self->{_thingies} = \@thingies;
    return;
}

Note that, if the value for the parameter is not valid, an instance of Perl::Critic::Exception::Configuration::Option::Policy::ParameterValue is thrown. This allows "Perl::Critic" to include that problem along with any other problems found with the user's configuration in a single error message.

Using Both supported_parameters() and initialize_if_enabled()

There are cases where a Policy needs additional initialization beyond configuration or where the way it acts depends upon the combination of multiple parameters. In such situations, you will need to create an implementation of initialize_if_enabled(). If you want to take advantage of the supplied parameter handling from within implementation of initialize_if_enabled(), note that the information from supported_parameters() will already have been used, with user-supplied parameter values validated and placed into the Policy by the time initialize_if_enabled() has been called. It is likely that you will not need to refer the contents of the $config parameter; just pull the information you need out of $self. In fact, any value for the parameter values will be gone.

ADDITIONAL FEATURES

default_maximum_violations_per_document()

Certain problems that a Policy detects can be endemic to a particular file; if there's one violation, there's likely to be many. A good example of this is Perl::Critic::Policy::TestingAndDebugging::RequireUseStrict; if there's one line before "use strict", there's a good chance that the entire file is missing "use strict". In such cases, it's not much help to the user to report every single violation. If you've got such a policy, you should override default_maximum_violations_per_document() method to provide a limit. The user can override this value with a value for "maximum_violations_per_document" in their .perlcriticrc.

See the source code for Perl::Critic::Policy::ValuesAndExpressions::ProhibitMagicNumbers and Perl::Critic::Policy::TestingAndDebugging::RequireUseWarnings for examples.

is_safe()

Most Perl::Critic Policies are purely static. In other words, they never compile or execute any of the source code that they analyze. However it is possible to write dynamic Policies that do compile or execute code, which may result in unsafe operations (see Perl::Critic::Dynamic for an example). So the is_safe() method is used to indicate whether a Policy can be trusted to not cause mischief. By default, is_safe() returns true. But if you are writing a Policy that will compile or execute any of the source code that it analyzes, then you should override the is_safe() method to return false.

DISTRIBUTING YOUR POLICIES

Create a Distribution

You need to come up with a name for your set of policies. Sets of add-on policies are generally named "Perl::Critic::something", e.g. Perl::Critic::More.

The module representing the distribution will not actually have any functionality; it's just documentation and a name for users to use when installing via CPAN/CPANPLUS. The important part is that this will include a list of the included policies, with descriptions of each.

A typical implementation will look like:

package Perl::Critic::Example;
use strict;
use warnings;
our $VERSION = '1.000000';
1; # Magic true value required at end of module
__END__
=head1 NAME
Perl::Critic::Example - Policies for Perl::Critic that act as an example.
=head1 AFFILIATION
This module has no functionality, but instead contains documentation
for this distribution and acts as a means of pulling other modules
into a bundle.  All of the Policy modules contained herein will have
an "AFFILIATION" section announcing their participation in this
grouping.
=head1 SYNOPSIS
Some L<Perl::Critic|Perl::Critic> policies that will help you keep your
code nice and compliant.
=head1 DESCRIPTION
The included policies are:
=over
=item L<Perl::Critic::Policy::Documentation::Example|Perl::Critic::Policy::Documentation::Example>
Complains about some example documentation issues.  [Default severity: 3]
=item L<Perl::Critic::Policy::Variables::Example|Perl::Critic::Policy::Variables::Example>
All modules must have at least one variable.  [Default severity: 3]
=back
=head1 CONFIGURATION AND ENVIRONMENT
All policies included are in the "example" theme.  See the
L<Perl::Critic|Perl::Critic> documentation for how to make use of this.

Themes

Users can choose which policies to enable using themes. You should implement default_themes() so that users can take advantage of this. In particular, you should use a theme named after your distribution in all your policies; this should match the value listed in the "CONFIGURATION AND ENVIRONMENT" POD section as shown above.

default_themes { return qw< example math > }

If you're looking for ideas of what themes to use, have a look at the output of "perlcritic --list-themes".

Documentation

AFFILIATION

Since all policies have to go somewhere under the "Perl::Critic::Policy::" namespace, it isn't always clear what distribution a policy came from when browsing through their documentation. For this reason, you should include an "AFFILIATION" section in the POD for all of your policies that state where the policy comes from. For example:

=head1 AFFILIATION
This policy is part of L<Perl::Critic::Example|Perl::Critic::Example>.

CONFIGURATION

In order to make it clear what can be done with a policy, you should always include a "CONFIGURATION" section in your POD, even if it's only to say:

=head1 CONFIGURATION
This Policy is not configurable except for the standard options.

TESTING YOUR POLICY

The Perl::Critic distribution also contains a framework for testing your Policy. See Perl::Critic::TestUtils for the details.

HINT

When you're trying to figure out what PPI is going to hand you for a chunk of code, there is a tools/ppidump program in the Perl::Critic distribution that will help you. For example, when developing the above RequireBlockGrep example, you might want to try

tools/ppidump '@matches = grep /pattern/, @list;'

and

tools/ppidump '@matches = grep { /pattern/ } @list;'

to see the differences between the two cases.

Alternatively, see the "ppi_dumper" documentation at http://search.cpan.org/dist/App-PPI-Dumper/script/ppi_dumper and the "PPI::Tester" documentation at http://search.cpan.org/dist/PPI-Tester/lib/PPI/Tester.pm.
