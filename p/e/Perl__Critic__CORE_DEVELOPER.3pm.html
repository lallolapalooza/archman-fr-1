Perl::Critic::CORE_DEVELOPER(3pm) Documentation des contributeurs de Perl Perl::Critic::CORE_DEVELOPER(3pm)

NOM

Perl::Critic::CORE_DEVELOPER - Outils pour travailler sur le noyau de Perl::Critic.

DESCRIPTION

Ce document est un recueil de notes pour ceux qui travaillent sur le noyau de Perl::Critic. Ces notes sont à considérer comme informatives, bien qu'elles ne puissent être considérées comme faisant autorité. Il est naturel que l'utilisateur de ce document termine le travail à sa propre discrétion en fonction du travail réel effectué. Caveat lector.

Devenir un développeur principal

Voici mes opinions sur la façon de commencer. Notez que les étapes ne sont pas numérotées car je ne suis pas sûr qu'il y ait un ordre clair. Les points précédés de deux étoiles proviennent de la liste de diffusion ; les points précédés d'une étoile sont mon opinion. Bien que j'aie parfois ressenti l'utilité de commenter les points à deux étoiles, juste pour tout rendre totalement confus.

* Si vous n'êtes pas sûr de vous, installez Perl::Critic, puis téléchargez le code source et explorez-le.

** Abonnez-vous à la liste de diffusion des développeurs. Il y a des instructions dans "EXTENDING THE CRITIC" de Perl::Critic. La liste des "commits" est également une bonne option.

** Si vous travaillez sur un problème GitHub, vous devez mettre à jour le ticket pour indiquer que vous y travaillez, afin d'éviter que d'autres ne répètent vos efforts.

* Personnellement, je mettrais à jour GitHub lorsque je serais raisonnablement sûr de pouvoir le résoudre, juste pour éviter de mettre à jour à nouveau GitHub une semaine ou deux plus tard en disant "oops, j'ai vu trop grand". Mais c'est mon opinion.

* Le développement nécessite d'utiliser Module::Build au lieu d'ExtUtils::MakeMaker. En d'autres termes,

$ perl Build.PL

* Vous devez exécuter les tests d'auteur en exécutant

$ ./Build authortest

(mais pas 'make authortest', ce qui est l'une des raisons pour lesquelles vous devriez commencer avec Build.PL au lieu de Makefile.PL). Ceux-ci devraient s'exécuter proprement avant que vous ne déclariez votre travail terminé. Mon conseil, bien que ce ne soit pas une obligation, est de ne pas vous en préoccuper tant que votre code n'est pas fonctionnel.

Modules requis pour authortest

L'authortest nécessite un nombre de modules plus important que ce qui est nécessaire pour exécuter "Perl::Critic". La liste dépend probablement de la version de "Perl::Critic" que vous testez, elle n'est donc pas considérée comme définitive. Vous avez besoin des modules suivants en plus de tous les modules optionnels de Perl::Critic :

Devel::EnforceEncapsulation
Perl::Critic::More
Test::Kwalitee
Test::Memory::Cycle
Test::Perl::Critic
Test::Pod
Test::Pod::Coverage
Test::Without::Module

Vous pouvez savoir quels sont les modules optionnels en regardant recommended_module_versions() dans inc/Perl/Critic/BuildUtilities.pm.

En l'absence de "Test::Memory::Cycle", les tests pertinents sont sautés. En l'absence des autres modules, les tests sont lancés avec une grande solennité. Bien sûr, dans les deux cas, ils ne s'exécutent pas, donc la différence est principalement esthétique.

Dans Perl 5.12 et versions ultérieures, Devel::Cycle 1.11 doit être patché pour gérer une "Regexp" comme objet de première classe en Perl. Voir https://rt.cpan.org/Public/Bug/Display.html?id=56681 pour plus de détails.

Ajouter un élément de configuration global

Perlcritic gère les éléments de configuration globaux et les options de ligne de commande de manière très similaire. Ces notes couvriront l'ajout d'un élément de configuration global et d'une option correspondante, portant le même nom. Ces notes ne peuvent pas couvrir l'implémentation de la fonctionnalité du nouvel élément, seulement les mécanismes pour l'introduire dans Perl::Critic.

Conventions de nommage

Tous les noms sont en minuscules, sauf les noms de constantes (le cas échéant), qui sont en majuscules. Lorsque un nom contient plusieurs mots, les tirets sont utilisés pour séparer les mots dans le nom de l'élément de configuration et dans l'option de ligne de commande, et les traits de soulignement dans les noms des accesseurs et des valeurs d'attributs, et dans les noms des constantes le cas échéant.

Par exemple, si l'on ajoute "nouvel élément", l'élément de configuration est "new-item", l'option de ligne de commande est "--new-item", les accesseurs sont new_item(), et la valeur de l'attribut sera stockée dans "$self->{_new_item}". S'il y a des constantes impliquées, leurs noms commenceront par "NEW_ITEM_". Ces noms seront utilisés dans la discussion suivante.

Implémentation

Plusieurs fichiers doivent être modifiés pour intégrer votre nouvel élément de configuration ou option de ligne de commande.

lib/Perl/Critic/Utils/Constants.pm

S'il y a des constantes gérées dans votre implémentation, vous les placez ici. Vous aurez peut-être au moins

$NEW_ITEM_DEFAULT

à définir. Toutes les constantes de votre nouvel élément doivent être exportées, et elles doivent être exportées non seulement individuellement, mais aussi avec la balise d'exportation

new_item

lib/Perl/Critic/Command.pm

Si votre nouvel élément est une option de ligne de commande, sa spécification Getopt::Long doit être définie dans _get_option_specification(). Si votre élément de configuration global n'a pas d'option correspondante, vous n'avez pas besoin de modifier ce fichier.

lib/Perl/Critic/OptionsProcessor.pm

Si votre nouvel élément est un élément de configuration global, vous devez ajouter le code pour le gérer ici. Spécifiquement :

Vous devez ajouter du code à la méthode _init() pour stocker la valeur de votre élément en tant que valeur d'attribut, avec une valeur par défaut si nécessaire. En utilisant notre convention de nommage, un élément univalué serait stocké comme suit :

$self->{_new_item} = delete $args{'new-item'} //
    $NEW_ITEM_DEFAULT;

Si l'élément a des synonymes (par exemple, 'color' et 'colour' signifiant la même chose), vous devez les vérifier tous. Si l'élément acceptait une liste de valeurs, celles-ci seraient analysées et stockées comme une référence à un tableau.

Vous devez également ajouter et documenter un accesseur pour votre nouvel élément. Cela ressemblerait à ceci :

sub new_item {
    my ($self) = @_;
    return $self->{_new_item};
}

Dans le cas d'éléments à valeurs multiples, l'accesseur doit retourner la référence du tableau, donc l'exemple ci-dessus fonctionne également dans ce cas.

Note : Il n'y a pas de validation ici — cette classe est simplement un pont entre le fichier physique .perlcriticrc et Perl::Critic::Config, où elle est exécutée.

Si votre nouvel élément n'a pas d'option de configuration globale correspondante, vous n'avez pas besoin de modifier ce fichier.

lib/Perl/Critic/Config.pm

Vous devez écrire une méthode _validate_and_store_new_item() pour valider et stocker la valeur du nouvel élément. La signature de cette méthode dépend des détails de votre nouvel élément, mais elle doit inclure au moins la valeur de l'élément, même si il n'y a pas d'option de configuration globale correspondante. Si des erreurs de validation sont possibles, vous aurez également besoin d'un objet d'erreurs pour ajouter l'exception de validation. Comme les détails varient, le mieux est probablement de trouver une méthode similaire à celle que vous souhaitez écrire, et de l'adapter. La méthode _validate_and_store_top() est un bon point de départ pour un élément à valeur unique. La valeur validée doit être stockée dans "$self->{_new_item}".

Vous devez appeler _validate_and_store_new_item() dans la méthode _init().

Vous devez écrire et documenter une méthode d'accès pour la valeur du nouvel élément. L'accesseur typique pour un élément univalué est

sub new_item {
    my ($self) = @_;
    return $self->{_new_item};
}

mais l'accesseur pour un élément à valeurs multiples doit retourner un tableau :

sub new_item {
    my ($self) = @_;
    return @{ $self->{_new_item} };
}
Récemment, vous devez documenter votre propre élément.
lib/Perl/Critic/ProfilePrototype.pm
Si le nouvel élément a un élément de configuration global correspondant, vous devez mettre à jour la méthode to_string() pour inclure l'élément dans la chaîne. Votre implémentation doit être telle que la chaîne générée soit la même que la chaîne d'entrée de l'élément, à l'exception de l'espace blanc.
Si le nouvel élément n'a pas d'élément de configuration global correspondant, vous n'avez pas besoin de modifier ce fichier.
bin/perlcriticrc
Si le nouvel élément a une option de commande correspondante, vous devez la documenter ici. Si elle n'en a pas, vous n'avez pas besoin de modifier ce fichier.
examples/perlcriticrc
Si le nouvel élément a un élément de configuration global correspondant, vous devez l'ajouter ici. Si elle n'en a pas, vous n'avez pas besoin de modifier ce fichier.

Testing

Les fichiers de test suivants doivent être pris en compte pour modification :

t/00_modules.t
t/01_config.t
t/01_config_bad_perlcritic.t
t/04_options_processor.t
t/07_command.t
t/10_user_profile.t
t/16_roundtrip_defaults.t

Selon votre nouvel élément, vous n'aurez peut-être pas besoin de modifier tous ces fichiers, mais vous devriez au moins les passer en revue. En fonction de ce que fait réellement votre nouvel élément, d'autres fichiers de test pourraient également nécessiter des modifications.

DEPRECATION ET SUPPRESSION D'UNE SUBROUTINE OU MÉTHODE PUBLIQUE

C'est quelque chose à faire avec soin. Le code en question peut exister uniquement pour servir Perl::Critic, mais s'il est documenté comme public, il peut être utilisé "dans le monde réel", soit dans des extensions à Perl::Critic, soit par des utilisateurs de Perl::Critic.

Avant de déprécier du code public, le dépréciateur potentiel doit discuter de ces questions sur la liste des développeurs de Perl::Critic. Il y a des instructions sur la façon de s'abonner à cette liste dans "EXTENDING THE CRITIC" dans Perl::Critic.

Une fois qu'un consensus est atteint, les détails techniques de la dépréciation sont assez simples.

Vous devez insérer quelque chose comme ceci dans le code à déprécier :

warnings::warnif(
    'deprecated',
    'Perl::Critic::Utils::foo() deprecated, use blah::foo() instead.',
);

Vous devez déléguer la fonctionnalité de l'ancienne sous-routine à la nouvelle sous-routine, si cela est possible (cela n'est pas toujours réalisable).

Vous devez mettre à jour la documentation pour indiquer que l'ancien code est déprécié et quel est son remplacement.

Après que l'ancien code ait été déprécié pendant plusieurs versions de production, vous pouvez le supprimer.
