NOM

Perl::Critic::Policy::ErrorHandling::RequireCheckingReturnValueOfEval - Vous ne pouvez pas dépendre de la valeur de "$@"/"$EVAL_ERROR" pour savoir si un "eval" a échoué.

AFFILIATION

Cette politique fait partie de la distribution principale de Perl::Critic.

DESCRIPTION

Un idiome courant en perl pour gérer les erreurs possibles est d'utiliser "eval" suivi d'une vérification de $@/$EVAL_ERROR :

eval {
    ...
};
if ($EVAL_ERROR) {
    ...
}

Il y a un problème avec ceci : la valeur de $EVAL_ERROR peut changer entre la fin de "eval" et l'instruction "if". Le problème réside dans les destructeurs d'objets :

package Foo;
...
sub DESTROY {
    ...
    eval { ... };
    ...
}
package main;
eval {
    my $foo = Foo->new();
    ...
};
if ($EVAL_ERROR) {
    ...
}

En supposant qu'il n'y ait pas d'autres références à $foo créées, lorsque le bloc "eval" dans "main" est quitté, Foo::DESTROY() sera appelé, que "eval" ait terminé normalement ou non. Si l'"eval" dans "main" échoue, mais que l'"eval" dans Foo::DESTROY() réussit, alors $EVAL_ERROR sera vide au moment où le "if" est exécuté. D'autres problèmes surviennent si vous dépendez du contenu exact de $EVAL_ERROR et que les deux "eval" échouent, car les messages des deux seront concaténés.

Même s'il n'y a pas d'"eval" directement dans le code de la méthode DESTROY(), elle peut appeler du code qui utilise "eval" ou affecte autrement $EVAL_ERROR.

La solution consiste à s'assurer que, lors d'une sortie normale, un "eval" renvoie une valeur vraie et à tester cette valeur :

# Les constructeurs ne posent pas de problème.
my $object = eval { Class->new() };
# Pour couvrir la possibilité qu'une opération puisse correctement renvoyer une
# valeur fausse, terminez le bloc avec "1" :
if ( eval { something(); 1 } ) {
    ...
}
eval {
    ...
    1;
}
    or do {
        # Gestion d'erreur ici
    };

Malheureusement, vous ne pouvez pas utiliser la fonction "defined" pour tester le résultat ; "eval" renvoie une chaîne vide en cas d'échec.

Divers modules ont été écrits pour faciliter la localisation et la vérification correctes de $@/$EVAL_ERROR. Par exemple :

use Try::Tiny;
try {
    ...
} catch {
    # Gestion d'erreur ici ;
    # L'exception est dans $_/$ARG, pas dans $@/$EVAL_ERROR.
};  # Notez le point-virgule.

"Mais nous n'utilisons DESTROY() nulle part dans notre code !" dites-vous. C'est peut-être le cas, mais est-ce que l'un des modules tiers que vous utilisez en a ? Qu'en est-il de ceux que vous pourriez utiliser à l'avenir ou des versions mises à jour de ceux que vous utilisez déjà ?

CONFIGURATION

Cette politique n'est pas configurable, sauf pour les options standard.

VOIR AUSSI

Pour une manière simple et agréable, sans magie, de gérer correctement les exceptions, consultez Try::Tiny.
