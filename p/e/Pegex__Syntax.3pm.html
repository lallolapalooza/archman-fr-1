Pegex Syntax

Le terme « Pegex » peut être utilisé pour désigner à la fois l'outil Pegex et le langage de syntaxe Pegex qui est utilisé pour écrire les fichiers de grammaire Pegex. Ce document détaille la syntaxe Pegex.

Pegex est un langage auto-hébergé. Cela signifie que la grammaire pour définir le langage Pegex est écrite dans le langage Pegex lui-même. Vous pouvez le constater par vous-même ici : https://github.com/ingydotnet/pegex-pgx/blob/master/pegex.pgx.

Je voudrais que vous regardiez ce lien dès maintenant. Une grammaire Pegex (comme celle-ci) est composée de deux parties : une section de métadonnées et une section de règles.

La partie réelle d'une grammaire Pegex réside dans ses règles. La première règle de la grammaire susmentionnée est (en gros) :

grammar: meta_section rule_section

Ce qui dit, une grammaire EST une section de métadonnées suivie de une section de règles. Mais bon, nous le savions déjà !

Section de Métadonnées

Les déclarations de métadonnées se trouvent au début d'un fichier de grammaire, et ressemblent à ceci :

%pegexKeyword value

Jetons un coup d'œil au début du fichier pegex.pgx :

# This is the Pegex grammar for Pegex grammars!
%grammar pegex
%version 0.1.0

Cela définit deux valeurs de métadonnées : "grammar" et "version", qui spécifient respectivement le nom et la version de la grammaire.

Vous remarquerez peut-être aussi que la première ligne est un commentaire. Les commentaires commencent par un "#" et vont jusqu'à la fin de la ligne. Les commentaires sont autorisés presque partout dans la grammaire, même sur leurs propres lignes, après des déclarations, et même à l'intérieur de définitions d'expressions régulières, comme nous le verrons plus tard.

La section de métadonnées Pegex se termine lorsque la section des règles commence (avec la première définition de règle).

Section des Règles

Le reste d'une grammaire Pegex est un ensemble de règles nommées. Chaque règle est un nom de règle, suivi de « : », suivi de la définition de la règle, suivi de « ; » ou d'une nouvelle ligne.

Voici quelques exemples de règles de pegex.pgx (ce sont les règles qui commencent à définir une règle !) :

rule_definition:
    rule_start
    rule_group
    ending
rule_start: /
    ( rule_name )     # Capturer le nom de la règle
    BLANK*
    COLON -
/

Les définitions de règles sont des expressions infixes. Elles se composent de jetons séparés par des opérateurs, avec des parenthèses pour désambiguïser la précédence des liaisons. Il existe trois types de jetons distincts et trois opérateurs.

Les trois types de jetons sont : les références aux règles, les expressions régulières et les messages d'erreur. Les trois opérateurs sont ET (' '), OU ('|') et ALT ('%', '%%').

Voici un exemple de grammaire Pegex pour analyser JSON :

json: hash | array
array: / LSQUARE / ( node* % / COMMA / ) (
    / RSQUARE / | `missing ']'` )

Cela signifie : « json est soit un hash, soit un tableau. Un tableau est un « [ », zéro ou plusieurs nœuds séparés par des virgules, et un « ] ». Erreur s'il manque un « ] ». »

« hash », « array » et « node » sont des références aux règles, ce qui signifie qu'elles font référence à des règles nommées dans la grammaire qui doivent correspondre à cet endroit. Le texte entre une paire de « / » forme une expression régulière. Le texte entre guillemets inversés est un message d'erreur.

« LSQUARE », « RSQUARE » et « COMMA » sont également des références à des règles. Les règles peuvent être référencées dans des expressions régulières, à condition qu'elles fassent elles-mêmes référence à des expressions régulières. De cette façon, de grandes expressions régulières peuvent être construites à partir de petites, permettant la réutilisation et une meilleure lisibilité. Enfin, le * après « node » est appelé un « quantificateur ». Plus d'informations à leur sujet plus tard.

Références aux Règles

Une référence à une règle est le nom d'une règle entre crochets. Les crochets sont généralement omis. Dans une expression régulière, une référence à une règle sans "<>" doit être précédée d'un espace.

<sub_rule_name>
sub_rule_name

Lorsqu'elle est utilisée en dehors d'une expression régulière, une référence peut avoir plusieurs modificateurs de préfixe. Notez que les crochets ne sont pas obligatoires ici, mais améliorent la lisibilité.

=rule  # Zéro largeur positive (look-ahead)
!rule  # Zéro largeur négative (look-ahead)
.rule  # Sauter (c.-à-d. : analyser mais ne pas capturer de sous-motif)
-rule  # Aplatir (commencer à capturer sans faire de tableau)
+rule  # Toujours envelopper

(Le saut et l'enveloppement sont expliqués dans [Valeurs de retour]).

Une référence peut également avoir plusieurs quantificateurs suffixes. Similaire à la syntaxe des expressions régulières, un quantificateur indique combien de fois une règle (référence) doit correspondre.

rule?      # Optionnel
rule*      # Zéro ou plusieurs fois
rule+      # Une ou plusieurs fois
<rule>8    # Exactement 8 fois
<rule>2+   # 2 fois ou plus
<rule>2-3  # 2 ou 3 fois
<rule>0-6  # 0 à 6 fois

Remarque : vous devez utiliser des crochets si vous utilisez un modificateur numérique :

rule8    # INCORRECT ! Cela correspondrait à la règle « rule8 ».
rule2+   # INCORRECT ! Cela correspondrait à la règle « rule2 », 1 fois ou plus.
rule2-3  # INCORRECT ! Erreurs de syntaxe Pegex

Il existe un ensemble spécial d'« atomiques » prédéfinis qui font référence à des fragments d'expressions régulières. Les atomiques existent pour chaque caractère de ponctuation et pour les caractères courants dans les expressions régulières. Les atomiques améliorent la lisibilité dans les textes de grammaire et permettent d'utiliser des caractères spéciaux (comme / ou #) comme syntaxe Pegex.

Par exemple, une expression régulière pour correspondre à un commentaire pourrait être # suivie de n'importe quoi suivie d'une nouvelle ligne. En Pegex, vous écririez :

comment: / HASH ANY* EOL /

au lieu de :

comment: /#.*\r?\n/

Pegex compilerait le premier dans le second.

Voici quelques atomiques :

DASH    # -
PLUS    # +
TILDE   # ~
SLASH   # /
HASH    # # (littéral)
QMARK   # ? (littéral)
STAR    # * (littéral)
LPAREN  # ( (littéral)
RPAREN  # ) (littéral)
WORD    # \w
WS      # \s

La liste complète se trouve dans [Code source des atomes|<https://metacpan.org/source/Pegex::Grammar::Atoms].>

Expressions Régulières

Dans Pegex, la syntaxe d'une expression régulière est appelée « regex ». C'est-à-dire, lorsque le terme « regex » est utilisé, il fait référence à la syntaxe Pegex, et lorsque le terme « expression régulière » est utilisé, il fait référence à l'expression régulière qui est compilée dans la regex.

Une regex est une chaîne entre des parenthèses fléchées.

/regex/

La syntaxe de regex suit principalement Perl, avec les exceptions suivantes :

# Les règles entre crochets sont référencées dans la regex
/ ( <rule1> | 'non_rule' ) /  # 'non_rule' est interprété littéralement
# La syntaxe implique un modificateur /x, donc les espaces et les commentaires sont ignorés.
/ (
    rule1+   # Correspondre à rule1 une ou plusieurs fois
    |
    rule2
) /
# L'espace est déclaré avec - et +.
/ - rule3 + /  # - = \s*, + = \s+, etc.
# Toute syntaxe (?XX) peut avoir le signe ? supprimé
/ (: a | b ) /  # Idem que / (?: a | b ) /

Message d'Erreur

Un message d'erreur est une chaîne entre guillemets inversés. Si l'analyseur atteint un message d'erreur dans la grammaire, il lèvera une erreur d'analyse avec ce message.

`error message`

Opérateurs

Les opérateurs dans l'ordre décroissant de précédence sont : ALT, ET et OU.

ET et OU sont les opérateurs les plus courants. ET est représenté par l'absence d'opérateur. Comme dans ces règles :

r1: <a><b>
r2: a b

Ce sont les deux identiques. Ils signifient que la règle "a" et (immédiatement après) la règle "b".

OU signifie correspondre à l'un ou l'autre.

r: a | b | c

signifie faire correspondre la règle "a" ou la règle "b" ou la règle "c". Les règles sont vérifiées dans l'ordre et si l'une correspond, les autres sont ignorées.

Pegex Syntax

This page describes the PEGEX syntax.

Meta Section

The meta section is optional and is used for defining the top-level rule of the grammar, as well as any default return values.

%meta
    root = rule_name
    ret  = default_return_value
  • root: Specifies the name of the rule that starts the parse.
  • ret: Specifies a default value to return if no capture groups are specified in the root rule. This can be a scalar or an array reference.

Example:

%meta
    root = expression
    ret  = 0

If the root rule itself does not specify any capture groups, the parser will return 0.

Rule Section

The rule section defines the grammar rules. Each rule is defined by a name followed by a colon and then the rule's expression.

rule_name :: expression

Rules can be combined using the following operators:

  • | (alternation): Matches either the expression on the left or the expression on the right.
  • & (sequence): Matches the expression on the left followed by the expression on the right.
  • ? (optional): Matches the preceding expression zero or one time.
  • + (one or more): Matches the preceding expression one or more times.
  • * (zero or more): Matches the preceding expression zero or more times.
  • () (grouping): Groups expressions together.
  • {} (capture): Captures the result of the expression.
  • [] (skip): Skips the result of the expression.

Example:

expression ::= term (('+' | '-') term)*
term       ::= factor (('*' | '/') factor)*
factor     ::= NUMBER | '(' expression ')'

The "%%" means that a trailing separator is optional.

r: a+ %% b

would match these:

a
ab
aba
abab

ANY operators take precedence over everything else, similar to other parsers. These rules have the same binding precedence:

r1: a b | c % d
r2: (a b) | (c % d)

Parens are not only used for indicating binding precedence; they also can create quantifiable groups:

r1: (a b)+ c

would match:

abababac

Return Values

All return values are based on the capture groups ("$1/$2/$3/etc." type variables) of parsed RE statements. The exact structure of the result tree depends on the type of Receiver used. For example, Pegex::Tree will return:

$1              # single capture group
[ @+[1..$#+] ]  # multiple capture groups

This would be a match directly from the RE rule. As rules go further back, things are put into arrays, but only if there is more than one result. For example:

r: (a b)+ % +
a: /( ALPHA+ )/
b: /( DIGIT+ )( PLUS )/
# input = foobar123+
# output (using Pegex::Tree) = [
#     'foobar', [ '123', '+' ]
# ]
#
# input = foobar123+ boofar789+
# output (using Pegex::Tree) = [
#     [ 'foobar', [ '123', '+' ] ],
#     [ 'boofar', [ '789', '+' ] ],
# ]

Skipping

Any rule can use the skip modifier (DOT) to completely skip the return from that rule (and any children below it). The rule is still processed, but nothing is put into the tree. (This is different from, say, putting "undef" into the return.) This can also affect the number of values returned, and thus, whether a value comes as an array:

r: (a .b)+ % +
a: /( ALPHA+ )/
b: /( DIGIT+ )( PLUS )/
# input = foobar123+ boofar789+
# output (using Pegex::Tree) = [
#     'foobar',
#     'boofar',
# ]

The skip modifier can also be used with groups. (This is the only group modifier allowed so far.)

r: .(a b)+ % +
a: /( ALPHA+ )/
b: /( DIGIT+ )( PLUS )/
# output (using Pegex::Tree) = []

Wrapping

You can also turn on "wrapping" with the Pegex::Tree::Wrap receiver. This will wrap all match values in a hash with the rule name, like so:

{ rule_A => $match }
{ rule_B => [ @matches ] }

Note that this behavior can be "hard set" with the "+/-" rule modifiers:

-rule  # Flatten array captures
+rule  # Always wrap (even if using Pegex::Tree)

This is simply a check in the "gotrule" for the receiver. So, any specific "got_*" receiver methods will override even these settings, and choose to pass the match as-is. In this case, the "got_*" sub return value dictates what ultimately gets put into the tree object:

+rule_A   # in this case, the + is useless here
sub got_rule_A {
    my ($self, $matches_arrayref) = @_;
    return $matches_arrayref;
    # will be received as [ @matches ]
}

You can "correct" this behavior by passing it back to "gotrule":

+rule_A   # now + is honored
sub got_rule_A {
    my ($self, $matches_arrayref) = @_;
    return $self->gotrule($matches_arrayref);
    # will be received as { rule_A => [ @matches ] }
}
