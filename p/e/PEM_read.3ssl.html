NOM

PEM_read, PEM_read_bio, PEM_do_header, PEM_get_EVP_CIPHER_INFO, PEM_write, PEM_write_bio, PEM_ASN1_write, PEM_ASN1_write_bio, PEM_ASN1_write_bio_ctx - Routines d'encodage PEM

SYNTAXE

#include <openssl/pem.h>
int PEM_read(FILE *fp, char **name, char **header,
             unsigned char **data, long *len);
int PEM_read_bio(BIO *bp, char **name, char **header,
                 unsigned char **data, long *len);
int PEM_get_EVP_CIPHER_INFO(char *header, EVP_CIPHER_INFO *cinfo);
int PEM_do_header(EVP_CIPHER_INFO *cinfo, unsigned char *data, long *len,
                  pem_password_cb *cb, void *u);
int PEM_write(FILE *fp, const char *name, const char *header,
              const unsigned char *data, long len);
int PEM_write_bio(BIO *bp, const char *name, const char *header,
                  const unsigned char *data, long len);
int PEM_ASN1_write(i2d_of_void *i2d, const char *name, FILE *fp,
                   const void *x, const EVP_CIPHER *enc,
                   const unsigned char *kstr, int klen,
                   pem_password_cb *callback, void *u);
int PEM_ASN1_write_bio(i2d_of_void *i2d, const char *name, BIO *bp,
                       const void *x, const EVP_CIPHER *enc,
                       const unsigned char *kstr, int klen,
                       pem_password_cb *callback, void *u);
int PEM_ASN1_write_bio_ctx(OSSL_i2d_of_void_ctx *i2d, void *vctx,
                           const char *name, BIO *bp, const void *x,
                           const EVP_CIPHER *enc, const unsigned char *kstr,
                           int klen, pem_password_cb *callback, void *u);

DESCRIPTION

Ces fonctions lisent et écrivent des objets encodés en PEM, en utilisant le type PEM name, toute information d'en-tête header supplémentaire et les data brutes de longueur len.

PEM est le terme utilisé pour l'encodage de contenu binaire défini pour la première fois dans la RFC 1421 de l'IETF. Le contenu est une série de lignes encodées en base64, entourées de marqueurs de début/fin chacun sur sa propre ligne. Par exemple :

-----BEGIN PRIVATE KEY-----
MIICdg....
... bhTQ==
-----END PRIVATE KEY-----

Des lignes d'en-tête optionnelles peuvent apparaître après la ligne de début, et leur existence dépend du type d'objet écrit ou lu.

PEM_write() écrit dans le fichier fp, tandis que PEM_write_bio() écrit dans le BIO bp. Le name est le nom à utiliser dans le marqueur, le header est la valeur de l'en-tête ou NULL, et data et len spécifient les données et leur longueur.

Le tampon de data final est typiquement un objet ASN.1 qui peut être décodé avec la fonction d2i appropriée au type name ; voir d2i_X509(3) pour des exemples.

PEM_read() lit depuis le fichier fp, tandis que PEM_read_bio() lit depuis le BIO bp. Les deux ignorent toute donnée non-PEM qui précède le début de l'objet PEM suivant. Lorsqu'un objet est récupéré avec succès, le nom du type de "----BEGIN <type>-----" est retourné via l'argument name, tous les en-têtes d'encapsulation sont retournés dans header et le contenu décodé en base64 et sa longueur sont retournés via data et len respectivement. Les pointeurs name, header et data sont alloués via OPENSSL_malloc() et doivent être libérés par l'appelant via OPENSSL_free() lorsqu'ils ne sont plus nécessaires.

PEM_get_EVP_CIPHER_INFO() peut être utilisé pour déterminer si les data retournées par PEM_read() ou PEM_read_bio() sont chiffrées et pour récupérer le chiffrement et l'IV associés. L'appelant passe un pointeur vers une structure de type EVP_CIPHER_INFO via l'argument cinfo et le header retourné par PEM_read() ou PEM_read_bio(). Si l'appel réussit, 1 est retourné et le chiffrement et l'IV sont stockés à l'adresse pointée par cinfo. Lorsque l'en-tête est mal formé, non supporté, lorsque le chiffrement est inconnu ou qu'une erreur interne se produit, 0 est retourné. Cette fonction est obsolète, voir NOTES ci-dessous.

PEM_do_header() peut ensuite être utilisé pour déchiffrer les données si l'en-tête indique un chiffrement. L'argument cinfo est un pointeur vers la structure initialisée par l'appel précédent à PEM_get_EVP_CIPHER_INFO(). Les arguments data et len sont ceux retournés par l'appel précédent à PEM_read() ou PEM_read_bio(). Les arguments cb et u rendent possible de remplacer la fonction par défaut d'invite de mot de passe comme décrit dans PEM_read_PrivateKey(3). En cas de succès, les data sont déchiffrées sur place et len est mis à jour pour indiquer la longueur du texte en clair. Cette fonction est obsolète, voir NOTES ci-dessous.

Si les données sont a priori connues pour ne pas être chiffrées, alors ni PEM_do_header() ni PEM_get_EVP_CIPHER_INFO() n'ont besoin d'être appelés.

VALEURS DE RETOUR

PEM_read() et PEM_read_bio() retournent 1 en cas de succès et 0 en cas d'échec, ce dernier incluant le cas où aucun autre objet PEM ne reste dans le fichier d'entrée. Pour distinguer la fin du fichier des erreurs plus graves, l'appelant doit regarder la pile d'erreurs et vérifier PEM_R_NO_START_LINE, qui indique qu'aucun autre objet PEM n'a été trouvé. Voir ERR_peek_last_error(3), ERR_GET_REASON(3).

PEM_get_EVP_CIPHER_INFO() et PEM_do_header() retournent 1 en cas de succès, et 0 en cas d'échec. Les data sont probablement inutiles si ces fonctions échouent.

NOTES

Les fonctions PEM_get_EVP_CIPHER_INFO() et PEM_do_header() sont obsolètes. C'est parce que le format de chiffrement PEM sous-jacent est obsolète et devrait être évité. Il utilise un format de chiffrement avec une fonction de dérivation de clé spécifique à OpenSSL, qui utilise MD5 avec un compte d'itération de 1 ! Au lieu de cela, les clés privées devraient être stockées sous forme PKCS#8, avec un PBE PKCS#5 v2.0 fort. Voir PEM_write_PrivateKey(3) et d2i_PKCS8PrivateKey_bio(3).

PEM_do_header() ne fait aucune supposition concernant la phrase secrète reçue du rappel de mot de passe. Elle sera simplement traitée comme une séquence d'octets.

PEM_write() et PEM_write_bio() retournent le nombre d'octets encodés (sans compter l'en-tête et le marqueur de fin PEM) écrits en cas de succès ou 0 en cas d'échec.

PEM_ASN1_write_bio() et PEM_ASN1_write_bio_ctx() retournent 1 en cas de succès et 0 en cas d'échec. Cette dernière fonction transmet une valeur de contexte supplémentaire fournie par l'application à la fonction i2d qui sérialise l'objet ASN.1 d'entrée.
