NOM

Perl::Critic::Policy::InputOutput::RequireBriefOpen - Fermez les descripteurs de fichiers dès que possible après leur ouverture.

AFFILIATION

Cette politique fait partie de la distribution de base de Perl::Critic.

DESCRIPTION

Une façon dont les systèmes de production échouent de manière inattendue est de manquer de descripteurs de fichiers. Les descripteurs de fichiers sont une ressource limitée sur tous les systèmes d'exploitation que je connaisse, et en manquer est pratiquement impossible à récupérer. La solution est de ne pas en manquer en premier lieu. Qu'est-ce qui amène les programmes à manquer de descripteurs de fichiers ? Généralement, ce sont des fuites : vous ouvrez un descripteur de fichier et oubliez de le fermer, ou attendez simplement un temps très long avant de le fermer.

Ce problème est rarement révélé par les systèmes de tests, car les tests ne s'exécutent rarement assez longtemps ou n'ont pas assez de charge pour atteindre la limite de descripteurs de fichiers. Ainsi, la meilleure façon d'éviter le problème est 1) de toujours fermer tous les descripteurs de fichiers que vous ouvrez et 2) de les fermer dès que possible.

Cette politique prend note des appels à open() pour lesquels il n'y a pas d'appel close() correspondant dans les "N" lignes de code. Si vous avez vraiment besoin de faire beaucoup de traitement sur un descripteur de fichier ouvert, vous pouvez déplacer ce traitement vers une autre méthode comme celle-ci :

sub process_data_file {
    my ($self, $filename) = @_;
    open my $fh, '<', $filename
        or croak 'Failed to read datafile ' .  $filename . '; ' . $OS_ERROR;
    $self->_parse_input_data($fh);
    close $fh;
    return;
}
sub _parse_input_data {
    my ($self, $fh) = @_;
    while (my $line = <$fh>) {
        ...
    }
    return;
}

À titre exceptionnel, cette politique autorise également le code à renvoyer le descripteur de fichier après l'"open" au lieu de le fermer. Tout comme la fermeture, cependant, ce "return" doit être dans le bon nombre de lignes. À partir de là, c'est à vous de déterminer si le code ferme rapidement le descripteur de fichier.

Les descripteurs STDIN, STDOUT et STDERR sont exemptés de cette politique.

CONFIGURATION

Cette politique autorise les invocations de close() à être jusqu'à "N" lignes après leurs appels open() correspondants, où "N" est par défaut à 9. Vous pouvez remplacer cela pour le définir à un nombre différent avec le réglage "lines". Pour ce faire, placez des entrées dans un fichier .perlcriticrc comme ceci :

[InputOutput::RequireBriefOpen]
lines = 5

LIMITATIONS

"IO::File->new"

Cette politique ne recherche que les appels explicites "open". Elle ne détecte pas les appels à "CORE::open" ou "IO::File->new" ou similaires.

Est-ce la bonne lexicale ?

Nous ne vérifions pas actuellement les descripteurs de fichiers redéclarés. Ainsi, le code suivant est un faux négatif, par exemple, car le descripteur de fichier de portée externe n'est pas fermé :

open my $fh, '<', $file1 or croak;
if (open my $fh, '<', $file2) {
    print <$fh>;
    close $fh;
}

C'est un exemple 만든, mais il n'est pas rare que les gens utilisent $fh pour le nom du descripteur de fichier à chaque fois. Peut-être qu'il est temps de penser à de meilleurs noms de variables...
