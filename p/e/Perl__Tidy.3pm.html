Perl::Tidy(3) Documentation Perl fournie par l'utilisateur Perl::Tidy(3)

NOM

Perl::Tidy - Analyse et embellit le code source perl

SYNTAXE

use Perl::Tidy;
my $error_flag = Perl::Tidy::perltidy(
    source            => $source,
    destination       => $destination,
    stderr            => $stderr,
    argv              => $argv,
    perltidyrc        => $perltidyrc,
    logfile           => $logfile,
    errorfile         => $errorfile,
    teefile           => $teefile,
    debugfile         => $debugfile,
    formatter         => $formatter,    # objet callback (voir ci-dessous)
    dump_options      => $dump_options,
    dump_options_type => $dump_options_type,
    prefilter         => $prefilter_coderef,
    postfilter        => $postfilter_coderef,
);

DESCRIPTION

Ce module rend la fonctionnalité de l'utilitaire perltidy disponible pour les scripts perl. Tous les paramètres d'entrée, ou aucun, peuvent être omis, auquel cas le tableau @ARGV sera utilisé pour fournir les paramètres d'entrée comme décrit dans la page de manuel de perltidy(1).

Par exemple, le script perltidy n'est essentiellement que ceci :

use Perl::Tidy;
Perl::Tidy::perltidy();

L'appel à perltidy renvoie un scalaire $error_flag qui est VRAI si une erreur a provoqué une terminaison prématurée, et FAUX si le processus s'est terminé normalement. Des discussions supplémentaires sur les erreurs sont contenues ci-dessous dans la section GESTION DES ERREURS.

Le module accepte les flux d'entrée et de sortie par diverses méthodes. La liste suivante de paramètres peut être l'un des éléments suivants : un nom de fichier, une référence de TABLEAU, une référence de SCALAIRE, ou un objet avec une méthode getline ou print, selon le cas.

source            - la source du script à formater
destination       - la destination de la sortie formatée
stderr            - sortie d'erreur standard
perltidyrc        - le fichier .perltidyrc
logfile           - le flux du fichier .LOG, le cas échéant
errorfile         - le flux du fichier .ERR, le cas échéant
dump_options      - ref vers un hash pour recevoir les paramètres (voir ci-dessous),
dump_options_type - contrôle le contenu de dump_options
dump_getopt_flags - ref vers un hash pour recevoir les drapeaux Getopt
dump_options_category - ref vers un hash donnant la catégorie des options
dump_abbreviations    - ref vers un hash donnant toutes les abréviations

Le tableau suivant illustre la logique utilisée pour décider comment traiter un paramètre.

ref($param)  $param est supposé être :
-----------  ---------------------
undef        un nom de fichier
SCALAR       ref vers une chaîne
ARRAY        ref vers un tableau
(autre)      objet avec getline (si source) ou print méthode

Si le paramètre est un objet, et que l'objet a une méthode close, cette méthode close sera appelée à la fin du flux.

source
Si le paramètre source est fourni, il définit la source du flux d'entrée. Si un flux d'entrée est défini avec le paramètre source, aucun autre nom de fichier source ne peut être spécifié dans le tableau @ARGV ou le paramètre argv.
destination
Si le paramètre destination est fourni, il sera utilisé pour définir le fichier ou l'emplacement mémoire pour recevoir la sortie de perltidy.

Note importante si destination est une chaîne ou une référence de tableau. Les chaînes de caractères Perl qui sont décodées en utf8 par Perl::Tidy peuvent être retournées dans deux états possibles, décodé ou encodé, et il est important que le programme appelant et Perl::Tidy soient d'accord sur l'état à retourner. Un indicateur --encode-output-strings, ou simplement -eos, a été ajouté dans la version 20220217 de Perl::Tidy à cet effet.

  • Utilisez -eos si Perl::Tidy doit encoder toute chaîne qu'il décode. C'est le défaut actuel car cela fait de perltidy un bon filtre, et c'est le réglage correct pour la plupart des programmes. Mais n'utilisez pas ce réglage si le programme appelant encode également les données, car un double encodage corrompra les données.
  • Utilisez -neos si une chaîne doit rester décodée si elle a été décodée par Perl::Tidy. Ceci n'est approprié que si le programme appelant gérera tout encodage nécessaire avant de sortir la chaîne. Si nécessaire, cet indicateur peut être ajouté à la fin du paramètre argv passé à Perl::Tidy.

Pour plus d'informations, voir https://github.com/perltidy/perltidy/blob/master/docs/eos_flag.md.

Ce changement de comportement par défaut a été effectué sur une période comme suit :

  • Pour les versions antérieures à 20220217, l'indicateur -eos n'était pas disponible et le comportement était équivalent à -neos.
  • Dans la version 20220217, l'indicateur -eos a été ajouté mais le défaut est resté -neos.
  • Pour les versions après 20220217, le défaut a été réglé sur -eos.
stderr
Le paramètre stderr permet au programme appelant de rediriger le flux qui irait autrement vers le périphérique de sortie d'erreur standard vers l'un des types de flux listés ci-dessus. Ce flux contient des avertissements et des erreurs importants liés aux paramètres passés à perltidy.
perltidyrc
Si le fichier perltidyrc est fourni, il sera utilisé à la place de tout fichier de configuration .perltidyrc qui serait autrement utilisé.
errorfile
Le paramètre errorfile permet au programme appelant de capturer le flux qui irait autrement vers un fichier .ERR. Ce flux contient des avertissements ou des erreurs liés au contenu d'un fichier ou d'un flux source.

La raison pour laquelle cela est différent du flux stderr est que lorsque perltidy est appelé pour traiter plusieurs fichiers, il y aura jusqu'à un fichier .ERR créé pour chaque fichier et il serait très confus s'ils étaient combinés.

Cependant, si perltidy est appelé pour traiter un seul script perl, il peut être plus pratique de combiner le flux errorfile avec le flux stderr. Cela peut être fait en réglant le paramètre -se, auquel cas ce paramètre est ignoré.

logfile
Le paramètre logfile permet au programme appelant de capturer le flux de journalisation. Ce flux n'est créé que s'il est demandé avec un paramètre -g. Il contient des informations diagnostiques détaillées sur un script qui peuvent être utiles pour le débogage.
teefile
Le paramètre teefile permet au programme appelant de capturer le flux de copie. Ce flux n'est créé que s'il est demandé avec l'un des paramètres 'tee', un --tee-pod, --tee-block-comments, --tee-side-commnts, ou --tee-all-comments.
debugfile
Le paramètre debugfile permet au programme appelant de capturer le flux produit par le paramètre --DEBUG. Ce paramètre est principalement utilisé pour le débogage de perltidy lui-même.
argv
Si le paramètre argv est fourni, il sera utilisé à la place du tableau @ARGV. Le paramètre argv peut être une chaîne, une référence à une chaîne, ou une référence à un tableau. S'il s'agit d'une chaîne ou d'une référence à une chaîne, elle sera analysée en un tableau d'éléments comme si c'était une chaîne de ligne de commande.
dump_options
Si le paramètre dump_options est fourni, il doit être une référence vers un hash. Dans ce cas, les paramètres contenus dans tout fichier de configuration perltidyrc seront placés dans ce hash et perltidy retournera immédiatement. Ceci est équivalent à exécuter perltidy avec --dump-options, sauf que les paramètres sont retournés dans un hash plutôt que d'être affichés sur la sortie standard. De plus, par défaut, seuls les paramètres du fichier perltidyrc sont retournés, mais cela peut être modifié (voir le paramètre suivant). Ce paramètre fournit une méthode pratique pour que les programmes externes lisent un fichier perltidyrc. Un exemple de programme utilisant cette fonctionnalité, perltidyrc_dump.pl, est inclus dans la distribution.

Toute combinaison des paramètres dump_ peut être utilisée ensemble.

dump_options_type

OPTIONS

Les options sont décrites dans la page de manuel de perltidy(1).

ENVIRONNEMENT

PERLTIDY_PERLRC

Si cette variable d'environnement est définie, elle sera utilisée comme nom de fichier perltidyrc.

STATUT DE SORTIE

Le retour de perltidy est un indicateur d'erreur. VRAI si une erreur a provoqué une terminaison prématurée, FAUX si le processus s'est terminé normalement.

Le module Perl::Tidy utilise les codes de sortie du module Perl::Strip. Les codes de sortie possibles sont :

0
Succès
1
Erreur de syntaxe
2
Erreur lors de la lecture d'un fichier
3
Erreur lors de l'écriture d'un fichier
4
Erreur lors de l'exécution de l'interpréteur Perl
5
Paramètre non valide
6
Pas assez de mémoire
7
Erreur interne
8
Erreur de décodage
9
Erreur d'encodage

GESTION DES ERREURS

Le paramètre $stderr est un flux qui contient les messages d'erreur et d'avertissement du processus de formatage. Les erreurs de syntaxe dans le script perl source peuvent être signalées ici.

Le paramètre $errorfile est le fichier .ERR. Ce fichier ne sera créé que s'il y a des erreurs ou des avertissements liés au fichier source.

Le retour de la fonction perltidy est un indicateur d'erreur. Si cet indicateur est vrai, une erreur s'est produite et le script ne s'est pas terminé normalement.

GESTION DES ERREURS

La valeur de retour de perltidy peut être 0, 1 ou 2, pour indiquer le statut du résultat.

Une valeur de retour de 0 indique que perltidy s'est terminé avec succès et n'a affiché aucun message d'erreur.

Une valeur de retour de 1 indique que le processus s'est terminé prématurément en raison d'erreurs dans les paramètres d'entrée. Cela peut se produire, par exemple, si un paramètre est mal orthographié ou s'il reçoit une valeur invalide. Le programme appelant doit vérifier ce drapeau, car s'il est actif, le flux de destination sera vide ou incomplet et devra être ignoré. Les messages d'erreur dans le flux stderr indiqueront la cause de tout problème.

Une valeur de retour de 2 indique que perltidy s'est terminé avec succès mais qu'il y a des messages d'avertissement dans le flux stderr liés à des erreurs ou des conflits dans les paramètres, ou des messages d'erreur dans le flux errorfile liés à des erreurs de syntaxe dans le code source qui est en cours de nettoyage.

En cas d'erreur catastrophique irrécupérable, perltidy se terminera en appelant les fonctions croak ou confess pour aider le programmeur à localiser le problème. Celles-ci devraient normalement se produire pendant le développement du programme.

NOTES SUR LES PARAMÈTRES DE MISE EN FORME

Les paramètres qui contrôlent la mise en forme peuvent être passés de différentes manières : dans un fichier de configuration .perltidyrc, dans le paramètre perltidy, ou dans le paramètre argv.

Si le style -pbp est utilisé, le drapeau -nst doit également être spécifié. Ceci est nécessaire pour désactiver le drapeau -st contenu dans le paramètre -pbp, qui sinon dirigerait la sortie vers la console standard.

Exemples

L'exemple suivant utilise des références de chaînes pour stocker le code d'entrée et de sortie, ainsi que les flux d'erreurs, et montre comment l'erreur est vérifiée.

use Perl::Tidy;
my $source_string = <<'EOT';
my $error = Perl::Tidy::perltidy(argv=>$argv,source=>\$source_string,
  destination=>\$dest_string,stderr=>\$stderr_string,
errorfile=>\$errorfile_string,);
EOT
my $dest_string;
my $stderr_string;
my $errorfile_string;
my $argv = "-npro";   # Ignore tout .perltidyrc à cet endroit
$argv .= " -pbp";     # Formate selon les meilleures pratiques de perl
$argv .= " -nst";     # Doit désactiver -st si -pbp est spécifié
$argv .= " -se";      # -se ajoute errorfile à stderr
## $argv .= " --spell-check";  # commenter pour activer une erreur
print "<<RAW SOURCE>>\n$source_string\n";
my $error = Perl::Tidy::perltidy(
    argv        => $argv,
    source      => \$source_string,
    destination => \$dest_string,
    stderr      => \$stderr_string,
    errorfile   => \$errorfile_string,  # ignoré lorsque -se est spécifié
    ##phasers   => 'stun',              # commenter pour activer une erreur
);
if ($error) {
    # erreur dans les paramètres d'entrée, aucune sortie nettoyée
    print "<<STDERR>>\n$stderr_string\n";
    die "Arrêt en raison d'erreurs graves\n";
}
if ($dest_string)      { print "<<TIDIED SOURCE>>\n$dest_string\n" }
if ($stderr_string)    { print "<<STDERR>>\n$stderr_string\n" }
if ($errorfile_string) { print "<<.ERR file>>\n$errorfile_string\n" }

D'autres exemples sont donnés dans la section d'exemples de la distribution perltidy.

Utilisation de l'objet de rappel formatter

Le paramètre formatter est un objet de rappel facultatif qui permet à l'application de recevoir des lignes tokenisées de perltidy pour un traitement supplémentaire. Lorsque ce paramètre est utilisé, les deux options de mise en forme intégrées de perltidy (beautification ou html) sont ignorées. Le diagramme suivant montre le flux logique :

                  |-- (chemin normal)   -> mise en forme standard
caller->perltidy->|-- (-html flag )    -> créer du html
                  |-- (formatter donné)-> callback vers write_line

Cela peut être utile pour traiter les scripts perl d'une manière ou d'une autre. Le paramètre $formatter dans l'appel à perltidy :

formatter   => $formatter,

est un objet créé par l'appelant avec une méthode "write_line" qui accepte et traite des lignes tokenisées, une par appel. Voici un exemple simple d'un "write_line" qui imprime simplement le numéro de ligne, le type de ligne (déterminé par perltidy) et le texte de la ligne :

sub write_line {
    # appelé ligne par ligne par perltidy
    my $self              = shift;
    my $line_of_tokens    = shift;
    my $line_type         = $line_of_tokens->{_line_type};
    my $input_line_number = $line_of_tokens->{_line_number};
    my $input_line        = $line_of_tokens->{_line_text};
    print "$input_line_number:$line_type:$input_line";
}

Le programme complet, perllinetype, est contenu dans la section des exemples de la distribution source. Comme le montre cet exemple, la méthode de rappel reçoit un paramètre $line_of_tokens, qui est une référence à un hash d'informations utiles. Cet exemple utilise ces enregistrements de hash :

$line_of_tokens->{_line_number} - le numéro de ligne (1, 2, ...)
$line_of_tokens->{_line_text}   - le texte de la ligne
$line_of_tokens->{_line_type}   - le type de la ligne, l'un des suivants :
   SYSTEM         - code spécifique au système avant la ligne shebang
   CODE           - ligne de code perl (y compris les commentaires)
   POD_START      - ligne commençant par pod, comme '=head'
   POD            - texte de documentation pod
   POD_END        - dernière ligne de la section pod, '=cut'
   HERE           - texte here-document
   HERE_END       - dernière ligne du here-document (mot cible)
   FORMAT         - section de format
   FORMAT_END     - dernière ligne de la section de format, '.'
   DATA_START     - ligne __DATA__
   DATA           - texte non identifié après __DATA__
   END_START      - ligne __END__
   END            - texte non identifié après __END__
   ERROR          - nous avons un problème sérieux, probablement pas un script perl

La plupart des applications ne s'intéresseront qu'aux lignes de type COD. Pour un exemple supplémentaire, écrivons un programme qui vérifie l'une des variables connues telles que "&`", $&, et "$'", qui peuvent ralentir le traitement. Voici un exemple de write_line, du programme d'exemple find_naughty.pl, qui le fait :

sub write_line {
    # appelé par perltidy ligne par ligne
    # nous recherchons $`, $& et $'
    my ( $self, $line_of_tokens ) = @_;
    # nous extrayons certaines choses dont nous pourrions avoir besoin
    my $line_type         = $line_of_tokens->{_line_type};
    my $input_line_number = $line_of_tokens->{_line_number};
    my $input_line        = $line_of_tokens->{_line_text};
    my $rtoken_type       = $line_of_tokens->{_rtoken_type};
    my $rtokens           = $line_of_tokens->{_rtokens};
    chomp $input_line;
    # ignorer les commentaires, pod, etc.
    return if ( $line_type ne 'CODE' );
    # nous parcourons les jetons à la recherche de $`, $& et $'
    for ( my $j = 0 ; $j < @$rtoken_type ; $j++ ) {
        # nous voulons seulement examiner les types de jetons 'i' (identificateur)
        next unless $$rtoken_type[$j] eq 'i';
        # nous extrayons le texte du jeton
        my $token = $$rtokens[$j];
        # et nous le vérifions
        if ( $token =~ /^\$[\`\&\']$/ ) {
            print STDERR
              "$input_line_number: $token\n";
        }
    }
}

Cet exemple extrait ces variables de tokenisation du hash $line_of_tokens :

$rtoken_type = $line_of_tokens->{_rtoken_type};
$rtokens     = $line_of_tokens->{_rtokens};

La variable $rtoken_type est une référence à un tableau de codes de type de jeton, et $rtokens est une référence à un tableau de texte de jeton correspondant. Ils ne sont clairement définis que pour les lignes de type COD. Perltidy classe les jetons par type et a un code court pour chaque type. Vous pouvez obtenir une liste complète en exécutant perltidy depuis la ligne de commande avec :

perltidy --dump-token-types

Perl::Tidy(3pm) — archlinux man pages

NAME

Perl::Tidy - A Perl module to format Perl code

SYNOPSIS

    use Perl::Tidy;
    my $tidier = new Perl::Tidy;
    $tidier->load_perltidyrc( '/path/to/.perltidyrc' );
    $tidier->parse_string( $perl_code );
    my $formatted_code = $tidier->formatted_code;

DESCRIPTION

Perl::Tidy is a Perl module that provides functionality for formatting Perl code according to various style guidelines. It can be used as a library within other Perl programs or as a standalone command-line tool (the perltidy(1) script).

The module parses Perl code, analyzes its structure, and rewrites it with consistent indentation, spacing, and line breaks.

ERROR HANDLING

When Perl::Tidy encounters syntax errors in the input code, it attempts to report them. The level of detail and the exact format of error messages can depend on the configuration.

NOTES ON FORMATTING PARAMETERS

Perl::Tidy's behavior is controlled by a set of formatting parameters. These can be set via command-line options when using the perltidy(1) script, or programmatically through the module's methods. A common way to manage these parameters is through a configuration file named .perltidyrc in the project directory or the user's home directory.

EXAMPLES

The source distribution for Perl::Tidy includes an examples directory containing sample programs that demonstrate how to use the module's features.

Using the formatter Callback Object

Perl::Tidy offers a debugging feature that can be enabled with the -D flag on the command line. This feature writes detailed information about the tokenization process to a file. The callback object used for this process is accessible via the following method:

    $tidier->formatter( \&Perl::Tidy::Debugger::write_debug_entry );

When the -D flag is used, Perl::Tidy will iterate through all tokens. It specifically looks for tokens of type i (identifiers). The loop skips all other token types. When an identifier is found, its actual text is checked to see if it matches one of the identifiers being sought. If a match is found, the write_line function prints the token along with its line number.

The examples section of the source distribution contains some programs that utilize the formatter option.

For assistance with Perl::Tidy's method of breaking lines into tokens, you can run the following command from the command line:

    perltidy -D filename

Replace filename with the name of a short script you are interested in. This command will generate a file named filename.DEBUG containing interleaved lines of text and their corresponding token types. The -D flag has been available in perltidy since its inception for this specific purpose. If you wish to examine the code responsible for creating this debug file, it can be found in "sub Perl::Tidy::Debugger::write_debug_entry".

EXPORT

&perltidy

INSTALLATION

The 'Perl::Tidy' module includes a binary executable named 'perltidy', which is installed automatically when the module is installed. Note that the module name is case-sensitive. For example, the standard command to install using cpanm is:

    cpanm Perl::Tidy
