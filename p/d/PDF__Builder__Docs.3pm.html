Kit de développement logiciel

Il y a quatre niveaux d'implication avec PDF::Builder. Selon ce que vous voulez faire, différents types d'installations sont recommandés.

1.
Installer simplement PDF::Builder comme prérequis pour exécuter un autre paquet. Tout ce que vous avez à faire est d'installer le paquet CPAN pour PDF::Builder, et il chargera les fichiers .pm dans votre bibliothèque Perl. Si l'autre paquet a PDF::Builder comme prérequis, son installateur peut télécharger et installer PDF::Builder automatiquement.
2.
Vous voulez écrire un programme Perl qui utilise les fonctions de PDF::Builder. En plus d'installer PDF::Builder depuis CPAN, vous voudrez sa documentation. Obtenez une copie du produit depuis GitHub (https://github.com/PhilterPaper/Perl-PDF-Builder) ou sous forme de fichier tar compressé depuis CPAN. Cela inclut un utilitaire pour construire (à partir de POD) une bibliothèque de documents HTML, ainsi que des exemples (répertoire examples/) et des programmes exemples contribués (répertoire contrib/).
3.
Vous voulez modifier les fichiers de PDF::Builder. En plus des distributions CPAN et GitHub, vous *pouvez* choisir de conserver un dépôt Git local pour suivre vos modifications. Selon que votre copie de PDF::Builder est utilisée ou non à des fins de production, vous pourriez vouloir faire vos modifications et tests dans l'installation de la bibliothèque Perl (*en direct*) ou dans un autre endroit. Les tests "t" (répertoire t/) et les exemples fournissent de bons tests de régression pour vous assurer que vous n'avez rien cassé. Si vous faites vos modifications sur le code en direct, n'oubliez pas, une fois terminé, de copier les modifications dans la version maître que vous conservez !
4.
Vous voulez contribuer au développement de PDF::Builder. Vous aurez besoin d'un dépôt Git local (et d'un compte GitHub), de sorte que lorsque vous aurez tout terminé, vous pourrez émettre une "Demande de Tirage" pour attirer notre attention. Nous ne pouvons garantir que votre travail sera incorporé au projet, mais au moins nous y jetterons un œil. De temps en temps, une nouvelle version CPAN sera publiée.

Si vous voulez apporter des changements substantiels pour une utilisation publique, et que vous ne parvenez pas à un accord avec nous, vous pouvez même démarrer votre propre projet GitHub et enregistrer un nouveau projet CPAN (c'est ce que nous avons fait, en *forkant* PDF::API2). S'il vous plaît, ne présumez pas que nous ne voulons pas de vos changements -- proposez au moins ce que vous voulez faire par écrit, afin que nous puissions l'examiner. Nous cherchons toujours des personnes pour aider et développer PDF::Builder.

Bibliothèques optionnelles

PDF::Builder peut utiliser certaines bibliothèques optionnelles, qui ne sont pas *requises* pour une installation réussie. Si vous souhaitez améliorer la vitesse et les capacités de certaines fonctions, vous pourriez vouloir installer et utiliser ces bibliothèques :

  • Graphics::TIFF

    PDF::Builder a hérité d'une bibliothèque d'images TIFF assez lente, buggée et limitée de PDF::API2. Si Graphics::TIFF (disponible sur CPAN, utilise libtiff.a) est installé, PDF::Builder l'utilisera à la place, sauf si vous spécifiez qu'il doit utiliser l'ancienne bibliothèque Perl pure. La seule fois où vous pourriez envisager cela est lorsque vous devez passer un descripteur de fichier ouvert à "image_tiff" au lieu d'un nom de fichier. Voir les rapports de bogues résolus RT 84665 et RT 118047, ainsi que "image_tiff", pour plus d'informations.

  • Image::PNG::Libpng

    PDF::Builder a hérité d'une bibliothèque d'images PNG Perl pure assez lente et buggée de PDF::API2. Si Image::PNG::Libpng (disponible sur CPAN, utilise libpng.a) est installé, PDF::Builder l'utilisera à la place, sauf si vous spécifiez qu'il doit utiliser l'ancienne bibliothèque Perl pure. L'utilisation de la nouvelle bibliothèque vous donnera une vitesse améliorée, la capacité d'utiliser des échantillons de 16 bits et la capacité de lire des fichiers PNG entrelacés. Voir le rapport de bogue résolu RT 124349, ainsi que "image_png", pour plus d'informations.

  • HarfBuzz::Shaper

    Cette bibliothèque permet à PDF::Builder de gérer les écritures complexes (arabe, devanagari, etc.) ainsi que les systèmes d'écriture non LTR. Elle est également utile pour les écritures latines et autres écritures simples, pour les ligatures et un meilleur crénage. HarfBuzz::Shaper est basé sur un ensemble de bibliothèques HarfBuzz, qu'il tentera de construire si elles ne sont pas trouvées. Voir "textHS" pour plus d'informations.

  • Text::Markdown

    Cette bibliothèque est utilisée si vous voulez formater du code de style "Markdown" dans PDF::Builder, via la méthode column(). Elle traduit un certain dialecte de Markdown en HTML, qui est ensuite traité davantage.

  • HTML::TreeBuilder

    Cette bibliothèque est utilisée pour formater l'entrée HTML en une structure de données que PDF::Builder peut interpréter, via la méthode column(). Notez que si une entrée Markdown est utilisée, elle nécessitera également HTML::TreeBuilder pour traiter le HTML auquel le Markdown est traduit.

  • Pod::Simple::XHTML

    Cette bibliothèque est utilisée si vous souhaitez générer la documentation HTML à partir de la source POD et PM, en utilisant "docs/buildDoc.pl". Notez que l'ensemble complet de la documentation peut également être trouvé en ligne à l'adresse https://www.catskilltech.com/FreeSW/product/PDF-Builder/title/PDF%3A%3ABuilder/freeSW_full sous le lien "Documentation". Cette documentation en ligne est mise à jour à chaque publication CPAN, mais pas nécessairement lors de la mise à jour du dépôt GitHub.

Notez que le processus d'installation ne tentera **pas** d'installer ces bibliothèques automatiquement. Si vous ne souhaitez pas en utiliser une ou plusieurs, vous êtes libre de ne pas installer la (les) bibliothèque(s) optionnelle(s). Si vous souhaitez utiliser une ou plusieurs d'entre elles, envisagez de les installer *avant* d'installer PDF::Builder, afin que tous les tests t et/ou exemples qui utilisent ces bibliothèques puissent être exécutés lors de l'installation et de la vérification de PDF::Builder. N'oubliez pas que vous pouvez *toujours* installer une bibliothèque optionnelle plus tard, si vous souhaitez l'utiliser.

Chaînes (Texte de caractères)

Perl, et donc PDF::Builder, utilise des chaînes qui prennent en charge toute la gamme des caractères Unicode. Lors de l'importation de chaînes dans un programme Perl, par exemple en lisant du texte à partir d'un fichier, vous devez être conscient de leur encodage de caractères. Les encodages sur un seul octet (l'encodage par défaut est 'latin1'), représentés par des octets de valeur 0x00 à 0xFF (0..255), produiront des résultats différents si vous faites quelque chose qui dépend de l'encodage, comme le tri, la recherche ou la comparaison de deux caractères non ASCII. Cela s'applique également à tous les caractères (texte) codés en dur dans le programme Perl.

Vous pouvez toujours décoder le texte depuis un encodage externe (ASCII, UTF-8, Latin-3, etc.) vers l'encodage Perl (interne) multibyte UTF-8. Cela utilise un à quatre octets pour représenter chaque caractère. Voir le pragma "utf8" et le module "Encode" pour les détails sur le décodage du texte. Notez que seuls les polices TrueType ("ttfont") peuvent utiliser directement du texte encodé en UTF-8. Les autres types de polices (core, T1, etc.) ne peuvent utiliser que du texte encodé sur un seul octet. Si votre texte est ASCII, Latin-1 ou CP-1252, vous *pouvez* simplement laisser les chaînes Perl avec l'encodage par défaut sur un seul octet.

Ensuite, il y a la question de l'encodage de la *sortie* pour correspondre aux jeux de caractères de polices disponibles. Vous n'êtes pas réellement en train de *traduire* le texte en sortie, mais vous indiquez au système de sortie (et au lecteur) quel encodage le flux d'octets de sortie représente, et quels glyphes de caractères ils devraient générer.

Si vous limitez votre texte à l'ASCII pur (valeurs d'octets 0x00 .. 0x7F) ou même à Latin-1 ou CP-1252 (valeurs d'octets 0x00 .. 0xFF), vous pouvez utiliser des chaînes Perl par défaut (non UTF-8) et utiliser l'encodage de sortie par défaut (WinAnsiEncoding), qui est plus ou moins Windows CP-1252 (lui-même un sur-ensemble de ISO-8859-1 Latin-1). Si votre texte utilise d'autres caractères, vous devrez être conscient de l'encodage de vos chaînes de texte (dans la chaîne Perl et pour déclarer la génération de glyphes de sortie). Voir "Core Fonts", "PS Fonts" et "TrueType Fonts" dans "FONT METHODS" pour des informations supplémentaires.

Ordre de rendu

Pour le meilleur ou pour le pire, pour des raisons de compatibilité, PDF::Builder continue le même modèle de rendu que celui utilisé par PDF::API2 (et potentiellement ses prédécesseurs). Cela signifie que tous les éléments graphiques pour un objet graphique sont placés dans une entrée, et toutes les sorties de texte pour un objet texte sont incluses dans une autre entrée. Lequel est affiché en premier ? C'est celui qui est déclaré en premier. Cela peut entraîner des résultats inattendus, où les éléments sont rendus dans un ordre (apparemment) inverse. C'est-à-dire que les éléments texte et graphiques ne sont pas nécessairement affichés dans le même ordre où ils ont été créés dans le code. Deux éléments au sein du même objet (par exemple, $text) seront rendus dans le même ordre où ils ont été codés, mais les éléments de différents objets ne seront pas nécessairement rendus dans l'ordre attendu. L'exemple suivant (code source et extraits PDF annotés) tentera d'illustrer le problème :

use strict;
use warnings;
use PDF::Builder;
# démontrer l'ordre des objets texte et graphique
#
my $fname = "objorder";
my $paper_size = "Letter";
# voir le contenu des flux texte et graphique
my $pdf = PDF::Builder->new(compress => 'none');
$pdf->mediabox($paper_size);

# régler le chemin d'accès pour votre système d'exploitation
my $fontTR = $pdf->ttfont('C:\\Windows\\Fonts\\timesbd.ttf');

La séparation du texte et des graphiques signifie que seules certaines méthodes de texte sont disponibles dans un objet graphique, et seules certaines méthodes graphiques sont disponibles dans un objet texte. Il y a beaucoup de chevauchements, mais ils diffèrent. Il n'y a vraiment aucune raison pour que le code n'ait pas pu être écrit (dans PDF::API2, ou plus tôt) comme sortant vers un seul objet, ce qui conserverait tout dans le même ordre que les appels de méthode. Un avantage serait moins de surcharge d'objets et de flux dans le fichier PDF. Le seul inconvénient pourrait être qu'un objet pourrait plus facilement déborder et nécessiter d'être divisé en plusieurs objets, mais cela devrait être rare.

Vous devriez toujours pouvoir diviser manuellement un objet en terminant simplement la sortie vers le premier objet et en continuant avec la sortie vers le second objet, tant qu'il a été créé immédiatement après le premier objet. L'état graphique à la fin du premier objet devrait être l'état initial au début du second objet. Cependant, soyez prudent lorsque vous traitez des objets texte -- la spécification PDF stipule que les matrices de texte ne sont pas reportées d'un objet à l'autre (BT les réinitialise), vous devrez donc peut-être réinitialiser certains paramètres.

$grfx1 = $page->gfx();
$grfx2 = $page->gfx();
# écrire une quantité énorme de choses dans $grfx1
# écrire une quantité énorme de choses dans $grfx2, reprenant là où $grfx1 s'est arrêté

Dans tous les cas, maintenant que vous comprenez l'ordre de rendu et comment l'ordre des déclarations d'objets l'affecte, le texte et les graphiques peuvent maintenant être complètement contrôlés comme vous le souhaitez. Il n'est vraiment pas nécessaire d'ajouter un autre type d'objet "mixte" qui gérera tous les objets graphiques et texte, car cela entraînerait probablement un gonflement majeur du code pour très peu de bénéfices. Cependant, cela pourrait être envisagé à l'avenir s'il existe un besoin démontré, tel qu'un gonflement sérieux de la taille des fichiers PDF dû à la surcharge d'objets supplémentaire lors de l'entrelacement de la sortie texte et graphique.

Il n'existe actuellement pas de mécanisme général pour les objets à usage mixte, mais un exemple limité est l'implémentation actuelle du soulignement, du barré et du surlignage du texte (dans la balise column()) ; qui sont effectués dans l'objet texte, sortant temporairement (ET) en mode graphique pour dessiner les lignes, puis revenant (BT) en mode texte. Cela a été fait afin que les ajustements de coordonnées de ligne de base puissent être facilement effectués. Étant donné que "BT" réinitialise certains paramètres de texte, cela doit être fait avec soin !

Notes sur le support des fonctionnalités par les lecteurs

Les lecteurs PDF sont des logiciels complexes, écrits par différents groupes à différents moments. Ainsi, ils peuvent différer dans la façon dont ils prennent en charge les fonctionnalités et gèrent le contenu non standard (c'est-à-dire qui ne respecte pas tout à fait les normes !). La plupart des lecteurs actuels prennent en charge toutes ou la plupart des fonctionnalités jusqu'à la version PDF 1.7, et certains prennent en charge les fonctionnalités PDF 2.x. Notez que PDF::Builder prend en charge le PDF 1.4 dans la plupart des cas, avec quelques fonctionnalités PDF 1.5 ajoutées. Presque tous les lecteurs actuels devraient (en théorie) prendre en charge n'importe quel PDF produit avec PDF::Builder.

Il n'existe pas d'implémentation de référence officielle d'un lecteur, bien qu'Adobe Acrobat Reader (AAR, téléchargeable gratuitement) soit si répandu qu'il est presque une norme de facto. Au moins, nous essayons de faire fonctionner PDF::Builder, ses tests et ses exemples sur AAR. Parfois, cela peut être difficile, par exemple, la gestion des opérateurs de sauvegarde (q) et de restauration (Q) dans un flux de texte. La norme PDF suggère en quelque sorte que ceux-ci s'appliquent uniquement au flux graphique, et ne devraient éventuellement pas apparaître dans un flux de texte. La plupart des lecteurs semblent simplement ignorer q et Q dans un flux de texte, et AAR semble généralement le faire, mais certaines combinaisons de taille de flux et de compression semblent déclencher un avertissement dans AAR lors du chargement ! Ce cas particulier est maintenant un point mort, car save() et restore() ont été rétablis comme des no-ops (avec un seul message d'avertissement s'ils sont trouvés) dans un flux de texte.

Il nous a été signalé que certains opérateurs de flux peuvent ne pas être strictement autorisés dans certaines parties d'un flux (en particulier certains opérateurs d'état graphique après le début de la construction du chemin). Aucun lecteur ne semble poser de problème à ce sujet pour le moment, mais les utilisateurs doivent être conscients que l'ordre de leurs appels PDF::Builder pourrait devoir être mis à jour à un moment donné, pour obtenir des PDF utilisables sur tous les lecteurs. Si nécessaire, nous ajouterons du code pour l'appliquer (ou au moins, pour avertir des problèmes potentiels). N'hésitez pas à signaler si vous constatez que de telles restrictions sont nécessaires.

Notez également que tous les filtres (y compris les méthodes de compression) ne peuvent pas être pris en charge sur tous les lecteurs. Par exemple, à l'heure actuelle, AAR (et un certain nombre d'autres lecteurs) ne prennent apparemment pas en charge la compression CCITT Group 4 Fax (pour certaines images TIFF). Cela fait toujours l'objet d'une enquête.

Versions PDF Supportées

Lors de la création d'un fichier PDF à l'aide des fonctions de PDF::Builder, la sortie est marquée comme PDF 1.4. Cela ne signifie pas que toutes les fonctionnalités PDF jusqu'à 1.4 sont prises en charge ! Il manque très probablement des fonctionnalités dès la norme PDF 1.0.

Le gros problème survient lorsqu'un PDF de version 1.5 ou supérieure est importé ou ouvert dans PDF::Builder. S'il contient du contenu qui n'est pas réellement pris en charge par ce logiciel, il y a une chance que quelque chose se casse. Cela ne garantit pas qu'un PDF marqué comme "1.7" tombera en flammes lorsqu'il sera lu par PDF::Builder, ou qu'un PDF réécrit se cassera dans un lecteur, mais la possibilité existe. De nombreux logiciels d'écriture de PDF marquent simplement leur sortie comme la version la plus élevée de PDF à l'époque (généralement 1.7), même s'il n'y a pas de contenu au-delà, disons, 1.2. Il y a une certaine gestion des éléments PDF 1.5 dans PDF::Builder, comme les flux de référence croisée, mais la prise en charge au-delà de 1.4 est très limitée. Tout ce que nous pouvons dire, c'est d'être prudent lors de la manipulation de PDF dont la version est supérieure à 1.4, et de tester en profondeur, car ils pourraient se casser à un moment donné.

PDF::Builder comprend un mécanisme simple de contrôle de version, où la version PDF initiale à produire (par défaut 1.4) peut être définie par le programmeur. Les PDF d'entrée supérieurs à 1.4 (niveau de sortie actuel) recevront un avertissement (qui peut être supprimé) indiquant que le niveau de sortie sera porté à ce niveau. L'utilisation de fonctionnalités PDF supérieures au niveau de sortie actuel déclenchera également un avertissement indiquant que le niveau de sortie doit être porté au niveau nécessaire. Si cela n'est pas souhaité, vous devez éviter d'utiliser les fonctionnalités PDF qui sont supérieures au niveau de sortie PDF souhaité.

Historique

PDF::API2 a été initialement écrit par Alfred Reibenschuh, dérivé de Text::PDF de Martin Hosken via l'encapsulation Text::PDF::API. En 2009, Otto Hirr a commencé le fork PDF::API3, mais il n'a jamais abouti. En 2011, la maintenance de PDF::API2 a été reprise par Steve Simms. En 2017, PDF::Builder a été forké par Phil M. Perry, qui souhaitait un calendrier de nouvelles fonctionnalités et de corrections de bugs plus agressif que celui fourni par Simms, bien que certains travaux de Simms aient été portés depuis PDF::API2.

Selon la présentation d'Alfred Reibenschuh de 2005 intitulée "pdfapi2_for_fun_and_profit_APW2005.pdf" (sur http://pdfapi2.sourceforge.net, un site non maintenu), l'historique de PDF::API2 (le prédécesseur de PDF::Builder) est le suivant :

  • Premier code implémenté basé sur PDFlib-0.6 (AFPL)
  • Passage à Text::PDF avec une réécriture complète en Text::PDF::API (procédural)
  • Code non maintenable déclenchant une réécriture dans un nouvel espace de noms PDF::API2 (orienté objet, LGPL)
  • Structure d'objet rationalisée en 0.4x

À la demande de Simms, le nom de la nouvelle offre a été changé de PDF::API4 à PDF::Builder, afin de réduire le risque de confusion due au développement parallèle. L'intention de Perry est de maintenir toutes les méthodes internes aussi compatibles que possible avec PDF::API2, bien qu'il soit probable qu'il y ait une certaine dérive (incompatibilités) au fil du temps. Au moins initialement, tout programme écrit basé sur PDF::API2 devrait être convertible en PDF::Builder simplement en changeant "API2" partout où il apparaît en "Builder". Voir le fichier d'incompatibilités connues INFO/KNOWN_INCOMP pour plus d'informations.

Vérification d'intégrité

Les méthodes de PDF::Builder qui ouvrent un fichier PDF existant, le passent par la méthode de vérification d'intégrité, "$self->IntegrityCheck(level, content)". Cette méthode sert deux objectifs : 1) trouver tous les paramètres "/Version" qui remplacent la version PDF trouvée dans l'en-tête PDF, et 2) effectuer des validations de base sur le contenu du PDF.

Le paramètre "level" accepte les valeurs suivantes :

0
Ne pas afficher de messages de diagnostic ; retourner uniquement tout remplacement de version.
1
Afficher les messages de diagnostic de niveau erreur (grave), ainsi que retourner tout remplacement de version.

Les erreurs incluent, aucun objet /Root n'a été spécifié, ou s'il l'a été, l'objet indiqué n'a pas été trouvé. Un objet revendique un autre objet comme enfant (/Kids list), mais un autre objet a déjà revendiqué cet enfant. Un objet revendique un enfant, mais cet enfant n'a pas de Parent, ou l'enfant a un Parent différent.

2
Afficher les messages de diagnostic de niveau erreur (grave) et avertissement (moins grave), ainsi que retourner tout remplacement de version. C'est la valeur par défaut.
3
Afficher les messages de diagnostic de niveau erreur (grave), avertissement (moins grave) et note (informationnel), ainsi que retourner tout remplacement de version.

Les notes incluent, aucun objet /Info (facultatif) n'a été spécifié, ou s'il l'a été, l'objet indiqué n'a pas été trouvé. Un objet a été référencé, mais aucune entrée correspondante n'a été trouvée parmi les objets. (Cela peut être acceptable si l'objet n'est pas défini, ou s'il est sur la liste libre, car la référence sera alors ignorée.) Un objet est défini, mais il semble qu'aucun autre objet ne le référence.

4
Afficher les messages de diagnostic de niveau erreur, avertissement et note, ainsi que retourner tout remplacement de version. Afficher également la structure de données de diagnostic.
5
Afficher les messages de diagnostic de niveau erreur, avertissement et note, ainsi que retourner tout remplacement de version. Afficher également la structure de données de diagnostic et la structure de données $self (généralement utile uniquement si vous avez déjà lu le fichier PDF).

La version est une chaîne de caractères (par exemple, '1.5') si elle est trouvée, sinon "undef" (valeur indéfinie) est retournée.

Pour contrôler l'appel « automatique » à IntegrityCheck (via opens), le niveau peut être donné avec l'option (flag) "diaglevel => n", où "n" est compris entre 0 et 5.

MÉTHODES "BOX"

Remarque générale : Soyez prudent si vous spécifiez un Media Box (ou un autre "box") différent pour une page que le réglage global du "box", afin de définir toute la "chaîne" des boîtes sur la page, pour éviter les surprises. Par exemple, définir un Media Box global (taille du papier) et un Crop Box global, puis définir un nouveau Media Box au niveau de la page *sans* définir de nouveau Crop Box au niveau de la page, peut donner des résultats inattendus en matière de recadrage. De telles combinaisons ne sont pas bien définies.

Toutes les dimensions dans les boîtes utilisent par défaut l'unité d'utilisateur par défaut, qui est le point (1/72 pouce). Notez que la spécification PDF limite les tailles et les coordonnées à 14400 unités d'utilisateur (200 pouces, pour l'unité d'utilisateur par défaut d'un point). Les produits Adobe (jusqu'à présent) respectent cette limite pour Acrobat et Distiller. Il est utile de noter que d'autres générateurs et lecteurs PDF peuvent choisir d'ignorer la limite de 14400 unités, avec ou sans l'utilisation d'une unité d'utilisateur spécifiée. Par conséquent, PDF::Builder n'applique aucune limite aux coordonnées -- il vous incombe de considérer quels lecteurs et autres outils PDF peuvent être utilisés avec un PDF que vous produisez ! Notez également que les lecteurs Acrobat plus anciens avaient des limites de coordonnées aussi basses que 3240 unités d'utilisateur (45 pouces), et une taille *minimale* de média de 72 ou 3 unités d'utilisateur.

Unités d'utilisateur (userunit)

$pdf->userunit($nombre)
L'unité d'utilisateur par défaut dans le système de coordonnées PDF est un point (1/72 pouce). Vous pouvez la considérer comme un facteur d'échelle pour permettre des documents plus grands (ou même plus petits). Cette méthode peut être utilisée (pour PDF 1.6 et versions ultérieures) pour définir l'unité d'utilisateur à un certain nombre de points. Par exemple, userunit(72) définira le multiplicateur d'échelle à 72.0 points par unité d'utilisateur, soit 1 pouce par unité d'utilisateur. Tout nombre supérieur à zéro est acceptable, bien que certains lecteurs et outils puissent ne pas bien gérer les unités d'utilisateur inférieures à 1.0.

Tous les lecteurs ne respectent pas l'unité d'utilisateur, si vous en fournissez une, ou ne la gèrent pas exactement de la même manière. Adobe Distiller, par exemple, ne l'utilise pas. La manière dont les unités d'utilisateur sont gérées peut varier d'un lecteur à l'autre. Adobe Acrobat, à l'heure actuelle, respecte l'unité d'utilisateur dans les versions 7.0 et supérieures, mais la limite à 75000 (ce qui donne une taille de document maximale de 15 millions de pouces, soit 236,7 miles ou 381 km). D'autres lecteurs et outils PDF peuvent autoriser une limite plus grande (ou plus petite).

Vos résultats peuvent varier : Certains lecteurs ignorent un réglage global de l'unité d'utilisateur et ne les font pas hériter par les pages (PDF::Builder les duplique sur chaque page pour simuler l'héritage). Certains lecteurs peuvent émettre des avertissements erronés sur du contenu tronqué lorsqu'un Media Box est modifié alors que des unités d'utilisateur sont utilisées. Certains lecteurs font des choses étranges avec les Crop Boxes lorsqu'une unité d'utilisateur est en vigueur.

Selon le lecteur utilisé, l'effet d'une unité d'utilisateur plus grande (supérieure à 1) peut signifier une résolution plus faible (apparence plus grossière ou plus rêche) dans le document rendu. Si vous imprimez quelque chose de la taille d'un panneau d'affichage autoroutier, cela peut ne pas vous importer, mais vous devriez être conscient de cette possibilité (même avec des coordonnées fractionnaires). Inversement, une unité d'utilisateur inférieure à 1.0 (si elle est autorisée) réduit la taille autorisée de votre document, mais *peut* entraîner une résolution plus élevée.

Un réglage global de l'unité d'utilisateur (niveau PDF) est hérité par chaque page (une action de PDF::Builder, pas nécessairement automatique par le lecteur), ou peut être remplacé en appelant userunit dans la page. Ne donnez pas plus d'un réglage global de userunit, car seul le dernier sera utilisé. La définition de l'unité d'utilisateur d'une page (si "$page->" au lieu) est autorisée (remplaçant le réglage global pour cette page). Cependant, de nombreuses sources déconseillent de le faire, car les résultats peuvent ne pas être ceux attendus (encore une fois, selon les particularités du lecteur).

N'oubliez pas d'appeler "userunit" *avant* d'appeler quoi que ce soit concernant les tailles de page ou de boîte, ou les coordonnées. Surtout lors de la définition des tailles de boîte 'nommées', les méthodes doivent connaître l'unité d'utilisateur actuelle afin que les tailles de page nommées (en points) puissent être mises à l'échelle vers l'unité d'utilisateur actuelle.

Media Box (mediabox)

$pdf->mediabox($nom)
$pdf->mediabox($nom, orient => 'orientation' )
$pdf->mediabox($l,$h)
$pdf->mediabox($llx,$lly, $urx,$ury)
($llx,$lly, $urx,$ury) = $pdf->mediabox()
Définit le Media Box global (ou le Media Box de la page, si "$page->" au lieu). Ceci définit la largeur et la hauteur (ou par coordonnées d'angle, ou par nom standard) de la page de sortie elle-même, comme la taille physique du papier. C'est normalement la plus grande des "boîtes". Si une boîte subsidiaire (à l'intérieur) dépasse la boîte média, la partie du matériel ou des boîtes à l'extérieur de la boîte média sera ignorée. C'est-à-dire que la boîte média est La Boîte Qui Gouverne Toutes les Autres et est la limite globale pour les autres boîtes (certaines documentations font référence à la boîte média comme "coupant" les autres boîtes). De plus, la boîte média définit le *système de coordonnées* global pour les opérations de texte et de graphisme.

Si aucun argument n'est donné, les coordonnées du Media Box actuel (global ou de page) sont retournées à la place. L'ancienne fonction "get_mediabox" (page uniquement) a été dépréciée et supprimée. De plus, lors de la *définition* du Media Box, les coordonnées résultantes sont retournées. Cela vous permet de spécifier la taille de la page par un nom (alias) et d'obtenir les dimensions en retour, le tout en un seul appel.

Notez que de nombreuses imprimantes ne peuvent *pas* imprimer jusqu'au bord physique du papier, vous devez donc prévoir de laisser une marge blanche, même en dehors de toute marque de coupe et de fond perdu. Les imprimantes et les lecteurs à l'écran sont libres de supprimer tout contenu trouvé en dehors du Media Box, et les imprimantes peuvent supprimer une partie du matériel juste à l'intérieur du Media Box.

Un Media Box *global* est *requis* par la spécification PDF ; s'il n'est pas explicitement donné, PDF::Builder définira le Media Box global à la taille US Letter (8,5 pouces x 11 pouces). C'est la taille du média qui sera utilisée pour toutes les pages si vous ne spécifiez pas d'appel "mediabox" sur une page. C'est-à-dire qu'un réglage de mediabox global (niveau PDF) est hérité par chaque page, ou peut être remplacé en réglant mediabox dans la page. Ne donnez pas plus d'un réglage global de mediabox, car seul le dernier sera utilisé.

Si vous donnez un nom de chaîne unique (par exemple, 'A4'), vous pouvez facultativement ajouter une orientation pour faire tourner la page de 90 degrés en mode Paysage : "orient => 'L'" ou "orient => 'l'". "orient" est la seule option reconnue, et une chaîne commençant par 'L' ou 'l' (pour Paysage) est la seule valeur intéressante (tout le reste est traité comme un mode Portrait). L'axe *y* va toujours de 0 en bas de la page jusqu'à ce qui était la *largeur* de la page (maintenant, la *hauteur*) en haut, et de même pour l'axe *x* : 0 à gauche jusqu'à l'ancienne *hauteur* à droite. C'est-à-dire que le système de coordonnées est le même qu'auparavant, sauf que la hauteur et la largeur sont différentes.

Le coin inférieur gauche n'est *pas obligé* d'être 0,0. Il peut s'agir de toutes les valeurs que vous souhaitez, y compris des valeurs négatives (tant que les côtés du média résultant ont au moins un point de long). "mediabox" définit le système de coordonnées (y compris l'origine) des graphiques et du texte qui seront dessinés, ainsi que pour les "boîtes" ultérieures. Il est même possible de donner deux coins opposés quelconques (comme le coin supérieur gauche et le coin inférieur droit). Le système de coordonnées sera réorganisé (par le Lecteur) pour être toujours le minimum conventionnel "x" et "y" en bas à gauche (c'est-à-dire que vous ne pouvez pas faire en sorte que "y" augmente de haut en bas !).

Exemple :

$pdf = PDF::Builder->new();
$pdf->mediabox('A4'); # Taille A4 (595 points de large par 842 points de haut)
...
$pdf->saveas('notre/nouveau.pdf');
$pdf = PDF::Builder->new();
$pdf->mediabox(595, 842); # Taille A4, avec un coin inférieur gauche implicite de 0,0
...
$pdf->saveas('notre/nouveau.pdf');
$pdf = PDF::Builder->new;
$pdf->mediabox(0, 0, 595, 842); # Taille A4, avec un coin inférieur gauche explicite de 0,0
...
$pdf->saveas('notre/nouveau.pdf');
Consultez le code source de PDF::Builder::Resource::PaperSizes pour la liste complète des noms pris en charge (alias) et leurs dimensions en points. Vous êtes libre d'ajouter des tailles de papier supplémentaires à ce fichier, si vous le souhaitez. Vous pourriez vouloir le faire si vous utilisez fréquemment une taille de page standard en mode paysage (rotatif). Voir également l'appel "getPaperSizes" dans PDF::Builder::Util.
Ces noms (alias) sont également utilisables dans d'autres appels de "boîte", bien qu'utiles uniquement si la "boîte" a la même taille que le média complet (Media Box), et que cela ne vous dérange pas qu'ils commencent à 0,0.

Crop Box (cropbox)

$pdf->cropbox($name)
$pdf->cropbox($name, orient => 'orientation')
$pdf->cropbox($w,$h)
$pdf->cropbox($llx,$lly, $urx,$ury)
($llx,$lly, $urx,$ury) = $pdf->cropbox()
Définit la Crop Box globale (ou la Crop Box de la page, si "$page->" est utilisé à la place). Ceci définira la taille du média à laquelle la sortie sera ultérieurement découpée. Notez que cela ne produit pas en soi de marques de coupe pour guider la découpe du papier ! Les lecteurs PDF doivent considérer ceci comme la portion visible de la page, et tout ce qui se trouve à l'extérieur peut être découpé (invisible). Par défaut, elle est égale à la Media Box, mais peut être définie pour être plus petite, dans le système de coordonnées défini par la Media Box. Un réglage global sera hérité par chaque page, mais peut être remplacé sur une base par page.

Un lecteur ou une imprimante peut choisir de supprimer toute partie découpée (invisible) de la page, et d'afficher uniquement la zone à l'intérieur de la Crop Box. Par exemple, si votre Media Box de page est A4 (0,0 à 595,842 Points), et votre Crop Box est (100,100 à 495,742), un lecteur comme Adobe Acrobat Reader peut vous montrer une page de 395 par 642 Points (c'est-à-dire, juste la zone visible de votre page). D'autres lecteurs peuvent vous montrer la taille complète du média (Media Box) et une zone blanche de 100 Points de large (dans cet exemple) autour du contenu visible.

Si aucun argument n'est donné, les coordonnées actuelles de la Crop Box (globale ou de page) sont renvoyées à la place. La fonction précédente "get_cropbox" (page uniquement) était dépréciée et a été supprimée. Si aucune Crop Box n'a été définie, les coordonnées de la Media Box (qui existent toujours) seront renvoyées à la place. De plus, lors de la définition de la Crop Box, les coordonnées résultantes sont renvoyées. Cela vous permet de spécifier la crop box par un nom (alias) et d'obtenir les dimensions en retour, le tout en un seul appel.

Ne confondez pas la Crop Box avec la "Trim Box", qui indique où le papier imprimé est censé être réellement découpé. Certains lecteurs PDF peuvent réduire l'arrière-plan "papier" visible à la taille de la crop box ; d'autres peuvent simplement omettre tout contenu extérieur à celle-ci. Dans un cas comme dans l'autre, vous perdriez toutes les marques de coupe ou d'impression, les instructions d'impression, les points d'alignement des couleurs ou tout autre contenu en dehors de la Crop Box. Une bonne utilisation de la Crop Box serait de limiter l'impression à la zone où une imprimante peut fiablement déposer de l'encre, et de laisser blancs les bords où les mécanismes de manipulation du papier empêchent l'application d'encre ou de toner. Cela vous éviterait de placer accidentellement du contenu précieux dans une zone où une imprimante refusera d'imprimer, tout en vous permettant d'inclure une zone de fond perdu et de l'espace pour les marques et instructions de l'imprimeur. Inutile de dire que si votre imprimante ne peut pas imprimer jusqu'au bord du papier, vous devrez découper (couper) les feuilles imprimées pour obtenir de vrais fonds perdus.

Un réglage de cropbox global (niveau PDF) est hérité par chaque page, ou peut être remplacé en définissant cropbox au niveau de la page. Comme avec "mediabox", une seule crop box peut être définie à ce niveau (PDF). Comme avec "mediabox", une taille de média nommée peut avoir une orientation (l ou L) pour le mode Paysage. Notez que la Crop Box globale au niveau PDF sera utilisée même si la page obtient sa propre Media Box. C'est-à-dire, la Crop Box de la page hérite de la Crop Box globale, pas de la Media Box de la page, même si la page a sa propre taille de média ! Si vous définissez votre propre Media Box de page, vous devriez envisager de définir également explicitement la Crop Box de la page (et les autres boîtes).

Bleed Box (bleedbox)

$pdf->bleedbox($name)
$pdf->bleedbox($name, orient => 'orientation')
$pdf->bleedbox($w,$h)
$pdf->bleedbox($llx,$lly, $urx,$ury)
($llx,$lly, $urx,$ury) = $pdf->bleedbox()
Définit la Bleed Box globale (ou la Bleed Box de la page, si "$page->" est utilisé à la place). Ceci est typiquement utilisé pour l'impression sur papier, où vous voulez que l'encre ou la couleur (comme les onglets) soit imprimée un peu au-delà de la taille finale du papier, pour s'assurer que le papier découpé saigne (la coupe passe à travers l'encre), plutôt que de laisser accidentellement du papier blanc visible à l'extérieur. Laissez suffisamment de "fond perdu" au-delà de la ligne de coupe attendue pour tenir compte des variations mineures dans la manipulation du papier, le pliage et la découpe ; pour éviter de montrer du papier blanc sur le bord. La Bleed Box est là où l'impression pourrait réellement s'étendre ; la Trim Box est normalement à l'intérieur, où le papier serait effectivement découpé. La valeur par défaut est égale à la Crop Box, mais est souvent un peu plus petite. L'espace entre la Bleed Box et la Crop Box est disponible pour les instructions de l'imprimeur, les points d'alignement des couleurs, etc., tandis que les marques de coupe (guides de coupe) sont au moins partiellement à l'intérieur de la zone de fond perdu (et devraient être imprimées après le contenu).

Si aucun argument n'est donné, les coordonnées actuelles de la Bleed Box (globale ou de page) sont renvoyées à la place. La fonction précédente "get_bleedbox" (page uniquement) était dépréciée et a été supprimée. Si aucune Bleed Box n'a été définie, les coordonnées de la Crop Box (si elles sont définies) seront renvoyées, sinon les coordonnées de la Media Box (qui existent toujours) seront renvoyées. De plus, lors de la définition de la Bleed Box, les coordonnées résultantes sont renvoyées. Cela vous permet de spécifier la bleed box par un nom (alias) et d'obtenir les dimensions en retour, le tout en un seul appel.

Comme avec "mediabox", une seule bleed box peut être définie à ce niveau (PDF). Comme avec "mediabox", une taille de média nommée peut avoir une orientation (l ou L) pour le mode Paysage. Notez que la Bleed Box globale au niveau PDF sera utilisée même si la page obtient sa propre Crop Box. C'est-à-dire, la Bleed Box de la page hérite de la Bleed Box globale, pas de la Crop Box de la page, même si la page a sa propre taille de média ! Si vous définissez votre propre Media Box ou Crop Box de page, vous devriez envisager de définir également explicitement la Bleed Box de la page (et les autres boîtes).

Utilisation suggérée des boîtes

Voir "examples/Boxes.pl" pour un exemple d'utilisation des boîtes.

La façon dont vous définissez vos boîtes (ou laissez les valeurs par défaut) dépend de vous, selon que vous imprimez en recto-verso en format US Letter ou A4 sur votre imprimante laser, à relier en spirale sur la marge de reliure, ou que vous engagez un imprimeur professionnel. Dans ce dernier cas, discutez à l'avance avec l'entreprise d'impression de leurs capacités (et limitations) et des informations dont ils ont besoin à partir d'un fichier PDF. Par exemple, ils peuvent ne pas vouloir qu'une Crop Box soit définie, et demander des tailles de boîtes très spécifiques. Pour de grandes séries d'impression, ils peuvent imprimer plusieurs pages (N-up) en recto-verso sur de grandes bobines "signatures", qui sont ensuite pliées et

guillotinées (rogner) et reliées en livres ou magazines. Vous fourniriez normalement juste un PDF avec toutes les pages ; ils s'occuperaient de la mise en page des cahiers (qui inclut les décalages et les rotations de 180 degrés).

(Soit dit en passant, ne comptez pas sur une imprimerie commerciale pour avoir une police particulière disponible, alors assurez-vous de demander. Généralement, ils voudront que vous incorporiez toutes les polices utilisées, mais demandez d'abord, et double-vérifiez avant de remettre le travail d'impression ! Les polices TTF/OTF (ttfont()) sont incorporées par défaut, mais d'autres polices (core, ps, bdf, cjk) ne le sont pas ! Une imprimerie *peut* avoir une collection de polices de base, mais elle est libre de substituer une police "similaire" à une police de base donnée, et les résultats peuvent ne pas correspondre à ce que vous avez vu sur votre PC !)

En supposant que vous utilisez une imprimante laser ou jet d'encre à feuille unique (US Letter ou A4), avez-vous l'intention de rogner chaque feuille à une taille finale plus petite ? Si c'est le cas, vous pouvez réaliser de vrais fonds perdus en définissant une Trim Box et une Bleed Box légèrement plus grande. Vous imprimeriez les fonds perdus (jusqu'au bord fini) jusqu'à la Bleed Box, mais rien n'est imposé concernant la Bleed Box. À l'autre extrémité du spectre, vous définiriez la Media Box à la taille du papier physique imprimé. La plupart des imprimantes réservent un peu d'espace sur les côtés (et éventuellement en haut et en bas) pour la manipulation du papier, il est donc souvent bon de définir votre Crop Box comme la zone imprimable. N'oubliez pas que la Media Box définit le système de coordonnées utilisé, vous devez donc toujours éviter de sortir de la Crop Box avec du contenu (la plupart des lecteurs et imprimantes n'afficheront aucune encre en dehors de la Crop Box). Que vous définissiez ou non une Crop Box, vous vous retrouverez presque toujours avec du papier blanc au moins sur les côtés.

Pour les petits travaux internes, vous n'aurez probablement pas besoin de repères de couleur et d'autres instructions et informations professionnelles entre la Bleed Box et la Crop Box, mais les repères de coupe pour le rognage (si utilisés) doivent aller juste à l'extérieur de la Trim Box (partiellement ou entièrement à l'intérieur de la Bleed Box), et être dessinés *après* tout le contenu. Si vous ne rognez pas le papier, n'essayez pas d'effets de fond perdu (y compris des pages/couvertures avec une couleur de fond unie), car vous aurez généralement un bord blanc de toute façon (les imprimantes laissent un passage propre et sec pour les rouleaux d'entraînement). Ne vous attendez pas à ce qu'un document PDF ne soit jamais physiquement imprimé, et pas seulement affiché (où vous pouvez faire des choses comme des fonds perdus jusqu'au bord du média). Enfin, pour l'impression à feuille unique, une Art Box est probablement inutile, mais si vous combinez des pages en impressions N-up, ou effectuez d'autres manipulations, elle peut être utile.

Héritage des boîtes

Les Media, Crop, Bleed, Trim et Art Boxes qu'une page reçoit peuvent être un peu compliquées. Notez que généralement, seules les Media et Crop Boxes auront un effet visuel clair. L'effet visuel des autres boîtes (le cas échéant) peut être très subtil.

Premièrement, tout est défini au niveau global (PDF). La Media Box est toujours définie et est par défaut US Letter (8,5 pouces de large par 11 pouces de haut). La Crop Box globale hérite de la Media Box, sauf si elle est explicitement définie. Les Bleed, Trim et Art Boxes héritent de la Crop Box, sauf si elles sont explicitement définies. Une boîte globale ne doit être définie qu'une seule fois, car la dernière définie est celle qui sera écrite dans le PDF !

Deuxièmement, une page hérite des boîtes globales, pour ses réglages initiaux. Vous pouvez appeler l'une des méthodes de définition de boîte ("cropbox", "trimbox", etc.) pour définir explicitement (remplacer) toute boîte pour *cette* page. Notez que la définition d'une nouvelle Media Box pour la page ne réinitialise *pas* la Crop Box de la page -- elle utilise toujours ce qu'elle a hérité de la Crop Box globale. Vous devrez définir explicitement la Crop Box de la page si vous souhaitez un réglage différent. De même, les Bleed, Trim et Art Boxes de la page ne seront pas réinitialisées par une nouvelle Crop Box de page -- elles hériteront toujours des réglages globaux (PDF).

Troisièmement, la Media Box de la page (celle réellement utilisée pour les pages de sortie) rogne ou limite toutes les autres boîtes pour qu'elles ne dépassent pas sa taille. Par exemple, si la Media Box est US Letter, et que vous définissez une Crop Box de taille A4, la plus petite des deux hauteurs (11 pouces) sera effective, et la plus petite des deux largeurs (8,26 pouces, 595 points) sera effective. Les dimensions *données* d'une boîte sont retournées lors de la requête (get), pas les dimensions *effectives* rognées par la Media Box.

Plan (Marque-pages)

Il est possible de créer des *plans* (également appelés *marque-pages*) dans un document PDF. Vous n'êtes pas limité aux pages entières comme destinations, mais vous pouvez ajuster la dest() de destination pour afficher une partie spécifique d'une page.

Simple ensemble de plan à un niveau

Insère trois plans (au même niveau) dans une liste simple de 12 pages (exemple 055_outlines) :

my $doc = PDF::Builder-> open($infile);
$doc-> outlines
    -> outline
        -> dest( $doc-> openpage( 1 ))
        -> title( '1ère page (i)' );
$doc-> outlines
    -> outline
        -> dest( $doc-> openpage( 4 ))
        -> title( '4ème page (1)' );
$doc-> outlines
    -> outline
        -> dest( $doc-> openpage( 11 ))
        -> title( '11ème page (7)' );

dest() est par défaut un lien vers une page entière (donnée comme numéro de page ordinal, *pas* le numéro de page formaté du document). Le title() est ce que vous voyez dans la section Plan ou Marque-pages de votre lecteur PDF.

Un exemple de plan à plusieurs niveaux

Il est également possible de définir des plans imbriqués (à plusieurs niveaux). Pour le même ensemble de pages que ci-dessus, nous ajouterons deux pages imbriquées sous la page *i* et trois pages imbriquées sous la page *1*. Notez qu'il est courant de faire des *sections* de niveau supérieur (par exemple, *préface, corps, fin de matière*) et de placer toutes les pages réelles sous elles, mais vous devez toujours faire en sorte que chaque "en-tête" de section pointe vers une page réelle. Ainsi, *préface* pourrait pointer vers la page *i*, et avoir des plans pour *i, ii,* et *iii* imbriqués en dessous.

my $doc = PDF::Builder-> open($infile);
my $root =  # Objet Outlines (racine de l'ensemble)
    $doc-> outlines();
my $top0 =  # Objet Outline au niveau supérieur, initialement réduit (fermé)
$root -> outline($root)
        -> is_open(0)        
        -> dest( $doc-> openpage( 1 ))
        -> title( '1ère page (i)' );
my $top1 =  # Objet Outline au niveau supérieur
$root -> outline($root)
        -> dest( $doc-> openpage( 4 ))
        -> title( '4ème page (1)' );
my $top2 =  # Objet Outline au niveau supérieur. Pas d'enfants
$root -> outline($root)
        -> dest( $doc-> openpage( 11 ))
        -> title( '11ème page (7)' );
# ajouter les signets de niveau inférieur ici. il n'y a aucune raison qu'ils ne puissent pas être
# mélangés avec les niveaux supérieurs ci-dessus, à condition qu'ils viennent après
# que leur parent soit défini.
# deux pages sous la première page de niveau supérieur (i)
$top0 -> outline($top0)
          -> dest( $doc-> openpage( 2 ))
          -> title( '2ème page (ii)' );

$top0 -> outline($top0)
          -> dest( $doc-> openpage( 3 ))
          -> title( '3ème page (iii)' );
# trois pages sous la deuxième page de niveau supérieur (1). la troisième est
# insérée après la première et avant la deuxième.
my $first =
$top1 -> outline($top1)
          -> dest( $doc-> openpage( 5 ))
          -> title( '5ème page (2)' );

$top1 -> outline($top1)
          -> dest( $doc-> openpage( 6 ))
          -> title( '6ème page (3)' );

$first -> insert_after()
          -> dest( $doc-> openpage( 7 ))
          -> title( '7ème page (4)' );

Il est possible de définir un seul plan (lien) comme *fermé*, auquel cas tous les plans imbriqués en dessous seront masqués (avec un curseur "fermé"). Essayez d'éviter de dépasser deux niveaux de profondeur (un niveau d'imbrication), car la colonne Plans/Marque-pages est généralement assez étroite.

MÉTHODES DE POLICE

Polices de base

Ce sont les polices "intégrées", dans le sens où tout lecteur PDF est garanti de les fournir et de les prendre en charge. Les *métriques* des polices prises en charge sont livrées avec PDF::Builder, mais pas les polices elles-mêmes.

Les polices de base sont limitées aux *encodages à octet unique*. L'encodage par défaut pour les polices de base est WinAnsiEncoding (environ le sur-ensemble CP-1252/Windows-1252 de ISO-8859-1/Latin-1). Voir l'option "encode" ci-dessous pour changer cet encodage.

Il existe environ 14 polices de base (variantes normal, *italique*, **gras**, et **_gras italique_** pour Times [serif], Helvetica [sans serif], Courier [à pas fixe] ; plus deux polices symboles, Symbol et Zapf Dingbats) qui sont censées être disponibles sur n'importe quel lecteur PDF, **bien que d'autres polices avec des métriques très similaires soient souvent substituées.**

Les machines Windows disposent de 14 polices "de base" supplémentaires (15 si l'on compte Bank Gothic) : Georgia [serif], Verdana [sans serif], et Trebuchet [sans serif] en 4 variantes chacune, ainsi que Webdings et Wingdings). Celles-ci sont *généralement* disponibles sur une plateforme Windows (mais pas garanties !). Elles ne sont généralement pas installées par défaut sur les plateformes Linux, Mac et autres plateformes non Windows, alors soyez prudent si vous spécifiez ces polices.

Exemples

$font1 = $pdf->corefont('Times-Roman', encode => 'latin2');
$font2 = $pdf->corefont('Times-Bold');
$font3 = $pdf->corefont('Helvetica');
$font4 = $pdf->corefont('ZapfDingbats');

Les polices de base peuvent également être demandées via la méthode font()

$font5 = $pdf->font('Courier-Oblique');

ainsi qu'être intégrées dans FontManager

$font6 = $pdf->get_font('face'=>'Times', 'italic'=>1, 'bold'=>0);

Notes et limitations

  • Vous *ne pouvez pas* utiliser d'encodages UTF-8 ou d'autres encodages multibytes avec les polices de base, *seulement* des encodages à octet unique (256 caractères maximum). Un lecteur PDF ne sait tout simplement pas quoi faire d'un caractère multibyte, et le rendra probablement comme une séquence de caractères uniques (produisant des erreurs). Bien que la plupart des encodages à octet unique, du moins pour les langues européennes, soient pris en charge, il est possible que vous rencontriez un encodage qui inclut un caractère *non* trouvé dans un fichier de police donné, ou vice-versa (la police inclut des caractères auxquels l'encodage ne vous donne pas accès).
  • Ne confondez pas les points de code Unicode (comme ceux donnés avec une entité HTML) avec les valeurs à octet unique ou les caractères multibytes. La seule façon d'accéder à un caractère défini pour un encodage donné est avec une valeur d'*octet unique* dans la plage de 0 à 255. Par exemple, si vous ne pouvez pas taper directement un symbole "Euro", il s'agit de "\x80" dans de nombreux encodages -- vous l'utiliseriez à la place du point de code Unicode "\x{20AC}" ou "x\{E282AC}" UT
F-8 chaîne d'octets. Il s'agit de fournir une valeur d'octet unique que le lecteur PDF peut rechercher dans sa définition de police pour obtenir le caractère souhaité. Si le symbole "Euro" n'est pas présent dans le codage que vous utilisez, vous vous créerez des problèmes. Soyez conscient du système d'exploitation (système de fichiers) et de l'éditeur que vous utilisez pour votre codage lorsque vous créez un fichier avec votre texte pour le convertir en PDF ! Si vous avez tapé un "Euro" mais qu'il se trouve, par exemple, dans une chaîne d'octets UTF-8 dans le fichier, vous n'obtiendrez probablement pas un "Euro" dans votre PDF. Note : Les polices de type 1 utilisent des listes fixes de caractères attendus, ainsi que des métriques telles que leur largeur. Cela ne correspond pas toujours exactement à ce qu'utilise le fichier de police local du lecteur PDF. C'est généralement assez proche, mais dans plusieurs cas, des différences ont été constatées dans la liste des caractères entre les polices de type 1 et différents fichiers de police locaux, alors gardez cela à l'esprit. Il n'y a aucune garantie que tous les caractères (codes de point) trouvés dans un codage sur un seul octet se retrouvent dans un autre, ni que les métriques soient disponibles pour tous les caractères couverts par un codage sur un seul octet donné. Si vous écrivez en anglais, ou même dans plus de langues occidentales, ce n'est généralement pas un problème pour les polices de type 1, mais cela peut l'être pour d'autres langues et alphabets. Vous devez également être conscient qu'un lecteur PDF peut remplacer une autre police similaire (mais pas nécessairement identique) à la police demandée. Par exemple, sur les machines Windows, ils remplacent souvent "Arial" par "Helvetica". Les métriques (largeurs) sont les mêmes, mais les caractères sont légèrement différents. Les polices de type 1 sont censées être disponibles dans tous les lecteurs PDF, elles ne peuvent donc pas être incluses en tant que fichiers TTF (TrueType). Ce n'est pas considéré comme un problème pour les documents archivés (PDF/A), mais cela pourrait le devenir à un moment donné, alors soyez-en conscient. Notes et Limitations

  • ATTENTION : Il y a un "piège" avec les polices TrueType dont vous devez être conscient lorsque vous les utilisez. PDF::Builder génère dans le flux de texte une liste d'identifiants de glyphes sous forme de codes hexadécimaux à quatre chiffres, plutôt que la liste des codes d'octets de caractères utilisée par d'autres types de polices. L'intention est de permettre plus que les points Unicode standards (glyphes alternatifs pour les ligatures et autres usages). Ne comptez pas sur cela comme cryptage pour masquer votre contenu (le lecteur PDF l'affichera de toute façon !), même si cela rend difficile la recherche de texte spécifique dans un PDF à l'aide d'un éditeur de texte.
  • L'opérateur Tw, s'il est utilisé ("$text->wordspace(n)") pour ajuster l'espacement entre les mots, sera ignoré par la plupart, sinon par tous, des lecteurs PDF (y compris les produits Adobe). Cela est dû au fait que cet opérateur recherche des espaces ASCII réels (octets x20) dans le flux, pour y appliquer le changement de largeur. Notez que seuls les espaces ASCII sont affectés (pas les autres espaces), et pas du tout pour les polices TrueType et OpenType (car elles ont des identifiants de glyphes à 4 chiffres, pas des octets x20 !). PDF::Builder a été mis à jour pour tenter de respecter l'opérateur Tw lors de l'utilisation de polices TTF/OTF. Si le montant "Tw" est non nul, il divisera les phrases sur les espaces ASCII (x20) et placera individuellement les mots sur la page. Cela gonfle nécessairement la taille du fichier PDF, mais c'est la seule façon d'ajuster l'espacement des mots via la méthode wordspace(). Notez qu'encore une fois, seuls les espaces ASCII (x20) sont affectés (pour correspondre au comportement de l'opérateur Tw pour d'autres types de polices), et les autres espaces (xA0 espace requis/insécable, espace fine, etc.) ne sont pas gérés.
  • Avertissement : BaseEncoding n'est pas défini par défaut pour les polices TrueType, donc le texte dans le PDF n'est pas recherchable (par le lecteur PDF) à moins qu'un CMap ToUnicode ne soit inclus. Un CMap ToUnicode est inclus par défaut (unicodemap défini à 1) par PDF::Builder, mais peut être désactivé (pour des raisons de performance et de taille de fichier) en définissant unicodemap à 0. Cela produira du texte non recherchable, ce qui, en plus d'être agaçant pour les utilisateurs, peut empêcher les lecteurs d'écran et autres aides aux utilisateurs handicapés de fonctionner correctement !
  • Ne confondez pas les points de caractères Unicode (comme ceux donnés par une entité HTML) avec les valeurs d'un octet unique ou les caractères multibits. La seule façon d'accéder à un caractère défini pour un encodage donné est avec une valeur de code unique dans la plage autorisée. Par exemple, si vous ne pouvez pas taper directement un symbole "Euro", c'est "\x80" dans de nombreux encodages -- vous utiliseriez cela pour un encodage à un octet, ou pour UTF-8, le point de code Unicode "\x{20AC}". Vous ne donneriez jamais la chaîne d'octets UTF-8 "x\{E282AC}". Il doit être compréhensible dans le contexte de l'encodage actuel, afin que le code glyphe à 4 chiffres puisse être généré.
  • Soyez conscient de ce que la plateforme (système d'exploitation) et l'éditeur utilisent comme page de code lorsqu'il crée un fichier avec votre texte à transformer en PDF ! Si vous avez tapé un "Euro" mais que c'est, disons, une chaîne d'octets UTF-8 dans le fichier, et que vous utilisez un encodage à un octet, vous n'obtiendrez probablement pas un "Euro" dans votre PDF.

Où est la police que je viens d'ajouter ?

Eh bien, parfois vous avez de la chance et pouvez spécifier le répertoire exact où le fichier ".ttf" ou ".otf" résidera, ce qui facilite la spécification du chemin vers le fichier de police (pour des usages tels que ttfont(), font(), ou les appels à Font Manager). D'autres fois, le système d'exploitation joue à cache-cache avec vous, vous laissant dépenser beaucoup de temps et d'énergie pour traquer où se trouve le fichier. Les distributions Linux ont tendance à avoir leurs propres endroits favoris pour cacher les fichiers de polices, mais au moins elles ont tendance à être cohérentes ! D'autre part, Windows décide souvent qu'il sait mieux que vous, et place les fichiers dans un endroit inattendu, et sous un nom inattendu !

Pour savoir où votre fichier TTF ou OTF a fini, si vous ne voyez pas d'entrée évidente dans /Windows/Fonts (même si vous avez glissé-déposé le fichier de police là-bas), vous devez regarder dans /Users/XXXX/AppData/Local/Microsoft/Windows/Fonts, en fonction du nom d'utilisateur sous lequel vous étiez connecté lors de l'installation de la police. Même alors, vous n'avez peut-être pas fini, car le nom a pu être changé en quelque chose d'incompréhensible. Vous devrez peut-être examiner le mappage de Windows du nom de police au nom de fichier.

Dans la ligne de commande, ou l'équivalent que vous aimez utiliser, tapez "regedit" pour ouvrir l'éditeur de registre. Pour le niveau supérieur, choisissez (cliquez sur) soit "HKEY_LOCAL_MACHINE" (pour les paramètres globaux des polices, dans /Windows/Fonts) soit "HKEY_CURRENT_USER" (pour les polices installées par celui qui est actuellement connecté, dans /Users/XXXX/AppData...). À partir de là, les deux ont le même chemin : "SOFTWARE > Microsoft > Windows NT > CurrentVersion > Fonts". Cela devrait afficher une liste de toutes les polices installées (nom complet, par ex. "Papyrus Regular") et leur nom de fichier réel ("PAPYRUS.TTF"). Par exemple, je viens d'installer (glisser-déposer dans /Windows/Fonts) une police "Gothique" en lettres gothiques nommée English Towne Medium. Elle a fini dans mon répertoire /Users/XXXX... sous le nom "EnglishTowne.ttf".

Vous n'avez rien à changer dans le registre, regardez seulement. Vous pouvez changer des choses, y compris afficher/masquer la police, si vous souhaitez vous y intéresser.

Polices Synthétiques

Avertissement : BaseEncoding n'est pas défini par défaut pour ces polices, donc le texte dans le PDF n'est pas recherchable (par le lecteur PDF) à moins qu'un CMap ToUnicode ne soit inclus. Un CMap ToUnicode est inclus par défaut (unicodemap défini à 1) par PDF::Builder, mais peut être désactivé (pour des raisons de performance et de taille de fichier) en définissant unicodemap à 0. Cela produira du texte non recherchable, ce qui, en plus d'être agaçant pour les utilisateurs, peut empêcher les lecteurs d'écran et autres aides aux utilisateurs handicapés de fonctionner correctement !

Exemples :

$cf  = $pdf->corefont('Times-Roman', encode => 'latin1');
$sf  = $pdf->synfont($cf, condense => 0.85);   # compressé 85%
$sfb = $pdf->synfont($cf, bold => 1);          # épaissi de 10em
$sfi = $pdf->synfont($cf, oblique => -12);     # italique à -12 degrés

Notez que les polices CJK (créées avec la méthode "cjkfont") ne fonctionnent pas correctement avec "synfont". Cela est dû à une structure interne différente des polices CJK, par rapport aux polices de base corefont, ttfont et psfont. Si vous avez besoin d'une police CJK synthétisée (modifiée), vous pourriez essayer de trouver l'original TTF ou OTF, utiliser "ttfont" pour créer la police de base, et exécuter "synfont" contre celle-ci, de la manière décrite pour intégrer les "Polices CJK".

Pourquoi mon image est-elle retournée ou tournée ?

Quelque chose de pas rare lorsque l'on utilise des photos JPEG dans un PDF, c'est que les images sont tournées et/ou miroir (retournées). Cela peut également se produire lors de l'utilisation d'images TIFF. Ce qui se passe, c'est que l'appareil photo stocke une image telle qu'elle sort du capteur CCD, quelle que soit l'orientation de l'appareil, et ne la tourne pas dans la bonne orientation ! Par exemple, si vous prenez une photo "portrait" (haute) d'un arbre (téléphone tenu verticalement), et que vous l'utilisez dans un PDF, l'arbre peut apparaître comme s'il avait été coupé ! La bibliothèque HarfBuzz::Shaper peut être installée en option pour utiliser les capacités de mise en forme de texte de la bibliothèque HarfBuzz. Celles-ci incluent les ligatures et les croisements de caractères dans les scripts occidentaux (comme l'alphabet latin). Les scripts plus complexes comme ceux de l'arabe et des langues autochtones peuvent également être gérés, où différentes formes d'un caractère peuvent être sélectionnées automatiquement, les caractères peuvent être réordonnés et d'autres modifications peuvent être effectuées. L'exemple/HarfBuzz.pl donne quelques exemples de ce qui peut être fait.

Cependant, HarfBuzz ne fonctionne qu'avec les polices TrueType (.ttf) et OpenType (.otf). Il ne fonctionne pas avec les polices PostScript (Type1), core, bitmap ou CJK. Toutes les polices .ttf ne contiennent pas les instructions nécessaires pour guider HarfBuzz, mais la plupart des polices .otf le font. En d'autres termes, rien ne garantit qu'un fichier de police spécifique fonctionnera avec Shaper !

L'idée de base est de diviser le texte en « blocs » du même script (alphabet), de la même langue, de la même direction, de la même police, de la même taille et de la même variante (italique, gras, etc.). Ceux-ci peuvent varier d'un seul caractère à des chaînes de texte de paragraphe. Ceux-ci sont envoyés à HarfBuzz::Shaper ainsi que les drapeaux, le fichier de police à utiliser et d'autres informations de support, pour créer un tableau de caractères de sortie. Chaque élément est un hash décrivant le caractère à afficher, y compris son nom (s'il est disponible), son identifiant de caractère (numéro) dans la police sélectionnée, ses positions x et y (généralement 0), et ses valeurs de déplacement x et y, le tout en points. Pour les langues horizontales (LTR et RTL), le déplacement y est normalement de 0 et le déplacement x est la largeur du caractère dans la police, moins toute quantité de crénage.

Shaper essaiera de déterminer le script utilisé et la direction du texte, en se basant sur la plage Unicode ; et une estimation raisonnable pour la langue. La langue peut être remplacée, mais le script et la direction du texte ne peuvent actuellement pas être remplacés.

Un détail important : Le nombre de caractères (éléments du tableau) peut ne pas être égal au nombre de points (caractères) donnés dans la chaîne de texte d'un bloc ! Parfois, un caractère est décomposé en plusieurs parties (caractères multiples) ; parfois, plusieurs caractères peuvent être combinés en une seule ligature ; et les caractères peuvent être réorganisés (en particulier dans les scripts de droite à gauche comme l'hébreu et l'arabe). De plus, pour les scripts de droite à gauche (bidirectionnels) comme l'hébreu et l'arabe, le texte est affiché de gauche à droite (inverse de l'entrée).

Avec soin, un tableau Shaper peut être manipulé dans le code. Les éléments sont plus ou moins indépendants les uns des autres, ils peuvent donc être modifiés, réorganisés, insérés ou supprimés. Vous pouvez ajuster la position d'un caractère avec les éléments de hash 'dx' et 'dy'. La valeur 'ax' doit être laissée telle quelle, pour éviter les erreurs.

Gardez toute la structure du fichier. Le crénage n'est pas calculé, mais vous pouvez ajuster la valeur de "advance x" en utilisant l'une des méthodes suivantes :
axs
est une valeur substituée pour 'ax' (en points)
axsp
est une valeur substituée (en pourcentage) de l'original 'ax'
axr
réduit 'ax' de la valeur (en points). Si négatif, augmente 'ax'
axrp
réduit 'ax' de la valeur donnée (en pourcentage). De plus, un négatif augmente 'ax'

Attention : l'identifiant de caractère glyphe dans une table de font n'est pas forcément le même entre différentes fonts ! Par exemple, un espace ASCII (U+0020) pourrait être "<0001>" dans une font et "<0003>" dans une autre (même une apparentée). Un espace U+00A0 (espace insécable) pourrait être rendu comme un espace ASCII normal U+0020. Notez que si vous avez besoin de trouver un glyphe spécifique dans un tableau, surtout si le nombre d'éléments ne correspond pas, envisagez de créer une chaîne de caractères de type "marqueur" (espace, nbsp, trait d'union, trait d'union léger, etc.) et de la traiter avec HarfBuzz::Shaper pour obtenir les numéros de glyphes correspondants. Vous pourriez avoir à compter les espaces, par exemple, pour savoir où vous pourriez diviser un tableau de glyphes afin de l'ajuster à une ligne.

La fonction advancewidthHS() utilise les mêmes entrées que textHS(). Similaire à advancewidth(), elle renvoie la longueur du morceau en points. Contrairement à advancewidth(), vous ne pouvez pas outrepasser la font, la taille ou d'autres éléments du tableau de glyphes.

Une fois que vous avez traité (éventuellement modifié) le tableau de glyphes, passez à la fonction textHS() pour le rendre sur la page. N'oubliez pas que cette fonction ne gère qu'un seul bloc de texte ; elle n'effectue pas de division ou d'ajustement de ligne — c'est à vous de le faire manuellement. Pour les scripts occidentaux (par exemple, le latin), cela peut ne pas être très difficile, mais pour d'autres scripts qui nécessitent une modification importante des caractères bruts, il peut être assez difficile de diviser les mots, même si vous pouvez toujours diviser aux espaces entre les mots.

Un ensemble utile, mais non exhaustif, de fonctions sont permises par textHS(). La prise en charge inclut la définition de la direction (de haut en bas et de bas en haut, par exemple, pour les langues traditionnellement orientées), et des noms de scripts et de langues explicites (en fonction de ce que HarfBuzz lui-même offre). Les fonctionnalités telles que les ligatures disjointes ou la sélection manuelle de glyphes (par exemple, les swashes et les formes alternatives) ne sont **pas encore prises en charge**.

Actuellement, textHS() ne peut gérer qu'une seule chaîne de caractères. Nous examinons comment il pourrait être possible de l'adapter à une longueur de ligne (diviser un tableau) et comment les mots pourraient être divisés par des traits d'union rythmiques et doux. À un moment donné, la mise en forme de paragraphes et de pages pourrait être possible.

Cette section documente les capacités de balisage de la méthode column(). On s'attend à ce qu'elle soit mise à jour avec l'ajout de nouvelles fonctions.

Un certain type de Markdown est pris en charge, tel que traduit par le package Text::Markdown en HTML. C'est du HTML (et plus, comme entrée directe), ainsi qu'un sous-ensemble de CSS, qui est pris en charge par column(). Ce n'est pas le langage Markdown ou HTML complet, pour ainsi dire, alors vérifiez avant d'utiliser ! Il existe également un petit type de balisage none qui se contente de créer des paragraphes (séparés par des lignes vides).

Dans tous les cas de balisage, certaines configurations CSS peuvent être fournies comme paramètres ou options à l'appel de column(), y compris une section CSS style qui s'applique à la fois à l'entrée 'none' et à l'entrée Markdown.

Autres formes d'entrée

PDF::Builder ne prend actuellement en charge que les langages de balisage décrits ci-dessus. Si vous souhaitez utiliser un autre format (par exemple, le format POD de Perl ou le format man, ou même MS Word ou un autre format WYSIWYG), vous aurez besoin d'un utilitaire de conversion pour le convertir dans un format Markdown ou HTML pris en charge. De nombreux convertisseurs de ce type existent déjà, alors regardez (bien qu'il vous faudra peut-être faire un nettoyage avant que column() ne l'accepte).

Bien que PDF::Builder puisse prendre en charge directement d'autres formats à l'avenir, ce n'est pas garanti. Vous ne verrez pas d'entrée TeX/LaTeX, car ceux-ci ont déjà une excellente sortie PDF (et ce serait un travail colossal à traiter).

Inutile de dire que l'encodage utilisé pour créer le texte d'entrée doit correspondre à l'encodage de police spécifié.

En l'absence de balisage modifiant la police ou le style, ce qui est défini par le gestionnaire de polices comme la police actuelle sera utilisé. De cette façon, vous pouvez hériter de la police de la column() précédente, ou appeler "$text-"font($pdf->get_font(), size)> pour définir à la fois la police et la taille, ou simplement appeler "$pdf-"get_font()> pour définir uniquement la police, en s'appuyant sur l'option "font_size" ou le balisage CSS pour définir la taille.

Le remplissage des lignes (mise en forme des paragraphes) est actuellement assez primitif. Les mots ne seront pas séparés (hyphenés). Il est prévu d'ajouter à terme la mise en forme de paragraphes Knuth-Plass, ainsi qu'une hyphenation appropriée dépendante de la langue.

Chaque changement de police fournit automatiquement son ascendant maximum et son descendant minimum, les étendues au-dessus et en dessous de la ligne de base du texte. Chaque bloc de texte avec une face et une variante données, ou un changement de taille de police, recevra les mêmes étendues verticales -- les étendues sont globales à la police, et ne sont pas déterminées par glyphe. Ainsi, malheureusement, un bloc de texte "acemnorsuvwz" aura les mêmes étendues verticales qu'un bloc de texte "bdfghijklpqty". Pour une ligne de texte donnée, l'ascendant le plus haut et le descendant le plus bas (plus l'interlignage) seront utilisés pour positionner la ligne à une distance appropriée sous la ligne précédente (ou le haut de la colonne). Aucune tentative n'est faite pour "ajuster" les projections dans les renfoncements (comme un puzzle). S'il y a un retrait sur le côté d'une colonne, ou si elle n'est pas une ligne verticale droite, tant que la ligne de base s'inscrit dans le contour de la colonne, aucune vérification n'est effectuée pour savoir si les descendants ou les ascendants tomberont en dehors de la colonne définie (c'est-à-dire, projeteront dans le retrait). Nous suggérons d'essayer de garder les tailles de police relativement cohérentes, pour maintenir des étendues verticales de texte raisonnablement cohérentes.
