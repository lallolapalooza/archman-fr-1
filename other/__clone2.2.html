DESCRIPTIO

N

Ces appels système créent un nouveau processus (« fils »), d'une manière similaire à fork(

2).

Contrairement à fork(2), ces appels système offrent un contrôle plus précis sur les parties du contexte d'exécution qui sont partagées entre le processus appelant et le processus fils. Par exemple, à l'aide de ces appels système, l'appelant peut contrôler si les deux processus partagent ou non l'espace d'adresses virtuelles, la table des descripteurs de fichiers et la table des gestionnaires de signaux. Ces appels système permettent également de placer le nouveau processus fils dans des espaces de noms (namespaces) séparés (v

oir namespaces(7)).

Notez que dans cette page manuelle, « processus appelant » correspond normalement au « processus parent ». Mais voir les descriptions de CLONE_PARENT et CLONE_THREAD ci-

dessous.

La fonction wrapper

clone()

Lorsque le processus fils est créé avec la fonction wrapper clone(), il commence son exécution en appelant la fonction pointée par l'argument fn. (Cela diffère de fork(2), où l'exécution se poursuit dans le fils à partir du point de l'appel fork(2).) L'argument arg est passé comme argument de la fonction fn

.

Lorsque la fonction fn(arg) retourne, le processus fils se termine. L'entier retourné par fn est le code de sortie du processus fils. Le processus fils peut également se terminer explicitement en appelant exit(2) ou après avoir reçu un signal

fatal.

L'argument stack spécifie l'emplacement de la pile utilisée par le processus fils. Comme le fils et le processus appelant peuvent partager la mémoire, il n'est pas possible pour le processus fils de s'exécuter sur la même pile que le processus appelant. Le processus appelant doit donc configurer un espace mémoire pour la pile du fils et passer un pointeur vers cet espace à clone(). Les piles croissent vers le bas sur tous les processeurs exécutant Linux (sauf les processeurs HP PA), donc stack pointe généralement vers l'adresse la plus haute de l'espace mémoire configuré pour la pile du fils. Notez que clone() ne fournit aucun moyen par lequel l'appelant peut informer le noyau de la taille de la zone de

pile.

Les arguments restants de clone() sont dis

cutés ci-
dessous.

clone3(

)

L'appel système clone3() fournit un ensemble supérieur à la fonctionnalité de l'interface plus ancienne clone(). Il fournit également un certain nombre d'améliorations d'API, notamment : de l'espace pour des bits de drapeaux supplémentaires ; une meilleure séparation dans l'utilisation des différents arguments ; et la possibilité de spécifier la taille de la zone de pile du

fils.

Comme pour fork(2), clone3() retourne à la fois dans le parent et dans le fils. Il retourne 0 dans le processus fils et retourne le PID du fils dans le

parent.

Les groupes de threads étaient une fonctionnalité ajoutée dans Linux 2.4 pour prendre en charge la notion POSIX de threads d'un ensemble de threads partageant un seul PID. En interne, ce PID partagé est le soi-disant identifiant de groupe de threads (TGID) du groupe de threads. Depuis Linux 2.4, les appels à getpid(2) retournent le TGID de

Les threads au sein d'un groupe peuvent être distingués par leurs identifiants de threads (TID) uniques (à l'échelle du système). Le TID d'un nouveau thread est disponible comme résultat de la fonction retourné à l'appelant, et un thread peut obtenir son propre TID en utilisant gettid(

(Le thread est dit détach

Après que tous les threads d'un groupe de threads se sont terminés, le processus parent du groupe de threads reçoit un signal SIGCHLD (ou autre signal de terminaison)
.
Si l'un des threads d'un groupe de threads effectue un execve(2), alors tous les threads autres que le leader du groupe de threads sont terminés, et le nouveau programme est exécuté dans le leader du groupe de
threads.
Si l'un des threads d'un groupe de threads crée un enfant en utilisant fork(2), alors n'importe quel thread du groupe peut attendre (wait(2)) cet
enfant.

Les dispositions et actions des signaux s'appliquent à l'ensemble du processus : si un signal non géré est délivré à un thread, alors il affectera (terminera, arrêtera, reprendra, sera ignoré dans) tous les membres du groupe de
threads.
Chaque thread a son propre masque de signaux, tel que défini par sigprocmas
k(2).
Un signal peut être dirigé vers le processus ou vers un thread. Un signal dirigé vers le processus est ciblé sur un groupe de threads (c'est-à-dire, un TGID), et est délivré à un thread arbitrairement sélectionné parmi ceux qui ne bloquent pas le signal. Un signal peut être dirigé vers le processus parce qu'il a été généré par le noyau pour des raisons autres qu'une exception matérielle, ou parce qu'il a été envoyé en utilisant kill(2) ou sigqueue(3). Un signal dirigé vers un thread est ciblé sur (c'est-à-dire, délivré à) un thread spécifique. Un signal peut être dirigé vers un thread parce qu'il a été envoyé en utilisant tgkill(2) ou pthread_sigqueue(3), ou parce que le thread a exécuté une instruction de langage machine qui a déclenché une exception matérielle (par exemple, un accès mémoire invalide déclenchant SIGSEGV ou une exception en virgule flottante déclenchant SIGFP
E).
Un appel à sigpending(2) retourne un ensemble de signaux qui est l'union des signaux dirigés vers le processus en attente et des signaux en attente pour le thread
appelant.
Si un signal dirigé vers le processus est délivré à un groupe de threads, et que le groupe de threads a installé un gestionnaire pour le signal, alors le gestionnaire est invoqué dans exactement un membre du groupe de threads, arbitrairement sélectionné, qui n'a pas bloqué le signal. Si plusieurs threads dans un groupe attendent d'accepter le même signal en utilisant sigwaitinfo(2), le noyau sélectionnera arbitra
irement l'un de ces thread
s pour recevoir le signal.

VERSIONS

La fonction wrapper glibc clone() apporte quelques modifications dans la mémoire pointée par stack (modifications nécessaires pour configurer correctement la pile pour l'enfant) avant d'invoquer l'appel système clone(). Ainsi, dans les cas où clone() est utilisé pour créer récursivement des enfants, n'utilisez pas le tampon employé pour la pile du parent comme pile de l'enfant.

Sur i386, clone() ne doit pas être appelé via vsyscall, mais directement via int $0x80.

Différences bibliothèque C/noyau

L'appel système brut clone() correspond plus étroitement à fork(2) en ce que l'exécution dans l'enfant continue à partir du point de l'appel. En tant que tel, les arguments fn et arg de la fonction wrapper clone() sont omis.

Contrairement au wrapper glibc, l'appel système brut clone() accepte NULL comme argument stack (et clone3() autorise de même cl_args.stack à être NULL). Dans ce cas, l'enfant utilise une copie de la pile du parent. (Les sémantiques copy-on-write garantissent que l'enfant obtient des copies séparées des pages de pile lorsque l'un des processus modifie la pile.) Dans ce cas, pour un fonctionnement correct, l'option CLONE_VM ne doit pas être spécifiée. (Si l'enfant partage la mémoire du parent en raison de l'utilisation du flag CLONE_VM, aucune duplication copy-on-write n'a lieu et le chaos est susceptible d'en résulter.)

L'ordre des arguments diffère également dans l'appel système brut, et il existe des variations dans les arguments entre les architectures, comme détaillé dans les paragraphes suivants.

          int *parent_tid, unsigned long tls,

long clone(void *stack, unsigned long flags,

           unsigned long tls);
