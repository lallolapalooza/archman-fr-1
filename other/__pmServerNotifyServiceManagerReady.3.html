PMSERVERNOTIFYSERVICEMANAGERREADY(3) Manuel des fonctions de bibliothèque PMSERVERNOTIFYSERVICEMANAGERREADY(3)

NOM

__pmServerNotifyServiceManagerReady, __pmServerNotifyServiceManagerStopping - notification de démarrage et arrêt de service

C SYNTAXE

#include "pmapi.h"
#include "libpcp.h"

int __pmServerNotifyServiceManagerReady(pid_t mainpid);
int __pmServerNotifyServiceManagerStopping(pid_t mainpid);

cc ... -lpcp

AVERTISSEMENT

Cette documentation est destinée à un usage interne par les développeurs de Performance Co-Pilot (PCP).

Ces interfaces ne font pas partie des API PCP garanties comme restant fixes entre les versions, et elles peuvent ne pas fonctionner, ou fonctionner avec une sémantique différente à l'avenir.

DESCRIPTION

Au sein des bibliothèques et applications de Performance Co-Pilot (PCP), ces routines fournissent une interface pratique et portable vers les API de gestionnaires de services, telles que sd_notify(3).

Les démons de service PCP doivent appeler __pmServerNotifyServiceManagerReady immédiatement avant d'entrer dans leur boucle principale, qu'ils aient ou non effectué un fork ou un daemonisation. Cela notifiera le gestionnaire de services (s'il y en a un, selon la plateforme) que le service démon a démarré, et que le processus principal à suivre est mainpid.

De même, lors de l'arrêt, les démons de service doivent appeler __pmServerNotifyServiceManagerStopping pour notifier le gestionnaire de services (s'il y en a un) que le processus suivi du service est revenu de sa boucle principale et est sur le point de s'arrêter.

Ces routines sont conçues pour être portables et ne nécessitent donc aucun code conditionnel pour aucun démon de service sur aucune plateforme.

DIAGNOSTICS

Ces fonctions imprimeront des diagnostics sur le flux stderr si pmDebugOptions.services est défini.

CODE DE RETOUR

En cas de succès, __pmServerNotifyServiceManagerReady renvoie un entier positif qui dépend du gestionnaire de services de la plateforme. Dans le cas de systemd(1), le code de retour provient de sd_notify(3). Si la plateforme prend en charge systemd(1) mais que la variable d'environnement NOTIFY_SOCKET n'est pas définie (ce qui peut arriver si le programme serveur est démarré manuellement plutôt que par systemd(1)), le code de retour sera PM_ERR_GENERIC, qui sera normalement ignoré mais un diagnostic sera imprimé si pmDebugOptions.services est défini. Sur les plateformes qui n'ont pas de gestionnaire de services, le code de retour sera PM_ERR_NYI. Pour des raisons de compatibilité ascendante sur ces plateformes, le code de retour doit être ignoré.
