Bien noter : Cette page documente les interfaces fournies jusqu'à glibc 2.1. Depuis glibc 2.2, glibc ne fournit plus ces interfaces. Vous cherchez probablement les API fournies par la bibliothèque libdb à la

place.

La routine dbopen(3) est l'interface de bibliothèque vers les fichiers de bases de données. L'un des formats de fichiers pris en charge est les fichiers btree. La description générale des méthodes d'accès aux bases de données se trouve dans dbopen(3), cette page de manuel ne décrit que les informations spécifiques à

btree.

La structure de données btree est une structure d'arbre triée et équilibrée stockant des paires clé/données

associées.

La structure de données spécifique à la méthode d'accès btree fournie à dbopen(3) est définie dans le fichier d'inclusion <db.h> comme suit

: 


typedef struct {
    unsigned long flags;
    unsigned int  cachesize;
    int           maxkeypage;
    int           minkeypage;
    unsigned int  psize;
    int         (*compare)(const DBT *key1, const DBT *key2);
    size_t      (*prefix)(const DBT *key1, const DBT *key2);
    int           lorder;
}
BTREEINFO;

Autoriser les clés en double dans l'arbre, c'est-à-dire autoriser l'insertion si la clé à insérer existe déjà dans l'arbre. Le comportement par défaut, tel que décrit dans dbopen(3), est d'écraser une clé correspondante lors de l'insertion d'une nouvelle clé ou d'échouer si le drapeau R_NOOVERWRITE est spécifié. Le drapeau R_DUP est ignoré par le drapeau R_NOOVERWRITE, et si le drapeau R_NOOVERWRITE est spécifié, les tentatives d'ins
ertion de clés en dou
ble dans l'arbre échoueront.
Si la base de données contient des clés en double, l'ordre de récupération des paires clé/données est indéfini si la routine get est utilisée, cependant, les appels de routine seq avec le drapeau R_CURSOR défini renverront toujour
s le « premier »
logique de tout grou
pe de clés en double.
cachesi
ze
Une taille maximale suggérée (en octets) du cache mémoire. Cette valeur n'est qu'indicative, et la méthode d'accès allouera plus de mémoire plutôt que d'échouer. Puisque chaque recherche examine la page racine de l'arbre, mettre en cache les pages les plus récemment utilisées améliore considérablement le temps d'accès. De plus, les écritures physiques sont retardées aussi longtemps que possible, de sorte qu'un cache modéré peut réduire considérablement le nombre d'opérations d'E/S. Évidemment, l'utilisation d'un cache augmente (mais augmente seulement) la probabilité de corruption ou de perte de données si le système se bloque pendant la modification d'un arbre. Si cachesize est 0 (aucune taille n'est spécifiée), un cache par défaut est
utilisé.
maxkeypa
ge
Le nombre maximal de clés qui seront stockées sur une seule page. Actuellement non
implémenté.
minkeypa
ge
Le nombre minimal de clés qui seront stockées sur une seule page. Cette valeur est utilisée pour déterminer quelles clés seront stockées sur des pages de débordement, c'est-à-dire si une clé ou un élément de données est plus long que la taille de page divisée par la valeur minkeypage, il sera stocké sur des pages de débordement au lieu de la page elle-même. Si minkeypage est 0 (aucun nombre minimal de clés n'est spécifié), une valeur de 2 est
utilisée.
psi
ze
La taille de page est la taille (en octets) des pages utilisées pour les nœuds dans l'arbre. La taille de page minimale est de 512 octets et la taille de page maximale est de 64 Kio. Si psize est 0 (aucune taille de page n'est spécifiée), une taille de page est choisie en fonction de la taille de bloc d'E/S du système de fichiers
sous-jacent.
compa
re
Compare est la fonction de comparaison des clés. Elle doit renvoyer un entier inférieur, égal ou supérieur à zéro si le premier argument de clé est considéré comme respectivement inférieur, égal ou supérieur au second argument de clé. La même fonction de comparaison doit être utilisée sur un arbre donné chaque fois qu'il est ouvert. Si compare est NULL (aucune fonction de comparaison n'est spécifiée), les clés sont comparées lexicographiquement, les clés plus courtes étant considérées comme inférieures aux clés plus
longues.
pref
ix
Prefix est la fonction de comparaison de préfixe. Si spécifiée, cette routine doit renvoyer le nombre d'octets du second argument de clé nécessaires pour déterminer qu'il est supérieur au premier argument de clé. Si les clés sont égales, la longueur de la clé doit être renvoyée. Notez que l'utilité de cette routine dépend fortement des données, mais que, sur certains ensembles de données, elle peut produire des tailles d'arbre et des temps de recherche considérablement réduits. Si prefix est NULL (aucune fonction de préfixe n'est spécifiée) et qu'aucune fonction de comparaison n'est spécifiée, une routine de comparaison lexicographique par défaut est utilisée. Si prefix est NULL et qu'une routine de comparaison est spécifiée, aucune comparaison de préfixe n'est
effectuée.
lord
er
L'ordre des octets pour les entiers dans les métadonnées de la base de données stockée. Le nombre doit représenter l'ordre sous forme d'entier ; par exemple, l'ordre big endian serait le nombre 4 321. Si lorder est 0 (aucun ordre n'est spécifié
), l'ordre de l'hôte
actuel est utilisé.

Si le fichier existe déjà (et que le drapeau O_TRUNC n'est pas spécifié), les valeurs spécifiées pour les arguments flags, lorder et psize sont ignorées au profit des valeurs utilisées lors de la création de

l'arbre.

Les balayages séquentiels en avant d'un arbre vont de la clé la plus petite à la plus

grande.

L'espace libéré en supprimant des paires clé/données de l'arbre n'est jamais récupéré, bien qu'il soit normalement rendu disponible pour réutilisation. Cela signifie que la structure de stockage btree ne fait que croître. Les seules solutions sont d'éviter les suppressions excessives ou de créer périodiquement un nouvel arbre à partir du balayage d'un arbre

existant.

Les recherches, les insertions et les suppressions dans un btree se termineront toutes en O lg base N où la base est le facteur de rempliss

age moyen. Souvent, l'insertion de données ordonnées dans des btrees résulte en un faible facteur de remplissage. Cette implémentation a ét
é modifiée pour faire de l'insertion ordonnée le meilleur cas, ce qui donne un facteur de remplissage de page bien meilleur que la normale.
