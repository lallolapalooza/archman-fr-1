BORG-CREATE(1) Outil de sauvegarde borg BORG-CREATE(1)

NOM

borg-create - Créer une nouvelle archive

SYNTAXE

borg [options communes] create [options] ARCHIVE [CHEMIN...]

DESCRIPTION

Cette commande crée une archive de sauvegarde contenant tous les fichiers trouvés lors de la traversée récursive de tous les chemins spécifiés. Les chemins sont ajoutés à l'archive tels qu'ils sont donnés, ce qui signifie que si des chemins relatifs sont souhaités, la commande doit être exécutée depuis le répertoire correct.

Le hack slashdot dans les chemins (racines de récursion) est déclenché en utilisant /./ : /ceci/est/supprimé/./ceci/est/archivé signifie traiter cet objet du système de fichiers, mais supprimer le préfixe à gauche de ./ des éléments archivés (dans ce cas, ceci/est/archivé sera le chemin dans l'élément archivé).

Lorsque '-' est donné comme chemin, Borg lira les données depuis l'entrée standard et créera un fichier 'stdin' dans l'archive créée à partir de ces données. Dans certains cas, il est plus approprié d'utiliser --content-from-command. Voir la section "Lecture depuis stdin" ci-dessous pour plus de détails.

L'archive consommera très peu d'espace disque pour les fichiers ou parties de fichiers déjà stockés dans d'autres archives.

Le nom de l'archive doit être unique. Il ne doit pas se terminer par '.checkpoint' ou '.checkpoint.N' (où N est un nombre), car ces noms sont utilisés pour les points de contrôle et traités de manière spéciale.

Dans le nom de l'archive, vous pouvez utiliser les espaces réservés suivants : {now}, {utcnow}, {fqdn}, {hostname}, {user} et quelques autres.

La vitesse de sauvegarde est augmentée en ne retraîtant pas les fichiers qui font déjà partie des archives existantes et qui n'ont pas été modifiés. La détection des fichiers non modifiés est effectuée en comparant plusieurs valeurs de métadonnées de fichier avec les valeurs précédentes conservées dans le cache des fichiers.

Cette comparaison peut fonctionner dans différents modes, comme spécifié par --files-cache :

  • ctime,size,inode (défaut)
  • mtime,size,inode (comportement par défaut des versions de borg antérieures à 1.1.0rc4)
  • ctime,size (ignore le numéro d'inode)
  • mtime,size (ignore le numéro d'inode)
  • rechunk,ctime (tous les fichiers sont considérés comme modifiés - réencapsulation, cache ctime)
  • rechunk,mtime (tous les fichiers sont considérés comme modifiés - réencapsulation, cache mtime)
  • disabled (désactive le cache des fichiers, tous les fichiers sont considérés comme modifiés - réencapsulation)

Numéro d'inode : meilleure sécurité, mais souvent instable sur les systèmes de fichiers réseau

Normalement, la détection des modifications de fichiers prend en compte les informations d'inode pour améliorer la fiabilité de la détection des changements de fichiers. Ceci est problématique pour les fichiers situés sur SSHFS et des systèmes de fichiers réseau similaires qui ne fournissent pas de numéros d'inode stables ; ces fichiers seront toujours considérés comme modifiés. Vous pouvez utiliser les modes sans inode dans ce cas pour améliorer les performances, mais la fiabilité de la détection des changements pourrait être réduite.

ctime vs mtime : sécurité vs vitesse

  • ctime est un moyen plutôt sûr de détecter les modifications d'un fichier (métadonnées et contenu) car il ne peut pas être défini depuis l'espace utilisateur. Cependant, un changement de métadonnées seul mettra déjà à jour le ctime, il pourrait donc y avoir un certain rechunkage/hachage inutile même sans changement de contenu. Certains systèmes de fichiers ne prennent pas en charge le ctime (temps de changement). Par exemple, effectuer un chown ou un chmod sur un fichier changera son ctime.
  • mtime fonctionne généralement et ne se met à jour que si le contenu du fichier a été modifié. Mais mtime peut être arbitrairement défini depuis l'espace utilisateur, par exemple pour rétablir mtime à la même valeur qu'il avait avant qu'un changement de contenu ne se produise. Cela peut être utilisé malicieusement comme bien intentionné, mais dans les deux cas, les modes de cache basés sur mtime peuvent être problématiques.

L'option --files-changed contrôle comment Borg détecte si un fichier a changé pendant la sauvegarde :

  • ctime (défaut) : Utilise ctime pour détecter les changements. C'est l'option la plus sûre.
  • mtime : Utilise mtime pour détecter les changements.
  • disabled : Désactive complètement la détection "le fichier a changé pendant que nous le sauvegardions". Ce n'est pas recommandé à moins de savoir ce que vous faites, car cela pourrait entraîner des sauvegardes incohérentes si les fichiers changent pendant le processus de sauvegarde.

Les points de montage des systèmes de fichiers ou des instantanés de systèmes de fichiers doivent être les mêmes pour chaque création d'une nouvelle archive afin d'assurer un fonctionnement rapide. C'est parce que le cache des fichiers utilisé pour déterminer rapidement les fichiers modifiés utilise des noms de fichiers absolus. Si ce n'est pas possible, envisagez de créer un montage de liaison vers un emplacement stable.

L'option --progress affiche (de gauche à droite) l'Original, le Compressé et le Dédupliqué (respectivement O, C et D), puis le nombre de fichiers (N) traités jusqu'à présent, suivi du chemin en cours de traitement.

Lorsque vous utilisez --stats, vous obtiendrez des statistiques sur la quantité de données ajoutées - la taille dédupliquée "Cette archive" y est la plus intéressante car c'est la quantité qui fera croître votre dépôt. Veuillez noter que les statistiques "Toutes les archives" se réfèrent à l'état après la création. De plus, les options --stats et --dry-run sont mutuellement exclusives car les données ne sont pas réellement compressées et dédupliquées lors d'une exécution à blanc.

Pour plus d'aide sur les modèles d'inclusion/exclusion, consultez la sortie de la commande borg_patterns.

Pour plus d'aide sur les espaces réservés, consultez la sortie de la commande borg_placeholders.

Lecture depuis stdin

Si vous spécifiez '-' comme un des chemins à archiver, Borg lira les données depuis l'entrée standard et créera un fichier nommé 'stdin' dans l'archive. Cela peut être utile pour rediriger la sortie d'une autre commande vers Borg.

Cependant, il existe des cas où l'on souhaite archiver des données provenant de stdin sans qu'elles soient nécessairement traitées comme un fichier normal.

L'option --content-from-command vous permet de spécifier une commande dont la sortie sera archivée.

Les options --stdin-name, --stdin-user, --stdin-group et --stdin-mode vous permettent de spécifier les métadonnées du fichier 'stdin' dans l'archive.

Exemple

Pour archiver le contenu de tar -c . avec le nom tar-data dans l'archive nommée myarchive, vous pouvez utiliser :

borg create --content-from-command myarchive tar-data='tar -c .'

Pour archiver l'intégralité d'un système de fichiers (par exemple, /) tout en traitant les flux provenant de stdin, vous pouvez utiliser :

cat / | borg create --stdin-name rootfs myarchive -

L'option --paths-from-stdin est utile lorsque vous souhaitez passer une liste de chemins à Borg via stdin. Chaque chemin doit être sur une ligne séparée (ou séparé par un autre délimiteur spécifié avec --paths-delimiter).

echo "/home/user/Documents" | borg create --paths-from-stdin myarchive::mybackup /

--paths-from-command est une combinaison de --content-from-command et --paths-from-stdin. Elle interprète son argument comme une commande, et utilise la sortie de cette commande comme liste de chemins à sauvegarder.

borg create --paths-from-command myarchive::mybackup find /home/user -name "*.txt"

Dans cet exemple, la commande find /home/user -name "*.txt" sera exécutée, et sa sortie (une liste de fichiers .txt dans /home/user) sera utilisée comme chemins à sauvegarder dans l'archive myarchive::mybackup.

# Sauvegarder ~/Documents dans une archive nommée "my-documents"
$ borg create /chemin/vers/depot::my-documents ~/Documents
# idem, mais lister tous les fichiers au fur et à mesure du traitement
$ borg create --list /chemin/vers/depot::my-documents ~/Documents
# Sauvegarder /mnt/disk/docs, mais supprimer le préfixe de chemin en utilisant le hack slashdot
$ borg create /chemin/vers/depot::docs /mnt/disk/./docs
# Sauvegarder ~/Documents et ~/src mais exclure les fichiers pyc
$ borg create /chemin/vers/depot::my-files \
    ~/Documents                       \
    ~/src                             \
    --exclude '*.pyc'
# Sauvegarder les répertoires personnels en excluant les miniatures d'images (c'est-à-dire seuls
# /home/<un répertoire>/.thumbnails sont exclus, pas /home/*/*/.thumbnails etc.)
$ borg create /chemin/vers/depot::my-files /home \
    --exclude 'sh:home/*/.thumbnails'
# Sauvegarder le système de fichiers racine dans une archive nommée "root-YYYY-MM-DD"
# utiliser la compression zlib (bonne, mais lente) - par défaut est lz4 (rapide, faible taux de compression)
$ borg create -C zlib,6 --one-file-system /chemin/vers/depot::root-{now:%Y-%m-%d} /
# Sauvegarder vers un hôte distant (style "push") via ssh sur le port 2222,
# en se connectant en tant qu'utilisateur "borg" et en stockant dans /chemin/vers/depot
$ borg create ssh://borg@backup.example.org:2222/chemin/vers/depot::{fqdn}-root-{now} /
# Sauvegarder un hôte distant localement (style "pull") en utilisant sshfs
$ mkdir sshfs-mount
$ sshfs root@example.com:/ sshfs-mount
$ cd sshfs-mount
$ borg create /chemin/vers/depot::example.com-root-{now:%Y-%m-%d} .
$ cd ..
$ fusermount -u sshfs-mount
# Faire un grand effort de déduplication à granularité fine (gros surcoût de gestion

# documentation interne - mêmes paramètres que borg < 1.0 ou attic) :
$ borg create --chunker-params buzhash,10,23,16,4095 /chemin/vers/depot::small /smallstuff
# Sauvegarder un périphérique brut (ne doit pas être actif/en usage/monté à ce moment-là)
$ borg create --read-special --chunker-params fixed,4194304 /chemin/vers/depot::my-sdx /dev/sdX
# Sauvegarder une image de disque clairsemée (ne doit pas être actif/en usage/monté à ce moment-là)
$ borg create --sparse --chunker-params fixed,4194304 /chemin/vers/depot::my-disk my-disk.raw
# Pas de compression (none)
$ borg create --compression none /chemin/vers/depot::arch ~
# Super rapide, faible compression (lz4, par défaut)
$ borg create /chemin/vers/depot::arch ~
# Moins rapide, compression plus élevée (zlib, N = 0..9)
$ borg create --compression zlib,N /chemin/vers/depot::arch ~
# Encore plus lent, compression encore plus élevée (lzma, N = 0..9)
$ borg create --compression lzma,N /chemin/vers/depot::arch ~
# Compresser uniquement les données compressibles avec lzma,N (N = 0..9)
$ borg create --compression auto,lzma,N /chemin/vers/depot::arch ~
# Utiliser le nom d'hôte court, le nom d'utilisateur et l'heure actuelle dans le nom de l'archive

NOTE

S

Les motifs --exclude ne sont pas comme dans tar. Dans tar --exclude .bundler/gems exclura foo/.bundler/gems. Dans borg ce ne sera pas le cas, vous devez utiliser --exclude '*/.bundler/gems' pour obtenir le même

effet.

En plus de l'utilisation des motifs --exclude, il est possible d'utiliser --exclude-if-present pour spécifier le nom d'un objet du système de fichiers (par ex. un nom de fichier ou de dossier) qui, lorsqu'il est contenu dans un autre dossier, empêchera le dossier conteneur d'être sauvegardé. Par défaut, le dossier conteneur et tout son contenu seront omis de la sauvegarde. Cependant, si vous souhaitez inclure uniquement les objets spécifiés par --exclude-if-present dans votre sauvegarde, et ne pas inclure d'autres contenus du dossier conteneur, cela peut être activé en utilisant l'option --keep-exclude-tags

.

L'option -x ou --one-file-system exclut les répertoires qui sont des points de montage (et tout ce qu'ils contiennent). Elle détecte les points de montage en comparant le numéro de périphérique de la sortie de stat() du répertoire et de son répertoire parent. Plus précisément, elle exclut les répertoires pour lesquels stat() rapporte un numéro de périphérique différent de celui de leur parent. En général : sachez qu'il existe des répertoires avec des numéros de périphérique différents de leur parent, que le noyau ne considère pas comme des points de montage, et inversement. Les exemples sous Linux pour cela sont les montages par liaison (possiblement le même numéro de périphérique, mais toujours un point de montage) et tous les sous-volumes d'un système de fichiers Btrfs (numéros de périphérique différents de le parent mais pas nécessairement des points de montage). Les exemples sous macOS sont les montages APFS d'une installation macOS typique. Par conséquent, lors de l'utilisation de --one-file-system, vous devriez vérifier que la sauvegarde fonctionne comme

prévu.

Drapeaux des

éléments

--list produit une liste de tous les fichiers, répertoires et autres éléments du système de fichiers considérés (qu'ils aient ou non des changements de contenu). Pour chaque élément, il préfixe un drapeau d'une lettre qui indique le type et/ou le statut de

l'élément.

Si vous n'êtes intéressé que par un sous-ensemble de cette sortie, vous pouvez donner par ex. --filter=AME et cela n'affichera que les fichiers réguliers avec le statut A, M ou E (voir ci-dessous)

.

Un caractère en majuscule représente le statutdes fichiers réguliers par rapport au cache « files » (pas par rapport au dépôt – c'est un problème si le cache de fichiers n'est pas utilisé). Les métadonnées sont stockées dans tous les cas et pour 'A' et 'M', de nouveaux blocs de données sont également stockés. Pour 'U', tous les blocs de données se réfèrent à des blocs déjà existants.

  • 'A' = fichier régulier, ajouté (voir aussi a_status_oddity dans la FAQ)
  • 'M' = fichier régulier, modifié
  • 'U' = fichier régulier, inchangé
  • 'C' = fichier régulier, il a changé pendant que nous le sauvegardions
  • 'E' = fichier régulier, une erreur s'est produite lors de l'accès/lecture de ce fichier

Une minuscule signifie un type de fichier autre qu'un fichier régulier ; borg ne stocke généralement que leurs métadonnées :

  • 'd' = répertoire
  • 'b' = périphérique bloc
  • 'c' = périphérique caractère
  • 'h' = fichier régulier, lien physique (vers des inodes déjà vus)
  • 's' = lien symbolique
  • 'f' = fifo

Les autres indicateurs utilisés incluent :

  • 'i' = les données de sauvegarde ont été lues depuis l'entrée standard (stdin)
  • '-' = exécution à blanc, l'élément n'a pas été sauvegardé
  • 'x' = exclu, l'élément n'a pas été sauvegardé
  • '?' = code de statut manquant (si vous voyez cela, veuillez signaler un bug !)

Lecture des données de sauvegarde depuis stdin

Il existe deux méthodes pour lire depuis stdin. Soit spécifiez - comme chemin et redirigez directement vers borg :

backup-vm --id myvm --stdout | borg create REPO::ARCHIVE -

Ou utilisez --content-from-command pour que Borg gère l'exécution de la commande et le piping. Si vous le faites, le premier argument PATH est interprété comme la commande à exécuter et tous les arguments supplémentaires sont traités comme des arguments de la commande :

borg create --content-from-command REPO::ARCHIVE -- backup-vm --id myvm --stdout

-- est utilisé pour s'assurer que --id et --stdout ne sont pas considérés comme des arguments pour borg mais plutôt pour backup-vm.

La différence entre les deux approches est que le piping vers borg crée une archive même si la commande qui redirige vers borg se termine avec un échec. Dans ce cas, on peut se retrouver avec une sortie tronquée sauvegardée. Utiliser --content-from-command, en revanche, garantit que borg échouera sans créer d'archive si la commande échoue. La commande est considérée comme échouée lorsqu'elle a renvoyé un code de sortie non nul.

La lecture depuis stdin produit uniquement un flux de données sans métadonnées de fichier associées, et le cache de fichiers n'est pas nécessaire du tout. Il est donc sûr de le désactiver via --files-cache disabled et d'accélérer un peu la création de la sauvegarde.

Par défaut, le contenu lu depuis stdin est stocké dans un fichier nommé 'stdin'. Utilisez --stdin-name pour changer le nom.

Alimenter tous les chemins de fichiers depuis l'extérieur

Habituellement, vous donnez un chemin de départ (racine de récursion) à borg, puis borg parcourt automatiquement, trouve et sauvegarde tous les objets du système de fichiers qui s'y trouvent (en tenant compte éventuellement des règles d'inclusion/exclusion).

Si vous avez besoin de plus de contrôle et que vous souhaitez donner chaque chemin d'objet du système de fichiers individuellement à borg (peut-être en implémentant votre propre récursion ou vos propres règles), vous pouvez utiliser --paths-from-stdin ou --paths-from-command (avec ce dernier, borg échouera à créer une archive si la commande échoue).

Borg prend en charge les chemins avec le hack slashdot pour supprimer les préfixes de chemin ici aussi. Faites donc attention à ne pas le déclencher involontairement.
