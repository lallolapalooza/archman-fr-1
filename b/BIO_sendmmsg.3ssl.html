BIO_sendmmsg(3ssl)

Paquet: openssl

Licences: Apache-2.0

BIO_SENDMMSG(3ssl) OpenSSL BIO_SENDMMSG(3ssl)

NOM

BIO_sendmmsg, BIO_recvmmsg, BIO_dgram_set_local_addr_enable, BIO_dgram_get_local_addr_enable, BIO_dgram_get_local_addr_cap, BIO_err_is_non_fatal - envoyer et recevoir plusieurs datagrammes dans un seul appel

SYNOPSIS

#include <openssl/bio.h>
typedef struct bio_msg_st {
    void *data;
    size_t data_len;
    BIO_ADDR *peer, *local;
    uint64_t flags;
} BIO_MSG;
int BIO_sendmmsg(BIO *b, BIO_MSG *msg,
                 size_t stride, size_t num_msg, uint64_t flags,
                 size_t *msgs_processed);
int BIO_recvmmsg(BIO *b, BIO_MSG *msg,
                 size_t stride, size_t num_msg, uint64_t flags,
                 size_t *msgs_processed);
int BIO_dgram_set_local_addr_enable(BIO *b, int enable);
int BIO_dgram_get_local_addr_enable(BIO *b, int *enable);
int BIO_dgram_get_local_addr_cap(BIO *b);
int BIO_err_is_non_fatal(unsigned int errcode);

DESCRIPTION

BIO_sendmmsg() et BIO_recvmmsg() peuvent être utilisées pour envoyer et recevoir plusieurs messages dans un seul appel à un BIO. Elles sont analogues à sendmmsg(2) et recvmmsg(2) sur les systèmes d'exploitation qui fournissent ces fonctions.

La structure BIO_MSG fournit un sous-ensemble de la fonctionnalité de la structure struct msghdr définie par POSIX. Ces fonctions acceptent un tableau de structures BIO_MSG . Lors d'une invocation particulière, ces fonctions peuvent traiter toutes les structures passées, certaines d'entre elles, ou aucune. Cela est indiqué par la valeur stockée dans *msgs_processed, qui exprime le nombre de messages traités.

L'appelant doit définir le membre data d'un BIO_MSG sur un tampon contenant les données à envoyer, ou à remplir avec un message reçu. data_len doit être défini sur la taille du tampon en octets. Si le BIO_MSG donné est traité (en d'autres termes, si l'entier renvoyé par la fonction est supérieur ou égal à l'indice de tableau de ce BIO_MSG), data_len sera modifié pour spécifier la quantité réelle de données envoyées ou reçues.

Le champ flags d'un BIO_MSG fournit des drapeaux par message en entrée à l'invocation. Si l'invocation traite ce BIO_MSG, le champ flags est écrit avec les drapeaux par message en sortie, ou zéro si aucun drapeau de ce type n'est applicable.

Actuellement, aucun drapeau par message en entrée ou en sortie n'est défini et ce champ doit être défini à zéro avant d'appeler BIO_sendmmsg() ou BIO_recvmmsg().

L'argument flags de BIO_sendmmsg() et BIO_recvmmsg() fournit des drapeaux globaux qui affectent l'ensemble de l'invocation. Aucun drapeau global n'est actuellement défini et cet argument doit être défini à zéro.

Lorsque ces fonctions sont utilisées pour envoyer et recevoir des datagrammes, le champ peer d'un BIO_MSG permet de spécifier l'adresse de destination des datagrammes envoyés par datagramme, et de déterminer l'adresse source des datagrammes reçus. Le champ peer doit être défini pour pointer vers un BIO_ADDR, qui sera lu par BIO_sendmmsg() et utilisé comme adresse de destination pour les datagrammes envoyés, et écrit par BIO_recvmmsg() avec l'adresse source des datagrammes reçus.

De même, le champ local d'un BIO_MSG permet de spécifier l'adresse source des datagrammes envoyés par datagramme, et de déterminer l'adresse de destination des datagrammes reçus. Contrairement à peer, la prise en charge de local doit être activée explicitement sur un BIO avant de pouvoir être utilisée ; voir BIO_dgram_set_local_addr_enable(). Si local est non-NULL dans un BIO_MSG et que la prise en charge de local n'a pas été activée, le traitement de ce BIO_MSG échoue.

peer et local doivent être définis à NULL s'ils ne sont pas requis. La prise en charge de local peut ne pas être disponible sur toutes les plateformes ; sur ces plateformes, ces fonctions échouent toujours si local est non-NULL.

Si local est spécifié et que la prise en charge de l'adresse locale est activée, mais que le système d'exploitation ne rapporte pas d'adresse locale pour un message reçu spécifique, le BIO_ADDR auquel il pointe sera effacé (famille d'adresse définie sur "AF_UNSPEC"). Cela est connu pour se produire sur Windows lorsqu'un paquet est reçu qui a été envoyé par le système local, que l'adresse de destination du paquet soit l'adresse de bouclage ou l'adresse IP d'une interface locale non-bouclage. Cela est également connu pour se produire sur macOS dans certaines circonstances, comme pour les paquets envoyés avant que la prise en charge de l'adresse locale n'ait été activée pour une socket de réception. Ce sont des limitations spécifiques au système d'exploitation. En tant que tels, les utilisateurs de cette API utilisant la prise en charge de l'adresse locale doivent s'attendre à recevoir parfois un BIO_ADDR local effacé au lieu de la valeur correcte.

L'argument stride doit être défini sur sizeof(BIO_MSG). Cet argument facilite la rétrocompatibilité si des champs sont ajoutés à BIO_MSG. Les appelants doivent initialiser BIO_MSGà zéro.

num_msg doit être envoyé au nombre maximum de messages à envoyer ou recevoir, qui est également la longueur du tableau pointé par msg.

msgs_processed doit être non-NULL et pointer vers un entier écrit avec le nombre de messages traités avec succès ; voir la section VALEURS RENVOYÉES pour plus de détails.

Contrairement à la plupart des fonctions BIO, ces fonctions prennent explicitement en charge l'utilisation multi-thread. Plusieurs écrivants concurrents et plusieurs lecteurs concurrents du même BIO sont autorisés dans n'importe quelle combinaison. En tant que telles, ces fonctions ne définissent pas, ne réinitialisent pas ou ne modifient pas autrement les drapeaux de nouvelle tentative du BIO. La valeur de retour doit être utilisée pour déterminer si une opération doit être réessayée ; voir ci-dessous.

La prise en charge de l'utilisation concurrente s'étend à BIO_sendmmsg() et BIO_recvmmsg() uniquement, et aucune autre fonction ne peut être appelée sur un BIO donné pendant qu'un appel à BIO_sendmmsg() ou BIO_recvmmsg() est en cours, ou vice versa.

BIO_dgram_set_local_addr_enable() et BIO_dgram_get_local_addr_enable() contrôlent si la prise en charge de l'adresse locale est activée. Pour activer la prise en charge de l'adresse locale, appelez BIO_dgram_set_local_addr_enable() avec un argument de 1. L'appel échouera si la prise en charge de l'adresse locale n'est pas disponible pour la plateforme. BIO_dgram_get_local_addr_enable() récupère la valeur définie par BIO_dgram_set_local_addr_enable().

BIO_dgram_get_local_addr_cap() détermine si le BIO est capable de prendre en charge les adresses locales.

BIO_err_is_non_fatal() détermine si un code d'erreur emballé représente une erreur de nature transitoire.

NOTES

Certaines implémentations des méthodes BIO BIO_sendmmsg() et BIO_recvmmsg() peuvent toujours traiter au plus un message à la fois, par exemple lorsque la fonctionnalité au niveau du système d'exploitation pour transmettre ou recevoir plusieurs messages à la fois n'est pas disponible.

VALEURS RENVOYÉES

En cas de succès, les fonctions BIO_sendmmsg() et BIO_recvmmsg() renvoient 1 et écrivent le nombre de messages traités avec succès (qui n'a pas besoin d'être non nul) dans msgs_processed. Lorsqu'une valeur positive n est écrite dans msgs_processed, toutes les entrées du tableau BIO_MSG de 0 à n-1 inclus ont leurs champs data_len et flags mis à jour avec les résultats de l'opération sur ce message. Si l'appel était à BIO_recvmmsg() et que les champs peer ou local de ce message sont non-NULL, les structures BIO_ADDR auxquelles ils pointent sont écrites avec l'adresse pertinente.

En cas d'échec, les fonctions BIO_sendmmsg() et BIO_recvmmsg() renvoient 0 et écrivent zéro dans msgs_processed. Ainsi, msgs_processed est toujours écrit quel que soit le résultat de l'appel de fonction.

Si BIO_sendmmsg() et BIO_recvmmsg() échouent, elles lèvent toujours une erreur ERR_LIB_BIO en utilisant ERR_raise(3). Toute erreur peut être levée, mais les suivantes en particulier peuvent être notées :

BIO_R_LOCAL_ADDR_NOT_AVAILABLE
Le champ local a été défini sur une valeur non-NULL, mais la prise en charge de l'adresse locale n'est pas disponible ou n'est pas activée sur le BIO.
BIO_R_PEER_ADDR_NOT_AVAILABLE
Le champ peer a été défini sur une valeur non-NULL, mais la prise en charge de l'adresse du pair n'est pas disponible sur le BIO.
BIO_R_UNSUPPORTED_METHOD
La méthode BIO_sendmmsg() ou BIO_recvmmsg() n'est pas prise en charge sur le BIO.
BIO_R_NON_FATAL
L'appel a échoué en raison d'une erreur transitoire non fatale (par exemple, parce que le BIO est en mode non bloquant et que l'appel aurait autrement bloqué).

Les implémentations de cette interface qui n'effectuent pas d'appels système et qui transmettent donc les codes d'erreur système via ERR_LIB_SYS (par exemple, les implémentations basées sur la mémoire) doivent émettre ce code de raison pour indiquer une échec transitoire. Cependant, les utilisateurs de cette interface ne doivent pas tester ce code de raison directement, car il existe plusieurs codes d'erreur empaquetés possibles représentant un échec transitoire ; utilisez plutôt BIO_err_is_non_fatal() (discuté ci-dessous).

Erreurs de socket
Les erreurs de socket au niveau du système d'exploitation sont signalées à l'aide d'une erreur avec le code de bibliothèque ERR_LIB_SYS; pour un code d'erreur empaqueté errcode où "ERR_SYSTEM_ERROR(errcode) == 1", le code d'erreur de socket au niveau du système d'exploitation peut être récupéré à l'aide de ERR_GET_REASON(errcode). Le code d'erreur empaqueté peut être récupéré en appelant ERR_peek_last_error(3) après que l'appel à BIO_sendmmsg() ou BIO_recvmmsg() a retourné 0.
Erreurs non fatales
On peut déterminer si une erreur est transitoire en passant le code d'erreur empaqueté à BIO_err_is_non_fatal(). Les appelants devraient faire cela au lieu de tester le code de raison directement, car il existe de nombreux codes d'erreur possibles pouvant indiquer une erreur transitoire, dont beaucoup sont spécifiques au système.

Les tiers qui implémentent des BIO personnalisés prenant en charge les méthodes BIO_sendmmsg() ou BIO_recvmmsg() doivent noter qu'il est une partie requise du contrat de l'API qu'une erreur soit toujours levée lorsque l'une de ces fonctions retourne 0.

BIO_dgram_set_local_addr_enable() retourne 1 si la prise en charge de l'adresse locale a été activée ou désactivée avec succès, et 0 sinon.

BIO_dgram_get_local_addr_enable() retourne 1 si l'indicateur d'activation de la prise en charge de l'adresse locale a été récupéré avec succès.

BIO_dgram_get_local_addr_cap() retourne 1 si le BIO peut prendre en charge les adresses locales.

BIO_err_is_non_fatal() retourne 1 si le code d'erreur empaqueté passé représente une erreur de nature transitoire.
