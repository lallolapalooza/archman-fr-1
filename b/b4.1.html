NOM

B4 - Travailler avec des soumissions de code dans une archive public-inbox

SYNOPSIS

b4 {mbox,am,shazam,pr,diff,ty,kr,prep,send,trailers} [options]

DESCRIPTION

C'est une utilitaire d'aide pour travailler avec des correctifs et des demandes de fusion (pull requests) mis à disposition via une archive public-inbox comme lore.kernel.org. Elle est écrite pour simplifier la participation aux flux de travail basés sur les correctifs, comme ceux utilisés dans le développement du noyau Linux.

Le nom « b4 » a été choisi pour sa facilité de frappe et parce que B-4 était le prédécesseur de Lore et Data dans l'univers de Star Trek.

La documentation complète est disponible sur https://b4.docs.kernel.org/ .

SOUS-COMMANDES

Orienté mainteneurs :

  • mbox: Télécharger un fil de discussion en tant que fichier mbox
  • am: Créer un fichier mbox prêt pour git-am
  • shazam: Appliquer une série de correctifs à des dépôts git
  • pr: Travailler avec des demandes de fusion
  • ty: Créer des réponses modèles pour les correctifs et demandes de fusion traités
  • diff: Afficher des différences de style range-diff entre les versions de correctifs
  • kr: (STUB) Opérer sur des porte-clés compatibles patatt

Orienté contributeurs :

  • prep: préparer votre série pour la soumission
  • trailers: récupérer et appliquer les trailers de revue de code
  • send: envoyer votre série pour révision sur les listes de diffusion

Pour les options complètes et leur description, veuillez consulter b4 --help et b4 sous-commande --help.

b4 mbox

Cette commande permet de récupérer des fils de discussion entiers depuis une instance public-inbox distante. Vous pouvez ouvrir le fichier mbox résultant avec la plupart des clients de messagerie pour des actions comme répondre aux conversations ou réviser les soumissions de correctifs.

Vous pouvez fournir le message soit comme msgid, soit comme URL complète vers une archive public-inbox, ou vous pouvez le transmettre via stdin.

Pour les options et leur description, voir b4 mbox --help.

Exemples

b4 mbox [msgid]
Télécharger un fil de discussion depuis le serveur public-inbox par défaut et l'enregistrer dans le répertoire courant sous forme de fichier .mbox.
b4 mbox -m ~/Mail [msgid]
Télécharger un fil de discussion depuis votre dossier ~/Mail et l'enregistrer dans le répertoire courant sous forme de fichier .mbox.
b4 mbox -fo ~/Mail [public-inbox-url]
Télécharger le fil de discussion depuis ce serveur public-inbox et l'ajouter à votre boîte aux lettres existante, en filtrant les doublons déjà présents dans votre dossier de boîte aux lettres.

b4 am

Cette commande permet de récupérer des fils de discussion depuis une instance public-inbox et de les préparer pour les appliquer à un dépôt git à l'aide de la commande « git am ». Elle effectuera automatiquement les opérations suivantes :

  • choisir la dernière version soumise de la série (elle peut aussi vérifier l'existence de fils plus récents en utilisant -c )
  • vérifier les signatures DKIM et l'attestation patatt sur tous les correctifs et messages de revue de code
  • compiler tous les trailers de revue de code soumis (Reviewed-by, Acked-by, etc.) et les placer dans le message de commit
  • ajouter votre propre trailer Signed-off-by (avec -s)
  • reconstituer la série à partir de mises à jour partielles (par exemple, quelqu'un soumet une v2 d'un seul correctif au lieu de reconstituer la série entière)
  • deviner à quel endroit de l'historique de l'arbre les correctifs appartiennent, si le commit de base exact n'est pas spécifié (avec -g)
  • préparer l'arbre pour une fusion à trois voies (avec -3)
  • cherry-pick un sous-ensemble de correctifs d'une grande série (avec -P)

Remarque : À moins que vous n'intendiez de faire un travail préparatoire sur la série avant de l'appliquer au dépôt git (par exemple, une fusion à trois voies), vous devriez envisager d'utiliser b4 shazam pour appliquer la série récupérée.

Pour les options et leur description, voir b4 am --help.

Exemples

b4 am -sl [msgid]
Télécharger un fil de discussion depuis le serveur public-inbox par défaut, appliquer tous les trailers de suivi, ajouter votre propre trailer Signed-Off-By ainsi qu'un trailer Link: indiquant l'origine du correctif, puis enregistrer le fichier .mbox résultant dans le répertoire courant, prêt à être appliqué par « git am ».
b4 am -sl -P 1-3 [msgid]
Identique à l'exemple précédent, mais ne sélectionne que les correctifs 1, 2, 3 de la série entière.
b4 am -3 [msgid]
Télécharger la série et préparer l'arbre git local pour une fusion à trois voies en s'assurant que tous les blobs d'index existent.
b4 am --check [msgid]
Télécharger la série et montrer si elle passe les vérifications. Vous pouvez spécifier la commande à l'aide de l'option de configuration b4.am-perpatch-check-cmd . Pour le noyau Linux, la valeur par défaut sera l'ensemble d'options le plus courant de checkpatch.pl .

b4 shazam

C'est très similaire à b4 am, mais appliquera aussi les correctifs directement à l'arbre git courant en utilisant git am. Alternativement, lorsqu'il est utilisé avec -H, il peut récupérer la série de correctifs dans FETCH_HEAD comme s'il s'agissait d'une demande de fusion, prête à être révisée et fusionnée. B4 utilise la lettre de couverture comme modèle pour le commit de fusion.

Si vous voulez invoquer automatiquement git-merge, vous pouvez utiliser -M au lieu de -H. B4 ouvre automatiquement l'éditeur vous permettant de modifier le message du commit de fusion.

Remarque : les options -M et -H fonctionnent le mieux pour les séries dont les informations base-commit correspondent à un objet dans votre arbre local.

Pour les options et leur description, voir b4 shazam --help.

Exemples

b4 shazam -sl -M [msgid]
Télécharger un fil de discussion depuis le serveur public-inbox par défaut, appliquer tous les trailers de suivi, ajouter votre propre trailer Signed-Off-By ainsi qu'un trailer Link: avec l'origine du correctif, puis fusionner ce commit dans le dépôt git courant en utilisant la lettre de couverture comme modèle pour le commit de fusion.
b4 shazam -sl -M --merge-base v6.4-rc4 [msgid]
Identique à l'exemple précédent, mais force le merge-base à être l'objet commit-ish fourni au lieu de celui listé dans la série de correctifs elle-même.

b4 pr

Cette commande sert à travailler avec des demandes de fusion soumises en utilisant git-request-pull. Elle offre les avantages suivants par rapport à l'utilisation directe de git :

  • elle peut vérifier si la fusion est déjà appliquée avant d'effectuer un git fetch
  • elle vérifie la signature sur le tag ou le commit de tête spécifié dans la demande de fusion
  • elle peut suivre les demandes de fusion appliquées et envoyer des réponses aux soumetteurs en utilisant b4 ty

Pour les options et leur description, voir b4 pr --help.

Exemples

b4 pr [msgid]
Télécharger le message contenant la demande de fusion et l'appliquer à l'arbre git courant.

b4 ty

Si vous avez récupéré et appliqué des correctifs à votre arbre, vous devriez pouvoir lancer le « auto-thankanator », qui utilise le suivi de patch-id et du sujet de commit pour déterminer quelles séries parmi celles que vous avez récupérées vous avez déjà appliquées à votre arbre. Le processus est généralement assez rapide et assez précis.

Pour envoyer des courriels directement en utilisant -S, vous devriez avoir une section [sendemail] configurée quelque part dans vos fichiers de configuration git applicables. Par défaut, b4 ty écrit des fichiers .thanks dans le répertoire courant que vous pouvez modifier et envoyer en utilisant une commande comme mutt -f thanks.file.

Pour les options et leurs descriptions, voir b4 ty --help.

Exemples

b4 ty -a -S
Localiser toutes les séries récupérées que vous avez appliquées au dépôt git actuel et envoyer des remerciements à tous les membres de la conversation.
b4 ty -a -S --dry-run
Identique à ci-dessus, mais au lieu d'envoyer réellement le message, afficher d'abord ce que le message sera.

b4 diff

La sous-commande diff permet de comparer deux révisions différentes de la même série de patches en utilisant git range-diff. Notez que pour effectuer la comparaison range-diff, les deux révisions doivent s'appliquer proprement à l'arbre actuel, ce qui n'est pas toujours possible à réaliser.

Pour les options et leurs descriptions, voir b4 diff --help.

Exemples

b4 diff [msgid-of-vN]
Récupère le fil correspondant au msgid spécifié et tente de localiser automatiquement la version précédente de la série. Si cela réussit, affiche la sortie de git range-diff comparant les différences des patches.

b4 kr

Cette sous-commande permet de maintenir un trousseau local de clés de contributeurs.

Note : cette partie de b4 est en développement actif avec des améliorations prévues à court terme.

Pour les options et leurs descriptions, voir b4 kr --help.

Exemples

b4 kr --show-keys [msgid]
Récupère le fil spécifié et affiche toutes les clés cryptographiques utilisées pour attester les patches.

b4 prep, trailers, send

Ces commandes permettent de préparer et de soumettre une série de patches pour examen sur la liste de diffusion. La documentation complète est disponible en ligne à l'adresse suivante :


https://b4.docs.kernel.org/en/latest/contributor/overview.html

Pour les options, voir la sortie de b4 prep --help, b4 trailers --help et b4 send --help.

Exemples

b4 prep -n my-new-feature -f v6.4-rc4
Démarrer une nouvelle branche, en la créant à partir de la balise v6.4-rc4, et la préparer pour y ajouter d'autres patches.
b4 prep --edit-cover
Modifier la lettre de présentation de la série actuelle. Cette étape n'est pas requise pour la plupart des soumissions d'un seul patch.
b4 prep --auto-to-cc
Trouver toutes les adresses devant recevoir une copie de la soumission de la série de patches et les ajouter à la lettre de présentation.
b4 prep --check
Exécuter les vérifications configurées sur votre série pour identifier d'éventuels problèmes. Pour le noyau Linux, cela exécute checkpatch.pl avec l'ensemble de paramètres recommandé.
b4 send -o /tmp/outdir
Générer les patches que b4 va envoyer et les enregistrer dans le répertoire spécifié. Cela vous permet d'examiner la série avant de les envoyer réellement.
b4 send --preview-to [addr1@example.com addr2@example.com]
Envoyer une version « aperçu » de la série pour que quelqu'un la vérifie avant de la soumettre en amont.
b4 trailers -u
Récupérer les trailers de révision de code fournis pour votre série et les appliquer à la branche actuelle.

CONFIGURATION

La configuration de b4 est gérée via git-config(1), vous pouvez donc la stocker soit dans le fichier global $HOME/.gitconfig , soit dans un fichier .git/config par dépôt si votre flux de travail change selon le projet.

Pour voir les options de configuration disponibles, voir la documentation en ligne à l'adresse
https://b4.docs.kernel.org/en/latest/config.html

PROXY DES REQUÊTES

Les commandes effectuant des requêtes HTTP distantes peuvent être configurées pour utiliser un proxy en définissant la variable d'environnement HTTPS_PROXY , comme décrit dans
https://docs.python-requests.org/en/latest/user/advanced/#proxies .
