DESCRIPTIO

N

Le but de signer un dépôt est d'empêcher la falsification des paquets, que ce soit pendant la transmission ou sur la machine hôte du dépôt. Idéalement, vous devriez générer et signer les manifestes du dépôt sur une machine de compilation distincte située derrière un pare-feu. De cette façon, si (ou, en fait, lorsque) votre machine hôte est compromise, il sera difficile pour un attaquant de compromettre les paquets du dépôt sans être remarqué. Comme la clé du dépôt est conservée sur la machine de compilation (ou, mieux encore, sur un appareil PIV/PKCS#11 à sens unique ; voir ci-dessous), ils ne pourront pas re-signer le dépôt modifié. bpkg utilise la cryptographie à clé publique X.509 pour la signature des dépôts. Actuellement, seule l'authentification par

certificat

« first use » explicite est implémentée. C'est-à-dire que, pour un certificat inconnu (de cette configuration bpkg), les informations du sujet et l'empreinte numérique sont présentées à l'utilisateur. Si l'utilisateur confirme l'authenticité du certificat, alors celui-ci est ajouté à la configuration et tout dépôt qui présentera ce certificat à l'avenir sera considéré comme digne de confiance sans autres confirmations, à condition que son nom corresponde au sujet du certificat (voir ci-dessous). À l'avenir, un modèle basé sur une autorité de certification (CA) pourrait être ajouté. Le reste de ce guide montre comment créer une paire clé/certificat

pour

la signature de dépôts pkg et comment l'utiliser pour signer un dépôt. À la fin, il explique également brièvement comment stocker la clé privée sur un appareil PIV/PKCS#11 en prenant Yubikey 4 comme exemple. 1. Générer la clé

privée
La première étape consiste à générer la clé
privée :

$ openssl genrsa -aes256 2048 >key.pem 
Si vous souhaitez générer une clé sans protection par mot de passe
        (ce qui n'est pas une bonne idée, sauf pour les tests),
laissez l'option

-aes256 de côté. Vous devrez peut-être aussi ajouter -nodes en fonction de votre configuration openss

l(
1).
2. Générer le
certificat

Créez ensuite le fichier de configuration du certificat en enregistrant ce qui suit dans cert.conf. Vous voudrez peut-être le conserver au cas où vous auriez besoin de renouveler un certificat expiré, etc. 
name  = example.com
org   = Example, Inc
email = admin@example.com
[req]
distinguished_name = req_distinguished_name
x509_extensions    = v3_req
prompt             = no
utf8               = yes
[req_distinguished_name]
O  = $org
CN = name:$name
[v3_req]
keyUsage         = critical,digitalSignature
extendedKeyUsage = critical,codeSigning
subjectAltName   = email:
$email

Ajustez les trois premières lignes pour qu'elles correspondent à vos informations. Si le dépôt est hébergé par une organisation, utilisez le nom de l'organisation pour org. Si vous l'hébergez en tant qu'individu, mettez votre nom complet et réel là-bas. Utiliser un type d'alias ou de surnom est une mauvaise idée (sauf, encore une fois, pour les tests). Rappelez-vous que les utilisateurs de votre dépôt seront présentés avec ces informations et s'ils voient qu'il a été signé par quelqu'un nommé SmellySnook, ils ne lui feront probablement pas confiance. Utilisez également une adresse e-mail fonctionnelle au cas où les utilisateurs auraient besoin de vous contacter au sujet de problèmes avec votre certificat. Notez que le préfixe name: dans la

valeur

CN n'est pas une faute de frappe. Le champ name est un préfixe de nom de dépôt canonique avec la partie de type pkg: retirée. Tout dépôt dont le nom canonique commence par ce préfixe peut être authentifié par ce certificat (voir la documentation sur les manifestes de dépôt pour plus d'informations sur les noms canoniques). Par exemple, name example.com correspondra à tout dépôt hébergé sur {,www.,pkg.,bpkg.}example.com. Alors que name example.com/math correspondra à {...}example.com/pkg/1/ma

th mais pas à

{...}example.com/pkg/1/misc. Un nom de certificat peut également contenir un joker de sous-domaine. Un nom joker sous la forme *.example.com correspond à n'importe quel sous-domaine de niveau unique, par exemple foo.example.com mais pas foo.bar.example.com, tandis qu'un nom joker sous la forme**.example.com correspond à n'importe quel sous-domaine, y compris multi-niveaux. Les deux formes ci-dessus ne correspondent pas au domaine lui-même ( example.com dans l'exemple ci-dessus). Si c'est souhaité, les formes *example.com et **example.com devraient être utilisées à la place. Notez que ces formes ne correspondent toujours qu'à des sous-domaines. En d'autres termes, elles ne correspondront

pas à

fooexample.com. Les noms jokers sont moins sécurisés et sont donc normalement utilisés uniquement pour les tests et/ou les

dépôts internes.

openssl req -x509 -new -sha256 -key key.pem \ -config cert.conf -days

730 >cert.pem

5. Utiliser un appareil
PIV/PKCS#11

Cette étape facultative montre comment charger la clé privée dans Yubikey 4 puis l'utiliser à la place de la clé privée elle-même pour signer le dépôt. Notez que vous aurez besoin d'OpenSSL 1.0.2 ou ultérieur pour que la partie signature fonctionne.

Modifiez d'abord la MKEY, la PUK et le PIN de la Yubikey si nécessaire. Vous devriez absolument le faire si elle a encore les valeurs par défaut d'usine. Importez ensuite la clé privée et le certificat dans la Yubikey (remplacez mkey par la clé de

gestion) : 
yubico-piv-tool --key=<mkey> -a import-key -s 9c <key.pem
yubico-piv-tool --key=<mkey> -a import-certificate -s 9c <cert.
pem

Après cela, vous enregistrerez normalement le certificat/la clé privée sur un support de sauvegarde, le stockerez dans un endroit sécurisé et hors ligne, et retirerez la clé de la machine de

compilation.

Pour signer le dépôt avec la Yubikey, spécifiez les options suivantes au lieu de simplement --key comme à l'étape 4 (« SIGN key » est l'étiquette de la clé privée du

slot 9c) : 
bpkg rep-create                                                     \
  --openssl-option pkeyutl:-engine --openssl-option pkeyutl:pkcs11  \
  --openssl-option pkeyutl:-keyform --openssl-option pkeyutl:engine \
  --key "pkcs11:object=SIGN%20key"
/path/to/repository

Notez que pour les versions openssl antérieures à la 3.0.0 bpkg utilise la commande rsautl au lieu de pkeyutl pour

l'opérat
ion de sig
nature de
s données.
