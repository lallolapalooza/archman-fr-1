prj-spec = --directory|-d prj-dir | pkg-spec

.

DESCRIPTIO

N

La commande release gère la version du projet lors de la publication. Plus précisément, elle change d'abord la version d'instantané en la version de publication correspondante dans le fichier manifest de chaque paquet du projet, valide ces changements (sauf si --no-commit est spécifié), étiquette cette validation (sauf si --no-tag est spécifié) et, si --push est spécifié, pousse les changements vers le distant. Sauf si --no-open est spécifié, la commande release ouvre ensuite le prochain cycle de développement en changeant la version en une version d'instantané, en validant ces changements (sauf si --no-commit est spécifié) et, si --push est spécifié, en les poussant vers le distant. Notez que la validation, l'étiquetage et la poussée ne sont actuellement pris en charge que pour les dépôts de projet git(1

).

La commande release peut également être utilisée pour publier une nouvelle révision de paquet en passant l'option --revision. Dans ce mode, release incrémente le composant de révision de la version actuelle dans le fichier manifest de chaque paquet du projet, valide ces changements (sauf si --no-commit est spécifié), étiquette cette validation (sauf si --no-tag est spécifié) et, si --push est spécifié, pousse les changements vers le distant. Dans ce mode, release peut éventuellement être invité à mettre à jour une étiquette existante pour la version actuelle afin qu'elle pointe vers la dernière révision (--current-tag=update) ou à la supprimer (--current-tag=r

emove).

Lors de la publication d'une révision, l'index du dépôt du projet est censé contenir déjà d'autres changements, car pour une révision, tous les changements associés, y compris ceux de la version, doivent appartenir à une seule validation. Alternativement, une révision peut être publiée en amendement d'une ou plusieurs validations existantes à l'aide des options --amend et --squash. Dans ce cas, l'index peut toujours contenir des changements supplémentaires mais ce n'est pas

requis.

La commande release possède également un certain nombre de modes continue qui permettent de terminer des étapes qui ont été précédemment supprimées avec les options --no-* dans les modes principaux ci-dessus. Ce sont --tag qui étiquette la validation de publication et, si --push est spécifié, la pousse également vers le distant, ainsi que --open qui effectue l'ouverture du prochain cycle de développement comme décrit

ci-dessus.

Dans tous les modes qui effectuent une validation, si l'index du dépôt du projet contient déjà d'autres changements, le message de validation est automatiquement ouvert pour édition, sauf si --no-edit est spécifié. L'édition du message de validation en l'absence d'autres changements peut être demandée avec l'option --edit

.

Normalement, release opère sur tous les paquets d'un projet. Si aucun répertoire de projet n'est spécifié, le répertoire de travail courant est supposé et tous les paquets sont publiés, même si le répertoire courant est un répertoire de paquet. Si, cependant, un ou plusieurs répertoires de paquets sont spécifiés explicitement avec --directory|-d, alors release suppose que vous savez ce que vous faites et ne publie que ces paquets. Tous les p

aquets publiés doivent avoir la même version
mais peuvent avoir des révisions différentes.

FICHIERS D'OPTIONS PAR

DÉFAUT

Voir bdep-default-options-files(1) pour un aperçu des fichiers d'options par défaut. Pour la commande release, le répertoire de départ de la recherche est le répertoire du projet. Les fichiers d'options suivants sont recherchés dans chaque répertoire et, s'ils sont trouvés, chargés dans l'ordre indiqué

: 
bdep.options
bdep-release.options
bdep-release-{version|revision|open|tag}.options # (selon le
mode)

Les options de la commande release suivantes ne peuvent pas être spécifiées dans les fichiers d'options par défaut

: 
--directory|-
d --revision
--open --tag
