bdep(1) Manuel des commandes générales bdep(1)

NOM

bdep - gestionnaire de dépendances de projet

SYNTAXE

bdep --help
bdep --version
bdep help [commande | sujet]
bdep [options-communes] commande [options-commande] arguments-commande

DESCRIPTION

Le gestionnaire de dépendances de projet build2 est utilisé pour gérer les dépendances d'un projet pendant le développement.

Pour une description détaillée de toute commande ou sujet d'aide, utilisez la commande help ou consultez la page man correspondante (les pages man ont le préfixe bdep-, par exemple bdep-help(1)). Notez également que options-commande et arguments-commande peuvent être spécifiés dans n'importe quel ordre et options-communes peuvent être spécifiées dans le cadre des options-commande.

Un projet bdep est un répertoire, normalement sous un système de contrôle de version tel que git(1), appelé dépôt de projet. Un projet contient un ou plusieurs paquets. S'il en contient plusieurs, ils sont normalement liés, par exemple, la bibliothèque libhello et le programme hello.

Les paquets d'un projet peuvent dépendre d'autres paquets extérieurs au projet. Pour distinguer les deux, nous les appelons respectivement paquets de projet et paquets de dépendance. Naturellement, nos paquets de projet peuvent être les paquets de dépendance de quelqu'un d'autre.

Un projet simple, à paquet unique, contient le paquet à la racine du dépôt du projet. Par exemple (notez l'emplacement du manifeste et du fichier de verrouillage du paquet) :

hello/
|-- .git/
|-- ...
|-- lockfile
`-- manifest

Voir Manifeste de Paquet (#manifest-package) pour les détails du fichier manifest.

Si un projet contient plusieurs paquets ou si nous souhaitons placer le paquet dans un sous-répertoire, la racine du dépôt du projet doit contenir le fichier packages.manifest qui spécifie les emplacements des paquets. Par exemple :

hello/
|-- .git/
|-- hello/
|   |-- ...
|   |-- lockfile
|   `-- manifest
|-- libhello/
|   |-- ...
|   |-- lockfile
|   `-- manifest
`-- packages.manifest

Pour ce projet, packages.manifest aurait le contenu suivant :

: 1
location: hello/
:
location: libhello/

La racine du dépôt du projet contiendrait généralement également le fichier repositories.manifest qui liste les dépôts fournissant les paquets de dépendance. Par exemple :

hello/
|-- ...
|-- manifest
`-- repositories.manifest

Si notre projet hello souhaitait utiliser libhello comme paquet de dépendance, son repositories.manifest pourrait ressembler à ceci :

: 1
summary: dépôt de projet hello
:
role: prerequisite
location: https://example.com/libhello.git

Voir Manifeste de Liste de Dépôts (#manifest-repository-list) pour les détails du fichier repositories.manifest.

Pour le développement, un projet bdep est associé à une ou plusieurs configurations de construction de bpkg(1). Ces configurations sont utilisées comme support pour construire les paquets du projet et leurs dépendances.

La liste des configurations de construction associées ainsi que la liste des paquets du projet initialisés dans chaque configuration sont stockées dans la base de données de projet de bdep sous le sous-répertoire .bdep/ du répertoire racine du projet. Par exemple :

hello-gcc/     # Configuration de construction pour gcc.
hello-clang/   # Configuration de construction pour clang.
hello/
|-- .bdep/
|-- .git/
`-- ...

Le cœur de la fonctionnalité de bdep est la synchronisation d'état entre le projet et une ou plusieurs configurations de construction associées. Par exemple, si nous listons une nouvelle dépendance dans le fichier manifest du paquet, bdep récupère et configure cette dépendance dans une configuration de construction. De même, si nous mettons à niveau ou à la baisse une dépendance dans une configuration de construction, bdep met à jour l'entrée correspondante dans le fichier de verrouillage du paquet.

Un flux de travail typique de bdep comprendrait les étapes suivantes.

Obtenir le Projet

Normalement, nous utiliserions le système de contrôle de version pour obtenir le projet que nous voulons développer : 
$ git clone ssh://example.com/hello.git

Alternativement, nous pouvons utiliser la commande bdep-new(1) pour démarrer un nouveau projet (voir Nom du Paquet (#package-name) pour les détails sur la dénomination des projets) :

$ bdep new -l c++ -t exe hello

Similaire aux outils de contrôle de version, nous exécutons normalement bdep depuis le répertoire du projet ou l'un de ses sous-répertoires :

$ cd hello

Voir bdep-projects-configs(1) pour d'autres façons de spécifier l'emplacement du projet.

Initialiser le Projet

Ensuite, nous utilisons la commande bdep-init(1) pour créer de nouvelles ou ajouter des configurations de construction existantes et initialiser notre projet dans ces configurations : 
$ bdep init -C ../hello-gcc @gcc cc config.cxx=g++
$ bdep init -A ../hello-clang @clang

Si le répertoire de configuration est à côté du projet et que son nom est de la forme nom-prj-nom-cfg, alors la version raccourcie de l'initialisation peut être utilisée à la place :

$ bdep init -C @gcc cc config.cxx=g++
$ bdep init -A @clang

Après initialisation, nous pouvons utiliser la commande bdep-status(1) pour examiner l'état de notre projet dans ses configurations :

$ bdep status -a
dans la configuration @gcc :
hello configuré 0.1.0-a.0.19700101000000
dans la configuration @clang :
hello configuré 0.1.0-a.0.19700101000000

La plupart des commandes bdep opèrent sur une ou plusieurs configurations de construction associées au projet. Si nous n'en spécifions pas une explicitement, alors la configuration par défaut (généralement la première ajoutée ; gcc dans notre cas) est utilisée. Alternativement, nous pouvons spécifier les configurations par nom (si attribué), en tant que répertoires, ou avec --all|-a (voir bdep-projects-configs(1) pour les détails). Par exemple :

$ bdep status @clang @gcc      # par nom
$ bdep status -c ../hello-gcc  # comme répertoire

Si une commande opère sur plusieurs configurations (comme status -a dans l'exemple précédent), elle imprimera une ligne identifiant chaque configuration avant d'imprimer le résultat de la commande.

Par défaut, le répertoire source du projet est configuré pour être redirigé vers la configuration de construction par défaut. C'est-à-dire que nous pouvons exécuter le système de construction dans le répertoire source et il construira automatiquement dans la configuration redirigée ainsi que liera les résultats au répertoire source en utilisant des symlinks ou un autre mécanisme approprié (voir bdep-config(1) pour les détails). Par exemple :

$ b        # construire dans gcc
<...>
$ ./hello  # exécuter le résultat

Utiliser le système de construction directement sur des configurations autres que la par défaut nécessite de spécifier explicitement leurs chemins. Pour rendre cela plus pratique, les commandes bdep-update(1), bdep-test(1), et bdep-clean(1) nous permettent de les référencer par leurs noms, d'effectuer l'opération de système de construction souhaitée sur plusieurs d'entre elles à la fois, et, dans le cas de test, de l'effectuer sur les dépendances immédiates ou toutes les dépendances, ou un projet. Par exemple :

$ bdep test @gcc @clang
dans la configuration @gcc :
<...>
dans la configuration @clang :
<...>

Pour désinitialiser un projet dans une ou plusieurs configurations de construction, nous pouvons utiliser la commande bdep-deinit(1). Par exemple :

$ bdep deinit -a
Ajouter, Supprimer ou Modifier les Dépendances

Supposons que nous ayons trouvé libhello que nous aimerions utiliser dans notre projet. D'abord, nous modifions le fichier repositories.manifest de notre projet et ajoutons le dépôt de libhello comme notre prérequis : 
$ cat repositories.manifest
...
role: prerequisite
location: https://example.com/libhello.git
...

Ensuite, nous modifions notre fichier manifest et spécifions une dépendance sur libhello :

$ cat manifest
...
depends: libhello ^1.0.0
...

Synchroniser le Projet avec les
Configurations

Pour synchroniser les modifications des informations de dépendance du projet avec ses configurations de compilation, nous utilisons la commande bdep-sync(1). En continuant avec notre exemple, cela entraînera le téléchargement et la configuration de libhello puisque notre projet en dépend désormais : 
$ bdep sync
synchronizing:
  build libhello/1.0.0 (required by hello)
  upgrade hello/0.1.0-a.0.19700101000000#1
$ bdep status -i
hello configured 0.1.0-a.0.19700101000000#1
  libhello ^1.0.0 configured
1.0.0

Notez que par défaut, les configurations de compilation sont automatiquement synchronisées à chaque invocation du système de compilation (voir bdep-config(1) pour plus de détails). Par conséquent, nous avons rarement besoin d'exécuter explicitement la commande sync et pouvons plutôt simplement exécuter l'opération de compilation souhaitée (par exemple, update ou test) directement. Par exemple : update

ou 
$ b test
synchronizing:
  build libhello/1.0.0 (required by hello)
  upgrade hello/0.1.0-a.0.19700101000000#1
<...>

Il est également possible que plusieurs projets partagent une configuration de compilation. Dans ce cas, tous les projets sont synchronisés en une seule fois, quelle que soit le projet d'origine. Par exemple, si nous étions aussi les auteurs de libhello et l'hébergions dans un dépôt de contrôle de versions séparé (par opposition à être un paquet dans le dépôt hello), il serait naturel de le développer en même temps que hello dans les mêmes configurations

: 
$ cd ../libhello
$ bdep init -A ..
/hello-gcc @gcc $ bdep sync # sy
nchronizes both hello and libhello
Mettre à Niveau ou Rétrograder les
Dépendances

La commande bdep-sync(1) est également utilisée pour mettre à niveau ou rétrograder des dépendances (et elle est aussi exécutée comme dernière étape de init). Supposons que nous ayons appris qu'une nouvelle version de libhello a été publiée et que nous souhaitons l'essayer.

Pour actualiser la liste des paquets de dépendances disponibles, nous utilisons la commande bdep-fetch(1) (ou, comme raccourci, l' option -f de status

) : 
$ bdep fetch
$ bdep status libhello
libhello configured 1.0.0 available [1.
1.0]

Sans version explicite ni l' option --patch|-p , sync mettra à niveau la dépendance spécifiée vers la dernière version

disponible : 
$ bdep sync libhello
synchronizing:
  upgrade libhello/1.1.0
  reconfigure hello/0.1.0
$ bdep status -i
hello configured 0.1.0-a.0.19700101000000#1
  libhello ^1.0.0 configured
1.1.0

Supposons que nous n'ayons pas aimé la nouvelle version et que nous souhaitions revenir à l'ancienne. Pour rétrograder une dépendance, nous devons spécifier sa version

explicitement : 
$ bdep status -o libhello
libhello
configured 1.1.0 available [1.0.0]
(1.1.0) $ bdep sync libhello/1.0.0 synchronizing: downgrade libhello/1.1.0 reconfigure hello/0.1.0
