DESCRIPTIO

N

Construit une image à l'aide d'instructions provenant d'un ou plusieurs Containerfiles ou Dockerfiles et d'un répertoire de contexte de construction spécifié. Un Containerfile utilise la même syntaxe qu'un Dockerfile en interne. Pour ce document, un fichier désigné comme un Containerfile peut être un fichier nommé soit 'Containerfile' soit

'Dockerfile'.

Le répertoire de contexte de construction peut être spécifié comme l'URL http(s) d'une archive, d'un dépôt git ou d'un

Containerfile.

Si aucun répertoire de contexte n'est spécifié, Buildah supposera que le répertoire de travail courant est le contexte de construction, qui doit contenir un

Containerfile.

Les Containerfiles se terminant par le suffixe ".in" seront prétraités via cpp(1). Cela peut être utile pour décomposer les Containerfiles en plusieurs parties réutilisables qui peuvent être utilisées via la directive #include de CPP. Remarquez qu'un fichier Containerfile.in peut toujours être utilisé par d'autres outils lors d'un prétraitement manuel via cpp -E. Tous les commentaires (lignes commençant par # ) dans les Containerfile(s) inclus qui ne sont pas des commandes de prétraitement seront affichés comme des avertissements lors des

constructions.

Lorsque l'URL est une archive, le contenu de l'URL est téléchargé vers un emplacement temporaire et extrait avant

l'exécution.

Lorsque l'URL est un Containerfile, le fichier est téléchargé vers un emplacement

temporaire.

Lorsqu'un dépôt Git est défini comme URL, le dépôt est cloné localement puis utilisé comme contexte de construction. Une branche (ou un ID de commit) non par défaut et un sous-répertoire du dépôt git cloné peuvent être utilisés en incluant leurs noms à la fin de l'URL sous la forme myrepo.git#mybranch:subdir, myrepo.git#mycommit:subdir, ou myrepo.git#:subdir si le sous-répertoire doit

être utilisé depuis la
branche par défaut.

--add-host=[

Ajouter une correspondance personnalisée hôte-vers-IP (hôte:

ip)

Ajoute une ligne à /etc/hosts. Le format est nomhôte:ip. L'option --add-host peut être définie plusieurs fois. Entre en conflit avec l'option

--no-hosts.

Au lieu d'une adresse IP, l'indicateur spécial host-gateway peut être fourni. Cela se résout en une adresse IP que le conteneur peut utiliser pour se connecter à l'hôte. L'adresse IP choisie dépend de votre configuration réseau, il n'y a donc aucune garantie que Buildah puisse déterminer automatiquement l'adresse host-gateway, ce qui fera alors échouer Buildah avec un message d'erreur. L'adresse host-gateway est également utilisée par Buildah pour ajouter automatiquement les noms d'hôte host.containers.internal et host.docker.internal à /etc/hosts. Si aucune adresse host-gateway n'a été configurée manuellement et que Buildah échoue à déterminer l'adresse IP automatiquement, Buildah ignorera silencieusement l'ajout de ces noms d'hôte internes à /etc/hosts. --cpu-shares, -c=

0

CPU shares (relative

weight)

By default, all containers get the same proportion of CPU cycles. This proportion can be modified by changing the container's CPU share weighting relative to the weighting of all other running

containers.

To modify the proportion from the default of 1024, use the --cpu-shares flag to set the weighting to 2 or

higher.

The proportion will only apply when CPU-intensive processes are running. When tasks in one container are idle, other containers can use the left-over CPU time. The actual amount of CPU time will vary depending on the number of containers running on the

system.

For example, consider three containers, one has a cpu-share of 1024 and two others have a cpu-share setting of 512. When processes in all three containers attempt to use 100% of CPU, the first container would receive 50% of the total CPU time. If you add a fourth container with a cpu-share of 1024, the first container only gets 33% of the CPU. The remaining containers receive 16.5%, 16.5% and 33% of the

CPU.

On a multi-core system, the shares of CPU time are distributed over all CPU cores. Even if a container is limited to less than 100% of CPU time, it can use 100% of each individual CPU

core.

For example, consider a system with more than three cores. If you start one container {C0} with -c=512 running one process, and another container {C1} with -c=1024 running two processes, this can result in the following division of CPU

Construction d'une image en utilisant une URL

Cela clonera le dépôt GitHub spécifié depuis l'URL et l'utilisera comme contexte. Le Containerfile ou Dockerfile à la racine du dépôt est utilisé comme contexte de construction. Cela ne fonctionne que si le dépôt GitHub est un dépôt dédié.

buildah build https://github.com/containers/PodmanHello.git

Note : Github ne prend pas en charge l'utilisation de git:// pour effectuer l'opération de clone en raison de changements récents dans ses directives de sécurité (https://github.blog/2021-09-01-improving-git-protocol-security-github/). Utilisez une URL https:// si le dépôt source est hébergé sur Github.

Construction d'une image en utilisant une URL vers un contexte tarballisé

Buildah récupérera l'archive tarball, la décompressera et utilisera son contenu comme contexte de construction. Le Containerfile ou Dockerfile à la racine de l'archive et le reste de l'archive seront utilisés comme contexte de construction. Si vous passez également une option -f PATH/Containerfile, le système recherchera ce fichier à l'intérieur du contenu du tarball.

buildah build -f dev/Containerfile https://10.10.10.1/buildah/context.tar.gz

Note : les formats de compression pris en charge sont 'xz', 'bzip2', 'gzip' et 'identity' (aucune compression).

Utilisation des variables de temps de compilation

Remplacer la valeur définie pour la variable d'environnement HTTP_PROXY dans le Containerfile.

buildah build --build-arg=HTTP_PROXY="http://127.0.0.1:8321"

ENVIRONNEMENT

BUILD_REGISTRY_SOURCES

BUILD_REGISTRY_SOURCES, s'il est défini, est traité comme un objet JSON qui contient des listes de noms de registres sous les clés insecureRegistries, blockedRegistries et allowedRegistries.

Lors du téléchargement d'une image depuis un registre, si le nom du registre correspond à l'un des éléments de la liste blockedRegistries, la tentative de téléchargement de l'image est refusée. S'il y a des registres dans la liste allowedRegistries, et que le nom du registre ne figure pas dans la liste, la tentative de téléchargement est refusée.

TMPDIR La variable d'environnement TMPDIR permet à l'utilisateur de spécifier où les fichiers temporaires sont stockés lors du téléchargement et de l'envoi des images. Par défaut : '/var/tmp'.

Fichiers

.containerignore/.dockerignore

Si le fichier .containerignore/.dockerignore existe dans le répertoire de contexte, buildah build en lit le contenu. Si les deux existent, alors .containerignore est utilisé. Utilisez l'indicateur --ignorefile pour remplacer l'emplacement du fichier d'exclusion. Buildah utilise le contenu pour exclure les fichiers et répertoires du répertoire de contexte, lors de l'exécution des directives COPY et ADD dans le Containerfile/Dockerfile

Les utilisateurs peuvent spécifier une série de globales shell Unix dans un fichier .containerignore/.dockerignore pour identifier les fichiers/répertoires à exclure.

Buildah prend en charge une chaîne de caractères spéciale wildcard ** qui correspond à n'importe quel nombre de répertoires (y compris zéro). Par exemple, **/*.go exclura tous les fichiers se terminant par .go qui se trouvent dans tous les répertoires.

Exemple de fichier .containerignore :

# exclude this content for image
*/*.c
**/output*
src

*/*.c Exclut les fichiers et répertoires dont le nom se termine par .c dans n'importe quel sous-répertoire de premier niveau. Par exemple, le fichier source include/rootless.c.

**/output* Exclut les fichiers et répertoires commençant par output de n'importe quel répertoire.

src Exclut les fichiers nommés src et le répertoire src ainsi que tout leur contenu.

Les lignes commençant par ! (point d'exclamation) peuvent être utilisées pour faire des exceptions aux exclusions. L'exemple suivant est un fichier .containerignore/.dockerignore qui utilise ce mécanisme :

*.doc
!Help.doc

Exclure tous les fichiers doc sauf Help.doc de l'image.

Cette fonctionnalité est compatible avec la gestion des fichiers .containerignore décrits ici :

https://github.com/containers/common/blob/main/docs/containerignore.5.md

registries.conf (/etc/containers/registries.conf)

registries.conf est le fichier de configuration qui spécifie quels registres de conteneurs doivent être consultés lors de la complétion des noms d'images qui n'incluent pas de partie registre ou domaine.

policy.json (/etc/containers/policy.json)

Fichier de politique de signature. Il définit la politique de confiance pour les images de conteneurs. Contrôle quels registres de conteneurs peuvent être utilisés pour les images, et si l'outil doit faire confiance aux images ou non.
