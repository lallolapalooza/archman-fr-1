NOM

buildah-from - Crée un nouveau conteneur de travail, soit à partir de zéro, soit en utilisant une image spécifiée comme point de départ.

SYNOPSIS

buildah from [options] image

DESCRIPTION

Crée un conteneur de travail basé sur le nom d'image spécifié. Si le nom d'image fourni est "scratch", un nouveau conteneur vide est créé. Les noms d'images utilisent le format "transport":"détails".

Plusieurs transports sont supportés :

dir:chemin
Un répertoire local existant chemin contenant le manifeste, les archives de couches et les signatures sous forme de fichiers individuels. C'est un format non standardisé, principalement utile pour le débogage ou l'inspection non invasive des images.

docker://référence-docker (Par défaut)
Une image dans un registre implémentant la "Docker Registry HTTP API V2". Par défaut, utilise l'état d'autorisation dans $XDG_RUNTIME_DIR/containers/auth.json, qui est défini à l'aide de (buildah login). Voir containers-auth.json(5) pour plus d'informations. Si l'état d'autorisation n'y est pas trouvé, $HOME/.docker/config.json est vérifié, lequel est défini à l'aide de (docker login).
Si référence-docker n'inclut pas de nom de registre, localhost sera consulté en premier, suivi de tout registre nommé dans la configuration des registres.

docker-archive:chemin
Une image est récupérée sous forme de fichier formaté par podman load.

docker-daemon:référence-docker
Une image référence-docker stockée dans le stockage interne du démon docker. référence-docker doit inclure une balise ou un digest. Alternativement, lors de la lecture d'images, le format peut aussi être docker-daemon:algo:digest (un ID d'image).

oci:chemin:tag**
Une balise d'image dans un répertoire conforme à la "Open Container Image Layout Specification" à chemin.

oci-archive:chemin:tag
Une image tag dans un répertoire conforme à la "Open Container Image Layout Specification" à chemin.

DÉPENDANCES

Buildah résout le chemin du registre à partir duquel tirer en utilisant le fichier /etc/containers/registries.conf, containers-registries.conf(5). Si la commande buildah from échoue avec une erreur "image non trouvée", vérifiez d'abord que le fichier registries.conf est installé et configuré correctement.

VALEUR DE RETOUR

L'ID du conteneur qui a été créé. En cas d'erreur, 1 est retourné.

OPTIONS

--add-host=[]

Ajoute un mappage hôte-IP personnalisé (hôte:ip)

Ajoute une ligne à /etc/hosts. Le format est nom_hote:ip. L'option --add-host peut être définie plusieurs fois.

--arch="ARCH"

Définit l'ARCH de l'image à télécharger à la valeur fournie au lieu d'utiliser l'architecture de l'hôte. (Exemples : arm, arm64, 386, amd64, ppc64le, s390x)

--authfile chemin

Chemin du fichier d'authentification. Par défaut : ${XDG_RUNTIME_DIR}/containers/auth.json. Voir containers-auth.json(5) pour plus d'informations. Ce fichier est créé à l'aide de buildah login.

Si l'état d'autorisation n'y est pas trouvé, $HOME/.docker/config.json est vérifié, lequel est défini à l'aide de docker login.

Note : Vous pouvez également remplacer le chemin par défaut du fichier d'authentification en définissant la variable d'environnement REGISTRY_AUTH_FILE. export REGISTRY_AUTH_FILE=chemin

--cap-add=CAP_xxx

Ajoute la capacité spécifiée à l'ensemble par défaut de capacités qui seront fournies pour les futures invocations de buildah run qui utilisent ce conteneur. Certaines capacités sont accordées par défaut ; cette option peut être utilisée pour en ajouter.

--cap-drop=CAP_xxx

Supprime la capacité spécifiée de l'ensemble par défaut de capacités qui seront fournies pour les futures invocations de buildah run qui utilisent ce conteneur. Les capacités CAP_CHOWN, CAP_DAC_OVERRIDE, CAP_FOWNER, CAP_FSETID, CAP_KILL, CAP_NET_BIND_SERVICE, CAP_SETFCAP, CAP_SETGID, CAP_SETPCAP et CAP_SETUID sont accordées par défaut ; cette option peut être utilisée pour les supprimer. La liste des capacités par défaut est gérée dans containers.conf(5).

Si une capacité est spécifiée aux deux options --cap-add et --cap-drop, elle sera supprimée, quel que soit l'ordre dans lequel les options ont été données.

--cert-dir chemin

Utilise les certificats à chemin (*.crt, *.cert, *.key) pour se connecter au registre. Le répertoire de certificats par défaut est /etc/containers/certs.d.

--cgroup-parent=""

Chemin vers les cgroups sous lequel le cgroup pour le conteneur sera créé. Si le chemin n'est pas absolu, le chemin est considéré comme relatif au chemin des cgroups du processus init. Les cgroups seront créés s'ils n'existent pas déjà.

--cgroupns comment

Définit la configuration des espaces de noms IPC lorsque le conteneur est ensuite utilisé pour buildah run. La valeur configurée peut être "" (la chaîne vide) ou "private" pour indiquer qu'un nouvel espace de noms cgroup doit être créé, ou elle peut être "host" pour indiquer que l'espace de noms cgroup dans lequel buildah lui-même est en cours d'exécution doit être réutilisé.

--cidfile ContainerIDFile

Écrit l'ID du conteneur dans le fichier.

--cpu-period=0

Limite la période CFS (Completely Fair Scheduler) du CPU

Limite l'utilisation du CPU du conteneur. Ce drapeau indique au noyau de restreindre l'utilisation du CPU du conteneur à la période que vous spécifiez.

--cpu-quota=0

Limite le quota CFS (Completely Fair Scheduler) du CPU

Limite l'utilisation du CPU du conteneur. Par défaut, les conteneurs s'exécutent avec toutes les ressources CPU disponibles. Ce drapeau indique au noyau de restreindre l'utilisation du CPU du conteneur au quota que vous spécifiez.

--cpu-shares, -c=0

Parts CPU (poids relatif)

Par défaut, tous les conteneurs reçoivent la même proportion de cycles CPU. Cette proportion peut être modifiée en changeant le poids de part CPU du conteneur par rapport au poids de tous les autres conteneurs en cours d'exécution.

Pour modifier la proportion par rapport à la valeur par défaut de 1024, utilisez l'option --cpu-shares pour définir le poids à 2 ou plus.

La proportion ne s'appliquera que lorsque des processus intensifs en CPU s'exécutent. Lorsque les tâches d'un conteneur sont inactives, d'autres conteneurs peuvent utiliser le temps CPU restant. La quantité réelle de temps CPU variera en fonction du nombre de conteneurs en cours d'exécution sur le système.

Par exemple, considérez trois conteneurs, l'un a une cpu-share de 1024 et les deux autres un réglage de cpu-share de 512. Lorsque des processus dans les trois conteneurs tentent d'utiliser 100% du CPU, le premier conteneur recevrait 50% du temps CPU total. Si vous ajoutez un quatrième conteneur avec une cpu-share de 1024, le premier conteneur ne reçoit que 33% du CPU. Les conteneurs restants reçoivent respectivement 16,5%, 16,5% et 33% du CPU.

Sur un système multi-cœurs, les parts de temps CPU sont distribuées sur tous les cœurs CPU. Même si un conteneur est limité à moins de 100% du temps CPU, il peut utiliser 100% de chaque cœur CPU individuel.

Par exemple, considérez un système avec plus de trois cœurs. Si vous démarrez un conteneur {C0} avec -c=512 exécutant un processus, et un autre conteneur {C1} avec -c=1024 exécutant deux processus, cela peut entraîner la division suivante des parts CPU :

PID    conteneur	CPU	Part CPU
100    {C0}		0	100% du CPU0
101    {C1}		1	100% du CPU1
102    {C1}		2	100% du CPU2

CPUs dans lesquels autoriser l'exécution (0-3, 0,1)

--cpuset-mems=""

Nœuds mémoire (MEMs) dans lesquels autoriser l'exécution (0-3, 0,1). Uniquement effectif sur les systèmes NUMA.

Changement de propriétaire des montages de

volumes

Par défaut, Buildah ne modifie pas le propriétaire et le groupe des répertoires de volume sources montés dans les conteneurs. Si un conteneur est créé dans un nouvel espace de noms d'utilisateur, le UID et le GID dans le conteneur peuvent correspondre à un autre UID et GID sur

l'hôte.

Le suffixe :U indique à Buildah d'utiliser le UID et le GID de l'hôte corrects en se basant sur le UID et le GID à l'intérieur du conteneur, pour changer le propriétaire et le groupe du volume

source.

Étiquetage des montages de

volumes

Les systèmes d'étiquetage comme SELinux exigent que des étiquettes appropriées soient placées sur le contenu du volume monté dans un conteneur. Sans étiquette, le système de sécurité peut empêcher les processus s'exécutant à l'intérieur du conteneur d'utiliser le contenu. Par défaut, Buildah ne modifie pas les étiquettes définies par le système

d'exploitation.

Pour changer une étiquette dans le contexte du conteneur, vous pouvez ajouter l'un des deux suffixes :z ou :Z au montage de volume. Ces suffixes indiquent à Buildah de re-étiqueter les objets de fichiers sur les volumes partagés. L'option z indique à Buildah que deux conteneurs partagent le contenu du volume. En conséquence, Buildah étiquette le contenu avec une étiquette de contenu partagé. Les étiquettes de volume partagées permettent à tous les conteneurs de lire/écrire le contenu. L'option Z indique à Buildah d'étiqueter le contenu avec une étiquette privée non partagée. Seul le conteneur actuel peut utiliser un volume

privé.

Montages de volumes en superposition

(Overlay)

L'indicateur :O indique à Buildah de monter le répertoire de l'hôte comme stockage temporaire en utilisant le système de fichiers Overlay. Les conteneurs des commandes RUN sont autorisés à modifier le contenu du point de montage et sont stockés dans le stockage du conteneur dans un répertoire séparé. En termes de système de fichiers Overlay, le répertoire source sera le niveau inférieur (lower), et le répertoire de stockage du conteneur sera le niveau supérieur (upper). Les modifications du point de montage sont détruites lorsque la commande RUN termine son exécution, de manière similaire à un point de montage

tmpfs.

Toute exécution ultérieure de commandes RUN voit le contenu original du répertoire source, les modifications des commandes RUN précédentes n'existent

plus.

Un cas d'utilisation du montage en superposition est le partage du cache de paquets de l'hôte vers le conteneur pour permettre d'accélérer les

constructions.

Par défaut, les volumes montés en liaison sont privés. Cela signifie que tout montage effectué à l'intérieur du conteneur ne sera pas visible sur l'hôte et vice versa. Ce comportement peut être modifié en spécifiant une propriété de propagation du montage de

volume.

Lorsque la politique de propagation du montage est définie sur shared, tout montage effectué à l'intérieur du conteneur sur ce volume sera visible à la fois par l'hôte et le conteneur. Lorsque la politique de propagation du montage est définie sur slave, la propagation unidirectionnelle du montage est activée et tout montage effectué sur l'hôte pour ce volume ne sera visible qu'à l'intérieur du conteneur. Pour contrôler la propriété de propagation du montage du volume, utilisez l'indicateur de propagation :[r]shared, :[r]slave, [r]private ou [r]unbindable. La propriété de propagation ne peut être spécifiée que pour les volumes montés en liaison et non pour les volumes internes ou les volumes nommés. Pour que la propagation du montage fonctionne sur le point de montage source (le point de montage où le répertoire source est monté), il doit avoir les bonnes propriétés de propagation. Pour les volumes partagés, le point de montage source doit être partagé. Et pour les volumes esclaves, le montage source doit être soit partagé, soit esclave. [1]

⟨#Footnote1⟩

Utilisez df <répertoire-source> pour déterminer le montage source, puis utilisez findmnt -o TARGET,PROPAGATION <répertoire-du-montage-source> pour déterminer les propriétés de propagation du montage source. Si l'utilitaire findmnt n'est pas disponible, le point de montage source peut être déterminé en regardant l'entrée de montage dans /proc/self/mountinfo. Regardez les champs optionnels et voyez si des propriétés de propagation sont spécifiées. shared:X signifie que le montage est partagé (shared), master:X signifie que le montage est esclave (slave) et s'il n'y a rien, cela signifie que le montage est privé (private). [1]

⟨#Footnote1⟩

Pour changer les propriétés de propagation d'un point de montage, utilisez la commande mount. Par exemple, pour monter en liaison le répertoire source /foo, faites mount --bind /foo /foo et mount --make-private --make-shared /foo. Cela convertira /foo en un point de montage partagé (shared). Les propriétés de propagation du montage source peuvent être changées directement. Par exemple, si / est le montage source pour /foo, alors utilisez mount --make-shared / pour convertir / en un montage pa

rtagé (shared).
