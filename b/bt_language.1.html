NOM

bt_language - le langage de données BibTeX, tel que reconnu par btparse

SYNOPSIS

# Grammaire lexicale, mode 1 : niveau supérieur
AT                    \@
NEWLINE               \n
COMMENT               \%~[\n]*\n
WHITESPACE            [\ \r\t]+
JUNK                  ~[\@\n\ \r\t]+
# Grammaire lexicale, mode 2 : dans une entrée
NEWLINE               \n
COMMENT               \%~[\n]*\n
WHITESPACE            [\ \r\t]+
NUMBER                [0-9]+
NAME                  [a-z0-9\!\$\&\*\+\-\.\/\:\;\<\>\?\[\]\^\_\`\|]+
LBRACE                \{
RBRACE                \}
LPAREN                \(
RPAREN                \)
EQUALS                =
HASH                  \#
COMMA                 ,
QUOTE                 \"
# Grammaire lexicale, mode 3 : chaînes
# (très compliqué -- voir le texte)
# Grammaire syntaxique :
bibfile : ( entry )*
entry : AT NAME body
body : STRING                    # pour les entrées de type commentaire
     | ENTRY_OPEN contents ENTRY_CLOSE
contents : ( NAME | NUMBER ) COMMA fields   # pour les entrées régulières
         | fields                # pour les définitions de macro
         | value                 # pour les entrées de préambule
fields : field { COMMA fields }
       | 
field : NAME EQUALS value
value : simple_value ( HASH simple_value )*
simple_value : STRING
             | NUMBER
             | NAME

DESCRIPTION

L'un des problèmes de BibTeX est qu'il n'existe pas de spécification formelle du langage. Cela signifie que les utilisateurs qui explorent les recoins arcanes du langage sont largement livrés à eux-mêmes, et que les programmeurs qui implémentent leurs propres analyseurs sont complètement livrés à eux-mêmes---sauf à observer le comportement de l'implémentation originale.

D'autres implémenteurs d'analyseurs (Nelson Beebe de "bibclean" en particulier) ont pris la peine d'expliquer le langage accepté par leur analyseur, et dans cet esprit, ce qui suit est présenté.

Si vous n'êtes pas familier avec les arcanes des langages réguliers et sans contexte, vous n'aurez pas une vie facile pour comprendre ceci. Ceci n'est pas une introduction au langage BibTeX ; n'importe quel livre LaTeX serait plus adapté pour apprendre le langage de données lui-même.

GRAMMAIRE LEXICALE

Le scanner lexical a trois modes distincts : niveau supérieur, dans une entrée, et chaîne. Grossièrement, le niveau supérieur est le mode initial ; nous entrons dans le mode « dans une entrée » en voyant un "@" au niveau supérieur ; et en voyant le "}" ou ")" qui termine l'entrée, nous retournons au niveau supérieur. Nous entrons dans le mode chaîne en voyant un " ou un "{" non délimiteur d'entrée depuis le mode « dans une entrée ». Notez que le langage lexical est à la fois non régulier (parce que les accolades doivent s'équilibrer) et sensible au contexte (parce que "{" peut signifier des choses différentes selon son contexte syntaxique). Cela dit, nous utiliserons des expressions régulières pour décrire les éléments lexicaux, car elles sont le point de départ utilisé par le scanner lexical lui-même. Le reste de la grammaire lexicale sera expliqué de manière informelle dans le texte.

Depuis le niveau supérieur, les jetons suivants sont reconnus selon les expressions régulières à droite :

AT                    \@
NEWLINE               \n
COMMENT               \%~[\n]*\n
WHITESPACE            [\ \r\t]+
JUNK                  ~[\@\n\ \r\t]+

(Notez qu'il s'agit de la syntaxe d'expressions régulières PCCTS, qui devrait être assez familière aux utilisateurs d'autres moteurs de regex. Une bizarrerie est qu'une classe de caractères est négée avec "~[...]" plutôt qu'avec "[^...]".)

En voyant "at" au niveau supérieur, nous entrons dans le mode « dans une entrée ». Les espaces blancs, le bruit, les nouvelles lignes et les commentaires sont tous ignorés, ces deux derniers incrémentant un compteur de lignes. (Le bruit est explicitement reconnu pour permettre le schéma de « commentaire implicite » de "bibtex".)

Depuis le mode « dans une entrée », nous reconnaissons la nouvelle ligne, le commentaire et l'espace blanc de manière identique au mode niveau supérieur. De plus, les jetons suivants sont reconnus :

NUMBER                [0-9]+
NAME                  [a-z0-9\!\$\&\*\+\-\.\/\:\;\<\>\?\[\]\^\_\`\|]+
LBRACE                \{
RBRACE                \}
LPAREN                \(
RPAREN                \)
EQUALS                =
HASH                  \#
COMMA                 ,
QUOTE                 \"

À ce stade, le scanner lexical commence à ressembler suspectement à une grammaire sans contexte plutôt qu'à une collection d'expressions régulières indépendantes. Cependant, il est nécessaire de conserver cette complexité dans le scanner car certains caractères ("{" et "(" en particulier) ont des significations lexicales très différentes selon les jetons qui les ont précédés dans le flux d'entrée.

En particulier, "{" et "(" sont traités comme des « ouvreurs d'entrée » s'ils suivent un jeton "at" et un jeton "name" , à moins que la valeur du jeton "name" ne soit "comment". (Notez le passage du niveau supérieur au mode « dans une entrée » entre les deux jetons.) Dans le cas @comment , le délimiteur est considéré comme démarrant une chaîne, et nous entrons dans le mode chaîne. Sinon, le délimiteur est enregistré, et quand nous voyons un "}" ou ")" correspondant, il est considéré comme un « fermeur d'entrée ». (Les accolades sont équilibrées automatiquement ici car l'analyseur lexical des chaînes prend soin de compter la profondeur des accolades.)

Partout ailleurs, "{" est considéré comme démarrant une chaîne, et nous entrons dans le mode chaîne. " démarre toujours une chaîne, quel que soit le contexte. Les autres jetons ("name", "number", "equals", "hash", et "comma") sont reconnus inconditionnellement.

Notez que "name" est un jeton fourre-tout utilisé pour les types d'entrées, les clés de citation, les noms de champs et les noms de macro ; parce que BibTeX a des règles légèrement différentes (largement non documentées) pour ces divers éléments, un peu de ruse est nécessaire pour faire fonctionner les choses. Comme point de départ, considérez la définition de BibTeX de ce qui est autorisé pour une clé d'entrée : une séquence de n'importe quels caractères sauf

" # % ' ( ) , = { }

plus l'espace. Il y a quelques problèmes avec ce schéma. D'abord, sans spécifier le jeu de caractères dont sont tirés ces « 10 magiques », c'est un peu difficile de savoir ce qui est réellement autorisé. Deuxièmement, autoriser les caractères "@" pourrait conduire à une syntaxe BibTeX confuse (cela ne confond pas BibTeX, mais cela pourrait confondre un lecteur humain). Enfin, autoriser certains caractères qui sont spéciaux pour TeX signifie que BibTeX peut générer du code TeX invalide : essayez de mettre une barre oblique inverse ("\") ou un tilde ("~") dans une clé de citation. (Cette dernière exception est plutôt spécifique à l'application « générer du code (La)TeX à partir d'une base de données BibTeX », mais comme c'est l'application principale pour les bases de données BibTeX, alors ce sera probablement l'application principale pour btparse, au moins initialement. Ainsi, il est logique de prêter attention à ce problème.)

Dans btparse, donc, un nom est défini comme toute séquence de lettres, chiffres, soulignés, et des caractères suivants :

! $ & * + - . / : ; < > ? [ ] ^ _ ` |

Cette liste a été dérivée en retirant les « 10 magiques » de BibTeX de l'ensemble des caractères ASCII 7 bits imprimables (32-126), puis en retirant en outre "@", "\", et "~". Cela signifie que btparse interdit certaines des clés d'entrée les plus bizarres que BibTeX accepterait, comme "\foo@bar", mais autorise toujours une chaîne avec des chiffres initiaux. En fait, d'après la définition ci-dessus, il semble que btparse accepterait une chaîne de tous chiffres comme un « nom ; » Ce n'est pas le cas, cependant, car le scanner lexical reconnaît d'abord une telle chaîne de chiffres comme un nombre. Il y a deux problèmes ici : les clés d'entrée BibTeX peuvent en fait être entièrement numériques, et les noms de champs ne peuvent pas commencer par un chiffre. (Ce sont deux des différences pas si évidentes dans le traitement par BibTeX des clés et des noms de champs.) Les astuces utilisées pour gérer ces problèmes sont implémentées dans l'analyseur syntaxique plutôt que dans le scanner lexical, donc

NAME

btparse - A parser for the BibTeX language

SYNOPSIS

btparse [options] filename

DESCRIPTION

This manual page describes the BibTeX language syntax as recognized by the btparse parser.

The parser is written using PCCTS (Purdue Compiler Construction Tool Set), and it is organized into two main parts: a lexical analyzer (lexer) and a syntactic analyzer (parser). The lexical grammar defines the smallest meaningful units (tokens) of the language, and the syntactic grammar defines how these tokens are combined to form valid statements.

LEXICAL GRAMMAR

The lexical grammar is described in terms of the tokens recognized by the lexer. The syntactic grammar is described in "SYNTACTIC GRAMMAR" below.

The string lexer recognizes "lbrace", "rbrace", "lparen", and "rparen" tokens in order to count brace- or parenthesis-depth. This is necessary so it knows when to accept a string delimited by braces or parentheses. (Note that a parenthesis-delimited string is only allowed after @comment---this is not a normal BibTeX construct.) In addition, it converts each non-space whitespace character (newline, carriage-return, and tab) to a single space. (Sequences of whitespace are not collapsed; that's the domain of string post-processing, which is well removed from the scanner or parser.) Finally, it accepts """ to delimit quote-delimited strings. Apart from those restrictions, the string lexer accepts anything up to the end-of-string delimiter.

SYNTACTIC GRAMMAR

(The language used to describe the grammar here is the extended Backus-Naur Form (EBNF) used by PCCTS. Terminals are represented by uppercase strings, non-terminals by lowercase strings; terminal names are the same as those given in the lexical grammar above. "( foo )*" means zero or more repetitions of the "foo" production, and "{ foo }" means an optional "foo".)

A file is just a sequence of zero or more entries:

bibfile : ( entry )*

An entry is an at-sign, a name (the "entry type"), and the entry body:

entry : AT NAME body

A body is either a string (this alternative is only tried if the entry type is "comment") or the entry contents:

body : STRING                    # for comment entries
     | ENTRY_OPEN contents ENTRY_CLOSE

("ENTRY_OPEN" and "ENTRY_CLOSE" are either "{" and "}" or "(" and ")", depending what is seen in the input for a particular entry.)

There are three possible productions for the "contents" non-terminal. Only one applies to any given entry, depending on the entry metatype (which in turn depends on the entry type). Currently, btparse supports four entry metatypes: comment, preamble, macro definition, and regular. The first two correspond to @comment and @preamble entries; "macro definition" is for @string entries; and "regular" is for all other entry types. (The library will be extended to handle @modify and @alias entry types, and corresponding "modify" and "alias" metatypes, when BibTeX 1.0 is released and the exact syntax is known.) The "metatype" concept is necessary so that all entry types that aren't specifically recognized fall into the "regular" metatype. It's also convenient not to have to "strcmp" the entry type all the time.

contents : ( NAME | NUMBER ) COMMA fields     # for regular entries
         | fields                # for macro definition entries
         | value                 # for preamble entries

Note that the entry key is not just a "NAME", but "( NAME | NUMBER)". This is necessary because BibTeX allows all-numeric entry keys, but btparse's lexical scanner recognizes such digit strings as "NUMBER" tokens.

"fields" is a comma-separated list of fields, with an optional single trailing comma:

fields : field { COMMA fields }
       |

A "field" is a single "field = value" assignment:

field : NAME EQUALS value

Note that "NAME" here is a restricted version of the "name" token described in "LEXICAL GRAMMAR" above. Any "name" token will be accepted by the parser, but it is immediately checked to ensure that it doesn't begin with a digit; if so, an artificial syntax error is triggered. (This is for compatibility with BibTeX, which doesn't allow field names to start with a digit.)

A "value" is a series of simple values joined by '#' characters:

value : simple_value ( HASH simple_value )*

A simple value is a string, number, or name (for macro invocations):

simple_value : STRING
             | NUMBER
             | NAME
