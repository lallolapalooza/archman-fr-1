Cette commande exécute la commande, en rendant tous les gems spécifiés dans le [Gemfile(5)][Gemfile(5)] disponibles pour require dans les programmes

Par défaut, lors de la tentative d'utiliser bundle exec sur un fichier avec un shebang ruby, Bundler exécutera Kernel.load sur ce fichier au lieu d'utiliser Kernel.exec. Dans la grande majorité des cas, il s'agit d'une amélioration des performances. Dans quelques cas rares, cela pourrait causer des effets de bord subtils (comme une dépendance au contenu exact de $0 ou __FILE__) et l'optimisation peut être désactivée en activant le paramètre disable_e

Lancement de

sous-shell

Tout code Ruby qui ouvre un sous-shell (comme system, les backticks, ou %x{}) utilisera automatiquement l'environnement Bundler actuel. Si vous devez lancer une commande shell vers une commande Ruby qui ne fait pas partie de votre bundle actuel, utilisez la méthode with_unbundled_env avec un bloc. Tout sous-shell créé à l'intérieur du bloc recevra l'environnement qui existait avant l'activation de Bundler. Par exemple, les commandes Homebrew exécutent Ruby, mais ne fonctionnent pas à l'intérieur d'un bundle

: 
Bundler.with_unbun
dled_env do `brew
install wget` end

Utiliser with_unbundled_env est également nécessaire si vous lancez une commande shell vers un bundle différent. Toutes les commandes Bundler exécutées dans un sous-shell hériteront du Gemfile actuel, donc les commandes qui doivent s'exécuter dans le contexte d'un bundle différent doivent également utiliser with_unbundled_env

. 
Bundler.with_unbundled_env do
  Dir.chdir "/other/bundler/project" do
    `bundle exec ./script`
end
end

Bundler fournit des helpers de commodité qui enveloppent system et exec, et ils peuvent être utilisés comme ceci

: 
Bundler.unbundled_system('brew
install wget') Bundler.unbun
dled_exec('brew install wget')

PLUGINS

RUBYGEMS

Actuellement, le système de plugins Rubygems requiert que tous les fichiers nommés rubygems_plugin.rb sur le chemin de chargement de n'importe quel gem installé lorsque n'importe quel code Ruby requiert rubygems.rb. Cela inclut les exécutables installés dans le système, comme rails, rackup, et rspec

.

Puisque les plugins Rubygems peuvent contenir du code Ruby arbitraire, ils finissent souvent par s'activer eux-mêmes ou leurs

dépendances.

Par exemple, le gem gemcutter 0.5 dépendait de json_pure. Si vous aviez cette version de gemcutter installée (même si vous aviez aussi une version plus récente sans ce problème), Rubygems activerait gemcutter 0.5 et json_pure <la

test>.

Si votre Gemfile(5) contenait aussi json_pure (ou un gem avec une dépendance sur json_pure), la version la plus récente sur votre système pourrait entrer en conflit avec la version dans votre Gemfile(5), ou la version instantanée dans votre Gemfile.l

ock.

Si cela se produit, bundler dira

: 
You have already activated json_pure 1
.4.6 but your Gemfile requires json_p
ure 1.4.3. Consider using bundle exec.

Dans cette situation, vous voulez presque certainement supprimer le gem sous-jacent avec le plugin gem problématique. En général, les auteurs de ces plugins (dans ce cas, le gem gemcutter) ont publié des versions plus récentes qui font plus attention dans leurs

plugins.

Vous pouvez trouver une liste de tous les gems contenant des plugins gem en

exécutant 
ruby -e "puts Gem
.find_files('ruby
gems_plugin.rb')"
