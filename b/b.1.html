DESCRIPTIO

N

Le pilote du système de construction build2 exécute un ensemble de méta-opérations sur des opérations sur des cibles selon la spécification de construction, ou buildspec en abrégé. Ce processus peut être contrôlé en spécifiant les options du pilote et les variables du système de construction

.

Notez que les options, variables et les fragments buildspec peuvent être spécifiés dans n'importe quel ordre. Pour éviter de traiter un argument qui commence par '-' comme une option, ajoutez le séparateur '--'. Pour éviter de traiter un argument qui contient '=' comme une variable, ajoutez le second séparateur '--'

.

Tous les composants du buildspec peuvent être omis. Si la méta-opération est omise, elle prend par défaut la valeur perform. Si l'opération est omise, elle prend par défaut l'opération par défaut pour cette méta-opération. Pour perform, c'est update. Enfin, si la cible est omise, elle prend par défaut le répertoire de travail courant. Une méta-opération sur une opération est appelée une action. Certaines opérations et méta-opérations peuvent prendre des paramètres supplémentaires. Par exemple

: 
$ b                       # perform(update(./))
$ b foo/                  # perform(update(foo/))
$ b foo/ bar/             # perform(update(foo/ bar/))
$ b update                # perform(update(./))
$ b 'clean(../)'          # perform(clean(../))
$ b perform               # perform(update(./))
$ b configure             # configure(?(./))
$ b 'configure(../)'      # configure(?(../))
$ b clean update          # perform(clean(./) update(./))
$ b configure update      # configure(?(./)) perform(update(./))
$ b 'create(conf/, cxx)'  # create(?(conf/),
cxx)

Remarquez le point d'interrogation utilisé pour indiquer l'opération par défaut (imaginaire) pour la méta-opération configure. Pour configure, l'opération par défaut est « toutes les opérations ». C'est-à-dire qu'elle configurera toutes les opérations pour la cible

spécifiée.

Vous pouvez aussi « générer » plusieurs opérations pour le même ensemble de cibles. Comparez

: 
$ b 'clean(foo/ bar/)' 'update(foo/ bar/)'
$ b '{clean update}(foo/ bar/)
'

Quelques autres exemples utiles de buildspec

: 
$ b '{clean update}(...)'        # reconstruire
$ b '{clean update clean}(...)'  # s'assurer que la construction réussit
$ b '{clean test clean}(...)'    # s'assurer que les tests passent
$ b '{clean disfigure}(...)'     # similaire à
distclean

Dans les shells POSIX, les parenthèses sont des caractères spéciaux et doivent être entre guillemets lorsqu'elles sont utilisées dans un buildspec. En plus d'être un inconvénient en soi, l'utilisation de guillemets inhibe aussi l'auto-complétion des chemins. Pour aider dans cette situation, une syntaxe de raccourci est disponible pour exécuter une seule opération ou méta-opération, par exemple

: 
$ b clean: foo/ bar/                # clean(foo/ bar/)
$ b configure: src/@out/            # configure(src/@out/)
$ b create: conf/, cxx              # create(conf/, cxx)
$ b configure: config.cxx=g++ src/  # configure(src/) config.
cxx=g++

Pour activer la syntaxe de raccourci, le premier argument buildspec doit commencer par un nom d'opération ou de méta-opération et se terminer par deux-points (:). Pour transformer la syntaxe de raccourci en la syntaxe buildspec normale, les deux-points sont remplacés par la parenthèse ouvrante ('('), le reste des arguments buildspec est traité tel quel, et la parenthèse fermante finale (')') est

ajoutée.

Pour chaque cible, le pilote s'attend à trouver un buildfile soit dans le répertoire de la cible ou, si le répertoire fait partie de l' arbre de sortie (out_base), dans le répertoire src correspondant (src_bas

e).

Par exemple, en supposant que foo/ est le répertoire source d'un projet

En plus des constructions in-source et out-of-source, build2 prend aussi en charge la configuration du répertoire source d'un projet comme transféré vers une construction out-of-source. Avec une telle configuration transférée en place, si nous exécutons le pilote du système de construction depuis le répertoire source, il construira automatiquement dans le répertoire de sortie et reliera (en utilisant des liens symboliques ou un autre mécanisme approprié) certaines cibles « intéressantes » (exécutables, documentation, etc.) au répertoire source pour un accès facile. En continuant avec l'exemple précédent

: 
$ b configure: foo/@foo-out/,forward  # foo/ transféré vers foo-out/
$ cd foo/
$ b                                   # construire dans foo-out/
$ ./foo                               # lien symbolique vers
foo-out/foo

La possibilité de spécifier des variables build2 dans la ligne de commande est normalement utilisée pour passer des valeurs de configuration, par exemple

: 
$ b config.cxx=clang++ config.cxx.
coptions=-O3

Similairement au buildspec, les shells POSIX inhibent souvent l'auto-complétion des chemins à droite d'une affectation de variable. Pour aider dans cette situation, l'affectation peut être divisée en trois arguments de ligne de commande séparés, par exemple

: 
$ b config.import.libhello = ..

--max-stack nu

La taille maximale de la pile en KBytes à autoriser pour les threads nouvellement créés. Pour les systèmes basés sur pthreads, le pilote interroge la taille de la pile du thread principal et utilise la même taille pour créer des threads supplémentaires. Cela permet d'ajuster la taille de la pile à l'aide de mécanismes familiers, tels que ulimit. Cependant, parfois, la taille de la pile du thread principal est excessivement grande. Par conséquent, le pilote vérifie si elle est supérieure à une limite prédéfinie (64 Mo sur les systèmes 64 bits et 32 Mo sur les systèmes 32 bits) et la limite à une valeur plus raisonnable (8 Mo) si c'est le cas. Cette option permet de contourner cette vérification avec la valeur spéciale zéro indiquant que la taille de la pile du thread principal doit être utilisée telle
quelle.

FICHIERS D'OPTIONS PAR DÉFAUT Au lieu d'avoir un format de fichier de configuration séparé pour la configuration des outils, la chaîne d'outils build2 utilise des fichiers d'options par défaut

qui

contiennent les mêmes options que celles qui peuvent être spécifiées sur la ligne de commande. Les fichiers d'options par défaut sont comme les fichiers d'options que l'on peut spécifier avec --options-file, sauf qu'ils sont chargés par défaut. Les fichiers d'options par défaut du pilote du système de construction sont appelés b.

options

et sont recherchés dans le sous-répertoire .build2/ du répertoire personnel et dans le répertoire système (par exemple, /etc/build2/) s'il est configuré. Notez que ces fichiers peuvent aussi contenir des surcharges de variables globales en plus des options. Une fois la recherche terminée, les fichiers sont chargés dans l'ordre inverse, c'est-à-dire en commençant par le répertoire système (s'il y en a un), suivi du répertoire personnel, et en terminant

par

les options spécifiées sur la ligne de commande. En d'autres termes, les fichiers sont chargés du plus générique au plus spécifique, les options de la ligne de commande ayant la capacité de surcharger toutes les valeurs spécifiées dans les fichiers d'options par défaut. Si un fichier d'options

par

défaut contient --no-default-options, alors la recherche s'arrête au répertoire contenant ce fichier et aucun fichier externe n'est chargé. Si cette option est spécifiée sur

la
