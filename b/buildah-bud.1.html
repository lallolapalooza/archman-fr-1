NOM

buildah-build - Construire une image en utilisant les instructions des fichiers Containerfile

SYNOPSIS

buildah build [options] [contexte]

buildah bud [options] [contexte]

DESCRIPTION

Construit une image en utilisant les instructions d'un ou plusieurs fichiers Containerfile ou Dockerfile et un répertoire de contexte de build spécifié. Un fichier Containerfile utilise la même syntaxe qu'un Dockerfile en interne. Pour ce document, un fichier désigné comme Containerfile peut être un fichier nommé 'Containerfile' ou 'Dockerfile'.

Le répertoire de contexte de build peut être spécifié comme l'URL http(s) d'une archive, d'un dépôt git ou d'un fichier Containerfile.

Si aucun répertoire de contexte n'est spécifié, Buildah considérera le répertoire de travail courant comme le contexte de build, qui devrait contenir un fichier Containerfile.

Les fichiers Containerfile se terminant par le suffixe ".in" seront pré-traités via cpp(1). Cela peut être utile pour décomposer les fichiers Containerfile en plusieurs parties réutilisables qui peuvent être utilisées via la directive #include de CPP. Notez qu'un fichier Containerfile.in peut toujours être utilisé par d'autres outils lorsqu'il est pré-traité manuellement via cpp -E. Les commentaires (lignes commençant par #) dans les fichiers Containerfile inclus qui ne sont pas des commandes de pré-traitement seront affichés sous forme d'avertissements pendant les builds.

Lorsque l'URL est une archive, le contenu de l'URL est téléchargé vers un emplacement temporaire et extrait avant l'exécution.

Lorsque l'URL est un fichier Containerfile, le fichier est téléchargé vers un emplacement temporaire.

Lorsqu'un dépôt Git est défini comme URL, le dépôt est cloné localement puis utilisé comme contexte de build. Une branche non par défaut (ou un ID de commit) et un sous-répertoire du dépôt git cloné peuvent être utilisés en incluant leurs noms à la fin de l'URL sous la forme monrepo.git#mabranch:sousrep, monrepo.git#moncommit:sousrep, ou monrepo.git#:sousrep si le sous-répertoire doit être utilisé à partir de la branche par défaut.

OPTIONS

--add-host=[]

Ajouter un mappage hôte-IP personnalisé (hôte:ip)

Ajoute une ligne à /etc/hosts. Le format est nom_hote:adresse_ip. L'option --add-host peut être définie plusieurs fois. Entre en conflit avec l'option --no-hosts.

Au lieu d'une adresse IP, le mot-clé spécial host-gateway peut être fourni. Celui-ci se résout en une adresse IP que le conteneur peut utiliser pour se connecter à l'hôte. L'adresse IP choisie dépend de votre configuration réseau, il n'y a donc aucune garantie que Buildah puisse déterminer automatiquement l'adresse host-gateway, ce qui entraînerait l'échec de Buildah avec un message d'erreur. Vous pouvez remplacer cette adresse IP en utilisant l'option host_containers_internal_ip dans containers.conf.

L'adresse host-gateway est également utilisée par Buildah pour ajouter automatiquement les noms d'hôte host.containers.internal et host.docker.internal à /etc/hosts. Vous pouvez empêcher cela en fournissant l'option --no-hosts, ou en définissant host_containers_internal_ip="none" dans containers.conf. Si aucune adresse host-gateway n'a été configurée manuellement et que Buildah ne parvient pas à déterminer l'adresse IP automatiquement, Buildah omettra silencieusement d'ajouter ces noms d'hôte internes à /etc/hosts. Si Buildah s'exécute dans une machine virtuelle utilisant podman machine (cela inclut les hôtes Mac et Windows), Buildah omettra silencieusement d'ajouter les noms d'hôte internes à /etc/hosts, sauf si une adresse IP a été configurée manuellement ; les noms d'hôte internes sont résolus par le résolveur DNS de gvproxy à la place.

Buildah utilisera le fichier /etc/hosts de l'hôte comme base par défaut, c'est-à-dire que tout nom d'hôte présent dans ce fichier sera également présent dans le fichier /etc/hosts du conteneur. Un fichier de base différent peut être configuré en utilisant la configuration base_hosts_file dans containers.conf.

--all-platforms

Au lieu de construire pour un ensemble de plateformes spécifiées à l'aide de l'option --platform, inspectez les images de base du build, et construisez pour toutes les plateformes pour lesquelles elles sont toutes disponibles. Les étapes qui utilisent scratch comme point de départ ne peuvent pas être inspectées, donc au moins une étape non-scratch doit être présente pour que la détection fonctionne utilement.

--annotation annotation[=valeur]

Ajoute une annotation d'image (par exemple, annotation=valeur) aux métadonnées de l'image. Peut être utilisée plusieurs fois. Si annotation est nommée, mais que ni = ni une valeur n'est fournie, alors annotation est définie sur une valeur vide.

Note : ces informations ne sont pas présentes dans les formats d'image Docker, elles sont donc ignorées lors de l'écriture des images dans des formats Docker.

--arch="ARCH"

Définit l'ARCH de l'image à construire, ainsi que celle de l'image de base à tirer, si le build en utilise une, à la valeur fournie au lieu d'utiliser l'architecture de l'hôte. (Exemples : arm, arm64, 386, amd64, ppc64le, s390x)

--authfile chemin

Chemin du fichier d'authentification. Par défaut est ${XDG_RUNTIME_DIR}/containers/auth.json. Voir containers-auth.json(5) pour plus d'informations. Ce fichier est créé en utilisant buildah login.

Si l'état d'autorisation ne s'y trouve pas, ${HOME}/.docker/config.json est vérifié, qui est défini en utilisant docker login.

Note : Vous pouvez également remplacer le chemin par défaut du fichier d'authentification en définissant la variable d'environnement REGISTRY_AUTH_FILE. export REGISTRY_AUTH_FILE=chemin

--build-arg arg=valeur

Spécifie un argument de build et sa valeur, qui sera interpolé dans les instructions lues à partir des fichiers Containerfile de la même manière que les variables d'environnement, mais qui ne sera pas ajouté à la liste des variables d'environnement dans la configuration de l'image résultante.

Veuillez vous référer à la section VARIABLES DE TEMPS DE BUILD ⟨#build-time-variables⟩ pour la liste des variables qui peuvent être remplacées dans le fichier Containerfile au moment de l'exécution.

--build-arg-file chemin

Spécifie un fichier contenant des lignes d'arguments de build de la forme arg=valeur. Le nom de fichier suggéré est argfile.conf.

Les lignes de commentaires commençant par # sont ignorées, ainsi que les lignes vides. Toutes les autres doivent être au format arg=valeur passé à --build-arg.

Si plusieurs arguments sont fournis via les options --build-arg-file et --build-arg, les arguments de build seront fusionnés à travers tous les fichiers et arguments de ligne de commande fournis.

Tout fichier fourni dans une option --build-arg-file sera lu avant les arguments fournis via l'option --build-arg.

Lorsqu'un nom d'argument donné est spécifié plusieurs fois, la dernière instance est celle qui est transmise aux builds résultants. Cela signifie que les valeurs --build-arg remplacent toujours celles d'un --build-arg-file.

--build-context nom=valeur

Spécifie un contexte de build supplémentaire en utilisant son nom court et son emplacement. Des contextes de build supplémentaires peuvent être référencés de la même manière que nous accédons à différents stages dans l'instruction COPY.

Les valeurs valides pourraient être : * Répertoire local – par exemple, --build-context projet2=../chemin/vers/projet2/src * URL HTTP vers une archive tar – par exemple, --build-context src=https://example.org/releases/src.tar * Image conteneur – spécifiée avec un préfixe container-image://, par exemple, --build-context alpine=container-image://alpine:3.15, (accepte également docker://, docker-image://)

Du côté du Containerfile, vous pouvez référencer le contexte de build sur toutes les commandes qui acceptent le paramètre “from”. Voici à quoi cela pourrait ressembler :

FROM [nom]
COPY --from=[nom] ...
RUN --mount=from=[nom] …

La valeur de [nom] est mise en correspondance avec l'ordre de priorité suivant :

  • Contexte de build nommé défini avec --build-context [nom]=..
  • Étape définie avec AS [nom] dans Containerfile
  • Image [nom], locale ou dans un registre distant

--cache-from

Dépôt à utiliser comme liste potentielle de sources de cache. Lorsqu'il est spécifié, Buildah essaiera de rechercher des images de cache dans les dépôts spécifiés et tentera de télécharger des images de cache au lieu d'exécuter réellement les étapes de build localement. Buildah tentera de télécharger uniquement les images précédemment mises en cache si elles sont considérées comme des correspondances de cache valides.

Utilisez l'option --cache-to pour remplir un ou plusieurs dépôts distants avec du contenu de cache.

Exemple

# remplir un cache et le consulter également
buildah build -t test --layers --cache-to registry/myrepo/cache --cache-from registry/myrepo/cache .

L'option --layers doit être spécifiée, sinon l'option --cache-from est

ignorée.

Note : L'option --cache-from de Buildah est conçue différemment de l'option --cache-from de Docker et BuildKit. Le mécanisme de cache distribué de Buildah récupère lui-même les images intermédiaires depuis le registre distant, contrairement à Docker et BuildKit où l'image intermédiaire est stockée dans l'image elle-même. L'approche de Buildah est similaire à celle de kaniko, qui ne gonfle pas la taille de l'image originale avec des images intermédiaires. De plus, les images intermédiaires peuvent réellement être conservées de manière distribuée sur un ou plusieurs registres distants à l'aide du mécanisme de cache de

Buildah.

--cpu-shares, -c=

0

Partages CPU (poids

relatif)

Par défaut, tous les conteneurs reçoivent la même proportion de cycles CPU. Cette proportion peut être modifiée en changeant le poids de partage CPU du conteneur par rapport au poids de tous les autres conteneurs en cours

d'exécution.

Pour modifier la proportion par défaut de 1024, utilisez le drapeau --cpu-shares pour définir le poids à 2 ou

plus.

La proportion ne s'appliquera que lorsque des processus gourmands en CPU sont en cours d'exécution. Lorsque les tâches d'un conteneur sont inactives, les autres conteneurs peuvent utiliser le temps CPU restant. La quantité réelle de temps CPU variera en fonction du nombre de conteneurs en cours d'exécution sur le

système.

Par exemple, considérez trois conteneurs, l'un a un cpu-share de 1024 et les deux autres ont un paramètre cpu-share de 512. Lorsque les processus des trois conteneurs tentent d'utiliser 100% du CPU, le premier conteneur recevrait 50% du temps CPU total. Si vous ajoutez un quatrième conteneur avec un cpu-share de 1024, le premier conteneur ne reçoit que 33% du CPU. Les conteneurs restants reçoivent 16,5%, 16,5% et 33% du

CPU.

Sur un système multi-cœurs, les parts de temps CPU sont distribuées sur tous les cœurs CPU. Même si un conteneur est limité à moins de 100% du temps CPU, il peut utiliser 100% de chaque cœur CPU

individuel.

Par exemple, considérez un système avec plus de trois cœurs. Si vous démarrez un conteneur {C0} avec -c=512 exécutant un processus, et un autre conteneur {C1} avec -c=1024 exécutant deux processus, cela peut entraîner la division suivante des parts de CPU

:

102    {C1}		2	100% de

--cw option

s

Produire une image adaptée à une utilisation comme charge de travail confidentielle s'exécutant dans un environnement d'exécution de confiance (TEE) utilisant krun (c'est-à-dire, crun compilé avec la fonctionnalité libkrun activée et invoqué en tant que krun). krun.

La valeur pour options est une liste de paires clé=valeur séparées par des virgules, fournissant les informations de configuration nécessaires pour produire les données supplémentaires qui seront incluses dans l'image du

conteneur.

Les clés reconnues sont

attestation_url : L'emplacement d'un courtier de clés / serveur d'attestation. Au moment de l'exécution, krun est censé contacter le serveur pour récupérer la phrase secrète à l'aide de l'identifiant de charge de travail, qui est également stocké dans l'image du conteneur. Si aucune valeur n'est spécifiée, une valeur de phrase secrète doit être

spécifiée.

cpus : Le nombre de CPU virtuels avec lesquels l'image est censée être exécutée au moment de l'exécution. Si non spécifié, une valeur par défaut sera

fournie.

firmware_library : L'emplacement de la bibliothèque partagée libkrunfw-sev. Si non spécifié, buildah vérifie sa présence dans un certain nombre d'emplacements codés en

dur. ">memory : La quantité de mémoire que l'image s'attend à utiliser à l'exécution, exprimée en mégaoctets. Si non spécifiée, une valeur par défaut sera

fournie.

passphrase : La phrase secrète à utiliser pour chiffrer l'image disque qui sera incluse dans l'image conteneur. Si aucune valeur n'est spécifiée, mais qu'une valeur attestation_url est spécifiée, une phrase secrète générée aléatoirement sera utilisée. slop : Espace supplémentaire à allouer pour l'image disque par rapport à la taille du contenu de l'image conteneur, exprimé soit comme un pourcentage (..%), soit comme une valeur de taille (octets, ou unités plus grandes si des suffixes comme KB ou MB sont présents), soit comme une somme de deux spécifications ou plus. Si non spécifié, buildah suppose que 25 % d'espace de plus que le contenu suffira, mais cette option est fournie au cas où sa supposition serait

Par défaut, les volumes montés par liaison (bind) sont privés. Cela signifie que tout montage effectué à l'intérieur du conteneur ne sera pas visible sur l'hôte et vice versa. Ce comportement peut être modifié en spécifiant une propriété de propagation du montage de

volume.

Lorsque la politique de propagation du montage est définie sur shared, tout montage effectué à l'intérieur du conteneur sur ce volume sera visible à la fois par l'hôte et le conteneur. Lorsque la politique de propagation du montage est définie sur slave, la propagation de montage unidirectionnelle est activée et tout montage effectué sur l'hôte pour ce volume ne sera visible qu'à l'intérieur du conteneur. Pour contrôler la propriété de propagation du montage du volume, utilisez l'indicateur :[r]shared, :[r]slave ou :[r]private. La propriété de propagation ne peut être spécifiée que pour les volumes montés par liaison et non pour les volumes internes ou les volumes nommés. Pour que la propagation du montage fonctionne sur le point de montage source (le point de montage où le répertoire source est monté), il doit avoir les propriétés de propagation appropriées. Pour les volumes partagés, le point de montage source doit être partagé. Et pour les volumes esclaves, le montage source doit être soit partagé, soit esclave. [1]

⟨#Footnote1⟩

Utilisez df <source-dir> pour déterminer le montage source et puis utilisez findmnt -o TARGET,PROPAGATION <source-mount-dir> pour déterminer les propriétés de propagation du montage source. Si l'utilitaire findmnt n'est pas disponible, le point de montage source peut être déterminé en examinant l'entrée de montage dans /proc/self/mountinfo. Regardez les champs optionnels et voyez si des propriétés de propagation sont spécifiées. shared:X signifie que le montage est partagé (shared), master:X signifie que le montage est esclave (slave) et s'il n'y a rien, cela signifie que le montage est privé (private). [1]

⟨#Footnote1⟩

Pour changer les propriétés de propagation d'un point de montage, utilisez la commande mount. Par exemple, pour monter par liaison le répertoire sourcetory /foo do mount --bind /foo /foo et mount --make-private --make-shared /foo. Cela convertira /foo en un point de montage partagé. Les propriétés de propagation du montage source peuvent être modifiées directement. Par exemple, si / est le montage source pour /foo, alors utilisez mount --make-shared / pour convertir / en un montage

par
tagé.
