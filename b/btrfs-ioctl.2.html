NOM

btrfs-ioctl - documentation sur les ioctl de btrfs

NOM

btrfs-ioctl - documentation pour l'interface ioctl de btrfs

DESCRIPTION

L'appel système ioctl() est un moyen de demander l'exécution d'actions personnalisées sur un système de fichiers, au-delà des interfaces standard (comme les appels système). Un ioctl est spécifié par un numéro et une structure de données associée qui implémente une fonctionnalité, généralement non disponible dans d'autres systèmes de fichiers. Le nombre d'ioctls augmente avec le temps et dans certains cas, ils sont promus au niveau VFS une fois que d'autres systèmes de fichiers adoptent la fonctionnalité. La compatibilité ascendante est maintenue et un ancien numéro d'ioctl peut devenir disponible au niveau VFS.

APERÇU

Les ioctls sont définis par un numéro et associés à une structure de données contenant des informations supplémentaires. Tous les ioctls utilisent un descripteur de fichier (fd) comme point de référence ; il peut s'agir du système de fichiers ou d'un répertoire à l'intérieur du système de fichiers.

Un ioctl peut être utilisé de manière schématique comme suit :

struct btrfs_ioctl_args args;
memset(&args, 0, sizeof(args));
args.key = value;
ret = ioctl(fd, BTRFS_IOC_NUMBER, &args);

Le fd est le point d'entrée vers le système de fichiers et pour la plupart des ioctls, il n'importe pas quel répertoire est utilisé. Une distinction entre les fichiers et les répertoires a parfois de l'importance, et lorsque c'est le cas, cela est explicitement mentionné. L'argument args est la structure de données associée à la requête. Il est fortement recommandé d'initialiser toute la structure à zéro, car cela garantit la compatibilité future lorsque l'ioctl subira des extensions. Ne pas le faire pourrait entraîner une incompatibilité entre les anciennes versions de l'espace utilisateur et les nouvelles versions du noyau, ou vice versa. Le BTRFS_IOC_NUMBER indique quelle opération doit être effectuée sur les arguments donnés. Certains ioctls prennent une structure de données spécifique, certains partagent une structure commune, et il existe également des ioctls sans structure d'arguments. Les données passées à un ioctl peuvent être en entrée, en sortie, ou les deux.

La bibliothèque libbtrfsutil encapsule quelques ioctls pour plus de commodité. L'utilisation des ioctls bruts n'est pas découragée mais peut être fastidieuse, bien qu'elle ne nécessite pas de dépendance supplémentaire à une bibliothèque. La compatibilité ascendante est garantie et les changements incompatibles entraînent généralement une nouvelle version de l'ioctl. Des améliorations des ioctls existants peuvent avoir lieu et dépendent de la définition de drapeaux supplémentaires. L'espace inutilisé mis à zéro est généralement compris comme un mécanisme de communication de la compatibilité entre le noyau et l'espace utilisateur, et donc la mise à zéro est vraiment importante. Dans des cas exceptionnels, cela ne suffit pas et des drapeaux supplémentaires doivent être passés pour distinguer zéro en tant qu'initialisation implicite inutilisée et une valeur zéro valide. Ces cas sont documentés.

Les descripteurs de fichiers de fichiers réguliers sont obtenus par int fd = open(), les répertoires ouverts avec DIR *dir = opendir() peuvent être convertis en descripteur de fichier correspondant par fd = dirfd(dir).

BTRFS_IOC_INO_LOOKUP

Résout un numéro d'inode en chemin (nécessite CAP_SYS_ADMIN), ou lit l'identifiant du sous-volume contenant le fichier donné (non restreint, cas particulier). La taille du tampon du chemin est inférieure à PATH_MAX (4096), il est possible que le chemin soit tronqué à cause de cela. Également implémenté par btrfs inspect-internal rootid <#man-inspect-rootid>.

Le cas général nécessite CAP_SYS_ADMIN et peut résoudre n'importe quel fichier vers son chemin. Le cas particulier pour lire le sous-volume contenant n'est pas restreint :

struct btrfs_ioctl_ino_lookup_args args;
fd = open("file", ...);
args.treeid = 0;
args.objectid = BTRFS_FIRST_FREE_OBJECTID;
ioctl(fd, BTRFS_IOC_INO_LOOKUP, &args);
/* args.treeid contient maintenant l'identifiant du sous-volume */
