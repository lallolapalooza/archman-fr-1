BOOSTER(1) Manuel des commandes générales BOOSTER(1)

NOM

booster - générateur d'initramfs rapide et sécurisé

DESCRIPTION

Booster est un outil pour créer les images initramfs nécessaires au début du processus de démarrage de Linux. Booster est conçu dans le but d'être rapide et pour les cas d'utilisation de chiffrement complet du disque.

Avantages de Booster :

  • Temps de construction d'image et temps de démarrage rapides.
  • Support prêt à l'emploi pour la configuration de chiffrement complet du disque basée sur LUKS.
  • Liaison de données de type Clevis. Le système de fichiers chiffré peut être lié à une puce TPM2 ou à un service réseau. Cela permet de déverrouiller le disque automatiquement, mais uniquement si le service TPM2/réseau est présent.
  • Détecte et déverrouille automatiquement le chiffrement de partition de type systemd-cryptenroll (fido2 et tpm2).
  • Facile à configurer.
  • Découverte automatique de la configuration de l'hôte. Cela permet de créer des images minimalistes spécifiques à l'hôte actuel.

FICHIER DE CONFIGURATION

Le fichier de configuration du générateur booster se trouve dans /etc/booster.yaml. Voici un exemple de fichier de configuration :

network:
  interfaces: enp0s31f2,2e:1d:61:30:a3:63
  dhcp: on
  # on peut utiliser soit dhcp ci-dessus, soit la configuration statique ci-dessous
  ip: 10.0.2.15/24
  gateway: 10.0.2.255
  dns_servers: 192.168.1.1,8.8.8.8
universal: false
modules: -*,hid_apple,kernel/sound/usb/,kernel/fs/btrfs/btrfs.ko,kernel/lib/crc4.ko.xz
compression: zstd
mount_timeout: 5m6s
strip: true
extra_files: vim,/usr/share/vim/vim82/,fsck,fsck.ext4
vconsole: true
enable_lvm: true
enable_mdraid: true
  • Le nœud network, s'il est présent, initialise le réseau au moment du démarrage. Il est nécessaire si le montage d'un système de fichiers racine nécessite un accès réseau (par exemple, en cas de liaison Tang). Le réseau peut être configuré dynamiquement avec DHCPv4 ou statiquement dans cette configuration. Dans le premier cas, dhcp est défini sur on. Dans le second cas, la configuration permet de spécifier ip - l'adresse IP de la machine et son masque réseau, gateway - la passerelle par défaut, dns_servers - une liste de serveurs DNS séparés par des virgules. Le nœud network accepte également la propriété interfaces - une liste d'interfaces réseau séparées par des virgules (spécifiées par leur nom ou leur adresse MAC) à activer au démarrage. Les noms de réseau comme enp0s31f6 sont résolus en adresses MAC au moment de la génération, puis transmis à init. Si le nœud interfaces n'est pas spécifié, toutes les interfaces sont activées au démarrage.
  • universal est un indicateur booléen qui indique à booster de générer une image universelle. Par défaut, booster génère une image spécifique à l'hôte qui inclut les modules noyau utilisés sur l'hôte actuel. Par exemple, si l'hôte n'a pas de puce TPM2, les modules TPM sont ignorés. Une image universelle inclut de nombreux modules noyau et outils qui pourraient être nécessaires pour un large éventail de configurations matérielles.
  • modules est une liste de modules supplémentaires séparés par des virgules à ajouter ou à supprimer de l'image générée. On peut utiliser le nom d'un module ou un chemin relatif au répertoire des modules (/usr/lib/modules/$KERNEL_VERSION). Le suffixe de l'algorithme de compression (par exemple, ".xz", ".gz) peut être omis du nom du fichier du module. Si l'élément commence par un signe moins (-), cela signifie "ne pas l'ajouter à l'image", sinon les modules sont ajoutés. Si le chemin se termine par une barre oblique (/), il est considéré comme un répertoire et tous les modules de ce répertoire doivent être ajoutés récursivement. Un symbole spécial * (étoile) signifie tous les modules. Il peut être utilisé, par exemple, pour ajouter tous les modules ou supprimer tous les modules prédéfinis de l'image. Booster prend également en compte les dépendances des modules, toutes les dépendances des modules spécifiés seront ajoutées à l'image.
  • modules_force_load liste de noms de modules qui sont chargés de force pendant le processus de démarrage avant de passer en espace utilisateur. Tout module dans cette liste est automatiquement ajouté à l'image, il n'est donc pas nécessaire de le dupliquer dans la propriété modules.
  • append_all_modaliases est un indicateur booléen qui demande à booster d'ajouter tous les alias de modules de l'hôte à l'image booster. Cet indicateur est utile pour déboguer les problèmes de délai de démarrage lorsque certains modules importants manquent dans l'image. Définir cet indicateur à true aidera à imprimer les noms des modules pour les alias qui ont été demandés par le noyau mais manquants dans l'image.
  • compression est un indicateur qui spécifie la compression pour le fichier initramfs de sortie. Les algorithmes actuellement pris en charge sont "zstd", "gzip", "xz", "lz4", "none". Si aucune option n'est spécifiée, "zstd" est utilisé comme compression par défaut.
  • mount_timeout délai d'attente pour que le système de fichiers racine apparaisse. Le format du champ est un nombre décimal suivi d'un nombre d'unité. Les unités valides sont "s", "m", "h". Si aucune valeur n'est spécifiée, le délai d'attente par défaut (3 minutes) est utilisé. Pour désactiver complètement le délai d'attente, spécifiez "0s".
  • strip est un indicateur booléen qui active le nettoyage des fichiers ELF avant de les ajouter à l'image. Les binaires, les bibliothèques partagées et les modules noyau sont des exemples de fichiers ELF qui sont traités avec l'outil UNIX strip.
Cette option n'est pas compatible avec les modules signés. Si vous voyez une erreur de démarrage booster: finit(crc32,generic): key was rejected by service, veuillez définir l'option de configuration strip sur false.
  • extra_files est une liste de fichiers supplémentaires séparés par des virgules à ajouter à l'image. Si un élément commence par une barre oblique ("/"), il est considéré comme un chemin absolu. Sinon, c'est un chemin relatif à /usr/bin. Si l'élément est un répertoire, son contenu est ajouté récursivement. Il existe quelques cas spéciaux :
  • l'ajout de busybox à l'image active un shell d'urgence en cas de panique pendant le processus de démarrage.
  • l'ajout de fsck active la vérification du système de fichiers au démarrage. Il nécessite également que le binaire spécifique au système de fichiers appelé fsck.$rootfstype soit ajouté à l'image. Les systèmes de fichiers sont corrigés automatiquement et si cela échoue, le démarrage s'arrête et il incombe à l'utilisateur de corriger le système de fichiers racine.
  • vconsole est un indicateur qui active la configuration de la console précoce. S'il est défini sur true, booster lit la configuration depuis /etc/vconsole.conf et /etc/locale.conf et ajoute la disposition de clavier et les polices requises à l'image générée. Les propriétés de configuration suivantes sont prises en compte : KEYMAP, KEYMAP_TOGGLE, FONT, FONT_MAP, FONT_UNIMAP. Voir également man vconsole.conf https://man.archlinux.org/man/vconsole.conf.5.fr.
  • enable_lvm est un indicateur qui active l'assemblage des volumes LVM au moment du démarrage. Cet indicateur garantit également que tous les modules/binaires requis sont ajoutés à l'image.
  • enable_mdraid est un indicateur qui active l'assemblage MdRaid au moment du démarrage. Cet indicateur garantit également que tous les modules/binaires requis sont ajoutés à l'image.
  • enable_zfs est un indicateur qui active le système de fichiers ZFS comme système de fichiers racine. Cet indicateur garantit également que tous les modules/binaires requis sont ajoutés à l'image. Notez que si ZFS est activé, l'option de démarrage zfs= doit être utilisée à la place de l'option de démarrage root=.

Une fois que vous avez terminé de modifier votre fichier de configuration et que vous souhaitez régénérer les images booster dans /boot, utilisez /usr/lib/booster/regenerate_images. Il s'agit d'un script pratique qui effectue le même type de régénération d'image que si vous aviez installé booster avec votre gestionnaire de paquets.

    PARAMÈTRES DU NOYAU POUR LE DÉMARRAGE

    Certaines parties des fonctionnalités de démarrage de booster peuvent être modifiées avec les paramètres de démarrage du noyau. Ces paramètres sont généralement définis via la configuration du chargeur de démarrage. Booster boot utilise les paramètres de noyau suivants :

    • root=$deviceref référence de périphérique pour le périphérique racine. Voir les notes ci-dessous pour savoir comment spécifier la référence de périphérique. Si root= pointe vers une partition LUKS, celle-ci est automatiquement déverrouillée en tant que périphérique /dev/mapper/root et montée en racine. Booster prend également en charge la découverte automatique de la partition racine https://systemd.io/DISCOVERABLE_PARTITIONS/ - si aucun paramètre root= n'est spécifié, booster vérifie la présence de partitions avec un type GPT spécifique et l'utilise pour le montage en racine.
    • rootfstype=$TYPE (par exemple rootfstype=ext4). Par défaut, booster essaie de détecter le type du système de fichiers racine. Mais si la détection automatique ne fonctionne pas, ce paramètre de noyau est utile. Veuillez également soumettre un ticket afin que nous puissions améliorer le code de détection des types de fichiers.
    • rootflags=$OPTIONS options de montage pour le système de fichiers racine, par exemple rootflags=user_xattr,nobarrier. En mode de découverte automatique de partition, l'attribut GPT 60 (« read-only ») est pris en compte.
    • rd.luks.uuid=$UUID UUID de la partition LUKS contenant la partition racine. Booster essaiera de déverrouiller ce périphérique LUKS.
    • rd.luks.name=$UUID=$NAME similaire au paramètre rd.luks.uuid mais spécifie également le nom utilisé pour l'ouverture du périphérique LUKS.
    • rd.luks.key=$UUID=$PATH chemin absolu vers un fichier de clé dans l'initrd/initramfs qui peut être utilisé pour déverrouiller le périphérique identifié par UUID ; si ce fichier n'existe pas ou échoue à déverrouiller, une demande de mot de passe sera utilisée à la place.
    • rd.luks.options=opt1,opt2 liste d'options LUKS séparées par des virgules. Les options prises en charge sont discard, same-cpu-crypt, submit-from-crypt-cpus, no-read-workqueue, no-write-workqueue. Notez que booster prend également en charge les options persistantes LUKS v2 stockées avec les métadonnées de la partition. Toutes les options de ligne de commande sont ajoutées en plus des options persistantes.
    • rd.modules_force_load liste de modules du noyau supplémentaires, séparés par des virgules, qui doivent être chargés de force.
    • resume=$deviceref référence de périphérique pour le périphérique de mise en veille prolongée sur disque.
    • zfs=$pool/$dataset spécifie quel jeu de données ZFS doit être utilisé pour la partition racine. Cette option n'est utilisée que si l'option de configuration ZFS est activée. Si le système de fichiers ZFS est activé, le paramètre de démarrage root= est ignoré.
    • booster.log configure la journalisation de booster init. Elle accepte une liste séparée par des virgules des valeurs suivantes :
    L'une des valeurs de niveau (du plus verbeux au moins verbeux) - debug, info, warning, error. Si le niveau n'est pas spécifié, info est utilisé par défaut.
    console - imprime les journaux de booster init sur la console.
    Le journal de debug est également imprimé dans le tampon kmsg du noyau et est disponible pour lecture avec dmesg ou avec journalctl -b. Si le niveau de debug est activé, la limitation de kmsg est automatiquement désactivée.
    • booster.debug une option obsolète qui est équivalente à booster.log=debug,console.
    • quiet Définit la verbosité de booster init au minimum. Cette option est ignorée si booster.debug ou booster.log est défini.
    • init=$PATH chemin vers le binaire d'init en espace utilisateur. Si non spécifié, la valeur par défaut /sbin/init est utilisée.

    NOTES

    RÉFÉRENCE DE PÉRIPHÉRIQUE

    La référence de périphérique est un moyen de spécifier un périphérique ou une partition dans les paramètres du noyau. Elle est étiquetée comme $deviceref ci-dessus. La référence de périphérique a l'une des valeurs suivantes :

    • /dev/XXX chemin vers un fichier de périphérique spécifique, il peut s'agir d'un chemin vers un périphérique/partition réel comme /dev/sda1, /dev/nvme0n1 ou d'un chemin vers un périphérique virtuel dm-mapper comme /dev/mapper/root ou /dev/vg_mesos/lv_mesos_containers.
    • UUID=$UUID ou /dev/disk/by-uuid/$UUID référence le périphérique par son UUID de système de fichiers/LUKS. Voir les notes sur les règles de formatage des UUID ci-dessous.
    • LABEL=$LABEL ou /dev/disk/by-label/$LABEL référence le périphérique par son étiquette de système de fichiers/LUKS.
    • PARTUUID=$UUID ou /dev/disk/by-partuuid/$UUID référence le périphérique par l'UUID de partition GPT.
    • PARTUUID=$UUID/PARTNROFF=$OFFSET référence le périphérique à $OFFSET depuis une partition GPT spécifiée par $UUID, par exemple PARTUUID=fd59d06d-ffa8-473b-94f0-6584cb2b6665/PARTNROFF=2.
    • PARTLABEL=$LABEL ou /dev/disk/by-partlabel/$LABEL référence le périphérique par l'étiquette de partition GPT.
    • HWPATH=$PATH ou /dev/disk/by-path/$PATH référence le périphérique par son chemin matériel déterministe, par exemple pci-0000:02:00.0-nvme-1-part2.
    • WWID=$ID ou /dev/disk/by-id/$ID référence le périphérique par son wwid, par exemple nvme-KXG6AZNV256G_TOSHIBA_40SA13GZF6B1-part3

    PARAMÈTRES UUID

    Les paramètres de démarrage tels que root=UUID=$UUID et rd.luks.uuid=$UUID vous permettent de spécifier le périphérique bloc par son UUID. Le format du UUID est xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx où x est un symbole hexadécimal en minuscule ou majuscule. Le paramètre UUID peut éventuellement être entouré du symbole de guillemet " bien que cela ne soit pas recommandé. Les exemples suivants montrent le format correct des paramètres : root=UUID=ac8299a8-91ce-4bf6-a524-55a62844b787, root=UUID="ac8299a8-91ce-4bf6-a524-55a62844b787" (non recommandé), rd.luks.uuid=ac8299a8-91ce-4bf6-a524-55a62844b787, rd.luks.uuid="ac8299a8-91ce-4bf6-a524-55a62844b787" (non recommandé).

    SÉLECTION DES MODULES

    Il s'agit d'une note résumant l'algorithme qui calcule quels modules vont se retrouver dans l'image booster générée. La liste initiale des modules pour booster est defaultModulesList - un ensemble de modules prédéfinis en dur défini dans generator.go. Ce sont les modules sélectionnés qui couvrent très probablement la plupart des besoins de démarrage du système - disque, système de fichiers, clavier, tpm, pilotes ethernet, usb.

    Si l'option de configuration universal est définie à false (valeur par défaut), le mode hôte est utilisé. C'est-à-dire que l'image est générée avec uniquement les pilotes nécessaires pour le matériel de l'hôte actuel. Pour ce faire, booster récupère tous les modules actuellement chargés depuis /sys/module/ et calcule l'intersection avec defaultModulesList.

    Ensuite, booster examine l'option de configuration modules , une liste d'éléments séparés par des virgules. Il parcourt tous les éléments de gauche à droite. La règle de filtrage du mode hôte ne s'applique pas à cette liste de modules spécifiés manuellement.

    Si l'élément commence par le signe moins - alors il supprime les modules donnés de l'image, sinon les modules sont ajoutés à l'image.

    Si l'élément est un nom de module, ce module est ajouté/supprimé. Notez que par convention, le nom d'un module du noyau peut être calculé à partir de son nom de fichier en remplaçant tous les tirets par des traits de soulignement, par exemple. Pour le module hid-apple.ko.gz le nom sera hid_apple.

    Si l'élément est un chemin vers le fichier du module relatif à /usr/lib/modules/$KERNEL_VERSION alors le module est ajouté/supprimé. Notez que le suffixe de l'algorithme de compression peut être omis du nom de fichier du module.

    Si l'élément se termine par le symbole slash / alors cet élément est considéré comme un répertoire relatif à /usr/lib/modules/$KERNEL_VERSION. Booster parcourt ce répertoire récursivement et ajoute/supprime les modules à l'image. Le signe moins peut être utilisé avec les répertoires.

    Le symbole étoile * est un raccourci pour « tous les modules », il peut être utilisé pour ajouter tous les modules ou retirer tous les modules de l'image.

    Ensuite, booster passe à l'option modules_force_load qui consiste en des noms de modules à charger au démarrage. Tous ces modules sont également ajoutés à l'image.

    À l'étape finale, booster calcule les graphes de dépendances entre les modules et toutes les dépendances requises. Par exemple, si un utilisateur a manuellement ajouté ext4 et que le système de build du noyau indique que le module ext nécessite mbcache et jbd2 alors à la fois mbcache et jbd2 sont automatiquement ajoutés à l'image.

    IMAGE DE DÉMARRAGE UNIFIÉE

    Une Image de Démarrage Unifiée https://uapi-group.org/specifications/specs/unified_kernel_image/ (UKI) est un binaire PE qui regroupe divers composants de démarrage (par exemple le noyau, l'initrd et un stub de démarrage UEFI) en un seul exécutable. Cela permet de démarrer directement via le firmware (UEFI) ainsi que d'authentifier tous les composants de démarrage d'un coup pour Secure Boot.

    Pour générer des UKI avec Booster, veuillez installer le générateur UKI de systemd (systemd-ukify) depuis le gestionnaire de paquets de votre distribution et utiliser /usr/lib/booster/regenerate_uki. C'est un script de commodité qui effectue le même type de régénération d'image que si vous installiez booster avec votre gestionnaire de paquets, puis passe le résultat au générateur UKI de systemd (ukify) en entrée. Le script ne passe qu'un sous-ensemble des composants de démarrage, notamment le microcode du système, l'initrd, le fichier os-release, l'image de démarrage et le noyau. Les entrées de ligne de commande du noyau de l'UKI sont héritées de /etc/booster.yaml.

    Veuillez noter que pour démarrer l'UKI par défaut, il peut être nécessaire de configurer le(s) fichier(s) de configuration de votre chargeur de démarrage en conséquence.

    DÉBOGAGE

    Si vous rencontrez un problème avec l'outil de démarrage booster, vous pouvez activer le mode de débogage pour obtenir plus d'informations sur ce qui se passe. Il suffit d'ajouter le paramètre du noyau booster.log=debug,console et booster fournira des logs supplémentaires.

    Utiliser TFTP pour télécharger les logs d'un appareil non démarrable

    En cas d'échec de démarrage, lorsque les appareils sont manquants, les logs peuvent toujours être récupérés depuis busybox en utilisant le réseau. Tout d'abord, configurez un serveur tftp (port 69) sur une autre machine/VM. Par exemple sur Archlinux, pacman -S atftp; systemctl start atftpd. Ensuite, modifiez /etc/booster.yaml et ajoutez le support réseau et busybox (extra_files: busybox). Regénérez l'initramfs et redémarrez. Une fois dans busybox, récupérez les logs et envoyez-les au serveur tftp :

    $ dmesg >boot.log
$ lsmod >mods.log
$ tftp -pl boot.log <ip du serveur>
$ tftp -pl mods.log <ip du serveur>

    Les logs se trouveront dans /srv/atftp sur le serveur.

    Délai d'attente au démarrage

    Si vous obtenez l'erreur booster: Timeout waiting for root filesystem, veuillez ajouter le drapeau de configuration append_all_modaliases et reconstruire l'image. Avec ce drapeau, vous obtiendrez une liste des modules qui ont été demandés par le noyau mais qui sont absents de l'image booster. Certains de ces modules pourraient être requis pour démarrer votre système.

    EXEMPLES

    Créez un fichier initramfs spécifique pour le noyau/hôte actuel. Le fichier de sortie est booster.img :

    $ booster build booster.img

    Créez une image universelle avec de nombreux modules (tels que les pilotes SATA/TPM/NVME/...) inclus :

    $ booster build --universal booster.img

    Créez un initramfs pour la version du noyau 5.4.91-1-lts et copiez-le dans /boot/booster-lts.img :

    $ booster build --kernel-version 5.4.91-1-lts /boot/booster-lts.img

    Voici une configuration systemd-boot stockée dans /boot/loader/entries/booster.conf. Dans cet exemple, e122d09e-87a9-4b35-83f7-2592ef40cefa est un UUID pour la partition LUKS et 08684949-bcbb-47bb-1c17-089aaa59e17e est un UUID pour le système de fichiers chiffré (par exemple, ext4). Veuillez vous référer à la documentation de votre chargeur de démarrage pour plus d'informations sur sa configuration.

    title Linux with Booster
linux /vmlinuz-linux
initrd /booster-linux.img
options rd.luks.uuid=e122d09e-87a9-4b35-83f7-2592ef40cefa root=UUID=08684949-bcbb-47bb-1c17-089aaa59e17e rw

    Les utilisateurs du système de fichiers Btrfs avec un système installé sur un sous-volume doivent ajouter les rootflags correspondant à leur entrée dans /etc/fstab. Dans cet exemple, 69bc4dd2-7f6c-4821-aa6b-d80d9c97d470 est un UUID pour la partition Btrfs, avec le système installé sur le sous-volume nommé root et /etc/fstab ressemble à ceci :

    UUID=69bc4dd2-7f6c-4821-aa6b-d80d9c97d470	/         	btrfs     	rw,relatime,autodefrag,compress=zstd:2,space_cache,subvol=root	0 0

    Ainsi, /boot/loader/entries/booster.conf devrait ressembler à ceci :

    title Linux with Booster
linux /vmlinuz-linux
initrd /booster-linux.img
options root=UUID=69bc4dd2-7f6c-4821-aa6b-d80d9c97d470 rw rootflags=relatime,autodefrag,compress=zstd:2,space_cache,subvol=root

    Créez une Unified Kernel Image et écrivez le résultat dans /boot/EFI/Linux :

    $ /usr/lib/booster/regenerate_uki build /boot/EFI/Linux
