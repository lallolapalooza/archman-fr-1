NOM

badvpn-tun2socks - créer un périphérique TUN pour router le trafic TCP via un serveur SOCKS

SYNOPIS

badvpn-tun2socks
[--help]
[--version]
[--logger <stdout/syslog>]
[--syslog-facility <chaîne>] [--syslog-ident <chaîne>]
[--loglevel <0-5/none/error/warning/notice/info/debug>]
[--channel-loglevel <nom-canal> <0-5/none/error/warning/notice/info/debug>] ...
[--tundev <nom>]
--netif-ipaddr <adresse ip>
--netif-netmask <masque ip>
--socks-server-addr <adresse>
[--udpgw-remote-server-addr <adresse>]
[--udpgw-max-connections <nombre>]
[--udpgw-connection-buffer-size <nombre>]

Le format de l'adresse est a.b.c.d:port (IPv4) ou [adresse]:port (IPv6).

DESCRIPTION

badvpn-tun2socks est un utilitaire réseau utilisé pour "socksifier" les connexions TCP au niveau réseau. Il implémente un périphérique TUN qui accepte toutes les connexions TCP entrantes (indépendamment de la destination IP), et les transfère via un serveur SOCKS. Cela permet de transférer toutes les connexions via SOCKS, sans aucune modification des applications. Il peut être utilisé, par exemple, pour transférer des connexions via un serveur SSH distant.

EXEMPLE

Cet exemple montre comment utiliser tun2socks en combinaison avec la fonction de transfert dynamique de SSH.

Connectez-vous au serveur SSH, en passant -D localhost:1080 à la commande ssh pour activer le transfert dynamique. Cela fera ouvrir à ssh un serveur SOCKS local que tun2socks utilisera pour transférer les connexions.

Créez d'abord un périphérique TUN (par exemple en utilisant openvpn) :

  openvpn --mktun --dev tun0 --user <un_utilisateur>

Configurez l'adresse IP du nouveau périphérique tun :

  ifconfig tun0 10.0.0.1 netmask 255.255.255.0

Lancez maintenant le programme badvpn-tun2socks :

  badvpn-tun2socks --tundev tun0 --netif-ipaddr 10.0.0.2 --netif-netmask 255.255.255.0 \
                   --socks-server-addr 127.0.0.1:1080

Notez que l'adresse 10.0.0.2 n'est pas une faute de frappe. Elle spécifie l'adresse IP du routeur virtuel à l'intérieur du périphérique TUN, et doit être différente de l'adresse IP de l'interface TUN elle-même (mais dans le même sous-réseau).

Vous devriez maintenant être capable de pinger l'adresse IP du routeur virtuel (10.0.0.2) :

  ping -n 10.0.0.2

Tout ce qu'il reste à faire est de router les connexions via le périphérique TUN au lieu de la passerelle par défaut existante. Ceci est fait comme suit :

1. Ajoutez une route vers le serveur SSH via votre passerelle existante, avec une métrique inférieure à celle de la route par défaut originale.

2. Si vos serveurs DNS se trouvent dans un réseau qui n'est pas directement connecté (par exemple, sur Internet), ajoutez également des routes pour eux (comme pour le serveur SSH). Ceci est nécessaire car tun2socks ne transfère pas UDP par défaut (voir ci-dessous).

3. Ajoutez une route par défaut via le routeur virtuel dans le périphérique TUN, avec une métrique inférieure à celle de la route par défaut originale, mais supérieure à celles des routes SSH et DNS.

Cela fera en sorte que toutes les connexions externes passent par le périphérique TUN, à l'exception de la connexion SSH (sinon SSH passerait par le périphérique TUN, qui passerait par... SSH).

Par exemple (en supposant qu'il n'y ait pas de routes par défaut existantes avec une métrique <=6 ; sinon, supprimez-les ou modifiez leurs métriques) :

  route add <IP_du_serveur_SSH> gw <IP_de_la_passerelle_originale> metric 5
  <idem pour le DNS>
  route add default gw 10.0.0.2 metric 6

TRANSFERT UDP

tun2socks peut transférer des paquets UDP, cependant cela nécessite un démon de transfert, badvpn-udpgw, exécuté sur le serveur SSH distant :

  badvpn-udpgw --listen-addr 127.0.0.1:7300

Dites ensuite à tun2socks de transférer les paquets UDP via le forwarder :

  --udpgw-remote-server-addr 127.0.0.1:7300
