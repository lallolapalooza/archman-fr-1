Valider la structure de l'arbre de travail, la cohérence de la branche et l'historique du dépôt.

Cette commande vérifie diverses invariants concernant le stockage des branches et des dépôts pour détecter la corruption de données ou des bogues de brz.

Les vérifications de l'arbre de travail et de la branche ne donneront de sortie que si un problème est détecté. Les champs de sortie de la vérification du dépôt sont :

revisions
C'est simplement le nombre de révisions vérifiées. Cela n'indique
pas un problème.

versionedfiles
C'est simplement le nombre de fichiers versionnés vérifiés. Cela
n'indique pas un problème.

unreferenced ancestors
Textes qui sont des ancêtres d'autres textes, mais
ne sont pas correctement référencés par l'ascendance de la révision. C'est un
problème subtil que Breezy peut contourner.

unique file texts
C'est le nombre total de contenus de fichiers uniques
vus dans les révisions vérifiées. Cela n'indique pas un problème.

repeated file texts
C'est le nombre total de textes répétés vus
dans les révisions vérifiées. Les textes peuvent être répétés lorsque leurs entrées de fichier
sont modifiées, mais que le contenu du fichier ne l'est pas. Cela n'indique
pas un problème.

Si aucune restriction n'est spécifiée, toutes les données trouvées à l'emplacement donné seront vérifiées.

brz check --repo bar


Vérifier tout à 'baz' :

Effectue une fusion à trois voies.

La source de la fusion peut être spécifiée soit sous forme de branche, soit sous forme de chemin vers un fichier contenant une directive de fusion générée avec brz send. Si aucun n'est spécifié, le défaut est la branche en amont ou la branche la plus récemment fusionnée en utilisant --remember. La source de la fusion peut également être spécifiée sous forme de chemin vers un fichier dans une autre branche : dans ce cas, seules les modifications apportées à ce fichier sont fusionnées dans l'arbre de travail actuel.

Lors de la fusion depuis une branche, par défaut, brz essaiera de fusionner tous les nouveaux travaux de l'autre branche, en déterminant automatiquement une révision de base appropriée. Si cela échoue, vous pourriez avoir besoin de spécifier une base explicite.

Pour choisir une autre révision de fin, passez "--revision OTHER". brz essaiera de fusionner tous les nouveaux travaux jusqu'à la révision OTHER incluse.

Si vous spécifiez deux valeurs, "--revision BASE..OTHER", seules les révisions de BASE à OTHER, excluant BASE mais incluant OTHER, seront fusionnées. Si cela entraîne le saut de certaines révisions, c'est-à-dire si la branche de destination ne contient pas déjà la révision BASE, une telle fusion est communément appelée un "cherrypick". Contrairement à une fusion normale, Breezy ne suit pas actuellement les cherrypicks. Les modifications ressemblent à une validation normale, et l'historique des modifications de l'autre branche n'est pas stocké dans la validation.

Les numéros de révision sont toujours relatifs à la branche source.

Merge fera de son mieux pour combiner les modifications de deux branches, mais il existe certains types de problèmes qu'un humain seul peut résoudre. Lorsqu'il rencontre ces problèmes, il marquera un conflit. Un conflit signifie que vous devez corriger quelque chose avant de pouvoir valider.

Utilisez brz resolve lorsque vous avez corrigé un problème. Voir aussi brz conflicts.

S'il n'y a pas de branche par défaut définie, la première fusion la définira (utilisez --no-remember pour éviter de la définir). Après cela, vous pouvez omettre la branche pour utiliser la branche par défaut. Pour changer la branche par défaut, utilisez --remember. La valeur ne sera enregistrée que si l'emplacement distant est accessible.

Les résultats de la fusion sont placés dans le répertoire de travail de destination, où ils peuvent être examinés (avec brz diff), testés, puis validés pour enregistrer le résultat de la fusion.

merge refuse de s'exécuter s'il y a des modifications non validées, sauf si --force est donné. Si --force est donné, alors les modifications de la source seront fusionnées avec l'arbre de travail actuel, y compris toute modification non validée dans l'arbre. L'option --force peut également être utilisée pour créer une révision de fusion qui a plus de deux parents.

Si l'on souhaite fusionner des modifications de l'arbre de travail de l'autre branche sans fusionner de révisions validées, l'option --uncommitted peut être donnée.

Pour sélectionner uniquement certaines modifications à fusionner, utilisez "merge -i", ce qui vous invitera à appliquer chaque groupe de différences et modification de fichier, similaire à "shelve".

Exemples :
Pour fusionner toutes les nouvelles révisions de brz.dev :


brz merge ../brz.dev


Pour fusionner les modifications jusqu'à et y compris la révision 82
de brz.dev :


brz merge -r 82 ../brz.dev


Pour fusionner les modifications introduites par 82, sans les
modifications précédentes :


brz merge -r 81..82 ../brz.dev


Pour appliquer une directive de fusion contenue dans /tmp/merge :


brz merge /tmp/merge


Pour créer une révision de fusion avec trois parents à partir des deux
branches feature1a et feature1b :


brz merge ../feature1a
brz merge ../feature1b --force
brz commit -m 'révision avec trois parents'

Donner une liste de fichiers ne rétablira que ces fichiers. Sinon, tous les fichiers seront rétablis. Si la révision n'est pas spécifiée avec '--revision', la révision de base de l'arbre de travail est utilisée. Une opération revert n'affecte que l'arbre de travail, pas l'historique des révisions comme la branche et le dépôt ou la révision de base de l'arbre de travail.

Pour supprimer seulement certains changements, sans rétablir une version antérieure, utilisez merge à la place. Par exemple, "merge . -r -2..-3" (n'oubliez pas le ".") supprimera les changements introduits par l'avant-dernier commit (-2), sans affecter les changements introduits par le dernier commit (-1). Pour supprimer certains changements morceau par morceau, voir la commande shelve. (Les fichiers modifiés uniquement par merge ne sont pas sauvegardés.) Les fichiers de sauvegarde ont '.~#~' ajouté à leur nom, où # est un nombre.

Lorsque vous fournissez des fichiers, vous pouvez utiliser leur chemin actuel ou le chemin de la révision cible. Vous pouvez donc utiliser revert pour "supprimer" la suppression d'un fichier par son nom. Si vous nommez un répertoire, tout le contenu de ce répertoire sera rétabli.

Si vous avez ajouté de nouveaux fichiers depuis la révision cible, ils seront supprimés. Si les fichiers à supprimer ont été modifiés, des sauvegardes seront créées comme ci-dessus. Les répertoires contenant des fichiers inconnus ne seront pas supprimés.

L'arbre de travail contient une liste de révisionsqui ont été fusionnées mais pas encore validées. Ces révisions seront incluses comme parents supplémentaires du prochain commit. Normalement, utiliser revert efface également cette liste et annule les fichiers. Si des fichiers sont spécifiés, revert laisse la liste des fusions non validées intacte et ne fait que rétablir les fichiers. Utilisez `brz revert` dans la racine de l'arbre pour rétablir tous les fichiers mais conserver les fusions enregistrées, et `brz revert --forget-merges` pour effacer la liste des fusions en attente sans rétablir aucun fichier.

En utilisant « brz revert --forget-merges », il est possible d'appliquer tous les changements d'une branche en une seule révision. Pour ce faire, effectuez la fusion comme désiré. Ensuite, utiliser revert avec l'option « --forget-merges » conservera le contenu de l'arbre tel qu'il était, mais effacera la liste des fusions en attente. Le prochain commit contiendra alors tous les changements présents dans l'autre branche, mais sans aucune autre révision parente. Comme cette technique oublie l'origine de ces changements, elle peut entraîner des conflits supplémentaires lors des fusions ultérieures impliquant les mêmes branches source et cible.

Envoie par e-mail ou crée une directive de fusion pour soumettre des changements.

Une directive de fusion fournit de nombreux éléments nécessaires pour demander des fusions :

* Une description lisible par machine de la fusion à effectuer

* Un patch optionnel qui est une prévisualisation des changements demandés

* Un bundle optionnel de données de révision, afin que les changements puissent être appliqués
directement depuis la directive de fusion, sans récupérer de données d'une
branche.

`brz send` crée un ensemble de données compact qui, lorsqu'il est appliqué à l'aide de brz merge, a le même effet que la fusion à partir de la branche source.

Par défaut, la directive de fusion est autonome et peut être appliquée à n'importe quelle branche contenant submit_branch dans son ascendance, sans nécessiter d'accès à la branche source.

Si --no-bundle est spécifié, Breezy n'envoie pas le contenu des révisions, mais seulement une requête structurée pour fusionner depuis l'emplacement public. Dans ce cas, la branche publique est nécessaire et elle doit être à jour et accessible au destinataire. La branche publique est toujours incluse si elle est connue, afin que les gens puissent la vérifier ultérieurement.

La branche de soumission par défaut est le parent de la branche source, mais peut être remplacée. La branche de soumission et la branche publique seront mémorisées dans branch.conf la première fois qu'elles seront utilisées pour une branche particulière. La branche source par défaut est celle contenant le répertoire de travail, mais peut être changée en utilisant --from.

La branche de soumission et la branche publique suivent le comportement habituel de --remember : S'il n'y a pas d'emplacement par défaut défini, la première opération send le définira (utilisez --no-remember pour éviter de le définir). Après cela, vous pouvez omettre l'emplacement pour utiliser le défaut. Pour changer le défaut, utilisez --remember. La valeur ne sera enregistrée que si l'emplacement peut être accédé.

Afin de calculer ces changements, brz doit analyser la branche de soumission. Il est donc plus efficace que la branche de soumission soit un miroir local. Si un emplacement public est connu pour la branche de soumission, cet emplacement est utilisé dans la directive de fusion.

Pour utiliser un programme de messagerie spécifique, définissez l'option de configuration mail_client. Les valeurs prises en charge pour les clients spécifiques sont « claws », « evolution », « kmail », « mail.app » (Mail.app de MacOS X), « mutt » et « thunderbird » ; les options génériques sont « default », « editor », « emacsclient », « mapi » et « xdg-email ». NOM

brz - Interface de ligne de commande pour le système de contrôle de version Breezy

SYNOPIS

brz [OPTIONS] COMMANDE [ARGUMENTS...]

DESCRIPTION

L'outil en ligne de commande brz est le programme principal pour interagir avec le système de contrôle de version Breezy. Il peut être utilisé pour une variété de tâches, y compris la gestion des dépôts, le suivi des modifications, la collaboration et la gestion des versions.

La commande brz peut être utilisée avec de nombreuses sous-commandes, chacune avec son propre ensemble d'options et d'arguments. L'aide générale peut être obtenue avec brz --help, et l'aide pour une commande spécifique avec brz commande --help.

APERÇU DES COMMANDES

RÉFÉRENCE DES COMMANDES

brz view

La commande brz view permet de gérer les vues du dépôt. Une vue permet de suivre un ensemble spécifique de fichiers ou de répertoires au sein d'un dépôt. Cela peut être utile pour gérer différents états de travail ou pour se concentrer sur des parties spécifiques d'un grand projet.

Options:

Désactiver la vue actuelle sans la supprimer.
--delete
Supprimer la vue actuelle ou spécifiée.
--name ARG
Spécifie un nom pour la vue. Si non spécifié, fait référence à la vue actuelle.
--all
Appliquer l'opération à toutes les vues définies.
--switch ARG
Basculer vers la vue nommée spécifiée.
--help, -h
Afficher le message d'aide.
--usage

--quiet, -q
Afficher uniquement les erreurs et les avertissements.
--verbose, -v

brz view fichier1 repertoire1 ...


Pour lister la vue actuelle:


brz view

brz view --delete

brz view --switch off
