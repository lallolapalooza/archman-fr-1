BIO_should_retry(3ssl)

Paquet: openssl

Licences: Apache-2.0

BIO_SHOULD_RETRY(3ssl) OpenSSL BIO_SHOULD_RETRY(3ssl)

NOM

BIO_should_read, BIO_should_write, BIO_should_io_special, BIO_retry_type, BIO_should_retry, BIO_get_retry_BIO, BIO_get_retry_reason, BIO_set_retry_reason - Fonctions de réessai de BIO

SYNOPSIS

#include <openssl/bio.h>
int BIO_should_read(BIO *b);
int BIO_should_write(BIO *b);
int BIO_should_io_special(iBIO *b);
int BIO_retry_type(BIO *b);
int BIO_should_retry(BIO *b);
BIO *BIO_get_retry_BIO(BIO *bio, int *reason);
int BIO_get_retry_reason(BIO *bio);
void BIO_set_retry_reason(BIO *bio, int reason);

DESCRIPTION

Ces fonctions déterminent pourquoi un BIO n'est pas en mesure de lire ou d'écrire des données. Elles sont généralement appelées après un échec de l'appel BIO_read_ex() ou BIO_write_ex() .

BIO_should_retry() est vrai si l'appel qui a produit cette condition doit être réessayé ultérieurement.

Si BIO_should_retry() est faux, alors la cause est une condition d'erreur.

BIO_should_read() est vrai si la cause de la condition est que le BIO n'a pas suffisamment de données à renvoyer. Vérifiez la lisibilité et/ou réessayez la dernière opération.

BIO_should_write() est vrai si la cause de la condition est que le BIO a des données en attente d'écriture. Vérifiez l'écriture et/ou réessayez la dernière opération.

BIO_should_io_special() est vrai si une condition « spéciale », c'est-à-dire une raison autre que la lecture ou l'écriture, est la cause de la condition.

BIO_retry_type() renvoie un masque de la cause d'une condition de réessai composé des valeurs BIO_FLAGS_READ, BIO_FLAGS_WRITE, BIO_FLAGS_IO_SPECIAL bien que les types de BIO actuels ne définissent qu'une seule de ces valeurs.

BIO_get_retry_BIO() détermine la raison précise de la condition spéciale, il renvoie le BIO qui a causé cette condition et si reason n'est pas NULL, il contient le code de raison. La signification du code de raison et l'action à entreprendre dépendent du type de BIO qui a entraîné cette condition.

BIO_get_retry_reason() renvoie la raison d'une condition spéciale si on lui passe le BIO pertinent, par exemple celui renvoyé par BIO_get_retry_BIO().

BIO_set_retry_reason() définit la raison de réessai d'une condition spéciale pour un BIO donné. Cela ne serait généralement appelé que par les implémentations de BIO.

NOTES

BIO_should_read(), BIO_should_write(), BIO_should_io_special(), BIO_retry_type(), et BIO_should_retry()sont implémentés comme des macros.

Si BIO_should_retry() renvoie faux, la « condition d'erreur » précise dépend du type de BIO qui l'a causée et du code de retour de l'opération BIO. Par exemple, si un appel à BIO_read_ex() sur un BIO socket renvoie 0 et que BIO_should_retry() est faux, la cause sera que la connexion a été fermée. Une condition similaire sur un BIO fichier signifiera qu'il a atteint l'EOF. Certains types de BIO peuvent placer des informations supplémentaires sur la file d'erreurs. Pour plus de détails, consultez les pages manuelles des types de BIO individuels.

Si la structure d'E/S sous-jacente est en mode bloquant, presque tous les types de BIO actuels ne demanderont pas de réessai, car les appels d'E/S sous-jacents ne le feront pas. Si l'application sait que le type de BIO ne signalera jamais de réessai, elle n'a pas besoin d'appeler BIO_should_retry() après un appel d'E/S BIO échoué. Cela se fait généralement avec les BIO fichier.

Les BIO SSL sont la seule exception actuelle à cette règle : ils peuvent demander un réessai même si la structure d'E/S sous-jacente est bloquante, si une négociation (handshake) se produit lors d'un appel à BIO_read(). Une application peut réessayer l'appel échoué immédiatement ou éviter cette situation en définissant SSL_MODE_AUTO_RETRY sur la structure SSL sous-jacente.

Bien qu'une application puisse réessayer immédiatement un appel non bloquant échoué, cela est probablement très inefficace car l'appel échouera à plusieurs reprises jusqu'à ce que les données puissent être traitées ou soient disponibles. Une application attendra normalement que la condition nécessaire soit satisfaite. La manière dont cela se fait dépend de la structure d'E/S sous-jacente.

Par exemple, si la cause est ultimement un socket et que BIO_should_read() est vrai, un appel à select() peut être fait pour attendre que les données soient disponibles, puis réessayer l'opération BIO. En combinant les conditions de réessai de plusieurs BIO non bloquants dans un seul appel select() , il est possible de servir plusieurs BIO dans un seul thread, bien que les performances peuvent être mauvaises si des BIO SSL sont présents car de longs délais peuvent survenir lors du processus de négociation initial.

Il est possible qu'un BIO se bloque indéfiniment si la structure d'E/S sous-jacente ne peut pas traiter ou renvoyer de données. Cela dépend du comportement des fonctions d'E/S de la plateforme. C'est souvent indésirable : une solution est d'utiliser des E/S non bloquantes et d'utiliser un délai d'attente sur l'appel select() (ou équivalent).

BUGS

Les fonctions ASN1 d'OpenSSL ne peuvent pas gérer élégamment les E/S non bloquantes : elles ne peuvent pas réessayer après une lecture ou une écriture partielle. Cela est généralement contourné en ne passant les données pertinentes aux fonctions ASN1 que lorsque la structure entière peut être lue ou écrite.

VALEURS RENVOYÉES

BIO_should_read(), BIO_should_write(), BIO_should_io_special(), et BIO_should_retry() renvoient soit 1 soit 0 en fonction des conditions réelles du BIO.

BIO_retry_type() renvoie une combinaison de drapeaux présentant la cause d'une condition de réessai ou faux s'il n'y a pas de condition de réessai.

BIO_get_retry_BIO() renvoie une structure BIO valide.

BIO_get_retry_reason() renvoie la raison d'une condition spéciale.
