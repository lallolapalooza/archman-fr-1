NOM

bgerror - Commande appelée pour traiter les erreurs en arrière-plan

SYNOPSIS

bgerror message

DESCRIPTION

La version 8.5 de Tcl prend en charge la commande interp bgerror, qui permet aux applications d'enregistrer dans un interpréteur la commande qui gérera les erreurs en arrière-plan dans cet interpréteur. Dans les versions antérieures de Tcl, ce niveau de contrôle n'était pas disponible, et les applications ne pouvaient contrôler la gestion des erreurs en arrière-plan qu'en créant une commande portant le nom spécifique bgerror dans l'espace de noms global d'un interpréteur. La documentation suivante décrit les exigences de l'interface de la commande bgerror qu'une application pourrait définir pour conserver la compatibilité avec les versions de Tcl antérieures à la 8.5. Les applications qui ont l'intention de ne prendre en charge que les versions de Tcl 8.5 et ultérieures devraient simplement utiliser interp bgerror.

La commande bgerror n'existe pas en tant que partie intégrante de Tcl. Au lieu de cela, les applications individuelles ou les utilisateurs peuvent définir une commande bgerror (par exemple, comme une procédure Tcl) s'ils souhaitent gérer les erreurs en arrière-plan.

Une erreur en arrière-plan est une erreur qui se produit dans un gestionnaire d'événements ou une autre commande qui n'est pas originaire de l'application. Par exemple, si une erreur se produit lors de l'exécution d'une commande spécifiée avec la commande after, il s'agit d'une erreur en arrière-plan. Pour une erreur non en arrière-plan, l'erreur peut simplement être renvoyée par les évaluations de commandes Tcl imbriquées jusqu'à ce qu'elle atteigne le code de niveau supérieur dans l'application ; l'application peut alors signaler l'erreur de la manière qu'elle souhaite. Lorsqu'une erreur en arrière-plan se produit, le déroulement se termine dans la bibliothèque Tcl et il n'y a aucun moyen évident pour Tcl de signaler l'erreur.

Lorsque Tcl détecte une erreur en arrière-plan, il enregistre des informations sur l'erreur et appelle une commande de gestionnaire enregistrée par interp bgerror plus tard en tant que gestionnaire d'événements inactif. La commande de gestionnaire par défaut appelle à son tour la commande bgerror. Avant d'invoquer bgerror, Tcl restaure les variables errorInfo et errorCode à leurs valeurs au moment où l'erreur s'est produite, puis il appelle bgerror avec le message d'erreur comme seul argument. Tcl suppose que l'application a implémenté la commande bgerror, et que la commande signalera l'erreur d'une manière qui ait du sens pour l'application. Tcl ignorera tout résultat renvoyé par la commande bgerror tant qu'aucune erreur n'est générée.

Si une autre erreur Tcl se produit dans la commande bgerror (par exemple, parce qu'aucune commande bgerror n'a été définie), Tcl signale l'erreur elle-même en écrivant un message sur stderr.

Si plusieurs erreurs en arrière-plan s'accumulent avant que bgerror ne soit appelée pour les traiter, bgerror sera appelée une fois pour chaque erreur, dans l'ordre où elles se sont produites. Cependant, si bgerror renvoie avec une exception de rupture, toutes les erreurs restantes sont ignorées sans appeler bgerror.

Si vous écrivez du code qui sera utilisé par d'autres dans le cadre d'un package ou d'un autre type de bibliothèque, envisagez d'éviter bgerror. La raison en est que le programmeur de l'application peut également souhaiter définir un bgerror, ou utiliser un autre code qui le fait et aura donc du mal à intégrer votre code.

EXEMPLE

Cette procédure bgerror ajoute les erreurs à un fichier, avec un horodatage.

proc bgerror {message} {
    set timestamp [clock format [clock seconds]]
    set fl [open mylog.txt {WRONLY CREAT APPEND}]
    puts $fl "$timestamp: bgerror dans $::argv '$message'"
    close $fl
}
