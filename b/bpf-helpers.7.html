NOM

BPF-HELPERS - liste des fonctions d'assistance eBPF

DESCRIPTION

Le sous-système extended Berkeley Packet Filter (eBPF) se compose de programmes écrits dans un langage pseudo-assembleur, puis attachés à l'un des nombreux points d'ancrage du noyau et exécutés en réaction à des événements spécifiques. Ce cadre diffère du BPF « classique » (ou « cBPF ») plus ancien à plusieurs égards, dont la capacité à appeler des fonctions spéciales (ou « helpers ») depuis un programme. Ces fonctions sont restreintes à une liste blanche de helpers définie dans le noyau.

Ces helpers sont utilisés par les programmes eBPF pour interagir avec le système, ou avec le contexte dans lequel ils fonctionnent. Par exemple, ils peuvent être utilisés pour imprimer des messages de débogage, pour obtenir le temps écoulé depuis le démarrage du système, pour interagir avec les maps eBPF, ou pour manipuler des paquets réseau. Comme il existe plusieurs types de programmes eBPF, et qu'ils ne s'exécutent pas dans le même contexte, chaque type de programme ne peut appeler qu'un sous-ensemble de ces helpers.

En raison des conventions eBPF, un helper ne peut pas avoir plus de cinq arguments.

En interne, les programmes eBPF appellent directement les fonctions d'assistance compilées sans nécessiter d'interface de fonctions étrangères. Par conséquent, l'appel de helpers n'introduit aucun surcoût, offrant ainsi d'excellentes performances.

Ce document tente de lister et de documenter les helpers disponibles pour les développeurs eBPF. Ils sont triés par ordre chronologique (les helpers les plus anciens dans le noyau en haut).

long bpf_trace_printk(const char *fmt, u32 fmt_size, ...)
Description
Ce helper est une fonctionnalité de type « printk() » pour le débogage. Il imprime un message défini par le format fmt (de taille fmt_size) dans le fichier /sys/kernel/tracing/trace de TraceFS, si disponible. Il peut prendre jusqu'à trois arguments supplémentaires u64 (en tant que helper eBPF, le nombre total d'arguments est limité à cinq).

Chaque fois que le helper est appelé, il ajoute une ligne à la trace. Les lignes sont jetées tant que /sys/kernel/tracing/trace est ouvert, utilisez /sys/kernel/tracing/trace_pipe pour éviter cela. Le format de la trace est personnalisable, et la sortie exacte dépend des options définies dans /sys/kernel/tracing/trace_options (voir aussi le fichier README dans le même répertoire). Cependant, elle est généralement définie par défaut sur quelque chose comme :

telnet-470   [001] .N.. 419421.045894: 0x00000001: <formatted msg>

Dans l'exemple ci-dessus :

  • telnet est le nom de la tâche courante.
  • 470 est le PID de la tâche courante.
  • 001 est le numéro du CPU sur lequel la tâche s'exécute.
  • Dans .N.., chaque caractère fait référence à un ensemble d'options (si les IRQ sont activées, options d'ordonnancement, si des IRQ matérielles/logicielles sont en cours d'exécution, niveau de preempt_disabled respectivement). N signifie que TIF_NEED_RESCHED et PREEMPT_NEED_RESCHED sont définis.
  • 419421.045894 est un horodatage.
  • 0x00000001 est une valeur fictive utilisée par BPF pour le registre du pointeur d'instruction.
  • <formatted msg> est le message formaté avec fmt.

Les spécificateurs de conversion pris en charge par fmt sont similaires, mais plus limités que pour printk(). Ils sont %d, %i, %u, %x, %ld, %li, %lu, %lx, %lld, %lli, %llu, %llx, %p, %s. Aucun modificateur (taille du champ, remplissage par des zéros, etc.) n'est disponible, et le helper renverra -EINVAL (mais n'imprimera rien) s'il rencontre un spécificateur inconnu.

De plus, notez que bpf_trace_printk() est lent et ne doit être utilisé qu'à des fins de débogage. Pour cette raison, un bloc de notification (s'étendant sur plusieurs lignes) est imprimé dans les journaux du noyau et indique que le helper ne doit pas être utilisé « en production » la première fois que ce helper est utilisé (ou plus précisément, lorsque les tampons trace_printk() sont alloués). Pour transmettre des valeurs à l'espace utilisateur, les événements perf sont préférables.

Retour
Le nombre d'octets écrits dans le tampon, ou une erreur négative en cas d'échec.

long bpf_l3_csum_replace(struct sk_buff *skb, u32 offset, u64 from, u64 to, u64 size)
Description
Recalculer la somme de contrôle de couche 3 (par exemple, IP) pour le paquet associé à skb. Le calcul est incrémental, de sorte que la fonction utilitaire doit connaître la valeur précédente du champ d'en-tête qui a été modifié (from), la nouvelle valeur de ce champ (to), et le nombre d'octets (2 ou 4) pour ce champ, stocké dans size. Alternativement, il est possible de stocker la différence entre la valeur précédente et la nouvelle valeur du champ d'en-tête dans to, en mettant from et size à 0. Pour les deux méthodes, offset indique l'emplacement de la somme de contrôle IP dans le paquet.

Cette fonction utilitaire fonctionne en combinaison avec bpf_csum_diff(), qui ne met pas à jour la somme de contrôle sur place, mais offre plus de flexibilité et peut gérer des tailles supérieures à 2 ou 4 pour la somme de contrôle à mettre à jour.

Un appel à cette fonction utilitaire est susceptible de modifier le tampon de paquet sous-jacent. Par conséquent, au moment du chargement, toutes les vérifications sur les pointeurs précédemment effectuées par le vérificateur sont invalidées et doivent être effectuées à nouveau, si la fonction utilitaire est utilisée en combinaison avec un accès direct au paquet.

Return
0 en cas de succès, ou une erreur négative en cas d'échec.
long bpf_l4_csum_replace(struct sk_buff *skb, u32 offset, u64 from, u64 to, u64 flags)
Description
Recalculer la somme de contrôle de couche 4 (par exemple, TCP, UDP ou ICMP) pour le paquet associé à skb. Le calcul est incrémental, de sorte que la fonction utilitaire doit connaître la valeur précédente du champ d'en-tête qui a été modifié (from), la nouvelle valeur de ce champ (to), et le nombre d'octets (2 ou 4) pour ce champ, stocké dans les quatre bits les plus bas de flags. Alternativement, il est possible de stocker la différence entre la valeur précédente et la nouvelle valeur du champ d'en-tête dans to, en mettant from et les quatre bits les plus bas de flags à 0. Pour les deux méthodes, offset indique l'emplacement de la somme de contrôle IP dans le paquet. En plus de la taille du champ, flags peut être ajouté (OU bit à bit) aux drapeaux réels. Avec BPF_F_MARK_MANGLED_0, une somme de contrôle nulle est laissée intacte (sauf si BPF_F_MARK_ENFORCE est également ajouté), et pour les mises à jour résultant en une somme de contrôle nulle, la valeur est définie sur CSUM_MANGLED_0 à la place. Le drapeau BPF_F_PSEUDO_HDR indique que le champ d'en-tête modifié fait partie de l'en-tête pseudo. Le drapeau BPF_F_IPV6 doit être défini pour les paquets IPv6.

Cette fonction utilitaire fonctionne en combinaison avec bpf_csum_diff(), qui ne met pas à jour la somme de contrôle sur place, mais offre plus de flexibilité et peut gérer des tailles supérieures à 2 ou 4 pour la somme de contrôle à mettre à jour.

Un appel à cette fonction utilitaire est susceptible de modifier le tampon de paquet sous-jacent. Par conséquent, au moment du chargement, toutes les vérifications sur les pointeurs précédemment effectuées par le vérificateur sont invalidées et doivent être effectuées à nouveau, si la fonction utilitaire est utilisée en combinaison avec un accès direct au paquet.

Return
0 en cas de succès, ou une erreur négative en cas d'échec.
long bpf_tail_call(void *ctx, struct bpf_map *prog_array_map, u32 index)
Description
Cette fonction utilitaire spéciale est utilisée pour déclencher un "tail call", ou en d'autres termes, pour sauter vers un autre programme eBPF. Le même cadre de pile est utilisé (mais les valeurs sur la pile et dans les registres de l'appelant ne sont pas accessibles à l'appelé). Ce mécanisme permet d'enchaîner les programmes, soit pour augmenter le nombre maximal d'instructions eBPF disponibles, soit pour exécuter des programmes donnés dans des blocs conditionnels. Pour des raisons de sécurité, il existe une limite supérieure au nombre de tail calls successifs qui peuvent être effectués.

Lors de l'appel à cette fonction utilitaire, le programme tente de sauter vers un programme référencé à l'index index dans prog_array_map, une carte spéciale de type BPF_MAP_TYPE_PROG_ARRAY, et passe ctx, un pointeur vers le contexte.

Si l'appel réussit, le noyau exécute immédiatement la première instruction du nouveau programme. Il ne s'agit pas d'un appel de fonction, et il ne revient jamais au programme précédent. Si l'appel échoue, la fonction utilitaire n'a aucun effet et l'appelant continue d'exécuter ses instructions suivantes. Un appel peut échouer si le programme de destination pour le saut n'existe pas (c'est-à-dire si index est supérieur au nombre d'entrées dans prog_array_map), ou si le nombre maximum de tail calls a été atteint pour cette chaîne de programmes. Cette limite est définie dans le noyau par la macro MAX_TAIL_CALL_CNT (non accessible à l'espace utilisateur), qui est actuellement définie à 33.

Return
0 en cas de succès, ou une erreur négative en cas d'échec.
long bpf_clone_redirect(struct sk_buff *skb, u32 ifindex, u64 flags)
Description
Duplique et redirige le paquet associé à skb vers un autre périphérique réseau d'index ifindex. Les interfaces entrantes et sortantes peuvent être utilisées pour la redirection. La valeur BPF_F_INGRESS dans flags est utilisée pour faire la distinction (le chemin entrant est sélectionné si le drapeau est présent, sinon le chemin sortant). C'est le seul drapeau pris en charge pour le moment.

Par rapport à la fonction utilitaire bpf_redirect(), bpf_clone_redirect() a le coût associé de duplication du tampon de paquet, mais cela peut être exécuté en dehors du programme eBPF. Inversement, bpf_redirect() est plus efficace, mais il est géré via un code d'action où la redirection se produit uniquement après le retour du programme eBPF.

Un appel à cette fonction utilitaire est susceptible de modifier le tampon de paquet sous-jacent. Par conséquent, au moment du chargement, toutes les vérifications sur les pointeurs précédemment effectuées par le vérificateur sont invalidées et doivent être effectuées à nouveau, si la fonction utilitaire est utilisée en combinaison avec un accès direct au paquet.

Return
0 en cas de succès, ou une erreur négative en cas d'échec. Une erreur positive indique une éventuelle perte ou congestion sur le périphérique cible. Les codes d'erreur positifs spécifiques ne sont pas définis.

u32 bpf_get_cgroup_classid(struct sk_buff *skb)
Description
Récupérer la classid pour la tâche courante, c'est-à-dire pour le cgroup net_cls auquel skb appartient.

Cet helper peut être utilisé sur le chemin de sortie (egress) TC, mais pas sur l'entrée (ingress).

Le cgroup net_cls fournit une interface pour étiqueter les paquets réseau sur la base d'un identifiant fourni par l'utilisateur pour tout le trafic provenant des tâches appartenant au cgroup concerné. Voir également la documentation du noyau correspondante, disponible dans les sources Linux dans le fichier Documentation/admin-guide/cgroup-v1/net_cls.rst.

Le noyau Linux a deux versions pour les cgroups : il y a les cgroups v1 et les cgroups v2. Les deux sont disponibles pour les utilisateurs, qui peuvent utiliser un mélange des deux, mais notez que le cgroup net_cls est réservé aux cgroup v1 uniquement. Cela le rend incompatible avec les programmes BPF exécutés sur les cgroups, qui est une fonctionnalité réservée aux cgroup v2 (un socket ne peut contenir des données que pour une seule version de cgroups à la fois).

Cet helper n'est disponible que si le noyau a été compilé avec l'option de configuration CONFIG_CGROUP_NET_CLASSID définie à "y" ou à "m".

Return
La classid, ou 0 pour la classid par défaut non configurée.

long bpf_skb_get_tunnel_key(struct sk_buff *skb, struct bpf_tunnel_key *key, u32 size, u64 flags)
Description
Obtenir les métadonnées du tunnel. Cet helper prend un pointeur key vers une struct bpf_tunnel_key vide de size, qui sera remplie avec les métadonnées du tunnel pour le paquet associé à skb. Les flags peuvent être définis à BPF_F_TUNINFO_IPV6, ce qui indique que le tunnel est basé sur le protocole IPv6 au lieu d'IPv4.

La struct bpf_tunnel_key est un objet qui généralise les paramètres principaux utilisés par divers protocoles de tunneling dans une seule struct. De cette façon, elle peut être utilisée pour prendre facilement une décision basée sur le contenu de l'en-tête d'encapsulation, « résumé » dans cette struct. En particulier, elle contient l'adresse IP de l'extrémité distante (IPv4 ou IPv6, selon le cas) dans key->remote_ipv4 ou key->remote_ipv6. De plus, cette struct expose le key->tunnel_id, qui est généralement associé à un VNI (Virtual Network Identifier), le rendant programmable avec l'helper bpf_skb_set_tunnel_key().

Imaginons que le code suivant fait partie d'un programme attaché à l'interface d'entrée TC, à une extrémité d'un tunnel GRE, et est censé filtrer tous les messages provenant d'extrémités distantes avec une adresse IPv4 autre que 10.0.0.1 :

int ret;
struct bpf_tunnel_key key = {};
ret = bpf_skb_get_tunnel_key(skb, &key, sizeof(key), 0);
if (ret < 0)
        return TC_ACT_SHOT;     // drop packet
if (key.remote_ipv4 != 0x0a000001)
        return TC_ACT_SHOT;     // drop packet
return TC_ACT_OK;               // accept packet

Cette interface peut également être utilisée avec tous les périphériques d'encapsulation qui peuvent fonctionner en mode « collect metadata » : au lieu d'avoir un périphérique réseau par configuration spécifique, le mode « collect metadata » n'exige qu'un seul périphérique où la configuration peut être extraite de cet helper.

Cela peut être utilisé avec divers tunnels tels que VXLan, Geneve, GRE ou IP in IP (IPIP).

Return
0 en cas de succès, ou une erreur négative en cas d'échec.
long bpf_skb_set_tunnel_key(struct sk_buff *skb, struct bpf_tunnel_key *key, u32 size, u64 flags)
Description
Remplir les métadonnées du tunnel pour le paquet associé à skb. Les métadonnées du tunnel sont définies au contenu de key, de size. Les flags peuvent être définis à une combinaison des valeurs suivantes :
BPF_F_TUNINFO_IPV6
Indiquer que le tunnel est basé sur le protocole IPv6 au lieu d'IPv4.
BPF_F_ZERO_CSUM_TX
Pour les paquets IPv4, ajouter un drapeau aux métadonnées du tunnel indiquant que le calcul de la somme de contrôle doit être ignoré et la somme de contrôle définie à zéro.
BPF_F_DONT_FRAGMENT
Ajouter un drapeau aux métadonnées du tunnel indiquant que le paquet ne doit pas être fragmenté.
BPF_F_SEQ_NUMBER
Ajouter un drapeau aux métadonnées du tunnel indiquant qu'un numéro de séquence doit être ajouté à l'en-tête du tunnel avant d'envoyer le paquet. Ce drapeau a été ajouté pour l'encapsulation GRE, mais pourrait être utilisé avec d'autres protocoles à l'avenir.
BPF_F_NO_TUNNEL_KEY
Ajouter un drapeau aux métadonnées du tunnel indiquant qu'aucune clé de tunnel ne doit être définie dans l'en-tête de tunnel résultant.

Voici une utilisation typique sur le chemin de transmission :

struct bpf_tunnel_key key;
     populate key ...
bpf_skb_set_tunnel_key(skb, &key, sizeof(key), 0);
bpf_clone_redirect(skb, vxlan_dev_ifindex, 0);

Voir également la description de l'helper bpf_skb_get_tunnel_key() pour des informations supplémentaires.

Return
0 en cas de succès, ou une erreur négative en cas d'échec.
u64 bpf_perf_event_read(struct bpf_map *map, u64 flags)
Description
Lire la valeur d'un compteur d'événement perf. Cet helper repose sur une map de type BPF_MAP_TYPE_PERF_EVENT_ARRAY. La nature du compteur d'événement perf est sélectionnée lorsque map est mise à jour avec les descripteurs de fichier d'événement perf. La map est un tableau dont la taille est le nombre de CPU disponibles, et chaque cellule contient une valeur relative à un CPU. La valeur à récupérer est indiquée par flags, qui contient l'index du CPU à rechercher, masqué avec BPF_F_INDEX_MASK. Alternativement, flags peut être défini à BPF_F_CURRENT_CPU pour indiquer que la valeur pour le CPU courant doit être récupérée.

Notez qu'avant Linux 4.13, seuls les événements perf matériels peuvent être récupérés.

De plus, sachez que le helper plus récent bpf_perf_event_read_value() est recommandé par rapport à bpf_perf_event_read() en général. Ce dernier a quelques particularités d'ABI où l'erreur et la valeur du compteur sont utilisées comme code de retour (ce qui est incorrect car les plages peuvent se chevaucher). Ce problème est corrigé avec bpf_perf_event_read_value(), qui fournit en même temps plus de fonctionnalités par rapport à l'interface bpf_perf_event_read(). Veuillez vous référer à la description de bpf_perf_event_read_value() pour plus de détails.

Return
La valeur du compteur d'événement perf lue depuis la map, ou un code d'erreur négatif en cas d'échec.
long bpf_redirect(u32 ifindex, u64 flags)
Description
Redirige le paquet vers un autre périphérique réseau d'indice ifindex. Cette fonction d'aide est quelque peu similaire à bpf_clone_redirect(), sauf que le paquet n'est pas cloné, ce qui améliore les performances.

À l'exception de XDP, les interfaces d'entrée et de sortie peuvent être utilisées pour la redirection. La valeur BPF_F_INGRESS dans flags est utilisée pour faire la distinction (le chemin d'entrée est sélectionné si le drapeau est présent, le chemin de sortie sinon). Actuellement, XDP ne prend en charge que la redirection vers l'interface de sortie et n'accepte aucun drapeau.

Le même effet peut également être obtenu avec la fonction plus générique bpf_redirect_map(), qui utilise une carte BPF pour stocker la cible de redirection au lieu de la fournir directement à la fonction d'aide.

Retour
Pour XDP, la fonction d'aide retourne XDP_REDIRECT en cas de succès ou XDP_ABORTED en cas d'erreur. Pour les autres types de programmes, les valeurs sont TC_ACT_REDIRECT en cas de succès ou TC_ACT_SHOT en cas d'erreur.
u32 bpf_get_route_realm(struct sk_buff *skb)
Description
Récupère le domaine ou la route, c'est-à-dire le champ tclassid de la destination pour le paquet skb. Description

La nature du compteur d'événements perf est sélectionnée lorsque la map est mise à jour avec des descripteurs de fichiers d'événements perf. Cette aide se comporte de manière similaire à l'aide bpf_perf_event_read(), sauf qu'au lieu de simplement renvoyer la valeur observée, elle remplit la structure buf. Cela permet de récupérer des données supplémentaires : notamment, les temps activé et en cours d'exécution (dans buf->enabled et buf->running, respectivement) sont copiés. En général, bpf_perf_event_read_value() est recommandée plutôt que bpf_perf_event_read(), qui présente certains problèmes d'ABI et offre moins de fonctionnalités.

Ces valeurs sont intéressantes, car les compteurs matériels PMU (Performance Monitoring Unit) sont des ressources limitées. Lorsqu'il y a plus d'événements perf basés sur PMU ouverts que de compteurs disponibles, le noyau multiplexera ces événements afin que chaque événement obtienne un certain pourcentage (mais pas la totalité) du temps PMU. Dans le cas où le multiplexage se produit, le nombre d'échantillons ou la valeur du compteur ne reflèteront pas la situation par rapport à l'absence de multiplexage. Cela rend les comparaisons entre différentes exécutions difficiles. Typiquement, la valeur du compteur doit être normalisée avant d'être comparée à d'autres expériences. La normalisation habituelle est effectuée comme suit.

compteur_normalisé = compteur * t_activé / t_en_cours_exécution

Où t_activé est le temps d'activation de l'événement et t_en_cours_exécution est le temps d'exécution de l'événement depuis la dernière normalisation. Les temps d'activation et d'exécution sont accumulés depuis l'ouverture de l'événement perf. Pour obtenir un facteur d'échelle entre deux invocations d'un programme eBPF, les utilisateurs peuvent utiliser l'identifiant du CPU comme clé (ce qui est typique pour le modèle d'utilisation des tableaux perf) pour mémoriser la valeur précédente et effectuer le calcul à l'intérieur du programme eBPF.

Description
Acquérir un verrou tournant (spinlock) représenté par le pointeur lock, qui est stocké dans une valeur de map. Les verrous tournants dans les programmes BPF comportent un certain nombre de restrictions et de contraintes :

  • Les objets bpf_spin_lock ne sont autorisés que dans les maps de types BPF_MAP_TYPE_HASH et BPF_MAP_TYPE_ARRAY (cette liste pourrait être étendue à l'avenir).

  • Le programme BPF ne peut prendre qu'UN verrou à la fois, car en prendre deux ou plus pourrait provoquer des deadlocks.
  • Un seul struct bpf_spin_lock est autorisé par élément de map.
  • Lorsque le verrou est pris, les appels (soit BPF vers BPF, soit les helpers) ne sont pas autorisés.
  • Les instructions BPF_LD_ABS et BPF_LD_IND ne sont pas autorisées à l'intérieur d'une région protégée par un verrou tournant.

long bpf_check_mtu(void *ctx, u32 ifindex, u32 *mtu_len, s32 len_diff, u64 flags)
Description
Vérifie que la taille du paquet ne dépasse pas le MTU du périphérique réseau (basé sur ifindex). Cette fonction utilitaire sera probablement utilisée en combinaison avec des fonctions utilitaires qui ajustent/modifient la taille du paquet.

L'argument len_diff peut être utilisé pour interroger avec un changement de taille prévu. Cela permet de vérifier le MTU avant de modifier le contexte du paquet. Fournir un ajustement len_diff supérieur à la taille réelle du paquet (résultant en une taille de paquet négative) ne dépassera en principe pas le MTU, c'est pourquoi ce n'est pas considéré comme un échec. D'autres fonctions utilitaires BPF sont nécessaires pour effectuer le changement de taille prévu ; par conséquent, la responsabilité de la détection d'une taille de paquet négative incombe à ces fonctions utilitaires.

Spécifier ifindex zéro signifie que la vérification MTU est effectuée par rapport au périphérique réseau actuel. C'est pratique si cela n'est pas utilisé avant une redirection.

À l'entrée, mtu_len doit être un pointeur valide, sinon le vérificateur rejettera le programme BPF. Si la valeur mtu_len est initialisée à zéro, alors la taille du paquet de contexte est utilisée. Rappelez-vous que XDP et TC opèrent à L2, mais cette valeur est L3 car elle correspond aux valeurs MTU et IP-header tot_len qui sont L3 (comportement similaire à bpf_fib_lookup).

La table de routage du noyau Linux peut configurer des MTU à un niveau plus spécifique par route, ce qui n'est pas fourni par cette fonction utilitaire. Pour les vérifications MTU au niveau de la route, utilisez la fonction utilitaire bpf_fib_lookup().

ctx est soit struct xdp_md pour les programmes XDP, soit struct sk_buff pour les programmes tc cls_act.

long bpf_user_ringbuf_drain(struct bpf_map *map, void *callback_fn, void *ctx, u64 flags)
Description
Vide les échantillons du tampon circulaire utilisateur spécifié et invoque le rappel fourni pour chaque tel échantillon :

long (*callback_fn)(const struct bpf_dynptr *dynptr, void *ctx);

Si callback_fn renvoie 0, l'assistant continuera à essayer de vider l'échantillon suivant, jusqu'à un maximum de BPF_MAX_USER_RINGBUF_SAMPLES échantillons. Si la valeur de retour est 1, l'assistant ignorera le reste des échantillons et retournera. Les autres valeurs de retour ne sont pas utilisées actuellement et seront rejetées par le vérificateur.

Retour
Le nombre d'échantillons vidés si aucune erreur n'a été rencontrée lors du vidage des échantillons, ou 0 si aucun échantillon n'était présent dans le tampon circulaire. Si un producteur en espace utilisateur attendait via epoll sur cette map et qu'au moins un échantillon a été vidé, il recevra une notification d'événement l'informant de l'espace disponible dans le tampon circulaire. Si le drapeau BPF_RB_NO_WAKEUP est passé à cette fonction, aucune notification de réveil ne sera envoyée. Si le drapeau BPF_RB_FORCE_WAKEUP est passé, une notification de réveil sera envoyée même si aucun échantillon n'a été vidé.

En cas d'échec, la valeur renvoyée est l'une des suivantes :

-EBUSY si le tampon circulaire est contendu et qu'un autre contexte d'appel vidait simultanément le tampon circulaire.

-EINVAL si l'espace utilisateur ne suit pas correctement le tampon circulaire en raison d'une position de producteur non alignée sur 8 octets, d'un échantillon non aligné sur 8 octets, ou d'une position de producteur ne correspondant pas à la longueur annoncée d'un échantillon.

-E2BIG si l'espace utilisateur a tenté de publier un échantillon plus grand que la taille du tampon circulaire, our qui ne peut pas tenir dans une struct bpf_dynptr.

void *bpf_cgrp_storage_get(struct bpf_map *map, struct cgroup *cgroup, void *value, u64 flags)
Description
Récupère un bpf_local_storage à partir du cgroup.

Logiquement, cela peut être considéré comme l'obtention de la valeur à partir d'une map avec le cgroup comme clé. De ce point de vue, l'utilisation n'est pas très différente de bpf_map_lookup_elem(map, &cgroup) sauf que cet helper impose que la clé doit être une struct cgroup et que la map doit également être une BPF_MAP_TYPE_CGRP_STORAGE.

En réalité, la valeur du stockage local est intégrée directement dans l'objet cgroup lui-même, plutôt que d'être située dans la map BPF_MAP_TYPE_CGRP_STORAGE . Lorsque la valeur du stockage local est interrogée pour une map donnée sur un objet cgroup , le noyau effectuera une itération O(n) sur toutes les valeurs de stockage local actives pour cet objet cgroup jusqu'à ce que la valeur du stockage local pour la map soit trouvée.

Un flags optionnel (BPF_LOCAL_STORAGE_GET_F_CREATE) peut être utilisé afin qu'un nouveau bpf_local_storage soit créé s'il n'existe pas. value peut être utilisé avec BPF_LOCAL_STORAGE_GET_F_CREATE pour spécifier la valeur initiale d'un bpf_local_storage. Si value est NULL, le nouveau bpf_local_storage sera initialisé à zéro.

Return
Un pointeur bpf_local_storage est renvoyé en cas de succès.

NULL s'il est introuvable ou si une erreur s'est produite lors de l'ajout d'un nouveau bpf_local_storage.

Description

Return
0 en cas de succès.

-ENOENT si le bpf_local_storage est introuvable.

LICENSE

Les programmes eBPF peuvent avoir une licence associée, transmise avec les instructions de bytecode au noyau lorsque les programmes sont chargés. Le format de cette chaîne est identique à celui utilisé pour les modules du noyau (des licences doubles, telles que « Dual BSD/GPL », peuvent être utilisées). Certaines fonctions helper ne sont accessibles qu'aux programmes compatibles avec la GNU General Public License (GNU GPL).

Afin d'utiliser ces helpers, le programme eBPF doit être chargé avec la chaîne de licence correcte transmise (via attr) à l'appel système bpf() , ce qui se traduit généralement par une ligne similaire à la suivante dans le code source C du programme :

char ____license[] __attribute__((section("license"), used)) = "GPL";

IMPLEMENTATION

Cette page de manuel a pour but de documenter les fonctions helper eBPF existantes. Mais au moment de la rédaction, le sous-système BPF est en plein développement. De nouveaux types de programmes ou de maps eBPF sont ajoutés, ainsi que de nouvelles fonctions helper. Certains helpers sont occasionnellement rendus disponibles pour des types de programmes supplémentaires. Ainsi, malgré les efforts de la communauté, cette page pourrait ne pas être à jour. Si vous souhaitez vérifier par vous-même quelles fonctions helper existent dans votre noyau, ou quels types de programmes elles peuvent prendre en charge, voici quelques fichiers de l'arborescence du noyau qui pourraient vous intéresser :

  • include/uapi/linux/bpf.h est l'en-tête BPF principal. Il contient la liste complète de toutes les fonctions helper, ainsi que de nombreuses autres définitions BPF, y compris la plupart des drapeaux, structures ou constantes utilisés par les helpers.
  • net/core/filter.c contient la définition de la plupart des fonctions helper liées au réseau, et la liste des types de programmes à partir desquels elles peuvent être utilisées.
  • kernel/trace/bpf_trace.c est l'équivalent pour la plupart des helpers liés aux programmes de traçage.
  • kernel/bpf/verifier.c contient les fonctions utilisées pour vérifier que des types valides de maps eBPF sont utilisés avec une fonction helper donnée.
  • kernel/bpf/ le répertoire contient d'autres fichiers dans lesquels des helpers supplémentaires sont définis (pour les cgroups, les sockmaps, etc.).
  • L'utilitaire bpftool peut être utilisé pour sonder la disponibilité des fonctions helper sur le système (ainsi que les types de programmes et de maps pris en charge, et un certain nombre d'autres paramètres). Pour ce faire, exécutez bpftool feature probe (voir bpftool-feature(8) pour plus de détails). Ajoutez le unprivileged mot-clé pour lister les fonctionnalités disponibles pour les utilisateurs non privilégiés.

La compatibilité entre les fonctions helper et les types de programmes peut généralement être trouvée dans les fichiers où les fonctions helper sont définies. Recherchez les objets struct bpf_func_proto et les fonctions qui les renvoient : ces fonctions contiennent une liste des helpers qu'un type de programme donné peut appeler. Notez que l'étiquette default: du switch ... case utilisé pour filtrer les helpers peut appeler d'autres fonctions, qui permettent elles-mêmes l'accès à des helpers supplémentaires. L'exigence de licence GPL se trouve également dans ces struct bpf_func_proto.

La compatibilité entre les fonctions helper et les types de maps peut être trouvée dans la fonction check_map_func_compatibility() du fichier kernel/bpf/verifier.c.

Les fonctions helper qui invalident les vérifications sur les pointeurs data et data_end pour le traitement réseau sont listées dans la fonction bpf_helper_changes_pkt_data() du fichier net/core/filter.c.
