BTRFS peut avoir des profils différents sur un seul périphérique ou le même profil sur plusieurs périphériques.

La principale raison pour laquelle vous voudriez avoir des profils différents pour les données et les métadonnées est d'assurer une protection supplémentaire des métadonnées du système de fichiers en cas de défaillance des périphériques, car un seul secteur de métadonnées non récupérables peut corrompre le système de fichiers, alors qu'un seul secteur de données perdues peut être récupéré trivialement en supprimant le fichier corrompu.

Avant de changer de profil, assurez-vous qu'il y a suffisamment d'espace non alloué sur les disques existants pour créer de nouveaux groupes de blocs de métadonnées (pour les systèmes de fichiers de plus de 50 Gio, cela correspond à 1 Gio * (nombre_de_périphériques + 2)).

Les profils par défaut sur BTRFS sont :

  • données : single
métadonnées :
  • périphériques uniques : dup
  • périphériques multiples : raid1

Les types de filtres disponibles sont :

Types de filtres

profils=<profils>
Équilibre uniquement les groupes de blocs avec les profils donnés. Les paramètres sont une liste de noms de profils séparés par | (barre verticale).
utilisation=<pourcentage>, utilisation=<plage>
Équilibre uniquement les groupes de blocs dont l'utilisation est inférieure au pourcentage donné. La valeur 0 est autorisée et nettoiera les groupes de blocs complètement inutilisés, ce qui ne devrait pas nécessiter d'espace de travail supplémentaire. Vous pourriez vouloir utiliser utilisation=0 si l'équilibrage renvoie ENOSPC et que votre système de fichiers n'est pas trop plein.

L'argument peut être une valeur unique ou une plage. La valeur unique N signifie au plus N pour cent utilisés, équivalent à la syntaxe de plage ..N. Les noyaux antérieurs à 4.4 n'acceptent que le format de valeur unique. La limite inférieure de la plage est inclusive, la limite supérieure est exclusive.

périphériqueid=<id>
Équilibre uniquement les groupes de blocs qui ont au moins un bloc sur le périphérique donné. Pour lister les périphériques avec leurs ID, utilisez btrfs filesystem show.
plagedécalage=<plage>
Équilibre uniquement les groupes de blocs qui chevauchent la plage d'octets donnée sur n'importe quel périphérique. Utilisez-le en conjonction avec périphériqueid pour filtrer sur un périphérique spécifique. Le paramètre est une plage spécifiée sous la forme début..fin.
plagevirtuelle=<plage>
Équilibre uniquement les groupes de blocs qui chevauchent la plage d'octets donnée dans l'espace d'adressage virtuel interne du système de fichiers. C'est l'espace d'adressage que la plupart des rapports de btrfs dans les logs du noyau utilisent. Le paramètre est une plage spécifiée sous la forme début..fin.
convertir=<profil>
Convertit chaque groupe de blocs sélectionné au profil donné identifié par les paramètres.

Note :

À partir du noyau 4.5, les blocs de données peuvent être convertis vers/depuis le profil DUP sur un seul périphérique.

À partir du noyau 4.6, tous les profils peuvent être convertis vers/depuis DUP sur des systèmes de fichiers multi-périphériques.

Attention :

Les périphériques défectueux ou manquants ne sont pas immédiatement détectés pendant l'exécution et cela dépend d'événements ultérieurs tels qu'une écriture échouée ou une validation de transaction échouée. S'il existe un périphérique défaillant connu, ou un périphérique supprimé via l'interface /sys/block/<périphérique>/device/delete, le périphérique sera toujours accessible et écrit.

Dans un tel cas, il ne faut pas convertir vers un profil de redondance inférieure (par exemple, de RAID1 à SINGLE), car les tentatives de création de nouveaux blocs sur les nouveaux périphériques entraîneront divers problèmes.

L'action appropriée est d'utiliser btrfs replace ou btrfs device remove pour gérer le périphérique défaillant/manquant en premier. La conversion fonctionnera ensuite correctement avec tous les périphériques.

limiter=<nombre>, limiter=<plage>
Traite uniquement le nombre de blocs donné, après l'application de tous les filtres. Ceci peut être utilisé pour cibler spécifiquement un bloc en conjonction avec d'autres filtres (plagedécalage, plagevirtuelle) ou simplement pour limiter la quantité de travail effectuée par une seule exécution d'équilibrage.

L'argument peut être une valeur unique ou une plage. La valeur unique N signifie au plus N blocs, équivalent à la syntaxe de plage ..N. Les noyaux antérieurs à 4.4 n'acceptent que le format de valeur unique. Les limites inférieure et supérieure de la plage sont inclusives.

bandes=<plage>
Équilibre uniquement les groupes de blocs qui ont le nombre de bandes donné. Le paramètre est une plage spécifiée sous la forme début..fin. Pertinent pour les profils de groupes de blocs qui utilisent le striping, c'est-à-dire RAID0/10/5/6. Les limites inférieure et supérieure de la plage sont inclusives.
soft
Ne prend aucun paramètre. N'a de sens que lors de la conversion entre profils. Lorsque l'on convertit d'un profil à un autre et que le mode soft est activé, les blocs qui ont déjà le profil cible ne sont pas modifiés. Ceci est utile, par exemple, si la moitié du système de fichiers a été convertie précédemment mais a été annulée.

Le commutateur de mode soft est (comme tout autre filtre) par type. Par exemple, cela signifie que nous pouvons convertir les blocs de métadonnées de manière "dure" tout en convertissant les blocs de données sélectivement avec le commutateur soft.

Les noms de profils, utilisés dans profils et convertir sont parmi :

  • raid0
  • raid1
  • raid1c3
  • raid1c4
  • raid10
  • raid5
  • raid6
  • dup
  • single

Les profils mixtes données/métadonnées peuvent être convertis de la même manière, mais la conversion entre profils mixtes et non mixtes n'est pas implémentée. Pour les contraintes des profils, veuillez vous référer à mkfs.btrfs(8) <> section PROFILES <#man-mkfs-profiles>.

ENOSPC

La manière dont l'équilibrage fonctionne, il doit généralement créer temporairement un nouveau groupe de blocs et y déplacer les anciennes données avant que l'ancien groupe de blocs ne puisse être supprimé. Pour cela, il a besoin d'un espace de travail, sinon il échoue pour des raisons de ENOSPC. Ce n'est pas le même ENOSPC que si l'espace libre est épuisé. Ceci fait référence à l'espace au niveau des groupes de blocs, qui sont de grandes parties du système de fichiers contenant de nombreux extents de fichiers.

L'espace de travail libre peut être calculé à partir de la sortie de la commande btrfs filesystem show :

Label : 'BTRFS'  uuid : 8a9d72cd-ead3-469d-b371-9c7203276265
        Total devices 2 FS bytes used 77.03GiB
        devid    1 size 53.90GiB used 51.90GiB path /dev/sdc2
        devid    2 size 53.90GiB used 51.90GiB path /dev/sde1

size - used = espace de travail libre

53.90GiB - 51.90GiB = 2.00GiB

Un exemple de filtre qui ne nécessite pas d'espace de travail est utilisation=0. Cela parcourra tous les groupes de blocs inutilisés d'un type donné et récupérera l'espace. Après cela, il pourrait être possible d'exécuter d'autres filtres.

CONVERSIONS SUR PLUSIEURS PÉRIPHÉRIQUES

La conversion vers des profils basés sur le striping (RAID0, RAID5/6) nécessite de l'espace de travail sur chaque périphérique. Un équilibrage interrompu peut laisser des groupes de blocs partiellement remplis qui consomment l'espace de travail.

Un exemple plus complet lors du passage d'un à plusieurs périphériques, et inversement, peut être trouvé dans la section CAS D'UTILISATION TYPIQUES de btrfs-device(8) <>.

RENDRE LA DISPOSITION DES GROUPES DE BLOCS PLUS COMPACTE

La disposition des groupes de blocs n'est normalement pas visible ; la plupart des outils rapportent uniquement des nombres résumés d'espace libre ou utilisé, mais il existe encore quelques indices fournis.

Utilisons l'exemple suivant et commençons par la sortie :

$ btrfs filesystem df /path
Data, single: total=75.81GiB, used=64.44GiB
System, RAID1: total=32.00MiB, used=20.00KiB
Metadata, RAID1: total=15.87GiB, used=8.84GiB
GlobalReserve, single: total=512.00MiB, used=0.00B

En calculant grossièrement pour les données, 75G - 64G = 11G, le rapport utilisé/total est d'environ 85%. Comment pouvons-nous interpréter cela :

  • les blocs sont remplis à 85% en moyenne, c'est-à-dire que le filtre utilisation avec une valeur inférieure à 85 n'affectera probablement rien ;
  • dans un scénario plus réaliste, l'espace est réparti de manière inégale, nous pouvons supposer qu'il existe des blocs complètement utilisés et que les blocs restants sont partiellement remplis.

La compaction de la disposition pourrait être utilisée sur les deux. Dans le premier cas, cela répartirait les données d'un bloc donné sur les autres et le supprimerait. Ici, nous pouvons estimer qu'environ 850 Mio de données doivent être déplacées (85% d'un bloc de 1 Gio).

Dans le second cas, cibler les blocs partiellement utilisés déplacera moins de données et sera donc plus rapide. Une commande de filtre typique ressemblerait à ceci :

# btrfs balance start -dusage=50 /path
Done, had to relocate 2 out of 97 chunks
$ btrfs filesystem df /path
Data, single: total=74.03GiB, used=64.43GiB
System, RAID1: total=32.00MiB, used=20.00KiB
Metadata, RAID1: total=15.87GiB, used=8.84GiB
GlobalReserve, single: total=512.00MiB, used=0.00B

Comme vous pouvez le constater, le montant total de données a diminué d'environ 1 Gio, ce qui est un résultat attendu. Voyons ce qui se passe lorsque nous augmentons le filtre d'utilisation estimée.

# btrfs balance start -dusage=85 /path
Done, had to relocate 13 out of 95 chunks
$ btrfs filesystem df /path
Data, single: total=68.03GiB, used=64.43GiB
System, RAID1: total=32.00MiB, used=20.00KiB
Metadata, RAID1: total=15.87GiB, used=8.85GiB
GlobalReserve, single: total=512.00MiB, used=0.00B

Maintenant, le rapport utilisé/total est d'environ 94 % et nous avons déplacé environ 74G - 68G = 6G de données vers les groupes de blocs restants, c'est-à-dire que les 6 GiB sont maintenant libres de toute structure de système de fichiers et peuvent être réutilisés pour de nouveaux groupes de blocs de données ou de métadonnées.

Nous pouvons effectuer un exercice similaire avec les groupes de blocs de métadonnées, mais cela ne devrait généralement pas être nécessaire, sauf si le rapport utilisé/total est vraiment déséquilibré. Ici, le rapport est d'environ 50 %, mais la différence en valeur absolue est « quelques gigaoctets », ce qui peut être considéré comme normal pour une charge de travail avec des instantanés ou des reflinks mis à jour fréquemment.

# btrfs balance start -musage=50 /path
Terminé, 4 chunks sur 89 ont dû être relocalisés
$ btrfs filesystem df /path
Data, single: total=68.03GiB, used=64.43GiB
System, RAID1: total=32.00MiB, used=20.00KiB
Metadata, RAID1: total=14.87GiB, used=8.85GiB
GlobalReserve, single: total=512.00MiB, used=0.00B

Seulement 1 GiB de diminution, ce qui signifie probablement qu'il existe des groupes de blocs avec une bonne utilisation. Rendre la disposition des métadonnées plus compacte nécessiterait en revanche de mettre à jour plus de structures de métadonnées, c'est-à-dire beaucoup d'E/S. Comme l'espace de métadonnées épuisé est un problème plus grave, il n'est pas nécessaire de maintenir le rapport d'utilisation trop élevé. Pour les besoins de cet exemple, voyons les effets d'une compaction plus poussée :

# btrfs balance start -musage=70 /path
Terminé, 13 chunks sur 88 ont dû être relocalisés
$ btrfs filesystem df .
Data, single: total=68.03GiB, used=64.43GiB
System, RAID1: total=32.00MiB, used=20.00KiB
Metadata, RAID1: total=11.97GiB, used=8.83GiB
GlobalReserve, single: total=512.00MiB, used=0.00B

SE DÉBARRASSER DES GROUPES DE BLOCS COMPLÈTEMENT INUTILISÉS

Normalement, l'opération de balance a besoin d'un espace de travail pour déplacer temporairement les données avant que les anciens groupes de blocs ne soient supprimés. S'il n'y a pas d'espace de travail, elle se termine par no space left.

Il existe un cas particulier lorsque les groupes de blocs sont complètement inutilisés, éventuellement laissés après la suppression de nombreux fichiers ou d'instantanés. La suppression des groupes de blocs vides est automatique depuis la version 3.18. La même chose peut être faite manuellement, avec une exception notable : cette opération ne nécessite pas d'espace de travail. Elle peut donc être utilisée pour récupérer des groupes de blocs inutilisés afin de les rendre disponibles.

# btrfs balance start -dusage=0 /path

Cela devrait entraîner une diminution des total dans la sortie btrfs filesystem df .

CODE DE SORTIE

Sauf indication contraire ci-dessous, toutes les sous-commandes btrfs balance renvoient un code de sortie égal à zéro en cas de succès et non nul en cas d'échec.

Les sous-commandes pause, cancelet resume renvoient un code de sortie 2 si elles échouent parce qu'une opération de balance n'était pas en cours d'exécution.

La sous-commande status renvoie un code de sortie 0 si aucune opération de balance n'est en cours d'exécution, 1 si l'utilisation de la ligne de commande est incorrecte ou si une opération de balance est toujours en cours d'exécution, et 2 pour les autres erreurs.
