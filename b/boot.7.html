boot(7) Manuel d'informations diverses boot(7)

NOM

boot - Processus de démarrage du système basé sur UNIX System V Release 4

DESCRIPTION

Le processus de démarrage (ou "séquence de démarrage") varie dans ses détails selon les systèmes, mais peut être globalement divisé en phases contrôlées par les composants suivants :

(1)
matériel
(2)
chargeur du système d'exploitation (OS)
(3)
noyau
(4)
processus utilisateur racine (init(8) et inittab(5))
(5)
scripts de démarrage

Chacun de ces éléments est décrit plus en détail ci-dessous.

Matériel

Après la mise sous tension ou un redémarrage matériel, le contrôle est donné à un programme stocké en mémoire morte (normalement PROM) ; pour des raisons historiques liées à l'ordinateur personnel, ce programme est souvent appelé "le BIOS".

Ce programme effectue normalement un auto-test basique de la machine et accède à la mémoire non volatile pour lire d'autres paramètres. Cette mémoire dans le PC est une mémoire CMOS sauvegardée par pile, donc la plupart des gens s'y réfèrent comme "le CMOS" ; en dehors du monde des PC, elle est généralement appelée "la NVRAM" (mémoire vive non volatile).

Les paramètres stockés dans la NVRAM varient selon les systèmes, mais au minimum, ils doivent spécifier quel périphérique peut fournir un chargeur d'OS, ou du moins quels périphériques peuvent être sondés pour en trouver un ; un tel périphérique est connu comme "le périphérique de démarrage". L'étape de démarrage matériel charge le chargeur d'OS depuis une position fixe sur le périphérique de démarrage, puis lui transfère le contrôle.

Note :
Le périphérique à partir duquel le chargeur d'OS est lu peut être connecté via un réseau, auquel cas, les détails du démarrage sont spécifiés par des protocoles tels que DHCP, TFTP, PXE, Etherboot, etc.

Chargeur OS

Le travail principal du chargeur d'OS est de localiser le noyau sur un périphérique, de le charger, et de l'exécuter. La plupart des chargeurs d'OS permettent une utilisation interactive, afin de permettre la spécification d'un noyau alternatif (peut-être une sauvegarde au cas où celui compilé en dernier ne fonctionnerait pas) et de passer des paramètres optionnels au noyau.

Dans un PC traditionnel, le chargeur d'OS est situé dans le bloc initial de 512 octets du périphérique de démarrage ; ce bloc est connu comme "le MBR" (Master Boot Record).

Dans la plupart des systèmes, le chargeur d'OS est très limité en raison de diverses contraintes. Même sur les systèmes non-PC, il y a des limitations sur la taille et la complexité de ce chargeur, mais la limitation de taille du MBR du PC (512 octets, incluant la table de partition) rend presque impossible d'y intégrer beaucoup de fonctionnalités.

Par conséquent, la plupart des systèmes partagent le rôle de charger l'OS entre un chargeur d'OS primaire et un chargeur d'OS secondaire ; ce chargeur d'OS secondaire peut être situé dans une plus grande portion de stockage persistant, telle qu'une partition de disque.

Sous Linux, le chargeur d'OS est souvent grub(8) (une alternative est lilo(8)).

Noyau

Lorsque le noyau est chargé, il initialise divers composants de l'ordinateur et du système d'exploitation ; chaque portion de logiciel responsable d'une telle tâche est généralement considérée comme "un pilote" pour le composant applicable. Le noyau démarre le processus de pagination de la mémoire virtuelle (c'est un processus du noyau, appelé "kswapd" dans un noyau Linux moderne), et monte un système de fichiers à la racine, /.

Certains des paramètres qui peuvent être passés au noyau concernent ces activités (par exemple, le système de fichiers racine par défaut peut être remplacé) ; pour plus d'informations sur les paramètres du noyau Linux, lire bootparam(7).

Ce n'est qu'ensuite que le noyau crée le processus utilisateur initial, qui reçoit le numéro 1 comme son PID (process ID). Traditionnellement, ce processus exécute le programme /sbin/init, auquel sont passés les paramètres qui n'ont pas déjà été gérés par le noyau.

Processus utilisateur racine

Note :
La description suivante s'applique à un OS basé sur UNIX System V Release 4. Cependant, un certain nombre de systèmes largement utilisés ont adopté une approche connexe mais fondamentalement différente connue sous le nom de systemd(1), pour lequel le processus de démarrage est détaillé dans son bootup(7) associé.

Lorsque /sbin/init démarre, il lit /etc/inittab pour d'autres instructions. Ce fichier définit ce qui doit être exécuté lorsque le programme /sbin/init est invité à entrer dans un niveau d'exécution particulier, donnant à l'administrateur un moyen facile d'établir un environnement pour une certaine utilisation ; chaque niveau d'exécution est associé à un ensemble de services (par exemple, le niveau d'exécution S est le mode mono-utilisateur, et le niveau d'exécution 2 implique l'exécution de la plupart des services réseau).

L'administrateur peut changer le niveau d'exécution actuel via init(1), et interroger le niveau d'exécution actuel via runlevel(8).

Cependant, comme il n'est pas pratique de gérer les services individuels en éditant ce fichier, /etc/inittab ne fait que démarrer un ensemble de scripts qui démarrent/arrêtent réellement les services individuels.

Scripts de démarrage

Note :
La description suivante s'applique à un OS basé sur UNIX System V Release 4. Cependant, un certain nombre de systèmes largement utilisés (Slackware Linux, FreeBSD, OpenBSD) ont un schéma quelque peu différent pour les scripts de démarrage.

Pour chaque service géré (mail, serveur nfs, cron, etc.), il y a un unique script de démarrage situé dans un répertoire spécifique (/etc/init.d dans la plupart des versions de Linux). Chacun de ces scripts accepte comme unique argument le mot "start" (ce qui provoque le démarrage du service) ou le mot "stop" (ce qui provoque l'arrêt du service). Le script peut optionnellement accepter d'autres arguments pratiques (par exemple, "restart" pour arrêter puis démarrer, "status" pour afficher l'état du service, etc.). Exécuter le script sans arguments affiche les arguments possibles.

Répertoires de séquençage

Pour que des scripts spécifiques démarrent/arrêtent à des niveaux d'exécution spécifiques et dans un ordre spécifique, il existe des répertoires de séquençage, normalement de la forme /etc/rc[0-6S].d. Dans chacun de ces répertoires, il y a des liens (généralement symboliques) vers les scripts du répertoire /etc/init.d.

Un script primaire (généralement /etc/rc) est appelé depuis inittab(5) ; ce script primaire appelle le script de chaque service via un lien dans le répertoire de séquençage pertinent. Chaque lien dont le nom commence par 'S' est appelé avec l'argument "start" (démarrant ainsi le service). Chaque lien dont le nom commence par 'K' est appelé avec l'argument "stop" (arrêtant ainsi le service).

Pour définir l'ordre de démarrage ou d'arrêt au sein du même niveau d'exécution, le nom d'un lien contient un numéro d'ordre. De plus, pour plus de clarté, le nom d'un lien se termine généralement par le nom du service auquel il se réfère. Par exemple, le lien /etc/rc2.d/S80sendmail démarre le service sendmail(8) au niveau d'exécution 2. Cela se produit après que /etc/rc2.d/S12syslog a été exécuté mais avant que /etc/rc2.d/S90xfs ne soit exécuté.

Gérer ces liens revient à gérer l'ordre de démarrage et les niveaux d'exécution ; sous de nombreux systèmes, il existe des outils pour aider à cette tâche (par exemple, chkconfig(8)).
