DESCRIPTIO

N

La commande pkg-status affiche l'état des paquets spécifiés ou, si ver est spécifié, des versions de paquets. Si aucun paquet n'est spécifié, alors pkg-status affiche l'état de tous les paquets retenus (qui sont les paquets explicitement construits ; voir bpkg-pkg-build(1)). Ce dernier mode peut être modifié pour afficher l'état de tous les paquets en spécifiant l'option --all|-a. De plus, l'état des dépendances immédiates ou de toutes les dépendances des paquets ci-dessus peut être affiché en spécifiant respectivement les options --immediate|-i ou --recursive|-r. Notez que l'état est écrit sur stdout, pas stderr

.

Le format de sortie par défaut (voir l'option commune --stdout-format) est régulier avec des composants séparés par des espaces. Chaque ligne commence par le nom du paquet suivi de l'un des mots d'état listés ci-dessous. Certains d'entre eux peuvent être éventuellement suivis de ',' (sans espaces) et d'un mot de sous-état. Les lignes correspondant aux dépendances issues de configurations liées mentionneront en plus le répertoire de configuration entre crochets après le nom du

paquet.
unkno
wn

Le paquet ne fait pas partie de la configuration et n'est disponible dans aucun des
dépôts.
availab
le

Le paquet ne fait pas partie de la configuration mais est disponible dans l'un des
dépôts.
fetch
ed

Le paquet fait partie de la configuration et est
récupéré.
unpack
ed

Le paquet fait partie de la configuration et est
décompressé.
configur
ed

Le paquet fait partie de la configuration et est configuré. Peut être suivi du sous-état system indiquant un paquet provenant du système. La version d'un tel paquet système (décrit ci-dessous) peut être la valeur spéciale '*' indiquant une version
générique.
brok
en

Le paquet fait partie de la configuration et est cassé (les paquets cassés ne peuvent être purgés que ; voir bpkg-pkg-p
urge
(1)).

Si seul le nom du paquet a été spécifié sans la version du paquet, alors le mot d'état available est suivi de la liste des versions disponibles. Les versions qui ne sont disponibles que pour la mise à jour ou la rétrogradation sont affichées entre '[]' (de telles versions ne sont disponibles que comme dépendances de dépôts prérequis d'autres dépôts). Si l'option --system est spécifiée, alors la dernière version de cette liste peut avoir le préfixe sys: indiquant une version système disponible. Une telle version système peut être la valeur spéciale '?' indiquant qu'un paquet peut ou non être disponible depuis le système et que sa version est

inconnue.

Les mots d'état fetched, unpacked, configured et broken sont suivis de la version du paquet. Si la version du paquet a été spécifiée, alors le mot d'état unknown est également suivi de la

version.

Si l'état est fetched, unpacked, configured ou broken et que des versions plus récentes sont disponibles, alors la version du paquet est suivie du mot d'état available et de la liste des versions plus récentes. Pour voir à la place une liste de toutes les versions, y compris les plus anciennes, spécifiez l'option --old-available|-o. Dans ce cas, la version actuellement sélectionnée est affichée entre '()'

.

Si le nom du paquet a été spécifié avec la version, alors seul l'état (comme, configured, available, etc.) de cette version est

considéré.

Si un paquet est retenu, alors son nom est affiché avec le préfixe '!'. De même, si une version de paquet est retenue, alors la version est affichée avec le préfixe '!'. Les paquets retenus et les versions retenues ont été sélectionnés par l'utilisateur et ne sont pas automatiquement abandonnés et mis à jour,

respectivement.

Voici quelques exemples, en supposant que la configuration a libfoo 1.0.0 configuré et retenu (à la fois le paquet et la version) ainsi que libfoo 1.1.0 et 1.1.1 disponibles depuis la source et 1.1.0 depuis le

système. 
bpkg status libbar
libbar unknown
bpkg status libbar/1.0.0
libbar unknown 1.0.0
bpkg status libfoo/1.0.0
!libfoo configured !1.0.0
bpkg status libfoo/1.1.0
libfoo available 1.1.0
bpkg status --system libfoo/1.1.0
libfoo available 1.1.0 sys:1.1.0
bpkg status libfoo
!libfoo configured !1.0.0 available 1.1.0 1.1.1
bpkg status libfoo/1.1.1 libbar
libfoo available 1.1.1
libbar
unknown

Supposons maintenant que nous ayons abandonné libfoo de la configuration

: 
bpkg status libfoo/1.0.0
libfoo unknown 1.0.0
bpkg status libfoo
libfoo available 1.1.0 1.1.
1

Et supposons maintenant que nous ayons construit libfoo comme paquet système avec la version générique

: 
bpkg status libfoo
!libfoo configured,system !* available 1.1.0 1.1.
1

Un autre exemple de sortie d'état, cette fois en incluant les dépendances

: 
bpkg status -r libbaz
!libbaz configured 1.0.0
  libfoo configured 1.0.0
    bison [.bpkg/host/] configured 1.0.0
  libbar configured 2.0.
0

Si le format de sortie est json, alors la sortie est un tableau JSON d'objets qui sont la représentation sérialisée du C++ struct suivant package_

status : 
struct available_version
{
  string version;
  bool   system;
  bool   dependency;
};
struct package_status
{
  string                    name;
  optional<string>          configuration;
  optional<string>          constraint;
  string                    status;
  optional<string>          sub_status;
  optional<string>          version;
  bool                      hold_package;
  bool                      hold_version;
  vector<available_version> available_versions;
  vector<package_status>    dependencies;
}
;

Par exemple

: 
[
  {
    "name": "hello",
    "status": "configured",
    "version": "1.0.0",
    "hold_package": true,
    "available_versions": [
      {
        "version": "1.0.1"
      },
      {
        "version": "2.0.0"
      }
    ],
    "dependencies": [
      {
        "name": "libhello",
        "status": "configured",
        "version": "1.0.2",
      }
    ]
  }
]

Voir la section JSON OUTPUT dans bpkg-common-options(1) pour des détails sur les propriétés générales de ce format et la sémantique de la sérialisation des

struct.

Dans package_status, le membre configuration contient le répertoire absolu d'une configuration liée si ce paquet réside dans une configuration liée. Le membre constraint n'est présent que si l'option --constraint est spécifiée. Le membre version est absent si le membre status est unknown ou available et qu'aucune version de paquet n'est spécifiée sur la ligne de commande. Si le membre sub_status est system, alors le membre version peut être le spécial *. Le membre dependencies n'est présent que si les options --immediate|-i ou --recursive|-r sont

spécifiées.

Dans available_version, si le membre system est true, alors cette version est disponible depuis le système, auquel cas le membre version peut être le spécial ? ou *. Si le membre dependency est true, alors cette version n'est disponible que c

omme dépendance de dépôts
prérequis d'autres dépôts.
