Ce module Perl fournit une interface à la plupart des fonctionnalités disponibles dans les versions 2, 3, 5 et 6 de Berkeley DB. En général, il est sûr de supposer que l'interface fournie ici est identique à celle de Berkeley DB. Les principaux changements ont été faits pour que l'API de Berkeley DB fonctionne de manière perl. Notez que si vous utilisez Berkeley DB 2.x, les nouvelles fonctionnalités disponibles dans Berkeley DB 3.x ou plus tard ne sont pas disponibles via ce

module.

On s'attend à ce que le lecteur soit familier avec la documentation de Berkeley DB. Là où l'interface fournie ici est identique à celle de la bibliothèque Berkeley DB et... À

La classe BerkeleyDB::Env fournit une interface à la fonction Berkeley DB db_appinit dans Berkeley DB 2.x ou db_env_create et DBENV->open dans Berkeley DB 3.x (ou plus tard). Hash
Ce type de base de données permet de stocker des paires clé/valeur arbitraires dans des fichiers de données. Berkeley DB Concurrent Data Store

(CDS)

Le Berkeley DB Concurrent Data Store (CDS) est un mécanisme de verrouillage léger utile dans les scénarios où les transactions sont

excessives.

Qu'est-ce que le CDS

?

L'interface CDS de Berkeley DB est un mécanisme de verrouillage simple et léger qui permet un accès concurrent sûr aux bases de données Berkeley DB. Votre applica

tion peut avoir plusieurs processus lecteurs et écrivains, mais Berkeley DB s'arrangera pour qu'un seul processus puisse avoir un verrou d'écriture sur la base d
e données à la fois, c'est-à-dire que plusieurs processus peuvent lire depuis une base de données en même temps, mais tous les processus d'écriture seront sérialisés.

Dois-je l'utiliser

?

Bien que ce modèle de verrouillage simple soit tout à fait adéquat pour certaines applications, il sera trop restrictif pour d'autres. Avant de décider d'utiliser le mode CDS, vous devez vous assurer qu'il convient au comportement attendu de votre

application.

Les caractéristiques clés de ce modèle

sont
  • Toutes les opérations d'écriture sont
    • sérialisées.
  • Une opération d'écriture se bl
    • oquera jusqu'à ce que toutes
les lectures soient terminées.

Il y a quelques attributs de votre application dont vous devez être conscient avant de choisir d'utiliser le

CDS.

Premièrement, si votre application a besoin soit de la récupérabilité soit du support des transactions, alors le CDS ne conviendra

pas.

Ensuite, quel sera le ratio des opérations de lecture par rapport aux opérations d'écriture dans votre application

?

Si elle effectue principalement des opérations de lecture et très peu d'écritures, alors le CDS peut être

approprié.

Quel est le débit attendu des lectures/écritures dans votre application

?

Si votre application fait 90% d'écritures et 10% de lectures, mais qu'en moyenne vous n'avez une transaction que toutes les 5 secondes, alors le fait que toutes les écritures soient sérialisées n'aura pas d'importance, car il y aura rarement plusieurs processus d'écriture

bloqués.

En résumé, le mode CDS peut être approprié pour votre application si elle effectue principalement des lectures et très peu d'écritures, ou si le débit est faible. De plus, si vous n'avez pas besoin de pouvoir annuler une série d'opérations de base de données en cas d'erreur, alors le CDS

convient.

Si l'une de ces conditions n'est pas remplie, v

ous devrez utiliser les transactions de Berk
eley DB. Cela est hors du cadre de ce document.

Verrouillage

utilisé

Berkeley DB implémente le mode CDS en utilisant deux types de verrous en coulisses - à savoir les verrous de lecture et les verrous d'écriture. Un verrou de lecture permet à plusieurs processus d'accéder à la base de données pour la lecture en même temps. Un verrou d'écriture n'obtiendra l'accès à la base de données que lorsqu'il n'y a aucun verrou de lecture ou d'écriture actif. Le verrou d'écriture se bloquera jusqu'à ce que le processus détenant le verrou le

libère.

Plusieurs processus avec des verrous de lecture peuvent tous accéder à la base de données en même temps tant qu'aucun processus n'a de verrou d'écriture. Un processus avec un verrou d'écriture ne peut accéder à la base de données que s'il n'y a aucun autre verrou de lecture ou d'écriture

actif.

La plupart du temps, le mode CDS de Berkeley DB gérera tous les verrous sans que votre application ait à faire quoi que ce soit. Il y a cependant quelques exceptions dont vous devez être conscient - elles seront discutées dans « Mise à jour sûre des enregistrements » et « Curseurs implicites »

ci-dessous.

Un curseur Berkeley DB (créé avec "$db->db_cursor") tiendra un verrou sur la base de données jusqu'à ce qu'il soit explicitement fermé ou détruit. Cela signifie que le verrou a le potentiel d'être de longue

durée.

Par défaut, les curseurs de Berkeley DB créent un verrou de lecture, mais il est possible de créer un curseur qui détient un verrou d'écriture,

ainsi 
$cursor = $db->db_cursor(DB_WRITECURSOR)
;

Tant qu'un curseur de lecture ou d'écriture est actif, il bloquera tout autre processus qui voudrait écrire dans la base de

données.

Pour éviter les problèmes de blocage, ne gardez les curseurs ouverts que tant qu'ils sont nécessaires. Il en va de même lorsque vous utilisez la méthode "cursor" ou la méthode "cds_

lock".

Pour des informations complètes sur le CDS, voir la

La première chose à noter est que vous DEVEZ toujours utiliser un environnement Berkeley DB si vous voulez utiliser le verrouillage avec Berkeley

DB.

Rappelez-vous qu'en dehors des fichiers de base de données réels que vous créez explicitement vous-même, Berkeley DB en créera quelques-uns en coulisses pour gérer le verrouillage - ils ont généralement des noms comme "__db.001". C'est donc une bonne idée d'utiliser l'option "-Home", à moins que vous ne soyez d'accord pour que tous ces fichiers soient écrits dans le répertoire

courant.

Ensuite, n'oubliez pas d'inclure le drapeau "DB_CREATE" lors de l'ouverture de l'environnement pour la première fois. Une erreur courante est d'oublier d'ajouter cette option et de se demander ensuite pourquoi l'application ne fonctionne

pas.

Enfin, il est vital que tous les processus qui v

Mise à jour sûre d'un

enregistrement

L'un des principaux pièges lors de l'utilisation du CDS est si vous voulez mettre à jour un enregistrement dans une base de données, c'est-à-dire si vous voulez récupérer un enregistrement d'une base de données, le modifier d'une certaine manière et le remettre dans la base de

données.

Par exemple, disons que vous écrivez une application web et que vous voulez conserver un enregistrement du nombre de fois où votre site est consulté dans une base de données Berkeley DB. Votre code aura donc une ligne de code comme celle-ci (en supposant, bien sûr, que %hash a été lié à une base de données Berkeley DB)

: 
$hash{Counter} ++
;

Cela peut sembler inoffensif, mais il y a une condition de course qui rôde là-dedans. Si je réécris la ligne de code en utilisant l'API bas niveau de Berkeley DB, qui est ce qui sera réellement exécuté, la condition de course peut être plus apparente

: 
$db->db_get("Counter", $value);
++ $value ;
$db->db_put("Counter", $value)
;

Considérez ce qui se passe en coulisses lorsque vous exécutez les commandes ci-dessus. Premièrement, la valeur existante pour la clé "Counter" est récupérée depuis la base de données en utilisant "db_get". Un verrou de lecture sera utilisé pour cette partie de la mise à jour. La valeur est ensuite incrémentée, et la nouvelle valeur est écrite dans la base de données en utilisant "db_put". Cette fois, un verrou d'écriture sera

utilisé.

Voici le problème - il n'y a rien qui empêche deux (ou plus) processus d'exécuter la partie lecture en même temps. Rappelez-vous que plusieurs processus peuvent détenir un verrou de lecture sur la base de données en même temps. Ainsi, tous les deux récupéreront la même valeur, disons 7, depuis la base de données. Tous deux incrémentent la valeur à 8 et tentent de l'écrire dans la base de données. Berkeley DB s'assurera qu'un seul des processus obtient un verrou d'écriture, tandis que l'autre sera bloqué. Ainsi, le processus qui a eu la chance d'obtenir le verrou d'écriture va stocker la valeur 8 dans la base de données et libérer le verrou d'écriture. Maintenant, l'autre processus sera débloqué, et il écrira lui aussi la valeur 8 dans la base de données. Le résultat, dans cet exemple, est que nous avons manqué un incrément dans le

compteur.

Pour gérer ce type de scénario, vous devez rendre la mise à jour atomique. Une méthode de commodité, appelée "cds_lock", est fournie avec le module BerkeleyDB à cette fin. En utilisant "cds_lock", le code de mise à jour du compteur peut maintenant être réécrit ainsi

: re>my $lk = $dbh->cds_lock() ; $hash{Counter} ++ ; $lk->cds_unlock;

ou ceci, où la portée est utilisée pour limiter la durée de vie de l'objet

verrou 
{
    my $lk = $dbh->cds_lock() ;
    $hash{Counter} ++ ;
}

De même, "cds_lock" peut être utilisé avec l'API native Berkeley

DB 
my $lk = $dbh->cds_lock() ;
$db->db_get("Counter", $value);
++ $value ;
$db->db_put("Counter", $value);
$lk->
unlock;

La méthode "cds_lock" garantira que le processus actuel a un accès exclusif à la base de données jusqu'à ce que le verrou soit soit explicitement libéré, via "$lk->cds_unlock()" ou par la destruction de l'objet

verrou.

Si vous êtes intéressé, tout ce que "cds_lock" fait, c'est ouvrir un curseur "write". Cela a l'effet secondaire utile de maintenir un verrou d'écriture sur la base de données jusqu'à ce que le curseur soit détruit. Voici comment créer un curseur

d'écriture 
$cursor = $db->db_cursor(DB_WRITECURSOR)
;

Si vous avez instancié plusieurs objets "cds_lock" pour une base de données dans un seul processus, ce processus détiendra un verrou d'écriture sur la base de données jusqu'à ce que TOUS les objets "cds_lock" aient été

détruits.

Comme pour tous les curseurs d'écriture, vous devriez essayer de limiter la portée du "cds_lock" au temps le plus court possible. Rappelez-vous que la base de données complèt

e sera verrouillée pour les autres process
us tant que le verrou d'écriture est en place.

Impossible d'écrire avec un curseur de lecture pendant qu'un curseur d'écriture est

actif

Ce problème est plus facile à démontrer avec un exemple, alors considérez le code ci-dessous. L'intention du code est d'incrémenter les valeurs de tous les éléments d'une base de données de

un. 
# Assume $db is a database opened in a CDS environment.
# Create a write-lock
my $lock = $db->db_cursor(DB_WRITECURSOR);
# or
# my $lock = $db->cds_lock();
my $cursor = $db->db_cursor();
# Now loop through the database, and increment
# each value using c_put.
while ($cursor->c_get($key, $value, DB_NEXT) == 0)
{
     $cursor->c_put($key, $value+1, DB_CURRENT) == 0
         or die "$BerkeleyDB::Error\n";
}

Lorsque ce code est exécuté, il échouera sur la ligne "c_put" avec cette

erreur 
Tentative d'écriture sur un curseur en lecture
seule

Le curseur de lecture a automatiquement désactivé une opération d'écriture pour éviter un

interblocage.

La règle est donc -- vous NE POUVEZ PAS effectuer une opération d'écriture en utilisant un curseur en lecture seule (c'est-à-dire que vous ne pouvez pas utiliser "c_put" ou "c_del") alors qu'un autre curseur d'écriture est déjà

actif.

La solution de contournement pour ce problème est d'utiliser simplement "db_put" au lieu de "c_put", comme

ceci 
# Assume $db is a database opened in a CDS environment.
# Create a write-lock
my $lock = $db->db_cursor(DB_WRITECURSOR);
# or
# my $lock = $db->cds_lock();
my $cursor = $db->db_cursor();
# Now loop through the database, and increment
# each value using c_put.
while ($cursor->c_get($key, $value, DB_NEXT) == 0)
{
     $db->db_put($key, $value+1) == 0
         or die "$BerkeleyDB::Error\n";
}

Curseurs

implicites

Tous les curseurs Berkeley DB détiendront soit un verrou de lecture, soit un verrou d'écriture sur la base de données pour la durée de vie du curseur. Afin d'éviter le blocage des autres processus, vous devez vous assurer qu'ils ne sont pas de longue

durée.

Il y a plusieurs cas où l'interface Perl pour Berkeley DB créera un curseur en arrière-plan sans que vous en soyez conscient. La plupart d'entre eux sont très éphémères et n'affecteront pas l'exécution de votre script, mais il y a quelques exceptions

notables.

Considérez cet extrait de

code 
while (my ($k, $v) = each %hash)
{
    # do something
}

Pour implémenter la fonctionnalité "each", un curseur de lecture sera créé en arrière-plan pour vous permettre d'itérer à travers le hash lié, %hash. Tant que ce curseur est encore actif, un verrou de lecture sera évidemment détenu sur la base de données. Si votre application a d'autres processus d'écriture, ceux-ci seront bloqués jusqu'à ce que le curseur de lecture soit fermé. Cela n'arrivera pas avant la terminaison de la

boucle.

Pour éviter les problèmes de blocage, ne gardez les curseurs ouverts que le temps nécessaire. Il en va de même lorsque vous utilisez la méthode "cursor" ou la méthode "cds_lock"

.

Le comportement de verrouillage des fonctions "values" ou "keys", montrées ci-dessous, est subtilement

différent. 
foreach my $k (keys %hash)
{
    # do something
}
foreach my $v (values %hash)
{
    # do something
}

Tout comme dans la fonction "each", un curseur de lecture sera créé pour itérer sur la base de données dans ces deux cas. Là où "keys" et "values" diffèrent, c'est l'endroit où le curseur effectue l'itération à travers la base de données. Alors que "each" effectuait une seule itération à chaque fois qu'elle était invoquée, les fonctions "keys" et "values" itéreront à travers toute la base de données en une seule fois -- la base de données complète sera lue en mémoire avant la première itération de la

boucle.

Mis à part le fait qu'un verrou de lecture sera détenu pendant le temps requis pour itérer à travers la base de données, l'utilisation de "keys" et "values" est déconseillée car cela entraînera la lectu

re de la base de donnée
s complète en mémoire.

Éviter l'interblocage avec plusieurs bases de

données

Si votre application CDS utilise plusieurs fichiers de base de données, et que vous devez écrire dans plus d'un d'entre eux, vous devez faire attention à ne pas créer un

interblocage.

Par exemple, disons que vous avez deux bases de données, D1 et D2, et deux processus, P1 et P2. Supposons que vous vouliez écrire un enregistrement dans chaque base de données. Si P1 écrit les enregistrements dans les bases de données dans l'ordre D1, D2 tandis que le processus P2 écrit les enregistrements dans l'ordre D2, D1, il y a un potentiel

d'interblocage.

Ce scénario peut être évité soit en acquérant toujours les verrous d'écriture dans exactement le même ordre dans votre code d'application, soit en utilisant l'indicateur "DB_CDB_ALLDB" lors de l'ouverture de l'environnement. Cet indicateur fera qu'un verrou d'écriture s'appliquera à toutes les bases de données de l'environnement

.

Un exemple -- le problème de la terminaison

NULL.

Considérez le scénario suivant. Vous avez une base de données DBM que vous devez partager avec une application tierce en C. L'application C suppose que toutes les clés et valeurs sont terminées par NULL. Malheureusement, lorsque Perl écrit dans les bases de données DBM, il n'utilise pas la terminaison NULL, donc votre application Perl devra gérer elle-même la terminaison NULL. Lorsque vous écrivez dans la base de données, vous devrez utiliser quelque chose comme ceci

: 
$hash{"$key\0"} = "$value\0"
;

De même, le NULL doit être pris en compte lorsque vous considérez la longueur des clés/valeurs

existantes.

Ce serait beaucoup mieux si vous pouviez ignorer les terminaisons NULL problème dans le code principal de l'application et avoir un mécanisme qui ajoute automatiquement le NULL de terminaison à toutes les clés et valeurs lorsque vous écrivez dans la base de données et les fait supprimer lorsque vous lisez depuis la base de données. Comme je suis sûr que vous l'avez déjà deviné, c'est un problème que les filtres DBM peuvent résoudre très

facilement. 
use strict ;
use BerkeleyDB ;
my %hash ;
my $filename = "filt.db" ;
unlink $filename ;
my $db = tie %hash, 'BerkeleyDB::Hash',
            -Filename   => $filename,
            -Flags      => DB_CREATE
  or die "Cannot open $filename: $!\n" ;
# Installer les filtres DBM
$db->filter_fetch_key  ( sub { s/\0$//    } ) ;
$db->filter_store_key  ( sub { $_ .= "\0" } ) ;
$db->filter_fetch_value( sub { s/\0$//    } ) ;
$db->filter_store_value( sub { $_ .= "\0" } ) ;
$hash{"abc"} = "def" ;
my $a = $hash{"ABC"} ;
# ...
undef $db ;
untie %hash
;

J'espère que le contenu de chacun des filtres devrait être auto-

explicatif. Les deux filtres "fetch" suppriment le NULL de termi
naison, et les deux filtres "store" ajoutent un NULL de terminaison.

Un autre exemple -- la clé est un int

C.

Voici un autre exemple de la vie réelle. Par défaut, lorsque Perl écrit dans une base de données DBM, il écrit toujours la clé et la valeur sous forme de chaînes. Ainsi lorsque vous utilisez ceci

: 
$hash{12345} = "something"
;

la clé 12345 sera stockée dans la base de données DBM sous forme de chaîne de 5 octets "12345". Si vous voulez réellement que la clé soit stockée dans la base de données DBM sous forme d'int C, vous devrez utiliser "pack" lors de l'écriture, et "unpack" lors de la

lecture.

Voici un filtre DBM qui le fait

: 
use strict ;
use BerkeleyDB ;
my %hash ;
my $filename = "filt.db" ;
unlink $filename ;
my $db = tie %hash, 'BerkeleyDB::Btree',
            -Filename   => $filename,
            -Flags      => DB_CREATE
  or die "Cannot open $filename: $!\n" ;
$db->filter_fetch_key  ( sub { $_ = unpack("i", $_) } ) ;
$db->filter_store_key  ( sub { $_ = pack ("i", $_) } ) ;
$hash{123} = "def" ;
# ...
undef $db ;
untie %hash
;

s -- nous n'avons besoin que de manipuler
le contenu de la clé, il n'était donc pas néc
essaire d'installer des filtres de valeur.
