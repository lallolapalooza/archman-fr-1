DESCRIPTIO

N

bup split concatène le contenu des fichiers donnés (ou lit depuis stdin si aucun nom de fichier n'est fourni), découpe le contenu en morceaux d'environ 8k à l'aide d'un algorithme de somme de contrôle glissante, et enregistre les morceaux dans un dépôt bup. Les morceaux qui ont déjà été enregistrés ne le sont pas à nouveau (c'est-à-dire qu'ils sont « dédupliqués »)

.

En raison du fonctionnement de la somme de contrôle glissante, les morceaux tendent à être très stables malgré les modifications d'un fichier donné, y compris l'ajout, la suppression et la modification

d'octets.

Par exemple, si vous utilisez bup split pour sauvegarder un dump XML d'une base de données, et que le fichier XML change légèrement d'une exécution à l'autre, presque toutes les données seront toujours dédupliquées et la taille de chaque sauvegarde après la première sera généralement assez

petite.

Une autre technique consiste à rediriger la sortie des programmes tar(1) ou cpio(1) vers bup split. Lorsque des fichiers individuels dans l'archive tar changent légèrement ou sont ajoutés ou supprimés, bup traite toujours le reste de l'archive efficacement. (Notez que bup save est généralement une façon plus efficace d'accomplir cela, cependant.

)

Pour récupérer les données, utilisez bup-jo

in(
1).

MODE

S

Ces options sélectionnent le comportement principal de la commande, -n étant le choix le plus

probable.
-n, --name=no
m
après avoir créé le jeu de données, créer une branche git nommée nom afin qu'il puisse être accessible en utilisant ce nom. Si nom existe déjà, le nouveau jeu de données sera considéré comme un descendant de l'ancien nom. (Ainsi, vous pouvez créer continuellement de nouveaux jeux de données avec le même nom, et plus tard consulter l'historique de ce jeu de données pour voir comment il a changé au fil du temps.) Les données d'origine seront également disponibles en tant que fichier de premier niveau nommé « data » dans le VFS, accessible via bup fuse, bup ftp,
etc.
-t,
--tree
afficher l'identifiant de l'arbre git du jeu de données
résultant.
-c,
--commit
afficher l'identifiant du commit git du jeu de données
résultant.
-b,
--blobs
afficher une série d'identifiants de blobs git qui correspondent aux morceaux dans le jeu de données. Incompatible avec -n, -t et
-c.
--no
op
lire les données et les découper en blocs basés sur l'algorithme de somme de contrôle glissante « bupsplit », mais ne rien enregistrer dans le dépôt. Peut être combiné avec -b ou -t pour calculer (mais pas enregistrer) les blobs git ou les identifiants d'arbre du jeu de données. C'est principalement utile pour le benchmark et la validation de l'algorithme bupsplit. Incompatible avec -n et
-c.
--co
py
comme --noop, mais écrit aussi les données sur stdout. Cela peut être utile pour me
surer la vitesse de lecture+bupsplit+écrit
ure pour de grandes quantités de do
nnées. Incompatible avec -n, -t, -c et -b.

OPTION

S
-r, --remote=hôte:che
min
enregistrer l'ensemble de sauvegarde sur le serveur distant donné. Si chemin est omis, utilise le chemin par défaut sur le serveur distant (vous devez quand même inclure le « :'). La connexion au serveur distant est établie avec SSH. Si vous souhaitez spécifier le port, l'utilisateur ou la clé privée à utiliser pour la connexion SSH, nous vous recommandons d'utiliser le fichier ~/.ssh/config. Même si la destination est distante, un dépôt bup local est toujours
requis.
-d, --date=secondes-depuis-ep
och
spécifier la date inscrite dans le commit (secondes depuis 1970-01-01)
.
-q,
--quiet
désactiver les messages de
progression.
-v,
--verbose
augmenter le niveau de verbosité (peut être utilisé plusieurs
fois).
--git-i
ds
stdin est une liste d'identifiants d'objets git au lieu de données brutes. bup split lira le contenu de chaque objet git nommé (s'il existe dans le dépôt bup) et le découpera. Cela peut être utile pour convertir un dépôt git contenant de gros fichiers binaires pour utiliser le découpage par hachage de style bup à la place. Cette option est probablement la plus utile lorsqu'elle est combinée avec --keep-bound
aries.
--keep-boundar
ies
si plusieurs noms de fichiers sont donnés sur la ligne de commande, ils sont normalement concaténés comme si le contenu provenait d'un seul fichier. C'est-à-dire que l'ensemble de blobs/arbres produit est identique à ce qu'il aurait été s'il y avait eu un seul fichier en entrée. Cependant, si vous utilisez --keep-boundaries, chaque fichier est découpé séparément. Vous n'obtenez toujours qu'un seul arbre ou commit ou série de blobs, mais chaque blob provient d'un seul des fichiers ; la fin de l'un des fichiers en entrée met toujours fin à un
blob.
--ben
ch
afficher les temps d'exécution du benchmark sur
stderr.
--max-pack-size=octe
ts
ne jamais créer de fichiers pack git plus grands que le nombre d'octets donné. La valeur par défaut est de 1 milliard d'octets. Habituellement, il n'y a pas de raison de changer
cela.
--max-pack-objects=numob
js
ne jamais créer de fichiers pack git avec plus que le nombre d'objets donné. La valeur par défaut est de 200 000 objets. Habituellement, il n'y a pas de raison de changer
cela.
--fanout=numob
js
lors du découpage de fichiers très volumineux, essayer de maintenir le nombre d'éléments dans les arbres à une moyenne de numobj
s.
--bwlimit=octets/sec
onde
ne pas transmettre plus que octets/seconde octets par seconde au serveur. C'est utile pour éviter que vos sauvegardes n'absorbent toute la bande passante de votre réseau. Utilisez un suffixe comme k, M ou G pour spécifier respectivement des multiples de 1024, 1024*1024,
1024*1024*1024.
-#, --compress=
#
définir le niveau de compression à # (une v
aleur de 0 à 9, où 9 est le plus élevé
et 0 est sans compression). La valeur par
défaut est 1 (compression rapide et lâche)
