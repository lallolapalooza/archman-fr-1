DESCRIPTIO

N

BorgBackup (abrégé : Borg) est un programme de sauvegarde avec déduplication. Il prend en charge, en option, la compression et le chiffrement

authentifié.

L'objectif principal de Borg est de fournir un moyen efficace et sécurisé de sauvegarder des données. La technique de déduplication des données utilisée rend Borg adapté aux sauvegardes quotidiennes car seules les modifications sont stockées. La technique de chiffrement authentifié le rend adapté aux sauvegardes vers des cibles qui ne sont pas entièrement de

confiance.

Borg stocke un ensemble de fichiers dans une archive. Un dépôt est une collection d'archives. Le format des dépôts est propre à Borg. Borg ne distingue pas les archives les unes des autres d'une ma

nière autre que leur nom ; il n'importe pas quand ou où l
es archives ont été créées (par ex. sur des hôtes différents).

BORG_WORKAROUNDS
Une liste de chaînes séparées par des virgules qui déclenchent des solutions de contournement dans borg, par ex. pour contourner des bogues dans d'autres logiciels.

Les chaînes actuellement connues sont :

basesyncfile
Utilise le code BaseSyncFile plus simple pour éviter les problèmes avec sync_file_range. Vous pourriez en avoir besoin pour exécuter borg sur WSL (Windows Subsystem for Linux) ou dans des conteneurs systemd.nspawn sur certaines architectures (par ex. ARM). L'utilisation de ceci n'affecte pas la sécurité des données, mais pourrait entraîner une écriture plus intense sur le disque (pas de diffusion continue sur le disque).
retry_erofs
Réessaie d'ouvrir un fichier sans O_NOATIME si l'ouverture d'un fichier avec O_NOATIME a causé EROFS. Vous en aurez besoin pour créer des archives à partir de copies volumiques d'ombre dans WSL1 (Windows Subsystem for Linux 1).
authenticated_no_key
Solution de contournement pour une clé ou une phrase secrète perdue pour un dépôt en mode authentifié (ceux-ci sont uniquement authentifiés, mais pas chiffrés). Si la clé est manquante dans la configuration du dépôt, ajoutez key = anything.

Cette solution de contournement est uniquement pour les urgences et uniquement pour extraire des données d'un dépôt affecté (accès en lecture seule) :

BORG_WORKAROUNDS=authenticated_no_key borg extract repo::archive

Une fois que vous avez extrait toutes les données nécessaires, vous DEVEZ supprimer le dépôt :

BORG_WORKAROUNDS=authenticated_no_key borg delete repo

Vous pouvez maintenant initialiser un nouveau dépôt. Assurez-vous de ne plus utiliser la solution de contournement.

ignore_invalid_archive_tam
Solution de contournement pour les TAM d'archive invalides créés par borg < 1.2.5, voir #7791.

Cette solution de contournement devra probablement n'être utilisée qu'une seule fois lors du suivi des instructions de mise à niveau pour CVE-2023-36811, voir archives_tam_vuln.

Dans les opérations de production normales, cette solution de contournement ne devrait jamais être utilisée.

Répertoires et fichiers :
BORG_BASE_DIR
Par défaut $HOME ou ~$USER ou ~ (dans cet ordre). Si vous souhaitez déplacer tous les dossiers spécifiques à borg vers un chemin personnalisé en une seule fois, tout ce que vous avez à faire est de modifier BORG_BASE_DIR : les autres chemins pour le cache, la configuration, etc. s'adapteront en conséquence (en supposant que vous ne les ayez pas définis sur une autre valeur personnalisée).
BORG_CACHE_DIR
Par défaut $BORG_BASE_DIR/.cache/borg. Si BORG_BASE_DIR n'est pas explicitement défini pendant que la variable d'environnement XDG https://specifications.freedesktop.org/basedir-spec/0.6/ar01s03.html
XDG_CACHE_HOME est définie, alors $XDG_CACHE_HOME/borg est utilisé à la place. Ce répertoire contient le cache local et pourrait nécessiter beaucoup d'espace pour gérer de grands dépôts. Assurez-vous d'être conscient des aspects de sécurité associés à l'emplacement du cache : cache_security
BORG_CONFIG_DIR
Par défaut $BORG_BASE_DIR/.config/borg. Si BORG_BASE_DIR n'est pas explicitement défini pendant que la variable d'environnement XDG https://specifications.freedesktop.org/basedir-spec/0.6/ar01s03.html
XDG_CONFIG_HOME est définie, alors $XDG_CONFIG_HOME/borg est utilisé à la place. Ce répertoire contient tous les répertoires de configuration de borg, voir la FAQ pour un avis de sécurité concernant les données dans ce répertoire : home_config_borg
BORG_SECURITY_DIR
Par défaut $BORG_CONFIG_DIR/security. Ce répertoire contient les informations que borg utilise pour suivre son utilisation des NONCES ("nombres utilisés une seule fois" - généralement dans un contexte de chiffrement) et d'autres données pertinentes pour la sécurité.
BORG_KEYS_DIR
Par défaut $BORG_CONFIG_DIR/keys. Ce répertoire contient les clés pour les dépôts chiffrés.
BORG_KEY_FILE
Lorsqu'il est défini, utilise le chemin donné comme fichier de clé de dépôt. Veuillez noter que ce n'est que pour des applications plutôt spéciales qui gèrent entièrement les fichiers de clés en externe :
  • ce paramètre ne s'applique qu'aux modes fichier de clé (pas aux modes clé de dépôt).
  • l'utilisation d'un chemin absolu complet vers le fichier de clé est recommandée.
  • tous les répertoires du chemin donné doivent exister.
  • ce paramètre force borg à utiliser le fichier de clé à l'emplacement donné.
  • le fichier de clé doit exister (pour la plupart des commandes) ou sera créé (borg init).

Systèmes de fichiers

Nous déconseillons fortement d'utiliser Borg (ou tout autre logiciel de type base de données) sur des systèmes de fichiers non journalisés comme FAT, car il est impossible de supposer une quelconque cohérence en cas de pannes de courant (ou de déconnexion soudaine d'un disque externe ou d'autres défaillances similaires).

Bien que Borg utilise un stockage de données résistant à ces défaillances lorsqu'il est utilisé sur des systèmes de fichiers journalisés, il n'est pas possible de garantir cela avec certains matériels -- indépendamment du logiciel utilisé. Nous ne connaissons pas de liste de matériels affectés.

Si vous suspectez que votre dépôt Borg est toujours cohérent et lisible après l'une des défaillances mentionnées ci-dessus, exécutez borg check --verify-data pour vous assurer qu'il est cohérent. Exigences pour les systèmes de fichiers de dépôt Borg

  • Noms de fichiers longs
  • Au moins trois niveaux de répertoire avec des noms courts
  • Généralement, tailles de fichiers allant jusqu'à quelques centaines de Mo. Les grands dépôts peuvent nécessiter de grands fichiers (> 2 Go).
  • Jusqu'à 1000 fichiers par répertoire.
  • rename(2) / MoveFile(Ex) devrait fonctionner comme spécifié, c'est-à-dire sur le même système de fichiers, il devrait s'agir d'une opération de déplacement (pas de copie), et en cas de répertoire, il devrait échouer si la destination existe et n'est pas un répertoire vide, car cela est utilisé pour le verrouillage.
  • Les liens physiques sont nécessaires pour borg_upgrade (si l'option --inplace n'est pas utilisée). Les liens physiques sont également utilisés pour une mise à jour de fichier plus sûre et plus fiable (par ex. du fichier de configuration du dépôt), mais le c ode essaie de fon

Borg peut utiliser beaucoup de ressources en fonction de la taille du jeu de données avec lequel il

Si l'on utilise Borg en mode client/serveur (avec un dépôt ssh:), l'utilisation des ressources se fait en partie sur le client et en partie sur le

serveur.

Si l'on utilise Borg comme processus unique (avec un dépôt sur système de fichiers), toute l'utilisation des ressources se fait dans ce seul processus, il suffit donc d'additionner client + serveur pour obtenir l'utilisation approximative des

ressources.

Lors de l'utilisation de borg en mode client/serveur avec un dépôt de type <ssh:>, les processus ssh utilisés pour la couche de transport auront besoin d'un peu de CPU sur le client et sur le serveur en raison du chiffrement qu'ils effectuent - en particulier si vous faites transiter de grandes quantités de

Mémoire (RAM) client
:
L'index des chunks et l'index des fichiers sont lus en mémoire pour des raisons de performance. Peut nécessiter de grandes quantités de mémoire (voir ci-dessous). La compression, en particulier la compression lzma avec des niveaux élevés, peut nécessiter des quantités importantes de

Mémoire (RAM) serveur
:
Le processus serveur chargera l'index du dépôt en mémoire. Peut nécessiter des quantités considérables de mémoire, mais moins que sur le client (voir ci-dessous)
.
Index des chunks (client uniquement)
:
Proportionnel à la quantité de chunks de données dans votre dépôt. Beaucoup de chunks dans votre dépôt impliquent un gros index de chunks. Il est possible d'ajuster les paramètres du chunker (voir les options de create)
.
Index des fichiers (client uniquement)
:
Proportionnel à la quantité de fichiers dans vos dernières sauvegardes. Peut être désactivé (voir les options de create), mais la prochaine sauvegarde pourrait être beaucoup plus lente si vous le faites. Le bénéfice de vitesse de l'utilisation du cache de fichiers est proportionnel à la taille des
fichiers.
Index du dépôt (serveur uniquement)
:
Proportionnel à la quantité de chunks de données dans votre dépôt. Beaucoup de chunks dans votre dépôt impliquent un gros index de dépôt. Il est possible d'ajuster les paramètres du chunker (voir les options de create) pour influencer la quantité de chunks
créés.
Fichiers temporaires (client)
:
La lecture des données et des métadonnées depuis un dépôt monté via FUSE consommera jusqu'à la taille de tous les petits chunks dédupliqués du dépôt. Les gros chunks ne seront pas mis en cache
localement.
Fichiers temporaires (serveur)
:
Une quantité non négligeable de données sera stockée dans le répertoire temporaire distant pour chaque client qui s'y connecte. Pour certains distants, cela peut remplir le répertoire temporaire par défaut dans /tmp. Cela peut être remédié en s'assurant que la variable d'environnement $TMPDIR, $TEMP ou $TMP est correctement définie pour le processus sshd. Pour certains OS, cela peut être fait simplement en définissant la bonne valeur dans le .bashrc (ou le fichier de configuration de connexion équivalent pour d'autres shells), cependant dans d'autres cas il peut être nécessaire d'abord d'activer PermitUserEnvironment yes dans votre fichier sshd_config, puis d'ajouter environment="TMPDIR=/my/big/tmpdir" au début de la clé publique à utiliser dans le fichier authorize
d_hosts.
Fichiers de cache (client uniquement)
:
Contient l'index des chunks et l'index des fichiers (plus une collection d'index de chunks de archives uniques qui peuvent nécessiter d'énormes quantités d'espace disque, selon le nombre et la taille des archives - voir la FAQ pour savoir comment réduire)
.
