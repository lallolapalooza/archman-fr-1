NOM

bootctl - Contrôler les paramètres de démarrage du firmware EFI et gérer le chargeur de démarrage

SYNOPSIS

bootctl [OPTIONS...] {COMMANDE}

DESCRIPTION

bootctl peut vérifier l'état du firmware EFI et du chargeur de démarrage, lister et gérer les chargeurs de démarrage et les entrées de chargeur de démarrage disponibles, et installer, mettre à jour ou supprimer le systemd-boot(7) chargeur de démarrage sur le système actuel.

COMMANDES GÉNÉRIQUES DU FIRMWARE/CHARGEUR DE DÉMARRAGE EFI

Ces commandes sont disponibles sur tout système EFI, quel que soit le chargeur de démarrage utilisé.

status

Affiche des informations brèves sur le firmware du système, le chargeur de démarrage utilisé pour démarrer le système, les chargeurs de démarrage actuellement disponibles dans l'ESP, les chargeurs de démarrage listés dans la liste des chargeurs de démarrage du firmware et l'entrée de chargeur de démarrage par défaut actuelle. Si aucune commande n'est spécifiée, c'est la valeur par défaut implicite.

Voir l'exemple ci-dessous pour les détails de la sortie.

Ajouté dans la version 239.

reboot-to-firmware [BOOL]

Interroge ou définit l'indicateur "Reboot-Into-Firmware-Setup" du firmware EFI. Prend un argument booléen qui contrôle si le setup du firmware doit être affiché au prochain redémarrage du système. Si l'argument est omis, affiche l'état actuel de l'indicateur, ou si l'indicateur est pris en charge. Cela contrôle le même indicateur que systemctl reboot --firmware-setup, mais est plus bas niveau et permet de définir l'indicateur indépendamment de la demande effective de redémarrage.

Astuce : utiliser systemctl reboot --firmware-setup pour redémarrer une fois dans le setup du firmware. Voir systemctl(1) pour les détails.

Ajouté dans la version 251.

COMMANDES DE SPÉCIFICATION DU CHARGEUR DE DÉMARRAGE

Ces commandes sont disponibles pour tous les chargeurs de démarrage qui implémentent la Spécification du chargeur de démarrage[1], tels que systemd-boot.

list

Affiche toutes les entrées de chargeur de démarrage disponibles implémentant la Spécification du chargeur de démarrage[1], ainsi que toute autre entrée découverte ou générée automatiquement par un chargeur de démarrage implémentant l' Interface du chargeur de démarrage[2]. Une sortie JSON peut être demandée avec --json=.

Voir l'exemple ci-dessous pour les détails de la sortie.

Ajouté dans la version 239.

unlink ID

Supprime une entrée de chargeur de démarrage y compris les fichiers auxquels elle fait référence. Prend une chaîne d'ID d'entrée de chargeur de démarrage ou un motif glob comme argument. Les fichiers référencés tels que le noyau ou l'initrd ne sont supprimés que si aucune autre entrée ne fait référence à eux.

Ajouté dans la version 253.

cleanup

Supprime les fichiers des partitions ESP et XBOOTLDR qui appartiennent au jeton d'entrée mais ne sont référencés dans aucune entrée de chargeur de démarrage.

Ajouté dans la version 253.

COMMANDES DE L'INTERFACE DU CHARGEUR DE DÉMARRAGE

Ces commandes sont disponibles pour tous les chargeurs de démarrage qui implémentent la Spécification du chargeur de démarrage[1] et l' Interface du chargeur de démarrage[2], tels que systemd-boot.

set-default ID, set-oneshot ID, set-sysfail ID

Définit l'entrée de chargeur de démarrage par défaut. Prend une chaîne d'ID d'entrée de chargeur de démarrage ou un motif glob comme argument. La commande set-oneshot définira l'entrée par défaut uniquement pour le prochain démarrage, la commande set-default la définira de manière persistante pour tous les futurs démarrages. La commande set-sysfail définira l'entrée de chargeur de démarrage à utiliser en cas de défaillance du système. Les entrées de démarrage de défaillance du système (SysFail) peuvent éventuellement modifier l'ordre de sélection automatique en cas de défaillance, comme une défaillance de mise à jour du firmware de démarrage avec l'état de la défaillance enregistré dans la table système EFI.

bootctl list peut être utilisé pour lister les entrées de chargeur de démarrage disponibles et leurs ID.

De plus, l'ID de l'entrée de chargeur de démarrage peut être spécifié comme l'une des valeurs suivantes : @default, @oneshot ou @current, qui correspondent respectivement à l'entrée de chargeur de démarrage par défaut actuelle pour tous les futurs démarrages, l'entrée de chargeur de démarrage par défaut actuelle pour le prochain démarrage, et l'entrée de chargeur de démarrage actuellement amorcée. Ces ID spéciaux sont résolus aux valeurs actuelles des variables EFI LoaderEntryDefault, LoaderEntrySysFail, LoaderEntryOneShot et LoaderEntrySelected, voir Spécification du chargeur de démarrage[1] pour les détails. Ces ID spéciaux sont principalement utiles comme moyen rapide de rendre l'entrée de chargeur de démarrage actuellement amorcée le choix par défaut de manière persistante, ou de promouvoir l'entrée de chargeur de démarrage par défaut pour le prochain démarrage en entrée de chargeur de démarrage par défaut pour tous les futurs démarrages, mais peuvent être utilisés pour d'autres opérations également.

S'il est défini à @saved , l'entrée choisie sera sauvegardée en tant que variable EFI à chaque démarrage et sélectionnée automatiquement la prochaine fois que le chargeur de démarrage démarre.

Lorsqu'une chaîne vide ("") est spécifiée comme ID, la variable EFI correspondante sera annulée.

Astuce : utiliser systemctl reboot --boot-loader-entry=ID pour redémarrer dans une entrée de démarrage spécifique et systemctl reboot --boot-loader-menu=timeout pour redémarrer une fois dans le menu du chargeur de démarrage. Voir systemctl(1) pour les détails.

Ajouté dans la version 240.

set-timeout TIMEOUT, set-timeout-oneshot TIMEOUT

Définit le délai d'attente du menu du chargeur de démarrage en secondes. La commande set-timeout-oneshot définira le délai d'attente uniquement pour le prochain démarrage. Voir systemd.time(7) pour les détails sur la syntaxe des intervalles de temps.

Si cela est défini à menu-disabled ou menu-hidden ou 0, aucun menu n'est affiché et l'entrée par défaut sera amorcée immédiatement, alors que le fait de définir cela à menu-force désactive le délai d'attente tout en affichant toujours le menu. Lorsqu'une chaîne vide ("") est spécifiée, le chargeur de démarrage reviendra à son délai d'attente de menu par défaut.

Ajouté dans la version 250.

COMMANDES SYSTEMD-BOOT

Ces commandes gèrent le chargeur de démarrage EFI systemd-boot et ne fonctionnent pas en conjonction avec d'autres chargeurs de démarrage.

install

Installe systemd-boot dans la partition système EFI. Une copie de systemd-boot sera stockée en tant que chargeur par défaut/de secours EFI à ESP/EFI/BOOT/BOOT*.EFI. Le chargeur de démarrage est ensuite ajouté en haut de la liste des chargeurs de démarrage du firmware.

Ajouté dans la version 239.

update

Met à jour toutes les versions installées de systemd-boot(7), si la version disponible est plus récente que la version installée dans la partition système EFI. Cela inclut également le chargeur par défaut/de secours EFI à ESP/EFI/BOOT/BOOT*.EFI. Le chargeur de démarrage est ensuite ajouté à la fin de la liste des chargeurs de démarrage du firmware s'il est manquant.

Ajouté dans la version 239.

remove

Supprime toutes les versions installées de systemd-boot de la partition système EFI et de la liste des chargeurs de démarrage du firmware.

Ajouté dans la version 239.

is-installed

Vérifie si systemd-boot est installé dans l' ESP. Notez qu'un ESP unique peut héberger plusieurs chargeurs de démarrage ; cela vérifie donc si systemd-boot est un (parmi peut-être plusieurs) chargeur de démarrage installé — et non s'il est par défaut ni s'il est enregistré dans des variables EFI quelconques.

Ajouté dans la version 243.

random-seed

Génère une graine aléatoire et la stocke dans la partition système EFI (ESP), pour l'utilisation par le chargeur de démarrage systemd-boot . Si une graine aléatoire existe déjà dans l'ESP, elle est rafraîchie. Génère également un 'jeton système' aléatoire et le stocke de manière persistante en tant que variable EFI, s'il n'a pas été défini auparavant. Si le chargeur de démarrage trouve la graine aléatoire dans l'ESP et le jeton système dans la variable il dérivera une graine aléatoire à transmettre au système d'exploitation et une nouvelle graine à stocker dans l'ESP à partir de la combinaison des deux. La graine aléatoire transmise au système d'exploitation est créditée au pool d'entropie du noyau par le gestionnaire de système lors du démarrage précoce, et permet à l'espace utilisateur de démarrer avec un pool d'entropie entièrement initialisé très tôt. Voir aussi systemd-boot-random-seed.service(8).

Voir Random Seeds[3] pour plus d'informations.

Ajouté dans la version 243.

COMMANDES D'IMAGE DE NOYAU

kernel-identify KERNEL-IMAGE

Prend une image de noyau comme argument. Vérifie de quel type est l'image. Renvoie l'un de "uki", "addon", "pe", et "unknown".

Ajouté dans la version 253.

kernel-inspect KERNEL-IMAGE

Prend une image de noyau comme argument. Affiche des détails sur l'image.

Ajouté dans la version 253.

OPTIONS

Les options suivantes sont reconnues :

--esp-path=

Chemin vers la partition système EFI (ESP). Si non spécifié, /efi/, /boot/, et /boot/efi/ sont vérifiés à tour de rôle. Il est recommandé de monter l'ESP sur /efi/, si possible.

--boot-path=

Chemin vers la partition du chargeur de démarrage étendu, telle que définie dans la Spécification du chargeur de démarrage[1]. Si non spécifié, /boot/ est vérifié. Il est recommandé de monter la partition du chargeur de démarrage étendu sur /boot/, si possible.

--root=root

Prend un chemin de répertoire comme argument. Tous les chemins seront préfixés par le chemin de root alternatif donné, y compris les chemins de recherche de configuration.

Ajouté dans la version 252.

--image=image

Prend un chemin vers un fichier d'image disque ou un nœud de périphérique de bloc. Si spécifié, toutes les opérations sont appliquées au système de fichiers dans l'image disque indiquée. Cette option est similaire à --root=, mais opère sur les systèmes de fichiers stockés dans des images disques ou des périphériques de bloc. L'image disque doit contenir soit juste un système de fichiers, soit un ensemble de systèmes de fichiers dans une table de partitions GPT, suivant la Spécification des partitions découvrables[4]. Pour plus d'informations sur les images disques prises en charge, voir systemd-nspawn(1)'s switch of the same name.

Ajouté dans la version 252.

--image-policy=policy

Prend une chaîne de politique d'image comme argument, comme défini dans systemd.image-policy(7). La politique est appliquée lors de l'opération sur l'image disque spécifiée via --image=, voir ci-dessus. Si non spécifié, la valeur par défaut est la politique "*", c'est-à-dire que tous les systèmes de fichiers reconnus dans l'image sont utilisés.

--install-source=

Lors de l'installation de binaires avec --root= ou --image=, sélectionne la source à partir de laquelle les obtenir. Prend l'un de "auto" (par défaut), "image" ou "host". Avec "auto", les binaires seront choisis dans le répertoire ou l'image spécifié, et s'ils ne sont pas trouvés, ils seront choisis depuis l'hôte. Avec "image" ou "host", aucune recherche de secours ne sera effectuée si les binaires ne sont pas trouvés dans la source sélectionnée.

Ajouté dans la version 252.

-p, --print-esp-path

Cette option modifie le comportement de status. Affiche uniquement le chemin vers la partition système EFI (ESP) sur la sortie standard et termine.

Ajouté dans la version 236.

-x, --print-boot-path

Cette option modifie le comportement de status. Affiche uniquement le chemin vers la partition du chargeur de démarrage étendu si elle existe, et sinon le chemin vers l'ESP sur la sortie standard et termine. Cette commande est utile pour déterminer où placer les entrées du chargeur de démarrage, car elles sont de préférence placées dans la partition du chargeur de démarrage étendu si elle existe, et sinon dans l'ESP.

Les entrées de type #1 de la Spécification du chargeur de démarrage doivent généralement être placées dans le répertoire "$(bootctl -x)/loader/entries/". L'existence de ce répertoire peut aussi être utilisée comme indication que le support des entrées du chargeur de démarrage est disponible sur le système. De même, les entrées de type #2 de la Spécification du chargeur de démarrage doivent être placées dans le répertoire "$(bootctl -x)/EFI/Linux/".

Notez que cette option (similairement à l'option --print-esp-path mentionnée ci-dessus), est disponible indépendamment du chargeur de démarrage utilisé, c'est-à-dire aussi sans systemd-boot installé.

Ajouté dans la version 242.

--print-loader-path

Cette option modifie le comportement de status: elle affiche le chemin absolu vers le binaire EFI du chargeur de démarrage utilisé pour le démarrage actuel si cette information est disponible. Notez qu'aucune tentative n'est faite pour vérifier si le binaire existe toujours.

Ajouté dans la version 257.

--print-stub-path

Cette option modifie le comportement de status: elle affiche le chemin absolu vers le binaire EFI UKI/stub utilisé pour le démarrage actuel si cette information est disponible. Notez qu'aucune tentative n'est faite pour vérifier si le binaire existe toujours.

Ajouté dans la version 257.

-R, --print-root-device

Affiche le chemin vers le nœud de périphérique de bloc supportant le système de fichiers racine de l'OS local. Cela affiche un chemin tel que /dev/nvme0n1p5. Si le système de fichiers racine est supporté par dm-crypt/LUKS ou dm-verity, le périphérique de bloc sous-jacent est renvoyé. Si le système de fichiers racine est supporté par plusieurs périphériques de bloc (comme pris en charge par btrfs), l'opération échouera. Si l'option est spécifiée deux fois (c'est-à-dire -RR) et que le périphérique de bloc découvert est un périphérique de partition, le périphérique de bloc "entier" auquel il appartient est déterminé et affiché (par ex. /dev/nvme0n1). Si le système de fichiers racine est "tmpfs" (ou un système de fichiers en mémoire similaire), le périphérique de bloc supportant /usr/ est renvoyé si applicable. Si le système de fichiers racine est un système de fichiers réseau (par ex. NFS, CIFS), l'opération échouera.

Ajouté dans la version 254.

--variables=yes|no

Contrôle s'il faut modifier la liste du chargeur de démarrage du firmware stockée dans les variables EFI, et d'autres variables EFI. Si non spécifié, la valeur par défaut est no lorsqu'une exécution dans un environnement de conteneur est détectée, yes sinon.

Ajouté dans la version 258.

--random-seed=yes|no

Par défaut, la commande install initialise un fichier de graine aléatoire dans l'ESP. Lors de la création d'une image, il peut être souhaitable de désactiver cela afin d'éviter d'avoir la même graine dans toutes les instances.

Ajouté dans la version 257.

--graceful

Ignore l'échec lorsque la partition système EFI ne peut pas être trouvée, lorsque les variables EFI ne peuvent pas être écrites, ou qu'un chargeur de démarrage différent ou plus récent est déjà installé. Actuellement s'applique uniquement aux verbes is-installed, update, random-seed et install . Depuis la version v258, elle est activée implicitement lors de l'exécution à l'intérieur d'un chroot.

Ajouté dans la version 244.

-q, --quiet

Supprime l'affichage des résultats des différentes commandes et aussi les indications sur l'indisponibilité de l'ESP.

Ajouté dans la version 251.

--make-entry-directory=yes|no

Contrôle la création et la suppression du répertoire d'entrées de type #1 de la Spécification du chargeur de démarrage[1] sur le système de fichiers contenant des ressources telles que les images de noyau et d'initrd pendant install et removerespectivement. Le répertoire est nommé d'après le jeton d'entrée, tel que spécifié avec le paramètre --entry-token= décrit ci-dessous, et est placé immédiatement sous le répertoire racine $BOOT (c'est-à-dire sous le système de fichiers renvoyé par l'option --print-boot-path , voir ci-dessus). La valeur par défaut est "no".

Ajouté dans la version 251.

--entry-token=

Contrôle comment nommer et identifier les entrées du chargeur de démarrage pour cette installation d'OS. Accepté pendant install, et prend l'un de "auto", "machine-id", "os-id", "os-image-id" ou une chaîne arbitraire préfixée par "literal:" comme argument.

Si défini à machine-id les entrées sont nommées d'après l'ID de machine du système en cours d'exécution (par ex. "b0e793a9baf14b5fa13ecbe84ff637ac"). Voir machine-id(5) pour plus de détails sur le concept et le fichier de l'ID de machine.

Si défini à os-id les entrées sont nommées d'après l'ID de l'OS du système en cours d'exécution, c'est-à-dire le champ ID= de os-release(5) (par ex. "fedora"). De même, si défini à os-image-id les entrées sont nommées d'après l'ID de l'image OS du système en cours d'exécution, c'est-à-dire le champ IMAGE_ID= de os-release (par ex. "vendorx-cashier-system").

Si défini à auto (par défaut), le fichier /etc/kernel/entry-token sera lu s'il existe, et la valeur stockée sera utilisée. Sinon, si l'ID de machine local est initialisé, il est utilisé. Sinon, IMAGE_ID= de os-release sera utilisé, s'il est défini. Sinon, ID= de os-release sera utilisé, s'il est défini.

Sauf s'il est défini à "machine-id", ou lorsque --make-entry-directory=yes est utilisé, la chaîne de jeton sélectionnée est écrite dans un fichier /etc/kernel/entry-token, pour s'assurer qu'elle sera utilisée pour les futures entrées. Ce fichier est aussi lu par kernel-install(8), afin d'identifier sous quel nom générer les entrées du chargeur de démarrage pour les noyau nouvellement installés, ou pour déterminer les noms d'entrées pour en supprimer d'anciennes.

Utiliser l'ID de machine pour nommer les entrées est généralement préférable, cependant il y a des cas où utiliser les autres identifiants est une bonne option. Spécifiquement : si les données d'identification que l'ID de machine implique ne doivent pas être stockées sur la partition $BOOT (non chiffrée), ou si l'ID doit être généré au premier démarrage et n'est pas connu lorsque les entrées sont préparées. Notez que utiliser l'ID de machine a l'avantage que plusieurs installations parallèles du même OS peuvent coexister sur le même support, et qu'elles peuvent mettre à jour leurs entrées du chargeur de démarrage indépendamment. Lorsqu'un autre identifiant est utilisé (tel que l'ID de l'OS ou l'ID de l'image OS), les installations parallèles du même OS essaieraient d'utiliser le même nom d'entrée. Pour prendre en charge les installations parallèles, l'installateur doit utiliser un jeton d'entrée différent lors de l'ajout d'une seconde installation.

Ajouté dans la version 251.

--all-architectures

Installe les binaires pour toutes les architectures EFI prises en charge (ce qui implique --variables=no).

Ajouté dans la version 252.

--efi-boot-option-description=

Description de l'entrée ajoutée à la liste des options de démarrage du firmware. La valeur par défaut esto "Linux Boot Manager".

L'utilisation du nom d'entrée par défaut "Linux Boot Manager" est généralement préférable, car seul un chargeur de démarrage installé sur une seule partition ESP doit être utilisé pour démarrer un nombre quelconque d'installations d'OS trouvées sur les différents disques installés dans le système. Plus précisément, les distributions ne devraient pas utiliser cette option pour installer une entrée de marque dans la liste des options de démarrage. Cependant, dans les situations avec plusieurs disques, chacun avec sa propre partition ESP, il peut être utile de faciliter l'identification du chargeur de démarrage utilisé dans le menu des options de démarrage du micrologiciel.

Ajouté dans la version 252.

--dry-run

Exécution à blanc pour unlink et cleanup.

En mode d'exécution à blanc, les opérations unlink et cleanup se contentent d'afficher les fichiers qui seraient supprimés sans les supprimer réellement.

Ajouté dans la version 253.

--secure-boot-auto-enroll=yes|no, --private-key=CHEMIN/URI, --private-key-source=TYPE[:NOM], --certificate=CHEMIN, --certificate-source=TYPE[:NOM]

Configure l'ESP pour l'inscription automatique du Secure Boot lors de l'invocation de la commande install . Prend un argument booléen. Désactivé par défaut. L'activation de cette option fera en sorte que bootctl remplisse l'ESP avec des bases de signatures "PK", "KEK" et "db" signées, chacune contenant le certificat donné au format "DER" comme seule entrée. Ces bases de signatures Secure Boot seront récupérées et inscrites par systemd-boot si le Secure Boot est en mode de configuration et si l'inscription automatique du Secure Boot est activée.

Lors de la spécification de cette option, un certificat et une clé privée doivent également être fournis à l'aide des options --certificate= et --private-key= . L'option --certificate= prend un chemin vers un certificat X.509 encodé PEM ou une URI qui est transmise au fournisseur OpenSSL configuré avec --certificate-source qui prend "file" ou "provider", ce dernier étant suivi d'un identifiant de fournisseur spécifique, séparé par deux points, par exemple "provider:pkcs11". L'option --private-key= peut prendre un chemin ou une URI qui sera transmise au moteur ou au fournisseur OpenSSL, comme spécifié par --private-key-source= sous la forme d'un tuple "type:nom", tel que "engine:pkcs11". Le moteur ou le fournisseur de signature OpenSSL spécifié sera utilisé pour signer les listes de signatures EFI.

Ajouté dans la version 257.

--no-pager

Ne pas acheminer la sortie dans un visualiseur.

--json=MODE

Affiche la sortie formatée en JSON. Attend l'un de "short" (pour la sortie la plus courte possible sans espaces blancs ou sauts de ligne superflus), "pretty" (pour une version mise en forme de la même sortie, avec indentation et sauts de ligne) ou "off" (pour désactiver la sortie JSON, par défaut).

-h, --help

Affiche un court texte d'aide et se termine.

--version

Affiche une courte chaîne de version et se termine.

FICHIERS .EFI SIGNÉS

bootctl install et update rechercheront d'abord un fichier systemd-boot se terminant par le suffixe ".efi.signed" et le copieront à la place du fichier ".efi" normal. Cela permet aux distributions ou aux utilisateurs finaux de fournir des images signées pour le Secure Boot UEFI.

CODE DE SORTIE

En cas de succès, 0 est retourné, sinon un code d'échec non nul. bootctl --print-root-device retourne le code de sortie 80 si le système de fichiers racine n'est pas soutenu par un seul périphérique de bloc, et d'autres codes de sortie non nuls pour d'autres erreurs.

ENVIRONNEMENT

Si $SYSTEMD_RELAX_ESP_CHECKS=1 est défini, les contrôles de validation pour l'ESP sont assouplis, et le chemin spécifié avec --esp-path= peut faire référence à n'importe quel type de système de fichiers sur n'importe quel type de partition.

De même, $SYSTEMD_RELAX_XBOOTLDR_CHECKS=1 désactive certains contrôles de validation pour la partition Extended Boot Loader.
