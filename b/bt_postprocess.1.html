DESCRIPTIO

N

Quand btparse analyse une entrée BibTeX, il stocke initialement les résultats dans un arbre de syntaxe abstraite (AST), sous une forme qui reflète exactement les données analysées. Par exemple,

l'entrée 
@Article{Jones:1997a,
  AuThOr = "Bob   Jones" # and # "Jim Smith ",
  TITLE = "Feeding Habits of
           the Common Cockroach",
  JoUrNaL = j_ent,
  YEAR = 1997
}

serait analysée en un AST qui pourrait être représenté comme suit

: 
(entry,"Article")
  (key,"Jones:1997a")
  (field,"AuThOr")
    (string,"Bob   Jones")
    (macro,"and")
    (string,"Jim Smith ")
  (field,"TITLE")
    (string,"Feeding Habits of               the Common Cockroach")
  (field,"JoUrNaL")
    (macro,"j_ent")
  (field,"YEAR")
    (number,
"1997")

L'avantage de cette forme est que toutes les informations importantes de l'entrée sont facilement accessibles en parcourant l'arbre à l'aide des fonctions décrites dans bt_traversal. Le problème évident est que les données sont un peu trop brutes pour être immédiatement utiles : les types d'entrées et les noms de champs sont capitalisés de manière incohérente, les chaînes sont pleines d'espaces indésirables, les valeurs de champ ne sont pas réduites à une seule chaîne,

etc.

Tous ces problèmes sont traités par les fonctions de post-traitement de btparse, décrites ici. Normalement, vous n'aurez pas à appeler ces fonctions --- la bibliothèque fait la bonne chose pour vous après l'analyse de chaque entrée, et vous pouvez personnaliser ce qu'est exactement la bonne chose pour votre application. (Par exemple, vous pouvez lui dire d'étendre les macros, mais pas de concaténer les sous-chaînes ensemble.) Cependant, il est concevable que vous souhaitiez déplacer le post-traitement dans votre propr

e code et hors du contrôle de la bibliothèque. Plus probablement, vous pourriez avoir des chaînes qui proviennent d'autre chose que des fichiers BibTeX et que vous aimeriez traiter comme des chaînes BibTeX ; pour cette situation, les fonctions
de post-traitement sont essentielles. Enfin, vous pourriez simplement être curieux de savoir ce qui arrive exactement à vos données après leur analyse. Si c'est le cas, vous êtes au bon endroit pour des explications détaillées à l'extrême.

FONCTION

S

btparse offre quatre points d'entrée vers son code de post-traitement. Parmi ceux-ci, probablement seulement le premier et le dernier --- pour le traitement de chaînes individuelles et d'entrées entières --- seront couramment

utilisés.

Points d'entrée de

post-traitement

Pour comprendre pourquoi quatre points d'entrée sont offerts, une explication de l'AST d'exemple montré ci-dessus aidera. Tout d'abord, l'entrée entière est représentée par le nœud "(entry,"Article")" ; ce nœud a la clé de l'entrée et toutes ses paires champ/valeur comme enfants. Les nœuds d'entrée sont retournés par bt_parse_entry() et bt_parse_entry_s() (voir bt_input) ainsi que bt_next_entry() (qui parcourt une liste d'entrées retournées par bt_parse_file() --- voir bt_traversal). Des entrées entières peuvent être post-traitées avec bt_postprocess_

entry().

Vous pourriez aussi avoir besoin de post-traiter un champ individuel, ou seulement la valeur qui lui est associée. (La différence est que le traitement du champ peut changer le nom du champ --- par exemple en minuscules --- en plus de la valeur du champ.) Le nœud "(field,"AuThOr")" ci-dessus est un exemple d'un sous-AST de champ, et "(string,"Bob Jones")" est le premier nœud de la liste de valeurs simples représentant la valeur de ce champ. (Rappelez-vous qu'une valeur de champ est, en général, une liste de valeurs simples.) Les nœuds de champ sont retournés par bt_next_field(), les nœuds de valeur par bt_next_value(). Les premiers peuvent être passés à bt_postprocess_field() pour le post-traitement, les seconds à bt_postprocess_

value().

Enfin, des chaînes individuelles peuvent arriver dans votre programme de nombreux endroits autres qu'un AST btparse. Pour cette raison, bt_postprocess_string() est disponible pou

r post-traiter des
chaînes arbitraires.

Options de

post-traitement

Toutes les routines de post-traitement ont un paramètre "options", que vous pouvez utiliser pour ajuster finement le post-traitement. (C'est juste comme les options de traitement de chaînes par méta-type que vous pouvez définir avant d'analyser des entrées ; voir bt_set_stringopts() dans bt_input.) Comme ailleurs dans la bibliothèque, "options" est un bitmap construit en combinant par un ou logique diverses constantes prédéfinies. Ces constantes et leurs effets sont documentées dans "String processing option macros" dans

btparse.

Post-traite une chaîne individuelle, "s", qui est modifiée sur place. La seule option de post-traitement qui a du sens sur des chaînes individuelles est de savoir s'il faut réduire les espaces selon les règles BibTeX ; ainsi, si "options & BTO_COLLAPSE" est faux, cette fonction n'a aucun effet. (Bien qu'elle fasse quand même un passage complet sur la chaîne. C'est pour une future expansion.

)

Les règles exactes pour réduire les espaces sont simples : les caractères d'espacement non-espace (principalement les tabulations et les retours à la ligne) sont convertis en espace, toutes les chaînes de plus d'un espace à l'intérieur sont réduites à un seul espace, et tous les espaces de début ou de fin sont supprimés. (Le fait de s'assurer que tout l'espacement est des espaces est en fait fait par le scanner lexical de btparse, donc les chaînes dans les AST de btparse n'auront jamais d'espacement à part les espaces. De même, toute chaîne passée à bt_postprocess_string() ne devrait pas contenir

de caractères d
'espacement non-espace.)

bt_postprocess(1)

btparse, version 0.91

2025-07-14

NAME

bt_postprocess, bt_postprocess_value, bt_postprocess_field, bt_postprocess_entry - post-process parsed BibTeX data

SYNOPSIS

bt_postprocess_value (AST *value, btshort options, boolean replace);
bt_postprocess_field (AST *field, btshort options, boolean replace);
bt_postprocess_entry (AST *entry, btshort options);

DESCRIPTION

These functions provide ways to canonicalize values from a parsed BibTeX file. They are intended to be used after the file has been parsed, to clean up the values (e.g. expanding macros, collapsing whitespace, converting numbers to strings).

The core of the post-processing logic is in bt_postprocess_value. The other functions are convenience wrappers around it.

BTO_OPTIONS

The options argument is a bitmask specifying which operations to perform. The possible bits are:

BTO_CONVERT
Convert numbers to strings. (This is pretty trivial, just changing the node type.)
BTO_EXPAND
Expand any macros. This means replacing macro references with their definitions. This is done recursively, so macros defined in terms of other macros will also be expanded.
BTO_PASTE
Concatenate adjacent string literals and macro expansions. For example, (string, "hello") (macro, "there") (string, "!") would become (string, "hello there!").
BTO_COLLAPSE
Collapse sequences of whitespace characters (spaces, tabs, newlines) into a single space. This is intended to happen *after* macros have been expanded and adjacent strings have been pasted together.

FUNCTIONS

bt_postprocess_value ()
AST * bt_postprocess_value (AST *   value,
                                 btshort options,
                                 boolean replace);

This is the main workhorse. It takes a pointer to the sub-AST representing the value to be processed, a bitmask of options, and a boolean flag. If replace is true, the original AST is modified in-place. If false, a new AST is created and returned.

The return value is a pointer to the fully processed value. If replace is true, this will be the same as the input value. If replace is false, it will be a newly allocated AST node (or possibly a pointer to an existing node if no changes were necessary).

If the value is a list of elements and the BTO_PASTE option is set, but the list contains non-string/non-macro elements (e.g. numbers, or other lists), then BTO_PASTE is ignored for that list. If the value is a list and BTO_PASTE is not specified, then each element in the list is processed recursively, but the list itself is not modified (except that its elements might be replaced if replace is true).

If the value is a list and BTO_PASTE is specified, and all elements are strings or macros, then the list is converted into a single string element, containing the pasted, expanded, and potentially whitespace-collapsed value. If the list was empty, an empty string is returned. If the original list had only one element, that element is returned (after recursive processing). Only when the original list had two or more elements will the result be a single string element.

If a list was processed without BTO_PASTE, the last string in the list is returned (after processing).

Consider what might be done to the value of the "author" field in the above example, which is the concatenation of a string, a macro, and another string. Assume that the macro "and" expands to " and ", and that the variable "value" points to the sub-AST for this value. The original sub-AST corresponding to this value is

(string,"Bob   Jones")
(macro,"and")
(string,"Jim Smith ")

To fully process this value in-place, you would call

bt_postprocess_value (value, BTO_FULL, TRUE);

This would convert the value to a single-element list,

(string,"Bob Jones and Jim Smith")

and return the fully-processed string "Bob Jones and Jim Smith". Note that the "and" macro has been expanded, interpolated between the two literal strings, everything pasted together, and finally whitespace collapsed. (Collapsing whitespace before concatenating the strings would be a bad idea.)

(Incidentally, "BTO_FULL" is just a macro for the combination of all possible string-processing options, currently:

BTO_CONVERT | BTO_EXPAND | BTO_PASTE | BTO_COLLAPSE

There are two other similar shortcut macros: "BTO_MACRO" to express the special string-processing done on macro values, which is the same as "BTO_FULL" except for the absence of "BTO_COLLAPSE"; and "BTO_MINIMAL", which means no string-processing is to be done.)

Let's say you'd rather preserve the list nature of the value, while expanding macros and converting any numbers to strings. (This conversion is trivial: it just changes the type of the node from "BTAST_NUMBER" to "BTAST_STRING". "Number" values are always stored as a string of digits, just as they appear in the file.) This would be done with the call

bt_postprocess_value
       (value, BTO_CONVERT|BTO_EXPAND|BTO_COLLAPSE,TRUE);

which would change the list to

(string,"Bob Jones")
(string,"and")
(string,"Jim Smith")

Note that whitespace is collapsed here before any concatenation can be done; this is probably a bad idea. But you can do it if you wish. (If you get any ideas about cooking up your own value post-processing scheme by doing it in little steps like this, take a look at the source to bt_postprocess_value(); it should dissuade you from such a venture.)

bt_postprocess_field ()
char * bt_postprocess_field (AST *   field,
                                 btshort  options,
                                 boolean replace);

This is little more than a front-end to bt_postprocess_value(); the only difference is that you pass it a "field" AST node (eg. the "(field,"AuThOr")" in the above example), and that it transforms the field name in addition to its value. In particular, the field name is forced to lowercase; this behaviour is (currently) not optional.

Returns the string returned by bt_postprocess_value().

bt_postprocess_entry ()
void bt_postprocess_entry (AST *  entry,
                               btshort options);

Post-processes all values in an entry. If "entry" points to the AST for a "regular" or "macro definition" entry, then the values are just what you'd expect: everything on the right-hand side of a field or macro "assignment." You can also post-process comment and preamble entries, though. Comment entries are essentially one big string, so only whitespace collapsing makes sense on them. Preambles may have multiple strings pasted together, so all the string-processing options apply to them. (And there's nothing to prevent you from using macros in a preamble.)
