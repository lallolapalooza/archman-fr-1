bdep-new(1)

Paquet: build2

bdep-new(1) Manuel des commandes générales bdep-new(1)

NOM

bdep-new - créer et initialiser un nouveau projet

SYNTAXE

bdep new [options] [--no-init] spécification [nom]
bdep new [options] --config-add|-A rép-cfg [@nom-cfg] spécification [nom]
bdep new [options] --config-create|-C rép-cfg [@nom-cfg] spécification [nom]
         [args-cfg]
bdep new [options] --package [spéc-prj] spécification [nom]
bdep new [options] --source [spéc-prj] spécification [nom]

spécification     = [langage] [type] [vcs]
langage     = --lang|-l (c|c++)[,opts-lang...]
type     = --type|-t (exe|lib|bare|empty)[,opts-type...]
vcs      = --vcs|-s (git|none)[,opts-vcs...]
spéc-prj = --directory|-d rép-prj
args-cfg = [-- [opts-bpkg]] [--existing|-e | (module | var-cfg)...]

DESCRIPTION

La commande new crée et initialise un nouveau projet (les trois premières formes), un nouveau paquet dans un projet déjà existant (la forme --package), ou un nouveau sous-répertoire source dans un projet/paquet déjà existant (la forme --source). Toutes les formes sauf --source créent d'abord, selon la spécification, un nouveau projet build2 appelé nom dans le sous-répertoire nom du répertoire de travail courant (sauf si remplacé avec --output-dir|-o ou, dans le cas de --package, avec --directory|-d). Si nom contient un composant de répertoire, alors le projet/paquet est créé dans ce répertoire, comme s'il avait été spécifié avec --output-dir|-o.

La première forme, sauf si l'option --no-init est spécifiée, initialise ensuite une base de données de projet vide comme si la commande bdep-init(1) avait été exécutée avec l'option --empty. Par exemple :

$ bdep new -l c++ -t exe hello
$ tree hello/
hello/
|-- hello/
|   |-- hello.cxx
|   `-- buildfile
|-- buildfile
`-- manifest

De même, la deuxième et la troisième forme ajoutent une configuration de build existante ou en créent une nouvelle, puis initialisent le projet dans cette configuration comme si la commande bdep-init(1) avait été exécutée avec l'option --config-add ou --config-create, respectivement. Par exemple :

$ bdep new -l c++ -t exe -C @gcc hello cc config.cxx=g++

La forme --package ajoute le nouveau paquet au fichier packages.manifest, le créant si nécessaire. Si aucun répertoire de projet n'est explicitement spécifié avec --directory|-d, alors il sera déduit du répertoire de travail courant (voir bdep-projects-configs(1) pour les détails sur la spécification des projets). Notez que les paquets imbriqués ne sont pas autorisés. Par exemple :

$ bdep new -t empty hello
$ cd hello
$ bdep new --package -l c++ -t lib libhello
$ bdep new --package -l c++ -t exe hello
$ bdep init -C @gcc cc config.cxx=g++
$ cd ..
$ tree hello/
hello/
|-- hello/
|   |-- hello/
|   |   |-- hello.cxx
|   |   `-- buildfile
|   |-- buildfile
|   `-- manifest
|-- libhello/
|   |-- libhello/
|   |   |-- hello.hxx
|   |   |-- hello.cxx
|   |   `-- buildfile
|   |-- buildfile
|   `-- manifest
`-- packages.manifest

La forme --source fonctionne *comme si* elle créait d'abord, selon la spécification, un projet temporaire nommé nom, puis copiait son sous-répertoire source (par défaut nom/nom/) dans le répertoire de travail courant (sauf si remplacé avec --output-dir|-o). Si aucun répertoire de projet/paquet n'est explicitement spécifié avec --directory|-d, alors le répertoire de travail courant est supposé. Par exemple :

$ bdep new -l c++ -t bare hello
$ cd hello
$ bdep new --source -l c++ -t lib libhello
$ bdep new --source -l c++ -t exe hello
$ bdep init -C @gcc cc config.cxx=g++
$ cd ..
$ tree hello/
hello/
|-- hello/
|   |-- hello.cxx
|   `-- buildfile
|-- libhello/
|   |-- hello.hxx
|   |-- hello.cxx
|   `-- buildfile
|-- buildfile
`-- manifest

Dans toutes les formes, si nom est omis, alors le nom du répertoire de travail courant (sauf si remplacé avec --output-dir|-o) est utilisé comme nom du sous-répertoire projet/paquet/source. Voir Nom de paquet (#nom-paquet) pour les détails sur les noms de projet/paquet.

Le sous-répertoire source peut être personnalisé avec la sous-option de type de projet subdir (voir ci-dessous pour les détails). Par exemple :

$ bdep new -l c++ -t lib,subdir=libhello/io libhello-io
$ tree libhello-io/
libhello-io/
`-- libhello/
    `-- io/
        |-- hello-io.hxx
        `-- hello-io.cxx

Par défaut, le sous-répertoire source est créé dans le répertoire racine du projet/paquet et contient à la fois les en-têtes (y compris les en-têtes publics pour les bibliothèques) ainsi que les sources. Ceci peut être personnalisé de plusieurs manières en utilisant les sous-options prefix* et split (voir ci-dessous pour les détails). Par exemple, pour déplacer le sous-répertoire source à l'intérieur de src/ :

$ bdep new -l c++ -t exe,prefix=src hello
$ tree hello/
hello/
`-- src/
    `-- hello/
        `-- hello.cxx

Et pour diviser le sous-répertoire source de la bibliothèque en en-têtes publics et autres fichiers source :

$ bdep new -l c++ -t lib,split libhello
$ tree libhello/
libhello/
|-- include/
|   `-- libhello/
|       `-- hello.hxx
`-- src/
    `-- libhello/
        `-- hello.cxx

Voir la section MISE EN PAGE SOURCE ci-dessous pour les détails et plus d'exemples.

Le répertoire de sortie peut déjà contenir des fichiers existants à condition qu'ils n'entrent pas en conflit avec les fichiers à créer. La commande new reconnaît également certains fichiers bien connus et tente d'utiliser les informations extraites dans le fichier manifest du paquet. Plus précisément, elle essaie de deviner la licence à partir du fichier LICENSE ainsi que d'extraire le résumé de README.md. Ceci permet le flux de travail suivant :

# Créer un projet avec LICENSE et README.md sur l'un des services
# d'hébergement Git (GitHub, GitLab, etc.).
$ git clone .../libhello.git
$ cd libhello
$ bdep new -l c++ -t lib

Le projet, le paquet ou le sous-répertoire source créé peut être personnalisé davantage à l'aide des hooks pré et post-création spécifiés avec les options --pre-hook et --post-hook, respectivement. Les hooks pré sont exécutés avant que tout nouveau fichier ne soit créé et le hook post – après que tous les fichiers aient été créés. Les commandes des hooks sont exécutées dans le répertoire du projet, du paquet ou source comme leur répertoire de travail courant. Par exemple

: 
$ bdep new --post-hook "echo .idea/ >>.gitignore"
hello

Les hooks pré sont principalement utiles pour déplacer/renommer des fichiers existants qui entreraient autrement en conflit avec des fichiers créé par la commande new. Par exemple :

$ bdep new --pre-hook  "mv .gitignore .gitignore.bak" \
           --post-hook "cat .gitignore.bak >>.gitignore" \
           --post-hook "rm .gitignore.bak" ...

Voir la documentation des options --pre-hook et --post-hook ci-dessous pour plus de détails.

NOUVELLES OPTIONS

--no-init
N'initialise pas un ensemble de configuration de build vide.
--package
Crée un nouveau package à l'intérieur d'un projet déjà existant plutôt qu'un nouveau projet.
--source
Crée un nouveau sous-répertoire source à l'intérieur d'un projet ou package déjà existant plutôt qu'un nouveau projet.
--output-dir|-o dir
Crée le projet, le package ou le sous-répertoire source dans le répertoire spécifié.
--directory|-d dir
Suppose que le projet/package se trouve dans le répertoire spécifié plutôt que dans le répertoire de travail actuel. Utilisé uniquement avec --package ou --source.
--type|-t type[,opt...]
Spécifie le type de projet et les options. Les valeurs valides pour type sont exe (projet exécutable, par défaut), lib (projet bibliothèque), bare (projet nu sans code source) et empty (projet vide prêt à être rempli de packages). Les valeurs valides pour opt sont spécifiques au type.
--lang|-l lang[,opt...]
Spécifie le langage du projet et les options. Les valeurs valides pour lang sont c et c++ (par défaut). Les valeurs valides pour opt sont spécifiques au langage.
--vcs|-s vcs[,opt...]
Spécifie le système de contrôle de version du projet et les options. Les valeurs valides pour vcs sont git (par défaut) et none. Les valeurs valides pour opt sont spécifiques au système.
--pre-hook command
--post-hook command
Exécute la commande spécifiée avant/après la création du projet, du package ou du répertoire source.

La valeur de command est interprétée comme une ligne de commande séparée par des espaces, potentiellement entre guillemets, composée d'un programme ou d'une commande intégrée portable (testscript#builtins) éventuellement suivie d'arguments et de redirections. Spécifiquement, un seul niveau de guillemets (simples ou doubles) est supprimé et les espaces ne sont pas traités comme des séparateurs à l'intérieur de tels fragments entre guillemets. Actuellement, seule la redirection stdout vers un fichier est prise en charge. Par exemple :

$ bdep new --post-hook "echo '.idea/ # IDE' >>.gitignore" hello

Les éléments de la ligne de commande (programme, arguments, etc.) peuvent éventuellement contenir des substitutions – noms de variables entourés du symbole de substitution @ – qui sont remplacés par les valeurs de variables correspondantes pour produire la commande réelle. Les noms de variables suivants sont reconnus, le double symbole de substitution (@@) servant de séquence d'échappement.

@mode@ - l'un de 'project', 'package', ou 'source'
@name@ - nom du projet, du package ou du sous-répertoire source
@base@ - base du nom (nom sans extension)
@stem@ - tige du nom (base du nom sans le préfixe 'lib')
@root@ - répertoire racine du projet/package
@pfx@  - préfixe combiné relatif à la racine du projet/package
@inc@  - préfixe d'en-tête divisé relatif à la racine du projet/package
@src@  - préfixe source divisé relatif à la racine du projet/package
@sub@  - sous-répertoire source relatif au préfixe d'en-tête/source
@type@ - type (--type|-t valeur : 'exe', 'lib', etc.)
@lang@ - langage (--lang|-l valeur : 'c', 'c++', etc.)
@vcs@  - système de contrôle de version (--vcs|-s valeur : 'git', etc.)

Notez que les variables @inc@ et @src@ ne sont définies que si le préfixe d'en-tête/source est divisé avec la variable combinée @pfx@, sinon celle-ci est définie.

Par exemple :

$ bdep new --post-hook "echo bin/ >>@name@/.gitignore" hello

Ces variables de substitution sont également mises à la disposition du programme de hook sous forme de variables d'environnement BDEP_NEW_* (BDEP_NEW_MODE, BDEP_NEW_NAME, etc.).

--no-amalgamation

STRUCTURE SOURCE

Les projets C et C++ emploient une variété déroutante de structures de code source dont la plupart entrent dans deux classes générales : combinée, où tout le so

urce code for a single executable or library resides in the same directory and split, where headers (typically public headers of a library) and other source files reside in separate directories (most commonly called include/ and src/

).

To support the creation of such varying layouts the new command divides paths leading to source code inside a package/project into a number of customizable

components: 
libhello/{include,src}/hello/
    ^         ^          ^
    |         |          |
 project/   source    source
 package    prefix  subdirectory
root

Note that while the same physical layout can be achieved with various combinations of source prefix and subdirectory, there will be differences in semantics since the headers in the project are included with the source subdirectory (if any) as a prefix. See Canonical Project Structure (intro#proj-struct) for rationale and

details.

As we have already seen, the source subdirectory can be customized with the subdir project type sub-option. For

example: 
# libhello/hello/
$ bdep new -l c++ -t lib,subdir=hello libhello
$ tree libhello/
libhello/
`-- hello/
    |-- hello.hxx
    `-- hello.
cxx

Note: pass -l c++,cpp if you prefer the .hpp/.cpp source file naming

scheme.

The source prefix can be combined, in which case it can be customized with the single prefix project type sub-option. For

example: 
# hello/src/hello/
$ bdep new -l c++ -t exe,prefix=src hello
$ tree hello/
hello/
`-- src/
    `-- hello/
        `-- hello.
cxx

The prefix can also be split, in which case the prefix-include and prefix-source sub-options can be used to customize the respective directories independently. If either is omitted, then the corresponding prefix is left empty. For

example: 
# libhello/{include,.}/libhello/
$ bdep new -l c++ -t lib,prefix-include=include libhello
$ tree libhello/
libhello/
|-- include/
|   `-- libhello/
|       `-- hello.hxx
`-- libhello/
    `-- hello.
cxx

The split sub-option is a convenient shortcut for the most common case where the header prefix is include/ and source prefix is src/. For

example: 
# libhello/{include,src}/libhello/
$ bdep new -l c++ -t lib,split libhello
$ tree libhello/
libhello/
|-- include/
|   `-- libhello/
|       `-- hello.hxx
`-- src/
    `-- libhello/
        `-- hello.
cxx

The source subdirectory can be omitted by specifying the no-subdir project type sub-option. For

example: 
# hello/src/
$ bdep new -l c++ -t exe,prefix=src,no-subdir hello
$ tree hello/
hello/
`-- src/
    `-- hello.
cxx

The same but for the split layout (we also have to disable the generated version header that is not supported in this layout)

: 
# libhello/{include,src}/
$ bdep new -l c++ -t lib,split,no-subdir,no-version libhello
$ tree libhello/
libhello/
|-- include/
|   `-- hello.hxx
`-- src/
    `-- hello.
cxx

To achieve the layout where all the source code resides in the project root, we omit both the source prefix and subdirectory (we also have to disable a couple of other features that are not supported in this layout)

: 
# hello/
$ bdep new -l c++ -t lib,no-subdir,no-version,no-tests libhello
$ tree libhello/
libhello/
|-- hello.cxx
`-- hello.
hxx

We can also omit the source subdirectory but only in the source prefix of the split layout by specifying the no-subdir-source sub-option. For

example: 
# libhello/{include/hello,src}/
$ bdep new -l c++ -t lib,split,subdir=hello,no-subdir-source libhello
$ tree libhello/
libhello/
|-- include/
|   `-- hello/
|       `-- hello.hxx
`-- src/
    `-- hello.
cxx

Similarly, we can also omit the source subdirectory but only in the header prefix of the split layout by specifying the no-subdir-include sub-option (we also have to disable the generated version header that is not supported in this layout)

: 
# libhello/{include,src/hello}/
$ bdep new                                                         \
  -l c++                                                           \
  -t lib,split,subdir=hello,no-subdir-include,no-version           \
  libhello
$ tree libhello/
libhello/
|-- include/
|   `-- hello.hxx
`-- src/
    `-- hello/
        `-- hello.
cxx

To achieve the split layout where the include/ directory is inside src/

: 
# libhello/src/{include,.}/hello/
$ bdep new                                                         \
  -l c++                                                           \
  -t lib,prefix-include=src/include,prefix-source=src,subdir=hello \
  libhello
$ tree libhello/
libhello/
`-- src/
    |-- include/
    |   `-- hello/
    |       `-- hello.hxx
    `-- hello/
        `-- hello.
cxx

A similar layout but without the source subdirectory in src/

: 
# libhello/src/{include/hello,.}/
$ bdep new                                                         \
  -l c++                                                           \
  -t lib,prefix-include=src/include,prefix-source=src,\
subdir=hello,no-subdir-source                                      \
  libhello
$ tree libhello/
libhello/
`-- src/
    |-- include/
    |   `-- hello/
    |       `-- hello.hxx
    `-- hello.
cxx

The layout used by the Boost

libraries: 
# libhello/{include/hello,libs/hello/src}/
$ bdep new                                                         \
  -l c++                                                           \
  -t lib,prefix-include=include,prefix-source=libs/hello/src,\
subdir=hello,no-subdir-source                                      \
  libhello
$ tree libhello/
libhello/
|-- include/
|   `-- hello/
|       `-- hello.hxx
`-- libs/
    `-- hello/
        `-- src/
            `-- hello.
cxx

A layout where multiple components each have their own include/src

split: 
# hello/libhello1/{include/hello1,src}/
# hello/libhello2/{include/hello2,src}/
$ bdep new -l c++ -t bare hello
$ bdep new -d hello --source                                       \
  -l c++                                                           \
  -t lib,\
prefix-include=libhello1/include,prefix-source=libhello1/src,\
subdir=hello1,no-subdir-source                                     \
  libhello1
$ bdep new -d hello --source                                       \
  -l c++                                                           \
  -t lib,\
prefix-include=libhello2/include,prefix-source=libhello2/src,\
subdir=hello2,no-subdir-source                                     \
  libhello2
$ tree hello/
hello/
|-- libhello1/
|   |-- include/
|   |   `-- hello1/
|   |       `-- hello1.hxx
|   `-- src/
|       `-- hello1.cxx
`-- libhello2/
    |-- include/
    |   `-- hello2/
    |       `-- hello2.hxx
    `-- src/
        `-- hello2.
cxx

A layout where libraries and executables have different

prefixes: 
# hello/libs/libhello/{include/hello,src}/
# hello/src/hello/
$ bdep new -l c++ -t bare hello
$ bdep new -d hello --source                                       \
  -l c++                                                           \
  -t lib,\
prefix-include=libs/libhello/include,prefix-source=libs/libhello/src,\
subdir=hello,no-subdir-source                                      \
  libhello
$ bdep new -d hello --source -l c++ -t exe,prefix=src hello
$ tree hello/
hello/
|-- libs/
|   `-- libhello/
|       |-- include/
|       |   `-- hello/
|       |       `-- hello.hxx
|       `-- src/
|           `-- hello.cxx
`-- src/
    `-- hello/
        `-- hello.
cxx

When packaging a third-party project for build2, one of the common approaches is to create a project with the split layout and the buildfiles in the source prefix directories rather than in the source

subdirectories: 
# hello/libhello/{include,src}/hello/
# hello/libhello/{include,src}/buildfile
$ bdep new -l c -t empty hello
$ bdep new -d hello --package                                      \
  -l c                                                             \
  -t lib,                                                          \
split,subdir=hello,no-version,no-symexport,buildfile-in-prefix     \
  libhello
$ tree hello/
hello/
`-- libhello/
    |-- include/
    |   |-- buildfile
    |   `-- hello/
    |       `-- hello.h
    `-- src/
        |-- buildfile
        `-- hello/
            `-- hello.
c

After that the upstream project is added as a git submodule to the project root directory and the source subdirectories are replaced with the symbolic links to the directories inside the upstream project

directory: 
$ tree hello/
hello/
|-- libhello/
|   |-- include/
|   |   |-- buildfile
|   |   `-- hello/ -> ../../u
pstream/include/hello/ | `-- src/ | |-- buildfile | `-- hello/ -> ../../upstream/src/ `--
upstream/ |-- include/ | `-- hello/ | `-- hello.h `-- src/ `-- hello.c

DEFAULT OPTIONS

FILES

See bdep-default-options-files(1) for an overview of the default options files. For the new command the search start directory is the project directory in the package and source modes and the parent directory of the new project in all other modes. The following options files are searched for in each directory and, if found, loaded in the order

listed: 
bdep.options
bdep-{config config-add}.options                # if --config-add|-A
bdep-{config config-add config-create}.options  # if --config-create|-C
bdep-new.options
bdep-new-{project|package|source}.options # (mode-dependent
)

The following new command options cannot be specified in the default options

files: 
--output-dir|-o
--directory|-d
--package
--source
--no-checks
--config-add|-A
--config-create|-C
--wipe

While the presence of the --pre-hook or --post-hook options in remote defau

ll trigger a prompt.

T

The BDEP_AUTHOR_EMAIL environment variable can be used to specify the package email address. If not set, the new command will first try to obtain the email from the version control system (if used) and then from the EMAIL environment variable. If all these methods fail, a dummy you@example.org

email
is used.
