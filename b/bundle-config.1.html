CLÉS DE

CONFIGURATION

Les clés de configuration dans bundler ont deux formes : la forme canonique et la forme variable d'environnement

.

Par exemple, passer l'indicateur --without à bundle install(1) bundle-install.1.html empêche Bundler d'installer certains groupes spécifiés dans le Gemfile(5). Bundler persiste cette valeur dans app/.bundle/config afin que les appels à Bundler.setup n'essaient pas de trouver des gems depuis le Gemfile que vous n'avez pas installées. De plus, les appels ultérieurs à bundle install(1) bundle-install.1.html se souviennent de ce paramètre et sautent ces

groupes.

La forme canonique de cette configuration est "without". Pour convertir la forme canonique en la forme variable d'environnement, mettez-la en majuscules et préfixez-la avec BUNDLE_. La forme variable d'environnement de "without" est BUNDLE_WITHOUT

.

Toute période dans les clés de configuration doit être remplacée par deux underscores lors de la définition via des variables d'environnement. La clé de configuration local.rack devient la variable d'environnement BUNDLE_LOCAL__RAC

K
.

MÉMORISATION DES

OPTIONS

Les drapeaux passés à bundle install ou à l'environnement d'exécution de Bundler, tels que --path foo ou --without production, sont mémorisés entre les commandes et enregistrés dans la configuration de votre application locale (normalement, ./.bundle/co

nfig).

Cependant, cela sera changé dans bundler 4, il vaut donc mieux ne pas s'appuyer sur ce comportement. Si ces options doivent être mémorisées, il vaut mieux les définir en utilisant bundle config (par ex., bundle config set --local path foo)

.

Les drapeaux qui peuvent être configurés sont

:
--b
in
Crée un répertoire (par défaut ~/bin) et y place tous les exécutables de la gem. Ces exécutables s'exécutent dans le contexte de Bundler. Si vous l'utilisez, vous pouvez ajouter ce répertoire à la variable PATH de votre environnement. Par exemple, si la gem rails est livrée avec un exécutable rails, ce drapeau créera un exécutable bin/rails qui garantit que toutes les dépendances référencées seront résolues en utilisant les gems du
bundle.
--deployme
nt
En mode déploiement, Bundler « déployera » le bundle pour une utilisation en production. Veuillez vérifier attentivement si vous souhaitez activer cette option dans les environnements development ou test
.
--on
ly
Une liste de groupes séparés par des espaces pour n'installer que les gems des groupes spécifiés. Veuillez vérifier attentivement si vous souhaitez installer également des gems sans groupe, car elles sont placées dans le groupe defaultp. Par exemple seulement test:default installera tous les gems spécifiés dans le groupe test et sans
celui-ci.
--pa
th
L'emplacement où installer les gems spécifiés. La valeur par défaut est celle des paramètres de Rubygems. Bundler partage cet emplacement avec Rubygems, gem install ... installera également le gem là-bas. Par conséquent, les gems installés sans --path ... apparaîtront en appelant gem list. De même, les gems installés à d'autres emplacements n'y figureront
pas.
--witho
ut
Une liste séparée par des espaces ou par des deux-points de groupes référençant les gems à ignorer lors de
l'installation.
--wi
th
Une liste séparée par des espaces ou par des deux-points de groupes optionnels référen
çant les gems à
inclure lors de
l'installation.

OPTIONS DE

COMPILATION

Vous pouvez utiliser bundle config pour indiquer à Bundler les drapeaux à passer à l'installateur de gems à chaque fois que bundler tente d'installer un gem

particulier.

Un exemple très courant, le gem mysql, nécessite que les utilisateurs de Snow Leopard passent des drapeaux de configuration à gem install pour spécifier où trouver l'exécutable mysql_config

. 
gem install mysql -- --with-mysql-config=/usr/local/mysql/bin/mysql_
con
fig

Étant donné que l'emplacement précis de cet exécutable peut varier d'une machine à l'autre, vous pouvez spécifier ces drapeaux machine par

machine. 
bundle config set --global build.mysql --with-mysql-config=/usr/local/mysql/bin/mysql_
con
fig

Après avoir exécuté cette commande, chaque fois que bundler devra installer le gem mysql, il transmettra les drap

eaux que vous
avez spécifiés.

DÉPÔTS GIT

LOCAUX

Bundler vous permet également de travailler avec un dépôt git local au lieu d'utiliser la version distante. Cela peut être réalisé en configurant un remplacement local

: 
bundle config set --local local.NOM_DU_GEM /chemin/vers/le/dépôt/git
/lo
cal

Par exemple, pour utiliser un dépôt Rack local, un développeur pourrait appeler

: 
bundle config set
--local local.rac
k ~/Work/git/rack

Maintenant, au lieu de récupérer le dépôt git distant, le remplacement local sera utilisé. De manière similaire à une source de chemin, chaque fois que le dépôt git local change, les changements seront automatiquement pris en compte par Bundler. Cela signifie qu'un commit dans le dépôt git local mettra à jour la révision dans le Gemfile.lock avec la révision du dépôt git local. Cela nécessite la même attention que les sous-modules git. Avant de pousser vers le dépôt distant, vous devez vous assurer que le remplacement local a été poussé, sinon vous pourriez pointer vers un commit qui n'existe que sur votre machine locale. Vous devrez également encoder les noms d'utilisateur et mots de passe en échappement

CGI.

Bundler effectue de nombreuses vérifications pour s'assurer qu'un développeur ne travaille pas avec des références invalides. En particulier, nous forçons un développeur à spécifier une branche dans le Gemfile afin d'utiliser cette fonctionnalité. Si la branche spécifiée dans le Gemfile et la branche courante dans le dépôt git local ne correspondent pas, Bundler interrompra l'exécution. Cela garantit qu'un développeur travaille toujours avec les bonnes branches et empêche le verrouillage accidentel sur une branche

différente.

Enfin, Bundler s'assure également que la révision courante dans le Gemfile.lock existe dans le dépôt git local. Ce faisant, Bundler vo

us force à récupérer les derniers c
hangements dans les dépôts distants.

GEMS

Bundler vous permet de configurer des identifiants pour n'importe quelle source de gems, ce qui vous évite de mettre des secrets dans votre

bundle config set --global https

C'est particulièrement utile pour les dépôts privés sur des hôtes tels que GitHub, où vous pouvez utiliser des jetons OAuth personnels

Notez que tous les identifiants configurés seront masqués par les commandes informatives telles que bundle config list ou bundle config get, sauf si vous utilisez le drapeau --parseable. Cela permet d'éviter de divulguer involontairement des identifiants lors de la copie de la sortie de

bundler.

Notez également que pour garantir une correspondance correcte entre les noms de variables d'environnement valides et les noms d'hôtes valides, bundler effectue les transformations suivantes

:
  • Tout caractère - dans un nom d'hôte est remplacé par trois underscores (___) dans la variable d'environnement
    • correspondante.
  • Tout caractère . dans un nom d'hôte est remplacé par deux underscores (__) dans la variable d'env
    • ironnement co
rrespondante.

Cela signifie que si vous avez un serveur de gems nommé my.gem-host.com, vous devrez utiliser la variable BUNDLE_MY__GEM___HOST__COM pour

configurer ses ident
ifiants via ENV.
