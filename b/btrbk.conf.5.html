NOM

btrbk.conf - fichier de configuration de btrbk

SYNOPIS

/etc/btrbk.conf
/etc/btrbk/btrbk.conf

DESCRIPTION

Le fichier de configuration de btrbk spécifie quels sous-volumes btrfs sur le système de fichiers doivent être traités, quels sous-volumes cibles doivent être utilisés pour créer les sauvegardes, et où les instantanés doivent être générés. La politique de rétention, ainsi que la plupart des autres options, peuvent être définies globalement ou dans une section.

Les options spécifiées s'appliquent toujours à la dernière section rencontrée, remplaçant les valeurs définies dans les sections de niveau supérieur. Cela signifie que les options globales doivent être définies avant que toute section ne soit définie.

Les lignes vides sont ignorées. Un caractère dièse (#) commence un commentaire qui s'étend jusqu'à la fin de la ligne.

SECTIONS

volume <répertoire-volume>|<url> (optionnel)

Chemin absolu pointant vers un système de fichiers btrfs contenant le ou les sous-volumes source à sauvegarder. Généralement le point de montage d'un système de fichiers btrfs monté avec l'option subvolid=5.

subvolume <nom-sous-volume>

Sous-volume à sauvegarder, relatif au <répertoire-volume> de la section volume, ou absolu si la section volume est omise. Accepte le caractère joker "*".

Notez que si ce sous-volume est la racine btrfs (id=5), il doit avoir un UUID valide, ce qui n'est pas le cas pour les systèmes de fichiers créés avec btrfs-progs < 4.16.

target [send-receive|raw] <répertoire-cible>|<url>

Répertoire cible où les sous-volumes de sauvegarde doivent être créés. Le type de cible optionnel est par défaut « send-receive », voir TYPES DE CIBLE ci-dessous pour les détails.

Plusieurs sections target sont autorisées, dans n'importe quel contexte : un target défini dans un contexte volume ou global sera utilisé pour toutes les sections subvolume sous-jacentes (astuce : exécutez "btrbk list" ou "btrbk config print" pour voir la configuration résultante).

Si un <url> est spécifié, les actions btrbk (commandes shell) sont exécutées à distance via ssh, en utilisant les Options SSH décrites ci-dessous. Les formats acceptés sont :

ssh://<nom-hote>[:<port>]/<répertoire>
<nom-hote>:<répertoire>

Où <nom-hote> est soit un nom d'hôte, une adresse IPv4 en notation décimale pointée, soit une littérale IP encapsulée entre crochets (par exemple, "[2001:db8::7]").

Si vous vous connectez à des machines virtuelles, envisagez de configurer plusieurs sections volume pour un <nom-hote>, avec des numéros de <port> distincts pour chaque machine.

OPTIONS

Les options décrites ici peuvent être spécifiées dans le contexte global ainsi que dans les sections volume, subvolume et target, sauf indication contraire.

Options de base

timestamp_format short|long|long-iso

Format d'horodatage utilisé comme suffixe pour les noms des nouveaux sous-volumes d'instantanés. Par défaut « long ».

short

AAAAJJMM[_N] (par exemple, "20150825", "20150825_1")

long

AAAAJJMM[<T>]HHMM[_N] (par exemple, "20150825T1531")

long-iso

AAAAJJMM[<T>]HHMMSS&plusmn;HHMM[_N] (par exemple, "20150825T153123+0200")

Notez qu'un suffixe "_N" est ajouté à l'horodatage si un instantané ou une sauvegarde existe déjà avec l'horodatage de la date/heure actuelle.

Utilisez « long-iso » si vous voulez vous assurer que btrbk ne crée jamais d'horodatages ambigus (ce qui peut arriver si plusieurs instantanés sont créés lors d'un changement d'heure d'été/hiver).

Notez que l'utilisation de « long-iso » a des implications sur la planification, voir Heure de référence ci-dessous.

snapshot_dir <répertoire>

Répertoire dans lequel les instantanés btrfs sont créés, relatif au <répertoire-volume> de la section volume, ou absolu si la section volume> est omise. Notez que btrbk ne crée pas automatiquement ce répertoire, et la création de l'instantané échouera s'il n'est pas présent.

snapshot_name <nom-base>

Nom de base de l'instantané (et de la sauvegarde) créé. Cette option n'est valide que dans la section subvolume. Par défaut <nom-sous-volume>.

snapshot_create always|onchange|ondemand|no

Si défini sur « always », les instantanés sont toujours créés. Si défini sur « onchange », les instantanés ne sont créés que si le dernier instantané n'est pas à jour, c'est-à-dire si le sous-volume source a changé (plus précisément : la génération btrfs a été augmentée) depuis la création du dernier instantané. Si défini sur « ondemand », les instantanés ne sont créés que si au moins un sous-volume cible est accessible (utile si vous manquez d'espace disque et que vous n'utilisez btrbk que pour les sauvegardes sur un disque externe qui n'est pas toujours connecté). Si défini sur « no », les instantanés ne sont jamais créés (utile si une autre instance de btrbk s'occupe de la création des instantanés). Par défaut « always ».

incremental yes|no|strict

Si défini, des sauvegardes incrémentielles sont créées. Si défini sur « strict », les sauvegardes non incrémentielles (initiales) ne sont jamais créées, et les sauvegardes incrémentielles sont restreintes aux parents liés (par relation parent-uuid). Par défaut « yes ».

Notez que même si la chaîne parent-uuid est rompue, les instantanés et les sauvegardes peuvent toujours partager des données (ce qui est particulièrement vrai pour les sauvegardes créées avec l'option incremental activée), et sont parfaitement adaptés comme parents pour les opérations d'envoi/réception incrémentielles. Mais comme btrbk ne peut pas en être certain, de telles opérations sont interdites en mode "incremental strict".

noauto yes|no

Si défini, le contexte est ignoré par toutes les actions btrbk sauf s'il est explicitement activé par un argument de commande <filtre> btrbk correspondant (par exemple, "btrbk run monfiltre").

Options de groupement

group <nom-groupe> [<nom-groupe>]...

Ajoute la section courante (volume, sous-volume ou cible) à des groupes définis par l'utilisateur, qui peuvent être utilisés comme filtre pour la plupart des commandes btrbk (voir ÉNONCÉS DE FILTRE de btrbk(1)). Cette option peut être définie plusieurs fois dans le même contexte.

Options de politique de rétention

preserve_day_of_week monday|tuesday|...|sunday

Définit quel jour un instantané/sauvegarde est considéré comme une sauvegarde « hebdomadaire ». Les sauvegardes hebdomadaires, mensuelles et annuelles sont conservées ce jour de la semaine (voir POLITIQUE DE RÉTENTION ci-dessous). Par défaut « sunday ».

preserve_hour_of_day [0..23]

Définit après quelle heure (en heures pleines après minuit) un instantané/sauvegarde est considéré comme une sauvegarde « quotidienne ». Les sauvegardes quotidiennes, hebdomadaires, mensuelles et annuelles sont conservées à cette heure (voir POLITIQUE DE RÉTENTION ci-dessous). Ignoré sur les instantanés ou sauvegardes sans information d'heure (timestamp_format short). Par défaut « 0 ».

snapshot_preserve no|<politique-de-r&#233;tention>

Définit la politique de rétention pour les instantanés (voir POLITIQUE DE RÉTENTION ci-dessous). Si défini sur « no », conserve les instantanés selon snapshot_preserve_min uniquement. Par défaut « no ».

Notez que snapshot_preserve n'a aucun effet si snapshot_preserve_min est défini sur « all » (le défaut).

snapshot_preserve_min all|latest|<nombre>{h,d,w,m,y}

Conserve tous les instantanés pendant un minimum d'heures (h), de jours (d), de semaines (w), de mois (m) ou d'années (y), quel que soit leur nombre. Si défini sur « all », conserve tous les instantanés indéfiniment. Si défini sur « latest », conserve le dernier instantané. Par défaut « all ».

target_preserve no|<politique-de-r&#233;tention>

Définit la politique de rétention pour les sauvegardes (voir POLITIQUE DE RÉTENTION ci-dessous). Si défini sur « no », conserve

TYPES DE CIBLE

send-receive

Sauvegardes créées en utilisant la commande btrfs send et btrfs receive. Ce sont des instantanés btrfs classiques.

raw

Sauvegardes créées en copiant directement les sous-volumes source dans le répertoire cible. Peut être utilisé pour des sauvegardes de fichiers sur des systèmes de fichiers non-btrfs. Notez que les sauvegardes créées de cette manière ne peuvent pas être utilisées comme parents pour des sauvegardes incrémentielles.

OPTIONS SSH

Si un <url> est spécifié dans une section volume ou target, btrbk utilisera ssh pour toutes les opérations de sous-volume (par exemple, le listage des sous-volumes, la création d'instantanés ou de sauvegardes). Les options ssh suivantes peuvent être spécifiées dans la section global ou target (dans ce dernier cas, elles ne s'appliquent qu'à ce target spécifique).

ssh_identity <chemin-vers-clé-privée>

Chemin vers la clé privée ssh à utiliser pour l'authentification. Par défaut, la valeur par défaut de ssh est utilisée.

ssh_user <nom-utilisateur>

Nom d'utilisateur à utiliser pour la connexion ssh. Par défaut, le nom d'utilisateur courant est utilisé.

ssh_port <numéro-de-port>

Numéro de port à utiliser pour la connexion ssh. Par défaut, le port 22 est utilisé.

ssh_compress yes|no

Active la compression pour la connexion ssh. Par défaut « no ».

ssh_options <options-ssh>

Options ssh supplémentaires à passer à la commande ssh (par exemple, "-o ConnectTimeout=5"). Peut être spécifié plusieurs fois.

OPTIONS SSH CIBLE

Les options suivantes peuvent être spécifiées dans le contexte target pour contrôler le comportement de btrfs send et btrfs receive lors de la copie vers une cible distante.

target_ssh_options <options-ssh>

Options ssh supplémentaires à passer à la commande ssh utilisée pour l'opération de réception sur la cible distante (par exemple, "-o ConnectTimeout=5"). Peut être spécifié plusieurs fois.

target_ssh_compress yes|no

Active la compression pour la connexion ssh utilisée pour l'opération de réception sur la cible distante. Par défaut « no ».

target_ssh_user <nom-utilisateur>

Nom d'utilisateur à utiliser pour la connexion ssh à la cible distante. Par défaut, le nom d'utilisateur courant est utilisé.

target_ssh_port <numéro-de-port>

Numéro de port à utiliser pour la connexion ssh à la cible distante. Par défaut, le port 22 est utilisé.

target_ssh_identity <chemin-vers-clé-privée>

Chemin vers la clé privée ssh à utiliser pour l'authentification auprès de la cible distante. Par défaut, la valeur par défaut de ssh est utilisée.

OPTIONS DE SHELL À DISTANCE

Si un <url> est spécifié dans une section volume, btrbk utilisera le shell spécifié par remote_shell pour exécuter des commandes à distance. La valeur par défaut est ssh.

remote_shell <chemin-vers-shell>

Chemin vers le shell à utiliser pour exécuter des commandes à distance. Peut être ssh, rsh, ou tout autre shell capable d'exécuter des commandes à distance.

remote_shell_options <options-shell>

Options supplémentaires à passer au shell distant.

POLITIQUE DE RÉTENTION

La politique de rétention contrôle combien de temps les instantanés et les sauvegardes sont conservés. La politique est appliquée de manière hiérarchique, en commençant par les sauvegardes annuelles, puis mensuelles, puis hebdomadaires, puis quotidiennes. Les sauvegardes sont ensuite conservées sur le jour de la semaine spécifié par preserve_day_of_week, et à l'heure spécifiée par preserve_hour_of_day.

La politique de rétention est définie par les options suivantes :

snapshot_preserve

Spécifie la politique de rétention pour les instantanés. La valeur peut être un entier suivi de {h,d,w,m,y} (par exemple, 7d pour conserver les instantanés pendant 7 jours), ou les valeurs spéciales `all` (conserver tout) ou `latest` (conserver uniquement le dernier).

snapshot_preserve_min

Garantit qu'au moins un instantané est conservé pendant la période spécifiée. Par exemple, si snapshot_preserve est défini sur 7d et snapshot_preserve_min sur 30d, alors tous les instantanés des 30 derniers jours seront conservés.

target_preserve

Spécifie la politique de rétention pour les sauvegardes (créées avec l'option target). Fonctionne de la même manière que snapshot_preserve.

target_preserve_min

Garantit qu'au moins une sauvegarde est conservée pendant la période spécifiée. Fonctionne de la même manière que snapshot_preserve_min.

preserve_day_of_week

Définit le jour de la semaine où un instantané/une sauvegarde sera considéré comme hebdomadaire. Les jours possibles sont `monday`, `tuesday`, `wednesday`, `thursday`, `friday`, `saturday`, `sunday`. La valeur par défaut est `sunday`.

preserve_hour_of_day

Définit l'heure de la journée (en heures, de 0 à 23) où un instantané/une sauvegarde sera considéré comme quotidien. Les valeurs par défaut est 0.

Exemple de politique de rétention :

# Conserver les 7 derniers jours, 4 dernières semaines, 6 derniers mois, 2 dernières années
# Conserver au moins un instantané par jour pendant 30 jours
# Conserver au moins un instantané par semaine pendant 1 an
# Conserver au moins un instantané par mois pendant 3 ans
# Conserver au moins un instantané par an pour toujours
snapshot_preserve 7d 4w 6m 2y
snapshot_preserve_min 30d 1y 3y
preserve_day_of_week monday
preserve_hour_of_day 3

HEURE DE RÉFÉRENCE

Le calcul de la politique de rétention est basé sur l'heure actuelle et les métadonnées des instantanés/sauvegardes. Les timestamps sont comparés à l'heure actuelle pour déterminer si un instantané/une sauvegarde est « ancien » ou « récent ».

Si l'option timestamp_format est définie sur `long-iso`, btrbk utilisera des timestamps avec fuseau horaire. Si le fuseau horaire de la machine sur laquelle btrbk s'exécute est différent de celui utilisé lors de la création des instantanés/sauvegardes, cela peut entraîner des résultats inattendus.

Pour éviter cela, il est recommandé de définir explicitement le fuseau horaire lors de l'exécution de btrbk, par exemple en utilisant la variable d'environnement `TZ`:

TZ=Europe/Paris btrbk run

GROUPE DE TRANSACTIONS BTRFS

btrbk peut créer des instantanés de plusieurs sous-volumes dans le même groupe de transactions btrfs. Cela garantit que tous les instantanés créés au cours d'une seule exécution de btrbk sont cohérents entre eux.

L'option transaction_group, définie dans le contexte global ou volume, active cette fonctionnalité.

transaction_group yes|no

Active ou désactive la création de groupes de transactions btrfs. Par défaut « no ».

EXEMPLE

Voici un exemple de fichier de configuration btrbk.conf :

# Sauvegarder le sous-volume /home vers un disque externe
volume /mnt/btrfs-disk
    snapshot_dir snapshots
    subvolume home
        snapshot_name home_backup
        snapshot_preserve 7d 4w 6m 1y
        snapshot_preserve_min 30d

# Sauvegarder le sous-volume /etc vers un serveur distant via SSH
volume ssh://remote.server.com
    subvolume etc
        snapshot_name etc_backup
        target /backups/etc
        target_preserve 7d 4w
        target_preserve_min 30d
        ssh_user backupuser
        ssh_port 2222

Btrfs Specific

Options

incremental_prefs <list-spec>[:<amount>]..

.
Specify the preferences to determine the best common (correlated) parent and clone sources for incremental backups, by choosing from predefined candidate lists.

The list-spec defines from what candidate list the next parent/clone-src doit être ajouté à une liste de résultats ; amount définit combien (par exemple « sro:1 sro:1 » est identique à « sro:2 »), ou tous si omis. Tout candidat qui est déjà dans les résultats est

éliminé.

La liste résultante des sous-volumes est ensuite utilisée comme paramètres pour la commande btrfs-send(8) : le premier pour « -p <parent> », tous les autres pour « -c <clone-src> »

.

Disponibles list-spec (listes de candidats = sous-ensembles filtrés de sous-volumes corrélés)

:

sro,sr

n
Tous depuis snapshot_dir correspondant à snapshot_name, avec la relation parent_uuid, triés par horodatage btrbk (o=plus ancien n=plus récent)
.

sao,sa

n
Tous depuis snapshot_dir correspondant à snapshot_name, triés par horodatage btrbk (o=plus ancien n=plus récent)
.

aro,ar

n
Tous depuis incremental_resolve, avec la relation parent_uuid, triés par cgen (o=plus ancien n=plus récent)

snapshot.

Si défini à « mountpoint », utilise les parents dans l'arborescence du système de fichiers sous le point de montage du snapshot et du répertoire cible. Si défini à « directory », utilise les parents strictement sous les répertoires snapshot/cible. Définissez ceci à « directory » si vous rencontrez des problèmes d'accès (lorsque btrbk n'est pas exécuté en tant que root). Par défaut « mountpoint »
.

btrfs_commit_dele

te yes|no
Si défini, attendre le commit de la transaction à la fin de chaque suppression de snapshot ou de sauvegarde (définit l'option --commit-each pour « btrfs subvolume delete »). Par défaut « no »
.

send_protocol <number>|no *expérimental

*
Utilise la version N du protocole btrfs send. Si activé sur la cible, btrbk ajoute « --proto <number> » à la commande btrfs-send(8). Par défaut « no » (défaut btrfs)
.

send_compressed_data yes|no *expérimental

*
Envoie les données qui sont compressées sur le système de fichiers directement sans les décompresser. Cela nécessite la version de protocole 2 ou supérieure (btrfs-progs >= 5.19), et implique « send_protocol 2 ». Si activé sur la cible, btrbk ajoute « --compressed-data » à la commande btrfs-send(8). Par défaut « no » (défaut btrfs)
.

*

archive_qgroup_destroy yes|no *expérimental

*

POLITIQUE DE

RÉTENTION

Les politiques de rétention sont définies individuellement pour les snapshots, les sauvegardes et les archives (résumés sous le nom de « sauvegardes » dans le texte suivant), en utilisant une combinaison de

:

*_preserve_min all|latest|no|<number>{h,d,w,m,

y}
Durée pendant laquelle toutes les sauvegardes sont
préservées.

*_preserve no|<retention_policy

>
Planification (points uniques dans le temps) pour lesquels des sauvegardes individuelles sont
préservées.

Notez que si « preserve_min » est défini à « all » (la valeur par défaut), tout réglage de « preserve » n'a évidemment aucun

effet.

Le format pour <retention_policy> est

: 
[<hourly>h] [<daily>
d] [<weekly>w] [<mo
nthly>m] [<yearly>y]

hourl

y
Définit combien d'heures en arrière les sauvegardes horaires doivent être préservées. La première sauvegarde d'une heure est considérée comme une sauvegarde
horaire.

dail

y
Définit combien de jours en arrière les sauvegardes quotidiennes doivent être préservées. La première sauvegarde d'un jour (en commençant à preserve_hour_of_day) est considérée comme une sauvegarde
quotidienne.

weekl

y
Définit combien de semaines en arrière les sauvegardes hebdomadaires doivent être préservées. La première sauvegarde quotidienne créée à preserve_day_of_week (ou la première sauvegarde de cette semaine si aucune n'a été faite ce jour-là) est considérée comme une sauvegarde
hebdomadaire.

monthl

y
Définit combien de mois en arrière les sauvegardes mensuelles doivent être préservées. Chaque première sauvegarde hebdomadaire d'un mois est considérée comme une sauvegarde
mensuelle.

yearl

y
Définit combien d'années en arrière les sauvegardes annuelles doivent être préservées. Chaque première sauvegarde mensuelle d'une année est considérée comme une sauvegarde
annuelle.

Utilisez un astérisque pour « all » (par exemple « target_preserve 60d *m » indique : « préserver les sauvegardes quotidiennes pour 60 jours en arrière, et toutes les sauvegardes mensuelles »)

.

Astuce : Exécutez btrbk avec l'option -S, --print-schedule pour obtenir une sortie complète des résultats du

planificateur.

Heure de

référence

L'heure locale sur l'hôte exécutant btrbk définit l'heure de référence pour tous les calculs de date/heure, en particulier pour le « début d'un jour », et par conséquent pour les premières sauvegardes quotidiennes, hebdomadaires, mensuelles ou annuelles. L'heure locale sur les hôtes distants (source/cible ssh) n'est jamais

utilisée.

Sauf si « timestamp_format long-iso » est défini, les sauvegardes quotidiennes sont préservées à « preserve_hour_of_day » (par défaut minuit) dans le fuseau horaire respectif (et non à « 00:00 UTC », qui serait « 14:00 » à Honolulu). Cela devient pertinent pour les configurations avec plusieurs instances btrbk, par exemple de nombreuses instances uniquement-snapshot (réparties dans le monde), et une instance uniquement-fetch sur le serveur de

sauvegarde.

Avertissement

:
•Si « timestamp_format long-iso » est défini, chaque instance btrbk su
r a une interprétation différente de « premier dans le jour ». Assurez
-vous d'exécuter btrbk avec le même fuseau horaire sur chaque hôte, par
exemple en définissant la variable d'environnement TZ (voir tzset(3)).

TYPES DE

CIBLE

send-receiv

e
Sauvegarde vers un système de fichiers btrfs, en utilisant « btrfs send/receive ». C'est le type de cible recommandé (standard). Le <target-directory> doit être un chemin absolu et pointer vers un sous-volume ou un répertoire dans un système de fichiers btrfs. Voir btrfs-send(8), btrfs-receive(8)
.

raw *expérimental

*
Sauvegarde vers un fichier brut (indépendant du système de fichiers) à partir de la sortie de btrfs-send(8), avec compression et chiffrement optionnels.

Notez que le mécanisme de préservation de la cible est actuellement désactivé pour les sauvegardes incrémentielles brutes (btrbk ne supprime aucun fichier incrémentiel brut)

!

Les sauvegardes brutes consistent en deux fichiers : le fichier de données principal contenant le flux btrfs send, et un fichier annexe « .info » contenant les métadonnées

: 
<snapshot-name>.<timestamp>[_N].btrfs[.g
z|.bz2|...][.gpg] <snapshot-name>.<times
tamp>[_N].btrfs[.gz|.bz2|...][.gpg].info

Pour les sauvegardes incrémentielles (« incremental yes »), veuillez noter que

:
•Dès qu'un seul fichier de sauvegarde incrémentielle est perdu ou corrompu, toutes les sauvegardes incrémentielles ultérieures deviennent invalides, car il n'y a plus de parent commun pour les images incrémentielles suivantes. Cela peut être un bon compromis pour un plan de sauvegarde de vacances, mais pour le long terme, assurez-vous de déclencher une sauvegarde non incrémentielle de temps en
temps.
•Il n'y a actuellement aucun support pour la rotation des sauvegardes incrémentielles : si incremental est défini, une sauvegarde complète doit être déclenchée manuellement de temps en temps afin de pouvoir supprimer les anciennes
sauvegardes.
