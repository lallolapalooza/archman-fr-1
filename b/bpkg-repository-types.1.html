NOM

bpkg-repository-types - types de dépôts, structure et URLs

DESCRIPTION

Ce sujet d'aide décrit les types de dépôts reconnus par bpkg, leur structure et le format de leurs URLs. Actuellement, trois types de dépôts sont pris en charge : pkg basé sur des archives, dir basé sur des répertoires, et git basé sur un système de contrôle de version.

L'emplacement du dépôt peut spécifier le type de dépôt dans le composant de schéma de l'URL sous la forme type+protocole. Par exemple :

git+https://example.com/foo
dir+file:///tmp/repo

Notez que la spécification explicite n'est nécessaire que lorsque le type correct ne peut pas être deviné à partir de l'URL. Voir bpkg-rep-add(1) pour plus de détails.

DÉPOTS PKG

Un dépôt pkg est basé sur une archive. C'est-à-dire qu'il contient une collection de divers paquets/versions sous forme de fichiers d'archive. Pour plus d'informations sur la structure des dépôts pkg, reportez-vous au Manuel du gestionnaire de paquets build2. L'emplacement du dépôt pkg peut être un chemin de répertoire local ou une URL http(s)://.

DÉPOTS DIR

Un dépôt dir est basé sur un répertoire. C'est-à-dire qu'il contient une collection de divers paquets sous forme de répertoires, mais une seule version par paquet peut être présente dans un tel dépôt. L'emplacement du dépôt dir peut être un chemin de répertoire local ou une URL file://.

Un dépôt dir est censé contenir soit le fichier manifest, soit le fichier packages.manifest dans le répertoire racine du dépôt. S'il ne contient que manifest, il est supposé être un dépôt simple, à paquet unique, le fichier manifest étant son manifeste de paquet. Sinon, le fichier packages.manifest devrait lister les emplacements des paquets disponibles tels que décrits dans Manifeste de liste de paquets pour les dépôts dir (#manifest-package-list-dir).

Un dépôt dir peut également contenir le fichier repositories.manifest dans le répertoire racine du dépôt. Ce fichier peut être utilisé pour décrire le dépôt lui-même ainsi que pour spécifier ses dépôts prérequis et complémentaires. Voir Manifeste de liste de dépôts (#manifest-repository-list) pour les détails sur le format et la sémantique de ce fichier.

DÉPOTS GIT

Un dépôt git est basé sur le contrôle de version. C'est-à-dire qu'il contient normalement plusieurs versions du même paquet (mais peut également contenir plusieurs paquets, généralement liés, dans le même dépôt).

Un dépôt git a la même structure et les mêmes fichiers de manifeste que le dépôt dir. Voir Manifeste de liste de paquets pour les dépôts dir (#manifest-package-list-dir) et Manifeste de liste de dépôts (#manifest-repository-list) pour les détails sur leur format et leur sémantique.

Théoriquement, un dépôt git peut contenir autant de versions de paquets qu'il y a de commits. En pratique, cependant, nous ne nous intéressons normalement qu'à un petit sous-ensemble d'entre eux, tandis que la récupération et le traitement des informations nécessaires pour tous pourraient être prohibitivement coûteux. Par conséquent, par défaut, seuls les tags annoncés sous la forme refs/tags/v* où la partie après v est également une version standard valide (#module-version) sont considérés comme des sources de versions de paquets utiles. Ces commits correspondent normalement aux versions publiées et sont appelés l'ensemble par défaut. Notez que seule la dernière révision de chaque version est prise en compte.

Au lieu de l'ensemble par défaut, il est possible de fournir un ensemble personnalisé de versions disponibles en spécifiant un ou plusieurs identifiants de commit et/ou références et/ou motifs de référence dans le fragment d'URL du dépôt (voir git-ls-remote(1) pour les détails sur les références annoncées). Par exemple :

https://example.com/foo.git#v1.2.3
https://example.com/foo.git#master
https://example.com/foo.git#af234f56
https://example.com/foo.git#tags/releases/*
https://example.com/foo.git#HEAD,tags/v1.*.*,heads/feature-*

De plus, il est possible d'étendre (ou de réduire) l'ensemble par défaut en utilisant la notation spéciale ## dans le fragment. Par exemple :

https://example.com/foo.git##HEAD     - ensemble par défaut plus HEAD
https://example.com/foo.git##heads/*  - ensemble par défaut plus branches
https://example.com/foo.git##-v1.*    - ensemble par défaut moins v1.*

Un fragment d'URL de dépôt git est une liste de filtres de référence séparés par des virgules sous la forme suivante :

[nom-ref][@commit]

Soit nom-ref, soit commit, soit les deux doivent être spécifiés. Si les deux sont spécifiés, nom-ref est uniquement utilisé pour minimiser la quantité de données récupérées et commit est censé appartenir à son historique. Par exemple :

.../foo.git#master@48fba3625d65941bb85a39061bcf795d4949c778

La partie nom-ref peut être un identifiant de commit abrégé ou une référence annoncée ou un motif de référence sous refs/. Tandis que commit doit être le SHA1 complet de 40 caractères qui n'a pas besoin d'être annoncé. Par commodité, un filtre de 40 caractères composé uniquement de chiffres hexadécimaux est considéré comme commit même s'il n'est pas précédé de @. Dans le cas improbable où cela produirait un résultat incorrect, la forme @ avec commit omis peut être utilisée. Par exemple :

.../foo.git#48fba3625d65941bb85a39061bcf795d4949c778   (identifiant de commit)
.../foo.git#deadbeefdeadbeefdeadbeefdeadbeefdeadbeef@  (référence)

La partie nom-ref peut utiliser les caractères jokers * et ? avec la sémantique standard ainsi que la séquence de caractères ** qui correspond de manière récursive dans les sous-répertoires. Par exemple :

.../foo.git#tags/v*    - tags/v1.2.3 mais pas tags/old/v0.1.0
.../foo.git#tags/v**   - tags/v1.2.3 et tags/old/v0.1.0

Un nom-ref relatif est recherché dans refs/, refs/tags/ et refs/heads/ ainsi que parmi les références symboliques comme HEAD. Pour l'ancrer à refs/, rendez-le absolu, par exemple :

.../foo.git#tags/v*   - refs/tags/v1.2.3 mais aussi refs/heads/tags/voo
.../foo.git#/tags/v*  - uniquement refs/tags/v1.2.3

Bien qu'un motif de nom-ref soit autorisé à ne correspondre à aucune référence, une non-motif qui ne résout pas en une référence est invalide.

Si un nom-ref commence par un signe moins (-), il est traité comme un filtre d'exclusion – toutes les références qu'il correspond sont exclues de l'ensemble inclus par les filtres précédents (ou l'ensemble par défaut). Par exemple :

.../foo.git#v*,-v1.*  - exclure v1.* de v*
.../foo.git##-v1.*    - exclure v1.* de l'ensemble par défaut

Pour prendre en charge la spécification d'un moins initial littéral, un nom-ref qui commence par un plus (+) est traité comme un filtre d'inclusion. Par exemple :

.../foo.git#+x   - inclure  x
.../foo.git#+-x  - inclure -x
.../foo.git#++x  - inclure +x

Les protocoles git actuellement pris en charge sont git://, ssh:// (mais pas la syntaxe pseudo-URL scp), http:// et https:// pour les dépôts distants et file:// pour les dépôts locaux. Bien que bpkg essaie de minimiser la quantité d'informations (historique) récupérées, ce n'est pas toujours possible pour certains protocoles et/ou configurations de serveur, comme discuté ci-dessous.

Un dépôt git accessible via http(s):// peut utiliser le protocole dumb ou smart (référez-vous à la documentation git pour les détails). Le protocole dumb ne fournit qu'un support limité pour la minimisation de la récupération et si ce protocole est utilisé, alors bpkg n'a pas d'autre choix que de télécharger une quantité substantielle d'historique.

Le protocole smart permet la récupération d'un historique minimal pour les tags et les branches. Que cela soit également possible pour (tous) les identifiants de commit dépend si le serveur est configuré pour autoriser la récupération de commits non annoncés. Pour plus de détails, référez-vous aux valeurs de configuration git uploadpack.allowReachableSHA1InWant et uploadpack.allowAnySHA1InWant.

Les protocoles git:// et ssh:// sont similaires au protocole smart http:// en ce sens qu'ils prennent en charge la récupération d'un historique minimal pour les tags et les branches et peuvent ou non prendre en charge cela pour les identifiants de commit en fonction de la configuration du serveur. Notez, cependant, que contrairement à http(s)://, pour ces protocoles bpkg n'essaie pas de détecter si la récupération de commits non annoncés est autorisée et suppose toujours que ce n'est pas le cas. Sur la base de ces informations, pour obtenir des résultats optimaux, le protocole recommandé pour les dépôts distants est smart https://. De plus, si vous prévoyez de référencer des identifiants de commit non annoncés, envisagez également de configurer le serveur pour autoriser la récupération de commits non annoncés.

Le file:// prend en charge la minimisation des récupérations de la même manière que git:// et est donc traité de la même façon.
