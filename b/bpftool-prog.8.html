programme du OBJ en tant que PATH. bpftool prog loadall épingle tous les programmes du OBJ sous le répertoire PATH. type est PATH. optionnel, s'il n'est pas spécifié le type de programme sera déduit des noms de sections. Par défaut bpftool créera de nouvelles maps comme déclarées dans l'objet ELF étant chargé. Le paramètre map permet la réutilisation de maps existantes. Il peut être spécifié plusieurs fois, chaque fois pour une map différente. IDX fait référence à l'index de la map à remplacer dans le fichier ELF en comptant à partir de 0, tandis que NAME permet de remplacer une map par son nom. MAP spécifie la map à utiliser, en faisant référence à elle par id ou via un fichier épinglé. Si offload_dev NAME est spécifié, le programme sera chargé sur le périphérique réseau donné (offload). Si xdpmeta_dev NAME est spécifié, le programme deviendra lié au périphérique sans offload, ce qui facilite l'accès aux métadonnées XDP. L'argument optionnel pinmaps peut être fourni pour épingler toutes les maps sous le répertoire MAP_DIR. Si autoattach est spécifié, le programme sera attaché

If avant l'épinglage. Dans ce cas, seul le lien (représentant le programme attaché à son hook) est épinglé, pas le programme en tant que tel, donc le chemin n'apparaîtra pas dans bpftool prog show -f, mais seulement dans bpftool link show -f. De plus, cela ne fonctionne que lorsque bpftool (libbpf) est capable de déduire toutes les informations nécessaires depuis le fichier objet, en particulier, ce n'est pas pris en charge pour tous les types de programmes. Si un programme ne prend pas en charget autoattach, bpftool revient au marquage standard pour ce

programme.

L'option kernel_btf permet de spécifier un fichier BTF externe pour remplacer le fichier vmlinux BTF du système lors des relocalisations CO-RE. Notez que toute autre fonctionnalité reposant sur BTF (comme les programmes fentry/fexit, struct_ops) nécessite le fichier BTF du noyau réellement en cours d'exécution sur l'hôte, souvent exposé dans /sys/kernel/btf/vm

linux.

Note : PATH doit se trouver dans un point de montage bpffs. Il ne doit pas contenir de caractère point ('.'), qui est réservé pour de futures extensions de bpf

f

bpftool prog attach PROG ATTACH_TYPE [MAP
]
Attacher le programme bpf PROG (de type spécifié par ATTACH_TYPE). La plupart des ATTACH_TYPE nécessitent un MAP paramètre, à l'exception de flow_dissector qui est attaché à l'espace de noms réseau
courant.
bpftool prog detach PROG ATTACH_TYPE [MAP
]
Détacher le programme bpf PROG (de type spécifié par ATTACH_TYPE). La plupart des ATTACH_TYPE nécessitent un MAP paramètre, à l'exception de flow_dissector qui est détaché de l'espace de noms réseau
courant.
bpftool prog
tracelog
Affiche le pipe de trace du système sur la console (stdout). Appuyez sur <Ctrl+C> pour arrêter l'affichage. Les programmes BPF peuvent écrire dans ce pipe de trace à l'exécution avec l'aide bpf_trace_printk(). Cela ne doit être utilisé qu'à des fins de débogage. Pour diffuser des données des programmes BPF vers l'espace utilisateur, on peut utiliser les événements perf (voir aussi bpftool-map
(8)).
bpftool prog tracelog { stdout | stderr } PR
OG
Affiche le flux BPF du programme. Les programmes BPF peuvent écrire dans ces flux à l'exécution avec la kfunc bpf_stream_vprintk(). Le noyau peut écrire des messages d'erreur dans le flux d'erreur standard. Cette fonctionnalité ne doit être utilisée qu'à des fins de
débogage.
bpftool prog run PROG data_in FILE [data_out FILE [data_size_out L]] [ctx_in FILE [ctx_out FILE [ctx_size_out M]]] [repeat N
]
Exécute le programme BPF PROG dans l'infrastructure de test BPF du noyau, ce qui signifie que le programme travaille sur les données et le contexte fournis par l'utilisateur, et non sur des paquets réels ou des fonctions surveillées, etc. La valeur de retour et la durée du test d'exécution sont affichées sur la console.

Les données d'entrée sont lues depuis le FILE passé avec data_in. Si ce FILE est "-", les données d'entrée sont lues depuis l'entrée standard. Le contexte d'entrée, s'il y en a, est lu depuis le FILE passé avec ctx_in. De même, "-" peut être utilisé pour lire depuis l'entrée standard, mais seulement si l'entrée standard n'est pas déjà utilisée pour les données d'entrée. Si un FILE est passé avec data_out, les données de sortie sont écrites dans ce fichier. De même, le contexte de sortie est écrit dans le FILE passé avec ctx_out. Pour les deux flux de sortie, "-" peut être utilisé pour afficher sur la sortie standard (en texte brut, ou en JSON si l'option correspondante a été passée). Si les mots-clés de sortie sont omis, les données et le contexte de sortie sont jetés. Les mots-clés data_size_out et ctx_size_out servent à passer la taille (en octets) des tampons de sortie au noyau, bien que la valeur par défaut de 32 kB devrait être largement suffisante dans la plupart des

cas.

Le mot-clé repeat sert à indiquer le nombre d'exécutions consécutives à effectuer. Notez que les données et le contexte de sortie affichés dans les fichiers correspondent à la dernière de ces exécutions. La durée affichée à la fin des exécutions est une moyenne sur toutes les exécutions effectuées par la

commande.

Tous les types de programmes ne prennent pas en charge l'exécution de test. Parmi ceux qui le font, tous ne peuvent pas prendre les arguments ctx_in/ctx_out. bpftool n'effectue pas de

vérification sur les
types de programmes.

Cs
Profiler METRICs pour le programme bpf PROG pendant DURATION secondes ou jusqu'à ce que l'utilisateur appuie sur <Ctrl+C>. DURATION est optionnel. Si DURATION n'est pas spécifié, le profilage s'exécutera jusqu'à UINT_MAX sec
ondes.
