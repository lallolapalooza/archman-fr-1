NOM

bpkg-pkg-build - construire un paquet

SYNTAXE

bpkg pkg-build|build [options] [--upgrade|-u | --patch|-p]
                     [cfg-var... --] pkg-spec...
bpkg pkg-build|build [options]  --upgrade|-u | --patch|-p
                     [cfg-var... --]

pkg-spec = [flags](([scheme:]pkg[ver-spec]),...[@rep-loc] |
                   [@]rep-loc                            |
                   file                                  |
                   dir/)
flags      = ?
scheme     = sys
ver-spec   = /version | version-constraint

DESCRIPTION

La commande pkg-build construit un ou plusieurs paquets, y compris toutes leurs dépendances. Outre la construction de nouveaux paquets, cette commande est également utilisée pour mettre à niveau ou rétrograder les paquets déjà présents dans la configuration. Et à moins que l'option --keep-unused|-K ne soit spécifiée, pkg-build supprimera également les paquets de dépendance qui ne seraient plus utilisés.

La première forme (un ou plusieurs paquets spécifiés) construit de nouveaux paquets ou met à niveau (par défaut ou si --upgrade est spécifié) ou patch (si --patch est spécifié) les paquets spécifiés. La seconde forme (aucun argument mais --upgrade ou --patch spécifié) met à niveau ou patch tous les paquets bloqués de la configuration (voir ci-dessous pour plus de détails sur les paquets bloqués).

Dans les deux formes, la spécification des options --immediate|-i ou --recursive|-r entraîne que pkg-build met à niveau ou patch également les dépendances immédiates ou toutes les dépendances des paquets spécifiés (première forme) ou bloqués (seconde forme), respectivement. Notez également que dans la première forme, ces options ne peuvent être spécifiées qu'avec un --upgrade ou --patch explicite.

Chaque paquet peut être spécifié juste par son nom (pkg) avec une spécification de version optionnelle (ver-spec), auquel cas le code source du paquet sera automatiquement récupéré depuis l'un des dépôts configurés. Voir les commandes bpkg-rep-add(1) et bpkg-rep-fetch(1) pour plus d'informations sur les dépôts de paquets. La spécification de version (ver-spec) peut être soit la version exacte sous la forme /version, soit la contrainte de version telle que décrite dans Package Version Constraint (#package-version-constraint). Si ver-spec n'est pas spécifié, alors la dernière version disponible sera construite. Pour rétrograder, la version souhaitée doit être spécifiée explicitement. Par exemple :

bpkg build foo libfoo/1.2.3 "bar < 2.0.0"

Alternativement, l'emplacement du dépôt de paquets (rep-loc) peut être spécifié dans la commande de construction. Dans ce cas, si ver-spec n'est pas spécifié, alors la dernière version disponible depuis ce dépôt sera construite. Par exemple :

bpkg build foo,libfoo/1.2.3@https://git.example.org/foo.git#master

Si seul l'emplacement est spécifié, alors les dernières versions de tous les paquets disponibles directement depuis ce dépôt seront construites (notez que cela n'inclut pas les paquets disponibles depuis les dépôts complémentaires). Le délimiteur @ peut être omis si l'emplacement est une URL. Par exemple :

bpkg build https://git.example.org/foo.git#master
bpkg build @/path/to/repository/

Un nom de paquet (pkg) peut être préfixé par un schéma de paquet (scheme). Actuellement, le seul schéma reconnu est sys, qui indique à pkg-build de configurer le paquet comme disponible depuis le système plutôt que de le construire à partir des sources.

La version du paquet système (ver-spec) ne peut pas être une contrainte de version, mais peut être la valeur spéciale '/*', qui indique que la version doit être considérée comme inconnue mais satisfaisant toute contrainte de version. Si non spécifié, alors pkg-build tentera d'interroger le gestionnaire de paquets système pour la version installée, à moins que le gestionnaire de paquets système ne soit pas supporté ou que cette fonctionnalité ne soit désactivée avec --sys-no-query, auquel cas le ver-spec '/*' est supposé. Si le gestionnaire de paquets système est supporté, alors l'installation automatique d'un paquet disponible peut être demandée avec l'option --sys-install. Notez que si la version n'est pas explicitement spécifiée, alors au moins un paquet fictif (stub) doit être disponible depuis l'un des dépôts, à moins que l'option --sys-no-stub ne soit spécifiée.

Enfin, un paquet peut être spécifié soit comme le chemin vers l'archive du paquet (file), soit vers le répertoire du paquet (dir/; notez qu'il doit se terminer par un séparateur de répertoire). Voir les commandes bpkg-pkg-fetch(1) et bpkg-pkg-unpack(1) pour plus d'informations sur la sémantique de la spécification du paquet comme archive ou répertoire.

Des variables de configuration supplémentaires (cfg-var), s'il y en a, doivent être spécifiées avant les paquets (pkg-spec) et doivent être séparées par --. Ces variables ne sont effectives que lors de la configuration et uniquement pour les paquets qui ont été explicitement spécifiés sur la ligne de commande (sauf pour les remplacements globaux). Elles peuvent également être spécifiées pour ne s'appliquer qu'à des paquets spécifiques en utilisant le mécanisme de groupement d'arguments discuté ci-dessous. Voir bpkg-pkg-configure(1) pour plus d'informations sur les variables de configuration.

Par défaut, un paquet spécifié explicitement sur la ligne de commande est construit pour être bloqué : il ne sera pas considéré pour une suppression automatique s'il n'a plus de dépendants. Seules les versions des dépôts qui ont été ajoutés à la configuration (bpkg-rep-add(1)) sont considérées comme disponibles pour être construites et bloquées.

Alternativement, un paquet peut être construit (ou, plus couramment, mis à niveau/rétrogradé) en tant que dépendance en spécifiant le drapeau ? (flags) ou l'option --dependency. Un tel paquet ne sera ajouté à la configuration que s'il a effectivement des dépendants et, une fois qu'il n'est plus utilisé, il sera automatiquement supprimé. Seules les versions des dépôts prérequis des paquets dépendants sont considérées comme disponibles pour être construites en tant que dépendance.

Les paquets (bloqués et en tant que dépendances) qui sont spécifiés avec une version de paquet explicite (ver-spec) ou comme une archive ou un répertoire, auront leurs versions bloquées, c'est-à-dire qu'ils ne seront pas mis à niveau automatiquement.

À titre d'illustration, supposons dans l'exemple suivant que le dépôt stable contienne les paquets foo 1.0.0 ainsi que libfoo 1.0.0 et 1.1.0, tandis que testing contient libfoo 2.0.0, que testing est complété par stable, et que foo dépend de libfoo >= 1.0.0 :

bpkg fetch https://example.org/1/testing
bpkg build foo            # construit foo    1.0.0 pour blocage
                          # construit libfoo 1.1.0 en tant que dépendance
bpkg build ?libfoo/1.0.0  # rétrograde libfoo 1.0.0 en tant que dépendance,
                          #           bloque également la version 1.0.0
bpkg build ?libfoo/2.0.0  # erreur : 2.0.0 indisponible dans le dépôt du
                          #        dépendant (foo) (stable)
bpkg build libfoo/2.0.0   # met à niveau libfoo 2.0.0 pour blocage,
                          #         bloque également la version 2.0.0

PKG-BUILD OPTIONS DE PACKAGE

Les options suivantes (ainsi que des variables de configuration supplémentaires) peuvent être regroupées pour s'appliquer à un pkg-spec spécifique ainsi qu'être spécifiées globalement, auquel cas elles s'appliquent à tous les packages spécifiés (voir bpkg-argument-grouping(1) pour plus de détails).

--upgrade|-u
Mettre à niveau les packages vers la dernière version disponible qui satisfait toutes les contraintes.
--patch|-p
Mettre à niveau les packages vers la dernière version de correctif disponible qui satisfait toutes les contraintes.
--deorphan
Remplacer les packages orphelins par les meilleures versions de packages disponibles qui satisfont toutes les contraintes.

Il peut arriver qu'un package construit n'ait plus le package correspondant disponible dans le dépôt dont il provient (par exemple, suite à bpkg-rep-fetch(1) ou bpkg-rep-remove(1)). Un tel package est appelé un orphelin. Sans l'option --deorphan, la mise à niveau, la rétrogradation ou le correctif d'un orphelin le laissera inchangé si une version plus appropriée du package n'est pas disponible. Si l'option --deorphan est spécifiée, alors un orphelin sera remplacé par un non-orphelin. Dans ce cas, si --upgrade, --patch, ou la version du package est spécifiée, alors la nouvelle version est sélectionnée en conséquence. Sinon, la version la plus proche de la version orpheline est sélectionnée en utilisant l'ordre de préférence suivant : (1) même version, révision et itération, (2) dernière itération de même version et révision, (3) révision ultérieure de même version, (4) correctif ultérieur de même version, (5) mineure ultérieure de même version, (6) dernière version disponible, y compris les précédentes (voir Version de Package (#package-version) pour plus de détails).

--immediate|-i
Mettre également à niveau, corriger ou désorpheliner les dépendances immédiates.
--recursive|-r
Mettre également à niveau, corriger ou désorpheliner toutes les dépendances, récursivement.
--upgrade-immediate
Mettre à niveau les dépendances immédiates.
--patch-immediate
Corriger les dépendances immédiates.
--deorphan-immediate
Désorpheliner les dépendances immédiates.
--upgrade-recursive
Mettre à niveau toutes les dépendances, récursivement.
--patch-recursive
Corriger toutes les dépendances, récursivement.
--deorphan-recursive
Désorpheliner toutes les dépendances, récursivement.
--dependency
Construire, mettre à niveau ou rétrograder un package en tant que dépendance plutôt que de le maintenir.
--keep-out
Conserver les répertoires de sortie des packages externes entre les mises à niveau et les rétrogradations. Référez-vous à bpkg-pkg-disfigure(1) pour plus de détails.
--disfigure
Défigurer les packages entre les mises à niveau et les rétrogradations, provoquant efficacement une reconfiguration à partir de zéro.
--checkout-root dir
Extraire les packages provenant de dépôts basés sur le contrôle de version dans le répertoire spécifié plutôt que dans le répertoire de configuration. Référez-vous à l'option --output-root dans bpkg-pkg-checkout(1) pour plus de détails.
--checkout-purge
Supprimer les répertoires de packages (sources) extraits lorsque les packages sont purgés. Référez-vous à l'option --output-purge dans bpkg-pkg-checkout(1) pour plus de détails.
--config-name name
Nom de la configuration liée dans laquelle construire ce(s) package(s). Par défaut, le package est construit dans la configuration actuelle. Répétez cette option pour spécifier plusieurs configurations.
--config-id num
ID numérique de la configuration liée dans laquelle construire ce(s) package(s). Par défaut, le package est construit dans la configuration actuelle. Répétez cette option pour spécifier plusieurs configurations.
--config-uuid uuid
UUID de la configuration liée dans laquelle construire ce(s) package(s). Par défaut, le package est construit dans la configuration actuelle. Répétez cette option pour spécifier plusieurs configurations.

PKG-BUILD OPTIONS GLOBALES

--yes|-y
Suppose que la réponse à toutes les invites est yes. Notez que cela exclut les invites du gestionnaire de packages système ; voir --sys-yes pour plus de détails.
--for|-f operation
Au lieu de l'opération de système de build par défaut update, effectue la variante update-for-operation où operation est normalement install ou test.
--keep-unused|-K
Ne pas abandonner les packages de dépendance qui ont été construits automatiquement mais qui ne seront plus utilisés.
--update-dependent|-U
Mettre à jour sans confirmation les packages dépendants qui sont reconfigurés en raison de la mise à niveau ou de la rétrogradation de leurs dépendances.
--leave-dependent|-L
Ne pas proposer de mettre à jour les packages dépendants qui sont reconfigurés en raison de la mise à niveau ou de la rétrogradation de leurs dépendances.
--configure-only|-c
Configurer tous les packages mais ne pas mettre à jour.
--print-only
Afficher sur stdout ce qui serait fait sans rien faire réellement.
--plan header
Afficher le plan (même si --yes est spécifié) et le faire commencer par la ligne d'en-tête header (sauf si elle est vide).
--no-fetch
Ne pas extraire les dépôts spécifiés dans le cadre de la commande de build.
--fetch-shallow
Ne pas ré-extraire les dépôts complémentaires et prérequis des dépôts spécifiés dans le cadre de la commande de build. Référez-vous à l'option --shallow dans bpkg-rep-fetch(1) pour plus de détails.
--mask-repository rep
Pendant la durée de l'exécution de la commande, prétendre que le dépôt spécifié a été supprimé, comme si la commande rep-remove avait été exécutée. Le dépôt peut être spécifié soit par son nom, soit par son emplacement (URL ou chemin de répertoire). Notez que les dépôts complémentaires et prérequis du dépôt sont également considérés comme masqués, récursivement, sauf s'ils sont complémentaires et/ou prérequis d'autres dépôts non masqués. Répétez cette option pour masquer plusieurs dépôts.
--mask-repository-uuid v
Pendant la durée de l'exécution de la commande, prétendre que le dépôt spécifié a été supprimé de la configuration spécifiée. Similaire à --mask-repository mais ne masque le dépôt que dans une seule configuration. La valeur de l'option est une paire clé-valeur sous la forme :

config-uuid=rep

Répétez cette option pour masquer plusieurs dépôts.

--no-refinement
Ne pas essayer d'affiner la configuration en proposant de supprimer les dépendances inutilisées qui ont potentiellement été laissées lors de l'exécution précédente de la commande pkg-build ou pkg-drop si la commande est autrement un noop (n'effectue aucune nouvelle construction de package, mise à niveau, etc.).
--no-move
Ne pas déplacer les packages de dépendance entre les configurations. Dans ce mode, les options --config-* spécifient les emplacements actuels des packages plutôt que les nouveaux.
--noop-exit code
Sortir avec le code d'erreur spécifié si l'exécution de la commande est un noop (n'effectue aucune nouvelle construction de package, mise à niveau, etc.).
--rebuild-checksum sum
Hacher les noms, versions et configurations de tous les packages qui seraient construits. Si le checksum résultant correspond au checksum spécifié, sortir sans rien construire (potentiellement avec un code d'erreur spécial spécifié avec l'option --noop-exit). Sinon, procéder à la construction normale. Dans les deux cas, afficher le checksum résultant sur stdout.
--no-private-config code
S'il n'y a pas de configuration d'un type approprié liée pour construire une dépendance de temps de construction, au lieu de créer automatiquement une configuration privée de ce type, sortir avec le code d'erreur spécifié en affichant sur stdout la chaîne de dépendances commençant par la dépendance de temps de construction (avec sa contrainte, le cas échéant) et se terminant par la dépendance de niveau supérieur (avec ses répertoires de configuration), une entrée par ligne. Par exemple :

libbar/1.0.0 /path/to/li
