La partie la plus importante de bupstash est le dépôt. C'est là que toutes les données sont stockées sous une forme principalement chiffrée. Le client bupstash interagit avec le dépôt via stdin/stdout du processus bupstash-serve(1). Cela peut se faire localement, ou via un protocole tel que

ssh.

Comme la plupart des données sont chiffrées, la structure du dépôt est assez

La structure d'arbre de

hash

Bupstash stocke des flux de données arbitraires dans le dépôt en divisant le flux en morceaux, en adressant les morceaux par hmac, puis en compressant et chiffrant les morceaux avec la partie clé publique d'une clé bupstash. Chaque morceau est ensuite stocké dans le répertoire de données dans un fichier nommé d'après le hash hmac du contenu. Comme nous générons une séquence de morceaux avec des adresses hmac correspondantes, nous pouvons construire une structure d'arbre à partir de ces adresses. Les nœuds feuilles de l'arbre sont simplement les données chiffrées. Les autres nœuds de l'arbre sont simplement des listes non chiffrées de hash hmac, qui peuvent pointer vers des nœuds feuilles chiffrés ou d'autres sous-arbres. L'idée clé derrière l'arbre de hash est que nous pouvons convertir un flux de données arbitraire en une seule adresse HMAC avec des morceaux de taille approximativement égale. Lorsque plusieurs arbres de hash sont ajoutés au dépôt, ils partagent une structure et permettent la

déduplication.

Ce schéma d'adressage et de chiffrement a certaines propriétés importantes

:
○
Le propriétaire du dépôt ne peut pas deviner le contenu des morceaux car la clé HMAC est inconnue de
lui.
○
Le propriétaire du dépôt ne peut pas déchiffrer les feuilles de l'arbre de hash, car elles sont
chiffrées.
○
Le propriétaire du dépôt peut parcourir l'arbre de hash à des fins de collecte de
déchets.
○
Le propriétaire du dépôt peut exécuter une collecte de déchets sans récupérer les nœuds feuilles du stockage à
froid.
○
Le propriétaire du dépôt peut pousser un flux de nœuds d'arbre de hash vers un client sans aller-retour
réseau.
○
Un client peut envoyer des flux de données à un dépôt sans partager la clé de
chiffrement.
○
Un client peut récupérer et vérifier un flux de données en vérifiant les
hmacs.

Ces propriétés sont souhaitables pour permettre des p

erformances élevées de collecte de déchets et de
streaming de données avec préchargement côté dépôt.

Découpage et

déduplication

Les données sont dédupliquées en divisant un flux de données en petits morceaux, et en ne stockant jamais le même morceau deux fois. Les performances de cette déduplication sont donc déterminées par la façon dont les points de découpage des morceaux sont définis. Pour les lecteurs curieux - bupstash utilise quelque chose appelé « content def

ined chunking » pour trouver
des découpages de blocs efficaces.

Formats des

blocs

Les blocs dans la base de données sont de l'un des types suivants ; en général, nous connaissons le type d'un bloc à partir des métadonnées de l'élément et de la hauteur de l'arbre de

hachage.

Bloc de données

chiffré

Ces blocs forment les racines de nos arbres de hachage, ils contiennent des données chiffrées. Ils contiennent un paquet d'échange de clés, avec suffisamment d'informations pour que la clé maîtresse dérive la clé de

session.

]

Après déchiffrement, le bloc est éventuellement compressé, il s'agit donc soit de données compressées, soit de données avec un octet de pied de page

nul.

COMPRESSED_DATA[...] || DECOMPRESSED_SIZE[4] || COMPRESSION_TYPE[1

]

o

u

DATA[...] ||

0x00

Les types de compression valides sont

hachage

Ces blocs forment des nœuds non feuilles dans notre arbre de hachage, ils se composent d'un tableau d'adresses préfixé par le nombre total de blocs de données qui se trouvent sous eux dans
