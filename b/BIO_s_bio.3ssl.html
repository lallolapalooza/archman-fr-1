DESCRIPTIO

N

BIO_s_bio() renvoie la méthode pour un BIO pair. Un BIO pair est une paire de BIO source/puits où les données écrites dans l'une des moitiés de la paire sont mises en tampon et peuvent être lues depuis l'autre moitié. Les deux moitiés doivent généralement être gérées par le même thread d'application car aucun verrouillage n'est effectué sur les structures de données

internes.

Étant donné que les chaînes de BIO se terminent généralement par un BIO source/puits, il est possible de faire de celui-ci une moitié d'un BIO pair et d'avoir toutes les données traitées par la chaîne sous le contrôle de

l'application.

Une utilisation typique des BIO pairs est de placer les E/S TLS/SSL sous le contrôle de l'application ; cela peut être utilisé lorsque l'application souhaite utiliser un transport non standard pour TLS/SSL ou lorsque les routines de socket normales sont

inappropriées.

Les appels à BIO_read_ex() liront les données du tampon ou demanderont une nouvelle tentative si aucune donnée n'est

disponible.

Les appels à BIO_write_ex() placeront les données dans le tampon ou demanderont une nouvelle tentative si le tampon est

plein.

Les appels standard BIO_ctrl_pending() et BIO_ctrl_wpending() peuvent être utilisés pour déterminer la quantité de données en attente dans le tampon de lecture ou

d'écriture.

BIO_reset() efface toutes les données du tampon

d'écriture.

BIO_make_bio_pair() joint deux BIO distincts en une paire

connectée.

BIO_destroy_pair() détruit l'association entre deux BIO connectés. Libérer l'une des moitiés de la paire détruira automatiquement

l'association.

BIO_shutdown_wr() est utilisé pour fermer un BIO b. Après cet appel, aucune écriture supplémentaire sur le BIO b n'est autorisée (elles renverront une erreur). Les lectures sur l'autre moitié de la paire renverront les données en attente ou EOF lorsque toutes les données en attente ont été

lues.

BIO_set_write_buf_size() définit la taille du tampon d'écriture du BIO b à size. Si la taille n'est pas initialisée, une valeur par défaut est utilisée. Celle-ci est actuellement de 17K, suffisante pour un enregistrement TLS de taille

maximale.

BIO_get_write_buf_size() renvoie la taille du tampon

d'écriture.

BIO_new_bio_pair() combine les appels à BIO_new(), BIO_make_bio_pair() et BIO_set_write_buf_size() pour créer une paire connectée de BIO bio1, bio2 avec des tailles de tampon d'écriture writebuf1 et writebuf2. Si l'une des tailles est nulle, la taille par défaut est utilisée. BIO_new_bio_pair() ne vérifie pas si bio1 ou bio2 pointent vers un autre BIO, les valeurs sont écrasées, BIO_free() n'est pas

appelé.

BIO_get_write_guarantee() et BIO_ctrl_get_write_guarantee() renvoient la longueur maximale de données qui peut être actuellement écrite dans le BIO. Les écritures plus grandes que cette valeur renverront une valeur de BIO_write_ex() inférieure à la quantité demandée ou, si le tampon est plein, demanderont une nouvelle tentative. BIO_ctrl_get_write_guarantee() est une fonction alors que BIO_get_write_guarantee() est une

macro.

BIO_get_read_request() et BIO_ctrl_get_read_request() renvoient la quantité de données demandée, ou la taille du tampon si elle est inférieure, si la dernière tentative de lecture sur l'autre moitié du BIO pair a échoué en raison d'un tampon vide. Cela peut être utilisé pour déterminer combien de données doivent être écrites dans le BIO pour que la prochaine lecture réussisse : c'est le plus utile dans les applications TLS/SSL où la quantité de données lue est généralement significative plutôt qu'une simple taille de tampon. Après une lecture réussie, cet appel renverra zéro. Il renverra également zéro une fois que de nouvelles données ont été écrites satisfaisant la demande de lecture ou une partie de celle-ci. Notez que BIO_get_read_request() ne renvoie jamais une quantité supérieure à celle renvoyée par BIO_get_write_gua

rantee().

BIO_ctrl_reset_read_request() peut également être utilisé pour réinitialiser la valeur renvoyée par BIO_get_read_re

quest()
à zéro.

NOTE

S

Les deux moitiés d'un BIO pair doivent être libérées. C'est-à-dire que même si une moitié est implicitement libérée en raison d'un appel à BIO_free_all() ou SSL_free(), l'autre moitié doit être

libérée.

Lorsqu'il est utilisé dans des applications bidirectionnelles (telles que TLS/SSL), il faut veiller à vider tout les données du tampon d'écriture. Cela peut être fait en appelant BIO_pending() sur l'autre moitié de la paire et, si des données sont en attente, en les lisant et en les envoyant au transport sous-jacent. Cela doit être fait avant tout traitement normal (comme appeler select() ) en raison d'une demande et BIO_should_read() étant

vrai.

Pour comprendre pourquoi cela est important, considérons un cas où une demande est envoyée en utilisant BIO_write_ex() et une réponse est lue avec BIO_read_ex() ; cela peut se produire lors d'une poignée de main TLS/SSL par exemple. BIO_write_ex() réussira et placera les données dans le tampon d'écriture. BIO_read_ex() échouera initialement et BIO_should_read() sera vrai. Si l'application attend ensuite que des données soient disponibles sur le transport sous-jacent avant de vider le tampon d'écriture, elle ne réussira jamais car la demande n'a jamais été envoyée

!

BIO_eof() est vrai si aucune donnée n'est dans le BIO pairé et si le BIO pairé a été

fermé.

EXEMPLE

S

Le BIO pair peut être utilisé pour avoir un contrôle total sur l'accès réseau d'une application. L'application peut appeler select() sur le socket au besoin sans avoir à passer par l'interface

SSL. 
BIO *internal_bio, *network_bio;
...
BIO_new_bio_pair(&internal_bio, 0, &network_bio, 0);
SSL_set_bio(ssl, internal_bio, internal_bio);
SSL_operations(); /* ex. SSL_read et SSL_write */
...
application |   moteur TLS
   |        |
   +----------> SSL_operations()
            |     /\    ||
            |     ||    \/
            |   BIO-pair (internal_bio)
            |   BIO-pair (network_bio)
            |     ||     /\
            |     \/     ||
   +-----------< BIO_operations()
   |        |
   |        |
  socket
 ...
 SSL_free(ssl);                /* libère implicitement internal_bio */
 BIO_free(network_bio);
 ..
.

Comme le BIO pair ne mettra les données en tampon et n'accédera jamais directement à la connexion, il se comporte de manière non bloquante et renverra dès que le tampon d'écriture est plein ou que le tampon de lecture est vidé. L'application doit alors vider le tampon d'écriture et/ou remplir le tampon de

lecture.

Utilisez BIO_ctrl_pending() pour savoir si des données sont mises en tampon dans le BIO et doivent être transférées vers le réseau. Utilisez BIO_ctrl_get_read_request() pour savoir combien d'octets doivent être écrits dans le tampon avant que SSL_operation() puisse êtr

e continué
avec succès.

AVERTISSEMEN

TS

Comme les données sont mises en tampon, SSL_operation() peut renvoyer avec une condition ERROR_SSL_WANT_READ, mais il reste des données dans le tampon d'écriture. Une application ne doit pas se fier à la valeur d'erreur de SSL_operation() mais doit s'assurer que le tampon d'écriture est toujours vidé en premier. Sinon, un

blocage mutuel peut survenir car le pair pourrait
attendre les données avant de pouvoir continuer.
