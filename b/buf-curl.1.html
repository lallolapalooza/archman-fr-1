buf-curl - Invoquer un

point d'entrée RPC,
à la manière de 'cURL'

SYNOPSI

S

buf cu

rl [dra
peaux]

DESCRIPTIO

N

Cette commande vous aide à invoquer des points d'entrée RPC HTTP sur un serveur utilisant gRPC ou

Connect.

Par défaut, la réflexion côté serveur est utilisée, sauf si le drapeau --reflect est défini à false. Sans réflexion côté serveur, un drapeau --schema doit être fourni pour indiquer le schéma Protobuf de la méthode

invoquée.

Le seul argument positionnel est l'URL de la méthode RPC à invoquer. Le nom de la méthode à invoquer provient des deux derniers composants du chemin de l'URL, qui doivent être respectivement le nom de service entièrement qualifié et le nom de la

méthode.

L'URL peut utiliser soit http, soit https comme schéma. Si http est utilisé, alors HTTP 1.1 sera utilisé, sauf si le drapeau --http2-prior-knowledge est défini. Si https est utilisé, alors HTTP/2 sera préféré lors de la négociation de protocole et HTTP 1.1 ne sera utilisé que si le serveur ne prend pas en charge

HTTP/2.

Le protocole RPC par défaut utilisé sera Connect. Pour utiliser un autre protocole (gRPC ou gRPC-Web), utilisez le drapeau --protocol. Notez que le protocole gRPC ne peut pas être utilisé avec HTTP 1.

1.

La requête d'entrée est spécifiée via le drapeau -d ou --data. Si absent, une requête vide est envoyée. Si la valeur du drapeau commence par un arobase (@), alors le reste de la valeur du drapeau est interprété comme un nom de fichier à partir duquel lire le corps de la requête. Si ce nom de fichier est simplement un tiret (-), alors le corps de la requête est lu depuis stdin. Le corps de la requête est un document JSON contenant le message de requête formaté en JSON. Si la méthode RPC invoquée est une méthode de streaming côté client, le corps de la requête peut se composer de plusieurs valeurs JSON, les unes à la suite des autres. Les documents JSON doivent généralement être séparés par des espaces, bien que cela ne soit pas strictement requis, sauf si le type de message de requête a une représentation JSON personnalisée qui n'est pas un objet

JSON.

Les métadonnées de requête (c'est-à-dire les en-têtes) sont définies à l'aide des drapeaux -H ou --header. La valeur du drapeau est au format "name: value". Mais si elle commence par un arobase (@), le reste de la valeur est interprété comme un nom de fichier à partir duquel les en-têtes sont lus, chacun sur une ligne séparée. Si le nom de fichier est simplement un tiret (-), alors les en-têtes sont lus depuis

stdin.

Si les en-têtes et le corps de la requête doivent tous deux être lus depuis le même fichier (ou tous deux lus depuis stdin), le fichier doit inclure les en-têtes d'abord, puis une ligne vide, puis le corps de la

requête.

Exemples

:

Émettre un RPC unaire vers un serveur gRPC en texte clair (c'est-à-dire "h2c"), où le schéma du service se trouve dans un module Buf dans le répertoire courant, en utilisant un message de requête vide

: 
$ buf curl --schema . --protocol grpc --http2-prior-knowledge  \
     http://localhost:20202/foo.bar.v1.FooService/DoSomethin
g

Émettre un RPC vers un serveur Connect, où le schéma provient du Buf Schema Registry, en utilisant une requête définie comme argument de ligne de commande

: 
$ buf curl --schema buf.build/connectrpc/eliza  \
     --data '{"name": "Bob Loblaw"}'          \
     https://demo.connectrpc.com/connectrpc.eliza.v1.ElizaService/Introduc
e

Émettre un RPC unaire vers un serveur prenant en charge la réflexion, avec une sortie verbeuse

: 
$ buf curl --data '{"sentence": "I am not feeling well."}' -v  \
	 https://demo.connectrpc.com/connectrpc.eliza.v1.ElizaService/Sa
y

Émettre un RPC de streaming côté client vers un serveur gRPC-web prenant en charge la réflexion, où les en-têtes personnalisés et les données de requête se trouvent tous deux dans un heredoc

: 
$ buf curl --data @- --header @- --protocol grpcweb                              \
	 https://demo.connectrpc.com/connectrpc.eliza.v1.ElizaService/Converse  \
   <<EOM
Custom-Header-1: foo-bar-baz
Authorization: token jas8374hgnkvje9wpkerebncjqol4
{"sentence": "Hi, doc. I feel hungry."}
{"sentence": "What is the answer to life, the universe, and everything?"}
{"sentence": "If you were a fish, what of fish would you be?."}
EOM

Notez que la réflexion côté serveur (c'est-à-dire l'utilisation du drapeau --reflect) ne fonctionne pas avec HTTP 1.1 car le protocole repose sur le streaming bidirectionnel. Si la réflexion côté serveur est utilisée, l'URL supposée pour le service de réflexion est la même que l'URL donnée, mais avec les deux derniers éléments supprimés et remplacés par le nom du service et de la méthode pour la réflexion côté

serveur.

Si une erreur se produit due à une utilisation incorrecte ou à une autre erreur inattendue,

ce programme retournera un code de sortie inférieur à 8. Si le RPC échoue autrement, ce progr
amme retournera un code de sortie qui est le code gRPC, décalé de trois bits vers la gauche.

--cacert="" Chemin vers un fichier de pool de certificats X509 encodé en PEM qui contient l'ensemble des autorités/émetteurs de certificats de confiance. Si omis, l'ensemble par défaut de certificats de confiance du système est utilisé pour vérifier le certificat du serveur. Cette option n'est valide que lorsque l'URL utilise le schéma https. Elle ne s'applique pas si le drapeau --insecure ou -k est

utilisé

-E, --cert="" Chemin vers un fichier de certificat X509 encodé en PEM, pour utiliser des certificats clients avec TLS. Cette option n'est valide que lorsque l'URL utilise le schéma https. Un drapeau --key doit également être présent pour fournir la clé privée correspondant au certificat

donné

--connect-timeout=0 La limite de temps, en secondes, pour établir une connexion avec le serveur. Il n'y a pas de limite si ce drapeau n'est pas

présent

-d, --data="" Données de requête. Il doit s'agir de zéro ou plusieurs documents JSON, chacun indiquant un message de requête. Pour les RPC unaires, il doit y avoir exactement un document JSON. Une valeur spéciale de '@' signifie lire les données depuis le fichier à . Si le chemin est "-", alors les données de requête sont lues depuis stdin. Si le même fichier est indiqué comme celui utilisé avec les drapeaux d'en-têtes de requête (--header ou -H), le fichier doit contenir tous les en-têtes, puis une ligne vide, puis le corps de la requête. Il n'est pas permis d'indiquer stdin si le schéma doit être fourni via stdin comme jeu de descripteurs de fichier ou

image

--emit-defaults[=false] Émettre les valeurs par défaut pour les réponses encodées en

JSON.

-H, --header=[] En-têtes de requête à inclure avec l'invocation RPC. Ce drapeau peut être spécifié plusieurs fois pour indiquer plusieurs en-têtes. Chaque valeur de drapeau doit avoir la forme "name: value". Une valeur spéciale de '@' signifie lire les en-têtes depuis le fichier à . Si le chemin est "-", alors les en-têtes sont lus depuis stdin. Si le même fichier est indiqué comme celui utilisé avec le drapeau de données de requête (--data ou -d), le fichier doit contenir tous les en-têtes, puis une ligne vide, puis le corps de la requête. Il n'est pas permis d'indiquer stdin si le schéma doit être fourni via stdin comme jeu de descripteurs de fichier ou

image

-h, --help[=false] aide pour

--http2-prior-knowledge[=false] Ce drapeau peut être utilisé pour indiquer que HTTP/2 doit être utilisé. Sans cela, HTTP 1.1 sera utilisé avec les URLs ayant un schéma http, et la négociation de protocole sera utilisée pour choisir soit HTTP 1.1, soit HTTP/2 pour les URLs ayant un schéma https. Avec ce drapeau défini, HTTP/2 est toujours utilisé, même en texte

clair.

--http3[=false] Ce drapeau peut être utilisé pour indiquer que HTTP/3 doit être utilisé. Sans cela, HTTP 1.1 sera utilisé avec les URLs ayant un schéma http, et la négociation de protocole sera utilisée pour choisir soit HTTP 1.1, soit HTTP/2 pour les URLs ayant un schéma https. Avec ce drapeau défini, HTTP/3 est toujours

utilisé.

-k, --insecure[=false] Si défini, la connexion TLS sera non sécurisée et le certificat du serveur NE SERA PAS vérifié. Cela est généralement déconseillé. Cette option n'est valide que lorsque l'URL utilise le schéma

https

--keepalive-time=60 La durée, en secondes, entre les transmissions de maintien de connexion

TCP

--key="" Chemin vers un fichier de clé privée X509 encodé en PEM, pour utiliser des certificats clients avec TLS. Cette option n'est valide que lorsque l'URL utilise le schéma https. Un drapeau --cert ou -E doit également être présent pour fournir le certificat et la clé publique correspondant à la clé privée

donnée

--list-methods[=false] Lorsqu'il est défini, la commande liste les méthodes prises en charge puis se termine. Si la réflexion côté serveur est utilisée pour fournir le schéma RPC, alors l'URL donnée doit être une URL de base, n'incluant pas de nom de service ou de méthode. Si la source du schéma n'est pas la réflexion côté serveur, l'URL n'est pas utilisée et peut être

omise.

--list-services[=false] Lorsqu'il est défini, la commande liste les services pris en charge puis se termine. Si la source du schéma n'est pas la réflexion côté serveur, l'URL n'est pas utilisée et peut être

omise. p">-n, --netrc[=false] Si vrai, un fichier nommé .netrc dans le répertoire personnel de l'utilisateur sera examiné pour trouver les identifiants de la requête. --netrc-file="" C'est exactement comme utiliser --netrc ou -n, sauf que le fichier nommé est utilisé à la place d'un fichier nommé .netrc dans le répertoire personnel de l'utilisateur. Cet indicateur ne peut pas être utilisé avec l'indicateur --netrc ou -n. Il est ignoré si un indicateur --header ou -H est fourni qui définit un en-tête nommé 'Authorization'

-o, --output="" Chemin du fichier de sortie à créer avec les données de réponse. Si absent, la réponse est imprimée sur

--reflect[=true] Si vrai, utiliser le reflet serveur pour déterminer le

--reflect-header=[] En-têtes de requête à inclure avec les requêtes de reflet. Cet indicateur ne peut être utilisé que lorsque --reflect est également défini. Cet indicateur peut être spécifié plus d'une fois pour indiquer plusieurs en-têtes. Chaque valeur d'indicateur doit avoir la forme "name: value". Mais une valeur spéciale de '*' peut être utilisée pour indiquer que tous les en-têtes de requête normaux (depuis les indicateurs --header et -H) doivent également être inclus avec les requêtes de reflet. Une valeur spéciale de '@' signifie lire les en-têtes depuis le fichier à . Si le chemin est "-" alors les en-têtes sont lus depuis stdin. Il n'est pas autorisé d'indiquer un fichier avec le même chemin que celui utilisé avec l'indicateur de données de requête (--data ou -d). De plus, il n'est pas autorisé d'indiquer stdin si le schéma est censé être fourni via stdin comme jeu de descripteurs de fichier ou

image

--reflect-protocol="" Le protocole de reflet à utiliser pour télécharger les informations depuis le serveur. Cet indicateur ne peut être utilisé que lorsque le reflet serveur est utilisé. Par défaut, cette commande essaiera tous les protocoles de reflet connus du plus récent au plus ancien. Si cela résulte en une erreur "Not Implemented", alors les protocoles plus anciens seront utilisés. En pratique, cela signifie que "grpc-v1" est essayé en premier, et "grpc-v1alpha" est utilisé si cela ne fonctionne pas. Si des protocoles de reflet plus récents sont introduits, ils peuvent être préférés en l'absence de cet indicateur explicitement défini sur un protocole spécifique. Les valeurs valides pour cet indicateur sont "grpc-v1" et "grpc-v1alpha". Celles-ci correspondent aux services nommés "grpc.reflection.v1.ServerReflection" et "grpc.reflection.v1alpha.ServerReflection"

respectivement

--schema=[] Le module à utiliser pour le schéma RPC. Cela est nécessaire si le serveur ne prend pas en charge le reflet serveur. Le format de cet argument est le même que pour les arguments des autres sous-commandes buf telles que build et generate. Il peut indiquer un répertoire, un fichier, un module distant dans le Buf Schema Registry, ou même stdin ("-") pour alimenter une image ou un jeu de descripteurs de fichier à la commande dans un pipeline shell. Si plusieurs indicateurs schema sont présents, ils seront consultés dans l'ordre pour résoudre les noms de service et de type. Définir cet indicateur implique --reflect=false sauf si un indicateur reflect est explicitement présent. Si les indicateurs schema et reflect sont utilisés, le reflet sera utilisé en premier et les schémas seront consultés dans l'ordre par la suite si le reflet échoue à résoudre un élément de

schéma.

--servername="" Le nom du serveur à utiliser dans les poignées de main TLS (pour SNI) si le schéma d'URL est https. Si non spécifié, la valeur par défaut est l'hôte d'origine dans l'URL ou la valeur dans un en-tête "Host" si celui-ci est

fourni

--unix-socket="" Le chemin d'un socket unix qui sera utilisé à la place d'ouvrir un socket TCP vers l'hôte et le port indiqués dans

l'URL

-u, --user="" Les identifiants utilisateur à envoyer, via un en-tête d'autorisation basique. La valeur doit être au format "username:password". Si la valeur n'a pas de deux-points, on suppose que c'est simplement le nom d'utilisateur, auquel cas on vous demandera de saisir un mot de passe. Cela remplace l'utilisation d'un fichier .netrc. C'est ignoré si un indicateur --header ou -H est fourni qui définit un en-tête nommé 'Authorization'

.

-A, --user-agent="" La chaîne user agent à envoyer. C'est ignoré si un indicateur --header ou -H est fourni qui définit un en-tête nommé

'User-Agent'.
