DESCRIPTIO

N

Avant que de nombreux outils IPMI puissent être utilisés sur un réseau, le contrôleur de gestion de carte mère (BMC) d'une machine doit être configuré. La configuration peut être assez intimidante pour ceux qui ne connaissent pas bien IPMI. Cette page man espère fournir suffisamment d'informations sur la configuration du BMC afin que vous puissiez configurer le BMC pour votre système. Lorsque c'est approprié, des configurations BMC typiques seront

suggérées.

Voici un exemple de fichier de configuration partiellement généré en exécutant l'option --checkout avec la commande ipmi-config(8). Cette configuration provient de la catégorie core des valeurs de configuration (par défaut). Cette configuration d'exemple devrait être suffisante pour la plupart des utilisateurs après la saisie des adresses IP et MAC locales appropriées. À la suite de cet exemple, des sections séparées de cette page man discuteront des différentes sections du fichier de configuration plus en détail avec des explications sur la façon dont le BMC peut être configuré pour différents

environnements.

Notez que de nombreuses options peuvent être disponibles ou non sur votre machine particulière. Par exemple, Serial-Over-Lan (SOL) n'est disponible que sur les machines IPMI 2.0. Par conséquent, si vous cherchez à configurer une machine IPMI 1.5, de nombreuses options liées à SOL ou à IPMI 2.0 ne vous seront pas disponibles. Le nombre d'utilisateurs configurables peut également varier pour votre machine

particulière.

Le fichier de configuration ci-dessous et la plupart de cette page man supposent que l'utilisateur souhaite configurer un BMC pour une utilisation avec IPMI sur LAN. Diverses options de configuration de ipmi-config(8) ont été laissées de côté ou ignorées car elles sont considérées comme inutiles. Les futures versions de cette page man essayeront d'inclure plus

d'informations.

Section User1, User2, ..

.

Les sections User du fichier de configuration du BMC servent à configurer les noms d'utilisateur pour la communication IPMI sur LAN. Le nombre d'utilisateurs configurables sur votre système varie selon le fabricant. À l'exception du nom d'utilisateur pour User1, toutes les sections sont

identiques.

Le ou les noms d'utilisateur que vous souhaitez configurer pour le BMC sont définis avec Username. Le premier nom d'utilisateur sous Section User1 est généralement le nom d'utilisateur NULL et ne peut pas être modifié. Le mot de passe pour le nom d'utilisateur peut être spécifié avec Password. Il peut être laissé vide pour définir un mot de passe NULL. Chaque utilisateur que vous souhaitez activer doit être activé via l'option de configuration Enable_User. Il est recommandé que tous les noms d'utilisateur aient des mots de passe non-NULL ou soient désactivés pour des raisons de

sécurité.

Lan_Enable_Ipmi_Msgs est utilisé pour activer ou désactiver l'accès IPMI sur LAN pour l'utilisateur. Cela devrait être défini sur "Yes" pour permettre aux outils IPMI sur LAN de

fonctionner.

Lan_Privilege_Limit spécifie la limite de niveau de privilège maximum autorisée pour l'utilisateur. Différentes commandes IPMI ont différentes restrictions de privilège. Par exemple, déterminer l'état d'alimentation d'une machine ne nécessite que le niveau de privilège "User". Cependant, le cycle d'alimentation nécessite le privilège "Operator". Généralement, vous voudrez attribuer au moins un utilisateur avec une limite de privilège de "Administrator" afin que toutes les fonctions du système soient disponibles pour au moins un utilisateur via IPMI sur

LAN.

Lan_Session_Limit spécifie le nombre de sessions IPMI simultanées autorisées pour l'utilisateur. La plupart des utilisateurs voudront définir cela à "0" pour autoriser un nombre illimité de sessions IPMI simultanées. Ce champ est considéré comme facultatif par les normes IPMI et peut entraîner des erreurs lors de la tentative de le configurer avec une valeur non nulle. Si des erreurs surviennent, remettre la valeur à 0 devrait résoudre les

problèmes.

SOL_Payload_Access spécifie si un utilisateur particulier est autorisé à se connecter avec Serial-Over-LAN (SOL). Cela devrait être défini sur "Yes" pour autoriser ce nom d'utilisateur à utiliser

SOL.

La configuration d'exemple ci-dessus désactive "User2" mais active l'utilisateur par défaut "NULL" (c'est-à-dire anonyme). De nombreux outils IPMI (open source et fournisseurs) ne permettent pas à l'utilisateur de saisir un nom d'utilisateur et supposent le nom d'utilisateur NULL par défaut. Si les outils que vous souhaitez utiliser permettent la saisie de noms d'utilisateur, il est recommandé qu'un des noms d'utilisateur non-NULL soit activé et que le nom d'utilisateur NULL soit désactivé pour des raisons de sécurité. Il est recommandé de désactiver le nom d'utilisateur NULL dans la section User1, afin que les utilisateurs soient tenus de spécifier un nom d'utilisateur pour la communication IPMI sur

LAN.

Certaines cartes mères peuvent nécessiter qu'un Username soit configuré avant que les autres champs ne soient lus/écrits. Si c'est le cas, ces champs seront définis sur <username-no

t-set
-yet>.

Section

Lan_Channel

La section Lan_Channel configure une variété de paramètres de configuration IPMI sur LAN. Les configurations Volatile et Non_Volatile peuvent être définies. Les configurations Volatile sont immédiatement configurées sur le BMC et auront un effet immédiat sur le système. Les configurations Non_Volatile ne sont disponibles qu'après la prochaine réinitialisation du système. Généralement, les Volatile et Non_Volatile devraient être configurés de manière

identique.

Le paramètre Access_Mode configure la disponibilité d'IPMI sur LAN sur le système. Généralement, cela devrait être défini sur "Always_Available" pour activer IPMI sur

LAN.

Le Privilege_Limit définit le privilège maximum que tout utilisateur du système peut avoir lors de l'exécution d'IPMI sur LAN. Cela devrait être défini au niveau de privilège maximum configuré pour un nom d'utilisateur. Généralement, cela devrait être défini sur "Administrator"

.

Généralement User_Level_Auth et Per_Message_Auth devraient être définis sur "Yes" pour une sécurité supplémentaire. Désactiver User_Level_Auth permet l'exécution des commandes IPMI privilégiées "User" sans authentification. Désactiver Per_Message_Auth permet à moins de messages IPMI individuels de nécessiter une authentificatio

n
.

Section

Lan_Conf_Auth

Cette section détermine quels types de mécanismes d'authentification de mot de passe sont autorisés pour les utilisateurs à différents niveaux de privilège sous le protocole IPMI 1.5. Les méthodes d'authentification actuellement prises en charge pour IPMI 1.5 sont None (nom d'utilisateur/mot de passe non requis), Straight_Password (les mots de passe sont envoyés en clair), MD2 (les mots de passe sont hachés avec MD2), et MD5 (les mots de passe sont hachés avec MD5). Différents noms d'utilisateur à différents niveaux de privilège peuvent être autorisés à s'authentifier différemment via cette configuration. Par exemple, un nom d'utilisateur avec les privilèges "User" peut être autorisé à s'authentifier avec un mot de passe en clair, mais un nom d'utilisateur avec les privilèges "Administrator" peut être autorisé à s'authentifier uniquement avec

MD5.

La configuration d'exemple ci-dessus prend en charge MD2 et MD5 l'authentification pour tous les utilisateurs aux niveaux de privilège "User", "Operator", et "Administrator". Tous les mécanismes d'authentification ont été désactivés pour le niveau de privilège

"Callback".

En général, vous ne voulez pas autoriser un utilisateur quelconque à s'authentifier avec None ou Straight_Password pour des raisons de sécurité. MD2 et MD5 sont des algorithmes de signature numérique qui peuvent chiffrer les mots de passe au minimum. Si vous avez choisi de prendre en charge le nom d'utilisateur NULL (User1 activé) et les mots de passe NULL (mot de passe NULL pour User1), vous devrez activer les champs d'authentification None ci-dessus pour permettre aux utilisateurs de se connecter via No

ne
.

Section

Lan_Conf_Misc

Cette section liste les options de configuration IPMI sur LAN diverses. Ce sont des options de configuration IPMI facultatives qui ne sont pas implémentées sur tous les

BMC.

Normalement, un client ne peut pas résoudre l'adresse MAC Ethernet sans que le système d'exploitation distant soit en cours d'exécution. Cependant, IPMI sur LAN ne fonctionnerait pas lorsque la machine est éteinte ou si l'adresse IP utilisée par le système d'exploitation pour cette interface réseau diffère de l'adresse IP du BMC. Une façon de contourner cela est via les ARP gratuits. Les ARP gratuits sont des paquets ARP générés par le BMC et envoyés pour annoncer l'adresse IP et MAC du BMC. Les autres machines sur le réseau peuvent stocker ces informations dans leur cache ARP local pour une résolution ultérieure d'IP/nom d'hôte. Cela permettrait à IPMI sur LAN de fonctionner lorsque la machine distante est éteinte. L'option Enable_Gratuitous_Arps vous permet d'activer ou de désactiver cette fonctionnalité. L'option Gratuitous_Arp_Interval vous permet de configurer la fréquence à laquelle les ARP gratuits sont envoyés sur le

réseau.

Au lieu des ARP gratuits, certains BMC sont capables de répondre aux requêtes ARP, même lorsqu'ils sont éteints. Si cette fonctionnalité est offerte, elle peut être activée via l'option Enable_Arp_Response

.

En général, l'activation des ARP gratuits est acceptable. Cependant, cela augmentera le trafic sur votre réseau. Si vous utilisez IPMI sur un grand cluster, les ARP gratuits peuvent facilement submerger votre réseau. Ils devraient être réglés pour se produire moins fréquemment ou être désactivés. S'ils sont désactivés, l'adresse MAC de la machine distante devrait être stockée de manière permanente dans le cache ARP local via arp(8)

.

Voir bmc-watchdog(8) pour une méthode qui permet de désactiver les ARP gratuits lorsque le système

d'exploitation est en cours d'exécution, mais
de les activer lorsque le système est à l'arrêt.

e

Cette section prend en charge la configuration des identifiants de suite de chiffrement IPMI 2.0 (y compris Serial-over-LAN). Si votre machine ne prend pas en charge IPMI 2.0, les champs ne seront pas

Chaque identifiant de suite de chiffrement décrit une combinaison d'un algorithme d'authentification, d'un algorithme d'intégrité et d'un algorithme de chiffrement pour IPMI 2.0. L'algorithme de confidentialité est utilisé pour chiffrer les données. Section Lan_Conf_Auth

Cette section est pour le paramétrage des algorithmes d'authentification, d'intégrité et de chiffrement pour les canaux LAN. Le niveau de privilège minimum requis pour se connecter via ces algorithmes est spécifié par Privilege_Level. Cette valeur doit être réglée au niveau de privilège maximum configuré pour un nom d'utilisateur qui a accès aux algorithmes d'authentification, d'intégrité et de chiffrement. Typiquement, ceci est le privilège "Administrator".

Les champs Force_Authentication, Force_Integrity et Force_Confidentiality peuvent être utilisés pour forcer ces algorithmes. Il est recommandé de les activer. Cependant, le support forcé de l'authentification, de l'intégrité et/ou du chiffrement dépend des identifiants des suites de chiffrement supportés.

13 - Algorithme d'authentification = HMAC-MD5 ; Algorithme d'intégrité = MD5-128 ; Algorithme de chiffrement = xRC4-128

14 - Algorithme d'authentification = HMAC-MD5 ; Algorithme d'intégrité = MD5-128 ; Algorithme de chiffrement = xRC4-40

En général, les algorithmes basés sur HMAC-SHA1 sont plus robustes que ceux basés sur HMAC-MD5, qui sont meilleurs que les algorithmes MD5-128. Les algorithmes de chiffrement AES-CBC-128 sont plus robustes que les algorithmes xRC4-128, qui sont meilleurs que les algorithmes xRC4-40. L'identifiant de suite de chiffrement 3 est donc généralement considéré comme le plus sûr. Certains utilisateurs peuvent souhaiter définir l'identifiant de suite de chiffrement 3 à un niveau de privilège et désactiver tous les autres identifiants de suites de chiffrement.

L'exemple de configuration ci-dessus a décidé d'autoriser tout utilisateur ayant des privilèges "Administrator" à utiliser n'importe quelle suite d'algorithmes de chiffrement qui nécessite un algorithme d'authentification, d'intégrité et de chiffrement. Typiquement, le niveau de privilège maximum configuré pour un nom d'utilisateur doit être défini pour au moins un identifiant de suite de chiffrement. Typiquement, il s'agit du privilège "Administrator".

Un certain nombre d'identifiants de suites de chiffrement sont implémentés en option, de sorte que les identifiants de suites de chiffrement disponibles sur votre système peuvent varier.

Section SOL_Conf

Cette section est dédiée à la configuration du Serial-Over-Lan (SOL) et ne sera disponible à la configuration que sur les machines concernées. SOL peut être activé avec le champ Enable_SOL. Le niveau de privilège minimum requis pour se connecter avec SOL est spécifié par SOL_Privilege_Level. Cette valeur doit être réglée au niveau de privilège maximum configuré pour un nom d'utilisateur qui a SOL activé. Typiquement, il s'agit du privilège "Administrator". L'authentification et le chiffrement peuvent être forcés ou non en utilisant respectivement les champs Force_SOL_Payload_Authentication et Force_SOL_Payload_Encryption. Il est recommandé de les activer. Cependant, le support forcé de l'authentification et/ou du chiffrement dépend des identifiants des suites de chiffrement supportés.

Les options Character_Accumulate_Interval, Character_Send_Threshold, SOL_Retry_Count et SOL_Retry_Interval sont utilisées pour définir les vitesses de sortie des caractères SOL. Character_Accumulate_Interval détermine la fréquence à laquelle les données série doivent être envoyées régulièrement et Character_Send_Threshold indique le nombre de caractères qui, s'il est dépassé, forcera l'envoi des données série. SOL_Retry_Count indique le nombre de fois où les paquets doivent être retransmis si les accusés de réception ne sont pas reçus. SOL_Retry_Interval indique l'intervalle de temps d'attente. Généralement, les nombres recommandés par le fabricant seront suffisants. Cependant, vous pourriez souhaiter expérimenter avec ces valeurs pour un débit SOL plus rapide.

Non_Volatile_Bit_Rate et Volatile_Bit_Rate déterminent le débit en bauds que le BMC doit utiliser. Ceci doit correspondre au débit en bauds réglé dans le BIOS et le système d'exploitation, tel que agetty(8). En règle générale, les options Volatile et Non_Volatile doivent être réglées de manière identique.

En plus d'activer SOL dans cette section, les utilisateurs individuels doivent également être capables de se connecter avec SOL. Voir la section Section User1, User2, ... ci-dessus pour plus de détails.
