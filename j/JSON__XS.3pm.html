INCRÉMENTALE

Dans certains cas, il est nécessaire d'analyser de manière incrémentale les textes JSON. Bien que ce module doive toujours garder à la fois le texte JSON et la structure de données Perl résultante en mémoire en même temps, il vous permet d'analyser un flux JSON de manière incrémentale.    or die "bigfile: $!";

   sysread $fh, my $buf, 65536
      or die "read error: $!";
   $json->incr_parse ($buf); # void context, so no parsing
   # Exit the loop once we found and removed(!) the initial "[".
   # In essence, we are (ab-)using the $json object as a simple scalar
   # we append data to.
   last if $json->incr_text =~ s/^ \s* \[ //x;
}
# now we have the skipped the initial "[", so continue
# parsing all the elements.
for (;;) {
   # in this loop we read data until we got a single JSON object
   for (;;) {
      if (my $obj = $json->incr_parse) {
         # do something with $obj
         last;
      }
      # add more data
      sysread $fh, my $buf, 65536
         or die "read error: $!";
      $json->incr_parse ($buf); # void context, so no parsing
   }
   # in this loop we read data until we either found and parsed the
   # separating "," between elements, or the final "]"
   for (;;) {
      # first skip whitespace
      $json->incr_text =~ s/^\s*//;
      # if we find "]", we are done
      if ($json->incr_text =~ s/^\]//) {
         print "finished.\n";
         exit;

      # if we find ",", we can continue avec l'élément suivant
      if ($json->incr_text =~ s/^,//) {
         last;
      }
      # si nous trouvons autre chose, il y a une erreur d'analyse !
      if (length $json->incr_text) {
         die "parse error near ", $json->incr_text;
      }
      # sinon ajouter plus de données
      sysread $fh, my $buf, 65536
         or die "read error: $!";
      $json->incr_parse ($buf); # contexte void, donc pas d'analyse
}

Si aucun des paramètres n'est activé ou si les méthodes respectives sont absentes, "JSON::XS" lèvera une exception.

Pour la désérialisation, il n'y a que deux cas à considérer : soit une étiquette non standard a été utilisée, auquel cas "allow_tags" décide, soit les objets ne peuvent pas être désérialisés automatiquement, auquel cas vous pouvez utiliser le post-traitement ou les rappels "filter_json_object" ou "filter_json_single_key_object" pour obtenir des objets réels à partir de votre JSON.

Cette section ne considère que le cas des valeurs étiquetées : si un objet JSON étiqueté est rencontré lors du décodage et que "allow_tags" est désactivé, une erreur d'analyse surviendra (comme si les valeurs étiquetées ne faisaient pas partie de la grammaire).

Si "allow_tags" est activé, "JSON::XS" recherchera la méthode "THAW" du nom de package/classe utilisé lors de la sérialisation (il ne tentera pas de charger le package en tant que module Perl). S'il n'y a pas de telle méthode, le décodage échouera avec une erreur.

Sinon, la méthode "THAW" est invoquée avec le nom de classe comme premier argument, la chaîne constante "JSON" comme second argument, et toutes les valeurs du tableau JSON (les valeurs retournées à l'origine par la méthode "FREEZE") comme arguments restants.

La méthode doit alors retourner l'objet. Bien que techniquement vous puissiez retourner n'importe quel scalaire Perl, vous pourriez avoir à activer le paramètre "enable_nonref" pour que cela fonctionne dans tous les cas, il est donc préférable de retourner une référence enveloppée réelle.

À titre d'exemple, implémentons une fonction "THAW" qui régénère le "My::Object" de l'exemple "FREEZE" précédent :

sub My::Object::THAW {
   my ($class, $serialiser, $type, $id) = @_;
   $class->new (type => $type, id => $id)
}

NOTES SUR LES INDICATEURS D'ENCODAGE/CODESET

Le lecteur intéressé a peut-être vu un certain nombre d'indicateurs qui signifient des encodages ou des jeux de caractères - "utf8", "latin1" et "ascii". Il semble y avoir une certaine confusion quant à leur rôle, voici donc une brève comparaison :

"utf8" contrôle si le texte JSON créé par "encode" (et attendu par "decode") est encodé en UTF-8 ou non, tandis que "latin1" et "ascii" contrôlent uniquement si "encode" échappe les valeurs de caractères en dehors de leur plage de jeu de caractères respective. Aucun de ces indicateurs ne se contredit, bien que certaines combinaisons aient moins de sens que d'autres.

Des précautions ont été prises pour rendre tous les indicateurs symétriques par rapport à "encode" et "decode", c'est-à-dire que les textes encodés avec n'importe quelle combinaison de ces valeurs d'indicateur seront correctement décodés lorsque les mêmes indicateurs sont utilisés - en général, si vous utilisez des paramètres d'indicateurs différents lors de l'encodage par rapport au décodage, vous avez probablement un bug quelque part.

Vous trouverez ci-dessous une discussion détaillée de ces indicateurs. Notez qu'un "jeu de caractères" est simplement un ensemble abstrait de paires caractère-point de code, tandis qu'un encodage prend ces numéros de point de code et les *encode*, dans notre cas en octets. Unicode est (entre autres choses) un jeu de caractères, UTF-8 est un encodage, et ISO-8859-1 (= latin 1) et ASCII sont à la fois des jeux de caractères *et* des encodages en même temps, ce qui peut être déroutant.

Indicateur "utf8" désactivé
Lorsque "utf8" est désactivé (par défaut), "encode"/"decode" génèrent et attendent des chaînes Unicode, c'est-à-dire que les caractères avec des valeurs Unicode élevées ( > 255) seront encodés comme tels, et de même ces caractères seront décodés tels quels, aucun changement ne leur sera apporté, sauf en les "(ré-)interprétant" comme des points de code Unicode ou des caractères Unicode, respectivement (pour Perl, ce sont les mêmes choses dans les chaînes, sauf si vous faites des choses bizarres/étranges/idiotes).

C'est utile lorsque vous souhaitez effectuer l'encodage vous-même (par exemple, lorsque vous souhaitez avoir des textes JSON encodés en UTF-16) ou lorsque une autre couche effectue l'encodage pour vous (par exemple, lors de l'impression sur un terminal à l'aide d'un gestionnaire de fichier qui encode transparentement en UTF-8, vous ne voulez certainement pas encoder vos données en UTF-8 d'abord et avoir Perl qui les encode une autre fois).

Indicateur "utf8" activé
Si l'indicateur "utf8" est activé, "encode"/"decode" encoderont tous les caractères en utilisant la séquence multi-octets UTF-8 correspondante, et s'attendront à ce que vos chaînes d'entrée soient encodées en UTF-8, c'est-à-dire qu'aucun "caractère" de la chaîne d'entrée ne doit avoir une valeur > 255, car UTF-8 ne le permet pas.

L'indicateur "utf8" bascule donc entre deux modes : désactivé signifie que vous obtiendrez une chaîne Unicode dans Perl, activé signifie que vous obtiendrez une chaîne d'octets/binaire encodée en UTF-8 dans Perl.

Indicateurs "latin1" ou "ascii" activés
Avec "latin1" (ou "ascii") activé, "encode" échappera les caractères avec des valeurs ordinales > 255 (> 127 avec "ascii") et encodera les caractères restants conformément à l'indicateur "utf8".

Si "utf8" est désactivé, le résultat est également correctement encodé dans ces jeux de caractères (car tous deux sont des sous-ensembles propres d'Unicode, ce qui signifie qu'une chaîne Unicode avec toutes les valeurs de caractères < 256 est la même chose qu'une chaîne ISO-8859-1, et une chaîne Unicode avec toutes les valeurs de caractères < 128 est la même chose qu'une chaîne ASCII dans Perl).

Si "utf8" est activé, vous obtenez toujours une chaîne correctement encodée en UTF-8, indépendamment de ces indicateurs, seulement certains caractères seront échappés en utilisant "\uXXXX" plus souvent qu'auparavant.

Notez que les chaînes encodées en ISO-8859-1 ne sont *pas* compatibles avec l'encodage UTF-8, tandis que les chaînes encodées en ASCII le sont. C'est parce que l'encodage ISO-8859-1 n'est *pas* un sous-ensemble d'UTF-8 (bien que le *jeu de caractères* ISO-8859-1 soit un sous-ensemble d'Unicode), tandis qu'ASCII l'est.

Étonnamment, "decode" ignorera ces indicateurs et traitera donc toutes les valeurs d'entrée comme étant régies par l'indicateur "utf8". S'il est désactivé, cela vous permet de décoder des chaînes encodées en ISO-8859-1 et ASCII, car tous deux sont des sous-ensembles stricts d'Unicode. S'il est activé, vous pouvez décoder correctement des chaînes encodées en UTF-8.

Ainsi, ni "latin1" ni "ascii" ne sont incompatibles avec l'indicateur "utf8" - ils régissent seulement quand le moteur de sortie JSON échappe un caractère ou non.

L'utilisation principale de "latin1" est de stocker des données binaires sous forme de JSON de manière relativement efficace, au détriment de la compatibilité avec la plupart des décodeurs JSON.

L'utilisation principale de "ascii" est de forcer la sortie à ne pas contenir de caractères avec des valeurs > 127, ce qui signifie que vous pouvez interpréter la chaîne résultante comme UTF-8, ISO-8859-1, ASCII, KOI8-R ou à peu près n'importe quel jeu de caractères et encodage 8 bits, et obtenir toujours la même structure de données. Ceci est utile lorsque votre canal de transfert JSON n'est pas propre en 8 bits ou que l'encodage peut être corrompu entre les deux (par exemple, dans les e-mails), et fonctionne car ASCII est un sous-ensemble propre de la plupart des encodages 8 bits et multi-octets utilisés dans le monde.

JSON et ECMAscript

La syntaxe JSON est basée sur la manière dont les littéraux sont représentés en javascript (le prédécesseur non standardisé d'ECMAscript), ce qui explique probablement pourquoi il est appelé "JavaScript Object Notation".

Cependant, JSON n'est ni un sous-ensemble (ni un sur-ensemble, bien sûr) d'ECMAscript (la norme) ou de javascript (quel que soit ce que les navigateurs implémentent réellement).

Si vous souhaitez utiliser la fonction "eval" de javascript pour "analyser" du JSON, vous pourriez rencontrer des erreurs d'analyse pour des textes JSON valides, ou la structure de données résultante pourrait ne pas être interrogeable :

L'un des problèmes est que U+2028 et U+2029 sont des caractères valides dans les chaînes JSON, mais ne sont pas autorisés dans les littéraux de chaîne ECMAscript, de sorte que le fragment Perl suivant ne produira pas une sortie qui soit garantie d'être analysable par la fonction "eval" de javascript :

CONSIDÉRATIONS DE

SÉCURITÉ

Lorsque vous utilisez JSON dans un protocole, communiquer avec des créatures potentiellement hostiles et non dignes de confiance nécessite relativement peu de

mesures.

Tout d'abord, votre décodeur JSON devrait être sûr, c'est-à-dire qu'il ne devrait pas avoir de débordements de tampon. Évidemment, ce module devrait garantir cela et j'essaie dur de faire en sorte que ce soit le cas, mais on ne sait

jamais.

Deuxièmement, vous devez éviter les attaques par épuisement de ressources. Cela signifie que vous devriez limiter la taille des textes JSON que vous acceptez, ou vous assurer que lorsque vos ressources sont épuisées, c'est tout à fait acceptable (par exemple en utilisant un processus séparé qui peut planter en toute sécurité). La taille d'un texte JSON en octets ou en caractères est généralement une bonne indication de la taille des ressources nécessaires pour le décoder en une structure Perl. Bien que JSON::XS puisse vérifier la taille du texte JSON, il pourrait être trop tard lorsque vous l'avez déjà en mémoire, vous pourriez donc vouloir vérifier la taille avant d'accepter la

chaîne.

Troisièmement, JSON::XS utilise la pile C de manière récursive lors du décodage des objets et des tableaux. La pile C est une ressource limitée : par exemple, sur ma machine amd64 avec une taille de pile de 8 Mo, je peux décoder environ 180k tableaux imbriqués mais seulement 14k objets JSON imbriqués (en raison de la récursion profonde de perl lui-même lors de croak pour libérer la temporaires). Si cela est dépassé, le programme plante. Pour être prudent, la limite d'imbrication par défaut est fixée à 512. Si votre processus a une pile plus petite, vous devriez ajuster ce paramètre en conséquence avec la méthode "max_

depth".

Quelque chose d'autre pourrait aussi vous faire exploser, que j'ai oublié de prendre en compte. Dans ce cas, vous gardez les morceaux. Je suis toujours ouvert aux indices, cependant..

.

Gardez également à l'esprit que JSON::XS pourrait fuiter le contenu de vos structures de données Perl dans ses messages d'erreur, lorsque vous sérialisez donc des informations sensibles, vous pourriez vouloir vous assurer que les exceptions levées par JSON::XS ne finiront pas devant des yeux non dignes de

confiance.
