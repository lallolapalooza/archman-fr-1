DESCRIPTIO

N

Ce module est un emballage léger pour les modules compatibles JSON::XS avec quelques fonctionnalités supplémentaires. Tous les modules de backend convertissent une structure de données Perl en texte JSON et inversement. Ce module utilise JSON::XS par défaut, et lorsque JSON::XS n'est pas disponible, il utilise JSON::PP, qui fait partie du cœur Perl depuis la version 5.14. Si JSON::PP n'est pas non plus disponible, ce module utilise alors JSON::backportPP (qui est en fait JSON::PP dans un fichier .pm différent) inclus dans la même distribution que ce module. Vous pouvez également spécifier explicitement d'utiliser Cpanel::JSON::XS, un fork de JSON::XS par Reini

Urban.

Tous ces modules de backend ont de légères incompatibilités entre eux, y compris des fonctionnalités supplémentaires que les autres modules ne p

rennent pas en charge, mais tant que vous n'utilisez que des fonctionnalités communes (les plus importantes sont décrites ci-dessous), la m
igration d'un backend à l'autre devrait être raisonnablement facile. Pour plus de détails, consultez chaque module de backend que vous utilisez.

CHOIX DU

BACKEND

Ce module respecte une variable d'environnement appelée "PERL_JSON_BACKEND" lorsqu'il décide quel module backend utiliser. Si cette variable d'environnement n'est pas définie, il essaie de charger JSON::XS, et si JSON::XS n'est pas disponible, il utilise JSON::PP, puis JSON::backportPP si JSON::PP n'est pas non plus

disponible.

Si vous ne voulez jamais qu'il utilise des modules pure perl, définissez la variable comme ceci ("export" peut être "setenv", "set" et le reste, selon votre environnement)

:

XS

Si vous préférez Cpanel::JSON::XS à JSON::XS, alors

Vous voudrez peut-être aussi définir cette variable en haut de vos fichiers de test, afin de ne pas être dérangé par les incompatibilités entre backends (vous devez envelopper cela dans "BEGIN", et définir avant d'utiliser "use" le module JSON, car il décide de son backend dès qu'il est chargé)

Si $activer est vrai (ou manquant), alors "decode" acceptera certaines extensions à la syntaxe JSON normale (voir ci-dessous). "encode" ne sera en aucun cas affecté. Sachez que cette option vous fait accepter des textes JSON non valides comme s'ils étaient valides !. Je suggère de n'utiliser cette option que pour analyser des fichiers spécifiques à une application écrits par des humains (fichiers de configuration, fichiers de ressources, etc.)

Si $activer est faux (par défaut), alors "decode" n'acceptera que des textes JSON valides.

Les extensions actuellement acceptées sont :

  • les éléments de liste peuvent avoir une virgule finale

    JSON sépare les éléments du tableau et les paires clé-valeur par des virgules. Cela peut être gênant si vous écrivez des textes JSON manuellement et souhaitez pouvoir ajouter rapidement des éléments. Cette extension accepte donc une virgule à la fin de tels éléments, pas seulement entre eux :

    [
   1,
   2, <- cette virgule n'est normalement pas autorisée
]
{
   "k1": "v1",
   "k2": "v2", <- cette virgule n'est normalement pas autorisée
}
  • commentaires de style shell '#'

    Chaque fois que JSON autorise les espaces blancs, les commentaires de style shell sont en plus autorisés. Ils sont terminés par le premier caractère de retour chariot ou de saut de ligne, après quoi plus d'espaces blancs et de commentaires sont autorisés.

    [
   1, # ce commentaire n'est pas autorisé en JSON
      # pas plus que celui-ci...
]

canonique

$json = $json->canonique([$activer])

$activé = $json->get_canonique

Si $activer est vrai (ou manquant), alors la méthode "encode" produira des objets JSON en triant leurs clés. Cela entraîne une surcharge relativement élevée.

Si $activer est faux, alors la méthode "encode" produira les paires clé-valeur dans l'ordre où Perl les stocke (ce qui changera probablement entre les exécutions du même script, et peut changer même au sein de la même exécution à partir de 5.18).

Cette option est utile si vous voulez que la même structure de données soit encodée en un texte JSON identique (compte tenu des mêmes paramètres globaux). Si elle est désactivée, le même hachage pourrait être encodé différemment même s'il contient les mêmes données, car les paires clé-valeur n'ont pas d'ordre inhérent en Perl.

Ce paramètre n'a aucun effet lors du décodage de textes JSON.

Ce paramètre n'a actuellement aucun effet sur les hachages liés.

autoriser_nonref

$json = $json->autoriser_nonref([$activer])

$activé = $json->get_autoriser_nonref

Contrairement aux autres options booléennes, cette option est activée par défaut à partir de la version 4.0.

Si $activer est vrai (ou manquant), alors la méthode "encode" peut convertir une non-référence en sa chaîne, nombre ou valeur JSON null correspondante, ce qui est une extension à la RFC4627. De même, "decode" acceptera ces valeurs JSON au lieu de planter.

Si $activer est faux, alors la méthode "encode" plantera si elle ne reçoit pas de référence de tableau ou de hachage, car les textes JSON doivent être un objet ou un tableau. De même, "decode" plantera si elle reçoit quelque chose qui n'est pas un objet ou un tableau JSON.

Exemple, encoder un scalaire Perl comme valeur JSON avec "autoriser_nonref" activé, résultant en un texte JSON invalide :

JSON->new->autoriser_nonref->encode ("Bonjour, le monde !")
=> "Bonjour, le monde !"

autoriser_inconnu

$json = $json->autoriser_inconnu ([$activer])

$activé = $json->get_autoriser_inconnu

Si $activer est vrai (ou manquant), alors "encode" ne lèvera pas d'exception lorsqu'il rencontrera des valeurs qu'il ne peut pas représenter en JSON (par exemple, des descripteurs de fichiers), mais encodera à la place une valeur JSON "null". Notez que les objets bénis ne sont pas inclus ici et sont gérés séparément par c<autoriser_bénis>.

Si $activer est faux (par défaut), alors "encode" lèvera une exception lorsqu'il rencontrera quelque chose qu'il ne peut pas encoder en JSON.

Cette option n'affecte en rien "decode", et il est recommandé de la laisser désactivée, sauf si vous connaissez votre partenaire de communication.

autoriser_bénis

$json = $json->autoriser_bénis([$activer])

$activé = $json->get_autoriser_bénis

Voir "SÉRIALISATION D'OBJETS" pour les détails.

Si $activer est vrai (ou manquant), alors la méthode "encode" ne plantera pas lorsqu'elle rencontrera une référence bénie qu'elle ne peut pas convertir autrement. Au lieu de cela, une valeur JSON "null" sera encodée au lieu de l'objet.

Si $activer est faux (par défaut), alors "encode" lèvera une exception lorsqu'elle rencontrera un objet béni qu'elle ne peut pas convertir autrement.

Ce paramètre n'a aucun effet sur "decode".

convertir_bénis

$json = $json->convertir_bénis([$activer])

$activé = $json->get_convertir_bénis

Voir "SÉRIALISATION D'OBJETS" pour les détails.

Si $activer est vrai (ou manquant), alors "encode", lorsqu'il rencontre un objet béni, vérifiera la disponibilité de la méthode "TO_JSON" sur la classe de l'objet. Si elle est trouvée, elle sera appelée en contexte scalaire et le scalaire résultant sera encodé au lieu de l'objet.

La méthode "TO_JSON" peut appeler `die` en toute sécurité si elle le souhaite. Si "TO_JSON" renvoie d'autres objets bénis, ceux-ci seront traités de la même manière. "TO_JSON" doit veiller à ne pas provoquer un cycle de récursion infini (== crash) dans ce cas. Le nom de "TO_JSON" a été choisi car d'autres méthodes appelées par le noyau Perl (== pas par l'utilisateur de l'objet) sont généralement en majuscules et pour éviter les collisions avec toute fonction ou méthode "to_json".

Si $activer est faux (par défaut), alors "encode" ne considérera pas ce type de conversion.

Ce paramètre n'a aucun effet sur "decode".

autoriser_tags (depuis la version 3.0)

$json = $json->autoriser_tags([$activer])
$activé = $json->get_autoriser_tags

Voir "SÉRIALISATION D'OBJETS" pour les détails.

Si $activer est vrai (ou manquant), alors "encode", lorsqu'il rencontre un objet béni, vérifiera la disponibilité de la méthode "FREEZE" sur la classe de l'objet. Si elle est trouvée, elle sera utilisée pour sérialiser l'objet en une valeur JSON balisée non standard (que les décodeurs JSON ne peuvent pas décoder).

Cela amène également "decode" à analyser ces valeurs JSON balisées et à les désérialiser via un appel à la méthode "THAW".

Si $activer est faux (par défaut), alors "encode" ne considérera pas ce type de conversion, et les valeurs JSON balisées provoqueront une erreur d'analyse dans "decode", comme si les balises ne faisaient pas partie de la grammaire.

valeurs_booléennes (depuis la version 4.0)

$json->valeurs_booléennes([$faux, $vrai])
($faux,  $vrai) = $json->get_valeurs_booléennes

Par défaut, les booléens JSON seront décodés comme des objets surchargés $JSON::faux et $JSON::vrai.

Avec cette méthode, vous pouvez spécifier vos propres valeurs booléennes pour le décodage - lors du décodage, le "faux" JSON sera décodé comme une copie de $faux, et le "vrai" JSON sera décodé comme $vrai ("copie" ici signifie la même chose qu'attribuer une valeur à une autre variable, c'est-à-dire "$copie = $faux").

C'est utile lorsque vous souhaitez passer une structure de données décodée directement à d'autres sérialiseurs comme YAML, Data::MessagePack, etc.

Notez que cela ne fonctionne que lorsque vous "décodez". Vous pouvez définir des objets booléens incompatibles (comme booléens), mais lorsque vous "encodez" une structure de données avec de tels objets booléens, vous devez toujours activer "convertir_bénis" (et ajouter une méthode "TO_JSON" si nécessaire).

Appeler cette méthode sans arguments réinitialisera les booléens à leurs valeurs par défaut.

"get_valeurs_booléennes" renverra les valeurs $faux et $vrai, ou la liste vide lorsqu'elles sont définies par défaut.

filtrer_objet_json

$json = $json->filtrer_objet_json([$coderef])

Lorsque $coderef est spécifié, il sera appelé depuis "decode" chaque fois qu'il décodera un objet JSON. Le seul argument est une référence au hachage nouvellement créé. Si le code référencé renvoie un scalaire unique (qui n'a pas besoin d'être une référence), cette valeur (ou plutôt une copie) sera insérée dans la structure de données désérialisée. S'il renvoie une liste vide (NOTE : pas "undef", qui est un scalaire valide), le hachage original désérialisé sera inséré. Ce paramètre peut ralentir considérablement le décodage.

SERIALIZACIÓN DE OBJETOS

Dado que JSON no puede representar directamente objetos Perl, debes elegir entre una representación puramente JSON (sin capacidad de deserialización automática del objeto) o una extensión no estándar de la sintaxis JSON, los valores etiquetados.

SERIALIZACIÓN

Lo que ocurre cuando este módulo encuentra un objeto Perl depende de las configuraciones "allow_blessed", "convert_blessed" y "allow_tags", que se utilizan en este orden:

1. "allow_tags" está habilitado y el objeto tiene un método "FREEZE".
En este caso, "JSON" crea un valor etiquetado de JSON, utilizando una extensión no estándar de la sintaxis JSON. Esto se logra invocando el método "FREEZE" del objeto, con el primer argumento siendo el objeto a serializar y el segundo argumento siendo la cadena constante "JSON" para distinguirlo de otros serializadores.

El método "FREEZE" puede devolver cualquier número de valores (es decir, cero o más). Estos valores y el nombre de la clase/objeto del objeto se codificarán como un valor etiquetado de JSON en el siguiente formato:

("clase")[VALORES_DEVUELTOS...]

por ejemplo:

("URI")["http://www.google.com/"]
("MyDate")[2013,10,29]
("ImageData::JPEG")["Z3...VlCg=="]

Por ejemplo, el método hipotético "My::Object""FREEZE" podría usar los miembros "type" y "id" del objeto para codificar el objeto:

sub My::Object::FREEZE {
   my ($self, $serialiser) = @_;
   ($self->{type}, $self->{id})
}
2. "convert_blessed" está habilitado y el objeto tiene un método "TO_JSON".
En este caso, el método "TO_JSON" del objeto se invoca en contexto escalar. Debe devolver un único escalar que pueda ser codificado directamente en JSON. Este escalar reemplaza al objeto en el texto JSON.

Por ejemplo, el siguiente método "TO_JSON" convertirá todos los objetos URI en cadenas JSON cuando se serialicen. La pérdida de que estos valores fueran originalmente objetos URI es irrelevante.

sub URI::TO_JSON {
   my ($uri) = @_;
   $uri->as_string
}
3. "allow_blessed" está habilitado.
El objeto se serializa como un valor JSON nulo.
4. Ninguno de los anteriores.
Si ninguna de las configuraciones está habilitada o los métodos respectivos no existen, este módulo lanza una excepción.

DESERIALIZACIÓN

Para la deserialización hay dos casos a considerar: o se ha utilizado un etiquetado no estándar, en cuyo caso "allow_tags" decide, o el objeto no puede ser deserializado automáticamente, en cuyo caso se puede utilizar postprocesamiento o los callbacks "filter_json_object" o "filter_json_single_key_object" para obtener objetos reales a partir de tu JSON.

Esta sección solo considera el caso de valores etiquetados: se encuentra un objeto JSON etiquetado durante la deserialización y "allow_tags" está deshabilitado, lo que resulta en un error (como si los valores etiquetados no estuvieran en la gramática).

Si "allow_tags" está habilitado, este módulo buscará el método "THAW" de la clase/espacio de nombres utilizado durante la serialización (no intentará cargar el espacio de nombres como un módulo Perl). Si no existe tal método, la deserialización fallará con un error.

De lo contrario, se invoca el método "THAW" con el nombre de la clase como primer argumento, la cadena constante "JSON" como segundo argumento, y todos los valores de la lista JSON (los valores originales devueltos por el método "FREEZE") como argumentos restantes.

El método debe devolver el objeto. Aunque técnicamente puedes devolver cualquier escalar Perl, quizás tengas que habilitar la opción "allow_nonref" para que funcione en todos los casos, por lo que es mejor devolver una referencia bendecida real.

Como ejemplo, implementamos un método "THAW" que regenera el "My::Object" del ejemplo de "FREEZE":

sub My::Object::THAW {
   my ($class, $serialiser, $type, $id) = @_;
   $class->new (type => $type, id => $id)
}

NOTAS SOBRE LAS BANDERAS DE CODIFICACIÓN/JUEGO DE CARACTERES

Esta sección se tomó de JSON::XS.

El lector interesado podría haber visto varias banderas que indican las codificaciones o juegos de caracteres - "utf8", "latin1" y "ascii". Existe cierta confusión sobre lo que hacen estas, así que aquí hay una breve comparación:

"utf8" controla si el texto JSON generado por "encode" (y esperado por "decode") está codificado en UTF-8 o no, mientras que "latin1" y "ascii" solo controlan si "encode" escapa los valores de caracteres fuera del rango de su juego de caracteres. Ninguna de estas banderas se contradice entre sí, aunque algunas combinaciones son menos sensatas que otras.

Se ha tenido cuidado para que todas las banderas sean simétricas con respecto a "encode" y "decode", es decir, los textos codificados con cualquier combinación de estas banderas se decodificarán correctamente cuando se usen las mismas banderas; en general, si utilizas diferentes configuraciones de banderas durante la codificación frente a la decodificación, probablemente haya un error en alguna parte.

A continuación se presenta una discusión detallada de estas banderas. Tenga en cuenta que un juego de caracteres es simplemente un conjunto abstracto de pares de código de carácter, mientras que una codificación toma esos números de código y los *codifica*, en nuestro caso a octetos. Unicode es (entre otros) un juego de caracteres, UTF-8 es una codificación, y ISO-8859-1 (= latin 1) y ASCII son ambos juegos de caracteres y codificaciones simultáneamente, lo que puede ser confuso.

"utf8" flag disabled
Cuando "utf8" está deshabilitado (por defecto), "encode"/"decode" generan y esperan cadenas Unicode, es decir, los caracteres con valores ordinales altos (> 255) se codifican así, y también se decodifican como tales, sin cambios, excepto para "(re)interpretar" ellos como puntos de código Unicode o caracteres Unicode respectivamente (para Perl, estos son lo mismo, a menos que hagas algo peculiar/extraño/impresionante).

Esto es útil cuando quieres realizar la codificación tú mismo (por ejemplo, cuando quieres que el texto JSON esté codificado en UTF-16) o cuando otra capa realiza la codificación por ti (por ejemplo, al imprimir a una terminal usando un archivo que codifica transparentemente a UTF-8, no quieres codificar tus datos primero como UTF-8 y luego volver a codificarlos por Perl).

"utf8" flag enabled
Cuando "utf8" está habilitado, "encode"/"decode" codificarán todos los caracteres usando la secuencia de bytes UTF-8 correspondiente, y esperarán que tus cadenas de entrada estén codificadas como UTF-8, es decir, ningún carácter de la cadena de entrada debe tener un valor > 255, ya que UTF-8 no lo permite.

La bandera "utf8" se comporta así entre dos modos: deshabilitada significa que obtendrás una cadena Unicode en Perl, habilitada significa que obtendrás una cadena codificada en UTF-8/binaria en Perl.

"latin1" or "ascii" flags enabled
Cuando las banderas "latin1" o "ascii" están habilitadas, "encode" escapa los caracteres con valores ordinales > 255 (> 127 con "ascii") y codifica los caracteres restantes según la bandera "utf8".

Si "utf8" está deshabilitado, el resultado también se codificará correctamente en esos juegos de caracteres (ya que ambos son subconjuntos válidos de Unicode, por lo que una cadena Unicode con todos los valores de caracteres < 256 es lo mismo que una cadena ISO-8859-1, y una cadena Unicode con todos los valores de caracteres < 128 es lo mismo que una cadena ASCII en Perl).

Si "utf8" está habilitado, aún obtienes una cadena correctamente codificada como UTF-8, independientemente de estas banderas, solo que algunos caracteres se escaparán usando .
