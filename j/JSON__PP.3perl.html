JSON::PP(3perl) Guide de référence du programmeur Perl JSON::PP(3perl)

NOM

JSON::PP - Module pure-Perl compatible JSON::XS.

SYNTAXE

use JSON::PP;
# fonctions exportées, elles croakent en cas d'erreur
# et attendent/génèrent de l'UTF-8
$utf8_encoded_json_text = encode_json $perl_hash_or_arrayref;
$perl_hash_or_arrayref  = decode_json $utf8_encoded_json_text;
# Interface orientée objet
$json = JSON::PP->new->ascii->pretty->allow_nonref;

$pretty_printed_json_text = $json->encode( $perl_scalar );
$perl_scalar = $json->decode( $json_text );

# Notez que JSON version 2.0 et au-dessus utiliseront automatiquement
# JSON::XS ou JSON::PP, donc vous devriez juste pouvoir faire :

use JSON;

DESCRIPTION

JSON::PP est un décodeur/encodeur JSON pur perl, et (presque) compatible avec JSON::XS, beaucoup plus rapide, écrit en C par Marc Lehmann. JSON::PP fonctionne comme un module de secours lorsque vous utilisez le module JSON sans avoir installé JSON::XS.

En raison de cette fonctionnalité de secours de JSON.pm, JSON::PP essaie de ne pas être plus compatible avec JavaScript que JSON::XS (c'est-à-dire de ne pas échapper de caractères supplémentaires tels que U+2028 et U+2029, etc.), afin que vous ne perdiez pas silencieusement cette compatibilité JavaScript lorsque vous utilisez JSON.pm et installez JSON::XS pour la vitesse ou par accident. Si vous avez besoin d'un module pur perl compatible RFC7159 et compatible JavaScript, essayez JSON::Tiny, qui est dérivé du framework web Mojolicious et qui est également plus petit et plus rapide que JSON::PP.

JSON::PP fait partie du cœur de Perl depuis Perl 5.14, principalement pour les modules de la chaîne d'outils CPAN afin d'analyser META.json.

INTERFACE FONCTIONNELLE

Cette section est tirée de JSON::XS presque mot pour mot. "encode_json" et "decode_json" sont exportés par défaut.

encode_json

$json_text = encode_json $perl_scalar

Convertit la structure de données Perl donnée en une chaîne binaire encodée en UTF-8 (c'est-à-dire que la chaîne ne contient que des octets). Croake en cas d'erreur.

Cet appel de fonction est fonctionnellement identique à :

$json_text = JSON::PP->new->utf8->encode($perl_scalar)

Sauf qu'il est plus rapide.

decode_json

$perl_scalar = decode_json $json_text

L'inverse de "encode_json" : attend une chaîne UTF-8 (binaire) et essaie de l'analyser comme un texte JSON encodé en UTF-8, renvoyant la référence résultante. Croake en cas d'erreur.

Cet appel de fonction est fonctionnellement identique à :

$perl_scalar = JSON::PP->new->utf8->decode($json_text)

Sauf qu'il est plus rapide.

JSON::PP::is_bool

$is_boolean = JSON::PP::is_bool($scalar)

Retourne vrai si le scalaire passé représente soit JSON::PP::true soit JSON::PP::false, deux constantes qui agissent comme 1 et 0 respectivement et qui sont également utilisées pour représenter les "vrai" et "faux" JSON dans les chaînes Perl.

Sur perl 5.36 et supérieur, retournera également vrai lorsqu'on lui donnera l'une des valeurs booléennes standard de perl, comme le résultat d'une comparaison.

Voir MAPPING, ci-dessous, pour plus d'informations sur la manière dont les valeurs JSON sont mappées à Perl.

INTERFACE ORIENTÉE OBJET

Cette section est également tirée de JSON::XS.

L'interface orientée objet vous permet de configurer votre propre style d'encodage ou de décodage, dans les limites des formats supportés.

new

$json = JSON::PP->new

Crée un nouvel objet JSON::PP qui peut être utilisé pour décoder/encoder des chaînes JSON. Tous les indicateurs booléens décrits ci-dessous sont par défaut *désactivés* (à l'exception de "allow_nonref", qui est activé par défaut depuis la version 4.0).

Les mutateurs pour les indicateurs renvoient tous l'objet JSON::PP à nouveau et donc les appels peuvent être chaînés :

my $json = JSON::PP->new->utf8->space_after->encode({a => [1,2]})
=> {"a": [1, 2]}

ascii

$json = $json->ascii([$enable])

$enabled = $json->get_ascii

Si $enable est vrai (ou manquant), alors la méthode "encode" ne générera pas de caractères en dehors de la plage de codes 0..127 (qui est l'ASCII). Tous les caractères Unicode en dehors de cette plage seront échappés en utilisant soit un seul \uXXXX (caractères BMP) soit une séquence d'échappement double \uHHHH\uLLLLL, conformément à la RFC4627. Le texte JSON encodé résultant peut être traité comme une chaîne Unicode native, une chaîne encodée en ASCII, en latin1 ou en UTF-8, ou tout autre sur-ensemble de l'ASCII.

Si $enable est faux, alors la méthode "encode" n'échappera pas les caractères Unicode sauf si requis par la syntaxe JSON ou d'autres indicateurs. Ceci résulte en un format plus rapide et plus compact.

Voir aussi la section NOTES SUR LES INDICATEURS D'ENCODAGE/CODESET plus loin dans ce document.

L'utilisation principale de cet indicateur est de produire des textes JSON qui peuvent être transmis sur un canal 7 bits, car les textes JSON encodés ne contiendront aucun caractère 8 bits.

JSON::PP->new->ascii(1)->encode([chr 0x10401])
=> ["\ud801\udc01"]

latin1

$json = $json->latin1([$enable])

$enabled = $json->get_latin1

Si $enable est vrai (ou manquant), alors la méthode "encode" encodera le texte JSON résultant en latin1 (ou iso-8859-1), en échappant tous les caractères en dehors de la plage de codes 0..255. La chaîne résultante peut être traitée comme un texte JSON encodé en latin1 ou une chaîne Unicode native. La méthode "decode" ne sera affectée en aucune façon par cet indicateur, car "decode" attend par défaut de l'Unicode, qui est un sur-ensemble strict du latin1.

Si $enable est faux, alors la méthode "encode" n'échappera pas les caractères Unicode sauf si requis par la syntaxe JSON ou d'autres indicateurs.

Voir aussi la section NOTES SUR LES INDICATEURS D'ENCODAGE/CODESET plus loin dans ce document.

L'utilisation principale de cet indicateur est l'encodage efficace de données binaires en texte JSON, car la plupart des octets ne seront pas échappés, résultant en une taille encodée plus petite. Le désavantage est que le texte JSON résultant est encodé en latin1 (et doit être correctement traité comme tel lors du stockage et du transfert), un encodage rare pour le JSON. Il est donc plus utile lorsque vous souhaitez stocker efficacement des structures de données connues pour contenir des données binaires dans des fichiers ou des bases de données, et non lorsque vous communiquez avec d'autres encodeurs/décodeurs JSON.

JSON::PP->new->latin1->encode (["\x{89}\x{abc}"]
=> ["\x{89}\\u0abc"]    # (syntaxe perl, U+abc échappé, U+89 non)

utf8

$json = $json->utf8([$enable])

$enabled = $json->get_utf8

Si $enable est vrai (ou manquant), alors la méthode "encode" encodera le résultat JSON en UTF-8, comme requis par de nombreux protocoles, tandis que la méthode "decode" s'attend à recevoir une chaîne encodée en UTF-8. Veuillez noter que les chaînes encodées en UTF-8 ne contiennent aucun caractère en dehors de la plage 0..255, elles sont donc utiles pour les E/S octets/binaires. Dans les versions futures, l'activation de cette option pourrait activer la détection automatique des familles d'encodage UTF-16 et UTF-32, comme décrit dans la RFC4627.

Si $enable est faux, alors la méthode "encode" renverra la chaîne JSON sous forme de chaîne Unicode (non encodée), tandis que "decode" s'attend donc à une chaîne Unicode. Tout décodage ou encodage (par exemple, vers UTF-8 ou UTF-16) doit être effectué par vous-même, par exemple en utilisant le module Encode.

Voir aussi la section NOTES SUR LES INDICATEURS D'ENCODAGE/CODESET plus loin dans ce document.

Exemple, sortie JSON encodée en UTF-16BE :

use Encode;
$jsontext = encode "UTF-16BE"

Le

allow_nonref

$json = $json->allow_nonref([$enable])
$enabled = $json->get_allow_nonref

If $enable is true (or missing), then "encode" will happily encode non-reference values (like numbers, strings, etc.) directly. The default is false, which means that only references (hashes, arrays, etc.) will be encoded, and anything else will be croaked upon.

This setting has no effect on "decode".

allow_unicode

$json = $json->allow_unicode([$enable])
$enabled = $json->get_allow_unicode

If $enable is true (or missing), then "encode" will output Unicode characters directly, without escaping them. It will also cause Perl's wide character functions to be used in "decode".

If $enable is false (the default), then "encode" will escape all non-ASCII characters using "\//uNNNN" sequences, and "decode" will produce only ASCII strings. This is the most compatible mode.

canonical

$json = $json->canonical([$enable])
$enabled = $json->get_canonical

If $enable is true (or missing), then "encode" will sort the keys of JSON objects (Perl hashes) alphabetically. This is useful for comparing JSON outputs.

If $enable is false (the default), then the order of keys is preserved as much as possible.

convert_blessed

$json = $json->convert_blessed([$enable])
$enabled = $json->get_convert_blessed

If $enable is true (or missing), then "encode" will serialise blessed objects. It does this by checking for the availability of a "TO_JSON" method on the object's class. If found, it will be called, and the return value will be used as the JSON representation of the object.

The "TO_JSON" method may safely call die if it wants. If "TO_JSON" returns other blessed objects, those will be handled in the same way. "TO_JSON" must take care of not causing an endless recursion cycle (== crash) in this case. The name of "TO_JSON" was chosen because other methods called by the Perl core (== not by the user of the object) are usually in upper case letters and to avoid collisions with any "to_json" function or method.

If $enable is false (the default), then "encode" will not consider this type of conversion.

This setting has no effect on "decode".

allow_tags

$json = $json->allow_tags([$enable])
$enabled = $json->get_allow_tags

See "OBJECT SERIALISATION" for details.

If $enable is true (or missing), then "encode", upon encountering a blessed object, will check for the availability of the "FREEZE" method on the object's class. If found, it will be used to serialise the object into a nonstandard tagged JSON value (that JSON decoders cannot decode).

It also causes "decode" to parse such tagged JSON values and deserialise them via a call to the "THAW" method.

If $enable is false (the default), then "encode" will not consider this type of conversion, and tagged JSON values will cause a parse error in "decode", as if tags were not part of the grammar.

boolean_values

$json->boolean_values([$false, $true])
($false,  $true) = $json->get_boolean_values

By default, JSON booleans will be decoded as overloaded $JSON::PP::false and $JSON::PP::true objects.

With this method you can specify your own boolean values for decoding - on decode, JSON "false" will be decoded as a copy of $false, and JSON "true" will be decoded as $true ("copy" here is the same thing as assigning a value to another variable, i.e. "$copy = $false").

This is useful when you want to pass a decoded data structure directly to other serialisers like YAML, Data::MessagePack and so on.

Note that this works only when you "decode". You can set incompatible boolean objects (like boolean), but when you "encode" a data structure with such boolean objects, you still need to enable "convert_blessed" (and add a "TO_JSON" method if necessary).

Calling this method without any arguments will reset the booleans to their default values.

"get_boolean_values" will return both $false and $true values, or the empty list when they are set to the default.

core_bools

$json->core_bools([$enable]);

If $enable is true (or missing), then "decode", will produce standard perl boolean values. Equivalent to calling:

$json->boolean_values(!!1, !!0)

"get_core_bools" will return true if this has been set. On perl 5.36, it will also return true if the boolean values have been set to perl's core booleans using the "boolean_values" method.

The methods "unblessed_bool" and "get_unblessed_bool" are provided as aliases for compatibility with Cpanel::JSON::XS.

filter_json_object

$json = $json->filter_json_object([$coderef])

When $coderef is specified, it will be called from "decode" each time it decodes a JSON object. The only argument is a reference to the newly-created hash. If the code references returns a single scalar (which need not be a reference), this value (or rather a copy of it) is inserted into the deserialised data structure. If it returns an empty list (NOTE: not "undef", which is a valid scalar), the original deserialised hash will be inserted. This setting can slow down decoding considerably.

When $coderef is omitted or undefined, any existing callback will be removed and "decode" will not change the deserialised hash in any way.

Example, convert all JSON objects into the integer 5:

my $js = JSON::PP->new->filter_json_object(sub { 5 });
# returns [5]
$js->decode('[{}]');
# returns 5
$js->decode('{"a":1, "b":2}');

filter_json_single_key_object

$json = $json->filter_json_single_key_object($key [=> $coderef])

Works remotely similar to "filter_json_object", but is only called for JSON objects having a single key named $key.

This $coderef is called before the one specified via "filter_json_object", if any. It gets passed the single value in the JSON object. If it returns a single value, it will be inserted into the data structure. If it returns nothing (not even "undef" but the empty list), the callback from "filter_json_object" will be called next, as if no single-key callback were specified.

If $coderef is omitted or undefined, the corresponding callback will be disabled. There can only ever be one callback for a given key.

As this callback gets called less often then the "filter_json_object" one, decoding speed will not usually suffer as much. Therefore, single-key objects make excellent targets to serialise Perl objects into, especially as single-key JSON objects are as close to the type-tagged value concept as JSON gets (it's basically an ID/VALUE tuple). Of course, JSON does not support this in any way, so you need to make sure your data never looks like a serialised Perl hash.

Typical names for the single object key are "__class_whatever__", or "$__dollars_are_rarely_used__$" or "}ugly_brace_placement", or even things like "__class_md5sum(classname)__", to reduce the risk of clashing with real hashes.

Example, decode JSON objects of the form "{ "__widget__" => <id> }" into the corresponding $WIDGET{<id>} object:

# return whatever is in $WIDGET{5}:
JSON::PP
   ->new
   ->filter_json_single_key_object (__widget__ => sub {
         $WIDGET{ $_[0] }
      })
   ->decode ('{"__widget__": 5')
# this can be used with a TO_JSON method in some "widget" class
# for serialisation to json:
sub WidgetBase::TO_JSON {
   my ($self) = @_;
   unless ($self->{id}) {
      $self->{id} = ..get..some..id..;
      $WIDGET{$self->{id}} = $self;
   }
   { __widget__ => $self->{id} }
}

shrink

$json = $json->shrink([$enable])

$enabled = $json->get_shrink

If $enable is true (or missing), the string returned by "encode" will be shrunk (i.e. downgraded if possible).

The actual definition of what shrink does might change in future versions, but it will always try to save space at the expense of time.

If $enable is false, then JSON::PP does nothing.

max_depth

$json = $json->max_depth([$maximum_nesting_depth])

$max_depth = $json->get_max_depth

Sets the maximum nesting level (default 512) accepted while encoding or decoding. If a higher nesting level is detected in JSON text or a Perl data structure, then the encoder and decoder will stop and croak at that point.

Nesting level is defined by number of hash- or arrayrefs that the encoder needs to traverse to reach a given point or the number of "{" or "[" characters without their matching closing parenthesis crossed to reach a given character in a string.

Setting the maximum depth to one disallows any nesting, so that ensures that the object is only a single hash/object or array.

If no argument is given, the highest possible setting will be used, which is rarely useful.

See "SECURITY CONSIDERATIONS" in JSON::XS for more info on why this is useful.

max_size

$json = $json->max_size([$maximum_string_size])

Set the maximum length a JSON text may have (in bytes) where decoding is being attempted. The default is 0, meaning no limit. ANALYSE

INCRÉMENTALE

Cette section est également tirée de JSON::

XS.

Dans certains cas, il est nécessaire d'analyser les textes JSON de manière incrémentale. Bien que ce module doive toujours garder à la fois le texte JSON et la structure de données Perl résultante en mémoire en même temps, il vous permet d'analyser un flux JSON de manière incrémentale. Il le fait en accumulant du texte jusqu'à ce qu'il ait un objet JSON complet, qu'il peut alors décoder. Ce processus est similaire à l'utilisation de "decode_prefix" pour voir si un objet JSON complet est disponible, mais est beaucoup plus efficace (et peut être implémenté avec un minimum d'appels de méthode)

.

JSON::PP n'essaiera d'analyser le texte JSON qu'une fois qu'il est sûr d'avoir suffisamment de texte pour obtenir un résultat décisif, en utilisant un analyseur très simple mais véritablement incrémental. Cela signifie qu'il ne s'arrêtera pas toujours aussi tôt que l'analyseur complet, par exemple, il ne détecte pas les parenthèses non appariées. La seule chose qu'il garantit est qu'il commence à décoder dès qu'un texte JSON syntaxiquement valide a été vu. Cela signifie que vous devez définir des limites de ressources (par exemple "max_size") pour vous assurer que l'analyseur s'arrêtera d'analyser en présence d'erreurs de

syntaxe.

Les méthodes suivantes implémentent cet analyseur

incrémental.

ENCODING/CODESET FLAG NOTES


When you are encoding to a terminal using a filehandle that
    transparently encodes to UTF-8 you certainly do NOT want to UTF-8 encode
    your data first and have Perl encode it another time).



  
"utf8" flag enabled

  
If the "utf8"-flag is enabled, "encode"/"decode" will encode all
      characters using the corresponding UTF-8 multi-byte sequence, and will
      expect your input strings to be encoded as UTF-8, that is, no
      "character" of the input string must have any value > 255, as UTF-8
      does not allow that.
    
The "utf8" flag therefore switches between two modes: disabled
        means you will get a Unicode string in Perl, enabled means you get an
        UTF-8 encoded octet/binary string in Perl.

  

  
"latin1" or "ascii" flags enabled

  
With "latin1" (or "ascii") enabled, "encode" will escape characters
      with ordinal values > 255 (> 127 with "ascii") and encode the
      remaining characters as specified by the "utf8" flag.
    
If "utf8" is disabled, then the result is also correctly
        encoded in those character sets (as both are proper subsets of Unicode,
        meaning that a Unicode string with all character values < 256 is the
        same thing as a ISO-8859-1 string, and a Unicode string with all
        character values < 128 is the same thing as an ASCII string in
        Perl).

    
If "utf8" is enabled, you still get a correct UTF-8-encoded
        string, regardless of these flags, just some more characters will be
        escaped using "\uXXXX" then before.

    
Note that ISO-8859-1-encoded strings are not compatible
        with UTF-8 encoding, while ASCII-encoded strings are. That is because
        the ISO-8859-1 encoding is NOT a subset of UTF-8 (despite the
        ISO-8859-1 codeset being a subset of Unicode), while ASCII is.

    
Surprisingly, "decode" will ignore these flags and so treat
        all input values as governed by the "utf8" flag. If it is disabled, this
        allows you to decode ISO-8859-1- and ASCII-encoded strings, as both
        strict subsets of Unicode. If it is enabled, you can correctly decode
        UTF-8 encoded strings.

    
So neither "latin1" nor "ascii" are incompatible with the
        "utf8" flag - they only govern when the JSON output engine escapes a
        character or not.

    
The main use for "latin1" is to relatively efficiently store
        binary data as JSON, at the expense of breaking compatibility with most
        JSON decoders.

    
The main use for "ascii" is to force the output to not
        contain characters with values > 127, which means you can interpret
        the resulting string as UTF-8, ISO-8859-1, ASCII, KOI8-R or most about
        any character set and 8-bit-encoding, and still get the same data
        structure back. This is useful when your channel for JSON transfer is
        not 8-bit clean or the encoding might be mangled in between (e.g. in
        mail), and works because ASCII is a proper subset of most 8-bit and
        multibyte encodings in use in the world.
