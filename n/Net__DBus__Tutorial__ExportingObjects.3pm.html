NOM

Net::DBus::Tutorial::ExportingObjects - tutoriels sur la fourniture d'un service DBus

DESCRIPTION

Ce document fournit un tutoriel sur la fourniture d'un service DBus en utilisant les liaisons d'application Perl Net::DBus. Les exemples de ce document seront basés sur le code de la distribution Music::Player, qui est un simple service DBus fournissant un lecteur de pistes musicales.

CRÉATION D'UN OBJET

La première étape dans la création d'un objet consiste à créer un nouveau package qui hérite de Net::DBus::Object. L'objet Music::Player::Manager fournit une API pour gérer la collection de backends de lecteurs musicaux pour différents types de pistes. Pour commencer, créons le squelette du package et son constructeur. Le constructeur du super type, Net::DBus::Object, attend deux paramètres : une poignée vers le service Net::DBus possédant l'objet, et un chemin sous lequel l'objet sera exporté. Étant donné que la classe manager est destinée à être un objet singleton, nous pouvons coder en dur son chemin dans le constructeur :

package Music::Player::Manager;
use base qw(Net::DBus::Object);
sub new {
    my $class = shift;
    my $service = shift;
    my $self = $class->SUPER::new($service, "/music/player/manager");
    bless $self, $class;
    return $self;
}
1;

Maintenant, comme mentionné, le gestionnaire gérera un certain nombre de backends de lecteurs différents. Nous devons donc fournir des méthodes pour enregistrer de nouveaux backends et interroger ceux capables de lire un type de fichier particulier. Modifions donc le code ci-dessus en ajoutant une table de hachage dans le constructeur pour stocker les backends :

sub new {
    my $class = shift;
    my $service = shift;
    my $self = $class->SUPER::new($service, "/music/player/manager");
    $self->{backends} = {};
    bless $self, $class;
    return $self;
}

Et maintenant, une méthode pour enregistrer un nouveau backend. Celle-ci prend un nom de module Perl et l'utilise pour instancier un backend. Comme les backends seront également des objets DBus, nous devons passer une référence au service auquel nous sommes attachés, ainsi qu'un chemin sous lequel enregistrer le backend. Nous utilisons la méthode "get_service" pour récupérer une référence au service auquel le gestionnaire est attaché, et nous attachons le backend du lecteur à ce même service : Lorsqu'une méthode sur un objet DBus est invoquée, le premier paramètre est la référence de l'objet ($self), et le reste correspond aux paramètres fournis à l'appel de méthode. Ainsi, écrire une implémentation de méthode dans DBus n'est en réalité pas différent du Perl orienté objet normal (cf perltoot) :

sub register_backend {
    my $self = shift;
    my $name = shift;
    my $module = shift;
    eval "use $module";
    if ($@) {
        die "impossible de charger le backend $module: $@" ;
    }
    $self->{backends}->{$name} = $module->new($self->get_service,
                                              "/music/player/backend/$name");
}

En regardant ceci, on pourrait se demander ce qui se passe si la méthode "die" est déclenchée. Dans un tel scénario, plutôt que de terminer le processus de service, l'erreur sera capturée et propagée à l'appelant distant pour qu'il la gère.

Les backends de lecteur fournissent une méthode "get_track_types" qui renvoie une référence d'array des types de pistes musicales qu'ils prennent en charge. Nous pouvons utiliser cette méthode pour fournir une API permettant une récupération facile d'un backend pour un type de piste particulier. Cette méthode renverra un chemin avec lequel l'objet backend peut être accédé

sub find_backend {
    my $self = shift;
    my $extension = shift;
    foreach my $name (keys %{$self->{backends}}) {
       my $backend = $self->{backends}->{$name};
       foreach my $type (@{$backend->get_track_types}) {
          if ($type eq $extension) {
              return $backend->get_object_path;
          }
       }
    }
    die "pas de backend pour le type $extension";
}

Prenons un moment rapide pour considérer comment cette méthode serait utilisée pour lire une piste musicale. Si vous ne l'avez pas déjà fait, rafraîchissez votre mémoire à partir de Net::DBus::Tutorial::UsingObjects. Maintenant, nous avons un fichier MP3 que nous souhaitons lire, nous recherchons donc le chemin d'un backend, récupérons l'objet correspondant, et lisons la piste :

...obtenir le service de lecteur musical...
# Demander un chemin vers un lecteur pour les fichiers mp3
my $path = $service->find_backend("mp3");
# $path contient maintenant '/music/player/backend/mpg123'
# et nous pouvons obtenir l'objet backend
my $backend = $service->get_object($path);
# et enfin lire la piste
$backend->play("/vol/music/beck/guero/09-scarecrow.mp3");

FOURNIR DES DONNÉES D'INTROSPECTION

Le code ci-dessus est un objet complet et fonctionnel, prêt à être enregistré auprès d'un service, et comme les paramètres et les valeurs de retour pour les deux méthodes sont tous deux de simples chaînes, nous pourrions nous arrêter là. Dans certains cas, cependant, on pourrait vouloir être plus spécifique quant aux types de données attendus pour les paramètres, par exemple les entiers signés par rapport aux non signés. L'ajout d'une typisation explicite des données rend également l'interaction avec d'autres langages de programmation plus fiable. La fourniture de définitions explicites de types de données pour les méthodes exportées est connue dans le monde DBus sous le nom "Introspection", et cela rend la vie beaucoup plus fiable pour les utilisateurs de son service, qui pourraient utiliser un langage fortement typé comme C.

La première étape pour fournir des données d'introspection pour un objet DBus en Perl consiste à spécifier le nom de l'interface fournie par l'objet. Il s'agit typiquement d'une chaîne séparée par des points, par convention contenant le nom de domaine de l'application comme premier composant. La plupart des modules Perl finissent par se retrouver sur CPAN, on pourrait donc utiliser "org.cpan" comme premier composant, suivi du nom du package du module (en remplaçant :: par .), par exemple "org.cpan.music.player.manager". S'il n'est pas prévu d'héberger le module sur CPAN, un domaine personnel/de projet pourrait être utilisé, par exemple "com.berrange.music.player.manager". L'interface d'un objet est définie en chargeant le module Net::DBus::Exporter, en fournissant l'interface comme premier paramètre. Le code d'exemple précédent serait donc modifié pour ressembler à ceci :

package Music::Player::Manager;
use base qw(Net::DBus);
use Net::DBus::Exporter qw(com.berrange.music.player.manager)

Ensuite, il est nécessaire de fournir des types de données pour les paramètres et les valeurs de retour des méthodes. Le module Net::DBus::Exporter fournit une méthode "dbus_method" à cet effet, qui prend trois paramètres : le nom de la méthode exportée, une référence d'array des types de paramètres, et une référence d'array des types de retour (cette dernière peut être omise s'il n'y a pas de valeurs de retour). Cela peut être appelé à n'importe quel moment dans le code du module, mais par convention, il est préférable d'associer les appels à "dbus_method" à l'implémentation réelle de la méthode, ainsi :

dbus_method("register_backend", ["string", "string"]);
sub register_backend {
    my $self = shift;
    my $name = shift;
    my $module = shift;
    .. reste du corps de la méthode tronqué ...
}

Et, par conséquent :

dbus_method("find_backend", ["string"], ["string"])
sub find_backend {
    my $self = shift;
    my $extension = shift;
    ... corps de la méthode tronqué ...
}

DÉFINIR UN SERVICE

Maintenant que les objets ont été écrits, il est temps de définir un service. Un service n'est rien de plus qu'un nom bien connu pour un contrat d'API donné. Un contrat peut être considéré comme une définition d'une liste de chemins d'objets et des interfaces correspondantes qu'ils fournissent. Ainsi, quelqu'un d'autre pourrait venir et fournir une implémentation alternative de lecteur musical en utilisant les liaisons Python ou QT pour DBus, et s'il fournissait le même ensemble de chemins d'objets et d'interfaces, il pourrait légitimement enregistrer le même service sur le bus.

Le module Net::DBus::Service fournit les moyens d'enregistrer un service. Son constructeur attend une référence à l'objet bus (une instance de Net::DBus), ainsi que le nom du service. Comme pour les noms d'interface, le premier composant d'un nom de service est généralement dérivé d'un nom de domaine, puis suffixé par le nom de l'application, formant dans notre exemple "org.cpan.Music.Player". DÉFINIR UN SERVICE

Ce qui précède dans ce tutoriel est un exemple de ce dernier. Il est typique d'instancier et d'enregistrer ces objets dans le constructeur pour le service. Ainsi, un objet de service pour l'application lecteur de musique ressemblerait à ceci :

package Music::Player;
use base qw(Net::DBus::Service);
sub new {
    my $class = shift;
    my $bus = shift;
    my $self = $class->SUPER::new($bus, "org.cpan.music.player");
    bless $self, $class;
    $self->{manager} = Music::Player::Manager->new($self);
    return $self;
}

Net::DBus::Service fournit automatiquement un objet spécial à tous les services, sous le chemin "/org/freedesktop/DBus/Exporter". Cet objet implémente l'interface "org.freedesktop.DBus.Exporter" qui a une méthode "ListObject". Cela permet aux clients de déterminer une liste de tous les objets exportés dans un service. Bien que cela ne soit pas fonctionnellement nécessaire pour la plupart des applications, c'est néanmoins un outil utile pour les développeurs qui déboguent des applications, ou qui se demandent ce qu'un service fournit.

SE CONNECTER AU BUS

La dernière étape pour mettre notre service en marche est de le connecter au bus. Cela soulève une énigme intéressante : doit-on exporter le service sur le bus système (partagé par tous les utilisateurs et processus de la machine), ou sur le bus de session (un par utilisateur connecté à une machine). Dans certains cas, la réponse est évidente, un seul des deux bus ayant conceptuellement un sens. Dans d'autres cas, cependant, les bus de session et système sont valides. Dans le premier cas, on utiliserait les méthodes "session" ou <system> sur Net::DBus pour obtenir une poignée du bus désiré, tandis que dans le second cas, la méthode "find" serait utilisée. Celle-ci applique une heuristique pour déterminer le bus correct en fonction de l'environnement d'exécution. Dans le cas du lecteur de musique, les deux bus sont pertinents, donc le code pour connecter le service au bus ressemblerait à ceci :

use Net::DBus;
my $bus = Net::DBus->find;
my $player = Music::Player->new($bus);

Avec le service attaché au bus, il suffit d'exécuter la boucle de traitement des événements principale pour écouter et gérer les messages DBus entrants. Le code ci-dessus est donc modifié pour démarrer un simple réacteur :

use Net::DBus;
use Net::DBus::Reactor;
my $bus = Net::DBus->find;
my $player = Music::Player->new($bus);
Net::DBus::Reactor->main->run;
exit 0;

En enregistrant ce code dans un script "/usr/bin/music-player.pl", la programmation est terminée et le service est prêt à être utilisé par les clients sur le bus.

ACTIVATION DU SERVICE

On pourrait maintenant se demander comment démarrer au mieux le service, en particulier s'il s'agit d'un service capable de fonctionner sur les bus système et de session. DBus a la réponse dans le concept d'"activation". Ce qui se passe, c'est que lorsqu'un client sur le bus tente d'appeler une méthode, ou d'enregistrer un gestionnaire de signal contre un service qui ne fonctionne pas actuellement, il essaiera d'abord de démarrer le service. Les services qui souhaitent participer à ce processus doivent simplement placer un simple fichier de définition de service dans le répertoire "/usr/share/dbus-1/services". Le fichier doit être nommé pour correspondre au nom du service, avec l'extension de fichier ".service" ajoutée. Par exemple, "/usr/share/dbus-1/services/org.cpan.music.player.service" Le fichier contient deux clés, d'abord le nom du service, et ensuite le nom de l'exécutable utilisé pour exécuter le service, ou dans ce cas le script Perl. Ainsi, pour notre service simple, le fichier de données contiendrait :

[D-BUS Service]
Name=org.cpan.music.player
Exec=/usr/bin/music-player.pl
