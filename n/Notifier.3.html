ARGUMENTS

Procédure à appeler pour préparer l'attente d'événement dans Tcl_DoOneEvent.

Procédure que Tcl_DoOneEvent doit appeler après l'attente des événements. Vérifie si des événements se sont produits et, le cas échéant, les met en file d'attente.

Valeur arbitraire d'un mot à passer à setupProc, checkProc, ou deleteProc.

Indique le temps maximum à attendre pour un événement. Ceci est spécifié comme un intervalle (durée d'attente), pas comme une heure absolue (quand se réveiller). Tcl_Event *evPtr (entrée)
Un événement à ajouter à la file d'attente des événements. Le stockage pour l'événement doit avoir été alloué par l'appelant en utilisant Tcl_Alloc ou ckalloc.

INTRODUCTION

Les interfaces décrites ici sont utilisées pour personnaliser la boucle d'événements Tcl. Les deux personnalisations les plus courantes sont l'ajout de nouvelles sources d'événements et la fusion de la boucle d'événements de Tcl avec une autre boucle d'événements, telle que celle fournie par une application dans laquelle Tcl est intégrée. Chacune de ces tâches est décrite dans une section distincte ci-dessous.

Les procédures de cette entrée de manuel sont les éléments de base sur lesquels le notifier d'événements Tcl est construit. Le notifier d'événements est la couche la plus basse du mécanisme d'événements Tcl. Il se compose de trois choses :

[1]
Sources d'événements : celles-ci représentent les moyens par lesquels des événements peuvent être générés. Par exemple, il existe une source d'événements de minuteur qui implémente la procédure Tcl_CreateTimerHandler et la commande after, et il existe une source d'événements de fichier qui implémente la procédure Tcl_CreateFileHandler sur les systèmes Unix. Une source d'événements doit fonctionner avec le notifier pour détecter les événements aux moments opportuns, les enregistrer dans la file d'attente des événements et informer finalement le logiciel de niveau supérieur qu'ils se sont produits. Les procédures Tcl_CreateEventSource, Tcl_DeleteEventSource, et Tcl_SetMaxBlockTime, Tcl_QueueEvent, et Tcl_DeleteEvents sont principalement utilisées par les sources d'événements.
[2]
La file d'attente d'événements : pour les applications non multithreadées, il existe une file unique pour toute l'application, contenant les événements qui ont été détectés mais pas encore traités. Les sources d'événements placent les événements dans la file d'attente afin qu'ils puissent être traités en ordre à des moments appropriés pendant la boucle d'événements. La file d'attente d'événements garantit une discipline équitable de traitement des événements, de sorte qu'aucune source d'événements ne puisse affamer les autres. Elle permet également de sauvegarder les événements pour un traitement ultérieur. Les applications multithreadées fonctionnent de manière similaire, à la différence qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. Tcl_QueueEvent est utilisé (principalement par les sources d'événements) pour ajouter des événements à la file d'attente des événements et Tcl_DeleteEvents est utilisé pour supprimer des événements de la file sans les traiter. Dans une application multithreadée, Tcl_QueueEvent ajoute un événement à la file du thread courant, et Tcl_ThreadQueueEvent ajoute un événement à la file d'un thread spécifique.
[3]
La boucle d'événements : afin de détecter et de traiter les événements, l'application entre dans une boucle qui attend que les événements se produisent, les place dans la file d'attente des événements, puis les traite. La plupart des applications le feront en appelant la procédure Tcl_DoOneEvent, qui est décrite dans une entrée de manuel distincte.

La plupart des applications Tcl n'ont pas besoin de se soucier des détails internes du notifier Tcl. Cependant, le notifier est maintenant suffisamment flexible pour être redirigé soit vers une nouvelle plateforme, soit pour utiliser une boucle d'événements externe (comme la boucle d'événements Motif, lorsque Tcl est intégrée dans une application Motif). Les procédures Tcl_WaitForEvent et Tcl_SetTimer sont normalement implémentées par Tcl, mais peuvent être remplacées par de nouvelles versions pour rediriger le notifier (les procédures Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler, et Tcl_DeleteFileHandler doivent également être remplacées ; voir CRÉATION D'UN NOUVEAU NOTIFIER ci-dessous pour plus de détails). Les procédures Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode, et Tcl_SetServiceMode sont fournies pour aider à connecter la boucle d'événements de Tcl à une boucle d'événements externe telle que celle de Motif.

BASES DU NOTIFIER

La manière la plus simple de comprendre le fonctionnement du notifier est de considérer ce qui se passe lorsque Tcl_DoOneEvent est appelée. Tcl_DoOneEvent reçoit un argument flags qui indique quels types d'événements peuvent être traités et s'il faut bloquer ou non si aucun événement n'est prêt. Tcl_DoOneEvent effectue les opérations suivantes :

[1]
Vérifie la file d'attente des événements pour voir si elle contient des événements qui peuvent être traités. Si c'est le cas, traite le premier événement possible, le retire de la file et retourne. Elle le fait en appelant Tcl_ServiceEvent et en passant l'argument flags.
[2]
Prépare le blocage pour un événement. Pour ce faire, Tcl_DoOneEvent invoque une procédure setup dans chaque source d'événements. La source d'événements effectuera une initialisation spécifique à la source d'événements et appellera éventuellement Tcl_SetMaxBlockTime pour limiter le temps pendant lequel Tcl_WaitForEvent bloquera si aucun nouvel événement ne se produit.
[3]
Appelle Tcl_WaitForEvent. Cette procédure est implémentée différemment selon les plateformes ; elle attend qu'un événement se produise, en se basant sur les informations fournies par les sources d'événements. Elle peut amener l'application à bloquer si timePtr spécifie un intervalle autre que 0. Tcl_WaitForEvent retourne lorsqu'un événement s'est produit, tel qu'un fichier devenant lisible ou l'expiration de l'intervalle spécifié par timePtr. S'il n'y a aucun événement pour lequel Tcl_WaitForEvent doit attendre, de sorte qu'il bloquerait indéfiniment, il retourne immédiatement et Tcl_DoOneEvent retourne 0.
[4]
Appelle une procédure check dans chaque source d'événements. La procédure check détermine si des événements intéressant cette source se sont produits. Si c'est le cas, les événements sont ajoutés à la file d'attente des événements.
[5]
Vérifie la file d'attente des événements

CRÉATION D'UNE NOUVELLE SOURCE D'ÉVÉNEMENTS

Une source d'événements se compose de trois procédures appelées par le dispatch, plus des procédures C supplémentaires qui sont appelées par du code de haut niveau pour organiser les callbacks d'événements basés sur le temps. Les trois procédures appelées par le dispatch se composent des procédures de configuration et de vérification décrites précédemment, plus une procédure supplémentaire qui est appelée lorsqu'un événement est retiré de la file d'attente des événements pour être traité.

La procédure Tcl_CreateEventSource crée une nouvelle source d'événements. Ses arguments spécifient la procédure de configuration et la procédure de vérification pour la source d'événements. SetupProc doit correspondre au prototype suivant :

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

L'argument clientData sera le même que l'argument clientData de Tcl_CreateEventSource ; il est généralement utilisé pour pointer vers des informations privées gérées par la source d'événements. L'argument flags sera le même que l'argument flags passé à Tcl_DoOneEvent, sauf qu'il ne sera jamais 0 (Tcl_DoOneEvent remplace 0 par TCL_ALL_EVENTS). Flags indique quels types d'événements doivent être pris en compte ; si le bit correspondant à cette source d'événements n'est pas défini, la source d'événements doit retourner immédiatement sans effectuer d'action. Par exemple, la source d'événements de fichier vérifie le bit TCL_FILE_EVENTS.

Le SetupProc doit s'assurer que l'application se réveille lorsque des événements du type souhaité se produisent. Cela peut être fait de manière dépendante de la plateforme. Par exemple, sous Unix, une source d'événements pourrait appeler Tcl_CreateFileHandler ; sous Windows, elle pourrait demander une notification avec un événement Windows. Pour les sources d'événements basées sur des minuteries, comme les événements temporels ou tout événement sondé, la source d'événements peut appeler Tcl_SetMaxBlockTime pour forcer l'application à se réveiller même s'il n'y a pas d'événements. Si aucune source d'événements n'appelle Tcl_SetMaxBlockTime, Tcl_WaitForEvent attendra suffisamment longtemps pour qu'un événement se produise ; sinon, elle n'attendra que la durée la plus courte spécifiée par l'une des sources d'événements. Si une source d'événements sait qu'elle a déjà des événements prêts à être signalés, elle peut demander un temps de blocage maximal nul. Par exemple, la procédure de configuration de la source d'événements X s'assure de vérifier s'il y a déjà des événements en file d'attente. S'il y en a, elle appelle Tcl_SetMaxBlockTime avec un temps de blocage maximal de 0 afin que Tcl_WaitForEvent ne se bloque pas s'il n'y a pas de nouvelles données sur la connexion X. L'argument timePtr de Tcl_WaitForEvent pointe vers une structure décrivant un intervalle de temps en secondes et microsecondes :

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

Le champ usec doit être inférieur à 1000000.

Les informations fournies à Tcl_SetMaxBlockTime ne sont utilisées que pour le prochain appel à Tcl_WaitForEvent ; elles sont ignorées après le retour de Tcl_WaitForEvent. La prochaine fois qu'une attente d'événements sera effectuée, chaque procédure de configuration de source d'événements sera à nouveau appelée et pourra spécifier de nouvelles données pour cette attente d'événements.

Si l'application utilise une boucle d'événements externe au lieu de Tcl_DoOneEvent, les sources d'événements peuvent avoir besoin d'appeler Tcl_SetMaxBlockTime à d'autres moments. Par exemple, si un nouveau gestionnaire d'événements qui a besoin de sonder les événements est enregistré, la source d'événements peut appeler Tcl_SetMaxBlockTime pour définir un temps de blocage maximal nul afin de forcer la boucle d'événements externe à appeler Tcl. Dans ce cas, Tcl_SetMaxBlockTime appelle Tcl_SetTimer avec l'intervalle le plus court vu depuis le dernier appel à Tcl_DoOneEvent ou Tcl_ServiceAll.

En plus de la procédure générique Tcl_SetMaxBlockTime, d'autres procédures spécifiques à la plateforme peuvent également être disponibles pour le setupProc, s'il y a des informations supplémentaires nécessaires à Tcl_WaitForEvent sur cette plateforme. Par exemple, sur les systèmes Unix, l'interface Tcl_CreateFileHandler peut être utilisée pour attendre les événements de fichier.

La deuxième procédure fournie par chaque source d'événements est sa procédure de vérification, indiquée par l'argument checkProc de Tcl_CreateEventSource. CheckProc doit correspondre au prototype suivant :

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Les arguments de cette procédure sont les mêmes que ceux de setupProc. CheckProc est appelé par Tcl_DoOneEvent après avoir attendu les événements. On suppose qu'au moins une source d'événements est prête à ajouter un événement. Tcl_DoOneEvent appelle chaque source d'événements dans l'ordre, de sorte que toutes ont une chance d'ajouter tout événement prêt. La procédure de vérification fait deux choses. Premièrement, elle doit vérifier si des événements se sont déclenchés. Différentes sources d'événements le font différemment.

Si une source d'événements détecte un événement intéressant, elle doit ajouter l'événement à la file d'attente des événements de Tcl. Pour ce faire, la source d'événements appelle Tcl_QueueEvent. L'argument evPtr est un pointeur vers une structure allouée dynamiquement contenant l'événement (voir ci-dessous pour les problèmes de gestion de mémoire). Chaque source d'événements peut définir sa propre structure d'événement avec des informations pertinentes pour chaque source d'événements. Cependant, le premier membre de la structure doit être une structure de type Tcl_Event, et le pointeur vers cette structure est utilisé lors de la communication entre la source d'événements et le reste du dispatch. Un Tcl_Event a la définition suivante :

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La source d'événements doit remplir le champ proc de la structure avant d'appeler Tcl_QueueEvent. Le nextPtr est utilisé pour chaîner les événements dans la file d'attente et ne doit pas être modifié par la source d'événements.

Un événement peut être ajouté à la file d'attente dans l'une des trois positions, en fonction de l'argument position de Tcl_QueueEvent :

TCL_QUEUE_TAIL
Ajouter l'événement à la fin de la file d'attente, de sorte que tous les événements en attente soient traités en premier. C'est presque toujours la bonne position pour les nouveaux événements.
TCL_QUEUE_HEAD
Ajouter l'événement au début de la file d'attente, de sorte qu'il soit traité avant tous les événements déjà en file d'attente.
TCL_QUEUE_MARK
Ajouter l'événement au début de la file d'attente, sauf s'il y a d'autres événements au début dont la position est TCL_QUEUE_MARK ; si c'est le cas, ajouter le nouvel événement juste après tous les TCL_QUEUE_MARK existants. Cette valeur de position est utilisée pour insérer une séquence ordonnée d'événements au début de la file d'attente, comme une série d'événements Enter et Leave générés lors d'une opération de capture ou de libération dans Tk.

Lors du traitement d'un événement de la file d'attente (étapes 1 et 4 ci-dessus), Tcl_ServiceEvent appellera le proc spécifié dans la première structure Tcl_Event qui a été mise dans la file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

Le premier argument de proc est un pointeur vers l'événement, qui sera le même que le premier argument de l'appel à Tcl_QueueEvent qui a ajouté l'événement à la file d'attente. Le deuxième argument de proc est le flags de l'appel actuel à Tcl_ServiceEvent ; il est utilisé par la source d'événements pour retourner immédiatement si ses événements ne sont pas pertinents.

Il incombe à proc de gérer l'événement, généralement en appelant une ou plusieurs commandes Tcl ou des callbacks de niveau C. Une fois que la source d'événements a fini de gérer l'événement, elle retourne 1 pour indiquer que l'événement peut être retiré de la file d'attente. Si pour une raison quelconque la source d'événements décide que l'événement ne peut pas être géré à ce moment-là, elle peut retourner 0 pour indiquer que l'événement doit être différé à plus tard ; dans ce cas, Tcl_ServiceEvent passera à l'événement suivant dans la file d'attente et tentera de le traiter. Il y a plusieurs raisons pour lesquelles une source d'événements pourrait différer un événement. Une possibilité est que les événements de ce type soient exclus par l'argument flags. Par exemple, la source d'événements de fichier retourne toujours 0 si le bit TCL_FILE_EVENTS n'est pas défini dans flags. Un autre exemple de report d'événements se produit dans Tk si Tk_RestrictEvents a été appelé pour reporter certains types d'événements de fenêtre.

Lorsque proc retourne 1, Tcl_ServiceEvent retire l'événement de la file d'attente des événements et libère son stockage. Vous devez noter que le stockage d'un événement doit être alloué par la source d'événements (en utilisant Tcl_Alloc ou la macro Tcl ckalloc) avant d'appeler Tcl_QueueEvent, mais il sera libéré par Tcl_ServiceEvent, et non par la source d'événements.

Les applications multithread fonctionnent de manière similaire, sauf qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. L'appel à Tcl_QueueEvent dans une application multithread ajoute un événement à la file d'attente du thread actuel. Pour ajouter un événement à la file d'attente d'un autre thread, utilisez Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent accepte en argument un Tcl_ThreadId, qui identifie de manière unique un thread dans une application Tcl. Pour obtenir le Tcl_ThreadId du thread actuel, utilisez la procédure Tcl_GetCurrentThread. (Un thread devrait alors passer cet identifiant à d'autres threads afin que ceux-ci puissent ajouter des événements à sa file d'attente.) Après avoir ajouté un événement à la file d'attente d'un autre thread, Tcl_ThreadAlert est généralement appelé pour "réveiller" ce thread de dispatch afin de le notifier du nouvel événement.

Tcl_DeleteEvents peut être utilisé explicitement pour supprimer un ou plusieurs événements de la file d'attente des événements. Tcl_DeleteEvents appelle le proc pour chaque événement dans la file d'attente, supprimant ceux pour lesquels la procédure retourne 1. Les événements pour lesquels la procédure retourne 0 restent dans la file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

L'argument clientData sera le même que l'argument clientData de Tcl_DeleteEvents ;

il est généralement utilisé pour pointer vers des informations privées gérées par la source d'événements. Le evPtr pointera vers l'événement suivant dans la file d'attente.

Tcl_DeleteEventSource supprime une source d'événements. Les arguments setupProc, checkProc et clientData doivent correspondre exactement à ceux fournis à Tcl_CreateEventSource pour que la source d'événements soit supprimée. Si aucune source de ce type n'existe, Tcl_DeleteEventSource n'a aucun effet.

CRÉATION D'UN NOUVEAU NOTIFICATEUR

Le notificateur se compose de toutes les procédures décrites dans cette entrée de manuel, plus Tcl_DoOneEvent et Tcl_Sleep, qui sont disponibles sur toutes les plateformes, et Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont spécifiques à Unix. La plupart de ces procédures sont génériques, en ce sens qu'elles sont les mêmes pour tous les notificateurs. Cependant, aucune des procédures n'est dépendante du notificateur : Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler et Tcl_ServiceModeHook. Pour prendre en charge une nouvelle plateforme ou pour intégrer Tcl à une boucle d'événements spécifique à une application, vous devez écrire de nouvelles versions de ces procédures.

Tcl_InitNotifier initialise l'état du notificateur et retourne un descripteur à l'état du notificateur. Tcl appelle cette procédure lors de l'initialisation d'un interpréteur Tcl. De même, Tcl_FinalizeNotifier arrête le notificateur, et est appelée par Tcl_Finalize lors de l'arrêt d'un interpréteur Tcl.

Tcl_WaitForEvent est la procédure de plus bas niveau du notificateur ; elle est responsable de l'attente d'un événement « intéressant » ou de l'expiration d'un temps donné. Avant que Tcl_WaitForEvent ne soit invoquée, chacune des procédures de configuration des sources d'événements aura été appelée. L'argument timePtr de Tcl_WaitForEvent donne le temps maximum de blocage pour un événement, basé sur les appels à Tcl_SetMaxBlockTime effectués par les procédures de configuration et sur d'autres informations (telles que le bit TCL_DONT_WAIT dans flags).

Idéalement, Tcl_WaitForEvent ne devrait attendre qu'un événement se produise ; elle ne devrait pas réellement traiter l'événement de quelque manière que ce soit. Plus tard, les sources d'événements traiteront les événements bruts et créeront des Tcl_Events dans la file d'attente des événements dans leurs procédures checkProc. Cependant, sur certaines plateformes (comme Windows), cela n'est pas possible ; les événements peuvent être traités dans Tcl_WaitForEvent, y compris la mise en file d'attente de Tcl_Events et plus encore (par exemple, les rappels pour les widgets natifs peuvent être invoqués). La valeur de retour de Tcl_WaitForEvent doit être 0, 1 ou -1. Sur les plateformes comme Windows où les événements sont traités dans Tcl_WaitForEvent, une valeur de retour de 1 signifie qu'il peut y avoir d'autres événements en attente qui n'ont pas été traités. C'est un signe pour l'appelant qu'il doit rappeler Tcl_WaitForEvent s'il souhaite que tous les événements en attente soient traités. Une valeur de retour de 0 signifie qu'un nouvel appel à Tcl_WaitForEvent n'aura aucun effet : soit il s'agit d'une plateforme où Tcl_WaitForEvent attend seulement sans traiter d'événements, soit Tcl_WaitForEvent sait avec certitude qu'il n'y a pas d'événements supplémentaires à traiter (par exemple, elle est retournée parce que le temps est écoulé). Enfin, une valeur de retour de -1 signifie que la boucle d'événements n'est plus opérationnelle et que l'application devrait probablement se terminer. Sous Windows, cela se produit lorsqu'un message WM_QUIT est reçu ; sous Unix, cela se produit lorsque Tcl_WaitForEvent attendrait éternellement car il n'y avait pas de sources d'événements actives et que le délai d'attente était infini.

Tcl_AlertNotifier est utilisé dans les applications multithreadées pour permettre à n'importe quel thread de « réveiller » le notificateur pour l'alerter de nouveaux événements dans sa file d'attente. Tcl_AlertNotifier nécessite en argument le descripteur du notificateur retourné par Tcl_InitNotifier.

Si le notificateur sera utilisé avec une boucle d'événements externe, alors il doit également prendre en charge l'interface Tcl_SetTimer. Tcl_SetTimer est appelée par Tcl_SetMaxBlockTime chaque fois que le temps de blocage maximum a été réduit. Tcl_SetTimer doit organiser la boucle d'événements externe pour qu'elle appelle Tcl_ServiceAll après l'intervalle spécifié, même si aucun événement ne s'est produit. Cette interface est nécessaire car Tcl_WaitForEvent n'est pas appelée lorsqu'il y a une boucle d'événements externe. Si le notificateur ne sera utilisé qu'à partir de Tcl_DoOneEvent, alors Tcl_SetTimer n'a rien à faire.

Tcl_ServiceModeHook est appelée par la partie indépendante de la plateforme du notificateur lorsque le code client effectue un appel à Tcl_SetServiceMode. Ce hook est fourni pour prendre en charge les systèmes d'exploitation qui nécessitent une gestion spéciale des événements lorsque l'application est dans une boucle modale (le notificateur Windows, par exemple, utilise ce hook pour créer une fenêtre de communication).

Sur les systèmes Unix, la source d'événements de fichier nécessite également le support du notificateur. La source d'événements de fichier se compose des procédures Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont décrites dans la page de manuel de Tcl_CreateFileHandler.

Les interfaces Tcl_Sleep et Tcl_DoOneEvent sont décrites dans leurs pages de manuel respectives.

La manière la plus simple de créer un nouveau notificateur est de consulter le code d'un notificateur existant, tel que les fichiers unix/tclUnixNotfy.c ou win/tclWinNotify.c dans la distribution source de Tcl.

REMPLACEMENT DU NOTIFICATEUR

Un notificateur qui a été écrit selon les conventions ci-dessus peut également être installé dans un processus en cours à la place du notificateur standard. Ce mécanisme est utilisé de sorte qu'un seul exécutable puisse être utilisé (avec le notificateur standard) comme programme autonome et réutilisé (avec un notificateur de remplacement dans une extension chargeable) comme extension d'un autre programme, tel qu'un plugin de navigateur Web.

Pour ce faire, l'extension effectue un appel à Tcl_SetNotifier en passant un pointeur vers une structure de données Tcl_NotifierProcs. La structure a la disposition suivante :

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Après l'appel à Tcl_SetNotifier, les pointeurs donnés dans la structure Tcl_NotifierProcs remplacent tout notificateur qui avait été installé dans le processus.

Il est extrêmement déconseillé de remplacer un notificateur en cours d'exécution. Normalement, Tcl_SetNotifier doit être appelé au moment de l'initialisation du processus, avant le premier appel à Tcl_InitNotifier.

BOUCLES D'ÉVÉNEMENTS EXTERNES

Les interfaces du notificateur sont conçues pour que Tcl puisse être intégré dans des applications qui ont leurs propres boucles d'événements privées. Dans ce cas, l'application n'appelle pas Tcl_DoOneEvent, sauf dans le cas de boucles d'événements récursives telles que les appels aux commandes Tcl update ou vwait. La plupart du temps est passé dans la boucle d'événements externe de l'application. Dans ce cas, le notificateur doit organiser la boucle d'événements externe pour qu'elle rappelle Tcl lorsque quelque chose se passe sur les différentes sources d'événements Tcl. Ces rappels doivent organiser la mise en file d'attente des événements Tcl appropriés sur la file d'attente des événements Tcl.

Comme la boucle d'événements externe n'appelle pas Tcl_DoOneEvent régulièrement, il appartient au notificateur d'organiser l'appel à Tcl_ServiceEvent chaque fois qu'il y a des événements en attente sur la file d'attente des événements Tcl. La manière la plus simple de le faire est d'appeler Tcl_ServiceAll à la fin de chaque rappel de la boucle d'événements externe. Cela garantira que toutes les sources d'événements sont interrogées, que tous les événements mis en file d'attente sont traités et que tous les gestionnaires inactifs en attente sont traités avant de rendre le contrôle à l'application. De plus, les sources d'événements qui ont besoin d'interroger les événements peuvent appeler Tcl_SetMaxBlockTime pour forcer la boucle d'événements externe à appeler Tcl même si aucun événement n'est disponible sur la file d'attente des événements du système.

En tant qu'effet secondaire du traitement des événements détectés dans la boucle d'événements externe principale, Tcl peut appeler Tcl_DoOneEvent pour démarrer une boucle d'événements récursive dans des commandes comme vwait. Tcl_DoOneEvent appellera la boucle d'événements externe, ce qui entraînera des rappels comme décrit dans le paragraphe précédent, ce qui entraînera des appels à Tcl_ServiceAll. Cependant, dans ces cas, il est indésirable de traiter les événements dans Tcl_ServiceAll. Le traitement des événements là est inutile car le contrôle reviendra immédiatement à la boucle d'événements externe et donc à Tcl_DoOneEvent, qui peut traiter les événements elle-même. De plus, Tcl_DoOneEvent est censé traiter un seul événement, tandis que Tcl_ServiceAll traite normalement tous les événements en attente. Pour gérer cette situation, Tcl_DoOneEvent définit un indicateur pour Tcl_ServiceAll qui lui fait retourner sans traiter d'événements. Cet indicateur est appelé le mode de service ; Tcl_DoOneEvent le restaure à sa valeur précédente avant de retourner.

Dans certains cas, cependant, il peut être nécessaire que Tcl_ServiceAll traite les événements même lorsqu'il a été appelé depuis Tcl_DoOneEvent. Cela se produit lorsqu'il y a une autre boucle d'événements récursive appelée via un gestionnaire d'événements appelé par Tcl_DoOneEvent (comme celui qui fait partie d'un widget natif). Dans ce cas, Tcl_DoOneEvent peut ne pas avoir l'occasion de traiter les événements, donc Tcl_ServiceAll doit tous les traiter. Toute boucle d'événements récursive qui appelle une boucle d'événements externe plutôt que Tcl_DoOneEvent doit réinitialiser le mode de service afin que tous les événements soient traités dans Tcl_ServiceAll. Ceci est fait en appelant la procédure Tcl_SetServiceMode. Si Tcl_SetServiceMode reçoit TCL_SERVICE_NONE, alors les appels à Tcl_ServiceAll retourneront immédiatement sans traiter d'événements. Si Tcl_SetServiceMode reçoit TCL_SERVICE_ALL, alors les appels à Tcl_ServiceAll se comporteront normalement. Tcl_SetServiceMode retourne la valeur précédente du mode de service, qui doit être restaurée lorsque la boucle récursive se termine. Tcl_GetServiceMode retourne la valeur actuelle du mode de service.
