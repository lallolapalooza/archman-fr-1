Net::Server::Multiplex(3) Documentation Perl fournie par l'utilisateur Net::Server::Multiplex(3)

NOM

Net::Server::Multiplex - Multiplexe plusieurs connexions au sein d'un même processus

SYNTAXE

package MyPlexer;
use base qw(Net::Server::Multiplex);
sub mux_input {
    #...code...
}
__PACKAGE__->run();

DESCRIPTION

Cette personnalité est conçue pour gérer plusieurs connexions au sein d'un même processus. Elle ne doit être utilisée qu'avec des protocoles garantis de pouvoir répondre rapidement paquet par paquet. Si la détermination d'une réponse peut prendre du temps ou une durée inconnue, toutes les autres connexions établies seront bloquées jusqu'à ce que la réponse soit terminée. Si cette condition risque de se produire, cette personnalité ne devrait probablement pas être utilisée.

Elle combine des fonctionnalités intéressantes de Net::Server (comme la configuration du socket d'écoute du serveur, le traitement des fichiers de configuration, la gestion sécurisée des signaux, la gestion pratique de l'E/S standard de style inet, les fonctions de journalisation, la désactivation et le suivi des PID, et la redémarrabilité -SIGHUP) et des fonctionnalités intéressantes de IO::Multiplex (E/S tamponnées automatiques et objets par descripteur de fichier) pour une interface facile à utiliser.

Consultez examples/samplechat.pl distribué avec Net::Server pour un exemple simple de serveur de chat utilisant plusieurs de ces fonctionnalités.

FLUX DE TRAITEMENT

Le flux de traitement est écrit de manière ouverte, facile à remplacer et facile à accrocher. Le flux de base est illustré ci-dessous.

  $self->configure_hook;
  $self->configure(@_);
  $self->post_configure;
  $self->post_configure_hook;
  $self->pre_bind;
  $self->bind;
  if (redémarrage du serveur) {
      $self->restart_open_hook();
  }
  $self->post_bind_hook;
  $self->post_bind;
  $self->pre_loop_hook;
  $self->loop; # Ceci exécute essentiellement IO::Multiplex::loop
  # Pour les routines à l'intérieur d'un $self->loop
  # Voir TRAITEMENT CLIENT ci-dessous
  $self->pre_server_close_hook;
  $self->post_child_cleanup_hook;
  $self->server_close;
  if (redémarrage du serveur) {
      $self->restart_close_hook();
      $self->hup_server;
      # Recommencer le processus en commençant par configure_hook
}

Le serveur se termine ensuite.

TRAITEMENT CLIENT

Ce qui suit représente le flux du programme de traitement des clients :

$self->{server}->{client} = Net::Server::Proto::TCP->accept();  # NOTE : Multiplexé avec mux_input() ci-dessous
if (check_for_dequeue secondes écoulées) {
    $self->run_dequeue();
}
$self->get_client_info;
$self->post_accept_hook; # Style Net::Server
if ($self->allow_deny
    && $self->allow_deny_hook) {
  # (Le $self->process_request() de style Net::Server n'est jamais appelé.)
  # Un objet unique spécifique au client est créé
  # pour toutes les méthodes mux_* à partir de ce moment.
  $self = __PACKAGE__->new($self, client);
  $self->mux_connection; # Style IO::Multiplex
  for (chaque paquet reçu) {
    $self->mux_input;  # NOTE : Multiplexé avec accept() ci-dessus
  }
} else {
  $self->request_denied_hook;
  # Notez que si allow_deny ou allow_deny_hook échoue,
  # new(), mux_connection(), et mux_input() ne seront jamais appelés.
  # mux_eof() et mux_close() seront toujours appelés, mais en utilisant un
  # objet de rappel de socket d'écoute commun au lieu d'un objet unique spécifique au client.
}
$self->mux_eof;
$self->post_process_request_hook;
$self->mux_close;

Ce processus boucle ensuite en multiplexant entre le accept() pour la prochaine connexion et mux_input() lorsqu'une entrée arrive afin d'éviter de bloquer l'un ou l'autre.

HOOKS

Les méthodes *_hook mentionnées ci-dessus sont destinées à être remplacées par vos propres sous-routines si vous souhaitez fournir des fonctionnalités supplémentaires.

La méthode loop() de Net::Server a été remplacée pour exécuter la routine de boucle de IO::Multiplex à la place. Les méthodes Net::Server peuvent accéder à l'objet IO::Multiplex à l'"$self->{mux}" si désiré. Les méthodes IO::Multiplex peuvent accéder à l'objet Net::Server à l'"$self->{net_server}" si désiré.

La méthode process_request() n'est jamais utilisée avec cette personnalité.

Les autres hooks et méthodes Net::Server devraient fonctionner de la même manière.

"$self->run_dequeue()"
Ce hook n'est appelé qu'en conjonction avec le paramètre check_for_dequeue. Il s'exécutera toutes les check_for_dequeue secondes. Comme aucun fork n'est effectué, ce hook doit s'exécuter rapidement afin d'éviter de bloquer le reste du traitement.

TEMPS MORTS

set_timeout

Pour utiliser la fonctionnalité de délai d'attente optionnelle de IO::Multiplex, vous devez spécifier un délai en utilisant la méthode set_timeout.

$self->{net_server}->{mux}->set_timeout($fh, $secondes_maintenant);

$fh peut être soit un socket client, soit un descripteur de fichier de socket d'écoute dans le mux. $secondes_maintenant peut être fractionnaire pour obtenir des délais d'attente plus précis. Ceci est utilisé conjointement avec mux_timeout, que vous devez définir vous-même.

mux_timeout

La routine principale loop() appellera $obj->mux_timeout($mux, $fh) lorsque le délai d'attente spécifié dans set_timeout est atteint, où $fh est le même que celui spécifié dans set_timeout() et $obj est son objet correspondant (soit l'objet unique spécifique au client, soit l'objet de rappel principal d'écoute) et $mux est l'objet principal IO::Multiplex lui-même.

INTERFACE DE RAPPEL

Les objets de rappel doivent prendre en charge l'interface suivante. Vous n'avez pas à fournir toutes ces méthodes, fournissez simplement celles qui vous intéressent. Elles sont identiques aux hooks IO::Multiplex, sauf que STDOUT est lié au descripteur de fichier client correspondant pour votre commodité et pour mieux émuler le modèle Net::Server. Cependant, contrairement à certaines autres personnalités de Net::Server, vous ne devez jamais lire directement depuis STDIN. Vous devez définir une ou plusieurs des méthodes suivantes :

mux_connection ($mux,$fh)

(OPTIONNEL) Exécuté une fois lorsque le client se connecte initialement si allow_deny réussit. Notez que le hash de propriété "$self->{net_server}->{server}" peut être modifié par des connexions futures via Net::Server. Toutes les valeurs qu'il contient et que cet objet pourrait avoir besoin d'utiliser plus tard doivent être copiées dans son propre objet à ce stade.

Exemple:
$self->{peerport} = $self->{net_server}->{server}->{peerport};

mux_input ($mux,$fh,\$data)

(REQUIS) Exécuté chaque fois qu'un paquet est lu. Il doit consommer $data en commençant par la gauche et laisser les données non consommées dans le scalaire pour les futurs appels à mux_input.

mux_eof ($mux,$fh,\$data)

(OPTIONNEL) Exécuté une fois lorsque le client a fini d'écrire. Il doit consommer le reste de $data puisque mux_input() ne sera plus jamais exécuté.

mux_close ($mux,$fh)

(OPTIONNEL) Exécuté après la fermeture complète du socket client. Aucune autre tentative de lecture ou d'écriture vers le client ou vers STDOUT ne doit être effectuée.

mux_timeout ($mux,$fh)

(OPTIONNEL) Exécuté une fois lorsque le réglage set_timeout expire, comme expliqué ci-dessus.

BUGS

Ceci n'est connu que pour fonctionner avec des serveurs TCP.

Si vous avez besoin d'utiliser l'interface set_timeout / mux_timeout de style IO::Multiplex, vous ne pouvez pas utiliser le check_for_d de style Net::Server

Net::Server::Multiplex(3pm)

NAME

Net::Server::Multiplex - A multiplexing server subclass

SYNOPSIS

    use Net::Server;
    use Net::Server::Multiplex;

    my $server = Net::Server::Multiplex->new(
        Proto     => 'tcp',
        Address   => 'localhost',
        Port      => 8080,
        ReuseAddr => 1,
        MaxServers => 5,
        MinServers => 2,
        MaxRequests => 100,
        Timeout   => 10,
        Listen    => 10,
        AllowApologies => 1,
        User => 'nobody',
        Group => 'nobody',
        PidFile => '/var/run/myserver.pid',
        LogFile => '/var/log/myserver.log',
    );

    $server->run(
        sub {
            my $connection = shift;
            # handle connection
        }
    );

DESCRIPTION

This module extends Net::Server to provide a multiplexing server, using the IO::Multiplex module to handle multiple client connections efficiently.

PROCESS FLOW

The server accepts incoming connections and forks a new process for each connection. Each child process then uses IO::Multiplex to handle multiple connections within that process. This approach allows for a large number of concurrent connections without a prohibitive number of processes.

CLIENT PROCESSING

The run method takes a subroutine reference as an argument. This subroutine is called for each new client connection. The subroutine receives the client connection object as its argument and is responsible for handling the communication with the client.

HOOKS

Net::Server::Multiplex supports the following hooks:

pre_accept
Called before accepting a new connection.
post_accept
Called after accepting a new connection.
pre_fork
Called before forking a new process.
post_fork
Called after forking a new process (in the child process).
pre_client
Called before handling a client connection.
post_client
Called after handling a client connection.
pre_close
Called before closing a client connection.
post_close
Called after closing a client connection.

TIMEOUTS

The Timeout parameter sets the maximum time a client connection can remain idle. If a connection exceeds this timeout, it will be closed.

The MuxTimeout parameter is used internally by IO::Multiplex to specify the maximum time to wait for activity on any multiplexed socket before checking for timeouts.

CALLBACK INTERFACE

The run_dequeue method provides a compatibility interface to comply with the Net::Server::Fork style run_dequeue. It is implemented in terms of the IO::Multiplex style set_timeout and mux_timeout methods. This method will not work if the check_for_dequeue option is specified.
