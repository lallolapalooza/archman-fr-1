Qu'est-ce que perl-ldap ?

perl-ldap est le nom de la distribution. La distribution perl-ldap contient les modules Net::LDAP.

Pourquoi une autre implémentation Perl LDAP ?

L'objectif de perl-ldap est d'être aussi portable que possible. Pour ce faire, il est entièrement implémenté en Perl. Ainsi, partout où Perl fonctionne, perl-ldap fonctionnera. Ce n'est pas le cas pour d'autres implémentations qui nécessitent un compilateur C.

TERMINOLOGIE LDAP ET ANNuaire.

Afin d'aider l'utilisateur à mieux comprendre le module perl-ldap, une terminologie LDAP clé est définie ici.

Qu'est-ce qu'un annuaire ?

Un annuaire est une base de données hiérarchique à usage spécial qui contient généralement des informations typées telles que des chaînes de caractères, des données binaires ou des certificats X.509.

Qu'est-ce que LDAP ?

LDAP signifie Lightweight Directory Access Protocol (Protocole léger d'accès aux annuaires). Le mot Protocole est le mot clé dans la définition de la phrase précédente. LDAP n'est PAS du matériel ou du logiciel. C'est un protocole qui définit comment un client et un serveur communiqueront entre eux.

Le Lightweight Directory Access Protocol est défini dans une série de Requests For Comments, mieux connues sous le nom de RFC. Les RFC peuvent être trouvées sur Internet à l'adresse http://www.ietf.org/ (le dépôt maître) et dans de nombreux autres endroits. Il existe un lien vers toutes les RFC liées à LDAP sur le site web de perl-ldap, à l'adresse http://ldap.perl.org/rfc.html. Certains des numéros de RFC les plus importants sont RFC 4510 - 4519 pour LDAP (anciennement appelé LDAPv3) et le RFC historique 1777 pour LDAPv2.

Qu'est-ce qu'un annuaire LDAP ?

Au sens strict de la définition, il n'existe pas d'annuaire LDAP. Pour être pratique dans cette situation, les professionnels des annuaires parlent tous les jours de leur annuaire comme d' "un annuaire LDAP" car il est facile à dire et qu'il véhicule le type de protocole utilisé pour communiquer avec leur annuaire. En utilisant cette définition, un annuaire LDAP est un annuaire dont le logiciel serveur est conforme au Lightweight Directory Access Protocol lors de la communication avec un client.

Qu'est-ce qu'une Entrée ?

La définition traditionnelle d'un objet annuaire est appelée une Entrée. Les entrées sont composées d'attributs qui contiennent les informations à enregistrer sur l'objet.

(Une entrée dans LDAP est quelque peu analogue à un enregistrement dans une table d'une base de données SQL, mais ne vous attardez pas trop sur cette analogie !)

Les entrées sont conservées dans une structure en arbre inversée. Les entrées peuvent donc contenir des entrées subordonnées, et les entrées doivent avoir une seule entrée supérieure directe.

Ent

Qu'est-ce qu'une entrée ?

Une entrée est un objet dans l'annuaire. Par exemple, une personne peut être une entrée. Une imprimante peut être une entrée. Un emplacement peut être une entrée.

Chaque entrée a un nom unique dans l'annuaire.

Les entrées avec des entrées subordonnées sont appelées des entrées « non feuilles ».

Les entrées sans entrées subordonnées sont appelées des entrées « feuilles ».

L'entrée directement supérieure d'une entrée est appelée le « parent » de l'entrée.

On dit aussi que les entrées « non feuilles » ont des entrées « enfants ».

Qu'est-ce qu'un attribut ?

Les entrées dans un annuaire sont composées d'attributs qui contiennent des informations sur l'objet. Chaque attribut a un type et peut contenir une ou plusieurs valeurs.

Par exemple :

cn=Road Runner

est un attribut de type « cn » et de valeur unique.

Chaque attribut est décrit par une « syntaxe » qui définit quel type d'informations peut être stocké dans les valeurs des attributs. Tenter de stocker une valeur qui n'est pas conforme à la syntaxe de l'attribut entraînera une erreur.

Par exemple :

jpegPhoto=unknown

n'est pas autorisé par l'annuaire, car les jpegPhotos ne peuvent contenir que des images au format JPEG.

La plupart des syntaxes utilisées dans LDAP décrivent cependant des chaînes de caractères plutôt que des objets binaires (comme les JPEGs ou les certificats).

En LDAPv3, la plupart de ces syntaxes prennent en charge Unicode codé en UTF-8. Comme les modules Net::LDAP ne modifient pas les chaînes que vous leur passez comme valeurs d'attributs (elles sont envoyées au serveur LDAP telles quelles), pour utiliser des caractères accentués, il vous suffit de coder vos chaînes en UTF-8. Il existe des modules sur CPAN qui vous aideront dans cette tâche.

Notez que les serveurs LDAPv2 utilisaient un système appelé T.61 au lieu d'Unicode et d'UTF-8. La plupart des serveurs n'implémentent pas T.61 correctement, et il est recommandé d'utiliser LDAPv3 à la place.

Les attributs peuvent également être recherchés. Les algorithmes utilisés pour effectuer différents types de recherches sont décrits par les « règles de correspondance » de l'attribut. Certaines règles de correspondance sont sensibles à la casse et d'autres ne le sont pas, par exemple. Parfois, aucune règle de correspondance n'est définie pour un attribut particulier : il n'y a aucun moyen de rechercher des jpegPhotos contenant une sous-chaîne !

Vous pouvez examiner toutes les définitions d'attributs d'un serveur en lisant le schéma du serveur.

Qu'est-ce qu'une classe d'objets ?

Une classe d'objets est le nom associé à un groupe d'attributs qui doivent être présents dans une entrée, et au groupe d'attributs qui peuvent également être présents dans une entrée.

Les classes d'objets peuvent être dérivées (sous-classées) d'autres classes d'objets. Par exemple, la classe d'objets très utilisée « inetOrgPerson » est dérivée de « organizationalPerson », qui est elle-même dérivée de « person », qui est elle-même dérivée de « top ».

Chaque entrée possède un attribut appelé « objectClass » qui liste tous les noms des classes d'objets (et leurs superclasses) utilisées avec l'entrée.

Vous pouvez examiner toutes les définitions de classes d'objets d'un serveur en lisant le schéma du serveur.

Qu'est-ce qu'un nom unique (DN) ?

Chaque entrée d'un annuaire possède un nom unique, ou DN. C'est un identifiant d'entrée unique dans l'ensemble de l'annuaire. Deux entrées ne peuvent pas avoir le même DN dans le même annuaire.

Exemples de DN :

cn=Road Runner, ou=bird, dc=cartoon, dc=com
ou=bird, dc=cartoon, dc=com
dc=cartoon, dc=com
dc=com

Qu'est-ce qu'un nom relatif unique (RDN) ?

Chaque DN est composé d'une séquence de noms relatifs uniques, ou RDN. Les séquences de RDN sont séparées par des virgules (,). En LDAPv2, les points-virgules (;) étaient également autorisés. Il peut y avoir plus d'un RDN identique dans un annuaire, mais ils doivent avoir des entrées parentes différentes.

Techniquement, un RDN contient des assertions attribut-valeur, ou AVA. Lorsqu'une AVA est écrite, le nom de l'attribut est séparé de la valeur de l'attribut par un signe égal (=).

Exemple de DN :

cn=Road Runner,ou=bird,dc=cartoon,dc=com
RDN du DN précédent :
RDN => cn=Road Runner
RDN => ou=bird
RDN => dc=cartoon
RDN => dc=com

Les RDN peuvent contenir plusieurs attributs, bien que ce soit un peu inhabituel. On les appelle RDN multi-AVA, et chaque AVA est séparée dans le RDN des autres par un signe plus (+).

Exemple de DN avec un RDN multi-AVA :

cn=Road Runner+l=Arizona,ou=bird,dc=cartoon,dc=com

Où est conservé le nom d'une entrée ?

Les entrées ne contiennent pas leur DN. Lorsque vous récupérez une entrée d'une recherche, le serveur vous indique le DN de chaque entrée.

En revanche, les entrées contiennent bien leur RDN. Rappelez-vous que le RDN est formé d'une ou plusieurs assertions attribut-valeur (AVA) ; chaque entrée doit contenir tous les attributs et valeurs du RDN.

Par exemple, l'entrée :

cn=Road Runner+l=Arizona,ou=bird,dc=cartoon,dc=com

doit contenir un attribut « cn » contenant au moins la valeur « Road Runner », et un attribut « l » contenant au moins la valeur « Arizona ».

Les attributs utilisés dans le RDN peuvent contenir des valeurs supplémentaires, mais l'entrée n'a toujours qu'un seul DN.

Qu'est-ce qu'une base de recherche ?

Une base de recherche est un nom unique qui sert de point de départ aux requêtes de recherche.

Exemple de DN :

cn=Road Runner,ou=bird,dc=cartoon,dc=com

Bases de recherche possibles pour le DN précédent :

Base => cn=Road Runner,ou=bird,dc=cartoon,dc=com
Base => ou=bird,dc=cartoon,dc=com
Base => dc=cartoon,dc=com
Base => dc=com

Définir la base de recherche sur la branche la plus basse possible de l'annuaire accélérera considérablement les recherches.

Quelle est la différence entre un serveur LDAP et une base de données relationnelle ?

La différence la plus fondamentale est qu'un serveur d'annuaire est une base de données spécialisée conçue pour fournir des recherches rapides. Alors qu'une base de données relationnelle est optimisée pour les transactions (où une série d'opérations est comptée comme 1, donc si l'une des étapes échoue, le SGBDR peut revenir à l'état où il était avant que vous ne commenciez).

Les annuaires sont également généralement hiérarchiques (les SGBDR sont généralement plats, mais vous pouvez implémenter une hiérarchie à l'aide de tables et de requêtes), peuvent être mis en réseau, distribués et répliqués.

LDAP fournit un standard ouvert pour un service d'annuaire.

Typiquement, nous utilisons LDAP pour les annuaires d'e-mails (tous les clients de messagerie populaires fournissent maintenant un client LDAP) et les services d'autorisation (authentification et contrôle d'accès).

Vous pourriez utiliser un SGBDR pour ce type de requêtes, mais il n'y a pas de standard défini, en particulier sur TCP/IP pour se connecter aux bases de données sur le réseau. Il existe des protocoles spécifiques à la langue (comme DBI pour Perl et JDBC pour Java) qui masquent ce problème derrière une abstraction d'API, mais ce n'est pas un substitut à un protocole d'accès standard.

LDAP commence à être utilisé pour des rôles traditionnellement dévolus aux SGBDR en termes de gestion générale des données, car il est plus facile de configurer un serveur LDAP (une fois que l'on comprend la nomenclature de base) et qu'on n'a pas besoin d'un DBA pour écrire ses requêtes, et surtout, tous les serveurs LDAP parlent le même protocole essentiel, vous n'avez donc pas à vous soucier d'un pilote de base de données essayant de le connecter à Internet. Une fois qu'un serveur LDAP est opérationnel, il est automatiquement disponible sur le net. Il est possible de se connecter à un serveur LDAP à partir d'une variété de mécanismes, y compris presque tous les langages de programmation possibles.

Vous trouverez plus d'informations sur ce sujet sur les URL suivantes :

http://www.openldap.org/faq/data/cache/378.html
http://www.isode.com/whitepapers/ic-6055.html

Quelle est la différence entre une référence LDAP et un renvoi LDAP ?

Un renvoi est retourné lorsque l'opération entière doit être renvoyée à un autre serveur.

Une référence de continuation est retournée lorsqu'une partie de l'opération doit être renvoyée à un autre serveur.

Voir la RFC 4511 section 4.5.3 pour plus de détails.

INSTALLATION de perl-ldap

Comment installer perl-ldap ?

Pour installer les modules présents dans la distribution perl-ldap, suivez les mêmes étapes que pour la plupart des autres distributions trouvées sur CPAN, à savoir :

# remplacez 0.62 par la version que vous avez
gunzip perl-ldap-0.62.tar.gz
tar xvf perl-ldap-0.62.tar
cd perl-ldap-0.62
perl Makefile.PL
make
make test
make install

Mais je n'ai pas `make`, comment puis-je installer perl-ldap ?

Eh bien, par chance, les modules de perl-ldap ne font rien de complexe, une simple copie suffit donc pour l'installation. Exécutez d'abord :

perl -V

Cela affichera des informations sur la version de Perl que vous avez installée. Vers le bas, vous trouverez quelque chose comme :

@INC:
  /usr/local/lib/perl/5.18.2
  /usr/local/share/perl/5.18.2
  /usr/lib/perl5
  /usr/share/perl5
  /usr/lib/perl/5.18
  /usr/share/perl/5.18
  /usr/local/lib/site_per

Ceci est une liste de répertoires que Perl recherche lorsqu'il est à la recherche d'un module. Le répertoire dont vous avez besoin est le répertoire site_perl, mais sans le nom d'architecture du système, dans ce cas, c'est "/usr/local/lib/site_perl". Les fichiers requis peuvent ensuite être installés avec :

# remplacez 0.62 par la version que vous avez
gunzip perl-ldap-0.62.tar.gz
tar xvf perl-ldap-0.62.tar
cd perl-ldap-0.62/lib
cp -r * /usr/local/lib/site_perl

Comment puis-je charger perl-ldap dans une installation ActiveState Perl ?

Il existe plusieurs façons pour perl-ldap d'être

installée dans un arbre ActiveState Perl.

1.
La commande ActiveState ppm peut être utilisée pour installer perl-ldap. Lorsqu'une nouvelle version de perl-ldap est publiée, il faut un certain temps à ActiveState pour intégrer la nouvelle version dans le système ppm d'ActiveState.
2.
Si l'utilisateur dispose de nmake, il peut effectuer une installation normale de modules Perl en utilisant nmake au lieu de make.
3.
Si l'utilisateur ne dispose ni de nmake ni de make, il peut installer perl-ldap en utilisant le script install-nomake en exécutant la commande suivante. 
perl install-nomake

Le script install-nomake peut être utilisé sur tout système sur lequel make n'est pas installé.

UTILISATION DE NET::LDAP

Comment puis-je me connecter à mon serveur ?

La connexion au serveur est créée lorsque vous créez un nouvel objet Net::LDAP, par exemple :

$ldap = Net::LDAP->new($server);

Net::LDAP->new renvoie parfois undef, pourquoi ?

Le constructeur renverra undef s'il y a eu un problème lors de la connexion au serveur spécifié. Tout message d'erreur sera disponible dans $@

Quel est le bon format du DN de liaison ?

Le DN utilisé pour se lier à un répertoire est un DN ENTIÈREMENT QUALIFIÉ. La structure exacte du DN dépendra des données qui ont été stockées dans le serveur.

Voici des exemples valides.

uid=clif,ou=People,dc=umich,dc=edu
cn=directory manager,ou=admins,dc=umich,dc=edu

Dans certains serveurs, le DN entièrement qualifié du gestionnaire de répertoire serait le suivant.

cn=directory manager

Comment puis-je savoir quand le serveur renvoie une erreur, bind() renvoie toujours true ?

La plupart des méthodes de Net::LDAP renvoient un objet Net::LDAP::Message, ou une sous-classe de celui-ci. Cet objet contiendra les résultats du serveur, y compris le code de résultat.

Ainsi, par exemple, pour déterminer le résultat de l'opération de liaison (bind).

$mesg = $ldap->bind( $dn, password => $passwd );
if ( $mesg->code ) {
  # Gérer les codes d'erreur ici
}

Comment puis-je définir la version LDAP d'une connexion à mon serveur LDAP ?

Ceci est fait en ajoutant l'option version lors de la connexion ou de la liaison au serveur LDAP.

Par exemple ;

$ldap = Net::LDAP->new( $server, version => 3 );

ou

$mesg = $ldap->bind( $dn, password => $passwd, version => 3 );

                         version => 3);

You can also use the constructor in a more compact form. Note that in the case of the compact form, the port is optional, and the version is optional. Note also that in the compact form, the first argument can be a URI.

use Net::LDAP;
$ldap = Net::LDAP->new('ldap.acme.com'); # port defaults to 389
$ldap = Net::LDAP->new('ldap.acme.com', port => 1000);
$ldap = Net::LDAP->new('ldap.acme.com', version => 2);

There is a default port of 389 and a default version of 3. So the previous example is equivalent to:

use Net::LDAP;
$ldap = Net::LDAP->new('ldap.acme.com', port => 389, version => 3);

With perl-ldap 0.27 the default LDAP version is 3.

I did a search on my directory using the 'search' method. Where did the results go?

Your search results are stored in a 'search object'. Consider the following:

use Net::LDAP;
$ldap = Net::LDAP->new('ldap.acme.com') or die "$@";
$mesg = $ldap->search(
                      base   => "o=acme.com",
                      filter => "uid=jsmith",
                     );

$mesg is a search object. It is a reference blessed into the Net::LDAP::Search package. By calling methods on this object you can obtain information about the result and also the individual entries.

The first thing to check is if the search was successful. This is done with the method $mesg->code. This method will return the status code that the server returned. A success will yield a zero value, but there are other values, some of which could also be considered a success. See Net::LDAP::Constant

use Net::LDAP::Util qw(ldap_error_text);
die ldap_error_text($mesg->code)
  if $mesg->code;

There are two ways in which you can access the entries. You can access then with an index or you can treat the container like a stack and shift each entry in turn. For example

# as an array
# How many entries were returned from the search
my $max = $mesg->count;
for (my $index = 0 ; $index < $max ; $index++) {
  my $entry = $mesg->entry($index);
  # ...
}
# or as a stack
while (my $entry = $mesg->shift_entry) {
  # ...
}

In each case $entry is an entry object. It is a reference blessed into the Net::LDAP::Entry package. By calling methods on this object you can obtain information about the entry.

For example, to obtain the DN for the entry

$dn = $entry->dn;

To obtain the attributes that a given entry has

@attrs = $entry->attributes;

And to get the list of values for a given attribute

@values = $entry->get( 'sn' );

And to get the first of the values for a given attribute

$values = $entry->get( 'cn' );

One thing to remember is that attribute names are case insensitive, so 'sn', 'Sn', 'sN' and 'SN' are all the same.

So, if you want to print all the values for the attribute 'ou' then this is as simple as

foreach ($entry->get_value( 'ou' )) {
    print $_,"\n";
  }

Now if you just want to print all the values for all the attributes you can do

foreach my $attr ($entry->attributes) {
  foreach my $value ($entry->get_value($attr)) {
    print $attr, ": ", $value, "\n";
  }
}

How do I limit the scope of a directory search?

You limit the scope of a directory search by setting the scope parameter of search request. Consider the following:

use Net::LDAP;
$ldap = Net::LDAP->new('ldap.acme.com') or die "$@";
$mesg = $ldap->search(
                      base   => "o=acme.com",
                      scope  => 'sub',
                      filter => "uid=jsmith",
                     );

Values for the scope parameter are as follows.

base
Search only the base object.
one
Search the entries immediately below the base object.
sub
subtree
Search the whole tree below (and including) the base object. This is the default.
children
Search the whole subtree below the base object, excluding the base object itself.

Note: children scope requires LDAPv3 subordinate feature extension.

GETTING SEARCH RESULTS

There are two ways of retrieving the results of a requested LDAP search; inline and by using a callback subroutine.

USING THE INLINE APPROACH

Using the inline approach involves requesting the data and then waiting for all of the data to be returned before the user starts processing the data.

Example:

use Net::LDAP;
$ldap = Net::LDAP->new('ldap.acme.com') or die "$@";
$mesg = $ldap->search(
                      base   => "o=acme.com",
                      scope  => 'sub',
                      filter => "sn=smith",
                     );
#
# At this point the user can get the returned data as an array
# or as a stack.
# In this example we will use an array
# How many entries were returned from the search
my $max = $mesg->count;
for (my $index = 0 ; $index < $max ; $index++)
{
  my $entry = $mesg->entry($index);
  my $dn = $entry->dn; # Obtain DN of this entry
  @attrs = $entry->attributes; # Obtain attributes for this entry.
  foreach my $var (@attrs)
  {
    #get a list of values for a given attribute
    $attr = $entry->get_value( $var, asref => 1 );
    if ( defined($attr) )
    {
      foreach my $value ( @$attr )
      {
        print "$var: $value\n";  # Print each value for the attribute.
      }
    }
  }
}

As you can see the example is straightforward, but there is one drawback to this approach. You must wait until all entries for the request search to be returned before you can process the data. If there several thousand entries that match the search filter this could take quite a long time period.

USING THE CALLBACK SUBROUTINE APPROACH

Using the callback approach involves requesting the data be sent to a callback subroutine as each entry arrives at the client.

A callback is just a subroutine that is passed two parameters when it is called, the mesg and entry objects.

Example:

use Net::LDAP;
$ldap = Net::LDAP->new('ldap.acme.com') or die "$@";
$mesg = $ldap->search(
                      base   => "o=acme.com",
                      scope  => 'sub',
                      filter => "sn=smith",
                      callback => \&callback,
                     );
#
# At this point the user needs to check the status of the
# ldap search.
#
if ( $mesg->code )
{
   $errstr = $mesg->code;
   print "Error code:  $errstr\n";
   $errstr = ldap_error_text($errstr);
   print "$errstr\n";
}
sub callback
{
my ( $mesg, $entry) = @_;
  #
  # First you must check to see if something was returned.
  # Last execution of callback subroutine will have no
  # defined entry and mesg object
  #
  if ( !defined($entry) )
  {
    print "No records found matching filter $match.\n"
    if ($mesg->count == 0) ; # if mesg is not defined nothing will print.
    return;
  }
  my $dn = $entry->dn; # Obtain DN of this entry
  @attrs = $entry->attributes; # Obtain attributes for this entry.
  foreach my $var (@attrs)
  {
   #get a list of values for a given attribute
   $attr = $entry->get_value( $var, asref => 1 );
   if ( defined($attr) )
   {
     foreach my $value ( @$attr )
     {
       print "$var: $value\n";  # Print each value for the attribute.
     }
   }
  }
  #
  # For large search requests the following line of code
  # may be very important, it will reduce the amount of memory
  # used by the search results.
  #
  # If the user is not worried about memory usage then the line
  # of code can be omitted.
  #
  $mesg->pop_entry;
}  # End of callback subroutine

As you can see the example is straightforward and it does not waste time waiting for all of the entries to be returned. However if the pop_entry method is not used the callback approach can allocate a lot of memory to the search request.

USING LDAP GROUPS.

What are LDAP groups?

LDAP groups are object classes that contain an attribute that can store multiple DN values. Two standard object classes are 'groupOfNames' (which has a 'member' attribute) and 'groupOfUniqueNames' (which has a 'uniqueMember' attribute.)

According to the RFCs a group can be a member of another group, but some LDAP server vendors restrict this flexibility by not allowing nested groups in their servers.

Two scripts for working with groups are available in the contrib directory. They are isMember.pl and printMembers.pl.

How do you format a filter to search

Comment formater un filtre pour rechercher des entrées dont l'attribut 'member' a une valeur particulière ?

Demander (member=*) est OK - l'annuaire utilise la règle de correspondance d'égalité qui est définie pour l'attribut member.

Demander (member=c*) n'est pas OK - il n'y a pas de règle de correspondance de sous-chaîne définie pour l'attribut member. C'est parce que les valeurs de member ne sont *pas* des chaînes de caractères, mais des noms distinctifs. Il n'y a pas de règle de correspondance de sous-chaîne pour les DN, voir la section 2.7 de la RFC 4519.

Ce que vous devez faire est d'obtenir les résultats de (member=*) puis de sélectionner les résultats requis parmi les valeurs retournées. Vous devez le faire en utilisant la connaissance de la représentation textuelle des DN définie dans la RFC 4514, ce qui est important car le même DN peut avoir des représentations textuelles différentes. Vous devez donc effectuer une canonisation si vous voulez être correct.

Est-il possible d'obtenir une entrée complète, DN et attributs sans spécifier le nom des attributs ?

Oui, spécifiez simplement que vous voulez une liste de zéro attribut en retour. La RFC indique que cela demande au serveur de retourner tous les attributs lisibles (il peut y avoir des contrôles d'accès pour en empêcher certains d'être retournés).

Donc, dans la méthode de recherche, définissez simplement (pour LDAPv2) :

attrs => [ ]

Si vous utilisez LDAPv3, vous pouvez spécifier un attribut appelé "*" à la place, ce qui vous permet de demander des attributs supplémentaires (c'est-à-dire opérationnels) dans la même recherche.

attrs => [ "*" ]

Pour obtenir tous les attributs opérationnels dans une recherche, certains serveurs autorisent l'utilisation de l'attribut pseudo "+". Ainsi, avec ces serveurs

attrs => [ "*", "+" ]

retournera le maximum d'informations du serveur.

Que se passe-t-il lorsque vous supprimez un attribut qui n'existe pas ?

C'est une erreur de supprimer un attribut qui n'existe pas. Lorsque vous recevez l'erreur, le serveur ignore l'intégralité de l'opération de modification que vous lui avez envoyée, vous devez donc vous assurer que l'erreur ne se produit pas.

Une autre approche, si vous utilisez LDAPv3 (notez qu'à partir de la version .27, Net::LDAP utilise LDAPv3 par défaut) est d'utiliser un 'replace' avec votre nom d'attribut et aucune valeur. En LDAPv3, cela est défini pour fonctionner toujours, même si cet attribut n'existe pas dans l'entrée.

C'est-à-dire :

my $mesg = $ldap->modify( $entry, replace => { %qv_del_arry } );

Mais assurez-vous d'utiliser LDAPv3, car il est défini pour *ne pas* fonctionner en LDAPv2. (Une belle incompatibilité entre LDAPv2 et LDAPv3.)

Comment puis-je supprimer une référence d'un arbre LDAP ?

Comme il s'agit d'une fonctionnalité propriétaire, vous devrez consulter la documentation de votre serveur. Vous pourriez trouver que vous devez utiliser un contrôle. S'il existe un contrôle appelé quelque chose comme ManageDsaIT, c'est celui que vous devriez probablement utiliser. Pour un fonctionnement correct, vous aurez besoin du numéro OID de ManageDsaIT ; 2.16.840.1.113730.3.4.2 et ne pas spécifier de valeur pour type.

Le code requis ressemblera à l'extrait de code suivant.

$mesg =  $ldap->delete("ref=\"ldap://acme/c=us,o=bricks\",o=clay",
                control => {type => "2.16.840.1.113730.3.4.2"} );

Comment puis-je ajouter une entrée ACI/ACL à un serveur d'annuaire avec perl-ldap ?

Les ACI et ACL sont des fonctionnalités propriétaires dans LDAP. L'extrait de code suivant fonctionne avec un serveur d'annuaire Netscape. Vous devrez spécifier le bon DN (-DN-) et le bon attribut (-ATTRNAMEs-).

my $aci = '(target="ldap:///-DN-")(targetattr="-ATTRNAMEs-")(version 3.0;
            acl "-ACLNAME-"; deny(all) userdn = "ldap:///self";)' ;
$ldap->modify($dn_modif, add => {'aci' => $aci });

Comment puis-je éviter les incohérences de type de fichier et de type de données lors du chargement de données à partir d'un système Win32 ?

Lors du chargement d'un attribut binaire avec des données lues à partir d'un fichier sur un système Win32, il a été noté que vous devriez définir le mode "binmode" sur le fichier avant de lire le contenu du fichier dans le tableau de données.

Une autre solution possible à ce problème est de convertir les données binaires en une chaîne encodée en base64, puis de stocker la chaîne encodée dans le fichier. Ensuite, lors de la lecture du fichier, décodez la chaîne encodée en base64 pour revenir au binaire, puis utilisez perl-ldap pour stocker les données dans le répertoire.

Comment puis-je rechercher les comptes désactivés dans Active Directory ?

Les valeurs binaires dans "userAccountControl" nécessitent que la règle de correspondance LDAP_MATCHING_RULE_BIT_AND soit utilisée dans un terme de filtre extensible :

$mesg = $ldap->search( base   => 'cn=Users,dc=your,dc=ads,dc=domain',
                       filter => '(&(objectclass=user)' .
                                    (userAccountControl:1.2.840.113556.1.4.803:=2))',
                       attrs  => [ '1.1' ]
                     );

Avec les groupes, la même chose s'applique au champ binaire "groupType" :

$mesg = $ldap->search( base   => 'cn=Users,dc=your,dc=ads,dc=domain',
                       filter => '(&(objectclass=group)' .
                                    (groupType:1.2.840.113556.1.4.803:=2147483648))',
                                    # 2147483648 = 0x80000000
                       attrs  => [ '1.1' ]
                     );

Comment puis-je rechercher tous les membres d'un groupe dans AD (y compris l'imbrication de groupes) ?

AD vous permet de trouver tous les membres d'un groupe spécifié, les membres directs plus ceux qui sont membres du groupe via l'imbrication de groupes.

L'astuce ici est la règle de correspondance spéciale "LDAP_MATCHING_RULE_IN_CHAIN" :

$mesg = $ldap->search( base   => 'cn=Users,dc=your,dc=ads,dc=domain',
                       filter => '(memberOf:1.2.840.113556.1.4.1941:=cn=Testgroup,dc=your,dc=ads,dc=domain)',
                       attrs  => [ '1.1' ]
                     );

Comment puis-je rechercher tous les groupes dont un utilisateur est membre dans AD (y compris l'imbrication de groupes) ?

De même, vous pouvez rechercher tous les groupes dont un utilisateur est membre, que ce soit directement ou via l'imbrication de groupes.

$mesg = $ldap->search( base   => 'dc=your,dc=ads,dc=domain',
                       filter => '(member:1.2.840.113556.1.4.1941:=cn=TestUser,ou=Users,dc=your,dc=ads,dc=domain)',
                       attrs  => [ '1.1' ]
                     );

Comment puis-je rechercher tous les membres d'un grand groupe dans AD ?

AD restreint normalement le nombre de valeurs d'attributs retournées dans une seule requête. Le nombre exact dépend de la version du serveur AD : il était d'environ 1000 dans Win2000, 1500 dans Win2003 et est de 5000 dans Win2008 & Win2008R2.

L'exécution de la même recherche standard à nouveau donnera les mêmes valeurs.

Alors, comment pouvez-vous obtenir tous les membres d'un très grand groupe AD ?

L'astuce à utiliser ici est d'utiliser l'option de plage de Microsoft lors de la recherche, c'est-à-dire au lieu d'effectuer une recherche pour simplement "member", effectuez plusieurs recherches pour, par exemple, "member;range=1000-*" où l'indice de début de plage augmente en conséquence :

my $mesg;
my @members;
my $index = 0;
while ($index ne '*') {
  $mesg = $ldap->search( base   => 'cn=Testgroup,dc=your,dc=ads,dc=domain',
                         filter => '(objectclass=group)',
                         scope  => 'base',
                         attrs  => [ ($index > 0) ? "member;range=$index-*" : 'member' ]
                       );
  if ($mesg->code == LDAP_SUCCESS) {
    my $entry = $mesg->entry(0);
    my $attr;
    # grand groupe : faisons la danse de l'option de plage
    if (($attr) = grep(/^member;range=/, $entry->attributes)) {
      push(@members, $entry->get_value($attr));
      if ($attr =~ /^member;range=\d+-(.*)$/) {
        $index = $1;
        $index++  if ($index ne '*');
      }
    }
    # petit groupe : pas besoin de la danse de la plage
    else {
      @members = $entry->get_value('member');
      last;
    }
  }
  # échec
  else {
    last;
  }
}
if ($mesg->code == LDAP_SUCCESS) {
  # succès : @members contient les membres du groupe
}
else {
  # échec : gérez l'erreur dans $mesg
}

Voir http://msdn.microsoft.com/en-us/library/windows/desktop/aa367017.aspx pour plus de détails.

Comment puis-je réinitialiser le mot de passe d'un utilisateur ...

... sur la plupart des serveurs LDAP ?

La plupart des serveurs LDAP utilisent l'attribut standard userPassword comme attribut à définir lorsque vous souhaitez modifier le mot de passe d'un utilisateur.

Ils permettent généralement de définir le mot de passe soit en utilisant l'opération de modification normale sur l'attribut userPassword, soit en utilisant l'opération étendue de modification de mot de passe LDAP définie dans la RFC3062.

La méthode recommandée est l'opération étendue de modification de mot de passe, qui offre un moyen standardisé de définir les mots de passe des utilisateurs, mais n'est malheureusement pas disponible sur tous les serveurs LDAP.

La disponibilité de l'opération étendue de modification de mot de passe peut être vérifiée en recherchant l'attribut supportedExtension avec la valeur 1.3.6.1.4.1.4203.1.11.1 dans l'objet RootDSE.

Si l'opération étendue de modification de mot de passe n'est pas disponible, l'alternative est la modification régulière de l'attribut userPassword.

Mais cette méthode présente certains inconvénients :

  • Selon le type de serveur, les arguments des opérations de modification peuvent varier. Certains veulent que la modification soit effectuée avec un remplacement, d'autres veulent qu'elle soit effectuée en supprimant explicitement l'ancien mot de passe et en ajoutant le nouveau. Th

Mantén toda la estructura del archivo.

  • ¿Depende incluso May incluso de si cambias la contraseña del usuario firmado o como administrador para otro usuario?
  • Con la operación de modificar algunos servidores esperan que el cliente realice la hash de la contraseña en el cliente. Es decir, todos los clientes que establezcan contraseñas deben acordar el algoritmo y el formato de la contraseña hash.
  • Algunos servidores LDAP no permiten establecer la contraseña si la conexión no es suficientemente segura. Es decir, requieren soporte SSL o TLS para establecer la contraseña (lo cual es altamente recomendado, sin embargo).

Aquí se muestra un ejemplo de cómo cambiar tu propia contraseña (para brevete error checking se deja fuera):

use Net::LDAP;
my $ldap = Net::LDAP->new('ldaps://server.domain')  or  die "$@";
my $mesg = $ldap->bind('cn=Joe User,dc=perl,dc=ldap,dc=org',
                       password => 'oldPW');
my $rootdse = $ldap->root_dse();
if ($rootdse->supported_extension('1.3.6.1.4.1.4203.1.11.1')) {
    require Net::LDAP::Extension::SetPassword;
    $mesg = $ldap->set_password(user => 'cn=Joe User,dc=perl,dc=ldap,dc=org',
                                oldpasswd => 'oldPW',
                                newpasswd => 'newPW');
}
else {
    $mesg = $ldap->modify('cn=Joe User,dc=perl,dc=ldap,dc=org',
                          changes => [
                              delete => [ userPassword => $oldPW ]
                              add    => [ userPassword => $newPW ] ]);
}
$ldap->unbind();

... en MS Active Directory?

Con Active Directory la contraseña de un usuario se almacena en la atributo unicodePwd y se cambia mediante la operación de modificar estándar.

ADS espera que esta contraseña esté codificada en Unicode - UTF-16 exacta. Antes de la conversión de Unicode, la contraseña debe estar rodeada por comillas dobles que no pertenecen al password del usuario.

Para que la operación de modificar de contraseña sea exitosa, se requiere SSL.

Cuando se cambia la contraseña del usuario firmado en el directorio ADS, espera que se la realice eliminando la antigua y añadiendo la nueva. Cuando se la realiza como un usuario con privilegios de administrador, también se permite reemplazar el valor de unicodePwd con una nueva.

El perl-ldap contiene métodos de utilidad para Active Directory que permiten realizar este tipo de tareas de forma muy fácil.

Aquí está un ejemplo que demuestra cómo establecer tu propia contraseña desde $oldPW a $newPW (de nuevo, prácticamente sin chequeo de errores):

use Net::LDAP;
use Net::LDAP::Extra qw(AD);
my $ldap = Net::LDAP->new('ldaps://ads.domain.controller')  or  die "$@";
my $mesg = $ldap->bind('cn=Joe User,dc=your,dc=ads,dc=domain',
                       password => $oldPW);
$mesg = $ldap->change_ADpassword('cn=Joe User,dc=your,dc=ads,dc=domain',
                                 $oldPW, $newPW);
$ldap->unbind();

Y el mismo para perl-ldap versiones antes de 0.49, donde todo tiene que hacerse a mano:

use Net::LDAP;
use Unicode::Map8;
use Unicode::String qw(utf16);
# construir el mapa de conversión desde tu conjunto de caracteres local a Unicode
my $charmap = Unicode::Map8->new('latin1')  or die;
# rodear la contraseña con comillas dobles y convertirla a UTF-16
# byteswap() fue necesario en experimentos en i386 Linux, YMMV
my $oldUniPW = $charmap->tou('"'.$oldPW.'"')->byteswap()->utf16();
my $newUniPW = $charmap->tou('"'.$newPW.'"')->byteswap()->utf16();
my $ldap = Net::LDAP->new('ldaps://ads.domain.controller')  or  die "$@";
my $mesg = $ldap->bind('cn=Joe User,dc=your,dc=ads,dc=domain',
                       password => $oldPW);
$mesg = $ldap->modify('cn=Joe User,dc=your,dc=ads,dc=domain',
                      changes => [
                          delete => [ unicodePwd => $oldUniPW ]
                          add    => [ unicodePwd => $newUniPW ] ]);
$ldap->unbind();

Comment puis-je simuler la défaillance d'un serveur ?

Perl-ldap ne gère pas le basculement des serveurs, mais plusieurs options de programmation existent pour contourner cette situation.

Voici une solution possible :

$ldaps = Net::LDAPS->new([ $ldapserverone, $ldapservertwo ],
                         port=>636, timeout=>5)  or  die "$@";

Pour les versions de perl-ldap antérieures à 0.27, le même objectif peut être atteint en utilisant :

unless ( $ldaps =
          Net::LDAPS->new($ldapserverone,
                          port=>636,timeout=>5) )
        {
            $ldaps = Net::LDAPS->new($ldapservertwo,
                                     port=>636,timeout=>20) ||
            return
            "Can't connect to $ldapserverone or $ldapservertwo via LDAPS: $@";
        }

Utilisation des certificats X.509.

Comment stocker les certificats X.509 dans l'annuaire ?

La première question est qu'il existe de nombreuses façons différentes de stocker les certificats, par exemple PEM, DER, PKCS#7 et PKCS#12. L'annuaire utilise uniquement le format DER (plus précisément, il utilise uniquement le format BER). C'est un format binaire.

Votre premier travail consiste à vous assurer que vos certificats sont au format DER/BER. Vous pouvez utiliser OpenSSL pour convertir du PEM comme suit :

openssl x509 -inform PEM -in cert.pem -outform DER -out cert.der

Consultez la documentation d'OpenSSL pour savoir comment effectuer d'autres conversions.

Pour ajouter un certificat à l'annuaire, il suffit d'introduire le certificat DER/BER dans une variable scalaire et de l'ajouter à l'attribut userCertificate de l'enregistrement. La méthode pour le faire dépendra de la version de LDAP que vous utilisez.

Pour introduire le certificat, essayez quelque chose comme ceci :

my $cert;
{
    local $/ = undef; # Mode de lecture
    open CERT, "cert.der" or die;
    binmode CERT;     # pour Windows etc.
    $cert = <CERT>;
    close CERT;
}
# Le certificat est maintenant dans $cert

Pour LDAPv2, étant donné que la plupart des fournisseurs d'annuaires ignorent la représentation des certificats définie dans la RFC 1778, vous devez ajouter cette valeur à l'annuaire comme suit :

$res = $ldap->modify("cn=My User, o=My Company,c=XY",
                     add => [
                             'userCertificate' => [ $cert ]
                            ]);
die "Modify failed (" . ldap_error_name($res->code) . ")\n"
    if $res->code;

Pour LDAPv3, vous devez le faire comme suit :

$res = $ldap->modify("cn=My User, o=My Company, c=XY",
                     add => [
                             'userCertificate;binary' => [ $cert ]
                            ]);
die "Modify failed (" . ldap_error_name($res->code) . ")\n"
    if $res->code;

Naturellement, l'enregistrement auquel vous essayez d'ajouter le certificat doit utiliser des classes d'objets qui autorisent l'attribut userCertificate, sinon la modification échouera avec une erreur de violation de classe d'objet. La classe d'objet inetOrgPerson autorise l'attribut userCertificate, ainsi que la classe d'objet auxiliaire strongAuthenticationUser. D'autres peuvent également le faire.

Comment rechercher des objets par le contenu des certificats ?

L'annuaire doit prendre en charge une ou plusieurs des règles de correspondance de certificats *Match.

Après avoir utilisé le filtre (dans le cas de certificatExactMatch)

(userCertificate={ serialNumber 1234, issuer "cn=CA,o=TrustCenter" })

permet de rechercher les objets qui contiennent l'attribut userCertificate avec un certificat correspondant à ces critères.

Veuillez noter que la syntaxe exacte des valeurs pour serialNumber et issuer peut dépendre du serveur LDAP. Dans tous les cas, l'exemple ci-dessus fonctionne avec OpenLDAP 2.4.33.
