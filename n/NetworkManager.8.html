NETWORKMANAGER(8) Démons de gestion réseau NETWORKMANAGER(8)

NOM

NetworkManager - démon de gestion du réseau

SYNOPIS

NetworkManager [OPTIONS...]

DESCRIPTION

Le démon NetworkManager tente de rendre la configuration et le fonctionnement du réseau aussi simples et automatiques que possible en gérant la connexion réseau principale et les autres interfaces réseau, telles que les périphériques Ethernet, Wi-Fi et haut débit mobile. NetworkManager connectera tout périphérique réseau lorsqu'une connexion pour ce périphérique deviendra disponible, à moins que ce comportement ne soit désactivé. Les informations sur le réseau sont exportées via une interface D-Bus à toute application intéressée, fournissant une API riche avec laquelle inspecter et contrôler les paramètres et le fonctionnement du réseau.

SCRIPTS DE DISPATCHER

Le service NetworkManager-dispatcher peut exécuter des scripts pour l'utilisateur en réponse à des événements réseau. Voir le manuel NetworkManager-dispatcher(8).

OPTIONS

Les options suivantes sont comprises :

--version | -V

Affiche la version du logiciel NetworkManager et quitte.

--help | -h

Affiche les options disponibles de NetworkManager et quitte.

--no-daemon | -n

Ne pas daemoniser.

--debug | -d

Ne pas daemoniser, et diriger la sortie des logs vers le terminal de contrôle en plus de syslog.

--pid-file | -p

Spécifie l'emplacement d'un fichier PID. Le fichier PID est utilisé pour stocker le PID du processus en cours et empêche l'exécution de plusieurs instances.

--state-file

Spécifie le fichier pour stocker l'état de NetworkManager de manière persistante. Si non spécifié, la valeur par défaut de /var/lib/NetworkManager/NetworkManager.state est utilisée.

--config

Spécifie le fichier de configuration pour configurer divers paramètres pour NetworkManager. Si non spécifié, la valeur par défaut de /etc/NetworkManager/NetworkManager.conf est utilisée avec un fallback vers l'ancien 'nm-system-settings.conf' s'il est situé dans le même répertoire. Voir NetworkManager.conf(5) pour plus d'informations sur le fichier de configuration.

--configure-and-quit [initrd]

Quitte après que tous les périphériques aient atteint un état stable. Le paramètre facultatif initrd active un mode où aucun processus n'est laissé en cours d'exécution après l'arrêt de NetworkManager, ce qui est utile pour s'exécuter à partir d'un disque RAM initial au démarrage.

--plugins

Liste les plugins utilisés pour gérer les paramètres de connexion à l'échelle du système. Cette liste a la préférence sur les plugins spécifiés dans le fichier de configuration. Voir le réglage main.plugins dans NetworkManager.conf(5) pour les options prises en charge.

--log-level

Définit la quantité d'informations que NetworkManager envoie à la destination des logs (généralement la facilité "daemon" de syslog). Par défaut, seuls les messages d'information, d'avertissement et d'erreur sont enregistrés. Voir la section sur la journalisation dans NetworkManager.conf(5) pour plus d'informations.

--log-domains

Une liste séparée par des virgules spécifiant quelles opérations sont enregistrées dans la destination des logs (généralement syslog). Par défaut, la plupart des domaines sont activés pour la journalisation. Voir la section sur la journalisation dans NetworkManager.conf(5) pour plus d'informations.

--print-config

Affiche la configuration de NetworkManager sur la sortie standard et quitte. Voir NetworkManager.conf(5). Ceci n'inclut pas les profils de connexion. Visualisez-les avec nmcli connection.

Ceci lit les fichiers de configuration depuis le disque. Si NetworkManager est actuellement en cours d'exécution, assurez-vous qu'il a la même configuration chargée.

PROPRIETES UDEV

Le gestionnaire de périphériques udev(7) est utilisé pour la découverte des périphériques réseau. La propriété suivante influence la manière dont NetworkManager gère les périphériques :

NM_UNMANAGED

Si défini sur "1" ou "true", le périphérique est configuré comme non géré par NetworkManager. Notez que l'utilisateur peut toujours outrepasser explicitement cette configuration par des moyens tels que nmcli device set "$DEVICE" managed yes ou "device*.managed=1" dans NetworkManager.conf.

ID_NET_MANAGED_BY

Si NM_UNMANAGED est défini, cela n'a aucun effet. Sinon, si l'attribut est défini sur autre chose que "org.freedesktop.NetworkManager", le périphérique est non géré.

NM_AUTO_DEFAULT_LINK_LOCAL_ONLY

Si défini sur "1" ou "true", les connexions générées automatiquement "Connexion filaire N" n'activeront que l'adressage local de liaison pour IPv4 et IPv6. Cela peut être utile sur les périphériques Thunderbolt ou les périphériques USB point à point.

ID_NET_AUTO_LINK_LOCAL_ONLY

Respecté et traité de la même manière que si NM_AUTO_DEFAULT_LINK_LOCAL_ONLY était défini.

ID_NET_DHCP_BROADCAST

Si défini sur "1" ou "true", utilisez des requêtes de diffusion pour les offres DHCPv4. Cela peut avoir du sens pour les périphériques qui ne peuvent pas gérer les messages unicast avant d'être configurés.

SIGNALS

Le processus NetworkManager gère les signaux suivants :

SIGHUP

Le signal provoque le rechargement de la configuration de NetworkManager. Notez que tous les paramètres de configuration ne peuvent pas être modifiés à la volée et que certains changements ne seront appliqués qu'après le prochain redémarrage du démon. Un SIGHUP implique également des actions de rechargement supplémentaires, comme une mise à jour DNS et le redémarrage du plugin DNS. Ce dernier peut être utile par exemple lors de l'utilisation du plugin dnsmasq et de la modification de sa configuration dans /etc/NetworkManager/dnsmasq.d. Cependant, cela signifie également une interruption de la résolution de noms. À l'avenir, d'autres actions pourraient être ajoutées. Un SIGHUP signifie mettre à jour la configuration de NetworkManager et recharger tout ce qui est pris en charge. Notez que cela ne recharge pas les connexions depuis le disque. Pour cela, il existe une API D-Bus et l'action reload de nmcli.

SIGUSR1

Le signal force la réécriture de la configuration DNS. Contrairement à SIGHUP, cela ne redémarre pas le plugin DNS et n'interrompra pas la résolution de noms. Lorsque NetworkManager ne gère pas le DNS, le signal force un redémarrage des opérations qui dépendent de la configuration DNS (comme la résolution du nom d'hôte système via DNS inversé, ou la résolution des pairs WireGuard) ; par conséquent, il peut être utilisé pour indiquer à NetworkManager que le contenu de resolv.conf a été modifié extérieurement. À l'avenir, d'autres actions pourraient être ajoutées. Un SIGUSR1 signifie écrire des données telles que resolv.conf, ou rafraîchir un cache. C'est un sous-ensemble de ce qui est fait pour SIGHUP sans recharger la configuration depuis le disque.

SIGUSR2

Le signal n'a actuellement aucun effet mais est réservé pour une utilisation future.

Une alternative à un signal pour recharger la configuration est l'appel D-Bus Reload. Il permet une sélection plus granulaire de ce qu'il faut recharger, il ne retourne qu'une fois le rechargement terminé, et il est protégé par PolicyKit.

DEPANNAGE

NetworkManager configure uniquement votre système. Donc, lorsque votre configuration réseau ne fonctionne pas comme prévu, la première étape consiste à examiner votre système pour comprendre ce qui est réellement configuré et si c'est correct. La deuxième étape consiste à déterminer comment dire à NetworkManager de faire la bonne chose.

Vous pouvez par exemple essayer de ping des hôtes (par adresse IP ou nom DNS), regarder ip link show, ip address show et ip route show, et regarder /etc/resolv.conf pour les problèmes de résolution de noms. Regardez également les profils de connexion que vous avez configurés dans NetworkManager (nmcli connection et nmcli connection show "$PROFILE") et les interfaces configurées (nmcli device).

Si cela ne suffit pas, examinez les fichiers journaux de NetworkManager. NetworkManager journalise vers syslog, donc en fonction de la configuration de votre système, vous pouvez appeler journalctl pour obtenir les journaux. /VAR/LIB/NETWORKMANAGER/SECRET_KEY ET /ETC/MACHINE-ID

L'identité d'une machine est importante car divers paramètres en dépendent. Par exemple, ipv6.addr-gen-mode=stable et ethernet.cloned-mac-address=stable génèrent des identifiants en hachant l'identité de la machine. Voir aussi la propriété de connexion connection.stable-id, qui est une graine par profil qui est hachée avec l'identité de la machine pour générer ces adresses et identifiants.

Si vous copiez et restaurez une machine, vous devriez probablement préserver l'identité de la machine. Dans ce cas, préservez les fichiers /var/lib/NetworkManager/secret_key et /etc/machine-id. D'autre part, si vous clonez une machine virtuelle, vous voudrez probablement que le clone ait une identité différente. Il existe déjà des outils sous Linux pour gérer /etc/machine-id (voir machine-id(5)).

L'identité de la machine est déterminée par /var/lib/NetworkManager/secret_key. Si ce fichier n'existe pas, NetworkManager créera un fichier avec un contenu aléatoire. Pour générer une nouvelle identité, il suffit de supprimer le fichier et après le redémarrage, un nouveau fichier sera créé. Le fichier doit être en lecture seule pour root et doit contenir au moins 16 octets qui seront utilisés pour semer les divers endroits où des identifiants stables sont utilisés.

À partir de 1.16.0, NetworkManager prend en charge une clé secrète version 2. Pour une telle clé, /var/lib/NetworkManager/secret_key commence par "nm-v2:" en ASCII suivi d'au moins 32 octets de données aléatoires. De plus, les versions récentes de NetworkManager créent toujours de telles clés secrètes lorsque le fichier n'existe pas encore. Avec la clé secrète version 2, /etc/machine-id est également haché dans le cadre de la génération d'adresses et d'identifiants. L'avantage est que vous pouvez maintenir /var/lib/NetworkManager/secret_key stable, et ne devez générer /etc/machine-id que lorsque vous clonez une VM.
