NEXT(3perl) Guide de référence du programmeur Perl NEXT(3perl)

NOM

NEXT - Fournit une classe pseudo NEXT (et autres) permettant le ré-dispatch de méthodes

SYNOPIS

use NEXT;
package P;
sub P::method   { print "$_[0]: P method\n";   $_[0]->NEXT::method() }
sub P::DESTROY  { print "$_[0]: P dtor\n";     $_[0]->NEXT::DESTROY() }
package Q;
use base qw( P );
sub Q::AUTOLOAD { print "$_[0]: Q AUTOLOAD\n"; $_[0]->NEXT::AUTOLOAD() }
sub Q::DESTROY  { print "$_[0]: Q dtor\n";     $_[0]->NEXT::DESTROY() }
package R;
sub R::method   { print "$_[0]: R method\n";   $_[0]->NEXT::method() }
sub R::AUTOLOAD { print "$_[0]: R AUTOLOAD\n"; $_[0]->NEXT::AUTOLOAD() }
sub R::DESTROY  { print "$_[0]: R dtor\n";     $_[0]->NEXT::DESTROY() }
package S;
use base qw( Q R );
sub S::method   { print "$_[0]: S method\n";   $_[0]->NEXT::method() }
sub S::AUTOLOAD { print "$_[0]: S AUTOLOAD\n"; $_[0]->NEXT::AUTOLOAD() }
sub S::DESTROY  { print "$_[0]: S dtor\n";     $_[0]->NEXT::DESTROY() }
package main;
my $obj = bless {}, "S";
$obj->method();             # Appelle S::method, P::method, R::method
$obj->missing_method(); # Appelle S::AUTOLOAD, Q::AUTOLOAD, R::AUTOLOAD
# Nettoyage : Appelle S::DESTROY, Q::DESTROY, P::DESTROY, R::DESTROY

DESCRIPTION

Le module "NEXT" ajoute une classe pseudo nommée "NEXT" à tout programme qui l'utilise. Si une méthode "m" appelle "$self->NEXT::m()", l'appel à "m" est redispatché comme si la méthode appelante n'avait pas été trouvée à l'origine.

Note : Avant d'utiliser ce module, veuillez consulter "next::method" dans le module core "mro" (voir https://metacpan.org/pod/mro#next::method). "mro" est un module core depuis Perl 5.9.5.

Autrement dit, un appel à "$self->NEXT::m()" reprend la recherche de méthodes dans la hiérarchie de classes de $self, qui a commencé avec l'appel original à "m".

Notez que ce n'est pas la même chose que "$self->SUPER::m()", qui commence une nouvelle recherche limitée aux frères et sœurs de la classe actuelle. "$self->NEXT::m()" peut remonter dans la classe actuelle pour trouver une méthode appropriée chez d'autres frères et sœurs de la classe $self, tandis que "$self->SUPER::m()" ne le peut pas.

Une utilisation typique serait dans le destructeur d'une hiérarchie de classes, comme montré dans l'exemple de SYNOPIS. Chaque classe de la hiérarchie a une méthode DESTROY qui effectue une action spécifique à la classe, puis redispatche l'appel vers le haut de la hiérarchie. En conséquence, lors de la destruction d'un objet de classe S, les destructeurs de toutes ses classes parentes sont appelés (dans un ordre de profondeur, gauche).

Une autre utilisation typique du redispatch serait dans les méthodes "AUTOLOAD". Si une méthode "AUTOLOAD" détermine qu'elle ne peut pas gérer un appel spécifique, elle pourrait tenter de redispatche cet appel, en espérant qu'une autre "AUTOLOAD" (plus haut ou à gauche) s'en sortira mieux.

Par défaut, si une tentative de redispatch ne trouve pas d'autre méthode dans la hiérarchie de l'objet, elle se tait et ne fait rien (mais voir "Exiger le redispatch"). Cette grâce de laisser passer est également différente du comportement (généralement agaçant) de "SUPER", qui lève une exception si elle ne peut pas redispatcher.

Notez qu'il est fatal pour toute méthode (y compris "AUTOLOAD") de tenter de redispatcher une méthode qui n'a pas le même nom. Par exemple:

sub S::oops { print "oops!\n"; $_[0]->NEXT::other_method() }

Exiger le redispatch

Il est possible de rendre le redispatch "NEXT" plus exigeant (c'est-à-dire, comme "SUPER"), de telle sorte que le redispatch lève une exception s'il ne trouve pas de méthode "next" appropriée à appeler.

Pour ce faire, invoquez simplement le redispatch comme suit :

$self->NEXT::ACTUAL::method();

au lieu de :

$self->NEXT::method();

Le "ACTUAL" indique à "NEXT" qu'il doit y avoir une méthode "next" réelle à appeler, sinon une exception sera levée.

"NEXT::ACTUAL" est plus couramment utilisé dans les méthodes "AUTOLOAD" comme un moyen de rejeter une requête "AUTOLOAD", tout en conservant le comportement normal d'exception en cas d'échec :

sub AUTOLOAD {
        if ($AUTOLOAD =~ /foo|bar/) {
                # gérer ici
        }
        else {  # essayer ailleurs
                shift()->NEXT::ACTUAL::AUTOLOAD(@_);
        }
}

En utilisant "NEXT::ACTUAL", s'il n'y a pas d'autre "AUTOLOAD" pour gérer l'appel, une exception sera levée (comme cela se produit généralement sans "AUTOLOAD" approprié).

Éviter les répétitions

Si le redispatch "NEXT" est utilisé dans les méthodes d'une hiérarchie en "diamant" :

#     A   B
#    / \ /
#   C   D
#    \ /
#     E
use NEXT;
package A;                 
sub foo { print "appelé A::foo\n"; shift->NEXT::foo() }
package B;                 
sub foo { print "appelé B::foo\n"; shift->NEXT::foo() }
package C; @ISA = qw( A );
sub foo { print "appelé C::foo\n"; shift->NEXT::foo() }
package D; @ISA = qw(A B);
sub foo { print "appelé D::foo\n"; shift->NEXT::foo() }
package E; @ISA = qw(C D);
sub foo { print "appelé E::foo\n"; shift->NEXT::foo() }
E->foo();

alors les méthodes dérivées peuvent (re)hériter des méthodes des classes parentes par deux chemins distincts ou plus (par exemple, de la manière dont "E" hérite de "A::foo" deux fois — via "C" et "D"). Dans de tels cas, une séquence de redispatches "NEXT" appellera la méthode héritée plusieurs fois autant de fois qu'elle est héritée. Par exemple, le code ci-dessus imprime :

appelé E::foo
appelé C::foo
appelé A::foo
appelé D::foo
appelé A::foo
appelé B::foo

(c'est-à-dire que "A::foo" est appelé deux fois).

Dans certains cas, cela peut être l'effet désiré dans une hiérarchie en diamant, mais dans d'autres (par exemple, pour les destructeurs), il pourrait être plus approprié d'appeler chaque méthode une seule fois lors d'une séquence de redispatches.

Pour couvrir de tels cas, vous pouvez redispatcher les méthodes en utilisant :

$self->NEXT::DISTINCT::method();

au lieu de :

$self->NEXT::method();

cela fait en sorte que le redispatch ne visite chaque méthode distincte qu'une seule fois. C'est-à-dire, il saute toute classe dans la hiérarchie qui a déjà été visitée lors du redispatch. Ainsi, par exemple, si l'exemple ci-dessus était réécrit :

package A;                 
sub foo { print "appelé A::foo\n"; shift->NEXT::DISTINCT::foo() }
package B;                 
sub foo { print "appelé B::foo\n"; shift->NEXT::DISTINCT::foo() }
package C; @ISA = qw( A );
sub foo { print "appelé C::foo\n"; shift->NEXT::DISTINCT::foo() }
package D; @ISA = qw(A B);
sub foo { print "appelé D::foo\n"; shift->NEXT::DISTINCT::foo() }
package E; @ISA = qw(C D);
sub foo { print "appelé E::foo\n"; shift->NEXT::DISTINCT::foo() }
E->foo();

alors il imprimerait :

appelé E::foo
appelé C::foo
appelé A::foo
appelé D::foo
appelé B::foo

et sauterait le deuxième appel à "A::foo" (car il ne serait pas distinct du premier appel à "A::foo").

Notez que vous pouvez également utiliser :

$self->NEXT::DISTINCT::ACTUAL::method();

ou :

$self->NEXT::ACTUAL::DISTINCT::method();

pour obtenir à la fois l'invocation unique et l'exception en cas d'échec.

Notez que, pour des raisons de compatibilité historique, vous pouvez également utiliser "NEXT::UNSEEN" au lieu de "NEXT::DISTINCT".

EXEMPLE

L'exemple suivant illustre le fonctionnement du redispatch :

use NEXT;
package A;
sub foo { print "appelé A::foo\n"; shift->NEXT::foo() }
package B;
sub foo { print "appelé B::foo\n"; shift->NEXT::foo() }
package C;
sub foo { print "appelé C::foo\n"; shift->NEXT::foo() }
package D;
sub foo { print "appelé D::foo\n"; shift->NEXT::foo() }
package E;
sub foo { print "appelé E::foo\n"; shift->NEXT::foo() }
E->foo();

NAME

NEXT - Pseudo-classes for invoking methods via inheritance

SYNOPSIS

    use NEXT;
    $obj->NEXT::method(@args);
    $obj->EVERY::method(@args);
    $obj->EVERY::LAST::method(@args);

DESCRIPTION

The "NEXT" module provides a pair of pseudo-classes, "NEXT" and "EVERY", that allow you to invoke methods via inheritance in ways that go beyond the standard Perl mechanism.

Standard Perl method calls resolve to a single method, selected from the class hierarchy using a depth-first, left-to-right search. Once that method is found and invoked, the search stops. This is usually what you want, but sometimes you may want to invoke a method from a specific superclass (or superclasses), or you may want to invoke *every* method of a given name in the entire class hierarchy.

The "NEXT" pseudo-class allows you to do just that. A call of the form:

$obj->NEXT::Some::Class::method(@args);

invokes the method named "method" in the specific superclass "Some::Class" of the object in $obj. If "Some::Class" is not a direct superclass of $obj's class, "NEXT" will search up the inheritance hierarchy until it finds the first class that is a superclass of "Some::Class" and has a method named "method", and invokes that method.

If "Some::Class" is omitted:

$obj->NEXT::method(@args);

then "NEXT" invokes the method that would normally be called *next* in the method resolution order after the current method.

This is particularly useful for implementing extensible methods, such as:

package Base;
sub do_something {
    print "Base doing something\n";
    my $self->NEXT::do_something(@_); # Call next method in hierarchy
}
package Derived;
use base 'Base';
sub do_something {
    print "Derived doing something\n";
    $_[0]->SUPER::do_something(@_); # Call the superclass method
}
package MoreDerived;
use base 'Derived';
sub do_something {
    print "MoreDerived doing something\n";
    $_[0]->NEXT::do_something(@_); # Call next method (Derived::do_something)
}

Note that when implementing an extensible method, you must choose between using "NEXT::method" and "SUPER::method". Using "NEXT::method" has the effect of chaining *all* methods with that name in the hierarchy, whereas "SUPER::method" calls only the immediate superclass's method (if one exists). Consequently, you will typically only use "NEXT::method" when implementing the base class method, and "SUPER::method" when implementing a derived class method.

The "NEXT" pseudo-class works by temporarily modifying the class hierarchy seen by the standard Perl method lookup mechanism. This is achieved by manipulating the @ISA arrays of the relevant classes at runtime. It is therefore essential that the "use NEXT;" statement appears *before* any method calls that rely on its functionality.

Yet another pseudo-class that "NEXT" provides is "EVERY". Its behaviour is considerably simpler than that of the "NEXT" family. A call to:

$obj->EVERY::foo();

calls every method named "foo" that the object in $obj has inherited. That is:

use NEXT;
package A; @ISA = qw(B D X);
sub foo { print "A::foo " }
package B; @ISA = qw(D X);
sub foo { print "B::foo " }
package X; @ISA = qw(D);
sub foo { print "X::foo " }
package D;
sub foo { print "D::foo " }
package main;
my $obj = bless {}, 'A';
$obj->EVERY::foo();        # prints" A::foo B::foo X::foo D::foo

Prefixing a method call with "EVERY::" causes every method in the object's hierarchy with that name to be invoked. As the above example illustrates, they are not called in Perl's usual "left-most-depth-first" order. Instead, they are called "breadth-first-dependency-wise".

That means that the inheritance tree of the object is traversed breadth-first and the resulting order of classes is used as the sequence in which methods are called. However, that sequence is modified by imposing a rule that the appropriate method of a derived class must be called before the same method of any ancestral class. That's why, in the above example, "X::foo" is called before "D::foo", even though "D" comes before "X" in @B::ISA.

In general, there's no need to worry about the order of calls. They will be left-to-right, breadth-first, most-derived-first. This works perfectly for most inherited methods (including destructors), but is inappropriate for some kinds of methods (such as constructors, cloners, debuggers, and initializers) where it's more appropriate that the least-derived methods be called first (as more-derived methods may rely on the behaviour of their "ancestors"). In that case, instead of using the "EVERY" pseudo-class:

$obj->EVERY::foo();        # prints" A::foo B::foo X::foo D::foo

you can use the "EVERY::LAST" pseudo-class:

$obj->EVERY::LAST::foo();  # prints" D::foo X::foo B::foo A::foo

which reverses the order of method call.

Whichever version is used, the actual methods are called in the same context (list, scalar, or void) as the original call via "EVERY", and return:

  • A hash of array references in list context. Each entry of the hash has the fully qualified method name as its key and a reference to an array containing the method's list-context return values as its value.
  • A reference to a hash of scalar values in scalar context. Each entry of the hash has the fully qualified method name as its key and the method's scalar-context return values as its value.
  • Nothing in void context (obviously).

Using "EVERY" methods

The typical way to use an "EVERY" call is to wrap it in another base method, that all classes inherit. For example, to ensure that every destructor an object inherits is actually called (as opposed to just the left-most-depth-first-est one):

package Base;
sub DESTROY { $_[0]->EVERY::Destroy }
package Derived1; 
use base 'Base';
sub Destroy {...}
package Derived2; 
use base 'Base', 'Derived1';
sub Destroy {...}

et cetera. Every derived class than needs its own clean-up behaviour simply adds its own "Destroy" method (not a "DESTROY" method), which the call to "EVERY::LAST::Destroy" in the inherited destructor then correctly picks up.

Likewise, to create a class hierarchy in which every initializer inherited by a new object is invoked:

package Base;
sub new {
        my ($class, %args) = @_;
        my $obj = bless {}, $class;
        $obj->EVERY::LAST::Init(\%args);
}
package Derived1; 
use base 'Base';
sub Init {
        my ($argsref) = @_;
        ...
}
package Derived2; 
use base 'Base', 'Derived1';
sub Init {
        my ($argsref) = @_;
        ...
}

et cetera. Every derived class than needs some additional initialization behaviour simply adds its own "Init" method (not a "new" method), which the call to "EVERY::LAST::Init" in the inherited constructor then correctly picks up.

BUGS AND IRRITATIONS

Because it's a module, not an integral part of the interpreter, "NEXT" has to guess where the surrounding call was found in the method look-up sequence. In the presence of diamond inheritance patterns it occasionally guesses wrong.

It's also too slow (despite caching).
