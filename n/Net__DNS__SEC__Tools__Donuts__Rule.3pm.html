Net::DNS::SEC::Tools::Donuts::Rule(3) Documentation Perl fournie par l'utilisateur Net::DNS::SEC::Tools::Donuts::Rule(3)

NOM

Net::DNS::SEC::Tools::Donuts::Rule - Définir des règles de vérification d'enregistrements DNS pour donuts

DESCRIPTION

Cette classe enveloppe une définition de règle qui est utilisée par l'outil de vérification de fichiers de zone DNS donuts. Elle stocke les données qui implémentent une règle donnée.

Les règles sont définies dans les fichiers de configuration de règles de donuts en utilisant la syntaxe suivante. Voir la page de manuel de donuts pour savoir où placer ces fichiers et comment les charger.

FORMAT DE FICHIER DE RÈGLES

Chaque fichier de règles peut contenir plusieurs règles. Chaque règle est composée d'un certain nombre de parties. Au minimum, elle doit contenir une section nom et une section test. Tout le reste est facultatif et/ou a des valeurs par défaut associées. Le format du fichier de règles suit cet exemple :

nom: nom_de_la_regle
classe: Avertissement
<test>
  my ($enregistrement) = @_;
  return "problème trouvé"
    if ($enregistrement{xxx} != yyy);
</test>

Des détails supplémentaires sur chaque section peuvent être trouvés ci-dessous. Outre les jetons ci-dessous, d'autres données spécifiques aux règles peuvent être stockées dans des jetons, et chaque règle est une table hash des jetons ci-dessus comme clés et leurs données associées. Cependant, il y a quelques exceptions où des jetons spéciaux impliquent des significations spéciales. Ces jetons spéciaux incluent test et init. Voir ci-dessous pour les détails.

Chaque définition de règle dans un fichier doit être séparée par une ligne vide.

Les lignes commençant par le caractère '#' seront ignorées en tant que commentaire.

nom
Le nom de la règle. Ceci est obligatoire, car l'utilisateur peut avoir besoin de faire référence à des noms à l'avenir pour une utilisation avec le flag -i, spécifiant le comportement dans les fichiers de configuration, et pour d'autres usages.

Par convention, tous les noms doivent être spécifiés en utilisant des lettres majuscules et des caractères '_' entre les mots. Le mot le plus à gauche doit donner une indication d'une catégorie de test globale, comme "DNSSEC". Plus les règles sont nommées, plus l'utilisateur aura de pouvoir pour sélectionner certains types de règles via donuts -i et d'autres flags.

Exemple :

nom: TEST_DNSSEC_FONCTIONNALITE_SÉCURISÉE
niveau
Le niveau d'exécution de la règle, tel que reconnu par donuts. donuts n'exécutera que les règles à un niveau égal ou supérieur au niveau d'exécution actuel de donuts. Le niveau d'exécution est spécifié par l'option -l de donuts ; si elle n'est pas donnée, le niveau d'exécution par défaut est 5.

Le niveau par défaut de chaque règle est 5.

En général, les problèmes plus graves devraient recevoir des nombres plus bas et les problèmes moins graves devraient être placés à un nombre plus élevé. La valeur maximale est 9, qui est réservée aux règles de débogage uniquement. 8 est le niveau maximum de règle que les règles définies par l'utilisateur devraient utiliser.

Exemple :

nom: TEST_DNSSEC_FONCTIONNALITE_SÉCURISÉE
niveau: 2
classe
Le code classe indique le type de problème associé à la règle. Il par défaut à "Erreur", et la seule autre valeur qui devrait être utilisée est "Avertissement".

Cette valeur est affichée à l'utilisateur. Techniquement, toute valeur pourrait être spécifiée, mais l'utilisation de quelque chose d'autre que la convention Erreur/Avertissement pourrait casser la portabilité dans les versions futures.

Exemple :
nom: TEST_DNSSEC_FONCTIONNALITE_SÉCURISÉE
classe: Avertissement

type-de-regle
Les règles tombent dans l'un des deux types (actuellement) : enregistrement ou nom. Les règles enregistrement ont leur section de test évaluée pour chaque enregistrement dans un fichier de zone. Les règles nom, quant à elles, sont appelées une fois par nom d'enregistrement stocké dans la base de données. Voir la description de test ci-dessous pour plus de détails sur les arguments passés à chaque type de règle.

La valeur par défaut pour cette clause est enregistrement.

Exemple :

nom: TEST_DNSSEC_FONCTIONNALITE_SÉCURISÉE
type-de-regle: enregistrement
type
Les règles qui testent un type particulier d'enregistrement devraient spécifier le champ type avec le type d'enregistrement qu'elles testeront. La règle ne sera exécutée que pour les enregistrements de ce type.

Par exemple, si une règle teste un aspect particulier d'un enregistrement MX, elle devrait spécifier "MX" dans ce champ.

Exemple :

nom: TEST_DNSSEC_FONCTIONNALITE_SÉCURISÉE
type: MX
init
Un bloc de code à exécuter immédiatement lors de l'analyse de la règle à partir du fichier de définition de la règle. Ceci est utile pour le code d'amorçage à effectuer uniquement au démarrage. Par exemple, des instructions perl telles que "use MODULE::NAME;" ou similaires devraient être utilisées dans les sections init.

Les sections init sont enveloppées dans une syntaxe de type XML qui spécifie le début et la fin de la section de code init.

Exemple :

<init>
  use Mon::Module;
  $valeur = calculer();
</init>
test
Un bloc de code définissant le test à exécuter pour chaque enregistrement ou nom d'enregistrement. L'instruction de test suit la même spécification de code multiligne décrite dans la clause init ci-dessus. Plus précisément, toutes les lignes entre les accolades <test> et </test> sont considérées comme faisant partie du code de test.

Le contenu du test doit être un bloc de code perl. S'il n'est pas sous la forme d'une sous-routine anonyme (entourée des marqueurs "sub {" et "}"), le code sera automatiquement placé dans un bloc de sous-routine de base pour en faire une sous-routine anonyme.

PAR EXEMPLE, le code résultant pour un test de type enregistrement ressemblera à ceci :

package main;
no strict;
sub
{
  my ($enregistrement, $regle) = @_;
  CODE_TEST
}

Et pour un test de type nom :

package main;
no strict;
sub
{
  my ($enregistrements, $regle, $nom_enregistrement) = @_;
  CODE_TEST
}

(Encore une fois, cette structure n'est créée que si la définition de test ne commence pas déjà par "sub {")

Lorsque le code de test est exécuté et que le test échoue, il doit retourner une chaîne d'erreur qui sera affichée à l'utilisateur. Le texte sera renvoyé à la ligne avant l'affichage (et doit donc être du texte non formaté.) Si le test recherche plusieurs problèmes, une référence à un tableau de chaînes d'erreur peut être retournée. Un bloc de test qui n'a aucune erreur à signaler doit retourner soit une chaîne vide, soit une référence à un tableau vide.

Il existe deux types de tests (actuellement), et le code de test est appelé avec des arguments qui dépendent de la clause type-de-regle de la règle. Ces arguments et conventions d'appel sont les suivants :

tests enregistrement
Ces extraits de code sont censés tester un seul enregistrement Net::DNS::RR.

Il est appelé avec deux arguments :

1) $enregistrement: L'enregistrement à tester
2) $regle: La référence à l'objet Net::DNS::SEC::Tools::Donuts::Rule et les informations de définition de la règle.

Ceux-ci sont liés automatiquement à $enregistrement et $regle pour que le code de test puisse les utiliser.

tests nom
Ces extraits de code sont censés tester tous les enregistrements associés à un nom d'enregistrement donné.

Il est appelé avec trois arguments :

1) $enregistrements: Une référence de table hash vers tous les types d'enregistrements associés à ce nom d'enregistrement (par exemple, 'example.com' peut avoir une référence de table hash contenant une entrée pour 'A', 'MX', ...). Chaque valeur de la table hash contiendra un tableau de tous les enregistrements pour ce type (par exemple, l'entrée de table hash pour la clé 'A' peut contenir un tableau avec 2 enregistrements Net::DNS::RR, un pour chaque enregistrement A attaché à l'entrée 'example.com').
2) $regle: La référence à l'objet Net::DNS::SEC::Tools::Donuts::Rule et les informations de définition de la règle.
3) $nom_enregistrement: Le nom d'enregistrement vérifié (le nom associé aux données de 1) ci-dessus qui pourrait être, par exemple, "example.com", ou "www.example.com").

Ceux-ci sont liés à $enregistrements

, $règle et $nomrecord automatiquement pour que le code de test puisse les utiliser.

Exemples de règles :

# règle locale pour exiger que chaque enregistrement ait un
# TTL > 60 secondes
name: DNS_TTL_AT_LEAST_60
level: 8
type: record
<test>
  return "Le TTL pour $record->{nom} est trop petit" si ($record->ttl < 60);
</test>
# règle de politique locale pour exiger que tout ce qui a un enregistrement A
# ait aussi un enregistrement HINFO
name: DNS_MX_MUST_HAVE_A
level: 8
type: name
<test>
  return "$nomrecord a un enregistrement A mais n'a pas d'enregistrement HINFO"
    si (existe($records->{'A'}) && !existe($records->{'HINFO'}));
</test>
feature: NOM
La balise feature empêche cette règle de s'exécuter à moins que le mot-clé NOM n'ait été spécifié à l'aide de l'indicateur --features.
desc: DESCRIPTION
Une brève description de ce que la règle teste, qui sera affichée à l'utilisateur dans l'aide ou dans le résumé des erreurs lorsque donuts affichera les résultats.
requires: PERLMODULE1 PERLMODULE2 ...
Cela permet aux règles de dépendre de modules perl installés. Ils seront requis et importés au début de l'exécution de la règle. S'ils n'existent pas, une erreur sera enregistrée en utilisant donuts_error() indiquant que le module est requis pour que la règle fonctionne.
help: TOKEN: AIDE-TOKEN
Si la règle est configurable via le fichier .donuts.conf de l'utilisateur, cela décrit les tokens de configuration pour l'utilisateur lorsqu'il demande une aide de configuration via les indicateurs -H ou --help-config. Les tokens peuvent être utilisés dans les règles en y accédant via la référence $règle passée au code (le deuxième argument).

Exemples :

1) Dans le fichier de règle (ceci est une définition de règle incomplète) :
   name:           UN_TEST
   myconfig:       40
   help: myconfig: Un nombre spécial pour configurer ce test
   <test>
    # ... utiliser $règle->{'myconfig'}
   </test>
2) Cela permet à l'utilisateur de modifier la valeur de myconfig via son
   fichier .donuts.conf :
   # changer la configuration de UN_TEST...
   name:     UN_TEST
   myconfig: 40
3) et l'exécution de donuts -H affichera la ligne d'aide pour myconfig.
noindent: 1
nowrap: 1
Normalement, donuts effectuera un retour à la ligne du résumé des erreurs produit par une règle pour permettre un formatage automatique des résultats d'erreur. Parfois, cependant, les règles peuvent souhaiter auto-formater leurs sorties. L'option nowrap indique à donuts que la sortie est pré-formatée mais doit toujours être indentée pour s'aligner avec la sortie du reste du texte d'erreur (actuellement environ 15 espaces.) La balise noindent, cependant, indique qu'aucun retour à la ligne ni indentation ne doit être effectué, mais que l'erreur doit être imprimée telle quelle.
