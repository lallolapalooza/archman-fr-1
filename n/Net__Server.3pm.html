NOM

Net::Server - Moteur de serveur Perl extensible et général

SYNOPSIS

#!/usr/bin/perl -w -T
package MyPackage;
use base qw(Net::Server);
sub process_request {
    my $self = shift;
    while (<STDIN>) {
        s/[\r\n]+$//;
        print "Vous avez dit '$_'\015\012"; # écho de base
        last if /quit/i;
    }
}
MyPackage->run(port => 160, ipv => '*');
# commande rapide pour démarrer
perl -e 'use base qw(Net::Server); main->run(port => 20208)'
NOTE : à partir de Net::Server 2.005, la valeur par défaut pour
      ipv est IPv* ce qui signifie que si aucun hôte n'est passé, ou
      si un nom d'hôte est passé, tous les sockets IPv4 et IPv6 disponibles seront
      liés. Vous pouvez forcer IPv4 uniquement en ajoutant un ipv => 4
      dans l'une des configurations possibles.

* Prise en charge complète d'IPv6
* Sockets SSL fonctionnels et https (avec et sans IO::Socket::SSL)
* Mode Serveur Unique
* Mode Serveur Inetd

* Mode Géré Préfork (PreFork)
* Mode Fork
* Mode Multiplexage utilisant un seul processus
* Acceptation multi-ports en modes Single, Preforking et Forking
* Daemon HTTP de base (prend en charge IPv6, SSL, journaux de style apache complets)
* Daemon PSGI de base
* Acceptation/réception simultanée sur les sockets tcp/udp/unix, ssl/tcp et IPv4/IPv6
* Gestion sécurisée des signaux en modes Fork/PreFork pour éviter les problèmes de signaux Perl

* Capacité de défilement dans tous les modes Fork et PreFork.
* Compatible Taint
* Écrit en Perl
* Protection contre les dépassements de tampon
* Flux de processus propre
* Extensibilité

DESCRIPTION

"Net::Server" est un moteur de serveur Perl extensible et générique.

"Net::Server" tente d'être un serveur générique comme "Net::Daemon" et "NetServer::Generic". Il inclut la capacité de fonctionner comme un processus inetd ("Net::Server::INET"), un serveur à connexion unique ("Net::Server" ou "Net::Server::Single"), un serveur par fork ("Net::Server::Fork"), un serveur préfork qui maintient un nombre constant d'enfants préforkés ("Net::Server::PreForkSimple"), ou comme un serveur préfork géré qui maintient le nombre d'enfants en fonction de la charge du serveur ("Net::Server::PreFork"). Dans tous les types sauf inetd, le serveur offre la possibilité de se connecter à un ou plusieurs ports serveur.

Les types de serveurs supplémentaires sont rendus possibles via des "personnalités" ou des sous-classes de "Net::Server". En déplaçant les différents types de serveurs hors de la classe principale "Net::Server", le concept "Net::Server" est facilement extensible à d'autres types (dans un avenir proche, nous aimerions ajouter une personnalité "Thread").

"Net::Server" emprunte plusieurs concepts au serveur Web Apache. "Net::Server" utilise des "crochets" pour permettre à des serveurs personnalisés tels que SMTP, HTTP, POP3, etc. d'être superposés à la classe de base "Net::Server". De plus, la classe "Net::Server::PreFork" emprunte les concepts de min_start_servers, max_servers et min_waiting servers. "Net::Server::PreFork" utilise également le concept d'une acceptation sérialisée par flock lors de l'acceptation sur plusieurs ports (PreFork peut choisir entre flock, IPC::Semaphore et pipe pour contrôler la sérialisation).

PERSONNALITÉS

"Net::Server" est construit autour d'une classe commune (Net::Server) et est étendu à l'aide de sous-classes, ou "personnalités". Chaque personnalité hérite, surcharge ou améliore les méthodes de base de la classe de base.

Plusieurs personnalités de base sont incluses avec le package Net::Server, chacune ayant son utilité propre.

Fork
Trouvé dans le module Net/Server/Fork.pm (voir Net::Server::Fork). Ce serveur se lie à un ou plusieurs ports puis attend une connexion. Lorsqu'une demande client est reçue, le parent crée un enfant par fork, qui gère alors le client et se termine. Ceci est bien pour les services modérément sollicités.
INET
Trouvé dans le module Net/Server/INET.pm (voir Net::Server::INET). Ce serveur est conçu pour être utilisé avec inetd. Les méthodes "pre_bind", "bind", "accept" et "post_accept" sont toutes surchargées car ces services sont gérés par le démon INET.
MultiType
Trouvé dans le module Net/Server/MultiType.pm (voir Net::Server::MultiType). Ce serveur n'a aucune fonctionnalité de serveur propre. Il est conçu pour les serveurs qui ont besoin d'un moyen simple et facile de basculer entre différentes personnalités. Plusieurs paramètres "server_type" peuvent être donnés et Net::Server::MultiType parcourra jusqu'à ce qu'il trouve une classe qu'il peut utiliser.
Multiplex
Trouvé dans le module Net/Server/Multiplex.pm (voir Net::Server::Multiplex). Ce serveur se lie à un ou plusieurs ports. Il utilise IO::Multiplex pour multiplexer entre l'attente de nouvelles connexions et l'attente d'entrée sur les connexions établies. Cette personnalité est conçue pour s'exécuter en un seul processus sans fork. La méthode "process_request" n'est jamais utilisée, mais le rappel "mux_input" est utilisé à la place (voir aussi IO::Multiplex). Voir examples/samplechat.pl pour un exemple utilisant la plupart des fonctionnalités de Net::Server::Multiplex.
PreForkSimple
Trouvé dans le module Net/Server/PreFork.pm (voir Net::Server::PreFork). Ce serveur se lie à un ou plusieurs ports, puis crée par fork "max_servers" processus enfants. Le serveur s'assurera qu'à tout moment, il y a toujours "max_servers" processus disponibles pour recevoir une demande client. Chacun de ces enfants traitera jusqu'à "max_requests" connexions client. Ce type est bon pour un site très sollicité qui peut dédier des processus max_server quel que soit le niveau de charge. Il devrait bien évoluer pour la plupart des applications. L'acceptation multi-ports est réalisée en utilisant soit flock, IPC::Semaphore, soit pipe pour sérialiser les enfants. La sérialisation peut également être activée pour un port unique afin de contourner un système d'exploitation qui n'autorise pas plusieurs enfants à accepter simultanément. Pour une discussion plus approfondie sur la sérialisation, voir Net::Server::PreFork.
PreFork
Trouvé dans le module Net/Server/PreFork.pm (voir Net::Server::PreFork). Ce serveur se lie à un ou plusieurs ports, puis crée par fork "min_servers" processus enfants. Le serveur s'assurera qu'à tout moment, il y a au moins "min_spare_servers" mais pas plus de "max_spare_servers" processus disponibles pour recevoir une demande client, jusqu'à un maximum de "max_servers". Chacun de ces enfants traitera jusqu'à "max_requests" connexions client. Ce type est bon pour un site très sollicité et devrait bien évoluer pour la plupart des applications. L'acceptation multi-ports est réalisée en utilisant soit flock, IPC::Semaphore, soit pipe pour sérialiser les enfants. La sérialisation peut également être activée pour un port unique afin de contourner un système d'exploitation qui n'autorise pas plusieurs enfants à accepter simultanément. Pour une discussion plus approfondie sur la sérialisation, voir Net::Server::PreFork.
Single
Toutes les méthodes reviennent à Net::Server. Cette personnalité n'est fournie que comme parallélisme pour Net::Server::MultiType.
HTTP
Trouvé dans le module Net/Server/HTTP.pm (voir Net::Server::HTTP). Ce serveur est un démon HTTP de base qui prend en charge IPv6, SSL et les journaux de style Apache.
PSGI
Trouvé dans le module Net/Server/PSGI.pm (voir Net::Server::PSGI). Ce serveur est un démon PSGI de base qui prend en charge IPv6 et SSL.

ACCÈS AUX SOCKET

Une fois démarré, Net::Server s'occupe de se lier au port et d'attendre les connexions. Une fois qu'une connexion est reçue, Net::Server accepte sur le socket et stockera le résultat (la connexion client) dans $self->{server}->{client}. Cette propriété est un Socket béni dans les classes IO::Socket. Les serveurs UDP sont légèrement différents en ce sens qu'ils effectueront un recv au lieu d'un accept.

Pour faciliter la programmation, lors de la phase post_accept, STDIN et STDOUT sont ouverts à la connexion client. Cela permet aux programmes d'être écrits en utilisant <STDIN> et print "out\n" pour imprimer sur la connexion client. UDP nécessitera l'utilisation d'un appel ->send.

EXEMPLE DE CODE

Ce qui suit est un serveur très simple. La fonctionnalité principale se produit dans l'appel de la méthode process_request comme montré ci-dessous. Notez l'utilisation des timeouts pour empêcher le déni de service lors de la lecture. (D'autres exemples d'utilisation de "Net::Server" peuvent, ou seront, inclus avec cette distribution).

#!/usr/bin/perl -w -T
package MyPackage;
use strict;
use base qw(Net::Server::PreFork); # n'importe quelle personnalité fera l'affaire
MyPackage->run;
# surcharger le gestionnaire d'écho par défaut
sub process_request {
    my $self = shift;
    eval {
        local $SIG{'ALRM'} = sub { die "Timed Out!\n" };
        my $timeout = 30; # donner à l'utilisateur 30 secondes pour taper quelques lignes
        my $previous_alarm = alarm($timeout);
        while (<STDIN>) {
            s/\r?\n$//;
            print "Vous avez dit '$_'\r\n";
            alarm($timeout);
        }
        alarm($previous_alarm);
    };
    if ($@ =~ /timed out/i) {
        print STDOUT "Timed Out.\r\n";
        return;
    }
}
1;

L'exécution de ce fichier depuis la ligne de commande invoquera un Net::Server utilisant la personnalité PreFork. Lors de la construction d'une couche serveur par-dessus Net::Server, il est important d'utiliser des fonctionnalités telles que les timeouts pour prévenir les attaques par déni de service.

Net::Server est livré avec un serveur d'écho intégré par défaut. Vous pouvez le tester en exécutant simplement la commande suivante depuis la ligne de commande :

net-server

Si vous vouliez essayer une autre variante, vous pourriez essayer

net-server PreFork

Si vous vouliez essayer un serveur HTTP de base, vous pourriez utiliser

net-server HTTP

Ou si vous vouliez tester un CGI que vous écrivez, vous pourriez utiliser

net-server HTTP --app ../../mycgi.cgi

ARGUMENTS

Il y a au moins cinq façons possibles de passer des arguments à Net::Server. Ce sont : les passer à la méthode new, les passer sur la ligne de commande, les passer en paramètres à run, utiliser un fichier de configuration, retourner des valeurs dans la méthode default_values, ou configurer les valeurs dans post_configure_hook.

La méthode "options" est utilisée pour déterminer quels arguments le serveur recherchera et peut être utilisée pour étendre les paramètres analysés. Tous les arguments trouvés sur la ligne de commande, les paramètres passés à run, et les arguments trouvés dans le conf_file seront comparés aux clés du modèle d'options. Tous les paramètres de ligne de commande qui ne correspondent pas resteront en place et pourront être traités davantage par le serveur dans les divers hooks (en regardant dans @ARGV). Les arguments passés à new auront automatiquement priorité sur toutes les autres options (cela peut être utilisé si vous souhaitez interdire à un utilisateur de passer d'autres arguments).

Les arguments consistent en des paires clé-valeur. Sur la ligne de commande, ces paires suivent la mode POSIX de "--key value" ou "--key=value", ainsi que "key=value". Dans le fichier de configuration, le passage de paramètres peut être mieux illustré par l'expression régulière suivante : ($key,$val)=~/^(\w+)\s+(\S+?)\s+$/. Le passage d'arguments à la méthode run se fait comme suit : "<Net::Server->run(key1 =" 'val1')>>. Le passage d'arguments via un objet préconstruit peut être mieux illustré dans le code suivant :

#!/usr/bin/perl -w -T
package MyPackage;
use strict;
use base qw(Net::Server);
my $server = MyPackage->new({
    key1 => 'val1',
});
$server->run;

Les cinq méthodes de passage d'arguments peuvent être utilisées simultanément. Une fois qu'un argument a été défini, il n'est pas écrasé si une autre méthode passe le même argument. "Net::Server" recherchera les arguments dans l'ordre suivant :

1) Arguments passés à la méthode C<new>.
2) Arguments passés sur la ligne de commande.
3) Arguments passés à la méthode C<run>.
4) Arguments passés via un fichier de configuration.
5) Arguments définis dans la méthode C<default_values>.

De plus, les hooks suivants sont disponibles :

1) Arguments définis dans le configure_hook (se produit après new
   mais avant que toutes les autres zones ne soient vérifiées).
2) Arguments définis et validés dans le post_configure_hook
   (se produit après que toutes les autres zones aient été vérifiées).

Chacun de ces niveaux remplacera les paramètres du même nom spécifiés dans les niveaux suivants. Par exemple, spécifier --setsid=0 sur la ligne de commande remplacera une valeur de "setsid 1" dans le fichier de configuration.

Notez que la méthode configure_hook ne retourne pas de valeurs à définir, mais est là pour permettre la configuration de valeurs avant que la méthode de configuration ne soit appelée.

Les paires clé/valeur utilisées par le serveur sont supprimées par le processus de configuration afin que les couches serveur au-dessus de "Net::Server" puissent passer et lire leurs propres paramètres.

AJOUT D'ARGUMENTS PERSONNALISÉS

Il est possible d'ajouter vos propres paramètres personnalisés à ceux analysés par Net::Server. Le code suivant montre comment cela est fait :

sub options {
    my $self     = shift;
    my $prop     = $self->{'server'};
    my $template = shift;
    # configurer les options dans les classes parentes
    $self->SUPER::options($template);
    # ajouter une option à valeur unique
    $prop->{'my_option'} ||= undef;
    $template->{'my_option'} = \ $prop->{'my_option'};
    # ajouter une option à valeurs multiples
    $prop->{'an_arrayref_item'} ||= [];
    $template->{'an_arrayref_item'} = $prop->{'an_arrayref_item'};
}

La surcharge de la méthode "options" permet d'ajouter vos propres champs personnalisés. Un hashref de modèle est passé, qui doit ensuite être modifié pour contenir tous vos champs personnalisés. Les champs destinés à recevoir une seule valeur scalaire doivent avoir une référence vers le scalaire de destination. Les champs destinés à recevoir plusieurs valeurs doivent référencer l'arrayref de destination correspondant.

Il vous incombe de valider vos options personnalisées une fois qu'elles ont été analysées. Le post_configure_hook est un bon endroit pour effectuer votre validation.

Certains e-mails ont demandé pourquoi nous utilisons cette méthode de "modèle". L'idée est que vous créez la structure de données pour stocker les valeurs, et vous créez également un moyen d'insérer les valeurs dans la structure de données. Le modèle est le moyen d'acheminer les valeurs vers la structure de données du serveur. Une des possibilités (qui n'est probablement pas beaucoup utilisée) est qu'en vous permettant de spécifier le mappage, vous pourriez construire une structure de données imbriquée - même si les arguments passés sont plats. Cela vous permet également de configurer des alias pour vos noms.

Par exemple, une structure de base pourrait ressembler à ceci :

$prop = $self->{'server'}
$prop->{'my_custom_option'} ||= undef;
$prop->{'my_custom_array'}  ||= [];
$template = {
    my_custom_option => \ $prop->{'my_custom_option'},
    mco              => \ $prop->{'my_custom_option'}, # alias
    my_custom_array  => $prop->{'my_custom_array'},
    mca              => $prop->{'my_custom_array'}, # un alias
};
$template->{'mco2'} = $template->{'mco'}; # une autre façon d'aliaser

Mais vous pourriez aussi avoir des données plus complexes :

$prop = $self->{'server'};
$prop->{'one_layer'} = {
    two_layer => [
        undef,
        undef,
    ],
};
$template = {
    param1 => \ $prop->{'one_layer'}->{'two_layer'}->[0],
    param2 => \ $prop->{'one_layer'}->{'two_layer'}->[1],
};

Ceci est bien sûr un exemple artificiel - mais il montre que vous pouvez obtenir les données des arguments plats passés à n'importe quel type de structure dont vous avez besoin - avec seulement un peu d'effort.

conf_file
Nom du fichier depuis lequel les paires clé-valeur supplémentaires pour initialiser le serveur seront lues. La valeur par défaut est undef.

Il existe deux façons de spécifier un emplacement par défaut pour conf_file. La première consiste à passer la valeur par défaut à la méthode run, comme suit :

MyServer->run({
   conf_file => '/etc/my_server.conf',
});

Si l'utilisateur final passe --conf_file=/etc/their_server.conf, la valeur sera remplacée.

La deuxième façon a été ajoutée dans la version 0.96. Elle utilise la méthode default_values, comme suit :

sub default_values {
    return {
        conf_file => '/etc/my_server.conf',
    }
}

Cette méthode a l'avantage de pouvoir être surchargée dans la méthode run.

Si vous ne voulez pas que l'utilisateur puisse spécifier un conf_file, vous pouvez passer conf_file à la méthode new lors de la création de votre objet :

MyServer->new({
   conf_file => '/etc/my_server.conf',
})->run;

Si vous le passez ainsi, la valeur passée à new supplantera toute autre valeur passée.

log_level
Plage de 0 à 4 en niveau. Spécifie quel niveau d'erreur sera enregistré. "0" signifie que l'enregistrement est désactivé. "4" signifie très verbeux. Ces niveaux doivent correspondre aux niveaux syslog. La valeur par défaut est 2. Ces niveaux correspondent aux niveaux syslog selon les paires clé/valeur suivantes : 0=>'err', 1=>'warning', 2=>'notice', 3=>'info', 4=>'debug'.
log_file
Nom du fichier journal ou du système de journalisation où écrire. Si aucun nom n'est spécifié et que le hook write_to_log n'est pas surchargé, le journal sera envoyé à STDERR. La valeur par défaut est undef.

log_file peut également être le nom d'une classe de journalisation enfichable de Net::Server. Net::Server est livré avec Sys::Syslog et Log::Log4perl. Si log_file ressemble au nom d'un module, "Net::Server::Log::" sera ajouté au début et le module sera requis. La classe doit fournir une méthode "initialize" qui renvoie une fonction unique qui sera utilisée pour la journalisation. La fonction renvoyée sera passée le niveau du message et le message.

Si le nom magique "Sys::Syslog" est utilisé, tous les journaux seront traités par le module Net::Server::Log::Sys::Syslog. Si syslog est utilisé, les paramètres "syslog_logsock", "syslog_ident", "syslog_logopt" et "syslog_facility" peuvent également être définis. Voir Net::Server::Log::Sys::Syslog.

Si le nom magique "Log::Log4perl" est utilisé, tous les journaux seront dirigés vers le système Log4perl. Si utilisé, "log4perl_conf", "log4perl_poll", "log4perl_logger" peuvent être définis. Voir Net::Server::Log::Log::Log4per.

Si un "log_file" est spécifié ou si "setsid" est défini, STDIN et STDOUT seront automatiquement ouverts sur /dev/null et STDERR sera ouvert sur STDOUT. Cela évitera que toute sortie ne soit déposée dans le terminal.

log_function
Peut prendre un coderef ou un nom de méthode qui sera appelé lorsqu'un événement de journalisation se produit. Le niveau du message et le message de l'événement lui seront transmis.

Note : Les fonctions dépendantes de stdout ne fonctionneront pas pendant process_request si tie_stdout est activé (comme dans Net::Server::HTTP).

pid_file
Nom du fichier où le PID du processus parent est stocké. S'applique généralement uniquement aux serveurs qui forquent. La valeur par défaut est none (undef).
port
Voir Net::Server::Proto pour des exemples de configuration supplémentaires.

Port local auquel se lier. S'il s'agit d'un port bas, le processus doit démarrer en tant que root. Si plusieurs ports sont spécifiés, ils seront tous ouverts au démarrage du serveur. Il peut s'agir de la forme "host:port/proto", "host:port/proto/ipv", "host:port", "port/proto", ou "port", où host représente un nom d'hôte sur la machine locale, et port représente le numéro de port (par exemple, "80") ou la désignation du service (par exemple, "http"), où ipv représente la version du protocole (IPv4 ou IPv6 ou IPv*) et proto représente le protocole à utiliser. Voir Net::Server::Proto. Voici quelques chaînes de ports valides :

20203                            # port seulement
localhost:20203                  # hôte et port
localhost:http                   # localhost avec port 80
localhost:20203/tcp              # hôte, port, protocole
localhost:20203/tcp/IPv*         # hôte, port, protocole et famille
localhost, 20203, tcp, IPv*      # idem
localhost | 20203 | tcp | IPv*   # idem
localhost:20203/IPv*             # lier toutes les interfaces locales pour IPv4 ou 6 (par défaut)
localhost:20203/IPv4/IPv6        # lier localhost sur IPv4 et 6 (échoue si ne peut pas faire les deux)
*:20203                          # lier toutes les interfaces locales

De plus, lorsqu'il est passé en code (non en ligne et non en configuration), le port peut être passé sous forme de hashref ou d'arrayhashref d'informations :

port => {
    host  => 'localhost',
    port  => '20203',
    ipv   => 6,     # IPv6 seulement
    proto => 'udp', # protocole UDP
}
port => [{
    host  => '*',
    port  => '20203',
    ipv   => 4,     # IPv4 seulement
    proto => 'tcp', # (défaut)
}, {
    host  => 'localhost',
    port  => '20204',
    ipv   => '*',      # défaut - toutes les interfaces IPv4 et IPv6 liées à localhost
    proto => 'ssleay', # ou ssl - utilisant SSL
}],

Un host explicite dans une spécification de port supplante une adresse de liaison par défaut (un "host", voir ci-dessous). La partie host peut être entre crochets, mais lorsqu'il s'agit d'une adresse IPv6 numérique, elle doit être entre crochets pour éviter toute ambiguïté dans l'analyse d'un numéro de port, par exemple : "[::1]:80". Cependant, vous pouvez également utiliser des barres verticales, des espaces blancs ou des virgules pour séparer ces éléments. Note : l'hôte et le numéro de port doivent venir en premier.

Si le protocole n'est pas spécifié, proto sera utilisé comme le "proto" spécifié dans les arguments. Si "proto" n'est pas spécifié, "tcp" sera utilisé par défaut. Si host n'est pas spécifié, host sera utilisé comme le "host" spécifié dans les arguments. Si "host" n'est pas spécifié, "*" sera utilisé par défaut. Le port par défaut est 20203. La configuration passée à new ou run peut être un scalaire avec un numéro de port ou un tableau de ports. Si "ipv" n'est pas spécifié, "*" sera utilisé par défaut (toute adresse résolue sous IPv4 ou IPv6).

Si vous travaillez avec des sockets Unix, vous pouvez également spécifier "socket_file|unix" ou "socket_file|type|unix" où type est SOCK_DGRAM ou SOCK_STREAM.

Sur les systèmes qui le prennent en charge, une valeur de port de 0 peut être utilisée pour que le système d'exploitation attribue un port automatiquement. La valeur du port attribué sera stockée dans la propriété NS_port de l'objet Net::Server::Proto::TCP et sera également disponible dans la méthode sockport. Lorsque le serveur traite une requête, la propriété $self->{server}->{sockport} contient le port connecté.

host
Hôte local ou adresse sur laquelle le port sera lié. Si '*' est donné, le port sera lié à toutes les adresses disponibles sur la machine. L'argument "host" fournit un hôte local par défaut si l'argument "port" omet une spécification d'hôte. Voir Net::Server::Proto. Voir IO::Socket. La configuration passée à new ou run peut être un scalaire avec un seul hôte ou un tableau d'hôtes - si le tableau d'hôtes est plus court que le tableau de ports, le dernier enregistrement sera utilisé pour étendre le tableau d'hôtes jusqu'à la taille du tableau de ports.

Si une adresse IPv4 est passée, un socket IPv4 sera créé. Si une adresse IPv6 est passée, un socket IPv6 sera créé. Si un nom d'hôte est passé, Net::Server examinera la valeur de ipv (par défaut IPv4) pour déterminer le type de socket à créer. La spécification ipv peut éventuellement être passée dans le nom d'hôte.

host => "127.0.0.1",  # une adresse IPv4
host => "::1",        # une adresse IPv6
host => 'localhost',  # adresses correspondant à localhost (par défaut tout IPv4 et/ou IPv6)
host => 'localhost/IPv*',  # idem
ipv  => 6,
host => 'localhost',  # adresses correspondant à localhost (IPv6)
ipv  => 4,
host => 'localhost',  # adresses correspondant à localhost (IPv4)
ipv  => 'IPv4 IPv6',
host => 'localhost',  # adresses correspondant à localhost (nécessite IPv6 et IPv4)
host => '*',          # toute interface locale (tout IPv6 ou IPv4)
host => '*/IPv*',     # idem (tout IPv6 ou IPv4)
ipv  => 4,
host => '*',          # toute interface IPv4 locale
proto
Voir Net::Server::Proto. Protocole à utiliser lors de la liaison des ports. Voir IO::Socket. Depuis la version 2.0, Net::Server prend en charge tcp, udp, unix, unixdgram, ssl et ssleay. D'autres types devront être ajoutés ultérieurement (ou des modules personnalisés étendant la classe Net::Server::Proto pourront être utilisés). La configuration passée à new ou run peut être un scalaire avec un seul proto ou un tableau de protos - si le tableau de protos est plus court que le tableau de ports, le dernier enregistrement sera utilisé pour étendre le tableau de protos jusqu'à la taille du tableau de ports.

De plus, proto peut également contenir la spécification d'ipv.

ipv (IPv4 et IPv6)
Voir Net::Server::Proto.

Ce paramètre est utilisé pour spécifier le type de socket à créer. La valeur par défaut est IPv4.

log_level
Plage de 0 à 4 en niveau. Spécifie quel niveau d'erreur sera enregistré. "0" signifie que l'enregistrement est désactivé. "4" signifie très verbeux. Ces niveaux doivent correspondre aux niveaux syslog. La valeur par défaut est 2. Ces niveaux correspondent aux niveaux syslog selon les paires clé/valeur suivantes : 0=>'err', 1=>'warning', 2=>'notice', 3=>'info', 4=>'debug'.

IPv6 est maintenant disponible sous Net::Server. Il sera utilisé automatiquement si une adresse IPv6 est passée, ou si ipv est explicitement défini sur IPv6, ou si ipv est laissé à la valeur par défaut d'IPv*. C'est un changement significatif par rapport aux versions 2.004 et antérieures où la valeur par défaut était IPv4. Cependant, le comportement précédent a causé de la confusion sur les hôtes uniquement IPv6, et sur les hôtes qui n'avaient que des entrées IPv6 pour un nom d'hôte local. Essayer de passer une adresse IPv4 lorsque ipv est défini sur 6 (uniquement 6 - pas * ou 4) entraînera une erreur.

localhost:20203 # utilisera IPv6 s'il existe une entrée correspondante pour localhost
                # utilisera également IPv4 s'il existe une entrée v4 correspondante pour localhost
localhost:20203:IPv*  # identique (par défaut)
localhost:20203:IPv6  # utilisera IPv6
[::1]:20203           # utilisera IPv6 (adresse de style IPv6)
localhost:20203:IPv4  # utilisera IPv4
127.0.0.1:20203       # utilisera IPv4 (adresse de style IPv4)
localhost:20203:IPv4:IPv6 # se liera aux deux v4 et v6 - échoue sinon
# ou sous forme de hashref comme
port => {
    host => "localhost",
    ipv  => 6, # se lie uniquement à IPv6
}
port => {
    host => "localhost",
    ipv  => 4, # se lie uniquement à IPv4
}
port => {
    host => "::1",
    ipv  => "IPv6", # identique à passer "6"
}
port => {
    host => "localhost/IPv*",       # n'importe quel IPv4 ou IPv6
}
port => {
    host => "localhost IPv4 IPv6",  # doit créer les deux
}

Dans de nombreuses solutions Net::Server proposées, IPv* était activé par défaut. Pour les versions 2.000 à 2.004, le défaut précédent d'IPv4 était utilisé. Nous avons tenté de faciliter la définition d'IPv4, d'IPv6 ou d'IPv*. Si vous ne voulez pas ou n'avez pas besoin d'IPv6, définissez simplement ipv sur 4, passez IPv4 dans la spécification de port, définissez $ENV{'IPV'}=4; avant d'exécuter le serveur, définissez $ENV{'NO_IPV6'}, ou désinstallez IO::Socket::IP et/ou IO::Socket::INET6.

Sur ma machine locale, la commande suivante produit la sortie suivante :

perl -e 'use base qw(Net::Server); main->run(host => "localhost")'
Résolu [localhost]:20203 en [::1]:20203, IPv6
Résolu [localhost]:20203 en [127.0.0.1]:20203, IPv4
Liaison au port TCP 20203 sur l'hôte ::1 avec IPv6
Liaison au port TCP 20203 sur l'hôte 127.0.0.1 avec IPv4

Ma machine locale a l'IPv6 activé et il existe des entrées pour localhost sur IPv6 ::1 et IPv4 127.0.0.1. Je pourrais également choisir de lier explicitement les ports plutôt que de dépendre de ipv => "*" pour les résoudre, comme dans l'exemple suivant :

perl -e 'use base qw(Net::Server); main->run(port => [20203,20203], host => "localhost", ipv => [4,6])'
Liaison au port TCP 20203 sur l'hôte localhost avec IPv4
Liaison au port TCP 20203 sur l'hôte localhost avec IPv6

Il existe un cas spécial d'utilisation de host => "*" ainsi que de ipv => "*". La méthode Net::Server::Proto::_bindv6only est utilisée pour vérifier le paramètre système de "sysctl -n net.ipv6.bindv6only" (ou net.inet6.ip6.v6only). Si ce paramètre est faux, un socket IPv6 écoutera l'adresse IPv4 correspondante. Par exemple, l'adresse [::] (équivalent IPv6 de INADDR_ANY) écoutera également 0.0.0.0. L'adresse ::FFFF:127.0.0.1 (IPv6) écouterait également 127.0.0.1 (IPv4). Dans ce cas, un seul socket sera créé car il gérera les deux cas (une erreur est retournée si une tentative est faite d'écouter les deux adresses lorsque bindv6only est faux).

Cependant, si net.ipv6.bindv6only (ou son équivalent) est vrai, alors un nom d'hôte (tel que *) résolvant à la fois une entrée IPv4 et une entrée IPv6 entraînera un socket IPv4 ainsi qu'un socket IPv6.

Sur ma machine linux qui utilise par défaut net.ipv6.bindv6only=0, la sortie suivante est produite.

perl -e 'use base qw(Net::Server); main->run(host => "*")'
Résolu [*]:8080 en [::]:8080, IPv6
N'inclut pas l'hôte résolu [0.0.0.0] IPv4 car il sera géré par [::] IPv6
Liaison au port TCP 8080 sur l'hôte :: avec IPv6

Si j'exécute "sudo /sbin/sysctl -w net.ipv6.bindv6only=1", la sortie suivante est produite.

perl -e 'use base qw(Net::Server); main->run(host => "*")'
Résolu [*]:8080 en [0.0.0.0]:8080, IPv4
Résolu [*]:8080 en [::]:8080, IPv6
Liaison au port TCP 8080 sur l'hôte 0.0.0.0 avec IPv4
Liaison au port TCP 8080 sur l'hôte :: avec IPv6

BSD diffère de linux et utilise généralement par défaut net.inet6.ip6.v6only=0. S'il ne peut être déterminé sur votre OS, il sera par défaut faux et le message de journalisation passera de "il sera géré" à "il devrait être géré" (si vous avez un moyen peu coûteux en ressources de vérifier sur votre plateforme, n'hésitez pas à m'envoyer un e-mail). Assurez-vous de vérifier les journaux lors des tests de votre serveur pour vous assurer que vous avez lié les ports souhaités. Vous pouvez toujours passer des spécifications de port IPv4 et IPv6 explicites individuelles si nécessaire. Par exemple, si votre système dispose d'interfaces IPv4 et IPv6 mais que vous souhaitez uniquement vous lier aux entrées IPv6, vous devriez utiliser un nom d'hôte de [::] au lieu de [*].

Si bindv6only (ou son équivalent) est faux, et que vous recevez une connexion IPv4 sur un port IPv6 lié, la représentation textuelle de l'adresse IPv4 du pair sera généralement sous la forme d'une adresse IPv6 mappée IPv4, par exemple "::FFFF:127.0.0.1".

Le paramètre ipv a été choisi car il n'entre pas en conflit avec d'autres utilisations existantes, il est très similaire à ipv4 ou ipv6, il permet au code utilisateur de ne pas avoir besoin de connaître Socket::AF_INET ou IO::Socket::INET6 ou Socket::AF_UNSPEC, et il est court.

listen
Voir IO::Socket. Non utilisé avec le protocole udp (ou UNIX SOCK_DGRAM).
ipv6_package
Net::Server::Proto essaiera de déterminer la classe de socket appropriée à utiliser si un socket v6 est nécessaire. Il essaiera par défaut IO::Socket::IP en premier, puis IO::Socket::INET6. La spécification de ce package permet d'utiliser un package spécifique (notez que IO::Socket::SSL utilisé par Proto::SSL détermine lui-même son package de socket ipv6).
reverse_lookups
Spécifie s'il faut rechercher le nom d'hôte de l'IP connecté. Les informations sont mises en cache dans l'objet serveur sous la propriété "peerhost". Par défaut, la recherche inversée n'est pas utilisée (undef).

Peut être défini sur les valeurs "double", "double-detail", "double-autofail", ou "double-debug" pour définir double_reverse_lookups.

double_reverse_lookups
Si défini, définit également reverse_lookups.

Identique à la définition de reverse_lookups sur "double". Recherche les IP auxquelles le nom d'hôte se résout pour s'assurer que l'IP de connexion est l'une de ces IP.

Définit peerhost_rev comme un hashref des adresses IP auxquelles le nom s'est résolu lors de get_client_info.

Si double_reverse_lookups est défini, la méthode double_reverse_lookup est appelée pendant la méthode allow_deny. La méthode double_reverse_lookup reçoit :

addr  - l'adresse IPv4 ou IPv6
host  - le nom d'hôte auquel addr s'est résolu
addrs - le hashref des adresses IP auxquelles host s'est résolu
orig  - l'adresse originale non filtrée

Fait retourner false à allow_deny s'il n'y a pas de nom d'hôte, pas d'IP inversées, ou si l'une des adresses IP ne correspond pas à l'adresse IP de connexion. Envoie un message de niveau de journalisation 3.

Peut définir double_reverse_lookups sur l'une des options suivantes pour ajuster la journalisation :

detail   - ajoute les addrs aux messages d'échec
autofail - échoue à chaque connexion et journalise
debug    - journalise les informations d'adresse (mais ne pas échouer) pour les connexions réussies

Les commandes en ligne suivantes peuvent aider au débogage :

net-server HTTP --reverse_lookups=double-debug --log_level=3
# curl localhost:8080 dans une autre fenêtre
2022/11/30-22:16:45 CONNECT TCP Peer: "[::ffff:127.0.0.1]:44766" (localhost)  Local: "[::ffff:127.0.0.1]:8080"
2022/11/30-22:16:45 Double reverse debug:  addr: 127.0.0.1,  host: localhost,  addrs: (127.0.0.1),  orig_addr: ::ffff:127.0.0.1

La double_reverse_lookup est appelée avant l'exécution des règles allow/deny.

allow/deny
Peut être spécifié plusieurs fois. Contient une regex à comparer au peeraddr entrant ou au peerhost (si reverse_lookups a été activé). Si les options allow ou deny sont données, le client entrant doit correspondre à un allow et ne pas correspondre à un deny, sinon la connexion client sera fermée. Par défaut, des tableaux vides.
cidr_allow/cidr_deny
Peut être spécifié plusieurs fois. Contient un bloc CIDR à comparer au peeraddr entrant. Si les options cidr_allow ou cidr_deny sont données, le client entrant doit correspondre à un cidr_allow et ne pas correspondre à un cidr_deny, sinon la connexion client sera fermée. Par défaut, des tableaux vides.
chroot
Répertoire vers lequel se chrooter après que le processus de liaison a eu lieu et que le serveur s'exécute toujours en tant que root. Par défaut, undef.
user
Identifiant utilisateur ou nom d'utilisateur à adopter après que le processus de liaison a eu lieu. Par défaut, "nobody." Si vous souhaitez que le serveur s'exécute en tant que root, vous devrez spécifier "user" égal à "root".
group
Identifiant de groupe ou nom de groupe à adopter après que le processus de liaison a eu lieu. Par défaut, "nobody." Si vous souhaitez que le serveur s'exécute en tant que root, vous devrez spécifier "group" égal à "root".
background
Spécifie si le serveur doit forker après la méthode bind pour se libérer de la ligne de commande. Par défaut, undef. Le processus sera également mis en arrière-plan si "setsid" est défini.
setsid
Spécifie si le serveur doit forker après la méthode bind pour se libérer de la ligne de commande, puis exécuter la commande POSIX::setsid() pour véritablement démoniaiser. Par défaut, undef. Si un "log_file" est donné ou si "setsid" est défini, STDIN et STDOUT seront automatiquement ouverts sur /dev/null et STDERR sera ouvert sur STDOUT. Cela empêchera toute sortie d'apparaître sur le terminal.
no_close_by_child
Booléen. Spécifie si un enfant
ked child process has permission or not to shutdown the entire server process. If set to 1, the child may NOT signal the parent to shutdown all children. Default is undef (not set).
no_client_stdout
Booléen. Valeur par défaut : undef (non défini). Indique que STDIN et STDOUT ne doivent pas être ouverts sur le handle client une fois qu'une connexion a été acceptée. Par défaut, Net::Server ouvrira STDIN et STDOUT sur le socket client, ce qui facilitera la lecture et l'écriture directes depuis et vers le socket pour de nombreux types de scripts en utilisant les méthodes d'impression et de lecture normales. La désactivation de cette option est utile sur les clients qui peuvent ouvrir leurs propres connexions à STDIN et STDOUT.

Cette option n'a aucun effet sur STDIN et STDOUT, qui disposent d'une propriété client magique liée aux STDIN et STDOUT déjà ouverts.

leave_children_open_on_hup
Booléen. Valeur par défaut : undef (non défini). Si défini, le processus parent ne tentera pas de fermer les processus enfants si le processus parent reçoit un signal HUP. Le processus parent reconfigurera le port ouvert et commencera à suivre un nouvel ensemble d'enfants.

Les enfants d'un serveur Fork se termineront après leur requête en cours. Les enfants d'un serveur de type Prefork termineront la requête en cours puis se termineront.

Note - le processus parent nouvellement redémarré démarrera un nouvel ensemble de serveurs sur les serveurs fork. Le nouveau processus parent tentera de suivre les enfants du processus parent précédent, mais les canaux de communication personnalisés (pipes ouverts du processus enfant vers le processus parent précédent) ne seront plus disponibles pour les anciens processus enfants. Les nouveaux processus enfants se connecteront toujours correctement au nouveau processus parent.

sig_passthrough
Par défaut : none. Permet de transmettre les signaux demandés aux enfants. Prend un seul nom de signal, une liste de noms séparés par des virgules ou un tableau de noms de signaux. Il envoie d'abord les signaux aux enfants avant d'appeler tout signal actuellement enregistré sous ce nom.
tie_client_stdout
Par défaut : undef. Si défini, utilisera l'interface liée de Net::Server::TiedHandle pour STDIN et STDOUT. Cette interface permet à SSL et SSLEAY de fonctionner. Elle permet également d'intercepter la lecture et l'écriture via les callbacks tied_stdin_callback et tied_stdout_callback.
tied_stdin_callback
Par défaut : undef. Appelé lors de la lecture de données STDIN si tie_client_stdout a été défini, ou si la méthode tie_stdout du handle client renvoie true. Il reçoit la connexion client, le nom de la méthode qui serait appelée, et les arguments qui sont passés. Le callback est alors responsable d'appeler cette méthode sur le handle ou d'effectuer une autre opération d'entrée.
tied_stdout_callback
Par défaut : undef. Appelé lors de l'écriture de données sur STDOUT si tie_client_stdout a été défini, ou si la méthode tie_stdout du handle client renvoie true. Il reçoit la connexion client, le nom de la méthode qui serait appelée, et les arguments qui sont passés. Le callback est alors responsable d'appeler cette méthode sur le handle ou d'effectuer une autre opération de sortie.

PROPRIÉTÉS

Tous les "ARGUMENTS" listés ci-dessus deviennent des propriétés de l'objet serveur sous le même nom. Ces propriétés, ainsi que d'autres propriétés internes, sont disponibles pendant les hooks et d'autres appels de méthode.

La structure d'un objet Net::Server est illustrée ci-dessous :

$self = bless({
    server => {
        key1 => 'val1',
        # plus de clés/valeurs
    },
}, 'Net::Server');

Cette structure a été choisie afin que toutes les propriétés liées au serveur soient regroupées sous une seule clé du hash de l'objet. Ceci afin que d'autres objets puissent s'appuyer sur la classe d'objet Net::Server tout en conservant un espace de noms relativement propre dans le hash.

Vous pouvez obtenir et définir les propriétés de deux manières. La manière suggérée est d'accéder directement aux propriétés via

my $val = $self->{server}->{key1};

L'accès direct aux propriétés accélérera le processus du serveur - bien que certains pourraient juger cela comme un mauvais style. Une deuxième manière a été fournie pour les types orientés objet qui croient aux méthodes. La deuxième manière consiste en les méthodes suivantes :

my $val = $self->get_property( 'key1' );
my $self->set_property( key1 => 'val1' );

Les propriétés peuvent être modifiées à tout moment avec prudence (ne pas mettre la propriété sock à undef, car cela fermerait la connexion client).

FLUX DE PROCESSUS

Le flux de processus est écrit de manière ouverte, facile à remplacer et facile à accrocher. Le flux de base est montré ci-dessous. C'est le flux de la méthode "$self->run".

$self->configure_hook;
$self->configure(@_);
$self->post_configure;
$self->post_configure_hook;
$self->pre_bind;
$self->bind;
$self->post_bind_hook;
$self->post_bind;
$self->pre_loop_hook;
$self->loop;
### routines dans un $self->loop standard
# $self->accept;
# $self->run_client_connection;
# $self->done;
$self->pre_server_close_hook;
$self->server_close;

Le serveur se termine ensuite.

Pendant la phase de traitement du client ("$self->run_client_connection"), ce qui suit représente le flux du programme :

$self->post_accept;
$self->get_client_info;
$self->post_accept_hook;
if ($self->allow_deny
    && $self->allow_deny_hook) {
    $self->process_request;
} else {
    $self->request_denied_hook;
}
$self->post_process_request_hook;
$self->post_process_request;
$self->post_client_connection_hook;

La méthode allow_deny appelle $self->double_reverse_lookup si les recherches inverses doubles sont activées.

Le processus boucle ensuite et attend la prochaine connexion. Pour une discussion plus approfondie, veuillez lire le code.

Pendant la phase de fermeture du serveur ("$self->server_close"), ce qui suit représente le flux du programme :

$self->close_children;  # si il y en a
$self->post_child_cleanup_hook;
if (Restarting server) {
    $self->restart_close_hook();
    $self->hup_server;
}
$self->shutdown_sockets;
$self->server_exit;

MÉTHODES PRINCIPALES DU SERVEUR

"$self->run"
Cette méthode intègre le flux de processus principal. Ce flux est listé ci-dessus.

La méthode run peut être appelée de l'une des manières suivantes.

MyPackage->run(port => 20201);
MyPackage->new({port => 20201})->run;
my $obj = bless {server=>{port => 20201}}, 'MyPackage';
$obj->run;

La méthode ->run devrait typiquement être la dernière méthode appelée dans un script de démarrage de serveur (le serveur se terminera à la fin de la méthode ->run).

"$self->configure"
Cette méthode tente de lire les configurations depuis la ligne de commande, depuis l'appel de la méthode run, ou depuis un fichier conf_file spécifié (le conf_file peut être spécifié par des paramètres passés, ou dans les default_values). Tous les paramètres configurés sont ensuite stockés dans la propriété {"server"} de l'objet Server.
"$self->post_configure"
Le hook post_configure commence le démarrage du serveur. Pendant que cette méthode s'exécute, les instances de serveur en cours sont vérifiées, les pid_files sont créés, les log_files sont créés, Sys::Syslog est initialisé (si nécessaire), le lancement du processus en arrière-plan se produit et le serveur ferme STDIN et STDOUT (si nécessaire).
"$self->pre_bind"
Cette méthode est utilisée pour initialiser tous les objets socket utilisés par le serveur.
"$self->bind"
Cette méthode se lie effectivement aux sockets initialisés (ou se relie si le serveur a reçu un HUP).
"$self->post_bind"
Pendant cette méthode, les privilèges sont abaissés. Les signaux INT, TERM et QUIT sont configurés pour exécuter server_close. Sig PIPE est configuré sur IGNORE. Sig CHLD est configuré sur sig_chld. Et sig HUP est configuré pour appeler sig_hup.

Sous les personnalités Fork, PreFork et PreFork simple, ces signaux sont enregistrés en utilisant Net::Server::SIG pour permettre une gestion sûre des signaux.

"$self->loop"

"$self->server_startup"
Cette méthode est appelée juste avant que le serveur ne commence réellement à écouter les connexions.

Cette méthode initialise le serveur, la mise en place des options de configuration, l'ouverture des sockets et la gestion des signaux. Elle prépare le serveur à accepter les connexions entrantes.

"$self->server_init"
Cette méthode est appelée au début de la méthode run.

Elle est utilisée pour configurer le serveur, lire les options de configuration, initialiser les fichiers de journalisation et les fichiers de processus (pid_files). La méthode charge le reste de la configuration.

"$self->run"
La méthode principale qui fait tourner le serveur.

Elle appelle server_startup, puis entre dans une boucle pour accepter et gérer les connexions entrantes.

Elle s'arrête lorsque le serveur reçoit un signal pour se terminer ou redémarrer.

HOOKS

"Net::Server" fournit un certain nombre de "hooks" permettant aux serveurs construits sur "Net::Server" de réagir à différents niveaux d'exécution sans avoir à utiliser "SUPER" dans les méthodes principales intégrées. L'emplacement des hooks peut être vu dans la section FLUX DE PROCESSUS.

Presque toutes les méthodes de hook par défaut ne font rien. Pour utiliser un hook, il suffit de surcharger la méthode dans votre sous-classe. Par exemple, pour ajouter votre propre post_configure_hook, vous pourriez faire quelque chose comme suit :

package MyServer;
sub post_configure_hook {
    my $self = shift;
    my $prop = $self->{'server'};
    # faire une validation ici
}

Ce qui suit décrit les hooks disponibles dans la classe Net::Server simple (d'autres variantes comme Fork ou PreFork ont des hooks supplémentaires).

"$self->configure_hook()"
Ce hook a lieu immédiatement après l'appel de la méthode "->run()". Ce hook permet de configurer l'objet avant que toute configuration intégrée n'ait lieu. Cela permet une configurabilité personnalisée.
"$self->post_configure_hook()"
Ce hook se produit juste après la lecture des paramètres de configuration et l'initiation de la journalisation et de la création du fichier pid. Il se produit également avant l'appel des méthodes "->pre_bind()" et "->bind()". Ce hook permet de vérifier les paramètres de configuration.
"$self->post_bind_hook()"
Ce hook se produit juste après le processus de liaison (bind) et juste avant que toute opération de chroot, de changement d'utilisateur ou de groupe ne se produise. À ce stade, le processus s'exécutera toujours sous l'utilisateur qui a démarré le serveur.
"$self->pre_loop_hook()"
Ce hook se produit après que le chroot, le changement d'utilisateur et le changement de groupe ont eu lieu. Il permet une préparation avant le début de la boucle.
"$self->can_read_hook()"
Ce hook se produit après qu'un socket devient lisible lors d'une requête accept_multi_port (accept_multi_port est utilisé s'il y a plusieurs ports liés pour accepter, ou si le paramètre de configuration "multi_port" est défini sur vrai). Ce hook est destiné à permettre le traitement de descripteurs arbitraires ajoutés à IO::Select utilisé pour accept_multi_port. Ces descripteurs pourraient être ajoutés pendant le post_bind_hook. Aucun support interne n'est ajouté pour le traitement de ces descripteurs ou leur ajout à IO::Socket. Il faut être prudent quant à ce qui se passe pendant le can_read_hook, car un temps de réponse long rendra le serveur susceptible aux attaques par déni de service (DOS). Une valeur de retour vraie indique que le serveur ne doit pas transmettre le descripteur lisible aux phases post_accept et process_request.

Il est généralement suggéré de rechercher d'autres moyens pour envoyer des messages via des sockets non créés par Net::Server.

"$self->post_accept_hook()"
Ce hook se produit après qu'un client s'est connecté au serveur. À ce stade, STDIN et STDOUT sont mappés au socket client. Ce hook se produit avant le traitement de la requête.
"$self->allow_deny_hook()"
Ce hook permet de vérifier les informations IP et hôte au-delà de la routine "$self->allow_deny()". Si ce hook retourne 1, la requête client sera traitée, sinon, la requête sera refusée.

Depuis la version 2.000, la connexion client est passée en argument.

"$self->request_denied_hook()"
Ce hook se produit si "$self->allow_deny()" ou "$self->allow_deny_hook()" ont eu lieu.
"$self->post_process_request_hook()"
Ce hook se produit après le traitement de la requête, mais avant que la connexion client ne soit fermée.
"$self->post_client_connection_hook"

REDÉMARRAGE

Chacun des personnages de serveur (sauf INET) prend en charge le redémarrage via le signal HUP (voir "kill -l"). Lorsqu'un HUP est reçu, le serveur ferme les enfants (s'il y en a), s'assure que les sockets sont ouverts et se réexécute en utilisant les mêmes arguments de ligne de commande qui ont initialement lancé le serveur. (Note : il est important que @ARGV ne soit pas modifié tant que "->run" n'est pas appelé).

Net::Server tente de trouver la ligne de commande utilisée pour lancer le programme. La tentative est effectuée avant le traitement de tout fichier de configuration ou argument. Le résultat de cette tentative est stocké à l'aide de la méthode "->commandline". Le contenu de la ligne de commande peut également être récupéré en utilisant la même méthode. Le contenu stocké peut contenir des éléments taint qui provoqueront l'arrêt du serveur lorsqu'il est utilisé avec le drapeau -T (mode taint). Comme il est impossible de décider arbitrairement de ce qui est sûr et de ce qui ne l'est pas, le programme individuel doit nettoyer les éléments taint avant un redémarrage.

sub configure_hook{
    my $self = shift;
    ### voir le contenu
    my $ref  = $self->commandline;
    use Data::Dumper;
    print Dumper $ref;
    ### décontamination arbitraire - très risqué
    my @untainted = map {/(.+)/;$1} @$ref;
    $self->commandline(\@untainted)
}

ARRÊT

Chacun des personnages Fork et PreFork prend en charge un arrêt en douceur via le signal QUIT. Lorsqu'un QUIT est reçu, le parent signale aux enfants puis attend leur fermeture.

Tous les personnages de serveur prennent en charge un arrêt en douceur via les signaux TERM et INT.

DÉPLOIEMENT

Depuis la version 2.000, les personnages Fork et PreFork acceptent les signaux TTIN et TTOU. Lorsqu'un TTIN est reçu, max_servers est incrémenté de 1. Si un TTOU est reçu, max_servers est décrémenté de 1. Cela permet d'ajuster le nombre de processus de traitement sans avoir à redémarrer le serveur.

Si log_level est défini sur 3, la nouvelle valeur est affichée dans les logs.

use Net::Server;
