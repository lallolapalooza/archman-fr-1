NOM

Net::OpenSSH - Paquet client SSH Perl implémenté sur OpenSSH

SYNTAXE

use Net::OpenSSH;
my $ssh = Net::OpenSSH->new($host);
$ssh->error and
  die "Impossible d'établir la connexion SSH : ". $ssh->error;
$ssh->system("ls /tmp") or
  die "La commande distante a échoué : " . $ssh->error;
my @ls = $ssh->capture("ls");
$ssh->error and
  die "La commande ls distante a échoué : " . $ssh->error;
my ($out, $err) = $ssh->capture2("find /root");
$ssh->error and
  die "La commande find distante a échoué : " . $ssh->error;
my ($rin, $pid) = $ssh->pipe_in("cat >/tmp/foo") or
  die "La méthode pipe_in a échoué : " . $ssh->error;
print $rin "hello\n";
close $rin;
my ($rout, $pid) = $ssh->pipe_out("cat /tmp/foo") or
  die "La méthode pipe_out a échoué : " . $ssh->error;
while (<$rout>) { print }
close $rout;
my ($in, $out ,$pid) = $ssh->open2("foo");
my ($pty, $pid) = $ssh->open2pty("foo");
my ($in, $out, $err, $pid) = $ssh->open3("foo");
my ($pty, $err, $pid) = $ssh->open3pty("login");
my $sftp = $ssh->sftp();
$sftp->error and die "SFTP a échoué : " . $sftp->error;

DESCRIPTION

Net::OpenSSH est un paquet client shell sécurisé implémenté au-dessus du client binaire OpenSSH ("ssh").

Sous le capot

Ce paquet est implémenté autour de la fonctionnalité de multiplexage présente dans les versions ultérieures d'OpenSSH. Cette fonctionnalité permet d'exécuter plusieurs sessions sur une seule connexion SSH (OpenSSH 4.1 fut le premier à fournir toutes les fonctionnalités requises).

Lorsqu'un nouvel objet Net::OpenSSH est créé, le client OpenSSH "ssh" est lancé en mode maître, établissant une connexion persistante (pour la durée de vie de l'objet) avec le serveur.

Ensuite, chaque fois qu'une nouvelle opération est demandée, un nouveau processus "ssh" est lancé en mode esclave, réutilisant effectivement la connexion SSH maître pour envoyer la requête au côté distant.

Net::OpenSSH contre les modules Net::SSH::.*

Pourquoi devriez-vous utiliser Net::OpenSSH plutôt que l'un des autres clients SSH Perl disponibles ?

Eh bien, voici mon avis (biaisé) :

Net::SSH::Perl n'est plus très bien maintenu de nos jours (mise à jour : un nouveau mainteneur est intervenu, donc cette situation pourrait changer !!!), nécessite un tas de modules (certains très difficiles à installer) pour être raisonnablement efficace et a une API qui est limitée à certains égards.

Net::SSH2 est bien meilleur que Net::SSH::Perl, mais pas encore complètement stable. Il peut être très difficile à installer sur certains systèmes d'exploitation spécifiques et son API est également limitée, de la même manière que Net::SSH::Perl.

Utiliser Net::SSH::Expect, en général, est une mauvaise idée. Gérer l'interaction avec un shell via Expect de manière générique ne peut tout simplement pas être fait de manière fiable.

Net::SSH est juste un wrapper autour de n'importe quelle commande binaire SSH disponible sur la machine. Il peut être très lent car il établit une nouvelle connexion SSH pour chaque opération effectuée.

En comparaison, Net::OpenSSH est un module pure Perl qui n'a aucune dépendance obligatoire (évidemment, en dehors de la nécessité des binaires OpenSSH).

Net::OpenSSH a une interface très "Perlesque". La plupart des opérations sont effectuées d'une manière très similaire à celle des fonctions intégrées de Perl et des modules courants (par exemple, IPC::Open2).

Il est également très rapide. La surcharge introduite par le lancement d'un nouveau processus ssh pour chaque opération n'est pas perceptible (du moins sur ma machine Linux). Le goulot d'étranglement est la latence intrinsèque au protocole, donc Net::OpenSSH est probablement aussi rapide qu'un client SSH peut l'être.

Être basé sur OpenSSH est aussi un avantage : une implémentation du protocole SSH éprouvée, stable, sécurisée (à des niveaux paranoïaques), indispensable et bien maintenue est utilisée.

D'un autre côté, Net::OpenSSH ne fonctionne pas sous Windows, même pas sous Cygwin.

Net::OpenSSH nécessite spécifiquement le client SSH OpenSSH (à ma connaissance, la fonctionnalité de multiplexage n'est disponible sur aucun autre client SSH). Cependant, notez qu'il interagira avec n'importe quel logiciel serveur, pas seulement les serveurs exécutant le "sshd" d'OpenSSH.

Pour l'authentification par mot de passe, IO::Pty doit être installé. D'autres modules et binaires sont également requis pour implémenter des fonctionnalités spécifiques (par exemple Net::SFTP::Foreign, Expect ou rsync(1)).

Net::OpenSSH et Net::SSH2 ne prennent pas en charge la version 1 du protocole SSH.

API

Arguments optionnels

Presque toutes les méthodes de ce paquet acceptent comme premier argument une référence optionnelle à une table d'association contenant des paramètres ("\%opts"). Par exemple, ces deux appels de méthode sont équivalents :

my $out1 = $ssh->capture(@cmd);
my $out2 = $ssh->capture({}, @cmd);

Gestion des erreurs

La plupart des méthodes retournent undef (ou une liste vide) pour indiquer un échec.

La méthode "error" peut toujours être utilisée pour vérifier explicitement les erreurs. Par exemple :

my ($output, $errput) = $ssh->capture2({timeout => 1}, "find /");
$ssh->error and die "ssh a échoué : " . $ssh->error;

Méthodes Net::OpenSSH

Voici les méthodes fournies par le paquet :

Net::OpenSSH->new($host, %opts)
Crée une nouvelle connexion maître SSH

$host peut être un nom d'hôte ou une adresse IP. Il peut également contenir le nom de l'utilisateur, son mot de passe et le numéro de port TCP sur lequel le serveur écoute :

my $ssh1 = Net::OpenSSH->new('jack@foo.bar.com');
my $ssh2 = Net::OpenSSH->new('jack:secret@foo.bar.com:10022');
my $ssh3 = Net::OpenSSH->new('jsmith@2001:db8::1428:57ab'); # IPv6

Les adresses IPv6 peuvent éventuellement être entourées de crochets :

my $ssh4 = Net::OpenSSH->new('jsmith@[::1]:1022');

Cette méthode réussit toujours à retourner un nouvel objet. La vérification des erreurs doit être effectuée explicitement après :

my $ssh = Net::OpenSSH->new($host, %opts);
$ssh->error and die "Impossible de se connecter à $host en ssh : " . $ssh->error;

Si vous rencontrez des problèmes pour connecter Net::OpenSSH à l'hôte distant, lisez le chapitre de dépannage vers la fin de ce document.

Options acceptées :

Nom de connexion
port => $port
Numéro de port TCP sur lequel le serveur est en cours d'exécution
password => $mot_de_passe
Mot de passe fourni par l'utilisateur pour l'authentification.

Notez que l'utilisation de l'authentification par mot de passe dans les scripts automatisés est une très mauvaise idée. Lorsque cela est possible, vous devriez utiliser l'authentification par clé publique à la place.

passphrase => $phrase_de_passe

Utilise la clé stockée dans le chemin de fichier donné pour l'authentification.
gateway => $passerelle
Si l'argument donné est un objet passerelle tel que retourné par la méthode "find_gateway" dans Net::OpenSSH::Gateway, utilisez-le pour vous connecter à l'hôte distant.

S'il s'agit d'une référence à une table d'association, appelez d'abord la méthode "find_gateway".

Par exemple, les fragments de code suivants sont équivalents :

my $gateway = Net::OpenSSH::Gateway->find_gateway(
        proxy => 'http://proxy.corporate.com');
$ssh = Net::OpenSSH->new($host, gateway => $gateway);

et

$ssh = Net::OpenSSH->new($host,
        gateway => { proxy => 'http://proxy.corporate.com'});

proxy_command => $proxy_command
Utilise la commande donnée pour établir la connexion à l'hôte distant (voir "ProxyCommand" sur ssh_config(5)).
batch_mode => 1
Désactive la demande de mot de passe et de phrases secrètes à l'utilisateur.
ctl_dir => $path
Répertoire où le socket de contrôle maître SSH sera créé.

Ce répertoire et ses parents doivent être inscriptibles uniquement par l'utilisateur effectif actuel ou par root, sinon la connexion sera interrompue pour éviter une opération non sécurisée.

Par défaut, "~/.libnet-openssh-perl" est utilisé.

ctl_path => $path
Chemin vers le socket de contrôle maître SSH.

Habituellement, cette option doit être évitée car le module est capable de choisir lui-même un chemin de socket inutilisé. Une exception à cette règle est lorsque la fonctionnalité "external_master" est activée.

Notez que la longueur du chemin est généralement limitée entre 92 et 108 octets, en fonction du système d'exploitation sous-jacent.

ssh_cmd => $cmd
Nom ou chemin complet du binaire OpenSSH "ssh". Par exemple : 
my $ssh = Net::OpenSSH->new($host, ssh_cmd => '/opt/OpenSSH/bin/ssh');
scp_cmd => $cmd
Nom ou chemin complet du binaire OpenSSH "scp".

Par défaut, il est déduit de celui de "ssh".

rsync_cmd => $cmd
Nom ou chemin complet du binaire "rsync". La valeur par défaut est "rsync".
remote_shell => $name
Nom du shell distant. Utilisé pour sélectionner le backend de mise entre guillemets des arguments.
timeout => $timeout
Temps maximum acceptable qui peut s'écouler sans trafic réseau ou autre événement sur les méthodes qui ne sont pas immédiates (par exemple, lors de l'établissement de la connexion SSH maître ou à l'intérieur des méthodes "capture", "system", "scp_get", etc.).

Voir aussi "Timeouts".

kill_ssh_on_timeout => 1
Cette option indique à Net::OpenSSH de tuer le processus esclave SSH local lorsque certaines opérations expirent.

Voir aussi "Timeouts".

strict_mode => 0
Par défaut, la connexion sera interrompue si le chemin vers le socket utilisé pour le multiplexage est jugé non sécurisé (par exemple, si l'un des répertoires parents est inscriptible par d'autres utilisateurs).

Cette option peut être utilisée pour désactiver cette fonctionnalité. À utiliser avec précaution !!!

async => 1
Par défaut, le constructeur attend que le socket de multiplexage soit disponible. Cette option peut être utilisée pour reporter l'attente jusqu'à ce que le socket soit effectivement utilisé.

Par exemple, le code suivant se connecte à plusieurs machines distantes en parallèle :

my (%ssh, %ls);
# plusieurs connexions sont établies en parallèle :
for my $host (@hosts) {
    $ssh{$host} = Net::OpenSSH->new($host, async => 1);
}
# puis pour exécuter une commande sur toutes les machines (séquentiellement) :
for my $host (@hosts) {
    $ssh{$host}->system('ls /');
}
connect => 0
Ne pas lancer le processus SSH maître tout de suite.
master_opts => [...]
Options supplémentaires à passer à la commande "ssh" lors de l'établissement de la connexion maître. Par exemple : 
my $ssh = Net::OpenSSH->new($host,
    master_opts => [-o => "ProxyCommand corkscrew httpproxy 8080 $host"]);
default_ssh_opts => [...]
Options par défaut de la commande SSH esclave pour "open_ex" et les méthodes dérivées.

Par exemple :

my $ssh = Net::OpenSSH->new($host,
    default_ssh_opts => [-o => "ConnectionAttempts=0"]);
forward_agent => 1
forward_agent => 'always'
Active le transfert de l'agent d'authentification.

Lorsque "always" est passé comme argument, le transfert d'agent sera activé par défaut dans tous les canaux créés à partir de l'objet. Sinon, il devra être explicitement demandé lors de l'appel des méthodes de création de canal (c'est-à-dire "open_ex" et ses dérivations).

Cette option ne peut pas être utilisée lors du passage d'une phrase secrète (via "passphrase") pour déverrouiller la clé privée de connexion.

Notez que Net::OpenSSH n'exécutera pas "ssh-agent" pour vous. Cela doit être fait à l'avance et la variable d'environnement "SSH_AUTH_SOCK" doit être définie pour pointer vers l'emplacement approprié.

forward_X11 => 1
Active le transfert du protocole X11

default_stdout_fh => $fh

Par exemple :

open my $stderr_fh, '>>', '/tmp/$host.err' or die ...;
open my $stdout_fh, '>>', '/tmp/$host.log' or die ...;
my $ssh = Net::OpenSSH->new($host, default_stderr_fh => $stderr_fh,
                                   default_stdout_fh => $stdout_fh);
$ssh->error and die "SSH connection failed: " . $ssh->error;
$ssh->scp_put("/foo/bar*", "/tmp")
  or die "scp failed: " . $ssh->error;
default_stdin_file => $fn
default_stdout_file => $fn
default_stderr_file => $fn
Ouvre les noms de fichiers donnés et les utilise comme valeurs par défaut.
master_stdout_fh => $fh

Redirige les flux stdio correspondants du processus SSH maître vers les descripteurs de fichiers donnés.
master_stdout_discard => $bool

Écarte les flux stdio correspondants.
expand_vars => $bool
Active l'expansion des variables à l'intérieur des arguments de commande et des chemins de fichiers.

vars => \%vars
Ensemble initial de variables.
external_master => 1
Au lieu de lancer un nouveau client OpenSSH en mode maître, le module essaie de réutiliser un client existant. "ctl_path" doit également être passé lorsque cette option est définie. Voir aussi "get_ctl_path".

Exemple :

$ssh = Net::OpenSSH->new('foo', external_master => 1, ctl_path = $path);

Lorsque "external_master" est défini, l'argument du nom d'hôte devient facultatif ( 0.0.0.0 est passé à OpenSSH qui ne l'utilise pas du tout).

default_encoding => $encoding

Définit les encodages par défaut. Voir "Data encoding".
password_prompt => $string
password_prompt => $re
Par défaut, lors de l'utilisation de l'authentification par mot de passe, le module s'attend à ce que le côté distant envoie une invite de mot de passe correspondant à "/[?:]/".

Cette option peut être utilisée pour remplacer cette valeur par défaut dans les rares cas où une invite différente est utilisée.

Exemples :

password_prompt => ']'; # pas besoin d'échapper ']'
password_prompt => qr/[:?>]/;
login_handler => \&custom_login_handler
Certains serveurs SSH distants peuvent nécessiter une interaction de connexion/authentification personnalisée non prise en charge nativement par Net::OpenSSH. Dans ce cas, vous pouvez utiliser cette option pour remplacer la logique de connexion par défaut.

La fonction de rappel sera appelée à plusieurs reprises comme "custom_login_handler($ssh, $pty, $data)" où $ssh est l'objet Net::OpenSSH actuel, "pty" un objet IO::Pty attaché au tty du processus SSH esclave, et $data une référence à un scalaire que vous pouvez utiliser à volonté.

Le gestionnaire de connexion doit renvoyer 1 après le processus de connexion.

soit se termine avec succès, soit retourne 0 s'il reste encore quelque chose à faire.

En cas d'erreur, il doit mourir.

Notez que les opérations bloquantes ne doivent pas être effectuées dans le gestionnaire de connexion (du moins si vous souhaitez que les fonctionnalités "async" et "timeout" fonctionnent).

Voir aussi le script d'exemple "login_handler.pl" dans le répertoire "examples".

L'utilisation de cette option est incompatible avec les options "password" et "passphrase", vous devrez gérer vous-même le mot de passe ou la phrase secrète à partir du gestionnaire personnalisé.

master_setpgrp => 1
Lorsque cette option est définie, le processus maître s'exécute dans un groupe de processus différent. Par conséquent, il ne mourra pas lorsque l'utilisateur appuiera sur Ctrl-C dans le terminal.

Afin de permettre au processus SSH maître de demander des informations à l'utilisateur, le module peut le définir comme processus contrôlant le terminal lors de l'établissement de la connexion (en utilisant "tcsetpgrp" en POSIX). Ensuite, le processus contrôlant le terminal est réinitialisé.

Cette fonctionnalité est hautement expérimentale. Veuillez signaler tout problème que vous pourriez rencontrer.

master_pty_force => 1
Par défaut, Net::OpenSSH attache le processus SSH maître à un pty uniquement lorsqu'un type d'authentification interactive est demandé. Si ce drapeau est défini, un pty sera toujours attaché.

Cela permet d'obtenir de meilleurs diagnostics pour certains types d'erreurs (comme, par exemple, les mauvaises clés d'hôte) et permet également de récupérer le journal du pty en utilisant get_master_pty_log.

$ssh->error
Retourne la condition d'erreur de la dernière opération effectuée.

La valeur retournée est une variable duale comme $! (voir "$!" dans perlvar) qui affiche un message informatif lorsqu'elle est utilisée dans un contexte de chaîne de caractères ou un numéro d'erreur dans un contexte numérique (les codes d'erreur apparaissent dans Net::OpenSSH::Constants).

$ssh->get_master_pty_log
Afin de gérer l'authentification par mot de passe ou la saisie de la phrase secrète pour une clé privée, Net::OpenSSH peut exécuter le processus SSH maître attaché à un pty.

Dans ce cas, et après qu'un appel au constructeur a retourné une erreur de connexion, cette méthode peut être appelée pour récupérer la sortie capturée au niveau du pty (le journal est supprimé lorsque la connexion est établie avec succès).

Toutes les données consommées depuis le pty par les gestionnaires de connexion personnalisés seront manquantes dans le journal retourné.

$ssh->get_user
$ssh->get_host
$ssh->get_port
Retourne les paramètres de connexion SSH correspondants.
$ssh->get_ctl_path
Retourne le chemin vers le socket où le processus maître OpenSSH écoute les nouvelles connexions multiplexées.
($in, $out, $err, $pid) = $ssh->open_ex(\%opts, @cmd)
Note : il s'agit d'une méthode de bas niveau qui, probablement, vous n'avez pas besoin d'utiliser !

Cette méthode démarre la commande @cmd sur la machine distante en créant de nouveaux tuyaux pour les canaux d'E/S comme spécifié dans la table de hachage %opts.

Si @cmd est omis, le shell de l'utilisateur distant est exécuté.

Retourne quatre valeurs, les trois premières ($in, $out et $err) correspondent au côté local des tuyaux créés (elles peuvent être undef) et la quatrième ($pid) au PID du nouveau processus esclave SSH. Une liste vide est retournée en cas d'échec.

Notez que "waitpid" doit être utilisé par la suite pour récupérer le processus esclave SSH.

Options acceptées :

stdin_pipe => 1
Crée un nouveau tuyau et connecte le côté lecture au flux stdin du processus distant. Le côté écriture est retourné comme première valeur ($in).
stdin_pty => 1
Similaire à "stdin_pipe", mais au lieu d'un tuyau régulier, il utilise un pseudo-tty (pty).

Notez que sur certains systèmes d'exploitation (par exemple, HP-UX, AIX), les ttys ne sont pas fiables. Ils peuvent déborder lorsque des blocs importants sont écrits ou lorsque les données sont écrites plus rapidement qu'elles ne sont lues.

stdin_fh => $fh
Duplique $fh et l'utilise comme flux stdin du processus distant.
stdin_file => $filename
stdin_file => \@open_args
Ouvre le fichier du nom donné pour lecture et l'utilise comme flux stdin du processus distant.

Si une référence de tableau est passée, son contenu est utilisé comme arguments pour l'appel open sous-jacent. Par exemple :

$ssh->system({stdin_file => ['-|', 'gzip -c -d file.gz']}, $rcmd);
stdin_discard => 1
Utilise /dev/null comme flux stdin du processus distant.
stdout_pipe => 1
Crée un nouveau tuyau et connecte le côté écriture au flux stdout du processus distant. Le côté lecture est retourné comme deuxième valeur ($out).
stdout_pty => 1
Connecte le flux stdout du processus distant au pseudo-tty. Cette option nécessite que "stdin_pty" soit également défini.
stdout_fh => $fh
Duplique $fh et l'utilise comme flux stdout du processus distant.
stdout_file => $filename
stdout_file => \@open_args
Ouvre le fichier du nom donné et redirige stdout là-bas.
stdout_discard => 1
Utilise /dev/null comme flux stdout du processus distant.
stdinout_socket => 1
Crée une nouvelle paire de sockets, attache les flux stdin et stdout du processus esclave SSH à une extrémité et retourne l'autre comme première valeur ($in) et undef pour la seconde ($out).

Exemple :

my ($socket, undef, undef, $pid) = $ssh->open_ex({stdinout_socket => 1},
                                                 '/bin/netcat $dest');

Voir aussi "open2socket".

stdinout_dpipe => $cmd
stdinout_dpipe => \@cmd
Exécute la commande donnée localement en attachant ses flux stdio à ceux de la commande SSH distante. Conceptuellement, cela équivaut à la commande shell dpipe(1).
stderr_pipe => 1
Crée un nouveau tuyau et connecte le côté écriture au flux stderr du processus distant. Le côté lecture est retourné comme troisième valeur ($err).

Exemple :

my $pid = $ssh->open_ex({stdinout_dpipe => 'vncviewer -stdio'},
                        x11vnc => '-inetd');
stderr_fh => $fh
Duplique $fh et l'utilise comme flux stderr du processus distant.
stderr_file => $filename
Ouvre le fichier du nom donné et y redirige stderr.
stderr_to_stdout => 1
Fait pointer stderr vers stdout.
tty => $bool
Indique à "ssh" d'allouer un pseudo-tty pour le processus distant. Par défaut, un tty est alloué si le flux stdin de la commande distante est attaché à un tty.

Lorsque ce drapeau est défini et que stdin n'est pas attaché à un tty, les processus SSH maître et esclave peuvent générer des avertissements sans conséquence concernant des opérations tty échouées. Ceci est dû à un bug présent dans les anciennes versions d'OpenSSH.

close_slave_pty => 0
Lorsqu'un pseudo pty est utilisé pour le flux stdin, le côté esclave est automatiquement fermé sur le processus parent après le fork de la commande ssh.

Cette option désactive cette fonctionnalité, de sorte que le pty esclave peut être accédé sur le processus parent comme "$pty->slave". Il devra être fermé explicitement (voir IO::Pty)

quote_args => $bool
Voir "Shell quoting" ci-dessous.
remote_shell => $shell
Définit le shell distant. Permet de modifier le mécanisme de citation des arguments d'une manière spécifique à la commande.

Cela peut être utile lors de l'interaction avec une machine Windows où l'analyse des arguments peut être effectuée au niveau de la commande de manière personnalisée.

Exemple :

$ssh->system({remote_shell => 'MSWin'}, echo => $line);
$ssh->system({remote_shell => 'MSCmd,MSWin'}, type => $file);
forward_agent => $bool
Active/désactive le transfert de l'agent d'authentification.

Cette option ne peut être utilisée que lorsque le transfert d'agent a été précédemment demandé dans le constructeur.

forward_X11 => $bool
Active/désactive le transfert du protocole X11.

Cette option ne peut être utilisée que lorsque le transfert X11 a été précédemment demandé dans le constructeur.

ssh_opts => \@opts
Liste des options supplémentaires pour le
"ssh" commande.

Cette fonctionnalité doit être utilisée avec précaution, car les options fournies ne sont en aucun cas vérifiées par le module et pourraient interférer avec celui-ci.

tunnel => $bool
Au lieu d'exécuter une commande sur l'hôte distant, cette option demande à Net::OpenSSH de créer un tunnel TCP. Les arguments deviennent l'IP et le port de destination, ou le chemin distant pour un socket Unix.

Exemple:

my ($in, $out, undef, $pid) = $ssh->open_ex({tunnel => 1}, $IP, $port);
my ($in, $out, undef, $pid) = $ssh->open_ex({tunnel => 1}, $socket_path);

Voir aussi "Tunnels".

subsystem => $bool
Demande une connexion à un sous-système SSH. Le nom du sous-système doit être passé en argument, comme dans l'exemple suivant : 
my $s = $ssh->open2socket({subsystem => 1}, 'netconf');
encoding => $encoding
argument_encoding => $encoding
Définit les encodages. Voir "Data encoding".

Exemple d'utilisation :

# similaire à la fonction open2 d'IPC::Open2 :
my ($in_pipe, $out_pipe, undef, $pid) =
    $ssh->open_ex( { stdin_pipe => 1,
                     stdout_pipe => 1 },
                   @cmd )
    or die "open_ex a échoué : " . $ssh->error;
# effectuer des IO via $in/$out

Citation de shell

Par défaut, lors de l'invocation de commandes distantes, ce module tente d'imiter la fonctionnalité de "system" de Perl en matière de traitement des arguments. La description de "system" dans perlfunc :

Le traitement des arguments dépend du nombre d'arguments. S'il y a plus d'un argument dans LIST, ou si LIST est une liste avec plus d'une valeur, le programme donné par le premier élément de la liste est exécuté avec les arguments donnés par le reste de la liste. S'il n'y a qu'un seul argument scalaire, on vérifie s'il contient des métacaractères de shell, et s'il y en a, l'argument entier est passé au shell du système pour traitement (il s'agit de « /bin/sh -c » sur les plates-formes Unix, mais cela varie sur d'autres plates-formes).

Par exemple, la méthode "system" de Net::OpenSSH :

$ssh->system("ls -l *");
$ssh->system('ls', '-l', '/');

Le premier appel passe l'argument sans modification à ssh et l'exécute côté distant via le shell qui interprète les métacaractères.

Le second appel échappe tous les métacaractères de shell de sorte qu'il soit effectivement équivalent à l'appel de la commande directement et non via le shell.

Comme le protocole Secure Shell ne fournit pas ce mode de fonctionnement et échappe toujours un nouveau shell où la commande donnée est exécutée, Net::OpenSSH cite tous les métacaractères de shell dans la liste des commandes.

Toutes les méthodes qui invoquent une commande distante (system, open_ex, etc.) acceptent l'option "quote_args" qui permet de forcer ou de désactiver la citation des arguments du shell.

Par exemple :

$ssh->system({quote_args => 1}, "/chemin avec espaces/bin/foo");

fonctionne correctement pour gérer les espaces dans le chemin du programme.

Le mécanisme de citation de shell implémente quelques extensions (par exemple, la redirection vers /dev/null côté distant) qui peuvent être désactivées avec l'option "quote_args_extended" :

$ssh->system({ stderr_discard => 1,
               quote_args => 1, quote_args_extended => 0 },
             @cmd);

L'option "quote_args" peut également être utilisée pour désactiver la citation lorsqu'il y a plus d'un argument. Par exemple, pour obtenir un motif développé par le shell distant :

$ssh->system({quote_args => 0}, 'ls', '-l', "/tmp/files_*.dat");

La méthode "shell_quote" peut être utilisée pour citer certains arguments et en laisser d'autres inchangés :

$ssh->system({quote_args => 0},
             $ssh->shell_quote('ls', '-l'),
             "/tmp/files_*.dat");

Délais d'attente

Pour arrêter les processus distants lorsqu'ils dépassent le délai d'attente, la meilleure façon serait d'envoyer des signaux via la connexion SSH conformément au standard du protocole. Cependant, OpenSSH n'implémente pas cette fonctionnalité, Net::OpenSSH doit donc recourir à des méthodes imparfaites :

  • fermer les flux d'E/S de l'écoute distante

    La fermeture des flux d'entrée standard (STDIN) et de sortie standard (STDOUT) d'un processus distant inactif amènera le processus à tenter d'accéder à l'un d'eux et déclenchera un SIGPIPE.

    Les processus distants peuvent ne pas accéder à STDIN ou STDOUT, mais Net::OpenSSH ne peut fermer ces canaux que lorsqu'il les capture, cette approche ne fonctionne donc pas toujours.

  • terminer le processus SSH local

    Cette action peut laisser le processus distant en vie, créant un processus orphelin distant, Net::OpenSSH ne l'utilise donc pas, sauf si l'option de construction "kill_ssh_on_timeout" est définie.

Heureusement, les futures versions d'OpenSSH pourront signaler les processus distants via le canal mux.

Expansion des variables

La fonctionnalité d'expansion des variables permet de définir des variables qui s'étendent automatiquement dans les arguments de commande et les chemins de fichiers.

Cette fonctionnalité est désactivée par défaut et est utilisée avec des modules tels que Net::OpenSSH::Parallel et d'autres similaires.

Les variables sont délimitées par une paire de signes de pourcentage ("%"), par exemple "%HOST%". De plus, deux signes de pourcentage consécutifs sont remplacés par un seul.

Les variables spéciales "HOST", "USER" et "PORT" sont conservées en interne par le module et prennent les valeurs évidentes.

L'expansion des variables se produit avant l'expansion des commandes dans le shell (voir "Expansion des commandes dans le shell").

Un exemple d'utilisation :

my $ssh = Net::OpenSSH->new('server.foo.com', expand_vars => 1);
$ssh->set_var(ID => 42);
$ssh->system("ls >/tmp/ls.out-%HOST%-%ID%");

redirigera la sortie de la commande "ls" vers "/tmp/ls.out-server.foo.com-42" sur l'hôte distant.

Ports de tunnel

En plus d'exécuter des commandes sur l'hôte distant, Net::OpenSSH permet également de créer des ports de tunnel vers des machines distantes accessibles depuis le serveur SSH.

Cette fonctionnalité est fournie via l'option "tunnel" de la méthode "open_ex", ainsi que via les méthodes wrapper "open_tunnel" et "capture_tunnel", et d'autres là où cela est approprié.

Exemple :

$ssh->system({tunnel => 1,
              stdin_data => "GET / HTTP/1.0\r\n\r\n",
              stdout_file => "/tmp/$server.res"},
             $server, 80)
    or die "impossible de récupérer la page : " . $ssh->error;

ou pour capturer la sortie de plusieurs requêtes en parallèle :

my @pids;
for (@servers) {
  my $pid = $ssh->spawn({tunnel => 1,
                         stdin_file => "/tmp/request.req",
                         stdout_file => "/tmp/$_.res"},
                        $_, 80);
  if ($pid) {
    push @pids, $pid;
  }
  else {
    warn "impossible de lancer le processus de tunnel vers $_ : " . $ssh->error;
  }
}
waitpid ($_, 0) for (@pids);

En outre, pour créer un tunnel, un nouveau processus "ssh" est généré avec l'option "-W${address}:${port}" (disponible à partir d'OpenSSH 5.4), qui le dirige vers l'adresse distante donnée. Contrairement à l'utilisation de "ssh" avec l'option "-L" pour créer un tunnel, aucun port TCP n'est ouvert côté local, cette opération est donc totalement sécurisée.

Le PID du nouveau processus est retourné par les méthodes nommées. Vous devez faire un `waitpid` sur le PID une fois que les gestionnaires de canaux pour le côté local ont été fermés.

Il est nécessaire qu'OpenSSH version 5.4 ou supérieure soit installée pour que la fonctionnalité de tunnel fonctionne. Notez également que la redirection de port peut être administrativement interdite côté serveur (voir sshd(8) et sshd_config(5) ou la documentation fournie par votre fournisseur de serveur SSH).

Tunnels vers des sockets UNIX

Lors de la connexion à des hôtes exécutant une version récente d'OpenSSH sshd, il est également possible d'ouvrir des connexions vers des sockets UNIX.

Par exemple :

my $response = $ssh->capture({tunnel => 1, stdin_data => $request },
                             "/tmp/socket-foo");

Actuellement, cette fonctionnalité nécessite un client OpenSSH patché. Le patch est disponible sous le nom de "patches/openssh-fwd-stdio-to-streamlocal-1.patch".

Redirections de ports

Net::OpenSSH n'offre pas de support direct pour la gestion des redirections de ports entre le serveur et le client. Cependant, cela peut être facilement fait en passant des options personnalisées aux méthodes.

Par exemple, les options de tunnel peuvent être passées au constructeur :

my $ssh = Net::OpenSSH->new(...
                  master_opts => -Llocalhost:1234:localhost:3306');

Vous pouvez également modifier les redirections de ports pour une connexion SSH en cours à l'aide de la commande Control :

# configurer un tunnel :
$ssh->system({ssh_opts => ['-O','forward',
                           '-L127.0.0.1:12345:127.0.0.1:3306']});
# annuler le tunnel :
$ssh->system({ssh_opts => ['-O', 'cancel',
                           '-L127.0.0.1:12345:127.0.0.1:3306']});

Encodage des données

Net::OpenSSH offre un certain support pour convertir de manière transparente les données envoyées ou reçues par le serveur distant en représentation interne Unicode de Perl.

Les méthodes qui prennent en charge cette fonctionnalité sont celles qui déplacent des données entre les structures Perl (par exemple, "capture", "capture2", "capture_tunnel" et les méthodes prenant en charge l'option "stdin_data"). Les données accessibles via des tuyaux, des sockets ou des redirections ne sont pas affectées par les options d'encodage.

Il est également possible de définir l'encodage de la commande et des arguments passés au serveur distant sur la ligne de commande.

Par défaut, si aucune option d'encodage n'est fournie dans le constructeur ou dans les appels de méthode, Net::OpenSSH n'effectuera aucune transformation d'encodage, traitant les données comme "latin1".

Lorsque les données ne peuvent pas être converties entre la représentation interne de Perl et l'encodage sélectionné dans une méthode Net::OpenSSH, une erreur "OSSH_ENCODING_ERROR" sera levée.

Les options d'encodage prises en charge sont les suivantes :

stream_encoding => $encoding
définit l'encodage des données reçues et envoyées dans les méthodes de capture.
argument_encoding => $encoding
définit l'encodage des arguments de la ligne de commande.
encoding => $encoding
définit à la fois "argument_encoding" et "stream_encoding"

Le constructeur accepte également "default_encoding", "default_stream_encoding" et "default_argument_encoding" qui définissent les valeurs par défaut.

Détournement de la fonctionnalité "new"

Lorsqu'une référence de code est installée dans $Net::OpenSSH::FACTORY, les appels à "new" sont dirigés à travers elle.

Cette fonctionnalité peut être utilisée pour transporter le flux d'entrée et de sortie des processus.

apparent implementation of connection caching, par exemple :

my $old_factory = $Net::OpenSSH::FACTORY;
my %cache;
sub factory {
  my ($class, %opts) = @_;
  my $signature = join("\0", $class, map { $_ => $opts{$_} }, sort keys %opts);
  my $old = $cache{signature};
  return $old if ($old and $old->error != OSSH_MASTER_FAILED);
  local $Net::OpenSSH::FACTORY = $old_factory;
  $cache{$signature} = $class->new(%opts);
}
$Net::OpenSSH::FACTORY = \&factory;

... et je suis sûr que cela peut être détourné de plusieurs autres manières !

mod_perl et mod_perl2

mod_perl et mod_perl2 lient STDIN et STDOUT à des objets qui ne sont pas soutenus par de vrais descripteurs de fichiers au niveau du système d'exploitation. Net::OpenSSH échouera si l'un de ces descripteurs est utilisé explicitement ou implicitement lors de l'appel à une commande distante.

La solution consiste à les rediriger vers "/dev/null" ou vers un fichier :

open my $def_in, '<', '/dev/null' or die "impossible d'ouvrir /dev/null";
my $ssh = Net::OpenSSH->new($host,
                            default_stdin_fh => $def_in);
my $out = $ssh->capture($cmd1);
$ssh->system({stdout_discard => 1}, $cmd2);
$ssh->system({stdout_to_file => '/tmp/output'}, $cmd3);

Notez également que d'un point de vue sécurité, exécuter "ssh" depuis le processus du serveur web n'est pas une bonne idée. Un attaquant exploitant un bug d'Apache pourrait accéder aux clés et mots de passe SSH et obtenir un accès illimité aux systèmes distants.

Si possible, utilisez une file d'attente (comme TheSchwartz) ou tout autre mécanisme pour exécuter les commandes ssh depuis un autre processus exécuté sous un compte utilisateur différent.

Assurez-vous au minimum que "~www-data/.ssh" (ou similaire) n'est pas accessible via le serveur web !

AnyEvent (et cadriciels similaires)

Net::OpenSSH fournit toute la fonctionnalité nécessaire pour être intégré dans des cadriciels de programmation orientés événement tels que AnyEvent ou IO::Async de la manière suivante :

1. Créer un objet Net::OpenSSH déconnecté :
my $ssh = Net::OpenSSH->new($host, async => 1, ...);
2. Laisser l'objet se connecter à l'hôte distant :
Utiliser un minuteur pour appeler la méthode "wait_for_master" en mode asynchrone de manière répétée jusqu'à ce qu'elle renvoie une valeur vraie indiquant le succès.

De plus, l'état d'erreur de l'objet doit être vérifié après chaque appel afin de détecter les connexions échouées. Par exemple :

my $ssh = Net::OpenSSH->new(..., async => 1);
my $w;
$w = AE::timer 0.1, 0.1, sub {
  if ($ssh->wait_for_master(1)) {
    # la connexion a été établie !
    # les commandes distantes peuvent maintenant être exécutées
    undef $w;
    on_ssh_success(...);
  }
  elsif ($ssh->error) {
    # la connexion ne peut pas être établie
    undef $w;
    on_ssh_failure(...);
  }
}
3. Utiliser le cadriciel d'événements pour lancer les processus distants :
Appeler Net::OpenSSH "make_remote_command" pour construire des commandes qui peuvent être exécutées en utilisant les mécanismes réguliers du cadriciel pour lancer des commandes externes.

La vérification des erreurs doit également être effectuée à ce stade car la connexion SSH pourrait être rompue.

Par exemple :

if (defined(my $cmd = $ssh->make_remote_command(echo => 'hello!')) {
  AnyEvent::Util::run_cmd($cmd, %run_cmd_opts);
}
else {
  # quelque chose s'est mal passé !
}

Alternativement, l'une des méthodes "open*" fournies par Net::OpenSSH pourrait également être utilisée pour lancer des commandes distantes.

4. Une fois terminé, déconnecter de manière asynchrone
Après avoir lancé une déconnexion asynchrone avec disconnect(1), appelez répétitivement "wait_for_master" jusqu'à obtenir une valeur définie mais fausse : 
$ssh->disconnect(1);
my $w; $w = AE::timer 0.1, 0.1, sub {
  my $res = $ssh->wait_for_master(1);
  if (defined $res && !$res) {
    undef $w;
    undef $ssh;
  }
};

Faites attention à ne pas laisser l'objet $ssh sortir de la portée tant que la déconnexion n'est pas terminée, sinon son destructeur attendra et bloquera votre programme jusqu'à ce que la déconnexion soit terminée.

DÉPANNAGE

Généralement, Net::OpenSSH fonctionne sans problème, mais lorsqu'il échoue, certains utilisateurs ont du mal à trouver la cause du problème. Ce mini-guide de dépannage devrait vous aider à le trouver et à le résoudre.

1 - Vérifier le message d'erreur
Ajoutez dans votre script, après l'appel au constructeur Net::OpenSSH, une vérification d'erreur : 
$ssh = Net::OpenSSH->new(...);
$ssh->error and die "connexion SSH échouée : " . $ssh->error;

Le message d'erreur indiquera ce qui s'est mal passé.

2 - Vérifier les paramètres de connexion
Croyez-le ou non, passer de mauvais paramètres à Net::OpenSSH est l'une des principales causes d'échec, alors vérifiez que vous utilisez les bons paramètres.

Spécifiquement, si vous les obtenez de l'extérieur, assurez-vous qu'ils n'ont pas d'espaces supplémentaires ou de nouvelles lignes attachées (avez-vous besoin de "chomp" ?).

Les mots de passe et les URIs peuvent contenir des caractères "$" ou "@". Si vous les avez codés en dur dans votre script, vérifiez qu'ils sont correctement cités (et d'ailleurs, utilisez "strict").

3 - Version d'OpenSSH
Assurez-vous que vous avez une version de "ssh" suffisamment récente : 
$ ssh -V
OpenSSH_5.1p1 Debian-5, OpenSSL 0.9.8g 19 Oct 2007

OpenSSH version 4.1 a été le premier à prendre en charge la fonctionnalité de multiplexage et est le minimum requis par le module pour fonctionner. Je vous conseille d'utiliser la dernière version d'OpenSSH (actuellement 7.5).

L'option de constructeur "ssh_cmd" vous permet de sélectionner le binaire "ssh" à utiliser. Par exemple :

$ssh = Net::OpenSSH->new($host,
                         ssh_cmd => "/opt/OpenSSH/5.8/bin/ssh")

Certains fournisseurs de matériel (par exemple, Sun, euh... Oracle) incluent des versions personnalisées d'OpenSSH groupées avec le système d'exploitation. En principe, Net::OpenSSH devrait fonctionner avec ces clients SSH tant qu'ils sont dérivés d'une version d'OpenSSH suffisamment récente. Quoi qu'il en soit, mon conseil est d'utiliser le vrai logiciel OpenSSH si vous le pouvez !

4 - Exécuter ssh depuis la ligne de commande
Vérifiez que vous pouvez vous connecter à l'hôte distant en utilisant les mêmes paramètres que ceux que vous passez à Net::OpenSSH. En particulier, assurez-vous que vous exécutez "ssh" en tant que le même utilisateur local.

Si vous exécutez votre script depuis un serveur web, l'utilisateur serait probablement "www", "apache" ou quelque chose de similaire.

Les problèmes courants sont :

  • La clé publique de l'hôte distant n'est pas présente dans le fichier known_hosts.

    Le protocole SSH utilise des clés publiques pour identifier les hôtes distants afin qu'ils ne puissent pas être remplacés par des tiers malveillants.

    Pour OpenSSH, généralement la clé publique du serveur est stockée dans "/etc/s

    • "/etc/ssh/ssh_host_dsa_key.pub" ou "/etc/ssh/ssh_host_rsa_key.pub" et quelle clé doit être copiée dans le fichier "~/.ssh/known_hosts" de la machine locale (d'autres implémentations SSH pourraient utiliser d'autres emplacements de fichiers).
    • La clé publique de l'hôte distant dans le fichier des connus est incorrecte.

      C'est un autre problème courant qui se produit lorsqu'un serveur est remplacé ou redémarré à partir de zéro et que sa clé publique change pour être différente de celle installée dans le fichier des connus.

      La façon la plus simple de résoudre ce problème est de supprimer manuellement l'ancienne clé du fichier des connus à l'aide de n'importe quel éditeur, puis de se connecter au serveur en répondant "yes" lorsqu'on vous demande la nouvelle clé.

    • Les autorisations incorrectes sur le répertoire "~/.ssh" ou son contenu.

      Le client OpenSSH effectue plusieurs vérifications sur les autorisations du répertoire "~/.ssh" et son contenu et refuse de les utiliser lorsqu'ils sont mal configurés. Consultez la section FILES de la page ssh(1) du man.

    • Configuration incorrecte pour l'authentification par mot de passe ou par clé publique.

      Vérifiez que vous utilisez le bon mot de passe ou que la clé publique de l'utilisateur est correctement installée sur le serveur.

    5 - vérifications de sécurité sur le socket de multiplexage
    Net::OpenSSH effectue quelques vérifications de sécurité sur le répertoire où le socket de multiplexage doit être placé pour s'assurer qu'il ne peut pas être accédé par d'autres utilisateurs.

    L'emplacement par défaut du socket de multiplexage est sous "~/.libnet-openssh-perl". Il peut être modifié en utilisant les arguments "ctl_dir" et "ctl_path" du constructeur de classe.

    Les exigences pour ce répertoire et ses parents sont :

    • Ils doivent tous appartenir à l'utilisateur qui exécute le script ou à root.
    • Ils doivent avoir un seuil d'autorisations de 0755 ou plus restrictif, de sorte que personne d'autre ne puisse y effectuer d'opérations d'écriture.

    L'option du constructeur "strict_mode" désactive ces vérifications de sécurité, mais ne doit pas être utilisée à moins que vous ne compreniez ses implications.

    6 - le système de fichiers doit supporter les sockets
    Certains systèmes de fichiers (comme FAT ou AFS, par exemple) ne supportent pas le placement de sockets à l'intérieur.

    Assurez-vous que le chemin "ctl_dir" n'est pas à l'intérieur de ces systèmes de fichiers.

DÉBOGAGE

Le débogage interne de Net::OpenSSH est contrôlé par la variable $Net::OpenSSH::debug. Chaque bit de cette variable active le débogage de certains sous-systèmes comme suit :

bit 1 - erreurs
Affiche les changements dans l'attribut interne de l'objet où les erreurs sont stockées.
bit 2 - ctl_path
Affiche les informations sur le calcul de ctl_path et les tests effectués sur ce répertoire pour décider s'il est sûr d'y placer le socket de multiplexage.
bit 4 - connexion
Affiche les informations sur l'établissement de nouvelles connexions maître.
bit 8 - commandes et arguments
Affiche les commandes et les arguments de chaque appel système/exec.
bit 16 - exécution de commandes
Affiche des informations sur la progression de l'exécution des commandes.
bit 32 - destruction
Affiche des informations sur la destruction des objets Net::OpenSSH et la fin des processus maître SSH.
bit 64 - boucle_IO
Affiche des informations sur la progression de la boucle_IO dans les opérations de capture.
bit 128 - hexadumps
Génère des hexadumps des informations circulant sur les canaux SSH pendant les captures.
bit 512 - suivi du processus maître au niveau du système d'exploitation
Utilise le module Net::OpenSSH::OSTracer pour suivre le processus maître SSH au niveau du système d'exploitation.

Par exemple, pour activer tous les indicateurs de débogage, vous pouvez utiliser :

$Net::OpenSSH::debug = ~0;

Notez que la signification des indicateurs et les informations générées sont uniquement destinées au débogage du module et peuvent changer sans préavis entre les versions.

Si vous utilisez l'authentification par mot de passe, l'activation du débogage pour IO::Tty peut également afficher des informations intéressantes :

$IO::Tty::DEBUG = 1;

Enfin, par défaut, la sortie de débogage est envoyée à "STDERR". Vous pouvez la modifier en pointant $Net::OpenSSH::debug_fh vers un autre descripteur de fichier. Par exemple :

BEGIN {
  open my $out, '>', '/tmp/debug.txt or warn $!;
  $Net::OpenSSH::debug_fh = $out;
  $Net::OpenSSH::debug = -1;
}

SÉCURITÉ

Ce module est-il sûr ?

Oui ? Eh bien, il essaie de l'être !

D'un point de vue de la sécurité, l'objectif de ce module est d'être aussi sûr que OpenSSH, votre système d'exploitation, votre shell et votre environnement en général.

Il ne prend aucune mesure de complaisance juste pour vous faciliter la vie si cela implique de diminuer le niveau de sécurité (par exemple, désactiver "StrictHostKeyChecking" par défaut).

Dans les fonctionnalités de code qui ne sont pas simplement des proxys vers OpenSSH, le module tente de maintenir les mêmes normes de sécurité qu'OpenSSH (par exemple, vérifier les autorisations des répertoires et des fichiers lors du placement du socket de multiplexage).

D'un autre côté, en suivant la philosophie d'OpenSSH, le module permet de désactiver presque (tout ?) de ces mesures de sécurité. Mais ce n'est pas parce qu'il le permet que c'est une bonne idée de le faire !

Si vous êtes un programmeur débutant ou un utilisateur de SSH, et qu'en cherchant sur Google vous avez trouvé un paramètre que vous ne comprenez pas mais qui semble résoudre vos problèmes de connexion... croyez-moi, il est probable que ce soit une mauvaise idée de l'utiliser ! Demandez à quelqu'un qui connaît vraiment le sujet !

Pour être clair, si votre code contient l'un des mots-clés de la liste suivante (et que vous ne savez pas pourquoi), vous endommagez probablement la sécurité du protocole SSH :

strict_mode
StrictHostKeyChecking
UserKnownHostsFile

D'autres aspects de sécurité dont vous pourriez être conscient sont :

Mode-taint
Le module prend en charge le mode-taint.

Si vous êtes dans un environnement exposé, vous devriez activer ce mode dans votre script pour capturer toute commande non validée exécutée côté distant.

Environnements-web
C'est une mauvaise idée d'établir des connexions SSH depuis votre serveur web car si celui-ci est compromis, l'attaquant pourrait utiliser les identifiants de votre script pour se connecter à l'hôte distant et faire ce qu'il veut.
Exécution de commandes
Le module peut gérer le quotation des commandes et des arguments de manière flexible et puissante.

C'est une fonctionnalité que vous devriez utiliser car elle réduit la probabilité qu'un attaquant puisse injecter et exécuter des commandes arbitraires sur l'hôte distant (et même pour les scripts non exposés, il est toujours recommandé d'activer le quotation des arguments).

Cependant, gardez à l'esprit que le quotation des arguments n'est qu'un hack pour émuler la fonction d'invocation sans shell des fonctions Perl comme "system" et similaires. Il pourrait y avoir des bugs dans le code de quotation, votre shell pourrait avoir des règles de quotation différentes de celles des cas extrêmes d'un problème ou autre. Si votre script est exposé à l'extérieur, vous devriez examiner vos entrées et limiter ce que vous acceptez comme valide.

[* même si c'est une partie du module testée de manière plus intensive !]

Shellshock
(voir Shellshock http://en.wikipedia.org/wiki/Shellshock_%28software_bug%29)

Lors de l'exécution de commandes locales, le module évite toujours d'appeler le shell, il n'est donc pas affecté par Shellshock.

Cependant, certaines commandes ("scp", "rsync" et "ssh" lors de l'utilisation de l'option "ProxyCommand") appellent d'autres commandes sous le shell de l'utilisateur. Cela ouvre la porte à l'exploitation de Shellshock local.

L'invocation du shell côté distant est inévitable en raison de l'architecture du protocole.

Par défaut, SSH n'envoie pas de variables d'environnement, mais certaines distributions Linux modifient explicitement la configuration par défaut d'OpenSSH pour autoriser l'envoi et l'acceptation de certaines spécifiques (par exemple, "LANG" et "LC_*" sur Debian et ses dérivés, et Fedora fait de même). Cela ouvre également la porte à l'exploitation de Shellshock.

Notez que le shell utilisé pour invoquer des commandes n'est pas "/bin/sh" mais le shell de l'utilisateur configuré dans "/etc/passwd", PAM ou tout système d'authentification utilisé sur le système local ou distant. Les utilisateurs Debian, ne vous inquiétez pas d'être affectés car leur "/bin/sh" pointe vers "dash" !

Questions fréquentes sur le module :

Connexion aux commutateurs, routeurs, etc.
Q : Je ne peux pas exécuter la méthode "system", "capture", etc., lorsque je me connecte à certains routeurs, commutateurs, etc. Qu'est-ce que je fais de mal ?

R : Le protocole SSH permet deux modes de fonctionnement : mode commande et mode interactif.

Le mode commande est conçu pour exécuter des commandes individuelles sur l'hôte distant. Il ouvre un canal SSH entre les deux hôtes, demande à l'ordinateur distant d'exécuter une commande donnée, et le ferme une fois terminé. C'est ce que vous obtenez, par exemple, lorsque vous exécutez quelque chose comme...

$ ssh my.unix.box cat foo.txt

... et c'est aussi le mode dans lequel Net::OpenSSH exécute des commandes sur l'hôte distant.

Le mode interactif lance un shell sur les hôtes distants avec ses flux d'entrée/sortie redirigés vers ceux des flux locaux, permettant à l'utilisateur d'interagir de manière transparente avec celui-ci.

Certains appareils (comme probablement celui que vous utilisez) n'exécutent pas un shell standard et général (par exemple, "bash", "csh" ou "ksh"), mais des programmes personnalisés spécifiquement pour configurer l'appareil.

Normalement, le serveur SSH exécuté par ces appareils ne prend pas en charge le mode commande. Il attaque inconditionnellement le shell limité à toute connexion SSH entrante et attend que l'utilisateur entre des commandes via le flux stdin redirigé.

La seule façon de contourner cette limitation est de faire en sorte que votre script communique avec le shell limité (1- ouvrir une nouvelle session SSH, 2- attendre l'invite du shell, 3- envoyer une commande, 4- lire la sortie jusqu'à atteindre l'invite du shell, répéter à partir de 3). L'outil le plus approprié à cet effet est probablement Expect, utilisé seul ou en combinaison avec Net::OpenSSH (voir "Expect").

Certains appareils prennent en charge le mode commande mais n'acceptent qu'une seule instruction par connexion. Dans ce cas, l'utilisation d'Expect est probablement également la meilleure option.

Maintenant, il y a un nouvel acteur : Net::CLI::Interact, qui pourrait être plus approprié qu'Expect, et Net::Appliance::Session pour travailler spécifiquement avec des appareils réseau.

Connexion échouée
Q : Je n'arrive pas à faire fonctionner le module pour me connecter à l'hôte distant... Que se passe-t-il ?

R : Avez-vous lu la section de dépannage ? (voir "TROUBLESHOOTING").

Désactivation de StrictHostKeyChecking
Q : Pourquoi "ssh" ne s'exécute-t-il pas avec "StrictHostKeyChecking=no" ?

R : L'utilisation de "StrictHostKeyChecking=no" diminue le niveau de sécurité par défaut du protocole SSH et peut facilement aboutir à un SSH mal configuré (par exemple, lorsque "known_hosts" est inscriptible) qui peut être falsifié pour se connecter à un mauvais hôte et effectuer des attaques de type man-in-the-middle, etc.

Je vous recommande de ne pas utiliser cette option à moins de comprendre pleinement ses implications en matière de sécurité.

Si vous souhaitez l'utiliser, passez-la au constructeur :

$ssh = Net::OpenSSH->new($host,
         master_opts => [-o => "StrictHostKeyChecking=no"],
         ...);
STDOUT/STDERR du processus enfant n'est pas un vrai descripteur de fichier système
Q : Les appels à "system", "capture", etc., échouent avec l'erreur ci-dessus, que se passe-t-il ?

R : Le flux d'entrée/sortie standard rapporté est fermé ou n'est pas associé à un fichier réel (par exemple, c'est un handle attaché). Redirigez le flux vers "/dev/null" ou vers un fichier réel :

my $out = $ssh->capture({stdin_discard => 1, stderr_to_stdout => 1},
                        $cmd);

Voir également le journal de mod_perl ci-dessus.

Solaris (et AIX et probablement d'autres)
Q : J'ai essayé d'utiliser Net::OpenSSH sur Solaris et il semble avoir un problème... Que se passe-t-il ?

R : Le client SSH inclus dans Solaris est une ancienne version d'OpenSSH qui ne fournit pas la fonctionnalité de multiplication requise par Net::OpenSSH. Vous devrez installer le client OpenSSH.

Des paquets précompilés sont disponibles auprès de Sun Freeware (http://www.sunfreeware.com). Sélectionnez votre version du système d'exploitation et l'architecture du processeur, téléchargez le paquet OpenSSH et ses dépendances, puis installez-les. Assurez-vous que le client OpenSSH est dans votre PATH avant le "ssh" système, ou, alternativement, vous pouvez spécifier un chemin d'exécution complet dans vos scripts comme suit :

$ssh = Net::OpenSSH->new($host,
                         ssh_cmd => '/usr/local/bin/ssh');

Le système d'exploitation AIX et probablement d'autres Unix incluent également des clients SSH qui manquent de la fonctionnalité de multiplication et nécessitent l'installation du véritable client OpenSSH.

Je ne peux pas changer de répertoire de travail
Q : Je veux exécuter une commande dans un répertoire donné mais je ne peux pas changer de répertoire de travail. Par exemple : 
$ssh->system('cd /home/foo/bin');
$ssh->systen('ls');

n'affiche pas le contenu de "/home/foo/bin".

Qu'est-ce que je fais de mal ?

R : Net::OpenSSH (et par conséquent, tous les modules SSH disponibles sur CPAN, mais pas Net::SSH::Expect) exécute chaque commande dans une nouvelle session, donc la plupart des effets des shells qui s'exécutent de votre côté deviennent inutiles (par exemple, "cd", "export", "ulimit", "umask", etc. vous pouvez généralement les lister en exécutant "help" depuis le shell).

Une solution consiste à combiner plusieurs commandes en une seule, par exemple :

$ssh->system('cd /home/foo/bin && ls');

Notez que l'opérateur de shell "&&" est utilisé à la place de ";" pour abandonner la commande dès que l'un des sous-commandes échoue.

Plusieurs commandes peuvent également être combinées tout en utilisant la fonction de quantificateurs à arguments multiples, comme suit :

$ssh->system(@cmd1, \\'&&', @cmd2, \\'&&', @cmd3, ...);
Exécution de processus distants en arrière-plan
Q : Je dois pouvoir me connecter à plusieurs machines depuis mon script, y lancer un processus en arrière-plan, puis revenir immédiatement pendant que les processus distants continuent de s'exécuter... Comment faire ?

R : Si les systèmes distants exécutent une version d'Unix/Linux, la bonne façon est d'utiliser nohup(1) qui désolidarise le processus distant des flux d'entrée/sortie et demande au shell d'exécuter la commande en arrière-plan. Par exemple :

$ssh->system("nohup $long_running_command &");

Il pourrait également être possible de démoniser le programme distant. Si le programme est écrit en Perl, vous pouvez utiliser App::Daemon pour cela (en réalité, il existe plusieurs modules CPAN qui fournissent cette fonctionnalité).

Dans tous les cas, vous remarquerez que vous ne devriez pas utiliser "spawn" pour cela.

Limite de sessions serveur MaxSessions
Q : J'ai créé un objet $ssh puis forcé la création de nombreux processus enfants utilisant cet objet. Lorsque le nombre d'enfants dépasse "MaxSessions" tel que défini dans la configuration du serveur sshd (par défaut 10), tenter de connecter de nouvelles commandes distantes me demande mon mot de passe.

R : Lorsque le client SSH esclave reçoit une réponse des serveurs distants indiquant que le nombre maximum de sessions pour la connexion actuelle a été atteint, il rouvre une connexion directe sans passer par le socket de multiplication.

Pour éviter que cela ne se produise, vous pouvez utiliser l'astuce suivante :

$ssh = Net::OpenSSH->new(host,
    default_ssh_opts => ['-oConnectionAttempts=0'],
    ...);
Exécution de commandes distantes avec sudo
Q : Comment puis-je exécuter des commandes distantes en utilisant "sudo" pour devenir root d'abord ?

R : La manière la plus simple est de dire à "sudo" de lire le mot de passe depuis stdin avec le drapeau "-S" et de ne pas utiliser les identifiants mis en cache avec le drapeau "-k". Vous pourriez également vouloir utiliser le drapeau "-p" pour dire à "sudo" d'imprimer un message vide. Par exemple :

my @out = $ssh->capture({ stdin_data => "$sudo_passwd\n" },
                        'sudo', '-Sk',
                        '-p', '',
                        '--',
                        @cmd);

Si la version de sudo installée sur l'hôte distant ne prend pas en charge le drapeau "-S" (qui dit à sudo de lire le mot de passe depuis son flux stdin), vous pouvez faire ceci :

my @out = $ssh->capture({ tty => 1,
                          stdin_data => "$sudo_passwd\n" },
                        'sudo', '-k',
                        '-p', '',
                        '--',
                        @cmd);

Cela peut générer un avertissement inoffensif et spurious de la connexion maître SSH (car nous demandons l'allocation d'un tty côté distant et côté local, nous l'attachons à une paire de tuyaux normaux).

Si pour une raison quelconque les méthodes décrites ci-dessus échouent, vous pouvez toujours revenir à l'utilisation d'Expect pour interagir avec le "sudo" distant. Voir le script d'exemple "examples/expect.pl" de ce module.

Interactivité
Q : Que dois-je faire pour interagir avec le shell distant ?

R : Vous pouvez utiliser Expect pour interagir avec le shell distant. L'interactivité est ce qui permet à l'utilisateur d'interagir de manière transparente avec le shell distant.

SESSIONS

Q: ¿Cómo inicio una sesión remota interactiva?

A: Simplemente llama al método "system" con una lista de argumentos vacía:

my $ssh = Net::OpenSSH->new(...);
$ssh->system;
Q: ¿Y si quiero ejecutar una sesión interactiva "sftp"?

Los programas que utilizan una conexión SSH subyacente suelen proporcionar algún mecanismo (por ejemplo, la opción de línea de comandos "-o") para pasar opciones adicionales al comando "ssh" usado para ejecutar esa conexión. Solo necesitamos utilizar ese mecanismo para pasar la ruta al socket de control.

Por ejemplo, en el caso particular de "sftp":

$cp = $ssh->get_ctl_path;
system "sftp", "-oControlPath=$cp", $host;

Problemas conocidos

Net::OpenSSH no funciona en Windows. La función de multiplexación de OpenSSH requiere pasar manejadores de archivos a través de sockets, lo cual no es compatible en ninguna versión de Windows.

Tampoco funciona en VMS... tal vez no funcione en nada que no sea un sistema Linux/Unix moderno.

Las versiones antiguas de "ssh" de OpenSSH pueden dejar los flujos de entrada/salida en modo no bloqueante. Esto puede causar fallos al escribir en "STDOUT" o "STDERR" después de usar el módulo. Para evitar este problema, se puede usar la función Perl "fcntl" en perlfunc para desactivar la bandera no bloqueante:

use Fcntl qw(F_GETFL F_SETFL O_NONBLOCK);
my $flags = fcntl(STDOUT, F_GETFL, 0);
fcntl(STDOUT, F_SETFL, $flags & ~O_NONBLOCK);

CONTRIBUIR CÓDIGO

El código fuente de este módulo está alojado en GitHub: http://github.com/salva/p5-Net-OpenSSH.

Se aceptan contribuciones al módulo, pero debes obedecer las siguientes reglas:

Solo se requiere Perl 5.8.4
Sí, es bastante antiguo, pero Net::OpenSSH está pensado para ser utilizado también por administradores que a veces tienen que lidiar con sistemas antiguos. La razón para elegir 5.8.4 es que ha sido el perl por defecto en Solaris durante mucho tiempo.
Evitar el síndrome de "Todo el mundo es un PC con Linux"
El módulo debe funcionar en cualquier sistema Unix o Linux (más o menos) que sea sensato. En particular, no se debe asumir que las utilidades y cadenas de herramientas de GNU están disponibles.
Las dependencias son opcionales
Para hacer que el módulo sea muy fácil de instalar, no se permiten dependencias obligatorias en otros módulos de CPAN. Los módulos opcionales que se cargan solo cuando son necesarios son aceptables cuando se usan para agregar nueva funcionalidad (como es el caso de IO::Pty). El código de unificación para la integración con módulos de terceros también es aceptable (como lo es con Expect). El uso de módulos de extensiones de lenguaje o similares no es aceptable.
Las pruebas deben ser laxas
No queremos falsos negativos durante las pruebas. Si hay dudas, las pruebas deben pasar. Además, si las pruebas invocan algún programa externo, se debe verificar que el programa externo esté disponible y funcione como se espera, o bien se deben omitir esas pruebas.
Compatibilidad inversa
Actualmente Net::OpenSSH es bastante estable y hay muchos scripts que lo utilizan que no queremos romper, por lo que mantener la API de compatibilidad inversa es una prioridad. Probablemente solo problemas de seguridad puedan justificar un cambio incompatible ahora.
