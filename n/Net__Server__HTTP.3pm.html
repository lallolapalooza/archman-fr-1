Net::Server::HTTP(3) Documentation des paquets contribués Perl Net::Server::HTTP(3)

Nom

Net::Server::HTTP - classe de base pour un serveur HTTP basé sur Net::Server

TEST ONE LINER

perl -e 'use base qw(Net::Server::HTTP); main->run(port => 8080)'
# lancera un serveur echo

SYNTAXE

use base qw(Net::Server::HTTP);
__PACKAGE__->run;
sub process_http_request {
    my $self = shift;
    print "Content-type: text/html\n\n";
    print "<form method=post action=/bam><input type=text name=foo><input type=submit></form>";
    require Data::Dumper;
    local $Data::Dumper::Sortkeys = 1;
    require CGI;
    my $form = {};
    my $q = CGI->new; $form->{$_} = $q->param($_) for $q->param;
    print "<pre>".Data::Dumper->Dump([\%ENV, $form], ['*ENV', 'form'])."</pre>";
}

DESCRIPTION

Bien que Net::Server::HTTP ne se trouve pas dans le parallélisme normal des autres arômes de Net::Server, la gestion des requêtes HTTP est une fonctionnalité couramment demandée et c'est un protocole standard et simple.

Net::Server::HTTP commence par le type de base MultiType par défaut qui correspond à Net::Server::PreFork. Il est facile de le changer à n'importe quel autre arôme de Net::Server en passant server_type => $other_flavor dans la configuration du serveur. Le port a également été défini par défaut à 80 - mais pourrait facilement être changé à un autre via la configuration du serveur. Vous pouvez également facilement ajouter SSL en incluant proto => "ssl" et en fournissant un SSL_cert_file et SSL_key_file.

Par exemple, voici un serveur de base qui se connectera à toutes les interfaces, parlera HTTP sur le port 8080 et HTTPS sur 8443, et parlera IPv4 et IPv6 si disponible.

use base qw(Net::Server::HTTP);
__PACKAGE__->run(
    port  => [8080, "8443/ssl"],
    ipv   => '*', # IPv6 si disponible
    SSL_key_file  => '/my/key',
    SSL_cert_file => '/my/cert',
);

MÉTHODES

"_init_access_log"
Utilisé pour ouvrir et initialiser tout access_log (voir access_log_file et access_log_format).
"_tie_client_stdout"
Utilisé pour initialiser l'analyse automatisée des en-têtes de réponse.
"process_http_request"
Le handle du client est passé et STDIO est lié à celui-ci. Pendant cette méthode, %ENV sera déjà configuré avec un environnement CGI standard. Vous devez vous assurer d'imprimer l'en-tête Content-type. C'est une différence importante par rapport aux autres bases Net::Server standard.
"process_request"
Cette méthode a été surchargée dans Net::Server::HTTP - vous ne devriez pas l'utiliser lorsque vous utilisez Net::Server::HTTP. Cette méthode surchargée analyse l'environnement, configure les alertes de requête et gère les échecs. Elle appelle process_http_request une fois que la requête est prête et que les en-têtes ont été analysés.
"request_denied_hook"
Cette méthode a été surchargée pour appeler send_400. Elle est nouvelle. Pour obtenir le comportement précédent (où le client est fermé sans indication), fournissez simplement
"process_headers"
Utilisé pour lire les en-têtes entrants et configurer %ENV.
"_init_http_request_info"
Appelé à la fin de process_headers. Initialise le contenu de http_request_info.
"http_request_info"
Renvoie un hashref d'informations spécifiques à la requête actuelle. Ces informations seront utilisées pour un enregistrement ultérieur.
"send_status"
Reçoit un statut HTTP, un message optionnel, un corps optionnel et un flag optionnel generate_body. Envoie les en-têtes corrects. 
$self->send_status(500);
$self->send_status(500, 'Internal Server Error');
$self->send_status(500, 'Internal Server Error', "<h1>Internal Server Error</h1><p>Msg</p>");
$self->send_status(500, undef, undef, ['Msg']);
"send_400"
Appelle send_status avec 400 et les arguments passés comme generate_body.
"send_500"
Appelle send_status avec 500 et l'argument passé à send_500.
c<log_http_request>
Appelé à la fin de post_process_request. La méthode par défaut recherche l'access_log_format par défaut et vérifie si le logging a été initialisé pendant _init_access_log. Si les deux existent, http_request_info est formé en utilisant http_log_format et le résultat est enregistré.
"http_log_format"
Reçoit une chaîne de format, et request_info et renvoie une chaîne formatée. Le format doit suivre la spécification mod_log_config d'Apache. Comme dans la spécification mod_log_config, les barres obliques inverses, les guillemets doivent être échappés avec des barres obliques inverses et vous pouvez également inclure des caractères \n et \t.

Voici une liste des paramètres disponibles ainsi qu'un exemple de sortie basé sur un serveur HTTP très basique.

%%                %                 # un signe pourcentage
%a                ::1               # ip distante
%A                ::1               # ip locale
%b                83                # taille de la réponse (- si 0) format de log commun
%B                83                # taille de la réponse
%{bar}C           baz               # valeur du cookie pour ce nom
%D                916               # temps écoulé en microsecondes
%{HTTP_COOKIE}e   bar=baz           # valeur de %ENV pour ce nom
%f                -                 # nom de fichier - non utilisé
%h                ::1               # hôte distant si les requêtes sont actives, ip distante sinon
%H                http              # protocole de la requête
%{Host}i          localhost:8080    # valeur de la requête pour ce nom
%I                336               # octets reçus, y compris les en-têtes
%l                -                 # nom de connexion distante - non utilisé
%m                GET               # méthode de la requête
%n                Just a news       # news %ENV pour ce nom
%{Content-type}o  text/html         # en-tête de sortie pour ce nom
%O                189               # taille de la réponse, y compris les en-têtes
%p                8080              # port du serveur
%P                22999             # PID - ne supporte pas %{tid}P
q                 ?hello=there      # chaîne de requête, y compris ? (- sinon)
r                 GET /bam?hello=there HTTP/1.1      # première ligne de la requête
%s                200               # code d'état de la réponse
%u                -                 # utilisateur distant - non utilisé
%U                /bam              # chemin de la requête (sans chaîne de requête)
%t                [06/Jun/2012:12:14:21 -0600]       # format d'heure de log http_log_time standard
%t{%F %T %z}t     [2012-06-06 12:14:21 -0600]        # format d'heure formaté
%T                0                 # temps écoulé en secondes
%v                localhost:8080    # vhost http_log_vhost - implémentation partielle
%V                localhost:8080    # vhost http_log_vhost - implémentation partielle
%X                -                 # connexion terminée et est 'close' (-)

De plus, l'analyse des logs permet le format suivant :

%>s               200               # dernier état de la requête
%<s               200               # état de la requête d'origine
%400a             -                 # ip distante si l'état est 400
%!400a            ::1               # ip distante si l'état n'est pas 400
%!200a            -                 # ip distante si l'état n'est pas 200

Il y a quelques éléments qui ne sont pas entièrement implémentés :

> et <    # pas de redirection interne
%I         # la réponse est basée sur la taille de l'en-tête et Content-length, pas sur le nombre correct d'octets lus, bien que dans les cas courants, ceux-ci seraient les mêmes.
%X         # pas de keepalive sur le serveur par défaut.
%v et %V  # pas de vhosts sur le serveur HTTP par défaut.
%{tid}P    # les serveurs par défaut ne sont pas multithreadés.

Voir l'option "access_log_format" pour savoir comment configurer un format différent ainsi que pour voir la chaîne par défaut.

"exec_cgi"
Permet d'appeler un exécutable CGI.

NOM

Net::Server::HTTP

SYNOPIS

use base qw(Net::Server::HTTP);
__PACKAGE__->run;
sub process_http_request {
    my $self = shift;
    if ($ENV{'PATH_INFO'} && $ENV{'PATH_INFO'} =~ s{^ (/foo) (?= $ | /) }{}x) {
       $ENV{'SCRIPT_NAME'} = $1;
       my $file = "/var/www/cgi-bin/foo"; # supposant que cela existe
       return $self->exec_cgi($file);
    }
    print "Content-type: text/html\n\n";
    print "<a href=/foo>Foo</a>";
}

DESCRIPTION

Ce script s'exécutera en tant que CGI. Il utilisera IPC::Open3 pour forcer un nouveau processus et lire/écrire depuis celui-ci.

EXEMPLE

use base qw(Net::Server::HTTP);
__PACKAGE__->run;
sub process_http_request {
    my $self = shift;
    if ($ENV{'PATH_INFO'} && $ENV{'PATH_INFO'} =~ s{^ (/foo) (?= $ | /) }{}x) {
       $ENV{'SCRIPT_NAME'} = $1;
       my $file = "/var/www/cgi-bin/foo"; # supposant que cela existe
       return $self->exec_cgi($file);
    }
    print "Content-type: text/html\n\n";
    print "<a href=/foo>Foo</a>";
}

OPTIONS

En plus des arguments de ligne de commande des classes Net::Server, vous pouvez également configurer les options suivantes.

max_header_size
Par défaut, 100 000. Le nombre maximum d'octets à lire lors de l'analyse des en-têtes.
server_revision
Par défaut, Net::Server::HTTP/$Net::Server::VERSION.
timeout_header
Par défaut, 15 - le nombre de secondes pendant lesquelles on attend l'analyse des en-têtes.
timeout_idle
Par défaut, 60 - le nombre de secondes pendant lesquelles une requête peut être inactive avant d'être fermée.
access_log_file
Par défaut, undef. S'il est vrai, il représente l'emplacement où le fichier de journal d'accès doit être écrit. Si une valeur spéciale STDERR ou /dev/stderr est passée, le journal d'accès sera écrit au même endroit que le journal ERROR. Si une valeur spéciale STDOUT ou /dev/stdout est passée, le journal d'accès sera écrit au même endroit que STDOUT.
access_log_function
Peut prendre un coderef ou le nom d'une fonction à appeler lorsque la méthode log_http_request est invoquée. Le message de journal d'accès formaté lui sera passé.
access_log_format
Doit être un format de journal Apache valide qui sera passé à http_log_format. Voir la méthode http_log_format pour plus d'informations.
app
Prendra un ou plusieurs éléments et les enregistrera pour la distribution. Les arguments peuvent être passés sous forme d'arrayref avec des paires emplacement/destination, un hashref avec des paires emplacement/destination, un coderef qui utilisera / comme emplacement et le coderef comme destination, une chaîne avec un espace indiquant « emplacement destination », une chaîne avec « emplacement=destination », ou enfin une chaîne qui sera utilisée à la fois comme emplacement et destination. Pour les éléments passés sous forme d'arrayref ou de hashref, la destination peut être un coderef qui sera appelé et doit gérer la requête. Dans tous les autres cas, la destination doit être un exécutable valide approprié pour être passé à exec_cgi.

Les emplacements sont ajoutés dans l'ordre où ils sont configurés. Ils sont ajoutés à une expression régulière qui est appliquée à la chaîne PATH_INFO. Si la correspondance réussit, $ENV{'SCRIPT_NAME'} est défini sur la partie correspondante et la partie correspondante est supprimée de $ENV{'PATH_INFO'}

Une fois qu'une application a été transmise, le serveur doit écouter sur /. Par conséquent, si / n'a pas été spécifiquement configuré pour la distribution, la première cible de distribution trouvée sera également utilisée pour gérer /.

Pour plus de commodité, si le niveau de journal est de 2 ou plus, la table de distribution est affichée dans le journal.

Ce mécanisme est maintenu comme un mécanisme générique approprié pour être surchargé par les serveurs qui gèrent une distribution plus complexe. Pour le moment, il n'y a pas de gestion des vhosts. À un moment donné, la capacité par défaut d'afficher du contenu statique et probablement la capacité de configurer des vhosts seront ajoutées - ou vous devrez attendre un module tiers.

app => "/home/paul/foo.cgi",
  # Dispatch: /home/paul/foo.cgi => home/paul/foo.cgi
  # Dispatch: / => home/paul/foo.cgi (par défaut)
app => "../../foo.cgi",
app => "./bar.cgi",
app => "bim=./bar.cgi",
  # Dispatch: /foo.cgi => ../../foo.cgi
  # Dispatch: /bar.cgi => ./bar.cgi
  # Dispatch: /baz => ./bar.cgi
  # Dispatch: /bim => ./bar.cgi
  # Dispatch: / => ../../foo.cgi (par défaut)
app => "../../foo.cgi",
app => "./bar.cgi",
  # Dispatch: /foo.cgi => ../../foo.cgi
  # Dispatch: / => ./bar.cgi
# vous pouvez également faire cela sur la ligne de commande
net-server HTTP app ../../foo.cgi app /=./bar.cgi
# options étendues lorsqu'elles sont configurées à partir du code
Net::Server::HTTP->run(app => { # perd l'ordre de correspondance
  '/' => sub { ... },
  '/foo' => sub { ... },
  '/bar' => '/path/to/some.cgi',
});
Net::Server::HTTP->run(app => [
  '/' => sub { ... },
  '/foo' => sub { ... },
  '/bar' => '/path/to/some.cgi',
]));
Par défaut, text/html. Définissez cette valeur sur toute réponse qui n'a pas encore reçu de type de contenu.
Par défaut, ne permet pas de corps de contenu dans 204, 304 ou 1xx. Définissez ce drapeau pour envoyer un type de contenu également dans ces statuts.
