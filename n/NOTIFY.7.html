NOM

NOTIFY - générer une notification

SYNTAXE

NOTIFY canal [ , charge_utile ]

DESCRIPTION

La commande NOTIFY envoie un événement de notification, accompagné d'une chaîne facultative de « charge utile » (payload), à chaque application cliente qui a précédemment exécuté LISTEN canal pour le nom de canal spécifié dans la base de données actuelle. Les notifications sont visibles par tous les utilisateurs.

NOTIFY fournit un mécanisme de communication inter-processus simple pour une collection de processus accédant à la même base de données PostgreSQL. Une chaîne de charge utile peut être envoyée avec la notification, et des mécanismes de plus haut niveau pour passer des données structurées peuvent être construits en utilisant les tables de la base de données pour passer des données supplémentaires du notificateur au(x) récepteur(s).

Les informations transmises au client pour un événement de notification comprennent le nom du canal de notification, l'ID de processus du serveur de la session notifiante et la chaîne de charge utile, qui est une chaîne vide si elle n'a pas été spécifiée.

Il appartient au concepteur de la base de données de définir les noms de canaux qui seront utilisés dans une base de données donnée et ce que chacun signifie. Couramment, le nom du canal est le même que le nom d'une table dans la base de données, et l'événement de notification signifie essentiellement « J'ai modifié cette table, regardez-la pour voir ce qu'il y a de nouveau ». Mais aucune association de ce type n'est appliquée par les commandes NOTIFY et LISTEN. Par exemple, un concepteur de base de données pourrait utiliser plusieurs noms de canaux différents pour signaler différents types de changements à une seule table. Alternativement, la chaîne de charge utile pourrait être utilisée pour différencier divers cas.

Lorsque NOTIFY est utilisé pour signaler l'occurrence de changements à une table particulière, une technique de programmation utile est de placer NOTIFY dans un déclencheur d'instruction qui est déclenché par les mises à jour de table. De cette façon, la notification se produit automatiquement lorsque la table est modifiée, et le programmeur d'application ne peut pas oublier de le faire par inadvertance.

NOTIFY interagit de manière importante avec les transactions SQL. Premièrement, si un NOTIFY est exécuté à l'intérieur d'une transaction, les événements de notification ne sont pas délivrés avant et à moins que la transaction ne soit validée. Ceci est approprié, car si la transaction est annulée, toutes les commandes qu'elle contient n'ont eu aucun effet, y compris NOTIFY. Mais cela peut être déconcertant si l'on s'attend à ce que les événements de notification soient livrés immédiatement. Deuxièmement, si une session d'écoute reçoit un signal de notification alors qu'elle est dans une transaction, l'événement de notification ne sera pas délivré à son client connecté avant juste après que la transaction soit terminée (validée ou annulée). Là encore, le raisonnement est que si une notification était livrée dans une transaction qui était plus tard annulée, on voudrait que la notification soit annulée d'une manière ou d'une autre — mais le serveur ne peut pas « reprendre » une notification une fois qu'elle a été envoyée au client. Ainsi, les événements de notification ne sont délivrés qu'entre les transactions. Le résultat est que les applications utilisant NOTIFY pour une signalisation en temps réel devraient essayer de garder leurs transactions courtes.

Si le même nom de canal est signalé plusieurs fois avec des chaînes de charge utile identiques au sein de la même transaction, seule une instance de l'événement de notification est livrée aux récepteurs. D'autre part, les notifications avec des chaînes de charge utile distinctes seront toujours livrées comme des notifications distinctes. De même, les notifications de transactions différentes ne seront jamais fusionnées en une seule notification. À l'exception de la suppression des instances ultérieures de notifications dupliquées, NOTIFY garantit que les notifications de la même transaction sont livrées dans l'ordre où elles ont été envoyées. Il est également garanti que les messages de transactions différentes sont livrés dans l'ordre dans lequel les transactions ont été validées.

Il est courant qu'un client qui exécute NOTIFY écoute lui-même le même canal de notification. Dans ce cas, il recevra un événement de notification, tout comme toutes les autres sessions d'écoute. Selon la logique de l'application, cela pourrait entraîner un travail inutile, par exemple, lire une table de base de données pour trouver les mêmes mises à jour que cette session vient d'écrire. Il est possible d'éviter un travail supplémentaire en remarquant si l'ID de processus du serveur de la session notifiante (fourni dans le message d'événement de notification) est le même que l'ID de processus de sa propre session (disponible à partir de libpq). Lorsque ceux-ci sont identiques, l'événement de notification est le travail propre de la session qui rebondit, et peut être ignoré.

PARAMETRES

canal

Nom du canal de notification à signaler (n'importe quel identifiant).

charge_utile

La chaîne « charge utile » à communiquer avec la notification. Elle doit être spécifiée comme une simple chaîne littérale. Dans la configuration par défaut, elle doit être plus courte que 8000 octets. (Si des données binaires ou de grandes quantités d'informations doivent être communiquées, il est préférable de les placer dans une table de base de données et d'envoyer la clé de l'enregistrement.)

NOTES

Il existe une file d'attente qui conserve les notifications envoyées mais pas encore traitées par toutes les sessions d'écoute. Si cette file d'attente devient pleine, les transactions appelant NOTIFY échoueront lors de la validation. La file d'attente est assez grande (8 Go dans une installation standard) et devrait être suffisamment dimensionnée pour presque tous les cas d'utilisation. Cependant, aucun nettoyage ne peut avoir lieu si une session exécute LISTEN puis entre dans une transaction pendant une très longue période. Une fois la file d'attente à moitié pleine, vous verrez des avertissements dans le fichier journal vous signalant la session qui empêche le nettoyage. Dans ce cas, vous devez vous assurer que cette session termine sa transaction actuelle afin que le nettoyage puisse procéder.

La fonction pg_notification_queue_usage renvoie la fraction de la file d'attente actuellement occupée par des notifications en attente. Voir la Section 9.27 pour plus d'informations.

Une transaction qui a exécuté NOTIFY ne peut pas être préparée pour une validation en deux phases.

pg_notify

Pour envoyer une notification, vous pouvez également utiliser la fonction pg_notify(texte, texte). La fonction prend le nom du canal comme premier argument et la charge utile comme second. La fonction est beaucoup plus facile à utiliser que la commande NOTIFY si vous avez besoin de travailler avec des noms de canaux et des charges utiles non constants.

EXEMPLES

Configurer et exécuter une séquence écouter/notifier depuis psql :

LISTEN virtual;
NOTIFY virtual;
Notification asynchrone « virtual » reçue du processus serveur avec PID 8448.
NOTIFY virtual, 'Ceci est la charge utile';
Notification asynchrone « virtual » avec la charge utile « Ceci est la charge utile » reçue du processus serveur avec PID 8448.
LISTEN foo;
SELECT pg_notify('fo' || 'o', 'pay' || 'load');
Notification asynchrone « foo » avec la charge utile « payload » reçue du processus serveur avec PID 14728.

COMPATIBILITE

Il n'y a pas d'instruction NOTIFY dans la norme SQL.
