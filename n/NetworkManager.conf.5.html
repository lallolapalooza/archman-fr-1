NETWORKMANAGER.CONF(5) Configuration NETWORKMANAGER.CONF(5)

NOM

NetworkManager.conf - Fichier de configuration de NetworkManager

SYNTAXE

/etc/NetworkManager/NetworkManager.conf, /etc/NetworkManager/conf.d/nom.conf, /run/NetworkManager/conf.d/nom.conf, /usr/lib/NetworkManager/conf.d/nom.conf, /var/lib/NetworkManager/NetworkManager-intern.conf

DESCRIPTION

NetworkManager.conf est le fichier de configuration de NetworkManager. Il est utilisé pour définir divers aspects du comportement de NetworkManager. L'emplacement du fichier principal et des répertoires de configuration peut être modifié à l'aide des options --config, --config-dir, --system-config-dir et --intern-config de NetworkManager, respectivement.

Si un fichier de configuration par défaut de NetworkManager est fourni par les distributions, vous ne devriez pas le modifier, car vos modifications pourraient être écrasées par des mises à jour de paquets. Au lieu de cela, vous pouvez ajouter des fichiers .conf supplémentaires au répertoire /etc/NetworkManager/conf.d. Ceux-ci sont lus dans l'ordre, les fichiers ultérieurs écrasant les précédents. Les paquets peuvent installer des snippets de configuration supplémentaires dans /usr/lib/NetworkManager/conf.d. Ce répertoire est traité en premier, même avant NetworkManager.conf. Les scripts peuvent également placer la configuration de démarrage dans /run/NetworkManager/conf.d. Ce répertoire est traité en deuxième, également avant NetworkManager.conf. Le chargement d'un fichier /run/NetworkManager/conf.d/nom.conf peut être évité en plaçant un fichier /etc/NetworkManager/conf.d/nom.conf. De même, un fichier /usr/lib/NetworkManager/conf.d/nom.conf peut être masqué en plaçant un fichier du même nom dans /etc/NetworkManager/conf.d ou /run/NetworkManager/conf.d.

NetworkManager peut surcharger certaines options de configuration de l'utilisateur via D-Bus ou des opérations internes. Dans ce cas, écrivez ces changements dans /var/lib/NetworkManager/NetworkManager-intern.conf. Ce fichier n'est pas destiné à être modifié par l'utilisateur, mais il est lu en dernier et peut masquer les configurations de NetworkManager.conf.

Certains paramètres de configuration peuvent être rechargés à l'exécution soit en envoyant le signal SIGHUP, soit via l'appel D-Bus' Reload.

NetworkManager ne nécessite aucune configuration dans NetworkManager.conf. Selon votre cas d'utilisation, vous pourriez supprimer tous les fichiers pour restaurer la configuration par défaut (rétablir les valeurs par défaut). Cependant, notez que votre distribution ou d'autres paquets pourraient supprimer des snippets de configuration pour NetworkManager, dans le cadre de la configuration d'usine par défaut.

FORMAT DE FICHIER

Le format du fichier de configuration est de type clé-valeur (similaire au format ini). Il se compose de sections (groupes) de paires clé-valeur. Les lignes commençant par un '#' et les lignes vides sont considérées comme des commentaires. Les sections commencent par une ligne d'en-tête contenant la section entre '[...' et ']', et se terminent implicitement au début de la section suivante ou à la fin du fichier. Chaque paire clé-valeur doit être contenue dans une section.

Pour les clés qui prennent une liste de périphériques comme valeur, vous pouvez spécifier les périphériques par leurs adresses MAC ou noms d'interface, ou utiliser la valeur '*' pour spécifier tous les périphériques. Voir la section intitulée "Format de liste de périphériques" ci-dessous.

Un fichier de configuration simple ressemble à ceci:

[main]
plugins=keyfile

En tant qu'extension du format keyfile normal, vous pouvez également ajouter une valeur à une liste-valeur précédemment définie en faisant:

plugins+=another-plugin
plugins-=remove-me

SECTION PRINCIPALE

plugins

Liste des noms de plugins de configuration système séparés par des virgules. Ces plugins sont utilisés pour lire et écrire les configurations de profils réseau du système. Lorsque plusieurs plugins sont spécifiés, les connexions sont lues à partir de tous les plugins spécifiés. Lors de l'écriture d'une connexion, les plugins sont interrogés quant au type de connexion à enregistrer dans l'ordre indiqué ici ; si le premier plugin ne peut pas écrire cette connexion (ou ne peut écrire aucune connexion), le plugin suivant est essayé, etc. Si aucun des plugins ne peut enregistrer la connexion, une erreur est renvoyée à l'utilisateur.

La valeur par défaut et le nombre de plugins disponibles dépendent de la distribution. Voir la section intitulée "PLUGINS" pour les plugins disponibles. Notez que le plugin keyfile natif de NetworkManager est toujours ajouté à la fin de cette liste (s'il n'y est pas déjà).

monitor-connection-files

Ce paramètre a été supprimé et n'a aucun effet. Les profils sur disque ne sont jamais rechargés automatiquement. Utilisez par exemple nmcli connection reload pour cela.

auth-polkit

Ce paramètre a été supprimé et n'a aucun effet.

SECTION LOGGING

level

Niveau de journalisation. Les niveaux valides sont ERR, WARNING, INFO, DEBUG, TRACE. Le niveau par défaut est INFO.

audit

Si vrai, NetworkManager effectuera des journaux d'audit de toutes les modifications de connexion qui se produisent à travers lui. Le niveau par défaut est faux.

SECTION DHCP

hostname

Si cette option est définie sur `no`, NetworkManager ne définira pas le nom d'hôte du système à partir des informations DHCP. Le nom d'hôte du système ne sera alors jamais changé dynamiquement. Le nom d'hôte par défaut est `yes`, ce qui signifie que NetworkManager tentera de définir le nom d'hôte du système à partir des informations DHCP si une connexion lui permet de le faire.

SECTION IP4

ignore-routes-with-metric

Cette option peut être définie sur une valeur entière. Si NetworkManager voit une route avec une métrique supérieure à la valeur spécifiée, il l'ignorera. Cela peut être utilisé pour empêcher les routes par défaut d'autres connexions d'interférer avec votre connexion actuelle. Par défaut, cette option est désactivée.

ignore-routes-from-all-gateways

Si cette option est définie sur `yes`, NetworkManager ignorera toutes les routes qui ont été ajoutées par des passerelles qui ne sont pas spécifiquement mentionnées dans l'option `routes-from-gateways`. La valeur par défaut est `no`.

routes-from-gateways

Liste de passerelles séparées par des virgules. NetworkManager ignorera toutes les routes qui ont été ajoutées par des passerelles qui ne sont pas dans cette liste. Cette option n'est pertinente que lorsque ignore-routes-from-all-gateways est définie sur `yes`.

SECTION IP6

ignore-routes-with-metric

Identique à la section IP4, mais pour les routes IPv6.

ignore-routes-from-all-gateways

Identique à la section IP4, mais pour les routes IPv6.

routes-from-gateways

Identique à la section IP4, mais pour les routes IPv6.

SECTION DEVICE

wifi-scan-regdomain

La région d'analyse Wi-Fi. Si définie, la recherche de réseaux Wi-Fi sera limitée à cette région. Cela peut être utilisé pour se conformer aux réglementations locales. La valeur par défaut est vide, ce qui signifie aucune restriction.

SECTION CONNECTION

auto-dns

Si cette option est définie sur `no`, NetworkManager n'essaiera pas de configurer automatiquement les serveurs DNS pour les connexions. Si vous désactivez cette option, vous devrez configurer les serveurs DNS manuellement ou via DHCP. La valeur par défaut est `yes`.

dns-priority

Spécifie la priorité des serveurs DNS. Les valeurs plus élevées indiquent une priorité plus élevée. Ceci est utilisé pour décider quel serveur DNS utiliser lorsqu'il y a plusieurs serveurs DNS disponibles. La valeur par défaut est 0.

dns-search-domains

Une liste de domaines de recherche DNS séparés par des virgules. Ceux-ci seront ajoutés à la configuration DNS du système. Les domaines de recherche sont utilisés pour résoudre les noms d'hôtes qui ne sont pas entièrement qualifiés.

dns-options

Une liste d'options DNS séparées par des virgules. Celles-ci seront ajoutées à la configuration DNS du système. Les options DNS peuvent être utilisées pour configurer divers aspects du comportement du résolveur DNS.

dns-nameservers

Une liste de serveurs DNS séparés par des virgules. Ceux-ci seront ajoutés à la configuration DNS du système.

perm-change-wifi-ssid

Si cette option est définie sur `yes`, seul l'utilisateur root pourra changer le SSID des réseaux Wi-Fi. Par défaut, tous les utilisateurs peuvent changer le SSID des réseaux Wi-Fi.

SECTION LOOPBACK

link

Si cette option est définie sur `no`, l'interface de bouclage ne sera pas activée par NetworkManager. La valeur par défaut est `yes`.

SECTION KEYFILE

unmanaged-devices

Une liste de périphériques séparés par des virgules qui doivent être ignorés par NetworkManager. Les périphériques peuvent être spécifiés par leur adresse MAC ou leur nom d'interface. Par exemple : unmanaged-devices=mac:00:11:22:33:44:55;interface-name:eth0.

SECTION CLONAGE D'ADRESSE MAC DES PÉRIPHÉRIQUES

cloned-mac-address

Adresse MAC à cloner pour les périphériques Wi-Fi. Si cette option est définie, NetworkManager tentera de cloner cette adresse MAC pour les périphériques Wi-Fi. Ceci est utile pour les réseaux qui exigent une adresse MAC spécifique.

SECTION MODEM

user-device-name

Si cette option est définie sur `yes`, NetworkManager tentera de trouver un nom d'utilisateur pour les périphériques modem et l'utilisera dans le nom du périphérique. Par défaut, cette option est définie sur `no`.

SECTION WIMAX

rc-manager

Le gestionnaire de connexion à utiliser pour WiMAX. Les valeurs valides sont `internal` et `external`. La valeur par défaut est `internal`.

SECTION DOT11

disable-scan-while-scanning

Si cette option est définie sur `yes`, NetworkManager désactivera l'analyse Wi-Fi pendant qu'il est déjà en train d'analyser. Ceci est utile pour réduire l'utilisation de la batterie sur les appareils portables. La valeur par défaut est `no`.

SECTION RACELENGTH

max-retries

Nombre maximal de tentatives pour établir une connexion. Par défaut, 3.

SECTION CLONAGE D'ADRESSE MAC DES PÉRIPHÉRIQUES

cloned-mac-address

Adresse MAC à cloner pour les périphériques Wi-Fi. Si cette option est définie, NetworkManager tentera de cloner cette adresse MAC pour les périphériques Wi-Fi. Ceci est utile pour les réseaux qui exigent une adresse MAC spécifique.

SECTION DEVICE

wifi-country

Le pays Wi-Fi. Si définie, la configuration Wi-Fi sera limitée à ce pays. Cela peut être utilisé pour se conformer aux réglementations locales. La valeur par défaut est vide, ce qui signifie aucune restriction.

EXEMPLES

Configurer NetworkManager pour utiliser uniquement le plugin keyfile :

[main]
plugins=keyfile

Désactiver la journalisation de débogage :

[logging]
level=INFO

Ignorer les routes avec une métrique supérieure à 100 :

[ip4]
ignore-routes-with-metric=100

Ne pas configurer automatiquement les serveurs DNS :

[connection]
auto-dns=no

Ne pas permettre à des utilisateurs non privilégiés de changer le SSID des réseaux Wi-Fi :

[connection]
perm-change-wifi-ssid=yes

Ignorer l'interface `eth0` et tous les périphériques Wi-Fi :

[keyfile]
unmanaged-devices=interface-name:eth0;type:wifi

dns

Définit le mode de traitement DNS.

Si la clé n'est pas spécifiée, la valeur par défaut est utilisée, sauf si /etc/resolv.conf est un lien symbolique vers /run/systemd/resolve/stub-resolv.conf, /run/systemd/resolve/resolv.conf, /lib/systemd/resolv.conf ou /usr/lib/systemd/resolv.conf. Dans ce cas, systemd-resolved est choisi automatiquement.

default: NetworkManager mettra à jour /etc/resolv.conf pour refléter les serveurs de noms fournis par les connexions actives. Le paramètre rc-manager (ci-dessous) contrôle la manière dont cela est fait.

dnsmasq: NetworkManager exécutera dnsmasq comme serveur de noms de cache local, en utilisant le "Forwarding conditionnel" si vous êtes connecté à un VPN, puis mettra à jour resolv.conf pour pointer vers le serveur de noms local. Il est possible de passer des options personnalisées à l'instance dnsmasq en les ajoutant à des fichiers dans le répertoire "/etc/NetworkManager/dnsmasq.d/". Notez que lorsque plusieurs serveurs en amont sont disponibles, dnsmasq les contactera initialement en parallèle, puis utilisera le plus rapide à répondre, sondant à nouveau d'autres serveurs après un certain temps. Ce comportement peut être modifié en passant les options 'all-servers' ou 'strict-order' à dnsmasq (voir la page de manuel pour plus de détails).

systemd-resolved: NetworkManager poussera la configuration DNS vers systemd-resolved

dnsconfd: NetworkManager poussera la configuration DNS vers dnsconfd

Notez que les plugins dnsmasq, systemd-resolved et dnsconfd sont des serveurs de noms locaux en cache. Par conséquent, lorsque NetworkManager écrit /run/NetworkManager/resolv.conf et /etc/resolv.conf (selon le paramètre rc-manager ci-dessous), le serveur de noms sera uniquement localhost. NetworkManager écrit également un fichier /run/NetworkManager/no-stub-resolv.conf qui contient les serveurs de noms d'origine transmis au plugin DNS.

Lors de l'utilisation de dnsmasq, systemd-resolved et dnsconfd, les serveurs DNS ajoutés par connexion seront toujours interrogés en utilisant le périphérique sur lequel la connexion a été activée.

rc-manager

Définit le mode de gestion de resolv.conf. Cette option concerne la manière dont NetworkManager écrit dans /etc/resolv.conf, le cas échéant. La valeur par défaut dépend des options de compilation de NetworkManager, et cette version de NetworkManager a été compilée avec une valeur par défaut de "symlink". Indépendamment de ce paramètre, NetworkManager écrira toujours sa version de resolv.conf dans son répertoire d'état d'exécution sous /run/NetworkManager/resolv.conf.

Si vous configurez dns=none ou rendez /etc/resolv.conf immuable avec chattr +i, NetworkManager ignorera ce paramètre et choisira toujours unmanaged (ci-dessous).

auto: si le plugin systemd-resolved est configuré via le paramètre dns ou s'il est détecté comme plugin DNS principal, NetworkManager mettra à jour systemd-resolved sans toucher à /etc/resolv.conf. Alternativement, si resolvconf ou netconfig sont activés au moment de la compilation et que le binaire correspondant est trouvé, NetworkManager l'utilisera automatiquement. Notez que si vous installez ou désinstallez ces binaires, vous devez recharger le paramètre rc-manager avec SIGHUP ou systemctl reload NetworkManager. En dernier recours, il utilise l'option symlink (voir la suivante).

symlink: Si /etc/resolv.conf est un fichier régulier ou n'existe pas, NetworkManager écrira le fichier directement. Si /etc/resolv.conf est plutôt un lien symbolique, NetworkManager le laissera tel quel. Sauf si le lien symbolique pointe vers le fichier interne /run/NetworkManager/resolv.conf, auquel cas le lien symbolique sera mis à jour pour émettre une notification inotify. Cela permet à l'utilisateur d'indiquer facilement à NetworkManager de ne pas gérer /etc/resolv.conf en le remplaçant par un lien symbolique.

file: NetworkManager écrira /etc/resolv.conf en tant que fichier régulier. S'il trouve un lien symbolique vers une cible existante, il suivra le lien symbolique et mettra à jour la cible à la place. En aucun cas un lien symbolique existant ne sera remplacé par un fichier. Notez que les versions antérieures de NetworkManager se comportaient différemment et remplaçaient les liens symboliques pendants par un fichier simple.

resolvconf: NetworkManager exécutera resolvconf pour mettre à jour la configuration DNS.

netconfig: NetworkManager exécutera netconfig pour mettre à jour la configuration DNS.

unmanaged: ne pas toucher à /etc/resolv.conf.

none: alias obsolète pour symlink.

systemd-resolved

Envoyer en plus la configuration DNS de la connexion à systemd-resolved. La valeur par défaut est "true".

Notez que ce paramètre n'a aucun effet si le plugin dns principal est déjà systemd-resolved. Il est complémentaire au paramètre dns pour configurer systemd-resolved aux côtés du plugin principal.

Si systemd-resolved est activé, soit via ce paramètre, soit via le plugin DNS principal, la vérification de connectivité résout le nom d'hôte par périphérique.

debug

Liste séparée par des virgules d'options pour aider au débogage. Cette valeur sera combinée avec la variable d'environnement NM_DEBUG. Actuellement, les valeurs suivantes sont prises en charge :

RLIMIT_CORE: définit ulimit -c unlimited pour écrire des dumps de cœur. Attention, un dump de cœur peut contenir des informations sensibles telles que des mots de passe ou des paramètres de configuration.

fatal-warnings: définit g_log_set_always_fatal() pour planter sur les messages d'avertissement de glib. Ceci est équivalent à l'option de ligne de commande --g-fatal-warnings.

autoconnect-retries-default

Le nombre de fois où une activation de connexion doit être automatiquement tentée avant de passer à une autre. Cette valeur s'applique uniquement aux connexions qui peuvent se connecter automatiquement et dont la propriété connection.autoconnect-retries est définie sur -1. Si non spécifié, les connexions seront tentées 4 fois. Définir cette valeur sur 1 signifie tenter l'activation une fois, sans nouvelle tentative.

firewall-backend

Le backend de pare-feu pour la configuration du masquage en mode partagé. Défini sur iptables, nftables ou none. iptables et nftables nécessitent respectivement les applications iptables et nft. none signifie ignorer la configuration du pare-feu si les utilisateurs souhaitent gérer le pare-feu eux-mêmes. Si non spécifié, il sera détecté automatiquement.

iwd-config-path

Si la valeur est "auto" (la valeur par défaut), IWD est interrogé pour son répertoire d'état actuel lorsqu'il apparaît sur D-Bus -- le répertoire où IWD conserve ses fichiers de configuration réseau -- généralement /var/lib/iwd. NetworkManager tentera alors d'écrire des copies des profils de connexion nouveaux ou modifiés, convertis au format IWD, dans ce répertoire, rendant ainsi les propriétés de connexion IWD modifiables. NM écrasera les fichiers existants sans en préserver le contenu.

Le chemin peut également être remplacé en pointant vers un répertoire spécifique existant et inscriptible. D'un autre côté, définir ceci sur une chaîne vide ou toute autre valeur désactive le mécanisme de conversion de profil.

Ce mécanisme permet de modifier les paramètres du profil de connexion tels que la configuration 802.1x à l'aide des clients NetworkManager. Sans cela, de tels changements n'ont aucun effet sur IWD.

migrate-ifcfg-rh

Si NetworkManager tente de convertir automatiquement tout profil de connexion stocké au format ifcfg-rh au format keyfile. La prise en charge de ifcfg-rh est obsolète et sera éventuellement supprimée. Si activée, la migration est effectuée à chaque démarrage du démon. La valeur par défaut est false.

SECTION KEYFILE

Cette section contient les options spécifiques au plugin keyfile, et n'est normalement utilisée que si vous n'utilisez aucun autre plugin spécifique à la distribution.

hostname

Cette clé est obsolète et n'a plus aucun effet car le nom d'hôte est maintenant stocké dans /etc/hostname ou d'autres fichiers de configuration système selon les options de compilation.

path

L'emplacement où les keyfiles sont lus et stockés. Ceci est par défaut "/etc/NetworkManager/system-connections".

rename

NetworkManager choisit automatiquement un nom de fichier lors du stockage d'un nouveau profil sur disque. Ce nom dépend du nom du profil (connection.id). Lors de la mise à jour du nom d'un profil, le fichier n'est pas renommé afin de ne pas casser les scripts qui dépendent du nom de fichier pour le profil. En définissant cette option sur "true", NetworkManager renomme le keyfile lors de la mise à jour du profil, afin de suivre le nom du profil. Ceci est par défaut "false".

unmanaged-devices

Définit les périphériques qui doivent être ignorés par NetworkManager.

Un périphérique non géré en raison de cette option est strictement non géré et ne peut être annulé en utilisant l'API comme nmcli device set $IFNAME managed yes. De plus, un périphérique qui n'est pas géré pour d'autres raisons, comme une règle udev, ne peut pas être rendu géré avec cette option (par exemple, en utilisant un spécificateur except:). Ces deux points le différencient de l'option device*.managed qui peut pour cette raison être un meilleur choix.

Voir la section "Format de la liste des périphériques" pour la syntaxe sur la façon de spécifier un périphérique.

Exemple :

unmanaged-devices=interface-name:em4
unmanaged-devices=mac:00:22:68:1c:59:b1;mac:00:1E:65:30:D1:C4;interface-name:eth2

SECTION IFUPDOWN

Cette section contient les options spécifiques à ifupdown et n'a donc d'effet que lors de l'utilisation du plugin ifupdown.

managed

Si défini sur true, les interfaces listées dans /etc/network/interfaces sont gérées par NetworkManager. Si défini sur false, toute interface listée dans /etc/network/interfaces sera ignorée par NetworkManager. Rappelez-vous que NetworkManager contrôle la route par défaut, donc comme l'interface est ignorée, NetworkManager peut attribuer la route par défaut à une autre interface.

La valeur par défaut est false.

SECTION DEJOURNALISATION

Cette section contrôle la journalisation de NetworkManager. La journalisation est très importante pour comprendre ce que NetworkManager fait. Lorsque vous signalez un bug, vous ne devez pas filtrer ou limiter inutilement le fichier journal. Activez simplement level=TRACE et domains=ALL pour collecter tout.

La méthode recommandée pour activer la journalisation est d'utiliser un fichier /etc/NetworkManager/conf.d/95-logging.conf qui contient

[logging]
level=TRACE
domains=ALL

et redémarrez le démon avec systemctl restart NetworkManager. Ensuite, reproduisez le problème. Vous pouvez trouver les journaux dans syslog (par exemple journalctl, ou journalctl -u NetworkManager pour n'afficher que les journaux de NetworkManager).

Toute configuration ici est remplacée par les options de ligne de commande --log-level et --log-domains. Vous pouvez également reconfigurer la journalisation à la volée avec nmcli general logging level "$LEVEL" domains "$DOMAINS". Cependant, il est souvent intéressant d'obtenir un journal complet dès le début. En particulier, lors du débogage d'un problème, activez la journalisation de niveau TRACE dans NetworkManager.conf et redémarrez le service pour activer une journalisation détaillée en temps réel.

En définissant nm.debug dans la ligne de commande du noyau (depuis /run/NetworkManager/proc-cmdline ou /proc/cmdline), la journalisation de débogage est activée. Cela remplace à la fois les options de ligne de commande et les configurations de NetworkManager.conf.

La journalisation de NetworkManager s'efforce de ne pas contenir de données sensibles privées et devrait être acceptable à partager. Cependant, il peut y avoir des adresses IP et des configurations réseau qui, si vous les considérez privées, doivent être vérifiées avant d'être partagées. Évitez cependant de modifier le journal de manière à en déformer le sens.

NetworkManager utilise syslog ou systemd-journald, selon la configuration. Dans tous les cas, les journaux de débogage sont verbeux et peuvent être limités ou filtrés par le démon de journalisation. Pour systemd-journald, consultez RateLimitIntervalSec et RateLimitBurst dans journald.conf pour savoir comment désactiver cela.

level

Le niveau de verbosité par défaut de la journalisation. L'un des suivants : OFF, ERR, WARN, INFO, DEBUG, TRACE, par ordre de verbosité croissant.

OFF désactive toute journalisation. INFO est le niveau de verbosité par défaut pour les opérations régulières. TRACE est pour le débogage.

Les autres niveaux sont le plus souvent inutiles. Par exemple, DEBUG est entre TRACE et INFO, mais est trop verbeux pour les opérations régulières et manque de messages intéressants pour le débogage. Dans la plupart des cas, lors du débogage d'un problème ou du signalement d'un bug, collectez les journaux de niveau TRACE pour avoir une vue d'ensemble.

domains

Filtre les messages par leur sujet. Lors du débogage d'un problème, il est préférable de collecter tous les journaux (domains=ALL) au début. Les parties inutiles peuvent toujours être ignorées plus tard.

Dans le cas rare de réglage de certains sujets, les domaines de journalisation suivants sont disponibles : PLATFORM, RFKILL, ETHER, WIFI, BT, MB, DHCP4, DHCP6, PPP, WIFI_SCAN, IP4, IP6, AUTOIP4, DNS, VPN, SHARING, SUPPLICANT, AGENTS, SETTINGS, SUSPEND, CORE, DEVICE, OLPC, WIMAX, INFINIBAND, FIREWALL, ADSL, BOND, VLAN, BRIDGE, DBUS_PROPS, TEAM, CONCHECK, DCB, DISPATCH, AUDIT, SYSTEMD, VPN_PLUGIN, PROXY.

De plus, ces domaines spéciaux peuvent être utilisés : NONE, ALL, DEFAULT, DHCP, IP.

Vous pouvez spécifier des remplacements de niveau de journalisation par domaine avec un deux-points et un niveau de journalisation dans n'importe quel domaine. Par exemple, "WIFI:DEBUG,WIFI_SCAN:OFF". Un autre exemple est ALL,VPN_PLUGIN:TRACE pour activer toute la journalisation (voir ci-dessous à propos de VPN_PLUGIN).

En général, le fichier journal ne doit pas contenir de mots de passe ou de données privées. Cependant, il est toujours conseillé de vérifier le fichier avant de le publier ou de le joindre à un rapport de bug. C'est pourquoi ce domaine sera exclu lors de la définition de ALL ou DEFAULT avec des niveaux plus verbeux que INFO.

backend

Le backend de journalisation. Les valeurs supportées sont "syslog" et "journal". Lorsque NetworkManager est démarré avec "--debug", tous les messages seront également imprimés sur stderr. Si non spécifié, la valeur par défaut est "journal".

audit

Les journaux d'audit sont-ils envoyés à auditd, le démon d'audit. S'il est faux, les journaux sont uniquement envoyés au système de journalisation de NetworkManager. S'il est défini sur vrai, ils sont également envoyés à auditd. La valeur par défaut est vrai.

SECTION CONNEXION

Spécifie les valeurs par défaut pour les connexions.

Ces valeurs par défaut ne sont consultées que si la propriété correspondante du profil de connexion le permet. Cela signifie que toutes ces propriétés correspondent à une propriété du profil de connexion (par exemple, connection.mud-url). Ce n'est que si la propriété du profil est définie sur une valeur spéciale indiquant qu'il faut utiliser la valeur par défaut que la valeur par défaut de NetworkManager.conf est consultée. Selon la propriété, la valeur spéciale indiquant le remplacement de la valeur par défaut est souvent quelque chose comme une valeur vide, une valeur non définie, ou une valeur numérique spéciale comme 0 ou -1. Cela signifie que la valeur effectivement utilisée peut d'abord être configurée pour chaque profil, et ces valeurs par défaut ne sont pertinentes que si la valeur du profil est explicitement définie pour utiliser la valeur par défaut de NetworkManager.conf.

Note : Bien que nmcli prenne en charge plusieurs alias et fonctionnalités pratiques pour configurer les propriétés, les configurations de cette section ne le font pas. Par exemple, les valeurs énumérées ne peuvent généralement être configurées que par leur nombre magique numérique.

Exemple :

[connection]
ipv6.ip6-privacy=0

Propriétés supportées

Toutes les propriétés ne peuvent pas être remplacées, seules les suivantes sont supportées pour définir les valeurs par défaut (voir nm-settings-nmcli(5) pour les détails).

802-1x.auth-timeout

cdma.mtu

connection.auth-retries

Si non spécifié, la valeur par défaut est de 3 tentatives avant d'échouer la connexion.

connection.autoconnect-ports

connection.autoconnect-slaves

Ceci est obsolète, veuillez utiliser "connection.autoconnect-ports" à la place.

connection.down-on-poweroff

La connexion sera-t-elle désactivée avant l'arrêt du système ?

connection.ip-ping-addresses-require-all

Est-ce qu'un seul ping réussi dans la liste des adresses cibles suffit, ou tous les pings doivent-ils réussir sur toute la liste des adresses cibles ?

connection.mud-url

Si non spécifié, l'URL MUD se comporte par défaut comme "none".

connection.lldp

connection.llmnr

Si non spécifié, les valeurs par défaut dépendent du plugin DNS. Avec systemd-resolved, la valeur par défaut est actuellement "yes" (2) et pour les autres plugins c'est "no" (0).

Actuellement, seul le plugin DNS systemd-resolve prend en charge cette configuration. Si la valeur n'est spécifiée ni dans le profil ni dans la valeur globale ici, la valeur est déterminée par systemd-resolved. Voir MulticastDNS= dans resolved.conf(5).

Si non spécifié, la valeur de repli est 0x22 ("enabled,subflow"). Cependant, si le système sysctl /proc/sys/net/mptcp/enabled est désactivé, NetworkManager ne configurera toujours pas les points d'extrémité.

Si non spécifié, les valeurs par défaut dépendent du plugin DNS. Avec systemd-resolved, la valeur par défaut est la configuration globale et pour les autres plugins c'est "no" (0).

Si non spécifié, il se comporte comme la valeur par défaut "00:00:00:00:00:00".

Sections

Vous pouvez configurer plusieurs sections de connexion en ayant différentes sections dont le nom commence par "connection". Exemple :

[connection]
ipv6.ip6-privacy=0
connection.autoconnect-ports=1
vpn.timeout=120
[connection-wifi-wlan0]
match-device=interface-name:wlan0
ipv4.route-metric=50
[connection-wifi-other]
match-device=type:wifi
ipv4.route-metric=55
ipv6.ip6-privacy=1

Les sections d'un même fichier sont traitées dans l'ordre d'apparition, à l'exception de la section [connection] qui est toujours traitée en dernier. Dans l'exemple ci-dessus, l'ordre est [connection-wifi-wlan0], [connection-wlan-other] et [connection]. Lors de la recherche d'une valeur de configuration par défaut, les sections sont parcourues jusqu'à ce que la valeur demandée soit trouvée. Dans l'exemple ci-dessus, "ipv4.route-metric" pour l'interface wlan0 est défini sur 50, et pour toutes les autres interfaces de type Wi-Fi sur 55. De plus, les appareils Wi-Fi auraient les adresses privées IPv6 activées par défaut, mais les autres appareils l'auraient désactivée. Notez que "wlan0" obtient également "ipv6.ip6-privacy=1", car bien que la section "[connection-wifi-wlan0]" corresponde à l'appareil, elle ne contient pas cette propriété et la recherche se poursuit.

Lorsque vous avez différentes sections dans plusieurs fichiers, les sections des fichiers lus ultérieurement ont une priorité plus élevée. Ainsi, au sein d'un même fichier, la priorité des sections va de haut en bas. Entre plusieurs fichiers, les définitions ultérieures priment.

Les propriétés suivantes contrôlent en outre l'application d'une section de connexion.

match-device

Une spécification d'appareil optionnelle qui restreint l'application de la section. Voir la section intitulée « Format de la liste des appareils » pour les valeurs possibles.

stop-match

Une valeur booléenne optionnelle qui vaut "non" par défaut. Si la section correspond (sur la base de match-device), les sections ultérieures ne seront pas prises en compte même si la propriété en question n'est pas présente. Dans l'exemple ci-dessus, si [connection-wifi-wlan0] avait stop-match défini sur oui, l'appareil wlan0 aurait la propriété ipv6.ip6-privacy non spécifiée. Autrement dit, la recherche de la propriété ne se poursuivrait pas dans les sections de connexion [connection-wifi-other]
] ou [connection].

SECTION DESAPPAREILS

Contient la configuration persistante par appareil.

Exemple :

[device]
match-device=interface-name:eth3
managed=1

Propriétés prises en charge

Les propriétés suivantes peuvent être configurées par appareil.

managed

Indique si l'appareil est géré ou non. Un appareil peut être marqué comme géré via les règles udev (ENV{NM_UNMANAGED}) ou via les plugins de configuration (keyfile.unmanaged-devices). C'est encore une autre façon de faire. Notez que cette configuration peut être annulée à l'exécution via D-Bus. Elle a également une priorité plus élevée que les règles udev.

carrier-wait-timeout

Spécifie le délai d'attente pour le signal porteur en millisecondes. La valeur par défaut est de 6000 millisecondes. Ce paramètre existe car certains pilotes/matériels peuvent prendre beaucoup de temps pour détecter si le câble est branché.

Lorsque l'appareil perd le signal porteur, NetworkManager ne réagit pas immédiatement. Au lieu de cela, il attend ce délai avant de considérer la liaison comme perdue.

De plus, au démarrage, NetworkManager considère l'appareil comme occupé pendant ce temps, tant que l'appareil n'a pas de signal porteur. Cela retarde le signal de fin de démarrage et NetworkManager-wait-online. Configurer une valeur trop élevée signifie bloquer NetworkManager-wait-online plus longtemps que nécessaire lors du démarrage avec le câble débranché. La configurer trop bas signifie que NetworkManager déclarera la fin du démarrage trop tôt, bien que le signal porteur soit sur le point d'arriver et que l'activation automatique soit sur le point de se produire. Notez que si un profil n'a qu'une configuration IP statique ou si la configuration de couche 3 est désactivée, il peut déjà se connecter automatiquement sans signal porteur sur l'appareil. Une fois qu'un tel profil atteint l'état entièrement activé, la fin du démarrage est considérée comme atteinte même si l'appareil n'a pas encore de signal porteur.

ignore-carrier

Spécifie les appareils pour lesquels NetworkManager ignorera (partiellement) l'état du signal porteur. Normalement, pour les types d'appareils qui prennent en charge la détection du signal porteur, tels que Ethernet et InfiniBand, NetworkManager n'autorisera l'activation d'une connexion sur l'appareil que si le signal porteur est présent (c'est-à-dire qu'un câble est branché), et il désactivera l'appareil si le signal porteur disparaît pendant quelques secondes.

Un appareil pour lequel le signal porteur est ignoré permettra d'activer des connexions sur cet appareil même lorsqu'il n'a pas de signal porteur, à condition que la connexion utilise uniquement des adresses IP configurées statiquement. De plus, il permettra à toute connexion active (statique ou dynamique) de rester active sur l'appareil lorsque le signal porteur est perdu.

Notez que la propriété "carrier" des interfaces D-Bus des NMDevices et des appareils reflétera toujours l'état réel de l'appareil ; c'est juste que NetworkManager n'utilisera pas cette information.

Les types maîtres tels que bond, bridge et team ignorent le signal porteur par défaut, tandis que d'autres types d'appareils réagissent aux changements de signal porteur par défaut.

Ce paramètre remplace le paramètre principal obsolète main.ignore-carrier ci-dessus.

keep-configuration

Au démarrage, NetworkManager essaie de ne pas interférer avec les interfaces déjà configurées. Il le fait en générant une connexion en mémoire basée sur la configuration actuelle de l'interface.

Si cette connexion générée correspond à l'une des connexions persistantes existantes, la connexion persistante est activée. S'il n'y a pas de correspondance, la connexion générée est activée comme "externe", ce qui signifie que la connexion est considérée comme active, mais NetworkManager ne touche pas réellement à l'interface.

Il est possible de désactiver ce comportement en réglant keep-configuration sur "no". De cette façon, au démarrage, NetworkManager essaie toujours d'activer la connexion persistante la plus appropriée (celle avec la priorité d'auto-connexion la plus élevée ou, en cas d'égalité, celle activée le plus récemment).

Notez que lorsque NetworkManager est redémarré, il stocke l'état précédent dans /run/NetworkManager ; en particulier, il enregistre l'UUID de la connexion précédemment active afin qu'elle puisse être réactivée après le redémarrage. Par conséquent, keep-configuration n'a aucun effet sur le redémarrage du service.

allowed-connections

Une liste de connexions qui peuvent être activées sur l'appareil. Voir la section "Format de liste de connexions" pour la syntaxe de spécification d'une connexion. Si cette option n'est pas spécifiée, toutes les connexions peuvent potentiellement être activées sur l'appareil, à condition que le type de connexion et les autres paramètres correspondent.

Un cas d'utilisation notable est de filtrer les connexions qui peuvent être activées en fonction de la manière dont elles ont été créées ; voir le mot-clé origin dans la section "Format de liste de connexions".

wifi.scan-rand-mac-address

Configure la randomisation de l'adresse MAC d'un appareil Wi-Fi pendant le scan. La valeur par défaut est "yes", auquel cas une adresse MAC aléatoire et localement administrée sera utilisée. Le paramètre wifi.scan-generate-mac-address-mask peut être utilisé pour influencer l'adresse MAC générée afin d'utiliser certains OUI de fournisseurs. Si désactivé, l'adresse MAC pendant le scan reste inchangée par rapport à ce qui est configuré. Pour l'adresse MAC configurée pendant que l'appareil est associé, voir plutôt le paramètre par connexion wifi.cloned-mac-address.

wifi.backend

Spécifie le backend Wi-Fi utilisé pour l'appareil. Actuellement, les options prises en charge sont wpa_supplicant et iwd (expérimental). Si non spécifié, la valeur par défaut est "wpa_supplicant".

wifi.scan-generate-mac-address-mask

Comme les paramètres par connexion ethernet.generate-mac-address-mask et wifi.generate-mac-address-mask, cela peut être utilisé pour configurer les adresses MAC générées pendant le scan. Voir nm-settings-nmcli(5) pour plus de détails.

wifi.iwd.autoconnect

Si wifi.backend est iwd, régler cette option sur "false" force la désactivation du mécanisme d'auto-connexion de IWD pour cet appareil et les connexions seront initiées uniquement par NetworkManager, qu'elles soient commandées par un client ou automatiques. La laisser sur "true" (par défaut) empêche NetworkManager d'initier automatiquement des connexions et permet à IWD d'utiliser sa logique de classement et de scan des réseaux pour décider des meilleurs réseaux auxquels se connecter automatiquement ensuite. Les paramètres d'auto-connexion-priorité et de tentatives-d'auto-connexion des connexions seront ignorés. D'autres paramètres comme les permissions ou le multi-connexion peuvent interférer avec les tentatives de connexion de IWD.

sriov-num-vfs

Spécifie le nombre de fonctions virtuelles (VF) à activer pour un appareil physique PCI prenant en charge la virtualisation single-root I/O (SR-IOV).

Sections

La section [device] fonctionne de la même manière que la section [connection]. C'est-à-dire que plusieurs sections commençant toutes par le préfixe "device" peuvent être spécifiées. Les paramètres "match-device" et "stop-match" sont disponibles pour faire correspondre une section d'appareil à un appareil. L'ordre des sections multiples est également de haut en bas dans le fichier et les fichiers ultérieurs écrasent les paramètres précédents. Voir "Sections" dans la section "SECTION DE CONNEXION" pour les détails.

SECTION CONNECTIVITY

Cette section contrôle la fonctionnalité optionnelle de vérification de connectivité de NetworkManager. Cela permet à NetworkManager de détecter si le système peut réellement accéder à Internet ou s'il est derrière un portail captif.

La vérification de connectivité sert deux objectifs. D'une part, elle expose un état de connectivité sur D-Bus, que d'autres applications peuvent utiliser. Par exemple, l'assistant de portail de Gnome utilise cela comme signal pour afficher une page de connexion de portail captif. L'autre utilisation est que la route par défaut des appareils sans connectivité globale se voit pénaliser de +20000 en métrique de route. Ceci a pour but de fournir une meilleure route par défaut aux appareils ayant une connectivité globale. Par exemple, lorsqu'il est connecté à WWAN et à un réseau Wi-Fi derrière un portail captif, WWAN reste préféré jusqu'à la connexion.

Notez que votre distribution pourrait définir /proc/sys/net/ipv4/conf/*/rp_filter sur un filtrage strict. Cela fonctionne mal avec la vérification de connectivité par appareil, qui utilise SO_BINDDEVICE pour envoyer des requêtes sur tous les appareils. Un réglage rp_filter strict rejettera toute réponse et la vérification de connectivité sur toutes les routes sauf la meilleure échouera.

enabled

Indique si la vérification de connectivité est activée. Notez que pour activer la vérification de connectivité, une URI valide doit également être configurée. La valeur est vraie par défaut, mais comme l'URI est non définie par défaut, la vérification de connectivité peut être désactivée. Le but principal de cette option est d'avoir un seul indicateur pour désactiver la vérification de connectivité. Notez que ce paramètre peut également être défini via l'API D-Bus à l'exécution. Dans ce cas, la valeur est stockée dans le fichier /var/lib/NetworkManager/NetworkManager-intern.conf.

uri

L'URI d'une page Web à demander périodiquement lors de la vérification de la connectivité. Cette page doit renvoyer l'en-tête "X-NetworkManager-Status" avec la valeur "online". Alternativement, le contenu de son corps doit être défini sur "NetworkManager is online". La vérification du contenu du corps peut être contrôlée par l'option "response". Si cette option est vide ou manquante, la vérification de connectivité est désactivée.

interval

Spécifié en secondes ; contrôle la fréquence de vérification de la connectivité lorsqu'une connexion réseau existe. Si réglé sur 0, la vérification de connectivité est désactivée. Si absent, la valeur par défaut est de 300 secondes.

timeout

Spécifié en secondes ; contrôle combien de temps attendre une réponse avant que la connectivité ne soit marquée comme limitée. Si absent, la valeur par défaut est de 20 secondes.

response

Si défini, contrôle quel contenu du corps NetworkManager vérifie lors de la requête de l'URI pour la vérification de connectivité. Notez que cela compare uniquement si la réponse HTTP commence par le texte spécifié, cela ne compare pas la chaîne exacte. Ce comportement pourrait changer à l'avenir, alors évitez de vous y fier. Si absent, la réponse par défaut est "NetworkManager is online". Si réglé sur vide, le serveur HTTP est censé répondre avec le code de statut 204 ou n'envoyer aucune donnée.

NAME

NetworkManager : Gestion du réseau sous Linux

SYNOPSIS

Le format de fichier suivant est utilisé :

interface-name:vboxnet*,except:interface-name:vboxnet2
*,except:mac:00:22:68:1c:59:b1

DESCRIPTION

Le fichier contient une liste de connexions qui peuvent être spécifiées comme suit :

*

Correspond à n'importe quelle connexion.

uuid:UUID

Correspond à la connexion par son UUID, par exemple

uuid:83037490-1d17-4986-a397-01f1db3a7fc2

id:ID

Correspond à la connexion par son nom.

origin:ORIGIN

Correspond à la connexion par son origine, stockée dans le tag org.freedesktop.NetworkManager.origin des paramètres utilisateur. Par exemple, utilisez except:origin:nm-initrd-generator pour interdire l'activation des connexions créées par le générateur d'initrd.

except:SPEC

Correspond à une exclusion de connexion. Une exclusion a une priorité plus élevée que les correspondances positives précédentes.

S'il n'y a qu'une liste d'exclusions, le comportement est le même que s'il y avait également une correspondance universelle. Cela signifie que si aucune des exclusions ne correspond, le résultat global sera toujours une correspondance positive.

FILE FORMAT

Les spécifications peuvent être concaténées avec des virgules ou des points-virgules. L'ordre n'a pas d'importance car les spécifications sont inclusives ou exclusives (except:), les exclusions ayant la priorité la plus élevée.

Le caractère backslash est supporté pour échapper les séparateurs ';' et ',', ainsi que pour exprimer des caractères spéciaux tels que la nouvelle ligne ('\n'), la tabulation ('\t'), l'espace ('\s') et le backslash ('\\'). L'espace n'est pas un séparateur mais sera supprimé entre deux spécifications (sauf s'il est échappé comme '\s').
