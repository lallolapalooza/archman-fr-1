NetworkManager-dispatcher(8) Services de gestion de réseau NetworkManager-dispatcher(8)

Nom

NetworkManager-dispatcher - Déclencher des scripts utilisateur pour NetworkManager

Synopsis

NetworkManager [OPTIONS]

Description

Le service NetworkManager-dispatcher est un service activé par D-Bus qui exécute des scripts utilisateur en réponse à certains changements dans NetworkManager.

NetworkManager-dispatcher exécute des scripts dans le répertoire /etc/NetworkManager/dispatcher.d ou dans des sous-répertoires par ordre alphabétique lorsque des événements réseau se produisent. Les fichiers dans /etc ont la priorité sur ceux identifiés dans /usr/lib. Chaque script doit être un fichier exécutable régulier appartenant à root. De plus, il ne doit pas être inscriptible par le groupe ou les autres, et ne doit pas avoir l'attribut setuid.

Chaque script reçoit deux arguments : le premier est le nom de l'interface sur laquelle l'opération a été effectuée, et le second est l'action. Pour les actions sur les périphériques, l'interface est le nom de l'interface réseau appropriée pour la configuration IP. Ainsi, il peut s'agir de VPN_IP_IFACE, DEVICE_IP_IFACE ou DEVICE_IFACE, selon le cas. Pour l'action hostname, le nom de l'interface est toujours "none". Pour les actions connectivity-change et dns-change, le nom de l'interface est vide.

Les actions sont :

pre-up

L'interface est connectée au réseau mais pas encore complètement activée. Les scripts agissant sur cet événement doivent être placés ou liés dans le répertoire /etc/NetworkManager/dispatcher.d/pre-up.d, et NetworkManager attend que le script soit complètement exécuté avant d'indiquer aux applications que l'interface est complètement activée.

up

L'interface a été activée.

pre-down

L'interface va être désactivée mais n'a pas encore été déconnectée du réseau. Les scripts agissant sur cet événement doivent être placés ou liés dans le répertoire /etc/NetworkManager/dispatcher.d/pre-down.d, et NetworkManager attend que le script soit complètement exécuté avant de déconnecter l'interface de son réseau. Note : cet événement n'est pas émis en cas de déconnexion forcée, comme lorsque l'opérateur perd la connexion ou qu'un signal réseau passe sous le seuil. Il n'est émis que lorsqu'il y a une possibilité de gérer proprement une déconnexion réseau.

down

L'interface a été désactivée.

vpn-pre-up

La connexion VPN est connectée au réseau mais pas encore complètement activée. Les scripts agissant sur cet événement doivent être placés ou liés dans le répertoire /etc/NetworkManager/dispatcher.d/pre-up.d, et NetworkManager attend que le script soit complètement exécuté avant d'indiquer aux applications que la connexion VPN est complètement activée.

vpn-up

Une connexion VPN a été activée.

vpn-pre-down

La connexion VPN va être désactivée mais n'a pas encore été déconnectée du réseau. Les scripts agissant sur cet événement doivent être placés ou liés dans le répertoire /etc/NetworkManager/dispatcher.d/pre-down.d, et NetworkManager attend que le script soit complètement exécuté avant de déconnecter la connexion VPN de son réseau. Note : cet événement n'est pas émis en cas de déconnexion forcée, comme lorsque la connexion VPN se termine de manière inattendue ou lorsque la connectivité générale est perdue. Il n'est émis que lorsqu'il y a une possibilité de gérer proprement la déconnexion d'une connexion VPN.

vpn-down

Une connexion VPN a été désactivée.

hostname

Le nom du système a été mis à jour. Utilisez gethostname(2) pour le récupérer. Le nom de l'interface (premier argument) est vide et aucune variable d'environnement n'est définie pour cette action.

dhcp4-change

Le bail DHCPv4 a changé (renouvellement, regroupement, etc.).

dhcp6-change

Le bail DHCPv6 a changé (renouvellement, regroupement, etc.).

connectivity-change

L'état de connectivité réseau a changé (pas de connexion, connecté, etc.).

reapply

La connexion a été réappliquée sur le périphérique.

dns-change

La configuration DNS a changé. Cette action est générée même si NetworkManager est configuré pour ne pas gérer resolv.conf (par exemple, avec dns=none). Dans ce cas, le script déclencheur peut découvrir la configuration DNS fournie par les connexions actuelles en consultant le fichier /run/NetworkManager/resolv.conf.

device-add

Cette action est appelée lorsqu'une connexion de type générique a la propriété generic.device-handler définie. La propriété indique le nom d'un script déclencheur à exécuter dans le répertoire /etc/NetworkManager/dispatcher.d/device. Note : contrairement aux autres actions, un seul script sera exécuté.

Le script doit effectuer toute action nécessaire pour créer l'interface pour la connexion de type générique. En cas de succès, il retourne 0. En cas d'échec, il retourne une valeur non nulle. Le script peut retourner des valeurs à NetworkManager en écrivant sur la sortie standard ; chaque ligne doit contenir un nom de clé suivi de '=' et de la valeur de la clé. Les clés actuellement comprises sont :

IFINDEX

Indique l'index de l'interface créée par le script. Cette clé est requise si le script réussit ; si elle n'est pas définie, l'activation échouera. La clé est ignorée en cas d'échec du script.

ERROR

Indique un message d'erreur expliquant la raison de l'échec du script. Elle est ignorée lorsque le script réussit.

Comme le service déclencheur capture la sortie standard pour analyser ces clés, tout ce qui est écrit sur la sortie standard n'apparaîtra pas dans le journal du service déclencheur. Utilisez la sortie d'erreur pour imprimer des messages dans le journal (par exemple, pour le débogage). Seuls les 8 premiers Kio de la sortie standard et, parmi ceux-ci, les 64 premières lignes sont pris en compte ; le reste est ignoré.

device-delete

Cette action est l'inverse de device-add et est appelée pour supprimer l'interface d'une connexion de type générique. Tous les aspects décrits pour device-add s'appliquent également à cette action, à l'exception que la clé IFINDEX est ignorée. Il n'est pas nécessaire de supprimer le lien noyau dans le gestionnaire car NetworkManager s'en charge déjà ; par conséquent, l'action est utile pour tout nettoyage supplémentaire requis.

L'environnement contient plus d'informations sur l'interface et la connexion. Les variables suivantes sont disponibles pour être utilisées dans les scripts déclencheurs :

NM_DISPATCHER_ACTION

L'action de déclenchement telle que "up" ou "dhcp4-change", identique au premier argument de la ligne de commande. Depuis NetworkManager 1.12.0.

CONNECTION_UUID

L'UUID de la configuration de connexion.

CONNECTION_ID

Le nom (ID) de la configuration de connexion.

CONNECTION_DBUS_PATH

Le chemin D-Bus de NetworkManager pour la connexion.

CONNECTION_FILENAME

Le nom du fichier de support de la configuration de connexion (s'il existe).

CONNECTION_EXTERNAL

Si "1", indique que la connexion décrit une configuration réseau créée en dehors de NetworkManager.

DEVICE_IFACE

Le nom de l'interface de contrôle du périphérique. Selon le type de périphérique, il diffère de DEVICE_IP_IFACE. Par exemple, pour les périphériques ADSL, il pourrait s'agir de "atm0" ou pour les périphériques WWAN, il pourrait s'agir de "ttyUSB0".

DEVICE_IP_IFACE

Le nom de l'interface IP du périphérique. C'est l'interface réseau sur laquelle les adresses IP et les routes seront configurées.

IP4_ADDRESS_N

L'adresse IPv4 au format "adresse/préfixe passerelle", où N est un nombre de 0 à (# adresses IPv4 - 1). L'élément passerelle dans cette variable est considéré comme obsolète, utilisez IP4_GATEWAY à la place.

IP4_NUM_ADDRESSES

La variable contient le nombre d'adresses IPv4 que le script peut s'attendre à trouver.

IP4_GATEWAY

L'adresse IPv4 de la passerelle en notation décimale pointée traditionnelle.

IP4_ROUTE_N

La route IPv4 au format "adresse/préfixe prochaine-saut métrique", où N est un nombre de 0 à (# routes IPv4 - 1).

IP4_NUM_ROUTES

La variable contient le nombre de routes IPv4 que le script peut s'attendre à trouver.

IP4_NAMESERVERS

La variable contient une liste d'espaces des serveurs DNS actifs.
S serveurs.

IP4_DOMAINS

La variable contient une liste d'espaces des domaines de recherche.

DHCP4_<dhcp-option-name>

Si la connexion a utilisé DHCP pour la configuration d'adresse, la configuration DHCP reçue est passée dans l'environnement en utilisant les noms d'options DHCP standard, préfixés par "DHCP4_", comme "DHCP4_HOST_NAME=foobar".

IP6_<name> et DHCP6_<name>

Les mêmes variables que pour IPv4 sont disponibles pour IPv6, mais les préfixes sont IP6_ et DHCP6_ à la place.

CONNECTIVITY_STATE

L'état de la connectivité réseau, qui peut prendre les valeurs définies par le type NMConnectivityState, de l'API D-Bus org.freedesktop.NetworkManager : UNKNOWN, NONE, PORTAL, LIMITED ou FULL. Remarque : cette variable ne sera définie que pour les actions de changement de connectivité.

En cas de VPN, VPN_IP_IFACE est défini, et les variables IP4_*, IP6_* avec le préfixe VPN sont également exportées, comme VPN_IP4_ADDRESS_0, VPN_IP4_NUM_ADDRESSES.

Le contenu du paramètre utilisateur pour la connexion en cours d'activation est également passé via les variables d'environnement. Chaque clé est stockée dans une variable nommée CONNECTION_USER_ concaténée avec le codage du nom de la clé. Le codage fonctionne comme suit :

•les lettres minuscules deviennent majuscules
•les lettres majuscules sont précédées d'un underscore
•les chiffres ne changent pas
•un point est remplacé par un double underscore
•tout autre caractère est codé avec un underscore suivi de sa représentation octale à 3 chiffres

Par exemple, la clé test.foo-Bar2 est stockée dans une variable nommée CONNECTION_USER_TEST__FOO_055_BAR2.

Les scripts de dispatch sont exécutés un par un, mais de manière asynchrone par rapport au processus principal NetworkManager, et seront tués s'ils s'exécutent trop longtemps. Si votre script risque de prendre un temps arbitrairement long pour s'achever, vous devriez créer un processus enfant et laisser le parent revenir immédiatement. Les scripts qui sont des liens symboliques pointant vers le répertoire /etc/NetworkManager/dispatcher.d/no-wait.d/ sont exécutés immédiatement, sans attendre la fin des scripts précédents, et en parallèle. Soyez également conscient qu'une fois qu'un script est mis en file d'attente, il sera toujours exécuté, même si un événement ultérieur le rend obsolète. (Par exemple, si une interface monte, puis redescend rapidement, il est possible qu'un ou plusieurs scripts "up" soient exécutés après que l'interface soit descendue.)
