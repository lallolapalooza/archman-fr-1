Enveloppement autour de NBD.create. Appelle la fonction d'entrée avec un nouveau handle, et s'assure que NBD.close est appelé même si la fonction lève une exception.

val set_debug_callback : t -> (string -> string -> int) -> unit

NBD.set_debug_callback t debug

Définit le callback de débogage.

Définit le callback de débogage. Cette fonction est appelée lorsque des messages de débogage de la bibliothèque sont émis, lorsque le débogage est activé sur un handle. Les paramètres de la fonction de rappel sont les « données utilisateur » passées à cette fonction, le nom de la fonction libnbd émettant le message (« contexte »), et le message lui-même (« msg »). S'il n'y a pas de callback de débogage défini sur un handle, les messages sont imprimés sur stderr.

Le callback ne doit pas appeler les API libnbd sur le même handle, car il pourrait être appelé tout en conservant le verrouillage du handle et provoquer un blocage.

val set_private_data : t -> int -> int

NBD.set_private_data t private_data

Définit les données privées du handle.

Les handles contiennent un champ de données privées que les applications peuvent utiliser à quelque fin que ce soit. Cette fonction définit la valeur de ce champ et retourne l'ancienne valeur (ou 0 si elle n'avait pas été précédemment définie).

val set_export_name : t -> string -> unit

NBD.set_export_name t export_name

définir le nom d'exportation

Certains serveurs NBD peuvent servir plusieurs images disque ("exports"). Le nom d'exportation est choisi par le client pendant le processus de négociation. Le nom d'exportation par défaut est la chaîne vide "".

Certains serveurs NBD ignorent cette valeur et servent le même contenu quel que soit le nom d'exportation. Cette fonctionnalité n'est pertinente que lors de la connexion à des serveurs utilisant le nouveau style de protocole, car l'ancien style ne prenait pas en charge les noms d'exportation.

Le protocole NBD limite les noms d'exportation à 4096 octets, mais les serveurs peuvent ne pas prendre en charge la longueur complète. Le codage des noms d'exportation est toujours UTF-8.

Si le mode option n'est pas utilisé, le nom d'exportation doit être défini avant de commencer une connexion. Cependant, lorsque nbd_set_opt_mode(3) a activé le mode option, il est possible de changer le nom d'exportation avant que nbd_opt_go(3) ne soit appelé. En particulier, l'utilisation de nbd_opt_list(3) pendant la négociation peut être utilisée pour déterminer un nom que le serveur est disposé à accepter, et nbd_opt_info(3) peut être utilisé pour apprendre des détails sur une exportation avant de se connecter.

Cet appel peut être omis si nbd_connect_uri(3) est utilisé pour se connecter à une URI qui inclut un nom d'exportation.

val get_export_name : t -> string

NBD.get_export_name t

obtenir le nom d'exportation

Obtient le nom d'exportation associé au descripteur. C'est le nom demandé par libnbd ; voir nbd_get_canonical_export_name(3) pour déterminer si le serveur a un nom canonique différent pour l'exportation donnée (plus courant lorsque le nom d'exportation par défaut est demandé, qui est une chaîne vide "").

val set_request_block_size : t -> bool -> unit

NBD.set_request_block_size t request

contrôler si le mode d'option NBD_OPT_GO demande des tailles de bloc

Par défaut, lors de la connexion à une exportation, libnbd demande au serveur de signaler toute contrainte de taille de bloc. Le protocole NBD indique qu'un serveur peut fournir des tailles de bloc indépendamment du fait que le client les demande, et libnbd signalera ces tailles (voir nbd_get_block_size(3)) ; cependant, si le client ne demande pas les tailles de bloc, le serveur peut refuser la connexion plutôt que de traiter une demande de client non alignée. Cette fonction permet de tester le comportement du serveur en émulant d'anciens clients.

Note : Même si la taille de bloc est demandée, le serveur n'est pas obligé de fournir une taille. De plus, si des tailles de bloc sont fournies (que le client les demande ou non), libnbd s'alignera sur ces tailles, sauf lorsque nbd_set_strict_mode(3) est utilisé pour éviter les vérifications de sécurité côté client.

val get_request_block_size : t -> bool

NBD.get_request_block_size t

voir si le mode d'option NBD_OPT_GO demande des tailles de bloc

Renvoie l'état du drapeau de demande de taille de bloc sur ce descripteur.

val set_full_info : t -> bool -> unit

NBD.set_full_info t request

contrôler si le mode d'option NBD_OPT_GO demande des détails supplémentaires

Par défaut, lors de la connexion à une exportation, libnbd ne demande que les détails nécessaires aux services de données. Le protocole NBD indique qu'un serveur peut fournir des informations facultatives, telles que le nom canonique de l'exportation (voir nbd_get_canonical_export_name(3)) ou une description de l'exportation (voir nbd_get_export_description(3)), mais qu'une indication du client rend plus probable la fourniture de ces informations supplémentaires. Cette fonction contrôle si libnbd fournira cette indication.

Note : Bien que des informations complètes soient demandées, le serveur n'est pas obligé de répondre avec tous les détails que libnbd a demandés. De même, libnbd ignorera toutes les informations facultatives du serveur qui n'ont pas été précédemment enseignées à libnbd. De plus, l'indication de demande de tailles de bloc est contrôlée indépendamment par nbd_set_request_block_size(3).

val get_full_info : t -> bool

NBD.get_full_info t

voir si le mode d'option NBD_OPT_GO demande des détails supplémentaires

Renvoie l'état du drapeau d'informations complètes sur ce descripteur.

val get_canonical_export_name : t -> string

NBD.get_canonical_export_name t

renvoyer le nom d'exportation canonique, si le serveur en a un

Le protocole NBD permet à un serveur de signaler un nom d'exportation facultatif, qui peut différer de celui demandé par le client (défini par nbd_set_export_name(3) ou nbd_connect_uri(3)). Cette fonction accède à tout nom renvoyé par le serveur ; il peut être identique à celui demandé par le client, mais il est plus susceptible de différer lorsque le client a demandé une connexion à l'exportation par défaut (une chaîne vide "").

Certains serveurs ne signaleront pas de nom d'exportation si le client ne le demande pas explicitement, via nbd_set_full_info(3).

val get_export_description : t -> string

NBD.get_export_description t

renvoyer la description d'exportation, si le serveur en a une

Le protocole NBD permet à un serveur de signaler une description d'exportation facultative. Cette fonction renvoie toute description renvoyée par le serveur.

Certains serveurs ne signaleront pas de description si le client ne la demande pas explicitement, via nbd_set_full_info(3). Pour qemu-nbd(8), une description est définie avec *-D*.

val set_tls : t -> TLS.t -> unit

NBD.set_tls t tls

activer ou exiger TLS (authentification et chiffrement)

Active ou exige TLS (connexions authentifiées et chiffrées) vers le serveur NBD. Les réglages possibles sont :

"LIBNBD_TLS_DISABLE" Désactiver TLS. (La valeur par défaut, sauf si nbd_connect_uri(3) est utilisé avec une URI qui exige TLS).

Ce réglage est également nécessaire si nbd_set_opt_mode(3) est utilisé et que vous souhaitez interagir en texte clair avec un serveur implémentant le mode "SELECTIVETLS" du protocole NBD avant d'activer TLS avec nbd_opt_starttls(3). La plupart des serveurs prenant en charge TLS préfèrent le mode "FORCEDTLS" du protocole NBD, donc cette forme d'interaction manuelle est principalement utile lors des tests d'intégration.

"LIBNBD_TLS_ALLOW" Activer TLS si possible.

Cette option est dangereuse (ou plutôt, une perte d'effort) dans certains cas, car elle pourrait se rabattre sur une connexion non chiffrée ou non authentifiée si TLS ne pouvait pas être établi. Utilisez "LIBNBD_TLS_REQUIRE" si la connexion doit être chiffrée.

Certains serveurs peuvent refuser la connexion si TLS échoue, de sorte que le repli n'est pas toujours possible.

"LIBNBD_TLS_REQUIRE" Exiger une connexion TLS chiffrée et authentifiée. Échoue toujours si la connexion n'est pas chiffrée et authentifiée.

En plus d'appeler cette commande, vous devrez peut-être également fournir le répertoire de certificats (nbd_set_tls_certificates(3)), le nom d'utilisateur (nbd_set_tls_username(3)) et/ou les fichiers de clés pré-partagées (PSK) (nbd_set_tls_psk_file(3)). Pour l'instant, lors de l'utilisation de nbd_connect_uri(3), tout paramètre de requête lié à TLS n'est pas géré automatiquement. La définition du niveau supérieur supérieur à zéro échouera si libnbd n'a pas été compilé avec gnutls ; vous pouvez vérifier si c'est le cas avec nbd_supports_tls(3).

val get_tls_negotiated : t -> bool

NBD.get_tls_negotiated t

voir si TLS a été négocié sur une connexion

Après la connexion, vous pouvez appeler cette fonction pour voir si la connexion utilise TLS.

Ceci est généralement utile uniquement si vous avez défini le mode de demande TLS sur "LIBNBD_TLS_ALLOW" (voir nbd_set_tls(3)), car dans ce mode, nous essayons d'utiliser TLS mais nous nous rabattons sur une connexion non chiffrée si elle n'est pas disponible. Cette fonction vous indiquera si TLS a été négocié ou non.

En mode "LIBNBD_TLS_REQUIRE" (plus sûr), la connexion échouerait si TLS n'était pas négocié. Avec le mode "LIBNBD_TLS_DISABLE", TLS n'est pas automatiquement tenté ; mais si le serveur utilise le mode moins courant "SELECTIVETLS", cette fonction indique si une connexion a été activée manuellement avec nbd_opt_starttls(3) ou si la connexion est toujours en texte clair.

val set_tls_certificates : t -> string -> unit

NBD.set_tls_certificates t dir

définir le chemin du répertoire des certificats TLS

Définit le chemin du répertoire des certificats TLS. S'il n'est pas défini et que TLS est utilisé, un chemin précompilé par défaut sera utilisé. Pour root, il s'agit de "/etc/pki/libnbd/". Pour non-root, il s'agit de "$HOME/.pki/libnbd" et "$HOME/.config/pki/libnbd". Si aucun de ces répertoires ne peut être trouvé, les CA de confiance du système sont utilisées.

Cette fonction peut être appelée indépendamment du fait que TLS soit pris en charge, mais n'aura aucun effet si nbd_set_tls(3) n'est pas utilisé pour demander ou exiger TLS.

val set_request_extended_headers : t -> bool -> unit

NBD.set_request_extended_headers t request

contrôler l'utilisation des en-têtes étendus

Par défaut, libnbd tente de négocier les en-têtes étendus avec le serveur, car cette extension de protocole permet l'utilisation des actions 64 bits, zero, trim et block status. Cependant, pour les tests d'intégration, il peut être utile de désactiver ce drapeau plutôt que de trouver un moyen de modifier le serveur pour échouer à la demande de négociation.

Pour des raisons de compatibilité ascendante, le réglage de ce bouton est ignoré si nbd_set_request_structured_replies(3) est également défini sur false, car l'utilisation d'en-têtes étendus implique des réponses structurées.

val get_extended_headers_negotiated : t -> bool

NBD.get_extended_headers_negotiated t

voir si les en-têtes étendus sont en cours d'utilisation

Après la connexion, vous pouvez appeler ceci pour savoir si la connexion utilise des en-têtes étendus. Notez que ce réglage est persistant ; cela peut renvoyer vrai même après qu'un second appel à nbd_opt_extended_headers(3) renvoie faux car le serveur a détecté une demande en double.

Lorsque les en-têtes étendus ne sont pas utilisés, les commandes sont limitées à une longueur de 32 bits, même lorsque l'API libnbd utilise un paramètre de 64 bits pour exprimer la longueur. Mais même lorsque les en-têtes étendus sont pris en charge, le serveur peut imposer d'autres limites, visibles via nbd_get_block_size(3).

Notez que lorsque les en-têtes étendus sont négociés, vous devriez préférer l'utilisation de nbd_block_status_64(3) à celle de nbd_block_status(3) si l'un des méta-contextes que vous avez demandés via nbd_add_meta_context(3) peut renvoyer des valeurs de statut 64 bits ; cependant, tous les méta-contextes bien connus couverts par les constantes actuelles "LIBNBD_CONTEXT_*" ne renvoient que des statuts 32 bits.

val set_request_structured_replies : t -> bool -> unit

Il est également utile de le définir sur faux avant d'utiliser nbd_set_opt_mode(3) si vous souhaitez contrôler quand envoyer nbd_opt_structured_reply(3) pendant la négociation.

Notez que la définition de ce bouton sur faux désactive également toute demande automatique d'en-têtes étendus.

Notez que si la connexion négocie des en-têtes étendus, cette fonction renvoie vrai (car les en-têtes étendus impliquent des réponses structurées) même si aucune demande explicite de réponses structurées n'a été tentée.

val set_request_meta_context : t -> bool -> unit

NBD.set_request_meta_context t request

contrôler si la connexion demande automatiquement des méta-contextes

Cette fonction contrôle si l'acte de se connecter à une exportation (tous les appels "nbd_connect_*" lorsque nbd_set_opt_mode(3) est faux, ou nbd_opt_go(3) et nbd_opt_info(3) lorsque le mode d'option est activé) tente également d'émettre NBD_OPT_SET_META_CONTEXT lorsque le serveur prend en charge les réponses structurées ou les en-têtes étendus et que des contextes ont été enregistrés par nbd_add_meta_context(3). Le réglage par défaut est vrai ; cependant, l'étape supplémentaire de négociation des méta-contextes n'est pas toujours souhaitable : effectuer à la fois l'info et le go sur la même exportation fonctionne sans avoir besoin de renégocier les contextes lors du second appel ; les tests d'intégration d'autres serveurs peuvent bénéficier de l'invocation manuelle de nbd_opt_set_meta_context(3) à d'autres moments de la séquence de négociation ; et même en utilisant uniquement nbd_opt_info(3), il peut être plus rapide de collecter les résultats du serveur en s'appuyant sur la fonction de rappel passée à nbd_opt_list_meta_context(3) plutôt que sur une série d'appels post-traitement à nbd_can_meta_context(3).

Notez que ce contrôle n'a aucun effet si le serveur ne négocie pas les réponses structurées ou les en-têtes étendus, ou si le client n'a pas demandé de contextes via nbd_add_meta_context(3). La définition de ce contrôle sur faux peut entraîner l'échec de nbd_block_status(3).

val get_request_meta_context : t -> bool

NBD.get_request_meta_context t

voir si la connexion demande automatiquement des méta-contextes

Renvoie l'état du drapeau de requête automatique de méta-contexte sur ce descripteur.

val set_handshake_flags : t -> HANDSHAKE_FLAG.t list -> unit

NBD.set_handshake_flags t flags

contrôler l'utilisation des drapeaux de négociation

Par défaut, libnbd tente de négocier tous les drapeaux de négociation possibles qui sont également pris en charge par le serveur, car omettre un drapeau de négociation peut empêcher l'utilisation d'autres fonctionnalités telles que le chiffrement TLS ou les réponses structurées. Cependant, pour les tests d'intégration, il peut être utile de réduire l'ensemble des drapeaux pris en charge par le client pour tester qu'un serveur particulier peut gérer divers clients qui étaient conformes aux versions antérieures de la spécification NBD.

L'argument "flags" est un masque de bits, incluant zéro ou plusieurs des drapeaux de négociation suivants :

"LIBNBD_HANDSHAKE_FLAG_FIXED_NEWSTYLE" = 1 Le serveur gère gracieusement les requêtes d'options inconnues du client, plutôt que de se déconnecter. Sans ce drapeau, un client ne peut pas demander en toute sécurité à utiliser des extensions telles que le chiffrement TLS ou les réponses structurées, car la demande peut amener un serveur plus ancien à interrompre la connexion.

"LIBNBD_HANDSHAKE_FLAG_NO_ZEROES" = 2 Si le client est forcé d'utiliser "NBD_OPT_EXPORT_NAME" au lieu du "NBD_OPT_GO" préféré, ce drapeau permet au serveur d'envoyer moins d'octets de remplissage entièrement nuls sur la connexion.

Pour plus de commodité, la constante "LIBNBD_HANDSHAKE_FLAG_MASK" est disponible pour décrire tous les drapeaux pris en charge par cette version de libnbd. Les futures extensions NBD peuvent ajouter d'autres drapeaux, qui à leur tour peuvent être activés par défaut dans les nouvelles versions de libnbd. Ainsi, lors de la tentative de désactivation d'un seul bit spécifique, il est plus sage d'appeler d'abord nbd_get_handshake_flags(3) et de modifier cette valeur, plutôt que de définir aveuglément une valeur constante.

val get_handshake_flags : t -> HANDSHAKE_FLAG.t list

NBD.get_handshake_flags t

voir quels drapeaux de négociation sont pris en charge

Renvoie l'état des drapeaux de négociation sur ce descripteur. Lorsque le descripteur n'a pas encore terminé une connexion (voir nbd_aio_is_created(3)), cela renvoie les drapeaux que le client est prêt à utiliser, à condition que le serveur annonce également ces drapeaux. Une fois la connexion prête (voir nbd_aio_is_ready(3)), cela renvoie les drapeaux qui ont été effectivement convenus entre le serveur et le client. Si le protocole NBD définit de nouveaux drapeaux de négociation, alors la valeur renvoyée par une version plus récente de la bibliothèque peut inclure des bits qui étaient indéfinis au moment de la compilation.

val set_pread_initialize : t -> bool -> unit

NBD.set_pread_initialize t request

contrôler si libnbd pré-initialise les tampons de lecture

Par défaut, libnbd pré-initialisera le contenu d'un tampon passé à des appels tels que nbd_pread(3) à zéro avant de vérifier toute autre erreur, de sorte que même si une application cliente a passé un tampon non initialisé mais ne vérifie pas les erreurs, cela ne résultera pas en un risque de sécurité potentiel causé par une fuite accidentelle de contenu heap précédent (voir CVE-2022-0485 dans libnbd-security(3) pour un exemple de faille de sécurité dans une application construite contre une version antérieure de libnbd qui manquait de pré-initialisation cohérente). Cependant, pour une application cliente qui a vérifié qu'un tampon non initialisé n'est jamais référencé, ou qui effectue sa propre pré-initialisation, les efforts de nettoyage de libnbd ne font que pénaliser les performances (bien que le temps passé en pré-initialisation puisse pâlir en comparaison du temps passé à attendre les paquets réseau).

Appeler cette fonction avec

th "request" à faux indique libnbd d'ignorer l'étape d'initialisation du tampon dans les commandes de lecture.

vérifier si libnbd pré-initialise les tampons de lecture

Retourne si libnbd effectue une pré-initialisation d'un tampon passé à nbd_pread(3) et similaires à tous les zéros, comme défini par nbd_set_pread_initialize(3).

val set_strict_mode : t -> STRICT.t list -> unit

NBD.set_strict_mode t flags

contrôler la rigueur de suivi du protocole NBD

Par défaut, libnbd essaie de détecter les requêtes qui déclencheraient un comportement indéfini dans le protocole NBD, et les rejette côté client sans entraîner de trafic réseau, plutôt que de risquer un comportement serveur indéfini. Cependant, pour les tests d'intégration, il peut être utile d'assouplir la rigueur de libnbd, pour le forcer à envoyer de telles requêtes sur le réseau afin de tester la robustesse du serveur face à un tel trafic.

L'argument "flags" est un masque de bits, incluant zéro ou plus des indicateurs de rigueur suivants :

"LIBNBD_STRICT_COMMANDS" = 0x1 Si cet indicateur est défini, il rejette les requêtes client qui ne sont pas conformes à l'ensemble des drapeaux serveur annoncés (par exemple, tenter une écriture sur un serveur en lecture seule, ou tenter d'utiliser "LIBNBD_CMD_FLAG_FUA" alors que nbd_can_fua(3) a renvoyé faux). Si cet indicateur est effacé, il repose sur le serveur pour rejeter les commandes inattendues.

"LIBNBD_STRICT_FLAGS" = 0x2 Si cet indicateur est défini, il rejette les requêtes client qui tentent de définir un indicateur de commande non reconnu par libnbd (ceux en dehors de "LIBNBD_CMD_FLAG_MASK"), ou un indicateur non normalement associé à une commande (comme l'utilisation de "LIBNBD_CMD_FLAG_FUA" sur une commande de lecture). Si cet indicateur est effacé, tous les indicateurs sont envoyés au serveur, même si l'envoi d'un tel indicateur peut amener le serveur à modifier sa réponse d'une manière qui perturbe libnbd, causant potentiellement un blocage ou la fin de la connexion.

Les indicateurs connus par libnbd comme étant associés à une commande donnée (comme "LIBNBD_CMD_FLAG_DF" pour nbd_pread_structured(3) conditionné par nbd_can_df(3)) sont contrôlés par "LIBNBD_STRICT_COMMANDS" ; et "LIBNBD_CMD_FLAG_PAYLOAD_LEN" est géré automatiquement par libnbd à moins que "LIBNBD_STRICT_AUTO_FLAG" ne soit désactivé.

Notez que le protocole NBD ne prend en charge que 16 bits d'indicateurs de commande, même si l'API libnbd utilise "uint32_t" ; les bits en dehors de la plage autorisée par le protocole sont toujours une erreur côté client.

"LIBNBD_STRICT_BOUNDS" = 0x4 Si cet indicateur est défini, il rejette les requêtes client qui dépasseraient les limites de l'export sans envoyer de trafic au serveur. Si cet indicateur est effacé, il repose sur le serveur pour détecter les requêtes hors limites.

"LIBNBD_STRICT_ZERO_SIZE" = 0x8 Si cet indicateur est défini, il rejette les requêtes client de longueur 0. Si cet indicateur est effacé, il autorise les requêtes de longueur nulle au serveur, ce qui peut produire des résultats indéfinis.

"LIBNBD_STRICT_ALIGN" = 0x10 Si cet indicateur est défini, et que le serveur a fourni des tailles de bloc minimales (voir "LIBNBD_SIZE_MINIMUM" pour nbd_get_block_size(3)), cet indicateur rejette les requêtes client dont la longueur et le décalage ne sont pas alignés sur les exigences minimales du serveur. Si cet indicateur est effacé, les requêtes non alignées sont envoyées au serveur, où il appartient au serveur de les honorer ou de les rejeter.

"LIBNBD_STRICT_PAYLOAD" = 0x20 Si cet indicateur est défini, le client refuse d'envoyer une commande au serveur avec une taille supérieure au maximum de charge utile sortante de libnbd (voir "LIBNBD_SIZE_PAYLOAD" pour nbd_get_block_size(3)), que le serveur ait annoncé une taille de bloc maximale ou non. Si cet indicateur est effacé, des requêtes de taille excessive allant jusqu'à 64 Mio peuvent être tentées, bien que les requêtes supérieures à 32 Mio soient susceptibles de provoquer la déconnexion de certains serveurs.

"LIBNBD_STRICT_AUTO_FLAG" = 0x40 Si cet indicateur est défini, les commandes qui acceptent l'indicateur "LIBNBD_CMD_FLAG_PAYLOAD_LEN" (comme nbd_pwrite(3) et nbd_block_status_filter(3)) ignorent la présence ou l'absence de cet indicateur de l'appelant, envoyant à la place la valeur sur le fil qui correspond aux attentes du serveur en fonction de si des en-têtes étendus ont été négociés lors de la connexion. Si cet indicateur est effacé, l'appelant assume la responsabilité de l'état de l'indicateur de longueur de charge utile (défini ou effacé) lors des commandes affectées, ce qui peut être utile lors des tests d'intégration mais est plus susceptible de conduire à un comportement indéfini.

Pour plus de commodité, la constante "LIBNBD_STRICT_MASK" est disponible pour décrire tous les indicateurs de rigueur pris en charge par cette compilation de libnbd. Les versions futures de libnbd peuvent ajouter d'autres indicateurs, qui seront probablement activés par défaut pour un filtrage supplémentaire côté client. Ainsi, lorsque vous tentez d'assouplir un seul bit spécifique tout en conservant les vérifications restantes côté client, il est plus judicieux d'appeler d'abord nbd_get_strict_mode(3) et de modifier cette valeur, plutôt que de définir aveuglément une valeur constante.

val get_strict_mode : t -> STRICT.t list

NBD.get_strict_mode t

voir quels indicateurs de rigueur sont en vigueur

Retourne les indicateurs indiquant quels éléments de rigueur du protocole sont appliqués localement par libnbd plutôt que par le serveur. La valeur de retour d'une version de bibliothèque plus récente peut inclure des bits qui étaient indéfinis au moment de la compilation.

val set_opt_mode : t -> bool -> unit

NBD.set_opt_mode t enable

contrôler le mode optionnel, pour la pause pendant la négociation d'options

Définissez cet indicateur sur vrai pour demander qu'une commande de connexion "nbd_connect_*" s'arrête pour la négociation d'options plutôt que de procéder jusqu'à l'état prêt, lors de la communication avec un serveur newstyle. Ce réglage n'a aucun effet lors de la connexion à un serveur oldstyle.

Notez que libnbd tente par défaut "NBD_OPT_STARTTLS", "NBD_OPT_EXTENDED_HEADERS", et "NBD_OPT_STRUCTURED_REPLY" avant de vous permettre de contrôler les étapes de négociation restantes ; si vous avez besoin de contrôler ces étapes également, définissez d'abord nbd_set_tls(3) sur "LIBNBD_TLS_DISABLE", et nbd_set_request_extended_headers(3) ou nbd_set_request_structured_replies(3) sur faux, avant de commencer la tentative de connexion.

Lorsque le mode optionnel est activé, vous avez un contrôle fin sur les options qui sont négociées, par rapport au défaut où le serveur négocie tout en votre nom en utilisant les paramètres définis avant de commencer la connexion. Pour quitter le mode et passer à l'état prêt, vous devez utiliser nbd_opt_go(3) avec succès ; un échec de nbd_opt_go(3) renvoie à l'état de négociation pour permettre un changement de nom d'export avant de réessayer. Vous pouvez également utiliser nbd_opt_abort(3) ou nbd_shutdown(3) pour terminer la connexion sans finaliser la négociation.

val get_opt_mode : t -> bool

NBD.get_opt_mode t

retourne si le mode optionnel était activé

Retourne vrai si le mode de négociation d'options a été activé sur ce handle.

val opt_go : t -> unit

NBD.opt_go t

terminer la négociation et passer à l'utilisation d'un export

Demande au serveur de finaliser la négociation et de passer à la gestion de l'export précédemment spécifié par le plus récent nbd_set_export_name(3) ou nbd_connect_uri(3). Ceci ne peut être utilisé que si nbd_set_opt_mode(3) a activé le mode optionnel.

Par défaut, libnbd demandera automatiquement tous les contextes méta enregistrés par nbd_add_meta_context(3) dans le cadre de cet appel ; mais cela peut être supprimé avec nbd_set_request_meta_context(3), en particulier si nbd_opt_set_meta_context(3) a été utilisé plus tôt dans la séquence de négociation.

Si cela échoue, le serveur peut toujours être en cours de négociation, où il est possible de tenter une autre option telle qu'un nom d'export différent ; bien que les anciens serveurs aient plutôt terminé la connexion.

val opt_abort : t -> unit

NBD.opt_abort t

terminer la négociation et fermer la connexion

Demande au serveur de finaliser la négociation, gracieusement si possible, puis de fermer la connexion. Ceci ne peut être utilisé que si nbd_set_opt_mode(3) a activé le mode optionnel.

val opt_starttls : t -> bool

NBD.opt_starttls t

demander au serveur d'initier TLS

Demande au serveur d'initier une connexion TLS sécurisée, en envoyant "NBD_OPT_STARTTLS". Ceci ne peut être utilisé que si nbd_set_opt_mode(3) a activé le mode optionnel ; de plus, si vous utilisez nbd_set_tls(3) pour demander autre chose que le défaut "LIBNBD_TLS_DISABLE", alors libnbd aura déjà tenté une connexion TLS avant de vous permettre de contrôler la négociation d'options. Cette commande est désactivée si nbd_supports_tls(3) renvoie faux.

Cette fonction est principalement utile pour les tests d'intégration de cas limites dans la gestion des serveurs ; en particulier, une mauvaise utilisation de cette fonction couplée à un serveur qui ne prend pas soin de réinitialiser les commandes stateful comme nbd_opt_structured_reply(3) pourrait résulter en une faille de sécurité (voir CVE-2021-3716 contre nbdkit, par exemple). Ainsi, lorsque la sécurité est une préoccupation, vous devriez plutôt préférer utiliser nbd_set_tls(3) avec "LIBNBD_TLS_REQUIRE" et laisser libnbd négocier TLS automatiquement.

Cette fonction renvoie vrai si le serveur répond avec succès, faux si le serveur répond avec une erreur, et échoue uniquement si le serveur ne répond pas (par exemple, en cas de perte de connexion, qui peut inclure le cas où le serveur rejette les identifiants fournis pendant la négociation TLS). Notez que le protocole NBD stipule que demander TLS alors qu'il est déjà activé est une erreur client ; la plupart des serveurs échoueront gracieusement à une deuxième demande, mais cela ne dégrade pas une session TLS déjà établie, comme rapporté par nbd_get_tls_negotiated(3).

val opt_extended_headers : t -> bool

NBD.opt_extended_headers t

demander au serveur d'activer les en-têtes étendus

Demande au serveur d'utiliser des en-têtes étendus, en envoyant "NBD_OPT_EXTENDED_HEADERS". Ceci ne peut être utilisé que si nbd_set_opt_mode(3) a activé le mode optionnel ; de plus, libnbd demande par défaut automatiquement ceci à moins que vous n'utilisiez nbd_set_request_extended_headers(3) ou nbd_set_request_structured_replies(3) avant la connexion. Cette fonction est principalement utile pour les tests d'intégration de cas limites dans la gestion des serveurs.

Cette fonction renvoie vrai si le serveur répond avec succès, faux si le serveur répond avec une erreur, et échoue uniquement si le serveur ne répond pas (par exemple, en cas de perte de connexion). Notez que certains serveurs rejettent une deuxième demande comme redondante ; libnbd suppose qu'une fois qu'une demande a réussi, les en-têtes étendus sont pris en charge (comme visible par nbd_get_extended_headers_negotiated(3)) indépendamment du fait que les appels ultérieurs à cette fonction renvoient faux. Si cette fonction renvoie vrai, l'utilisation des réponses structurées est implicite.

val opt_structured_reply : t -> bool

NBD.opt_structured_reply t

demande au serveur d'activer les réponses structurées

Demande au serveur d'utiliser des réponses structurées, en envoyant "NBD_OPT_STRUCTURED_REPLY". Ceci ne peut être utilisé que si nbd_set_opt_mode(3) a activé le mode optionnel ; de plus, libnbd demande automatiquement ceci par défaut, sauf si vous utilisez nbd_set_request_structured_replies(3) avant de vous connecter. Cette fonction est principalement utile pour les tests d'intégration des cas limites dans la gestion par le serveur.

Cette fonction renvoie vrai si le serveur répond avec succès, faux si le serveur répond avec une erreur, et échoue uniquement si le serveur ne répond pas (par exemple, en cas de perte de connexion). Notez que certains serveurs échouent une seconde demande comme étant redondante ; libnbd suppose qu'une fois qu'une demande a réussi, les réponses structurées sont prises en charge (comme visible par nbd_get_structured_replies_negotiated(3)) quel que soit le résultat des appels ultérieurs à cette fonction. De même, un serveur peut échouer cette demande si des en-têtes étendus sont déjà négociés, car les en-têtes étendus ont la priorité.

val opt_list : t -> (string -> string -> int) -> int

NBD.opt_list t list

demande au serveur de lister toutes les exportations lors de la négociation

Demande au serveur de lister toutes les exportations qu'il prend en charge. Ceci ne peut être utilisé que si nbd_set_opt_mode(3) a activé le mode optionnel.

La fonction "list" est appelée une fois par exportation annoncée, avec toute "user_data" passée à cette fonction, et avec "name" et "description" fournies par le serveur. De nombreux serveurs omettent les descriptions, auquel cas "description" sera une chaîne vide. N'oubliez pas qu'il n'est pas sûr d'appeler nbd_set_export_name(3) depuis le contexte de la fonction de rappel ; votre code doit plutôt copier tout "name" nécessaire pour une utilisation ultérieure après l'achèvement de cette fonction. À l'heure actuelle, la valeur de retour du rappel est ignorée, bien qu'un retour de -1 doive être évité.

Pour plus de commodité, lorsque cette fonction réussit, elle renvoie le nombre d'exportations qui ont été annoncées par le serveur.

Tous les serveurs ne comprennent pas cette demande, et même lorsqu'elle est comprise, le serveur peut intentionnellement envoyer une liste vide pour éviter une fuite d'informations, peut rencontrer une erreur après la livraison de résultats partiels, ou peut refuser de répondre à plus d'une requête par connexion afin d'éviter une négociation qui ne se résout pas. Ainsi, cette fonction peut réussir même lorsqu'aucune exportation n'est signalée, ou peut échouer mais avoir une liste non vide. De même, le protocole NBD ne spécifie pas de limite supérieure au nombre d'exportations qui pourraient être annoncées, donc le code client doit être conscient qu'un serveur peut envoyer une longue liste.

Pour nbd-server(1), vous devrez autoriser les clients à faire des requêtes de liste en ajoutant "allowlist=true" à la section " generic " de /etc/nbd-server/config. Pour qemu-nbd(8), une description est définie avec *-D*.

val opt_info : t -> unit

NBD.opt_info t

demande au serveur des informations sur une exportation

Demande au serveur de fournir des informations sur le nom d'exportation précédemment spécifié par le dernier appel à nbd_set_export_name(3) ou nbd_connect_uri(3). Ceci ne peut être utilisé que si nbd_set_opt_mode(3) a activé le mode optionnel.

En cas de succès, des fonctions comme nbd_is_read_only(3) et nbd_get_size(3) rapporteront des détails sur cette exportation. Si nbd_set_request_meta_context(3) est défini (par défaut) et que des réponses structurées ou des en-têtes étendus ont été négociés, il est également valide d'utiliser nbd_can_meta_context(3) après cet appel. Cependant, il peut être plus efficace de désactiver ce paramètre et d'utiliser manuellement nbd_opt_list_meta_context(3) avec son approche de rappel, pour savoir quels contextes une exportation prend en charge. En général, si nbd_opt_go(3) est appelé ensuite, cet appel réussira probablement avec les détails restant identiques, bien que cela ne soit pas garanti par tous les serveurs.

Tous les serveurs ne comprennent pas cette demande, et même lorsqu'elle est comprise, le serveur peut échouer la demande même si un appel correspondant à nbd_opt_go(3) réussirait.

val opt_list_meta_context : t -> (string -> int) -> int

NBD.opt_list_meta_context t context

liste les contextes méta disponibles, en utilisant une liste de requêtes implicite

Demande au serveur de lister les contextes méta disponibles associés à l'exportation précédemment spécifiée par le dernier appel à nbd_set_export_name(3) ou nbd_connect_uri(3), et avec une liste de requêtes issues d'appels antérieurs à nbd_add_meta_context(3) (voir nbd_opt_list_meta_context_queries(3) si vous souhaitez fournir une liste de requêtes explicite à la place). Le protocole NBD permet à un client de décider du nombre de requêtes à poser au serveur. Plutôt que de prendre cette liste de requêtes comme paramètre de cette fonction, libnbd réutilise la liste actuelle des contextes méta demandés telle que définie par nbd_add_meta_context(3) ; vous pouvez utiliser nbd_clear_meta_contexts(3) pour définir une liste de requêtes différente. Notez qu'une réponse du serveur peut être encodée pour représenter plusieurs contextes réalisables dans une seule chaîne, plutôt que plusieurs chaînes par nom de contexte réel qui réussiraient lors de nbd_opt_go(3) ; il est donc toujours nécessaire d'utiliser nbd_can_meta_context(3) après la connexion pour voir quels contextes sont effectivement pris en charge.

La fonction "context" est appelée une fois par réponse du serveur, avec toute "user_data" passée à cette fonction, et avec "name" fourni par le serveur. N'oubliez pas qu'il n'est pas sûr d'appeler nbd_add_meta_context(3) depuis le contexte de la fonction de rappel ; votre code doit plutôt copier tout "name" nécessaire pour une utilisation ultérieure après l'achèvement de cette fonction. À l'heure actuelle, la valeur de retour du rappel est ignorée, bien qu'un retour de -1 doive être évité.

Pour plus de commodité, lorsque cette fonction réussit, elle renvoie le nombre de réponses renvoyées par le serveur.

Tous les serveurs ne comprennent pas cette demande, et même lorsqu'elle est comprise, le serveur peut intentionnellement envoyer une liste vide car il ne prend pas en charge le contexte demandé, ou peut rencontrer une erreur après la livraison de résultats partiels. Ainsi, cette fonction peut réussir même lorsqu'aucun contexte n'est signalé, ou peut échouer mais avoir une liste non vide. De même, le protocole NBD ne spécifie pas de limite supérieure au nombre de réponses qui pourraient être annoncées, donc le code client doit être conscient qu'un serveur peut envoyer une longue liste.

val opt_list_meta_context_queries : t -> string list -> (string -> int) -> int

liste les contextes méta disponibles, en utilisant une liste de requêtes explicite

Demande au serveur de lister les contextes méta disponibles associés à l'exportation précédemment spécifiée par le dernier appel à nbd_set_export_name(3) ou nbd_connect_uri(3), et avec une liste explicite de requêtes fournie en paramètre (voir nbd_opt_list_meta_context(3) si vous souhaitez réutiliser une liste de requêtes implicite à la place). Le protocole NBD permet à un client de décider du nombre de requêtes à poser au serveur. Pour cette fonction, la liste est explicite dans le paramètre "queries". Tous les serveurs ne comprennent pas cette demande, et même lorsqu'elle est comprise, le serveur peut intentionnellement envoyer une liste vide car il ne prend pas en charge le contexte demandé, ou peut rencontrer une erreur après la livraison de résultats partiels. Ainsi, cette fonction peut réussir même lorsqu'aucun contexte n'est signalé, ou peut échouer mais avoir une liste non vide. De même, le protocole NBD ne spécifie pas de limite supérieure au nombre de réponses qui pourraient être annoncées, donc le code client doit être conscient qu'un serveur peut envoyer une longue liste.

val connect_uri : t -> string -> unit

NBD.connect_uri t uri

se connecter à une URI NBD

Connecte (synchrone) à un serveur NBD et exporte en spécifiant l'URI NBD. Les URI NBD sont un moyen standard de spécifier un point de terminaison de périphérique bloc réseau, en utilisant une syntaxe telle que "nbd://example.com" qui est pratique, bien définie et pérenne.

Cet appel fonctionne en analysant le paramètre URI et en appelant nbd_set_export_name(3) et nbd_set_tls(3) et d'autres appels si nécessaire, suivis par nbd_connect_tcp(3), nbd_connect_unix(3) ou nbd_connect_vsock(3).

Cet appel retourne lorsque la connexion est établie. Par défaut, cela va jusqu'à la phase de transmission, mais nbd_set_opt_mode(3) peut être utilisé pour un contrôle manuel sur la négociation d'options effectuée avant la phase de transmission.

Exemples d'URI pris en charge "nbd://example.com" Connexion via TCP, non chiffrée, à "example.com" port 10809.

"nbds://example.com" Connexion via TCP avec TLS, à "example.com" port 10809. Si le serveur ne prend pas en charge TLS, cela échouera.

"nbd+unix:///foo?socket=/tmp/nbd.sock" Connexion via le socket de domaine Unix /tmp/nbd.sock à un serveur NBD fonctionnant localement. Le nom d'exportation est défini sur "foo" (notez sans aucun caractère "/" en préfixe).

"nbds+unix://alice@/?socket=/tmp/nbd.sock&tls-certificat es=certs" Connexion via un socket de domaine Unix, activation de TLS et définition du chemin vers un répertoire contenant les certificats et les clés.

"nbd+vsock:///" Dans ce scénario, libnbd s'exécute dans une machine virtuelle. Connexion via "AF_VSOCK" à un serveur NBD s'exécutant sur l'hyperviseur.

"nbd+ssh://server/" Connexion au "server" distant en utilisant Secure Shell, et tunnel NBD vers un serveur NBD écoutant sur le port 10809.

Schéma URI Le schéma est la partie avant le premier ":". Les schémas suivants sont

pris en charge dans la version actuelle de libnbd :

"nbd:" Connexion via TCP sans utiliser TLS.

"nbds:" Connexion via TCP. TLS est requis et la connexion échouera si le serveur ne prend pas en charge TLS.

"nbd+unix:" "nbds+unix:" Connexion via un socket de domaine Unix, sans ou avec TLS respectivement. Le paramètre "socket" est requis.

"nbd+vsock:" "nbds+vsock:" Connexion via le transport "AF_VSOCK", sans ou avec TLS respectivement. Vous pouvez utiliser nbd_supports_vsock(3) pour voir si cette version de libnbd prend en charge "AF_VSOCK".

"nbd+ssh:" "nbds+ssh:" *Expérimental*

Tunnel NBD via une connexion Secure Shell. Cela nécessite que ssh(1) soit installé localement et que nc(1) (du projet nmap) soit installé sur le serveur distant.

Autorité de l'URI La partie autorité de l'URI " nomutilisateur@ nomserveur :port " est analysée en fonction du transport. Pour TCP, elle spécifie le serveur auquel se connecter et le numéro de port facultatif. Pour "+unix", elle ne doit pas être présente. Pour "+vsock", le nom du serveur est le CID numérique (par exemple, 2 pour se connecter à l'hôte) et le numéro de port facultatif peut être présent. Pour "+ssh", le serveur Secure Shell et le port facultatif. Si le "nomutilisateur" est présent, il est utilisé pour l'authentification TLS.

Nom d'exportation de l'URI Pour tous les transports, un nom d'exportation peut être présent, analysé conformément à la spécification URI NBD. Notez que le caractère "/" initial ne fait pas partie du nom d'exportation :

Nom d'exportation de l'URI nbd://localhost/ "" (chaîne vide) nbd://localhost/export "export"

Il est possible de remplacer le nom d'exportation par programme en utilisant nbd_set_opt_mode(3) pour activer le mode d'options, puis en utilisant nbd_set_export_name(3) et nbd_opt_go(3) dans le cadre de la négociation ultérieure.

Requête de l'URI Enfin, la partie requête de l'URI peut contenir :

socket=SOCKET Spécifie le socket de domaine Unix sur lequel se connecter. Doit être présent pour le transport "+unix", facultatif pour "+ssh", et ne doit pas être présent pour les autres transports.

tls-certificates=DIR Définit le répertoire des certificats. Voir nbd_set_tls_certificates(3). Notez que ce n'est pas autorisé par défaut - voir la section suivante.

tls-psk-file=PSKFILE Définit le fichier PSK. Voir nbd_set_tls_psk_file(3). Notez que ce n'est pas autorisé par défaut - voir la section suivante.

tls-hostname="SERVER" Définit le nom d'hôte TLS. Voir nbd_set_tls_hostname(3).

tls-verify-peer=false Ne pas vérifier le certificat du serveur. Voir nbd_set_tls_verify_peer(3). La valeur par défaut est "true".

Désactivation des fonctionnalités URI Pour des raisons de sécurité, vous pourriez vouloir désactiver certaines fonctionnalités URI. Le pré-filtrage des URI est sujet aux erreurs et ne doit pas être tenté. Utilisez plutôt les API libnbd ci-dessous pour contrôler ce qui peut apparaître dans les URI. Notez que vous devez appeler ces fonctions sur le même descripteur avant d'appeler nbd_connect_uri(3) ou nbd_aio_connect_uri(3).

Transports TCP, socket de domaine Unix, "AF_VSOCK" ou SSH Par défaut : tous autorisés

Pour sélectionner les transports autorisés, appelez nbd_set_uri_allow_transports(3).

TLS Par défaut : connexions non-TLS et TLS autorisées

Pour forcer TLS à être désactivé ou activé dans les URI, appelez nbd_set_uri_allow_tls(3).

Connexion à un socket de domaine Unix dans le système de fichiers local Par défaut : autorisé

Pour empêcher cela, vous devez désactiver le transport "+unix" en utilisant nbd_set_uri_allow_transports(3).

Lecture à partir de fichiers locaux Par défaut : refusé

Pour autoriser les URI à contenir des références à des fichiers locaux (par exemple, pour des paramètres comme "tls-psk-file"), appelez nbd_set_uri_allow_local_file(3).

Fonctionnalités facultatives Cet appel échouera si libnbd n'a pas été compilé avec libxml2 ; vous pouvez tester si c'est le cas avec nbd_supports_uri(3).

La prise en charge des URI nécessitant TLS échouera si libnbd n'a pas été compilé avec gnutls ; vous pouvez tester si c'est le cas avec nbd_supports_tls(3).

Construction d'une URI à partir d'une connexion existante Voir nbd_get_uri(3).

Vérifier si une chaîne est une URI NBD Voir nbd_is_uri(3).

Différences avec l'analyse des URI NBD par qemu et glib qemu(1) prend également en charge les URI NBD et possède un analyseur URI distinct. Dans qemu ≤ 9.0, cela était fait à l'aide de leur propre analyseur. Dans qemu ≥ 9.1, cela est fait à l'aide des fonctions "g_uri" de glib. L'analyseur actuel (basé sur glib) n'analyse pas la partie nom d'exportation de l'URI exactement de la même manière que libnbd, ce qui peut entraîner le fonctionnement des URI dans libnbd mais pas dans qemu ou vice versa. Seules les URI utilisant des noms d'exportation devraient être affectées. Pour plus de détails, voir https://gitlab.com/qemu-project/qemu/-/issues/2584.

Limitations sur les numéros de port vsock Le protocole vsock(7) autorise les ports non signés de 32 bits, réservant les ports 0, 1 et 2 à des fins spéciales. Sous Linux, les ports < 1024 sont réservés aux processus privilégiés.

libxml2 (utilisé pour analyser l'URI) impose des restrictions supplémentaires. libxml2 < 2.9 limitait les numéros de port à 99 999 999. libxml2 ≥ 2.9 limite les numéros de port à ≤ 0x7fff_ffff (31 bits).

val get_block_size : t -> SIZE.t -> int64

NBD.get_block_size t size_type

retourne une contrainte de taille de bloc spécifique du serveur

Retourne une contrainte de taille de bloc spécifique annoncée par le serveur. Si zéro est retourné, cela signifie que le serveur n'a pas annoncé de contrainte.

Les contraintes sont des indices. Les serveurs diffèrent dans leur comportement quant à savoir s'ils appliquent ou non les contraintes.

Le paramètre "size_type" sélectionne la contrainte à lire. Il peut être l'un des suivants :

"LIBNBD_SIZE_MINIMUM" = 0 Si non nul, ce sera une puissance de 2 entre 1 et 64k ; toute requête client qui n'est pas alignée en longueur ou en décalage sur cette taille est susceptible d'échouer avec "EINVAL". La taille de l'image sera généralement aussi un multiple de cette valeur (sinon, les quelques derniers octets sont inaccessibles tout en respectant les contraintes d'alignement).

Si zéro (signifiant qu'aucune information n'a été retournée par le serveur), il est plus sûr de supposer une taille de bloc minimale de 512, bien que de nombreux serveurs prennent en charge une taille de bloc minimale de 1.

Si le serveur fournit une contrainte, alors libnbd honore par défaut cette contrainte côté client, sauf si "LIBNBD_S

TRICT_ALIGN" est effacé dans nbd_set_strict_mode(3).

"LIBNBD_SIZE_PREFERRED" = 1 Si non nul, c'est une puissance de 2 représentant la taille préférée pour des E/S efficaces. Des requêtes plus petites peuvent entraîner des surcoûts tels que des cycles de lecture-modification-écriture qui ne seront pas présents lors de l'utilisation d'E/S multiples de cette valeur. Cette valeur peut être supérieure à la taille de l'exportation.

Si zéro (ce qui signifie qu'aucune information n'a été retournée par le serveur), utiliser 4k comme taille de bloc préférée tend à donner de bonnes performances.

"LIBNBD_SIZE_MAXIMUM" = 2 Si non nul, cela représente la longueur maximale que le serveur est prêt à gérer pendant nbd_pread(3) ou nbd_pwrite(3). D'autres fonctions comme nbd_zero(3) peuvent encore être capables d'utiliser des tailles plus grandes. Notez que cette fonction retourne ce que le serveur a annoncé, mais libnbd lui-même impose un maximum de 64M.

Si zéro (ce qui signifie qu'aucune information n'a été retournée par le serveur), certains serveurs NBD se déconnecteront abruptement si une transaction envoie ou reçoit plus de 32M de données.

"LIBNBD_SIZE_PAYLOAD" = 3 Cette valeur n'est pas annoncée par le serveur, mais représente plutôt la taille maximale de la charge utile sortante pour une connexion donnée que libnbd appliquera, sauf si "LIBNBD_STRICT_PAYLOAD" est effacé dans nbd_set_strict_mode(3). Elle est toujours non nulle : jamais inférieure à 1M, jamais supérieure à 64M, et correspond à "LIBNBD_SIZE_MAXIMUM" lorsque c'est possible.

Les futures extensions NBD peuvent entraîner des valeurs "size_type" supplémentaires. Notez que par défaut, libnbd demande toutes les tailles de bloc disponibles, mais qu'un serveur peut différer dans les tailles qu'il choisit de rapporter si nbd_set_request_block_size(3) modifie la façon dont le client demande les tailles.

Cet appel ne bloque pas, car il retourne des données qui sont sauvegardées dans le handle à partir de la négociation du protocole NBD.

val pread : ?flags:CMD_FLAG.t list -> t -> bytes -> int64 -> unit

NBD.pread t ?flags buf offset

lire depuis le serveur NBD

Émet une commande de lecture vers le serveur NBD pour la plage commençant à "offset" et se terminant à "offset" + "count" - 1. NBD ne peut lire que tout ou rien en utilisant cet appel. L'appel retourne lorsque les données ont été entièrement lues dans "buf" ou qu'il y a une erreur. Voir aussi nbd_pread_structured(3), si une visibilité plus fine est requise dans les réponses du serveur, ou si vous voulez utiliser "LIBNBD_CMD_FLAG_DF".

Notez que libnbd applique actuellement un tampon de lecture maximum de 64 MiB, même si le serveur autoriserait un tampon plus grand dans une seule transaction ; les tentatives de dépassement entraîneront une erreur "ERANGE" . Le serveur peut imposer une limite plus petite, qui peut être connue avec nbd_get_block_size(3).

Le paramètre "flags" doit être 0 pour l'instant (il existe pour les futures extensions du protocole NBD).

Notez que si cette commande échoue, et que nbd_get_pread_initialize(3) retourne true, alors libnbd a nettoyé "buf", mais il n'est pas spécifié si les contenus de "buf" seront lus comme zéro ou comme des résultats partiels du serveur. Si nbd_get_pread_initialize(3) retourne false, alors libnbd n'a pas nettoyé "buf", et les contenus sont indéfinis en cas d'échec.

Par défaut, libnbd rejettera les tentatives d'utilisation de cette fonction avec des paramètres susceptibles d'entraîner une défaillance du serveur, comme la demande d'un indicateur de commande inconnu. La fonction nbd_set_strict_mode(3) peut être utilisée pour modifier les scénarios qui doivent attendre une réponse du serveur plutôt que de échouer rapidement.

val pread_structured : ?flags:CMD_FLAG.t list -> t -> bytes -> int64 -> (bytes -> int64 -> int -> int Stdlib.ref -> int) -> unit

NBD.pread_structured t ?flags buf offset chunk

lire depuis le serveur NBD

Émet une commande de lecture vers le serveur NBD pour la plage commençant à "offset" et se terminant à "offset" + "count" - 1. La réponse du serveur peut être subdivisée en fragments qui peuvent arriver dans le désordre avant réassemblage dans le tampon d'origine ; le rappel "chunk" est utilisé pour la notification après l'arrivée de chaque fragment, et peut effectuer des vérifications supplémentaires sur la réponse du serveur. Le rappel ne peut pas appeler les API "nbd_*" sur le même handle car il détient le verrou du handle et provoquera un interblocage. Si le rappel retourne -1, et qu'aucune erreur antérieure n'a été détectée, alors la commande de lecture globale échouera avec toute valeur non nulle stockée dans le paramètre "error" du rappel (avec une valeur par défaut de "EPROTO") ; mais tous les fragments ultérieurs continueront d'invoquer le rappel.

La fonction "chunk" est appelée une fois par fragment de données reçu, avec "user_data" passé à cette fonction. Les paramètres "subbuf" et "count" représentent le sous-ensemble du tampon d'origine qui a été récemment rempli avec les résultats du serveur (en C, "subbuf" pointe toujours dans "buf" d'origine ; mais cette garantie peut ne pas s'étendre à d'autres liaisons de langage). Le paramètre "offset" représente le décalage absolu auquel "subbuf" commence dans l'image (notez que ce n'est pas le décalage relatif de "subbuf" dans le tampon "buf" d'origine). Les modifications apportées à "error" en sortie sont ignorées, sauf si le rappel échoue. Le sens d'entrée du paramètre "error" est contrôlé par le paramètre "status", qui est l'un des éléments suivants :

"LIBNBD_READ_DATA" = 1 "subbuf" a été rempli avec "count" octets de données. En entrée, "error" contient la valeur errno de toute erreur détectée précédemment, ou zéro.

"LIBNBD_READ_HOLE" = 2 "subbuf" représente un trou, et contient "count" octets NUL. En entrée, "error" contient la valeur errno de toute erreur détectée précédemment, ou zéro.

"LIBNBD_READ_ERROR" = 3 "count" est 0, donc "subbuf" est inutilisable. En entrée, "error" contient la valeur errno rapportée par le serveur comme s'étant produite lors de la lecture de cet "offset", qu'une erreur antérieure ait été détectée ou non.

Les futures extensions NBD peuvent autoriser d'autres valeurs pour "status", mais celles-ci ne seront pas retournées à un client qui n'a pas opté pour demander de telles extensions. Si le serveur n'est pas conforme, il est possible que la fonction "chunk" soit appelée plus de fois que prévu ou avec "count" 0 pour "LIBNBD_READ_DATA" ou "LIBNBD_READ_HOLE". Il est également possible que la fonction "chunk" ne soit pas appelée du tout (en particulier, "LIBNBD_READ_ERROR" n'est utilisé que lorsqu'une erreur est associée à un décalage particulier, et non lorsque le serveur signale une erreur générique), mais vous êtes assuré que le rappel a été appelé au moins une fois si la lecture globale réussit. Libnbd ne vérifie pas si le serveur a respecté l'exigence qu'un appel de lecture ne doit pas avoir de fragments qui se chevauchent et ne doit pas réussir sans suffisamment de fragments pour couvrir la requête entière.

Notez que libnbd applique actuellement un tampon de lecture maximum de 64 MiB, même si le serveur autoriserait un tampon plus grand dans une seule transaction ; les tentatives de dépassement entraîneront une erreur "ERANGE" . Le serveur peut imposer une limite plus petite, qui peut être connue avec nbd_get_block_size(3).

Le paramètre "flags" peut être 0 pour aucun drapeau, ou peut contenir "LIBNBD_CMD_FLAG_DF" signifiant que le serveur ne doit pas répondre avec plus d'un fragment (si cela est pris en charge - certains serveurs ne peuvent pas le faire, voir nbd_can_df(3)). Libnbd ne vérifie pas si le serveur obéit réellement au drapeau.

Notez que si cette commande échoue, et que nbd_get_pread_initialize(3) retourne true, alors libnbd a nettoyé "buf", mais il n'est pas spécifié si les contenus de "buf" seront lus comme zéro ou comme des résultats partiels du serveur. Si nbd_get_pread_initialize(3) retourne false, alors libnbd n'a pas nettoyé "buf", et les contenus sont indéfinis en cas d'échec.

Par défaut, libnbd rejettera les tentatives d'utilisation de cette fonction avec des paramètres susceptibles d'entraîner une défaillance du serveur, comme la demande d'un indicateur de commande inconnu. La fonction nbd_set_strict_mode(3) peut être utilisée pour modifier les scénarios qui doivent attendre une réponse du serveur plutôt que de échouer rapidement.

val block_status : ?flags:CMD_FLAG.t list -> t -> int64 -> int64 -> (string -> int64 -> int64 array -> int Stdlib.ref -> int) -> unit

NBD.block_status t ?flags count offset extent

envoyer la commande d'état de bloc, avec rappel 32 bits

émet la commande d'état de bloc au serveur NBD. Si elle est prise en charge par le serveur, cela provoque la retour d'informations de contexte de bloc commençant à partir de l'offset spécifié. Le paramètre « count » est une indication : le serveur peut choisir de retourner moins d'informations ou le bloc final peut s'étendre au-delà de la plage demandée. S'il existe plusieurs contextes pris en charge, le nombre de blocs et la longueur cumulée de ces blocs ne doivent pas nécessairement être égaux entre les contextes.

Notez que tous les serveurs ne peuvent pas prendre en charge un « count » de 4 Gio ou plus ; nbd_get_extended_headers_negotiated(3) indique quels serveurs analyseront une requête supérieure à 32 bits. Le protocole NBD n'a pas encore de moyen pour un client de savoir si le serveur imposera une taille d'état de bloc encore plus petite, bien qu'une future extension pourrait ajouter une restriction visible dans nbd_get_block_size(3). De plus, cette fonction est intrinsèquement limitée aux valeurs 32 bits. Si le serveur répond avec une taille d'extension supérieure à 32 bits (possible uniquement lors de l'utilisation d'en-têtes d'extension), la fonction de rappel recevra une erreur « EOVERFLOW ». Pour obtenir les informations d'extension complètes à partir d'un serveur qui prend en charge les extensions 64 bits, vous devez utiliser nbd_block_status_64(3).

Selon les contextes de métadonnées qui ont été activés avant la connexion (voir nbd_add_meta_context(3)) et ceux qui sont pris en charge par le serveur (voir nbd_can_meta_context(3)), cet appel retourne des informations sur les blocs en appelant la fonction de rappel « extent ». La fonction de rappel ne peut pas appeler les API « nbd_* » du même handle car elle détient le verrou du handle et provoquera un interblocage. Si la fonction de rappel retourne -1 et qu'aucune erreur préalable n'est détectée, la commande d'état de bloc échouera généralement avec toute valeur non nulle stockée dans le paramètre « error » de la fonction de rappel (avec une valeur par défaut de « EPROTO ») ; mais tout autre contexte continuera à invoquer la fonction de rappel.

La fonction « extent » est appelée une fois pour chaque type de contexte de métadonnées disponible, avec le « user_data » passé à cette fonction. Le paramètre « metacontext » est une chaîne telle que « base:allocation ». Le tableau « entries » est un tableau de paires d'entiers où le premier élément de chaque paire est la longueur (en octets) du bloc et le second élément est un champ d'état/statut/indicateur spécifique au contexte de métadonnées. Le nombre de paires passées à la fonction est « nr_entries/2 ». La documentation du protocole NBD dans la section sur « NBD_REPLY_TYPE_BLOCK_STATUS » décrit la signification de ce tableau ; pour les contextes connus de libnbd, contient des constantes commençant par « LIBNBD_STATE_ » qui peuvent aider à déchiffrer les valeurs. Au moment de l'entrée dans la fonction de rappel, le paramètre « error » contient la valeur de errno de toute erreur précédemment détectée, mais même si une erreur antérieure a été détectée, les valeurs actuelles de « metacontext » et « entries » sont valides.

Il est possible que la fonction « extent » soit appelée plus de fois que prévu (si le serveur est défectueux), vous devez donc toujours vérifier le champ « metacontext » pour vous assurer que vous recevez les données attendues. Il est également possible que la fonction « extent » ne soit pas appelée du tout, même pour les contextes de métadonnées que vous avez demandés. Cela indique que le serveur ne prend pas en charge le contexte ou qu'il y a une autre raison pour laquelle il ne peut pas retourner les données.

Le paramètre « flags » peut être 0 pour aucun indicateur, ou il peut contenir « LIBNBD_CMD_FLAG_REQ_ONE », ce qui signifie que le serveur ne retournera qu'un seul extrait par contexte de métadonnées où cet extrait ne dépasse pas « count » octets ; cependant, libnbd ne vérifie pas si le serveur a respecté l'indicateur.

Par défaut, libnbd rejettera les tentatives d'utilisation de cette fonction avec des paramètres susceptibles de provoquer une défaillance du serveur, comme la demande d'un indicateur de commande inconnu. La fonction nbd_set_strict_mode(3) peut être utilisée pour modifier les scénarios qui doivent attendre une réponse du serveur avant de pouvoir échouer rapidement.

val aio_get_direction : t -> int

NBD.aio_get_direction t

retourne la direction de lecture ou d'écriture

Retourne la direction actuelle de cette connexion, c'est-à-dire si l'on attend ensuite de lire des données du serveur, d'écrire des données au serveur, ou les deux. Il retourne

0 Nous ne sommes pas censés interagir avec le descripteur de fichier du serveur à partir de l'état actuel. Il n'est pas utile de tenter d'utiliser poll(2); si la connexion n'est pas morte, alors le progrès de la machine à états doit plutôt provenir d'un autre moyen tel que nbd_aio_connect(3).

"LIBNBD_AIO_DIRECTION_READ" = 1 Nous sommes censés lire ensuite du serveur. Si vous utilisez poll(2), vous définiriez "events = POLLIN". Si "revents" retourne "POLLIN" ou "POLLHUP", vous appelleriez alors nbd_aio_notify_read(3).

Notez qu'une fois que libnbd atteint nbd_aio_is_ready(3), cette direction est retournée même lorsqu'il n'y a pas de commandes en cours (voir nbd_aio_in_flight(3)). Dans une utilisation mono-thread de libnbd, il n'est pas utile de faire un poll avant d'émettre une commande, car sinon le serveur ne réveillera jamais le poll. Dans un scénario multi-thread, vous pouvez avoir un thread qui démarre une boucle de polling avant toute commande, mais tout autre thread qui émet une commande aura besoin d'un moyen de sortir le thread de polling du poll au cas où l'émission de la commande changerait la direction de polling nécessaire. Les moyens possibles pour y parvenir incluent le polling d'activité sur un pipe vers soi-même, ou l'utilisation de pthread_kill(3) pour envoyer un signal qui est masqué sauf pendant ppoll(2).

"LIBNBD_AIO_DIRECTION_WRITE" = 2 Nous sommes censés écrire ensuite au serveur. Si vous utilisez poll(2), vous définiriez "events = POLLOUT". Si "revents" retourne "POLLOUT", vous appelleriez alors nbd_aio_notify_write(3).

"LIBNBD_AIO_DIRECTION_BOTH" = 3 Nous sommes censés lire ou écrire ensuite au serveur. Si vous utilisez poll(2), vous définiriez "events = POLLIN|POLLOUT". Si seule l'une des deux options "POLLIN" ou "POLLOUT" est retournée, alors voir ci-dessus. Cependant, si les deux sont retournées, il est préférable d'appeler uniquement nbd_aio_notify_read(3), car le traitement de la réponse du serveur peut changer l'état de la connexion et invalider la nécessité d'écrire plus de commandes.

Envoie une notification à la machine à états que la connexion est inscriptible. Généralement, cela est appelé après que votre boucle principale ait détecté que le descripteur de fichier associé à cette connexion est inscriptible.

val aio_is_created : t -> bool

NBD.aio_is_created t

vérifie si la connexion vient d'être créée

Retourne vrai si cette connexion vient d'être créée. C'est l'état avant que le handle n'ait commencé à se connecter à un serveur. Dans cet état, le handle peut commencer à être connecté en appelant des fonctions telles que nbd_aio_connect(3).

val aio_is_connecting : t -> bool

NBD.aio_is_connecting t

vérifie si la connexion est en cours de connexion ou de handshake

Retourne vrai si cette connexion est en cours de connexion au serveur ou en cours de handshake et de négociation d'options, ce qui se produit avant que le handle ne soit prêt à émettre des commandes (voir nbd_aio_is_ready(3)).

val aio_is_negotiating : t -> bool

NBD.aio_is_negotiating t

vérifie si la connexion est prête à envoyer une commande d'option de handshake

Retourne vrai si cette connexion est prête à démarrer une autre commande de négociation d'option pendant le handshake avec le serveur. Une commande d'option ramènera à l'état de connexion (voir nbd_aio_is_connecting(3)). Notez que cet état ne peut pas être atteint à moins d'être demandé par nbd_set_opt_mode(3), et même dans ce cas, cela ne fonctionne qu'avec les serveurs newstyle ; un serveur oldstyle passera directement à nbd_aio_is_ready(3).

val aio_is_ready : t -> bool

NBD.aio_is_ready t

vérifie si la connexion est à l'état prêt

Retourne vrai si cette connexion est connectée au serveur NBD, que le handshake est terminé, et que la connexion est inactive ou en attente d'une réponse. Dans cet état, le handle est prêt à émettre des commandes.

val aio_is_processing : t -> bool

NBD.aio_is_processing t

vérifie si la connexion traite une commande

Retourne vrai si cette connexion est connectée au serveur NBD, que le handshake est terminé, et que la connexion traite des commandes (soit en écrivant une requête, soit en lisant une réponse).

Notez que l'état prêt (nbd_aio_is_ready(3)) n'est pas inclus. Dans l'état prêt, les commandes peuvent être *en cours* (le *serveur* les traite), mais libnbd ne les traite pas.

val aio_is_dead : t -> bool

NBD.aio_is_dead t

vérifie si la connexion est morte

Retourne vrai si la connexion a rencontré une erreur fatale et est morte. Dans cet état, le handle ne peut être que fermé. Il n'y a aucun moyen de récupérer un handle à partir de l'état mort.

val aio_is_closed : t -> bool

NBD.aio_is_closed t

vérifie si la connexion est fermée

Retourne vrai si la connexion est fermée. Il n'y a aucun moyen de reconnecter une connexion fermée. Au lieu de cela, vous devez fermer tout le handle.

val aio_command_completed : t -> int64 -> bool

NBD.aio_command_completed t cookie

vérifie si la commande est terminée

Retourne vrai si la commande est terminée. Si cette fonction retourne vrai, alors la commande a réussi et elle a été retirée. Retourne faux si la commande est toujours en cours. Cela peut aussi échouer avec une erreur si la commande a échoué (dans ce cas, la commande est également retirée). Une commande est retirée soit par cette commande, soit en utilisant un callback d'achèvement qui retourne 1.

Le paramètre "cookie" est le cookie unique positif de 64 bits pour la commande, tel que retourné par un appel tel que nbd_aio_pread(3).

val aio_peek_command_completed : t -> int64

NBD.aio_peek_command_completed t

vérifie si une commande est terminée

Retourne le cookie unique positif de 64 bits de la première commande non retirée mais terminée, 0 s'il y a des commandes en cours mais qu'aucune n'attend d'être retirée, ou -1 en cas d'erreur, y compris lorsqu'il n'y a pas de commandes en cours. Tout cookie retourné par cette fonction doit toujours être passé à nbd_aio_command_completed(3) pour réellement retirer la commande et savoir si la commande a réussi.

val aio_in_flight : t -> int

NBD.aio_in_flight t

vérifie combien de commandes aio sont toujours en cours

Retourne le nombre de commandes aio en cours qui attendent encore une réponse du serveur avant de pouvoir être retirées. Si cela retourne une valeur non nulle lors de la demande de déconnexion du serveur (voir nbd_aio_disconnect(3) et nbd_shutdown(3)), libnbd n'essaie pas d'attendre que ces commandes se terminent gracieusement ; si le serveur abandonne les commandes lors de l'arrêt, nbd_aio_command_completed(3) rapportera ces commandes comme ayant échoué avec un statut de "ENOTCONN".

val get_version : t -> string

NBD.get_version t

retourne la version de la bibliothèque

Retourne la version de libnbd. Elle est retournée sous forme de chaîne de caractères dans le format "majeur.mineur.release" où majeur, mineur et release sont de petits entiers positifs. Par exemple :

mineur ↓ "1.0.3" ↑ ↑ majeur release

majeur = 0 Le numéro majeur était 0 pour les premières versions expérimentales de libnbd où nous avions encore une API instable.

majeur = 1 Le numéro majeur est 1 pour les versions de libnbd avec une API et une ABI stables à long terme. Il n'est pas prévu que le numéro majeur soit différent de 1.

mineur = 0, 2, ... (pair) Le numéro mineur est pair pour les versions stables.

mineur = 1, 3, ... (impair) Le numéro mineur est impair pour les versions de développement. Notez que les nouvelles API ajoutées dans une version de développement restent expérimentales et sujettes à modification dans cette branche jusqu'à ce qu'elles apparaissent dans une version stable.

release Le numéro de release est incrémenté pour chaque sortie d'une branche particulière.

val kill_subprocess : t -> int -> unit

NBD.kill_subprocess t signum

tue le serveur exécuté en tant que sous-processus

Cet appel peut être utilisé pour tuer le serveur exécuté en tant que sous-processus qui a été précédemment créé à l'aide de nbd_connect_command(3). Vous n'avez pas besoin d'utiliser cet appel. Il n'est nécessaire que si le serveur ne se termine pas lorsque la socket est fermée.

Le paramètre "signum" est le numéro de signal optionnel à envoyer (voir signal(7)). Si "signum" est 0, alors "SIGTERM" est envoyé.

val get_subprocess_pid : t -> int64

NBD.get_subprocess_pid t

obtient l'identifiant du processus du sous-processus

Pour les connexions qui créent un sous-processus comme nbd_connect_command(3), ceci retourne l'identifiant du processus (PID) du sous-processus. Ceci n'est pris en charge que sur certaines plateformes.

Ceci est principalement utile dans les cas de débogage. Par exemple, cela pourrait être utilisé pour savoir où attacher gdb(1) pour diagnostiquer un plantage dans le sous-processus du serveur NBD.

val get_uri : t -> string

NBD.get_uri t

construit un URI NBD pour une connexion

Ceci fait un effort maximal pour construire un URI NBD qui pourrait être utilisé pour se reconnecter au même serveur (en utilisant nbd_connect_uri(3)).

Dans certains cas, il n'y a pas assez d'informations dans le handle pour créer un URI avec succès (par exemple, si vous vous êtes connecté avec nbd_connect_socket(3)). Dans de tels cas, l'appel retourne "NULL" et des informations de diagnostic supplémentaires sont disponibles via nbd_get_errno(3) et nbd_get_error(3) comme d'habitude.

Même si un URI est retourné, il n'est pas garanti qu'il fonctionne, et il peut ne pas être optimal.

L'option *--uri* de nbdinfo(1) est un moyen d'accéder à cette API depuis les scripts shell.

val is_uri : t -> string -> bool

NBD.is_uri t uri

détecte si une chaîne peut être un URI NBD

Détecte si le paramètre "uri" peut être un URI NBD ou non. La fonction retourne vrai si "uri" est susceptible d'être un URI NBD, ou faux sinon.

Ceci peut être utilisé pour écrire des programmes qui acceptent soit un URI, soit autre chose comme un nom de fichier comme paramètre. nbdcopy(1) est l'un de ces programmes.

Le test actuel est heuristique. En particulier, il ne garantit *pas* que nbd_connect_uri(3) fonctionnera.
