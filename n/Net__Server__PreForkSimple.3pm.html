Net::Server::PreForkSimple(3) Documentation Perl fournie par l'utilisateur Net::Server::PreForkSimple(3)

NOM

Net::Server::PreForkSimple - Personnalité de Net::Server

SYNTAXE

use base qw(Net::Server::PreForkSimple);
sub process_request {
    #...code...
}
__PACKAGE__->run();

DESCRIPTION

Veuillez lire d'abord le pod sur Net::Server. Ce module est une personnalité, ou une extension, ou une sous-classe du module Net::Server.

Cette personnalité se lie à un ou plusieurs ports, puis crée "max_servers" processus enfants. Le serveur s'assurera qu'à tout moment, il y a toujours "max_servers" processus disponibles pour recevoir une requête client. Chacun de ces enfants traitera jusqu'à "max_requests" connexions client. Ce type est bon pour un site très fréquenté qui peut maintenir "max_servers" processus dédiés au service. (L'acceptation multi-ports utilise par défaut flock pour sérialiser les enfants).

À l'heure actuelle, il ne semble pas que ce module réussisse les tests sur les systèmes Win32. Toutes idées ou correctifs pour faire réussir les tests seraient les bienvenus.

EXEMPLE DE CODE

Veuillez voir l'exemple listé dans Net::Server.

ARGUMENTS EN LIGNE DE COMMANDE

En plus des arguments en ligne de commande de la classe de base Net::Server, Net::Server::PreFork contient plusieurs autres paramètres configurables.

Clé               Valeur                  Défaut
max_servers       \d+                     50
max_requests      \d+                     1000
serialize         (flock|semaphore
                   |pipe|none)  undef
# serialize utilise par défaut flock sur multi_port ou sur Solaris
lock_file         "nom_fichier"              File::Temp->new
check_for_dead    \d+                     30
max_dequeue       \d+                     undef
check_for_dequeue \d+                     undef
max_servers
Le nombre maximum de processus enfants à démarrer et maintenir. Cela ne s'applique pas aux processus de défilement (dequeue).
max_requests
Le nombre de connexions client à recevoir avant qu'un enfant ne se termine.
serialize
Détermine si le serveur sérialise les connexions enfants. Les options sont undef, flock, semaphore, pipe, ou none. La valeur par défaut est undef. Sur les serveurs multi_port ou sur les serveurs exécutés sous Solaris, la valeur par défaut est flock. L'option flock utilise un verrou exclusif bloquant sur le fichier spécifié dans lock_file (voir ci-dessous). L'option semaphore utilise IPC::Semaphore (grâce à Bennett Todd) pour donner des exemples de code. L'option pipe lit sur un tube pour choisir le suivant. L'option flock devrait être la plus robuste, tandis que l'option pipe devrait être la plus portable. (Flock peut abandonner le blocage si le processus meurt entre l'acceptation sur le socket et la lecture de la connexion client - semaphore et pipe ne le font pas). Une option none n'effectuera aucune sérialisation. Si "none" est passé et qu'il y a plusieurs ports, la sérialisation par défaut sera utilisée à la place de "none".
lock_file
Nom du fichier à utiliser pour la sérialisation par acceptation flock afin de sérialiser la séquence d'acceptation entre les enfants. La valeur par défaut sera un nom de fichier temporaire généré. Si la valeur par défaut est utilisée, le fichier de verrouillage sera supprimé lorsque le serveur se fermera.
check_for_dead
Nombre de secondes à attendre avant de vérifier si un enfant est mort sans en informer le parent.
max_dequeue
Le nombre maximum de processus de défilement à démarrer. Si une valeur de zéro ou undef est donnée, aucun processus de défilement ne sera démarré. Le nombre de processus de défilement en cours d'exécution sera vérifié par la variable check_for_dead.
check_for_dequeue
Nombre de secondes à attendre avant de créer un processus de défilement. Le hook run_dequeue doit être défini lors de l'utilisation de ce paramètre. Il est prévu d'utiliser le processus de défilement pour s'occuper d'éléments tels que les files d'attente de courrier. Si une valeur undef est donnée, aucun processus de défilement ne sera démarré.

FICHIER DE CONFIGURATION

"Net::Server::PreFork" permet d'utiliser un fichier de configuration pour lire les paramètres du serveur. Le format de ce fichier de configuration est simple, avec des paires clé-valeur. Les commentaires et les espaces blancs sont ignorés.

#-------------- fichier test.conf --------------
### informations du serveur
max_servers   80
max_requests  1000
### utilisateur et groupe à devenir
user        quelqu'un
group       toutlemonde
### journalisation ?
log_file    /var/log/serveur.log
log_level   3
pid_file    /tmp/serveur.pid
### contrôle d'accès
allow       .+\.(net|com)
allow       domain\.com
deny        a.+
### lancer le processus en arrière-plan ?
background  1
### ports à lier
host        127.0.0.1
port        localhost:20204
port        20205
### recherches inversées ?
# reverse_lookups on
#-------------- fichier test.conf --------------

FLUX DES PROCESSUS

Le flux des processus suit Net::Server jusqu'à la phase de boucle. À ce stade, "max_servers" processus sont créés et attendent les connexions. Lorsqu'un enfant accepte une connexion, termine le traitement d'un client ou se termine, il transmet cette information au parent, qui assure le suivi et s'assure que "max_servers" processus sont toujours en exécution.

HOOKS

Le serveur PreForkSimple possède les hooks suivants en plus des hooks fournis par la classe de base Net::Server. Voir Net::Server

"$self->run_n_children_hook()"
Ce hook se produit au début de run_n_children, qui est appelé à chaque fois que le serveur s'apprête à démarrer des processus enfants supplémentaires. Cela permet au parent de faire un peu de comptabilité (selon le besoin). L'idée de ce hook provient de James FitzGibbon.
"$self->child_init_hook()"
Ce hook a lieu immédiatement après la création du processus enfant par le parent et avant que l'enfant ne commence à accepter des connexions. Il est destiné à des mesures de sécurité supplémentaires telles que le chroot. Il est suggéré que tous les modules Perl soient utilisés à ce stade, afin d'utiliser le maximum de mémoire partagée possible.
"$self->child_finish_hook()"
Ce hook a lieu juste avant que l'enfant n'informe le parent qu'il se termine. Il est destiné à enregistrer des informations ou à effectuer un nettoyage général.
"$self->run_dequeue()"
Ce hook n'est appelé qu'en conjonction avec le paramètre check_for_dequeue.
"$self->idle_loop_hook()"
Ce hook est appelé à chaque passage dans la boucle d'attente du processus principal.

DÉPLOIEMENT À CHAUD

Depuis la version 2.000, le serveur PreForkSimple accepte les signaux TTIN et TTOU. Lorsqu'un signal TTIN est reçu, max_servers est augmenté de 1. Si un signal TTOU est reçu, max_servers est diminué de 1. Cela permet d'ajuster le nombre de processus de gestion sans avoir à redémarrer le serveur.

BOGUES

Les tests ne semblent pas fonctionner sous Win32. Toutes idées ou correctifs seraient les bienvenus.
