exception Unix_error of error * string * string

Levée par les appels système ci-dessous lorsqu'une erreur est rencontrée. Le premier composant est le code d'erreur ; le second composant est le nom de la fonction ; le troisième composant est le paramètre chaîne de la fonction, s'il y en a un, ou une chaîne vide sinon.

UnixLabels.Unix_error et Unix.Unix_error sont identiques, et attraper l'une attrapera l'autre.

Cette fonction est identique à Sys.getenv .

putenv name value définit la valeur associée à une variable dans l'environnement du processus. name est le nom de la variable d'environnement, et value sa nouvelle valeur associée.

val execv : string -> string array -> 'a

execv prog args exécute le programme dans le fichier prog , avec les arguments args , et l'environnement du processus actuel. Notez que le premier argument, args.(0) , est par convention le nom de fichier du programme exécuté, tout comme Sys.argv.(0) . Ces fonctions execv* ne retournent jamais : en cas de succès, le programme actuel est remplacé par le nouveau.

Sous Windows : le CRT lance simplement un nouveau processus et termine le processus actuel. Cela aura des conséquences indésirables si, par exemple, un autre processus attend le processus actuel. Il est recommandé d'utiliser Unix.create_process ou l'une des fonctions open_process_* à la place.

val fork : unit -> int

Forks un nouveau processus. L'entier retourné est 0 pour le processus enfant, le pid du processus enfant pour le processus parent. Il échoue si le processus OCaml est multi-cœurs (un domaine a été lancé). De plus, si un thread du module Thread a été lancé, le processus enfant peut être dans un état corrompu.

Lève Invalid_argument sous Windows. Utilisez Unix.create_process ou les threads à la place.

Lève Failure si un domaine a été lancé.

val wait : unit -> int * process_status

Attend qu'un des processus enfants meure, et retourne son pid et son statut de terminaison.

Lève Invalid_argument sous Windows. Utilisez Unix.waitpid à la place.

val waitpid : wait_flag list -> int -> int * process_status

Identique à Unix.wait , mais attend le processus enfant dont le pid est donné. Un pid de -1 signifie attendre n'importe quel enfant. Un pid de 0 signifie attendre n'importe quel enfant du même groupe de processus que le processus actuel. Les arguments de pid négatifs représentent des groupes de processus. La liste des options indique si waitpid doit retourner immédiatement sans attendre, et s'il doit signaler les enfants arrêtés.

Sous Windows : ne peut attendre qu'un PID donné, pas n'importe quel processus enfant.

val system : string -> process_status

Exécute la commande donnée, attend qu'elle se termine et retourne son statut de terminaison. La chaîne est interprétée par le shell /bin/sh (ou l'interpréteur de commandes cmd.exe sous Windows) et peut donc contenir des redirections, des guillemets, des variables, etc. Pour bien échapper les espaces et les caractères spéciaux du shell dans les noms de fichiers ou les arguments de commande, l'utilisation de Filename.quote_command est recommandée. Le résultat WEXITED 127 indique que le shell n'a pas pu être exécuté.

val _exit : int -> 'a

Termine immédiatement le processus appelant, retournant le code de statut donné au système d'exploitation : généralement 0 pour indiquer aucune erreur, et un petit entier positif pour indiquer un échec. Contrairement à exit , Unix._exit n'effectue aucune finalisation : les fonctions enregistrées avec at_exit ne sont pas appelées, les canaux d'entrée/sortie ne sont pas vidés et le système d'exécution C n'est pas non plus finalisé.

L'utilisation typique de Unix._exit est après une opération Unix.fork , lorsque le processus enfant rencontre une erreur fatale et doit se terminer. Dans ce cas, il est préférable de ne pas effectuer d'action de finalisation dans le processus enfant, car ces actions pourraient interférer avec des actions similaires effectuées par le processus parent. Par exemple, les canaux de sortie ne doivent pas être vidés par le processus enfant, car le processus parent pourrait les vider à nouveau plus tard, entraînant une sortie en double.

Unix file descriptors

This module provides access to the primitives of the Unix kernel for file descriptor handling.

File descriptors

type file_descr

Abstract type for file descriptors. A file descriptor is a small integer that designates an open file or a primitive I/O channel, like a pipe, a socket, or a terminal. File descriptors are used by the operating system to identify various I/O objects. The standard descriptors 0, 1, and 2 are typically associated with the standard input, output, and error streams, respectively.

val openfile : string -> open_flag list -> file_perm -> file_descr

Open the file named by the given string. The flags and permissions for opening are given by the lists of flags and permissions. The list of flags must contain either O_RDONLY , O_WRONLY or O_RDWR . If the file is opened in write mode (O_WRONLY or O_RDWR ), the permissions are given by the third argument. Otherwise, this argument is ignored.

The following flags are available:

O_RDONLY
Open for reading only.
O_WRONLY
Open for writing only.
O_RDWR
Open for reading and writing.
O_CREAT
If the file does not exist, create it.
O_TRUNC
If the file exists and is opened for writing, truncate it to zero length.
O_APPEND
Append data to the end of the file.
O_NONBLOCK
Do not block when opening the file. If the open operation would block, it returns an error. This flag is ignored on some systems.
O_EXCL
Used in conjunction with O_CREAT . If the file exists, fail.
O_NOCTTY
If opening a terminal device, do not make it the controlling terminal for the process.
O_SYNC
Synchronize writes to the file.
O_DSYNC
Synchronize writes to the file. Same as O_SYNC , except that reading the file is not necessarily delayed.

The following permissions are available:

P_USR
User permissions.
P_GRP
Group permissions.
P_OTH
Other permissions.
P_READ
Read permission.
P_WRITE
Write permission.
P_EXECUTE
Execute permission.
P_ALL
All permissions.

For example, openfile "my_file" [O_CREAT; O_RDWR] [P_USR; P_WRITE] opens the file my_file for reading and writing, creating it if it doesn't exist, with read and write permissions for the owner.

val close : file_descr -> unit

Close the given file descriptor. Any attempt to use this descriptor after closing it results in an exception.

val read : file_descr -> string -> int -> int -> int

Read at most count bytes from the file descriptor fd into the string s , starting at position offset . Return the number of bytes actually read. A return value of 0 indicates end-of-file.

val write : file_descr -> string -> int -> int -> int

Write the bytes from the string s , starting at position offset and containing count bytes, to the file descriptor fd . Return the number of bytes actually written.

val lseek : file_descr -> int -> seek_command -> int

Set the current position for a file descriptor, and return the resulting offset (from the beginning of the file).

val pipe : unit -> file_descr * file_descr

Create a pipe. Return a pair of file descriptors, one for reading and one for writing.

val dup : file_descr -> file_descr

Duplicate the given file descriptor. The new descriptor refers to the same open file description as the original, sharing the file offset, file status flags, and current settings for file flags. See dup2 for a way to control which descriptor is duplicated.

val dup2 : file_descr -> file_descr -> unit

Duplicate the file descriptor oldfd into newfd . If newfd was previously open, it is closed first. This function is useful for redirecting standard input, output, or error streams.

Example: To redirect standard output to a file descriptor `fd`: `Unix.dup2 fd Unix.stdout`.

val ioctl : file_descr -> int -> [<`int] Ctypes.Val.t -> unit

Perform an ioctl operation on the given file descriptor. The second argument is the request code, and the third argument is the argument to the ioctl call. The type of the argument depends on the request code.

val isatty : file_descr -> bool

Return true if the given file descriptor refers to a terminal or console window, false otherwise.

Channels

val in_channel_of_descr : file_descr -> in_channel

Create an input channel reading from the given descriptor. The channel is initially in binary mode; use set_binary_mode_in ic false if text mode is desired. Text mode is supported only if the descriptor refers to a file or pipe, but is not supported if it refers to a socket.

On Windows: set_binary_mode_in always fails on channels created with this function.

Beware that input channels are buffered, so more characters may have been read from the descriptor than those accessed using channel functions. Channels also keep a copy of the current position in the file.

Closing the channel ic returned by in_channel_of_descr fd using close_in ic also closes the underlying descriptor fd . It is incorrect to close both the channel ic and the descriptor fd .

If several channels are created on the same descriptor, one of the channels must be closed, but not the others. Consider for example a descriptor s connected to a socket and two channels ic = in_channel_of_descr s and oc = out_channel_of_descr s . The recommended closing protocol is to perform close_out oc , which flushes buffered output to the socket then closes the socket. The ic channel must not be closed and will be collected by the GC eventually.

val out_channel_of_descr : file_descr -> out_channel

Create an output channel writing on the given descriptor. The channel is initially in binary mode; use set_binary_mode_out oc false if text mode is desired. Text mode is supported only if the descriptor refers to a file or pipe, but is not supported if it refers to a socket.

On Windows: set_binary_mode_out always fails on channels created with this function.

Beware that output channels are buffered, so you may have to call flush to ensure that all data has been sent to the descriptor. Channels also keep a copy of the current position in the file.

Closing the channel oc returned by out_channel_of_descr fd using close_out oc also closes the underlying descriptor fd . It is incorrect to close both the channel ic and the descriptor fd .

See Unix.in_channel_of_descr for a discussion of the closing protocol when several channels are created on the same descriptor.

File operations on large files

module LargeFile : sig end

File operations on large files. This sub-module provides 64-bit variants of the functions Unix.LargeFile.lseek (for positioning a file descriptor), Unix.LargeFile.truncate and Unix.LargeFile.ftruncate (for changing the size of a file), and Unix.LargeFile.stat , Unix.LargeFile.lstat and Unix.LargeFile.fstat (for obtaining information on files). These alternate functions represent positions and sizes by 64-bit integers (type int64 ) instead of regular integers (type int ), thus allowing operating on files whose sizes are greater than max_int .

Mapping files into memory

val map_file : file_descr -> ?pos:int64 -> ('a, 'b) Bigarray.kind -> 'c Bigarray.layout -> bool -> int array -> ('a, 'b, 'c) Bigarray.Genarray.t

Memory mapping of a file as a Bigarray. map_file fd kind layout shared dims returns a Bigarray of kind kind , layout layout , and dimensions as specified in dims . The data contained in this Bigarray are the contents of the file referred to by the file descriptor fd (as opened previously with Unix.openfile , for example). The optional pos parameter is the byte offset in the file of the data being mapped; it defaults to 0 (map from the beginning of the file).

If shared is true , all modifications performed on the array are reflected in the file. This requires that fd be opened with write permissions. If shared is false , modifications performed on the array are done in memory only, using copy-on-write of the modified pages; the underlying file is not affected.

Unix.map_file is much more efficient than reading the whole file in a Bigarray, modifying that Bigarray, and writing it afterwards.

To adjust automatically the dimensions of the Bigarray to the actual size of the file, the major dimension (that is, the first dimension for an array with C layout, and the last dimension for an array with Fortran layout) can be given as -1 . Unix.map_file then determines the major dimension from the size of the file. The file must contain an integral number of sub-arrays as determined by the non-major dimensions, otherwise Failure is raised.

If all dimensions of the Bigarray are given, the file size is matched against the size of the Bigarray. If the file is larger than the Bigarray, only the initial portion of the file is mapped to the Bigarray. If the file is smaller than the big array, the file is automatically grown to the size of the Bigarray. This requires write permissions on fd .

Array accesses are bounds-checked, but the bounds are determined by the initial call to map_file . Therefore, you should make sure no other process modifies the mapped file while you're accessing it, or a SIGBUS signal may be raised. This happens, for instance, if the file is shrunk.

Invalid_argument or Failure may be raised in cases where argument validation fails.

val set_close_on_exec : file_descr -> unit

Définit le drapeau « fermer à l'exécution » sur le descripteur donné. Un descripteur avec le drapeau fermer à l'exécution est automatiquement fermé lorsque le processus courant lance un autre programme avec l'une des fonctions exec, create_process et open_process.

Il est souvent une faille de sécurité de laisser fuiter des descripteurs de fichier ouverts sur, par exemple, un fichier privé vers un programme externe : le programme obtient alors l'accès au fichier privé et peut en faire de mauvaises choses. Par conséquent, il est fortement recommandé de définir tous les descripteurs de fichier « fermer à l'exécution », sauf dans les très rares cas où un descripteur de fichier doit réellement être transmis à un autre programme.

La meilleure façon de définir un descripteur de fichier « fermer à l'exécution » est de le créer dans cet état. À cette fin, la fonction openfile a des drapeaux O_CLOEXEC et O_KEEPEXEC pour imposer le mode « fermer à l'exécution » ou le mode « garder à l'exécution », respectivement. Toutes les autres opérations du module Unix qui créent des descripteurs de fichier ont un argument optionnel ?cloexec:bool pour indiquer si le descripteur de fichier doit être créé en mode « fermer à l'exécution » (en écrivant ~cloexec:true) ou en mode « garder à l'exécution » (en écrivant ~cloexec:false). Pour des raisons historiques, le mode de création de descripteur de fichier par défaut est « garder à l'exécution », si aucun argument optionnel cloexec n'est donné. Ce n'est pas un défaut sûr, il est donc fortement recommandé de passer des arguments cloexec explicites aux opérations qui créent des descripteurs de fichier.

Les arguments optionnels cloexec et le drapeau O_KEEPEXEC ont été introduits dans OCaml 4.05. Auparavant, la pratique courante consistait à créer des descripteurs de fichier dans le mode par défaut, « garder à l'exécution », puis à appeler set_close_on_exec sur ces descripteurs de fichier fraîchement créés. Ce n'est pas aussi sûr que de créer le descripteur de fichier en mode « fermer à l'exécution » car, dans les programmes multithreadés, une fenêtre de vulnérabilité existe entre le moment où le descripteur de fichier est créé et le moment où set_close_on_exec se termine. Si un autre thread lance un autre programme pendant cette fenêtre, le descripteur fuira, car il est toujours en mode « garder à l'exécution ».

Concernant les garanties d'atomicité données par ~cloexec:true ou par l'utilisation du drapeau O_CLOEXEC : sur toutes les plateformes, il est garanti qu'un thread Caml exécuté simultanément ne peut pas laisser fuir le descripteur en lançant un nouveau processus. Sous Linux, cette garantie s'étend aux threads C exécutés simultanément. En février 2017, d'autres systèmes d'exploitation manquent des appels système nécessaires et exposent toujours une fenêtre de vulnérabilité pendant laquelle un thread C peut voir le descripteur de fichier nouvellement créé en mode « garder à l'exécution ».

Commandes pour Unix.lockf .

val lockf : file_descr -> lock_command -> int -> unit

lockf fd mode len place un verrou sur une région du fichier ouvert comme fd . La région commence à la position de lecture/écriture actuelle pour fd (définie par Unix.lseek ) et s'étend sur len octets vers l'avant si len est positif, len octets vers l'arrière si len est négatif, ou jusqu'à la fin du fichier si len est zéro. Un verrou d'écriture empêche tout autre processus d'acquérir un verrou de lecture ou d'écriture sur la région. Un verrou de lecture empêche tout autre processus d'acquérir un verrou d'écriture sur la région, mais permet à d'autres processus d'acquérir des verrous de lecture sur celle-ci.

Les commandes F_LOCK et F_TLOCK tentent de placer un verrou d'écriture sur la région spécifiée. Les commandes F_RLOCK et F_TRLOCK tentent de placer un verrou de lecture sur la région spécifiée. Si un ou plusieurs verrous placés par un autre processus empêchent le processus actuel d'acquérir le verrou, F_LOCK et F_RLOCK bloquent jusqu'à ce que ces verrous soient supprimés, tandis que F_TLOCK et F_TRLOCK échouent immédiatement avec une exception. F_ULOCK supprime tous les verrous que le processus actuel a sur la région spécifiée. Enfin, la commande F_TEST teste si un verrou d'écriture peut être acquis sur la région spécifiée, sans placer réellement de verrou. Elle retourne immédiatement si elle réussit, ou échoue sinon.

Ce qui se passe lorsqu'un processus tente de verrouiller une région d'un fichier qui est déjà verrouillée par le même processus dépend du système d'exploitation. Sur les systèmes conformes POSIX, la deuxième opération de verrouillage réussit et peut "promouvoir" le verrou plus ancien de verrou de lecture à verrou d'écriture. Sous Windows, la deuxième opération de verrouillage bloquera ou échouera.

val open_connection : sockaddr -> in_channel * out_channel

Se connecte à un serveur à l'adresse donnée. Retourne une paire de canaux tamponnés connectés au serveur. N'oubliez pas d'appeler flush sur le canal de sortie au bon moment pour assurer une synchronisation correcte.

Les deux canaux retournés par open_connection partagent un descripteur de socket. Par conséquent, une fois la connexion terminée, vous devriez appeler close_out sur le canal de sortie, ce qui fermera également le socket sous-jacent. N'appelez pas close_in sur le canal d'entrée ; il sera collecté par le GC éventuellement.

val shutdown_connection : in_channel -> unit

``Arrête'' une connexion établie avec Unix.open_connection ; c'est-à-dire, transmet une condition de fin de fichier au serveur lisant de l'autre côté de la connexion. Cela ne ferme pas le socket ni les canaux utilisés par la connexion. Voir Unix.open_connection pour savoir comment les fermer une fois la connexion terminée.

val establish_server : (in_channel -> out_channel -> unit) -> sockaddr -> unit

Établit un serveur à l'adresse donnée. La fonction passée comme premier argument est appelée pour chaque connexion avec deux canaux tamponnés connectés au client. Un nouveau processus est créé pour chaque connexion. La fonction Unix.establish_server ne retourne jamais normalement.

Les deux canaux donnés à la fonction partagent un descripteur de socket. La fonction n'a pas besoin de fermer les canaux, car cela se produit automatiquement lorsque la fonction retourne. Si la fonction préfère une fermeture explicite, elle doit fermer le canal de sortie en utilisant close_out et laisser le canal d'entrée non fermé, pour les raisons expliquées dans Unix.in_channel_of_descr .
