Module UnixLabels

Interface avec le système Unix.

Pour utiliser la version étiquetée de ce module, ajoutez module Unix = UnixLabels dans votre implémentation.

Note : toutes les fonctions de ce module (sauf UnixLabels.error_message et UnixLabels.handle_unix_error ) peuvent lever l'exception UnixLabels.Unix_error chaque fois que l'appel système sous-jacent signale une erreur.

val execv : prog:string -> args:string array -> 'a

execv prog args execute the program in file prog , with the arguments args , and the current process environment. Note that the first argument, args.(0) , is by convention the filename of the program being executed, just like Sys.argv.(0) . These execv* functions never return: on success, the current program is replaced by the new one.

On Windows: the CRT simply spawns a new process and exits the current one. This will have unwanted consequences if e.g. another process is waiting on the current one. Using UnixLabels.create_process or one of the open_process_* functions instead is recommended.

Raises Unix_error on failure

val execve : prog:string -> args:string array -> env:string array -> 'a

Same as UnixLabels.execv , except that the third argument provides the environment to the program executed.

val execvp : prog:string -> args:string array -> 'a

Same as UnixLabels.execv , except that the program is searched in the path.

val execvpe : prog:string -> args:string array -> env:string array -> 'a

Same as UnixLabels.execve , except that the program is searched in the path.

val fork : unit -> int

Fork a new process. The returned integer is 0 for the child process, the pid of the child process for the parent process. It fails if the OCaml process is multi-core (any domain has been spawned). In addition, if any thread from the Thread module has been spawned, then the child process might be in a corrupted state.

Raises Invalid_argument on Windows. Use UnixLabels.create_process or threads instead.

Raises Failure if any domain has been spawned.

val wait : unit -> int * process_status

Wait until one of the children processes die, and return its pid and termination status.

Raises Invalid_argument on Windows. Use UnixLabels.waitpid instead.

val waitpid : mode:wait_flag list -> int -> int * process_status

Same as UnixLabels.wait , but waits for the child process whose pid is given. A pid of -1 means wait for any child. A pid of 0 means wait for any child in the same process group as the current process. Negative pid arguments represent process groups. The list of options indicates whether waitpid should return immediately without waiting, and whether it should report stopped children.

On Windows: can only wait for a given PID, not any child process.

val system : string -> process_status

Execute the given command, wait until it terminates, and return its termination status. The string is interpreted by the shell /bin/sh (or the command interpreter cmd.exe on Windows) and therefore can contain redirections, quotes, variables, etc. To properly quote whitespace and shell special characters occurring in file names or command arguments, the use of Filename.quote_command is recommended. The result WEXITED 127 indicates that the shell couldn't be executed.

val _exit : int -> 'a

Terminate the calling process immediately, returning the given status code to the operating system: usually 0 to indicate no errors, and a small positive integer to indicate failure. Unlike exit , Unix._exit performs no finalization whatsoever: functions registered with at_exit are not called, input/output channels are not flushed, and the C run-time system is not finalized either.

The typical use of Unix._exit is after a Unix.fork operation, when the child process runs into a fatal error and must exit. In this case, it is preferable to not perform any finalization action in the child process, as these actions could interfere with similar actions performed by the parent process. For example, output channels should not be flushed by the child process, as the parent process may flush them again later, resulting in duplicate output.

Interfacing with the standard input/output library

Bibliothèque standard d'entrée/sortie

val in_channel_of_descr : file_descr -> in_channel

Crée un canal d'entrée lisant à partir du descripteur donné. Le canal est initialement en mode binaire ; utilisez set_binary_mode_in ic false si le mode texte est souhaité. Le mode texte n'est pris en charge que si le descripteur fait référence à un fichier ou à un pipe, mais n'est pas pris en charge s'il fait référence à une socket.

Sous Windows : set_binary_mode_in échoue toujours sur les canaux créés avec cette fonction.

Attention, les canaux d'entrée sont mis en tampon, de sorte que plus de caractères peuvent avoir été lus du descripteur que ceux qui sont accessibles à l'aide des fonctions de canal. Les canaux conservent également une copie de la position actuelle dans le fichier.

La fermeture du canal ic retourné par in_channel_of_descr fd en utilisant close_in ic ferme également le descripteur sous-jacent fd . Il est incorrect de fermer à la fois le canal ic et le descripteur fd .

Si plusieurs canaux sont créés sur le même descripteur, l'un des canaux doit être fermé, mais pas les autres. Considérez par exemple un descripteur s connecté à une socket et deux canaux ic = in_channel_of_descr s et oc = out_channel_of_descr s . Le protocole de fermeture recommandé est d'effectuer close_out oc , ce qui vide la sortie mise en tampon vers la socket puis ferme la socket. Le canal ic ne doit pas être fermé et sera récupéré par le GC éventuellement.

val out_channel_of_descr : file_descr -> out_channel

Crée un canal de sortie écrivant sur le descripteur donné. Le canal est initialement en mode binaire ; utilisez set_binary_mode_out oc false si le mode texte est souhaité. Le mode texte n'est pris en charge que si le descripteur fait référence à un fichier ou à un pipe, mais n'est pas pris en charge s'il fait référence à une socket.

Sous Windows : set_binary_mode_out échoue toujours sur les canaux créés avec cette fonction.

Attention, les canaux de sortie sont mis en tampon, vous devrez donc peut-être appeler flush pour vous assurer que toutes les données ont été envoyées au descripteur. Les canaux conservent également une copie de la position actuelle dans le fichier.

La fermeture du canal oc retourné par out_channel_of_descr fd en utilisant close_out oc ferme également le descripteur sous-jacent fd . Il est incorrect de fermer à la fois le canal ic et le descripteur fd .

Voir Unix.in_channel_of_descr pour une discussion sur le protocole de fermeture lorsque plusieurs canaux sont créés sur le même descripteur.

Mappage de fichiers en mémoire

val map_file : file_descr -> ?pos:int64 -> kind:('a, 'b) Bigarray.kind -> layout:'c Bigarray.layout -> shared:bool -> dims:int array -> ('a, 'b, 'c) Bigarray.Genarray.t

Mappage mémoire d'un fichier en tant que Bigarray. map_file fd ~kind ~layout ~shared ~dims retourne un Bigarray de type kind , disposition layout et dimensions spécifiées dans dims . Les données contenues dans ce Bigarray sont le contenu du fichier référencé par le descripteur de fichier fd (ouvert précédemment avec UnixLabels.openfile , par exemple). Le paramètre optionnel pos est le décalage en octets dans le fichier des données mappées ; il vaut par défaut 0 (mappage depuis le début du fichier).

Si shared est true , toutes les modifications effectuées sur le tableau sont reflétées dans le fichier. Cela nécessite que fd soit ouvert avec les permissions d'écriture. Si shared est false , les modifications effectuées sur le tableau se font uniquement en mémoire, utilisant la copie sur écriture des pages modifiées ; le fichier sous-jacent n'est pas affecté.

UnixLabels.map_file est beaucoup plus efficace que de lire l'intégralité du fichier dans un Bigarray, de modifier ce Bigarray, puis de l'écrire par la suite.

Pour ajuster automatiquement les dimensions du Bigarray à la taille réelle du fichier, la dimension majeure (c'est-à-dire la première dimension pour un tableau avec disposition C, et la dernière dimension pour un tableau avec disposition Fortran) peut être donnée comme -1 . UnixLabels.map_file détermine alors la dimension majeure à partir de la taille du fichier. Le fichier doit contenir un nombre entier de sous-tableaux tel que déterminé par les dimensions non majeures, sinon Failure est levée.

Si toutes les dimensions du Bigarray sont données, la taille du fichier est comparée à la taille du Bigarray. Si le fichier est plus grand que le Bigarray, seule la portion initiale du fichier est mappée au Bigarray. Si le fichier est plus petit que le Bigarray, le fichier est automatiquement agrandi à la taille du Bigarray. Cela nécessite des permissions d'écriture sur fd .

Les accès aux tableaux sont vérifiés aux limites, mais les limites sont déterminées par l'appel initial à map_file . Par conséquent, vous devriez vous assurer qu'aucun autre processus ne modifie le fichier mappé pendant que vous y accédez, sinon un signal SIGBUS peut être levé. Cela se produit, par exemple, si le fichier est réduit.

Invalid_argument ou Failure peuvent être levés dans les cas où la validation des arguments échoue.

val set_nonblock : file_descr -> unit

Définit l'indicateur « non bloquant » sur le descripteur donné. Lorsque l'indicateur non bloquant est défini, la lecture sur un descripteur pour lequel il n'y a temporairement aucune donnée disponible lève l'erreur EAGAIN ou EWOULDBLOCK au lieu de bloquer ; l'écriture sur un descripteur pour lequel il n'y a temporairement pas de place pour écrire lève également EAGAIN ou EWOULDBLOCK.

val clear_nonblock : file_descr -> unit

Efface l'indicateur « non bloquant » sur le descripteur donné. Voir UnixLabels.set_nonblock.

val set_close_on_exec : file_descr -> unit

Définit l'indicateur « fermer à l'exécution » (close-on-exec) sur le descripteur donné. Un descripteur avec l'indicateur close-on-exec est automatiquement fermé lorsque le processus courant démarre un autre programme avec l'une des fonctions exec, create_process et open_process.

Il s'agit souvent d'une faille de sécurité de laisser fuiter des descripteurs de fichiers ouverts sur, par exemple, un fichier privé vers un programme externe : le programme obtient alors l'accès au fichier privé et peut en faire de mauvaises choses. Par conséquent, il est fortement recommandé de définir tous les descripteurs de fichiers « close-on-exec », sauf dans les très rares cas où un descripteur de fichier doit réellement être transmis à un autre programme.

La meilleure façon de définir un descripteur de fichier « close-on-exec » est de le créer dans cet état. À cette fin, la fonction openfile possède les indicateurs O_CLOEXEC et O_KEEPEXEC pour imposer le mode « close-on-exec » ou le mode « keep-on-exec », respectivement. Toutes les autres opérations du module Unix qui créent des descripteurs de fichiers ont un argument optionnel ?cloexec:bool pour indiquer si le descripteur de fichier doit être créé en mode « close-on-exec » (en écrivant ~cloexec:true) ou en mode « keep-on-exec » (en écrivant ~cloexec:false). Pour des raisons historiques, le mode de création par défaut des descripteurs de fichiers est « keep-on-exec », si aucun argument optionnel cloexec n'est donné. Ce n'est pas un défaut sûr, il est donc fortement recommandé de passer des arguments cloexec explicites aux opérations qui créent des descripteurs de fichiers.

Les arguments optionnels cloexec et l'indicateur O_KEEPEXEC ont été introduits dans OCaml 4.05. Auparavant, la pratique courante était de créer des descripteurs de fichiers dans le mode par défaut, « keep-on-exec », puis d'appeler set_close_on_exec sur ces descripteurs de fichiers fraîchement créés. Ce n'est pas aussi sûr que de créer le descripteur de fichier en mode « close-on-exec » car, dans les programmes multithreadés, une fenêtre de vulnérabilité existe entre le moment où le descripteur de fichier est créé et le moment où set_close_on_exec se termine. Si un autre thread lance un autre programme pendant cette fenêtre, le descripteur fuira, car il est toujours en mode « keep-on-exec ».

Concernant les garanties d'atomicité données par ~cloexec:true ou par l'utilisation de l'indicateur O_CLOEXEC : sur toutes les plateformes, il est garanti qu'un thread Caml s'exécutant concurremment ne peut pas laisser fuiter le descripteur en démarrant un nouveau processus. Sous Linux, cette garantie s'étend aux threads C s'exécutant concurremment. En février 2017, d'autres systèmes d'exploitation manquent des appels système nécessaires et exposent toujours une fenêtre de vulnérabilité pendant laquelle un thread C peut voir le descripteur de fichier nouvellement créé en mode « keep-on-exec ».

Efface l'indicateur « fermer à l'exécution » (close-on-exec) sur le descripteur donné. Voir UnixLabels.set_close_on_exec.

Gestion de haut niveau des processus et des redirections

val create_process : prog:string -> args:string array -> stdin:file_descr -> stdout:file_descr -> stderr:file_descr -> int

create_process ~prog ~args ~stdin ~stdout ~stderr crée un nouveau processus qui exécute le programme dans le fichier prog, avec les arguments args. Notez que le premier argument, args.(0) , est par convention le nom du fichier du programme exécuté, tout comme Sys.argv.(0) . Le pid du nouveau processus est retourné immédiatement ; le nouveau processus s'exécute de manière concurrente avec le processus courant. Les entrées et sorties standard du nouveau processus sont connectées aux descripteurs stdin, stdout et stderr. Passer par exemple Unix.stdout pour stdout empêche la redirection et fait en sorte que le nouveau processus ait la même sortie standard que le processus courant. Le fichier exécutable prog est recherché dans le chemin. Le nouveau processus a le même environnement que le processus courant.

val create_process_env : prog:string -> args:string array -> env:string array -> stdin:file_descr -> stdout:file_descr -> stderr:file_descr -> int

create_process_env ~prog ~args ~env ~stdin ~stdout ~stderr fonctionne comme UnixLabels.create_process, sauf que l'argument supplémentaire env spécifie l'environnement passé au programme.

Liens symboliques

val symlink : ?to_dir:bool -> src:string -> dst:string -> unit

symlink ?to_dir ~src ~dst crée le fichier dst comme lien symbolique vers le fichier src . Sous Windows, ~to_dir indique si le lien symbolique pointe vers un répertoire ou un fichier ; si omis, symlink examine src en utilisant stat et choisit appropriément. Si src n'existe pas, false est supposé (pour cette raison, il est recommandé de spécifier le paramètre ~to_dir dans le code nouveau). Sous Unix, ~to_dir est ignoré.

Les liens symboliques Windows sont disponibles à partir de Windows Vista. Il existe des différences importantes entre les liens symboliques Windows et leurs équivalents POSIX.

Les liens symboliques Windows existent en deux saveurs : répertoire et régulier, qui désignent si le lien symbolique pointe vers un répertoire ou un fichier. Le type doit être correct : un lien symbolique de répertoire qui pointe en fait vers un fichier ne peut pas être sélectionné avec chdir, et un lien symbolique de fichier qui pointe en fait vers un répertoire ne peut être lu ou écrit (notez que la couche d'émulation de Cygwin ignore cette distinction).

Lorsque des liens symboliques sont créés vers des cibles existantes, cette distinction n'a pas d'importance et symlink crée automatiquement le type de lien symbolique correct. La distinction est importante lorsqu'un lien symbolique est créé vers une cible inexistante.

L'autre mise en garde est que, par défaut, les liens symboliques sont une opération privilégiée. Les administrateurs devront toujours s'exécuter en mode élevé (ou avec UAC désactivé) et, par défaut, les comptes utilisateurs normaux devront se voir accorder le privilège SeCreateSymbolicLinkPrivilege via la Stratégie de sécurité locale (secpol.msc) ou via Active Directory.

UnixLabels.has_symlink peut être utilisé pour vérifier qu'un processus est capable de créer des liens symboliques.

val has_symlink : unit -> bool

Retourne true si l'utilisateur est capable de créer des liens symboliques. Sous Windows, cela indique que l'utilisateur a non seulement le privilège SeCreateSymbolicLinkPrivilege, mais qu'il s'exécute également en mode élevé, si nécessaire. Sur d'autres plateformes, cela indique simplement que l'appel système de lien symbolique est disponible.

Commandes pour UnixLabels.lockf .

val lockf : file_descr -> mode:lock_command -> len:int -> unit

lockf fd ~mode ~len place un verrou sur une région du fichier ouvert sous fd . La région commence à la position de lecture/écriture actuelle pour fd (définie par UnixLabels.lseek ), et s'étend sur len octets vers l'avant si len est positif, len octets vers l'arrière si len est négatif, ou jusqu'à la fin du fichier si len est zéro. Un verrou d'écriture empêche tout autre processus d'acquérir un verrou de lecture ou d'écriture sur la région. Un verrou de lecture empêche tout autre processus d'acquérir un verrou d'écriture sur la région, mais permet à d'autres processus d'acquérir des verrous de lecture sur celle-ci.

Les commandes F_LOCK et F_TLOCK tentent de placer un verrou d'écriture sur la région spécifiée. Les commandes F_RLOCK et F_TRLOCK tentent de placer un verrou de lecture sur la région spécifiée. Si un ou plusieurs verrous placés par un autre processus empêchent le processus courant d'acquérir le verrou, F_LOCK et F_RLOCK bloquent jusqu'à ce que ces verrous soient supprimés, tandis que F_TLOCK et F_TRLOCK échouent immédiatement avec une exception. F_ULOCK supprime tous les verrous que le processus courant détient sur la région spécifiée. Enfin, la commande F_TEST teste si un verrou d'écriture peut être acquis sur la région spécifiée, sans placer réellement de verrou. Elle retourne immédiatement en cas de succès, ou échoue sinon.

Fonctions de connexion réseau de haut niveau

val open_connection : sockaddr -> in_channel * out_channel

Se connecte à un serveur à l'adresse donnée. Retourne une paire de canaux tamponnés connectés au serveur. N'oubliez pas d'appeler flush sur le canal de sortie aux moments appropriés pour assurer une synchronisation correcte.

Les deux canaux retournés par open_connection partagent un descripteur de socket. Par conséquent, lorsque la connexion est terminée, vous devriez appeler close_out sur le canal de sortie, ce qui fermera également le socket sous-jacent. N'appelez pas close_in sur le canal d'entrée ; il sera collecté par le GC éventuellement.

val shutdown_connection : in_channel -> unit

« Ferme » une connexion établie avec UnixLabels.open_connection ; c'est-à-dire qu'elle transmet une condition de fin de fichier au serveur qui lit de l'autre côté de la connexion. Cela ne ferme pas le socket et les canaux utilisés par la connexion. Voir Unix.open_connection pour savoir comment les fermer une fois la connexion terminée.

val establish_server : (in_channel -> out_channel -> unit) -> addr:sockaddr -> unit

Établit un serveur à l'adresse donnée. La fonction donnée comme premier argument est appelée pour chaque connexion avec deux canaux tamponnés connectés au client. Un nouveau processus est créé pour chaque connexion. La fonction UnixLabels.establish_server ne retourne jamais normalement.

Les deux canaux donnés à la fonction partagent un descripteur de socket. La fonction n'a pas besoin de fermer les canaux, car cela se produit automatiquement lorsque la fonction retourne. Si la fonction préfère une fermeture explicite, elle doit fermer le canal de sortie à l'aide de close_out et laisser le canal d'entrée non fermé, pour les raisons expliquées dans Unix.in_channel_of_descr .

Lève Invalid_argument sous Windows. Utilisez des threads à la place.
