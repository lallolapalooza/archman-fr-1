NOM

URI::file - URI qui correspond aux noms de fichiers locaux

SYNTAXE

use URI::file;
$u1 = URI->new("file:/foo/bar");
$u2 = URI->new("foo/bar", "file");
$u3 = URI::file->new($path);
$u4 = URI::file->new("c:\\windows\\", "win32");
$u1->file;
$u1->file("mac");

DESCRIPTION

La classe "URI::file" prend en charge les objets "URI" appartenant au schéma URI file. Ce schéma nous permet de mapper les noms de fichiers conventionnels trouvés sur divers systèmes informatiques à l'espace de noms URI, voir RFC 8089 https://www.rfc-editor.org/rfc/rfc8089.html.

Si vous souhaitez simplement construire des objets URI file à partir de chaînes URI, utilisez le constructeur normal "URI". Si vous souhaitez construire des objets URI file à partir des noms de fichiers réels utilisés par divers systèmes, utilisez l'un des constructeurs "URI::file" suivants :

$u = URI::file->new( $filename, [$os] )
Mappe un nom de fichier dans l'espace de noms URI file:, crée un objet URI et le retourne. Le $filename est interprété comme appartenant au système d'exploitation indiqué ($os), qui par défaut a la valeur de la variable $^O. Le $filename peut être absolu ou relatif, et le type d'objet URI correspondant à $os est retourné.
$u = URI::file->new_abs( $filename, [$os] )
Identique à URI::file->new, mais s'assure que l'URI retournée représente un nom de fichier absolu. Si l'argument $filename est relatif, le nom est résolu par rapport au répertoire courant, c'est-à-dire que ce constructeur est en réalité identique à : 
URI::file->new($filename)->abs(URI::file->cwd);
$u = URI::file->cwd
Retourne un URI file qui représente le répertoire de travail courant. Voir Cwd.

Les méthodes suivantes sont prises en charge pour les URI file (en plus des méthodes communes et génériques décrites dans URI) :

$u->file( [$os] )
Retourne un nom de fichier. Il mappe de l'espace de noms URI vers l'espace de noms de fichiers du système d'exploitation indiqué.

Il peut retourner "undef" si le nom ne peut pas être représenté dans le système de fichiers indiqué.

$u->dir( [$os] )
Certains systèmes utilisent une forme différente pour les noms de répertoires que pour les fichiers simples. Utilisez cette méthode si vous savez que vous voulez utiliser le nom pour un répertoire.

Le module "URI::file" peut être utilisé pour mapper des noms de fichiers génériques à des noms adaptés au système courant. À ce titre, il peut remplacer avantageusement le module "File::Spec". Par exemple, le code suivant traduit le nom de fichier de style UNIX Foo/Bar.pm en un nom adapté au système local :

$file = URI::file->new("Foo/Bar.pm", "unix")->file;
die "Impossible de mapper le nom de fichier Foo/Bar.pm pour $^O" unless defined $file;
open(FILE, $file) || die "Impossible d'ouvrir '$file': $!";
# faire quelque chose avec FILE

NOTES DE TRANSCODAGE

La plupart des systèmes informatiques actuels ont des systèmes de fichiers organisés hiérarchiquement. Le mappage des noms utilisés dans ces systèmes vers la syntaxe URI générique nous permet de travailler avec des URI de fichiers relatifs qui se comportent comme ils le devraient lorsqu'ils sont résolus à l'aide de l'algorithme générique pour les URI (spécifié dans RFC 3986 https://www.rfc-editor.org/rfc/rfc3986.html). Le mappage d'un nom de fichier vers la syntaxe URI générique implique le mappage du caractère séparateur de chemin vers "/" et l'encodage de tous les caractères réservés qui apparaissent dans les segments de chemin du nom de fichier. Si les segments de chemin constitués des chaînes "." ou ".." ont une signification différente de celle spécifiée pour les URI génériques, alors ils doivent également être encodés.

Si le système de fichiers a des spécifications de périphérique, de volume ou de lecteur comme racine de l'espace de noms, alors il est judicieux de les mapper au champ d'autorité de la syntaxe URI générique. Cela garantit que les URI relatifs ne peuvent pas être résolus "au-dessus" d'eux, c'est-à-dire, généralement comment les noms de fichiers relatifs fonctionnent sur ces systèmes.

Une autre utilisation courante du champ d'autorité est d'encoder l'hôte sur lequel ce nom de fichier est valide. Le nom d'hôte "localhost" est spécial et a généralement la même signification qu'un champ d'autorité manquant ou vide. Cette utilisation est en conflit avec son utilisation comme spécification de périphérique, mais peut souvent être résolue pour les spécifications de périphérique contenant des caractères non valides dans les noms d'hôtes simples.

Le mappage des noms de fichiers vers les URI n'est normalement pas un mappage un-à-un. Il existe généralement de nombreux URI qui correspondent à un nom de fichier donné. Par exemple, une autorité de "localhost" mappe de la même manière qu'un URI avec une autorité manquante ou vide.

Exemple 1 : Le Mac classique (Mac OS 9 et versions antérieures) utilisait ":" comme séparateur de chemin, mais pas de la même manière qu'un URI générique. ":foo" était un nom relatif. "foo:bar" était un nom absolu. De plus, les segments de chemin pouvaient contenir le caractère "/" ainsi que les littéraux "." ou "..". Le mappage ressemble donc à ceci :

Mac classique         URI
----------            -------------------
:foo:bar     <==>     foo/bar
:            <==>     ./
::foo:bar    <==>     ../foo/bar
:::          <==>     ../../
foo:bar      <==>     file:/foo/bar
foo:bar:     <==>     file:/foo/bar/
..           <==>     %2E%2E
<undef>      <==      /
foo/         <==      file:/foo%2F
./foo.txt    <==      file:/.%2Ffoo.txt

Notez que si vous souhaitez une URL relative, vous *devez* faire précéder le chemin de ":". Tout chemin commençant par [^:] est traité comme absolu.

Exemple 2 : Le système de fichiers UNIX est facile à mapper, car il utilise le même séparateur de chemin que les URI, a une racine unique, et les segments "." et ".." ont la même signification. Les URI qui contiennent le caractère "\0" ou "/" dans un segment de chemin ne peuvent pas être transformés en noms de fichiers UNIX valides.

UNIX                  URI
----------            ------------------
foo/bar      <==>     foo/bar
/foo/bar     <==>     file:/foo/bar
/foo/bar     <==      file://localhost/foo/bar
file:         ==>     ./file:
<undef>      <==      file:/fo%00/bar
/            <==>     file:/

VARIABLES DE CONFIGURATION

Les variables de configuration suivantes influencent le comportement de la classe et de ses méthodes :

%URI::file::OS_CLASS
Ce hachage mappe les identifiants d'OS aux classes d'implémentation. Vous pourriez vouloir ajouter ou modifier ceci si vous souhaitez intégrer votre propre classe de gestionnaire de fichiers. Normalement, les clés doivent correspondre aux valeurs $^O utilisées.

S'il n'y a pas de correspondance, l'implémentation "Unix" est utilisée.

$URI::file::DEFAULT_AUTHORITY
Ceci détermine quelle chaîne d'"autorité" inclure dans les URI de fichiers absolus. Par défaut, c'est "". Si vous préférez des URI verbeux, vous pourriez le définir sur "localhost".

Définir cette valeur sur "undef" force un comportement compatible avec URI v1.31 et antérieur. Dans ce mode, les noms d'hôtes dans les chemins UNC et les lettres de lecteur sont mappés au composant d'autorité sous Windows, tandis que nous produisons des URI sans autorité sous Unix.
