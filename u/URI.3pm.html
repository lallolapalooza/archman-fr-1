NOM

URI - Identifiants Uniformes de Ressources (absolus et relatifs)

SYNOPIS

use URI ();
$u1 = URI->new("http://www.example.com");
$u2 = URI->new("foo", "http");
$u3 = $u2->abs($u1);
$u4 = $u3->clone;
$u5 = URI->new("HTTP://WWW.example.com:80")->canonical;
$str = $u->as_string;
$str = "$u";
$scheme = $u->scheme;
$opaque = $u->opaque;
$path   = $u->path;
$frag   = $u->fragment;
$u->scheme("ftp");
$u->host("ftp.example.com");
$u->path("cpan/");

DESCRIPTION

Ce module implémente la classe "URI". Les objets de cette classe représentent des "références d'identifiants uniformes de ressources" telles que spécifiées dans la RFC 2396 (et mises à jour par la RFC 2732).

Un identifiant uniforme de ressource est une chaîne compacte de caractères qui identifie une ressource abstraite ou physique. Un identifiant uniforme de ressource peut être classé comme Localisateur Uniforme de Ressource (URL) ou Nom Uniforme de Ressource (URN). La distinction entre URL et URN n'a pas d'importance pour l'interface de la classe "URI". Une "référence URI" est un URI qui peut avoir des informations supplémentaires sous forme d'identifiant de fragment.

Une référence URI absolue se compose de trois parties : un *schéma*, une *partie spécifique au schéma* et un identifiant de *fragment*. Un sous-ensemble des références URI partage une syntaxe commune pour les espaces de noms hiérarchiques. Pour ceux-ci, la partie spécifique au schéma est décomposée en composants d'*autorité*, de *chemin* et de *requête*. Ces URI peuvent également prendre la forme de références URI relatives, où le composant schéma (et généralement aussi l'autorité) est manquant, mais implicite par le contexte de la référence URI. Les trois formes de syntaxe de référence URI sont résumées comme suit :

<schéma>:<partie-spécifique-au-schéma>#<fragment>
<schéma>://<autorité><chemin>?<requête>#<fragment>
<chemin>?<requête>#<fragment>

Les composants dans lesquels une référence URI peut être divisée dépendent du *schéma*. La classe "URI" fournit des méthodes pour obtenir et définir les composants individuels. Les méthodes disponibles pour un objet "URI" spécifique dépendent du schéma.

CONSTRUCTEURS

Les méthodes suivantes construisent de nouveaux objets "URI" :

$uri = URI->new( $str )
$uri = URI->new( $str, $scheme )
Construit un nouvel objet URI. La représentation textuelle d'un URI est donnée en argument, avec une spécification de schéma optionnelle. Les enveloppes communes des URI comme "" et <>, ainsi que les espaces blancs en début et fin de chaîne, sont automatiquement supprimés de l'argument $str avant d'être traités.

Le constructeur détermine le schéma, le mappe à une sous-classe URI appropriée, construit un nouvel objet de cette classe et le retourne.

Si le schéma n'est pas l'un de ceux que URI reconnaît, vous obtiendrez toujours un objet URI pour lequel vous pouvez utiliser les méthodes génériques. La méthode "$uri->has_recognized_scheme" peut être utilisée pour tester cela.

L'argument $scheme n'est utilisé que lorsque $str est un URI relatif. Il peut s'agir d'une simple chaîne qui désigne le schéma, d'une chaîne contenant une référence URI absolue ou d'un objet "URI" absolu. Si aucun $scheme n'est spécifié pour un URI relatif $str, alors $str est simplement traité comme un URI générique (aucune méthode spécifique au schéma disponible).

L'ensemble des caractères disponibles pour la construction de références URI est restreint (voir URI::Escape). Les caractères hors de cet ensemble sont automatiquement échappés par le constructeur URI.

$uri = URI->new_abs( $str, $base_uri )
Construit un nouvel objet URI absolu. L'argument $str peut désigner un URI relatif ou absolu. S'il est relatif, il est rendu absolu en utilisant $base_uri comme base. Le $base_uri doit être un URI absolu.
$uri = URI::file->new( $filename )
$uri = URI::file->new( $filename, $os )
Construit un nouvel URI de type *file* à partir d'un nom de fichier. Voir URI::file.
$uri = URI::file->new_abs( $filename )
$uri = URI::file->new_abs( $filename, $os )
Construit un nouvel URI de type *file* absolu à partir d'un nom de fichier. Voir URI::file.
$uri = URI::file->cwd
Retourne le répertoire de travail courant sous forme d'URI de type *file*. Voir URI::file.
$uri->clone
Retourne une copie de $uri.

METHODES COMMUNES

Les méthodes décrites dans cette section sont disponibles pour tous les objets "URI".

Les méthodes qui donnent accès aux composants d'un URI retournent toujours l'ancienne valeur du composant. La valeur retournée est "undef" si le composant était absent. Il y a généralement une différence entre un composant qui est vide (représenté par "") et un composant qui est manquant (représenté par "undef"). Si une méthode d'accès reçoit un argument, elle met à jour le composant correspondant en plus de retourner l'ancienne valeur du composant. Passer un argument indéfini supprime le composant (si possible). La description de chaque méthode d'accès indique si le composant est passé sous forme de chaîne échappée (encodée en pourcentage) ou non échappée. Un composant qui peut être divisé en sous-parties est généralement passé échappé, car le déséchappement pourrait en changer la sémantique.

Les méthodes communes disponibles pour tous les URI sont :

$uri->scheme
$uri->scheme( $nouveau_schéma )
Définit et retourne la partie schéma de $uri. Si $uri est relatif, alors $uri->scheme retourne "undef". Si appelée avec un argument, elle met à jour le schéma de $uri, changeant potentiellement la classe de $uri, et retourne l'ancien schéma. La méthode croise si le nouveau nom de schéma est illégal ; un nom de schéma doit commencer par une lettre et doit être composé uniquement de lettres US-ASCII, de chiffres et de quelques marques spéciales : ".", "+", "-". Cette restriction signifie effectivement que le schéma doit être passé non échappé. Passer un argument indéfini à la méthode schéma rend l'URI relatif (si possible).

La casse des lettres n'a pas d'importance pour les noms de schéma. La chaîne retournée par $uri->scheme est toujours en minuscules. Si vous voulez le schéma tel qu'il était écrit dans l'URI dans sa casse d'origine, vous pouvez utiliser la méthode $uri->_scheme à la place.

$uri->has_recognized_scheme
Retourne VRAI si le schéma de l'URI est l'un de ceux que URI reconnaît.

Elle sera également VRAI pour les URL relatives où un schéma reconnu a été fourni au constructeur, même si "$uri->scheme" retourne "undef" pour ceux-ci.

$uri->opaque
$uri->opaque( $nouveau_opaque )
Définit et retourne la partie spécifique au schéma de l'$uri (tout ce qui se trouve entre le schéma et le fragment) sous forme de chaîne échappée.
$uri->path
$uri->path( $nouveau_chemin )
Définit et retourne la même valeur que $uri->opaque, sauf si l'URI prend en charge la syntaxe générique pour les espaces de noms hiérarchiques. Dans ce cas, la méthode générique est remplacée pour définir et retourner la partie de l'URI entre le *nom d'hôte* et le *fragment*.
$uri->fragment
$uri->fragment( $nouveau_frag )
Retourne l'identifiant de fragment d'une référence URI sous forme de chaîne échappée.
$uri->as_string
Retourne un objet URI sous forme de chaîne ASCII simple. Les objets URI sont également convertis automatiquement en chaînes simples par surcharge. Cela signifie que les objets $uri peuvent être utilisés comme des chaînes simples dans la plupart des constructions Perl.
$uri->as_iri
Retourne une représentation Unicode de l'URI.

$uri->canonical
Retourne une version normalisée de l'URI. Les règles de normalisation dépendent du schéma. Elles impliquent généralement la mise en minuscules du schéma et des composants du nom d'hôte Internet, la suppression de la spécification de port explicite si elle correspond au port par défaut, la mise en majuscules de toutes les séquences d'échappement et le déséchappement des octets qui peuvent être mieux représentés par des caractères simples.

Pour des raisons d'efficacité, si le $uri est déjà sous forme normalisée, une référence à celui-ci est retournée au lieu d'une copie.

$uri->eq( $other_uri )
URI::eq( $first_uri, $other_uri )
Teste si deux références d'URI sont égales. Les références d'URI qui se normalisent en la même chaîne sont considérées comme égales. La méthode peut également être utilisée comme une fonction ordinaire qui peut également tester deux arguments de chaîne.

Si vous avez besoin de tester si deux références d'objet "URI" désignent le même objet, utilisez l'opérateur '=='.

$uri->abs( $base_uri )
Retourne une référence d'URI absolue. Si $uri est déjà absolue, une référence à celle-ci est simplement retournée. Si le $uri est relatif, un nouvel URI absolu est construit en combinant le $uri et le $base_uri, puis retourné.
$uri->rel( $base_uri )
Retourne une référence d'URI relative si possible, en la rendant dénote la même ressource par rapport à $base_uri. Sinon, $uri est simplement retourné.
$uri->secure
Retourne une valeur VRAIE si l'URI est considéré comme pointant vers une ressource sur un canal sécurisé, tel qu'un canal crypté SSL ou TLS.

MÉTHODES GÉNÉRIQUES

Les méthodes suivantes sont disponibles pour les schémas qui utilisent la syntaxe commune/générique pour les espaces de noms hiérarchiques. Les descriptions des schémas ci-dessous indiquent lesquels. Les schémas inconnus sont supposés prendre en charge la syntaxe générique, et donc les méthodes suivantes :

$uri->authority
$uri->authority( $new_authority )
Définit et retourne le composant d'autorité échappé de l' $uri.
$uri->path
$uri->path( $new_path )
Définit et retourne le composant de chemin échappé de l' $uri (la partie entre le nom d'hôte et la requête ou le fragment). Le chemin ne peut jamais être indéfini, mais il peut être la chaîne vide.
$uri->path_query
$uri->path_query( $new_path_query )
Définit et retourne les composants de chemin et de requête comme une seule entité. Le chemin et la requête sont séparés par un caractère "?", mais la requête peut elle-même contenir "?".
$uri->path_segments
$uri->path_segments( $segment, ... )
Définit et retourne le chemin. Dans un contexte scalaire, il retourne la même valeur que $uri->path. Dans un contexte de liste, il retourne les segments de chemin non échappés qui composent le chemin. Les segments de chemin qui ont des paramètres sont retournés sous forme de tableau anonyme. Le premier élément est le segment de chemin non échappé proprement dit ; les éléments suivants sont des chaînes de paramètres échappées. Un tel tableau anonyme utilise la surcharge afin qu'il puisse également être traité comme une chaîne, mais cette chaîne n'inclut pas les paramètres.

Notez que les chemins absolus ont la chaîne vide comme premier path_segment, c'est-à-dire que le chemin "/foo/bar" a 3 path_segments ; "", "foo" et "bar".

$uri->query
$uri->query( $new_query )
Définit et retourne le composant de requête échappé de l' $uri.
$uri->query_form
$uri->query_form( $key1 => $val1, $key2 => $val2, ... )
$uri->query_form( $key1 => $val1, $key2 => $val2, ..., $delim )
$uri->query_form( \@key_value_pairs )
$uri->query_form( \@key_value_pairs, $delim )
$uri->query_form( \%hash )
$uri->query_form( \%hash, $delim )
Définit et retourne les composants de requête qui utilisent le format application/x-www-form-urlencoded. Les paires clé/valeur sont séparées par "&", et la clé est séparée de la valeur par un caractère "=".

Le formulaire peut être défini soit en passant des paires clé/valeur séparées, soit via une référence de tableau ou de hachage. Passer un tableau vide ou un hachage vide supprime le composant de requête, tandis que ne passer aucun argument laisse le composant inchangé. L'ordre des clés est indéfini si une référence de hachage est passée. L'ancienne valeur est toujours retournée sous forme de liste de paires clé/valeur séparées. Affecter cette liste à un hachage est déconseillé car les clés retournées peuvent se répéter.

Les valeurs passées lors de la définition du formulaire peuvent être des chaînes simples ou des références à des tableaux de chaînes. Passer un tableau de valeurs a le même effet que de passer la clé de manière répétée avec une seule valeur à la fois. Toutes les instructions suivantes ont le même effet :

$uri->query_form(foo => 1, foo => 2);
$uri->query_form(foo => [1, 2]);
$uri->query_form([ foo => 1, foo => 2 ]);
$uri->query_form([ foo => [1, 2] ]);
$uri->query_form({ foo => [1, 2] });

Le paramètre $delim peut être passé comme ";" pour forcer la délimitation des paires clé/valeur par ";" au lieu de "&" dans la chaîne de requête. Cette pratique est souvent recommandée pour les URL intégrées dans des documents HTML ou XML, car elle évite les problèmes d'échappement du caractère "&". Vous pouvez également définir la variable $URI::DEFAULT_QUERY_FORM_DELIMITER à ";" pour le même effet global.

@keys = $u->query_param
@values = $u->query_param( $key )
$first_value = $u->query_param( $key )
$u->query_param( $key, $value,... )
Si $u->query_param est appelé sans arguments, il retourne toutes les clés de paramètre distinctes de l'URI. Dans un contexte scalaire, il retourne le nombre de clés distinctes.

Lorsqu'un argument $key est donné, la méthode retourne les valeurs de paramètre avec la clé donnée. Dans un contexte scalaire, seule la première valeur de paramètre est retournée.

Si des arguments supplémentaires sont donnés, ils sont utilisés pour mettre à jour les paramètres successifs avec la clé donnée. Si l'une des valeurs fournies est une référence de tableau, le tableau est déréférencé pour obtenir les valeurs réelles.

Veuillez noter que vous pouvez fournir plusieurs valeurs à cette méthode, mais vous ne pouvez pas fournir plusieurs clés.

Faites ceci :

$uri->query_param( widget_id => 1, 5, 9 );

NE FAITES PAS ceci :

$uri->query_param( widget_id => 1, frobnicator_id => 99 );
$u->query_param_append($key, $value,...)
Ajoute de nouveaux paramètres avec la clé donnée sans toucher aux anciens paramètres ayant la même clé. Cela peut être expliqué comme une version plus efficace de : 
$u->query_param($key,
                $u->query_param($key),
                $value,...);

Une différence est que cette expression retournerait les anciennes valeurs de $key, tandis que la méthode query_param_append() ne le fait pas.

@values = $u->query_param_delete($key)
$first_value = $u->query_param_delete($key)
Supprime toutes les paires clé/valeur avec la clé donnée. Les anciennes valeurs sont retournées. Dans un contexte scalaire, seule la première valeur est retournée.

L'utilisation de la méthode query_param_delete() est légèrement plus efficace que l'équivalent :

$u->query_param($key, []);
$hashref = $u->query_form_hash
$u->query_form_hash( \%new_form )
Retourne une référence à un hachage qui représente les paires clé/valeur du formulaire de requête. Si une clé apparaît plusieurs fois, la valeur du hachage devient une référence de tableau.

Notez que les informations de séquence sont perdues. Cela signifie que :

$u->query_form_hash($u->query_form_hash);

n'est pas nécessairement une opération nulle, car elle peut réorganiser les paires clé/valeur. Les valeurs retournées par la méthode query_param() devraient cependant rester les mêmes.

$uri->query_keywords
$uri->query_keywords( $keywords, ... )
$uri->query_keywords( \@keywords )
Définit et retourne les composants de requête qui utilisent le format de mots-clés séparés par "+".

Les mots-clés peuvent être définis soit en passant directement des mots-clés séparés, soit en passant une référence à un tableau de mots-clés. Passer un tableau vide supprime le composant de requête, tandis que ne passer aucun argument laisse le composant inchangé. L'ancienne valeur est toujours retournée sous forme de liste de mots séparés.

MÉTHODES SERVEUR

Pour les schémas où le composant authority désigne un hôte Internet, les méthodes suivantes sont disponibles en plus des méthodes génériques.

$uri->userinfo
$uri->userinfo( $new_userinfo )
Définit et retourne la partie userinfo échappée du composant d'autorité.

Pour certains schémas, il s'agit d'un nom d'utilisateur et d'un mot de passe séparés par un deux-points. Cette pratique n'est pas recommandée. L'intégration de mots de passe en texte clair (comme dans une URI) s'est avérée être un risque de sécurité dans presque tous les cas où elle a été utilisée.

$uri->host
$uri->host( $new_host )
Définit et retourne le nom d'hôte non échappé.

Si la chaîne $new_host se termine par un deux-points et un nombre, alors ce nombre définit également le port.

Pour les adresses IPv6, les crochets autour de l'adresse brute sont supprimés dans la valeur de retour de $uri->host. Lors de la définition de l'attribut host à une adresse IPv6, vous pouvez utiliser une adresse brute ou une adresse entourée de crochets. L'adresse doit être entourée de crochets si vous souhaitez également passer une nouvelle valeur de port.

my $uri = URI->new("http://www.xn--ri-sample/foo/bar.html");
print $u->host; # www.xn--ri-sample-fra0f
$uri->ihost
Retourne l'hôte sous forme Unicode. Tout A-label IDNA (caractères unicode encodés avec le préfixe xn--) sont convertis en U-labels (caractères unicode). 
my $uri = URI->new("http://www.\xC3\xBCri-sample/foo/bar.html");
print $u->ihost; # www.\xC3\xBCri-sample
$uri->port
$uri->port( $new_port )
Définit et renvoie le port. Le port est un entier simple qui doit être supérieur à 0.

Si un port n'est pas spécifié explicitement dans l'URI, le port par défaut du schéma de l'URI est renvoyé. Si vous ne souhaitez pas que le port par défaut soit substitué, vous pouvez utiliser la méthode $uri->_port à la place.

$uri->host_port
$uri->host_port( $new_host_port )
Définit et renvoie l'hôte et le port comme une seule unité. La valeur renvoyée inclut un port, même s'il correspond au port par défaut. La partie hôte et la partie port sont séparées par un deux-points : ":".

Pour les adresses IPv6, les parenthèses sont préservées ; ainsi URI->new("http://[::1]/")->host_port renvoie "[::1]:80". Comparez cela avec $uri->host qui supprimera les parenthèses.

$uri->default_port
Renvoie le port par défaut du schéma d'URI auquel $uri appartient. Pour http, c'est le nombre 80, pour ftp, c'est le nombre 21, etc. Le port par défaut d'un schéma ne peut pas être modifié.

PRISE EN CHARGE SPÉCIFIQUE AU SCHÉMA

Une prise en charge spécifique au schéma est fournie pour les schémas d'URI suivants. Pour les objets "URI" qui n'appartiennent pas à l'un de ceux-ci, vous ne pouvez utiliser que les méthodes communes et génériques.

data:
Le schéma d'URI data est spécifié dans la RFC 2397. Il permet l'inclusion de petits éléments de données comme données « immédiates », comme s'ils avaient été inclus en externe.

Les objets "URI" appartenant au schéma data prennent en charge les méthodes communes et deux nouvelles méthodes pour accéder à leurs composants spécifiques au schéma : $uri->media_type et $uri->data. Voir URI::data pour plus de détails.

file:
Une ancienne spécification du schéma d'URI file se trouve dans la RFC 1738. Une nouvelle spécification basée sur la RFC 2396 n'est pas encore disponible, mais les références d'URI de fichier sont couramment utilisées.

Les objets "URI" appartenant au schéma file prennent en charge les méthodes communes et génériques. De plus, ils fournissent deux méthodes pour mapper les URI de fichier vers des noms de fichiers locaux ; $uri->file et $uri->dir. Voir URI::file pour plus de détails.

ftp:
Une ancienne spécification du schéma d'URI ftp se trouve dans la RFC 1738. Une nouvelle spécification basée sur la RFC 2396 n'est pas encore disponible, mais les références d'URI ftp sont couramment utilisées.

Les objets "URI" appartenant au schéma ftp prennent en charge les méthodes communes, génériques et serveur. De plus, ils fournissent deux méthodes pour accéder aux sous-composants userinfo : $uri->user et $uri->password.

Il prend également en charge l'accès au mode de chiffrement ($uri->encrypt_mode), qui a ses propres valeurs par défaut pour les schémas d'URI ftps et ftpes.

gopher:
Le schéma d'URI gopher est spécifié dans "draft-murali-url-gopher-1996-12-04" et sera espérons-le disponible en tant que spécification basée sur la RFC 2396.

Les objets "URI" appartenant au schéma gopher prennent en charge les méthodes communes, génériques et serveur. De plus, ils prennent en charge certaines méthodes pour accéder aux composants de chemin spécifiques à gopher : $uri->gopher_type, $uri->selector, $uri->search, $uri->string.

http:
Le schéma d'URI http est spécifié dans la RFC 2616. Ce schéma est utilisé pour référencer des ressources hébergées par des serveurs HTTP.

Les objets "URI" appartenant au schéma http prennent en charge les méthodes communes, génériques et serveur.

https:
Le schéma d'URI https est une invention de Netscape couramment implémentée. Ce schéma est utilisé pour référencer des serveurs HTTP via des connexions SSL. Sa syntaxe est la même que celle de http, mais le port par défaut est différent.
geo:
Le schéma d'URI geo est spécifié dans la RFC 5870 http://tools.ietf.org/html/rfc5870. Ce schéma est utilisé pour référencer une localisation physique dans un système de référence de coordonnées à deux ou trois dimensions de manière compacte, simple, lisible par l'homme et indépendante du protocole.

Les objets "URI" appartenant au schéma geo prennent en charge les méthodes communes.

icap:
Le schéma d'URI icap est spécifié dans la RFC 3507 http://tools.ietf.org/html/rfc3507. Ce schéma est utilisé pour référencer des ressources hébergées par des serveurs ICAP.

Les objets "URI" appartenant au schéma icap prennent en charge les méthodes communes, génériques et serveur.

icaps:
Le schéma d'URI icaps est également spécifié dans la RFC 3507 http://tools.ietf.org/html/rfc3507. Ce schéma est utilisé pour référencer des serveurs ICAP via des connexions SSL. Sa syntaxe est la même que celle de icap, y compris le même port par défaut.
irc:
Le schéma d'URI irc est spécifié dans draft-butcher-irc-url-04 https://datatracker.ietf.org/doc/html/draft-butcher-irc-url-04. Ce schéma est utilisé pour référencer des serveurs IRC et leurs ressources.

Les objets "URI" appartenant aux schémas irc ou ircs prennent en charge les méthodes de connexion et les méthodes spécifiques à IRC suivantes : $uri->entity, $uri->flags, $uri->options.

ldap:
Le schéma d'URI ldap est spécifié dans la RFC 2255. LDAP est le Lightweight Directory Access Protocol. Un URI ldap décrit une opération de recherche LDAP à effectuer pour récupérer des informations d'un annuaire LDAP.

Les objets "URI" appartenant au schéma ldap prennent en charge les méthodes communes, génériques et serveur, ainsi que les méthodes spécifiques à ldap : $uri->dn, $uri->attributes, $uri->scope, $uri->filter, $uri->extensions. Voir URI::ldap pour plus de détails.

ldapi:
Similaire au schéma d'URI ldap, mais utilise un socket de domaine UNIX. Les méthodes serveur ne sont pas prises en charge, et le chemin du socket local est disponible sous forme de $uri->un_path. Le schéma ldapi est utilisé par le paquet OpenLDAP. Il n'y a pas de spécification réelle pour celui-ci, mais il est mentionné dans diverses pages de manuel d'OpenLDAP.
ldaps:
Similaire au schéma d'URI ldap, mais utilise une connexion SSL. Ce schéma est déprécié, car la méthode préférée est d'utiliser le mécanisme start_tls.
mailto:
Le schéma d'URI mailto est spécifié dans la RFC 2368. Ce schéma était à l'origine utilisé pour désigner l'adresse e-mail Internet d'un individu ou d'un service. Il a été (dans la RFC 2368) étendu pour permettre la définition d'autres champs d'en-tête de courrier et du corps du message.

Les objets "URI" appartenant au schéma mailto prennent en charge les méthodes communes et les méthodes de requête génériques. De plus, ils prennent en charge les méthodes spécifiques à mailto suivantes : $uri->to, $uri->headers.

Notez que la partie "foo@example.com" d'un mailto n'est pas l'"userinfo" et l'"host" mais plutôt le "path". Cela permet à un URI mailto de contenir plusieurs adresses e-mail séparées par des virgules.

mms:
La spécification de l'URL mms se trouve à http://sdp.ppona.com/. Les objets "URI" appartenant au schéma mms prennent en charge les méthodes communes, génériques et serveur, à l'exception des sous-composants liés à userinfo et à la requête.
news:
Les schémas d'URI news, nntp et snews sont spécifiés dans <draft-gilman-news-url-01> et seront espérons-le disponibles en tant que spécification basée sur la RFC 2396 bientôt. (Mise à jour : en avril 2010, ils sont dans la RFC 5538 https://tools.ietf.org/html/rfc5538.

Les objets "URI" appartenant au schéma news prennent en charge les méthodes communes, génériques et serveur. De plus, ils fournissent des méthodes pour accéder au chemin : $uri->group et $uri->message.

nntp:
Voir le schéma news.
nntps:
Voir le schéma news et la RFC 5538 https://tools.ietf.org/html/rfc5538.
otpauth:
Le schéma d'URI otpauth est spécifié dans https://github.com/google/google-authenticator/wiki/Key-Uri-Format. Ce schéma est utilisé pour encoder les clés secrètes à utiliser dans les schémas TOTP ou HOTP.

Les objets "URI" appartenant au schéma otpauth prennent en charge les méthodes communes.

SCHEMES

mailto:
La spécification du schéma d'URI mailto se trouve dans la RFC 6068. Les objets URI appartenant au schéma mailto ne supportent que les méthodes communes. Ils fournissent également des méthodes supplémentaires pour accéder aux champs d'en-tête des e-mails : $uri->header, et $uri->to. Ces derniers sont également accessibles en tant que méthodes génériques.

Les adresses mailto ne peuvent pas être utilisées dans des URL absolues. Elles ne sont valides que dans des URL relatives.

news:
La spécification du schéma d'URI news se trouve dans la RFC 5538. Les objets URI appartenant au schéma news supportent les méthodes communes, génériques et serveur.
nntp:
La spécification du schéma d'URI nntp se trouve dans la RFC 1738. Les objets URI appartenant au schéma nntp supportent les méthodes communes, génériques et serveur.
pop:
Le schéma d'URI pop est spécifié dans la RFC 2384. Ce schéma est utilisé pour référencer une boîte aux lettres POP3.

"URI" objets appartenant au schéma pop supportent les méthodes communes, génériques et serveur, ainsi que deux méthodes d'autorisation d'e-mail : "user" et "auth".

rlogin:
Une ancienne spécification du schéma d'URI rlogin se trouve dans la RFC 1738. Les objets "URI" appartenant au schéma rlogin supportent les méthodes communes, génériques et serveur.
rtsp:
La spécification de l'URL rtsp se trouve dans la section 3.2 de la RFC 2326. Les objets "URI" appartenant au schéma rtsp supportent les méthodes communes, génériques et serveur, à l'exception des sous-composants relatifs à l'userinfo et à la requête.
rtspu:
Le schéma d'URI rtspu est utilisé pour communiquer avec des serveurs RTSP sur UDP au lieu de TCP. La syntaxe est la même que pour rtsp.
rsync:
Les informations sur rsync sont disponibles sur http://rsync.samba.org/. Les objets "URI" appartenant au schéma rsync supportent les méthodes communes, génériques et serveur. De plus, ils fournissent des méthodes pour accéder aux sous-composants userinfo : $uri->user et $uri->password.
sip:
La spécification des URI sip est décrite dans les sections 19.1 et 25 de la RFC 3261. Les objets "URI" appartenant au schéma sip supportent les méthodes communes, génériques et serveur à l'exception des sous-composants liés au chemin. De plus, ils fournissent deux méthodes pour obtenir et définir les paramètres sip : $uri->params_form et $uri->params.
sips:
Voir le schéma sip. Sa syntaxe est la même que sip, mais le port par défaut est différent.
smb:
Les objets "URI" appartenant au schéma smb supportent les méthodes communes, génériques et serveur. De plus, ils fournissent des méthodes pour accéder aux sous-composants userinfo ($uri->user et $uri->password) ainsi qu'aux méthodes $uri->authdomain et $uri->sharename.
smtp:
Le schéma d'URI smtp est spécifié dans le brouillon draft-earhart-url-smtp-00 https://datatracker.ietf.org/doc/html/draft-earhart-url-smtp-00. Ce schéma est utilisé pour référencer un serveur SMTP.

"URI" objets appartenant au schéma smtp supportent les méthodes communes, génériques et serveur, ainsi que deux méthodes d'autorisation d'e-mail : "user" et "auth".

snews:
Voir le schéma news. Sa syntaxe est la même que news, mais le port par défaut est différent.
telnet:
Une ancienne spécification du schéma d'URI telnet se trouve dans la RFC 1738. Les objets "URI" appartenant au schéma telnet supportent les méthodes communes, génériques et serveur.
tn3270:
Ces URI sont utilisées comme les URI telnet mais pour les connexions aux mainframes IBM. Les objets "URI" appartenant au schéma tn3270 supportent les méthodes communes, génériques et serveur.
ssh:
Les informations sur ssh sont disponibles sur http://www.openssh.com/. Les objets "URI" appartenant au schéma ssh supportent les méthodes communes, génériques et serveur. De plus, ils fournissent des méthodes pour accéder aux sous-composants userinfo : $uri->user et $uri->password.
sftp:
Les objets "URI" appartenant au schéma sftp supportent les méthodes communes, génériques et serveur. De plus, ils fournissent des méthodes pour accéder aux sous-composants userinfo : $uri->user et $uri->password.
urn:
La syntaxe des Uniform Resource Names est spécifiée dans la RFC 2141. Les objets "URI" appartenant au schéma urn fournissent les méthodes communes, ainsi que les méthodes $uri->nid et $uri->nss, qui retournent respectivement l'identifiant de l'espace de noms et la chaîne spécifique à l'espace de noms.

L'identifiant de l'espace de noms fonctionne essentiellement comme l'identifiant de schéma des URI, et divise davantage l'espace de noms URN. Les assignations d'identifiants d'espaces de noms sont maintenues à http://www.iana.org/assignments/urn-namespaces.

La casse des lettres n'est pas significative pour l'identifiant de l'espace de noms. Il est toujours retourné en minuscules par la méthode $uri->nid. La méthode $uri->_nid peut être utilisée si vous le souhaitez dans sa casse d'origine.

urn:isbn:
L'espace de noms "urn:isbn:" contient les International Standard Book Numbers (ISBN) et est décrit dans la RFC 3187. Un objet "URI" appartenant à cet espace de noms possède les méthodes supplémentaires suivantes (si le module Business::ISBN est disponible) : $uri->isbn, $uri->isbn_publisher_code, $uri->isbn_group_code (anciennement isbn_country_code, qui est toujours supporté mais émet un avertissement de dépréciation), $uri->isbn_as_ean.
urn:oid:
L'espace de noms "urn:oid:" contient les Object Identifiers (OID) et est décrit dans la RFC 3061. Un identifiant d'objet se compose de séquences de chiffres séparées par des points. Un objet "URI" appartenant à cet espace de noms possède une méthode supplémentaire appelée $uri->oid qui peut être utilisée pour obtenir/définir la valeur oid. Dans un contexte de liste, les numéros oid sont retournés comme des éléments séparés.
ws:
Le schéma d'URI <ws> est spécifié dans la RFC 6455 http://tools.ietf.org/html/rfc6455. Le Protocole "WebSocket" permet une communication bidirectionnelle entre un client exécutant du code non fiable dans un environnement contrôlé vers un hôte distant qui a opté pour les communications de ce code.
wss:
Le schéma d'URI wss est également spécifié dans la RFC 6455 http://tools.ietf.org/html/rfc6455. Ce schéma est utilisé pour référencer des serveurs "WebSocket" via des connexions SSL.

VARIABLES DE CONFIGURATION

Les variables de configuration suivantes influencent le comportement de la classe et de ses méthodes :

$URI::ABS_ALLOW_RELATIVE_SCHEME
Certains anciens analyseurs permettaient la présence du nom du schéma dans l'URL relative si celui-ci était identique au schéma de l'URL de base. La RFC 2396 indique que cela doit être évité, mais vous pouvez activer cet ancien comportement en définissant la variable $URI::ABS_ALLOW_RELATIVE_SCHEME à une valeur VRAIE. La différence est démontrée par les exemples suivants : 
URI->new("http:foo")->abs("http://host/a/b")
    ==>  "http:foo"
local $URI::ABS_ALLOW_RELATIVE_SCHEME = 1;
URI->new("http:foo")->abs("http://host/a/b")
    ==>  "http:/host/a/foo"
$URI::ABS_REMOTE_LEADING_DOTS
Vous pouvez également faire en sorte que la méthode abs() ignore les segments ".." excessifs dans l'URI relative en définissant $URI::ABS_REMOTE_LEADING_DOTS à une valeur VRAIE. La différence est démontrée par les exemples suivants : 
URI->new("../../../foo")->abs("http://host/a/b")
    ==> "http://host/../../foo"
local $URI::ABS_REMOTE_LEADING_DOTS = 1;
URI->new("../../../foo")->abs("http://host/a/b")
    ==> "http://host/foo"
$URI::DEFAULT_QUERY_FORM_DELIMITER
Cette valeur peut être définie à ";" pour que les paires "clé=valeur" de la requête soient délimitées par ";" au lieu de "&" qui est la valeur par défaut.

VARIABLES D'ENVIRONNEMENT

URI_HAS_RESERVED_SQUARE_BRACKETS
Avant la version 5.11, URI traitait les crochets comme des caractères réservés dans toute la chaîne d'URI. Cependant, ces crochets ne sont réservés que dans la partie autorité/hôte de l'URI et nulle part ailleurs (RFC 3986).

À partir de la version 5.11, URI tient compte de cette distinction. La définition de la variable d'environnement "URI_HAS_RESERVED_SQUARE_BRACKETS" (programmatiquement ou via le shell), restaure le comportement précédent.

#-- restaurer le comportement de la version 5.10 programmatiquement
BEGIN {
  $ENV{URI_HAS_RESERVED_SQUARE_BRACKETS} = 1;
}
use URI ();

Note : cette variable d'environnement n'est utilisée que lors de l'initialisation et doit être définie
avant que le module URI ne soit utilisé/requis. La modifier au moment de l'exécution n'a aucun effet.

Sa valeur peut être vérifiée programmatiquement en accédant à la constante "URI::HAS_RESERVED_SQUARE_BRACKETS".

BUGS

Il y a quelques points qui ne sont pas tout à fait corrects :

  • L'utilisation de variables d'expression régulière comme $1 directement comme arguments des méthodes d'accès à l'URI ne fonctionne pas très bien avec les implémentations Perl actuelles. J'argumenterais que c'est en fait un bug dans Perl. La solution de contournement consiste à les échapper. Exemple : 
    /(...)/ || die;
$u->query("$1");
  • L'échappement (encodage en pourcentage) des caractères dans la plage 128 .. 255 passés au constructeur URI ou lors de la définition de parties d'URI en utilisant les méthodes d'accès dépend de l'état du drapeau interne UTF8 (voir utf8::is_utf8) de la chaîne passée. Si le drapeau UTF8 est défini, la version encodée UTF-8 du caractère est encodée en pourcentage. Si le drapeau UTF8 n'est pas défini, la version Latin-1 (octet) du caractère est encodée en pourcentage. Cela expose essentiellement l'encodage interne des chaînes Perl.

PARSING DES URIS AVEC EXPRESSIONS RÉGULIÈRES

En alternative à ce module, l'expression régulière (officielle) suivante peut être utilisée pour décoder une URI :

my($scheme, $authority, $path, $query, $fragment) =
$uri =~ m|(?:([^:/?#]+):)?(?://([^/?#]*))?([^?#]*)(?:\?([^#]*))?(?:#(.*))?|;

Le module "URI::Split" fournit la fonction uri_split() comme alternative lisible.
