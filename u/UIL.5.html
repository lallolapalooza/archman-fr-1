NOM

UIL — Le format de fichier du langage d'interface utilisateur

SYNTAXE

MODULE nom_module
[ NAMES = CASE_INSENSITIVE | CASE_SENSITIVE ]
[ CHARACTER_SET = jeu_de_caracteres ]
[ OBJECTS = { nom_widget = GADGET | WIDGET; [...] } ]
{ [
[ section_valeur ] |
[ section_procedure ] |
[ section_liste ] |
[ section_objet ] |
[ section_identifiant ]
[ ... ]
] }
END MODULE;

DESCRIPTION

Le langage UIL est utilisé pour décrire l'état initial d'une interface utilisateur pour une application basée sur des widgets. UIL décrit les widgets utilisés dans l'interface, les ressources de ces widgets et les callbacks de ces widgets. Le fichier UIL est compilé en un fichier UID à l'aide de la commande uil ou du compilateur appelable Uil(). Le contenu du fichier UID compilé peut ensuite être accédé par les diverses fonctions de gestion des ressources Motif (MRM) depuis un programme d'application.

Le fichier UID est indépendant de la plateforme sur laquelle le programme Motif sera finalement exécuté. En d'autres termes, le même fichier UID peut être utilisé sur n'importe quel système capable d'exécuter Motif.

Fichier

Un fichier UIL consiste en un seul module complet, décrit dans la syntaxe ci-dessus, ou, si le fichier doit être inclus dans un fichier UIL plus grand, une seule "section" complète, telle que décrite ci-dessous. UIL utilise cinq types de sections différents : valeur, procédure, liste, objet et identificateur.

UIL est un langage libre. Cela signifie que les constructions de haut niveau telles que les déclarations d'objets et de valeurs n'ont pas besoin de commencer dans une colonne particulière et peuvent s'étendre sur plusieurs lignes. Les constructions de bas niveau telles que les mots-clés et les caractères de ponctuation peuvent également commencer dans n'importe quelle colonne ; cependant, à l'exception des littéraux de chaînes et des commentaires, elles ne peuvent pas s'étendre sur plusieurs lignes.

Le compilateur UIL accepte des lignes d'entrée jusqu'à 132 caractères de long.

MODULE nom_module
Le nom par lequel le module UIL est connu dans le fichier UID. Ce nom est stocké dans le fichier UID pour une utilisation ultérieure lors de la récupération des ressources par MRM. Ce nom est toujours stocké en majuscules dans le fichier UID.
NAMES = CASE_INSENSITIVE | CASE_SENSITIVE
Indique si les noms doivent être traités comme sensibles à la casse ou insensibles à la casse. La valeur par défaut est sensible à la casse. La clause de sensibilité à la casse doit être la première clause dans l'en-tête du module, et doit en tout cas précéder toute instruction contenant un nom. Si les noms sont sensibles à la casse dans un module UIL, les mots-clés UIL dans ce module doivent être en minuscules. Chaque nom est stocké dans le fichier UIL dans la même casse qu'il apparaît dans le module UIL. Si les noms sont insensibles à la casse, alors les mots-clés peuvent être en majuscules, minuscules ou casse mixte, et l'équivalent en majuscules de chaque nom est stocké dans le fichier UID.
CHARACTER_SET = jeu_de_caracteres
Spécifie le jeu de caractères par défaut pour les littéraux de chaînes dans le module qui ne définissent pas explicitement leur jeu de caractères. Le jeu de caractères par défaut, en l'absence de cette clause, est le composant codeset de la variable d'environnement LANG, ou la valeur de XmFALLBACK_CHARSET si LANG n'est pas définie ou n'a pas de composant codeset. La valeur de XmFALLBACK_CHARSET est définie par le fournisseur UIL, mais est généralement ISO8859-1 (équivalent à ISO_LATIN1). L'utilisation de cette clause désactive tout traitement de littéraux de chaînes localisés activé par l'option de compilation -s ou l'élément de structure de données Uil_command_type use_setlocale_flag.
OBJECTS = { nom_widget = GADGET | WIDGET; }
Indique si la forme widget ou gadget du contrôle spécifié par nom_widget est utilisée par défaut. Par défaut, la forme widget est utilisée, de sorte que le mot-clé gadget est généralement le seul utilisé. Le contrôle spécifié doit être l'un de ceux qui ont à la fois une version widget et une version gadget : XmCascadeButton, XmLabel, XmPushButton, XmSeparator et XmToggleButton. La forme de plus d'un contrôle peut être spécifiée en les délimitant par des points-virgules. La forme gadget ou widget d'une instance d'un contrôle peut être spécifiée avec les mots-clés GADGET et WIDGET dans une déclaration d'objet particulière.
section_valeur
Fournit un moyen de nommer une expression de valeur ou un littéral. Le nom de la valeur peut ensuite être référencé par des déclarations qui se produisent ailleurs dans le module UIL dans tout contexte où une valeur peut être utilisée. Les valeurs peuvent être référencées de manière anticipée. Les sections de valeurs sont décrites plus en détail plus loin sur la page de référence.
section_procedure
Définit les routines de rappel utilisées par un widget et les routines de création pour les widgets définis par l'utilisateur. Ces définitions sont utilisées pour la vérification des erreurs. Les sections de procédures sont décrites plus en détail plus loin sur la page de référence.
section_liste
Fournit un moyen de regrouper un ensemble d'arguments, de contrôles (enfants), de rappels ou de procédures pour une utilisation ultérieure dans le module UIL. Les listes peuvent contenir d'autres listes, de sorte que vous pouvez établir une hiérarchie pour montrer clairement quels arguments, contrôles, rappels et procédures sont communs à quels widgets. Les sections de listes sont décrites plus en détail plus loin sur la page de référence.
section_objet
Définit les objets qui composent l'interface utilisateur de l'application. Vous pouvez référencer les noms d'objets dans des déclarations qui se produisent ailleurs dans le module UIL dans tout contexte où un nom d'objet peut être utilisé (par exemple, dans une liste de contrôles, comme référence symbolique à un ID de widget, ou comme argument tag_value pour une procédure de rappel). Les objets peuvent être référencés de manière anticipée. Les sections d'objets sont décrites plus en détail plus loin sur la page de référence.
section_identifiant
Définit une liaison d'exécution de données à des noms qui apparaissent dans le module UIL. Les sections d'identificateurs sont décrites plus en détail plus loin sur la page de référence.

Le fichier UIL peut également contenir des commentaires et des directives d'inclusion, qui sont décrits avec les éléments principaux du format de fichier UIL dans les sections suivantes.

Commentaires

Les commentaires peuvent prendre l'une des deux formes suivantes :

•
Le commentaire est introduit par la séquence /* suivie du texte du commentaire et terminé par la séquence */. Cette forme de commentaire peut s'étendre sur plusieurs lignes sources.
•
Le commentaire est introduit par un ! (point d'exclamation), suivi du texte du commentaire et terminé par la fin de la ligne source.

Aucune des deux formes de commentaire ne peut être imbriquée.

Sections de valeurs

VALUE nom_valeur : [ EXPORTED | PRIVATE ] expression_valeur | imported type_valeur ;

Le nom de la valeur peut être référencé par des déclarations qui se produisent plus tard dans le module UIL dans tout contexte où une valeur peut être utilisée. Les valeurs peuvent être référencées de manière anticipée.

Sections de procédures

Une section de procédure se compose du mot-clé PROCEDURE suivi d'une séquence de déclarations de procédures. Sa syntaxe est la suivante :

PROCEDURE
     nom_de_procédure [ ( [ type_valeur ]) ];

Utilisez une déclaration de procédure pour déclarer

•
Une routine qui peut être utilisée comme routine de rappel pour un widget
•
La fonction de création d'un widget défini par l'utilisateur

Vous pouvez référencer un nom de procédure dans des déclarations qui apparaissent plus tard dans le module UIL, dans tout contexte où une procédure peut être utilisée. Les procédures peuvent être référencées à l'avance. Vous ne pouvez pas utiliser un nom déjà utilisé dans un autre contexte comme nom de procédure.

Dans une déclaration de procédure, vous avez la possibilité de spécifier qu'un paramètre sera passé à la routine de rappel correspondante au moment de l'exécution. Ce paramètre est appelé balise de rappel. Vous pouvez spécifier le type de données de la balise de rappel en plaçant le type de données entre parenthèses après le nom de la procédure. Lorsque vous compilez le module, le compilateur UIL vérifie que l'argument que vous spécifiez dans les références à la procédure est de ce type. Notez que le type de données de la balise de rappel doit être l'un des types de données UIL valides. Vous pouvez utiliser un widget comme balise de rappel, à condition que le widget soit défini dans la même hiérarchie de widgets que le rappel, c'est-à-dire qu'ils aient un ancêtre commun qui se trouve dans la même hiérarchie UIL.

La liste suivante résume la manière dont le compilateur UIL vérifie le type et le nombre d'arguments, en fonction de la déclaration de procédure.

Aucun paramètre
Aucune vérification de type ou de nombre d'arguments n'est effectuée. Vous pouvez fournir 0 ou 1 argument dans la référence à la procédure.
( )
Vérifie que le nombre d'arguments est de 0 (zéro).
(ANY)
Vérifie que le nombre d'arguments est de 1. Ne vérifie pas le type d'argument. Utilisez le type ANY pour empêcher la vérification de type sur les balises de procédure.
(type)
Vérifie la présence d'un argument du type spécifié.
(nom_de_classe)
Vérifie la présence d'un argument de widget de la classe de widget spécifiée.

Bien qu'il soit possible d'utiliser n'importe quel type de données UIL pour spécifier le type d'une balise dans une déclaration de procédure, vous devez pouvoir représenter ce type de données dans le langage de programmation que vous utilisez. Certains types de données (tels que les entiers, les booléens et les chaînes) sont des types de données courants reconnus par la plupart des langages de programmation. D'autres types de données UIL (tels que les tables de chaînes) sont plus complexes et peuvent nécessiter que vous mettiez en place une structure de données correspondante appropriée dans l'application afin de passer une balise de ce type à une routine de rappel.

Vous pouvez également utiliser une déclaration de procédure pour spécifier la fonction de création d'un widget défini par l'utilisateur. Dans ce cas, vous ne spécifiez aucun paramètre formel. La procédure est appelée avec les trois arguments standards passés à toutes les fonctions de création de widget. (Voir la documentation de Motif Toolkit pour plus d'informations sur les fonctions de création de widget.)

Sections de listes

Une section de liste se compose du mot-clé LIST suivi d'une séquence de déclarations de listes. Sa syntaxe est la suivante :

LIST
     nom_de_liste: { element_de_liste; [...] }
     [...]

Vous pouvez également utiliser des sections de listes pour regrouper un ensemble d'arguments, de contrôles (enfants), de rappels ou de procédures pour une utilisation ultérieure dans le module UIL. Les listes peuvent contenir d'autres listes, vous permettant ainsi de définir une hiérarchie pour montrer clairement quels arguments, contrôles, rappels et procédures sont communs à quels widgets. Vous ne pouvez pas mélanger les différents types de listes ; une liste d'un type particulier ne peut pas contenir d'éléments d'un type de liste différent ni référencer le nom d'un type de liste différent. Un nom de liste est toujours privé au module UIL dans lequel vous déclarez la liste et ne peut pas être stocké comme ressource nommée dans un fichier UID.

Les types de listes supplémentaires sont décrits dans les sections suivantes.

Structure de la liste d'arguments

Une liste d'arguments définit quels arguments doivent être spécifiés dans le paramètre de la liste d'arguments lorsque la routine de création d'un objet particulier est appelée au moment de l'exécution. Une liste d'arguments spécifie également les valeurs de ces arguments. Les listes d'arguments ont la syntaxe suivante :

LIST
     nom_de_liste: ARGUMENTS {
          nom_argument = expression_valeur;
          [...] }
[...]

Le nom de l'argument doit être soit un nom d'argument intégré, soit un nom d'argument défini par l'utilisateur spécifié avec la fonction ARGUMENT.

Si vous utilisez un nom d'argument intégré comme entrée de liste d'arguments dans une définition d'objet, le compilateur UIL vérifie le nom de l'argument pour s'assurer qu'il est pris en charge par le type d'objet que vous définissez. Si le même nom d'argument apparaît plus d'une fois dans une liste d'arguments donnée, la dernière entrée utilisant ce nom d'argument remplace toutes les entrées précédentes portant ce nom, et le compilateur émet un message.

Certains arguments, tels que XmNitems et XmNitemCount, sont couplés par le compilateur UIL. Lorsque vous spécifiez l'un des arguments, le compilateur définit également l'autre. L'argument couplé n'est pas disponible pour vous.

Motif Toolkit et X Toolkit (intrinsèques) prennent en charge les arguments de contrainte. Un argument de contrainte est un argument qui est passé aux enfants d'un objet, en plus des arguments normalement disponibles. Par exemple, le widget Form accorde un ensemble d'arguments de contrainte à ses enfants. Ces arguments contrôlent la position des enfants au sein du Form.

Contrairement aux arguments utilisés pour définir les attributs d'un widget particulier, les arguments de contrainte sont utilisés exclusivement pour définir des attributs supplémentaires des enfants d'un widget particulier. Ces attributs affectent le comportement des enfants au sein de leur parent. Pour fournir des arguments de contrainte aux enfants, vous incluez les arguments dans la liste d'arguments de l'enfant.

Voir l'Annexe B pour des informations sur les arguments pris en charge par les widgets. Voir l'Annexe C pour des informations sur les types de valeurs valides pour chaque argument intégré.

Structure de la liste de rappels

Utilisez une liste de rappels pour définir quels événements de rappel doivent être traités par un widget particulier au moment de l'exécution. Les listes de rappels ont la syntaxe suivante :

LIST nom_de_liste : CALLBACKS { nom_raison = PROCEDURE nom_procédure [ ( [ expression_valeur ] ) ]; | nom_raison = liste_procédure ; [...] } [...]

Pour les widgets Motif Toolkit, le nom de la raison doit être un nom de raison intégré. Pour un widget défini par l'utilisateur, vous pouvez utiliser un nom de raison que vous avez précédemment spécifié à l'aide de la fonction REASON. Si vous utilisez une raison intégrée dans une définition d'objet, le compilateur UIL s'assure que cette raison est prise en charge par le type d'objet que vous définissez. L'Annexe B montre les raisons prises en charge par chaque objet.

Si le même nom de raison apparaît plus d'une fois dans une liste de rappels, la dernière entrée faisant référence à ce nom remplace toutes les entrées précédentes utilisant la même raison, et le compilateur UIL émet un message de diagnostic.

Si vous spécifiez une valeur nommée pour l'argument de procédure (balise de rappel), le type de données de la valeur doit correspondre au type spécifié pour la balise de rappel dans la déclaration de procédure correspondante. Lors de la spécification d'un nom de widget comme expression de valeur de procédure, vous devez également spécifier le type du widget et un espace avant le nom du widget.

Étant donné que le compilateur UIL produit un fichier UID plutôt qu'un module objet (.o), la liaison du nom UIL à l'adresse du point d'entrée de la procédure n'est pas effectuée par le chargeur, mais est établie au moment de l'exécution avec la fonction MRM MrmRegisterNames. Vous appelez cette fonction avant de récupérer des objets, en lui fournissant les noms UIL et les adresses des procédures de chaque rappel. Le nom que vous enregistrez auprès de MRM dans le programme d'application doit correspondre au nom que vous avez spécifié pour la procédure dans le module UIL.

Chaque procédure de rappel reçoit trois arguments. Les deux premiers arguments ont la même forme pour chaque rappel. La forme du troisième argument varie d'un objet à l'autre.

Le premier argument est l'adresse de la structure de données maintenue par Motif Toolkit pour cette instance d'objet. Cette adresse est appelée l'ID du widget pour cet objet.

Le deuxième argument est l'adresse de la valeur que vous avez spécifiée dans la liste de rappels pour cette procédure. Si vous ne spécifiez pas d'argument, l'adresse est NULL. Notez que, dans le cas où la valeur que vous avez spécifiée est une chaîne ou un XmString, la valeur spécifiée dans la liste de rappels représente déjà une adresse plutôt qu'une valeur réelle. Dans le cas d'une chaîne simple, par exemple, la valeur est l'adresse du premier caractère de cette chaîne. Dans ces cas, UIL n'ajoute pas de niveau d'indirection, et le deuxième argument de la procédure de rappel est simplement la valeur telle que spécifiée dans la liste de rappels.

Le troisième argument est le nom de la raison que vous avez spécifié dans la liste de rappels.

Structure de la liste de contrôles

Une liste de contrôles définit quels objets sont des enfants de, ou contrôlés par

, un objet particulier. Chaque entrée d'une liste de contrôles a la syntaxe suivante :

LIST
     nom_liste: CONTROLS {
          [nom_enfant: ] [MANAGED | UNMANAGED] définition_objet;
          [...] }
     [...]

Si vous spécifiez le mot-clé MANAGED à l'exécution, l'objet est créé et géré ; si vous spécifiez UNMANAGED à l'exécution, l'objet est seulement créé. Les objets sont gérés par défaut.

Vous pouvez utiliser nom_enfant pour spécifier des ressources pour les enfants créés automatiquement d'un contrôle particulier. Les noms des enfants créés automatiquement sont formés en ajoutant Xm_ au nom du widget enfant. Ce nom est spécifié dans la documentation du widget parent.

Contrairement à la liste d'arguments et à la liste de callbacks, une entrée de liste de contrôles identique à une entrée précédente ne remplace pas l'entrée précédente. À l'exécution, chaque entrée de liste de contrôles provoque la création d'un enfant lors de la création du parent. Si la même définition d'objet est utilisée pour plusieurs enfants, plusieurs instances de l'enfant sont créées à l'exécution. Voir l'Annexe B pour une liste des types de widgets qui peuvent être contrôlés par d'autres types de widgets.

Structure de la liste des procédures

Vous pouvez spécifier plusieurs procédures pour une raison de callback dans UIL en définissant une liste de procédures. Tout comme pour les autres types de listes, les listes de procédures peuvent être définies en ligne ou dans une section de liste et référencées par leur nom.

Si vous définissez une raison plus d'une fois (par exemple, lorsque la raison est définie à la fois dans une liste de procédures référencée et dans la liste de callbacks pour l'objet), les définitions précédentes sont écrasées par la définition la plus récente. La syntaxe d'une liste de procédures est la suivante :

LIST
     nom_liste: PROCEDURES {
          nom_procédure [ ( [ expression_valeur ]) ];
          [...] }
     [...]

Lorsque vous spécifiez un nom de widget comme expression de valeur de procédure, vous devez également spécifier le type du widget et un espace avant le nom du widget.

Sections d'objet

Une section d'objet consiste en le mot-clé OBJECT suivi d'une séquence de déclarations d'objets. Elle a la syntaxe suivante :

OBJECT nom_objet:
     [ EXPORTED | PRIVATE | IMPORTED ] type_objet
          [ PROCEDURE fonction_création ]
          [ nom_objet [ WIDGET | GADGET ] | {définitions_listes } ]

Utilisez une déclaration d'objet pour définir les objets qui doivent être stockés dans le fichier UID. Vous pouvez référencer le nom de l'objet dans les déclarations qui apparaissent ailleurs dans le module UIL dans tout contexte où un nom d'objet peut être utilisé (par exemple, dans une liste de contrôles, comme référence symbolique à un identifiant de widget, ou comme argument valeur_tag pour une procédure de callback). Les objets peuvent être référencés en avant ; c'est-à-dire que vous pouvez déclarer un nom d'objet après l'avoir référencé. Toutes les références à un nom d'objet doivent être cohérentes avec le type de l'objet, tel que spécifié dans la déclaration de l'objet. Vous pouvez spécifier un objet comme exporté, importé ou privé.

La définition de l'objet peut contenir une séquence de listes qui définissent les arguments, la hiérarchie et les callbacks pour le widget. Vous pouvez spécifier une seule liste de chaque type pour un objet. Lorsque vous déclarez un widget défini par l'utilisateur, vous devez inclure une référence à la fonction de création du widget pour le widget défini par l'utilisateur.

Note : Plusieurs widgets de la boîte à outils Motif sont en fait composés de deux widgets liés. Par exemple, XmScrolledText et XmScrolledList se composent chacun des widgets enfants XmText et XmList sous un widget XmScrolledWindow. Lorsque ce type de widget est créé, ses ressources sont disponibles pour les deux widgets sous-jacents. Cela peut occasionnellement causer des problèmes, comme lorsque le programmeur souhaite qu'une routine XmNdestroyCallback soit nommée pour agir lors de la destruction du widget. Dans ce cas, la ressource de callback sera disponible pour les deux sous-widgets, et provoquera une erreur lors de la destruction du widget. Pour éviter ces problèmes, le programmeur doit créer séparément les widgets parent et enfant, plutôt que de s'appuyer sur ces widgets liés.

Utilisez le mot-clé GADGET ou WIDGET pour spécifier le type d'objet ou pour remplacer la variante par défaut pour ce type d'objet. Vous pouvez utiliser le nom de la boîte à outils Motif d'un type d'objet qui a une variante gadget (par exemple, XmLabelGadget) comme attribut d'une déclaration d'objet. Le type_objet peut être n'importe quel type d'objet, y compris les gadgets. Vous devez spécifier le mot-clé GADGET ou WIDGET uniquement dans la déclaration d'un objet, pas lorsque vous référencez l'objet. Vous ne pouvez pas spécifier le mot-clé GADGET ou WIDGET pour un objet défini par l'utilisateur ; les objets définis par l'utilisateur sont toujours des widgets.

Sections d'identificateurs

La section d'identificateur vous permet de définir un identificateur, un mécanisme qui permet la liaison à l'exécution de données à des noms qui apparaissent dans un module UIL. La section d'identificateur se compose du mot-clé réservé IDENTIFIER, suivi d'une liste de noms, chaque nom étant suivi d'un point-virgule.

IDENTIFIER nom_identificateur; [...;]

Vous pouvez plus tard utiliser ces noms dans le module UIL comme valeur d'un argument d'un widget ou comme valeur de tag pour une procédure de callback. À l'exécution, vous utilisez les fonctions MRM MrmRegisterNames et MrmRegisterNamesInHierarchy pour lier le nom de l'identificateur aux données (ou, dans le cas des callbacks, à l'adresse des données) associées à l'identificateur.

Chaque module UIL a un seul espace de noms ; par conséquent, vous ne pouvez pas utiliser un nom que vous avez utilisé pour une valeur, un objet ou une procédure comme nom d'identificateur dans le même module.

Le compilateur UIL n'effectue aucun contrôle de type sur l'utilisation des identificateurs dans un module UIL. Contrairement à une valeur UIL, un identificateur n'a pas de type UIL qui lui est associé. Indépendamment du type particulier pour lequel un argument de widget ou un tag de procédure de callback est défini, vous pouvez utiliser un identificateur dans ce contexte à la place d'une valeur du type correspondant.

Pour référencer ces noms d'identificateurs dans un module UIL, vous utilisez le nom de l'identificateur partout où vous souhaitez que sa valeur soit utilisée.

Directives include

La directive include incorpore le contenu d'un fichier spécifié dans un module UIL. Ce mécanisme permet à plusieurs modules UIL de partager des définitions communes. La syntaxe de la directive include est la suivante :

INCLUDE FILE nom_fichier;

Le compilateur UIL remplace la directive include par le contenu du fichier inclus et le traite comme si ce contenu était apparu dans le fichier source UIL actuel.

Vous pouvez imbriquer les fichiers inclus ; c'est-à-dire qu'un fichier inclus peut contenir des directives include. Le compilateur UIL peut traiter jusqu'à 100 références (y compris le fichier contenant le module UIL). Par conséquent, vous pouvez inclure jusqu'à 99 fichiers dans un seul module UIL, y compris les fichiers imbriqués. Chaque fois qu'un fichier est ouvert, il compte comme une référence, donc inclure le même fichier deux fois compte comme deux références.

Le nom_fichier est une chaîne simple contenant une spécification de fichier qui identifie le fichier à inclure. Les règles pour trouver le fichier spécifié sont similaires aux règles pour trouver les fichiers d'en-tête, ou fichiers .h, en utilisant la directive include #include, avec une chaîne entre guillemets en C. UIL utilise l'option -I pour spécifier un répertoire de recherche pour les fichiers inclus.

•
Si vous ne fournissez pas de répertoire, le compilateur UIL recherche le fichier inclus dans le répertoire du fichier source principal.
•
Si le compilateur ne trouve pas le fichier inclus là, le compilateur le recherche dans le même répertoire que le fichier source.
•
Si vous fournissez un répertoire, le compilateur UIL recherche uniquement ce répertoire pour le fichier.

Noms et chaînes

Les noms peuvent être composés de n'importe quels caractères de A à Z, a à z, 0 à 9, $ (signe dollar) et _ (souligné). Les noms ne peuvent pas commencer par un chiffre (0 à 9). La longueur maximale d'un nom est de 31 caractères.

UIL vous donne le choix entre des noms sensibles à la casse ou insensibles à la casse via une clause dans l'en-tête MODULE. Par exemple, si les noms sont sensibles à la casse, les noms "sample" et "Sample" sont distincts l'un de l'autre. Si les noms sont insensibles à la casse, ces noms sont traités comme le même nom et peuvent être utilisés de manière interchangeable. Par défaut, UIL suppose que les noms sont sensibles à la casse.

En mode CASE-INSENSITIVE, le compilateur sort tous les noms du fichier UID en majuscules. En mode CASE-SENSITIVE, les noms apparaissent dans le fichier UIL exactement comme ils apparaissent dans la source.

Littéraux de chaîne

Un littéral de chaîne est une séquence de zéro ou plusieurs caractères 8 bits ou 16 bits, ou une combinaison, délimités par des apostrophes (') ou des guillemets doubles ("). Les littéraux de chaîne peuvent également contenir des caractères multibytes délimités par des guillemets doubles. Les littéraux de chaîne ne peuvent pas dépasser 2000 caractères.

Un littéral de chaîne entre apostrophes peut s'étendre sur plusieurs lignes sources. Pour continuer un littéral de chaîne entre apostrophes, terminez la ligne continuée par une barre oblique inverse (\). Le littéral continue avec le premier caractère de la ligne suivante.

Les littéraux de chaîne entre guillemets doubles ne peuvent pas s'étendre sur plusieurs lignes sources. (Étant donné que les chaînes entre guillemets doubles peuvent contenir des séquences d'échappement et d'autres caractères spéciaux, vous ne pouvez pas utiliser le caractère de barre oblique inverse pour désigner la continuation de la chaîne.) Pour construire une valeur de chaîne qui doit s'étendre sur plusieurs lignes sources, utilisez l'opérateur de concaténation décrit plus loin dans cette section.

La syntaxe d'un littéral de chaîne est l'une des suivantes :

'[chaîne_de_caractères]'
[#jeu_car]"[chaîne_de_caractères]"

Les deux formes de chaîne associent un jeu de caractères à une valeur de chaîne. UIL utilise les règles suivantes pour déterminer le jeu de caractères et le format de stockage des littéraux de chaîne :

•
Une chaîne déclarée comme 'chaîne' est équivalente à #jeu_car_actuel"chaîne", où jeu_car_actuel sera la partie codeset de la valeur de la variable d'environnement LANG si elle est définie ou la valeur de XmFALLBACK_CHARSET si LANG n'est pas définie ou n'a pas de composant codeset. Par défaut, XmFALLBACK_CHARSET est ISO8859-1 (équivalent à ISO_LATIN1), mais les fournisseurs peuvent définir une valeur par défaut différente.
•
Une chaîne déclarée comme "chaîne" est équivalente à #jeu_car"chaîne" si vous avez spécifié jeu_car comme jeu de caractères par défaut pour le module. Si aucun jeu de caractères par défaut n'a été spécifié pour le module, alors si l'option -s est fournie à la commande uil ou si l'indicateur use_setlocale_flag est défini pour le compilateur appelable, Uil(), la chaîne sera interprétée comme une chaîne dans la locale actuelle. Cela signifie que la chaîne est analysée dans la locale de l'utilisateur en appelant setlocale, son jeu de caractères est XmFONTLIST_DEFAULT_TAG, et que si la chaîne est convertie en une chaîne composée, elle est stockée sous forme de segment de texte codé par locale. Sinon, "chaîne" est équivalente à #jeu_car_actuel"chaîne", où jeu_car_actuel est interprété comme décrit pour les chaînes entre apostrophes.
•
Une chaîne de la forme "chaîne" ou #jeu_car"chaîne" est stockée comme une chaîne terminée par un caractère nul.

Si le jeu_car dans une chaîne spécifiée sous la forme ci-dessus n'est pas un jeu de caractères intégré, et n'est pas un jeu de caractères défini par l'utilisateur, le jeu de caractères de la chaîne sera défini sur XmFONTLIST_DEFAULT_TAG, et un message d'information sera émis à l'utilisateur pour noter que cette substitution a été effectuée.

Littéraux de chaînes composites

Une chaîne composite se compose d'une chaîne de caractères 8 bits, 16 bits ou multibit, d'un jeu de caractères nommé et d'une direction d'écriture. Son type de données UIL est compound_string.

La direction d'écriture d'une chaîne composite est implicite par le jeu de caractères spécifié pour la chaîne. Vous pouvez définir explicitement la direction d'écriture d'une chaîne composite en utilisant la fonction COMPOUND_STRING.

Une chaîne composite peut être constituée d'une séquence de chaînes composites concaténées, de chaînes terminées par null, ou d'une combinaison des deux, chacune pouvant avoir une propriété de jeu de caractères et une direction d'écriture différentes. Utilisez l'opérateur de concaténation & (esperluette) pour créer une séquence de chaînes composites.

Chaque chaîne de la séquence est stockée, y compris les informations sur le jeu de caractères et la direction d'écriture.

En général, un littéral de chaîne est stocké dans le fichier UID sous forme de chaîne composite lorsque le littéral est constitué de chaînes concaténées ayant des jeux de caractères ou des directions d'écriture différents, ou lorsque vous utilisez la chaîne pour spécifier une valeur pour un argument qui nécessite une valeur de chaîne composite. Si vous souhaitez garantir qu'un littéral de chaîne soit stocké en tant que chaîne composite, vous devez utiliser la fonction COMPOUND_STRING.

Cependant, cette conversion est coûteuse en termes de consommation de stockage.

Un littéral entier représente la valeur d'un nombre entier. Les littéraux entiers ont la forme d'un signe optionnel suivi d'un ou plusieurs chiffres décimaux. Un littéral entier ne doit pas contenir d'espaces ou de virgules intégrés.

Littéral booléen

Un littéral booléen représente la valeur Vrai (mot-clé réservé TRUE ou On) ou Faux (mot-clé réservé FALSE ou Off). Ces mots-clés sont soumis aux règles de sensibilité à la casse.

La consommation de stockage de données pour les littéraux booléens est la même que celle des littéraux entiers.

Vous pourriez obtenir des résultats inattendus à l'exécution si vous passez une valeur ayant un type de données que le widget ne prend pas en charge pour cet argument.

Une chaîne peut être soit une chaîne composite unique, soit une séquence de chaînes composites. Si les deux chaînes concaténées ont des propriétés différentes (telles que la direction d'écriture ou le jeu de caractères), le résultat de la concaténation est une chaîne composite multisegment.

La chaîne résultant de la concaténation est une chaîne terminée par un caractère nul, sauf si l'une des conditions suivantes est remplie :

•
L'un des opérandes est une chaîne composite
•
Les opérandes ont des propriétés de jeu de caractères différentes
•
Les opérandes ont des directions d'écriture différentes

Alors la chaîne résultante est une chaîne composite. Vous ne pouvez pas utiliser de valeurs importées ou exportées comme opérandes de l'opérateur de concaténation.

Le résultat de chaque opérateur a le même type que ses opérandes. Vous ne pouvez pas mélanger les types dans une expression sans utiliser de routines de conversion.

Vous pouvez utiliser des parenthèses pour outrepasser la précédence normale des opérateurs. Dans une séquence d'opérateurs unaires, les opérations sont effectuées de droite à gauche. Par exemple, - + -A est équivalent à -(+(-A)). Dans une séquence d'opérateurs binaires de même précédence, les opérations sont effectuées de gauche à droite. Par exemple, A*B/C*D est équivalent à ((A*B)/C)*D.

Une déclaration de valeur donne un nom à une valeur. Vous ne pouvez pas redéfinir la valeur de ce nom dans une déclaration de valeur ultérieure. Vous pouvez utiliser une valeur contenant des opérateurs et des fonctions partout où vous pouvez utiliser une valeur dans un module UIL. Vous ne pouvez pas utiliser de valeurs importées comme opérandes dans des expressions.

Plusieurs des opérateurs binaires sont définis pour plusieurs types de données. Par exemple, l'opérateur de multiplication (*) est défini pour les opérandes flottants et entiers.

Pour que le compilateur UIL puisse effectuer ces opérations binaires, les deux opérandes doivent être du même type. Si vous fournissez des opérandes de types de données différents, le compilateur UIL convertira automatiquement l'un des opérandes au type de l'autre selon les règles de conversion suivantes :

•
Si les opérandes sont un entier et un booléen, le booléen est converti en entier.
•
Si les opérandes sont un entier et un nombre à virgule flottante, l'entier est converti en nombre à virgule flottante.
•
Si les opérandes sont un nombre à virgule flottante et un booléen, le booléen est converti en nombre à virgule flottante.

Vous pouvez également convertir explicitement le type de données d'une valeur en utilisant l'une des fonctions de conversion INTEGER, FLOAT ou SINGLE_FLOAT.

COLOR(expression_chaîne[,FOREGROUND|BACKGROUND])
La fonction COLOR supporte la définition des couleurs. En utilisant la fonction COLOR, vous pouvez désigner une valeur pour spécifier une couleur et ensuite utiliser cette valeur pour les arguments nécessitant une valeur de couleur. L'expression en chaîne nomme la couleur que vous souhaitez définir ; les mots-clés optionnels FOREGROUND et BACKGROUND identifient comment la couleur doit être affichée sur un appareil monochrome lorsque la couleur est utilisée dans la définition d'une table de couleurs.
Le compilateur UIL n'a pas de noms de couleurs intégrés. Les couleurs sont un attribut dépendant du serveur d'un objet. Les couleurs sont définies sur chaque serveur et peuvent avoir des valeurs différentes de rouge-vert-bleu (RVB) sur chaque serveur. La chaîne que vous spécifiez comme argument de couleur doit être reconnue par le serveur sur lequel votre application s'exécute.
Dans un fichier UID, UIL représente une couleur sous forme de chaîne de caractères. MRM appelle les routines de traduction X qui convertissent une chaîne de couleur en valeur de pixel spécifique à l'appareil. Si vous exécutez sur un serveur monochrome, toutes les couleurs se traduisent par du noir ou du blanc. Si vous êtes sur un serveur couleur, les noms de couleurs se traduisent par leurs couleurs appropriées si les conditions suivantes sont remplies :
•
La couleur est définie.
•
La table de couleurs n'est pas encore pleine.
Si la table de couleurs est pleine, même les couleurs valides se traduisent par du noir ou du blanc (premier plan ou arrière-plan).
Les interfaces ne spécifient généralement pas les couleurs des widgets, afin que la sélection des couleurs puisse être contrôlée par l'utilisateur via le fichier .Xdefaults.
Pour écrire une application qui s'exécute sur des appareils monochromes et couleur, vous devez spécifier quelles couleurs dans une table de couleurs (définie avec la fonction COLOR_TABLE) correspondent à l'arrière-plan et quelles couleurs correspondent au premier plan. UIL vous permet d'utiliser la fonction COLOR pour désigner cette correspondance dans la définition de la couleur. L'exemple suivant montre comment utiliser la fonction COLOR pour mapper la couleur rouge à la couleur d'arrière-plan sur un appareil monochrome :
VALEUR c: COULEUR ( 'rouge',ARRIEREPLAN );
La correspondance n'entre en jeu que lorsque MRM reçoit une couleur et que l'application doit être affichée sur un appareil monochrome. Dans ce cas, chaque couleur est considérée comme appartenant à l'une des trois catégories suivantes :
•
La couleur est mappée à la couleur d'arrière-plan sur l'appareil monochrome.
•
La couleur est mappée à la couleur de premier plan sur l'appareil monochrome.
•
La correspondance monochrome n'est pas définie pour cette couleur.
Si la couleur est mappée à la couleur de premier plan ou d'arrière-plan, MRM substitue la couleur de premier plan ou d'arrière-plan, respectivement. Si vous ne spécifiez pas la correspondance monochrome pour une couleur, MRM passe la chaîne de couleur au toolkit Motif pour la mapper à la couleur de premier plan ou d'arrière-plan.

#replace
This directive causes the current translation table to be discarded and replaced with the new translations specified in the XmNtranslations resource. Duplicate translations are ignored. For example, if a translation for <b><code>Btn1Down</code></b> is already defined in the current translations for a PushButton, the translation defined by new_translations overrides the current definition.
#augment
This directive causes the new translations to be added to the current translation table. If a translation for an event already exists, the new translation is ignored unless the event is specified more than once. In this case, the last translation specified takes precedence. Duplicate translations are ignored. For example, if a translation for <b><code>Btn1Down</code></b> is already defined in the current translations for a PushButton, the translation defined by new_translations overrides the current definition. If the #augment directive is specified, the current definition takes precedence. The #replace directive replaces all current translations with those specified in the XmNtranslations resource.

Renditions and Render Tables

In addition to the string direction, each compound string carries a great deal of information about how its text is to be rendered. Each compound string contains a "tag," identifying the "rendition" to be used to draw that string. The rendition contains such information as the font, the size, the color, whether the text is to be underlined or crossed out, and the position and style of any tab stops. Many renditions are combined into a "render table," which is specified to any widget with the XmNrenderTable resource, and in the widget's controls list.

UIL implements render tables, renditions, tab lists, and tab stops as a special class of objects, in a form similar to the widget class. These objects are not themselves widgets or gadgets, but the format used by UIL to specify widget resources provides a convenient way to specify the qualities and dependencies of these objects.

For example, a render table, included in some widget's controls list, must also have a controls list in its specification, containing the names of its member renditions. Each rendition, in its specification, will contain an arguments list specifying such qualities as the font, the color, and whether the text is to be underlined. Any of the renditions may also control a tablist, which will itself control one or more tab stops.

Please refer to the Motif Programmer's Guide for a complete description of renditions and render tables, and for an example of how to use them in UIL.
