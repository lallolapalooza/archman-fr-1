F_GETSIG(2const) F_GETSIG(2const)

NOM

F_GETOWN, F_SETOWN, F_GETOWN_EX, F_SETOWN_EX, F_GETSIG, F_SETSIG - gestion des signaux

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <fcntl.h>
int fcntl(int fd, F_GETOWN);
int fcntl(int fd, F_SETOWN, int arg);
#define _GNU_SOURCE
#include <fcntl.h>
int fcntl(int fd, F_GETOWN_EX, struct f_owner_ex *arg);
int fcntl(int fd, F_SETOWN_EX, const struct f_owner_ex *arg);
int fcntl(int fd, F_GETSIG);
int fcntl(int fd, F_SETSIG, int arg);

DESCRIPTION

F_GETOWN, F_SETOWN, F_GETOWN_EX, F_SETOWN_EX, F_GETSIG et F_SETSIG sont utilisés pour gérer les signaux de disponibilité des E/S :

F_GETOWN
Retourne (comme résultat de la fonction) l'identifiant de processus ou l'identifiant de groupe de processus qui reçoit actuellement les signaux SIGIO et SIGURG pour des événements sur le descripteur de fichier fd. Les identifiants de processus sont retournés sous forme de valeurs positives ; les identifiants de groupes de processus sont retournés sous forme de valeurs négatives (mais voir la section BUGS ci-dessous).
F_SETOWN
Définit l'identifiant de processus ou l'identifiant de groupe de processus qui recevra les signaux SIGIO et SIGURG pour des événements sur le descripteur de fichier fd. L'identifiant du processus ou groupe de processus cible est spécifié dans arg. Un identifiant de processus est spécifié comme une valeur positive ; un identifiant de groupe de processus est spécifié comme une valeur négative. Le plus souvent, le processus appelant se spécifie lui-même comme propriétaire (c'est-à-dire que arg est spécifié comme getpid(2)).
En plus de définir le propriétaire du descripteur de fichier, il faut aussi activer la génération de signaux sur le descripteur de fichier. Ceci est fait en utilisant l'opération F_SETFL(2const) pour définir le drapeau d'état de fichier O_ASYNC sur le descripteur de fichier. Par la suite, un signal SIGIO est envoyé chaque fois que des entrées ou sorties deviennent possibles sur le descripteur de fichier. L'opération F_SETSIG de fcntl() peut être utilisée pour obtenir la livraison d'un signal autre que SIGIO.
L'envoi d'un signal au processus (groupe) propriétaire spécifié par F_SETOWN est soumis aux mêmes vérifications de permissions que celles décrites pour kill(2), où le processus émetteur est celui qui utilise F_SETOWN (mais voir la section BUGS ci-dessous). Si cette vérification de permission échoue, le signal est silencieusement ignoré. Note : L'opération F_SETOWN enregistre les identifiants de l'appelant au moment de l'appel fcntl(), et ce sont ces identifiants sauvegardés qui sont utilisés pour les vérifications de permissions.
Si le descripteur de fichier fd fait référence à un socket, F_SETOWN sélectionne également le destinataire des signaux SIGURG qui sont délivrés lorsque des données hors bande arrivent sur ce socket. (SIGURG est envoyé dans toute situation où select(2) signalerait le socket comme ayant une « condition exceptionnelle ».)
Ce qui suit était vrai dans Linux 2.6.x jusqu'à et y compris Linux 2.6.11 :
Si une valeur non nulle est donnée à F_SETSIG dans un processus multithread exécuté avec une bibliothèque de threads qui supporte les groupes de threads (par exemple, NPTL), alors une valeur positive donnée à F_SETOWN a une signification différente : au lieu d'être un identifiant de processus identifiant un processus entier, c'est un identifiant de thread identifiant un thread spécifique au sein d'un processus. Par conséquent, il peut être nécessaire de passer à F_SETOWN le résultat de gettid(2) au lieu de getpid(2) pour obtenir des résultats sensés lorsque F_SETSIG est utilisé. (Dans les implémentations de threading Linux actuelles, l'identifiant du thread principal est le même que son identifiant de processus. Cela signifie qu'un programme monothread peut également utiliser gettid(2) ou getpid(2) dans ce scénario.) Notez cependant que les déclarations de ce paragraphe ne s'appliquent pas au signal SIGURG généré pour les données hors bande sur un socket : ce signal est toujours envoyé soit à un processus, soit à un groupe de processus, en fonction de la valeur donnée à F_SETOWN.
Le comportement ci-dessus a été accidentellement supprimé dans Linux 2.6.12 et ne sera pas restauré. À partir de Linux 2.6.32, utilisez F_SETOWN_EX pour cibler les signaux SIGIO et SIGURG sur un thread particulier.
F_GETOWN_EX
Retourne les paramètres actuels du propriétaire du descripteur de fichier tels que définis par une opération F_SETOWN_EX précédente. L'information est retournée dans la structure pointée par arg, qui a la forme suivante :

struct f_owner_ex {
    int   type;
    pid_t pid;
};

Le champ type aura l'une des valeurs F_OWNER_TID, F_OWNER_PID, ou F_OWNER_PGRP. Le champ pid est un entier positif représentant un identifiant de thread, un identifiant de processus ou un identifiant de groupe de processus. Voir F_SETOWN_EX pour plus de détails.
F_SETOWN_EX
Cette opération accomplit une tâche similaire à F_SETOWN. Elle permet à l'appelant de diriger les signaux de disponibilité des E/S vers un thread, un processus ou un groupe de processus spécifique. L'appelant spécifie la cible des signaux via arg, qui est un pointeur vers une structure f_owner_ex. Le champ type aura l'une des valeurs suivantes, qui définissent comment pid est interprété :
F_OWNER_TID
Envoie le signal au thread dont l'identifiant de thread (la valeur retournée par un appel à clone(2) ou gettid(2)) est spécifié dans pid.
F_OWNER_PID
Envoie le signal au processus dont l'identifiant est spécifié dans pid.
F_OWNER_PGRP
Envoie le signal au groupe de processus dont l'identifiant est spécifié dans pid. (Notez qu'à la différence de F_SETOWN, un identifiant de groupe de processus est spécifié ici comme une valeur positive.)
F_GETSIG
Retourne (comme résultat de la fonction) le signal envoyé lorsque des entrées ou sorties deviennent possibles. Une valeur de zéro signifie que SIGIO est envoyé. Toute autre valeur (y compris SIGIO) est le signal envoyé à la place, et dans ce cas des informations supplémentaires sont disponibles pour le gestionnaire de signal s'il est installé avec SA_SIGINFO. arg est ignoré.
F_SETSIG
Définit le signal envoyé lorsque des entrées ou sorties deviennent possibles à la valeur donnée dans arg. Une valeur de zéro signifie d'envoyer le signal par défaut SIGIO. Toute autre valeur (y compris SIGIO) est le signal à envoyer à la place, et dans ce cas des informations supplémentaires sont disponibles pour le gestionnaire de signal s'il est installé avec SA_SIGINFO.
En utilisant F_SETSIG avec une valeur non nulle, et en définissant SA_SIGINFO pour le gestionnaire de signal (voir sigaction(2)), des informations supplémentaires sur les événements d'E/S sont transmises au gestionnaire dans une structure siginfo_t. Si le champ si_code indique que la source est SI_SIGIO, le champ si_fd donne le descripteur de fichier associé à l'événement. Sinon, il n'y a aucune indication quels descripteurs de fichiers sont en attente, et vous devriez utiliser les mécanismes habituels (select(2), poll(2), read(2) avec O_NONBLOCK défini, etc.) pour déterminer quels descripteurs de fichiers sont disponibles pour les E/S.
Notez que le descripteur de fichier fourni dans si_fd est celui qui a été spécifié lors de l'opération F_SETSIG. Cela peut conduire à un cas limite inhabituel. Si le descripteur de fichier est dupliqué (dup(2) ou similaire), et que le descripteur de fichier original est fermé, alors les événements d'E/S continueront d'être générés, mais le champ si_fd conterra le numéro du descripteur de fichier maintenant fermé.

En sélectionnant un signal temps réel (valeur >= SIGRTMIN), plusieurs événements d'E/S peuvent être mis en file d'attente en utilisant les mêmes numéros de signal. (La mise en file d'attente dépend de la mémoire disponible.) Des informations supplémentaires sont disponibles si SA_SIGINFO est défini pour le gestionnaire de signal, comme ci-dessus.
Notez que Linux impose une limite au nombre de signaux temps réel qui peuvent être mis en file d'attente pour un processus (voir getrlimit(2) et signal(7)) et si cette limite est atteinte, le noyau revient à la livraison de SIGIO, et ce signal est livré à l'ensemble du processus plutôt qu'à un thread spécifique.

En utilisant ces mécanismes, un programme peut implémenter une E/S entièrement asynchrone sans utiliser select(2) ou poll(2) la plupart du temps.

L'utilisation de O_ASYNC est spécifique à BSD et Linux. La seule utilisation de F_GETOWN et F_SETOWN spécifiée dans POSIX.1 est en conjonction avec l'utilisation du signal SIGURG sur les sockets. (POSIX ne spécifie pas le SIGIO signal.) F_GETOWN_EX, F_SETOWN_EX, F_GETSIG, et F_SETSIG sont spécifiques à Linux. POSIX a l'E/S asynchrone et la structure aio_sigevent pour réaliser des choses similaires ; celles-ci sont également disponibles dans Linux dans le cadre de la GNU C Library (glibc).

ANOMALIES

F_GETOWN

Une limitation des conventions d'appel système Linux sur certaines architectures (notamment i386) signifie que si un ID de groupe de processus (négatif) à renvoyer par F_GETOWN tombe dans la plage -1 à -4095, alors la valeur de retour est mal interprétée par glibc comme une erreur dans l'appel système ; c'est-à-dire que la valeur de retour de fcntl() sera -1, et errno contiendra l'ID de groupe de processus (positif). L'opération F_GETOWN_EX spécifique à Linux évite ce problème. Depuis glibc 2.11, glibc rend le problème du noyau F_GETOWN invisible en implémentant F_GETOWN en utilisant F_GETOWN_EX.

F_SETOWN

Dans Linux 2.4 et antérieur, il existe une anomalie qui peut survenir lorsqu'un processus non privilégié utilise F_SETOWN pour spécifier le propriétaire d'un descripteur de fichier socket comme un processus (groupe) autre que l'appelant. Dans ce cas, fcntl() peut renvoyer -1 avec errno défini à EPERM, même lorsque le processus (groupe) propriétaire est un auquel l'appelant a la permission d'envoyer des signaux. Malgré ce retour d'erreur, le propriétaire du descripteur de fichier est défini, et des signaux seront envoyés au propriétaire.
