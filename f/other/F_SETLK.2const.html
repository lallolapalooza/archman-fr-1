DESCRIPTION

Verrouillage de enregistrement protecteur

Linux implémente les verrous d'enregistrement UNIX traditionnels (« associés aux processus »), standardisés par POSIX. Pour une alternative spécifique à Linux avec de meilleures sémantiques, voir la discussion sur les verrous de description de fichier ouvert ci-dessous.

F_SETLK, F_SETLKW et F_GETLK sont utilisés pour acquérir, libérer et tester l'existence de verrous d'enregistrement (également connus sous le nom de verrous de plage d'octets, de segment de fichier ou de région de fichier). Le troisième argument, lock, est un pointeur vers une structure qui a au moins les champs suivants (dans un ordre non spécifié).


struct flock {
    ...
    short l_type;    /* Type de verrou : F_RDLCK,
                        F_WRLCK, F_UNLCK */
    short l_whence;  /* Comment interpréter l_start :
                        SEEK_SET, SEEK_CUR, SEEK_END */
    off_t l_start;   /* Décalage de départ pour le verrou */
    off_t l_len;     /* Nombre d'octets à verrouiller */
    pid_t l_pid;     /* PID du processus bloquant notre verrou
                        (défini par F_GETLK et F_OFD_GETLK) */
    ...
};

Les champs l_whence, l_start et l_len de cette structure spécifient la plage d'octets que nous souhaitons verrouiller. Des octets au-delà de la fin du fichier peuvent être verrouillés, mais pas des octets avant le début du fichier.

l_start est le décalage de départ pour le verrou, et est interprété par rapport à : soit le début du fichier (si l_whence est SEEK_SET) ; soit le décalage de fichier actuel (si l_whence est SEEK_CUR) ; soit la fin du fichier (si l_whence est SEEK_END). Dans les deux derniers cas, l_start peut être un nombre négatif à condition que le décalage ne se trouve pas avant le début du fichier.

l_len spécifie le nombre d'octets à verrouiller. Si l_len est positif, alors la plage à verrouiller couvre les octets l_start jusqu'à et y compris l_start+l_len-1. Spécifier 0 pour l_len a la signification spéciale : verrouiller tous les octets à partir de l'emplacement spécifié par l_whence et l_start jusqu'à la fin du fichier, quelle que soit la croissance du fichier.

POSIX.1-2001 autorise (mais n'exige pas) une implémentation à supporter une valeur négative de l_len ; si l_len est négatif, l'intervalle décrit par lock couvre les octets l_start+l_len jusqu'à et y compris l_start-1. Ceci est supporté depuis Linux 2.4.21 et Linux 2.5.49.

Le champ l_type peut être utilisé pour placer un verrou en lecture (F_RDLCK) ou en écriture (F_WRLCK) sur un fichier. N'importe quel nombre de processus peut détenir un verrou en lecture (verrou partagé) sur une région de fichier, mais un seul processus peut détenir un verrou en écriture (verrou exclusif). Un verrou exclusif exclut tous les autres verrous, qu'ils soient partagés ou exclusifs. Un seul processus peut détenir un seul type de verrou sur une région de fichier ; si un nouveau verrou est appliqué sur une région déjà verrouillée, le verrou existant est converti au nouveau type de verrou. (Ces conversions peuvent impliquer de diviser, de réduire ou de fusionner avec un verrou existant si la plage d'octets spécifiée par le nouveau verrou ne coïncide pas précisément avec la plage du verrou existant.)

F_SETLK
Acquérir un verrou (lorsque l_type est F_RDLCK ou F_WRLCK) ou libérer un verrou (lorsque l_type est F_UNLCK) sur les octets spécifiés par les champs l_whence, l_start et l_len de lock. Si un verrou conflictuel est détenu par un autre processus, cet appel renvoie -1 et définit errno à EACCES ou EAGAIN. (L'erreur retournée dans ce cas diffère entre les implémentations, donc POSIX exige qu'une application portable vérifie les deux erreurs.)
F_SETLKW
Comme pour F_SETLK, mais si un verrou conflictuel est détenu sur le fichier, attendez que ce verrou soit libéré. Si un signal est capturé pendant l'attente, l'appel est interrompu et (après le retour du gestionnaire de signal) revient immédiatement (avec une valeur de retour -1 et errno défini à EINTR ; voir signal(7)).
F_GETLK
À l'entrée de cet appel, lock décrit un verrou que nous souhaiterions placer sur le fichier. Si le verrou pouvait être placé, fcntl() ne le place pas réellement, mais renvoie F_UNLCK dans le champ l_type de lock et laisse les autres champs de la structure inchangés.
Si un ou plusieurs verrous incompatibles empêchent le placement de ce verrou, alors fcntl() renvoie des détails sur l'un de ces verrous dans les champs l_type, l_whence, l_start et l_len de lock. Si le verrou conflictuel est un verrou d'enregistrement traditionnel (associé au processus), alors le champ l_pid est défini sur le PID du processus détenant ce verrou. Si le verrou conflictuel est un verrou de description de fichier ouvert, alors l_pid est défini à -1. Notez que les informations retournées peuvent déjà être obsolètes au moment où l'appelant les examine.

Pour placer un verrou en lecture, fd doit être ouvert en lecture. Pour placer un verrou en écriture, fd doit être ouvert en écriture. Pour placer les deux types de verrou, ouvrez un fichier en lecture-écriture.

Lors du placement de verrous avec F_SETLKW, le noyau détecte les interblocages, par lesquels deux processus ou plus ont leurs requêtes de verrou bloquées mutuellement par les verrous détenus par les autres processus. Par exemple, supposons que le processus A détient un verrou en écriture sur l'octet 100 d'un fichier, et que le processus B détient un verrou en écriture sur l'octet 200. Si chaque processus tente ensuite de verrouiller l'octet déjà verrouillé par l'autre processus en utilisant F_SETLKW, alors, sans détection d'interblocage, les deux processus resteraient bloqués indéfiniment. Lorsque le noyau détecte de tels interblocages, il provoque l'échec immédiat de l'une des requêtes de verrou bloquantes avec l'erreur EDEADLK ; une application qui rencontre une telle erreur doit libérer certains de ses verrous pour permettre à d'autres applications de progresser avant de tenter de regagner les verrous dont elle a besoin. Les interblocages circulaires impliquant plus de deux processus sont également détectés. Notez, cependant, qu'il existe des limitations à l'algorithme de détection d'interblocage du noyau ; voir BUGS.

En plus d'être supprimés par un F_UNLCK explicite, les verrous d'enregistrement sont automatiquement libérés lorsque le processus se termine.

Les verrous d'enregistrement ne sont pas hérités par un enfant créé via fork(2), mais sont préservés lors d'un execve(2).

En raison de la mise en mémoire tampon effectuée par la bibliothèque stdio(3), l'utilisation du verrouillage d'enregistrement avec les routines de ce paquet doit être évitée ; utilisez plutôt read(2) et write(2).

Les verrous d'enregistrement décrits ci-dessus sont associés au processus (contrairement aux verrous de description de fichier ouvert décrits ci-dessous). Cela a certaines conséquences fâcheuses :

•
Si un processus ferme un descripteur de fichier quelconque se référant à un fichier, alors tous les verrous du processus sur ce fichier sont libérés, quel que soit le(s) descripteur(s) de fichier sur lequel les verrous ont été obtenus. C'est mauvais : cela signifie qu'un processus peut perdre ses verrous sur un fichier tel que /etc/passwd ou /etc/mtab lorsqu'une fonction de bibliothèque décide, pour une raison quelconque, d'ouvrir, de lire et de fermer le même fichier.
•
Les threads d'un processus partagent les verrous. En d'autres termes, un programme multithread ne peut pas utiliser le verrouillage d'enregistrement pour s'assurer que les threads n'accèdent pas simultanément à la même région d'un fichier.

Les verrous de description de fichier ouvert résolvent ces deux problèmes.

Verrous de description de fichier ouvert (non-POSIX)

Les verrous de descriptions de fichiers ouverts sont des verrous de plage d'octets consultatifs dont le fonctionnement est, dans la plupart des cas, identique aux verrous d'enregistrement traditionnels décrits ci-dessus. Ce type de verrou est spécifique à Linux et est disponible depuis Linux 3.15. (Il existe une proposition auprès de l'Austin Group pour inclure ce type de verrou dans la prochaine révision de POSIX.1.) Pour une explication des descriptions de fichiers ouverts, voir open(2).

La principale différence entre les deux types de verrous est que, alors que les verrous d'enregistrement traditionnels sont associés à un processus, les verrous de descriptions de fichiers ouverts sont associés à la description de fichier ouvert sur laquelle ils sont acquis, tout comme les verrous acquis avec flock(2). Par conséquent (et contrairement aux verrous d'enregistrement consultatifs traditionnels), les verrous de descriptions de fichiers ouverts sont hérités lors de fork(2) (et clone(2) avec CLONE_FILES), et ne sont automatiquement libérés que lors de la dernière fermeture de la description de fichier ouvert, au lieu d'être libérés lors de toute fermeture du fichier.

Les combinaisons de verrous conflictuelles (c'est-à-dire un verrou de lecture et un verrou d'écriture, ou deux verrous d'écriture) où l'un des verrous est un verrou de description de fichier ouvert et l'autre est un verrou d'enregistrement traditionnel entrent en conflit même lorsqu'ils sont acquis par le même processus sur le même descripteur de fichier.

Les verrous de descriptions de fichiers ouverts placés via la même description de fichier ouvert (c'est-à-dire via le même descripteur de fichier, ou via un duplicata du descripteur de fichier créé par fork(2), dup(2), F_DUPFD(2const), et ainsi de suite) sont toujours compatibles : si un nouveau verrou est placé sur une région déjà verrouillée, le verrou existant est converti en nouveau type de verrou. (Ces conversions peuvent entraîner la division, la réduction ou la coalescence avec un verrou existant, comme expliqué ci-dessus.)

En revanche, les verrous de descriptions de fichiers ouverts peuvent entrer en conflit les uns avec les autres lorsqu'ils sont acquis via différentes descriptions de fichiers ouverts. Ainsi, les threads d'un programme multithread peuvent utiliser des verrous de descriptions de fichiers ouverts pour synchroniser l'accès à une région de fichier en demandant à chaque thread d'effectuer son propre appel à open(2) sur le fichier et d'appliquer les verrous via le descripteur de fichier résultant.

Comme pour les verrous consultatifs traditionnels, le troisième argument de fcntl(), lock, est un pointeur vers une structure flock. Par opposition aux verrous d'enregistrement traditionnels, le champ l_pid de cette structure doit être mis à zéro lors de l'utilisation des opérations décrites ci-dessous.

Les opérations de travail avec les verrous de descriptions de fichiers ouverts sont analogues à celles utilisées avec les verrous traditionnels :

F_OFD_SETLK
Acquérir un verrou de description de fichier ouvert (lorsque l_type est F_RDLCK ou F_WRLCK) ou libérer un verrou de description de fichier ouvert (lorsque l_type est F_UNLCK) sur les octets spécifiés par les champs l_whence, l_start et l_len de lock. Si un verrou conflictuel est détenu par un autre processus, cet appel retourne -1 et définit errno à EAGAIN.
F_OFD_SETLKW
Comme pour F_OFD_SETLK, mais si un verrou conflictuel est détenu sur le fichier, attend que ce verrou soit libéré. Si un signal est intercepté pendant l'attente, l'appel est interrompu et (après le retour du gestionnaire de signaux) retourne immédiatement (avec une valeur de retour de -1 et errno défini à EINTR ; voir signal(7)).
F_OFD_GETLK
À l'entrée de cet appel, lock décrit un verrou de description de fichier ouvert que nous aimerions placer sur le fichier. Si le verrou pouvait être placé, fcntl() ne le place pas réellement, mais retourne F_UNLCK dans le champ l_type de lock et laisse les autres champs de la structure inchangés. Si un ou plusieurs verrous incompatibles empêcheraient le placement de ce verrou, des détails sur l'un de ces verrous sont renvoyés via lock, comme décrit ci-dessus pour F_GETLK.

Dans l'implémentation actuelle, aucune détection de interblocage n'est effectuée pour les verrous de descriptions de fichiers ouverts. (Cela contraste avec les verrous d'enregistrement associés aux processus, pour lesquels le noyau effectue une détection d'interblocage.)

Verrouillage obligatoire

Attention : l'implémentation Linux du verrouillage obligatoire n'est pas fiable. Voir BUGS ci-dessous. En raison de ces bugs, et du fait que la fonctionnalité est supposée être peu utilisée, depuis Linux 4.5, le verrouillage obligatoire est devenu une fonctionnalité optionnelle, régie par une option de configuration (CONFIG_MANDATORY_FILE_LOCKING). Cette fonctionnalité n'est plus du tout prise en charge dans Linux 5.15 et les versions ultérieures.

Par défaut, les verrous d'enregistrement traditionnels (associés aux processus) et les verrous de descriptions de fichiers ouverts sont consultatifs. Les verrous consultatifs ne sont pas appliqués et ne sont utiles qu'entre processus coopératifs.

Les deux types de verrous peuvent également être obligatoires. Les verrous obligatoires sont appliqués à tous les processus. Si un processus tente d'effectuer un accès incompatible (par exemple, une lecture ou une écriture) sur une région de fichier qui a un verrou obligatoire incompatible, le résultat dépend de la présence ou non du drapeau O_NONBLOCK pour sa description de fichier ouvert. Si le drapeau O_NONBLOCK n'est pas activé, l'appel système est bloqué jusqu'à ce que le verrou soit supprimé ou converti dans un mode compatible avec l'accès. Si le drapeau O_NONBLOCK est activé, l'appel système échoue avec l'erreur EAGAIN.

Pour utiliser les verrous obligatoires, le verrouillage obligatoire doit être activé à la fois sur le système de fichiers qui contient le fichier à verrouiller et sur le fichier lui-même. Le verrouillage obligatoire est activé sur un système de fichiers en utilisant l'option « -o mand » avec mount(8), ou le drapeau MS_MANDLOCK pour mount(2). Le verrouillage obligatoire est activé sur un fichier en désactivant la permission d'exécution pour le groupe sur le fichier et en activant le bit de permission set-group-ID (voir chmod(1) et chmod(2)).

Le verrouillage obligatoire n'est pas spécifié par POSIX. Certains autres systèmes prennent également en charge le verrouillage obligatoire, bien que les détails sur la façon de l'activer varient d'un système à l'autre.

Perte de verrous

Lorsqu'un verrou consultatif est obtenu sur un système de fichiers en réseau tel que NFS, il est possible que le verrou soit perdu. Cela peut se produire en raison d'une action administrative sur le serveur, ou en raison d'une partition réseau (c'est-à-dire une perte de connectivité réseau avec le serveur) qui dure suffisamment longtemps pour que le serveur suppose que le client ne fonctionne plus.

Lorsque le système de fichiers détermine qu'un verrou a été perdu, les futures requêtes de lecture ou d'écriture peuvent échouer avec l'erreur EIO. Cette erreur persistera jusqu'à ce que le verrou soit supprimé ou que le descripteur de fichier soit fermé. Depuis Linux 3.12, cela se produit au moins pour NFSv4 (y compris toutes les versions mineures).

Certaines versions d'UNIX envoient un signal (SIGLOST) dans cette circonstance. Linux ne définit pas ce signal et ne fournit aucune notification asynchrone de verrous perdus.

En cas d'erreur, -1 est retourné et errno est défini pour indiquer l'erreur.

Voir fcntl(2).

lock est en dehors de votre espace d'adressage accessible.
EINTR
op est F_SETLKW ou F_OFD_SETLKW et l'opération a été interrompue par un signal ; voir signal(7).
EINTR
op est F_GETLK, F_SETLK, F_OFD_GETLK, ou F_OFD_SETLK, et l'opération a été interrompue par un signal avant que le verrou ne soit vérifié ou acquis. Très probablement lors du verrouillage d'un fichier distant (par exemple, verrouillage via NFS), mais peut parfois se produire localement.

op est F_OFD_SETLK, F_OFD_SETLKW, ou F_OFD_GETLK, et l_pid n'a pas été spécifié comme zéro.
ENOLCK
Trop de verrous de segments ouverts, table des verrous pleine, ou un protocole de verrouillage distant a échoué (par exemple, verrouillage via NFS).

NOTES

Verrouillage de fichier

L'appel système fcntl() original de Linux n'était pas conçu pour gérer les grands décalages de fichiers (dans la structure flock). Par conséquent, un appel système fcntl64() a été ajouté dans Linux 2.4. Le nouvel appel système utilise une structure différente pour le verrouillage de fichier, flock64, et les opérations correspondantes, F_GETLK64, F_SETLK64 et F_SETLKW64. Cependant, ces détails peuvent être ignorés par les applications utilisant glibc, dont la fonction wrapper fcntl() utilise de manière transparente l'appel système plus récent lorsqu'il est disponible.

Verrouillage d'enregistrement et

NFS

Avant Linux 3.12, si un client NFSv4 perdait le contact avec le serveur pendant un certain temps (défini comme plus de 90 secondes sans communication), il pouvait perdre et récupérer un verrou sans jamais en être conscient. (La période après laquelle le contact est supposé perdu est connue comme le leasetime NFSv4. Sur un serveur NFS Linux, cela peut être déterminé en regardant /proc/fs/nfsd/nfsv4leasetime, qui exprime la période en secondes. La valeur par défaut pour ce fichier est 90.) Ce scénario présente potentiellement un risque de corruption de données, car un autre processus pourrait acquérir un verrou pendant la période intermédiaire et effectuer des E/S sur le

fichier.

Depuis Linux 3.12, si un client NFSv4 perd le contact avec le serveur, toute E/S sur le fichier par un processus qui « pense » détenir un verrou échouera jusqu'à ce que ce processus ferme et rouvre le fichier. Un paramètre du noyau, nfs.recover_lost_locks, peut être défini à 1 pour obtenir le comportement pré-3.12, où le client tentera de récupérer les

verrous perdus lorsque le contact est rétabli avec le serv
eur. En raison du risque de corruption de données qui l'acc
ompagne, ce paramètre a une valeur par défaut de 0 (désactivé).

d'interblocage
