fcntl_locking(2) Manuel des appels système fcntl_locking(2)

NOM

F_GETLK, F_SETLK, F_SETLKW, F_OFD_GETLK, F_OFD_SETLK, F_OFD_SETLKW - verrouillage

BIBLIOTHÈQUE

Bibliothèque C standard (libc,-lc)

SYNOPSIS

#include <fcntl.h>
int fcntl(int fd, F_GETLK, struct flock *lock);
int fcntl(int fd, F_SETLK, const struct flock *lock);
int fcntl(int fd, F_SETLKW, const struct flock *lock);
int fcntl(int fd, F_OFD_GETLK, struct flock *lock);
int fcntl(int fd, F_OFD_SETLK, const struct flock *lock);
int fcntl(int fd, F_OFD_SETLKW, const struct flock *lock);

DESCRIPTION

Verrouillage de plage conseillé

Linux implémente les verrous de plage UNIX traditionnels (« associés au processus »), tels que standardisés par POSIX. Pour une alternative propre à Linux avec une meilleure sémantique, voir la discussion sur les verrous de description de fichier ouvert ci-dessous.

F_SETLK, F_SETLKW, et F_GETLK sont utilisés pour acquérir, libérer et tester l'existence de verrous de plage (également connus sous le nom de verrous par plage d'octets, par segment de fichier ou par région de fichier). Le troisième argument, lock, est un pointeur vers une structure qui contient au moins les champs suivants (dans un ordre non spécifié).


struct flock {
    ...
    short l_type;    /* Type de verrou : F_RDLCK,
                        F_WRLCK, F_UNLCK */
    short l_whence;  /* Comment interpréter l_start :
                        SEEK_SET, SEEK_CUR, SEEK_END */
    off_t l_start;   /* Décalage de départ du verrou */
    off_t l_len;     /* Nombre d'octets à verrouiller */
    pid_t l_pid;     /* PID du processus bloquant notre verrou
                        (défini par F_GETLK et F_OFD_GETLK) */
    ...
};

Les champs l_whence, l_start, et l_len de cette structure spécifient la plage d'octets que nous souhaitons verrouiller. Les octets au-delà de la fin du fichier peuvent être verrouillés, mais pas les octets avant le début du fichier.

l_start est le décalage de départ du verrou, et est interprété relativement à : le début du fichier (si l_whence vaut SEEK_SET) ; le décalage courant du fichier (si l_whence vaut SEEK_CUR) ; ou la fin du fichier (si l_whence vaut SEEK_END). Dans les deux derniers cas, l_start peut être un nombre négatif à condition que le décalage ne se situe pas avant le début du fichier.

l_len spécifie le nombre d'octets à verrouiller. Si l_len est positif, alors la plage à verrouiller couvre les octets l_start jusqu'à et y compris l_start+l_len-1. Spécifier 0 pour l_len a le sens spécial suivant : verrouiller tous les octets à partir de l'emplacement spécifié par l_whence et l_start jusqu'à la fin du fichier, quelle que soit la taille à laquelle le fichier croît.

POSIX.1-2001 permet (mais n'exige pas) qu'une implémentation supporte une valeur négative pour l_len ; si l_len est négatif, l'intervalle décrit par lock couvre les octets l_start+l_len jusqu'à et y compris l_start-1. Cela est pris en charge depuis Linux 2.4.21 et Linux 2.5.49.

Le champ l_type peut être utilisé pour poser un verrou de lecture (F_RDLCK) ou d'écriture (F_WRLCK) sur un fichier. Un nombre quelconque de processus peut détenir un verrou de lecture (verrou partagé) sur une région de fichier, mais un seul processus peut détenir un verrou d'écriture (verrou exclusif). Un verrou exclusif exclut tous les autres verrous, tant partagés qu'exclusifs. Un processus unique ne peut détenir qu'un seul type de verrou sur une région de fichier ; si un nouveau verrou est appliqué à une région déjà verrouillée, alors le verrou existant est converti au nouveau type de verrou. (De telles conversions peuvent impliquer de diviser, réduire ou fusionner avec un verrou existant si la plage d'octets spécifiée par le nouveau verrou ne coïncide pas exactement avec la plage du verrou existant.)

F_SETLK
Acquérir un verrou (quand l_type vaut F_RDLCK ou F_WRLCK) ou libérer un verrou (quand l_type vaut F_UNLCK) sur les octets spécifiés par les champs l_whence, l_start, et l_len de lock. Si un verrou conflictuel est détenu par un autre processus, cet appel renvoie -1 et définit errno à EACCES ou EAGAIN. (L'erreur renvoyée dans ce cas diffère selon les implémentations, POSIX exige donc qu'une application portable vérifie les deux erreurs.)
F_SETLKW
Comme F_SETLK, mais si un verrou conflictuel est détenu sur le fichier, alors attendre que ce verrou soit libéré. Si un signal est capturé pendant l'attente, alors l'appel est interrompu et (après le retour du gestionnaire de signal) renvoie immédiatement (avec une valeur de retour -1 et errno défini à EINTR; voir signal(7)).
F_GETLK
En entrée de cet appel, lock décrit un verrou que nous aimerions poser sur le fichier. Si le verrou pouvait être posé, fcntl() ne le pose pas réellement, mais renvoie F_UNLCK dans le champ l_type de lock et laisse les autres champs de la structure inchangés.
Si un ou plusieurs verrous incompatibles empêcheraient la pose de ce verrou, alors fcntl() renvoie les détails de l'un de ces verrous dans les champs l_type, l_whence, l_start, et l_len de lock. Si le verrou conflictuel est un verrou de plage traditionnel (associé au processus), alors le champ l_pid est défini au PID du processus détenant ce verrou. Si le verrou conflictuel est un verrou de description de fichier ouvert, alors l_pid est défini à -1. Notez que les informations renvoyées peuvent déjà être obsolètes au moment où l'appelant les inspecte.

Afin de poser un verrou de lecture, fd doit être ouvert en lecture. Afin de poser un verrou d'écriture, fd doit être ouvert en écriture. Pour poser les deux types de verrous, ouvrir un fichier en lecture-écriture.

Lors de la pose de verrous avec F_SETLKW, le noyau détecte les impasses, où deux processus ou plus ont leurs requêtes de verrouillage mutuellement bloquées par des verrous détenus par les autres processus. Par exemple, supposons que le processus A détient un verrou d'écriture sur l'octet 100 d'un fichier, et que le processus B détient un verrou d'écriture sur l'octet 200. Si chaque processus tente ensuite de verrouiller l'octet déjà verrouillé par l'autre processus en utilisant F_SETLKW, alors, sans détection d'impasses, les deux processus resteraient bloqués indéfiniment. Quand le noyau détecte de telles impasses, il provoque l'échec immédiat de l'une des requêtes de verrouillage bloquantes avec l'erreur EDEADLK; une application qui rencontre une telle erreur devrait libérer certains de ses verrous pour permettre à d'autres applications de continuer avant de tenter de récupérer les verrous dont elle a besoin. Les impasses circulaires impliquant plus de deux processus sont également détectées. Notez cependant qu'il existe des limitations à l'algorithme de détection d'impasses du noyau ; voir BUGS.

En plus d'être supprimés par un F_UNLCKexplicite, les verrous de plage sont automatiquement libérés quand le processus se termine.

Les verrous de plage ne sont pas hérités par un enfant créé via fork(2), mais sont préservés à travers un execve(2).

En raison de la mise en tampon effectuée par la bibliothèque stdio(3) , l'utilisation du verrouillage de plage avec les routines de ce paquet devrait être évitée ; utiliser read(2) et write(2) à la place.

Les verrous de plage décrits ci-dessus sont associés au processus (contrairement aux verrous de description de fichier ouvert décrits ci-dessous). Cela a quelques conséquences fâcheuses :

•
Si un processus ferme n'importe quel descripteur de fichier référençant un fichier, alors tous les verrous de ce processus sur ce fichier sont libérés, indépendamment du(des) descripteur(s) de fichier sur lequel(s) les verrous ont été obtenus. C'est mauvais : cela signifie qu'un processus peut perdre ses verrous sur un fichier tel que /etc/passwd ou /etc/mtab quand, pour une raison quelconque, une fonction de bibliothèque décide d'ouvrir, lire et fermer le même fichier.
•
Les threads d'un processus partagent les verrous. En d'autres termes, un programme multithread ne peut pas utiliser le verrouillage de plage pour s'assurer que les threads n'accèdent pas simultanément à la même région d'un fichier.

Les verrous de description de fichier ouvert résolvent ces deux problèmes.

Verrous de description de fichier ouvert (non-POSIX)

Les verrous de description de fichier ouverte (open file description locks) sont des verrous de plage d'octets consultatifs dont le fonctionnement est, dans la plupart des cas, identique aux verrous de fichier traditionnels décrits ci-dessus. Ce type de verrou est spécifique à Linux et est disponible depuis Linux 3.15. (Une proposition est en cours auprès de l'Austin Group pour inclure ce type de verrou dans la prochaine révision de POSIX.1.) Pour une explication des descriptions de fichier ouvertes, voir open(2).

La différence principale entre les deux types de verrous est que, si les verrous de fichier traditionnels sont associés à un processus, les verrous de description de fichier ouverte sont associés à la description de fichier ouverte sur laquelle ils sont acquis, un peu comme les verrous acquis avec flock(2). Par conséquent (et contrairement aux verrous de fichier consultatifs traditionnels), les verrous de description de fichier ouverte sont hérités à travers fork(2) (et clone(2) avec CLONE_FILES), et ne sont automatiquement libérés qu'à la dernière fermeture de la description de fichier ouverte, au lieu d'être libérés à chaque fermeture du fichier.

Les combinaisons de verrous conflictuels (c'est-à-dire un verrou de lecture et un verrou d'écriture, ou deux verrous d'écriture) où l'un des verrous est un verrou de description de fichier ouverte et l'autre est un verrou de fichier traditionnel entrent en conflit même s'ils sont acquis par le même processus sur le même descripteur de fichier.

Les verrous de description de fichier ouverte placés via la même description de fichier ouverte (c'est-à-dire via le même descripteur de fichier, ou via un duplicata du descripteur de fichier créé par fork(2), dup(2), F_DUPFD(2const), etc.) sont toujours compatibles : si un nouveau verrou est placé sur une région déjà verrouillée, le verrou existant est converti au nouveau type de verrou. (Ces conversions peuvent entraîner un découpage, un rétrécissement ou une fusion avec un verrou existant, comme discuté ci-dessus.)

D'un autre côté, les verrous de description de fichier ouverte peuvent entrer en conflit les uns avec les autres lorsqu'ils sont acquis via des descriptions de fichier ouvertes différentes. Ainsi, les threads d'un programme multi-thread peuvent utiliser les verrous de description de fichier ouverte pour synchroniser l'accès à une région de fichier en faisant effectuer à chaque thread son propre open(2) sur le fichier et en appliquant des verrous via le descripteur de fichier résultant.

Comme pour les verrous consultatifs traditionnels, le troisième argument de fcntl(), lock, est un pointeur vers une structure flock . Contrairement aux verrous de fichier traditionnels, le champ l_pid de cette structure doit être défini à zéro lors de l'utilisation des opérations décrites ci-dessous.

Les opérations pour travailler avec les verrous de description de fichier ouverte sont analogues à celles utilisées avec les verrous traditionnels :

F_OFD_SETLK
Acquérir un verrou de description de fichier ouverte (lorsque l_type vaut F_RDLCK ou F_WRLCK) ou libérer un verrou de description de fichier ouverte (lorsque l_type vaut F_UNLCK) sur les octets spécifiés par les champs l_whence, l_startet l_len de lock. Si un verrou conflictuel est détenu par un autre processus, cet appel retourne -1 et définit errno à EAGAIN.
F_OFD_SETLKW
Comme F_OFD_SETLK, mais si un verrou conflictuel est détenu sur le fichier, alors attendre que ce verrou soit libéré. Si un signal est capturé pendant l'attente, l'appel est interrompu et (après le retour du gestionnaire de signal) retourne immédiatement (avec une valeur de retour -1 et errno défini à EINTR; voir signal(7)).
F_OFD_GETLK
En entrée de cet appel, lock décrit un verrou de description de fichier ouverte que nous aimerions placer sur le fichier. Si le verrou pouvait être placé, fcntl() ne le place pas réellement, mais retourne F_UNLCK dans le champ l_type de lock et laisse les autres champs de la structure inchangés. Si un ou plusieurs verrous incompatibles empêcheraient le placement de ce verrou, les détails sur l'un de ces verrous sont retournés via lock, comme décrit ci-dessus pour F_GETLK.

Dans l'implémentation actuelle, aucune détection d'interblocage n'est effectuée pour les verrous de description de fichier ouverte. (Cela contraste avec les verrous de fichier associés à un processus, pour lesquels le noyau effectue une détection d'interblocage.)

Verrouillage obligatoire

Avertissement: l'implémentation Linux du verrouillage obligatoire n'est pas fiable. Voir BUGS ci-dessous. En raison de ces bogues, et du fait que cette fonctionnalité est peu utilisée, depuis Linux 4.5, le verrouillage obligatoire est devenu une fonctionnalité optionnelle, régie par une option de configuration (CONFIG_MANDATORY_FILE_LOCKING). Cette fonctionnalité n'est plus du tout prise en charge dans Linux 5.15 et les versions ultérieures.

Par défaut, les verrous de fichier traditionnels (associés à un processus) et les verrous de description de fichier ouverte sont consultatifs. Les verrous consultatifs ne sont pas appliqués de force et ne sont utiles qu'entre processus coopératifs.

Les deux types de verrous peuvent également être obligatoires. Les verrous obligatoires sont appliqués à tous les processus. Si un processus tente d'effectuer un accès incompatible (par exemple read(2) ou write(2)) sur une région de fichier ayant un verrou obligatoire incompatible, le résultat dépend de l'activation ou non du drapeau O_NONBLOCK pour sa description de fichier ouverte. Si le drapeau O_NONBLOCK n'est pas activé, l'appel système est bloqué jusqu'à ce que le verrou soit retiré ou converti en un mode compatible avec l'accès. Si le drapeau O_NONBLOCK est activé, l'appel système échoue avec l'erreur EAGAIN.

Pour utiliser les verrous obligatoires, le verrouillage obligatoire doit être activé à la fois sur le système de fichiers contenant le fichier à verrouiller et sur le fichier lui-même. Le verrouillage obligatoire est activé sur un système de fichiers à l'aide de l'option "-o mand" de mount(8), ou du drapeau MS_MANDLOCK pour mount(2). Le verrouillage obligatoire est activé sur un fichier en désactivant la permission d'exécution du groupe sur le fichier et en activant le bit de permission set-group-ID (voir chmod(1) et chmod(2)).

Le verrouillage obligatoire n'est pas spécifié par POSIX. Certains autres systèmes prennent également en charge le verrouillage obligatoire, bien que les détails pour l'activer varient d'un système à l'autre.

Verrous perdus

Lorsqu'un verrou consultatif est obtenu sur un système de fichiers en réseau tel que NFS, il est possible que le verrou soit perdu. Cela peut se produire en raison d'une action administrative sur le serveur, ou en raison d'une partition réseau (c'est-à-dire une perte de connectivité réseau avec le serveur) qui dure suffisamment longtemps pour que le serveur suppose que le client ne fonctionne plus.

Lorsque le système de fichiers détermine qu'un verrou a été perdu, les requêtes read(2) ou write(2) ultérieures peuvent échouer avec l'erreur EIO. Cette erreur persiste jusqu'à ce que le verrou soit retiré ou que le descripteur de fichier soit fermé. Depuis Linux 3.12, cela se produit au moins pour NFSv4 (y compris toutes les versions mineures).

Certaines versions d'UNIX envoient un signal (SIGLOST) dans cette circonstance. Linux ne définit pas ce signal et ne fournit aucune notification asynchrone des verrous perdus.

VALEUR RETOURNÉE

Zéro.

En cas d'erreur, -1 est retourné et errno est défini pour indiquer l'erreur.

ERREURS

Voir fcntl(2).

EBADF
op vaut F_SETLK ou F_SETLKW et le mode d'ouverture du descripteur de fichier ne correspond pas au type de verrou demandé.
EDEADLK
Il a été détecté que l'opération F_SETLKW spécifiée causerait un interblocage.
EFAULT
lock est en dehors de votre espace d'adressage accessible.
EINTR
op vaut F_SETLKW ou F_OFD_SETLKW et l'opération a été interrompue par un signal ; voir signal(7).
EINTR
op vaut F_GETLK, F_SETLK, F_OFD_GETLKou F_OFD_SETLK, et l'opération a été interrompue par un signal avant que le verrou n'ait été vérifié ou acquis. Le plus probable lors du verrouillage d'un fichier distant (par exemple, verrouillage via NFS), mais cela peut parfois se produire localement.
EINVAL
op vaut F_OFD_SETLK, F_OFD_SETLKWou F_OFD_GETLK, et l_pid n'a pas été spécifié comme zéro.
ENOLCK
Trop de verrous de segment ouverts, table de verrous pleine, ou un protocole de verrouillage distant a échoué (par exemple, verrouillage via NFS).

NOTES

Verrouillage de fichier

L'appel système fcntl() original de Linux n'a pas été conçu pour gérer les grands décalages de fichier (dans la structure flock ). Par conséquent, un appel système fcntl64() a été ajouté dans Linux 2.4. Le nouvel appel système utilise une structure différente pour le verrouillage de fichier, flock64, et des opérations correspondantes, F_GETLK64, F_SETLK64et F_SETLKW64. Cependant, ces détails peuvent être ignorés par les applications utilisant glibc, dont la fonction d'enveloppe fcntl() utilise de manière transparente l'appel système plus récent lorsqu'il est disponible.

Verrous de fichier

Depuis Linux 2.0, il n'y a pas d'interaction entre les types de verrous posées par flock(2) et fcntl().

Plusieurs systèmes ont plus de champs dans struct flock tels que, par exemple, l_sysid (pour identifier la machine où le verrou est détenu). Clairement, l_pid seul ne sera pas très utile si le processus détenant le verrou peut se trouver sur une autre machine ; sur Linux, bien que présent sur certaines architectures (telles que MIPS32), ce champ n'est pas utilisé.

L'appel système fcntl() original de Linux n'a pas été conçu pour gérer de grands décalages de fichier (dans la structure flock ). Par conséquent, un appel système fcntl64() a été ajouté dans Linux 2.4. Le nouvel appel système utilise une structure différente pour le verrouillage de fichier, flock64, et des opérations correspondantes, F_GETLK64, F_SETLK64, et F_SETLKW64. Cependant, ces détails peuvent être ignorés par les applications utilisant glibc, dont la fonction enveloppe fcntl() utilise de manière transparente l'appel système plus récent lorsqu'il est disponible.

Verrouillage d'enregistrement et NFS

Avant Linux 3.12, si un client NFSv4 perdait le contact avec le serveur pendant un certain temps (défini comme plus de 90 secondes sans communication), il pouvait perdre et récupérer un verrou sans jamais en être conscient. (La période de temps après laquelle le contact est supposé perdu est connue comme le leasetime NFSv4. Sur un serveur NFS Linux, cela peut être déterminé en regardant /proc/fs/nfsd/nfsv4leasetime, qui exprime la période en secondes. La valeur par défaut pour ce fichier est 90.) Ce scénario présente potentiellement un risque de corruption de données, car un autre processus pourrait acquérir un verrou dans l'intervalle et effectuer des E/S sur le fichier.

Depuis Linux 3.12, si un client NFSv4 perd le contact avec le serveur, toute E/S sur le fichier par un processus qui « pense » détenir un verrou échouera jusqu'à ce que ce processus ferme et rouvre le fichier. Un paramètre du noyau, nfs.recover_lost_locks, peut être défini à 1 pour obtenir le comportement pré-3.12, où le client tentera de récupérer les verrous perdus lorsque le contact est rétabli avec le serveur. En raison du risque associé de corruption de données, ce paramètre vaut par défaut 0 (désactivé).

BOGUES

Détection d'interblocage

L'algorithme de détection d'interblocage employé par le noyau lorsqu'il traite les requêtes F_SETLKW peut produire à la fois de faux négatifs (échecs à détecter des interblocages, laissant un ensemble de processus en interblocage bloqués indéfiniment) et de faux positifs (erreurs EDEADLK alors qu'il n'y a pas d'interblocage). Par exemple, le noyau limite la profondeur de verrouillage de sa recherche de dépendances à 10 étapes, ce qui signifie que les chaînes d'interblocage circulaires dépassant cette taille ne seront pas détectées. De plus, le noyau peut indiquer à tort un interblocage lorsque deux processus ou plus créés à l'aide de clone(2) avec l'indicateur CLONE_FILES posent des verrous qui semblent (au noyau) entrer en conflit.

Verrouillage obligatoire

L'implémentation du verrouillage obligatoire dans Linux est sujette à des conditions de course qui le rendent peu fiable : un appel write(2) qui se chevauche avec un verrou peut modifier des données après que le verrou obligatoire a été acquis ; un appel read(2) qui se chevauche avec un verrou peut détecter des modifications de données qui n'ont été faites qu'après qu'un verrou d'écriture a été acquis. Des courses similaires existent entre les verrous obligatoires et mmap(2). Il est donc déconseillé de se fier au verrouillage obligatoire.
