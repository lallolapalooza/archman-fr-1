NOM

F_GETLK, F_SETLK, F_SETLKW, F_OFD_GETLK, F_OFD_SETLK, F_OFD_SETLKW - verrouillage

BIBLIOTHÈQUE

Bibliothèque C standard (libc,-lc)

SYNOPSIS

#include <fcntl.h>
int fcntl(int fd, F_GETLK, struct flock *lock);
int fcntl(int fd, F_SETLK, const struct flock *lock);
int fcntl(int fd, F_SETLKW, const struct flock *lock);
int fcntl(int fd, F_OFD_GETLK, struct flock *lock);
int fcntl(int fd, F_OFD_SETLK, const struct flock *lock);
int fcntl(int fd, F_OFD_SETLKW, const struct flock *lock);

DESCRIPTION

Verrouillage d'enregistrement consultatif

Linux implémente les verrous d'enregistrement UNIX traditionnels (« associés au processus »), tels que standardisés par POSIX. Pour une alternative propre à Linux avec une meilleure sémantique, voir la discussion sur les verrous de description de fichier ouvert ci-dessous.

F_SETLK, F_SETLKWet F_GETLK sont utilisés pour acquérir, libérer et tester l'existence de verrous d'enregistrement (également connus sous le nom de verrous par plage d'octets, par segment de fichier ou par région de fichier). Le troisième argument, lock, est un pointeur vers une structure qui a au moins les champs suivants (dans un ordre non spécifié).


struct flock {
    ...
    short l_type;    /* Type de verrou : F_RDLCK,
                        F_WRLCK, F_UNLCK */
    short l_whence;  /* Comment interpréter l_start :
                        SEEK_SET, SEEK_CUR, SEEK_END */
    off_t l_start;   /* Décalage de départ du verrou */
    off_t l_len;     /* Nombre d'octets à verrouiller */
    pid_t l_pid;     /* PID du processus bloquant notre verrou
                        (défini par F_GETLK et F_OFD_GETLK) */
    ...
};

Les champs l_whence, l_startet l_len de cette structure spécifient la plage d'octets que nous souhaitons verrouiller. Les octets au-delà de la fin du fichier peuvent être verrouillés, mais pas les octets avant le début du fichier.

l_start est le décalage de départ du verrou, et est interprété relativement à l'une des positions suivantes : le début du fichier (si l_whence vaut SEEK_SET) ; le décalage de fichier courant (si l_whence vaut SEEK_CUR) ; ou la fin du fichier (si l_whence vaut SEEK_END). Dans les deux derniers cas, l_start peut être un nombre négatif à condition que le décalage ne se situe pas avant le début du fichier.

l_len spécifie le nombre d'octets à verrouiller. Si l_len est positif, alors la plage à verrouiller couvre les octets l_start jusqu'à et y compris l_start+l_len-1. Spécifier 0 pour l_len a la signification spéciale suivante : verrouiller tous les octets à partir de l'emplacement spécifié par l_whence et l_start jusqu'à la fin du fichier, quelle que soit la taille à laquelle le fichier croît.

POSIX.1-2001 permet (mais n'exige pas) qu'une implémentation prenne en charge une valeur négative pour l_len ; si l_len est négatif, l'intervalle décrit par lock couvre les octets l_start+l_len jusqu'à et y compris l_start-1. Cela est pris en charge depuis Linux 2.4.21 et Linux 2.5.49.

Le champ l_type peut être utilisé pour placer un verrou de lecture (F_RDLCK) ou d'écriture (F_WRLCK) sur un fichier. Un nombre quelconque de processus peut détenir un verrou de lecture (verrou partagé) sur une région de fichier, mais un seul processus peut détenir un verrou d'écriture (verrou exclusif). Un verrou exclusif exclut tous les autres verrous, tant partagés qu'exclusifs. Un seul processus ne peut détenir qu'un seul type de verrou sur une région de fichier ; si un nouveau verrou est appliqué à une région déjà verrouillée, le verrou existant est converti au nouveau type de verrou. (De telles conversions peuvent impliquer la division, la réduction ou la fusion avec un verrou existant si la plage d'octets spécifiée par le nouveau verrou ne coïncide pas exactement avec la plage du verrou existant.)

F_SETLK
Acquérir un verrou (quand l_type vaut F_RDLCK ou F_WRLCK) ou libérer un verrou (quand l_type vaut F_UNLCK) sur les octets spécifiés par les champs l_whence, l_startet l_len de lock. Si un verrou conflictuel est détenu par un autre processus, cet appel renvoie -1 et définit errno à EACCES ou EAGAIN. (L'erreur renvoyée dans ce cas diffère selon les implémentations ; POSIX exige donc qu'une application portable vérifie les deux erreurs.)
F_SETLKW
Comme F_SETLK, mais si un verrou conflictuel est détenu sur le fichier, attendre que ce verrou soit libéré. Si un signal est capté pendant l'attente, l'appel est interrompu et (après le retour du gestionnaire de signal) retourne immédiatement (avec une valeur de retour -1 et errno défini à EINTR; voir signal(7)).
F_GETLK
En entrée de cet appel, lock décrit un verrou que nous aimerions placer sur le fichier. Si le verrou pouvait être placé, fcntl() ne le place pas réellement, mais renvoie F_UNLCK dans le champ l_type de lock et laisse les autres champs de la structure inchangés.
Si un ou plusieurs verrous incompatibles empêcheraient le placement de ce verrou, alors fcntl() renvoie les détails de l'un de ces verrous dans les champs l_type, l_whence, l_startet l_len de lock. Si le verrou conflictuel est un verrou d'enregistrement traditionnel (associé au processus), le champ l_pid est défini au PID du processus détenant ce verrou. Si le verrou conflictuel est un verrou de description de fichier ouvert, l_pid est défini à -1. Notez que les informations renvoyées peuvent déjà être obsolètes au moment où l'appelant les examine.

Afin de placer un verrou de lecture, fd doit être ouvert en lecture. Afin de placer un verrou d'écriture, fd doit être ouvert en écriture. Pour placer les deux types de verrous, ouvrez un fichier en lecture-écriture.

Lors du placement de verrous avec F_SETLKW, le noyau détecte les interblocages, où deux processus ou plus ont leurs requêtes de verrouillage mutuellement bloquées par des verrous détenus par les autres processus. Par exemple, supposons que le processus A détient un verrou d'écriture sur l'octet 100 d'un fichier, et que le processus B détient un verrou d'écriture sur l'octet 200. Si chaque processus tente ensuite de verrouiller l'octet déjà verrouillé par l'autre processus en utilisant F_SETLKW, alors, sans détection d'interblocage, les deux processus resteraient bloqués indéfiniment. Lorsque le noyau détecte de tels interblocages, il provoque l'échec immédiat de l'une des requêtes de verrouillage bloquantes avec l'erreur EDEADLK; une application qui rencontre une telle erreur devrait libérer certains de ses verrous pour permettre à d'autres applications de continuer avant de tenter de récupérer les verrous dont elle a besoin. Les interblocages circulaires impliquant plus de deux processus sont également détectés. Notez cependant qu'il existe des limitations à l'algorithme de détection d'interblocage du noyau ; voir BUGS.

En plus d'être supprimés par un F_UNLCKexplicite, les verrous d'enregistrement sont automatiquement libérés lorsque le processus se termine.

Les verrous d'enregistrement ne sont pas hérités par un enfant créé via fork(2), mais sont préservés à travers un execve(2).

En raison de la mise en mémoire tampon effectuée par la bibliothèque stdio(3) , l'utilisation du verrouillage d'enregistrement avec les routines de ce paquet devrait être évitée ; utilisez plutôt read(2) et write(2) .

Les verrous d'enregistrement décrits ci-dessus sont associés au processus (contrairement aux verrous de description de fichier ouvert décrits ci-dessous). Cela a quelques conséquences fâcheuses :

•
Si un processus ferme n'importe quel descripteur de fichier référençant un fichier, alors tous les verrous de ce processus sur ce fichier sont libérés, indépendamment du(des) descripteur(s) de fichier sur lequel(s) les verrous ont été obtenus. C'est mauvais : cela signifie qu'un processus peut perdre ses verrous sur un fichier tel que /etc/passwd ou /etc/mtab lorsque, pour une raison quelconque, une fonction de bibliothèque décide d'ouvrir, lire et fermer le même fichier.
•
Les threads d'un processus partagent les verrous. En d'autres termes, un programme multithread ne peut pas utiliser le verrouillage d'enregistrement pour s'assurer que les threads n'accèdent pas simultanément à la même région d'un fichier.

Les verrous de description de fichier ouvert résolvent ces deux problèmes.

Verrous de description de fichier ouvert (non-POSIX)</h2>

Les verrous de description de fichier ouverte sont des verrous advisory par plage d'octets dont le fonctionnement est dans la plupart des cas identique aux verrous de fichier traditionnels décrits ci-dessus. Ce type de verrou est spécifique à Linux et est disponible depuis Linux 3.15. (Il existe une proposition auprès du groupe Austin pour inclure ce type de verrou dans la prochaine révision de POSIX.1.) Pour une explication des descriptions de fichier ouvertes, voir open(2).

La principale différence entre les deux types de verrous est que, alors que les verrous de fichier traditionnels sont associés à un processus, les verrous de description de fichier ouverte sont associés à la description de fichier ouverte sur laquelle ils sont acquis, un peu comme les verrous acquis avec flock(2). Par conséquent (et contrairement aux verrous advisory traditionnels), les verrous de description de fichier ouverte sont hérités à travers fork(2) (et clone(2) avec CLONE_FILES), et ne sont automatiquement libérés qu'à la dernière fermeture de la description de fichier ouverte, au lieu d'être libérés à chaque fermeture du fichier.

Les combinaisons de verrous conflictuels (c'est-à-dire un verrou de lecture et un verrou d'écriture, ou deux verrous d'écriture) où l'un des verrous est un verrou de description de fichier ouverte et l'autre est un verrou de fichier traditionnel entrent en conflit même lorsqu'ils sont acquis par le même processus sur le même descripteur de fichier.

Les verrous de description de fichier ouverte placés via la même description de fichier ouverte (c'est-à-dire via le même descripteur de fichier, ou via un duplicata du descripteur de fichier créé par fork(2), dup(2), F_DUPFD(2const), etc.) sont toujours compatibles : si un nouveau verrou est placé sur une région déjà verrouillée, alors le verrou existant est converti au nouveau type de verrou. (Ces conversions peuvent entraîner une division, un rétrécissement ou une fusion avec un verrou existant, comme discuté ci-dessus.)

D'un autre côté, les verrous de description de fichier ouverte peuvent entrer en conflit les uns avec les autres lorsqu'ils sont acquis via différentes descriptions de fichier ouvertes. Ainsi, les threads d'un programme multithread peuvent utiliser les verrous de description de fichier ouverte pour synchroniser l'accès à une région de fichier en faisant effectuer à chaque thread son propre open(2) sur le fichier et en appliquant des verrous via le descripteur de fichier résultant.

Comme avec les verrous advisory traditionnels, le troisième argument de fcntl(), lock, est un pointeur vers une structure flock . Par contraste avec les verrous de fichier traditionnels, le champ l_pid de cette structure doit être mis à zéro lors de l'utilisation des opérations décrites ci-dessous.

Les opérations pour travailler avec les verrous de description de fichier ouverte sont analogues à celles utilisées avec les verrous traditionnels :

F_OFD_SETLK
Acquérir un verrou de description de fichier ouverte (lorsque l_type vaut F_RDLCK ou F_WRLCK) ou libérer un verrou de description de fichier ouverte (lorsque l_type vaut F_UNLCK) sur les octets spécifiés par les champs l_whence, l_startet l_len de lock. Si un verrou conflictuel est détenu par un autre processus, cet appel renvoie -1 et met errno à EAGAIN.
F_OFD_SETLKW
Comme F_OFD_SETLK, mais si un verrou conflictuel est détenu sur le fichier, alors attendre que ce verrou soit libéré. Si un signal est capturé pendant l'attente, alors l'appel est interrompu et (après le retour du gestionnaire de signal) retourne immédiatement (avec une valeur de retour -1 et errno mis à EINTR; voir signal(7)).
F_OFD_GETLK
En entrée de cet appel, lock décrit un verrou de description de fichier ouverte que nous aimerions placer sur le fichier. Si le verrou pouvait être placé, fcntl() ne le place pas réellement, mais renvoie F_UNLCK dans le champ l_type de lock et laisse les autres champs de la structure inchangés. Si un ou plusieurs verrous incompatibles empêcheraient ce verrou d'être placé, alors les détails sur l'un de ces verrous sont renvoyés via lock, comme décrit ci-dessus pour F_GETLK.

Dans l'implémentation actuelle, aucune détection de deadlock n'est effectuée pour les verrous de description de fichier ouverte. (Cela contraste avec les verrous de fichier associés à un processus, pour lesquels le noyau effectue bien une détection de deadlock.)

Verrouillage obligatoire

Avertissement: l'implémentation Linux du verrouillage obligatoire est peu fiable. Voir BUGS ci-dessous. En raison de ces bogues, et du fait que cette fonctionnalité est peu utilisée, depuis Linux 4.5, le verrouillage obligatoire est devenu une fonctionnalité optionnelle, régie par une option de configuration (CONFIG_MANDATORY_FILE_LOCKING). Cette fonctionnalité n'est plus du tout prise en charge dans Linux 5.15 et les versions ultérieures.

Par défaut, les verrous de fichier traditionnels (associés à un processus) et les verrous de description de fichier ouverte sont advisory. Les verrous advisory ne sont pas appliqués et ne sont utiles qu'entre processus coopératifs.

Les deux types de verrous peuvent également être obligatoires. Les verrous obligatoires sont appliqués à tous les processus. Si un processus tente d'effectuer un accès incompatible (par exemple, read(2) ou write(2)) sur une région de fichier qui a un verrou obligatoire incompatible, alors le résultat dépend de savoir si l'indicateur O_NONBLOCK est activé pour sa description de fichier ouverte. Si l'indicateur O_NONBLOCK n'est pas activé, alors l'appel système est bloqué jusqu'à ce que le verrou soit retiré ou converti en un mode compatible avec l'accès. Si l'indicateur O_NONBLOCK est activé, alors l'appel système échoue avec l'erreur EAGAIN.

Pour utiliser les verrous obligatoires, le verrouillage obligatoire doit être activé à la fois sur le système de fichiers qui contient le fichier à verrouiller, et sur le fichier lui-même. Le verrouillage obligatoire est activé sur un système de fichiers à l'aide de l'option "-o mand" de mount(8), ou de l'indicateur MS_MANDLOCK pour mount(2). Le verrouillage obligatoire est activé sur un fichier en désactivant la permission d'exécution du groupe sur le fichier et en activant le bit de permission set-group-ID (voir chmod(1) et chmod(2)).

Le verrouillage obligatoire n'est pas spécifié par POSIX. Certains autres systèmes prennent également en charge le verrouillage obligatoire, bien que les détails pour l'activer varient d'un système à l'autre.

Verrous perdus

Lorsqu'un verrou advisory est obtenu sur un système de fichiers en réseau tel que NFS, il est possible que le verrou soit perdu. Cela peut se produire en raison d'une action administrative sur le serveur, ou en raison d'une partition réseau (c'est-à-dire une perte de connectivité réseau avec le serveur) qui dure suffisamment longtemps pour que le serveur suppose que le client ne fonctionne plus.

Lorsque le système de fichiers détermine qu'un verrou a été perdu, les requêtes read(2) ou write(2) ultérieures peuvent échouer avec l'erreur EIO. Cette erreur persistera jusqu'à ce que le verrou soit retiré ou que le descripteur de fichier soit fermé. Depuis Linux 3.12, cela se produit au moins pour NFSv4 (y compris toutes les versions mineures).

Certaines versions d'UNIX envoient un signal (SIGLOST) dans cette circonstance. Linux ne définit pas ce signal et ne fournit aucune notification asynchrone des verrous perdus.

NAME

F_OFD_SETLKW, F_OFD_SETLK, F_OFD_GETLK - fcntl(2) for open file description locks

LIBRARY

Standard C library (libc, −lc)

SYNOPSIS

#include <fcntl.h>

int fcntl(int fd, int cmd, struct flock *lock);
int fcntl(int fd, int cmd, struct flock64 *lock);

DESCRIPTION

These commands are similar to fcntl(2) F_SETLK, F_SETLKW, and F_GETLK, but they operate on locks associated with the open file description referred to by the file descriptor fd, rather than the file description created by the most recent open(2) call.

Open file description locks are associated with the file descriptor itself, not with the file or inode. This means that if a file is opened multiple times, each file descriptor refers to a distinct open file description and thus has its own set of locks.

The commands are:

F_OFD_SETLK
Set a file lock. This is a nonblocking call. If the lock cannot be acquired immediately (e.g., because it would conflict with an existing lock), then fcntl(2) returns −1 and sets errno to EAGAIN.
F_OFD_SETLKW
Set a file lock. This is a blocking call. If the lock cannot be acquired immediately, the process will sleep until the lock can be acquired. The caller should take care to avoid deadlocks. If the operation is interrupted by a signal, it will return −1 with errno set to EINTR.
F_OFD_GETLK
Test for existing locks. If there is a lock that would conflict with the lock requested by the caller, then that lock is returned in the lock structure. If there is no such lock, the lock structure is unmodified, except that its l_type field is set to F_UNLCK.

The lock argument is a pointer to a struct flock (or struct flock64 on older kernels) structure, which specifies the lock to be placed or tested. The structure has the following fields:

struct flock {
    off_t   l_start;    /* Starting offset */
    off_t   l_len;      /* Number of bytes, or 0 for whole file */
    pid_t   l_pid;      /* PID of lock owner */
    short   l_type;     /* Type of lock: F_RDLCK, F_WRLCK, F_UNLCK */
    short   l_whence;   /* How to interpret l_start:
                           SEEK_SET, SEEK_CUR, SEEK_END */
};

l_type can be F_RDLCK (shared read lock), F_WRLCK (exclusive write lock), or F_UNLCK (unlock).

l_whence indicates the starting point for the lock range. It can be SEEK_SET (relative to the start of the file), SEEK_CUR (relative to the current file offset), or SEEK_END (relative to the end of the file).

l_start is the starting offset of the locked region. l_len is the length of the locked region. If l_len is 0, the lock extends from l_start to the end of the file.

Unlike traditional record locks (see fcntl(2) and flock(2)), open file description locks are not associated with the file's inode. Instead, they are associated with the open file description. This means that if a file is opened multiple times (e.g., with different flags or by different processes), each open file description maintains its own set of locks. A lock acquired on file descriptor fd1 will not conflict with a lock on file descriptor fd2 unless fd1 and fd2 refer to the same open file description.

Open file description locks are inherited across fork(2) calls, but not across execve(2) calls.

A process can acquire multiple locks on the same file description, and can hold both read and write locks simultaneously on different regions of the file.

The l_pid field is set by the kernel when returning information about an existing lock (e.g., for F_GETLK). It is ignored when placing or testing locks.

Traditional record locks (obtained via fcntl(2) F_SETLK, F_SETLKW, F_GETLK, or flock(2)) and open file description locks (obtained via F_OFD_SETLK, F_OFD_SETLKW, F_OFD_GETLK) do not interact. That is, a lock of one type does not prevent the acquisition or holding of a lock of the other type.

RETURN VALUE

On success, fcntl() returns a non-negative value. On error, it returns −1 and sets errno to indicate the error.

ERRORS

The following values can be set in errno:

EBADF
fd is not a valid open file descriptor.
EDEADLK
A deadlock was detected when using F_OFD_SETLKW.
EFAULT
lock points to memory outside the process's accessible address space.
EINTR
F_OFD_SETLKW was interrupted by a signal.
EINVAL
The value of cmd is not recognized, or the values in the lock structure are invalid (e.g., an invalid l_type, or l_whence is not one of SEEK_SET, SEEK_CUR, or SEEK_END).
ENOLCK
The system-imposed limit on the total number of locks has been reached.
EAGAIN
F_OFD_SETLK was attempted on a resource that was already locked.
ENOTSUP
The filesystem does not support locking.

STANDARDS

These commands were introduced in Linux 3.12. They are not part of any POSIX or other standard.

HISTORY

Open file description locks were introduced in Linux 3.12.

NOTES

Caveats concerning struct flock
Several systems have more fields in struct flock such as, for example, l_sysid (to identify the machine where the lock is held). Clearly, l_pid alone is not going to be very useful if the process holding the lock may live on a different machine; on Linux, while present on some architectures (such as MIPS32), this field is not used.

The original Linux fcntl() system call was not designed to handle large file offsets (in the struct flock structure). Consequently, an fcntl64() system call was added in Linux 2.4. The newer system call employs a different structure for file locking, flock64, and corresponding operations, F_GETLK64, F_SETLK64, and F_SETLKW64. However, these details can be ignored by applications using glibc, whose fcntl() wrapper function transparently employs the more recent system call where it is available.

Record locking and NFS

Before Linux 3.12, if an NFSv4 client loses contact with the server for a period of time (defined as more than 90 seconds with no communication), it might lose and regain a lock without ever being aware of the fact. (The period of time after which contact is assumed lost is known as the NFSv4 leasetime. On a Linux NFS server, this can be determined by looking at /proc/fs/nfsd/nfsv4leasetime, which expresses the period in seconds. The default value for this file is 90.) This scenario potentially risks data corruption, since another process might acquire a lock in the intervening period and perform file I/O.

Since Linux 3.12, if an NFSv4 client loses contact with the server, any I/O to the file by a process which "thinks" it holds a lock will fail until that process closes and reopens the file. A kernel parameter, nfs.recover_lost_locks, can be set to 1 to obtain the pre-3.12 behavior, whereby the client will attempt to recover lost locks when contact is reestablished with the server. Because of the attendant risk of data corruption, this parameter defaults to 0 (disabled).

BUGS

Deadlock detection

The deadlock-detection algorithm employed by the kernel when dealing with F_SETLKW requests can yield both false negatives (failures to detect deadlocks, leaving a set of deadlocked processes blocked indefinitely) and false positives (EDEADLK errors when there is no deadlock). For example, the kernel limits the lock depth of its dependency search to 10 steps, meaning that circular deadlock chains that exceed that size will not be detected. In addition, the kernel may falsely indicate a deadlock when two or more processes created using the clone(2) CLONE_FILES flag place locks that appear (to the kernel) to conflict.

Mandatory locking

The Linux implementation of mandatory locking is subject to race conditions which render it unreliable: a write(2) call that overlaps with a lock may modify data after the mandatory lock is acquired; a read(2) call that overlaps with a lock may detect changes to data that were made only after a write lock was acquired. Similar races exist between mandatory locks and mmap(2). It is therefore inadvisable to rely on mandatory locking.
