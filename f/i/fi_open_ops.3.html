NOM

fi_domain - Ouvre un domaine d'accès au fabric

SYNOPSIS

#include <rdma/fabric.h>
#include <rdma/fi_domain.h>
int fi_domain(struct fid_fabric *fabric, struct fi_info *info,
    struct fid_domain **domain, void *context);
int fi_domain2(struct fid_fabric *fabric, struct fi_info *info,
    struct fid_domain **domain, uint64_t flags, void *context);
int fi_close(struct fid *domain);
int fi_domain_bind(struct fid_domain *domain, struct fid *eq,
    uint64_t flags);
int fi_open_ops(struct fid *domain, const char *name, uint64_t flags,
    void **ops, void *context);
int fi_set_ops(struct fid *domain, const char *name, uint64_t flags,
    void *ops, void *context);

ARGUMENTS

fabric
Domaine de fabric
info
Informations sur le fabric, incluant les capacités et attributs du domaine. Le struct fi_info doit avoir été obtenu à l'aide de fi_getinfo() ou fi_dupinfo().
domain
Un domaine d'accès ouvert.
context
Contexte spécifié par l'utilisateur et associé au domaine. Ce contexte est renvoyé dans le cadre de tout événement asynchrone associé au domaine.
eq
File d'événements pour les opérations asynchrones initiées sur le domaine.
name
Nom associé à une interface.
ops
Opérations de l'interface de fabric.

DESCRIPTION

Un domaine d'accès désigne généralement une carte réseau physique ou virtuelle ou un port matériel ; cependant, un domaine peut s'étendre sur plusieurs composants matériels à des fins de basculement ou de répartition des données. Un domaine définit la limite pour associer différentes ressources entre elles. Les ressources de fabric appartenant au même domaine peuvent partager des ressources.

fi_domain

Ouvre un domaine d'accès au fabric, également appelé domaine de ressources. Les domaines de fabric sont identifiés par un nom. Les propriétés du domaine ouvert sont spécifiées à l'aide du paramètre info.

fi_domain2

Similaire à fi_domain, mais accepte un paramètre supplémentaire flags. Utilisé principalement pour ouvrir un domaine pair. Voir fi_peer(3).

fi_open_ops

fi_open_ops est utilisé pour ouvrir des interfaces spécifiques au fournisseur. Les interfaces du fournisseur peuvent être utilisées pour accéder à des ressources et opérations de bas niveau spécifiques au domaine de ressources ouvert. Les détails des interfaces de domaine sont hors du cadre de cette documentation.

fi_set_ops

fi_set_ops assigne des rappels qu'un fournisseur doit invoquer à la place de l'exécution de tâches sélectionnées. Cela permet aux utilisateurs de modifier ou de contrôler le comportement par défaut d'un fournisseur. Conceptuellement, cela permet à l'utilisateur d'intercepter des fonctions spécifiques utilisées par un fournisseur et de les remplacer par les siennes.

Les opérations modifiées sont identifiées à l'aide d'une chaîne de caractères bien connue, passée en paramètre name. Le format du paramètre ops dépend de la valeur de name. Le paramètre ops fera référence à une structure contenant les rappels et autres champs nécessaires au fournisseur pour invoquer les fonctions de l'utilisateur.

Si un fournisseur accepte la substitution, il renverra FI_SUCCESS. Si la substitution est inconnue ou non prise en charge, le fournisseur renverra -FI_ENOSYS. Les substitutions doivent être définies avant d'allouer des ressources sur le domaine.

Les opérations fi_set_ops suivantes et les structures de rappel correspondantes sont définies.

FI_SET_OPS_HMEM_OVERRIDE – Substitutions de mémoire hétérogène

La substitution HMEM permet aux utilisateurs de remplacer les opérations liées à HMEM qu'un fournisseur pourrait effectuer. Actuellement, la portée de la substitution HMEM est de permettre à un utilisateur de définir les fonctions de déplacement de mémoire qu'un fournisseur doit utiliser lors de l'accès à un tampon utilisateur. Les fonctions de déplacement de mémoire définies par l'utilisateur doivent prendre en compte tous les différents types d'interface HMEM qu'un fournisseur peut rencontrer.

Tous les objets alloués sur un domaine hériteront de cette substitution.

Voici le nom d'opération et la structure de la substitution HMEM.

#define FI_SET_OPS_HMEM_OVERRIDE "hmem_override_ops"
struct fi_hmem_override_ops {
    size_t  size;
    ssize_t (*copy_from_hmem_iov)(void *dest, size_t size,
        enum fi_hmem_iface iface, uint64_t device, const struct iovec *hmem_iov,
        size_t hmem_iov_count, uint64_t hmem_iov_offset);
    ssize_t (*copy_to_hmem_iov)(enum fi_hmem_iface iface, uint64_t device,
    const struct iovec *hmem_iov, size_t hmem_iov_count,
        uint64_t hmem_iov_offset, const void *src, size_t size);
};

Tous les champs de struct fi_hmem_override_ops doivent être définis (non nuls) à une valeur valide.

size
Doit être défini à sizeof(struct fi_hmem_override_ops). Le champ size est utilisé à des fins de compatibilité ascendante et descendante.
copy_from_hmem_iov
Copie des données du périphérique/hmem vers la mémoire hôte. Cette fonction doit renvoyer un fi_errno négatif en cas d'erreur, ou le nombre d'octets copiés en cas de succès.
copy_to_hmem_iov
Copie des données de la mémoire hôte vers le périphérique/hmem. Cette fonction doit renvoyer un fi_errno négatif en cas d'erreur, ou le nombre d'octets copiés en cas de succès.

fi_domain_bind

Associe une file d'événements au domaine. Une file d'événements liée à un domaine sera la file d'événements par défaut associée aux événements de contrôle asynchrones survenant sur le domaine ou sur les points d'extrémité actifs alloués sur un domaine. Cela inclut les événements CM. Les points d'extrémité peuvent diriger leurs événements de contrôle vers d'autres files d'événements en se liant directement à la file.

Obsolète: Lier une file d'événements à un domaine avec le drapeau FI_REG_MR indique que le fournisseur doit effectuer toutes les opérations d'enregistrement de mémoire de manière asynchrone, avec la complétion rapportée via la file d'événements. Si une file d'événements n'est pas liée au domaine avec le drapeau FI_REG_MR, les demandes d'enregistrement de mémoire se complètent de manière synchrone.

fi_close

L'appel fi_close est utilisé pour libérer toutes les ressources associées à un domaine ou à une interface. Tous les objets associés au domaine ouvert doivent être libérés avant d'appeler fi_close, sinon l'appel renverra -FI_EBUSY.

domain

En entrée de fi_getinfo, un utilisateur peut définir cette valeur sur une instance de domaine ouvert pour limiter la sortie au domaine donné. En sortie de fi_getinfo, si aucun domaine n'a été spécifié

fi_getinfo

The fi_getinfo call is used to retrieve information about the capabilities and supported features of the libfabric providers. It allows an application to query for information about the fabric, specific providers, and the interfaces and features they support. This information can then be used to select the appropriate provider and configure libfabric settings for optimal performance and functionality.

Description

The fi_getinfo call is used to retrieve information about libfabric providers. The hints parameter is a bitmask of flags that specify the desired features and capabilities of the provider. The name parameter specifies the name of the provider to query, or NULL if any provider supporting the hints should be returned.

The info parameter is a pointer to a fi_info structure that will be populated with the information about the selected provider. If multiple providers match the hints, fi_getinfo will return information about the first matching provider found.

The returned fi_info structure contains various fields that describe the provider's capabilities, including:

  • api_version: The libfabric API version supported by the provider.

  • fabric_attr: Attributes of the fabric.

  • domain_attr: Attributes of the domain.

  • ep_attr: Attributes of the endpoint.

  • tx_attr: Attributes of the transmit interface.

  • rx_attr: Attributes of the receive interface.

  • threading: The threading model supported by the provider.

  • progress: The progress model supported by the provider.

  • resource_mgmt: The resource management model supported by the provider.

  • addr_format: The address format used by the provider.

  • protocol: The protocol used by the provider.

  • options: Additional options supported by the provider.

  • domain: A pointer to the domain instance.

  • fabric: A pointer to the fabric instance.

If the name parameter is NULL, fi_getinfo will return information about the first available provider that matches the specified hints. If a specific provider is requested via the name parameter, fi_getinfo will return information about that provider if it matches the hints.

If the application has opened an instance of the named domain, this will reference the first opened instance. If no instance has been opened, this field will be NULL.

The domain instance returned by fi_getinfo should only be considered valid if the application does not close any domain instances from another thread while fi_getinfo is being processed.

Name

The name of the access domain.

Prise en charge multithread (threading)

Le modèle de threading spécifie le niveau de sérialisation requis d'une application lors de l'utilisation des interfaces de transfert de données libfabric. Les interfaces de contrôle sont toujours considérées comme sûres pour les threads, sauf si le modèle de progression du contrôle est FI_PROGRESS_CONTROL_UNIFIED. Une interface de contrôle sûre pour les threads permet à plusieurs threads de faire progresser l'interface de contrôle et (selon le modèle de threading sélectionné) à un ou plusieurs threads de faire progresser les interfaces de données en même temps. Les applications qui peuvent garantir la sérialisation dans leur accès aux ressources et interfaces allouées par le fournisseur permettent à un fournisseur d'éliminer les verrous de niveau inférieur.

FI_THREAD_COMPLETION
Le modèle de threading d'achèvement est le mieux adapté aux applications multithread utilisant des points d'extrémité évolutifs qui souhaitent une opération sans verrou. Les applications doivent sérialiser l'accès à tous les objets associés par un mécanisme d'achèvement commun (par exemple, contextes d'émission et de réception liés au même CQ ou compteur). Il est recommandé que les fournisseurs qui prennent en charge les points d'extrémité évolutifs prennent en charge ce modèle de threading.

Les applications souhaitant exploiter FI_THREAD_COMPLETION doivent dédier des contextes d'émission, des contextes de réception, des files d'attente d'achèvement et des compteurs à des threads individuels.

FI_THREAD_DOMAIN
Le modèle de threading de domaine est le mieux adapté aux applications monothread et aux applications multithread utilisant des points d'extrémité standard qui souhaitent une opération sans verrou. Les applications doivent sérialiser l'accès à tous les objets sous le même domaine. Cela inclut les points d'extrémité, les contextes d'émission et de réception, les files d'attente d'achèvement et les compteurs, et les régions de mémoire enregistrées.
FI_THREAD_ENDPOINT (obsolète)
Le modèle de threading de point d'extrémité est similaire à FI_THREAD_FID, mais avec la restriction supplémentaire que la sérialisation est requise lors de l'accès au même point d'extrémité, même si plusieurs contextes d'émission et de réception sont utilisés.
FI_THREAD_FID (obsolète)
Un modèle de sérialisation de descripteur de fabric (FID) exige que les applications sérialisent l'accès aux ressources de fabric individuelles associées aux opérations de transfert de données et aux achèvements. Pour l'accès aux points d'extrémité, la sérialisation n'est requise que lors de l'accès au même flux de données de point d'extrémité. Plusieurs threads peuvent initier des transferts sur différents contextes d'émission ou sur le même point d'extrémité sans sérialisation, et aucune sérialisation n'est requise entre la soumission des requêtes de transfert de données et les opérations de réception de données.
FI_THREAD_SAFE
Un modèle de sérialisation sûr pour les threads permet à une application multithread d'accéder à toutes les ressources allouées via n'importe quelle interface sans restriction. Tous les fournisseurs sont tenus de prendre en charge FI_THREAD_SAFE.
FI_THREAD_UNSPEC
Cette valeur indique qu'aucun modèle de threading n'a été défini. Elle peut être utilisée dans les indications d'entrée pour l'appel fi_getinfo. Lorsqu'elle est spécifiée, les fournisseurs renvoient un modèle de threading qui permet le plus grand niveau de parallélisme.

Modèles de progression (progress)

La progression est la capacité de l'implémentation sous-jacente à terminer le traitement d'une requête asynchrone. Dans de nombreux cas, le traitement d'une requête asynchrone nécessite l'utilisation du processeur hôte. Par exemple, un message reçu peut devoir être mis en correspondance avec le bon tampon, ou une requête expirée peut devoir être retransmise. Pour des raisons de performance, il peut être indésirable que le fournisseur alloue un thread à cet effet, ce qui entrera en concurrence avec les threads de l'application.

La progression du contrôle indique la méthode utilisée par le fournisseur pour faire progresser les opérations de contrôle asynchrones. Les opérations de contrôle sont des fonctions qui n'impliquent pas directement le transfert de données d'application entre les points d'extrémité. Elles incluent les routines de gestion des vecteurs d'adresses, d'enregistrement de mémoire et de connexion.

La progression des données indique la méthode utilisée par le fournisseur pour faire progresser les opérations de transfert de données. Cela inclut les files d'attente de messages, les opérations RMA, la messagerie taguée et les opérations atomiques, ainsi que leur traitement d'achèvement.

Le champ de progression définit le comportement des opérations de contrôle et de données. Pour les applications qui nécessitent une portabilité de compilation entre les séries libfabric version 1 et version 2, le champ de progression peut être référencé comme data_progress.

La progression nécessite souvent une action prise à la fois du côté de l'émetteur et du côté du récepteur d'une opération. C'est souvent une exigence pour les transferts fiables, en raison du traitement des tentatives et des accusés de réception.

Pour équilibrer performance et facilité d'utilisation, les modèles de progression suivants sont définis.

FI_PROGRESS_AUTO
Ce modèle de progression indique que le fournisseur fera progresser une opération asynchrone sans intervention supplémentaire de l'application. Lorsque FI_PROGRESS_AUTO est fourni en sortie à fi_getinfo en l'absence d'indications de progression, cela indique souvent que la fonctionnalité souhaitée est implémentée par le matériel du fournisseur ou qu'il s'agit d'un service standard du système d'exploitation.

Il est recommandé que les fournisseurs prennent en charge FI_PROGRESS_AUTO. Cependant, si un fournisseur ne prend pas nativement en charge la progression automatique, forcer l'utilisation de FI_PROGRESS_AUTO peut entraîner l'allocation de threads sous les interfaces de fabric.

Notez que les versions antérieures de la bibliothèque exigeaient que les fournisseurs prennent en charge FI_PROGRESS_AUTO. Cependant, dans certains cas, les threads de progression ne peuvent pas être bloqués lorsque la communication est inactive, ce qui entraîne des threads tournant dans les fonctions de progression. Par conséquent, ces fournisseurs ne prenaient en charge que FI_PROGRESS_MANUAL.

FI_PROGRESS_MANUAL
Ce modèle de progression indique que le fournisseur nécessite l'utilisation d'un thread d'application pour terminer une requête asynchrone. Lorsque la progression manuelle est définie, le fournisseur tentera de faire avancer une opération asynchrone lorsque l'application tente d'attendre ou de lire une file d'attente d'événements, une file d'attente d'achèvement ou un compteur où l'opération terminée sera signalée. La progression se produit également lorsque l'application traite un ensemble de sondage ou d'attente associé à la file d'attente d'événements ou d'achèvement.

Seules les opérations d'attente définies par l'interface de fabric entraîneront la progression d'une opération. Les fonctions d'attente du système d'exploitation ou externes, telles que select, poll, ou les routines pthread, ne le peuvent pas.

Les exigences de progression manuelle s'appliquent non seulement aux points d'extrémité qui initient des opérations d'émission, mais aussi aux points d'extrémité qui peuvent être la cible de telles opérations. Ceci est valable même si le point d'extrémité cible ne générera pas d'événements d'achèvement pour les opérations. Par exemple, un point d'extrémité qui agit purement comme cible d'opérations RMA ou atomiques qui utilise une progression manuelle peut toujours avoir besoin de l'aide de l'application pour traiter les opérations reçues.

FI_PROGRESS_CONTROL_UNIFIED
Ce modèle de progression indique que l'utilisateur synchronisera la progression des opérations de données et de contrôle lui-même (c'est-à-dire que cela permet à l'interface de contrôle de NE PAS être sûre pour les threads). Il implique une progression manuelle, et lorsqu'il est combiné avec threading = FI_THREAD_DOMAIN/FI_THREAD_COMPLETION, il permet à Libfabric de supprimer tous les verrous du chemin critique de progression des données.
FI_PROGRESS_UNSPEC
Cette valeur indique qu'aucun modèle de progression n'a été défini. Elle peut être utilisée dans les indications d'entrée pour l'appel fi_getinfo.

Gestion des ressources (resource_mgmt)

La gestion des ressources (RM) est une prise en charge du fournisseur et du protocole pour se protéger contre le dépassement des ressources locales et distantes. Cela inclut les contextes d'émission et de réception locaux et distants, les files d'attente d'achèvement, et les tampons de données source et cible.

Lorsqu'elle est activée, les applications bénéficient d'un certain niveau de protection contre le dépassement des files d'attente du fournisseur et des tampons de données locaux et distants. Une telle prise en charge peut être intégrée directement dans le matériel et/ou le protocole réseau, mais peut également nécessiter que des vérifications soient activées dans le logiciel du fournisseur. En désactivant la gestion des ressources, une application assume toute responsabilité pour prévenir les dépassements de files d'attente et de tampons, mais le faire peut permettre à un fournisseur d'éliminer les appels de synchronisation internes, tels que les variables atomiques ou les verrous.

Il convient de noter que même si la gestion des ressources est désactivée, l'implémentation du fournisseur et le protocole peuvent toujours fournir un certain niveau de protection contre les dépassements. Cependant, une telle protection n'est pas garantie. Les valeurs suivantes pour la gestion des ressources sont définies.

FI_RM_DISABLED
Le fournisseur est libre de choisir une implémentation et un protocole qui ne protègent pas contre les dépassements de ressources. L'application est responsable de la protection des ressources.
FI_RM_ENABLED
La gestion des ressources est activée pour ce domaine de fournisseur.
FI_RM_UNSPEC
Cette valeur indique qu'aucun modèle de gestion des ressources n'a été défini. Elle peut être utilisée dans les indications d'entrée pour l'appel fi_getinfo.

Le comportement des différentes options de gestion des ressources dépend de la fiabilité ou de l'absence de fiabilité du point d'extrémité, ainsi que des détails d'implémentation spécifiques au fournisseur et au protocole, comme indiqué dans le tableau suivant. La colonne Ressource indique la ressource à laquelle une opération de transfert de données accède.

Tx Ctx / Rx Ctx
Fait référence aux contextes d'émission/réception lors de la soumission d'une opération de transfert de données. Lorsque RM est activé, la tentative de soumettre une requête échouera si le contexte est plein. Si RM est désactivé, une erreur indéfinie (spécifique au fournisseur) se produira. De telles erreurs doivent être considérées comme fatales pour le contexte, et les applications doivent prendre des mesures pour éviter les débordements de file d'attente.
Tx CQ / Rx CQ
Fait référence à la file d'achèvement associée au contexte Tx ou Rx lorsqu'une opération locale se termine. Lorsque RM est désactivé, les applications doivent veiller à ce que les files d'achèvement ne soient pas débordées. Lorsqu'un débordement se produit, une erreur indéfinie mais fatale se produira, affectant tous les points de terminaison associés à la CQ. Les débordements peuvent être évités en dimensionnant correctement les CQ ou en différant la publication d'une opération de transfert de données tant qu'il n'y a pas d'espace disponible dans la CQ pour stocker son achèvement. Lorsque RM est activé, les fournisseurs peuvent utiliser différents mécanismes pour empêcher les débordements de CQ. Cela inclut l'échec (retour de -FI_EAGAIN) de la publication d'opérations qui pourraient entraîner des débordements de CQ, ou la reprise interne des requêtes (qui sera masquée à l'application). Voir les notes à la fin de cette section concernant les restrictions de gestion des ressources des CQ.
EP cible / Pas de tampon Rx
EP cible fait référence aux ressources associées au point de terminaison qui est la cible d'une opération d'émission. Cela inclut la file de réception du point de terminaison cible, les tampons de réception publiés (pas de tampons Rx), la file d'achèvement côté réception et d'autres files de traitement de paquets associées. Le comportement défini est celui observé par l'initiateur d'une requête. Pour les points de terminaison FI_EP_DGRAM, si les files de l'EP cible sont incapables d'accepter les messages entrants, les messages reçus seront abandonnés. Pour les points de terminaison fiables, si RM est désactivé, l'opération d'émission se terminera en erreur. Un fournisseur peut choisir de retourner un achèvement d'erreur avec le code d'erreur FI_ENORX pour cette opération d'émission afin qu'elle puisse être retentée. Si RM est activé, le fournisseur retentera l'opération en interne.
Débordement de tampon Rx
Cela fait référence aux tampons publiés pour recevoir les messages étiquetés ou non étiquetés entrants, avec le comportement défini du point de vue de l'émetteur. Le comportement pour le traitement des messages reçus qui sont plus grands que les tampons fournis par l'application est spécifique au fournisseur. Les fournisseurs peuvent soit tronquer le message et rapporter un achèvement réussi, soit faire échouer l'opération. Pour les points de terminaison de datagramme, les envois échoués entraîneront l'abandon du message. Pour les points de terminaison fiables, les opérations d'envoi peuvent se terminer avec succès, mais être tronquées côté réception. Cela peut se produire lorsque le côté cible met en tampon les données reçues jusqu'à ce qu'un tampon d'application soit disponible. Le statut d'achèvement peut également dépendre du modèle d'achèvement sélectionné par l'application (par exemple FI_DELIVERY_COMPLETE versus FI_TRANSMIT_COMPLETE).
RMA non apparié / Débordement RMA
Le RMA non apparié et les débordements RMA concernent le traitement des opérations RMA et atomiques. Contrairement aux opérations d'envoi, les opérations RMA qui tentent d'accéder à une adresse mémoire qui n'est pas enregistrée pour de telles opérations, ou qui tentent d'accéder en dehors de la région mémoire cible, échoueront, entraînant une erreur de transmission.
EP injoignable
Le point de terminaison injoignable est un scénario spécifique aux connexions sans fil où des opérations d'émission sont émises vers des points de terminaison cibles injoignables. De tels scénarios incluent l'absence de route vers l'hôte ou une NIC cible en panne. Pour les points de terminaison FI_EP_DGRAM, les opérations d'émission ciblant un point de terminaison injoignable seront abandonnées. Pour FI_EP_RDM, les opérations cibles ciblant un point de terminaison injoignable entraîneront une erreur de transmission.

Lorsqu'une erreur de gestion des ressources se produit sur un point de terminaison connecté, le point de terminaison passera à un état désactivé et la connexion sera démantelée. Un point de terminaison désactivé abandonnera toute opération en file d'attente ou en cours.

Le comportement des erreurs de gestion des ressources sur les points de terminaison sans connexion dépend du type d'erreur. Si RM est désactivé et que l'une des erreurs suivantes se produit, le point de terminaison sera désactivé : Tx Ctx, Rx Ctx, Tx CQ ou Rx CQ. Pour les autres erreurs (EP cible, pas de tampon Rx, etc.), l'opération peut échouer, mais le point de terminaison restera activé. Un point de terminaison désactivé abandonnera ou fera échouer toute opération en file d'attente ou en cours. De plus, un point de terminaison désactivé doit être réactivé avant d'accepter de nouvelles opérations de transfert de données.

Il existe une restriction notable sur les protections offertes par la gestion des ressources. Cela se produit lorsque la gestion des ressources est activée sur un point de terminaison qui a été lié à une ou plusieurs files d'achèvement à l'aide de l'indicateur FI_SELECTIVE_COMPLETION. Les opérations publiées sur un tel point de terminaison peuvent spécifier qu'un achèvement réussi ne doit pas générer une entrée sur la file d'achèvement correspondante. (C'est-à-dire que l'opération laisse l'indicateur FI_COMPLETION non défini). Dans de telles situations, le fournisseur n'est pas tenu de réserver une entrée dans la file d'achèvement pour gérer le cas où l'opération échoue et génère effectivement une entrée CQ, ce qui nécessiterait effectivement de suivre l'opération jusqu'à son achèvement. Les applications soucieuses d'éviter les débordements de CQ en cas d'erreurs doivent s'assurer qu'il y a suffisamment d'espace dans la CQ pour signaler les opérations échouées. Cela peut généralement être atteint en dimensionnant la CQ à au moins la même taille que la ou les files du point de terminaison qui y sont liées.

AV Type (av_type)

Spécifie le type de vecteurs d'adresses utilisables avec ce domaine. Pour plus de détails sur le type de AV, voir fi_av(3). Les valeurs suivantes peuvent être spécifiées.

FI_AV_MAP (obsolète)
Seuls les vecteurs d'adresses de type AV map sont demandés ou pris en charge.
FI_AV_TABLE
Seuls les vecteurs d'adresses de type AV index sont demandés ou pris en charge.
FI_AV_UNSPEC
Tout format de vecteur d'adresses est demandé et pris en charge.

Les vecteurs d'adresses ne sont utilisés que par les points de terminaison sans connexion. Les applications nécessitant l'utilisation d'un type spécifique de vecteur d'adresses doivent définir l'attribut de domaine av_type à la valeur nécessaire lors de l'appel à fi_getinfo. La valeur FI_AV_UNSPEC peut être utilisée pour indiquer que le fournisseur peut prendre en charge l'un ou l'autre format de vecteur d'adresses. Dans ce cas, un fournisseur peut retourner FI_AV_UNSPEC pour indiquer que l'un ou l'autre format est supportable, ou peut retourner un autre type d'AV pour indiquer le type d'AV optimal pris en charge par ce domaine.

Mode d'enregistrement mémoire (mr_mode)

Définit les bits de mode spécifiques à l'enregistrement mémoire utilisés avec ce domaine. Les détails complets sur les options de mode MR sont disponibles dans fi_mr(3). Les valeurs suivantes peuvent être spécifiées.

FI_MR_ALLOCATED
Indique que l'enregistrement mémoire se produit sur les tampons de données alloués, et que des pages physiques doivent soutenir toutes les adresses virtuelles en cours d'enregistrement.
FI_MR_COLLECTIVE
Exige que les tampons de données passés aux opérations collectives soient explicitement enregistrés pour les opérations collectives à l'aide du drapeau FI_COLLECTIVE.
FI_MR_ENDPOINT
L'enregistrement mémoire se produit au niveau du point de terminaison, plutôt qu'au niveau du domaine.
FI_MR_LOCAL
Le fournisseur est optimisé pour que les applications enregistrent la mémoire pour les tampons de données accédés localement. Les tampons de données utilisés dans les opérations d'envoi et de réception et comme tampon source pour les opérations RMA et atomiques doivent être enregistrés par l'application pour les domaines d'accès ouverts avec cette capacité.
FI_MR_MMU_NOTIFY
Indique que l'application est responsable de notifier le fournisseur lorsque les tables de pages référençant une région mémoire enregistrée ont pu être mises à jour.
FI_MR_PROV_KEY
Les clés d'enregistrement mémoire sont sélectionnées et retournées par le fournisseur.
FI_MR_RAW
Le fournisseur nécessite une configuration supplémentaire dans le cadre de son processus d'enregistrement mémoire. Ce mode est requis par les fournisseurs qui utilisent une clé mémoire qui est plus grande que 64 bits.
FI_MR_RMA_EVENT
Indique que les régions mémoire associées aux compteurs de complétion doivent être activées explicitement après avoir été liées à n'importe quel compteur.
FI_MR_UNSPEC (obsolète)
Défini pour compatibilité – versions de bibliothèque 1.4 et antérieures. Définir mr_mode à 0 indique que FI_MR_BASIC ou FI_MR_SCALABLE sont demandés et pris en charge.
FI_MR_VIRT_ADDR
Les régions mémoire enregistrées sont référencées par les pairs à l'aide de l'adresse virtuelle de la région mémoire enregistrée, plutôt qu'un décalage basé sur 0.
FI_MR_BASIC (obsolète)
Défini pour compatibilité – versions de bibliothèque 1.4 et antérieures. Seules les opérations d'enregistrement mémoire de base sont demandées ou prises en charge. Ce mode est équivalent aux drapeaux FI_MR_VIRT_ADDR, FI_MR_ALLOCATED et FI_MR_PROV_KEY étant définis dans les versions de bibliothèque ultérieures. Ce drapeau ne peut pas être utilisé en conjonction avec d'autres bits mr_mode.
FI_MR_SCALABLE (obsolète)
Défini pour compatibilité – versions de bibliothèque 1.4 et antérieures. Seules les opérations d'enregistrement mémoire évolutives sont demandées ou prises en charge. L'enregistrement évolutif utilise l'adressage basé sur les décalages, avec des clés mémoire sélectionnables par l'application. Pour les versions de bibliothèque 1.5 et ultérieures, c'est la valeur par défaut si aucun bit mr_mode n'est défini. Ce drapeau ne peut pas être utilisé en conjonction avec d'autres bits mr_mode.

Les tampons utilisés dans les opérations de transfert de données peuvent nécessiter de notifier le fournisseur de leur utilisation avant qu'un transfert de données puisse avoir lieu. Le champ mr_mode indique le type d'enregistrement mémoire qui est requis, et quand l'enregistrement est nécessaire. Les applications qui nécessitent l'utilisation d'un mode d'enregistrement spécifique doivent définir l'attribut de domaine mr_mode sur la valeur nécessaire lors de l'appel à fi_getinfo. La valeur FI_MR_UNSPEC peut être utilisée pour indiquer la prise en charge de n'importe quel mode d'enregistrement.

Taille de la clé MR (mr_key_size)

Taille de la clé d'accès distant de la région mémoire, en octets. Les applications qui demandent leur propre clé MR doivent sélectionner une valeur dans la plage spécifiée par cette valeur. Les tailles de clés supérieures à 8 octets nécessitent d'utiliser le bit de mode FI_RAW_KEY.

Taille des données CQ (cq_data_size)

Les applications peuvent inclure un petit message avec un transfert de données qui est placé directement dans une file d'attente de complétion distante dans le cadre d'un événement de complétion. Cela est appelé données CQ distantes (parfois appelées données immédiates). Ce champ indique le nombre d'octets que le fournisseur prend en charge pour les données CQ distantes. Si pris en charge (une valeur non nulle est retournée), la taille minimale des données CQ distantes doit être d'au moins 4 octets.

Nombre de files d'attente de complétion (cq_cnt)

Le nombre optimal de files d'attente de complétion prises en charge par le domaine, par rapport à n'importe quels attributs CQ spécifiés ou par défaut. La valeur cq_cnt peut être une valeur fixe du nombre maximum de CQ prises en charge par le matériel sous-jacent, ou peut être une valeur dynamique, basée sur les attributs par défaut d'une CQ allouée, tels que la taille de la CQ et le format de données.

Nombre de points de terminaison (ep_cnt)

Le nombre total de points de terminaison prises en charge par le domaine, par rapport à n'importe quels attributs de point de terminaison spécifiés ou par défaut. La valeur ep_cnt peut être une valeur fixe du nombre maximum de points de terminaison prises en charge par le matériel sous-jacent, ou peut être une valeur dynamique, basée sur les attributs par défaut d'un point de terminaison alloué, telles que les capacités et la taille du point de terminaison. Le nombre de points de terminaison est le nombre de points de terminaison adressables prises en charge par le fournisseur. Les fournisseurs retournent des limites de capacité basées sur les capacités maximales configurées du matériel. Les fournisseurs ne peuvent pas prédire toutes les limitations système possibles sans connaissance a posteriori acquise pendant l'exécution qui limitera davantage ces maximums matériels (par ex. consommation mémoire de l'application, utilisation des FD, etc.).

Nombre de contextes de transmission (tx_ctx_cnt)

Le nombre de files de commandes sortantes prises en charge de manière optimale par le fournisseur. Pour un fournisseur de bas niveau, cela représente le nombre de files de commandes vers le matériel et/ou le nombre de moteurs de transmission parallèles effectivement pris en charge par le matériel et les caches. Les applications qui allouent plus de contextes de transmission que cette valeur finiront par partager les ressources sous-jacentes. Par défaut, il y a un seul contexte de transmission associé à chaque point de terminaison, mais dans un modèle d'utilisation avancé, un point de terminaison peut être configuré avec plusieurs contextes de transmission.

Nombre de contextes de réception (rx_ctx_cnt)

Le nombre de files de traitement entrantes prises en charge de manière optimale par le fournisseur. Pour un fournisseur de bas niveau, cela représente le nombre de files matérielles qui peuvent être effectivement utilisées pour traiter les paquets entrants. Les applications qui allouent plus de contextes de réception que cette valeur finiront par partager les ressources sous-jacentes. Par défaut, un seul contexte de réception est associé à chaque point de terminaison, mais dans un modèle d'utilisation avancé, un point de terminaison peut être configuré avec plusieurs contextes de réception.

Contexte de transmission maximal du point de terminaison (max_ep_tx_ctx)

Le nombre maximum de contextes de transmission qui peuvent être associés à un point de terminaison.

Contexte de réception maximal du point de terminaison (max_ep_rx_ctx)

Le nombre maximum de contextes de réception qui peuvent être associés à un point de terminaison.

Partage maximal du contexte de transmission (max_ep_stx_ctx)

Le nombre maximum de points de terminaison qui peuvent être associés à un contexte de transmission partagé.

Partage maximal du contexte de réception (max_ep_srx_ctx)

Le nombre maximum de points de terminaison qui peuvent être associés à un contexte de réception partagé.

Nombre de compteurs (cntr_cnt)

Le nombre optimal de compteurs de complétion prises en charge par le domaine. La valeur cq_cnt peut être une valeur fixe du nombre maximum de compteurs pris en charge par le matériel sous-jacent, ou peut être une valeur dynamique, basée sur les attributs par défaut du domaine.

Limite IOV MR (mr_iov_limit)

C'est le nombre maximum de vecteurs IO (éléments scatter-gather) qu'une seule opération d'enregistrement mémoire peut référencer.

Capacités (caps)

Capacités au niveau du domaine. Les capacités du domaine indiquent les fonctionnalités au niveau du domaine qui sont prises en charge par le fournisseur.

Voici les capacités principales prises en charge : FI_DIRECTED_RECV : Lorsque le domaine est configuré avec FI_DIRECTED_RECV et FI_AV_AUTH_KEY, les régions mémoire peuvent être limitées à des clés d'autorisation spécifiques.

FI_AV_USER_ID
Indique que le domaine prend en charge la capacité d'ouvrir des vecteurs d'adresse avec le drapeau FI_AV_USER_ID. Si cette capacité de domaine n'est pas définie, les vecteurs d'adresse ne peuvent pas être ouverts avec FI_AV_USER_ID. Notez que FI_AV_USER_ID peut toujours être pris en charge via les appels d'insertion AV sans cette capacité de domaine définie. Voir fi_av(3).
FI_PEER
Spécifie que le domaine doit prendre en charge l'importation de ressources à utiliser dans le flux de l'API pair. Le domaine doit prendre en charge l'importation owner_ops lors de l'ouverture d'un CQ, d'un compteur et d'une file de réception partagée.

Les capacités secondaires suivantes sont prises en charge :

FI_LOCAL_COMM
À un niveau conceptuel, ce champ indique que le périphérique sous-jacent prend en charge la communication en boucle locale. Plus précisément, ce champ indique qu'un point de terminaison peut communiquer avec d'autres points de terminaison alloués à partir du même domaine nommé sous-jacent. Si ce champ n'est pas défini, une application peut avoir besoin d'utiliser un domaine ou un mécanisme alternatif (par ex. la mémoire partagée) pour communiquer avec des pairs qui s'exécutent sur le même nœud.
FI_REMOTE_COMM
Ce champ indique que le fournisseur sous-jacent prend en charge la communication avec des nœuds accessibles via le réseau. Si ce champ n'est pas défini, le fournisseur ne prend en charge que la communication entre des processus qui s'exécutent sur le même nœud – un fournisseur de mémoire partagée, par exemple.
FI_SHARED_AV
Indique que le domaine prend en charge la possibilité de partager des vecteurs d'adresses entre plusieurs processus à l'aide de la fonctionnalité de vecteur d'adresses nommé.

Voir fi_getinfo(3) pour une discussion sur les capacités primaires et secondaires.

Clé d'autorisation par défaut (auth_key)

La clé d'autorisation par défaut à associer aux points de terminaison et aux enregistrements de mémoire créés dans le domaine. Ce champ est ignoré sauf si le fabric est ouvert avec la version d'API 1.5 ou supérieure.

Si la taille auth_key du domaine est définie à la valeur FI_AV_AUTH_KEY, auth_key doit être NULL.

Longueur de la clé d'autorisation par défaut (auth_key_size)

La longueur en octets de la clé d'autorisation par défaut pour le domaine. Si définie à 0, aucune clé d'autorisation ne sera associée aux points de terminaison et aux enregistrements de mémoire créés dans le domaine, sauf si elle est spécifiée dans les attributs du point de terminaison ou de l'enregistrement de mémoire. Ce champ est ignoré sauf si le fabric est ouvert avec la version d'API 1.5 ou supérieure.

Si la taille est définie à la valeur FI_AV_AUTH_KEY, tous les points de terminaison et les régions de mémoire seront configurés pour utiliser les clés d'autorisation associées au AV. Les fournisseurs qui prennent en charge les clés d'autorisation et les points de terminaison sans connexion doivent prendre en charge cette option.

Taille maximale des données d'erreur (max_err_data)

La quantité maximale de données d'erreur, en octets, qui peut être renvoyée dans le cadre d'une erreur de file d'achèvement ou d'événement. Cette valeur correspond au champ err_data_size dans struct fi_cq_err_entry et struct fi_eq_err_entry.

Nombre de régions de mémoire (mr_cnt)

Le nombre optimal de régions de mémoire prises en charge par le domaine, ou par le point de terminaison si le bit mr_mode FI_MR_ENDPOINT a été défini. La valeur mr_cnt peut être une valeur fixe correspondant au nombre maximal de MR prises en charge par le matériel sous-jacent, ou une valeur dynamique, basée sur les attributs par défaut du domaine, tels que les modes d'enregistrement de mémoire pris en charge. Les applications peuvent définir mr_cnt en entrée de fi_getinfo, afin d'indiquer leurs exigences d'enregistrement de mémoire. Cela peut permettre au fournisseur d'optimiser le cache d'enregistrement de mémoire ou les tables de recherche.

Classe de trafic (tclass)

Cela spécifie la classe de trafic par défaut qui sera associée à tous les points de terminaison créés dans le domaine. Voir fi_endpoint(3) pour des informations supplémentaires.

Nombre maximal de clés d'autorisation par point de terminaison (max_ep_auth_key)

Le nombre maximal de clés d'autorisation qui peuvent être prises en charge par point de terminaison sans connexion.

Identifiant de groupe de pairs maximal (max_group_id)

La valeur maximale qu'un groupe de pairs peut se voir attribuer, inclusive. Les identifiants de groupe de pairs valides doivent être compris entre 0 et max_group_id. Voir fi_av(3) pour des informations supplémentaires sur les groupes de pairs et leur utilisation. Les utilisateurs peuvent demander la prise en charge des groupes de pairs en définissant cette valeur à une valeur non nulle. Les fournisseurs qui ne peuvent pas satisfaire le max_group_id demandé feront échouer fi_getinfo(). En sortie, les fournisseurs peuvent renvoyer une valeur supérieure à celle demandée par l'application.

VALEUR DE RETOUR

Renvoie 0 en cas de succès. En cas d'erreur, une valeur négative correspondant à l'errno du fabric est renvoyée. Les valeurs d'errno du fabric sont définies dans rdma/fi_errno.h.

NOTES

Les utilisateurs doivent appeler fi_close pour libérer toutes les ressources allouées au domaine du fabric.

Les ressources de fabric suivantes sont associées aux domaines : points de terminaison actifs, régions de mémoire, files d'événements d'achèvement et vecteurs d'adresses.

Les attributs du domaine reflètent les limitations et les capacités du matériel sous-jacent et/ou du fournisseur logiciel. Ils ne reflètent pas les limitations du système, telles que le nombre de pages physiques qu'une application peut épingler ou le nombre de descripteurs de fichiers que l'application peut ouvrir. Par conséquent, les maximums rapportés peuvent ne pas être atteignables, même sur des systèmes peu chargés, sans qu'un administrateur configure les ressources de manière appropriée pour le ou les fournisseurs installés.
