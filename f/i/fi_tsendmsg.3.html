DESCRIPTIO

N

Les messages étiquetés sont des transferts de données qui portent une clé ou une étiquette avec le tampon de message. L'étiquette est utilisée au point de terminaison de réception pour faire correspondre le message entrant avec un tampon de réception correspondant. Les étiquettes de message correspondent lorsque l'étiquette du tampon de réception est la même que celle du tampon d'envoi, les bits ignorés étant masqués. Cela peut s'énoncer comme suit 

: 
send_tag & ~ignore =
= recv_tag & ~ignore
ou send_tag | ignore
== recv_tag | ignore

En général, les étiquettes de message sont vérifiées par rapport aux tampons de réception dans l'ordre dans lequel les messages ont été publiés sur le point de terminaison. Voir la discussion sur l'ordre ci-dessous pour plus de

détails.

Les fonctions d'envoi – fi_tsend, fi_tsendv, fi_tsendmsg, fi_tinject et fi_tsenddata – sont utilisées pour transmettre un message étiqueté d'un point de terminaison à un autre. La principale différence entre les fonctions d'envoi réside dans le nombre et le type de paramètres qu'elles acceptent en entrée. Sinon, elles effectuent la même fonction

générale.

Les fonctions de réception – fi_trecv, fi_trecvv, fi_recvmsg – publient un tampon de données sur un point de terminaison pour recevoir des messages étiquetés entrants. Similairement aux opérations d'envoi, les opérations de réception fonctionnent de manière asynchrone. Les utilisateurs ne doivent pas toucher aux tampons de données publiés tant que l'opération de réception n'est pas terminée. Les tampons de réception publiés sont appariés avec les messages d'envoi entrants en fonction des étiquettes associées aux tampons d'envoi et de

réception.

Un point de terminaison doit être activé avant qu'une application puisse y publier des opérations d'envoi ou de réception. Pour les points de terminaison connectés, les tampons de réception peuvent être publiés avant que connect ou accept ne soit appelé sur le point de terminaison. Cela garantit que les tampons sont disponibles pour recevoir les données entrantes immédiatement après l'établissement de la

connexion.

Les opérations de message terminées sont signalées à l'utilisateur via un ou plusieurs collecteurs d'événements associés au point de terminaison. Les utilisateurs fournissent un contexte qui est associé à chaque opération et qui est renvoyé à l'utilisateur dans le cadre de la complétion de l'événement. Voir fi_cq pour les détails des événements de

complétion.

fi_tsen

d

L'appel fi_tsend transfère les données contenues dans le tampon de données spécifié par l'utilisateur vers un point de terminaison distant, les limites du message étant mainten

ues. Le point de terminaison local doit être connecté à un point de terminaison ou à une destination distante avant que fi_tsend ne soit appelé. Sauf si le point de terminaison
a été configuré différemment, le tampon de données passé à fi_tsend ne doit pas être touché par l'application tant que l'appel fi_tsend n'est pas terminé de manière asynchrone.

fi_tsend

v

L'appel fi_tsendv ajoute la prise en charge d'une liste scatter-gather à fi

_tsend. fi_tsendv transfère l'ensemble des tampons de données référencés pa
r le paramètre iov vers un point de terminaison distant en un seul message.

fi_tsendms

g

entrée.

_tinject, mais permet l'envoi de données CQ distantes (voir

fi_trecv

L'appel fi_trecv publie un tampon de données dans la file de réception de l'extrémité correspondante. Les réceptions publiées sont parcourues dans l'ordre où elles ont été publiées afin de faire correspondre les envois. Les limites des messages sont préservées. L'ordre dans lequel les réceptions se complètent dépend du type d'extrémité et du protocole.

fi_trecvv

L'appel fi_trecvv ajoute la prise en charge d'une liste de dispersion-gathering à fi_trecv. fi_trecvv publie l'ensemble des tampons de données référencés par le paramètre iov pour recevoir des données entrantes.

fi_trecvmsg

L'appel fi_trecvmsg prend en charge la publication de tampons sur des extrémités connectées et non connectées, avec la possibilité de contrôler l'opération de réception pour chaque appel à l'aide de drapeaux. La fonction fi_trecvmsg prend une struct fi_msg_tagged en entrée.

DRAPEAUX

Les appels fi_trecvmsg et fi_tsendmsg permettent à l'utilisateur de spécifier des drapeaux qui peuvent modifier le traitement par défaut des messages de l'extrémité. Les drapeaux spécifiés avec fi_trecvmsg / fi_tsendmsg remplacent la plupart des drapeaux précédemment configurés avec l'extrémité, sauf indication contraire (voir fi_endpoint). La liste suivante de drapeaux est utilisable avec fi_trecvmsg et/ou fi_tsendmsg.

FI_REMOTE_CQ_DATA
S'applique à fi_tsendmsg. Indique que des données CQ distantes sont disponibles et doivent être envoyées dans le cadre de la requête. Voir fi_getinfo pour plus de détails sur FI_REMOTE_CQ_DATA. Ce drapeau est défini implicitement pour fi_tsenddata et fi_tinjectdata.
FI_COMPLETION
Indique qu'une entrée de complétion doit être générée pour l'opération spécifiée. L'extrémité doit être liée à une file de complétion avec FI_SELECTIVE_COMPLETION correspondant à l'opération spécifiée, sinon ce drapeau est ignoré.
FI_MORE
Indique que l'utilisateur a des requêtes supplémentaires qui seront publiées immédiatement après le retour de l'appel en cours. L'utilisation de ce drapeau peut améliorer les performances en permettant au fournisseur d'optimiser son accès au matériel de fabric.
FI_INJECT
S'applique à fi_tsendmsg. Indique que le tampon de données sortantes doit être rendu à l'utilisateur immédiatement après le retour de l'appel d'envoi, même si l'opération est traitée de manière asynchrone. Cela peut nécessiter que l'implémentation du fournisseur sous-jacent copie les données dans un tampon local et les transfère depuis ce tampon. Ce drapeau ne peut être utilisé qu'avec des messages plus petits que inject_size.
FI_MULTI_RECV
S'applique aux opérations de réception étiquetées publiées lorsque la fonctionnalité FI_TAGGED_MULTI_RECV est activée. Ce drapeau permet à l'utilisateur de publier un seul tampon de réception étiqueté qui recevra plusieurs messages entrants. Les messages reçuis seront empaquetés dans le tampon de réception jusqu'à ce que le tampon soit consommé. L'utilisation de ce drapeau peut faire qu'une seule opération de réception publiée génère plusieurs événements lorsque des messages sont placés dans le tampon. Le placement des données reçues dans le tampon peut être soumis à des restrictions d'alignement spécifiques au fournisseur.

Le tampon sera libéré par le fournisseur lorsque l'espace de tampon disponible descend en dessous du minimum spécifié (voir FI_OPT_MIN_MULTI_RECV). Notez qu'une entrée dans la file de complétion de réception associée sera toujours générée lorsque le tampon a été consommé, même si d'autres complétions de réception ont été supprimées (c'est-à-dire que le contexte Rx a été configuré pour FI_SELECTIVE_COMPLETION). Voir le drapeau de complétion FI_MULTI_RECV fi_cq(3).

FI_INJECT_COMPLETE
S'applique à fi_tsendmsg. Indique qu'une complétion doit être générée lorsque le(s) tampon(s) source peuvent être réutilisés.
FI_TRANSMIT_COMPLETE
S'applique à fi_tsendmsg. Indique qu'une complétion ne doit pas être générée tant que l'opération n'a pas été transmise avec succès et n'est plus suivie par le fournisseur.
FI_MATCH_COMPLETE
S'applique à fi_tsendmsg. Indique qu'une complétion ne doit être générée qu'après que le message a été soit apparié avec un tampon étiqueté, soit écarté par l'application cible.
FI_FENCE
S'applique aux transmissions. Indique que l'opération demandée, aussi appelée opération clôturée (fenced), et toute opération publiée après l'opération clôturée seront différées jusqu'à ce que toutes les opérations précédentes ciblant la même extrémité pair se soient complétées. Les opérations publiées après la clôture verront et/ou remplaceront les résultats de toute opération initiée avant l'opération clôturée.

L'ordre des opérations à partir de la publication de l'opération clôturée (inclusive) jusqu'à la publication d'une opération clôturée subséquente (exclusive) est contrôlé par la sémantique d'ordonnancement de l'extrémité.

FI_AUTH_KEY
Valable uniquement avec les domaines configurés avec FI_AV_AUTH_KEY et les extrémités non connectées configurées avec FI_DIRECTED_RECV ou FI_TAGGED_DIRECTED_RECV. Lorsqu'il est utilisé avec fi_trecvmsg, ce drapeau indique que src_addr est une clé d'autorisation fi_addr_t au lieu d'une extrémité fi_addr_t.

Les drapeaux suivants peuvent être utilisés avec fi_trecvmsg.

FI_PEEK
Le drapeau peek peut être utilisé pour voir si un message spécifié est arrivé. Une requête peek est souvent utile sur les extrémités ayant la mise en tampon allouée par le fournisseur activée. Contrairement aux opérations de réception standard, une opération de réception avec le drapeau FI_PEEK défini ne reste pas en file d'attente auprès du fournisseur après que le peek se soit complété avec succès. L'opération peek fonctionne de manière asynchrone, et les résultats de l'opération peek sont disponibles dans la file de complétion associée à l'extrémité. Si aucun message correspondant aux tags spécifiés dans la requête peek n'est trouvé, alors une entrée d'erreur de file de complétion avec le champ err défini à FI_ENOMSG sera disponible.

Si une requête peek trouve un message correspondant, l'opération se complétera avec succès. Les données de complétion retournées indiqueront les métadonnées associées au message, telles que la longueur du message, les drapeaux de complétion, les données CQ disponibles, le tag et l'adresse source. Les données disponibles dépendent du format de l'entrée de complétion (par exemple struct fi_cq_tagged_entry).

FI_CLAIM
Si ce drapeau est utilisé en conjonction avec FI_PEEK, il indique que si la requête peek se complète avec succès – indiquant qu'un message correspondant a été localisé – le message est réclamé par l'appelant. Les messages réclamés ne peuvent être récupérés qu'à l'aide d'une opération de réception appariée et subséquente avec le drapeau FI_CLAIM défini. Une opération de réception avec le drapeau FI_CLAIM défini, mais FI_PEEK non défini, est utilisée pour récupérer un message précédemment réclamé.

Afin d'utiliser le drapeau FI_CLAIM, une application doit fournir une structure struct fi_context comme contexte pour l'opération de réception. La même structure fi_context utilisée pour une opération FI_PEEK + FI_CLAIM doit être utilisée par la requête FI_CLAIM appariée.

FI_DISCARD
Ce drapeau peut être utilisé en conjonction avec FI_PEEK ou FI_CLAIM. Si ce drapeau est utilisé en conjonction avec FI_PEEK, il indique que si la requête peek se complète avec succès – indiquant qu'un message correspondant a été localisé – le message est écarté par le fournisseur, car les données ne sont pas nécessaires à l'application. Ce drapeau peut également être utilisé en conjonction avec FI_CLAIM afin d'écarter un message précédemment réclamé à l'aide d'une requête FI_PEEK + FI_CLAIM.

Si ce drapeau est défini, les tampons d'entrée et les paramètres de longueur sont ignorés.

VALEUR RETOURNÉE

Les appels d'envoi et de réception étiquetés retournent 0 en cas de succès. En cas d'erreur, une valeur négative correspondant au fabric errno est retournée. Les valeurs de fabric errno sont définies dans fi_errno.h.

ERREURS

-FI_EAGAIN
Voir fi_msg(3) pour une description détaillée du traitement de FI_EAGAIN.
-FI_EINVAL
Indique qu'un argument invalide a été fourni par l'utilisateur.
-FI_EOTHER
Indique qu'une erreur non spécifiée s'est produite.
