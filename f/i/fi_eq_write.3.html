NOM

fi_eq - Opérations de file d'événements

fi_eq_open / fi_close
Ouvre/ferme une file d'événements
fi_control
Opération de contrôle de la file d'événements
fi_eq_read / fi_eq_readerr
Lit un événement depuis une file d'événements
fi_eq_write
Écrit un événement dans une file d'événements
fi_eq_sread
Lecture synchrone (bloquante) d'une file d'événements
fi_eq_strerror
Convertit les informations d'erreur spécifiques au fournisseur en une chaîne imprimable

SYNOPSIS

#include <rdma/fi_domain.h>
int fi_eq_open(struct fid_fabric *fabric, struct fi_eq_attr *attr,
    struct fid_eq **eq, void *context);
int fi_close(struct fid *eq);
int fi_control(struct fid *eq, int command, void *arg);
ssize_t fi_eq_read(struct fid_eq *eq, uint32_t *event,
    void *buf, size_t len, uint64_t flags);
ssize_t fi_eq_readerr(struct fid_eq *eq, struct fi_eq_err_entry *buf,
    uint64_t flags);
ssize_t fi_eq_write(struct fid_eq *eq, uint32_t event,
    const void *buf, size_t len, uint64_t flags);
ssize_t fi_eq_sread(struct fid_eq *eq, uint32_t *event,
    void *buf, size_t len, int timeout, uint64_t flags);
const char * fi_eq_strerror(struct fid_eq *eq, int prov_errno,
      const void *err_data, char *buf, size_t len);

ARGUMENTS

fabric
Descripteur de tissu (fabric) ouvert
eq
File d'événements
attr
Attributs de la file d'événements
context
Contexte spécifié par l'utilisateur associé à la file d'événements.
event
Événement signalé
buf
Pour les appels de lecture, le tampon de données dans lequel écrire les événements. Pour les appels d'écriture, un événement à insérer dans la file d'événements. Pour fi_eq_strerror, un tampon optionnel qui reçoit les informations d'erreur imprimables.
len
Longueur du tampon de données
flags
Drapeaux supplémentaires à appliquer à l'opération
command
Commande de l'opération de contrôle à effectuer sur la file d'événements.
arg
Argument de contrôle optionnel
prov_errno
Valeur d'erreur spécifique au fournisseur
err_data
Données d'erreur spécifiques au fournisseur liées à une complétion
timeout
Délai d'attente spécifié en millisecondes

DESCRIPTION

Les files d'événements sont utilisées pour signaler des événements associés aux opérations de contrôle. Elles sont associées à l'enregistrement mémoire, aux vecteurs d'adresses, à la gestion des connexions, ainsi qu'aux événements de niveau tissu (fabric) et domaine. Les événements signalés sont soit associés à une opération demandée, soit affiliés à un appel qui s'enregistre pour des types d'événements spécifiques, comme l'écoute de demandes de connexion.

fi_eq_open

fi_eq_open alloue une nouvelle file d'événements.

Les propriétés et le comportement d'une file d'événements sont définis par struct fi_eq_attr.

struct fi_eq_attr {
    size_t               size;      /* # entrées pour la file d'événements */
    uint64_t             flags;     /* drapeaux d'opération */
    enum fi_wait_obj     wait_obj;  /* objet d'attente demandé */
    int                  signaling_vector; /* affinité d'interruption */
    struct fid_wait     *wait_set;  /* ensemble d'attente optionnel, obsolète */
};
size
Spécifie la taille minimale d'une file d'événements.
flags
Drapeaux qui contrôlent la configuration de la file d'événements.
- FI_WRITE
Indique que l'application nécessite la prise en charge de l'insertion d'événements utilisateur dans la file d'événements. Si ce drapeau est défini, l'opération fi_eq_write doit être prise en charge par le fournisseur. Si le drapeau FI_WRITE n'est pas défini, l'application ne peut pas invoquer fi_eq_write.
- FI_AFFINITY
Indique que le champ signaling_vector (voir ci-dessous) est valide.
wait_obj
Les files d'événements peuvent être associées à un objet d'attente spécifique. Les objets d'attente permettent aux applications de se bloquer jusqu'à ce que l'objet d'attente soit signalé, indiquant qu'un événement est disponible pour être lu. Les utilisateurs peuvent utiliser fi_control pour récupérer l'objet d'attente sous-jacent associé à une file d'événements, afin de l'utiliser dans d'autres appels système. Les valeurs suivantes peuvent être utilisées pour spécifier le type d'objet d'attente associé à une file d'événements :
- FI_WAIT_NONE
Utilisé pour indiquer que l'utilisateur ne se bloquera pas (n'attendra pas) d'événements sur la file d'événements. Lorsque FI_WAIT_NONE est spécifié, l'application ne peut pas appeler fi_eq_sread. C'est la valeur par défaut si aucun objet d'attente n'est spécifié.
- FI_WAIT_UNSPEC
Spécifie que l'utilisateur n'attendra sur la file d'événements qu'à l'aide d'appels d'interface tissu (fabric), tels que fi_eq_sread. Dans ce cas, le fournisseur sous-jacent peut sélectionner l'objet d'attente le plus approprié ou le plus performant disponible, y compris des mécanismes d'attente personnalisés. Les applications qui sélectionnent FI_WAIT_UNSPEC ne sont pas garanties de pouvoir récupérer l'objet d'attente sous-jacent.
- FI_WAIT_SET (obsolète)
Indique que la file d'événements doit utiliser un objet ensemble d'attente pour attendre des événements. Si spécifié, le champ wait_set doit référencer un objet ensemble d'attente existant.
- FI_WAIT_FD
Indique que la file d'événements doit utiliser un descripteur de fichier comme mécanisme d'attente. Un objet d'attente descripteur de fichier doit être utilisable dans les routines select, poll et epoll. Cependant, un fournisseur peut signaler un objet d'attente FD en le marquant comme lisible ou avec une erreur.
- FI_WAIT_MUTEX_COND (obsolète)
Spécifie que la file d'événements doit utiliser un mutex pthread et une variable de condition comme objet d'attente.
- FI_WAIT_YIELD
Indique que la file d'événements attendra sans objet d'attente mais cédera plutôt à chaque attente. Permet l'utilisation de fi_eq_sread via une boucle d'attente active (spin).
signaling_vector
Si le drapeau FI_AFFINITY est défini, cela indique le numéro de CPU logique (0..max cpu - 1) que les interruptions associées à la file d'événements doivent cibler. Ce champ doit être traité comme une suggestion pour le fournisseur et peut être ignoré si le fournisseur ne prend pas en charge l'affinité d'interruption.
wait_set (obsolète)
Si wait_obj est FI_WAIT_SET, ce champ référence un objet d'attente auquel la file d'événements doit s'attacher. Lorsqu'un événement est inséré dans la file d'événements, l'ensemble d'attente correspondant sera signalé si toutes les conditions nécessaires sont remplies. L'utilisation d'un wait_set permet une méthode optimisée d'attente d'événements à travers plusieurs files d'événements. Ce champ est ignoré si wait_obj n'est pas FI_WAIT_SET.

fi_close

L'appel fi_close libère toutes les ressources associées à une file d'événements. Tout événement restant sur la file d'événements lors de sa fermeture est perdu.

La file d'événements ne doit être liée à aucun autre objet avant d'être fermée, sinon l'appel retournera -FI_EBUSY.

fi_control

L'appel fi_control est utilisé pour accéder aux détails spécifiques au fournisseur ou à l'implémentation de la file d'événements. L'accès à la file d'événements doit être sérialisé à travers tous les appels lorsque fi_control est invoqué, car il peut rediriger l'implémentation des opérations EQ. Les commandes de contrôle suivantes sont utilisables avec une EQ.

FI_GETWAIT (void **)
Cette commande permet à l'utilisateur de récupérer l'objet d'attente de bas niveau associé à la EQ. Le format de l'objet d'attente est spécifié lors de la création de la EQ, via les attributs de la EQ. Le paramètre arg de fi_control doit être une adresse où un pointeur vers l'objet d'attente retourné sera écrit. Cela doit être un 'int *' pour FI_WAIT_FD, ou `struct fi_mutex_cond' pour FI_WAIT_MUTEX_COND (obsolète).
struct fi_mutex_cond {
    pthread_mutex_t     *mutex;
    pthread_cond_t      *cond;
};

fi_eq_read

L'opération fi_eq_read effectue une lecture non bloquante de données d'événement à partir de la EQ. Le format des données d'événement est basé sur le type d'événement récupéré depuis la EQ, tous les événements commençant par un en-tête struct fi_eq_entry. Au plus un événement sera retourné par opération de lecture de la EQ. Le nombre d'octets lus avec succès depuis la EQ est retourné par la lecture. L'indicateur FI_PEEK peut être utilisé pour indiquer que les données d'événement doivent être lues depuis la EQ sans être consommées. Une lecture ultérieure sans l'indicateur FI_PEEK retirerait alors l'événement de la EQ.

Les types d'événements suivants peuvent être rapportés à une EQ, avec des informations concernant le format associé à chaque événement.

Opérations de Contrôle Asynchrones
Les opérations de contrôle asynchrones sont des requêtes de base qui ont simplement besoin de générer un événement pour indiquer qu'elles sont terminées. Celles-ci incluent les types d'événements suivants : l'enregistrement mémoire, la résolution du vecteur d'adresses et les adhésions au multicast.

Les requêtes de contrôle rapportent leur complétion en insérant une struct fi_eq_entry dans la EQ. Le format de cette structure est :

struct fi_eq_entry {
    fid_t            fid;        /* fid associé à la requête */
    void            *context;    /* contexte de l'opération */
    uint64_t         data;       /* données spécifiques à la complétion */
};

Pour la complétion des opérations de contrôle asynchrones de base, l'événement retourné indiquera l'opération qui s'est terminée, et le fid référencera le descripteur de fabrique associé à l'événement. Pour l'enregistrement mémoire, ce sera un événement FI_MR_COMPLETE et le fid_mr. La résolution d'adresse référencera un événement FI_AV_COMPLETE et fid_av. Les adhésions au multicast rapporteront un FI_JOIN_COMPLETE et fid_mc. Le champ context sera défini sur le contexte spécifié comme partie de l'opération, si disponible, sinon le contexte sera associé au descripteur de fabrique. Le champ data sera défini comme décrit dans la page man pour le type d'objet correspondant (par exemple, voir fi_av(3) pour une description de la façon dont les insertions asynchrones dans le vecteur d'adresses sont complétées).

Notification de Connexion
Les notifications de connexion sont des notifications de gestion de connexion utilisées pour établir ou démanteler des connexions entre points de terminaison. Il existe trois événements de notification de connexion : FI_CONNREQ, FI_CONNECTED et FI_SHUTDOWN. Les notifications de connexion sont rapportées en utilisant struct fi_eq_cm_entry :
struct fi_eq_cm_entry {
    fid_t            fid;        /* fid associé à la requête */
    struct fi_info  *info;       /* informations du point de terminaison */
    uint8_t         data[];     /* données de connexion de l'application */
};

Un événement de demande de connexion (FI_CONNREQ) indique qu'un point de terminaison distant souhaite établir une nouvelle connexion vers un point de terminaison d'écoute, ou passif. Le fid est le point de terminaison passif. Les informations concernant les capacités et attributs du point de terminaison actif demandé sont disponibles via le champ info. L'application est responsable de libérer cette structure en appelant fi_freeinfo lorsqu'elle n'en a plus besoin. Le champ connreq de fi_info référencera la demande de connexion associée à cet événement. Pour accepter une connexion, un point de terminaison doit d'abord être créé en passant une structure fi_info référençant ce champ connreq à fi_endpoint(). Ce point de terminaison est ensuite passé à fi_accept() pour compléter l'acceptation de la tentative de connexion. La création du point de terminaison est plus facilement accomplie en passant le fi_info retourné comme partie de l'événement CM à fi_endpoint(). Si la connexion doit être rejetée, le connreq est passé à fi_reject().

Toute donnée d'application échangée comme partie de la demande de connexion est placée au-delà de la structure fi_eq_cm_entry. La quantité de données disponible dépend de l'application et est limitée à l'espace de tampon fourni par l'application lorsque fi_eq_read est appelé. La quantité de données retournées peut être calculée en utilisant la valeur de retour de fi_eq_read. Notez que la quantité de données retournées est limitée par le protocole de connexion sous-jacent, et la longueur de toute donnée retournée peut inclure un remplissage de protocole. En conséquence, la longueur retournée peut être plus grande que celle spécifiée par le pair connectant.

Si une demande de connexion a été acceptée, un événement FI_CONNECTED sera généré des deux côtés de la connexion. Le côté actif – celui qui a appelé fi_connect() – peut recevoir des données utilisateur comme partie de l'événement FI_CONNECTED. Les données utilisateur sont passées au gestionnaire de connexion sur le côté passif via l'appel fi_accept. Aucune donnée utilisateur n'est fournie avec un événement FI_CONNECTED sur le côté d'écoute de la connexion.

La notification qu'un pair distant s'est déconnecté d'un point de terminaison actif se fait via l'événement FI_SHUTDOWN. La notification d'arrêt utilise struct fi_eq_cm_entry comme déclaré ci-dessus. Le champ fid pour une notification d'arrêt fait référence au fid_ep du point de terminaison actif.

Notification d'Erreur Asynchrone
Les erreurs asynchrones sont utilisées pour rapporter des problèmes avec les ressources de fabrique. Les erreurs rapportées peuvent être fatales ou transitoires, selon l'erreur, et résultent en la désactivation de la ressource. Les ressources désactivées feront échouer les opérations soumises contre elles jusqu'à ce qu'elles soient explicitement réactivées par l'application.

Des erreurs asynchrones peuvent être rapportées pour les files d'attente de complétion et les points de terminaison de tous types. Des erreurs de CQ peuvent survenir lorsque la gestion des ressources a été désactivée et que le fournisseur a détecté un débordement de file. Les erreurs de point de terminaison peuvent être le résultat de nombreuses actions, mais sont souvent associées à une opération échouée. Les opérations peuvent échouer en raison de débordements de tampon, de permissions invalides, de clés d'accès mémoire incorrectes, d'échecs de routage réseau, de problèmes d'accessibilité réseau, etc.

Les erreurs asynchrones sont rapportées en utilisant struct fi_eq_err_entry, comme défini ci-dessous. Le descripteur de fabrique (fid) associé à l'erreur est fourni comme partie des données d'erreur. Un code d'erreur est également disponible pour déterminer la cause de l'erreur.

fi_eq_sread

L'appel fi_eq_sread est l'équivalent bloquant (ou synchrone) de fi_eq_read. Il se comporte de manière similaire à l'appel non bloquant, à l'exception que les appels ne retourneront pas tant qu'un événement n'a pas été lu depuis la EQ ou qu'une erreur ou un délai d'attente ne s'est produit. Spécifier un délai d'attente négatif signifie un délai d'attente infini.

Les threads bloqués dans cette fonction retourneront à l'appelant s'ils sont signalés par une source externe. C'est vrai même si le délai d'attente ne s'est pas produit ou a été spécifié comme infini.

Il est invalide pour les applications d'appeler cette fonction si la EQ a été configurée avec un objet d'attente de FI_WAIT_NONE ou FI_WAIT_SET.

fi_eq_readerr

La fonction de lecture d'erreur, fi_eq_readerr, récupère des informations concernant toute opération asynchrone qui s'est terminée avec une erreur inattendue. fi_eq_readerr est un appel non bloquant, retournant immédiatement qu'une complétion d'erreur ait été trouvée ou non.

Les EQ sont optimisées pour rapporter les opérations qui se sont terminées avec succès. Les opérations qui échouent sont rapportées 'hors bande'. De telles opérations sont récupérées en utilisant la fonction fi_eq_readerr. Lorsqu'une opération qui se termine avec une erreur inattendue est insérée dans une EQ, elle est placée dans une file d'attente d'erreur temporaire. Tenter de lire depuis une EQ alors qu'un élément est dans la file d'attente d'erreur résulte en un échec FI_EAVAIL. Les applications peuvent utiliser ce code de retour pour déterminer quand appeler fi_eq_readerr.

Les informations d'erreur sont rapportées à l'utilisateur via struct fi_eq_err_entry. Le format de cette structure est défini ci-dessous.

struct fi_eq_err_entry {
    fid_t            fid;        /* fid associé à l'erreur */
    void            *context;    /* contexte de l'opération */
    uint64_t         data;       /* données spécifiques à la complétion */
    int              err;        /* code d'erreur positif */
    int              prov_errno; /* code d'erreur du fournisseur */
    void            *err_data;   /* données d'erreur supplémentaires */
    size_t           err_data_size; /* taille de err_data */
};

Le fid référencera le descripteur de fabrique associé à l'événement. Pour l'enregistrement mémoire, ce sera le fid_mr, la résolution d'adresse référencera un fid_av, et les événements CM feront référence à un fid_ep. Le champ context sera défini sur le contexte spécifié comme partie de l'opération.

Le champ data sera défini comme décrit dans la page man pour le type d'objet correspondant (par exemple, voir fi_av(3) pour une description de la façon dont les insertions asynchrones dans le vecteur d'adresses sont complétées).

La raison générale de l'erreur est fournie via le champ err. Des informations d'erreur spécifiques au fournisseur ou à l'opération peuvent également être disponibles via les champs prov_errno et err_data. Les utilisateurs peuvent appeler fi_eq_strerror pour convertir les informations d'erreur spécifiques au fournisseur en une chaîne imprimable à des fins de débogage.

En entrée, err_data_size indique la taille du tampon err_data en octets. En sortie, err_data_size sera défini au nombre d'octets copiés dans le tampon err_data. Les informations err_data sont généralement utilisées avec fi_eq_strerror pour fournir des détails sur le type d'erreur survenu.

À des fins de compatibilité, si err_data_size vaut 0 en entrée, ou si la fabrique a été ouverte avec une version < 1.5, err_data sera défini à un tampon de données appartenant au fournisseur. Le contenu du tampon restera valide jusqu'à un appel de lecture ultérieur sur la EQ. Les applications doivent sérialiser l'accès à la EQ lors du traitement des erreurs pour s'assurer que le tampon référencé par err_data ne change pas.

CHAMPS D'ÉVÉNEMENT

Les structures de données d'entrée de la EQ partagent de nombreux éléments en commun champs. Leurs significations sont les mêmes ou similaires pour tous les formats de structure EQ, avec des détails spécifiques décrits ci-dessous.

fid
Cela correspond au descripteur de fabric associé à l'événement. Le type de fid dépend de l'événement signalé. Pour FI_CONNREQ, il s'agira du fid de l'extrémité passive. FI_CONNECTED et FI_SHUTDOWN feront référence à l'extrémité active. FI_MR_COMPLETE et FI_AV_COMPLETE feront respectivement référence au descripteur de fabric MR ou AV. FI_JOIN_COMPLETE pointera vers le descripteur de multicast renvoyé dans le cadre de l'opération de jointure. Les applications peuvent utiliser la valeur fid->context pour récupérer le contexte associé au descripteur de fabric.
context
La valeur de context est définie sur le paramètre context spécifié avec l'opération qui a généré l'événement. Si aucun paramètre context n'est associé à l'opération, ce champ sera NULL.
data
Data est une valeur ou un ensemble d'octets spécifique à l'opération. Pour les événements de connexion, data sont les données de l'application échangées dans le cadre du protocole de connexion.
err
Ce code err est un errno de fabric positif associé à un événement. La valeur err indique la raison générale d'une erreur, si une erreur s'est produite. Voir fi_errno.3 pour une liste des codes d'erreur possibles.
prov_errno
En cas d'erreur, prov_errno peut contenir un code d'erreur spécifique au fournisseur. L'utilisation de ce champ et sa signification sont spécifiques au fournisseur. Il est destiné à être utilisé comme aide au débogage. Voir fi_eq_strerror pour plus de détails sur la conversion de cette valeur d'erreur en une chaîne lisible par l'homme.
err_data
En cas d'erreur, err_data peut référencer une quantité de données spécifique au fournisseur associée à une erreur. L'utilisation de ce champ et sa signification sont spécifiques au fournisseur. Il est destiné à être utilisé comme aide au débogage. Voir fi_eq_strerror pour plus de détails sur la conversion de ces données d'erreur en une chaîne lisible par l'homme.
err_data_size
En entrée, err_data_size indique la taille du tampon err_data en octets. En sortie, err_data_size sera défini sur le nombre d'octets copiés dans le tampon err_data. Les informations err_data sont généralement utilisées avec fi_eq_strerror pour fournir des détails sur le type d'erreur qui s'est produite.

Par souci de compatibilité, si err_data_size vaut 0 en entrée, ou si le fabric a été ouvert avec une version < 1.5, err_data sera défini sur un tampon de données appartenant au fournisseur. Le contenu du tampon restera valide jusqu'à un appel de lecture ultérieur sur l'EQ. Les applications doivent sérialiser l'accès à l'EQ lors du traitement des erreurs pour s'assurer que le tampon référencé par err_data ne change pas.

NOTES

Si une file d'événements a débordé, elle sera placée dans un état « overrun ». Les opécions d'écriture sur une EQ en débordement échoueront avec -FI_EOVERRUN. Les opérations de lecture continueront de renvoyer tous les événements valides, non corrompus, s'il y en a. Une fois que tous les événements valides ont été récupérés, toute tentative de lecture de l'EQ entraînera le renvoi d'un événement d'erreur FI_EOVERRUN. Les files d'événements en débordement sont considérées comme fatales et ne peuvent pas être utilisées pour signaler des événements supplémentaires une fois que le débordement s'est produit.

VALEURS DE RETOUR

fi_eq_open
Renvoie 0 en cas de succès. En cas d'erreur, une valeur négative correspondant au errno de fabric est renvoyée.
fi_eq_read / fi_eq_readerr
En cas de succès, renvoie le nombre d'octets lus depuis la file d'événements. En cas d'erreur, une valeur négative correspondant au errno de fabric est renvoyée. Si aucune donnée n'est disponible pour être lue depuis la file d'événements, -FI_EAGAIN est renvoyé.
fi_eq_sread
En cas de succès, renvoie le nombre d'octets lus depuis la file d'événements. En cas d'erreur, une valeur négative correspondant au errno de fabric est renvoyée. Si le délai d'attente expire ou si le thread appelant reçoit un signal et qu'aucune donnée n'est disponible pour être lue depuis la file d'événements, -FI_EAGAIN est renvoyé.
fi_eq_write
En cas de succès, renvoie le nombre d'octets écrits dans la file d'événements. En cas d'erreur, une valeur négative correspondant au errno de fabric est renvoyée.
fi_eq_strerror
Renvoie une interprétation sous forme de chaîne de caractères de l'erreur spécifique au fournisseur renvoyée avec une complétion.

Les valeurs de errno de fabric sont définies dans rdma/fi_errno.h.
