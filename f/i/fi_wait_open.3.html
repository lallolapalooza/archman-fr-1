NOM

fi_poll - Opérations d'interrogation et d'ensemble d'attente (obsolète)

fi_poll_open / fi_close (obsolète)
Ouvrir/fermer un ensemble d'interrogation
fi_poll_add / fi_poll_del (obsolète)
Ajouter/supprimer une file d'attente de complétion ou un compteur dans/un ensemble d'interrogation.
fi_poll (obsolète)
Interroger l'avancement et les événements sur plusieurs files d'attente de complétion et compteurs.
fi_wait_open / fi_close (obsolète)
Ouvrir/fermer un ensemble d'attente
fi_wait (obsolète)
Attend qu'un ou plusieurs objets d'attente d'un ensemble soient signalés.
fi_trywait
Indique quand il est sûr de bloquer sur des objets d'attente en utilisant des appels natifs du système d'exploitation.
fi_control
Contrôle le fonctionnement ou les attributs de l'ensemble d'attente.

SYNOPSIS

#include <rdma/fi_domain.h>
int fi_poll_open(struct fid_domain *domain, struct fi_poll_attr *attr,
    struct fid_poll **pollset);
int fi_close(struct fid *pollset);
int fi_poll_add(struct fid_poll *pollset, struct fid *event_fid,
    uint64_t flags);
int fi_poll_del(struct fid_poll *pollset, struct fid *event_fid,
    uint64_t flags);
int fi_poll(struct fid_poll *pollset, void **context, int count);
int fi_wait_open(struct fid_fabric *fabric, struct fi_wait_attr *attr,
    struct fid_wait **waitset);
int fi_close(struct fid *waitset);
int fi_wait(struct fid_wait *waitset, int timeout);
int fi_trywait(struct fid_fabric *fabric, struct fid **fids, size_t count);
int fi_control(struct fid *waitset, int command, void *arg);

DESCRIPTION

fi_poll_open (obsolète)

fi_poll_open crée un nouvel ensemble d'interrogation. Un ensemble d'interrogation permet une méthode optimisée pour faire progresser les opérations asynchrones sur plusieurs files d'attente de complétion et compteurs et vérifier leur complétion.

Un ensemble d'interrogation est défini avec les attributs suivants.

struct fi_poll_attr {
    uint64_t             flags;     /* drapeaux d'opération */
};
flags
Drapeaux qui définissent le fonctionnement par défaut de l'ensemble d'interrogation. L'utilisation de ce champ est réservée et doit être défini à 0 par l'appelant.

fi_close (obsolète)

L'appel fi_close libère toutes les ressources associées à un ensemble d'interrogation. L'ensemble d'interrogation ne doit être associé à aucune autre ressource avant d'être fermé, sinon l'appel retournera -FI_EBUSY.

fi_poll_add (obsolète)

Associe une file d'attente de complétion ou un compteur à un ensemble d'interrogation.

fi_poll_del (obsolète)

Supprime une file d'attente de complétion ou un compteur d'un ensemble d'interrogation.

fi_poll (obsolète)

Fait progresser toutes les files d'attente de complétion et compteurs associés à un ensemble d'interrogation et vérifie les événements. Si des événements ont pu se produire, les contextes associés aux files d'attente de complétion et/ou aux compteurs sont retournés. Les files d'attente de complétion retourneront leur contexte si elles ne sont pas vides. Le contexte associé à un compteur sera retourné si la valeur de succès ou la valeur d'erreur du compteur ont changé depuis la dernière fois que fi_poll, fi_cntr_set, ou fi_cntr_add ont été appelés. Le nombre de contextes est limité à la taille du tableau de contextes, indiqué par le paramètre count.

Notez que fi_poll indique seulement que des événements peuvent être disponibles. Dans certains cas, les fournisseurs peuvent consommer ces événements en interne, pour faire progresser, par exemple. Cela peut entraîner des retours de faux positifs de fi_poll. Les applications devraient faire avancer leur progression en se basant sur les résultats de la lecture des événements d'une file d'attente de complétion ou de la lecture des valeurs de compteur. La fonction fi_poll retournera toujours toutes les files d'attente de complétion et tous les compteurs qui ont de nouveaux événements.

fi_wait_open (obsolète)

fi_wait_open alloue un nouvel ensemble d'attente. Un ensemble d'attente permet une méthode optimisée d'attente d'événements sur plusieurs files d'attente de complétion et compteurs. Si possible, un ensemble d'attente utilise un seul objet d'attente sous-jacent qui est signalé lorsqu'une condition spécifiée se produit sur une file d'attente de complétion ou un compteur associé.

Les propriétés et le comportement d'un ensemble d'attente sont définis par struct fi_wait_attr.

struct fi_wait_attr {
    enum fi_wait_obj     wait_obj;  /* objet d'attente demandé */
    uint64_t             flags;     /* drapeaux d'opération */
};
wait_obj
Les ensembles d'attente sont associés à des objets d'attente spécifiques. Les objets d'attente permettent aux applications de bloquer jusqu'à ce que l'objet d'attente soit signalé, indiquant qu'un événement est disponible pour être lu. Les valeurs suivantes peuvent être utilisées pour spécifier le type d'objet d'attente associé à un ensemble d'attente : FI_WAIT_UNSPEC, FI_WAIT_FD, FI_WAIT_MUTEX_COND (obsolète), et FI_WAIT_YIELD.
- FI_WAIT_UNSPEC
Spécifie que l'utilisateur n'attendra sur l'ensemble d'attente qu'en utilisant des appels d'interface de tissu, tels que fi_wait. Dans ce cas, le fournisseur sous-jacent peut sélectionner l'objet d'attente le plus approprié ou le plus performant disponible, y compris des mécanismes d'attente personnalisés. Les applications qui sélectionnent FI_WAIT_UNSPEC ne sont pas garanties de récupérer l'objet d'attente sous-jacent.
- FI_WAIT_FD
Indique que l'ensemble d'attente devrait utiliser un descripteur de fichier unique comme mécanisme d'attente, tel qu'exposé à l'application. En interne, cela peut nécessiter l'utilisation de epoll pour supporter l'attente sur un seul descripteur de fichier. Les objets d'attente par descripteur de fichier doivent être utilisables dans les routines POSIX select(2) et poll(2), et Linux epoll(7) (si disponibles). Les fournisseurs signalent un objet d'attente FD en le marquant comme lisible ou avec une erreur.
- FI_WAIT_MUTEX_COND (obsolète)
Spécifie que l'ensemble d'attente devrait utiliser un mutex pthread et une variable cond comme objet d'attente.
- FI_WAIT_POLLFD
Cette option est similaire à FI_WAIT_FD, mais permet au mécanisme d'attente d'utiliser plusieurs descripteurs de fichier comme mécanisme d'attente, tel que vu par l'application. L'utilisation de FI_WAIT_POLLFD peut éliminer le besoin d'utiliser epoll pour abstraire la nécessité de vérifier plusieurs descripteurs de fichier lors de l'attente d'événements. Les descripteurs de fichier doivent être utilisables dans les routines POSIX select(2) et routines poll(2), et correspond directement à leur utilisation avec poll. Voir la section NOTES ci-dessous pour plus de détails sur l'utilisation de pollfd.
- FI_WAIT_YIELD
Indique que l'ensemble d'attente attendra sans objet d'attente mais produira (yield) à chaque attente.
flags
Indicateurs qui définissent le comportement par défaut de l'ensemble d'attente. L'utilisation de ce champ est réservée et doit être mise à 0 par l'appelant.

fi_close (obsolète)

L'appel fi_close libère toutes les ressources associées à un ensemble d'attente. L'ensemble d'attente ne doit être lié à aucune autre ressource ouverte avant sa fermeture, sinon l'appel renverra -FI_EBUSY.

fi_wait (obsolète)

Attend sur un ensemble d'attente jusqu'à ce qu'un ou plusieurs de ses objets d'attente sous-jacents soient signalés.

fi_trywait

L'appel fi_trywait a été introduit dans la version 1.3 de libfabric. Le comportement de l'utilisation d'objets d'attente natifs sans l'utilisation de fi_trywait est spécifique au fournisseur et doit être considéré comme non déterministe.

L'appel fi_trywait() est utilisé conjointement avec les appels système natifs pour bloquer sur des objets d'attente, tels que les descripteurs de fichiers. L'application doit appeler fi_trywait et obtenir une valeur de retour de FI_SUCCESS avant de bloquer sur un objet d'attente natif. Ne pas le faire peut entraîner le non-signalement de l'objet d'attente, et l'application pourrait ne pas observer les événements souhaités. Le pseudo-code suivant illustre l'utilisation de fi_trywait en conjonction avec l'appel OS select(2).

fi_control(&cq->fid, FI_GETWAIT, (void *) &fd);
FD_ZERO(&fds);
FD_SET(fd, &fds);
while (1) {
    if (fi_trywait(&cq, 1) == FI_SUCCESS)
        select(fd + 1, &fds, NULL, &fds, &timeout);
    do {
        ret = fi_cq_read(cq, &comp, 1);
    } while (ret > 0);
}

fi_trywait() retournera FI_SUCCESS s'il est sûr de bloquer sur les objets d'attente correspondant aux descripteurs de fabric, ou -FI_EAGAIN s'il y a des événements en file d'attente sur le descripteur de fabric ou si le blocage pouvait bloquer l'application.

L'appel prend un tableau de descripteurs de fabric. Pour chaque objet d'attente qui sera passé à la routine d'attente native, le descripteur de fabric correspondant doit d'abord être passé à fi_trywait. Tous les descripteurs de fabric passés dans un seul appel fi_trywait doivent utiliser le même type d'objet d'attente sous-jacent.

Les types de descripteurs de fabric suivants peuvent être passés à fi_trywait : files d'attente d'événements, files d'attente de complétion, compteurs et ensembles d'attente. Les applications qui souhaitent utiliser des appels d'attente natifs doivent sélectionner des objets d'attente spécifiques lors de l'allocation de telles ressources. Par exemple, en définissant la valeur wait_obj de l'attribut de création de l'élément à FI_WAIT_FD.

Dans le cas où l'objet d'attente à vérifier appartient à un ensemble d'attente, seul l'ensemble d'attente lui-même doit être passé à fi_trywait. Les ressources de fabric associées à l'ensemble d'attente ne le sont pas.

En recevant une valeur de retour de -FI_EAGAIN de fi_trywait, une application doit lire toutes les complétions et événements mis en file d'attente, et appeler fi_trywait à nouveau avant de tenter de bloquer. Les applications peuvent utiliser un ensemble de sondage (poll set) de fabric pour identifier les files d'attente de complétion et les compteurs qui pourraient nécessiter un traitement.

fi_control

L'appel fi_control est utilisé pour accéder aux détails spécifiques du fournisseur ou de l'implémentation d'un fid qui prend en charge les appels bloquants, tels que les ensembles d'attente, les files d'attente de complétion, les compteurs et les files d'attente d'événements. L'accès à l'ensemble d'attente ou au fid doit être sérialisé sur tous les appels lorsque fi_control est invoqué, car il peut rediriger l'implémentation des opérations de l'ensemble d'attente. Les commandes de contrôle suivantes sont utilisables avec un ensemble d'attente ou un fid.

FI_GETWAIT (void **)
Cette commande permet à l'utilisateur de récupérer l'objet d'attente de bas niveau associé à un ensemble d'attente ou à un fid. Le format de l'ensemble d'attente est spécifié lors de la création de l'ensemble d'attente, via les attributs de l'ensemble d'attente. Le paramètre arg de fi_control doit être une adresse où un pointeur vers l'objet d'attente renvoyé sera écrit. Il doit s'agir d'un ’int *’ pour FI_WAIT_FD, `struct fi_mutex_cond' pour FI_WAIT_MUTEX_COND (obsolète), ou `struct fi_wait_pollfd' pour FI_WAIT_POLLFD. La prise en charge de FI_GETWAIT est spécifique au fournisseur.
FI_GETWAITOBJ (enum fi_wait_obj *)
Cette commande renvoie le type d'objet d'attente associé à un ensemble d'attente ou à un fid.

VALEURS DE RETOUR

Retourne FI_SUCCESS en cas de succès. En cas d'erreur, une valeur négative correspondant à l'errno de fabric est retournée.

Les valeurs d'errno de fabric sont définies dans rdma/fi_errno.h.

fi_poll
En cas de succès, si des événements sont disponibles, renvoie le nombre d'entrées écrites dans le tableau de contexte.

NOTES

Dans de nombreuses situations, les appels bloquants peuvent devoir attendre des signaux envoyés à un certain nombre de descripteurs de fichiers. C'est le cas, par exemple, pour les fournisseurs basés sur des sockets, tels que tcp et udp, ainsi que pour les fournisseurs utilitaires tels que multi-rail. Pour simplifier, lorsque epoll est disponible, il peut être utilisé pour limiter le nombre de descripteurs de fichiers qu'une application doit surveiller. L'utilisation d'epoll peut également être requise pour prendre en charge FI_WAIT_FD.

Cependant, afin de prendre en charge l'attente sur plusieurs descripteurs de fichiers sur les systèmes où le support d'epoll n'est pas disponible, ou où les performances d'epoll pourraient avoir un impact négatif sur les performances, FI_WAIT_POLLFD offre ce mécanisme. Une différence significative entre l'utilisation d'objets d'attente POLLFD et FD est qu'avec FI_WAIT_POLLFD, les descripteurs de fichiers peuvent changer dynamiquement. Par exemple, les descripteurs de fichiers associés à l'ensemble d'attente d'une file d'attente de complétion peuvent changer à mesure que les associations d'endpoints avec la CQ sont ajoutées et supprimées.

La structure fi_wait_pollfd est utilisée pour récupérer tous les descripteurs de fichiers pour les fids utilisant FI_WAIT_POLLFD pour prendre en charge les appels bloquants.

struct fi_wait_pollfd {
    uint64_t      change_index;
    size_t        nfds;
    struct pollfd *fd;
};
change_index
Le change_index peut être utilisé pour déterminer s'il y a eu des changements dans la liste des descripteurs de fichiers. Chaque fois qu'un descripteur de fichier est ajouté, supprimé, ou que ses événements sont mis à jour, ce champ est incrémenté par le fournisseur. Les applications souhaitant attendre directement sur des descripteurs de fichiers doivent mettre en cache la valeur change_index. Avant de bloquer sur des événements de descripteurs de fichiers, l'application doit utiliser fi_control() pour récupérer l'index de changement actuel et le comparer à sa valeur mise en cache. Si les valeurs diffèrent, alors l'application doit mettre à jour sa liste de descripteurs de fichiers avant de bloquer.
nfds
En entrée de fi_control(), cela indique le nombre d'entrées dans le tableau struct pollfd *. En sortie, il sera défini sur le nombre d'entrées nécessaires pour stocker le nombre actuel de descripteurs de fichiers. Si la valeur d'entrée est inférieure à la valeur de sortie, fi_control() renverra l'erreur -FI_ETOOSMALL. Notez que la définition de nfds = 0 permet un moyen efficace de vérifier le change_index.
fd
Ceci pointe vers un tableau d'entrées struct pollfd. Le nombre d'entrées est spécifié par le champ nfds. Si le nombre d'entrées nécessaires est inférieur ou égal au nombre d'entrées disponibles, le tableau struct pollfd sera rempli avec une liste de descripteurs de fichiers et les événements correspondants qui peuvent être utilisés dans les appels select(2) et poll(2).

Le change_index est mis à jour uniquement lorsque les descripteurs de fichiers associés à l'ensemble de fichiers pollfd ont changé. La vérification du change_index est une étape supplémentaire nécessaire lors de l'utilisation directe des objets d'attente FI_WAIT_POLLFD. L'utilisation de la fonction fi_trywait() est toujours requise si l'on accède directement aux objets d'attente.
