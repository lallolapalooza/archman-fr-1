DESCRIPTIO

N

Les files d'attente d'achèvement sont utilisées pour signaler des événements associés aux transferts de données. Elles sont associées aux envois et réceptions de messages, au RMA, aux opérations atomiques, aux messages étiquetés et aux événements déclenchés. Les événements signalés sont généralement associés à un point de terminaison de fabrique, mais peuvent aussi faire référence à des régions mémoire utilisées comme cible d'une opération RMA ou

atomique.

fi_cq_ope

n

fi_cq_open alloue une nouvelle file d'attente d'achèvement. Contrairement aux files d'attente d'événements, les files d'attente d'achèvement sont associées à un domaine de ressources et peuvent être entièrement déchargées sur le matériel du

fournisseur.

Les files d'attente d'achèvement peuvent être associées à un objet d'attente spécifique. Les objets d'attente permettent aux applications de se bloquer jusqu'à ce que l'objet d'attente soit signalé, indiquant qu'un achèvement est disponible pour être lu. Les utilisateurs peuvent utiliser fi_control pour récupérer l'objet d'attente sous-jacent associé à une file d'attente d'achèvement, afin de l'utiliser dans d'autres appels système. Les valeurs suivantes peuvent être utilisées pour spécifier le type d'objet d'attente associé à un CQ : FI_WAIT_NONE, FI_WAIT_UNSPEC, FI_WAIT_SET, FI_WAIT_FD, FI_WAIT_MUTEX_COND (obsolète), et FI_WAIT_YIELD. La valeur par défaut est
FI_WAIT_NONE.

fi_cq_sreadfrom.

Dans ce cas, le fournisseur sous-jacent peut sélectionner l'objet d'attente le plus approprié ou le plus performant disponible, y compris des mécanismes d'attente personnalisés. Les applications qui sélectionnent FI_WAIT_UNSPEC ne sont pas garanties de récupérer l'objet d'attente
sous-jacent.

Le seuil indique le nombre d'entrées qui doivent être mises en file dans le CQ avant que l'attente ne soit

FI_WAIT_NONE.

à travers plusieurs files d'événements et de complétions. Ce champ est ignoré si wait_obj n'est pas FI_WAIT_SET.

fi_clos

e

L'appel fi_close libère toutes les ressources associées à une file de complétion. Toutes les complétions restant sur le CQ lors de sa fermeture sont

perdues.

Lors de la fermeture du CQ, il ne doit y avoir aucun point de terminaison ouvert, aucun co

ntexte de transmission ni aucun contexte de réception associé au CQ. Si des ressources sont
toujours associées au CQ lors de la tentative de fermeture, l'appel retournera -FI_EBUSY.

fi_contro

l

L'appel fi_control est utilisé pour accéder aux détails spécifiques au fournisseur ou à l'implémentation de la file de complétion. L'accès au CQ doit être sérialisé à travers tous les appels lorsque fi_control est invoqué, car il peut rediriger l'implémentation des opérations de CQ. Les commandes de contrôle suivantes sont utilisables avec un

CQ.
FI_GETWAIT (void
**)
Cette commande permet à l'utilisateur de récupérer l'objet d'attente de bas niveau associé au CQ. Le
format de l'objet d'attente est spécifié lors de la création du CQ, à travers les attributs du CQ.
Le paramètre arg de fi_control doit être une adresse où un pointeur vers l'objet d'attente ret
ourné sera écrit. Voir fi_eq.3 pour plus de détails sur l'utilisation de fi_control avec FI_GETWAIT.

fi_cq_rea

d

L'opération fi_cq_read effectue une lecture non bloquante des données de complétion à partir du CQ. Le format de l'événement de complétion est déterminé à l'aide de l'option fi_cq_format qui a été spécifiée lorsque le CQ a été ouvert. Plusieurs complétions peuvent être récupérées depuis un CQ en un seul appel. Le nombre maximal d'entrées à retourner est limité au paramètre count spécifié, le nombre d'entrées lues avec succès depuis le CQ étant retourné par l'appel. (Voir la section des valeurs de retour ci-dessous.) Une valeur count de 0 peut être utilisée pour faire avancer le progrès sur les points de terminaison associés lorsque le progrès manuel est

activé.

Les CQ sont optimisés pour signaler les opérations qui se sont terminées avec succès. Les opérations qui échouent sont signalées « hors bande » (out of band). De telles opérations sont récupérées à l'aide d

e la fonction fi_cq_readerr. Lorsqu'une opération qui s'est terminée avec une erreur inattendue est rencontrée, elle est placée dans une file d'erreurs temporaire. Tenter de lire depuis un CQ alors qu'u
n élément est dans la file d'erreurs entraîne l'échec de fi_cq_read avec un code de retour de -FI_EAVAIL. Les applications peuvent utiliser ce code de retour pour déterminer quand appeler fi_cq_readerr.

fi_cq_readfro

m

L'appel fi_cq_readfrom se comporte de manière identique à fi_cq_read, à l'exception qu'il permet au CQ de retourner des informations d'adresse source à l'utilisateur pour toute donnée reçue. Les données d'adresse source ne sont disponibles que pour les points de terminaison configurés avec la capacité FI_SOURCE. Si fi_cq_readfrom est appelé sur un point de terminaison pour lequel les données d'adressage source ne sont pas disponibles, l'adresse source sera définie à FI_ADDR_NOTAVAIL. Le nombre d'entrées src_addr en entrée doit être le même que le paramètre

count.

Les données d'adressage source retournées sont converties depuis l'adresse native utilisée par le fabric sous-jacent en un fi_addr_t, qui peut être utilisé dans les opérations de transmission. Dans la plupart des cas, le retour d'un fi_addr_t nécessite que l'adresse source ait déjà été insérée dans le vecteur d'adresses associé au point de terminaison récepteur. C'est le cas pour les vecteurs d'adresses de type FI_AV_TABLE. Dans certains fournisseurs, lorsque FI_AV_MAP est utilisé, les adresses sources peuvent être converties algorithmiquement en un fi_addr_t utilisable, même si l'adresse source n'a pas été insérée dans le vecteur d'adresses. Cela est permis par l'API, car cela permet au fournisseur d'éviter la recherche d'adresse dans le traitement des messages reçus. Dans aucun cas les fournisseurs n'insèrent d'adresses dans un AV en dehors d'un appel de l'application à fi_av_insert ou un appel

similaire.

Pour les points de terminaison alloués avec la capacité FI_SOURCE_ERR, si l'adresse source ne peut pas être convertie en une valeur fi_addr_t valide, fi_cq_readfrom retournera -FI_EAVAIL, même si les données ont été reçues avec succès. La complétion sera alors signalée à travers fi_cq_readerr avec le code d'erreur -FI_EADDRNOTAVAIL. Voir fi_cq_readerr pour les

détails.

Si FI_SOURCE est spécifié sans FI_SOURCE_ERR, les adresses sources qui ne peuvent pas être mappées vers un fi_addr_t utilisable seront signalées comme FI_ADDR_NOTAVAI

L
.

fi_cq_sread /

fi_cq_sreadfrom

Les appels fi_cq_sread et fi_cq_sreadfrom sont les opérations bloquantes équivalentes à fi_cq_read et fi_cq_readfrom. Leur comportement est similaire aux appels non bloquants, à l'exception que les appels ne retourneront pas tant qu'une complétion n'a pas été lue depuis le CQ ou qu'une erreur ou un délai d'attente ne se

produit.

Les threads bloqués dans cette fonction retourneront à l'appelant s'ils sont signalés par une source externe. C'est vrai même si le délai d'attente ne s'est pas produit ou a été spécifié comme

infini.

Il est invalide pour les applications d'appeler ces

fonctions si le CQ a été configuré avec un obje
t d'attente de type FI_WAIT_NONE ou FI_WAIT_SET.

fi_cq_reader

r

La fonction de lecture d'erreur, fi_cq_readerr, récupère des informations concernant toute opération asynchrone qui s'est terminée avec une erreur inattendue. fi_cq_readerr est un appel non bloquant, retournant immédiatement que ce qu'une complétion d'erreur ait été trouvée ou

non.

Les informations d'erreur sont signalées à l'utilisateur à travers la structure fi_cq_err_entry. Le format de cette structure est défini

ci-dessous. 
struct fi_cq_err_entry {
    void     *op_context; /* operation context */
    uint64_t flags;       /* completion flags */
    size_t   len;         /* size of received data */
    void     *buf;        /* receive data buffer */
    uint64_t data;        /* completion data */
    uint64_t tag;         /* message tag */
    size_t   olen;        /* overflow length */
    int      err;         /* positive error code */
    int      prov_errno;  /* provider error code */
    void    *err_data;    /*  error data */
    size_t   err_data_size; /* size of err_data */
    fi_addr_t src_addr; /* error source address
*/
}
;

La raison générale de l'erreur est fournie à travers le champ err. Des informations d'erreur spécifiques au fournisseur peuvent également être disponibles à travers les champs prov_errno et err_data. Les utilisateurs peuvent appeler fi_cq_strerror pour convertir les informations d'erreur spécifiques au fournisseur en une chaîne imprimable à des fins de débogage. Voir les détails des champs ci-dessous pour plus d'informations sur l'utilisation de err_data et

err_data_size.

Notez que des complétions d'erreur sont générées pour toutes les opérations, y compris celles pour lesquelles une complétion n'a pas été demandée (par ex. un point de terminaison est configuré avec FI_SELECTIVE_COMPLETION, mais la requête n'avait pas l'indicateur FI_COMPLETION défini). Dans de tels cas, les fournisseurs renverront autant d'informations que ce que le logiciel et le matériel sous-jacents rendent disponibles concernant l'échec, les autres champs seront définis à NULL ou 0. Cela inclut la valeur op_context, qui n'a peut- être pas été fournie ou qui a été ignorée en entrée dans le cadre du

transfert.

Les codes d'erreur de complétion notables sont donnés

ci-dessous.
FI_EADDRNOTAV
AIL

ue le transfert de données a été reçu et traité avec succès, les champs fi_cq_err_entry contenant des informations sur la complétion. Le champ err_data sera défini sur les données d'adresse source. L'adresse source se
ra dans le même format que celui spécifié via le champ addr_format de fi_info pour le domaine ouvert. Celle-ci peut être passée directement à un appel fi_av_insert pour ajouter l'adresse source au vecteur d'adresses.

Pour les versions d'API 1.20 et ultérieures, si l'EP est configuré avec FI_AV_AUTH_KEY, src_addr sera défini sur le handle de clé d'autorisation fi_addr_t ou un ID de clé d'autorisation défini par l'utilisateur correspondant au transfert de données entrant. Sinon, la valeur sera définie à FI_ADDR_NOTAVAI

L
.

SÉMANTIQUE D'ÉVÉNEMENTS D'ACHÈVEMENT

Libfabric définit plusieurs « niveaux » d'achèvement, identifiés à l'aide de drapeaux opérationnels. Chaque drapeau indique le moment le plus tôt auquel un événement d'achèvement peut être généré par un fournisseur, et les hypothèses qu'une application peut faire lors du traitement d'un achèvement. Les drapeaux opérationnels sont définis ci-dessous, avec un exemple de la manière dont un fournisseur pourrait implémenter la sémantique. Notez que seule la conformité à la sémantique est requise du fournisseur, et non l'implémentation. Les fournisseurs peuvent implémenter des sémantiques d'achèvement plus strictes que nécessaire pour une opération donnée, mais seul le comportement défini par le niveau d'achèvement est garanti.

Pour aider à comprendre les différences conceptuelles entre les niveaux d'achèvement, considérez l'envoi d'une lettre. Placer la lettre dans la boîte aux lettres locale pour la collecte est similaire à « achèvement d'injection ». Avoir la lettre collectée et déposée dans la boîte aux lettres de destination est équivalent à « achèvement de transmission ». La sémantique « achèvement de livraison » est une garantie plus forte, avec une personne à la destination signant pour la lettre. Cependant, la personne qui a signé pour la lettre n'est pas nécessairement le destinataire prévu. L'option « achèvement de correspondance » est similaire à l'achèvement de livraison, mais exige que le destinataire prévu signe pour la lettre.

Le niveau « achèvement de validation » a une sémantique différente des niveaux mentionnés précédemment. L'achèvement de validation serait plus proche de la lettre arrivant à destination et étant placée dans un coffre-fort ignifuge.

Les drapeaux opérationnels pour les niveaux d'achèvement décrits sont définis ci-dessous.

FI_INJECT_COMPLETE
Indique qu'un achèvement doit être généré lorsque le(s) tampon(s) source peuvent être réutilisés. Un achèvement garantit que les tampons ne seront plus lus et que l'application peut les récupérer. Aucune autre garantie n'est donnée quant à l'état de l'opération.

Exemple : Un fournisseur peut générer cet événement d'achèvement après avoir copié le tampon source dans un tampon réseau, soit en mémoire hôte, soit sur la NIC. Un achèvement d'injection n'indique pas que les données ont été transmises sur le réseau, et une erreur locale pourrait survenir après la génération de l'événement d'achèvement, ce qui pourrait empêcher leur transmission.

L'achèvement d'injection permet le signalement d'achèvement le plus rapide (et donc la réutilisation des tampons), mais fournit les garanties les plus faibles contre les erreurs réseau.

Remarque : Ce drapeau est utilisé pour contrôler le moment où une entrée d'achèvement est insérée dans une file d'achèvement. Il ne s'applique pas aux opérations qui ne génèrent pas d'entrée de file d'achèvement, comme l'opération fi_inject, et n'est pas soumis à la restriction de limite de message inject_size.

FI_TRANSMIT_COMPLETE
Indique qu'un achèvement doit être généré lorsque l'opération de transmission est terminée par rapport au fournisseur local. Le comportement exact dépend du type de point de terminaison.

Pour les points de terminaison fiables :

Indique qu'un achèvement doit être généré lorsque l'opération a été délivrée au point de terminaison pair. Un achèvement garantit que l'opération ne dépend plus de la fabrique ni des ressources locales. L'état de l'opération au point de terminaison pair n'est pas défini.

Exemple : Un fournisseur peut générer un événement d'achèvement de transmission lors de la réception d'un accusé de réception du point de terminaison pair. L'état du message chez le pair est inconnu et peut être mis en tampon dans la NIC cible au moment où l'accusé de réception a été généré.

Pour les points de terminaison non fiables :

Indique qu'un achèvement doit être généré lorsque l'opération a été délivrée à la fabrique. Un achèvement garantit que l'opération ne dépend plus des ressources locales. L'état de l'opération au sein de la fabrique n'est pas défini.

FI_DELIVERY_COMPLETE
Indique qu'un achèvement ne doit pas être généré tant qu'une opération n'a pas été traitée par le(s) point(s) de terminaison de destination. Un achèvement garantit que le résultat de l'opération est disponible ; cependant, des étapes supplémentaires peuvent être nécessaires à la destination pour récupérer les résultats. Par exemple, une application peut avoir besoin de fournir des tampons de réception afin de récupérer les messages mis en tampon par le fournisseur.

L'achèvement de livraison indique que le message a été traité par le pair. Si un tampon d'application était prêt à recevoir les résultats du message à son arrivée, alors l'achèvement de livraison indique que les données ont été placées dans le tampon de l'application.

Ce mode d'achèvement ne s'applique qu'aux points de terminaison fiables. Pour les opérations qui renvoient des données à l'initiateur, comme une lecture RMA ou un atomic-fetch, le point de terminaison source est également considéré comme un point de terminaison de destination. C'est le mode d'achèvement par défaut pour de telles opérations.

FI_MATCH_COMPLETE
Indique qu'un achèvement ne doit être généré qu'après que l'opération a été appariée à un tampon spécifié par l'application. Les opérations utilisant cette sémantique d'achèvement dépendent de l'application à la cible qui réclame le message ou les résultats. Par conséquent, l'achèvement de correspondance peut impliquer des accusés de réception supplémentaires au niveau du fournisseur ou des délais importants. Cependant, ce modèle d'achèvement permet aux applications pairs de synchroniser leur exécution. De nombreux fournisseurs peuvent ne pas prendre en charge cette sémantique.
FI_COMMIT_COMPLETE
Indique qu'un achèvement ne doit pas être généré (localement ou chez le pair) tant que le résultat d'une opération n'a pas été rendu persistant. Un achèvement garantit que le résultat est à la fois disponible et durable, en cas de panne de courant.

Ce mode d'achèvement ne s'applique qu'aux opérations ciblant des régions de mémoire persistante sur des points de terminaison fiables. Ce mode d'achèvement est expérimental.

FI_FENCE
Ceci n'est pas un niveau d'achèvement, mais joue un rôle dans l'ordonnancement des achèvements entre des opérations qui ne seraient normalement pas ordonnées. Une opération marquée avec le drapeau FI_FENCE et toutes les opérations soumises après l'opération clôturée sont différées jusqu'à ce que toutes les opérations précédentes ciblant le même point de terminaison pair soient terminées. De plus, l'achèvement de l'opération clôturée indique que les opérations précédentes ont atteint le même niveau d'achèvement que l'opération clôturée. Par exemple, si une opération est soumise avec FI_DELIVERY_COMPLETE | FI_FENCE, alors son achèvement indique que les opérations précédentes ont satisfait la sémantique requise pour FI_DELIVERY_COMPLETE. C'est vrai même si l'opération précédente a été soumise avec un niveau d'achèvement inférieur, comme FI_TRANSMIT_COMPLETE ou FI_INJECT_COMPLETE.

Notez qu'un achèvement généré pour une opération soumise avant l'opération clôturée ne garantit que le niveau d'achèvement initialement demandé a été atteint. C'est l'achèvement de l'opération clôturée qui garantit que les sémantiques supplémentaires ont été satisfaites.

Les sémantiques d'achèvement ci-dessus sont définies par rapport à l'initiateur de l'opération. Les différentes sémantiques sont utiles pour décrire quand l'initiateur peut réutiliser un tampon de données, et garantissent l'état qu'un transfert doit atteindre avant qu'un achèvement ne soit généré. Cela permet aux applications de déterminer un traitement d'erreur approprié en cas de défaillances de communication.

SÉMANTIQUE D'ACHÈVEMENT À LA CIBLE

La sémantique d'achèvement à la cible est utilisée pour déterminer quand les données à la cible sont visibles par l'application pair. La visibilité indique qu'une lecture mémoire au même adresse qui était la cible d'un transfert de données renverra les résultats du transfert. La cible d'un transfert peut être identifiée par l'initiateur, comme c'est le cas pour les opérations RMA et atomiques, ou déterminée par la cible, par exemple en fournissant un tampon de réception appariant. La visibilité globale indique que les résultats sont disponibles quelle que soit l'origine de la lecture mémoire. Par exemple, la lecture peut provenir d'un processus s'exécutant sur un CPU hôte, elle peut être accessible par un transfert de données ultérieur via la fabrique, ou lue depuis un périphérique pair tel qu'un GPU.

En termes de sémantique d'achèvement, la visibilité indique généralement que le transfert remplit les exigences FI_DELIVERY_COMPLETE du point de vue de la cible. La sémantique d'achèvement de la cible peut être, mais n'est pas nécessairement, liée à la sémantique d'achèvement spécifiée par l'initiateur du transfert.

Souvent, les processus de la cible ne déclarent pas explicitement une sémantique d'achèvement souhaitée et s'appuient plutôt sur la sémantique par défaut. Le comportement par défaut est basé sur plusieurs facteurs, y compris :

•
si un événement d'achèvement est même généré à la cible
•
le type de transfert impliqué (par ex. msg vs RMA)
•
les garanties d'ordonnancement des données et des messages du point de terminaison
•
les propriétés du tampon de mémoire ciblé
•
la sémantique d'achèvement spécifiée par l'initiateur

De manière générale, les sémantiques d'achèvement de la cible sont regroupées en fonction du fait que le transfert génère ou non un événement d'achèvement à la cible. Cela inclut l'écriture d'une entrée CQ ou la mise à jour d'un compteur d'achèvement. Dans les cas d'utilisation courants, les transferts utilisant une interface de message (FI_MSG ou FI_TAGGED) génèrent généralement des événements de cible, tandis que les transferts impliquant une interface RMA (FI_RMA ou FI_ATOMIC) souvent non. Il y a des exceptions à ces deux cas, selon les liaisons point de terminaison à CQ et compteur et les drapeaux opérationnels. Par exemple, les écritures RMA transportant des données CQ distantes généreront un événement d'achèvement à la cible, et sont fréquemment utilisées pour transmettre la visibilité à l'application cible. Les directives générales pour la sémantique côté cible sont décrites ci-dessous, suivies des exceptions qui modifient ce comportement.

Par défaut, les achèvements générés à la cible indiquent que les données transférées sont immédiatement disponibles pour être lues depuis le tampon de la cible. C'est-à-dire que la cible voit une sémantique FI_DELIVERY_COMPLETE (ou meilleure), même si l'initiateur a demandé une sémantique inférieure. Pour les applications utilisant uniquement des tampons de données alloués depuis la mémoire hôte, c'est souvent suffisant.

Pour les opérations qui ne génèrent pas un événement de complétion à la cible, la visibilité des données à la cible peut devoir être inférée sur la base d'opérations ultérieures qui génèrent effectivement des complétions à la cible. En l'absence d'une complétion à la cible, lorsqu'une complétion d'une opération est écrite à l'initiateur, la sémantique de visibilité de l'opération à la cible s'aligne sur la sémantique de complétion de l'initiateur. Par exemple, si une opération RMA se termine à l'initiateur comme soit FI_INJECT_COMPLETE soit FI_TRANSMIT_COMPLETE, la visibilité des données à la cible n'est pas

garantie.

Un ou plusieurs des mécanismes suivants peuvent être utilisés par le processus cible pour garantir que les résultats d'un transfert de données qui n'a pas généré de complétion à la cible sont désormais visibles. Cette liste n'est pas exhaustive de toutes les options, mais définit des utilisations courantes. Dans les descriptions ci-dessous, le premier transfert ne résulte pas en un événement de complétion à la cible, mais est éventuellement suivi d'un transfert qui en génère

un.
•
Si l'endpoint garantit l'ordre des messages entre deux transferts, la complétion à la cible d'un second transfert indiquera que les données du premier transfert sont disponibles. Par exemple, si l'endpoint supporte l'ordre d'envoi après écriture (FI_ORDER_SAW), alors une complétion de réception correspondant à l'envoi indiquera que les données écrites sont disponibles. Ceci est indépendant de la sémantique de complétion de l'initiateur pour l'écriture ou l'envoi. Lorsque l'ordre est garanti, le second transfert peut être mis en file d'attente auprès du fournisseur immédiatement après la mise en file du
premier.
•
Si l'endpoint ne garantit pas l'ordre des messages, l'initiateur doit prendre des mesures supplémentaires pour assurer la visibilité. Si l'initiateur demande la sémantique FI_DELIVERY_COMPLETE pour la première opération, l'initiateur peut attendre que l'opérations se termine localement. Une fois la complétion lue, la complétion à la cible d'un second transfert indiquera que les données du premier transfert sont
visibles.
•
Alternativement, si l'ordre des messages n'est pas garanti par l'endpoint, l'initiateur peut utiliser les indicateurs FI_FENCE et FI_DELIVERY_COMPLETE sur le second tr
ansfert de données pour forcer les premiers transferts à satisfaire la sémantique FI_DELIVERY_COMPLETE. Si le second transfert génère une complétion à la cible, cela
indiquera que les données sont visibles. Sinon, une complétion à la cible pour tout transfert après l'opération clôturée indiquera que les données sont visibles.

Les sémantiques ci-dessus s'appliquent aux transferts ciblant des tampons de mémoire hôte traditionnels. Cependant, le comportement peut différer lorsque la mémoire de dispositif et/ou la mémoire persistante est impliquée (bits de capacité FI_HMEM et FI_PMEM). Lorsque la mémoire hétérogène est impliquée, le concept de domaines de mémoire entre en jeu. Les domaines de mémoire identifient la séparation physique de la mémoire, qui peut ou non être accessible à travers le même espace d'adressage virtuel. Voir la page de manuel fi_mr(3) pour plus de détails sur les domaines de

mémoire.

L'ordre des complétions et la visibilité des données ne sont bien définis que pour les transferts ciblant le même domaine de mémoire. Les applications doivent être conscientes des différences d'ordre et de visibilité lorsque les transferts ciblent différents domaines de mémoire. De plus, les applications doivent également se soucier du domaine de mémoire dans lequel les complétions elles-mêmes sont écrites et s'il diffère du domaine de mémoire ciblé par un transfert. Dans certaines situations, soit le fournisseur soit l'application peuvent avoir besoin d'appeler des API spécifiques au dispositif pour synchroniser ou vider les caches de mémoire du dispositif afin d'obtenir la visibilité des données

souhaitée.

Lorsque la mémoire hétérogène est utilisée, la sémantique de complétion à la cible par défaut pour les transferts qui génèrent une complétion à la cible est toujours FI_DELIVERY_COMPLETE, cependant, les applications devraient être conscientes qu'il peut y avoir un impact négatif sur les performances globales pour les fournisseurs afin de satisfaire cette

exigence.

Par exemple, un processus cible peut utiliser un GPU pour accélérer des calculs. Une région de mémoire mappant vers la mémoire sur le GPU peut être exposée aux pairs soit comme une cible RMA soit publiée localement comme un tampon de réception. Dans ce cas, l'application est concernée par deux domaines de mémoire – mémoire système et mémoire GPU. Les complétions sont écrites dans la mémoire

système.

En continuant l'exemple, un processus pair envoie un message étiqueté. Ce message est apparié avec le tampon de réception situé dans la mémoire GPU. La NIC copie les données du réseau vers le tampon de réception et écrit une entrée dans la file de complétion. Notez que les deux domaines de mémoire ont été accédés dans le cadre de ce transfert. Les données du message ont été dirigées vers la mémoire GPU, mais la complétion est allée vers la mémoire hôte. Comme des domaines de mémoire séparés peuvent ne pas être synchronisés les uns avec les autres, il est possible que le CPU hôte voie et traite l'entrée de complétion avant que le transfert vers la mémoire GPU ne soit visible soit pour le GPU hôte soit même pour le logiciel s'exécutant sur le GPU. Du point de vue du fournisseur, la visibilité de la complétion n'implique pas la visibilité des données écrites dans le domaine de mémoire du

GPU.

La sémantique de complétion par défaut à la cible application pour les opérations de message est FI_DELIVERY_COMPLETE. Une implémentation de fournisseur anticipée dans cette situation est que le logiciel du fournisseur s'exécutant sur le CPU hôte intercepte l'entrée CQ, détecte que les données ont atterri dans la mémoire hétérogène, et effectue la synchronisation ou l'opération de vidage nécessaire du dispositif avant de remonter la complétion à l'application. Cela garantit que les données sont visibles pour le CPU et le logiciel GPU avant que l'application ne traite la

complétion.

En plus du coût du logiciel du fournisseur interceptant les complétions et vérifiant si un transfert ciblait de la mémoire hétérogène, la synchronisation du dispositif elle-même peut impacter les performances. Par conséquent, les applications peuvent demander une sémantique de complétion plus basse lors de la publication des réceptions. Cela indique au fournisseur que l'application sera responsable du traitement de toute opération de vidage spécifique au dispositif qui pourrait être nécessaire. Voir fi_msg(3)

FLAGS.

Pour les transferts de données qui ne génèrent pas une complétion à la cible, tels que RMA ou atomiques, il est de la responsabilité de l'application de s'assurer que tous les tampons cibles répondent aux exigences de visibilité nécessaires de l'application. Les méthodes à puces mentionnées précédemment pour notifier la cible que les données sont visibles peuvent ne pas être suffisantes, car le logiciel du fournisseur à la cible pourrait manquer du contexte nécessaire pour assurer la visibilité. Cela implique que l'application puisse avoir besoin d'appeler directement les API de synchronisation/vidage du

dispositif.

Par exemple, une application pair pourrait effectuer plusieurs écritures RMA ciblant des tampons de mémoire GPU. Si le fournisseur décharge les opérations RMA dans la NIC, le logiciel du fournisseur à la cible ne sera pas au courant que les opérations RMA ont eu lieu. Si le pair envoie un message à l'application cible indiquant que les opérations RMA sont terminées, l'application doit s'assurer que les données RMA sont visibles pour le CPU hôte ou le GPU avant d'exécuter du code qui accède aux données. La complétion à la cible d'avoir reçu le message envoyé n'est pas suffisante, même si l'ordre d'envoi après écriture est

supporté.

La plupart des sémantiques de complétion à la cible pour la mémoire hétérogène correspondent à FI_TRANSMIT_COMPLETE ou FI_DELIVERY_COMPLETE. La mémoire persistante (capacité FI_PMEM), cependant, est souvent utilisée avec la sémantique FI_COMMIT_COMPLETE. Les concepts de complétion hétérogènes s'appliquent

toujours.

Pour les transferts marqués par l'initiateur avec FI_COMMIT_COMPLETE, une complétion à la cible indique que les résultats sont visibles et durables. Pour les transferts ciblant la mémoire persistante, mais utilisant une sémantique de complétion différente à l'initiateur, la visibilité à la cible est similaire à celle décrite ci-dessus. La durabilité n'est associée qu'aux transferts marqués avec FI_COMMIT_COMPLETE

.

Pour les transferts ciblant la mémoire persistante qui demandent FI_DELIVERY_COMPLETE, alors une complétion, soit à l'initiateur soit à la cible, indique que les données sont visibles. La visibilité à la cible peut être transmise en utilisant l'un des mécanismes décrits ci-dessus – générer une complétion à la cible, envoyer un message depuis l'initiateur, etc. De même, si l'initiateur a demandé FI_TRANSMIT_COMPLETE, alors des étapes supplémentaires sont nécessaires pour assurer la visibilité à la cible. Par exemple, le transfert peut générer une complétion à la cible, qui indiquerait la visibilité, mais pas la durabilité. L'initiateur peut également suivre le transfert par une autre opération qui force la visibilité, comme utiliser FI_FENCE en conjonction avec FI_DELIVERY_COMPLET

E
.

NOTE

S

Une file de complétion doit être liée à au moins un endpoint activé avant que toute opération telle que fi_cq_read, fi_cq_readfrom, fi_cq_sread, fi_cq_sreadfrom etc. puisse être appelée sur

celle-ci.

Si une file de complétion a été débordée, elle sera placée dans un état `overrun'. Les opérations de lecture continueront de retourner toute complétion valide, non corrom

pue, si disponible. Après que toutes les complétions valides ont été récupérées, toute tentative de lecture du CQ résultera en un événement d'erreur FI_EOVERRUN. Les file
s de complétion débordées sont considérées comme fatales et ne peuvent pas être utilisées pour signaler des complétions supplémentaires une fois le débordement survenu.
