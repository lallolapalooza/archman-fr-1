NOM

fi_join_collective
Opération où un sous-ensemble de pairs rejoint un nouveau groupe collectif.
fi_barrier / fi_barrier2
Opération collective qui ne se termine pas tant que tous les pairs n'ont pas entré l'appel de barrière.
fi_broadcast
Un seul émetteur transmet des données à tous les pairs, y compris lui-même.
fi_alltoall
Chaque pair distribue une tranche de ses données locales à tous les pairs.
fi_allreduce
Opération collective où tous les pairs diffusent une opération atomique à tous les autres pairs.
fi_allgather
Chaque pair envoie une copie complète de ses données locales à tous les pairs.
fi_reduce_scatter
Appel collectif où les données sont collectées depuis tous les pairs et fusionnées (réduites). Les résultats de la réduction sont distribués aux pairs, chaque pair recevant une tranche des résultats.
fi_reduce
Appel collectif où les données sont collectées depuis tous les pairs vers un pair racine et fusionnées (réduites).
fi_scatter
Un seul émetteur distribue (disperse) une tranche de ses données locales à tous les pairs.
fi_gather
Tous les pairs envoient leurs données à un pair racine.
fi_query_collective
Retourne des informations sur les opérations collectives prises en charge par un fournisseur, et les limitations du collectif.

DESCRIPTION

En général, les opérations collectives peuvent être considérées comme des opérations atomiques coordonnées entre un ensemble de points de terminaison pairs. Les lecteurs doivent consulter la page man fi_atomic(3) pour plus de détails sur les opérations atomiques et les types de données définis par libfabric.

Une opération collective est un échange de communication de groupe. Elle implique plusieurs pairs échangeant des données avec d'autres pairs participant à l'appel collectif. Les opérations collectives nécessitent une étroite coordination par tous les membres participants. Tous les participants doivent invoquer le même appel collectif avant qu'un seul membre puisse terminer son opération localement. Par conséquent, les appels collectifs peuvent solliciter le fabric, ainsi que les tampons de données locaux et distants.

Les interfaces collectives de libfabric ciblent les fabrics qui prennent en charge le déchargement de parties de la communication collective vers des commutateurs réseau, des NIC et d'autres périphériques. Cependant, aucune exigence d'implémentation n'est imposée au fournisseur.

La première étape pour utiliser un appel collectif est d'identifier les points de terminaison pairs qui y participeront. L'appartenance au collectif suit l'un des deux modèles, tous deux pris en charge par libfabric. Dans le premier modèle, l'application gère l'appartenance. Cela signifie généralement que l'application effectue elle-même une opération collective en utilisant la communication point à point pour identifier les membres qui participeront. De plus, l'application peut interagir avec un gestionnaire de ressources de fabric pour réserver les ressources réseau nécessaires à l'exécution des opérations collectives. Dans ce modèle, l'application informera libfabric que l'appartenance a déjà été établie.

Un modèle distinct déplace la gestion de l'appartenance sous libfabric et directement dans le fournisseur. Dans ce modèle, l'application doit identifier quelles adresses pairs seront membres. Cette information est transmise au fournisseur libfabric, qui est alors responsable de coordonner la création du groupe collectif. Dans le modèle géré par le fournisseur, le fournisseur effectuera généralement l'opération collective nécessaire pour établir le groupe de communication et interagira avec tous les agents de gestion de fabric.

Dans les deux modèles, l'appartenance au collectif est communiquée au fournisseur en créant et configurant un ensemble de vecteurs d'adresses (AV set). Un AV set représente un sous-ensemble ordonné d'adresses dans un vecteur d'adresses (AV). Les détails sur la création et la configuration d'un AV set sont disponibles dans fi_av_set(3).

Une fois qu'un AV set a été programmé avec les informations d'appartenance au collectif, un point de terminaison est joint à l'ensemble. Cela utilise l'opération fi_join_collective et fonctionne de manière asynchrone. Cela diffère de la manière dont un point de terminaison est associé de manière synchroneousément avec un AV à l'aide de l'appel fi_ep_bind(). À la fin de l'opération fi_join_collective, un fi_addr est fourni qui est utilisé comme adresse cible lors de l'invocation d'une opération collective.

Pour la commodité des développeurs, un ensemble d'API collectives est défini. Les API collectives diffèrent des interfaces de message et RMA en ce que le format des données est connu du fournisseur, et l'opération collective peut effectuer une opération sur ces données. Cela aligne étroitement les opérations collectives avec les interfaces atomiques.

Rejoindre une collectivité (fi_join_collective)

Cette attache un point de terminaison à un groupe d'appartenance à une collectivité. Libfabric traite les membres collectifs comme un groupe multicast, et l'appel fi_join_collective attache le point de terminaison à ce groupe multicast. Par défaut, le point de terminaison rejoindra le groupe en fonction des capacités de transfert de données du point de terminaison. Par exemple, si le point de terminaison a été configuré pour à la fois envoyer et recevoir des données, alors le point de terminaison pourra initier et recevoir des transferts vers et depuis la collectivité. Les indicateurs d'entrée peuvent être utilisés pour restreindre l'accès au groupe collectif, sous réserve des limitations de capacité du point de terminaison.

Les opérations de rejoindre une collectivité s'achèvent de manière asynchrone et peuvent impliquer des transferts sur le tissu, selon l'implémentation du fournisseur. Un point de terminaison doit être lié à une file d'événements avant d'appeler fi_join_collective. Le résultat de l'opération de rejoindre sera rapporté à la file d'événements (EQ) sous la forme d'un événement FI_JOIN_COMPLETE. Les applications ne peuvent pas lancer de transferts collectifs avant de recevoir la notification indiquant que l'opération de rejoindre est terminée. Notez qu'un point de terminaison peut commencer à recevoir des messages du groupe collectif dès que le rejoindre est terminé, ce qui peut se produire avant la génération de l'événement FI_JOIN_COMPLETE.

L'opération de rejoindre une collectivité est elle-même une opération collective. Tous les pairs participants doivent appeler fi_join_collective avant qu'un pair individuel quelconque ne signale que le rejoindre est terminé. Les appartenance collectives gérées par l'application en sont une exception. Avec les appartenance gérées par l'application, l'appel fi_join_collective peut être complété localement sans communication sur le tissu. Pour les appartenance gérées par le fournisseur, l'appel de rejoindre une collectivité requiert en entrée une coll_addr qui fait référence soit à une adresse associée à un ensemble AV (voir fi_av_set_addr), soit à un groupe collectif existant (obtenu par un appel précédent à fi_join_collective). L'appel fi_join_collective créera un nouveau sous-groupe collectif. Si des appartenance gérées par l'application sont utilisées, coll_addr doit être défini à FI_ADDR_UNAVAIL.

Les applications doivent appeler fi_close sur le groupe collectif pour déconnecter le point de terminaison du groupe. Après qu'une opération de rejoindre est terminée, l'appel fi_mc_addr peut être utilisé pour récupérer l'adresse associée au groupe multicast. Voir fi_cm(3) pour des détails supplémentaires sur fi_mc_addr().

Barrière (fi_barrier)

L'opération fi_barrier fournit un mécanisme pour synchroniser les pairs. La barrière ne résulte en aucun transfert de données au niveau de l'application. Une barrière ne se termine pas localement tant que tous les pairs n'ont pas invoqué l'appel de barrière. Cela signifie à l'application locale que le travail des pairs qui se sont terminés avant qu'ils n'aient appelé la barrière est achevé.

Barrière (fi_barrier2)

L'opération fi_barrier2 est la même que fi_barrier, mais avec un paramètre supplémentaire pour transmettre des indicateurs d'opération.

Diffusion (fi_broadcast)

fi_broadcast transfère un tableau de données d'un seul émetteur à tous les autres membres du groupe collectif. Le paramètre buf d'entrée est traité comme le tampon d'émission si le rang local est la racine, sinon c'est le tampon de réception. L'opération de diffusion agit comme une écriture ou une lecture atomique sur un tableau de données. Par conséquent, le format des données dans buf est spécifié à travers le paramètre datatype. Tout datatype non void peut être diffusé.

Le diagramme suivant montre un exemple de diffusion utilisé pour transférer un tableau d'entiers à un groupe de pairs.

All to All (fi_alltoall)

L'opération collective fi_alltoall consiste à distribuer (ou disperser) différentes portions d'un tableau de données aux pairs. Elle s'explique le mieux à l'aide d'un exemple. Ici, trois pairs effectuent un all to all collectif pour échanger différentes entrées d'un tableau d'entiers.

[1]   [2]   [3]
[5]   [6]   [7]
[9]  [10]  [11]
   \   |   /
   All to all
   /   |   \
[1]   [5]   [9]
[2]   [6]  [10]
[3]   [7]  [11]

Chaque pair envoie une partie de ses données aux autres pairs.

Les opérations all to all peuvent être effectuées sur tout datatype non void. Cependant, all to all n'effectue pas d'opération sur les données elles-mêmes, donc aucune opération n'est spécifiée.

All Reduce (fi_allreduce)

fi_allreduce peut être décrit comme tous les pairs fournissant une entrée à une opération atomique, avec le résultat copié vers chaque pair. Conceptuellement, cela peut être vu comme chaque pair émettant une opération atomique multicast vers tous les autres pairs, récupérant les résultats, et les combinant. La combinaison des résultats est appelée la réduction. L'opération fi_allreduce() prend en entrée un tableau de données et l'opération atomique spécifiée à effectuer. Les résultats de la réduction sont écrits dans le tampon de résultat.

Tout datatype non void peut être spécifié. Les opérations atomiques valides sont listées ci-dessous dans l'appel fi_query_collective. Le diagramme suivant montre un exemple d'opération all reduce impliquant la sommation d'un tableau d'entiers entre trois pairs.

Conceptuellement, all gather peut être vu comme l'opposé du composant de dispersion (scatter) de reduce-scatter. All gather collecte les données de tous les pairs dans un seul tableau, puis copie ce tableau vers chaque pair.

Reduce-Scatter (fi_reduce_scatter)

L'opération collective fi_reduce_scatter est similaire à une opération fi_allreduce, suivie d'un all to all. Avec reduce scatter, tous les pairs fournissent une entrée à une opération atomique, similaire à all reduce. Cependant, plutôt que le résultat complet étant copié vers chaque pair, chaque participant ne reçoit qu'une tranche du résultat.

Interroger les attributs collectifs (fi_query_collective)

L'appel fi_query_collective rapporte quelles opérations collectives sont prises en charge par le fournisseur sous-jacent, pour des points de terminaison correctement configurés. Les opérations collectives nécessaires à une application qui ne sont pas prises en charge par le fournisseur doivent être implémentées par l'application. L'appel de requête vérifie si un fournisseur prend en charge une opération collective spécifique pour un datatype et une opération donnés, si applicable.

Le nom de la collectivité, ainsi que le datatype et l'opération associée, si applicable, sont fournis en entrée à fi_query_collective.

Le paramètre coll peut faire référence à l'une de ces collectivités : FI_BARRIER, FI_BROADCAST, FI_ALLTOALL, FI_ALLREDUCE, FI_ALLGATHER, FI_REDUCE_SCATTER, FI_REDUCE, FI_SCATTER, ou FI_GATHER. Des détails supplémentaires sur l'opération collective sont spécifiés à travers le paramètre struct fi_collective_attr. Pour les collectivités qui agissent sur les données, l'opération et le type de données associé doivent être spécifiés. fi_join_collective(3)

NAME

fi_join_collective, fi_query_collective - establish and query collective operations

SYNOPSIS

#include <rdma/fabric.h>

int fi_join_collective(
    struct fid_ep *ep,
    void *context);

int fi_query_collective(
    struct fid_ep *ep,
    const struct fi_collective_attr *attr,
    struct fi_collective_attr *query_attr);

ARGUMENTS

ep
An endpoint addressing the collective operation. See fi_endpoint(3) for additional information.
context
User specified context for the collective join operation. This context will be returned in the completion associated with the collective join. See fi_cq(3) for additional information.
attr
Input attributes for the collective operation. If attr is NULL, then the query will be performed against all supported collective operations on the endpoint.
query_attr
Output attributes of the queried collective operation. See the fi_collective_attr struct description below.

DESCRIPTION

Collective operations are a set of operations that involve multiple participants. For example, a reduce operation involves all participants contributing data, with the result being returned to all participants. Collective operations are implemented using underlying atomic operations and are only supported on endpoints that are addressed to both transmit and receive.

The fi_join_collective call registers the calling application with the collective operation. This call should be made by all participants in the collective operation before initiating any collective operations. The context associated with the call is returned in the completion associated with the join operation.

The fi_query_collective call is used to discover the collective operations supported by the specified endpoint, along with any limits or constraints on those operations.

The fi_collective_attr structure is used to describe collective operations:

struct fi_collective_attr {
    enum fi_op op;
    enum fi_datatype datatype;
    struct fi_atomic_attr datatype_attr;
    size_t max_members;
      uint64_t mode;
};

For a description of struct fi_atomic_attr, see fi_atomic(3).

op
On input, this specifies the atomic operation involved with the collective call. This should be set to one of the following values: FI_MIN, FI_MAX, FI_SUM, FI_PROD, FI_LOR, FI_LAND, FI_BOR, FI_BAND, FI_LXOR, FI_BXOR, FI_ATOMIC_READ, FI_ATOMIC_WRITE, of FI_NOOP. For collectives that do not exchange application data (fi_barrier), this should be set to FI_NOOP.
datatype
On onput, specifies the datatype of the data being modified by the collective. This should be set to one of the following values: FI_INT8, FI_UINT8, FI_INT16, FI_UINT16, FI_INT32, FI_UINT32, FI_INT64, FI_UINT64, FI_FLOAT, FI_DOUBLE, FI_FLOAT_COMPLEX, FI_DOUBLE_COMPLEX, FI_LONG_DOUBLE, FI_LONG_DOUBLE_COMPLEX, or FI_VOID. For collectives that do not exchange application data (fi_barrier), this should be set to FI_VOID.
datatype_attr.count
The maximum number of elements that may be used with the collective.
datatype_attr.size
The size of the datatype as supported by the provider. Applications should validate the size of datatypes that differ based on the platform, such as FI_LONG_DOUBLE.
max_members
The maximum number of peers that may participate in a collective operation.
mode
This field is reserved and should be 0.

If a collective operation is supported, the query call will return FI_SUCCESS, along with attributes on the limits for using that collective operation through the provider.

Completions

Collective operations map to underlying fi_atomic operations. For a discussion of atomic completion semantics, see fi_atomic(3). The completion, ordering, and atomicity of collective operations match those defined for point to point atomic operations.

FLAGS

The following flags are defined for the specified operations.

FI_SCATTER
Applies to fi_query_collective. When set, requests attribute information on the reduce-scatter collective operation.

RETURN VALUE

Returns 0 on success. On error, a negative value corresponding to fabric errno is returned. Fabric errno values are defined in rdma/fi_errno.h.

ERRORS

-FI_EAGAIN
See fi_msg(3) for a detailed description of handling FI_EAGAIN.
-FI_EOPNOTSUPP
The requested atomic operation is not supported on this endpoint.
-FI_EMSGSIZE
The number of collective operations in a single request exceeds that supported by the underlying provider.

NOTES

Collective operations map to atomic operations. As such, they follow most of the conventions and restrictions as peer to peer atomic operations. This includes data atomicity, data alignment, and message ordering semantics. See fi_atomic(3) for additional information on the datatypes and operations defined for atomic and collective operations.

SEE ALSO

fi_getinfo(3), fi_av(3), fi_atomic(3), fi_cm(3)

NOM

fi_join_collective, fi_query_collective - établir et interroger les opérations collectives

SYNTAXE

#include <rdma/fabric.h>

int fi_join_collective(
    struct fid_ep *ep,
    void *context);

int fi_query_collective(
    struct fid_ep *ep,
    const struct fi_collective_attr *attr,
    struct fi_collective_attr *query_attr);

ARGUMENTS

ep
Un point d'extrémité adressant l'opération collective. Voir fi_endpoint(3) pour plus d'informations.
context
Contexte spécifié par l'utilisateur pour l'opération de jointure collective. Ce contexte sera renvoyé dans la complétion associée à la jointure collective. Voir fi_cq(3) pour plus d'informations.
attr
Attributs d'entrée pour l'opération collective. Si attr est NULL, alors la requête sera effectuée sur toutes les opérations collectives prises en charge sur le point d'extrémité.
query_attr
Attributs de sortie de l'opération collective interrogée. Voir la description de la structure fi_collective_attr ci-dessous.

DESCRIPTION

Les opérations collectives sont un ensemble d'opérations impliquant plusieurs participants. Par exemple, une opération de réduction implique que tous les participants contribuent des données, le résultat étant renvoyé à tous les participants. Les opérations collectives sont implémentées à l'aide d'opérations atomiques sous-jacentes et ne sont prises en charge que sur les points d'extrémité qui sont adressés à la fois pour la transmission et la réception.

L'appel fi_join_collective enregistre l'application appelante auprès de l'opération collective. Cet appel doit être effectué par tous les participants de l'opération collective avant d'initier toute opération collective. Le contexte associé à l'appel est renvoyé dans la complétion associée à l'opération de jointure.

L'appel fi_query_collective est utilisé pour découvrir les opérations collectives prises en charge par le point d'extrémité spécifié, ainsi que toutes les limites ou contraintes sur ces opérations.

La structure fi_collective_attr est utilisée pour décrire les opérations collectives :

struct fi_collective_attr {
    enum fi_op op;
    enum fi_datatype datatype;
    struct fi_atomic_attr datatype_attr;
    size_t max_members;
      uint64_t mode;
};

Pour une description de la structure fi_atomic_attr, voir fi_atomic(3).

op
En entrée, cela spécifie l'opération atomique impliquée dans l'appel collectif. Cela doit être défini sur l'une des valeurs suivantes : FI_MIN, FI_MAX, FI_SUM, FI_PROD, FI_LOR, FI_LAND, FI_BOR, FI_BAND, FI_LXOR, FI_BXOR, FI_ATOMIC_READ, FI_ATOMIC_WRITE, ou FI_NOOP. Pour les collectives qui n'échangent pas de données d'application (fi_barrier), cela doit être défini sur FI_NOOP.
datatype
En entrée, spécifie le type de données qui est modifié par la collective. Cela doit être défini sur l'une des valeurs suivantes : FI_INT8, FI_UINT8, FI_INT16, FI_UINT16, FI_INT32, FI_UINT32, FI_INT64, FI_UINT64, FI_FLOAT, FI_DOUBLE, FI_FLOAT_COMPLEX, FI_DOUBLE_COMPLEX, FI_LONG_DOUBLE, FI_LONG_DOUBLE_COMPLEX, ou FI_VOID. Pour les collectives qui n'échangent pas de données d'application (fi_barrier), cela doit être défini sur FI_VOID.
datatype_attr.count
Le nombre maximal d'éléments pouvant être utilisés avec la collective.
datatype_attr.size
La taille du type de données telle que prise en charge par le fournisseur. Les applications doivent valider la taille des types de données qui diffèrent en fonction de la plateforme, tels que FI_LONG_DOUBLE.
max_members
Le nombre maximal de pairs pouvant participer à une opération collective.
mode
Ce champ est réservé et doit être 0.

Si une opération collective est prise en charge, l'appel de requête renverra FI_SUCCESS, ainsi que les attributs sur les limites d'utilisation de cette opération collective via le fournisseur.

Completions

Les opérations collectives correspondent à des opérations fi_atomic sous-jacentes. Pour une discussion sur la sémantique de complétion atomique, voir fi_atomic(3). La complétion, l'ordonnancement et l'atomicité des opérations collectives correspondent à ceux définis pour les opérations atomiques point à point.

FLAGS

Les drapeaux suivants sont définis pour les opérations spécifiées.

FI_SCATTER
S'applique à fi_query_collective. Lorsqu'il est défini, demande des informations d'attributs sur l'opération collective reduce-scatter.

VALEUR DE RETOUR

Renvoie 0 en cas de succès. En cas d'erreur, une valeur négative correspondant à un errno de fabric est renvoyée. Les valeurs errno de fabric sont définies dans rdma/fi_errno.h.

ERREURS

-FI_EAGAIN
Voir fi_msg(3) pour une description détaillée de la gestion de FI_EAGAIN.
-FI_EOPNOTSUPP
L'opération atomique demandée n'est pas prise en charge sur ce point d'extrémité.
-FI_EMSGSIZE
Le nombre d'opérations collectives dans une seule requête dépasse ce qui est pris en charge par le fournisseur sous-jacent.

NOTES

Les opérations collectives correspondent à des opérations atomiques. En tant que telles, elles suivent la plupart des conventions et restrictions des opérations atomiques point à point. Cela inclut l'atomicité des données, l'alignement des données et la sémantique d'ordonnancement des messages. Voir fi_atomic(3) pour plus d'informations sur les types de données et les opérations définis pour les opérations atomiques et collectives.
