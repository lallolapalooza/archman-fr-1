NOM

file — détermine le type de fichier

SYNTAXE

file [-bcdEhiklLNnprsSvzZ0] [--apple] [--exclude-quiet] [--extension] [--mime-encoding] [--mime-type] [-e nom_test] [-F séparateur] [-f fichier_noms] [-m fichiers_magiques] [-P nom=valeur] fichier ...

file -C [-m fichiers_magiques]

file [--help]

DESCRIPTION

Ce manuel décrit la version 5.46 de la commande file.

file teste chaque argument pour tenter de le classifier. Il existe trois ensembles de tests, effectués dans l'ordre suivant : tests du système de fichiers, tests magiques, et tests linguistiques. Le premier test qui réussit provoque l'affichage du type de fichier.

Le type affiché contiendra généralement l'un des mots texte (le fichier ne contient que des caractères imprimables et quelques caractères de contrôle courants et peut probablement être lu sur un terminal ASCII), exécutable (le fichier contient le résultat de la compilation d'un programme sous une forme compréhensible par un noyau UNIX ou autre), ou données signifiant tout le reste (les données sont généralement “binaires” ou non imprimables). Les exceptions sont les formats de fichiers bien connus (fichiers de vidage, archives tar) qui sont connus pour contenir des données binaires. Lors de la modification des fichiers magiques ou du programme lui-même, assurez-vous de préserver ces mots-clés. Les utilisateurs dépendent du fait de savoir que tous les fichiers lisibles dans un répertoire portent le mot “texte”. Ne faites pas comme Berkeley et ne changez pas “shell commands text” en “shell script”.

Les tests du système de fichiers sont basés sur l'examen du résultat d'un appel système stat(2). Le programme vérifie si le fichier est vide, ou s'il s'agit d'un type de fichier spécial. Tous les types de fichiers connus appropriés au système sur lequel vous exécutez (sockets, liens symboliques, ou tubes nommés (FIFO) sur les systèmes qui les implémentent) sont déduits s'ils sont définis dans le fichier d'en-tête système <sys/stat.h>.

Les tests magiques sont utilisés pour vérifier les fichiers avec des données dans des formats fixes particuliers. L'exemple canonique est un fichier exécutable binaire (programme compilé) a.out, dont le format est défini dans <elf.h>, <a.out.h> et éventuellement <exec.h> dans le répertoire standard d'inclusion. Ces fichiers ont un “nombre magique” stocké à un endroit particulier près du début du fichier qui indique au système d'exploitation UNIX que le fichier est un exécutable binaire, et de quel type. Le concept de “nombre magique” a été étendu aux fichiers de données. Tout fichier ayant un identifiant invariant à un petit décalage fixe dans le fichier peut généralement être décrit de cette manière. Les informations identifiant ces fichiers sont lues à partir du fichier magique compilé /usr/share/file/misc/magic.mgc, ou des fichiers dans le répertoire /usr/share/file/misc/magic si le fichier compilé n'existe pas. De plus, si $HOME/.magic.mgc ou $HOME/.magic existe, il sera utilisé de préférence aux fichiers magiques système.

Si un fichier ne correspond à aucune des entrées du fichier magique, il est examiné pour voir s'il semble être un fichier texte. Les jeux de caractères ASCII, ISO-8859-x, les jeux de caractères étendus 8 bits non-ISO (tels que ceux utilisés sur les systèmes Macintosh et IBM PC), Unicode encodé en UTF-8, Unicode encodé en UTF-16 et EBCDIC peuvent être distingués par les différentes plages et séquences d'octets qui constituent le texte imprimable dans chaque jeu. Si un fichier passe l'un de ces tests, son jeu de caractères est signalé. Les fichiers ASCII, ISO-8859-x, UTF-8 et ASCII étendu sont identifiés comme “texte” car ils seront principalement lisibles sur presque tous les terminaux ; UTF-16 et EBCDIC ne sont que des “données caractères” car, bien qu'ils contiennent du texte, il s'agit d'un texte qui nécessitera une traduction avant de pouvoir être lu. De plus, file tentera de déterminer d'autres caractéristiques des fichiers de type texte. Si les lignes d'un fichier sont terminées par CR, CRLF, ou NEL, au lieu du LF standard Unix, cela sera signalé. Les fichiers contenant des séquences d'échappement incorporées ou des caractères superposés seront également identifiés.

Une fois que file a déterminé le jeu de caractères utilisé dans un fichier de type texte, il tentera de déterminer dans quelle langue le fichier est écrit. Les tests linguistiques recherchent des chaînes particulières (voir <names.h>) qui peuvent apparaître n'importe où dans les premiers blocs d'un fichier. Par exemple, le mot-clé .br indique que le fichier est très probablement un fichier d'entrée troff(1), tout comme le mot-clé struct indique un programme C. Ces tests sont moins fiables que les deux groupes précédents, ils sont donc effectués en dernier. Les routines de test linguistique recherchent également certains éléments divers (tels que les archives tar(1), les fichiers JSON).

Tout fichier qui ne peut pas être identifié comme ayant été écrit dans l'un des jeux de caractères listés ci-dessus est simplement dit “données”.

OPTIONS

--apple
Demande à la commande file d'afficher le type de fichier et le code créateur tels qu'utilisés par les anciennes versions de MacOS. Le code est composé de huit lettres, la première décrivant le type de fichier, la seconde le créateur. Cette option ne fonctionne correctement que pour les formats de fichiers pour lesquels la sortie de style Apple est définie.

Ne pas préfixer les noms de fichiers aux lignes de sortie (mode bref).

ENVIRONNEMEN

T

La variable d'environnement MAGIC peut être utilisée pour définir le nom du fichier magic par défaut. Si cette variable est définie, alors file n'essaiera pas d'ouvrir $HOME/.magic. file ajoute «.mgc » à la valeur de cette variable selon les besoins. La variable d'environnement POSIXLY_CORRECT contrôle (sur les systèmes qui prennent en charge les liens symboliques) si file essaie de suivre les liens symboliques ou non. Si elle est définie, alors file suit les liens symboliques, sinon il ne les suit pas. C'est aussi contrôlé par les options -L et -h

.

CONFORMITÉ AUX

NORMES

On pense que ce programme dépasse la définition d'interface System V de FILE(CMD), autant qu'on peut le déterminer à partir du langage vague qui y est contenu. Son comportement est principalement compatible avec le programme System V du même nom. Cependant, cette version connaît plus de règles magic, donc elle produira une sortie différente (bien que plus précise) dans de nombreux

cas.

La différence significative entre cette version et System V est que cette version traite tout espace blanc comme un délimiteur, de sorte que les espaces dans les chaînes de motifs doivent être échappés. Par

exemple, 
>10	string	lan
guage impress
(imPRESS data)

dans un fichier magic existant devrait être changé

en 
>10	string	lan
guage\ impress
(imPRESS data)

De plus, dans cette version, si une chaîne de motif contient une barre oblique inverse, elle doit être échappée. Par

exemple 
0	string		\begi
ndata Andrew T
oolkit document

dans un fichier magic existant devrait être changé

oolkit document

Les versions SunOS 3.2 et ultérieures de Sun Microsystems incluent une commande file dérivée de celle de System V, mais avec certaines extensions. Cette version diffère de celle de Sun seulement de manière mineure. Elle inclut l'extension de l'opérateur ‘&’, utilisé comme, par

SÉCURIT

É

Sur les systèmes où libseccomp (https://github.com/seccomp/libseccomp) est disponible, file fait respecter la limitation des appels système aux seuls appels nécessaires au fonctionnement du programme. Cette application n'apporte aucun avantage de sécurité lorsque file est demandé de décompresser des fichiers d'entrée en exécutant des programmes externes avec l'option -z. Pour permettre l'exécution de décompresseurs externes, il faut désactiver la sandbox en utilisant l'option -S

.

HISTORIQU

E

Il y a eu une commande file dans chaque UNIX depuis au moins la version de recherche 4 (page de man datant de novembre 1973). La version System V a introduit un changement majeur significatif : la liste externe des types magic. Cela a ralenti légèrement le programme mais l'a rendu beaucoup plus

flexible.

Ce programme, basé sur la version System V, a été écrit par Ian Darwin ⟨ian@darwinsys.com⟩ sans regarder le code source de

quiconque.

John Gilmore a révisé le code de manière extensive, le rendant meilleur que la première version. Geoff Collyer a trouvé plusieurs insuffisances et a fourni quelques entrées magic. Contribution de l'opérateur ‘&’ par Rob McMahon, ⟨cudcv@warwick.ac.uk⟩,

1989.

Guy Harris, ⟨guy@netapp.com⟩, a fait de nombreuses modifications de 1993 à

aujourd'hui.

Développement et maintenance principaux de 1990 à aujourd'hui par Christos Zoulas ⟨christos@astron.

com⟩.

Modifié par Chris Lowth ⟨chris@lowth.com⟩, 2000 : gérer l'option -i pour afficher les chaînes de type mime, en utilisant un fichier magic alternatif et une logique

interne.

Modifié par Eric Fischer ⟨enf@pobox.com⟩, juillet 2000, pour identifier les codes de caractères et tenter d'identifier les langages des fichiers

non-ASCII.

Modifié par Reuben Thomas ⟨rrt@sc3d.org⟩, 2007-2011, pour améliorer la prise en charge MIME, fusionner les règles magic MIME et non-MIME, prendre en charge les répertoires ainsi que les fichiers de règles magic, appliquer de nombreuses corrections de bogues, mettre à jour et corriger beaucoup de règles magic, améliorer le système de compilation, améliorer la documentation et réécrire les liaisons Python en Python

pur.

Continuer à éliminer tous les bogues magic. Voir le BTS de Debian pour une bonne

Stocker des chaînes de longueur arbitraire, par exemple pour les motifs %s, afin qu'elles puissent être affichées. Corrige le bogue Debian #271672. Cela peut être fait en allouant les chaînes dans un pool de chaînes, en stockant le pool de chaînes à la fin du fichier magic et en convertissant tous les pointeurs de chaînes en décalages relatifs depuis le pool de

Ajouter la syntaxe pour les décalages relatifs après le niveau courant (bogue Debian #466037)

.

Ajouter une option pour imprimer les URL des sources des descriptions de

fichiers.

Combiner les recherches de scripts et ajouter un moyen de faire correspondre les noms d'exécutables aux types MIME (par exemple, avoir une valeur magique pour !:mime qui provoque la recherche de la chaîne résultante dans une table). Cela éviterait d'ajouter le même code magique à chaque nouvel interpréteur de

hash-bang.

Lorsqu'un descripteur de fichier est disponible, nous pouvons sauter et ajuster le tampon au lieu de la gestion de tampon approximative que nous faisons

actuellement.

Corriger « name » et « use » pour vérifier la cohérence à la compilation (« name » en double, « use » pointant vers un « name » indéfini). Rendre « name » / « use » plus efficace en maintenant une liste de noms triée. Cas particulier pour ^ pour inverser l'ordre des octets dans l'analyseur afin qu'il n'ait pas besoin d'être échappé, et le

documenter.

Il faut cependant faire attention car cela a des implications sur les performances et donc sur la sécurité, car on peut ralentir les choses en se déplaçant de manière

répétée.
