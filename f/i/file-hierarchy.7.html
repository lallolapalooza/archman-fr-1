systemd(1) sont organisés sur la base d'une hiérarchie du système de fichiers inspirée d'UNIX, plus précisément la hiérarchie décrite dans la spécification File System Hierarchy[1] et hier(7), avec diverses extensions, partiellement documentées dans la XDG Base Directory Specification[2] et XDG User Directories[3]. Cette page manuelle décrit un sous-ensemble plus généralisé, bien que minimal et modernisé, de ces spécifications qui définit plus strictement les suggestions et les restrictions que systemd impose à la hiérarchie du système de fichiers. Notez que ce document ne tente pas de définir la structure des répertoires de manière exhaustive, il documente seulement un squelette d'arborescence de répertoires que les distributions dérivées peuvent étendre. Pour cette raison, des répertoires traditionnels tels que /usr/include/ ou /var/spool/ ne sont pas couverts, même s'il pourrait (ou non) être pertinent de les inclure dans la structure d'un OS réellement déployé. Beaucoup des chemins décrits ici peuvent être interrogés avec l'outil systemd-path(1). STRUCTURE GÉNÉRALE / La racine du système de fichiers.

DONNÉES SYSTÈME VARIABLES

PERSISTANTES

/var

/
Données système variables et persistantes. Inscriptible pendant le fonctionnement normal du système. Ce répertoire peut être pré-rempli avec des données fournies par le fournisseur, mais les applications doivent être capables de reconstruire les fichiers et répertoires nécessaires dans cette sous-hiérarchie s'ils sont manquants, car le système peut démarrer sans que ce répertoire soit peuplé. La persistance est recommandée, mais facultative, pour supporter les systèmes éphémères. Ce répertoire peut ne devenir disponible ou inscriptible que très tard pendant le démarrage. Les composants qui doivent fonctionner pendant le démarrage précoce ne doivent donc pas dépendre inconditionnellement de ce
répertoire.

/var/cache

/
Données de cache système persistantes. Les composants système peuvent placer des données non essentielles dans ce répertoire. Vider ce répertoire ne devrait avoir aucun effet sur le fonctionnement des programmes, à l'exception des temps d'exécution accrus nécessaires pour reconstruire ces
caches.

/var/lib

/
Données système persistantes. Les composants système peuvent placer des données privées dans ce
répertoire.

/var/log

/
Journaux système persistants. Les composants système peuvent placer des journaux privés dans ce répertoire, bien qu'il soit recommandé de faire la plupart des journaux via les appels syslog(3) et sd_journal_pr
int(3).

/var/tmp

/
L'emplacement pour les fichiers temporaires plus volumineux et persistants. Contrairement à /tmp/, ce répertoire est généralement monté depuis un système de fichiers physique persistant et peut donc accepter des fichiers plus volumineux. (Utilisez /tmp/ pour les petits fichiers éphémères.) Ce répertoire n'est généralement pas vidé au démarrage, mais un nettoyage basé sur le temps des fichiers qui n'ont pas été accédés depuis un certain temps est appliqué.

Si les applications trouvent la variable d'environnement $TMPDIR définie, elles devraient utiliser le répertoire spécifié dedans au lieu de /var/tmp/ (voir environ(7) pour les détails)

.

Les mêmes restrictions de sécurité que pour /tmp/ s'appliquent : mkstemp(3), mkdtemp(3), et des appels similaires devraient être utilisés. Pour plus de détails sur ce répertoire, voir Utilisation sûre de

SYSTÈMES DE FICHIERS VIRTUELS NOYAU ET

API

/dev

/
Le répertoire racine pour les nœuds de périphériques. Habituellement, ce répertoire est monté comme une instance "devtmpfs", mais peut être d'un type différent dans les configurations en bac à sable/conteneurisées. Ce répertoire est géré conjointement par le noyau et systemd-udevd(8), et ne devrait pas être écrit par d'autres composants. Un certain nombre de systèmes de fichiers virtuels à usage spécifique peuvent être montés sous ce
répertoire.

/dev/shm

/
Emplacement pour les segments de mémoire partagée POSIX, créés via shm_open(3). Ce répertoire est vidé au démarrage, et est un système de fichiers "tmpfs". Étant donné que tous les utilisateurs ont un accès en écriture à ce répertoire, une attention particulière doit être portée pour éviter les conflits de noms et les vulnérabilités. Pour les utilisateurs normaux, les segments de mémoire partagée dans ce répertoire sont généralement supprimés lorsque l'utilisateur se déconnecte. Habituellement, il est préférable d'utiliser des fichiers mappés en mémoire dans /run/ (pour les programmes système) ou $XDG_RUNTIME_DIR (pour les programmes utilisateur) au lieu de segments de mémoire partagée POSIX, car ces répertoires ne sont pas inscriptibles par tous et ne sont donc pas vulnérables aux conflits de noms sensibles sur le plan de la
sécurité.

/proc

/
Un système de fichiers virtuel du noyau exposant la liste des processus et d'autres fonctionnalités. Ce système de fichiers est principalement une API pour interagir avec le noyau et non un endroit où des fichiers normaux peuvent être stockés. Pour les détails, voir proc(5). Un certain nombre de systèmes de fichiers virtuels à usage spécifique peuvent être montés sous ce
répertoire.

/proc/sys

/
Une hiérarchie sous /proc/ exposant un certain nombre de réglages ajustables du noyau. La manière principale de configurer les paramètres dans cette arborescence de fichiers API est via les fichiers sysctl.d(5). Dans les configurations en bac à sable/conteneurisées, ce répertoire est généralement monté en lecture
seule.

/sys

/
Un système de fichiers virtuel du noyau exposant les périphériques découverts et d'autres fonctionnalités. Ce système de fichiers est principalement une API pour interagir avec le noyau et non un endroit où des fichiers normaux peuvent être stockés. Dans les configurations en bac à sable/conteneurisées, ce répertoire est généralement monté en lecture seule. Un certain nombre de systèmes de fichiers virtuels à usage spécifique peuvent être montés sous ce
répertoire.

/sys/fs/cgroup

/
Un système de fichiers virtuel du noyau exposant les groupes de contrôle de processus (cgroups). Ce système de fichiers est une API pour interagir avec le noyau et pas un endroit où des fichiers normaux peuvent être stockés. Sur les systèmes actuels fonctionnant en mode "unified" par défaut, ce répertoire sert de point de montage pour le système de fichiers "cgroup2", qui fournit une hiérarchie cgroup unifiée pour tous les contrôleurs de ressources. Sur les systèmes avec des configurations non par défaut, ce répertoire peut à la place être un système de fichiers tmpfs contenant des points de montage pour divers contrôleurs de ressources "cgroup" (v1) ; dans de telles configurations, si "cgroup2" est monté, il sera monté sur /sys/fs/cgroup/unified/, mais cgroup2 n'aura pas de contrôleurs de ressources attachés. Dans les configurations en bac à sable/conteneurisées, ce répertoire peut soit ne pas exister, soit inclure un sous-ensemble de
fonctionnalités
.

ACCÈS EN

ÉCRITURE

Accès en écriture non

privilégié

Les processus non privilégiés manquent généralement d'accès en écriture à la plupart de la

hiérarchie.

Les exceptions pour les utilisateurs normaux sont /tmp/, /var/tmp/, /dev/shm/, ainsi que le répertoire personnel $HOME (généralement trouvé sous /home/) et le répertoire d'exécution $XDG_RUNTIME_DIR (trouvé sous /run/user/) de l'utilisateur, qui sont tous

inscriptibles.

Pour les processus système non privilégiés, seuls /tmp/, /var/tmp/ et /dev/shm/ sont inscriptibles. Si un processus système non privilégié a besoin d'un répertoire privé inscriptible dans /var/ ou /run/, il est recommandé de soit le créer avant de déposer les privilèges dans le code du démon, de le créer via des fragments tmpfiles.d(5) pendant le démarrage, ou via les directives StateDirectory= et RuntimeDirectory= des unités de service (voir systemd.unit(5) pour les détails)

.

/tmp/, /var/tmp/ et /dev/shm/ devraient être montés nosuid et nodev, ce qui signifie que le mode set-user-id et caractère ou bloc les périphériques spéciaux ne sont pas interprétés sur ces systèmes de fichiers. En général, il n'est pas possible de les monter noexec, car divers programmes utilisent ces répertoires pour du code généré dynamiquement ou optimisé, et avec cet indicateur ces cas d'utilisation seraient cassés. L'utilisation de cet indicateur est acceptable sur des installations ou systèmes spécialisés où tous les logiciels susceptibles d'être installés sont connus et ne nécessitent pas une telle fonctionnalité. Voir la discussion sur nosuid/ nodev/ noexecdansmount(8) et PROT_EXEC dans mmap(2) . Absence d'acc
