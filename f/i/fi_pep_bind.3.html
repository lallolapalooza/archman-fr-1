DESCRIPTION

Les points de terminaison sont des portails de communication au niveau du transport. Il existe deux types de points de terminaison : actifs et passifs. Les points de terminaison passifs appartiennent à un domaine de fabric et sont le plus souvent utilisés pour écouter les demandes de connexion entrantes. Cependant, un point de terminaison passif peut être utilisé pour réserver une adresse de fabric qui peut être accordée à un point de terminaison actif. Les points de terminaison actifs appartiennent aux domaines d'accès et peuvent effectuer des transferts de données.

Les points de terminaison actifs peuvent être orientés connexion ou sans connexion, et peuvent fournir une fiabilité des données. Les interfaces de transfert de données – messages (fi_msg), messages étiquetés (fi_tagged), RMA (fi_rma) et opérations atomiques (fi_atomic) – sont associées aux points de terminaison actifs. Dans les configurations de base, un point de terminaison actif possède des files d'émission et de réception. En général, les opérations qui génèrent du trafic sur le fabric sont soumises à la file d'émission. Cela comprend toutes les opérations RMA et atomiques, ainsi que les messages envoyés et les messages étiquetés envoyés. Les opérations qui soumettent des tampons pour la réception de données entrantes sont soumises à la file de réception.

Les points de terminaison actifs sont créés dans l'état désactivé. Ils doivent passer dans un état activé avant d'accepter des opérations de transfert de données, y compris la soumission de tampons de réception. L'appel fi_enable est utilisé pour faire passer un point de terminaison actif dans un état activé. Les appels fi_connect et fi_accept feront également passer un point de terminaison dans l'état activé, s'il n'est pas déjà actif.

Afin de faire passer un point de terminaison dans un état activé, il doit être lié à une ou plusieurs ressources de fabric. Un point de terminaison qui va générer des achèvements asynchrones, soit par des opérations de transfert de données, soit par des événements d'établissement de connexion, doit être lié aux files d'achèvement ou aux files d'événements appropriées, respectivement, avant d'être activé. De plus, les points de terminaison qui utilisent la progression manuelle doivent être associés aux files d'achèvement ou aux files d'événements pertinentes afin de faire avancer la progression. Pour les points de terminaison qui ne sont utilisés que comme cible d'opérations RMA ou atomiques, cela signifie lier le point de terminaison à une file d'achèvement associée au traitement de la réception. Les points de terminaison sans connexion doivent être liés à un vecteur d'adresses.

Une fois qu'un point de terminaison a été activé, il peut être associé à un vecteur d'adresses. Des tampons de réception peuvent lui être soumis et des appels peuvent être effectués aux routines d'établissement de connexion. Les points de terminaison sans connexion peuvent également effectuer des transferts de données.

Le comportement d'un point de terminaison peut être ajusté en définissant ses données de contrôle et ses options de protocole. Cela permet au fournisseur sous-jacent de rediriger les appels de fonction vers des implémentations optimisées pour répondre au comportement de l'application souhaité.

Si un point de terminaison subit une erreur critique, il repassera dans un état désactivé. Les erreurs critiques sont signalées par la file d'événements associée au EP. Dans certains cas, un point de terminaison désactivé peut être réactivé. La capacité de repasser dans un état activé est propre au fournisseur et dépend du type d'erreur que le point de terminaison a subi.n un point de terminaison est désactivé à la suite d'une erreur critique, toutes les opérations en attente sont

abandonnées.

fi_ep_bind est utilisé pour associer un point de terminaison à d'autres ressources allouées, telles que des files d'achèvement, des compteurs, des vecteurs d'adresses, des files d'événements, des contextes partagés et des régions mémoire. Le type d'objets qui doivent être liés à un point de terminaison dépend du type de point de terminaison et de sa

configuration.

Les points de terminaison passifs doivent être liés à une file d'événements (EQ) qui prend en charge les événements de gestion de connexion. Les points de terminaison sans connexion doivent être liés à un seul vecteur d'adresses. Si un point de terminaison utilise un contexte d'émission et/ou de réception partagé, les contextes partagés doivent être liés au point de terminaison. Les files d'achèvement (CQ), les compteurs, les vecteurs d'adresses (AV) et les contextes partagés doivent être liés aux points de terminaison avant qu'ils ne soient activés, que ce soit explicitement ou

implicitement.

Un point de terminaison doit être lié à des files d'achèvement capables de signaler les achèvements de toute opération asynchrone initiée sur le point de terminaison. Par exemple, si le point de terminaison prend en charge des transferts sortants (envois, RMA, atomiques, etc.), il doit être lié à une file d'achèvement qui peut signaler les achèvements de transmission. C'est vrai même si le point de terminaison est configuré pour supprimer les achèvements réussis, afin que les opérations qui se terminent en erreur puissent être signalées à

l'utilisateur.

fi_cancel tente d'annuler une opération asynchrone en attente. L'annulation d'une opération amène le fournisseur de fabric à rechercher l'opération et, si elle est toujours en attente, à la terminer comme ayant été annulée. Une entrée de file d'erreur sera disponible dans la file d'erreur associée avec le code d'erreur FI_ECANCELED. D'un autre côté, si l'opération s'est terminée avant l'appel à fi_cancel, alors le statut d'achèvement de cette opération sera disponible dans la file d'achèvement associée. Aucune entrée spécifique liée à fi_cancel elle-même ne sera

publiée.

L'annulation utilise le paramètre context associé à une opération pour identifier la requête à annuler. Les opérations soumises sans paramètre de contexte valide – soit aucun paramètre

de contexte n'est spécifié, soit la valeur de contexte a été ignorée par le fournisseur – ne peuvent pas être annulées. Si plusieurs opérations en attente correspondent au paramètre de c
ontexte, une seule sera annulée. Dans ce cas, l'opération qui est annulée est spécifique au fournisseur. L'opération d'annulation est asynchrone, mais se terminera dans un délai limité.

fi_ep_alias

Cet appel crée un alias de l'endpoint spécifié. Conceptuellement, un alias d'endpoint fournit un chemin logiciel alternatif de l'application vers le matériel du fournisseur sous-jacent. Un EP alias diffère de son endpoint parent uniquement par ses drapeaux de transfert de données par défaut. Par exemple, un EP alias peut être configuré pour utiliser un mode de complétion différent. Par défaut, un EP alias hérite des mêmes drapeaux de transfert de données que l'endpoint parent. Une application peut utiliser fi_control pour modifier les drapeaux opérationnels du EP

alias.

Lors de l'allocation d'un alias, une application peut configurer soit les drapeaux opérationnels de transmission, soit ceux de réception. Cela évite d'avoir besoin d'un appel séparé à fi_contro

l pour définir ces drapeaux. Les drapeaux passés à fi_ep_alias doivent inclure FI_TRANSMIT ou FI_RECV (pas les deux) avec les autres drapeaux opérationnels OR’és. Cela remplacera respectivement
les drapeaux de transmission ou de réception pour les opérations postées via l'endpoint alias. Tous les aliases alloués doivent être fermés pour que l'endpoint sous-jacent puisse être libéré.

Taille d'ordre RMA maximale

La taille d'ordre maximale spécifie l'ordre de livraison des données de transport vers la mémoire cible pour les opérations RMA et atomiques. L'ordre des données est distinct, mais dépend de l'ordre des messages (défini ci-dessous). L'ordre des données n'est pas spécifié là où l'ordre des messages n'est pas défini.

L'ordre des données fait référence à l'accès à la même mémoire cible par des opérations ultérieures. Lorsque des opérations de lecture ou d'écriture RMA consécutives accèdent au même emplacement de mémoire enregistré, l'ordre des données indique si la deuxième opération lit ou écrit la mémoire cible après que la première opération ait été terminée. Par exemple, une lecture RMA qui suit une écriture RMA lira-t-elle les données qui ont été écrites ? De même, une écriture RMA qui suit une lecture RMA mettra-t-elle à jour le tampon cible après que la lecture ait transféré les données originales ? L'ordre des données répond à ces questions, même en présence d'erreurs, comme la nécessité de renvoyer des données en raison d'un trafic réseau perdu ou corrompu.

L'ordre RMA s'applique entre deux opérations, et non au sein d'un seul transfert de données. Par conséquent, l'ordre est défini par emplacement de mémoire adressable à l'octet. C'est-à-dire que l'ordre spécifie si l'emplacement X est accédé par la deuxième opération après la première opération. Rien n'est impliqué concernant l'achèvement de la première opération avant que la deuxième opération ne soit initiée. Par exemple, si la première opération met à jour les emplacements X et Y, mais que la deuxième opération n'accède qu'à l'emplacement X, aucune garantie n'est définie par rapport à l'emplacement Y et à la deuxième opération.

Afin de prendre en charge les grands transferts de données découpés en plusieurs paquets et envoyés via plusieurs chemins à travers le fabric, l'ordre des données peut être limité aux transferts d'une taille spécifique ou inférieure. Les fournisseurs spécifient quand l'ordre des données est maintenu à travers les valeurs suivantes. Notez que même si l'ordre des données n'est pas maintenu, l'ordre des messages peut l'être.

max_order_raw_size
Taille de lecture après écriture. Si défini, une opération de lecture RMA ou atomique émise après une opération d'écriture RMA ou atomique, toutes deux de taille inférieure à la taille, sera ordonnée. Lorsque les emplacements de mémoire cible se chevauchent, l'opération de lecture RMA ou atomique verra les résultats de l'écriture RMA ou atomique précédente.
max_order_war_size
Taille d'écriture après lecture. Si défini, une opération d'écriture RMA ou atomique émise après une opération de lecture RMA ou atomique, toutes deux de taille inférieure à la taille, sera ordonnée. L'opération de lecture RMA ou atomique verra la valeur initiale de l'emplacement de mémoire cible avant qu'une écriture RMA ou atomique ultérieure ne mette à jour la valeur.
max_order_waw_size
Taille d'écriture après écriture. Si défini, une opération d'écriture RMA ou atomique émise après une opération d'écriture RMA ou atomique, toutes deux de taille inférieure à la taille, sera ordonnée. L'emplacement de mémoire cible reflétera les résultats de la deuxième écriture RMA ou atomique.

Une valeur de taille d'ordre de 0 indique que l'ordre n'est pas garanti. Une valeur de -1 garantit l'ordre pour toute taille de données.

mem_tag_format - Format de balise mémoire

Le champ de format de balise mémoire est utilisé pour transmettre des informations sur l'utilisation des paramètres tag et ignore dans les appels d'API fi_tagged, ainsi que les critères de correspondance. Ces informations sont utilisées par le fournisseur pour optimiser la prise en charge de la correspondance des balises, y compris l'alignement avec les protocoles de transport. Les formats de balise suivants sont définis :

FI_TAG_BITS
Si spécifié en entrée de fi_getinfo, cela indique que les balises contiennent jusqu'à 64 bits de données, et le récepteur doit appliquer ignore_bits aux balises lors de la correspondance des tampons de réception avec les envois. La sortie de fi_getinfo définira 0 ou plusieurs bits de poids fort de mem_tag_format à 0 pour indiquer ces bits de balise qui sont ignorés ou réservés par le fournisseur. Les applications doivent vérifier le nombre de bits de poids fort qui sont à 0 et les définir à 0 sur tous les bits de balise et d'ignore.

La valeur de FI_TAG_BITS est 0, ce qui en fait le comportement par défaut si les indications sont laissées non initialisées après avoir été allouées par fi_allocinfo(). Ce format offre la plus grande flexibilité aux applications, mais limite les options d'optimisation du fournisseur. FI_TAG_BITS s'aligne sur le comportement défini pour les versions 1.x de libfabric.

FI_TAG_MPI
FI_TAG_MPI est une utilisation contrainte de FI_TAG_BITS. Lorsqu'il est sélectionné, les applications traitent la balise comme des champs de données, plutôt que comme des bits, avec la possibilité de générer un joker pour chaque champ. Le format de balise MPI cible spécifiquement les implémentations et applications basées sur MPI. Une balise au format MPI se compose de 2 champs : une balise de message et un identifiant de charge utile. La balise de message est une balise de 32 bits pouvant être recherchée. La correspondance sur une balise de message nécessite de rechercher dans une liste de tampons publiés sur le récepteur, ce que nous appelons une balise pouvant être recherchée. L'entier tag dans les messages point-à-point MPI peut être mappé directement au champ de balise de message de libfabric.

Le deuxième champ est un identifiant qui correspond à l'opération ou aux données transportées dans la charge utile du message. Par exemple, ce champ peut être utilisé pour identifier le type d'opération collective associée à une charge utile de message. Notez que seule la taille et le comportement pour les formats de balise MPI sont définis. L'utilisation décrite des champs n'est qu'une suggestion.

Les applications qui utilisent le format MPI doivent initialiser leurs balises à l'aide de la fonction fi_tag_mpi(). Les bits d'ignore doivent être spécifiés comme FI_MPI_IGNORE_TAG, FI_MPI_IGNORE_PAYLOAD, ou leur combinaison par OU binaire.

FI_TAG_CCL
Le format FI_TAG_CCL restreint davantage le format FI_TAG_MPI. Lorsqu'il est utilisé, un seul champ de balise peut être défini, qui doit correspondre exactement à la cible. Le champ ne peut pas être généré en joker. Le format de balise CCL cible les bibliothèques et applications de communication collective. Le format CCL se compose d'un seul champ : un identifiant de charge utile. L'identifiant correspond à l'opération ou aux données transportées dans la charge utile du message. Par exemple, ce champ peut être utilisé pour identifier si un message est destiné à une communication point-à-point ou fait partie d'une opération collective, et dans ce dernier cas, le type d'opération collective.

Le format de balise CCL ne nécessite pas la recherche de tampons de réception correspondants, mais seulement le routage du message vers la file de messages virtuelle correcte en fonction de l'identifiant de charge utile.

Les applications qui utilisent le format CCL passent l'identifiant de charge utile directement comme balise et définissent les bits d'ignore à 0.

FI_TAG_MAX_FORMAT
Si la valeur de mem_tag_format est >= FI_TAG_MAX_FORMAT, le format de balise est traité comme un ensemble de champs de bits. Le comportement est fonctionnellement identique à FI_TAG_BITS. La description suivante est fournie pour la compatibilité ascendante et décrit comment le fournisseur peut interpréter le champ mem_tag_format si la valeur est >= FI_TAG_MAX_FORMAT.

Le format de balise mémoire peut être utilisé pour diviser le tableau de bits en champs séparés. Le mem_tag_format commence éventuellement par une série de bits définis à 0, pour signifier les bits qui sont ignorés par le fournisseur. Après le préfixe initial des bits d'ignore, le tableau consistera en des groupes alternés de bits définis à tous les 1 ou tous les 0. Chaque groupe de bits correspond à un champ balisé. L'implication de définir un champ balisé est que lorsqu'un masque est appliqué au tableau de bits balisés, tous les bits appartenant à un seul champ seront soit définis à 1, soit à 0, collectivement.

Par exemple, un mem_tag_format de 0x30FF indique la prise en charge de 14 bits balisés, séparés en 3 champs. Le premier champ se compose de 2 bits, le deuxième champ de 4 bits, et le dernier champ de 8 bits. Des masques valides pour un tel champ balisé seraient une combinaison par OU binaire de zéro ou plusieurs des valeurs suivantes : 0x3000, 0x0F00 et 0x00FF. Le fournisseur peut ne pas valider le masque fourni par l'application pour des raisons de performance.

En identifiant les champs au sein d'une balise, un fournisseur peut être en mesure d'optimiser ses routines de recherche. Une application qui demande des champs de balise doit fournir des masques de balise qui définissent tous les bits de masque correspondant à un champ soit à tous les 0, soit à tous les 1. Lors de la négociation des champs de balise, une application peut demander un nombre spécifique de champs d'une taille donnée. Un fournisseur doit renvoyer un format de balise qui prend en charge le nombre de champs demandés, chaque champ étant au moins de la taille demandée, ou échouer à la demande. Un fournisseur peut augmenter la taille des champs. Lors de la remontée des complétions (voir FI_CQ_FORMAT_TAGGED), il n'est pas garanti que le fournisseur effacera les bits de balise non pris en charge dans le champ de balise de l'entrée de complétion.

Il est recommandé que les tailles de champs soient ordonnées de la plus petite à la plus grande. Une balise générique et non structurée et un masque peuvent être obtenus en demandant un tableau de bits composé de 1 et 0 alternés.

tx_ctx_cnt - Nombre de contextes de transmission

Nombre de contextes de transmission à associer à l'extrémité. S'il n'est pas spécifié (0), 1 contexte sera assigné si l'extrémité prend en charge les transferts sortants. Les contextes de transmission sont des files de transmission indépendantes qui peuvent être configurées séparément. POINTS DE TERMINAISON ÉVOLUTIFS

Un point de terminaison évolutif est un port de communication qui prend en charge plusieurs contextes de transmission et de réception. Les points de terminaison évolutifs sont vaguement basés sur le concept réseau de mise à l'échelle côté transmission/réception, également connu sous le nom de multi-queue. La prise en charge des points de terminaison évolutifs est spécifique au domaine. Les points de terminaison évolutifs peuvent améliorer les performances des applications multithreads et parallèles, en permettant aux threads d'accéder à des files d'attente de transmission et de réception indépendantes. Un point de terminaison évolutif a une seule adresse au niveau du transport, ce qui peut réduire les besoins en mémoire pour stocker les données d'adressage distant, par rapport à l'utilisation de points de terminaison standard. Les points de terminaison évolutifs ne peuvent pas être utilisés directement pour les opérations de communication et nécessitent que l'application crée explicitement des contextes de transmission et de réception comme décrit ci-dessous.

fi_tx_context

Les contextes de transmission sont des files d'attente de transmission indépendantes. L'ordre et la synchronisation entre les contextes ne sont pas définis. Conceptuellement, un contexte de transmission se comporte de manière similaire à un point de terminaison d'envoi uniquement. Un contexte de transmission peut être configuré avec moins de capacités que le point de terminaison de base et avec des attributs différents (tels que les exigences d'ordre et la taille d'injection) que d'autres contextes associés au même point de terminaison évolutif. Chaque contexte de transmission a sa propre file d'attente de complétion. Le nombre de contextes de transmission associés à un point de terminaison est spécifié lors de la création du point de terminaison.

L'appel fi_tx_context est utilisé pour récupérer un contexte spécifique, identifié par un index (voir ci-dessus pour les détails sur les attributs du contexte de transmission). Les fournisseurs peuvent allouer des contextes dynamiquement lorsque fi_tx_context est appelé, ou peuvent créer statiquement tous les contextes lorsque fi_endpoint est invoqué. Par défaut, un contexte de transmission hérite des propriétés de son point de terminaison associé. Cependant, les applications peuvent demander des attributs spécifiques au contexte via le paramètre attr. La prise en charge des attributs par contexte de transmission est spécifique au fournisseur et n'est pas garantie. Les fournisseurs renverront les attributs réels attribués au contexte via le paramètre attr, s'il est fourni.

fi_rx_context

Les contextes de réception sont des files d'attente de réception indépendantes pour recevoir les données entrantes. L'ordre et la synchronisation entre les contextes ne sont pas garantis. Conceptuellement, un contexte de réception se comporte de manière similaire à un point de terminaison de réception uniquement. Un contexte de réception peut être configuré avec moins de capacités que le point de terminaison de base et avec des attributs différents (tels que les exigences d'ordre et la taille d'injection) que d'autres contextes associés au même point de terminaison évolutif. Chaque contexte de réception a sa propre file d'attente de complétion. Le nombre de contextes de réception associés à un point de terminaison est spécifié lors de la création du point de terminaison.

Les contextes de réception sont souvent associés à des flux de routage, qui spécifient quels paquets entrants ciblant un point de terminaison évolutif doivent être traités. Cependant, les contextes de réception peuvent être ciblés directement par l'initiateur, si le protocole sous-jacent le prend en charge. Ces contextes sont appelés « nommés ». La prise en charge des contextes nommés doit être indiquée en définissant la capacité FI_NAMED_RX_CTX lors de la création du point de terminaison correspondant. La prise en charge des contextes de réception nommés est coordonnée avec les vecteurs d'adresses. Voir fi_av(3) et fi_rx_addr(3).

L'appel fi_rx_context est utilisé pour récupérer un contexte spécifique, identifié par un index (voir ci-dessus pour les détails sur les attributs du contexte de réception). Les fournisseurs peuvent allouer des contextes dynamiquement lorsque fi_rx_context est appelé, ou peuvent créer statiquement tous les contextes lorsque fi_endpoint est invoqué. Par défaut, un contexte de réception hérite des propriétés de son point de terminaison associé. Cependant, les applications peuvent demander des attributs spécifiques au contexte via le paramètre attr. La prise en charge des attributs par contexte de réception est spécifique au fournisseur et n'est pas garantie. Les fournisseurs renverront les attributs réels attribués au contexte via le paramètre attr, s'il est fourni.

CONTEXTES PARTAGÉS

Les contextes partagés sont des contextes de transmission et de réception explicitement partagés entre un ou plusieurs points de terminaison. Un contexte partageable permet à une application d'utiliser une seule ressource fournisseur dédiée parmi plusieurs points de terminaison adressables par transport. Cela peut considérablement réduire les ressources nécessaires pour gérer la communication sur plusieurs points de terminaison en multiplexant le traitement de transmission et/ou de réception, avec le coût potentiel de sérialisation de l'accès entre plusieurs points de terminaison. La prise en charge des contextes partageables est spécifique au domaine.

Conceptuellement, les contextes de transmission partageables sont des files d'attente de transmission auxquelles plusieurs points de terminaison peuvent accéder. L'utilisation d'un contexte de transmission partagé est largement opaque pour une application. Les applications doivent allouer et lier des contextes de transmission partagés aux points de terminaison, mais les opérations sont publiées directement sur le point de terminaison. Les contextes de transmission partagés ne sont pas associés à des files d'attente de complétion ou à des compteurs. Les opérations terminées sont publiées dans les files d'attente de complétion liées au point de terminaison. Un point de terminaison ne peut être associé qu'à un seul contexte de transmission partagé.

Contrairement aux contextes de transmission partagés, les applications interagissent directement avec les contextes de réception partagés. Les utilisateurs publient des tampons de réception directement dans un contexte de réception partagé, les tampons étant utilisables par tout point de terminaison lié au contexte de réception partagé. Les contextes de réception partagés ne sont pas associés à des files d'attente de complétion ou à des compteurs. Les opérations de réception terminées sont publiées dans les files d'attente de complétion liées au point de terminaison. Un point de terminaison ne peut être associé qu'à un seul contexte de réception, et tous les points de terminaison sans connexion associés à un contexte de réception partagé doivent également partager le même vecteur d'adresses.

Les points de terminaison associés à un contexte de transmission partagé peuvent utiliser des contextes de réception dédiés, et vice versa. Ou un point de terminaison peut utiliser des contextes de transmission et de réception partagés. Et il n'y a aucune obligation que le même groupe de points de terminaison partageant un contexte d'un type partage également le contexte d'un type alternatif. De plus, un point de terminaison peut utiliser un contexte partagé d'un type, mais un ensemble évolutif de contextes du type alternatif.

fi_stx_context

Cet appel est utilisé pour ouvrir un contexte de transmission partageable (voir ci-dessus pour les détails sur les attributs du contexte de transmission). Les points de terminaison associés à un contexte de transmission partagé doivent utiliser un sous-ensemble des attributs du contexte de transmission. Notez que c'est l'inverse de l'exigence pour les contextes de transmission des points de terminaison évolutifs.

fi_srx_context

Ceci alloue un contexte de réception partageable (voir ci-dessus pour les détails sur les attributs du contexte de réception). Les points de terminaison associés à un contexte de réception partagé doivent utiliser un sous-ensemble des attributs du contexte de réception. Notez que c'est l'inverse de l'exigence pour les contextes de réception des points de terminaison évolutifs.

POINTS DE TERMINAISON SOCKET

La fonctionnalité et la description suivantes doivent être considérées comme expérimentales. Tant que la balise expérimentale n'est pas supprimée, les interfaces, la sémantique et les structures de données associées aux points de terminaison socket peuvent changer entre les versions de la bibliothèque.

Cette section s'applique aux points de terminaison de type FI_EP_SOCK_STREAM et FI_EP_SOCK_DGRAM, communément appelés points de terminaison socket.

Les points de terminaison socket sont définis avec une sémantique qui leur permet d'être plus facilement adoptés par les développeurs familiers avec l'API socket UNIX, ou par des middlewares qui exposent l'API socket, tout en tirant parti des fonctionnalités matérielles hautes performances.

La principale différence entre les points de terminaison socket et les autres points de terminaison actifs est que les points de terminaison socket utilisent des transferts de données synchrones. Les tampons passés aux opérations d'envoi et de réception reviennent sous le contrôle de l'application après le retour de l'appel de fonction. Par conséquent, aucune complétion de transfert de données n'est signalée à l'application, et les points de terminaison socket ne sont pas associés à des files d'attente de complétion ou à des compteurs.

Les points de terminaison socket prennent en charge un sous-ensemble des opérations de message : fi_send, fi_sendv, fi_sendmsg, fi_recv, fi_recvv, fi_recvmsg et fi_inject. Étant donné que les transferts de données sont synchrones, la valeur de retour des opérations d'envoi et de réception indique le nombre d'octets transférés en cas de succès, ou une valeur négative en cas d'erreur, y compris -FI_EAGAIN si le point de terminaison ne peut envoyer ou recevoir aucune donnée en raison de files d'attente pleines ou vides, respectivement.

Les points de terminaison socket sont associés à des files d'attente d'événements et à des vecteurs d'adresses, et traitent les événements de gestion de connexion de manière asynchrone, comme les autres points de terminaison. Contrairement aux sockets UNIX, les points de terminaison socket doivent toujours être déclarés comme actifs ou passifs.

Les points de terminaison socket se comportent comme des sockets non bloquants. Afin de prendre en charge la sémantique select et poll, les points de terminaison socket actifs sont associés à un descripteur de fichier qui est signalé chaque fois que le point de terminaison est prêt à envoyer et/ou recevoir des données. Le descripteur de fichier peut être récupéré à l'aide de fi_control.

INDICATEURS D'OPÉRATION

Les indicateurs d'opération sont obtenus en combinant les indicateurs suivants par OU. Les indicateurs d'opération définissent les indicateurs par défaut appliqués aux opérations de transfert de données d'un point de terminaison, là où un paramètre d'indicateurs n'est pas disponible. Les opérations de transfert de données qui prennent des indicateurs en entrée remplacent la valeur op_flags des attributs de contexte de transmission ou de réception d'un point de terminaison.

NAME

fi_pep_bind — bind a fabric endpoint to a provider resource

SYNOPSIS

#include <rdma/fabric.h>

int fi_pep_bind(struct fi_pep *pep, void *object,
    fi_addr_t *addr, size_t count);
int fi_pep_bind(struct fi_pep *pep, void *object,
    fi_addr_t *addr, size_t count);

ARGUMENTS

pep
A pointer to a fabric PEP object. This object must have been previously created by a call to fi_pep_open.
object
A pointer to the resource to bind to the PEP object. The type of object is determined by the flag parameter passed to fi_pep_open.
addr
A pointer to a list of fabric addresses. The addresses must correspond to the type of object being bound to the PEP.
count
The number of addresses in the addr list.

DESCRIPTION

The fi_pep_bind call binds a fabric PEP object to a provider resource. The type of resource being bound is determined by the flag parameter used when opening the PEP object via fi_pep_open.

For example, if the PEP was opened with the FI_PEP_JOIN_MC flag, then the object parameter would be a pointer to a multicast group, and the addr parameter would be a list of addresses to join within that multicast group.

The fi_pep_bind call is used to associate a PEP with resources that it will manage or participate in. The specific behavior and required parameters for fi_pep_bind depend on the type of PEP being created.

The function call is used to bind a PEP to specific addresses. The type of addresses supported is determined by the PEP type and the flags used to open the PEP.

OPERATION FLAGS

FI_CQ_BIND
Indicates that a completion queue should be bound to the endpoint. The object parameter is a pointer to the completion queue object to bind. The addr and count parameters are ignored.
FI_MSG_BIND
Indicates that the endpoint is being bound to a message queue. The object parameter is a pointer to the message queue object. The addr and count parameters are ignored.
FI_SELECTIVE_COMPLETION
Indicates that completions should only be generated for operations that explicitly request them. The object parameter is ignored. The addr and count parameters are ignored. See fi_cq(3) for additional details on completion semantics.
FI_TRANSMIT_SOME
Indicates that data should be transmitted with associated completion indications. This means that a completion entry should not be generated (locally or at the peer) until the result of an operation has been made persistent. See fi_cq(3) for additional details on completion semantics.
FI_COMPLETION
Indicates that a completion queue entry should be written for data transfer operations. This flag only applies to operations issued on an endpoint that was bound to a completion queue with the FI_SELECTIVE_COMPLETION flag set, otherwise, it is ignored. See the fi_ep_bind section above for more detail.
FI_DELIVERY_COMPLETE
Indicates that a completion should be generated when the operation has been processed by the destination endpoint(s). See fi_cq(3) for additional details on completion semantics.
FI_INJECT
Indicates that all outbound data buffers should be returned to the user’s control immediately after a data transfer call returns, even if the operation is handled asynchronously. This may require that the provider copy the data into a local buffer and transfer out of that buffer. A provider can limit the total amount of send data that may be buffered and/or the size of a single send that can use this flag. This limit is indicated using inject_size (see inject_size above).
FI_INJECT_COMPLETE
Indicates that a completion should be generated when the source buffer(s) may be reused. See fi_cq(3) for additional details on completion semantics.
FI_MULTICAST
Indicates that data transfers will target multicast addresses by default. Any fi_addr_t passed into a data transfer operation will be treated as a multicast address.
FI_MULTI_RECV
Applies to posted receive operations. This flag allows the user to post a single buffer that will receive multiple incoming messages. Received messages will be packed into the receive buffer until the buffer has been consumed. Use of this flag may cause a single posted receive operation to generate multiple completions as messages are placed into the buffer. The placement of received data into the buffer may be subjected to provider specific alignment restrictions. The buffer will be released by the provider when the available buffer space falls below the specified minimum (see FI_OPT_MIN_MULTI_RECV).
FI_TRANSMIT_COMPLETE
Indicates that a completion should be generated when the transmit operation has completed relative to the local provider. See fi_cq(3) for additional details on completion semantics.

NOTES

Users should call fi_close to release all resources allocated to the fabric endpoint.

Endpoints allocated with the FI_CONTEXT or FI_CONTEXT2 mode bits set must typically provide struct fi_context(2) as their per operation context parameter. (See fi_getinfo.3 for details.) However, when FI_SELECTIVE_COMPLETION is enabled to suppress CQ completion entries, and an operation is initiated without the FI_COMPLETION flag set, then the context parameter is ignored. An application does not need to pass in a valid struct fi_context(2) into such data transfers.

Operations that complete in error that are not associated with valid operational context will use the endpoint context in any error reporting structures.

Although applications typically associate individual completions with either completion queues or counters, an endpoint can be attached to both a counter and completion queue. When combined with using selective completions, this allows an application to use counters to track successful completions, with a CQ used to report errors. Operations that complete with an error increment the error counter and generate a CQ completion event.

As mentioned in fi_getinfo(3), the ep_attr structure can be used to query providers that support various endpoint attributes. fi_getinfo can return provider info structures that can support the minimal set of requirements (such that the application maintains correctness). However, it can also return provider info structures that exceed application requirements. As an example, consider an application requesting no msg_order. The resulting output from fi_getinfo may have all the ordering bits set. The application can reset the ordering bits it does not require before creating the endpoint. The provider is free to implement a stricter ordering than is required by the application.

RETURN VALUES

Returns 0 on success. On error, a negative value corresponding to fabric errno is returned. For fi_cancel, a return value of 0 indicates that the cancel request was submitted for processing, a return value of -FI_EAGAIN indicates that the request could not be submitted and that it should be retried once progress has been made. For fi_setopt/fi_getopt, a return value of -FI_ENOPROTOOPT indicates the provider does not support the requested option.

Fabric errno values are defined in rdma/fi_errno.h.

ERRORS

-FI_EDOMAIN
A resource domain was not bound to the endpoint or an attempt was made to bind multiple domains.
-FI_ENOCQ
The endpoint has not been configured with necessary completion queue.
-FI_EOPBADSTATE
The endpoint’s state does not permit the requested operation.
