NOM

fi_cq - Opérations sur la file d'attente de complétion

fi_cq_open / fi_close
Ouvrir/fermer une file d'attente de complétion
fi_control
Contrôler l'opération ou les attributs du CQ.
fi_cq_read / fi_cq_readfrom / fi_cq_readerr
Lire une complétion depuis une file d'attente de complétion
fi_cq_sread / fi_cq_sreadfrom
Une lecture synchrone (bloquante) qui attend qu'une condition spécifiée soit remplie avant de lire une complétion depuis une file d'attente de complétion.
fi_cq_signal
Débloquer tout thread attendant dans fi_cq_sread ou fi_cq_sreadfrom.
fi_cq_strerror
Convertit les informations d'erreur spécifiques au fournisseur en une chaîne imprimable.

DESCRIPTION

Les files d'attente de complétion sont utilisées pour signaler les événements associés aux transferts de données. Elles sont associées aux envois et réceptions de messages, à la mémoire distante (RMA), aux opérations atomiques, aux messages tagués et aux événements déclenchés. Les événements signalés sont généralement associés à un point de terminaison du fabric, mais peuvent également faire référence à des régions mémoire utilisées comme cibles d'une opération RMA ou atomique.

fi_cq_open

fi_cq_open alloue une nouvelle file d'attente de complétion. Contrairement aux files d'attente d'événements, les files d'attente de complétion sont associées à un domaine de ressources et peuvent être entièrement déchargées dans le matériel du fournisseur.

Les propriétés et le comportement d'une file d'attente de complétion sont définis par la structure fi_cq_attr.

struct fi_cq_attr {
    size_t               size;      /* # entrées pour CQ */
    uint64_t             flags;     /* indicateurs d'opération */
    enum fi_cq_format    format;    /* format de complétion */
    enum fi_wait_obj     wait_obj;  /* objet d'attente demandé */
    int                  signaling_vector; /* affinité d'interruption */
    enum fi_cq_wait_cond wait_cond; /* format de condition d'attente */
    struct fid_wait     *wait_set;  /* ensemble d'attente optionnel, déprécié */
};
size
Spécifie la taille minimale d'une file d'attente de complétion. Une valeur de 0 indique que le fournisseur peut choisir une valeur par défaut.
flags
Indicateurs qui contrôlent la configuration du CQ.
- FI_AFFINITY
Indique que le champ signaling_vector (voir ci-dessous) est valide.
format
Les files d'attente de complétion permettent à l'application de sélectionner la quantité de détails qu'elle doit stocker et signaler. L'attribut format permet à l'application de sélectionner l'un des plusieurs formats de complétion, indiquant la structure des données que la file d'attente de complétion doit retourner lors de la lecture. Les formats pris en charge et les structures qui y correspondent sont listés ci-dessous. La signification des champs d'entrée du CQ est définie dans la section Champs de complétion.
- FI_CQ_FORMAT_UNSPEC
Si un format non spécifié est demandé, le CQ utilisera un format par défaut sélectionné par le fournisseur.
- FI_CQ_FORMAT_CONTEXT
Ne fournit que le contexte spécifié par l'utilisateur qui était associé à la complétion.
struct fi_cq_entry {
    void     *op_context; /* contexte d'opération */
};

wait_obj
Les CQ peuvent être associés à un objet d'attente spécifique. Les objets d'attente permettent aux applications de bloquer jusqu'à ce que l'objet d'attente soit signalé, indiquant qu'une complétion est disponible à lire. Les utilisateurs peuvent utiliser fi_control pour récupérer l'objet d'attente sous-jacent associé à un CQ, afin de l'utiliser dans d'autres appels système. Les valeurs suivantes peuvent être utilisées pour spécifier le
type d'objet d'attente associé à une CQ : FI_WAIT_NONE, FI_WAIT_UNSPEC, FI_WAIT_SET, FI_WAIT_FD, FI_WAIT_MUTEX_COND (obsolète), et FI_WAIT_YIELD. La valeur par défaut est FI_WAIT_NONE.
- FI_WAIT_NONE
Utilisé pour indiquer que l'utilisateur ne se bloquera pas (n'attendra pas) les complétions sur la CQ. Lorsque FI_WAIT_NONE est spécifié, l'application ne peut pas appeler fi_cq_sread ou fi_cq_sreadfrom.
- FI_WAIT_UNSPEC
Spécifie que l'utilisateur n'attendra sur la CQ qu'à l'aide d'appels d'interface fabric, tels que fi_cq_sread ou fi_cq_sreadfrom. Dans ce cas, le fournisseur sous-jacent peut sélectionner l'objet d'attente le plus approprié ou le plus performant disponible, y compris des mécanismes d'attente personnalisés. Les applications qui sélectionnent FI_WAIT_UNSPEC ne sont pas garanties de récupérer l'objet d'attente sous-jacent.
- FI_WAIT_SET (obsolète)
Indique que la file de complétion doit utiliser un objet ensemble d'attente pour attendre les complétions. Si spécifié, le champ wait_set doit référencer un objet ensemble d'attente existant.
- FI_WAIT_FD
Indique que la CQ doit utiliser un descripteur de fichier comme mécanisme d'attente. Un objet d'attente de descripteur de fichier doit être utilisable dans les routines select, poll et epoll. Cependant, un fournisseur peut signaler un objet d'attente FD en le marquant comme lisible, inscriptible, ou avec une erreur.
- FI_WAIT_MUTEX_COND (obsolète)
Spécifie que la CQ doit utiliser un mutex pthread et une variable de condition comme objet d'attente.
- FI_WAIT_YIELD
Indique que la CQ attendra sans objet d'attente mais cédera plutôt la main à chaque attente. Permet l'utilisation de fi_cq_sread et fi_cq_sreadfrom via une rotation active.
signaling_vector
Si l'indicateur FI_AFFINITY est défini, cela indique le numéro de CPU logique (0..max cpu - 1) que les interruptions associées à la CQ doivent cibler. Ce champ doit être traité comme une suggestion pour le fournisseur et peut être ignoré si le fournisseur ne prend pas en charge l'affinité des interruptions.
wait_cond
Par défaut, lorsqu'une complétion est insérée dans une CQ qui prend en charge les lectures bloquantes (fi_cq_sread/fi_cq_sreadfrom), l'objet d'attente correspondant est signalé. Les utilisateurs peuvent spécifier une condition qui doit d'abord être remplie avant que l'attente soit satisfaite. Ce champ indique comment le fournisseur doit interpréter le champ cond, qui décrit la condition nécessaire pour signaler l'objet d'attente.

Une condition d'attente doit être traitée comme une optimisation. Les fournisseurs ne sont pas tenus de satisfaire les exigences de la condition avant de signaler l'objet d'attente. Les applications ne doivent pas compter sur le fait que la condition soit nécessairement vraie lorsqu'un appel de lecture bloquante se termine.

Si wait_cond est défini à FI_CQ_COND_NONE, alors aucune condition supplémentaire n'est appliquée au signal de l'objet d'attente de la CQ, et l'insertion de toute nouvelle entrée déclenchera la condition d'attente. Si wait_cond est défini à FI_CQ_COND_THRESHOLD, alors le champ cond est interprété comme une valeur de seuil size_t. Le seuil indique le nombre d'entrées qui doivent être mises en file dans la CQ avant que l'attente soit satisfaite.

Ce champ est ignoré si wait_obj est défini à FI_WAIT_NONE.

wait_set (obsolète)
Si wait_obj est FI_WAIT_SET, ce champ référence un objet d'attente auquel la file de complétion doit s'attacher. Lorsqu'un événement est inséré dans la file de complétion, l'ensemble d'attente correspondant sera signalé si toutes les conditions nécessaires sont remplies. L'utilisation d'un wait_set permet une méthode optimisée d'attente des événements à travers plusieurs files d'événements et de complétions. Ce champ est ignoré si wait_obj n'est pas FI_WAIT_SET.

fi_close

L'appel fi_close libère toutes les ressources associées à une file de complétion. Toute complétion restant dans la CQ lors de sa fermeture est perdue.

Lors de la fermeture de la CQ, il ne doit y avoir aucun point de terminaison ouvert, ni contexte de transmission ou de réception associé à la CQ. Si des ressources sont toujours associées à la CQ lors de la tentative de fermeture, l'appel retournera -FI_EBUSY.

fi_control

L'appel fi_control est utilisé pour accéder aux détails spécifiques au fournisseur ou à l'implémentation de la file de complétion. L'accès à la CQ doit être sérialisé sur tous les appels lorsque fi_control est invoqué, car cela peut rediriger l'implémentation des opérations de CQ. Les commandes de contrôle suivantes sont utilisables avec une CQ.

FI_GETWAIT (void **)
Cette commande permet à l'utilisateur de récupérer l'objet d'attente de bas niveau associé à la CQ. Le format de l'objet d'attente est spécifié lors de la création de la CQ, à travers les attributs de la CQ. Le paramètre arg de fi_control doit être une adresse où un pointeur vers l'objet d'attente retourné sera écrit. Voir fi_eq.3 pour plus de détails sur l'utilisation de fi_control avec FI_GETWAIT.

fi_cq_read

L'opération fi_cq_read effectue une lecture non bloquante des données de complétion depuis la CQ. Le format de l'événement de complétion est déterminé à l'aide de l'option fi_cq_format qui a été spécifiée lorsque la CQ a été ouverte. Plusieurs complétions peuvent être récupérées depuis une CQ dans un seul appel. Le nombre maximal d'entrées à retourner est limité au paramètre count spécifié, avec le nombre d'entrées lues avec succès depuis la CQ retourné par l'appel. (Voir la section des valeurs de retour ci-dessous.) Une valeur de count de 0 peut être utilisée pour faire progresser les points de terminaison associés lorsque la progression manuelle est activée.

Les CQ sont optimisées pour signaler les opérations qui se sont terminées avec succès. Les opérations qui échouent sont signalées « hors bande ». De telles opérations sont récupérées à l'aide de la fonction fi_cq_readerr. Lorsqu'une opération qui s'est terminée avec une erreur inattendue est rencontrée, elle est placée dans une file d'erreur temporaire. Tenter de lire depuis une CQ alors qu'un élément est dans la file d'erreur entraîne l'échec de fi_cq_read avec un code de retour de -FI_EAVAIL. Les applications peuvent utiliser ce code de retour pour déterminer quand appeler fi_cq_readerr.

fi_cq_readfrom

L'appel fi_cq_readfrom se comporte de manière identique à fi_cq_read, à l'exception qu'il permet à la CQ de retourner des informations d'adresse source à l'utilisateur pour toutes les données reçues. Les données d'adresse source ne sont disponibles que pour les points de terminaison configurés avec la capacité FI_SOURCE. Si fi_cq_readfrom est appelé sur un point de terminaison pour lequel les données d'adressage source ne sont pas disponibles, l'adresse source sera définie à FI_ADDR_NOTAVAIL. Le nombre d'entrées src_addr d'entrée doit être le même que le paramètre count.

Les données d'adressage source retournées sont converties depuis l'adresse native utilisée par le fabric sous-jacent en un fi_addr_t, qui peut être utilisé dans les opérations de transmission. Dans la plupart des circonstances, le retour d'un fi_addr_t nécessite que l'adresse source ait déjà été insérée dans le vecteur d'adresses associé au point de terminaison de réception. C'est le cas pour les vecteurs d'adresses de type FI_AV_TABLE. Dans certains fournisseurs lorsque FI_AV_MAP est utilisé, les adresses source peuvent être converties algorithmiquement en un fi_addr_t utilisable, même si l'adresse source n'a pas été insérée dans le vecteur d'adresses. Cela est permis par l'API, car cela permet au fournisseur d'éviter la recherche d'adresse dans le traitement des messages reçus. Dans aucun cas les fournisseurs n'insèrent des adresses dans un AV en dehors d'un appel de l'application à fi_av_insert ou un appel similaire.

Pour les points de terminaison alloués avec la capacité FI_SOURCE_ERR, si l'adresse source ne peut pas être convertie en une valeur fi_addr_t valide, fi_cq_readfrom retournera -FI_EAVAIL, même si les données ont été reçues avec succès. La complétion sera alors rapportée à travers fi_cq_readerr avec le code d'erreur -FI_EADDRNOTAVAIL. Voir fi_cq_readerr pour plus de détails.

Si FI_SOURCE est spécifié sans FI_SOURCE_ERR, les adresses source qui ne peuvent pas être mappées vers un fi_addr_t utilisable seront signalées comme FI_ADDR_NOTAVAIL.

fi_cq_sread / fi_cq_sreadfrom

Les appels fi_cq_sread et fi_cq_sreadfrom sont les opérations équivalentes bloquantes à fi_cq_read et fi_cq_readfrom. Leur comportement est similaire aux appels non bloquants, à l'exception que les appels ne retourneront pas jusqu'à ce qu'une complétion ait été lue depuis la CQ ou qu'une erreur ou un délai d'attente se produise.

Les threads bloqués dans cette fonction retourneront à l'appelant s'ils sont signalés par une source externe. C'est vrai même si le délai d'attente ne s'est pas écoulé ou s'il a été spécifié comme infini.

Il est invalide pour les applications d'appeler ces fonctions si la CQ a été configurée avec un objet d'attente de type FI_WAIT_NONE ou FI_WAIT_SET.

fi_cq_readerr

La fonction de lecture d'erreur, fi_cq_readerr, récupère les informations concernant toute opération asynchrone qui s'est terminée avec une erreur inattendue. fi_cq_readerr est un appel non bloquant, retournant immédiatement que la complétion d'erreur ait été trouvée ou non.

Les informations d'erreur sont rapportées à l'utilisateur à travers la structure fi_cq_err_entry. Le format de cette structure est défini ci-dessous.

struct fi_cq_err_entry {
    void     *op_context; /* operation context */
    uint64_t flags;       /* completion flags */
    size_t   len;         /* size of received data */
    void     *buf;        /* receive data buffer */
    uint64_t data;        /* completion data */
    uint64_t tag;         /* message tag */
    size_t   olen;        /* overflow length */
    int      err;         /* positive error code */
    int      prov_errno;  /* provider error code */
    void    *err_data;    /*  error data */
    size_t   err_data_size; /* size of err_data */
    fi_addr_t src_addr; /* error source address */
};

La raison générale de l'erreur est fournie à travers le champ err. Des informations d'erreur spécifiques au fournisseur peuvent également être disponibles à travers les champs prov_errno et err_data. Les utilisateurs peuvent appeler fi_cq_strerror pour convertir les informations d'erreur spécifiques au fournisseur en une chaîne imprimable à des fins de débogage. Voir les détails des champs ci-dessous pour plus d'informations sur l'utilisation de err_data et err_data_size.

Notez que des complétions d'erreur sont générées pour toutes les opérations, y compris celles pour lesquelles une complétion n'a pas été demandée (par exemple, un point de terminaison est configuré avec FI_SELECTIVE_COMPLETION, mais la requête n'avait pas l'indicateur FI_COMPLETION défini). Dans de tels cas, les fournisseurs renverront autant d'informations que ce qui est rendu disponible par le logiciel et le matériel sous-jacents concernant la défaillance, les autres champs seront définis à NULL ou 0. Cela inclut la valeur op_context, qui n'aurait peut-être pas été fournie ou a été ignorée en entrée dans le cadre du transfert.

Les codes d'erreur de complétion notables sont donnés ci-dessous.

FI_EADDRNOTAVAIL
Ce code d'erreur est utilisé par les CQ configurés avec FI_SOURCE_ERR pour signaler des complétions pour lesquelles une adresse source fi_addr_t utilisable n'a pas pu être trouvée. Un code d'erreur FI_EADDRNOTAVAIL indique que le transfert de données a été reçu et traité avec succès, les champs fi_cq_err_entry contenant des informations sur la complétion. Le champ err_data sera défini sur les données de l'adresse source. L'adresse source sera dans le même format que celui spécifié via le champ addr_format de fi_info pour le domaine ouvert. Celle-ci peut être passée directement à un appel fi_av_insert pour ajouter l'adresse source au vecteur d'adresses.

Pour les versions d'API 1.20 et ultérieures, si l'EP est configuré avec FI_AV_AUTH_KEY, src_addr sera défini sur le gestionnaire de clé d'autorisation fi_addr_t ou un identifiant de clé d'autorisation défini par l'utilisateur correspondant au transfert de données entrant. Sinon, la valeur sera définie à FI_ADDR_NOTAVAIL.

fi_cq_signal

L'appel fi_cq_signal débloquera tout thread en attente dans fi_cq_sread ou fi_cq_sreadfrom. Cela peut être utilisé pour réveiller un thread qui est bloqué en attente de la lecture d'une opération de complétion. L'opération fi_cq_signal n'est disponible que si le CQ a été configuré avec un objet d'attente.

CHAMPS DE COMPLÉTION

Les structures de données d'entrée de CQ partagent de nombreux champs identiques. La signification de ces champs est la même pour tous les formats de structure d'entrée de CQ.

op_context
Le contexte d'opération est la valeur de contexte spécifiée par l'application qui a été fournie avec une opération asynchrone. Le champ op_context est valide pour toutes les complétions associées à une opération asynchrone.

Pour les événements de complétion qui ne sont pas associés à une opération publiée, ce champ sera défini à NULL. Cela inclut les complétions générées à la cible en réponse à des opécations d'écriture RMA qui transportent des données de CQ (indicateurs FI_REMOTE_WRITE | FI_REMOTE_CQ_DATA définis), lorsque le bit de mode FI_RX_CQ_DATA n'est pas requis.

flags
Cela spécifie les indicateurs associés à l'opération complétée. La Section des indicateurs de complétion ci-dessous liste les valeurs d'indicateurs valides. Les indicateurs sont définis pour toutes les complétions pertinentes.
len
Ce champ len s'applique aux opérations de réception complétées (par ex. fi_recv, fi_trecv, etc.) et aux écritures complétées avec des données de cq distantes côté répondeur (par ex. fi_write, avec l'indicateur FI_REMOTE_CQ_DATA). Il indique la taille du message de données transféré – c'est-à-dire combien d'octets de données ont été placés dans le tampon de réception/cible associé par un appel fi_send/fi_tsend/fi_write etc. correspondant. Si un point d'extrémité a été configuré avec le mode FI_MSG_PREFIX, len reflète également la taille du tampon de préfixe.
buf
Le champ buf n'est valide que pour les opérations de réception complétées, et ne s'applique que lorsque le tampon de réception a été publié avec l'indicateur FI_MULTI_RECV. Dans ce cas, buf pointe vers l'emplacement de départ où les données de réception ont été placées.
data
Le champ data n'est valide que si l'indicateur de complétion FI_REMOTE_CQ_DATA est défini, et ne s'applique qu'aux complétions de réception. Si FI_REMOTE_CQ_DATA est défini, ce champ contiendra les données de complétion fournies par le pair dans le cadre de sa requête d'émission. Les données de complétion seront données dans l'ordre des octets de l'hôte.
tag
Un tag ne s'applique qu'aux messages reçus qui se produisent via les interfaces taguées. Ce champ contient le tag qui était inclus avec le message reçu. Le tag sera dans l'ordre des octets de l'hôte.
olen
Le champ olen s'applique aux messages reçus. Il est utilisé pour indiquer qu'un message reçu a dépassé l'espace de tampon disponible et a été tronqué. Le olen spécifie la quantité de données qui n'a pas tenu dans le tampon de réception disponible et a été ignorée.
err
Ce code err est un errno de tissu positif associé à une complétion. La valeur err indique la raison générale d'une erreur, si une erreur s'est produite. Voir fi_errno.3 pour une liste des codes d'erreur possibles.
prov_errno
En cas d'erreur, prov_errno peut contenir un code d'erreur spécifique au fournisseur. L'utilisation de ce champ et sa signification sont spécifiques au fournisseur. Il est destiné à être utilisé comme aide au débogage. Voir fi_cq_strerror pour des détails supplémentaires sur la conversion de cette valeur d'erreur en une chaîne lisible par l'humain.
err_data
Le champ err_data est utilisé pour renvoyer des informations spécifiques au fournisseur, si disponibles, concernant l'erreur. En entrée, err_data doit référencer un tampon de données de taille err_data_size. En sortie, le fournisseur remplira ce tampon avec toutes les données spécifiques au fournisseur qui peuvent aider à identifier la cause de l'erreur. Le contenu du champ err_data et sa signification sont spécifiques au fournisseur. Il est destiné à être utilisé comme aide au débogage. Voir fi_cq_strerror pour des détails supplémentaires sur la conversion de ces données d'erreur en une chaîne lisible par l'humain. Voir la note de compatibilité ci-dessous sur la façon dont ce champ est utilisé pour les versions plus anciennes de libfabric.
err_data_size
En entrée, err_data_size indique la taille du tampon err_data en octets. En sortie, err_data_size sera défini au nombre d'octets copiés dans le tampon err_data. Les informations err_data sont généralement utilisées avec fi_cq_strerror pour fournir des détails sur le type d'erreur qui s'est produite.

Pour des raisons de compatibilité, le comportement des champs err_data et err_data_size peut être modifié par rapport à ce qui est listé ci-dessus. Si err_data_size vaut 0 en entrée, ou si le tissu a été ouvert avec une version < 1.5, alors tout tampon référencé par err_data sera ignoré en entrée. Dans cette situation, en sortie err_data sera défini sur un tampon de données appartenant au fournisseur. Le contenu du tampon restera valide jusqu'à un appel de lecture ultérieur contre le CQ. Les applications doivent sérialiser l'accès au CQ lors du traitement des erreurs pour s'assurer que le tampon référencé par err_data ne change pas.

src_addr
Utilisé pour renvoyer des informations liées à l'adresse source pour les événements d'erreur. La façon dont ce champ est utilisé est spécifique à l'événement d'erreur.

COMPLETION EVENT SEMANTICS

The libfabric completion event semantics define the earliest point at which a provider may report an operation as completed. This is controlled by operational flags passed to operations that generate completion events. These flags provide different levels of guarantees to the application about the state of the operation. Understanding these semantics is crucial for managing data buffers and handling potential communication failures.

The completion event semantics are defined with respect to the initiator of the operation. They describe when the initiator can safely reuse its data buffers and what state the operation must reach before a completion event is generated.

To illustrate the different levels, consider the analogy of mailing a letter:

  • Inject Complete (FI_INJECT_COMPLETE): This is like dropping a letter into your local mailbox. The post office (provider) has taken possession of it, and you can reuse your envelope (buffer). However, there's no guarantee it has left your immediate area or that it will reach its destination.

  • Transmit Complete (FI_TRANSMIT_COMPLETE): This is like the letter being picked up from your mailbox and dropped into the destination mailbox at the post office. It's on its way, and no longer dependent on your local mailbox. For reliable endpoints, this means it has been delivered to the peer endpoint's network interface; for unreliable endpoints, it means it has been handed off to the fabric. The state at the destination is not guaranteed.

  • Delivery Complete (FI_DELIVERY_COMPLETE): This is like someone signing for the letter at the destination. The letter has arrived and been processed by the recipient's end. If a receive buffer was ready, the data is in it. For operations returning data, this also applies to the source endpoint.

  • Match Complete (FI_MATCH_COMPLETE): This is similar to delivery complete, but requires the *intended* recipient to sign for the letter. The operation is not considered complete until it's matched with an application-specified buffer at the target. This allows for tighter synchronization but may introduce delays.

  • Commit Complete (FI_COMMIT_COMPLETE): This is the strongest guarantee, akin to the letter arriving at its destination and being placed in a fireproof safe. The operation's result is persistent and durable, even in case of power failure. This is currently an experimental feature for operations targeting persistent memory regions over reliable endpoints.

The operational flags that define these completion levels are:

FI_INJECT_COMPLETE
Indicates that the source buffer(s) may be reused. The provider guarantees that the buffers will not be read from again. No other guarantees are made regarding the state of the operation (e.g., transmission). This offers the fastest completion reporting and buffer reuse but the weakest guarantees against network errors. Note that this flag controls when a completion entry is generated and does not apply to operations like `fi_inject` that do not generate completion entries.
FI_TRANSMIT_COMPLETE
Indicates that the transmit operation has completed relative to the local provider.
  • For reliable endpoints: The operation has been delivered to the peer endpoint. It is no longer dependent on the fabric or local resources. The state at the peer endpoint is not defined (e.g., the message might be buffered on the target NIC).
  • For unreliable endpoints: The operation has been delivered to the fabric. It is no longer dependent on local resources. The state within the fabric is not defined.
FI_DELIVERY_COMPLETE
Indicates that an operation has been processed by the destination endpoint(s). The result of the operation is available, though additional steps might be needed at the destination to retrieve it (e.g., providing a receive buffer). This completion mode applies only to reliable endpoints. For operations returning data (RMA read, atomic-fetch), the source endpoint is also considered a destination. This is the default completion mode for such operations.
FI_MATCH_COMPLETE
Indicates that a completion is generated only after the operation has been matched with an application-specified buffer at the target. This ensures synchronization between peer applications but may involve additional delays. Many providers may not support this semantic.
FI_COMMIT_COMPLETE
Indicates that a completion is generated only after the result of an operation has been made persistent (locally or at the peer). The result is guaranteed to be available and durable, even in case of power failure. This applies only to operations targeting persistent memory regions over reliable endpoints and is considered experimental.
FI_FENCE
This is not a completion level itself but an ordering mechanism. Operations marked with `FI_FENCE` and all subsequent operations targeting the same peer are deferred until all preceding operations to that peer have completed. The completion of a fenced operation signifies that all prior operations have met the same completion level as the fenced operation, even if they were posted with a lower level. For example, `FI_DELIVERY_COMPLETE | FI_FENCE` means prior operations have met `FI_DELIVERY_COMPLETE` requirements.

The completion semantics help applications determine when to reuse data buffers and understand the state of operations, aiding in error handling for communication failures.

TARGET COMPLETION SEMANTICS

Target completion semantics determine when data written to a target memory location becomes visible to a peer application. Visibility means that a memory read to that address will return the results of the transfer. This visibility can be global, meaning accessible from anywhere (CPU, fabric, peer devices like GPUs).

Typically, target visibility implies that the transfer meets at least `FI_DELIVERY_COMPLETE` requirements from the target's perspective. The target's completion semantic is not always directly tied to the initiator's specified semantic.

Target processes often rely on default semantics, which are influenced by factors such as:

  • Whether a completion event is generated at the target.

  • The type of transfer (message vs. RMA).

  • Endpoint ordering guarantees.

  • Properties of the target memory buffer.

  • The initiator's specified completion semantic.

Generally, target completion semantics are categorized by whether a completion event is generated at the target (e.g., updating a CQ entry or counter). Message-based transfers (`FI_MSG`, `FI_TAGGED`) usually generate target events, while RMA transfers (`FI_RMA`, `FI_ATOMIC`) often do not. Exceptions exist, such as RMA writes carrying remote CQ data, which generate target completion events and signal visibility to the target application.

By default, completions generated at the target indicate that the transferred data is immediately readable from the target buffer. This means the target experiences at least `FI_DELIVERY_COMPLETE` semantics, regardless of what the initiator requested. This default behavior is often sufficient for applications using host memory buffers.

En l'absence d'une complétion à la cible, lorsqu'une complétion d'une opération est écrite à l'initiateur, la sémantique de visibilité de l'opération à la cible s'aligne sur la sémantique de complétion de l'initiateur. Par exemple, si une opération RMA se termine à l'initiateur avec soit FI_INJECT_COMPLETE soit FI_TRANSMIT_COMPLETE, la visibilité des données à la cible n'est pas garantie.

Un ou plusieurs des mécanismes suivants peuvent être utilisés par le processus cible pour garantir que les résultats d'un transfert de données qui n'a pas généré de complétion à la cible sont maintenant visibles. Cette liste n'est pas exhaustive de toutes les options, mais définit les usages courants. Dans les descriptions ci-dessous, le premier transfert ne résulte pas en un événement de complétion à la cible, mais est éventuellement suivi d'un transfert qui en génère un.

•
Si le point de terminaison garantit l'ordre des messages entre deux transferts, la complétion à la cible d'un second transfert indiquera que les données du premier transfert sont disponibles. Par exemple, si le point de terminaison supporte l'ordre d'envoi après écriture (FI_ORDER_SAW), alors une complétion de réception correspondant à l'envoi indiquera que les données écrites sont disponibles. Cela tient indépendamment de la sémantique de complétion de l'initiateur pour l'écriture ou l'envoi. Lorsque l'ordre est garanti, le second transfert peut être mis en file d'attente auprès du fournisseur immédiatement après la mise en file du premier.
•
Si le point de terminaison ne garantit pas l'ordre des messages, l'initiateur doit prendre des mesures supplémentaires pour assurer la visibilité. Si l'initiateur demande la sémantique FI_DELIVERY_COMPLETE pour la première opération, il peut attendre que l'opération se termine localement. Une fois la complétion lue, la complétion à la cible d'un second transfert indiquera que les données du premier transfert sont visibles.
•
Alternativement, si l'ordre des messages n'est pas garanti par le point de terminaison, l'initiateur peut utiliser les indicateurs FI_FENCE et FI_DELIVERY_COMPLETE sur le second transfert de données pour forcer les premiers transferts à satisfaire la sémantique FI_DELIVERY_COMPLETE. Si le second transfert génère une complétion à la cible, cela indiquera que les données sont visibles. Sinon, une complétion à la cible pour tout transfert après l'opération clôturée indiquera que les données sont visibles.

Les sémantiques ci-dessus s'appliquent aux transferts ciblant des tampons de mémoire hôte traditionnels. Cependant, le comportement peut différer lorsque la mémoire de dispositif et/ou la mémoire persistante sont impliquées (bits de capacité FI_HMEM et FI_PMEM). Lorsque la mémoire hétérogène est impliquée, le concept de domaines de mémoire entre en jeu. Les domaines de mémoire identifient la séparation physique de la mémoire, qui peut ou non être accessible à travers le même espace d'adressage virtuel. Voir la page de manuel fi_mr(3) pour plus de détails sur les domaines de mémoire.

L'ordre des complétions et la visibilité des données ne sont bien définis que pour les transferts ciblant le même domaine de mémoire. Les applications doivent être conscientes des différences d'ordre et de visibilité lorsque les transferts ciblent différents domaines de mémoire. De plus, les applications doivent également se préoccuper du domaine de mémoire dans lequel les complétions elles-mêmes sont écrites et s'il diffère du domaine de mémoire ciblé par un transfert. Dans certaines situations, soit le fournisseur soit l'application peuvent avoir besoin d'appeler des API spécifiques au dispositif pour synchroniser ou vider les caches de mémoire du dispositif afin d'obtenir la visibilité des données souhaitée.

Lorsque la mémoire hétérogène est utilisée, la sémantique de complétion à la cible par défaut pour les transferts qui génèrent une complétion à la cible est toujours FI_DELIVERY_COMPLETE, cependant, les applications doivent être conscientes qu'il peut y avoir un impact négatif sur les performances globales pour les fournisseurs afin de satisfaire cette exigence.

Par exemple, un processus cible peut utiliser un GPU pour accélérer des calculs. Une région de mémoire mappant vers la mémoire sur le GPU peut être exposée aux pairs soit comme une cible RMA soit publiée localement comme un tampon de réception. Dans ce cas, l'application est concernée par deux domaines de mémoire – la mémoire système et la mémoire GPU. Les complétions sont écrites dans la mémoire système.

En continuant l'exemple, un processus pair envoie un message étiqueté. Ce message est apparié avec le tampon de réception situé dans la mémoire GPU. La NIC copie les données du réseau vers le tampon de réception et écrit une entrée dans la file de complétion. Notez que les deux domaines de mémoire ont été accessibles dans le cadre de ce transfert. Les données du message ont été dirigées vers la mémoire GPU, mais la complétion est allée vers la mémoire hôte. Comme des domaines de mémoire séparés peuvent ne pas être synchronisés les uns avec les autres, il est possible que le CPU hôte voie et traite l'entrée de complétion avant que le transfert vers la mémoire GPU ne soit visible soit pour le GPU hôte soit même pour le logiciel s'exécutant sur le GPU. Du point de vue du fournisseur, la visibilité de la complétion n'implique pas la visibilité des données écrites dans le domaine de mémoire du GPU.

La sémantique de complétion par défaut à la cible application pour les opérations de message est FI_DELIVERY_COMPLETE. Une implémentation de fournisseur anticipée dans cette situation est que le logiciel du fournisseur s'exécutant sur le CPU hôte intercepte l'entrée CQ, détecte que les données ont atterri dans la mémoire hétérogène, et effectue l'opération de synchronisation ou de vidage nécessaire du dispositif avant de signaler la complétion à l'application. Cela garantit que les données sont visibles pour le CPU et le logiciel GPU avant que l'application ne traite la complétion.

En plus du coût du logiciel du fournisseur interceptant les complétions et vérifiant si un transfert cible la mémoire hétérogène, la synchronisation du dispositif elle-même peut impacter les performances. Par conséquent, les applications peuvent demander une sémantique de complétion plus basse lors de la publication de réceptions. Cela indique au fournisseur que l'application sera responsable du traitement de toute opération de vidage spécifique au dispositif qui pourrait être nécessaire. Voir fi_msg(3) FLAGS.

Pour les transferts de données qui ne génèrent pas de complétion à la cible, tels que RMA ou atomiques, il est de la responsabilité de l'application de s'assurer que tous les tampons cibles répondent aux exigences de visibilité nécessaires de l'application. Les méthodes à puces mentionnées précédemment pour notifier la cible que les données sont visibles peuvent ne pas être suffisantes, car le logiciel du fournisseur à la cible pourrait manquer du contexte nécessaire pour assurer la visibilité. Cela implique que l'application pourrait avoir besoin d'appeler directement les API de synchronisation/vidage du dispositif.

Par exemple, une application pair pourrait effectuer plusieurs écritures RMA ciblant des tampons de mémoire GPU. Si le fournisseur décharge les opérations RMA dans la NIC, le logiciel du fournisseur à la cible ne sera pas au courant que les opérations RMA ont eu lieu. Si le pair envoie un message à l'application cible indiquant que les opérations RMA sont terminées, l'application doit s'assurer que les données RMA sont visibles pour le CPU ou le GPU hôte avant d'exécuter du code qui accède aux données. La complétion à la cible d'avoir reçu le message envoyé n'est pas suffisante, même si l'ordre d'envoi après écriture est supporté.

La plupart des sémantiques de complétion de la mémoire hétérogène à la cible correspondent à FI_TRANSMIT_COMPLETE ou FI_DELIVERY_COMPLETE. La mémoire persistante (capacité FI_PMEM), cependant, est souvent utilisée avec la sémantique FI_COMMIT_COMPLETE. Les concepts de complétion hétérogène s'appliquent toujours.

Pour les transferts marqués par l'initiateur avec FI_COMMIT_COMPLETE, une complétion à la cible indique que les résultats sont visibles et durables. Pour les transferts ciblant la mémoire persistante, mais utilisant une sémantique de complétion différente à l'initiateur, la visibilité à la cible est similaire à celle décrite ci-dessus. La durabilité n'est associée qu'aux transferts marqués avec FI_COMMIT_COMPLETE.

Pour les transferts ciblant la mémoire persistante qui demandent FI_DELIVERY_COMPLETE, une complétion, à l'initiateur ou à la cible, indique que les données sont visibles. La visibilité à la cible peut être transmise en utilisant l'un des mécanismes décrits ci-dessus – générer une complétion à la cible, envoyer un message depuis l'initiateur, etc. De même, si l'initiateur a demandé FI_TRANSMIT_COMPLETE, des étapes supplémentaires sont nécessaires pour assurer la visibilité à la cible. Par exemple, le transfert peut générer une complétion à la cible, ce qui indiquerait la visibilité, mais pas la durabilité. L'initiateur peut également suivre le transfert par une autre opération qui force la visibilité, comme utiliser FI_FENCE en conjonction avec FI_DELIVERY_COMPLETE.

NOTES

Une file de complétion doit être liée à au moins un point de terminaison activé avant que toute opération telle que fi_cq_read, fi_cq_readfrom, fi_cq_sread, fi_cq_sreadfrom etc. puisse y être appelée.

Si une file de complétion a été débordée, elle sera placée dans un état `overrun'. Les opérations de lecture continueront de retourner toute complétion valide et non corrompue, si disponible. Après que toutes les complétions valides ont été récupérées, toute tentative de lecture de la CQ résultera en un événement d'erreur FI_EOVERRUN. Les files de complétion débordées sont considérées comme fatales et ne peuvent pas être utilisées pour signaler des complétions supplémentaires une fois le débordement survenu.

VALEURS DE RETOUR

fi_cq_open / fi_cq_signal

: Retourne 0 en cas de succès. En cas d'erreur, retourne un errno de tissu négatif.

fi_cq_read / fi_cq_readfrom

: En cas de succès, retourne le nombre de complétions récupérées de la file de complétion. En cas d'erreur, retourne un errno de tissu négatif, avec ces deux erreurs explicitement identifiées : Si aucune complétion n'est disponible pour être lue depuis la CQ, retourne -FI_EAGAIN. Si la complétion la plus haute est pour un transfert échoué (une entrée d'erreur), retourne -FI_EAVAIL.

fi_cq_sread / fi_cq_sreadfrom

: En cas de succès, retourne le nombre de complétions récupérées de la file de complétion. En cas d'erreur, retourne un errno de tissu négatif, avec ces deux erreurs explicitement identifiées : Si le délai d'attente expire ou le thread appelant est signalé et qu'aucune donnée n'est disponible pour être lue depuis la file de complétion, retourne -FI_EAGAIN. Si la complétion la plus haute est pour un transfert échoué (une entrée d'erreur), retourne -FI_EAVAIL.

fi_cq_readerr

: En cas de succès, retourne la valeur positive 1 (nombre d'entrées d'erreur retournées). En cas d'erreur, retourne un errno de tissu négatif, avec cette erreur explicitement identifiée : Si aucune complétion d'erreur n'est disponible pour être lue depuis la CQ, retourne -FI_EAGAIN.

fi_cq_strerror

: Retourne une interprétation en chaîne de caractères du fournisseur erreur spécifique retournée avec une complétion.

Les valeurs errno de Fabric sont définies dans rdma/fi_errno.h.
