DESCRIPTION

Les vecteurs d'adresses (AV) sont utilisés pour mapper des adresses de plus haut niveau, qui peuvent être plus naturelles pour une application, en adresses spécifiques au fabric. Par exemple, un point d'extrémité peut être associé à une adresse struct sockaddr_in, indiquant que le point d'extrémité est joignable en utilisant un port TCP sur une adresse IPv4. Cela peut être vrai même si le point d'extrémité communique en utilisant un protocole réseau propriétaire. Le but de l'AV est d'associer une adresse de plus haut niveau à une valeur plus simple et plus efficace qui peut être utilisée par l'API libfabric d'une manière indépendante du fabric. L'adresse mappée est de type fi_addr_t et est renvoyée via un appel d'insertion AV.

Le processus de mappage d'une adresse est spécifique au fabric et au fournisseur, mais peut impliquer des protocoles de résolution d'adresses et de gestion de fabric longs. Les opérations AV sont synchrones par défaut (l'option asynchrone a été obsolète, voir ci-dessous). Voir la section NOTES pour les restrictions des AV sur les adresses dupliquées.

Obsolète : Les opérations AV peuvent être configurées pour fonctionner de manière asynchrone en spécifiant l'indicateur FI_EVENT à fi_av_open. Lors de la demande d'opération asynchrone, l'application doit d'abord lier une file d'événements à l'AV avant d'insérer des adresses.

fi_av_open

fi_av_open alloue ou ouvre un vecteur d'adresses. Les propriétés et le comportement du vecteur d'adresses sont définis par struct fi_av_attr.

struct fi_av_attr {
    enum fi_av_type  type;        /* type d'AV */
    int              rx_ctx_bits; /* bits d'adresse pour identifier le contexte rx */
    size_t           count;       /* nombre d'entrées pour AV */
    size_t           ep_per_node; /* nombre de points d'extrémité par adresse de fabric */
    const char       *name;       /* nom système de l'AV */
    void             *map_addr;   /* adresse mmap de base */
    uint64_t         flags;       /* indicateurs d'opération */
};
type
Un type d'AV correspond à une implémentation conceptuelle d'un vecteur d'adresses. Le type spécifie comment une application visualise les données stockées dans l'AV, y compris la manière dont elles peuvent être accessibles. Les valeurs valides sont :
- FI_AV_MAP (obsolète)
Les adresses insérées dans un AV sont mappées à une adresse native du fabric pour être utilisée par l'application. L'utilisation de FI_AV_MAP exige qu'une application stocke la valeur fi_addr_t renvoyée qui est associée à chaque adresse insérée. L'avantage de FI_AV_MAP est que la valeur fi_addr_t renvoyée peut contenir des données d'adresse encodées, qui sont immédiatement disponibles lors du traitement des requêtes de transfert de données. Cela peut éliminer ou réduire le nombre de recherches en mémoire nécessaires lors de l'initiation d'un transfert. Le désavantage de FI_AV_MAP est l'augmentation de l'utilisation de la mémoire nécessaire pour stocker les adresses renvoyées. Les adresses sont stockées dans l'AV en utilisant un mécanisme spécifique au fournisseur, y compris, mais sans s'y limiter, un arbre, une table de hachage ou maintenu sur le tas. Cette option est obsolète, et les fournisseurs sont encouragés à aligner le comportement de FI_AV_MAP avec FI_AV_TABLE.
- FI_AV_TABLE
Les adresses insérées dans un AV de type FI_AV_TABLE sont accessibles en utilisant un simple index. Conceptuellement, l'AV peut être traité comme un tableau d'adresses, bien que le fournisseur puisse implémenter l'AV en utilisant divers mécanismes. Lorsque FI_AV_TABLE est utilisé, le fi_addr_t renvoyé est un index, l'index d'une adresse insérée étant le même que son ordre d'insertion dans la table. L'index de la première adresse insérée dans une FI_AV_TABLE sera 0, et les insertions successives recevront des indices séquentiels. Des indices séquentiels seront attribués lors des appels d'insertion sur le même AV. Étant donné que les valeurs fi_addr_t renvoyées par un appel d'insertion sont déterministes, les applications n'ont peut-être pas besoin de fournir les paramètres de sortie fi_addr_t aux appels d'insertion. L'exception est lorsque les paramètres fi_addr_t sont également utilisés comme entrée pour fournir des clés d'authentification o

- FI_EVENT
(obsolète)
Lorsque le drapeau FI_EVENT est spécifié, toutes les opérations d'insertion sur ce AV se feront de manière asynchrone. Il y aura une entrée d'erreur EQ générée pour chaque échec d'insertion d'adresse, suivie d'un événement non-erreur indiquant que l'opération d'insertion est terminée. Il y aura toujours un événement de complétion non-erreur pour chaque op
ération d'insertion, même si toutes les adresses échouent. Le champ context dans toutes les complétions sera le contexte spécifié à l'appel d'insertion, et le champ data dans l'entrée de complétion finale rapportera le nombre d'adresses insérées avec succès. Si une erreur se produit pendant l'insertion asynchrone, une entrée de complétion d'erreur est reto
urnée (voir fi_eq(3) pour une discussion de la structure de complétion d'erreur fi_eq_err_entry). Le champ context de la complétion d'erreur sera le contexte qui a été spécifié dans l'appel d'insertion ; le champ data contiendra l'index de l'adresse ayant échoué. Une complétion d'erreur sera retournée pour chaque adresse qui échoue à s'insérer dans le AV.

Si un AV est ouvert avec FI_EVENT, toute tentative d'insertion avant qu'un EQ soit lié au AV échouera avec

-FI_ENOEQ.

d'erreur.

fi_av_inser

t

L'appel fi_av_insert insère zéro ou plusieurs adresses dans un AV. Le nombre d'adresses est spécifié à travers le paramètre count. Le paramètre addr référence un tableau d'adresses à insérer dans le AV. Les adresses insérées dans un vecteur d'adresses doivent être dans le même format que spécifié dans le champ addr_format de la structure fi_info fournie lors de l'ouverture du domaine correspondant. Lors de l'utilisation du format FI_ADDR_STR, le paramètre addr doit référencer un tableau de chaînes (char **)

.

Obsolète : Pour les AV de type FI_AV_MAP, une fois les adresses insérées mappées, les valeurs mappées sont écrites dans le tampon référencé par fi_addr. Le tampon fi_addr doit rester valide jusqu'à ce que l'insertion AV soit terminée et qu'un événement ait été généré pour une file d'événements associée. La valeur du fi_addr retourné doit être considérée comme opaque par l'application pour les AV de type FI_AV_MAP. La valeur retournée peut pointer vers une structure interne ou un codage spécifique au fournisseur de données d'adressage de bas niveau, par exemple. Dans ce dernier cas, l'utilisation de FI_AV_MAP peut permettre d'éviter les références mémoire pendant les opérations de transfert de

données.

Pour les AV de type FI_AV_TABLE, les adresses sont placées dans le tableau dans l'ordre. Une adresse est insérée à l'index le plus bas correspondant à un emplacement de tableau non utilisé, les indices commençant à 0. C'est-à-dire que la première adresse insérée peut être référencée à l'index 0, la deuxième à l'index 1, et ainsi de suite. Lorsque des adresses sont insérées dans un tableau AV, les valeurs fi_addr assignées seront de simples indices correspondant à l'entrée dans le tableau où l'adresse a été insérée. Les valeurs d'index s'accumulent à travers les appels d'insertion successifs dans l'ordre où les appels sont faits, pas nécessairement dans l'ordre où les insertions se

terminent.

Parce que les insertions se produisent à un index prédéterminé, le paramètre fi_addr peut être NULL. Si fi_addr est non-NULL, il doit référencer un tableau de fi_addr_t, et le tampon doit rester valide jusqu'à ce que l'opération d'insertion se termine. Notez que si fi_addr est NULL et qu'une opération synchrone est demandée sans utiliser le drapeau FI_SYNC_ERR, les échecs d'insertion individuels ne peuvent pas être rapportés et l'application doit utiliser d'autres appels, comme fi_av_lookup pour savoir quelles adresses spécifiques ont échoué à

s'insérer.

Si le vecteur d'adresses est configuré avec des clés d'autorisation, le paramètre fi_addr peut être utilisé comme entrée pour définir les clés d'autorisation associées aux adresses de point de terminaison en cours d'insertion. Cela se fait en définissant le fi_addr sur une clé d'autorisation fi_addr_t générée à partir de fi_av_insert_auth_key et en définissant le drapeau FI_AUTH_KEY. Si le drapeau FI_AUTH_KEY n'est pas défini, les adresses en cours d'insertion ne seront associées à aucune clé d'autorisation. Qu'une adresse puisse être dissociée d'une clé d'autorisation ou non dépend du fournisseur. Si un fournisseur ne peut pas prendre en charge cette dissociation, une erreur sera retournée. Lors d'une insertion réussie avec le drapeau FI_AUTH_KEY, les fi_addr_t retournés seront mappés à l'adresse du point de terminaison contre les clés d'autorisation spécifiées. Ces fi_addr_t peuvent être utilisés comme cible pour les opérations de transfert de données

locales.

Si le point de terminaison prend en charge FI_DIRECTED_RECV ou FI_TAGGED_DIRECTED_RECV, ces fi_addr_t peuvent être utilisés pour restreindre les tampons de réception à une adresse de point de terminaison et une clé d'autorisation

spécifiques.

Pour les vecteurs d'adresses configurés avec FI_AV_USER_ID, tous les événements cibles ultérieurs correspondant à l'adresse en cours d'insertion retourneront FI_ADDR_NOTAVAIL jusqu'à ce que l'utilisateur définisse un ID utilisateur pour ce fi_addr_t. Cela se fait en utilisant fi_av_set_user_id

.

FI_FIREWALL_ADDR
Ce drapeau indique que l'adresse se trouve derrière un pare-feu et que les connexions sortantes ne sont pas autorisées. S'il n'existe pas de connexion et que le fournisseur ne peut pas contourner le pare-feu, une erreur FI_EFIREWALLADDR doit être attendue. Si plusieurs adresses sont insérées simultanément, le drapeau s'applique à toutes. De plus, il est possible qu'une connexion soit disponible au moment de l'insertion, mais qu'elle soit plus tard déchirée. Les reconnexions futures déclenchées par des opérations sur l'ep (fi_send, par exemple) peuvent également échouer avec la même erreur.

fi_av_insertsvc

L'appel fi_av_insertsvc se comporte de manière similaire à fi_av_insert, mais permet à l'application de spécifier les noms de nœud et de service, de manière similaire aux entrées de fi_getinfo, plutôt qu'une adresse encodée. Les paramètres nœud et service sont définis de la même manière que dans fi_getinfo(3). Le nœud doit être une chaîne correspondant à un nom d'hôte ou à une adresse réseau. La chaîne de service correspond à une représentation textuelle d'une adresse de transport. Les applications peuvent également passer une adresse formatée FI_ADDR_STR comme paramètre nœud. Dans de tels cas, le paramètre service doit être NULL. Voir fi_getinfo.3 pour les détails sur l'utilisation de FI_ADDR_STR. Les drapeaux supportés sont les mêmes que pour fi_av_insert.

fi_av_insertsym

fi_av_insertsym effectue une insertion symétrique qui insère une plage séquentielle de nœuds et/ou d'adresses de service dans un AV. Le paramètre svccnt indique le nombre d'adresses de transport (point de terminaison) à insérer dans l'AV pour chaque adresse de nœud, avec le paramètre service spécifiant l'adresse de transport de départ. Les adresses de transport insérées seront dans la plage {service, service + svccnt - 1}, inclusive. Toutes les adresses de service pour un nœud seront insérées avant que le nœud suivant ne soit inséré.

Le paramètre nodecnt indique le nombre d'adresses de nœud (réseau) à insérer dans l'AV, avec le paramètre node spécifiant l'adresse de nœud de départ. Les adresses de nœud insérées seront dans la plage {node, node + nodecnt - 1}, inclusive. Si node est une chaîne non numérique, telle qu'un nom d'hôte, elle doit contenir un suffixe numérique si nodecnt > 1.

À titre d'exemple, si node = « 10.1.1.1 », nodecnt = 2, service = « 5000 » et svccnt = 2, les adresses suivantes seront insérées dans l'AV dans l'ordre indiqué : 10.1.1.1:5000, 10.1.1.1:5001, 10.1.1.2:5000, 10.1.1.2:5001. Si node était remplacé par le nom d'hôte « host10 », les adresses seraient : host10:5000, host10:5001, host11:5000, host11:5001.

Le nombre total d'adresses insérées sera nodecnt x svccnt.

Les drapeaux supportés sont les mêmes que pour fi_av_insert.

fi_av_remove

fi_av_remove supprime un ensemble d'adresses d'un vecteur d'adresses. Les valeurs fi_addr_t correspondantes sont invalidées et ne peuvent pas être utilisées dans des appels de transfert de données. Le comportement des opérations en cours qui référencent les adresses supprimées est indéfini.

Notez que la suppression d'une adresse peut ne pas désactiver la réception de données du point de terminaison pair. fi_av_close nettoiera automatiquement toute ressource associée.

Si l'adresse supprimée provient de fi_av_insert_auth_key, l'adresse ne sera supprimée que si tous les points de terminaison, qui ont été activés contre la clé d'autorisation correspondante, ont été fermés. Si tous les points de terminaison ne sont pas fermés, -FI_EBUSY sera retourné. De plus, le drapeau FI_AUTH_KEY doit être défini lors de la suppression d'une clé d'autorisation fi_addr_t.

fi_av_lookup

Cet appel retourne l'adresse stockée dans le vecteur d'adresses qui correspond au fi_addr donné. L'adresse retournée est dans le même format que celles stockées par l'AV. En entrée, le paramètre addrlen doit indiquer la taille du tampon addr. Si l'adresse réelle est plus grande que ce qui peut tenir dans le tampon, elle sera tronquée. En sortie, addrlen est défini à la taille du tampon nécessaire pour stocker l'adresse, qui peut être plus grande que la valeur d'entrée.

fi_rx_addr

Cette fonction est utilisée pour convertir une adresse de point de terminaison, retournée par fi_av_insert, en une adresse qui spécifie un contexte de réception cible. La valeur de rx_ctx_bits doit correspondre à celle spécifiée dans les attributs de l'AV pour l'adresse donnée.

Les points de terminaison connectés qui supportent plusieurs contextes de réception, mais qui ne sont pas associés à des vecteurs d'adresses, doivent spécifier FI_ADDR_NOTAVAIL pour le paramètre fi_addr.

fi_av_straddr

La fonction fi_av_straddr convertit l'adresse fournie en une chaîne imprimable. L'adresse spécifiée doit être dans le même format que celles stockées par l'AV, bien que l'adresse elle-même ne soit pas requise pour avoir été insérée. En entrée, le paramètre len doit spécifier la taille du tampon référencé par buf. En sortie, addrlen est défini à la taille du tampon nécessaire pour stocker l'adresse. Cette taille peut être plus grande que la longueur d'entrée. Si le tampon fourni est trop petit, les résultats seront tronqués. fi_av_straddr retourne un pointeur vers buf.

fi_av_insert_auth_key

Cette fonction associe des clés d'autorisation à un vecteur d'adresses. Cela nécessite que le domaine soit ouvert avec FI_AV_AUTH_KEY. FI_AV_AUTH_KEY permet aux points de terminaison et aux régions mémoire d'être associés à des clés d'autorisation provenant du vecteur d'adresses. Ce comportement permet à un point de terminaison ou à une région mémoire unique d'être associé à plusieurs clés d'autorisation.

Lorsque les points de terminaison ou les régions mémoire sont activés, ils sont configurés avec les clés d'autorisation du vecteur d'adresses à ce moment-là. Les insertions ultérieures de clés d'autorisation ne se propageront pas aux points de terminaison et aux régions mémoire déjà activés.

Les paramètres auth_key et auth_key_size sont utilisés pour entrer la clé d'autorisation dans le vecteur d'adresses. La structure de la clé d'autorisation est spécifique au fournisseur. Si auth_key_size ne correspond pas à la structure spécifique au fournisseur, -FI_EINVAL sera retourné.

La sortie de fi_av_insert_auth_key est un gestionnaire de clé d'autorisation fi_addr_t représentant toutes les adresses de point de terminaison contre cette clé d'autorisation spécifique. Pour toutes les opérations, y compris le vecteur d'adresses, l'enregistrement de mémoire et les transferts de données, qui peuvent accepter une clé d'autorisation fi_addr_t en entrée, le drapeau FI_AUTH_KEY doit être spécifié. Sinon, le fi_addr_t sera traité comme un fi_addr_t retourné par fi_av_insert et les fonctions associées.

Pour les points de terminaison activés avec FI_DIRECTED_RECV, les clés d'autorisation fi_addr_t peuvent être utilisées pour restreindre les messages entrants aux seules adresses de point de terminaison au sein de la clé d'autorisation. Cela nécessitera de passer le drapeau FI_AUTH_KEY à fi_recvmsg et fi_trecvmsg.

Pour les domaines activés avec FI_DIRECTED_RECV, les clés d'autorisation fi_addr_t peuvent être utilisées pour restreindre l'accès à la région mémoire aux seules adresses de point de terminaison au sein de la clé d'autorisation. Cela nécessitera de passer le drapeau FI_AUTH_KEY à fi_mr_regattr.

Ces clés d'autorisation fi_addr_t peuvent ensuite être utilisées comme entrée pour les fonctions d'insertion d'adresse de point de terminaison pour générer un fi_addr_t pour une adresse de point de terminaison et une clé d'autorisation spécifiques. Cela nécessitera de passer le drapeau FI_AUTH_KEY à fi_av_insert et les fonctions associées.

Pour les vecteurs d'adresses configurés avec FI_AV_USER_ID et les points de terminaison avec FI_SOURCE_ERR, tous les événements d'erreur FI_EADDRNOTAVAIL ultérieurs retourneront FI_ADDR_NOTAVAIL jusqu'à ce que l'utilisateur définisse un identifiant utilisateur pour cette clé d'autorisation fi_addr_t. Cela se fait en utilisant fi_av_set_user_id.

Pour les vecteurs d'adresses configurés sans FI_AV_USER_ID et les points de terminaison avec FI_SOURCE_ERR, tous les événements d'erreur FI_EADDRNOTAVAIL ultérieurs retourneront le gestionnaire de clé d'autorisation fi_addr_t.

Les drapeaux sont réservés pour une utilisation future et doivent être 0.

NOTE

S

Un AV ne doit stocker qu'une seule instance d'une adresse. Tenter d'insérer une copie en double de la même adresse dans un AV peut entraîner un comportement indéfini, selon l'implémentation du fournisseur. Les fournisseurs ne s

ont pas tenus de vérifier les doublons, car cela pourrait entraîner une charge importante pour le processus d'insertion. Pour assurer la portabilité, les applications peuvent avoir besoin de suivre quelles adresses de pairs ont
été insérées dans un AV donné afin d'éviter les entrées en double. Cependant, les fournisseurs doivent prendre en charge la suppression, suivie de la réinsertion d'une adresse. Seules les insertions en double sont restreintes.

IDENTIFIANTS UTILISATEUR POUR LES

ADRESSES

Comme décrit ci-dessus, les adresses de point de terminaison et les clés d'autorisation insérées dans un AV sont mappées à une valeur fi_addr_t. Le fi_addr_t d'adresse de point de terminaison est utilisé dans les API de transfert de données pour spécifier la destination d'un transfert sortant, dans les API de réception pour indiquer la source d'un transfert entrant, et également dans les événements de complétion pour signaler l'adresse source des transferts entrants. Les fi_addr_t de clé d'autorisation sont utilisés dans les API de réception et MR pour réserver les opérations entrantes à une clé d'autorisation spécifique, et également dans les événements d'erreur de complétion si le point de terminaison est configuré avec FI_SOURCE_ERR. Le bit de capacité et le drapeau FI_AV_USER_ID fournissent un mécanisme par lequel la valeur fi_addr_t rapportée par un événement de complétion réussi ou en erreur est remplacée par une valeur spécifiée par l'utilisateur. Cela est utile pour les applications qui doivent mapper l'adresse source à leur propre structure de

données.

La prise en charge de FI_AV_USER_ID dépend du fournisseur, car il peut ne pas être faisable pour un fournisseur de mettre en œuvre cette prise en charge sans surcoût important. Par exemple, certains fournisseurs peuvent avoir besoin d'ajouter un mécanisme de recherche inverse. Cette fonctionnalité peut être indisponible si des AV partagés sont demandés, ou avoir un impact négatif sur l'empreinte mémoire par processus si elle est implémentée. Pour les fournisseurs qui ne prennent pas en charge FI_AV_USER_ID, les utilisateurs peuvent être en mesure de faire un compromis entre le traitement de recherche et le surcoût du protocole, en transportant l'identification de la source dans un en-tête de

message.

Pour les vecteurs d'adresses ouverts sans FI_AV_USER_ID, les valeurs fi_addr_t spécifiées par l'utilisateur sont fournies dans le cadre de l'insertion d'adresses (par exemple fi_av_insert) via le paramètre fi_addr. Le paramètre fi_addr agit comme entrée/sortie dans ce cas. Lorsque le drapeau FI_AV_USER_ID est passé à l'un des appels d'insertion, l'appelant doit spécifier une valeur d'identifiant fi_addr_t à associer à chaque adresse. Le fournisseur enregistrera cet identifiant et l'utilisera là où c'est requis dans le cadre de tout événement de complétion. Notez que la sortie de l'appel d'insertion AV est inchangée. Le fournisseur renverra une valeur fi_addr_t qui mappe chaque adresse, et cette valeur doit être utilisée pour toutes les opérations de transfert de

données.

Pour les vecteurs d'adresses ouverts avec FI_AV_U

SER_ID, fi_av_set_user_id est utilisé pour déf
inir le fi_addr_t spécifié par l'utilisateur.

GROUPES DE

PAIRS

Les groupes de pairs fournissent un mapping direct vers les constructeurs de communicateurs HPC et

IA.

Les adresses dans un AV représentent l'ensemble complet des pairs avec lesquels un processus local peut communiquer. Un groupe de pairs représente conceptuellement un sous-ensemble de ces pairs. Un groupe de pairs peut être utilisé pour identifier des pairs travaillant sur une tâche commune, qui doivent avoir leur communication logiquement séparée des autres trafics. Les groupes de pairs ne sont pas un mécanisme de sécurité, mais aident plutôt à séparer les données. Un pair donné peut appartenir à 0 ou plusieurs groupes de pairs, sans limite sur le nombre de pairs pouvant appartenir à un seul groupe de

pairs.

Les groupes de pairs sont identifiés à l'aide d'une valeur entière, connue sous le nom d'identifiant de groupe. Les identifiants de groupe sont sélectionnés par l'utilisateur et transmis dans le cadre d'une valeur fi_addr_t. La gestion d'un identifiant de groupe et de sa relation avec les adresses insérées dans un AV est directement contrôlée par l'utilisateur. Lorsqu'il est activé, les messages envoyés sont marqués comme appartenant à un groupe de pairs spécifique, et les tampons de réception publiés doivent avoir un identifiant de groupe correspondant pour recevoir les

données.

Les utilisateurs sont responsables de la sélection d'un identifiant de groupe de pairs valide, sous réserve de la limitation négociée à l'aide de l'attribut de domaine max_group_id. L'identifiant de groupe d'un fi_addr_t peut être défini à l'aide de la fonction fi_group_addr()

VALEURS DE

RETOUR

Les appels d'insertion, à l'exclusion de fi_av_insert_auth_key, pour un AV ouvert pour un fonctionnement synchrone renverront le nombre d'adresses qui ont été insérées avec succès. En cas d'échec, la valeur de retour sera inférieure au nombre d'adresses

spécifié.

Obsolète : Les appels d'insertion, à l'exclusion de fi_av_insert_auth_key, pour un AV ouvert pour un fonctionnement asynchrone (avec le drapeau FI_EVENT spécifié) renverront FI_SUCCESS si l'opération a été initiée avec succès. En cas d'échec, un errno de fabric négatif sera renvoyé. Les fournisseurs sont autorisés à interrompre les opérations d'insertion en cas d'erreur. Les adresses qui ne sont pas insérées parce qu'elles ont été interrompues échoueront avec un code d'erreur

FI_ECANCELED.

Dans les deux modes de fonctionnement synchrone et asynchrone, le tampon fi_addr associé à une insertion échouée ou interrompue sera défini à FI_ADDR_NOTAVAIL

.

Tous les autres appels renvoient FI_SUCCESS en cas de succès, ou une

valeur négative correspondant à un errno de fabric en cas d'erreur.
Les valeurs de errno de fabric sont définies dans rdma/fi_errno.h.
