NOM

Partager un objet fabric entre différents fournisseurs ou ressources
struct fid_peer_av
Un vecteur d'adressage partageable entre fournisseurs indépendants
struct fid_peer_av_set
Un ensemble de vecteurs d'adressage partageable entre fournisseurs indépendants

Une file d'achèvement qui peut être partagée entre fournisseurs indépendants
struct fid_peer_cntr
Un compteur qui peut être partagé entre fournisseurs indépendants

Un contexte de réception partagé qui peut être partagé entre fournisseurs indépendants

SYNOPSIS

#include <rdma/fabric.h>
#include <rdma/fi_ext.h>
#include <rdma/providers/fi_peer.h>
int fi_export_fid(struct fid *fid, uint64_t flags,
    struct fid **expfid, void *context);
int fi_import_fid(struct fid *fid, struct fid *expfid, uint64_t flags);

ARGUMENTS

fid
Identifiant fabric renvoyé pour l'objet ouvert.
expfid
Objet fabric exporté qui peut être partagé avec un autre fournisseur.
flags
Drapeaux de contrôle pour l'opération.
*context:
Contexte défini par l'utilisateur qui sera associé à un objet fabric.

DESCRIPTION

AVIS : Les API peer décrites dans cette page man sont en développement et peuvent changer entre les versions de libfabric. Les structures de données et les définitions d'API ne doivent pas être considérées comme stables entre les versions. Les fournisseurs utilisés en tant que pairs doivent cibler la même version de libfabric.

Les fonctions définies dans cette page man sont généralement utilisées par les fournisseurs pour communiquer avec d'autres fournisseurs, appelés fournisseurs pairs, ou par d'autres bibliothèques pour communiquer avec le noyau de libfabric, appelées bibliothèques pairs. La plupart des intergiciels et des applications ne devraient pas avoir besoin d'accéder à cette fonctionnalité, car la documentation vise principalement les développeurs de fournisseurs.

Les fournisseurs pairs sont un moyen pour des fournisseurs développés indépendamment d'être utilisés ensemble de manière étroite, de sorte que les frais de superposition et la duplication des fonctionnalités du fournisseur peuvent être évités. Les fournisseurs pairs sont liés en ayant un fournisseur exportant une fonctionnalité spécifique à un autre. Cela se fait en ayant un fournisseur exportant un objet fabric partageable (fid), qui est importé par un ou plusieurs fournisseurs pairs.

Par exemple, un fournisseur qui utilise TCP pour communiquer avec des pairs distants peut souhaiter utiliser le fournisseur de mémoire partagée pour communiquer avec des pairs locaux. Pour éliminer les frais de superposition, le fournisseur basé sur TCP peut exporter sa file d'achèvement et son contexte de réception partagé et les importer dans le fournisseur de mémoire partagée.

Les mécanismes généraux utilisés pour partager des objets fabric entre des fournisseurs pairs sont similaires, indépendamment de l'objet partagé. Cependant, parce que l'objectif d'utiliser des fournisseurs pairs est d'éviter les frais de superposition, les fournisseurs doivent être explicitement écrits pour prendre en charge les mécanismes de fournisseur pair.

Lors de l'importation de tout objet fabric partagé dans un pair, le propriétaire créera un fid_peer_* séparé pour chaque fournisseur pair dans lequel il prévoit d'importer. Le propriétaire passera ce fid_peer_* unique à chaque pair via le paramètre context de l'appel d'initialisation de la ressource (c.-à-d. fi_cq_open, fi_srx_context, fi_cntr_open, etc). Le contexte fi_peer_indiquera le fid_peer alloué par le propriétaire pour que le pair l'utilise, mais est temporaire pour l'appel d'initialisation et ne peut pas être accédé par le pair après l'initialisation. Le pair ne définira que les peer_ops du fid alloué par le propriétaire et enregistrera une référence au fid_peer_* importé pour l'utiliser dans le flux de l'API pair. Le pair allouera son propre fid pour un usage interne et renverra ce fid au propriétaire via le paramètre fid régulier de l'appel d'initialisation (comme s'il s'agissait simplement d'une autre ressource ouverte). Le propriétaire est responsable de l'enregistrement du fid pair renvoyé par l'appel d'ouverture afin de le fermer plus tard (ou de faire progresser dans le cas du cq_fid).

Il existe deux modèles de fournisseurs pairs. Dans l'exemple ci-dessus, les deux pairs sont des fournisseurs complets à part entière et utilisables de manière autonome. Dans un deuxième modèle, l'un des pairs est connu sous le nom de fournisseur de déchargement. Un fournisseur de déchargement implémente un sous-ensemble de l'API libfabric et cible l'utilisation de matériel d'accélération spécifique. Par exemple, les commutateurs réseau peuvent prendre en charge des opérations collectives, telles que la barrière ou la diffusion. Un fournisseur de déchargement peut être écrit spécifiquement pour tirer parti de cette capacité ; cependant, un tel fournisseur n'est pas utilisable à des fins générales. Par conséquent, un fournisseur de déchargement est associé à un fournisseur pair principal.

AV PAIR

L'AV pair permet le partage des métadonnées d'adressage entre fournisseurs. Il cible spécifiquement le cas d'utilisation où un fournisseur principal est associé à un fournisseur de déchargement, où le fournisseur de déchargement tire parti de la communication qui a déjà été établie via le fournisseur principal. Dans d'autres situations, comme celle mentionnée ci-dessus associant un fournisseur tcp avec un fournisseur de mémoire partagée, chaque pair aura probablement son propre AV qui n'est pas partagé.

La configuration d'un AV pair est similaire à celle d'une CQ partagée, décrite ci-dessous. Le propriétaire de l'AV crée un objet fid_peer_av qui fait le lien vers son fid_av réel. Le fid_peer_av est ensuite importé par le fournisseur de déchargement.

Les AV pairs sont configurés par le propriétaire en appelant l'appel fi_av_open() du pair, en passant le drapeau FI_PEER et en pointant le paramètre context vers struct fi_peer_av_context.

Les structures de données pour prendre en charge les AV pairs sont :

struct fid_peer_av;
struct fi_ops_av_owner {
    size_t  size;
    int (*query)(struct fid_peer_av *av, struct fi_av_attr *attr);
    fi_addr_t (*ep_addr)(struct fid_peer_av *av, struct fid_ep *ep);
};
struct fid_peer_av {
    struct fid fid;
    struct fi_ops_av_owner *owner_ops;
};
struct fi_peer_av_context {
    size_t size;
    struct fid_peer_av *av;
};

fi_ops_av_owner::query()

Cet appel renvoie les attributs actuels de l'AV pair. Le propriétaire définit les champs de la structure d'entrée fi_av_attr en fonction de l'état actuel de l'AV pour les renvoyer à l'appelant.

fi_ops_av_owner::ep_addr()

Cette fonction de recherche renvoie le fi_addr de l'adresse associée à l'extrémité locale donnée. Si l'adresse de l'extrémité locale n'a pas été insérée dans l'AV, la fonction doit renvoyer FI_ADDR_NOTAVAIL.

ENSEMBLE D'AV PAIR

L'ensemble d'AV pair permet le partage des données d'adressage collectif entre fournisseurs. Il cible spécifiquement le cas d'utilisation associant un fournisseur principal à un fournisseur de déchargement collectif. La configuration d'un ensemble d'AV pair est similaire à celle d'une CQ partagée, décrite ci-dessous. Le propriétaire de l'ensemble d'AV crée un objet fid_peer_av_set qui fait le lien vers son fid_av_set. Le fid_peer_av_set est importé par le fournisseur de déchargement.

Les ensembles d'AV pairs sont configurés par le propriétaire en appelant l'appel fi_av_set_open() du pair, en passant le drapeau FI_PEER_AV et en pointant le paramètre context vers struct fi_peer_av_set_context.

Les structures de données pour prendre en charge les ensembles d'AV pairs sont :

struct fi_ops_av_set_owner {
    size_t  size;
    int (*members)(struct fid_peer_av_set *av, fi_addr_t *addr,
               size_t *count);
};
struct fid_peer_av_set {
    struct fid fid;
    struct fi_ops_av_set_owner *owner_ops;
};
struct fi_peer_av_set_context {
    size_t size;
    struct fi_peer_av_set *av_set;
};

fi_ops_peer_av_owner::members

Cet appel renvoie un tableau d'adresses AV qui sont membres de l'ensemble d'AV. La taille du tableau est spécifiée via le paramètre count. À la sortie, count est défini au nombre d'adresses dans l'ensemble d'AV. Si la valeur de count en entrée est too petit, la fonction renvoie -FI_ETOOSMALL. Sinon, la fonction renvoie un tableau de valeurs fi_addr.

CQ PAIR

Le CQ pair définit un mécanisme par lequel un fournisseur pair peut insérer des complétions dans le CQ appartenant à un autre fournisseur. Cela évite le surcoût pour l'utilisateur libfabric d'accéder à plusieurs CQ.

Pour configurer un CQ pair, un fournisseur crée un objet fid_peer_cq, qui renvoie vers le fid_cq réel du fournisseur. L'objet fid_peer_cq est ensuite importé par un fournisseur pair. Le fid_peer_cq définit des rappels que les fournisseurs utilisent pour communiquer entre eux. Le fournisseur qui alloue le fid_peer_cq est connu comme le propriétaire, l'autre fournisseur étant appelé le pair. Un propriétaire peut établir des relations de pair avec plusieurs fournisseurs.

Les CQ pairs sont configurés par le propriétaire en appelant l'appel fi_cq_open() du pair. Le propriétaire transmet le drapeau FI_PEER à fi_cq_open(). Lorsque FI_PEER est spécifié, le paramètre context transmis à fi_cq_open() doit référencer une struct fi_peer_cq_context. Les fournisseurs qui ne prennent pas en charge les CQ pairs doivent faire échouer l'appel fi_cq_open() avec -FI_EINVAL (indiquant un drapeau invalide). Le fid_peer_cq référencé par la struct fi_peer_cq_context doit rester valide jusqu'à ce que le CQ du pair soit fermé.

Les structures de données pour prendre en charge les CQ pairs sont définies comme suit :

struct fi_ops_cq_owner {
    size_t  size;
    ssize_t (*write)(struct fid_peer_cq *cq, void *context, uint64_t flags,
        size_t len, void *buf, uint64_t data, uint64_t tag, fi_addr_t src);
    ssize_t (*writeerr)(struct fid_peer_cq *cq,
        const struct fi_cq_err_entry *err_entry);
};
struct fid_peer_cq {
    struct fid fid;
    struct fi_ops_cq_owner *owner_ops;
};
struct fi_peer_cq_context {
    size_t size;
    struct fid_peer_cq *cq;
};

Pour struct fid_peer_cq, le propriétaire initialise les champs fid et owner_ops. struct fi_ops_cq_owner est utilisée par le pair pour communiquer avec le fournisseur propriétaire.

Si une progression manuelle est nécessaire sur le CQ pair, le propriétaire doit faire avancer la progression en utilisant la fonction fi_cq_read() avec le paramètre buf défini à NULL et count égal à 0. Le fournisseur pair doit définir les autres fonctions qui tentent de lire le CQ du pair (c'est-à-dire fi_cq_readerr, fi_cq_sread, etc.) pour renvoyer -FI_ENOSYS.

fi_ops_cq_owner::write()

Cet appel indique au propriétaire d'insérer de nouvelles complétions dans le CQ. Le champ fi_cq_attr::format, ainsi que d'autres attributs associés, détermine quels paramètres d'entrée sont valides. Les paramètres qui ne sont pas signalés dans le cadre d'une complétion sont ignorés par le propriétaire et doivent être définis à 0, NULL ou une autre valeur appropriée par l'utilisateur. Par exemple, si l'adressage source n'est pas renvoyé avec une complétion, le paramètre src doit être défini à FI_ADDR_NOTAVAIL et ignoré en entrée.

Le propriétaire est responsable du verrouillage, de la signalisation des événements et du débordement du CQ. Les données transmises via le rappel write sont relatives à l'utilisateur. Par exemple, le fi_addr_t est relatif à l'AV du pair. Le propriétaire est responsable de la conversion de l'adresse si l'adressage source est nécessaire.

(À déterminer : le débordement du CQ doit-il renvoyer à l'utilisateur pour le contrôle de flux ? Avons-nous besoin de rappels de backoff / resume dans ops_cq_user ?)

fi_ops_cq_owner::writeerr()

Le comportement de cet appel est similaire aux opérations write(). Il insère une complétion indiquant qu'un transfert de données a échoué dans le CQ.

EXEMPLE CONFIGURATION D'UN CQ PAIR

La description ci-dessus définit le mécanisme générique pour le partage de CQ entre fournisseurs. Cette section décrit une implémentation possible pour démontrer l'utilisation des API. Dans l'exemple, le fournisseur A utilise le fournisseur B comme pair pour les transferts de données ciblant des points de terminaison sur le nœud local.

1. Le fournisseur A est configuré pour utiliser le fournisseur B comme pair. Cela peut être codé dans le fournisseur A ou défini via une variable d'environnement.
2. L'application appelle :
   fi_cq_open(domain_a, attr, &cq_a, app_context)
3. Le fournisseur A alloue cq_a et le configure automatiquement pour être utilisé comme un cq pair.
4. Le fournisseur A prend ces étapes :
   allouer peer_cq et référencer cq_a
   définir peer_cq_context->cq = peer_cq
   définir attr_b.flags |= FI_PEER
   fi_cq_open(domain_b, attr_b, &cq_b, peer_cq_context)
5. Le fournisseur B alloue un cq, mais le configure de sorte que toutes les complétions soient écrites dans le peer_cq. Les opérations du cq pour lire depuis le cq sont définies sur des appels enosys.
6. Le fournisseur B insère ses propres rappels dans l'objet peer_cq. Il crée une référence entre l'objet peer_cq et son propre cq.

COMPTEUR PAIR

Le compteur pair définit un mécanisme par lequel un fournisseur pair peut incrémenter une valeur ou une erreur dans le compteur appartenant à un autre fournisseur.

La configuration d'un compteur pair est similaire à celle d'un CQ pair décrite ci-dessus. L'objet compteur du propriétaire est importé directement dans le pair.

Les structures de données pour prendre en charge les compteurs pairs sont définies comme suit :

struct fi_ops_cntr_owner {
    size_t size;
    void (*inc)(struct fid_peer_cntr *cntr);
    void (*incerr)(struct fid_peer_cntr *cntr);
};
struct fid_peer_cntr {
    struct fid fid;
    struct fi_ops_cntr_owner *owner_ops;
};
struct fi_peer_cntr_context {
    size_t size;
    struct fid_peer_cntr *cntr;
};

Comme pour le CQ pair, si une progression manuelle est nécessaire sur le compteur pair, le propriétaire doit faire avancer la progression en utilisant fi_cntr_read() et fi_cntr_read() ne doit rien faire d'autre que faire avancer le cntr pair. Le fournisseur pair doit définir les autres fonctions qui tentent d'accéder au cntr du pair (c'est-à-dire fi_cntr_readerr, fi_cntr_set, etc.) pour renvoyer -FI_ENOSYS.

fi_ops_cntr_owner::inc()

Cet appel indique au propriétaire d'incrémenter la valeur du cntr.

fi_ops_cntr_owner::incerr()

Le comportement de cet appel est similaire aux opérations inc(). Il incrémente l'erreur du cntr indiquant qu'un transfert de données a échoué dans le cntr.

DOMAINE PAIR

Le domaine pair permet à un fournisseur d'accéder aux opérations d'un objet domaine de son pair. Par exemple, un fournisseur de déchargement peut utiliser un domaine pair pour enregistrer des tampons mémoire auprès du fournisseur principal.

La configuration d'un domaine pair est similaire à celle d'un CQ pair décrite ci-dessus. L'objet domaine du propriétaire est importé directement dans le pair.

Les domaines pairs sont configurés par le propriétaire en appelant l'appel fi_domain2() du pair. Le propriétaire transmet le drapeau FI_PEER à fi_domain2(). Lorsque FI_PEER est spécifié, le paramètre context transmis à fi_domain2() doit référencer une struct fi_peer_domain_context. Les fournisseurs qui ne prennent pas en charge les domaines pairs doivent faire échouer l'appel fi_domain2() avec -FI_EINVAL. Le fid_domain référencé par la struct fi_peer_domain_context doit rester valide jusqu'à ce que le domaine du pair soit fermé.

Les structures de données pour prendre en charge les domaines pairs sont définies comme suit :

struct fi_peer_domain_context {
    size_t size;
    struct fid_domain *domain;
};

EQ PAIR

L'EQ pair définit un mécanisme par lequel un fournisseur pair peut insérer des événements dans l'EQ appartenant à un autre fournisseur. Cela évite le surcoût pour l'utilisateur libfabric d'accéder à plusieurs EQ.

La configuration d'un EQ pair est similaire à celle d'un CQ pair décrite ci-dessus. L'objet EQ du propriétaire est importé directement dans le fournisseur pair.

Les EQ pairs sont configurés par le propriétaire en appelant l'appel fi_eq_open() du pair. Le propriétaire transmet le drapeau FI_PEER à fi_eq_open(). Lorsque FI_PEER est spécifié, le paramètre context transmis à fi_eq_open() doit référencer une struct fi_peer_eq_context. Les fournisseurs qui ne prennent pas en charge les EQ pairs doivent faire échouer l'appel fi_eq_open() avec -FI_EINVAL (indiquant un drapeau invalide). Le fid_eq référencé par la struct fi_peer_eq_context doit rester valide jusqu'à ce que l'EQ du pair soit fermé.

Les structures de données pour prendre en charge les EQ pairs sont définies comme suit :

struct fi_peer_eq_context {
    size_t size;
    struct fid_eq *eq;
};

SRX PAIR

Le SRX pair définit un mécanisme par lequel les fournisseurs pairs peuvent partager un contexte de réception partagé commun. Cela évite le surcoût d'avoir des files de réception séparées, peut éliminer les copies mémoire et garantit un ordonnancement correct des messages au niveau de l'application.

La configuration d'un SRX pair est similaire à celle d'un CQ pair décrite ci-dessus. Un objet fid_peer_srx relie le propriétaire du SRX au fournisseur pair. Les SRX pairs sont configurés par le propriétaire en appelant l'appel fi_srx_context() du pair avec le drapeau FI_PEER défini. Le paramètre context transmis à fi_srx_context() doit être une struct fi_peer_srx_context.

Le fournisseur propriétaire initialise tous les éléments du fid_peer_srx et des structures référencées (fi_ops_srx_owner et fi_ops_srx_peer), à l'exception des fonctions de rappel fi_ops_srx_peer. Celles-ci doivent être initialisées par le fournisseur pair avant de retourner de l'appel fi_srx_contex() et sont utilisées par le propriétaire pour contrôler les actions du pair.

Les structures de données pour prendre en charge les SRX pairs sont définies comme suit :

struct fid_peer_srx;
struct fi_peer_rx_entry {
    struct fi_peer_srx *srx;
    fi_addr_t addr;
    size_t msg_size;
    uint64_t tag;
    uint64_t cq_data;
    uint64_t flags;
    void *context;
    size_t count;
    void **desc;
    void *peer_context;
    void *owner_context;
    struct iovec *iov;
};
struct fi_peer_match_attr {
    fi_addr_t addr;
    size_t msg_size;
    uint64_t tag;
};
struct fi_ops_srx_owner {
    size_t size;
    int (*get_msg)(struct fid_peer_srx *srx,
                   struct fi_peer_match_attr *attr,
                   struct fi_peer_rx_entry **entry);
    int (*get_tag)(struct fid_peer_srx *srx,
                   struct fi_peer_match_attr *attr,
                   uint64_t tag, struct fi_peer_rx_entry **entry);
    int (*queue_msg)(struct fi_peer_rx_entry *entry);
    int (*queue_tag)(struct fi_peer_rx_entry *entry);
    void (*foreach_unspec_addr)(struct fid_peer_srx *srx,
                  fi_addr_t (*get_addr)(struct fi_peer_rx_entry *));
    void (*free_entry)(struct fi_peer_rx_entry *entry);
};
struct fi_ops_srx_peer {
    size_t size;
    int (*start_msg)(struct fi_peer_rx_entry *entry);
    int (*start_tag)(struct fi_peer_rx_entry *entry);
    int (*discard_msg)(struct fi_peer_rx_entry *entry);
    int (*discard_tag)(struct fi_peer_rx_entry *entry);
};
struct fid_peer_srx {
    struct fid_ep ep_fid;
    struct fi_ops_srx_owner *owner_ops;
    struct fi_ops_srx_peer *peer_ops;
};
struct fi_peer_srx_context {
    size_t size;
    struct fid_peer_srx *srx;
};

La propriété des valeurs des champs de structure et des fonctions de rappel est similaire à celle définie pour les CQ pairs, par rapport aux opérations propriétaire et pair.

Le propriétaire est responsable de l'acquisition de tous les verrous nécessaires avant toute opération qui pourrait entraîner des rappels de pair. Les fonctions suivantes sont des fonctions de niveau de progression : get_msg(), get_tag(), queue_msg(), queue_tag(), free_entry(), start_msg(), start_tag(), discard_msg(), discard_tag(). Si nécessaire, il est de la responsabilité du propriétaire d'acquérir le verrou approprié avant d'appeler la fonction fi_cq_read() d'un pair, ou une fonction similaire, qui fait avancer la progression.

Les fonctions suivantes sont des fonctions de niveau domaine : foreach_unspec_addr(). Cette fonction est utilisée en dehors du flux de progression des messages (c'est-à-dire pendant fi_av_insert()). Le propriétaire de l'srx est responsable de l'acquisition du même verrou, si nécessaire.

fi_peer_rx_entry

fi_peer_rx_entry définit une entrée de réception commune pour une utilisation entre le propriétaire et le pair. L'entrée est allouée et définie par le propriétaire et passée entre le propriétaire et le pair pour communiquer les détails de l'entrée de réception publiée par l'application. Tous les champs sont initialisés par le propriétaire, sauf dans le cas des messages inattendus où le pair peut initialiser toutes les données supplémentaires disponibles avant de mettre le message en file d'attente avec le propriétaire. Les champs peer_context et owner_context sont uniquement modifiables par le pair et le propriétaire, respectivement, pour stocker des informations supplémentaires spécifiques au fournisseur.

fi_ops_srx_owner::get_msg() / get_tag()

Ces appels sont invoqués par le fournisseur pair pour obtenir le(s) tampon(s) de réception où un message entrant doit être placé. Le fournisseur pair passera les champs pertinents pour demander une rx_entry correspondante au propriétaire. Si l'adressage source est requis, l'adresse (addr) sera passée ; sinon, l'adresse sera définie sur FI_ADDR_NOTAVAIL. Le champ msg_size indique la taille du message reçu. Ce champ peut être nécessaire au propriétaire lors du traitement de FI_MULTI_RECV ou FI_PEEK. Le propriétaire définira le champ peer_entry->msg_size sur get_msg/tag() pour que le propriétaire et le pair l'utilisent plus tard, si nécessaire. Ce champ sera défini à la fois sur les chemins attendus et inattendus. Le rx_entry->iov retourné par le propriétaire fait référence à la taille complète de la réception publiée passée au pair. Le fournisseur pair est responsable de vérifier qu'un message entrant tient dans l'espace de tampon fourni et de générer des erreurs de troncature. Le paramètre tag n'est utilisé que pour les messages étiquetés mais doit être défini à 0 pour les cas non étiquetés. Un fi_peer_rx_entry est alloué par le propriétaire, qu'une correspondance ait été trouvée ou non. Si une correspondance a été trouvée, le propriétaire retournera FI_SUCCESS et la rx_entry sera remplie avec les champs de réception connus pour que le pair les traite en conséquence. Cela inclut les informations qui ont été passées aux appels ainsi que le rx_entry->flags avec soit FI_MSG | FI_RECV (pour get_msg()) ou FI_TAGGED | FI_RECV (pour get_tag()). Le fournisseur pair est responsable de la complétion avec tout autre drapeau, si nécessaire. Si aucune correspondance n'a été trouvée, le propriétaire retournera -FI_ENOENT ; la rx_entry sera toujours valide mais ne correspondra pas à une réception publiée existante. Lorsque le pair obtient FI_ENOENT, il doit allouer toutes les ressources dont il a besoin pour traiter le message plus tard (sur start_msg/tag) et définir le rx_entry->peer_context de manière appropriée, suivi d'un appel à queue_msg/tag du propriétaire. Les appels get et queue doivent être sérialisés. Lorsque le propriétaire obtient une réception correspondante pour le message inattendu mis en file d'attente, il appellera la fonction start du pair pour notifier le pair de la rx_entry mise à jour (ou la fonction discard du pair si le message doit être écarté)

fi_ops_srx_owner::queue_msg() / queue_tag()

Appelé par le pair pour mettre en file d'attente un message entrant inattendu dans l'srx. Une fois mis en file d'attente par le pair, le propriétaire est responsable de le démarrer une fois qu'il est apparié à un tampon de réception, ou de l'écarter si nécessaire.

fi_ops_srx_owner::foreach_unspec_addr()

Appelé par le pair lorsque des mises à jour d'adressage se sont produites avec le pair. Cela déclenche le propriétaire à parcourir toutes les entrées dont l'adresse est encore inconnue et à appeler la fonction get_addr fournie sur chacune pour récupérer les informations d'adresse mises à jour.

fi_ops_srx_owner:: free_entry()

Appelé par le pair lorsqu'il a complètement terminé d'utiliser une entrée de pair allouée par le propriétaire.

fi_ops_srx_peer::start_msg() / start_tag()

Ces appels indiquent qu'un get_msg() ou get_tag() asynchrone est terminé et qu'un tampon est maintenant disponible pour recevoir le message. Le contrôle du fi_peer_rx_entry est rendu au fournisseur pair et a été initialisé pour la réception du message entrant.

fi_ops_srx_peer::discard_msg() / discard_tag()

Indique que le message et les données associés au fi_peer_rx_entry spécifié doivent être écartés. Cela indique souvent que l'application a annulé ou écarté l'opération de réception. Aucune complétion ne doit être générée par le fournisseur pair pour un message écarté. Le contrôle du fi_peer_rx_entry est rendu au fournisseur pair.

EXEMPLE CONFIGURATION D'UN SRX PAIR

La description ci-dessus définit le mécanisme générique pour le partage des SRX entre les fournisseurs. Cette section décrit une implémentation possible pour démontrer l'utilisation des API. Dans l'exemple, le fournisseur A utilise le fournisseur B comme pair pour les transferts de données visant des points de terminaison sur le nœud local.

1. Le fournisseur A est configuré pour utiliser le fournisseur B comme pair. Cela peut être codé
   dans le fournisseur A ou défini via une variable d'environnement.
2. L'application appelle :
   fi_srx_context(domain_a, attr, &srx_a, app_context)
3. Le fournisseur A alloue srx_a et le configure automatiquement pour être utilisé
   comme srx pair.
4. Le fournisseur A prend les étapes suivantes :
   allouer peer_srx et référencer srx_a
   définir peer_srx_context->srx = peer_srx
   définir attr_b.flags |= FI_PEER
   fi_srx_context(domain_b, attr_b, &srx_b, peer_srx_context)
5. Le fournisseur B alloue un srx, mais le configure de sorte que tous les tampons de
   réception soient obtenus à partir du peer_srx. Les opérations srx pour publier des réceptions sont
   définies sur des appels enosys.
6. Le fournisseur B insère ses propres rappels dans l'objet peer_srx. Il
   crée une référence entre l'objet peer_srx et son propre srx.

EXEMPLE FLUX DE RÉCEPTION D'UN SRX PAIR

Ce qui suit décrit des flux logiciels simplifiés, à titre d'exemple, pour le traitement des messages de réception à l'aide d'un SRX pair. Le premier flux démontre le cas où un tampon de réception attend lorsque le message arrive.

1. L'application appelle fi_recv() / fi_trecv() sur le propriétaire.
2. Le propriétaire met le tampon de réception en file d'attente.
3. Un message est reçu par le fournisseur pair.
4. Le pair appelle owner->get_msg() / get_tag().
5. Le propriétaire retire le tampon de réception mis en file d'attente et le retourne au
   pair. L'appel get entry se terminera avec FI_SUCCESS.
6. Lorsque le pair a fini de traiter le message et l'a complété sur son propre
   CQ, le pair appellera free_entry pour libérer l'entrée avec le propriétaire.

Le deuxième cas ci-dessous montre le flux lorsqu'un message arrive avant que l'application n'ait publié le tampon de réception correspondant.

1. Un message est reçu par le fournisseur pair.
2. Le pair appelle owner->get_msg() / get_tag(). Si l'adresse entrante est
   FI_ADDR_UNSPEC, le propriétaire ne peut pas faire correspondre ce message à une réception publiée avec
   FI_DIRECTED_RECV et ne peut le faire correspondre qu'aux réceptions publiées avec FI_ADDR_UNSPEC.
3. Le propriétaire ne trouve pas de tampon de réception correspondant.
4. Le propriétaire alloue une rx_entry avec tous les champs connus et retourne -FI_ENOENT.
5. Le pair alloue toutes les ressources nécessaires pour gérer le traitement asynchrone
   et définit peer_context en conséquence, en appelant la fonction queue
   du propriétaire lorsqu'il est prêt à mettre en file d'attente le message inattendu provenant du pair.
6. L'application appelle fi_recv() / fi_trecv() sur le propriétaire, en publiant le
   tampon de réception correspondant.
7. Le propriétaire fait correspondre la réception avec le message mis en file d'attente sur le pair. Notez que
   le propriétaire ne peut pas faire correspondre une réception dirigée avec un message inattendu dont
   l'adresse est inconnue.
8. Le propriétaire retire la requête mise en file d'attente, remplit le reste des champs connus
   et appelle la fonction peer->start_msg() / start_tag().
9. Lorsque le pair a fini de traiter le message et l'a complété sur son propre
   CQ, le pair appellera free_entry pour libérer l'entrée avec le propriétaire.

Chaque fois que l'adressage d'un pair est mis à jour (par exemple via fi_av_insert()), il doit appeler la fonction foreach_unspec_addr() du propriétaire pour déclencher toute mise à jour nécessaire des entrées inconnues. On attend du propriétaire qu'il parcourt toutes les entrées nécessaires et appelle la fonction get_addr() fournie sur chacune d'elles afin d'obtenir des informations d'adressage mises à jour. Une fois l'adresse connue, le propriétaire peut procéder à la réception des réceptions dirigées dans ces entrées.

fi_export_fid / fi_import_fid

Cela permet aux bibliothèques de niveau supérieur ou à l'application de redéfinir ou de définir le comportement de bas niveau de libfabric. FI_PEER_TRANSFE

R

Les fournisseurs envoient fréquemment des messages de contrôle à leurs homologues distants dans le cadre de leur protocole de communication. Par exemple, un fournisseur peut envoyer un message ACK pour garantir une livraison fiable d'un message ou pour satisfaire une sémantique de complétion demandée. Lorsque deux fournisseurs ou plus se coordonnent en tant que pairs, il peut être plus efficace si les messages de contrôle des deux fournisseurs pairs passent par le même transport. Dans certains cas, comme lorsqu'un des pairs est un fournisseur de déchargement (offload), cela peut même être requis. Les transferts entre pairs définissent le mécanisme par lequel cette communication se

produit.

Les transferts entre pairs permettent à un pair d'envoyer et de recevoir des transferts de données via son pair associé. Les fournisseurs qui nécessitent cette fonctionnalité l'indiquent en définissant le drapeau FI_PEER_TRANSFER comme bit de mode, c.-à-d. fi_info::

mode.

Pour utiliser un tel fournisseur en tant que pair, le fournisseur principal, ou propriétaire, doit configurer les transferts entre pairs en ouvrant un point de terminaison de transfert entre pairs et en acceptant les transferts avec ce drapeau défini. La configuration des transferts entre pairs implique les structures de données suivantes

: 
struct fi_ops_transfer_peer {
    size_t size;
    ssize_t (*complete)(struct fid_ep *ep, struct fi_cq_tagged_entry *buf,
            fi_addr_t *src_addr);
    ssize_t (*comperr)(struct fid_ep *ep, struct fi_cq_err_entry *buf);
};
struct fi_peer_transfer_context {
    size_t size;
    struct fi_info *info;
    struct fid_ep *ep;
    struct fi_ops_transfer_peer *peer_ops;
}
;

Les contextes de transfert entre pairs forment un lien virtuel entre les points de terminaison alloués sur chacun des fournisseurs pairs. La configuration d'un contexte de transfert entre pairs se fait via l'API fi_endpoint(). Le fournisseur principal appelle fi_endpoint() avec le bit de mode FI_PEER_TRANSFER défini dans le paramètre info, et le paramètre context doit référencer la struct fi_peer_transfer_context définie

ci-dessus.

Le champ size indique la taille de la struct fi_peer_transfer_context passée au pair. Cela est utilisé pour la compatibilité ascendante. Le champ info est facultatif. S'il est fourni, il définit les attributs des objets du fournisseur principal. Il peut être utilisé pour signaler les capacités et les restrictions sur les transferts entre pairs, comme la nécessité ou non d'une inscription en mémoire, les tailles de message maximales, les sémantiques d'ordonnancement des données et des complétions, etc. Si le fournisseur importateur ne peut pas satisfaire ces restrictions, il doit faire échouer l'appel fi_endpoint()

.

Le champ peer_ops contient des rappels (callbacks) du fournisseur principal vers le pair et est utilisé pour signaler la complétion (succès ou échec) des transferts de données initiés par le pair. Les fonctions de rappel définies dans la struct fi_ops_transfer_peer doivent être définies par le fournisseur pair

avant de retourner de l'appel fi_endpoint(). Les actions que le fournisseur pair peut entreprendre au sein des rappels de complétion sont le moins restreintes possible et peuvent inclure l'un des types d'opérations suivants : initiation de transferts de données supplémentaires, écriture d'événements dans la C
Q ou l'EQ du propriétaire, et inscription/désinscription en mémoire. Le propriétaire doit s'assurer qu'un interblocage ne peut pas survenir avant d'invoquer le rappel du pair si ce dernier invoque l'une de ces opérations. De plus, le propriétaire doit éviter les appels récursifs dans les rappels de complétion.
