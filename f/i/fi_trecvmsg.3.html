DESCRIPTIO

N

Les messages étiquetés sont des transferts de données qui portent une clé ou une étiquette avec le tampon de message. L'étiquette est utilisée au point de terminaison de réception pour faire correspondre le message entrant avec un tampon de réception correspondant. Les étiquettes de message correspondent lorsque l'étiquette du tampon de réception est la même que celle du tampon d'envoi, les bits ignorés étant masqués. Cela peut s'énoncer comme suit

: 
send_tag & ~ignore =
= recv_tag & ~ignore
ou send_tag | ignore
== recv_tag | ignore

En général, les étiquettes de message sont vérifiées par rapport aux tampons de réception dans l'ordre dans lequel les messages ont été publiés sur le point de terminaison. Voir la discussion sur l'ordonnancement ci-dessous pour plus de

détails.

Les fonctions d'envoi – fi_tsend, fi_tsendv, fi_tsendmsg, fi_tinject et fi_tsenddata – sont utilisées pour transmettre un message étiqueté d'un point de terminaison à un autre. La principale différence entre les fonctions d'envoi réside dans le nombre et le type de paramètres qu'elles acceptent en entrée. Sinon, elles effectuent la même fonction

générale.

Les fonctions de réception – fi_trecv, fi_trecvv, fi_recvmsg – publient un tampon de données sur un point de terminaison pour recevoir des messages étiquetés entrants. Similairement aux opérations d'envoi, les opérations de réception fonctionnent de manière asynchrone. Les utilisateurs ne doivent pas toucher aux tampons de données publiés tant que l'opération de réception n'est pas terminée. Les tampons de réception publiés sont appariés aux messages d'envoi entrants en fonction des étiquettes associées aux tampons d'envoi et de

réception.

Un point de terminaison doit être activé avant qu'une application puisse y publier des opérations d'envoi ou de réception. Pour les points de terminaison connectés, les tampons de réception peuvent être publiés avant que connect ou accept ne soit appelé sur le point de terminaison. Cela garantit que les tampons sont disponibles pour recevoir les données entrantes immédiatement après l'établissement de la

connexion.

Les opérations de message terminées sont signalées à l'utilisateur via un ou plusieurs collecteurs d'événements associés au point de terminaison. Les utilisateurs fournissent un contexte qui est associé à chaque opération et qui est retourné à l'utilisateur dans le cadre de la complétion de l'événement. Voir fi_cq pour les détails des événements de

complétion.

d

NOM

fi_trecv, fi_trecvv, fi_trecvmsg - poster des tampons de réception marqués

SYNTAXIS

#include <rdma/fabric.h>

ssize_t fi_trecv(struct fi_endpoint *endp, void *buf, size_t len, void *desc,
                 uint64_t tag, uint64_t flag);
ssize_t fi_trecvv(struct fi_endpoint *endp, struct fi_iov *iov, size_t niov,
                  uint64_t tag, uint64_t flag);
ssize_t fi_trecvmsg(struct fi_endpoint *endp, struct fi_msg_tagged *msg,
                    uint64_t flags);

ARGUMENTS

endp
Le point de terminaison sur lequel poster la réception.
buf
Le tampon à poster pour la réception. Applicable uniquement pour fi_trecv.
len
La taille du tampon de réception. Applicable uniquement pour fi_trecv.
desc
Un descripteur de tampon associé, s'il y en a un. Applicable uniquement pour fi_trecv.
iov
Une liste de structures fi_iov référençant les tampons de réception. Applicable uniquement pour fi_trecvv.
niov
Le nombre d'éléments dans le tableau iov. Applicable uniquement pour fi_trecvv.
tag
La balise de réception à associer à cette opération de réception. La balise est comparée à la balise d'un message sortant pour déterminer si le message correspond.
flag
Indicateurs pour contrôler le comportement de la réception. Peut être utilisé avec fi_trecv et fi_trecvv.
msg
Pointeur vers une structure fi_msg_tagged qui décrit les tampons, les balises, les adresses et les drapeaux pour une opération de réception marquée. Applicable uniquement pour fi_trecvmsg.

DESCRIPTION

Les appels fi_trecv, fi_trecvv et fi_trecvmsg sont utilisés pour poster des tampons sur la file d'attente de réception d'un point de terminaison pour les communications marquées. Ces opérations sont asynchrones, et les réceptions sont associées à une balise qui sera comparée aux balises des messages sortants.

fi_trecv

L'appel fi_trecv poste un tampon de données sur la file d'attente de réception du point de terminaison correspondant. Les réceptions postées sont recherchées dans l'ordre où elles ont été postées afin de correspondre aux envois. Les limites de messages sont maintenues. L'ordre dans lequel les réceptions s'achèvent dépend du type de point de terminaison et du protocole.

fi_trecvv

L'appel fi_trecvv ajoute la prise en charge d'une liste de diffusion (scatter-gather) à fi_trecv. fi_trecvv poste l'ensemble des tampons de données référencés par le paramètre iov pour recevoir des données entrantes.

fi_trecvmsg

L'appel fi_trecvmsg prend en charge le post des tampons sur des points de terminaison connectés et sans connexion, avec la capacité de contrôler l'opération de réception par appel via l'utilisation de drapeaux. La fonction fi_trecvmsg prend en entrée une structure fi_msg_tagged.

DRAPEAUX

Les appels fi_trecvmsg et fi_tsendmsg permettent à l'utilisateur de spécifier des drapeaux qui peuvent modifier la gestion par défaut des messages du point de terminaison. Les drapeaux spécifiés avec fi_trecvmsg / fi_tsendmsg remplacent la plupart des drapeaux précédemment configurés avec le point de terminaison, sauf indication contraire (voir fi_endpoint). La liste suivante de drapeaux est utilisable avec fi_trecvmsg et/ou fi_tsendmsg.

FI_REMOTE_CQ_DATA
S'applique à fi_tsendmsg. Indique que les données CQ distantes sont disponibles et doivent être envoyées dans le cadre de la requête. Voir fi_getinfo pour plus de détails sur FI_REMOTE_CQ_DATA. Ce drapeau est implicitement défini pour fi_tsenddata et fi_tinjectdata.
FI_COMPLETION
Indique qu'une entrée de complétion doit être générée pour l'opération spécifiée. Le point de terminaison doit être lié à une file d'attente de complétion avec FI_SELECTIVE_COMPLETION qui correspond à l'opération spécifiée, sinon ce drapeau est ignoré.
FI_MORE
Indique que l'utilisateur a des requêtes supplémentaires qui seront immédiatement postées après le retour de l'appel actuel. L'utilisation de ce drapeau peut améliorer les performances en permettant au fournisseur d'optimiser son accès au matériel de la fabric.
FI_INJECT
S'applique à fi_tsendmsg. Indique que le tampon de données sortant doit être retourné à l'utilisateur immédiatement après le retour de l'appel d'envoi, même si l'opération est traitée de manière asynchrone. Cela peut nécessiter que l'implémentation du fournisseur sous-jacente copie les données dans un tampon local et les transfère à partir de ce tampon. Ce drapeau ne peut être utilisé qu'avec des messages plus petits que inject_size.
FI_MULTI_RECV
S'applique aux opérations de réception marquées postées lorsque la capacité FI_TAGGED_MULTI_RECV est activée. Ce drapeau permet à l'utilisateur de poster un seul tampon de réception marqué qui recevra plusieurs messages entrants. Les messages reçus seront regroupés dans le tampon de réception jusqu'à ce que le tampon soit consommé. L'utilisation de ce drapeau peut entraîner la génération de plusieurs événements pour une seule opération de réception postée à mesure que les messages sont placés dans le tampon. Le placement des données reçues dans le tampon peut être soumis à des restrictions d'alignement spécifiques au fournisseur.

Le tampon sera libéré par le fournisseur lorsque l'espace tampon disponible tombera en dessous du minimum spécifié (voir FI_OPT_MIN_MULTI_RECV). Notez qu'une entrée dans la file d'attente de réception associée sera toujours générée lorsque le tampon aura été consommé, même si d'autres complétions de réception ont été supprimées (c'est-à-dire que le contexte Rx a été configuré pour FI_SELECTIVE_COMPLETION). Voir le drapeau de complétion FI_MULTI_RECV de fi_cq(3).

FI_INJECT_COMPLETE
S'applique à fi_tsendmsg. Indique qu'une complétion doit être générée lorsque les tampons source peuvent être réutilisés.
FI_TRANSMIT_COMPLETE
S'applique à fi_tsendmsg. Indique qu'une complétion ne doit pas être générée tant que l'opération n'a pas été transmise avec succès et n'est plus suivie par le fournisseur.
FI_MATCH_COMPLETE
S'applique à fi_tsendmsg. Indique qu'une complétion doit être générée uniquement après que le message a été soit mis en correspondance avec un tampon marqué, soit rejeté par l'application cible.
FI_FENCE
S'applique aux transmissions. Indique que l'opération demandée, également appelée opération clôturée, et toute opération postée après l'opération clôturée seront différées jusqu'à ce que toutes les opérations précédentes ciblant le même point de terminaison distant soient terminées. Les opérations postées après la clôture verront et/ou remplaceront les résultats de toute opération initiée avant l'opération clôturée.

L'ordre des opérations commençant par le post de l'opération clôturée (inclusivement) jusqu'au post d'une opération clôturée ultérieure (exclusivement) est contrôlé par les sémantiques d'ordre du point de terminaison.

FI_AUTH_KEY
Valide uniquement avec des domaines configurés avec FI_AV_AUTH_KEY et des points de terminaison sans connexion configurés avec FI_DIRECTED_RECV ou FI_TAGGED_DIRECTED_RECV. Lorsqu'il est utilisé avec fi_trecvmsg, ce drapeau indique que src_addr est une clé d'autorisation fi_addr_t au lieu d'un point de terminaison fi_addr_t.

Les drapeaux suivants peuvent être utilisés avec fi_trecvmsg.

FI_PEEK
Le drapeau peek peut être utilisé pour voir si un message spécifié est arrivé. Une requête peek est souvent utile sur les points de terminaison qui ont un tampon alloué par le fournisseur activé. Contrairement aux opérations de réception standard, une opération de réception avec le drapeau FI_PEEK défini ne reste pas mise en file d'attente auprès du fournisseur après la réussite de la complétion du peek. L'opération peek fonctionne de manière asynchrone, et les résultats de l'opération peek sont disponibles dans la file d'attente de complétion associée au point de terminaison. Si aucun message ne correspond aux balises spécifiées dans la requête peek, une entrée d'erreur de file d'attente de complétion avec le champ err défini sur FI_ENOMSG sera disponible.

Si une requête peek localise un message correspondant, l'opération se terminera avec succès. Les données de complétion retournées indiqueront les métadonnées associées au message, telles que la longueur du message, les drapeaux de complétion, les données de CQ disponibles, la balise et l'adresse source. Les données disponibles sont soumises au format de l'entrée de complétion (par exemple, struct fi_cq_tagged_entry).

FI_CLAIM
Si ce drapeau est utilisé conjointement avec FI_PEEK, il indique que si la requête peek se termine avec succès – indiquant qu'un message correspondant a été trouvé – le message est réclamé par l'appelant. Les messages réclamés ne peuvent être récupérés que via une opération de réception ultérieure, appariée avec le drapeau FI_CLAIM défini. Une opération de réception avec le drapeau FI_CLAIM défini, mais sans FI_PEEK, est utilisée pour récupérer un message précédemment réclamé.

Pour utiliser le drapeau FI_CLAIM, une application doit fournir une structure fi_context comme contexte pour l'opération de réception. La même structure fi_context utilisée pour une opération FI_PEEK + FI_CLAIM doit être utilisée par la requête FI_CLAIM appariée.

FI_DISCARD
Ce drapeau peut être utilisé conjointement avec FI_PEEK ou FI_CLAIM. S'il est utilisé conjointement avec FI_PEEK, il indique que si la requête peek se termine avec succès – indiquant qu'un message correspondant a été trouvé – le message est rejeté par le fournisseur, car les données ne sont pas nécessaires à l'application. Ce drapeau peut également être utilisé conjointement avec FI_CLAIM afin de rejeter un message précédemment réclamé à l'aide d'une requête FI_PEEK + FI_CLAIM.

Si ce drapeau est défini, les paramètres de tampon(s) d'entrée et de longueur sont ignorés.

VALEUR DE RETOUR

Les appels d'envoi et de réception marqués retournent 0 en cas de succès. En cas d'erreur, une valeur négative correspondant au errno du fabric est retournée. Les valeurs errno du fabric sont définies dans fi_errno.h.
