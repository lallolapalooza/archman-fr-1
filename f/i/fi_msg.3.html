NOM

fi_msg - Opérations de transfert de données de message

fi_recv / fi_recvv / fi_recvmsg
Publier un tampon pour recevoir un message entrant

fi_send / fi_sendv / fi_sendmsg fi_inject / fi_senddata : Initier une opération pour envoyer un message

SYNOPSIS

#include <rdma/fi_endpoint.h>
ssize_t fi_recv(struct fid_ep *ep, void * buf, size_t len,
    void *desc, fi_addr_t src_addr, void *context);
ssize_t fi_recvv(struct fid_ep *ep, const struct iovec *iov, void **desc,
    size_t count, fi_addr_t src_addr, void *context);
ssize_t fi_recvmsg(struct fid_ep *ep, const struct fi_msg *msg,
    uint64_t flags);
ssize_t fi_send(struct fid_ep *ep, const void *buf, size_t len,
    void *desc, fi_addr_t dest_addr, void *context);
ssize_t fi_sendv(struct fid_ep *ep, const struct iovec *iov,
    void **desc, size_t count, fi_addr_t dest_addr, void *context);
ssize_t fi_sendmsg(struct fid_ep *ep, const struct fi_msg *msg,
    uint64_t flags);
ssize_t fi_inject(struct fid_ep *ep, const void *buf, size_t len,
    fi_addr_t dest_addr);
ssize_t fi_senddata(struct fid_ep *ep, const void *buf, size_t len,
    void *desc, uint64_t data, fi_addr_t dest_addr, void *context);
ssize_t fi_injectdata(struct fid_ep *ep, const void *buf, size_t len,
    uint64_t data, fi_addr_t dest_addr);

ARGUMENTS

ep
Point de terminaison de la fabrique sur lequel initier l'envoi ou publier le tampon de réception.
buf
Tampon de données à envoyer ou recevoir.
len
Longueur du tampon de données à envoyer ou recevoir, spécifiée en octets. Les transferts valides vont de 0 octet jusqu'à max_msg_size du point de terminaison.
iov
Tampon de données vectorisé.
count
Nombre d'entrées de données vectorisées.
desc
Descripteur associé au tampon de données. Voir fi_mr(3).
data
Données CQ distantes à transférer avec le message envoyé.
dest_addr
Adresse de destination pour les transferts sans connexion. Ignoré pour les points de terminaison connectés.
src_addr
S'applique uniquement aux points de terminaison sans connexion configurés avec FI_DIRECTED_RECV. Pour toutes les autres configurations de point de terminaison, src_addr est ignoré. src_addr définit l'adresse source à recevoir. Par défaut, src_addr est traité comme une adresse de point de terminaison source (c'est-à-dire un fi_addr_t retourné par fi_av_insert / fi_av_insertsvc / fi_av_remove). Si l'indicateur FI_AUTH_KEY est spécifié avec fi_recvmsg, src_addr est traité comme une clé d'autorisation source (c'est-à-dire un fi_addr_t retourné par fi_av_insert_auth_key). S'il est défini à FI_ADDR_UNSPEC, toute adresse source peut correspondre.
msg
Descripteur de message pour les opérations d'envoi et de réception.
flags
Indicateurs supplémentaires à appliquer pour l'opération d'envoi ou de réception.
context
Pointeur spécifié par l'utilisateur à associer à l'opération. Ce paramètre est ignoré si l'opération ne générera pas une complétion réussie, sauf si un indicateur d'opération spécifie que le paramètre context doit être utilisé pour l'entrée requise.

DESCRIPTION

Les fonctions d'envoi – fi_send, fi_sendv, fi_sendmsg, fi_inject et fi_senddata – sont utilisées pour transmettre un message d'un point de terminaison à un autre. La principale différence entre les fonctions d'envoi réside dans le nombre et le type de paramètres qu'elles acceptent en entrée. Sinon, elles effectuent la même fonction générale. Les messages envoyés à l'aide des opérations fi_msg sont reçus par un point de terminaison distant dans un tampon publié pour recevoir de tels messages.

Les fonctions de réception – fi_recv, fi_recvv, fi_recvmsg – publient un tampon de données sur un point de terminaison pour recevoir les messages entrants. Similaire aux opérations d'envoi, les opérations de réception fonctionnent de manière asynchrone. Les utilisateurs ne doivent pas toucher aux tampons de données publiés tant que l'opération de réception n'est pas terminée.

Un point de terminaison doit être activé avant qu'une application puisse y publier des opérations d'envoi ou de réception. Pour les points de terminaison connectés, les tampons de réception peuvent être publiés avant que connect ou accept soit appelé sur le point de terminaison. Cela garantit que les tampons sont disponibles pour recevoir les données entrantes immédiatement après l'établissement de la connexion.

Les opérations de message terminées sont signalées à l'utilisateur via un ou plusieurs collecteurs d'événements associés au point de terminaison. Les utilisateurs fournissent un contexte qui est associé à chaque opération, et est retourné à l'utilisateur en tant que partie de l'événement de complétion. Voir fi_cq pour les détails des événements de complétion.

fi_send

L'appel fi_send transfère les données contenues dans le tampon de données spécifié par l'utilisateur vers un point de terminaison distant, les limites de message étant préservées.

fi_sendv

L'appel fi_sendv ajoute la prise en charge d'une liste scatter-gather à fi_send. Le fi_sendv transfère l'ensemble des tampons de données référencés par le paramètre iov vers un point de terminaison distant en tant que message unique.

fi_sendmsg

L'appel fi_sendmsg prend en charge les transferts de données sur les points de terminaison connectés et sans connexion, avec la possibilité de contrôler l'opération d'envoi par appel via l'utilisation d'indicateurs. La fonction fi_sendmsg prend une struct fi_msg en entrée.

struct fi_msg {
    const struct iovec *msg_iov; /* scatter-gather array */
    void               **desc;   /* local request descriptors */
    size_t             iov_count;/* # elements in iov */
    fi_addr_t          addr;     /* optional endpoint address */
    void               *context; /* user-defined context */
    uint64_t           data;     /* optional message data */
};

fi_inject

L'appel d'injection d'envoi est une version optimisée de fi_send avec les caractéristiques suivantes. Le tampon de données est disponible pour réutilisation immédiatement au retour de l'appel, et aucune entrée CQ ne sera écrite si le transfert se termine avec succès.

Conceptuellement, cela signifie que la fonction fi_inject se comporte comme si l'indicateur de transfert FI_INJECT était défini, les complétions sélectives sont activées, et l'indicateur FI_COMPLETION n'est pas spécifié. Notez que l'entrée CQ sera supprimée même si le comportement par défaut du point de terminaison est d'écrire des entrées CQ pour toutes les complétions réussies. Voir la discussion sur les indicateurs ci-dessous pour plus de détails. La taille de message demandée qui peut être utilisée avec fi_inject est limitée par inject_size.

Si FI_HMEM est activé, l'appel fi_inject ne peut accepter un tampon dont iface est égal à FI_HMEM_SYSTEM que si le fournisseur requiert le mr_mode FI_MR_HMEM. Cette limitation s'applique à tous les appels fi_*inject* et n'affecte pas la manière dont inject_size est rapporté.

fi_senddata

L'appel d'envoi de données est similaire à fi_send, mais permet l'envoi de données CQ distantes (voir l'indicateur FI_REMOTE_CQ_DATA) dans le cadre du transfert.

fi_injectdata

L'appel d'injection de données est similaire à fi_inject, mais permet l'envoi de données CQ distantes (voir l'indicateur FI_REMOTE_CQ_DATA) dans le cadre du transfert.

fi_recv

L'appel fi_recv publie un tampon de données dans la file de réception du point de terminaison correspondant. Les réceptions publiées sont recherchées dans l'ordre dans lequel elles ont été publiées afin de correspondre aux envois. Les limites de message sont préservées. L'ordre dans lequel les réceptions se complètent dépend du type de point de terminaison et du protocole. Pour les points de terminaison sans connexion, le paramètre src_addr peut être utilisé pour indiquer qu'un tampon doit être publié pour recevoir les données entrantes d'un point de terminaison distant spécifique.

fi_recvv

L'appel fi_recvv ajoute la prise en charge d'une liste scatter-gather à fi_recv. Le fi_recvv publie l'ensemble des tampons de données référencés par le paramètre iov pour une réception de données entrantes.

fi_recvmsg

L'appel fi_recvmsg prend en charge la publication de tampons sur des points d'extrémité connectés et sans connexion, avec la possibilité de contrôler l'opération de réception par appel à l'aide d'indicateurs. La fonction fi_recvmsg prend une structure fi_msg en entrée.

INDICATEURS

Les appels fi_recvmsg et fi_sendmsg permettent à l'utilisateur de spécifier des indicateurs qui peuvent modifier le comportement par défaut de gestion des messages du point d'extrémité. Les indicateurs spécifiés avec fi_recvmsg / fi_sendmsg remplacent la plupart des indicateurs précédemment configurés avec le point d'extrémité, sauf indication contraire (voir fi_endpoint.3). La liste suivante d'indicateurs est utilisable avec fi_recvmsg et/ou fi_sendmsg.

FI_REMOTE_CQ_DATA
S'applique à fi_sendmsg. Indique que les données de CQ distantes sont disponibles et doivent être envoyées dans le cadre de la requête. Voir fi_getinfo pour plus de détails sur FI_REMOTE_CQ_DATA. Cet indicateur est implicitement défini pour fi_senddata et fi_injectdata.
FI_COMPLETION
Indique qu'une entrée d'achèvement doit être générée pour l'opération spécifiée. Le point d'extrémité doit être lié à une file d'attente d'achèvement avec FI_SELECTIVE_COMPLETION correspondant à l'opération spécifiée, sinon cet indicateur est ignoré.
FI_MORE
Indique que l'utilisateur a des requêtes supplémentaires qui seront immédiatement publiées après le retour de l'appel actuel. L'utilisation de cet indicateur peut améliorer les performances en permettant au fournisseur d'optimiser son accès au matériel de tissu.
FI_INJECT
S'applique à fi_sendmsg. Indique que le tampon de données sortantes doit être renvoyé à l'utilisateur immédiatement après le retour de l'appel d'envoi, même si l'opération est gérée de manière asynchrone. Cela peut nécessiter que l'implémentation du fournisseur sous-jacent copie les données dans un tampon local et transfère à partir de ce tampon. Cet indicateur ne peut être utilisé qu'avec des messages plus petits que inject_size.
FI_MULTI_RECV
S'applique aux opérations de réception publiées. Cet indicateur permet à l'utilisateur de publier un seul tampon qui recevra plusieurs messages entrants. Les messages reçus seront empaquetés dans le tampon de réception jusqu'à ce que le tampon soit consommé. L'utilisation de cet indicateur peut entraîner une seule opération de réception publiée générant plusieurs événements à mesure que les messages sont placés dans le tampon. Le placement des données reçues dans le tampon peut être soumis à des restrictions d'alignement spécifiques au fournisseur.

Le tampon sera libéré par le fournisseur lorsque l'espace tampon disponible tombera en dessous du minimum spécifié (voir FI_OPT_MIN_MULTI_RECV). Notez qu'une entrée dans la file d'attente d'achèvement de réception associée sera toujours générée lorsque le tampon aura été consommé, même si d'autres achèvements de réception ont été supprimés (c'est-à-dire que le contexte Rx a été configuré pour FI_SELECTIVE_COMPLETION). Voir l'indicateur d'achèvement FI_MULTI_RECV fi_cq(3).

FI_INJECT_COMPLETE
S'applique à fi_sendmsg. Indique qu'un achèvement doit être généré lorsque les tampons sources peuvent être réutilisés.
FI_TRANSMIT_COMPLETE
S'applique à fi_sendmsg et fi_recvmsg. Pour les envois, indique qu'un achèvement ne doit pas être généré tant que l'opération n'a pas été transmise avec succès et n'est plus suivie par le fournisseur. Pour les opérations de réception, indique qu'un achèvement peut être généré dès que le message a été traité par le fournisseur local, même si les données du message ne sont pas visibles par tous les éléments de traitement. Voir fi_cq(3) pour les sémantiques d'achèvement côté cible.
FI_DELIVERY_COMPLETE
S'applique à fi_sendmsg. Indique qu'un achèvement doit être généré lorsque l'opération a été traitée par la destination.
FI_FENCE
S'applique aux transmissions. Indique que l'opération demandée, également connue sous le nom d'opération clôturée, et toute opération publiée après l'opération clôturée seront différées jusqu'à ce que toutes les opérations précédentes ciblant le même point d'extrémité pair soient terminées. Les opérations publiées après la clôture verront et/ou remplaceront les résultats de toute opération initiée avant l'opération clôturée.

L'ordre des opérations commençant par la publication de l'opération clôturée (inclusive) jusqu'à la publication d'une opération clôturée ultérieure (exclusive) est contrôlé par les sémantiques d'ordre du point d'extrémité.

FI_MULTICAST
S'applique aux transmissions. Cet indicateur indique que l'adresse spécifiée comme destination du transfert de données est une adresse de multidiffusion. Cet indicateur doit être utilisé dans tous les transferts de multidiffusion, conjointement avec une fi_addr_t de multidiffusion.
FI_AUTH_KEY
Valide uniquement avec les domaines configurés avec FI_AV_AUTH_KEY et les points d'extrémité sans connexion configurés avec FI_DIRECTED_RECV. Lorsqu'il est utilisé avec fi_recvmsg, cet indicateur indique que src_addr est une clé d'autorisation fi_addr_t au lieu d'une fi_addr_t de point d'extrémité.

NOTES

Si un point d'extrémité a été configuré avec FI_MSG_PREFIX, l'application doit inclure un espace tampon de taille msg_prefix_size, tel que spécifié par les attributs du point d'extrémité. Le tampon de préfixe doit se trouver au début des données référencées par le paramètre buf, ou être référencé par le premier vecteur d'entrées/sorties. L'espace de préfixe de message ne peut pas être divisé entre plusieurs vecteurs d'entrées/sorties. La taille du tampon de préfixe doit être incluse dans la longueur totale du tampon.

VALEUR DE RETOUR

Retourne 0 en cas de succès. En cas d'erreur, une valeur négative correspondant à un errno de tissu est retournée. Les valeurs errno de tissu sont définies dans rdma/fi_errno.h.

Voir la discussion ci-dessous pour les détails de la gestion de FI_EAGAIN.

ERREURS

-FI_EAGAIN
Indique que le fournisseur sous-jacent manque actuellement des ressources nécessaires pour initier l'opération demandée. Les raisons pour lesquelles un fournisseur renvoie FI_EAGAIN sont variées. Cependant, les raisons courantes incluent un tampon interne insuffisant ou des files d'attente de traitement pleines.

Un tampon interne insuffisant est souvent associé aux opérations qui utilisent FI_INJECT. Dans de tels cas, des tampons supplémentaires peuvent devenir disponibles à mesure que les opérations publiées se terminent.

Des files d'attente de traitement pleines peuvent être un état temporaire lié au traitement local (par exemple, un grand message est en cours de transfert), ou peuvent être le résultat du contrôle de flux. Dans ce dernier cas, les files d'attente peuvent rester bloquées jusqu'à ce que des ressources supplémentaires soient disponibles côté distant du transfert.

Dans tous les cas, l'opération peut être retentée après que des ressources supplémentaires soient devenues disponibles. Lors de l'utilisation de FI_PROGRESS_MANUAL, l'application doit vérifier les achèvements de transmission et de réception après avoir reçu FI_EAGAIN comme valeur de retour, indépendamment de l'opération qui a échoué. Ceci est également fortement recommandé lors de l'utilisation de FI_PROGRESS_AUTO, car des accusés de réception ou des messages de contrôle de flux peuvent devoir être traités pour reprendre l'exécution.
