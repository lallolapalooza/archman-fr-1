NOM

File::RsyncP::Digest - Interface Perl aux algorithmes de résumé rsync

SYNOPSIS

use File::RsyncP::Digest;

$rsDigest = new File::RsyncP::Digest;
# spécifier la version du protocole rsync (par défaut <= 26 -> résumés bogués).
$rsDigest->protocol(version);

# résumés MD4 de fichier
$rsDigest->reset();
$rsDigest->add(LIST);
$rsDigest->addfile(HANDLE);
$digest = $rsDigest->digest();
$string = $rsDigest->hexdigest();
# Retourne une paire de 32 octets de résumés (protocole <= 26 et >= 27).
$digestPair = $rsDigest->digest2();
$digest = File::RsyncP::Digest->hash(SCALAR);
$string = File::RsyncP::Digest->hexhash(SCALAR);

# résumés de bloc
$digests = $rsDigest->blockDigest($data, $blockSize, $md4DigestLen,
                                  $checksumSeed);
$digests = $rsDigest->blockDigestUpdate($state, $blockSize,
                            $blockLastLen, $md4DigestLen, $checksumSeed);
$digests2 = $rsDigest->blockDigestExtract($digests16, $md4DigestLen);

DESCRIPTION

Le module File::RsyncP::Digest vous permet de calculer les résumés rsync, y compris l'algorithme de résumé de message MD4 de RSA Data Security Inc., et les sommes de contrôle Adler32 depuis des programmes Perl.

Résumés Rsync

Rsync utilise deux résumés principaux (ou sommes de contrôle), pour vérifier avec une très haute probabilité que les données sous-jacentes sont identiques, sans avoir besoin d'échanger les données sous-jacentes.

Le côté serveur (distant) de rsync génère une valeur checksumSeed (généralement unix time()) qui est échangée pendant le démarrage du protocole. Cette valeur est utilisée dans les calculs des sommes de contrôle de fichier et MD4. Cela fait que les sommes de contrôle de bloc et de fichier changent à chaque exécution de Rsync.

Résumé de fichier
C'est un résumé MD4 de la checksumSeed, suivi du contenu entier du fichier. Ce résumé a une longueur de 128 bits. Le résumé de fichier est envoyé à la fin des deltas d'un fichier pour garantir que le fichier reconstruit est correct. Ce résumé est également calculé et envoyé en option dans le cadre de la liste de fichiers si l'option --checksum est spécifiée à rsync.
Résumé de bloc
Chaque fichier est divisé en blocs d'une longueur par défaut de 700 octets. Le résumé de chaque bloc est formé en calculant la somme de contrôle Adler32 du bloc, et également le résumé MD4 du bloc suivi de la checksumSeed. Pendant la phase 1, seuls les deux premiers octets du résumé MD4 sont envoyés, ce qui signifie que le résumé total est de 6 octets ou 48 bits (4 octets pour Adler32 et les 2 premiers octets du résumé MD4). Pendant la phase 2 (qui est nécessaire pour les fichiers reçus ayant un résumé de fichier incorrect), le résumé MD4 complet est utilisé (128 bits), ce qui signifie que le résumé de bloc est de 20 octets ou 160 bits. (Avant le protocole rsync XXX, le résumé complet de 20 octets était envoyé à chaque fois et il n'y avait qu'une seule phase.)

Ce module contient des routines pour calculer les résumés de fichier et de bloc d'une manière identique à rsync.

Soit dit en passant, rsync contient deux bugs dans son implémentation de MD4 (jusqu'à et y compris la version 26 du protocole rsync) :

  • MD4Final() n'est pas appelé lorsque la taille des données (c'est-à-dire la taille du fichier ou du bloc plus 4 octets pour la checksumSeed) est un multiple de 64.
  • MD4 n'est pas correct pour des tailles de données totales supérieures à 512 Mo (2^32 bits). Le MD4 de Rsync ne maintient la taille des données qu'à l'aide d'un compteur de 32 bits, il déborde donc pour les tailles de fichier supérieures à 512 Mo.

Les effets de ces bugs sont bénins : le résumé MD4 ne devrait pas être affaibli cryptographiquement et les deux côtés sont cohérents.

Ce module implémente les deux versions du résumé MD4 : la version boguée pour les versions de protocole <= 26 et la version correcte pour les versions de protocole >= 27. Le mode par défaut est la version boguée (versions de protocole <= 26).

Vous pouvez spécifier la version du protocole rsync pour déterminer quelle version de MD4 est utilisée :

# spécifier la version du protocole rsync (par défaut <= 26 -> résumés bogués).
$rsDigest->protocol(version);

De plus, vous pouvez obtenir les deux résumés en un seul appel. Le résultat est retourné comme un seul scalaire de 32 octets : les 16 premiers octets constituent le résumé bogué et les 16 octets suivants le résumé correct :

# Retourne une paire de 32 octets de résumés (protocole <= 26 et >= 27).
$digestPair = $rsDigest->digest2();

Utilisation

Un nouvel objet de contexte de résumé rsync est créé avec l'opération new. Plusieurs contextes de résumé simultanés peuvent être maintenus, si désiré.

Calcul des résumés de bloc

Après la création d'un contexte, la fonction pour calculer les sommes de contrôle de bloc est :

$digests = $rsDigest->blockDigest($data, $blockSize, $md4DigestLen,
                                  $checksumSeed)

Le premier argument est la donnée, qui peut contenir autant de données brutes que vous le souhaitez (c'est-à-dire plusieurs blocs). La somme de contrôle Adler32 et le résumé MD4 sont calculés pour chaque bloc dans $data. Le bloc final partiel (s'il est présent) est également traité. Les 4 octets de la checksumSeed entière sont ajoutés à la fin de chaque calcul de résumé de bloc si elle est non nulle. La $blockSize est spécifiée dans le deuxième argument (par défaut 700). Le troisième argument, $md4DigestLen, spécifie combien d'octets du résumé MD4 sont inclus dans les données retournées. Rsync utilise une valeur de 2 pour la première passe (ce qui signifie que 6 octets de résumés totaux sont retournés par bloc), et tous les 16 octets pour la seconde passe (ce qui signifie que 20 octets de résumés totaux sont retournés par bloc). Le nombre d'octets retourné est le nombre d'octets dans chaque résumé (Alder32 + MD4 partiel/complet) multiplié par le nombre de blocs :

(4 + md4DigestLen) * ceil(length(data) / blockSize);

Pour permettre la mise en cache des sommes de contrôle de bloc (lorsque la checksumSeed est inconnue), puis leur mise à jour rapide avec la checksumSeed connue, les données de somme de contrôle doivent d'abord être calculées avec une longueur de résumé de -1 et une checksumSeed de 0 :

$state = $rsDigest->blockDigest($data, $blockSize, -1, 0);

Le $state retourné doit être sauvegardé pour une récupération ultérieure, avec la longueur du dernier bloc partiel (par exemple, length($data) % $blockSize). La longueur de $state dépend du nombre de blocs et de la taille des blocs. En plus des 16 octets de l'état MD4, jusqu'à 63 octets de données non traitées par bloc sont également enregistrés dans $state. Pour chaque bloc,

16 + ($blockSize % 64)

octets sont enregistrés dans $state, donc $state est le plus compact lorsque $blockSize est un multiple de 64. (Le dernier bloc, partiel, peut avoir une taille de bloc plus petite, nécessitant jusqu'à 63 octets d'état même si $blockSize est un multiple de 64.)

Une fois la checksumSeed connue, les sommes de contrôle mises à jour peuvent ensuite être calculées en utilisant :

$digests = $rsDigest->blockDigestUpdate($state, $blockSize,
                            $blockLastLen, $md4DigestLen, $checksumSeed);

Le premier argument est l'état des sommes de contrôle mises en cache provenant de blockDigest. Le troisième argument est la longueur du dernier bloc (partiel).

Alternativement, j'espère ajouter une option --checksum-seed=n à rsync qui permet de définir la checksumSeed à 0. Cela entraîne l'omission de la checksumSeed du calcul MD4 et facilite grandement la mise en cache des sommes de contrôle. Une checksumSeed nulle n'affaiblit pas le résumé de bloc. Je ne suis pas sûr que cela affaiblisse ou non le résumé de fichier (la checksumSeed est appliquée au début du résumé de fichier et à la fin du résumé de bloc). Dans ce cas, les sommes de contrôle complètes de 16 octets devraient être calculées en utilisant :

$digests16 = $rsDigest->blockDigest($data, $blockSize, 16, 0);

et pour la phase 1 les sous-chaînes MD4 de 2 octets peuvent être extraites avec :

$digests2  = $rsDigest->blockDigestExtract($digests16, 2);

$digests16 original n'a pas besoin de traitement supplémentaire pour la phase 2.

Calcul des résumés de fichier

De plus, des fonctions identiques à Digest::MD4 sont fournies pour permettre le calcul du résumé de fichier MD4 de rsync. La checksumSeed, si elle n'est pas nulle, est incluse au début des données, avant que le contenu du fichier ne soit ajouté.

Le contexte est mis à jour avec l'opération add qui ajoute les chaînes contenues dans le paramètre LIST. Notez cependant que "add('foo', 'bar')",

add('foo') suivi de add('bar') et add('foobar') devraient tous donner le même résultat.

La valeur finale de l'empreinte de message MD4 est retournée par l'opération digest sous forme de chaîne binaire de 16 octets. Cette opération fournit le résultat des opérations add effectuées depuis la dernière opération new ou reset . Notez que l'opération digest est effectivement une opération destructive, à lecture unique. Une fois qu'elle a été effectuée, le contexte doit être réinitialisé avant d'être utilisé pour calculer une autre valeur d'empreinte.

Plusieurs fonctions de commodité sont également fournies. L'opération addfile prend un descripteur de fichier ouvert et le lit jusqu'à la fin du fichier par blocs de 1024 octets, en ajoutant le contenu au contexte. Le descripteur de fichier peut être spécifié par nom ou passé comme une référence de type-glob, comme montré dans les exemples ci-dessous. L'opération hexdigest appelle digest et retourne le résultat sous forme de chaîne imprimable de chiffres hexadécimaux. C'est exactement la même opération que celle effectuée par l'opération unpack dans les exemples ci-dessous.

L'opération hash peut agir soit comme une fonction membre statique (c'est-à-dire que vous l'invoquez sur la classe MD4 comme dans le synopsis ci-dessus), soit comme une fonction virtuelle normale. Dans les deux cas, elle effectue le cycle MD4 complet (réinitialisation, ajout, empreinte) sur la valeur scalaire fournie. C'est pratique pour traiter de petites quantités de données. Lorsqu'elle est invoquée sur la classe, un contexte temporaire est créé. Lorsqu'elle est invoquée à travers un objet contexte déjà créé, ce contexte est utilisé. Cette dernière forme est légèrement plus efficace. L'opération hexhash est analogue à hexdigest.

EXEMPLES

use File::RsyncP::Digest;

my $rsDigest = new File::RsyncP::Digest;
$rsDigest->add('foo', 'bar');
$rsDigest->add('baz');
my $digest = $rsDigest->digest();

print("Rsync MD4 Digest is " . unpack("H*", $digest) . "\n");

L'exemple ci-dessus afficherait le message

Rsync MD4 Digest is 6df23dc03f9b54cc38a0fc1483df6e21

Pour calculer les sommes de contrôle de bloc rsync de phase 1 (4 + 2 = 6 octets par bloc) pour un fichier de 2000 octets contenant 700 a, 700 b et 600 c, avec une graine de somme de contrôle de 0x12345678 :

use File::RsyncP::Digest;

my $rsDigest = new File::RsyncP::Digest;
my $data = ("a" x 700) . ("b" x 700) . ("c" x 600);
my $digest = $rsDigest->rsyncChecksum($data, 700, 2, 0x12345678);

print("Rsync block checksums are " . unpack("H*", $digest) . "\n");

Cela affichera :

Rsync block checksums are 3c09a624641bf80b0ce3abd208e8645d5b49

Le même résultat peut être obtenu en deux étapes en sauvegardant l'état, puis en terminant le calcul :

my $state = $rsDigest->blockDigest($data, 700, -1, 0);
my $digest = $rsDigest->blockDigestUpdate($state, 700,
                                length($data) % 700, 2, 0x12345678);

ou en calculant des empreintes MD4 de longueur complète, et en extrayant la version de 2 octets :

my $digest16 = $rsDigest->blockDigest($data, 700, 16, 0x12345678);
my $digest   = $rsDigest->blockDigestExtract($digest16, 2);
