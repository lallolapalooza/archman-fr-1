fi_msg - Opérations de transfert de données de message

fi_recv / fi_recvv / fi_recvmsg
Poster un tampon pour recevoir un message entrant

fi_send / fi_sendv / fi_sendmsg fi_inject / fi_senddata : Initialiser une opération pour envoyer un message

len
Longueur du tampon de données à envoyer ou recevoir, spécifiée en octets. Les transferts valides vont de 0 octet à la taille maximale de message (max_msg_size) du point de terminaison.

Adresse de destination pour les transferts sans connexion. Ignoré pour les points de terminaison connectés.

Ne s'applique qu'aux points de terminaison sans connexion configurés avec FI_DIRECTED_RECV. Pour toutes les autres configurations de point de terminaison, src_addr est ignoré. src_addr définit l'adresse source à partir de laquelle recevoir. Par défaut, src_addr est traité comme une adresse de point de terminaison source (c'est-à-dire fi_addr_t retourné par fi_av_insert / fi_av_insertsvc / fi_av_remove). Si l'indicateur FI_AUTH_KEY est spécifié avec fi_recvmsg, src_addr est traité comme une clé d'autorisation source (c'est-à-dire fi_addr_t retourné par fi_av_insert_auth_key). S'il est défini sur FI_ADDR_UNSPEC, toute adresse source peut correspondre.

Pointeur spécifié par l'utilisateur pour l'associer à l'opération. Ce paramètre est ignoré si l'opération ne génère pas de complétion réussie, sauf si un indicateur d'opération spécifie que le paramètre context doit être utilisé pour une entrée requise.

DESCRIPTION

Les fonctions d'envoi – fi_send, fi_sendv, fi_sendmsg, fi_inject et fi_senddata – sont utilisées pour transmettre un message d'un point de terminaison à un autre. La principale différence entre les fonctions d'envoi réside dans le nombre et le type de paramètres qu'elles acceptent en entrée. Sinon, elles effectuent la même fonction générale. Les messages envoyés à l'aide des opérations fi_msg sont reçus par un point de terminaison distant dans un tampon posté pour recevoir de tels messages.

Les fonctions de réception – fi_recv, fi_recvv, fi_recvmsg – postent un tampon de données à un point de terminaison pour recevoir les messages entrants. Similairement aux opérations d'envoi, les opérations de réception sont asynchrones. Les utilisateurs ne doivent pas toucher les tampons de données postés jusqu'à ce que l'opération de réception soit terminée.

Un point de terminaison doit être activé avant qu'une application puisse lui poster des opérations d'envoi ou de réception. Pour les points de terminaison connectés, les tampons de réception peuvent être postés avant que connect ou accept ne soient appelés sur le point de terminaison. Cela garantit que des tampons sont disponibles pour recevoir les données entrantes immédiatement après l'établissement de la connexion.

Les opérations de message complétées sont signalées à l'utilisateur par une ou plusieurs collecteurs d'événements associés au point de terminaison. Les utilisateurs fournissent un contexte associé à chaque opération, qui est renvoyé à l'utilisateur dans le cadre de l'événement de complétion. Voir fi_cq pour les détails des événements de complétion.

fi_send

L'appel fi_send transfère les données contenues dans le tampon de données spécifié par l'utilisateur vers un point de terminaison distant, en maintenant les frontières du message.

fi_sendv

L'appel fi_sendv ajoute la prise en charge d'une liste de diffusion/collecte à fi_send. fi_sendv transfère l'ensemble des tampons de données référencés par le paramètre iov vers un point de terminaison distant en tant que message unique.

fi_sendmsg

L'appel fi_sendmsg prend en charge les transferts de données sur les points de terminaison connectés et sans connexion, avec la capacité de contrôler l'opération d'envoi par appel grâce à l'utilisation d'indicateurs. La fonction fi_sendmsg prend une structure fi_msg en entrée.

struct fi_msg {
    const struct iovec *msg_iov; /* tableau de diffusion/collecte */
    void               **desc;   /* descripteurs de requête locaux */
    size_t             iov_count;/* nombre d'éléments dans iov */
    fi_addr_t          addr;     /* adresse de point de terminaison optionnelle */
    void               *context; /* contexte défini par l'utilisateur */
    uint64_t           data;     /* données de message optionnelles */
};

fi_inject

L'appel d'injection d'envoi est une version optimisée de fi_send avec les caractéristiques suivantes. Le tampon de données est disponible pour une réutilisation immédiate au retour de l'appel, et aucune entrée CQ ne sera écrite si le transfert s'achève avec succès.

Conceptuellement, cela signifie que la fonction fi_inject se comporte comme si l'indicateur de transfert FI_INJECT était défini, que les complétions sélectives sont activées, et que l'indicateur FI_COMPLETION n'est pas spécifié. Notez que l'entrée CQ sera supprimée même si le comportement par défaut du point de terminaison est d'écrire des entrées CQ pour toutes les complétions réussies. Voir la discussion sur les indicateurs ci-dessous pour plus de détails. La taille de message demandée qui peut être utilisée avec fi_inject est limitée par inject_size.

Si FI_HMEM est activé, l'appel fi_inject ne peut accepter qu'un tampon avec l'interface égale à FI_HMEM_SYSTEM si l'interface requiert le mode mr FI_MR_HMEM. Cette limitation s'applique à tous les appels fi_*inject* et n'affecte pas la manière dont inject_size est rapporté.

fi_senddata

L'appel d'envoi de données est similaire à fi_send, mais permet l'envoi de données de CQ distantes (voir l'indicateur FI_REMOTE_CQ_DATA) dans le cadre du transfert.

fi_injectdata

L'appel d'injection de données est similaire à fi_inject, mais permet l'envoi de données de CQ distantes (voir l'indicateur FI_REMOTE_CQ_DATA) dans le cadre du transfert.

fi_recv

L'appel fi_recv poste un tampon de données dans la file de réception du point de terminaison correspondant. Les réceptions postées sont recherchées dans l'ordre où elles ont été postées afin de faire correspondre les envois. Les frontières des messages sont maintenues. L'ordre dans lequel les réceptions s'achèvent dépend du type de point de terminaison et du protocole. Pour les points de terminaison sans connexion, le paramètre src_addr peut être utilisé pour indiquer qu'un tampon doit être posté pour recevoir les données entrantes d'un point de terminaison distant spécifique.

fi_recvv

L'appel fi_recvv ajoute la prise en charge d'une liste de diffusion/collecte à fi_recv. fi

_recvv publie l'ensemble des tampons de

données référencés par le paramètre iov pour recevoir des données entrantes.

fi_recvms

g

L'appel fi_recvmsg permet de publier des tampons sur des points de

terminaison connectés et non connectés, avec la possibilité de con
trôler l'opération de réception pour chaque appel à l'aide de drapeaux. La fonction fi_recvmsg prend une struct fi_msg en entrée.

Les drapeaux spécifiés avec fi_recvmsg / fi_sendmsg remplacent la plupart des drapeaux précédemment configurés avec le point de terminaison, sauf indication contraire (voir fi_endpoint.3). NOTE

S

Si un point de terminaison a été configuré avec FI_MSG_PREFIX, l'application doit inclure un espace de tampon de taille msg_prefix_size, tel que spécifié par les attribu

ts du point de terminaison. Le tampon de préfixe doit se trouver au début des données référencées par le paramètre buf, ou être référencé par le premier vecteur d'E/S. L'
espace de préfixe de message ne peut pas être réparti entre plusieurs vecteurs d'E/S. La taille du tampon de préfixe doit être incluse dans la longueur totale du tampon.

ERREUR

S
-FI_EAGA
IN
Indique que le fournisseur sous-jacent manque actuellement des ressources nécessaires pour initier l'opér
ation demandée. Les raisons pour lesquelles un fournisseur retourne FI_EAGAIN sont variées. Cependant,
les raisons courantes incluent un tamponnage interne insuffisant ou des files de traitement pleines.

Un tamponnage interne insuffisant est souvent associé aux opérations utilisant FI_INJECT. Dans de tels cas, un tamponnage supplémentaire peut devenir disponible à mesure que les opérations publiées se

terminent.

Des files de traitement pleines peuvent être un état temporaire lié au traitement local (par exemple, un grand message est en cours de transfert), ou peuvent être le résultat d'un contrôle de flux. Dans ce dernier cas, les files peuvent rester bloquées jusqu'à ce que des ressources supplémentaires soient disponibles côté distant du

transfert.

Dans tous les cas, l'opération peut être réessayée après que des ressources supplémentaires deviennent disponibles. Lors de l'utilisation de FI_PROGRESS_MANUAL, l'application doit vér

ifier les complétions de transmission et de réception après avoir reçu FI_EAGAIN comme valeur de retour, indépendamment de l'opération qui a échoué. Cela est également fortement
recommandé lors de l'utilisation de FI_PROGRESS_AUTO, car des accusés de réception ou des messages de contrôle de flux peuvent nécessiter d'être traités afin de reprendre l'exécution.
