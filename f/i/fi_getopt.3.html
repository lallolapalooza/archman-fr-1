DESCRIPTION

Les points de terminaison sont des portails de communication de niveau transport. Il existe deux types de points de terminaison : actifs et passifs. Les points de terminaison passifs appartiennent à un domaine de fabric et sont le plus souvent utilisés pour écouter les demandes de connexion entrantes. Cependant, un point de terminaison passif peut être utilisé pour réserver une adresse de fabric qui peut être accordée à un point de terminaison actif. Les points de terminaison actifs appartiennent à des domaines d'accès et peuvent effectuer des transferts de données.

Les points de terminaison actifs peuvent être orientés connexion ou sans connexion, et peuvent fournir une fiabilité des données. Les interfaces de transfert de données – messages (fi_msg), messages étiquetés (fi_tagged), RMA (fi_rma) et atomiques (fi_atomic) – sont associées aux points de terminaison actifs. Dans les configurations de base, un point de terminaison actif possède des files d'émission et de réception. En général, les opérations qui génèrent du trafic sur le fabric sont soumises à la file d'émission. Cela inclut toutes les opérations RMA et atomiques, ainsi que les messages envoyés et les messages étiquetés envoyés. Les opérations qui soumettent des tampons pour la réception des données entrantes sont soumises à la file de réception.

Les points de terminaison actifs sont créés dans un état désactivé. Ils doivent passer dans un état activé avant d'accepter des opérations de transfert de données, y compris la soumission de tampons de réception. L'appel fi_enable est utilisé pour faire passer un point de terminaison actif dans un état activé. Les appels fi_connect et fi_accept feront également passer un point de terminaison dans l'état activé, s'il n'est pas déjà actif.

Afin de faire passer un point de terminaison dans un état activé, il doit être associé à une ou plusieurs ressources de fabric. Un point de terminaison qui générera des achèvements asynchrones, que ce soit par des opérations de transfert de données ou des événements d'établissement de connexion, doit être associé aux files d'achèvement ou aux files d'événements appropriées, respectivement, avant d'être activé. De plus, les points de terminaison qui utilisent une progression manuelle doivent être associés aux files d'achèvement ou aux files d'événements pertinentes afin de faire progresser le traitement. Pour les points de terminaison utilisés uniquement comme cible d'opérations RMA ou atomiques, cela signifie associer le point de terminaison à une file d'achèvement associée au traitement de réception. Les points de terminaison sans connexion doivent être associés à un vecteur d'adresses.

Une fois qu'un point de terminaison a été activé, il peut être associé à un vecteur d'adresses. Des tampons de réception peuvent lui être soumis et des appels peuvent être effectués vers les routines d'établissement de connexion. Les points de terminaison sans connexion peuvent également effectuer des transferts de données.

Le comportement d'un point de terminaison peut être ajusté en définissant ses données de contrôle et ses options de protocole. Cela permet au fournisseur sous-jacent de rediriger les appels de fonction vers des implémentations optimisées pour répondre au comportement souhaité de l'application.

Si un point de terminaison rencontre une erreur critique, il repassera dans un état désactivé. Les erreurs critiques sont signalées via la file d'événements associée au point de terminaison. Dans certains cas, un point de terminaison désactivé peut être réactivé. La capacité de repasser dans un état activé dépend du fournisseur et dépend du type d'erreur que le point de terminaison a rencontré. Lorsque un point de terminaison est désactivé à la suite d'une erreur critique, toutes les opérations en attente sont

abandonnées.

fi_cancel tente d'annuler une opération asynchrone en attente. L'annulation d'une opération fait que le fournisseur de tissu recherche l'opérateur et, si elle est toujours en attente, la complète comme ayant été annulée. Une entrée de file d'erreur sera disponible dans la file d'erreur associée avec le code d'erreur FI_ECANCELED. D'un autre côté, si l'opération s'est terminée avant l'appel à fi_cancel, alors l'état de complétion de cette opération sera disponible dans la file de complétion associée. Aucune entrée spécifique liée à fi_cancel elle-même ne sera

postée.

ontext, seule une sera annulée. Dans ce cas, l'opération annulée est spécifique au fournisseur. L'opération d'annulation est asynchrone, mais se terminera dans un délai limité.

fi_ep_alias

Cet appel crée un alias vers le point de terminaison spécifié. Conceptuellement, un alias de point de terminaison fournit un chemin logiciel alternatif depuis l'application vers le matériel du fournisseur sous-jacent. Un point de terminaison alias diffère de son point de terminaison parent uniquement par ses indicateurs de transfert de données par défaut. Par exemple, un point de terminaison alias peut être configuré pour utiliser un mode de complétion différent. Par défaut, un point de terminaison alias hérite des mêmes indicateurs de transfert de données que le point de terminaison parent. Une application peut utiliser fi_control pour modifier les indicateurs opérationnels du point de terminaison

alias.

Lors de l'allocation d'un alias, une application peut configurer soit les indicateurs opérationnels de transmission, soit ceux de réception. Cela évite d'avoir besoin d'un appel séparant à fi_control pour définir ces

indicateurs. Les indicateurs passés à fi_ep_alias doivent inclure FI_TRANSMIT ou FI_RECV (mais pas les deux) avec les autres indicateurs opérationnels combinés par un opérateur OR. Cela remplacera respectivement les
indicateurs de transmission ou de réception pour les opérations postées via le point de terminaison alias. Tous les alias alloués doivent être fermés pour que le point de terminaison sous-jacent puisse être libéré.

Taille d'ordre RMA maximale

La taille d'ordre maximale spécifie l'ordre de livraison des données de transport vers la mémoire cible pour les opérations RMA et atomiques. L'ordre des données est distinct, mais dépend de l'ordre des messages (défini ci-dessous). L'ordre des données n'est pas spécifié là où l'ordre des messages n'est pas défini.

L'ordre des données fait référence à l'accès à la même mémoire cible par des opérations ultérieures. Lorsque des opérations de lecture ou d'écriture RMA consécutives accèdent au même emplacement de mémoire enregistré, l'ordre des données indique si la seconde opération lit ou écrit la mémoire cible après que la première opération a été complétée. Par exemple, une lecture RMA qui suit une écriture RMA lira-t-elle les données qui ont été écrites ? De même, une écriture RMA qui suit une lecture RMA mettra-t-elle à jour le tampon cible après que la lecture a transféré les données originales ? L'ordre des données répond à ces questions, même en présence d'erreurs, comme la nécessité de renvoyer des données en raison d'un trafic réseau perdu ou corrompu.

L'ordre RMA s'applique entre deux opérations, et non au sein d'un seul transfert de données. Par conséquent, l'ordre est défini par emplacement de mémoire adressable à l'octet. C'est-à-dire que l'ordre spécifie si l'emplacement X est accédé par la seconde opération après la première opération. Rien n'est impliqué sur l'achèvement de la première opération avant que la seconde opération soit initiée. Par exemple, si la première opération met à jour les emplacements X et Y, mais que la seconde opération n'accède qu'à l'emplacement X, aucune garantie n'est définie concernant l'emplacement Y et la seconde opération.

Afin de supporter les grands transferts de données découpés en plusieurs paquets et envoyés en utilisant plusieurs chemins à travers le fabric, l'ordre des données peut être limité aux transferts d'une taille spécifique ou inférieure. Les fournisseurs spécifient quand l'ordre des données est maintenu à travers les valeurs suivantes. Notez que même si l'ordre des données n'est pas maintenu, l'ordre des messages peut l'être.

max_order_raw_size
Taille de lecture après écriture. Si défini, une opération de lecture RMA ou atomique émise après une opération d'écriture RMA ou atomique, toutes deux plus petites que la taille, sera ordonnée. Lorsque les emplacements de mémoire cible se chevauchent, l'opération de lecture RMA ou atomique verra les résultats de l'écriture RMA ou atomique précédente.
max_order_war_size
Taille d'écriture après lecture. Si défini, une opération d'écriture RMA ou atomique émise après une opération de lecture RMA ou atomique, toutes deux plus petites que la taille, sera ordonnée. L'opération de lecture RMA ou atomique verra la valeur initiale de l'emplacement de mémoire cible avant qu'une écriture RMA ou atomique ultérieure ne mette à jour la valeur.
max_order_waw_size
Taille d'écriture après écriture. Si défini, une opération d'écriture RMA ou atomique émise après une opération d'écriture RMA ou atomique, toutes deux plus petites que la taille, sera ordonnée. L'emplacement de mémoire cible reflétera les résultats de la seconde écriture RMA ou atomique.

Une valeur de taille d'ordre de 0 indique que l'ordre n'est pas garanti. Une valeur de -1 garantit l'ordre pour toute taille de données.

mem_tag_format - Format de balise mémoire

Le champ de format de balise mémoire est utilisé pour transmettre des informations sur l'utilisation des paramètres de balise et d'ignorance dans les appels d'API fi_tagged, ainsi que les critères de correspondance. Ces informations sont utilisées par le fournisseur pour optimiser la prise en charge de la correspondance de balises, y compris l'alignement avec les protocoles de transport. Les formats de balise suivants sont définis :

FI_TAG_BITS
Si spécifié en entrée de fi_getinfo, cela indique que les balises contiennent jusqu'à 64 bits de données, et le récepteur doit appliquer ignore_bits aux balises lors de la correspondance des tampons de réception avec les envois. La sortie de fi_getinfo mettra 0 ou plusieurs bits de poids fort de mem_tag_format à 0 pour indiquer ces bits de balise qui sont ignorés ou réservés par le fournisseur. Les applications doivent vérifier le nombre de bits de poids fort qui sont à 0 et les mettre à 0 sur tous les bits de balise et d'ignorance.

La valeur de FI_TAG_BITS est 0, ce qui en fait le comportement par défaut si les indications ne sont pas initialisées après avoir été allouées par fi_allocinfo(). Ce format offre la plus grande flexibilité aux applications, mais limite les options d'optimisation du fournisseur. FI_TAG_BITS s'aligne sur le comportement défini pour les versions 1.x de libfabric.

FI_TAG_MPI
FI_TAG_MPI est une utilisation contrainte de FI_TAG_BITS. Lorsqu'il est sélectionné, les applications traitent la balise comme des champs de données, plutôt que comme des bits, avec la possibilité de mettre en joker chaque champ. Le format de balise MPI cible spécifiquement les implémentations et applications basées sur MPI. Une balise au format MPI se compose de 2 champs : une balise de message et un identifiant de charge utile. La balise de message est une balise de 32 bits recherchable. La correspondance sur une balise de message nécessite de parcourir une liste de tampons publiés chez le récepteur, que nous appelons une balise recherchable. L'entier de balise dans les messages point à point MPI peut être directement mappé au champ de balise de message de libfabric.

Le second champ est un identifiant qui correspond à l'opération ou aux données transportées dans la charge utile du message. Par exemple, ce champ peut être utilisé pour identifier le type d'opération collective associée à une charge utile de message. Notez que seule la taille et le comportement des formats de balise MPI sont définis. L'utilisation décrite des champs n'est qu'une suggestion.

Les applications qui utilisent le format MPI doivent initialiser leurs balises en utilisant la fonction fi_tag_mpi(). Les bits d'ignorance doivent être spécifiés comme FI_MPI_IGNORE_TAG, FI_MPI_IGNORE_PAYLOAD, ou leur combinaison par OU binaire.

FI_TAG_CCL
Le format FI_TAG_CCL restreint davantage le format FI_TAG_MPI. Lorsqu'il est utilisé, un seul champ de balise peut être défini, qui doit correspondre exactement à la cible. Le champ ne peut pas être mis en joker. Le format de balise CCL cible les bibliothèques et applications de communication collective. Le format CCL se compose d'un seul champ : un identifiant de charge utile. L'identifiant correspond à l'opération ou aux données transportées dans la charge utile du message. Par exemple, ce champ peut être utilisé pour identifier si un message est destiné à la communication point à point ou fait partie d'une opération collective, et dans ce dernier cas, le type d'opération collective.

Le format de balise CCL ne nécessite pas la recherche de tampons de réception correspondants, mais seulement le routage du message vers la file de messages virtuelle correcte en fonction de l'identifiant de charge utile.

Les applications qui utilisent le format CCL passent l'identifiant de charge utile directement comme balise et définissent les bits d'ignorance à 0.

FI_TAG_MAX_FORMAT
Si la valeur de mem_tag_format est >= FI_TAG_MAX_FORMAT, le format de balise est traité comme un ensemble de champs de bits. Le comportement est fonctionnellement identique à FI_TAG_BITS. La description suivante est fournie pour la rétrocompatibilité et décrit comment le fournisseur peut interpréter le champ mem_tag_format si la valeur est >= FI_TAG_MAX_FORMAT.

Le format de balise mémoire peut être utilisé pour diviser le tableau de bits en champs séparés. Le mem_tag_format commence éventuellement par une série de bits définis à 0, pour signifier les bits qui sont ignorés par le fournisseur. Après le préfixe initial de bits ignorés, le tableau se composera de groupes alternés de bits définis à tous les 1 ou tous les 0. Chaque groupe de bits correspond à un champ balisé. L'implication de définir un champ balisé est que lorsqu'un masque est appliqué au tableau de bits balisé, tous les bits appartenant à un champ unique seront soit définis à 1, soit à 0, collectivement.

Par exemple, un mem_tag_format de 0x30FF indique la prise en charge de 14 bits balisés, séparés en 3 champs. Le premier champ se compose de 2 bits, le second champ de 4 bits, et le dernier champ de 8 bits. Des masques valides pour un tel champ balisé seraient une combinaison par OU bitaire de zéro ou plusieurs des valeurs suivantes : 0x3000, 0x0F00, et 0x00FF. Le fournisseur peut ne pas valider le masque fourni par l'application pour des raisons de performance.

En identifiant les champs au sein d'une balise, un fournisseur peut être en mesure d'optimiser ses routines de recherche. Une application qui demande des champs de balise doit fournir des masques de balise qui définissent soit tous les bits de masque correspondant à un champ à tous les 0, soit à tous les 1. Lors de la négociation des champs de balise, une application peut demander un nombre spécifique de champs d'une taille donnée. Un fournisseur doit retourner un format de balise qui supporte le nombre de champs demandé, chaque champ étant au moins de la taille demandée, ou échouer la demande. Un fournisseur peut augmenter la taille des champs. Lors du rapport des complétions (voir FI_CQ_FORMAT_TAGGED), il n'est pas garanti que le fournisseur effacera les bits de balise non supportés dans le champ de balise de l'entrée de complétion.

Il est recommandé que les tailles de champs soient ordonnées de la plus petite à la plus grande. Une balise générique et non structurée peut être obtenue en demandant un tableau de bits composé de 1 et 0 alternés.

tx_ctx_cnt - Nombre de contextes de transmission

Nombre de contextes de transmission à associer à l'extrémité. Si non spécifié (0), 1 contexte sera assigné si l'extrémité supporte les transferts sortants. Les contextes de transmission sont des files de transmission indépendantes qui peuvent être configurées séparément. Chaque contexte de transmission peut être lié à une CQ distincte, et aucun ordre n'est défini entre les contextes. De plus, aucune synchronisation n'est nécessaire lors de l'accès aux contextes en parallèle.

Si le nombre est défini à la valeur FI_SHARED_CONTEXT, l'extrémité sera configurée pour utiliser un contexte de transmission partagé, si supporté par le fournisseur. Les fournisseurs qui ne supportent pas les contextes de transmission partagés échoueront la demande.

Voir les sections sur les extrémités évolutives et les contextes partagés pour plus de détails.

POINTS DE TERMINAISON ÉVOLUTIFS

Un point de terminaison évolutif est un portail de communication qui prend en charge plusieurs contextes de transmission et de réception. Les points de terminaison évolutifs sont librement modélisés sur le concept réseau de mise à l'échelle côté transmission/réception, également connu sous le nom de multi-file. La prise en charge des points de terminaison évolutifs est spécifique au domaine. Les points de terminaison évolutifs peuvent améliorer les performances des applications multi-thread et parallèles en permettant aux threads d'accéder à des files de transmission et de réception indépendantes. Un point de terminaison évolutif a une seule adresse de niveau transport, ce qui peut réduire les besoins en mémoire nécessaires pour stocker les données d'adressage distant, par rapport à l'utilisation de points de terminaison standard. Les points de terminaison évolutifs ne peuvent pas être utilisés directement pour les opérations de communication et nécessitent que l'application crée explicitement des contextes de transmission et de réception comme décrit ci-dessous.

fi_tx_context

Les contextes de transmission sont des files de transmission indépendantes. L'ordonnancement et la synchronisation entre les contextes ne sont pas définis. Conceptuellement, un contexte de transmission se comporte de manière similaire à un point de terminaison en écriture seule. Un contexte de transmission peut être configuré avec moins de fonctionnalités que le point de terminaison de base et avec des attributs différents (tels que les exigences d'ordonnancement et la taille d'injection) que les autres contextes associés au même point de terminaison évolutif. Chaque contexte de transmission a sa propre file d'achèvement. Le nombre de contextes de transmission associés à un point de terminaison est spécifié lors de la création du point de terminaison.

L'appel fi_tx_context est utilisé pour récupérer un contexte spécifique, identifié par un index (voir ci-dessus pour les détails sur les attributs du contexte de transmission). Les fournisseurs peuvent allouer dynamiquement des contextes lorsque fi_tx_context est appelé, ou peuvent créer statiquement tous les contextes lorsque fi_endpoint est invoqué. Par défaut, un contexte de transmission hérite des propriétés de son point de terminaison associé. Cependant, les applications peuvent demander des attributs spécifiques au contexte via le paramètre attr. La prise en charge des attributs par contexte de transmission est spécifique au fournisseur et n'est pas garantie. Les fournisseurs renverront les attributs réellement assignés au contexte via le paramètre attr, s'il est fourni.

fi_rx_context

Les contextes de réception sont des files de réception indépendantes pour recevoir les données entrantes. L'ordonnancement et la synchronisation entre les contextes ne sont pas garantis. Conceptuellement, un contexte de réception se comporte de manière similaire à un point de terminaison en lecture seule. Un contexte de réception peut être configuré avec moins de fonctionnalités que le point de terminaison de base et avec des attributs différents (tels que les exigences d'ordonnancement et la taille d'injection) que les autres contextes associés au même point de terminaison évolutif. Chaque contexte de réception a sa propre file d'achèvement. Le nombre de contextes de réception associés à un point de terminaison est spécifié lors de la création du point de terminaison.

Les contextes de réception sont souvent associés à des flux de routage, qui spécifient quels paquets entrants ciblant un point de terminaison évolutif doivent être traités. Cependant, les contextes de réception peuvent être ciblés directement par l'initiateur, si le protocole sous-jacent le prend en charge. De tels contextes sont appelés « nommés ». La prise en charge des contextes nommés doit être indiquée en définissant la capacité caps FI_NAMED_RX_CTX lorsque le point de terminaison correspondant est créé. La prise en charge des contextes de réception nommés est coordonnée avec les vecteurs d'adresse. Voir fi_av(3) et fi_rx_addr(3).

L'appel fi_rx_context est utilisé pour récupérer un contexte spécifique, identifié par un index (voir ci-dessus pour les détails sur les attributs du contexte de réception). Les fournisseurs peuvent allouer dynamiquement des contextes lorsque fi_rx_context est appelé, ou peuvent créer statiquement tous les contextes lorsque fi_endpoint est invoqué. Par défaut, un contexte de réception hérite des propriétés de son point de terminaison associé. Cependant, les applications peuvent demander des attributs spécifiques au contexte via le paramètre attr. La prise en charge des attributs par contexte de réception est spécifique au fournisseur et n'est pas garantie. Les fournisseurs renverront les attributs réellement assignés au contexte via le paramètre attr, s'il est fourni.

CONTEXTES PARTAGÉS

Les contextes partagés sont des contextes de transmission et de réception explicitement partagés entre un ou plusieurs points de terminaison. Un contexte partageable permet à une application d'utiliser une seule ressource dédiée du fournisseur parmi plusieurs points de terminaison adressables par transport. Cela peut grandement réduire les ressources nécessaires pour gérer la communication sur plusieurs points de terminaison en multiplexant le traitement de transmission et/ou de réception, avec le coût potentiel de la sérialisation de l'accès sur plusieurs points de terminaison. La prise en charge des contextes partageables est spécifique au domaine.

Conceptuellement, les contextes de transmission partageables sont des files de transmission qui peuvent être accessibles par de nombreux points de terminaison. L'utilisation d'un contexte de transmission partagé est principalement opaque pour une application. Les applications doivent allouer et lier les contextes de transmission partagés aux points de terminaison, mais les opérations sont postées directement au point de terminaison. Les contextes de transmission partagés ne sont pas associés à des files d'achèvement ou des compteurs. Les opérations terminées sont postées aux CQ liées au point de terminaison. Un point de terminaison ne peut être associé qu'à un seul contexte de transmission partagé.

Contrairement aux contextes de transmission partagés, les applications interagissent directement avec les contextes de réception partagés. Les utilisateurs postent des tampons de réception directement à un contexte de réception partagé, les tampons étant utilisables par n'importe quel point de terminaison lié au contexte de réception partagé. Les contextes de réception partagés ne sont pas associés à des files d'achèvement ou des compteurs. Les opérations de réception terminées sont postées aux CQ liées au point de terminaison. Un point de terminaison ne peut être associé qu'à un seul contexte de réception, et tous les points de terminaison sans connexion associés à un contexte de réception partagé doivent également partager le même vecteur d'adresse.

Les points de terminaison associés à un contexte de transmission partagé peuvent utiliser des contextes de réception dédiés, et vice-versa. Ou un point de terminaison peut utiliser des contextes de transmission et de réception partagés. Et il n'y a pas d'exigence selon laquelle le même groupe de points de terminaison partageant un contexte d'un type partage également le contexte d'un type alternatif. De plus, un point de terminaison peut utiliser un contexte partagé d'un type, mais un ensemble évolutif de contextes de l'autre type.

fi_stx_context

Cet appel est utilisé pour ouvrir un contexte de transmission partageable (voir ci-dessus pour les détails sur les attributs du contexte de transmission). Les points de terminaison associés à un contexte de transmission partagé doivent utiliser un sous-ensemble des attributs du contexte de transmission. Notez que c'est l'inverse de l'exigence pour les contextes de transmission des points de terminaison évolutifs.

fi_srx_context

Cela alloue un contexte de réception partageable (voir ci-dessus pour les détails sur les attributs du contexte de réception). Les points de terminaison associés à un contexte de réception partagé doivent utiliser un sous-ensemble des attributs du contexte de réception. Notez que c'est l'inverse de l'exigence pour les contextes de réception des points de terminaison évolutifs.

POINTS DE TERMINAISON SOCKET

La fonctionnalité et la description suivantes doivent être considérées comme expérimentales. Tant que la balise expérimental n'est pas retirée, les interfaces, la sémantique et les structures de données associées aux points de terminaison socket peuvent changer entre les versions de la bibliothèque.

Cette section s'applique aux points de terminaison de type FI_EP_SOCK_STREAM et FI_EP_SOCK_DGRAM, communément appelés points de terminaison socket.

Les points de terminaison socket sont définis avec une sémantique qui leur permet d'être plus facilement adoptés par les développeurs familiers avec l'API socket UNIX, ou par des logiciels intermédiaires qui exposent l'API socket, tout en profitant encore des fonctionnalités matérielles haute performance.

La différence clé entre les points de terminaison socket et les autres points de terminaison actifs est que les points de terminaison socket utilisent des transferts de données synchrones. Les tampons passés aux opérations d'envoi et de réception reprennent le contrôle de l'application lors du retour de l'appel de fonction. Par conséquent, aucun achèvement de transfert de données n'est signalé à l'application, et les points de terminaison socket ne sont pas associés à des files d'achèvement ou des compteurs.

Les points de terminaison socket prennent en charge un sous-ensemble d'opérations de message : fi_send, fi_sendv, fi_sendmsg, fi_recv, fi_recvv, fi_recvmsg et fi_inject. Comme les transferts de données sont synchrones, la valeur de retour des opérations d'envoi et de réception indique le nombre d'octets transférés en cas de succès, ou une valeur négative en cas d'erreur, y compris -FI_EAGAIN si le point de terminaison ne peut pas envoyer ou recevoir de données à cause de files pleines ou vides, respectivement.

Les points de terminaison socket sont associés à des files d'événements et des vecteurs d'adresse, et traitent les événements de gestion de connexion de manière asynchrone, similairement aux autres points de terminaison. Contrairement aux sockets UNIX, les points de terminaison socket doivent toujours être déclarés comme actifs ou passifs.

Les points de terminaison socket se comportent comme des sockets non bloquants. Afin de prendre en charge la sémantique select et poll, les points de terminaison socket actifs sont associés à un descripteur de fichier qui est signalé chaque fois que le point de terminaison est prêt à envoyer et/ou recevoir des données. Le descripteur de fichier peut être récupéré en utilisant fi_control.
