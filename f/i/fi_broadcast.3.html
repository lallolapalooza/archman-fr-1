NOM

fi_join_collective
Opération où un sous-ensemble de pairs rejoint un nouveau groupe collectif.
fi_barrier / fi_barrier2
Opération collective qui ne se termine pas tant que tous les pairs n'ont pas entré dans l'appel de barrière.
fi_broadcast
Un seul émetteur transmet des données à tous les pairs, y compris lui-même.
fi_alltoall
Chaque pair distribue une tranche de ses données locales à tous les pairs.
fi_allreduce
Opération collective où tous les pairs diffusent une opération atomique à tous les autres pairs.
fi_allgather
Chaque pair envoie une copie complète de ses données locales à tous les pairs.
fi_reduce_scatter
Appel collectif où les données sont collectées à partir de tous les pairs et fusionnées (réduites). Les résultats de la réduction sont distribués aux pairs, chaque pair recevant une tranche des résultats.
fi_reduce
Appel collectif où les données sont collectées à partir de tous les pairs vers un pair racine et fusionnées (réduites).
fi_scatter
Un seul émetteur distribue (disperse) une tranche de ses données locales à tous les pairs.
fi_gather
Tous les pairs envoient leurs données à un pair racine.
fi_query_collective
Renvoie des informations sur les opérations collectives prises en charge par un fournisseur, et les limitations du collectif.

DESCRIPTION

En général, les opérations collectives peuvent être considérées comme des opérations atomiques coordonnées entre un ensemble de points de terminaison pairs. Les lecteurs doivent consulter la page man fi_atomic(3) pour plus de détails sur les opérations atomiques et les types de données définis par libfabric.

Une opération collective est un échange de communication de groupe. Elle implique plusieurs pairs échangeant des données avec d'autres pairs participant à l'appel collectif. Les opérations collectives nécessitent une étroite coordination par tous les membres participants. Tous les participants doivent invoquer le même appel collectif avant qu'un seul membre ne puisse terminer son opération localement. En conséquence, les appels collectifs peuvent solliciter le fabric, ainsi que les tampons de données locaux et distants.

Les interfaces collectives de libfabric ciblent les fabrics qui prennent en charge le déchargement de parties de la communication collective vers les commutateurs réseau, les cartes réseau (NIC) et d'autres périphériques. Cependant, aucune exigence d'implémentation n'est imposée au fournisseur.

La première étape pour utiliser un appel collectif consiste à identifier les points de terminaison pairs qui participeront. L'appartenance au collectif suit l'un des deux modèles, tous deux pris en charge par libfabric. Dans le premier modèle, l'application gère l'appartenance. Cela signifie généralement que l'application effectue elle-même une opération collective en utilisant une communication point à point pour identifier les membres qui participeront. De plus, l'application peut interagir avec un gestionnaire de ressources de fabric pour réserver des ressources réseau nécessaires à l'exécution des opérations collectives. Dans ce modèle, l' application informera libfabric que l'appartenance a déjà été établie.

Un modèle distinct déplace la gestion de l'appartenance sous libfabric et directement dans le fournisseur. Dans ce modèle, l'application doit identifier quelles adresses pairs seront membres. Cette information est transmise au fournisseur libfabric, qui est alors responsable de coordonner la création du groupe collectif. Dans le modèle géré par le fournisseur, le fournisseur effectuera généralement l'opération collective nécessaire pour établir le groupe de communication et interagira avec tous les agents de gestion de fabric.

Dans les deux modèles, l'appartenance au collectif est communiquée au fournisseur en créant et configurant un ensemble de vecteurs d'adresses (AV set). Un AV set représente un sous-ensemble ordonné d'adresses dans un vecteur d'adresses (AV). Des détails sur la création et la configuration d'un AV set sont disponibles dans fi_av_set(3).

Une fois qu'un AV set a été programmé avec les informations d'appartenance au collectif, un point de terminaison est joint à l'ensemble. Cela utilise l' opération fi_join_collective et fonctionne de manière asynchrone. Cela diffère de la façon dont un point de terminaison est associé de manière synchrone avec un AV en utilisant l'appel `fi_ep_bind()`. Une fois l'opération `fi_join_collective` terminée, un `fi_addr` est fourni et utilisé comme adresse cible lors de l'invocation d'une opération collective.

Pour la commodité des développeurs, un ensemble d'API collectives est défini. Les API collectives diffèrent des interfaces de messagerie et RMA en ce que le format des données est connu du fournisseur, et que la collective peut effectuer une opération sur ces données. Cela aligne étroitement les opérations collectives avec les interfaces atomiques.

Rejoindre Collective (fi_join_collective)

Cet appel attache un point de terminaison à un groupe de membres collectifs. Libfabric traite les membres collectifs comme un groupe de multidiffusion, et l'appel `fi_join_collective` attache le point de terminaison à ce groupe de multidiffusion. Par défaut, le point de terminaison rejoindra le groupe en fonction des capacités de transfert de données du point de terminaison. Par exemple, si le point de terminaison a été configuré pour envoyer et recevoir des données, alors le point de terminaison pourra initier et recevoir des transferts vers et depuis la collective. Les indicateurs d'entrée peuvent être utilisés pour restreindre l'accès au groupe collectif, sous réserve des limitations de capacité du point de terminaison.

Les opérations de jointure collective s'achèvent de manière asynchrone et peuvent impliquer des transferts de tissu, en fonction de l'implémentation du fournisseur. Un point de terminaison doit être lié à une file d'attente d'événements avant d'appeler `fi_join_collective`. Le résultat de l'opération de jointure sera rapporté à l'EQ en tant qu'événement FI_JOIN_COMPLETE. Les applications ne peuvent pas émettre de transferts collectifs avant de recevoir une notification que l'opération de jointure est terminée. Notez qu'un point de terminaison peut commencer à recevoir des messages du groupe collectif dès que la jointure est terminée, ce qui peut se produire avant que l'événement FI_JOIN_COMPLETE ne soit généré.

L'opération de jointure collective est elle-même une opération collective. Tous les pairs participants doivent appeler `fi_join_collective` avant que tout pair individuel ne signale que la jointure est terminée. Les adhésions collectives gérées par l'application font exception. Avec les adhésions gérées par l'application, l'appel `fi_join_collective` peut être terminé localement sans communication de tissu. Pour les adhésions gérées par le fournisseur, l'appel de jointure collective nécessite en entrée un `coll_addr` qui fait référence soit à une adresse associée à un ensemble AV (voir `fi_av_set_addr`) soit à un groupe collectif existant (obtenu par un appel précédent à `fi_join_collective`). L'appel `fi_join_collective` créera un nouveau sous-groupe collectif. Si les adhésions gérées par l'application sont utilisées, `coll_addr` doit être défini sur FI_ADDR_UNAVAIL.

Les applications doivent appeler `fi_close` sur le groupe collectif pour déconnecter le point de terminaison du groupe. Une fois l'opération de jointure terminée, l'appel `fi_mc_addr` peut être utilisé pour récupérer l'adresse associée au groupe de multidiffusion. Voir `fi_cm(3)` pour des détails supplémentaires sur `fi_mc_addr()`.

Barrière (fi_barrier)

L'opération `fi_barrier` fournit un mécanisme pour synchroniser les pairs. La barrière ne résulte en aucun transfert de données au niveau de l'application. Une barrière ne se termine pas localement tant que tous les pairs n'ont pas invoqué l'appel de barrière. Cela signifie pour l'application locale que le travail des pairs qui s'est terminé avant qu'ils n'appellent la barrière est terminé.

Barrière (fi_barrier2)

L'opération `fi_barrier2` est identique à `fi_barrier`, mais avec un paramètre supplémentaire pour passer des indicateurs d'opération.

Diffusion (fi_broadcast)

`fi_broadcast` transfère un tableau de données d'un seul expéditeur à tous les autres membres du groupe collectif. Le paramètre `buf` d'entrée est traité comme le tampon de transmission si le rang local est la racine, sinon c'est le tampon de réception. L'opération de diffusion agit comme une écriture ou une lecture atomique sur un tableau de données. Par conséquent, le format des données dans `buf` est spécifié par le paramètre `datatype`. Tout type de données non-void peut être diffusé.

Tout à Tous (fi_alltoall)

La collective `fi_alltoall` implique la distribution (ou dispersion) de différentes parties d'un tableau de données aux pairs. Elle s'explique mieux par un exemple. Ici, trois pairs effectuent une collective tout à tous pour échanger différentes entrées dans un tableau d'entiers.

[1]   [2]   [3]
[5]   [6]   [7]
[9]  [10]  [11]
   \   |   /
   Tout à tous
   /   |   \
[1]   [5]   [9]
[2]   [6]  [10]
[3]   [7]  [11]

Chaque pair envoie une partie de ses données aux autres pairs.

Les opérations tout à tous peuvent être effectuées sur n'importe quel type de données non-void. Cependant, tout à tous n'effectue pas d'opération sur les données elles-mêmes, donc aucune opération n'est spécifiée.

Tout Réduire (fi_allreduce)

`fi_allreduce` peut être décrit comme tous les pairs fournissant des entrées dans une opération atomique, avec le résultat copié à chaque pair. Conceptuellement, cela peut être vu comme chaque pair émettant une opération atomique de multidiffusion à tous les autres pairs, récupérant les résultats et les combinant. La combinaison des résultats est appelée la réduction. L'opération `fi_allreduce()` prend en entrée un tableau de données et l'opération atomique spécifiée à effectuer. Les résultats de la réduction sont écrits dans le tampon de résultat.

N'importe quel type de données non-void peut être spécifié. Les opérations atomiques valides sont listées ci-dessous dans l'appel `fi_query_collective`. Le diagramme suivant montre un exemple d'opération tout réduire impliquant la somme d'un tableau d'entiers entre trois pairs.

Réduire-Disperser (fi_reduce_scatter)

La collective `fi_reduce_scatter` est similaire à une opération `fi_allreduce`, suivie de tout à tous. Avec reduce scatter, tous les pairs fournissent des entrées dans une opération atomique, similaire à tout réduire. Cependant, au lieu que le résultat complet soit copié à chaque pair, chaque participant ne reçoit qu'une tranche du résultat.

Ceci est montré par l'exemple suivant:

La collective `fi_scatter` est la seconde moitié d'une opération `fi_reduce_scatter`. Les données d'un seul point de terminaison `root` sont divisées et distribuées à tous les pairs.

L'opération de dispersion est utilisée pour distribuer les résultats aux pairs. Aucune opération atomique n'est effectuée sur les données.

Interroger les attributs collectifs (fi_query_collective)

L'appel `fi_query_collective` signale quelles opérations collectives sont prises en charge par le fournisseur sous-jacent, pour les points de terminaison correctement configurés. Les opérations collectives nécessaires à une application qui ne sont pas prises en charge par le fournisseur doivent être implémentées par l'application. L'appel de requête vérifie si un fournisseur prend en charge une opération collective spécifique pour un type de données et une opération donnés, le cas échéant.

Le nom de la collective, ainsi que le type de données et l'opération associée, le cas échéant, sont fournis en entrée dans `fi_query_collective`.

Le paramètre `coll` peut faire référence à l'une de ces collectives: FI_BARRIER, FI_BROADCAST, FI_ALLTOALL, FI_ALLREDUCE, FI_ALLGATHER, FI_REDUCE_SCATTER, FI_REDUCE, FI_SCATTER, ou FI_GATHER. Des détails supplémentaires sur l'opération collective sont spécifiés via la structure `fi_collective_attr`. Pour les collectives qui agissent sur des données, l'opération et le type de données associé doivent être spécifiés via

ARGUMENTS

endpt
The fabric endpoint on which the collective operation is to be performed.
buf
Buffer containing the data to be sent or received.
len
The size of the data in bytes. For all-to-all operations, this is the size of the data per peer.
datatype
The datatype of the data being transferred. Must be one of the values defined for datatype below.
root
The rank of the root node. Only applicable for operations where the root node plays a special role (e.g., fi_broadcast, fi_gather, fi_reduce).
flags
Flags to control the behavior of the collective operation. Can be FI_SCATTER or any valid flags for fi_msg(3).
sbuf
Send buffer. For some operations (e.g., fi_gather, fi_reduce), this buffer is only used on the root node.
rbuf
Receive buffer. For some operations (e.g., fi_broadcast, fi_gather), this buffer is only used on the root node.
op
The reduction operation to perform. Must be one of the values defined for op below.

DESCRIPTION

Collective operations provide optimized communication patterns for common multi-process communication needs. They are built on top of the underlying fabric provider's atomic operations.

The following collective operations are supported:

fi_broadcast
Broadcasts a message from the root node to all other participating nodes.
fi_gather
Gathers data from all participating nodes to the root node.
fi_reduce
Performs a reduction operation on data from all participating nodes and stores the result on the root node.
fi_reduce_scatter
Performs a reduction operation on data from all participating nodes and distributes a distinct portion of the result to each node.
fi_allgather
Gathers data from all participating nodes and distributes the combined data to all nodes.
fi_alltoall
Each participating node sends its data to every other node, and receives data from every other node.

The fi_alloc_collective_attr, fi_free_collective_attr and fi_query_collective functions are used to query the capabilities and limitations of collective operations on a given endpoint. The fi_query_collective function takes a pointer to a struct fi_collective_attr which will be filled with information about the collective operations supported by the provider, along with their respective limits. The fi_alloc_collective_attr function is used to allocate memory for a struct fi_collective_attr, and fi_free_collective_attr is used to free the allocated memory.

The following structure defines the attributes that can be queried for a collective operation:

struct fi_collective_attr {
    enum fi_op op;
    enum fi_datatype datatype;
    struct fi_atomic_attr datatype_attr;
    size_t max_members;
      uint64_t mode;
};

For a description of struct fi_atomic_attr, see fi_atomic(3).

op
On input, this specifies the atomic operation involved with the collective call. This should be set to one of the following values: FI_MIN, FI_MAX, FI_SUM, FI_PROD, FI_LOR, FI_LAND, FI_BOR, FI_BAND, FI_LXOR, FI_BXOR, FI_ATOMIC_READ, FI_ATOMIC_WRITE, of FI_NOOP. For collectives that do not exchange application data (fi_barrier), this should be set to FI_NOOP.
datatype
On onput, specifies the datatype of the data being modified by the collective. This should be set to one of the following values: FI_INT8, FI_UINT8, FI_INT16, FI_UINT16, FI_INT32, FI_UINT32, FI_INT64, FI_UINT64, FI_FLOAT, FI_DOUBLE, FI_FLOAT_COMPLEX, FI_DOUBLE_COMPLEX, FI_LONG_DOUBLE, FI_LONG_DOUBLE_COMPLEX, or FI_VOID. For collectives that do not exchange application data (fi_barrier), this should be set to FI_VOID.
datatype_attr.count
The maximum number of elements that may be used with the collective.
datatype_attr.size
The size of the datatype as supported by the provider. Applications should validate the size of datatypes that differ based on the platform, such as FI_LONG_DOUBLE.
max_members
The maximum number of peers that may participate in a collective operation.
mode
This field is reserved and should be 0.

If a collective operation is supported, the query call will return FI_SUCCESS, along with attributes on the limits for using that collective operation through the provider.

Completions

Collective operations map to underlying fi_atomic operations. For a discussion of atomic completion semantics, see fi_atomic(3). The completion, ordering, and atomicity of collective operations match those defined for point to point atomic operations.

FLAGS

The following flags are defined for the specified operations.

FI_SCATTER
Applies to fi_query_collective. When set, requests attribute information on the reduce-scatter collective operation.

RETURN VALUE

Returns 0 on success. On error, a negative value corresponding to fabric errno is returned. Fabric errno values are defined in rdma/fi_errno.h.

ERRORS

-FI_EAGAIN
See fi_msg(3) for a detailed description of handling FI_EAGAIN.
-FI_EOPNOTSUPP
The requested atomic operation is not supported on this endpoint.
-FI_EMSGSIZE
The number of collective operations in a single request exceeds that supported by the underlying provider.

NOTES

Collective operations map to atomic operations. As such, they follow most of the conventions and restrictions as peer to peer atomic operations. This includes data atomicity, data alignment, and message ordering semantics. See fi_atomic(3) for additional information on the datatypes and operations defined for atomic and collective operations.

SEE ALSO

fi_getinfo(3), fi_av(3), fi_atomic(3), fi_cm(3)
