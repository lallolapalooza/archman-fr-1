DESCRIPTIO

N

FileCheck lit deux fichiers (un depuis l'entrée standard, et un spécifié sur la ligne de commande) et utilise l'un pour vérifier l'autre. Ce comportement est particulièrement utile pour la suite de tests, qui souhaite vérifier que la sortie d'un outil (par ex. llc) contient les informations attendues (par exemple, un movsd depuis esp ou ce qui est intéressant). Cela est similaire à l'utilisation de grep, mais il est optimisé pour faire correspondre plusieurs entrées différentes dans un fichier dans un ordre

spécifique.

Le fichier fichier-de-correspondance spécifie le fichier qui contient les motifs à faire correspondre. Le fichier à vérifier est lu depuis l'entrée standard sauf si l'option --input-file

est uti

TUTORIE

L

FileCheck est généralement utilisé à partir des tests de régression LLVM, étant invoqué sur la ligne RUN du test. Un exemple simple d'utilisation de FileCheck depuis une ligne RUN ressemble à ceci

: 
; RUN: llvm-as
< %s | llc -
march=x86-64
| FileCheck %s

Cette syntaxe indique de canaliser le fichier actuel ("%s") vers llvm-as, de canaliser cela vers llc, puis de canaliser la sortie de llc vers FileCheck. Cela signifie que FileCheck vérifiera son entrée standard (la sortie de llc) par rapport à l'argument de nom de fichier spécifié (le fichier .ll original spécifié par "%s"). Pour voir comment cela fonctionne, regardons le reste du fichier .ll (après la ligne RUN)

: 
define void @sub1(i32* %p, i32 %v) {
entry:
; CHECK: sub1:
; CHECK: subl
        %
0 = tail call i32 @llvm.atomic.load.sub.i32.p0i32(i32* %p, i32 %v) ret vo
id } define void @inc4(i64* %p) { entry: ; CHECK: inc4: ; CHECK: incq %0
= tail call i64 @llvm.atomic.load.add.i64.p0i64(i64* %p, i64 1) ret void }

Ici, vous pouvez voir quelques lignes "CHECK:" spécifiées dans les commentaires. Maintenant, vous pouvez voir comment le fichier est canalisé vers llvm-as, puis llc, et la sortie du code machine est ce que nous vérifions. FileCheck vérifie la sortie du code machine pour s'assurer qu'elle correspond à ce que les lignes "CHECK:"

spécifient.

La syntaxe des lignes "CHECK:" est très simple : ce sont des chaînes fixes qui doivent apparaître dans l'ordre. FileCheck ignore par défaut les différences d'espaces horizontaux (par exemple, une espace peut correspondre à une tabulation) mais sinon, le contenu de la ligne "CHECK:" doit correspondre exactement à quelque chose dans le fichier de

test.

Une chose agréable à propos de FileCheck (par rapport à grep) est qu'il permet de fusionner des cas de test en groupes logiques. Par exemple, parce que le test ci-dessus vérifie les étiquettes "sub1:" et "inc4:", il ne correspondra pas s'il n'y a pas de "subl" entre ces étiquettes. S'il existait ailleurs dans le fichier, cela ne compterait pas : "grep subl" correspond si "subl" existe n'importe où dans le

fichier.

FileCheck Blocs de substitution de

chaînes

Il est souvent utile de faire correspondre un motif puis de vérifier qu'il réapparaît plus tard dans le fichier. Pour les tests de génération de code, cela peut être utile pour autoriser n'importe quel registre, mais vérifier que ce registre est utilisé de manière cohérente plus tard. Pour ce faire, FileCheck prend en charge les blocs de substitution de chaînes qui permettent de définir des variables de chaînes et de les substituer dans des motifs. Voici un exemple simple

: 
; CHECK: test5:
; CHECK:
notw [[REGISTER:
%[a-z]+]] ; CHECK: and
w {{.*}}[[REGISTER]]

La première ligne de vérification correspond à une expression régulière %[a-z]+ et la capture dans la variable de chaîne REGISTER. La deuxième ligne vérifie que quoi que ce soit qui se trouve dans REGISTER apparaît plus tard dans le fichier après un "andw". Les blocs de substitution de chaînes de FileCheck sont toujours contenus dans des paires [[ ]], et les noms de variables de chaînes peuvent être formés avec l'expression régulière \$[a-zA-Z_][a-zA-Z0-9_]*. Si un deux-points suit le nom, alors c'est une définition de la variable ; sinon, c'est une

substitution.

Les variables FileCheck peuvent être définies plusieurs fois, et les substitutions obtiennent toujours la dernière valeur. Les variables peuvent également être substituées plus tard sur la même ligne où elles ont été définies. Par exemple

: 
; CHECK:
op [[REG:
r[0-9]+]]
, [[REG]]

Peut être utile si vous voulez que les opérandes de op soient le même registre, et que vous ne vous souciez pas exactement de quel registre il

s'agit.

Si --enable-var-scope est en vigueur, les variables dont les noms commencent par $ sont considérées comme globales. Toutes les autres variables sont locales. Toutes les variables locales sont indéfinies au début de chaque bloc CHECK-LABEL. Les variables g

lobales ne sont pas affectées par CHECK-LABEL. Cela facilite la garantie que les tests
individuels ne sont pas affectés par les variables définies dans les tests précédents.

FileCheck prend également en charge les blocs de substitution numérique qui permettent de définir des variables numériques et de vérifier des valeurs numériques qui satisfont une contrainte d'expression numérique basée sur ces variables via une substitution numérique. FileCheck Variables numériques

pseudo

Il y a parfois besoin de vérifier une sortie qui contient des numéros de ligne du fichier de correspondance, par ex. lors du test des diagnostics du compilateur. Cela introduit une certaine fragilité de la structure du fichier de correspondance, car les lignes "CHECK:" contiennent des numéros de ligne absolus dans le même fichier, qui doivent être mis à jour chaque fois que les numéros de ligne changent en raison de l'ajout ou de la suppression de

texte.

Pour prendre en charge ce cas, les expressions FileCheck comprennent la variable numérique pseudo @LINE qui s'évalue au numéro de ligne du motif CHECK où elle est

trouvée.

De cette façon, les motifs de correspondance peuvent être placés près des lignes de test pertinentes et inclure des références relatives aux numéros de ligne, par exemple

// CHECK-NEXT: {{^int a}}
// CHECK
-NEXT: {{^ \^
}} // CHECK-NEXT:
{{^ ;}} int a

Pour prendre en charge les anciens usages de @LINE comme variable de chaîne spéciale, FileCheck accepte également les utilisations suivantes de @LINE avec la syntaxe de substitution de chaîne : [[@LINE]], [[@LINE+<décalage>]] et [[@LINE-<décalage>]] sans aucun espace à l'intérieur des crochets et où décalage est

un e
ntier.
