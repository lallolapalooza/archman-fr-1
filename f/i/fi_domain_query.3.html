NOM

fi_domain - Ouvrir un domaine d'accès au tissu

SYNTAXE

#include <rdma/fabric.h>
#include <rdma/fi_domain.h>
int fi_domain(struct fid_fabric *fabric, struct fi_info *info,
    struct fid_domain **domain, void *context);
int fi_domain2(struct fid_fabric *fabric, struct fi_info *info,
    struct fid_domain **domain, uint64_t flags, void *context);
int fi_close(struct fid *domain);
int fi_domain_bind(struct fid_domain *domain, struct fid *eq,
    uint64_t flags);
int fi_open_ops(struct fid *domain, const char *name, uint64_t flags,
    void **ops, void *context);
int fi_set_ops(struct fid *domain, const char *name, uint64_t flags,
    void *ops, void *context);

ARGUMENTS

fabric
Domaine du tissu.
info
Informations sur le tissu, y compris les capacités et attributs du domaine. La structure fi_info doit avoir été obtenue en utilisant soit fi_getinfo() soit fi_dupinfo().
domain
Un domaine d'accès ouvert.
context
Contexte spécifié par l'utilisateur associé au domaine. Ce contexte est renvoyé dans le cadre de tout événement asynchrone associé au domaine.
eq
File d'attente d'événements pour les opérations asynchrones initiées sur le domaine.
name
Nom associé à une interface.
ops
Opérations d'interface du tissu.

DESCRIPTION

Un domaine d'accès fait généralement référence à une carte réseau ou un port matériel physique ou virtuel ; cependant, un domaine peut s'étendre sur plusieurs composants matériels pour la reprise sur erreur ou la répartition des données. Un domaine définit la frontière pour l'association de différentes ressources. Les ressources du tissu appartenant au même domaine peuvent partager des ressources.

fi_domain

Ouvre un domaine d'accès au tissu, également appelé domaine de ressources. Les domaines de tissu sont identifiés par un nom. Les propriétés du domaine ouvert sont spécifiées à l'aide du paramètre info.

fi_domain2

Similaire à fi_domain, mais accepte un paramètre supplémentaire flags. Principalement utilisé pour ouvrir un domaine pair. Voir fi_peer(3).

fi_open_ops

fi_open_ops est utilisé pour ouvrir des interfaces spécifiques au fournisseur. Les interfaces du fournisseur peuvent être utilisées pour accéder à des ressources et opérations de bas niveau qui sont spécifiques au domaine de ressources ouvert. Les détails des interfaces de domaine sortent du cadre de cette documentation.

fi_set_ops

fi_set_ops attribue des callbacks que le fournisseur doit appeler à la place de l'exécution de tâches sélectionnées. Cela permet aux utilisateurs de modifier ou de contrôler le comportement par défaut d'un fournisseur. Conceptuellement, cela permet à l'utilisateur de brancher des fonctions spécifiques utilisées par un fournisseur et de les remplacer par les siennes.

Les opérations modifiées sont identifiées par une chaîne de caractères bien connue, passée comme paramètre name. Le format du paramètre ops dépend de la valeur de name. Le paramètre ops référencera une structure contenant les callbacks et autres champs nécessaires au fournisseur pour appeler les fonctions de l'utilisateur.

Si un fournisseur accepte la substitution, il renverra FI_SUCCESS. Si la substitution est inconnue ou non prise en charge, le fournisseur renverra -FI_ENOSYS. Les substitutions doivent être définies avant l'allocation de ressources sur le domaine.

Les opérations fi_set_ops suivantes et les structures de callback correspondantes sont définies.

FI_SET_OPS_HMEM_OVERRIDE – Substitutions Mémoire Hétérogène

La substitution HMEM permet aux utilisateurs de substituer les opérations liées à HMEM qu'un fournisseur peut effectuer. Actuellement, la portée de la substitution HMEM est de permettre à un utilisateur de définir les fonctions de mouvement de mémoire qu'un fournisseur doit utiliser lors de l'accès à un tampon utilisateur. Les fonctions de mouvement de mémoire définies par l'utilisateur doivent prendre en compte tous les différents types d'interfaces HMEM qu'un fournisseur peut rencontrer.

Tous les objets alloués sur un domaine hériteront de cette substitution.

Voici le nom de l'opération de substitution HMEM et sa structure.

#define FI_SET_OPS_HMEM_OVERRIDE "hmem_override_ops"
struct fi_hmem_override_ops {
    size_t  size;
    ssize_t (*copy_from_hmem_iov)(void *dest, size_t size,
        enum fi_hmem_iface iface, uint64_t device, const struct iovec *hmem_iov,
        size_t hmem_iov_count, uint64_t hmem_iov_offset);
    ssize_t (*copy_to_hmem_iov)(enum fi_hmem_iface iface, uint64_t device,
    const struct iovec *hmem_iov, size_t hmem_iov_count,
        uint64_t hmem_iov_offset, const void *src, size_t size);
};

Tous les champs de la structure fi_hmem_override_ops doivent être définis (non nuls) à une valeur valide.

size
Ceci doit être défini à sizeof(struct fi_hmem_override_ops). Le champ size est utilisé à des fins de compatibilité ascendante et descendante.
copy_from_hmem_iov
Copier des données depuis le périphérique/hmem vers la mémoire hôte. Cette fonction doit renvoyer un fi_errno négatif en cas d'erreur, ou le nombre d'octets copiés en cas de succès.
copy_to_hmem_iov
Copier des données depuis la mémoire hôte vers le périphérique/hmem. Cette fonction doit renvoyer un fi_errno négatif en cas d'erreur, ou le nombre d'octets copiés en cas de succès.

fi_domain_bind

Associe une file d'attente d'événements au domaine. Une file d'attente d'événements liée à un domaine sera l'EQ par défaut associée aux événements de contrôle asynchrones qui se produisent sur le domaine ou aux points d'extrémité actifs alloués sur un domaine. Cela inclut les événements CM. Les points d'extrémité peuvent diriger leurs événements de contrôle vers des EQ alternatifs en se liant directement avec l'EQ.

Déprécié : Lier une file d'attente d'événements à un domaine avec le drapeau FI_REG_MR indique que le fournisseur doit effectuer toutes les opérations d'enregistrement de mémoire de manière asynchrone, avec la complétion signalée via la file d'attente d'événements. Si aucune file d'attente d'événements n'est liée au domaine avec le drapeau FI_REG_MR, alors les requêtes d'enregistrement de mémoire se terminent de manière synchrone.

fi_close

L'appel fi_close est utilisé pour libérer toutes les ressources associées à un domaine ou une interface. Tous les objets associés au domaine ouvert doivent être libérés avant d'appeler fi_close, sinon l'appel renverra -FI_EBUSY.

Support multi-threading

(threading)

Le modèle de threading spécifie le niveau de sérialisation requis d'une application lors de l'utilisation des interfaces de transfert de données de libfabric. Les interfaces de contrôle sont toujours considérées comme thread-safe, sauf si le modèle de progression de contrôle est FI_PROGRESS_CONTROL_UNIFIED. Une interface de contrôle thread-safe permet à plusieurs threads de faire progresser l'interface de contrôle et (selon le modèle de threading sélectionné) à un ou plusieurs threads de faire progresser les interfaces de données en même temps. Les applications qui peuvent garantir la sérialisation dans leur accès aux ressources et interfaces allouées par le fournisseur permettent à un fournisseur d'éliminer les verrous de bas

niveau.
FI_THREAD_COMPLET
ION
Le modèle de threading par complétion convient le mieux aux applications multi-threadées utilisant des points d'extrémité évolutifs qui souhaitent un fonctionnement sans verro
u. Les applications doivent sérialiser l'accès à tous les objets associés par un mécanisme de complétion commun (par exemple, les contextes d'émission et de réception li
és à la même CQ ou au même compteur). Il est recommandé que les fournisseurs qui prennent en charge les points d'extrémité évolutifs prennent en charge ce modèle de threading.

Les applications souhaitant tirer parti de FI_THREAD_COMPLETION doivent réserver les contextes d'émission, les contextes de réception, les files de complétion et les compteurs à des threads

individuels.
FI_THREAD_DOM
AIN
Le modèle de threading par domaine convient le mieux aux applications mono-threadées et aux applications multi-threadées utilisant des points d'extrémité standard qui souhaitent un fonctionnement sans verrou. Les applications doivent sérialiser l'accès à tous les objets sous le même domaine. Cela inclut les points d'extrémité, les contextes d'émission et de réception, les files de complétion et les compteurs, ainsi que les régions mémoire
enregistrées.
FI_THREAD_ENDPOINT
(obsolète)
Le modèle de threading par point d'extrémité est similaire à FI_THREAD_FID, mais avec la restriction supplémentaire que la sérialisation est requise lors de l'accès au même point d'extrémité, même si plusieurs contextes d'émission et de réception sont
utilisés.
FI_THREAD_FID
(obsolète)
Un modèle de sérialisation par descripteur de fabric (FID) exige des applications qu'elles sérialisent l'accès aux ressources de fabric individuelles associées aux opérations de transfert de données et aux complétions. Pour l'accès aux points d'extrémité, la sérialisation n'est requise que lors de l'accès au même flux de données de point d'extrémité. Plusieurs threads peuvent initier des transferts sur différents contextes d'émission ou le même point d'extrémité sans sérialisation, et aucune sérialisation n'est requise entre la soumission des requêtes de transmission de données et les opérations de réception de
données.
FI_THREAD_SA
FE
Un modèle de sérialisation thread-safe permet à une application multi-threadée d'accéder à toutes les ressources allouées via n'importe quelle interface sans restriction. Tous les fournisseurs doivent prendre en charge
FI_THREAD_SAFE.

Modèles de progression

(progress)

La progression est la capacité de l'implémentation sous-jacente à terminer le traitement d'une requête asynchrone. Dans de nombreux cas, le traitement d'une requête asynchrone nécessite l'utilisation du processeur hôte. Par exemple, un message reçu peut devoir être apparié avec le bon tampon, ou une requête ayant expiré peut devoir être retransmise. Pour des raisons de performance, il peut être indésirable pour le fournisseur d'allouer un thread à cette fin, qui entrerait en concurrence avec les threads de

l'application.

La progression de contrôle indique la méthode utilisée par le fournisseur pour faire progresser les opérations de contrôle asynchrones. Les opérations de contrôle sont des fonctions qui n'impliquent pas directement le transfert de données d'application entre points d'extrémité. Elles incluent les routines de vecteur d'adresses, d'enregistrement mémoire et de gestion de

connexion.

La progression de données indique la méthode utilisée par le fournisseur pour faire progresser les opérations de transfert de données. Cela inclut les opérations de file de messages, RMA, de messagerie avec étiquette et atomiques, ainsi que leur traitement de

complétion.

Le champ progress définit le comportement des opérations de contrôle et de données. Pour les applications nécessitant la portabilité de compilation entre les séries libfabric version 1 et version 2, le champ progress peut être référencé comme

data_progress.

La progression nécessite fréquemment qu'une action soit prise à la fois côté émission et côté réception d'une opération. C'est souvent une exigence pour les transferts fiables, en raison du traitement des reconnexions et des accusés de

réception.

Pour trouver un équilibre entre performance et facilité d'utilisation, les modèles de progression suivants sont

définis.
FI_PROGRESS_A
UTO
Ce modèle de progression indique que le fournisseur fera progresser une opération asynchrone sans intervention supplémentaire de l'applic
ation. Lorsque FI_PROGRESS_AUTO est fourni en sortie de fi_getinfo en l'absence d'indications de progression, cela indique souvent q
ue la fonctionnalité souhaitée est implémentée par le matériel du fournisseur ou est un service standard du système d'exploitation.

Il est recommandé que les fournisseurs prennent en charge FI_PROGRESS_AUTO. Cependant, si un fournisseur ne prend pas en charge nativement la progression automatique, forcer l'utilisation de FI_PROGRESS_AUTO peut entraîner l'allocation de threads sous les interfaces de

fabric.

Notez que les versions précédentes de la bibliothèque exigeaient des fournisseurs qu'ils prennent en charge FI_PROGRESS_AUTO. Cependant, dans certains cas, les threads de progression ne peuvent pas être bloqués lorsque la communication est au repos, ce qui entraîne des threads tournant en boucle dans les fonctions de progression. En conséquence, ces fournisseurs ne prenaient en charge que FI_PROGRESS_MANUAL

.
FI_PROGRESS_MAN
UAL
Ce modèle de progression indique que le fournisseur nécessite l'utilisation d'un thread d'application pour terminer une requête asynchrone. Lorsque la progression manuelle est définie, le fo
urnisseur tentera de faire avancer une opération asynchrone lorsque l'application tente d'attendre ou de lire une file d'événements, une file de complétion ou un compteur où l'opération
terminée sera signalée. La progression se produit également lorsque l'application traite un ensemble de sondage ou d'attente qui a été associé à la file d'événements ou de complétion.

Seules les opérations d'attente définies par l'interface de fabric entraîneront la progression d'une opération. Les fonctions d'attente du système d'exploitation ou externes, telles que select, poll ou les routines pthread, ne le peuvent

pas.

Les exigences de progression manuelle ne s'appliquent pas seulement aux points d'extrémité qui initient des opérations d'émission, mais aussi aux points d'extrémité qui peuvent être la cible de telles opérations. Cela reste vrai même si le point d'extrémité cible ne générera pas d'événements de complétion pour les opérations. Par exemple, un point d'extrémité qui agit purement comme cible d'opérations RMA ou atomiques utilisant la progression manuelle peut encore avoir besoin de l'aide de l'application pour traiter les opérations

reçues.

données.

Gestion des ressources

(resource_mgmt)

La gestion des ressources (RM) est le support du fournisseur et du protocole pour se protéger contre le débordement des ressources locales et distantes. Cela inclut les contextes d'émission et de réception locaux et distants, les files de complétion, ainsi que les tampons de données source et

cible.

Lorsqu'elle est activée, l'application bénéficie d'un certain niveau de protection contre le débordement des files du fournisseur et des tampons de données locaux et distants. Un tel support peut être intégré directement dans le matériel et/ou le protocole réseau, mais peut également nécessiter que des vérifications soient activées dans le logiciel du fournisseur. En désactivant la gestion des ressources, l'application assume toute la responsabilité de prévenir le débordement des files et des tampons, mais cela peut permettre à un fournisseur d'éliminer les appels de synchronisation internes, tels que les variables atomiques ou les

verrous.

Il convient de noter que même si la gestion des ressources est désactivée, l'implémentation du fournisseur et le protocole peuvent encore fournir un certain niveau de protection contre les débordements. Cependant, une telle protection n'est pas garantie. Les valeurs suivantes pour la gestion des ressources sont

définies.
FI_RM_DISABL
ED

ressources.

Fait référence à la file d'achèvement associée au contexte Tx ou Rx lorsqu'une opération locale se termine. Les fournisseurs peuvent soit tronquer le message et rapporter un achèvement réussi, soit faire échouer l'opération. Lorsqu'une erreur de gestion des ressources se produit sur un point de terminaison connecté, le point de terminaison passera à un état désactivé et la connexion sera démantelée. Un point de terminaison désactivé abandonnera toute opération en file d'attente ou en

cours.

Le comportement des erreurs de gestion des ressources sur les points de terminaison sans connexion dépend du type d'erreur. Si RM est désactivé et que l'une des erreurs suivantes se produit, le point de terminaison sera désactivé : Tx Ctx, Rx Ctx, Tx CQ ou Rx CQ. Pour les autres erreurs (EP cible, pas de tampon Rx, etc.), l'opération peut échouer, mais le point de terminaison restera activé. Un point de terminaison désactivé abandonnera ou fera échouer toute opération en file d'attente ou en cours. De plus, un point de terminaison désactivé doit être réactivé avant d'accepter de nouvelles opérations de transfert de

données.

Il existe une restriction notable sur les protections offertes par la gestion des ressources. Cela se produit lorsque la gestion des ressources est activée sur un point de terminaison qui a été lié à une ou plusieurs files d'achèvement à l'aide de l'indicateur FI_SELECTIVE_COMPLETION. Les opérations publiées sur un tel point de terminaison peuvent spécifier qu'un achèvement

réussi ne doit pas générer une entrée sur la file d'achèvement correspondante. (C'est-à-dire que l'opération laisse l'indicateur FI_COMPLETION non défini). Dans de telles situations, le fournisseur n'est pas tenu de réserver une entrée dans la file d'achèvement pour gérer le cas où l'opération échoue et génère effectivement une entrée de CQ, ce qui nécessiterait effective
ment de suivre l'opération jusqu'à son achèvement. Les applications soucieuses d'éviter les débordements de CQ en cas d'erreurs doivent s'assurer qu'il y a suffisamment d'espace dans la CQ pour signaler les opérations échouées. Cela peut généralement être atteint en dimensionnant la CQ à au moins la même taille que la ou les files du point de terminaison qui y sont liées.

REMARQUE

S

Les utilisateurs doivent appeler fi_close pour libérer toutes les ressources allouées au domaine du

fabric.

Les ressources de fabric suivantes sont associées aux domaines : points de terminaison actifs, régions de mémoire, files d'événements d'achèvement et vecteurs

d'adresses.

Les attributs du domaine reflètent les limitations et les capacités du matériel et/ou du fournisseur de logiciels sous-jacent. Ils ne reflètent pas les limitations du système, telles

que le nombre de pages physiques qu'une application peut épingler ou le nombre de descripteurs de fichiers que l'application peut ouvrir. Par conséquent, les maxima rapportés peuvent
ne pas être atteignables, même sur des systèmes peu chargés, sans qu'un administrateur configure les ressources du système de manière appropriée pour le ou les fournisseurs installés.
