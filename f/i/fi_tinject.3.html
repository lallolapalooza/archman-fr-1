DESCRIPTIO

N

Les messages étiquetés sont des transferts de données qui portent une clé ou une étiquette avec le tampon de message. L'étiquette est utilisée au point de terminaison de réception pour faire correspondre le message entrant avec un tampon de réception correspondant. Les étiquettes de message correspondent lorsque l'étiquette du tampon de réception est la même que celle du tampon d'envoi, les bits ignorés étant masqués. Cela peut s'énoncer ainsi

: 
send_tag & ~ignore =
= recv_tag & ~ignore
ou send_tag | ignore
== recv_tag | ignore

En général, les étiquettes de message sont vérifiées par rapport aux tampons de réception dans l'ordre dans lequel les messages ont été publiés sur le point de terminaison. Voir la discussion sur l'ordre ci-dessous pour plus de

détails.

Les fonctions d'envoi – fi_tsend, fi_tsendv, fi_tsendmsg, fi_tinject et fi_tsenddata – sont utilisées pour transmettre un message étiqueté d'un point de terminaison à un autre. La principale différence entre les fonctions d'envoi réside dans le nombre et le type de paramètres qu'elles acceptent en entrée. Sinon, elles effectuent la même fonction

générale.

Les fonctions de réception – fi_trecv, fi_trecvv, fi_recvmsg – publient un tampon de données sur un point de terminaison pour recevoir des messages étiquetés entrants. Similairement aux opérations d'envoi, les opérations de réception fonctionnent de manière asynchrone. Les utilisateurs ne doivent pas toucher aux tampons de données publiés tant que l'opération de réception n'est pas terminée. Les tampons de réception publiés sont appariés avec les messages d'envoi entrants en fonction des étiquettes associées aux tampons d'envoi et de

réception.

Un point de terminaison doit être activé avant qu'une application puisse y publier des opérations d'envoi ou de réception. Pour les points de terminaison connectés, les tampons de réception peuvent être publiés avant que connect ou accept soit appelé sur le point de terminaison. Cela garantit que les tampons sont disponibles pour recevoir les données entrantes immédiatement après l'établissement de la

connexion.

Les opérations de message terminées sont signalées à l'utilisateur via un ou plusieurs collecteurs d'événements associés au point de terminaison. Les utilisateurs fournissent un contexte qui est associé à chaque opération et qui est renvoyé à l'utilisateur dans le cadre de la complétion de l'événement. Voir fi_cq pour les détails sur les événements de

complétion.

d

NOM

fi_trecv, fi_trecvv, fi_trecvmsg - poster des tampons de réception tagués

SYNTAXE

#include <rdma/fi_tagged.h>

ssize_t fi_trecv(struct fi_endpoint *endpt, void *buf, size_t len, void *key,
    uint64_t tag, uint32_t match_flags, void *context);

ssize_t fi_trecvv(struct fi_endpoint *endpt, struct fi_iov *iov, size_t count,
    void *key, uint64_t tag, uint32_t match_flags, void *context);

ssize_t fi_trecvmsg(struct fi_endpoint *endpt, struct fi_msg_tagged *msg,
    uint32_t flags);

La valeur de balise pour la recherche de message. Les messages reçus avec une balise correspondante (en tenant compte desmatch_flags) seront placés dans ce tampon.

DESCRIPTION

Les appels de réception tagués sont utilisés pour poster des tampons sur la file d'attente de réception d'un point de terminaison. Ces tampons sont ensuite utilisés pour recevoir des messages tagués envoyés par d'autres points de terminaison.

fi_trecv

L'appel fi_trecv poste un tampon de données dans la file d'attente de réception du point de terminaison correspondant. Les réceptions postées sont recherchées dans l'ordre où elles ont été postées afin de faire correspondre les envois. Les limites des messages sont maintenues. L'ordre dans lequel les réceptions se terminent dépend du type de point de terminaison et du protocole.

fi_trecvv

L'appel fi_trecvv ajoute la prise en charge d'une liste scatter-gather à fi_trecv. fi_trecvv poste l'ensemble des tampons de données référencés par le paramètreiovpour recevoir des données entrantes.

fi_trecvmsg

L'appel fi_trecvmsg permet de poster des tampons sur des points de terminaison connectés et sans connexion, avec la possibilité de contrôler l'opération de réception par appel grâce à l'utilisation de drapeaux. La fonction fi_trecvmsg prend en entrée une structure fi_msg_tagged.

DRAPEAUX

Les appels fi_trecvmsg et fi_tsendmsg permettent à l'utilisateur de spécifier des drapeaux qui peuvent modifier le comportement par défaut de gestion des messages du point de terminaison. Les drapeaux spécifiés avec fi_trecvmsg / fi_tsendmsg remplacent la plupart des drapeaux précédemment configurés avec le point de terminaison, sauf indication contraire (voir fi_endpoint). La liste suivante de drapeaux est utilisable avec fi_trecvmsg et/ou fi_tsendmsg.

FI_REMOTE_CQ_DATA
S'applique à fi_tsendmsg. Indique que des données de CQ distantes sont disponibles et doivent être envoyées dans le cadre de la requête. Voir fi_getinfo pour plus de détails sur FI_REMOTE_CQ_DATA. Ce drapeau est implicitement défini pour fi_tsenddata et fi_tinjectdata.
FI_COMPLETION
Indique qu'une entrée de complétion doit être générée pour l'opération spécifiée. Le point de terminaison doit être lié à une file d'attente de complétion avec FI_SELECTIVE_COMPLETION qui correspond à l'opération spécifiée, sinon ce drapeau est ignoré.
FI_MORE
Indique que l'utilisateur a des requêtes supplémentaires qui seront immédiatement postées après le retour de l'appel actuel. L'utilisation de ce drapeau peut améliorer les performances en permettant au fournisseur d'optimiser son accès au matériel fabric.
FI_INJECT
S'applique à fi_tsendmsg. Indique que le tampon de données sortantes doit être retourné à l'utilisateur immédiatement après le retour de l'appel d'envoi, même si l'opération est gérée de manière asynchrone. Cela peut nécessiter que l'implémentation du fournisseur sous-jacent copie les données dans un tampon local et transfère à partir de ce tampon. Ce drapeau ne peut être utilisé qu'avec des messages plus petits queinject_size.
FI_MULTI_RECV
S'applique aux opérations de réception taguées postées lorsque la capacité FI_TAGGED_MULTI_RECV est activée. Ce drapeau permet à l'utilisateur de poster un seul tampon de réception tagué qui recevra plusieurs messages entrants. Les messages reçus seront empilés dans le tampon de réception jusqu'à ce que le tampon soit consommé. L'utilisation de ce drapeau peut entraîner une seule opération de réception postée pour générer plusieurs événements à mesure que les messages sont placés dans le tampon. Le placement des données reçues dans le tampon peut être soumis à des restrictions d'alignement spécifiques au fournisseur.

Le tampon sera libéré par le fournisseur lorsque l'espace tampon disponible tombera en dessous du minimum spécifié (voir FI_OPT_MIN_MULTI_RECV). Notez qu'une entrée dans la file d'attente de complétion de réception associée sera toujours générée lorsque le tampon aura été consommé, même si d'autres complétions de réception ont été supprimées (c'est-à-dire que le contexte Rx a été configuré pour FI_SELECTIVE_COMPLETION). Voir le drapeau de complétion FI_MULTI_RECV fi_cq(3).

FI_INJECT_COMPLETE
S'applique à fi_tsendmsg. Indique qu'une complétion doit être générée lorsque les tampons sources peuvent être réutilisés.
FI_TRANSMIT_COMPLETE
S'applique à fi_tsendmsg. Indique qu'une complétion ne doit pas être générée tant que l'opération n'a pas été transmise avec succès et n'est plus suivie par le fournisseur.
FI_MATCH_COMPLETE
S'applique à fi_tsendmsg. Indique qu'une complétion doit être générée uniquement après que le message a été mis en correspondance avec un tampon tagué ou a été rejeté par l'application cible.
FI_FENCE
S'applique aux transmissions. Indique que l'opération demandée, également appelée opération clôturée, et toute opération postée après l'opération clôturée seront différées jusqu'à ce que toutes les opérations précédentes ciblant le même point de terminaison pair soient terminées. Les opérations postées après la clôture verront et/ou remplaceront les résultats de toute opération initiée avant l'opération clôturée.

L'ordre des opérations commençant par la publication de l'opération clôturée (inclusive) jusqu'à la publication d'une opération clôturée subséquente (exclusive) est contrôlé par la sémantique d'ordre du point de terminaison.

FI_AUTH_KEY
Valide uniquement avec les domaines configurés avec FI_AV_AUTH_KEY et les points de terminaison sans connexion configurés avec FI_DIRECTED_RECV ou FI_TAGGED_DIRECTED_RECV. Lorsqu'il est utilisé avec fi_trecvmsg, ce drapeau indique quesrc_addrest une clé d'autorisation fi_addr_t au lieu d'un point de terminaison fi_addr_t.

Les drapeaux suivants peuvent être utilisés avec fi_trecvmsg.

FI_PEEK
Le drapeaupeekpeut être utilisé pour voir si un message spécifié est arrivé. Une requêtepeekest souvent utile sur les points de terminaison pour lesquels la mise en mémoire tampon allouée par le fournisseur est activée. Contrairement aux opérations de réception standard, une opération de réception avec le drapeau FI_PEEK défini ne reste pas dans la file d'attente du fournisseur après la réussite de la complétion de lapeek. L'opérationpeekfonctionne de manière asynchrone et les résultats de l'opérationpeeksont disponibles dans la file d'attente de complétion associée au point de terminaison. Si aucun message ne correspond aux balises spécifiées dans la requêtepeek, une entrée d'erreur dans la file d'attente de complétion avec le champerrdéfini sur FI_ENOMSG sera disponible.

Si une requêtepeeklocalise un message correspondant, l'opération se termine avec succès. Les données de complétion renvoyées indiqueront les métadonnées associées au message, telles que la longueur du message, les drapeaux de complétion, les données CQ disponibles, la balise et l'adresse source. Les données disponibles sont soumises au format de l'entrée de complétion (par exemple,struct fi_cq_tagged_entry).

FI_CLAIM
Si ce drapeau est utilisé en conjonction avec FI_PEEK, il indique que si la requêtepeekse termine avec succès (indiquant qu'un message correspondant a été trouvé), le message est réclamé par l'appelant. Les messages réclamés ne peuvent être récupérés qu'à l'aide d'une opération de réception ultérieure et appariée avec le drapeau FI_CLAIM défini. Une opération de réception avec le drapeau FI_CLAIM défini, mais sans FI_PEEK, est utilisée pour récupérer un message précédemment réclamé.

Pour utiliser le drapeau FI_CLAIM, une application doit fournir une structure fi_context comme contexte pour l'opération de réception. La même structure fi_context utilisée pour une opération FI_PEEK + FI_CLAIM doit être utilisée par la requête FI_CLAIM appariée.

FI_DISCARD
Ce drapeau peut être utilisé en conjonction avec FI_PEEK ou FI_CLAIM. S'il est utilisé en conjonction avec FI_PEEK, il indique que si la requêtepeekse termine avec succès (indiquant qu'un message correspondant a été trouvé), le message est rejeté par le fournisseur, car les données ne sont pas nécessaires à l'application. Ce drapeau peut également être utilisé en conjonction avec FI_CLAIM afin de rejeter un message précédemment réclamé à l'aide d'une requête FI_PEEK + FI_CLAIM.

Si ce drapeau est défini, les paramètres de tampon(s) et de longueur d'entrée sont ignorés.

VALEUR DE RETOUR

Les appels d'envoi et de réception tagués retournent 0 en cas de succès. En cas d'erreur, une valeur négative correspondant à l'errno du fabric est retournée. Les valeurserrnodu fabric sont définies dans fi_errno.h.
