PRÉSENTATIO

N

Le fournisseur de hooking est une fonction utilitaire qui peut intercepter les appels à n'importe quel fournisseur

. Le fournisseur de hook est toujours disponible, mais n'a aucun impact sur les appels tant qu'il n'est pas activé.
Il est utile pour fournir des données de performance sur des appels sélectionnés ou des informations de débogage.

FONCTIONNALITÉS PRISES EN

CHARGE

Le support du hooking est activé via la variable d'environnement FI_HOOK. Pour activer le hooking, FI_HOOK doit être défini sur le nom d'un ou plusieurs des fournisseurs de hooking disponibles. Lorsque plusieurs hooks sont spécifiés, les noms doivent être séparés par un point-virgule. Pour obtenir une liste des fournisseurs de hooking disponibles sur le système actuel, on peut utiliser l'utilitaire fi_info avec l'option de ligne de commande `–env'. Les fournisseurs de hooking sont généralement identifiés par la présence de `hook' dans le nom du

fournisseur.

Les fournisseurs de hooking connus incluent les suivants

:
ofi_hook_pe
rf
Cela intercepte les appels d'opérations de données du « chemin rapide ». Les données de performance sont capturées à l'entrée et à la sortie de l'appel, afin de fournir une moyenne de la durée de chaque appel pour se terminer. Voir la section HOOKS DE PERFORMANCE pour les données de performance
disponibles.
ofi_hook_tra
ce
Cela intercepte la plupart des appels d'API pour les communications de fabric. Les API et leurs paramètres d'exécution sont journalisés pour fournir des informations de trace détaillées pour le débogage. Voir la section HOOKS DE TRACE pour les API activées pour la
trace.
ofi_hook_prof
ile
Cela intercepte les appels d'opérations de données, les appels d'opérations cq et les appels d'enregistrement mr. Les appels d'API et la quantité de données traitées sont accumulés, pour fournir une vue de l'utilisation des API et un histogramme de la taille des données traitées lors de l'exécution d'une charge de travail. Voir la section HOOKS DE PROFIL pour le rapport en
détail.
ofi_hook_moni
tor
Similaire à ofi_hook_profile, cela intercepte les appels d'opérations de données, les appels d'opérations cq et les appels d'enregistrement mr. Les appels d'API et

HOOKS DE

PERFORMANCE

Le fournisseur de hook permet la capture de données de performance en ligne en accédant à l'Unité de Gestion des Performances du CPU (PMU). Les données PMU ne sont disponibles que sur les systèmes Linux. De plus, l'accès aux données PMU peut être restreint aux applications privilégiées (super-utilisateur)

.

Les données de performance sont capturées pour les appels critiques de transfert de données : fi_msg, fi_rma, fi_tagged, fi_cq et fi_cntr. Les données capturées sont affichées comme données journalisées en utilisant le niveau de trace FI_LOG_LEVEL. Les données de performance sont journalisées lorsque le fabric associé est

détruit.

La variable d'environnement FI_PERF_CNTR est utilisée pour identifier quel compteur de performance est suivi. Les compteurs suivants sont disponibles

:
cpu_cycl
es
Compte le nombre de cycles CPU que chaque fonction prend pour se
terminer.
cpu_ins
tr

e chaque fonction prend pour se termine
r. C'est le compteur de performan
ce par défaut si aucun n'est spécifié.

HOOKS DE

PROFIL

Ce fournisseur de hook permet la capture des appels d'opérations de données et de la quantité de données traitées. Il est activé en définissant FI_HOOK sur « profile »

.

Le fournisseur compte l'API invoquée et accumule la taille des données traitées par chaque appel d'API. Pour les opérations de données et cq, au lieu d'accumuler toutes les données ensemble, il décompose la taille des données en tranches de taille et accumule la quantité de données dans la tranche correspondante en fonction de la taille des données traitées. Pour les opérations d'enregistrement mr, il décompose la mémoire enregistrée par iface HMEM. À la fin, lorsque le fabric associé est détruit, le fournisseur génère un rapport de

profil.

Le rapport contient l'utilisation des API d'opérations de données, la quantité de données reçues dans chaque format CQ et la quantité de mémoire enregistrée pour les opérations rma s'il y en a. De plus, les API d'opérations de données sont regroupées en 4 groupes en fonction de la nature des opérations, envoi de messages (fi_sendXXX, fi_tsendXXX), réception de messages (fi_recvXXX, fi_trecvXXX), lecture rma (fi_readXXX) et écriture rma (fi_writeXXX) pour présenter le pourcentage d'utilisation de chaque

API.

HOOKS DE

MONITORING

Ce fournisseur de hook s'appuie sur le fournisseur de hook « profile » et fournit des capacités de lecture continue utiles pour le monitoring des applications libfabric. Il est activé en définissant FI_HOOK sur « monitor »

.

Similaire au fournisseur de hook « profile », ce fournisseur compte le nombre d'appels d'API invoqués et accumule la quantité de données traitées par chaque appel d'API. Consultez la documentation sur le hook « profile » pour plus

d'informations.

L'export des données est facilité à l'aide d'un fichier de communication sur le système de fichiers, qui est créé pour chaque fournisseur libfabric hooké. Le hook de monitoring s'attend à être exécuté sur un tmpfs. Si disponible et sauf indication contraire, les fichiers seront créés sous le tmpfs

/dev/shm.

Un échantillonneur peut lire périodiquement ce fichier pour extraire les données collectées. Tous les N appels d'API interceptés ou « ticks », le fournisseur vérifiera si l'export des données a été demandé par l'échantillonneur. Si c'est le cas, les données de compteur actuellement collectées sont copiées dans le fichier et l'échantillonneur est informé des nouvelles données. Les données de compteur locales au fournisseur sont ensuite effacées. Chaque échantillon contient le delta du compteur par rapport à l'échantillon

précédent.

Les fichiers de communication seront créés au chemin $FI_OFI_HOOK_MONITOR_BASEPATH/<uid>/<hostname> et aura le nom : <ppid>_<pid>_<id séquentiel>_<id de job>_<nom du fournisseur>. ppid et pid sont pris du point de vue de l'application supervisée. Dans un environnement par lots utilisant SLURM, l'identifiant de job est défini sur l'identifiant de job SLURM, sinon il est défini sur

0.

Voir fi_mon_sampler(1) pour la documentation sur l'utilisation du échantillonneur du fournisseur de

supervision.

N

:

ATH
Chaîne de chemin de base pour les fichiers de communication. (par défaut :
/dev/shm/ofi)
FI_OFI_HOOK_MONITOR_DIR_M

Mode/permissions POSIX pour les répertoires dans le chemin de base. (par défaut :
01700)
FI_OFI_HOOK_MONITOR_FILE_M
ODE
Mode/permissions POSIX pour les fichiers de communication. (par défaut :
0600)
FI_OFI_HOOK_MONITOR_TICK_
MAX
Nombre d'appels d'API avant que les fichiers de communication ne soient vérifiés pour une requête de données. (par défaut :
1024)
FI_OFI_HOOK_MONITOR_LIN
GER
Indique si les fichiers de communication doivent persister après la terminaison. (par défaut : 0)
Cela est utile pour permettre à l'échantillonneur de lire les dernières données de compteurs

sans échantillonneur entraîne l'encombrement de fichiers dans FI_OFI_HOOK_MONITOR_BASEPATH.
Assurez-vous de soit exécuter un échantillonneur soit de nettoyer ces fichiers manuellement.

LIMITATION

S

La fonctionnalité de hook n'est pas disponible pour les fournisseurs construits à l'aide de la fonctionnalité FI_FABRIC_DIRECT. C'est-à-dire que le lien direct vers un fournisseur empêche le

hook.

Le fournisseur de hooks ne fonctionne pas avec les opérations déclenc

hées. Les applications qui utilisent les opérations FI_TRIGGER e
t qui tentent d'intercepter les appels vont probablement planter.
