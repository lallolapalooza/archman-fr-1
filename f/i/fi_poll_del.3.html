fi_poll_open crée un nouvel ensemble d'interrogation. Un ensemble d'interrogation permet une méthode optimisée pour faire progresser des opérations asynchrones sur plusieurs files d'attente de complétion et compteurs et vérifier leur

fi_poll

(obsolète)

Fait progresser toutes les files d'attente de complétion et tous les compteurs associés à un ensemble d'interrogation et vérifie les événements. Si des événements ont pu se produire, les contextes associés aux files d'attente de complétion et/ou aux compteurs sont retournés. Les files d'attente de complétion retourneront leur contexte si elles ne sont pas vides. Le contexte associé à un compteur sera retourné si la valeur de succès ou la valeur d'erreur du compteur a changé depuis la dernière fois que fi_poll, fi_cntr_set ou fi_cntr_add ont été appelés. Le nombre de contextes est limité à la taille du tableau de contextes, indiqué par le paramètre

count.

Notez que fi_poll indique seulement que des événements peuvent être disponibles. Dans certains cas, les fournisseurs peuvent consommer ces événements en interne, par exemple pour faire progresser les

opérations. Cela peut entraîner des retours positifs erronés de fi_poll. Les applications devraient faire progresser leurs opérations en se basant sur les résultats de la lecture des événements d'une f
ile d'attente de complétion ou de la lecture des valeurs de compteur. La fonction fi_poll retournera toujours toutes les files d'attente de complétion et tous les compteurs qui ont de nouveaux événements.

fi_wait_open

(obsolète)

fi_wait_open alloue un nouvel ensemble d'attente. Un ensemble d'attente permet une méthode optimisée d'attente d'événements sur plusieurs files d'attente de complétion et compteurs. Si possible, un ensemble d'attente utilise un seul objet d'attente sous-jacent qui est signalé lorsqu'une condition spécifiée se produit sur une file d'attente de complétion ou un compteur

associé.

Les propriétés et le comportement d'un ensemble d'attente sont définis par struct

fi_wait_attr. 
struct fi_wait_attr {
    enum fi_wait_obj     wait_obj;  /* requested wait object */
    uint64_t             flags;     /* operation flags
*/
}
;
wait_o
bj
Les ensembles d'attente sont associés à des objets d'attente spécifiques. Les objets d'attente permettent aux applications de bloquer jusqu'à ce que l'objet d'attente soit signalé, indiquant qu'un événement est disponible pour être lu. Les valeurs suivantes peuvent être utilisées pour spécifier le type d'objet d'attente associé à un ensemble d'attente : FI_WAIT_UNSPEC, FI_WAIT_FD, FI_WAIT_MUTEX_COND (obsolète) et
FI_WAIT_YIELD.
- FI_WAIT_UNSP
EC
Spécifie que l'utilisateur n'attendra sur l'ensemble d'attente qu'à l'aide d'appels de l'interface fabric, tels que fi_wait. Dans ce cas, le fournisseur sous-jacent peut sélectionner l'objet d'attente le plus approprié ou le plus performant disponible, y compris des mécanismes d'attente personnalisés. Les applications qui sélectionnent FI_WAIT_UNSPEC ne sont pas garanties de récupérer l'objet d'attente
sous-jacent.
- FI_WAIT_
FD
Indique que l'ensemble d'attente doit utiliser un descripteur de fichier unique comme mécanisme d'attente, tel qu'exposé à l'application. En interne, cela peut nécessiter l'utilisation de epoll pour prendre en charge l'attente sur un seul descripteur de fichier. Les objets d'attente par descripteur de fichier doivent être utilisables dans les routines POSIX select(2) et poll(2), et Linux epoll(7) (si disponibles). Les fournisseurs signalent un objet d'attente FD en le marquant comme lisible ou avec une
erreur.
- FI_WAIT_MUTEX_COND
(obsolète)
Spécifie que l'ensemble d'attente doit utiliser un mutex pthread et une variable de condition comme objet
d'attente.
- FI_WAIT_POLL
FD
Cette option est similaire à FI_WAIT_FD, mais permet au mécanisme d'attente d'utiliser plusieurs descripteurs de fichier comme mécanisme d'attente, tel que vu par l'application. L'utilisation de FI_WAIT_POLLFD peut éliminer le besoin d'utiliser epoll pour abstraire la nécessité de vérifier plusieurs descripteurs de fichier lors de l'attente d'événements. Les descripteurs de fichier doivent être utilisables dans les routines POSIX select(2) et poll(2), et correspond directement à son utilisation avec poll. Voir la section NOTES ci-dessous pour plus de détails sur l'utilisation de
pollfd.
- FI_WAIT_YIE
LD
Indique que l'ensemble d'attente attendra sans objet d'attente mais cédera plutôt à chaque
attente.

fi_trywai

t

L'appel fi_trywait a été introduit dans la version 1.3 de libfabric. Le comportement de l'utilisation d'objets d'attente natifs sans l'utilisation de fi_trywait est spécifique au fournisseur et doit être considéré comme non

déterministe.

L'appel fi_trywait() est utilisé en conjonction avec les appels natifs du système d'exploitation pour bloquer sur des objets d'attente, tels que les descripteurs de fichier. L'application doit appeler fi_trywait et obtenir une valeur de retour FI_SUCCESS avant de bloquer sur un objet d'attente natif. Le fait de ne pas le faire peut entraîner le fait que l'objet d'attente ne soit pas signalé et que l'application n'observe pas les événements souhaités. Le pseudo-code suivant démontre l'utilisation de fi_trywait en conjonction avec l'appel select(2) du système

d'exploitation. 
fi_control(&cq->fid, FI_GETWAIT, (void *) &fd);
FD_ZERO(&fds);
FD_SET(fd, &fds);
while (1) {
    if (fi_trywait(&cq, 1) == FI_SUCCESS)
        select(fd + 1, &fds, NULL, &fds, &timeout);
    do {
        ret = fi_cq_read(cq, &comp, 1);
    } while (ret >
0);
}

fi_trywait() retournera FI_SUCCESS s'il est sûr de bloquer sur le(s) objet(s) d'attente correspondant(aux) au(des) descripteur(s) de fabric, ou -FI_EAGAIN s'il y a des événements en file d'attente sur le descripteur de fabric ou si le blocage pourrait faire planter

l'application.

L'appel prend un tableau de descripteurs de fabric. Pour chaque objet d'attente qui sera passé à la routine d'attente native, le descripteur de fabric correspondant doit d'abord être passé à fi_trywait. Tous les descripteurs de fabric passés dans un seul appel fi_trywait doivent utiliser le même type d'objet d'attente

sous-jacent.

Les types de descripteurs de fabric suivants peuvent être passés à fi_trywait : les files d'événements, les files de complétion, les compteurs et les ensembles d'attente. Les applications qui souhaitent utiliser des appels d'attente natifs doivent sélectionner des objets d'attente spécifiques lors de l'allocation de telles ressources. Par exemple, en définissant la valeur de l'attribut de création wait_obj de l'élément à

FI_WAIT_FD.

Si l'objet d'attente à vérifier appartient à un ensemble d'attente, seul l'ensemble d'attente lui-même doit être passé à fi_trywait. Les ressources de fabric associées à l'ensemble d'attente ne le doivent

pas.

En recevant une valeur de retour de -FI_EAGAIN de fi_trywait, une application doit lire toutes les complétions et événements

en file d'attente, et appeler fi_trywait à nouveau avant de tenter de bloquer. Les applications peuvent utiliser un ense
mble de sondage de fabric pour identifier les files de complétion et les compteurs qui peuvent nécessiter un traitement.

fi_contro

l

L'appel fi_control est utilisé pour accéder aux détails spécifiques au fournisseur ou à l'implémentation des fids qui prennent en charge les appels bloquants, tels que les ensembles d'attente, les files de complétion, les compteurs et les files d'événements. L'accès à l'ensemble d'attente ou au fid doit être sérialisé sur tous les appels lorsque fi_control est invoqué, car il peut rediriger l'implémentation des opérations d'ensemble d'attente. Les commandes de contrôle suivantes sont utilisables avec un ensemble d'attente ou un

fid.
FI_GETWAIT (void
**)
Cette commande permet à l'utilisateur de récupérer l'objet d'attente de bas niveau associé à un ensemble d'attente ou à un fid. Le format de l'ensemble d'attente est spécifié lors de la création de l'ensemble d'attente, à travers les attributs de l'ensemble d'attente. Le paramètre arg de fi_control doit être une adresse où un pointeur vers l'objet d'attente retourné sera écrit. Cela doit être un 'int *' pour FI_WAIT_FD, `struct fi_mutex_cond' pour FI_WAIT_MUTEX_COND (obsolète), ou `struct fi_wait_pollfd' pour FI_WAIT_POLLFD. La prise en charge de FI_GETWAIT est spécifique au

NOTE

S

Dans de nombreuses situations, les appels bloquants peuvent avoir besoin d'attendre des signaux envoyés à un certain nombre de descripteurs de fichier. Par exemple, c'est le cas pour les fournisseurs basés sur les sockets, tels que tcp et udp, ainsi que pour les fournisseurs utilitaires tels que multi-rail. Par simplicité, lorsque epoll est disponible, il peut être utilisé pour limiter le nombre de descripteurs de fichier qu'une application doit surveiller. L'utilisation d'epoll peut également être requise pour prendre en charge

FI_WAIT_FD.

Cependant, afin de prendre en charge l'attente sur plusieurs descripteurs de fichier sur les systèmes où la prise en charge d'epoll n'est pas disponible, ou où les performances d'epoll pourraient nuire aux performances, FI_WAIT_POLLFD fournit ce mécanisme. Une différence significative entre l'utilisation des objets d'attente POLLFD et FD est qu'avec FI_WAIT_POLLFD, les descripteurs de fichier peuvent changer dynamiquement. À titre d'exemple, les descripteurs de fichier associés à l'ensemble d'attente d'une file de complétion peuvent changer à mesure que les associations d'extrémité avec la CQ sont ajoutées et

supprimées.

La structure fi_wait_pollfd est utilisée pour récupérer tous les descripteurs de fichier pour les fids utilisant FI_WAIT_POLLFD pour prendre en charge les appels

bloquants. 
struct fi_wait_pollfd {
    uint64_t      change_index;
    size_t        nfds;
    struct pollfd
*fd;
}
;
change_ind
ex
Le change_index peut être utilisé pour déterminer s'il y a eu des changements dans la liste des descripteurs de fichier. Chaque fois qu'un descripteur de fichier est ajouté, supprimé ou que ses événements sont mis à jour, ce champ est incrémenté par le fournisseur. Les applications souhaitant attendre directement sur les descripteurs de fichier doivent mettre en cache la valeur de change_index. Avant de bloquer sur les événements des descripteurs de fichier, l'application doit utiliser fi_control() pour récupérer le change_index actuel et le comparer à sa valeur en cache. Si les valeurs diffèrent, l'application doit mettre à jour sa liste de descripteurs de fichier avant de
bloquer.
nf
ds
En entrée de fi_control(), cela indique le nombre d'entrées dans le tableau struct pollfd *. En sortie, cela sera défini au nombre d'entrées nécessaires pour stocker le nombre actuel de descripteurs de fichier. Si la valeur d'entrée est inférieure à la valeur de sortie, fi_control() retournera l'erreur -FI_ETOOSMALL. Notez que définir nfds = 0 permet une manière efficace de vérifier le
change_index.
f
d
Cela pointe vers un tableau d'entrées struct pollfd. Le nombre d'entrées est spécifié à travers le champ nfds. Si le nombre d'ent
rées nécessaires est inférieur ou égal au nombre d'entrées disponibles, le tableau struct pollfd sera rempli avec une liste
de descripteurs de fichier et les événements correspondants qui peuvent être utilisés dans les appels select(2) et poll(2).

Le change_index n'est mis à jour que lorsque les descripteurs de fichier associés à l'ensemble de fichiers pollfd ont changé. Vér

ifier le change_index est une étape supplémentaire nécessaire lorsque l'on travaille directement avec des objets d'attente FI
_WAIT_POLLFD. L'utilisation de la fonction fi_trywait() est toujours requise si l'on accède directement aux objets d'attente.
