DESCRIPTIO

N

L'application findscu implémente un SCU pour la classe de service Query/Retrieve et la classe de service Basic Worklist Management. findscu ne prend en charge que la fonctionnalité de requête à l'aide du message C-FIND. Elle envoie des clés de requête à un SCP et atte

nd les réponses. L'application peut être utilisée pour tester les SCP
des classes de service Query/Retrieve et Basic Worklist Management.

NOTE

S

Chaque fichier fourni sur la ligne de commande sera envoyé au SCP dans le cadre d'une requête C-FIND. Le fichier de requête doit être un jeu de données DICOM valide contenant la partie jeu de données d'un message C-FIND-RQ. Le fichier de requête pourrait, par exemple, être créé avec l'utilitaire dump2dcm à partir d'un script comme l'exemple suivant

: 
# requête des noms et identifiants de patients
(0008,0052) CS [PATIENT]     # QueryRetrieveLevel
(0010,0010) PN []            # PatientName
(0010,0020) LO []            #
PatientID

Les attributs individuels de chaque fichier envoyé peuvent être modifiés ou complétés à l'aide de l'option -k. Par exemple, la commande

: 
findscu -P -k "(0010,0010)=HEWETT*" caesar 5678 patqry.
dcm

lorsqu'elle est envoyée au SCP caesar sur le port TCP/IP 5678, fera en sorte que tout attribut PatientName dans patqry.dcm ait la valeur "HEWETT*". Si un tel attribut est présent, il sera remplacé ; s'il est absent, il sera inséré. L' option -k peut être présente plus d'une fois. La partie valeur (après le '=') peut être absente, ce qui fait que l'attribut est envoyé avec une longueur

nulle.

Dans les versions antérieures de findscu, les clés de balises étaient spécifiées sans accolades autour des numéros de groupe et d'élément, par ex. "0010,0010" au lieu de "(0010,0010)". Il est recommandé de passer à la nouvelle syntaxe ; cependant, l'ancienne syntaxe fonctionne

toujours.

De plus, -k accepte les noms de dictionnaire au lieu des balises d'éléments pour spécifier les éléments DICOM. Par exemple, l'appel findscu ci-dessus se lit alors ainsi

: 
findscu -P -k PatientName="HEWETT*" caesar 5678 patqry.
dcm

Il est également possible de spécifier des séquences, des éléments et des attributs imbriqués à l'aide de l' option -k. Dans ces cas, une notation "chemin" spéciale doit être utilisée, par

ex. 
findscu -W -k "(0040,0100)[0].Modality=CT" caesar
5678

Cette commande interroge un serveur de liste de travail sur l'hôte caesar pour toute procédure planifiée pour les modalités CT en spécifiant la balise (0040,0100) "Scheduled Procedure Step Sequence" et un attribut "Modality" dans le premier élément de cette séquence avec la valeur "CT". Les détails sur cette notation de chemin se trouvent dans la documentation de dcmodify

.

Si aucun fichier n'est spécifié sur la ligne de commande, la requête doit être spécifiée complètement avec une ou plusieurs options -k. Si plusieurs fichiers de requête sont fournis, findscu enverra plusieurs requêtes C-FIND au

SCP.

Chaque jeu d'identifiants de réponse reçu sera envoyé au logger sauf si l'option --hide-responses, l'une des variantes --extract ci-dessous, --quiet ou une configuration appropriée du logger est utilisée. Dans de tels cas, la sortie vers le logger peut être forcée avec l'option --show-responses

.

En outre, les jeux de données de réponse peuvent également être extraits en tant que fichiers DICOM individuels (à l'aide de l'option --extract) ou en fichiers XML (à l'aide de l'option --extract-xml). Le format de sortie de ce dernier est décrit par le fichier dcm2xml.dtd (commençant par l'élément de premier niveau "data-set"). Pour les fichiers XML, le jeu de caractères spécifique est automatiquement mappé vers un encodage XML approprié. Si cela n'est pas possible, par ex. dans le cas des jeux de caractères ISO 2022, les caractères non ASCII et ceux inférieurs à #32 sont stockés sous la forme "&" où "nnn" fait référence au code numérique du caractère. Veuillez noter que cela peut entraîner des références d'entités de caractères invalides (telles que "&" pour ESC) et que cela fera que la plupart des analyseurs XML rejetteront le

document.

Alternativement, tous les jeux de données de réponse d'une association peuvent être extraits dans un seul fichier XML à l'aide de l'option --extract-xml-single. L'élément de premier niveau du document XML est "responses" (avec un attribut "type" valant "C-FIND"). Les jeux de données individuels sont stockés comme décrit ci-dessus. Si la prise en charge de la conversion de jeu de caractères est activée, l'encodage UTF-8 est utilisé, c'est-à-dire que tous les jeux de données sont convertis en encodage UTF-8 (ce qui est fortement recommandé afin d'éviter les problèmes avec les caractères non ASCII lorsque différents jeux de caractères sont utilisés)

.

JOURNALISATI

ON

Le niveau de sortie du journal des différentes outils de ligne de commande et des bibliothèques sous-jacentes peut être spécifié par l'utilisateur. Par défaut, seules les erreurs et les avertissements sont écrits sur le flux d'erreur standard. En utilisant l'option --verbose, des messages informatifs tels que les détails de traitement sont également rapportés. L'option --debug peut être utilisée pour obtenir plus de détails sur l' activité interne, par ex. à des fins de débogage. D'autres niveaux de journalisation peuvent être sélectionnés à l'aide de l'option --log-level. En mode --quiet, seules les erreurs fatales sont rapportées. Dans de tels événements d'erreur très graves, l'application se terminera généralement. Pour plus de détails sur les différents niveaux de journalisation, voir la documentation du module

"oflog".

Si la sortie du journal doit être écrite dans un fichier (éventuellement avec rotation du fichier journal), dans syslog (Unix) ou dans le journal des événements (Windows), l'option --log-config peut être utilisée. Ce fichier de configuration permet également de diriger uniquement certains messages vers un flux de sortie particulier et de filtrer certains messages en fonction du module ou de l'application où ils sont générés. Un exemple de fichier de configuration est fourni dans <etcdir>/l

ogger
.cfg.

LIGNE DE

COMMANDE

Tous les outils de ligne de commande utilisent la notation suivante pour les paramètres : les crochets enclos les valeurs optionnelles (0-1), trois points de suspension indiquent que plusieurs valeurs sont autorisées (1-n), une combinaison des deux signifie de 0 à n

valeurs.

Les options de ligne de commande sont distinguées des paramètres par un signe '+' ou '-' en tête, respectivement. Habituellement, l'ordre et la position des options de ligne de commande sont arbitraires (c'est-à-dire qu'elles peuvent apparaître n'importe où). Cependant, si des options sont mutuellement exclusives, la dernière occurrence la plus à droite est utilisée. Ce comportement est conforme aux règles d'évaluation standard des shells Unix

courants.

En outre, un ou plusieurs fichiers de commande peuvent être spécifiés en utilisant un signe '@' comme préfixe du nom de fichier (par ex. @command.txt). Un tel argument de commande est remplacé par le contenu du fichier texte correspondant (plusieurs espaces blancs sont traités comme un seul séparateur s'ils n'apparaissent pas entre deux guillemets) avant toute autre évaluation. Veuillez noter qu'un fichier de commande ne peut pas contenir un autre fichier de commande. Cette approche simple mais efficace permet de résumer des combinaisons courantes d'options/paramètres et évite des lignes de commande longues et déroutantes (un exemple est fourni dans le fichier <datadir>/du

mppat
.txt).

ENVIRONNEMEN

T

L'utilitaire findscu essaiera de charger les dictionnaires de données DICOM spécifiés dans la variable d'environnement DCMDICTPATH. Par défaut, c'est-à-dire si la variable d'environnement DCMDICTPATH n'est pas définie, le fichier <datadir>/dicom.dic sera chargé sauf si le dictionnaire est intégré à l'application (par défaut sous Windows)

.

Le comportement par défaut devrait être préféré et la variable d'environnement DCMDICTPATH n'est utilisée que lorsque des dictionnaires de données alternatifs sont nécessaires. La variable d'environnement DCMDICTPATH a le même format que la variable PATH du shell Unix en ce sens qu'un deux-points (":") sépare les entrées. Sur les systèmes Windows, un point-virgule (";") est utilisé comme séparateur. Le code du dictionnaire de données essaiera de charger chaque fichier spécifié dans la variable d'environnement DCMDICTPATH. C'est une erreur si aucun dictionnaire de données ne peut être

chargé.

Selon les options de ligne de commande spécifiées, l'utilitaire findscu essaiera de charger les tables de correspondance de jeu de caractères. Cela se produit lorsque DCMTK a été compilé avec la bibliothèque oficonv (qui est la configuration par défaut) et que les tables de correspondance ne sont pas intégrées à la bibliothèque (par défaut lorsque DCMTK utilise des bibliothèques partagées)

.

Les fichiers de table de correspondance sont attendus dans le <datadir> de DCMTK. La variable d'environnement DCMICONVPATH peut être utilisée pour spécifier un emplacement différent. Si un emplacement diffé

rent est spécifié, ces tables de correspondance
remplacent également toutes les tables intégrées.
