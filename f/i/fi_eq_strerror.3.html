NOM

fi_eq - Opérations sur les files d'attente d'événements

fi_eq_open / fi_close
Ouvrir/fermer une file d'attente d'événements
fi_control
Contrôler l'opération de l'EQ
fi_eq_read / fi_eq_readerr
Lire un événement depuis une file d'attente d'événements
fi_eq_write
Écrit un événement dans une file d'attente d'événements
fi_eq_sread
Une lecture synchrone (bloquante) d'une file d'attente d'événements
fi_eq_strerror
Convertit les informations d'erreur spécifiques au fournisseur en une chaîne imprimable

SYNOPSIS

#include <rdma/fi_domain.h>
int fi_eq_open(struct fid_fabric *fabric, struct fi_eq_attr *attr,
    struct fid_eq **eq, void *context);
int fi_close(struct fid *eq);
int fi_control(struct fid *eq, int command, void *arg);
ssize_t fi_eq_read(struct fid_eq *eq, uint32_t *event,
    void *buf, size_t len, uint64_t flags);
ssize_t fi_eq_readerr(struct fid_eq *eq, struct fi_eq_err_entry *buf,
    uint64_t flags);
ssize_t fi_eq_write(struct fid_eq *eq, uint32_t event,
    const void *buf, size_t len, uint64_t flags);
ssize_t fi_eq_sread(struct fid_eq *eq, uint32_t *event,
    void *buf, size_t len, int timeout, uint64_t flags);
const char * fi_eq_strerror(struct fid_eq *eq, int prov_errno,
      const void *err_data, char *buf, size_t len);

DESCRIPTION

Les files d'attente d'événements sont utilisées pour signaler les événements associés aux opérations de contrôle. Elles sont liées à l'enregistrement de mémoire, aux vecteurs d'adresses, à la gestion des connexions et aux événements de niveau fabric et domaine. Les événements signalés sont soit associés à une opération demandée, soit affiliés à un appel qui enregistre des types d'événements spécifiques, tels que l'écoute des demandes de connexion.

fi_eq_open

fi_eq_open alloue une nouvelle file d'attente d'événements.

Les propriétés et le comportement d'une file d'attente d'événements sont définis par la structure fi_eq_attr.

struct fi_eq_attr {
    size_t               size;      /* nombre d'entrées pour EQ */
    uint64_t             flags;     /* indicateurs d'opération */
    enum fi_wait_obj     wait_obj;  /* objet d'attente demandé */
    int                  signaling_vector; /* affinité d'interruption */
    struct fid_wait     *wait_set;  /* jeu d'attente optionnel, obsolète */
};
size
Spécifie la taille minimale d'une file d'attente d'événements.
flags
Indicateurs qui contrôlent la configuration de l'EQ.
- FI_WRITE
Indique que l'application nécessite la prise en charge de l'insertion d'événements utilisateur dans l'EQ. Si cet indicateur est défini, l'opération fi_eq_write doit être prise en charge par le fournisseur. Si l'indicateur FI_WRITE n'est pas défini, l'application ne peut pas appeler fi_eq_write.
- FI_AFFINITY
Indique que le champ signaling_vector (voir ci-dessous) est valide.
wait_obj
Les EQ peuvent être associés à un objet d'attente spécifique. Les objets d'attente permettent aux applications de bloquer jusqu'à ce que l'objet d'attente soit signalé, indiquant qu'un événement est disponible à lire. Les utilisateurs peuvent utiliser fi_control pour récupérer l'objet d'attente sous-jacent associé à un EQ, afin de l'utiliser dans d'autres appels système. Les valeurs suivantes peuvent être utilisées pour spécifier le type d'objet d'attente associé à un EQ :
- FI_WAIT_NONE
Utilisé pour indiquer que l'utilisateur ne bloquera pas (n'attendra pas) les événements sur l'EQ. Lorsque FI_WAIT_NONE est spécifié, l'application ne peut pas appeler fi_eq_sread. C'est la valeur par défaut si aucun objet d'attente n'est spécifié.
- FI_WAIT_UNSPEC
Spécifie que l'utilisateur n'attendra sur l'EQ qu'en utilisant les appels de l'interface fabric, tels que fi_eq_sread. Dans ce cas, le fournisseur sous-jacent peut sélectionner l'objet d'attente le plus approprié ou le plus performant disponible, y compris des mécanismes d'attente personnalisés. Les applications qui choisissent FI_WAIT_UNSPEC ne sont pas garanties de récupérer l'objet d'attente sous-jacent.
- FI_WAIT_SET (obsolète)
Indique que la file d'attente d'événements doit utiliser un objet de jeu d'attente pour attendre les événements. Si spécifié, le champ wait_set doit référencer un objet de jeu d'attente existant.
- FI_WAIT_FD
Indique que l'EQ doit utiliser un descripteur de fichier comme mécanisme d'attente. Un objet d'attente de descripteur de fichier doit être utilisable dans les routines select, poll et epoll. Cependant, un fournisseur peut signaler un objet d'attente FD en le marquant comme lisible ou avec une erreur.
- FI_WAIT_MUTEX_COND (obsolète)
Spécifie que l'EQ doit utiliser un mutex pthread et une variable de condition comme objet d'attente.
- FI_WAIT_YIELD
Indique que l'EQ attendra sans objet d'attente mais cédera à chaque attente. Permet l'utilisation de fi_eq_sread via une boucle serrée.
signaling_vector
Si l'indicateur FI_AFFINITY est défini, celui-ci indique le numéro de CPU logique (0..max cpu - 1) auquel les interruptions associées à l'EQ doivent cibler. Ce champ doit être traité comme une indication pour le fournisseur et peut être ignoré si le fournisseur ne prend pas en charge l'affinité d'interruption.
wait_set (obsolète)
Si wait_obj est FI_WAIT_SET, ce champ fait référence à un objet d'attente auquel la file d'attente d'événements doit s'attacher. Lorsqu'un événement est inséré dans la file d'attente d'événements, le jeu d'attente correspondant sera signalé si toutes les conditions nécessaires sont remplies. L'utilisation d'un wait_set permet une méthode optimisée pour attendre les événements sur plusieurs files d'attente d'événements. Ce champ est ignoré si wait_obj n'est pas FI_WAIT_SET.

fi_close

L'appel fi_close libère toutes les ressources associées à une file d'attente d'événements. Tous les événements qui restent dans l'EQ lors de sa fermeture sont perdus.

L'EQ ne doit être lié à aucun autre objet avant d'être fermé, sinon l'appel retournera -FI_EBUSY.

fi_control

L'appel fi_control est utilisé pour accéder aux détails spécifiques du fournisseur ou de l'implémentation de la file d'attente d'événements. L'accès à l'EQ doit être sérialisé sur tous les appels lorsque fi_contr

FI_GETWAIT (void **)
Cette commande permet à l'utilisateur de récupérer l'objet de veille de bas niveau associé à l'EQ. Le format de l'objet de veille est spécifié lors de la création de l'EQ, via les attributs de l'EQ. Le paramètre fi_control arg doit être une adresse où un pointeur vers l'objet de veille retourné sera écrit. Il doit s'agir d'un 'int *' pour FI_WAIT_FD, ou de `struct fi_mutex_cond' pour FI_WAIT_MUTEX_COND (obsolète).
struct fi_mutex_cond {
    pthread_mutex_t     *mutex;
    pthread_cond_t      *cond;
};

fi_eq_read

Les opérations fi_eq_read effectuent une lecture non bloquante des données d'événement depuis l'EQ. Le format des données d'événement est basé sur le type d'événement récupéré de l'EQ, tous les événements commençant par un en-tête struct fi_eq_entry. Au plus un événement sera retourné par opération de lecture d'EQ. Le nombre d'octets lus avec succès depuis l'EQ est retourné par la lecture. Le drapeau FI_PEEK peut être utilisé pour indiquer que les données d'événement doivent être lues de l'EQ sans être consommées. Une lecture ultérieure sans le drapeau FI_PEEK supprimerait alors l'événement de l'EQ.

Les types d'événements suivants peuvent être rapportés à une EQ, ainsi que des informations concernant le format associé à chaque événement.

Opérations de contrôle asynchrones
Les opérations de contrôle asynchrones sont des requêtes de base qui nécessitent simplement de générer un événement pour indiquer qu'elles sont terminées. Celles-ci incluent les types d'événements suivants : enregistrement de mémoire, résolution de vecteur d'adresses et jointures multicast.

Les requêtes de contrôle rapportent leur achèvement en insérant une struct fi_eq_entry dans l'EQ. Le format de cette structure est :

struct fi_eq_entry {
    fid_t            fid;        /* fid associé à la requête */
    void            *context;    /* contexte de l'opération */
    uint64_t         data;       /* données spécifiques à l'achèvement */
};

Pour l'achèvement des opérations de contrôle asynchrones de base, l'événement retourné indiquera l'opération qui s'est terminée, et le fid fera référence au descripteur de tissu associé à l'événement. Pour l'enregistrement de mémoire, il s'agira d'un événement FI_MR_COMPLETE et du fid_mr. La résolution d'adresses fera référence à un événement FI_AV_COMPLETE et fid_av. Les jointures multicast rapporteront un FI_JOIN_COMPLETE et fid_mc. Le champ context sera défini sur le contexte spécifié dans le cadre de l'opération, sinon le contexte sera associé au descripteur de tissu. Le champ data sera défini comme décrit dans la page de manuel du type d'objet correspondant (par exemple, voir fi_av(3) pour une description de la manière dont les insertions de vecteur d'adresses asynchrones sont complétées).

Notification de connexion
Les notifications de connexion sont des notifications de gestion de connexion utilisées pour établir ou supprimer des connexions entre points d'extrémité. Il existe trois événements de notification de connexion : FI_CONNREQ, FI_CONNECTED et FI_SHUTDOWN. Les notifications de connexion sont rapportées en utilisant la struct fi_eq_cm_entry :
struct fi_eq_cm_entry {
    fid_t            fid;        /* fid associé à la requête */
    struct fi_info  *info;       /* informations sur le point d'extrémité */
    uint8_t         data[];     /* données de connexion de l'application */
};

Un événement de demande de connexion (FI_CONNREQ) indique qu'un point d'extrémité distant souhaite établir une nouvelle connexion à un point d'extrémité d'écoute, ou passif. Le fid est le point d'extrémité passif. Les informations concernant les capacités et attributs du point d'extrémité actif demandé sont disponibles via le champ info. L'application est responsable de la libération de cette structure en appelant fi_freeinfo lorsqu'elle n'est plus nécessaire. Le champ fi_info connreq fera référence à la demande de connexion associée à cet événement. Pour accepter une connexion, un point d'extrémité doit d'abord être créé en passant une structure fi_info référençant ce champ connreq à fi_endpoint(). Ce point d'extrémité est ensuite passé à fi_accept() pour achever l'acceptation de la tentative de connexion. La création du point d'extrémité est plus facilement accomplie en passant la fi_info retournée dans le cadre de l'événement CM à fi_endpoint(). Si la connexion doit être rejetée, le connreq est passé à fi_reject().

Toutes les données d'application échangées dans le cadre de la demande de connexion sont placées au-delà de la structure fi_eq_cm_entry. La quantité de données disponibles dépend de l'application et est limitée à l'espace tampon fourni par l'application lors de l'appel à fi_eq_read. La quantité de données retournées peut être calculée à l'aide de la valeur de retour de fi_eq_read. Notez que la quantité de données retournées est limitée par le protocole de connexion sous-jacent, et la longueur de toutes les données retournées peut inclure un rembourrage de protocole. Par conséquent, la longueur retournée peut être supérieure à celle spécifiée par le pair connectant.

Si une demande de connexion a été acceptée, un événement FI_CONNECTED sera généré des deux côtés de la connexion. Le côté actif – celui qui a appelé fi_connect() – peut recevoir des données utilisateur dans le cadre de l'événement FI_CONNECTED. Les données utilisateur sont transmises au gestionnaire de connexion côté passif via l'appel fi_accept. Les données utilisateur ne sont pas fournies avec un événement FI_CONNECTED côté écoute de la connexion.

La notification qu'un pair distant s'est déconnecté d'un point d'extrémité actif se fait via l'événement FI_SHUTDOWN. La notification de fermeture utilise la struct fi_eq_cm_entry telle que déclarée ci-dessus. Le champ fid pour une notification de fermeture fait référence au fid_ep du point d'extrémité actif.

Notification d'erreur asynchrone
Les erreurs asynchrones sont utilisées pour signaler des problèmes avec les ressources du tissu. Les erreurs signalées peuvent être fatales ou transitoires, en fonction de l'erreur, et entraîner la désactivation de la ressource. Les ressources désactivées échoueront les opérations soumises contre elles jusqu'à ce qu'elles soient explicitement réactivées par l'application.

Des erreurs asynchrones peuvent être rapportées pour les files d'attente de complétion et les points d'extrémité de tous types. Les erreurs de CQ peuvent survenir lorsque la gestion des ressources a été désactivée et que le fournisseur a détecté un dépassement de file d'attente. Les erreurs de point d'extrémité peuvent résulter de nombreuses actions, mais sont souvent associées à une opération échouée. Les opérations peuvent échouer en raison de dépassements de tampon, de permissions invalides, de clés d'accès mémoire incorrectes, de défaillances de routage réseau, de problèmes de joignabilité réseau, etc.

Les erreurs asynchrones sont rapportées en utilisant la struct fi_eq_err_entry, telle que définie ci-dessous. Le descripteur de tissu (fid) associé à l'erreur est fourni dans le cadre des données d'erreur. Un code d'erreur est également disponible pour déterminer la cause de l'erreur.

fi_eq_sread

L'appel fi_eq_sread est l'équivalent bloquant (ou synchrone) de fi_eq_read. Il se comporte de manière similaire à l'appel non bloquant, à l'exception près que les appels ne retourneront pas tant qu'un événement n'aura pas été lu de l'EQ ou qu'une erreur ou un délai d'attente ne se sera pas produit. Spécifier un délai d'attente négatif signifie un délai d'attente infini.

Les threads bloquant dans cette fonction retourneront à l'appelant s'ils sont signalés par une source externe. Ceci est vrai même si le délai d'attente ne s'est pas produit ou était spécifié comme infini.

Il est invalide pour les applications d'appeler cette fonction si l'EQ a été configurée avec un objet de veille de FI_WAIT_NONE ou FI_WAIT_SET.

fi_eq_readerr

La fonction de lecture d'erreurs, fi_eq_readerr, récupère des informations concernant toute opération asynchrone qui s'est terminée avec une erreur inattendue. fi_eq_readerr est un appel non bloquant, retournant immédiatement, qu'une complétion d'erreur ait été trouvée ou non.

Les EQs sont optimisées pour signaler les opérations qui se sont terminées avec succès. Les opérations qui échouent sont rapportées "hors bande". Ces opérations sont récupérées à l'aide de la fonction fi_eq_readerr. Lorsqu'une opération qui se termine avec une erreur inattendue est insérée dans une EQ, elle est placée dans une file d'erreurs temporaire. Tenter de lire depuis une EQ pendant qu'un élément est dans la file d'erreurs entraîne un échec FI_EAVAIL. Les applications peuvent utiliser ce code de retour pour déterminer quand appeler fi_eq_readerr.

Les informations d'erreur sont rapportées à l'utilisateur via la struct fi_eq_err_entry. Le format de cette structure est défini ci-dessous.

struct fi_eq_err_entry {
    fid_t            fid;        /* fid associé à l'erreur */
    void            *context;    /* contexte de l'opération */
    uint64_t         data;       /* données spécifiques à l'achèvement */
    int              err;        /* code d'erreur positif */
    int              prov_errno; /* code d'erreur du fournisseur */
    void            *err_data;   /* données d'erreur supplémentaires */
    size_t           err_data_size; /* taille de err_data */
};

Le fid fera référence au descripteur de tissu associé à l'événement. Pour l'enregistrement de mémoire, ce sera le fid_mr, la résolution d'adresses fera référence à un fid_av, et les événements CM feront référence à un fid_ep. Le champ context sera défini sur le contexte spécifié dans le cadre de l'opération.

Le champ data sera défini comme décrit dans la page de manuel du type d'objet correspondant (par exemple, voir fi_av(3) pour une description de la manière dont les insertions de vecteur d'adresses asynchrones sont complétées).

La raison générale de l'erreur est fournie par le champ err. Des informations d'erreur spécifiques au fournisseur ou opérationnelles peuvent également être disponibles via les champs prov_errno et err_data. Les utilisateurs peuvent appeler fi_eq_strerror pour convertir les informations d'erreur spécifiques au fournisseur en une chaîne imprimable à des fins de débogage.

En entrée, err_data_size indique la taille du tampon err_data en octets. En sortie, err_data_size sera défini sur le nombre d'octets copiés dans le tampon err_data. Les informations err_data sont généralement utilisées avec fi_eq_strerror pour fournir des détails sur le type d'erreur qui s'est produit.

À des fins de compatibilité, si err_data_size est 0 en entrée, ou si le tissu a été ouvert avec une version < 1.5, err_data sera défini sur un tampon de données détenu par le fournisseur. Le contenu du tampon restera valide jusqu'à un appel de lecture ultérieur contre l'EQ. Les applications doivent sérialiser l'accès à l'EQ lors du traitement des erreurs pour garantir que le tampon référencé par err_data ne change pas.

CHAMP D'ÉVÉNEMENT

Les structures de données des entrées EQ partagent plusieurs des éléments communs

me champs. Leurs significations sont les mêmes ou similaires pour tous les formats de structure EQ, avec des détails spécifiques décrits ci-dessous.

fid
Cela correspond au descripteur de fabric associé à l'événement. Le type de fid dépend de l'événement signalé. Pour FI_CONNREQ, il s'agira du fid de l'extrémité passive. FI_CONNECTED et FI_SHUTDOWN feront référence à l'extrémité active. FI_MR_COMPLETE et FI_AV_COMPLETE feront référence respectivement aux descripteurs de fabric MR ou AV. FI_JOIN_COMPLETE pointera vers le descripteur de multicast renvoyé dans le cadre de l'opération de jointure. Les applications peuvent utiliser la valeur fid->context pour récupérer le contexte associé au descripteur de fabric.
context
La valeur de context est définie sur le paramètre context spécifié avec l'opération qui a généré l'événement. Si aucun paramètre context n'est associé à l'opération, ce champ sera NULL.
data
Data est une valeur ou un ensemble d'octets spécifique à l'opération. Pour les événements de connexion, data sont les données de l'application échangées dans le cadre du protocole de connexion.
err
Ce code err est un errno de fabric positif associé à un événement. La valeur err indique la raison générale d'une erreur, si une erreur s'est produite. Voir fi_errno.3 pour une liste des codes d'erreur possibles.
prov_errno
En cas d'erreur, prov_errno peut contenir un code d'erreur spécifique au fournisseur. L'utilisation de ce champ et sa signification sont spécifiques au fournisseur. Il est destiné à être utilisé comme aide au débogage. Voir fi_eq_strerror pour plus de détails sur la conversion de cette valeur d'erreur en une chaîne lisible par l'homme.
err_data
En cas d'erreur, err_data peut référencer une quantité de données spécifique au fournisseur associée à une erreur. L'utilisation de ce champ et sa signification sont spécifiques au fournisseur. Il est destiné à être utilisé comme aide au débogage. Voir fi_eq_strerror pour plus de détails sur la conversion de ces données d'erreur en une chaîne lisible par l'homme.
err_data_size
En entrée, err_data_size indique la taille du tampon err_data en octets. En sortie, err_data_size sera défini sur le nombre d'octets copiés dans le tampon err_data. Les informations err_data sont généralement utilisées avec fi_eq_strerror pour fournir des détails sur le type d'erreur survenue.

Par compatibilité, si err_data_size vaut 0 en entrée, ou si le fabric a été ouvert avec une version < 1.5, err_data sera défini sur un tampon de données appartenant au fournisseur. Le contenu du tampon restera valide jusqu'à un appel de lecture ultérieur sur l'EQ. Les applications doivent sérialiser l'accès à l'EQ lors du traitement des erreurs pour garantir que le tampon référencé par err_data ne change pas.

NOTES

Si une file d'événements a été débordée, elle sera placée dans un état « overrun ». Les opécions d'écriture sur une EQ débordée échoueront avec -FI_EOVERRUN. Les opérations de lecture continueront de renvoyer tous les événements valides et non corrompus, s'il y en a. Une fois tous les événements valides récupérés, toute tentative de lecture de l'EQ entraînera le renvoi d'un événement d'erreur FI_EOVERRUN. Les files d'événements débordées sont considérées comme fatales et ne peuvent pas être utilisées pour signaler des événements supplémentaires une fois le débordement survenu.

VALEURS DE RETOUR

fi_eq_open
Renvoie 0 en cas de succès. En cas d'erreur, une valeur négative correspondant à l'errno de fabric est renvoyée.
fi_eq_read / fi_eq_readerr
En cas de succès, renvoie le nombre d'octets lus depuis la file d'événements. En cas d'erreur, une valeur négative correspondant à l'errno de fabric est renvoyée. Si aucune donnée n'est disponible pour être lue depuis la file d'événements, -FI_EAGAIN est renvoyé.
fi_eq_sread
En cas de succès, renvoie le nombre d'octets lus depuis la file d'événements. En cas d'erreur, une valeur négative correspondant à l'errno de fabric est renvoyée. Si le délai d'attente expire ou si le thread appelant reçoit un signal et qu'aucune donnée n'est disponible pour être lue depuis la file d'événements, -FI_EAGAIN est renvoyé.
fi_eq_write
En cas de succès, renvoie le nombre d'octets écrits dans la file d'événements. En cas d'erreur, une valeur négative correspondant à l'errno de fabric est renvoyée.
fi_eq_strerror
Renvoie une chaîne de caractères interprétant l'erreur spécifique au fournisseur renvoyée avec une complétion.

Les valeurs d'errno de fabric sont définies dans rdma/fi_errno.h.
