NOM

fips_module - Guide du module FIPS d'OpenSSL

SYNOPSIS

Voir les pages de manuel individuelles pour plus de détails.

DESCRIPTION

Ce guide détaille différentes façons dont OpenSSL peut être utilisé en conjonction avec le module FIPS. L'approche correcte à utiliser dépendra de vos circonstances spécifiques et de ce que vous essayez d'atteindre.

Pour des informations relatives à l'installation du module FIPS, voir https://github.com/openssl/openssl/blob/master/README-FIPS.md.

Notez que les anciennes fonctions FIPS_mode() et FIPS_mode_set() ne sont plus présentes, vous devez donc les supprimer de votre application si vous les utilisez.

Les applications écrites pour utiliser le module FIPS d'OpenSSL 3.0 ne doivent utiliser aucune API ou fonctionnalité héritée qui contourne le module FIPS. Plus précisément, cela inclut :

  • Les API cryptographiques de bas niveau (utilisez plutôt les API de haut niveau, telles qu'EVP)
  • Les Engines
  • Toute fonction qui crée ou modifie des "METHODS" personnalisées (par exemple EVP_MD_meth_new(), EVP_CIPHER_meth_new(), EVP_PKEY_meth_new(), RSA_meth_new(), EC_KEY_METHOD_new(), etc.)

Toutes les API ci-dessus sont dépréciées dans OpenSSL 3.0 - une règle simple est donc d'éviter d'utiliser toutes les fonctions dépréciées. Voir ossl-guide-migration(7) pour une liste des fonctions dépréciées.

Faire utiliser le module FIPS par toutes les applications par défaut

Une approche simple est de faire en sorte que toutes les applications utilisant OpenSSL n'utilisent que le module FIPS pour les algorithmes cryptographiques par défaut.

Cette approche peut être réalisée purement par configuration. Tant que les applications sont compilées et liées contre OpenSSL 3.0 et ne remplacent pas le chargement du fichier de configuration par défaut ou ses paramètres, elles peuvent automatiquement commencer à utiliser le module FIPS sans nécessiter de modifications de code supplémentaires.

Pour ce faire, le fichier de configuration OpenSSL par défaut devra être modifié. L'emplacement de ce fichier de configuration dépendra de la plateforme et des options qui ont été données pendant le processus de compilation. Vous pouvez vérifier l'emplacement du fichier de configuration en exécutant cette commande :

$ openssl version -d
OPENSSLDIR: "/usr/local/ssl"

Attention : De nombreux systèmes d'exploitation installent OpenSSL par défaut. Il est courant de ne pas avoir la bonne version d'OpenSSL dans votre $PATH. Vérifiez que vous exécutez une version OpenSSL 3.0 comme ceci :

$ openssl version -v
OpenSSL 3.0.0-dev xx XXX xxxx (Library: OpenSSL 3.0.0-dev xx XXX xxxx)

La OPENSSLDIR valeur ci-dessus donne le nom du répertoire où le fichier de configuration par défaut est stocké. Dans ce cas, le fichier de configuration par défaut sera donc appelé /usr/local/ssl/openssl.cnf.

Modifiez le fichier de configuration pour ajouter les lignes suivantes près du début :

config_diagnostics = 1
openssl_conf = openssl_init
.include /usr/local/ssl/fipsmodule.cnf
[openssl_init]
providers = provider_sect
alg_section = algorithm_sect
[provider_sect]
fips = fips_sect
base = base_sect
[base_sect]
activate = 1
[algorithm_sect]
default_properties = fips=yes

Évidemment, l'emplacement du fichier include ci-dessus doit correspondre au chemin et au nom du fichier de configuration du module FIPS que vous avez installé précédemment. Voir https://github.com/openssl/openssl/blob/master/README-FIPS.md.

Pour une utilisation FIPS, il est recommandé que l'option config_diagnostics soit activée pour empêcher l'utilisation accidentelle d'algorithmes non validés FIPS via une configuration cassée ou erronée. Voir config(5).

Toutes les applications qui utilisent OpenSSL 3.0 et qui sont démarrées après ces changements utiliseront uniquement le module FIPS, sauf si ces applications prennent des mesures explicites pour éviter ce comportement par défaut. Notez que cette configuration active également le fournisseur "base". Le fournisseur base n'inclut aucun algorithme cryptographique (et n'affecte donc pas le statut de validation des opérations cryptographiques), mais inclut d'autres algorithmes de support qui peuvent être nécessaires. Il est conçu pour être utilisé en conjonction avec le module FIPS.

L'avantage principal de cette approche est qu'elle est simple et qu'aucune modification de code n'est requise dans les applications pour bénéficier du module FIPS. Il y a quelques inconvénients à cette approche :

  • Vous ne voudrez peut-être pas que toutes les applications utilisent le module FIPS.

    Il se peut que certaines applications devraient utiliser le module FIPS et que d'autres non.

  • Si les applications prennent des mesures explicites pour ne pas charger le fichier de configuration par défaut ou définir des paramètres différents.

    Cette méthode ne fonctionnera pas dans ces cas.

  • Les algorithmes disponibles dans le module FIPS sont un sous-ensemble des algorithmes disponibles dans le fournisseur OpenSSL par défaut.

    Si des applications tentent d'utiliser des algorithmes qui ne sont pas présents, elles échoueront.

  • L'utilisation de certaines API dépréciées évite l'utilisation du module FIPS.

    Si des applications utilisent ces API, le module FIPS ne sera pas utilisé.

Faire utiliser le module FIPS par des applications sélectionnées par défaut

Une variation de l'approche ci-dessus consiste à faire la même chose au niveau de chaque application individuelle. Le fichier de configuration OpenSSL par défaut dépend de la valeur compilée pour OPENSSLDIR comme décrit dans la section ci-dessus. Cependant, il est également possible de remplacer le fichier de configuration à utiliser via la variable d'environnement OPENSSL_CONF . Par exemple, ce qui suit, sur Unix, fera en sorte que l'application soit exécutée avec un emplacement de fichier de configuration non standard :

$ OPENSSL_CONF=/my/nondefault/openssl.cnf myapplication

En utilisant ce mécanisme, vous pouvez contrôler quel fichier de configuration est chargé (et donc si le module FIPS est chargé) application par application.

Cela élimine l'inconvénient listé ci-dessus selon lequel vous ne voudrez peut-être pas que toutes les applications utilisent le module FIPS. Tous les autres avantages et inconvénients s'appliquent toujours.

Chargement programmatique du module FIPS (contexte de bibliothèque par défaut)

Les applications peuvent choisir de charger le fournisseur FIPS explicitement plutôt que de s'appuyer sur la configuration pour le faire. Le fichier de configuration est toujours nécessaire pour stocker les données de configuration du module FIPS (telles que son statut de test d'intégrité et ses données d'intégrité). Mais dans ce cas, nous n'activons pas automatiquement le fournisseur FIPS via ce fichier de configuration.

Pour faire les choses de cette manière, configurez comme pour "Faire utiliser le module FIPS par toutes les applications par défaut" ci-dessus, mais modifiez le fichier fipsmodule.cnf pour supprimer ou mettre en commentaire la ligne qui dit "activate = 1" (notez que définir cette valeur à 0 n'est pas suffisant). Cela signifie que toutes les informations de configuration requises seront disponibles pour charger le module FIPS, mais qu'il ne sera pas automatiquement chargé au démarrage de l'application. Le fournisseur FIPS peut alors être chargé programmatiquement comme ceci :

#include <openssl/provider.h>
int main(void)
{
    OSSL_PROVIDER *fips;
    OSSL_PROVIDER *base;
    fips = OSSL_PROVIDER_load(NULL, "fips");
    if (fips == NULL) {
        printf("Failed to load FIPS provider\n");
        exit(EXIT_FAILURE);
    }
    base = OSSL_PROVIDER_load(NULL, "base");
    if (base == NULL) {
        OSSL_PROVIDER_unload(fips);
        printf("Failed to load base provider\n");
        exit(EXIT_FAILURE);
    }
    /* Rest of application */
    OSSL_PROVIDER_unload(base);
    OSSL_PROVIDER_unload(fips);
    exit(EXIT_SUCCESS);
}

Notez que cela devrait être l'une des premières choses que vous faites dans votre application. Si des fonctions OpenSSL sont appelées qui nécessitent l'utilisation de fonctions cryptographiques avant que cela ne se produise, alors, si aucun fournisseur n'a encore été chargé, le fournisseur par défaut sera automatiquement chargé. Si vous chargez ensuite explicitement le fournisseur FIPS, vous aurez à la fois le fournisseur FIPS et le fournisseur par défaut chargés en même temps. Il n'est pas spécifié quelle implémentation d'un algorithme sera utilisée si plusieurs implémentations sont disponibles et que vous n'avez pas explicitement spécifiée via une requête de propriété (voir ci-dessous) pour déterminer laquelle utiliser.

Notez également que dans cet exemple, nous avons chargé en plus le fournisseur « base ». Celui-ci charge un sous-ensemble d'algorithmes également disponibles dans le fournisseur par défaut - en particulier les algorithmes non cryptographiques qui peuvent être utilisés en conjonction avec le fournisseur FIPS. Par exemple, celui-ci contient des algorithmes pour l'encodage et le décodage des clés. Si vous décidez de ne pas charger le fournisseur par défaut, vous voudrez généralement charger le fournisseur base à la place.

Dans cet exemple, nous utilisons le contexte de bibliothèque « default ». Les fonctions OpenSSL opèrent dans la portée d'un contexte de bibliothèque. Si aucun contexte de bibliothèque n'est explicitement spécifié, le contexte de bibliothèque par défaut est utilisé. Pour plus de détails sur les contextes de bibliothèque, voir la OSSL_LIB_CTX(3) page de manuel.

Charger le module FIPS en même temps que d'autres fournisseurs

Il est possible d'avoir le fournisseur FIPS et d'autres fournisseurs (comme le fournisseur par défaut) tous chargés en même temps dans le même contexte de bibliothèque. Vous pouvez utiliser une chaîne de requête de propriété lors des récupérations d'algorithmes pour spécifier quelle implémentation vous souhaitez utiliser.

Par exemple, pour récupérer une implémentation de SHA256 conforme aux normes FIPS, vous pouvez spécifier la requête de propriété « fips=yes » comme ceci :

EVP_MD *sha256;
sha256 = EVP_MD_fetch(NULL, "SHA2-256", "fips=yes");

Si aucune requête de propriété n'est spécifiée, ou si plus d'une implémentation correspond à la requête de propriété, il n'est pas spécifié quelle implémentation d'un algorithme particulier sera retournée.

Cet exemple montre une demande explicite pour une implémentation de SHA256 du fournisseur par défaut :

EVP_MD *sha256;
sha256 = EVP_MD_fetch(NULL, "SHA2-256", "provider=default");

Il est également possible de définir une chaîne de requête de propriété par défaut. L' exemple suivant définit la requête de propriété par défaut de « fips=yes » pour toutes les récupérations dans le contexte de bibliothèque par défaut :

EVP_set_default_properties(NULL, "fips=yes");

Si une fonction de récupération a à la fois une requête de propriété explicite spécifiée et une requête de propriété par défaut définie, les deux requêtes sont fusionnées et s'appliquent toutes les deux. La requête de propriété locale remplace les propriétés par défaut si le même nom de propriété est spécifié dans les deux.

Il existe deux propriétés intégrées importantes que vous devez connaître :

La propriété « provider » vous permet de spécifier à partir de quel fournisseur vous voulez qu'une implémentation soit récupérée, par ex. « provider=default » ou « provider=fips ». Tous les algorithmes implémentés dans un fournisseur ont cette propriété définie.

Il existe aussi la propriété « fips » . Tous les algorithmes FIPS correspondent à la requête de propriété « fips=yes ». Il existe également quelques algorithmes non cryptographiques disponibles dans les fournisseurs par défaut et base qui ont aussi la propriété « fips=yes » définie pour eux. Ce sont les algorithmes d'encodage et de décodage qui peuvent (par exemple) être utilisés pour écrire une clé générée dans le fournisseur FIPS sur un fichier. Les algorithmes d'encodage et de décodage ne sont pas dans le module FIPS lui-même mais sont autorisés à être utilisés en conjonction avec les algorithmes FIPS.

Il est possible de spécifier des propriétés par défaut dans un fichier de configuration. Par exemple, le fichier de configuration suivant charge automatiquement les fournisseurs par défaut et FIPS et définit la valeur de propriété par défaut à « fips=yes ». Notez que ce fichier de configuration ne charge pas le fournisseur « base ». Tous les algorithmes de soutien qui sont dans « base » sont aussi dans « default », il est donc inutile dans ce cas :

config_diagnostics = 1
openssl_conf = openssl_init
.include /usr/local/ssl/fipsmodule.cnf
[openssl_init]
providers = provider_sect
alg_section = algorithm_sect
[provider_sect]
fips = fips_sect
default = default_sect
[default_sect]
activate = 1
[algorithm_sect]
default_properties = fips=yes

Charger le module FIPS par programmation (contexte de bibliothèque non par défaut)

En plus d'utiliser des propriétés pour séparer l'utilisation du module FIPS des autres utilisations, cela peut également être réalisé à l'aide de contextes de bibliothèque. Dans cet exemple, nous créons deux contextes de bibliothèque. Dans l'un, nous supposons l'existence d'un fichier de configuration appelé openssl-fips.cnf qui charge et configure automatiquement les fournisseurs FIPS et base. L'autre contexte de bibliothèque utilisera simplement le fournisseur par défaut.

OSSL_LIB_CTX *fips_libctx, *nonfips_libctx;
OSSL_PROVIDER *defctxnull = NULL;
EVP_MD *fipssha256 = NULL, *nonfipssha256 = NULL;
int ret = 1;
/*
 * Créer deux contextes de bibliothèque non par défaut. Un pour l'usage FIPS et
 * un pour l'usage non-FIPS
 */
fips_libctx = OSSL_LIB_CTX_new();
nonfips_libctx = OSSL_LIB_CTX_new();
if (fips_libctx == NULL || nonfips_libctx == NULL)
    goto err;
/* Empêcher quoi que ce soit d'utiliser le contexte de bibliothèque par défaut */
defctxnull = OSSL_PROVIDER_load(NULL, "null");
/*
 * Charger le fichier de configuration pour le contexte de bibliothèque FIPS. Nous supposons que
 * ce fichier de configuration activera automatiquement les fournisseurs FIPS et base
 * donc nous n'avons pas besoin de les charger explicitement ici.
 */
if (!OSSL_LIB_CTX_load_config(fips_libctx, "openssl-fips.cnf"))
    goto err;
/*
 * Définir la requête de propriété par défaut sur le contexte de bibliothèque FIPS pour
 * garantir que seuls les algorithmes FIPS peuvent être utilisés. Il y a quelques algorithmes non approuvés
 * FIPS dans le fournisseur FIPS pour des raisons de rétrocompatibilité.
 */
if (!EVP_set_default_properties(fips_libctx, "fips=yes"))
    goto err;
/*
 * Nous n'avons rien de spécial à faire pour charger le fournisseur
 * par défaut dans nonfips_libctx. Cela se produit automatiquement si aucun
 * autre fournisseur n'est chargé.
 * Parce que nous n'appelons pas OSSL_LIB_CTX_load_config() explicitement pour
 * nonfips_libctx, il utilisera simplement le fichier de configuration par défaut.
 */
/* À titre d'exemple, obtenir quelques fonctions de hachage */
/* Obtenir une fonction de hachage validée FIPS */
fipssha256 = EVP_MD_fetch(fips_libctx, "SHA2-256", NULL);
if (fipssha256 == NULL)
    goto err;
/* Obtenir une fonction de hachage non validée FIPS */
nonfipssha256 = EVP_MD_fetch(nonfips_libctx, "SHA2-256", NULL);
if (nonfipssha256 == NULL)
    goto err;
/* Utiliser les fonctions de hachage */
printf("Success\n");
ret = 0;
err:
EVP_MD_free(fipssha256);
EVP_MD_free(nonfipssha256);
OSSL_LIB_CTX_free(fips_libctx);
OSSL_LIB_CTX_free(nonfips_libctx);
OSSL_PROVIDER_unload(defctxnull);
return ret;

Notez que nous avons utilisé le fournisseur spécial « null » ici que nous chargeons dans le contexte de bibliothèque par défaut. Nous aurions pu choisir d'utiliser le contexte de bibliothèque par défaut pour l'usage FIPS et de simplement créer un contexte de bibliothèque supplémentaire pour les autres usages - ou l'inverse. Cependant, si le code n'a pas été converti pour utiliser des contextes de bibliothèque, le contexte de bibliothèque par défaut sera automatiquement utilisé. Cela pourrait être le cas pour vos propres applications existantes ainsi que pour certaines parties d'OpenSSL lui-même. Toutes les parties d'OpenSSL ne sont pas conscientes du contexte de bibliothèque. Si cela se produit, vous pourriez « accidentellement » utiliser le mauvais contexte de bibliothèque pour une opération particulière. Pour être sûr que cela n'arrive pas, vous pouvez charger le fournisseur « null » dans le contexte de bibliothèque par défaut. Parce qu'un fournisseur a été explicitement chargé, le fournisseur par défaut ne sera pas chargé automatiquement. Cela signifie que le code utilisant le contexte par défaut par accident échouera car aucun algorithme ne sera disponible.

Voir « Library Context » dans ossl-guide-migration(7) pour des informations supplémentaires sur le contexte de bibliothèque.

Utiliser les encodeurs et décodeurs avec le module FIPS

Les encodeurs et décodeurs sont utilisés pour lire et écrire des clés ou des paramètres depuis ou vers un format externe (par exemple un fichier PEM). Si votre application génère des clés ou des paramètres qui doivent ensuite être écrits en format PEM ou DER, il est probable que vous devrez utiliser un encodeur pour cela. De même, vous avez besoin d'un décodeur pour lire les clés et les paramètres précédemment enregistrés. Dans la plupart des cas, cela sera invisible pour vous si vous utilisez des API qui existaient dans OpenSSL 1.1.1 ou antérieur telles que i2d_PrivateKey(3). Cependant, l'encodeur/décodeur approprié devra être disponible dans le contexte de bibliothèque associé à l'objet clé ou paramètre. Les encodeurs et décodeurs OpenSSL intégrés sont implémentés à la fois dans les fournisseurs par défaut et base et ne sont pas dans la frontière du module FIPS. Cependant, comme ce ne sont pas des algorithmes cryptographiques en soi, il est toujours possible de les utiliser en conjonction avec le module FIPS, et par conséquent ces encodeurs/décodeurs ont la propriété « fips=yes » définie pour eux. Vous devez vous assurer que soit le fournisseur par défaut soit le fournisseur base est chargé dans le contexte de bibliothèque dans ce cas.

Utiliser le module FIPS dans SSL/TLS

Écrire une application qui utilise libssl en conjonction avec le module FIPS est très similaire à écrire une application libssl normale. Si vous utilisez des propriétés globales et le contexte de bibliothèque par défaut pour spécifier l'utilisation d'algorithmes validés FIPS, cela se produira automatiquement pour tous les algorithmes cryptographiques dans libssl. Si vous utilisez un contexte de bibliothèque non par défaut pour charger le fournisseur FIPS, vous pouvez le fournir à libssl en utilisant la fonction SSL_CTX_new_ex(3). Cela fonctionne comme un remplacement direct pour la fonction SSL_CTX_new(3) sauf qu'elle vous fournit la capacité de spécifier le contexte de bibliothèque à utiliser. Vous pouvez également utiliser la même fonction pour spécifier des propriétés spécifiques à libssl à utiliser.

Dans ce premier exemple, nous créons deux objets SSL_CTX en utilisant deux contextes de bibliothèque différents.

/*
 * Nous supposons qu'un contexte de bibliothèque non par défaut avec le fournisseur
 * FIPS chargé a été créé appelé fips_libctx.
 */
SSL_CTX *fips_ssl_ctx = SSL_CTX_new_ex(fips_libctx, "fips=yes", TLS_method());
/*
 * Nous supposons qu'un contexte de bibliothèque non par défaut avec le fournisseur
 * par défaut chargé a été créé appelé non_fips_libctx.
 */
SSL_CTX *non_fips_ssl_ctx = SSL_CTX_new_ex(non_fips_libctx, NULL,
                                           TLS_method());

Dans ce deuxième exemple, nous créons deux objets SSL_CTX en utilisant des propriétés différentes pour spécifier l'utilisation FIPS :

/*
 * La propriété « fips=yes » inclut tous les algorithmes approuvés FIPS
 * ainsi que les encodeurs du fournisseur par défaut qui sont autorisés
 * à être utilisés. Le NULL ci-dessous indiquees que nous utilisons le
 * contexte de bibliothèque par défaut.
 */
SSL_CTX *fips_ssl_ctx = SSL_CTX_new_ex(NULL, "fips=yes", TLS_method());
/*
 * La propriété "provider!=fips" permet les algorithmes de tous les
 * fournisseurs sauf le fournisseur FIPS
 */
SSL_CTX *non_fips_ssl_ctx = SSL_CTX_new_ex(NULL, "provider!=fips",
                                           TLS_method());

Confirmer qu'un algorithme est fourni par le module FIPS

Une chaîne de liens doit être suivie pour passer d'une instance d'algorithme au fournisseur qui l'implémente. Le processus est similaire pour tous les algorithmes. L'exemple d'une fonction de hachage est utilisé ici.

Pour passer d'un EVP_MD_CTX à un EVP_MD, utilisez EVP_MD_CTX_md(3) . Pour passer du EVP_MD à son OSSL_PROVIDER, utilisez EVP_MD_get0_provider(3). Pour extraire le nom du OSSL_PROVIDER, utilisez OSSL_PROVIDER_get0_name(3).

Indicateurs FIPS

Des indicateurs FIPS ont été ajoutés au fournisseur FIPS dans OpenSSL 3.4. FIPS 140-3 exige l'utilisation d'indicateurs si le fournisseur FIPS autorise des algorithmes non approuvés. Un algorithme est approuvé s'il passe toutes les vérifications requises telles que la taille minimale de la clé. Par défaut, une erreur se produira si une vérification échoue. Pour des raisons de compatibilité ascendante, certains algorithmes individuels peuvent contourner les vérifications en utilisant soit une option dans la configuration FIPS (voir « FIPS indicator options » dans fips_config(5)) SOIT dans le code en utilisant un « context setter » d'algorithme. Contourner la vérification signifie que l'algorithme n'est pas conforme FIPS. OSSL_INDICATOR_set_callback(3) peut être appelé pour enregistrer un rappel pour journaliser les algorithmes non approuvés. À la fin de toute opération d'algorithme, le statut approuvé peut être interrogé en utilisant un « context getter » d'algorithme pour récupérer l'indicateur (par exemple « fips-indicator »). Un exemple de « context setter » d'algorithme est « key-check » dans « Supported parameters » dans EVP_KDF-HKDF(7).

Les algorithmes suivants utilisent « fips-indicator » pour interroger si l'algorithme est approuvé :

Génération de clés DSA
La génération de clés DSA n'est plus approuvée. Voir « DSA parameters » dans EVP_PKEY-DSA(7)
Signatures DSA
La génération de signatures DSA n'est plus approuvée. Voir « Signature Parameters » dans EVP_SIGNATURE-DSA(7)
Signatures ECDSA
Voir « ECDSA Signature Parameters » dans EVP_SIGNATURE-ECDSA(7)
Génération de clés EC
Voir « Common EC parameters » dans EVP_PKEY-EC(7)
Chiffrement RSA
Le remplissage « pkcs1 » n'est plus approuvé.

Voir « RSA Asymmetric Cipher parameters » dans EVP_ASYM_CIPHER-RSA(7) et « RSA KEM parameters » dans EVP_KEM-RSA(7)

Signatures RSA
Voir « Signature Parameters » dans EVP_SIGNATURE-RSA(7)
DRBG
Voir « Supported parameters » dans EVP_RAND-HASH-DRBG(7) et EVP_RAND-HMAC-DRBG(7)/Supported parameters>
DES
Le Triple-DES n'est plus approuvé pour le chiffrement. Voir « Parameters » dans EVP_CIPHER-DES(7)
DH
Voir « DH and DHX key exchange parameters » dans EVP_KEYEXCH-DH(7)
ECDH
Voir « ECDH Key Exchange parameters » dans EVP_KEYEXCH-ECDH(7)
KDF
Voir la documentation pertinente sur les KDF, par exemple « Supported parameters » dans EVP_KDF-HKDF(7)
CMAC et KMAC
Voir « Supported parameters » dans EVP_MAC-CMAC(7) et « Supported parameters » dans EVP_MAC-KMAC(7)

Les algorithmes FIPS suivants ne sont pas approuvés et utilisent le « fips-indicator ».

RAND-TEST-RAND
Voir « Supported parameters » dans EVP_RAND-TEST-RAND(7) Le rappel d'indicateur n'est PAS déclenché pour cet algorithme car il est utilisé en interne à des fins non sécuritaires.
Génération de clés et échange de clés X25519 et X448

Les algorithmes non approuvés (non validés FIPS) ont une valeur de requête de propriété de « fips=no ».

Les algorithmes suivants utilisent un indicateur unique et ne déclenchent pas le rappel d'indicateur.

Les chiffrements AES-GCM prennent en charge l'indicateur « iv-generated »
Voir « PARAMETERS » dans EVP_EncryptInit(3) pour plus d'informations.
Les signatures ECDSA et RSA prennent en charge l'indicateur « verify-message ».
Voir « ECDSA Signature Parameters » dans EVP_SIGNATURE-ECDSA(7) et « Signature Parameters » dans EVP_SIGNATURE-RSA(7) /pour plus d'informations.

NOTES

Certaines versions publiées d'OpenSSL ne contiennent pas de fournisseur FIPS validé. Pour déterminer quelles versions ont subi le processus de validation, veuillez consulter la page de téléchargements d'OpenSSL https://www.openssl.org/source/. Si vous avez besoin de fonctionnalités approuvées FIPS, il est essentiel de construire votre fournisseur FIPS à l'aide de l'une des versions validées listées là-bas. Normalement, il est possible d'utiliser un fournisseur FIPS construit à partir de l'une des versions validées aux côtés de libcrypto et libssl compilés à partir de n'importe quelle version au sein de la même série de version majeure. Cette flexibilité vous permet de traiter les correctifs de bogues et les CVE qui se situent en dehors de la limite FIPS.

Comme le fournisseur FIPS prend toujours en charge les algorithmes non validés FIPS, la requête de propriété "fips=yes" est obligatoire pour les applications qui souhaitent fonctionner de manière approuvée FIPS.
