DESCRIPTIO

N

fio est un outil qui créera un certain nombre de threads ou de processus effectuant un type particulier d'action d'E/S tel que spécifié par l'

utilisateur. L'utilisation typique de fio consiste à écrire un fichier
de tâches correspondant à la charge d'E/S que l'on souhaite simuler.

FORMAT DES FICHIERS DE

TÂCHE

Tout paramètre situé après les options sera considéré comme un fichier de tâche, sauf s'il correspond à un paramètre de fichier de tâche. Plusieurs fichiers de tâche peuvent être listés et chaque fichier de tâche sera considéré comme un groupe séparé. Fio bloquera l'exécution entre chaque

groupe.

Fio accepte un ou plusieurs fichiers de tâche décrivant ce qu'il doit faire. Le format du fichier de tâche est celui du fichier ini classique, où les noms entourés de crochets [] définissent le nom de la tâche. Vous êtes libre d'utiliser le nom ASCII de votre choix, sauf *global* qui a une signification particulière. Après le nom de la tâche suit une séquence de zéro ou plusieurs paramètres, un par ligne, qui définissent le comportement de la tâche. Si le premier caractère d'une ligne est ';' ou '#', la ligne entière est ignorée en tant que

commentaire.

Une section *global* définit les valeurs par défaut pour les tâches décrites dans ce fichier. Une tâche peut remplacer un paramètre de section *global*, et un fichier de tâche peut même avoir plusieurs sections *global* si vous le souhaitez. Une tâche n'est affectée que par une section *global* située au-dessus

d'elle.

L'option --cmdhelp liste également toutes les options. Utilisée avec un argument de commande, --cmdhelp détaillera la commande do

nnée.

Consultez le répertoire `examples/' pour trouver de l'inspiration sur la manière d'écrire des fichiers de tâche. Notez que les exigences de copyright et de licence s'appliquent actuellement aux fichiers

`examples/'.

Notez que la longueur maximale

d'une ligne dans un fichier de
tâche est de 8192 octets.

Cible fichier/périphérique

directory=str
Préfaxe les filenames avec ce répertoire. Utilisé pour placer les fichiers dans un emplacement différent de `./'. Vous pouvez spécifier un certain nombre de répertoires en séparant les noms par un caractère ':'. Ces répertoires seront assignés et distribués également aux clones de tâches créés par numjobs tant qu'ils utilisent des noms de fichiers générés. Si des filenames spécifiques sont définis, fio utilisera le premier répertoire listé, et donc en faisant correspondre la sémantique de filename (qui génère un fichier pour chaque clone s'il n'est pas spécifié, mais laisse tous les clones utiliser le même fichier s'il est défini).

Voir l'option filename pour des informations sur la façon d'échapper les caractères ':' dans le chemin du répertoire lui-même.

Note : Pour contrôler le répertoire que fio utilisera pour les fichiers d'état internes, utilisez --aux-path.

filename=str
Fio crée normalement un nom de fichier basé sur le nom de la tâche, le numéro de thread et le numéro de fichier (voir filename_format). Si vous voulez partager des fichiers entre les threads d'une tâche ou plusieurs tâches avec des chemins de fichiers fixes, spécifiez un filename pour chacun d'eux pour remplacer la valeur par défaut. Si l'ioengine est basé sur fichier, vous pouvez spécifier un nombre de fichiers en séparant les noms par un ':' deux-points. Donc si vous vouliez qu'une tâche ouvre `/dev/sda' et `/dev/sdb' comme deux fichiers de travail, vous utiliseriez `filename=/dev/sda:/dev/sdb'. Cela signifie également que chaque fois que cette option est spécifiée, nrfiles est ignoré. La taille des fichiers réguliers spécifiés par cette option sera size divisé par le nombre de fichiers à moins qu'une taille explicite ne soit spécifiée par filesize.

Chaque deux-points dans le chemin souhaité doit être échappé avec un caractère '\'. Par exemple, si le chemin est `/dev/dsk/foo@3,0:c' alors vous utiliserez `filename=/dev/dsk/foo@3,0\:c' et si le chemin est `F:\filename' alors vous utiliserez `filename=F\:\filename'.

Sous Windows, les périphériques disque sont accessibles sous la forme `\\.\PhysicalDrive0' pour le premier périphérique, `\\.\PhysicalDrive1' pour le second, etc. Note : Windows et FreeBSD empêchent l'accès en écriture aux zones du disque contenant des données en cours d'utilisation (par exemple, des systèmes de fichiers).

Pour l'accès HTTP et S3, spécifiez un chemin d'URL valide ou une clé S3, respectivement. Un nom de fichier pour S3 de style chemin inclut un nom de bucket (`/bucket/k/e.y') tandis qu'un nom de fichier S3 de style hérité virtuel (`/k/e.y') n'en inclut pas car son nom de bucket est spécifié dans http_host.

Le nom de fichier `-' est un nom réservé, signifiant *stdin* ou *stdout*. Lequel des deux dépend de la direction de lecture/écriture définie.

filename_format=str
Si plusieurs fichiers sont partagés entre des tâches, il est généralement nécessaire que fio génère les noms exacts que vous souhaitez. Par défaut, fio nommera un fichier en se basant sur la spécification de format de fichier par défaut de `jobname.jobnumber.filenumber'. Avec cette option, cela peut être personnalisé. Fio reconnaîtra et remplacera les mots-clés suivants dans cette chaîne :
$jobname
Le nom du thread ou du processus travailleur.
$clientuid
L'adresse IP du processus fio lors de l'utilisation du mode client/serveur.
$jobnum
Le numéro incrémental du thread ou du processus travailleur.
$filenum
Le numéro incrémental du fichier pour ce thread ou processus travailleur.

Pour que les tâches dépendantes partagent un ensemble de fichiers, cette option peut être définie pour que fio génère des noms de fichiers partagés entre les deux. Par exemple, si `testfiles.$filenum' est spécifié, le fichier numéro 4 pour n'importe quelle tâche sera nommé `testfiles.4'. La valeur par défaut de `$jobname.$jobnum.$filenum' sera utilisée si aucun autre spécificateur de format n'est donné.

Si vous spécifiez un chemin, les répertoires seront créés jusqu'au répertoire principal du fichier. Donc, par exemple, si vous spécifiez `a/b/c/$jobnum`, alors les répertoires a/b/c seront créés avant la partie de configuration du fichier de la tâche. Si vous spécifiez directory, alors le chemin sera relatif à ce répertoire, sinon il sera traité comme le chemin absolu.

Ce paramètre s'applique uniquement à zonemode=zbd.

Les périphériques blocs zonés sont des périphériques blocs composés de plusieurs zones. Chaque zone a un type, par exemple conventionnel ou séquentiel. Une zone conventionnelle peut être écrite à n'importe quel décalage qui est un multiple de la taille du bloc. Les zones séquentielles doivent être écrites séquentiellement. La position à laquelle une écriture doit se produire est appelée pointeur d'écriture. Un périphérique bloc zoné peut être géré par l'hôte (host managed) ou connu de l'hôte (host aware). Pour les périphériques gérés par l'hôte, l'hôte doit s'assurer que les écritures se font séquentiellement. Fio reconnaît les périphériques gérés par l'hôte et sérialise les écritures dans les zones séquentielles pour ces périphériques.

Si une lecture se produit dans une zone séquentielle au-delà du pointeur d'écriture, le périphérique bloc zoné complétera la lecture sans lire de données du support de stockage. Comme ces lectures entraînent des chiffres de bande passante et d'IOPS irréalistes, fio ne lit au-delà du pointeur d'écriture que si on le lui dit explicitement. Défaut : faux.

Les périphériques blocs zonés peuvent avoir une limite appelée 'max_open_zones' (même nom que le paramètre) sur le nombre total de zones qui peuvent être simultanément dans les conditions 'implicitement ouverte' ou 'explicitement ouverte'. (io_uring,libaio)cmdprio_percentage=entier[,entier]
Définit le pourcentage d'E/S qui seront émises avec la priorité la plus élevée. Défaut : 0. Une seule valeur s'applique aux lectures et aux écritures. Des valeurs séparées par des virgules peuvent être spécifiées pour les lectures et les écritures. Pour que cette option soit efficace, la priorité NCQ doit être prise en charge et activée, et l'option direct=1 doit être utilisée. Fio doit également être exécuté en tant qu'utilisateur root. Contrairement aux statistiques slat/clat/lat, qui peuvent être suivies et rapportées indépendamment, les statistiques par priorité ne suivent et ne rapportent qu'un seul type de latence. Par défaut, la latence de complétion (clat) sera rapportée ; si lat_percentiles est défini, la latence totale (lat) sera rapportée.

Si non spécifié lorsque cmdprio_percentage ou cmdprio_bssplit est défini, la valeur par défaut est la classe de priorité la plus élevée. Une seule valeur s'applique aux lectures et aux écritures. Des valeurs séparées par des virgules peuvent être spécifiées pour les lectures et les écritures. Voir le manuel ionice(1). Voir également l'option prioclass.

Définit l'indice de priorité d'E/S à utiliser pour les E/S qui doivent être émises avec une priorité lorsque cmdprio_percentage ou cmdprio_bssplit est défini. Des valeurs séparées par des virgules peuvent être spécifiées pour les lectures et les écritures. Voir également l'option priohint.

Si non spécifié lorsque cmdprio_percentage ou cmdprio_bssplit est défini, la valeur par défaut est 0. Linux nous limite à une valeur positive comprise entre 0 et 7, 0 étant la plus élevée. Référez-vous à la page de manuel appropriée pour les autres systèmes d'exploitation, car la signification de la priorité peut différer. Voir également l'option prio.

io_submit_mode=s
tr
Cette option contrôle la manière dont fio soumet les E/S au moteur d'E/S. La valeur par défaut est `inline', ce qui signifie que les fils de travail fio soumettent et récoltent les E/S directement. Si elle est définie à `offload', les fils de travail délégueront la soumission d'E/S à un pool dédié de fils d'E/S. Cela nécessite une certaine coordination et a donc un peu de surcoût supplémentaire, surtout pour les E/S à faible profondeur de file où cela peut augmenter les latences. L'avantage est que fio peut gérer les taux de soumission indépendamment des taux de complétion du périphérique. Cela évite un rapport de latence déséquilibré si les E/S s'accumulent sure appareil côté (problème d'omission coordonnée). Notez que cette option ne peut pas être utilisée de manière fiable avec les moteurs d'E/S asynchrones.

Gestion des erreurs

exitall_on_error
Lorsqu'un travail se termine avec une erreur, terminez les autres. Par défaut, on attend que chaque travail se termine.
continue_on_error=str
Normalement, fio terminera le travail à la première défaillance observée. Si cette option est définie, fio continuera le travail en cas d' 'erreur non fatale' (EIO ou EILSEQ) jusqu'à ce que le temps d'exécution soit dépassé ou que la taille d'E/S spécifiée soit atteinte. Si cette option est utilisée, deux statistiques supplémentaires sont ajoutées : le nombre total d'erreurs et la première erreur. Le champ d'erreur donné dans les statistiques est la première erreur rencontrée pendant l'exécution.

Note : une erreur d'écriture du périphérique peut passer inaperçue par fio lors de l'utilisation d'E/S mises en mémoire tampon, car l'appel système write() (ou similaire) ne fait que marquer les pages du noyau, sauf si `sync` ou `direct` est utilisé. Les erreurs d'E/S du périphérique se produisent lorsque les données marquées sont effectivement écrites sur le disque. Si des écritures entièrement synchrones ne sont pas souhaitables, `fsync` ou `fdatasync` peuvent également être utilisés. Ceci est spécifique aux écritures, car les lectures sont toujours synchrones.

Les valeurs autorisées sont :

none
Sortir en cas d'erreurs d'E/S ou de vérification.
read
Continuer en cas d'erreurs de lecture, sortir pour toutes les autres.
write
Continuer en cas d'erreurs d'écriture, sortir pour toutes les autres.
io
Continuer en cas d'erreur d'E/S, sortir pour toutes les autres.
verify
Continuer en cas d'erreurs de vérification, sortir pour toutes les autres.
all
Continuer en cas de toutes les erreurs.
0
Alias rétrocompatible pour 'none'.
1
Alias rétrocompatible pour 'all'.
ignore_error=str
Parfois, vous souhaitez ignorer certaines erreurs pendant le test, auquel cas vous pouvez spécifier une liste d'erreurs pour chaque type d'erreur, au lieu de simplement pouvoir ignorer l'erreur 'non fatale' par défaut en utilisant continue_on_error. `ignore_error=READ_ERR_LIST,WRITE_ERR_LIST,VERIFY_ERR_LIST` les erreurs pour le type d'erreur donné sont séparées par ':'. L'erreur peut être un symbole ('ENOSPC', 'ENOMEM') ou un entier. Exemple :

ignore_error=EAGAIN,ENOSPC:122

Cette option ignorera EAGAIN de READ, et ENOSPC et 122(EDQUOT) de WRITE. Cette option fonctionne en remplaçant continue_on_error par la liste des erreurs pour chaque type d'erreur s'il y en a.

Si défini, enregistre toutes les erreurs même si elles ne sont pas fatales, par défaut `true`. Si désactivé, seule l'erreur fatale sera enregistrée.

SORTIE JSON+

Le format de sortie json+ est identique au format de sortie json, à l'exception qu'il ajoute un vidage complet des classes de latence de complétion. Chaque objet bins contient un ensemble de paires (clé, valeur) où les clés sont des durées de latence et les valeurs comptent le nombre d'E/S ayant des latences de complétion correspondant à la durée donnée. Par exemple, considérez :

La colocalisation est une pratique courante utilisée pour tirer le meilleur parti d'une machine. Savoir quelles charges de travail s'entendent bien les unes avec les autres et lesquelles ne le font pas est une tâche bien plus difficile. Bien que fio puisse rejouer des charges de travail de manière concurrente via plusieurs tâches, il laisse une certaine variabilité à l'ordonnanceur, ce qui rend les résultats plus difficiles à reproduire. La fusion est un moyen de rendre l'ordre des événements

cohérent.

La fusion est intégrée au rejeu d'E/S et est effectuée lorsqu'un merge_blktrace_file est spécifié. La liste de fichiers passée à read_iolog passe par le processus de fusion et produit un seul fichier stocké dans le fichier spécifié. CPU PROFILAGE DE

L'INactivité

Dans certains cas, nous voulons comprendre la surcharge CPU dans un test. Par exemple, nous testons des correctifs pour leur mérite spécifique de savoir s'ils réduisent l'utilisation du CPU. Fio implémente une approche par ballon pour créer un thread par CPU qui s'exécute à la priorité d'inactivité, ce qui signifie qu'il ne s'exécute que lorsque personne d'autre n'a besoin du cpu. En mesurant la quantité de travail effectuée par le thread, l'inactivité de chaque CPU peut en être déduite en

conséquence.

Une unité de travail est définie comme le toucher d'une page complète de caractères non signés. La moyenne et l'écart type

du temps pour compléter une unité de travail sont rapportés dans la section "unit work". Des options peuvent être choisi
es pour rapporter l'inactivité détaillée par CPU ou l'inactivité globale du système en agrégeant les statistiques par CPU.

VÉRIFICATION ET

DÉCLENCHEURS

Fio est généralement exécuté de l'une de deux manières, lorsque la vérification des données est effectuée. La première est un travail d'écriture normal d'un certain type avec la vérification activée. Lorsque la phase d'écriture est terminée, fio passe aux lectures et vérifie tout ce qu'il a écrit. Le deuxième modèle consiste à exécuter uniquement la phase d'écriture, puis plus tard à exécuter le même travail (mais avec des lectures au lieu d'écritures) pour répéter les mêmes motifs d'E/S et vérifier le contenu. Ces deux méthodes dépendent de la fin de la phase d'écriture, car fio n'a sinon aucune idée de la quantité de données qui a été

écrite.

Avec les déclencheurs de vérification, fio prend en charge le vidage de l'état d'écriture actuel vers des fichiers locaux. Ensuite, une charge de travail de vérification de lecture ultérieure peut charger cet état et savoir exactement où s'arrêter. C'est utile pour tester des cas où l'alimentation est coupée à un serveur de manière contrôlée, par

exemple.

Un déclencheur de vérification se compose de deux éléments

:

1) Stocker l'état d'écriture de chaque

travail.

2) Exécuter un

déclenchement.

L'état d'écriture est relativement petit, de l'ordre de centaines d'octets à quelques kilo-octets. Il contient des informations sur le nombre de complétions effectuées, les dernières X complétions,

etc.

Un déclencheur est invoqué soit par la création ('touch') d'un fichier spécifié dans le système, soit par un paramètre de délai d'attente. Si fio est exécuté avec `--trigger-file=/tmp/trigger-file', alors il vérifiera continuellement l' existence de `/tmp/trigger-file'. Lorsqu'il voit ce fichier, il déclenchera le déclencheur (sauvegardant ainsi l'état et exécutant la commande de déclenchement)

.

Pour les exécutions client/serveur, il y a à la fois un déclencheur local et un déclencheur distant. Si fio s'exécute comme backend serveur, il enverra les états des tâches au client pour un stockage sûr, puis exécutera le déclencheur distant, s'il est spécifié. Si un déclencheur local est spécifié, le serveur enverra toujours l'état d'écriture en retour, mais le client exécutera alors le

déclencheur.
