N

Les files d'événements sont utilisées pour signaler des événements associés à des opérations de contrôle. Elles sont associées à l'enregistrement mémoire, aux vecteurs d'adresse, à la gestion des connexions, ainsi qu'aux événements de niveau tissu et domaine. Les événements signalés sont soit associés à une opération demandée, soit affiliés à un appel qui s'inscrit pour des types d'événements spécifiques, comme l'écoute des demandes de

connexion.

fi_contro

l

L'appel fi_control est utilisé pour accéder aux détails spécifiques au fournisseur ou à l'implémentation de la file d'événements. L'accès à la file d'événements doit être sérialisé à travers tous les appels lorsque fi_controls invoqué, car il peut rediriger l'implémentation des opérations EQ. Les commandes de contrôle suivantes sont utilisables avec une EQ.

FI_GETWAIT (void **)
Cette commande permet à l'utilisateur de récupérer l'objet d'attente de bas niveau associé à l'EQ. Le format de l'objet d'attente est spécifié lors de la création de l'EQ, via les attributs de l'EQ. Le paramètre fi_control doit être une adresse où un pointeur vers l'objet d'attente renvoyé sera écrit. Il doit s'agir d'un ’int *’ pour FI_WAIT_FD, ou de `struct fi_mutex_cond' pour FI_WAIT_MUTEX_COND (obsolète).
struct fi_mutex_cond {
    pthread_mutex_t     *mutex;
    pthread_cond_t      *cond;
};

fi_eq_read

L'opération fi_eq_read effectue une lecture non bloquante des données d'événements depuis l'EQ. Le format des données d'événements est basé sur le type d'événement récupéré de l'EQ, tous les événements commençant par un en-tête struct fi_eq_entry. Au plus un événement sera renvoyé par opération de lecture d'EQ. Le nombre d'octets lus avec succès depuis l'EQ est renvoyé par la lecture. Le drapeau FI_PEEK peut être utilisé pour indiquer que les données d'événements doivent être lues de l'EQ sans être consommées. Une lecture ultérieure sans le drapeau FI_PEEK supprimerait alors l'événement de l'EQ.

Les types d'événements suivants peuvent être rapportés à une EQ, ainsi que des informations concernant le format associé à chaque événement.

Opérations de contrôle asynchrones
Les opérations de contrôle asynchrones sont des requêtes de base qui nécessitent simplement de générer un événement pour indiquer qu'elles sont terminées. Celles-ci incluent les types d'événements suivants : enregistrement de mémoire, résolution de vecteur d'adresse, et jointures multicast.

Les requêtes de contrôle signalent leur achèvement en insérant une struct fi_eq_entry dans l'EQ. Le format de cette structure est :

struct fi_eq_entry {
    fid_t            fid;        /* fid associé à la requête */
    void            *context;    /* contexte de l'opération */
    uint64_t         data;       /* données spécifiques à l'achèvement */
};

Pour l'achèvement des opérations de contrôle asynchrones de base, l'événement renvoyé indiquera l'opération qui est terminée, et le fid référencera le descripteur de tissu associé à l'événement. Pour l'enregistrement de mémoire, il s'agira d'un événement FI_MR_COMPLETE et du fid_mr. La résolution d'adresse référencera un événement FI_AV_COMPLETE et le fid_av. Les jointures multicast rapporteront un FI_JOIN_COMPLETE et le fid_mc. Le champ context sera défini sur le contexte spécifié dans le cadre de l'opération, sinon le contexte sera associé au descripteur de tissu. Le champ data sera défini comme décrit dans la page de manuel du type d'objet correspondant (par exemple, voir fi_av(3) pour une description de la manière dont les insertions de vecteurs d'adresses asynchrones sont terminées).

Notification de connexion
Les notifications de connexion sont des notifications de gestion de connexion utilisées pour établir ou rompre des connexions entre des points d'extrémité. Il existe trois événements de notification de connexion : FI_CONNREQ, FI_CONNECTED et FI_SHUTDOWN. Les notifications de connexion sont rapportées en utilisant struct fi_eq_cm_entry :
struct fi_eq_cm_entry {
    fid_t            fid;        /* fid associé à la requête */
    struct fi_info  *info;       /* informations du point d'extrémité */
    uint8_t         data[];     /* données de connexion applicatives */
};

Un événement de demande de connexion (FI_CONNREQ) indique qu'un point d'extrémité distant souhaite établir une nouvelle connexion à un point d'extrémité écoutant, ou passif. Le fid est le point d'extrémité passif. Les informations concernant les capacités et attributs du point d'extrémité actif demandé sont disponibles dans le champ info. L'application est responsable de libérer cette structure en appelant fi_freeinfo lorsqu'elle n'est plus nécessaire. Le champ connreq de fi_info référencera la demande de connexion associée à cet événement. Pour accepter une connexion, un point d'extrémité doit d'abord être créé en passant une structure fi_info référençant ce champ connreq à fi_endpoint(). Ce point d'extrémité est ensuite passé à fi_accept() pour compléter l'acceptation de la tentative de connexion. La création du point d'extrémité est plus facilement réalisée en passant le fi_info renvoyé dans le cadre de l'événement CM à fi_endpoint(). Si la connexion doit être rejetée, le connreq est passé à fi_reject().

Toutes les données applicatives échangées dans le cadre de la demande de connexion sont placées au-delà de la structure fi_eq_cm_entry. La quantité de données disponibles dépend de l'application et est limitée à l'espace tampon fourni par l'application lors de l'appel à fi_eq_read. La quantité de données renvoyées peut être calculée à l'aide de la valeur de retour de fi_eq_read. Notez que la quantité de données renvoyées est limitée par le protocole de connexion sous-jacent, et la longueur des données renvoyées peut inclure un remplissage de protocole. Par conséquent, la longueur renvoyée peut être supérieure à celle spécifiée par le pair connectant.

Si une demande de connexion a été acceptée, un événement FI_CONNECTED sera généré des deux côtés de la connexion. Le côté actif – celui qui a appelé fi_connect() – peut recevoir des données utilisateur dans le cadre de l'événement FI_CONNECTED. Les données utilisateur sont transmises au gestionnaire de connexion du côté passif via l'appel fi_accept. Les données utilisateur ne sont pas fournies avec un événement FI_CONNECTED du côté d'écoute de la connexion.

La notification qu'un pair distant s'est déconnecté d'un point d'extrémité actif se fait via l'événement FI_SHUTDOWN. La notification de fermeture utilise struct fi_eq_cm_entry tel que déclaré ci-dessus. Le champ fid pour une notification de fermeture fait référence au fid_ep du point d'extrémité actif.

Notification d'erreur asynchrone
Les erreurs asynchrones sont utilisées pour signaler des problèmes avec les ressources du tissu. Les erreurs signalées peuvent être fatales ou transitoires, en fonction de l'erreur, et entraînent la désactivation de la ressource. Les ressources désactivées feront échouer les opérations soumises à leur encontre jusqu'à ce qu'elles soient explicitement réactivées par l'application.

Des erreurs asynchrones peuvent être signalées pour les files d'attente d'achèvement et les points d'extrémité de tous types. Les erreurs de CQ peuvent survenir lorsque la gestion des ressources a été désactivée et que le fournisseur a détecté un dépassement de file d'attente. Les erreurs de point d'extrémité peuvent résulter de nombreuses actions, mais sont souvent associées à une opération ayant échoué. Les opérations peuvent échouer en raison de dépassements de tampon, d'autorisations invalides, de clés d'accès mémoire incorrectes, d'échecs de routage réseau, de problèmes d'atteignabilité réseau, etc.

Les erreurs asynchrones sont rapportées en utilisant struct fi_eq_err_entry, tel que défini ci-dessous. Le descripteur de tissu (fid) associé à l'erreur est fourni dans le cadre des données d'erreur. Un code d'erreur est également disponible pour déterminer la cause de l'erreur.

fi_eq_sread

L'appel fi_eq_sread est l'équivalent bloquant (ou synchrone) de fi_eq_read. Il se comporte de manière similaire à l'appel non bloquant, à l'exception que les appels ne retourneront pas tant qu'un événement n'aura pas été lu de l'EQ ou qu'une erreur ou un délai d'attente ne se sera produit. Spécifier un délai d'attente négatif signifie un délai d'attente infini.

Les threads bloqués dans cette fonction retourneront à l'appelant s'ils sont signalés par une source externe. Ceci est vrai même si le délai d'attente n'a pas expiré ou était spécifié comme infini.

Il est invalide pour les applications d'appeler cette fonction si l'EQ a été configurée avec un objet d'attente de FI_WAIT_NONE ou FI_WAIT_SET.

fi_eq_readerr

La fonction de lecture d'erreur, fi_eq_readerr, récupère des informations concernant toute opération asynchrone qui s'est terminée avec une erreur inattendue. fi_eq_readerr est un appel non bloquant, retournant immédiatement si une complétion d'erreur a été trouvée ou non.

Les EQ sont optimisées pour signaler les opérations qui se sont terminées avec succès. Les opérations qui échouent sont signalées "hors bande". Ces opérations sont récupérées à l'aide de la fonction fi_eq_readerr. Lorsqu'une opération qui se termine avec une erreur inattendue est insérée dans une EQ, elle est placée dans une file d'erreurs temporaire. Tenter de lire à partir d'une EQ alors qu'un élément se trouve dans la file d'erreurs entraîne un échec FI_EAVAIL. Les applications peuvent utiliser ce code de retour pour déterminer quand appeler fi_eq_readerr.

Les informations d'erreur sont rapportées à l'utilisateur via la structure fi_eq_err_entry. Le format de cette structure est défini ci-dessous.

struct fi_eq_err_entry {
    fid_t            fid;        /* fid associé à l'erreur */
    void            *context;    /* contexte de l'opération */
    uint64_t         data;       /* données spécifiques à l'achèvement */
    int              err;        /* code d'erreur positif */
    int              prov_errno; /* code d'erreur du fournisseur */
    void            *err_data;   /* données d'erreur supplémentaires */
    size_t           err_data_size; /* taille de err_data */
};

Le fid référencera le descripteur de tissu associé à l'événement. Pour l'enregistrement de mémoire, ce sera le fid_mr, la résolution d'adresses référencera un fid_av, et les événements CM feront référence à un fid_ep. Le champ context sera défini sur le contexte spécifié dans le cadre de l'opération.

Le champ data sera défini comme décrit dans la page de manuel du type d'objet correspondant (par exemple, voir fi_av(3) pour une description de la manière dont les insertions de vecteurs d'adresses asynchrones sont terminées).

La raison générale de l'erreur est fournie via le champ err. Des informations d'erreur spécifiques au fournisseur ou opérationnelles peuvent également être disponibles via les champs prov_errno et err_data. Les utilisateurs peuvent appeler fi_eq_strerror pour convertir les informations d'erreur spécifiques au fournisseur en une chaîne imprimable à des fins de débogage.

En entrée, err_data_size indique la taille du tampon err_data en octets. En sortie, err_data_size sera défini sur le nombre d'octets copiés dans le tampon err_data. Les informations err_data sont généralement utilisées avec fi_eq_strerror pour fournir des détails sur le type d'erreur qui s'est produit.

À des fins de compatibilité, si err_data_size est 0 en entrée, ou si le tissu a été ouvert avec la version < 1.5, err_data sera défini sur un tampon de données appartenant au fournisseur. Le contenu du tampon restera valide jusqu'à un appel de lecture ultérieur contre l'EQ. Les applications doivent sérialiser l'accès à l'EQ lors du traitement des erreurs pour garantir que le tampon référencé par err_data ne change pas.

NOTE

S

Si une file d'événements a été débordée, elle sera placée dans un état « overrun ». Les opérations d'écriture sur une EQ débordée échoueront avec -FI_EOVERRUN. Les opérations de lecture continuer

ont de renvoyer tous les événements valides, non corrompus, s'il y en a. Une fois tous les événements valides récupérés, toute tentative de lecture de la EQ entraînera le renvoi d'un événeme
nt d'erreur FI_EOVERRUN. Les files d'événements débordées sont considérées comme fatales et ne peuvent pas être utilisées pour signaler des événements supplémentaires une fois le débordement survenu.
