fi_lnx - Le

fournisseur
LINKx (LNX)

PRÉSENTATIO

N

Le fournisseur LNX est conçu pour lier deux fournisseurs ou plus, permettant aux applications d'utiliser de manière transparente plusieurs

fournisseurs ou NIC. Ce fournisseur utilise l'infrastructure de pairs (peer) de libfabric pour faciliter l'utilisation des fournisseurs
sous-jacents. Cette version du fournisseur est capable de lier n'importe quel fournisseur libfabric qui prend en charge la capacité FI_PEER.

FONCTIONNALITÉS PRISES EN

CHARGE

Cette version contient une implémentation initiale du fournisseur LNX qui offre les fonctionnalités suivantes

:
Types de point de
terminaison
Le fournisseur ne prend en charge que le type de point de terminaison FI_EP_RD
M.
Capacités du point de
terminaison
LNX est une couche de transmission directe (passthrough) sur le chemin d'envoi. Sur le chemin de réception, LNX utilise l'infrastructure de pairs pour créer des files de réception partagées (SRQ). Les requêtes de réception sont placées sur la SRQ au lieu de la file de réception du fournisseur principal. Lorsque le fournisseur reçoit un message, il interroge la SRQ pour trouver une correspondance. Si une correspondance est trouvée, la requête de réception est terminée, sinon le message est placé sur la file inattendue partagée (SUQ) de LNX. Les requêtes de réception suivantes interrogent la SUQ pour trouver des correspondances. La première version du fournisseur ne prend en charge que les opérations balisées (tagged). Les autres types de messages seront pris en charge dans les futures
versions.
Mod
es
Le fournisseur n'exige pas l'utilisation de bits de mode
particuliers.
Progress
ion
LNX utilise l'infrastructure de pairs pour fournir une file d'achèvement partagée. Chaque fournisseur lié doit toujours gérer sa propre progression. Les événements d'achèvement seront cependant placés sur la file d'achèvement partagée, qui est transmise à l'application pour y
accéder.
Format
d'adresse
LNX enveloppe les adresses des fournisseurs liés dans un seul bloc binaire commun. Il n'altère ni ne modifie le format d'adresse des fournisseurs liés. Il les enveloppe dans une structure LNX qui est ensuite aplatie et retournée à l'application. Celle-ci est transmise entre les différents nœuds. Le fournisseur LNX est capable d'analyser le format aplati et d'opérer sur les différentes liaisons. Cela suppose que les nœuds du même groupe utilisent tous la même version du fournisseur avec exactement les mêmes liaisons. C'est-à-dire : vous ne pouvez pas avoir un nœud liant shm+cxi tandis qu'un autre lie
shm+rxm.
Opérations de
message
LNX est conçu pour intercepter les opérations de message telles que fi_tsenddata et, sur la base de critères spécifiques, transférer l'opération au fournisseur approprié. LNX peut lier n'importe quel fournisseur qui prend en charge la capacité FI_PEER. Le fournisseur SHM est un cas particulier en ce sens qu'il est toujours utilisé pour la communication intra-nœud s'il fait partie de la liaison. Sinon, tous les autres fournisseurs de la liaison sont utilisés en
round-robin.
Utilisation du
fournisseur
Pour utiliser le fournisseur, l'utilisateur doit définir la variable d'environnement FI_LNX_PROV_LINKS avec les fournisseurs liés ; voir la syntaxe dans la description de la variable. Cela permet la définition de plusieurs liaisons. Chaque liaison définit le fournisseur à ajouter à la liaison ainsi qu'une liste explici
te de domaines. Si seul le nom du fournisseur est spécifié, alors tous les domaines sont ajoutés à la liaison. Le fournisseur retourne la liste des liaisons spécifiées à l'application dans l'appel fi_getinfo(). Puisqu'il peut y avoir plusieurs fournisseurs dans la liaison, le premier domaine du premier fournisseur non-
shm dont les fi_info sont utilisés sert d'information de liaison. Cela signifie que si une liaison est définie comme suit : - shm+cxi:cxi0,cxi1 Les informations fi_info de cxi0 sont utilisées comme fi_info de liaison avec la modification des noms de fournisseur et de domaine. C'est important car les informations PCI f
ont partie des fi_info et certaines applications peuvent utiliser les informations PCI pour décider quelle liaison utiliser. Un critère de sélection courant est l'interface la plus proche du cœur auquel le processus est lié. Afin de prendre cette détermination, l'application a besoin des informations PCI de l'interface

LIMITATIONS ET TRAVAIL

FUTUR
Support
matériel
LNX ne prend pas en charge le déchargement matériel (hardware offload) ; ex. l'appariement de balises matériel. C'est une limitation inhérente à l'utilisation de l'infrastructure de pairs. En raison de l'utilisation d'une file de réception partagée que les fournisseurs liés doivent interroger lorsqu'un message est reçu, tout déchargement matériel nécessitant l'envoi des tampons de réception directement au matériel ne fonctionnera pas avec la file de réception partagée. La file de réception partagée présente deux avantages ; 1) réduire l'utilisation de la mémoire, 2) coordonner les opérations de réception. Pour le point 2, cela est nécessaire lors de la réception depuis FI_ADDR_UNSPEC. Dans ce cas, les deux fournisseurs faisant partie de la liaison peuvent entrer en concurrence pour obtenir l'accès au tampon de réception. C'est un travail futur de déterminer une manière d'utiliser l'appariement de balises matériel et d'autres capacités de déchargement matériel avec
LNX
Enregistrement de
mémoire
Dans le cadre de l'opération d'enregistrement de mémoire, différents matériels peuvent effectuer des étapes spécifiques au matériel telles que l'épinglage de la mémoire (memory pinning). Du fait que les API d'enregistrement de mémoire ne spécifient pas les adresses source ou destination, il n'est pas possible pour LNX de déterminer vers quel fournisseur transférer l'enregistrement de mémoire. LNX enregistre donc la mémoire auprès de tous les fournisseurs liés. Cela peut ne pas être efficace et peut avoir des effets secondaires imprévus. Une meilleure méthode est nécessaire pour prendre en charge l'enregistrement de mémoire. Une option est d'avoir un cache d'enregistrement de mémoire dans lnx pour éviter les opérations
coûteuses.
Types
d'opération
Cette version de LNX ne prend en charge que les opérations balisées. Les futures versions étendront la prise en charge à d'autres types
d'opérations.
Multi-ra
il
LNX implémente une fonctionnalité multi-rail qui permet la transmission de messages sur plusieurs interfaces, pilotée par la configuration de la liaison. Elle prend en charge la configuration de plusieurs domaines de fournisseurs au sein d'une seule liaison. Par exemple, la configuration suivante : FI_LNX_PROV_LINKS="cx
i:cxi0,cxi1" Définit une liaison qui inclut les domaines cxi0 et cxi1. Lorsqu'une application utilise cette liaison, les messages sont distribués de manière round-robin sur les deux domaines. De même, toutes les adresses de pairs disponibles sont utilisées de manière round-robin, assurant une communication équilibrée. Une exc
eption s'applique au fournisseur shm : s'il est inclus dans la liaison, tout le trafic intra-nœud est acheminé via le fournisseur shm. Pour la configuration suivante : FI_LNX_PROV_LINKS="tcp;ofi_rxm+cxi:cxi0" La liaison se compose de tous les domaines tcp associés au fournisseur tcp;ofi_rxm, ainsi que de cxi0. Les mess
ages sont répartis également sur tous les points de terminaison de domaine et les adresses de pairs. Le fournisseur s'assure que les types de points de terminaison locaux correspondent aux adresses distantes correspondantes — par exemple, si le fournisseur tcp est utilisé, les messages sont dirigés vers l'adresse tcp du pair.

PARAMÈTRES

D'EXÉCUTION

Le fournisseur LNX vérifie les variables d'environnement suivantes

:
FI_LNX_PROV_LI
NKS
Cette variable d'environnement est utilisée pour spécifier les fournisseurs à lier. Elle doit être définie pour que le fournisseur LNX retourne une liste de blocs fi_info dans l'appel fi_getinfo(). Le format qui doit être utilisé est : link ::= group [`|' group] group ::= provider [`+' provider [`:' provider_list]] provider_list ::= provider [`,' provider] provider ::= [a-zA-Z0-9_]+ Exemples : - shm+cxi:cxi0 - shm+cxi:cxi0,cxi1 - shm+cxi:cxi0|shm+cxi:cxi1 - shm+cxi Sur un système avec quatre domaines cxi, le dernier exemple est équivalent à : - shm+cxi:cxi0,cxi1,cxi2,
cxi3
FI_LNX_DISABLE_
SHM
Par défaut, cette variable d'environnement est définie à 0. Cependant, l'utilisateur peut la définir à un,
et alors le fournisseur SHM ne sera pas utilisé. Cela peut être utile pour le débogage et l'analyse des per
formances. Le fournisseur SHM sera naturellement utilisé pour toutes les opérations intra-nœud. Par conséque
nt, pour tester SHM de manière isolée avec LNX, les processus peuvent être limités au même nœud uniquement.
