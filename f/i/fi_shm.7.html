PRÉSENTATIO

N

Le fournisseur SHM est un fournisseur complet pouvant être utilisé sur des systèmes Linux prena

nt en charge la mémoire partagée et les appels process_vm_readv/process_vm_writev. Le fournisse
ur est destiné à fournir des communications performantes entre les processus d'un même système.

FONCTIONNALITÉS PRISES EN

CHARGE

Le fournisseur SHM offre les fonctionnalités suivantes

:
Types de points de
terminaison
Le fournisseur ne prend en charge que le type de point de terminaison FI_EP_RD
M.
Capacités des points de
terminaison
Les points de terminaison peuvent prendre en charge n'importe quelle combinaison des capacités de transfert de données suivantes : FI_MSG, FI_TAGGED, FI_RMA, et FI_ATOMICS. Ces capacités peuvent être affinées par FI_SEND, FI_RECV, FI_READ, FI_WRITE, FI_REMOTE_READ et FI_REMOTE_WRITE afin de limiter la direction des
opérations.
Mod
es
Le fournisseur n'exige l'utilisation d'aucun bit de
mode.
Progress
ion
Le fournisseur SHM prend en charge FI_PROGRESS_MANUAL. Les tampons de données côté réception ne sont pas modifiés en dehors des routines de traitement de l'achèvement. Le fournisseur traite les messages à l'aide de trois méthodes différentes, en fonction de la taille du message. Pour les messages de moins de 4096 octets, les achèvements tx sont générés immédiatement après l'envoi. Pour les messages plus volumineux, les achèvements tx ne sont pas générés avant que le côté réception ait traité le
message.
Format
d'adresse
Le fournisseur SHM utilise le format d'adresse FI_ADDR_STR, qui suit le motif de format général « [préfixe]://[adresse] ». L'application peut fournir des adr
esses via le paramètre node ou hints. Tant que l'adresse est dans un format FI_ADDR_STR valide (contient « :// »), l'adresse sera utilisée telle quelle. Si la
saisie de l'application est mal formatée ou si aucune saisie n'a été fournie, le fournisseur SHM la résoudra selon les normes suivantes du fournisseur SHM :

(flags & FI_SOURCE) ? src_addr : dest_addr = - si (node && service) : « fi_ns://node:service » - si (service) : « fi_ns://service » - si (node && !service) : « fi_shm://node » - si (!node && !service) : « fi_shm://PID

»

!(flags & FI_SOURCE) - src_addr = « fi_shm://PID

»

En d'autres termes, si l'application fournit une adresse source et/ou de destination dans un format FI_ADDR_STR acceptable (contient « :// »), l'appel à util_getinfo remplira avec succès src_addr et dest_addr avec la saisie fournie. Si la saisie n'est pas dans un format ADDR_STR, le fournisseur de mémoire partagée créera alors une adresse FI_ADDR_STR correcte avec soit le préfixe « fi_ns:// » (format nœud/service), soit le préfixe « fi_shm:// » (format shm), indiquant si l'adresse est une adresse « unique » et si elle nécessite ou non un identifiant de nom de point de terminaison supplémentaire pour la rendre unique. Pour le fournisseur de mémoire partagée, nous supposons que le service (avec ou sans nœud) suffit à la rendre unique, mais qu'un nœud seul ne suffit pas. Si seul un nœud est fourni, le préfixe « fi_shm:// » est utilisé pour indiquer qu'il ne s'agit pas d'une adresse unique. Si aucun nœud ni service n'est fourni (et dans le cas de la définition de l'adresse src sans FI_SOURCE et sans hints), l'identifiant de processus sera utilisé comme adresse par défaut. Lors de la création du point de terminaison, si src_addr a le préfixe « fi_shm:// », le fournisseur ajoutera « :[uid]:[ep_idx] » comme nom de point de terminaison unique (essentiellement, à la place d'un service). Dans le cas du préfixe « fi_ns:// » (ou de tout autre préfixe fourni par l'application), aucune information supplémentaire n'est nécessaire pour le rendre unique et il ne contiendra que l'adresse définie par l'application. Notez que le nom réel du point de terminaison n'inclura pas le préfixe « *:// » de FI_ADDR_STR car il ne peut être inclus dans aucun nom de région de mémoire partagée. Le fournisseur supprimera le préfixe avant de définir le nom du point de terminaison. Par conséquent, les adresses « fi_prefix1://my_node:my_service » et « fi_prefix2://my_node:my_service » donneraient des points de terminaison et des régions portant le même nom. L'application peut également remplacer le nom du point de terminaison après avoir créé un point de terminaison en utilisant setname() sans aucune restriction de format

d'adresse.

Drapeaux de message Le fournisseur prend en charge les drapeaux de message suivants : - FI_CLAIM - FI_COMPLETION - FI_DELIVERY_COMPLETE - FI_DISCARD - FI_INJECT - FI_MULTI_RECV - FI_PEEK - FI_REMOTE_CQ_DAT

A

Mode d'enregistrement MR Le fournisseur peut optimiser les appels RMA si l'application prend en charge FI_MR_VIRT_ADDR. Sinon, aucun mode MR supplémentaire n'est requis. Si la prise en charge de FI_HMEM est demandée, le fournisseur exigera

FI_MR_HMEM.

Opérations atomiques Le fournisseur prend en charge toutes les combinaisons de type de données et d'o

pérations tant que le message fait moins de 4096 oc
tets (ou 2048 pour les opérations de comparaison).

DS

A

L'Intel Data Streaming Accelerator (DSA) est un accélérateur intégré dans les processeurs Intel Xeon à partir de la génération Sapphire Rapids. L'une des capacités du DSA est de décharger le CPU des opérations de copie mémoire. Un système peut avoir un ou plusieurs périphériques DSA. Chaque périphérique DSA peut avoir une ou plusieurs files de travail. La spécification du DSA peut être trouvée

ici.

Le protocole SAR du fournisseur SHM est activé pour tirer parti du DSA afin de décharger les opérations de copie mémoire entrantes et sortantes des tampons SAR dans les régions de mémoire partagée. Pour tirer pleinement parti de la capacité de déchargement du DSA, les opérations de copie mémoire sont effectuées de manière asynchrone. Le thread initiateur de copie construit les commandes DSA et les soumet aux files de travail. Une opération de copie peut consister en plus d'une commande DSA. Dans ce cas, les commandes sont réparties sur toutes les files de travail disponibles de manière circulaire. Le thread de progression vérifie l'achèvement des commandes DSA. Si la commande de copie se termine avec succès, il notifie alors au pair de consommer les données. Si le DSA rencontre une faute de page lors de l'exécution de la commande, la faute de page est signalée via des enregistrements d'achèvement. Dans ce cas, le thread de progression accède à la page pour résoudre la faute de page et resoumet la commande après ajustement pour les achèvements partiels. L'un des avantages du fait de rendre les opérations de copie mémoire asynchrones est que les transferts de données entre différents points de terminaison cibles peuvent désormais être initiés en parallèle. L'utilisation d'Intel DSA dans le protocole SAR est désactivée par défaut et peut être activée à l'aide d'une variable d'environnement. Notez que CMA doit être désactivé, par ex. FI_SHM_DISABLE_CMA=0, afin que le DSA puisse être utilisé. Voir la section PARAMÈTRES

D'EXÉCUTION.

La compilation avec les capacités DSA dépend de la bibliothèque accel-config qui peut être trouvée ici. L'exécution avec DSA nécessite l'utilisation du noyau Linux 5.19.0-rc3 ou

ultérieur.

Les périphériques DSA doivent être configurés une seule fois avant l'exécution. Ce fichier de configuration (https://github.com/intel/idxd-config/blob/stable/contrib/configs/os_profile.conf) peut êt

re utilisé comme modèle avec l'utilitaire accel
-config pour configurer les périphériques DSA.
