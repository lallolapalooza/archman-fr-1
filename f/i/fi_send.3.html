NOM

fi_msg - Opérations de transfert de données par message

fi_recv / fi_recvv / fi_recvmsg
Poster un tampon pour recevoir un message entrant

fi_send / fi_sendv / fi_sendmsg fi_inject / fi_senddata : Initialiser une opération pour envoyer un message

SYNTAXE

#include <rdma/fi_endpoint.h>
ssize_t fi_recv(struct fid_ep *ep, void * buf, size_t len,
    void *desc, fi_addr_t src_addr, void *context);
ssize_t fi_recvv(struct fid_ep *ep, const struct iovec *iov, void **desc,
    size_t count, fi_addr_t src_addr, void *context);
ssize_t fi_recvmsg(struct fid_ep *ep, const struct fi_msg *msg,
    uint64_t flags);
ssize_t fi_send(struct fid_ep *ep, const void *buf, size_t len,
    void *desc, fi_addr_t dest_addr, void *context);
ssize_t fi_sendv(struct fid_ep *ep, const struct iovec *iov,
    void **desc, size_t count, fi_addr_t dest_addr, void *context);
ssize_t fi_sendmsg(struct fid_ep *ep, const struct fi_msg *msg,
    uint64_t flags);
ssize_t fi_inject(struct fid_ep *ep, const void *buf, size_t len,
    fi_addr_t dest_addr);
ssize_t fi_senddata(struct fid_ep *ep, const void *buf, size_t len,
    void *desc, uint64_t data, fi_addr_t dest_addr, void *context);
ssize_t fi_injectdata(struct fid_ep *ep, const void *buf, size_t len,
    uint64_t data, fi_addr_t dest_addr);

ARGUMENTS

ep
Point de terminaison du tissu sur lequel initialiser l'envoi ou poster un tampon de réception.
buf
Tampon de données à envoyer ou à recevoir.
len
Longueur du tampon de données à envoyer ou à recevoir, spécifiée en octets. Les transferts valides vont de 0 octet jusqu'à la taille maximale de message du point de terminaison.
iov
Tampon de données vectoriel.
count
Nombre d'entrées de données vectorielles.
desc
Descripteur associé au tampon de données. Voir fi_mr(3).
data
Données de la file d'attente de complétion (CQ) distante à transférer avec le message envoyé.
dest_addr
Adresse de destination pour les transferts sans connexion. Ignoré pour les points de terminaison connectés.
src_addr
Ne s'applique qu'aux points de terminaison sans connexion configurés avec FI_DIRECTED_RECV. Pour toutes les autres configurations de points de terminaison, src_addr est ignoré. src_addr définit l'adresse source à partir de laquelle recevoir. Par défaut, src_addr est traité comme une adresse de point de terminaison source (c'est-à-dire fi_addr_t retourné par fi_av_insert / fi_av_insertsvc / fi_av_remove). Si l'indicateur FI_AUTH_KEY est spécifié avec fi_recvmsg, src_addr est traité comme une clé d'autorisation source (c'est-à-dire fi_addr_t retourné par fi_av_insert_auth_key). S'il est défini sur FI_ADDR_UNSPEC, toute adresse source peut correspondre.
msg
Descripteur de message pour les opérations d'envoi et de réception.
flags
Indicateurs supplémentaires à appliquer pour l'opération d'envoi ou de réception.
context
Pointeur spécifié par l'utilisateur à associer à l'opération. Ce paramètre est ignoré si l'opération ne génère pas de complétion réussie, à moins qu'un indicateur d'opération ne spécifie que le paramètre context doit être utilisé pour une entrée requise.

DESCRIPTION

Les fonctions d'envoi – fi_send, fi_sendv, fi_sendmsg, fi_inject, et fi_senddata – sont utilisées pour transmettre un message d'un point de terminaison à un autre. La principale différence entre les fonctions d'envoi réside dans le nombre et le type de paramètres qu'elles acceptent en entrée. Sinon, elles remplissent la même fonction générale. Les messages envoyés à l'aide des opérations fi_msg sont reçus par un point de terminaison distant dans un tampon posté pour recevoir de tels messages.

Les fonctions de réception – fi_recv, fi_recvv, fi_recvmsg – postent un tampon de données à un point de terminaison pour recevoir les messages entrants. Semblables aux opérations d'envoi, les opérations de réception fonctionnent de manière asynchrone. Les utilisateurs ne doivent pas toucher les tampons de données postés tant que l'opération de réception n'est pas terminée.

Un point de terminaison doit être activé avant qu'une application puisse lui poster des opérations d'envoi ou de réception. Pour les points de terminaison connectés, les tampons de réception peuvent être postés avant l'appel de connect ou accept sur le point de terminaison. Cela garantit que des tampons sont disponibles pour recevoir les données entrantes immédiatement après l'établissement de la connexion.

Les opérations de message terminées sont rapportées à l'utilisateur via un ou plusieurs collecteurs d'événements associés au point de terminaison. Les utilisateurs fournissent un contexte qui est associé à chaque opération, et qui est renvoyé à l'utilisateur dans le cadre de l'événement de complétion. Voir fi_cq pour les détails sur les événements de complétion.

fi_send

L'appel fi_send transfère les données contenues dans le tampon de données spécifié par l'utilisateur vers un point de terminaison distant, en maintenant les limites du message.

fi_sendv

L'appel fi_sendv ajoute la prise en charge d'une liste de diffusion/collecte à fi_send. fi_sendv transfère l'ensemble des tampons de données référencés par le paramètre iov vers un point de terminaison distant sous forme d'un seul message.

fi_sendmsg

L'appel fi_sendmsg prend en charge les transferts de données sur les points de terminaison connectés et sans connexion, avec la possibilité de contrôler l'opération d'envoi par appel grâce à l'utilisation d'indicateurs. La fonction fi_sendmsg prend une structure fi_msg en entrée.

struct fi_msg {
    const struct iovec *msg_iov; /* tableau scatter-gather */
    void               **desc;   /* descripteurs de requête locaux */
    size_t             iov_count;/* nombre d'éléments dans iov */
    fi_addr_t          addr;     /* adresse de point de terminaison optionnelle */
    void               *context; /* contexte défini par l'utilisateur */
    uint64_t           data;     /* données de message optionnelles */
};

fi_inject

L'appel d'injection d'envoi est une version optimisée de fi_send avec les caractéristiques suivantes. Le tampon de données est disponible pour réutilisation immédiatement après le retour de l'appel, et aucune entrée de file d'attente de complétion (CQ) ne sera écrite si le transfert s'achève avec succès.

Conceptuellement, cela signifie que la fonction fi_inject se comporte comme si l'indicateur de transfert FI_INJECT était défini, les completions sélectives sont activées, et l'indicateur FI_COMPLETION n'est pas spécifié. Notez que l'entrée CQ sera supprimée même si le comportement par défaut du point de terminaison est d'écrire des entrées CQ pour toutes les completions réussies. Voir la discussion sur les indicateurs ci-dessous pour plus de détails. La taille de message demandée qui peut être utilisée avec fi_inject est limitée par inject_size.

Si FI_HMEM est activé, l'appel fi_inject ne peut accepter un tampon avec une interface égale à FI_HMEM_SYSTEM que si le fournisseur exige le mode FI_MR_HMEM. Cette limitation s'applique à tous les appels fi_*inject* et n'affecte pas la manière dont inject_size est rapporté.

fi_senddata

L'appel d'envoi de données est similaire à fi_send, mais permet l'envoi de données de CQ distantes (voir l'indicateur FI_REMOTE_CQ_DATA) dans le cadre du transfert.

fi_injectdata

L'appel d'injection de données est similaire à fi_inject, mais permet l'envoi de données de CQ distantes (voir l'indicateur FI_REMOTE_CQ_DATA) dans le cadre du transfert.

fi_recv

L'appel fi_recv poste un tampon de données à la file d'attente de réception du point de terminaison correspondant. Les réceptions postées sont recherchées dans l'ordre où elles ont été postées afin de faire correspondre les envois. Les limites de message sont maintenues. L'ordre dans lequel les réceptions s'achèvent dépend du type de point de terminaison et du protocole. Pour les points de terminaison sans connexion, le paramètre src_addr peut être utilisé pour indiquer qu'un tampon doit être posté pour recevoir les données entrantes d'un point de terminaison distant spécifique.

fi_recvmsg

L'appel fi_recvmsg permet de publier des tampons sur des points de terminaison connectés et non connectés, avec la possibilité de contrôler l'opération de réception pour chaque appel à l'aide de drapeaux. La fonction fi_recvmsg prend une struct fi_msg en entrée.

DRAPEAUX

Les appels fi_recvmsg et fi_sendmsg permettent à l'utilisateur de spécifier des drapeaux qui peuvent modifier le traitement par défaut des messages du point de terminaison. Les drapeaux spécifiés avec fi_recvmsg / fi_sendmsg remplacent la plupart des drapeaux précédemment configurés avec le point de terminaison, sauf indication contraire (voir fi_endpoint.3). La liste suivante de drapeaux est utilisable avec fi_recvmsg et/ou fi_sendmsg.

FI_REMOTE_CQ_DATA
S'applique à fi_sendmsg. Indique que des données CQ distantes sont disponibles et doivent être envoyées comme partie de la requête. Voir fi_getinfo pour des détails supplémentaires sur FI_REMOTE_CQ_DATA. Ce drapeau est implicitement défini pour fi_senddata et fi_injectdata.
FI_COMPLETION
Indique qu'une entrée de complétion doit être générée pour l'opération spécifiée. Le point de terminaison doit être lié à une file de complétion avec FI_SELECTIVE_COMPLETION qui correspond à l'opération spécifiée, ou ce drapeau est ignoré.
FI_MORE
Indique que l'utilisateur a des requêtes supplémentaires qui seront immédiatement publiées après le retour de l'appel courant. L'utilisation de ce drapeau peut améliorer les performances en permettant au fournisseur d'optimiser son accès au matériel de fabric.
FI_INJECT
S'applique à fi_sendmsg. Indique que le tampon de données sortantes doit être rendu à l'utilisateur immédiatement après le retour de l'appel d'envoi, même si l'opération est traitée de manière asynchrone. Cela peut nécessiter que l'implémentation du fournisseur sous-jacent copie les données dans un tampon local et transfère à partir de ce tampon. Ce drapeau ne peut être utilisé qu'avec des messages plus petits que inject_size.
FI_MULTI_RECV
S'applique aux opérations de réception publiées. Ce drapeau permet à l'utilisateur de publier un tampon unique qui recevra plusieurs messages entrants. Les messages reçuis seront empaquetés dans le tampon de réception jusqu'à ce que le tampon soit consommé. L'utilisation de ce drapeau peut faire qu'une seule opération de réception publiée génère plusieurs événements lorsque des messages sont placés dans le tampon. Le placement des données reçues dans le tampon peut être soumis à des restrictions d'alignement spécifiques au fournisseur.

Le tampon sera libéré par le fournisseur lorsque l'espace de tampon disponible descend en dessous du minimum spécifié (voir FI_OPT_MIN_MULTI_RECV). Notez qu'une entrée dans la file de complétion de réception associée sera toujours générée lorsque le tampon a été consommé, même si d'autres complétions de réception ont été supprimées (c'est-à-dire que le contexte Rx a été configuré pour FI_SELECTIVE_COMPLETION). Voir le drapeau de complétion FI_MULTI_RECV fi_cq(3).

FI_INJECT_COMPLETE
S'applique à fi_sendmsg. Indique qu'une complétion doit être générée lorsque le(s) tampon(s) source peuvent être réutilisés.
FI_TRANSMIT_COMPLETE
S'applique à fi_sendmsg et fi_recvmsg. Pour les envois, indique qu'une complétion ne doit pas être générée jusqu'à ce que l'opération ait été transmise avec succès et ne soit plus suivie par le fournisseur. Pour les opérations de réception, indique qu'une complétion peut être générée dès que le message a été traité par le fournisseur local, même si les données du message peuvent ne pas être visibles par tous les éléments de traitement. Voir fi_cq(3) pour la sémantique de complétion côté cible.
FI_DELIVERY_COMPLETE
S'applique à fi_sendmsg. Indique qu'une complétion doit être générée lorsque l'opération a été traitée par la destination.
FI_FENCE
S'applique aux transmissions. Indique que l'opération demandée, également connue sous le nom d'opération clôturée (fenced), et toute opération publiée après l'opération clôturée seront différées jusqu'à ce que toutes les opérations précédentes ciblant le même point de terminaison pair aient été complétées. Les opérations publiées après la clôture verront et/ou remplaceront les résultats de toute opération initiée avant l'opération clôturée.

L'ordre des opérations à partir de la publication de l'opération clôturée (inclusive) jusqu'à la publication d'une opération clôturée subséquente (exclusive) est contrôlé par la sémantique d'ordre du point de terminaison.

FI_MULTICAST
S'applique aux transmissions. Ce drapeau indique que l'adresse spécifiée comme destination de transfert de données est une adresse de multidiffusion (multicast). Ce drapeau doit être utilisé dans tous les transferts de multidiffusion, en conjonction avec un fi_addr_t de multidiffusion.
FI_AUTH_KEY
Valable uniquement avec les domaines configurés avec FI_AV_AUTH_KEY et les points de terminaison non connectés configurés avec FI_DIRECTED_RECV. Lorsqu'il est utilisé avec fi_recvmsg, ce drapeau indique que src_addr est une clé d'autorisation fi_addr_t au lieu d'un fi_addr_t de point de terminaison.

NOTES

Si un point de terminaison a été configuré avec FI_MSG_PREFIX, l'application doit inclure un espace de tampon de taille msg_prefix_size, tel que spécifié par les attributs du point de terminaison. Le tampon de préfixe doit se trouver au début des données référencées par le paramètre buf, ou être référencé par le premier vecteur d'E/S. L'espace de préfixe de message ne peut pas être divisé entre plusieurs vecteurs d'E/S. La taille du tampon de préfixe doit être incluse dans la longueur totale du tampon.

VALEUR RETOURNÉE

Retourne 0 en cas de succès. En cas d'erreur, une valeur négative correspondant à l'errno du fabric est retournée. Les valeurs d'errno du fabric sont définies dans rdma/fi_errno.h.

Voir la discussion ci-dessous pour les détails sur le traitement de FI_EAGAIN.

ERREURS

-FI_EAGAIN
Indique que le fournisseur sous-jacent manque actuellement des ressources nécessaires pour initier l'opération demandée. Les raisons pour lesquelles un fournisseur retourne FI_EAGAIN sont variées. Cependant, les raisons courantes incluent un tamponnage interne insuffisant ou des files de traitement pleines.

Un tamponnage interne insuffisant est souvent associé aux opérations qui utilisent FI_INJECT. Dans de tels cas, un tamponnage supplémentaire peut devenir disponible à mesure que les opérations publiées se complètent.

Des files de traitement pleines peuvent être un état temporaire lié au traitement local (par exemple, un grand message est en cours de transfert), ou peuvent être le résultat d'un contrôle de flux. Dans ce dernier cas, les files peuvent rester bloquées jusqu'à ce que des ressources supplémentaires soient disponibles côté distant du transfert.

Dans tous les cas, l'opération peut être réessayée après que des ressources supplémentaires deviennent disponibles. Lors de l'utilisation de FI_PROGRESS_MANUAL, l'application doit vérifier les complétions de transmission et de réception après avoir reçu FI_EAGAIN comme valeur de retour, indépendamment de l'opération qui a échoué. Cela est également fortement recommandé lors de l'utilisation de FI_PROGRESS_AUTO, car des accusés de réception ou des messages de contrôle de flux peuvent nécessiter d'être traités afin de reprendre l'exécution.
