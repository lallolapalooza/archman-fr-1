NOM

firewalld.direct - Fichier de configuration directe de firewalld

SYNOPSIS

/etc/firewalld/direct.xml

DÉPRECATION

L'interface directe est dépréciée. Elle sera supprimée dans une future version. Elle est remplacée par les politiques, voir firewalld.policies(5).

DESCRIPTION

La configuration directe offre un accès plus direct au pare-feu. Elle nécessite que l'utilisateur connaisse les concepts de base d'ip(6)tables/ebtables, c'est-à-dire table (filter/mangle/nat/...), chaîne (INPUT/OUTPUT/FORWARD/...), commandes (-A/-D/-I/...), paramètres (-p/-s/-d/-j/...) et cibles (ACCEPT/DROP/REJECT/...). La configuration directe ne doit être utilisée qu'en dernier recours lorsqu'il n'est pas possible d'utiliser firewalld.zone(5). Voir aussi Options directes dans firewall-cmd(1).

Un fichier de configuration directe de firewalld contient des informations sur les chaînes directes permanentes, les règles et le passage...

Voici la structure d'un fichier de configuration directe :

<?xml version="1.0" encoding="utf-8"?>
<direct>
  [ <chain ipv="ipv4|ipv6|eb" table="table" chain="chaîne"/> ]
  [ <rule ipv="ipv4|ipv6|eb" table="table" chain="chaîne" priority="priorité"> args </rule> ]
  [ <passthrough ipv="ipv4|ipv6|eb"> args </passthrough> ]
</direct>

direct

La balise de début et de fin obligatoire 

direct
définit la configuration directe. Cette balise ne peut être utilisée qu'une seule fois dans un fichier de configuration directe. Il n'y a pas d'attributs pour 
direct
.

chain

Est une balise facultative d'élément vide et peut être utilisée plusieurs fois. Elle peut être utilisée pour définir des noms pour des chaînes supplémentaires. Une entrée de chaîne a exactement trois attributs :

ipv="ipv4|ipv6|eb"

La famille IP dans laquelle la chaîne sera créée. Il peut s'agir de ipv4, ipv6 ou eb.

table="table"

Le nom de la table dans laquelle la chaîne sera créée. Il peut s'agir de l'une des tables utilisables pour iptables, ip6tables ou ebtables. Pour les valeurs possibles, voir la section TABLES des pages de manuel d'iptables, ip6tables ou ebtables.

chain="chaîne"

Le nom de la chaîne qui sera créée. Assurez-vous qu'il n'existe pas déjà une autre chaîne portant ce nom.

N'oubliez pas d'ajouter une règle ou une règle de passage avec une option --jump ou --goto pour connecter la chaîne à une autre.

rule

Est une balise d'élément facultative et peut être utilisée plusieurs fois. Elle peut être utilisée pour ajouter des règles à une chaîne intégrée ou ajoutée. Une entrée de règle a exactement quatre attributs :

ipv="ipv4|ipv6|eb"

La famille IP dans laquelle la règle sera ajoutée. Il peut s'agir de ipv4, ipv6 ou eb.

table="table"

Le nom de la table dans laquelle la règle sera ajoutée. Il peut s'agir de l'une des tables utilisables pour iptables, ip6tables ou ebtables. Pour les valeurs possibles, voir la section TABLES des pages de manuel d'iptables, ip6tables ou ebtables.

chain="chaîne"

Le nom de la chaîne dans laquelle la règle sera ajoutée. Il peut s'agir d'une chaîne intégrée ou d'une chaîne créée avec la balise 
chain
. Si le nom de la chaîne est une chaîne intégrée, la règle sera ajoutée à chain_direct, sinon le nom de chaîne fourni est utilisé. chain_direct est créé en interne pour toutes les chaînes intégrées afin de garantir que les règles ajoutées ne conflictuent pas avec les règles créées par firewalld.

priority="priorité"

La priorité est utilisée pour ordonner les règles. Une priorité de 0 signifie que la règle est ajoutée en haut de la chaîne ; avec une priorité plus élevée, la règle sera ajoutée plus bas. Les règles ayant la même priorité sont au même niveau et l'ordre de ces règles n'est pas fixe et peut changer. Si vous voulez vous assurer qu'une règle sera ajoutée après une autre, utilisez une priorité basse pour la première et une priorité plus élevée pour la suivante.

Les args peuvent être n'importe quels arguments d'iptables ou d'ip6tables qui ne conflictuent pas avec les attributs table ou chain.

passthrough

Est une balise d'élément facultative et peut être utilisée plusieurs fois. Elle peut être utilisée pour ajouter des règles à une chaîne intégrée ou ajoutée. Une entrée de règle a exactement un attribut :

ipv="ipv4|ipv6|eb"

La famille IP dans laquelle la règle de passage sera ajoutée. Il peut s'agir de ipv4, ipv6 ou eb.

Les args peuvent être n'importe quels arguments d'iptables ou d'ip6tables.

La règle de passage sera ajoutée directement à la chaîne. Il n'y a pas de mécanisme comme pour la règle directe 

rule
. L'utilisateur de la règle de passage doit s'assurer qu'il n'y aura pas de conflit avec les règles créées par firewalld.

AVERTISSEMENTS

Selon la valeur de FirewallBackend (voir firewalld.conf(5)), les règles directes se comportent différemment dans certains scénarios.

Priorité d'acceptation/rejet de paquets

En raison de détails d'implémentation de netfilter dans le noyau, si FirewallBackend=nftables est utilisé, les règles directes qui ACCEPTENT les paquets ne provoquent pas réellement leur acceptation immédiate par le système. Ces paquets sont toujours soumis à la règle nftables de firewalld. Cela signifie essentiellement qu'il existe deux pare-feux indépendants et que les paquets doivent être acceptés par les deux (iptables et nftables). Par ailleurs, ce scénario se produit également à l'intérieur de nftables (encore une fois, en raison de netfilter) s'il y a plusieurs chaînes attachées au même hook - ce n'est pas aussi simple que iptables vs nftables.

Il existe une poignée d'options pour contourner le problème de l'ACCEPT :

1. Règles Rich

Si une règle rich peut être utilisée, elle doit toujours être préférée aux règles directes. Les règles Rich seront converties dans le FirewallBackend activé. Voir firewalld.richlanguage(5).

2. Acceptation Générale

Les utilisateurs peuvent ajouter une acceptation explicite à la règle nftables. Cela peut être fait en ajoutant l'interface ou la source à la zone trusted.

Cette stratégie est souvent employée par des éléments qui effectuent leur propre filtrage, tels que : libvirt, podman, docker.

Attention : Cela signifie que firewalld ne filtrera pas ces paquets. Tout le filtrage doit être effectué via des règles directes ou des règles iptables hors bande.

3. Acceptation Sélective

Alternativement, n'activez que le service, le port, l'adresse ou autre élément pertinent dans la zone appropriée.

4. Revenir au backend iptables

En dernier recours, revenez au backend iptables en définissant FirewallBackend=iptables. Les utilisateurs doivent être conscients que le développement de firewalld se concentre sur le backend nftables.

Pour les règles directes qui DROPPENT les paquets, les paquets sont immédiatement rejetés, quelle que soit la valeur de FirewallBackend. Par conséquent, aucune considération spéciale n'est nécessaire.

Firewalld garantit le comportement ACCEPT/DROP ci-dessus en enregistrant les hooks nftables avec une priorité inférieure à celle des hooks iptables.

Priorité de l'interface directe

Avec FirewallBackend=iptables, les règles internes de haut niveau de firewalld s'appliquent avant l'exécution des règles directes. Cela inclut les règles d'acceptation des connexions existantes. Dans le passé, cela a surpris certains utilisateurs. Par exemple, si un utilisateur ajoute une règle directe pour rejeter le trafic sur le port de destination 22, les sessions SSH existantes continueraient de fonctionner, mais les nouvelles connexions seraient refusées.

Avec FirewallBackend=nftables, les règles directes ont été

délibérément une priorité plus élevée que toutes les autres règles firewalld. Cela inclut les règles pour accepter les connexions existantes.

EXEMPLE

Mise en liste noire des réseaux 192.168.1.0/24 et 192.168.5.0/24 avec journalisation et abandon précoce dans la table brute :

<?xml version="1.0" encoding="utf-8"?>
<direct>
  <chain ipv="ipv4" table="raw" chain="denylist"/>
  <rule ipv="ipv4" table="raw" chain="PREROUTING" priority="0">-s 192.168.1.0/24 -j denylist</rule>
  <rule ipv="ipv4" table="raw" chain="PREROUTING" priority="1">-s 192.168.5.0/24 -j denylist</rule>
  <rule ipv="ipv4" table="raw" chain="denylist" priority="0">-m limit --limit 1/min -j LOG --log-prefix "denylisted: "</rule>
  <rule ipv="ipv4" table="raw" chain="denylist" priority="1">-j DROP</rule>
</direct>
