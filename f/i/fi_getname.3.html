DESCRIPTIO

N

Les fonctions de gestion des connexions sont utilisées pour connecter un point de terminaison orienté connexion (FI_EP_MSG) à un pair à

l'écoute.

fi_liste

n

L'appel fi_listen indique que le point de terminaison spécifié doit passer à un état de connexion passif, lui permettant d'accepter les demandes de connexion entrantes. Les demandes de connexion adressées à un point de terminaison

à l'écoute sont signalées de manière asynchrone à l'utilisateur via une file d'événements CM liée, en utilisant le type d'événement FI_CONNREQ. Le nombre de demandes de connexion en attente qui peuvent être mises en file d'attente
sur un point de terminaison est limité par le paramètre backlog du point de terminaison à l'écoute. Le backlog est initialisé en fonction des valeurs de configuration administratives, mais peut être ajusté via l'appel fi_control.

fi_connec

t

L'appel fi_connect initie une demande de connexion sur un point de terminaison

orienté connexion vers l'adresse de destination. fi_connect ne peut être app
elé qu'une seule fois sur un point de terminaison au cours de sa durée de vie.

fi_accept /

fi_reject

Les appels fi_accept et fi_reject sont utilisés sur le côté passif (à l'écoute) d'une connexion pour accepter ou rejeter une demande de connexion, respectivement. Pour accepter une connexion, l'application à l'écoute attend d'abord un événement de demande de connexion (FI_CONNREQ). Après avoir reçu un tel événement, l'application alloue un nouveau point de terminaison pour accepter la connexion. Ce point de terminaison doit être alloué à l'aide d'une structure fi_info référençant le handle de cet événement FI_CONNREQ. fi_accept est ensuite invoqué avec le point de terminaison nouvellement alloué. Si l'application à l'écoute souhaite rejeter une demande de connexion, elle appelle fi_reject avec le point de terminaison à l'écoute et une référence à la demande de

connexion.

Une demande de connexion acceptée avec succès entraînera la réception d'un événement FI_CONNECTED par le point de terminaison actif (en cours de connexion) sur sa file d'événements associée. Une demande de connexion rejetée ou échouée générera un événement d'erreur. L'entrée d'erreur fournira des détails supplémentaires décrivant la raison de la tentative

échouée.

Un événement FI_CONNECTED sera également généré sur le côté passif pour le point de terminaison acceptant une fois que la connexion a été correctement établie. Le fid de l'événement FI_CONN

ECTED sera celui du point de terminaison passé à fi_accept, par opposition au point de terminaison passif à l'écoute. Les transferts de données sortants ne peuvent pas être initiés sur un po
int de terminaison orienté connexion tant qu'un événement FI_CONNECTED n'a pas été généré. Cependant, les tampons de réception peuvent être associés à un point de terminaison à tout moment.

fi_shutdow

n

L'appel fi_shutdown est utilisé pour déconnecter gracieusement un point de terminaison de son pair. Le paramètre flags est réservé et doit être

0.

Les opérations en attente soumises au point de terminaison lors de l'appel de fi_shutdown seront annulées ou abandonnées. La notification des opérations annulées sera rapportée par le fournisseur aux files d'achèvement (completion queues) correspondantes. Les opérations abandonnées seront silencieusement supprimées, sans qu'aucun achèvement ne soit généré. Le choix d'annuler ou d'abandonner les opérations dépend du fournisseur. Cependant, tous les achèvements annulés seront écrits avant le retour de

fi_shutdown.

Lorsqu'il est appelé, fi_shutdown n'affecte pas les achèvements déjà écrits dans une file d'achèvement. Tous les achèvements en file d'attente associés aux opérations asynchrones soumises au point de terminaison peuvent toujours être récupérés depuis les files d'achèvement correspondantes après qu'un point de terminaison a été

arrêté.

Un événement FI_SHUTDOWN sera généré pour un point de terminaison lorsque le pair distant émet une déconnexion via fi_shutdown ou ferme brutalement l

e point de terminaison. Notez que dans le cas d'une fermeture brutale, un événement FI_SHUTDOWN ne sera généré que si le système distant est joignabl
e et si un service ou un agent noyau sur le système distant est capable de notifier le point de terminaison local que la connexion a été interrompue.

fi_clos

e

Fi_close est utilisé pour dissocier un point de terminaison d'un groupe de multidif

fusion et fermer toutes les ressources associées au groupe. Fi_close doit être appe
lé sur tous les groupes de multidiffusion auxquels un point de terminaison rejoint.

fi_setnam

e

L'appel fi_setname peut être utilisé pour modifier ou attribuer l'adresse du point de terminaison local. Il est conceptuellement similaire à l'opération de liaison (bind) des sockets. Un point de terminaison peut se voir attribuer une adresse lors de sa création, via la structure fi_info. L'appel fi_setname permet à un point de terminaison d'être créé sans être associé à un service spécifique (par ex., un numéro de port) et/ou à une adresse de nœud (par ex., réseau), l'adressage étant attribué dynamiquement. Le format des données d'adressage spécifiées doit correspondre à celui spécifié via la structure fi_info lors de la création du point de

terminaison.

Si aucune adresse de service n'est spécifiée et qu'une adresse de service n'a pas encore été attribuée au point de terminaison, alors le fournisseur allouera une adresse de service et

l'attribuera au point de terminaison. Si une adresse de nœud ou de service est spécifiée, alors, à l'issue de l'exécution réussie de fi_setname, le point de terminaison se verra attr
ibuer l'adressage donné. Si une adresse ne peut pas être attribuée, ou si l'adresse du point de terminaison ne peut pas être modifiée, un code d'erreur de tissu approprié est renvoyé.

fi_getname /

fi_getpeer

Les appels fi_getname et fi_getpeer peuvent être utilisés pour récupérer respectivement l'adresse locale ou distante du point de terminaison. En entrée, le paramètre addrlen doit indiquer la taille du tampon addr. Si l'adresse réelle est plus grande que ce qui peut tenir dans le tampon, elle sera tronquée et -FI_ETOOSMALL sera renvoyé.. Sur la sortie, addrlen est défini à la taille du tampon nécessaire pour stocker l'adresse, qui peut être plus grande que la valeur d'entrée.

fi_getname n'est pas garanti de retourner une adresse source valide avant que le point de terminaison spécifié n'ait été activé ou qu'une adresse ne lui ait été attribuée. Un point de terminaison peut être activé explicitement via fi_enable, ou implicitement, par exemple via fi_connect ou fi_listen. Une adresse peut être attribuée en utilisant fi_setname. fi_getpeer n'est pas garanti de retourner une adresse de pair valide jusqu'à ce qu'un point de terminaison soit complètement connecté – un événement FI_CONNECTED a été généré.

fi_join

Cet appel attache un point de terminaison à un groupe de multidiffusion. Par défaut, le point de terminaison rejoindra le groupe en fonction des capacités de transfert de données du point de terminaison. Par exemple, si le point de terminaison a été configuré pour envoyer et recevoir des données, alors le point de terminaison sera capable d'initier et de recevoir des transferts vers et depuis le groupe de multidiffusion. Les drapeaux fi_join peuvent être utilisés pour restreindre l'accès au groupe de multidiffusion, sous réserve des limitations de capacité du point de terminaison.

Les opérations de jointure de multidiffusion s'achèvent de manière asynchrone. Un point de terminaison doit être lié à une file d'événements avant d'appeler fi_join. Le résultat de l'opération de jointure sera signalé à l'EQ comme un événement FI_JOIN_COMPLETE. Les applications ne peuvent pas émettre de transferts de multidiffusion avant de recevoir une notification que l'opération de jointure est terminée. Notez qu'un point de terminaison peut commencer à recevoir des messages du groupe de multidiffusion dès que la jointure est terminée, ce qui peut se produire avant que l'événement FI_JOIN_COMPLETE ne soit généré.

Les applications doivent appeler fi_close sur le groupe de multidiffusion pour déconnecter le point de terminaison du groupe. Après la fin d'une opération de jointure, l'appel fi_mc_addr peut être utilisé pour récupérer l'adresse associée au groupe de multidiffusion.

fi_mc_addr

Retourne l'adresse fi_addr_t associée à un groupe de multidiffusion. Cette adresse doit être utilisée lors de la transmission de données vers un groupe de multidiffusion et associée au drapeau d'opération FI_MULTICAST.

DRAPEAUX

Sauf dans les fonctions notées ci-dessous, les drapeaux sont réservés et doivent être 0.

FI_SEND
S'applique à fi_join. Ce drapeau indique que le point de terminaison doit rejoindre le groupe de multidiffusion en tant que membre d'envoi uniquement. Le point de terminaison doit être configuré pour les opérations de transmission pour utiliser ce drapeau, sinon une erreur se produira.
FI_RECV
S'applique à fi_join. Ce drapeau indique que le point de terminaison doit rejoindre le groupe de multidiffusion avec uniquement des permissions de réception. Le point de terminaison doit être configuré pour les opérations de réception pour utiliser ce drapeau, sinon une erreur se produira.

VALEUR DE RETOUR

Retourne 0 en cas de succès. En cas d'erreur, une valeur négative correspondant au numéro d'erreur fabric est retournée. Les numéros d'erreur fabric sont définis dans rdma/fi_errno.h.

ERREURS

NOTES

Pour les points de terminaison orientés connexion, le tampon référencé par param sera envoyé dans le cadre de la demande ou de la réponse de connexion, sous réserve des contraintes du protocole de connexion sous-jacent. Les applications peuvent utiliser fi_getopt avec l'option de point de terminaison FI_OPT_CM_DATA_SIZE pour déterminer la taille des données d'application qui peuvent être échangées dans le cadre d'une demande ou d'une réponse de connexion. Les appels fi_connect, fi_accept et fi_reject tronqueront silencieusement toute donnée d'application qui ne rentre pas dans les messages de protocole sous-jacents. Les données utilisateur échangées dans le cadre du processus de connexion sont disponibles dans la structure fi_eq_cm_entry, pour les événements FI_CONNREQ et FI_CONNECTED, ou comme err_data supplémentaire à fi_eq_err_entry, dans le cas d'une connexion rejetée.
