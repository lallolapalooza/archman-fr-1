DESCRIPTION

Les transferts atomiques sont utilisés pour lire et mettre à jour des données situées dans des régions de mémoire distante de manière atomique. Conceptuellement, ils sont similaires aux opérations atomiques locales de nature similaire (par ex. incrément atomique, comparaison et échange, etc.). Les mises à jour des données distantes impliquent l'une de plusieurs opérations sur les données et agissent sur des types de données spécifiques, comme listés ci-dessous. En tant que tel, les transferts atomiques ont connaissance du format des données accessibles. Une fonction atomique unique peut opérer sur un tableau de données en appliquant une opération atomique à chaque entrée, mais l'atomicité d'une opération est limitée à un seul type de données ou entrée.

Types de données atomiques

Les fonctions atomiques peuvent opérer sur l'un des types de données identifiés suivants. Une fonction atomique donnée peut prendre en charge tout type de données, sous réserve des contraintes d'implémentation du fournisseur.

FI_INT8
Entier signé sur 8 bits.
FI_UINT8
Entier non signé sur 8 bits.
FI_INT16
Entier signé sur 16 bits.
FI_UINT16
Entier non signé sur 16 bits.
FI_INT32
Entier signé sur 32 bits.
FI_UINT32
Entier non signé sur 32 bits.
FI_INT64
Entier signé sur 64 bits.
FI_UINT64
Entier non signé sur 64 bits.
FI_INT128
Entier signé sur 128 bits.
FI_UINT128
Entier non signé sur 128 bits.
FI_FLOAT
Valeur flottante en simple précision (IEEE 754).
FI_DOUBLE
Valeur flottante en double précision (IEEE 754).
FI_FLOAT_COMPLEX
Une paire ordonnée de valeurs flottantes en simple précision (IEEE 754), où la première valeur représente la partie réelle d'un nombre complexe et la seconde représente la partie imaginaire.
FI_DOUBLE_COMPLEX
Une paire ordonnée de valeurs flottantes en double précision (IEEE 754), où la première valeur représente la partie réelle d'un nombre complexe et la seconde représente la partie imaginaire.
FI_LONG_DOUBLE
Une valeur flottante de précision étendue double (IEEE 754). Notez que la taille d'un long double et le nombre de bits utilisés pour la précision dépendent du compilateur, de la plateforme et/ou du fournisseur. Les développeurs qui utilisent long double doivent s'assurer que libfabric est compilé à l'aide d'un format long double compatible avec leur application, et que ce format est pris en charge par le fournisseur. Le mécanisme utilisé pour cette validation dépasse actuellement la portée de l'API libfabric.
FI_LONG_DOUBLE_COMPLEX
Une paire ordonnée de valeurs flottantes de précision étendue double (IEEE 754), la première valeur représentant la partie réelle d'un nombre complexe et la seconde représentant la partie imaginaire.
FI_FLOAT16

FI_BFLOAT16
Valeur flottante brain 16 bits (IEEE 754-2008).
FI_FLOAT8_E4M3
Valeur flottante 8 bits avec un exposant de 4 bits et une mantisse de 3 bits.
FI_FLOAT8_E5M2
Valeur flottante 8 bits avec un exposant de 5 bits et une mantisse de 2 bits.

Opérations Atomiques

Les opérations atomiques suivantes sont définies. Une opération atomique agit souvent sur une valeur cible dans le tampon mémoire distant et une valeur source fournie avec la fonction atomique. Elle peut également transporter des données source pour remplacer la valeur cible dans les opérations de comparaison et d'échange. Une description conceptuelle de chaque opération est fournie.

FI_MIN
Minimum
if (buf[i] < addr[i])
    addr[i] = buf[i]
FI_MAX
Maximum
if (buf[i] > addr[i])
    addr[i] = buf[i]
FI_SUM
Somme
addr[i] = addr[i] + buf[i]
FI_PROD
Produit
addr[i] = addr[i] * buf[i]
FI_LOR
OU logique
addr[i] = (addr[i] || buf[i])
FI_LAND
ET logique
addr[i] = (addr[i] && buf[i])
FI_BOR
OU binaire
addr[i] = addr[i] | buf[i]
FI_BAND
ET binaire
addr[i] = addr[i] & buf[i]
FI_LXOR
OU exclusif logique (XOR)
addr[i] = ((addr[i] && !buf[i]) || (!addr[i] && buf[i]))
FI_BXOR
OU exclusif binaire (XOR)
addr[i] = addr[i] ^ buf[i]
FI_ATOMIC_READ
Lire des données de manière atomique
result[i] = addr[i]
FI_ATOMIC_WRITE
Écrire des données de manière atomique
addr[i] = buf[i]
FI_CSWAP
Comparer les valeurs et, si elles sont égales, échanger avec les données
if (compare[i] == addr[i])
    addr[i] = buf[i]
FI_CSWAP_NE
Comparer les valeurs et, si elles sont différentes, échanger avec les données
if (compare[i] != addr[i])
    addr[i] = buf[i]
FI_CSWAP_LE
Comparer les valeurs et, si elles sont inférieures ou égales, échanger avec les données
if (compare[i] <= addr[i])
    addr[i] = buf[i]
FI_CSWAP_LT
Comparer les valeurs et, si elles sont inférieures, échanger avec les données
if (compare[i] < addr[i])
    addr[i] = buf[i]
FI_CSWAP_GE
Comparer les valeurs et, si elles sont supérieures ou égales, échanger avec les données
if (compare[i] >= addr[i])
    addr[i] = buf[i]
FI_CSWAP_GT
Comparer les valeurs et, si elles sont supérieures, échanger avec les données
if (compare[i] > addr[i])
    addr[i] = buf[i]
FI_MSWAP
Échanger des bits masqués avec des données
addr[i] = (buf[i] & compare[i]) | (addr[i] & ~compare[i])
FI_DIFF
Calculer la différence
addr[i] = addr[i] - buf[i]

Fonctions Atomiques de Base

Les fonctions atomiques de base – fi_atomic, fi_atomicv, fi_atomicmsg – sont utilisées pour transmettre des données à un nœud distant, où l'opération atomique spécifiée est effectuée sur les données cibles. Le résultat d'une fonction atomique de base est stocké dans la région mémoire distante. La principale différence entre les fonctions atomiques réside dans le nombre et le type de paramètres qu'elles acceptent en entrée. Sinon, elles effectuent la même fonction générale.

L'appel fi_atomic transfère les données contenues dans le tampon de données spécifié par l'utilisateur vers un nœud distant. Pour les points de terminaison sans connexion, le point de terminaison de destination est spécifié par le paramètre dest_addr. À moins que le point de terminaison n'ait été configuré différemment, le tampon de données passé à fi_atomic ne doit pas être modifié par l'application tant que l'appel fi_atomic ne s'est pas terminé de manière asynchrone. Le tampon cible d'une opération atomique de base doit autoriser l'accès en lecture et/ou écriture à distance, selon le cas.

L'appel fi_atomicv ajoute la prise en charge d'une liste de dispersion-collecte à fi_atomic. fi_atomicv transfère l'ensemble des tampons de données référencés par le paramètre ioc vers le nœud distant pour traitement.

L'appel fi_inject_atomic est une version optimisée de fi_atomic. La fonction fi_inject_atomic se comporte comme si le drapeau de transfert FI_INJECT était défini, et FI_COMPLETION ne l'était pas. Autrement dit, le tampon de données est disponible pour réutilisation immédiatement au retour de fi_inject_atomic, et aucun événement de complétion ne sera généré pour cette opération atomique. L'événement de complétion sera supprimé même si le point de terminaison n'a pas été configuré avec FI_SELECTIVE_COMPLETION. Voir la discussion sur les drapeaux ci-dessous pour plus de détails. La taille de message demandée utilisable avec fi_inject_atomic est limitée par inject_size.

La fonction fi_atomicmsg prend en charge les fonctions atomiques sur les points de terminaison connectés et sans connexion, avec la possibilité de contrôler l'opération atomique par appel grâce à l'utilisation de drapeaux. La fonction fi_atomicmsg prend une structure fi_msg_atomic en entrée.

struct fi_msg_atomic {
    const struct fi_ioc *msg_iov; /* tableau de dispersion-collecte local */
    void                **desc;   /* descripteurs d'accès locaux */
    size_t              iov_count;/* # d'éléments dans ioc */
    const void          *addr;    /* adresse de point de terminaison optionnelle */
    const struct fi_rma_ioc *rma_iov; /* SGL distant */
    size_t              rma_iov_count;/* # d'éléments dans le SGL distant */
    enum fi_datatype    datatype; /* type de données de l'opérande */
    enum fi_op          op;       /* opération atomique */
    void                *context; /* contexte défini par l'utilisateur */
    uint64_t            data;     /* données optionnelles */
};
struct fi_ioc {
    void        *addr;    /* adresse locale */
    size_t      count;    /* # d'opérandes cibles */
};
struct fi_rma_ioc {
    uint64_t    addr;     /* adresse cible */
    size_t      count;    /* # d'opérandes cibles */
    uint64_t    key;      /* clé d'accès */
};

La liste des opérations atomiques suivante est utilisable avec les opérations atomiques de base : FI_MIN, FI_MAX, FI_SUM, FI_PROD, FI_LOR, FI_LAND, FI_BOR, FI_BAND, FI_LXOR, FI_BXOR, et FI_ATOMIC_WRITE.

Fonctions Fetch-Atomic

Les fonctions fetch-atomic – fi_fetch_atomic, fi_fetch_atomicv, et fi_fetch_atomicmsg – se comportent de manière similaire à la fonction atomique de base équivalente. La différence entre les appels fetch et base atomiques est que les routines fetch-atomic retournent la valeur initiale qui était stockée à la cible à l'utilisateur. La valeur initiale est lue dans le tampon de résultat fourni par l'utilisateur. Le tampon cible des opérations fetch-atomic doit être activé pour l'accès en lecture à distance.

La liste des opérations atomiques suivante est utilisable avec les opérations fetch-atomiques : FI_MIN, FI_MAX, FI_SUM, FI_PROD, FI_LOR, FI_LAND, FI_BOR, FI_BAND, FI_LXOR, FI_BXOR, FI_ATOMIC_READ, et FI_ATOMIC_WRITE.

Pour les opérations FI_ATOMIC_READ, l'opérande du tampon source (par exemple, le paramètre buf de fi_fetch_atomic) est ignoré et peut être NULL. Les résultats sont écrits dans le tampon de résultat.

Fonctions Compare-Atomic

='permalink' href='#Compare-Atomic_Functions'>Fonctions Compare-Atomic

Les fonctions atomiques de comparaison – fi_compare_atomic, fi_compare_atomicv et fi_compare atomicmsg – sont utilisées pour des opérations qui nécessitent de comparer les données cibles à une valeur avant d'effectuer une opération d'échange (swap). Les fonctions atomiques de comparaison prennent en charge : FI_CSWAP, FI_CSWAP_NE, FI_CSWAP_LE, FI_CSWAP_LT, FI_CSWAP_GE, FI_CSWAP_GT et FI_MSWAP.

Fonctions atomiques valides

Les fonctions atomiques valides – fi_atomicvalid, fi_fetch_atomicvalid et fi_compare_atomicvalid – indiquent quelles opérations le fournisseur local prend en charge. Les opérations nécessaires non prises en charge par le fournisseur doivent être émulées par l'application. Chaque appel valide correspond à un ensemble de fonctions atomiques. fi_atomicvalid vérifie si un fournisseur prend en charge une opération atomique de base spécifique pour un type de données et une opération donnés. fi_fetch_atomicvalid indique si un fournisseur prend en charge une opération fetch-atomic spécifique pour un type de données et une opération donnés. Et fi_compare_atomicvalid vérifie si un fournisseur prend en charge une opération compare-atomic spécifiée pour un type de données et une opération donnés.

Si une opération est prise en charge, un appel atomique valide renverra 0, ainsi qu'un nombre d'unités de données atomiques sur lesquelles un seul appel de fonction opérera.

Interroger les attributs atomiques

L'appel fi_query_atomic agit comme une opération atomique valide améliorée (voir les définitions des fonctions atomiques valides ci-dessus). Elle est fournie, en partie, pour une extensibilité future. L'opération d'interrogation signale quelles opérations atomiques sont prises en charge par le domaine, pour des points d'extrémité configurés de manière appropriée.

Le comportement de fi_query_atomic est ajusté en fonction du paramètre flags. Si flags vaut 0, l'opération signale les attributs atomiques pris en charge pour les opérations atomiques de base, similaire à fi_atomicvalid pour les points d'extrémité. Si flags a le bit FI_FETCH_ATOMIC défini, l'opération se comporte similaire à fi_fetch_atomicvalid. De même, le bit FI_COMPARE_ATOMIC fait que l'interrogation agit comme fi_compare_atomicvalid. Les bits FI_FETCH_ATOMIC et FI_COMPARE_ATOMIC ne peuvent pas être définis tous les deux.

Si le bit FI_TAGGED est défini, le fournisseur indiquera s'il prend en charge les opérations atomiques vers les tampons de réception étiquetés (tagués). Le bit FI_TAGGED peut être utilisé seul, ou en conjonction avec les drapeaux FI_FETCH_ATOMIC et FI_COMPARE_ATOMIC.

La sortie de fi_query_atomic est struct fi_atomic_attr :

struct fi_atomic_attr {
    size_t count;
    size_t size;
};

Le champ d'attribut count est défini comme pour les appels atomiques valides. Le champ size indique la taille en octets du type de données atomique. Le champ size est utile pour les types de données dont la taille peut différer en fonction de la plateforme ou du compilateur, tels que FI_LONG_DOUBLE.

Complétions

Les opérations atomiques terminées sont signalées à l'initiateur de la requête via une file d'attente de complétion (CQ) ou un compteur associé. Tout contexte fourni par l'utilisateur spécifié avec la requête sera renvoyé dans le cadre de toute événement de complétion écrit dans une CQ. Voir fi_cq pour les détails des événements de complétion.

Tout résultat renvoyé à l'initiateur dans le cadre d'une opération atomique sera disponible avant la génération d'un événement de complétion. Cela sera vrai même si la sémantique de complétion demandée fournit une garantie plus faible. C'est-à-dire que les opérations atomiques fetch ont la sémantique FI_DELIVERY_COMPLETE. Les complétions générées pour d'autres types d'opérations atomiques indiquent qu'il est sûr de réutiliser les tampons de données sources.

Toute mise à jour des données à la cible d'une opération atomique sera visible pour les agents (processus CPU, NIC et autres appareils) sur le nœud cible avant que l'un des événements suivants ne se produise. Si l'opération atomique génère un événement de complétion ou met à jour un compteur de complétion au point d'extrémité cible, les résultats seront disponibles avant la notification de complétion. Après le traitement d'une complétion pour l'atomique, si l'initiateur soumet un transfert entre les mêmes points d'extrémité qui génère une complétion à la cible, les résultats seront disponibles avant l'événement du transfert suivant. Ou, si un transfert de données fenced (clôturé) de l'initiateur suit la requête atomique, les résultats seront disponibles avant une complétion à la cible pour le transfert fenced.

La correction des opérations atomiques sur une région mémoire cible n'est garantie que lorsqu'elle est effectuée par un seul acteur pour une fenêtre de temps donnée. Un acteur est défini comme un seul domaine libfabric sur la cible (identifié par le nom du domaine, et non une instance ouverte de ce domaine), un complexe CPU cohérent, ou un autre appareil (par ex. GPU) capable d'effectuer des opérations atomiques sur la mémoire cible. Les résultats des opérations atomiques effectuées par plusieurs acteurs simultanément sont indéfinis. Par exemple, émettre des opérations atomiques basées sur le CPU vers une région cible mise à jour simultanément par des atomiques basées sur la NIC peut laisser les données de la région dans un état inconnu. Les résultats des opérations atomiques d'un premier acteur doivent être visibles pour un second acteur avant que le second acteur n'émette ses propres atomiques.

DRAPEAUX

Les appels fi_atomicmsg, fi_fetch_atomicmsg et fi_compare_atomicmsg permettent à l'utilisateur de spécifier des drapeaux qui peuvent modifier l'opération de transfert de données par défaut. Les drapeaux spécifiés avec les opérations de messages atomiques remplacent la plupart des drapeaux précédemment configurés avec le point d'extrémité, sauf indication contraire (voir fi_control). La liste suivante de drapeaux est utilisable avec les appels de messages atomiques.

FI_COMPLETION
Indique qu'une entrée de complétion doit être générée pour l'opération spécifiée. Le point d'extrémité doit être lié à une file d'attente de complétion avec FI_SELECTIVE_COMPLETION qui correspond à l'opération spécifiée, ou ce drapeau est ignoré.
FI_MORE
Indique que l'utilisateur a des requêtes supplémentaires qui seront immédiatement publiées après le retour de l'appel courant. L'utilisation de ce drapeau peut améliorer les performances en permettant au fournisseur d'optimiser son accès au matériel de fabric.
FI_INJECT
Indique que le contrôle des tampons de données constantes doit être rendu à l'utilisateur immédiatement après le retour de l'appel, même si l'opération est gérée de manière asynchrone. Cela peut nécessiter que l'implémentation du fournisseur sous-jacent copie les données dans un tampon local et les transfère depuis ce tampon. Les tampons de données constantes font référence à tout tampon de données ou iovec utilisé par les API atomiques qui sont marqués comme `const'. Les tampons non constants ou de sortie ne sont pas affectés par ce drapeau et peuvent être accédés par le fournisseur à tout moment jusqu'à ce que l'opération soit terminée. Ce drapeau ne peut être utilisé qu'avec des messages plus petits que inject_size.
FI_FENCE
S'applique aux transmissions. Indique que l'opération demandée, également connue comme l'opération fenced, et toute opération publiée après l'opération fenced seront différées jusqu'à ce que toutes les opérations précédentes ciblant le même point d'extrémité pair aient été terminées. Les opérations publiées après le fencing verront et/ou remplaceront les résultats de toute opération initiée avant l'opération fenced.

L'ordre des opérations à partir de la publication de l'opération fenced (inclusive) jusqu'à la publication d'une opération fenced suivante (exclusive) est contrôlé par la sémantique d'ordre du point d'extrémité.

FI_TAGGED
Spécifie que la cible de l'opération atomique est un tampon de réception étiqueté (tagué) au lieu d'un tampon RMA. Lorsqu'un tampon tagué est la région mémoire cible, le paramètre addr est utilisé comme décalage en octets à base 0 dans le tampon tagué, le paramètre key spécifiant le tag.

VALEUR DE RETOUR

Renvoie 0 en cas de succès. En cas d'erreur, une valeur négative correspondant à l'errno du fabric est renvoyée. Les valeurs d'errno du fabric sont définies dans rdma/fi_errno.h.

ERREURS

-FI_EAGAIN
Voir fi_msg(3) pour une description détaillée du traitement de FI_EAGAIN.
-FI_EOPNOTSUPP
L'opération atomique demandée n'est pas prise en charge sur ce point d'extrémité.
-FI_EMSGSIZE
Le nombre d'opérations atomiques dans une seule requête dépasse celui pris en charge par le fournisseur sous-jacent.

NOTES

Les opérations atomiques opèrent sur un tableau de valeurs d'un type de données spécifique. L'atomicité n'est garantie que pour chaque opération de type de données, et non sur l'ensemble du tableau. Le pseudo-code suivant illustre cette opération pour une écriture atomique non signée sur 64 bits. ATOMIC_WRITE_U64 est une macro dépendante de la plateforme qui écrit atomiquement 8 octets dans un emplacement mémoire aligné.

fi_atomic(ep, buf, count, NULL, dest_addr, addr, key,
      FI_UINT64, FI_ATOMIC_WRITE, context)
{
    for (i = 1; i < count; i ++)
        ATOMIC_WRITE_U64(((uint64_t *) addr)[i],
                 ((uint64_t *) buf)[i]);
}

Le nombre d'éléments du tableau sur lesquels opérer est spécifié via un paramètre count. Celui-ci doit être compris entre 1 et le maximum renvoyé via l'opération valide pertinente, inclus. L'opération demandée et le type de données doivent également être valides pour le fournisseur donné.

L'ordre des opérations atomiques transportées dans le cadre de différents messages de requête est soumis aux définitions d'ordre des messages et des données attribuées aux points d'extrémité émetteur et récepteur. L'ordre des messages et des données sont tous deux requis si les résultats de deux opérations atomiques vers les mêmes tampons de données doivent refléter la seconde opération agissant sur les résultats de la première. Voir fi_endpoint(3) pour plus de détails et les restrictions de taille des messages.
