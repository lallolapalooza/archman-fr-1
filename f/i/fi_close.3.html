DESCRIPTIO

N

Un domaine d'accès fait généralement référence à une carte réseau physique ou virtuelle ou à un port matériel ; cependant, un domaine peut s'étendre sur plusieurs composants matériels à des fins de basculement ou de répartition des données. Un domaine définit la limite pour associer différentes ressources ensemble. Les ressources de tissu appartenant au même domaine peuvent partager des

ressources.

fi_set_op

s

fi_set_ops assigne des rappels qu'un fournisseur doit invoquer à la place de l'exécution de tâches sélectionnées. Cela permet aux utilisateurs de modifier ou de contrôler le comportement par défaut d'un fournisseur. Conceptuellement, cela permet à l'utilisateur d'intercepter des fonctions spécifiques utilisées par un fournisseur et de les remplacer par les

siennes.

Les opérations modifiées sont identifiées à l'aide d'une chaîne de caractères bien connue, passée en paramètre name. Le format du paramètre ops dépend de la valeur de name. Le paramètre ops fera référence à une structure contenant les rappels et autres champs nécessaires au fournisseur pour invoquer les fonctions de

l'utilisateur.

Si un fournisseur accepte le remplacement, il renverra FI_SUCCESS. Si le remplacement est inconnu ou non pris en charge, le fournisseur renverra -FI_ENOSYS. Les remplacements doivent être définis avant d'allouer des ressources sur le

domaine.

Les opérations fi_set_ops suivantes et les structures de rappel correspondantes sont

définies.

Support multi-thread

(threading)

Le modèle de threading spécifie le niveau de sérialisation requis d'une application lors de l'utilisation des interfaces de transfert de données de libfabric. Les interfaces de contrôle sont toujours considérées comme thread-safe, sauf si le modèle de progression de contrôle est FI_PROGRESS_CONTROL_UNIFIED. Une interface de contrôle thread-safe permet à plusieurs threads de faire progresser l'interface de contrôle et (selon le modèle de threading sélectionné) à un ou plusieurs threads de faire progresser les interfaces de données en même temps. Les applications qui peuvent garantir la sérialisation dans leur accès aux ressources et interfaces allouées par le fournisseur permettent à un fournisseur d'éliminer les verrous de bas

niveau.
FI_THREAD_COMPLET
ION
Le modèle de threading par complétion est le mieux adapté aux applications multi-thread utilisant des points de terminaison évolutifs (scalable endpoints) qui souhaitent un fonction
nement sans verrou. Les applications doivent sérialiser l'accès à tous les objets qui sont associés par un mécanisme de complétion commun (par exemple, les contextes d'émission et de
réception liés au même CQ ou compteur). Il est recommandé que les fournisseurs qui prennent en charge les points de terminaison évolutifs prennent en charge ce modèle de threading.

Les applications souhaitant tirer parti de FI_THREAD_COMPLETION doivent dédier les contextes d'émission, les contextes de réception, les files de complétion et les compteurs à des threads

individuels.
FI_THREAD_DOM
AIN
Le modèle de threading de domaine est le mieux adapté aux applications mono-thread et aux applications multi-thread utilisant des points de terminaison standard qui souhaitent un fonctionnement sans verrou. Les applications doivent sérialiser l'accès à tous les objets sous le même domaine. Cela inclut les points de terminaison, les contextes d'émission et de réception, les files de complétion et les compteurs, et les régions de mémoire
enregistrées.
FI_THREAD_ENDPOINT
(obsolète)
Le modèle de threading de point de terminaison est similaire à FI_THREAD_FID, mais avec la restriction supplémentaire que la sérialisation est requise lors de l'accès au même point de terminaison, même si plusieurs contextes d'émission et de réception sont
utilisés.
FI_THREAD_FID
(obsolète)
Un modèle de sérialisation de descripteur de tissu (FID) requiert des applications qu'elles sérialisent l'accès aux ressources de tissu individuelles associées aux opérations de transfert de données et aux complétions. Pour l'accès au point de terminaison, la sérialisation n'est requise que lors de l'accès au même flux de données de point de terminaison. Plusieurs threads peuvent initier des transferts sur différents contextes d'émission ou le même point de terminaison sans sérialisation, et aucune sérialisation n'est requise entre la soumission des requêtes de transmission de données et les opérations de réception de
données.
FI_THREAD_SA
FE
Un modèle de sérialisation thread-safe permet à une application multi-thread d'accéder à toutes les ressources allouées via n'importe quelle interface sans restriction. Tous les fournisseurs doivent prendre en charge
FI_THREAD_SAFE.
FI_THREAD_UNS
PEC
Cette valeur indique qu'aucun modèle de threading n'a été défini. El
le peut être utilisée sur les indications d'entrée de l'appel fi_ge
tinfo. Lorsqu'elle est spécifiée, les fournisseurs retourneront un
modèle de threading qui permet le plus grand niveau de parallélisme.

Modèles de progression

(progress)

La progression est la capacité de l'implémentation sous-jacente à terminer le traitement d'une requête asynchrone. Dans de nombreux cas, le traitement d'une requête asynchrone nécessite l'utilisation du processeur hôte. Par exemple, un message reçu peut avoir besoin d'être apparié avec le bon tampon, ou une requête ayant expiré peut avoir besoin d'être retransmise. Pour des raisons de performance, il peut être indésirable pour le fournisseur d'allouer un thread à cette fin, qui entrerait en concurrence avec les threads de

l'application.

La progression de contrôle indique la méthode que le fournisseur utilise pour faire progresser les opérations de contrôle asynchrones. Les opérations de contrôle sont des fonctions qui n'impliquent pas directement le transfert de données d'application entre les points de terminaison. Elles incluent les routines de vecteur d'adresses, d'enregistrement de mémoire et de gestion de

connexion.

La progression de données indique la méthode que le fournisseur utilise pour faire progresser les opérations de transfert de données. Cela inclut les opérations de file de messages, RMA, messagerie étiquetée et atomiques, ainsi que leur traitement de

complétion.

Le champ progress définit le comportement des opérations de contrôle et de données. Pour les applications nécessitant une portabilité de compilation entre les séries libfabric version 1 et version 2, le champ progress peut être référencé comme

data_progress.

La progression nécessite fréquemment qu'une action soit prise à la fois du côté de la transmission et du côté de la réception d'une opération. C'est souvent une exigence pour les transferts fiables, en raison du traitement des reconnaissements et des retransmissions

.

Pour équilibrer entre performance et facilité d'utilisation, les modèles de progression suivants sont

définis.
FI_PROGRESS_A
UTO
Ce modèle de progression indique que le fournisseur fera progresser une opération asynchrone sans intervention supplémentaire de l'ap
plication. Lorsque FI_PROGRESS_AUTO est fourni en sortie de fi_getinfo en l'absence d'indications de progression, cela indique souvent
que la fonctionnalité souhaitée est implémentée par le matériel du fournisseur ou est un service standard du système d'exploitation.

Il est recommandé que les fournisseurs prennent en charge FI_PROGRESS_AUTO. Cependant, si un fournisseur ne prend pas en charge nativement la progression automatique, le fait de forcer l'utilisation de FI_PROGRESS_AUTO peut entraîner l'allocation de threads sous les interfaces de

tissu.

Notez que les versions précédentes de la bibliothèque exigeaient que les fournisseurs prennent en charge FI_PROGRESS_AUTO. Cependant, dans certains cas, les threads de progression ne peuvent pas être bloqués lorsque la communication est inactive, ce qui entraîne des threads tournant en boucle dans les fonctions de progression. Par conséquent, ces fournisseurs ne prenaient en charge que FI_PROGRESS_MANUAL

.
FI_PROGRESS_MAN
UAL
Ce modèle de progression indique que le fournisseur nécessite l'utilisation d'un thread d'application pour terminer une requête asynchrone. Lorsque la progression manuelle est définie, l
e fournisseur tentera de faire avancer une opération asynchrone lorsque l'application tente d'attendre ou de lire une file d'événements, une file de complétion ou un compteur où l'opérati
on terminée sera signalée. La progression se produit également lorsque l'application traite un ensemble de sondage ou d'attente qui a été associé à la file d'événements ou de complétion.

Seules les opérations d'attente définies par l'interface de tissu entraîneront la progression d'une opération. Les fonctions d'attente du système d'exploitation ou externes, telles que select, poll ou les routines pthread, ne le peuvent

pas.

Les exigences de progression manuelle ne s'appliquent pas seulement aux points de terminaison qui initient des opérations d'émission, mais aussi aux points de terminaison qui peuvent être la cible de telles opérations. Cela reste vrai même si le point de terminaison cible ne générera pas d'événements de complétion pour les opérations. Par exemple, un point de terminaison qui agit purement comme cible d'opérations RMA ou atomiques utilisant la progression manuelle peut encore avoir besoin de l'assistance de l'application pour traiter les opérations

reçues.
FI_PROGRESS_CONTROL_UNIF
IED
Ce modèle de progression indique que l'utilisateur synchronisera lui-même la progression des opérations de données et de contrôle (c.-à-d. cela permet à l'interface de contrôle de NE PAS être thread-safe). Cela implique une progression manuelle, et lorsqu'il est combiné avec threading=FI_THREAD_DOMAIN/FI_THREAD_COMPLETION, cela permet à Libfabric d'éliminer tous les verrouillages dans le chemin critique de progression des
données.
FI_PROGRESS_UNS
PEC
Cette valeur indique qu'aucun modèle
de progression n'a été défini. Elle
peut être utilisée sur les indicat
ions d'entrée de l'appel fi_getinfo.

Gestion des ressources

(resource_mgmt)

La gestion des ressources (RM) est le support du fournisseur et du protocole pour protéger contre le débordement des ressources locales et distantes. Cela inclut les contextes d'émission et de réception locaux et distants, les files de complétion, et les tampons de données source et

cible.

Lorsqu'elle est activée, l'application reçoit un certain niveau de protection contre le débordement des files d'attente du fournisseur et des tampons de données locaux et distants. Un tel support peut être intégré directement dans le matériel et/ou le protocole réseau, mais peut également nécessiter que des vérifications soient activées dans le logiciel du fournisseur. En désactivant la gestion des ressources, l'application assume toute la responsabilité de prévenir les débordements des files et des tampons, mais le faire peut permettre à un fournisseur d'éliminer les appels de synchronisation internes, tels que les variables atomiques ou les

verrous.

Il convient de noter que même si la gestion des ressources est désactivée, l'implémentation du fournisseur et le protocole peuvent toujours fournir un certain niveau de protection contre les débordements. Cependant, une telle protection n'est pas garantie. Les valeurs suivantes pour la gestion des ressources sont

définies.
FI_RM_DISABL
ED
Le fournisseur est libre de sélectionner une implémentation et un protocole qui ne protègent pas contre le débordement des ressources. L'application est responsable de la protection des
ressources.

ED

fournisseur.

Rx

Les fournisseurs peuvent soit tronquer le message et signaler un achèvement réussi, soit faire échouer l'opération. Pour les points de terminaison de type datagramme, les envois échoués entraîneront l'abandon du message. Lorsqu'une erreur de gestion des ressources se produit sur un point de terminaison connecté, le point de terminaison passera à un état désactivé et la connexion sera démantelée. Un point de terminaison désactivé abandonnera toute opération en file d'attente ou en

cours.

Le comportement des erreurs de gestion des ressources sur les points de terminaison sans état dépend du type d'erreur. Si la GR est désactivée et que l'une des erreurs suivantes se produit, le point de terminaison sera désactivé : Ctx Tx, Ctx Rx, CQ Tx ou CQ Rx. Pour les autres erreurs (EP cible, pas de tampon Rx, etc.), l'opération peut échouer, mais le point de terminaison restera activé. Un point de terminaison désactivé abandonnera ou fera échouer toute opération en file d'attente ou en cours. De plus, un point de terminaison désactivé doit être réactivé avant d'accepter de nouvelles opérations de transfert de

données.

Il existe une restriction notable sur les protections offertes par la gestion des ressources. Cela se produit lorsque la gestion des ressources est activée sur un point de terminaison qui a été lié à une ou plusieurs files d'achèvement à l'aide de l'indicateur FI_SELECTIVE_COMPLETION. Les opérations affichées sur un tel point de terminaison peuvent spécifier qu'un achèveme

nt réussi ne doit pas générer d'entrée dans la file d'achèvement correspondante. (C'est-à-dire que l'opération laisse l'indicateur FI_COMPLETION non défini). Dans de telles situations, le fournisseur n'est pas tenu de réserver une entrée dans la file d'achèvement pour gérer le cas où l'opération échoue et génère effectivement une entrée de CQ, ce qui nécessiterait effectiv
ement de suivre l'opération jusqu'à son achèvement. Les applications soucieuses d'éviter les débordements de CQ en cas d'erreurs doivent s'assurer qu'il y a suffisamment d'espace dans la CQ pour signaler les opérations échouées. Cela peut généralement être atteint en dimensionnant la CQ à au moins la même taille que la ou les files du point de terminaison qui y sont liées.

Mode d'enregistrement mémoire (mr_mode)

Définit les bits de mode spécifiques à l'enregistrement mémoire utilisés avec ce domaine. Les détails complets sur les options du mode MR sont disponibles dans fi_mr(3). Les valeurs suivantes peuvent être spécifiées.

FI_MR_ALLOCATED
Indique que l'enregistrement mémoire s'effectue sur des tampons de données alloués, et que des pages physiques doivent couvrir toutes les adresses virtuelles enregistrées.
FI_MR_COLLECTIVE
Exige que les tampons de données passés aux opérations collectives soient explicitement enregistrés pour les opérations collectives à l'aide du drapeau FI_COLLECTIVE.
FI_MR_ENDPOINT
L'enregistrement mémoire s'effectue au niveau du point de terminaison, plutôt qu'au niveau du domaine.
FI_MR_LOCAL
Le fournisseur est optimisé pour que les applications enregistrent la mémoire des tampons de données accessibles localement. Les tampons de données utilisés dans les opérations d'envoi et de réception et comme tampon source pour les opérations RMA et atomiques doivent être enregistrés par l'application pour les domaines d'accès ouverts avec cette capacité.
FI_MR_MMU_NOTIFY
Indique que l'application est responsable de notifier le fournisseur lorsque les tables de pages référençant une région mémoire enregistrée peuvent avoir été mises à jour.
FI_MR_PROV_KEY
Les clés d'enregistrement mémoire sont sélectionnées et retournées par le fournisseur.
FI_MR_RAW
Le fournisseur nécessite une configuration supplémentaire dans le cadre de son processus d'enregistrement mémoire. Ce mode est requis par les fournisseurs qui utilisent une clé mémoire de plus de 64 bits.
FI_MR_RMA_EVENT
Indique que les régions mémoire associées aux compteurs de complétion doivent être explicitement activées après avoir été liées à un compteur.
FI_MR_UNSPEC (obsolète)
Défini pour des raisons de compatibilité - versions 1.4 et antérieures de la bibliothèque. Définir mr_mode à 0 indique que FI_MR_BASIC ou FI_MR_SCALABLE sont demandés et supportés.
FI_MR_VIRT_ADDR
Les régions mémoire enregistrées sont référencées par les pairs en utilisant l'adresse virtuelle de la région mémoire enregistrée, plutôt qu'un décalage basé sur 0.
FI_MR_BASIC (obsolète)
Défini pour des raisons de compatibilité - versions 1.4 et antérieures de la bibliothèque. Seules des opérations d'enregistrement mémoire basiques sont demandées ou supportées. Ce mode est équivalent à la définition des drapeaux FI_MR_VIRT_ADDR, FI_MR_ALLOCATED et FI_MR_PROV_KEY dans les versions ultérieures de la bibliothèque. Ce drapeau ne peut pas être utilisé conjointement avec d'autres bits de mr_mode.
FI_MR_SCALABLE (obsolète)
Défini pour des raisons de compatibilité - versions 1.4 et antérieures de la bibliothèque. Seules des opérations d'enregistrement mémoire évolutives sont demandées ou supportées. L'enregistrement évolutif utilise une adressage basé sur décalage, avec des clés mémoire sélectionnables par l'application. Pour les versions 1.5 et ultérieures de la bibliothèque, c'est le comportement par défaut si aucun bit de mr_mode n'est défini. Ce drapeau ne peut pas être utilisé conjointement avec d'autres bits de mr_mode.

Les tampons utilisés dans les opérations de transfert de données peuvent nécessiter de notifier le fournisseur de leur utilisation avant qu'un transfert de données ne puisse avoir lieu. Le champ mr_mode indique le type d'enregistrement mémoire requis et quand l'enregistrement est nécessaire. Les applications qui nécessitent l'utilisation d'un mode d'enregistrement spécifique doivent définir l'attribut de domaine mr_mode à la valeur nécessaire lors de l'appel à fi_getinfo. La valeur FI_MR_UNSPEC peut être utilisée pour indiquer la prise en charge de n'importe quel mode d'enregistrement.

Taille Clé MR (mr_key_size)

Taille de la clé d'accès à distance de la région mémoire, en octets. Les applications qui demandent leur propre clé MR doivent sélectionner une valeur dans la plage spécifiée par cette valeur. Les tailles de clé supérieures à 8 octets nécessitent l'utilisation du bit de mode FI_RAW_KEY.

Taille Données CQ (cq_data_size)

Les applications peuvent inclure un petit message avec un transfert de données qui est placé directement dans une file d'attente de complétion distante dans le cadre d'un événement de complétion. Ceci est appelé données CQ distantes (parfois appelées données immédiates). Ce champ indique le nombre d'octets que le fournisseur supporte pour les données CQ distantes. Si supporté (une valeur non nulle est retournée), la taille minimale des données CQ distantes doit être d'au moins 4 octets.

Nombre File d'attente Complétion (cq_cnt)

Le nombre optimal de files d'attente de complétion supportées par le domaine, par rapport à tous les attributs de CQ spécifiés ou par défaut. La valeur cq_cnt peut être une valeur fixe du nombre maximum de CQ supportées par le matériel sous-jacent, ou une valeur dynamique, basée sur les attributs par défaut d'un CQ alloué, tels que la taille et le format des données du CQ.

Nombre Points terminaison (ep_cnt)

Le nombre total de points de terminaison supportés par le domaine, par rapport à tous les attributs de points de terminaison spécifiés ou par défaut. La valeur ep_cnt peut être une valeur fixe du nombre maximum de points de terminaison supportés par le matériel sous-jacent, ou une valeur dynamique, basée sur les attributs par défaut d'un point de terminaison alloué, tels que les capacités et la taille du point de terminaison. Le nombre de points de terminaison est le nombre de points de terminaison adressables supportés par le fournisseur. Les fournisseurs retournent des limites de capacité basées sur les capacités maximales configurées du matériel. Les fournisseurs ne peuvent pas prédire toutes les limitations système possibles sans connaissance a posteriori acquise pendant l'exécution qui limitera davantage ces maximums matériels (par exemple, consommation de mémoire de l'application, utilisation de FD, etc.).

Nombre Contexte Transmission (tx_ctx_cnt)

Le nombre de files d'attente de commandes sortantes optimalement supportées par le fournisseur. Pour un fournisseur de bas niveau, cela représente le nombre de files d'attente de commandes vers le matériel et/ou le nombre de moteurs de transmission parallèles effectivement supportés par le matériel et les caches. Les applications qui allouent plus de contextes de transmission que cette valeur finiront par partager les ressources sous-jacentes. Par défaut, il y a un seul contexte de transmission associé à chaque point de terminaison, mais dans un modèle d'utilisation avancé, un point de terminaison peut être configuré avec plusieurs contextes de transmission.

Nombre Contexte Réception (rx_ctx_cnt)

Le nombre de files d'attente de traitement entrantes optimalement supportées par le fournisseur. Pour un fournisseur de bas niveau, cela représente le nombre de files d'attente matérielles qui peuvent être effectivement utilisées pour traiter les paquets entrants. Les applications qui allouent plus de contextes de réception que cette valeur finiront par partager les ressources sous-jacentes. Par défaut, un seul contexte de réception est associé à chaque point de terminaison, mais dans un modèle d'utilisation avancé, un point de terminaison peut être configuré avec plusieurs contextes de réception.

Contexte Transmission Point terminaison Max (max_ep_tx_ctx)

Le nombre maximum de contextes de transmission qui peuvent être associés à un point de terminaison.

Contexte Réception Point terminaison Max (max_ep_rx_ctx)

Le nombre maximum de contextes de réception qui peuvent être associés à un point de terminaison.

Partage Max Contexte Transmission (max_ep_stx_ctx)

Le nombre maximum de points de terminaison qui peuvent être associés à un contexte de transmission partagé.

Partage Max Contexte Réception (max_ep_srx_ctx)

Le nombre maximum de points de terminaison qui peuvent être associés à un contexte de réception partagé.

Nombre Compteurs (cntr_cnt)

Le nombre optimal de compteurs de complétion supportés par le domaine. La valeur cq_cnt peut être une valeur fixe du nombre maximum de compteurs supportés par le matériel sous-jacent, ou une valeur dynamique, basée sur les attributs par défaut du domaine.

Limite MR IOV (mr_iov_limit)

C'est le nombre maximum de vecteurs IO (éléments scatter-gather) qu'une seule opération d'enregistrement mémoire peut référencer.

FI_AV_USER_ID

NOM

fi_close - fermer un domaine Fabric

SYNOPSIS

#include <rdma/fabric.h>
int fi_close(struct fi_info *info);

ARGUMENTS

info
Structure des informations du domaine Fabric à fermer. Ceci est généralement obtenu par un appel à fi_getinfo.

DESCRIPTION

La fonction fi_close est utilisée pour libérer toutes les ressources associées à un domaine Fabric. Cela inclut tous les points d'extrémité, les régions de mémoire, les files d'attente d'événements de complétion et les vecteurs d'adresses qui ont été créés avec le domaine. L'appelant est responsable de la fermeture de tous les objets créés à partir d'un domaine avant d'appeler fi_close sur le domaine lui-même.

La structure fi_info passée à fi_close doit contenir un pointeur vers une structure fi_fabric valide qui a été retournée par fi_getinfo.

Les ressources suivantes sont associées aux domaines:

Points d'extrémité actifs
Régions de mémoire
Files d'attente d'événements de complétion
Vecteurs d'adresses

Les appelants doivent fermer tous les objets créés à partir d'un domaine avant d'appeler fi_close sur le domaine lui-même. L'ordre de fermeture des objets est le suivant:

  1. Vecteurs d'adresses (AV)
  2. Files d'attente d'événements de complétion (CQ et EQ)
  3. Régions de mémoire (MR)
  4. Points d'extrémité (EP)
  5. Domaine Fabric

Les fournisseurs doivent s'assurer que toutes les ressources associées à un domaine sont libérées lorsqu'un domaine est fermé. Cela inclut toute mémoire allouée, handles de périphériques, etc.

DOMAIN ATTRIBUTES

La structure fi_info utilisée par fi_close contient plusieurs attributs qui décrivent les capacités et les limitations du domaine Fabric sous-jacent. Ces attributs sont généralement définis par un appel à fi_getinfo et sont utilisés par le programmeur pour comprendre ce que le domaine peut supporter.

Les attributs suivants sont pertinents pour la compréhension des domaines Fabric:

Fabric_Version (fabric_ver)
Version de l'API Fabric.
Maximum_Endpoints (max_ep)
Nombre maximum de points d'extrémité qui peuvent être créés dans le domaine.
Maximum_Completion_Queues (max_cq)
Nombre maximum de files d'attente de complétion qui peuvent être créées dans le domaine.
Maximum_Address_Vectors (max_av)
Nombre maximum de vecteurs d'adresses qui peuvent être créés dans le domaine.
Maximum_Memory_Regions (max_mr)
Nombre maximum de régions de mémoire qui peuvent être enregistrées dans le domaine.
Maximum_Completion_Queue_Entries (max_cq_size)
Nombre maximum d'entrées dans une file d'attente de complétion.
Maximum_Event_Queue_Entries (max_eq_size)
Nombre maximum d'entrées dans une file d'attente d'événements.
Maximum_Message_Size (max_msg_size)
Taille maximale d'un message qui peut être envoyé ou reçu dans le domaine.
Maximum_Initiator_Depth (max_initiator_depth)
Profondeur maximale des opérations d'initiation qui peuvent être en attente sur un point d'extrémité.
Maximum_Responder_Resources (max_responder_resources)
Nombre maximal de ressources répondant qui peuvent être allouées pour un point d'extrémité.
Domain_Capabilities (domain_cap)
Capacités du domaine Fabric. Les bits suivants sont pris en charge:
FI_MSG
Le domaine prend en charge les opérations de messagerie.
FI_RDM
Le domaine prend en charge les opérations de datagrammes à fiabilité modérée.
FI_DIRECTED_RECV
Le domaine prend en charge la réception directe vers une file d'attente de réception spécifique.
FI_TAGGED_RECV
Le domaine prend en charge la réception étiquetée.
FI_WRITE, FI_READ
Le domaine prend en charge les opérations d'écriture et de lecture à accès direct.
FI_ATOMIC
Le domaine prend en charge les opérations atomiques.
FI_REMOTE_CQ_ACCESS
Le domaine prend en charge l'accès distant aux files d'attente de complétion.
FI_CQ_ENTRY_REF
Le domaine prend en charge la référence des entrées de file d'attente de complétion.
FI_EQ_READ_NEVER
Ne pas utiliser d'opérations de lecture sur les files d'attente d'événements lors de l'ouverture d'une CQ, d'un compteur et d'une file d'attente de réception partagée.

Les capacités secondaires prises en charge sont les suivantes:

FI_LOCAL_COMM
Au niveau conceptuel, ce champ indique que le périphérique sous-jacent prend en charge la communication en boucle arrière (loopback). Plus spécifiquement, ce champ indique qu'un point d'extrémité peut communiquer avec d'autres points d'extrémité qui sont alloués à partir du même domaine nommé sous-jacent. Si ce champ n'est pas défini, une application peut avoir besoin d'utiliser un domaine ou un mécanisme alternatif (par exemple, mémoire partagée) pour communiquer avec des pairs qui s'exécutent sur le même nœud.
FI_REMOTE_COMM
Ce champ indique que le fournisseur sous-jacent prend en charge la communication avec des nœuds accessibles sur le réseau. Si ce champ n'est pas défini, alors le fournisseur ne prend en charge que la communication entre les processus qui s'exécutent sur le même nœud - un fournisseur de mémoire partagée, par exemple.
FI_SHARED_AV
Indique que le domaine prend en charge la capacité de partager des vecteurs d'adresses entre plusieurs processus en utilisant la fonctionnalité de vecteur d'adresses nommé.

Voir fi_getinfo(3) pour une discussion sur les capacités primaires par rapport aux capacités secondaires.

Clé d'autorisation par défaut (auth_key)

La clé d'autorisation par défaut à associer aux points d'extrémité et aux enregistrements de mémoire créés dans le domaine. Ce champ est ignoré à moins que le fabric ne soit ouvert avec la version d'API 1.5 ou supérieure.

Si domain auth_key_size est défini sur la valeur FI_AV_AUTH_KEY, auth_key doit être NULL.

Longueur de la clé d'autorisation par défaut (auth_key_size)

La longueur en octets de la clé d'autorisation par défaut pour le domaine. Si elle est définie sur 0, alors aucune clé d'autorisation ne sera associée aux points d'extrémité et aux enregistrements de mémoire créés dans le domaine, sauf indication contraire dans les attributs du point d'extrémité ou de l'enregistrement de mémoire. Ce champ est ignoré à moins que le fabric ne soit ouvert avec la version d'API 1.5 ou supérieure.

Si la taille est définie sur la valeur FI_AV_AUTH_KEY, tous les points d'extrémité et toutes les régions de mémoire seront configurés pour utiliser des clés d'autorisation associées à l'AV. Les fournisseurs qui prennent en charge les clés d'autorisation et les points d'extrémité sans connexion doivent prendre en charge cette option.

Taille maximale des données d'erreur (max_err_data)

La quantité maximale de données d'erreur, en octets, qui peuvent être renvoyées dans le cadre d'une complétion ou d'une erreur de file d'attente d'événements. Cette valeur correspond au champ err_data_size dans struct fi_cq_err_entry et struct fi_eq_err_entry.

Nombre de régions de mémoire (mr_cnt)

Le nombre optimal de régions de mémoire prises en charge par le domaine, ou le point d'extrémité si le bit mr_mode FI_MR_ENDPOINT a été défini. La valeur mr_cnt peut être une valeur fixe du nombre maximal de MR prises en charge par le matériel sous-jacent, ou peut être une valeur dynamique, basée sur les attributs par défaut du domaine, tels que les modes d'enregistrement de mémoire pris en charge. Les applications peuvent définir mr_cnt en entrée de fi_getinfo, afin d'indiquer leurs exigences en matière d'enregistrement de mémoire. Cela peut permettre au fournisseur d'optimiser les tables de cache ou de recherche d'enregistrement de mémoire.

Classe de trafic (tclass)

Ceci spécifie la classe de trafic par défaut qui sera associée à tout point d'extrémité créé dans le domaine. Voir fi_endpoint(3) pour des informations supplémentaires.

Nombre maximal de clés d'autorisation par point d'extrémité (max_ep_auth_key)

Le nombre maximal de clés d'autorisation pouvant être prises en charge par point d'extrémité sans connexion.

Identifiant maximal de groupe de pairs (max_group_id)

La valeur maximale qui peut être attribuée à un groupe de pairs, inclusivement. Les identifiants de groupe de pairs valides doivent être compris entre 0 et max_group_id. Voir fi_av(3) pour des informations supplémentaires sur les groupes de pairs et leur utilisation. Les utilisateurs peuvent demander la prise en charge des groupes de pairs en définissant ceci sur une valeur non nulle. Les fournisseurs qui ne peuvent pas répondre à la valeur max_group_id demandée échoueront lors de l'appel à fi_getinfo(). En sortie, les fournisseurs peuvent retourner une valeur supérieure à celle demandée par l'application.

VALEUR DE RETOUR

Retourne 0 en cas de succès. En cas d'erreur, une valeur négative correspondant à un errno Fabric est retournée. Les valeurs d'errno Fabric sont définies dans rdma/fi_errno.h.

NOTES

Les utilisateurs doivent appeler fi_close pour libérer toutes les ressources allouées au domaine Fabric.

Les ressources Fabric suivantes sont associées aux domaines: points d'extrémité actifs, régions de mémoire, files d'attente d'événements de complétion et vecteurs d'adresses.

Les attributs du domaine reflètent les limitations et les capacités du matériel et/ou du fournisseur logiciel sous-jacent. Ils ne reflètent pas les limitations du système, telles que le nombre de pages physiques qu'une application peut épingler ou le nombre de descripteurs de fichiers que l'application peut ouvrir. Par conséquent, les maximums signalés peuvent ne pas être réalisables, même sur des systèmes légèrement chargés, sans qu'un administrateur ne configure correctement les ressources système pour les fournisseurs installés.
