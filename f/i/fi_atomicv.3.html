DESCRIPTIO

N

Les transferts atomiques sont utilisés pour lire et mettre à jour des données situées dans des régions de mémoire distantes de manière atomique. Conceptuellement, ils sont similaires aux opérations atomiques locales de nature similaire (par ex. incrémentation atomique, échange conditionnel, etc.). Les mises à jour des données distantes impliquent l'une de plusieurs opérations sur les données et agissent sur des types de données spécifiques, comme listés ci-dessous. En tant que tel, les transferts atomiques ont connaissance du format des données étant accédées. Une fonction atomique unique peut opérer sur un tableau de données en appliquant une opération atomique à chaque entrée, mais l'atomicité d'une opération est limitée à un seul type de données ou

entrée.

Opérations atomiques

Les opérations atomiques suivantes sont définies. Une opération atomique agit souvent sur une valeur cible dans le tampon de mémoire distant et une valeur source fournie avec la fonction atomique. Elle peut également transporter des données source pour remplacer la valeur cible dans les opérations de comparaison et d'échange (compare and swap). Une description conceptuelle de chaque opération est fournie.

FI_MIN
Minimum
if (buf[i] < addr[i])
    addr[i] = buf[i]
FI_MAX
Maximum
if (buf[i] > addr[i])
    addr[i] = buf[i]
FI_SUM
Somme
addr[i] = addr[i] + buf[i]
FI_PROD
Produit
addr[i] = addr[i] * buf[i]
FI_LOR
OU logique
addr[i] = (addr[i] || buf[i])
FI_LAND
ET logique
addr[i] = (addr[i] && buf[i])
FI_BOR
OU bit à bit
addr[i] = addr[i] | buf[i]
FI_BAND
ET bit à bit
addr[i] = addr[i] & buf[i]
FI_LXOR
OU exclusif logique (XOR)
addr[i] = ((addr[i] && !buf[i]) || (!addr[i] && buf[i]))
FI_BXOR
OU exclusif bit à bit (XOR)
addr[i] = addr[i] ^ buf[i]
FI_ATOMIC_READ
Lire des données de manière atomique
result[i] = addr[i]
FI_ATOMIC_WRITE
Écrire des données de manière atomique
addr[i] = buf[i]
FI_CSWAP
Comparer les valeurs et, si elles sont égales, échanger avec les données
if (compare[i] == addr[i])
    addr[i] = buf[i]
FI_CSWAP_NE
Comparer les valeurs et, si elles ne sont pas égales, échanger avec les données
if (compare[i] != addr[i])
    addr[i] = buf[i]
FI_CSWAP_LE
Comparer les valeurs et, si l'une est inférieure ou égale, échanger avec les données
if (compare[i] <= addr[i])
    addr[i] = buf[i]
FI_CSWAP_LT
Comparer les valeurs et, si l'une est inférieure, échanger avec les données
if (compare[i] < addr[i])
    addr[i] = buf[i]
FI_CSWAP_GE
Comparer les valeurs et, si l'une est supérieure ou égale, échanger avec les données
if (compare[i] >= addr[i])
    addr[i] = buf[i]
FI_CSWAP_GT
Comparer les valeurs et, si l'une est supérieure, échanger avec les données
if (compare[i] > addr[i])
    addr[i] = buf[i]
FI_MSWAP
Échanger les bits masqués avec les données
addr[i] = (buf[i] & compare[i]) | (addr[i] & ~compare[i])
FI_DIFF
Calculer la différence
addr[i] = addr[i] - buf[i]

Fonctions atomiques de base

Les fonctions atomiques de base – fi_atomic, fi_atomicv, fi_atomicmsg – sont utilisées pour transmettre des données à un nœud distant, où l'opération atomique spécifiée est effectuée sur les données cibles. Le résultat d'une fonction atomique de base est stocké dans la région de mémoire distante. La principale différence entre les fonctions atomiques réside dans le nombre et le type de paramètres qu'elles acceptent en entrée. Sinon, elles effectuent la même fonction générale.

L'appel fi_atomic transfère les données contenues dans le tampon de données spécifié par l'utilisateur vers un nœud distant. Pour les points d'extrémité sans connexion, le point d'extrémité de destination est spécifié via le paramètre dest_addr. Sauf si le point d'extrémité a été configuré différemment, le tampon de données passé à fi_atomic ne doit pas être modifié par l'application tant que l'appel fi_atomic n'est pas terminé de manière asynchrone. Le tampon cible d'une opération atomique de base doit permettre un accès en lecture et/ou en écriture à distance, selon le cas.

L'appel fi_atomicv ajoute la prise en charge d'une liste scatter-gather à fi_atomic. fi_atomicv transfère l'ensemble des tampons de données référencés par le paramètre ioc vers un nœud distant pour traitement.

L'appel fi_inject_atomic est une version optimisée de fi_atomic. La fonction fi_inject_atomic se comporte comme si le drapeau de transfert FI_INJECT était défini et que FI_COMPLETION ne l'était pas. C'est-à-dire que le tampon de données est disponible pour être réutilisé immédiatement après le retour de fi_inject_atomic, et aucun événement de complétion ne sera généré pour cette opération atomique. L'événement de complétion sera supprimé même si le point d'extrémité n'a pas été configuré avec FI_SELECTIVE_COMPLETION. Voir la discussion sur les drapeaux ci-dessous pour plus de détails. La taille de message demandée pouvant être utilisée avec fi_inject_atomic est limitée par inject_size.

L'appel fi_atomicmsg prend en charge les fonctions atomiques sur les points d'extrémité connectés et sans connexion, avec la possibilité de contrôler l'opération atomique par appel à l'aide de drapeaux. La fonction fi_atomicmsg prend une struct fi_msg_atomic en entrée.

struct fi_msg_atomic {
    const struct fi_ioc *msg_iov; /* local scatter-gather array */
    void                **desc;   /* local access descriptors */
    size_t              iov_count;/* # elements in ioc */
    const void          *addr;    /* optional endpoint address */
    const struct fi_rma_ioc *rma_iov; /* remote SGL */
    size_t              rma_iov_count;/* # elements in remote SGL */
    enum fi_datatype    datatype; /* operand datatype */
    enum fi_op          op;       /* atomic operation */
    void                *context; /* user-defined context */
    uint64_t            data;     /* optional data */
};
struct fi_ioc {
    void        *addr;    /* local address */
    size_t      count;    /* # target operands */
};
struct fi_rma_ioc {
    uint64_t    addr;     /* target address */
    size_t      count;    /* # target operands */
    uint64_t    key;      /* access key */
};

La liste suivante d'opérations atomiques est utilisable avec les opérations atomiques de base : FI_MIN, FI_MAX, FI_SUM, FI_PROD, FI_LOR, FI_LAND, FI_BOR, FI_BAND, FI_LXOR, FI_BXOR et FI_ATOMIC_WRITE.

Fonctions atomiques avec récupération (Fetch-Atomic)

Les fonctions atomiques avec récupération – fi_fetch_atomic, fi_fetch_atomicv et fi_fetch_atomicmsg – se comportent de manière similaire à la fonction atomique de base équivalente. La différence entre les appels atomiques avec récupération et les appels atomiques de base est que les routines atomiques avec récupération renvoient la valeur initiale stockée à la cible à l'utilisateur. La valeur initiale est lue dans le tampon de résultat fourni par l'utilisateur. Le tampon cible des opérations atomiques avec récupération doit être autorisé pour un accès en lecture à distance.

La liste suivante d'opérations atomiques est utilisable avec les opérations atomiques avec récupération : FI_MIN, FI_MAX, FI_SUM, FI_PROD, FI_LOR, FI_LAND, FI_BOR, FI_BAND, FI_LXOR, FI_BXOR, FI_ATOMIC_READ et FI_ATOMIC_WRITE.

Pour les opérations FI_ATOMIC_READ, l'opérande du tampon source (par exemple, le paramètre buf de fi_fetch_atomic) est ignoré et peut être NULL. Les résultats sont écrits dans le tampon de résultat.

Les fonctions atomiques de comparaison – fi_compare_atomic, fi_compare_atomicv et fi_compare_atomicmsg – sont utilisées pour les opérations qui nécessitent de comparer les données cibles à une valeur avant d'effectuer une opération d'échange (swap). Les fonctions atomiques de comparaison prennent en charge : FI_CSWAP, FI_CSWAP_NE, FI_CSWAP_LE, FI_CSWAP_LT, FI_CSWAP_GE, FI_CSWAP_GT et FI_MSWAP.

Fonctions atomiques de validation

Les fonctions atomiques de validation – fi_atomicvalid, fi_fetch_atomicvalid et fi_compare_atomicvalid – indiquent quelles opérations sont prises en charge par le fournisseur local. Les opérations nécessaires qui ne sont pas prises en charge par le fournisseur doivent être émulées par l'application. Chaque appel de validation correspond à un ensemble de fonctions atomiques. fi_atomicvalid vérifie si un fournisseur prend en charge une opération atomique de base spécifique pour un type de données et une opération donnés. fi_fetch_atomicvalid indique si un fournisseur prend en charge une opération atomique de récupération (fetch-atomic) spécifique pour un type de données et une opération donnés. Et fi_compare_atomicvalid vérifie si un fournisseur prend en charge une opération atomique de comparaison (compare-atomic) spécifiée pour un type de données et une opération donnés.

Si une opération est prise en charge, un appel atomique de validation renverra 0, ainsi qu'un nombre d'unités de données atomiques sur lesquelles un seul appel de fonction opérera.

Interrogation des attributs atomiques

L'appel fi_query_atomic agit comme une opération atomique de validation améliorée (voir les définitions des fonctions atomiques de validation ci-dessus). Il est fourni, en partie, pour une extensibilité future. L'opération d'interrogation signale quelles opérations atomiques sont prises en charge par le domaine, pour des points d'extrémité convenablement configurés.

Le comportement de fi_query_atomic est ajusté en fonction du paramètre flags. Si flags vaut 0, l'opération signale les attributs atomiques pris en charge pour les opérations atomiques de base, de manière similaire à fi_atomicvalid pour les points d'extrémité. Si le bit FI_FETCH_ATOMIC de flags est défini, l'opération se comporte de manière similaire à fi_fetch_atomicvalid. De même, le bit FI_COMPARE_ATOMIC fait que l'interrogation agit comme fi_compare_atomicvalid. Les bits FI_FETCH_ATOMIC et FI_COMPARE_ATOMIC ne peuvent pas être définis simultanément.

Si le bit FI_TAGGED est défini, le fournisseur indiquera s'il prend en charge les opérations atomiques vers des tampons de réception étiquetés (tagged). Le bit FI_TAGGED peut être utilisé seul, ou en conjonction avec les drapeaux FI_FETCH_ATOMIC et FI_COMPARE_ATOMIC.

La sortie de fi_query_atomic est struct fi_atomic_attr :

struct fi_atomic_attr {
    size_t count;
    size_t size;
};

Le champ d'attribut count est défini comme pour les appels atomiques de validation. Le champ size indique la taille en octets du type de données atomique. Le champ size est utile pour les types de données dont la taille peut varier selon la plateforme ou le compilateur, tels que FI_LONG_DOUBLE.

Complétions

Les opérations atomiques terminées sont signalées à l'initiateur de la requête via une file d'attente de complétion (CQ) ou un compteur associé. Tout contexte fourni par l'utilisateur spécifié avec la requête sera renvoyé dans le cadre de tout événement de complétion écrit dans une CQ. Voir fi_cq pour les détails des événements de complétion.

Tout résultat renvoyé à l'initiateur dans le cadre d'une opération atomique sera disponible avant la génération d'un événement de complétion. Cela sera vrai même si la sémantique de complétion demandée fournit une garantie plus faible. C'est-à-dire que les opérations atomiques de récupération (fetch) ont une sémantique FI_DELIVERY_COMPLETE. Les complétions générées pour d'autres types d'opérations atomiques indiquent qu'il est sûr de réutiliser les tampons de données sources.

Toute mise à jour des données à la cible d'une opération atomique sera visible par les agents (processus CPU, cartes réseau et autres périphériques) sur le nœud cible avant que l'un des événements suivants ne se produise. Si l'opération atomique génère un événement de complétion ou met à jour un compteur de complétion au point d'extrémité cible, les résultats seront disponibles avant la notification de complétion. Après le traitement d'une complétion pour l'opération atomique, si l'initiateur soumet un transfert entre les mêmes points d'extrémité qui génère une complétion à la cible, les résultats seront disponibles avant l'événement du transfert suivant. Ou, si un transfert de données clôturé (fenced) de l'initiateur suit la requête atomique, les résultats seront disponibles avant une complétion à la cible pour le transfert clôturé.

La correction des opérations atomiques sur une région mémoire cible n'est garantie que lorsqu'elles sont effectuées par un seul acteur pour une fenêtre de temps donnée. Un acteur est défini comme un seul domaine libfabric sur la cible (identifié par le nom du domaine, et non une instance ouverte de ce domaine), un complexe CPU cohérent, ou un autre périphérique (par ex. GPU) capable d'effectuer des opérations atomiques sur la mémoire cible. Les résultats des opérations atomiques effectuées simultanément par plusieurs acteurs sont indéfinis. Par exemple, émettre des opérations atomiques basées sur le CPU vers une région cible mise à jour simultanément par des opérations atomiques basées sur la carte réseau peut laisser les données de la région dans un état inconnu. Les résultats des opérations atomiques d'un premier acteur doivent être visibles par un deuxième acteur avant que ce dernier n'émette ses propres opérations atomiques.

DRAPEAUX

Les appels fi_atomicmsg, fi_fetch_atomicmsg et fi_compare_atomicmsg permettent à l'utilisateur de spécifier des drapeaux qui peuvent modifier l'opération de transfert de données par défaut. Les drapeaux spécifiés avec les opérations de message atomiques remplacent la plupart des drapeaux précédemment configurés avec le point d'extrémité, sauf indication contraire (voir fi_control). La liste suivante de drapeaux est utilisable avec les appels de message atomiques.

FI_COMPLETION
Indique qu'une entrée de complétion doit être générée pour l'opération spécifiée. Le point d'extrémité doit être lié à une file d'attente de complétion avec FI_SELECTIVE_COMPLETION qui correspond à l'opération spécifiée, sinon ce drapeau est ignoré.
FI_MORE
Indique que l'utilisateur a des requêtes supplémentaires qui seront immédiatement postées après le retour de l'appel courant. L'utilisation de ce drapeau peut améliorer les performances en permettant au fournisseur d'optimiser son accès au matériel de fabric.
FI_INJECT
Indique que le contrôle des tampons de données constantes doit être rendu à l'utilisateur immédiatement après le retour de l'appel, même si l'opération est gérée de manière asynchrone. Cela peut nécessiter que l'implémentation du fournisseur sous-jacent copie les données dans un tampon local et effectue le transfert depuis ce tampon. Par tampons de données constantes, on entend tout tampon de données ou iovec utilisé par les API atomiques qui est marqué comme `const'. Les tampons non constants ou de sortie ne sont pas affectés par ce drapeau et peuvent être accédés par le fournisseur à tout moment jusqu'à ce que l'opération soit terminée. Ce drapeau ne peut être utilisé qu'avec des messages plus petits que inject_size.
FI_FENCE
S'applique aux transmissions. Indique que l'opération demandée, également connue sous le nom d'opération clôturée (fenced), et toute opération postée après l'opération clôturée seront différées jusqu'à ce que toutes les opérations précédentes ciblant le même point d'extrémité pair aient été terminées. Les opérations postées après la clôture verront et/ou remplaceront les résultats de toute opération initiée avant l'opération clôturée.

L'ordre des opérations à partir de la publication de l'opération clôturée (inclusive) jusqu'à la publication d'une opération clôturée subsérente (exclusive) est contrôlé par la sémantique d'ordonnancement du point d'extrémité.

FI_TAGGED
Spécifie que la cible de l'opération atomique est un tampon de réception étiqueté (tagged) au lieu d'un tampon RMA. Lorsqu'un tampon étiqueté est la région mémoire cible, le paramètre addr est utilisé comme décalage en octets à base 0 dans le tampon étiqueté, le paramètre key spécifiant le tag.

VALEUR DE RETOUR

Renvoie 0 en cas de succès. En cas d'erreur, une valeur négative correspondant à errno de fabric est renvoyée. Les valeurs de errno de fabric sont définies dans rdma/fi_errno.h.

-FI_EAGAIN
Voir fi_msg(3) pour une description détaillée de la gestion de FI_EAGAIN.
-FI_EOPNOTSUPP
L'opération atomique demandée n'est pas prise en charge sur ce point d'extrémité.
-FI_EMSGSIZE
Le nombre d'opérations atomiques dans une seule requête dépasse celui pris en charge par le fournisseur sous-jacent.

NOTES

Les opérations atomiques opèrent sur un tableau de valeurs d'un type de données spécifique. L'atomicité n'est garantie que pour chaque opération de type de données, et non sur l'ensemble du tableau. Le pseudo-code suivant illustre cette opération pour une écriture atomique non signée de 64 bits. ATOMIC_WRITE_U64 est une macro dépendante de la plateforme qui écrit atomiquement 8 octets à un emplacement mémoire aligné.

fi_atomic(ep, buf, count, NULL, dest_addr, addr, key,
      FI_UINT64, FI_ATOMIC_WRITE, context)
{
    for (i = 1; i < count; i ++)
        ATOMIC_WRITE_U64(((uint64_t *) addr)[i],
                 ((uint64_t *) buf)[i]);
}

Le nombre d'éléments du tableau sur lesquels opérer est spécifié via un paramètre count. Celui-ci doit être compris entre 1 et le maximum renvoyé par l'opération de validation pertinente, inclus. L'opération et le type de données demandés doivent également être valides pour le fournisseur donné.

L'ordre des opérations atomiques transportées dans le cadre de différents messages de requête est soumis aux définitions d'ordonnancement des messages et des données attribuées aux points d'extrémité émetteur et récepteur. Les ordonnancements des messages et des données sont tous deux requis si les résultats de deux opérations atomiques vers les mêmes tampons de données doivent refléter la deuxième opération agissant sur les résultats de la première. Voir fi_endpoint(3) pour plus de détails et les restrictions de taille de message.
