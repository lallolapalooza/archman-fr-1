Filter::Simple(3perl) Guide du programmeur Perl Filter::Simple(3perl)

NOM

Filter::Simple - Filtrage de source simplifié

SYNTAXE

# dans MyFilter.pm :
    package MyFilter;
    use Filter::Simple;
    FILTER { ... };
    # ou simplement :
    #
    # use Filter::Simple sub { ... };
# dans le code de l'utilisateur :
    use MyFilter;
    # ce code est filtré
    no MyFilter;
    # ce code ne l'est pas

DESCRIPTION

Le problème

Le filtrage de source est une fonctionnalité extrêmement puissante des versions récentes de Perl. Il permet d'étendre le langage lui-même (par exemple, le module Switch), de simplifier le langage (par exemple, Language::Pythonesque), ou de refondre complètement le langage (par exemple, Lingua::Romana::Perligata). Effectivement, il permet d'utiliser toute la puissance de Perl comme son propre langage de macros, appliqué récursivement.

L'excellent module Filter::Util::Call (par Paul Marquess) fournit une interface Perl utilisable pour le filtrage de source, mais il est souvent trop puissant et pas assez simple comme il pourrait l'être.

Pour utiliser le module, il est nécessaire de faire ce qui suit :

1.
Télécharger, construire et installer le module Filter::Util::Call. (Si vous avez Perl 5.7.1 ou plus récent, c'est déjà fait pour vous.)
2.
Configurer un module qui fait un "use Filter::Util::Call".
3.
Dans ce module, créer une sous-routine "import".
4.
Dans la sous-routine "import", appeler "filter_add", en lui passant soit une référence de sous-routine.
5.
Dans la référence de sous-routine, appeler "filter_read" ou "filter_read_exact" pour "amorcer" $_ avec les données du code source du fichier qui "utilisera" votre module. Vérifier la valeur de statut retournée pour voir si du code source a réellement été lu.
6.
Traiter le contenu de $_ pour modifier le code source de la manière souhaitée.
7.
Retourner la valeur de statut.
8.
Si l'acte de désimportation de votre module (via un "no") doit entraîner la cessation du filtrage du code source, créer une sous-routine "unimport" et lui faire appeler "filter_del". S'assurer que l'appel à "filter_read" ou "filter_read_exact" à l'étape 5 ne lira pas accidentellement après le "no". Ceci limite effectivement les filtres de code source à une opération ligne par ligne, sauf si la sous-routine "import" effectue un pré-pré-parsing sophistiqué du code source qu'elle filtre.

Par exemple, voici un filtre de code source minimal dans un module nommé BANG.pm. Il convertit simplement chaque occurrence de la séquence "BANG\s+BANG" en la séquence "die 'BANG' if $BANG" dans tout morceau de code suivant une instruction "use BANG;" (jusqu'à la prochaine instruction "no BANG;", le cas échéant) :

package BANG;
use Filter::Util::Call ;
sub import {
    filter_add( sub {
    my $caller = caller;
    my ($status, $no_seen, $data);
    while ($status = filter_read()) {
        if (/^\s*no\s+$caller\s*;\s*?$/) {
            $no_seen=1;
            last;
        }
        $data .= $_;
        $_ = "";
    }
    $_ = $data;
    s/BANG\s+BANG/die 'BANG' if \$BANG/g
        unless $status < 0;
    $_ .= "no $class;\n" if $no_seen;
    return 1;
    })
}
sub unimport {
    filter_del();
}
1 ;

Ce niveau de sophistication met le filtrage hors de portée de nombreux programmeurs.

Une solution

Le module Filter::Simple fournit une interface simplifiée à Filter::Util::Call ; une interface suffisante pour la plupart des cas courants.

Au lieu du processus ci-dessus, avec Filter::Simple, la tâche de configuration d'un filtre de code source est réduite à :

1.
Télécharger et installer le module Filter::Simple. (Si vous avez Perl 5.7.1 ou plus récent, c'est déjà fait pour vous.)
2.
Configurer un module qui fait un "use Filter::Simple" puis appelle "FILTER { ... }".
3.
Dans la sous-routine anonyme ou le bloc passé à "FILTER", traiter le contenu de $_ pour modifier le code source de la manière souhaitée.

En d'autres termes, l'exemple précédent deviendrait :

package BANG;
use Filter::Simple;
FILTER {
    s/BANG\s+BANG/die 'BANG' if \$BANG/g;
};
1 ;

Notez que le code source est passé comme une seule chaîne, donc toute expression régulière utilisant "^" ou "$" pour détecter les limites de ligne nécessitera le drapeau "/m".

Désactivation ou modification du comportement <no>

Par défaut, le filtre installé ne filtre que jusqu'à une ligne constituée de l'un des trois "terminateurs" de source standards :

no NomDuModule;  # commentaire facultatif

ou :

__END__

ou :

__DATA__

mais cela peut être modifié en passant un deuxième argument à "use Filter::Simple" ou "FILTER" (rappelez-vous simplement : il n'y a *pas* de virgule après le bloc initial lorsque vous utilisez "FILTER").

Ce deuxième argument peut être soit une expression régulière "qr" (qui est alors utilisée pour correspondre à la ligne de terminaison), soit une valeur fausse définie (qui indique qu'aucune ligne de terminaison ne doit être recherchée), soit une référence à un hash (auquel cas la terminaison est la valeur associée à la clé 'terminator').

Par exemple, pour que le filtre précédent ne filtre que jusqu'à une ligne de la forme :

GNAB esu;

vous écririez :

package BANG;
use Filter::Simple;
FILTER {
    s/BANG\s+BANG/die 'BANG' if \$BANG/g;
}
qr/^\s*GNAB\s+esu\s*;\s*?$/;

ou :

FILTER {
    s/BANG\s+BANG/die 'BANG' if \$BANG/g;
}
{ terminator => qr/^\s*GNAB\s+esu\s*;\s*?$/ };

et pour empêcher le filtre d'être désactivé de quelque manière que ce soit :

package BANG;
use Filter::Simple;
FILTER {
    s/BANG\s+BANG/die 'BANG' if \$BANG/g;
}
"";    # ou : 0

ou :

FILTER {
    s/BANG\s+BANG/die 'BANG' if \$BANG/g;
}
{ terminator => "" };

Notez que, quelle que soit la valeur que vous définissez pour le modèle de terminaison, la terminaison elle-même doit être contenue sur une seule ligne source.

Interface tout-en-un

La séparation du chargement de Filter::Simple :

use Filter::Simple;

de la configuration du filtrage :

FILTER { ... };

est utile car elle permet à d'autres codes (typiquement du code de support de parser ou des variables de cache) d'être définis avant l'invocation du filtre. Cependant, il n'y a souvent pas besoin d'une telle séparation.

Dans ces cas, il est plus facile d'ajouter la sous-routine de filtrage et toute spécification de terminaison directement à l'instruction "use" qui charge Filter::Simple, comme ceci :

use Filter::Simple sub {
    s/BANG\s+BANG/die 'BANG' if \$BANG/g;
};

Ceci est exactement équivalent à :

use Filter::Simple;
BEGIN {
    Filter::Simple::FILTER {
        s/BANG\s+BANG/die 'BANG' if \$BANG/g;
    };
}

sauf que la sous-routine "FILTER" n'est pas exportée par Filter::Simple.

It is very common when filtering source to only want to apply the filter to the non-character-string parts of the code, or alternatively to only the character

strings.

Filter::Simple supports this type of filtering by automatically exporting the "FILTER_ONLY"

subroutine.

"FILTER_ONLY" takes a sequence of specifiers that install separate (and possibly multiple) filters that act on only parts of the source code. For

example: 
use Filter::Simple;
FILTER_ONLY
    code      => sub { s/BANG\s+BANG/die 'BANG' if \$BANG/g },
    quotelike => sub { s/BANG\s+BANG/CHITTY CHITTY/g }
;

The "code" subroutine will only be used to filter parts of the source code that are not quotelikes, POD, or "__DATA__". The "quotelike" subroutine only filters Perl quotelikes (including here documents)

    all   => sub { print if $::DEBUG
};

Filtrage uniquement des parties de code du code

source

Most source code ceases to be grammatically correct when it is broken up into the pieces between string literals and regexes. So the 'code' and 'code_no_comments' component filter behave slightly differently from the other partial filters described in the previous

section.

Rather than calling the specified processor on each individual piece of code (i.e. on the bits between quotelikes), the 'code...' partial filters operate on the entire source code, but with the quotelike bits (and, in the case of 'code_no_comments', the comments) "blanked

out".

That is, a 'code...' filter replaces each quoted string, quotelike, regex, POD, and __DATA__ section with a placeholder. The delimiters of this placeholder are the contents of the $; variable at the time the filter is applied (normally "\034"). The remaining four bytes are a unique identifier for the component being

replaced.

This approach makes it comparatively easy to write code preprocessors without worrying about the form or contents of strings, regexes,

etc.

For convenience, during a 'code...' filtering operation, Filter::Simple provides a package variable ($Filter::Simple::placeholder) that contains a pre-compiled regex that matches any placeholder...and captures the identifier within the placeholder. Placeholders can be moved and re-ordered within the source code as

needed.

In addition, a second package variable (@Filter::Simple::components) contains a list of the various pieces of $_, as they were originally split up to allow placeholders to be

inserted.

Once the filtering has been applied, the original strings, regexes, POD, etc. are re-inserted into the code, by replacing each placeholder with the corresponding original component (from @components). Note that this means that the @components variable must be treated with extreme care within the filter. The @components array stores the "back- translations" of each placeholder inserted into $_, as well as the interstitial source code between placeholders. If the placeholder backtranslations are altered in @components, they will be similarly changed when the placeholders are removed from $_ after the filter is

complete.

For example, the following filter detects concatenated pairs of strings/quotelikes and reverses the order in which they are

concatenated: 
package DemoRevCat;
use Filter::Simple;
FILTER_ONLY code => sub {
    my $ph = $Filter::Simple::placeholder;
    s{ ($ph) \s* [.] \s* ($ph) }{ $2.$1 }gx
}
;

code: 
use DemoRevCat;
my $str = "abc" . q(def);
print
"$str\n";

would

become: 
my $str = q(def)."abc";
print
"$str\n";

and hence

print: 
defa
b

Utilisation de Filter::Simple avec une sous-routine "import"

explicite

Filter::Simple generates a special "import" subroutine for your module (see "How it works") which would normally replace any "import" subroutine you might have explicitly

declared.

However, Filter::Simple is smart enough to notice your existing "import" and Do The Right Thing with it. That is, if you explicitly define an "import" subroutine in a package that's using Filter::Simple, that "import" subroutine will still be invoked immediately after any filter you

install.

The only thing you have to remember is that the "import" subroutine must be declared before the filter is installed. If you use "FILTER" to install the

filter: 
package Filter::TurnItUpTo11;
use Filter::Simple;
FILTER { s/(\w+)/\U$1/ }
;

that will almost never be a problem, but if you install a filtering subroutine by passing it directly to the "use Filter::Simple"

statement: 
package Filter::TurnItUpTo11;
use Filter::Simple sub{ s/(\w+)/\U$1/ }
;

then you must make sure that your "import" subroutine appears before that "use" st

atem
ent.

Utilisation conjointe de Filter::Simple et

d'Exporter

Likewise, Filter::Simple is also smart enough to Do The Right Thing if you use

Exporter: 
package Switch;
use base Exporter;
use Filter::Simple;
@EXPORT    = qw(switch case);
@EXPORT_OK = qw(given  when);
FILTER { $_ = magic_Perl_filter($_)
}

Immediately after the filter has been applied to the source, Filter::Simple will pass control to Exporter, so it can do its magic

too.

Of course, here too, Filter::Simple has to know you're using Exporter before it applies the filter. That's almost never a problem, but if you're nervous about it, you can guarantee that things will work correctly by ensuring that your "use base Exporter" always precedes your "use Filte

r::Si
mple".

Fonctionnemen

t

The Filter::Simple module exports into the package that calls "FILTER" (or "use"s it directly) -- such as package "BANG" in the above example -- two automagically constructed subroutines -- "import" and "unimport" -- which take care of all the nasty

details.

In addition, the generated "import" subroutine passes its own argument list to the filtering subroutine, so the BANG.pm filter could easily be made

parametric: 
package BANG;
use Filter::Simple;
FILTER {
    my ($die_msg, $var_name) = @_;
    s/BANG\s+BANG/die '$die_msg' if \${$var_name}/g;
};
# and in some user code:
use BANG "BOOM", "BAM";  # "BANG BANG" becomes: die 'BOOM' if
$BAM

The specified filtering subroutine is called every time a "use BANG" is encountered, and passed all the source code following that call, up to either the next "no BANG;" (or whatever terminator you've set) or the end of the source file, whichever occurs first. By default, any "no BANG;" call must appear by

itself on a se
parate line, or it is ignored.
