DESCRIPTIO

N

Les files d'achèvement sont utilisées pour signaler des événements associés aux transferts de données. Elles sont associées aux envois et réceptions de messages, aux opérations RMA, atomiques, aux messages étiquetés et aux événements déclenchés. Les événements signalés sont généralement associés à un point de terminaison de tissu, mais peuvent également faire référence à des régions mémoire utilisées comme cible d'une opération RMA ou

atomique.

L'opération fi_cq_read effectue une lecture non bloquante des données de complétion depuis la CQ. Le format de l'événement de complétion est déterminé à l'aide de l'option fi_cq_format qui a été spécifiée lorsque la CQ a été ouverte. L'appel fi_cq_readfrom se comporte de manière identique à fi_cq_read, à l'exception qu'il permet à la CQ de retourner des informations d'adresse source à l'utilisateur pour toute donnée reçue. Les données d'adresse source ne sont disponibles que pour les points d'extrémité configurés avec la capacité FI_SOURCE. Si fi_cq_readfrom est appelé sur un point d'extrémité pour lequel les données d'adressage source ne sont pas disponibles, l'adresse source sera définie à FI_ADDR_NOTAVAIL. Le nombre d'entrées src_addr en entrée doit être le même que le paramètre

count.

Les données d'adressage source retournées sont converties depuis l'adresse native utilisée par le fabric sous-jacent en un fi_addr_t, qui peut être utilisé dans les opérations de transmission. Dans la plupart des cas, le retour d'un fi_addr_t nécessite que l'adresse source ait déjà été insérée dans le vecteur d'adresses associé au point d'extrémité de réception. C'est le cas pour les vecteurs d'adresses de type FI_AV_TABLE. Dans certains fournisseurs, lorsque FI_AV_MAP est utilisé, les adresses sources peuvent être converties algorithmiquement en un fi_addr_t utilisable, même si l'adresse source n'a pas été insérée dans le vecteur d'adresses. Cela est permis par l'API, car cela permet au fournisseur d'éviter la recherche d'adresses dans le traitement des messages reçus. En aucun cas les fournisseurs n'insèrent d'adresses dans un AV en dehors d'un appel de l'application à fi_av_insert ou un appel

similaire.

COMPLETIONS

Completion Notification

The libfabric API supports asynchronous operations that complete by generating a completion event. Completion events are reported to the application via a completion queue (CQ). Completions are typically generated by the underlying fabric provider in response to operations such as send, receive, RMA, atomic, and multicast operations. Applications can request completion notifications through various mechanisms, including polling, waiting on event objects, or receiving signals.

The fi_cq_read and fi_cq_readfrom calls are used to retrieve completions from a CQ. These calls may block if the CQ is empty and the application has not configured the CQ for non-blocking operations. In such cases, the application can use fi_cq_signal to explicitly unblock a thread waiting on the CQ. Errors that occur during asynchronous operations are reported as completion events. The fi_cq_err_entry structure is used to report these errors, providing detailed information about the failure.

When an error occurs, the provider will report as much information as is available about the failure. Fields that are not applicable or could not be determined will be set to NULL or 0. This includes the op_context value, which may not have been provided or was ignored on input as part of the transfer.

Notable completion error codes are given below.

FI_EADDRNOTAVAIL
This error code is used by CQs configured with FI_SOURCE_ERR to report completions for which a usable fi_addr_t source address could not be found. An error code of FI_EADDRNOTAVAIL indicates that the data transfer was successfully received and processed, with the fi_cq_err_entry fields containing information about the completion. The err_data field will be set to the source address data. The source address will be in the same format as specified through the fi_info addr_format field for the opened domain. This may be passed directly into an fi_av_insert call to add the source address to the address vector.

For API versions 1.20 and later, if the EP is configured with FI_AV_AUTH_KEY, src_addr will be set to the fi_addr_t authorization key handle or a user-define authorization key ID corresponding to the incoming data transfer. Otherwise, the value will be set to FI_ADDR_NOTAVAIL.

fi_cq_signal

The fi_cq_signal call will unblock any thread waiting in fi_cq_sread or fi_cq_sreadfrom. This may be used to wake-up a thread that is blocked waiting to read a completion operation. The fi_cq_signal operation is only available if the CQ was configured with a wait object.

CHAMP_CHAMPIONSHIPS

The CQ entry data structures share many of the same fields. The meanings of these fields are the same for all CQ entry structure formats.

op_context
The operation context is the application specified context value that was provided with an asynchronous operation. The op_context field is valid for all completions that are associated with an asynchronous operation.

For completion events that are not associated with a posted operation, this field will be set to NULL. This includes completions generated at the target in response to RMA write operations that carry CQ data (FI_REMOTE_WRITE | FI_REMOTE_CQ_DATA flags set), when the FI_RX_CQ_DATA mode bit is not required.

flags
This specifies flags associated with the completed operation. The Completion Flags section below lists valid flag values. Flags are set for all relevant completions.
len
This len field applies to completed receive operations (e.g. fi_recv, fi_trecv, etc.) and the completed write with remote cq data on the responder side (e.g. fi_write, with FI_REMOTE_CQ_DATA flag). It indicates the size of transferred message data – i.e. how many data bytes were placed into the associated receive/target buffer by a corresponding fi_send/fi_tsend/fi_write et al call. If an endpoint has been configured with the FI_MSG_PREFIX mode, the len also reflects the size of the prefix buffer.
buf
The buf field is only valid for completed receive operations, and only applies when the receive buffer was posted with the FI_MULTI_RECV flag. In this case, buf points to the starting location where the receive data was placed.
data
The data field is only valid if the FI_REMOTE_CQ_DATA completion flag is set, and only applies to receive completions. If FI_REMOTE_CQ_DATA is set, this field will contain the completion data provided by the peer as part of their transmit request. The completion data will be given in host byte order.
tag
A tag applies only to received messages that occur using the tagged interfaces. This field contains the tag that was included with the received message. The tag will be in host byte order.
olen
The olen field applies to received messages. It is used to indicate that a received message has overrun the available buffer space and has been truncated. The olen specifies the amount of data that did not fit into the available receive buffer and was discarded.
err
This err code is a positive fabric errno associated with a completion. The err value indicates the general reason for an error, if one occurred. See fi_errno.3 for a list of possible error codes.
prov_errno
On an error, prov_errno may contain a provider specific error code. The use of this field and its meaning is provider specific. It is intended to be used as a debugging aid. See fi_cq_strerror for additional details on converting this error value into a human readable string.
err_data
The err_data field is used to return provider specific information, if available, about the error. On input, err_data should reference a data buffer of size err_data_size. On output, the provider will fill in this buffer with any provider specific data which may help identify the cause of the error. The contents of the err_data field and its meaning is provider specific. It is intended to be used as a debugging aid. See fi_cq_strerror for additional details on converting this error data into a human readable string. See the compatibility note below on how this field is used for older libfabric releases.
err_data_size
On input, err_data_size indicates the size of the err_data buffer in bytes. On output, err_data_size will be set to the number of bytes copied to the err_data buffer. The err_data information is typically used with fi_cq_strerror to provide details about the type of error that occurred.

For compatibility purposes, the behavior of the err_data and err_data_size fields is may be modified from that listed above. If err_data_size is 0 on input, or the fabric was opened with release < 1.5, then any buffer referenced by err_data will be ignored on input. In this situation, on output err_data will be set to a data buffer owned by the provider. The contents of the buffer will remain valid until a subsequent read call against the CQ. Applications must serialize access to the CQ when processing errors to ensure that the buffer referenced by err_data does not change.

SÉMANTIQUES DES ÉVÉNEMENTS DE

COMPLÉTION

Libfabric définit plusieurs « niveaux » de complétion, identifiés à l'aide de drapeaux opérationnels. Chaque drapeau indique le moment le plus tôt auquel un événement de complétion peut être généré par un fournisseur, et les hypothèses qu'une application peut faire lors du traitement d'une complétion. Les drapeaux opérationnels sont définis ci-dessous, avec un exemple de la manière dont un fournisseur pourrait implémenter la sémantique. Notez que seule la conformité à la sémantique est requise du fournisseur, et non l'implémentation. Les fournisseurs peuvent implémenter des sémantiques de complétion plus fortes que nécessaire pour une opération donnée, mais seul le comportement défini par le niveau de complétion est

garanti.

Pour aider à comprendre les différences conceptuelles entre les niveaux de complétion, considérez l'envoi d'une lettre. Placer la lettre dans la boîte aux lettres locale pour la collecte est similaire à « inject complete ». Avoir la lettre collectée et déposée dans la boîte aux lettres de destination équivaut à « transmit complete ». La sémantique « delivery complete » est une garantie plus forte, avec une personne à la destination signant pour la lettre. Cependant, la personne qui a signé pour la lettre n'est pas nécessairement le destinataire prévu. L'option « match complete » est similaire à delivery complete, mais exige que le destinataire prévu signe pour la

lettre.

Le niveau « commit complete » a des sémantiques différentes des niveaux précédemment mentionnés. Commit complete serait plus proche de la lettre arrivant à destination et étant placée dans un coffre-fort

ignifugé.

Les drapeaux opérationnels pour les niveaux de complétion décrits sont définis

ci-dessous.
FI_INJECT_COMPL
ETE

réutilisés. Une complétion garantit que les tampons ne seront plus lus et que l'applicati

Exemple : Un fournisseur peut générer cet événement de complétion après avoir copié le tampon source dans un tampon réseau, soit en mémoire hôte, soit sur la NIC. Une inject complete n'indique pas que les données ont été transmises sur le réseau, et une erreur locale pourrait survenir après la génération de l'événement de complétion, ce qui pourrait empêcher leur

transmission.

Inject complete permet le signalement de complétion le plus rapide (et donc la réutilisation des tampons), mais fournit les garanties les plus faibles contre les erreurs

réseau.

SÉMANTIQUES DE COMPLÉTION À LA

CIBLE

La sémantique de complétion à la cible est utilisée pour déterminer quand les données à la cible sont visibles par l'application paire. La visibilité indique qu'une lecture mémoire au même adresse qui était la cible d'un transfert de données retournera les résultats du transfert. La cible d'un transfert peut être identifiée par l'initiateur, comme c'est le cas pour les opérations RMA et atomiques, ou déterminée par la cible, par exemple en fournissant un tampon de réception appariant. La visibilité globale indique que les résultats sont disponibles quelle que soit l'origine de la lecture mémoire. Par exemple, la lecture peut provenir d'un processus s'exécutant sur un CPU hôte, elle peut être accédée par un transfert de données ultérieur via la fabrique, ou lue depuis un dispositif pair tel qu'un

GPU.

En termes de sémantiques de complétion, la visibilité indique généralement que le transfert satisfait les exigences FI_DELIVERY_COMPLETE du point de vue de la cible. La sémantique de complétion de la cible peut être, mais n'est pas nécessairement, liée à la sémantique de complétion spécifiée par l'initiateur du

transfert.

Souvent, les processus de la cible ne déclarent pas explicitement une sémantique de complétion souhaitée et s'appuient plutôt sur la sémantique par défaut. Le comportement par défaut est basé sur plusieurs facteurs, notamment

De manière générale, les sémantiques de complétion de la cible sont regroupées en fonction du fait que le transfert génère ou non un événement de complétion à la cible. Cela inclut l'écriture d'une entrée CQ ou la mise à jour d'un compteur de complétion. Dans les cas d'utilisation courants, les transferts qui utilisent une interface de message (FI_MSG ou FI_TAGGED) génèrent typiquement des événements de cible, tandis que les transferts impliquant une interface RMA (FI_RMA ou FI_ATOMIC) ne le font souvent pas. Il existe des exceptions à ces deux cas, selon les liaisons point de terminaison-CQ et compteur, et les drapeaux opérationnels. Par exemple, les écritures RMA qui transportent des données CQ distantes généreront un événement de complétion à la cible, et sont fréquemment utilisées pour transmettre la visibilité à l'application cible. Les directives générales pour les sémantiques côté cible sont décrites ci-dessous, suivies des exceptions qui modifient ce

comportement.

Par défaut, les complétions générées à la cible indiquent que les données transférées sont immédiatement disponibles pour être lues depuis le tampon de la cible. C'est-à-dire que la cible voit des sémantiques FI_DELIVERY_COMPLETE (ou meilleures), même si l'initiateur a demandé des sémantiques inférieures. Pour les applications utilisant uniquement des tampons de données alloués à partir de la mémoire hôte, c'est souvent

suffisant. ">Pour les opérations qui ne génèrent pas un événement de complétion à la cible, la visibilité des données à la cible peut devoir être inférée sur la base d'opérations ultérieures qui génèrent effectivement des complétions à la cible. En l'absence d'une complétion à la cible, lorsqu'une complétion d'une opération est écrite à l'initiateur, la sémantique de visibilité de l'opérations à la cible s'aligne avec la sémantique de complétion de l'initiateur. Par exemple, si une opération RMA se termine à l'initiateur soit comme FI_INJECT_COMPLETE soit comme FI_TRANSMIT_COMPLETE, la visibilité des données à la cible n'est pas

garantie.

Un ou plusieurs des mécanismes suivants peuvent être utilisés par le processus cible pour garantir que les résultats d'un transfert de données qui n'a pas généré une complétion à la cible sont maintenant visibles. Cette liste n'est pas exhaustive de toutes les options, mais définit des usages courants. Dans les descriptions ci-dessous, le premier transfert ne résulte pas en un événement de complétion à la cible, mais est éventuellement suivi d'un transfert qui en génère

un.
•
Si le point de terminaison garantit l'ordre des messages entre deux transferts, la complétion à la cible d'un second transfert indiquera que les données du premier transfert sont disponibles. Par exemple, si le point de terminaison supporte l'ordre d'envoi après écriture (FI_ORDER_SAW), alors une complétion de réception correspondant à l'envoi indiquera que les données écrites sont disponibles. Ceci est indépendant de la sémantique de complétion de l'initiateur pour l'écriture ou l'envoi. Lorsque l'ordre est garanti, le second transfert peut être mis en file d'attente auprès du fournisseur immédiatement après la mise en file du
premier.
•
Si le point de terminaison ne garantit pas l'ordre des messages, l'initiateur doit prendre des mesures supplémentaires pour assurer la visibilité. Si l'initiateur demande la sémantique FI_DELIVERY_COMPLETE pour la première opération, l'initiateur peut attendre que l'opérations se termine localement. Une fois la complétion lue, la complétion à la cible d'un second transfert indiquera que les données du premier transfert sont
visibles.
•
Alternativement, si l'ordre des messages n'est pas garanti par le point de terminaison, l'initiateur peut utiliser les indicateurs FI_FENCE et FI_DELIVERY_COMPLETE sur le s
econd transfert de données pour forcer les premiers transferts à respecter la sémantique FI_DELIVERY_COMPLETE. Si le second transfert génère une complétion à la cible, cel
a indiquera que les données sont visibles. Sinon, une complétion à la cible pour tout transfert après l'opération clôturée (fenced) indiquera que les données sont visibles.

Les sémantiques ci-dessus s'appliquent aux transferts ciblant des tampons de mémoire hôte traditionnels. Cependant, le comportement peut différer lorsque la mémoire de dispositif et/ou la mémoire persistante sont concernées (bits de capacité FI_HMEM et FI_PMEM). Lorsque la mémoire hétérogène est concernée, le concept de domaines de mémoire entre en jeu. Les domaines de mémoire identifient la séparation physique de la mémoire, qui peut ou ne peut pas être accessible à travers le même espace d'adressage virtuel. Voir la page de manuel fi_mr(3) pour plus de détails sur les domaines de

mémoire.

L'ordre des complétions et la visibilité des données ne sont bien définis que pour les transferts ciblant le même domaine de mémoire. Les applications doivent être conscientes des différences d'ordre et de visibilité lorsque les transferts ciblent différents domaines de mémoire. De plus, les applications doivent également se préoccuper du domaine de mémoire dans lequel les complétions elles-mêmes sont écrites et s'il diffère du domaine de mémoire ciblé par un transfert. Dans certaines situations, soit le fournisseur soit l'application peuvent avoir besoin d'appeler des API spécifiques au dispositif pour synchroniser ou vider les caches de mémoire du dispositif afin d'atteindre la visibilité des données

souhaitée.

Lorsque la mémoire hétérogène est utilisée, la sémantique de complétion à la cible par défaut pour les transferts qui génèrent une complétion à la cible est toujours FI_DELIVERY_COMPLETE, cependant, les applications doivent être conscientes qu'il peut y avoir un impact négatif sur les performances globales pour les fournisseurs afin de satisfaire cette

exigence.

Par exemple, un processus cible peut utiliser un GPU pour accélérer des calculs. Une région de mémoire mappant la mémoire sur le GPU peut être exposée aux pairs soit comme une cible RMA soit postée localement comme un tampon de réception. Dans ce cas, l'application est concernée par deux domaines de mémoire – la mémoire système et la mémoire GPU. Les complétions sont écrites dans la mémoire

système.

En continuant l'exemple, un processus pair envoie un message étiqueté. Ce message est apparié avec le tampon de réception situé dans la mémoire GPU. La NIC copie les données du réseau vers le tampon de réception et écrit une entrée dans la file de complétion. Notez que les deux domaines de mémoire ont été accessibles dans le cadre de ce transfert. Les données du message ont été dirigées vers la mémoire GPU, mais la complétion est allée vers la mémoire hôte. Comme des domaines de mémoire séparés peuvent ne pas être synchronisés les uns avec les autres, il est possible que le CPU hôte voie et traite l'entrée de complétion avant que le transfert vers la mémoire GPU ne soit visible soit pour le GPU hôte soit même pour le logiciel s'exécutant sur le GPU. Du point de vue du fournisseur, la visibilité de la complétion n'implique pas la visibilité des données écrites dans le domaine de mémoire du

GPU.

La sémantique de complétion par défaut à la cible l'application pour les opérations de message est FI_DELIVERY_COMPLETE. Une implémentation de fournisseur anticipée dans cette situation est que le logiciel du fournisseur s'exécutant sur le CPU hôte intercepte l'entrée de CQ, détecte que les données ont atterri dans la mémoire hétérogène, et effectue la synchronisation de dispositif ou l'opération de vidage nécessaire avant de rapporter la complétion à l'application. Cela garantit que les données sont visibles pour le CPU et le logiciel GPU avant que l'application ne traite la

complétion.

En plus du coût du logiciel du fournisseur interceptant les complétions et vérifiant si un transfert ciblait la mémoire hétérogène, la synchronisation du dispositif elle-même peut impacter les performances. Par conséquent, les applications peuvent demander une sémantique de complétion plus basse lors de la publication de réceptions. Cela indique au fournisseur que l'application sera responsable du traitement de toute opération de vidage spécifique au dispositif qui pourrait être nécessaire. Voir fi_msg(3)

FLAGS.

Pour les transferts de données qui ne génèrent pas une complétion à la cible, tels que RMA ou les atomiques, il est de la responsabilité de l'application de s'assurer que tous les tampons cibles répondent aux exigences de visibilité nécessaires de l'application. Les méthodes à puces mentionnées précédemment pour notifier la cible que les données sont visibles peuvent ne pas être suffisantes, car le logiciel du fournisseur à la cible pourrait manquer du contexte nécessaire pour assurer la visibilité. Cela implique que l'application pourrait avoir besoin d'appeler directement les API de synchronisation/vidage du

dispositif.

Par exemple, une application pair pourrait effectuer plusieurs écritures RMA ciblant des tampons de mémoire GPU. Si le fournisseur décharge les opérations RMA dans la NIC, le logiciel du fournisseur à la cible ne sera pas conscient que les opérations RMA ont eu lieu. Si le pair envoie un message à l'application cible indiquant que les opérations RMA sont terminées, l'application doit s'assurer que les données RMA sont visibles pour le CPU ou le GPU hôte avant d'exécuter du code qui accède aux données. La complétion à la cible d'avoir reçu le message envoyé n'est pas suffisante, même si l'ordre d'envoi après écriture est

supporté.

La plupart des sémantiques de complétion pour la mémoire hétérogène de la cible correspondent à FI_TRANSMIT_COMPLETE ou FI_DELIVERY_COMPLETE. La mémoire persistante (capacité FI_PMEM), cependant, est souvent utilisée avec la sémantique FI_COMMIT_COMPLETE. Les concepts de complétion hétérogène s'appliquent

toujours.

Pour les transferts marqués par l'initiateur avec FI_COMMIT_COMPLETE, une complétion à la cible indique que les résultats sont visibles et durables. Pour les transferts ciblant la mémoire persistante, mais utilisant une sémantique de complétion différente à l'initiateur, la visibilité à la cible est similaire à celle décrite ci-dessus. La durabilité n'est associée qu'aux transferts marqués avec FI_COMMIT_COMPLETE

.

Pour les transferts ciblant la mémoire persistante qui demandent FI_DELIVERY_COMPLETE, alors une complétion, à l'initiateur ou à la cible, indique que les données sont visibles. La visibilité à la cible peut être conveyée en utilisant l'un des mécanismes décrits ci-dessus – générer une complétion à la cible, envoyer un message depuis l'initiateur, etc. De même, si l'initiateur a demandé FI_TRANSMIT_COMPLETE, alors des étapes supplémentaires sont nécessaires pour assurer la visibilité à la cible. Par exemple, le transfert peut générer une complétion à la cible, ce qui indiquerait la visibilité, mais pas la durabilité. L'initiateur peut également suivre le transfert par une autre opération qui force la visibilité, comme utiliser FI_FENCE en conjonction avec FI_DELIVERY_COMPLET

E
.

: En cas de succès, retourne la valeur positive 1 (nombre d'entrées d'erreur retournées). En

cas d'erreur, retourne un errno de tissu négatif, avec cette erreur explicitement identifié
e : Si aucune complétion d'erreur n'est disponible à lire depuis le CQ, retourne -FI_EAGAIN.

fi_cq_strerro

r

: Retourne une chaîne de caractères d'interprétation du coder erreur spécifique renvoyée avec une complétion.
