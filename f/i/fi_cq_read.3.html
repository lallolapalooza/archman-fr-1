DESCRIPTIO

N

Les files d'achèvement sont utilisées pour signaler des événements associés à des transferts de données. Elles sont associées aux envois et réceptions de messages, au RMA, aux opérations atomiques, aux messages étiquetés et aux événements déclenchés. Les événements signalés sont généralement associés à un point de terminaison de fabric, mais peuvent également faire référence à des régions mémoire utilisées comme cible d'une opération RMA ou

atomique.

fi_cq_ope

n

fi_cq_open alloue une nouvelle file d'achèvement. Contrairement aux files d'événements, les files d'achèvement sont associées à un domaine de ressources et peuvent être entièrement déchargées sur le matériel du

fournisseur.

Les propriétés et le comportement d'une file d'achèvement sont définis par struct

fi_cq_attr.

Les CQ peuvent être associées à un objet d'attente spécifique. Les objets d'attente permettent aux applications de se bloquer jusqu'à ce que l'objet d'attente soit signalé, indiquant qu'un achèvement est disponible pour être lu. Les utilisateurs peuvent utiliser fi_control pour récupérer l'objet d'attente sous-jacent associé à une CQ, afin de l'utiliser dans d'autres appels système. Les valeurs suivantes peuvent être utilisées pour type d'objet d'attente associé à une CQ : FI_WAIT_NONE, FI_WAIT_UNSPEC, FI_WAIT_SET, FI_WAIT_FD, FI_WAIT_MUTEX_COND (obsolète), et FI_WAIT_YIELD. La valeur par défaut est
FI_WAIT_NONE.

NE
Utilisé pour indiquer que l'utilisateur ne bloquera pas (n'attendra pas) les complétions sur la CQ. Lorsque FI_WAIT_NONE est spécifié, l'application ne peut pas appeler fi_cq_sread ou
fi_cq_sreadfrom.
- FI_WAIT_UNSP
EC
Spécifie que l'utilisateur n'attendra sur la CQ qu'à l'aide d'appels d'interface fabric, tels que fi_cq_sread ou fi_cq_sreadfrom. Dans ce cas, le fournisseur sous-jacent peut sélectionner l'objet d'attente le plus approprié ou le plus performant disponible, y compris des mécanismes d'attente personnalisés. Les applications qui sélectionnent FI_WAIT_UNSPEC ne sont pas garanties de pouvoir récupérer l'objet d'attente
sous-jacent.

Indique que la CQ doit utiliser un descripteur de fichier comme mécanisme d'attente. Un objet d'attente de type descripteur de fichier doit être utilisable dans les routines select, poll et epoll. Cependant, un fournisseur peut signaler un objet d'attente FD en le marquant comme lisible, inscriptible ou avec une

Par défaut, lorsqu'une complétion est insérée dans une CQ qui prend en charge les lectures bloquantes (fi_cq_sread/fi_cq_sreadfrom), l'objet d'a
ttente correspondant est signalé. Les utilisateurs peuvent spécifier une condition qui doit d'abord être remplie avant que l'attente soit satisfa
ite. Ce champ indique comment le fournisseur doit interpréter le champ cond, qui décrit la condition nécessaire pour signaler l'objet d'attente.

Une condition d'attente doit être traitée comme une optimisation. Les fournisseurs ne sont pas tenus de satisfaire les exigences de la condition avant de signaler l'objet d'attente. Les applications ne doivent pas compter sur le fait que la condition soit nécessairement vraie lorsqu'un appel de lecture bloquante

retourne.

Le seuil indique le nombre d'entrées qui doivent être mises en file d'attente dans la CQ avant que l'attente soit

satisfaite.

FI_WAIT_NONE.

à travers plusieurs files d'événements et de complétions. Ce champ est ignoré si wait_obj n'est pas FI_WAIT_SET.

fi_clos

e

L'appel fi_close libère toutes les ressources associées à une file de complétion. Toutes les complétions restant sur la CQ lors de sa fermeture sont

perdues.

Lors de la fermeture de la CQ, il ne doit y avoir aucun point de terminaison ouvert, auc

un contexte de transmission ou de réception associé à la CQ. Si des ressources sont tou
jours associées à la CQ lors de la tentative de fermeture, l'appel retournera -FI_EBUSY.

fi_contro

l

L'appel fi_control est utilisé pour accéder aux détails spécifiques au fournisseur ou à l'implémentation de la file de complétion. L'accès à la CQ doit être sérialisé à travers tous les appels lorsque fi_control est invoqué, car il peut rediriger l'implémentation des opérations de CQ. Les commandes de contrôle suivantes sont utilisables avec une

CQ.
FI_GETWAIT (void
**)
Cette commande permet à l'utilisateur de récupérer l'objet d'attente de bas niveau associé à la CQ. Le
format de l'objet d'attente est spécifié lors de la création de la CQ, à travers les attributs de la
CQ. Le paramètre arg de fi_control doit être une adresse où un pointeur vers l'objet d'attente r
etourné sera écrit. Voir fi_eq.3 pour plus de détails sur l'utilisation de fi_control avec FI_GETWAIT.

fi_cq_rea

d

L'opération fi_cq_read effectue une lecture non bloquante des données de complétion depuis la CQ. Le format de l'événement de complétion est déterminé à l'aide de l'option fi_cq_format qui a été spécifiée lorsque la CQ a été ouverte. Plusieurs complétions peuvent être récupérées depuis une CQ en un seul appel. Le nombre maximum d'entrées à retourner est limité au paramètre count spécifié, le nombre d'entrées lues avec succès depuis la CQ étant retourné par l'appel. (Voir la section des valeurs de retour ci-dessous.) Une valeur count de 0 peut être utilisée pour faire avancer le progrès sur les points de terminaison associés lorsque le progrès manuel est

activé.

Les CQ sont optimisées pour signaler les opérations qui se sont terminées avec succès. Les opérations qui échouent sont signalées « hors bande ». Ces opérations sont récupérées à l'aide de la fonction

fi_cq_readerr. Lorsqu'une opération qui s'est terminée avec une erreur inattendue est rencontrée, elle est placée dans une file d'erreurs temporaire. Tenter de lire depuis une CQ alors qu'un élém
ent est dans la file d'erreurs entraîne l'échec de fi_cq_read avec un code de retour de -FI_EAVAIL. Les applications peuvent utiliser ce code de retour pour déterminer quand appeler fi_cq_readerr.

fi_cq_readfro

m

L'appel fi_cq_readfrom se comporte de manière identique à fi_cq_read, à l'exception qu'il permet à la CQ de retourner des informations d'adresse source à l'utilisateur pour toute donnée reçue. Les données d'adresse source ne sont disponibles que pour les points de terminaison configurés avec la capacité FI_SOURCE. Si fi_cq_readfrom est appelé sur un point de terminaison pour lequel les données d'adressage source ne sont pas disponibles, l'adresse source sera définie à FI_ADDR_NOTAVAIL. Le nombre d'entrées src_addr en entrée doit être le même que le paramètre

count.

Les données d'adressage source retournées sont converties depuis l'adresse native utilisée par le fabric sous-jacent en un fi_addr_t, qui peut être utilisé dans les opérations de transmission. Dans la plupart des cas, le retour d'un fi_addr_t nécessite que l'adresse source ait déjà été insérée dans le vecteur d'adresses associé au point de terminaison récepteur. C'est le cas pour les vecteurs d'adresses de type FI_AV_TABLE. Dans certains fournisseurs lorsque FI_AV_MAP est utilisé, les adresses sources peuvent être converties algorithmiquement en un fi_addr_t utilisable, même si l'adresse source n'a pas été insérée dans le vecteur d'adresses. Cela est permis par l'API, car cela permet au fournisseur d'éviter la recherche d'adresse dans le traitement des messages reçus. Dans aucun cas les fournisseurs n'insèrent des adresses dans un AV en dehors de l'appel de fi_av_insert ou d'un appel similaire par une

application.

Pour les points de terminaison alloués avec la capacité FI_SOURCE_ERR, si l'adresse source ne peut pas être convertie en une valeur fi_addr_t valide, fi_cq_readfrom retournera -FI_EAVAIL, même si les données ont été reçues avec succès. La complétion sera alors signalée à travers fi_cq_readerr avec le code d'erreur -FI_EADDRNOTAVAIL. Voir fi_cq_readerr pour plus de

détails.

Si FI_SOURCE est spécifié sans FI_SOURCE_ERR, les adresses sources qui ne peuvent pas être mappées vers un fi_addr_t utilisable seront signalées comme FI_ADDR_NOTAVAI

L
.

fi_cq_sread /

fi_cq_sreadfrom

Les appels fi_cq_sread et fi_cq_sreadfrom sont les opérations bloquantes équivalentes à fi_cq_read et fi_cq_readfrom. Leur comportement est similaire aux appels non bloquants, à l'exception que les appels ne retourneront pas tant qu'une complétion n'a pas été lue depuis la CQ ou qu'une erreur ou un délai d'attente ne se

produit.

Les threads bloqués dans cette fonction retourneront à l'appelant s'ils sont signalés par une source externe. C'est vrai même si le délai d'attente ne s'est pas produit ou a été spécifié comme

infini.

Il est invalide pour les applications d'appeler ces

fonctions si la CQ a été configurée avec un obje
t d'attente de type FI_WAIT_NONE ou FI_WAIT_SET.

fi_cq_reader

r

La fonction de lecture d'erreur, fi_cq_readerr, récupère les informations concernant toute opération asynchrone qui s'est terminée avec une erreur inattendue. fi_cq_readerr est un appel non bloquant, retournant immédiatement qu'une complétion d'erreur ait été trouvée ou

non.

Les informations d'erreur sont rapportées à l'utilisateur à travers la structure fi_cq_err_entry. Le format de cette structure est défini

ci-dessous. 
struct fi_cq_err_entry {
    void     *op_context; /* operation context */
    uint64_t flags;       /* completion flags */
    size_t   len;         /* size of received data */
    void     *buf;        /* receive data buffer */
    uint64_t data;        /* completion data */
    uint64_t tag;         /* message tag */
    size_t   olen;        /* overflow length */
    int      err;         /* positive error code */
    int      prov_errno;  /* provider error code */
    void    *err_data;    /*  error data */
    size_t   err_data_size; /* size of err_data */
    fi_addr_t src_addr; /* error source address
*/
}
;

La raison générale de l'erreur est fournie à travers le champ err. Des informations d'erreur spécifiques au fournisseur peuvent également être disponibles à travers les champs prov_errno et err_data. Les utilisateurs peuvent appeler fi_cq_strerror pour convertir les informations d'erreur spécifiques au fournisseur en une chaîne imprimable à des fins de débogage. Voir les détails des champs ci-dessous pour plus d'informations sur l'utilisation de err_data et

err_data_size.

Notez que des complétions d'erreur sont générées pour toutes les opérations, y compris celles pour lesquelles une complétion n'a pas été demandée (par ex. un point de terminaison est configuré avec FI_SELECTIVE_COMPLETION, mais la requête n'avait pas l'indicateur FI_COMPLETION défini). Dans de tels cas, les fournisseurs renverront autant d'informations que ce que les logiciels et matériels sous-jacents rendent disponibles concernant l'échec, les autres champs seront définis à NULL ou 0. Cela inclut la valeur op_context, qui n'a peut-être pas été fournie ou a été ignorée en entrée dans le cadre du

transfert.

Les codes d'erreur de complétion notables sont donnés

ci-dessous.
FI_EADDRNOTAV
AIL
Ce code d'erreur est utilisé par les CQ configurés avec FI_SOURCE_ERR pour signaler des complétions pour lesquelles une adresse source fi_addr_t utilisable n'a pas pu être trouvée. Un code d'erreur FI_EADDRNOTAVAIL indiqu
e que le transfert de données a été reçu et traité avec succès, les champs de fi_cq_err_entry contenant des informations sur la complétion. Le champ err_data sera défini sur les données de l'adresse source. L'adresse sour
ce sera dans le même format que celui spécifié via le champ addr_format de fi_info pour le domaine ouvert. Celle-ci peut être passée directement à un appel fi_av_insert pour ajouter l'adresse source au vecteur d'adresses.

Pour les versions d'API 1.20 et ultérieures, si l'EP est configuré avec FI_AV_AUTH_KEY, src_addr sera défini sur le handle de clé d'autorisation fi_addr_t ou un identifiant de clé d'autorisation défini par l'utilisateur correspondant au transfert de données entrant. Sinon, la valeur sera définie à FI_ADDR_NOTAVAI

L
.

Le contenu du champ err_data et sa signification sont spécifiques au fournisseur. Il est destiné à être utilisé comme aide au débogage. Voir fi_cq_strerror pour plus de détails sur la conversion de ces données d'erreur en une chaîne lisible par l'humain. Voir la note de compatibilité ci-dessous sur la façon dont ce champ est utilisé pour les versions plus anciennes de

SÉMANTIQUE DES ÉVÉNEMENTS D'ACHÈVEMENT

Libfabric définit plusieurs `niveaux' d'achèvement, identifiés à l'aide de drapeaux opérationnels. Chaque drapeau indique le moment le plus tôt auquel un événement d'achèvement peut être généré par un fournisseur, ainsi que les hypothèses qu'une application peut faire lors du traitement d'un achèvement. Les drapeaux opérationnels sont définis ci-dessous, accompagnés d'un exemple de la manière dont un fournisseur pourrait implémenter la sémantique. Notez que seule la conformité à la sémantique est requise du fournisseur, et non l'implémentation. Les fournisseurs peuvent implémenter des sémantiques d'achèvement plus strictes que nécessaire pour une opération donnée, mais seul le comportement défini par le niveau d'achèvement est garanti.

Pour aider à comprendre les différences conceptuelles entre les niveaux d'achèvement, considérez l'envoi d'une lettre. Placer la lettre dans la boîte aux lettres locale pour la récupération est similaire à `inject complete'. Avoir la lettre récupérée et déposée dans la boîte aux lettres de destination est équivalent à `transmit complete'. La sémantique `delivery complete' est une garantie plus forte, avec une personne à la destination signant pour la lettre. Cependant, la personne qui a signé pour la lettre n'est pas nécessairement le destinataire prévu. L'option `match complete' est similaire à delivery complete, mais exige que le destinataire prévu signe pour la lettre.

Le niveau `commit complete' a une sémantique différente des niveaux mentionnés précédemment. Commit complete serait plus proche de la lettre arrivant à la destination et étant placée dans un coffre-fort ignifuge.

Les drapeaux opérationnels pour les niveaux d'achèvement décrits sont définis ci-dessous.

FI_INJECT_COMPLETE
Indique qu'un achèvement doit être généré lorsque le(s) tampon(s) source peuvent être réutilisés. Un achèvement garantit que les tampons ne seront plus lus et que l'application peut les récupérer. Aucune autre garantie n'est donnée quant à l'état de l'opération.

Exemple : Un fournisseur peut générer cet événement d'achèvement après avoir copié le tampon source dans un tampon réseau, soit en mémoire hôte, soit sur la NIC. Un achèvement inject ne signifie pas que les données ont été transmises sur le réseau, et une erreur locale pourrait survenir après la génération de l'événement d'achèvement, ce qui pourrait empêcher leur transmission.

Inject complete permet le signalement d'achèvement le plus rapide (et donc la réutilisation des tampons), mais fournit les garanties les plus faibles contre les erreurs réseau.

Remarque : Ce drapeau est utilisé pour contrôler le moment où une entrée d'achèvement est insérée dans une file d'achèvement. Il ne s'applique pas aux opérations qui ne génèrent pas d'entrée de file d'achèvement, comme l'opération fi_inject, et n'est pas soumis à la restriction de limite de message inject_size.

FI_TRANSMIT_COMPLETE
Indique qu'un achèvement doit être généré lorsque l'opération de transmission est terminée par rapport au fournisseur local. Le comportement exact dépend du type de point de terminaison.

Pour les points de terminaison fiables :

Indique qu'un achèvement doit être généré lorsque l'opération a été délivrée au point de terminaison pair. Un achèvement garantit que l'opération ne dépend plus du tissu ni des ressources locales. L'état de l'opération au point de terminaison pair n'est pas défini.

Exemple : Un fournisseur peut générer un événement transmit complete lors de la réception d'un accusé de réception du point de terminaison pair. L'état du message chez le pair est inconnu et peut être mis en tampon dans la NIC cible au moment où l'accusé de réception a été généré.

Pour les points de terminaison non fiables :

Indique qu'un achèvement doit être généré lorsque l'opération a été délivrée au tissu. Un achèvement garantit que l'opération ne dépend plus des ressources locales. L'état de l'opération au sein du tissu n'est pas défini.

FI_DELIVERY_COMPLETE
Indique qu'un achèvement ne doit pas être généré tant qu'une opération n'a pas été traitée par le(s) point(s) de terminaison de destination. Un achèvement garantit que le résultat de l'opération est disponible ; cependant, des étapes supplémentaires peuvent être nécessaires à la destination pour récupérer les résultats. Par exemple, une application peut avoir besoin de fournir des tampons de réception afin de récupérer les messages mis en tampon par le fournisseur.

Delivery complete indique que le message a été traité par le pair. Si un tampon d'application était prêt à recevoir les résultats du message à son arrivée, alors delivery complete indique que les données ont été placées dans le tampon de l'application.

Ce mode d'achèvement ne s'applique qu'aux points de terminaison fiables. Pour les opérations qui renvoient des données à l'initiateur, telles que la lecture RMA ou l'atomic-fetch, le point de terminaison source est également considéré comme un point de terminaison de destination. C'est le mode d'achèvement par défaut pour de telles opérations.

FI_MATCH_COMPLETE
Indique qu'un achèvement ne doit être généré qu'après que l'opération a été appariée à un tampon spécifié par l'application. Les opérations utilisant cette sémantique d'achèvement dépendent de l'application à la cible qui réclame le message ou les résultats. Par conséquent, match complete peut impliquer des accusés de réception supplémentaires au niveau du fournisseur ou des délais importants. Cependant, ce modèle d'achèvement permet aux applications pairs de synchroniser leur exécution. De nombreux fournisseurs peuvent ne pas prendre en charge cette sémantique.
FI_COMMIT_COMPLETE
Indique qu'un achèvement ne doit pas être généré (localement ou chez le pair) tant que le résultat d'une opération n'a pas été rendu persistant. Un achèvement garantit que le résultat est à la fois disponible et durable, en cas de panne de courant.

Ce mode d'achèvement ne s'applique qu'aux opérations ciblant des régions de mémoire persistante sur des points de terminaison fiables. Ce mode d'achèvement est expérimental.

FI_FENCE
Ceci n'est pas un niveau d'achèvement, mais joue un rôle dans l'ordonnancement des achèvements entre des opérations qui ne seraient normalement pas ordonnées. Une opération marquée avec le drapeau FI_FENCE et toutes les opérations soumises après l'opération clôturée sont différées jusqu'à ce que toutes les opérations précédentes ciblant le même point de terminaison pair soient terminées. De plus, l'achèvement de l'opération clôturée indique que les opérations précédentes ont atteint le même niveau d'achèvement que l'opération clôturée. Par exemple, si une opération est soumise avec FI_DELIVERY_COMPLETE | FI_FENCE, alors son achèvement indique que les opérations précédentes ont satisfait la sémantique requise pour FI_DELIVERY_COMPLETE. C'est vrai même si l'opération précédente a été soumise avec un niveau d'achèvement inférieur, comme FI_TRANSMIT_COMPLETE ou FI_INJECT_COMPLETE.

Notez qu'un achèvement généré pour une opération soumise avant l'opération clôturée ne garantit que le niveau d'achèvement initialement demandé a été atteint. C'est l'achèvement de l'opération clôturée qui garantit que les sémantiques supplémentaires ont été satisfaites.

Les sémantiques d'achèvement ci-dessus sont définies par rapport à l'initiateur de l'opération. Les différentes sémantiques sont utiles pour décrire quand l'initiateur peut réutiliser un tampon de données, et garantissent à quel état un transfert doit parvenir avant qu'un achèvement ne soit généré. Cela permet aux applications de déterminer la gestion d'erreur appropriée en cas de défaillance de communication.

SÉMANTIQUE D'ACHÈVEMENT DE LA CIBLE

La sémantique d'achèvement à la cible est utilisée pour déterminer quand les données à la cible sont visibles par l'application pair. La visibilité indique qu'une lecture mémoire à la même adresse qui était la cible d'un transfert de données renverra les résultats du transfert. La cible d'un transfert peut être identifiée par l'initiateur, comme c'est le cas pour les opérations RMA et atomiques, ou déterminée par la cible, par exemple en fournissant un tampon de réception apparié. La visibilité globale indique que les résultats sont disponibles quelle que soit l'origine de la lecture mémoire. Par exemple, la lecture pourrait provenir d'un processus s'exécutant sur un CPU hôte, elle peut être accessible par un transfert de données ultérieur sur le tissu, ou lue depuis un appareil pair tel qu'un GPU.

En termes de sémantique d'achèvement, la visibilité indique généralement que le transfert satisfait les exigences FI_DELIVERY_COMPLETE du point de vue de la cible. La sémantique d'achèvement de la cible peut être, mais n'est pas nécessairement, liée à la sémantique d'achèvement spécifiée par l'initiateur du transfert.

Souvent, les processus de la cible ne déclarent pas explicitement une sémantique d'achèvement souhaitée et s'appuient plutôt sur la sémantique par défaut. Le comportement par défaut est basé sur plusieurs facteurs, notamment :

•
si un événement d'achèvement est même généré à la cible
•
le type de transfert impliqué (par ex. msg vs RMA)
•
les garanties d'ordonnancement des données et des messages du point de terminaison
•
les propriétés du tampon mémoire ciblé
•
la sémantique d'achèvement spécifiée par l'initiateur

De manière générale, les sémantiques d'achèvement de la cible sont regroupées en fonction du fait que le transfert génère ou non un événement d'achèvement à la cible. Cela inclut l'écriture d'une entrée CQ ou la mise à jour d'un compteur d'achèvement. Dans les cas d'utilisation courants, les transferts utilisant une interface de message (FI_MSG ou FI_TAGGED) génèrent typiquement des événements de cible, tandis que les transferts impliquant une interface RMA (FI_RMA ou FI_ATOMIC) souvent non. Il existe des exceptions à ces deux cas, selon les liaisons point de terminaison à CQ et compteur et les drapeaux opérationnels. Par exemple, les écritures RMA transportant des données CQ distantes généreront un événement d'achèvement à la cible, et sont fréquemment utilisées pour transmettre la visibilité à l'application cible. Les directives générales pour la sémantique côté cible sont décrites ci-dessous, suivies des exceptions qui modifient ce comportement.

Par défaut, les achèvements générés à la cible indiquent que les données transférées sont immédiatement disponibles pour être lues depuis le tampon de la cible. C'est-à-dire que la cible voit une sémantique FI_DELIVERY_COMPLETE (ou meilleure), même si l'initiateur a demandé une sémantique inférieure. Pour les applications utilisant uniquement des tampons de données alloués à partir de la mémoire hôte, c'est souvent suffisant.
