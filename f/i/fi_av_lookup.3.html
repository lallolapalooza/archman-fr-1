DESCRIPTIO

N

Les vecteurs d'adresses sont utilisés pour mapper des adresses de niveau supérieur, qui peuvent être plus naturelles pour une application à utiliser, vers des adresses spécifiques au fabric. Par exemple, un point de terminaison peut être associé à une adresse struct sockaddr_in, indiquant que le point de terminaison est accessible via un numéro de port TCP sur une adresse IPv4. Cela peut être le cas même si le point de terminaison communique à l'aide d'un protocole réseau propriétaire. Le but du AV est d'associer une adresse de niveau supérieur à une valeur plus simple et plus efficace qui peut être utilisée par l'API libfabric de manière indépendante du fabric. L'adresse mappée est de type fi_addr_t et est retournée via un appel d'insertion

AV.

Le processus de mappage d'une adresse est spécifique au fabric et au fournisseur, mais peut impliquer une résolution d'adresse et des protocoles de gestion de fabric longs. Les opérations AV sont synchrones par défaut (l'option asynchrone a été obsolète, voir ci-dessous). Voir la section NOTES pour les restrictions AV sur les adresses en

double.

Obsolète : les opérations AV peuvent être définies pour fonctionner de manière asynchrone en spécifiant le drapeau FI_EVENT à fi_av_open. Lors de la demande d'une opération asynchrone, l'application doit d'abord lier une file d'événements à l'AV avant d'insérer des

adresses.

fi_av_ope

n

fi_av_open alloue ou ouvre un vecteur d'adresses. Les propriétés et le comportement du vecteur d'adresses sont définis par struct

fi_av_attr. 
struct fi_av_attr {
    enum fi_av_type  type;        /* type of AV */
    int              rx_ctx_bits; /* address bits to identify rx ctx */
    size_t           count;       /* # entries for AV */
    size_t           ep_per_node; /* # endpoints per fabric address */
    const char       *name;       /* system name of AV */
    void             *map_addr;   /* base mmap address */
    uint64_t         flags;       /* operation flags
*/
}
;
ty
pe
Un type AV correspond à une implémentation conceptuelle d'un vecteur d'adresses. Le type spécifie comment une application voit les données stockées dans l'AV, y compris comment elles peuvent être accessibles. Les valeurs valides
sont :
- FI_AV_MAP
(obsolète)
Les adresses insérées dans un AV sont mappées vers une adresse fabric native pour utilisation par l'application. L'utilisation de FI_AV_MAP nécessite que l'application stocke la valeur fi_addr_t retournée associée à chaque adresse insérée. L'avantage d'utiliser FI_AV_MAP est que la valeur fi_addr_t retournée peut contenir des données d'adresse encodées, immédiatement disponibles lors du traitement des requêtes de transfert de données. Cela peut éliminer ou réduire le nombre de recherches en mémoire nécessaires pour initier un transfert. L'inconvénient de FI_AV_MAP est l'augmentation de l'utilisation mémoire nécessaire pour stocker les adresses retournées. Les adresses sont stockées dans l'AV à l'aide d'un mécanisme spécifique au fournisseur, incluant, mais sans s'y limiter, un arbre, une table de hachage, ou maintenues sur le tas. Cette option est obsolète, et les fournisseurs sont encouragés à aligner le comportement de FI_AV_MAP avec
FI_AV_TABLE.
- FI_AV_TAB
LE
Les adresses insérées dans un AV de type FI_AV_TABLE sont accessibles à l'aide d'un index simple. Conceptuellement, l'AV peut être traité comme un tableau d'adresses, bien que le fournisseur puisse implémenter l'AV à l'aide de divers mécanismes. Lorsque FI_AV_TABLE est utilisé, le fi_addr_t retourné est un index, l'index d'une adresse insérée étant le même que son ordre d'insertion dans le tableau. L'index de la première adresse insérée dans un FI_AV_TABLE sera 0, et les insertions suivantes recevront des indices séquentiels. Des indices séquentiels seront assignés à travers les appels d'insertion sur le même AV. Parce que les valeurs fi_addr_t retournées d'un appel d'insertion sont déterministes, les applications peuvent ne pas avoir besoin de fournir les paramètres de sortie fi_addr_t aux appels d'insertion. L'exception est lorsque les paramètres fi_addr_t sont également utilisés comme entrée pour fournir l'authentification clés ou des identifiants définis par
l'utilisateur.
- FI_AV_UNSP
EC
Le fournisseur choisira son type AV préféré. Le type AV utilisé sera renvoyé via le champ type dans
fi_av_attr.

Le nombre de bits demandé doit être sélectionné de telle sorte que 2 ^ rx_ctx_bits >= rx_ctx_cnt pour le point de
terminaison.

Le map_addr détermine l'adresse fi_addr_t de base qu'un fournisseur doit utiliser lors du partage d'un
AV de type FI_AV_MAP entre processus. Les processus qui fournissent la même valeur de map_addr pour

Le map_addr peut être utilisé par le fournisseur pour mmap la mémoire allouée pour un AV partagé entre processus ; cependant, le fournisseur n'est pas tenu d'utiliser le map_addr de cette manière. La relation entre le map_addr et tout fi_addr_t retourné n'est pas

définie.

- FI_EVENT
(obsolète)
Lorsque l'indicateur FI_EVENT est spécifié, toutes les opérations d'insertion sur ce AV se feront de manière asynchrone. Une entrée d'erreur EQ sera générée pour chaque échec d'insertion d'adresse, suivie d'un événement non-erreur indiquant que l'opération d'insertion est terminée. Il y aura toujours un événement de complétion non-erreur pour chaque
opération d'insertion, même si toutes les adresses échouent. Le champ context dans toutes les complétions sera le contexte spécifié pour l'appel d'insertion, et le champ data dans l'entrée de complétion finale rapportera le nombre d'adresses insérées avec succès. Si une erreur se produit lors de l'insertion asynchrone, une entrée de complétion d'erreur
est retournée (voir fi_eq(3) pour une discussion sur la structure de complétion d'erreur fi_eq_err_entry). Le champ context de la complétion d'erreur sera le contexte spécifié dans l'appel d'insertion ; le champ data contiendra l'index de l'adresse ayant échoué. Une complétion d'erreur sera retournée pour chaque adresse qui échoue à s'insérer dans le AV.

Si un AV est ouvert avec FI_EVENT, toute insertion tentée avant qu'une EQ soit liée au AV échouera avec

-FI_ENOEQ.

Les complétions d'erreur pour les insertions échouées contiendront l'index de l'adresse ayant échoué dans le champ index de l'entrée de complétion

d'erreur.

Notez que l'ordre de livraison des complétions d'insertion peut ne pas correspondre à l'ordre dans lequel les appels à fi_av_insert ont été faits. La seule garantie est que toutes les complétions d'erreur pour un appel donné à fi_av_insert précéderont la complétion non-erreur associée unique. • .RS

fi_clos

e

L'appel fi_close est utilisé pour libérer toutes les ressources associées à un vecteur d'adresses. Notez que tous les événements mis en file d'attente sur une file d'événements référençant le AV restent intacts. Il est recommandé aux appelants de récupérer tous les événements associés au AV avant de le

fermer.

Lors de la fermeture du vecteur d'adresses, il ne doit y avoir aucun point

de terminaison ouvert associé au AV. Si des ressources sont toujours assoc
iées au AV lors de la tentative de fermeture, l'appel retournera -FI_EBUSY.

fi_av_bind

(obsolète)

Associe une file d'événements au AV. Si un AV a été ouvert avec FI_EVENT, alors une file d'événements doit être liée

au AV avant toute tentative d'appel d'insertion. Tout appel d'insertion d'adresses avant qu'une file d'événement
s ait été liée échouera avec -FI_ENOEQ. Les indicateurs sont réservés pour une utilisation future et doivent être 0.

fi_av_inser

t

L'appel fi_av_insert insère zéro ou plusieurs adresses dans un AV. Le nombre d'adresses est spécifié via le paramètre count. Le paramètre addr référence un tableau d'adresses à insérer dans le AV. Les adresses insérées dans un vecteur d'adresses doivent être dans le même format que spécifié dans le champ addr_format de la structure fi_info fournie lors de l'ouverture du domaine correspondant. Lors de l'utilisation du format FI_ADDR_STR, le paramètre addr doit référencer un tableau de chaînes (char **)

.

Obsolète : Pour les AV de type FI_AV_MAP, une fois que les adresses insérées ont été mappées, les valeurs mappées sont écrites dans le tampon référencé par fi_addr. Le tampon fi_addr doit rester valide jusqu'à ce que l'insertion AV soit terminée et qu'un événement ait été généré vers une file d'événements associée. La valeur du fi_addr retourné doit être considérée comme opaque par l'application pour les AV de type FI_AV_MAP. La valeur retournée peut pointer vers une structure interne ou un encodage spécifique au fournisseur de données d'adressage de bas niveau, par exemple. Dans ce dernier cas, l'utilisation de FI_AV_MAP peut permettre d'éviter les références mémoire lors des opérations de transfert de

données.

Pour les AV de type FI_AV_TABLE, les adresses sont placées dans la table dans l'ordre. Une adresse est insérée à l'index le plus bas correspondant à un emplacement de table non utilisé, les indices commençant à 0. C'est-à-dire que la première adresse insérée peut être référencée à l'index 0, la deuxième à l'index 1, et ainsi de suite. Lorsque des adresses sont insérées dans une table AV, les valeurs fi_addr assignées seront de simples indices correspondant à l'entrée dans la table où l'adresse a été insérée. Les valeurs d'index s'accumulent au fil des appels d'insertion successifs dans l'ordre où les appels sont faits, pas nécessairement dans l'ordre où les insertions se

terminent.

Parce que les insertions se produisent à un index prédéterminé, le paramètre fi_addr peut être NULL. Si fi_addr est non-NULL, il doit référencer un tableau de fi_addr_t, et le tampon doit rester valide jusqu'à ce que l'opération d'insertion se termine. Notez que si fi_addr est NULL et qu'une opération synchrone est demandée sans utiliser l'indicateur FI_SYNC_ERR, les échecs d'insertion individuels ne peuvent pas être rapportés et l'application doit utiliser d'autres appels, tels que fi_av_lookup pour savoir quelles adresses spécifiques ont échoué à

s'insérer.

Si le vecteur d'adresses est configuré avec des clés d'autorisation, le paramètre fi_addr peut être utilisé comme entrée pour définir les clés d'autorisation associées aux adresses de point de terminaison étant insérées. Cela est fait en définissant fi_addr sur une clé d'autorisation fi_addr_t générée à partir de fi_av_insert_auth_key et en définissant l'indicateur FI_AUTH_KEY. Si l'indicateur FI_AUTH_KEY n'est pas défini, les adresses étant insérées ne seront associées à aucune clé d'autorisation. Qu'une adresse puisse ou non être dissociée d'une clé d'autorisation dépend du fournisseur. Si un fournisseur ne peut pas prendre en charge cette dissociation, une erreur sera retournée. Lors d'une insertion réussie avec l'indicateur FI_AUTH_KEY, les fi_addr_t retournés seront mappés à l'adresse du point de terminaison contre les clés d'autorisation spécifiées. Ces fi_addr_t peuvent être utilisés comme cible pour les opérations de transfert de données

locales.

Si le point de terminaison prend en charge FI_DIRECTED_RECV ou FI_TAGGED_DIRECTED_RECV, ces fi_addr_t peuvent être utilisés pour restreindre les tampons de réception à une adresse de point de terminaison et une clé d'autorisation

spécifiques.

Pour les vecteurs d'adresses configurés avec FI_AV_USER_ID, tous les événements cibles ultérieurs correspondant à l'adresse étant insérée retourneront FI_ADDR_NOTAVAIL jusqu'à ce que l'utilisateur définisse un ID utilisateur pour ce fi_addr_t. Cela est fait en utilisant fi_av_set_user_id

.

L'indicateur suivant peut être passé aux appels d'insertion AV : fi_av_insert, fi_av_insertsvc, ou

- FI_MO
RE
Afin de permettre une insertion d'adresses optimisée, l'application peut spécifier l'indicateur FI_MORE à l'appel d'insertion pour donner un indice au fournisseur que plus de requêtes d'insertion suivront, permettant au fournisseur d'agréger les requêtes d'insertions si souhaité. Une application peut effectuer un nombre quelconque d'appels d'insertion avec FI_MORE défini, à condition qu'ils soient suivis d'un appel d'insertion sans FI_MORE. Cela indique au fournisseur que la liste d'insertion est complète. Les fournisseurs sont libres d'ignorer FI_MORE.
- FI_SYNC_ERR
Ce drapeau s'applique uniquement aux insertions synchrones et est utilisé pour récupérer les détails d'erreur des insertions échouées. S'il est défini, le paramètre contexte des appels d'insertion référence un tableau d'entiers, avec contexte défini à l'adresse du premier élément du tableau. Le résultat de la tentative d'insertion de chaque adresse sera écrit à l'emplacement correspondant du tableau. Les insertions réussies seront mises à jour à 0. Les échecs contiendront un code errno de fabric.
- FI_AV_USER_ID
Pour les vecteurs d'adresses configurés sans FI_AV_USER_ID spécifié, ce drapeau associe un identifiant assigné par l'utilisateur à chaque entrée AV qui est retournée avec n'importe quelle entrée de complétion à la place de l'adresse de l'AV. Si un fournisseur ne supporte pas FI_AV_USER_ID avec insert, demander ce drapeau lors d'une insertion entraînera une erreur d'exécution.

L'utilisation du drapeau FI_AV_USER_ID par insertion est invalide si l'AV a été ouverte avec FI_AV_USER_ID ou si le domaine correspondant a été configuré avec FI_AV_AUTH_KEY.

Avec libfabric 1.20, il est recommandé aux utilisateurs de spécifier le FI_AV_USER_ID lors de l'ouverture d'une AV et d'utiliser fi_av_set_user_id. • .RS 2

FI_FIREWALL_ADDR
Ce drapeau indique que l'adresse se trouve derrière un pare-feu et que les connexies sortantes ne sont pas autorisées. S'il n'existe pas de connexion et que le fournisseur ne peut pas contourner le pare-feu, une erreur FI_EFIREWALLADDR doit être attendue. Si plusieurs adresses sont insérées simultanément, le drapeau s'applique à toutes. De plus, il est possible qu'une connexion soit disponible au moment de l'insertion, mais qu'elle soit ensuite interrompue. Les reconnexions futures déclenchées par des opérations sur l'ep (fi_send, par exemple) peuvent également échouer avec la même erreur.

fi_av_insertsvc

L'appel fi_av_insertsvc se comporte de manière similaire à fi_av_insert, mais permet à l'application de spécifier les noms de nœud et de service, similairement aux entrées de fi_getinfo, plutôt qu'une adresse encodée. Les paramètres node et service sont définis de la même manière que dans fi_getinfo(3). Node doit être une chaîne correspondant à un nom d'hôte ou à une adresse réseau. La chaîne service correspond à une représentation textuelle d'une adresse de transport. Les applications peuvent également passer une adresse au format FI_ADDR_STR en paramètre node. Dans de tels cas, le paramètre service doit être NULL. Voir fi_getinfo.3 pour les détails sur l'utilisation de FI_ADDR_STR. Les drapeaux supportés sont les mêmes que pour fi_av_insert.

fi_av_insertsym

fi_av_insertsym effectue une insertion symétrique qui insère une plage séquentielle de nœuds et/ou d'adresses de service dans une AV. Le paramètre svccnt indique le nombre d'adresses de transport (point de terminaison) à insérer dans la AV pour chaque adresse de nœud, avec le paramètre service spécifiant l'adresse de transport de départ. Les adresses de transport insérées seront dans la plage {service, service + svccnt - 1}, inclusive. Toutes les adresses de service d'un nœud seront insérées avant que le nœud suivant ne soit inséré.

Le paramètre nodecnt indique le nombre d'adresses de nœud (réseau) à insérer dans la AV, avec le paramètre node spécifiant l'adresse de nœud de départ. Les adresses de nœud insérées seront dans la plage {node, node + nodecnt - 1}, inclusive. Si node est une chaîne non numérique, telle qu'un nom d'hôte, elle doit contenir un suffixe numérique si nodecnt > 1.

À titre d'exemple, si node = “10.1.1.1”, nodecnt = 2, service = “5000” et svccnt = 2, les adresses suivantes seront insérées dans la AV dans l'ordre indiqué : 10.1.1.1:5000, 10.1.1.1:5001, 10.1.1.2:5000, 10.1.1.2:5001. Si node était remplacé par le nom d'hôte “host10”, les adresses seraient : host10:5000, host10:5001, host11:5000, host11:5001.

Le nombre total d'adresses insérées sera nodecnt x svccnt.

Les drapeaux supportés sont les mêmes que pour fi_av_insert.

fi_av_remove

fi_av_remove supprime un ensemble d'adresses d'un vecteur d'adresses. Les valeurs fi_addr_t correspondantes sont invalidées et ne peuvent pas être utilisées dans des appels de transfert de données. Le comportement des opérations en cours qui référencent les adresses supprimées est indéfini.

Notez que la suppression d'une adresse peut ne pas désactiver la réception de données depuis le point de terminaison pair. fi_av_close nettoiera automatiquement toute ressource associée.

Si l'adresse supprimée provient de fi_av_insert_auth_key, l'adresse ne sera supprimée que si tous les points de terminaison, qui ont été activés contre la clé d'autorisation correspondante, ont été fermés. Si tous les points de terminaison ne sont pas fermés, -FI_EBUSY sera retourné. De plus, le drapeau FI_AUTH_KEY doit être défini lors de la suppression d'une clé d'autorisation fi_addr_t.

fi_av_lookup

Cet appel retourne l'adresse stockée dans le vecteur d'adresses qui correspond au fi_addr donné. L'adresse retournée est au même format que celles stockées par la AV. En entrée, le paramètre addrlen doit indiquer la taille du tampon addr. Si l'adresse réelle est plus grande que ce qui peut tenir dans le tampon, elle sera tronquée. En sortie, addrlen est défini à la taille du tampon nécessaire pour stocker l'adresse, qui peut être plus grande que la valeur d'entrée.

fi_rx_addr

Cette fonction est utilisée pour convertir une adresse de point de terminaison, retournée par fi_av_insert, en une adresse qui spécifie un contexte de réception cible. La valeur de rx_ctx_bits doit correspondre à celle spécifiée dans les attributs de la AV pour l'adresse donnée.

Les points de terminaison connectés qui supportent plusieurs contextes de réception, mais qui ne sont pas associés à des vecteurs d'adresses, doivent spécifier FI_ADDR_NOTAVAIL pour le paramètre fi_addr.

fi_av_straddr

La fonction fi_av_straddr convertit l'adresse fournie en une chaîne imprimable. L'adresse spécifiée doit être au même format que celles stockées par la AV, bien que l'adresse elle-même n'ait pas besoin d'avoir été insérée. En entrée, le paramètre len doit spécifier la taille du tampon référencé par buf. En sortie, addrlen est défini à la taille du tampon nécessaire pour stocker l'adresse. Cette taille peut être plus grande que la longueur d'entrée. Si le tampon fourni est trop petit, les résultats seront tronqués. fi_av_straddr retourne un pointeur vers buf.

fi_av_insert_auth_key

Cette fonction associe des clés d'autorisation à un vecteur d'adresses. Cela nécessite que le domaine soit ouvert avec FI_AV_AUTH_KEY. FI_AV_AUTH_KEY permet aux points de terminaison et aux régions mémoire d'être associés à des clés d'autorisation depuis le vecteur d'adresses. Ce comportement permet à un point de terminaison ou à une région mémoire unique d'être associé à plusieurs clés d'autorisation.

Lorsque les points de terminaison ou les régions mémoire sont activés, ils sont configurés avec les clés d'autorisation du vecteur d'adresses à ce moment-là. Les insertions ultérieures de clés d'autorisation ne se propageront pas aux points de terminaison et aux régions mémoire déjà activés.

Les paramètres auth_key et auth_key_size sont utilisés pour entrer la clé d'autorisation dans le vecteur d'adresses. La structure de la clé d'autorisation est spécifique au fournisseur. Si auth_key_size ne correspond pas à la structure spécifique au fournisseur, -FI_EINVAL sera retourné.

La sortie de fi_av_insert_auth_key est un gestionnaire de clé d'autorisation fi_addr_t représentant toutes les adresses de point de terminaison contre cette clé d'autorisation spécifique. Pour toutes les opérations, y compris le vecteur d'adresses, l'enregistrement mémoire et les transferts de données, qui peuvent accepter une clé d'autorisation fi_addr_t en entrée, le drapeau FI_AUTH_KEY doit être spécifié. Sinon, le fi_addr_t sera traité comme un fi_addr_t retourné par fi_av_insert et les fonctions associées.

Pour les points de terminaison activés avec FI_DIRECTED_RECV, les clés d'autorisation fi_addr_t peuvent être utilisées pour restreindre les messages entrants aux seules adresses de point de terminaison au sein de la clé d'autorisation. Cela nécessitera de passer le drapeau FI_AUTH_KEY à fi_recvmsg et fi_trecvmsg.

Pour les domaines activés avec FI_DIRECTED_RECV, les clés d'autorisation fi_addr_t peuvent être utilisées pour restreindre l'accès aux régions mémoire aux seules adresses de point de terminaison au sein de la clé d'autorisation. Cela nécessitera de passer le drapeau FI_AUTH_KEY à fi_mr_regattr.

Ces clés d'autorisation fi_addr_t peuvent ensuite être utilisées comme entrée pour les fonctions d'insertion d'adresse de point de terminaison pour générer un fi_addr_t pour une adresse de point de terminaison et une clé d'autorisation spécifiques. Cela nécessitera de passer le drapeau FI_AUTH_KEY à fi_av_insert et les fonctions associées.

Pour les vecteurs d'adresses configurés avec FI_AV_USER_ID et les points de terminaison avec FI_SOURCE_ERR, tous les événements d'erreur FI_EADDRNOTAVAIL ultérieurs retourneront FI_ADDR_NOTAVAIL jusqu'à ce que l'utilisateur définisse un ID utilisateur pour cette clé d'autorisation fi_addr_t. Cela se fait en utilisant fi_av_set_user_id.

Pour les vecteurs d'adresses configurés sans FI_AV_USER_ID et les points de terminaison avec FI_SOURCE_ERR, tous les événements d'erreur FI_EADDRNOTAVAIL ultérieurs retourneront le gestionnaire de clé d'autorisation fi_addr_t.

Les drapeaux sont réservés pour une utilisation future et doivent être 0.

The addresses in an AV represent the full set of peers that a local process may communicate with. A peer group conceptually represents a subset of those peers. A peer group may be used to identify peers working on a common task, which need their communication logically separated from other traffic. Peer groups are not a security mechanism, but instead help separate data. A given peer may belong to 0 or more peer groups, with no limit placed on how many peers can belong to a single peer group.
