DESCRIPTION

Les files d'attente de complétion sont utilisées pour signaler les événements associés aux transferts de données. Elles sont associées aux envois et réceptions de messages, à la mémoire distante (RMA), aux opérations atomiques, aux messages tagués et aux événements déclenchés. Les événements signalés sont généralement associés à un point d'accès réseau (endpoint), mais peuvent également faire référence à des régions mémoire utilisées comme cible d'une opération RMA ou atomique.

fi_cq_open

fi_cq_open alloue une nouvelle file d'attente de complétion. Contrairement aux files d'attente d'événements, les files d'attente de complétion sont associées à un domaine de ressources et peuvent être entièrement déchargées sur le matériel du fournisseur.

Les propriétés et le comportement d'une file d'attente de complétion sont définis par la structure fi_cq_attr.

struct fi_cq_attr {
    size_t               size;      /* # entrées pour la CQ */
    uint64_t             flags;     /* indicateurs d'opération */
    enum fi_cq_format    format;    /* format de complétion */
    enum fi_wait_obj     wait_obj;  /* objet d'attente demandé */
    int                  signaling_vector; /* affinité d'interruption */
    enum fi_cq_wait_cond wait_cond; /* format de condition d'attente */
    struct fid_wait     *wait_set;  /* jeu d'attente facultatif, déprécié */
};
size
Spécifie la taille minimale d'une file d'attente de complétion. Une valeur de 0 indique que le fournisseur peut choisir une valeur par défaut.
flags
Indicateurs qui contrôlent la configuration de la CQ.
- FI_AFFINITY
Indique que le champ signaling_vector (voir ci-dessous) est valide.
format
Les files d'attente de complétion permettent à l'application de sélectionner la quantité de détails à stocker et à signaler. L'attribut format permet à l'application de sélectionner l'un des plusieurs formats de complétion, indiquant la structure des données que la file d'attente de complétion doit retourner lors de la lecture. Les formats pris en charge et les structures correspondantes sont listés ci-dessous. La signification des champs d'entrée de la CQ est définie dans la section Champs de complétion.
- FI_CQ_FORMAT_UNSPEC
Si un format non spécifié est demandé, la CQ utilisera un format par défaut sélectionné par le fournisseur.
- FI_CQ_FORMAT_CONTEXT
Ne fournit que le contexte spécifié par l'utilisateur associé à la complétion.

wait_obj
Les CQ peuvent être associées à un objet d'attente spécifique. Les objets d'attente permettent aux applications de bloquer jusqu'à ce que l'objet d'attente soit signalé, indiquant qu'une complétion est disponible à lire. Les utilisateurs peuvent utiliser fi_control pour récupérer l'objet d'attente sous-jacent associé à une CQ, afin de l'utiliser dans d'autres appels système. type d'objet d'attente associé à une CQ : FI_WAIT_NONE, FI_WAIT_UNSPEC, FI_WAIT_SET, FI_WAIT_FD, FI_WAIT_MUTEX_COND (obsolète), et FI_WAIT_YIELD. La valeur par défaut est FI_WAIT_NONE.
- FI_WAIT_NONE
Utilisé pour indiquer que l'utilisateur ne bloquera pas (n'attendra pas) les complétions sur la CQ. Lorsque FI_WAIT_NONE est spécifié, l'application ne peut pas appeler fi_cq_sread ou fi_cq_sreadfrom.
- FI_WAIT_UNSPEC
Spécifie que l'utilisateur attendra sur la CQ uniquement à l'aide d'appels d'interface fabric, tels que fi_cq_sread ou fi_cq_sreadfrom. Dans ce cas, le fournisseur sous-jacent peut sélectionner l'objet d'attente le plus approprié ou le plus performant disponible, y compris des mécanismes d'attente personnalisés. Les applications qui sélectionnent FI_WAIT_UNSPEC ne sont pas garanties de récupérer l'objet d'attente sous-jacent.
- FI_WAIT_SET (obsolète)
Indique que la file d'attente de complétion doit utiliser un objet d'ensemble d'attente pour attendre les complétions. Si spécifié, le champ wait_set doit référencer un objet d'ensemble d'attente existant.
- FI_WAIT_FD
Indique que la CQ doit utiliser un descripteur de fichier comme mécanisme d'attente. Un objet d'attente de descripteur de fichier doit être utilisable dans les routines select, poll et epoll. Cependant, un fournisseur peut signaler un objet d'attente FD en le marquant comme lisible, inscriptible ou avec une erreur.
- FI_WAIT_MUTEX_COND (obsolète)
Spécifie que la CQ doit utiliser un mutex pthread et une variable de condition comme objet d'attente.
- FI_WAIT_YIELD
Indique que la CQ attendra sans objet d'attente mais cédera à chaque attente. Permet l'utilisation de fi_cq_sread et fi_cq_sreadfrom via une boucle d'attente active (spin).
signaling_vector
Si l'indicateur FI_AFFINITY est défini, cela indique le numéro de CPU logique (0..nombre maximal de CPU - 1) que les interruptions associées à la CQ doivent cibler. Ce champ doit être traité comme un indice pour le fournisseur et peut être ignoré si le fournisseur ne prend pas en charge l'affinité d'interruption.
wait_cond
Par défaut, lorsqu'une complétion est insérée dans une CQ qui prend en charge les lectures bloquantes (fi_cq_sread/fi_cq_sreadfrom), l'objet d'attente correspondant est signalé. Les utilisateurs peuvent spécifier une condition qui doit d'abord être remplie avant que l'attente ne soit satisfaite. Ce champ indique comment le fournisseur doit interpréter le champ cond, qui décrit la condition nécessaire pour signaler l'objet d'attente.

Une condition d'attente doit être traitée comme une optimisation. Les fournisseurs ne sont pas tenus de répondre aux exigences de la condition avant de signaler l'objet d'attente. Les applications ne doivent pas s'appuyer sur le fait que la condition est nécessairement vraie lorsqu'un appel de lecture bloquant retourne.

Si wait_cond est défini sur FI_CQ_COND_NONE, aucune condition supplémentaire n'est appliquée au signalement de l'objet d'attente de la CQ, et l'insertion de toute nouvelle entrée déclenchera la condition d'attente. Si wait_cond est défini sur FI_CQ_COND_THRESHOLD, le champ cond est interprété comme une valeur de seuil size_t. Le seuil indique le nombre d'entrées qui doivent être mises en file d'attente dans la CQ avant que l'attente ne soit satisfaite.

Ce champ est ignoré si wait_obj est défini sur FI_WAIT_NONE.

wait_set (obsolète)
Si wait_obj est FI_WAIT_SET, ce champ référence un objet d'attente auquel la file d'attente de complétion doit s'attacher. Lorsqu'un événement est inséré dans la file d'attente de complétion, l'ensemble d'attente correspondant sera signalé si toutes les conditions nécessaires sont remplies. L'utilisation d'un wait_set permet une méthode optimisée d'attente d'événements sur plusieurs files d'attente d'événements et de complétion. Ce champ est ignoré si wait_obj n'est pas FI_WAIT_SET.

fi_close

L'appel fi_close libère toutes les ressources associées à une file d'attente de complétion. Toutes les complétions qui restent sur la CQ lorsqu'elle est fermée sont perdues.

Lors de la fermeture de la CQ, il ne doit y avoir aucun point de terminaison (endpoint) ouvert, aucun contexte d'émission (transmit context) ou aucun contexte de réception (receive context) associé à la CQ. Si des ressources sont toujours associées à la CQ lors de la tentative de fermeture, l'appel retournera -FI_EBUSY.

fi_control

L'appel fi_control est utilisé pour accéder aux détails spécifiques au fournisseur ou à l'implémentation de la file d'attente de complétion. L'accès à la CQ doit être sérialisé sur tous les appels lors de l'invocation de fi_control, car il peut rediriger l'implémentation des opérations de CQ. Les commandes de contrôle suivantes sont utilisables avec une CQ.

FI_GETWAIT (void **)
Cette commande permet à l'utilisateur de récupérer l'objet d'attente de bas niveau associé à la CQ. Le format de l'objet d'attente est spécifié lors de la création de la CQ, via les attributs de la CQ. Le paramètre d'argument fi_control doit être une adresse où un pointeur vers l'objet d'attente retourné sera écrit. Voir fi_eq.3 pour des détails supplémentaires sur l'utilisation de fi_control avec FI_GETWAIT.

fi_cq_read

L'opération fi_cq_read effectue une lecture non bloquante des données de complétion à partir de la CQ. Le format de l'événement de complétion est déterminé à l'aide de l'option fi_cq_format qui a été spécifiée lors de l'ouverture de la CQ. Plusieurs complétions peuvent être récupérées d'une CQ en un seul appel. Le nombre maximal d'entrées à retourner est limité au paramètre count spécifié, le nombre d'entrées effectivement lues à partir de la CQ étant retourné par l'appel. (Voir la section sur les valeurs de retour ci-dessous.) Une valeur de count de 0 peut être utilisée pour faire progresser les points de terminaison associés lorsque la progression manuelle est activée.

Les CQ sont optimisées pour signaler les opérations qui se sont terminées avec succès. Les opérations qui échouent sont signalées "hors bande". Ces opérations sont récupérées à l'aide de la fonction fi_cq_readerr. Lorsqu'une opération qui s'est terminée avec une erreur inattendue est rencontrée, elle est placée dans une file d'erreurs temporaire. Tenter de lire à partir d'une CQ pendant qu'un élément est dans la file d'erreurs entraîne l'échec de fi_cq_read avec un code de retour de -FI_EAVAIL. Les applications peuvent utiliser ce code de retour pour déterminer quand appeler fi_cq_readerr.

fi_cq_readfrom

L'appel fi_cq_readfrom se comporte de manière identique à fi_cq_read, à la différence qu'il permet à la CQ de retourner des informations d'adresse source à l'utilisateur pour toutes les données reçues. Les données d'adresse source ne sont disponibles que pour les points de terminaison configurés avec la capacité FI_SOURCE. Si fi_cq_readfrom est appelé sur un point de terminaison pour lequel les données d'adressage source ne sont pas disponibles, l'adresse source sera définie sur FI_ADDR_NOTAVAIL. Le nombre d'entrées src_addr d'entrée doit être le même que le paramètre count.

Les données d'adressage source retournées sont converties de l'adresse native utilisée par le fabric sous-jacent en un fi_addr_t, qui peut être utilisé dans les opérations de transmission. Dans la plupart des cas, le retour de fi_addr_t nécessite que l'adresse source ait déjà été insérée dans le vecteur d'adresses associé au point de terminaison de réception. C'est le cas pour les vecteurs d'adresses de type FI_AV_TABLE. Dans certains fournisseurs (select providers), lorsque FI_AV_MAP est utilisé, les adresses source peuvent être converties algorithmiquement en un fi_addr_t utilisable, même si l'adresse source n'a pas été insérée dans le vecteur d'adresses. Ceci est autorisé par l'API, car cela permet au fournisseur d'éviter la recherche d'adresses dans le cadre du traitement des messages de réception. Dans aucun cas, les fournisseurs n'insèrent des adresses dans un AV séparément d'une application appelant fi_av_insert ou un appel similaire.

Pour les points de terminaison alloués avec la capacité FI_SOURCE_ERR, si l'adresse source ne peut pas être convertie en une valeur fi_addr_t valide, fi_cq_readfrom retournera -FI_EAVAIL, même si les données ont été reçues avec succès. La complétion sera alors rapportée via fi_cq_readerr avec le code d'erreur -FI_EADDRNOTAVAIL. Voir fi_cq_readerr pour les détails.

Si FI_SOURCE est spécifié sans FI_SOURCE_ERR, les adresses source qui ne peuvent pas être mappées à un fi_addr_t utilisable seront signalées comme FI_ADDR_NOTAVAIL.

fi_cq_sread / fi_cq_sreadfrom

Les appels fi_cq_sread et fi_cq_sreadfrom sont les équivalents bloquants des opérations fi_cq_read et fi_cq_readfrom. Leur comportement est similaire aux appels non bloquants, à la différence que les appels ne retourneront pas tant qu'une complétion n'a pas été lue à partir de la CQ ou qu'une erreur ou un délai d'attente ne s'est produit.

Les threads bloquant dans cette fonction retourneront à l'appelant s'ils sont signalés par une source externe. Ceci est vrai même si le délai d'attente n'a pas expiré ou était spécifié comme infini.

Il est invalide pour les applications d'appeler ces fonctions si la CQ a été configurée avec un objet d'attente de FI_WAIT_NONE ou FI_WAIT_SET.

fi_cq_readerr

La fonction de lecture d'erreur, fi_cq_readerr, récupère les informations concernant toute opération asynchrone qui s'est terminée avec une erreur inattendue. fi_cq_readerr est un appel non bloquant, retournant immédiatement, qu'une complétion d'erreur ait été trouvée ou non.

Les informations d'erreur sont rapportées à l'utilisateur via la structure fi_cq_err_entry. Le format de cette structure est défini ci-dessous.

struct fi_cq_err_entry {
    void     *op_context; /* contexte de l'opération */
    uint64_t flags;       /* indicateurs de complétion */
    size_t   len;         /* taille des données reçues */
    void     *buf;        /* tampon de données de réception */
    uint64_t data;        /* données de complétion */
    uint64_t tag;         /* tag du message */
    size_t   olen;        /* longueur de dépassement (overflow) */
    int      err;         /* code d'erreur positif */
    int      prov_errno;  /* code d'erreur du fournisseur */
    void    *err_data;    /* données d'erreur */
    size_t   err_data_size; /* taille de err_data */
    fi_addr_t src_addr; /* adresse source de l'erreur */
};

La raison générale de l'erreur est fournie par le champ err. Des informations d'erreur spécifiques au fournisseur peuvent également être disponibles via les champs prov_errno et err_data. Les utilisateurs peuvent appeler fi_cq_strerror pour convertir les informations d'erreur spécifiques au fournisseur en une chaîne imprimable à des fins de débogage. Voir les détails des champs ci-dessous pour plus d'informations sur l'utilisation de err_data et err_data_size.

Notez que les complétions d'erreur sont générées pour toutes les opérations, y compris celles pour lesquelles aucune complétion n'a été demandée (par exemple, un point de terminaison est configuré

igured avec FI_SELECTIVE_COMPLETION, mais la requête n'avait pas le drapeau FI_COMPLETION défini). Dans de tels cas, les fournisseurs renverront autant d'informations que possible à partir du logiciel et du matériel sous-jacents concernant l'échec ; d'autres champs seront définis sur NULL ou 0. Cela inclut la valeur op_context, qui peut ne pas avoir été fournie ou a été ignorée en entrée dans le cadre du transfert.

Les codes d'erreur de complétion notables sont indiqués ci-dessous.

FI_EADDRNOTAVAIL
Ce code d'erreur est utilisé par les CQ configurés avec FI_SOURCE_ERR pour signaler les complétions pour lesquelles une adresse source fi_addr_t utilisable n'a pas pu être trouvée. Un code d'erreur de FI_EADDRNOTAVAIL indique que le transfert de données a été reçu et traité avec succès, avec les champs fi_cq_err_entry contenant des informations sur la complétion. Le champ err_data sera défini sur les données de l'adresse source. L'adresse source sera dans le même format que spécifié via le champ fi_info addr_format pour le domaine ouvert. Elle peut être passée directement à un appel fi_av_insert pour ajouter l'adresse source au vecteur d'adresses.

Pour les versions d'API 1.20 et ultérieures, si l'EP est configuré avec FI_AV_AUTH_KEY, src_addr sera défini sur le handle de clé d'autorisation fi_addr_t ou un ID de clé d'autorisation défini par l'utilisateur correspondant au transfert de données entrant. Sinon, la valeur sera définie sur FI_ADDR_NOTAVAIL.

fi_cq_signal

L'appel fi_cq_signal débloquera tout thread en attente dans fi_cq_sread ou fi_cq_sreadfrom. Il peut être utilisé pour réveiller un thread qui est bloqué en attendant de lire une opération de complétion. L'opération fi_cq_signal n'est disponible que si le CQ a été configuré avec un objet d'attente.

CHAMPS  DE  COMPLETION

Les structures de données des entrées CQ partagent de nombreux champs identiques. Les significations de ces champs sont les mêmes pour tous les formats de structures d'entrée CQ.

op_context
Le contexte d'opération est la valeur de contexte spécifiée par l'application qui a été fournie avec une opération asynchrone. Le champ op_context est valide pour toutes les complétions associées à une opération asynchrone.

Pour les événements de complétion qui ne sont pas associés à une opération publiée, ce champ sera défini sur NULL. Cela inclut les complétions générées à la cible en réponse aux opérations d'écriture RMA qui transportent des données CQ (drapeaux FI_REMOTE_WRITE | FI_REMOTE_CQ_DATA définis), lorsque le bit de mode FI_RX_CQ_DATA n'est pas requis.

flags
Ceci spécifie les drapeaux associés à l'opération terminée. La section Drapeaux de complétion ci-dessous liste les valeurs de drapeaux valides. Les drapeaux sont définis pour toutes les complétions pertinentes.
len
Ce champ len s'applique aux opérations de réception terminées (par exemple, fi_recv, fi_trecv, etc.) et à l'écriture terminée avec données cq distantes côté répondeur (par exemple, fi_write, avec le drapeau FI_REMOTE_CQ_DATA). Il indique la taille des données de *message* transférées – c'est-à-dire la quantité d'octets de données placés dans le tampon de réception/cible associé par un appel fi_send/fi_tsend/fi_write et al correspondant. Si un point de terminaison a été configuré avec le mode FI_MSG_PREFIX, len reflète également la taille du tampon de préfixe.
buf
Le champ buf n'est valide que pour les opérations de réception terminées, et s'applique uniquement lorsque le tampon de réception a été publié avec le drapeau FI_MULTI_RECV. Dans ce cas, buf pointe vers l'emplacement de départ où les données de réception ont été placées.
data
Le champ data n'est valide que si le drapeau de complétion FI_REMOTE_CQ_DATA est défini, et ne s'applique qu'aux complétions de réception. Si FI_REMOTE_CQ_DATA est défini, ce champ contiendra les données de complétion fournies par le pair dans le cadre de sa demande de transmission. Les données de complétion seront fournies dans l'ordre des octets hôtes.
tag
Une balise s'applique uniquement aux messages reçus via les interfaces balisées. Ce champ contient la balise incluse avec le message reçu. La balise sera dans l'ordre des octets hôtes.
olen
Le champ olen s'applique aux messages reçus. Il est utilisé pour indiquer qu'un message reçu a dépassé l'espace tampon disponible et a été tronqué. olen spécifie la quantité de données qui n'a pas pu tenir dans le tampon de réception disponible et qui a été rejetée.
err
Ce code d'erreur est un errno du tissu positif associé à une complétion. La valeur err indique la raison générale d'une erreur, si une s'est produite. Voir fi_errno.3 pour une liste des codes d'erreur possibles.
prov_errno
En cas d'erreur, prov_errno peut contenir un code d'erreur spécifique au fournisseur. L'utilisation de ce champ et sa signification sont spécifiques au fournisseur. Il est destiné à être utilisé comme aide au débogage. Voir fi_cq_strerror pour plus de détails sur la conversion de cette valeur d'erreur en une chaîne lisible par l'homme.
err_data
Le champ err_data est utilisé pour retourner des informations spécifiques au fournisseur, si disponibles, sur l'erreur. En entrée, err_data doit référencer un tampon de données de taille err_data_size. En sortie, le fournisseur remplira ce tampon avec toute donnée spécifique au fournisseur qui peut aider à identifier la cause de l'erreur. Le contenu du champ err_data et sa signification sont spécifiques au fournisseur. Il est destiné à être utilisé comme aide au débogage. Voir fi_cq_strerror pour plus de détails sur la conversion de ces données d'erreur en une chaîne lisible par l'homme. Voir la note de compatibilité ci-dessous sur la façon dont ce champ est utilisé pour les anciennes versions de libfabric.
err_data_size
En entrée, err_data_size indique la taille du tampon err_data en octets. En sortie, err_data_size sera défini sur le nombre d'octets copiés dans le tampon err_data. Les informations err_data sont généralement utilisées avec fi_cq_strerror pour fournir des détails sur le type d'erreur qui s'est produit.

À des fins de compatibilité, le comportement des champs err_data et err_data_size peut être modifié par rapport à ce qui est indiqué ci-dessus. Si err_data_size est 0 en entrée, ou si le tissu a été ouvert avec la version < 1.5, alors tout tampon référencé par err_data sera ignoré en entrée. Dans cette situation, en sortie, err_data sera défini sur un tampon de données détenu par le fournisseur. Le contenu du tampon restera valide jusqu'à un appel de lecture ultérieur sur le CQ. Les applications doivent sérialiser l'accès au CQ lors du traitement des erreurs pour s'assurer que le tampon référencé par err_data ne change pas.

src_addr
Utilisé pour retourner des informations relatives aux adresses source pour les événements d'erreur. La façon dont ce champ est utilisé dépend de l'événement d'erreur.

DRAPEAUX  DE  COMPLETION

Les drapeaux de complétion fournissent des détails supplémentaires concernant l'opération terminée. Les drapeaux de complétion suivants sont définis.

FI_SEND
Indique que la complétion était pour une opération d'envoi. Ce drapeau peut être combiné avec un drapeau FI_MSG ou FI_TAGGED.
FI_RECV
Indique que la complétion était pour une opération de réception. Ce drapeau peut être combiné avec un drapeau FI_MSG ou FI_TAGGED.
FI_RMA
Indique qu'une opération RMA est terminée. Ce drapeau peut être combiné avec un drapeau FI_READ, FI_WRITE, FI_REMOTE_READ ou FI_REMOTE_WRITE.
FI_ATOMIC
Indique qu'une opération atomique est terminée. Ce drapeau peut être combiné avec un drapeau FI_READ, FI_WRITE, FI_REMOTE_READ ou FI_REMOTE_WRITE.
FI_MSG
Indique qu'une opération basée sur des messages est terminée. Ce drapeau peut être combiné avec un drapeau FI_SEND ou FI_RECV.
FI_TAGGED
Indique qu'une opération de message balisé est terminée. Ce drapeau peut être combiné avec un drapeau FI_SEND ou FI_RECV.
FI_MULTICAST
Indique qu'une opération de multidiffusion est terminée. Ce drapeau peut être combiné avec FI_MSG et les drapeaux pertinents. Ce drapeau n'est garanti d'être valide pour les messages reçus que si le point de terminaison a été configuré avec FI_SOURCE.
FI_READ
Indique qu'une opération de lecture RMA ou atomique initiée localement est terminée. Ce drapeau peut être combiné avec un drapeau FI_RMA ou FI_ATOMIC.
FI_WRITE
Indique qu'une opération d'écriture RMA ou atomique initiée localement est terminée. Ce drapeau peut être combiné avec un drapeau FI_RMA ou FI_ATOMIC.
FI_REMOTE_READ
Indique qu'une opération de lecture RMA ou atomique initiée à distance est terminée. Ce drapeau peut être combiné avec un drapeau FI_RMA ou FI_ATOMIC.
FI_REMOTE_WRITE
Indique qu'une opération d'écriture RMA ou atomique initiée à distance est terminée. Ce drapeau peut être combiné avec un drapeau FI_RMA ou FI_ATOMIC.
FI_REMOTE_CQ_DATA
Ceci indique que des données CQ distantes sont disponibles dans le cadre de la complétion.
FI_MULTI_RECV
Ce drapeau s'applique aux tampons de réception qui ont été publiés avec le drapeau FI_MULTI_RECV défini. Ce drapeau de complétion indique que le tampon de réception d'origine référencé par la complétion a été consommé et libéré par le fournisseur. Les fournisseurs peuvent définir ce drapeau sur le dernier message reçu dans le tampon multi-réception, ou peuvent générer une complétion distincte indiquant que le tampon a été libéré.

Les applications peuvent distinguer entre ces deux cas en examinant le champ des drapeaux de l'entrée de complétion. Si des drapeaux supplémentaires, tels que FI_RECV, sont définis, la complétion est associée à un message reçu. Dans ce cas

e, le champ buf fera référence à l'emplacement où le message reçu a été placé dans le tampon de réception multiple. Les autres ch

amps de l'entrée d'achèvement seront déterminés en fonction du message reçu. Si les autres bits de drapeau sont à zéro, le fourni
sseur indique que le tampon de réception multiple a été libéré et que l'entrée d'achèvement n'est pas associée à un message reçu.

D'ACHÈVEMENT

Libfabric définit plusieurs « niveaux » d'achèvement, identifiés à l'aide de drapeaux opérationnels. Chaque drapeau indique le plus tôt auquel un événement d'achèvement peut être généré par un fournisseur, et les hypothèses qu'une application peut faire lors du traitement d'un achèvement. Les drapeaux opérationnels sont définis ci-dessous, avec un exemple de la manière dont un fournisseur pourrait implémenter la sémantique. Notez que seule la conformité à la sémantique est requise du fournisseur, et non l'implémentation. Les fournisseurs peuvent implémenter des sémantiques d'achèvement plus fortes que nécessaire pour une opération donnée, mais seul le comportement défini par le niveau d'achèvement est

garanti.

Pour aider à comprendre les différences conceptuelles entre les niveaux d'achèvement, considérez l'envoi d'une lettre. Placer la lettre dans la boîte aux lettres locale pour la collecte est similaire à « inject complete ». Avoir la lettre collectée et déposée dans la boîte aux lettres de destination équivaut à « transmit complete ». La sémantique « delivery complete » est une garantie plus forte, avec une personne à la destination signant pour la lettre. Cependant, la personne qui a signé pour la lettre n'est pas nécessairement le destinataire prévu. L'option « match complete » est similaire à delivery complete, mais exige que le destinataire prévu signe pour la

lettre.

Le niveau « commit complete » a des sémantiques différentes des niveaux mentionnés précédemment. Commit complete serait plus proche de la lettre arrivant à la destination et étant placée dans un coffre-fort

ignifugé.

SÉMANTIQUES D'ACHÈVEMENT À LA

CIBLE

La sémantique d'achèvement à la cible est utilisée pour déterminer quand les données à la cible sont visibles par l'application paire. La visibilité indique qu'une lecture mémoire au même adresse qui était la cible d'un transfert de données retournera les résultats du transfert. La cible d'un transfert peut être identifiée par l'initiateur, comme c'est le cas pour les opérations RMA et atomiques, ou déterminée par la cible, par exemple en fournissant un tampon de réception appariant. La visibilité globale indique que les résultats sont disponibles quelle que soit l'origine de la lecture mémoire. Par exemple, la lecture peut provenir d'un processus s'exécutant sur un CPU hôte, elle peut être accessible par un transfert de données ultérieur via le tissu, ou lue depuis un appareil pair tel qu'un

GPU.

En termes de sémantiques d'achèvement, la visibilité indique généralement que le transfert remplit les exigences de FI_DELIVERY_COMPLETE du point de vue de la cible. La sémantique d'achèvement à la cible peut être, mais n'est pas nécessairement, liée à la sémantique d'achèvement spécifiée par l'initiateur du

transfert.

Souvent, les processus de la cible ne déclarent pas explicitement une sémantique d'achèvement souhaitée et s'appuient plutôt sur la sémantique par défaut. Le comportement par défaut est basé sur plusieurs facteurs, notamment

De manière générale, les sémantiques d'achèvement à la cible sont regroupées en fonction du fait que le transfert génère ou non un événement d'achèvement à la cible. Cela inclut l'écriture d'une entrée CQ ou la mise à jour d'un compteur d'achèvement. Dans les cas d'utilisation courants, les transferts qui utilisent une interface de message (FI_MSG ou FI_TAGGED) génèrent généralement des événements de cible, tandis que les transferts impliquant une interface RMA (FI_RMA ou FI_ATOMIC) souvent non. Il existe des exceptions à ces deux cas, selon les liaisons point de terminaison à CQ et aux compteurs et les drapeaux opérationnels. Par exemple, les écritures RMA qui transportent des données CQ distantes généreront un événement d'achèvement à la cible, et sont fréquemment utilisées pour transmettre la visibilité à l'application cible. Les directives générales pour les sémantiques côté cible sont décrites ci-dessous, suivies des exceptions qui modifient ce

comportement.

Par défaut, les achèvements générés à la cible indiquent que les données transférées sont immédiatement disponibles pour être lues depuis le tampon de cible. C'est-à-dire que la cible voit des sémantiques FI_DELIVERY_COMPLETE (ou meilleures), même si l'initiateur a demandé des sémantiques inférieures. Pour les applications utilisant uniquement des tampons de données alloués à partir de la mémoire hôte, c'est souvent

suffisant. >Pour les opérations qui ne génèrent pas d'événement de complétion à la cible, la visibilité des données à la cible peut devoir être déduite d'opérations ultérieures qui génèrent des complétions de cible. En l'absence de complétion de cible, lorsqu'une complétion d'une opération est écrite à l'initiateur, la sémantique de visibilité de l'opération à la cible s'aligne sur la sémantique de complétion de l'initiateur. Par exemple, si une opération RMA se termine à l'initiateur comme FI_INJECT_COMPLETE ou FI_TRANSMIT_COMPLETE, la visibilité des données à la cible n'est pas garantie.

Un ou plusieurs des mécanismes suivants peuvent être utilisés par le processus cible pour garantir que les résultats d'un transfert de données qui n'a pas généré de complétion à la cible sont maintenant visibles. Cette liste n'est pas exhaustive, mais définit des utilisations courantes. Dans les descriptions ci-dessous, le premier transfert ne résulte pas en un événement de complétion à la cible, mais est éventuellement suivi d'un transfert qui en résulte.

•
Si le point de terminaison garantit l'ordre des messages entre deux transferts, la complétion cible d'un second transfert indiquera que les données du premier transfert sont disponibles. Par exemple, si le point de terminaison prend en charge l'ordre envoi après écriture (FI_ORDER_SAW), alors une complétion de réception correspondant à l'envoi indiquera que les données d'écriture sont disponibles. Ceci est indépendant de la sémantique de complétion de l'initiateur pour l'écriture ou l'envoi. Lorsque l'ordre est garanti, le second transfert peut être mis en file d'attente auprès du fournisseur immédiatement après la mise en file d'attente du premier.
•
Si le point de terminaison ne garantit pas l'ordre des messages, l'initiateur doit prendre des mesures supplémentaires pour assurer la visibilité. Si l'initiateur demande les sémantiques FI_DELIVERY_COMPLETE pour la première opération, l'initiateur peut attendre que l'opération se termine localement. Une fois la complétion lue, la complétion de cible d'un second transfert indiquera que les données du premier transfert sont visibles.
•
Alternativement, si l'ordre des messages n'est pas garanti par le point de terminaison, l'initiateur peut utiliser les indicateurs FI_FENCE et FI_DELIVERY_COMPLETE sur le second transfert de données pour forcer les premiers transferts à respecter les sémantiques FI_DELIVERY_COMPLETE. Si le second transfert génère une complétion à la cible, cela indiquera que les données sont visibles. Sinon, une complétion de cible pour tout transfert après l'opération clôturée indiquera que les données sont visibles.

Les sémantiques ci-dessus s'appliquent aux transferts ciblant des tampons de mémoire d'hôte traditionnels. Cependant, le comportement peut différer lorsque la mémoire de périphérique et/ou la mémoire persistante sont impliquées (bits de capacité FI_HMEM et FI_PMEM). Lorsque la mémoire hétérogène est impliquée, le concept de domaines de mémoire entre en jeu. Les domaines de mémoire identifient la séparation physique de la mémoire, qui peut ou non être accessible via le même espace d'adressage virtuel. Voir la page de manuel fi_mr(3) pour plus de détails sur les domaines de mémoire.

L'ordre des complétions et la visibilité des données ne sont bien définis que pour les transferts qui ciblent le même domaine de mémoire. Les applications doivent être conscientes des différences d'ordre et de visibilité lorsque les transferts ciblent différents domaines de mémoire. De plus, les applications doivent également se préoccuper du domaine de mémoire dans lequel les complétions elles-mêmes sont écrites et s'il diffère du domaine de mémoire ciblé par un transfert. Dans certaines situations, le fournisseur ou l'application peut devoir appeler des API spécifiques au périphérique pour synchroniser ou vider les caches de mémoire des périphériques afin d'obtenir la visibilité des données souhaitée.

Lorsque la mémoire hétérogène est utilisée, la sémantique de complétion cible par défaut pour les transferts qui génèrent une complétion à la cible est toujours FI_DELIVERY_COMPLETE ; cependant, les applications doivent être conscientes qu'il peut y avoir un impact négatif sur les performances globales pour les fournisseurs afin de répondre à cette exigence.

Par exemple, un processus cible peut utiliser un GPU pour accélérer les calculs. Une région mémoire mappant vers la mémoire du GPU peut être exposée aux pairs soit comme cible RMA, soit affichée localement comme tampon de réception. Dans ce cas, l'application est concernée par deux domaines de mémoire : la mémoire système et la mémoire GPU. Les complétions sont écrites dans la mémoire système.

Pour continuer l'exemple, un processus pair envoie un message tagué. Ce message est mis en correspondance avec le tampon de réception situé dans la mémoire GPU. La carte réseau copie les données du réseau dans le tampon de réception et écrit une entrée dans la file d'attente de complétion. Notez que les deux domaines de mémoire ont été accédés dans le cadre de ce transfert. Les données du message étaient dirigées vers la mémoire GPU, mais la complétion est allée dans la mémoire hôte. Comme des domaines de mémoire distincts peuvent ne pas être synchronisés les uns avec les autres, il est possible que le CPU hôte voie et traite l'entrée de complétion avant que le transfert vers la mémoire GPU ne soit visible par le GPU hôte ou même par le logiciel s'exécutant sur le GPU. Du point de vue du *fournisseur*, la visibilité de la complétion n'implique pas la visibilité des données écrites dans le domaine de mémoire du GPU.

La sémantique de complétion cible par défaut au niveau de l'*application* pour les opérations de message est FI_DELIVERY_COMPLETE. Une implémentation attendue du fournisseur dans cette situation est que le logiciel fournisseur s'exécutant sur le CPU hôte intercepte l'entrée CQ, détecte que les données sont arrivées dans la mémoire hétérogène, et effectue la synchronisation de périphérique ou l'opération de vidage nécessaire avant de rapporter la complétion à l'application. Cela garantit que les données sont visibles par le logiciel CPU *et* GPU avant que l'application ne traite la complétion.

En plus du coût de l'interception des complétions par le logiciel fournisseur et de la vérification si un transfert a ciblé la mémoire hétérogène, la synchronisation du périphérique elle-même peut avoir un impact sur les performances. Par conséquent, les applications peuvent demander une sémantique de complétion inférieure lors de la publication des réceptions. Cela indique au fournisseur que l'application sera responsable de la gestion de toute opération de vidage spécifique au périphérique qui pourrait être nécessaire. Voir fi_msg(3) FLAGS.

Pour les transferts de données qui ne génèrent pas de complétion à la cible, tels que RMA ou les atomiques, il incombe à l'application de s'assurer que tous les tampons cibles respectent les exigences de visibilité nécessaires de l'application. Les méthodes mentionnées précédemment sous forme de liste à puces pour notifier la cible que les données sont visibles peuvent ne pas être suffisantes, car le logiciel fournisseur à la cible pourrait manquer du contexte nécessaire pour assurer la visibilité. Cela implique que l'application pourrait avoir besoin d'appeler directement des API de synchronisation/vidage de périphérique.

Par exemple, une application pair pourrait effectuer plusieurs écritures RMA qui ciblent des tampons de mémoire GPU. Si le fournisseur décharge les opérations RMA dans la carte réseau, le logiciel fournisseur à la cible ne sera pas conscient que les opérations RMA ont eu lieu. Si le pair envoie un message à l'application cible indiquant que les opérations RMA sont terminées, l'application doit s'assurer que les données RMA sont visibles par le CPU hôte ou le GPU avant d'exécuter du code qui accède aux données. La complétion cible de la réception du message envoyé n'est pas suffisante, même si l'ordre envoi-après-écriture est pris en charge.

La plupart des sémantiques de complétion de mémoire hétérogène cible correspondent à FI_TRANSMIT_COMPLETE ou FI_DELIVERY_COMPLETE. La mémoire persistante (capacité FI_PMEM), cependant, est souvent utilisée avec les sémantiques FI_COMMIT_COMPLETE. Les concepts de complétion hétérogène s'appliquent toujours.

Pour les transferts marqués par l'initiateur avec FI_COMMIT_COMPLETE, une complétion à la cible indique que les résultats sont visibles et durables. Pour les transferts ciblant la mémoire persistante, mais utilisant une sémantique de complétion différente à l'initiateur, la visibilité à la cible est similaire à celle décrite ci-dessus. La durabilité n'est associée qu'aux transferts marqués avec FI_COMMIT_COMPLETE.

Pour les transferts ciblant la mémoire persistante qui demandent FI_DELIVERY_COMPLETE, une complétion, à l'initiateur ou à la cible, indique que les données sont visibles. La visibilité à la cible peut être transmise en utilisant l'un des mécanismes décrits ci-dessus : générer une complétion de cible, envoyer un message de l'initiateur, etc. De même, si l'initiateur a demandé FI_TRANSMIT_COMPLETE, des étapes supplémentaires sont nécessaires pour assurer la visibilité à la cible. Par exemple, le transfert peut générer une complétion à la cible, ce qui indiquerait la visibilité, mais pas la durabilité. L'initiateur peut également suivre le transfert avec une autre opération qui force la visibilité, par exemple en utilisant FI_FENCE conjointement avec FI_DELIVERY_COMPLETE.

NOTES

Une file d'attente de complétion doit être liée à au moins un point de terminaison activé avant que toute opération telle que fi_cq_read, fi_cq_readfrom, fi_cq_sread, fi_cq_sreadfrom etc. puisse être appelée sur celle-ci.

Si une file d'attente de complétion a été débordée, elle sera placée dans un état de "dépassement". Les opérations de lecture continueront à renvoyer toutes les complétions valides et non corrompues, si disponibles. Une fois toutes les complétions valides récupérées, toute tentative de lecture de la file de complétion entraînera le renvoi d'un événement d'erreur FI_EOVERRUN. Les files d'attente de complétion débordées sont considérées comme fatales et ne peuvent pas être utilisées pour signaler des complétions supplémentaires une fois le dépassement produit.

VALEURS DE RETOUR

fi_cq_open / fi_cq_signal

: Renvoie 0 en cas de succès. En cas d'erreur, renvoie un errno de tissu négatif.

fi_cq_read / fi_cq_readfrom

: En cas de succès, renvoie le nombre de complétions récupérées de la file d'attente de complétion. En cas d'erreur, renvoie un errno de tissu négatif, avec ces deux erreurs explicitement identifiées : Si aucune complétion n'est disponible à lire dans la CQ, renvoie -FI_EAGAIN. Si la complétion la plus récente concerne un transfert échoué (une entrée d'erreur), renvoie -FI_EAVAIL.

fi_cq_sread / fi_cq_sreadfrom

: En cas de succès, renvoie le nombre de complétions récupérées de la file d'attente de complétion. En cas d'erreur, renvoie un errno de tissu négatif, avec ces deux erreurs explicitement identifiées : Si le délai d'attente expire ou si le thread appelant est signalé et qu'aucune donnée n'est disponible à lire dans la file d'attente de complétion, renvoie -FI_EAGAIN. Si la complétion la plus récente concerne un transfert échoué (une entrée d'erreur), renvoie -FI_EAVAIL.

fi_cq_readerr

: En cas de succès, renvoie la valeur positive 1 (nombre d'entrées d'erreur renvoyées). En cas d'erreur, renvoie un errno de tissu négatif, avec cette erreur explicitement identifiée : Si aucune complétion d'erreur n'est disponible à lire dans la CQ, renvoie -FI_EAGAIN.

fi_cq_strerror

: Renvoie une interprétation sous forme de chaîne de caractères du fournisseur

fi_cq_signal(3) — Libfabric Programmer’s Manual

NAME

fi_cq_signal, fi_cq_read, fi_cq_sread, fi_cq_readfrom, fi_cq_process ― completion queue (CQ) operation functions

SYNOPSIS

#include <rdma/fabric.h>

int fi_cq_signal(struct fi_cq_handle *handle);
int fi_cq_read(struct fi_cq_handle *handle,
              void *buf,
              size_t count);
int fi_cq_sread(struct fi_cq_handle *handle,
               void *buf,
               size_t count);
int fi_cq_readfrom(struct fi_cq_handle *handle,
                  void *buf,
                  size_t count,
                  struct sockaddr *from);
int fi_cq_process(struct fi_cq_handle *handle,
                 void *buf,
                 size_t count,
                 uint64_t flags);

ARGUMENTS

handle
A reference to the completion queue (CQ) object. This handle must have been previously created using fi_cq_open. A CQ handle is associated with a specific domain and endpoint. The CQ handle must be opened with the appropriate flags to support the requested operation.
buf
The buffer into which completion queue events will be read. The buffer must be large enough to hold the specified count of completion queue events. The size of each completion event is determined by the size of the fi_cq_entry structure, which can vary depending on the capabilities of the underlying fabric provider.
count
The maximum number of completion queue events to read into the buffer. This value should be a positive integer.
from
An optional pointer to a sockaddr structure. If specified, the sender address information of the received message will be written into this structure. The size of the address information depends on the network protocol and the fabric provider.
flags
Flags that control the behavior of the completion queue operation. Possible flags are defined in rdma/fabric.h. The following flags are relevant to fi_cq_process:
  • FI_NEXT: Indicates that the caller is requesting the next available completion event.
  • FI_CLAIM: Indicates that the caller is attempting to claim ownership of a completion event. This is useful in multi-threaded environments where multiple threads may be accessing the same completion queue.
  • FI_DEADLINE: Specifies a deadline for the operation. The operation will return with FI_ETIMEDOUT if the deadline is reached before a completion event is available.

DESCRIPTION

The fi_cq_signal, fi_cq_read, fi_cq_sread, fi_cq_readfrom, and fi_cq_process functions are used to retrieve completion queue (CQ) events from a libfabric communication endpoint.

A completion queue is an essential component of asynchronous communication in libfabric. It is used to signal the completion of operations such as sending and receiving messages, memory registration, and other fabric-related activities. When an operation completes, a completion event is posted to the CQ.

fi_cq_signal: This function signals the completion queue, indicating that a new completion event is available. This can be useful for synchronization purposes, allowing other threads or processes to be notified when a new event has been posted to the CQ.

fi_cq_read: This function attempts to read one or more completion events from the CQ into the provided buffer. If no events are available, the function will block until an event is posted or the operation times out (if a timeout is configured).

fi_cq_sread: This function is similar to fi_cq_read, but it is designed for use with synthetic completion queues. Synthetic CQs are used to inject custom completion events into the CQ, allowing applications to manage their own event flow.

fi_cq_readfrom: This function is similar to fi_cq_read, but it also retrieves the sender's address information if the completion event is associated with a received message. This is useful for applications that need to know the source of incoming data.

fi_cq_process: This function provides a more general mechanism for processing completion events. It allows the caller to specify flags that control the behavior of the operation, such as claiming ownership of an event or specifying a deadline. This function is often used in conjunction with event loops or polling mechanisms.

The size of each completion event is determined by the fi_cq_entry structure. The exact fields available within this structure depend on the fabric provider and the capabilities of the underlying hardware. Common fields include:

COMPLETION FIELDS

fi_cq_entry.op_code
The type of operation that completed.
fi_cq_entry.flags
Flags associated with the completion event.
fi_cq_entry.tag
A user-defined tag associated with the operation.
fi_cq_entry.len
The number of bytes transferred for the operation.
fi_cq_entry.emsg_id
The message identifier for the operation.
fi_cq_entry.addr
The source or destination address associated with the operation.

COMPLETION FLAGS

The following flags can be returned in the fi_cq_entry.flags field:

FI_SUCCESS
The operation completed successfully.
FI_ERROR
The operation resulted in an error.
FI_MSG
The completion event is associated with a message operation.
FI_SIGNALED
The completion event was signaled.
FI_RECV
The completion event is associated with a receive operation.
FI_SEND
The completion event is associated with a send operation.
FI_ABORT
The operation was aborted.
FI_TRANSMIT
The completion event is associated with a transmit operation.
FI_RECV_COMP
The completion event is associated with a receive completion.
FI_SEND_COMP
The completion event is associated with a send completion.

COMPLETION EVENT SEMANTICS

Fabric providers may offer different semantics for completion events. The following are common semantics:

FI_CQ_EVENT_ANY
Any type of completion event.
FI_CQ_EVENT_SEND
Send completion events.
FI_CQ_EVENT_RECV
Receive completion events.
FI_CQ_EVENT_RECVV
Receive vector completion events.
FI_CQ_EVENT_READ
Read completion events.
FI_CQ_EVENT_WRITE
Write completion events.

TARGET COMPLETION SEMANTICS

The following semantics apply to the target completion queue:

FI_CQ_TARGET_CQ_EVENT_ANY
Any type of completion event on the target CQ.
FI_CQ_TARGET_CQ_EVENT_SEND
Send completion events on the target CQ.
FI_CQ_TARGET_CQ_EVENT_RECV
Receive completion events on the target CQ.

NOTES

The exact behavior and available fields of completion queue events can vary depending on the underlying fabric provider and the configuration of the libfabric environment. It is recommended to consult the documentation for the specific fabric provider being used for detailed information.

When reading completion events, it is important to handle potential errors that may be returned. The fi_cq_entry.flags field can indicate errors, and the functions themselves can return specific error codes.

In multi-threaded applications, care must be taken to synchronize access to completion queues to avoid race conditions. The fi_cq_process function with the FI_CLAIM flag can be helpful in managing concurrent access.

RETURN VALUES

These functions return:

0
On success. The number of completion events read is returned by fi_cq_read, fi_cq_sread, and fi_cq_readfrom.
A negative value
On error. Specific error codes are defined in rdma/fi_errno.h. Common error codes include:
FI_EAGAIN
No completion events are currently available.
FI_EINVAL
An invalid argument was provided.
FI_ENOMSG
No message available for the requested operation.
FI_ETIMEDOUT
The operation timed out.
FI_ECATEGORY
An error occurred related to the operation category.

The specific error returned with a completion.

Fabric errno values are defined in rdma/fi_errno.h.
