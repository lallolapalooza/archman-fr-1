DESCRIPTIO

N

Les compteurs enregistrent le nombre d'opérations demandées qui se sont terminées. Les compteurs peuvent fournir un mécanisme de complétion léger en permettant la suppression des entrées de complétion de CQ. Ils sont utiles pour les applications qui ont seulement besoin de connaître le nombre de requêtes terminées, et non les détails de chaque requête. Par exemple, les compteurs peuvent être utiles pour implémenter un contrôle de flux basé sur les crédits ou pour suivre le nombre de processus distants ayant répondu à une

requête.

Les compteurs ne comptent généralement que les complétions réussies. Cependant, si une opération se termine en erreur, elle peut incrémenter une valeur d'erreur associée. C'est-à-dire qu'un compteur stocke en réalité deux valeurs distinctes, les complétions en erreur mettant à jour une valeur spécifique aux

erreurs.

Les compteurs sont mis à jour selon la sémantique d'événement de complétion définie dans fi_cq(3). Le moment de la mise à jour est basé sur le type de transfert et tout indicateur d'opération

spécifié.

Un compteur capture différents types d'événements. Le type spécifique à compter est l'un des suivants
:
- FI_CNTR_EVENTS_C
OMP
Le compteur s'incrémente pour chaque complétion réussie survenant sur un point de terminaison lié associé. Le type de complétions – envois et/ou réceptions – qui sont comptées peut être restreint à l'aide d'indicateurs de contrôle lors de la liaison du compteur et du point de terminaison. Les compteurs s'incrémentent sur toutes les complétions réussies, indépendamment du fait que l'opération génère une entrée dans une file
d'événements.
- FI_CNTR_EVENTS_BY
TES
Le compteur est incrémenté du nombre d'octets utilisateur, à l'exclusion de toute donnée CQ, transférés dans un message de transport lors de l'atteinte de la sémantique de complétion spécifiée. Pour les compteurs côté initiateur, le compte reflète la taille du transfert demandé et est mis à jour après que le message atteint le niveau de complétion souhaité (FI_INJECT_COMPLETE, FI_TRANSMIT_COMPLETE, etc.). Pour les opérations d'écriture et d'envoi, le compte reflète le nombre d'octets transférés au pair. Pour les opérations de lecture, le compte reflète le nombre d'octets renvoyés dans une réponse de lecture. Les opérations qui peuvent à la fois écrire et lire des données, comme les opérations atomiques, se comportent comme des opérations de lecture côté initiateur, mais comme des écritures côté cible. Pour les compteurs côté cible, le compte reflète la taille des données utilisateur reçues et est incrémenté selon la sémantique de complétion côté cible. Dans la plupart des cas, cela indique FI_DELIVERY_COMPLETE, mais peut différer lors de l'accès à la mémoire de périphérique (HMEM). En cas d'erreur, la taille du transfert n'est pas appliquée au champ d'erreur, ce champ est incrémenté de 1. Le type de transfert FI_COLLECTIVE n'est pas pris en
charge.
wait_o
bj
Les compteurs peuvent être associés à un objet d'attente spécifique. Les objets d'attente permettent aux applications de se bloquer jusqu'à ce que l'objet d'attente soit signalé, indiquant qu'un compteur a atteint un seuil spécifique. Les utilisateurs peuvent utiliser fi_control pour récupérer l'objet d'attente sous-jacent associé à un compteur, afin de l'utiliser dans d'autres appels système. Les valeurs suivantes peuvent être utilisées pour spécifier le type d'objet d'attente associé à un compteur : FI_WAIT_NONE, FI_WAIT_UNSPEC, FI_WAIT_SET, FI_WAIT_FD, FI_WAIT_MUTEX_COND (obsolète), et FI_WAIT_YIELD. La valeur par défaut est
FI_WAIT_NONE.
- FI_WAIT_NO
NE
Utilisé pour indiquer que l'utilisateur ne se bloquera pas (n'attendra pas) les événements sur le
compteur.
- FI_WAIT_UNSP
EC
Spécifie que l'utilisateur n'attendra sur le compteur qu'à l'aide d'appels d'interface de fabric, tels que fi_cntr_wait. Dans ce cas, le fournisseur sous-jacent peut sélectionner l'objet d'attente le plus approprié ou le plus performant disponible, y compris des mécanismes d'attente personnalisés. Les applications qui sélectionnent FI_WAIT_UNSPEC ne sont pas garanties de récupérer l'objet d'attente
sous-jacent.
- FI_WAIT_SET (ob
solète)
Indique que le compteur d'événements doit utiliser un objet de jeu d'attente pour attendre les événements. Si spécifié, le champ wait_set doit référencer un objet de jeu d'attente
existant.
- FI_WAIT_
FD
Indique que le compteur doit utiliser un descripteur de fichier comme mécanisme d'attente. Un objet d'attente par descripteur de fichier doit être utilisable dans les routines select, poll et epoll. Cependant, un fournisseur peut signaler un objet d'attente FD en le marquant comme lisible, inscriptible, ou avec une
erreur.
- FI_WAIT_MUTEX_COND
(obsolète)
Spécifie que le compteur doit utiliser un mutex et une variable de condition pthread comme objet
d'attente.
- FI_WAIT_YIE
LD
Indique que le compteur attendra sans objet d'attente mais cédera plutôt la main à chaque attente. Permet l'utilisation de fi_cntr_wait via une rotation
active.
wait_set
(obsolète)
Si wait_obj est FI_WAIT_SET, ce champ référence un objet d'attente au quel le compteur d'événements doit s'attacher. Lorsqu'un événement est ajouté au compteur d'événements, le jeu d'attente correspondant sera signalé si toutes les conditions nécessaires sont réunies. L'utilisation d'un wait_set permet une méthode optimisée d'attente des événements à travers plusieurs compteurs d'événements. Ce champ est ignoré si wait_obj n'est pas
FI_WAIT_SET.

fi_close

L'appel fi_close libère toutes les ressources associées à un compteur. Lors de la fermeture du compteur, aucun point d

e terminaison ouvert, contexte d'émission, contexte de réception ou région mémoire ne doit être associé au compteur

Cet appel peut être utilisé pour attendre que le compteur atteigne le seuil spécifié, ou jusqu'à ce qu'une erreur ou un délai d'attente se produise. Lors d'un retour réussi de cet appel, le compteur sera supérieur ou égal à la valeur de seuil

d'entrée.

Si une opération associée au compteur rencontre une erreur, elle incrémentera la valeur d'erreur associée au compteur. Tout changement dans la valeur d'erreur d'un compteur débloquera tout thread à l'intérieur de

fi_cntr_wait.

Si l'appel se termine en raison d'un délai d'attente, -FI_ETIMEDOUT sera renvoyé. La valeur d'erreur associée au compteur reste

inchangée.

NOTE

S

Afin de prendre en charge une variété d'implémentations de compteurs, les mises à jour apportées aux valeurs des compteurs (par exemple fi_cntr_set ou fi_cntr_add) peuvent ne pas être immédiatement visibles pour les opérations de lecture du compteur (c'est-à-dire fi_cntr_read ou fi_cntr_readerr). Un petit délai, mais indéfini, peut survenir entre le changement du compteur et la mise à jour de la valeur rapportée. Cependant, une valeur mise à jour finale sera éventuellement reflétée dans la valeur du compteur

lue.

De plus, les applications doivent s'assurer que la valeur d'un compteur est stable et non susceptible de changer avant d'appeler fi_cntr_set ou fi_cntr_seterr. Sinon, la valeu

r résultante du compteur après fi_cntr_set / fi_cntr_seterr est indéfinie, car les mises à jour du compteur peuvent être perdues. Une valeur de compteur est considérée comme st
able si toutes les mises à jour précédentes utilisant fi_cntr_set / fi_cntr_seterr et les résultats des opérations associées sont reflétés dans la valeur observée du compteur.
