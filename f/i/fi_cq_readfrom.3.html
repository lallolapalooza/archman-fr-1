DESCRIPTIO

N

Les files d'achèvement sont utilisées pour signaler des événements associés aux transferts de données. Elles sont associées aux envois et réceptions de messages, au RMA, aux opérations atomiques, aux messages étiquetés et aux événements déclenchés. Les événements signalés sont généralement associés à un point de terminaison de fabric, mais peuvent également faire référence à des régions mémoire utilisées comme cible d'une opération RMA ou

atomique.

fi_cq_ope

n

fournisseur.

Les CQ peuvent être associées à un objet d'attente spécifique. Les objets d'attente permettent aux applications de se bloquer jusqu'à ce que l'objet d'attente soit signalé, indiquant qu'un achèvement est disponible pour être lu. Les utilisateurs peuvent utiliser fi_control pour récupérer l'objet d'attente sous-jacent associé à une CQ, afin de l'utiliser dans d'autres appels système. Les valeurs suivantes peuvent être utilisées pour spécifiertype d'objet d'attente associé à une CQ : FI_WAIT_NONE, FI_WAIT_UNSPEC, FI_WAIT_SET, FI_WAIT_FD, FI_WAIT_MUTEX_COND (obsolète), et FI_WAIT_YIELD. La valeur par défaut est
FI_WAIT_NONE.

fi_cq_sreadfrom.
- FI_WAIT_UNSP
EC
Spécifie que l'utilisateur n'attendra sur la CQ qu'à l'aide d'appels d'interface fabric, tels que fi_cq_sread ou fi_cq_sreadfrom. Dans ce cas, le fournisseur sous-jacent peut sélectionner l'objet d'attente le plus approprié ou le plus performant disponible, y compris des mécanismes d'attente personnalisés. Les applications qui sélectionnent FI_WAIT_UNSPEC ne sont pas garanties de récupérer l'objet d'attente
sous-jacent.

Par défaut, lorsqu'une complétion est insérée dans une CQ qui prend en charge les lectures bloquantes (fi_cq_sread/fi_cq_sreadfrom), l'objet d'att
ente correspondant est signalé. Les utilisateurs peuvent spécifier une condition qui doit d'abord être remplie avant que l'attente soit satis

Une condition d'attente doit être traitée comme une optimisation. Les fournisseurs ne sont pas tenus de satisfaire les exigences de la condition avant de signaler l'objet d'attente. Le seuil indique le nombre d'entrées qui doivent être mises en file dans la CQ avant que l'attente soit

satisfaite.

FI_WAIT_NONE.

fi_clos

e

L'appel fi_close libère toutes les ressources associées à une file d'attente de complétion. Toute complétion restant sur la CQ lorsqu'elle est fermée est

perdue.

Lors de la fermeture de la CQ, il ne doit y avoir aucun point de terminaison ouvert, aucun

contexte de transmission ou aucun contexte de réception associé à la CQ. Si des ressources sont
toujours associées à la CQ lors de la tentative de fermeture, l'appel retournera -FI_EBUSY.

fi_contro

l

L'appel fi_control est utilisé pour accéder aux détails spécifiques au fournisseur ou à l'implémentation de la file d'attente de complétion. L'accès à la CQ doit être sérialisé à travers tous les appels lorsque fi_control est invoqué, car cela peut rediriger l'implémentation des opérations de CQ. Les commandes de contrôle suivantes sont utilisables avec une

CQ.
FI_GETWAIT (void
**)
Cette commande permet à l'utilisateur de récupérer l'objet d'attente de bas niveau associé à la CQ.
Le format de l'objet d'attente est spécifié lors de la création de la CQ, à travers les attributs de
la CQ. Le paramètre arg de fi_control doit être une adresse où un pointeur vers l'objet d'attente ret
ourné sera écrit. Voir fi_eq.3 pour plus de détails sur l'utilisation de fi_control avec FI_GETWAIT.

fi_cq_rea

d

L'opération fi_cq_read effectue une lecture non bloquante des données de complétion depuis la CQ. Le format de l'événement de complétion est déterminé à l'aide de l'option fi_cq_format qui a été spécifiée lorsque la CQ a été ouverte. Plusieurs complétions peuvent être récupérées depuis une CQ dans un seul appel. Le nombre maximum d'entrées à retourner est limité au paramètre count spécifié, le nombre d'entrées lues avec succès depuis la CQ étant retourné par l'appel. (Voir la section des valeurs de retour ci-dessous.) Une valeur count de 0 peut être utilisée pour faire progresser les points de terminaison associés lorsque la progression manuelle est

activée.

Les CQ sont optimisées pour signaler les opérations qui se sont terminées avec succès. Les opérations qui échouent sont signalées « hors bande ». De telles opérations sont récupérées à l'aide de la f

onction fi_cq_readerr. Lorsqu'une opération qui s'est terminée avec une erreur inattendue est rencontrée, elle est placée dans une file d'erreurs temporaire. Tenter de lire depuis une CQ alors qu'un é
lément est dans la file d'erreurs entraîne l'échec de fi_cq_read avec un code de retour de -FI_EAVAIL. Les applications peuvent utiliser ce code de retour pour déterminer quand appeler fi_cq_readerr.

fi_cq_readfro

m

L'appel fi_cq_readfrom se comporte de manière identique à fi_cq_read, à l'exception qu'il permet à la CQ de retourner des informations d'adresse source à l'utilisateur pour toute donnée reçue. Les données d'adresse source ne sont disponibles que pour les points de terminaison configurés avec la capacité FI_SOURCE. Si fi_cq_readfrom est appelé sur un point de terminaison pour lequel les données d'adressage source ne sont pas disponibles, l'adresse source sera définie à FI_ADDR_NOTAVAIL. Le nombre d'entrées src_addr en entrée doit être le même que le paramètre

count.

Les données d'adressage source retournées sont converties depuis l'adresse native utilisée par le fabric sous-jacent en un fi_addr_t, qui peut être utilisé dans les opérations de transmission. Dans la plupart des circonstances, le retour d'un fi_addr_t nécessite que l'adresse source ait déjà été insérée dans le vecteur d'adresses associé au point de terminaison récepteur. Cela est vrai pour les vecteurs d'adresses de type FI_AV_TABLE. Dans certains fournisseurs lorsque FI_AV_MAP est utilisé, les adresses sources peuvent être converties algorithmiquement en un fi_addr_t utilisable, même si l'adresse source n'a pas été insérée dans le vecteur d'adresses. Cela est permis par l'API, car cela permet au fournisseur d'éviter la recherche d'adresse dans le traitement des messages reçus. Dans aucun cas les fournisseurs n'insèrent d'adresses dans un AV indépendamment d'un appel de l'application à fi_av_insert ou un appel

similaire.

Pour les points de terminaison alloués avec la capacité FI_SOURCE_ERR, si l'adresse source ne peut pas être convertie en une valeur fi_addr_t valide, fi_cq_readfrom retournera -FI_EAVAIL, même si les données ont été reçues avec succès. La complétion sera alors signalée à travers fi_cq_readerr avec le code d'erreur -FI_EADDRNOTAVAIL. Voir fi_cq_readerr pour les

détails.

Si FI_SOURCE est spécifié sans FI_SOURCE_ERR, les adresses sources qui ne peuvent pas être mappées vers un fi_addr_t utilisable seront signalées comme FI_ADDR_NOTAVAI

L
.

fi_cq_sread /

fi_cq_sreadfrom

Les appels fi_cq_sread et fi_cq_sreadfrom sont les opérations bloquantes équivalentes à fi_cq_read et fi_cq_readfrom. Leur comportement est similaire aux appels non bloquants, à l'exception que les appels ne retourneront pas jusqu'à ce qu'une complétion ait été lue depuis la CQ ou qu'une erreur ou un délai d'attente (timeout) se

produise.

Les threads bloqués dans cette fonction retourneront à l'appelant s'ils sont signalés par une source externe. Cela est vrai même si le délai d'attente ne s'est pas écoulé ou s'il a été spécifié comme

infini.

Il est invalide pour les applications d'appeler ces

fonctions si la CQ a été configurée avec un o
bjet d'attente de type FI_WAIT_NONE ou FI_WAIT_SET.

fi_cq_reader

r

La fonction de lecture d'erreur, fi_cq_readerr, récupère des informations concernant toute opération asynchrone qui s'est terminée avec une erreur inattendue. fi_cq_readerr est un appel non bloquant, retournant immédiatement que la complétion d'erreur ait été trouvée ou

non.

Les informations d'erreur sont rapportées à l'utilisateur à travers la structure fi_cq_err_entry. Le format de cette structure est défini

ci-dessous. 
struct fi_cq_err_entry {
    void     *op_context; /* contexte de l'opération */
    uint64_t flags;       /* indicateurs de complétion */
    size_t   len;         /* taille des données reçues */
    void     *buf;        /* tampon de données de réception */
    uint64_t data;        /* données de complétion */
    uint64_t tag;         /* étiquette de message */
    size_t   olen;        /* longueur de débordement */
    int      err;         /* code d'erreur positif */
    int      prov_errno;  /* code d'erreur du fournisseur */
    void    *err_data;    /* données d'erreur */
    size_t   err_data_size; /* taille de err_data */
    fi_addr_t src_addr; /* adresse source de l'erreur
*/
}
;

La raison générale de l'erreur est fournie à travers le champ err. Des informations d'erreur spécifiques au fournisseur peuvent également être disponibles à travers les champs prov_errno et err_data. Les utilisateurs peuvent appeler fi_cq_strerror pour convertir des informations d'erreur spécifiques au fournisseur en une chaîne imprimable à des fins de débogage. Voir les détails des champs ci-dessous pour plus d'informations sur l'utilisation de err_data et

err_data_size.

Notez que des complétions d'erreur sont générées pour toutes les opérations, y compris celles pour lesquelles une complétion n'a pas été demandée (par ex. un point de terminaison estnfigured avec FI_SELECTIVE_COMPLETION, mais la requête n'avait pas le drapeau FI_COMPLETION défini). Dans de tels cas, les fournisseurs retourneront autant d'informations que possible sur l'échec, fournies par le logiciel et le matériel sous-jacents ; les autres champs seront définis à NULL ou à 0. Cela inclut la valeur op_context, qui peut ne pas avoir été fournie ou a été ignorée en entrée dans le cadre du transfert.

Les codes d'erreur de complétion notables sont indiqués ci-dessous.

FI_EADDRNOTAVAIL
Ce code d'erreur est utilisé par les CQ configurés avec FI_SOURCE_ERR pour signaler les complétions pour lesquelles une adresse source fi_addr_t utilisable n'a pas pu être trouvée. Un code d'erreur FI_EADDRNOTAVAIL indique que le transfert de données a été reçu et traité avec succès, les champs fi_cq_err_entry contenant des informations sur la complétion. Le champ err_data sera défini sur les données de l'adresse source. L'adresse source sera dans le même format que spécifié par le champ addr_format de fi_info pour le domaine ouvert. Elle peut être passée directement à un appel fi_av_insert pour ajouter l'adresse source au vecteur d'adresses.

Pour les versions d'API 1.20 et ultérieures, si l'EP est configuré avec FI_AV_AUTH_KEY, src_addr sera défini sur le handle de clé d'autorisation fi_addr_t ou un identifiant de clé d'autorisation défini par l'utilisateur correspondant au transfert de données entrant. Sinon, la valeur sera définie sur FI_ADDR_NOTAVAIL.

fi_cq_signal

L'appel fi_cq_signal débloquera tout thread en attente dans fi_cq_sread ou fi_cq_sreadfrom. Cela peut être utilisé pour réveiller un thread bloqué en attente de lecture d'une opération de complétion. L'opération fi_cq_signal n'est disponible que si le CQ a été configuré avec un objet d'attente.

CHAMP_DE_COMPLETION

Les structures de données d'entrée CQ partagent plusieurs des mêmes champs. Les significations de ces champs sont les mêmes pour tous les formats de structure d'entrée CQ.

op_context
Le contexte de l'opération est la valeur de contexte spécifiée par l'application qui a été fournie avec une opération asynchrone. Le champ op_context est valide pour toutes les complétions associées à une opération asynchrone.

Pour les événements de complétion non associés à une opération postée, ce champ sera défini à NULL. Cela inclut les complétions générées à la cible en réponse aux opérations d'écriture RMA qui transportent des données CQ (drapeaux FI_REMOTE_WRITE | FI_REMOTE_CQ_DATA définis), lorsque le bit de mode FI_RX_CQ_DATA n'est pas requis.

flags
Ceci spécifie les drapeaux associés à l'opération complétée. La section Drapeaux de Complétion ci-dessous liste les valeurs de drapeaux valides. Les drapeaux sont définis pour toutes les complétions pertinentes.
len
Ce champ len s'applique aux opérations de réception complétées (par exemple, fi_recv, fi_trecv, etc.) et à l'écriture complétée avec des données de CQ distantes côté répondeur (par exemple, fi_write, avec le drapeau FI_REMOTE_CQ_DATA). Il indique la taille des données de *message* transférées – c'est-à-dire le nombre d'octets de données qui ont été placés dans le tampon de réception/cible associé par un appel fi_send/fi_tsend/fi_write et al. correspondant. Si un point de terminaison a été configuré avec le mode FI_MSG_PREFIX, le len reflète également la taille du tampon préfixe.
buf
Le champ buf n'est valide que pour les opérations de réception complétées, et ne s'applique que lorsque le tampon de réception a été posté avec le drapeau FI_MULTI_RECV. Dans ce cas, buf pointe vers l'emplacement de départ où les données de réception ont été placées.
data
Le champ data n'est valide que si le drapeau de complétion FI_REMOTE_CQ_DATA est défini, et ne s'applique qu'aux complétions de réception. Si FI_REMOTE_CQ_DATA est défini, ce champ contiendra les données de complétion fournies par le pair dans le cadre de sa requête de transmission. Les données de complétion seront fournies dans l'ordre des octets de l'hôte.
tag
Une balise s'applique uniquement aux messages reçus qui se produisent en utilisant les interfaces balisées. Ce champ contient la balise qui a été incluse avec le message reçu. La balise sera dans l'ordre des octets de l'hôte.
olen
Le champ olen s'applique aux messages reçus. Il est utilisé pour indiquer qu'un message reçu a dépassé l'espace tampon disponible et a été tronqué. L'olen spécifie la quantité de données qui n'a pas pu tenir dans le tampon de réception disponible et qui a été supprimée.
err
Ce code d'erreur err est un errno de fabric positif associé à une complétion. La valeur err indique la raison générale d'une erreur, si une erreur s'est produite. Voir fi_errno.3 pour une liste des codes d'erreur possibles.
prov_errno
En cas d'erreur, prov_errno peut contenir un code d'erreur spécifique au fournisseur. L'utilisation de ce champ et sa signification sont spécifiques au fournisseur. Il est destiné à être utilisé comme aide au débogage. Voir fi_cq_strerror pour plus de détails sur la conversion de cette valeur d'erreur en une chaîne lisible par l'homme.
err_data
Le champ err_data est utilisé pour retourner des informations spécifiques au fournisseur, si disponibles, sur l'erreur. En entrée, err_data doit faire référence à un tampon de données de taille err_data_size. En sortie, le fournisseur remplira ce tampon avec toutes les données spécifiques au fournisseur qui pourraient aider à identifier la cause de l'erreur. Le contenu du champ err_data et sa signification sont spécifiques au fournisseur. Il est destiné à être utilisé comme aide au débogage. Voir fi_cq_strerror pour plus de détails sur la conversion de ces données d'erreur en une chaîne lisible par l'homme. Voir la note de compatibilité ci-dessous sur la façon dont ce champ est utilisé pour les versions antérieures de libfabric.
err_data_size
En entrée, err_data_size indique la taille du tampon err_data en octets. En sortie, err_data_size sera défini sur le nombre d'octets copiés dans le tampon err_data. Les informations err_data sont généralement utilisées avec fi_cq_strerror pour fournir des détails sur le type d'erreur qui s'est produit.

Par souci de compatibilité, le comportement des champs err_data et err_data_size peut être modifié par rapport à ce qui est indiqué ci-dessus. Si err_data_size est 0 en entrée, ou si le fabric a été ouvert avec une version < 1.5, alors tout tampon référencé par err_data sera ignoré en entrée. Dans ce cas, en sortie, err_data sera défini sur un tampon de données appartenant au fournisseur. Le contenu du tampon restera valide jusqu'à ce qu'un appel de lecture ultérieur sur le CQ. Les applications doivent sérialiser l'accès au CQ lors du traitement des erreurs pour garantir que le tampon référencé par err_data ne change pas.

src_addr
Utilisé pour retourner des informations liées aux adresses sources pour les événements d'erreur. L'utilisation de ce champ est spécifique à l'événement d'erreur.

D'ACHÈVEMENT

Libfabric définit plusieurs « niveaux » d'achèvement, identifiés à l'aide de drapeaux opérationnels. Chaque drapeau indique le moment le plus tôt auquel un événement d'achèvement peut être généré par un fournisseur, et les hypothèses qu'une application peut faire lors du traitement d'un achèvement. Les drapeaux opérationnels sont définis ci-dessous, avec un exemple de la manière dont un fournisseur pourrait implémenter la sémantique. Notez que seule la conformité à la sémantique est requise du fournisseur, et non l'implémentation. Les fournisseurs peuvent implémenter des sémantiques d'achèvement plus strictes que nécessaire pour une opération donnée, mais seul le comportement défini par le niveau d'achèvement est

garanti.

Pour aider à comprendre les différences conceptuelles entre les niveaux d'achèvement, considérez l'envoi d'une lettre. Placer la lettre dans la boîte aux lettres locale pour la collecte est similaire à « inject complete ». Avoir la lettre collectée et déposée dans la boîte aux lettres de destination est équivalent à « transmit complete ». La sémantique « delivery complete » est une garantie plus forte, avec une personne à la destination signant pour la lettre. Cependant, la personne qui a signé pour la lettre n'est pas nécessairement le destinataire prévu. L'option « match complete » est similaire à delivery complete, mais exige que le destinataire prévu signe pour la

lettre.

Le niveau « commit complete » a des sémantiques différentes des niveaux mentionnés précédemment. Commit complete serait plus proche de la lettre arrivant à la destination et étant placée dans un coffre-fort

ignifugé.

CIBLE

La sémantique d'achèvement à la cible est utilisée pour déterminer quand les données à la cible sont visibles par l'application paire. La visibilité indique qu'une lecture mémoire au même adresse qui était la cible d'un transfert de données retournera les résultats du transfert. La cible d'un transfert peut être identifiée par l'initiateur, comme c'est le cas pour les opérations RMA et atomiques, ou déterminée par la cible, par exemple en fournissant un tampon de réception appariant. La visibilité globale indique que les résultats sont disponibles quelle que soit l'origine de la lecture mémoire. Par exemple, la lecture peut provenir d'un processus s'exécutant sur un CPU hôte, elle peut être accessible par un transfert de données ultérieur via la fabrique, ou lue depuis un appareil pair tel qu'un

GPU.

En termes de sémantique d'achèvement, la visibilité indique généralement que le transfert remplit les exigences FI_DELIVERY_COMPLETE du point de vue de la cible. La sémantique d'achèvement de la cible peut être, mais n'est pas nécessairement, liée à la sémantique d'achèvement spécifiée par l'initiateur du

transfert.

Dans les cas d'utilisation courants, les transferts qui utilisent une interface de message (FI_MSG ou FI_TAGGED) génèrent généralement des événements de cible, tandis que les transferts impliquant une interface RMA (FI_RMA ou FI_ATOMIC) souvent pas. Par exemple, si une opération RMA se termine à l'initiateur avec soit FI_INJECT_COMPLETE soit FI_TRANSMIT_COMPLETE, la visibilité des données à la cible n'est pas

Cette liste n'est pas exhaustive, mais définit des utilisations courantes. Dans les descriptions ci-dessous, le premier transfert ne résulte pas en un événement de complétion à la cible, mais est éventuellement suivi d'un transfert qui en génère

•
Si le point de terminaison garantit l'ordre des messages entre deux transferts, la complétion à la cible d'un second transfert indiquera que les données du premier transfert sont disponibles. Par exemple, si le point de terminaison supporte l'ordre d'envoi après écriture (FI_ORDER_SAW), alors une complétion de réception correspondant à l'envoi indiquera que les données écrites sont disponibles. Cela est indépendant de la sémantique de complétion de l'initiateur pour l'écriture ou l'envoi. Lorsque l'ordre est garanti, le second transfert peut être mis en file d'attente auprès du fournisseur immédiatement après la mise en file du
premier.
•
Si le point de terminaison ne garantit pas l'ordre des messages, l'initiateur doit prendre des mesures supplémentaires pour assurer la visibilité. Si l'initiateur demande la sémantique FI_DELIVERY_COMPLETE pour la première opération, il peut attendre que l'opération se termine localement. Une fois la complétion lue, la complétion à la cible d'un second transfert indiquera que les données du premier transfert sont

•

Les sémantiques ci-dessus s'appliquent aux transferts ciblant des tampons de mémoire hôte traditionnels. Cependant, le comportement peut différer lorsque la mémoire de dispositif et/ou la mémoire persistante sont impliquées (bits de capacité FI_HMEM et FI_PMEM). Lorsque la mémoire hétérogène est impliquée, le concept de domaines de mémoire entre en jeu. Les domaines de mémoire identifient la séparation physique de la mémoire, qui peut ou non être accessible à travers le même espace d'adressage virtuel. Voir la page de manuel fi_mr(3) pour plus de détails sur les domaines de

mémoire.

L'ordre des complétions et la visibilité des données ne sont bien définis que pour les transferts ciblant le même domaine de mémoire. Les applications doivent être conscientes des différences d'ordre et de visibilité lorsque les transferts ciblent différents domaines de mémoire. De plus, les applications doivent également se préoccuper du domaine de mémoire dans lequel les complétions elles-mêmes sont écrites et s'il diffère du domaine de mémoire ciblé par un transfert. Dans certaines situations, soit le fournisseur soit l'application peuvent avoir besoin d'appeler des API spécifiques au dispositif pour synchroniser ou vider les caches de mémoire du dispositif afin d'atteindre la visibilité des données

souhaitée.

Lorsque la mémoire hétérogène est utilisée, la sémantique de complétion à la cible par défaut pour les transferts qui génèrent une complétion à la cible est toujours FI_DELIVERY_COMPLETE. Cependant, les applications doivent être conscientes qu'il peut y avoir un impact négatif sur les performances globales pour les fournisseurs afin de satisfaire cette

exigence.

Par exemple, un processus cible peut utiliser un GPU pour accélérer des calculs. Une région de mémoire mappant de la mémoire sur le GPU peut être exposée aux pairs soit comme une cible RMA, soit publiée localement comme un tampon de réception. Dans ce cas, l'application est concernée par deux domaines de mémoire – la mémoire système et la mémoire GPU. Les complétions sont écrites dans la mémoire

système.

En continuant l'exemple, un processus pair envoie un message étiqueté. Ce message est apparié avec le tampon de réception situé dans la mémoire GPU. La NIC copie les données du réseau vers le tampon de réception et écrit une entrée dans la file de complétion. Notez que les deux domaines de mémoire ont été accessibles dans le cadre de ce transfert. Les données du message ont été dirigées vers la mémoire GPU, mais la complétion est allée vers la mémoire hôte. Comme des domaines de mémoire séparés peuvent ne pas être synchronisés les uns avec les autres, il est possible que le CPU hôte voie et traite l'entrée de complétion avant que le transfert vers la mémoire GPU ne soit visible soit pour le GPU hôte, soit même pour le logiciel s'exécutant sur le GPU. Du point de vue du fournisseur, la visibilité de la complétion n'implique pas la visibilité des données écrites dans le domaine de mémoire du

GPU.

La sémantique de complétion par défaut à la cible application pour les opérations de message est FI_DELIVERY_COMPLETE. Une implémentation anticipée du fournisseur dans cette situation est que le logiciel du fournisseur s'exécutant sur le CPU hôte intercepte l'entrée de CQ, détecte que les données ont atterri dans la mémoire hétérogène, et effectue l'opération de synchronisation ou de vidage du dispositif nécessaire avant de signaler la complétion à l'application. Cela garantit que les données sont visibles pour le CPU et le logiciel GPU avant que l'application ne traite la

complétion.

En plus du coût du logiciel du fournisseur interceptant les complétions et vérifiant si un transfert ciblait de la mémoire hétérogène, la synchronisation du dispositif elle-même peut impacter les performances. Par conséquent, les applications peuvent demander une sémantique de complétion plus basse lors de la publication de réceptions. Cela indique au fournisseur que l'application sera responsable du traitement de toute opération de vidage spécifique au dispositif qui pourrait être nécessaire. Voir fi_msg(3)

FLAGS.

Pour les transferts de données qui ne génèrent pas une complétion à la cible, tels que les RMA ou les atomiques, il est de la responsabilité de l'application de s'assurer que tous les tampons cibles répondent aux exigences de visibilité nécessaires de l'application. Les méthodes à puces mentionnées précédemment pour notifier la cible que les données sont visibles peuvent ne pas être suffisantes, car le logiciel du fournisseur à la cible pourrait manquer du contexte nécessaire pour assurer la visibilité. Cela implique que l'application pourrait avoir besoin d'appeler directement les API de synchronisation/vidage du

dispositif.

Par exemple, une application pair pourrait effectuer plusieurs écritures RMA ciblant des tampons de mémoire GPU. Si le fournisseur décharge les opérations RMA dans la NIC, le logiciel du fournisseur à la cible ne sera pas au courant que les opérations RMA ont eu lieu. Si le pair envoie un message à l'application cible indiquant que les opérations RMA sont terminées, l'application doit s'assurer que les données RMA sont visibles pour le CPU ou le GPU hôte avant d'exécuter du code qui accède aux données. La complétion à la cible d'avoir reçu le message envoyé n'est pas suffisante, même si l'ordre d'envoi après écriture est

supporté.

La plupart des sémantiques de complétion pour la mémoire hétérogène à la cible correspondent à FI_TRANSMIT_COMPLETE ou FI_DELIVERY_COMPLETE. La mémoire persistante (capacité FI_PMEM), cependant, est souvent utilisée avec la sémantique FI_COMMIT_COMPLETE. Les concepts de complétion hétérogène s'appliquent

toujours.

Pour les transferts marqués par l'initiateur avec FI_COMMIT_COMPLETE, une complétion à la cible indique que les résultats sont visibles et durables. Pour les transferts ciblant la mémoire persistante, mais utilisant une sémantique de complétion différente à l'initiateur, la visibilité à la cible est similaire à celle décrite ci-dessus. La durabilité n'est associée qu'aux transferts marqués avec FI_COMMIT_COMPLETE

.

Pour les transferts ciblant la mémoire persistante qui demandent FI_DELIVERY_COMPLETE, une complétion, soit à l'initiateur soit à la cible, indique que les données sont visibles. La visibilité à la cible peut être transmise en utilisant l'un des mécanismes décrits ci-dessus – générer une complétion à la cible, envoyer un message depuis l'initiateur, etc. De même, si l'initiateur a demandé FI_TRANSMIT_COMPLETE, des étapes supplémentaires sont nécessaires pour assurer la visibilité à la cible. Par exemple, le transfert peut générer une complétion à la cible, ce qui indiquerait la visibilité, mais pas la durabilité. L'initiateur peut également suivre le transfert par une autre opération qui force la visibilité, comme utiliser FI_FENCE en conjonction avec FI_DELIVERY_COMPLET

E
.

NOTE

S

Une file de complétion doit être liée à au moins un point de terminaison activé avant que toute opération telle que fi_cq_read, fi_cq_readfrom, fi_cq_sread, fi_cq_sreadfrom, etc. puisse y être

appelée.

Si une file de complétion a débordé, elle sera placée dans un état `overrun'. Les opérations de lecture continueront de retourner toute complétion valide et non corrompue, si

disponible. Après que toutes les complétions valides ont été récupérées, toute tentative de lecture de la CQ résultera en un retour d'un événement d'erreur FI_EOVERRUN. Les fi
les de complétion en débordement sont considérées comme fatales et ne peuvent pas être utilisées pour signaler des complétions supplémentaires une fois le débordement survenu.
