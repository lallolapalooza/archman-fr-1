NOM

fi_msg - Opérations de transfert de données de message

fi_recv / fi_recvv / fi_recvmsg
Publier un tampon pour recevoir un message entrant

fi_send / fi_sendv / fi_sendmsg fi_inject / fi_senddata : Initier une opération pour envoyer un message

SYNOPSIS

#include <rdma/fi_endpoint.h>
ssize_t fi_recv(struct fid_ep *ep, void * buf, size_t len,
    void *desc, fi_addr_t src_addr, void *context);
ssize_t fi_recvv(struct fid_ep *ep, const struct iovec *iov, void **desc,
    size_t count, fi_addr_t src_addr, void *context);
ssize_t fi_recvmsg(struct fid_ep *ep, const struct fi_msg *msg,
    uint64_t flags);
ssize_t fi_send(struct fid_ep *ep, const void *buf, size_t len,
    void *desc, fi_addr_t dest_addr, void *context);
ssize_t fi_sendv(struct fid_ep *ep, const struct iovec *iov,
    void **desc, size_t count, fi_addr_t dest_addr, void *context);
ssize_t fi_sendmsg(struct fid_ep *ep, const struct fi_msg *msg,
    uint64_t flags);
ssize_t fi_inject(struct fid_ep *ep, const void *buf, size_t len,
    fi_addr_t dest_addr);
ssize_t fi_senddata(struct fid_ep *ep, const void *buf, size_t len,
    void *desc, uint64_t data, fi_addr_t dest_addr, void *context);
ssize_t fi_injectdata(struct fid_ep *ep, const void *buf, size_t len,
    uint64_t data, fi_addr_t dest_addr);

ARGUMENTS

ep
Point de terminaison du fabric sur lequel initier l'envoi ou publier le tampon de réception.
buf
Tampon de données à envoyer ou recevoir.
len
Longueur du tampon de données à envoyer ou recevoir, spécifiée en octets. Les transferts valides vont de 0 octet jusqu'à la max_msg_size du point de terminaison.
iov
Tampon de données vectorisé.
count
Nombre d'entrées de données vectorisées.
desc
Descripteur associé au tampon de données. Voir fi_mr(3).
data
Données CQ distantes à transférer avec le message envoyé.
dest_addr
Adresse de destination pour les transferts sans connexion. Ignoré pour les points de terminaison connectés.
src_addr
S'applique uniquement aux points de terminaison sans connexion configurés avec FI_DIRECTED_RECV. Pour toutes les autres configurations de point de terminaison, src_addr est ignoré. src_addr définit l'adresse source à partir de laquelle recevoir. Par défaut, src_addr est traité comme une adresse de point de terminaison source (c'est-à-dire un fi_addr_t retourné par fi_av_insert / fi_av_insertsvc / fi_av_remove). Si l'indicateur FI_AUTH_KEY est spécifié avec fi_recvmsg, src_addr est traité comme une clé d'autorisation source (c'est-à-dire un fi_addr_t retourné par fi_av_insert_auth_key). S'il est défini à FI_ADDR_UNSPEC, n'importe quelle adresse source peut correspondre.
msg
Descripteur de message pour les opérations d'envoi et de réception.
flags
Indicateurs supplémentaires à appliquer pour l'opération d'envoi ou de réception.
context
Pointeur spécifié par l'utilisateur à associer à l'opération. Ce paramètre est ignoré si l'opération ne générera pas une complétion réussie, sauf si un indicateur d'opération spécifie que le paramètre context doit être utilisé pour l'entrée requise.

DESCRIPTION

Les fonctions d'envoi – fi_send, fi_sendv, fi_sendmsg, fi_inject et fi_senddata – sont utilisées pour transmettre un message d'un point de terminaison à un autre point de terminaison. La principale différence entre les fonctions d'envoi réside dans le nombre et le type de paramètres qu'elles acceptent en entrée. Sinon, elles effectuent la même fonction générale. Les messages envoyés à l'aide des opérations fi_msg sont reçus par un point de terminaison distant dans un tampon publié pour recevoir de tels messages.

Les fonctions de réception – fi_recv, fi_recvv, fi_recvmsg – publient un tampon de données sur un point de terminaison pour recevoir des messages entrants. Comme les opérations d'envoi, les opérations de réception fonctionnent de manière asynchrone. Les utilisateurs ne doivent pas toucher aux tampons de données publiés tant que l'opération de réception n'est pas terminée.

Un point de terminaison doit être activé avant qu'une application puisse y publier des opérations d'envoi ou de réception. Pour les points de terminaison connectés, les tampons de réception peuvent être publiés avant l'appel de connect ou accept sur le point de terminaison. Cela garantit que les tampons sont disponibles pour recevoir les données entrantes immédiatement après l'établissement de la connexion.

Les opérations de message terminées sont signalées à l'utilisateur via un ou plusieurs collecteurs d'événements associés au point de terminaison. Les utilisateurs fournissent un contexte qui est associé à chaque opération et qui est retourné à l'utilisateur dans le cadre de la complétion de l'événement. Voir fi_cq pour les détails des événements de complétion.

fi_send

L'appel fi_send transfère les données contenues dans le tampon de données spécifié par l'utilisateur vers un point de terminaison distant, les limites de message étant maintenues.

fi_sendv

L'appel fi_sendv ajoute la prise en charge d'une liste scatter-gather à fi_send. Le fi_sendv transfère l'ensemble des tampons de données référencés par le paramètre iov vers un point de terminaison distant en un seul message.

fi_sendmsg

L'appel fi_sendmsg prend en charge les transferts de données sur les points de terminaison connectés et sans connexion, avec la possibilité de contrôler l'opération d'envoi par appel à l'aide d'indicateurs. La fonction fi_sendmsg prend une struct fi_msg en entrée.

struct fi_msg {
    const struct iovec *msg_iov; /* scatter-gather array */
    void               **desc;   /* local request descriptors */
    size_t             iov_count;/* # elements in iov */
    fi_addr_t          addr;     /* optional endpoint address */
    void               *context; /* user-defined context */
    uint64_t           data;     /* optional message data */
};

fi_inject

L'appel d'envoi inject est une version optimisée de fi_send avec les caractéristiques suivantes. Le tampon de données est disponible pour être réutilisé immédiatement au retour de l'appel, et aucune entrée CQ ne sera écrite si le transfert se termine avec succès.

Conceptuellement, cela signifie que la fonction fi_inject se comporte comme si l'indicateur de transfert FI_INJECT était défini, que les complétions sélectives sont activées et que l'indicateur FI_COMPLETION n'est pas spécifié. Notez que l'entrée CQ sera supprimée même si le comportement par défaut du point de terminaison est d'écrire des entrées CQ pour toutes les complétions réussies. Voir la discussion sur les indicateurs ci-dessous pour plus de détails. La taille de message demandée qui peut être utilisée avec fi_inject est limitée par inject_size.

Si FI_HMEM est activé, l'appel fi_inject ne peut accepter un tampon dont iface est égal à FI_HMEM_SYSTEM que si le fournisseur requiert le mr_mode FI_MR_HMEM. Cette limitation s'applique à tous les appels fi_*inject* et n'affecte pas la manière dont inject_size est signalé.

fi_senddata

L'appel d'envoi de données est similaire à fi_send, mais permet l'envoi de données CQ distantes (voir l'indicateur FI_REMOTE_CQ_DATA) dans le cadre du transfert.

fi_injectdata

L'appel d'injection de données est similaire à fi_inject, mais permet l'envoi de données CQ distantes (voir l'indicateur FI_REMOTE_CQ_DATA) dans le cadre du transfert.

fi_recv

L'appel fi_recv publie un tampon de données dans la file de réception du point de terminaison correspondant. Les réceptions publiées sont recherchées dans l'ordre dans lequel elles ont été publiées afin de correspondre aux envois. Les limites de message sont maintenues. L'ordre dans lequel les réceptions se terminent dépend du type de point de terminaison et du protocole. Pour les points de terminaison sans connexion, le paramètre src_addr peut être utilisé pour indiquer qu'un tampon doit être publié pour recevoir les données entrantes d'un point de terminaison distant spécifique.

fi_recvv

L'appel fi_recvv ajoute la prise en charge d'une liste scatter-gather à fi_recv. Le fi_recvv publie l'ensemble des tampons de

données référencés par le paramètre
iov pour recevoir des données entrantes.

g

terminaison connectés et non connectés, avec la possibilité de con
trôler l'opération de réception pour chaque appel à l'aide de dra

Les drapeaux spécifiés avec fi_recvmsg / fi_sendmsg remplacent la plupart des drapeaux précédemment configurés avec le point de terminaison, sauf indication contraire (voir fi_endpoint.3). NOTE

S

Si un point de terminaison a été configuré avec FI_MSG_PREFIX, l'application doit inclure un espace de tampon de taille msg_prefix_size, tel que spécifié par les attri

buts du point de terminaison. Le tampon préfixe doit se trouver au début des données référencées par le paramètre buf, ou être référencé par le premier vecteur d'E/S. L
'espace de préfixe de message ne peut pas être réparti entre plusieurs vecteurs d'E/S. La taille du tampon préfixe doit être incluse dans la longueur totale du tampon.

ERREUR

S
-FI_EAGA
IN
Indique que le fournisseur sous-jacent manque actuellement des ressources nécessaires pour initier l'opér
ation demandée. Les raisons pour lesquelles un fournisseur retourne FI_EAGAIN sont variées. Cependant,
les raisons courantes incluent un tamponnage interne insuffisant ou des files de traitement pleines.

Un tamponnage interne insuffisant est souvent associé aux opérations utilisant FI_INJECT. Dans de tels cas, un tamponnage supplémentaire peut devenir disponible à mesure que les opérations publiées se

complètent.

Des files de traitement pleines peuvent être un état temporaire lié au traitement local (par exemple, un grand message est en cours de transfert), ou peuvent être le résultat d'un contrôle de flux. Dans ce dernier cas, les files peuvent rester bloquées jusqu'à ce que des ressources supplémentaires soient disponibles du côté distant du

transfert.

Dans tous les cas, l'opération peut être réessayée après que des ressources supplémentaires sont devenues disponibles. Lors de l'utilisation de FI_PROGRESS_MANUAL, l'application doit v

érifier les complétions de transmission et de réception après avoir reçu FI_EAGAIN comme valeur de retour, indépendamment de l'opération qui a échoué. Cela est également fortement
recommandé lors de l'utilisation de FI_PROGRESS_AUTO, car des accusés de réception ou des messages de contrôle de flux peuvent nécessiter d'être traités afin de reprendre l'exécution.
