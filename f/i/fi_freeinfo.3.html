DESCRIPTIO

N

L'appel fi_getinfo() est utilisé pour découvrir quelles fonctionnalités de communication sont disponibles dans le système, ainsi que la meilleure façon dont elles peuvent être utilisées par une application. L'appel est librement modélisé sur getaddrinfo(). fi_getinfo() permet à une application d'échanger des informations entre une application et les fournisseurs libfabric concernant son ensemble requis de communication. Il fournit la capacité d'accéder à des détails réseau complexes, équilibrés entre expressivité et simplicité

d'utilisation.

fi_getinfo retourne des informations sur les services de fabric disponibles pour atteindre un nœud ou un service spécifié, sous réserve des indications fournies. Les appelants peuvent spécifier NULL pour node, service et hints afin d'obtenir des informations sur les fournisseurs disponibles et leurs modèles d'utilisation optimaux. Si aucune information de fabric correspondante n'est disponible, info sera défini à NULL et l'appel retournera

-FI_ENODATA.

Sur la base des paramètres d'indications, de node et de service d'entrée, une liste de domaines et de points de terminaison de fabric sera retournée. Chaque structure fi_info décrira un point de terminaison qui répond aux critères de communication spécifiés par l'application. Chaque point de terminaison sera associé à un domaine. Les applications peuvent restreindre le nombre de points de terminaison retournés en incluant des critères supplémentaires dans leurs indications de recherche. Assouplir ou éliminer les indications d'entrée augmentera le nombre et le type de points de terminaison disponibles. Les fournisseurs qui retournent plusieurs points de terminaison pour un seul appel fi_getinfo doivent retourner les points de terminaison les plus performants en premier. Les fournisseurs peuvent indiquer qu'un point de terminaison et un domaine peuvent prendre en charge des capacités supplémentaires par rapport à celles demandées par l'utilisateur, uniquement si un tel support n'affectera pas défavorablement les performances ou la sécurité de

l'application.

Le paramètre version est utilisé par l'application pour demander la version souhaitée des interfaces. La version détermine le format de toutes les structures de données utilisées par n'importe laquelle des interfaces de fabric. Les applications devraient utiliser la macro FI_VERSION(majeur, mineur) pour indiquer la version, avec des valeurs entières codées en dur pour les valeurs majeure et mineure. Les valeurs d'énumération FI_MAJOR_VERSION et FI_MINOR_VERSION définies dans fabric.h spécifient la dernière version de la bibliothèque installée. Cependant, il est recommandé que les valeurs entières de FI_MAJOR_VERSION et FI_MINOR_VERSION soient utilisées, plutôt que de référencer les types d'énumération, afin d'assurer la compatibilité avec les futures versions de la bibliothèque. Cela protège contre la compilation de l'application depuis les sources contre une version plus récente de la bibliothèque qui introduit de nouveaux champs dans les structures de données, qui ne seraient pas initialisés par

l'application.

Node, service ou hints peuvent être fournis, avec n'importe quelle combinaison prise en charge. Si node est fourni, fi_getinfo tentera de résoudre l'adresse de fabric vers le nœud donné. Si node n'est pas donné, fi_getinfo tentera de résoudre les informations d'adressage de fabric sur la base des indications fournies. Node est couramment utilisé pour fournir une adresse réseau (telle qu'une adresse IP) ou un nom d'hôte. Service est généralement associé à une adresse de transport (telle qu'un numéro de port TCP). Les paramètres node et service peuvent être mappés par les fournisseurs vers des adresses de fabric natives. Les applications peuvent également passer une adresse au format FI_ADDR_STR (voir les détails du format ci-dessous) comme paramètre node. Dans de tels cas, le paramètre service doit être

NULL.

Le paramètre hints, s'il est fourni, peut être utilisé pour limiter la sortie résultante comme indiqué ci-dessous. En règle générale, spécifier une valeur non nulle pour les indications d'entrée indique qu'un fournisseur doit prendre en charge la valeur demandée ou faire échouer l'opération avec -FI_ENODATA. À l'exception des bits de mode, les indications définies à zéro sont traitées comme un joker. Une valeur d'indication mise à zéro entraîne le retour par les fournisseurs soit d'une valeur par défaut, soit d'une valeur qui fonctionne le mieux pour leur implémentation. Les bits de mode définis à zéro indiquent que l'application ne prend en charge aucun

mode.

L'appelant doit appeler fi_freeinfo pour libérer les structures fi_info retournées par cet

appel.

L'appel fi_allocinfo allouera et mettra à zéro une structure fi_info et

toutes les sous-structures associées. fi_dupinfo dupliquera une seu
le structure fi_info et toutes les sous-structures qu'elle contient.

CAPACITÉS

Les capacités de l'interface sont obtenues en combinant les indicateurs suivants par une opération OU logique. Si les capacités dans le paramètre hint sont définies à 0, le fournisseur sous-jacent retournera l'ensemble des capacités qui sont prises en charge. Sinon, les fournisseurs retourneront des données correspondant à l'ensemble de capacités spécifié. Les fournisseurs peuvent indiquer la prise en charge de capacités supplémentaires au-delà de celles demandées lorsque l'utilisation de capacités étendues n'affectera pas définitivement les performances négativement et n'exposera pas l'application à des communications au-delà de ce qui a été demandé. Les applications peuvent utiliser cette fonctionnalité pour demander un ensemble minimal de exigences, puis vérifier les capacités retournées pour activer des optimisations supplémentaires.

FI_ATOMIC
Spécifie que le point de terminaison prend en charge un ensemble d'opérations atomiques. Les points de terminaison prenant en charge cette capacité prennent en charge les opérations définies par struct fi_ops_atomic. En l'absence d'indicateurs pertinents, FI_ATOMIC implique la capacité d'initier et d'être la cible de lectures et d'écritures atomiques distantes. Les applications peuvent utiliser les indicateurs FI_READ, FI_WRITE, FI_REMOTE_READ et FI_REMOTE_WRITE pour restreindre les types d'opérations atomiques prises en charge par un point de terminaison.
FI_AV_USER_ID
Demande au fournisseur de prendre en charge l'association d'un identifiant spécifié par l'utilisateur avec chaque adresse de vecteur d'adresse (AV). Les identifiants utilisateur sont retournés avec les données d'achèvement à la place de l'adresse AV. Voir fi_domain(3) et fi_av(3) pour plus de détails.
FI_COLLECTIVE
Demande la prise en charge des opérations collectives. Les points de terminaison prenant en charge cette capacité prennent en charge les opérations collectives définies dans fi_collective(3).
FI_DIRECTED_RECV
Demande au point de terminaison de communication d'utiliser l'adresse source d'un message entrant lors de son appariement avec un tampon de réception. Si cette capacité n'est pas définie, le paramètre src_addr pour les opérations de réception de messages et balisés est ignoré.
FI_TAGGED_DIRECTED_RECV
Similaire à FI_DIRECTED_RECV, mais s'applique uniquement aux opérations de réception balisées.
FI_EXACT_DIRECTED_RECV
Similaire à FI_DIRECTED_RECV, mais exige que l'adresse source soit exacte, c'est-à-dire que FI_ADDR_UNSPEC n'est pas autorisé. Cette capacité peut être utilisée seule, ou en conjonction avec FI_DIRECTED_RECV ou FI_TAGGED_DIRECTED_RECV comme modificateur pour interdire l'utilisation de FI_ADDR_UNSPEC comme adresse source.
FI_FENCE
Indique que le point de terminaison prend en charge l'indicateur FI_FENCE sur les opérations de transfert de données. La prise en charge nécessite le suivi de la complétion de toutes les requêtes d'émission précédentes vers un point de terminaison distant spécifié avant d'initier l'opération clôturée. Les opérations clôturées sont souvent utilisées pour faire respecter l'ordre entre des opérations qui ne sont pas autrement garanties par le fournisseur ou le protocole sous-jacent.
FI_HMEM
Spécifie que le point de terminaison doit prendre en charge les transferts vers et depuis la mémoire du périphérique.
FI_LOCAL_COMM
Indique que le point de terminaison prend en charge la communication locale de l'hôte. Cet indicateur peut être utilisé en conjonction avec FI_REMOTE_COMM pour indiquer que la communication locale et distante sont requises. Si ni FI_LOCAL_COMM ni FI_REMOTE_COMM ne sont spécifiés, le fournisseur indiquera la prise en charge de la configuration qui affecte les performances de manière minimale. Les fournisseurs qui définissent FI_LOCAL_COMM mais pas FI_REMOTE_COMM, par exemple un fournisseur de mémoire partagée, peuvent uniquement être utilisés pour la communication entre processus sur le même système.
FI_MSG
Spécifie qu'un point de terminaison doit prendre en charge l'envoi et la réception de messages ou de datagrammes. Les capacités de message impliquent la prise en charge de files d'attente d'envoi et/ou de réception. Les points de terminaison prenant en charge cette capacité prennent en charge les opérations définies par struct fi_ops_msg.

Les caps peuvent être utilisées pour spécifier ou restreindre le type d'opérations de messagerie qui sont prises en charge. En l'absence d'indicateurs pertinents, FI_MSG implique la capacité d'envoyer et de recevoir des messages. Les applications peuvent utiliser les indicateurs FI_SEND et FI_RECV pour optimiser un point de terminaison en mode envoi uniquement ou réception uniquement.

FI_MULTICAST
Indique que le point de terminaison prend en charge les transferts de données en multicast. Cette capacité doit être associée à FI_MSG. Les applications peuvent utiliser FI_SEND et FI_RECV pour optimiser le multicast en mode envoi uniquement ou réception uniquement.
FI_MULTI_RECV
Spécifie que le point de terminaison doit prendre en charge l'indicateur FI_MULTI_RECV lors de la publication de tampons de réception.
FI_TAGGED_MULTI_RECV
Spécifie que le point de terminaison doit prendre en charge l'indicateur FI_MULTI_RECV lors de la publication de tampons de réception balisés.
FI_NAMED_RX_CTX
Demande que les points de terminaison prenant en charge plusieurs contextes de réception permettent à un initiateur de cibler (ou de nommer) un contexte de réception spécifique dans le cadre d'une opération de transfert de données.
FI_PEER
Spécifie que le fournisseur doit prendre en charge son utilisation en tant que fournisseur pair dans le flux de l'API pair. Le fournisseur doit prendre en charge l'importation de owner_ops lors de l'ouverture d'un CQ, d'un compteur et d'une file de réception partagée.
FI_READ
Indique que l'utilisateur a besoin d'un point de terminaison capable d'initier des lectures contre des régions mémoire distantes. Cet indicateur exige que FI_RMA et/ou FI_ATOMIC soient définis.
FI_RECV
Indique que l'utilisateur a besoin d'un point de terminaison capable de recevoir des transferts de données de messages. Les transferts de messages incluent les opérations de message de base ainsi que la fonctionnalité de message balisé.
FI_REMOTE_COMM
Indique que le point de terminaison prend en charge la communication avec des points de terminaison situés sur des nœuds distants (à travers le tissu). Voir FI_LOCAL_COMM pour des détails supplémentaires. Les fournisseurs qui définissent FI_REMOTE_COMM mais pas FI_LOCAL_COMM, par exemple des NIC qui manquent de prise en charge de la boucle de retour, ne peuvent pas être utilisés pour communiquer avec des processus sur le même système.
FI_REMOTE_READ
Indique que l'utilisateur a besoin d'un point de terminaison capable de recevoir des opérations de lecture mémoire de points de terminaison distants. Cet indicateur exige que FI_RMA et/ou FI_ATOMIC soient définis.
FI_REMOTE_WRITE
Indique que l'utilisateur a besoin d'un point de terminaison capable de recevoir des opérations d'écriture mémoire de points de terminaison distants. Cet indicateur exige que FI_RMA et/ou FI_ATOMIC soient définis.
FI_RMA
Spécifie que le point de terminaison doit prendre en charge ROpérations de lecture et d'écriture mémoire. Les points d'extrémité prenant en charge cette capacité prennent en charge les opérations définies par la structure fi_ops_rma. En l'absence de tout indicateur pertinent, FI_RMA implique la capacité d'initier et d'être la cible de lectures et d'écritures mémoire à distance. Les applications peuvent utiliser les indicateurs FI_READ, FI_WRITE, FI_REMOTE_READ et FI_REMOTE_WRITE pour restreindre les types d'opérations RMA prises en charge par un point
d'extrémité.

Les transferts de messages balisés associent une clé ou un tag spécifié par l'utilisateur à chaque message, utilisé à des fins d'appariement côté distant. Les points d'extrémité prenant en charge cette capacité prennent en charge les opérations définies par la structure fi_ops_tagged. En l'absence de tout indicateur pertinent, FI_TAGGED implique la capacité d'envoyer et de recevoir des messages balisés. Les applications peuvent utiliser les indicateurs FI_SEND et FI_RECV pour optimiser un point d'extrémité en mode envoi uniquement ou réception

Les capacités peuvent être regroupées en trois catégories générales : primaires, secondaires et modificateurs primaires. Les capacités primaires doivent être explicitement demandées par une application, et un fournisseur doit n'activer la prise en charge que de ces capacités primaires qui ont été sélectionnées. Les modificateurs primaires sont utilisés pour limiter une capacité primaire, comme restreindre un point d'extrémité à l'envoi uniquement. Si aucun modificateur n'est spécifié pour une capacité applicable, tous les modificateurs pertinents sont supposés. Voir les définitions ci-dessus pour plus de

détails.

Les capacités secondaires peuvent être demandées de manière optionnelle par une application. Si demandées, un fournisseur doit prendre en charge la capacité ou échouer à la requête fi_getinfo (FI_ENODATA). Un fournisseur peut optionnellement signaler des capacités secondaires non sélectionnées si cela ne compromettrait pas les performances ou la

sécurité.

FI_PEER

MOD

E

Les bits de mode opérationnel sont utilisés pour transmettre des exigences qu'une application doit respecter lors de l'utilisation des interfaces de tissu. Les modes spécifient des manières optimales d'accéder au point d'extrémité ou au domaine rapporté. Les applications conçues pour prendre en charge un mode d'opération spécifique peuvent voir des performances améliorées lorsque ce mode est souhaité par le fournisseur. Il est recommandé que les fournisseurs prennent en charge les applications qui désactivent tout mode préféré par le

fournisseur.

En entrée de fi_getinfo, les applications définissent les bits de mode qu'elles prennent en charge. En sortie, les fournisseurs effaceront les bits de mode qui ne sont pas nécessaires pour atteindre des performances élevées. Les bits de mode restant définis indiquent les exigences de l'application pour utiliser les interfaces de tissu créées à l'aide du fi_info retourné. L'ensemble des modes est listé ci-dessous. Si une structure hints NULL est fournie, alors l'ensemble des modes pris en charge par le fournisseur sera retourné dans la ou les structures

info.
FI_ASYNC_I
OV
Les applications peuvent référencer plusieurs tampons de données comme partie d'une seule opération via l'utilisation de vecteurs d'entrées/sorties (IOV/SGEs). Typiquement, le contenu d'un vecteur d'entrées/sorties est copié par le fournisseur dans une zone de tampon interne, ou directement vers le matériel sous-jacent. Cependant, lorsque un grand nombre d'entrées IOV sont prises en charge, la mise en tampon des IOV peut avoir un impact négatif sur les performances et la consommation de mémoire. Le mode FI_ASYNC_IOV indique que l'application doit fournir la mise en tampon nécessaire pour les vecteurs d'entrées/sorties. Lorsqu'il est défini, une application ne doit pas modifier un vecteur d'entrées/sorties de longueur > 1, y compris tout tableau de descripteurs de mémoire associé, jusqu'à ce que l'opération associée soit
terminée.
FI_CONTE
XT
Spécifie que le fournisseur exige que les applications utilisent la structure fi_context comme paramètre de contexte par opération pour les opérations qui génèrent des complétions complètes. Cette structure doit être traitée comme opaque par l'application. Pour des raisons de performance, cette structure doit être allouée par l'utilisateur, mais peut être utilisée par le fournisseur de tissu pour suivre l'opération. Typiquement, les utilisateurs intègrent la structure fi_context dans leur propre structure de contexte. La structure fi_context doit rester valide jusqu'à ce que l'opération correspondante se termine ou soit annulée avec succès. En tant que telle, fi_context ne doit PAS être allouée sur la pile. Le faire risque de provoquer une corruption de pile difficile à déboguer. Les utilisateurs ne doivent pas mettre à jour ni interpréter les champs de cette structure, ni la réutiliser tant que l'opération d'origine n'est pas terminée. Si une opération ne génère pas de complétion (c.-à-d. que le point d'extrémité a été configuré avec FI_SELECTIVE_COMPLETION et que l'opération n'a pas été initiée avec l'indicateur FI_COMPLETION), alors le paramètre de contexte est ignoré par le fournisseur de tissu. La structure est spécifiée dans rdma/fabric.
h.
FI_CONTEX
T2
Ce bit est similaire à FI_CONTEXT, mais double l'exigence du fournisseur sur la taille de la structure de contexte par opération. Lorsqu'il est défini, cela spécifie que le fournisseur exige que les applications utilisent la structure fi_context2 comme paramètre de contexte par opération. Ou, de manière optionnelle, une application peut fournir un tableau de deux structures fi_context (p. ex. struct fi_context[2]) à la place. Les exigences pour utiliser la structure fi_context2 sont identiques à celles définies pour FI_CONTEXT
ci-dessus.
FI_LOCAL_MR
(obsolète)
Le fournisseur est optimisé pour que les applications enregistrent la mémoire pour les tampons de données accédés localement. Les tampons de données utilisés dans les opérations d'envoi et de réception et comme tampon source pour les opérations RMA et atomiques doivent être enregistrés par l'application pour les domaines d'accès ouverts avec cette capacité. Cet indicateur est défini pour la compatibilité et est ignoré si la version de l'application est 1.5 ou ultérieure et que le mr_mode du domaine est défini sur autre chose que FI_MR_BASIC ou FI_MR_SCALABLE. Voir l'attribut de domaine mr_mode fi_domain(3) et fi_mr(3)
.
FI_MSG_PREF
IX
Le mode de préfixe de message indique qu'une application fournira de l'espace de tampon devant tous les tampons d'envoi et de réception de messages pour utilisation par le fournisseur. Typiquement, le fournisseur uti
lise cet espace pour implémenter un protocole, les en-têtes de protocole étant écrits dans la zone de préfixe. Le contenu de l'espace de préfixe doit être traité comme opaque. L'utilisation de FI_MSG_PREFIX peut améli
orer les performances de l'application sur certains fournisseurs en réduisant le nombre de vecteurs d'entrées/sorties référencés par le matériel sous-jacent et en éliminant l'allocation de tampons par le fournisseur.

FI_MSG_PREFIX ne s'applique qu'aux opérations d'envoi et de réception, y compris les envois et réceptions balisés. Les RMA et opérations atomiques ne nécessitent pas que l'application fournisse des tampons de préfixe. L'espace de tampon de préfixe doit être fourni avec tous les envois et réceptions, quelle que soit la taille du transfert ou les autres options de transfert. La propriété des tampons de préfixe est traitée de la même manière que celle des tampons de message correspondants, mais la taille du tampon de préfixe n'est pas comptée dans les limites de message, y compris

inject.

Les applications qui prennent en charge le mode de préfixe doivent fournir de l'espace de tampon avant leurs propres données de message. La taille de l'espace qui doit être fournie est spécifiée par l'attribut de point d'extrémité msg_prefix_size. Les fournisseurs sont tenus de définir un msg_prefix_size qui est un multiple de 8 octets. De plus, les applications peuvent recevoir des paquets générés par le fournisseur qui ne contiennent pas de données d'application. Ces messages reçus indiqueront une taille de transfert égale ou inférieure à msg_prefix_size

.

Le pointeur de tampon donné à toutes les opérations d'envoi et de réception doit pointer vers le début de la région de préfixe du tampon (par opposition à la charge utile). Pour les opérations d'envoi/réception scatter-gather, le tampon de préfixe doit être une région contiguë, bien qu'il puisse être ou non directement adjacent à la portion de charge utile du

tampon.
FI_RX_CQ_DA
TA
Ce bit de mode ne s'applique qu'aux transferts de données qui définissent FI_REMOTE_CQ_DATA.
Lorsqu'il est défini, un transfert de données qui transporte des données CQ distantes consomme
ra un tampon de réception sur la ceci. C'est vrai même pour les opérations qui normalement
ne consommeraient pas les tampons de réception publiés, comme les opérations d'écriture RMA.

NOTE

S

Divers appels libfabric, y compris fi_getinfo, prennent une struct fi_info en entrée. Les applications doivent utiliser les structures fi_info allouées par libfabric. Une struct fi_info mise à zéro peut être allouée avec fi_allocinfo, qui peut ensuite être initialisée par l'utilisateur. Une struct fi_info peut être copiée pour modification en utilisant l'appel fi_dupinfo()

.

Si des indices sont fournis, l'opération sera contrôlée par les valeurs fournies dans les différents champs (voir la section sur fi_info). Les applications qui nécessitent des interfaces de communication spécifiques, des domaines, des capacités ou d'autres exigences peuvent les spécifier en utilisant les champs dans hints. Libfabric retourne une liste chaînée dans info qui pointe vers une liste d'interfaces correspondantes. info est mis à NULL s'il n'y a aucune interface de communication ou si aucune ne correspond aux indices

d'entrée.

Si node est fourni, fi_getinfo tentera de résoudre l'adresse de fabric vers le node donné. Si node n'est pas fourni, fi_getinfo tentera de résoudre les informations d'adressage de fabric sur la base des indices fournis. L'appelant doit appeler fi_freeinfo pour libérer les structures fi_info retournées par

fi_getinfo.

Si ni node, ni service, ni hints ne sont fournis, alors fi_getinfo retourne simplement la liste de toutes les interfaces de communication

disponibles.

Plusieurs threads peuvent appeler

fi_getinfo simultanément, sans auc
une exigence de sérialisation.
