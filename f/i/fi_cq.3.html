DESCRIPTIO

N

Les files d'attente de complétion sont utilisées pour signaler les événements associés aux transferts de données. Elles sont associées aux envois et réceptions de messages, RMA, atomiques, messages étiquetés et événements déclenchés. Les événements signalés sont généralement associés à un point de terminaison de fabric, mais peuvent aussi faire référence à des régions mémoire utilisées comme cible d'une opération RMA ou

atomique.

fi_cq_ope

n

fi_cq_open alloue une nouvelle file d'attente de complétion. Contrairement aux files d'attente d'événements, les files d'attente de complétion sont associées à un domaine de ressources et peuvent être entièrement déchargées dans le matériel du

fournisseur.

Les propriétés et le comportement d'une file d'attente de complétion sont définis par struct

fi_cq_attr.

Les CQ peuvent être associées à un objet d'attente spécifique. Les objets d'attente permettent aux applications de se bloquer jusqu'à ce que l'objet d'attente soit signalé, indiquant qu'une complétion est disponible pour être lue. Les utilisateurs peuvent utiliser fi_control pour récupérer l'objet d'attente sous-jacent associé à une CQ, afin de l'utiliser dans d'autres appels système. Les valeurs suivantes peuvent être utilisées pour type d'objet d'attente associé à une CQ : FI_WAIT_NONE, FI_WAIT_UNSPEC, FI_WAIT_SET, FI_WAIT_FD, FI_WAIT_MUTEX_COND (obsolète), et FI_WAIT_YIELD. La valeur par défaut est
FI_WAIT_NONE.

fi_cq_sreadfrom.
- FI_WAIT_UNSP
EC
Spécifie que l'utilisateur n'attendra sur la CQ qu'à l'aide d'appels de l'interface fabric, tels que fi_cq_sread ou fi_cq_sreadfrom. Dans ce cas, le fournisseur sous-jacent peut sélectionner l'objet d'attente le plus approprié ou le plus performant disponible, y compris des mécanismes d'attente personnalisés. Les applications qui sélectionnent FI_WAIT_UNSPEC ne sont pas garanties de pouvoir récupérer l'objet d'attente
sous-jacent.

Par défaut, lorsqu'une complétion est insérée dans une CQ qui prend en charge les lectures bloquantes (fi_cq_sread/fi_cq_sreadfrom), l'objet d'at
tente correspondant est signalé. Les utilisateurs peuvent spécifier une condition qui doit d'abord être remplie avant que l'attente ne soit satisf
aite. Ce champ indique comment le fournisseur doit interpréter le champ cond, qui décrit la condition nécessaire pour signaler l'objet d'attente.

Une condition d'attente doit être traitée comme une optimisation. Les fournisseurs ne sont pas tenus de satisfaire les exigences de la condition avant de signaler l'objet d'attente. Les applications ne doivent pas compter sur le fait que la condition soit nécessairement vraie lorsqu'un appel de lecture bloquante

retourne.

Si wait_cond est défini à FI_CQ_COND_THRESHOLD, alors le champ cond est interprété comme une valeur de seuil de type size_t. Le seuil indique le nombre d'entrées qui doivent être mises en file d'attente dans la CQ avant que l'attente ne soit

satisfaite.

FI_WAIT_NONE.

(obsolète)
Si wait_obj est FI_WAIT_SET, ce champ référence un objet d'attente auquel la file de complétion doit s'attacher. Lorsq

à travers plusieurs files d'événements et de complétions. Ce champ est ignoré si wait_obj n'est pas FI_WAIT_SET.

fi_clos

e

L'appel fi_close libère toutes les ressources associées à une file de complétion. Toutes les complétions restant sur la CQ lors de sa fermeture sont

perdues.

Lors de la fermeture de la CQ, il ne doit y avoir aucun point d'extrémité ouvert, aucun cont

exte de transmission ni aucun contexte de réception associé à la CQ. Si des ressources sont
toujours associées à la CQ lors de la tentative de fermeture, l'appel retournera -FI_EBUSY.

fi_contro

l

L'appel fi_control est utilisé pour accéder aux détails spécifiques au fournisseur ou à l'implémentation de la file de complétion. L'accès à la CQ doit être sérialisé à travers tous les appels lorsque fi_control est invoqué, car il peut rediriger l'implémentation des opérations de CQ. Les commandes de contrôle suivantes sont utilisables avec une

CQ.
FI_GETWAIT (void
**)
Cette commande permet à l'utilisateur de récupérer l'objet d'attente de bas niveau associé à la CQ. Le f
ormat de l'objet d'attente est spécifié lors de la création de la CQ, à travers les attributs de la CQ.
Le paramètre arg de fi_control doit être une adresse à laquelle un pointeur vers l'objet d'attente
retourné sera écrit. Voir fi_eq.3 pour plus de détails sur l'utilisation de fi_control avec FI_GETWAIT.

fi_cq_rea

d

L'opération fi_cq_read effectue une lecture non bloquante des données de complétion à partir de la CQ. Le format de l'événement de complétion est déterminé en utilisant l'option fi_cq_format qui a été spécifiée lorsque la CQ a été ouverte. Plusieurs complétions peuvent être récupérées depuis une CQ en un seul appel. Le nombre maximal d'entrées à retourner est limité au paramètre count spécifié, avec le nombre d'entrées lues avec succès depuis la CQ retourné par l'appel. (Voir la section des valeurs de retour ci-dessous.) Une valeur de count de 0 peut être utilisée pour faire progresser les points d'extrémité associés lorsque la progression manuelle est

activée.

Les CQ sont optimisées pour signaler les opérations qui se sont terminées avec succès. Les opérations qui échouent sont signalées « hors bande » (out of band). De telles opérations sont récupérées en utilisa

nt la fonction fi_cq_readerr. Lorsqu'une opération qui s'est terminée avec une erreur inattendue est rencontrée, elle est placée dans une file d'erreurs temporaire. Tenter de lire depuis une CQ alors qu'
un élément est dans la file d'erreurs entraîne l'échec de fi_cq_read avec un code de retour de -FI_EAVAIL. Les applications peuvent utiliser ce code de retour pour déterminer quand appeler fi_cq_readerr.

fi_cq_readfro

m

L'appel fi_cq_readfrom se comporte de manière identique à fi_cq_read, à l'exception qu'il permet à la CQ de retourner des informations d'adresse source à l'utilisateur pour toute donnée reçue. Les données d'adresse source ne sont disponibles que pour les points d'extrémité configurés avec la capacité FI_SOURCE. Si fi_cq_readfrom est appelé sur un point d'extrémité pour lequel les données d'adressage source ne sont pas disponibles, l'adresse source sera définie sur FI_ADDR_NOTAVAIL. Le nombre d'entrées src_addr en entrée doit être le même que le paramètre

count.

Les données d'adressage source retournées sont converties depuis l'adresse native utilisée par le fabric sous-jacent en un fi_addr_t, qui peut être utilisé dans les opérations de transmission. Dans la plupart des cas, le retour d'un fi_addr_t nécessite que l'adresse source ait déjà été insérée dans le vecteur d'adresses associé au point d'extrémité de réception. C'est le cas pour les vecteurs d'adresses de type FI_AV_TABLE. Dans certains fournisseurs lorsque FI_AV_MAP est utilisé, les adresses sources peuvent être converties algorithmiquement en un fi_addr_t utilisable, même si l'adresse source n'a pas été insérée dans le vecteur d'adresses. Cela est permis par l'API, car cela permet au fournisseur d'éviter la recherche d'adresse dans le traitement des messages reçus. Dans aucun cas les fournisseurs n'insèrent d'adresses dans un AV en dehors d'un appel d'application à fi_av_insert ou un appel

similaire.

Pour les points d'extrémité alloués en utilisant la capacité FI_SOURCE_ERR, si l'adresse source ne peut pas être convertie en une valeur fi_addr_t valide, fi_cq_readfrom retournera -FI_EAVAIL, même si les données ont été reçues avec succès. La complétion sera alors signalée à travers fi_cq_readerr avec le code d'erreur -FI_EADDRNOTAVAIL. Voir fi_cq_readerr pour plus de

détails.

Si FI_SOURCE est spécifié sans FI_SOURCE_ERR, les adresses sources qui ne peuvent pas être mappées vers un fi_addr_t utilisable seront signalées comme FI_ADDR_NOTAVAI

L
.

fi_cq_sread /

fi_cq_sreadfrom

Les appels fi_cq_sread et fi_cq_sreadfrom sont les opérations bloquantes équivalentes à fi_cq_read et fi_cq_readfrom. Leur comportement est similaire aux appels non bloquants, à l'exception que les appels ne retourneront pas tant qu'une complétion n'a pas été lue depuis la CQ ou qu'une erreur ou un délai d'attente ne s'est

produit.

Les threads bloqués dans cette fonction retourneront à l'appelant s'ils sont signalés par une source externe. C'est vrai même si le délai d'attente ne s'est pas produit ou s'il a été spécifié comme

infini.

Il est invalide pour les applications d'appeler ces

fonctions si la CQ a été configurée avec un obje
t d'attente de type FI_WAIT_NONE ou FI_WAIT_SET.

fi_cq_reader

r

La fonction de lecture d'erreur, fi_cq_readerr, récupère des informations concernant toute opération asynchrone qui s'est terminée avec une erreur inattendue. fi_cq_readerr est un appel non bloquant, retournant immédiatement qu'une complétion d'erreur ait été trouvée ou

non.

Les informations d'erreur sont signalées à l'utilisateur à travers la structure fi_cq_err_entry. Le format de cette structure est défini

ci-dessous. 
struct fi_cq_err_entry {
    void     *op_context; /* operation context */
    uint64_t flags;       /* completion flags */
    size_t   len;         /* size of received data */
    void     *buf;        /* receive data buffer */
    uint64_t data;        /* completion data */
    uint64_t tag;         /* message tag */
    size_t   olen;        /* overflow length */
    int      err;         /* positive error code */
    int      prov_errno;  /* provider error code */
    void    *err_data;    /*  error data */
    size_t   err_data_size; /* size of err_data */
    fi_addr_t src_addr; /* error source address
*/
}
;

La raison générale de l'erreur est fournie à travers le champ err. Des informations d'erreur spécifiques au fournisseur peuvent également être disponibles à travers les champs prov_errno et err_data. Les utilisateurs peuvent appeler fi_cq_strerror pour convertir les informations d'erreur spécifiques au fournisseur en une chaîne imprimable à des fins de débogage. Voir les détails des champs ci-dessous pour plus d'informations sur l'utilisation de err_data et

err_data_size.

Notez que des complétions d'erreur sont générées pour toutes les opérations, y compris celles pour lesquelles une complétion n'a pas été demandée (par ex. un point d'extrémité est configuré avec FI_SELECTIVE_COMPLETION, mais la requête n'avait pas l'indicateur FI_COMPLETION défini). Dans de tels cas, les fournisseurs renverront autant d'informations que ce qui est rendu disponible par le logiciel et le matériel sous-jacents concernant l'échec, les autres champs seront définis à NULL ou 0. Cela inclut la valeur op_context, qui n'a peut-être pas été fournie ou a été ignorée en entrée dans le cadre du

transfert.

Les codes d'erreur de complétion notables sont donnés

ci-dessous.
FI_EADDRNOTAV
AIL

ue le transfert de données a été reçu et traité avec succès, les champs fi_cq_err_entry contenant des informations sur la complétion. Le champ err_data sera défini sur les données de l'adresse source. L'adresse source
sera dans le même format que celui spécifié via le champ addr_format de fi_info pour le domaine ouvert. Celle-ci peut être passée directement à un appel fi_av_insert pour ajouter l'adresse source au vecteur d'adresses.

Pour les versions d'API 1.20 et ultérieures, si l'EP est configuré avec FI_AV_AUTH_KEY, src_addr sera défini sur le gestionnaire de clé d'autorisation fi_addr_t ou un identifiant de clé d'autorisation défini par l'utilisateur correspondant au transfert de données entrant. Sinon, la valeur sera définie à FI_ADDR_NOTAVAI

L
.

SÉMANTIQUE DES ÉVÉNEMENTS D'ACHÈVEMENT

Libfabric définit plusieurs `niveaux' d'achèvement, identifiés à l'aide de drapeaux opérationnels. Chaque drapeau indique le moment le plus tôt auquel un événement d'achèvement peut être généré par un fournisseur, et les hypothèses qu'une application peut faire lors du traitement d'un achèvement. Les drapeaux opérationnels sont définis ci-dessous, avec un exemple de la manière dont un fournisseur pourrait implémenter la sémantique. Notez que seule la sémantique doit être respectée par le fournisseur et non l'implémentation. Les fournisseurs peuvent implémenter des sémantiques d'achèvement plus fortes que nécessaire pour une opération donnée, mais seul le comportement défini par le niveau d'achèvement est garanti.

Pour aider à comprendre les différences conceptuelles entre les niveaux d'achèvement, considérez l'envoi d'une lettre. Placer la lettre dans la boîte aux lettres locale pour la collecte est similaire à `achèvement par injection'. Avoir la lettre collectée et déposée dans la boîte aux lettres de destination est équivalent à `achèvement par transmission'. La sémantique `achèvement par livraison' est une garantie plus forte, avec une personne à la destination signant pour la lettre. Cependant, la personne qui a signé pour la lettre n'est pas nécessairement le destinataire prévu. L'option `achèvement par correspondance' est similaire à l'achèvement par livraison, mais nécessite que le destinataire prévu signe pour la lettre.

Le niveau `achèvement par engagement' a des sémantiques différentes des niveaux mentionnés précédemment. L'achèvement par engagement serait plus proche de la lettre arrivant à destination et étant placée dans un coffre-fort ignifugé.

Les drapeaux opérationnels pour les niveaux d'achèvement décrits sont définis ci-dessous.

FI_INJECT_COMPLETE
Indique qu'un achèvement doit être généré lorsque le(s) tampon(s) source peuvent être réutilisés. Un achèvement garantit que les tampons ne seront plus lus et que l'application peut les récupérer. Aucune autre garantie n'est donnée quant à l'état de l'opération.

Exemple : Un fournisseur peut générer cet événement d'achèvement après avoir copié le tampon source dans un tampon réseau, soit en mémoire hôte, soit sur la NIC. Un achèvement par injection n'indique pas que les données ont été transmises sur le réseau, et une erreur locale pourrait survenir après la génération de l'événement d'achèvement, ce qui pourrait empêcher leur transmission.

L'achèvement par injection permet le signalement d'achèvement le plus rapide (et donc la réutilisation des tampons), mais fournit les garanties les plus faibles contre les erreurs réseau.

Remarque : Ce drapeau est utilisé pour contrôler le moment où une entrée d'achèvement est insérée dans une file d'achèvement. Il ne s'applique pas aux opérations qui ne génèrent pas d'entrée de file d'achèvement, comme l'opération fi_inject, et n'est pas soumis à la restriction de limite de message inject_size.

FI_TRANSMIT_COMPLETE
Indique qu'un achèvement doit être généré lorsque l'opération de transmission est terminée par rapport au fournisseur local. Le comportement exact dépend du type de point de terminaison.

Pour les points de terminaison fiables :

Indique qu'un achèvement doit être généré lorsque l'opération a été livrée au point de terminaison pair. Un achèvement garantit que l'opération ne dépend plus de la fabrique ni des ressources locales. L'état de l'opération au point de terminaison pair n'est pas défini.

Exemple : Un fournisseur peut générer un événement d'achèvement par transmission lors de la réception d'un accusé de réception du point de terminaison pair. L'état du message chez le pair est inconnu et peut être mis en tampon dans la NIC cible au moment où l'accusé de réception a été généré.

Pour les points de terminaison non fiables :

Indique qu'un achèvement doit être généré lorsque l'opération a été livrée à la fabrique. Un achèvement garantit que l'opération ne dépend plus des ressources locales. L'état de l'opération au sein de la fabrique n'est pas défini.

FI_DELIVERY_COMPLETE
Indique qu'un achèvement ne doit pas être généré tant qu'une opération n'a pas été traitée par le(s) point(s) de terminaison de destination. Un achèvement garantit que le résultat de l'opération est disponible ; cependant, des étapes supplémentaires peuvent être nécessaires à la destination pour récupérer les résultats. Par exemple, une application peut avoir besoin de fournir des tampons de réception afin de récupérer les messages qui ont été mis en tampon par le fournisseur.

L'achèvement par livraison indique que le message a été traité par le pair. Si un tampon d'application était prêt à recevoir les résultats du message lorsqu'il est arrivé, alors l'achèvement par livraison indique que les données ont été placées dans le tampon de l'application.

Ce mode d'achèvement ne s'applique qu'aux points de terminaison fiables. Pour les opérations qui retournent des données à l'initiateur, comme une lecture RMA ou un fetch atomique, le point de terminaison source est également considéré comme un point de terminaison de destination. C'est le mode d'achèvement par défaut pour de telles opérations.

FI_MATCH_COMPLETE
Indique qu'un achèvement doit être généré uniquement après que l'opération a été appariée à un tampon spécifié par l'application. Les opérations utilisant cette sémantique d'achèvement dépendent de l'application à la cible qui réclame le message ou les résultats. Par conséquent, l'achèvement par correspondance peut impliquer des accusés de réception supplémentaires au niveau du fournisseur ou des délais importants. Cependant, ce modèle d'achèvement permet aux applications pairs de synchroniser leur exécution. De nombreux fournisseurs peuvent ne pas prendre en charge cette sémantique.
FI_COMMIT_COMPLETE
Indique qu'un achèvement ne doit pas être généré (localement ou chez le pair) tant que le résultat d'une opération n'a pas été rendu persistant. Un achèvement garantit que le résultat est à la fois disponible et durable, en cas de panne de courant.

Ce mode d'achèvement ne s'applique qu'aux opérations qui ciblent des régions de mémoire persistante via des points de terminaison fiables. Ce mode d'achèvement est expérimental.

FI_FENCE
Ceci n'est pas un niveau d'achèvement, mais joue un rôle dans l'ordonnancement des achèvements entre des opérations qui ne seraient normalement pas ordonnées. Une opération marquée avec le drapeau FI_FENCE et toutes les opérations soumises après l'opération clôturée sont différées jusqu'à ce que toutes les opérations précédentes ciblant le même point de terminaison pair soient terminées. De plus, l'achèvement de l'opération clôturée indique que les opérations précédentes ont atteint le même niveau d'achèvement que l'opération clôturée. Par exemple, si une opération est soumise avec FI_DELIVERY_COMPLETE | FI_FENCE, alors son achèvement indique que les opérations précédentes ont satisfait la sémantique requise pour FI_DELIVERY_COMPLETE. C'est vrai même si l'opération précédente a été soumise avec un niveau d'achèvement inférieur, comme FI_TRANSMIT_COMPLETE ou FI_INJECT_COMPLETE.

Notez qu'un achèvement généré pour une opération soumise avant l'opération clôturée ne garantit que le niveau d'achèvement initialement demandé a été atteint. C'est l'achèvement de l'opération clôturée qui garantit que les sémantiques supplémentaires ont été satisfaites.

Les sémantiques d'achèvement ci-dessus sont définies par rapport à l'initiateur de l'opération. Les différentes sémantiques sont utiles pour décrire quand l'initiateur peut réutiliser un tampon de données, et garantissent à quel état un transfert doit parvenir avant qu'un achèvement ne soit généré. Cela permet aux applications de déterminer une gestion d'erreur appropriée en cas de défaillances de communication.

SÉMANTIQUE D'ACHÈVEMENT À LA CIBLE

La sémantique d'achèvement à la cible est utilisée pour déterminer quand les données à la cible sont visibles pour l'application pair. La visibilité indique qu'une lecture mémoire à la même adresse qui était la cible d'un transfert de données retournera les résultats du transfert. La cible d'un transfert peut être identifiée par l'initiateur, comme c'est le cas pour les opérations RMA et atomiques, ou déterminée par la cible, par exemple en fournissant un tampon de réception appariant. La visibilité globale indique que les résultats sont disponibles quelle que soit l'origine de la lecture mémoire. Par exemple, la lecture peut provenir d'un processus s'exécutant sur un CPU hôte, elle peut être accessible par un transfert de données ultérieur via la fabrique, ou lue depuis un appareil pair tel qu'un GPU.

En termes de sémantique d'achèvement, la visibilité indique généralement que le transfert remplit les exigences de FI_DELIVERY_COMPLETE du point de vue de la cible. La sémantique d'achèvement à la cible peut être, mais n'est pas nécessairement, liée à la sémantique d'achèvement spécifiée par l'initiateur du transfert.

Souvent, les processus de la cible ne déclarent pas explicitement une sémantique d'achèvement souhaitée et s'appuient plutôt sur la sémantique par défaut. Le comportement par défaut est basé sur plusieurs facteurs, notamment :

•
si un événement d'achèvement est même généré à la cible
•
le type de transfert impliqué (par ex. msg vs RMA)
•
les garanties d'ordonnancement des données et des messages des points de terminaison
•
les propriétés du tampon de mémoire ciblé
•
la sémantique d'achèvement spécifiée par l'initiateur

De manière générale, les sémantiques d'achèvement à la cible sont regroupées en fonction du fait que le transfert génère ou non un événement d'achèvement à la cible. Cela inclut l'écriture d'une entrée CQ ou la mise à jour d'un compteur d'achèvement. Dans les cas d'utilisation courants, les transferts qui utilisent une interface de message (FI_MSG ou FI_TAGGED) génèrent typiquement des événements à la cible, tandis que les transferts impliquant une interface RMA (FI_RMA ou FI_ATOMIC) souvent non. Il y a des exceptions à ces deux cas, selon les liaisons point de terminaison à CQ et compteurs et les drapeaux opérationnels. Par exemple, les écritures RMA qui transportent des données CQ distantes généreront un événement d'achèvement à la cible, et sont fréquemment utilisées pour transmettre la visibilité à l'application cible. Les directives générales pour la sémantique côté cible sont décrites ci-dessous, suivies des exceptions qui modifient ce comportement.

Par défaut, les achèvements générés à la cible indiquent que les données transférées sont immédiatement disponibles pour être lues depuis le tampon de la cible. C'est-à-dire que la cible voit des sémantiques FI_DELIVERY_COMPLETE (ou meilleures), même si l'initiateur a demandé des sémantiques inférieures. Pour les applications utilisant uniquement des tampons de données alloués en mémoire hôte, c'est souvent suffisant.

Pour les operations qui ne génèrent pas un événement d'achèvement à la cible, la visibilité des données à la cible peut devoir être déduite sur la base d'opérations ultérieures qui génèrent des achèvements à la cible. En l'absence d'un achèvement à la cible, lorsqu'un achèvement d'une opération est écrit à l'initiateur, la sémantique de visibilité de l'opération à la cible s'aligne sur la sémantique d'achèvement de l'initiateur. Par exemple, si une opération RMA se termine à l'initiateur comme FI_INJECT_COMPLETE ou FI_TRANSMIT_COMPLETE, la visibilité des données à la cible n'est pas

garantie.

Un ou plusieurs des mécanismes suivants peuvent être utilisés par le processus cible pour garantir que les résultats d'un transfert de données qui n'a pas généré d'achèvement à la cible sont désormais visibles. Cette liste n'est pas exhaustive de toutes les options, mais définit les utilisations courantes. Dans les descriptions ci-dessous, le premier transfert ne résulte pas en un événement d'achèvement à la cible, mais est éventuellement suivi d'un transfert qui en génère

un.
•
Si le point de terminaison garantit l'ordre des messages entre deux transferts, l'achèvement à la cible d'un second transfert indiquera que les données du premier transfert sont disponibles. Par exemple, si le point de terminaison prend en charge l'ordre d'envoi après écriture (FI_ORDER_SAW), alors un achèvement de réception correspondant à l'envoi indiquera que les données écrites sont disponibles. Ceci est indépendant de la sémantique d'achèvement de l'initiateur pour l'écriture ou l'envoi. Lorsque l'ordre est garanti, le second transfert peut être mis en file d'attente auprès du fournisseur immédiatement après la mise en file du
premier.
•
Si le point de terminaison ne garantit pas l'ordre des messages, l'initiateur doit prendre des mesures supplémentaires pour assurer la visibilité. Si l'initiateur demande la sémantique FI_DELIVERY_COMPLETE pour la première opération, l'initiateur peut attendre que l'opération se termine localement. Une fois l'achèvement lu, l'achèvement à la cible d'un second transfert indiquera que les données du premier transfert sont
visibles.
•
Alternativement, si l'ordre des messages n'est pas garanti par le point de terminaison, l'initiateur peut utiliser les indicateurs FI_FENCE et FI_DELIVERY_COMPLETE sur
le second transfert de données pour forcer les premiers transferts à respecter la sémantique FI_DELIVERY_COMPLETE. Si le second transfert génère un achèvement à la cibl
e, cela indiquera que les données sont visibles. Sinon, un achèvement à la cible pour tout transfert après l'opération clôturée indiquera que les données sont visibles.

Les sémantiques ci-dessus s'appliquent aux transferts ciblant des tampons de mémoire hôte traditionnels. Cependant, le comportement peut différer lorsque la mémoire de dispositif et/ou la mémoire persistante est impliquée (bits de capacité FI_HMEM et FI_PMEM). Lorsque la mémoire hétérogène est impliquée, le concept de domaines de mémoire entre en jeu. Les domaines de mémoire identifient la séparation physique de la mémoire, qui peut ou non être accessible à travers le même espace d'adresses virtuelles. Voir la page de manuel fi_mr(3) pour plus de détails sur les domaines de

mémoire.

L'ordre des achèvements et la visibilité des données ne sont bien définis que pour les transferts ciblant le même domaine de mémoire. Les applications doivent être conscientes des différences d'ordre et de visibilité lorsque les transferts ciblent différents domaines de mémoire. De plus, les applications doivent également se préoccuper du domaine de mémoire dans lequel les achèvements eux-mêmes sont écrits et s'il diffère du domaine de mémoire ciblé par un transfert. Dans certaines situations, soit le fournisseur soit l'application peuvent avoir besoin d'appeler des API spécifiques au dispositif pour synchroniser ou vider les caches de mémoire du dispositif afin d'obtenir la visibilité des données

souhaitée.

Lorsque la mémoire hétérogène est utilisée, la sémantique d'achèvement à la cible par défaut pour les transferts qui génèrent un achèvement à la cible est toujours FI_DELIVERY_COMPLETE, cependant, les applications doivent être conscientes qu'il peut y avoir un impact négatif sur les performances globales pour les fournisseurs afin de satisfaire cette

exigence.

Par exemple, un processus cible peut utiliser un GPU pour accélérer des calculs. Une région de mémoire mappant à la mémoire sur le GPU peut être exposée aux pairs soit comme une cible RMA soit postée localement comme un tampon de réception. Dans ce cas, l'application est concernée par deux domaines de mémoire – système et mémoire GPU. Les achèvements sont écrits dans la mémoire

système.

En continuant l'exemple, un processus pair envoie un message étiqueté. Ce message est apparié avec le tampon de réception situé dans la mémoire GPU. La NIC copie les données du réseau dans le tampon de réception et écrit une entrée dans la file d'achèvement. Notez que les deux domaines de mémoire ont été accessibles dans le cadre de ce transfert. Les données du message ont été dirigées vers la mémoire GPU, mais l'achèvement est allé à la mémoire hôte. Comme des domaines de mémoire séparés peuvent ne pas être synchronisés les uns avec les autres, il est possible que le CPU hôte voie et traite l'entrée d'achèvement avant que le transfert vers la mémoire GPU ne soit visible soit par le GPU hôte soit même par le logiciel s'exécutant sur le GPU. Du point de vue du fournisseur, la visibilité de l'achèvement n'implique pas la visibilité des données écrites dans le domaine de mémoire du

GPU.

La sémantique d'achèvement par défaut à la cible application pour les opérations de message est FI_DELIVERY_COMPLETE. Une implémentation prévue du fournisseur dans cette situation est que le logiciel du fournisseur s'exécutant sur le CPU hôte intercepte l'entrée CQ, détecte que les données ont atterri dans la mémoire hétérogène, et effectue l'opération de synchronisation ou de vidage du dispositif nécessaire avant de rapporter l'achèvement à l'application. Cela garantit que les données sont visibles par le CPU et le logiciel GPU avant que l'application ne traite

l'achèvement.

En plus du coût du logiciel du fournisseur interceptant les achèvements et vérifiant si un transfert ciblait de la mémoire hétérogène, la synchronisation du dispositif elle-même peut impacter les performances. Par conséquent, les applications peuvent demander une sémantique d'achèvement plus basse lors de la publication de réceptions. Cela indique au fournisseur que l'application sera responsable du traitement de toute opération de vidage spécifique au dispositif qui pourrait être nécessaire. Voir fi_msg(3)

FLAGS.

Pour les transferts de données qui ne génèrent pas d'achèvement à la cible, tels que RMA ou atomiques, il est de la responsabilité de l'application de s'assurer que tous les tampons de la cible répondent aux exigences de visibilité nécessaires de l'application. Les méthodes à puces mentionnées précédemment pour notifier la cible que les données sont visibles peuvent ne pas être suffisantes, car le logiciel du fournisseur à la cible pourrait manquer du contexte nécessaire pour assurer la visibilité. Cela implique que l'application pourrait avoir besoin d'appeler directement les API de synchronisation/vidage du

dispositif.

Par exemple, une application pair pourrait effectuer plusieurs écritures RMA ciblant des tampons de mémoire GPU. Si le fournisseur décharge les opérations RMA dans la NIC, le logiciel du fournisseur à la cible ne sera pas au courant que les opérations RMA ont eu lieu. Si le pair envoie un message à l'application cible indiquant que les opérations RMA sont terminées, l'application doit s'assurer que les données RMA sont visibles par le CPU hôte ou le GPU avant d'exécuter du code qui accède aux données. L'achèvement à la cible d'avoir reçu le message envoyé n'est pas suffisant, même si l'ordre d'envoi après écriture est pris en

charge.

La plupart des sémantiques d'achèvement de la mémoire hétérogène à la cible correspondent à FI_TRANSMIT_COMPLETE ou FI_DELIVERY_COMPLETE. La mémoire persistante (capacité FI_PMEM), cependant, est souvent utilisée avec la sémantique FI_COMMIT_COMPLETE. Les concepts d'achèvement hétérogène s'appliquent

toujours.

Pour les transferts marqués par l'initiateur avec FI_COMMIT_COMPLETE, un achèvement à la cible indique que les résultats sont visibles et durables. Pour les transferts ciblant la mémoire persistante, mais utilisant une sémantique d'achèvement différente à l'initiateur, la visibilité à la cible est similaire à celle décrite ci-dessus. La durabilité n'est associée qu'aux transferts marqués avec FI_COMMIT_COMPLETE

.

NAME

fi_cq — completion queue interface

SYNOPSIS

#include <rdma/fabric.h>

ARGUMENTS

fi_cq_open(3)
ssize_t fi_cq_read(struct fi_cq_ops *ops, void *buf,
    size_t count);
ssize_t fi_cq_readfrom(struct fi_cq_ops *ops, void *buf,
    size_t count, void *addr, size_t *addrlen);
ssize_t fi_cq_readerr(struct fi_cq_ops *ops, void *buf,
    size_t count);
int fi_cq_sread(struct fi_cq_ops *ops, void *buf, size_t count,
    uint64_t delay);
int fi_cq_sreadfrom(struct fi_cq_ops *ops, void *buf, size_t count,
    void *addr, size_t *addrlen, uint64_t delay);
int fi_cq_sreaderr(struct fi_cq_ops *ops, void *buf,
    size_t count, uint64_t delay);
int fi_cq_getopt(struct fi_cq *cq, uint64_t opt, void *val);
int fi_cq_setopt(struct fi_cq *cq, uint64_t opt, void *val);
int fi_cq_close(struct fi_cq *cq);
fi_cq_bind(3)
fi_cq_control(3)
fi_cq_strerror(3)

DESCRIPTION

The libfabric completion queue (CQ) interface provides a mechanism for applications to retrieve notifications of the completion of asynchronous operations. These operations include sends, receives, data transfers, and other fabric-related events.

A completion queue is created using the fi_cq_open(3) call, and it is associated with a specific fabric domain and endpoint. The type of completion queue created (e.g., generic, event-based) is determined by the flags passed to fi_cq_open(3).

Once a CQ is created, applications can retrieve completions using the fi_cq_read, fi_cq_readfrom, and fi_cq_readerr functions. These functions allow applications to read one or more completion entries from the CQ into a provided buffer.

The fi_cq_sread, fi_cq_sreadfrom, and fi_cq_sreaderr functions provide synchronous reading capabilities, blocking until a completion is available or a specified timeout occurs.

The fi_cq_getopt and fi_cq_setopt functions allow applications to retrieve and set various options on the completion queue.

The CQ is destroyed using the fi_cq_close function.

COMPLETION FIELDS

Completion entries retrieved from a CQ typically contain the following fields:

major
The primary completion status code.
flags
Flags indicating specific completion attributes or events.
op_errno
The specific error code associated with the operation that generated the completion, if an error occurred.
user_data
User-defined data associated with the operation.
count
The number of bytes transferred or the quantity associated with the operation.
source_fid
The fabric identifier of the source of the operation (e.g., remote endpoint).
sender_id
Identifier of the sender (e.g., peer endpoint ID).
receiver_id
Identifier of the receiver (e.g., local endpoint ID).

COMPLETION FLAGS

Completion flags provide additional context about the event. Common flags include:

FI_SUCCESS
Operation completed successfully.
FI_NO_DATA
No data was transferred.
FI_MORE
More completions are available in the CQ.
FI_COMPLETION_ERROR
The operation resulted in an error.
FI_REJECTED
The operation was rejected.
FI_ABORTED
The operation was aborted.

COMPLETION EVENT SEMANTICS

Completion event semantics define how completion events are generated and delivered. Libfabric supports different semantics, configurable during CQ creation and via the fi_cq_setopt function. These semantics influence when an event is posted to the CQ and how it is reported to the application.

TARGET COMPLETION SEMANTICS

Target completion semantics refer to how the completion of an operation is signaled on the receiving side. This can involve different mechanisms, such as explicit acknowledgments or implicit signaling based on data reception.

NOTES

The specific fields and flags available in completion entries may vary depending on the underlying fabric provider and the capabilities exposed.

Error codes returned by the CQ functions are defined in rdma/fi_errno.h. The fi_cq_strerror function can be used to obtain a human-readable string representation of a Libfabric error code.

When an error occurs during an operation that generates a completion, the major field of the completion entry will indicate an error status, and the op_errno field will contain the specific error code returned with a completion.

Fabric errno values are defined in rdma/fi_errno.h.

RETURN VALUES

The functions described in this manual page return zero on success, and a negative error number on failure. The error number can be checked in the errno variable, or by using the fi_strerror(3) function.

Specific return values for each function are detailed in their respective manual pages. Common return values include:

0
Success.
-FI_ENOMSG
No completion messages are available.
-FI_EINVAL
Invalid argument provided.
-FI_EPROTO
Protocol error.
-FI_EBADF
Bad file descriptor.

fi_cq — interface de la file d'attente de complétion

#include <rdma/fabric.h>

DESCRIPTION

L'interface de file d'attente de complétion (CQ) de libfabric fournit un mécanisme permettant aux applications de recevoir des notifications de fin des opérations asynchrones. Ces opérations comprennent les envois, les réceptions, les transferts de données et d'autres événements liés au tissu.

Une file d'attente de complétion est créée à l'aide de l'appel fi_cq_open(3) et elle est associée à un domaine de tissu et à un point d'accès spécifiques. Le type de file d'attente de complétion créé (par exemple, générique, basé sur les événements) est déterminé par les indicateurs passés à fi_cq_open(3).

Une fois qu'une CQ est créée, les applications peuvent récupérer les complétions à l'aide des fonctions fi_cq_read, fi_cq_readfrom et fi_cq_readerr. Ces fonctions permettent aux applications de lire une ou plusieurs entrées de complétion à partir de la CQ dans un tampon fourni.

Les fonctions fi_cq_sread, fi_cq_sreadfrom et fi_cq_sreaderr fournissent des capacités de lecture synchrones, bloquant jusqu'à ce qu'une complétion soit disponible ou qu'un délai spécifié se produise.

Les fonctions fi_cq_getopt et fi_cq_setopt permettent aux applications de récupérer et de définir diverses options sur la file d'attente de complétion.

La CQ est détruite à l'aide de la fonction fi_cq_close.

CHAMP COMPLETION

Les entrées de complétion récupérées d'une CQ contiennent généralement les champs suivants :

major
Le code d'état de complétion principal.
flags
Indicateurs indiquant des attributs ou événements de complétion spécifiques.
op_errno
Le code d'erreur spécifique associé à l'opération qui a généré la complétion, si une erreur s'est produite.
user_data
Données définies par l'utilisateur associées à l'opération.
count
Le nombre d'octets transférés ou la quantité associée à l'opération.
source_fid
L'identifiant du tissu de la source de l'opération (par exemple, point d'accès distant).
sender_id
Identifiant de l'expéditeur (par exemple, ID de point d'accès pair).
receiver_id
Identifiant du récepteur (par exemple, ID de point d'accès local).

FLAGS COMPLETION

Les indicateurs de complétion fournissent un contexte supplémentaire sur l'événement. Les indicateurs courants comprennent :

FI_SUCCESS
Opération terminée avec succès.
FI_NO_DATA
Aucune donnée n'a été transférée.
FI_MORE
Plus de complétions sont disponibles dans la CQ.
FI_COMPLETION_ERROR
L'opération a entraîné une erreur.
FI_REJECTED
L'opération a été rejetée.
FI_ABORTED
L'opération a été abandonnée.

SEMANTIQUE EVENEMENT COMPLETION

Les sémantiques des événements de complétion définissent comment les événements de complétion sont générés et livrés. Libfabric prend en charge différentes sémantiques, configurables lors de la création de la CQ et via la fonction fi_cq_setopt. Ces sémantiques influencent le moment où un événement est posté à la CQ et comment il est rapporté à l'application.

SEMANTIQUE COMPLETION CIBLE

Les sémantiques de complétion cible font référence à la manière dont la fin d'une opération est signalée du côté récepteur. Cela peut impliquer différents mécanismes, tels que des accusés de réception explicites ou une signalisation implicite basée sur la réception des données.

NOTES

Les champs et indicateurs spécifiques disponibles dans les entrées de complétion peuvent varier en fonction du fournisseur de tissu sous-jacent et des capacités exposées.

Les codes d'erreur renvoyés par les fonctions CQ sont définis dans rdma/fi_errno.h. La fonction fi_cq_strerror peut être utilisée pour obtenir une représentation textuelle lisible par un humain d'un code d'erreur Libfabric.

Lorsqu'une erreur se produit pendant une opération qui génère une complétion, le champ major de l'entrée de complétion indiquera un état d'erreur, et le champ op_errno contiendra le code d'erreur spécifique renvoyé avec une complétion.

Les valeurs errno du tissu sont définies dans rdma/fi_errno.h.
