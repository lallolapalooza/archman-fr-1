NOM

fi_join_collective
Opération où un sous-ensemble de pairs rejoint un nouveau groupe collectif.
fi_barrier / fi_barrier2
Opération collective qui ne se termine pas tant que tous les pairs n'ont pas entré dans l'appel de barrière.
fi_broadcast
Un seul émetteur transmet des données à tous les pairs, y compris lui-même.
fi_alltoall
Chaque pair distribue une tranche de ses données locales à tous les pairs.
fi_allreduce
Opération collective où tous les pairs diffusent une opération atomique à tous les autres pairs.
fi_allgather
Chaque pair envoie une copie complète de ses données locales à tous les pairs.
fi_reduce_scatter
Appel collectif où les données sont collectées depuis tous les pairs et fusionnées (réduites). Les résultats de la réduction sont redistribués aux pairs, chaque pair recevant une tranche des résultats.
fi_reduce
Appel collectif où les données sont collectées depuis tous les pairs vers un pair racine et fusionnées (réduites).
fi_scatter
Un seul émetteur distribue (disperse) une tranche de ses données locales à tous les pairs.
fi_gather
Tous les pairs envoient leurs données à un pair racine.
fi_query_collective
Renvoie des informations sur les opérations collectives prises en charge par un fournisseur et sur les limitations de l'opération collective.

DESCRIPTION

En général, les opérations collectives peuvent être considérées comme des opérations atomiques coordonnées entre un ensemble de points de terminaison pairs. Les lecteurs doivent se référer à la page man fi_atomic(3) pour les détails sur les opérations atomiques et les types de données définis par libfabric.

Une opération collective est un échange de communication de groupe. Elle implique plusieurs pairs échangeant des données avec d'autres pairs participant à l'appel collectif. Les opérations collectives nécessitent une étroite coordination par tous les membres participants. Tous les participants doivent invoquer le même appel collectif avant qu'un seul membre puisse terminer son opération localement. En conséquence, les appels collectifs peuvent solliciter le fabric ainsi que les tampons de données locaux et distants.

Les interfaces collectives de libfabric ciblent les fabrics qui prennent en charge le déchargement d'une partie de la communication collective vers les commutateurs réseau, les NIC et d'autres périphériques. Cependant, aucune exigence d'implémentation n'est imposée au fournisseur.

La première étape pour utiliser un appel collectif consiste à identifier les points de terminaison pairs qui y participeront. L'appartenance au collectif suit l'un des deux modèles, tous deux pris en charge par libfabric. Dans le premier modèle, l'application gère l'appartenance. Cela signifie généralement que l'application effectue elle-même une opération collective en utilisant la communication point à point pour identifier les membres qui participeront. De plus, l'application peut interagir avec un gestionnaire de ressources de fabric pour réserver les ressources réseau nécessaires à l'exécution des opérations collectives. Dans ce modèle, l'application informera libfabric que l'appartenance a déjà été établie.

Un modèle séparé déplace la gestion de l'appartenance sous libfabric et directement dans le fournisseur. Dans ce modèle, l'application doit identifier quelles adresses pairs seront membres. Ces informations sont transmises au fournisseur libfabric, qui est alors responsable de coordonner la création du groupe collectif. Dans le modèle géré par le fournisseur, le fournisseur effectuera généralement l'opération collective nécessaire pour établir le groupe de communication et interagira avec tout agent de gestion de fabric.

Dans les deux modèles, l'appartenance au collectif est communiquée au fournisseur en créant et configurant un ensemble de vecteurs d'adresses (AV set). Un AV set représente un sous-ensemble ordonné d'adresses dans un vecteur d'adresses (AV). Les détails sur la création et la configuration d'un AV set sont disponibles dans fi_av_set(3).

Une fois qu'un AV set a été programmé avec les informations d'appartenance au collectif, un point de terminaison est joint à l'ensemble. Cela utilise l'opération fi_join_collective et fonctionne de manière asynchrone. Cela diffère de la manière dont un point de terminaison est associé de manière synchrone avec un AV utilisant l'appel fi_ep_bind(). Une fois l'opération fi_join_collective terminée, un fi_addr est fourni et utilisé comme adresse cible lors de l'invocation d'une opération collective.

Pour la commodité des développeurs, un ensemble d'API collectives est défini. Les API collectives diffèrent des interfaces de messagerie et RMA en ce sens que le format des données est connu du fournisseur, et que la collective peut effectuer une opération sur ces données. Cela rapproche les opérations collectives des interfaces atomiques.

Rejoindre la Collective (fi_join_collective)

Cet appel attache un point de terminaison à un groupe de membres collectifs. Libfabric traite les membres collectifs comme un groupe de multidiffusion, et l'appel fi_join_collective attache le point de terminaison à ce groupe de multidiffusion. Par défaut, le point de terminaison rejoindra le groupe en fonction des capacités de transfert de données du point de terminaison. Par exemple, si le point de terminaison a été configuré pour envoyer et recevoir des données, alors le point de terminaison pourra initier et recevoir des transferts vers et depuis la collective. Les indicateurs d'entrée peuvent être utilisés pour restreindre l'accès au groupe collectif, sous réserve des limitations des capacités du point de terminaison.

Les opérations de rejoindre la collective s'achèvent de manière asynchrone et peuvent impliquer des transferts de tissu, en fonction de l'implémentation du fournisseur. Un point de terminaison doit être lié à une file d'événements avant d'appeler fi_join_collective. Le résultat de l'opération de rejoindre sera signalé à l'EQ comme un événement FI_JOIN_COMPLETE. Les applications ne peuvent pas émettre de transferts collectifs tant qu'elles n'ont pas reçu la notification que l'opération de rejoindre est terminée. Notez qu'un point de terminaison peut commencer à recevoir des messages du groupe collectif dès que l'opération de rejoindre est terminée, ce qui peut se produire avant que l'événement FI_JOIN_COMPLETE ne soit généré.

L'opération de rejoindre la collective est elle-même une opération collective. Tous les pairs participants doivent appeler fi_join_collective avant qu'un pair individuel ne signale que l'opération de rejoindre est terminée. Les adhésions collectives gérées par l'application font exception. Avec les adhésions gérées par l'application, l'appel fi_join_collective peut être terminé localement sans communication par tissu. Pour les adhésions gérées par le fournisseur, l'appel de rejoindre la collective nécessite en entrée un coll_addr qui fait référence à une adresse associée à un ensemble AV (voir fi_av_set_addr) ou à un groupe collectif existant (obtenu par un appel précédent à fi_join_collective). L'appel fi_join_collective créera un nouveau sous-groupe collectif. Si les adhésions gérées par l'application sont utilisées, coll_addr doit être défini sur FI_ADDR_UNAVAIL.

Les applications doivent appeler fi_close sur le groupe collectif pour déconnecter le point de terminaison du groupe. Après la fin d'une opération de rejoindre, l'appel fi_mc_addr peut être utilisé pour récupérer l'adresse associée au groupe de multidiffusion. Voir fi_cm(3) pour plus de détails sur fi_mc_addr().

Barrière (fi_barrier)

L'opération fi_barrier fournit un mécanisme pour synchroniser les pairs. La barrière ne entraîne aucun transfert de données au niveau de l'application. Une barrière ne se termine pas localement tant que tous les pairs n'ont pas invoqué l'appel de barrière. Cela signifie pour l'application locale que le travail des pairs qui s'est terminé avant qu'ils n'appellent la barrière est terminé.

Barrière (fi_barrier2)

L'opération fi_barrier2 est identique à fi_barrier, mais avec un paramètre supplémentaire pour passer des indicateurs d'opération.

Diffusion (fi_broadcast)

fi_broadcast transfère un tableau de données d'un seul expéditeur à tous les autres membres du groupe collectif. Le paramètre buf d'entrée est traité comme le tampon de transmission si le rang local est la racine, sinon c'est le tampon de réception. L'opération de diffusion agit comme une écriture ou une lecture atomique d'un tableau de données. Par conséquent, le format des données dans buf est spécifié par le paramètre datatype. Tout type de données non void peut être diffusé.

Tout vers Tous (fi_alltoall)

La collective fi_alltoall implique la distribution (ou la dispersion) de différentes portions d'un tableau de données aux pairs. Cela s'explique mieux à l'aide d'un exemple. Ici, trois pairs effectuent une collective tout vers tous pour échanger différentes entrées dans un tableau d'entiers.

[1]   [2]   [3]
[5]   [6]   [7]
[9]  [10]  [11]
   \   |   /
   All to all
   /   |   \
[1]   [5]   [9]
[2]   [6]  [10]
[3]   [7]  [11]

Chaque pair envoie une partie de ses données aux autres pairs.

Les opérations tout vers tous peuvent être effectuées sur tout type de données non void. Cependant, tout vers tous n'effectue pas d'opération sur les données elles-mêmes, donc aucune opération n'est spécifiée.

Tout Réduire (fi_allreduce)

fi_allreduce peut être décrit comme tous les pairs fournissant une entrée dans une opération atomique, avec le résultat copié dans chaque pair. Conceptuellement, cela peut être considéré comme chaque pair émettant une opération atomique de multidiffusion à tous les autres pairs, récupérant les résultats et les combinant. La combinaison des résultats est appelée la réduction. L'opération fi_allreduce() prend en entrée un tableau de données et l'opération atomique spécifiée à effectuer. Les résultats de la réduction sont écrits dans le tampon de résultat.

Tout type de données non void peut être spécifié. Les opérations atomiques valides sont listées ci-dessous dans l'appel fi_query_collective. Le diagramme suivant montre un exemple d'opération tout réduire impliquant la somme d'un tableau d'entiers entre trois pairs.

      sum

Tout rassembler peut être effectué sur tout type de données non void. Cependant, tout rassembler n'effectue pas d'opération sur les données elles-mêmes, donc aucune opération n'est spécifiée.

Réduire-Disperser (fi_reduce_scatter)

La collective fi_reduce_scatter est similaire à une opération fi_allreduce, suivie de tout vers tous. Avec reduce scatter, tous les pairs fournissent une entrée dans une opération atomique, similaire à all reduce. Cependant, au lieu que le résultat complet soit copié dans chaque pair, chaque participant ne reçoit qu'une tranche du résultat.

Ceci est montré par l'exemple suivant :

[1]  [1]  [1]
[5]  [5]  [5]
[9]  [9]  [9]
  \   |   /
     sum (reduce)
      |
     [3]
    [15]
    [27]
      |
   scatter
  /   |   \
[3] [15] [27]

L'appel reduce scatter prend en charge le même type de données et la même opération atomique que fi_allreduce.

La collective fi_reduce est la première moitié d'une opération fi_allreduce. Avec reduce, tous les pairs fournissent une entrée dans une opération atomique, avec les résultats collectés par un seul point de terminaison `root'.

Disperser (fi_scatter)

La collective fi_scatter est la seconde moitié d'une opération fi_reduce_scatter. Les données d'un seul point de terminaison `root' sont divisées et distribuées à tous les pairs.

Ceci est montré par l'exemple suivant :

L'opération scatter est utilisée pour distribuer les résultats aux pairs. Aucune opération atomique n'est effectuée sur les données.

L'opération fi_gather est utilisée pour collecter (rassembler) les résultats de tous les pairs et les stocker sur un pair `root'.

Interroger les Attributs Collectifs (fi_query_collective)

L'appel fi_query_collective signale quelles opérations collectives sont prises en charge par le fournisseur sous-jacent, pour les points de terminaison correctement configurés. Les opérations collectives nécessaires à une application qui ne sont pas prises en charge par le fournisseur doivent être implémentées par l'application. L'appel de requête vérifie si un fournisseur prend en charge une opération collective spécifique pour un type de données et une opération donnés, le cas échéant.

Le nom de la collective, ainsi que le type de données et l'opération associée, le cas échéant, sont fournis en entrée dans fi_query_collective.

NOM

fi_allreduce, fi_collective — Collective operations

SYNTAXIS

#include <libfabric/fabric.h>

ssize_t fi_allreduce(
    fi_addr_t group,
    void *buf,
    size_t len,
    enum fi_datatype datatype,
    enum fi_op op,
    uint64_t flags);

ssize_t fi_collective(
    struct fid_ep *ep,
    const void *in,
    void *out,
    size_t len,
    enum fi_datatype datatype,
    enum fi_op op,
    uint64_t flags);

struct fi_collective_attr;

ARGUMENTS

group
The group address of the collective operation. This can be a unicast, multicast, or global address.
buf
The buffer used for the collective operation. The buffer is used for both input and output for collective operations that combine data (e.g. fi_allreduce).
len
The length of the data to be transferred. This length is in units of the specified datatype.
datatype
The datatype of the data involved in the collective operation. This should be set to one of the values defined for enum fi_datatype. See fi_atomic(3) for a list of supported datatypes.
op
The atomic operation to perform. This should be set to one of the values defined for enum fi_op. See fi_atomic(3) for a list of supported operations.
flags
Flags that control the behavior of the collective operation. See FLAGS below.
ep
The endpoint to use for the collective operation.
in
The input buffer for the collective operation. This parameter is used for collective operations that separate input and output buffers.
out
The output buffer for the collective operation. This parameter is used for collective operations that separate input and output buffers.

DESCRIPTION

Collective operations provide a mechanism for performing operations across a group of endpoints. These operations are typically used in parallel computing environments for tasks such as data distribution, reduction, and synchronization.

The fi_allreduce function performs a reduction operation across a group of endpoints. It takes input data from each participating endpoint, performs a specified reduction operation on the data, and then distributes the result to all participating endpoints. The result is stored in the buf argument.

The fi_collective function is a more general interface for collective operations. It allows for separate input and output buffers, and supports a wider range of collective operations beyond just reduction. The specific collective operation performed is determined by the op and flags arguments.

Collective operations are built on top of atomic operations. The semantics and behavior of collective operations are closely related to those of atomic operations. For details on supported datatypes and operations, refer to the fi_atomic(3) man page.

The fi_query_collective function can be used to query the supported collective operations and their attributes. The following structure is used to describe the attributes of a collective operation:

struct fi_collective_attr {
    enum fi_op op;
    enum fi_datatype datatype;
    struct fi_atomic_attr datatype_attr;
    size_t max_members;
      uint64_t mode;
};

For a description of struct fi_atomic_attr, see fi_atomic(3).

op
En entrée, spécifie l'opération atomique impliquée dans l'appel collectif. Ceci doit être défini à l'une des valeurs suivantes : FI_MIN, FI_MAX, FI_SUM, FI_PROD, FI_LOR, FI_LAND, FI_BOR, FI_BAND, FI_LXOR, FI_BXOR, FI_ATOMIC_READ, FI_ATOMIC_WRITE, ou FI_NOOP. Pour les collectifs qui n'échangent pas de données applicatives (fi_barrier), ceci doit être défini à FI_NOOP.
datatype
En entrée, spécifie le type de données des données modifiées par le collectif. Ceci doit être défini à l'une des valeurs suivantes : FI_INT8, FI_UINT8, FI_INT16, FI_UINT16, FI_INT32, FI_UINT32, FI_INT64, FI_UINT64, FI_FLOAT, FI_DOUBLE, FI_FLOAT_COMPLEX, FI_DOUBLE_COMPLEX, FI_LONG_DOUBLE, FI_LONG_DOUBLE_COMPLEX, ou FI_VOID. Pour les collectifs qui n'échangent pas de données applicatives (fi_barrier), ceci doit être défini à FI_VOID.
datatype_attr.count
Le nombre maximum d'éléments pouvant être utilisés avec le collectif.
datatype_attr.size
La taille du type de données tel que supporté par le fournisseur. Les applications doivent valider la taille des types de données qui diffèrent en fonction de la plateforme, comme FI_LONG_DOUBLE.
max_members
Le nombre maximum de pairs pouvant participer à une opération collective.
mode
Ce champ est réservé et doit être 0.

Si une opération collective est supportée, l'appel de requête retournera FI_SUCCESS, ainsi que les attributs sur les limites d'utilisation de cette opération collective via le fournisseur.

Achèvements

Les opérations collectives sont mappées aux opérations atomiques sous-jacentes. Pour une discussion sur la sémantique d'achèvement atomique, voir fi_atomic(3). L'achèvement, l'ordonnancement et l'atomicité des opérations collectives correspondent à ceux définis pour les opérations atomiques point à point.

FLAGS

Les drapeaux suivants sont définis pour les opérations spécifiées.

FI_SCATTER
S'applique à fi_query_collective. Lorsqu'il est défini, demande des informations sur les attributs de l'opération collective reduce-scatter.

VALEUR DE RETOUR

Retourne 0 en cas de succès. En cas d'erreur, une valeur négative correspondant à l'errno de fabric est retournée. Les valeurs d'errno de fabric sont définies dans <rdma/fi_errno.h>.

ERREURS

-FI_EAGAIN
Voir fi_msg(3) pour une description détaillée de la gestion de FI_EAGAIN.
-FI_EOPNOTSUPP
L'opération atomique demandée n'est pas supportée sur ce point de terminaison.
-FI_EMSGSIZE
Le nombre d'opérations collectives dans une seule requête dépasse ce qui est supporté par le fournisseur sous-jacent.

NOTES

Les opérations collectives sont mappées aux opérations atomiques. À ce titre, elles suivent la plupart des conventions et restrictions des opérations atomiques pair à pair. Cela inclut l'atomicité des données, l'alignement des données et la sémantique d'ordonnancement des messages. Voir fi_atomic(3) pour des informations supplémentaires sur les types de données et les opérations définies pour les opérations atomiques et collectives.
