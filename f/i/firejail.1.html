DESCRIPTIO

N

Firejail est un programme bac à sable SUID qui réduit le risque de failles de sécurité en restreignant l'environnement d'exécution des applications non fiables à l'aide des espaces de noms Linux, de seccomp-bpf et des capacités Linux. Il permet à un processus et à tous ses descendants d'avoir leur propre vue privée des ressources du noyau partagées globalement, telles que la pile réseau, la table des processus et la table de montage. Firejail peut fonctionner dans un environnement SELinux ou AppArmor, et il est intégré aux groupes de contrôle Linux (Control Groups)

.

Écrit en C avec pratiquement aucune dépendance, le logiciel s'exécute sur n'importe quel ordinateur Linux avec un noyau version 3.x ou plus récent. Il peut mettre en bac à sable tout type de processus : serveurs, applications graphiques et même les sessions de connexion

utilisateur.

Firejail permet à l'utilisateur de gérer la sécurité des applications à l'aide de profils de sécurité. Chaque profil définit un ensemble de permissions pour une application ou un groupe d'applications spécifique. Le logiciel inclut des profils de sécurité pour plusieurs programmes Linux plus courants, tels que Mozilla Firefox, Chromium, VLC, Transmission,

etc.

Firejail est actuellement implémenté en tant que binaire SUID, ce qui signifie que si un compte utilisateur malveillant ou compromis parvient à exploiter un bug dans Firejail, cela pourrait en fin de compte mener à une élévation de privilèges vers root. Pour atténuer ce risque, il est recommandé de n'autoriser que des utilisateurs de confiance à exécuter firejail (voir firejail-users(5) pour des détails sur la façon d'y parvenir). Pour plus de détails sur les compromis entre sécurité et utilisabilité de Firejail, voir : #4601

.

Les technologies de bac à sable alternatives comme Snap (voir https://snapcraft.io) et Flatpak (voir https://flatpak.org) ne sont pas prises en charge. Les paquets Snap et Flatpak ont leurs propres out

ils de gestion natifs et ne fonctionneront pas l

UTILISATI

ON

Sans aucune option, la bac à sable se compose d'un système de fichiers construit dans un nouvel espace de noms de montage, et de nouveaux espaces de noms PID et UTS. Les espaces de noms IPC, réseau et utilisateur peuvent être ajoutés à l'aide des options de ligne de commande. Le système de fichiers par défaut de Firejail est basé sur le système de fichiers de l'hôte, avec les répertoires système principaux montés en lecture seule. Ces répertoires sont /etc, /var, /usr, /bin, /sbin, /lib, /lib32, /libx32 et /lib64. Seuls /home et /tmp sont

inscriptibles.

Au démarrage, Firejail cherche d'abord un profil dans ~/.config/firejail/ et s'il n'en trouve pas, il cherche dans /etc/firejail/. Pour plus de détails sur la résolution des profils, voir https://github.com/netblue30/firejail/wiki/Creating-Profiles#locations-and-types. Si un profil approprié n'est pas trouvé, Firejail utilisera un profil par défaut. Le profil par défaut est plutôt restrictif. Si l'application ne fonctionne pas, utilisez l'option --noprofile pour le désactiver. Pour plus d'informations, voir la section PROFILS DE SÉCURITÉ

ci-dessous.

Si aucun argument de programme n'est spécifié, Firejail lance le shell préféré de l'utilisateur. Exemples

--ip=dhcp
Acquiert une adresse IP et une passerelle par défaut pour la dernière interface définie par une option --net, ainsi que configure les serveurs DNS en fonction de la réponse DHCP. Cette option nécessite que le client DHCP ISC dhclient soit installé et le démarrera automatiquement dans le bac à sable.

Exemple :
$ firejail --net=br0 --ip=dhcp

Cette option ne doit pas être utilisée conjointement avec l'option --dns si le serveur DHCP est configuré pour attribuer des serveurs DNS aux clients, car les serveurs DNS spécifiés manuellement seront écrasés.

Le client DHCP ne libérera PAS le bail DHCP à la fin du bac à sable. Si votre serveur DHCP nécessite que les baux soient explicitement libérés, envisagez d'exécuter un client DHCP et de libérer le bail manuellement en conjonction avec l'option --net=none.

--ip=none
Aucune adresse IP et aucune passerelle par défaut ne sont configurées pour la dernière interface définie par une option --net. Utilisez cette option si vous avez l'intention de démarrer un client DHCP externe dans le bac à sable.

Exemple :
$ firejail --net=eth0 --ip=none

Si l'interface correspondante n'a pas d'adresse IP configurée, cette option est activée par défaut.

--join=nom|pid
Rejoint le bac à sable identifié par nom ou par PID. Par défaut, un shell /bin/bash est démarré après avoir rejoint le bac à sable. Si un programme est spécifié, le programme est exécuté dans le bac à sable. Si la commande --join est émise par un utilisateur normal, tous les filtres de sécurité sont configurés pour le nouveau processus comme ils le sont dans le bac à sable. Si la commande --join est émise par root, les filtres de sécurité et les configurations de CPU ne sont pas appliqués au processus rejoignant le bac à sable.

Exemple :
$ firejail --name=mygame --caps.drop=all warzone2100 &
$ firejail --join=mygame

$ firejail --join=3272

Dans le contexte de firejail, répertoire supérieur signifie, si le chemin du fichier en liste blanche est par exemple /etc/somedir/somefile, alors le répertoire supérieur serait /etc. Tous les autres répertoires supérieurs comme /opt, /usr et ainsi de suite, n'ont pas changé, donc tous les fichiers qui y sont sont toujours accessibles, à moins qu'un fichier ou répertoire à l'intérieur de ceux-ci soit également en liste blanche. Avertissement : le support de Landlock dans firejail est considéré comme expérimental et instable. Le contenu de landlock-common.inc est susceptible de changer et la fonctionnalité est encore en cours d'expansion dans le noyau Linux. De plus, notez que sa fonctionnalité chevauche les fonctionnalités existantes de firejail, telles que les commandes blacklist, read-only et read-write. Ses règles d'accès au système de fichiers ne peuvent actuellement restreindre que l'accès direct aux chemins ; elle ne peut pas faire apparaître uniquement des chemins sélectionnés dans la sandbox comme le font les commandes whitelist et private-etc (voir aussi unveil(2) sur OpenBSD). Enfin, notez que selon la version du noyau Linux, Landlock peut ne pas protéger tous les appels système pertinents (voir la documentation de Landlock du noyau pour plus de détails). Par conséquent, il est recommandé de considérer Landlock comme une couche de protection supplémentaire, à utiliser avec d'autres fonctionnalités de firejail (plutôt que comme un mécanisme infaillible à lui seul)

.

Landlock est un module de sécurité Linux introduit pour la première fois dans la version 5.13 du noyau Linux. Il permet aux processus non privilégiés de restreindre leur accès au système de fichiers. Une fois imposées, ces restrictions ne peuvent jamais être supprimées, et tous les processus enfants créés par des processus restreints par Landlock héritent de ces restrictions. Firejail prend en charge Landlock comme fonctionnalité de sandbox supplémentaire. Elle peut être utilisée pour garantir qu'une application en sandbox ne peut accéder qu'aux fichiers et répertoires auxquels elle a été explicitement autorisée à accéder. Firejail prend en charge le remplissage de l'ensemble de règles à la fois avec un ensemble de règles de base (voir landlock-common.inc) et avec un ensemble de règles

personnalisé.
Notes importantes
:
- Actuellement, seule la version 1 de l'ABI Landlock est prise en charge.

- Si "lsm=" est utilisé dans la ligne de commande du noyau, il doit contenir "landlock" (comme "lsm=apparmor,landlock"), sinon il sera

désactivé.

- Un processus ne peut installer un ensemble de règles Landlock que s'il dispose soit de CAP_SYS_ADMIN dans son ensemble de capacités effectives, soit de la restriction "No New Privileges" activée. En raison de cela, l'activation de la fonctionnalité Landlock fera aussi que Firejail activera la restriction "No New Privileges", quel que soit le profil ou l'option --nonewprivs de la ligne de

commande.

PROFILES

Several command line options can be passed to the program using profile files. Firejail chooses the profile file as

follows:

1. If a profile file is provided by the user with --profile=FILE option, the profile FILE is loaded. If a profile name is given, it is searched for first in the ~/.config/firejail directory and if not found then in /etc/firejail directory. Profile names do not include the .profile suffix. If there is a file with the same name as the given profile name, it will be used instead of doing the profile search. To force a profile search, prefix the profile name with a colon (:), eg. --profile=:PROFILE_NAME.

Example:
$ firejail --profile=/home/netblue/icecat.profile icecat
Reading profile /home/netblue/icecat.profile
[...
]
$ firejail --profile=icecat icecat-wrapper.sh
Reading profile /etc/firejail/icecat.profile
[...
]

2. If a profile file with the same name as the application is present in ~/.config/firejail directory or in /etc/firejail, the profile is loaded. ~/.config/firejail takes precedence over /etc/firejail.

Example:
$ firejail icecat
Command name #icecat#
Found icecat profile in /home/netblue/.config/firejail directory
Reading profile /home/netblue/.config/firejail/icecat.profile
[...
]

3. Use default.profile file if the sandbox is started by a regular user, or server.profile file if the sandbox is started by root. Firejail looks for these files in ~/.config/firejail directory, followed by /etc/firejail directory. To disable default profile loading, use --noprofile command option.

Example:
