fileevent(n) Commandes intégrées de Tcl fileevent(n)

NOM

fileevent - Exécuter un script lorsqu'un canal devient lisible ou inscriptible

SYNOPSIS

fileevent channelId readable ?script?

fileevent channelId writable ?script?

DESCRIPTION

Cette commande est utilisée pour créer des gestionnaires d'événements de fichier. Un gestionnaire d'événements de fichier est une liaison entre un canal et un script, de sorte que le script est évalué chaque fois que le canal devient lisible ou inscriptible. Les gestionnaires d'événements de fichier sont le plus souvent utilisés pour permettre la réception de données d'un autre processus sur une base pilotée par les événements, afin que le récepteur puisse continuer à interagir avec l'utilisateur tout en attendant que les données arrivent. Si une application invoque gets ou read sur un canal bloquant alors qu'aucune donnée d'entrée n'est disponible, le processus se bloquera ; jusqu'à ce que les données d'entrée arrivent, il ne pourra pas traiter d'autres événements, il semblera donc à l'utilisateur qu'il « fige ». Avec fileevent, le processus peut savoir quand des données sont présentes et n'invoquer gets ou read que lorsqu'ils ne bloqueront pas.

L'argument channelId de fileevent fait référence à un canal ouvert tel qu'un canal standard Tcl (stdin, stdout, ou stderr), la valeur de retour d'une invocation de open ou socket, ou le résultat d'une commande de création de canal fournie par une extension Tcl.

Si l'argument script est spécifié, alors fileevent crée un nouveau gestionnaire d'événements : script sera évalué chaque fois que le canal devient lisible ou inscriptible (selon le deuxième argument de fileevent). Dans ce cas, fileevent renvoie une chaîne vide. Les gestionnaires d'événements readable et writable d'un fichier sont indépendants et peuvent être créés et supprimés séparément. Cependant, il peut y avoir au plus un gestionnaire readable et un gestionnaire writable pour un fichier à un instant donné dans un interpréteur donné. Si fileevent est appelé lorsque le gestionnaire spécifié existe déjà dans l'interpréteur appelant, le nouveau script remplace l'ancien.

Si l'argument script n'est pas spécifié, fileevent renvoie le script actuel pour channelId, ou une chaîne vide s'il n'y en a pas. Si l'argument script est spécifié comme une chaîne vide, le gestionnaire d'événements est supprimé, de sorte qu'aucun script ne sera invoqué. Un gestionnaire d'événements de fichier est également supprimé automatiquement chaque fois que son canal est fermé ou que son interpréteur est supprimé.

Un canal est considéré comme lisible s'il y a des données non lues disponibles sur le périphérique sous-jacent. Un canal est également considéré comme lisible s'il y a des données non lues dans un tampon d'entrée, sauf dans le cas particulier où la tentative la plus récente de lecture depuis le canal était un appel gets qui n'a pas pu trouver une ligne complète dans le tampon d'entrée. Cette fonctionnalité permet de lire un fichier ligne par ligne en mode non bloquant à l'aide des événements. Un canal est également considéré comme lisible si une condition de fin de fichier ou d'erreur est présente sur le fichier ou le périphérique sous-jacent. Il est important pour script de vérifier ces conditions et de les traiter de manière appropriée ; par exemple, s'il n'y a pas de vérification particulière pour la fin de fichier, une boucle infinie peut survenir où script ne lit aucune donnée, se termine, et est immédiatement invoqué à nouveau.

Un canal est considéré comme inscriptible si au moins un octet de données peut être écrit sur le fichier ou le périphérique sous-jacent sans bloquer, ou si une condition d'erreur est présente sur le fichier ou le périphérique sous-jacent.

L'E/S pilotée par les événements fonctionne le mieux pour les canaux qui ont été placés en mode non bloquant avec la commande fconfigure . En mode bloquant, une commande puts peut bloquer si vous lui donnez plus de données que le fichier ou le périphérique sous-jacent ne peut en accepter, et une commande gets ou read bloquera si vous essayez de lire plus de données que ce qui est prêt ; un fichier ou un périphérique sous-jacent lisible peut même ne pas garantir qu'une lecture bloquante [read 1] réussira (les contre-exemples étant les encodages multi-octets, les transformations de compression ou de chiffrement). Dans tous ces cas, aucun événement ne sera traité pendant que les commandes bloquent.

En mode non bloquant, puts, read, et gets ne bloquent jamais. Voir la documentation des commandes individuelles pour savoir comment elles gèrent les canaux bloquants et non bloquants.

Le test de la condition de fin de fichier doit être effectué après toute tentative de lecture des données du canal. Le drapeau eof est défini une fois qu'une tentative de lecture de la fin des données s'est produite, et un test avant cette lecture nécessitera qu'un événement supplémentaire soit déclenché.

Le script d'un événement de fichier est exécuté au niveau global (hors du contexte de toute procédure Tcl) dans l'interpréteur où la commande fileevent a été invoquée. Si une erreur se produit lors de l'exécution du script, la commande enregistrée avec interp bgerror est utilisée pour signaler l'erreur. De plus, le gestionnaire d'événements de fichier est supprimé s'il renvoie une erreur ; cela est fait afin de prévenir les boucles infinies dues à des gestionnaires défectueux.

EXEMPLE

Dans cette configuration, GetData sera appelé avec le canal comme argument chaque fois que $chan devient lisible. L'appel read lira les données binaires actuellement disponibles sans bloquer. Ici, le fileevent du canal est supprimé lorsqu'une fin de fichier se produit pour éviter d'être appelé en continu (voir ci-dessus). Alternativement, le canal peut être fermé dans cette condition.

proc GetData {chan} {
    set data [read $chan]
    puts "[string length $data] $data"
    if {[eof $chan]} {
        fileevent $chan readable {}
    }
}
fconfigure $chan -blocking 0 -translation binary
fileevent $chan readable [list GetData $chan]

L'exemple suivant démontre l'utilisation de gets pour lire des données orientées ligne.

proc GetData {chan} {
    if {[gets $chan line] >= 0} {
        puts $line
    }
    if {[eof $chan]} {
        close $chan
    }
}
fconfigure $chan -blocking 0 -buffering line -translation crlf
fileevent $chan readable [list GetData $chan]
