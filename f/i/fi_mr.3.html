DESCRIPTIO

N

Les régions mémoire enregistrées associent des tampons mémoire aux permissions accordées pour l'accès par les ressources fabric. Un tampon mémoire doit être enregistré auprès d'un domaine de ressources avant de pouvoir être utilisé comme cible d'un transfert de données RMA ou atomique distant. De plus, un fournisseur fabric peut exiger que les tampons de données soient enregistrés avant d'être utilisés dans des transferts locaux. Les restrictions d'enregistrement mémoire sont contrôlées à l'aide d'un ensemble distinct de bits de mode, spécifié à travers les attributs du domaine (champ mr_mode). Chaque bit mr_mode exige que l'application prenne des mesures spécifiques afin d'utiliser les tampons mémoire avec les interfaces

libfabric.

Dans un cas particulier, une nouvelle région mémoire peut être créée à partir d'une région mémoire existante. Une telle nouvelle région mémoire est appelée un sous-MR, et la région mémoire existante est appelée le MR de base. Les sous-MR peuvent être utilisés pour partager des ressources matérielles, telles que les traductions d'adresses virtuelles vers physiques et l'épinglage de pages. Cela peut améliorer les performances lors de la création et de la destruction de sous-régions nécessitant différents droits d'accès. Le MR de base lui-même peut aussi être un sous-MR, permettant une hiérarchie de régions

mémoire.

Ce qui suit s'applique à l'enregistrement

mémoire.
Enregistrement mémoire par
défaut
Si aucun bit mr_mode n'est défini, les comportements par défaut décrits ci-dessous sont suivis. Historiquement, c
es valeurs par défaut étaient collectivement appelées enregistrement mémoire évolutif. Les exigences par défaut s
ont décrites ci-dessous, suivies des définitions de la manière dont chaque bit mr_mode modifie la définition.

Compatibilité : Pour les versions 1.4 et antérieures de la bibliothèque, cela était indiqué en définissant mr_mode à FI_MR_SCALABLE et le bit de mode fi_info FI_LOCAL_MR à 0. FI_MR_SCALABLE et FI_LOCAL_MR ont été dépréciés dans la version 1.5 de libfabric, bien qu'ils soient pris en charge à des fins de compatibilité

ascendante.

Pour des raisons de sécurité, l'enregistrement mémoire est requis pour les tampons de données qui sont accédés directement par un processus pair. Par exemple, l'enregistrement est requis pour les tampons cibles RMA (lus ou écrits), et ceux accédés par des opérations atomiques ou

collectives.

Par défaut, l'enregistrement se produit sur des plages d'adresses virtuelles. Comme l'enregistrement fait référence à des plages d'adresses, plutôt qu'à des tampons de données alloués, les plages d'adresses n'ont pas besoin de correspondre à des tampons de données alloués par l'application au moment où l'appel d'enregistrement est effectué. C'est-à-dire qu'une application peut enregistrer n'importe quelle plage d'adresses dans son espace d'adresses virtuelles, que ces adresses soient ou non soutenues par des pages physiques ou aient été

allouées.

Notez que des pages physiques doivent soutenir les adresses avant que les adresses ne soient accédées dans le cadre d'une opération de transfert de données, sinon les transferts de données échoueront. De plus, selon l'opération, cela pourrait entraîner la réception d'une faute de segmentation par le processus local pour avoir accédé à une mémoire

invalide.

Une fois enregistrées, les régions mémoire résultantes sont accessibles par les pairs à partir d'une adresse de base de 0. C'est-à-dire que l'adresse cible qui est spécifiée est un décalage en octets dans la région

enregistrée.

L'application sélectionne également la clé d'accès associée au MR. La taille de la clé est limitée à un maximum de 8

octets.

Avec l'enregistrement évolutif, les tampons de données accédés localement ne sont pas enregistrés. Cela inclut les tampons source pour toutes les opérations de transmission – envois, envois étiquetés, RMA et opérations atomiques – ainsi que les tampons publiés pour les opérations de réception et de réception

étiquetée.

Bien que le comportement d'enregistrement mémoire par défaut soit pratique pour les développeurs d'applications, il est difficile à implémenter dans le matériel. Les tentatives de masquer les exigences matérielles à l'application entraînent souvent des impacts significatifs et inacceptables sur les performances. Les bits mr_mode suivants sont fournis en entrée à fi_getinfo. Si un fournisseur exige le comportement défini pour un bit mr_mode, il laissera le bit défini en sortie de fi_getinfo. Sinon, le fournisseur peut effacer le bit pour indiquer que le comportement n'est pas

nécessaire.

En définissant un bit mr_mode, l'application a accepté d'ajuster son comportement comme indiqué. Il est important de noter que les applications qui choisissent de prendre en charge un mr_mode doivent être préparées à gérer le cas où le mr_mode n'est pas requis. Un fournisseur effacera un bit mr_mode s'il n'est pas

nécessaire.
FI_MR_LOCAL
Lorsque le bit de mode FI_MR_LOCAL est défini, les applications doivent enregistrer tous les tampons de données qui seront accessibles par le matériel local et fournir un paramètre desc valide dans les opérations de transfert de données applicables.

Lorsque FI_MR_LOCAL est non défini, les applications ne sont pas tenues d'enregistrer les tampons de données avant de les utiliser pour des opérations locales (par exemple, tampons d'envoi et de réception de données). Avant libfabric 1.22, le paramètre desc était ignoré. Dans libfabric 1.22 et versions ultérieures, le paramètre desc doit être valide ou NULL. Ce comportement permet aux applications de passer éventuellement un paramètre desc valide. Si le paramètre desc est NULL, tout enregistrement de mémoire locale requis sera géré par le fournisseur.

Un fournisseur peut masquer les exigences d'enregistrement local aux applications en utilisant un cache d'enregistrement interne ou des mécanismes similaires. Ces mécanismes peuvent toutefois avoir un impact négatif sur les performances de certaines applications, notamment celles qui gèrent leurs propres tampons réseau. Afin de prendre en charge un large éventail d'applications, sans affecter indûment leurs performances, les applications qui souhaitent gérer leurs propres enregistrements de mémoire locale peuvent le faire en utilisant les appels d'enregistrement de mémoire et en passant un paramètre desc valide.

Note : le bit de mode FI_MR_LOCAL mr_mode remplace le bit de mode FI_LOCAL_MR fi_info. Lorsque FI_MR_LOCAL est défini, FI_LOCAL_MR est ignoré.

FI_MR_RAW
Les régions de mémoire brutes sont utilisées pour prendre en charge les fournisseurs avec des clés de plus de 64 bits ou nécessitant une configuration au pair. Lorsque le bit FI_MR_RAW est défini, les applications doivent utiliser fi_mr_raw_attr() localement et fi_mr_map_raw() au pair avant de cibler une région de mémoire dans le cadre de toute demande de transfert de données.
FI_MR_VIRT_ADDR
Le bit FI_MR_VIRT_ADDR indique que le fournisseur référence les régions de mémoire par adresse virtuelle, plutôt que par un décalage basé sur 0. Les pairs qui ciblent des régions de mémoire enregistrées avec FI_MR_VIRT_ADDR spécifient le tampon mémoire de destination en utilisant l'adresse virtuelle de la cible, avec tout décalage dans la région spécifié comme adresse virtuelle + décalage. La prise en charge de ce bit implique généralement que les pairs doivent échanger des données d'adressage avant d'initier toute opération RMA ou atomique.

Pour les régions de mémoire enregistrées à l'aide de FI_MR_DMABUF, l'adresse virtuelle de départ de la région DMA-buf est obtenue en ajoutant le champ offset au champ base_addr de la structure fi_mr_dmabuf qui a été spécifiée lors de l'appel d'enregistrement.

FI_MR_ALLOCATED
Lorsqu'il est défini, toutes les régions de mémoire enregistrées doivent être soutenues par des pages de mémoire physique au moment de l'appel d'enregistrement. De plus, les applications ne doivent pas effectuer d'opérations susceptibles de modifier le mappage de l'adresse virtuelle à la page physique sous-jacente (par exemple, appeler free() sur un MR alloué). Ne pas respecter cela peut entraîner l'adresse virtuelle pointant vers un ensemble de pages physiques tandis que le MR pointe vers un autre ensemble de pages physiques.

Lorsqu'il n'est pas défini, les régions de mémoire enregistrées n'ont pas besoin d'être soutenues par des pages de mémoire physique au moment de l'appel d'enregistrement. De plus, le mappage de l'adresse virtuelle à la page physique sous-jacente est autorisé à changer, et le fournisseur garantira la mise à jour du MR correspondant en conséquence. Ce comportement permet des cas d'utilisation d'application où la mémoire peut être fréquemment libérée et réallouée ou la mémoire système migrée de/vers la mémoire de périphérique.

Lorsqu'il n'est pas défini, il incombe à l'application de s'assurer qu'une région de mémoire enregistrée référence des pages physiques valides pendant qu'un transfert de données est actif dessus, sinon le transfert de données peut échouer. Les modifications apportées par l'application à la plage d'adresses virtuelles doivent être coordonnées avec le trafic réseau entrant ou sortant de cette plage.

S'il n'est pas défini et que FI_HMEM est pris en charge, la possibilité que le mappage de l'adresse virtuelle à l'adresse physique change s'étend également aux interfaces HMEM. Si un fournisseur ne peut pas prendre en charge un mappage d'adresse virtuelle à adresse physique pour une interface HMEM donnée, le fournisseur doit fournir un repli raisonnable ou l'opération doit échouer.

FI_MR_PROV_KEY
Ce mode de région mémoire indique que le fournisseur ne prend pas en charge les clés MR demandées par l'application. Les clés MR sont retournées par le fournisseur. Les applications qui prennent en charge FI_MR_PROV_KEY peuvent obtenir la clé du fournisseur en utilisant fi_mr_key(), sauf si FI_MR_RAW est également défini. La clé retournée doit ensuite être échangée avec les pairs avant d'initier une opération RMA ou atomique.
FI_MR_MMU_NOTIFY
FI_MR_MMU_NOTIFY est généralement défini par les fournisseurs qui prennent en charge l'enregistrement de mémoire contre des régions mémoire qui ne sont pas nécessairement soutenues par des pages physiques allouées au moment de l'enregistrement de la mémoire. (C'est-à-dire, FI_MR_ALLOCATED est généralement 0). Cependant, ces fournisseurs exigent que les applications notifient le fournisseur avant que le MR ne soit accédé dans le cadre d'une opération de transfert de données. Cette notification informe le fournisseur que toutes les pages physiques nécessaires soutiennent désormais la région. La notification est nécessaire pour les fournisseurs qui ne peuvent pas s'accrocher directement aux tables de pages du système d'exploitation ou à l'unité de gestion de la mémoire. Voir fi_mr_refresh() pour les détails de la notification.
FI_MR_RMA_EVENT
Ce bit de mode indique que le fournisseur doit configurer les régions de mémoire associées aux événements RMA avant leur utilisation. Cela inclut toutes les régions de mémoire associées aux compteurs d'achèvement. Lorsqu'il est défini, les applications doivent indiquer si une région de mémoire sera associée à un compteur d'achèvement dans le cadre de sa création. Ceci est fait en passant le drapeau FI_RMA_EVENT à l'appel d'enregistrement de mémoire.

Ces régions de mémoire seront créées dans un état désactivé et devront être associées à tous les compteurs d'achèvement avant d'être activées. Pour activer une région de mémoire, l'application doit appeler fi_mr_enable(). Après avoir appelé fi_mr_enable(), aucune autre liaison de ressources ne pourra être effectuée sur la région de mémoire.

FI_MR_ENDPOINT
Ce bit de mode indique que le fournisseur associe les régions de mémoire aux points d'extrémité plutôt qu'aux domaines. Les régions de mémoire enregistrées auprès du fournisseur sont créées dans un état désactivé et doivent être liées à un point d'extrémité avant d'être activées. Pour lier le MR à un point d'extrémité, l'application doit utiliser fi_mr_bind(). Pour activer la région de mémoire, l'application doit appeler fi_mr_enable().
FI_MR_HMEM
Ce bit de mode est associé à la capacité FI_HMEM.

Si FI_MR_HMEM est défini, l'application doit enregistrer les tampons alloués à l'aide d'un appel de périphérique et fournir un paramètre desc valide dans les opérations de transfert de données applicables, même s'ils ne sont utilisés que pour des opérations locales (par exemple, tampons d'envoi et de réception de données). La mémoire du périphérique doit être enregistrée à l'aide de l'appel fi_mr_regattr, avec les champs iface et device remplis.

Si FI_MR_HMEM n'est pas défini, l'application n'a pas besoin d'enregistrer les tampons de périphérique pour les opérations locales. De plus, fi_mr_regattr n'est pas requis pour l'enregistrement de la mémoire du périphérique. Il incombe au fournisseur de découvrir les attributs d'enregistrement de mémoire de périphérique appropriés, le cas échéant.

Similaire à lorsque FI_MR_LOCAL n'est pas défini, si FI_MR_HMEM n'est pas défini, les applications peuvent éventuellement passer un paramètre desc valide. Si le paramètre desc est NULL, tout enregistrement de mémoire locale requis sera géré par le fournisseur.

Si FI_MR_HMEM est défini, mais FI_MR_LOCAL ne l'est pas, seuls les tampons de périphérique doivent être enregistrés lorsqu'ils sont utilisés localement. Dans ce cas, le paramètre desc passé dans les opérations de transfert de données doit être valide ou NULL. De même, si FI_MR_LOCAL est défini, mais pas FI_MR_HMEM, le paramètre desc doit être valide ou NULL.

FI_MR_COLLECTIVE
Ce bit est associé à la capacité FI_COLLECTIVE.

Si FI_MR_COLLECTIVE est défini, le fournisseur exige que les régions mémoire utilisées dans les opérations collectives soient explicitement enregistrées pour être utilisées avec des appels collectifs. Cela nécessite d'enregistrer les régions passées aux appels collectifs en utilisant le drapeau FI_COLLECTIVE.

Si FI_MR_COLLECTIVE n'est pas défini, l'enregistrement de mémoire pour les opérations collectives est facultatif. Les applications peuvent éventuellement passer un paramètre desc valide. Si le paramètre desc est NULL, tout enregistrement de mémoire locale requis sera géré par le fournisseur.

Enregistrement de mémoire de base (obsolète)
L'enregistrement de mémoire de base a été déprécié dans la version 1.5 de libfabric, mais il est pris en charge pour des raisons de compatibilité ascendante. L'enregistrement de mémoire de base est indiqué en définissant mr_mode sur FI_MR_BASIC. FI_MR_BASIC doit être défini seul et non associé à des bits mr_mode. Contrairement aux autres bits mr_mode, si FI_MR_BASIC est défini en entrée de fi_getinfo(), il ne sera pas effacé par le fournisseur. C'est-à-dire que définir mr_mode sur FI_MR_BASIC force l'enregistrement de base si le fournisseur le prend en charge.

Le comportement de l'enregistrement de base est équivalent à l'exigence des bits mr_mode suivants : FI_MR_VIRT_ADDR, FI_MR_ALLOCATED et FI_MR_PROV_KEY. De plus, les fournisseurs qui prennent en charge l'enregistrement de base nécessitent généralement le bit de mode fi_info (obsolète) FI_LOCAL_MR, qui a été incorporé dans le bit de mode mr_mode FI_MR_LOCAL.

Les fonctions d'enregistrement – fi_mr_reg, fi_mr_regv et fi_mr_regattr – sont utilisées pour enregistrer une ou plusieurs régions mémoire auprès des ressources fabric. La principale différence entre les fonctions d'enregistrement réside dans le nombre et le type de paramètres qu'elles acceptent en entrée. Sinon, elles effectuent la même fonction générale.

Obsolète : Par défaut, l'enregistrement de mémoire s'achève de manière synchrone. C'est-à-dire que l'appel d'enregistrement ne retournera pas avant que l'enregistrement ne soit terminé. L'enregistrement de mémoire peut s'achever de manière asynchrone en liant le domaine de ressources à une file d'attente d'événements à l'aide du drapeau FI_REG_MR. Voir fi_domain_bind. Lorsque l'enregistrement de mémoire est asynchrone, afin d'éviter une condition de concurrence entre le retour de l'appel d'enregistrement et la lecture correspondante de l'événement à partir de l'EQ, le paramètre de sortie mr sera écrit avant que tout événement associé à l'opération ne puisse être lu par l'application. Un événement asynchrone ne sera pas généré à moins que l'appel d'enregistrement ne retourne succès (0).

fi_mr_reg

L'appel fi_mr_reg enregistre

sters le tampon mémoire spécifié par l'utilisateur avec le domaine de ressources. Le tampon est activé pour l'accès par le matériel du tissu (fabric) en fonction des permissions d'accès fournies. Voir la description du champ d'accès pour les attributs de la région mémoire

ci-dessous.

La mémoire enregistrée est associée à un descripteur de mémoire local et, de manière optionnelle, à une clé de mémoire distante. Un descripteur de mémoire est un identifiant spécifique au fournisseur associé à la mémoire enregistrée. Les descripteurs de mémoire correspondent souvent à des indices ou des clés spécifiques au matériel associés à la région mémoire. Les clés de mémoire distantes fournissent une protection limitée contre l'accès non désiré par un nœud distant. Les accès distants à une région mémoire doivent fournir la clé associée à l'enregistrement

.

Étant donné que les clés MR doivent être fournies par un processus distant, une application peut utiliser le paramètre requested_key pour indiquer qu'une valeur de clé spécifique doit être retournée. La prise en charge des clés demandées par l'utilisateur est spécifique au fournisseur et est déterminée par la valeur du drapeau FI_MR_PROV_KEY dans l'attribut de domaine

mr_mode.

Les opérations RMA et atomiques distantes indiquent l'emplacement au sein d'une région mémoire enregistrée en spécifiant une adresse. L'emplacement est référencé en ajoutant le décalage (offset) soit à l'adresse virtuelle de base du tampon, soit à 0, selon le

mr_mode.

Le paramètre offset est réservé pour une utilisation future et doit être

0.

Pour les demandes d'enregistrement de mémoire asynchrones, le résultat sera rapporté à l'utilisateur via une file d'événements associée au domaine de ressources. Si l'opération réussit, la structure de région mémoire allouée sera retournée à l'utilisateur via le paramètre mr. L'adresse mr doit rester valide jusqu'à ce que l'opération d'enregistrement soit terminée. Le contexte spécifié avec la demande d'enregistrement est retourné avec l'événement

d'achèvement.

fi_clos

e

Fi_close est utilisé pour libérer toutes les ressources associées à l'enregistrement d'une région mémoire. Une fois désenregistrée, l'accès futur à la mémoire enregistrée n'est pas garanti. Les opérations actives ou en file d'attente qui référencent une région mémoire en cours de fermeture peuvent tenter d'accéder à une région mémoire invalide et échouer. Après la fermeture d'une MR, toute nouvelle opération ciblant la MR fermée échouera également. Les applications sont responsables de s'assurer qu'une MR n'est plus nécessaire avant de la fermer. Notez que les accès à une MR fermée depuis un pair distant entraîneront une erreur chez le pair. L'état de l'extrémité (endpoint) local ne sera pas

affecté.

Pour les MR associées à une extrémité (drapeau FI_MR_ENDPOINT défini), la MR doit être fermée avant l'extrémité. Si des ressources sont toujours associées à la MR lors de la tentative de fermeture, l'appel retournera

NOTES

L'accès direct à la mémoire d'une application par un pair distant nécessite que l'application enregistre le(s) tampon(s) mémoire ciblé(s). Cela se fait généralement en appelant l'une des routines fi_mr_reg*. Pour FI_MR_PROV_KEY, le fournisseur renverra une clé qui doit être utilisée par le pair lors de l'accès à la région mémoire. L'application est responsable du transfert de cette clé vers le pair. Si le mode FI_MR_RAW a été défini, la clé doit être récupérée à l'aide de la fonction fi_mr_raw_attr.

FI_MR_RAW permet de prendre en charge les fournisseurs qui nécessitent plus de 8 octets pour leurs clés de protection ou qui ont besoin d'une configuration supplémentaire avant qu'une clé puisse être utilisée pour les transferts. Après qu'une clé brute a été récupérée, elle doit être échangée avec le pair distant. Le pair doit utiliser fi_mr_map_raw pour convertir la clé brute en une clé utilisable de 64 bits. La conversion doit être effectuée même si la clé brute fait 64 bits ou moins.

Les fonctions de support des clés brutes sont utilisables avec toutes les régions mémoire enregistrées, même si FI_MR_RAW n'a pas été défini. Il est recommandé que les applications portables visent à utiliser ces interfaces ; cependant, leur utilisation entraîne une surcharge supplémentaire en messages et en mémoire, ce qui les rend moins désirables pour les applications hautement évolutives.

Il peut y avoir des cas où le support pair à pair des périphériques ne doit pas être utilisé ou ne peut pas être utilisé, par exemple lorsque la configuration ACS du PCIe ne permet pas le transfert. La variable d'environnement FI_HMEM_DISABLE_P2P peut être définie pour informer Libfabric que les transactions pair à pair ne doivent pas être utilisées. Le fournisseur peut choisir d'effectuer une copie à la place, ou échouera dans le support de FI_HMEM si le fournisseur est incapable de le faire.

DOMAINES MÉMOIRE

Les domaines mémoire identifient la séparation physique de la mémoire qui peut ou non être accessible à travers le même espace d'adresse virtuel. Traditionnellement, les applications ne traitaient qu'un seul domaine mémoire, celui de la mémoire hôte étroitement couplée aux CPU du système. Avec l'introduction des sous-systèmes mémoire de périphérique et non uniformes, les applications doivent souvent savoir à quel domaine mémoire une adresse virtuelle particulière est mappée.

En règle générale, les périphériques physiques séparés peuvent être considérés comme ayant leurs propres domaines mémoire. Par exemple, une NIC peut avoir une mémoire accessible par l'utilisateur, et serait considérée comme un domaine mémoire séparé de la mémoire sur un GPU. Les domaines mémoire de la NIC et du GPU sont tous deux séparés de la mémoire du système hôte. Les GPU ou accélérateurs de calcul individuels peuvent avoir des domaines mémoire distincts, ou peuvent être connectés de telle manière (par exemple, un fabric spécifique au GPU) que tous les GPU appartiendraient au même domaine mémoire. Malheureusement, l'identification des domaines mémoire est spécifique à chaque système et à sa configuration physique et/ou virtuelle.

Comprendre les domaines mémoire dans les environnements mémoire hétérogènes est important car cela peut impacter l'ordre et la visibilité des données telles que vues par une application. Il est également important de comprendre à quel domaine mémoire une application est le plus étroitement couplée. Dans la plupart des cas, les applications sont étroitement couplées à la mémoire hôte. Cependant, une application s'exécutant directement sur un GPU ou une NIC peut être plus étroitement couplée à la mémoire associée à ces périphériques.

Les régions mémoire sont souvent associées à un seul domaine mémoire. Le domaine est souvent indiqué par les champs iface et device de fi_mr_attr. Bien qu'il soit possible que les pages physiques soutenant une région de mémoire virtuelle migrent entre les domaines mémoire en fonction des motifs d'accès. Par exemple, les pages physiques référencées par une plage d'adresses virtuelles pourraient migrer entre la mémoire hôte et la mémoire GPU, selon l'unité de calcul qui l'utilise activement.

Voir les pages de manuel fi_endpoint(3) et fi_cq(3) pour une discussion supplémentaire sur la sémantique d'ordre des messages, des données et des complétions, y compris l'impact des domaines mémoire.

Renvoie 0 en cas de succès. En cas d'erreur, une valeur négative correspondant à l'errno du fabric est renvoyée.

Les valeurs d'errno du fabric sont définies dans rdma/fi_errno.h.

Le requested_key est déjà utilisé.
-FI_EKEYREJECTED

CACHE D'ENREGISTREMENT MÉMOIRE

De nombreuses NIC matérielles accessibles par libfabric nécessitent que les tampons de données soient enregistrés avec le matériel pendant que le matériel y accède. Cela garantit que les mappages d'adresses virtuelles vers physiques pour ces tampons ne changent pas pendant que le transfert a lieu. L'impact des performances de l'enregistrement des régions mémoire peut être significatif. Par conséquent, certains fournisseurs utilisent un cache d'enregistrement, en particulier lorsqu'ils travaillent avec des applications qui sont incapables de gérer leurs propres tampons réseau. Un cache d'enregistrement évite la surcharge d'enregistrer et de désenregistrer un tampon de données à chaque transfert.

Si un cache d'enregistrement va être utilisé pour la mémoire hôte et périphérique, le périphérique doit prendre en charge l'adressage virtuel unifié. Si le périphérique ne prend pas en charge l'adressage virtuel unifié, soit uneitionnel de cache d'enregistrement est requis pour suivre cette mémoire de périphérique, ou la mémoire de périphérique ne peut pas être mise en

cache.

En règle générale, si le matériel nécessite le bit de mode FI_MR_LOCAL décrit ci-dessus, mais que cela n'est pas pris en charge par l'application, un cache d'enregistrement de mémoire peut être utilisé. Les variables d'environnement suivantes peuvent être utilisées pour configurer les caches d'enregistrement

.
FI_MR_CACHE_MAX_S
IZE
Cela définit le nombre total d'octets pour toutes les régions mémoire qui peuvent être suivies par le cache. Si ce n'est pas défini, le cache n'a pas de limite sur le nombre d'octets qui peuvent être enregistrés et mis en cache. Le définir réduira la quantité de mémoire qui n'est pas activement utilisée dans le cadre d'un transfert de données et qui est enregistrée auprès d'un fournisseur. Par défaut, la taille du cache est
illimitée.
FI_MR_CACHE_MAX_CO
UNT
Cela définit le nombre total de régions mémoire qui peuvent être enregistrées auprès du cache. Si ce n'est pas défini, une limite par défaut est choisie. Le définir réduira le nombre de régions qui sont enregistrées, quelle que soit leur taille, et qui ne sont pas activement utilisées dans le cadre d'un transfert de données. Le définir à zéro désactivera la mise en cache des
enregistrements.
FI_MR_CACHE_MONI
TOR
Le moniteur de cache est responsable de la détection des changements de mémoire système (FI_HMEM_SYSTEM) effectués entre les adresses virtuelles utilisées par une application et les pages physiques sous-jacentes. Les options de moniteur valides sont : userfaultfd, memhooks, kdreg2 et disabled. Sélectionner disabled désactivera le cache d'enregistrement. Memhooks fonctionne en interceptant les appels pertinents d'allocation et de libération de mémoire qui peuvent entraîner des changements de correspondance, tels que malloc, mmap, free, etc. Notez que memhooks fonctionne au niveau du lien elf et n'utilise pas les crochets de mémoire de glibc. Kdreg2 est fourni sous la forme d'un module de noyau Linux
chargeable.

Les options de moniteur valides sont : 0 ou 1. Notez que le moniteur de mémoire ROCR nécessite une version de ROCR avec l'adressage virtuel unifié

LED
