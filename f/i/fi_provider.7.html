D'ENSEMBLE

Voir fi_arch(7) pour une brève description de la manière dont les fournisseurs s'intègrent dans l'architecture de

libfabric.

Conceptuellement, un fournisseur de fabric implémente et mappe l'API libfabric sur des logiciels et/ou du matériel de réseau de plus bas niveau. La plupart des appels d'application à l'API libfabric vont directement à l'implémentation de cette API par le

fournisseur.

Les fournisseurs Libfabric sont regroupés en différents types : cœur, utilitaire, de interception (hooking) et de décharge (offload). Ceux-ci sont décrits plus en détail ci-dessous. Le diagramme suivant illustre l'architecture entre les types de

fournisseurs. 
---------------------------- libfabric API ---------------------------- 
  [core]   pr
ovider|<- [hooking provider] [services] API | --- libfabric API ---
|<- [utility provider] | ---------------- libfabric API -----
------------- |<- [core provider] <-peer API-> [offload provider]

Tous les fournisseurs se branchent sur libfabric en utilisant une API de fournisseur exportée. libfabric prend en charge à la fois les fournisseurs internes, qui sont livrés avec la bibliothèque pour la commodité de l'utilisateur, ainsi que les fournisseurs externes. Les bibliothèques de fournisseurs externes doivent se trouver dans le chemin de recherche des bibliothèques, se terminer par le suffixe « -fi » et exporter la fonction fi_prov_ini()

.

Une fois enregistré auprès du cœur de libfabric, un fournisseur sera signalé aux applications dans le cadre du processus de découverte. Les fournisseurs de interception et les fournisseurs utilitaires intercepteront les appels libfabric de l'application pour effectuer certaines tâches avant de passer l'appel au fournisseur suivant. S'il n'est pas nécessaire d'intercepter un appel API spécifique, l'appelera directement le fournisseur cœur. Lorsque c'est possible, la communication entre fournisseurs se fait en utilisant les API libfabric elles-mêmes, y compris l'utilisation d'extensions spécifiques au fournisseur pour réduire la surcharge des

appels.

libfabric définit un ensemble d'API qui ciblent spécifiquement les fournisseurs pouvant être utilisés comme pairs (peers). Ces API sont,

étrangement, appelées API pairs (peer APIs). Les API pairs font techniquement partie de l'API libfabric externe, mais ne sont pas co
nçues pour une utilisation directe par les applications et ne sont pas considérées comme stables pour la rétrocompatibilité de l'API.

Fournisseurs

cœur

Les fournisseurs cœur sont des fournisseurs autonomes qui ciblent généralement une classe spécifique de périphériques réseau. C'est-à-dire, une carte réseau (NIC) spécifique, une classe de matériel réseau ou une interface logicielle de plus bas niveau. Les fournisseurs cœur sont généralement ceux dont la plupart des développeurs d'applications se préoccupent. Les fournisseurs cœur peuvent ne prendre en charge que des fonctionnalités et des interfaces libfabric qui se mappent efficacement au matériel sous-jacent ou aux protocoles

réseau.

Les fournisseurs cœur suivants sont intégrés à libfabric par défaut, en supposant que tous les prérequis de compilation sont satisfaits. C'est-à- dire, que les bibliothèques nécessaires sont installées, que le support du système d'exploitation est disponible, etc. Cette liste n'est pas

exhaustive.

Fournisseurs

utilitaires

Les fournisseurs utilitaires sont nommés avec un préfixe de départ « ofi_ ». Les fournisseurs utilitaires sont distincts des fournisseurs cœur en ce qu'ils ne sont pas associés à des classes spécifiques de périphériques. Ils travaillent plutôt avec les fournisseurs cœur pour étendre leurs fonctionnalités et interagir avec les fournisseurs cœur à travers les interfaces libfabric en interne. Les fournisseurs utilitaires sont utilisés pour prendre en charge un type de point de terminaison spécifique sur un type de point de terminaison plus

simple.

Les fournisseurs utilitaires apparaissent dans le nom du fournisseur retourné. Voir fi_fabric(3). Les fournisseurs utilitaires sont activés automatiquement pour les fournisseurs cœur qui ne prennent pas en charge l'ensemble de fonctionnalités demandé par une

application.

Fournisseurs de

interception

Les fournisseurs de interception sont principalement utilisés à des fins de débogage. Puisque les fournisseurs de interception sont compilés et inclus dans les versions de libfabric, ils sont toujours disponibles et n'ont aucun impact sur les performances à moins d'être activés. Les fournisseurs de interception peuvent se superposer à tous les autres fournisseurs et intercepter, ou « hooker », leurs appels afin d'effectuer une tâche dédiée, comme la collecte de données de performance sur les chemins d'appel ou la fourniture de sorties de

débogage.

Voir fi_hook(7

) pour plus d
'informations.

Fournisseurs de

décharge

Les fournisseurs de décharge commencent par le préfixe de nom « off_ ». Un fournisseur de décharge est destiné à être associé à d'autres fo

urnisseurs cœur et/ou utilitaires. Un fournisseur de décharge vise à accélérer des types spécifiques de communication, généralement en tiran
t parti des services réseau qui ont été déchargés dans le matériel, bien que le support de décharge matérielle réelle ne soit pas une exigence.

Fournisseur LINKx

(LNX)

Le fournisseur LNX est conçu pour lier deux fournisseurs ou plus, permettant aux applications d'utiliser de manière transparente plusieurs fournisseurs ou NIC. Ce fournisseur utilise l'infrastructure pair de libfabric pour aider à l'utilisation des fournisseurs sous-jacents. Cette version du fournisseur est capable de lier n'importe quel fournisseur libfabric qui prend en charge la capacité

FI_PEER.

Voir fi_lnx(7

) pour plus d'
informations.
