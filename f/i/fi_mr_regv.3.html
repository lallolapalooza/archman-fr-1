DESCRIPTION

Les régions mémoire enregistrées associent des tampons mémoire à des permissions accordées pour l'accès par les ressources du tissu (fabric). Un tampon mémoire doit être enregistré auprès d'un domaine de ressources avant de pouvoir être utilisé comme cible d'une opération RMA (Remote Memory Access) ou d'un transfert de données atomique. De plus, un fournisseur de tissu (fabric provider) peut exiger que les tampons de données soient enregistrés avant d'être utilisés dans des transferts locaux. Les restrictions d'enregistrement mémoire sont contrôlées à l'aide d'un ensemble distinct de bits de mode, spécifiés via les attributs du domaine (champ `mr_mode`). Chaque bit de `mr_mode` exige qu'une application prenne des mesures spécifiques afin d'utiliser les tampons mémoire avec les interfaces libfabric.

À titre de cas particulier, une nouvelle région mémoire peut être créée à partir d'une région mémoire existante. Une telle nouvelle région mémoire est appelée une sous-MR (sub-MR), et la région mémoire existante est appelée la MR de base (base MR). Les sous-MR peuvent être utilisées pour partager des ressources matérielles, telles que les traductions d'adresses virtuelles en physiques et le "pinning" de pages. Cela peut améliorer les performances lors de la création et de la destruction de sous-régions qui nécessitent des droits d'accès différents. La MR de base elle-même peut également être une sous-MR, permettant une hiérarchie de régions mémoire.

Les points suivants s'appliquent à l'enregistrement mémoire :

Enregistrement Mémoire par Défaut
Si aucun bit de `mr_mode` n'est défini, les comportements par défaut décrits ci-dessous sont suivis. Historiquement, ces valeurs par défaut étaient collectivement appelées enregistrement mémoire évolutif (scalable memory registration). Les exigences par défaut sont décrites ci-dessous, suivies des définitions de la manière dont chaque bit de `mr_mode` modifie la définition.

Compatibilité : Pour les versions 1.4 et antérieures de la bibliothèque, ceci était indiqué en définissant `mr_mode` sur FI_MR_SCALABLE et le bit de mode FI_LOCAL_MR de `fi_info` à 0. FI_MR_SCALABLE et FI_LOCAL_MR ont été dépréciés dans la version 1.5 de libfabric, bien qu'ils soient pris en charge à des fins de compatibilité ascendante.

Pour des raisons de sécurité, l'enregistrement mémoire est requis pour les tampons de données qui sont directement accessibles par un processus pair. Par exemple, l'enregistrement est requis pour les tampons cibles RMA (lus ou écrits), et ceux accessibles par des opérations atomiques ou collectives.

Par défaut, l'enregistrement se fait sur des plages d'adresses virtuelles. Comme l'enregistrement fait référence à des plages d'adresses, plutôt qu'à des tampons de données alloués, les plages d'adresses n'ont pas besoin de correspondre à des tampons de données alloués par l'application au moment de l'appel d'enregistrement. Autrement dit, une application peut enregistrer n'importe quelle plage d'adresses dans son espace d'adressage virtuel, que ces adresses soient sauvegardées par des pages physiques ou aient été allouées ou non.

Notez que les pages physiques doivent sauvegarder les adresses avant que celles-ci ne soient accessibles dans le cadre d'une opération de transfert de données, sous peine d'échec des transferts de données. De plus, selon l'opération, cela pourrait entraîner la réception d'une erreur de segmentation par le processus local pour avoir accédé à une mémoire invalide.

Une fois enregistrées, les régions mémoire résultantes sont accessibles par les pairs à partir d'une adresse de base de 0. Autrement dit, l'adresse cible spécifiée est un décalage en octets dans la région enregistrée.

L'application sélectionne également la clé d'accès associée à la MR. La taille de la clé est limitée à un maximum de 8 octets.

Avec l'enregistrement évolutif, les tampons de données accessibles localement ne sont pas enregistrés. Cela inclut les tampons sources pour toutes les opérations d'envoi – send, tagged send, RMA, et atomics – ainsi que les tampons postés pour les opérations de réception et de réception marquée (tagged receive).

Bien que le comportement par défaut de l'enregistrement mémoire soit pratique pour les développeurs d'applications, il est difficile à implémenter en matériel. Les tentatives de masquer les exigences matérielles à l'application entraînent souvent des impacts significatifs et inacceptables sur les performances. Les bits de `mr_mode` suivants sont fournis en entrée de `fi_getinfo`. Si un fournisseur exige le comportement défini pour un bit de `mr_mode`, il laissera le bit défini en sortie de `fi_getinfo`. Sinon, le fournisseur peut effacer le bit pour indiquer que le comportement n'est pas nécessaire.

En définissant un bit de `mr_mode`, l'application a accepté d'ajuster son comportement comme indiqué. Notamment, les applications qui choisissent de prendre en charge un `mr_mode` doivent être préparées à gérer le cas où le `mr_mode` n'est pas requis. Un fournisseur effacera un bit de `mr_mode` s'il n'est pas nécessaire.

FI_MR_LOCAL
Lorsque le bit de mode FI_MR_LOCAL est défini, les applications doivent enregistrer tous les tampons de données qui seront accédés par le matériel local et fournir un paramètre desc valide dans les opérations de transfert de données applicables.

Lorsque FI_MR_LOCAL n'est pas défini, les applications ne sont pas tenues d'enregistrer les tampons de données avant de les utiliser pour des opérations locales (par exemple, les tampons de données d'envoi et de réception). Avant libfabric 1.22, le paramètre desc était ignoré. Dans libfabric 1.22 et les versions ultérieures, le paramètre desc doit être soit valide, soit NULL. Ce comportement permet aux applications de passer éventuellement un paramètre desc valide. Si le paramètre desc est NULL, toute inscription mémoire locale requise sera gérée par le fournisseur.

Un fournisseur peut masquer les exigences d'inscription locale des applications en utilisant un cache d'inscription interne ou des mécanismes similaires. Cependant, de tels mécanismes peuvent nuire aux performances de certaines applications, notamment celles qui gèrent leurs propres tampons réseau. Afin de prendre en charge la gamme d'applications la plus large possible, sans nuire indûment à leurs performances, les applications qui souhaitent gérer leurs propres inscriptions mémoire locales peuvent le faire en utilisant les appels d'inscription mémoire et en passant un paramètre desc valide.

Remarque : le bit de mode mr_mode FI_MR_LOCAL remplace le bit de mode fi_info FI_LOCAL_MR. Lorsque FI_MR_LOCAL est défini, FI_LOCAL_MR est ignoré.

FI_MR_RAW
Les régions mémoire brutes sont utilisées pour prendre en charge les fournisseurs dont les clés dépassent 64 bits ou qui nécessitent une configuration au niveau du pair. Lorsque le bit FI_MR_RAW est défini, les applications doivent utiliser fi_mr_raw_attr() localement et fi_mr_map_raw() au niveau du pair avant de cibler une région mémoire dans le cadre de toute requête de transfert de données.
FI_MR_VIRT_ADDR
Le bit FI_MR_VIRT_ADDR indique que le fournisseur référence les régions mémoire par adresse virtuelle, plutôt que par un décalage de base 0. Les pairs qui ciblent des régions mémoire enregistrées avec FI_MR_VIRT_ADDR spécifient le tampon mémoire de destination en utilisant l'adresse virtuelle de la cible, avec tout décalage dans la région spécifié comme adresse virtuelle + décalage. La prise en charge de ce bit implique généralement que les pairs doivent échanger des données d'adressage avant d'initier toute opération RMA ou atomique.

Pour les régions mémoire enregistrées à l'aide de FI_MR_DMABUF, l'`adresse virtuelle' de départ de la région DMA-buf est obtenue en ajoutant le champ offset au champ base_addr de la structure fi_mr_dmabuf qui a été spécifié via l'appel d'inscription.

FI_MR_ALLOCATED
Lorsqu'il est défini, toutes les régions mémoire enregistrées doivent être soutenues par des pages mémoire physiques au moment où l'appel d'inscription est effectué. De plus, les applications ne doivent pas effectuer d'opérations qui pourraient entraîner la modification du mappage de l'adresse virtuelle sous-jacente aux pages physiques (par exemple, appeler free() sur un MR alloué). Le non-respect de cela peut entraîner le fait que l'adresse virtuelle pointe vers un ensemble de pages physiques tandis que le MR pointe vers un autre ensemble de pages physiques.

Lorsqu'il n'est pas défini, les régions mémoire enregistrées n'ont pas besoin d'être soutenues par des pages mémoire physiques au moment où l'appel d'inscription est effectué. De plus, le mappage de l'adresse virtuelle sous-jacente aux pages physiques est autorisé à changer, et le fournisseur s'assurera que le MR correspondant est mis à jour en conséquence. Ce comportement permet des cas d'utilisation d'applications où la mémoire peut être fréquemment libérée et réallouée, ou où la mémoire du système migre vers/depuis la mémoire du périphérique.

Lorsqu'il n'est pas défini, l'application est responsable de s'assurer qu'une région mémoire enregistrée référence des pages physiques valides pendant qu'un transfert de données est actif contre elle, sinon le transfert de données peut échouer. Les modifications de l'application de la plage d'adresses virtuelles doivent être coordonnées avec le trafic réseau vers ou depuis cette plage.

S'il n'est pas défini et que FI_HMEM est pris en charge, la capacité du mappage de l'adresse virtuelle à l'adresse physique à changer s'étend également aux interfaces HMEM. Si un fournisseur ne peut pas prendre en charge la modification de l'adresse virtuelle à l'adresse physique pour une interface HMEM donnée, le fournisseur devrait prendre en charge une solution de repli raisonnable ou l'opération devrait échouer.

FI_MR_PROV_KEY
Ce mode de région mémoire indique que le fournisseur ne prend pas en charge les clés MR demandées par l'application. Les clés MR sont retournées par le fournisseur. Les applications qui prennent en charge FI_MR_PROV_KEY peuvent obtenir la clé du fournisseur à l'aide de fi_mr_key(), sauf si FI_MR_RAW est également défini. La clé retournée doit ensuite être échangée avec les pairs avant d'initier une opération RMA ou atomique.
FI_MR_MMU_NOTIFY
FI_MR_MMU_NOTIFY est généralement défini par les fournisseurs qui prennent en charge l'inscription mémoire contre des régions mémoire qui ne sont pas nécessairement soutenues par des pages physiques allouées au moment où l'inscription mémoire se produit. (C'est-à-dire que FI_MR_ALLOCATED est généralement 0). Cependant, de tels fournisseurs exigent que les applications notifient le fournisseur avant que le MR ne soit accédé dans le cadre d'une opération de transfert de données. Cette notification informe le fournisseur que toutes les pages physiques nécessaires soutiennent désormais la région. La notification est nécessaire pour les fournisseurs qui ne peuvent pas s'interposer directement dans les tables de pages du système d'exploitation ou l'unité de gestion de la mémoire. Voir fi_mr_refresh() pour les détails de la notification.
FI_MR_RMA_EVENT
Ce bit de mode indique que le fournisseur doit configurer les régions mémoire associées à des événements RMA avant leur utilisation. Cela inclut toutes les régions mémoire associées à des compteurs d'achèvement. Lorsqu'il est défini, les applications doivent indiquer si une région mémoire sera associée à un compteur d'achèvement dans le cadre de la création de la région. Cela se fait en passant le drapeau FI_RMA_EVENT à l'appel d'inscription mémoire.

De telles régions mémoire seront créées dans un état désactivé et doivent être associées à tous les compteurs d'achèvement avant d'être activées. Pour activer une région mémoire, l'application doit appeler fi_mr_enable(). Après avoir appelé fi_mr_enable(), aucune autre liaison de ressource ne peut être effectuée à la région mémoire.

FI_MR_ENDPOINT
Ce bit de mode indique que le fournisseur associe les régions mémoire aux points de terminaison plutôt qu'aux domaines. Les régions mémoire enregistrées auprès du fournisseur sont créées dans un état désactivé et doivent être liées à un point de terminaison avant d'être activées. Pour lier le MR à un point de terminaison, l'application doit utiliser fi_mr_bind(). Pour activer la région mémoire, l'application doit appeler fi_mr_enable().
FI_MR_HMEM
Ce bit de mode est associé à la capacité FI_HMEM.

Si FI_MR_HMEM est défini, l'application doit enregistrer les tampons qui ont été alloués à l'aide d'un appel de périphérique et fournir un paramètre desc valide dans les opérations de transfert de données applicables, même s'ils ne sont utilisés que pour des opérations locales (par exemple, les tampons de données d'envoi et de réception). La mémoire du périphérique doit être enregistrée à l'aide de l'appel fi_mr_regattr, avec les champs iface et device remplis.

Si FI_MR_HMEM n'est pas défini, l'application n'a pas besoin d'enregistrer les tampons de périphérique pour les opérations locales. De plus, fi_mr_regattr n'est pas requis pour l'inscription de la mémoire du périphérique. Il incombe au fournisseur de découvrir les attributs d'inscription de la mémoire du périphérique appropriés, le cas échéant.

De manière similaire à si FI_MR_LOCAL n'est pas défini, si FI_MR_HMEM n'est pas défini, les applications peuvent éventuellement passer un paramètre desc valide. Si le paramètre desc est NULL, toute inscription mémoire locale requise sera gérée par le fournisseur.

Si FI_MR_HMEM est défini, mais que FI_MR_LOCAL n'est pas défini, seuls les tampons de périphérique doivent être enregistrés lorsqu'ils sont utilisés localement. Dans ce cas, le paramètre desc passé aux opérations de transfert de données doit être soit valide, soit NULL. De même, si FI_MR_LOCAL est défini, mais que FI_MR_HMEM ne l'est pas, le paramètre desc doit être soit valide, soit NULL.

FI_MR_COLLECTIVE
Ce bit est associé à la capacité FI_COLLECTIVE.

Si FI_MR_COLLECTIVE est défini, le fournisseur exige que les régions mémoire utilisées dans les opérations de collecte soient explicitement enregistrées pour une utilisation avec les appels collectifs. Cela nécessite d'enregistrer les régions passées aux appels collectifs à l'aide du drapeau FI_COLLECTIVE.

Si FI_MR_COLLECTIVE n'est pas défini, l'inscription mémoire pour les opérations de collecte est facultative. Les applications peuvent éventuellement passer un paramètre desc valide. Si le paramètre desc est NULL, toute inscription mémoire locale requise sera gérée par le fournisseur.

Inscription mémoire de base (obsolète)
L'inscription mémoire de base a été dépréciée dans la version 1.5 de libfabric, mais est prise en charge pour la compatibilité ascendante. L'inscription mémoire de base est indiquée en définissant mr_mode égal à FI_MR_BASIC. FI_MR_BASIC doit être défini seul et non associé à des bits mr_mode. Contrairement aux autres bits mr_mode, si FI_MR_BASIC est défini en entrée de fi_getinfo(), il ne sera pas effacé par le fournisseur. C'est-à-dire que définir mr_mode égal à FI_MR_BASIC force l'inscription de base si le fournisseur la prend en charge.

Le comportement de l'inscription de base est équivalent à exiger les bits mr_mode suivants : FI_MR_VIRT_ADDR, FI_MR_ALLOCATED et FI_MR_PROV_KEY. De plus, les fournisseurs qui prennent en charge l'inscription de base exigent généralement le bit de mode fi_info (obsolète) FI_LOCAL_MR, qui a été incorporé dans le bit de mode mr_mode FI_MR_LOCAL.

Les fonctions d'inscription – fi_mr_reg, fi_mr_regv et fi_mr_regattr – sont utilisées pour enregistrer une ou plusieurs régions mémoire avec des ressources de tissu. La principale différence entre les fonctions d'inscription réside dans le nombre et le type de paramètres qu'elles acceptent en entrée. Sinon, elles effectuent la même fonction générale.

Obsolète : Par défaut, l'inscription mémoire se termine de manière synchrone. C'est-à-dire que l'appel d'inscription ne retournera pas avant que l'inscription ne soit terminée. L'inscription mémoire peut se terminer de manière asynchrone en liant le domaine de ressource à une file d'événements à l'aide du drapeau FI_REG_MR. Voir fi_domain_bind. Lorsque l'inscription mémoire est asynchrone, afin d'éviter une condition de course entre le retour de l'appel d'inscription et la lecture correspondante de l'événement depuis la file d'événements, le paramètre de sortie mr sera écrit avant que tout événement associé à l'opération ne puisse être lu par l'application. Un événement asynchrone ne sera pas généré à moins que l'appel d'inscription ne retourne un succès (0).

ci-dessous.

La mémoire enregistrée est associée à un descripteur mémoire local et, de manière optionnelle, à une clé mémoire distante. Un descripteur mémoire est un identifiant spécifique au fournisseur associé à la mémoire enregistrée. Les descripteurs mémoire correspondent souvent à des indices ou des clés spécifiques au matériel associés à la région mémoire. Les clés mémoire distantes fournissent une protection limitée contre les accès indésirables par un nœud distant. Les accès distants à une région mémoire doivent fournir la clé associée à l'enregistrement

Comme les clés MR doivent être fournies par un processus distant, une application peut utiliser le paramètre requested_key pour indiquer qu'une valeur de clé spécifique doit être retournée. La prise en charge des clés demandées par l'utilisateur est spécifique au fournisseur et est déterminée par la valeur du drapeau FI_MR_PROV_KEY dans l'attribut de domaine

Fi_close est utilisé pour libérer toutes les ressources associées à l'enregistrement d'une région mémoire. Une fois désenregistrée, l'accès futur à la mémoire enregistrée n'est pas garanti. Les opérations actives ou en file d'attente qui référencent une région mémoire en cours de fermeture peuvent tenter d'accéder à une région mémoire invalide et échouer. Après la fermeture d'une MR, toute nouvelle opération visant la MR fermée échouera également. Les applications sont responsables de s'assurer qu'une MR n'est plus nécessaire avant de la fermer. affecté.

-FI_EBUSY.

Les enregistrements DMA-buf sont utilisés pour partager la mémoire d'un périphérique donné avec la carte réseau du tissu et ne nécessitent pas que la mémoire du périphérique soit mappée dans l'espace d'adressage virtuel du processus appelant.

Cette structure fait référence à une région de mémoire de périphérique basée sur DMA-buf. Ce champ n'est utilisable que si l'application a demandé avec succès le support de FI_HMEM et que le drapeau FI_MR_DMABUF est passé à l'appel d'enregistrement de mémoire. Les régions DMA-buf sont des références basées sur des fichiers vers la mémoire du périphérique. De telles régions sont identifiées à travers la structure fi_mr_dmabuf.

struct fi_mr_dmabuf {
    int      fd;
    uint64_t offset;
    size_t   len;
    void     *base_addr;
};

Le fd est le descripteur de fichier associé à la région DMA-buf. L'offset est le décalage dans la région à partir duquel l'enregistrement de mémoire doit commencer. Et len est la taille de la région à enregistrer, en commençant à l'offset. Le base_addr est l'adresse virtuelle de départ alignée sur la page de la région mémoire allouée par le DMA-buf. Si une adresse virtuelle de base n'est pas disponible (par exemple parce que le processus appelant n'a pas mappé la région mémoire dans son espace d'adressage), base_addr peut être défini à NULL.

Le choix de dmabuf plutôt que du champ mr_iov est contrôlé en spécifiant le drapeau FI_MR_DMABUF.

iov_count

Le nombre d'entrées dans le tableau mr_iov. Le nombre maximal de tampons mémoire pouvant être associés à une seule région mémoire est spécifié par l'attribut de domaine mr_iov_limit. Voir fi_domain(3).

access

Indique le type d' opérations que l'extrémité locale ou un pair peut effectuer sur la région mémoire enregistrée. Les permissions d'accès prises en charge sont le OU bit à bit des drapeaux suivants :

FI_SEND
Le tampon mémoire peut être utilisé pour les transferts de données de messages sortants. Cela inclut les opérations d'envoi fi_msg et fi_tagged, ainsi que les opérations fi_collective.
FI_RECV
Le tampon mémoire peut être utilisé pour recevoir des transferts de messages entrants. Cela inclut les opérations de réception fi_msg et fi_tagged, ainsi que les opérations fi_collective.
FI_READ
Le tampon mémoire peut être utilisé comme tampon de résultat pour les opérations de lecture RMA et atomiques côté initiateur. Notez que du point de vue de l'application, le tampon mémoire est écrit par le réseau.
FI_WRITE
Le tampon mémoire peut être utilisé comme tampon source pour les opérations d'écriture RMA et atomiques côté initiateur. Notez que du point de vue de l'application, l'extrémité lit depuis le tampon mémoire et copie les données sur le réseau.
FI_REMOTE_READ
Le tampon mémoire peut être utilisé comme tampon source d'une opération de lecture RMA côté cible. Le contenu du tampon mémoire n'est pas modifié par de telles opérations.
FI_REMOTE_WRITE
Le tampon mémoire peut être utilisé comme tampon cible d'une opération d'écriture RMA ou atomique. Le contenu du tampon mémoire peut être modifié à la suite de telles opérations.
FI_COLLECTIVE
Ce drapeau fournit une indication explicite que le tampon mémoire peut être utilisé avec des opérations collectives. L'utilisation de ce drapeau est requise si le bit mr_mode FI_MR_COLLECTIVE a été défini sur le domaine. Ce drapeau doit être associé à FI_SEND et/ou FI_RECV.

Notez que certains fournisseurs peuvent ne pas faire respecter les permissions d'accès à granularité fine. Par exemple, une région mémoire enregistrée pour l'accès FI_WRITE peut aussi se comporter comme si FI_SEND avait été spécifié. Un assouplissement de l'application de telles permissions est permis, bien que non garanti, à condition que la sécurité soit maintenue.

offset

Le champ offset est réservé à une utilisation future et doit être 0.

requested_key

Une clé d'accès spécifiée par l'application associée à la région mémoire. La clé MR doit être fournie par un processus distant lors de la réalisation d'opérations RMA ou atomiques sur une région mémoire. Les applications peuvent utiliser le champ requested_key pour indiquer qu'une clé spécifique doit être utilisée par le fournisseur. Cela permet aux applications d'utiliser des valeurs de clé bien connues, ce qui peut éviter aux applications d'avoir à échanger et stocker des clés. Le support des clés demandées par l'utilisateur dépend du fournisseur et est déterminé par le drapeau FI_MR_PROV_KEY dans le champ d'attribut de domaine mr_mode. Selon le fournisseur, la clé demandée par l'utilisateur peut être ignorée si la région mémoire est destinée uniquement à un accès local. Un fournisseur peut être incapable de le faire si le matériel supporte les clés demandées par l'utilisateur et que la même clé est utilisée à la fois pour l'accès local et distant.

context

Contexte d'application associé aux opérations d'enregistrement de mémoire asynchrones. Cette valeur est retournée dans le cadre de tout événement asynchrone associé à l'enregistrement. Ce champ est ignoré pour les appels d'enregistrement synchrones.

auth_key_size

La taille de la clé référencée par le champ auth_key en octets, ou 0 si aucune clé d'autorisation n'est donnée. Ce champ est ignoré sauf si le tissu est ouvert avec la version d'API 1.5 ou supérieure.

Si le domaine est ouvert avec FI_AV_AUTH_KEY, auth_key_size doit être égal à sizeof(struct fi_mr_auth_key).

auth_key

Indique la clé à associer à cet enregistrement de mémoire. Les clés d'autorisation sont utilisées pour limiter la communication entre extrémités. Seules les extrémités pairs programmées pour utiliser la même clé d'autorisation peuvent accéder à la région mémoire. La clé d'autorisation du domaine sera utilisée si le auth_key_size fourni est 0. Ce champ est ignoré sauf si le tissu est ouvert avec la version d'API 1.5 ou supérieure.

Dans les cas où une plage VA n'a aucune page qui la supporte, ce qui est pris en charge lorsque FI_MR_ALLOCATED n'est pas défini, le fournisseur peut ne pas connaître la taille de page optimale lors de l'enregistrement. NOTES

L'accès direct à la mémoire d'une application par un pair distant nécessite que l'application enregistre le(s) tampon(s) mémoire ciblé(s). Ceci se fait généralement en appelant l'une des routines fi_mr_reg*. Pour FI_MR_PROV_KEY, le fournisseur renverra une clé qui doit être utilisée par le pair lors de l'accès à la région mémoire. L'application est responsable du transfert de cette clé vers le pair. Si le mode FI_MR_RAW a été défini, la clé doit être récupérée à l'aide de la fonction fi_mr_raw_attr.

FI_MR_RAW permet de prendre en charge les fournisseurs qui nécessitent plus de 8 octets pour leurs clés de protection ou qui ont besoin d'une configuration supplémentaire avant qu'une clé puisse être utilisée pour les transferts. Après qu'une clé brute a été récupérée, elle doit être échangée avec le pair distant. Le pair doit utiliser fi_mr_map_raw pour convertir la clé brute en une clé utilisable de 64 bits. La conversion doit être effectuée même si la clé brute fait 64 bits ou moins.

Les fonctions de support des clés brutes sont utilisables avec toutes les régions mémoire enregistrées, même si FI_MR_RAW n'a pas été défini. Il est recommandé que les applications portables ciblent l'utilisation de ces interfaces ; cependant, leur utilisation entraîne une surcharge supplémentaire en messages et en mémoire, ce qui les rend moins désirables pour les applications hautement évolutives.

Il peut y avoir des cas où le support pair à pair du périphérique ne doit pas être utilisé ou ne peut pas être utilisé, par exemple lorsque la configuration ACS du PCIe ne permet pas le transfert. La variable d'environnement FI_HMEM_DISABLE_P2P peut être définie pour informer Libfabric que les transactions pair à pair ne doivent pas être utilisées. Le fournisseur peut choisir d'effectuer une copie à la place, ou échouera dans le support de FI_HMEM si le fournisseur est incapable de le faire.

L'indicateur suivant peut être spécifié à tout appel d'enregistrement mémoire.

FI_RMA_EVENT
Cet indique que la région mémoire spécifiée sera associée à un compteur de complétion utilisé pour compter les opérations RMA qui accèdent à la MR.
FI_RMA_PMEM
Cet indique que la région mémoire sous-jacente est soutenue par de la mémoire persistante et sera utilisée dans des opérations RMA. Il doit être spécifié si des sémantiques de complétion persistantes ou des transferts de données persistants sont requis lors de l'accès à la région enregistrée.
FI_HMEM_DEVICE_ONLY
Cet indique que la mémoire n'est accessible que par un périphérique. Quel périphérique est spécifié par les champs iface et device de fi_mr_attr. Cela fait référence aux régions mémoire qui ont été allouées à l'aide d'un appel AllocDevice d'API de périphérique (par opposition à l'utilisation de l'allocation hôte ou de l'allocation mémoire unifiée/partagée). Cet indicateur n'est utilisable que pour les domaines ouverts avec le support de capacité FI_HMEM.
FI_HMEM_HOST_ALLOC
Cet indique que la mémoire n'est détenue que par l'hôte. Qu'elle puisse être accessible par le périphérique dépend de l'implémentation. Le champ iface de fi_mr_attr est toujours utilisé pour identifier l'API du périphérique, mais le champ device est ignoré. Cela fait référence aux régions mémoire qui ont été allouées à l'aide d'un appel AllocHost d'API de périphérique (par opposition à une allocation hôte de type malloc, une allocation mémoire unifiée/partagée, ou AllocDevice). Cet indicateur n'est utilisable que pour les domaines ouverts avec le support de capacité FI_HMEM.
FI_MR_DMABUF
Cet indique que la région mémoire à enregistrer est une région soutenue par DMA-buf. Lorsqu'il est défini, la région est spécifiée à travers le champ dmabuf de la structure fi_mr_attr. Cet indicateur n'est utilisable que pour les domaines ouverts avec le support de capacité FI_HMEM.
FI_MR_SINGLE_USE
Cet indique que la région mémoire n'est utilisée que pour une seule opération. Une fois l'opération terminée, la clé associée à la région mémoire est automatiquement invalidée et ne peut plus être utilisée pour un accès distant.
FI_AUTH_KEY
Valable uniquement avec les domaines configurés avec FI_AV_AUTH_KEY. Lorsqu'il est utilisé avec fi_mr_regattr, cet indique que le champ fi_mr_auth_key::src_addr contient une clé d'autorisation fi_addr_t (c'est-à-dire un fi_addr_t renvoyé par fi_av_insert_auth_key) au lieu d'un fi_addr_t de point de terminaison (c'est-à-dire un fi_addr_t renvoyé par fi_av_insert / fi_av_insertsvc / fi_av_remove).

DOMAINES MÉMOIRE

Les domaines mémoire identifient la séparation physique de la mémoire qui peut ou non être accessible à travers le même espace d'adresse virtuel. Traditionnellement, les applications ne traitaient qu'un seul domaine mémoire, celui de la mémoire hôte étroitement couplée aux CPU du système. Avec l'introduction des sous-systèmes mémoire de périphérique et non uniformes, les applications doivent souvent savoir à quel domaine mémoire une adresse virtuelle particulière est mappée.

En règle générale, les périphériques physiques séparés peuvent être considérés comme ayant leurs propres domaines mémoire. Par exemple, une NIC peut avoir de la mémoire accessible à l'utilisateur, et serait considérée comme un domaine mémoire séparé de la mémoire sur un GPU. Les domaines mémoire de la NIC et du GPU sont séparés de la mémoire du système hôte. Les GPU ou accélérateurs de calcul individuels peuvent avoir des domaines mémoire distincts, ou peuvent être connectés de telle manière (par exemple, un fabric spécifique au GPU) que tous les GPU appartiendraient au même domaine mémoire. Malheureusement, l'identification des domaines mémoire est spécifique à chaque système et à sa configuration physique et/ou virtuelle.

Comprendre les domaines mémoire dans les environnements mémoire hétérogènes est important car cela peut impacter l'ordre et la visibilité des données telles que vues par une application. Il est également important de comprendre à quel domaine mémoire une application est le plus étroitement couplée. Dans la plupart des cas, les applications sont étroitement couplées à la mémoire hôte. Cependant, une application s'exécutant directement sur un GPU ou une NIC peut être plus étroitement couplée à la mémoire associée à ces périphériques.

Les régions mémoire sont souvent associées à un seul domaine mémoire. Le domaine est souvent indiqué par les champs iface et device de fi_mr_attr. Bien qu'il soit possible que les pages physiques soutenant une région de mémoire virtuelle migrent entre les domaines mémoire en fonction des motifs d'accès. Par exemple, les pages physiques référencées par une plage d'adresses virtuelles pourraient migrer entre la mémoire hôte et la mémoire GPU, selon l'unité de calcul qui l'utilise activement.

Voir les pages de manuel fi_endpoint(3) et fi_cq(3) pour une discussion supplémentaire sur la sémantique d'ordre des messages, des données et des complétions, y compris l'impact des domaines mémoire.

NAME

fi_mr_regv - register memory regions

SYNOPSIS

#include <rdma/fi_rma.h>

int
fi_mr_regv(struct fid_mr *mr, void *addr, size_t len,
    uint64_t access, uint64_t flags, void *desc, size_t *count);

ARGUMENTS

mr
Resource descriptor of the memory region.
addr
Starting address of the memory region. This argument is only used if desc is NULL.
len
The length of the memory region. This argument is only used if desc is NULL.
access
Memory region access permissions. See fi_mr_reg() for valid flags.
flags
Optional flags that modify behavior. See fi_mr_reg() for valid flags.
desc
Array of struct fi_fregion structures that define the memory regions to be registered. If this argument is NULL, then the memory region is defined by the addr and len arguments.
count
On input, the size of the desc array. On return, the number of regions that were successfully registered.

DESCRIPTION

The fi_mr_regv call registers one or more memory regions for use with Remote Direct Memory Access (RDMA) operations. The memory regions are specified either by a contiguous block of memory defined by addr and len, or by an array of struct fi_fregion structures.

The fi_fregion structure is defined as follows:

struct fi_fregion {
    void *addr;
    size_t len;
};

The access and flags arguments are the same as those used by fi_mr_reg.

The count argument specifies the number of struct fi_fregion entries in the desc array. On successful return, count will be updated to reflect the number of regions that were actually registered.

MEMORY REGION ATTRIBUTES

The following flags can be specified for the access parameter:

FI_READ
The memory region can be read by a remote host.
FI_WRITE
The memory region can be written to by a remote host.
FI_REMOTE_READ
The memory region can be read by a remote host.
FI_REMOTE_WRITE
The memory region can be written to by a remote host.
FI_SENT_WRITE
The memory region can be written to by a remote host.
FI_RECV_WRITE
The memory region can be written to by a remote host.
FI_SUM_WRITE
The memory region can be written to by a remote host.
FI_COMPARE_EXCHANGE
The memory region supports atomic compare and swap operations.
FI_READ_ATOMIC
The memory region supports atomic read operations.
FI_WRITE_ATOMIC
The memory region supports atomic write operations.

The following flags can be specified for the flags parameter:

FI_MR_LOCAL
The memory region is local to the process. This flag should be set if the application intends to use the memory region for local access only. This can improve performance by allowing the fabric provider to avoid certain registration overheads.
FI_MR_VIRT_ALLOC
The memory region is virtually allocated. This flag should be set if the application intends to register memory that is virtually allocated, such as memory allocated using fi_alloc. This flag is typically used in conjunction with FI_HMEM.
FI_MR_ANCHOR
The memory region is an anchor point for subsequent memory registrations. This flag is typically used with registered memory that is allocated by the fabric provider, such as pinned memory.

NOTES

The fi_mr_regv function is a more flexible version of fi_mr_reg that allows applications to register multiple, potentially non-contiguous, memory regions with a single call. This can be useful for registering memory that has been allocated in chunks, or for registering memory that is scattered across different address spaces.

If the FI_MR_LOCAL flag is specified, the memory region is assumed to be local to the process and can be accessed directly by the application. This can improve performance by allowing the fabric provider to avoid certain registration overheads.

If the FI_MR_VIRT_ALLOC flag is specified, the memory region is assumed to be virtually allocated. This flag is typically used in conjunction with FI_HMEM, which provides hardware memory management capabilities.

If the FI_MR_ANCHOR flag is specified, the memory region is treated as an anchor point for subsequent memory registrations. This flag is typically used with registered memory that is allocated by the fabric provider, such as pinned memory.

The memory regions registered with fi_mr_regv can be unbound using fi_mr_unreg.

FLAGS

See fi_mr_reg.

MEMORY DOMAINS

Memory regions are associated with memory domains. Memory domains are created using fi_domain_open.

RETURN VALUES

On success, fi_mr_regv returns a handle to the registered memory region. On failure, it returns a negative error value.

ERRORS

See fi_mr_reg.

MEMORY REGISTRATION CACHE

An additional registration cache is required to track this device memory, or device memory cannot be cached.

As a general rule, if hardware requires the FI_MR_LOCAL mode bit described above, but this is not supported by the application, a memory registration cache may be in use. The following environment variables may be used to configure registration caches.

FI_MR_CACHE_MAX_SIZE
This defines the total number of bytes for all memory regions that may be tracked by the cache. If not set, the cache has no limit on how many bytes may be registered and cached. Setting this will reduce the amount of memory that is not actively being used as part of a data transfer that is registered with a provider. By default, the cache size is unlimited.
FI_MR_CACHE_MAX_COUNT
This defines the total number of memory regions that may be registered with the cache. If not set, a default limit is chosen. Setting this will reduce the number of regions that are registered, regardless of their size, which are not actively being used as part of a data transfer. Setting this to zero will disable registration caching.
FI_MR_CACHE_MONITOR
The cache monitor is responsible for detecting system memory (FI_HMEM_SYSTEM) changes made between the virtual addresses used by an application and the underlying physical pages. Valid monitor options are: userfaultfd, memhooks, kdreg2, and disabled. Selecting disabled will turn off the registration cache. Userfaultfd is a Linux kernel feature used to report virtual to physical address mapping changes to user space. Memhooks operates by intercepting relevant memory allocation and deallocation calls which may result in the mappings changing, such as malloc, mmap, free, etc. Note that memhooks operates at the elf linker layer, and does not use glibc memory hooks. Kdreg2 is supplied as a loadable Linux kernel module.
FI_MR_CUDA_CACHE_MONITOR_ENABLED
The CUDA cache monitor is responsible for detecting CUDA device memory (FI_HMEM_CUDA) changes made between the device virtual addresses used by an application and the underlying device physical pages. Valid monitor options are: 0 or 1. Note that the CUDA memory monitor requires a CUDA toolkit version with unified virtual addressing enabled.
FI_MR_ROCR_CACHE_MONITOR_ENABLED
The ROCR cache monitor is responsible for detecting ROCR device memory (FI_HMEM_ROCR) changes made between the device virtual addresses used by an application and the underlying device physical pages. Valid monitor options are: 0 or 1. Note that the ROCR memory monitor requires a ROCR version with unified virtual addressing enabled.
FI_MR_ZE_CACHE_MONITOR_ENABLED
The ZE cache monitor is responsible for detecting oneAPI Level Zero device memory (FI_HMEM_ZE) changes made between the device virtual addresses used by an application and the underlying device physical pages. Valid monitor options are: 0 or 1.

More direct access to the internal registration cache is possible through the fi_open() call, using the “mr_cache” service name. Once opened, custom memory monitors may be installed. A memory monitor is a component of the cache responsible for detecting changes in virtual to physical address mappings. Some level of control over the cache is possible through the above mentioned environment variables.
