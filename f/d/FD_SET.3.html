DESCRIPTIO

N

AVERTISSEMENT : select() ne peut surveiller que les numéros de descripteurs de fichiers inférieurs à FD_SETSIZE (1024) — une limite déraisonnablement basse pour de nombreuses applications modernes — et cette limitation ne changera pas. Toutes les applications modernes devraient plutôt utiliser poll(2) ou epoll(7), qui ne souffrent pas de cette

limitation.

select() permet à un programme de surveiller plusieurs descripteurs de fichiers, en attendant qu'un ou plusieurs descripteurs de fichiers deviennent « prêts » pour une certaine classe d'opération d'entrée-sortie (par ex., lecture possible). Un descripteur de fichier est considéré comme prêt s'il est possible d'effectuer l'opération d'entrée-sortie correspondante (par ex., read(2), ou un write(2) suffisamment petit) sans

bloquer.

fd_se

t

Un type de structure pouvant représenter un ensemble de descripteurs de fichiers. Selon POSIX, le nombre maximal de descripteurs de fichiers dans une structure fd_set est la valeur de la macro FD_SETSIZ

Ensembles de descripteurs de

fichiers

Les arguments principaux de select() sont trois « ensembles » de descripteurs de fichiers (déclarés avec le type fd_set), qui permettent à l'appelant d'attendre trois classes d'événements sur l'ensemble spécifié de descripteurs de fichiers. Chacun des arguments fd_set peut être spécifié comme NULL si aucun descripteur de fichier n'est à surveiller pour la classe d'événements

correspondante.

Bien noter : Au retour, chacun des ensembles de descripteurs de fichiers est modifié sur place pour indiquer quels descripteurs de fichiers sont actuellement « prêts ». Ainsi, si l'on utilise select() dans une boucle, les ensembles doivent être réinitialisés avant chaque

appel.

Le contenu d'un ensemble de descripteurs de fichiers peut être manipulé à l'aide des macros suivantes

L'appel système pselect() permet à une application d'attendre en toute sécurité jusqu'à ce qu'un descripteur de fichier devienne prêt ou jusqu'à ce qu'un signal soit

Le fonctionnement de select() et pselect() est identique, à ces trois différences près

•
select() utilise un délai d'attente qui est un struct timeval (avec secondes et microsecondes), tandis que pselect() utilise un struct timespec (avec secondes et nanosecondes)

•
select() peut mettre à jour l'argument timeout pour indiquer combien de temps restait. pselect() ne modifie pas cet

BUGS

POSIX permet à une implémentation de définir une limite supérieure, annoncée via la constante FD_SETSIZE, sure de descripteurs de fichiers pouvant être spécifiés dans un ensemble de descripteurs de fichiers. Le noyau Linux n'impose aucune limite fixe, mais l'implémentation glibc fait de fd_set un type de taille fixe, avec FD_SETSIZE défini à 1024, et les macros FD_*() fonctionnant selon cette limite. Pour surveiller des descripteurs de fichiers supérieurs à 1023, utilisez plutôt poll(2) ou epoll(

7).

L'implémentation des arguments fd_set en tant qu'arguments valeur-résultat est une erreur de conception qui est évitée dans poll(2) et epoll(

7).

Selon POSIX, select() devrait vérifier tous les descripteurs de fichiers spécifiés dans les trois ensembles de descripteurs de fichiers, jusqu'à la limite nfds-1. Cependant, l'implémentation actuelle ignore tout descripteur de fichier dans ces ensembles qui est supérieur au numéro de descripteur de fichier maximum que le processus a actuellement ouvert. Selon POSIX, tout tel descripteur de fichier spécifié dans l'un des ensembles devrait entraîner l'erreur EBADF

.

À partir de glibc 2.1, glibc a fourni une émulation de pselect() implémentée à l'aide de sigprocmask(2) et select(). Cette implémentation est restée vulnérable à la condition de concurrence même que pselect() a été conçu pour prévenir. Les versions modernes de glibc utilisent l'appel système (exempt de condition de concurrence) pselect() sur les noyaux où il est

fourni.

Sur Linux, select() peut signaler un descripteur de fichier de socket comme « prêt pour la lecture », alors qu'une lecture subséquente se bloque néanmoins. Cela pourrait par exemple se produire lorsque des données sont arrivées mais qu'à l'examen, elles ont une somme de contrôle incorrecte et sont rejetées. Il peut y avoir d'autres circonstances dans lesquelles un descripteur de fichier est signalé à tort comme prêt. Il peut donc être plus sûr d'utiliser O_NONBLOCK sur les sockets qui ne devraient pas

bloquer.

Sur Linux, select() modifie également timeout si l'appel est interrompu par un gestionnaire de signal (c'est-à-dire le retour d'erreur EINTR). Cela n'est pas autorisé par POSIX.1. L'appel système Linux pselect() a le même comportement, mais l'enveloppe glibc masque ce comportement en copiant internément le timeout dans une variable locale et en pas

sant cette variable à
l'appel système.

EXEMPLE

S 
#include <stdio.h>
#include <stdlib.h>
#include <sys/select.h>
#include <sys/time.h>
int
main(void)
{
    int             retval;
    fd_set          rfds;
    struct timeval  tv;
    /* Surveiller stdin (fd 0) pour voir quand il a des données en entrée.  */
    FD_ZERO(&rfds);
    FD_SET(0, &rfds);
    /* Attendre jusqu'à cinq secondes.  */
    tv.tv_sec = 5;
    tv.tv_usec = 0;
    retval = select(1, &rfds, NULL, NULL, &tv);
    /* Ne vous fiez pas à la valeur de tv maintenant ! */
    if (retval == -1)
        perror("select()");
    else if (retval)
        printf("Data is available now.\n");
        /* FD_ISSET(0, &rfds) sera vrai.  */
    else
        printf("No data within five seconds.\n");
    exit(EXIT_SUCCESS);
}
