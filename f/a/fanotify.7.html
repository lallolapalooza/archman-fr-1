NOM

fanotify - surveillance des événements du système de fichiers

DESCRIPTION

L'API fanotify fournit la notification et l'interception des événements du système de fichiers. Les cas d'utilisation incluent l'analyse antivirus et la gestion hiérarchique du stockage. Dans l'API fanotify d'origine, seul un ensemble limité d'événements était pris en charge. En particulier, il n'y avait pas de prise en charge des événements de création, de suppression et de déplacement. La prise en charge de ces événements a été ajoutée dans Linux 5.1. (Voir inotify(7) pour les détails d'une API qui notifiait ces événements avant Linux 5.1.)

Les capacités supplémentaires par rapport à l'API inotify(7) incluent la possibilité de surveiller tous les objets d'un système de fichiers monté, la possibilité de prendre des décisions sur les permissions d'accès et la possibilité de lire ou de modifier des fichiers avant leur accès par d'autres applications.

Les appels système suivants sont utilisés avec cette API : fanotify_init(2), fanotify_mark(2), read(2), write(2), et close(2).

fanotify_init(), fanotify_mark(), et les groupes de notification

L'appel système fanotify_init(2) crée et initialise un groupe de notification fanotify et renvoie un descripteur de fichier s'y référant.

Un groupe de notification fanotify est un objet interne au noyau qui contient une liste de fichiers, répertoires, systèmes de fichiers et points de montage pour lesquels des événements doivent être créés.

Pour chaque entrée d'un groupe de notification fanotify, deux masques binaires existent : le masque mark et le masque ignore. Le masque mark définit les activités de fichiers pour lesquelles un événement doit être créé. Le masque ignore définit les activités pour lesquelles aucun événement ne doit être généré. L'existence de ces deux types de masques permet de marquer un système de fichiers, un point de montage ou un répertoire pour recevoir des événements, tout en ignorant simultanément les événements pour des objets spécifiques sous un point de montage ou un répertoire.

L'appel système fanotify_mark(2) ajoute un fichier, un répertoire, un système de fichiers ou un point de montage à un groupe de notification et spécifie quels événements doivent être rapportés (ou ignorés), ou supprime ou modifie une telle entrée.

Une utilisation possible du masque ignore est pour un cache de fichiers. Les événements intéressants pour un cache de fichiers sont la modification d'un fichier et la fermeture de celui-ci. Par conséquent, le répertoire ou le point de montage mis en cache doit être marqué pour recevoir ces événements. Après avoir reçu le premier événement informant qu'un fichier a été modifié, l'entrée de cache correspondante sera invalidée. Plus aucun événement de modification pour ce fichier n'est intéressant jusqu'à ce que le fichier soit fermé. Par conséquent, l'événement de modification peut être ajouté au masque ignore. Lors de la réception de l'événement de fermeture, l'événement de modification peut être retiré du masque ignore et l'entrée du cache de fichier peut être mise à jour.

Les entrées dans les groupes de notification fanotify font référence aux fichiers et répertoires via leur numéro d'inode et aux points de montage via leur ID de montage. Si des fichiers ou des répertoires sont renommés ou déplacés à l'intérieur du même point de montage, les entrées respectives survivent. Si des fichiers ou des répertoires sont supprimés ou déplacés vers un autre point de montage ou si des systèmes de fichiers ou des points de montage sont démontés, les entrées correspondantes sont supprimées.

La file d'attente des événements

Au fur et à mesure que les événements se produisent sur les objets du système de fichiers surveillés par un groupe de notification, le système fanotify génère des événements qui sont collectés dans une file d'attente. Ces événements peuvent ensuite être lus (en utilisant read(2) ou une fonction similaire) à partir du descripteur de fichier fanotify retourné par fanotify_init(2).

Deux types d'événements sont générés : les événements de notification et les événements de permission. Les événements de notification sont purement informatifs et ne nécessitent aucune action de la part de l'application réceptrice, à une exception près : si un descripteur de fichier valide est fourni dans un événement générique, le descripteur de fichier doit être fermé. Les événements de permission sont des requêtes à l'application réceptrice pour décider si l'autorisation d'accéder à un fichier doit être accordée. Pour ces événements, le destinataire doit écrire une réponse qui décide si l'accès est accordé ou non.

Un événement est retiré de la file d'attente des événements du groupe fanotify lorsqu'il a été lu. Les événements de permission qui ont été lus sont conservés dans une liste interne du groupe fanotify jusqu'à ce qu'une décision de permission ait été prise en écrivant dans le descripteur de fichier fanotify ou que le descripteur de fichier fanotify soit fermé.

Lecture des événements fanotify

Appeler read(2) pour le descripteur de fichier retourné par fanotify_init(2) bloque (si le drapeau FAN_NONBLOCK n'est pas spécifié dans l'appel à fanotify_init(2)) jusqu'à ce qu'un événement de fichier se produise ou que l'appel soit interrompu par un signal (voir signal(7)).

Après un appel réussi à read(2), le tampon de lecture contient une ou plusieurs des structures suivantes :


struct fanotify_event_metadata {
    __u32 event_len;
    __u8 vers;
    __u8 reserved;
    __u16 metadata_len;
    __aligned_u64 mask;
    __s32 fd;
    __s32 pid;
};

Les enregistrements d'informations sont des informations supplémentaires qui peuvent être fournies avec la structure générique fanotify_event_metadata. Les flags passés à fanotify_init(2) influencent le type d'enregistrements d'informations qui peuvent être retournés pour un événement. Par exemple, si un groupe de notification est initialisé avec FAN_REPORT_FID ou FAN_REPORT_DIR_FID, alors les écouteurs d'événements doivent également s'attendre à recevoir une structure fanotify_event_info_fid avec la structure fanotify_event_metadata, où les descripteurs de fichiers sont utilisés pour identifier les objets du système de fichiers plutôt que des descripteurs de fichiers. Les enregistrements d'informations peuvent également être empilés, ce qui signifie que l'utilisation des différents drapeaux FAN_REPORT_* conjointement est prise en charge. Dans de tels cas, plusieurs enregistrements d'informations peuvent être retournés pour un événement avec la structure générique fanotify_event_metadata. Par exemple, si un groupe de notification est initialisé avec FAN_REPORT_TARGET_FID et FAN_REPORT_PIDFD, alors un écouteur d'événements doit s'attendre à recevoir jusqu'à deux enregistrements d'informations fanotify_event_info_fid et un enregistrement d'informations fanotify_event_info_pidfd avec la structure générique fanotify_event_metadata. Il est important de noter que fanotify ne garantit pas l'ordre des enregistrements d'informations lorsqu'un groupe de notification est initialisé avec une configuration basée sur l'empilement. Chaque enregistrement d'informations possède une structure imbriquée de type fanotify_event_info_header. Il est impératif pour les écouteurs d'événements d'inspecter le champ info_type de cette structure afin de déterminer le type d'enregistrement d'informations qui a été reçu pour un événement donné.

Dans les cas où un groupe fanotify identifie les objets du système de fichiers par des descripteurs de fichier, les écouteurs d'événements doivent également s'attendre à recevoir un ou plusieurs des objets d'enregistrement d'informations ci-dessous avec la structure générique fanotify_event_metadata dans le tampon de lecture :


struct fanotify_event_info_fid {
    struct fanotify_event_info_header hdr;
    __kernel_fsid_t fsid;
    unsigned char handle[];
};

Dans les cas où un groupe fanotify est initialisé avec FAN_REPORT_PIDFD, les écouteurs d'événements doivent s'attendre à recevoir l'objet d'enregistrement d'informations ci-dessous avec la structure générique fanotify_event_metadata dans le tampon de lecture :


struct fanotify_event_info_pidfd {
        struct fanotify_event_info_header hdr;
        __s32 pidfd;
};

Dans les cas où un groupe fanotify est initialisé avec FAN_REPORT_MNT, les écouteurs d'événements doivent s'attendre à recevoir l'objet d'enregistrement d'informations ci-dessous avec la structure générique fanotify_event_metadata dans le tampon de lecture. Cette structure est définie comme suit :


struct fanotify_event_info_mnt {
    struct fanotify_event_info_header hdr;
    __u64 mnt_id;
};

En cas d'événement FAN_FS_ERROR, un enregistrement d'informations supplémentaire décrivant l'erreur qui s'est produite est retourné avec la structure générique fanotify_event_metadata dans le tampon de lecture. Cette structure est définie comme suit :


struct fanotify_event_info_error {
    struct fanotify_event_info_header hdr;
    __s32 error;
    __u32 error_count;
};

lass="Pp">En cas d'événements FAN_PRE_ACCESS, un enregistrement d'informations supplémentaire décrivant la plage d'accès est renvoyé aux côtés de la structure générique fanotify_event_metadata dans le tampon de lecture. Cette structure est définie comme suit :


struct fanotify_event_info_range {
    struct fanotify_event_info_header hdr;
    __u32 pad;
    __u64 offset;
    __u64 count;
};

Tous les enregistrements d'informations contiennent une structure imbriquée de type fanotify_event_info_header. Cette structure contient des méta-informations sur l'enregistrement d'informations qui peuvent avoir été renvoyées avec la structure générique fanotify_event_metadata. Cette structure est définie comme suit :


struct fanotify_event_info_header {
	__u8 info_type;
	__u8 pad;
	__u16 len;
};

Pour des raisons de performance, il est recommandé d'utiliser une grande taille de tampon (par exemple, 4096 octets), afin que plusieurs événements puissent être récupérés par une seule opération read(2).

La valeur de retour de read(2) est le nombre d'octets placés dans le tampon, ou -1 en cas d'erreur (mais voir BUGS).

Les champs de la structure fanotify_event_metadata sont les suivants :

event_len
Ceci est la taille des données pour l'événement actuel et le décalage vers l'événement suivant dans le tampon. À moins que le groupe n'identifie les objets du système de fichiers par descripteurs de fichier, la valeur de event_len est toujours FAN_EVENT_METADATA_LEN. Pour un groupe qui identifie les objets du système de fichiers par descripteurs de fichier, event_len inclut également les enregistrements d'identifiants de fichier de taille variable.
vers
Ce champ contient un numéro de version pour la structure. Il doit être comparé à FANOTIFY_METADATA_VERSION pour vérifier que les structures renvoyées au moment de l'exécution correspondent aux structures définies au moment de la compilation. En cas de décalage, l'application doit abandonner l'utilisation du descripteur de fichier fanotify.
reserved
Ce champ n'est pas utilisé.
metadata_len
Ceci est la taille de la structure. Ce champ a été introduit pour faciliter l'implémentation d'en-têtes optionnels par type d'événement. Aucun en-tête optionnel de ce type n'existe dans l'implémentation actuelle.
mask
Ceci est un masque de bits décrivant l'événement (voir ci-dessous).
fd
Ceci est un descripteur de fichier ouvert pour l'objet accédé, ou FAN_NOFD si un dépassement de file d'attente s'est produit. Avec un groupe fanotify qui identifie les objets du système de fichiers par descripteurs de fichier, les applications doivent s'attendre à ce que cette valeur soit définie à FAN_NOFD pour chaque événement reçu. Le descripteur de fichier peut être utilisé pour accéder au contenu du fichier ou répertoire surveillé. L'application de lecture est responsable de la fermeture de ce descripteur de fichier.
Lors de l'appel à fanotify_init(2), l'appelant peut spécifier (via l'argument event_f_flags) divers indicateurs d'état de fichier qui doivent être définis sur la description de fichier correspondant à ce descripteur de fichier. De plus, l'indicateur d'état de fichier (interne au noyau) FMODE_NONOTIFY est défini sur la description de fichier ouverte. Cet indicateur supprime la génération d'événements fanotify. Par conséquent, lorsque le récepteur de l'événement fanotify accède au fichier ou répertoire notifié à l'aide de ce descripteur de fichier, aucun événement supplémentaire ne sera créé.
Lorsqu'un groupe fanotify est initialisé à l'aide de FAN_REPORT_FD_ERROR, ce champ contiendra une valeur d'erreur négative si un descripteur de fichier n'a pas pu être ouvert et en cas de dépassement de file d'attente, la valeur sera -EBADF.
pid
Si l'indicateur FAN_REPORT_TID a été défini dans fanotify_init(2), il s'agit du TID du thread qui a provoqué l'événement. Sinon, il s'agit du PID du processus qui a provoqué l'événement.

Un programme écoutant les événements fanotify peut comparer ce PID au PID renvoyé par getpid(2), pour déterminer si l'événement est causé par l'écouteur lui-même, ou s'il est dû à un accès de fichier par un autre processus.

Le masque de bits dans mask indique quels événements se sont produits pour un seul objet du système de fichiers. Plusieurs bits peuvent être définis dans ce masque, si plus d'un événement s'est produit pour l'objet du système de fichiers surveillé. En particulier, les événements consécutifs pour le même objet du système de fichiers et provenant du même processus peuvent être fusionnés en un seul événement, à l'exception du fait que deux événements de permission ne sont jamais fusionnés en une seule entrée de file d'attente.

Les bits qui peuvent apparaître dans mask sont les suivants :

FAN_ACCESS
Un fichier ou un répertoire (mais voir BUGS) a été accédé (lu).
FAN_OPEN
Un fichier ou un répertoire a été ouvert.
FAN_OPEN_EXEC
Un fichier a été ouvert dans l'intention d'être exécuté. Voir NOTES dans fanotify_mark(2) pour plus de détails.
FAN_ATTRIB
Les métadonnées d'un fichier ou d'un répertoire ont été modifiées.
FAN_CREATE
Un fichier ou un répertoire enfant a été créé dans un parent surveillé.
FAN_DELETE
Un fichier ou un répertoire enfant a été supprimé dans un parent surveillé.
FAN_DELETE_SELF
Un fichier ou un répertoire surveillé a été supprimé.
FAN_RENAME
Un fichier ou un répertoire a été déplacé vers ou depuis un répertoire parent surveillé.
FAN_MOVED_FROM
Un fichier ou un répertoire a été déplacé d'un répertoire parent surveillé.
FAN_MOVED_TO
Un fichier ou un répertoire a été déplacé vers un répertoire parent surveillé.
FAN_MOVE_SELF
Un fichier ou un répertoire surveillé a été déplacé.

FAN_ACCESS_PERM
Une application souhaite lire un fichier ou un répertoire, par exemple en utilisant read(2) ou readdir(2). Le lecteur doit écrire une réponse (comme décrit ci-dessous) qui détermine si la permission d'accéder à l'objet du système de fichiers doit être accordée.
FAN_OPEN_PERM
Une application souhaite ouvrir un fichier ou un répertoire. Le lecteur doit écrire une réponse qui détermine si la permission d'ouvrir l'objet du système de fichiers doit être accordée.
FAN_OPEN_EXEC_PERM
Une application souhaite ouvrir un fichier pour exécution. Le lecteur doit écrire une réponse qui détermine si la permission d'ouvrir l'objet du système de fichiers pour exécution doit être accordée. Voir NOTES dans fanotify_mark(2) pour plus de détails.

Pour vérifier tout événement de fermeture, le masque de bits suivant peut être utilisé :

FAN_CLOSE
Un fichier a été fermé. Ceci est un synonyme de :

FAN_CLOSE_WRITE | FAN_CLOSE_NOWRITE

Pour vérifier tout événement de déplacement, le masque de bits suivant peut être utilisé :

FAN_MOVE
Un fichier ou un répertoire a été déplacé. Ceci est un synonyme de :

FAN_MOVED_FROM | FAN_MOVED_TO

Les bits suivants peuvent apparaître dans mask uniquement en conjonction avec d'autres bits de type d'événement :

FAN_ONDIR

Voir fanotify_mark(2) pour plus de détails. L'indicateur FAN_ONDIR n'est rapporté dans un masque d'événement que si le groupe fanotify identifie les objets du système de fichiers par descripteurs de fichier.

NOTE

S

L'API fanotify n'est disponible que si le noyau a été compilé avec l'option de configuration CONFIG_FANOTIFY activée. De plus, la gestion des permissions fanotify n'est disponible que si l'option de configuration CONFIG_FANOTIFY_ACCESS_PERMISSIONS est

activée.

Limitations et

avertissements

Fanotify ne signale que les événements déclenchés par un programme en espace utilisateur à travers l'API du système de fichiers. Par conséquent, il ne détecte pas les événements distants qui se produisent sur les systèmes de fichiers

réseau.

L'API fanotify ne signale pas les accès aux fichiers et les modifications qui peuvent survenir en raison de mmap(2), msync(2) et munmap(

2).

Les événements pour les répertoires ne sont créés que si le répertoire lui-même est ouvert, lu et fermé. L'ajout, la suppression ou la modification des enfants d'un répertoire marqué ne crée pas d'événements pour le répertoire surveillé

lui-même.

La surveillance fanotify des répertoires n'est pas récursive : pour surveiller les sous-répertoires d'un répertoire, des marques supplémentaires doivent être créées. L'événement FAN_CREATE peut être utilisé pour détecter lorsqu'un sous-répertoire a été créé sous un répertoire marqué. Une marque supplémentaire doit alors être définie sur le sous-répertoire nouvellement créé. Cette approche est sujette à des conditions de course, car elle peut perdre des événements qui se sont produits à l'intérieur du sous-répertoire nouvellement créé, avant qu'une marque ne soit ajoutée à ce sous-répertoire. La surveillance des points de montage offre la capacité de surveiller un arborescence de répertoires complète sans conditions de course. La surveillance des systèmes de fichiers offre la capacité de surveiller les modifications effectuées depuis n'importe quel montage d'une instance de système de fichiers sans conditions de

course.

La file d'attente des

événements peut débord
er. Dans ce cas, les é
vénements sont perdus.

BOGUE

S

Avant Linux 3.19, fallocate(2) ne générait pas d'événements fanotify. Depuis Linux 3.19, les appels à fallocate(2) génèrent des événements FAN_MODIFY

.

En tant que Linux 3.17, les bogues suivants existent

:
•
Sur Linux, un objet de système de fichiers peut être accessible par plusieurs chemins, par exemple, une partie d'un système de fichiers peut être remontée en utilisant l'option --bind de mount(8). Un écouteur qui a marqué un point de montage ne sera notifié que des événements déclenchés pour un objet de système de fichiers en utilisant le même point de montage. Tout autre événement passera
inaperçu.
•
Lorsqu'un événement est généré, aucune vérification n'est effectuée pour voir si l'identifiant utilisateur du processus receveur est autorisé à lire ou écrire le fichier avant de transmettre un descripteur de fichier pour ce fichier. Cela pose un risque de sécurité lorsque la capacité CAP_SYS_ADMIN est définie pour les programmes exécutés par des utilisateurs non
privilégiés.
•
Si un appel à read(2) traite plusieurs événements de la file fanotify et qu'une erreur se produit, la valeur de retour sera la taille totale des événements copiés avec succès dans le tampon de l'espace utilisateur avant que l'erreur ne se produise. La valeur de retour ne sera pas -1, et errno ne sera pas défini. Ainsi, l
'application de lectu
re n'a aucun moyen d

#define _GNU_SOURCE     /* Nécessaire pour obtenir la définition de O_LARGEFILE */
#include <errno.h>
#include <fcntl.h>
#include <limits.h>
#include <poll.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/fanotify.h>
#include <unistd.h>
/* Lire tous les événements fanotify disponibles depuis le descripteur de fichier 'fd'.  */
static void
handle_events(int fd)
{
    const struct fanotify_event_metadata *metadata;
    struct fanotify_event_metadata buf[200];
    ssize_t size;
    char path[PATH_MAX];
    ssize_t path_len;
    char procfd_path[PATH_MAX];
    struct fanotify_response response;
    /* Boucle tant que des événements peuvent être lus depuis le descripteur de fichier fanotify.  */
    for (;;) {
        /* Lire quelques événements.  */
        size = read(fd, buf, sizeof(buf));
        if (size == -1 && errno != EAGAIN) {
            perror("read");
            exit(EXIT_FAILURE);
        }
        /* Vérifier si la fin des données disponibles est atteinte.  */
        if (size <= 0)
            break;
        /* Pointer vers le premier événement dans le tampon.  */
        metadata = buf;
        /* Boucler sur tous les événements dans le tampon.  */
        while (FAN_EVENT_OK(metadata, size)) {
            /* Vérifier que les structures d'exécution et de compilation correspondent.  */
            if (metadata->vers != FANOTIFY_METADATA_VERSION) {
                fprintf(stderr,
                        "Incompatibilité de la version des métadonnées fanotify.\n");
                exit(EXIT_FAILURE);
            }
            /* metadata->fd contient soit FAN_NOFD, indiquant un
               débordement de file d'attente, soit un descripteur de fichier (un entier
               non négatif).  Ici, nous ignorons simplement le débordement de file d'attente.  */
            if (metadata->fd >= 0) {
                /* Gérer l'événement de permission d'ouverture.  */
                if (metadata->mask & FAN_OPEN_PERM) {
                    printf("FAN_OPEN_PERM: ");
                    /* Autoriser l'ouverture du fichier.  */
                    response.fd = metadata->fd;
                    response.response = FAN_ALLOW;
                    write(fd, &response, sizeof(response));
                }
                /* Gérer l'événement de fermeture d'un fichier accessible en écriture.  */
                if (metadata->mask & FAN_CLOSE_WRITE)
                    printf("FAN_CLOSE_WRITE: ");
                /* Récupérer et imprimer le chemin du fichier accédé.  */
                snprintf(procfd_path, sizeof(procfd_path),
                         "/proc/self/fd/%d", metadata->fd);
                path_len = readlink(procfd_path, path,
                                    sizeof(path) - 1);
                if (path_len == -1) {
                    perror("readlink");
                    exit(EXIT_FAILURE);
                }
                path[path_len] = '\0';
                printf("Fichier %s\n", path);
                /* Fermer le descripteur de fichier de l'événement.  */
                close(metadata->fd);
            }
            /* Passer à l'événement suivant.  */
            metadata = FAN_EVENT_NEXT(metadata, size);
        }
    }
}
int
main(int argc, char *argv[])
{
    char buf;
    int fd, poll_num;
    nfds_t nfds;
    struct pollfd fds[2];
    /* Vérifier que le point de montage est fourni.  */
    if (argc != 2) {
        fprintf(stderr, "Usage: %s MOUNT\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    printf("Appuyez sur la touche entrée pour terminer.\n");
    /* Créer le descripteur de fichier pour accéder à l'API fanotify.  */
    fd = fanotify_init(FAN_CLOEXEC | FAN_CLASS_CONTENT | FAN_NONBLOCK,
                       O_RDONLY | O_LARGEFILE);
    if (fd == -1) {
        perror("fanotify_init");
        exit(EXIT_FAILURE);
    }
    /* Marquer le montage pour:
       - les événements de permission avant l'ouverture des fichiers
       - les événements de notification après la fermeture d'un
         descripteur de fichier accessible en écriture.  */
    if (fanotify_mark(fd, FAN_MARK_ADD | FAN_MARK_MOUNT,
                      FAN_OPEN_PERM | FAN_CLOSE_WRITE, AT_FDCWD,
                      argv[1]) == -1) {
        perror("fanotify_mark");
        exit(EXIT_FAILURE);
    }
    /* Préparer pour le sondage.  */
    nfds = 2;
    fds[0].fd = STDIN_FILENO;       /* Entrée console */
    fds[0].events = POLLIN;
    fds[1].fd = fd;                 /* Entrée fanotify */
    fds[1].events = POLLIN;
    /* C'est la boucle pour attendre les événements entrants.  */
    printf("Écoute des événements.\n");
    while (1) {
        poll_num = poll(fds, nfds, -1);
        if (poll_num == -1) {
            if (errno == EINTR)     /* Interrompu par un signal */
                continue;           /* Redémarrer poll() */
            perror("poll");         /* Erreur inattendue */
            exit(EXIT_FAILURE);
        }
        if (poll_num > 0) {
            if (fds[0].revents & POLLIN) {
                /* L'entrée console est disponible: vider stdin et quitter.  */
                while (read(STDIN_FILENO, &buf, 1) > 0 && buf != '\n')
                    continue;
                break;
            }
            if (fds[1].revents & POLLIN) {
                /* Les événements fanotify sont disponibles.  */
                handle_events(fd);
            }
        }
    }
    printf("Écoute des événements arrêtée.\n");
    exit(EXIT_SUCCESS);
}

#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <limits.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <sys/fanotify.h>
#include <unistd.h>
#define BUF_SIZE 256
int
main(int argc, char *argv[])
{
    int fd, ret, event_fd, mount_fd;
    ssize_t size, path_len;
    char path[PATH_MAX];
    char procfd_path[PATH_MAX];
    char events_buf[BUF_SIZE];
    struct file_handle *file_handle;
    struct fanotify_event_metadata *metadata;
    struct fanotify_event_info_fid *fid;
    const char *file_name;
    struct stat sb;
    if (argc != 2) {
        fprintf(stderr, "Nombre invalide d'arguments de ligne de commande.\n");
        exit(EXIT_FAILURE);
    }
    mount_fd = open(argv[1], O_DIRECTORY | O_RDONLY);
    if (mount_fd == -1) {
        perror(argv[1]);
        exit(EXIT_FAILURE);
    }
    /* Créer un descripteur de fichier fanotify avec FAN_REPORT_DFID_NAME comme
       drapeau afin que le programme puisse recevoir des événements fid avec le
       nom de l'entrée de répertoire.  */
    fd = fanotify_init(FAN_CLASS_NOTIF | FAN_REPORT_DFID_NAME, 0);
    if (fd == -1) {
        perror("fanotify_init");
        exit(EXIT_FAILURE);
    }
    /* Placer une marque sur l'objet du système de fichiers fourni dans argv[1].  */
    ret = fanotify_mark(fd, FAN_MARK_ADD | FAN_MARK_ONLYDIR,
                        FAN_CREATE | FAN_ONDIR,
                        AT_FDCWD, argv[1]);
    if (ret == -1) {
        perror("fanotify_mark");
        exit(EXIT_FAILURE);
    }
    printf("Écoute des événements.\n");
    /* Lire les événements de la file d'attente d'événements dans un tampon.  */
    size = read(fd, events_buf, sizeof(events_buf));
    if (size == -1 && errno != EAGAIN) {
        perror("read");
        exit(EXIT_FAILURE);
    }
    /* Traiter tous les événements dans le tampon.  */
    for (metadata = (struct fanotify_event_metadata *) events_buf;
            FAN_EVENT_OK(metadata, size);
            metadata = FAN_EVENT_NEXT(metadata, size)) {
        fid = (struct fanotify_event_info_fid *) (metadata + 1);
        file_handle = (struct file_handle *) fid->handle;
        /* S'assurer que les informations de l'événement sont du bon type.  */
        if (fid->hdr.info_type == FAN_EVENT_INFO_TYPE_FID ||
            fid->hdr.info_type == FAN_EVENT_INFO_TYPE_DFID) {
            file_name = NULL;
        } else if (fid->hdr.info_type == FAN_EVENT_INFO_TYPE_DFID_NAME) {
            file_name = file_handle->f_handle +
                        file_handle->handle_bytes;
        } else {
            fprintf(stderr, "Type d'informations d'événement inattendu reçu.\n");
            exit(EXIT_FAILURE);
        }
        if (metadata->mask == FAN_CREATE)
            printf("FAN_CREATE (fichier créé):\n");
        if (metadata->mask == (FAN_CREATE | FAN_ONDIR))
            printf("FAN_CREATE | FAN_ONDIR (sous-répertoire créé):\n");
	/* metadata->fd est défini à FAN_NOFD lorsque le groupe identifie
	   les objets par des handles de fichier.  Pour obtenir un descripteur de fichier pour
	   l'objet de fichier correspondant à un événement, vous pouvez utiliser la
	   struct file_handle qui est fournie dans le
	   fanotify_event_info_fid en conjonction avec l'
	   appel système open_by_handle_at(2).  Un contrôle pour ESTALE est
	   fait pour prendre en compte la situation où le descripteur de
	   fichier de l'objet a été supprimé avant cet appel système.  */
        event_fd = open_by_handle_at(mount_fd, file_handle, O_RDONLY);
        if (event_fd == -1) {
            if (errno == ESTALE) {
                printf("File handle is no longer valid.  "
                        "File has been deleted\n");
                continue;
            } else {
                perror("open_by_handle_at");
                exit(EXIT_FAILURE);
            }
        }
        snprintf(procfd_path, sizeof(procfd_path), "/proc/self/fd/%d",
                event_fd);
        /* Récupérer et afficher le chemin de la dentry modifiée.  */
        path_len = readlink(procfd_path, path, sizeof(path) - 1);
        if (path_len == -1) {
            perror("readlink");
            exit(EXIT_FAILURE);
        }
        path[path_len] = '\0';
        printf("\tDirectory '%s' has been modified.\n", path);
        if (file_name) {
            ret = fstatat(event_fd, file_name, &sb, 0);
            if (ret == -1) {
                if (errno != ENOENT) {
                    perror("fstatat");
                    exit(EXIT_FAILURE);
                }
                printf("\tEntry '%s' does not exist.\n", file_name);
            } else if ((sb.st_mode & S_IFMT) == S_IFDIR) {
                printf("\tEntry '%s' is a subdirectory.\n", file_name);
            } else {
                printf("\tEntry '%s' is not a subdirectory.\n",
                        file_name);
            }
        }
        /* Fermer le descripteur de fichier associé à cet événement.  */
        close(event_fd);
    }
    printf("All events processed successfully.  Program exiting.\n");
    exit(EXIT_SUCCESS)
;
}
