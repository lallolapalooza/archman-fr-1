DESCRIPTIO

N

Pour un aperçu de l'API fanotify, voir fanotify

(7).

fanotify_init() initialise un nouveau groupe fanotify et renvoie un descripteur de fichier pour la file d'événements associée au

groupe.

Le descripteur de fichier est utilisé dans les appels à fanotify_mark(2) pour spécifier les fichiers, répertoires, montages ou systèmes de fichiers pour lesquels des événements fanotify doivent être créés. Ces événements sont reçus en lisant depuis le descripteur de fichier. Certains événements sont purement informatifs, indiquant qu'un fichier a été accédé. D'autres événements peuvent être utilisés pour déterminer si une autre application est autorisée à accéder à un fichier ou à un répertoire. L'autorisation d'accéder aux objets du système de fichiers est accordée en écrivant dans le descripteur de

fichier.

Plusieurs programmes peuvent utiliser l'interface fanotify en même temps pour surveiller les mêmes

fichiers.

Le nombre de groupes fanotify par utilisateur est limité. Voir fanotify(7) pour des détails sur cette

limite.

L'argument flags contient un champ multi-bits définissant la classe de notification de l'application d'écoute et d'autres champs à un seul bit spécifiant le comportement du descripteur de

fichier.

S'il existe plusieurs écouteurs pour les événements de permission, la classe de notification est utilisée pour établir l'ordre dans lequel les écouteurs reçoivent les

événements.

Une seule des classes de notification suivantes peut être spécifiée dans flags

:
FAN_CLASS_PRE_CONT
ENT
Cette valeur permet la réception d'événements notifiant qu'un fichier a été accédé et d'événements pour les décisions de permission si un fichier peut être accédé. Elle est destinée aux écouteurs d'événements qui peuvent avoir besoin d'écrire des données dans des fichiers avant que leurs données finales puissent être accédées. Cette classe de notification pourrait être utilisée par des gestionnaires de stockage hiérarchique, par exemple. L'utilisation de ce drapeau nécessite la capacité CAP_SYS_ADMI
N.
FAN_CLASS_CONT
ENT
Cette valeur permet la réception d'événements notifiant qu'un fichier a été accédé et d'événements pour les décisions de permission si un fichier peut être accédé. Elle est destinée aux écouteurs d'événements qui ont besoin d'accéder à des fichiers lorsqu'ils contiennent déjà leur contenu final. Cette classe de notification pourrait être utilisée par des programmes de détection de logiciels malveillants, par exemple. L'utilisation de ce drapeau nécessite la capacité CAP_SYS_ADMI
N.
FAN_CLASS_NO
TIF
C'est la valeur par défaut. Elle n'a pas besoin d'être spécifiée. Cette valeur
permet uniquement la réception d'événements notifiant qu'un fichier a été accédé
. Les décisions de permission avant l'accès au fichier ne sont pas possibles.

Les écouteurs avec des classes de notification différentes recevront les événements dans l'ordre FAN_CLASS_PRE_CONTENT, FAN_CLASS_CONTENT, FAN_CLASS_NOTIF. L'ordre de notification pour les écouteurs dans la même classe de notification est

indéfini.

Les bits suivants peuvent être définis en plus dans flags

:
FAN_CLOEX
EC
Définir le drapeau close-on-exec (FD_CLOEXEC) sur le nouveau descripteur de fichier. Voir la description du drapeau O_CLOEXEC dans open(
2).
FAN_NONBLO
CK
Activer le drapeau non bloquant (O_NONBLOCK) pour le descripteur de fichier. La lecture depuis le descripteur de fichier ne bloquera pas. À la place, si aucune donnée n'est disponible, read(2) échoue avec l'erreur EAGAI
N.
FAN_UNLIMITED_QU
EUE
Supprimer la limite sur le nombre d'événements dans la file d'événements. Voir fanotify(7) pour des détails sur cette limite. L'utilisation de ce drapeau nécessite la capacité CAP_SYS_ADMI
N.
FAN_UNLIMITED_MA
RKS
Supprimer la limite sur le nombre de marques fanotify par utilisateur. Voir fanotify(7) pour des détails sur cette limite. L'utilisation de ce drapeau nécessite la capacité CAP_SYS_ADMI
N.
FAN_REPORT_TID (depuis Linux 4.
20)
Signaler l'identifiant de thread (TID) au lieu de l'identifiant de processus (PID) dans le champ pid de la struct fanotify_event_metadata fournie à read(2) (voir fanotify(7)). L'utilisation de ce drapeau nécessite la capacité CAP_SYS_ADMI
N.
FAN_ENABLE_AUDIT (depuis Linux 4.
15)
Activer la génération d'enregistrements de journal d'audit concernant la médiation d'accès effectuée par les événements de permission. La réponse à l'événement de permission doit être marquée avec le drapeau FAN_AUDIT pour qu'un enregistrement de journal d'audit soit généré. L'utilisation de ce drapeau nécessite la capacité CAP_AUDIT_WRIT
E.
FAN_REPORT_FID (depuis Linux
5.1)
Cette valeur permet la réception d'événements qui contiennent des informations supplémentaires sur l'objet du système de fichiers sous-jacent corrélé à un événement. Un enregistrement supplémentaire de type FAN_EVENT_INFO_TYPE_FID encapsule les informations sur l'objet et est inclus à côté de la structure générique de métadonnées d'événement. Le descripteur de fichier utilisé pour représenter l'objet corrélé à un événement est remplacé par une poignée de fichier. Elle est destinée aux applications qui peuvent trouver l'utilisation d'une poignée de fichier pour identifier un objet plus adaptée qu'un descripteur de fichier. De plus, elle peut être utilisée pour les applications surveillant un répertoire ou un système de fichiers qui sont intéressées par les événements de modification d'entrée de répertoire FAN_CREATE, FAN_DELETE, FAN_MOVE, et FAN_RENAME, ou par des événements tels que FAN_ATTRIB, FAN_DELETE_SELF, et FAN_MOVE_SELF. Tous les événements ci-dessus nécessitent un groupe fanotify qui identifie les objets du système de fichiers par des poignées de fichier. Notez que sans le drapeau FAN_REPORT_TARGET_FID, pour les événements de modification d'entrée de répertoire, il y a un enregistrement d'information qui identifie le répertoire modifié et non l'objet enfant créé/supprimé/déplacé. L'utilisation de FAN_CLASS_CONTENT ou FAN_CLASS_PRE_CONTENT n'est pas autorisée avec ce drapeau et entraînera l'erreur EINVAL. Voir fanotify(7) pour des détails
supplémentaires.
FAN_REPORT_DIR_FID (depuis Linux
5.9)
Les événements pour les groupes fanotify initialisés avec ce drapeau contiendront (voir les exceptions ci-dessous) des informations supplémentaires sur un objet répertoire corrélé à un événement. Un enregistrement supplémentaire de type FAN_EVENT_INFO_TYPE_DFID encapsule les informations sur l'objet répertoire et est inclus à côté de la structure générique de métadonnées d'événement. Pour les événements qui se produisent sur un objet non-répertoire, la structure supplémentaire inclut une poignée de fichier qui identifie l'objet répertoire parent du système de fichiers. Notez qu'il n'y a aucune garantie que l'objet répertoire du système de fichiers sera trouvé à l'emplacement décrit par les informations de la poignée de fichier au moment où l'événement est reçu. Lorsqu'il est combiné avec le drapeau FAN_REPORT_FID, deux enregistrements peuvent être signalés avec les événements qui se produisent sur un objet non-répertoire, un pour identifier l'objet non-répertoire lui-même et un pour identifier l'objet répertoire parent. Notez que dans certains cas, un objet du système de fichiers n'a pas de parent, par exemple, lorsqu'un événement se produit sur un fichier non lié mais ouvert. Dans ce cas, avec le drapeau FAN_REPORT_FID, l'événement sera signalé avec un seul enregistrement pour identifier l'objet non-répertoire lui-même, car il n'y a pas de répertoire associé à l'événement. Sans le drapeau FAN_REPORT_FID, aucun événement ne sera signalé. Voir fanotify(7) pour des détails
supplémentaires.
FAN_REPORT_NAME (depuis Linux 5.9)
Les
événements pour les groupes fanotify initialisés avec cet indicateur contiendront des informations supplémentaires sur le nom de l'entrée de répertoire corrélée à un événement. Cet indicateur doit être fourni conjointement avec l'indicateur FAN_REPORT_DIR_FID. Fournir cette valeur d'indicateur sans FAN_REPORT_DIR_FID entraînera l'erreur EINVAL. Cet indicateur peut être combiné avec l'indicateur FAN_REPORT_FID. Un enregistrement supplémentaire de type FAN_EVENT_INFO_TYPE_DFID_NAME, qui encapsule les informations sur l'entrée de répertoire, est inclus à côté de la structure générique de métadonnées d'événement et remplace l'enregistrement d'informations supplémentaires de type FAN_EVENT_INFO_TYPE_DFID. L'enregistrement supplémentaire inclut un descripteur de fichier qui identifie un objet de système de fichiers de répertoire, suivi d'un nom qui identifie une entrée dans ce répertoire. Pour les événements de modification d'entrée de répertoire FAN_CREATE, FAN_DELETE, et FAN_MOVE, le nom rapporté est celui de l'entrée de répertoire créée/supprimée/déplacée. L'événement FAN_RENAME peut contenir deux enregistrements d'informations. L'un de type FAN_EVENT_INFO_T YPE_OLD_DFID_NAME identifiant l'ancienne entrée de répertoire, et un autre de type FAN_EVENT_INFO_TYPE _NEW_DFID_NAME identifiant la nouvelle entrée de répertoire. Pour les autres événements qui se produisent sur un objet répertoire, le descripteur de fichier rapporté est celui de l'objet répertoire lui-même et le nom rapporté est '.'. Pour les autres événements qui se produisent sur un objet non-répertoire, le descripteur de fichier rapporté est celui de l'objet répertoire parent et le nom rapporté est le nom d'une entrée de répertoire où l'objet se trouvait au moment de l'événement. La justification de cette logique est que le descripteur de fichier du répertoire rapporté peut être passé à open_by_handle_at(2) pour obtenir un descripteur de fichier de répertoire ouvert et que ce descripteur de fichier, avec le nom rapporté, peut être utilisé pour appeler fstatat(2). La même règle qui s'applique au type d'enregistrement FAN_EVENT_INFO_TYPE_DFID s'applique aussi au type d'enregistrement FAN_EVENT_INFO_TYPE_DFID_NAME : si un objet non-répertoire n'a pas de parent, soit l'événement ne sera pas rapporté, soit il sera rapporté sans les informations d'entrée de répertoire. Notez qu'il n'y a aucune garantie que l'objet de système de fichiers sera trouvé à l'emplacement décrit par les informations d'entrée de répertoire au moment où l'événement est reçu. Voir fanotify(7) pour des détails supplémentaires. FAN_REPORT_DFID_
