DESCRIPTIO

N

Pour un aperçu de l'API fanotify, voir fanotify

(7).

fanotify_mark() ajoute, supprime ou modifie une marque fanotify sur un objet de système de fichiers. L'appelant doit avoir la permission de lecture sur l'objet de système de fichiers qui doit être

marqué.

L'argument fanotify_fd est un descripteur de fichier renvoyé par fanotify_in

it(2).

flags est un masque de bits décrivant la modification à effectuer. Il doit inclure exactement l'une des valeurs suivantes

:
FAN_MARK_A
DD
Les événements dans mask seront ajoutés au masque de marque (ou au masque d'ignoré). mask doit être non vide, sinon l'erreur EINVAL se
produira.
FAN_MARK_REM
OVE
Les événements de l'argument mask seront supprimés du masque de marque (ou du masque d'ignoré). mask doit être non vide, sinon l'erreur EINVAL se
produira.
FAN_MARK_FLU
SH
Supprime soit toutes les marques pour les systèmes de fichiers, soit toutes les marques pour les montages, soit toutes les marques pour les répertoires et fichiers du groupe fanotify. Si flags contient FAN_MARK_MOUNT, toutes les marques pour les montages sont supprimées du groupe. Si flags contient FAN_MARK_FILESYSTEM, toutes les marques pour les systèmes de fichiers sont supprimées du groupe. Sinon, toutes les marques pour les répertoires et fichiers sont supprimées. Aucun autre drapeau que, et au plus un parmi, les drapeaux FAN_MARK_MNTNS, FAN_MARK_MOUNT, ou FAN_MARK_FILESYSTEM ne peut être utilisé en conjonction avec FAN_MARK_FLUSH. mask est
ign
oré.

Si aucune des valeurs ci-dessus n'est spécifiée, ou si plus d'une est spécifiée, l'appel échoue avec l'erreur EINVAL

.

De plus, zéro ou plusieurs des valeurs suivantes peuvent être combinées par un OU bit à bit dans flags

:
FAN_MARK_DONT_FOL
LOW
Si path est un lien symbolique, marquer le lien lui-même plutôt que le fichier auquel il fait référence. (Par défaut, fanotify_mark() déréférence path s'il s'agit d'un lien symbolique.
)
FAN_MARK_ONLY
DIR
Si l'objet de système de fichiers à marquer n'est pas un répertoire, l'erreur ENOTDIR doit être
levée.
FAN_MARK_MNTNS (depuis Linux 6.
14)
Marquer l'espace de noms de montage spécifié par path. Si path ne représente pas un espace de noms de montage (par exemple /proc/pid/ns/mnt), l'appel échoue avec l'erreur EINVAL. Un groupe fanotify initialisé avec le drapeau FAN_REPORT_MNT est
requis.
FAN_MARK_MOU
NT
Marquer le montage spécifié par path. Si path n'est pas lui-même un point de montage, le montage contenant path sera marqué. Tous les répertoires, sous-répertoires et les fichiers contenus dans le montage seront surveillés. Les événements qui nécessitent que les objets de système de fichiers soient identifiés par des poignées de fichier, tels que FAN_CREATE, FAN_ATTRIB, FAN_MOVE, et FAN_DELETE_SELF, ne peuvent pas être fournis comme mask lorsque flags contient FAN_MARK_MOUNT. Tenter de le faire entraînera le retour de l'erreur EINVAL. L'utilisation de ce drapeau nécessite la capacité CAP_SYS_ADMI
N.
FAN_MARK_FILESYSTEM (depuis Linux 4.
20)
Marquer le système de fichiers spécifié par path. Le système de fichiers contenant path sera marqué. Tous les fichiers et répertoires contenus dans le système de fichiers depuis n'importe quel point de montage seront surveillés. L'utilisation de ce drapeau nécessite la capacité CAP_SYS_ADMI
N.
FAN_MARK_IGNORED_M
ASK
Les événements dans mask doivent être ajoutés au ou supprimés du masque d'ignoré. Notez que les drapeaux FAN_ONDIR, et FAN_EVENT_ON_CHILD n'ont aucun effet lorsqu'ils sont fournis avec ce drapeau. L'effet du réglage des drapeaux FAN_ONDIR, et FAN_EVENT_ON_CHILD dans le masque de marque sur les événements qui sont définis dans le masque d'ignoré est indépendant de la version du noyau Linux. Plus précisément, avant Linux 5.9, le réglage d'un masque de marque sur un fichier et d'une marque avec masque d'ignoré sur son répertoire parent ne permettait pas d'ignorer les événements sur le fichier, quel que soit le FAN_EVENT_ON_CHILD dans le masque de marque du répertoire parent. Lorsque le masque d'ignoré est mis à jour avec le drapeau FAN_MARK_IGNORED_MASK sur une marque qui a été précédemment mise à jour avec le drapeau FAN_MARK_IGNORE, la mise à jour échoue avec l'erreur EEXIST
.
FAN_MARK_IGNORE (depuis Linux 6.0, 5.15.154, et 5.10.
220)
Ce drapeau a un effet similaire au réglage du drapeau FAN_MARK_IGNORED_MASK. Les événements dans mask doivent être ajoutés au ou supprimés du masque d'ignoré. Contrairement au drapeau FAN_MARK_IGNORED_MASK, ce drapeau a aussi pour effet que les drapeaux FAN_ONDIR, et FAN_EVENT_ON_CHILD prennent effet sur le masque d'ignoré. Plus précisément, à moins que le drapeau FAN_ONDIR ne soit défini avec FAN_MARK_IGNORE, les événements sur les répertoires ne seront pas ignorés. Si le drapeau FAN_EVENT_ON_CHILD est défini avec FAN_MARK_IGNORE, les événements sur les enfants seront ignorés. Par exemple, une marque sur un répertoire avec la combinaison d'un masque avec l'événement FAN_CREATE et le drapeau FAN_ONDIR et un masque d'ignoré avec l'événement FAN_CREATE et sans le drapeau FAN_ONDIR, entraînera l'obtention uniquement des événements de création de sous-répertoires. Lors de l'utilisation du drapeau FAN_MARK_IGNORE pour ajouter à un masque d'ignoré d'une marque d'inode de montage, de système de fichiers ou de répertoire, le drapeau FAN_MARK_IGNORED_SURV_MODIFY doit être spécifié. Le fait de ne pas le faire entraînera l'erreur EINVAL ou EISDIR
.
FAN_MARK_IGNORED_SURV_MOD
IFY
Le masque d'ignoré doit survivre aux événements de modification. Si ce drapeau n'est pas défini, le masque d'ignoré est effacé lorsqu'un événement de modification se produit sur l'objet marqué. L'omission de ce drapeau est généralement utilisée pour supprimer les événements (par exemple, FAN_OPEN) pour un fichier spécifique, jusqu'à ce que le contenu de ce fichier spécifique ait été modifié. Il est beaucoup moins utile de supprimer les événements sur un système de fichiers entier, ou un montage, ou sur tous les fichiers à l'intérieur d'un répertoire, jusqu'à ce que le contenu de certains fichiers ait été modifié. Pour cette raison, le drapeau FAN_MARK_IGNORE nécessite le drapeau FAN_MARK_IGNORED_SURV_MODIFY sur une marque d'inode de montage, de système de fichiers ou de répertoire. Ce drapeau ne peut pas être supprimé d'une marque une fois défini. Lorsque le masque d'ignoré est mis à jour sans ce drapeau sur une marque qui a été précédemment mise à jour avec les drapeaux FAN_MARK_IGNORE et FAN_MARK_IGNORED_SURV_MODIFY, la mise à jour échoue avec l'erreur EEXIST
.
FAN_MARK_IGNORE_S
URV
C'est un synonyme pour (FAN_MARK_IGNORE|FAN_MARK_IGNORED_SUR
V_MODIFY).
FAN_MARK_EVICTABLE (depuis Linux 5.19, 5.15.154, et 5.10.
220)
Lorsqu'une marque d'inode est créée avec ce drapeau, l'objet inode ne sera pas épinglé au cache d'inodes, permettant ainsi à l'objet inode d'être évacué du cache d'inodes lorsque la pression sur la mémoire du système est élevée. L'évacuation de l'objet inode entraîne la perte de la marque évacuable. Lorsque le masque d'une marque d'inode évacuable est mis à jour sans utiliser le drapeau FAN_MARK_EVICATBLE, l'inode marqué est épinglé au cache d'inodes et la marque n'est plus évacuable. Lorsque le masque d'une marque d'inode non évacuable est mis à jour avec le drapeau FAN_MARK_EVICTABLE, la marque d'inode reste non évacuable et la mise à jourdate fails with EEXIST error. Mounts and filesystems are not evictable objects, therefore, an attempt to create a mount mark or a filesystem mark with the FAN_MARK_EVICTABLE flag, will result in the error EINVAL. For example, inode marks can be used in combination with mount marks to reduce the amount of events from noninteresting paths. The event listener reads events, checks if the path reported in the event is of interest, and if it is not, the listener sets a mark with an ignore mask on the directory. Evictable inode marks allow using this method for a large number of directories without the concern of pinning all inodes and exhausting the system's memory.

mask defines which events shall be listened for (or which shall be ignored). It is a bit mask composed of the following values:

FAN_ACCESS
Crée un événement lorsqu'un fichier ou un répertoire (mais voir BUGS) est accédé (lu).
FAN_MODIFY
Crée un événement lorsqu'un fichier est modifié (écrit).
FAN_CLOSE_WRITE
Crée un événement lorsqu'un fichier accessible en écriture est fermé.
FAN_CLOSE_NOWRITE
Crée un événement lorsqu'un fichier en lecture seule ou un répertoire est fermé.
FAN_OPEN
Crée un événement lorsqu'un fichier ou un répertoire est ouvert.
FAN_OPEN_EXEC (depuis Linux 5.0)
Crée un événement lorsqu'un fichier est ouvert avec l'intention de l'exécuter. Voir NOTES pour plus de détails.
FAN_ATTRIB (depuis Linux 5.1)
Crée un événement lorsque les métadonnées d'un fichier ou d'un répertoire ont changé. Un groupe fanotify qui identifie les objets du système de fichiers par descripteurs de fichiers est requis.
FAN_CREATE (depuis Linux 5.1)
Crée un événement lorsqu'un fichier ou un répertoire a été créé dans un répertoire parent marqué. Un groupe fanotify qui identifie les objets du système de fichiers par descripteurs de fichiers est requis.
FAN_DELETE (depuis Linux 5.1)
Crée un événement lorsqu'un fichier ou un répertoire a été supprimé dans un répertoire parent marqué. Un groupe fanotify qui identifie les objets du système de fichiers par descripteurs de fichiers est requis.
FAN_DELETE_SELF (depuis Linux 5.1)
Crée un événement lorsque le fichier ou répertoire marqué lui-même est supprimé. Un groupe fanotify qui identifie les objets du système de fichiers par descripteurs de fichiers est requis.
FAN_MOVED_FROM (depuis Linux 5.1)
Crée un événement lorsqu'un fichier ou un répertoire a été déplacé depuis un répertoire parent marqué. Un groupe fanotify qui identifie les objets du système de fichiers par descripteurs de fichiers est requis.
FAN_MOVED_TO (depuis Linux 5.1)
Crée un événement lorsqu'un fichier ou un répertoire a été déplacé vers un répertoire parent marqué. Un groupe fanotify qui identifie les objets du système de fichiers par descripteurs de fichiers est requis.
FAN_RENAME (depuis Linux 5.17, 5.15.154, et 5.10.220)
Cet événement contient les mêmes informations que les événements FAN_MOVED_FROM et FAN_MOVED_TO, mais il est représenté par un seul événement avec jusqu'à deux enregistrements d'informations. Un groupe fanotify qui identifie les objets du système de fichiers par descripteurs de fichiers est requis. Si l'objet du système de fichiers à marquer n'est pas un répertoire, l'erreur ENOTDIR sera levée.
FAN_MOVE_SELF (depuis Linux 5.1)
Crée un événement lorsque le fichier ou répertoire marqué lui-même a été déplacé. Un groupe fanotify qui identifie les objets du système de fichiers par descripteurs de fichiers est requis.
FAN_MNT_ATTACH
FAN_MNT_DETACH (les deux depuis Linux 6.14)
Crée un événement lorsqu'un montage a été attaché ou détaché d'un espace de noms de montage marqué, respectivement. Une tentative de définir ce flag sur un inode, un montage ou un système de fichiers entraînera l'erreur EINVAL. Un groupe fanotify initialisé avec le flag FAN_REPORT_MNT et le flag de marque FAN_MARK_MNTNS sont requis. Un enregistrement d'information supplémentaire de type FAN_EVENT_INFO_TYPE_MNT est renvoyé avec l'événement. Voir fanotify(7) pour plus de détails.
FAN_FS_ERROR (depuis Linux 5.16, 5.15.154, et 5.10.220)
Crée un événement lorsqu'une erreur de système de fichiers entraînant des métadonnées de système de fichiers incohérentes est détectée. Un enregistrement d'information supplémentaire de type FAN_EVENT_INFO_TYPE_ERROR est renvoyé pour chaque événement dans le tampon de lecture. Un groupe fanotify qui identifie les objets du système de fichiers par descripteurs de fichiers est requis. Les événements de ce type dépendent du support du système de fichiers sous-jacent. Au moment de la rédaction, seul le système de fichiers ext4 signale les événements FAN_FS_ERROR. Voir fanotify(7) pour plus de détails.
FAN_OPEN_PERM
Crée un événement lorsqu'une permission pour ouvrir un fichier ou un répertoire est demandée. Un descripteur de fichier fanotify créé avec FAN_CLASS_PRE_CONTENT ou FAN_CLASS_CONTENT est requis.
FAN_OPEN_EXEC_PERM (depuis Linux 5.0)
Crée un événement lorsqu'une permission pour ouvrir un fichier en vue de son exécution est demandée. Un descripteur de fichier fanotify créé avec FAN_CLASS_PRE_CONTENT ou FAN_CLASS_CONTENT est requis. Voir NOTES pour plus de détails.
FAN_ACCESS_PERM
Crée un événement lorsqu'une permission de lire un fichier ou un répertoire est demandée. Un descripteur de fichier fanotify créé avec FAN_CLASS_PRE_CONTENT ou FAN_CLASS_CONTENT est requis.
FAN_PRE_ACCESS (depuis Linux 6.14)
Crée un événement avant l'accès en lecture ou en écriture à une plage de fichier, offrant ainsi à l'écouteur d'événements la possibilité de modifier le contenu du fichier avant d'accéder au contenu de la plage spécifiée. Un enregistrement d'information supplémentaire de type FAN_EVENT_INFO_TYPE_RANGE est renvoyé pour chaque événement dans le tampon de lecture. Un descripteur de fichier fanotify créé avec FAN_CLASS_PRE_CONTENT est requis.
FAN_ONDIR
Crée des événements pour les répertoires — par exemple, lorsque opendir(3), readdir(3) (mais voir BUGS), et closedir(3) sont appelés. Sans ce flag, des événements sont créés uniquement pour les fichiers. Dans le contexte des événements d'entrée de répertoire, tels que FAN_CREATE, FAN_DELETE, FAN_MOVED_FROM et FAN_MOVED_TO, la spécification du flag FAN_ONDIR est requise pour créer des événements lorsque les entrées de sous-répertoires sont modifiées (c'est-à-dire mkdir(2) / rmdir(2)).
FAN_EVENT_ON_CHILD
Des événements pour les enfants immédiats des répertoires marqués seront créés. Le flag n'a aucun effet lors du marquage de montages et de systèmes de fichiers. Notez que des événements ne sont pas générés pour les enfants des sous-répertoires des répertoires marqués. Plus précisément, les événements de modification d'entrée de répertoire FAN_CREATE, FAN_DELETE, FAN_MOVED_FROM et FAN_MOVED_TO ne sont pas générés pour les modifications d'entrées effectuées à l'intérieur des sous-répertoires des répertoires marqués. Notez que les événements FAN_DELETE_SELF et FAN_MOVE_SELF ne sont pas générés pour les enfants des répertoires marqués. Pour surveiller des arbres de répertoires complets, il est nécessaire de marquer le montage ou le système de fichiers pertinent.

Les valeurs composées suivantes sont définies :

FAN_CLOSE
Un fichier est fermé (FAN_CLOSE_WRITE|FAN_CLOSE_NOWRITE).
FAN_MOVE
Un fichier ou un répertoire a été déplacé (FAN_MOVED_FROM|FAN_MOVED_TO).

L'objet du système de fichiers à marquer est déterminé par le descripteur de fichier dirfd et le nom de chemin spécifié dans path :

•
Si path est NULL, dirfd détermine l'objet du système de fichiers à marquer.
•
Si path est NULL et dirfd prend la valeur spéciale AT_FDCWD, le répertoire de travail courant est à marquer.
•
Si path est absolu, il détermine l'objet du système de fichiers à marquer, et dirfd est ignoré.
•
Si path est relatif et dirfd n'a pas la valeur AT_FDCWD, alors l'objet du système de fichiers à marquer est déterminé en interprétant path relativement au répertoire auquel fait référence dirfd.
•
Si path est relatif et dirfd a la valeur AT_FDCWD, alors l'objet du système de fichiers à marquer est déterminé en interprétant path relativement au répertoire de travail courant. (Voir openat(2) pour une explication de l'utilité de l'argument dirfd.)

VALEUR DE RETOUR

En cas de succès, fanotify_mark() retourne 0. En cas d'erreur, -1 est retourné et errno est défini pour indiquer l'erreur.

REMARQUE

S

FAN_OPEN_EXEC et FAN_OPEN_EXEC_PER

M

Lors de l'utilisation de FAN_OPEN_EXEC ou FAN_OPEN_EXEC_PERM dans mask, les événements de ces types seront renvoyés uniquement lorsque l'exécution directe d'un programme se produit. Plus précisément, cela signifie que les événements de ces types seront générés pour les fichiers qui sont ouverts en utilisant execve(2), execveat(2), ou uselib(2). Les événements de ces types ne seront pas levés dans la situation où un interpréteur est passé (ou lit) un fichier pour

l'interpréter.

De plus, si une marque a également été placée sur le chargeur dynamique Linux, un utilisateur devrait aussi s'attendre à recevoir un événement pour lui lorsqu'un objet ELF a été ouvert avec succès en utilisant execve(2) ou execveat

(2).

Par exemple, si le binaire ELF suivant était invoqué et qu'une marque FAN_OPEN_EXEC avait été placée sur /

: 


$ /bin/echo
foo

L'application d'écoute dans ce cas recevrait des événements FAN_OPEN_EXEC pour à la fois le binaire ELF et l'interpréteur, respectivement

:
