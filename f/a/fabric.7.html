Libfabric est une bibliothèque logicielle de fabric haute performance conçue

pour fournir des interfaces à faible latence vers le matériel fabric. Pour une d
iscussion approfondie de la motivation et de la conception, voir fi_guide(7).

VUE

D'ENSEMBLE

Libfabric fournit l'« E/S directes de processus » au logiciel applicatif communiquant à travers le logiciel et le matériel fabric. Les E/S directes de processus, historiquement appelées RDMA, permettent à une application d'accéder directement aux ressources réseau sans intervention du système d'exploitation. Les transferts de données peuvent se faire directement vers et depuis la mémoire de

l'application.

Il y a deux composants au logiciel libfabric

:
Fournisseurs
Fabric
Conceptuellement, un fournisseur fabric peut être vu comme un pilote NIC matériel local, bien qu'un fournisseur ne soit pas limité par cette définition. Le premier composant de libfabric est un cadre général capable de gérer différents types de matériel fabric. Tous les périphériques de matériel fabric et leurs pilotes logiciels doivent prendre en charge ce cadre. Les périphériques et les pilotes qui se branchent sur le cadre libfabric sont appelés fournisseurs fabric, ou simplement fournisseurs. Les détails des fournisseurs se trouvent dans fi_provider(7)
.
Interfaces
Fabric
Le deuxième composant est un ensemble d'opérations de communication. Libfabric définit plusie
urs ensembles de fonctions de communication que les fournisseurs peuvent prendre en charge. I
l n'est pas requis que les fournisseurs implémentent toutes les interfaces qui sont définies
; cependant, les fournisseurs indiquent clairement quelles interfaces ils prennent en charge.

INTERFACES

FABRIC

Les interfaces fabric sont conçues de telle manière qu'elles sont cohésives et pas simplement une union d'interfaces disjointes. Les interfaces sont logiquement divisées en deux groupes : les interfaces de contrôle et les opérations de communication. Les interfaces de contrôle sont un ensemble commun d'opérations qui fournissent l'accès aux ressources de communication locales, telles que les vecteurs d'adresses et les files d'événements. Les opérations de communication exposent des modèles particuliers de communication et des fonctionnalités fabric, telles que les files de messages, l'accès mémoire distant et les opérations atomiques. Les opérations de communication sont associées aux points de terminaison

fabric.

Les applications utiliseront typiquement les interfaces de contrôle pour découvrir les capacités locales et allouer les

ressources nécessaires. Elles alloueront ensuite et configureront un point de terminaison de communication pour envoyer
et recevoir des données, ou effectuer d'autres types de transferts de données, avec des points de terminaison distants.

INTERFACES DE

CONTRÔLE

Les API des interfaces de contrôle donnent aux applications accès aux ressources réseau. Cela implique de lister toutes les interfaces disponibles, d'obtenir les capacités des interfaces et d'ouvrir un

fournisseur.
fi_getinfo - Informations
Fabric
L'appel fi_getinfo est l'appel de base utilisé pour découvrir et demander les services fabric offerts par l
e système. Les applications peuvent utiliser cet appel pour indiquer le type de communication qu'elles désir
ent. Les résultats de fi_getinfo, fi_info, sont utilisés pour réserver et configurer les ressources fabric.

fi_getinfo retourne une liste de structures fi_info. Chaque structure référence un seul fournisseur fabric, indiquant les interfaces que le fournisseur prend en charge, ainsi qu'un ensemble nommé de ressources. Un fournisseur fabric peut inclure plusieurs structures fi_info dans la liste

retournée.
fi_fabric - Domaine
Fabric
Un domaine fabric représente une collection de ressources matérielles et logicielles qui accèdent à un réseau physique ou virtuel unique. Tous les ports réseau sur un système qui peuvent communiquer entre eux à travers le fabric appartiennent au même domaine fabric. Un domaine fabric partage des adresses réseau et peut s'étendre sur plusieurs fournisseurs. libfabric prend en charge les systèmes connectés à plusieurs
fabrics.
fi_domain - Domaines
d'accès
Un domaine d'accès représente une connexion logique unique dans un fabric. Il peut correspondre à un seul NIC physique ou virtuel ou à un port. Un domaine d'accès définit la limite à travers laquelle les ressources fabric peuvent être associées. Chaque domaine d'accès appartient à un seul domaine
fabric.
fi_endpoint - Point de terminaison
Fabric
Un point de terminaison fabric est un portail de communication. Un point de terminaison peut être actif ou passif. Les points de terminaison passifs sont utilisés pour écouter les demandes de connexion. Les points de terminaison actifs peuvent effectuer des transferts de données. Les points de terminaison sont configurés avec des capacités de communication spécifiques et des interfaces de transfert de
données.
fi_eq - File
d'événements
Les files d'événements sont utilisées pour collecter et signaler l'achèvement des opérations et événements asynchrones. Les files d'événements signalent des événements qui ne sont pas directement associés aux opérations de transfert de
données.
fi_cq - File
d'achèvement
Les files d'achèvement sont des files d'événements haute performance utilisées pour signaler l'achèvement des opérations de transfert de
données.
fi_cntr - Compteurs
d'événements
Les compteurs d'événements sont utilisés pour signaler le nombre d'opérations asynchrones achevées. Les compteurs d'événements sont considérés comme légers, en ce sens qu'un achèvement incrémente simplement un compteur, plutôt que de placer une entrée dans une file
d'événements.
fi_mr - Région
mémoire
Les régions mémoire décrivent les tampons mémoire locaux de l'application. Afin que les ressources fabric puissent accéder à la mémoire de l'application, l'application doit d'abord accorder la permission au fournisseur fabric en construisant une région mémoire. Les régions mémoire sont requises pour certains types d'opérations de transfert de données, telles que les transferts RMA (voir ci-dessous)
.
fi_av - Vecteur
d'adresses
Les vecteurs d'adresses sont utilisés pour mapper des adresses de niveau supérieur, telles que les adresses IP, qui peuvent être
plus naturelles pour une application à utiliser, vers des adresses spécifiques au fabric. L'utilisation de vecteurs d'adresses pe
rmet aux fournisseurs de réduire la quantité de mémoire nécessaire pour maintenir de grands tableaux de recherche d'adress
es, et d'éliminer les méthodes coûteuses de résolution et de recherche d'adresses pendant les opérations de transfert de données.

INTERFACES DE TRANSFERT DE

DONNÉES

Les points de terminaison fabric sont associés à plusieurs interfaces de transfert de données. Chaque ensemble d'interfaces est conçu pour prendre en charge un style spécifique de communication, avec un point de terminaison permettant l'utilisation des différentes interfaces en conjonction. Les interfaces de transfert de données suivantes sont définies par

libfabric.
fi_msg - File de
messages
Les files de messages exposent une interface simple de file FIFO basée sur les messages à l'application. Les transferts de données par message permettent aux applications d'envoyer et de recevoir des données avec le maintien des limites de
messages.
fi_tagged - Files de messages
étiquetés
Les listes de messages étiquetés exposent des opérations de transfert de données envoi/réception construites sur le concept de messagerie étiquetée. La file de messages étiquetés est conceptuellement similaire aux files de messages standard, mais avec l'ajout d'étiquettes de 64 bits pour chaque message. Les messages envoyés sont appariés avec les tampons de réception qui sont étiquetés avec une valeur
similaire.
fi_rma - Accès mémoire
distant
Les transferts RMA sont des opérations unilatérales qui lisent ou écrivent des données directement vers une région mémoire distante. En dehors de la définition de la région mémoire appropriée, les opérations RMA ne nécessitent pas d'interaction côté cible pour que le transfert de données soit
terminé.
fi_atomic -
Atomique
Les opérations atomiques peuvent effectuer l'une de plusieurs opérations sur une région mémoire distante.
Les opérations atomiques incluent des fonctionnalités bien connues, telles que atomic-add et compare-and-
swap, plus plusieurs autres appels prédéfinis. Contrairement aux autres interfaces de transfert de donnée
s, les opérations atomiques sont conscientes de la mise en forme des données dans la région mémoire cible.

INTERFACE DE JOURNALISATION

La journalisation peut être contrôlée à l'aide des variables d'environnement FI_LOG_LEVEL, FI_LOG_PROV et FI_LOG_SUBSYS.

FI_LOG_LEVEL
FI_LOG_LEVEL contrôle la quantité de données de journalisation qui sont produites. Les niveaux de journalisation suivants sont définis.
- Avertissement
Avertissement est le réglage le moins prolixe et est destiné à signaler les erreurs ou les avertissements.
- Trace
Trace est plus prolixe et est destiné à inclure des sorties non détaillées utiles au traçage de l'exécution du programme.
- Info
Info est un trafic élevé et est destiné à une sortie détaillée.
- Debug
Debug est un trafic élevé et est susceptible d'affecter les performances de l'application. La sortie Debug n'est disponible que si la bibliothèque a été compilée avec le débogage activé.
FI_LOG_PROV
La variable d'environnement FI_LOG_PROV active ou désactive la journalisation à partir de fournisseurs spécifiques. Les fournisseurs peuvent être activés en les listant séparés par des virgules. Si la liste commence par le symbole `^', la liste sera niée. Par défaut, tous les fournisseurs sont activés.

Exemple : Pour activer la journalisation à partir des fournisseurs psm3 et sockets : FI_LOG_PROV=“psm3,sockets”

Exemple : Pour activer la journalisation à partir de fournisseurs autres que psm3 : FI_LOG_PROV=“^psm3”

FI_LOG_SUBSYS
La variable d'environnement FI_LOG_SUBSYS active ou désactive la journalisation au niveau du sous-système. La syntaxe pour activer ou désactiver les sous-systèmes est similaire à celle utilisée pour FI_LOG_PROV. Les sous-systèmes suivants sont définis.
- noyau
Fournit des sorties relatives au framework principal et à sa gestion des fournisseurs.
- fabric
Fournit des sorties spécifiques aux interactions associées à l'objet fabric.
- domaine
Fournit des sorties spécifiques aux interactions associées à l'objet domain.
- ep_ctrl
Fournit des sorties spécifiques aux opérations de transfert non de données des points d'extrémité, telles que les opérations CM.
- ep_data
Fournit des sorties spécifiques aux opérations de transfert de données des points d'extrémité.
- av
Fournit des sorties spécifiques aux opérations de vecteur d'adresse.
- cq
Fournit des sorties spécifiques aux opérations de file d'attente de complétion.
- eq
Fournit des sorties spécifiques aux opérations de file d'attente d'événements.
- mr
Fournit des sorties spécifiques à l'enregistrement de mémoire.

INSTALLATION ET SELECTION DES FOURNISSEURS

Les scripts de construction de libfabric installeront tous les fournisseurs pris en charge par le système d'installation. Les fournisseurs pour lesquels les prérequis de construction sont manquants seront désactivés. Les fournisseurs installés vérifieront dynamiquement le matériel nécessaire lors de l'initialisation de la bibliothèque et répondront de manière appropriée aux requêtes des applications.

Les utilisateurs peuvent activer ou désactiver les fournisseurs disponibles via les options de configuration de construction. Voir `configure –help' pour plus de détails. En général, un fournisseur spécifique peut être contrôlé à l'aide de l'option de configuration `–enable-'. Par exemple, `–enable-udp' (ou `–enable-udp=yes') ajoutera le fournisseur udp à la construction. Pour désactiver le fournisseur, `–enable-udp=no' peut être utilisé. Pour construire le fournisseur en tant que bibliothèque chargeable dynamiquement autonome (c'est-à-dire fournisseur DL), `–enable-udp=dl' peut être utilisé.

Les fournisseurs peuvent également être activés ou désactivés à l'exécution à l'aide de la variable d'environnement FI_PROVIDER. La variable FI_PROVIDER est définie sur une liste de fournisseurs à inclure, séparés par des virgules. Si la liste commence par le symbole `^', alors la liste sera niée.

Exemple : Pour activer uniquement les fournisseurs udp et tcp, définissez : FI_PROVIDER="udp,tcp"

Lorsque libfabric est installé, les fournisseurs DL sont placés sous le *chemin de fournisseur par défaut*, qui est déterminé par la manière dont libfabric est construit et installé. Généralement, le chemin de fournisseur par défaut est <libfabric-install-dir>/lib/libfabric ou <libfabric-install-dir>/lib64/libfabric. Par défaut, libfabric essaie de trouver les fournisseurs DL dans l'ordre suivant :

1.
Utilise `dlopen' pour charger les bibliothèques de fournisseurs nommées lib<nom_prov>-fi.so pour tous les fournisseurs activés au moment de la construction. Le chemin de recherche de `ld.so' est utilisé pour localiser les fichiers. Cette étape est ignorée si libfabric est configuré avec l'option `–enable-restricted-dl'.
2.
Essaie de charger chaque fichier sous le chemin de fournisseur par défaut en tant que fournisseur DL.

La variable FI_PROVIDER_PATH peut être utilisée pour modifier l'emplacement de recherche des fournisseurs DL et la manière de résoudre les conflits si plusieurs fournisseurs du même nom sont trouvés. La définition de FI_PROVIDER_PATH à n'importe quelle valeur, même vide, entraînera l'omission de l'étape 1 et peut modifier le répertoire de recherche utilisé à l'étape 2.

Dans sa forme la plus simple, la variable FI_PROVIDER_PATH est définie sur une liste de répertoires séparés par des deux-points. Ces répertoires remplacent le chemin de fournisseur par défaut utilisé à l'étape 2. Par exemple :

FI_PROVIDER_PATH=/opt/libfabric:/opt/libfabric2

Par défaut, si plusieurs fournisseurs (y compris les fournisseurs intégrés) du même nom sont trouvés, le premier avec la version la plus élevée est actif et tous les autres sont masqués. Cela peut être modifié en définissant la variable FI_PROVIDER_PATH pour commencer par `@', ce qui force le premier à être actif quelle que soit sa version. Par exemple :

FI_PROVIDER_PATH=@/opt/libfabric:/opt/libfabric2

La variable FI_PROVIDER_PATH peut également spécifier des fournisseurs préférés en fournissant des chemins complets vers les bibliothèques au lieu de répertoires à rechercher. Un fournisseur préféré a la priorité sur les autres fournisseurs du même nom. La spécification d'un fournisseur préféré doit être précédée de `+'. Par exemple :

FI_PROVIDER_PATH=+/opt/libfabric2/libtcp-fi.so:/opt/libfabric:+/opt/libfabric2/libudp-fi.so

Si FI_PROVIDER_PATH est défini, mais qu'aucun répertoire n'est fourni, le chemin de fournisseur par défaut est utilisé. Quelques exemples :

FI_PROVIDER_PATH=
FI_PROVIDER_PATH=@
FI_PROVIDER_PATH=+/opt/libfabric/libtcp-fi.so
FI_PROVIDER_PATH=@+/opt/libfabric/libtcp-fi.so

L'utilitaire fi_info, inclus dans le package libfabric, peut être utilisé pour obtenir des informations sur les fournisseurs disponibles sur le système. De plus, il peut récupérer une liste de toutes les variables d'environnement qui peuvent être utilisées pour configurer libfabric et chaque fournisseur. Voir fi_info(1) pour plus de détails.

CONTROLES DES VARIABLES D'ENVIRONNEMENT

Les fonctionnalités principales de libfabric et de ses fournisseurs peuvent être configurées par un administrateur via l'utilisation de variables d'environnement. Les pages man décrivent généralement les variables les plus couramment accessibles, telles que celles mentionnées ci-dessus. Cependant, libfabric définit des interfaces pour publier et obtenir des variables d'environnement. Celles-ci sont destinées aux fournisseurs, mais permettent aux applications et aux utilisateurs d'obtenir la liste complète des variables qui peuvent être définies, ainsi qu'une brève description de leur utilisation.

Une liste complète des variables disponibles peut être obtenue en exécutant l'application fi_info, avec l'option de ligne de commande -e ou –env.

NOTES

Appels Système

Étant donné que libfabric est conçu pour fournir aux applications un accès direct au matériel de fabric, il existe des limites quant à la manière dont les ressources libfabric peuvent être utilisées conjointement avec les appels système. Ces limitations sont notables pour les développeurs qui pourraient être familiarisés avec la programmation de l'interface sockets. Bien que les limites soient spécifiques au fournisseur, les restrictions suivantes s'appliquent à de nombreux fournisseurs et doivent être respectées par les applications souhaitant une portabilité entre les fournisseurs.

fork
Les ressources de fabric ne sont pas garanties d'être disponibles pour les processus enfants. Cela inclut les objets, tels que les points d'extrémité et les files d'attente de complétion, ainsi que les tampons de données contrôlés par l'application qui ont été assignés au réseau. Par exemple, les tampons de données qui ont été enregistrés auprès d'un domaine de fabric peuvent ne pas être disponibles dans un processus enfant en raison des restrictions de copie en écriture.

Imblocage CUDA

Dans certains cas, les appels à cudaMemcpy() dans libfabric peuvent entraîner un blocage. Cela se produit généralement lorsqu'un noyau CUDA se bloque en attendant qu'un cudaMemcpy sur l'hôte se termine. Les applications qui peuvent provoquer un tel comportement peuvent limiter la capacité de Libfabric à invoquer des opérations d'API CUDA avec l'option de point d'extrémité FI_OPT_CUDA_API_PERMITTED. Voir fi_endpoint(3) pour plus de détails.

Un autre mécanisme qui peut être utilisé pour éviter les blocages est GDRCopy de Nvidia. L'utilisation de GDRCopy nécessite une bibliothèque externe et un module noyau disponibles sur https://github.com/NVIDIA/gdrcopy. Libfabric doit être configuré avec le support GDRCopy en utilisant l'option --with-gdrcopy, et être exécuté avec FI_HMEM_CUDA_USE_GDRCOPY=1. Cela peut ne pas être pris en charge par tous les fournisseurs.

CHANGEMENTS ABI

Les versions de libfabric maintiennent la compatibilité avec les versions antérieures, de sorte que les applications compilées puissent continuer à fonctionner telles quelles, et que les applications précédemment écrites se compilent contre des versions plus récentes de la bibliothèque sans nécessiter de modifications du code source. retournées.
