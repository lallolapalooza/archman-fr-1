access(2) Manuel des appels système access(2)

NOM

access, faccessat, faccessat2 - vérifier les permissions utilisateur pour un fichier

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNOPSIS

#include <unistd.h>
int access(const char *path, int mode);
#include <fcntl.h>            /* Définition des constantes AT_* */

                /* Mais voir les différences bibliothèque C/noyau, ci-dessous */

            int dirfd, const char *path, int mode, int flags);

DESCRIPTION

access() vérifie si le processus appelant peut accéder au fichier path. Si path est un lien symbolique, il est déréférencé.

Le mode spécifie le(s) contrôle(s) d'accessibilité à effectuer, et est soit la valeur F_OK, soit un masque constitué du OU bit à bit de l'une ou plusieurs des valeurs R_OK, W_OK et X_OK. F_OK teste l'existence du fichier. R_OK, W_OK et X_OK testent si le fichier existe et accorde les permissions de lecture, d'écriture et d'exécution, respectivement.

Le contrôle est effectué en utilisant l'UID et le GID *réels* du processus appelant, plutôt que les IDs effectifs comme c'est le cas lors d'une tentative d'opération (par ex., open(2)) sur le fichier. De même, pour l'utilisateur root, le contrôle utilise l'ensemble des capacités autorisées plutôt que l'ensemble des capacités effectives ; et pour les utilisateurs non-root, le contrôle utilise un ensemble vide de capacités.

Ceci permet aux programmes set-user-ID et aux programmes dotés de capacités de déterminer facilement l'autorité de l'utilisateur qui les a appelés. En d'autres termes, access() ne répond pas à la question "puis-je lire/écrire/exécuter ce fichier ?". Il répond à une question légèrement différente : "(en supposant que je suis un binaire set-user-ID) est-ce que *l'utilisateur qui m'a appelé* peut lire/écrire/exécuter ce fichier ?", ce qui donne aux programmes set-user-ID la possibilité d'empêcher les utilisateurs malveillants de les faire lire des fichiers que les utilisateurs ne devraient pas pouvoir lire.

Si le processus appelant est privilégié (c'est-à-dire que son UID réel est zéro), alors un contrôle X_OK réussit pour un fichier régulier si la permission d'exécution est activée pour le propriétaire du fichier, le groupe, ou les autres.

faccessat()

faccessat() fonctionne exactement comme access(), sauf pour les différences décrites ici.

Si path est relatif, alors il est interprété par rapport au répertoire référencé par le descripteur de fichier dirfd (plutôt que par rapport au répertoire de travail courant du processus appelant, comme le fait access() pour un nom de chemin relatif).

Si path est relatif et dirfd est la valeur spéciale AT_FDCWD, alors path est interprété par rapport au répertoire de travail courant du processus appelant (comme access()).

Si path est absolu, alors dirfd est ignoré.

flags est construit en combinant par OU zéro ou plusieurs des valeurs suivantes :

AT_EACCESS
Effectuer les contrôles d'accès en utilisant les IDs utilisateur et groupe effectifs. Par défaut, faccessat() utilise les IDs réels (comme access()).
AT_EMPTY_PATH (depuis Linux 5.8)
Si path est une chaîne vide, opérer sur le fichier référencé par dirfd (qui peut avoir été obtenu en utilisant l'option open(2) O_PATH). Dans ce cas, dirfd peut faire référence à n'importe quel type de fichier, pas seulement un répertoire. Si dirfd est AT_FDCWD, l'appel opère sur le répertoire de travail courant. Cette option est spécifique à Linux ; définissez _GNU_SOURCE pour obtenir sa définition.
AT_SYMLINK_NOFOLLOW
Si path est un lien symbolique, ne pas le déréférencer : retourner à la place des informations sur le lien lui-même.

Voir openat(2) pour une explication de la nécessité de faccessat().

faccessat2()

La description de faccessat() donnée ci-dessus correspond à POSIX.1 et à l'implémentation fournie par glibc. Cependant, l'implémentation de glibc était une émulation imparfaite (voir BUGS) qui masquait le fait que l'appel système Linux brut faccessat() n'a pas d'argument flags. Pour permettre une implémentation correcte, Linux 5.8 a ajouté l'appel système faccessat2(), qui prend en charge l'argument flags et permet une implémentation correcte de la fonction wrapper faccessat().

VALEUR DE RETOUR

En cas de succès (toutes les permissions demandées accordées, ou mode est F_OK et le fichier existe), zéro est retourné. En cas d'erreur (au moins un bit dans mode a demandé une permission qui est refusée, ou mode est F_OK et le fichier n'existe pas, ou une autre erreur s'est produite), -1 est retourné, et errno est défini pour indiquer l'erreur.

NOTE

S

Avertissement : L'utilisation de ces appels pour vérifier si un utilisateur est autorisé à, par exemple, ouvrir un fichier avant de le faire réellement en utilisant open(2) crée une faille de sécurité, car l'utilisateur pourrait exploiter le court intervalle de temps entre la vérification et l'ouverture du fichier pour le manipuler. Pour cette raison, l'utilisation de cet appel système devrait être évitée. (Dans l'exemple décrit ci-dessus, une alternative plus sûre serait de basculer temporairement l'UID effectif du processus vers l'ID réel puis d'appeler open(2).

)

access() déréférence toujours les liens symboliques. Si vous devez vérifier les permissions sur un lien symbolique, utilisez faccessat() avec le drapeau AT_SYMLINK_NOFOLLOW

.

Ces appels renvoient une erreur si l'un des types d'accès dans mode est refusé, même si certains des autres types d'accès dans mode sont

autorisés.

Un fichier n'est accessible que si les permissions sur chacun des répertoires dans le préfixe de chemin de path accordent l'accès de recherche (c'est-à-dire d'exécution). Si un répertoire est inaccessible, alors l'appel access() échoue, quelles que soient les permissions sur le fichier

lui-même.

Seuls les bits d'accès sont vérifiés, pas le type ou le contenu du fichier. Par conséquent, si un répertoire est trouvé comme étant inscriptible, cela signifie probablement que des fichiers peuvent être créés dans le répertoire, et non que le répertoire peut être écrit comme un fichier. De même, un fichier DOS peut être signalé comme exécutable, mais l'appel execve(2) échouera quand

même.

Ces appels peuvent ne pas fonctionner correctement sur les systèmes de fichiers NFSv2 avec la correspondance UID activée, car l

a correspondance UID est effectuée sur le serveur et masquée au client, qui vérifie les permissions. (Les versions NFS 3 e
t supérieures effectuent la vérification sur le serveur.) Des problèmes similaires peuvent survenir avec les montages FUSE.

BUG

S

Parce que l'appel système faccessat() du noyau Linux ne prend pas en charge un argument flags, la fonction wrapper faccessat() fournie dans glibc 2.32 et antérieures émule la fonctionnalité requise en utilisant une combinaison de l'appel système faccessat() et de fstatat(2). Cependant, cette émulation ne tient pas compte des ACL. À partir de glibc 2.33, la fonction wrapper évite ce bogue en utilisant l'appel système faccessat2() lorsqu'il est fourni par le noyau

sous-jacent.

Dans Linux 2.4 (et antérieur), il y a une certaine étrangeté dans le traitement des tests X_OK pour le superutilisateur. Si toutes les catégories de permission d'exécution sont désactivées pour un fichier non-répertoire, alors le seul test access() qui renvoie -1 est lorsque mode est spécifié comme simplement X_OK ; si R_OK ou W_OK est aussi spécifié dans mode, alors access() renvoie 0 pour de tels fichiers. Les premières versions de Linux 2.6 (jusqu'à et y compris Linux 2.6.3) se comportaient aussi de la même manière que Linux 2.

4.

Avant Linux 2.6.20, ces appels ignoraient l'effet du drapeau MS_NOEXEC s'il était utilisé pour mount(2)er le système de fichiers sous-jacent. Depuis Linux 2.6.20, le drapeau MS_NOEXE

C est r
especté.
