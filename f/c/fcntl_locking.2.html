de description de fichier ouverte (non-POSIX)

Les verrous de description de fichier ouvert sont des verrous par plage d'octets consultatifs dont le fonctionnement est, dans la plupart des cas, identique aux verrous d'enregistrement traditionnels décrits ci-dessus. Ce type de verrou est spécifique à Linux et disponible depuis la version 3.15. (Il existe une proposition auprès de l'Austin Group pour inclure ce type de verrou dans la prochaine révision de POSIX.1.) Pour une explication des descriptions de fichiers ouverts, voir open(2).

La principale différence entre les deux types de verrous est que, alors que les verrous d'enregistrement traditionnels sont associés à un processus, les verrous de description de fichier ouvert sont associés à la description de fichier ouverte sur laquelle ils sont acquis, tout comme les verrous acquis avec flock(2). Par conséquent (et contrairement aux verrous d'enregistrement consultatifs traditionnels), les verrous de description de fichier ouvert sont hérités après fork(2) (et clone(2) avec CLONE_FILES), et ne sont automatiquement libérés qu'à la dernière fermeture de la description de fichier ouverte, au lieu d'être libérés à toute fermeture du fichier.

Les combinaisons de verrous conflictuels (c'est-à-dire un verrou de lecture et un verrou d'écriture, ou deux verrous d'écriture) où l'un des verrous est un verrou de description de fichier ouvert et l'autre est un verrou d'enregistrement traditionnel entrent en conflit même lorsqu'ils sont acquis par le même processus sur le même descripteur de fichier.

Les verrous de description de fichier ouvert placés via la même description de fichier ouverte (c'est-à-dire via le même descripteur de fichier, ou via un duplicata du descripteur de fichier créé par fork(2), dup(2), F_DUPFD(2const), et ainsi de suite) sont toujours compatibles : si un nouveau verrou est placé sur une région déjà verrouillée, le verrou existant est converti en nouveau type de verrou. (Ces conversions peuvent entraîner la division, la réduction ou la coalescence avec un verrou existant, comme discuté ci-dessus.)

En revanche, les verrous de description de fichier ouvert peuvent entrer en conflit les uns avec les autres lorsqu'ils sont acquis via différentes descriptions de fichiers ouverts. Ainsi, les threads d'un programme multithread peuvent utiliser les verrous de description de fichier ouvert pour synchroniser l'accès à une région de fichier en faisant en sorte que chaque thread effectue sa propre ouverture (open(2)) sur le fichier et applique des verrous via le descripteur de fichier résultant.

Comme pour les verrous consultatifs traditionnels, le troisième argument de fcntl(), lock, est un pointeur vers une structure flock. Contrairement aux verrous d'enregistrement traditionnels, le champ l_pid de cette structure doit être mis à zéro lors de l'utilisation des opérations décrites ci-dessous.

Les opérations pour travailler avec les verrous de description de fichier ouvert sont analogues à celles utilisées avec les verrous traditionnels :

F_OFD_SETLK
Acquérir un verrou de description de fichier ouvert (lorsque l_type est F_RDLCK ou F_WRLCK) ou libérer un verrou de description de fichier ouvert (lorsque l_type est F_UNLCK) sur les octets spécifiés par les champs l_whence, l_start et l_len de lock. Si un verrou conflictuel est détenu par un autre processus, cet appel renvoie -1 et définit errno à EAGAIN.
F_OFD_SETLKW
Comme pour F_OFD_SETLK, mais si un verrou conflictuel est détenu sur le fichier, attendez que ce verrou soit libéré. Si un signal est capturé pendant l'attente, l'appel est interrompu et (après le retour du gestionnaire de signal) revient immédiatement (avec la valeur de retour -1 et errno défini à EINTR ; voir signal(7)).
F_OFD_GETLK
À l'entrée de cet appel, lock décrit un verrou de description de fichier ouvert que nous aimerions placer sur le fichier. Si le verrou pouvait être placé, fcntl() ne le place pas réellement, mais renvoie F_UNLCK dans le champ l_type de lock et laisse les autres champs de la structure inchangés. Si un ou plusieurs verrous incompatibles empêchaient ce verrou d'être placé, les détails d'un de ces verrous sont renvoyés via lock, comme décrit ci-dessus pour F_GETLK.

Dans l'implémentation actuelle, aucune détection de interblocage n'est effectuée pour les verrous de description de fichier ouvert. (Ceci contraste avec les verrous d'enregistrement associés à un processus, pour lesquels le noyau effectue une détection d'interblocage.)

Verrouillage obligatoire

Attention : l'implémentation Linux du verrouillage obligatoire n'est pas fiable. Voir BUGS ci-dessous. En raison de ces bugs, et du fait que la fonctionnalité est peu utilisée, depuis Linux 4.5, le verrouillage obligatoire est devenu une fonctionnalité optionnelle, régie par une option de configuration (CONFIG_MANDATORY_FILE_LOCKING). Cette fonctionnalité n'est plus du tout prise en charge dans Linux 5.15 et versions ultérieures.

Par défaut, les verrous d'enregistrement traditionnels (associés à un processus) et les verrous de description de fichier ouvert sont consultatifs. Les verrous consultatifs ne sont pas appliqués et ne sont utiles qu'entre processus coopératifs.

Les deux types de verrous peuvent également être obligatoires. Les verrous obligatoires sont appliqués à tous les processus. Si un processus tente d'effectuer un accès incompatible (par exemple, read(2) ou write(2)) sur une région de fichier qui possède un verrou obligatoire incompatible, le résultat dépend de la présence ou non de l'indicateur O_NONBLOCK pour sa description de fichier ouverte. Si l'indicateur O_NONBLOCK n'est pas activé, l'appel système est bloqué jusqu'à ce que le verrou soit supprimé ou converti en un mode compatible avec l'accès. Si l'indicateur O_NONBLOCK est activé, l'appel système échoue avec l'erreur EAGAIN.

Pour utiliser les verrous obligatoires, le verrouillage obligatoire doit être activé à la fois sur le système de fichiers contenant le fichier à verrouiller et sur le fichier lui-même. Le verrouillage obligatoire est activé sur un système de fichiers en utilisant l'option « -o mand » avec mount(8), ou le drapeau MS_MANDLOCK pour mount(2). Le verrouillage obligatoire est activé sur un fichier en désactivant la permission d'exécution pour le groupe sur le fichier et en activant le bit de permission set-group-ID (voir chmod(1) et chmod(2)).

Le verrouillage obligatoire n'est pas spécifié par POSIX. Certains autres systèmes prennent également en charge le verrouillage obligatoire, bien que les détails sur la façon de l'activer varient d'un système à l'autre.

Verrous perdus

Lorsqu'un verrou consultatif est obtenu sur un système de fichiers réseau tel que NFS, il est possible que le verrou soit perdu. Cela peut se produire en raison d'une action administrative sur le serveur, ou en raison d'une partition réseau (c'est-à-dire une perte de connectivité réseau avec le serveur) suffisamment longue pour que le serveur suppose que le client ne fonctionne plus.

Lorsque le système de fichiers détermine qu'un verrou a été perdu, les futures requêtes read(2) ou write(2) peuvent échouer avec l'erreur EIO. Cette erreur persistera jusqu'à ce que le verrou soit supprimé ou que le descripteur de fichier soit fermé. Depuis Linux 3.12, cela se produit au moins pour NFSv4 (y compris toutes les versions mineures).

Certaines versions d'UNIX envoient un signal (SIGLOST) dans cette circonstance. Linux ne définit pas ce signal et ne fournit aucune notification asynchrone de verrous perdus.

Verrouillage de fichier

L'appel système fcntl() original sous Linux n'était pas conçu pour gérer les grands décalages de fichier (dans la structure flock). Par conséquent, un appel système fcntl64() a été ajouté dans Linux 2.4. Le nouvel appel système utilise une structure différente pour le verrouillage de fichier, flock64, et des opérations correspondantes, F_GETLK64, F_SETLK64 et F_SETLKW64. Cependant, ces détails peuvent être ignorés par les applications utilisant glibc, dont la fonction enveloppe fcntl() utilise de manière transparente l'appel système plus récent là où il est disponible.
