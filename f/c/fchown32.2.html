chown(2) Manuel des appels système chown(2)

NOM

chown, fchown, lchown, fchownat - changer le propriétaire d'un fichier

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <unistd.h>
int chown(const char *path, uid_t owner, gid_t group);
int fchown(int fd, uid_t owner, gid_t group);
int lchown(const char *path, uid_t owner, gid_t group);
#include <fcntl.h>           /* Définition des constantes AT_* */
#include <unistd.h>
int fchownat(int dirfd, const char *path,
             uid_t owner, gid_t group, int flags);

DESCRIPTION

Ces appels système changent le propriétaire et le groupe d'un fichier. Les appels système chown(), fchown() et lchown() ne diffèrent que par la manière dont le fichier est spécifié :

•
chown() change la propriété du fichier spécifié par path, qui est déréférencé si c'est un lien symbolique.
•
fchown() change la propriété du fichier référencé par le descripteur de fichier ouvert fd.
•
lchown() est comme chown(), mais ne déréférence pas les liens symboliques.

Seul un processus privilégié (Linux : celui possédant la capacité CAP_CHOWN) peut changer le propriétaire d'un fichier. Le propriétaire d'un fichier peut changer le groupe du fichier pour n'importe quel groupe dont ce propriétaire fait partie. Un processus privilégié (Linux : avec CAP_CHOWN) peut changer le groupe arbitrairement.

Si owner ou group est spécifié comme -1, alors cet ID n'est pas modifié.

Lorsque le propriétaire ou le groupe d'un fichier exécutable est changé par un utilisateur non privilégié, les bits de mode S_ISUID et S_ISGID sont effacés. POSIX ne spécifie pas si cela doit également se produire lorsque root effectue le chown() ; le comportement de Linux dépend de la version du noyau, et depuis Linux 2.2.13, root est traité comme les autres utilisateurs. Dans le cas d'un fichier non exécutable en groupe (c'est-à-dire, pour lequel le bit S_IXGRP n'est pas défini), le bit S_ISGID indique le verrouillage obligatoire, et n'est pas effacé par un chown().

Lorsque le propriétaire ou le groupe d'un fichier exécutable est changé (par n'importe quel utilisateur), tous les ensembles de capacités pour le fichier sont effacés.

fchownat()

L'appel système fchownat() fonctionne exactement de la même manière que chown(), à l'exception des différences décrites ici.

Si path est relatif, alors il est interprété par rapport au répertoire référencé par le descripteur de fichier dirfd (plutôt que par rapport au répertoire de travail courant du processus appelant, comme le fait chown() pour un nom de fichier relatif).

Si path est relatif et dirfd est la valeur spéciale AT_FDCWD, alors path est interprété par rapport au répertoire de travail courant du processus appelant (comme chown()).

Si path est absolu, alors dirfd est ignoré.

L'argument flags est un masque de bits créé en combinant par OU 0 ou plusieurs des valeurs suivantes ;

AT_EMPTY_PATH (depuis Linux 2.6.39)
Si path est une chaîne vide, opérez sur le fichier référencé par dirfd (qui peut avoir été obtenu en utilisant la fonction open(2) avec le drapeau O_PATH). Dans ce cas, dirfd peut faire référence à n'importe quel type de fichier, pas seulement un répertoire. Si dirfd est AT_FDCWD, l'appel opère sur le répertoire de travail courant. Ce drapeau est spécifique à Linux ; définissez _GNU_SOURCE pour obtenir sa définition.
AT_SYMLINK_NOFOLLOW
Si path est un lien symbolique, ne le déréférencez pas : opérez à la place sur le lien lui-même, comme lchown(). (Par défaut, fchownat() déréférence les liens symboliques, comme chown().)

Voir openat(2) pour une explication de la nécessité de fchownat().

VALEUR DE RETOUR

En cas de succès, zéro est retourné. En cas d'erreur, -1 est retourné, et errno est défini pour indiquer l'erreur.

ERREURS

Selon le système de fichiers, des erreurs autres que celles listées ci-dessous peuvent être retournées.

Les erreurs les plus générales pour chown() sont listées ci-dessous.

EACCES
L'autorisation de recherche est refusée sur un composant du préfixe du chemin. (Voir aussi path_resolution(7).)
EBADF
(fchown()) fd n'est pas un descripteur de fichier ouvert valide.
EBADF
(fchownat()) path est relatif mais dirfd n'est ni AT_FDCWD ni un descripteur de fichier valide.
EFAULT
path pointe en dehors de votre espace d'adressage accessible.
EINVAL
(fchownat()) Drapeau invalide spécifié dans flags.
EIO
(fchown()) Une erreur d'E/S de bas niveau s'est produite lors de la modification de l'inode.
ELOOP
Trop de liens symboliques ont été rencontrés lors de la résolution de path.
ENAMETOOLONG
path est trop long.
ENOENT
Le fichier n'existe pas.
ENOMEM
Mémoire noyau insuffisante disponible.
ENOTDIR
Un composant du préfixe du chemin n'est pas un répertoire.
ENOTDIR
(fchownat()) path est relatif et dirfd est un descripteur de fichier faisant référence à un fichier autre qu'un répertoire.
EPERM
Le processus appelant n'avait pas les permissions requises (voir ci-dessus) pour changer le propriétaire et/ou le groupe.
EPERM
Le fichier est marqué comme immuable ou en écriture seule. (Voir FS_IOC_SETFLAGS(2const).)
EROFS
Le fichier nommé réside sur un système de fichiers en lecture seule.

VERSIONS

La version 4.4BSD ne peut être utilisée que par le superutilisateur (c'est-à-dire, les utilisateurs ordinaires ne peuvent pas donner la propriété de fichiers).

NF

S

Les sémantiques de chown() sont volontairement violées sur les systèmes de fichiers NFS qui ont le mappage UID activé. De plus, la sémantique de tous les appels système qui accèdent au contenu du fichier est violée, car chown() peut entraîner une révocation immédiate de l'accès sur des fichiers déjà ouverts. La mise en cache côté client peut entraîner un délai entre le moment où la p

ropriété a été modifiée pour permettre l'accès à un utilisateur et le moment où l
e fichier peut réellement être accessible par l'utilisateur sur d'autres clients.

détails

historiques

Les appels système Linux originaux chown(), fchown(), et lchown() ne prenaient en charge que des ID utilisateur et groupe de 16 bits. Par la suite, Linux 2.4 a ajouté chown32(), fchown32(), et lchown32(), prenant en charge les ID de 32 bits. Les wrappers de fonction glibc chown(), fchown(), et lchown() gèrent de manière transparente les variations entre les versions du

noyau.

Avant Linux 2.1.81 (sauf 2.1.46), chown() ne suivait pas les liens symboliques. Depuis Linux 2.1.81, chown() suit les liens symboliques, et il y a un nouvel appel système lchown() qui ne suit pas les liens symboliques. Depuis Linux 2.1.86, ce nouvel appel (qui a la même sémantique que l'ancien chown()) a obtenu le même numéro d'appel système, et chown() a obtenu le

numéro nou
vellement introduit.

EXEMPLE

S

Le programme suivant change la propriété du fichier nommé dans son deuxième argument de ligne de commande vers la valeur spécifiée dans son premier argument de ligne de commande. Le nouveau propriétaire peut être spécifié soit comme un ID utilisateur numérique, ou comme un nom d'utilisateur (qui est converti en ID utilisateur en utilisant getpwnam(3) pour effectuer une recherche dans le fichier de mot de passe du système)

.

source du

programme 
#include <pwd.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <unistd.h>
int
main(int argc, char *argv[])
{
    char           *endptr;
    uid_t          uid;
    struct passwd  *pwd;
    if (argc != 3 || argv[1][0] == '\0') {
        fprintf(stderr, "%s <owner> <file>\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    uid = strtol(argv[1], &endptr, 10);  /* Allow a numeric string */
    if (*endptr != '\0') {         /* Was not pure numeric string */
        pwd = getpwnam(argv[1]);   /* Try getting UID for username */
        if (pwd == NULL) {
            perror("getpwnam");
            exit(EXIT_FAILURE);
        }
        uid = pwd->pw_uid;
    }
    if (chown(argv[2], uid, -1) == -1) {
        perror("chown");
        exit(EXIT_FAILURE);
    }
    exit(EXIT_SUCCESS)
;
}
