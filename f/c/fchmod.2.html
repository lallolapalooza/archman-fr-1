DESCRIPTIO

N

Les appels système chmod() et fchmod() changent les bits de mode d'un fichier. (Le mode du fichier se compose des bits de permission du fichier plus les bits set-user-ID, set-group-ID et sticky.) Ces appels système ne diffèrent que par la manière dont le fichier est spécifié

:
•
chmod() change le mode du fichier spécifié dont le chemin d'accès est donné dans path, qui est déréférencé s'il s'agit d'un lien
symbolique.
•
fchmod() change le mode du fichier auquel fait référence le descripteur de fichier ouvert fd
.

Le nouveau mode du fichier est spécifié dans mode, qui est un masque de bits créé en combinant par OU logique zéro ou plusieurs des éléments suivants

S_ISUID

L'UID effectif du processus appelant doit correspondre au propriétaire du fichier, ou le processus doit être privilégié (sous Linux : il doit avoir la capacité CAP_FOWNER)

.

Si le processus appelant n'est pas privilégié (sous Linux : n'a pas la capacité CAP_FSETID), et que le groupe du fichier ne correspond ni au GID effectif du processus ni à l'un de ses GID supplémentaires, le bit S_ISGID sera désactivé, mais cela ne provoquera pas le retour d'une

erreur.

Par mesure de sécurité, selon le système de fichiers, les bits d'exécution set-user-ID et set-group-ID peuvent être désactivés si un fichier est écrit. (Sous Linux, cela se produit si le processus qui écrit n'a pas la capacité CAP_FSETID.) Sur certains systèmes de fichiers, seul le superutilisateur peut définir le bit sticky, qui peut avoir une signification particulière. Pour le bit sticky, et pour les bits set-user-ID et set-group-ID sur les répertoires, voir inode(

7).

Sur les systèmes de fichiers NFS, la restriction des permissions influence immédiatement les fichiers déjà ouverts, car le contrôle d'accès est effectué sur le serveur, mais les fichiers ouverts sont maintenus par le client. L'élargissement des permissions peut être retardé pour les autres clients si la mise en cache des attributs est activée sur

ceux-ci.

L' appel système fchmodat() fonctionne exactement de la même manière que chmod(), à l'exception des différences décrites

ici.

Si path est relatif, il est alors interprété par rapport au répertoire auquel fait référence le descripteur de fichier dirfd (plutôt que par rapport au répertoire de travail courant du processus appelant, comme le fait chmod() pour un chemin d'accès relatif)

.

Si path est relatif et dirfd est la valeur spéciale AT_FDCWD, alors path est interprété par rapport au répertoire de travail courant du processus appelant (comme chmod())

.

Si path est absolu, alors dirfd est

ignoré.

VERSIONS

Différences bibliothèque C/noyau

La fonction wrapper fchmodat() de la bibliothèque C GNU implémente l'interface spécifiée par POSIX décrite dans cette page. Cette interface diffère de l'appel système Linux sous-jacent, qui n'a pas d'argument flags.

Notes glibc

Sur les anciens noyaux où fchmodat() n'est pas disponible, la fonction wrapper glibc se rabat sur l'utilisation de chmod(). Lorsque path est un nom de chemin relatif, glibc construit un nom de chemin basé sur le lien symbolique dans /proc/self/fd qui correspond à l'argument dirfd.
