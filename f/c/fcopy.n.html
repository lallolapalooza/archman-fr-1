DESCRIPTIO

N

La commande fcopy copie des données d'un canal d'E/S, inchan vers un autre canal d'E/S, outchan. La commande fcopy exploite la mise en mémoire tampon du système d'E/S de Tcl pour éviter des copies supplémentaires et pour éviter de mettre en mémoire tampon trop de données en mémoire principale lors de la copie de fichiers volumineux vers des destinations lentes comme les sockets

réseau.

La commande fcopy transfère les données de inchan jusqu'à la fin du fichier ou jusqu'à ce que size octets ou caractères aient été transférés ; size est en octets si les deux canaux utilisent le même encodage, et en caractères sinon. Si aucun argument -size n'est donné, la copie se poursuit jusqu'à la fin du fichier. Toutes les données lues depuis inchan sont copiées vers outchan. Sans l'option -command, fcopy se bloque jusqu'à ce que la copie soit terminée et renvoie le nombre d'octets ou de caractères (en utilisant les mêmes règles que pour l'option -size) écrits dans outchan

.

L'argument -command fait fonctionner fcopy en arrière-plan. Dans ce cas, il renvoie immédiatement et le callback est appelé plus tard lorsque la copie est terminée. Le callback est appelé avec un ou deux arguments supplémentaires qui indiquent combien d'octets ont été écrits dans outchan. Si une erreur s'est produite pendant la copie en arrière-plan, le deuxième argument est la chaîne d'erreur associée à l'erreur. Avec une copie en arrière-plan, il n'est pas nécessaire de mettre inchan ou outchan en mode non bloquant ; la commande fcopy s'en charge automatiquement. Cependant, il est nécessaire d'entrer dans la boucle d'événements en utilisant la commande vwait ou en utilisant

Tk.

Vous n'êtes pas autorisé à effectuer d'autres opérations d'entrée sur inchan, ou des opérations de sortie sur outchan, pendant un fcopy en arrière-plan. L'inverse est tout à fait légitime, comme le montre l'exemple de fcopy bidirectionnel

ci-dessous.

Si inchan ou outchan est fermé pendant que la copie est en cours, la copie en cours est arrêtée et le callback de commande n'est pas appelé. Si inchan est fermé, toutes les données déjà mises en file d'attente pour outchan sont

écrites.

Notez que inchan peut devenir lisible pendant une copie en arrière-plan. Vous devriez désactiver tous les gestionnaires fileevent pendant une copie en arrière-plan afin que ces gestionnaires n'interfèrent pas avec la copie. Toute tentative d'E/S du mauvais côté (par un gestionnaire fileevent ou autrement) provoquera une erreur « channel busy »

.

Fcopy traduit les séquences de fin de ligne dans inchan et outchan selon l'option -translation de ces canaux. Voir l'entrée de manuel pour fconfigure pour les détails sur l'option -translation. Les traductions signifient que le nombre d'octets lus depuis inchan peut être différent du nombre d'octets écrits dans outchan. Seul le nombre d'octets écrits dans outchan est rapporté, soit comme valeur de retour d'un fcopy synchrone soit comme argument du callback pour un fcopy async

hrone.

Fcopy respecte les encodages et les traductions de caractères configurés pour les canaux. Cela signifie que les caractères entrants sont convertis d'abord en UTF-8 puis dans l'encodage du canal fcopy écrit. Voir l'entrée de manuel pour fconfigure pour les détails sur les options -encoding et -translation. Aucune conversion n'est effectuée si les deux canaux sont réglés sur l'encodage « binary » et ont des traductions correspondantes. Si seul le canal de sortie est réglé sur l'encodage « binary », le système écrira la représentation UTF-8 interne des caractères entrants. Si seul

le canal d'entrée est réglé sur l'encodage « binary », le système supposera que les octets entrants sont des caractères UTF-8 valides et les conver
tira selon l'encodage de sortie. Le comportement du système pour les octets qui ne sont pas des caractères UTF-8 valides est indéfini dans ce cas.

possible.

proc Cleanup {in out bytes {error {}}} {
    global total
    set total $bytes
    close $in
    close $out
    if {[string length $error] != 0} {
        # error occurred during the copy
    }
}

Le troisième exemple copie par morceaux et teste la fin de fichier dans le callback de

commande. 
proc CopyMore {in out chunk bytes {error {}}} {
    global total done
    incr total $bytes
    if {([string length $error] != 0) || [eof $in]} {
        set done $total
        close $in
        close $out
    } else {
        fcopy $in $out -size $chunk \
                -command [list CopyMore $in $out $chunk]
    }
}
set in [open $file1]
set out [socket $server $port]
set chunk 1024
set total 0
fcopy $in $out -size $chunk \
        -comma
nd [list CopyMore $in $
out $chunk] vwait done

     global flows done
     puts "$dir is over."
     incr flows -1
     if {$flows<=0} {set done 1}
