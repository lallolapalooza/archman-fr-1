DESCRIPTIO

N

ferm est une interface pour iptables. Il lit les règles à partir d'un fichier de configuration structuré et appelle iptables(8) pour les insérer dans le noyau en cours

d'exécution.

Le but de ferm est de rendre les règles de pare-feu faciles à écrire et faciles à lire. Il tente de réduire la tâche fastidieuse d'écrire les règles, permettant ainsi à l'administrateur du pare-feu de consacrer plus de temps au développement de bonnes règles plutôt qu'à l'implémentation correcte de la

règle.

Pour y parvenir, ferm utilise un langage de configuration simple mais puissant, qui permet les variables, les fonctions, les tableaux et les blocs. Il permet également d'inclure d'autres fichiers, vous permettant de créer des bibliothèques de structures et de fonctions couramment

utilisées.

ferm, prononcé « firm », signifie « For Easy Rul

e Making » (Pour une fabr
ication facile de règles).

INTRODUCTIO

N

Commençons par un exemple simple

: 
chain INPUT {
    proto tcp ACCEPT;
}

Cela ajoutera une règle à la chaîne d'entrée prédéfinie, correspondant à et acceptant tous les paquets TCP. Ok, rendons cela plus compliqué

: 
chain (INPUT OUTPUT) {
    proto (udp tcp) ACCEPT;
}

Cela insérera 4 règles, à savoir 2 dans la chaîne input et 2 dans la chaîne output, correspondant à et acceptant à la fois les paquets UDP et TCP. Normalement, vous taperiez ceci

: 
iptables -A INPUT -p tcp -j ACCEPT
iptables -A OUTPUT -p tcp -j ACCEPT
iptables -A INPUT -p udp -j ACCEPT
iptables -A OUTPUT -p udp -j
ACCEPT

Notez combien moins de frappes nous devons faire ? :

-)

Fondamentalement, c'est tout ce qu'il y a à faire, bien que vous puissiez le rendre beaucoup plus complexe. Quelque chose à regarder

: 
chain INPUT {
    policy ACCEPT;
    daddr 10.0.0.0/8 proto tcp dport ! ftp jump mychain sport :1023 TOS 4 settos 8 mark 2;
    daddr 10.0.0.0/8 proto tcp dport ftp REJECT;
}

Mon point ici est que *vous* devez faire de belles règles, les garder lisibles pour vous et les autres, et ne pas en faire un

désordre.

Cela aiderait le lecteur si les règles de pare-feu résultantes étaient placées ici pour référence. De plus, vous pourriez inclure la version imbriquée avec une meilleure

lisibilité.

Essayez d'utiliser des commentaires pour montrer ce que vous faites

: 
# cette ligne active le proxy http transparent pour le réseau interne :
proto tcp if eth0 daddr ! 192.168.0.0/255.255.255.0
    dport http REDIRECT to-ports
3128;

Vous m'en serez reconnaissant plus tard

! 
chain INPUT {
    policy ACCEPT;
    interface (eth0 ppp0) {
        # refuser l'accès aux hackers notoires, revenir ici si aucune correspondance
        # n'a été trouvée pour reprendre le filtrage normal
        jump badguys;
        protocol tcp jump fw_tcp;
        protocol udp jump fw_udp;
    }
}

Plus vous imbriquez, mieux cela semble. Assurez-vous que l'ordre que vous spécifiez est correct, vous ne voudriez pas faire ceci

: 
chain FORWARD {
    proto ! udp DROP;
    proto tcp dport ftp ACCEPT;
}

car la deuxième règle ne correspondra jamais. La meilleure façon est de spécifier d'abord tout ce qui est autorisé, puis de refuser tout le reste. Regardez les exemples pour plus de bons aperçus. La plupart des gens font quelque chose comme ceci

: 
proto tcp {
    dport (
        ssh http ftp
    ) ACCEPT;
    dport 1024:65535 ! syn ACCEPT;
    DROP;
}

STRUCTURE D'UN FICHIER DE

PARE-FEU

La structure d'un fichier de pare-feu approprié ressemble à du code C simplifié. Seuls quelques caractères syntaxiques sont utilisés dans les fichiers de configuration de ferm. En dehors de ces caractères spéciaux, ferm utilise des « clés » et des « valeurs », pensez-y comme des options et des paramètres, ou comme des variables et des valeurs, peu

importe.

Avec ces mots, vous définissez les caractéristiques de votre pare-feu. Chaque pare-feu se compose de deux choses : d'abord, vérifier si le trafic réseau correspond à certaines conditions, et ensuite, quoi faire de ce

trafic.

Vous pouvez spécifier des conditions qui sont valides pour le programme d'interface noyau que vous utilisez, probablement iptables(8). Par exemple, dans iptables, lorsque vous essayez de faire correspondre des paquets TCP, vous diriez

: 
iptables --protocol
tcp

Dans ferm, cela deviendra

: 
protocol
tcp;

Juste taper ceci dans ferm ne fait rien, vous devez dire à ferm (en fait, vous devez dire à iptables(8) et au noyau) quoi faire avec tout trafic qui correspond à cette condition

: 
iptables --protocol tcp -j
ACCEPT

Ou, traduit en ferm

: 
protocol tcp
ACCEPT;

Le caractère ; est à la fin de chaque règle ferm. Ferm ignore les sauts de ligne, ce qui signifie que l'exemple ci-dessus est identique au suivant

: 
protocol tcp
ACCEPT;

Mots-clé

s

Dans la section précédente, nous avons déjà introduit quelques mots-clés de base comme "chain", "protocol" et "ACCEPT". Explorons leur

nature.

Il y a trois types de mots-clés

:
  • les mots-clés de localisation définissent où une règle sera créée. Exemple : &quot;table", "chaîne".
  • correspondance Les mots clés effectuent un test sur tous les paquets qui passent. La règle actuelle est sans effet si une (ou plusieurs) des correspondances n'est pas validée. Exemple : "proto", "daddr".

    La plupart des correspondances sont suivies d'un paramètre : "proto tcp", "daddr 172.16.0.0/12".

  • cible Les mots clés indiquent quoi faire avec un paquet. Exemple : "ACCEPT", "REJECT", "jump".

    Certaines cibles définissent des mots clés supplémentaires pour spécifier les détails : "REJECT reject-with icmp-net-unreachable".

Chaque règle se compose d'un emplacement et d'une cible, plus un nombre quelconque de correspondances :

table filter                  # emplacement
proto tcp dport (http https)  # correspondance
ACCEPT;                       # cible

Strictement parlant, il existe un quatrième type : les mots clés ferm (qui contrôlent le comportement interne de ferm), mais ils seront expliqués plus tard.

Paramètres

De nombreux mots clés acceptent des paramètres. Ceux-ci peuvent être spécifiés comme des littéraux, des références de variables ou des listes (tableaux) :

proto udp
saddr $TRUSTED_HOSTS;
proto tcp dport (http https ssh);
LOG log-prefix "alerte fun de wardriver : ";

Certains d'entre eux peuvent être niés (les listes ne peuvent pas être niées) :

proto !esp;
proto udp dport !domain;

Les mots clés qui ne prennent pas de paramètres sont niés par un préfixe '!' :

proto tcp !syn;

Lisez iptables(8) pour savoir où le ! peut être utilisé.

MOTS_CLÉS_DE_BASE

Mots_clés_d_emplacement

domain [ip|ip6]
Définit le domaine. "ip" signifie "IPv4" (iptables) et "ip6" est pour le support IPv6, en utilisant "ip6tables". La valeur par défaut est celle spécifiée avec --domain ou "ip" si l'option n'a pas été spécifiée.
table [filter|nat|mangle]
Spécifie dans quelle table netfilter cette règle sera insérée : "filter" (par défaut), "nat" ou "mangle".
chain [nom-de-chaîne]
Spécifie la chaîne netfilter (au sein de la table actuelle) à laquelle cette règle sera insérée. Les noms de chaînes prédéfinis courants sont "INPUT", "OUTPUT", "FORWARD", "PREROUTING", "POSTROUTING", en fonction de la table. Consultez la documentation netfilter pour plus de détails.

Si vous spécifiez une chaîne inexistante ici, ferm ajoutera la règle à une chaîne personnalisée portant ce nom.

policy [ACCEPT|DROP|..]
Spécifie la politique par défaut pour la chaîne actuelle (intégrée uniquement). Peut être une des cibles intégrées (ACCEPT, DROP, REJECT, ...). Un paquet qui ne correspond à aucune règle dans une chaîne sera traité comme spécifié par la politique.

Pour éviter toute ambiguïté, spécifiez toujours explicitement les politiques de toutes les chaînes prédéfinies.

@subchain ["NOM-DE-CHAÎNE"] { ... }
Fonctionne comme les opérateurs de bloc normaux (c'est-à-dire sans le mot clé @subchain), sauf que ferm déplace les règles à l'intérieur des accolades dans une nouvelle chaîne personnalisée. Le nom de cette chaîne est choisi automatiquement par ferm.

Dans de nombreux cas, c'est plus rapide qu'un simple bloc, car le noyau peut ignorer un grand bloc de règles lorsqu'une condition préalable est fausse. Imaginez l'exemple suivant :

table filter chain INPUT {
    saddr (1.2.3.4 2.3.4.5 3.4.5.6 4.5.6.7 5.6.7.8) {
        proto tcp dport (http https ssh) ACCEPT;
        proto udp dport domain ACCEPT;
    }
}

Cela génère 20 règles. Lorsqu'un paquet arrive qui ne valide pas la correspondance saddr, il vérifie néanmoins les 20 règles. Avec @subchain, cette vérification est effectuée une seule fois, ce qui entraîne un filtrage réseau plus rapide et une charge CPU réduite :

table filter chain INPUT {
    saddr (1.2.3.4 2.3.4.5 3.4.5.6 4.5.6.7 5.6.7.8) @subchain {
        proto tcp dport (http https ssh) ACCEPT;
        proto udp dport domain ACCEPT;
    }
}

Optionnellement, vous pouvez définir le nom de la sous-chaîne :

saddr (1.2.3.4 2.3.4.5 3.4.5.6) @subchain "foobar" {
    proto tcp dport (http https ssh) ACCEPT;
    proto udp dport domain ACCEPT;
}

Le nom peut être soit une chaîne littérale entre guillemets, soit une expression ferm développée telle que @cat("interface_", $iface) ou @substr($var,0,20).

Vous pouvez obtenir le même résultat en déclarant explicitement une chaîne personnalisée, mais vous pourriez trouver que l'utilisation de @subchain demande moins de frappe.

@gotosubchain ["NOM-DE-CHAÎNE"] { ... }
Fonctionne comme @subchain sauf qu'au lieu d'utiliser la cible jump, il utilise la cible goto. Voir la discussion ci-dessous pour la différence entre ces deux cibles.
@preserve
Préserve les règles existantes de la chaîne actuelle : 
chain (foo bar) @preserve;

Avec cette option, ferm charge l'ensemble de règles précédent à l'aide de iptables-save, extrait toutes les chaînes "préservées" et insère leurs données dans la sortie.

"Les chaînes préservées" ne doivent pas être modifiées avec ferm : aucune règle et aucune politique.

Si le nom de la chaîne commence et se termine par une barre oblique, ferm l'interprétera comme une expression régulière Perl et préservera toutes les chaînes correspondantes. Par exemple, ce qui suit préserve toutes les chaînes avec le préfixe KUBE-SEP- :

chain "/^KUBE-SEP-.*/" @preserve;

Mots_clés_de_correspondance_iptables_de_base

interface [nom-d-interface]
Définit le nom de l'interface, votre carte réseau externe, comme eth0, ou dialup comme ppp1, ou tout autre périphérique que vous souhaitez faire correspondre pour les paquets qui passent. C'est équivalent au commutateur "-i" dans iptables(8).
outerface [nom-d-interface]
Identique à interface, uniquement pour faire correspondre l'interface sortante d'un paquet, comme dans iptables(8).
protocol [nom-de-protocole|numéro-de-protocole]
Actuellement pris en charge par le noyau : TCP, UDP et ICMP, ou leurs numéros respectifs.

Au lieu de protocol, vous pouvez également utiliser le raccourci proto.

saddr|daddr [spécification-d-adresse]
Correspond aux paquets provenant de l'adresse spécifiée (saddr) ou destinés à l'adresse (daddr).

Exemples :

saddr 192.168.0.0/24 ACCEPT; # (identique au suivant :)
saddr 192.168.0.0/255.255.255.0 ACCEPT;
daddr mon.domaine.com ACCEPT;
fragment
Spécifie que seuls les paquets IP fragmentés doivent correspondre. Lorsque les paquets sont plus grands que la taille maximale de paquet que votre système peut gérer (appelée Unité de Transmission Maximale ou MTU), ils seront coupés en morceaux et envoyés un par un sous forme de paquets uniques. Voir ifconfig(8) si vous souhaitez trouver la MTU pour votre système (la valeur par défaut est généralement de 1500 octets).

Les fragments sont fréquemment utilisés dans les attaques DOS car il est impossible de connaître l'origine d'un paquet fragmenté.

sport|dport [spécification-de-port]
Correspond aux paquets sur le port TCP ou UDP spécifié. "sport" correspond au port source, et dport correspond au port de destination.

Cette correspondance ne peut être utilisée qu'après avoir spécifié "protocol tcp" ou "protocol udp", car seuls ces deux protocoles ont réellement des ports.

Et quelques exemples de ports/plages valides :

dport 80 ACCEPT;
dport http ACCEPT;
dport ssh:http ACCEPT;
dport 0:1023 ACCEPT; # équivalent à :1023
dport 1023:65535 ACCEPT;
syn
Spécifie que le drapeau SYN dans un paquet TCP doit correspondre, qui est utilisé pour établir de nouvelles connexions TCP. Vous pouvez identifier les connexions entrantes avec ceci, et décider si vous souhaitez les autoriser ou non. Les paquets qui n'ont pas ce drapeau proviennent probablement d'une connexion déjà établie, il est donc considéré comme raisonnablement sûr de les laisser passer.
module [nom-de-module]
Charge un module iptables. La plupart des modules fournissent des mots clés de correspondance supplémentaires. Nous y reviendrons plus tard.

Au lieu de module, vous pouvez également utiliser le raccourci mod.

Dans le code ferm réel, les variables sont utilisées comme n'importe quel autre paramètre de mot-clé

ACCEPT;

Notez que les variables ne peuvent être utilisées que dans les paramètres de mot-clé ("192.168.1.1", "http") ; elles ne peuvent pas contenir de mots-clés ferm comme "proto" ou

"interface".

Les variables ne sont valides que dans le bloc courant

@def $DEV_INTERNET = eth1;

    proto tcp {
        @def $DEV_INTERNET = ppp0;
        interface $DEV_INTERNET dport http ACCEPT;

    interface $DEV_INTERNET DROP;
}

sera développé en

chain INPUT {
    proto tcp {
        interface ppp0 dport http ACCEPT;
    }
    interface eth1 DROP;
}

Le "def $DEV_INTERNET = ppp0" n'est valide que dans le bloc "proto tcp" ; le bloc parent connaît toujours "set $DEV_INTERNET =

eth1".

s

    ferm(1) - ferm Manual Page

    NOM

    ferm - outil de gestion de pare-feu basé sur iptables

    SYNOPSIS

    ferm [OPTIONS] ... <config-file>

    DESCRIPTION

    ferm est un outil de gestion de pare-feu qui permet de définir des règles de pare-feu dans des fichiers de configuration structurés et lisibles. Il génère ensuite des commandes iptables correspondantes pour appliquer ces règles.

    OPTIONS

    -v, --verbose
    Augmente le niveau de verbosité. Peut être utilisé plusieurs fois pour augmenter davantage le niveau.
    -f, --force
    Force l'application des règles, même si des erreurs surviennent lors de la génération des commandes iptables.
    -c, --check
    Vérifie la syntaxe du fichier de configuration sans appliquer les règles.
    -p, --print
    Imprime les commandes iptables générées sans les exécuter.
    --flush
    Supprime toutes les règles de pare-feu actuelles avant d'appliquer les nouvelles.
    --restore
    Restaure les règles de pare-feu à partir d'un fichier sauvegardé (généralement créé par ferm --save).
    --save [fichier]
    Sauvegarde les règles de pare-feu actuelles dans le fichier spécifié (ou dans un fichier par défaut).
    -h, --help
    Affiche un message d'aide et quitte.
    -V, --version
    Affiche les informations de version et quitte.

    FICHIERS DE CONFIGURATION

    Le fichier de configuration de ferm utilise une syntaxe spécifique pour définir les interfaces, les chaînes, les règles et les politiques par défaut.

    EXEMPLES

    Appliquer les règles définies dans /etc/ferm/ferm.conf :

    ferm /etc/ferm/ferm.conf

    Vérifier la syntaxe du fichier de configuration :

    ferm --check /etc/ferm/ferm.conf

    Imprimer les commandes iptables générées :

    ferm --print /etc/ferm/ferm.conf
