DESCRIPTIO

N

Les macros de test de fonctionnalités permettent au programmeur de contrôler les définitions qui sont exposées par les fichiers d'en-tête système lors de la compilation d'un

programme.

REMARQUE : afin d'être efficaces, une macro de test de fonctionnalités doit être définie avant d'inclure n'importe quel fichier d'en-tête. Cela peut être fait soit dans la commande de compilation (cc -DMACRO=valeur) soit en définissant la macro dans le code source avant d'inclure n'importe quels en-têtes. L'exigence selon laquelle la macro doit être définie avant d'inclure n'importe quel fichier d'en-tête existe parce que les fichiers d'en-tête peuvent s'inclure librement les uns les autres. Ainsi, par exemple, dans les lignes suivantes, définir la macro _GNU_SOURCE peut n'avoir aucun effet parce que le fichier d'en-tête <abc.h> inclut lui-même <xyz.h> (POSIX le permet explicitement)

: 


#include <abc.h>
#define _GNU_SOURCE
#include <xyz.
h>

Certaines macros de test de fonctionnalités sont utiles pour créer des applications portables, en empêchant l'exposition de définitions non standard. D'autres macros peuvent être utilisées pour exposer des définitions non standard qui ne sont pas exposées par

défaut.

Les effets précis de chacune des macros de test de fonctionnalités décrites ci-dessous peuvent être déterminés en inspectant le fichier d'en-tête <features.h>. Remarque : les applications n'ont pas besoin d'inclure directement <features.h> ; en effet, le faire est activement découragé. Voir

REMARQUES.

_XOPEN_SOURCE_EXTENDED
Si cette macro est définie, *et* que _XOPEN_SOURCE est définie, alors les définitions correspondant aux extensions UNIX XPG4v2 (SUSv1) (UNIX 95) sont exposées. Définir _XOPEN_SOURCE avec une valeur de 500 ou plus produit également le même effet que définir _XOPEN_SOURCE_EXTENDED. L'utilisation de _XOPEN_SOURCE_EXTENDED dans le nouveau code source doit être évitée.
Étant donné que définir _XOPEN_SOURCE avec une valeur de 500 ou plus a le même effet que définir _XOPEN_SOURCE_EXTENDED, cette dernière macro de test de fonctionnalité (obsolète) n'est généralement pas décrite dans la SYNOPSIS des pages de manuel.
_ISOC99_SOURCE (depuis glibc 2.1.3)
Expose les déclarations conformes à la norme ISO C99.
Les versions antérieures de glibc 2.1.x reconnaissaient une macro équivalente nommée _ISOC9X_SOURCE (car la norme C99 n'était pas encore finalisée). Bien que l'utilisation de cette macro soit obsolète, glibc continue de la reconnaître pour des raisons de compatibilité ascendante.
Définir _ISOC99_SOURCE expose également les définitions de l'amendement 1 de la norme ISO C (1990) ("C95"). (Le principal changement dans C95 était la prise en charge des jeux de caractères internationaux.)
L'invocation du compilateur C avec l'option -std=c99 produit les mêmes effets que la définition de cette macro.
_ISOC11_SOURCE (depuis glibc 2.16)
Expose les déclarations conformes à la norme ISO C11. Définir cette macro active également les fonctionnalités C99 et C95 (comme _ISOC99_SOURCE).
L'invocation du compilateur C avec l'option -std=c11 produit les mêmes effets que la définition de cette macro.
_LARGEFILE64_SOURCE
Expose les définitions de l'API alternative spécifiée par le LFS (Large File Summit) comme une "extension transitoire" à la Single UNIX Specification. (Voir http://opengroup.org/platform/lfs.html.) L'API alternative consiste en un ensemble de nouveaux objets (c'est-à-dire des fonctions et des types) dont les noms se terminent par "64" (par exemple, off64_t par rapport à off_t, lseek64() par rapport à lseek(), etc.). Les nouveaux programmes ne devraient pas utiliser cette macro ; il convient plutôt d'utiliser _FILE_OFFSET_BITS=64.
_LARGEFILE_SOURCE
Cette macro était historiquement utilisée pour exposer certaines fonctions (notamment fseeko(3) et ftello(3)) qui traitent les limitations des API antérieures (fseek(3) et ftell(3)) qui utilisent long pour les décalages de fichiers. Cette macro est implicitement définie si _XOPEN_SOURCE est définie avec une valeur supérieure ou égale à 500. Les nouveaux programmes ne devraient pas utiliser cette macro ; définir _XOPEN_SOURCE comme décrit ci-dessus ou définir _FILE_OFFSET_BITS avec la valeur 64 est le mécanisme préféré pour obtenir le même résultat.
_FILE_OFFSET_BITS
Définir cette macro avec la valeur 64 convertit automatiquement les références aux fonctions et types de données 32 bits liés aux opérations d'E/S de fichiers et de système de fichiers en références à leurs homologues 64 bits. Ceci est utile pour effectuer des E/S sur de gros fichiers (> 2 Go) sur des systèmes 32 bits. C'est également utile lors de l'appel de fonctions telles que copy_file_range(2) qui ont été ajoutées plus récemment et qui n'existent qu'en versions 64 bits. (Définir cette macro permet aux programmes correctement écrits d'utiliser de gros fichiers avec une simple recompilation.)
Les systèmes 64 bits permettent naturellement des tailles de fichiers supérieures à 2 Go, et sur ces systèmes, cette macro n'a aucun effet.
_TIME_BITS
Définir cette macro avec la valeur 64 change la largeur de time_t(3type) à 64 bits, ce qui permet de gérer les horodatages au-delà de 2038. Elle est étroitement liée à _FILE_OFFSET_BITS et, selon l'implémentation, peut nécessiter sa définition. Cette macro est disponible depuis glibc 2.34.
_BSD_SOURCE (dépréciée depuis glibc 2.20)
Définir cette macro avec n'importe quelle valeur permet aux fichiers d'en-tête d'exposer des définitions dérivées de BSD.
Dans les versions de glibc jusqu'à et y compris 2.18, définir cette macro entraînait également la préférence des définitions BSD dans certaines situations où les normes entraient en conflit, à moins qu'une ou plusieurs des macros _SVID_SOURCE, _POSIX_SOURCE, _POSIX_C_SOURCE, _XOPEN_SOURCE, _XOPEN_SOURCE_EXTENDED, ou _GNU_SOURCE ne soient définies, auquel cas les définitions BSD étaient défavorisées. Depuis glibc 2.19, _BSD_SOURCE ne préfère plus les définitions BSD en cas de conflit.
Depuis glibc 2.20, cette macro est dépréciée. Elle a maintenant le même effet que la définition de _DEFAULT_SOURCE, mais génère un avertissement à la compilation (sauf si _DEFAULT_SOURCE est également définie). Utilisez _DEFAULT_SOURCE à la place. Pour permettre la compilation sans avertissement du code qui nécessite _BSD_SOURCE dans glibc 2.19 et versions antérieures, et _DEFAULT_SOURCE dans glibc 2.20 et versions ultérieures, définissez *à la fois* _BSD_SOURCE et _DEFAULT_SOURCE.
_SVID_SOURCE (dépréciée depuis glibc 2.20)
Définir cette macro avec n'importe quelle valeur permet aux fichiers d'en-tête d'exposer des définitions dérivées de System V. (SVID == System V Interface Definition ; voir standards(7).)
Depuis glibc 2.20, cette macro est dépréciée de la même manière que _BSD_SOURCE.
_DEFAULT_SOURCE (depuis glibc 2.19)
Cette macro peut être définie pour garantir que les définitions "par défaut" sont fournies même lorsque les défauts seraient autrement désactivés, comme c'est le cas lorsque des macros individuelles sont explicitement définies, ou que le compilateur est invoqué dans l'un de ses modes "standard" (par exemple, cc -std=c99). Définir _DEFAULT_SOURCE sans définir d'autres macros individuelles ou sans invoquer le compilateur dans l'un de ses modes "standard" n'a aucun effet.
Les définitions "par défaut" comprennent celles requises par POSIX.1-2008 et ISO C99, ainsi que diverses définitions initialement dérivées de BSD et System V. Sur glibc 2.19 et versions antérieures, ces défauts étaient approximativement équivalents à la définition explicite des éléments suivants :

cc -D_BSD_SOURCE -D_SVID_SOURCE -D_POSIX_C_SOURCE=200809

_ATFILE_SOURCE (depuis glibc 2.4)
Définir cette macro avec n'importe quelle valeur permet aux fichiers d'en-tête d'exposer les déclarations d'une série de fonctions avec le suffixe "at" ; voir openat(2). Depuis glibc 2.10, cette macro est également implicitement définie si _POSIX_C_SOURCE est définie avec une valeur supérieure ou égale à 200809L.
_GNU_SOURCE
Définir cette macro (avec n'importe quelle valeur) définit implicitement _ATFILE_SOURCE, _LARGEFILE64_SOURCE, _ISOC99_SOURCE, _XOPEN_SOURCE_EXTENDED, _POSIX_SOURCE, _POSIX_C_SOURCE avec la valeur 200809L (200112L avant glibc 2.10 ; 199506L avant glibc 2.5 ; 199309L avant glibc 2.1) et _XOPEN_SOURCE avec la valeur 700 (600 avant glibc 2.10 ; 500 avant glibc 2.2). De plus, diverses extensions spécifiques à GNU sont également exposées.
Depuis glibc 2.19, définir _GNU_SOURCE a également pour effet de définir implicitement _DEFAULT_SOURCE. Avant glibc 2.20, définir _GNU_SOURCE avait également pour effet de définir implicitement _BSD_SOURCE et _SVID_SOURCE.
_REENTRANT
Historiquement, sur diverses bibliothèques C, il était nécessaire de définir cette macro dans tout code multithreadé. (Certaines bibliothèques C peuvent encore l'exiger.) Dans glibc, cette macro exposait également des définitions de certaines fonctions réentrantes.
Cependant, glibc est thread-safe par défaut depuis de nombreuses années ; depuis glibc 2.3, le seul effet de la définition de _REENTRANT a été d'activer une ou deux des mêmes déclarations qui sont également activées en définissant _POSIX_C_SOURCE avec une valeur de 199606L ou plus.
_REENTRANT est maintenant obsolète. Dans glibc 2.25 et versions ultérieures, définir _REENTRANT équivaut à définir _POSIX_C_SOURCE avec la valeur 199606L. Si un niveau de conformité POSIX supérieur est sélectionné par tout autre moyen (tel que _POSIX_C_SOURCE lui-même, _XOPEN_SOURCE, _DEFAULT_SOURCE, ou _GNU_SOURCE), alors définir _REENTRANT n'a aucun effet.
Cette macro est automatiquement définie si l'on compile avec cc -pthread.
_THREAD_SAFE
Synonyme de _REENTRANT (dépréciée), fourni pour la compatibilité avec certaines autres implémentations.
_FORTIFY_SOURCE (depuis glibc 2.3.4)
Définir cette macro permet d'effectuer quelques vérifications légères pour détecter certains débordements de tampon lors de l'utilisation de diverses fonctions de manipulation de chaînes et de mémoire (par exemple, memcpy(3), memset(3), stpcpy(3), strcpy(3), strncpy(3), strcat(3), strncat(3), sprintf(3), snprintf(3), vsprintf(3), vsnprintf(3), gets(3), et leurs variantes en caractères larges). Pour certaines fonctions, la cohérence des arguments est vérifiée ; par exemple, une vérification est effectuée pour s'assurer que open(2) a reçu un argument mode lorsque les drapeaux spécifiés incluent O_CREAT. Pas toutes
l problèmes ne sont détectés, seulement
quelques cas courants.
Si _FORTIFY_SOURCE est défini à 1, avec un niveau d'optimisation du compilateur de 1 (gcc -O1) et supérieur, des vérifications qui ne devraient pas changer le comportement des programmes conformes sont effectuées. Avec _FORTIFY_SOURCE défini à 2, des vérifications supplémentaires sont ajoutées, mais certains programmes conformes peuvent

Certaines des vérifications peuvent être effectuées à la compilation (via la logique des macros implémentée dans les fichiers d'en-tête), et résultent en des avertissements du compilateur ; d'autres vérifications ont lieu à l'exécution, et résultent en une erreur d'exécution si la vérification
échoue.

Par exemple, un programme où l'argument de taille de malloc(3) est variable peut maintenant être

NOTE

<features.h> est un fichier d'en-tête spécifique à Linux/glibc. D'autres systèmes ont un fichier analogue, mais généralement avec un nom différent. Ce fichier d'en-tête est inclus automatiquement par d'autres fichiers d'en-tête selon les besoins : il n'est pas nécessaire de l'inclure explicitement afin d'utiliser les macros de test de

Selon lesquelles des macros de test de fonctionnalité ci-dessus sont définies, <features.h> définit en interne diverses autres macros qui sont vérifiées par d'autres fichiers d'en-tête glibc. Ces macros ont des noms préfixés par deux tirets bas (par exemple, __USE_MISC). Les programmes ne devraient jamais définir ces macros directement : à la place, la ou les macros de test
