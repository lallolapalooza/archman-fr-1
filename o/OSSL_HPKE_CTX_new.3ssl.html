DESCRIPTION

Ces fonctions fournissent une API pour utiliser la forme de chiffrement hybride à clé publique (HPKE) définie dans la RFC9180. La compréhension de la spécification HPKE est probablement nécessaire avant d'utiliser ces API. HPKE est utilisé par diverses autres spécifications IETF, notamment la spécification TLS Encrypted Client Hello (ECH) et d'autres.

HPKE est un construct standardisé et très flexible pour chiffrer "vers" une clé publique qui prend en charge les combinaisons d'une méthode d'encapsulation de clé (KEM), d'une fonction de dérivation de clé (KDF) et d'un algorithme de chiffrement authentifié avec données associées (AEAD), avec authentification optionnelle de l'expéditeur.

L'expéditeur et le destinataire ici utiliseront généralement une application ou un protocole qui utilise HPKE. Par exemple, avec ECH, l'expéditeur sera un navigateur et le destinataire sera un serveur web.

Structures de données

OSSL_HPKE_SUITE est une structure qui contient les identifiants des algorithmes utilisés pour les opérations KEM, KDF et AEAD.

OSSL_HPKE_CTX est un contexte qui maintient l'état interne lorsque les opérations HPKE sont effectuées. Des objets OSSL_HPKE_CTX séparés doivent être utilisés pour l'expéditeur et le destinataire. Tenter d'utiliser un seul contexte pour les deux entraînera des erreurs.

Identifiants OSSL_HPKE_SUITE

Les identifiants utilisés par OSSL_HPKE_SUITE sont :

L'identifiant KEM kem_id est l'un des suivants :

0x10 OSSL_HPKE_KEM_ID_P256
0x11 OSSL_HPKE_KEM_ID_P384
0x12 OSSL_HPKE_KEM_ID_P521
0x20 OSSL_HPKE_KEM_ID_X25519
0x21 OSSL_HPKE_KEM_ID_X448

L'identifiant KDF kdf_id est l'un des suivants :

0x01 OSSL_HPKE_KDF_ID_HKDF_SHA256
0x02 OSSL_HPKE_KDF_ID_HKDF_SHA384
0x03 OSSL_HPKE_KDF_ID_HKDF_SHA512

L'identifiant AEAD aead_id est l'un des suivants :

0x01 OSSL_HPKE_AEAD_ID_AES_GCM_128
0x02 OSSL_HPKE_AEAD_ID_AES_GCM_256
0x03 OSSL_HPKE_AEAD_ID_CHACHA_POLY1305
0xFFFF OSSL_HPKE_AEAD_ID_EXPORTONLY
Le dernier identifiant ci-dessus indique que les opérations AEAD ne sont pas nécessaires. OSSL_HPKE_export() peut être utilisé, mais OSSL_HPKE_open() et OSSL_HPKE_seal() renverront une erreur s'ils sont appelés avec un contexte utilisant cet identifiant AEAD.

Modes HPKE

HPKE prend en charge les variantes d'authentification suivantes à l'aide d'un identifiant de mode :

OSSL_HPKE_MODE_BASE, 0x00
L'authentification n'est pas utilisée.
OSSL_HPKE_MODE_PSK, 0x01
Authentifie la possession d'une clé pré-partagée (PSK).
OSSL_HPKE_MODE_AUTH, 0x02
Authentifie la possession d'une clé privée d'expéditeur basée sur KEM.
OSSL_HPKE_MODE_PSKAUTH, 0x03
Une combinaison de OSSL_HPKE_MODE_PSK et OSSL_HPKE_MODE_AUTH. La PSK et la clé publique/privée d'authentification de l'expéditeur doivent être fournies avant que l'opération d'encapsulation/désencapsulation ne fonctionne.

Pour plus d'informations relatives à l'authentification, voir « Modes HPKE à clé pré-partagée » et « Modes HPKE authentifiés par l'expéditeur ».

Rôles HPKE

Les contextes HPKE ont un rôle - soit expéditeur, soit destinataire. Ceci est utilisé pour contrôler quelles fonctions peuvent être appelées et pour que les expéditeurs ne réutilisent pas une clé et un nonce avec différents textes en clair.

OSSL_HPKE_CTX_free(), OSSL_HPKE_export(), OSSL_HPKE_CTX_set1_psk() et OSSL_HPKE_CTX_get_seq() peuvent être appelés quel que soit le rôle.

OSSL_HPKE_ROLE_SENDER, 0
Un OSSL_HPKE_CTX avec ce rôle peut être utilisé avec OSSL_HPKE_encap(), OSSL_HPKE_seal(), OSSL_HPKE_CTX_set1_ikme() et OSSL_HPKE_CTX_set1_authpriv().
OSSL_HPKE_ROLE_RECEIVER, 1
Un OSSL_HPKE_CTX avec ce rôle peut être utilisé avec OSSL_HPKE_decap(), OSSL_HPKE_open(), OSSL_HPKE_CTX_set1_authpub() et OSSL_HPKE_CTX_set_seq().

Appeler une fonction avec un rôle incorrect défini sur OSSL_HPKE_CTX entraînera une erreur.

Limites de taille des paramètres

Afin d'améliorer l'interopérabilité, la section 7.2.1 de la RFC9180 suggère une taille maximale RECOMMANDÉE de 64 octets pour divers paramètres d'entrée. Dans cette implémentation, nous appliquons une limite de 66 octets pour ikmlen, psklen et labe

llen, et pour la longueur de la chaîne pskid pour les fonctions HPKE ci-dessous. La constante OSSL_HPKE_MAX_PARMLEN est définie comme la limite de cette valeur. (Nous avons choisi 66 octets afin de pouvoir valider tous les vecteurs de test présents dans RFC9180, Annexe A.)

Conformément à RFC9180, section 9.5, nous définissons une constante OSSL_HPKE_MIN_PSKLEN avec une valeur de 32 pour la longueur minimale d'une clé pré-partagée, passée dans psklen.

Bien que RFC9180 recommande également une limite de 64 octets pour le paramètre infolen, cela n'est pas suffisant pour le traitement du TLS Encrypted ClientHello (ECH), nous imposons donc une limite de OSSL_HPKE_MAX_INFOLEN avec une valeur de 1024 comme limite pour le paramètre infolen.

Context Construct/Free

OSSL_HPKE_CTX_new() crée un objet de contexte OSSL_HPKE_CTX utilisé pour les opérations HPKE ultérieures, étant donné un mode (voir "HPKE Modes"), un suite (voir "OSSL_HPKE_SUITE Identifiers") et un role (voir "HPKE Roles"). Les paramètres libctx et propq sont utilisés lors de la récupération d'algorithmes auprès des fournisseurs et peuvent être définis sur NULL.

OSSL_HPKE_CTX_free() libère le contexte OSSL_HPKE_CTX ctx qui a été créé précédemment par un appel à OSSL_HPKE_CTX_new(). Si l'argument de OSSL_HPKE_CTX_free() est NULL, rien n'est fait.

APIs de l'expéditeur

L'objectif d'un expéditeur est d'utiliser HPKE pour chiffrer à l'aide d'une clé publique, via l'utilisation d'un KEM, puis d'un KDF et enfin d'un AEAD. La première étape consiste à encapsuler (en utilisant OSSL_HPKE_encap()) la valeur publique de l'expéditeur à l'aide de la clé publique du destinataire (pub) et à dériver en interne des secrets. Cela produit la valeur publique encapsulée (enc) à envoyer au destinataire dans le protocole qui utilise HPKE. Après avoir effectué l'étape d'encapsulation, l'expéditeur peut ensuite effectuer un ou plusieurs appels à OSSL_HPKE_seal() pour chiffrer des textes en clair à l'aide du secret stocké dans ctx.

OSSL_HPKE_encap() utilise le contexte HPKE ctx, la valeur publique du destinataire pub de taille publen, et un paramètre optionnel info de taille infolen, pour produire la valeur publique encapsulée enc. En entrée, enclen doit contenir la taille maximale du tampon enc, et retourne la taille de sortie. Une erreur se produira si enclen en entrée est plus petit que la valeur retournée par OSSL_HPKE_get_public_encap_size(). info peut être utilisé pour lier d'autres artefacts de protocole ou d'application tels que des identifiants. Généralement, la valeur publique encapsulée enc correspond à une valeur privée éphémère à usage unique créée dans le cadre du processus d'encapsulation. Un seul appel à OSSL_HPKE_encap() est autorisé pour un OSSL_HPKE_CTX donné.

OSSL_HPKE_seal() prend le contexte OSSL_HPKE_CTX ctx, le tampon de texte en clair pt de taille ptlen et un tampon optionnel de données authentifiées supplémentaires aad de taille aadlen, et retourne le texte chiffré ct de taille ctlen. En entrée, ctlen doit contenir la taille maximale du tampon ct, et retourne la taille de sortie. Une erreur se produira si ctlen en entrée est plus petit que la valeur retournée par OSSL_HPKE_get_public_encap_size().

OSSL_HPKE_encap() doit être appelé avant OSSL_HPKE_seal(). OSSL_HPKE_seal() peut être appelé plusieurs fois, avec un "nonce" interne incrémenté de un après chaque appel.

APIs du destinataire

Les destinataires utilisant HPKE nécessitent une valeur privée généralement moins éphémère afin que la valeur publique puisse être distribuée aux expéditeurs potentiels via le protocole utilisé par HPKE. Pour cette raison, les destinataires généreront généralement d'abord une paire de clés et devront gérer leur valeur de clé privée en utilisant des mécanismes standard sortant du cadre de cette API. Les clés privées utilisent des pointeurs EVP_PKEY(3) normaux, de sorte que les mécanismes normaux de gestion des clés privées peuvent être utilisés pour les valeurs pertinentes.

Afin de permettre l'encapsulation, le destinataire doit rendre sa valeur publique disponible à l'expéditeur. Il n'y a pas de format HPKE générique défini pour cela - le formatage pertinent est destiné à être défini par l'application/les protocoles qui utilisent HPKE. ECH, par exemple, définit une structure de données ECHConfig qui combine la valeur publique avec d'autres éléments de données ECH. Les fonctions de bibliothèque normales doivent donc être utilisées pour extraire la valeur publique dans le format requis en fonction de la EVP_PKEY(3) pour la valeur privée.

OSSL_HPKE_keygen() offre un moyen aux destinataires de générer une paire de clés basée sur la suite HPKE à utiliser. Elle retourne un pointeur EVP_PKEY(3) pour la valeur privée priv et une clé publique encodée pub de taille publen. En entrée, publen doit contenir la taille maximale du tampon pub, et retourne la taille de sortie. Une erreur se produira si publen en entrée est trop petit. Les paramètres libctx et propq sont utilisés lors de la récupération d'algorithmes auprès des fournisseurs et peuvent être définis sur NULL. La spécification HPKE définit également un schéma de génération de clés déterministe où la valeur privée est dérivée d'un matériel de clé initial (IKM), donc OSSL_HPKE_keygen() a également une option pour utiliser ce schéma, en utilisant le paramètre ikm de taille ikmlen. Si ikm est NULL ou si ikmlen est zéro, alors une clé générée aléatoirement pour la suite pertinente sera produite. Si requis, ikmlen doit être supérieur ou égal à OSSL_HPKE_get_recommended_ikmelen().

OSSL_HPKE_decap() prend en entrée la valeur publique encapsulée de l'expéditeur produite par OSSL_HPKE_encap() (enc) et le pointeur EVP_PKEY(3) du destinataire (prov), puis régénère le secret interne dérivé par l'expéditeur. Comme précédemment, un paramètre optionnel info permet de lier ce secret dérivé à d'autres artefacts d'application/protocole. Un seul appel à OSSL_HPKE_decap() est autorisé pour un OSSL_HPKE_CTX donné.

OSSL_HPKE_open() est utilisé par le destinataire pour déchiffrer le texte chiffré ct de taille ctlen en utilisant le ctx et les données authentifiées supplémentaires aad de taille aadlen, pour produire le texte en clair pt de taille ptlen. En entrée, ptlen doit contenir la taille maximale du tampon pt, et retourne la taille de sortie. Un tampon pt de même taille que le tampon ct suffira - généralement la sortie en texte clair sera légèrement plus petite que l'entrée chiffrée. Une erreur se produira si ptlen en entrée est trop petit. OSSL_HPKE_open() peut être appelé plusieurs fois, mais comme avec OSSL_HPKE_seal(), il y a une valeur de nonce incrémentée en interne, donc les textes chiffrés doivent être présentés dans le même ordre que celui utilisé par OSSL_HPKE_seal(). Voir "Ré-ordonnancement" si vous avez besoin de traiter plusieurs textes chiffrés dans un ordre différent.

Exportation des secrets

HPKE définit un moyen de produire des secrets exportés à utiliser par l'application.

OSSL_HPKE_export() prend en entrée le OSSL_HPKE_CTX, et une étiquette fournie par l'application label de taille labellen, pour produire un secret secret de taille secretlen. L'expéditeur doit d'abord appeler OSSL_HPKE_encap(), et le destinataire doit appeler OSSL_HPKE_decap() afin de dériver le même secret partagé.

Plusieurs appels à OSSL_HPKE_export() avec les mêmes entrées produiront le même secret. OSSL_HPKE_AEAD_ID_EXPORTONLY peut être utilisé comme aead_id de OSSL_HPKE_SUITE qui est passé à OSSL_HPKE_CTX_new() si l'utilisateur a besoin de produire un secret partagé, mais ne souhaite pas effectuer le chiffrement HPKE.

Modes HPKE authentifiés par l'expéditeur

HPKE définit des modes qui prennent en charge l'authentification de l'expéditeur basée sur KEM OSSL_HPKE_MODE_AUTH et OSSL_HPKE_MODE_PSKAUTH. Cela fonctionne en liant les valeurs privées/publiques d'authentification de l'expéditeur aux opérations d'encapsulation et de décapsulation. La clé utilisée pour de tels modes doit également utiliser le même KEM que celui utilisé pour l'échange global. OSSL_HPKE_keygen() peut être utilisé pour générer la valeur privée requise.

OSSL_HPKE_CTX_set1_authpriv() peut être utilisé par l'expéditeur pour définir la clé privée EVP_PKEY de l'expéditeur priv dans le OSSL_HPKE_CTX ctx avant d'appeler OSSL_HPKE_encap().

OSSL_HPKE_CTX_set1_authpub() peut être utilisé par le destinataire pour définir la clé publique encodée de l'expéditeur pub de taille publen dans le OSSL_HPKE_CTX ctx avant d'appeler OSSL_HPKE_decap().

Modes HPKE à clé pré-partagée

HPKE définit également un équivalent symétrique à l'authentification décrite ci-dessus en utilisant une clé pré-partagée (PSK) et un identifiant PSK. Les PSK peuvent être utilisés avec les modes OSSL_HPKE_MODE_PSK et OSSL_HPKE_MODE_PSKAUTH.

OSSL_HPKE_CTX_set1_psk() définit la chaîne d'identifiant PSK pskid, et le tampon PSK psk de taille psklen dans le ctx. Si nécessaire, cela doit être appelé avant OSSL_HPKE_encap() ou OSSL_HPKE_decap(). Conformément à RFC9180, si nécessaire, psk et pskid doivent être définis sur des valeurs non NULL. Les PSK étant symétriques, les mêmes appels doivent avoir lieu des deux côtés, expéditeur et destinataire.

Génération de clés déterministe pour les expéditeurs

Normalement, la clé privée éphémère de l'expéditeur est générée aléatoirement dans OSSL_HPKE_encap() et reste secrète. OSSL_HPKE_CTX_set1_ikme() permet à l'utilisateur de remplacer ce comportement en définissant un matériel de clé d'entrée déterministe ikm de taille ikmlen dans le OSSL_HPKE_CTX ctx. Si nécessaire, OSSL_HPKE_CTX_set1_ikme() peut éventuellement être appelé avant OSSL_HPKE_encap(). ikmlen doit être supérieur ou égal à OSSL_HPKE_get_recommended_ikmelen().

Il est généralement indésirable d'utiliser OSSL_HPKE_CTX_set1_ikme(), car cela expose le secret pertinent à l'application plutôt que de le préserver dans la bibliothèque, et est plus susceptible de conduire à l'utilisation de valeurs prévisibles ou de valeurs qui fuitent.

Ré-ordonnancement

NOM

OSSL_HPKE_CTX_new

SYNOPIS

OSSL_HPKE_CTX_new()

DESCRIPTION

La fonction OSSL_HPKE_CTX_new() crée un nouvel objet OSSL_HPKE_CTX, qui est utilisé pour effectuer des opérations HPKE.

VALEURS DE RETOUR

OSSL_HPKE_CTX_new() retourne un pointeur OSSL_HPKE_CTX ou NULL en cas d'erreur.

EXEMPLES

Cet exemple démontre un aller-retour minimal utilisant HPKE.

#include <stddef.h>
#include <string.h>;
#include <openssl/hpke.h>;
#include <openssl/evp.h>;
/*
 * c'est assez grand pour cet exemple, un code réel aurait besoin d'une gestion différente
 */
#define LBUFSIZE 48
/* Faire un aller-retour, générer une clé, chiffrer et déchiffrer */
int main(int argc, char **argv)
{
    int ok = 0;
    int hpke_mode = OSSL_HPKE_MODE_BASE;
    OSSL_HPKE_SUITE hpke_suite = OSSL_HPKE_SUITE_DEFAULT;
    OSSL_HPKE_CTX *sctx = NULL, *rctx = NULL;
    EVP_PKEY *priv = NULL;
    unsigned char pub[LBUFSIZE];
    size_t publen = sizeof(pub);
    unsigned char enc[LBUFSIZE];
    size_t enclen = sizeof(enc);
    unsigned char ct[LBUFSIZE];
    size_t ctlen = sizeof(ct);
    unsigned char clear[LBUFSIZE];
    size_t clearlen = sizeof(clear);
    const unsigned char *pt = "un message pas dans une bouteille";
    size_t ptlen = strlen((char *)pt);
    const unsigned char *info = "Quelques informations";
    size_t infolen = strlen((char *)info);
    unsigned char aad[] = { 1, 2, 3, 4, 5, 6, 7, 8 };
    size_t aadlen = sizeof(aad);
    /*
     * Générer la paire de clés du destinataire.
     * Le destinataire donne cette clé publique à l'expéditeur.
     */
    if (OSSL_HPKE_keygen(hpke_suite, pub, &publen, &priv,
                         NULL, 0, NULL, NULL) != 1)
        goto err;
    /* actions de l'expéditeur - chiffrer les données en utilisant la clé publique du destinataire */
    if ((sctx = OSSL_HPKE_CTX_new(hpke_mode, hpke_suite,
                                  OSSL_HPKE_ROLE_SENDER,
                                  NULL, NULL)) == NULL)
        goto err;
    if (OSSL_HPKE_encap(sctx, enc, &enclen, pub, publen, info, infolen) != 1)
        goto err;
    if (OSSL_HPKE_seal(sctx, ct, &ctlen, aad, aadlen, pt, ptlen) != 1)
        goto err;
    /* actions du destinataire - déchiffrer les données en utilisant la clé privée du destinataire */
    if ((rctx = OSSL_HPKE_CTX_new(hpke_mode, hpke_suite,
                                  OSSL_HPKE_ROLE_RECEIVER,
                                  NULL, NULL)) == NULL)
        goto err;
    if (OSSL_HPKE_decap(rctx, enc, enclen, priv, info, infolen) != 1)
        goto err;
    if (OSSL_HPKE_open(rctx, clear, &clearlen, aad, aadlen, ct, ctlen) != 1)
        goto err;
    ok = 1;
err:
    /* nettoyer */
    printf(ok ? "Tout va bien !\n" : "Erreur !\n");
    OSSL_HPKE_CTX_free(rctx);
    OSSL_HPKE_CTX_free(sctx);
    EVP_PKEY_free(priv);
    return 0;
}

AVERTISSEMENTS

Notez que l'API OSSL_HPKE_CTX_set_seq() peut être dangereuse - si elle est utilisée avec GCM, cela pourrait entraîner une réutilisation du nonce, ce qui est un danger connu. Évitez donc cela complètement, ou soyez très, très prudent lorsque vous utilisez cette API.

L'utilisation d'une valeur IKM pour la génération de clé déterministe (via OSSL_HPKE_CTX_set1_ikme() ou OSSL_HPKE_keygen()) crée un potentiel de fuite de clés (ou de valeurs IKM). Utilisez cela uniquement si c'est vraiment nécessaire et si vous comprenez comment les clés ou les valeurs IKM pourraient être détournées.

{
    int ok = 0;
    int hpke_mode = OSSL_HPKE_MODE_BASE;
    OSSL_HPKE_SUITE hpke_suite = OSSL_HPKE_SUITE_DEFAULT;
    OSSL_HPKE_CTX *sctx = NULL, *rctx = NULL;
    EVP_PKEY *priv = NULL;
    unsigned char pub[LBUFSIZE];
    size_t publen = sizeof(pub);
    unsigned char enc[LBUFSIZE];
    size_t enclen = sizeof(enc);
    unsigned char ct[LBUFSIZE];
    size_t ctlen = sizeof(ct);
    unsigned char clear[LBUFSIZE];
    size_t clearlen = sizeof(clear);
    const unsigned char *pt = "un message pas dans une bouteille";
    size_t ptlen = strlen((char *)pt);
    const unsigned char *info = "Quelques informations";
    size_t infolen = strlen((char *)info);
    unsigned char aad[] = { 1, 2, 3, 4, 5, 6, 7, 8 };
    size_t aadlen = sizeof(aad);
    /*
     * Générer la paire de clés du destinataire.
     * Le destinataire donne cette clé publique à l'expéditeur.
     */
    if (OSSL_HPKE_keygen(hpke_suite, pub, &publen, &priv,
                         NULL, 0, NULL, NULL) != 1)
        goto err;
    /* actions de l'expéditeur - chiffrer les données en utilisant la clé publique du destinataire */
    if ((sctx = OSSL_HPKE_CTX_new(hpke_mode, hpke_suite,
                                  OSSL_HPKE_ROLE_SENDER,
                                  NULL, NULL)) == NULL)
        goto err;
    if (OSSL_HPKE_encap(sctx, enc, &enclen, pub, publen, info, infolen) != 1)
        goto err;
    if (OSSL_HPKE_seal(sctx, ct, &ctlen, aad, aadlen, pt, ptlen) != 1)
        goto err;
    /* actions du destinataire - déchiffrer les données en utilisant la clé privée du destinataire */
    if ((rctx = OSSL_HPKE_CTX_new(hpke_mode, hpke_suite,
                                  OSSL_HPKE_ROLE_RECEIVER,
                                  NULL, NULL)) == NULL)
        goto err;
    if (OSSL_HPKE_decap(rctx, enc, enclen, priv, info, infolen) != 1)
        goto err;
    if (OSSL_HPKE_open(rctx, clear, &clearlen, aad, aadlen, ct, ctlen) != 1)
        goto err;
    ok = 1;
err:
    /* nettoyer */
    printf(ok ? "Tout va bien !\n" : "Erreur !\n");
    OSSL_HPKE_CTX_free(rctx);
    OSSL_HPKE_CTX_free(sctx);
    EVP_PKEY_free(priv);
    return 0;
}

AVERTISSEMENTS

Notez que l'API OSSL_HPKE_CTX_set_seq() peut être dangereuse - si elle est utilisée avec GCM, cela pourrait entraîner une réutilisation du nonce, ce qui est un danger connu. Évitez donc cela complètement, ou soyez très, très prudent lorsque vous utilisez cette API.

L'utilisation d'une valeur IKM pour la génération de clé déterministe (via OSSL_HPKE_CTX_set1_ikme() ou OSSL_HPKE_keygen()) crée un potentiel de fuite de clés (ou de valeurs IKM). Utilisez cela uniquement si c'est vraiment nécessaire et si vous comprenez comment les clés ou les valeurs IKM pourraient être détournées.
