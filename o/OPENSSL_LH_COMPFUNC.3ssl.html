NAME

LHASH, LHASH_OF, DEFINE_LHASH_OF_EX, DEFINE_LHASH_OF, OPENSSL_LH_COMPFUNC, OPENSSL_LH_HASHFUNC, OPENSSL_LH_DOALL_FUNC, LHASH_DOALL_ARG_FN_TYPE, IMPLEMENT_LHASH_HASH_FN, IMPLEMENT_LHASH_COMP_FN, lh_TYPE_new, lh_TYPE_free, lh_TYPE_flush, lh_TYPE_insert, lh_TYPE_delete, lh_TYPE_retrieve, lh_TYPE_doall, lh_TYPE_doall_arg, OPENSSL_LH_doall_arg_thunk, OPENSSL_LH_set_thunks, OPENSSL_LH_num_items, OPENSSL_LH_get_down_load, OPENSSL_LH_set_down_load, OPENSSL_LH_error - table de hachage dynamique typée

La macro suivante est obsolète :

DEFINE_LHASH_OF(TYPE);

DESCRIPTION

Cette librairie initie une table de hachage dynamique typée. Les entrées de la table de hachage peuvent être des structures arbitraires. Normalement, elles consistent en des champs clé et valeur. Dans cette description, TYPE est utilisé comme substitut pour tout type de données OpenSSL, comme SSL_SESSION.

Pour définir une nouvelle table de hachage dynamique typée, utilisez DEFINE_LHASH_OF_EX(). DEFINE_LHASH_OF() était précédemment utilisé à cet effet, mais est maintenant obsolète. La macro DEFINE_LHASH_OF_EX() fournit toutes les fonctions de DEFINE_LHASH_OF() sauf certaines statistiques obsolètes (voir OPENSSL_LH_stats(3)).

lh_TYPE_new() crée une structure LHASH_OF(TYPE) pour stocker des entrées de données arbitraires, et spécifie les callbacks 'hash' et 'compare' qui seront utilisés pour organiser les entrées de la table. Le callback 'hash' prend un pointeur vers une entrée de la table comme argument et retourne une valeur de hachage de 32 bits pour le champ clé. La valeur de hachage est tronquée à une puissance de 2, assurez-vous donc que votre fonction de hachage retourne des bits de faible ordre bien mélangés. Le callback 'compare' prend deux arguments (pointeurs vers deux entrées de la table de hachage) et retourne 0 si leurs clés sont égales, ou une valeur non nulle dans le cas contraire.

Si votre table de hachage contiendra des éléments d'un type spécifique et que les callbacks 'hash' et 'compare' hacheront/compareront ces types, vous pouvez utiliser les macros IMPLEMENT_LHASH_HASH_FN et IMPLEMENT_LHASH_COMP_FN pour créer des wrappers de prototype requis par lh_TYPE_new(). Par exemple :

/*
 * Implémenter les fonctions de hachage et de comparaison ; "stuff" peut être n'importe quel mot.
 */
static unsigned long stuff_hash(const TYPE *a)
{
    ...
}
static int stuff_cmp(const TYPE *a, const TYPE *b)
{
    ...
}
/*
 * Implémenter les fonctions wrapper.
 */
static IMPLEMENT_LHASH_HASH_FN(stuff, TYPE)
static IMPLEMENT_LHASH_COMP_FN(stuff, TYPE)

Si le type doit être utilisé à plusieurs endroits, les macros suivantes peuvent être utilisées dans un fichier d'en-tête commun pour déclarer les wrappers de fonction :

DECLARE_LHASH_HASH_FN(stuff, TYPE)
DECLARE_LHASH_COMP_FN(stuff, TYPE)

Une table de hachage d'objets TYPE peut être créée en utilisant ceci :

LHASH_OF(TYPE) *htable;
htable = B<lh_I<TYPE>_new>(LHASH_HASH_FN(stuff), LHASH_COMP_FN(stuff));

lh_TYPE_free() libère la structure LHASH_OF(TYPE) table. Les entrées de la table de hachage ne seront pas libérées ; considérez utiliser lh_TYPE_doall() pour libérer toute entrée restante dans la table de hachage (voir ci-dessous). Si l'argument est NULL, rien ne sera fait.

lh_TYPE_flush() vide la structure LHASH_OF(TYPE) table. De nouvelles entrées peuvent être ajoutées à la table vidée. Les entrées de la table de hachage ne seront pas libérées ; considérez utiliser lh_TYPE_doall() pour libérer toute entrée restante dans la table de hachage (voir ci-dessous).

lh_TYPE_insert() insère la structure pointée par data dans table. Si une entrée avec la même clé existe déjà, l'ancienne valeur sera remplacée. Vous devez noter que lh_TYPE_insert() stocke des pointeurs, les données ne sont pas copiées.

lh_TYPE_delete() supprime une entrée de table.

lh_TYPE_retrieve() recherche une entrée dans table. Normalement, data est une structure avec les champs clé(s) définis ; la fonction retournera un pointeur vers une structure complètement remplie.

lh_TYPE_doall() appelle func pour chaque entrée de la table de hachage. Par exemple :

/* Libère les ressources appartenant à 'a' (implémenté différemment) */
void TYPE_cleanup_doall(TYPE *a);
/* Implémenter un wrapper compatible avec le prototype de "TYPE_cleanup" */
IMPLEMENT_LHASH_DOALL_FN(TYPE_cleanup, TYPE)
/* Appelle "TYPE_cleanup" à tous les éléments d'une table de hachage. */
lh_TYPE_doall(hashtable, LHASH_DOALL_FN(TYPE_cleanup));
/* Ensuite, la table de hachage elle-même peut être libérée */
lh_TYPE_free(hashtable);

lh_TYPE_doall_arg() est identique à lh_TYPE_doall() sauf que func est appelée avec arg comme second argument et func doit être de type LHASH_DOALL_ARG_FN(TYPE) (un prototype de callback qui reçoit à la fois l'entrée de la table et un argument supplémentaire). Comme avec lh_doall(), vous pouvez choisir de déclarer votre callback avec un prototype correspondant aux types que vous traitez et d'utiliser les macros declare/implement pour créer des wrappers compatibles qui casteront les variables avant d'appeler vos callbacks spécifiques au type. Un exemple de cela est montré ici (impression de toutes les entrées de la table de hachage à un BIO fourni par l'utilisateur) :

/* Imprime 'a' dans 'output_bio' (implémenté différemment) */
void TYPE_print_doall_arg(const TYPE *a, BIO *output_bio);
/* Implémenter un wrapper compatible avec le prototype de "TYPE_print" */
static IMPLEMENT_LHASH_DOALL_ARG_FN(TYPE, const TYPE, BIO)
/* Imprime toute la table de hachage dans un BIO spécifique */
lh_TYPE_doall_arg(hashtable, LHASH_DOALL_ARG_FN(TYPE_print), BIO,
                  logging_bio);

Notez : Il n'est pas sûr par défaut d'utiliser lh_TYPE_delete() dans un callback passé à lh_TYPE_doall() ou lh_TYPE_doall_arg(). La raison est que la suppression d'un élément de la table de hachage peut entraîner la réduction de sa taille et son re-hachage. lh_TYPE_delete() ne doit pas être utilisé dans un callback passé à lh_TYPE_doall() ou lh_TYPE_doall_arg().

b>TYPE_doall() et lh_TYPE_doall_arg() sont non sécurisés et présenteront un comportement indéfini dans ces conditions, car ces fonctions supposent que la taille de la table de hachage et les pointeurs de seaux ne changent pas pendant l'appel.

S'il est souhaité d'utiliser lh_TYPE_doall() ou lh_TYPE_doall_arg() avec lh_TYPE_delete(), il est essentiel d'appeler lh_TYPE_set_down_load() avec un argument down_load de 0 en premier. Cela désactive la contraction de la table de hachage et garantit qu'il sera sûr de supprimer des éléments d'une table de hachage pendant un appel à lh_TYPE_doall() ou lh_TYPE_doall_arg().

Il n'est jamais sûr d'appeler lh_TYPE_insert() pendant un appel à lh_TYPE_doall() ou lh_TYPE_doall_arg().

lh_TYPE_error() peut être utilisé pour déterminer si une erreur s'est produite lors de la dernière opération.

lh_TYPE_num_items() retourne le nombre d'éléments dans la table de hachage.

lh_TYPE_get_down_load() et lh_TYPE_set_down_load() obtiennent et définissent le facteur utilisé pour déterminer quand la table de hachage est contractée. Le facteur est le facteur de charge au niveau ou en dessous duquel la contraction de la table de hachage se produira, multiplié par LH_LOAD_MULT, où le facteur de charge est le nombre d'éléments divisé par le nombre de nœuds. Définir cette valeur à 0 désactive la contraction de la table de hachage.

OPENSSL_LH_new() est identique à lh_TYPE_new() sauf qu'il n'est pas spécifique au type. Ainsi, au lieu de retourner une valeur LHASH_OF(TYPE), il retourne un void *. De même, les fonctions OPENSSL_LH_free(), OPENSSL_LH_flush(), OPENSSL_LH_insert(), OPENSSL_LH_delete(), OPENSSL_LH_retrieve(), OPENSSL_LH_doall(), OPENSSL_LH_doall_arg(), OPENSSL_LH_num_items(), OPENSSL_LH_get_down_load(), OPENSSL_LH_set_down_load() et OPENSSL_LH_error() sont équivalentes aux fonctions lh_TYPE portant le même nom, sauf qu'elles retournent ou utilisent un void * où la fonction lh_TYPE équivalente retourne ou utilise un TYPE * ou un LHASH_OF(TYPE) *. Les fonctions lh_TYPE sont implémentées comme des enveloppes à vérification de type autour des fonctions OPENSSL_LH. La plupart des applications ne devraient pas appeler les fonctions OPENSSL_LH directement.

OPENSSL_LH_set_thunks() et OPENSSL_LH_doall_arg_thunk(), bien que publiques par nécessité, sont en réalité des fonctions internes et ne devraient pas être utilisées.

VALEURS DE RETOUR

lh_TYPE_new() et OPENSSL_LH_new() retournent NULL en cas d'erreur, sinon un pointeur vers la nouvelle structure LHASH.

Lorsqu'une entrée de table de hachage est remplacée, lh_TYPE_insert() ou OPENSSL_LH_insert() retournent la valeur qui est remplacée. NULL est retourné en cas d'opération normale et en cas d'erreur.

lh_TYPE_delete() et OPENSSL_LH_delete() retournent l'entrée qui est supprimée. NULL est retourné s'il n'y a pas une telle valeur dans la table de hachage.

lh_TYPE_retrieve() et OPENSSL_LH_retrieve() retournent l'entrée de la table de hachage si elle a été trouvée, NULL sinon.

lh_TYPE_error() et OPENSSL_LH_error() retournent 1 si une erreur s'est produite lors de la dernière opération, 0 sinon. C'est seulement significatif après les opérations non de récupération.

lh_TYPE_free(), OPENSSL_LH_free(), lh_TYPE_flush(), OPENSSL_LH_flush(), lh_TYPE_doall() OPENSSL_LH_doall(), lh_TYPE_doall_arg() et OPENSSL_LH_doall_arg() ne retournent aucune valeur.

NOTE

Le code LHASH n'est pas thread-safe. Toutes les opérations de mise à jour, ainsi que les appels à lh_TYPE_error() ou OPENSSL_LH_error() doivent être effectuées sous un verrou d'écriture. Toutes les opérations de récupération doivent être effectuées sous un verrou de lecture, sauf si des statistiques d'utilisation précises sont souhaitées. Dans ce cas, un verrou d'écriture doit également être utilisé pour les opérations de récupération. Pour la sortie des statistiques d'utilisation, en utilisant les fonctions de OPENSSL_LH_stats(3), un verrou de lecture suffit.

Le code LHASH considère les entrées de table comme des données constantes. Ainsi, il représente en interne les éléments insérés avec lh_insert() avec un type de pointeur "const void *". C'est pourquoi les callbacks, tels que ceux utilisés par lh_doall() et lh_doall_arg(), déclarent leurs prototypes avec "const", même pour les paramètres qui renvoient les pointeurs de données des éléments de la table - par souci de cohérence, les données fournies par l'utilisateur sont toujours "const" en ce qui concerne le code LHASH. Cependant, comme les appelants fournissent eux-mêmes ces pointeurs, ils peuvent choisir s'ils doivent également traiter tous ces paramètres comme constants.

Par exemple, une table de hachage peut être maintenue par un code qui, pour des raisons d'encapsulation, n'a qu'un accès "const" aux données indexées dans la table de hachage (c'est-à-dire qu'elles sont retournées comme "const" depuis d'autres parties de leur code) - dans ce cas, les prototypes LHASH sont appropriés tels quels. Inversement, si l'appelant est responsable de la durée de vie des données en question, il peut alors souhaiter apporter des modifications à l'élément de table passé dans les callbacks lh_doall() ou lh_doall_arg() (voir l'exemple "TYPE_cleanup" ci-dessus). Si c'est le cas, l'appelant peut soit éliminer le "const" (s'il fournit lui-même les callbacks bruts), soit utiliser les macros pour déclarer/implémenter les fonctions wrapper sans types "const".

Les appelants qui n'ont qu'un accès "const" aux données qu'ils indexent dans une table, mais qui déclarent des callbacks sans types constants (ou qui éliminent le "const" eux-mêmes), créent donc leurs propres risques/erreurs sans y être encouragés par l'API. Dans un ordre d'idées similaire, ceux qui auditionnent le code devraient prêter une attention particulière à toutes les instances des macros DECLARE/IMPLEMENT_LHASH_DOALL_[ARG_]_FN qui fournissent des types sans aucun qualificateur "const".

BOGUES

lh_TYPE_insert() et OPENSSL_LH_insert() retournent NULL à la fois pour le succès et l'erreur.

HISTORIQUE

Dans OpenSSL 1.0.0, l'interface lhash a été revue pour un meilleur contrôle des types.

Dans OpenSSL 3.1, DEFINE_LHASH_OF_EX() a été introduit et DEFINE_LHASH_OF() a été déprécié.

OPENSSL_LH_doall_arg_thunk(), OPENSSL_LH_set_thunks() ont été ajoutés dans OpenSSL 3.3.
