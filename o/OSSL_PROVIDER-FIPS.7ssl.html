NOM

OSSL_PROVIDER-FIPS(7ssl) - Fournisseur FIPS d'OpenSSL

DESCRIPTION

Le fournisseur FIPS d'OpenSSL est un fournisseur spécial qui se conforme aux spécifications des normes de traitement de l'information fédérales (FIPS) FIPS 140-3. Ce « module » contient un ensemble d'algorithmes cryptographiques approuvés qui sont validés par un laboratoire de test autorisé.

Propriétés

Les implémentations de ce fournisseur ont spécifiquement ces propriétés définies pour les algorithmes approuvés :

"provider=fips"
"fips=yes"

Cela peut être utilisé dans les requêtes de propriétés comme EVP_MD_fetch(3) ou EVP_CIPHER_fetch(3), ainsi qu'avec d'autres fonctions qui acceptent une chaîne de requête de propriétés, comme EVP_PKEY_CTX_new_from_name(3).

Pour être conforme à FIPS, il est obligatoire d'inclure "fips=yes" dans toutes les requêtes de propriétés. Cela garantit que seules les implémentations approuvées sont utilisées pour les opérations cryptographiques. La requête "fips=yes" peut également inclure d'autres opérations non cryptographiques qui ne sont pas dans le fournisseur FIPS, telles que les encodeurs de clés asymétriques, voir OSSL_PROVIDER-default(7) « Gestion des clés asymétriques ».

Il n'est pas obligatoire d'inclure "provider=fips" dans votre requête de propriétés. Inclure "provider=fips" dans votre requête de propriétés garantit que le fournisseur FIPS d'OpenSSL est utilisé pour les opérations cryptographiques, et non pour d'autres fournisseurs FIPS capables.

Algorithmes approuvés

Les algorithmes récupérés avec "fips=yes" peuvent toujours être non approuvés si certaines conditions ne sont pas remplies. Voir fips_module(7) pour plus d'informations sur les drapeaux FIPS.

Paramètres du fournisseur

Voir provider-base(7) pour une liste des paramètres de base. Le fournisseur FIPS d'OpenSSL gère également les paramètres liés aux drapeaux FIPS, tels que ceux spécifiés dans fips_config(5).

AUTO-TESTS

Une exigence des modules FIPS est d'exécuter des auto-tests des algorithmes cryptographiques. FIPS 140-3 exige que des tests de réponse connue soient exécutés au démarrage, ainsi que des tests conditionnels qui s'exécutent lors des opérations cryptographiques.

Un mécanisme de rappel optionnel est disponible pour renvoyer des informations à l'utilisateur en utilisant OSSL_SELF_TEST_set_callback(3).

Les paramètres passés au rappel sont décrits dans OSSL_SELF_TEST_new(3)

Le module FIPS d'OpenSSL utilise le mécanisme suivant pour fournir des informations sur les auto-tests au fur et à mesure de leur exécution. Ceci est utile pour le débogage si un auto-test échoue. Le rappel permet également de forcer un auto-test à échouer, afin de vérifier qu'il fonctionne correctement en cas d'échec. Notez que tous les auto-tests s'exécutent même si un échec d'auto-test se produit.

Le module FIPS passe le(s) type(s) suivant(s) à OSSL_SELF_TEST_onbegin().

"Module_Integrity" (OSSL_SELF_TEST_TYPE_MODULE_INTEGRITY)
Utilise HMAC SHA256 sur le fichier du module pour valider que le module n'a pas été modifié. La valeur d'intégrité est comparée à une valeur écrite dans un fichier de configuration lors de l'installation.
"KAT_Integrity" (OSSL_SELF_TEST_TYPE_KAT_INTEGRITY)
Utilisé lors du test d'intégrité du module pour effectuer un test de réponse connue sur HMAC SHA256 avant de l'utiliser.
"KAT_Cipher" (OSSL_SELF_TEST_TYPE_KAT_CIPHER)
Test de réponse connue pour un chiffrement symétrique.
"KAT_AsymmetricCipher" (OSSL_SELF_TEST_TYPE_KAT_ASYM_CIPHER)
Test de réponse connue pour un chiffrement asymétrique.
"KAT_Digest" (OSSL_SELF_TEST_TYPE_KAT_DIGEST)
Test de réponse connue pour un digest.
"KAT_AsymmetricKeyGeneration" (OSSL_SELF_TEST_TYPE_KAT_ASYM_KEYGEN)
Test de réponse connue pour la génération de clés asymétriques.
"KAT_Signature" (OSSL_SELF_TEST_TYPE_KAT_SIGNATURE)
Test de réponse connue pour une signature.
"PCT_Signature" (OSSL_SELF_TEST_TYPE_PCT_SIGNATURE)
Test de cohérence par paires pour une signature.
"KAT_KDF" (OSSL_SELF_TEST_TYPE_KAT_KDF)
Test de réponse connue pour une fonction de dérivation de clé.
"KAT_KA" (OSSL_SELF_TEST_TYPE_KAT_KA)

"DRBG" (OSSL_SELF_TEST_TYPE_DRBG)

AUTO-TEST

Le module AUTOTEST permet l'auto-test des composants cryptographiques. Ces tests sont conçus pour vérifier la correction et la fonctionnalité des algorithmes et des fournisseurs cryptographiques implémentés dans le système.

EXEMPLES

Un exemple simple de rappel d'auto-test est montré ci-dessous à titre illustratif.

#include <openssl/self_test.h>
static OSSL_CALLBACK self_test_cb;
static int self_test_cb(const OSSL_PARAM params[], void *arg)
{
  int ret = 0;
  const OSSL_PARAM *p = NULL;
  const char *phase = NULL, *type = NULL, *desc = NULL;
  p = OSSL_PARAM_locate_const(params, OSSL_PROV_PARAM_SELF_TEST_PHASE);
  if (p == NULL || p->data_type != OSSL_PARAM_UTF8_STRING)
      goto err;
  phase = (const char *)p->data;
  p = OSSL_PARAM_locate_const(params, OSSL_PROV_PARAM_SELF_TEST_DESC);
  if (p == NULL || p->data_type != OSSL_PARAM_UTF8_STRING)
      goto err;
  desc = (const char *)p->data;
  p = OSSL_PARAM_locate_const(params, OSSL_PROV_PARAM_SELF_TEST_TYPE);
  if (p == NULL || p->data_type != OSSL_PARAM_UTF8_STRING)
      goto err;
  type = (const char *)p->data;
  /* Faire une journalisation */
  if (strcmp(phase, OSSL_SELF_TEST_PHASE_START) == 0)
      BIO_printf(bio_out, "%s : (%s) : ", desc, type);
  if (strcmp(phase, OSSL_SELF_TEST_PHASE_PASS) == 0
          || strcmp(phase, OSSL_SELF_TEST_PHASE_FAIL) == 0)
      BIO_printf(bio_out, "%s\n", phase);
  /* Corrompre l'auto-test SHA1 pendant la phase 'corrupt' en retournant 0 */
  if (strcmp(phase, OSSL_SELF_TEST_PHASE_CORRUPT) == 0
          && strcmp(desc, OSSL_SELF_TEST_DESC_MD_SHA1) == 0) {
      BIO_printf(bio_out, "%s %s", phase, desc);
      return 0;
  }
  ret = 1;
err:
  return ret;
}

NOTES

Certaines versions publiées d'OpenSSL n'incluent pas de fournisseur FIPS validé. Pour déterminer quelles versions ont subi le processus de validation, veuillez consulter la page de téléchargement d'OpenSSL https://www.openssl.org/source/. Si vous avez besoin de fonctionnalités approuvées par FIPS, il est essentiel de construire votre fournisseur FIPS en utilisant l'une des versions validées listées là-bas. Normalement, il est possible d'utiliser un fournisseur FIPS construit à partir de l'une des versions validées aux côtés de libcrypto et libssl compilés à partir de n'importe quelle version de la même série de versions majeures. Cette flexibilité vous permet de résoudre les bogues et les CVE qui sortent des limites de FIPS.

Vous pouvez charger le fournisseur FIPS dans plusieurs contextes de bibliothèque comme tout autre fournisseur. Cependant, la restriction suivante s'applique. Le fournisseur FIPS ne peut pas être utilisé par plusieurs copies de la bibliothèque cryptographique OpenSSL dans un seul processus.

Comme le fournisseur enregistre les rappels de cœur dans la bibliothèque cryptographique obtenue lors de l'appel OSSL_provider_init() dans des données globales, il échouera si des invocations ultérieures de sa fonction OSSL_provider_init() renvoient des adresses différentes de ces rappels par rapport à l'appel initial. Cela se produit lorsque différentes copies de la bibliothèque cryptographique sont présentes dans la mémoire du processus et que les deux essaient de charger le même fournisseur FIPS. Une solution de contournement consiste à avoir une copie différente du fournisseur FIPS chargée pour chacune des instances de la bibliothèque cryptographique dans le processus.
