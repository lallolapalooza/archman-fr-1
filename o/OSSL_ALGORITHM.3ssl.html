OSSL_ALGORITHM(3ssl)

Paquet: openssl

Licences: Apache-2.0

OSSL_ALGORITHM(3ssl) OpenSSL OSSL_ALGORITHM(3ssl)

NOM

OSSL_ALGORITHM - Type central OpenSSL pour définir un algorithme récupérable

SYNTAXE

#include <openssl/core.h>
typedef struct ossl_algorithm_st OSSL_ALGORITHM;
struct ossl_algorithm_st {
    const char *algorithm_names;     /* clé */
    const char *property_definition; /* clé */
    const OSSL_DISPATCH *implementation;
    const char *algorithm_description;
};

DESCRIPTION

Le type OSSL_ALGORITHM est une structure publique qui décrit un algorithme fourni par un provider(7). Des tableaux de ce type sont retournés par les providers à la demande des bibliothèques OpenSSL pour décrire les algorithmes pour lesquels les providers fournissent des implémentations, et avec quelles propriétés.

Les tableaux de ce type doivent être terminés par un tuple où algorithm_names est NULL.

Ce type de tableau est typiquement retourné par la fonction de requête d'opération du provider, décrite plus en détail dans "Fonctions du provider" dans provider-base(7).

Champs OSSL_ALGORITHM

algorithm_names
Cette chaîne est un ensemble de noms / identifiants séparés par des deux-points, et est utilisée par la fonctionnalité de récupération appropriée (telle que EVP_CIPHER_fetch(3), EVP_MD_fetch(3), etc.) pour trouver l'algorithme désiré.

Plusieurs noms / identifiants permettent à une implémentation d'algorithme spécifique d'être récupérée de plusieurs manières. Par exemple, l'algorithme RSA a les identifiants connus suivants :

  • "RSA"
  • "rsaEncryption"

    C'est le nom de l'identifiant d'objet (OID) de l'algorithme, tel que donné par le module ASN.1 des RFC PKCS#1 https://www.rfc-editor.org/rfc/rfc8017#appendix-C

  • 1.2.840.113549.1.1.1

    C'est l'OID lui-même pour "rsaEncryption", sous forme textuelle décimale canonique.

La chaîne algorithm_names résultante ressemblerait à ceci :

"RSA:rsaEncryption:1.2.840.113549.1.1.1"

Les bibliothèques OpenSSL utilisent le premier des noms d'algorithmes comme nom principal ou canonique, pour chaque implémentation d'algorithme.

Voir les notes "À propos des noms d'algorithmes" ci-dessous pour une discussion plus approfondie sur algorithm_names et comment cela peut interagir avec les applications et les bibliothèques, y compris celles d'OpenSSL.

property_definition
Cette chaîne définit un ensemble de propriétés associées à une implémentation d'algorithme particulière, et est utilisée par la fonctionnalité de récupération appropriée (telle que EVP_CIPHER_fetch(3), EVP_MD_fetch(3), etc.) pour une recherche plus fine d'une implémentation d'algorithme, ce qui est utile dans le cas où plusieurs implémentations du même algorithme sont disponibles.

Voir property(7) pour une description plus approfondie du contenu de cette chaîne.

implementation
Pointeur vers un tableau OSSL_DISPATCH(3), contenant des pointeurs vers les fonctions d'une implémentation d'algorithme particulière.
algorithm_description
Une chaîne avec une courte description de l'algorithme, lisible par l'homme.

NOTES

À propos des noms d'algorithmes

Les providers peuvent avoir besoin d'enregistrer des OID ASN.1 pour les algorithmes en utilisant OBJ_create(3) (via l'appel core_obj_create décrit dans provider-base(7), car certaines applications ou bibliothèques -- potentiellement toujours les bibliothèques OpenSSL, même -- utilisent des NID pour rechercher des algorithmes.

Dans ce scénario, vous devez vous assurer que le algorithm_names de l'OSSL_ALGORITHM correspondant inclut à la fois le nom court et le nom long.

La plupart du temps, l'enregistrement d'OID ASN.1 comme ceci ne devrait pas être nécessaire, et les applications et bibliothèques sont encouragées à utiliser OBJ_obj2txt(3) pour obtenir une représentation textuelle de l'OID, qui peut être un nom long ou court pour les OID enregistrés, ou l'OID lui-même sous forme textuelle décimale canonique s'il ne l'est pas (ou si OBJ_obj2txt(3) est appelé avec no_name = 1).

Il est recommandé de s'assurer que le algorithm_names de l'OSSL_ALGORITHM correspondant inclut les noms connus ainsi que l'OID lui-même sous forme textuelle décimale canonique. Cela devrait couvrir tous les scénarios.
