SELECT(7) Documentation PostgreSQL 18.1 SELECT(7)

NOM

SELECT, TABLE, WITH — récupérer des lignes d'une table ou d'une vue

SYNTAXE

[ WITH [ RECURSIVE ] requête_with [, ...] ]
SELECT [ ALL | DISTINCT [ ON ( expression [, ...] ) ] ]
    [ { * | expression [ [ AS ] nom_sortie ] } [, ...] ]
    [ FROM élément_from [, ...] ]
    [ WHERE condition ]
    [ GROUP BY [ ALL | DISTINCT ] élément_groupement [, ...] ]
    [ HAVING condition ]
    [ WINDOW nom_fenêtre AS ( définition_fenêtre ) [, ...] ]
    [ { UNION | INTERSECT | EXCEPT } [ ALL | DISTINCT ] select ]
    [ ORDER BY expression [ ASC | DESC | USING opérateur ] [ NULLS { FIRST | LAST } ] [, ...] ]
    [ LIMIT { nombre | ALL } ]
    [ OFFSET début [ ROW | ROWS ] ]
    [ FETCH { FIRST | NEXT } [ nombre ] { ROW | ROWS } { ONLY | WITH TIES } ]
    [ FOR { UPDATE | NO KEY UPDATE | SHARE | KEY SHARE } [ OF référence_from [, ...] ] [ NOWAIT | SKIP LOCKED ] [...] ]
où élément_from peut être l'un des éléments suivants :
    [ ONLY ] nom_table [ * ] [ [ AS ] alias [ ( alias_colonne [, ...] ) ] ]
                [ TABLESAMPLE méthode_échantillonnage ( argument [, ...] ) [ REPEATABLE ( graine ) ] ]
    [ LATERAL ] ( select ) [ [ AS ] alias [ ( alias_colonne [, ...] ) ] ]
    nom_requête_with [ [ AS ] alias [ ( alias_colonne [, ...] ) ] ]
    [ LATERAL ] nom_fonction ( [ argument [, ...] ] )
                [ WITH ORDINALITY ] [ [ AS ] alias [ ( alias_colonne [, ...] ) ] ]
    [ LATERAL ] nom_fonction ( [ argument [, ...] ] ) AS alias ( définition_colonne [, ...] )
    [ LATERAL ] nom_fonction ( [ argument [, ...] ] ) AS ( définition_colonne [, ...] )
    [ LATERAL ] ROWS FROM( nom_fonction ( [ argument [, ...] ] ) [ AS ( définition_colonne [, ...] ) ] [, ...] )
                [ WITH ORDINALITY ] [ [ AS ] alias [ ( alias_colonne [, ...] ) ] ]
    élément_from type_join élément_from { ON condition_join | USING ( colonne_join [, ...] ) [ AS alias_join_using ] }
    élément_from NATURAL type_join élément_from
    élément_from CROSS JOIN élément_from
et élément_groupement peut être l'un des éléments suivants :
    ( )
    expression
    ( expression [, ...] )
    ROLLUP ( { expression | ( expression [, ...] ) } [, ...] )
    CUBE ( { expression | ( expression [, ...] ) } [, ...] )
    GROUPING SETS ( élément_groupement [, ...] )
et requête_with est :
    nom_requête_with [ ( nom_colonne [, ...] ) ] AS [ [ NOT ] MATERIALIZED ] ( select | values | insert | update | delete | merge )
        [ SEARCH { BREADTH | DEPTH } FIRST BY nom_colonne [, ...] SET nom_colonne_seq_recherche ]
        [ CYCLE nom_colonne [, ...] SET nom_colonne_marque_cycle [ TO valeur_marque_cycle DEFAULT valeur_par_défaut_marque_cycle ] USING nom_colonne_chemin_cycle ]
TABLE [ ONLY ] nom_table [ * ]

DESCRIPTION

SELECT récupère des lignes d'une ou plusieurs tables. Le traitement général de SELECT est le suivant :

1.Toutes les requêtes de la liste WITH sont calculées. Elles servent efficacement de tables temporaires qui peuvent être référencées dans la liste FROM. Une requête WITH qui est référencée plus d'une fois dans FROM n'est calculée qu'une seule fois, sauf indication contraire avec NOT MATERIALIZED. (Voir Clause WITH ci-dessous.)
2.Tous les éléments de la liste FROM sont calculés. (Chaque élément de la liste FROM est une table réelle ou virtuelle.) Si plusieurs éléments sont spécifiés dans la liste FROM, ils sont combinés par produit cartésien. (Voir Clause FROM ci-dessous.)
3.Si la clause WHERE est spécifiée, toutes les lignes qui ne satisfont pas la condition sont éliminées de la sortie. (Voir Clause WHERE ci-dessous.)
4.Si la clause GROUP BY est spécifiée, ou s'il y a des appels de fonction d'agrégation, la sortie est combinée en groupes de lignes qui correspondent sur une ou plusieurs valeurs, et les résultats des fonctions d'agrégation sont calculés. Si la clause HAVING est présente, elle élimine les groupes qui ne satisfont pas la condition donnée. (Voir Clause GROUP BY et Clause HAVING ci-dessous.) Bien que les colonnes de sortie de la requête soient nominalement calculées à l'étape suivante, elles peuvent également être référencées (par nom ou par numéro ordinal) dans la clause GROUP BY.
5.Les lignes de sortie réelles sont calculées en utilisant les expressions de sortie SELECT pour chaque ligne ou groupe de lignes sélectionné. (Voir Liste SELECT ci-dessous.)
6.SELECT DISTINCT élimine les lignes dupliquées du résultat. SELECT DISTINCT ON élimine les lignes qui correspondent sur toutes les expressions spécifiées. SELECT ALL (par défaut) renverra toutes les lignes candidates, y compris les doublons. (Voir Clause DISTINCT ci-dessous.)
7.En utilisant les opérateurs UNION, INTERSECT et EXCEPT, la sortie de plusieurs instructions SELECT peut être combinée pour former un seul ensemble de résultats. L'opérateur UNION renvoie toutes les lignes qui sont dans l'un ou l'autre des ensembles de résultats, ou dans les deux. L'opérateur INTERSECT renvoie toutes les lignes qui sont strictement dans les deux ensembles de résultats. L'opérateur EXCEPT renvoie les lignes qui sont dans le premier ensemble de résultats mais pas dans le second. Dans les trois cas, les lignes dupliquées sont éliminées, sauf si ALL est spécifié. Le mot-clé DISTINCT peut être ajouté pour spécifier explicitement l'élimination des lignes dupliquées. Notez que DISTINCT est le comportement par défaut ici, même si ALL est le comportement par défaut pour SELECT lui-même. (Voir Clause UNION, Clause INTERSECT et Clause EXCEPT ci-dessous.)
8.Si la clause ORDER BY est spécifiée, les lignes renvoyées sont triées dans l'ordre spécifié. Si ORDER BY n'est pas donné, les lignes sont renvoyées dans l'ordre le plus rapide que le système trouve pour les produire. (Voir Clause ORDER BY ci-dessous.)
9.Si la clause LIMIT (ou FETCH FIRST) ou OFFSET est spécifiée, l'instruction SELECT ne renvoie qu'un sous-ensemble des lignes résultantes. (Voir Clause LIMIT ci-dessous.)
10.Si FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE ou FOR KEY SHARE est spécifié, l'instruction SELECT verrouille les lignes sélectionnées contre les mises à jour concurrentes. (Voir La Clause de Verrouillage ci-dessous.)

Vous devez avoir le privilège SELECT sur chaque colonne utilisée dans une commande SELECT. L'utilisation de FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE ou FOR KEY SHARE requiert également le privilège UPDATE (pour au moins une colonne de chaque table ainsi sélectionnée).

PARAMÈTRES

Clause WITH

La clause WITH permet de spécifier une ou plusieurs sous-requêtes qui peuvent être référencées par nom dans la requête principale. Les sous-requêtes agissent effectivement comme des tables temporaires ou des vues pour la durée de la requête principale. Chaque sous-requête peut être une instruction SELECT, TABLE, VALUES, INSERT, UPDATE, DELETE ou MERGE. Lors de l'écriture d'une instruction de modification de données (INSERT, UPDATE, DELETE ou MERGE) dans WITH, il est courant d'inclure une clause RETURNING. C'est la sortie de RETURNING, et non la table sous-jacente que l'instruction modifie, qui forme la table temporaire lue par la requête principale. Si RETURNING est omis, l'instruction est toujours exécutée, mais elle ne produit aucune sortie et ne peut donc pas être référencée comme une table par la requête principale.

Un nom (sans qualification de schéma) doit être spécifié pour chaque requête WITH. Optionnellement, une liste de noms de colonnes peut être spécifiée ; si elle est omise, les noms de colonnes sont déduits de la sous-requête.

Si RECURSIVE est spécifié, il permet à une sous-requête SELECT de se référencer par son nom. Une telle sous-requête doit avoir la forme

terme_non_récursif UNION [ ALL | DISTINCT ] terme_récursif

où la référence récursive à elle-même doit apparaître dans la partie droite de l'UNION. Une seule référence récursive à elle-même est autorisée par requête. Les instructions de modification de données récursives ne sont pas prises en charge, mais vous pouvez utiliser les résultats d'une requête SELECT récursive dans une instruction de modification de données. Voir la Section 7.8 pour un exemple.

Un autre effet de RECURSIVE est que les requêtes WITH n'ont pas besoin d'être ordonnées : une requête peut en référencer une autre qui se trouve plus loin dans la liste. (Cependant, les références circulaires, ou la récursion mutuelle, ne sont pas implémentées.) Sans RECURSIVE, les requêtes WITH ne peuvent référencer que des requêtes WITH sœurs qui sont plus tôt dans la liste WITH.

Lorsqu'il y a plusieurs requêtes dans la clause WITH, RECURSIVE doit être écrit une seule fois, immédiatement après WITH. Il s'applique à toutes les requêtes de la clause WITH, bien qu'il n'ait aucun effet sur les requêtes qui n'utilisent pas de récursion ou de références avant.

La clause SEARCH optionnelle calcule une colonne de séquence de recherche qui peut être utilisée pour ordonner les résultats d'une requête récursive en ordre de parcours en largeur ou en profondeur. La liste de noms de colonnes fournie spécifie le r

La clause optionnelle CYCLE est utilisée pour détecter les cycles dans les requêtes récursives. La liste des noms de colonnes fournie spécifie la clé de ligne à utiliser pour suivre les lignes visitées. Une colonne nommée cycle_mark_col_name sera ajoutée à la liste des colonnes de résultat de la requête WITH. Si les deux clauses sont utilisées, la colonne ajoutée par la clause SEARCH apparaît avant les colonnes ajoutées par la clause CYCLE.

La requête principale et les requêtes WITH sont toutes exécutées ( notionnellement) en même temps. Cela implique que les effets d'une instruction de modification de données dans WITH ne peuvent pas être vus par d'autres parties de la requête, autre que par la lecture de sa sortie RETURNING. Si deux instructions de modification de données tentent de modifier la même ligne, les résultats ne sont pas spécifiés.

Une propriété clé des requêtes WITH est qu'elles sont normalement évaluées une seule fois par exécution de la requête principale, même si la requête principale y fait référence plus d'une fois. En particulier, les instructions de modification de données sont garanties d'être exécutées une fois et une seule, que la requête principale lise tout ou partie de leur sortie.

Cependant, une requête WITH peut être marquée comme NOT MATERIALIZED pour supprimer cette garantie. Dans ce cas, la requête WITH peut être intégrée à la requête principale comme s'il s'agissait d'un simple sous-SELECT dans la clause FROM de la requête principale. Cela entraîne des calculs dupliqués si la requête principale se réfère à cette requête WITH plus d'une fois ; mais si chaque utilisation ne nécessite que quelques lignes de la sortie totale de la requête WITH, NOT MATERIALIZED peut permettre une économie nette en permettant d'optimiser conjointement les requêtes. NOT MATERIALIZED est ignoré s'il est attaché à une requête WITH qui est récursive ou qui n'est pas exempte d'effets de bord (c'est-à-dire qu'il ne s'agit pas d'un simple SELECT ne contenant aucune fonction volatile).

Par défaut, une requête WITH exempte d'effets de bord est intégrée à la requête principale si elle est utilisée exactement une fois dans la clause FROM de la requête principale. Cela permet une optimisation conjointe des deux niveaux de requête dans des situations où cela devrait être sémantiquement invisible. Cependant, une telle intégration peut être empêchée en marquant la requête WITH comme MATERIALIZED. Cela peut être utile, par exemple, si la requête WITH est utilisée comme une clôture d'optimisation pour empêcher le planificateur de choisir un mauvais plan. Les versions de PostgreSQL antérieures à v12 n'ont jamais effectué une telle intégration, donc les requêtes écrites pour les anciennes versions pourraient dépendre de WITH comme clôture d'optimisation.

Voir la section 7.8 pour des informations supplémentaires.

Clause FROM

La clause FROM spécifie une ou plusieurs tables sources pour le SELECT. Si plusieurs sources sont spécifiées, le résultat est le produit cartésien (jointure croisée) de toutes les sources. Mais généralement, des conditions de qualification sont ajoutées (via WHERE) pour restreindre les lignes retournées à un petit sous-ensemble du produit cartésien.

La clause FROM peut contenir les éléments suivants :

table_name

Le nom (éventuellement qualifié par le schéma) d'une table ou d'une vue existante. Si ONLY est spécifié avant le nom de la table, seule cette table est analysée. Si ONLY n'est pas spécifié, la table et toutes ses tables descendantes (le cas échéant) sont analysées. Optionnellement, * peut être spécifié après le nom de la table pour indiquer explicitement que les tables descendantes sont incluses.

alias

Un nom de substitution pour l'élément FROM contenant l'alias. Un alias est utilisé pour la brièveté ou pour éliminer l'ambiguïté pour les auto-jointures (où la même table est analysée plusieurs fois). Lorsqu'un alias est fourni, il masque complètement le nom réel de la table ou de la fonction ; par exemple, étant donné FROM foo AS f, le reste du SELECT doit faire référence à cet élément FROM comme f et non comme foo. Si un alias est écrit, une liste d'alias de colonnes peut également être écrite pour fournir des noms de substitution pour une ou plusieurs colonnes de la table.

TABLESAMPLE sampling_method ( argument [, ...] ) [ REPEATABLE ( seed ) ]

Une clause TABLESAMPLE après un table_name indique que la sampling_method spécifiée doit être utilisée pour récupérer un sous-ensemble des lignes de cette table. Cet échantillonnage précède l'application de tout autre filtre tel que les clauses WHERE. La distribution PostgreSQL standard inclut deux méthodes d'échantillonnage, BERNOULLI et SYSTEM, et d'autres méthodes d'échantillonnage peuvent être installées dans la base de données via des extensions.

Les méthodes d'échantillonnage BERNOULLI et SYSTEM acceptent chacune un seul argument qui est la fraction de la table à échantillonner, exprimée en pourcentage entre 0 et 100. Cet argument peut être toute expression réelle. (D'autres méthodes d'échantillonnage peuvent accepter plus ou différents arguments.) Ces deux méthodes retournent chacune un échantillon aléatoire de la table qui contiendra environ le pourcentage spécifié de lignes de la table. La méthode BERNOULLI scanne toute la table et sélectionne ou ignore chaque ligne indépendamment avec la probabilité spécifiée. La méthode SYSTEM effectue un échantillonnage au niveau des blocs, chaque bloc ayant la chance spécifiée d'être sélectionné ; toutes les lignes de chaque bloc sélectionné sont retournées. La méthode SYSTEM est significativement plus rapide que la méthode BERNOULLI lorsque de petits pourcentages d'échantillonnage sont spécifiés, mais elle peut retourner un échantillon moins aléatoire de la table en raison des effets de regroupement.

La clause optionnelle REPEATABLE spécifie une valeur ou une expression seed à utiliser pour générer des nombres aléatoires dans la méthode d'échantillonnage. La valeur seed peut être n'importe quelle valeur à virgule flottante non nulle. Deux requêtes qui spécifient les mêmes valeurs de seed et d'argument sélectionneront le même échantillon de la table, si la table n'a pas été modifiée entre-temps. Mais des valeurs de seed différentes produiront généralement des échantillons différents. Si REPEATABLE n'est pas donné, un nouvel échantillon aléatoire est sélectionné pour chaque requête, basé sur une seed générée par le système. Notez que certaines méthodes d'échantillonnage additionnelles n'acceptent pas REPEATABLE, et produiront toujours de nouveaux échantillons à chaque utilisation.

select

Un sous-SELECT peut apparaître dans la clause FROM. Cela agit comme si son résultat était créé comme une table temporaire pour la durée de cette seule commande SELECT. Notez que le sous-SELECT doit être entouré de parenthèses, et un alias peut être fourni de la même manière que pour une table. Une commande VALUES peut également être utilisée ici.

with_query_name

Une requête WITH est référencée en écrivant son nom, comme si le nom de la requête était un nom de table. (En fait, la requête WITH masque toute table réelle du même nom aux fins de la requête principale. Si nécessaire, vous pouvez faire référence à une table réelle du même nom en qualifiant le nom de la table par son schéma.) Un alias peut être fourni de la même manière que pour une table.

function_name

Les appels de fonction peuvent apparaître dans la clause FROM. (Ceci est particulièrement utile pour les fonctions qui retournent des ensembles de résultats, mais n'importe quelle fonction peut être utilisée.) Cela agit comme si la sortie de la fonction était créée comme une table temporaire pour la durée de cette seule commande SELECT. Si le type de résultat de la fonction est composite (y compris le cas d'une fonction avec plusieurs paramètres OUT), chaque attribut devient une colonne distincte dans la table implicite.

Lorsque la clause optionnelle WITH ORDINALITY est ajoutée à l'appel de fonction, une colonne supplémentaire de type bigint sera ajoutée aux colonnes de résultat de la fonction. Cette colonne numérote les lignes de l'ensemble de résultats de la fonction, en commençant par 1. Par défaut, cette colonne est nommée ordinality.

Un alias peut être fourni de la même manière qu'une table. Si un alias est écrit, une liste d'alias de colonnes peut également être écrite pour fournir des noms de substitution pour un ou plusieurs attributs du type de retour composite de la fonction, y compris la colonne d'ordinalité le cas échéant.

Plusieurs appels de fonction peuvent être combinés en un seul élément de clause FROM en les entourant de ROWS FROM( ... ). La sortie d'un tel élément est la concaténation de la première ligne de chaque fonction, puis de la deuxième ligne de chaque fonction, etc. Si certaines des fonctions produisent moins de lignes que d'autres, des valeurs NULL sont substituées aux données manquantes, de sorte que le nombre total de lignes retournées est toujours le même que pour la fonction qui a produit le plus de lignes.

Si la fonction a été définie comme retournant le type de données record, alors un alias ou le mot-clé AS doit être présent, suivi d'une liste de définition de colonnes sous la forme ( column_name data_type [, ... ]). La liste de définition des colonnes doit correspondre au nombre et aux types réels de colonnes retournées par la fonction.

Lors de l'utilisation de la syntaxe ROWS FROM( ... ), si l'une des fonctions nécessite une liste de définition de colonnes, il est préférable de placer la liste de définition de colonnes après l'appel de fonction à l'intérieur de ROWS FROM( ... ). Une liste de définition de colonnes peut être placée après le construct ROWS FROM( ... ) uniquement s'il n'y a qu'une seule fonction et aucune clause WITH ORDINALITY.

Pour utiliser ORDINALITY avec une liste de définition de colonnes, vous devez utiliser la syntaxe ROWS FROM( ... ) et placer la liste de définition de colonnes à l'intérieur de ROWS FROM( ... ).

join_type

L'un des éléments suivants :
•[ INNER ] JOIN
•LEFT [ OUTER ] JOIN
•RIGHT [ OUTER ] JOIN
•FULL [ OUTER ] JOIN

Pour les types de jointure INNER et OUTER, une condition de jointure doit être spécifiée, à savoir exactement l'un des ON join_condition, USING (join_column [, ...]), ou NATURAL. Voir ci-dessous pour la signification.

Une clause JOIN combine deux éléments FROM, que nous appellerons pour facilité "tables", bien qu'en réalité il puisse s'agir de tout type d'élément FROM. Utilisez des parenthèses si nécessaire pour déterminer l'ordre d'imbrication. En l'absence de parenthèses, les JOINs s'imbriquent de gauche à droite. Dans tous les cas, JOIN a une priorité plus forte que les virgules séparant les éléments de la liste FROM. Toutes les options de JOIN sont juste une notation

nalement pratique, puisqu'ils ne font rien que vous ne pourriez pas faire avec FROM et WHERE normaux.

LEFT OUTER JOIN renvoie toutes les lignes du produit cartésien qualifié (c'est-à-dire toutes les lignes combinées qui satisfont à sa condition de jointure), plus une copie de chaque ligne de la table de gauche pour laquelle aucune ligne de droite n'a satisfait à la condition de jointure. Cette ligne de gauche est étendue à toute la largeur de la table jointe en insérant des valeurs nulles pour les colonnes de droite. Notez que seule la condition de la clause JOIN est considérée pour décider quelles lignes ont des correspondances. Les conditions externes sont appliquées après.

Inversement, RIGHT OUTER JOIN renvoie toutes les lignes jointes, plus une ligne pour chaque ligne de droite non appariée (étendue avec des valeurs nulles à gauche). Ce n'est qu'une commodité de notation, car vous pourriez la convertir en LEFT OUTER JOIN en échangeant les tables de gauche et de droite.

FULL OUTER JOIN renvoie toutes les lignes jointes, plus une ligne pour chaque ligne de gauche non appariée (étendue avec des valeurs nulles à droite), plus une ligne pour chaque ligne de droite non appariée (étendue avec des valeurs nulles à gauche).

ON condition_jointure

condition_jointure est une expression résultant en une valeur de type booléen (similaire à une clause WHERE) qui spécifie quelles lignes d'une jointure sont considérées comme correspondantes.

USING ( colonne_jointure [, ...] ) [ AS alias_utilisation_jointure ]

Une clause de la forme USING ( a, b, ... ) est un raccourci pour ON table_gauche.a = table_droite.a ET table_gauche.b = table_droite.b .... De plus, USING implique que seule l'une des paires de colonnes équivalentes sera incluse dans la sortie de jointure, pas les deux.

Si un nom alias_utilisation_jointure est spécifié, il fournit un alias de table pour les colonnes de jointure. Seules les colonnes de jointure listées dans la clause USING sont adressables par ce nom. Contrairement à un alias régulier, cela ne masque pas les noms des tables jointes du reste de la requête. Contrairement également à un alias régulier, vous ne pouvez pas écrire une liste d'alias de colonne — les noms de sortie des colonnes de jointure sont les mêmes qu'ils apparaissent dans la liste USING.

NATURAL

NATURAL est un raccourci pour une liste USING qui mentionne toutes les colonnes des deux tables qui ont des noms correspondants. S'il n'y a pas de noms de colonnes communs, NATURAL est équivalent à ON TRUE.

CROSS JOIN

CROSS JOIN est équivalent à INNER JOIN ON (TRUE), c'est-à-dire qu'aucune ligne n'est supprimée par qualification. Ils produisent un simple produit cartésien, le même résultat que celui que vous obtenez en listant les deux tables au niveau supérieur de FROM, mais restreint par la condition de jointure (le cas échéant).

LATERAL

Le mot-clé LATERAL peut précéder une sous-requête SELECT FROM. Cela permet à la sous-requête SELECT de faire référence à des colonnes d'éléments FROM qui apparaissent avant elle dans la liste FROM. (Sans LATERAL, chaque sous-requête SELECT est évaluée indépendamment et ne peut donc pas référencer croisée d'autres éléments FROM.)

LATERAL peut également précéder un élément FROM d'appel de fonction, mais dans ce cas, c'est un bruit (noise word), car l'expression de fonction peut référencer des éléments FROM antérieurs dans tous les cas.

Un élément LATERAL peut apparaître au niveau supérieur de la liste FROM, ou dans un arbre JOIN. Dans ce dernier cas, il peut également faire référence à tous les éléments qui se trouvent sur le côté gauche d'un JOIN dont il est sur le côté droit.

Lorsque un élément FROM contient des références croisées LATERAL, l'évaluation procède comme suit : pour chaque ligne de l'élément FROM fournissant la ou les colonnes référencées croisée(s), ou ensemble de lignes de plusieurs éléments FROM fournissant les colonnes, l'élément LATERAL est évalué en utilisant la valeur de la ligne ou de l'ensemble de lignes des colonnes. Les lignes résultantes sont jointes comme d'habitude avec les lignes à partir desquelles elles ont été calculées. Ceci est répété pour chaque ligne ou ensemble de lignes des tables sources de colonnes.

Les tables sources de colonnes doivent être jointes INNER ou LEFT à l'élément LATERAL, sinon il n'y aurait pas d'ensemble de lignes bien défini à partir duquel calculer chaque ensemble de lignes pour l'élément LATERAL. Ainsi, bien qu'une construction telle que X RIGHT JOIN LATERAL Y soit syntaxiquement valide, elle n'est pas réellement autorisée pour Y faisant référence à X.

Clause WHERE

La clause WHERE optionnelle a la forme générale

WHERE condition

où condition est toute expression qui évalue à un résultat de type booléen. Toute ligne qui ne satisfait pas à cette condition sera éliminée de la sortie. Une ligne satisfait à la condition si elle renvoie true lorsque les valeurs de ligne réelles sont substituées aux références de variables.

Clause GROUP BY

La clause GROUP BY optionnelle a la forme générale

GROUP BY [ ALL | DISTINCT ] élément_groupement [, ...]

GROUP BY condensera en une seule ligne toutes les lignes sélectionnées qui partagent les mêmes valeurs pour les expressions groupées. Une expression utilisée à l'intérieur d'un élément_groupement peut être un nom de colonne d'entrée, ou le nom ou le numéro ordinal d'une colonne de sortie (élément de liste SELECT), ou une expression arbitraire formée à partir de valeurs de colonnes d'entrée. En cas d'ambiguïté, un nom GROUP BY sera interprété comme un nom de colonne d'entrée plutôt qu'un nom de colonne de sortie.

Si GROUPING SETS, ROLLUP ou CUBE sont présents comme éléments de groupement, alors la clause GROUP BY dans son ensemble définit un certain nombre d'ensembles de groupement indépendants. L'effet est équivalent à la construction d'un UNION ALL entre des sous-requêtes avec les ensembles de groupement individuels comme leurs clauses GROUP BY. La clause DISTINCT optionnelle supprime les ensembles dupliqués avant le traitement ; elle ne transforme pas l'UNION ALL en UNION DISTINCT. Pour plus de détails sur le traitement des ensembles de groupement, voir la Section 7.2.4.

Les fonctions d'agrégation, s'il y en a, sont calculées sur toutes les lignes constituant chaque groupe, produisant une valeur distincte pour chaque groupe. (S'il y a des fonctions d'agrégation mais pas de clause GROUP BY, la requête est traitée comme ayant un seul groupe comprenant toutes les lignes sélectionnées.) L'ensemble des lignes transmises à chaque fonction d'agrégation peut être davantage filtré en attachant une clause FILTER à l'appel de la fonction d'agrégation ; voir la Section 4.2.7 pour plus d'informations. Lorsqu'une clause FILTER est présente, seules les lignes qui la satisfont sont incluses dans l'entrée de cette fonction d'agrégation.

Lorsque GROUP BY est présent, ou que des fonctions d'agrégation sont présentes, il n'est pas valide pour les expressions de la liste SELECT de faire référence à des colonnes non groupées, sauf à l'intérieur de fonctions d'agrégation ou lorsque la colonne non groupée est fonctionnellement dépendante des colonnes groupées, car il y aurait autrement plus d'une valeur possible à retourner pour une colonne non groupée. Une dépendance fonctionnelle existe si les colonnes groupées (ou un sous-ensemble de celles-ci) sont la clé primaire de la table contenant la colonne non groupée.

Gardez à l'esprit que toutes les fonctions d'agrégation sont évaluées avant l'évaluation de toute expression "scalaire" dans la clause HAVING ou la liste SELECT. Cela signifie que, par exemple, une expression CASE ne peut pas être utilisée pour sauter l'évaluation d'une fonction d'agrégation ; voir la Section 4.2.14.

Actuellement, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE et FOR KEY SHARE ne peuvent pas être spécifiés avec GROUP BY.

Clause HAVING

La clause HAVING optionnelle a la forme générale

HAVING condition

où condition est la même que celle spécifiée pour la clause WHERE.

HAVING élimine les lignes de groupe qui ne satisfont pas à la condition. HAVING est différent de WHERE : WHERE filtre les lignes individuelles avant l'application de GROUP BY, tandis que HAVING filtre les lignes de groupe créées par GROUP BY. Chaque colonne référencée dans condition doit référencer sans ambiguïté une colonne de groupement, sauf si la référence apparaît dans une fonction d'agrégation ou si la colonne non groupée est fonctionnellement dépendante des colonnes de groupement.

La présence de HAVING transforme une requête en une requête groupée même s'il n'y a pas de clause GROUP BY. C'est la même chose que ce qui se passe lorsque la requête contient des fonctions d'agrégation mais pas de clause GROUP BY. Toutes les lignes sélectionnées sont considérées comme formant un seul groupe, et la liste SELECT et la clause HAVING ne peuvent référencer des colonnes de table qu'à l'intérieur de fonctions d'agrégation. Une telle requête émettra une seule ligne si la condition HAVING est vraie, zéro ligne si elle est fausse.

Actuellement, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE et FOR KEY SHARE ne peuvent pas être spécifiés avec HAVING.

Clause WINDOW

La clause WINDOW optionnelle a la forme générale

WINDOW nom_fenetre AS ( definition_fenetre ) [, ...]

où nom_fenetre est un nom qui peut être référencé à partir des clauses OVER ou des définitions de fenêtre ultérieures, et definition_fenetre est

[ nom_fenetre_existante ]
[ PARTITION BY expression [, ...] ]
[ ORDER BY expression [ ASC | DESC | USING opérateur ] [ NULLS { FIRST | LAST } ] [, ...] ]
[ clause_cadre ]

Si une nom_fenetre_existante est spécifiée, elle doit faire référence à une entrée précédente dans la liste WINDOW ; la nouvelle fenêtre copie sa clause de partitionnement de cette entrée, ainsi que sa clause de tri le cas échéant. Dans ce cas, la nouvelle fenêtre ne peut pas spécifier sa propre clause PARTITION BY, et elle peut spécifier ORDER BY uniquement si la fenêtre copiée n'en a pas. La nouvelle fenêtre utilise toujours sa propre clause de cadre ; la fenêtre copiée ne doit pas spécifier de clause de cadre.

Les éléments de la liste PARTITION BY sont interprétés de manière très similaire aux éléments d'une clause GROUP BY, sauf qu'il s'agit toujours d'expressions simples et jamais du nom ou du numéro d'une colonne de sortie. Une autre différence est que ces expressions peuvent contenir des appels de fonction d'agrégation, ce qui n'est pas autorisé dans une clause GROUP BY régulière. Ils sont autorisés ici car le fenêtrage se produit après le groupement et l'agrégation.

De même, les éléments de la liste ORDER BY sont interprétés de manière très similaire aux éléments d'une clause ORDER BY au niveau de l'instruction, sauf que les expressions sont toujours considérées comme des expressions simples et jamais le nom ou le numéro d'une colonne de sortie.

La clause_cadre optionnelle définit le cadre de fenêtre pour les fonctions de fenêtre qui dépendent du cadre (pas toutes le font). Le cadre de fenêtre est un ensemble de lignes liées pour chaque ligne de la requête (appelée ligne courante). La clause_cadre peut être l'une des suivantes :

{ RANGE | ROWS | GROUPS } debut_cadre [ exclusion_cadre ]
{ RANGE | ROWS | GROUPS } BETWEEN debut_cadre AND fin_cadre [ exclusion_cadre ]

où debut_cadre et fin_cadre peuvent être l'un des suivants :

UNB
UNBOUNDED PRECEDING
offset PRECEDING
CURRENT ROW
offset FOLLOWING
UNBOUNDED FOLLOWING

et frame_exclusion peut être l'une des valeurs suivantes

EXCLUDE CURRENT ROW
EXCLUDE GROUP
EXCLUDE TIES
EXCLUDE NO OTHERS

Si frame_end est omis, il est par défaut CURRENT ROW. Les restrictions sont que frame_start ne peut pas être UNBOUNDED FOLLOWING, frame_end ne peut pas être UNBOUNDED PRECEDING, et le choix de frame_end ne peut pas apparaître plus tôt dans la liste ci-dessus des options frame_start et frame_end que le choix frame_start — par exemple, RANGE BETWEEN CURRENT ROW AND offset PRECEDING n'est pas autorisé.

L'option de cadrage par défaut est RANGE UNBOUNDED PRECEDING, ce qui est identique à RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW; elle définit la fenêtre comme étant toutes les lignes depuis le début de la partition jusqu'à la dernière paire de la ligne courante (une ligne que la clause ORDER BY de la fenêtre considère comme équivalente à la ligne courante; toutes les lignes sont des paires s'il n'y a pas d'ORDER BY). En général, UNBOUNDED PRECEDING signifie que la fenêtre commence par la première ligne de la partition, et de même UNBOUNDED FOLLOWING signifie que la fenêtre se termine par la dernière ligne de la partition, indépendamment du mode RANGE, ROWS ou GROUPS. En mode ROWS, CURRENT ROW signifie que la fenêtre commence ou se termine avec la ligne courante; mais en mode RANGE ou GROUPS, cela signifie que la fenêtre commence ou se termine avec la première ou la dernière paire de la ligne courante dans l'ordre de ORDER BY. Les options offset PRECEDING et offset FOLLOWING varient en signification selon le mode de fenêtre. En mode ROWS, l'offset est un entier indiquant que la fenêtre commence ou se termine à ce nombre de lignes avant ou après la ligne courante. En mode GROUPS, l'offset est un entier indiquant que la fenêtre commence ou se termine à ce nombre de groupes de paires avant ou après le groupe de paires de la ligne courante, où un groupe de paires est un groupe de lignes équivalentes selon la clause ORDER BY de la fenêtre. En mode RANGE, l'utilisation d'une option offset exige qu'il y ait exactement une colonne ORDER BY dans la définition de la fenêtre. Ensuite, la fenêtre contient les lignes dont la valeur de la colonne de tri n'est pas supérieure à offset de moins (pour PRECEDING) ou plus (pour FOLLOWING) que la valeur de la colonne de tri de la ligne courante. Dans ces cas, le type de données de l'expression offset dépend du type de données de la colonne de tri. Pour les colonnes de tri numériques, il est généralement du même type que la colonne de tri, mais pour les colonnes de tri de type date/heure, c'est un intervalle. Dans tous ces cas, la valeur de l'offset doit être non nulle et non négative. De plus, bien que l'offset n'ait pas besoin d'être une constante simple, il ne peut pas contenir de variables, de fonctions d'agrégation ou de fonctions de fenêtre.

L'option frame_exclusion permet d'exclure les lignes autour de la ligne courante de la fenêtre, même si elles seraient incluses selon les options de début et de fin de fenêtre. EXCLUDE CURRENT ROW exclut la ligne courante de la fenêtre. EXCLUDE GROUP exclut la ligne courante et ses paires de tri de la fenêtre. EXCLUDE TIES exclut les paires de la ligne courante de la fenêtre, mais pas la ligne courante elle-même. EXCLUDE NO OTHERS spécifie simplement explicitement le comportement par défaut de non-exclusion de la ligne courante ou de ses paires.

Attention, le mode ROWS peut produire des résultats imprévisibles si l'ordre de ORDER BY ne trie pas les lignes de manière unique. Les modes RANGE et GROUPS sont conçus pour garantir que les lignes qui sont des paires dans l'ordre de ORDER BY sont traitées de la même manière: toutes les lignes d'un groupe de paires seront dans la fenêtre ou en seront exclues.

Le but d'une clause WINDOW est de spécifier le comportement des fonctions de fenêtre apparaissant dans la liste SELECT ou la clause ORDER BY de la requête. Ces fonctions peuvent référencer les entrées de la clause WINDOW par leur nom dans leurs clauses OVER. Une entrée de clause WINDOW ne doit pas nécessairement être référencée quelque part; si elle n'est pas utilisée dans la requête, elle est simplement ignorée. Il est possible d'utiliser des fonctions de fenêtre sans aucune clause WINDOW, car un appel de fonction de fenêtre peut spécifier sa définition de fenêtre directement dans sa clause OVER. Cependant, la clause WINDOW permet de gagner du temps lorsque la même définition de fenêtre est nécessaire pour plusieurs fonctions de fenêtre.

Actuellement, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE et FOR KEY SHARE ne peuvent pas être spécifiés avec WINDOW.

Les fonctions de fenêtre sont décrites en détail dans les sections 3.5, 4.2.8 et 7.2.5.

Liste SELECT

La liste SELECT (entre les mots-clés SELECT et FROM) spécifie les expressions qui forment les lignes de sortie de l'instruction SELECT. Les expressions peuvent (et le font généralement) faire référence aux colonnes calculées dans la clause FROM.

Tout comme dans une table, chaque colonne de sortie d'un SELECT a un nom. Dans un SELECT simple, ce nom est juste utilisé pour étiqueter la colonne pour l'affichage, mais lorsque le SELECT est une sous-requête d'une requête plus grande, le nom est vu par la requête plus grande comme le nom de colonne de la table virtuelle produite par la sous-requête. Pour spécifier le nom à utiliser pour une colonne de sortie, écrivez AS output_name après l'expression de la colonne. (Vous pouvez omettre AS, mais seulement si le nom de sortie désiré ne correspond à aucun mot-clé PostgreSQL (voir l'annexe C). Pour vous protéger contre de possibles ajouts futurs de mots-clés, il est recommandé d'écrire toujours AS ou de mettre le nom de sortie entre guillemets doubles.) Si vous ne spécifiez pas de nom de colonne, un nom est choisi automatiquement par PostgreSQL. Si l'expression de la colonne est une simple référence de colonne, le nom choisi est le même que le nom de cette colonne. Dans les cas plus complexes, un nom de fonction ou de type peut être utilisé, ou le système peut recourir à un nom généré comme ?column?.

Le nom d'une colonne de sortie peut être utilisé pour faire référence à la valeur de la colonne dans les clauses ORDER BY et GROUP BY, mais pas dans les clauses WHERE ou HAVING ; vous devez y écrire l'expression à la place.

Au lieu d'une expression, * peut être écrit dans la liste de sortie comme un raccourci pour toutes les colonnes des lignes sélectionnées. De même, vous pouvez écrire nom_table.* comme un raccourci pour les colonnes provenant de cette table uniquement. Dans ces cas, il n'est pas possible de spécifier de nouveaux noms avec AS ; les noms des colonnes de sortie seront les mêmes que les noms des colonnes de la table.

Conformément à la norme SQL, les expressions de la liste de sortie doivent être calculées avant d'appliquer DISTINCT, ORDER BY ou LIMIT. Ceci est évidemment nécessaire lorsque l'on utilise DISTINCT, car sinon il n'est pas clair quelles valeurs sont rendues distinctes. Cependant, dans de nombreux cas, il est pratique que les expressions de sortie soient calculées après ORDER BY et LIMIT ; en particulier si la liste de sortie contient des fonctions volatiles ou coûteuses. Avec ce comportement, l'ordre des évaluations de fonctions est plus intuitif et il n'y aura pas d'évaluations correspondant à des lignes qui n'apparaissent jamais dans la sortie. PostgreSQL évaluera effectivement les expressions de sortie après le tri et la limitation, tant que ces expressions ne sont pas référencées dans DISTINCT, ORDER BY ou GROUP BY. (À titre d'exemple contradictoire, SELECT f(x) FROM tab ORDER BY 1 doit clairement évaluer f(x) avant le tri.) Les expressions de sortie contenant des fonctions qui retournent un ensemble sont effectivement évaluées après le tri et avant la limitation, de sorte que LIMIT agira pour couper la sortie d'une fonction qui retourne un ensemble.


Note

Les versions de PostgreSQL antérieures à 9.6 ne fournissaient aucune garantie quant au moment de l'évaluation des expressions de sortie par rapport au tri et à la limitation ; cela dépendait de la forme du plan de requête choisi.

Clause DISTINCT

Si SELECT DISTINCT est spécifié, toutes les lignes dupliquées sont supprimées de l'ensemble de résultats (une ligne est conservée de chaque groupe de doublons). SELECT ALL spécifie le contraire : toutes les lignes sont conservées ; c'est le comportement par défaut.

SELECT DISTINCT ON ( expression [, ...] ) ne conserve que la première ligne de chaque ensemble de lignes où les expressions données s'évaluent à égalité. Les expressions DISTINCT ON sont interprétées en utilisant les mêmes règles que pour ORDER BY (voir ci-dessus). Notez que la « première ligne » de chaque ensemble est imprévisible à moins qu'ORDER BY ne soit utilisé pour garantir que la ligne désirée apparaît en premier. Par exemple :

SELECT DISTINCT ON (location) location, time, report
    FROM weather_reports
    ORDER BY location, time DESC;

récupère le rapport météorologique le plus récent pour chaque emplacement. Mais si nous n'avions pas utilisé ORDER BY pour forcer l'ordre descendant des valeurs de temps pour chaque emplacement, nous aurions obtenu un rapport d'une heure imprévisible pour chaque emplacement.

Les expressions (s) DISTINCT ON doivent correspondre aux expressions (s) ORDER BY les plus à gauche. La clause ORDER BY contiendra normalement des expressions supplémentaires qui déterminent la précédence désirée des lignes au sein de chaque groupe DISTINCT ON.

Actuellement, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE et FOR KEY SHARE ne peuvent pas être spécifiés avec DISTINCT.

Clause UNION

La clause UNION a cette forme générale :

select_statement UNION [ ALL | DISTINCT ] select_statement

select_statement est toute instruction SELECT sans clause ORDER BY, LIMIT, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE ou FOR KEY SHARE. (ORDER BY et LIMIT peuvent être attachés à une sous-expression si elle est entourée de parenthèses. Sans parenthèses, ces clauses s'appliqueront au résultat de l'UNION, et non à l'expression d'entrée de droite.)

L'opérateur UNION calcule l'union des ensembles des lignes renvoyées par les instructions SELECT impliquées. Une ligne fait partie de l'union des deux ensembles de résultats si elle apparaît dans au moins l'un des ensembles de résultats. Les deux instructions SELECT qui représentent les opérandes directs de l'UNION doivent produire le même nombre de colonnes, et les colonnes correspondantes doivent être de types de données compatibles.

Le résultat de UNION ne contient aucune ligne dupliquée sauf si l'option ALL est spécifiée. ALL empêche l'élimination des doublons. (Par conséquent, UNION ALL est généralement nettement plus rapide que UNION ; utilisez ALL lorsque vous le pouvez.) DISTINCT peut être écrit pour spécifier explicitement le comportement par défaut d'élimination des lignes dupliquées.

Plusieurs opérateurs UNION dans la même instruction SELECT sont évalués de gauche à droite, sauf indication contraire par des parenthèses.

Actuellement, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE et FOR KEY SHARE ne peuvent être spécifiés ni pour un résultat UNION ni pour aucune entrée d'un UNION.

Clause INTERSECT

La clause INTERSECT a cette forme générale :

select_statement INTERSECT [ ALL | DISTINCT ] select_statement

select_statement est toute instruction SELECT w

INTERSECT Clause

The INTERSECT clause has this general form:

select_statement INTERSECT [ ALL | DISTINCT ] select_statement

select_statement is any SELECT statement without an ORDER BY, LIMIT, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE, or FOR KEY SHARE clause.

The INTERSECT operator computes the set intersection of the rows returned by the involved SELECT statements. A row is in the intersection of two result sets if it appears in both result sets.

The result of INTERSECT does not contain any duplicate rows unless the ALL option is specified. With ALL, a row that has m duplicates in the left table and n duplicates in the right table will appear min(m,n) times in the result set. DISTINCT can be written to explicitly specify the default behavior of eliminating duplicate rows.

Multiple INTERSECT operators in the same SELECT statement are evaluated left to right, unless parentheses dictate otherwise. INTERSECT binds more tightly than UNION. That is, A UNION B INTERSECT C will be read as A UNION (B INTERSECT C).

Currently, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE and FOR KEY SHARE cannot be specified either for an INTERSECT result or for any input of an INTERSECT.

EXCEPT Clause

The EXCEPT clause has this general form:

select_statement EXCEPT [ ALL | DISTINCT ] select_statement

select_statement is any SELECT statement without an ORDER BY, LIMIT, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE, or FOR KEY SHARE clause.

The EXCEPT operator computes the set of rows that are in the result of the left SELECT statement but not in the result of the right one.

The result of EXCEPT does not contain any duplicate rows unless the ALL option is specified. With ALL, a row that has m duplicates in the left table and n duplicates in the right table will appear max(m-n,0) times in the result set. DISTINCT can be written to explicitly specify the default behavior of eliminating duplicate rows.

Multiple EXCEPT operators in the same SELECT statement are evaluated left to right, unless parentheses dictate otherwise. EXCEPT binds at the same level as UNION.

Currently, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE and FOR KEY SHARE cannot be specified either for an EXCEPT result or for any input of an EXCEPT.

ORDER BY Clause

The optional ORDER BY clause has this general form:

ORDER BY expression [ ASC | DESC | USING operator ] [ NULLS { FIRST | LAST } ] [, ...]

The ORDER BY clause causes the result rows to be sorted according to the specified expression(s). If two rows are equal according to the leftmost expression, they are compared according to the next expression and so on. If they are equal according to all specified expressions, they are returned in an implementation-dependent order.

Each expression can be the name or ordinal number of an output column (SELECT list item), or it can be an arbitrary expression formed from input-column values.

The ordinal number refers to the ordinal (left-to-right) position of the output column. This feature makes it possible to define an ordering on the basis of a column that does not have a unique name. This is never absolutely necessary because it is always possible to assign a name to an output column using the AS clause.

It is also possible to use arbitrary expressions in the ORDER BY clause, including columns that do not appear in the SELECT output list. Thus the following statement is valid:

SELECT name FROM distributors ORDER BY code;

A limitation of this feature is that an ORDER BY clause applying to the result of a UNION, INTERSECT, or EXCEPT clause can only specify an output column name or number, not an expression.

If an ORDER BY expression is a simple name that matches both an output column name and an input column name, ORDER BY will interpret it as the output column name. This is the opposite of the choice that GROUP BY will make in the same situation. This inconsistency is made to be compatible with the SQL standard.

Optionally one can add the key word ASC (ascending) or DESC (descending) after any expression in the ORDER BY clause. If not specified, ASC is assumed by default. Alternatively, a specific ordering operator name can be specified in the USING clause. An ordering operator must be a less-than or greater-than member of some B-tree operator family. ASC is usually equivalent to USING < and DESC is usually equivalent to USING >. (But the creator of a user-defined data type can define exactly what the default sort ordering is, and it might correspond to operators with other names.)

If NULLS LAST is specified, null values sort after all non-null values; if NULLS FIRST is specified, null values sort before all non-null values. If neither is specified, the default behavior is NULLS LAST when ASC is specified or implied, and NULLS FIRST when DESC is specified (thus, the default is to act as though nulls are larger than non-nulls). When USING is specified, the default nulls ordering depends on whether the operator is a less-than or greater-than operator.

Note that ordering options apply only to the expression they follow; for example ORDER BY x, y DESC does not mean the same thing as ORDER BY x DESC, y DESC.

Character-string data is sorted according to the collation that applies to the column being sorted. That can be overridden at need by including a COLLATE clause in the expression, for example ORDER BY mycolumn COLLATE "en_US". For more information see Section 4.2.10 and Section 23.2.

LIMIT Clause

The LIMIT clause consists of two independent sub-clauses:

LIMIT { count | ALL }
OFFSET start

The parameter count specifies the maximum number of rows to return, while start specifies the number of rows to skip before starting to return rows. When both are specified, start rows are skipped before starting to count the count rows to be returned.

If the count expression evaluates to NULL, it is treated as LIMIT ALL, i.e., no limit. If start evaluates to NULL, it is treated the same as OFFSET 0.

SQL:2008 introduced a different syntax to achieve the same result, which PostgreSQL also supports. It is:

OFFSET start { ROW | ROWS }
FETCH { FIRST | NEXT } [ count ] { ROW | ROWS } { ONLY | WITH TIES }

In this syntax, the start or count value is required by the standard to be a literal constant, a parameter, or a variable name; as a PostgreSQL extension, other expressions are allowed, but will generally need to be enclosed in parentheses to avoid ambiguity. If count is omitted in a FETCH clause, it defaults to 1. The WITH TIES option is used to return any additional rows that tie for the last place in the result set according to the ORDER BY clause; ORDER BY is mandatory in this case, and SKIP LOCKED is not allowed. ROW and ROWS as well as FIRST and NEXT are noise words that don't influence the effects of these clauses. According to the standard, the OFFSET clause must come before the FETCH clause if both are present; but PostgreSQL is laxer and allows either order.

When using LIMIT, it is a good idea to use an ORDER BY clause that constrains the result rows into a unique order. Otherwise you will get an unpredictable subset of the query's rows — you might be asking for the tenth through twentieth rows, but tenth through twentieth in what ordering? You don't know what ordering unless you specify ORDER BY.

The query planner takes LIMIT into account when generating a query plan, so you are very likely to get different plans (yielding different row orders) depending on what you use for LIMIT and OFFSET. Thus, using different LIMIT/OFFSET values to select different subsets of a query result will give inconsistent results unless you enforce a predictable result ordering with ORDER BY. This is not a bug; it is an inherent consequence of the fact that SQL does not promise to deliver the results of a query in any particular order unless ORDER BY is used to constrain the order.

It is even possible for repeated executions of the same LIMIT query to return different subsets of the rows of a table, if there is not an ORDER BY to enforce selection of a deterministic subset. Again, this is not a bug; determinism of the results is simply not guaranteed in such a case.

The Locking Clause

FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE and FOR KEY SHARE are locking clauses; they affect how SELECT locks rows as they are obtained from the table.

The locking clause has the general form

FOR lock_strength [ OF from_reference [, ...] ] [ NOWAIT | SKIP LOCKED ]

where lock_strength can be one of

UPDATE
NO KEY UPDATE
SHARE
KEY SHARE

from_reference must be a table alias or non-hidden table_name referenced in the FROM clause. For more information on each row-level lock mode, refer to Section 13.3.2.

To prevent the operation from waiting for other transactions to commit, use either the NOWAIT or SKIP LOCKED option. With NOWAIT, the statement reports an error, rather than waiting, if a selected row cannot be locked immediately. With SKIP LOCKED, any selected rows that cannot be immediately locked are skipped. Skipping locked rows provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table. Note that NOWAIT and SKIP LOCKED apply only to the row-level lock(s) — the required ROW SHARE table-level lock is still taken in the ordinary way (see Chapter 13). You can use LOCK with the NOWAIT option first, if you need to acquire the table-level lock without waiting.

If specific tables are named in a locking clause, then only rows coming from those tables are locked; any other tables used in the SELECT are simply read as usual. A locking clause without a table list affects all tables used in the statement. If a locking clause is applied to a view or sub-query, it affects all tables used in the view or sub-query. However, these clauses do not apply to WITH queries referenced by the primary query. If you want row locking to occur within a WITH query, specify a locking clause within the WITH query.

Multiple locking clauses can be writt

en si nécessaire de spécifier un comportement de verrouillage différent pour différentes tables. Si la même table est mentionnée (ou implicitement affectée) par plus d'une clause de verrouillage, elle est traitée comme si elle n'était spécifiée que par la plus forte. De même, une table est traitée comme NOWAIT si cela est spécifié dans l'une des clauses qui la concernent. Sinon, elle est traitée comme SKIP LOCKED si cela est spécifié dans l'une des clauses qui la concernent.

Les clauses de verrouillage ne peuvent pas être utilisées dans des contextes où les lignes retournées ne peuvent pas être clairement identifiées par des lignes de table individuelles ; par exemple, elles ne peuvent pas être utilisées avec l'agrégation.

Lorsqu'une clause de verrouillage apparaît au niveau supérieur d'une requête SELECT, les lignes verrouillées sont exactement celles qui sont retournées par la requête ; dans le cas d'une requête de jointure, les lignes verrouillées sont celles qui contribuent aux lignes de jointure retournées. De plus, les lignes qui satisfaisaient les conditions de la requête au moment de l'instantané de la requête seront verrouillées, bien qu'elles ne soient pas retournées si elles ont été mises à jour après l'instantané et ne satisfont plus les conditions de la requête. Si un LIMIT est utilisé, le verrouillage s'arrête une fois qu'un nombre suffisant de lignes a été retourné pour satisfaire la limite (mais notez que les lignes ignorées par OFFSET seront verrouillées). De même, si une clause de verrouillage est utilisée dans la requête d'un curseur, seules les lignes effectivement récupérées ou franchies par le curseur seront verrouillées.

Lorsqu'une clause de verrouillage apparaît dans une sous-requête SELECT, les lignes verrouillées sont celles retournées à la requête externe par la sous-requête. Cela peut impliquer moins de lignes que ce que suggérerait l'inspection seule de la sous-requête, car les conditions de la requête externe peuvent être utilisées pour optimiser l'exécution de la sous-requête. Par exemple,

SELECT * FROM (SELECT * FROM mytable FOR UPDATE) ss WHERE col1 = 5;

verrouillera uniquement les lignes dont col1 = 5, même si cette condition ne se trouve pas textuellement dans la sous-requête.

Les versions précédentes ne parvenaient pas à conserver un verrou qui est mis à niveau par un point de sauvegarde ultérieur. Par exemple, ce code :

BEGIN;
SELECT * FROM mytable WHERE key = 1 FOR UPDATE;
SAVEPOINT s;
UPDATE mytable SET ... WHERE key = 1;
ROLLBACK TO s;

ne parvenait pas à conserver le verrou FOR UPDATE après le ROLLBACK TO. Ceci a été corrigé dans la version 9.3.


Attention

Il est possible qu'une commande SELECT exécutée au niveau d'isolation de transaction READ COMMITTED et utilisant ORDER BY et une clause de verrouillage retourne des lignes dans le désordre. Ceci est dû au fait que ORDER BY est appliqué en premier. La commande trie le résultat, mais peut ensuite bloquer en essayant d'obtenir un verrou sur une ou plusieurs des lignes. Une fois que le SELECT est débloqué, certaines des valeurs des colonnes de tri peuvent avoir été modifiées, ce qui donne l'impression que les lignes apparaissent dans le désordre (bien qu'elles soient dans l'ordre en termes des valeurs des colonnes d'origine). Cela peut être contourné au besoin en plaçant la clause FOR UPDATE/SHARE dans une sous-requête, par exemple

SELECT * FROM (SELECT * FROM mytable FOR UPDATE) ss ORDER BY column1;

Notez que cela entraînera le verrouillage de toutes les lignes de mytable, alors que FOR UPDATE au niveau supérieur ne verrouillerait que les lignes réellement retournées. Cela peut entraîner une différence de performance significative, en particulier si ORDER BY est combiné avec LIMIT ou d'autres restrictions. Cette technique n'est donc recommandée que si des mises à jour concurrentes des colonnes de tri sont attendues et qu'un résultat strictement trié est requis.

Aux niveaux d'isolation de transaction REPEATABLE READ ou SERIALIZABLE, cela entraînerait un échec de sérialisation (avec un SQLSTATE de '40001'), il n'y a donc aucune possibilité de recevoir des lignes dans le désordre sous ces niveaux d'isolation.

Commande TABLE

La commande

TABLE nom

est équivalente à

SELECT * FROM nom

Elle peut être utilisée comme commande de premier niveau ou comme variante de syntaxe pour économiser de l'espace dans certaines parties de requêtes complexes. Seules les clauses WITH, UNION, INTERSECT, EXCEPT, ORDER BY, LIMIT, OFFSET, FETCH et FOR de verrouillage peuvent être utilisées avec TABLE ; la clause WHERE et toute forme d'agrégation ne peuvent pas être utilisées.

EXEMPLES

Pour joindre la table films et la table distributors :

SELECT f.title, f.did, d.name, f.date_prod, f.kind
    FROM distributors d JOIN films f USING (did);
       title       | did |     name     | date_prod  |   kind
-------------------+-----+--------------+------------+----------
 The Third Man     | 101 | British Lion | 1949-12-23 | Drama
 The African Queen | 101 | British Lion | 1951-08-11 | Romantic
 ...

Pour additionner la colonne len de tous les films et regrouper les résultats par genre :

SELECT kind, sum(len) AS total FROM films GROUP BY kind;
   kind   | total
----------+-------
 Action   | 07:34
 Comedy   | 02:58
 Drama    | 14:28
 Musical  | 06:42
 Romantic | 04:38

Pour additionner la colonne len de tous les films, regrouper les résultats par genre et afficher les totaux de groupe inférieurs à 5 heures :

SELECT kind, sum(len) AS total
    FROM films
    GROUP BY kind
    HAVING sum(len) < interval '5 hours';
   kind   | total
----------+-------
 Comedy   | 02:58
 Romantic | 04:38

Les deux exemples suivants sont des moyens identiques de trier les résultats individuels en fonction du contenu de la deuxième colonne (name) :

SELECT * FROM distributors ORDER BY name;
SELECT * FROM distributors ORDER BY 2;
 did |       name
-----+------------------
 109 | 20th Century Fox
 110 | Bavaria Atelier
 101 | British Lion
 107 | Columbia
 102 | Jean Luc Godard
 113 | Luso films
 104 | Mosfilm
 103 | Paramount
 106 | Toho
 105 | United Artists
 111 | Walt Disney
 112 | Warner Bros.
 108 | Westward

L'exemple suivant montre comment obtenir l'union des tables distributors et actors, en limitant les résultats à ceux qui commencent par la lettre W dans chaque table. Seules les lignes distinctes sont souhaitées, donc le mot-clé ALL est omis.

distributors:               actors:
 did |     name              id |     name
-----+--------------        ----+----------------
 108 | Westward               1 | Woody Allen
 111 | Walt Disney            2 | Warren Beatty
 112 | Warner Bros.           3 | Walter Matthau
 ...                         ...
SELECT distributors.name
    FROM distributors
    WHERE distributors.name LIKE 'W%'
UNION
SELECT actors.name
    FROM actors
    WHERE actors.name LIKE 'W%';
      name
----------------
 Walt Disney
 Walter Matthau
 Warner Bros.
 Warren Beatty
 Westward
 Woody Allen

Cet exemple montre comment utiliser une fonction dans la clause FROM, avec et sans liste de définition de colonnes :

CREATE FUNCTION distributors(int) RETURNS SETOF distributors AS $$
    SELECT * FROM distributors WHERE did = $1;
$$ LANGUAGE SQL;
SELECT * FROM distributors(111);
 did |    name
-----+-------------
 111 | Walt Disney
CREATE FUNCTION distributors_2(int) RETURNS SETOF record AS $$
    SELECT * FROM distributors WHERE did = $1;
$$ LANGUAGE SQL;
SELECT * FROM distributors_2(111) AS (f1 int, f2 text);
 f1  |     f2
-----+-------------
 111 | Walt Disney

Voici un exemple de fonction avec une colonne d'ordinalité ajoutée :

SELECT * FROM unnest(ARRAY['a','b','c','d','e','f']) WITH ORDINALITY;
 unnest | ordinality
--------+----------
 a      |        1
 b      |        2
 c      |        3
 d      |        4
 e      |        5
 f      |        6
(6 rows)

Cet exemple montre comment utiliser une clause WITH simple :

WITH t AS (
    SELECT random() as x FROM generate_series(1, 3)
  )
SELECT * FROM t
UNION ALL
SELECT * FROM t;
         x
--------------------
  0.534150459803641
  0.520092216785997
 0.0735620250925422
  0.534150459803641
  0.520092216785997
 0.0735620250925422

Notez que la requête WITH a été évaluée une seule fois, de sorte que nous avons obtenu deux ensembles des mêmes trois valeurs aléatoires.

Cet exemple utilise WITH RECURSIVE pour trouver tous les subordonnés (directs ou indirects) de l'employé Mary, et leur niveau d'indirectivité, à partir d'une table qui montre uniquement les subordonnés directs :

WITH RECURSIVE employee_recursive(distance, employee_name, manager_name) AS (
    SELECT 1, employee_name, manager_name
    FROM employee
    WHERE manager_name = 'Mary'
  UNION ALL
    SELECT er.distance + 1, e.employee_name, e.manager_name
    FROM employee_recursive er, employee e
    WHERE er.employee_name = e.manager_name
  )
SELECT distance, employee_name FROM employee_recursive;

Notez la forme typique des requêtes récursives : une condition initiale, suivie de UNION, suivie de la partie récursive de la requête. Assurez-vous que la partie récursive de la requête ne retournera éventuellement aucun tuple, sinon la requête bouclera indéfiniment. (Voir la Section 7.8 pour plus d'exemples.)

Cet exemple utilise LATERAL pour appliquer une fonction retournant un ensemble get_product_names() pour chaque ligne de la table manufacturers :

SELECT m.name AS mname, pname
FROM manufacturers m, LATERAL get_product_names(m.id) pname;

Les fabricants n'ayant actuellement aucun produit n'apparaîtraient pas dans le résultat, car il s'agit d'une jointure interne. Si nous souhaitions inclure les noms de tels fabricants dans le résultat, nous pourrions faire :

SELECT m.name AS mname, pname
FROM manufacturers m LEFT JOIN LATERAL get_product_names(m.id) pname ON true;

COMPATIBILITÉ

Bien sûr, l'instruction SELECT est compatible avec la norme SQL. Mais il existe quelques extensions et quelques fonctionnalités manquantes.

Clauses FROM omises

PostgreSQL permet d'omettre la clause FROM. Elle a une utilisation simple pour calculer les résultats d'expressions simples :

SELECT 2+2;
 ?column?
----------
        4

Certaines autres bases de données SQL ne peuvent pas le faire, sauf en introduisant une table factice d'une seule ligne à partir de laquelle faire le SELECT.

Listes SELECT vides

La liste des expressions de sortie après SELECT peut être vide, produisant une table de résultats à zéro colonne. Ce n'est pas une syntaxe valide selon la norme SQL. PostgreSQL l'autorise pour être cohérent avec l'autorisation des tables à zéro colonne. Cependant, une liste vide n'est pas autorisée lorsque DISTINCT est utilisé.

Omission du mot-clé AS

Dans la norme SQL, le mot-clé facultatif AS

peut être omis avant un nom de colonne de sortie lorsque le nouveau nom de colonne est un nom de colonne valide (c'est-à-dire qu'il n'est pas identique à un mot-clé réservé). PostgreSQL est légèrement plus restrictif : AS est requis si le nouveau nom de colonne correspond à un mot-clé quelconque, réservé ou non. Il est recommandé d'utiliser AS ou de mettre entre guillemets doubles les noms de colonnes de sortie, afin d'éviter tout conflit potentiel avec les futures additions de mots-clés.

Dans les éléments FROM, le standard et PostgreSQL autorisent tous deux l'omission de AS avant un alias qui est un mot-clé non réservé. Mais cela est impraticable pour les noms de colonnes de sortie, en raison d'ambiguïtés syntaxiques.

Omitting Aliases de Sous-SELECT dans FROM

Selon la norme SQL, une sous-SELECT dans la liste FROM doit avoir un alias. Dans PostgreSQL, cet alias peut être omis.

ONLY et Héritage

La norme SQL exige des parenthèses autour du nom de la table lors de l'écriture de ONLY, par exemple SELECT * FROM ONLY (tab1), ONLY (tab2) WHERE .... PostgreSQL considère ces parenthèses comme facultatives.

PostgreSQL autorise l'ajout d'un * final pour spécifier explicitement le comportement non-ONLY consistant à inclure les tables filles. Le standard ne le permet pas.

(Ces points s'appliquent de la même manière à toutes les commandes SQL prenant en charge l'option ONLY.)

Restrictions de la Clause TABLESAMPLE

La clause TABLESAMPLE est actuellement acceptée uniquement sur les tables régulières et les vues matérialisées. Selon la norme SQL, il devrait être possible de l'appliquer à n'importe quel élément FROM.

Appels de Fonctions dans FROM

PostgreSQL autorise un appel de fonction à être écrit directement comme un membre de la liste FROM. Dans la norme SQL, il serait nécessaire d'encapsuler un tel appel de fonction dans une sous-SELECT ; c'est-à-dire que la syntaxe FROM func(...) alias est approximativement équivalente à FROM LATERAL (SELECT func(...)) alias. Notez que LATERAL est considéré comme implicite ; c'est parce que le standard exige des sémantiques LATERAL pour un élément UNNEST() dans FROM. PostgreSQL traite UNNEST() de la même manière que les autres fonctions retournant des ensembles.

Espace de Noms Disponible pour GROUP BY et ORDER BY

Dans la norme SQL-92, une clause ORDER BY ne peut utiliser que des noms de colonnes de sortie ou des numéros, tandis qu'une clause GROUP BY ne peut utiliser que des expressions basées sur des noms de colonnes d'entrée. PostgreSQL étend chacune de ces clauses pour permettre également l'autre choix (mais il utilise l'interprétation du standard en cas d'ambiguïté). PostgreSQL permet également aux deux clauses de spécifier des expressions arbitraires. Notez que les noms apparaissant dans une expression seront toujours considérés comme des noms de colonnes d'entrée, et non comme des noms de colonnes de sortie.

SQL:1999 et les versions ultérieures utilisent une définition légèrement différente qui n'est pas entièrement compatible ascendante avec SQL-92. Dans la plupart des cas, cependant, PostgreSQL interprétera une expression ORDER BY ou GROUP BY de la même manière que SQL:1999.

Dépendances Fonctionnelles

PostgreSQL reconnaît la dépendance fonctionnelle (permettant d'omettre des colonnes de GROUP BY) uniquement lorsqu'une clé primaire de table est incluse dans la liste GROUP BY. La norme SQL spécifie des conditions supplémentaires qui devraient être reconnues.

LIMIT et OFFSET

Les clauses LIMIT et OFFSET sont une syntaxe spécifique à PostgreSQL, également utilisée par MySQL. La norme SQL:2008 a introduit les clauses OFFSET ... FETCH {FIRST|NEXT} ... pour la même fonctionnalité, comme montré ci-dessus dans Clause LIMIT. Cette syntaxe est également utilisée par IBM DB2. (Les applications écrites pour Oracle utilisent fréquemment une solution de contournement impliquant la colonne autogénérée rownum, qui n'est pas disponible dans PostgreSQL, pour implémenter les effets de ces clauses.)

FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE, FOR KEY SHARE

Bien que FOR UPDATE apparaisse dans la norme SQL, la norme l'autorise uniquement comme une option de DECLARE CURSOR. PostgreSQL l'autorise dans toute requête SELECT ainsi que dans les sous-SELECT, mais il s'agit d'une extension. Les variantes FOR NO KEY UPDATE, FOR SHARE et FOR KEY SHARE, ainsi que les options NOWAIT et SKIP LOCKED, n'apparaissent pas dans la norme.

Instructions de Modification de Données dans WITH

PostgreSQL autorise INSERT, UPDATE, DELETE et MERGE à être utilisées comme requêtes WITH. Ceci n'est pas trouvé dans la norme SQL.

Clauses non standard

DISTINCT ON ( ... ) est une extension de la norme SQL.

ROWS FROM( ... ) est une extension de la norme SQL.

Les options MATERIALIZED et NOT MATERIALIZED de WITH sont des extensions de la norme SQL.
