NOM

Win::Hivex::Regedit - Aide pour lire et écrire des fichiers au format regedit

SYNOPSIS

use Win::Hivex;
use Win::Hivex::Regedit qw(reg_import reg_export);
$h = Win::Hivex->open ('SOFTWARE', write => 1);
open FILE, "updates.reg";
reg_import (\*FILE, $h);
$h->commit (undef);
reg_export ($h, "\\Microsoft\\Windows NT\\CurrentVersion", \*OUTFILE,
   prefix => "HKEY_LOCAL_MACHINE\\SOFTWARE");

DESCRIPTION

Win::Hivex::Regedit est une bibliothèque d'aide pour lire et écrire le format de fichier regedit (ou ".REG") de Windows. C'est le format textuel couramment utilisé sous Windows pour distribuer des groupes de modifications du Registre Windows, et ce format est lu et écrit par les programmes propriétaires "reg.exe" et "regedit.exe" fournis avec Windows. Ce n'est pas le même format que le format binaire « hive » que la bibliothèque hivex elle-même peut lire et écrire. Notez que le format regedit n'est pas bien spécifié, et par conséquent des écarts peuvent survenir entre ce que le programme Windows peut lire/écrire et ce que nous pouvons lire/écrire. (Veuillez signaler les bugs pour tout écart constaté).

Win::Hivex::Regedit est la bibliothèque Perl de bas niveau. Il existe également un outil en ligne de commande pour combiner les fichiers hive et les fichiers reg (hivexregedit(1)). Si vous avez une machine virtuelle Windows dans laquelle vous devez fusionner des modifications au format regedit, utilisez l'outil de haut niveau virt-win-reg(1) (fait partie des outils libguestfs).

FONCTIONS

reg_import

reg_import ($fh, ($h|$map), [encoding => "UTF-16LE"]);

Cette fonction importe les clés de registre depuis le descripteur de fichier $fh soit dans la ruche $h soit via une fonction de mappage.

Le descripteur de ruche $h doit avoir été ouvert en écriture, c'est-à-dire en utilisant le drapeau "write => 1" pour "Win::Hivex->open".

Dans le fichier de ruche binaire, la première partie du nom de la clé (par exemple "HKEY_LOCAL_MACHINE\SOFTWARE") n'est pas stockée. Il faut simplement savoir (d'une manière ou d'une autre) que cela correspond à la ruche "SOFTWARE". Par conséquent, si vous recevez un fichier contenant un mélange de clés à ajouter à différentes ruches, vous devez avoir un moyen de les mapper aux descripteurs de ruche. Ceci sort du cadre de la bibliothèque hivex, mais si le deuxième argument est une référence à une fonction (CODEREF), alors cette fonction $map est appelée pour chaque nom de clé :

map ($keyname)
==> ($h, $keyname)

Comme montré, la fonction doit retourner une paire, le descripteur de ruche et le vrai nom de clé (avec le préfixe supprimé). Par exemple :

sub map {
  if ($_[0] =~ /^HKEY_LOCAL_MACHINE\\SOFTWARE(.*)/i) {
    return ($software_h, $1);
  } else ...
}

"encoding" est le codage utilisé par défaut pour les chaînes de caractères. S'il n'est pas spécifié, il utilise par défaut "UTF-16LE", cependant nous vous conseillons fortement de le spécifier. Voir « ENCODAGE DES CHAINES » ci-dessous.

Comme avec le programme regedit, nous fusionnons les nouvelles clés de registre avec celles existantes, et les nouvelles valeurs de nœud avec les anciennes. Vous pouvez utiliser le caractère "-" (moins) pour supprimer des clés et des valeurs individuelles. Ceci est expliqué en détail sur la page Wikipédia du Registre Windows.

N'oubliez pas que vous devez appeler "$h->commit (undef)" sur le descripteur hivex avant que tout changement ne soit écrit dans le fichier de ruche. Voir « ÉCRITURE DANS LES FICHIERS HIVE » dans hivex(3).

reg_export

reg_export ($h, $key, $fh,
            [prefix => $prefix],
            [unsafe_printable_strings => 1]);

Cette fonction exporte les clés de registre à partir de la racine $key et récursivement vers le bas dans le descripteur de fichier $fh.

$key est un chemin insensible à la casse du nœud de départ, relatif à la racine de la ruche. C'est une erreur si ce chemin n'existe pas. Les éléments du chemin doivent être séparés par des caractères antislash.

$prefix est ajouté avant chaque nom de clé. L'utilisation habituelle consiste à faire apparaître les noms de clés tels qu'ils seraient sous Windows. Par exemple, la clé "\Foo" dans le Registre SOFTWARE, avec $prefix "HKEY_LOCAL_MACHINE\SOFTWARE", serait écrite comme suit :

[HKEY_LOCAL_MACHINE\SOFTWARE\Foo]
"Key 1"=...
"Key 2"=...

Si "unsafe_printable_strings" n'est pas fourni ou est faux, alors la sortie est écrite en ASCII pur à 7 bits, avec des fins de ligne qui sont celles par défaut pour l'hôte local. Les chaînes sont toujours encodées en octets hexadécimaux. C'est sûr car cela préserve le contenu original et le codage des chaînes. Voir « ENCODAGE DES CHAINES » ci-dessous.

Si "unsafe_printable_strings" est vrai, alors les chaînes sont supposées être en UTF-16LE et sont converties en UTF-8 pour la sortie. Le point de code nul final dans la chaîne est supprimé s'il y en a un. Ceci est dangereux car cela ne préserve pas la fidélité des chaînes dans le Registre et parce que le type de contenu des chaînes n'est pas toujours UTF-16LE. Cependant, c'est utile si vous voulez simplement afficher les chaînes pour des modifications et débogages rapides.

Vous pourriez avoir besoin de convertir l'encodage du fichier à l'aide de iconv(1) et les fins de ligne à l'aide de unix2dos(1) si vous envoyez à un utilisateur Windows.

Les nœuds et les clés sont triés alphabétiquement dans la sortie.

Cette fonction n'imprime pas d'en-tête. Le vrai programme regedit imprimera un en-tête tel que :

Windows Registry Editor Version 5.00

suivi d'une ligne vide. (D'autres en-têtes sont possibles, voir la page Wikipédia sur le Registre Windows). Si vous voulez un en-tête, vous devez l'écrire vous-même.

reg_export_node

reg_export_node ($h, $node, $fh, ...);

Ceci est exactement identique à « reg_export » sauf qu'au lieu de spécifier le chemin d'une clé sous forme de chaîne, vous passez un descripteur de nœud $node de la bibliothèque hivex.

ENCODAGE DES CHAINES

La situation avec l'encodage des chaînes dans le Registre sous Windows est très confuse. Il existe deux principaux encodages que l'on trouve dans le fichier binaire (ruche) : ASCII 7 bits et UTF-16LE. (D'autres encodages sont possibles, il est également possible d'avoir des données binaires arbitraires incorrectement marquées avec un type chaîne).

Le fichier de ruche lui-même ne contient aucune indication de l'encodage de la chaîne. Windows devine probablement l'encodage.

Nous pensons que regedit devine probablement l'encodage à utiliser en fonction de l'encodage du fichier, ou alors a des valeurs par défaut différentes pour différentes versions de Windows. Aucun de ces choix n'est approprié pour un outil utilisé dans un système d'exploitation réel.

Lors de l'utilisation de « reg_import », vous devez spécifier l'encodage par défaut pour les chaînes à l'aide du paramètre "encoding". S'il n'est pas spécifié, il utilise par défaut UTF-16LE.

Le fichier lui-même qui est importé devrait être dans l'encodage local pour les fichiers (généralement UTF-8 sur les systèmes Linux modernes). Cela signifie que si vous recevez un fichier regedit d'un système Windows, vous devrez parfois le réencoder :

iconv -f utf-16le -t utf-8 < input.reg | dos2unix > output.reg

Lors de l'écriture de fichiers regedit (« reg_export »), nous contournons complètement cette folie. Toutes les chaînes (même celles en ASCII pur) sont écrites sous forme d'octets hexadécimaux, il n'y a donc aucun doute sur la manière dont elles devraient être encodées lorsqu'elles sont relues.
