Inline-FAQ - La FAQ de Inline

DESCRIPTION

Bienvenue dans la FAQ officielle de Inline. Dans ce cas, FAQ signifie : Formerly Answered Questions (Anciennement Questions traitées).

Il s'agit d'une collection d'anciens e-mails, parfois longs, que moi-même et d'autres avons envoyés à la liste de diffusion Inline. (inline@perl.org) Ils ont été revus et édités pour l'édification générale de Inline. Certains peuvent être liés à un langage spécifique. Ils sont présentés ici dans une disposition FAQ traditionnelle.

INLINE GÉNÉRAL

Comme il n'y a que quelques contenus pour l'instant, toutes les FAQs sont actuellement sous cette rubrique.

Dans quelle mesure un répertoire « .Inline » ou « _Inline » est-il jetable ?

Je dois probablement être plus catégorique sur le rôle des répertoires cache "_Inline/". Comme ils sont créés automatiquement, ils sont complètement jetables. Je les supprime tout le temps. Et il est tout à fait acceptable d'en avoir un différent pour chaque projet. En fait, tant que vous n'avez pas défini "~/.Inline/", Inline créera un nouveau répertoire "./_Inline" (sauf si vous avez fait quelque chose pour outrepasser ce processus automatique, comme utiliser l'option de configuration DIRECTORY, ou utiliser la variable d'environnement "PERL_INLINE_DIRECTORY"). Vous pouvez le déplacer vers "./.Inline" et il continuera de fonctionner si vous souhaitez lui donner plus de longévité et le cacher à la vue. Il existe une liste longue et compliquée de règles sur la manière dont les répertoires "[_.]Inline/" sont utilisés/créés. Mais cela a été conçu pour vous offrir le maximum de flexibilité et de facilité d'utilisation. N'ayez jamais peur de les détruire. Ils réapparaîtront la prochaine fois qu'ils seront nécessaires. :)

Quelle est la meilleure façon d'empaqueter le code Inline pour CPAN ?

Cette distribution inclut Inline::MakeMaker, décrit ci-dessous, qui prend des mesures spéciales lors de l'installation de votre module pour s'assurer que le code est compilé et installé, plutôt que compilé par les utilisateurs au moment de l'exécution. Mais les utilisateurs de votre module doivent installer Inline et le module de support de langage comme Inline::CPP comme prérequis pour votre module.

Une meilleure façon de distribuer votre module est avec Inline::Module, qui prend des mesures spéciales pour supprimer les dépendances sur Inline::* et le convertir en un simple module XS lors de la construction de votre distribution avant de le télécharger sur CPAN. Il s'intègre également facilement avec Dist::Zilla et d'autres outils d'auteur modernes pour une expérience d'auteur plus rationalisée.

Qu'est-il advenu de l'option « SITE_INSTALL » ?

"SITE_INSTALL" a disparu. J'allais la laisser et changer la sémantique, mais j'ai pensé qu'il valait mieux la supprimer, afin que les gens n'essaient pas de l'utiliser à l'ancienne. Il y a maintenant "_INSTALL_" (mais vous n'êtes pas censé le savoir :). Cela fonctionne magiquement grâce à l'utilisation de Inline::MakeMaker. Je l'ai expliqué plus tôt mais cela vaut la peine d'y revenir car c'est le plus grand changement pour la version 0.40. Voici comment installer 'définitivement' une extension Inline (module basé sur Inline) avec la version 0.40 :

1.
Créez un module avec Inline.
2.
Testez-le en utilisant le cache normal / local "_Inline/".
3.
Créez un fichier Makefile.PL (comme celui produit par h2xs)
4.
Changez 'use ExtUtils::MakeMaker' en 'use Inline::MakeMaker'
5.
Dans le WriteMakefile() de Makefile.PL, insérez : 
CONFIGURE_REQUIRES  =>  {
    'Inline::MakeMaker'     => 0.45,
    'ExtUtils::MakeMaker'   => 6.52,
},

(Voir la section « Writing Modules with Inline » de Inline.pod pour une explication / élaboration.)

6.
Changez votre 'use Inline C => DATA' en 'use Inline C => DATA => NAME => Foo

=> VERSION => 1.23' + Assurez-vous que NAME correspond au nom de votre package ('Foo'), ou => commence par 'Foo::'. + Si vous voulez supprimer un avertissement inoffensif qui apparaîtra => lors du chargement du module via « require », faites « Inline->init(); ». Voir => « Writing Modules with Inline » dans le pod Inline pour plus de détails. + Assurez-vous que => VERSION correspond à $Foo::VERSION. Cela doit être une chaîne de caractères (pas un nombre) => correspondant à "/^\d\.\d\d$/" + Faites la danse perl / make / test / install => (merci binkley :)

Avec Inline 0.41 (ou environ), vous pouvez sauter les étapes 3 et 4, et simplement dire "perl -MInline=INSTALL ./Foo.pm". Cela fonctionnera aussi pour les modules non-Inline. Cela deviendra la norme de fait (puisqu'il n'y a pas de norme facile) pour installer un module Perl. Cela permettra des paramètres de Makefile.PL comme "perl -MInline=INSTALL ./Foo.pm - PREFIX=/home/ingy/perl" et des choses comme ça. Cela utilisera également un MANIFEST si vous en fournissez un.

Comment créer une distribution binaire en utilisant Inline ?

J'ai trouvé comment créer et installer une distribution binaire PPM ; avec ou sans distribution du code C ! Et j'ai décidé de le partager avec vous tous :)

NOTE : Les futures versions d'Inline rendront ce processus une commande en une seule ligne. Mais
pour l'instant, utilisez cette recette simple.

La distribution Inline 0.40 est livrée avec un module d'extension d'exemple appelé Math::Simple. En théorie, vous pourriez distribuer ce module sur CPAN. Il dispose de tout le support nécessaire à l'installation. Vous le trouverez dans "Inline-0.40/modules/Math/Simple/". Voici les étapes pour le convertir en une distribution binaire sans code source C.

NOTE : Le destinataire de cette distribution binaire devra avoir le
module PPM.pm installé. Ce module nécessite de nombreux autres modules CPAN.
ActivePerl (disponible pour Win32, Linux et Solaris) les regroupe tous. Bien
qu'ActivePerl ne soit pas requis, cela rend les choses (beaucoup) plus
faciles.
