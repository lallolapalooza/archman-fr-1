NOM

Image::ExifTool::MIE - Lire/écrire les méta-informations MIE

SYNOPSIS

Ce module est utilisé par Image::ExifTool

DESCRIPTION

Ce module contient les routines requises par Image::ExifTool pour lire et écrire les informations dans les fichiers MIE.

QU'EST-CE QUE MIE ?

MIE signifie "Meta Information Encapsulation" (Encapsulation de méta-informations). Le format MIE est un format de méta-informations extensible et dédié qui prend en charge le stockage de méta-informations binaires ainsi que textuelles. MIE peut être utilisé pour encapsuler des méta-informations provenant de nombreuses sources et les regrouper avec n'importe quel type de fichier.

Caractéristiques

Ci-dessous se trouve une grille d'évaluation très subjective comparant les caractéristiques d'un certain nombre de formats de fichiers et de méta-informations courants, et les comparant à MIE. Les caractéristiques suivantes sont notées pour chaque format avec un score de 0 à 10 :

 1) Extensible (peut incorporer des informations définies par l'utilisateur).
 2) Identifiants de balises significatifs (indice sur la signification des informations inconnues).
 3) Capacité de lecture/écriture séquentielle (fluxable).
 4) Structure hiérarchique des informations.
 5) Lecteur/éditeur facile à implémenter.
 6) Ordre des informations bien défini.
 7) Longueurs de données importantes prises en charge : >64ko (+5) et >4Go (+5).
 8) Chaînes de texte localisées.
 9) Documents multiples dans un seul fichier.
10) Format compact qui ne gaspille ni l'espace disque ni la bande passante.
11) Méta-informations compressées prises en charge.
12) Éléments de données relocalisables (c.-à-d. sans décalages fixes).
13) Méta-informations binaires (+7) avec ordre d'octets variable (+3).
14) Balises obligatoires non requises (une complication inutile).
15) Ajouter des informations à la fin d'un fichier sans édition.

Par conception, MIE se classe en tête avec une marge significative. Les autres formats avec des scores raisonnables sont PDF, PNG et XMP, mais chacun a des points faibles importants. Ce qui peut surprendre, c'est que TIFF, EXIF et IPTC se classent si bas.

En plus d'obtenir des scores élevés pour toutes ces caractéristiques, le format MIE a la capacité unique d'encapsuler n'importe quel autre type de fichier, et fournit une méthode non intrusive pour ajouter des méta-informations à un fichier. Les méta-informations sont logiquement séparées des données du fichier original, ce qui est extrêmement important car les méta-informations sont couramment perdues lorsque les fichiers sont modifiés.

De plus, le format MIE prend en charge plusieurs fichiers par simple concaténation, permettant toutes sortes de fonctionnalités merveilleuses telles que des bases de données linéaires, des historiques de modification ou des mises à jour de fichiers non intrusives. Cette capacité peut également être exploitée pour permettre l'ajout de traînées au format MIE à certains autres types de fichiers.

SPÉCIFICATION DU FORMAT MIE 1.1 (2007-01-21)

Structure du fichier

Un fichier MIE se compose d'une série d'éléments MIE. Un élément MIE peut contenir soit des données, soit un groupe d'éléments MIE, fournissant un format hiérarchique pour stocker des données. Chaque élément MIE est identifié par un nom de balise lisible par l'homme, et peut stocker des données allant de 0 à 2^64-1 octets de longueur.

Signature du fichier

Le premier élément du fichier MIE doit être un élément de groupe MIE non compressé avec un nom de balise "0MIE". Cette restriction permet d'utiliser les 8 premiers octets d'un fichier MIE pour identifier un fichier au format MIE. Le tableau suivant liste les deux séquences d'octets initiales possibles pour un fichier au format MIE (la première pour l'ordre d'octets big-endian, et la seconde pour l'ordre d'octets little-endian) :

Numéro d'octet:      0    1    2    3    4    5    6    7
Caractères C:     ~ \x10 \x04    ?    0    M    I    E
    ou            ~ \x18 \x04    ?    0    M    I    E
Hexadécimal:     7e   10   04    ?   30   4d   49   45
    ou           7e   18   04    ?   30   4d   49   45
Décimal:        126   16    4    ?   48   77   73   69
    ou          126   24    4    ?   48   77   73   69

Notez que l'octet 1 peut avoir l'une des deux valeurs possibles (0x10 ou 0x18), et que l'octet 3 peut avoir n'importe quelle valeur (0x00 à 0xff).

Structure de l'élément

1 octet  SyncByte = 0x7e (décimal 126, caractère '~')
1 octet  FormatCode (voir ci-dessous)
1 octet  TagLength (T)
1 octet  DataLength (donne D si DataLength < 253)
T octets TagName (T donné par TagLength)
2 octets DataLength2 [existe seulement si DataLength == 255 (0xff)]
4 octets DataLength4 [existe seulement si DataLength == 254 (0xfe)]
8 octets DataLength8 [existe seulement si DataLength == 253 (0xfd)]
D octets DataBlock (D donné par DataLength)

La longueur minimale d'un élément est de 4 octets (pour un terminateur de groupe). La taille maximale de DataBlock est de 2^64-1 octets. TagLength et DataLength sont des entiers non signés, et l'ordre d'octets pour les champs DataLength multi-octets est spécifié par l'élément de groupe MIE contenant. Le SyncByte est aligné sur un octet, donc aucun remplissage n'est ajouté pour s'aligner sur une limite de N octets.

FormatCode

Le code de format est un masque de bits qui définit le format des données :

7654 3210
++++ ----  FormatType
---- +---  TypeModifier
---- -+--  Compressed
---- --++  FormatSize
FormatType (masque de bits 0xf0) :
0x00 - données autres (ou inconnues)
0x10 - groupe MIE
0x20 - chaîne de texte
0x30 - liste de chaînes de texte séparées par des caractères nuls
0x40 - entier
0x50 - rationnel
0x60 - virgule fixe
0x70 - virgule flottante
0x80 - espace libre
TypeModifier (masque de bits 0x08) :
Modifie la signification de certains FormatTypes (0x00-0x60) : 
0x08 - autres données sensibles à l'ordre d'octets du groupe MIE
0x18 - groupe MIE avec ordre d'octets little-endian
0x28 - chaîne de texte encodée UTF
0x38 - liste de chaînes de texte encodées UTF
0x48 - entier signé
0x58 - rationnel signé (le dénominateur est toujours non signé)
0x68 - virgule fixe signée
Compressed (masque de bits 0x04) :
Si ce bit est défini, le bloc de données est compressé à l'aide de Zlib deflate. Un groupe MIE entier peut être compressé, à l'exception des groupes de niveau fichier.
FormatSize (masque de bits 0x03) :
Donne la taille en octets de chaque élément de données : 
0x00 - 8 bits  (1 octet)
0x01 - 16 bits (2 octets)
0x02 - 32 bits (4 octets)
0x03 - 64 bits (8 octets)

Le nombre d'octets dans une seule valeur pour ce format est donné par 2**FormatSize (ou 1 << FormatSize). Le nombre de valeurs est la longueur des données divisée par ce nombre d'octets. C'est une erreur si la longueur des données n'est pas un multiple exact de la taille du format en octets.

La liste suivante contient toutes les valeurs de FormatCode MIE actuellement définies pour les données non compressées (ajoutez 0x04 à chaque valeur pour les données compressées) :

0x00 - autres données (insensibles à l'ordre d'octets du groupe MIE) (1)
0x01 - autres données 16 bits (peuvent être permutées)
0x02 - autres données 32 bits (peuvent être permutées)
0x03 - autres données 64 bits (peuvent être permutées)
0x08 - autres données (sensibles à l'ordre d'octets du groupe MIE) (1)
0x10 - groupe MIE avec valeurs big-endian (1)
0x18 - groupe MIE avec valeurs little-endian (1)
0x20 - chaîne ASCII (ISO 8859-1) (2,3)
0x28 - chaîne UTF-8 (2,3,4)
0x29 - chaîne UTF-16 (2,3,4)
0x2a - chaîne UTF-32 (2,3,4)
0x30 - liste de chaînes ASCII (ISO 8859-1) (3,5)
0x38 - liste de chaînes UTF-8 (3,4,5)
0x39 - liste de chaînes UTF-16 (3,4,5)
0x3a - liste de chaînes UTF-32 (3,4,5)
0x40 - entier non signé 8 bits
0x41 - entier non signé 16 bits
0x42 - entier non signé 32 bits
0x43 - entier non signé 64 bits (6)
0x48 - entier signé 8 bits
0x49 - entier signé 16 bits
0x4a - entier signé 32 bits
0x4b - entier signé 64 bits (6)
0x52 - rationnel non signé 32 bitsrationnel non signé (16 bits numérateur puis dénominateur) (7)
0x53 - rationnel non signé 64 bits (32 bits numérateur puis dénominateur) (7)
0x5a - rationnel signé 32 bits (dénominateur non signé) (7)
0x5b - rationnel signé 64 bits (dénominateur non signé) (7)
0x61 - virgule fixe non signée 16 bits (les 8 bits de poids fort sont la partie entière) (8)
0x62 - virgule fixe non signée 32 bits (les 16 bits de poids fort sont la partie entière) (8)
0x69 - virgule fixe signée 16 bits (les 8 bits de poids fort sont l'entier signé) (8)
0x6a - virgule fixe signée 32 bits (les 16 bits de poids fort sont l'entier signé) (8)
0x72 - flottant IEEE 32 bits (non recommandé pour des raisons de portabilité)
0x73 - double IEEE 64 bits (non recommandé pour des raisons de portabilité) (6)
0x80 - espace libre (les données de valeur ne contiennent pas d'informations utiles)

Notes :

1.
L'ordre des octets spécifié par le TypeModifier du groupe MIE s'applique au groupe MIE ainsi qu'à tous les éléments du groupe. Les données pour tous les FormatCodes sauf 0x08 (autres données, sensibles à l'ordre des octets) peuvent être transférées entre des groupes MIE ayant des ordres d'octets différents en permutant les octets des données non compressées selon le format de données spécifié. La liste suivante illustre le motif de permutation des octets, basé sur FormatSize, pour tous les types de format sauf les rationnels (FormatType 0x50). 
  FormatSize              Changement de la séquence d'octets
--------------      -----------------------------------
0x00 (8 bits)       0 1 2 3 4 5 6 7 --> 0 1 2 3 4 5 6 7 (pas de changement)
0x01 (16 bits)      0 1 2 3 4 5 6 7 --> 1 0 3 2 5 4 7 6
0x02 (32 bits)      0 1 2 3 4 5 6 7 --> 3 2 1 0 7 6 5 4
0x03 (64 bits)      0 1 2 3 4 5 6 7 --> 7 6 5 4 3 2 1 0

Les valeurs rationnelles se composent de deux entiers, elles sont donc permutées comme le FormatSize immédiatement inférieur. Par exemple, un rationnel 32 bits (FormatSize 0x02, et FormatCode 0x52 ou 0x5a) est permuté comme deux valeurs 16 bits (c'est-à-dire comme s'il avait FormatSize 0x01).

2.
Le TagName d'un élément de chaîne peut avoir un suffixe de 6 caractères pour indiquer un locale spécifique. (ex. "Title-en_US", ou "Keywords-de_DE").
3.
Les chaînes de texte ne sont normalement pas terminées par un caractère nul, cependant elles peuvent être remplies d'un ou plusieurs caractères nuls à la fin du bloc de données pour permettre l'édition des chaînes dans des blocs de données de longueur fixe. Les sauts de ligne dans le texte sont indiqués par un seul caractère LF (0x0a).
4.
Les chaînes UTF ne doivent pas commencer par une marque d'ordre des octets (BOM) car l'ordre des octets et la taille des octets sont spécifiés par le format MIE. Si un BOM est trouvé, il doit être traité comme une espace insécable de largeur nulle.
5.
Une liste de chaînes de texte séparées par des caractères nuls. Ces listes ne doivent pas être remplies de caractères nuls ou terminées par un caractère nul, car cela serait interprété comme des chaînes de longueur zéro supplémentaires. Pour les chaînes ASCII et UTF-8, le caractère nul est un simple zéro (0x00). Pour les chaînes UTF-16 ou UTF-32, le caractère nul est 2 ou 4 zéros respectivement.
6.
Les entiers et doubles 64 bits sont soumis à l'ordre des octets spécifié pour à la fois les mots de 32 bits et les octets à l'intérieur de ces mots. Par exemple, l'octet de poids fort est toujours le premier octet si big-endian, et le huitième octet si little-endian. Cela signifie qu'une certaine permutation est toujours nécessaire pour ces valeurs sur les systèmes où l'ordre des octets diffère de l'ordre des mots (ex. certains systèmes ARM), quelle que soit la finianness des valeurs stockées.
7.
Les valeurs rationnelles sont traitées comme deux entiers séparés. Le numérateur vient toujours en premier quel que soit l'ordre des octets. Dans une valeur rationnelle signée, seul le numérateur est signé. Le dénominateur de toutes les valeurs rationnelles est non signé (ex. un rationnel signé 64 bits de 0x80000000/0x80000000 évalue à -1, pas +1).
8.
Les valeurs en virgule fixe 32 bits sont converties en virgule flottante en les traitant comme un entier et en les divisant par une valeur appropriée. ex.) 
valeur fixe 16 bits = valeur entière 16 bits / 256.0
valeur fixe 32 bits = valeur entière 32 bits / 65536.0

TagLength

Donne la longueur de la chaîne TagName. Toute valeur entre 0 et 255 est valide, mais le TagLength de 0 n'est valide que pour le terminateur de groupe MIE.

DataLength

DataLength est un octet non signé qui donne le nombre d'octets dans le bloc de données. Une valeur entre 0 et 252 donne la longueur des données directement, et les nombres de 253 à 255 sont réservés pour les codes DataLength étendus. Les codes 255, 254 et 253 indiquent que l'élément contient un entier non signé supplémentaire de 2, 4 ou 8 octets représentant la longueur des données.

0-252      - longueur du bloc de données
255 (0xff) - utiliser DataLength2
254 (0xfe) - utiliser DataLength4
253 (0xfd) - utiliser DataLength8

Un DataLength de zéro est valide pour tout élément sauf un groupe MIE compressé. Un DataLength de zéro pour un groupe MIE non compressé indique que la longueur du groupe est inconnue. Pour les autres éléments, une longueur de zéro indique qu'il n'y a pas de données associées. Un élément terminateur doit avoir un DataLength de 0, 6 ou 10, et ne peut pas utiliser un DataLength étendu.

TagName

La chaîne TagName fait de 0 à 255 octets de long, et est composée des caractères ASCII A-Z, a-z, 0-9 et soulignement ('_'). De plus, un tiret ('-') est utilisé pour séparer le code langue/pays dans le TagName d'un texte localisé, et une chaîne d'unités (pouvant contenir d'autres caractères ASCII) peut apparaître entre crochets à la fin du TagName. La chaîne TagName n'est PAS terminée par un caractère nul. Un élément MIE avec une chaîne de tag de longueur zéro est réservé au terminateur de groupe.

Les éléments MIE sont triés par ordre alphabétique par TagName dans chaque groupe. Plusieurs éléments avec le même TagName sont autorisés, même dans le même groupe.

Les TagNames devraient être significatifs. La casse est significative. Les mots devraient être en minuscules avec une première lettre majuscule, et les acronymes devraient être entièrement en majuscules. Le soulignement ("_") est fourni pour permettre la séparation de deux acronymes ou deux nombres, mais il ne devrait pas être utilisé sauf si nécessaire. Aucune séparation n'est nécessaire entre un acronyme et un mot (ex. "ISOSetting").

Tous les TagNames devraient commencer par une lettre majuscule. Une exception à cette règle permet aux tags de commencer par un chiffre (0-9) s'ils doivent venir avant d'autres tags dans l'ordre de tri, ou par une lettre minuscule (a-z) s'ils doivent venir après. Par exemple, l'élément '0Type' commence par un chiffre donc il vient avant, et l'élément 'data' commence par une lettre minuscule pour qu'il vienne après les tags d'informations méta dans le groupe principal "0MIE".

Les noms de tags pour les chaînes de texte localisées ont un suffixe de 6 caractères avec le format suivant : Le premier caractère est un tiret ('-'), suivi d'un code de langue ISO 639-1 de 2 caractères en minuscules, puis un soulignement ('_'), et se termine par un code de pays ISO 3166-1 alpha 2 de 2 caractères en majuscules. (ex. "-en_US", "-en_GB", "-de_DE" ou "-fr_FR". Notez que "GB", et non "UK" est le code pour la Grande-Bretagne, bien que "UK" devrait être reconnu pour des raisons de compatibilité.) Le suffixe est inclus lors du tri alphabétique des tags, donc la locale par défaut (sans suffixe de nom de tag) vient toujours en premier. Si le pays est inconnu ou non applicable, un code de pays "XX" devrait être utilisé.

Les ensembles de tags avec des valeurs numériques peuvent permettre de spécifier des unités de mesure. La chaîne d'unités est stockée entre crochets à la fin du nom du tag, et est composée de zéro ou plusieurs caractères ASCII dans la plage 0x21 à 0x7d, excluant les caractères de crochets 0x28 et 0x29. (ex. "Resolution(/cm)" ou "SpecificHeat(J/kg.K)".) Voir Image::ExifTool::MIEUnits pour les détails. Les chaînes d'unités ne sont pas localisées, et ne peuvent pas être utilisées en combinaison avec des chaînes de texte localisées.

Les ensembles de tags qui nécessiteraient un préfixe commun devraient être ajoutés dans un groupe MIE séparé au lieu d'ajouter le préfixe à tous les noms de tags. Par exemple, au lieu de ces TagName's :

ExternalFlashType
ExternalFlashSerialNumber
ExternalFlashFired

on désignerait plutôt un groupe MIE "ExternalFlash" séparé pour contenir les éléments suivants :

Type
SerialNumber
Fired

DataLength2/4/8

Ces champs DataLength étendus n'existent que si DataLength est 255, 254 ou 253, et sont respectivement des entiers non signés de 2, 4 ou 8 octets donnant la longueur du bloc de données. L'une de ces valeurs doit être utilisée si le bloc de données est plus grand que 252 octets, mais elles peuvent être utilisées si désiré pour des blocs plus petits aussi (bien que cela puisse ajouter quelques octets inutiles à l'élément MIE).

DataBlock

La valeur de données pour l'élément MIE. Le format des données est donné par le FormatCode. Pour les éléments de groupe MIE, les données incluent tous les éléments contenus et le terminateur de groupe.

Groupes MIE

Tous les éléments de données MIE doivent être contenus dans un groupe. Un groupe commence par un élément de groupe MIE, et se termine par un terminateur de groupe. Les groupes peuvent être imbriqués dans une hiérarchie à une profondeur arbitraire.

Un élément de groupe MIE est identifié par un format code de 0x10 (ordre big endian) ou 0x18 (little endian). Le terminateur de groupe est distingué par un TagLength de zéro (c'est le seul élément autorisé à avoir un TagLength de zéro), et a un FormatCode de 0x00.

L'élément de groupe MIE est autorisé à avoir un DataLength de zéro seulement si les données ne sont pas compressées. Cette valeur spéciale indique que la longueur du groupe est inconnue (sinon la valeur minimale pour DataLength est 4, correspondant à la taille minimale du groupe qui inclut un terminateur d'au moins 4 octets). Si DataLength est zéro, tous les éléments du groupe doivent être analysés jusqu'à ce que le terminateur de groupe soit trouvé. S'il est non nul, DataLength inclut la longueur de tous les éléments contenus dans le groupe, y compris le terminateur de groupe. L'utilisation d'un DataLength non nul est encouragée car elle permet aux lecteurs de sauter rapidement des groupes MIE entiers. Pour les groupes compressés, DataLength doit être non nul, et est la longueur des données du groupe compressé (qui inclut le terminateur de groupe compressé).

Terminateur de groupe

Le terminateur de groupe a un FormatCode et un TagLength de zéro. Le DataLength du terminateur doit être de 0, 6 ou 10 octets, et les codes DataLength étendus ne peuvent pas être utilisés. Avec un DataLength de zéro, la séquence d'octets pour un terminateur est "7e 00 00 00" (hex). Avec un DataLength de 6 ou 10 octets, le bloc de données du terminateur contient des informations sur la longueur et l'ordre des octets du groupe précédent. Cette information supplémentaire est recommandée pour les groupes de niveau fichier, et est utilisée dans les fichiers MIE multi-documents et les trailers MIE pour permettre de scanner le fichier à l'envers depuis la fin. (Cela peut aussi permettre de récupérer certains documents si une partie du fichier est corrompue.) La structure de ce bloc de données de terminateur optionnel est la suivante :

4 ou 8 octets  GroupLength (entier non signé)
1 octet        ByteOrder (0x10 ou 0x18, identique au groupe MIE)
1 octet        GroupLengthSize (0x04 ou 0x08)

Les valeurs ByteOrder et GroupLengthSize donnent l'ordre des octets et la taille de l'entier GroupLength. La valeur GroupLength est la longueur totale du groupe MIE entier se terminant par ce terminateur, y compris l'élément de groupe MIE d'ouverture et le terminateur

lui-même.

Groupes MIE au niveau du

fichier

Les groupes MIE au niveau du fichier ne peuvent PAS être

compressés.

Tous les éléments d'un fichier MIE sont contenus dans un groupe spécial avec un TagName de "0MIE". Le but du groupe "OMIE" est de fournir une signature unique au début du fichier et d'encapsuler des informations permettant de combiner facilement les fichiers. Le groupe "0MIE" doit être terminé comme tout autre groupe, mais il est recommandé que le terminateur d'un groupe au niveau du fichier inclue le bloc de données optionnel (défini ci-dessus) pour fournir des informations sur la longueur du groupe et l'ordre des

octets.

Il est valide d'avoir plus d'un groupe "0MIE" au niveau du fichier, permettant plus

ieurs documents dans un seul fichier MIE. De plus, la structure MIE permet de génére
r des fichiers multi-documents en concaténant simplement deux fichiers MIE ou plus.

actuelle du fichier (à la fin des données lues à l'étape 1), se déplacer vers l'arrière de ce nombre d'octets pour trouver le début de l'élément de groupe MIE pour ce document.

etc.

Signature de la fin de

fichier

Le format MIE peut être utilisé pour des informations de fin de fichier ajoutées à d'autres types de fichiers. Lorsque cela est fait, une signature doit apparaître à la fin du groupe MIE principal pour identifier de manière unique la fin de fichier au format MIE. Pour y parvenir, une signature de fin de fichier "zmie" est écrite comme le dernier élément dans le groupe principal "0MIE". Cet élément a un FormatCode de 0, un TagLength de 4, un DataLength de 0, et un TagName de "zmie". Avec cette signature, la séquence d'octets hexadécimale "7e 00 04 00 7a 6d 69 65" apparaît immédiatement avant le terminateur final du groupe, et les 22 derniers octets de la fin de fichier correspondent à l'un des 4 motifs suivants (où la longueur de la fin de fichier est donnée par "xx", comme ci-dessus)

: 
?? ?? ?? ?? 7e 00 04 00 7a 6d 69 65 7e 00 00 06 xx xx xx xx 10 04
?? ?? ?? ?? 7e 00 04 00 7a 6d 69 65 7e 00 00 06 xx xx xx xx 18 04
7e 00 04 00 7a 6d 69 65 7e 00 00 0a xx xx xx xx xx xx xx xx 10 08
7e 00 04 00 7a 6d 69 65 7e 00 00 0a xx xx xx xx xx xx xx xx 18
08

Notez que le terminateur avec DataLength zéro ne peut pas être utilisé ici car la longueur de la fin de fichier doit être connue pour se déplacer vers l'arrière depuis la fin du

fichier.

t être ajoutées au même fichier e

Valeurs de données

MIE

Les valeurs de données MIE pour une balise donnée ne sont généralement pas limitées à un FormatCode spécifique. Toute valeur peut être représentée dans tout format approprié, y compris les nombres représentés sous forme de chaîne (ASCII ou UTF)

.

Il est préférable que les valeurs étroitement liées avec le même format soient écrites dans une seule balise plutôt que d'utiliser plusieurs balises. Cela améliore la localisation des valeurs similaires et réduit le surcoût des éléments MIE. Par exemple, au lieu de balises ImageWidth et ImageHeight séparées, une seule balise ImageSize est

définie.

Les balises qui peuvent prendre un ensemble discret de valeurs devraient avoir des valeurs significatives si possible. Cela améliore l'étendibilité du format et permet une interprétation plus raisonnable des valeurs non

reconnues.

Représentation

numérique

Les nombres entiers et en virgule flottante peuvent être représentés sous forme binaire ou sous forme de chaîne. Sous forme de chaîne, les entiers sont une série de chiffres avec un signe optionnel au début (ex. "[+|-]DDDDDD"), et les valeurs multiples sont séparées par un seul caractère espace (ex. "23 128 -32"). Les nombres en virgule flottante sont similaires mais peuvent aussi contenir un point décimal et/ou un exposant signé avec un caractère 'e' initial (ex. "[+|-]DD[.DDDDDD][e(+|-)EEE]"). La chaîne "inf" est utilisée pour représenter l'infini. Un avantage des chaînes numériques est qu'elles peuvent avoir une précision arbitrairement élevée car le nombre possible de chiffres significatifs est pratiquement

illimité.

Notez que les valeurs numériques peuvent avoir des unités de mesure associées qui sont spécifiées dans la chaîne

"TagName".

Format

Date/Heure

Toutes les dates MIE sont des chaînes de la forme "YYYY:mm:dd HH:MM:SS.ss+HH:MM". Les secondes fractionnaires (".ss") sont optionnelles, et si elles sont incluses, peuven

t contenir un nombre quelconque de chiffres significatifs (contrairement à tous les autres champs qui ont un nombre fixe de chiffres et doivent être complétés par des zér
os initiaux si nécessaire). Le fuseau horaire ("+HH:MM" ou "-HH:MM") est recommandé mais non requis. S'il n'est pas donné, le fuseau horaire local du système est supposé.

Type

MIME

Le type MIME de base pour un fichier MIE est "application/x-mie", cependant le type MIME spécifique dépend du type de sous-fichier, et est obtenu en ajoutant "x-mie-" au type MIME du sous-fichier. Par exemple, avec un sous-fichier de type "image/jpeg", le ty

pe MIME du fichier MIE est "image/x-mie-jpeg". Mais notez que le "x-" n'est pas dupliqué si le type MIME du sous-fichier commence déjà par "x-". Ainsi un sous-fichier avec le type MIME "image/x-raw" est contenu dans un fichier MIE de type "image/x-mie-raw",
et non "image/x-mie-x-raw". Dans le cas de plusieurs documents dans un fichier MIE, le type MIME est pris à partir du premier document. Quel que soit le type de sous-fichier, tous les fichiers au format MIE devraient avoir une extension de nom de fichier ".MIE".

Niveaux de prise en

charge

Les applications de lecture/écriture MIE de base peuvent choisir de ne pas fournir la prise en charge de certaines fonctionnalités avancées du format MIE. Les fonctionnalités qui peuvent ne pas être prises en charge par tous les logiciels sont

:
Compressi
on
Les logiciels ne prenant pas en charge la compression doivent ignorer les éléments et groupes compressés, mais devraient être capables de traiter les informations
restantes.
Grandes longueurs de
données
Certains logiciels peuvent limiter la taille maximale d'un groupe ou d'un élément MIE. Historiquement, une limite de 2 Go peut être imposée par c
ertains systèmes. Cependant, les longueurs de données sur 8 octets devraient être prises en charge par toutes les applications à condition que l
a valeur ne dépasse pas la limite du système. (ex. Pour les systèmes avec une limite de 2 Go, les longueurs de données sur 8 octets devraie
nt être prises en charge si les 17 bits de poids fort sont tous zéro.) Si une longueur de données supérieure à la limite du système est rencontr
ée, il peut être nécessaire que l'application arrête le traitement si elle ne peut pas se déplacer vers le élément suivant dans le fichier.

EXEMPLE

S

Cette section donne des exemples pour travailler avec les informations MIE en utilisant

ExifTool.

Encapsulation d'informations avec données dans un fichier

MIE

La commande suivante encapsule tout fichier reconnu par ExifTool dans un fichier MIE, et initialise les balises MIE à partir des informations du fichier

: 
exiftool -o new.mie -tagsfromfile FILE '-mie:all<all' \
    '-subfilename<filename' '-subfiletype<filetype' \
    '-subfilemimetype<mimetype' '-subfiledata<=FILE
'

où "FILE" est le nom du

fichier.

Pour les fichiers non reconnus, cette commande peut être utilisée

: 
exiftool -o new.mie -subfilename=FILE -subfiletype=TYPE \
    -subfilemimetype=MIME '-subfiledata<=FILE
'

où "TYPE" et "MIME" représentent respectivement le ty

pe de fichier source
et le type MIME.

Ajout d'une fin de fichier MIE à un

fichier

Le format MIE peut aussi être utilisé pour stocker des informations dans une fin de fichier ajoutée à un autre type de fichier. Attention, les fins de fichier peuvent ne pas être compatibles avec tous les formats de fichier, mais JPEG et TIFF sont deux formats où des informations de fin de fichier supplémentaires ne créent aucun problème pour l'analyse normale du fichier. Notez également que cette technique a l'inconvénient que les informations de fin de fichier sont souvent perdues si le fichier est ensuite modifié par d'autres

logiciels.

Créer une fin de fichier MIE avec ExifTool est un processus en deux étapes car ExifTool ne peut pas actuellement être utilisé pour ajouter directement une fin de fichier MIE. L'exemple ci-dessous illustre les étapes pour ajouter une fin de fichier MIE avec une petite image d'aperçu ("small.jpg") à une image JPEG de destination ("dst.jp

g").

Étape 1) Créer un fichier MIE avec un TrailerSignature contenant les informations souhaitées

: 
exiftool -o new.mie -trailersignature=1 -tagsfromfile small.jpg \
    '-previewimagetype<filetype' '-previewimagesize<imagesize' \
    '-previewimagename<filename' '-previewimage<=small.
jpg'

Étape 2) Ajouter les informations MIE à un autre fichier. Sous Unix, cela peut être fait avec la commande 'cat'

: 
cat new.mie >> dst.
jpg

Une fois ajoutées, ExifTool peut être ut

ilisé pour modifier ou supprimer un
trailer MIE dans une image JPEG ou TIFF.

Plusieurs documents MIE dans un seul

fichier

La spécification MIE permet à plusieurs documents MIE (ou trailers) d'exister dans un seul fichier. Un fichier de ce type peut être créé en concaténant simplement des documents MIE. ExifTool peut être utilisé pour accéder aux informations d'un document spécifique en ajoutant un numéro de copie au nom de groupe MIE. Par exemple

: 
# écrire la balise Author dans le deuxième document MIE
exiftool -mie2:author=phil test.mie # supprimer le premie
r document MIE d'un fichier exiftool -mie1:all= test.mie

Unités de

mesure

Certaines balises MIE permettent de spécifier des valeurs dans différentes unités de mesure. Dans le format de fichier MIE, ces unités sont combinées avec le nom de la balise, mais lors de l'utilisation d'ExifTool, elles sont spécifiées entre crochets après la valeur

: 
exiftool -mie:gpsaltitude='7500(ft)' test.
mie

Si aucune unité n'est

fournie, les unités pa
r défaut sont écrites.

Texte

localisé

Les valeurs de texte localisées sont accessibles en ajoutant un code langue/pays au nom de la balise. Par exemple

: 
exiftool -com
ment-en_us='t
his is a comm
ent' test.mie
