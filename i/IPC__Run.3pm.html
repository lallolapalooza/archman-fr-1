DESCRIPTION

IPC::Run vous permet d'exécuter et d'interagir avec des processus enfants en utilisant des fichiers, des tuyaux et des pseudo-ttys. Les utilisations de style system() et les utilisations scriptées sont supportées et peuvent être mélangées. De même, les styles d'API fonctionnelle et orientée objet sont tous deux supportés et peuvent être mélangés.

Divers opérateurs de redirection rappelant ceux vus sur les lignes de commande courantes sous Unix et DOS sont fournis.

MISE EN ROUTE SIMPLE

Voici un guide rapide pour une utilisation basique de la fonction run() d'IPC::Run.

Capturer la sortie et les erreurs d'une commande externe

Supposons que vous vouliez exécuter une commande dans votre shell. Nous utiliserons "ls" pour simplifier, bien qu'il existe de bien meilleures façons d'obtenir une liste de fichiers, telles que la fonction glob() ou le module File::Find.

La forme de base de run() a la commande et ses arguments passés sous forme d'arrayref dans le premier argument. La commande ne peut pas être une chaîne unique.

@cmd = [ 'ls', '-a', '-l', '-r', '-t' ];    # Oui
@cmd = ( 'ls -a -l -r -t' );                # Non

Après la commande, passez une référence scalaire "\$in" pour l'entrée à passer, et des références scalaires "\$out" et "\$err" pour recevoir le contenu de la sortie standard (stdout) et de la sortie d'erreur standard (stderr).

use IPC::Run qw( run );
@cmd = qw( ls -l -a -r -t );
run( \@cmd, \$in, \$out, \$err ) or die $?;
print("\$err is ", length($err), " bytes long\n");
print($err, "\n");
print("\$out is ", length($out), " bytes long\n");
print($out, "\n");

L'exécution de ceci montrera quelque chose comme :

$err is 0 bytes long
$out is 1410 bytes long
total 392
drwxr-xr-x    3 andy  staff     96 Mar 17 11:53 .github
-rw-r--r--    1 andy  staff    158 Mar 17 11:53 .gitignore
... etc ...

Notez que $out et $err sont toujours définis après un appel à run(), même s'ils ne reçoivent aucune donnée.

Passer l'entrée au programme externe

Si vous avez une entrée à passer, placez-la dans les variables $in. Par exemple, pour utiliser la commande "wc" pour compter les lignes, les mots et les caractères d'un bloc de texte :

$in = <<'CARROLL';
'Twas brillig, and the slithy toves
    Did gyre and gimble in the wabe:
All mimsy were the borogoves,
    And the mome raths outgrabe.
CARROLL
@cmd = qw( wc );
run( \@cmd, \$in, \$out, \$err ) or die $?;
print "$out";

Ceci donne la sortie :

4      23     140

Gérer les erreurs

Il est important de vérifier le code de retour de run() pour voir si la commande s'est exécutée avec succès. run() retourne un booléen vrai en cas de succès, et faux en cas d'échec. Notez que c'est l'inverse de system() de Perl, qui retourne 0 en cas de succès et une valeur non nulle en cas d'échec.

Pour le code d'erreur spécifique du sous-processus, vérifiez $? directement.

@cmd = qw( tar xzvf nonexistent.tar );
if ( !run( \@cmd, \$in, \$out, \$err ) ) {
    print "\$? = $?\n";
    print "err = $err\n";
}

L'exécution de ceci donne :

$? = 256
err = tar: Error opening archive: Failed to open 'nonexistent.tar'

Si le programme n'existe pas, alors run() fera un "die" et ne retournera rien du tout. Par exemple :

@cmd = qw( bogus-command );
my $rc = run( \@cmd, \$in, \$out, \$err );
print "run returned ", ($rc ? "true" : "false"), "\n";

L'exécution de ceci n'atteint pas l'instruction "print".

Command 'bogus-command' not found in [ list of paths ] at program.pl line N.

Pour gérer la possibilité d'un programme inexistant, appelez run() à l'intérieur d'un "eval".

my $rc;
eval { $rc = run( \@cmd, \$in, \$out, \$out ); 1; };
if ( !defined($rc) ) {
    print "run died: $@\n";
}
else {
    if ( $rc ) {
        print "run returned true\n";
    }
    else {
        print "run returned false\n";
        print "\$? = $?\n";
    }
}

Il semble que si l'enfant n'est pas entièrement créé au moment où CreateProcess retourne et que nous fermons le socket TCP qui lui est transmis, le socket parent peut aussi être fermé. Cela est observé avec les applications pumper Win32, et non le « vrai » processus enfant qui est lancé.

Je suppose que c'est parce que le kernel n'a pas encore eu le temps d'incrémenter le compteur de références sur l'extrémité de l'enfant (puisque l'enfant était lent à démarrer), donc la fermeture de l'extrémité enfant par le parent cause la fermeture du socket, fermant ainsi le socket

parent.

Étant une condition de course, c'est difficile à reproduire, mais je l'ai rencontré en testant ce code sur un partage de disque vers une machine samba. Dans ce cas, il faut à t/run.t beaucoup de temps pour lancer ses processus enfants (le parent se bloque dans le premier select pendant plusieurs secondes jusqu'à ce que l'enfant émette une sortie de

AVERTISSEMENT : Les coprocessus de fonction ("run \&foo, ...") souffrent de deux limitations. La première est qu'il est difficile de fermer tous les filehandles que l'enfant hérite du parent, puisqu'il n'y a aucun moyen de scanner tous les FILEHANDLEs ouverts dans Perl et que c'est à la fois pénible et un peu dangereux de fermer tous les descripteurs de fichier ouverts avec POSIX::close(). Pénible parce que nous ne pouvons pas non plus dire quels fds sont ouverts au niveau POSIX, donc nous devrions scanner tous les fds possibles et fermer ceux que nous ne voulons pas ouverts (normalement exec() ferme tout ce qui n'est pas héritable mais nous ne faisons pas exec() pour les processus

&sub.

Le deuxième problème est que les subs DESTROY de Perl et d'autres nettoyages à la sortie s'exécutent dans le processus enfant. Si des objets sont instanciés dans le parent avant que l'enfant soit forké, le DESTROY s'exécutera une fois dans le parent et une fois dans l'enfant. Quand les subs coprocessus se terminent, POSIX::_exit est appelé pour contourner cela, mais cela signifie que les objets qui sont encore référencés à ce moment-là ne sont pas nettoyés. Ainsi, définir des variables de package ou des variables de fermeture pour pointer vers des objets qui dépendent de DESTROY pour affecter des choses en dehors du processus (fichiers, etc), conduira à des

bugs.
