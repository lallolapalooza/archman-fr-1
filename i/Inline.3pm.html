NOM

Inline - Écrire des sous-routines Perl dans d'autres langages de programmation

VERSION

Ce document décrit la version 0.87d'Inline.

SYNOPSIS

use Inline C;
print "9 + 16 = ", add(9, 16), "\n";
print "9 - 16 = ", subtract(9, 16), "\n";
__END__
__C__
int add(int x, int y) {
  return x + y;
}
int subtract(int x, int y) {
  return x - y;
}

DESCRIPTION

Le module Inline vous permet de placer du code source provenant d'autres langages de programmation directement « inline » dans un script ou un module Perl. Le code est automatiquement compilé selon les besoins, puis chargé pour un accès immédiat depuis Perl.

Inline vous évite le désagrément d'avoir à écrire et compiler votre propre code de liaison en utilisant des outils comme XS ou SWIG. Tapez simplement le code où vous le souhaitez et exécutez votre Perl comme d'habitude. Tous les détails compliqués sont gérés pour vous. La compilation et l'installation de vos morceaux de code se font de manière transparente ; la seule chose que vous remarquerez est le délai de compilation lors de la première exécution.

Le code Inline n'est compilé que la première fois que vous l'exécutez (ou chaque fois qu'il est modifié), vous ne subissez donc la perte de performance qu'une seule fois. Le code qui est Inliné dans des modules distribués (comme sur le CPAN) sera compilé lorsque le module est installé, l'utilisateur final ne remarquera donc jamais le temps de compilation.

Mieux encore, cela fonctionne de la même manière sous Unix et sous Microsoft Windows. Voir Inline-Support pour les informations sur la prise en charge.

Pourquoi Inline ?

Voulez-vous savoir « Pourquoi utiliser d'autres langages en Perl ? » ou « Pourquoi devrais-je utiliser Inline pour le faire ? » ? Je vais essayer de répondre aux deux.

Pourquoi utiliser d'autres langages en Perl ?
La raison la plus évidente est la performance. Pour un langage interprété, Perl est très rapide. Beaucoup de gens diront « Tout ce que Perl peut faire, C peut le faire plus vite ». (Ils ne mentionnent jamais le temps de développement :-). De toute façon, vous pouvez peut-être éliminer un goulot d'étranglement dans votre code Perl en utilisant un autre langage, sans avoir à écrire tout le programme dans ce langage. Cela réduit votre temps de développement global, car vous utilisez Perl pour tout le code non critique.

Une autre raison est d'accéder à des fonctionnalités à partir d'API existantes qui utilisent le langage. Une partie de ce code peut ne être disponible que sous forme binaire. Mais en créant de petites sous-routines dans le langage natif, vous pouvez « coller » des bibliothèques existantes à votre Perl. En tant qu'utilisateur du CPAN, vous savez que la réutilisation du code est une bonne chose. Alors pourquoi jeter ces bibliothèques Fortran dès maintenant ?

Si vous utilisez Inline avec le langage C, alors vous pouvez accéder à tous les détails internes de Perl lui-même. Cela ouvre les vannes à la fois à un pouvoir extrême et à un danger extrême.

Peut-être que la meilleure raison est « Parce que vous le voulez ! ». La diversité rend le monde intéressant. TMTOWTDI !

Pourquoi devrais-je utiliser Inline pour le faire ?
Il existe déjà deux mécanismes majeurs pour étendre Perl avec C. Ce sont XS et SWIG. Tous deux sont similaires dans leurs capacités, du moins en ce qui concerne Perl. Et tous deux sont assez difficiles à apprendre par rapport à Inline.

Il y a une courbe d'apprentissage considérable à mettre en place et à utiliser l'environnement XS. Vous devez devenir assez intime avec les documents suivants :

  • perlxs
  • perlxstut
  • perlapi
  • perlguts
  • perlmod
  • h2xs
  • xsubpp
  • ExtUtils::MakeMaker

Avec Inline, vous pouvez être opérationnel en quelques minutes. Il existe un livre de recettes C avec de nombreux programmes courts mais complets que vous pouvez adapter à vos problèmes réels. Pas besoin d'apprendre le processus de construction compliqué qui se déroule en arrière-plan. Vous n'avez même pas besoin de compiler le code vous-même. Inline s'occupe de chaque dernier détail à l'exception de l'écriture du code C.

Les programmeurs Perl ne peuvent pas se soucier de choses idiotes comme la compilation. « Ajuster, Exécuter, Ajuster, Exécuter » est notre façon de vivre. Inline fait tout le sale travail pour vous.

Un autre avantage d'Inline est que vous pouvez l'utiliser directement dans un script. Vous pouvez même l'utiliser dans une commande Perl en une ligne. Avec XS et SWIG, vous devez toujours mettre en place un module entièrement séparé. Même si vous n'avez qu'une ou deux fonctions. Inline rend les choses faciles faciles, et les choses difficiles possibles. Tout comme Perl.

Enfin, Inline prend en charge plusieurs langages de programmation (pas seulement C et C++). Au moment de la rédaction, Inline prend en charge C, C++, Java, Python, Ruby, Tcl, Assembleur, Basic, Guile, Befunge, Octave, Awk, BC, TT (Template Toolkit), WebChat et même PERL. De nouveaux modules de prise en charge de langages Inline (ILSM) sont régulièrement ajoutés. Voir Inline-API pour savoir comment créer votre propre ILSM.

UTILISATION DU MODULE INLINE.PM

Inline est un peu différent de la plupart des modules Perl auxquels vous êtes habitué. Il n'importe aucune fonction dans votre espace de noms et il n'a aucune méthode orientée objet. Toute son interface (avec deux petites exceptions) est spécifiée à travers la commande 'use Inline ...' .

Cette section expliquera toutes les différentes façons de "use Inline". Si vous voulez commencer à utiliser C avec Inline immédiatement, voir Inline::C-Cookbook.

Les bases

La forme la plus basique pour utiliser Inline est :

use Inline X => "X source code";

où 'X' est l'un des langages de programmation Inline pris en charge. Le second paramètre identifie le code source que vous voulez lier à Perl. Le code source peut être spécifié en utilisant l'une des syntaxes suivantes :

Le mot-clé DATA.
use Inline Java => 'DATA';
# Le code Perl va ici ...
__DATA__
__Java__
/* Le code Java va ici ... */

La façon la plus simple et la plus visuellement propre de spécifier votre code source dans un programme Perl Inline est d'utiliser le mot-clé spécial "DATA" . Cela indique à Inline de chercher un marqueur spécial dans le flux d'entrée de votre poignée de fichier "DATA" . Dans cet exemple, le marqueur spécial est "__Java__", qui est le langage de programmation entouré de doubles underscores.

Au cas où vous l'auriez oublié, le pseudo-fichier "DATA" est composé de tout le texte après la section "__END__" ou "__DATA__" de votre programme. Si vous travaillez en dehors du paquet "main" , vous feriez mieux d'utiliser le marqueur "__DATA__" sinon Inline ne trouvera pas votre code.

Utiliser ce schéma garde votre code Perl en haut, et tout le vilain stuff Java en bas où il appartient. C'est visuellement propre et rend le code plus maintenable. Un excellent bénéfice secondaire est que vous n'avez pas besoin d'échapper de caractères comme vous le feriez dans une chaîne Perl. Le code source est verbatim. Pour ces raisons, je préfère cette méthode le plus.

Le seul problème avec ce style est que comme Perl ne peut pas lire la poignée de fichier "DATA" jusqu'à l'exécution, il ne peut évidemment pas lier vos fonctions qu'à l'exécution. L'effet net de cela est que vous ne pouvez pas utiliser vos fonctions Inline comme des mots nus (sans les pré-déclarer) car Perl n'a aucune idée de leur existence lors de la compilation.

Les mots-clés FILE et BELOW.
use Inline::Files;
use Inline Java => 'file';
# Le code Perl va ici ...
__JAVA__
/* Le code Java va ici ... */

C'est la méthode la plus récente pour spécifier votre code source. Elle utilise le module Perl "Inline::Files" écrit par Damian Conway. Le style et le sens de base sont les mêmes que pour le mot-clé "DATA" , mais il y a quelques subtilités syntaxiques et sémantiques.

D'abord, vous devez dire 'use Inline::Files' avant de 'use Inline' du code qui a besoin de ces fichiers. Le spécial ' "DATA" ' est remplacé soit par ' "file"' soit par ' "below"'. Cela permet l'utilisation du mauvais jeu de mots idiomatique suivant :use Inline C =>

'below';

Tous les programmeurs font des erreurs. Lorsque vous faites une erreur avec Inline, comme écrire du mauvais code C, vous obtiendrez un grand rapport d'erreur sur votre écran. Ce rapport vous indique où chercher pour faire le débogage. Certains langages peuvent également afficher les messages d'erreur générés lors de la

Lorsqu'Inline doit construire quelque chose, il crée un sous-répertoire sous

votre

"DIRECTORY/build/" répertoire. C'est là qu'il écrit tous les composants dont il a besoin pour construire votre extension. Des choses comme les fichiers XS, les Makefiles et les fichiers de journal de

sortie.

Si tout se passe bien, Inline supprimera ce sous-répertoire. S'il y a une erreur, Inline laissera le répertoire intact et affichera son emplacement. L'idée est que vous devez aller dans ce répertoire et comprendre ce qui s'est

Le fichier registre

'config'

Inline conserve un fichier en cache de toutes les métadonnées des Modules de Support de Langage Inline dans un fichier appelé "config" . Ce fichier peut être trouvé dans votre "directory" répertoire. Si le fichier n'existe pas, Inline en crée un nouveau. Il cherchera dans votre système tout module commençant par "Inline::" . Il appellera ensuite la méthode "register()" de ce module pour obtenir des informations utiles pour les invocations futures. Chaque fois que vous ajoutez un nouvel ILSM, vous devez supprimer ce fichier afin qu'Inline découvre automatiquement votre module de langage nouvellement installé. RACCOURCIS DE CONFIGURATION INLINE

Ceci est une liste de toutes les options de configuration par raccourci actuellement disponibles pour Inline. Spécifiez-les depuis la ligne de commande lorsque vous exécutez des scripts Inline.

perl -MInline=noclean inline_script.pl

ou

perl -MInline=info,force,noclean inline_script.pl

Vous pouvez spécifier plusieurs raccourcis séparés par des virgules. Ils ne sont pas sensibles à la casse. Vous pouvez aussi spécifier des raccourcis à l'intérieur du programme Inline comme ceci :

use Inline 'info', 'force', 'noclean';

NOTE : Si une instruction 'use Inline' est utilisée pour définir des raccourcis, elle ne peut pas être
utilisée à d'autres fins.

"clean"
Indique à Inline de supprimer tous les répertoires de construction qui pourraient traîner dans votre zone de construction. Normalement, ces répertoires sont supprimés immédiatement après une construction réussie. Les exceptions sont lorsque la construction échoue, ou lorsque vous utilisez les options "noclean" ou "reportbug" .
"force"
Force la recompilation du code, même si tout est à jour.
"global"
Active l'option "global_load" .
"info"
C'est une option très utile lorsque vous voulez savoir ce qui se passe sous le capot. Elle indique à Inline d'afficher des informations utiles sur "STDERR". Parmi les choses qui sont affichées se trouve une liste des fonctions Inline qui ont été correctement liées à Perl.
"noclean"
Indique à Inline de laisser les fichiers de construction après la compilation.
"noisy"
Utilise l'option "build_noisy" pour afficher des messages pendant une construction.
"reportbug"
Met Inline en mode "reportbug" , qui effectue un traitement spécial lorsque vous voulez signaler un bogue. "reportbug" force aussi automatiquement une construction et ne nettoie pas après. Cela vous permet de créer une archive tar et de l'envoyer par courriel. "reportbug" affichera des instructions exactes sur ce qu'il faut faire. Veuillez les lire et les suivre attentivement.

NOTE : "reportbug" vous informe d'utiliser la commande tar. Si votre système ne
dispose pas de tar, veuillez utiliser la commande "zip" équivalente.

"safe"
Active "safemode" . "untaint" l'activera automatiquement. Bien que ce mode effectue des vérifications de sécurité supplémentaires, il ne garantit pas la sécurité.
"site_install"
Ce paramètre servait à créer des modules Inline installables. Il a été complètement supprimé d'Inline et remplacé par un mécanisme beaucoup plus simple et plus puissant, "Inline::MakeMaker". Voir la section ci-dessous sur la façon de créer des modules avec Inline.
"_testing"
Utilisé en interne par Ct09parser.t et Ct10callback.t (dans la suite de tests d'Inline::C). Définir cette option avec Inline::C signifiera que des fichiers nommés "parser_id" et "void_test" sont créés dans le répertoire "./Inline_test" , en créant ce répertoire s'il n'existe pas déjà. "timers"
Active "build_timers" pour obtenir des informations de diagnostic supplémentaires sur les constructions.
"unsafe"
Désactive "safemode" . Utilisez ceci en combinaison avec "untaint" pour un temps de démarrage légèrement plus rapide sous "-T". N'utilisez ceci que si vous êtes sûr que l'environnement est sûr.

"version"
Indique à Inline de signaler sa version de publication.

ÉCRITURE DE MODULES AVEC INLINE

La méthode actuellement préférée pour créer des modules CPAN avec Inline est d'utiliser Inline::Module (distribué séparément). Inline est livré avec Inline::MakeMaker, qui vous aide à configurer un Makefile.PL qui invoque Inline au moment de l'installation pour compiler tout le code avant qu'il ne soit installé, mais le module résultant dépend toujours d'Inline et du module de support de langage comme Inline::C. Afin d'éviter cette dépendance, ce que vous voulez vraiment faire est de convertir votre distribution en XS simple avant de la téléverser sur CPAN. Inline::Module remplit ce rôle et s'intègre également bien avec des outils de création plus modernes.

Voir Inline::Module pour les détails sur cette approche, ou continuez à lire ci-dessous pour la technique plus ancienne d'Inline::MakeMaker.

Disons que vous vouliez écrire un module appelé "Math::Simple". Commencez par utiliser la commande suivante :

h2xs -PAXn Math::Simple

Cela générera un ensemble de fichiers qui forment le squelette de ce dont vous avez besoin pour un module distribuable. (Lisez la page de man de h2xs pour savoir ce que font les options) Ensuite, modifiez le fichier "Simple.pm" pour qu'il ressemble à ceci :

package Math::Simple;
$VERSION = '1.23';
use base 'Exporter';
@EXPORT_OK = qw(add subtract);
use strict;
use Inline C => 'DATA',
           version => '1.23',
           name => 'Math::Simple';
# L'appel Inline->init() suivant est facultatif - voir ci-dessous pour plus d'informations.
#Inline->init();
1;
__DATA__
=pod
=cut
__C__
int add(int x, int y) {
  return x + y;
}
int subtract(int x, int y) {
  return x - y;
}

Les points importants à noter ici sont que vous devez spécifier un "name" et un paramètre "version" . Le "name" doit correspondre au nom du package de votre module. Le paramètre "version" doit correspondre à la variable $VERSION de votre module et ils doivent être considérés comme valides par "version::parse".

NOTE : Ce sont les vérifications de cohérence d'Inline pour vous assurer que vous savez ce que vous faites
avant de téléverser votre code sur CPAN. Elles garantissent qu'une fois le module
installé sur le système de quelqu'un, le module ne serait pas
recompilé automatiquement pour quelque raison que ce soit. Cela fait que les modules basés sur Inline
fonctionnent exactement de la même manière que ceux basés sur XS.

Enfin, vous devez modifier le Makefile.PL. Changez simplement :

use ExtUtils::MakeMaker;

en

use Inline::MakeMaker;

Et, afin que la construction du module fonctionne correctement dans le shell cpan, ajoutez la directive suivante au WriteMakefile()du Makefile.PL :

CONFIGURE_REQUIRES  =>  {
    'Inline::MakeMaker'     => 0.45,
    'ExtUtils::MakeMaker'   => 6.52,
},

Cette directive "CONFIGURE_REQUIRES" garantit que le shell cpan installera Inline sur la machine de l'utilisateur (s'il n'est pas déjàdy présent) avant de construire votre module basé sur Inline. La spécification de "ExtUtils::MakeMaker => 6.52," est facultative et peut être omise si vous le souhaitez. Elle ne fait que s'assurer que certains avertissements inoffensifs concernant la directive "CONFIGURE_REQUIRES" ne seront pas émis lors de la construction du module. Cela signifie aussi, bien sûr, que ExtUtils::Makemaker sera d'abord mis à jour sur la machine de l'utilisateur, sauf si l'utilisateur a déjà la version 6.52 ou ultérieure.

Si le "Inline->init();" n'est pas fait, alors, une fois Math::Simple installé, un avertissement indiquant "One or more DATA sections were not processed by Inline" apparaîtra lorsque (et seulement lorsque) Math::Simple est chargé par un "require". C'est un avertissement inoffensif - et si vous êtes prêt à vivre avec, alors il n'est pas nécessaire de faire l'appel "Inline->init();".

Lorsque la personne qui installe "Math::Simple" fait un ""make"", le Makefile généré invoquera Inline de manière à ce que le code C soit compilé et que le code exécutable soit placé dans le répertoire "./blib" . Puis, lorsqu'un ""make install"" est fait, le module sera copié dans le répertoire sitelib Perl approprié (qui est l'endroit où un module installé devrait aller).

Maintenant, tout ce que vous avez à faire est :

perl Makefile.PL
make dist

Cela générera le fichier "Math-Simple-0.20.tar.gz" qui est un package distribuable. (Cela générera aussi quelques avertissements inoffensifs en relation avec "CONFIGURE_REQUIRES" sauf si la version de votre ExtUtils::MakeMaker est 6.52 ou ultérieure.) C'est tout ce qu'il y a à faire.

NOTE IMPORTANTE: Bien que les étapes ci-dessus produiront un module fonctionnel, vous avez encore quelques responsabilités en tant que nouvel auteur CPAN en herbe. Vous devez écrire beaucoup de documentation et beaucoup de tests. Jetez un œil à certains des meilleurs modules CPAN pour avoir des idées sur la création d'un excellent harnais de tests. En fait, ne m'écoutez pas, allez lire ceci :

  • perldoc perlnewmod
  • http://www.cpan.org/modules/04pause.html
  • http://www.cpan.org/modules/00modlist.long.html

COMMENT INLINE FONCTIONNE

En réalité, Inline automatise simplement tout ce que vous auriez à faire si vous le faisiez à la main (en utilisant XS, etc.).

Inline effectue les étapes suivantes :

  • Recevoir le code source

    Inline récupère le code source de votre script ou module avec des instructions comme les suivantes :

    use Inline C => "Source-Code";

    ou

    use Inline;
bind Inline C => "Source-Code";

    où "C" est le langage de programmation du code source, et "Source-Code" est une chaîne, un nom de fichier, une référence de tableau, ou le mot-clé spécial 'DATA' .

    Comme Inline est codé dans une instruction"use"", tout se fait pendant le temps de compilation de Perl. Si quelque chose doit être fait qui affectera le "Source-Code", cela doit être fait dans un bloc "BEGIN" qui est avant l'instruction ""use Inline ..."". Si vous avez vraiment besoin de spécifier du code à Inline à l'exécution, vous pouvez utiliser la méthode bind() .

    Le code source stocké dans la section 'DATA' de votre code est lu par une sous-routine "INIT" dans Inline. C'est parce que le descripteur de fichier "DATA" n'est pas disponible au moment de la compilation.

  • Vérifier si le code source a été construit

    Inline n'a besoin de construire le code source que s'il ne l'a pas encore été. Il accomplit cette tâche apparemment magique de manière extrêmement simple et directe. Il fait passer le texte source par le module "Digest::MD5" pour produire une "empreinte" de 128 bits qui est virtuellement unique. L'empreinte, avec un tas d'autres informations de contingence, est stockée dans un fichier ".inl" qui se trouve à côté de votre objet exécutable. Par exemple, le code "C" d'un script appelé "example.pl" pourrait créer ces fichiers :

    example_pl_3a9a.so
example_pl_3a9a.inl

    Si toutes les informations de contingence correspondent aux valeurs stockées dans le fichier ".inl" , alors passez à l'étape 8. (Aucune compilation n'est nécessaire)

  • Trouver un endroit pour construire et installer

    À ce stade, Inline sait qu'il doit construire le code source. La première chose à déterminer est où créer le grand désordre associé à la compilation, et où mettre l'objet une fois qu'il est terminé.

    Par défaut, Inline essaiera de construire et d'installer sous le premier endroit qui remplit l'une des conditions suivantes :

1.
L'option de configuration DIRECTORY= ; si spécifiée
2.
La variable d'environnement "PERL_INLINE_DIRECTORY" ; si définie
3.
".Inline/" (dans le répertoire courant) ; s'il existe et "$PWD != $HOME"
4.
bin.Inline (dans le répertoire de votre script) ; s'il existe
5.
"~/.Inline/" - s'il existe
6.
"./_Inline/" - s'il existe
7.
"bin/_Inline" - s'il existe
8.
Créer "./_Inline/" - si possible
9.
Créer "bin/_Inline/" - si possible

À défaut, Inline échouera. C'est rare et facilement remédiable en créant simplement un répertoire qu'Inline utilisera.

Si la variable d'environnement "PERL_INSTALL_ROOT" a été définie, vous devrez faire une disposition spéciale pour cela si la phase 'make install' de vos scripts Inline doit réussir.

Si l'option module est compilée pour une installation permanente, alors Inline n'utilisera "./_Inline/" pour construire, et le répertoire $Config{installsitearch} pour installer l'exécutable. Cette action est causée par Inline::MakeMaker, et est destinée à être utilisée dans des modules qui seront distribués sur le CPAN, afin qu'ils soient installés à l'endroit approprié.

  • Analyser la source pour des indices sémantiques

    Inline::C utilise le module "Parse::RecDescent" pour analyser vos morceaux de code source C et chercher des choses auxquelles il peut créer des liaisons d'exécution. Dans "C" il cherche toutes les définitions de fonctions et les décompose en noms et types de données. Ces éléments sont utilisés pour lier correctement la fonction "C" à une sous-routine "Perl" . D'autres langages Inline comme Python et Java utilisent en fait les modules "python" et "javac" pour analyser le code Inline.

  • Créer l'environnement de construction

    Maintenant, Inline peut prendre toutes les informations rassemblées et créer un environnement pour construire votre code source en un exécutable. Sans entrer dans tous les détails, il crée simplement les répertoires appropriés, crée les fichiers source appropriés, y compris un fichier XS (pour C) et un fichier "Makefile.PL".

  • Construire le code et installer l'exécutable

    Les planètes sont alignées. Maintenant pour la partie facile. Inline fait simplement ce que vous feriez pour installer un module. "`perl Makefile.PL && make && make test && make install>". Si quelque chose se passe mal, Inline échouera avec un message indiquant où chercher plus d'informations.

  • Nettoyer

    Par défaut, Inline supprimera tout le désordre créé par le processus de construction, en supposant que tout a fonctionné. Si la construction échoue, Inline laissera tout intact, afin que vous puissiez déboguer vos erreurs. Définir l'option raccourci "noclean" empêchera aussi Inline de nettoyer.

  • Charger dynamiquement l'exécutable

    Pour C (et C++), Inline utilise la méthode "DynaLoader::bootstrap" pour charger votre module externe dans l'espace de "Perl" . Maintenant, vous pouvez appeler toutes vos fonctions externes comme des sous-routines Perl.

    D'autres langages comme Python et Java fournissent leurs propres chargeurs.
