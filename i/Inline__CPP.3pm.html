Le module Inline::CPP vous permet de placer du code source C++ directement en l

N

"Nous devrions oublier les petites efficacités, disons 97 % du temps : l'optimisation prématurée est la racine de tous les maux. Inline::CPP concerne ce 3 %

Tom "Duff's Device" Duff a un jour écrit ce qui suit : "L'alternative à se prosterner devant le dieu de l'optimisation du code est de trouver un meilleur algorithme... ...Si votre code est trop lent, vous devez le rendre plus rapide. Si aucun meilleur algorithme n'est disponible, vous devez ga

Souvent, un Perl bien écrit est assez rapide. Mais lorsqu'on rencontre une situation où les performances ne sont pas suffisantes, et qu'aucun meilleur algorithme n'existe, se rapprocher du métal est un moyen de gagner des cycles, à condition que ce soit bien fait. Inline::CPP minimise la douleur liée à la liaison du code C++ à Perl via

Les performances peuvent aussi être évaluées en termes de besoins en mémoire. Les structures de données à la Perl sont magnifiquement simples à utiliser et assez puissantes. Mais cette beauté et cette puissance se paient au prix de la mémoire et de la vitesse. Si vous trouvez qu'il est trop coûteux en mémoire de conserver vos données dans un tableau Perl, et qu'une solution basée sur disque n'est, pour une raison quelconque, pas une option, le fardeau de la mémoire peut être allégé dans une certaine mesure en conservant les données dans un type de données

C++.

Cela ne peut aller que jusqu'à un certain point. Mais le dicton commun veut que si vous estimez qu'une quantité raisonnable de mémoire est nécessaire pour conserver une structure de données, doublez-la, puis multipliez par dix, et vous aurez une bonne idée de la quantité de mémoire dont Perl a besoin pour la conserver. Inline::CPP peut faciliter une alternative plus

légère.

"La bibliothèque standard épargne aux programmeurs la peine de réinventer la roue." -- Bjarne

Stroustrup

Inline::CPP concerne aussi le fait de ne pas réinventer la

Il existe déjà de nombreuses bibliothèques C et C++ qui fournissent une fonctionnalité bien testée, bien déboguée et bien comprise. Il n'y a souvent aucun grand avantage, à part la portabilité, à réécrire de telles bibliothèques en Perl pur. Même les réécrire en XS est fastidieux et sujette aux bogues. Inline::CPP peut être utilisé pour développer rapidement des liaisons Perl vers des bibliothèques C++

existantes.

En allégeant la charge cognitive et la corvée de boilerplate associées au XS pur, Inline::CPP peut aider le développeur à produire du code d'extension moins bugué. Choisir un compilateur

C++

Inline::CPP analyse simplement les signatures de sous-routines et de classes dans votre code C++ et crée des liaisons vers elles. Comme Inline::C, vous aurez besoin d'un compilateur approprié la première fois que vous exécutez le

script.

Si vous faites partie de la majorité chanceuse, vous accepterez les valeurs par défaut lors de l'installation d'Inline::CPP ; le compilateur C++ correct et les bibliothèques standard seront configurés pour vous. Si vous faites partie de la minorité malchanceuse (et décroissante), continuez à

lire.

Voici la règle : utilisez un compilateur C++ compatible avec le compilateur qui a construit "perl". Par exemple, si "perl" a été construit avec "gcc", utilisez "g++". Si vous êtes sur une machine Sun ou IRIX et que le compilateur C du système "cc" a construit "perl", alors utilisez le compilateur C++ du système, "CC"

.

Certains compilateurs compilent en fait à la fois C et C++ avec le même compilateur. Le "cl.exe" de Microsoft est un tel compilateur -- vous lui passez l'indicateur <-TP> pour le convaincre que vous voulez le mode C++. On espère que cela sera déduit par défaut au moment de

l'installation.

Si vous utilisez le compilateur GNU C++, assurez-vous que vous avez l'interfa

ce de commande g++ installée (certaines distributions Linux ne l'installent pas
par défaut, mais la fournissent via leurs utilitaires de gestion de paquets).

Utiliser Inline::

CPP

Inline::CPP est très similaire à Inline::C, et dans la plupart des cas peut être utilisé à la place d'Inline::C sans changer une seule ligne de Perl ou de C. Si vous ne l'avez pas déjà fait, vous devriez arrêter de lire maintenant et lire la documentation d'Inline::C, y compris le Inline::

C-Cookbook.

Ce module utilise une grammaire pour analyser votre code C++ et se lie aux fonctions ou classes qui sont reconnues. Si une fonction est reconnue, elle sera disponible depuis l'espace Perl. Si la signature de la fonction n'est pas reconnue, elle ne sera pas disponible depuis Perl, mais sera disponible depuis d'autres fonctions ou classes dans le code

C++.

L'exemple suivant montre comment des extraits C++ correspondent à Perl

:

Exemple 1

: 
use Inline CPP => <<'END';
using namespace std;
int doodle() { }
class Foo {
 public:
   Foo();
   ~Foo();
   int get_data() { return data; }
   void set_data(int a) { data = a; }
 private:
   int data;
};
Foo::Foo() { cout << "creating a Foo()" << endl; }
Foo::~Foo() { cout << "deleting a Foo()" << endl; }
END

Après avoir exécuté le code ci-dessus, votre environnement d'exécution Perl ressemblerait à ce qu'il serait si le code suivant avait été exécuté

: 
sub main::doodle { }
package main::Foo;
sub new { print "creating a Foo()\n"; bless {}, shift }
sub DESTROY { print "deleting a Foo()\n" }
sub get_data { my $o=shift; $o->{data} }
sub set_data { my $o=shift; $o->{data} = shift
}

La différence, bien sûr, est que dans le second cas, Perl fait le travail. Dans l'exemple Inline::CPP, tous les appels de fonction sont envoyés à votre code C++. Cela signifie que des choses comme celle-ci ne fonctionneront pas

:

10;

Cela ne fonctionne pas parce que $obj n'est pas un hachage béni. C'es

Phase de compilation

C++

La première fois que vous exécutez un programme qui utilise Inline::CPP, le code C++ sera compilé dans un dossier "_Inline/" ou ".Inline/" dans le répertoire de travail. La première exécution entraînera une pénalité de temps de démarrage liée à la compilation du code C++. Cependant, le cod

e compilé est mis en cache, et en supposant qu'il n'est pas modifié, les exécutio
ns suivantes ignoreront la compilation C++, et le temps de démarrage sera rapide.

Baser les distributions (CPAN) sur Inline::

CPP

Pour aller plus loin dans le concept de réutilisation de code, il est tout à fait possible d'empaqueter une distribution avec une dépendance à Inline::CPP. Lorsque l'utilisateur installe la distribution (alias, le module), le code C++ sera compilé au moment de la construction du module, et jamais plus (sauf si l'utilisateur met à niveau le module). L'utilisateur ne verra donc jamais le retard de démarrage associé à la compilation du code

C++.

Un exemple et une preuve de concept pour cette approche se trouvent dans le module CPAN Math::Prime::

FastSieve.

Cette approche implique l'utilisation de Inline::MakeMaker, et est bien documentée dans le POD d'Inline sous le titre Writing Modules with Inline http://search.cpan.org/perldoc?Inline#Writing_Modules_with_Inlin

e

Cependant, vous pourriez souhaiter supprimer complètement la dépendance à Inline::CPP du code que vous regroupez dans une distribution. Cela peut être fait en utilisant InlineX::CPP2XS, qui convertit le code généré par Inline::CPP en code Perl XS, adapté à la distribution sans la dépendance à Inline::CPP. InlineX::CPP2XS inclut un répertoire example/ qui convertit réellement Math::Prime::FastSieve en XS

pur.

Certains auteurs d'extensions choisissent d'implémenter d'abord en Inline::CPP, puis d'ajuster manuellement, puis de copier-coller le fichier XS résultant dans leur propre distribution, avec un effet similaire (et peut-être un contrôle un peu plus fin) que l'approche

CPP2XS.

Remplace le nom de la classe

C++.

Par défaut, un conflit de noms de classes C++ surviendrait en tentant d'implémenter les classes C++ "Foo::Bar::MyClass" et "Foo::Qux::MyClass" qui dépendent l'une de l'autre d'une certaine manière, car C++ voit les deux classes comme nommées uniquement "MyClass". Nous sommes incapables de résoudre ce conflit C++ en utilisant uniquement l'option de configuration "namespace", car "namespace" n'est appliqué qu'au nom du paquet Perl, pas au nom de la classe

C++.

À l'avenir, ce problème pourrait être résolu via le support d'Inline::CPP pour l'opérateur C++ natif "namespace" et/ou pour les noms de classes C++ qui contiennent le jeton de portée "::" double-deux-points

.

Pour l'instant, ce problème est résolu en utilisant l'option de configuration "classes", qui accepte soit une référence de hachage, soit une référence de code. Lorsqu'une référence de hachage est fournie, chaque clé de hachage est un nom de classe C++, et chaque valeur de hachage est un nom de classe Perl correspondant. Cette référence de hachage sert de mécanisme de mappage des noms de classes C++ vers Perl, et peut être utilisée en combinaison avec l'option de configuration "namespace" pour exercer un contrôle total sur le nommage des classes et des

paquets.

Lorsqu'une référence de code est fournie, elle doit accepter comme unique argument le nom de la classe C++, et retourner une chaîne unique contenant le nom du paquet Perl généré. Lorsqu'une référence de code est fournie pour l'option de configuration "classes", la valeur de l'option de configuration "namespace" est

ignorée.

La référence de hachage peut être considérée comme une méthode de mappage manuelle, et la référence de code comme une méthode de mappage

automatique.

Fichier d'exemple "/tmp/Foo__Bar__MyC

lass.c" :

    int a;
  public:

  private:
    int a;
  public:
    MyClass() :a(20) {}

    int other_fetch () { MyClass mybar; return mybar.fetch(); }

nous

Remplace l'espace de noms de base par

défaut.

Dans le comportement par défaut, une classe C++ "Foo" créée en invoquant Inline::CPP depuis "package Bar" entraînera que la classe C++ "Foo" sera accessible depuis Perl en tant que "Bar::Foo". Bien que ce comportement par défaut puisse être souhaitable dans certains cas, il pourrait être indésirable dans d'autres. Un exemple serait la création d'une classe "Foo" tout en invoquant Inline::CPP depuis le paquet "Foo". La classe résultante sera liée à Perl en tant que "Foo::Foo", ce qui n'est probablement pas ce qui était

voulu.

Ce comportement par défaut peut être remplacé en spécifiant une base alternative "namespace". Des exemples sont probablement la meilleure façon de l'expliquer

: 
package Foo;
use Inline CPP => config => namespace => 'Bar';
use Inline CPP => <<'EOCPP';
class Baz {
  private:
    int a;
  public:
    Baz() :a(20) {}
    int fetch () { return a; }
};
EOCPP
package main;
my $b = Bar::Baz->new();
print $b->fetch, "\n"; #
20.

Comme démontré ici, l'espace de noms dans lequel "Baz" réside peut maintenant être rendu indépendant du paquet à partir duquel Inline::CPP a été invoqué. Considérez plutôt le comportement par défaut

: 
package Foo;
use Inline CPP => <<'EOCPP';
class Foo {
  private:
    int a;
  public:
    Baz() :a(20) {}
    int fetch () { return a; }
};
EOCPP
package main;
my $b = Foo::Foo->new();
print $b->fetch, "\n"; #
20.

Il est probablement, dans ce cas, indésirable que la classe C++ "Foo" réside dans l'espace de noms Perl "Foo::Foo". Nous pouvons corriger cela en ajoutant notre propre configuration d'espace de noms

: 
package Foo;
use Inline CPP => config => namespace => q{};  # Dissocier du
# paquet appelant. use Inline CPP => <<'EOCPP'; class Baz { private: int a; public: Baz()
:a(20) {} int fetch () { return a; } }; EOCPP package main; my $b = Foo->new(); print $b->fetch, "\n"; # 20.

std_iostrea

Par défaut, Inline::CPP inclut l'en-tête iostream standard en haut de votre code. Inline::CPP essaiera de faire la sélection appropriée entre "iostream.h" (pour les compilateurs plus anciens) et "iostream" (pour les compilateurs plus récents "conformes à la norme")

Liaisons

C++-Perl

Cette section décrit comment les variables "Perl" sont mappées vers des variables "C++" et vice

versa.

Perl utilise une pile pour passer les arguments d'un sens à l'autre aux sous-routines. Lorsqu'un sub est appelé, il retire tous ses arguments de la pile ; lorsqu'il a terminé, il repousse ses valeurs de retour sur la

pile.

XS (le langage de Perl pour créer des extensions C ou C++ pour Perl) utilise des "typemaps" pour transformer des SV en types C et vice versa. Cela est fait à travers divers appels de macros XS, des conversions et l'API Perl. XS vous permet également de définir vos propres

mappages.

"Inline::CPP" utilise une approche beaucoup plus simple. Il analyse les fichiers typemap du système et ne lie qu'aux fonctions avec des types pris en charge. Vous pouvez dire à "Inline::CPP" à propos des fichiers typemap personnalisés

aussi.

Si vous avez des structures de données non triviales en C++ ou en Perl, vous devriez probablement simplement les passer en tant que SV* et faire la conversion vous-même dans votre fonction

C++.

En C++, une structure est une classe dont la portée par défaut est publique, pas privée. Inline::CPP lie aux structures en tenant compte de cela -- les méthodes get/set ne sont pas encore générées automatiquement (bien que cette fonctionnalité puisse être ajoutée à une prochaine version)

.

Si vous avez une structure C, vous pouvez utiliser Inline::Struct pour permettre à Perl un accès complet aux internes de la structure. Vous pouvez créer et modifier des structures depuis Perl, ainsi que passer des structures à des fonctions C++ et les renvoyer depuis des fonctions. Veuillez noter qu'Inline::Struct ne comprend aucune fonctionnalité C++, donc les constructeurs et les fonctions membres ne sont pas pris en charge. Voir Inline::Struct pour plus de

détails.

<iostream>, En-têtes Standard, Espaces de Noms C++, et Solutions de Portabilité

Inline::CPP inclut automatiquement <iostream> ou <iostream.h>, selon la préférence du compilateur cible. Cette distinction illustre un problème potentiel lors de l'écriture de code portable en C++. Le C++ hérité (avant la norme ANSI) utilisait des en-têtes nommés, par exemple, <iostream.h>. Comme le C++ hérité ne supportait pas les espaces de noms, ces outils standard n'étaient pas segmentés dans un espace de noms séparé.

Le C++ norme ANSI a changé cela. Les en-têtes ont été renommés sans le suffixe '.h', et les outils standard ont été placés dans l'espace de noms '"std"'. Les constructions "using namespace std" et "using std::string" ont également été ajoutées pour faciliter le travail avec les espaces de noms.

Ainsi, le code C++ pré-norme (hérité) pourrait ressembler à ceci :

#include <iostream.h>
int main() {
    cout << "Hello world.\n";
    return 0;
}

Les compilateurs C++ modernes « norme ANSI C++ » nécessiteraient un code comme celui-ci :

#include <iostream>
using namespace std;
int main() {
    cout << "Hello world.\n";
    return 0;
}

... ou ...

#include <iostream>
int main() {
    std::cout << "Hello world.\n";
    return 0;
}

... ou même ...

#include <iostream>
int main() {
    using std::cout;
    cout << "Hello world.\n";
    return 0;
}

Le premier extrait sera complètement incompatible avec le second, le troisième ou le quatrième extrait. Ce n'est pas un problème pour un développeur C++ qui connaît son compilateur cible. Mais Perl s'exécute à peu près partout. Si une portabilité similaire (y compris la compatibilité descendante) est un objectif de conception, Inline::CPP aide en fournissant deux constantes "#define" qui peuvent être vérifiées pour déterminer quel style d'en-têtes est utilisé. Les constantes sont :

__INLINE_CPP_STANDARD_HEADERS
__INLINE_CPP_NAMESPACE_STD

"__INLINE_CPP_STANDARD_HEADERS" sera défini si le compilateur cible accepte les en-têtes norme ANSI, tels que <iostream>. "__INLINE_CPP_NAMESPACE_STD" sera défini si le compilateur cible supporte les espaces de noms. En réalité, les deux sont synonymes ; le C++ norme ANSI utilise les espaces de noms, place les outils de la bibliothèque standard dans l'espace de noms "std", et invoque les en-têtes avec la convention de nommage moderne (sans suffixe '.h'). Donc, si l'un est défini, les deux devraient l'être.

Ils peuvent être utilisés comme suit :

use Inline CPP => 'DATA';
greet();
__DATA__
__CPP__
#ifdef __INLINE_CPP_STANDARD_HEADERS
#include <string>
#else
#include <string.h>
#endif
#ifdef __INLINE_CPP_NAMESPACE_STD
using namespace std;
#endif
void greet() {
    string mygreeting = "Hello world!\n";
    cout << mygreeting;
}

Vous pourriez décider que vous ne vous souciez pas de maintenir la portabilité avec les compilateurs qui vous enferment dans le C++ pré-norme -- il y a plus d'une décennie derrière nous. Mais si cela vous importe (peut-être basez-vous un module CPAN sur Inline::CPP), utilisez ces définitions de préprocesseur comme outil pour construire une solution largement portable.

Si vous le souhaitez, vous pouvez "#undef" l'une de ces définitions. Les définitions sont définies avant toute "auto_include" -- même <iostream>. Par conséquent, vous pouvez même lister "#undef __INLINE_CPP_...." dans une directive de configuration "auto_include". Je ne suis pas sûr que ce soit nécessaire, mais cela pourrait être utile pour les tests.

Indépendamment du type d'en-tête, Inline::CPP créera la définition suivante dans tout le code qu'il génère :

#define __INLINE_CPP 1

Cela peut être utile pour construire une logique de préprocesseur qui se comporte différemment sous Inline::CPP que sous un environnement non-Inline::CPP.

Exemple 3 - Les Points de Suspension Abrégés

L'un des grands avantages de Perl par rapport à C ou C++ est la capacité de passer un nombre arbitraire d'arguments à une sous-routine. Vous pouvez le faire en C, mais c'est compliqué et difficile à faire correctement. Toute cette complication est nécessaire car C ne donne pas au programmeur accès à la pile. Perl, en revanche, vous donne accès à tout.

Voici une fonction utile écrite en Perl qui est relativement lente :

sub average {
   my $average = 0;
   for (my $i=0; $i<@_; $i++) {
      $average *= $i;
      $average += $_[$i];
      $average /= $i + 1;
   }
   return $average;
}

Voici la même fonction écrite en C :

Exemple 5 - Les Elipses Revisitées (et le Surcharge ou les

Templates)

Cet exemple d'utilisation des elipses est adapté d'une discussion sur Perl Monks. Le problème était que quelqu'un voulait appeler des fonctions surchargées. Perl ne comprend pas les règles de surcharge de C++, et C++ n'a aucune idée de la manière dont Perl a l'intention d'appeler les fonctions ici. Nous écrivons donc un wrapper pour prendre le contrôle nous-mêmes

: 
use Inline CPP => 'DATA';
say multiadd( 1 );          # No dispatch; just return the value.
say multiadd( 1, 2 );       # Dispatch add( int, int ).
say multiadd( 1, 2, 3 );    # Dispatch add( int, int, int ).
say multiadd( 1, 2, 3, 4 ); # No dispatch; throw an exception.
__DATA__
__CPP__
#include <stdexcept>
// Inline::CPP won't create predictable bindings to overloaded functions.
int add ( int a, int b ) {
  return a + b;
}
int add ( int a, int b, int c ) {
  return a + b + c;
}
// But a function call with elipses can dispatch to overloaded functions since
// no Perl binding is required in reaching those functions.
int multiadd ( SV * a, ... ) {
  dXSARGS;  // Creates a variable 'items' that contains a paramater count.
  try{
    switch ( items ) {
      case 1:  return SvIV(ST(0));
      case 2:  return add( SvIV(ST(0)), SvIV(ST(1)) );
      case 3:  return add( SvIV(ST(0)), SvIV(ST(1)), SvIV(ST(2)) );
      default: throw std::runtime_error(
        "multiadd() - Too many args in function call"
      );
    }
  }
  catch ( std::runtime_error msg ) {
    croak( msg.what() );  // Perl likes croak for exceptions.
  }
}

Techniquement, l'une des versions de add() sera liée à Perl, mais son utilisation est fragile, car les règles déterminant laquelle se lie sont indéfinies. Cet exemple surmonte le problème de Perl/XS qui ne comprend pas la

surcharge en enveloppant simplement les appels aux fonctions surchargées dans une fonction
qui les comprend. Et nous utilisons les elipses pour gérer un nombre variable d'arguments. Cette même approche peut être appliquée à l'appel de code généré par template également.

Perl

Comme Inline requiert actuellement Perl 5.8.1 ou ultérieur. Puisque Inline::CPP dépend de Inline, Perl 5.8.1 est également requis pour Inline::CPP. Il est difficile d'imaginer que quelqu'un utilisant encore un

Perl antérieur à 5.8.1 veuille interfacer avec C++, mais si vous faites partie de ce camp, vous devrez rétrograder Inline et Inline::CPP vers des versions plus anciennes grâce à la magie de backpan. La versi
on 0.25 de Inline::CPP était toujours compatible avec Perl 5.005_03. Consultez le fichier Changes de la distribution Inline pour décider quelle version d'Inline est appropriée pour votre Perl antérieur à 5.8.1.

Standard

C++11

Inline::CPP est-il prêt pour le standard C++11 ? La réponse courte à cette question est « En grande partie, dans la mesure où votre compilateur est conforme au standard C++11. » Il y a deux questions à considérer. Premièrement, de quoi votre compilateur est-il capable (et comment activez-vous ces capacités), et deuxièmement, de quoi Perl a-t-il besoin de se

soucier.

Prenons la première question d'abord (parce que c'est la plus facile) : Utilisez l'option "ccflags" montrée ci-dessus pour passer le bon drapeau à votre compilateur afin d'activer les fonctionnalités C++11. La plupart de ce que votre compilateur prendra en charge, "Inline::CPP" s'en

occupera.

Vous devrez peut-être également utiliser le drapeau "cc" pour spécifier une version plus récente de le compilateur, si vous en avez plus d'un installé -- l'un qui gère C++11 et l'autre

non.

Maintenant pour la question de ce dont Perl a besoin de se soucier : Inline::CPP ne regarde pas à l'intérieur des fonctions ou des méthodes. Ce code est traité comme une boîte noire qui passe directement à votre compilateur. Donc à l'intérieur de vos fonctions et méthodes, n'hésitez pas à utiliser les fonctionnalités C++11 que vous

voulez.

Les zones critiques sont les en-têtes de fonctions, les définitions de classes et le code qui se trouve en dehors des fonctions ou des classes. Prenons les Enums par exemple

: 
enum Colors { RED, GREEN, BLUE }
;

Comment cela devrait-il se mappé vers Perl ? Il n'y a pas de réponse claire. C++11 ajoute le concept de portée aux enums

: 
enum class Colors { RED, GREEN, BLUE }
;

La manière dont cela devrait se lier à Perl devient encore plus difficile. La vérité est qu'Inline::CPP ne liera ni l'un ni l'autre à Perl. Et vous êtes probablement mieux avec cette approche que d'avoir soudainement $Colors::RED = 0; qui apparaît dans votre code Perl. Gardez cependant à l'esprit que la construction est passée directement à votre compilateur C++ compiler, donc n'hésitez pas à l'utiliser dans le code C++. Elle ne fuira simplement pas dans vos espaces de noms

Perl.

Pour le moment, l'omission la plus flagrante d'Inline::CPP concernant la syntaxe valide C++11 est la nouvelle syntaxe de « type de retour tardif ». C++11 a introduit la syntaxe légale suivante

: 
auto add ( int x, int y ) -> int { return x + y;
}

Cette omission ne sera un facteur que pour les fonctions que vous voulez lier à Perl. Si vous n'avez pas besoin que la fonction soit liée à Perl, la syntaxe est correcte ; Inline::CPP ignore simplement la fonction. Il est important de noter que les utilisations les plus courantes de cette syntaxe impliquent des templates et des lambdas. Les templates n'ont de sens pour Inline::CPP de toute façon. Et les lambdas sont toujours corrects, car ils ont lieu à l'intérieur des fonctions, donc Inline::CPP ne les voit de toute façon. Pour l'instant, n'utilisez simplement pas la syntaxe de type de retour tardif dans l' en-tête des fonctions qui doivent être liées à Perl. Cela pourrait être corrigé dans de futures révisions de la

grammaire.

Un autre problème est "constexp

r" : 
constexpr int multiply ( int x, int y ) { return x * y;
}

"constexpr" n'est pas reconnu par Inline::CPP, donc cette fonction ne sera pas liée à Perl. Je ne pense pas que les fonctions "constexpr" puissent même générer des liaisons externes, car elles sont résolues en une constante à la compilation. Elles n'ont vraiment pas de sens pour une utilisation externe (le compilateur ne peut pas savoir comment vous les appellerez). Par conséquent, elles seront ignorées par Inline::CPP (et passeront à votre compilateur, donc elles fonctionneront à l'intérieur de votre code C++)

.

Et enfin, les références

Rvalue :

Inline::CPP ne comprend pas (encore) ceci

: 
int x = 100;
int getInt ()
{
    return x;
}
int && getRvalueInt ()
{
    return std::move( x );
}

La fonction getInt() sera liée à Perl, mais la syntaxe "&&" n'est pas reconnue par Inline::CPP, et ne résultera pas en une liaison générée. Donc getRvalueInt() sera invisible pour Perl. Cependant, il est parfaitement légal de l'utiliser dans votre code C++ tant que vous n'avez pas besoin qu'il soit lié à

Perl.

À part cela (autant que je sache), vous êtes prêt à y aller ! Allez-y et utilisez la nouvelle version de "for( auto it: x ) {...}", ou même..

. 
for_each( v.begin(), v.end(), [] (int val) { std::cout << val; } )
;

La beauté d'Inline::CPP est que ce qui se passe à l'intérieur des boîtes noires des

fonctions ou des méthodes est sans rapport avec le processus de liaison. Ces exemples
« fonctionneront simplement », en supposant que votre compilateur C++ les comprend.

Voici quelques points à surveiller

:

La grammaire utilisée pour analyser le C++ est encore assez simple et ne permet pas plusieurs fonctionnalités de C++

:
Templates : Vous pouvez utiliser des bibliothèques de templatess dans votre code, mais Inline::CPP ne saura pas comment analyser et lier les définitions de templates. Le problème fondamental est que le compilateur C++ n'a aucune idée de la manière dont un langage dynamique comme Perl prévoit d'invoquer le code généré par les templates, et ne peut donc pas savoir quel code générer à partir des templates. Gardez les templates encapsulés, à l'écart de l'interface qui sera exposée à Perl, en enveloppant les appels dans des fonctions qui donneront au compilateur un type avec lequel
travailler.
Surchcharge
d'opérateurs
Surcharge de fonctions -- C'est un problème similaire à celui des templates. Perl ne connaît pas les règles de résolution des surcharges de fonctions de C++. Et C++ ne connaît pas Perl. XS n'a jamais été conçu pour gérer ce type de discordance. Cela empêche l'implémentation de la Règle des Trois pour du code destiné à être lié avec Perl, mais comme Perl gère vos liaisons, ce n'est probablement pas un
problème.
Ces trois problèmes (Templates, Surcharges d'Opérateurs et Surcharges de Fonctions) sont des situations où le langage C++ et le langage Perl ne se correspondent tout simplement pas bien. Plus vous vous habituerez à cette discordance, plus vous aurez un aperçu de ce qui fonctionnera et de ce qui ne fonctionnera pas. Les templates sont la manière dont un langage statique comme C++ gère le concept de programmation générique. Perl est un langage si dynamique que les templates (qui sont entièrement résolus à la compilation) ne peuvent pas être résolus lorsqu'ils sont appelés par Perl. Le concept de passage de paramètres de Perl est si dynamique que les signatures de fonctions (que C++ utilise pour résoudre les surcharges) ne peuvent pas non plus être mappées de manière significative. Il y aura d'autres fonctionnalités de C++ qui ne se mappent pas dans Perl, et vice versa. Pensez aux enums C++. Perl devrait-il les traiter comme des constantes en les mappant via la pragma constant ? La réponse est incertaine, et le fait est qu'ils ne seront pas du tout liés dans
Perl.
L'héritage multiple ne fonctionne pas correctement (pour l'instant)
.
Les tableaux multidimensionnels en tant que données membres ne sont pas implémentés (pour l'instant)
.
La déclaration d'un type de paramètre void n'est pas implémentée. Utilisez simplement "int myfunc();" au lieu de "int myfunc(void);". C'est du C++, pas du C. C'est bon,
vraiment.
Exceptions : Bien qu'il soit acceptable de lancer une exception avec 'throw', Perl ne saura pas comment s'en remettre, et vous obtiendrez un core-dump au lieu d'une mort à la Perl. La solution est simple, croak("Message"). Perl traitera cela comme un appel à "die". Le cinquième exemple ci-dessus démontre comment obtenir le meilleur des deux mondes : la riche gestion des exceptions de C++, et le "die" de
Perl.
L'essentiel est ceci : Attrapez vos throws. Et tout ce qui ne peut pas être géré avec élégance, re-lancez-le vers Perl en utilisant "cro
ak
".

D'autres problèmes de grammaire seront probablement découverts. C'est Perl,

C++, et XS, tous scellés dans une seule boîte de Pandore. Mais cela peu
t être amusant, ce qui est une description jamais applicable au XS brut.
