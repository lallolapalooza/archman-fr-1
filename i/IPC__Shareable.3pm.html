DESCRIPTIO

N

IPC::Shareable vous permet de lier une variable à la mémoire partagée, facilitant ainsi le partage du contenu de cette variable avec d'autres processus et scripts

Perl.

Les scalaires, les tableaux, les hachages et même les objets peuvent être liés. La variable liée peut contenir des structures de données arbitrairement complexes - y compris des références à des tableaux, des hachages de hachages,

etc.

L'association entre les variables dans des processus distincts est fournie par GLUE (alias « clé »). Il s'agit de n'importe quelle chaîne ou chaîne de caractères ou entier arbitraire qui sert d'identifiant commun pour les données à travers l'espace des processus. Ainsi, l'énoncé

: 
tie my $scalar, 'IPC::Shareable', { key => 'CHAÎNE GLUE', create => 1 }
;

...dans le programme un et

l'énoncé 
tie my $variable, 'IPC::Shareable', { key => 'CHAÎNE GLUE' }
;

...dans le programme deux créera et liera $scalar à la mémoire partagée dans le programme un et la liera à $variable dans le programme

deux.

Il n'y a pas de limite prédéfinie au nombre de processus pouvant se lier aux données ; ni de limite prédéfinie à la complexité des données sous-jacentes des variables liées. La quantité de données pouvant être partagée au sein d'une variable liée unique est limitée par la taille maximale du système pour un segment de mémoire partagée (la valeur exacte dépend du système)

.

Les structures de données liées sont toutes linéarisées (à l'aide du module Storable de Raphael Manfredi ou éventuellement JSON

) avant d'être ingurgitées dans la mémoire partagée. Lors de la récupération, le format original de la structure de données
est restauré. Les drapeaux de sémaphore peuvent être utilisés pour verrouiller les données entre des processus concurrents.

VERROUILLA

GE

IPC::Shareable fournit des méthodes pour implémenter un verrouillage consultatif au niveau de l'application des structures de données partagées. Ces méthodes sont appelées lock() et unlock(). Pour les utiliser, vous devez d'abord obtenir l'objet sous-jacent à la variable liée, soit en sauvegardant la valeur de retour de l'appel original à tie() soit en utilisant la fonction intégrée tied(

).

Pour verrouiller et ensuite déverrouiller une variable, faites ceci

: 
my $knot = tie my %hash, 'IPC::Shareable', { %options };
$knot->lock;
$hash{a} = 'foo';
$knot->
unlock;

ou de manière équivalente, si vous avez décidé de jeter la valeur de retour de tie()

: 
tie my %hash, 'IPC::Shareable', { %options };
tied(%hash)->lock;
$hash{a} = 'foo';
tied(%hash)->
unlock;

Cela placera un verrou exclusif sur les données de $scalar. Vous pouvez aussi obtenir des verrous partagés ou tenter d'obtenir un verrou sans

bloquer.

IPC::Shareable rend les constantes "LOCK_EX", "LOCK_SH", "LOCK_UN", et "LOCK_NB" exportables vers votre espace d'adressage avec les balises d'exportation ":lock", ":flock", ou ":all". Les valeurs devraient être les mêmes que les arguments d'option "flock" sta

ndard. 
if (tied(%hash)->lock(LOCK_SH|LOCK_NB)){
    print "The value is $hash{a}\n";
    tied(%hash)->unlock;
} else {
    print "Another process has an exclusive lock.\n";
}

Si aucun argument n'est fourni à "lock", la valeur par défaut est "LOCK_EX"

.

Il y a quelques pièges concernant le verrouillage et les signaux dont vous devriez prendre connaissance ; ceux-ci sont discutés dans

"NOTES".

Notez qu'en arrière-plan, nous effectuons une optimisation des verrous lors de la lecture et de l'écriture dans le stockage partagé même si les verrous consultatifs ne sont pas

utilisés.

L'utilisation des verrous consultatifs peut

accélérer les processus qui effectuent
plusieurs écritures/lectures en même temps.

N

perl(1) détruira l'objet sous-jacent à une variable liée lorsque la variable liée sort de la portée. Malheureusement pour IPC::Shareable, cela peut ne pas être souhaitable : d'autres processus peuvent encore avoir besoin d'un accès au segment de mémoire partagée

Notes

générales
o
Lorsque vous utilisez lock() pour verrouiller une variable, soyez prudent et protégez-vous contre les signaux. Dans des circonstances normales, la méthode "END" de "IPC::Shareable" déverrouille toutes les variables verrouillées lorsque le processus se termine. Cependant, si un signal non intercepté est reçu alors qu'un processus détient un verrou exclusif, "END" ne sera pas appelée et le verrou peut être maintenu même si le processus s'est terminé. Si cela vous inquiète, il vaut peut-être mieux implémenter vos propres méthodes de verrouillage.

Un avantage de l'utilisation de "flock" sur un fichier connu plutôt que du verrouillage implémenté avec des sémaphores dans "IPC::Shareable" est que lorsqu'un processus meurt, il libère automatiquement tous les verrous. Cela ne se produit avec "IPC::Shareable" que si le processus se termine

proprement.

L'alternative est de tenter de prendre en compte chaque fin de processus catastrophique possible (la gestion robuste des signaux en Perl est une source de nombreux débats, bien qu'elle fonction

ne généralement très bien) ou de vous familiariser avec les outils de votre système pour supprimer la mémoire partagée et les sémaphores. Ce problème doit être mis en balance avec les
améliorations de performance significatives que vous pouvez obtenir pour les plus grandes structures de données en utilisant le mécanisme de verrouillage implémenté dans IPC::Shareable.
o
Il existe un programme appelé "ipcs"(1/8) (et "ipcrm"(1/8)) disponible au moins sur Solaris et Linux qui pourrait être utile pour nettoyer les segments de mémoire partagée ou les ensembles de sémaphores moribonds produits par des bogues soit dans IPC::Shareable, soit dans les applications qui l'utilisent.

Exemples

: 
# Lister tous les sémaphores et segments de mémoire en usage sur le système
ipcs -a
# Lister tous les segments de mémoire et sémaphores avec l'ID de processus associé à chacun
ipcs -ap
# Lister uniquement les segments de mémoire partagée
ipcs -m
# Lister les détails d'un segment de mémoire individuel
ipcs -i 12345678
# Supprimer *tous* les sémaphores et segments de mémoire
ipcrm
-a

Cette version de IPC::Shareable ne comprend pas le format des segments de mémoire partagée créés par les versions antérieures à la 0.60. Si vous essayez de vous lier à de tels segments, vous obtiendrez une erreur. La seule solution est de supprimer les segments de mémoire partagée et de commencer avec un ensemble
neuf.

L'itération sur un hachage provoque une optimisation spéciale si vous n'avez pas obtenu de verrou (il est préférable d'obtenir un verrou de lecture (ou d'écriture) avant d'itérer sur un hachage lié à IPC::Shareable, mais nous tentons cette optimisation si vous ne le faites pas).

Pour les hachages liés, l'opération "fetch"/"thaw" est effectuée lorsque la première clé est accédée. Les accès ultérieurs aux clés et aux valeurs se font

sans accéder à la mémoire partagée. Faire une assignation au
hachage ou récupérer une autre valeur entre les accès aux
clés provoque le remplacement du hachage à partir de la
mémoire partagée. L'état de l'itérateur dans ce cas n'e
st pas défini par la documentation Perl. Caveat Emptor.
