NOM

Inline-API - Comment lier un langage de programmation à Perl en utilisant Inline.pm

SYNOPSIS

#!/usr/bin/perl
use Inline Foo;
say_it('foo');  # Utiliser Foo pour afficher "Hello, Foo"
__Foo__
foo-sub say_it {
    foo-my $foo = foo-shift;
    foo-print "Hello, $foo\n";
}

DESCRIPTION

Vous trouvez que Inline C est plutôt cool, mais ce dont vous avez vraiment besoin, c'est que Perl fonctionne avec le tout nouveau langage de programmation « Foo ». Eh bien, vous avez de la chance. "Inline.pm" prend en charge l'ajout de votre propre module de support de langage Inline (ILSM), comme "Inline::Foo".

Inline a toujours été conçu pour fonctionner avec de nombreux langages de programmation différents. Beaucoup de détails peuvent être partagés entre les implémentations, de sorte que "Inline::Java" a une interface similaire à "Inline::ASM". Tout le code commun se trouve dans "Inline.pm".

Les modules spécifiques à un langage comme "Inline::Python" sont des sous-classes de "Inline.pm". Ils peuvent hériter autant du comportement commun qu'ils le souhaitent et fournir un comportement spécifique. Cela se présente généralement sous la forme d'options de configuration et de la compilation spécifique au langage.

Le support de Inline C est probablement le meilleur modèle à copier. Depuis la version 0.30, tout le support C a été isolé dans le module "Inline::C" et la grammaire d'analyse est encore divisée en "Inline::C::grammar". Tous ces composants sont fournis avec la distribution Inline.

Ce POD vous donne tous les détails nécessaires pour implémenter un ILSM. Pour une assistance supplémentaire, contactez inline@perl.org. Voir [« VOIR AUSSI »] ci-dessous.

Nous examinerons le langage de plaisanterie Inline::Foo, qui est distribué avec Inline. C'est en fait un ILSM pleinement fonctionnel. Je l'utilise dans le banc de test d'Inline pour tester les fonctionnalités de base d'Inline. Il est très court et peut vous aider à comprendre l'API Inline.

A SQUELETTE

Pour le reste de ce tutoriel, supposons que nous écrivons un ILSM pour le langage fictif « Foo ». Nous l'appellerons « Inline::Foo ». Voici l'implémentation entière (fonctionnelle).

package Inline::Foo;
use strict;
$Inline::Foo::VERSION = '0.01';
@Inline::Foo::ISA = qw(Inline);
require Inline;
use Carp;
#===========================================================
# Enregistrer Foo comme module de support de langage Inline (ILSM)
#===========================================================
sub register {
    return {
        language => 'Foo',
        aliases => ['foo'],
        type => 'interpreted',
        suffix => 'foo',
       };
}
#===========================================================
# Messages d'erreur
#===========================================================
sub usage_config {
    my ($key) = @_;
    "'$key' n'est pas une option de configuration valide pour Inline::Foo\n";
}
sub usage_config_bar {
    "Valeur invalide pour l'option de configuration BAR de Inline::Foo";
}
#===========================================================
# Valider les options de configuration de Foo
#===========================================================
sub validate {
    my $o = shift;
    $o->{ILSM}{PATTERN} ||= 'foo-';
    $o->{ILSM}{BAR} ||= 0;
    while (@_) {
    my ($key, $value) = splice @_, 0, 2;
    if ($key eq 'PATTERN') {
        $o->{ILSM}{PATTERN} = $value;
        next;
    }
    if ($key eq 'BAR') {
        croak usage_config_bar
          unless $value =~ /^[01]$/;
        $o->{ILSM}{BAR} = $value;
        next;
    }
    croak usage_config($key);
    }
}
#===========================================================
# Analyser et compiler le code Foo
#===========================================================
sub build {
    my $o = shift;
    my $code = $o->{API}{code};
    my $pattern = $o->{ILSM}{PATTERN};
    $code =~ s/$pattern//g;
    $code =~ s/bar-//g if $o->{ILSM}{BAR};
    sleep 1;             # imiter le délai de compilation
    {
        package Foo::Tester;
        eval $code;
    }
    croak "La construction de Foo a échoué :\n$@" if $@;
    my $path = "$o->{API}{install_lib}/auto/$o->{API}{modpname}";
    my $obj = $o->{API}{location};
    $o->mkpath($path) unless -d $path;
    open FOO_OBJ, "> $obj"
      or croak "Impossible d'ouvrir $obj pour l'écriture\n$!";
    print FOO_OBJ $code;
    close \*FOO_OBJ;
}
#===========================================================
# Nécessaire uniquement pour les langages interprétés
#===========================================================
sub load {
    my $o = shift;
    my $obj = $o->{API}{location};
    open FOO_OBJ, "< $obj"
      or croak "Impossible d'ouvrir $obj pour l'écriture\n$!";
    my $code = join '', <FOO_OBJ>;
    close \*FOO_OBJ;
    eval "package $o->{API}{pkg};\n$code";
    croak "Impossible de charger le module Foo $obj :\n$@" if $@;
}
#===========================================================
# Renvoyer un petit rapport sur le code Foo.
#===========================================================
sub info {
    my $o = shift;
    my $text = <<'END';
Ceci est un petit rapport sur le code Foo. Peut-être qu'il contient
des informations sur les fonctions trouvées par l'analyseur qui seront
liées à Perl. Il sera inclus dans le texte produit par la
commande 'INFO' d'Inline.
END
    return $text;
}
1;

À l'exception de load(), les sous-routines de ce code sont obligatoires pour un ILSM. Leur fonctionnement est décrit ci-dessous. Quelques points à noter :

  • « Inline::Foo » doit être une sous-classe de Inline. Cela est accompli avec : 
    @Inline::Foo::ISA = qw(Inline);
  • La ligne '"require Inline;"' n'est pas nécessaire. Mais elle est là pour vous rappeler de ne pas écrire '"use Inline;"'. Cela ne fonctionnera pas.
  • Rappelez-vous, il n'est pas valide pour un utilisateur d'écrire : 
    use Inline::Foo;

    « Inline.pm » détectera cet usage pour vous dans sa méthode « import » , qui est automatiquement héritée puisque « Inline::Foo » est une sous-classe.

  • Dans la fonction build, vous devez normalement analyser votre code source. Inline::C utilise Parse::RecDescent pour le faire. Inline::Foo utilise simplement eval. (Après avoir supprimé toutes les occurrences de 'foo-').

    Une méthode d'analyse alternative qui fonctionne bien pour de nombreux ILSM (comme Java et Python) consiste à utiliser le compilateur du langage lui-même pour analyser le code pour vous. Cela fonctionne tant que le compilateur peut être amené à renvoyer les informations d'analyse.

L'API INLINE

Cette section est une spécification plus formelle des fonctionnalités que vous devrez fournir pour implémenter un ILSM.

Lorsqu'Inline détermine que du code « Foo » doit être compilé, il chargera automatiquement votre module ILSM. Il appellera alors diverses sous-routines que vous devez fournir. Nous appellerons ces sous-routines « callbacks ».

Vous devrez fournir les 5 sous-routines de rappel suivantes.

Le register() Callback

Cette sous-routine ne reçoit aucun argument. Elle renvoie une référence vers un hash de métadonnées de l'ILSM. Inline appelle cette routine uniquement lorsqu'il essaie de détecter de nouveaux ILSM qui ont été installés sur un système donné. Voici un exemple de la référence de hash que vous renverriez pour Foo :

{
    language => 'Foo',
    aliases => ['foo'],
    type => 'interpreted',
    suffix => 'foo',
};

Les éléments de métadonnées ont les significations suivantes :

language
C'est le nom propre du langage. Il est généralement implémenté comme « Inline::X » pour un langage donné 'X'.
aliases
C'est une référence vers un tableau d'alias de noms de langage. Le nom propre d'un langage ne peut contenir que des caractères de mot. A-Za-z0-9_ Un alias peut contenir n'importe quels caractères sauf les espaces et les guillemets. C'est utile pour des noms comme 'C++' et 'C#'.
type
Doit être défini sur 'compiled' ou 'interpreted'. Indique la catégorie du langage.
suffix
C'est l'extension de fichier pour l'objet en cache qui seraéé. Pour les langages « compilés », ce sera probablement 'so' ou 'dll'. La valeur appropriée se trouve dans "Config.pm".

Pour les langages interprétés, cette valeur peut être ce que vous voulez. Python utilise "pydat". Foo utilise "foo".

Le validate() Callback

Cette routine reçoit toutes les options de configuration qui n'ont pas déjà été traitées par le module Inline de base. Les options sont passées sous forme de paires clé/valeur. Il vous appartient de valider chaque option et de stocker sa valeur dans l'objet Inline (qui est également passé). Si une option particulière est invalide, vous devez provoquer une erreur (croak) avec un message d'erreur approprié.

Notez que tous les mots-clés reçus par cette routine seront convertis en majuscules par "Inline", quelle que soit la casse fournie par le programme.

Le build() Callback

Cette sous-routine est responsable de l'analyse et de la compilation du code source Foo. L'objet Inline est passé comme unique argument. Toutes les informations pertinentes seront stockées dans cet objet. build() est requis pour créer un objet de cache d'un nom spécifique, ou pour provoquer une erreur avec un message approprié.

C'est le cœur de votre ILSM. Comme cela sera probablement assez compliqué, il est probablement préférable que vous étudiiez un ILSM existant tel que "Inline::C".

Le load() Callback

Cette méthode n'a besoin d'être fournie que pour les langages interprétés. Sa responsabilité est de démarrer l'interpréteur.

Pour les langages compilés, la routine de chargement de "Inline.pm" est appelée, laquelle utilise "DynaLoader" pour charger l'objet partagé ou le DLL.

Le info() Callback

Cette méthode est appelée lorsque l'utilisateur utilise le "INFO" raccourci. Vous devez retourner une chaîne contenant un petit rapport sur le code Inliné.

L'OBJET INLINE

"Inline.pm" crée un objet Perl basé sur un hash pour chaque section de code source Inliné qu'il reçoit. Cet objet contient beaucoup d'informations sur le code, l'environnement et les options de configuration utilisées.

Cet objet est un hash qui est divisé en plusieurs sous-hashes. Les seuls deux sous-hashes qu'un ILSM devrait utiliser du tout sont $o->{API} et $o->{ILSM}. Le premier contient toutes les informations qu'Inline a rassemblées pour vous afin que vous puissiez créer/charger un objet en cache de votre conception. Le second est un dépôt où votre ILSM peut librement stocker des données dont il pourrait avoir besoin plus tard.

Cette section décrira tous les attributs de l'objet Inline "API".

L'attribut code
C'est le code source réel fourni par l'utilisateur. Il est stocké sous la forme d'une longue chaîne.
L'attribut language
Le nom propre du langage utilisé.
L'attribut language_id
Le nom du langage spécifié par l'utilisateur. Cela pourrait être 'C++' au lieu de 'CPP'.
L'attribut module
C'est le nom de fichier de l'objet partagé.
L'attribut modfname
C'est le nom de fichier de l'objet partagé.
L'attribut modpname
C'est l'extension du chemin d'installation de l'objet partagé.
L'attribut version
La version de "Inline.pm" utilisée.
L'attribut pkg
Le paquet Perl à partir duquel cet appel de Inline a été effectué.
L'attribut install_lib
C'est le répertoire dans lequel écrire l'objet partagé.
L'attribut build_dir
C'est le répertoire sous lequel vous devriez écrire tous vos fichiers liés à la construction.
L'attribut script
C'est le nom du script qui a invoqué Inline.
L'attribut location
C'est le chemin complet de l'objet exécutable en question.
L'attribut suffix
C'est le nom de l'extension de la bibliothèque partagée. (Généralement 'so' ou 'dll').

La méthode derive_minus_I

Les ILSM peuvent avoir besoin d'exécuter des sous-processus Perl avec un environnement similaire à l'actuel - en particulier @INC. Cette méthode peut être appelée pour retourner une liste de chemins absolus à passer à un interpréteur Perl pour recréer cet environnement. Vous devrez préfixer "-I" à chacun d'eux. Cette méthode omet de cette liste tout chemin qui apparaît dans $ENV{PERL5LIB} ou les bibliothèques par défaut de Perl, car ceux-ci seront déjà disponibles.

L'ESPACE DE NOMS INLINE

"Inline.pm" a été conçu de sorte que n'importe qui puisse écrire ses propres modules de support de langage. Il permet en outre à n'importe qui d'écrire une implémentation différente d'un langage Inline existant, comme C par exemple. Vous pouvez distribuer ce module sur le CPAN.

Si vous avez des projets d'implémenter et de distribuer un module Inline, je vous demanderais de travailler avec la communauté Inline. Nous pouvons être joints via la liste de diffusion Inline : inline@perl.org (Envoyez un courriel à inline-subscribe@perl.org pour vous abonner). Vous devriez y trouver les conseils et l'assistance nécessaires pour faire de votre module un succès.

La communauté Inline décidera si votre implémentation de COBOL sera distribuée comme le "Inline::COBOL" officiel ou devrait utiliser un espace de noms alternatif. En cas de litige, moi (Ingy döt Net) garde l'autorité finale. (et j'espère ne pas avoir à m'en servir :-) En fait modules@perl.org garde l' autorité finale.

Mais même si vous voulez travailler seul, vous êtes libre et le bienvenu pour écrire et distribuer des modules de support de langage Inline sur le CPAN. Vous devrez simplement les distribuer sous un nom de paquet différent.
