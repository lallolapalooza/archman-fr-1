DESCRIPTIO

N

Le module "Inline::Java" permet de placer du code source Java directement "en ligne" dans un script ou un module Perl. Un compilateur Java est lancé et le code Java est compilé. Ensuite, Perl interroge les classes Java pour savoir quelles méthodes publiques ont été définies. Ces classes et méthodes sont disponibles pour le programme Perl comme si elles avaient été écrites en

Perl.

Le processus d'interrogation des classes Java pour les méthodes publiques

se produit la première fois que vous exécutez votre code Java. L'espace de nom
s est mis en cache et les appels ultérieurs utilisent la version en cache.

UTILISATION DU MODULE Inline::

"Inline::Java" est guidé par fondamentalement la même idée que les autres modules de langage "Inline", comme "Inline::C" ou "Inline::CPP". Comme Java est à la fois compilé et interprété, la méthode pour obtenir votre code est différente, mais globalement, utiliser "Inline::Java" est très similaire à n'importe quel autre module de langage

Cette section expliquera les différentes façons de "use" Inline::Java. Pour plus de détails sur "Inline", voir 'perldoc

CLASSES ET

OBJETS

Étant donné que Java est orienté objet, toute interface entre Perl et Java doit prendre en charge les classes Java de manière

adéquate.

Exemple

: 
use Inline Java => <<'END' ;
   class Pod_1 {
      String data = "data" ;
      static String sdata = "static data" ;
      public Pod_1(){
      }
      public String get_data(){
         return data ;
      }
      public static String get_static_data(){
         return sdata ;
      }
      public void set_data(String d){
         data = d ;
      }
      private void priv(){
      }
   }
END
my $obj = new Pod_1 ;
print($obj->get_data() . "\n") ; # affiche data
$obj->set_data("new data") ;
print($obj->get_data() . "\n") ; # affiche new
data

"Inline::Java" a créé un nouveau espace de noms appelé "main::Pod_1" et a créé les fonctions suivantes

: 
sub main::Pod_::new { ... }
sub main::Pod_::Pod_1 { ... }
sub main::Pod_::get_data { ... }
sub main::Pod_::get_sdata { ... }
sub main::Pod_::set_data { ... }
sub main::Pod_::DESTROY { ...
}

Notez que seules les méthodes publiques sont exportées vers

Perl.

Les classes internes sont également prises en charge, vous devez simplement fournir une référence à un objet de classe externe en tant que premier paramètre du constructeur

EXCEPTION

S

Vous pouvez maintenant (depuis la version 0.31) attraper des exceptions en tant qu'objets lorsqu'elles sont levées depuis Java. Pour ce faire, vous utilisez les outils d'exception Perl habituels : eval et $@. Une fonction d'aide nommée 'caught' est fournie pour aider à déterminer le type de l'exception. Voici un exemple d'utilisation typique

: 
use Inline Java => <<'END' ;
   import java.util.* ;
   class Pod_9 {
      public Pod_9(boolean t) throws Exception {
         if (t){
            throw new Exception("ouch!") ;
         }
      }
   }
END
use Inline::Java qw(caught) ;
eval {
        my $obj = new Pod_9(1) ;
} ;
if ($@){
   if (caught("java.lang.Exception")){
      my $msg = $@->getMessage() ;
      print($msg . "\n") ; # affiche ouch!
   }
   else{
      # Ce n'était pas une exception Java après tous...
      die $@ ;
   }
}

Ce qu'il faut comprendre, c'est que $@ contient en fait une référence à l'objet Throwable qui a été lancé par Java. La fonction getMessage() est en réalité une méthode de la classe java.lang.Exception. Donc, si Java lance une exception personnalisée que vous avez dans votre code, vous aurez accès aux méthodes publiques de cet objet d'exception comme pour tout autre objet Java dans "Inline::Java". Note : "Inline::Java" utilise eval en arrière-plan, il est donc recommandé de stocker toute exception dans une variable temporaire avant de la traiter, surtout si vous allez appeler d'autres fonctions "Inline::Java". Il est également probablement une bonne idée de faire un undef sur $@ une fois que vous avez traité une exception Java, sinon l'objet conserve une référence jusqu'à ce que $@ soit réinitialisé par le prochain eval.

FILEHANDLES

Les descripteurs de fichiers Java (objets java.io.Reader, java.io.Writer, java.io.InputStream ou java.io.OutputStream) peuvent être encapsulés par la classe "Inline::Java::Handle" pour permettre la lecture ou l'écriture depuis Perl. Voici un exemple :

use Inline Java => <<'END' ;
   import java.io.* ;
   class Pod_91 {
      public static Reader getReader(String file) throws FileNotFoundException {
        return new FileReader(file) ;
      }
   }
END
 my $o = Pod_91->getReader('t/t13.txt') ;
 my $h = Inline::Java::Handle->new($o) ;
 # lire une ligne
 my $text = <$h>;
 chomp $text;
 print($text . "\n") ; # affiche 1

Ce qu'il faut comprendre, c'est que l'objet "Inline::Java::Handle" retourné contient en fait une référence au lecteur ou à l'écrivain Java. Il est probablement une bonne idée de le faire un undef une fois que vous avez terminé les opérations d'E/S afin que l'objet Java sous-jacent puisse être libéré.

ÉTUDE

Depuis la version 0.21, "Inline::Java" peut apprendre sur d'autres classes Java et les utiliser comme le code Java que vous écrivez dans votre script Perl. En fait, vous n'êtes même plus obligé d'écrire du code Java dans votre script Perl. Voici comment utiliser la fonction 'studying' :

use Inline (
   Java => 'study',
   study => ['java.util.HashMap'],
   autostudy => 1,
) ;
my $hm = new java::util::HashMap() ;
$hm->put("key", "value") ;
my $val = $hm->get("key") ;
print($val . "\n") ; # affiche value

Si vous ne souhaitez pas inclure de code Java dans votre script Perl, vous devez utiliser la chaîne 'study' comme code. Cela ignorera la section de compilation.

Vous pouvez également utiliser l'option autostudy pour indiquer à "Inline::Java" que vous souhaitez étudier toutes les classes qu'il rencontre :

use Inline Java => <<'END', autostudy => 1 ;
   import java.util.* ;
   class Pod_10 {
      public Pod_10(){
      }
      public HashMap get_hm(){
         HashMap hm = new HashMap() ;
         return hm ;
      }
   }
END
my $obj = new Pod_10() ;
my $hm = $obj->get_hm() ;
$hm->put("key", "value") ;
my $val = $hm->get("key") ;
print($val . "\n") ; # affiche value

Dans ce cas, "Inline::Java" intercepte la valeur de retour de la méthode get_hm(), constate qu'il s'agit d'un type qu'il ne connaît pas (java.lang.HashMap), et étudie immédiatement la classe. Après cet appel, la classe java.lang.HashMap est disponible pour être utilisée via Perl.

Dans certains cas, vous ne saurez peut-être pas quelles classes étudier avant l'exécution. Dans ces cas, vous pouvez utiliser la fonction study_classes() :

use Inline (
   Java => 'study',
   study => [],
) ;
use Inline::Java qw(study_classes) ;
study_classes(['java.util.HashMap'], undef) ;
my $hm = new java::util::HashMap() ;
$hm->put("key", "value") ;
my $val = $hm->get("key") ;
print($val . "\n") ; # affiche value

La fonction study_classes() prend 2 arguments, une référence à un tableau de noms de classes (comme l'option de configuration STUDY) et le nom du paquet dans lequel lier ces classes. Si le nom du paquet est indéfini, les classes seront liées au paquet actuel (appelant).

Note : Vous ne pouvez spécifier que les noms de paquets dans lesquels vous avez précédemment utilisé "Inline::Java".

CASTING DE TYPES

Parfois, vous devez manipuler un objet Java en utilisant un sous-type spécifique. C'est là que le casting de types est nécessaire. Voici un exemple :

use Inline (
   Java => 'study',
   study => ['java.util.HashMap'],
   autostudy => 1,
) ;
use Inline::Java qw(cast) ;
my $hm = new java::util::HashMap() ;
$hm->put('key', 'value') ;
my $entries = $hm->entrySet()->toArray() ;
foreach my $e (@{$entries}){
  # print($e->getKey() . "\n") ; # Non !
  print(cast('java.util.Map$Entry', $e)->getKey() . "\n") ; # affiche key
}

Dans ce cas, "Inline::Java" sait que $e est de type java.util.HashMap$Entry. Le problème est que ce type n'est pas public, et donc nous ne pouvons pas accéder à l'objet via ce type. Nous devons le caster en java.util.Map$Entry, qui est une interface publique et nous permettra d'accéder à la méthode getKey().

Vous pouvez également utiliser le casting de types pour forcer la sélection d'une signature de méthode spécifique pour les méthodes qui ont plusieurs signatures. Voir des exemples similaires dans la section "COERCION DE TYPES" ci-dessous.

COERCION DE TYPES

La coercion de types est l'équivalent du casting pour les types primitifs et les tableaux. Elle est utilisée pour forcer la sélection d'une signature de méthode spécifique lorsque "Inline::Java" a plusieurs choix. La fonction coerce retourne un objet spécial qui ne peut être utilisé que lors de l'appel de méthodes Java ou de l'assignation de membres Java. Voici un exemple :

use Inline Java => <<'END' ;
   class Pod_101 {
      public Pod_101(){
      }
      public String f(int i){
         return "int" ;
      }
      public String f(char c){
         return "char" ;
      }
   }
END
my $obj = new Pod_101() ;
print($obj->f('5') . "\n") ; # affiche int

Dans ce cas, "Inline::Java" appellera f(int i), car '5' est un entier. Mais '5' est également un char valide. Pour forcer l'appel de f(char c), faites ceci :

use Inline::Java qw(coerce) ;
$obj->f(coerce('char', '5')) ;
# ou
$obj->f(Inline::Java::coerce('char', '5')) ;

La fonction coerce force la sélection de la signature correspondante. Notez que la coercion doit correspondre exactement au type de l'argument. Coercer vers une classe qui étend le type de l'argument ne fonctionnera pas.

Un autre cas où la coercion de types est nécessaire est lorsque l'on veut passer un tableau comme java.lang.Object :

use Inline Java => <<'END';
   class Pod_8 {
      public Object o ;
      int a[] = {1, 2, 3} ;
      public Pod_8() {
      }
   }
END
my $obj = new Pod_8() ;
$obj->{o} = [1, 2, 3] ;      # Non !

La raison pour laquelle cela ne fonctionnera pas est simple. Lorsque "Inline::Java" voit un tableau, il vérifie le type Java auquel vous essayez de le faire correspondre pour valider la construction de votre liste Perl. Mais dans ce cas, il ne peut pas valider le tableau car vous l'assignez à un Object. Vous devez utiliser la version à trois paramètres de la fonction coerce pour ce faire :

$obj->{o} = Inline::Java::coerce(
  "java.lang.Object",
  [1, 2, 3],
  "[Ljava.lang.String;") ;

Cela indique à "Inline::Java" de valider votre liste Perl comme étant un String [], puis de le coercer en Object.

Voici comment construire les représentations de types de tableaux :

[<type>  -> tableau 1D de <type>
[[<type> -> tableau 2D de <type>
...
où <type> est l'un des suivants :
  B byte     S short     I int     J long
  F float    D double    C char    Z boolean
  L<class>; tableau d'objets <class>

Ceci est décrit plus en détail dans la plupart des livres Java traitant de la réflexion.

Mais vous n'avez besoin de le faire que si vous avez une liste Perl. Si vous avez déjà une référence de tableau Java obtenue ailleurs, vous n'avez même pas besoin de coercer :

$obj->{o} = $obj->{a} ;

MODES JNI VS CLIENT/SERVEUR

À partir de la version 0.20, il est possible d'utiliser l'extension JNI (Java Native Interface). Cela permet à "Inline::Java" de charger la machine virtuelle Java comme un objet partagé au lieu de l'exécuter comme un serveur autonome. Cela améliore les performances.

Si vous avez construit l'extension JNI, vous devez l'activer explicitement en faisant l'une des choses suivantes :

1.
Définir l'option de configuration JNI à 1
2.
Définir la variable d'environnement PERL_INLINE_JAVA_JNI à 1

Note : "Inline::Java" ne crée qu'une seule instance de machine virtuelle. Par conséquent, vous ne pouvez pas utiliser JNI pour certaines sections et client/serveur pour d'autres. La première section détermine le mode d'exécution.

Voir README.JNI pour plus d'informations sur l'extension JNI.

JVM PARTAGÉE

Depuis la version 0.30, la JVM "Inline::Java" peut maintenant être partagée entre plusieurs processus. Le premier processus à démarrer crée la JVM mais ne l'arrête pas à la sortie. Tous les autres processus peuvent alors se connecter à la JVM si nécessaire. Si certains de ces autres processus ont été créés en forquant le processus parent, la fonction Inline::Java->reconnect_JVM() doit être appelée dans l'enfant pour obtenir une nouvelle connexion à la JVM. Par ex :

use Inline (
   Java => <<'END',
      class Pod_11 {
         public static int i = 0 ;
         public Pod_11(){
            i++ ;
         }
      }
END
   shared_jvm => 1,
) ;
my $nb = 5 ;
for (my $i = 0 ; $i < $nb ; $i++){
   if (! fork()){
      Inline::Java::reconnect_JVM() ;
      my $f = new Pod_11() ;
      exit ;
   }
}
sleep(5) ;
my $f = new Pod_11() ;
print($f->{i} . "\n") ; # affiche 6

Une fois ce code exécuté, chacun des 6 processus aura créé une instance différente de la classe 't'. Les données peuvent être

partagé entre les processus en utilisant des membres statiques dans le code

Java.

Note : Le flux Java

System.out est fermé
en mode SHARED_JVM.

UTILISATION DE Inline::Java DANS UN

CGI

Si vous souhaitez utiliser "Inline::Java" dans un script CGI, procédez comme suit

: 
use CGI ;
use Inline (
   Java => <<'END',
      class Pod_counter {
         public static int cnt = 0 ;
         public Pod_counter(){
            cnt++ ;
         }
      }
END
   shared_jvm => 1,
   directory => '/somewhere/your/web/server/can/write',
) ;
my $c = new Pod_counter() ;
my $q = new CGI() ;
print
   $q->start_html() .
   "This page has been accessed " . $c->{cnt} . " times." .
   $q->end_html()
;

Dans ce scénario, le premier CGI à s'exécuter démarrera la JVM, mais ne l'arrêtera pas à la sortie. Les CGI suivants, puisqu'ils ont l'option shared_jvm activée, essaieront de se connecter à la JVM déjà existante avant d'en démarrer une nouvelle. Par conséquent, si la JVM venait à planter ou est tuée, le prochain CGI qui s'exécutera en démarrera une nouvelle. La JVM sera tuée lorsque Apache sera

arrêté.

Consultez la section BUGS AND DEFICIENCIES

si vous rencontrez des problèmes pour
démarrer le serveur shared_jvm dans un CGI.

Préchargement et PerlChildInitHandle

r

Si vous chargez "Inline::Java" lors du démarrage de votre serveur (pratique courante pour augmenter la mémoire partagée et réduire le temps d'exécution) et que vous utilisez "shared_jvm", alors tous vos processus Apache partageront la même connexion socktd à cette JVM. Cela entraînera une communication brouillée et des erreurs étranges (comme "Can't receive packet from JVM", "Broken pipe", etc)

.

Pour corriger cela, vous devez indiquer à Apache qu'après que chaque processus enfant a été forké, ils doivent chacun créer leurs propres connexions à la JVM. Cela se fait pendant l'étape "ChildInit"

.

Pour Apache 1.3.x, cela pourrait ressembler à

: 
# in httpd.conf
PerlChildInitHandler MyProject::
JavaReconnect

Et "MyProject::JavaReconnect" pourrait être aussi simple que ceci

: 
package MyProject::Jav
aReconnect; sub handl
er($$) { Inline::Java
::reconnect_JVM() } 1;

Lorsque vous signalez un bug, veuillez faire ce qui suit

: 
- Placez "use Inline REPORTBUG;" en haut de votre code, ou
  utilisez l'option de ligne de commande "perl -MInline=REPORTBUG ...".
- Exécutez votre code.
- Suivez les instructions
imprimées.

Voici quelques points à surveiller

:
1
.
Vous ne devriez nommer aucune de vos classes 'B', 'S', 'I', 'J', 'F', 'D', 'C', 'Z' ou 'L'. Ces classes semblent être utilisées en interne par Java pour représenter les types
primitifs.
2
.
Si vous mettez à niveau "Inline::Java" depuis une version précédente, assurez-vous de supprimer votre répertoire _Inline afin que les propres classes Java de "Inline::Java" soient reconstruites pour correspondre au code
Perl.
3
.
Dans certains environnements, c'est-à-dire CGI ou mod_perl, la JVM ne peut pas démarrer correctement en raison de la manière dont ces environnements configurent STDIN et STDOUT. Dans ces cas, vous souhaiterez peut-être contrôler la JVM (en mode partagé) manuellement en utilisant les commandes suivantes : 
% perl -MInline::Java::Server=status
% perl -MInline::Java::Server=start
% perl -MInline::Java::Server=stop
% perl -MInline::Java::
Server=restart

Vous pouvez spécifier les options de "Inline::Java" en définissant les variables d'environnement appropriées, et vous pouvez également définir le répertoire _Inline en utilisant la variable d'environnement PERL_INLINE_JAVA_DIREC

TORY.

De plus, vous souhaiterez peut-être également définir l'option start_jvm

à 0 dans vos scripts pour les empêcher d'essayer de démarrer leur
propre JVM si ils n'en trouvent pas, causant ainsi des problèmes.
4
.
En raison de problèmes avec les modules dont "Inline::Java" dépend, l'utilisation de chemins contenant des espaces n'est pas entièrement prise en charge sur toutes les plateformes. Cela s'applique au répertoire d'installation ainsi qu'au chemin pour J2SDK et les éléments
CLASSPATH.
5
.
Même s'il est exécuté régulièrement via un profileur, "Inline::Java" est relativemen
t lent com
paré au Perl ou
au Java natif.
