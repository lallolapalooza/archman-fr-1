IPC__Open3.3perl

IPC::Open3(3perl) Guide du programmeur Perl IPC::Open3(3perl)

NOM

IPC::Open3 - ouvrir un processus pour lecture, écriture et gestion des erreurs en utilisant open3()

SYNTAXE

use Symbol 'gensym'; # vivifier un handle séparé pour STDERR
my $pid = open3(my $chld_in, my $chld_out, my $chld_err = gensym,
                'some', 'cmd', 'and', 'args');
# ou passer la commande via le shell
my $pid = open3(my $chld_in, my $chld_out, my $chld_err = gensym,
                'some cmd and args');
# lire depuis STDIN du parent
# envoyer STDOUT et STDERR vers un handle déjà ouvert
open my $outfile, '>>', 'output.txt' or die "open failed: $!";
my $pid = open3(['&', *STDIN], ['&', $outfile], undef,
                'some', 'cmd', 'and', 'args');
# écrire vers STDOUT et STDERR du parent
my $pid = open3(my $chld_in, ['&', *STDOUT], ['&', *STDERR],
                'some', 'cmd', 'and', 'args');
# récolter le zombie et récupérer le statut de sortie
waitpid( $pid, 0 );
my $child_exit_status = $? >> 8;

DESCRIPTION

Extrêmement similaire à "open2" de IPC::Open2, "open3" lance la commande donnée et fournit des filehandles pour interagir avec les flux d'E/S standard de la commande.

my $pid = open3($chld_in, $chld_out, $chld_err, @command_and_args);

Il connecte $chld_in pour écrire dans l'entrée standard de l'enfant, $chld_out pour lire depuis la sortie standard de l'enfant, et $chld_err pour lire depuis le flux d'erreur standard de l'enfant. Si $chld_err est faux, ou est le même descripteur de fichier que $chld_out, alors "STDOUT" et "STDERR" de l'enfant sont sur le même filehandle. Cela signifie que vous ne pouvez pas passer une variable non initialisée pour $chld_err et laisser "open3" générer automatiquement un filehandle pour vous, mais gensym de Symbol peut être utilisé pour vivifier une nouvelle référence de glob ; voir "SYNTAXE". Le handle $chld_in aura l'autoflush activé.

Par défaut, les filehandles que vous passez sont utilisés comme paramètres de sortie. "open3" crée en interne trois pipes. L'extrémité d'écriture du premier pipe et les extrémités de lecture des autres pipes sont connectées à l'entrée standard/sortie/erreur de la commande, respectivement. Les extrémités de lecture et d'écriture correspondantes sont placées dans les trois premiers arguments de "open3".

Les arguments de filehandle peuvent prendre les formes suivantes :

  • Une variable non initialisée (techniquement, soit "undef", soit une chaîne vide fonctionneront) : "open3" génère un nouveau filehandle et l'assigne à l'argument, qui doit être une variable modifiable pour que cela fonctionne (sinon une exception sera levée).

    Cela ne fonctionne cependant pas pour $chld_err : si l'argument $chld_err est une valeur fausse, le flux d'erreur de l'enfant est automatiquement redirigé vers sa sortie standard.

  • Un handle existant sous la forme d'un typeglob comme *STDIN ou *FOO ou une référence à celui-ci : "open3" place le filehandle dans le slot "IO" du typeglob, ce qui signifie que le filehandle bareword correspondant (comme "STDIN" ou "FOO") peut être utilisé pour l'E/S depuis/vers le processus enfant. (Si le handle est déjà ouvert, il est automatiquement fermé au préalable.)
  • Une chaîne contenant le nom d'un handle bareword (comme 'STDIN' ou 'FOO') : ces chaînes sont résolues en typeglobs à l'exécution et agissent alors comme dans le cas décrit ci-dessus.

Cependant, il est possible de faire utiliser un handle existant directement par "open3" (comme argument d'entrée) et d'éviter la création d'un pipe. Pour ce faire, l'argument filehandle doit avoir l'une des deux formes suivantes :

  • Une référence de tableau comme "['&', $fh]", c'est-à-dire que le premier élément est la chaîne '&' et le second élément est le handle existant à utiliser dans le processus enfant.
  • Une chaîne de la forme '<&FOO' ou '>&FOO', c'est-à-dire une chaîne commençant par les deux caractères "<&" (pour l'entrée) ou ">&" (pour la sortie), suivis du nom d'un filehandle bareword. (La forme chaîne ne peut pas être utilisée avec des handles stockés dans des variables.)

Si vous utilisez cette forme pour $chld_in, le filehandle sera fermé dans le processus parent.

Les filehandles peuvent aussi être des entiers, auquel cas ils sont compris comme des descripteurs de fichiers.

"open3" retourne l'ID du processus enfant. Il ne retourne pas en cas d'échec : il lève simplement une exception correspondant à "/^open3:/". Cependant, les échecs d'"exec" dans l'enfant (comme fichier inexistant ou permission refusée) sont simplement rapportés à $chld_err sous Windows et OS/2, car il n'est pas possible de les intercepter.

Si le processus enfant meurt pour une raison quelconque, la prochaine écriture dans $chld_in est susceptible de générer un SIGPIPE dans le parent, ce qui est mortel par défaut. Vous pourriez donc souhaiter gérer ce signal.

Note : si vous spécifiez "-" comme commande, de manière analogue à "open(my $fh, "-|")", le processus enfant sera simplement le processus Perl bifurqué plutôt qu'une commande externe. Cette fonctionnalité n'est pas encore supportée sur les plateformes Win32.

"open3" n'attend pas et ne récolte pas le processus enfant après sa sortie. Sauf pour les programmes courts où il est acceptable de laisser le système d'exploitation s'en charger, vous devez le faire vous-même. Ceci est normalement aussi simple que d'appeler "waitpid $pid, 0" lorsque vous avez terminé avec le processus. Ne pas le faire peut entraîner une accumulation de processus défuntes ou "zombies". Voir "waitpid" dans perlfunc pour plus d'informations.

Si vous essayez de lire depuis l'écrivain stdout de l'enfant et son écrivain stderr, vous aurez des problèmes de blocage, ce qui signifie que vous voudrez utiliser "select" ou IO::Select, ce qui signifie qu'il vaut mieux utiliser "sysread" au lieu de "readline" pour les choses normales.

Ceci est très dangereux, car vous pourriez bloquer pour toujours. "open3" suppose qu'il va parler à quelque chose comme bc(1), en lui écrivant et en lui lisant. C'est vraisemblablement sûr car vous "savez" que des commandes comme bc(1) liront ligne par ligne et produiront une ligne à la fois. Des programmes comme sort(1) qui lisent leur flux d'entrée entier d'abord, cependant, sont très susceptibles de causer une interdiction.

Le gros problème avec cette approche est que si vous n'avez pas le contrôle du code source exécuté dans le processus enfant, vous ne pouvez pas contrôler ce qu'il fait du buffering du pipe. Ainsi, vous ne pouvez pas simplement ouvrir un pipe vers "cat -v" et lire et écrire continuellement une ligne à partir de celui-ci.
