NOM

error::pass5 - erreurs de la passe 5 de systemtap

DESCRIPTION

Les erreurs qui surviennent pendant la passe 5 (exécution) peuvent avoir diverses causes.

événements exceptionnels pendant l'exécution du script
Le traducteur et le runtime de systemtap incluent de nombreux contrôles d'erreurs visant à protéger les systèmes et les utilisateurs contre les erreurs ou les conditions transitoires. Le script peut appeler délibérément la fonction de tapset error() pour signaler un problème. Une partie de la mémoire nécessaire à l'accès aux variables $context peut être temporairement indisponible. Envisagez d'utiliser la construction try/catch pour encapsuler des fragments de script dans du code de gestion des exceptions. Envisagez d'utiliser l'option stap --suppress-handler-errors ou stap --skip-badvars.
épuisement des ressources
L'une des plusieurs limites de ressources d'espace ou de temps peut être dépassée par le script, y compris la surcharge du système, un trop grand nombre de tuples à stocker dans un tableau, etc. Certains messages d'erreur identifient la contrainte par un nom de macro, qui peut être augmentée individuellement. Envisagez d'utiliser les options stap --suppress-handler-errors et/ou stap -g --suppress-time-limits. Étendez ou désactivez des limites de ressources individuelles à l'aide de l'option stap -DSOME_LIMIT=NNNN. L'option stap -t peut identifier les sondes qui prennent trop de temps.
problèmes du serveur d'exécution distant
Si vous utilisez l'option stap --remote pour diriger un script systemtap vers une exécution ailleurs, assurez-vous qu'une connexion SSH peut être établie avec l'hôte distant et qu'il dispose du runtime systemtap actuel installé et disponible.
incompatibilité de version du noyau
Si vous voyez un message d'erreur « Couldn't insert module ... » lors de l'exécution du script, la version de l'arborescence de développement du noyau sélectionnée par stap (ou par l'utilisateur via l'option -r) peut ne pas correspondre à celle du noyau réellement en cours d'exécution. Cela peut arriver plus facilement si vous exécutez des noyaux personnalisés. Vérifiez la sortie de dmesg pour des indices.
problèmes d'installation/permissions
Il est possible que votre copie de systemtap n'ait pas été correctement installée. Par exemple, le programme /usr/bin/staprun peut manquer des autorisations setuid nécessaires, ou votre identifiant utilisateur appelant peut ne pas avoir les privilèges suffisants (root, ou stapusr et appartenances aux groupes associés). Les variables d'environnement peuvent interférer avec la localisation de /usr/libexec/.../stapio.
configuration de sécurité
SecureBoot ou d'autres mécanismes de signature de modules peuvent être actifs, empêchant le chargement de modules .ko. Un service stap-server local ou distant serait nécessaire pour gérer les clés en toute sécurité. Cette situation est détectée automatiquement sur la plupart des noyaux, mais sur certains, la variable d'environnement SYSTEMTAP_SIGN peut devoir être définie pour déclencher ce traitement supplémentaire lié à la signature. Vérifiez la sortie de dmesg pour des indices.

Le backend systemtap normal basé sur les modules du noyau peut être plus que ce que votre script requiert. Essayez les backends stap --runtime=bpf et/ou stap --runtime=dyninst. Bien qu'ils aient des limitations inhérentes, ils fonctionnent avec des privilèges et des risques perçus moindres.

Il peut être possible de désactiver temporairement les mesures de sécurité/verrouillage avec la combinaison de touches SysRQ+x, ou de manière permanente avec sudo mokutil --disable-validation et un redémarrage.

erreurs du programme cible
Le programme invoqué par l'option stap -c CMD peut se terminer avec un code non nul.
exceptions non interceptées dans le programme cible
Lors de l'utilisation de --runtime=dyninst, vous pouvez rencontrer un problème où le programme cible s'arrête avec un message tel que « terminate called after throwing an instance of 'foo_exception' ». C'est malheureusement une limitation de Dyninst, qui empêche parfois les exceptions de se dérouler correctement dans du code instrumenté.

RASSEMBLER PLUS D'INFORMATIONS

Augmenter la verbosité de la passe 5 avec une option telle que --vp 00001 peut aider à identifier le problème. Voir aussi : dmesg sur les machines concernées.
