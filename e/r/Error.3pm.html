Paquet: perl-error

Licences: PerlArtistic, GPL

NOM

Error - Gestion des erreurs/exceptions de manière orientée objet

VERSION

version 0.17030

RÉSUMÉ

use Error qw(:try);
throw Error::Simple( "A simple error");
sub xyz {
    ...
    record Error::Simple("A simple error")
        and return;
}
unlink($file) or throw Error::Simple("$file: $!",$!);
try {
    do_some_stuff();
    die "error!" if $condition;
    throw Error::Simple "Oops!" if $other_condition;
}
catch Error::IO with {
    my $E = shift;
    print STDERR "File ", $E->{'-file'}, " had a problem\n";
}
except {
    my $E = shift;
    my $general_handler=sub {send_message $E->{-description}};
    return {
        UserException1 => $general_handler,
        UserException2 => $general_handler
    };
}
otherwise {
    print STDERR "Well I don't know what to say\n";
}
finally {
    close_the_garage_door_already(); # Should be reliable
}; # Don't forget the trailing ; or you might be surprised

DESCRIPTION

Le paquet "Error" fournit deux interfaces. Premièrement "Error" fournit une interface procédurale pour la gestion des exceptions. Deuxièmement "Error" est une classe de base pour les erreurs/exceptions qui peuvent soit être lancées (throw) pour être capturées (catch) par la suite, soit simplement être enregistrées.

Les erreurs dans la classe "Error" ne doivent pas être lancées directement, mais l'utilisateur doit lancer des erreurs issues d'une sous-classe de "Error".

AVERTISSEMENT

L'utilisation du module "Error" est déconseillée en raison de la nature magique noire de son sucre syntaxique, qui a tendance à casser souvent. Ses mainteneurs ont cessé d'écrire activement du code qui l'utilise, et découragent les autres de le faire. Voir la section « VOIR AUSSI » ci-dessous pour de meilleures recommandations.

INTERFACE PROCÉDURALE

"Error" exporte des sous-routines pour effectuer la gestion des exceptions. Celles-ci seront exportées si le tag ":try" est utilisé dans la ligne "use" .

try BLOC CLAUSES
"try" est la sous-routine principale appelée par l'utilisateur. Toutes les autres sous-routines exportées sont des clauses pour la sous-routine try.

Le BLOC sera évalué et, si aucune erreur n'est lancée, try retournera le résultat du bloc.

"CLAUSES" sont les sous-routines ci-dessous, qui décrivent quoi faire en cas d'erreur lancée à l'intérieur du BLOC.

catch CLASSE with BLOC
Cette clause fera en sorte que toutes les erreurs satisfaisant "$err->isa(CLASSE)" soient capturées et traitées en évaluant "BLOC".

"BLOC" recevra deux arguments. Le premier sera l'erreur en cours de lancement. Le second est une référence à une variable scalaire. Si cette variable est définie par le bloc catch, alors, au retour du bloc catch, try continuera le traitement comme si le bloc catch n'avait jamais été trouvé. L'erreur sera également disponible dans $@.

Pour propager l'erreur, le bloc catch peut appeler "$err->throw"

Si la référence scalaire du second argument n'est pas définie, et que l'erreur n'est pas relancée, alors le bloc try courant retournera avec le résultat du bloc catch.

except BLOC
Quand "try" cherche un gestionnaire, si une clause except est trouvée "BLOC" est évalué. La valeur de retour de ce bloc doit être une référence à un HASHREF ou une liste de paires clé-valeur, où les clés sont des noms de classes et les valeurs sont des références CODE pour le gestionnaire des erreurs de ce type.
otherwise BLOC
Capture n'importe quelle erreur en exécutant le code dans "BLOC"

Quand il est évalué "BLOC" recevra un argument, qui sera l'erreur en cours de traitement. L'erreur sera également disponible dans $@.

Un seul bloc otherwise peut être spécifié par bloc try

finally BLOC
Exécute le code dans "BLOC" soit après que le code dans le bloc try s'est terminé avec succès, soit si le bloc try lance une erreur, alors "BLOC" sera exécuté après que le gestionnaire s'est terminé.

Si le gestionnaire lance une erreur, alors l'erreur sera capturée, le bloc finally sera exécuté et l'erreur sera relancée.

Un seul bloc finally peut être spécifié par bloc try

COMPATIBILITÉ

Moose exporte un mot-clé appelé "with" qui entre en conflit avec celui d'Error. Cet exemple retourne une erreur de prototype mismatch :

package MyTest;
use warnings;
use Moose;
use Error qw(:try);

(Merci à "maik.hentsche@amd.com" pour le rapport.).

INTERFACE CLASSE

CONSTRUCTEURS

L'objet "Error" est implémenté comme un HASH. Ce HASH est initialisé avec les arguments qui lui sont passés par son constructeur. Les éléments utilisés par, ou récupérables par la classe "Error" sont listés ci-dessous, d'autres classes peuvent en ajouter.

-file
-line
-text
-value
-object

Si "-file" ou "-line" ne sont pas spécifiés dans les arguments du constructeur, alors ceux-ci seront initialisés avec le nom du fichier et le numéro de ligne d'où le constructeur a été appelé.

Si l'erreur est associée à un objet, alors l'objet doit être passé comme argument "-object" . Cela permettra au paquet "Error" d'associer l'erreur à l'objet.

Le paquet "Error" se souvient de la dernière erreur créée, et aussi de la dernière erreur associée à un paquet. Cela pourrait être soit la dernière erreur créée par une sous-routine dans ce paquet, soit la dernière erreur qui a passé un objet bénit dans ce paquet comme argument "-object" .

Error->new()
Voir la documentation d'Error::Simple.
throw ( [ ARGS ] )
Crée un nouvel objet "Error" et lance une erreur, qui sera capturée par un bloc "try" englobant, s'il y en a un. Sinon cela fera quitter le programme.

"throw" peut également être appelé sur une erreur existante pour la relancer.

with ( [ ARGS ] )
Crée un nouvel objet "Error" et le retourne. C'est défini pour le sucre syntaxique, par ex. 
die with Some::Error ( ... );
record ( [ ARGS ] )
Crée un nouvel objet "Error" et le retourne. C'est défini pour le sucre syntaxique, par ex. 
record Some::Error ( ... )
    and return;

MÉTHODES STATIQUES

prior ( [ PAQUET ] )
Retourne la dernière erreur créée, ou la dernière erreur associée à "PAQUET"
flush ( [ PAQUET ] )
Vide la dernière erreur créée, ou la dernière erreur associée à "PACKAGE". Il est nécessaire de vider la pile d'erreurs avant de quitter le paquet, sinon les erreurs non capturées générées avec "record" seront signalées. 
$Error->flush;

MÉTHODES D'OBJET

stacktrace
Si la variable $Error::Debug était non nulle lorsque l'erreur a été créée, alors "stacktrace" retourne une chaîne créée en appelant "Carp::longmess". Si la variable était nulle, "stacktrace" retourne le texte de l'erreur auquel sont ajoutés le nom du fichier et le numéro de ligne où l'erreur a été créée, à condition que le texte ne se termine pas par un saut de ligne.
object
L'objet auquel cette erreur était associée
file
Le fichier à partir duquel le constructeur de cette erreur a été appelé
line
La ligne à partir de laquelle le constructeur de cette erreur a été appelé
text
Le texte de l'erreur
$err->associate($obj)
Associe une erreur à un objet pour permettre la propagation d'erreurs. C'est-à-dire : 
$ber->encode(...) ou
    return Error->prior($ber)->associate($ldap);

MÉTHODES DE SURCHARGE

stringify
Une méthode qui convertit l'objet en chaîne. Cette méthode peut simplement retourner la même chose que la méthode "text" , ou elle peut ajouter plus d'informations. Par exemple le nom du fichier et le numéro de ligne.

Par défaut, cette méthode retourne l'argument "-text" qui a été passé au constructeur, ou la chaîne "Died" si aucun n'a été donné.

value
Une méthode qui retournera une valeur pouvant être associée à l'erreur. Par exemple, si une erreur a été créée à la suite de l'échec d'un appel système, alors elle peut retourner la valeur numérique de $! au moment donné.

Par défaut, cette méthode retourne l'argument "-value" qui a été passé au constructeur.

CLASSES D'ERREUR PRÉDÉFINIES

Error::Simple

Cette classe peut être utilisée pour contenir des chaînes et des valeurs d'erreurs simples. Son constructeur prend deux arguments. Le premier est une valeur textuelle, le second est une valeur numérique. Ces valeurs sont celles qui seront retournées par les méthodes de surcharge.

Si la valeur textuelle se termine par "at file line 1" comme le font les chaînes de $@, alors cette information sera utilisée pour définir les arguments "-file" et "-line" de l'objet d'erreur.

Cette classe est utilisée en interne si un bloc eval meurt avec une erreur qui est une chaîne simple. (Sauf si $Error::ObjectifyCallback est modifié)

$Error::ObjectifyCallback

Cette variable contient une référence à une sous-routine qui convertit les erreurs qui sont des chaînes simples en objets. Elle est utilisée par Error.pm pour convertir les erreurs textuelles en objets, et peut être remplacée par l'utilisateur.

Elle accepte un seul argument qui est une référence à un hachage de paramètres nommés. Actuellement, le seul paramètre nommé passé est 'text' qui est le texte de l'erreur, mais d'autres peuvent être disponibles à l'avenir.

Par exemple, le code suivant fera en sorte que Error.pm lance des objets de la classe MyError::Bar par défaut :

sub throw_MyError_Bar
{
    my $args = shift;
    my $err = MyError::Bar->new();
    $err->{'MyBarText'} = $args->{'text'};
    return $err;
}
{
    local $Error::ObjectifyCallback = \&
    # Gestion des erreurs ici.
}

GESTIONNAIRES DE MESSAGES

"Error" fournit également des gestionnaires pour étendre la sortie de la fonction perl warn() , et pour gérer l'affichage d'une "Error" lancée qui n'est pas capturée ou autrement gérée. Ceux-ci ne sont pas installés par défaut, mais sont demandés en utilisant la balise ":warndie" dans la ligne "use" .

use Error qw( :warndie );

Ces nouveaux gestionnaires d'erreurs sont installés dans $SIG{__WARN__} et $SIG{__DIE__}. Si ces gestionnaires sont déjà définis lorsque la balise est importée, les anciennes valeurs sont stockées et utilisées pendant le nouveau code. Ainsi, pour organiser un traitement personnalisé des avertissements et des erreurs, vous devrez effectuer quelque chose comme ceci :

BEGIN {
  $SIG{__WARN__} = sub {
    print STDERR "Mon gestionnaire d'avertissements spécial : $_[0]"
  };
}
use Error qw( :warndie );

Notez que définir $SIG{__WARN__} après que la balise ":warndie" a été importée écrasera le gestionnaire que "Error" fournit. Si cela ne peut être évité, alors la balise peut être explicitement "import"ée plus tard

use Error;
$SIG{__WARN__} = ...;
import Error qw( :warndie );

EXEMPLE

Le gestionnaire "__DIE__" transforme des messages tels que

Can't call method "foo" on an undefined value at examples/warndie.pl line 16.

en

Unhandled perl error caught at toplevel:
  Can't call method "foo" on an undefined value
Thrown from: examples/warndie.pl:16
Full stack trace:
        main::inner('undef') called at examples/warndie.pl line 20
        main::outer('undef') called at examples/warndie.pl line 23

VOIR AUSSI

Voir Exception::Class pour un module différent fournissant une gestion d'exceptions orientée objet, avec une syntaxe pratique pour déclarer des hiérarchies pour celles-ci. Il ne fournit pas le sucre syntaxique d'Error comme "try { ... }", "catch { ... }", etc., ce qui peut être une bonne chose ou une mauvaise chose selon ce que vous voulez. (Parce que le sucre syntaxique d'Error a tendance à casser.)

Error::Exception vise à combiner Error et Exception::Class "avec une conversion correcte en chaîne".

TryCatch et Try::Tiny sont similaires dans le concept à Error.pm, fournissant seulement une syntaxe qui, on l'espère, casse moins.
