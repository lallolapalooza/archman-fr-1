NOM

error::dwarf - problèmes de qualité des informations de débogage dwarf

DESCRIPTION

Systemtap s'appuie parfois sur les informations de débogage ELF/DWARF des programmes instrumentés pour localiser les points de sonde, ou pour lire/écrire des variables contextuelles, tout comme le fait un débogueur symbolique. Même si l'examen du code source du programme peut montrer des variables ou des lignes où des sondes peuvent être souhaitées, le compilateur doit préserver ces informations pour que systemtap (ou un débogueur comme gdb) puisse y accéder précisément. Si un script requiert de telles données, mais que le compilateur n'en a pas préservé suffisamment, des erreurs de passe-2 peuvent en résulter.

Les conditions courantes qui déclenchent ces problèmes incluent :

informations de débogage manquantes ou non concordantes
Parfois, les informations de débogage sont installées, mais ne correspondent pas aux binaires sondés. Voir la page man warning::debuginfo pour plus d'aide afin de localiser les bonnes informations de débogage.
version du compilateur
Avant la version 4.5 de GCC, la qualité des informations de débogage était assez limitée. Souvent, les développeurs étaient conseillés de compiler leurs programmes avec les drapeaux -O0 -g pour désactiver l'optimisation. La version 4.5 de GCC a introduit une fonctionnalité appelée « affectations de suivi de variables » qui lui permet de générer des informations de débogage de haute qualité sous optimisation complète -O2 -g. Ce n'est pas parfait, mais bien meilleur qu'avant. Notez que, en raison d'un autre bug de gcc (PR51358), -O0 -g peut parfois dégrader la qualité des informations de débogage par rapport à -O2 -g.

Un autre problème connexe concerne la qualité des informations de débogage pour la zone de prologue d'une fonction (PR15123), où un programme compilé avec CFLAGS=-mfentry (en particulier le noyau, pour ftrace) peut manquer d'informations de débogage précises pour les instructions d'entrée pour les versions de gcc antérieures à la version 4.8. Si possible, arrangez-vous pour compiler vos programmes avec des CFLAGS -grecord-gcc-switches, et/ou essayez de relancer systemtap avec $PR15123_ASSUME_MFENTRY=1.

le système de build Linux endommage la qualité des informations de débogage
Un commit du noyau en amont #2062afb4f804a a introduit -fno-var-tracking-assignments dans KCFLAGS, réduisant considérablement la qualité des informations de débogage, ce qui peut causer des échecs de débogage. La solution la plus simple est d'effacer, supprimer, bref, éradiquer cette ligne du Makefile principal de Linux :

KBUILD_CFLAGS += [...] -fno-var-tracking-assignments [...]

inlining de fonctions
Même les versions modernes de gcc ont parfois des problèmes avec les paramètres des fonctions inlinées. Il peut être nécessaire de modifier le script pour sonder un endroit légèrement différent. Essayez une sonde .statement(), au lieu d'une sonde .function(), quelque part quelques lignes de code dans le corps de la fonction inlinée. Ou essayez de placer une sonde sur le site d'appel de la fonction inlinée. Ou utilisez la construction de langage de script if @defined($var) { ... } pour tester la résolvabilité de la variable de contexte avant de l'utiliser.
réorganisation des instructions
Le code fortement optimisé mélange souvent les instructions de plusieurs instructions source. Cela peut laisser systemtap sans endroit pour choisir de placer une sonde, en particulier une sonde d'instruction spécifiée par numéro de ligne. Systemtap peut conseiller d'essayer un numéro de ligne voisin, mais ceux-ci peuvent également ne pas bien fonctionner. Envisagez de placer une sonde par un caractère générique d'instruction ou une plage de numéros de ligne.
configuration d'elfutils
Il est possible que les informations de débogage DWARF recherchées soient disponibles, mais pas dans un format acceptable pour la copie d'elfutils utilisée par systemtap. Par exemple, votre copie de gcc pourrait produire des informations de débogage compressées (sections ELF .zdebug_* ou fichiers .xz) alors que votre copie d'elfutils pourrait manquer des capacités de décompression appropriées. Malheureusement, il n'y a pas de moyen facile de savoir si c'est le problème. Si vous construisez votre propre copie d'elfutils, assurez-vous que toutes les bibliothèques de décompression sont disponibles au moment de la compilation.
configuration des informations de débogage
Certains outils peuvent générer des informations de débogage non prises en charge par systemtap, telles que l'option CONFIG_DEBUG_INFO_SPLIT (fichiers .dwo) du noyau Linux. Privilégiez le format ELF/DWARF simple (éventuellement divisé, style Fedora) si possible.

ALTERNATIVES

Afin de réduire la dépendance aux informations de débogage ELF/DWARF, envisagez l'utilisation d'instrumentation compilée statiquement, telle que les points de trace du noyau, ou les marqueurs utilisateur de <sys/sdt.h>. Ces sites de hook d'instrumentation ont un coût relativement faible (juste une instruction NOP pour sdt.h), et garantissent presque la disponibilité des données de paramètres et un site de sonde fiable, le tout sans dépendance aux informations de débogage.
