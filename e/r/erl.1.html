Signaux

Sur les systèmes Unix, le runtime Erlang interprétera deux types de signaux.

SIGUSR1

Un signal SIGUSR1 force un vidage de crash.

SIGTERM

Un signal SIGTERM produira un message stop au processus init. Ceci est équivalent à un appel init:stop/0.

Introduit dans ERTS 8.3 (Erlang/OTP 19.3)

Le signal SIGUSR2 est réservé à un usage interne. Aucun autre signal n'est géré.

Si un fichier .erlang est trouvé, il est supposé contenir des expressions Erlang valides. Ces expressions sont évaluées comme si elles étaient entrées dans le shell.

Un fichier .erlang typique contient un ensemble de chemins de recherche, par exemple :

io:format("exécute le profil utilisateur dans $HOME/.erlang\n",[]).
code:add_path("/home/calvin/test/ebin").
code:add_path("/home/hobbes/bigappl-1.2/ebin").
io:format("rc .erlang terminé\n",[]).
•user_default et shell_default - Les fonctions du shell qui ne sont pas précédées d'un nom de module sont considérées comme des objets fonctionnels (funs), des fonctions intégrées (BIFs) ou appartiennent au module user_default ou shell_default.

Pour inclure des commandes de shell privées, définissez-les dans un module user_default et ajoutez l'argument suivant comme première ligne du fichier .erlang :

code:load_abs("..../user_default").

Si le contenu de .erlang est modifié et qu'une version privée de user_default est définie, l'environnement Erlang/OTP peut être personnalisé. Des modifications plus puissantes peuvent être apportées en fournissant des arguments de ligne de commande dans le script de démarrage erl. Pour plus d'informations, voir init.
