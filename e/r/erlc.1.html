erlc(1) Commandes utilisateur erlc(1)

NOM

erlc - Compilateur

DESCRIPTION

Le programme erlc fournit un moyen commun d'exécuter tous les compilateurs du système Erlang. En fonction de l'extension de chaque fichier d'entrée, erlc invoque le compilateur approprié. Indépendamment du compilateur utilisé, les mêmes options sont utilisées pour fournir des paramètres, tels que les chemins d'inclusion et le répertoire de sortie.

Le répertoire de travail courant, ".", n'est pas inclus dans le chemin du code lors de l'exécution du compilateur. Ceci afin d'éviter de charger des fichiers Beam à partir du répertoire de travail courant qui pourraient potentiellement entrer en conflit avec le compilateur ou le système Erlang/OTP utilisé par le compilateur.

erlc options fichier1.ext fichier2.ext...

Compile un ou plusieurs fichiers. Les fichiers doivent inclure l'extension, par exemple, .erl pour le code source Erlang, ou .yrl pour le code source Yecc. Erlc utilise l'extension pour invoquer le bon compilateur.

Options généralement utiles

Les options suivantes sont prises en charge :

-I <Répertoire>

Demande au compilateur de rechercher les fichiers d'inclusion dans le Répertoire. Lors de la rencontre d'une directive -include ou -include_lib, le compilateur recherche les fichiers d'en-tête dans les répertoires suivants :
•".", le répertoire de travail courant du serveur de fichiers
•Le nom de base du fichier compilé
•Les répertoires spécifiés à l'aide de l'option -I ; le dernier répertoire spécifié est recherché en premier

-o <Répertoire>

Le répertoire où le compilateur doit placer les fichiers de sortie. Par défaut, le répertoire de travail courant.

-D<Nom>

Définit une macro.

-D<Nom>=<Valeur>

Définit une macro avec la valeur spécifiée. La valeur peut être n'importe quel terme Erlang. Selon la plateforme, la valeur peut nécessiter des guillemets si le shell lui-même interprète certains caractères. Sur Unix, les termes contenant des tuples et des listes doivent être mis entre guillemets. Les termes contenant des espaces doivent être mis entre guillemets sur toutes les plateformes.

-Werror

Transforme tous les avertissements en erreurs.

-W<Numéro>

Définit le niveau d'avertissement à Numéro. Par défaut, 1. Pour désactiver les avertissements, utilisez -W0.

-W

Identique à -W1. Par défaut.

-v

Active la sortie verbeuse.

-b <Type_de_sortie>

Spécifie le type de fichier de sortie. Type_de_sortie est identique à l'extension du fichier de sortie, mais sans le point. Cette option est ignorée par les compilateurs qui ont un format de sortie unique.

-no-server

N'utilise pas le serveur de compilation.

-server

Utilise le serveur de compilation.

-enable-feature <Caractéristique>

Active la caractéristique caractéristique pendant la compilation. La caractéristique spéciale all peut être utilisée pour activer toutes les caractéristiques.

-disable-feature <caractéristique>

Désactive la caractéristique caractéristique pendant la compilation. La caractéristique spéciale all peut être utilisée pour désactiver toutes les caractéristiques non permanentes.

-list-features

Liste de courtes descriptions des caractéristiques configurables actuelles. Les caractéristiques non configurables (celles dont le statut est rejected ou permanent) ne seront pas affichées.

-describe-feature <caractéristique>

Affiche une description détaillée et l'historique de la caractéristique caractéristique.

-M

Produit une règle Makefile pour suivre les dépendances d'en-tête. La règle est envoyée à stdout. Aucun fichier objet n'est produit.

-MMD

Génère les dépendances comme effet secondaire. Le fichier objet sera produit normalement. Cette option remplace l'option -M.

-MF <Makefile>

Comme l'option -M, sauf que le fichier Makefile est écrit dans Makefile. Aucun fichier objet n'est produit.

-MD

Identique à -M -MF <Fichier>.Pbeam.

-MT <Cible>

En conjonction avec l'option -M ou -MF, modifie le nom de la règle émise en Cible.

-MQ <Cible>

Comme l'option -MT, sauf que les caractères spéciaux pour make/1 sont mis entre guillemets.

-MP

En conjonction avec l'option -M ou -MF, ajoute une cible « phony » pour chaque dépendance.

-MG

En conjonction avec l'option -M ou -MF, considère les en-têtes manquants comme des fichiers générés et les ajoute aux dépendances.

--

Signale qu'aucune autre option ne suivra. Le reste des arguments est traité comme des noms de fichiers, même s'ils commencent par des tirets.

+<Terme>

Une option commençant par un plus ( +) plutôt qu'un tiret est convertie en terme Erlang et passée inchangée au compilateur. Par exemple, l'option export_all pour le compilateur Erlang peut être spécifiée comme suit : 
erlc +export_all fichier.erl

Selon la plateforme, la valeur peut nécessiter des guillemets si le shell lui-même interprète certains caractères. Sur Unix, les termes contenant des tuples et des listes doivent être mis entre guillemets. Les termes contenant des espaces doivent être mis entre guillemets sur toutes les plateformes.

Options spéciales

Les options suivantes sont utiles dans des situations spéciales, comme la reconstruction du système OTP :

-pa <Répertoire>

Ajoute Répertoire au début du chemin du code dans l'émulateur Erlang invoqué. Cela peut être utilisé pour invoquer un compilateur différent de celui par défaut.

-pz <Répertoire>

Ajoute Répertoire à la fin du chemin du code dans l'émulateur Erlang invoqué.

Compilateurs supportés

Les compilateurs suivants sont pris en charge :

.erl

Code source Erlang. Il génère un fichier .beam.

Les options -P, -E, et -S sont équivalentes à +'P', +'E', et +'S', sauf qu'il n'est pas nécessaire d'inclure les guillemets simples pour les protéger du shell.

Options prises en charge : -I, -o, -D, -v, -W, -b.

.S

Code source assembleur Erlang. Il génère un fichier .beam.

Options prises en charge : identiques à celles pour .erl.

.core

Code source Erlang core. Il génère un fichier .beam.

Options prises en charge : identiques à celles pour .erl.

.yrl

Code source Yecc. Il génère un fichier .erl.

Utilisez l'option -I avec le nom d'un fichier pour utiliser ce fichier comme prologue personnalisé (option includefile).

Options prises en charge : -o, -v, -I, -W.

.mib

MIB pour SNMP. Il génère un fichier .bin.

Options prises en charge : -I, -o, -W.

.bin

Une MIB compilée pour SNMP. Il génère un fichier .hrl.

Options prises en charge : -o, -v.

.rel

Fichier script. Il génère un fichier de démarrage.

Utilisez l'option -I pour nommer les répertoires à rechercher pour les fichiers d'application (équivalent à path dans la liste d'options pour systools:make_script/2).

Option prise en charge : -o.

.asn1

Fichier ASN1. Il crée un fichier .erl, .hrl et .asn1db à partir d'un fichier .asn1. Compile également le .erl en utilisant le compilateur Erlang, sauf si l'option +noobj est spécifiée.

Options prises en charge : -I, -o, -b, -W.

.idl

Fichier IC. Il exécute le compilateur IDL.

Options prises en charge : -I, -o.

Serveur de compilation

Le serveur de compilation peut être utilisé pour

o potentiellement accélérer la construction de projets multi-fichiers en évitant de démarrer un système Erlang pour chaque fichier à compiler. Que cela accélère la construction dépend de la nature du projet et de la machine de

construction.

Par défaut, le serveur de compilation n'est pas utilisé. Il peut être activé en donnant à erlc l'option -server ou en définissant la variable d'environnement ERLC_USE_SERVER à yes ou true

.

Lorsque le serveur de compilation est activé, erlc l'utilisera automatiquement s'il est démarré et démarrera le serveur s'il ne l'est pas déjà. Le serveur se terminera de lui-même après être resté inactif pendant un certain nombre de

secondes.

erlc et le serveur de compilation communiquent via la distribution Erlang. Le serveur de compilation est démarré en tant que nœud caché, avec un nom qui inclut l'utilisateur courant. Ainsi, chaque utilisateur d'un ordinateur possède son propre serveur de

compilation.

L'utilisation du serveur de compilation n'accélère pas toujours la construction, car le serveur de compilation doit parfois être redémarré pour garantir la correction. Voici quelques exemples de situations qui forcent un redémarrage

:
•erlc souhaite utiliser une version différente d'Erlang que celle utilisée par le serveur de
compilation.
•erlc souhaite utiliser des options différentes pour erl que celles avec lesquelles le serveur de compilation a été démarré. (Un changement de chemin de code via l'option -pa pourrait charger des transformations d'analyse différentes. Par sécurité, le serveur de compilation sera redémarré lorsque n'importe quelle option erl est modifiée.
)
•Si le répertoire de travail courant pour erlc est différent du répertoire de travail actif lorsque le serveur de compilation a été démarré, et si le serveur de compilation a des tâches actives, il sera redémarré dès que ces tâches seront terminées. (Les systèmes de construction qui
compilent des fichiers aléatoirement à travers plusieurs répertoires en parallèle ne bénéficieront probablement pas du serveur de compilation.)

Variables

d'environnement

ERLC_EMULATO

R
La commande pour démarrer l'émulateur, qui doit être uniquement le chemin de l'émulateur sans aucun paramètre. Par défaut, c'est erl dans le même répertoire que le programme erlc lui-même, ou, s'il n'existe pas, erl dans n'importe lequel des répertoires spécifiés dans la variable d'environnement PATH
.

ERLC_USE_SERVE

R
Les valeurs autorisées sont yes ou true pour utiliser le serveur de compilation, et no ou false pour ne pas utiliser le serveur de compilation. Si d'autres valeurs sont données, erlc affichera un avertissement et
continuera.

ERLC_SERVER_I

D
Indique à erlc d'identifier le serveur de compilation par le nom donné, permettant à un utilisateur unique de lancer plusieurs constructions non liées en parallèle sans qu'elles n
e s'affectent mutuellement, ce qui peut être utile pour les machines de construction
partagées et similaires. Le nom doit être alphanumérique, et il est vide par défaut.
