Comme mentionné dans Encode, les encodages sont (au moins dans l'implémentation actuelle) définis comme des objets. La correspondance du nom d'encodage à l'objet se fait via le hash %Encode::Encoding. Bien que vous puissiez manipuler directement ce hash, il est fortement recommandé d'utiliser ce module de classe de base et d'ajouter les méthodes encode() et decode

Pourquoi l'API d'Encode est-elle différente

?

Il convient de noter que le comportement de $check est différent de celui de l'API publique externe. La logique est que le cas "non vérifié" est utile quand l'encodage fait partie d'un flux qui peut signaler des erreurs (par ex. STDERR). Dans de tels cas, il est souhaitable de faire passer tout d'une manière ou d'une autre sans causer des erreurs supplémentaires qui obscurcissent l'erreur originale. De plus, l'encodage est le mieux placé pour savoir quel est le bon caractère de remplacement, donc si c'est le comportement désiré, laisser le code de bas niveau le faire est le plus

efficace.

À l'inverse, si $check est vrai, le schéma ci-dessus permet à l'encodage de faire tout ce qu'il peut et de dire à la couche supérieure combien il a fait. Ce qui manque actuellement est un mécanisme pour rapporter ce qui s'est mal passé. L'interface la plus probable sera un appel de méthode supplémentaire à l'objet, ou peut-être (pour éviter d'imposer des objets par flux à des encodages autrement sans état) un paramètre

supplémentaire.

Il est également hautement souhaitable que les classes d'encodage héritent de "Encode::Encoding" comme classe de base. Cela permet à cette classe de définir un comportement supplémentaire pour tous les objets

d'encodage. 
package Encode::MyEncoding;
use parent qw(Encode::Encoding);
__PACKAGE__->Define(qw(myCanonical myAlias))
;

pour créer un objet avec "bless {Name => ...}, $class", et appeler define_encoding. Ils héritent de leur méthode "name" de "Encode::Enco

ding".
