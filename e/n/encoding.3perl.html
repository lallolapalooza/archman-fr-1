encoding(3perl) Guide du programmeur Perl encoding(3perl)

NOM

encoding - permet d'écrire votre script dans un encodage autre que ASCII et UTF-8

AVERTISSEMENT

Ce module est déprécié depuis perl v5.18. Voir "DESCRIPTION" et "BUGS".

SYNTAXE

use encoding "greek";  # Perl aime le grec ?
use encoding "euc-jp"; # Jperl !
# ou vous pouvez même faire ceci si votre shell supporte votre encodage natif
perl -Mencoding=latin2 -e'...' # Vous sentez-vous d'Europe centrale ?
perl -Mencoding=euc-kr -e'...' # Ou coréen ?
# plus de contrôle
# Un simple convertisseur euc-cn => utf-8
use encoding "euc-cn", STDOUT => "utf8";  while(<>){print};
# "no encoding;" est supporté
no encoding;
# une autre façon, Filtre
use encoding "euc-jp", Filter=>1;
# maintenant vous pouvez utiliser des identifiants en kanji -- en euc-jp !
# encoder basé sur la locale actuelle - usages spécialisés uniquement ;
# plein de dangers !!
use encoding ':locale';

DESCRIPTION

Ce pragma est utilisé pour permettre à un script Perl d'être écrit dans des encodages qui ne sont ni strictement ASCII ni UTF-8. Il traduit tout ou partie du script du programme Perl d'un encodage donné vers UTF-8, et change les couches PerlIO de "STDIN" et "STDOUT" vers l'encodage spécifié.

Ce pragma date de l'époque où les éditeurs compatibles UTF-8 étaient rares. Mais c'était il y a longtemps, et son utilité a grandement diminué. Cela, couplé au fait qu'il ne fonctionne pas avec les threads, ainsi qu'à d'autres problèmes (voir "BUGS"), a conduit à sa dépréciation. Il est prévu de supprimer ce pragma dans une future version de Perl. Les nouveaux codes devraient être écrits en UTF-8, et le pragma "use utf8" utilisé à la place (voir perluniintro et utf8 pour plus de détails). Les anciens codes devraient être convertis en UTF-8, via quelque chose comme la recette dans la "SYNOPSIS" (bien que cette approche simple puisse nécessiter des ajustements manuels par la suite).

Si UTF-8 n'est pas une option, il est recommandé d'utiliser un simple filtre source, tel que celui fourni par Filter::Encoding sur CPAN ou l'option "Filter" de ce pragma (voir ci-dessous).

La seule utilisation légitime de ce pragma est presque certainement une seule par fichier, près du début, avec une portée de fichier, car le fichier sera probablement écrit dans un seul encodage. Des restrictions supplémentaires s'appliquent dans les Perls avant v5.22 (voir "Avant Perl v5.22").

Il existe deux modes de fonctionnement de base (plus la désactivation) :

"use encoding ['ENCNAME'] ;"
Attention : Ce mode de fonctionnement n'est plus supporté depuis Perl v5.26.

C'est le fonctionnement normal. Il traduit diverses littérales rencontrées dans le fichier source Perl de l'encodage ENCNAME vers UTF-8, et convertit de manière similaire les points de code de caractères. Ceci est utilisé lorsque le script est une combinaison d'ASCII (pour les noms de variables et la ponctuation, etc), mais que les données littérales sont dans l'encodage spécifié.

ENCNAME est facultatif. S'il est omis, l'encodage spécifié dans la variable d'environnement "PERL_ENCODING" est utilisé. Si celle-ci n'est pas définie, ou si l'encodage résolu n'est pas connu de "Encode", l'erreur "Unknown encoding 'ENCNAME'" sera lancée.

À partir de Perl v5.8.6 ("Encode" version 2.0.1), ENCNAME peut être le nom ":locale". Ceci est pour des applications très spécialisées et est documenté dans "Le sous-pragma ":locale"" ci-dessous.

Les littérales qui sont converties sont "q//, qq//, qr//, qw///, qx//", et à partir de v5.8.1, "tr///". Les opérations qui font des conversions incluent "chr", "ord", "utf8::upgrade" (mais pas "utf8::downgrade"), et "chomp".

Également à partir de v5.8.1, le pseudo-descripteur de fichier "DATA" est traduit de l'encodage vers UTF-8.

Par exemple, vous pouvez écrire du code en EUC-JP comme suit :

my $Rakuda = "\xF1\xD1\xF1\xCC"; # Chameau en Kanji
             #<-car-><-car->   # 4 octets
s/\bCamel\b/$Rakuda/;

Et avec "use encoding "euc-jp"" en vigueur, c'est la même chose que ce code en UTF-8 :

my $Rakuda = "\x{99F1}\x{99DD}"; # deux Caractères Unicode
s/\bCamel\b/$Rakuda/;

Voir "EXEMPLE" ci-dessous pour un exemple plus complet.

À moins que "${^UNICODE}" (disponible à partir de v5.8.2) n'existe et ne soit non nul, les couches PerlIO de "STDIN" et "STDOUT" sont définies sur ":encoding(ENCNAME)". Par conséquent,

use encoding "euc-jp";
my $message = "Camel est le symbole de perl.\n";
my $Rakuda = "\xF1\xD1\xF1\xCC"; # Chameau en Kanji
$message =~ s/\bCamel\b/$Rakuda/;
print $message;

affichera

"\xF1\xD1\xF1\xCC est le symbole de perl.\n"

pas

"\x{99F1}\x{99DD} est le symbole de perl.\n"

Vous pouvez outrepasser cela en donnant des arguments supplémentaires ; voir ci-dessous.

Notez que "STDERR" NE SERA PAS modifié, quoi qu'il arrive.

Notez également que les descripteurs de fichiers non-STD restent inchangés. Utilisez "use open" ou "binmode" pour changer les couches de ceux-ci.

"use encoding ENCNAME, Filter=>1;"
Cela fonctionne comme ci-dessus, mais l'argument "Filter" avec une valeur non nulle provoque la traduction de l'intégralité du script, et pas seulement des littérales, de l'encodage vers UTF-8. Cela permet aux identifiants dans la source d'être également dans cet encodage. (Des problèmes peuvent survenir si l'encodage n'est pas un sur-ensemble de l'ASCII ; imaginez tous vos points-virgules étant traduits en quelque chose de différent.) On peut utiliser cette forme pour faire fonctionner 
${"\x{4eba}"}++

(Ceci est équivalent à "$humain++", où humain est un seul idéogramme Han).

Ceci signifie effectivement que votre code source se comporte comme s'il avait été écrit en UTF-8 avec "'use utf8"' en vigueur. Donc, même si votre éditeur ne supporte que Shift_JIS, par exemple, vous pouvez toujours essayer les exemples du Chapitre 15 de "Programming Perl, 3rd Ed.".

Cette option est significativement plus lente que l'autre.

"no encoding;"
Annule l'encodage du script. Les couches de "STDIN" et "STDOUT" sont réinitialisées à "":raw"" (le flux brut par défaut non traité d'octets).

OPTIONS

Définition individuelle de "STDIN" et/ou "STDOUT"

Les encodages de "STDIN" et "STDOUT" sont individuellement configurables par des paramètres du pragma :

use encoding 'euc-tw', STDIN => 'greek'  ...;

Dans ce cas, vous ne pouvez pas omettre le premier ENCNAME. "STDIN => undef" désactive complètement le transcodage I/O pour ce descripteur de fichier.

Le sous-pragma ":

locale"

À partir de la version 5.8.6, le nom d'encodage peut être ":locale". Cela signifie que l'encodage est pris depuis la locale actuelle, et non codé en dur par le pragma. Comme un script ne peut réellement être encodé que dans une seule encodage, cette option est dangereuse. Elle n'a de sens que si le script lui-même est écrit en ASCII, et que toutes les locales possibles qui seront utilisées lors de l'exécution du script sont des surensembles d'ASCII. Cela signifie que le script lui-même n'est pas modifié, mais que les canaux d'E/S se voient ajouter l'encodage spécifié, et que des opérations comme "chr" et "ord" utilisent cet

encodage.

ENCODAGES

Remarquez que seuls les littéraux (chaînes ou expressions rationnelles) ayant uniquement des points de code hérités sont affectés : si vous mélangez des données comme

ceci 
\x{100}\xDF
\xDF\x{100}

les données sont supposées être en (Latin 1 et) Unicode, et non dans votre encodage natif. En d'autres termes, cela correspondra en "grec"

: 
"\xDF" =~ /\x{3af}
/

mais cela ne correspondra

pas 
"\xDF\x{100}" =~ /\x{3af}\x{100}
/

car le "\xDF" (ISO 8859-7 GREEK SMALL LETTER IOTA WITH TONOS) à gauche ne sera pas mis à niveau en "\x{3af}" (Unicode GREEK SMALL LETTER IOTA WITH TONOS) à cause du "\x{100}" à gauche. Vous ne devriez pas mélanger vos données héritées et Unicode dans la même

chaîne.

Ce pragma affecte également l'encodage de la plage de points de code 0x80..0xFF : normalement, les caractères de cette plage restent des octets de huit bits (sauf s'ils sont combinés avec des caractères ayant des points de code 0x100 ou supérieurs, auquel cas tous les caractères doivent devenir encodés en UTF-8), mais si le pragma "encoding" est présent, même la plage 0x80..0xFF est toujours encodée en

UTF-8.

Après tout, le meilleur aspect de ce pragma est que vous n'avez pas à recourir à \x{

....} juste pour écrire votre nom dans un encodage natif. N'hésitez donc pas à mettr
e vos chaînes dans votre encodage entre guillemets et dans les expressions rationnelles.
