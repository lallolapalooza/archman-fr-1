ET PRÉCÉDENCE Les fichiers de configuration

sont

Les fichiers dans /etc/ remplacent les fichiers du même nom dans /run/, /usr/local/lib/ et /usr/lib/. Les fichiers dans /run/ remplacent les fichiers du même nom sous /usr/. Tous les fichiers

de

configuration sont triés par leur nom de fichier dans l'ordre lexicographique, quel que soit le répertoire dans lequel ils se trouvent. Si plusieurs fichiers spécifient la même option, l'entrée du fichier au nom lexicographiquement le plus tardif prendra la priorité. Ainsi, la configuration d'un fichier donné peut être soit remplacée complètement (en plaçant un fichier avec le même nom dans un répertoire de priorité supérieure), soit des paramètres individuels peuvent être modifiés (en spécifiant des paramètres supplémentaires dans un fichier avec un nom différent qui est ordonné plus tard). Les paquets

doivent

installer leurs fichiers de configuration dans /usr/lib/ (paquets de distribution) ou /usr/local/lib/ (installations locales) [1]. Les fichiers dans /etc/ sont réservés à l'administrateur local, qui peut utiliser cette logique pour remplacer les fichiers de configuration installés par les paquets du

fournisseur.

Il est recommandé de préfixer tous les noms de fichiers avec un nombre à deux chiffres et un tiret pour simplifier l'ordonnancement. Il est recommandé d'utiliser la plage 10-40 pour les fichiers de configuration dans /usr/ et la plage 60-90 pour les fichiers de configuration dans /etc/ et /run/, pour s'assurer que les fichiers de configuration locaux et transitoires auront toujours la priorité sur les fichiers de

En particulier, cela peut inclure des services qui exécutent des shells utilisateur. Par exemple dans l'environnement GNOME, l'émulateur de terminal graphique s'exécute en tant que l'unité utilisateur gnome-terminal-server.service, qui à son tour exécute le shell utilisateur, de sorte que ce shell héritera des variables d'environnement exportées par le gestionnaire utilisateur. Pour les autres instances du shell, non lancées par le gestionnaire de services utilisateur, l'environnement qu'elles héritent est défini par le programme qui les lance. Indice : en

général,

les unités systemd.service(5) contiennent des programmes lancés par systemd, et les unités systemd.scope(5) contiennent des programmes lancés par autre chose. Notez que ces fichiers n'affectent pas le bloc d'environnement du gestionnaire de services lui-même, mais exclusivement les blocs d'environnement transmis aux services qu'il gère. Les variables d'environnement définies de cette manière ne peuvent donc pas être utilisées pour influencer le comportement du gestionnaire de services. Afin d'apporter des modifications au

bloc

d'environnement du gestionnaire de services, l'environnement doit être modifié avant que le gestionnaire de services de l'utilisateur soit invoqué, par exemple depuis le gestionnaire de services système ou via un module PAM. Plus précisément, pour les connexions ssh, le service sshd(8) construit un environnement qui est une combinaison de variables transmises depuis le système distant et définies par sshd, voir la discussion dans ssh(1).
