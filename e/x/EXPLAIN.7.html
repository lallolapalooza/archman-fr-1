    FORMAT { TEXT | XML | JSON | YAML } DESCRIPTION Cette commande affiche le plan d'exécution que le planificateur
    PostgreSQL génère pour l'instruction fournie. Le plan d'exécution montre
    comment les table(s) référencées par l'instruction seront parcourues — par
    un simple balayage séquentiel, un balayage d'index, etc. — et si plusieurs
    tables sont référencées, quels algorithmes de jointure seront utilisés pour
    rassembler les lignes requises de chaque table d'entrée. La partie la plus critique de l'affichage est le coût d'exécution
    estimé de l'instruction, qui est l'estimation du planificateur de la durée
    d'exécution de l'instruction (mesurée en unités de coût arbitraires, mais
    qui conventionnellement signifient des récupérations de pages disque). En
    réalité, deux nombres sont affichés : le coût de démarrage avant que la
    première ligne puisse être retournée, et le coût total pour retourner
    toutes les lignes. Pour la plupart des requêtes, c'est le coût total qui
    compte, mais dans des contextes tels qu'une sous-requête dans EXISTS, le
    planificateur choisira le coût de démarrage le plus petit plutôt que le
    coût total le plus petit (puisque l'exécuteur s'arrêtera après avoir obtenu
    une ligne, de toute façon). De plus, si vous limitez le nombre de lignes à
    retourner avec une clause LIMIT, le planificateur fait une interpolation
    appropriée entre les coûts des points d'extrémité pour estimer quel plan est
    réellement le moins coûteux. L'option ANALYZE fait que l'instruction est réellement exécutée,
    et pas seulement planifiée. Ensuite, des statistiques réelles d'exécution
    sont ajoutées à l'affichage, incluant le temps total écoulé passé dans
    chaque nœud du plan (en millisecondes) et le nombre total de lignes qu'il a
    réellement retournées. C'est utile pour voir si les estimations du
    planificateur sont proches de la réalité. Important Gardez à l'esprit que l'instruction est réellement exécutée quand
    l'option ANALYZE est utilisée. Bien que EXPLAIN ignore toute sortie qu'un SELECT retournerait, les autres effets de bord de l'instruction se
    produiront comme d'habitude. Si vous souhaitez utiliser EXPLAIN ANALYZE sur une instruction INSE

SORTIES

Le résultat de la commande est une description textuelle du plan sélectionné pour la instruction, éventuellement annotée avec des statistiques d'exécution. La section 14.1 décrit les informations fournies.

NOTES

Afin de permettre au planificateur de requêtes de PostgreSQL de prendre des décisions raisonnablement éclairées lors de l'optimisation des requêtes, les données pg_statistic doivent être à jour pour toutes les tables utilisées dans la requête. Normalement, le démon autovacuum s'en chargera automatiquement. Mais si une table a récemment subi des changements substantiels dans son contenu, vous pourriez avoir besoin d'un ANALYZE manuel plutôt que d'attendre qu'autovacuum rattrape les changements.

Afin de mesurer le coût d'exécution de chaque nœud dans le plan d'exécution, l'implémentation actuelle de EXPLAIN ANALYZE ajoute un surcoût de profilage à l'exécution de la requête. Par conséquent, l'exécution de EXPLAIN ANALYZE sur une requête peut parfois prendre significativement plus de temps que l'exécution normale de la requête. Le montant du surcoût dépend de la nature de la requête, ainsi que de la plateforme utilisée. Le pire cas se produit pour les nœuds de plan qui en eux-mêmes nécessitent très peu de temps par exécution, et sur des machines qui ont des appels système relativement lents pour obtenir l'heure du jour.

EXEMPLES

Pour afficher le plan d'une requête simple sur une table avec une seule colonne entière et 10000 lignes :

EXPLAIN SELECT * FROM foo;
                       QUERY PLAN
---------------------------------------------------------
 Seq Scan on foo  (cost=0.00..155.00 rows=10000 width=4)
(1 row)

Voici la même requête, avec un format de sortie JSON :

EXPLAIN (FORMAT JSON) SELECT * FROM foo;
           QUERY PLAN
--------------------------------
 [                             +
   {                           +
     "Plan": {                 +
       "Node Type": "Seq Scan",+
       "Relation Name": "foo", +
       "Alias": "foo",         +
       "Startup Cost": 0.00,   +
       "Total Cost": 155.00,   +
       "Plan Rows": 10000,     +
       "Plan Width": 4         +
     }                         +
   }                           +
 ]
(1 row)

S'il existe un index et que nous utilisons une requête avec une condition WHERE indexable, EXPLAIN pourrait montrer un plan différent :

EXPLAIN SELECT * FROM foo WHERE i = 4;
                         QUERY PLAN
--------------------------------------------------------------
 Index Scan using fi on foo  (cost=0.00..5.98 rows=1 width=4)
   Index Cond: (i = 4)
(2 rows)

Voici la même requête, mais au format YAML :

EXPLAIN (FORMAT YAML) SELECT * FROM foo WHERE i='4';
          QUERY PLAN
-------------------------------
 - Plan:                      +
     Node Type: "Index Scan"  +
     Scan Direction: "Forward"+
     Index Name: "fi"         +
     Relation Name: "foo"     +
     Alias: "foo"             +
     Startup Cost: 0.00       +
     Total Cost: 5.98         +
     Plan Rows: 1             +
     Plan Width: 4            +
     Index Cond: "(i = 4)"
(1 row)

Le format XML est laissé comme exercice pour le lecteur.

Voici le même plan avec les estimations de coût supprimées :

EXPLAIN (COSTS FALSE) SELECT * FROM foo WHERE i = 4;
        QUERY PLAN
----------------------------
 Index Scan using fi on foo
   Index Cond: (i = 4)
(2 rows)

Voici un exemple de plan de requête pour une requête utilisant une fonction d'agrégation :

EXPLAIN SELECT sum(i) FROM foo WHERE i < 10;
                             QUERY PLAN
---------------------------------------------------------------------
 Aggregate  (cost=23.93..23.93 rows=1 width=4)
   ->  Index Scan using fi on foo  (cost=0.00..23.92 rows=6 width=4)
         Index Cond: (i < 10)
(3 rows)

Voici un exemple d'utilisation de EXPLAIN EXECUTE pour afficher le plan d'exécution d'une requête préparée :

PREPARE query(int, int) AS SELECT sum(bar) FROM test
    WHERE id > $1 AND id < $2
    GROUP BY foo;
EXPLAIN ANALYZE EXECUTE query(100, 200);
                                                       QUERY PLAN
-------------------------------------------------------------------------------------------------------------------------
 HashAggregate  (cost=10.77..10.87 rows=10 width=12) (actual time=0.043..0.044 rows=10.00 loops=1)
   Group Key: foo
   Batches: 1  Memory Usage: 24kB
   Buffers: shared hit=4
   ->  Index Scan using test_pkey on test  (cost=0.29..10.27 rows=99 width=8) (actual time=0.009..0.025 rows=99.00 loops=1)
         Index Cond: ((id > 100) AND (id < 200))
         Index Searches: 1
         Buffers: shared hit=4
 Planning Time: 0.244 ms
 Execution Time: 0.073 ms
(10 rows)

Bien sûr, les chiffres spécifiques montrés ici dépendent du contenu réel des tables impliquées. Notez également que les chiffres, et même la stratégie de requête sélectionnée, peuvent varier entre les versions de PostgreSQL en raison des améliorations du planificateur. De plus, la commande ANALYZE utilise un échantillonnage aléatoire pour estimer les statistiques de données ; par conséquent, il est possible que les estimations de coût changent après une nouvelle exécution de ANALYZE, même si la distribution réelle des données dans la table n'a pas changé.

Remarquez que l'exemple précédent a montré un plan « personnalisé » pour les valeurs de paramètres spécifiques données dans EXECUTE. Nous pourrions aussi souhaiter voir le plan générique pour une requête paramétrée, ce qui peut être fait avec GENERIC_PLAN :

EXPLAIN (GENERIC_PLAN)
  SELECT sum(bar) FROM test
    WHERE id > $1 AND id < $2
    GROUP BY foo;
                                  QUERY PLAN
-------------------------------------------------------------------------------
 HashAggregate  (cost=26.79..26.89 rows=10 width=12)
   Group Key: foo
   ->  Index Scan using test_pkey on test  (cost=0.29..24.29 rows=500 width=8)
         Index Cond: ((id > $1) AND (id < $2))
(4 rows)

Dans ce cas, l'analyseur a correctement inféré que $1 et $2 devraient avoir le même type de données que id, donc l'absence d'informations sur le type des paramètres de PREPARE n'était pas un problème. Dans d'autres cas, il pourrait être nécessaire de spécifier explicitement les types pour les symboles de paramètres, ce qui peut être fait en les convertissant, par exemple :

EXPLAIN (GENERIC_PLAN)
  SELECT sum(bar) FROM test
    WHERE id > $1::integer AND id < $2::integer
    GROUP BY foo;

COMPATIBILITÉ

Il n'existe aucune instruction EXPLAIN définie dans le standard SQL.

La syntaxe suivante était utilisée avant la version 9.0 de PostgreSQL et est toujours prise en charge :

EXPLAIN [ ANALYZE ] [ VERBOSE ] statement

Notez que dans cette syntaxe, les options doivent être spécifiées dans l'ordre exactement montré.
