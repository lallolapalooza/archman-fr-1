ExtUtils::MakeMaker::Tutorial(3perl) Guide de référence des programmeurs Perl ExtUtils::MakeMaker::Tutorial(3perl)

NOM

ExtUtils::MakeMaker::Tutorial - Écrire un module avec MakeMaker

RÉSUMÉ

use ExtUtils::MakeMaker;
WriteMakefile(
    NAME            => 'Your::Module',
    VERSION_FROM    => 'lib/Your/Module.pm'
);

DESCRIPTION

Ceci est un court tutoriel sur l'écriture d'un module simple avec MakeMaker. Ce n'est vraiment pas si difficile.

Le mantra

Les modules MakeMaker sont installés en utilisant ce simple mantra

perl Makefile.PL
make
make test
make install

Il existe beaucoup d'autres commandes et d'options, mais ce qui précède suffit.

La disposition

Les fichiers de base d'un module ressemblent à quelque chose comme ceci.

Makefile.PL
MANIFEST
lib/Your/Module.pm

C'est tout ce qui est strictement nécessaire. Il y a des fichiers supplémentaires que vous pourriez vouloir :

lib/Your/Other/Module.pm
t/some_test.t
t/some_other_test.t
Changes
README
INSTALL
MANIFEST.SKIP
bin/some_program
Makefile.PL
Lorsque vous exécutez Makefile.PL, il crée un Makefile. C'est tout l'intérêt de MakeMaker. Le Makefile.PL est un programme simple qui charge ExtUtils::MakeMaker et exécute la WriteMakefile() fonction pour générer un Makefile.

Voici un exemple de ce dont vous avez besoin pour un module simple :

use ExtUtils::MakeMaker;
WriteMakefile(
    NAME            => 'Your::Module',
    VERSION_FROM    => 'lib/Your/Module.pm'
);

NAME est l'espace de noms de premier niveau de votre module. VERSION_FROM est le fichier qui contient la $VERSION variable pour l'ensemble de la distribution. Généralement, c'est le même que votre module de premier niveau.

MANIFEST
Une simple liste de tous les fichiers de votre distribution. 
Makefile.PL
MANIFEST
lib/Your/Module.pm

Les chemins de fichiers dans un MANIFEST utilisent toujours les conventions Unix (c'est-à-dire /) même si vous n'êtes pas sur Unix.

Vous pouvez l'écrire à la main ou le générer avec 'make manifest'.

Voir ExtUtils::Manifest pour plus de détails.

lib/
C'est le répertoire où vont les fichiers .pm et .pod que vous souhaitez voir installés. Ils sont disposés selon l'espace de noms. Ainsi Foo::Bar est lib/Foo/Bar.pm.
t/
Les tests de vos modules vont ici. Chaque nom de fichier de test se termine par .t. Ainsi t/foo.t 'make test' exécutera ces tests.

Généralement, le t/ répertoire de test est plat, avec tous les fichiers de test situés directement à l'intérieur. Cependant, vous pouvez imbriquer des tests dans des sous-répertoires, par exemple :

t/foo/subdir_test.t

Pour ce faire, vous devez informer WriteMakefile() dans votre Makefile.PL fichier de la manière suivante :

test => {TESTS => 't/*.t t/*/*.t'}

Cela exécutera tous les tests dans t/, ainsi que tous les tests dans tous les sous-répertoires qui se trouvent sous t/. Vous pouvez imbriquer aussi profondément que cela a du sens pour votre projet. Ajoutez simplement une autre entrée dans la chaîne d'emplacement des tests. Par exemple, pour tester :

t/foo/bar/subdir_test.t

Vous utiliseriez la directive "test" suivante :

test => {TESTS => 't/*.t t/*/*/*.t'}

Notez que dans l'exemple ci-dessus, les tests dans le premier sous-répertoire ne seront pas exécutés. Pour exécuter tous les tests dans le sous-répertoire intermédiaire précédant celui où se trouvent les fichiers de test, vous devez le noter explicitement :

test => {TESTS => 't/*.t t/*/*.t t/*/*/*.t'}

Vous n'avez pas besoin de spécifier de caractères génériques si vous voulez seulement tester dans des sous-répertoires spécifiques. L'exemple suivant n'exécutera que les tests dans t/foo:

test => {TESTS => 't/foo/*.t'}

Les tests sont exécutés depuis le niveau supérieur de votre distribution. Ainsi à l'intérieur d'un test, vous feriez référence à ./lib pour entrer dans le répertoire lib, par exemple.

Changes
Un journal des modifications que vous avez apportées à ce module. La disposition est libre. Voici un exemple : 
1.01 Fri Apr 11 00:21:25 PDT 2003
    - thing() does some stuff now
    - fixed the wiggy bug in withit()
1.00 Mon Apr  7 00:57:15 PDT 2003
    - "Rain of Frogs" now supported
README
Une courte description de votre module, ce qu'il fait, pourquoi quelqu'un l'utiliserait et ses limitations. CPAN extrait automatiquement votre fichier README de l'archive et le rend disponible aux utilisateurs de CPAN, c'est la première chose qu'ils liront pour décider si votre module leur convient.
INSTALL
Instructions sur la façon d'installer votre module ainsi que toute dépendance. Informations suggérées à inclure ici : 
tout module supplémentaire requis pour l'utilisation
la version minimale de Perl requise
s'il ne fonctionne que sur certains systèmes d'exploitation
MANIFEST.SKIP
Un fichier rempli d'expressions régulières à exclure lors de l'utilisation de 'make manifest' pour générer le MANIFEST. Ces expressions régulières sont vérifiées contre chaque chemin de fichier trouvé dans la distribution (donc vous comparez avec "t/foo.t" et non "foo.t").

Voici un exemple :

~$          # ignore emacs and vim backup files
.bak$       # ignore manual backups
\#          # ignore CVS old revision files and emacs temp files

Puisque # peut être utilisé pour les commentaires, # doit être échappé.

MakeMaker est livré avec un MANIFEST.SKIP par défaut pour éviter des choses comme les répertoires de contrôle de version et les fichiers de sauvegarde. Spécifier le vôtre remplacera cette valeur par défaut.
