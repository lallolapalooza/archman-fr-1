ExtUtils::ParseXS(3perl) Guide de référence des programmeurs Perl ExtUtils::ParseXS(3perl)

NOM

ExtUtils::ParseXS - convertit le code XS Perl en code C

SYNOPSIS

use ExtUtils::ParseXS;
my $pxs = ExtUtils::ParseXS->new;
$pxs->process_file( filename => 'foo.xs' );
$pxs->process_file( filename => 'foo.xs',
                    output => 'bar.c',
                    'C++' => 1,
                    typemap => 'path/to/typemap',
                    hiertype => 1,
                    except => 1,
                    versioncheck => 1,
                    linenumbers => 1,
                    optimize => 1,
                    prototypes => 1,
                    die_on_error => 0,
                  );
# Interface historique non-OO utilisant un singleton :
use ExtUtils::ParseXS qw(process_file);
process_file( filename => 'foo.xs' );

DESCRIPTION

"ExtUtils::ParseXS" compilera le code XS en code C en intégrant les constructions nécessaires pour permettre aux fonctions C de manipuler les valeurs Perl et crée le code de liaison nécessaire pour permettre à Perl d'accéder à ces fonctions. Le compilateur utilise des typemaps pour déterminer comment associer les paramètres et variables des fonctions C aux valeurs Perl.

Le compilateur recherchera des fichiers typemap nommés typemap. Il utilisera le chemin de recherche suivant pour trouver les typemaps par défaut, avec le typemap le plus à droite ayant la priorité.

../../../typemap:../../typemap:../typemap:typemap

EXPORTATION

Aucune par défaut. process_file() et/ou report_error_count() peuvent être exportés sur demande. L'utilisation de l'interface fonctionnelle est déconseillée.

MÉTHODES

$pxs->new()
Retourne un nouvel objet analyseur/compilateur XS vide.
$pxs->process_file()
Cette méthode traite un fichier XS et envoie la sortie vers un fichier C. La méthode peut être appelée en tant que fonction (c'est l'interface historique) et utilisera alors un singleton comme invoquant.

Des paramètres nommés contrôlent la manière dont le traitement est effectué. Les paramètres suivants sont acceptés :

filename
Il s'agit du chemin complet du fichier XS à ouvrir et traiter. process_file() fera normalement un chdir() vers le nom de base du fichier.

Le nom de fichier peut être une référence à une chaîne, auquel cas les lignes de la chaîne forment le contenu du fichier « input », en utilisant le mécanisme standard "open $fh, '<', \$string" .

C++
Ajoute "extern "C"" au code C. La valeur par défaut est faux.
hiertype
Conserve "::" dans les noms de types afin que les types hiérarchiques C++ puissent être associés. La valeur par défaut est faux.
except
Ajoute des stubs de gestion des exceptions au code C. La valeur par défaut est faux.
typemap
Indique qu'un typemap fourni par l'utilisateur doit avoir la priorité sur les typemaps par défaut. Un typemap unique peut être spécifié sous forme de chaîne, ou plusieurs typemaps peuvent être spécifiés dans une référence de tableau, le dernier typemap ayant la priorité la plus élevée.
prototypes
Génère du code de prototype pour tous les xsubs. La valeur par défaut est faux.
versioncheck
S'assure à l'exécution que le fichier objet (dérivé du fichier ".xs" et les fichiers ".pm" ont le même numéro de version. La valeur par défaut est vrai.
linenumbers
Ajoute des directives "#line" à la sortie C afin que les messages d'erreur semblent provenir du fichier XS original. La valeur par défaut est vrai.
optimize
Active certaines optimisations. La seule optimisation actuellement concernée est l'utilisation de ciblespar le code C de sortie (voir perlguts). Ne pas optimiser peut ralentir considérablement le code généré, mais c'est la manière dont xsubpp" de 5.005 et antérieur fonctionnait. La valeur par défaut est d'optimiser.
inout
Active la reconnaissance des déclarations "IN", "OUT_LIST" et "INOUT_LIST" . La valeur par défaut est vrai.
argtypes
Active la reconnaissance de descriptions de signature de fonction de type ANSI. La valeur par défaut est vrai.
s
Note du mainteneur : Je n'ai aucune idée de ce que cela fait. Supprime les préfixes de fonction ?
die_on_error
Normalement, ExtUtils::ParseXS terminera le programme avec un exit(1) après avoir imprimé les détails de l'exception sur STDERR via (warn). Cela peut être gênant lorsqu'il est utilisé de manière programmatique et non via xsubpp, donc cette option peut être utilisée pour le faire mourir à la place en fournissant une valeur vraie. Lorsqu'elle n'est pas fournie, cette option prend par défaut la valeur de $ExtUtils::ParseXS::DIE_ON_ERROR qui à son tour vaut faux par défaut.
$pxs->report_error_count()
Cette méthode retourne le nombre d'erreurs [d'un certain type] rencontrées lors du traitement du fichier XS.

La méthode peut être appelée en tant que fonction (c'est l'interface historique) et utilisera alors un singleton comme invoquant.
