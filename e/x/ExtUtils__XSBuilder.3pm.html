NOM

ExtUtils::XSBuilder - Génération automatique de code de liaison XS pour Perl

DESCRIPTION

ExtUtils::XSBuilder est un ensemble de modules pour analyser des fichiers d'en-tête C et créer du code de liaison XS et de la documentation à partir de ceux-ci. Idéalement, cela permet de « créer » une interface vers une bibliothèque C sans coder une seule ligne. Comme aucune API C n'est idéale, certains ajustements sont nécessaires la plupart du temps. Ainsi, pour utiliser ce module, vous devez toujours être familier avec la programmation C et XS, mais cela vous évite beaucoup de travail ennuyeux et de copier-coller. De plus, lorsque l'API C change, la plupart du temps vous n'avez qu'à relancer XSBuilder pour obtenir votre nouvelle API Perl.

Le processus de création se déroule en étapes suivantes :

Dériver une classe de ExtUtils::XSBuilder::ParseSource

Cette classe doit redéfinir certaines méthodes pour indiquer à XSBuilder quels fichiers d'en-tête C analyser et quelques autres paramètres nécessaires. Vous devez au moins redéfinir la méthode "package" pour donner le nom du package que vous voulez créer, et soit la méthode "find_includes" qui retourne tous les fichiers d'en-tête C à analyser, soit la méthode "include_dirs" qui retourne une liste de tous les répertoires où chercher des fichiers d'en-tête C.

Bien sûr, il y a d'autres méthodes que vous pouvez redéfinir. Voir ExtUtils::XSBuilder::ParseSource pour une liste complète des méthodes redéfinissables.

Scanner les fichiers source

Si votre classe dérivée est appelée MyClass::ParseSource, vous lancez simplement l'analyse des sources avec

perl -MMyClass::ParseSource -e 'MyClass::ParseSource->run'

Vous pouvez aussi mettre cela dans un petit script pour faciliter l'utilisation, définir le chemin de librairie Perl, etc.

Pendant l'analyse des sources, XSBuilder crée un ensemble de tableaux qui contiennent les résultats de l'analyse. Si vous n'avez pas modifié les emplacements par défaut dans votre sous-classe, ces tableaux sont créés sous "xs/tables", suivi du nom du module retourné par la méthode "package" que vous avez créée. Là, vous trouverez quatre modules générés : "FunctionTable.pm", qui contient les déclarations de fonctions ; "StructureTable.pm", qui contient les structures ; "ConstantTable.pm", qui contient les constantes trouvées dans les fichiers d'en-tête ; et "CallbackTable.pm", qui contient les définitions pour les types de rappel (callbacks).

Comme l'analyse des sources peut prendre du temps, nous créons des tableaux intermédiaires et les transformons en code XS plus tard, plutôt que de créer le code XS directement. Comme nous sauvegardons le résultat, nous pouvons éviter de ré-analyser les fichiers source tant qu'ils ne changent pas.

Dériver une classe de ExtUtils::XSBuilder::WrapXS

La classe WrapXS est responsable de prendre les informations générées à la fois à partir des fichiers source et des fichiers de correspondance (voir ci-dessous) pour créer le code XS. Comme pour la classe ParseSource, vous devez redéfinir cette méthode avec votre propre implémentation pour indiquer à WrapXS quoi faire.

Voir ExtUtils::XSBuilder::WrapXS pour une liste des méthodes redéfinissables.

Créer les fichiers de correspondance

XSBuilder ne créera pas automatiquement de fonctions XS pour toutes les fonctions et structures C. Vous devez fournir des indications pour que les fichiers XS soient créés correctement. Les fichiers de correspondance sont le mécanisme pour fournir ces indications. Par défaut, les fichiers de correspondance se trouvent sous "xs/maps". Il y a quatre types de correspondance : "types", "functions", "structures", et "callbacks". Chaque fichier de correspondance est nommé avec un préfixe sélectionnable par l'utilisateur (par exemple "foo",) suivi d'un underscore, du nom du type de correspondance, et de l'extension de correspondance ".map". Par exemple, les indications pour les fonctions relatives au traitement des erreurs dans votre source peuvent être contenues dans un fichier de correspondance nommé "error_functions.map".

foo_types.map
Contient la correspondance des types C vers les classes Perl.
foo_functions.map
Contient la correspondance des fonctions C vers les fonctions Perl. Peut être utilisé pour réordonner les arguments, indiquer à XSBuilder quels arguments sont en fait des valeurs de retour et dans quel package Perl la fonction sera créée.
foo_structures.map
Contient la correspondance des structures C vers les classes Perl et définit pour quelles classes les méthodes d'accès doivent être créées. Vous pouvez aussi spécifier si vous voulez une méthode "new" pour la classe.
foo_callbacks.map
Contient la correspondance des fonctions de rappel C vers les fonctions de rappel Perl. Peut être utilisé pour réordonner les arguments, indiquer à XSBuilder quels arguments sont des valeurs de retour, et dans quel package Perl les fonctions seront créées.

Pour une description détaillée des formats de fichiers de correspondance, voir ci-dessous.

Pour avoir un point de départ, XSBuilder est capable de créer des fichiers de correspondance par défaut qui incluent simplement tous les types, fonctions et structures. Vous pouvez recréer les fichiers de correspondance à tout moment et XSBuilder ajoutera tous les éléments qui ne sont pas déjà dans les fichiers de correspondance.

Copiez d'abord le fichier _types.map du répertoire xsbuilder vers votre répertoire de correspondances. Ce fichier contient la correspondance standard pour quelques types de base.

Si, par exemple, votre classe dérivée est appelée MyClass::WrapXS, vous lancez simplement la création/mise à jour des fichiers de correspondance avec

perl -MMyClass::WrapXS -e 'MyClass::WrapXS->checkmaps(" ")'

L'argument de checkmaps fournit un caractère à préfixer à la première colonne des nouvelles entrées de correspondance. Si vous ne passez pas d'argument à checkmaps, aucun fichier de correspondance n'est écrit, et checkmaps ne fera que comparer ce qui manque. (Vous devez imprimer le résultat d'une manière ou d'une autre, par exemple en utilisant Data::Dumper). Vous pouvez aussi mettre cela dans un petit script pour faciliter l'utilisation, définir le chemin de librairie Perl, etc.

Après avoir créé vos correspondances par défaut, vous devez éditer le fichier "xs/maps/new_type.map" , qui contient tous les types trouvés dans la source. Ajoutez un pipe ("|") suivi du nom de la classe ou du type, par exemple

int                 | IV
struct request_rec  | Apache::RequestRec

.

Créer les fichiers XS

Maintenant nous pouvons créer le code. En exécutant

perl -MMyClass::WrapXS -e 'MyClass::WrapXS->run'

XSBuilder créera les fichiers XS, pm et Makefile.PL pour chaque module mentionné dans les fichiers de correspondance. Le résultat est placé comme une hiérarchie de répertoires sous WrapXS. Pour contrôler le contenu des fichiers "Makefile.PL" et "pm" , vous pouvez redéfinir les méthodes "makefilepl_text" et "pm_text" . Vous pouvez inclure du code supplémentaire dans les fichiers XS en écrivant un fichier d'inclusion qui est inclus en haut du fichier XS. Ce fichier peut contenir des fonctions auxiliaires qui ne peuvent pas être générées automatiquement. Les fichiers doivent être placés sous le répertoire "xs" , avec le chemin et le nom corrects. Par exemple, pour avoir un fichier d'en-tête inclus pour le module Apache::DAV, créez un fichier nommé "xs/Apache/DAV/Apache__DAV.h". La même chose peut être faite pour l'inclusion dans le fichier pm. En suivant l'exemple ci-dessus, le nom du fichier serait "xs/Apache/DAV/DAV_pm".

Format des fichiers de correspondance

Pour tous les fichiers de correspondance, les lignes vides sont ignorées et les lignes commençant par un "#" sont traitées comme des commentaires et sont aussi ignorées.

Fichier de correspondance des types

Contient la correspondance entre les types C et les classes Perl.

Le format est le nom du type C suivi du nom de la classe Perl ou du spécificateur de type XS, séparés par un "|". Exemple :

int                 | IV
struct request_rec  | Apache::RequestRec

Si vous avez une classe Perl avec un espace de noms à un seul niveau (par ex. Apache), vous devez le suffixer avec deux deux-points (par ex. "Apache::"). Lorsqu'un typedef et une structure portent le même nom, les structures doivent être écrites avec le préfixe "struct " (par ex. "struct foo".) De plus, vous pouvez donner l'identifiant pour le typemap si vous avez besoin d'une conversion spéciale et un ou plusieurs autres noms pour la structure :

struct request_rec  | Apache::RequestRec | T_APACHEOBJ | r

Un cinquième paramètre facultatif spécifie que les données doivent être copiées lorsqu'elles sont assignées à un membre de structure et sélectionne la manière dont la mémoire est allouée :

char *   | PV | | | strdup

Le code réel pour l'allocation de mémoire est fourni à l'intérieur de la map de structure, par exemple :

MALLOC=strdup:$dest = ($type)ap_pstrdup(obj -> pool, $src)
MALLOC=malloc:ap_palloc(obj -> pool, $src, sizeof($type)) ; memcpy($dest,$src,sizeof($type))

Cela donne deux façons d'allouer de la mémoire et de copier les données dedans. Le cinquième paramètre dans le typemap sélectionne laquelle de ces deux doit être utilisée. $src, $dest et $type sont remplacés par la source, la destination et le type. "obj" est un pointeur vers la structure C.

Types spéciaux

Chaîne, PV et PVnull
Une chaîne est représentée en C comme un pointeur vers une plage de caractères terminée par un caractère nul. En Perl, cela est appelé "PV" (pointer value). Lors de la conversion d'un Perl "undef" vers une chaîne C, Perl le convertit par défaut en une chaîne vide. Bien que cela soit sûr, ce n'est pas toujours ce qui est requis, car de nombreuses interfaces C traitent NULL comme un cas spécial. Pour cette raison le type "PVnull" est introduit, qui convertit "undef" en "NULL" et "NULL" en "undef".

Pour le faire fonctionner, vous avez besoin de la ligne suivante dans votre fichier de typemap :

PVnull          | PVnull | | | strdup

Maintenant, vous pouvez définir n'importe quel type, membre de structure ou argument de fonction comme type "PVnull".

Fichier map Functions

Contient la correspondance entre les fonctions C et les fonctions Perl. Cela peut être utilisé pour réordonner les arguments, indiquer à XSBuilder quels arguments sont des valeurs de retour, et dans quel paquet Perl la fonction sera créée.

Il y a quelques directives qui affectent les correspondances de fonctions qui suivent. Chaque directive peut apparaître dans le fichier plus d'une fois.

MODULE
le nom du module (nom de fichier) où la fonction devrait être définie, par ex. 
MODULE=Apache::Connection

définira les fonctions qui suivent dans des fichiers nommés Apache/Connection.{pm,xs}

PACKAGE
Le nom du paquet dans lequel les fonctions sont définies. Si non défini, PACKAGE prend par défaut la valeur de MODULE. Une valeur de 'guess' indique que le nom du paquet devrait être deviné en se basant sur le premier argument trouvé qui correspond à une classe Perl. Repli sur le préfixe (ap_ -> Apache, apr_ -> APR).
PREFIX
Le préfixe à retirer des fonctions C lors de la création des stubs XS. Par défaut, la valeur de PACKAGE, convertie en convention de nommage C. Par exemple, 
PREFIX=APR::Base64

retirera "apr_base64_" des fonctions C. Si le préfixe ne correspond pas, par défaut "ap_" ou "apr_".

NOTE : Vous devez avoir au moins une "MODULE" définition, sinon toutes les fonctions seront ignorées.

Le format des entrées est :

C function name | dispatch function name (dispatch argspec) | argspec | Perl alias

Le "dispatch function name" (la fonction C qui est réellement appelée) prend par défaut le nom de la fonction C. Si le nom de la fonction de dispatch est juste un préfixe (mpxs_, MPXS_), le "C function name" y est ajouté. Le type de retour peut être spécifié avant le "C function name", et prend par défaut la "return_type" dans le "{foo}::FunctionTable" module généré par le module "ParseSource" .

Le "dispatch argspec" est facultatif. S'il est fourni, il peut être utilisé pour passer des paramètres différents à la fonction de dispatch qu'à la fonction XS. Si le nom de fonction commence par "DEFINE_", une nouvelle fonction est définie (pour définir des fonctions qui ne sont pas analysées depuis la source). "argspec" doit être fourni. "DEFINE_" n'est pas inclus dans le nom de fonction généré.

Le "argspec" prend par défaut les arguments dans "{foo}::FunctionTable", tel que généré par le module "ParseSource" . Les types d'arguments peuvent être spécifiés pour remplacer ceux dans "{foo}::FunctionTable". Des valeurs par défaut peuvent aussi être spécifiées, par ex. arg=default_value

Par exemple :
ap_get_client_block | mpxs_ | r, SV *:buffer, bufsiz
ap_setup_client_block | | r, read_policy=REQUEST_CHUNKED_ERROR
ap_make_array | ap_make_array(r->pool, nelts, elt_size) | request_rec *:r, nelts, elt_size

argspec de '...' indique passthru, appelant la fonction avec

(aTHX_ I32 items, SP **sp, SV **MARK)

Pour marquer un argument comme étant seulement en retour, vous pouvez le préfixer avec < par ex.

dav_open_lockdb | | r, ro, <lockdb

sera appelé comme ($error reçoit la valeur de retour de la fonction C )

($error, $lockdb) = $r -> open_lockdb (0) ;

L'argument de retour (par ex. lockdb) sera toujours passé par adresse à la fonction.

L'alias de fonction, s'il est défini, sera créé dans le "PACKAGE"courant.

Les noms de fonctions sur les lignes qui ne commencent pas par un caractère de mot ou une seule espace sont ignorés. Les noms de fonctions peuvent être préfixés avec les symboles suivants :

'!' => 'désactivé ou pas encore implémenté',
'~' => 'implémenté mais pas auto-généré',
'-' => 'probablement jamais disponible pour Perl',
'>' => '"privé" pour votre bibliothèque C',
'?' => 'non classifié',

Fichier map Structures

Contient la correspondance entre les structures C et les classes Perl et définit les membres pour lesquels des méthodes d'accès doivent être créées. Une "new" méthode peut être spécifiée, si désiré. Le format ressemble à ce qui suit :

<struct_name>
  member1
  member2
  new
</struct_name>

Un nom de module facultatif peut être donné, pour spécifier dans quel module le code devrait être placé. Pour placer la structure dans My::Module, par exemple, spécifiez :

<struct_name MODULE=My::Module>

Pour tous les membres listés ici, XSBuilder générera une méthode d'accès pour lire et écrire son contenu. Si vous voulez nommer la méthode d'accès Perl différemment du membre C, vous pouvez écrire

cMemberValue | member_value | type

cela correspondra le membre de structure "cMemberValue" à la fonction d'accès "member_value". Par défaut, on utilise le même nom en Perl qu'en C. En troisième argument, vous pouvez donner un nom de type. Cela prend par défaut le type de la variable. Cela peut être utilisé pour spécifier un type différent, pour des besoins de conversion spéciaux. (par ex. PV versus PVnull) Si vous donnez le "new" membre, XSBuilder créera une méthode new pour cette classe, qui peut être utilisée pour créer une nouvelle instance et l'initialiser avec des données.

Fichier map Callbacks

Le format des entrées est :

C function name | argspec

Le contenu est le même que pour la map des fonctions, mais il contient les callbacks.

Méthodes générées supplémentaires

Pour les structures, XSBuilder générera deux méthodes supplémentaires : "new", et "init_callbacks".

new ($initialvalue)

Avec "new" vous pouvez créer un nouvel objet Perl pour une structure C. Optionnellement, vous pouvez passer soit une référence à un hash avec des données initiales, soit un autre objet, dont les données seront copiées dans le nouvel objet.

init_callbacks

"init_callbacks" devrait être appelé lors de l'initialisation de l'objet. Il remplira tous les membres de callback d'une structure avec des pointeurs qui provoquent un appel de méthode vers l'objet, lorsque le callback est appelé depuis C.

Vous pouvez l'appeler soit avec

$obj -> init_callbacks

ou

MyModule -> init_callbacks ($obj) ;

Callbacks

Un callback qui fait partie d'une structure provoquera un appel à la méthode portant le même nom que le membre de structure, préfixée avec "cb_". Par exemple, si vous avez un membre de structure nommé "open", alors la méthode Perl "cb_open" sera appelée chaque fois que le code C appelle le callback.

Si vous voulez appeler le callback vous-même, vous devez appeler la méthode qui est appelée comme le membre de structure, par ex. "open".

NOTE : Vousavez besoin d'appeler "init_callbacks" lors de l'initialisation de votre méthode pour pouvoir appeler les rappels.
