Cette commande traite ses arguments comme la spécification d'un ou plusieurs sous-processus à exécuter. Les arguments prennent la forme d'un pipeline de shell standard où chaque arg devient un mot d'une commande, et chaque commande distincte devient un sous-processus. Le résultat de la commande est la sortie standard du dernier sous-processus du pipeline, interprétée en utilisant l'encodage système ; pour utiliser un autre encodage (notamment pour les données binaires), le pipeline doit être ouvert, configuré et lu

explicitement.

Si les arguments initiaux à exec commencent par - alors ils sont traités comme des commutateurs de ligne de commande et ne font pas partie de la spécification du pipeline. Les commutateurs suivants sont actuellement pris en charge

si

Si le nom contient une barre oblique alors il doit faire référence à un exécutable accessible depuis le répertoire courant. Aucune expansion « glob » ni d'autres substitutions de type shell ne sont effectuées sur les arguments des

commandes.

Notez que l'échappement actuel respectivement le quoting des arguments pour windows fonctionne uniquement avec les exécutables utilisant CommandLineToArgv, la bibliothèque CRT ou similaire, ainsi qu'avec les fichiers batch windows (à l'exception du retour à la ligne, voir ci-dessous). Bien que ce soit l'algorithme d'échappement commun, mais, en fait, la façon dont l'exécutable analyse la ligne de commande (respectivement la divise en arguments uniques) est

déterminante.

Malheureusement, il n'y a actuellement aucun moyen de fournir des retours à la ligneligne caractère au sein d'un argument des fichiers batch (.cmd ou .bat) ou du processeur de commandes (cmd.exe /c), car cela provoque la troncature de la ligne de commande (ainsi que de la chaîne d'arguments) au premier caractère de nouvelle ligne. Mais cela fonctionne correctement avec un exécutable (en utilisant CommandLineToArgv, etc.).

Mise entre guillemets des arguments

Les arguments de la commande exec sont mappés aux arguments du programme appelé. Des guillemets supplémentaires (") sont automatiquement ajoutés autour des arguments si nécessaire. Les caractères spéciaux sont échappés en insérant des barres obliques inverses.

L'environnement MS-Windows exécute les programmes mentionnés dans les arguments et les fichiers batch appelés (conspec) remplacent les variables d'environnement, ce qui peut avoir des effets secondaires (vulnérabilités) ou casser toute mise entre guillemets déjà existante (par exemple, si la variable d'environnement contient un caractère spécial tel qu'un "). Les exemples sont :

% exec my-echo.cmd {test&whoami}
  test
  mylogin
% exec my-echo.cmd "ENV X:%X%"
  ENV X: CONTENT OF X
Le formatage suivant est effectué automatiquement sur chaque élément d'argument pour éviter l'exécution de sous-programmes : tout argument contenant un caractère spécial (&, |, ^, <, >, !, (, ), (, %) est automatiquement placé entre guillemets ("). Tout guillemet de données est échappé par l'insertion de barres obliques inverses.

La résolution automatique des variables d'environnement à l'aide de "%var%" est critique, mais présente plus d'avantages que de dangers et n'est pas échappée.

TCL 8.6.10 a affiné cette mise entre guillemets en ajoutant une mise entre guillemets pour les guillemets de données et une mise entre guillemets individuelle de "%". Cela peut casser les scripts existants qui dépendent de la fonctionnalité de remplacement des variables d'environnement. Ainsi, la mise entre guillemets individuelle de "%" a été supprimée dans TCL 8.6.14, car les variables d'environnement sont considérées comme plus utiles qu'un problème. Une solution avec des paramètres de commande est envisagée pour une future version de TCL.

Le widget de texte de la console Tk ne fournit pas de véritables capacités d'IO standard. Sous Tk, lors de la redirection depuis l'entrée standard, toutes les applications verront une fin de fichier immédiate ; les informations redirigées vers la sortie standard ou l'erreur standard seront ignorées.

Les barres obliques avant ou arrière sont acceptées comme séparateurs de chemin pour les arguments des commandes Tcl. Lors de l'exécution d'une application, le nom du chemin spécifié pour l'application peut également contenir des barres obliques avant ou arrière comme séparateurs de chemin. Gardez à l'esprit, cependant, que la plupart des applications Windows n'acceptent les arguments avec des barres obliques avant que comme délimiteurs d'options et les barres obliques arrière uniquement dans les chemins. Les arguments d'une application qui spécifient un nom de chemin avec des barres obliques avant ne seront pas automatiquement convertis pour utiliser le caractère barre oblique inverse. Si un argument contient des barres obliques avant comme séparateur de chemin, il peut ou peut ne pas être reconnu comme un nom de chemin, en fonction du programme.

Deux barres obliques avant ou arrière ou plus consécutives dans un chemin font référence à un chemin réseau. Par exemple, une simple concaténation du répertoire racine c:/ avec un sous-répertoire /windows/system donnera c://windows/system (deux barres obliques ensemble), ce qui fait référence au point de montage appelé system sur la machine appelée windows (et c:/ est ignoré), et n'est pas équivalent à c:/windows/system, qui décrit un répertoire sur l'ordinateur actuel. La commande file join doit être utilisée pour concaténer les composants du chemin.

Notez qu'il existe deux types généraux d'applications console Win32 :

[1]
CLI — Interface en ligne de commande, échange stdio simple. netstat.exe par exemple.
[2]
TUI — Interface utilisateur en mode texte, toute application qui accède à l'API de la console pour effectuer des actions telles que le mouvement du curseur, la définition de la couleur du texte, la détection des pressions sur les touches et le mouvement de la souris, etc. Un exemple serait telnet.exe de Windows 2000. Ces types d'applications ne sont pas courants dans un environnement Windows, mais existent.

exec ne fonctionnera pas bien avec les applications TUI en l'absence de console, comme c'est le cas lors du lancement d'applications sous wish. Il est souhaitable de masquer et détacher les applications console. C'est une limitation intentionnelle car exec souhaite communiquer via des pipes. L'extension Expect aborde ce problème lors de la communication avec une application TUI.

Lors de la tentative d'exécution d'une application, exec recherche d'abord le nom tel qu'il a été spécifié. Ensuite, dans l'ordre, .com, .exe, .bat et .cmd sont ajoutés à la fin du nom spécifié et il recherche le nom plus long. Si un nom de répertoire n'a pas été spécifié dans le nom de l'application, les répertoires suivants sont automatiquement recherchés dans l'ordre lors de la tentative de localisation de l'application :

  • Le répertoire à partir duquel l'exécutable Tcl a été chargé.
  • Le répertoire courant.
  • Le répertoire système Windows 32 bits.
  • Le répertoire personnel Windows.
  • Les répertoires listés dans le PATH.

Afin d'exécuter des commandes intégrées au shell telles que dir et copy, l'appelant doit préfixer la commande souhaitée avec “cmd.exe /c ” car les commandes intégrées ne sont pas implémentées à l'aide d'exécutables.

Unix (y compris macOS)
La commande exec est entièrement fonctionnelle et fonctionne comme décrit.

EXEMPLES UNIX

Voici quelques exemples d'utilisation de la commande exec sur Unix. Pour exécuter un programme simple et obtenir son résultat :

exec uname -a

TRAVAILLER AVEC DES RÉSULTATS NON NULS

Pour exécuter un programme qui peut retourner un résultat non nul, vous devriez encapsuler l'appel à exec dans catch et vérifier le contenu de l'option de retour -errorcode en cas d'erreur :

set status 0
if {[catch {exec grep foo bar.txt} results options]} {
    set details [dict get $options -errorcode]
    if {[lindex $details 0] eq "CHILDSTATUS"} {
        set status [lindex $details 2]
    } else {
        # Autre erreur ; la régénérer pour que l'appelant la gère
        return -options $options -level 0 $results
    }
}
C'est plus facile à écrire en utilisant la commande try, car cela simplifie le piégeage de types d'erreurs spécifiques. Ceci est fait en utilisant du code comme ceci : 
try {
    set results [exec grep foo bar.txt]
    set status 0
} trap CHILDSTATUS {results options} {
    set status [lindex [dict get $options -errorcode] 2]
}

TRAVAILLER AVEC DES ARGUMENTS ENTRE GUILLEMETS

Lors de la traduction d'une commande depuis une invocation de shell Unix, il faut faire attention au fait que les caractères d'apostrophe n'ont pas de signification spéciale pour Tcl. Ainsi :

awk '{sum += $1} END {print sum}' numbers.list
serait traduit en quelque chose comme : 
exec awk {{sum += $1} END {print sum}} numbers.list

TRAVAILLER AVEC LE GLOBBING

Si vous convertissez des invocations impliquant le globbing du shell, vous devez vous rappeler que Tcl ne gère pas le globbing ni l'expansion des éléments en plusieurs arguments par défaut. Au lieu de cela, vous devriez écrire des choses comme ceci :

exec ls -l {*}[glob *.tcl]

TRAVAILLER AVEC DES FRAGMENTS DE SCRIPTS SHELL FOURNIS PAR L'UTILISATEUR

Une technique utile peut être d'exposer aux utilisateurs d'un script la capacité de spécifier un fragment de script shell à exécuter qui recevra des données sur l'entrée standard produites par le programme Tcl. C'est une technique courante pour utiliser le programme lpr pour l'impression. La manière la plus simple de procéder est de passer le script de l'utilisateur à son shell pour traitement, car cela évite beaucoup de complexité liée à l'analyse d'autres langages.

set lprScript [obtenir de l'utilisateur...]
set postscriptData [générer d'une manière ou d'une autre...]
exec $env(SHELL) -c $lprScript << $postscriptData

EXEMPLES WINDOWS

Voici quelques exemples d'utilisation de la commande exec sous Windows. Pour démarrer une instance de notepad éditant un fichier sans attendre que l'utilisateur finisse d'éditer le fichier :

exec notepad myfile.txt &

Pour imprimer un fichier texte à l'aide de notepad :

exec notepad /p myfile.txt

TRAVAILLER AVEC DES PROGRAMMES CONSOLE

Si un programme appelle d'autres programmes, comme c'est fréquent avec les compilateurs, vous devrez peut-être recourir à des fichiers batch pour masquer les fenêtres de console qui apparaissent parfois :

exec cmp.bat somefile.c -o somefile

Avec le fichier cmp.bat ressemblant à ceci :

@gcc %*

ou à une autre variante utilisant des paramètres simples :

@gcc %1 %2 %3 %4 %5 %6 %7 %8 %9

TRAVAILLER AVEC LES COMMANDES INTÉGRÉES

Parfois, il faut être prudent, car différents programmes peuvent avoir le même nom et se trouver dans le PATH. Il peut alors arriver que taper une commande à l'invite DOS trouve un programme différent que la même commande exécutée via exec. Ceci est dû aux différences (documentées) de comportement entre exec et les fichiers batch DOS.

En cas de doute, utilisez la commande auto_execok : elle retournera le chemin complet du programme tel qu'il est vu par la commande exec. Cela s'applique en particulier si vous souhaitez exécuter des commandes « internes » comme dir à partir d'un script Tcl (si vous souhaitez simplement lister des noms de fichiers, utilisez la commande glob). Pour ce faire, utilisez ceci :

exec {*}[auto_execok dir] *.tcl
