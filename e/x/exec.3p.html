EXEC(3P) Manuel du programmeur POSIX EXEC(3P)

PROLOGUE

Cette page manuelle fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page manuelle Linux correspondante pour plus de détails sur le comportement de Linux), ou l'interface peut ne pas être implémentée sur Linux.

NOM

environ, execl, execle, execlp, execv, execve, execvp, fexecve — exécuter un fichier

SYNOPSIS

#include <unistd.h>
extern char **environ;
int execl(const char *path, const char *arg0, ... /*, (char *)0 */);
int execle(const char *path, const char *arg0, ... /*,
    (char *)0, char *const envp[]*/);
int execlp(const char *file, const char *arg0, ... /*, (char *)0 */);
int execv(const char *path, char *const argv[]);
int execve(const char *path, char *const argv[], char *const envp[]);
int execvp(const char *file, char *const argv[]);
int fexecve(int fd, char *const argv[], char *const envp[]);

DESCRIPTION

La famille de fonctions exec doit remplacer l'image du processus actuel par une nouvelle image de processus. La nouvelle image doit être construite à partir d'un fichier exécutable régulier appelé le fichier image du nouveau processus. Il ne doit pas y avoir de retour après un execréussi, car l'image du processus appelant est recouverte par la nouvelle image de processus.

La fonction fexecve() doit être équivalente à la fonction execve() sauf que le fichier à exécuter est déterminé par le descripteur de fichier fd au lieu d'un chemin d'accès. La position du fichier de fd est ignorée.

Lorsqu'un programme en langage C est exécuté à la suite d'un appel à l'une des fonctions de la famille exec , il doit être entré comme un appel de fonction en langage C comme suit :

int main (int argc, char *argv[]);

où argc est le nombre d'arguments et argv est un tableau de pointeurs de caractères vers les arguments eux-mêmes. De plus, la variable suivante, qui doit être déclarée par l'utilisateur si elle doit être utilisée directement :

extern char **environ;

est initialisée comme un pointeur vers un tableau de pointeurs de caractères vers les chaînes d'environnement. Les tableaux argv et environ sont chacun terminés par un pointeur nul. Le pointeur nul terminant le tableau argv n'est pas compté dans argc.

Les applications peuvent changer tout l'environnement en une seule opération en assignant à la variable environ un pointeur vers un tableau de pointeurs de caractères vers les nouvelles chaînes d'environnement. Après avoir assigné une nouvelle valeur à environ, les applications ne doivent pas compter sur le fait que les nouvelles chaînes d'environnement resteront partie de l'environnement, car un appel à getenv(), putenv(), setenv(), unsetenv(), ou toute fonction dépendant d'une variable d'environnement peut, en remarquant que environ a changé, copier les chaînes d'environnement vers un nouveau tableau et assigner à environ un pointeur vers celui-ci.

Toute application qui modifie directement les pointeurs vers lesquels la variable environ pointe a un comportement indéfini.

Les applications multi-thread conformes ne doivent pas utiliser la variable environ pour accéder ou modifier une variable d'environnement pendant qu'un autre thread modifie simultanément une variable d'environnement. Un appel à toute fonction dépendant d'une variable d'environnement doit être considéré comme une utilisation de la variable environ pour accéder à cette variable d'environnement.

Les arguments spécifiés par un programme avec l'une des fonctions exec doivent être transmis à la nouvelle image de processus dans les arguments correspondants de main().

L'argument path pointe vers un chemin d'accès qui identifie le fichier image du nouveau processus.

L'argument file est utilisé pour construire un chemin d'accès qui identifie le fichier image du nouveau processus. Si l'argument file contient un caractère <slash>, l'argument file doit être utilisé comme chemin d'accès pour ce fichier. Sinon, le préfixe de chemin pour ce fichier est obtenu en cherchant dans les répertoires passés comme variable d'environnement PATH (voir le volume Définitions de base de POSIX.1‐2017, Chapitre 8, Variables d'environnement). Si cette variable d'environnement n'est pas présente, les résultats de la recherche sont définis par l'implémentation.

Il existe deux façons distinctes dont le contenu du fichier image du processus peut causer l'échec de l'exécution, distinguées par le fait que errno est défini à [ENOEXEC] ou [EINVAL] (voir la section ERREURS). Dans les cas où les autres membres de la famille de fonctions exec échoueraient et définiraient errno à [ENOEXEC], les fonctions execlp() et execvp() doivent exécuter un interpréteur de commandes et l'environnement de la commande exécutée doit être comme si le processus avait invoqué l'utilitaire sh en utilisant execl() comme suit :

execl(<shell path>, arg0, file, arg1, ..., (char *)0);

où <chemin du shell> est un chemin d'accès non spécifié pour l'utilitaire sh , file est le fichier image du processus, et pour execvp(), où arg0, arg1, et ainsi de suite correspondent aux valeurs passées à execvp() dans argv[0], argv[1], et ainsi de suite.

Les arguments représentés par arg0,... sont des pointeurs vers des chaînes de caractères terminées par un caractère nul. Ces chaînes doivent constituer la liste d'arguments disponible pour la nouvelle image de processus. La liste est terminée par un pointeur nul. L'argument arg0 doit pointer vers une chaîne de nom de fichier associée au processus démarré par l'une des fonctions exec .

L'argument argv est un tableau de pointeurs de caractères vers des chaînes terminées par un caractère nul. L'application doit s'assurer que le dernier membre de ce tableau est un pointeur nul. Ces chaînes doivent constituer la liste d'arguments disponible pour la nouvelle image de processus. La valeur dans argv[0] doit pointer vers une chaîne de nom de fichier associée au processus démarré par l'une des fonctions exec .

L'argument envp est un tableau de pointeurs de caractères vers des chaînes terminées par un caractère nul. Ces chaînes doivent constituer l'environnement pour la nouvelle image de processus. Le tableau envp est terminé par un pointeur nul.

Pour les formes ne contenant pas de pointeur envp (execl(), execv(), execlp(), et execvp()), l'environnement pour la nouvelle image de processus doit être pris depuis la variable externe environ dans le processus appelant.

Le nombre d'octets disponibles pour les listes combinées d'arguments et d'environnement du nouveau processus est {ARG_MAX}. Il est défini par l'implémentation si les terminateurs nuls, les pointeurs et/ou les octets d'alignement sont inclus dans ce total.

Les descripteurs de fichier ouverts dans l'image du processus appelant doivent rester ouverts dans la nouvelle image de processus, sauf ceux dont l'attribut de fermeture à l'exec FD_CLOEXEC est défini. Pour les descripteurs de fichier qui restent ouverts, tous les attributs de la description de fichier ouverte restent inchangés. Pour tout descripteur de fichier fermé pour cette raison, les verrous de fichier sont supprimés à la suite de la fermeture comme décrit dans close(). Les verrous qui ne sont pas supprimés par la fermeture des descripteurs de fichier restent inchangés.

Si les descripteurs de fichier 0, 1 ou 2 seraient autrement fermés après un appel réussi à l'une des fonctions de la famille exec , les implémentations peuvent ouvrir un fichier non spécifié pour le descripteur de fichier dans la nouvelle image de processus. Si un utilitaire standard ou une application conforme est exécuté avec le descripteur de fichier 0 non ouvert en lecture ou avec le descripteur de fichier 1 ou 2 non ouvert en écriture, l'environnement dans lequel l'utilitaire ou l'application est exécuté doit être considéré comme non conforme, et par conséquent l'utilitaire ou l'application pourrait ne pas se comporter comme décrit dans cette norme.

Les flux de répertoire ouverts dans l'image du processus appelant doivent être fermés dans la nouvelle image de processus.

L'état de l'environnement en virgule flottante dans le thread initial de la nouvelle image de processus doit être défini à la valeur par défaut.

L'état des descripteurs de conversion et des descripteurs de catalogue de messages dans la nouvelle image de processus est indéfini.

Pour la nouvelle image de processus, l'équivalent de :

setlocale(LC_ALL, "C")

doit être exécuté au démarrage.

Les signaux définis sur l'action par défaut (SIG_DFL) dans l'image du processus appelant doivent être définis sur l'action par défaut dans la nouvelle image de processus. À l'exception de SIGCHLD, les signaux définis pour être ignorés (SIG_IGN) par l'image du processus appelant doivent être définis pour être ignorés par la nouvelle image de processus. Les signaux définis pour être interceptés par l'image du processus appelant doivent être définis sur l'action par défaut dans la nouvelle image de processus. (voir <signal.h> ). Si le signal SIGCHLD est défini comme ignoré par l'image de processus appelante, il n'est pas spécifié si le signal SIGCHLD est défini comme ignoré ou comme action par défaut dans la nouvelle image de processus. EXEMPLES

Utilisation de execl()

L'exemple suivant exécute la commande ls , en spécifiant le chemin de l'exécutable (/bin/ls) et en utilisant des arguments fournis directement à la commande pour produire une sortie en colonne unique.

#include <unistd.h>
int ret;
...
ret = execl ("/bin/ls", "ls", "-1", (char *)0);

Utilisation de execle()

L'exemple suivant est similaire à Utilisation de execl(). De plus, il spécifie l'environnement pour le nouveau fichier image de processus à l'aide de l' argument env .

#include <unistd.h>
int ret;
char *env[] = { "HOME=/usr/home", "LOGNAME=home", (char *)0 };
...
ret = execle ("/bin/ls", "ls", "-l", (char *)0, env);

Utilisation de execlp()

L'exemple suivant recherche l'emplacement de la commande ls parmi les répertoires spécifiés par la variable d'environnement PATH .

#include <unistd.h>
int ret;
...
ret = execlp ("ls", "ls", "-l", (char *)0);

Utilisation de execv()

L'exemple suivant passe des arguments à la commande ls dans le tableau cmd .

#include <unistd.h>
int ret;
char *cmd[] = { "ls", "-l", (char *)0 };
...
ret = execv ("/bin/ls", cmd);

Utilisation de execve()

L'exemple suivant passe des arguments à la commande ls dans le tableau cmd , et spécifie l'environnement pour le nouveau fichier image de processus à l'aide de l' argument env .

#include <unistd.h>
int ret;
char *cmd[] = { "ls", "-l", (char *)0 };
char *env[] = { "HOME=/usr/home", "LOGNAME=home", (char *)0 };
...
ret = execve ("/bin/ls", cmd, env);

Utilisation de execvp()

L'exemple suivant recherche l'emplacement de la commande ls parmi les répertoires spécifiés par la variable d'environnement PATH , et passe des arguments à la commande ls dans le tableau cmd .

#include <unistd.h>
int ret;
char *cmd[] = { "ls", "-l", (char *)0 };
...
ret = execvp ("ls", cmd);

UTILISATION PAR LES APPLICATIONS

L'état des descripteurs de conversion et des descripteurs de catalogue de messages dans le nouveau fichier image de processus étant indéfini, les applications conformes ne doivent pas compter sur leur utilisation et doivent les fermer avant d'appeler l'une des fonctions exec .

Les applications qui nécessitent une locale POSIX autre que la locale globale par défaut dans le nouveau fichier image de processus doivent appeler setlocale() avec les paramètres appropriés.

Lors de l'affectation d'une nouvelle valeur à la variable environ , les applications doivent s'assurer que l'environnement vers lequel elle pointera contient au moins ce qui suit :

1.
Toutes les variables définies par l'implémentation nécessaires à celle-ci pour fournir un environnement conforme. Voir l'entrée _CS_V7_ENV dans <unistd.h> et confstr() pour plus de détails.
2.
Une valeur pour PATH qui trouve les versions conformes de toutes les utilitaires standard avant toute autre version.

La même contrainte s'applique au tableau envp passé à execle() ou execve(), afin de garantir que le nouveau fichier image de processus est invoqué dans un environnement conforme.

Les applications ne doivent pas exécuter de programmes dont le descripteur de fichier 0 n'est pas ouvert en lecture ou dont le descripteur de fichier 1 ou 2 n'est pas ouvert en écriture, car cela pourrait faire que le programme exécuté se comporte mal. Afin de ne pas transmettre ces descripteurs de fichier à un programme exécuté, les applications ne doivent pas simplement les fermer, mais doivent les rouvrir sur, par exemple, /dev/null. Certaines implémentations peuvent les rouvrir automatiquement, mais les applications ne doivent pas compter sur le fait que cela soit fait.

Si une application souhaite effectuer un test de somme de contrôle du fichier exécuté avant de l'exécuter, le fichier devra être ouvert avec la permission de lecture pour effectuer le test de somme de contrôle.

Étant donné que la permission d'exécution est vérifiée par fexecve(), la description de fichier fd n'a pas besoin d'avoir été ouverte avec l'indicateur O_EXEC. Cependant, si le fichier à exécuter refuse la permission de lecture et d'écriture pour le processus préparant à faire l' exec, la seule façon de fournir le descripteur fd à fexecve() sera d'utiliser l'indicateur O_EXEC lors de l'ouverture de fd. Dans ce cas, l'application ne pourra pas effectuer un test de somme de contrôle car elle ne pourra pas lire le contenu du fichier.

Notez que lorsqu'un descripteur de fichier est ouvert en mode O_RDONLY, O_RDWR ou O_WRONLY, le descripteur de fichier peut être utilisé pour lire, lire et écrire, ou écrire le fichier, respectivement, même si le mode du fichier change après que le fichier a été ouvert. L'utilisation du mode d'ouverture O_EXEC est différente ; fexecve() ignorera le mode qui a été utilisé lorsque le descripteur de fichier a été ouvert et l' exec échouera si le mode du fichier associé à fd n'accorde pas la permission d'exécution au processus appelant au moment où fexecve() est appelée.

JUSTIFICATION

Les propositions initiales exigeaient que la valeur de argc passée à main() soit « un ou plus ». Cela était motivé par la même exigence dans les projets de la norme ISO C. En fait, les implémentations historiques ont passé une valeur de zéro lorsque aucun argument n'est fourni à l'appelant des fonctions exec . Cette exigence a été supprimée de la norme ISO C et a ensuite été supprimée de ce volume de POSIX.1‐2017 également. La formulation, en particulier l'utilisation du mot devrait, exige qu'une application POSIX Strictement Conforme passe au moins un argument à la fonction exec , garantissant ainsi que argc soit un ou plus lorsqu'elle est invoquée par une telle application. En fait, c'est une bonne pratique, car de nombreuses applications existantes référencent argv[0] sans d'abord vérifier la valeur de argc.

L'exigence pour une application POSIX Strictement Conforme stipule également que la valeur passée en premier argument soit une chaîne de nom de fichier associée au processus qui est démarré. Bien que certaines applications existantes passent un chemin plutôt qu'une chaîne de nom de fichier dans certaines circonstances, une chaîne de nom de fichier est plus généralement utile, car l'utilisation courante de argv[0] est pour l'impression de diagnostics. Dans certains cas, le nom de fichier passé n'est pas le nom de fichier réel du fichier ; par exemple, beaucoup d'implémentations de l'utilitaire login utilisent la convention de préfixer un <hyphen-minus> ('‐') au nom de fichier réel, ce qui indique à l'interpréteur de commandes invoqué qu'il s'agit d'un « shell de connexion ».

Notez également que les utilitaires test et [ nécessitent des chaînes spécifiques pour l' argument argv[0] afin d'avoir un comportement déterministe sur toutes les implémentations.

Historiquement, il y a eu deux façons dont les implémentations peuvent exec des scripts shell.

Une implémentation historique courante est que les fonctions execl(), execv(), execle() et execve() retournent une erreur [ENOEXEC] pour tout fichier non reconnaissable comme exécutable, y compris un script shell. Lorsque les fonctions execlp() et execvp() rencontrent un tel fichier, elles supposent que le fichier est un script shell et invoquent un interpréteur de commandes connu pour interpréter de tels fichiers. Cela est désormais exigé par POSIX.1‐2008. Ces implémentations de execvp() et execlp() ne donnent l'erreur [ENOEXEC] que dans le rare cas d'un problème avec le fichier exécutable de l'interpréteur de commandes. En raison de ces implémentations, l'erreur [ENOEXEC] n'est pas mentionnée pour execlp() ou execvp(), bien que les implémentations puissent toujours donner cela.

Une autre manière dont certaines implémentations historiques gèrent les scripts shell consiste à reconnaître les deux premiers octets du fichier comme la chaîne de caractères "#!" et à utiliser le reste de la première ligne du fichier comme nom de l'interpréteur de commandes à exécuter.

Une source potentielle de confusion notée par les développeurs de la standard concerne la manière dont le contenu d'un fichier d'image de processus affecte le comportement de la famille de fonctions exec . La description suivante détaille les actions entreprises :

1.
Si le fichier d'image de processus est un exécutable valide (dans un format exécutable et valide et avec les privilèges appropriés) pour ce système, alors le système exécute le fichier.
2.
Si le fichier d'image de processus a les privilèges appropriés et est dans un format exécutable mais non valide pour ce système (tel qu'un binaire reconnu pour une autre architecture), alors c'est une erreur et errno est défini à [EINVAL] (voir plus bas la RATIONALE sur [EINVAL]).
3.
Si le fichier d'image de processus a les privilèges appropriés mais n'est pas autrement reconnu :
a.
S'il s'agit d'un appel à execlp() ou execvp(), alors ils invoquent un interpréteur de commandes en supposant que le fichier d'image de processus est un script shell.
b.
S'il ne s'agit pas d'un appel à execlp() ou execvp(), alors une erreur se produit et errno est défini à [ENOEXEC].

Les applications qui n'ont pas besoin d'accéder à leurs arguments peuvent utiliser la forme :

main(void)

telle que spécifiée dans la norme ISO C. Cependant, l'implémentation fournira toujours les deux arguments argc et argv, même s'ils ne sont pas utilisés.

Certaines implémentations fournissent un troisième argument à main() appelé envp. Celui-ci est défini comme un pointeur vers l'environnement. La norme ISO C spécifie l'invocation de main() avec deux arguments, les implémentations doivent donc prendre en charge les applications écrites de cette manière. Étant donné que ce volume de POSIX.1‐2017 définit la variable globale environ, qui est également fournie par les implémentations historiques et peut être utilisée partout où envp pourrait être utilisé, il n'y a aucun besoin fonctionnel pour l'argument envp . Les applications devraient utiliser la fonction getenv() plutôt que d'accéder directement à l'environnement via envp ou environ. Les implémentations sont tenues de prendre en charge la séquence d'appel à deux arguments, mais cela n'interdit pas à une implémentation de prendre en charge envp comme troisième argument optionnel.

Ce volume de POSIX.1‐2017 spécifie que les signaux définis sur SIG_IGN restent définis sur SIG_IGN, et que la nouvelle image de processus hérite du masque de signaux du thread qui a appelé exec dans l'ancienne image de processus. Cela est cohérent avec les implémentations historiques et permet certaines fonctionnalités utiles, telles que la commande nohup . Cependant, il convient de noter que de nombreuses applications existantes supposent à tort qu'elles démarrent avec certains signaux définis sur l'action par défaut et/ou non bloqués. En particulier, les applications écrites avec un modèle de signal plus simple qui n'inclut pas le blocage des signaux, tel que celui de la norme ISO C, peuvent ne pas se comporter correctement si elles sont invoquées avec certains signaux bloqués. Par conséquent, il est préférable de ne pas bloquer ni ignorer les signaux à travers les execsans raison explicite de le faire, et surtout de ne pas bloquer les signaux à travers les execde programmes arbitraires (ne coopérant pas étroitement).

Les fonctions exec enregistrent toujours la valeur de l'UID effectif et du GID effectif du processus à la fin de l' exec, que le bit set-user-ID ou set-group-ID du fichier d'image de processus soit défini ou non.

L'affirmation selon laquelle argv[] et envp[] sont des constantes est incluse pour rendre explicite aux futurs rédacteurs de liaisons de langage que ces objets sont complètement constants. En raison d'une limitation de la norme ISO C, il n'est pas possible d'énoncer cette idée en C standard. Spécifier deux niveaux de const-qualification pour les paramètres argv[] et envp[] des fonctions exec pourrait sembler être le choix naturel, étant donné que ces fonctions ne modifient ni le tableau de pointeurs ni les caractères vers lesquels les fonctions pointent, mais cela interdirait le code correct existant. Au lieu de cela, seul le tableau de pointeurs est noté comme constant. Le tableau de compatibilité d'affectation pour dst=src dérivé de la norme ISO C résume la compatibilité :

dst: char *[] const char *[] char *const[] const char *const[]
src:
char *[] VALID — VALID —
const char *[] — VALID — VALID
char * const [] — — VALID —
const char *const[] — — — VALID

Puisque tout le code existant a un type source correspondant à la première ligne, la colonne qui donne le plus grand nombre de combinaisons valides est la troisième colonne. La seule autre possibilité est la quatrième colonne, mais son utilisation nécessiterait un cast sur les arguments argv ou envp . Il est regrettable que la quatrième colonne ne puisse pas être utilisée, car la déclaration qu'un non-expert utiliserait naturellement serait celle de la deuxième ligne.

La norme ISO C et ce volume de POSIX.1‐2017 ne sont pas en conflit quant à l'utilisation de environ, mais certaines implémentations historiques de environ peuvent causer un conflit. Tant que environ est traité de la même manière qu'un point d'entrée (par exemple, fork()), il est conforme aux deux normes. Une bibliothèque peut contenir fork(), mais s'il existe un fork() fourni par l'utilisateur, c'est ce fork() qui est privilégié et aucun problème n'en découle. La situation est similaire pour environ: la définition dans ce volume de POSIX.1‐2017 doit être utilisée s'il n'y a pas de environ fourni par l'utilisateur pour prendre le dessus. Au moins trois implémentations sont connues pour exister qui résolvent ce problème.

E2BIG
La limite {ARG_MAX} s'applique non seulement à la taille de la liste d'arguments, mais aussi à la somme de celle-ci et de la taille de la liste d'environnement.
EFAULT
Certains systèmes historiques renvoient [EFAULT] plutôt que [ENOEXEC] lorsque le nouveau fichier d'image de processus est corrompu. Ils sont non conformes.
EINVAL
Cette condition d'erreur a été ajoutée à POSIX.1‐2008 pour permettre à une implémentation de détecter les fichiers exécutables générés pour différentes architectures et d'indiquer cette situation à l'application. Les implémentations historiques des shells, execvp(), et execlp() qui rencontrent une erreur [ENOEXEC] exécuteront un shell en supposant que le fichier est un script shell. Cela ne produira pas l'effet désiré lorsque le fichier est un exécutable valide pour une architecture différente. Une implémentation peut maintenant choisir d'éviter ce problème en renvoyant [EINVAL] lorsqu'un exécutable valide pour une architecture différente est rencontré. Certaines implémentations historiques renvoient [EINVAL] pour indiquer que l'argument path contient un caractère avec le bit de poids fort défini. Les développeurs de la standard ont choisi de s'écarter de la pratique historique pour les raisons suivantes :
1.
La nouvelle utilisation de [EINVAL] fournira une certaine utilité à la communauté des utilisateurs.
2.
L'utilisation historique de [EINVAL] n'est pas acceptable dans un environnement d'exploitation internationalisé.
ENAMETOOLONG

Puisque le chemin du fichier peut être construit en prenant des éléments de la variable PATH et en les combinant avec le nom de fichier, la condition d'erreur [ENAMETOOLONG] pourrait également être atteinte de cette manière.
ETXTBSY
System V renvoie cette erreur lorsque le fichier exécutable est actuellement ouvert en écriture par un processus. Ce volume de POSIX.1‐2017 ne requiert ni ne prohibe ce comportement.

D'autres systèmes (tels que System V) peuvent renvoyer [EINTR] à partir de exec. Cela n'est pas traité par ce volume de POSIX.1‐2017, mais les implémentations peuvent avoir une fenêtre entre l'appel à exec et le moment où un signal pourrait faire en sorte que l'un des appels exec renvoie avec [EINTR].

Une déclaration explicite concernant l'environnement en virgule flottante (tel que défini dans l'en-tête <fenv.h> ) a été ajoutée pour clarifier que l'environnement en virgule flottante est défini sur ses valeurs par défaut lorsqu'un appel à l'une des fonctions exec réussit. Les exigences relatives à l'héritage ou à la définition par défaut pour les autres fonctions de démarrage de processus et de thread sont couvertes par des déclarations plus génériques dans leurs descriptions et peuvent être résumées comme suit :

posix_spawn()
Défini par défaut.
fork()
Hériter.
pthread_create()
Hériter.

La présente page de manuel a été générée par le projet man-pages et peut différer de celle d'autres systèmes.

NAME

execve - exécuter un programme

SYNOPSIS

#include <unistd.h>

int execve(const char *filename, char *const argv[], char *const envp[]);

DESCRIPTION

La fonction execve () exécute le programme spécifié par filename.

La fonction execve () remplace le processus courant par un nouveau processus. Le nouveau processus est chargé à partir du fichier exécutable spécifié par filename. Cette opération est réussie uniquement si le nouveau processus est chargé et commence à s'exécuter. Comme il n'y a pas de retour en cas de succès, les routines de terminaison (comme exit () ou exit_group ()) et les gestionnaires de signaux ne sont pas appelés.

filename doit être le chemin d'un fichier exécutable régulier. Le processus courant est remplacé, mais l'ID du processus et l'ID du parent restent inchangés.

Les arguments du nouveau programme sont fournis par le tableau de chaînes de caractères argv, qui doit se terminer par un pointeur NULL. La convention est que le premier élément de ce tableau (argv[0]) pointe vers une chaîne qui contient le nom du fichier associé à l'exécutable ; il est traditionnellement utilisé par les programmes pour leur propre nom. L'appelant doit fournir un tableau d'arguments valide, qui ne peut pas être NULL.

L'environnement du nouveau programme est fourni par le tableau de chaînes de caractères envp, qui doit également se terminer par un pointeur NULL. La convention est que chaque chaîne est de la forme clé=valeur. L'appelant doit fournir un tableau d'environnement valide, qui ne peut pas être NULL.

Si filename se termine par un suffixe spécial qui indique son type de fichier (par exemple, .sh pour un script shell), le noyau peut lancer un interpréteur approprié pour exécuter le fichier. La manière exacte dont les fichiers interprétés sont gérés est dépendante de l'implémentation, mais elle suit généralement la spécification du format de fichier interprété. Dans le cas des scripts shell, cela signifie qu'une ligne commençant par "#!" spécifie l'interpréteur (par exemple, "#!/bin/sh").

Lorsque execve () est appelée, le noyau essaie de localiser le fichier exécutable spécifié par filename. Le chemin filename peut être absolu ou relatif au répertoire de travail courant du processus appelant.

Le noyau effectue une série de vérifications avant d'exécuter le fichier, notamment :

  • Le fichier existe-t-il ?
  • Le fichier est-il un fichier exécutable régulier ?
  • Le processus appelant a-t-il les permissions d'exécution sur le fichier ?
  • Le fichier est-il dans un format exécutable reconnu par le système ?

Si le fichier est un fichier script shell ou d'un autre type interprété, le noyau recherche le line shebang (`#!`) au début du fichier pour trouver l'interpréteur.

Le processus courant est complètement remplacé par le nouveau programme. L'espace d'adressage du processus courant est libéré et remplacé par le nouvel exécutable. Les descripteurs de fichiers ouverts restent ouverts, sauf s'ils sont marqués pour être fermés sur exec (par exemple, avec fcntl ()). Les signaux configurés pour être ignorés sont ignorés, mais les signaux avec des gestionnaires par défaut ou des gestionnaires installés sont réinitialisés à leurs valeurs par défaut.

La taille de la pile du nouveau processus est déterminée par le système d'exploitation et l'exécutable lui-même.

La fonction execve () a des effets de bord sur les descripteurs de fichiers ouverts. S'ils ne sont pas marqués avec FD_CLOEXEC, ils restent ouverts et sont disponibles pour le nouveau processus. Les descripteurs de fichiers qui ont été ouverts dans le processus avant l'appel à execve () seront toujours disponibles dans le nouveau processus, avec les mêmes numéros de descripteur.

Les fichiers ouverts par le processus appelant restent ouverts dans le processus exécuté, sauf s'ils sont explicitement marqués pour être fermés à l'exécution. Les descripteurs de fichiers non marqués FD_CLOEXEC sont hérités par le nouveau processus.

RETURN VALUE

Si execve () réussit, elle ne retourne jamais au programme appelant. Si elle retourne, une erreur s'est produite.

ERRORS

Les erreurs seront définies dans errno. Les valeurs courantes incluent :

Les erreurs suivantes peuvent se produire :

EACCES
Une partie d'un composant du chemin n'a pas les permissions de recherche (X), ou le fichier lui-même n'est pas ouvert en lecture (R), ou le fichier n'est pas exécutable (X).
E2BIG
Trop d'arguments.
EFAULT
filename ou l'un des pointeurs dans argv ou envp pointe en dehors de l'espace d'adressage accessible du processus.
ELOOP
Trop de liens symboliques ont été résolus dans filename.
ENAMETOOLONG
filename est trop long.
ENOENT
Un composant du chemin filename n'existe pas ou filename est une chaîne vide.
ENOMEM
Pas assez de mémoire pour allouer le nouveau processus.
ENOTDIR
Un composant du chemin filename n'est pas un répertoire.
ETXTBUSY
Le fichier spécifié par filename est ouvert en écriture par un autre processus.
EPERM
Le fichier spécifié par filename a le bit SUID ou SGID activé, mais le fichier n'est pas un exécutable régulier.
UNKNOWN
Le format du fichier exécutable est invalide ou indéterminé.

EXAMPLES

Lancer le programme ls avec des arguments :

char *args[] = { "/bin/ls", "-l", NULL };
char *env[] = { "PATH=/bin", NULL };

execve("/bin/ls", args, env);

APPLICATION USAGE

L'utilisation de execve () est généralement déconseillée car elle est considérée comme une interface de bas niveau. Les fonctions de la famille exec comme execl (), execv (), execlp (), et execvp () sont généralement préférées car elles sont plus faciles à utiliser et à gérer.

RATIONALE

La fonction execve () est l'appel système sous-jacent qui implémente la sémantique de exec. Elle permet d'exécuter un fichier qui a été vérifié comme étant le fichier prévu. Il est possible de vérifier activement le fichier en lisant à partir du descripteur de fichier et de s'assurer que le fichier n'est pas échangé contre un autre entre la lecture et l'exécution. Alternativement, une fonction comme openat () peut être utilisée pour ouvrir un fichier qui a été trouvé en lisant le contenu d'un répertoire à l'aide de readdir ().
