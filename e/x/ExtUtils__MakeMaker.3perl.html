Attributs PREFIX et LIB

PREFIX et LIB peuvent être utilisés pour définir plusieurs attributs INSTALL* en une seule fois. Voici un exemple pour installer dans votre répertoire personnel.

# Les utilisateurs Unix, PREFIX=~ fonctionne bien
perl Makefile.PL PREFIX=/chemin/vers/votre/repertoire/personnel

Cela installera tous les fichiers du module sous votre répertoire personnel, avec les pages de manuel et les bibliothèques allant à un endroit approprié (généralement ~/man et ~/lib). La manière dont l'emplacement exact est déterminé est compliquée et dépend de la manière dont votre Perl a été configuré. INSTALL_BASE fonctionne plus comme ce que d'autres systèmes de construction appellent « prefix » que PREFIX, et nous vous recommandons d'utiliser celui-ci à la place.

Une autre manière de spécifier de nombreux répertoires INSTALL avec un seul paramètre est LIB.

perl Makefile.PL LIB=~/lib

Cela installera les fichiers indépendants de l'architecture du module dans ~/lib, et les fichiers dépendants de l'architecture dans ~/lib/$archname.

Notez que dans les deux cas, l'expansion du tilde est effectuée par MakeMaker, pas par perl par défaut, ni par make.

Les conflits entre les paramètres LIB, PREFIX et les différents arguments INSTALL* sont résolus de telle sorte que :

  • la définition de LIB remplace toute définition de INSTALLPRIVLIB, INSTALLARCHLIB, INSTALLSITELIB, INSTALLSITEARCH (et elles ne sont pas affectées par PREFIX) ;
  • sans LIB, la définition de PREFIX remplace la partie initiale $Config{prefix} de ces arguments INSTALL*, même si ces derniers sont explicitement définis (mais sont définis pour commencer toujours par $Config{prefix}).

Si l'utilisateur a les privilèges de superutilisateur et ne travaille pas sur AFS ou ses apparentés, alors les valeurs par défaut pour INSTALLPRIVLIB, INSTALLARCHLIB, INSTALLSCRIPT, etc. seront appropriées, et cette invocation sera la meilleure :

perl Makefile.PL;
make;
make test
make install

make install écrit par défaut une certaine documentation de ce qui a été fait dans le fichier "$(INSTALLARCHLIB)/perllocal.pod". Cette fonctionnalité peut être contournée en appelant make pure_install.

Liaison statique d'un nouveau binaire Perl

Une extension construite avec les étapes ci-dessus est prête à être utilisée sur les systèmes prenant en charge le chargement dynamique. Sur les systèmes qui ne prennent pas en charge le chargement dynamique, toute extension nouvellement créée doit être liée avec les ressources disponibles. MakeMaker prend en charge le processus de liaison en créant des cibles appropriées dans le Makefile chaque fois qu'une extension est construite. Vous pouvez invoquer la section correspondante du makefile avec

make perl

Cela produit un nouveau binaire perl dans le répertoire courant avec toutes les extensions liées qui peuvent être trouvées dans INST_ARCHLIB, SITELIBEXP et PERL_ARCHLIB. Pour ce faire, MakeMaker écrit un nouveau Makefile ; sur UNIX, ceci est appelé Makefile.aperl (peut dépendre du système). Si vous voulez forcer la création d'un nouveau perl, il est recommandé de supprimer ce Makefile.aperl, afin que les répertoires soient à nouveau parcourus à la recherche de bibliothèques liables.

Le binaire peut être installé dans le répertoire où perl réside normalement sur votre machine avec

make inst_perl

Pour produire un binaire perl avec un nom différent de "perl", dites soit

perl Makefile.PL MAP_TARGET=myperl
make myperl
make inst_perl

ou dites

perl Makefile.PL
make myperl MAP_TARGET=myperl
make inst_perl MAP_TARGET=myperl

Dans tous les cas, on vous proposera l'invocation correcte de la cible "inst_perl" qui installe le nouveau binaire dans INSTALLBIN.

make inst_perl écrit par défaut une certaine documentation de ce qui a été fait dans le fichier "$(INSTALLARCHLIB)/perllocal.pod". Ceci peut être contourné en appelant make pure_inst_perl.

Avertissement : la cible inst_perl: écrasera très probablement votre binaire perl existant. À utiliser avec précaution !

Parfois, vous pourriez vouloir construire un perl lié statiquement bien que votre système prenne en charge le chargement dynamique. Dans ce cas, vous pouvez définir explicitement le type de liaison avec l'invocation de Makefile.PL ou make :

perl Makefile.PL LINKTYPE=static    # recommandé

ou

make LINKTYPE=static                # fonctionne sur la plupart des systèmes

Détermination des emplacements de la bibliothèque Perl et d'installation

MakeMaker a besoin de savoir, ou de deviner, où certaines choses sont localisées. Surtout INST_LIB et INST_ARCHLIB (où mettre les fichiers pendant l'exécution de make(1) ), PERL_LIB et PERL_ARCHLIB (où lire les modules existants), et PERL_INC (fichiers d'en-tête et "libperl*.*").

Les extensions peuvent être construites soit en utilisant le contenu de l'arborescence du répertoire source de perl, soit à partir de la bibliothèque perl installée. La manière recommandée est de construire les extensions après avoir exécuté 'make install' sur perl lui-même. Vous pouvez le faire dans n'importe quel répertoire de votre disque dur qui n'est pas en dessous de l'arborescence source de perl. Le support pour les extensions sous le répertoire ext de la distribution perl n'est bon que pour les extensions standard qui accompagnent perl.

Si une extension est construite sous le répertoire "ext/" de la source de perl, alors MakeMaker définira PERL_SRC automatiquement (par exemple, "../.."). Si PERL_SRC est défini et que l'extension est reconnue comme une extension standard, alors les autres variables ont par défaut les valeurs suivantes :

PERL_INC     = PERL_SRC
PERL_LIB     = PERL_SRC/lib
PERL_ARCHLIB = PERL_SRC/lib
INST_LIB     = PERL_LIB
INST_ARCHLIB = PERL_ARCHLIB

Si une extension est construite à l'écart de la source de perl, alors MakeMaker laissera PERL_SRC non défini et utilisera par défaut la copie installée de la bibliothèque perl. Les autres variables ont par défaut les valeurs suivantes :

PERL_INC     = $archlibexp/CORE
PERL_LIB     = $privlibexp
PERL_ARCHLIB = $archlibexp
INST_LIB     = ./blib/lib
INST_ARCHLIB = ./blib/arch

Si perl n'a pas encore été installé, PERL_SRC peut être défini sur la ligne de commande comme montré dans la section précédente.

Quel répertoire dépendant de l'architecture ?

Si vous ne voulez pas conserver les valeurs par défaut pour les macros INSTALL*, MakeMaker vous aide à minimiser la saisie nécessaire : la relation habituelle entre INSTALLPRIVLIB et INSTALLARCHLIB est déterminée par Configure au moment de la compilation de perl. MakeMaker prend en charge l'utilisateur qui définit INSTALLPRIVLIB. Si INSTALLPRIVLIB est défini, mais pas INSTALLARCHLIB, alors MakeMaker définit ce dernier comme étant le même sous-répertoire de INSTALLPRIVLIB que Configure a décidé pour les homologues dans %Config, sinon il prend par défaut la valeur de INSTALLPRIVLIB. La même relation s'applique pour INSTALLSITELIB et INSTALLSITEARCH.

MakeMaker vous donne beaucoup plus de liberté que nécessaire pour configurer des variables internes et obtenir différents résultats. Il est utile de mentionner que make(1) vous permet également de configurer la plupart des variables utilisées dans le Makefile. Mais dans la majorité des situations, cela ne sera pas nécessaire, et ne devrait être fait que si l'auteur d'un paquet le recommande (ou si vous savez ce que vous faites).

Utilisation des attributs et des paramètres

Les attributs suivants peuvent être spécifiés comme arguments à WriteMakefile() ou comme paires NOM=VALEUR sur la ligne de commande. Les attributs qui sont devenus disponibles avec des versions ultérieures de MakeMaker sont indiqués.

Une liste lisible par ordinateur des attributs reconnus est disponible sous %ExtUtils::MakeMakers::Recognized_Att_Keys, prise en charge depuis la version 7.72. Vous pouvez vérifier si un paramètre particulier est pris en charge par la version actuelle d'ExtUtils::MakeMaker en vérifiant s'il existe dans le hachage.

Afin de maintenir la portabilité des attributs avec les versions plus anciennes de MakeMaker, vous pourriez vouloir utiliser App::EUMM::Upgrade avec votre "Makefile.PL".

Description en une ligne du module. Sera incluse dans le fichier PPD.

Tableau de chaînes contenant le nom (et l'adresse e-mail) du ou des auteurs du paquet. Utilisé dans les fichiers Meta CPAN (META.yml ou META.json) et les fichiers PPD (Perl Package Description) pour PPM (Perl Package Manager).

Utilisé lors de la création de fichiers PPD pour les paquets binaires. Il peut être défini sur un chemin complet ou relatif, ou une URL vers l'archive binaire pour une architecture particulière. Par exemple :

MakeMaker peut exécuter des programmes pour générer des fichiers pour vous au moment de la construction. Par défaut, tout fichier nommé *.PL (sauf Makefile.PL et Build.PL) dans le répertoire de premier niveau sera supposé être un programme Perl et sera exécuté en passant son propre nom de base en argument. Ce nom de base est en fait une cible de construction, et il y a l'intention, mais pas l'exigence, que le fichier *.PL crée le fichier passé en argument. Par exemple... 
perl foo.PL foo

Ce comportement peut être surchargé en fournissant votre propre ensemble de fichiers à rechercher. PL_FILES accepte une référence de hash, la clé étant le fichier à exécuter et la valeur est passée en premier argument lorsque le fichier PL est exécuté.

PL_FILES => {'bin/foobar.PL' => 'bin/foobar'}

perl bin/foobar.PL bin/foobar

PL_FILES => {'bin/foobar.PL' => [qw(bin/foobar1 bin/foobar2)]}

perl bin/foobar.PL bin/foobar1
perl bin/foobar.PL bin/foobar2

}

Dans ce cas, les fichiers d'entrée supplémentaires seront passés au programme après le fichier cible :

perl foo.PL bar.out bar1.in bar2.in
