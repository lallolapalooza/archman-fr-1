DESCRIPTIO

N

Dans de nombreuses applications, il est judicieux de laisser Perl utiliser Unicode pour les chaînes qu'il traite. La plupart des interfaces de Perl avec le monde extérieur sont toujours basées sur les octets. Les programmes doivent donc décoder les chaînes d'octets qui entrent dans le programme depuis l'extérieur et les ré-encoder à la

sortie.

Le système de locale POSIX est utilisé pour spécifier à la fois les conventions linguistiques demandées par l'utilisateur et le jeu de caractères préféré pour la consommation et la sortie. Le module "Encode::Locale" recherche le jeu de caractères et l'encodage (appelé CODESET dans le jargon des locales) et arrange les choses pour que le module Encode connaisse cet encodage sous le nom "locale". Cela signifie que les octets obtenus depuis l'environnement peuvent être convertis en chaînes Unicode en appelant "Encode::encode(locale => $bytes)" et reconvertis avec "Encode::decode(locale =>

$string)".

Lorsque les interfaces de système de fichiers font entrer et sortir des noms de fichiers du programme, nous devons également faire attention. La tendance est que les systèmes d'exploitation utilisent un encodage de fichier fixe qui ne dépend pas réellement de la locale ; et ce module détermine l'encodage le plus approprié pour les noms de fichiers. Le module Encode connaîtra cet encodage sous le nom "locale_fs". Pour les systèmes Unix traditionnels, ce sera un alias vers le même encodage que

"locale".

Pour les programmes s'exécutant dans une fenêtre de terminal (appelée "Console" sur certains systèmes), l'encodage "locale" est généralement un bon choix pour ce qui est attendu en entrée et en sortie. Certains systèmes nous permettent d'interroger l'encodage défini pour le terminal et "Encode::Locale" le fera si c'est disponible et rendra ces encodages connus sous les alias "Encode" "console_in" et "console_out". Pour les systèmes où nous ne pouvons pas déterminer l'encodage du terminal, ceux-ci seront aliasés vers le même encodage que "locale". Le conseil est d'utiliser "console_in" pour l'entrée provenant du terminal et "console_out" pour la sortie vers le

terminal.

Window

s

Windows a essentiellement 2 ensembles d'API. Une API large (basée sur le passage de chaînes UTF-16) et une API basée sur les octets basée sur un jeu de caractères appelé ANSI. Les interfaces Perl régulières vers l'OS n'utilisent actuellement que les API ANSI. Malheureusement, ANSI n'est pas un jeu de caractères

unique.

L'encodage qui correspond à ANSI varie selon les différentes éditions de Windows. Pour de nombreuses éditions occidentales de Windows, ANSI correspond à CP-1252 qui est un jeu de caractères similaire à ISO-8859-1. Conceptuellement, le jeu de caractères ANSI est un concept similaire au CODESET de locale POSIX, donc ce module détermine quelle est la page de code ANSI et la rend disponible sous la forme de $ENCODING_LOCALE et de l'alias d'encodage

"locale".

Les systèmes Windows utilisent également un autre jeu de caractères basé sur les octe

ts. Il s'appelle la page de code OEM. C'est l'encodage que la Console prend en entrée
et en sortie. Il est courant que la page de code OEM diffère de la page de code ANSI.

Mac OS

X

Sur Mac OS X, l'encodage du système de fichiers est toujours UTF-8 alors que la locale peut autrement être configurée normalement pour les systèmes

POSIX.

Les noms de fichiers sur Mac OS X seront au niveau de l'OS convertis en forme NFD. Un fichier créé en passant un nom de fichier NFC viendra en forme NFD de readdir(). Voir Unicode::Normalize pour plus de détails sur

NFD/NFC.

En fait, Apple ne suit pas le standard Unicode NFD puisque pas toutes les plages de caractère

s ne sont pas décomposées. On affirme que cela évite les problèmes avec les conversions aller
-retour depuis les anciens encodages de texte Mac. Voir Encode::UTF8Mac pour plus de détails.

POSIX (Linux et autres

Unix)

Les systèmes de fichiers peuvent varier quant à l'encodage à utiliser pour les noms de fichiers.

Puisque ce module n'a aucun moyen de déterminer réellement quel est le bon, il fait la meilleure
supposition qui est de supposer que les noms de fichiers sont encodés selon la locale actuelle. Il
est conseillé aux utilisateurs de toujours spécifier UTF-8 comme jeu de caractères de la locale.
