DESCRIPTIO

N

Souvent, les modules Perl sont écrits pour envelopper des fonctionnalités trouvées dans des en-têtes C existants, des bibliothèques, ou pour utiliser des fonctionnalités spécifiques au système d'exploitation. Il est utile dans le fichier Build.PL ou Makefile.PL de vérifier l'existence de ces prérequis avant d'essayer de construire réellement le

module.

Les objets de cette classe fournissent une extension autour de ExtUtils::CBuilder pour simplifier la création d'un fichier .c, sa compilation, son liaison et son exécution, pour tester si une certaine fonctionnalité est

présente.

Il peut aussi être nécessaire de rechercher la bibliothèque correcte

à lier, ou les bons répertoires d'inclusion pour y trouver les f
ichiers d'en-tête. Cette classe fournit aussi une aide pour cela.

Bibliothèques de

sockets

Certains systèmes d'exploitation fournissent l'API sockets BSD dans leur libc principale. D'autres la gardent dans une bibliothèque séparée à laquelle il faut se lier. L'exemple suivant démontre comment cela serait

géré. 
use ExtUtils::CChecker;
my $cc = ExtUtils::CChecker->new;
$cc->find_libs_for(
   diag => "no socket()",
   libs => [ "", "socket nsl" ],
   source => q[
#include <sys/socket.h>
int main(int argc, char *argv) {
  int fd = socket(PF_INET, SOCK_STREAM, 0);
  if(fd < 0)
    return 1;
  return 0;
}
] );
$cc->new_module_build(
   module_name => "Your::Name::Here",
   requires => {
      'IO::Socket' => 0,
   },
   ...
)->create_build_script
;

Test pour des fonctionnalités

optionnelles

Parfois, une fonction ou une capacité peut être fournie optionnellement par le système d'exploitation, ou vous pouvez souhaiter que votre module soit utilisable même si seul un support partiel est fourni, sans exiger que tout soit présent. Dans ces cas, il est traditionnel de détecter la présence de cette fonctionnalité optionnelle dans le script Build.PL, et de définir un symbole pour déclarer ce fait s'il est trouvé. Le code XS peut alors utiliser ce symbole pour choisir entre des implémentations différentes. Par exemple, le Build.P

L : 
use ExtUtils::CChecker;
my $cc = ExtUtils::CChecker->new;
$cc->try_compile_run(
   define => "HAVE_MANGO",
   source => <<'EOF' );
#include <mango.h>
#include <unistd.h>
int main(void) {
  if(mango() != 0)
    exit(1);
  exit(0);
}
EOF
$cc->new_module_build(
   ...
)->create_build_script
;

Si le code C compile et s'exécute avec succès, et se termine avec un statut vrai, le symbole "HAVE_MANGO" sera défini sur la ligne de commande du compilateur. Cela permet au code XS de le détecter, par

exemple 
int
mango()
  CODE:
#ifdef HAVE_MANGO
    RETVAL = mango();
#else
    croak("mango() not implemented");
#endif
  OUTPUT:
RETVAL

Ce module compilera alors même si le système d'exploitation m

anque de cette fonction particulière. Tenter d'invoquer la
fonction à l'exécution lancera simplement une exception.

En-têtes du noyau

Linux

Les systèmes d'exploitation construits au-dessus du noyau Linux ont souvent une association plus lâche avec leur version de noyau que la plupart des autres systèmes d'exploitation. Il peut arriver que le noyau en cours d'exécution soit plus récent, contenant plus de fonctionnalités, que ce que les en-têtes libc de la distribution le croiraient. Dans de telles circonstances, il peut être difficile de tirer parti de nouvelles options de socket, ioctl(), etc., sans les constantes qui les définissent et leurs structures de paramètres, car les fichiers d'en-tête pertinents ne sont pas visibles par le compilateur. Dans ce cas, il peut y avoir peu de choix que d'inclure certains des fichiers d'en-tête du noyau, qui fourniront les constantes et structures

requises.

Les en-têtes du noyau Linux peuvent être trouvés en utilisant le répertoire /lib/modules. Un fragment dans le Build.PL comme le suivant peut être

approprié. 
chomp( my $uname_r = `uname -r` );
my @dirs = (
   [],
   [ "/lib/modules/$uname_r/source/include" ],
);
$cc->find_include_dirs_for(
   diag => "no PF_MOONLASER",
   dirs => \@dirs,
   source => <<'EOF' );
#include <sys/socket.h>
#include <moon/laser.h>
int family = PF_MOONLASER;
struct laserwl lwl;
int main(int argc, char *argv[]) {
  return 0;
}
EOF

Ce fragment essaiera d'abord de compiler le programme tel quel, espérant que les en-têtes libc seront suffisants. S'il échoue, il essaiera alors d'inclure les en-têtes du noyau,

qui devraient rendre la constante et la struct
ure visibles, permettant au programme de compiler.

Création d'un fichier

"#include"

Parfois, plutôt que de définir des symboles sur la ligne de commande du compilateur, il est préférable de les écrire dans un fichier d'inclusion du préprocesseur C (.h). Cela peut être bénéfique pour la portabilité multiplateforme, car tous les compilateurs C ne peuvent pas prendre d'arguments "-D" supplémentaires sur la ligne de commande, ou les plateformes peuvent avoir de petites restrictions de longueur sur la longueur d'une ligne de

commande. 
use ExtUtils::CChecker;
my $cc = ExtUtils::CChecker->new(
   defines_to => "mymodule-config.h",
);
$cc->try_compile_run(
   define => "HAVE_MANGO",
   source => <<'EOF' );
#include <mango.h>
#include <unistd.h>
#include "mymodule-config.h"
int main(void) {
  if(mango() != 0)
    exit(1);
  exit(0);
}
EOF

Parce que le fichier mymodule-config.h est écrit et vidé après chaque opération de définition, il sera toujours utilisable dans des fragments C ultérieurs pour tester des fonctionnalités détectées dans les

précédents.

Il est suggéré de ne pas nommer le fichier simplement config.h, car le cœur de Perl lui-même a un fichier de ce nom contenant sa propr

e configuration détectée à la compilat
ion. Une confusion entre les deux pour
rait conduire à des résultats surprenants.
