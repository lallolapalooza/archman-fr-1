DESCRIPTIO

N

Exim est un agent de transfert de courrier (MTA) développé à l'Université de Cambridge. C'est un programme volumineux doté de très nombreuses fonctionnalités. Pour une spécification complète, voir le manuel de référence. Cette page man ne contient qu'une description des options de ligne de commande. Elle a été générée automatiquement à partir des sources du manuel de référence, sans trop de dégâts, on

l'espère.

Comme d'autres MTA, Exim remplace Sendmail, et est normalement appelé par les agents utilisateurs (MUA) en utilisant le chemin /usr/sbin/sendmail lorsqu'ils soumettent des messages pour livraison (certains systèmes d'exploitation utilisent /usr/lib/sendmail). Ce chemin est normalement configuré comme un lien symbolique vers le binaire Exim. Il peut aussi être utilisé par les scripts d'amorçage pou

r démarrer le démon Exim. Beaucoup des options de ligne de commande d'Exim s
ont compatibles avec Sendmail afin qu'il puisse agir comme un remplaçant direct.

ACTION PAR

DÉFAUT

Si aucune option n'est présente qui nécessite une action spécifique (comme démarrer le démon ou un gestionnaire de file d'attente, tester une adresse, recevoir un message dans un format spécifique, ou lister la file d'attente), et qu'il n'y a aucun argument sur la ligne de commande, Exim produit un bref message à son sujet et se

termine.

Cependant, s'il y a au moins un argument de ligne de commande, -bm (accepter un message local sur l'entrée standard, avec les arguments spécifiant les destinataires) est supposé. Ainsi, par exemple, si Exim est installé dans /usr/sbin, vous pouvez envoyer un message depuis la ligne de commande comme ceci

<contenu du message, incluant toutes les lignes d'en-tête>

Cette option est utilisée pour l'entrée SMTP par lots, qui est une interface alternative pour la soumission locale non interactive de messages. Plusieurs messages peuvent être soumis en une seule exécution. Cependant, malgré son nom, ceci n'est pas vraiment une entrée SMTP. Exim lit l'enveloppe de chaque message à partir de commandes SMTP sur l'entrée standard, mais ne génère aucune réponse. Si l'appelant est de confiance, ou si untrusted_set_sender est défini, les expéditeurs dans les commandes MAIL SMTP sont crus ; sinon, l'expéditeur est toujours l'appelant d'Exim.

Le message lui-même est lu depuis l'entrée standard, au format SMTP (les points initiaux sont doublés), terminé par une ligne contenant uniquement un point. Une erreur est provoquée si le point de terminaison est manquant. Un message supplémentaire peut alors

suivre.

Comme pour les autres soumissions locales de messages, le contenu des messages SMTP par lots entrants peut être vérifié à l'aide de la liste de contrôle (ACL) non-SMTP. Les adresses non qualifiées sont automatiquement qualifiées à l'aide de qualify_domain et qualify_recipient, selon le cas, sauf si l'option -bnq est

utilisée.

Certaines autres commandes SMTP sont reconnues dans l'entrée. HELO et EHLO agissent comme RSET ; VRFY, EXPN, ETRN, ATRN et HELP agissent comme NOOP ; QUIT quitte, en ignorant le reste de l'entrée

standard.

Si une erreur est rencontrée, des rapports sont écrits sur les flux de sortie standard et d'erreur, et Exim abandonne immédiatement. Le code de retour est 0 si aucune erreur n'a été détectée ; il est 1 si un ou plusieurs messages ont été acceptés avant la détection de l'erreur ; sinon

il est
2.

Cette option exécute Exim en tant que démon, attendant les connexions SMTP entrantes, de manière similaire à l'option -bd. Toutes les spécifications de port sur la ligne de commande et dans le fichier de configuration sont ignorées. L'exécution de la file d'attente ne peut pas être spécifiée.

-C <liste_de_fichiers>
Cette option amène Exim à trouver le fichier de configuration d'exécution à partir de la liste donnée au lieu de la liste spécifiée par le réglage de compilation CONFIGURE_FILE. Habituellement, la liste consistera en un seul nom de fichier, mais elle peut être une liste de noms séparés par des deux-points. Dans ce cas, le premier fichier qui existe est utilisé. L'échec de l'ouverture d'un fichier existant empêche Exim de poursuivre plus loin dans la liste, et une erreur est générée.

Lorsque cette option est utilisée par un appelant autre que root, et que la liste est différente de la liste compilée, Exim abandonne immédiatement son privilège root, et s'exécute avec l'uid et le gid réels et effectifs définis sur ceux de l'appelant. Cependant, si un fichier TRUSTED_CONFIG_LIST est défini dans Local/Makefile, ce fichier contient une liste de chemins complets, un par ligne, pour les fichiers de configuration qui sont de confiance. Le privilège root est conservé pour tout fichier de configuration ainsi listé, tant que l'appelant est l'utilisateur Exim (ou l'utilisateur spécifié dans l'option CONFIGURE_OWNER, le cas échéant), et tant que le fichier de configuration n'est pas inscriptible par des utilisateurs ou des groupes inappropriés.

Laisser TRUSTED_CONFIG_LIST non défini exclut la possibilité de tester une configuration utilisant -C de la réception à la livraison des messages, même si l'appelant est root. La réception fonctionne, mais à ce moment-là, Exim s'exécute en tant qu'utilisateur Exim, donc lorsqu'il se réexécute pour regagner le privilège pour la livraison, l'utilisation de -C entraîne la perte du privilège.

Si ALT_CONFIG_PREFIX est défini dans Local/Makefile, il spécifie une chaîne de préfixe par laquelle tout fichier nommé dans une option de commande -C doit commencer. De plus, le nom de fichier ne doit pas contenir la séquence /../. Cependant, si la valeur de l'option -C est identique à la valeur de CONFIGURE_FILE dans Local/Makefile, Exim ignore -C et procède comme d'habitude. Il n'y a pas de réglage par défaut pour ALT_CONFIG_PREFIX ; lorsqu'il n'est pas défini, tout nom de fichier peut être utilisé avec -C.

ALT_CONFIG_PREFIX peut être utilisé pour confiner les fichiers de configuration alternatifs à un répertoire auquel seul root a accès. Cela empêche quelqu'un qui a piraté le compte Exim d'exécuter un Exim privilégié avec un fichier de configuration arbitraire.

La fonctionnalité -C est utile pour s'assurer que les fichiers de configuration sont syntaxiquement corrects, mais ne peut pas être utilisée pour tester les livraisons, à moins que l'appelant ne soit privilégié, ou qu'il ne s'agisse d'une configuration exotique qui ne nécessite pas de privilège. Aucune vérification n'est effectuée sur le propriétaire ou le groupe des fichiers spécifiés par cette option.

-D<macro>=<valeur>
Cette option peut être utilisée pour remplacer les définitions de macros dans le fichier de configuration. Cependant, comme -C, si elle est utilisée par un appelant non privilégié, elle amène Exim à abandonner son privilège root. Si DISABLE_D_OPTION est défini dans Local/Makefile, l'utilisation de -D est complètement désactivée, et son utilisation provoque une sortie d'erreur immédiate.

Si WHITELIST_D_MACROS est défini dans Local/Makefile, alors il doit s'agir d'une liste de macros séparées par des deux-points qui sont considérées comme sûres et, si -D ne fournit que des macros de cette liste, et que les valeurs sont acceptables, alors Exim n'abandonnera pas le privilège root si l'appelant est root, l'utilisateur d'exécution Exim, ou le CONFIGURE_OWNER, s'il est défini. C'est un mécanisme de transition et il est prévu qu'il soit supprimé à l'avenir. Les valeurs acceptables pour les macros satisfont l'expression régulière : ^[A-Za-z0-9_/.-]*$

L'option entière (y compris le signe égal s'il est présent) doit être dans un seul élément de ligne de commande. -D peut être utilisé pour définir la valeur d'une macro à la chaîne vide, auquel cas le signe égal est facultatif. Ces deux commandes sont synonymes :


exim -DABC ...
exim -DABC= ...

Pour inclure des espaces dans un élément de définition de macro, des guillemets doivent être utilisés. Si vous utilisez des guillemets, des espaces sont autorisés autour du nom de la macro et du signe égal. Par exemple :


exim '-D ABC = quelque chose' ...

-D peut être répété jusqu'à 10 fois sur une ligne de commande. Seuls les noms de macros jusqu'à 22 lettres peuvent être définis.

-d<options de débogage>
Cette option provoque l'écriture d'informations de débogage dans le flux d'erreur standard. Elle est réservée aux administrateurs car la sortie de débogage peut afficher des requêtes de base de données contenant des informations de mot de passe. De plus, les détails des fichiers filtres des utilisateurs doivent être protégés. Si un utilisateur non administrateur utilise -d, Exim écrit un message d'erreur dans le flux d'erreur standard et se termine avec un code de retour non nul.

Lorsque -d est utilisé, -v est supposé. Si -d est donné seul, une grande quantité de données de débogage standard est produite. Cela peut être réduit, ou augmenté pour inclure des informations rarement nécessaires, en faisant suivre directement -d d'une chaîne composée de noms précédés de signes plus ou moins. L'option all exclut memory lorsqu'elle est utilisée comme +all, mais l'inclut pour -all. La raison est que +all est quelque chose que les gens ont tendance à utiliser lors de la génération de sortie de débogage pour les mainteneurs d'Exim. Si +memory est inclus, une quantité énorme de sortie rarement intéressante est générée, donc elle doit maintenant être demandée explicitement. Cependant, -all désactive tout.

L'option resolver ne produit de sortie que si le résolveur DNS a été compilé avec DEBUG activé. Ce n'est pas le cas sur certains systèmes d'exploitation. De plus, malheureusement, la sortie de débogage du résolveur DNS est écrite dans stdout plutôt que dans stderr.

Le défaut (-d sans argument) omet expand, filter, interface, load, memory, pid, resolver, et timestamp. Cependant, le sélecteur pid est forcé lorsque le débogage est activé pour un démon, qui le transmet ensuite à tous les Exims réexécutés. Exim ajoute également automatiquement le pid aux lignes de débogage lorsque plusieurs livraisons à distance sont exécutées en parallèle.

Le sélecteur timestamp provoque l'insertion de l'heure actuelle au début de toutes les lignes de sortie de débogage. Cela peut être utile pour identifier les retards de traitement.

Le sélecteur noutf8 désactive l'utilisation de caractères de dessin de ligne UTF-8 pour regrouper les informations connexes. Lorsqu'il est désactivé, l'art ASCII est utilisé à la place. L'utilisation de l'option +all ne définit pas ce modificateur.

Si l'option debug_print est définie dans un pilote, elle produit une sortie chaque fois qu'un débogage est sélectionné, ou si -v est utilisé.

Cette option définit le nom complet de l'expéditeur à utiliser lorsqu'un message généré localement est accepté. -f <adresse>
Cette option définit l'adresse de l'expéditeur de l'enveloppe d'un message généré localement (également connu sous le nom de chemin de retour). L'option ne peut normalement être utilisée que par un utilisateur de confiance, mais untrusted_set_sender peut être défini pour permettre aux utilisateurs non fiables de l'utiliser.

Les processus s'exécutant en tant que root ou utilisateur Exim sont toujours fiables. Les autres utilisateurs de confiance sont définis par les options trusted_users ou trusted_groups. En l'absence de -f, ou si l'appelant n'est pas fiable, l'expéditeur d'un message local est défini sur le nom de connexion de l'appelant au domaine qualifié par défaut.

Il existe une exception à la restriction d'utilisation de -f : un expéditeur vide peut être spécifié par n'importe quel utilisateur, fiable ou non, pour créer un message qui ne pourra jamais provoquer de rebond. Un expéditeur vide peut être spécifié soit sous forme de chaîne vide, soit sous forme d'une paire d'accolades sans rien entre les deux, comme dans ces exemples de commandes shell :


exim -f '<>' user@domain
exim -f "" user@domain

De plus, l'utilisation de -f n'est pas restreinte lors du test d'un fichier de filtre avec -bf ou lors du test ou de la vérification d'adresses à l'aide des options -bt ou -bv.

Permettre aux utilisateurs non fiables de modifier l'adresse de l'expéditeur ne permet pas en soi d'envoyer des courriels anonymes. -q
Cette option est normalement réservée aux utilisateurs administrateurs. Cependant, il existe une option de configuration appelée prod_requires_admin qui peut être définie sur false pour assouplir cette restriction (ainsi que la même exigence pour les options -M, -R et -S).

Si d'autres options de ligne de commande ne spécifient pas d'action, l'option -q démarre un processus de nettoyage de file d'attente. Celui-ci analyse la file d'attente des messages en attente et lance un processus de livraison pour chacun d'eux à tour de rôle. Il attend que chaque processus de livraison se termine avant de lancer le suivant. Un processus de livraison peut ne pas effectuer de livraisons si les temps de nouvelle tentative pour les adresses n'ont pas été atteints. Utilisez -qf (voir ci-dessous) si vous souhaitez outrepasser cela.

Si le processus de livraison lance d'autres processus pour livrer d'autres messages via des connexions SMTP, le nettoyeur de file d'attente attend que ceux-ci se terminent avant de continuer.

Lorsque tous les messages mis en file d'attente ont été considérés, le processus de nettoyage de file d'attente d'origine se termine. En d'autres termes, un seul passage est effectué sur le courrier en attente, un message à la fois. Utilisez -q avec une heure (voir ci-dessous) si vous souhaitez que cela soit répété périodiquement.

Exim traite les messages en attente dans un ordre imprévisible. Ce n'est pas très aléatoire, mais cela a probablement de bonnes chances d'être différent à chaque fois, ce qui est tout ce qui compte. Si un message particulier pose problème à un MTA distant, d'autres messages vers le même MTA ont une chance de passer s'ils sont essayés en premier.

Il est possible de faire traiter les messages dans l'ordre des identifiants de message lexicographiques, ce qui correspond essentiellement à l'ordre d'arrivée, en définissant l'option queue_run_in_order, mais ce n'est pas recommandé pour une utilisation normale.

-q<qflags>
Effectue un passage de la file d'attente. L'option -q peut être suivie d'une ou plusieurs lettres de drapeau qui modifient son comportement. Elles sont toutes facultatives, mais si plusieurs sont présentes, elles doivent apparaître dans le bon ordre. Chaque drapeau est décrit dans un élément séparé ci-dessous.
-qq...
Une option commençant par -qq demande un passage de file d'attente en deux étapes. Dans la première étape, la file d'attente est analysée comme si l'option queue_smtp_domains correspondait à tous les domaines. Les adresses sont routées, les livraisons locales se produisent, mais aucun transport distant n'est effectué.

Les performances seront optimales si l'option queue_run_in_order est fausse. Si tel est le cas et que l'option queue_fast_ramp est vraie et qu'un socket de notification de démon est disponible, alors dans la première phase du passage, une fois qu'un seuil de messages est routé pour un hôte donné, un processus de livraison est lancé en parallèle avec le reste de l'analyse.

La base de données d'indices qui se souvient des messages en attente pour des hôtes spécifiques est mise à jour, comme si la livraison à ces hôtes avait été différée.

Une fois la première analyse de la file d'attente terminée, une seconde analyse normale est effectuée, avec routage et livraison comme d'habitude. Les messages qui sont routés vers le même hôte devraient être majoritairement livrés via une seule connexion SMTP en raison des indices qui ont été mis en place lors de la première analyse de la file d'attente.

Les passages de file d'attente en deux phases devraient être utilisés sur les systèmes qui, même de manière intermittente, ont une file d'attente importante (tels que les opérateurs de listes de diffusion). Ils peuvent également être utiles pour les hôtes qui sont connectés à Internet de manière intermittente.

-q[q]i...
Si le drapeau i est présent, le nettoyeur de file d'attente n'exécute les processus de livraison que pour les messages qui n'ont pas été précédemment tentés. (i signifie "livraison initiale".) Cela peut être utile si vous mettez des messages dans la file d'attente en utilisant -odq et que vous souhaitez qu'un nettoyeur de file d'attente traite uniquement les nouveaux messages.
-q[q][i]f...
Si un drapeau f est présent, une tentative de livraison est forcée pour chaque message non gelé, alors que sans f, seules les adresses non gelées dont les temps de nouvelle tentative sont dépassés sont essayées.
-q[q][i]ff...
Si ff est présent, une tentative de livraison est forcée pour chaque message, qu'il soit gelé ou non.
-q[q][i][f[f]]l
Le drapeau l (la lettre "ell") spécifie que seules les livraisons locales doivent être effectuées. Si un message nécessite des livraisons distantes, il reste dans la file d'attente pour une livraison ultérieure.
-q[q][i][f[f]][l][G<name>[/<time>]]]
Si le drapeau G et un nom sont présents, le nettoyeur de file d'attente opère sur la file d'attente portant le nom donné plutôt que sur la file d'attente par défaut. Le nom ne doit pas contenir de caractère /. Pour un passage de file d'attente périodique (voir ci-dessous), ajoutez une barre oblique et une valeur de temps au nom.

Si d'autres options de ligne de commande spécifient une action, une option -qG<name> spécifiera une file d'attente sur laquelle opérer. Par exemple :


exim -bp -qGquarantine

exim -qGoffpeak -Rf @special.domain.example

Lors de l'analyse de la file d'attente, Exim peut être amené à ignorer les messages dont les identifiants sont lexicographiquement inférieurs à une valeur donnée en faisant suivre l'option -q d'un identifiant de message de départ. Par exemple :


exim -q 0t5C6f-0000c8-00

Les messages arrivés avant 0t5C6f-0000c8-00 ne sont pas inspectés. Si un second identifiant de message est donné, les messages dont les identifiants sont lexicographiquement supérieurs sont également ignorés. Si le même identifiant est donné deux fois, par exemple,

/usr/exim/bin/exim -bd -q30m

Un tel démon écoute les appels SMTP entrants et démarre également un processus de nettoyage de file d'attente toutes les 30 minutes.

Once a message is selected for delivery by this mechanism, all its addresses are processed. For the first selected message, Exim overrides any retry information and forces a delivery attempt for each undelivered address. This means that if delivery of any address in the first message is successful, any existing retry information is deleted, and so delivery attempts for that address in subsequently selected messages (which are processed without forcing) will run. However, if delivery of any address does not succeed, the retry information is updated, and in subsequently selected messages, the failing address will be

present.

-
t
When Exim is receiving a locally-generated, non-SMTP message on its standard input, the -t option causes the recipients of the message to be obtained from the To:, Cc:, and Bcc: header lines in the message instead of from the command arguments. The addresses are extracted before any rewriting takes place and the Bcc: header line, if present, is then removed.

If the command has any arguments, they specify addresses to which the message is not to be delivered. That is, the argument addresses are removed from the recipients list obtained from the headers. This is compatible with Smail 3 and in accordance with the documented behaviour of several versions of Sendmail, as described in man pages on a number of operating systems (e.g. Solaris 8, IRIX 6.5, HP-UX 11). However, some versions of Sendmail add argument addresses to those obtained from the headers, and the O'Reilly Sendmail book documents it that way. Exim can be made to add argument addresses instead of subtracting them by setting the option extract_addresses_remove_ar

guments false.

If there are any Resent- header lines in the message, Exim extracts recipients from all Resent-To:, Resent-Cc:, and Resent-Bcc: header lines instead of from To:, Cc:, and Bcc:. This is for compatibility with Sendmail and other MTAs. (Prior to release 4.20, Exim gave an error if -t was used in conjunction with Resent- header

lines.)

RFC 2822 [https://www.rfc-editor.org/rfc/rfc2822] talks about different sets of Resent- header lines (for when a message is resent several times). The RFC also specifies that they should be added at the front of the message, and separated by Received: lines. It is not at all clear how -t should operate in the present of multiple sets, nor indeed exactly what constitutes a "set". In practice, it seems that MUAs do not follow the RFC. The Resent- lines are often added at the end of the header, and if a message is resent more than once, it is common for the original set of Resent- headers to be renamed as X-Resent- when a new set is adde

d. This removes any
possible ambiguity.
