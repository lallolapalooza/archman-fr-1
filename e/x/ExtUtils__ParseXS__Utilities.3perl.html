SOUS-ROUTINES

Les fonctions suivantes ne sont pas considérées comme faisant partie de l'interface publique. Elles sont documentées ici pour le bénéfice des futurs mainteneurs de ce module.

standard_typemap_locations()

  • But

    Fournir une liste de chemins de fichiers où les fichiers typemap peuvent être trouvés. Les chemins de fichiers -- chemins relatifs vers des fichiers (pas seulement des chemins de répertoires) -- apparaissent dans cette liste de la plus faible à la plus haute priorité.

    La priorité la plus élevée est de chercher dans le répertoire courant.

    'typemap'

    Les deuxième et troisième priorités les plus élevées sont de chercher dans le répertoire parent du répertoire courant et dans un répertoire appelé lib/ExtUtils sous le répertoire parent.

    '../typemap',
'../lib/ExtUtils/typemap',

    Les quatrième à neuvième priorités les plus élevées sont de chercher dans les répertoires correspondants du grand-parent, de l'arrière-grand-parent et de l'arrière-arrière-grand-parent.

    '../../typemap',
'../../lib/ExtUtils/typemap',
'../../../typemap',
'../../../lib/ExtUtils/typemap',
'../../../../typemap',
'../../../../lib/ExtUtils/typemap',

    La dixième et les priorités suivantes sont de chercher dans les répertoires nommés ExtUtils qui sont des sous-répertoires des répertoires trouvés dans @INC -- à condition qu'un fichier nommé typemap existe réellement dans un tel répertoire. Exemple : '/usr/local/lib/perl5/5.10.1/ExtUtils/typemap',

    Cependant, ces chemins de fichiers apparaissent dans la liste retournée par

    standard_typemap_locations() dans l'ordre inverse, c'est-à-dire de la plus faible à la plus haute priorité.'/usr/local/lib/perl5/5.10.1/ExtUtils/typemap', '../../../../lib/ExtUtils/typemap', '../../../../typemap', '../../../lib/ExtUtils/typemap', '../../../typemap', '../../lib/ExtUtils/typemap', '../../typemap', '../lib/ExtUtils/typemap', '../typemap', 'typemap'

"map_type($self, $type, $varname)"

Retourne une version mappée du type C $type. En particulier, il convertit "Foo::bar" en "Foo__bar", convertit le spécial "array(type,n)" en "type *", et insère $varname (s'il est présent) dans tout type de pointeur de fonction. Ainsi "...(*)..." devient "...(* foo)...".

analyze_preprocessor_statement()

  • But

    Traiter une ligne conditionnelle CPP ("#if" etc), pour garder une trace de l'imbrication conditionnelle. En particulier, il met à jour "@{$self->{XS_parse_stack}}" qui contient la liste courante des conditions imbriquées, et "$self->{XS_parse_stack_top_if_idx}" qui indique le "if" le plus récent dans cette pile. Ainsi un "#if" empile, un "#endif" dépile, un "#else" modifie, etc. Chaque élément est un hachage de la forme :

    {
  type      => 'if',
  varname   => 'XSubPPtmpAAAA', # maintained by caller
                # XS functions defined within this branch of the
                # conditional (maintained by caller)
  functions =>  {
                  'Foo::Bar::baz' => 1,
                  ...
                }
                # XS functions seen within any previous branch
  other_functions => {... }

    Il met également à jour "$self->{bootcode_early}" et "$self->{bootcode_late}" avec des directives CPP supplémentaires.

  • Arguments 
    $self->analyze_preprocessor_statement($statement);

Méthodes de gestion des erreurs

Il existe quatre méthodes principales pour signaler des avertissements et des erreurs.

"$self->Warn(@messages)"
Cela équivaut à : 
warn "@messages in foo.xs, line 123\n";

Le fichier et le numéro de ligne sont basés sur le fichier en cours d'analyse. Cette méthode est destinée à être utilisée lorsque vous souhaitez émettre un avertissement, mais que vous pouvez continuer l'analyse et générer toujours un fichier C correct.

"$self->blurt(@messages)"
Cela équivaut à "Warn", sauf qu'elle incrémente également le compteur d'erreurs interne (qui peut être récupéré avec report_error_count()). Elle est utilisée pour signaler une erreur, mais là où l'analyse peut continuer (donc généralement pour une erreur sémantique plutôt qu'une erreur de syntaxe). On s'attend à ce que l'appelant signale finalement un échec d'une manière ou d'une autre. Par exemple, "xsubpp" a ceci comme dernière ligne : 
exit($self->report_error_count() ? 1 : 0);
"$self->death(@messages)"
Cela équivaut normalement à : 
$self->Warn(@messages);
exit(1);

Elle est utilisée pour quelque chose comme une erreur de syntaxe, où l'analyse ne peut pas continuer. Cependant, cela est gênant à des fins de test, car l'erreur ne peut pas être interceptée. Donc si $self est créé avec l'indicateur "die_on_error" , ou si $ExtUtils::ParseXS::DIE_ON_ERROR est vrai lorsque process_file() est appelé, alors à la place, elle appellera die() avec ce message.

"$self->WarnHint(@messages, $hints)"
C'est un jumeau plus obscur de "Warn", qui fait la même chose que "Warn", mais ensuite, produit toutes les lignes contenues dans la chaîne $hints , chaque ligne étant entourée de parenthèses. Par exemple : 
$self->WarnHint(@messages,
  "Have you set the foo switch?\nSee the manual for further info");

escape_file_for_line_directive()

  • But

    Échappe un nom de source de code donné (généralement un nom de fichier, mais peut aussi être une commande à partir de laquelle il a été lu) afin que les guillemets doubles et les barres obliques inversées soient échappés.

  • Arguments

    Une chaîne.

  • Valeur de retour

    Une chaîne avec les échappements pour les guillemets doubles et les barres obliques inversées.

"report_typemap_failure"

  • But

    Effectuer le signalement d'erreur pour les typemaps manquants.

  • Arguments

    L'objet "ExtUtils::ParseXS" .

    Un objet "ExtUtils::Typemaps" .

    La chaîne qui représente le type C qui n'a pas été trouvé dans le typemap.

    En option, la chaîne "death" ou "blurt" pour choisir si l'erreur est immédiatement fatale ou non. Par défaut : "blurt"

  • Valeur de retour

    Ne renvoie rien. Selon les arguments, cela peut appeler "death" ou "blurt", la première étant fatale.
