bzero(3) Manuel des fonctions de bibliothèque bzero(3)

NOM

bzero, explicit_bzero - initialiser une chaîne d'octets à zéro

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <strings.h>
void bzero(size_t n;
           void s[n], size_t n);
#include <string.h>
void explicit_bzero(size_t n;
           void s[n], size_t n);

DESCRIPTION

La fonction bzero() efface les données dans les n octets de la mémoire commençant à l'emplacement pointé par s, en écrivant des zéros (octets contenant '\0') dans cette zone.

La fonction explicit_bzero() effectue la même tâche que bzero(). Elle diffère de bzero() en ce qu'elle garantit que les optimisations du compilateur ne supprimeront pas l'opération d'effacement si le compilateur déduit que l'opération est "inutile".

VALEUR DE RETOUR

Aucune.

ATTRIBUTS

Pour une explication des termes utilisés dans cette section, voir attributes(7).

NORMES

Aucune.

HISTORIQUE

explicit_bzero()
glibc 2.25.
La fonction explicit_bzero() est une extension non standard qui est également présente sur certains systèmes BSD. Certaines autres implémentations ont une fonction similaire, telle que memset_explicit() ou memset_s().
bzero()
4.3BSD.
Marquée comme DÉSUÈTE dans POSIX.1-2001. Supprimée dans POSIX.1-2008.

NOTES

La fonction explicit_bzero() aborde un problème que les applications soucieuses de la sécurité peuvent rencontrer lors de l'utilisation de bzero() : si le compilateur peut déduire que l'emplacement à initialiser à zéro ne sera plus jamais utilisé par un programme correct, il peut supprimer complètement l'appel bzero(). C'est un problème si l'intention de l'appel bzero() était d'effacer des données sensibles (par exemple, des mots de passe) pour éviter la possibilité que les données soient divulguées par un programme incorrect ou compromis. Les appels à explicit_bzero() ne sont jamais optimisés par le compilateur.

La fonction explicit_bzero() ne résout pas tous les problèmes liés à l'effacement de données sensibles :

•
La fonction explicit_bzero() ne garantit pas que les données sensibles soient complètement effacées de la mémoire. (Il en va de même pour bzero().) Par exemple, il peut y avoir des copies des données sensibles dans un registre et dans des zones de pile temporaires. La fonction explicit_bzero() n'est pas consciente de ces copies et ne peut pas les effacer.
•
Dans certaines circonstances, explicit_bzero() peut diminuer la sécurité. Si le compilateur détermine que la variable contenant les données sensibles pourrait être optimisée pour être stockée dans un registre (car elle est suffisamment petite pour tenir dans un registre, et aucune opération autre que l'appel explicit_bzero() n'aurait besoin de prendre l'adresse de la variable), alors l'appel explicit_bzero() forcerait les données à être copiées du registre vers un emplacement en RAM qui est ensuite immédiatement effacé (tandis que la copie dans le registre reste inchangée). Le problème ici est que les données en RAM sont plus susceptibles d'être exposées par un bug que les données dans un registre, et donc l'appel explicit_bzero() crée une courte fenêtre temporelle où les données sensibles sont plus vulnérables qu'elles ne l'auraient été autrement si aucune tentative n'avait été faite pour effacer les données.

Notez que déclarer la variable sensible avec le qualificateur volatile n'élimine pas les problèmes ci-dessus. En fait, cela les aggraverait, car, par exemple, cela pourrait forcer une variable qui aurait autrement été optimisée dans un registre à être maintenue dans la RAM (plus vulnérable) pendant toute sa durée de vie.

Nonobstant les détails ci-dessus, pour les applications soucieuses de la sécurité, utiliser explicit_bzero() est généralement préférable à ne pas l'utiliser. Les développeurs de explicit_bzero() prévoient que les futurs compilateurs reconnaîtront les appels à explicit_bzero() et prendront des mesures pour garantir que toutes les copies des données sensibles soient effacées, y compris les copies dans les registres ou dans les zones de pile temporaires.
