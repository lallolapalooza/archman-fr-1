epoll

est capable de fonctionner à la fois en mode déclenché par front montant (ET) et en mode déclenché par niveau (LT). La différence entre les deux mécanismes peut être décrite comme suit. Supposons que ce scénario se produise : (1) Le descripteur de

La raison en est que le mode déclenché par front montant ne délivre des événements que lorsque des changements se produisent sur le descripteur de fichier surveillé, c'est-à-dire qu'un événement sera généré à chaque réception d'un bloc de données. Ainsi, à l'étape 5, l' appelant pourrait finir par attendre certaines données déjà présentes dans le tampon d'entrée. Dans l'exemple ci-dessus, un événement sur rfd sera généré à cause de l'écriture effectuée à l'étape 2 et l'événement est consommé à l'étape 3. Puisque l'opération de lecture effectuée à l'étape 4 ne consomme pas toutes les données du tampon , l'appel à epoll_wait(2) effectué à l'étape 5 pourrait bloquer indéfiniment. Dans cet exemple, listener est un socket non bloquant sur lequel listen(2) a été appelé. La fonction do_use_fd() utilise le nouveau descripteur de fichier prêt jusqu'à ce que EAGAIN soit renvoyé soit par read(2) ou write(2). Une application machine à états pilotée par événements devrait, àaprès avoir reçu EAGAIN, enregistre son état actuel afin qu'à l'appel suivant à do_use_fd() il continue à read(2) ou write(2) à partir de l'endroit où il s'était

#define MAX_EVENTS 10
struct epoll_event ev, events[MAX_EVENTS];
int listen_sock, conn_sock, nfds, epollfd;
/* Code pour configurer la socket d'écoute, 'listen_sock',
   (socket(), bind(), listen()) omis.  */
epollfd = epoll_create1(0);
if (epollfd == -1) {
    perror("epoll_create1");
    exit(EXIT_FAILURE);
}
ev.events = EPOLLIN;
ev.data.fd = listen_sock;
if (epoll_ctl(epollfd, EPOLL_CTL_ADD, listen_sock, &ev) == -1) {
    perror("epoll_ctl: listen_sock");
    exit(EXIT_FAILURE);
}
for (;;) {
    nfds = epoll_wait(epollfd, events, MAX_EVENTS, -1);
    if (nfds == -1) {
        perror("epoll_wait");
        exit(EXIT_FAILURE);
    }
    for (n = 0; n < nfds; ++n) {
        if (events[n].data.fd == listen_sock) {
            conn_sock = accept(listen_sock,
                               (struct sockaddr *) &addr, &addrlen);
            if (conn_sock == -1) {
                perror("accept");
                exit(EXIT_FAILURE);
            }
            setnonblocking(conn_sock);
            ev.events = EPOLLIN | EPOLLET;
            ev.data.fd = conn_sock;
            if (epoll_ctl(epollfd, EPOLL_CTL_ADD, conn_sock,
                        &ev) == -1) {
                perror("epoll_ctl: conn_sock");
                exit(EXIT_FAILURE);
            }
        } else {
            do_use_fd(events[n].data.fd);
        }
    }
}

Questions et

réponses
•
Quelle est la clé utilisée pour distinguer les descripteurs de fichier enregistrés dans une liste d'intérêt
?
La clé est la combinaison du numéro de descripteur de fichier et de la description de fichier ouverte (également connue sous le nom de « open file handle », la représentation interne du noyau d'un fichier ouvert)
.
•
Que se passe-t-il si vous enregistrez le même descripteur de fichier deux fois sur une instanc
e
epoll ? Vous obtiendrez probablement EEXIST. Cependant, il est possible d'ajouter un descripteur de fichier dupliqué (dup(2), dup2(2), fcntl(2) F_DUPFD) à la même instance epoll. Cela peut être une technique utile pour filtrer les événements, si les descripteurs de fichier dupliqués sont enregistrés avec des masques events
différents.
•
Deux instances epoll peuvent-elles attendre le même descripteur de fichier ? Si oui, les événements sont-ils rapportés aux deux descripteurs de fichier
epoll ?
Oui, et les événements seraient rapportés aux deux. Cependant, une programmation soignée peut être nécessaire pour faire cela
correctement.
•
Le descripteur de fichier epoll lui-même est-il pollable/epollable/sélectionnable
?
Oui. Si un descripteur de fichier epoll a des événements en attente, alors il indiquera être
lisible.
•
Que se passe-t-il si l'on tente de mettre un descripteur de fichier epoll dans son propre ensemble de descripteurs de fichier
?
L'appel epoll_ctl(2) échoue (EINVAL). Cependant, vous pouvez ajouter un descripteur de fichier epoll à l'intérieur d'un autre ensemble de descripteurs de fichier epoll
.
•
Puis-je envoyer un descripteur de fichier epoll via une socket de domaine UNIX à un autre processus
?
Oui, mais cela n'a pas de sens de le faire, car le processus receveur n'aurait pas de copies des descripteurs de fichier dans la liste
d'intérêt.
•
La fermeture d'un descripteur de fichier le fera-t-elle être retiré de toutes les listes d'intérêt epoll
?
Oui, mais soyez conscient du point suivant. Un descripteur de fichier est une référence à une description de fichier ouverte (voir open(2)). Chaque fois qu'un descripteur de fichier est dupliqué via dup(2), dup2(2), fcntl(2) F_DUPFD, ou fork(2), un nouveau descripteur de fichier faisant référence à la même description de fichier ouverte est créé. Une description de fichier ouverte continue d'exister jusqu'à ce que tous les descripteurs de fichier qui s'y réfèrent aient été
fermés.
Un descripteur de fichier n'est retiré d'une liste d'intérêt qu'après que tous les descripteurs de fichier faisant référence à la description de fichier sous-jacente ont été fermés. Cela signifie que même après qu'un descripteur de fichier faisant partie d'une liste d'intérêt a été fermé, des événements peuvent être rapportés pour ce descripteur de fichier si d'autres descripteurs de fichier faisant référence à la même description de fichier sous-jacente restent ouverts. Pour empêcher cela, le descripteur de fichier doit être explicitement retiré de la liste d'intérêt (en utilisant epoll_ctl(2) EPOLL_CTL_DEL) avant d'être dupliqué. Alternativement, l'application doit s'assurer que tous les descripteurs de fichier sont fermés (ce qui peut être difficile si des descripteurs de fichier ont été dupliqués en coulisses par des fonctions de bibliothèque qui utilisaient dup(2) ou fork(2
)).
•
Si plus d'un événement se produit entre deux appels à epoll_wait(2), sont-ils combinés ou rapportés séparément
?
Ils seront
combinés.
•
Une opération sur un descripteur de fichier affecte-t-elle les événements déjà collectés mais pas encore rapportés
?
Vous pouvez effectuer deux opérations sur un descripteur de fichier existant. La suppression serait sans objet dans ce cas. La modification relira l'E/S
disponible.
•
Dois-je lire/écrire continuellement un descripteur de fichier jusqu'à obtenir EAGAIN lorsque j'utilise l'indicateur EPOLLET (comportement à déclenchement par front montant)
?
Recevoir un événement de epoll_wait(2) devrait vous suggérer que ce descripteur de fichier est prêt pour l'opération d'E/S demandée. Vous devez le considérer comme prêt jusqu'à ce que la prochaine lecture/écriture (non bloquante) produise EAGAIN. Quand et comment vous utiliserez le descripteur de fichier dépend entièrement de
vous.
Pour les fichiers orientés paquet/jeton (par ex. socket de datagramme, terminal en mode canonique), la seule façon de détecter la fin de l'espace d'E/S en lecture/écriture est de continuer à lire/écrire jusqu'à EAGAI
N.
Pour les fichiers orientés flux (par ex. tube, FIFO, socket de flux), la condition selon laquelle l'espace d'E/S en lecture/écriture est épuisé peut également être détectée en vérifiant la quantité de données lues depuis / écrites vers le descripteur de fichier cible. Par exemple, si vous appelez read(2) en demandant à lire un certain montant de données et que read(2) renvoie un nombre de bytes inférieur, vous pouvez être sûr d'avoir épuisé l'espace d'E/S en lecture pour le descripteur de fichier. Il en va de même lors de l'écriture avec write(2). (Évitez cette dernière technique si vous ne pouvez p
as garantir que le descripteur de f
ichier surveillé fait toujours réf
érence à un fichier orienté flux.)

Pièges possibles et moyens de les

éviter
•
Affamement (déclenchement par front
montant)
S'il y a une grande quantité d'espace d'E/S, il est possible qu'en essayant de le vider, les autres fichiers ne soient pas traités, causant un affamement. (Ce problème n'est pas spécifique à epoll
.)
La solution est de maintenir une liste de prêts et de marquer le descripteur de fichier comme prêt dans sa structure de données associée, permettant ainsi à l'application de se souvenir des fichiers qui doivent être traités tout en faisant toujours un tour parmi tous les fichiers prêts. Cela permet aussi d'ignorer les événements ultérieurs que vous recevez pour des descripteurs de fichier déjà
prêts.
•
Si vous utilisez un cache d'événements.
..
Si vous utilisez un cache d'événements ou stockez tous les descripteurs de fichier renvoyés par epoll_wait(2), assurez-vous de fournir un moyen de marquer sa fermeture dynamiquement (c.-à-d. causée par le traitement d'un événement précédent). Supposez que vous recevez 100 événements de epoll_wait(2), et que dans l'événement #47, une condition cause la fermeture de l'événement #13. Si vous retirez la structure et close(2) le descripteur de fichier pour l'événement #13, alors votre cache d'événements pourrait encore dire qu'il y a des événements en attente pour ce descripteur de fichier, causant de la
confusion.
Une solution pour cela est d'appeler, lors du traitement de l'événement 47, epoll_ctl(EPOLL_CTL_DEL) pour supprimer le descripteur de fichier 13 et close(2), puis de marquer sa structure de données associée comme retirée et de la lier à une liste de nettoy
age. Si vous trouvez un autre événement pour le descript
eur de fichier 13 dans votre traitement par lots, v
ous découvrirez que le descripteur de fichier avait
été retiré précédemment et il n'y aura pas de confusion.
