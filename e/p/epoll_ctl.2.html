epoll_ctl(2) Manuel des appels système epoll_ctl(2)

NOM

epoll_ctl - interface de contrôle pour un descripteur de fichier epoll

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/epoll.h>
int epoll_ctl(int epfd, int op, int fd,
              struct epoll_event *_Nullable event);

DESCRIPTION

Cet appel système est utilisé pour ajouter, modifier ou supprimer des entrées dans la liste d'intérêt de l'instance epoll(7) référencée par le descripteur de fichier epfd. Il demande que l'opération op soit effectuée pour le descripteur de fichier cible, fd.

Les valeurs valides pour l'argument op sont :

EPOLL_CTL_ADD
Ajouter une entrée à la liste d'intérêt du descripteur de fichier epoll, epfd. L'entrée inclut le descripteur de fichier, fd, une référence à la description de fichier ouverte correspondante (voir epoll(7) et open(2)), et les paramètres spécifiés dans event.
EPOLL_CTL_MOD
Changer les paramètres associés à fd dans la liste d'intérêt avec les nouveaux paramètres spécifiés dans event.
EPOLL_CTL_DEL
Supprimer (désenrégistrer) le descripteur de fichier cible fd de la liste d'intérêt. L'argument event est ignoré et peut être NULL (mais voir la section BUGS ci-dessous).

L'argument event décrit l'objet lié au descripteur de fichier fd. La structure struct epoll_event est décrite dans epoll_event(3type).

Le membre data de la structure epoll_event spécifie les données que le noyau doit sauvegarder et ensuite retourner (via epoll_wait(2)) lorsque ce descripteur de fichier devient prêt.

Le membre events de la structure epoll_event est un masque de bits composé en combinant par OR zéro ou plusieurs types d'événements, retournés par epoll_wait(2), et des drapeaux d'entrée, qui affectent son comportement, mais ne sont pas retournés. Les types d'événements disponibles sont :

EPOLLIN
Le fichier associé est disponible pour les opérations de read(2).
EPOLLOUT
Le fichier associé est disponible pour les opérations de write(2).
EPOLLRDHUP (depuis Linux 2.6.17)
Le pair de la socket de flux a fermé la connexion, ou a arrêté la partie écriture de la connexion. (Ce drapeau est particulièrement utile pour écrire du code simple afin de détecter la fermeture par le pair lors de l'utilisation de la surveillance déclenchée par front.)
EPOLLPRI
Une condition exceptionnelle s'est produite sur le descripteur de fichier. Voir la discussion de POLLPRI dans poll(2).
EPOLLERR
Une condition d'erreur s'est produite sur le descripteur de fichier associé. Cet événement est également signalé pour l'extrémité d'écriture d'un tuyau lorsque l'extrémité de lecture a été fermée.
epoll_wait(2) signalera toujours cet événement ; il n'est pas nécessaire de le définir dans events lors de l'appel à epoll_ctl().
EPOLLHUP
Une déconnexion (hang up) s'est produite sur le descripteur de fichier associé.
epoll_wait(2) attendra toujours cet événement ; il n'est pas nécessaire de le définir dans events lors de l'appel à epoll_ctl().
Notez que lors de la lecture d'un canal tel qu'un tuyau ou une socket de flux, cet événement indique simplement que le pair a fermé son extrémité du canal. Les lectures ultérieures du canal retourneront 0 (fin de fichier) seulement après que toutes les données en attente dans le canal aient été consommées.

Et les drapeaux d'entrée disponibles sont :

EPOLLET
Demande une notification déclenchée par front pour le descripteur de fichier associé. Le comportement par défaut pour epoll est déclenché par niveau. Voir epoll(7) pour plus d'informations détaillées sur la notification déclenchée par front et déclenchée par niveau.
EPOLLONESHOT (depuis Linux 2.6.2)
Demande une notification unique (one-shot) pour le descripteur de fichier associé. Cela signifie qu'après un événement notifié pour le descripteur de fichier par epoll_wait(2), le descripteur de fichier est désactivé dans la liste d'intérêt et aucun autre événement ne sera signalé par l'interface epoll. L'utilisateur doit appeler epoll_ctl() avec EPOLL_CTL_MOD pour réarmer le descripteur de fichier avec un nouveau masque d'événements.
EPOLLWAKEUP (depuis Linux 3.5)
Si EPOLLONESHOT et EPOLLET sont désactivés et que le processus possède la capacité CAP_BLOCK_SUSPEND, assurez-vous que le système n'entre pas en mode "suspend" ou "hibernation" tant que cet événement est en attente ou en cours de traitement. L'événement est considéré comme étant "en cours de traitement" à partir du moment où il est retourné par un appel à epoll_wait(2) jusqu'au prochain appel à epoll_wait(2) sur le même descripteur de fichier epoll(7), la fermeture de ce descripteur de fichier, la suppression du descripteur de fichier d'événement avec EPOLL_CTL_DEL, ou la désactivation de EPOLLWAKEUP pour le descripteur de fichier d'événement avec EPOLL_CTL_MOD. Voir également BUGS.
EPOLLEXCLUSIVE (depuis Linux 4.5)
Définit un mode de réveil exclusif pour le descripteur de fichier epoll qui est attaché au descripteur de fichier cible, fd. Lorsqu'un événement de réveil se produit et que plusieurs descripteurs de fichier epoll sont attachés au même fichier cible en utilisant EPOLLEXCLUSIVE, un ou plusieurs des descripteurs de fichier epoll recevront un événement avec epoll_wait(2). Le comportement par défaut dans ce scénario (lorsque EPOLLEXCLUSIVE n'est pas défini) est que tous les descripteurs de fichier epoll reçoivent un événement. EPOLLEXCLUSIVE est donc utile pour éviter les problèmes de "thundering herd" dans certains scénarios.
Si le même descripteur de fichier se trouve dans plusieurs instances epoll, certaines avec le drapeau EPOLLEXCLUSIVE et d'autres sans, alors les événements seront fournis à toutes les instances epoll qui n'ont pas spécifié EPOLLEXCLUSIVE, et à au moins une des instances epoll qui a spécifié EPOLLEXCLUSIVE.
Les valeurs suivantes peuvent être spécifiées en conjonction avec EPOLLEXCLUSIVE : EPOLLIN, EPOLLOUT, EPOLLWAKEUP et EPOLLET. EPOLLHUP et EPOLLERR peuvent également être spécifiés, mais ce n'est pas obligatoire : comme d'habitude, ces événements sont toujours signalés s'ils se produisent, qu'ils soient spécifiés ou non dans events. Les tentatives de spécifier d'autres valeurs dans events entraînent l'erreur EINVAL.
EPOLLEXCLUSIVE ne peut être utilisé que dans une opération EPOLL_CTL_ADD ; les tentatives de l'utiliser avec EPOLL_CTL_MOD entraînent une erreur. Si EPOLLEXCLUSIVE a été défini à l'aide de epoll_ctl(), alors un EPOLL_CTL_MOD ultérieur sur la même paire epfd, fd entraîne une erreur. Un appel à epoll_ctl() qui spécifie EPOLLEXCLUSIVE dans events et spécifie le descripteur de fichier cible fd comme une instance epoll échouera également. L'erreur dans tous ces cas est EINVAL.

VALEUR DE RETOUR

En cas de succès, epoll_ctl() retourne zéro. En cas d'erreur, epoll_ctl() retourne -1 et errno est défini pour indiquer l'erreur.

ERREURS

EBADF
Le descripteur de fichier epfd n'est pas valide, ou fd n'est pas un descripteur de fichier valide.
EBADFD
L'opération op était EPOLL_CTL_DEL, et fd n'est pas enregistré dans la liste d'intérêt de epfd.
EEXIST
L'opération op était EPOLL_CTL_ADD, et le descripteur de fichier fd est déjà enregistré dans la liste d'intérêt de epfd.
EINVAL
epfd n'est pas un descripteur de fichier epoll ; ou l'objet spécifié par fd ne peut pas être utilisé avec epoll ; ou op n'est pas une opération valide ; ou une combinaison non valide de drapeaux a été spécifiée dans event.events ; ou EPOLLEXCLUSIVE a été spécifié avec une opération autre que EPOLL_CTL_ADD, ou il a été spécifié avec des drapeaux incompatibles, ou fd est lui-même un descripteur de fichier epoll.
ENOENT
L'opération op était EPOLL_CTL_MOD ou EPOLL_CTL_DEL, et le descripteur de fichier fd n'est pas enregistré dans la liste d'intérêt de epfd.
ENOMEM
Une allocation de mémoire a échoué dans le noyau.
ENOSPC
La limite de descripteurs de fichier epoll pour le processus a été atteinte.
EOVERFLOW
Le nombre d'enregistrements dans l'instance epoll a atteint sa limite.

CONFORMITÉ

Cet appel système est spécifique à Linux. Il est documenté dans le manuel Linux.

BUGS

Dans les versions du noyau Linux antérieures à 2.6.9, l'argument event ne pouvait pas être NULL pour EPOLL_CTL_DEL. Les programmes qui utilisaient cette fonctionnalité devaient passer une structure epoll_event bidon. Les programmes modernes peuvent passer NULL.

Dans les versions du noyau Linux antérieures à 4.5, l'utilisation de EPOLLWAKEUP était possible dans une opération EPOLL_CTL_MOD sur un descripteur de fichier déjà enregistré. Dans les noyaux plus récents, cela échoue avec EINVAL. La documentation de la page man pour EPOLLWAKEUP indique que le drapeau doit être clair lors de l'utilisation de EPOLL_CTL_MOD.

Avant Linux 2.6.9, l'opération EPOLL_CTL_DEL nécessitait un pointeur non nul dans event, même si cet argument est ignoré. Depuis Linux 2.6.9, event peut être spécifié comme NULL lors de l'utilisation de EPOLL_CTL_DEL. Les applications qui doivent être portables sur les noyaux antérieurs à Linux 2.6.9 doivent spécifier un pointeur non nul dans event

.

Si EPOLLWAKEUP est spécifié dans flags, mais que l'appelant ne possède pas la capacité CAP_BLOCK_SUSPEND, alors l'indicateur EPOLLWAKEUP est ignoré silencieusement. Ce comportement malheureux est nécessaire car aucune vérification de validité n'était effectuée sur l'argument flags dans l'implémentation originale, et l'ajout de l'indicateur EPOLLWAKEUP avec une vérification qui faisait échouer l'appel si l'appelant ne possédait pas la capacité CAP_BLOCK_SUSPEND a provoqué une panne dans au moins une application utilisateur existante qui se trouvait spécifier ce bit de manière aléatoire (et inutile). Une application robuste doit donc vérifier à deux fois qu'elle possède la capacité CAP_BLOCK_SUSPEND si elle tente d'utiliser l'indicateur EPOLLW
