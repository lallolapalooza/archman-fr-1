NOM

ejabberd.yml - fichier de configuration principal pour ejabberd.

SYNOPIS

ejabberd.yml

DESCRIPTION

Le fichier de configuration est écrit en langage YAML.


Attention

YAML est sensible à l'indentation, assurez-vous donc de respecter l'indentation, sinon vous obtiendrez des erreurs de configuration assez cryptiques.

Logiquement, les options de configuration sont divisées en 3 catégories principales : Modules, Listeners et tout le reste appelé options de Niveau Supérieur. Ainsi, ce document est divisé en 3 chapitres décrivant chaque catégorie séparément. Par conséquent, le contenu d'ejabberd.yml ressemblera généralement à ceci :

hosts:
  - example.com
  - domain.tld
loglevel: info
...
listen:
  -
    port: 5222
    module: ejabberd_c2s
  ...
modules:
  mod_roster: {}
  ...

Toute erreur de configuration (telle qu'une erreur de syntaxe, une option inconnue ou une valeur d'option invalide) est fatale dans le sens où ejabberd refusera de charger l'intégralité du fichier de configuration et ne démarrera pas ou abandonnera le rechargement de la configuration.

Toutes les options peuvent être modifiées à la volée en exécutant la commande ejabberdctl reload-config. Le rechargement de la configuration est atomique : soit toutes les options sont acceptées et appliquées simultanément, soit la nouvelle configuration est refusée sans aucun impact sur la configuration en cours d'exécution.

Certaines options peuvent être spécifiées pour des hôtes virtuels particuliers uniquement en utilisant les options host_config ou append_host_config. Ces options sont appelées locales. Les exemples sont modules, auth_method et default_db. Les options qui ne peuvent pas être définies par hôte virtuel sont appelées globales. Les exemples sont loglevel, certfiles et listen. C'est une erreur de configuration de placer des options globales sous la section host_config ou append_host_config - ejabberd refusera de charger une telle configuration.

Il n'est pas recommandé d'écrire ejabberd.yml à partir de zéro. Il est plutôt préférable de commencer par le fichier de configuration "par défaut" disponible à l'adresse https://github.com/processone/ejabberd/blob/25.10/ejabberd.yml.example. Une fois qu'ejabberd fonctionne, vous pouvez commencer à modifier les options de configuration pour répondre à vos besoins.

Notez que ce document vise à fournir une description complète de toutes les options de configuration qui peuvent être consultées pour comprendre la signification d'une option particulière, son format et ses valeurs possibles. Il sera assez difficile de comprendre comment configurer ejabberd en ne lisant que ce document - à cette fin, le lecteur est recommandé de lire le guide de configuration en ligne disponible à l'adresse https://docs.ejabberd.im/admin/configuration.

OPTIONS DE NIVEAU SUPÉRIEUR

Cette section décrit les options de niveau supérieur d'ejabberd 25.10. Les options qui ont changé dans cette version sont marquées du symbole 🟤.

access_rules: {NomAccès: {allow|deny: NomACL|DéfinitionACL}}

Cette option définit les règles d'accès basic.md#access-rules|d'accès. Chaque règle d'accès se voit attribuer un nom qui peut être référencé à partir d'autres parties du fichier de configuration (principalement à partir des options access des modules ejabberd). Chaque définition de règle peut contenir un nombre arbitraire de sections allow ou deny, et chaque section peut contenir n'importe quel nombre de règles ACL (voir l'option acl). Il n'y a pas de règles d'accès définies par défaut.

Exemple :

access_rules:
  configure:
    allow: admin
  something:
    deny: someone
    allow: all
  s2s_banned:
    deny: problematic_hosts
    deny: banned_forever
    deny:
      ip: 222.111.222.111/32
    deny:
      ip: 111.222.111.222/32
    allow: all
  xmlrpc_access:
    allow:
      user: peter@example.com
    allow:
      user: ivone@example.com
    allow:
      user: bot@example.com
      ip: 10.0.0.0/24

acl: {NomACL: {TypeACL: ValeurACL}}

Cette option définit les listes de contrôle d'accès ../configuration/basic.md#acl|d'accès : des ensembles nommés de règles qui sont utilisés pour faire correspondre différentes cibles (telles qu'un JID ou une adresse IP). Chaque ensemble de règles a un nom NomACL : il peut s'agir de n'importe quelle chaîne de caractères à l'exception de all ou none (ce sont des noms prédéfinis pour les règles qui correspondent à tout ou rien respectivement). Le nom NomACL peut être référencé à partir d'autres parties du fichier de configuration, par exemple dans l'option access_rules. Les règles de NomACL sont représentées par le mappage {TypeACL: ValeurACL}. Celles-ci peuvent être l'une des suivantes :

ip: Réseau

La règle correspond à n'importe quelle adresse IP du Réseau.

node_glob: Modèle

Identique à node_regexp, mais la correspondance est effectuée sur un Modèle spécifié selon les règles utilisées par le shell Unix.

node_regexp: user_regexp@server_regexp

La règle correspond à n'importe quel JID dont la partie nœud correspond à l'expression régulière user_regexp et dont la partie serveur correspond à l'expression régulière server_regexp.

resource: Resource

La règle correspond à n'importe quel JID avec une ressource Resource.

resource_glob: Modèle

Identique à resource_regexp, mais la correspondance est effectuée sur un Modèle spécifié selon les règles utilisées par le shell Unix.

resource_regexp: Regexp

La règle correspond à n'importe quel JID avec une ressource qui correspond à l'expression régulière Regexp.

server: Serveur

La règle correspond à n'importe quel JID du serveur Serveur. La valeur de Serveur doit être un nom d'hôte ou une adresse IP valide.

server_glob: Modèle

Identique à server_regexp, mais la correspondance est effectuée sur un Modèle spécifié selon les règles utilisées par le shell Unix.

server_regexp: Regexp

La règle correspond à n'importe quel JID du serveur qui correspond à l'expression régulière Regexp.

user: NomUtilisateur

Si NomUtilisateur est sous la forme "utilisateur@serveur", la règle correspond à un JID par rapport à cette valeur. Sinon, si NomUtilisateur est sous la forme "utilisateur", la règle correspond à n'importe quel JID qui a NomUtilisateur dans la partie nœud tant que la partie serveur de ce JID est un hôte virtuel servi par ejabberd.

user_glob: Modèle

Identique à user_regexp, mais la correspondance est effectuée sur un Modèle spécifié selon les règles utilisées par le shell Unix.

user_regexp: Regexp

Si Regexp est sous la forme "regexp@server", la règle correspond à n'importe quel JID dont la partie nœud correspond à l'expression régulière "regexp" tant que la partie serveur de ce JID est égale à "server". Si Regexp est sous la forme "regexp", la règle correspond à n'importe quel JID dont la partie nœud correspond à l'expression régulière "regexp" tant que la partie serveur de ce JID est un hôte virtuel servi par ejabberd.

acme: Options

Configuration ACME basic.md#acme|ACME, pour obtenir automatiquement des certificats SSL pour les domaines servis par ejabberd, ce qui signifie que les demandes et renouvellements de certificats sont effectués auprès d'un serveur CA (alias "serveur ACME") en mode entièrement automatisé. Les Options sont :

auto: vrai | faux

Faut-il demander automatiquement des certificats pour tous les domaines configurés (qui n'ont pas encore de certificat) au démarrage du serveur ou lors du rechargement de la configuration. La valeur par défaut est vrai.

ca_url: URL

L'URL du répertoire ACME utilisée comme point d'entrée pour le serveur ACME. La valeur par défaut est https://acme-v02.api.letsencrypt.org/directory - l'URL du répertoire de l'autorité Let’s Encrypt.

certfiles : [Chemin, ...]

L'option accepte une liste de chemins de fichiers (avec éventuellement des caractères génériques) contenant soit des certificats PEM, soit des clés privées PEM. Au démarrage ou lors du rechargement de la configuration, ejabberd lit tous les certificats de ces fichiers, les trie, supprime les doublons, trouve les clés privées correspondantes, puis reconstruit les chaînes de certificats complètes pour une utilisation dans les connexions TLS. Utilisez cette option lorsque TLS est activé dans l'un des listeners d'ejabberd : ejabberd_c2s, ejabberd_http, etc. NOTE : si vous modifiez les fichiers de certificats ou si vous changez la valeur de l'option, exécutez ejabberdctl reload-config pour reconstruire et recharger les chaînes de certificats.

Exemples :

Si vous utilisez les certificats Let’s Encrypt pour votre domaine "domain.tld", la configuration ressemblera à ceci :

certfiles:
  - /etc/letsencrypt/live/domain.tld/fullchain.pem
  - /etc/letsencrypt/live/domain.tld/privkey.pem

disable_sasl_mechanisms : [Mécanisme, ...]

Spécifie une liste de mécanismes SASL (tels que DIGEST-MD5 ou SCRAM-SHA1) qui ne doivent pas être proposés au client. Pour plus de commodité, la valeur de Mécanisme ne tient pas compte de la casse. La valeur par défaut est une liste vide, c'est-à-dire qu'aucun mécanisme n'est désactivé par défaut.

disable_sasl_scram_downgrade_protection : vrai | faux

Permet de désactiver l'envoi de données requises par XEP-0474: SASL SCRAM Downgrade Protection. Il existe des clients bogués connus (comme ceux qui utilisent strophejs 1.6.2) qui ne pourront pas s'authentifier lorsque le serveur envoie des données de cette spécification. mod_muc

Ce module fournit la prise en charge de XEP-0045 : Multi-User Chat. Les utilisateurs peuvent découvrir les chambres existantes, les rejoindre ou les créer. Les occupants d'une chambre peuvent discuter publiquement ou avoir des conversations privées.

Le service MUC permet à n'importe quel identifiant Jabber d'enregistrer un pseudonyme, de sorte que personne d'autre ne puisse utiliser ce pseudonyme dans aucune chambre du service MUC. Pour enregistrer un pseudonyme, ouvrez la Découverte de Services dans votre client XMPP et enregistrez-vous auprès du service MUC.

Il est également possible d'enregistrer un pseudonyme dans une chambre, de sorte que personne d'autre ne puisse utiliser ce pseudonyme dans cette chambre. Si un pseudonyme est enregistré dans le service MUC, ce pseudonyme ne peut pas être enregistré dans une chambre, et vice versa : un pseudonyme enregistré dans une chambre ne peut pas être enregistré auprès du service MUC.

Ce module prend en charge le clustering et l'équilibrage de charge. Un module peut être démarré par nœud de cluster. Les chambres sont distribuées au moment de leur création sur toutes les instances du module MUC disponibles. Le module de discussion multi-utilisateurs est clusterisé mais les chambres elles-mêmes ne sont pas clusterisées ni tolérantes aux pannes : si le nœud gérant un ensemble de chambres tombe en panne, les chambres disparaissent et seront recréées sur un nœud disponible lors de la première tentative de connexion.

mod_sip

This module adds SIP proxy/registrar support for the corresponding virtual host.


Note

It is not enough to just load this module. You should also configure listeners and DNS records properly. For details see the section about the listen.md#ejabberd_sip|ejabberd_sip listen module in the ejabberd Documentation.

Available options:

always_record_route: true | false

Always insert "Record-Route" header into SIP messages. With this approach it is possible to bypass NATs/firewalls a bit more easily. The default value is true.

flow_timeout_tcp: timeout()

The option sets a keep-alive timer for SIP outbound TCP connections. The default value is 2 minutes.

flow_timeout_udp: timeout()

The options sets a keep-alive timer for SIP outbound UDP connections. The default value is 29 seconds.

record_route: URI

When the option always_record_route is set to true or when SIP outbound is utilized, ejabberd inserts "Record-Route" header field with this URI into a SIP message. The default is a SIP URI constructed from the virtual host on which the module is loaded.

routes: [URI, ...]

You can set a list of SIP URIs of routes pointing to this SIP proxy server. The default is a list containing a single SIP URI constructed from the virtual host on which the module is loaded.

via: [URI, ...]

A list to construct "Via" headers for inserting them into outgoing SIP messages. This is useful if you’re running your SIP proxy in a non-standard network topology. Every URI element in the list must be in the form of "scheme://host:port", where "transport" must be tls, tcp, or udp, "host" must be a domain name or an IP address and "port" must be an internet port number. Note that all parts of the URI are mandatory (e.g. you cannot omit "port" or "scheme").

Example: 

modules:
  mod_sip:
    always_record_route: false
    record_route: "sip:example.com;lr"
    routes:
      - "sip:example.com;lr"
      - "sip:sip.example.com;lr"
    flow_timeout_udp: 30 sec
    flow_timeout_tcp: 1 min
    via:
      - tls://sip-tls.example.com:5061
      - tcp://sip-tcp.example.com:5060
      - udp://sip-udp.example.com:5060

ack_timeout : timeout()

Un délai d'attente pour les accusés de réception de stanza. Le régler sur infinity désactive effectivement le délai d'attente. La valeur par défaut est 1 minute.

cache_life_time : timeout()

Identique à l'option de niveau supérieur cache_life_time, mais appliquée uniquement à ce module. La valeur par défaut est 48 heures.

cache_size : pos_integer() | infinity

Identique à l'option de niveau supérieur cache_size, mais appliquée uniquement à ce module.

max_ack_queue : Size

Cette option spécifie le nombre maximum de stanzas non acquittées mises en file d'attente pour une retransmission éventuelle. Lorsque la limite est dépassée, la session client est terminée. Les valeurs autorisées sont des entiers positifs et infinity. Par défaut, elle est définie à la même valeur que l'option resume_timeout.

Identique à l'option de niveau supérieur queue_type, mais appliquée uniquement à ce module.

Si cette option est définie sur true, toutes les stanzas de message qui n'ont pas été acquittées par le client seront renvoyées lors du délai d'attente de la session. Ce comportement est souvent souhaitable, mais peut avoir des résultats inattendus dans certaines circonstances. Par exemple, un message envoyé à deux ressources pourrait être renvoyé à l'une d'elles si l'autre a expiré. Par conséquent, la valeur par défaut pour cette option est false, ce qui indique à ejabberd de générer plutôt un message d'erreur. Alternativement, l'option peut être définie sur if_offline. Dans ce cas, les messages non acquittés sont renvoyés uniquement si aucune autre ressource n'est en ligne lorsque la session expire. Sinon, des messages d'erreur sont générés.

Cette option configure la période (par défaut) pendant laquelle une session expire si la connexion est perdue. Pendant cette période, un client peut reprendre sa session. Notez que le client peut demander une valeur de délai d'attente différente, voir l'option max_resume_timeout. La définir sur 0 désactive effectivement la reprise de session. La valeur par défaut est 5 minutes.

Le client de l'utilisateur peut stocker un avatar dans le vCard de l'utilisateur. Le protocole d'avatars basés sur vCard (XEP-0153) fournit une méthode pour que les clients informent les contacts de la valeur du hachage de l'avatar. Cependant, les clients simples ou petits peuvent ne pas implémenter ce

Si ce module est activé, toutes les stanzas de présence sortantes des clients reçoivent automatiquement le hachage de l'avatar au nom du client. Ainsi, les contacts reçoivent les stanzas de présence avec les Données de mise à jour décrites dans XEP-0153 comme si le client les avait insérées lui-même. Si le client avait déjà inclus un tel élément dans la stanza de présence, il est remplacé par l'élément généré par

ejabberd.

En activant ce module, chaque modification de vCard produit un recalcul du hachage, et chaque présence envoyée par un client produit une récupération de hachage et une réécriture de la stanza de présence. Pour cette raison, l'activation de ce module introduira une surcharge de calcul sur les serveurs avec des clients qui changent fréquemment leur présence. Cependant, la surcharge est considérablement réduite par l'utilisation du cache, vous ne voudrez probablement pas définir use_cache à false

.

De nos jours, XEP-0153 est principalement utilisé en "lecture seule", c'est-à-dire que les clients modernes ne publient pas leurs avatars dans les vCards. Ainsi, dans la majorité des cas, le module n'est utilisé qu'avec mod_avatar pour assurer la rétrocompatibilit

é
