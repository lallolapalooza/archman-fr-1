INTRODUCTIO

N

Extra CMake Modules (ECM) fournit divers modules qui offrent des fonctions utiles pour les scripts CMake. ECM fournit en fait trois types de modules utilisables depuis les scripts CMake : ceux qui étendent les fonctionnalités de la commande find_package sont documentés dans ecm-find-modules(7) <#manual:ecm-find-modules(7)> ; ceux qui fournissent des paramètres standard pour les logiciels produits par la communauté KDE sont documentés dans ecm-kde-modules(7) <#manual:ecm-kde-modules(7)>. Les autres fournissent des macros et des fonctions pour une utilisation générale par les scripts CMake et sont documentés

ici.

Pour utiliser ces modules, vous devez indiquer à CMake de trouver le paquet ECM, puis ajouter soit ${ECM_MODULE_PATH} ou ${ECM_MODULE_DIR} à la variable CMAKE_MODULE_PATH

: 
find_package(ECM RE
QUIRED NO_MODULE) s
et(CMAKE_MODULE_PATH
${ECM_MODULE_DIR})

L'utilisation de ${ECM_MODULE_PATH} rendra également disponibles les modules de recherche et les modules

KDE.

Notez qu'il existe également des modules de chaîne d'outils, documentés dans ecm-toolchains(7) <#manual:ecm-toolchains(7)>, mais ceux-ci sont utilisés par les utilisateu

rs qui compilent le logiciel plutôt que par les
développeurs qui écrivent des scripts CMake.

ECMAddQch

Ce module fournit la fonction ecm_add_qch pour générer des fichiers de documentation d'API au format QCH, et la fonction ecm_install_qch_export pour générer et installer des cibles CMake exportées pour ces fichiers QCH générés afin de permettre aux compilations d'autres logiciels de générer des fichiers QCH pour créer des liens vers les fichiers QCH donnés.

ecm_add_qch(<nom_cible>
    NOM <nom>
    VERSION <version>
    QCH_INSTALL_DESTINATION <chemin_installation_fichier_qch>
    TAGFILE_INSTALL_DESTINATION <chemin_installation_fichier_tags>
    [COMPONENT <composant>]
    [BASE_NAME <nom_base>]
    [SOURCE_DIRS <repertoire> [<repertoire2> [...]]]
    [SOURCES <fichier> [<fichier2> [...]]]
    |MD_MAINPAGE <fichier_md>]
    [INCLUDE_DIRS <repertoire_inc> [<repertoire_inc2> [...]]]
    [IMAGE_DIRS <repertoire_img> [<repertoire_img2> [...]]]
    [EXAMPLE_DIRS <repertoire_ex> [<repertoire_ex2> [...]]]
    [ORG_DOMAIN <domaine>]
    [NAMESPACE <espace_nom>]
    [LINK_QCHS <qch> [<qch2> [...]]]
    [PREDEFINED_MACROS <macro[=contenu]> [<macro2[=contenu]> [...]]]
    [BLANK_MACROS <macro> [<macro2> [...]]]
    [CONFIG_TEMPLATE <fichier_template_config>]
    [VERBOSE]
)

Cette macro ajoute une cible nommée <nom_cible> pour la création d'un manuel de documentation d'API au format QCH à partir des sources données. Elle utilise actuellement doxygen, les versions futures pourraient optionnellement permettre également d'autres outils. À côté du fichier QCH, la cible générera un fichier de tags doxygen correspondant, qui permet de créer des liens à partir d'autres documentations vers le fichier QCH généré.

Il est recommandé de rendre l'utilisation de cette macro optionnelle, en faisant dépendre l'appel à ecm_add_qch d'une option CMake définie, avec un nom tel que BUILD_QCH et étant TRUE par défaut. Cela permettra aux développeurs d'économiser des ressources lors des cycles de développement sources normaux en définissant cette option sur FALSE.

La macro définira les propriétés de cible DOXYGEN_TAGFILE, QHP_NAMESPACE, QHP_NAMESPACE_VERSIONED, QHP_VIRTUALFOLDER et LINK_QCHS avec les valeurs respectives, pour permettre à d'autres codes d'y accéder, par exemple la macro ecm_install_qch_export. Pour activer l'utilisation de la cible <nom_cible> comme élément pour LINK_QCHS dans d'autres appels ecm_add_qch dans la construction actuelle, une propriété de cible DOXYGEN_TAGFILE_BUILD est en outre définie, avec le chemin du fichier de tags doxygen créé dans le répertoire de compilation. Si elle existe, ecm_add_qch utilisera cette propriété au lieu de DOXYGEN_TAGFILE pour accéder au fichier de tags.

NOM spécifie le nom de la documentation générée.

VERSION spécifie la version de la bibliothèque pour laquelle la documentation est créée.

BASE_NAME spécifie le nom de base pour les fichiers générés. Le nom de base par défaut est <nom>.

SOURCE_DIRS spécifie les répertoires (incl. sous-répertoires) contenant les fichiers sources pour lesquels la documentation d'API doit être générée. Les répertoires peuvent être relatifs au répertoire source actuel. Les dépendances aux fichiers dans les répertoires ne sont pas suivies actuellement, autrement qu'avec l'argument SOURCES. Donc, ne pas utiliser pour les sources générées pendant la compilation. Doit être utilisé lorsque SOURCES ou CONFIG_TEMPLATE ne sont pas utilisés.

SOURCES spécifie les fichiers sources pour lesquels la documentation d'API doit être générée. Doit être utilisé lorsque SOURCE_DIRS ou CONFIG_TEMPLATE ne sont pas utilisés.

MD_MAINPAGE spécifie un fichier au format Markdown qui doit être utilisé comme page principale. Cette page remplacera toute commande \mainpage dans les sources incluses.

INCLUDE_DIRS spécifie les répertoires qui doivent être recherchés pour les en-têtes inclus. Les répertoires peuvent être relatifs au répertoire source actuel. Depuis 5.63.

IMAGE_DIRS spécifie les répertoires contenant les images incluses dans la documentation. Les répertoires peuvent être relatifs au répertoire source actuel.

EXAMPLE_DIRS spécifie les répertoires contenant les exemples inclus dans la documentation. Les répertoires peuvent être relatifs au répertoire source actuel.

QCH_INSTALL_DESTINATION spécifie où le fichier QCH généré sera installé.

TAGFILE_INSTALL_DESTINATION spécifie où le fichier de tags généré sera installé.

COMPONENT spécifie le nom du composant d'installation auquel les règles d'installation pour le fichier QCH généré et le fichier de tags sont associées.

NAMESPACE peut être utilisé pour définir un espace de noms personnalisé <espace_nom> du fichier QCH généré. L'espace de noms est utilisé comme identifiant unique par QHelpEngine (voir https://doc.qt.io/qt-5/qthelpproject.html#namespace). L'espace de noms par défaut est <domaine>.<nom>. Doit être utilisé lorsque ORG_DOMAIN n'est pas utilisé.

ORG_DOMAIN peut être utilisé pour définir le préfixe du domaine d'organisation pour l'espace de noms par défaut du fichier QCH généré. Doit être utilisé lorsque NAMESPACE n'est pas utilisé.

LINK_QCHS spécifie une liste d'autres cibles QCH qui doivent être utilisées pour créer des références à la documentation d'API du code dans des bibliothèques externes. Pour chaque cible <qch> dans la liste, les propriétés de cible suivantes sont attendues : DOXYGEN_TAGFILE, QHP_NAMESPACE et QHP_VIRTUALFOLDER. Si l'une d'elles n'existe pas, <qch> sera ignoré. Utilisez la macro ecm_install_qch_export pour exporter une cible avec ces propriétés avec la configuration CMake d'une bibliothèque. Toute cible <qch> peut également être une cible créée précédemment dans le même système de compilation par un autre appel de ecm_add_qch.

PREDEFINED_MACROS spécifie une liste de macros C/C++ qui doivent être traitées comme spécifié par l'outil de génération de documentation d'API. Par exemple, des macros définies uniquement dans les fichiers générés, dont la définition pourrait ne pas être disponible pour l'outil.

BLANK_MACROS spécifie une liste de noms de macros C/C++ qui doivent être ignorés par l'outil de génération de documentation d'API et traités comme s'ils étaient résolus en chaînes vides. Par exemple, des macros d'exportation définies uniquement dans les fichiers générés, dont la définition pourrait ne pas être disponible pour l'outil.

CONFIG_TEMPLATE spécifie un fichier template CMake personnalisé pour le fichier de configuration créé pour contrôler l'exécution de l'outil de génération de documentation d'API. Les variables CMake suivantes doivent être utilisées : - ECM_QCH_DOXYGEN_QHELPGENERATOR_EXECUTABLE - ECM_QCH_DOXYGEN_FILEPATH, ECM_QCH_DOXYGEN_TAGFILE Les variables CMake suivantes peuvent être utilisées : - ECM_QCH_DOXYGEN_PROJECTNAME - ECM_QCH_DOXYGEN_PROJECTVERSION - ECM_QCH_DOXYGEN_VIRTUALFOLDER - ECM_QCH_DOXYGEN_FULLNAMESPACE - ECM_QCH_DOXYGEN_TAGFILES - ECM_QCH_DOXYGEN_WARN_LOGFILE - ECM_QCH_DOXYGEN_QUIET Il n'y a aucune garantie que les autres variables CMake actuellement utilisées dans le modèle de fichier de configuration par défaut seront également présentes avec la même sémantique dans les futures versions de cette macro.

VERBOSE indique à l'outil de génération de documentation d'API d'être plus verbeux sur son activité.

Le fichier de configuration par défaut pour l'outil de génération de documentation d'API, donc celui utilisé lorsque CONFIG_TEMPLATE n'est pas utilisé, permet au code de gérer le cas d'être traité par l'outil en définissant la macro préprocesseur C/C++ K_DOXYGEN lors de son exécution (depuis v5.67.0). Pour la compatibilité ascendante, la définition DOXYGEN_SHOULD_SKIP_THIS est également définie, mais son utilisation est dépréciée.

Exemple d'utilisation :

ecm_add_qch(
    MyLib_QCH
    NOM MyLib
    VERSION "0.42.0"
    ORG_DOMAIN org.myorg
    SOURCE_DIRS
        src
    LINK_QCHS
        Qt5Core_QCH
        Qt5Xml_QCH
        Qt5Gui_QCH
        Qt5Widgets_QCH
    BLANK_MACROS
        MyLib_EXPORT
        MyLib_DEPRECATED
    TAGFILE_INSTALL_DESTINATION ${CMAKE_INSTALL_PREFIX}/share/docs/tags
    QCH_INSTALL_DESTINATION ${CMAKE_INSTALL_PREFIX}/share/docs/qch
    COMPONENT Devel
)

ecm_install_qch_export(
    TARGETS [<nom> [<nom2> [...]]]
    FILE <fichier>
    DESTINATION <destination>
    [COMPONENT <composant>]
)

Cette macro crée et installe un fichier CMake <fichier> qui exporte les cibles QCH données <nom> etc., de sorte qu'elles puissent être récupérées par les compilations basées sur CMake d'autres logiciels qui génèrent également des fichiers QCH (en utilisant ecm_add_qch) et qui devraient inclure des liens vers les fichiers QCH créés par les cibles données. Le fichier CMake installé <fichier> est supposé être inclus par le fichier de configuration CMake créé pour le logiciel que les fichiers QCH associés documentent.

TARGETS spécifie les cibles QCH qui doivent être exportées. Si une cible n'existe pas ou n'a pas toutes les propriétés nécessaires, un avertissement sera généré et la cible sera ignorée. Ce comportement pourrait changer dans les versions futures pour aboutir à un échec.

FILE spécifie le nom du fichier CMake créé, typiquement avec une extension .cmake.

DESTINATION spécifie le répertoire sur disque vers lequel le fichier sera installé. Il s'agit généralement du même répertoire que celui où les fichiers de configuration CMake pour ce logiciel sont installés.

COMPONENT spécifie le nom du composant d'installation auquel la règle d'installation est associée.

Exemple d'utilisation :

ecm_install_qch_export(
    TARGETS MyLib_QCH
    FILE MyLibQCHTargets.cmake
    DESTINATION "${CMAKE_INSTALL_PREFIX}/lib/cmake/MyLib"
    COMPONENT Devel
)

ECMFindSubmodule

Find Git submodules and integrate them into the build.

This module helps to find Git submodules. These are specified in the .gitmodules file.

ecm_find_submodule(SUBMODULE <name>
                   [SOURCE <dir>]
                   [[GIT_TAG <tag>] | [GIT_SHA1 <sha1>]]
                   [GIT_REMOTE <remote>]
                   [NO_UPDATE_CLONE])

The SUBMODULE argument is the name of the submodule as it is specified in the .gitmodules file. The SOURCE argument specifies the directory relative to the top of the repository where the submodule resides. If it is not given, submodule will be used as the directory name.

If GIT_TAG or GIT_SHA1 are given, these will be used to check out a specific tag or SHA1. If neither is given, the current SHA1 from the repository will be used.

By default the submodule is checked out to a path relative to CMAKE_BINARY_DIR. The path is determined by the SOURCE argument, or the SUBMODULE argument if SOURCE is not given.

If the submodule is not yet checked out, it will be cloned and checked out. If it is already checked out, it will be updated to the specified tag or SHA1. The check out path is added to CMAKE_MODULE_PATH.

If NO_UPDATE_CLONE is specified, the submodule will not be updated or cloned if it is not present.

Set the default installation directories.

When this module is included, it defines CMake variables that can be used to control the default installation directories for headers, libraries, etc. These variables correspond to the ones used by the install() command.

By default these variables are set according to the KDE installation guidelines. They can be overridden by defining them before including this module.

The following variables are defined:

CMAKE_INSTALL_PREFIX
The default install prefix. If not specified, CMake defaults to /usr/local.
CMAKE_INSTALL_FULL_BINDIR
The default install directory for executables. If not specified, it defaults to ${CMAKE_INSTALL_PREFIX}/bin.
CMAKE_INSTALL_FULL_LIBDIR
The default install directory for libraries. If not specified, it defaults to ${CMAKE_INSTALL_PREFIX}/lib.
CMAKE_INSTALL_FULL_INCLUDEDIR
The default install directory for header files. If not specified, it defaults to ${CMAKE_INSTALL_PREFIX}/include.
CMAKE_INSTALL_FULL_INCLUDEDIR_NOARCH
The default install directory for header files not architecture-specific. Defaults to ${CMAKE_INSTALL_FULL_INCLUDEDIR}.
CMAKE_INSTALL_FULL_DATADIR
The default install directory for data files. Defaults to ${CMAKE_INSTALL_PREFIX}/share.
CMAKE_INSTALL_FULL_QDATADIR
The default install directory for Qt data files. Defaults to ${CMAKE_INSTALL_FULL_DATADIR}/qt5.
CMAKE_INSTALL_FULL_QMLDIR
The default install directory for QML files. Defaults to ${CMAKE_INSTALL_FULL_DATADIR}/qt5/qml.
CMAKE_INSTALL_FULL_PLUGINDIR
The default install directory for plugins. Defaults to ${CMAKE_INSTALL_FULL_LIBDIR}/qt5/plugins.
CMAKE_INSTALL_FULL_LOCALEDIR
The default install directory for locale data. Defaults to ${CMAKE_INSTALL_FULL_DATADIR}/locale.
CMAKE_INSTALL_FULL_CONFIGDIR
The default install directory for system-wide configuration files. Defaults to ${CMAKE_INSTALL_FULL_DATADIR}/etc.
CMAKE_INSTALL_FULL_APPDIR
The default install directory for application data. Defaults to ${CMAKE_INSTALL_FULL_DATADIR}/app.

Generate header files from templates.

This module provides the macro ecm_generate_headers which can be used to generate header files from templates.

ecm_generate_headers(OUT <output_directory>

                     ENABLE_FEATURE_X ON)

This will generate a header file named config.h in ${CMAKE_BINARY_DIR}/include/generated by substituting PACKAGE_VERSION and ENABLE_FEATURE_X in the config.h.in template.

ECMWinResolveSymlinks

Resolve pseudo-symlinks created by git when cloning on Windows.

When git checks out a repository with UNIX symlinks on Windows machine, it creates a text file for each symlink, containing a relative path to the real file. This function would recursively walk over specified directory and replace pseudo-symlinks with corresponding real file’s contents. It would then run git update-index --assume-unchanged on them to trick git.

This is useful for projects like “breeze-icons” that contain many identical icons implemented as symlinks.

ECMUninstallTarget

Add an uninstall target.

By including this module, an uninstall target will be added to your CMake project. This will remove all files installed (or updated) by a previous invocation of the install target. It will not remove files created or modified by an install(SCRIPT) or install(CODE) command; you should create a custom uninstallation target for these and use add_dependency to make the uninstall target depend on it:

include(ECMUninstallTarget)
install(SCRIPT install-foo.cmake)
add_custom_target(uninstall_foo COMMAND ${CMAKE_COMMAND} -P uninstall-foo.cmake)
add_dependency(uninstall uninstall_foo)

The target will fail if the install target has not yet been run (so it is not possible to run CMake on the project and then immediately run the uninstall target).

Warning:

CMake deliberately does not provide an uninstall target by default on the basis that such a target has the potential to remove important files from a user’s computer. Use with caution.

ECMUseFindModules

Selectively use some of the find modules provided by extra-cmake-modules.

This module is automatically available once extra-cmake-modules has been found, so it is not necessary to include(ECMUseFindModules) explicitly.

ecm_use_find_modules(DIR <dir>
                     MODULES module1.cmake [module2.cmake [...]]
                     [NO_OVERRIDE])

This allows selective use of the find modules provided by ECM, including deferring to CMake’s versions of those modules if it has them. Rather than adding ${ECM_FIND_MODULE_DIR} to CMAKE_MODULE_PATH, you use ecm_use_find_modules() to copy the modules you want to a local (build) directory, and add that to CMAKE_MODULE_PATH.

The find modules given to MODULES will be copied to the directory given by DIR (which should be located in ${CMAKE_BINARY_DIR} and added to CMAKE_MODULE_PATH). If NO_OVERRIDE is given, only modules not also provided by CMake will be copied.

Example:

find_package(ECM REQUIRED)
ecm_use_find_modules(
    DIR ${CMAKE_BINARY_DIR}/cmake
    MODULES FindEGL.cmake
    NO_OVERRIDE
)
set(CMAKE_MODULE_PATH ${CMAKE_BINARY_DIR}/cmake)

This example will make FindEGL.cmake available in your project, but only as long as it is not yet part of CMake. Calls to find_package(EGL) will then make use of this copied module (or the CMake module if it exists).

Another possible use for this macro is to take copies of find modules that can be installed along with config files if they are required as a dependency (for example, if targets provided by the find module are in the link interface of a library).
