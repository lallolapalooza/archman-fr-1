Escripts

précompilés Un script peut aussi contenir du code beam précompilé. Pour créer un escript précompilé, il est recommandé d'utiliser escript:create/2. Dans un script précompilé, l'interprétation de l'en-tête du script est la même que dans un script contenant du code source. Cela signifie que vous pouvez rendre un fichier beam exécutable en préfixant le fichier avec les lignes commençant par #! et %%! mentionnées ci-dessus. Dans un script précompilé, la fonction main/1 doit être

exportée.

Une autre option est d'avoir une archive Erlang entière dans le script. Dans un script archive, l'interprétation de l'en-tête du script est la même que dans un script contenant du code source. Cela signifie que vous pouvez rendre un fichier archive exécutable en préfixant le fichier avec les lignes commençant par #! et %%! mentionnées ci-dessus. Dans un script archive, la fonction main/1 doit être exportée. Par défaut, la fonction main/1 dans le module portant le même nom que le nom de base du fichier escript est appelée. Ce comportement peut être remplacé en définissant le drapeau -escript main Module comme l'un des drapeaux de l'émulateur. Module doit être le nom d'un module qui a une fonction main/1 exportée. Regrouper

des escripts Il est possible de regrouper des escripts avec un système d'exécution Erlang pour le rendre autosuffisant et relocalisable. Dans un tel système autonome, les escripts devraient être situés dans le répertoire bin de premier niveau du système autonome et avoir .escript comme extension de fichier. De plus, le programme (intégré) escript devrait être copié dans le même répertoire et porter le nom original du script (sans l'extension .escript). Cela permettra l'utilisation du système

d'exécution

Erlang regroupé. Le programme (intégré) escript détermine d'abord quelsystème d'exécution à utiliser et le démarre pour exécuter votre script. Habituellement, le système d'exécution se trouve dans la même installation Erlang que le programme escript lui-même. Mais pour les systèmes autonomes avec un ou plusieurs escripts, il peut arriver que le programme escript dans votre path démarre en réalité le système d'exécution fourni avec l'escript. C'est intentionnel, et cela se produit typiquement lorsque le répertoire bin du système autonome n'est pas dans le path d'exécution (car cela pourrait faire que son programme erl écrase celui souhaité) et que les escript(s) sont référencés via des liens symboliques depuis un répertoire bin du
