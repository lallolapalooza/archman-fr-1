DESCRIPTIO

N

eventfd() crée un « objet eventfd » qui peut être utilisé comme mécanisme d'attente/notification d'événements par les applications en espace utilisateur, et par le noyau pour notifier les applications en espace utilisateur d'événements. L'objet contient un entier non signé sur 64 bits (uint64_t) compteur qui est maintenu par le noyau. Ce compteur est initialisé avec la valeur spécifiée dans l'argument initval

.

En tant que valeur de retour, eventfd() renvoie un nouveau descripteur de fichier qui peut être utilisé pour référencer l'objet

eventfd.

Les valeurs suivantes peuvent être combinées par un OU bit à bit dans flags pour modifier le comportement de eventfd()

:
EFD_CLOEXEC (depuis Linux 2.6.
27)
Définit l'indicateur close-on-exec (FD_CLOEXEC) sur le nouveau descripteur de fichier. Voir la description de l'indicateur O_CLOEXEC dans open(2) pour les raisons pour lesquelles cela peut être
utile.
EFD_NONBLOCK (depuis Linux 2.6.
27)
Définit l'indicateur d'état de fichier O_NONBLOCK sur la description de fichier ouverte (voir open(2)) à laquelle le nouveau descripteur de fichier fait référence. L'utilisation de cet indicateur évite des appels supplémentaires à fcntl(2) pour obtenir le même
résultat.
EFD_SEMAPHORE (depuis Linux 2.6.
30)
Fournit des sémantiques de sémaphore pou
r les lectures depuis le nouveau descri
pteur de fichier. Voir ci-dessous.

Jusqu'à Linux 2.6.26, l'argument flags n'est pas utilisé et doit être spécifié comme

zéro.

Les opérations suivantes peuvent être effectuées sur le descripteur de fichier renvoyé par eventfd()

read(
2)
Chaque read(2) réussi renvoie un entier de 8 octets. Un read(2) échoue avec l'erreur EINVAL si la taille du tampon four
ni est infér
ieure à 8 octets.
La valeur renvoyée par read(2) est dans l'ordre d'octets de l'hôte — c'est-à-dire, l'ordre natif des entiers sur la machine
hôte.
La sémantique de read(2) dépend de la question de savoir si le compteur eventfd a actuellement une valeur non nulle et si l'indicateur EFD_SEMAPHORE a été spécifié lors de la
création du descripteu

•
Si EFD_SEMAPHORE n'a pas été spécifié et que le compteur eventfd a une valeur non nulle, alors un read(2) renvoie 8 octets contenant cette valeur, et la valeur du compteur est réinitialisée à
zéro.
•
Si EFD_SEMAPHORE a été spécifié et que le compteur eventfd a une valeur non nulle, alors un read(2) renvoie 8 octets contenant la valeur 1, et la valeur du compteur est décrémentée de
1.
•
Si le compteur eventfd est zéro au moment de l'appel à read(2), alors l'appel se bloque jusqu'à ce que le compteur devienne non nul (auquel moment, le read(2) se poursuit comme décrit ci-dessus) ou échoue avec l'erreur EAGAIN si le descripteur
de fichier a

2)
Un write(2) ajoute la valeur d'entier de 8 octets fournie dans son tampon au compteur. La valeur maximale pouvant être stockée dans le compteur est la plus grande valeur non signée sur 64 bits moins 1 (c'est-à-dire, 0xfffffffffffffffe). Si l'addition faisait dépasser la valeur maximale au compteur, alors le write(2) se bloque jusqu'à ce qu'un read(2) soit effectué sur le descripteur de fichier, ou échoue avec l'erreur EAGAIN si le descripteur de
fichier a été re
ndu non bloquant.
Un write(2) échoue avec l'erreur EINVAL si la taille du tampon fourni est inférieure à 8 octets, ou si une tentative est faite d'écrire la valeur 0xfffffffffffffff
f

Le descripteur de fichier renvoyé prend en charge poll(2) (et de manière analogue epoll(7)) et select(2), c
omme
suit :
•
Le descripteur de fichier est lisible (l'argument select(2) readfds ; l'indicateur poll(2) POLLIN) si le compteur a une valeur supérieure
à 0.
•
Le descripteur de fichier est inscriptible (l'argument select(2) writefds ; l'indicateur poll(2) POLLOUT) s'il est possible d'écrire une valeur d'au moins « 1 » sans se
bloquer.
•
Si un débordement de la valeur du compteur a été détecté, alors select(2) indique le descripteur de fichier comme étant à la fois lisible et inscriptible, et poll(2) renvoie un événement POLLERR. Comme noté ci-dessus, write(2) ne peut jamais faire déborder le compteur. Cependant, un débordement peut survenir si 2^64 « publications de signal » eventfd ont été effectuées par le sous-système KAIO (théoriquement possible, mais pratiquement peu probable). Si un débordement s'est produit, alors read(2) renverra cette valeur maximale uint64_t (c'est-à-

fffffff).

noyau

Il existe deux appels système Linux sous-jacents : eventfd() et le plus récent eventfd2(). Le premier appel système n'implémente pas d' argument flags. Le second appel système implémente les valeurs flags décrites ci-dessus. La fonction d'encapsulation de la glibc utilisera eventfd2() lorsqu'

NOTE

S

Les applications peuvent utiliser un descripteur de fichier eventfd au lieu d'un tube (voir pipe(2)) dans tous les cas où un tube est utilisé simplement pour signaler des événements. La surcharge du noyau d'un descripteur de fichier eventfd est beaucoup plus faible que celle d'un tube, et un seul descripteur de fichier est requis (contre les deux requis pour un tube)

.

Lorsqu'il est utilisé dans le noyau, un descripteur de fichier eventfd peut fournir un pont du noyau vers l'espace utilisateur, permettant, par exemple, des fonctionnalités comme KAIO (AIO du noyau) de signaler à un descripteur de fichier qu'une opération est

terminée.

Un point clé concernant un descripteur de fichier eventfd est qu'il peut être surveillé comme n'importe quel autre descripteur de fichier en utilisant select(2), poll(2), ou epoll(7). Cela signifie qu'une application peut surveiller simultanément la disponibilité des fichiers « traditionnels » et la disponibilité d'autres mécanismes du noyau qui prennent en charge l'interface eventfd. (Sans l' interface eventfd(), ces mécanismes ne pourraient pas être multiplexés via select(2), poll(2), ou epoll(7).

)

La valeur actuelle d'un compteur eventfd peut être consultée via l'entrée correspondant au descripteur de fichier dans le répertoire /proc/pid/fdinfo du processus. Voir proc(5) pour plu

s de
détails.

EXEMPLE

S

Le programme suivant crée un descripteur de fichier eventfd puis se divise (fork) pour créer un processus enfant. Pendant que le parent dort brièvement, l'enfant écrit chacun des entiers fournis dans les arguments de la ligne de commande du programme sur le descripteur de fichier eventfd. Lorsque le parent a terminé de dormir, il lit depuis le descripteur de fichier

eventfd.

La session de shell suivante montre une exécution d'exemple du programme

: 


$ ./a.out 1 2 4 7 14
Enfant écrit 1 sur efd
Enfant écrit 2 sur efd
Enfant écrit 4 sur efd
Enfant écrit 7 sur efd
Enfant écrit 14 sur efd
Enfant a terminé la boucle d'écriture
Parent sur le point de lire
Parent a lu 28 (0x1c) depuis
efd

Source du

programme 
#include <err.h>
#include <inttypes.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/eventfd.h>
#include <sys/types.h>
#include <unistd.h>
int
main(int argc, char *argv[])
{
    int       efd;
    uint64_t  u;
    ssize_t   s;
    if (argc < 2) {
        fprintf(stderr, "Usage: %s <num>...\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    efd = eventfd(0, 0);
    if (efd == -1)
        err(EXIT_FAILURE, "eventfd");
    switch (fork()) {
    case 0:
        for (size_t j = 1; j < argc; j++) {
            printf("Child writing %s to efd\n", argv[j]);
            u = strtoull(argv[j], NULL, 0);
                    /* strtoull() allows various bases */
            s = write(efd, &u, sizeof(uint64_t));
            if (s != sizeof(uint64_t))
                err(EXIT_FAILURE, "write");
        }
        printf("Child completed write loop\n");
        exit(EXIT_SUCCESS);
    default:
        sleep(2);
        printf("Parent about to read\n");
        s = read(efd, &u, sizeof(uint64_t));
        if (s != sizeof(uint64_t))
            err(EXIT_FAILURE, "read");
        printf("Parent read %"PRIu64" (%#"PRIx64") from efd\n", u, u);
        exit(EXIT_SUCCESS);
    case -1:
        err(EXIT_FAILURE, "fork");
}
}
