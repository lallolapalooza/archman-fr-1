DESCRIPTIO

N

eventfd() crée un « objet eventfd » qui peut être utilisé comme mécanisme d'attente/notification d'événements par les applications en espace utilisateur, et par le noyau pour notifier les applications en espace utilisateur d'événements. L'objet contient un entier non signé de 64 bits (uint64_t) compteur qui est maintenu par le noyau. Ce compteur est initialisé avec la valeur spécifiée dans l'argument initval

.

En tant que valeur de retour, eventfd() retourne un nouveau descripteur de fichier qui peut être utilisé pour référencer l'objet

eventfd.

Les valeurs suivantes peuvent être combinées par un OU bit à bit dans flags pour modifier le comportement de eventfd()

:
EFD_CLOEXEC (depuis Linux 2.6.
27)
Définit le drapeau close-on-exec (FD_CLOEXEC) sur le nouveau descripteur de fichier. Voir la description du drapeau O_CLOEXEC dans open(2) pour les raisons pour lesquelles cela peut être
utile.
EFD_NONBLOCK (depuis Linux 2.6.
27)
Définit le drapeau d'état de fichier O_NONBLOCK sur la description de fichier ouverte (voir open(2)) à laquelle le nouveau descripteur de fichier fait référence. L'utilisation de ce drapeau évite des appels supplémentaires à fcntl(2) pour obtenir le même
résultat.
EFD_SEMAPHORE (depuis Linux 2.6.
30)
Fournit une sémantique semblable à celle d'un
sémaphore pour les lectures depuis le nouveau
descripteur de fichier. Voir ci-dessous.

Jusqu'à Linux 2.6.26, l' argument flags n'est pas utilisé et doit être spécifié comme

zéro.

Les opérations suivantes peuvent être effectuées sur le descripteur de fichier retourné par eventfd()

:
read(
2)
Chaque read(2) réussi retourne un entier de 8 octets. Un read(2) échoue avec l'erreur EINVAL si la taille du tampon four
ni est infér
ieure à 8 octets.
La valeur retournée par read(2) est dans l'ordre d'octets de l'hôte — c'est-à-dire, l'ordre natif des entiers sur la machine
hôte.
La sémantique de read(2) dépend de savoir si le compteur eventfd a actuellement une valeur non nulle et si le drapeau EFD_SEMAPHORE a été spécifié lors d
e la création du descript
eur de fichier eventfd :
•
Si EFD_SEMAPHORE n'a pas été spécifié et que le compteur eventfd a une valeur non nulle, alors un read(2) retourne 8 octets contenant cette valeur, et la valeur du compteur est réinitialisée à
zéro.
•
Si EFD_SEMAPHORE a été spécifié et que le compteur eventfd a une valeur non nulle, alors un read(2) retourne 8 octets contenant la valeur 1, et la valeur du compteur est décrémentée de
1.
•
Si le compteur eventfd est zéro au moment de l'appel à read(2), alors l'appel se bloque jusqu'à ce que le compteur devienne non nul (auquel moment, le read(2) se poursuit comme décrit ci-dessus) ou échoue avec l'erreur EAGAIN si le descripteur
de fichier a

2)
Un appel write(2) ajoute la valeur entière de 8 octets fournie dans son tampon au compteur. La valeur maximale pouvant être stockée dans le compteur est la plus grande valeur non signée de 64 bits moins 1 (c'est-à-dire 0xfffffffffffffffe). Si l'addition fait que la valeur du compteur dépasse le maximum, alors le write(2) se bloque jusqu'à ce qu'un read(2) soit effectué sur le descripteur de fichier, ou échoue avec l'erreur EAGAIN si le descripteur de
fichier a été re
ndu non bloquant.
Un write(2) échoue avec l'erreur EINVAL si la taille du tampon fourni est inférieure à 8 octets, ou si une tentative est faite d'écrire la valeur 0xfffffffffffffff
f
.

Le descripteur de fichier retourné prend en charge poll(2) (et de manière analogue epoll(7)) et select(2), c
omme
suit :
•
Le descripteur de fichier est lisible (l' argument readfds de select(2) ; le drapeau POLLIN de poll(2)) si le compteur a une valeur supérieure
à 0.
•
Le descripteur de fichier est inscriptible (l' argument writefds de select(2) ; le drapeau POLLOUT de poll(2)) s'il est possible d'écrire une valeur d'au moins « 1 » sans se
bloquer.
•
Si un débordement de la valeur du compteur a été détecté, alors select(2) indique le descripteur de fichier comme étant à la fois lisible et inscriptible, et poll(2) retourne un événement POLLERR. Comme noté ci-dessus, write(2) ne peut jamais faire déborder le compteur. Cependant, un débordement peut se produire si 2^64 « publications de signal » eventfd ont été effectuées par le sous-système KAIO (théoriquement possible, mais pratiquement peu probable). Si un débordement s'est produit, alors read(2) retournera cette valeur uint64_t maximale (c'

C/noyau

Il existe deux appels système Linux sous-jacents : eventfd() et le plus récent eventfd2(). L'ancien appel système n'implémente pas un argument flags. Le plus récent appel système implémente les valeurs de flags décrites ci-dessus. La fonction wrapper de glibc utilisera eventfd2() lorsqu'

NOTE

S

Les applications peuvent utiliser un descripteur de fichier eventfd au lieu d'un tube (voir pipe(2)) dans tous les cas où un tube est utilisé simplement pour signaler des événements. La surcharge du noyau d'un descripteur de fichier eventfd est bien moindre que celle d'un tube, et un seul descripteur de fichier est requis (contre les deux requis pour un tube)

.

Lorsqu'il est utilisé dans le noyau, un descripteur de fichier eventfd peut fournir un pont du noyau vers l'espace utilisateur, permettant, par exemple, des fonctionnalités comme KAIO (AIO du noyau) de signaler à un descripteur de fichier qu'une opération est

terminée.

Un point clé concernant un descripteur de fichier eventfd est qu'il peut être surveillé comme n'importe quel autre descripteur de fichier en utilisant select(2), poll(2), ou epoll(7). Cela signifie qu'une application peut simultanément surveiller la disponibilité des fichiers « traditionnels » et la disponibilité des autres mécanismes du noyau qui prennent en charge l'interface eventfd. (Sans l'interface eventfd(), ces mécanismes ne pourraient pas être multiplexés via select(2), poll(2), ou epoll(7).

)

La valeur actuelle d'un compteur eventfd peut être consultée via l'entrée correspondant au descripteur de fichier dans le /proc/pid/fdinfo du processus. Voir proc(5) pour plu

s de
détails.

EXEMPLE

S

Le programme suivant crée un descripteur de fichier eventfd puis se duplique (fork) pour créer un processus enfant. Pendant que le parent dort brièvement, l'enfant écrit chacun des entiers fournis dans les arguments de la ligne de commande du programme dans le descripteur de fichier eventfd. Lorsque le parent a fini de dormir, il lit depuis le descripteur de fichier

eventfd.

La session shell suivante montre un exemple d'exécution du programme

: 


$ ./a.out 1 2 4 7 14
Child writing 1 to efd
Child writing 2 to efd
Child writing 4 to efd
Child writing 7 to efd
Child writing 14 to efd
Child completed write loop
Parent about to read
Parent read 28 (0x1c) from
efd

Source du

programme 
#include <err.h>
#include <inttypes.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/eventfd.h>
#include <sys/types.h>
#include <unistd.h>
int
main(int argc, char *argv[])
{
    int       efd;
    uint64_t  u;
    ssize_t   s;
    if (argc < 2) {
        fprintf(stderr, "Usage: %s <num>...\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    efd = eventfd(0, 0);
    if (efd == -1)
        err(EXIT_FAILURE, "eventfd");
    switch (fork()) {
    case 0:
        for (size_t j = 1; j < argc; j++) {
            printf("Child writing %s to efd\n", argv[j]);
            u = strtoull(argv[j], NULL, 0);
                    /* strtoull() allows various bases */
            s = write(efd, &u, sizeof(uint64_t));
            if (s != sizeof(uint64_t))
                err(EXIT_FAILURE, "write");
        }
        printf("Child completed write loop\n");
        exit(EXIT_SUCCESS);
    default:
        sleep(2);
        printf("Parent about to read\n");
        s = read(efd, &u, sizeof(uint64_t));
        if (s != sizeof(uint64_t))
            err(EXIT_FAILURE, "read");
        printf("Parent read %"PRIu64" (%#"PRIx64") from efd\n", u, u);
        exit(EXIT_SUCCESS);
    case -1:
        err(EXIT_FAILURE, "fork");
}
}
