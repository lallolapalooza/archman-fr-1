  puts ("stdin prêt");

  // avec sa fonction d'arrêt correspondante.
  ev_io_stop (EV_A_ w);
  // cela provoque l'arrêt de l'itération de tous les ev_run imbriqués
  ev_break (EV_A_ EVBREAK_ALL);

// un autre rappel, cette fois-ci pour un délai d'attente

timeout_cb (EV_P_ ev_timer *w, int revents)
{
  puts ("délai d'attente");
  // cela provoque l'arrêt de l'itération du ev_run le plus interne
  ev_break (EV_A_ EVBREAK_ONE);

int
main (void)
{
  // utilisez la boucle d'événements par défaut sauf si vous avez des besoins particuliers
  struct ev_loop *loop = EV_DEFAULT;
  // initialisez un watcher io, puis démarrez-le
  // celui-ci surveillera stdin pour devenir lisible
  ev_io_init (&stdin_watcher, stdin_cb, /*STDIN_FILENO*/ 0, EV_READ);

  ev_run (loop, 0);
  // break a été appelé, quittez donc
  return

À PROPOS DE

LIBEV

Libev est une boucle d'événements : vous enregistrez votre intérêt pour certains événements (comme un descripteur de fichier lisible ou l'expiration d'un délai d'attente), et elle gérera ces sources d'événements et fournira des événements à votre

programme.

Pour ce faire, elle doit prendre un contrôle plus ou moins complet sur votre processus (ou thread) en exécutant le gestionnaire de boucle d'événements, et communiquera ensuite les événements via un mécanisme de

rappel.

Vous enregistrez votre intérêt pour certains événements en enregistrant les fameux watchers d'événements, qui sont des structures C relativement petites que vous initialisez avec les détails de l'événement, puis vous les transmettez à libev en démarrant le

watcher.

FONCTIONNALIT

ÉS

Libev prend en charge « select », « poll », les interfaces aio spécifiques à Linux et « epoll », les mécanismes « kqueue » spécifiques aux BSD et les ports d'événements spécifiques à Solaris pour les événements de descripteur de fichier (« ev_io »), l'interface « inotify » de Linux (pour « ev_stat »), eventfd/signalfd de Linux (pour un réveil inter-thread plus rapide et plus propre (« ev_async »)/la gestion des signaux (« ev_signal »)), les minuteries relatives (« ev_timer »), les minuteries absolues avec reprogrammation personnalisée (« ev_periodic »), les signaux synchrones (« ev_signal »), les événements de changement d'état des processus (« ev_child »), et les watchers d'événements traitant du mécanisme de boucle d'événements lui-même (« ev_idle », « ev_embed », « ev_prepare » et « ev_check » watchers) ainsi que les watchers de fichiers (« ev_stat ») et même une prise en charge limitée des événements fork (« ev_fork »)

.

Elle est aussi assez rapide (voir ce benchmark http://libev.schmorp.de/bench.html l

REPRÉSENTATION DU

Libev représente le temps comme un nombre à virgule flottante unique, représentant le nombre de secondes (fractionnaire) depuis l'époque (POSIX) (en pratique quelque part près du début de 1970, les détails sont compliqués, ne posez pas la question). Ce type est appelé « ev_tstamp », et c'est ce que vous devriez utiliser aussi. Il est généralement un alias pour le « double » type en C. Lorsque vous devez effectuer des calculs dessus, vous devriez le traiter comme une valeur en virgule

flottante.

Contrairement à ce que le composant de nom « stamp » pourrait indiquer, il est aussi utilisé

pour les différences de

GESTION DES

ERREURS

Libev connaît trois classes d'erreurs : les erreurs du système d'exploitation, les erreurs d'utilisation et les erreurs internes (bugs)

.

Lorsque libev attrape une erreur du système d'exploitation qu'il ne peut pas gérer (par exemple un appel système indiquant une condition que libev ne peut pas corriger), il appelle le rappel défini via « ev_set_syserr_cb », qui est censé corriger le problème ou interrompre l'exécution. Par défaut, il imprime un message de diagnostic et appelle « abort () »

.

Lorsque libev détecte une erreur d'utilisation telle qu'un intervalle de minuterie négatif, il imprimera un message de diagnostic et interrompra l'exécution (via le mécanisme « assert », donc « NDEBUG » désactivera cette vérification) : ce sont des erreurs de programmation chez l'appelant de libev et doivent être corrigées

là-bas.

Via la macro « EV_FREQUENT », vous pouvez compiler et/ou activer un code de vérification de cohérence approfondi à l'intérieur de libev qui peut être utilisé pour vérifier les incohérences internes, généralement causées par des bugs

d'application.

Libev a aussi quelques vérifications d'erreurs internes « assert ». Celles-ci ne se déclenchent pas dans des circonstances normale

s, car elles indiquent soit un bug da
ns libev, soit quelque chose de pire.

Le mécanisme epoll mérite une mention honorable en tant que le plus mal conçu des mécanismes d'événements plus avancés : de simples irritants incluent la suppression silencieuse de descripteurs de fichiers, l'exigence d'un appel système par changement par descripteur de fichier (et la devinette inutile de paramètres), des problèmes avec dup, le retour avant la valeur de délai d'attente, entraînant des itérations supplémentaires (et ne donnant qu'une précision de 5ms alors que select sur la même plateforme donne 0.1ms) et ainsi de suite. Le plus gros problème est cependant les conditions de course lors du fork, - si un programme fait un fork alors le processus parent et l'enfant doivent tous deux recréer l'ensemble epoll, ce qui peut prendre un temps considérable (un appel système par descripteur de fichier) et est bien sûr difficile à

détecter.

Epoll est aussi notoirement bogué - l'intégration de descripteurs de fichiers epoll devrait fonctionner, mais bien sûr ne fonctionne pas, et epoll adore rapporter des événements pour des descripteurs de fichiers totalement différents (même déjà fermés, on ne peut donc même pas les retirer de l'ensemble) de ceux enregistrés dans l'ensemble (surtout sur les systèmes SMP). Libev essaie de contrer ces notifications erronées en utilisant un compteur de génération supplémentaire et en le comparant aux événements pour filtrer ceux qui sont erronés, en recréant l'ensemble si nécessaire. Epoll arrondit aussi par erreur les délais d'attente, mais ne vous donne aucun moyen de savoir quand et de combien, donc parfois vous devez attendre activement car epoll retourne immédiatement malgré un délai d'attente non nul. Et en dernier lieu, il refuse aussi de fonctionner avec certains descripteurs de fichiers qui fonctionnent parfaitement bien avec "select" (fichiers, de nombreux périphériques de caractères.

..).

Epoll est véritablement le désastre parmi les mécanismes de surveillance d'événements, un frankenpoll, assemblé à la hâte, sans pensée pour la conception ou l'interaction avec les autres. Oh, la douleur, s'arrêtera-t-elle

jamais...

Bien que l'arrêt, la configuration et le démarrage d'un observateur d'E/S dans la même itération entraînent une certaine mise en cache, il y a toujours un appel système par incident (car le même descripteur de fichier pourrait pointer vers une description de fichier différente maintenant), il est donc préférable d'éviter cela. De plus, les descripteurs de fichiers dupliqués avec "dup ()" pourraient ne pas très bien fonctionner si vous enregistrez des événements pour les deux descripteurs de

fichiers.

Les meilleures performances de ce backend sont obtenues en ne désenregistrant pas tous les observateurs d'un descripteur de fichier jusqu'à ce qu'il ait été fermé, si possible, c'est-à-dire en gardant au moins un observateur actif par descripteur de fichier à tout moment. L'arrêt et le démarrage d'un observateur (sans le reconfigurer) n'entraîne généralement pas non plus de surcoût supplémentaire. Un fork peut à la fois entraîner des notifications erronées ainsi que libev devant détruire et recréer l'objet epoll, ce qui peut prendre un temps considérable et devrait donc être

évité.

Tout cela signifie qu'en pratique, "EVBACKEND_SELECT" peut être aussi rapide ou plus rapide qu'epoll pour peut-être jusqu'à cent descripteurs de fichiers, selon l'utilisation. Tellement

triste.

Enfin, c'est ça, le gestionnaire d'événements. Cette fonction est généralement appelée après que vous avez initialisé tous vos observateurs et que vous souhaitez commencer à traiter les événements. Elle demandera au système d'exploitation s'il y a de nouveaux événements, appellera les rappels des observateurs, puis répétera l'ensemble du processus indéfiniment : C'est pourquoi les boucles d'événements sont appelées boucles.

Si l'argument flags est spécifié comme 0, elle continuera à traiter les événements jusqu'à ce qu'il n'y ait plus d'observateurs d'événements actifs ou que "ev_break" ait été

appelé.

La valeur de retour est fausse s'il n'y a plus d'observateurs actifs (ce qui signifie généralement "tous les travaux sont terminés" ou "impasse"), et vraie dans tous les autres cas (ce qui signifie généralement "vous devriez appeler "ev_run" à nouveau")

Veuillez noter qu'un "ev_break" explicite est généralement meilleur que de s'appuyer sur l'arrêt de tous les observateurs pour décider quand un programme a terminé (surtout dans les programmes interactifs), mais avoir un programme qui boucle automatiquement aussi longtemps qu'il le doit et pas plus en se fondant sur l'arrêt correct de ses observateurs, c'est vraiment une chose

belle.

Cette fonction est principalement sûre vis-à-vis des exceptions - vous pouvez sortir d'un appel "ev_run" en appelant "longjmp" dans un rappel, en lançant une exception C++, etc. Cela ne décrémente pas la valeur "ev_depth", et ne nettoiera pas non plus les ruptures "EVBREAK_ONE" en

attente.

réactif.

MODÈLES DE PRIORITÉ DES

WATCHERS

De nombreuses boucles d'événements prennent en charge les priorités des watchers, qui sont généralement de petits entiers qui influencent l'ordre d'invocation des rappels d'événements entre les watchers d'une certaine manière, toutes choses égales par

ailleurs.

Dans libev, les priorités des watchers peuvent être définies avec "ev_set_priority". Voir sa description pour les détails techniques plus poussés tels que la plage de priorité

réelle.

Il y a deux manières courantes dont ces priorités sont interprétées par les boucles d'événements

:

Dans le modèle d'exclusion plus courant, les priorités plus élevées « excluent » l'invocation des watchers de priorité plus faible, ce qui signifie que tant que les watchers de priorité plus élevée reçoivent des événements, les watchers de priorité plus faible ne sont pas

invoqués.

Le modèle moins courant uniquement-pour-l'ordre utilise les priorités uniquement pour ordonner l'invocation des rappels au sein d'une seule itération de boucle d'événements : Les watchers de priorité plus élevée sont invoqués avant ceux de priorité plus faible, mais ils sont tous invoqués avant de sonder de nouveaux

événements.

Libev utilise le deuxième modèle (uniquement-pour-l'ordre) pour tous ses watchers sauf les watchers idle (qui utilisent le modèle d'exclusion)

.

La raison derrière cela est que la mise en œuvre du modèle d'exclusion pour les watchers n'est pas bien prise en charge par la plupart des interfaces du noyau, et la plupart des bibliothèques d'événements sonderont simplement les mêmes événements encore et encore tant que leurs rappels n'ont pas été exécutés, ce qui est très inefficace dans le cas courant d'un watcher de haute priorité excluant une masse de watchers de priorité plus

faible.

Les priorités statiques (d'ordre) sont les plus utiles lorsque vous avez deux ou plus de watchers gérant la même ressource : un exemple d'utilisation typique est d'avoir un watcher "ev_io" pour recevoir des données, et un minuteur "ev_timer" associé pour gérer les délais d'attente. Sous charge, des données peuvent être reçues pendant que le programme traite d'autres tâches, mais comme les minuteurs sont normalement invoqués en premier, le gestionnaire de temporisation sera exécuté avant la vérification des données. Dans ce cas, donner au minuteur une priorité inférieure à celle du surveillant d'E/S garantit que les E/S seront traitées en premier, même dans des conditions défavorables (ce qui est généralement, mais pas

toujours,

ce que vous souhaitez). Puisque les surveillants inactifs utilisent le modèle d'exclusion mutuelle (« lock-out »), ce qui signifie que les surveillants inactifs ne seront exécutés que lorsque des surveillants de priorité égale ou supérieure n'ont reçu aucun événement, ils

peuvent

être utilisés pour implémenter le modèle d'exclusion mutuelle lorsque c'est requis. Par exemple, pour imiter la manière dont de nombreuses autres bibliothèques d'événements gèrent les priorités, vous pouvez associer un surveillant « ev_idle » à chaque surveillant de ce type, et dans le rappel (callback) du surveillant normal, vous démarrez simplement le surveillant inactif. noyau

pour le surveillant, mais lorsque le cas d'exclusion mutuelle est connu pour être rare (ce qui est en soi rare :), cela est faisable. Le problème spécial d'être trop

tôt

Si vous demandez à un minuteur d'appeler votre rappel après trois secondes, vous vous attendez à ce qu'il soit invoqué après trois secondes - mais bien sûr, cela ne peut pas être garanti à une précision infinie. Moins évidemment, cela ne peut pas être garanti à une précision quelconque par libev - imaginez par exemple quelqu'un suspendant le processus avec un signal STOP pendant quelques

heures.

Ainsi, libev essaie d'invoquer votre rappel dès que possible après que le délai soit écoulé, mais ne peut pas le

garantir.

Un mode de défaillance moins évident est d'appeler votre rappel trop tôt : de nombreuses boucles d'événements comparent les horodatages avec un « délai écoulé >= délai demandé », mais cela peut causer votre rappel à être invoqué bien plus tôt que vous ne vous y

attendriez.

Pour comprendre pourquoi, imaginez un système avec une horloge qui n'offre qu'une résolution de seconde entière (pensez windows si vous ne pouvez pas trouver un OS suffisamment cassé vous-même). Si vous planifiez un minuteur d'une seconde à l'heure 500.9, alors la boucle d'événements planifiera votre expiration à s'écouler à une heure système de 500 (500.9 tronqué à la résolution) + 1, ou

501.

Si une bibliothèque d'événements regarde l'expiration 0.1s plus tard, elle verra « 501 >= 501 » et invoquera le rappel 0.1s après son démarrage, même si un délai d'une seconde a été demandé - c'est être « trop tôt », malgré les meilleures

intentions.

C'est la raison pour laquelle libev n'invoquera jamais le rappel si le délai écoulé est égal au délai demandé, mais seulement lorsque le délai écoulé est supérieur au délai demandé. Dans l'exemple ci-dessus, libev n'invoquerait le rappel qu'à l'heure système 502, ou 1.1s après le démarrage du

minuteur.

Ainsi, bien que libev ne puisse pas garantir que votre rappel sera invoqué exactement quand demandé, il peut et garantit effectivement que le délai demandé a réellement écoulé, ou en d'autres termes, il fait toujours erreur du côté « trop tard »

.

Le problème spécial des mises à jour de

l'heure

Établir l'heure actuelle est une opération coûteuse (elle prend généralement au moins un appel système) : EV met donc à jour sa notion de l'heure actuelle seulement avant et après "ev_run" collecte de nouveaux événements, ce qui provoque une différence croissante entre "ev_now ()" et "ev_time ()" lors du traitement de nombreux événements en une

Les expirations relatives sont calculées par rapport à l'heure "ev_now ()". C'est généralement la bonne chose car cet horodatage fait référence à l'heure de l'événement déclenchant l'expiration que vous modifiez/démarrez. Si vous soupçonnez que le traitement des événements est retardé et que vous devez baser l'expiration sur l'heure actuelle, utilisez quelque chose comme ce qui suit pour l'ajuster

Le problème spécial des horloges non

synchronisées

Les systèmes modernes ont une variété d'horloges - libev lui-même utilise l'horloge « horloge murale » normale et, si disponible, l'horloge monotone (pour éviter les sauts temporels)

.

Aucune de ces horloges n'est synchronisée l'une avec l'autre ou avec une autre horloge du système, donc "ev_time ()" pourrait retourner une heure considérablement différente de "gettimeofday ()" ou "time ()". Sur un système GNU/Linux, par exemple, un appel à "gettimeofday" pourrait retourner un comptage de secondes d'une unité supérieur à un appel direct suivant à "time"

.

La morale de ceci est de ne comparer que les horodatages liés à libev avec "ev_time ()" et "ev_now ()", au moins si vous voulez une meilleure précision qu'une seconde

environ.

Un autre problème découle de ce manque de synchronisation : si libev utilise l'horloge monotone du système et que vous comparez des horodatages de "ev_time" ou "ev_now" du moment où vous avez démarré votre minuteur et du moment où votre rappel est invoqué, vous trouverez que parfois le rappel est un peu « en avance »

.

C'est parce que "ev_timer"s fonctionnent en temps réel, pas en temps d'horloge murale, donc libev s'assure que votre rappel n'est pas invoqué avant que le délai soit écoulé, mesuré selon le temps réel, pas selon l'horloge

système.

Si vos expirations sont basées sur une échelle de temps physique (par exemple « expirer cette connexion après 100 secondes ») alors cela ne devrait pas vous déranger car c'est exactement le bon

comportement.

Si vous voulez comparer des horodatages horloge murale/système à vos minuteurs, alors vous devez utiliser "ev_periodic"s, car ceux-ci sont basés sur le temps d'horloge murale, où vos comparaisons généreront toujours des résultats

corrects.

Les problèmes spéciaux de la

suspension

Lorsque vous quittez le monde des serveurs, il est assez courant de tomber sur des machines qui peuvent suspendre/hiberner - que se passe-t-il pour les horloges pendant une telle suspension

?

Quelques tests rapides effectués avec un Linux 2.6.28 indiquent qu'une suspension fige tous les processus, tandis que les horloges ("times", "CLOCK_MONOTONIC") continuent de tourner jusqu'à ce que le système soit suspendu, mais elles n'avanceront pas pendant que le système est suspendu. Cela signifie, à la reprise, ce sera comme si le programme avait été figé pendant quelques secondes, mais le temps de suspension ne sera pas compté dans "ev_timer" lorsqu'une source d'horloge monotone est utilisée. L'horloge temps réel a avancé comme prévu, mais si elle est utilisée comme seule source d'horloge, alors une longue suspension serait détectée comme un saut temporel par libev, et les minuteurs seraient ajustés en

conséquence.

Je ne serais pas surpris de voir un comportement différent entre systèmes d'exploitation, versions d'OS ou même du matériel

différent.

L'autre forme de suspension (contrôle de travail, ou l'envoi d'un SIGSTOP) verra un saut temporel dans les horloges monotones et l'horloge temps réel. Si le programme est suspendu pendant très longtemps, et que des sources d'horloge monotone sont utilisées, alors vous pouvez vous attendre à ce que "ev_timer"s expirent car le temps total de suspension sera compté pour les minuteurs. Lorsqu'aucune source d'horloge monotone n'est utilisée, libev supposera à nouveau un saut temporel et ajustera en

conséquence.

Il pourrait être bénéfique dans ce dernier cas d'appeler "ev_suspend" et "ev_resume" dans le code qui gère ";SIGTSTP", afin d'obtenir au moins un comportement déterministe dans ce cas (vous ne pouvez rien faire contre "SIGSTO

Les watchers périodiques sont aussi des minuteurs d'une certaine manière, mais ils sont très polyvalents (et malheureusement un peu complexes)

"ev_signal" - signalez-moi quand un signal est reçu

!

Les minuteries de signal se déclenchent lorsque le processus reçoit un signal spécifique une ou plusieurs fois. Bien que les signaux soient très asynchrones, libev essaiera de livrer les signaux de manière synchrone, c'est-à-dire comme partie du traitement normal des événements, comme tout autre

événement.

Si vous voulez que les signaux soient livrés de manière véritablement asynchrone, utilisez simplement "sigaction" comme vous le feriez sans libev et oubliez le partage du signal. Vous pouvez même utiliser "ev_async" depuis un gestionnaire de signal pour réveiller de manière synchrone une boucle

d'événements.

Vous pouvez configurer autant de minuteries que vous le souhaitez pour le même signal, mais seulement au sein de la même boucle, c'est-à-dire que vous pouvez surveiller "SIGINT" dans votre boucle par défaut et "SIGIO" dans une autre boucle, mais vous ne pouvez pas surveiller "SIGINT" à la fois dans la boucle par défaut et dans une autre boucle en même temps. Pour le moment, "SIGCHLD" est définitivement lié à la boucle par

défaut.

Ce n'est qu'après le démarrage de la première minuterie pour un signal que libev enregistre réellement quelque chose avec le noyau. Elle coexiste donc avec vos propres gestionnaires de signaux tant que vous n'en enregistrez aucun avec libev pour le même

signal.

Si possible et pris en charge, libev installera ses gestionnaires avec le comportement "SA_RESTART" (ou équivalent) activé, de sorte que les appels système ne devraient pas être indûment interrompus. Si vous avez un problème avec des appels système interrompus par des signaux, vous pouvez bloquer tous les signaux dans une minuterie "ev_check" et les débloquer dans une minuterie "ev_prepare"

.

Le problème spécial de l'héritage sur fork/execve/pthread_creat

e

Le masque de signaux ("sigprocmask") et la disposition du signal ("sigaction") sont indéfinis après le démarrage d'une minuterie de signal (et après son arrêt), c'est-à-dire que libev peut ou non bloquer le signal, et peut ou non définir ou restaurer le gestionnaire de signal installé (mais voir "EVFLAG_NOSIG

MASK").

Bien que cela n'ait pas d'importance pour la disposition du signal (libev ne définit jamais les signaux à "SIG_IGN", les gestionnaires seront donc réinitialisés à "SIG_DFL" lors de "execve"), cela a de l'importance pour le masque de signaux : de nombreux programmes ne s'attendent pas à ce que certains signaux soient

bloqués.

Cela signifie qu'avant d'appeler "exec" (depuis l'enfant) vous devriez réinitialiser le masque de signaux à ce que vous attendez comme « par défaut » (tout dégagé est généralement un bon choix)

.

La façon la plus simple de s'assurer que le masque de signaux est réinitialisé dans l'enfant est d'installer un gestionnaire de fork avec "pthread_atfork" qui le réinitialise. Cela capturera aussi les appels de fork effectués par des bibliothèques (comme la libc)

.

Dans les versions actuelles de libev, le signal ne sera pas bloqué indéfiniment sauf si vous utilisez l'API "signalfd" ("EV_SIGNALFD"). Bien que cela réduise la fenêtre d'opportunité pour les problèmes, cela ne disparaîtra pas, car libev doit modifier le masque de signaux, au moins

temporairement.

Je ne peux donc pas assez insister là-dessus : Si vous ne réinitialisez pas votre masque de signaux alors que vous vous attendez à ce qu'il soit vide, vous avez une condition de course dans votre code. Ce n'est pas une chose spécifique à libev, c'est vrai pour la plupart des bibliothèques

d'événements.

Le problème spécial de la gestion des signaux par les

threads

Les threads POSIX ont une sémantique de gestion des signaux problématique, spécifiquement, beaucoup de fonctionnalités (sigfd, sigwait etc.) ne fonctionnent réellement que si tous les threads d'un processus bloquent les signaux, ce qui est difficile à

réaliser.

Lorsque vous voulez utiliser sigwait (ou mélanger la gestion des signaux de libev avec la vôtre pour les mêmes signaux), vous pouvez aborder ce problème en bloquant globalement tous les signaux avant de créer des threads (ou en les créant avec un sigprocmask entièrement défini) et en spécifiant aussi "EVFLAG_NOSIGMASK" lors de la création des boucles. Désignez ensuite un thread comme « thread récepteur de signaux » qui gère ces signaux. Vous pouvez transmettre les signaux dont libev pourrait être intéressé en appelant "ev_feed_signal"

"ev_fork" - l'audace de reprendre la boucle d'événements après un

fork

Les observateurs de fork sont appelés lorsqu'un "fork ()" a été détecté (généralement parce que celui qui est un bon citoyen a pris soin d'en informer libev en appelant "ev_loop_fork"). L'invocation se fait avant que la boucle d'événements ne se bloque à nouveau et avant que les observateurs "ev_check" ne soient appelés, et uniquement dans l'enfant après le fork. Si le bon citoyen qui appelle "ev_default_fork" triche et l'appelle dans le mauvais processus, les gestionnaires de fork seront bien sûr invoqués

aussi.

Le problème spécial de la vie après le fork - comment est-ce possible

?

La plupart des utilisations de "fork ()" consistent à forker, puis à effectuer quelques appels simples pour configurer/modifier l'environnement du processus, suivis d'un appel à exec(). Cette séquence devrait être gérée par libev sans aucun

problème.

Cela change lorsque l'application souhaite réellement gérer des événements dans l'enfant, ou dans les deux processus, parent et enfant, effectivement « continuer » après le

fork.

Le mode de fonctionnement par défaut (pour libev, avec l'aide de l'application pour détecter les forks) est de dupliquer tout l'état dans l'enfant, comme on s'y attendrait lorsque soit le parent soit le processus enfant

continue.

Lorsque les deux processus souhaitent continuer à utiliser libev, c'est généralement le mauvais résultat. Dans ce cas, généralement un processus (typiquement le parent) est censé continuer avec tous les observateurs en place comme avant, tandis que l'autre processus souhaite généralement repartir de zéro, c'est-à-dire sans aucun observateur

actif.

La manière la plus propre et la plus efficace d'y parvenir avec libev est de simplement créer une nouvelle boucle d'événements, qui sera bien sûr « vide », et de l'utiliser pour les nouveaux observateurs. Cela a l'avantage de ne pas toucher plus de mémoire que nécessaire, évitant ainsi le copy-on-write, et l'inconvénient de devoir utiliser plusieurs boucles d'événements (qui ne prennent pas en charge les observateurs de signal)

.

Lorsque cela n'est pas possible, ou que vous souhaitez utiliser la boucle par défaut pour d'autres raisons, alors dans le processus qui souhaite repartir « de zéro », appelez "ev_loop_destroy (EV_DEFAULT)" suivi de "ev_default_loop (...)". Détruire la boucle par défaut va « orpheliner » (pas arrêter) tous les observateurs enregistrés, vous devez donc faire attention à ne pas exécuter de code qui modifie ces observateurs. Notez aussi que dans ce cas, vous devez réenregistrer tous les observateurs de

signal.

"ev_async" - comment réveiller une boucle

En général, vous ne pouvez pas utiliser une "ev_loop" depuis plusieurs threads ou d'autres sources asynchrones telles que les gestionnaires de signaux (par opposition à plusieurs boucles d'événements - celles-ci sont bien sûr sûres à utiliser dans différents threads)

Parfois, cependant, vous devez réveiller une boucle d'événements que vous ne contrôlez pas, par exemple parce qu'elle appartient à un autre thread. C'est ce que font les observateurs "ev_async" : tant que l'observateur "ev_async" est actif, vous pouvez le signaler en appelant "ev_async_send", ce qui est sûr pour les threads et les

signaux.

Cette fonctionnalité est très similaire aux observateurs "ev_signal", car les signaux sont aussi de nature asynchrone, et les signaux seront aussi compressés (c'est-à-dire que le nombre d'invocations de rappel peut être inférieur au nombre d'appels "ev_async_send"). En fait, vous pourriez utiliser les observateurs de signal comme une sorte d'« observateurs async globaux » en utilisant un observateur sur un signal autrement inutilisé, et "ev_feed_signal" pour signaler cet observateur depuis un autre thread, même sans savoir quelle boucle possède le

signal.

EXAMPLE

Here is a fictitious example of how to run an event loop in a different thread from where callbacks are being invoked and watchers are created/added/removed

The example uses a pthread mutex to protect the loop data, a condition variable to wait for callback invocations, an async watcher to notify the event loop thread and an unspecified mechanism to wake up the main

   static userdata u;

   // just used for the side effects

CALLBACKS

While the overhead of a callback that e.g. schedules a thread is small, it is still an overhead. If you embed libev, and your main usage is with some kind of threads or coroutines, you might want to customise libev so that doesn't need callbacks

anymore.

Imagine you have coroutines that you can switch to using a function "switch_to (coro)", that libev runs in a coroutine called "libev_coro" and that due to some magic, the currently active coroutine is stored in a global called "current_coro". Then you can build your own "wait for libev event" primitive by changing "EV_CB_DECLARE" and "EV_CB_INVOKE" (note the differing ";" conventions)

: 
#define EV_CB_DECLARE(type)   struct my_coro *cb;
#define EV_CB_INVOKE(watcher) switch_to ((watcher)->
cb)

That means instead of having a C callback function, you store the coroutine to switch to in each watcher, and instead of having libev call your callback, you instead have it switch to that

coroutine.

A coroutine might now wait for an event with a function called "wait_for_event". (the watcher needs to be started, as always, but it doesn't matter when, or whether the watcher is active or not when this function is called)

: 
void
wait_for_event (ev_watcher *w)
{
  ev_set_cb (w, current_coro);
  switch_to (libev_coro);
}

That basically suspends the coroutine inside "wait_for_event" and continues the libev coroutine, which, when appropriate, switches back to this or any other

coroutine.

waiters.

multithread
Libev utilise "sigprocmask" pour bloquer temporairement les signaux. Cela n'est pas autorisé dans un programme multithread ("pthread_sigmask" doit être utilisé). Les implémentations pthread typiques autoriseront soit "sigprocmask" dans le "thread principal" soit bloqueront les signaux au niveau du processus, les deux comportements seraient compatibles avec libev. L'interaction entre "sigprocmask" et "pthread_sigmask" pourrait compliquer les choses, cependant.

La manière la plus portable de gérer les signaux est de bloquer les si

gnaux dans tous les threads sauf le premier, et d'exécuter la b
oucle de gestion des signaux dans le premier thread également.
"long" doit être assez grand pour les tailles d'allocation de mémoire
courantes
Pour améliorer la portabilité et simplifier son API, libev utilise "long" en interne au lieu de "size_t" lors de l'allocation de ses structures de données. Sur les systèmes non-POSIX (Microsoft...), cela pourrait être inattendu bas, mais reste au moins 31 bits partout, ce qui est suffisant pour des centaines de millions de
watchers.
"double" doit contenir une valeur de temps en secondes avec une précision
suffisante
Le type "double" est utilisé pour représenter les horodatages. Il doit avoir au moins 51 bits de mantisse (et 9 bits d'exposant), ce qui est suffisant au moins jusqu'à l'an 4000 avec une précision à la milliseconde (l'objectif de conception de libev). Cette exigence est surremplie par les implémentations utilisant IEEE 754, qui sont essentiellement toutes les existantes.

Avec les doubles IEEE 754, vous obtenez une précision à la microseconde jusqu'à au moins l'an 2255 (et une précision à la milliseconde jusqu'à l'an 287396 - d'ici là, libev est soit obsolète, soit quelqu'un l'a patché pour utiliser "long double" ou quelque

chose comme ç
a, j
e plaisante).
