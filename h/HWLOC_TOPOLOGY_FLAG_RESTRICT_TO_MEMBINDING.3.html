Description détaillée

Plusieurs fonctions peuvent être appelées facultativement entre hwloc_topology_init() et hwloc_topology_load() pour configurer la manière dont la détection doit être effectuée, par exemple pour ignorer certains types d'objets, définir une topologie synthétique, etc.

Documentation du type énumération

enum hwloc_topology_flags_e

Drapeaux à définir sur un contexte de topologie avant le chargement. Les drapeaux doivent être donnés à hwloc_topology_set_flags(). Ils peuvent également être retournés par hwloc_topology_get_flags().

Énumérateur

HWLOC_TOPOLOGY_FLAG_INCLUDE_DISALLOWED
Détecter tout le système, ignorer les réservations, inclure les objets non autorisés. Rassembler toutes les ressources en ligne, même si certaines ont été désactivées par l'administrateur. Par exemple, ignorer les Cgroup/Cpusets Linux et rassembler tous les processeurs et nœuds mémoire. Cependant, les PU et nœuds NUMA hors ligne sont toujours ignorés.

Lorsque ce drapeau n'est pas défini, les PU et nœuds NUMA non autorisés ne sont pas ajoutés à la topologie. Les objets parents (paquet, cœur, cache, etc.) ne sont ajoutés que si certains de leurs enfants sont autorisés. Tous les PU et nœuds NUMA existants dans la topologie sont autorisés. hwloc_topology_get_allowed_cpuset() et hwloc_topology_get_allowed_nodeset() sont égaux au cpuset et au nodeset de l'objet racine.

Lorsque ce drapeau est défini, les ensembles réels de PU et de nœuds NUMA autorisés sont donnés par hwloc_topology_get_allowed_cpuset() et hwloc_topology_get_allowed_nodeset(). Ils peuvent être plus petits que le cpuset et le nodeset de l'objet racine.

Si la topologie actuelle est exportée en XML et réimportée ultérieurement, ce drapeau doit être défini à nouveau dans la topologie réimportée afin que les ressources non autorisées soient également réimportées.

HWLOC_TOPOLOGY_FLAG_IS_THISSYSTEM
Supposer que le backend sélectionné fournit la topologie du système sur lequel nous exécutons. Cela force hwloc_topology_is_thissystem() à retourner 1, c'est-à-dire que hwloc suppose que le backend sélectionné fournit la topologie du système sur lequel nous exécutons, même s'il ne s'agit pas du backend spécifique à l'OS mais du backend XML par exemple. Cela signifie que les fonctions d'attachement appellent réellement les appels système spécifiques à l'OS et effectuent réellement l'attachement, tandis que le backend XML fournirait autrement des hooks vides ne retournant que le succès.

Définir la variable d'environnement HWLOC_THISSYSTEM peut également entraîner le même comportement.

Cela peut être utilisé pour des raisons d'efficacité afin de détecter la topologie une seule fois, de la sauvegarder dans un fichier XML, puis de la recharger rapidement ultérieurement via le backend XML, tout en ayant les fonctions d'attachement qui effectuent réellement l'attachement.

HWLOC_TOPOLOGY_FLAG_THISSYSTEM_ALLOWED_RESOURCES
Obtenir l'ensemble des ressources autorisées à partir du système d'exploitation local même si la topologie a été chargée à partir d'une description XML ou synthétique. Si la topologie a été chargée à partir de XML ou d'une chaîne synthétique, la restreindre en appliquant les restrictions du processus actuel telles que les Cgroup/Cpusets Linux.

Cela est utile lorsque la topologie n'est pas chargée directement depuis la machine locale (par exemple pour des raisons de performance) et qu'elle contient toutes les ressources, alors que le processus en cours d'exécution est limité à une partie de la machine.

Ce drapeau est ignoré sauf si HWLOC_TOPOLOGY_FLAG_IS_THISSYSTEM est également défini, car la topologie chargée doit correspondre à la machine sous-jacente d'où les restrictions seront récupérées.

Définir la variable d'environnement HWLOC_THISSYSTEM_ALLOWED_RESOURCES entraînerait le même comportement.

HWLOC_TOPOLOGY_FLAG_IMPORT_SUPPORT
Importer le support depuis la topologie importée. Lors de l'importation d'une topologie XML depuis une machine distante, l'attachement est désactivé par défaut (voir HWLOC_TOPOLOGY_FLAG_IS_THISSYSTEM). Ce désactivation est également marquée en mettant des zéros dans les bits de fonctionnalité supportée correspondants rapportés par hwloc_topology_get_support().

Le drapeau HWLOC_TOPOLOGY_FLAG_IMPORT_SUPPORT importe réellement les bits de support depuis la machine distante. Il définit également le drapeau imported_support dans le tableau de la structure hwloc_topology_misc_support . Si le XML importé ne contenait aucune information de support (le hwloc exportateur est trop ancien), ce drapeau n'est pas défini.

Notez que ces fonctionnalités supportées ne sont pertinentes que pour l'installation hwloc qui a effectivement exporté la topologie XML (elles peuvent varier selon le système d'exploitation ou selon la manière dont hwloc a été compilé).

Notez que définir ce drapeau n'active cependant pas l'attachement pour la topologie hwloc importée localement, il rapporte seulement ce que le hwloc et la machine distante supportent.

HWLOC_TOPOLOGY_FLAG_RESTRICT_TO_CPUBINDING
Ne pas considérer les ressources en dehors de l'attachement CPU du processus. Si l'attachement du processus est limité à un sous-ensemble de cœurs, ignorer les autres cœurs lors de la découverte.

La topologie résultante est identique à celle qu'un appel à hwloc_topology_restrict() générerait, mais cet indicateur empêche également hwloc de toucher à d'autres ressources lors de la découverte.

Cet indiqueur indique en particulier au backend x86 de ne jamais réaffecter temporairement un thread sur un cœur exclu. C'est utile sur Windows car une telle réaffectation temporaire peut modifier l'affectation du processus. Un autre cas d'utilisation est d'éviter les cœurs qui ne seraient pas en mesure d'effectuer la découverte hwloc prochainement car ils sont occupés à exécuter des tâches temps réel de haute priorité.

Si l'affectation CPU du processus n'est pas prise en charge, l'affectation CPU du thread est considérée à la place si elle est prise en charge, ou l'indicateur est ignoré.

Cet indicateur nécessite HWLOC_TOPOLOGY_FLAG_IS_THISSYSTEM également car la prise en charge de l'affectation est requise.

HWLOC_TOPOLOGY_FLAG_RESTRICT_TO_MEMBINDING
Ne pas considérer les ressources en dehors de l'affectation mémoire du processus. Si l'affectation du processus est limitée à un sous-ensemble de nœuds NUMA, ignorer les autres nœuds NUMA lors de la découverte.

La topologie résultante est identique à celle qu'un appel à hwloc_topology_restrict() générerait, mais cet indicateur empêche également hwloc de toucher à d'autres ressources lors de la découverte.

Cet indicateur est destiné à être utilisé avec HWLOC_TOPOLOGY_FLAG_RESTRICT_TO_CPUBINDING lorsque les cœurs et les nœuds NUMA doivent être ignorés en dehors de l'affectation du processus.

Si l'affectation mémoire du processus n'est pas prise en charge, l'affectation mémoire du thread est considérée à la place si elle est prise en charge, ou l'indicateur est ignoré.

Cet indicateur nécessite HWLOC_TOPOLOGY_FLAG_IS_THISSYSTEM également car la prise en charge de l'affectation est requise.

HWLOC_TOPOLOGY_FLAG_DONT_CHANGE_BINDING
Ne jamais modifier l'affectation du processus ou du thread lors de la découverte. Cet indicateur désactive toutes les étapes de découverte hwloc qui nécessitent un changement de l'affectation du processus ou du thread. Cela n'affecte actuellement que le backend x86, qui est entièrement désactivé.

C'est utile lorsque hwloc_topology_load() est appelé pendant que l'application crée également des threads supplémentaires ou modifie l'affectation.

Cet indicateur est également un moyen strict de s'assurer que l'affectation du processus ne changera pas en raison de changements d'affectation des threads sur Windows (voir HWLOC_TOPOLOGY_FLAG_RESTRICT_TO_CPUBINDING).

HWLOC_TOPOLOGY_FLAG_NO_DISTANCES
Ignorer les distances. Ignorer les informations de distance provenant des systèmes d'exploitation (et de XML) et ainsi ne pas utiliser les distances pour le regroupement.
HWLOC_TOPOLOGY_FLAG_NO_MEMATTRS
Ignorer les attributs et les niveaux de mémoire. Ignorer les attributs de mémoire provenant des systèmes d'exploitation (et de XML). Ne pas non plus essayer de construire des niveaux de mémoire.
HWLOC_TOPOLOGY_FLAG_NO_CPUKINDS
Ignorer les types de CPU. Ignorer les informations sur les types de CPU provenant des systèmes d'exploitation (et de XML).

enum hwloc_type_filter_e

Indicateurs de filtrage des types. Par défaut, la plupart des objets sont conservés (HWLOC_TYPE_FILTER_KEEP_ALL). Les caches d'instructions, les caches côté mémoire, les objets E/S et Divers sont ignorés par défaut (HWLOC_TYPE_FILTER_KEEP_NONE). Les niveaux de groupe sont ignorés sauf s'ils apportent de la structure (HWLOC_TYPE_FILTER_KEEP_STRUCTURE).

Notez que les objets de groupe sont également ignorés individuellement (sans le niveau entier) lorsqu'ils n'apportent pas de structure.

Énumérateur

HWLOC_TYPE_FILTER_KEEP_ALL
Conserver tous les objets de ce type. Ne peut pas être défini pour HWLOC_OBJ_GROUP (les groupes ne sont conçus que pour ajouter plus de structure à la topologie).
HWLOC_TYPE_FILTER_KEEP_NONE
Ignorer tous les objets de ce type. Le type de niveau inférieur HWLOC_OBJ_PU, le type HWLOC_OBJ_NUMANODE , et le type de niveau supérieur ne peuvent pas être ignorés : HWLOC_OBJ_MACHINE .
HWLOC_TYPE_FILTER_KEEP_STRUCTURE
Ignorer les objets uniquement si leur niveau entier n'apporte aucune structure. Conserver le niveau entier d'objets si au moins un de ces objets ajoute de la structure à la topologie. Un objet apporte de la structure lorsqu'il a plusieurs enfants et qu'il n'est pas le seul enfant de son parent.

Si tous les objets du niveau sont le seul enfant de leur parent, et si aucun d'entre eux n'a plusieurs enfants, le niveau entier est supprimé.

Ne peut pas être défini pour les objets E/S et Divers car la structure de la topologie n'a pas d'importance pour ceux-ci.

HWLOC_TYPE_FILTER_KEEP_IMPORTANT
Ne conserver que les objets probablement importants du type donné. C'est seulement utile pour les types d'objets E/S. Pour HWLOC_OBJ_PCI_DEVICE et HWLOC_OBJ_OS_DEVICE, cela signifie que seuls les objets de types majeurs/communs sont conservés (stockage, réseau, OpenFabrics, CUDA, OpenCL, RSMI, NVML, et écrans). De plus, seuls les périphériques OS directement attachés en PCI (par ex. pas USB) sont rapportés. Pour HWLOC_OBJ_BRIDGE, cela signifie que les ponts sont conservés seulement s'ils ont des enfants.

Cet indicateur est équivalent à HWLOC_TYPE_FILTER_KEEP_ALL pour les types Normal, Mémoire et Divers car ils sont probablement importants.

Récupérer la prise en charge de la topologie. Chaque indicateur indique si une fonctionnalité est prise en charge. S'il est défini à 0, la fonctionnalité n'est pas prise en charge. S'il est défini à 1, la fonctionnalité est prise en charge, mais l'appel correspondant peut encore échouer dans certains cas particuliers.

Ces fonctionnalités sont également listées par hwloc-info --support

Les fonctionnalités rapportées sont celles que la topologie actuelle prend en charge sur la machine actuelle. Si la topologie a été exportée en XML depuis une autre machine et plus tard importée ici, la prise en charge décrit toujours ce qui est pris en charge pour cette topologie importée après l'importation. NAME

hwloc_topology_set_userdata — set the topology-specific userdata pointer

LIBRARY

Hardware Locality (libhwloc)

SYNOPSIS

                        #include <hwloc.h>
                    
                        void hwloc_topology_set_userdata (hwloc_topology_t topology, const void *userdata);

DESCRIPTION

Set the topology-specific userdata pointer. Each topology may store one application-given private data pointer. It is initialized to NULL. hwloc will never modify it.

Use it as you wish, after hwloc_topology_init() and until hwloc_topolog_destroy().

This pointer is not exported to XML.

RETURN VALUE

This function does not return a value.
