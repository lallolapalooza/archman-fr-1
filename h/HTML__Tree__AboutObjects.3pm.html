Point de vue de l'utilisateur sur les modules orientés

objet

-- Sean M.

Burke

La première fois que la plupart des programmeurs Perl rencontrent la programmation orientée objet, c'est lorsqu'ils doivent utiliser un module dont l'interface est orientée objet. C'est souvent une expérience déroutante, puisque parler de « méthodes » et de « constructeurs » est incompréhensible pour des programmeurs qui pensaient que fonctions et variables étaient tout ce dont il fallait se

soucier.

Les articles et les livres qui expliquent la programmation orientée objet (POO) le font en termes de comment programmer de cette façon. C'est compréhensible, et si vous apprenez à écrire votre propre code orienté objet, vous trouverez facile d'utiliser le code orienté objet que d'autres écrivent. Mais cette approche est la longue route pour les personnes dont l'objectif immédiat est simplement d'utiliser des modules orientés objet existants, mais qui ne veulent pas encore connaître tous les détails sordides de l'écriture de tels modules

eux-mêmes.

Cet article est destiné à ces programmeurs -- des programmeurs qui veulent en savoir sur les objets du point de vue de l'utilisation de modules orientés

objet.

Modules et leurs interfaces

fonctionnelles

Les modules sont la principale façon dont Perl permet de regrouper du code pour une utilisation ultérieure par vous-même ou par d'autres. Comme je suis sûr que vous ne pouvez pas vous empêcher de le remarquer en lisant The Perl Journal, CPAN (le Comprehensive Perl Archive Network) est le dépôt pour les modules (ou groupes de modules) que d'autres ont écrits, pour faire tout, depuis la composition de musique jusqu'à l'accès aux pages Web. Bon nombre de ces modules sont même fournis avec chaque installation de

Perl.

Un module que vous avez peut-être déjà utilisé, et dont l'interface est assez typique, est Text::Wrap. Il est fourni avec Perl, vous n'avez donc même pas besoin de l'installer depuis CPAN. Vous l'utilisez dans un de vos programmes, en faisant dire à votre code de programme, au début

: 
use Text::
Wrap;

et après cela, vous pouvez accéder à une fonction appelée "wrap", qui insère des sauts de ligne dans le texte que vous lui fournissez, de sorte que le texte sera aligné sur soixante-douze (ou combien que ce soit)

colonnes.

La façon dont ce "use Text::Wrap" fonctionne, c'est que le module Text::Wrap existe sous la forme d'un fichier "Text/Wrap.pm" quelque part dans l'une de vos bibliothèques. Ce fichier contient du code Perl..

.
Note de bas de page : Et mélangé au code Perl, il y a de la documentation, que vous lisez avec "perldoc Text::Wrap". Le programme perldoc ignore simplement le code et met en forme le texte de la documentation, alors que "use Text::Wrap" charge et exécute le code tout en ignorant la
documentation.

...qui, entre autres choses, définit une fonction appelée "Text::Wrap::wrap", puis "exporte" cette fonction, ce qui signifie que lorsque vous dites "wrap" après avoir dit "use Text::Wrap", vous appelez en fait la fonction "Text::Wrap::wrap". Certains modules n'exportent pas leurs fonctions, vous devez donc les appeler par leur nom complet, comme Text::Wrap::wrap(...paramètres...)

.

Que le module typique exporte ou non les fonctions qu'il fournit, un module est fondamentalement juste un conteneur pour des morceaux de code qui font des choses utiles. La façon dont le module vous permet d'interagir avec lui, c'est son interface. Et lorsque, comme avec Text::Wrap, son interface se compose de fonctions, on dit que le module a une interface fonctionnelle

.
Note de bas de page : le terme « fonction » (et donc « fonctionnel ») a plusieurs sens. J'utilise le terme ici dans son sens le plus large, pour faire référence aux routines -- des morceaux de code qui sont appelés par un certain nom et qui prennent des paramètres et renvoient une certaine
valeur.

Utiliser des modules avec des interfaces fonctionnelles est simple -- au lieu de définir votre propre fonction "wrap" avec "sub wrap { ... }", vous confiez à "use Text::Wrap" de le faire pour vous, ainsi que toutes les autres fonctions qu'il définit et exporte, selon la documentation du module. Sans trop de tracas, vous pouvez même écrire vos propres modules pour contenir vos fonctions fréquemment utilisées ; je suggère de jeter un œil à la page man "perlmod" pour plus d'indication

s sur la façon de
faire cela.

Modules avec interfaces orientées

objet

Supposons donc qu'un jour vous vouliez écrire un programme qui automatisera le processus de "ftp" d'un tas de fichiers d'un serveur vers votre machine locale, puis vers un autre

serveur.

Un rapide parcours de search.cpan.org révèle le module "Net::FTP", que vous pouvez télécharger et installer en utilisant les instructions d'installation normales (à moins que votre administrateur système ne l'ait déjà installé, comme beaucoup l'ont fait)

.

Comme Text::Wrap ou tout autre module avec une interface fonctionnelle familière, vous commencez à utiliser Net::FTP dans votre programme en disant

: 
use Net::
FTP;

Cependant, c'est là que la similarité se termine. Le premier indice de différence est que la documentation pour Net::FTP le désigne comme une classe. Une classe est un type de module, mais un qui a une interface orientée

objet.

Alors que des modules comme Text::Wrap fournissent des morceaux de code utiles sous forme de fonctions, à appeler comme fonction(...paramètres...) ou comme NomDuPaquet::fonction(...paramètres...), Net::FTP et d'autres modules avec des interfaces orientées objet fournissent des méthodes. Les méthodes sont un peu comme les fonctions en ce qu'elles ont un nom et des paramètres ; mais les méthodes ont une apparence différente, et sont différentes, parce que vous devez les appeler avec une syntaxe qui a un nom de classe ou un objet comme argument spécial. J'expliquerai la syntaxe des appels de méthode, puis j'expliquerai plus tard ce qu'ils signifient

tous.

Certaines méthodes sont destinées à être appelées comme méthodes de classe, avec le nom de classe (le même que le nom du module) comme argument spécial. Les méthodes de classe ressemblent à ceci

: 
NomDeClasse->nomdemethode(paramètre1, paramètre2, ...)
NomDeClasse->nomdemethode()   # si aucun paramètre
NomDeClasse->nomdemethode     # identique à
ci-dessus

que vous verrez parfois écrites

: 
nomdemethode NomDeClasse (paramètre1, paramètre2, ...)
nomdemethode NomDeClasse      # si aucun
paramètre

Fondamentalement, toutes les méthodes de classe servent à créer de nouveaux objets, et les méthodes qui créent des objets sont appelées «constructeurs » (et le processus de création est appelé « construction » ou « instanciation »). Les méthodes constructeurs ont généralement le nom "new", ou quelque chose incluant "new" ("new_from_file", etc.) ; mais elles peuvent concevablement porter n'importe quel nom -- la méthode constructeur de DBI est nommée "connect", par

exemple.

L'objet qu'une méthode constructeur renvoie est généralement capturé dans une variable scalaire

: 
$objet = NomDeClasse->new(param1, param2...)
;

Une fois que vous avez un objet (plus de détails plus tard sur ce que c'est exactement), vous pouvez utiliser l'autre type de syntaxe d'appel de méthode, la syntaxe pour les appels de méthode d'objet. Appeler des méthodes d'objet est juste comme les méthodes de classe, sauf qu'au lieu du NomDeClasse comme argument spécial, vous utilisez une expression qui produit un « objet ». Habituellement, c'est juste une variable scalaire dans laquelle vous avez précédemment capturé la sortie du constructeur. Les appels de méthode d'objet ressemblent à ceci

: 
$objet->nomdemethode(paramètre1, paramètre2, ...);
$objet->nomdemethode()   # si aucun paramètre
$objet->nomdemethode     # identique à
ci-dessus

qui est parfois écrit comme

: 
nomdemethode $objet (paramètre1, paramètre2, ...)
nomdemethode $objet      # si aucun
paramètre

Des exemples d'appels de méthode sont

: 
my $session1 = Net::FTP->new("ftp.myhost.com");
  # Appelle une méthode de classe "new", de la classe Net::FTP,
  #  avec le paramètre unique "ftp.myhost.com",
  #  et enregistre la valeur de retour (qui est, comme d'habitude,
  #  un objet), dans $session1.
  # Pourrait aussi être écrit :
  #  new Net::FTP('ftp.myhost.com')
$session1->login("sburke","aoeuaoeu")
  || die "échec de la connexion !\n";
   # appel de la méthode d'objet "login"
print "Répertoire :\n", $session1->dir(), "\n";
$session1->quit;
  # idem que $session1->quit()
print "Terminé\n";
exit;

Soit dit en passant, je suggère d'utiliser toujours les syntaxes avec des parenthèses et "->" dedans,

Note de bas de page : la paire de caractères "->" est censée ressembler à une flèche, pas à un "moins plus grand que" !

et d'éviter les syntaxes qui commencent par "nom_méthode $objet" ou "nom_méthode NomModule". Quand tout va bien, elles signifient toutes la même chose que les variantes avec "->", mais la syntaxe avec "->" est plus visuellement distincte des appels de fonction, et elle est également immunisée contre certains types d'ambiguïtés rares mais déroutantes qui peuvent survenir lorsque vous essayez d'appeler des méthodes portant le même nom que des sous-routines que vous avez définies.

Mais, indépendamment des alternatives syntaxiques, toute cette discussion sur la construction d'objets et de méthodes d'objets soulève la question : qu'est-ce qu'un objet ? Il y a plusieurs angles à cette question auxquels le reste de cet article répondra tour à tour : que pouvez-vous faire avec des objets ? qu'y a-t-il dans un objet ? qu'est-ce qu'une valeur d'objet ? et pourquoi certains modules utilisent-ils des objets du tout ?

Que Pouvez-vous Faire avec des Objets ?

Vous avez vu que vous pouvez créer des objets et appeler des méthodes d'objets avec eux. Mais à quoi servent les méthodes d'objets ? La réponse dépend de la classe :

Un objet Net::FTP représente une session entre votre ordinateur et un serveur FTP. Ainsi, les méthodes que vous appelez sur un objet Net::FTP servent à faire tout ce dont vous auriez besoin pour une connexion FTP. Vous établissez la session et vous vous connectez :

my $session = Net::FTP->new('ftp.aol.com');
die "Impossible de se connecter !" unless defined $session;
  # L'appel de méthode de classe à "new" renverra
  # le nouvel objet s'il réussit, sinon il
  # renverra undef.

$session->login('sburke', 'p@ssw3rD')
 || die "Ai-je encore changé mon mot de passe ?";
  # La méthode d'objet "login" renverra une valeur
  # vraie s'il se connecte effectivement, sinon
  # il renverra faux.

Vous pouvez utiliser l'objet de session pour changer de répertoire sur cette session :

$session->cwd("/home/sburke/public_html")
   || die "Hé, ça était VRAIMENT censé marcher !";
 # si le cwd échoue, il renverra faux

...récupérer des fichiers de la machine à l'autre bout de la session...

foreach my $f ('log_report_ua.txt', 'log_report_dom.txt',
               'log_report_browsers.txt')
{
  $session->get($f) || warn "La récupération de $f a échoué !"
};

...et bien plus encore, pour finir par fermer la connexion :

$session->quit();

En bref, les méthodes d'objets servent à faire des choses liées à (ou avec) ce que l'objet représente. Pour les sessions FTP, il s'agit d'envoyer des commandes au serveur à l'autre bout de la connexion, et c'est tout — là, les méthodes servent à faire quelque chose au monde extérieur à l'objet, et l'objet est juste quelque chose qui spécifie quelle partie du monde (enfin, quelle session FTP) agir.

Avec la plupart des autres classes, cependant, l'objet lui-même stocke une sorte d'information, et il n'est généralement pas logique de faire des choses avec un tel objet sans considérer les données qu'il contient.

Qu'y a-t-il dans un Objet ?

Un objet est (avec de rares exceptions) une structure de données contenant un ensemble d'attributs, chacun ayant une valeur, ainsi qu'un nom que vous utilisez lorsque vous lisez ou définissez la valeur de l'attribut. Certains des attributs de l'objet sont privés, ce qui signifie que vous ne les verrez jamais documentés car ils ne sont pas destinés à être lus ou écrits par vous ; mais la plupart des attributs documentés de l'objet sont au moins lisibles, et généralement modifiables, par vous. Les objets Net::FTP ont peu d'attributs, nous utiliserons donc des objets de la classe Business::US_Amort pour cet exemple. Business::US_Amort est une classe très simple (disponible sur CPAN) que j'ai écrite pour faire des calculs liés aux prêts (spécifiquement, l'amortissement, en utilisant des algorithmes de style américain).

Un objet de la classe Business::US_Amort représente un prêt avec des paramètres particuliers, c'est-à-dire des attributs. Les attributs les plus basiques d'un "objet prêt" sont son taux d'intérêt, son principal (combien d'argent il représente), et sa durée (combien de temps il faudra pour le rembourser). Vous devez définir ces attributs avant que quoi que ce soit d'autre puisse être fait avec l'objet. La manière d'accéder à ces attributs pour les objets prêt est la même que pour accéder aux attributs de n'importe quelle classe d'objets : via des accesseurs. Un accesseur est simplement toute méthode qui accède (en lecture ou en écriture, alias obtenir ou mettre) à un attribut de l'objet donné. De plus, les accesseurs sont la seule façon de modifier les attributs d'un objet. (Si la documentation d'un module veut que vous connaissiez une autre méthode, elle vous le dira.)

Généralement, pour des raisons de simplicité, un accesseur est nommé d'après l'attribut qu'il lit ou écrit. Avec les objets Business::US_Amort, les accesseurs que vous devez utiliser en premier sont "principal", "interest_rate", et "term". Ensuite, avec au moins ces attributs définis, vous pouvez appeler la méthode "run" pour calculer plusieurs choses concernant le prêt. Ensuite, vous pouvez appeler divers accesseurs, comme "total_paid_toward_interest", pour lire les résultats :

use Business::US_Amort;
my $loan = Business::US_Amort->new;
# Définir les attributs nécessaires :
$loan->principal(123654);
$loan->interest_rate(9.25);
$loan->term(20); # vingt ans
# MAINTENANT nous en savons assez pour calculer :
$loan->run;

# Et voir ce qui en est résulté :
print
  "Total payé en intérêts : UN INCROYABLE ",
  $loan->total_paid_interest, " !!\n";

Ceci illustre une convention courante avec les accesseurs : appeler l'accesseur sans arguments (comme avec $loan->total_paid_interest) signifie généralement lire la valeur de cet attribut, mais fournir une valeur (comme avec $loan->term(20)) signifie que vous voulez que cet attribut soit défini à cette valeur. Cela va de soi : pourquoi fourniriez-vous une valeur si ce n'est pour définir l'attribut à cette valeur ?

Bien que la durée, le principal et le taux d'intérêt d'un prêt soient tous des valeurs numériques uniques, les valeurs des objets peuvent être de n'importe quel type scalaire, ou un tableau, ou même une table de hachage. De plus, la ou les valeurs d'un attribut peuvent être des objets eux-mêmes. Par exemple, considérez les fichiers MIDI (comme je l'ai écrit dans TPJ#13) : un fichier MIDI se compose généralement de plusieurs pistes. Un fichier MIDI est assez complexe pour mériter d'être un objet avec des attributs tels que son tempo général, la variante du format de fichier qu'il utilise, et la liste des pistes d'instruments dans le fichier. Mais les pistes elles-mêmes sont assez complexes pour être aussi des objets, avec des attributs tels que leur type de piste, une liste de commandes MIDI s'il s'agit d'une piste MIDI, ou des données brutes si ce n'est pas le cas. J'ai donc fini par écrire les modules MIDI de sorte que l'attribut "tracks" d'un objet MIDI::Opus soit un tableau d'objets de la classe MIDI::Track. Cela peut sembler une entourloupe — vous demandez ce qu'il y a dans un objet, et vous obtenez *un autre* objet, ou plusieurs ! Mais dans ce cas, cela reflète exactement l'objectif du module — les fichiers MIDI contiennent des pistes MIDI, qui contiennent ensuite des données.

Qu'est-ce qu'une Valeur d'Objet ?

Lorsque vous appelez un constructeur comme Net::FTP->new(nom_hote), vous obtenez une valeur d'objet, une valeur que vous pouvez utiliser plus tard, en combinaison avec un nom de méthode, pour appeler des méthodes d'objets.

Maintenant, jusqu'à présent, nous avons fait semblant, dans les exemples ci-dessus, que les variables $session ou $loan *sont* les objets avec lesquels vous travaillez. Cette idée est inoffensive jusqu'à un certain point, mais c'est vraiment une conception erronée qui, au mieux, vous limitera dans ce que vous savez faire. La réalité n'est pas que les variables $session ou $query sont des objets ; c'est un peu plus indirect — elles *contiennent* des valeurs qui symbolisent des objets. Le type de valeur que $session ou $query contiennent est ce que j'appelle une valeur d'objet.

Pour comprendre de quel type de valeur il s'agit, pensez d'abord aux autres types de valeurs scalaires que vous connaissez : Les deux premières valeurs scalaires que vous avez probablement jamais rencontrées en Perl sont les nombres et les chaînes, qui, selon que vous les traitiez comme des nombres ou des chaînes, se transforment généralement les unes dans les autres sur demande ; c'est-à-dire que la chaîne de trois caractères "2.5" peut devenir la quantité deux et demi, et vice versa. Ensuite, surtout si vous avez commencé à utiliser "perl -w" tôt, vous avez découvert la valeur indéfinie, qui peut devenir 0 si vous la traitez comme un nombre, ou la chaîne vide si vous la traitez comme une chaîne.

Note de bas de page : Vous avez *peut-être* également appris les références, auquel cas vous êtes prêt à entendre que les valeurs d'objets ne sont qu'un type de référence, sauf qu'elles reflètent la classe qui a créé la chose à laquelle elles pointent, au lieu d'être simplement une référence de tableau, une référence de table de hachage, etc. *Si* cela a du sens pour vous, et que vous voulez en savoir plus sur la façon dont les objets sont implémentés en Perl, jetez un œil à la page de manuel "perltoot".

Et maintenant, vous découvrez les valeurs d'objets. Une valeur d'objet est une valeur qui pointe vers une structure de données quelque part en mémoire, où tous les attributs de cet objet sont stockés. Cette structure de données dans son ensemble appartient à une classe (probablement celle que vous avez nommée dans la méthode constructeur, comme ClassName->new), de sorte que la valeur d'objet puisse être utilisée dans les appels de méthodes d'objets.

Si vous voulez réellement *voir* ce qu'est une valeur d'objet, vous pourriez essayer de simplement dire "print $objet". Vous obtiendrez quelque chose comme ceci :

Net::FTP=GLOB(0x20154240)

ou

Business::US_Amort=HASH(0x15424020)

Ce n'est pas très utile si vous vouliez vraiment accéder à l'intérieur de l'objet, mais c'est parce que la valeur d'objet n'est qu'un symbole pour l'objet. Tout cela peut sembler très abstrait et métaphysique, donc une allégorie du monde réel pourrait être très utile :

Vous recevez une publicité par courrier indiquant que vous avez été sélectionné (im)personnellement pour avoir le rare privilège de demander une carte de crédit. Pour une raison quelconque, *cette* offre semble intéresod à vous, alors vous remplissez le formulaire et le renvoyez à la société de carte de crédit. Ils approuvent joyeusement la demande et créent votre compte, et vous envoient une carte avec un numéro dessus.

Maintenant, vous pouvez faire des choses avec le numéro de cette carte -- les employés des magasins peuvent enregistrer les articles que vous voulez acheter, et facturer votre compte en saisissant le numéro de la carte. Vous pouvez payer des articles que vous commandez en ligne en entrant le numéro de la carte dans le cadre de votre commande en ligne. Vous pouvez rembourser une partie du compte en envoyant aux gens de la carte de crédit un peu de votre argent (eh bien, un chèque) avec une note (généralement le coupon pré-imprimé) qui contient le numéro de la carte du compte que vous souhaitez rembourser. Et vous devriez pouvoir appeler l'ordinateur de la société de carte de crédit et lui poser des questions sur la carte, comme son solde, sa limite de crédit, son TAEG, et peut-être un détail des achats et paiements

récents.

Maintenant, ce que vous faites réellement, c'est manipuler un compte de carte de crédit, une entité complètement abstraite à laquelle sont attachées certaines données (solde, TAEG, etc). Mais pour faciliter l'accès, vous avez un numéro de carte de crédit qui est un symbole pour ce compte. Maintenant, ce symbole n'est qu'un ensemble de chiffres, et le numéro est effectivement dénué de sens et inutile en soi -- mais dans le contexte approprié, il est compris comme signifiant le compte de carte

de crédit auque
l vous accédez.

C'est exactement la relation entre les objets et les valeurs d'objet, et à partir de cette analogie, plusieurs faits sur les valeurs d'objet sont un peu plus explicables

:

* Une valeur d'objet ne fait rien en soi, mais elle est utile lorsque vous l'utilisez dans le contexte d'un appel $object->method, de la même manière que le numéro d'une carte est utile dans le contexte d'une opération traitant avec un compte de

carte.

De plus, plusieurs copies de la même valeur d'objet font toutes référence au même objet, de la même manière que faire plusieurs copies de votre numéro de carte ne changera pas le fait qu'elles font toutes référence au même compte unique (c'est vrai que vous « copiez » le numéro en l'écrivant simplement sur différents coupons de papier, ou que vous prenez la peine de forger des répliques exactes de votre propre carte de crédit en plastique). C'est pourquoi ceci

: 
$x = Net::FTP->new("ftp.aol.com");
$x->login("sburke", "aoeuaoeu")
;

fait la même chose que ceci

: 
$x = Net::FTP->new("ftp.aol.com");
$y = $x;
$z = $y;
$z->login("sburke", "aoeuaoeu")
;

C'est-à-dire, $z et $y et $x sont trois emplacements différents pour les valeurs, mais ce qui est dans ces emplacements sont toutes des valeurs d'objet pointant vers le même objet -- vous n'avez pas trois connexions FTP différentes, juste trois variables avec des valeurs pointant vers la même connexion FTP

unique.

* Vous ne pouvez pas dire grand-chose sur l'objet simplement en regardant la valeur d'objet, pas plus que vous ne pouvez voir le solde de votre compte de crédit en tenant la carte en plastique à la lumière, ou en additionnant les chiffres de votre numéro de carte de

crédit.

* Vous ne pouvez pas inventer vos propres valeurs d'objet et les faire fonctionner -- elles ne peuvent provenir que des méthodes constructrices de la classe appropriée. De même, vous obtenez un numéro de carte de crédit seulement en faisant approuver par une banque votre demande de compte de carte de crédit -- auquel moment ils vous font savoir quel est le numéro de votre nouvelle

carte.

Maintenant, il y a encore plus à dire sur le fait que vous ne pouvez pas inventer votre propre valeur d'objet : même si vous pouvez imprimer une valeur d'objet et obtenir une chaîne comme "Net::FTP=GLOB(0x20154240)", cette chaîne n'est qu'une représentation d'une valeur

d'objet.

En interne, une valeur d'objet a fondamentalement un type différent d'une chaîne, ou d'un nombre, ou de la valeur indéfinie -- si $x contient une vraie chaîne, alors l'emplacement de cette valeur en mémoire dit « ceci est une valeur de type chaîne, et ses caractères sont... », alors que si c'est une valeur d'objet, l'emplacement de la valeur en mémoire dit, « ceci est une valeur de type référence, et l'emplacement en mémoire vers lequel elle pointe est... » (et en regardant ce qui est à cet emplacement, Perl peut dire la classe de ce qui s'y trouve)

.

Les programmeurs Perl n'ont généralement pas à penser à tous ces détails des entrailles de Perl. Beaucoup d'autres langages vous forcent à être plus conscient des différences entre tous ceux-ci (et aussi entre les types de nombres, qui sont stockés différemment en fonction de leur taille et de s'ils ont des parties fractionnaires). Mais Perl fait de son mieux pour cacher les différents types de scalaires -- il transforme les nombres en chaînes et inversement selon le besoin, et prend la représentation en chaîne ou en nombre de undef ou des valeurs d'objet selon le besoin. Cependant, vous ne pouvez pas passer d'une représentation en chaîne d'une valeur d'objet à une valeur d'objet. Et c'est pourquoi ceci ne fonctionne pas

: 
 $x = Net::FTP->new('ftp.aol.com');
 $y = Net::FTP->new('ftp.netcom.com');
 $z = Net::FTP->new('ftp.qualcomm.com');
 $all = join(' ', $x,$y,$z);           # !!!
...plus tard...
 ($aol, $netcom, $qualcomm) = split(' ', $all);  # !!!
 $aol->login("sburke", "aoeuaoeu");
 $netcom->login("sburke", "qjkxqjkx");
 $qualcomm->login("smb", "dhtndhtn")
;

Cela échoue parce que $aol finit par contenir simplement la représentation en chaîne de la valeur d'objet de $x, pas la valeur d'objet elle-même -- quand "join" a essayé de joindre les caractères des « chaînes » $x, $y, et $z, Perl a vu qu'elles n'étaient pas du tout des chaînes, alors il a donné à "join" leurs représentations en

chaîne.

Malheureusement, cette distinction entre les valeurs d'objet et leurs représentations en chaîne ne s'intègre vraiment pas dans l'analogie des numéros de carte de crédit, parce que les numéros de carte de crédit sont vraiment des nombres -- même s'ils n'expriment aucune quantité significative, si vous les stockiez dans une base de données comme une quantité (par opposition à juste une chaîne ASCII), cela ne les empêcherait pas d'être valides en tant que numéros de carte de

crédit.

Cela peut sembler plutôt académique, mais il y a deux erreurs courantes que les programmeurs nouveaux aux objets font souvent, qui n'ont de sens qu'en termes de la distinction entre les valeurs d'objet et leurs représentations en chaîne

:

La première erreur courante consiste à oublier (ou à ne jamais avoir su dès le début) que quand vous utilisez une valeur comme clé de hachage, Perl utilise la représentation en chaîne de cette valeur. Quand vous voulez utiliser la valeur numérique deux et demi comme clé, Perl la transforme en la chaîne de trois caractères "2.5". Mais si vous voulez ensuite utiliser cette chaîne comme un nombre, Perl la traitera comme signifiant deux et demi, alors vous n'êtes généralement pas plus avisé que Perl a converti le nombre en chaîne et inversement. Mais rappelez-vous que Perl ne peut pas transformer les chaînes en objets -- alors si vous essayiez d'utiliser une valeur d'objet Net::FTP comme clé de hachage, Perl a en fait utilisé sa représentation en chaîne, comme "Net::FTP=GLOB(0x20154240)", mais cette chaîne est inutilisable comme valeur d'objet. (Incidemment, il y a un module Tie::RefHash qui implémente des hachages qui vous permettent d'utiliser de vraies valeurs d'objet comme clés.

)

La deuxième erreur courante avec les valeurs d'objet consiste à essayer de sauvegarder une valeur d'objet sur disque (qu'il s'agisse de l'imprimer dans un fichier, ou de la stocker dans un fichier de base de données conventionnel). Tout ce que vous obtiendrez est la chaîne, qui sera

inutile.

Quand vous voulez sauvegarder un objet et le restaurer plus tard, vous pouvez trouver que la classe de l'objet fournit déjà une méthode spécialement pour cela. Par exemple, MIDI::Opus fournit des méthodes pour écrire un objet sur disque en tant que fichier MIDI standard. Le fichier peut ensuite être relu en mémoire par une méthode constructrice MIDI::Opus, qui retournera un nouvel objet MIDI::Opus représentant le fichier que vous lui demandez de lire en mémoire. Des méthodes similaires sont disponibles avec, par exemple, les classes qui manipulent des images graphiques et peuvent les sauvegarder dans des fichiers, qui peuvent être relus plus

tard.

Mais certaines classes, comme Business::US_Amort, ne fournissent pas de telles méthodes pour stocker un objet dans un fichier. Dans ce cas, vous pouvez essayer d'utiliser l'un des modules Data::Dumper, Storable, ou FreezeThaw. L'utilisation de ceux-ci ne posera pas de problème pour les objets de la plupart des classes, mais cela peut rencontrer des limitations avec d'autres. Par exemple, un objet Business::US_Amort peut être transformé en une chaîne avec Data::Dumper, et cette chaîne écrite dans un fichier. Quand il est restauré plus tard, ses attributs seront accessibles normalement. Mais dans le cas peu probable où l'objet de prêt a été sauvegardé en pleine calcul, le calcul peut ne pas être reprenable. C'est à cause de la manière dont cette classe particulière fait ses calculs, mais des limitations similaires peuvent survenir avec des objets d'autres

classes.

Mais souvent, même vouloir sauvegarder un objet est fondamentalement faux -- que signifierait sauvegarder une session ftp ? Sauvegarder le nom d'hôte, le nom d'utilisateur, et le mot de passe ? le répertoire courant sur les deux machines ? le numéro de port TCP/IP local ? Dans le cas de la « sauvegarde » d'un objet Net::FTP,

vous ferez mieux de sauvegarder simplement les détails dont vous avez réellement besoin pour vos propres b
esoins, afin que vous puissiez créer un nouvel objet plus tard et simplement définir ces valeurs pour lui.

Alors Pourquoi Certains Modules Utilisent-ils les Objets

?

Tous ces détails de l'utilisation des objets sont définitivement suffisants pour vous faire vous demander -- est-ce que ça vaut la peine ? Si vous êtes un auteur de module, écrire votre module avec une interface orientée objet restreint l'audience des utilisateurs potentiels à ceux qui comprennent les concepts de base des objets et des valeurs d'objet, ainsi que la syntaxe de Perl pour appeler des méthodes. Pourquoi compliquer les choses en ayant une interface orientée objet

?

Une réponse quelque peu ésotérique est qu'un module a une interface orientée objet parce que l'intérieur du module est écrit dans un style orienté objet. Cet article est sur les bases des interfaces orientées objet, et ce serait aller bien trop loin pour expliquer ce qu'est la conception orientée objet. Mais la version courte est que la conception orientée objet est juste une manière d'attaquer des problèmes désordonnés. C'est une manière que beaucoup de programmeurs trouvent très utile (et que d'autres trouvent par hasard bien plus contraignante que ce que ça vaut, incidemment), et elle se trouve juste montrer pour vous, l'utilisateur de module, comme simplement le style

d'interface.

Mais une réponse plus simple est qu'une interface fonctionnelle est parfois un obstacle, parce qu'elle limite le nombre de choses que vous pouvez faire à la fois -- le limitant, en fait, à un. Pour beaucoup de problèmes que certains modules sont censés résoudre, se passer d'une interface orientée objet serait comme souhaiter que Perl n'utilise pas de filehandles. Les idées sont plutôt plus simples -- imaginez simplement que Perl vous permette d'accéder aux fichiers, mais seulement un à la fois, avec du code comme

: 
open("foo.txt") || die "Can't open foo.txt: $!";
while(readline) {
  print $_ if /bar/;
}
close;

Ce genre hypothétique de Perl serait simpler, en se passant de filehandles. Mais vous seriez mal barré si vous vouliez lire d'un fichier tout en lisant d'un autre, ou lire de deux fichiers et écrire dans un troisième.

De la même manière, un module FTP fonctionnel serait bien pour simplement télécharger des fichiers vers un serveur à la fois, mais il ne permettrait pas d'écrire facilement des programmes qui auraient besoin d'utiliser plusieurs sessions simultanées (comme « regarder le serveur A et le serveur B, et si A a un fichier nommé X.dat, alors le télécharger localement puis le téléverser sur le serveur B -- sauf si B a un fichier nommé Y.dat, auquel cas faire l'inverse »).

Certains types de problèmes que les modules résolvent se prêtent juste à une interface orientée objet. Pour ces types de tâches, une interface fonctionnelle serait plus familière, mais moins puissante. Apprendre à utiliser les interfaces des modules orientés objet demande de se familiariser avec les concepts de cet article. Mais au final, cela vous permettra d'utiliser une gamme plus large de modules et, avec eux, d'écrire des programmes qui peuvent faire plus.

Les détails techniques

Pour des raisons de clarté d'explication, j'ai dû simplifier certains faits concernant les objets. Voici quelques-uns des détails plus techniques :

* Tous les exemples que j'ai donnés de constructeurs étaient des méthodes de classe. Mais les méthodes d'objet peuvent aussi être des constructeurs, si la classe a été écrite pour fonctionner ainsi : $nouveau = $ancien->copie, $noeud_y = $noeud_x->nouveau_sousnoeud, ou similaire.

* J'ai donné l'impression qu'il y avait deux types de méthodes : méthodes d'objet et méthodes de classe. En fait, la même méthode peut être les deux, car ce n'est pas le type de méthode qui compte, mais le type d'appels qu'elle est écrite pour accepter -- des appels qui passent un objet, ou des appels qui passent un nom de classe.

* Le terme « valeur objet » n'est pas quelque chose que vous trouverez utilisé ailleurs. C'est juste mon raccourci pour ce qu'on appellerait correctement une « référence objet » ou une « référence à un élément béni ». En fait, les gens disent généralement « objet » quand ils veulent correctement dire une référence à cet objet.

* J'ai mentionné la création d'objets avec des constructeurs, mais je n'ai pas mentionné leur déstruction -- un destructeur est un type de méthode que vous appelez pour nettoyer l'objet une fois que vous avez terminé avec lui et que vous voulez qu'il disparaisse proprement (fermer des connexions, supprimer des fichiers temporaires, libérer de la mémoire, etc). Mais en raison de la façon dont Perl gère la mémoire, la plupart des modules ne nécessiteront pas à l'utilisateur de connaître les destructeurs.

* J'ai dit que la syntaxe des méthodes de classe doit avoir le nom de la classe, comme dans $session = Net::FTP->nouveau($hote). En fait, vous pouvez à la place utiliser toute expression qui retourne un nom de classe : $classe_ftp = 'Net::FTP'; $session = $classe_ftp->nouveau($hote). De plus, au lieu du nom de la méthode pour les appels de méthodes objet ou de classe, vous pouvez utiliser une variable scalaire contenant le nom de la méthode : $foo->$methode($hote). Mais, en pratique, ces syntaxes sont rarement utiles.

Et enfin, pour en apprendre davantage sur les objets du point de vue de la création de vos propres classes, consultez la documentation "perltoot", ou le livre exhaustif et clair de Damian Conway, Object Oriented Perl (Manning Publications 1999, ISBN 1-884777-79-1).
