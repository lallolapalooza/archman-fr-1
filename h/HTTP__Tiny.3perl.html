HTTP::Tiny(3perl) Guide du programmeur Perl HTTP::Tiny(3perl)

NOM

HTTP::Tiny - Un client HTTP/1.1 petit, simple et correct

VERSION

version 0.090

SYNOPSIS

use HTTP::Tiny;
my $response = HTTP::Tiny->new->get('http://example.com/');
die "Échec !\n" unless $response->{success};
print "$response->{status} $response->{reason}\n";
while (my ($k, $v) = each %{$response->{headers}}) {
    for (ref $v eq 'ARRAY' ? @$v : $v) {
        print "$k: $_\n";
    }
}
print $response->{content} if length $response->{content};

DESCRIPTION

Ceci est un client HTTP/1.1 très simple, conçu pour effectuer des requêtes simples sans la surcharge d'un grand framework comme LWP::UserAgent.

Il est plus correct et plus complet que HTTP::Lite. Il prend en charge les proxys et les redirections. Il reprend également correctement après EINTR.

Si IO::Socket::IP 0.25 ou une version ultérieure est installé, HTTP::Tiny l'utilisera à la place de IO::Socket::INET pour un support transparent de IPv4 et IPv6.

Le support des cookies nécessite HTTP::CookieJar ou une classe équivalente.

MÉTHODES

new

$http = HTTP::Tiny->new( %attributs );

Ce constructeur renvoie un nouvel objet HTTP::Tiny. Les attributs valides incluent :

  • "agent" — Une chaîne de caractères de type user-agent (par défaut : 'HTTP-Tiny/$VERSION'). Si "agent" — se termine par un espace, la chaîne de caractères user-agent par défaut est ajoutée.
  • "cookie_jar" — Une instance de HTTP::CookieJar — ou une classe équivalente qui prend en charge les méthodes "add" et "cookie_header"
  • "default_headers" — Un hashref d'en-têtes par défaut à appliquer aux requêtes
  • "local_address" — L'adresse IP locale à laquelle se lier
  • "keep_alive" — Réutiliser la dernière connexion (si pour le même schéma, hôte et port) (par défaut : 1)
  • "max_redirect" — Nombre maximum de redirections autorisées (par défaut : 5)
  • "max_size" — Taille maximale de la réponse en octets (uniquement lorsque vous n'utilisez pas de rappel de données). Si défini, les requêtes dont les réponses sont supérieures à cette taille renverront un code d'état 599.
  • "http_proxy" — URL d'un serveur proxy à utiliser pour les connexions HTTP (par défaut : $ENV{http_proxy} — si défini)
  • "https_proxy" — URL d'un serveur proxy à utiliser pour les connexions HTTPS (par défaut : $ENV{https_proxy} — si défini)
  • "proxy" — URL d'un serveur proxy générique pour les connexions HTTP et HTTPS (par défaut : $ENV{all_proxy} — si défini)
  • "no_proxy" — Liste des suffixes de domaines qui ne doivent pas être proxifiés. Doit être une chaîne de caractères séparée par des virgules ou une référence de tableau. (par défaut : $ENV{no_proxy} —)
  • "timeout" — Délai d'attente de la requête en secondes (par défaut : 60). Si l'ouverture, la lecture ou l'écriture d'une socket prend plus de temps que le délai d'attente, le code d'état de la réponse de la requête sera 599.
  • "verify_SSL" — Un booléen qui indique s'il faut valider le certificat TLS/SSL d'une connexion "https" — (par défaut : vrai). Changé de faux à vrai dans la version 0.083.
  • "SSL_options" — Un hashref d'options "SSL_*" — à passer à IO::Socket::SSL
  • $ENV{PERL_HTTP_TINY_SSL_INSECURE_BY_DEFAULT} - Modifie le comportement de vérification par défaut des certificats pour ne pas vérifier l'identité du serveur si défini à 1. N'est efficace que si "verify_SSL" n'est pas défini. Ajouté dans la version 0.083.

Une méthode d'accès/mutateur existe pour chaque attribut.

Passer une valeur explicite "undef" pour "proxy", "http_proxy" ou "https_proxy" empêchera de récupérer les proxys correspondants de l'environnement.

Les erreurs lors de l'exécution de la requête entraîneront un code d'état pseudo-HTTP de 599 et une raison de "Internal Exception". Le champ contenu de la réponse contiendra le texte de l'erreur.

Le paramètre "keep_alive" active une connexion persistante, mais uniquement vers un seul schéma de destination, hôte et port. Si des attributs pertinents pour la connexion sont modifiés via un accesseur, ou si l'ID de processus ou l'ID de thread change, la connexion persistante sera interrompue. Si vous souhaitez des connexions persistantes entre plusieurs destinations, utilisez plusieurs objets HTTP::Tiny.

Voir "SUPPORT TLS/SSL" pour plus d'informations sur les attributs "verify_SSL" et "SSL_options".

get|head|put|post|patch|delete

$response = $http->get($url);
$response = $http->get($url, \%options);
$response = $http->head($url);

Ces méthodes sont des raccourcis pour appeler request() pour la méthode donnée. L'URL doit avoir les caractères non sécurisés échappés et les noms de domaine internationaux encodés. Voir request() pour les options valides et une description de la réponse.

Le champ "success" de la réponse sera vrai si le code d'état est 2XX.

post_form

$response = $http->post_form($url, $form_data);
$response = $http->post_form($url, $form_data, \%options);

Cette méthode exécute une requête "POST" et envoie les paires clé/valeur d'un hachage ou d'une référence de tableau de données de formulaire à l'URL donnée avec un "content-type" de "application/x-www-form-urlencoded". Si les données sont fournies sous forme de référence de tableau, l'ordre est préservé ; si elles sont fournies sous forme de référence de hachage, les termes sont triés par clé pour la cohérence. Voir la documentation de la méthode "www_form_urlencode" pour les détails de l'encodage.

L'URL doit avoir les caractères non sécurisés échappés et les noms de domaine internationaux encodés. Voir request() pour les options valides et une description de la réponse. Tout en-tête "content-type" ou contenu dans le hashref d'options sera ignoré.

Le champ "success" de la réponse sera vrai si le code d'état est 2XX.

mirror

$response = $http->mirror($url, $file, \%options)
if ( $response->{success} ) {
    print "$file est à jour\n";
}

Exécute une requête "GET" pour l'URL et enregistre le corps de la réponse dans le nom de fichier fourni. L'URL doit avoir les caractères non sécurisés échappés et les noms de domaine internationaux encodés. Si le fichier existe déjà, la requête inclura un en-tête "If-Modified-Since" avec l'horodatage de modification du fichier. Vous pouvez spécifier vous-même un en-tête "If-Modified-Since" différent dans le hachage "$options->{headers}".

Le champ "success" de la réponse sera vrai si le code d'état est 2XX ou s'il est 304 (non modifié).

Si le fichier a été modifié et que la réponse du serveur inclut un en-tête "Last-Modified" correctement formaté, l'heure de modification du fichier sera mise à jour en conséquence.

$response = $http->request($method, $url);
$response = $http->request($method, $url, \%options);

REMARQUE : Les noms de méthode sont sensibles à la casse conformément à la spécification HTTP/1.1. N'utilisez pas "get" lorsque vous voulez vraiment "GET". Voir LIMITATIONS pour savoir comment cela s'applique aux

Si l'URL contient un segment "user:password", ceux-ci seront utilisés pour les en-têtes d'autorisation de style Basic. (Les en-têtes d'autorisation ne seront pas inclus dans une requête redirigée.) Par exemple

$http->request('GET', 'http://Aladdin:open sesame@example.com/')
;

Si le segment "user:password" contient des caractères réservés, ils doivent être échappés par pourcentage

: 
$http->request('GET', 'http://john%40example.com:password@example.com/')
;

Une référence de hachage d'options peut être ajoutée pour modifier la

requête.

Les options valides sont

:
  • "headers" — Une référence de hachage contenant les en-têtes à inclure avec la requête. Si la valeur d'un en-tête est une référence de tableau, l'en-tête sera affiché plusieurs fois avec chaque valeur du tableau. Ces en-têtes remplacent tous les en-têtes par
    • défaut.
  • "content" — Un scalaire à inclure comme corps de la requête OU une référence de code qui sera appelée itérativement pour produire le corps de la
    • requête
  • "trailer_callback" — Une référence de code qui sera appelée si elle existe pour fournir une référence de hachage des en-têtes de fin (utilisé uniquement avec l'encodage de transfert par
    • blocs)
  • "data_callback" — Une référence de code qui sera appelée pour chaque bloc de corps de réponse
    • reçu.
  • "peer" — Remplace la résolution de l'hôte et force toutes les connexions à n'aller que vers une adresse de pair spécifique, quelle que soit l'URL de la requête. Cela inclura toutes les redirections ! Cette option doit être utilisée avec une
    • extrême prudence (par exemple pour le débogage ou des circonstances très particulières). Elle peut être donnée soit comme
un scalaire, soit comme une référence de code qui recevra le nom d'hôte et dont la réponse sera prise comme adresse.

L'en-tête "Host" est généré à partir de l'URL conformément à la RFC 2616. Il est une erreur fatale de spécifier "Host" dans l'option "headers". Les autres en-têtes peuvent être ignorés ou écrasés si nécessaire pour la conformité du

transport.

Si l'option "content" est une référence de code, elle sera appelée itérativement pour fournir le corps de contenu de la requête. Elle doit renvoyer la chaîne vide ou undef lorsque l'itérateur est

épuisé.

Si l'option "content" est la chaîne vide, aucun en-tête "content-type" ou "content-length" ne sera

généré.

Si l'option "data_callback" est fournie, elle sera appelée itérativement jusqu'à ce que tout le corps de réponse soit reçu. Le premier argument sera une chaîne contenant un bloc du corps de réponse, le second argument sera la référence de hachage de réponse en cours, comme décrit ci-dessous. (Cela permet de personnaliser l'action de la callback en fonction du "status" ou des "headers" reçus avant le corps de contenu.

)

Les données de contenu dans la requête/réponse sont traitées comme des « octets bruts ». Toute encodage/décodage (avec les en-têtes associés) est la responsabilité de

l'appelant.

La méthode "request" renvoie une référence de hachage contenant la réponse. La référence de hachage aura les clés suivantes

:
  • "success" — Booléen indiquant si l'opération a renvoyé un code de statut
    • 2XX
  • "url" — URL qui a fourni la réponse. Il s'agit de l'URL de la requête sauf s'il y a eu des redirections, auquel cas il s'agit de la dernière URL interrogée dans une chaîne de
    • redirections
  • "status" — Le code de statut HTTP de la
    • réponse
  • "reason" — La phrase de réponse renvoyée par le
    • serveur
  • "content" — Le corps de la réponse. Si la réponse n'a pas de contenu ou si un callback de données est fourni pour consommer le corps de réponse, ce sera la chaîne
    • vide
  • "headers" — Une référence de hachage des champs d'en-tête. Tous les noms de champs d'en-tête seront normalisés en minuscules. Si un en-tête est répété, la valeur sera une référence de tableau ; sinon, ce sera un scalaire de chaîne contenant la
    • valeur
  • "protocol" - Si ce champ existe, c'est le protocole de la réponse tel que HTTP/1.0 ou HTTP/1.
    • 1
  • "redirects" Si ce champ existe, c'est une référence de tableau de références de hachage de réponse provenant des redirection
    • s, dans le même ordre que les redirections se sont produite
s. S'il n'existe pas, alors aucune redirection n'a eu lieu.

En cas d'erreur lors de l'exécution de la requête, le champ "status" contiendra 599, et le "content" contiendra le

texte de l'erreur.

www_form_urlencod

e 
$params = $http->www_form_urlencode( $data );
$response = $http->get("http://example.com/query?$params")
;

Cette méthode convertit les paires clé/valeur d'une référence de hachage ou de tableau de données en une chaîne "x-www-form-urlencoded". Les clés et valeurs de la référence de données seront encodées en UTF-8 et échappées conformément à la RFC 3986. Si une valeur est une référence de tableau, la clé sera répétée avec c

hacune des valeurs de la référence de tableau. Si les données sont fournies sous forme de référence de hach
age, les paires clé/valeur de la chaîne résultante seront triées par clé et valeur pour un ordre cohérent.

SUPPORT

TLS/SSL

Les connexions "https" directes sont prises en charge uniquement si IO::Socket::SSL 1.56 ou supérieur et Net::SSLeay 1.49 ou supérieur sont installés. Une erreur se produira si des versions suffisamment récentes de ces modules ne sont pas installées ou si le chiffrement TLS échoue. Vous pouvez également utiliser la fonction utilitaire HTTP::Tiny::can_ssl() qui renvoie un booléen pour voir si les modules requis sont

installés.

Une connexion "https" peut être établie via un proxy "http" qui prend en charge la commande CONNECT (c'est-à-dire la RFC 2817). Vous ne pouvez pas utiliser de proxy "https" via un proxy qui exige lui-même "https" pour

communiquer.

TLS/SSL fournit deux capacités distinctes

:
  • Canal de communication
    • chiffré
  • Vérification
    • de l'identit
é du serveur

Par défaut, HTTP::Tiny vérifie l'id

entité du serveur.

Cela a été changé dans la version 0.083 pour des raisons de sécurité. Le comportement par défaut précédent peut être activé en définissant $ENV{PERL_HTTP_TINY_SSL_INSECURE_BY_DEFAULT} à

1.

La vérification est effectuée en vérifiant que la connexion TLS/SSL a un certificat valide correspondant au nom d'hôte de la connexion et que le certificat a été vérifié par une CA. En supposant que vous faites confiance à la CA, cela vous protégera contre les attaques de type machine-in-the-middle http://en.wikipedia.org/wiki/Machine-in-the-middle_attack

.

La vérification des certificats nécessite un fichier ou un répertoire contenant des certificats de CA de

confiance.

IO::Socket::SSL::default_ca() est appelée pour détecter l'emplacement par défaut de vos certificats de CA. Elle prend également en charge les variables d'environnement "SSL_CERT_FILE" et "SSL_CERT_DIR", et utilisera Mozilla::CA en secours si aucun certificat n'est

trouvé.

Si IO::Socket::SSL::default_ca() n'est pas en mesure de trouver des certificats de CA utilisables, HTTP::Tiny cherchera plusieurs emplacements par défaut bien connus et spécifiques au système pour un fichier de certificat de CA en dernier recours

:
  • /etc/ssl/certs/ca-certificates.
    • crt
  • /etc/pki/tls/certs/ca-bundle.
    • crt
  • /etc/ssl/ca-bundle.
    • pem
  • /etc/openssl/certs/ca-certificates.
    • crt
  • /etc/ssl/cert.
    • pem
  • /usr/local/share/certs/ca-root-nss.
    • crt
  • /etc/pki/tls/cacert.
    • pem
  • /etc/certs
    • /ca-certif
icates.crt

Une erreur se produira si "verify_SSL" est vrai et qu'aucun fichier de certificat de CA n'est

disponible.

Si vous souhaitez un contrôle total sur les connexions TLS/SSL, l'attribut "SSL_options" vous permet de fournir une référence de hachage qui sera transmise à IO::Socket::SSL::start_SSL(), remplaçant toutes les options définies par HTTP::Tiny. Par exemple, pour fournir votre propre fichier de CA de confiance

: 
SSL_options => {
    SSL_ca_file => $file_path,
}

L'attribut "SSL_options" attribute pourrait aussi servir à fournir un certificat client pour l'authentification auprès d'un serveur ou à contrôle

r le choix du chiffrement utilisé pour la connexion TLS/SSL. V
oir la documentation de IO::Socket::SSL pour plus de détails.

SUPPORT DU

PROXY

HTTP::Tiny peut utiliser un proxy pour les requêtes "http" et "https". Seule l'autorisation de proxy de type Basic est prise en charge et elle doit être fournie dans l'URL du proxy : "http://user:pass@proxy.examp

le.com/".

HTTP::Tiny prend en charge les variables d'environnement de proxy suivantes

:
  • http_proxy ou
    • HTTP_PROXY
  • https_proxy ou
    • HTTPS_PROXY
  • all_pro
    • xy ou AL
L_PROXY

Si la variable d'environnement "REQUEST_METHOD" est définie, il peut s'agir d'un processus CGI et "HTTP_PROXY" serait définie à partir de l'en-tête "Proxy:", ce qui constitue un risque de sécurité. Si "REQUEST_METHOD" est définie, "HTTP_PROXY" (seulement la variante en majuscules) est ignorée, mais "CGI_HTTP_PROXY" est considérée à la

place.

Le tunneling de "https" à travers un proxy "http" à l'aide de la méthode CONNECT est pris en charge. Si votre proxy utilise lui-même "https", vous ne pouvez pas établir de tunnel "https" à travers

lui.

Soyez averti que le proxying d'une connexion "https" vous expose au risque d'une attaque de type man-in-the-middle par le serveur

proxy.

La variable d'environnement "no_proxy" est prise en charge au format d'une liste de suffixes de domaine séparés par des virgules pour lesquels le proxy ne doit pas être

utilisé.

Les arguments de proxy passés à "new" remplaceront leurs variables d'environnement

correspondantes
.

LIMITATION

S

HTTP::Tiny est conditionnellement conforme aux spécifications HTTP/1.1 sur http://www.w3.org/Pr

otocols/ :
  • « Message Syntax and Routing »
    • [RFC7230]
  • « Semantics and Content »
    • [RFC7231]
  • « Conditional Requests »
    • [RFC7232]
  • « Range Requests »
    • [RFC7233]
  • « Caching »
    • [RFC7234]
  • « Authent
    • ication »
[RFC7235]

Il tente de satisfaire à toutes les exigences « MUST » de la spécification, mais n'implémente pas toutes les exigences « SHOULD ». (Remarque : il a été développé contre l'ancienne spécification RFC 2616 et peut ne pas encore être conforme à la spécification révisée RFC 7230-7235.) De plus, HTTP::Tiny prend en charge la méthode "PATCH" de la RFC

5789.

Certaines limitations particulières à noter incluent

:
  • HTTP::Tiny se concentre sur le transport correct. Les utilisateurs sont responsables de s'assurer que les en-têtes et le contenu définis par l'utilisateur sont conformes à la spécification HTTP/1.
    • 1.
  • Les utilisateurs doivent s'assurer que les URL sont correctement échappées pour les caractères non sûrs et que les noms de domaine internationaux sont correctement encodés en ASCII. Voir URI::Escape, URI::_punycode et Net::IDN::
    • Encode.
  • La redirection est très stricte par rapport à la spécification. La redirection n'est automatique que pour les codes de réponse 301, 302, 307 et 308 si la méthode de requête est 'GET' ou 'HEAD'. Le code de réponse 303 est toujours converti en une redirection 'GET', comme le mandaté par la spécification. Il n'y a pas de support automatique pour les redirections de statut 305 (« Use proxy
    • »).
  • Il n'y a aucune disposition pour retarder un corps de requête à l'aide d'un en-tête "Expect". Les réponses "1XX" inattendues sont silencieusement ignorées conformément à la
    • spécification.
  • Seul le "Transfer-Encoding" de type 'chunked' est pris en
    • charge.
  • Il n'y a pas de support pour une Request-URI de '*' pour la requête
    • 'OPTIONS'.
  • Les en-têtes mentionnés dans les RFC et certains autres en-têtes bien connus sont générés avec leur cas
    • canonique. Les autres en-têtes sont envoyés dans le cas fourni par l'utilisateur. À l'exception des en-tê
tes de contrôle (qui sont envoyés en premier), les en-têtes sont envoyés dans un ordre arbitraire.

Malgré les limitations listées ci-dessus, HTTP::Tiny est considéré c

omme complet en termes de fonctionnalités. Les nouvelles demand
es de fonctionnalités doivent être adressées à HTTP::Tiny::UA.
