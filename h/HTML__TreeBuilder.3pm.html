DESCRIPTIO

N

(Cette classe fait partie de la distribution HTML::Tree.

)

Cette classe est destinée aux arborescences syntaxiques HTML qui sont construites à partir de la source HTML. La manière de l'utiliser est la suivante

:

1. démarrer un nouvel objet HTML::TreeBuilder (vide)

,

2. puis utiliser l'une des méthodes de HTML::Parser (probablement avec "$tree->parse_file($filename)" pour les fichiers, ou avec "$tree->parse($document_content)" et "$tree->eof" si vous avez le contenu dans une chaîne) pour analyser le document HTML dans l'arborescence $tree

.

(Vous pouvez combiner les étapes 1 et 2 avec les méthodes "new_from_file" ou "new_from_content".

)

2b. appeler "$root->elementify()" si vous le

souhaitez.

3. faire ce que vous avez besoin de faire avec l'arborescence syntaxique, impliquant probablement sa traversée à la recherche

d'informations,

4. les versions précédentes de HTML::TreeBuilder exigeaient que vous appeliez "$tree->delete()" pour effacer le contenu de l'arborescence de la mémoire lorsque vous avez terminé.

Cela n'est plus normalement requis. Voir "Weak Re
ferences" dans HTML::Element pour plus de détails.

ATTRIBUT

S

La plupart des attributs suivants, propres à HTML::TreeBuilder, contrôlent la manière dont l'analyse se déroule ; ils doivent être définis avant d'essayer d'analyser dans l'objet donné. Vous pouvez définir les attributs en passant une valeur VRAIE ou FAUSSE comme argument. Par exemple, "$root->implicit_tags" renvoie le paramètre actuel pour l'option "implicit_tags", "$root->implicit_tags(1)" active cette option, et "$root->implicit_tags(0)" la

désactive.

implicit_tag

s

Définir cet attribut à vrai indiquera à l'analyseur d'essayer de déduire les éléments implicites et les balises de fin implicites. S'il est faux, vous obtenez une arborescence d'analyse qui reflète simplement le texte tel qu'il est, ce qui est peu susceptible d'être utile autrement que pour une analyse rapide et approximative. (En fait, je serais curieux de savoir si quelqu'un trouve utile d'avoir "implicit_tags" défini à faux.) La valeur par défaut est

vrai.

Cela contrôle un aspect du comportement des éléments implicites, si "implicit_tags" est activé : si un élément texte (PCDATA) ou un élément phrasal (comme "<em>") doit être inséré sous "<body>", deux choses peuvent se produire : si "implicit_body_p_tag" est vrai, il est placé sous une nouvelle balise "<p>" implicite. t

S'il est défini à vrai (et qu'il est faux par défaut), TreeBuilder adoptera une vision plus stricte que la normale de ce qui peut se trouver sous un élément "<p>" ; s'il voit un élément non phrasal sur le point d'être inséré sous un "<p>", il fermera ce "<p>". Sinon, il ne fermera les éléments "<p>" que pour d'autres "<p>", les titres, et "<form>" (bien que ce dernier puisse être supprimé dans les futures versions)

Par exemple, lors du traitement de cet extrait de

En théorie, il devrait y avoir des options de sévérité comme celle-ci pour d'autres/ tous les éléments, pas seulement pour "<p>" ; mais je traite cela comme un cas particulier simplement en raison du fait que "<p>" apparaît si fréquemment et que sa balise de fin est si souvent omise ; et aussi parce que l'application de règles de sévérité au moment de l'analyse sur tous les éléments rend souvent de petites erreurs de codage HTML produire des arborescences d'analyse drastiquement mauvaises, d'après mon

expérience.

Si vous trouvez que vous aimeriez avoir une option comme celle-ci pour faire respecter les

modèles de contenu sur tous les éléments, alors je suggère que ce que vous voulez est un
e vérification du modèle de contenu comme étape après que TreeBuilder a terminé l'analyse.

Les objets de cette classe héritent des méthodes à la fois de HTML::Parser et de HTML::Element. Les méthodes héritées de HTML::Parser sont utilisées pour construire l'arbre HTML, et les méthodes héritées de HTML::Element sont celles que vous utilisez pour examiner l'arbre. En plus de cette documentation (HTML::TreeBuilder), vous devez aussi lire attentivement la documentation de HTML::Element, et aussi parcourir la documentation de HTML::Parser -- probablement seulement ses méthodes parse et parse_file sont

d'intérêt.

parse_fil

e 
$root->parse_file(...
)

[Une méthode importante héritée de HTML::Parser, voir cette dernière. Les versions actuelles de HTML::Parser peuvent prendre une spécification de fichier, ou un objet filehandle, comme *FOO, ou un objet de la classe IO::Handle, IO::File, IO::Socket) ou similaire. Je pense que vous devriez vérifier qu'un fichier donné existe avant d'appeler "$root->parse_file($filespec)".

Quand vous passez un nom de fichier à "parse_file", HTML::Parser l'ouvre en mode binaire, ce qui signifie qu'il est interprété comme Latin-1 (ISO-8859-1). Si le fichier est dans une autre encodage, comme UTF-8 ou UTF-16, cela ne fera pas les choses

correctement.

Une solution est d'ouvrir le fichier vous-même en utilisant la couche ":encoding" appropriée, et de passer le filehandle à "parse_file". Vous pouvez automatiser ce processus en utilisant "html_file" dans IO::HTML, qui utilisera l'algorithme de détection d'encodage HTML5 pour déterminer automatiquement la couche ":encoding" appropriée et

l'appliquer.

Dans la prochaine version majeure de HTML-Tree, je prévois qu'il utilise IO::HTML automatiquement. Si vous voulez vraiment que votre fichier soit ouvert en mode binaire, vous devriez l'ouvrir vous-même et passer le filehandle à "parse_file"

La valeur de retour est "undef" s'il y a une erreur lors de l'ouverture du fichier. Dans ce cas, l'erreur sera dans $!

gut

s 
@nodes = $root->guts();

;

En contexte liste (comme dans le premier cas), cette méthode retourne les nœuds non implicites les plus hauts dans un arbre. C'est utile quand vous analysez du code HTML que vous savez ne pas attendre un document HTML, mais plutôt juste un fragment d'un document HTML. Par exemple, si vous vouliez l'arbre d'analyse pour un fichier consistant juste en ceci

Alors vous l'obtiendriez avec "@nodes = $root->guts();". Il se trouve que dans ce cas, @nodes contiendra juste un objet élément, représentant le nœud "<li>" (avec "I like pie!" étant son nœud enfant texte). Cependant, considérez si vous analysiez ceci

Dans ce cas, "$root->guts()" retournerait trois éléments : un objet élément pour le premier "<hr>", une chaîne de texte "Hooboy!", et un autre objet élément "<hr>

Pour les cas où vous voulez définitivement un élément (pour que vous puissiez le traiter comme un "fragment de document", très grossièrement), appelez guts() en contexte scalairetexte, comme dans "$parent_for_nodes = $root->guts()". Cela fonctionne comme guts() en contexte liste ; en fait, guts() en contexte liste aurait retourné exactement une seule valeur, et si c'était un objet (par opposition à une chaîne de texte), alors c'est ce que "guts" en contexte scalaire retournera. Sinon, si guts() en contexte liste n'aurait retourné aucune valeur, alors guts() en contexte scalaire retourne undef. Dans tous les autres cas, guts() en contexte scalaire retourne implicitement un élément nœud "<div>", avec des enfants composés de tous les nœuds que guts() en contexte liste aurait retournés. Notez que cela peut détacher ces nœuds de l'arbre

HTML ET SES

MÉCONTENTS

L'HTML est plutôt plus difficile à analyser que ne le pensent généralement ceux qui

l'écrivent.

Voici le problème : l'HTML est un type de SGML qui permet la "minimisation" et l'"implication". En bref, cela signifie que vous n'avez pas besoin de fermer chaque balise que vous ouvrez (car l'ouverture d'une balise suivante peut implicitement la fermer), et si vous utilisez une balise qui ne peut pas survenir dans le contexte où vous semblez l'utiliser, dans certaines conditions l'analyseur pourra réaliser que vous voulez quitter le contexte actuel et entrer dans le nouveau, celui-ci étant le seul dans lequel votre code pourrait être correctement

interprété.

Maintenant, tout cela fonctionnerait de manière impeccable et sans problème si : 1) toutes les règles qui prescrivent et décrivent l'HTML étaient (et avaient été) clairement établies, et 2) tout le monde était conscient de ces règles et écrivait son code en conformité avec

elles.

Cependant, cela ne s'est pas passé de cette manière, et donc la plupart des pages HTML sont difficiles, voire impossibles, à analyser co

rrectement avec presque n'importe quel ensemble de règles SGML simples. C'est pourquoi les internes de HTML::TreeBuilder consistent
en beaucoup et beaucoup de cas particuliers -- au lieu d'être simplement un analyseur SGML générique avec les règles DTD HTML intégrées.

TRADUCTIONS

?

Les techniques que HTML::TreeBuilder utilise pour effectuer ce que je considère comme des analyses très robustes sur du code courant ne sont pas des choses qui ne peuvent fonctionner qu'en Perl. À ce jour, les algorithmes au centre de HTML::TreeBuilder ont été implémentés uniquement en Perl, autant que je sache ; et je ne prévois pas de m'y mettre pour les implémenter dans un autre langage dans un avenir

proche.

Si, cependant, quelqu'un cherche un projet de semestre pour un cours de programmation appliquée (ou s'il aime simplement le masochisme extra-scolaire), il ferait bien de considérer le choix comme sujet l'implémentation/adaptation de ces routines à tout autre langage de programmation intéressant qui, selon vous, souffre actuellement d'un manque d'analyse HTML robuste. Je suis ouvert à la correspondance sur ce sujet, et je fais remarquer que l'on peut apprendre énormément sur les langages en essayant de traduire entre eux, puis en comparant le

résultat.

La source de HTML::TreeBuilder peut sembler longue et complexe, mais elle est plutôt bien commentée, et les noms de symboles sont généralement auto-explicatifs. (Vous êtes encouragé à lire la source de l'analyseur HTML de Mozilla pour comparaison.) Une partie de la complexité provient de fonctionnalités peu utilisées, et une autre partie provient du fait que le tokeniseur HTML (HTML::Parser) soit un module séparé, nécessitant une interface quelque peu différente de celle que l'on trouverait dans un tokeniseur et constructeur d'arbre combiné. Mais la plupart de la longueur de la source vient du fait que c'est essentiellement une longue liste de cas particuliers, avec beaucoup et beaucoup de vérifications de cohérence, et de récupération de cohérence -- parce que, comme Roseanne Rosannadanna l'a dit un jour, "c'est toujours quelque ch

ose".

Les utilisateurs souhaitant comparer plusieurs analyseurs HTML devraient regarder la source de Tidy de Raggett ("http://www.w3.org/People/Raggett/tidy/"), Mozilla ("http://www.mozilla.org/"), et éventuellement fouiller dans la section des navigateurs de Yahoo pour trouver les divers navigateurs open-source ("http://dir.yahoo.com/Computers_and_Internet/Software/

Internet/World_Wid
e_Web/Browsers/").

* Un code HTML vraiment mauvais produira, souvent, un arbre d'analyse quelque peu répréhensible. Regrettable, mais inévitablement
