Description

détaillée

Les plateformes à mémoire hétérogène nécessitent des moyens de déterminer si un tampon doit être alloué sur une mémoire « rapide » (comme la HBM), une mémoire « normale » (DDR) ou même une mémoire « lente » mais de grande capacité (mémoire non volatile). Ces nœuds mémoire sont appelés « Cibles » (Targets), tandis que le CPU qui y accède est appelé l'« Initiateur » (Initiator). Les performances d'accès dépendent de leur localité (plateformes NUMA) ainsi que des performances intrinsèques des cibles (plateformes hétérogènes)

.

Les attributs suivants décrivent les performances des accès mémoire d'un Initiateur vers une Cible mémoire, par exemple leur latence ou leur bande passante. Les Initiateurs effectuant ces accès mémoire sont généralement des PU ou des Cœurs (décrits par un ensemble de CPU). Ainsi, un Cœur peut choisir où allouer un tampon mémoire en comparant les attributs de différents nœuds mémoire cibles à

proximité.

Il existe également des attributs qui sont valables pour tout le système. Leur valeur ne dépend pas d'un initiateur particulier effectuant un accès. La Capacité d'un nœud mémoire est un exemple d'attribut sans

initiateur.

Une façon d'utiliser cette API est de commencer par un cpuset décrivant les Cœurs auxquels un programme est lié. Le meilleur nœud NUMA cible pour allouer de la mémoire dans ce programme sur ces Cœurs peut être obtenu en passant ce cpuset comme initiateur à hwloc_memattr_get_best_target() avec l'attribut mémoire pertinent. Par exemple, si le code est limité par la latence, utilisez l'attribut

Latence.

Une approche plus flexible consiste à obtenir la liste des nœuds NUMA locaux en passant ce cpuset à hwloc_get_local_numanode_objs(). Les valeurs d'attributs pour ces nœuds, le cas échéant, peuvent ensuite être obtenues avec hwloc_memattr_get_value() et comparées manuellement avec les critères

souhaités.

Les attributs mémoire sont également utilisés en interne pour construire les Tiers Mémoire (Memory Tiers) qui fournissent un moyen simple de distinguer les nœuds NUMA de différentes sortes, comme expliqué dans Mémoire hétér

ogène.

En plus des tiers, hwloc définit un ensemble de nœuds « par défaut » à partir desquels les allocations mémoire normales doivent être effectuées (voir hwloc_topology_get_default_nodeset()). Cela est également utile pour diviser la machine en un ensemble de domaines NUMA non superposés, par exemple pour lier des tâches par

domaine.

aussi
Un exemple est disponible dans doc/examples/memory-attributes.c dans l'arborescence des

int hwloc_topology_get_default_nodeset (hwloc_topology_t topology, hwloc_nodeset_t nodeset, unsigned long

flags)

Retourne l'ensemble des nœuds NUMA par défaut. Sur les machines à mémoire hétérogène, certains nœuds NUMA sont considérés comme les nœuds par défaut, c'est-à-dire ceux à partir desquels les allocations de base doivent être faites. Ce sont généralement les nœuds DRAM

.

D'autres nœuds peuvent être réservés à un usage spécifique (mémoire de périphérique d'E/S, par exemple mémoire GPU), petits mais haute performance (HBM), grands mais lents (NVM), etc. Les tampons ne devraient généralement pas être alloués à partir de ceux-ci sauf si cela est explicitement

requis.

Cette fonction remplit nodeset avec les bits des nœuds NUMA considérés comme par

défaut.

Il est garanti que ces nœuds ont des ensembles de CPU non intersectants, c'est-à-dire que les cœurs ne peuvent plus avoir plusieurs nœuds NUMA locaux. Ainsi, cela peut être utilisé pour parcourir la plateforme divisée en localités NUMA distinctes, par exemple pour lier une tâche par domaine

NUMA.

Tout cœur qui avait des nœuds NUMA locaux dans la topologie initiale devrait toujours en avoir un dans le nœuds par défaut. Les cas particuliers où cela serait faux consistent en des plateformes asymétriques avec des nœuds DRAM manquants, ou des topologies qui ont déjà été restreintes à moins de nœuds

NUMA.

Le nœuds retourné peut être passé à hwloc_topology_restrict() avec HWLOC_RESTRICT_FLAG_BYNODESET pour supprimer tous les nœuds non par défaut de la topologie. La topologie résultante sera plus facile à utiliser lors du parcours des nœuds NUMA (désormais homogènes)

.

matériels.

HWLOC_LOCAL_NUMANODE_FLAG_LARGER_LOCALITY

This flag is not actually used by the core hwloc library. It is available for userspace applications or other libraries to extend the meaning of NUMA node locality flags for their own purposes.

NAME

HWLOC_LOCAL_NUMANODE_FLAG_LARGER_LOCALITY - Flag indicating larger NUMA node locality

SYNOPSIS

#define HWLOC_LOCAL_NUMANODE_FLAG_LARGER_LOCALITY

Detailed Description

The HWLOC_LOCAL_NUMANODE_FLAG_LARGER_LOCALITY flag is defined within the hwloc library but is not used internally by the library's core functions. Its purpose is to provide a reserved flag that userspace applications or other libraries can leverage to signify a specific type of NUMA node locality, particularly when indicating that a NUMA node has a "larger" locality compared to some baseline or other NUMA nodes.

This flag is intended for use in contexts where a more granular or application-specific interpretation of NUMA node locality is required than what the standard hwloc flags provide. For instance, an application might use this flag to denote a NUMA node that is closer to the CPU cores that are accessing it, or a node that has a higher degree of local memory access compared to other nodes.

When working with hwloc objects and their associated locality flags (e.g., using functions like hwloc_get_numanode_locality), developers can check for the presence of this flag to identify NUMA nodes that meet their custom criteria for "larger locality".
