DESCRIPTION

Ces fonctions initialisent une structure X509_STORE_CTX pour une utilisation ultérieure par X509_verify_cert(3) ou X509_STORE_CTX_verify(3).

X509_STORE_CTX_new_ex() renvoie une structure X509_STORE_CTX nouvellement initialisée associée au contexte de bibliothèque spécifié libctx et à la chaîne de requêtes de propriété propq. Tous les algorithmes cryptographiques récupérés lors du traitement avec le X509_STORE_CTX utiliseront ce contexte de bibliothèque et cette chaîne de requêtes de propriété.

X509_STORE_CTX_new() est identique à X509_STORE_CTX_new_ex(), sauf qu'il utilise le contexte de bibliothèque par défaut et une chaîne de requêtes de propriété NULL.

X509_STORE_CTX_cleanup() nettoie en interne une structure X509_STORE_CTX. Elle est utilisée par X509_STORE_CTX_init() et X509_STORE_CTX_free().

X509_STORE_CTX_free() libère complètement ctx. Après cet appel, ctx n'est plus valide. Si ctx est NULL, rien n'est fait.

X509_STORE_CTX_init() configure ctx pour une opération de vérification ultérieure.

X509_STORE_CTX_init() initialise l'état interne et les ressources du ctx donné. Entre autres, il définit les paramètres de vérification associés au nom de méthode "default", qui inclut le but "any", et reprend les pointeurs de fonction de rappel de trust_store (sauf si NULL). Il doit être appelé avant chaque appel à X509_verify_cert(3) ou X509_STORE_CTX_verify(3), c'est-à-dire qu'un contexte n'est valable que pour une seule vérification. Si vous souhaitez vérifier un certificat ou une chaîne supplémentaire avec le même ctx, vous devez rappeler X509_STORE_CTX_init(). Le magasin de certificats de confiance est défini sur trust_store de type X509_STORE. Celui-ci peut être NULL car il n'y a pas de certificats de confiance ou parce qu'ils sont fournis simplement comme une liste à l'aide de X509_STORE_CTX_set0_trusted_stack(). Le certificat à vérifier est défini sur target, et une liste de certificats supplémentaires peut être fournie dans untrusted, qui ne seront pas considérés comme fiables mais pourront être utilisés pour construire la chaîne. Le certificat target n'est pas copié (son compteur de références n'est pas mis à jour) et l'appelant ne doit pas le libérer avant que la vérification ne soit terminée. Chacun des paramètres trust_store, target et untrusted peut être NULL. Notez cependant que X509_verify_cert(3) et X509_STORE_CTX_verify(3) auront besoin d'une cible de vérification. Celle-ci peut également être définie à l'aide de X509_STORE_CTX_set_cert(). Pour X509_STORE_CTX_verify(3), qui prend par défaut le premier élément de la liste des certificats non fiables comme cible de vérification, cela peut également être défini indirectement à l'aide de X509_STORE_CTX_set0_untrusted().

X509_STORE_CTX_init_rpk() configure ctx pour une opération de vérification ultérieure pour la clé publique brute de target. Il se comporte de manière similaire à X509_STORE_CTX_init(). La clé publique brute target peut également être fournie séparément, via X509_STORE_CTX_set0_rpk(). La clé publique target n'est pas copiée (son compteur de références n'est pas mis à jour) et l'appelant ne doit pas la libérer avant que la vérification ne soit terminée.

X509_STORE_CTX_set0_trusted_stack() définit l'ensemble des certificats de confiance de ctx à sk. C'est une manière alternative de spécifier les certificats de confiance au lieu d'utiliser un X509_STORE lorsque sa complexité n'est pas nécessaire ou pour s'assurer que seul l'ensemble donné sk de certificats est considéré comme de confiance.

X509_STORE_CTX_set_cert() définit le certificat cible à vérifier dans ctx sur target. Le certificat cible n'est pas copié (son compteur de références n'est pas mis à jour) et l'appelant ne doit pas le libérer avant que la vérification ne soit terminée.

X509_STORE_CTX_set0_rpk() définit la clé publique brute cible à vérifier dans ctx sur target. Une clé publique brute non NULL préempte tout certificat cible, qui est alors ignoré. La clé publique target n'est pas copiée (son compteur de références n'est pas mis à jour) et l'appelant ne doit pas la libérer avant que la vérification ne soit terminée.

X509_STORE_CTX_set0_verified_chain() définit la chaîne validée sur chain. La propriété de la chaîne est transférée à ctx, et elle ne doit donc pas être libérée par l'appelant.

X509_STORE_CTX_get0_chain() renvoie le pointeur interne utilisé par ctx qui contient la chaîne construite (en sortie).

X509_STORE_CTX_get0_rpk() renvoie le pointeur interne utilisé par ctx qui contient la clé publique brute.

X509_STORE_CTX_set0_crls() définit un ensemble de CRLs à utiliser pour aider à la vérification du certificat sur sk. Ces CRLs ne seront utilisés que si la vérification des CRLs est activée dans la structure X509_VERIFY_PARAM associée. Cela peut être utilisé lorsque des CRLs "utiles" supplémentaires sont fournies dans le cadre d'un protocole, par exemple dans une structure PKCS#7.

X509_STORE_CTX_get0_param() récupère un pointeur interne vers les paramètres de vérification associés à ctx.

X509_STORE_CTX_set0_param() définit le pointeur interne des paramètres de vérification sur param. Après cet appel, param ne doit plus être utilisé.

X509_STORE_CTX_get0_untrusted() récupère un pointeur interne vers la pile de certificats non fiables associée à ctx.

DESCRIPTION

X509_STORE_CTX_new(), X509_STORE_CTX_new_ex(), X509_STORE_CTX_init(), X509_STORE_CTX_init_rpk(), X509_STORE_CTX_cleanup(), X509_STORE_CTX_free(), X509_STORE_CTX_get0_param(), X509_STORE_CTX_get0_verified_chain(), X509_STORE_CTX_get0_chain(), X509_STORE_CTX_set0_verified_chain(), X509_STORE_CTX_set_default(), X509_STORE_CTX_set_verify(), X509_STORE_CTX_set_ocsp_resp(), X509_STORE_CTX_set_purpose(), X509_STORE_CTX_set_trust(), X509_STORE_CTX_purpose_inherit(), X509_STORE_CTX_get0_rpk(), X509_STORE_CTX_set0_rpk(), X509_STORE_CTX_set0_param(), X509_STORE_CTX_set_cert(), X509_STORE_CTX_set0_trusted_stack(), X509_STORE_CTX_set0_crls(), X509_STORE_CTX_get_num_untrusted() all operate on the verification context.

A verification context X509_STORE_CTX holds all the information needed to perform a certificate chain verification. This includes the certificate to be verified, the trusted certificates, CRLs, and various other parameters that control the verification process.

X509_STORE_CTX_new() and X509_STORE_CTX_new_ex() allocate and initialize a new verification context. X509_STORE_CTX_new_ex() can be used to provide a custom memory allocator.

X509_STORE_CTX_init() initializes an existing verification context ctx. The certificate to be verified is passed in x509. The trusted certificates, CRLs, and other verification parameters are taken from the store. If x509 is NULL, then it is assumed that the certificate to be verified will be set later using X509_STORE_CTX_set_cert().

X509_STORE_CTX_init_rpk() initializes an existing verification context ctx using a resource public key (RPK) pkey. This is used for verifying certificates in environments without a traditional certificate chain, such as within TLS 1.3.

X509_STORE_CTX_cleanup() and X509_STORE_CTX_free() free up the verification context ctx. X509_STORE_CTX_cleanup() can be called to free up resources held by the context without freeing the context itself. X509_STORE_CTX_free() frees the context and all associated resources.

X509_STORE_CTX_get0_param() returns a pointer to the internal X509_VERIFY_PARAM structure used by the context. This structure holds parameters like the verification time, flags, purpose, trust, and depth limit.

X509_STORE_CTX_get0_rpk() returns a pointer to the RPK structure if it was set using X509_STORE_CTX_init_rpk() or X509_STORE_CTX_set0_rpk(), otherwise it returns NULL.

X509_STORE_CTX_set0_rpk() sets the RPK pkey in the context ctx. Ownership of the RPK is transferred to the context.

X509_STORE_CTX_set0_param() sets the verification parameters in the context ctx to be param. Ownership of param is transferred to ctx, and it should not be freed by the caller.

X509_STORE_CTX_set_cert() sets the certificate to be verified to x. This function is typically called after X509_STORE_CTX_init() if the certificate was not passed during initialization.

X509_STORE_CTX_set0_trusted_stack() sets the stack of trusted certificates to be used for verification. Ownership of the stack is transferred to ctx, and it should not be freed by the caller.

X509_STORE_CTX_set0_crls() sets the stack of CRLs to be used for verification. Ownership of the stack is transferred to ctx, and it should not be freed by the caller.

X509_STORE_CTX_get_num_untrusted() returns the number of untrusted certificates in the chain being verified.

X509_STORE_CTX_get0_verified_chain() returns the internal pointer used by the ctx that contains the validated chain. Note that the first chain element is the certificate itself. This does not count the first chain element.

X509_STORE_CTX_get0_chain() returns the internal pointer used by the ctx that contains the validated chain.

Details of the chain building and checking process are described in "Certification Path Building" in openssl-verification-options(1) and "Certification Path Validation" in openssl-verification-options(1).

X509_STORE_CTX_set0_verified_chain() sets the validated chain used by ctx to be chain. Ownership of the chain is transferred to ctx, and so it should not be free'd by the caller.

X509_STORE_CTX_set_default() looks up and sets the default verification method. This uses the function X509_VERIFY_PARAM_lookup() to find the set of parameters associated with the given verification method name. Among others, the parameters determine the trust model and verification purpose. More detail, including the list of currently predefined methods, is described for the -verify_name command-line option in "Verification Options" in openssl-verification-options(1).

X509_STORE_CTX_set_verify() provides the capability for overriding the default verify function. This function is responsible for verifying chain signatures and expiration times.

A verify function is defined as an X509_STORE_CTX_verify type which has the following signature:

int (*verify)(X509_STORE_CTX *);

This function should receive the current X509_STORE_CTX as a parameter and return 1 on success or 0 on failure.

X509 certificates may contain information about what purposes keys contained within them can be used for. For example "TLS WWW Server Authentication" or "Email Protection". This "key usage" information is held internally to the certificate itself. In addition the trust store containing trusted certificates can declare what purposes we trust different certificates for. This "trust" information is not held within the certificate itself but is "meta" information held alongside it. This "meta" information is associated with the certificate after it is issued and could be determined by a system administrator. For example a certificate might declare that it is suitable for use for both "TLS WWW Server Authentication" and "TLS Client Authentication", but a system administrator might only trust it for the former. An X.509 certificate extension exists that can record extended key usage information to supplement the purpose information described above. This extended mechanism is arbitrarily extensible and not well suited for a generic library API; applications that need to validate extended key usage information in certificates will need to define a custom "purpose" (see below) or supply a nondefault verification callback (X509_STORE_set_verify_cb_func(3)).

X509_STORE_CTX_set_ocsp_resp() sets the OCSP response(s) for the verification of a certificate chain or for including in the TLS handshake, when the client requests OCSP stapling. The stack of OCSP responses sk is not copied but just stored to the context. ctx holds a pointer to the stack, so the stack must outlive the ctx.

X509_STORE_CTX_set_purpose() sets the purpose for the target certificate being verified in the ctx. Built-in available values for the purpose argument are X509_PURPOSE_SSL_CLIENT, X509_PURPOSE_SSL_SERVER, X509_PURPOSE_NS_SSL_SERVER, X509_PURPOSE_SMIME_SIGN, X509_PURPOSE_SMIME_ENCRYPT, X509_PURPOSE_CRL_SIGN, X509_PURPOSE_ANY, X509_PURPOSE_OCSP_HELPER, X509_PURPOSE_TIMESTAMP_SIGN and X509_PURPOSE_CODE_SIGN. It is also possible to create a custom purpose value. Setting a purpose requests that the key usage and extended key usage (EKU) extensions optionally declared within the certificate and its chain are verified to be consistent with that purpose. For SSL client, SSL server, and S/MIME purposes, the EKU is checked also for the CA certificates along the chain, including any given trust anchor certificate. Potentially also further checks are done (depending on the purpose given). Every purpose also has an associated default trust value, which will also be set at the same time. During verification, this trust setting will be verified to check whether it is consistent with the trust set by the system administrator for certificates in the chain.

X509_STORE_CTX_set_trust() sets the trust value for the target certificate being verified in the ctx. Built-in available values for the trust argument are X509_TRUST_COMPAT, X509_TRUST_SSL_CLIENT, X509_TRUST_SSL_SERVER, X509_TRUST_EMAIL, X509_TRUST_OBJECT_SIGN, X509_TRUST_OCSP_SIGN, X509_TRUST_OCSP_REQUEST and X509_TRUST_TSA. It is also possible to create a custom trust value. Since X509_STORE_CTX_set_purpose() also sets the trust value it is normally sufficient to only call that function. If both are called then X509_STORE_CTX_set_trust() should be called after X509_STORE_CTX_set_purpose() since the trust setting of the last call will be used.

It should not normally be necessary for end user applications to call X509_STORE_CTX_purpose_inherit() directly. Typically applications should call X509_STORE_CTX_set_purpose() or X509_STORE_CTX_set_trust() instead. Using this function it is possible to set the purpose and trust values for the ctx at the same time. Both ctx and its internal verification parameter pointer must not be NULL. The def_purpose and purpose arguments can have the same purpose values as described for X509_STORE_CTX_set_purpose() above. The trust argument can have the same trust values as described in X509_STORE_CTX_set_trust() above. Any of the def_purpose, purpose or trust values may also have the value 0 to indicate that the supplied parameter should be ignored. After calling this function the purpose to be used for verification is set from the purpose argument unless the purpose was already set in ctx before, and the trust is set from the trust argument unless the trust was already set in ctx before. If trust is 0 then the trust value will be set from the default trust value for purpose. If the default trust value for the purpose is X509_TRUST_DEFAULT and trust is 0 then the default trust value associated with the def_purpose value is used for the trust setting instead.

NOTES

The certificates and CRLs in a store are used internally and should not be freed up until after the associated X509_STORE_CTX is freed.

BUGS

The certificates and CRLs in a context are used internally and should not be freed up until after the associated X509_STORE_CTX is freed. Copies should be made or reference counts increased instead.

RETURN VALUES

X509_STORE_CTX_new() returns a newly allocated context or NULL if an error occurred.

X509_STORE_CTX_init() and X509_STORE_CTX_init_rpk() return 1 for success or 0 if an error occurred.

X509_STORE_CTX_get0_param() returns a pointer to an X509_VERIFY_PARAM structure or NULL if an error occurred.

X509_STORE_CTX_get0_rpk() returns a pointer to an EVP_PKEY structure if present, or NULL if absent.

X509_STORE_CTX_cleanup(), X509_STORE_CTX_free(), X509_STORE_CTX_set0_trusted_stack(), X509_STORE_CTX_set_cert(), X509_STORE_CTX_set0_crls() and X509_STORE_CTX_set0_param() do not return values.

X509_STORE_CTX_set_default() returns 1 for success or 0 if an error occurred.

X509_STORE_CTX_get_num_untrusted() returns the number of untrusted certificates used.

X509_STORE_CTX *X509_STORE_CTX_new(void);

DESCRIPTION

X509_STORE_CTX_new() creates and initialises a new X509_STORE_CTX object. This object is used to hold the context for certificate verification operations.

The context typically includes the certificate chain to be verified, the list of trusted certificates (CA certificates), a set of options controlling the verification process, and a policy.

The created context is initially empty and needs to be populated using other functions, such as X509_STORE_CTX_init(), before being used for verification.

NOTES

The X509_STORE_CTX object should be freed using X509_STORE_CTX_free() when it is no longer needed.

BUGS

No bugs are known at present.

RETURN VALUES

X509_STORE_CTX_new() returns a pointer to the newly created X509_STORE_CTX object, or NULL if an error occurred during allocation.

DESCRIPTION

X509_STORE_CTX_new() crée et initialise un nouvel objet X509_STORE_CTX. Cet objet est utilisé pour contenir le contexte des opérations de vérification de certificat.

Le contexte comprend généralement la chaîne de certificats à vérifier, la liste des certificats de confiance (certificats d'autorité de certification), un ensemble d'options contrôlant le processus de vérification, et une politique.

Le contexte créé est initialement vide et doit être peuplé en utilisant d'autres fonctions, telles que X509_STORE_CTX_init(), avant d'être utilisé pour la vérification.

NOTES

L'objet X509_STORE_CTX doit être libéré à l'aide de X509_STORE_CTX_free() lorsqu'il n'est plus nécessaire.

Aucun bogues connus à l'heure actuelle.

X509_STORE_CTX_new() retourne un pointeur vers le nouvellement créé objet X509_STORE_CTX, ou NULL si une erreur s'est produite lors de l'allocation.
