NOM

XkbApplyCompatMapToKey - Applique la nouvelle configuration de compatibilité à une touche individuelle pour mettre à jour sa sémantique

SYNOPSIS

Bool XkbApplyCompatMapToKey (XkbDescPtr xkb, KeyCode key, XkbChangesPtr changes);

ARGUMENTS

xkb
description du clavier à mettre à jour
key
touche à mettre à jour
changes
note les modifications apportées à la description du clavier Xkb

DESCRIPTION

XkbApplyCompatMapToKey effectue essentiellement l'opération décrite dans la Transformation du Mappage Clavier Principal vers le Mappage Clavier Xkb sur une touche spécifique. Ceci met à jour le comportement, les actions, le statut de répétition et les liaisons de modificateurs virtuels de la touche.

Transformation du Mappage Clavier Principal vers le Mappage Clavier Xkb

Lorsqu'une requête de mappage clavier du protocole principal est reçue par le serveur, la carte clavier principale du serveur est mise à jour, puis la carte Xkb maintenue par le serveur est mise à jour. Étant donné qu'un client peut avoir explicitement configuré une partie du mappage clavier Xkb sur le serveur, cette régénération automatique du mappage clavier Xkb à partir du mappage clavier du protocole principal ne doit pas modifier les composants du mappage clavier Xkb qui ont été explicitement définis par un client. Le client doit définir des contrôles de substitution explicites pour empêcher cela (voir Composants Explicites - Éviter le Remappage Automatique par le Serveur). Le mappage principal vers Xkb est effectué comme suit :

Composants Explicites - Éviter le Remappage Automatique par le Serveur

Chaque fois qu'un client remappe le clavier en utilisant des requêtes du protocole principal, Xkb examine la carte pour déterminer les valeurs par défaut probables pour les composants qui ne peuvent pas être spécifiés à l'aide du protocole principal.

Ce remappage automatique pourrait remplacer les définitions explicitement demandées par une application, donc la description du clavier Xkb définit un masque de composants explicites pour chaque touche. Les aspects du remappage automatique listés dans le masque de composants explicites pour une touche ne sont pas modifiés par le mappage clavier automatique.

Les masques de composants explicites sont conservés dans le champ explicit de la carte serveur, qui est un tableau indexé par keycode. Chaque entrée de ce tableau est un masque qui est un OU inclusif bit à bit des valeurs indiquées dans le Tableau 1.

Tableau 1 Masques de Composants Explicites
Bit dans le Masque Explicite Valeur Protège contre
ExplicitKeyType1 (1<<0) Détermination automatique du type de touche associé au Groupe 1.
ExplicitKeyType2 (1<<1) Détermination automatique du type de touche associé au Groupe 2.
ExplicitKeyType3 (1<<2) Détermination automatique du type de touche associé au Groupe 3.
ExplicitKeyType4 (1<<3) Détermination automatique du type de touche associé au Groupe 4.
ExplicitInterpret (1<<4) Application de l'un des champs d'une interprétation de symbole à la touche concernée.
ExplicitAutoRepeat (1<<5) Détermination automatique du statut de répétition automatique pour la touche, comme spécifié dans une interprétation de symbole.
ExplicitBehavior (1<<6) Assignation automatique du comportement XkbKB_Lock à la touche, si le drapeau XkbSI_LockingKey est défini dans une interprétation de symbole.
ExplicitVModMap (1<<7) Détermination automatique de la carte de modificateurs virtuels pour la touche basée sur les actions assignées à la touche et les interprétations de symboles qui correspondent à la touche.
1.
Mapper les symboles des touches de la carte clavier principale vers les groupes et les symboles sur les touches de la carte clavier Xkb. Le mappage clavier principal a une largeur fixe, donc chaque touche du mappage principal a le même nombre de symboles qui lui est associé. La carte Xkb permet d'associer un nombre différent de symboles à chaque touche ; ces symboles peuvent être divisés en un nombre différent de groupes (1-4) pour chaque touche. Pour chaque touche, ce processus implique donc de partitionner le nombre fixe de symboles du mappage principal en un ensemble de groupes de longueur variable avec un nombre variable de symboles dans chaque groupe. Par exemple, si la carte du protocole principal a une largeur de cinq, la partition pour une touche pourrait résulter en un groupe avec deux symboles et un autre avec trois symboles. Une autre touche pourrait résulter en deux groupes de deux symboles plus un troisième groupe d'un symbole. La carte du protocole principal nécessite au moins deux symboles dans chacun des deux premiers groupes.
1a.
Pour chaque touche modifiée, déterminer le nombre de groupes représentés dans la nouvelle carte clavier principale. Ceci résulte en un décompte de groupes provisoire pour chaque touche de la carte Xkb.
1b.
Pour chaque touche modifiée, déterminer le nombre de symboles dans chacun des groupes trouvés à l'étape 1a. Il y a un contrôle de substitution explicite associé à chacun des quatre groupes possibles pour chaque touche Xkb, ExplicitKeyType1 à ExplicitKeyType4. Si aucun contrôle de substitution explicite n'est défini pour un groupe, le nombre de symboles utilisés pour ce groupe à partir de la carte principale est deux. Si le contrôle de substitution explicite est défini pour un groupe sur la touche, le nombre de symboles utilisés pour ce groupe Xkb à partir de la carte principale est la largeur du groupe Xkb, à une exception près : en raison de l'exigence du protocole principal d'au moins deux symboles dans les groupes un et deux, le nombre de symboles utilisés pour les groupes un et deux est le maximum de 2 ou la largeur du groupe Xkb.
1c.
Pour chaque touche modifiée, assigner les symboles de la carte principale au groupe approprié sur la touche. Si le nombre total de symboles requis par la carte Xkb pour une touche particulière nécessite plus de symboles que n'en contient la carte du protocole principal, les symboles supplémentaires sont considérés comme des keysyms NoSymbol ajoutés à la fin de l'ensemble principal. Si la carte principale contient plus de symboles que ce qui est nécessaire par la carte Xkb, les symboles de fin de la carte principale sont rejetés. En l'absence de substitution explicite pour le groupe un ou deux, les symboles sont assignés par ordre par groupe ; les premiers symboles de la carte principale sont assignés au groupe un, dans l'ordre, suivis du groupe deux, et ainsi de suite. Par exemple, si la carte principale contenait huit symboles par touche, et qu'une carte Xkb particulière contenait 2 symboles pour G1 et G2 et trois pour G3, les symboles seraient assignés comme suit (G est groupe, L est niveau de décalage) : 
              G1L1 G1L2 G2L1 G2L2 G3L1 G3L2 G3L3
Si une substitution explicite est définie pour le groupe un ou deux, les symboles sont pris de l'ensemble principal dans un ordre légèrement différent. Les quatre premiers symboles de l'ensemble principal sont assignés respectivement à G1L1, G1L2, G2L1, G2L2. Si le groupe un nécessite plus de symboles, ils sont pris ensuite, puis tout symbole supplémentaire requis par le groupe deux. Les symboles des groupes trois et quatre sont pris séquentiellement après le groupe deux. Par exemple, une touche avec quatre groupes et trois symboles dans chaque groupe prendrait les symboles de l'ensemble principal dans l'ordre suivant : 
   G1L1 G1L2 G2L1 G2L2 G1L3 G2L3 G3L1 G3L2 G3L3 G4L1 G4L2 G4L3
Comme mentionné précédemment, la carte du protocole principal nécessite au moins deux symboles dans les groupes un et deux. Pour cette raison, si une substitution explicite pour une touche Xkb est définie et que le groupe un et/ou deux est de largeur un, il n'est pas possible de générer les symboles pris de l'ensemble du protocole principal et assignés aux positions G1L2 et/ou G2L2.
1d.
Pour chaque groupe sur chaque touche modifiée, assigner un type de touche approprié pour les symboles du groupe.
1e.
Pour chaque touche modifiée, supprimer les groupes vides ou redondants.

À ce stade, les groupes et leurs symboles associés ont été assignés aux définitions de touche correspondantes dans la carte Xkb.

2.
Appliquer les interprétations de symboles pour modifier le fonctionnement de la touche. Cette phase est complètement ignorée si le bit de contrôle de substitution ExplicitInterpret est défini dans le masque des contrôles explicites pour la touche Xkb (voir Composants Explicites - Éviter le Remappage Automatique par le Serveur).
2a.

NOM

XkbApplyCompatMapToKey — applique une carte de compatibilité à une clé

SYNTAXE

#include <X11/extensions/XkbCompst.h>
void XkbApplyCompatMapToKey(Display *display,
    XkbKeyAction **key_actions, XkbSymInterpretPtr sym_interpret,
    XkbKeyNameRec *key_name, int device_spec);

ARGUMENTS

o display
Spécifie la connexion au serveur X.
o key_actions
Pointeur vers la structure des actions de clé à modifier.
o sym_interpret
Pointeur vers une structure XkbSymInterpretRec qui décrit une interprétation de symbole.
o key_name
Pointeur vers la structure XkbKeyNameRec pour la clé cible.
o device_spec
Spécifie le périphérique d'entrée.

DESCRIPTION

La fonction XkbApplyCompatMapToKey est utilisée pour appliquer les modifications d'une carte de compatibilité Xkb à une clé spécifique. Les cartes de compatibilité Xkb définissent comment les symboles (keysyms) sur une clé doivent être interprétés par le serveur X pour modifier le comportement de la clé.

Le processus d'application d'une carte de compatibilité à une clé implique généralement les étapes suivantes :

2a.
Localiser l'interprétation de symbole appropriée. Le serveur X recherche dans la carte de compatibilité actuelle une entrée qui correspond aux critères spécifiés par le symbole de la clé, les modificateurs actifs et le groupe sélectionné. Si une correspondance est trouvée, l'interprétation de symbole associée est utilisée. Sinon, une interprétation par défaut est appliquée.
2b.
Lorsque une correspondance est trouvée à l'étape 2a, appliquer l'interprétation du symbole pour modifier la sémantique associée au symbole dans la carte de clavier Xkb. Si aucune correspondance n'est trouvée, appliquer une interprétation par défaut.

Les interprétations de symboles utilisées à l'étape 2 sont configurables et peuvent être spécifiées à l'aide de structures XkbSymInterpretRec référencées par le champ sym_interpret d'une structure XkbCompatMapRec.

Interprétations de symboles - la structure XkbSymInterpretRec

Les interprétations de symboles sont utilisées pour guider le serveur X lorsqu'il modifie la carte de clavier Xkb à l'étape 2. Un ensemble initial d'interprétations de symboles est chargé par le serveur lors de son démarrage. Un client peut en ajouter de nouvelles à l'aide de XkbSetCompatMap.

Les interprétations de symboles entraînent la définition de sémantiques de clé. Lorsqu'une interprétation de symbole est appliquée, les composants suivants du traitement des événements clavier par le serveur peuvent être modifiés pour la clé particulière impliquée :

    Carte des modificateurs virtuels
    Répétition automatique
    Comportement de la clé (peut être défini sur XkbKB_Lock)
    Action de la clé
La structure XkbSymInterpretRec spécifie une interprétation de symbole : 
typedef struct {
    KeySym        sym;         /* keysym d'intérêt ou NULL */
    unsigned char flags;       /* XkbSI_AutoRepeat, XkbSI_LockingKey */
    unsigned char match;       /* spécifie comment les mods sont interprétés */
    unsigned char mods;        /* bits de modificateurs, correspondent à huit vrais modificateurs */
    unsigned char virtual_mod; /* 1 modificateur à ajouter à la carte des modificateurs virtuels de la clé */
    XkbAnyAction  act;         /* action à lier à la position du symbole sur la clé */
} XkbSymInterpretRec,*XkbSymInterpretPtr;
Si sym n'est pas NULL, il limite l'interprétation du symbole aux clés sur lesquelles ce keysym particulier est sélectionné par les modificateurs correspondant aux critères spécifiés par mods et match. Si sym est NULL, l'interprétation peut être appliquée à tout symbole sélectionné sur une clé lorsque les modificateurs correspondent aux critères spécifiés par mods et match.

match doit être l'une des valeurs indiquées dans le Tableau 2 et spécifie comment les vrais modificateurs spécifiés dans mods doivent être interprétés.

Tableau 2 Critères de correspondance des interprétations de symboles
Critères de correspondance Valeur Effet
XkbSI_NoneOf (0) Aucun des bits activés dans mods ne peut être activé, mais d'autres bits le peuvent.
XkbSI_AnyOfOrNone (1) Zéro ou plus des bits activés dans mods peuvent être activés, ainsi que d'autres.
XkbSI_AnyOf (2) Un ou plusieurs des bits activés dans mods peuvent être activés, ainsi que d'autres.
XkbSI_AllOf (3) Tous les bits activés dans mods doivent être activés, mais d'autres peuvent l'être également.
XkbSI_Exactly (4) Tous les bits activés dans mods doivent être activés, et aucun autre bit ne peut l'être.

En plus des bits ci-dessus, match peut contenir le bit XkbSI_LevelOneOnly, auquel cas les critères de correspondance des modificateurs spécifiés par mods et match ne s'appliquent que si sym est au niveau un de son groupe ; sinon, mods et match sont ignorés et le symbole correspond à une condition où aucun modificateur n'est défini.

#define XkbSI_LevelOneOnly  (0x80)  /* utiliser mods + match uniquement si sym est au niveau 1 */
Si aucune interprétation de symbole correspondante n'est trouvée, le serveur utilise une interprétation par défaut où : 
    sym =           0
    flags =         XkbSI_AutoRepeat
    match =         XkbSI_AnyOfOrNone
    mods =          0
    virtual_mod =   XkbNoModifier
    act =           SA_NoAction
Lorsqu'une interprétation de symbole correspondante est trouvée à l'étape 2a, l'interprétation est appliquée pour modifier la carte Xkb comme suit.

Le champ act spécifie une action unique à lier à la position du symbole ; tout événement clavier qui sélectionne le symbole déclenche l'action.

Si la carte de clavier Xkb pour la clé n'a pas son contrôle ExplicitVModMap défini, le bit XkbSI_LevelOneOnly et la position du symbole sont examinés. Si le bit XkbSI_LevelOneOnly n'est pas défini dans match ou si le symbole est dans la position G1L1, le champ virtual_mod est examiné. Si virtual_mod n'est pas XkbNoModifier, virtual_mod spécifie un seul modificateur virtuel à ajouter à la carte des modificateurs virtuels pour la clé. virtual_mod est spécifié comme un index dans la plage [0..15].

Si le symbole correspondant est dans la position G1L1 de la clé, deux bits dans le champ flags spécifient potentiellement des modifications de comportement supplémentaires :

#define  XkbSI_AutoRepeat  (1<<0)  /* la clé se répète si sym est en position G1L1 */
#define  XkbSI_LockingKey  (1<<1)  /* définit le comportement KB_Lock si sym est en psn G1L1 */
Si la carte de clavier Xkb pour la clé n'a pas son contrôle ExplicitAutoRepeat défini, son comportement de répétition automatique est défini en fonction de la valeur du bit XkbSI_AutoRepeat. Si le bit XkbSI_AutoRepeat est défini, le comportement de répétition automatique de la clé est activé ; sinon, il est désactivé.

Si la carte de clavier Xkb pour la clé n'a pas son contrôle ExplicitBehavior défini, son comportement de blocage est défini en fonction de la valeur du bit XkbSI_LockingKey. Si XkbSI_LockingKey est défini, le comportement de la clé est défini sur KB_Lock ; sinon, il est désactivé.
