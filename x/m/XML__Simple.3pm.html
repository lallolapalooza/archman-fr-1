NOM

XML::Simple - Une API pour les fichiers XML simples

SYNOPIS

VEUILLEZ NE PAS UTILISER CE MODULE DANS DE NOUVEAU CODE. Si vous ignorez cet avertissement et l'utilisez quand même, le mode qw(:strict) vous épargnera un peu de douleur.

use XML::Simple qw(:strict);
my $ref = XMLin([<fichier xml ou chaîne>] [, <options>]);
my $xml = XMLout($hashref [, <options>]);

Ou la manière orientée objet :

require XML::Simple qw(:strict);
my $xs = XML::Simple->new([<options>]);
my $ref = $xs->XMLin([<fichier xml ou chaîne>] [, <options>]);
my $xml = $xs->XMLout($hashref [, <options>]);

(ou voir "SUPPORT SAX" pour 'la manière SAX').

Note, dans ces exemples, les crochets sont utilisés pour dénoter les éléments optionnels et non pour impliquer que des éléments doivent être fournis dans des tableaux références.

STATUT DE CE MODULE

L'utilisation de ce module dans du nouveau code est fortement déconseillée. D'autres modules sont disponibles et fournissent des interfaces plus simples et cohérentes. En particulier, XML::LibXML est fortement recommandé et vous pouvez vous référer à Perl XML::LibXML by Example http://grantm.github.io/perl-libxml-by-example/ pour une introduction tutorielle.

XML::Twig est une autre excellente alternative.

Les principaux problèmes avec ce module sont le grand nombre d'options (dont certaines ont des valeurs par défaut malheureuses) et les interactions arbitraires entre ces options, produisant souvent des résultats inattendus.

Les patchs avec des corrections de bugs et des corrections de documentation sont les bienvenus, mais il est peu probable que de nouvelles fonctionnalités soient ajoutées.

DÉMARRAGE RAPIDE

Supposons que vous ayez un script appelé foo et un fichier d'options de configuration appelé foo.xml contenant ce qui suit :

<config logdir="/var/log/foo/" debugfile="/tmp/foo.debug">
  <server name="sahara" osname="solaris" osversion="2.6">
    <address>10.0.0.101</address>
    <address>10.0.1.101</address>
  </server>
  <server name="gobi" osname="irix" osversion="6.5">
    <address>10.0.0.102</address>
  </server>
  <server name="kalahari" osname="linux" osversion="2.0.34">
    <address>10.0.0.103</address>
    <address>10.0.1.103</address>
  </server>
</config>

Les lignes de code suivantes dans foo :

use XML::Simple qw(:strict);
my $config = XMLin(undef, KeyAttr => { server => 'name' }, ForceArray => [ 'server', 'address' ]);

vont 'absorber' les options de configuration dans le hashref $config (puisqu'aucun nom de fichier ou chaîne XML n'a été passé comme premier argument à XMLin(), le nom et l'emplacement du fichier XML seront déduits du nom et de l'emplacement du script). Vous pouvez afficher le contenu du hashref en utilisant Data::Dumper :

use Data::Dumper;
print Dumper($config);

ce qui produira quelque chose comme ceci (la mise en forme a été ajustée pour plus de brièveté) :

{
    'logdir'        => '/var/log/foo/',
    'debugfile'     => '/tmp/foo.debug',
    'server'        => {
        'sahara'        => {
            'osversion'     => '2.6',
            'osname'        => 'solaris',
            'address'       => [ '10.0.0.101', '10.0.1.101' ]
        },
        'gobi'          => {
            'osversion'     => '6.5',
            'osname'        => 'irix',
            'address'       => [ '10.0.0.102' ]
        },
        'kalahari'      => {
            'osversion'     => '2.0.34',
            'osname'        => 'linux',
            'address'       => [ '10.0.0.103', '10.0.1.103' ]
        }
    }
}

Votre script pourrait alors accéder au nom du répertoire de logs comme ceci :

print $config->{logdir};

similairement, la deuxième adresse du serveur 'kalahari' pourrait être référencée comme :

print $config->{server}->{kalahari}->{address}->[1];

Note : Si la correspondance entre la sortie de Data::Dumper et les instructions d'impression ci-dessus n'est pas évidente pour vous, veuillez vous référer au tutoriel sur les 'références' (aussi connu sous le nom : "la très courte introduction aux références de Mark") à perlreftut.

Dans cet exemple, l'option "ForceArray" a été utilisée pour lister les éléments qui peuvent apparaître plusieurs fois et doivent donc être représentés comme des tableaux références (même lorsqu'un seul élément est présent).

L'option "KeyAttr" a été utilisée pour indiquer que chaque élément "<server>" possède un identifiant unique dans l'attribut "name". Cela vous permet d'indexer directement un enregistrement de serveur particulier en utilisant le nom comme clé de hachage (comme montré ci-dessus).

Pour des besoins simples, c'est tout ce qu'il y a à savoir. Si vous souhaitez stocker votre XML dans un répertoire ou un fichier différent, ou le passer sous forme de chaîne, ou même le passer via un dérivé d'IO::Handle, vous devrez consulter les "OPTIONS". Si vous souhaitez désactiver ou ajuster la fonctionnalité de pliage de tableaux (cette transformation intéressante qui a produit $config->{server}), vous y trouverez également des options.

Si vous souhaitez générer du XML (par exemple pour écrire une version modifiée de $config en XML), consultez XMLout().

Si vos besoins ne sont pas si simples, ce n'est peut-être pas le module qu'il vous faut. Dans ce cas, vous pourriez vouloir lire "OÙ ALLER À PARTIR D'ICI ?".

DESCRIPTION

Le module XML::Simple fournit une couche d'API simple au-dessus d'un module d'analyse XML sous-jacent (soit XML::Parser, soit l'un des modules d'analyse SAX2). Deux fonctions sont exportées : XMLin() et XMLout(). Note : vous pouvez explicitement demander les versions en minuscules des noms de fonctions : xml_in() et xml_out().

L'approche la plus simple consiste à appeler directement ces deux fonctions, mais une interface orientée objet optionnelle (voir "INTERFACE OO OPTIONNELLE" ci-dessous) permet de les appeler comme méthodes d'un objet XML::Simple. L'interface objet peut également être utilisée à l'une ou l'autre extrémité d'un pipeline SAX.

XMLin()

Analyse les données au format XML et retourne une référence à une structure de données qui contient les mêmes informations sous une forme plus facilement accessible. (Sautez vers "EXEMPLES" ci-dessous pour plus d'exemples de code).

XMLin() accepte un spécificateur XML optionnel suivi de zéro ou plusieurs paires d'options 'nom => valeur'. Le spécificateur XML peut être l'un des éléments suivants :

Un nom de fichier
Si le nom de fichier ne contient pas de composantes de répertoire, XMLin() recherchera le fichier dans chaque répertoire du chemin de recherche (voir "OPTIONS" ci-dessous) ou dans le répertoire courant si l'option SearchPath n'est pas définie. Par exemple : 
$ref = XMLin('/etc/params.xml');

Notez que le nom de fichier '-' peut être utilisé pour analyser à partir de STDIN.

undef
S'il n'y a pas de spécificateur XML, XMLin() vérifiera le répertoire du script et chacun des répertoires SearchPath pour un fichier portant le même nom que le script mais avec l'extension '.xml'. Note : si vous souhaitez spécifier des options, vous devez spécifier la valeur 'undef'. Par exemple : 
$ref = XMLin(undef, ForceArray => 1);
Une chaîne XML
Une chaîne contenant du XML (reconnue par la présence des caractères '<' et '>') sera analysée directement. Par exemple : 
$ref = XMLin('<opt username="bob" password="flurp" />');
Un objet IO::Handle
Un objet IO::Handle sera lu jusqu'à EOF et son contenu sera analysé. Par exemple : 
$fh = IO::File->new('/etc/params.xml');
$ref = XMLin($fh);

XMLout()

Prend une structure de données (généralement un hashref) et retourne un encodage XML de cette structure. Si le XML résultant est analysé à l'aide de XMLin(), il devrait retourner une structure de données équivalente à l'original (voir les mises en garde ci-dessous).

La fonction XMLout() peut également être utilisée pour sortir

SAX SUPPORT

If you wish to use XML::Simple as a SAX driver, you should investigate the SAX() method. When XML::Simple is used this way, it will convert the SAX events to XML as they arrive and pass them to the XMLout() method (see the "Handler" option and "SAX SUPPORT" for more details).

When translating hashes to XML, hash keys which have a leading '-' will be silently skipped. This is the approved method for marking elements of a data structure which should be ignored by XMLout. (Note: If these items were not skipped the key names would be emitted as element or attribute names with a leading '-' which would not be valid XML).

Caveats

Some care is required in creating data structures which will be passed to XMLout(). Hash keys from the data structure will be encoded as either XML element names or attribute names. Therefore, you should use hash key names which conform to the relatively strict XML naming rules:

Names in XML must begin with a letter. The remaining characters may be letters, digits, hyphens (-), underscores (_) or full stops (.). It is also allowable to include one colon (:) in an element name but this should only be used when working with namespaces (XML::Simple can only usefully work with namespaces when teamed with a SAX Parser).

You can use other punctuation characters in hash values (just not in hash keys) however XML::Simple does not support dumping binary data.

If you break these rules, the current implementation of XMLout() will simply emit non-compliant XML which will be rejected if you try to read it back in. (A later version of XML::Simple might take a more proactive approach).

Note also that although you can nest hashes and arrays to arbitrary levels, circular data structures are not supported and will cause XMLout() to die.

If you wish to 'round-trip' arbitrary data structures from Perl to XML and back to Perl, then you should probably disable array folding (using the KeyAttr option) both with XMLout() and with XMLin(). If you still don't get the expected results, you may prefer to use XML::Dumper which is designed for exactly that purpose.

Refer to "WHERE TO FROM HERE?" if XMLout() is too simple for your needs.

OPTIONS

XML::Simple supports a number of options (in fact as each release of XML::Simple adds more options, the module's claim to the name 'Simple' becomes increasingly tenuous). If you find yourself repeatedly having to specify the same options, you might like to investigate "OPTIONAL OO INTERFACE" below.

If you can't be bothered reading the documentation, refer to "STRICT MODE" to automatically catch common mistakes.

Because there are so many options, it's hard for new users to know which ones are important, so here are the two you really need to know about:

  • check out "ForceArray" because you'll almost certainly want to turn it on
  • make sure you know what the "KeyAttr" option does and what its default value is because it may surprise you otherwise (note in particular that 'KeyAttr' affects both "XMLin" and "XMLout")

The option name headings below have a trailing 'comment' - a hash followed by two pieces of metadata:

  • Options are marked with 'in' if they are recognised by XMLin() and 'out' if they are recognised by XMLout().
  • Each option is also flagged to indicate whether it is: 
    'important'   - don't use the module until you understand this one
'handy'       - you can skip this on the first time through
'advanced'    - you can skip this on the second time through
'SAX only'    - don't worry about this unless you're using SAX (or
                alternatively if you need this, you also need SAX)
'seldom used' - you'll probably never use this unless you were the
                person that requested the feature

The options are listed alphabetically:

Note: option names are no longer case sensitive so you can use the mixed case versions shown here; all lower case as required by versions 2.03 and earlier; or you can add underscores between the words (eg: key_attr).

AttrIndent => 1 # out - handy

When you are using XMLout(), enable this option to have attributes printed one-per-line with sensible indentation rather than all on one line.

Cache => [ cache schemes ] # in - advanced

Because loading the XML::Parser module and parsing an XML file can consume a significant number of CPU cycles, it is often desirable to cache the output of XMLin() for later reuse.

When parsing from a named file, XML::Simple supports a number of caching schemes. The 'Cache' option may be used to specify one or more schemes (using an anonymous array). Each scheme will be tried in turn in the hope of finding a cached pre-parsed representation of the XML file. If no cached copy is found, the file will be parsed and the first cache scheme in the list will be used to save a copy of the results. The following cache schemes have been implemented:

storable
Utilises Storable.pm to read/write a cache file with the same name as the XML file but with the extension .stor
memshare
When a file is first parsed, a copy of the resulting data structure is retained in memory in the XML::Simple module's namespace. Subsequent calls to parse the same file will return a reference to this structure. This cached version will persist only for the life of the Perl interpreter (which in the case of mod_perl for example, may be some significant time).

Because each caller receives a reference to the same data structure, a change made by one caller will be visible to all. For this reason, the reference returned should be treated as read-only.

memcopy
This scheme works identically to 'memshare' (above) except that each caller receives a reference to a new data structure which is a copy of the cached version. Copying the data structure will add a little processing overhead, therefore this scheme should only be used where the caller intends to modify the data structure (or wishes to protect itself from others who might). This scheme uses Storable.pm to perform the copy.

Warning! The memory-based caching schemes compare the timestamp on the file to the time when it was last parsed. If the file is stored on an NFS filesystem (or other network share) and the clock on the file server is not exactly synchronised with the clock where your script is run, updates to the source XML file may appear to be ignored.

ContentKey => 'keyname' # in+out - seldom used

When text content is parsed to a hash value, this option lets you specify a name for the hash key to override the default 'content'. So for example:

XMLin('<opt one="1">Text</opt>', ContentKey => 'text')

will parse to:

{ 'one' => 1, 'text' => 'Text' }

instead of:

{ 'one' => 1, 'content' => 'Text' }

XMLout() will also honour the value of this option when converting a hashref to XML.

You can also prefix your selected key name with a '-' character to have XMLin() try a little harder to eliminate unnecessary 'content' keys after array folding. For example:

XMLin(
  '<opt><item name="one">First</item><item name="two">Second</item></opt>',
  KeyAttr => {item => 'name'},
  ForceArray => [ 'item' ],
  ContentKey => '-content'
)

will parse to:

{
  'item' => {
    'one' =>  'First'
    'two' =>  'Second'
  }
}

rather than this (without the '-'):

{
  'item' => {
    'one' => { 'content' => 'First' }
    'two' => { 'content' => 'Second' }
  }
}

DataHandler => code_ref # in - SAX only

When you use an XML::Simple object as a SAX handler, it will return a 'simple tree' data structure in the same format as XMLin() would return. If this option is set (to a subroutine reference), then when the tree is built the subroutine will be called and passed two arguments: a reference to the XML::Simple object and a reference to the data tree. The return value from the subroutine will be returned to the SAX driver. (See "SAX SUPPORT" for more details).

ForceArray => 1 # in - important

This option should be set to '1' to force nested elements to be represented as arrays even when there is only one. Eg, with ForceArray enabled, this XML:

<opt>
  <name>value</name>
</opt>

would parse to this:

{
  'name' => [
              'value'
            ]
}

instead of this (the default):

{
  'name' => 'value'
}

This option is especially useful if the data structure is likely to be written back out as XML and the default behaviour of rolling single nested elements up into attributes is not desirable.

ForceArray => [ noms ] # in - important

Cette forme alternative (et préférée) de l'option 'ForceArray' vous permet de spécifier une liste de noms d'éléments qui doivent toujours être forcés dans une représentation de tableau, plutôt que l'approche "tout ou rien" ci-dessus.

Il est également possible (depuis la version 2.05) d'inclure des expressions régulières compilées dans la liste - tous les noms d'éléments qui correspondent au modèle seront forcés en tableaux. Si la liste ne contient qu'une seule regex, il n'est pas nécessaire de l'envelopper dans un 'arrayref'. Par exemple :

ForceArray => qr/_list$/

ForceContent => 1 # in - rarement utilisé

Lorsque XMLin() analyse des éléments qui ont un contenu textuel ainsi que des attributs, le contenu textuel doit être représenté comme une valeur de hachage plutôt qu'un simple scalaire. Cette option vous permet de forcer le contenu textuel à être toujours analysé en valeur de hachage, même lorsqu'il n'y a pas d'attributs. Donc, par exemple :

XMLin('<opt><x>text1</x><y a="2">text2</y></opt>', ForceContent => 1)

sera analysé en :

{
  'x' => {           'content' => 'text1' },
  'y' => { 'a' => 2, 'content' => 'text2' }
}

au lieu de :

{
  'x' => 'text1',
  'y' => { 'a' => 2, 'content' => 'text2' }
}

GroupTags => { étiquette de regroupement => étiquette regroupée } # in+out - pratique

Vous pouvez utiliser cette option pour éliminer les niveaux d'indirection supplémentaires dans votre structure de données Perl. Par exemple, ce XML :

 <opt>
  <searchpath>
    <dir>/usr/bin</dir>
    <dir>/usr/local/bin</dir>
    <dir>/usr/X11/bin</dir>
  </searchpath>
</opt>

serait normalement lu dans une structure comme celle-ci :

{
  searchpath => {
                  dir => [ '/usr/bin', '/usr/local/bin', '/usr/X11/bin' ]
                }
}

Mais lorsqu'il est lu avec la valeur appropriée pour 'GroupTags' :

my $opt = XMLin($xml, GroupTags => { searchpath => 'dir' });

Il retournera cette structure plus simple :

{
  searchpath => [ '/usr/bin', '/usr/local/bin', '/usr/X11/bin' ]
}

L'élément de regroupement ("<searchpath>" dans l'exemple) ne doit contenir aucun attribut ni élément autre que l'élément regroupé.

Vous pouvez spécifier plusieurs correspondances 'élément de regroupement' à 'élément regroupé' dans le même hashref. Si cette option est combinée avec "KeyAttr", le pliage de tableau se produira d'abord, puis les noms des éléments regroupés seront éliminés.

"XMLout" utilisera également les mappings 'grouptag' pour réintroduire les balises autour des éléments regroupés. Attention cependant, cela se produira dans tous les endroits où le nom de 'l'étiquette de regroupement' apparaît - vous ne voudrez probablement pas utiliser le même nom pour les éléments et les attributs.

Handler => référence objet # out - SAX uniquement

Utilisez l'option 'Handler' pour que XMLout() génère des événements SAX plutôt que de retourner une chaîne XML. Pour plus de détails, voir « SUPPORT SAX » ci-dessous.

Note : l'implémentation actuelle de cette option génère une chaîne XML et utilise un analyseur SAX pour la traduire en événements SAX. Les règles d'encodage normales s'appliquent ici - vos données doivent être encodées en UTF8, sauf si vous spécifiez un encodage alternatif via l'option 'XMLDecl'; et au moment où les données atteignent l'objet gestionnaire, elles seront sous forme UTF8, quel que soit l'encodage que vous fournissez. Une implémentation future de cette option peut générer les événements directement.

KeepRoot => 1 # in+out - pratique

Dans sa tentative de retourner une structure de données exempte de détails superflus et de niveaux d'indirection inutiles, XMLin() supprime normalement le nom de l'élément racine. Définir l'option 'KeepRoot' à '1' fera conserver le nom de l'élément racine. Donc, après avoir exécuté ce code :

$config = XMLin('<config tempdir="/tmp" />', KeepRoot => 1)

Vous pourrez référencer le tempdir comme "$config->{config}->{tempdir}" au lieu de la valeur par défaut "$config->{tempdir}".

De même, définir l'option 'KeepRoot' à '1' indiquera à XMLout() que la structure de données contient déjà un nom d'élément racine et qu'il n'est pas nécessaire d'en ajouter un autre.

KeyAttr => [ liste ] # in+out - important

Cette option contrôle la fonctionnalité de 'pliage de tableau' qui traduit les éléments imbriqués d'un tableau en un hachage. Elle contrôle également le 'dépliage' des hachages en tableaux.

Par exemple, ce XML :

<opt>
  <user login="grep" fullname="Gary R Epstein" />
  <user login="stty" fullname="Simon T Tyson" />
</opt>

serait, par défaut, analysé comme suit :

{
  'user' => [
              {
                'login' => 'grep',
                'fullname' => 'Gary R Epstein'
              },
              {
                'login' => 'stty',
                'fullname' => 'Simon T Tyson'
              }
            ]
}

Si l'option 'KeyAttr => "login"' était utilisée pour spécifier que l'attribut 'login' est une clé, le même XML serait analysé comme suit :

{
  'user' => {
              'stty' => {
                          'fullname' => 'Simon T Tyson'
                        },
              'grep' => {
                          'fullname' => 'Gary R Epstein'
                        }
            }
}

Les noms des attributs clés doivent être fournis dans un 'arrayref' s'il y en a plus d'un. XMLin() tentera de faire correspondre les noms d'attributs dans l'ordre fourni. XMLout() utilisera le premier nom d'attribut fourni lors du 'dépliage' d'un hachage en un tableau.

Note 1 : La valeur par défaut pour 'KeyAttr' est ['name', 'key', 'id']. Si vous ne souhaitez pas de pliage en entrée ou de dépliage en sortie, vous devez définir cette option sur une liste vide pour désactiver la fonctionnalité.

Note 2 : Si vous souhaitez utiliser cette option, vous devriez également activer l'option "ForceArray". Sans 'ForceArray', un seul élément imbriqué sera converti en scalaire plutôt qu'en tableau et ne sera donc pas plié (car seuls les tableaux sont pliés).

KeyAttr => { liste } # in+out - important

Cette méthode alternative (et préférée) de spécification des attributs clés permet un contrôle plus fin sur quels éléments sont pliés et sur quels attributs. Par exemple, l'option 'KeyAttr => { package => 'id' }' provoquera le pliage de tous les éléments 'package' sur l'attribut 'id'. Aucun autre élément ayant un attribut 'id' ne sera plié du tout.

Note : XMLin() générera un avertissement (ou une erreur fatale en « MODE STRICT ») si cette syntaxe est utilisée et qu'un élément qui ne possède pas l'attribut clé spécifié est rencontré (par exemple, un élément 'package' sans attribut 'id', pour reprendre l'exemple ci-dessus). Les avertissements peuvent être supprimés avec le pragmatisme lexical "no warnings;" ou "no warnings 'XML::Simple';".

Deux variations supplémentaires sont rendues possibles en préfixant un caractère '+' ou '-' au nom de l'attribut :

L'option 'KeyAttr => { user => "+login" }' provoquera l'analyse de ce XML :

<opt>
  <user login="grep" fullname="Gary R Epstein" />
  <user login="stty" fullname="Simon T Tyson" />
</opt>

vers cette structure de données :

{
  'user' => {
              'stty' => {
                          'fullname' => 'Simon T Tyson',
                          'login'    => 'stty'
                        },
              'grep' => {
                          'fullname' => 'Gary R Epstein',
                          'login'    => 'grep'
                        }
            }
}

Le '+' indique que la valeur de l'attribut clé doit être copiée plutôt que déplacée vers la clé de hachage pliée.

Un préfixe '-' produirait ce résultat :

{
  'user' => {
              'stty' => {
                          'fullname' => 'Simon T Tyson',
                          '-login'    => 'stty'
                        },
              'grep' => {
                          'fullname' => 'Gary R Epstein',
                          '-login'    => 'grep'
                        }
            }
}

Comme décrit précédemment, "XMLout" ignorera les clés de hachage commençant par un '-' .

NoAttr => 1 # in+out - pratique

Lorsqu'il est utilisé avec XMLout(), le XML généré ne contiendra aucun attribut. Toutes les paires clé/valeur du hachage seront représentées comme des éléments imbriqués à la place.

Lorsqu'il est utilisé avec XMLin(), tous les attributs dans le XML seront ignorés.

NoEscape => 1 # out - rarement utilisé

Par défaut, XMLout() traduira les caractères '<', '>', '&' et '"' en '&

NoIndent => 1 # out - rarement utilisé

Définissez cette option sur 1 pour désactiver le mode de "mise en forme élégante" par défaut de XMLout(). Avec cette option activée, la sortie XML sera toute sur une seule ligne (sauf s'il y a des sauts de ligne dans les données) - cela peut être plus facile pour le traitement en aval.

NoSort => 1 # out - rarement utilisé

Les versions plus récentes de XML::Simple trient les éléments et les attributs par ordre alphabétique (*), par défaut. Activez cette option pour supprimer le tri - potentiellement pour des raisons de compatibilité rétroactive.

* En fait, le tri est alphabétique, mais les attributs ou noms d'éléments 'clé' (comme dans 'KeyAttr') sont triés en premier. De plus, lorsqu'une table de hachage de tables de hachage est "dépliée", les éléments sont triés par ordre alphabétique selon la valeur du champ clé.

NormaliseSpace => 0 | 1 | 2 # in - utile

Cette option contrôle la manière dont les espaces blancs dans le contenu textuel sont gérés. Les valeurs reconnues pour l'option sont :

  • 0 = (par défaut) les espaces blancs sont transmis sans modification (sauf bien sûr la normalisation des espaces blancs dans les valeurs d'attributs qui est mandatée par la recommandation XML)
  • 1 = les espaces blancs sont normalisés dans toute valeur utilisée comme clé de table de hachage (normaliser signifie supprimer les espaces blancs en tête et en fin et réduire les séquences de caractères d'espaces blancs à un seul espace)
  • 2 = les espaces blancs sont normalisés dans tout le contenu textuel

Remarque : vous pouvez écrire cette option avec un 'z' si cela vous semble plus naturel.

NSExpand => 1 # in+out utile - SAX uniquement

Cette option contrôle l'expansion des espaces de noms - la traduction des noms d'éléments et d'attributs de la forme 'préfixe:nom' en '{uri}nom'. Par exemple, le nom d'élément 'xsl:template' pourrait être développé en : '{http://www.w3.org/1999/XSL/Transform}template'.

Par défaut, XMLin() renverra les noms d'éléments et d'attributs tels qu'ils apparaissent dans le XML. Définir cette option sur 1 fera en sorte que tous les noms d'éléments et d'attributs soient développés pour inclure leur préfixe d'espace de noms.

Remarque : Vous devez utiliser un analyseur SAX pour que cette option fonctionne (c'est-à-dire qu'elle ne fonctionne pas avec XML::Parser).

Cette option contrôle également si XMLout() effectue la traduction inverse de '{uri}nom' en 'préfixe:nom'. La valeur par défaut est aucune traduction. Si vos données contiennent des noms développés, vous devriez définir cette option sur 1, sinon "XMLout" émettra du XML qui n'est pas bien formé.

Remarque : Vous devez avoir le module XML::NamespaceSupport installé si vous voulez que XMLout() traduise les URI en préfixes.

NumericEscape => 0 | 1 | 2 # out - utile

Utilisez cette option pour que les caractères 'élevés' (non-ASCII) dans votre structure de données Perl soient convertis en entités numériques (par exemple, &#8364;) dans la sortie XML. Trois niveaux sont possibles :

0 - par défaut : aucune échappement numérique (OK si vous écrivez en UTF8)

1 - seuls les caractères supérieurs à 0xFF sont échappés (c'est-à-dire que les caractères dans la plage 0x80-FF ne sont pas échappés), potentiellement utile avec la sortie ISO8859-1

2 - tous les caractères supérieurs à 0x7F sont échappés (bon pour une sortie ASCII pure)

OutputFile => < spécificateur de fichier> # out - utile

Le comportement par défaut de XMLout() est de renvoyer le XML sous forme de chaîne. Si vous souhaitez écrire le XML dans un fichier, fournissez simplement le nom du fichier en utilisant l'option 'OutputFile'.

Cette option accepte également un objet de descripteur IO - particulièrement utile dans Perl 5.8.0 et versions ultérieures pour la sortie en utilisant un encodage autre que UTF-8, par exemple :

open my $fh, '>:encoding(iso-8859-1)', $path or die "open($path): $!";
XMLout($ref, OutputFile => $fh);

Notez que XML::Simple n'exige pas que l'objet que vous passez à l'option OutputFile hérite de IO::Handle - il suppose simplement que l'objet prend en charge une méthode "print".

ParserOpts => [ Options XML::Parser ] # in - ne pas utiliser ceci

Remarque : Cette option est maintenant officiellement dépréciée. Si vous la trouvez utile, envoyez un e-mail à l'auteur avec un exemple de ce pourquoi vous l'utilisez. N'utilisez pas cette option pour définir le ProtocolEncoding, c'est tout simplement faux - corrigez le XML.

Cette option vous permet de passer des paramètres au constructeur de l'objet sous-jacent XML::Parser (ce qui suppose bien sûr que vous n'utilisez pas SAX).

RootName => 'chaîne' # out - utile

Par défaut, lorsque XMLout() génère du XML, l'élément racine sera nommé 'opt'. Cette option vous permet de spécifier un nom alternatif.

Spécifier undef ou une chaîne vide pour l'option RootName produira du XML sans élément racine. Dans la plupart des cas, le fragment XML résultant ne sera pas "bien formé" et ne pourra donc pas être relu par XMLin(). Néanmoins, l'option s'est avérée utile dans certaines circonstances.

SearchPath => [ liste ] # in - utile

Si vous passez à XMLin() un nom de fichier, mais que ce nom de fichier n'inclut aucun composant de répertoire, vous pouvez utiliser cette option pour spécifier quels répertoires doivent être recherchés pour localiser le fichier. Vous pourriez utiliser cette option pour rechercher d'abord dans le répertoire personnel de l'utilisateur, puis dans un répertoire global comme /etc.

Si un nom de fichier est fourni à XMLin() mais que SearchPath n'est pas défini, le fichier est supposé se trouver dans le répertoire courant.

Si le premier paramètre de XMLin() est undefined, le SearchPath par défaut contiendra uniquement le répertoire dans lequel le script lui-même est situé. Sinon, le SearchPath par défaut sera vide.

StrictMode => 1 | 0 # in+out rarement utilisé

Cette option vous permet d'activer ou de désactiver le "MODE STRICTE" pour un appel particulier, indépendamment du fait qu'il ait été activé au moment du chargement de XML::Simple.

SuppressEmpty => 1 | '' | undef # in+out - utile

Cette option contrôle ce que XMLin() doit faire avec les éléments vides (sans attributs et sans contenu). Le comportement par défaut est de les représenter comme des tables de hachage vides. Définir cette option sur une valeur vraie (par exemple, 1) fera en sorte que les éléments vides soient complètement ignorés. Définir l'option sur 'undef' ou la chaîne vide fera en sorte que les éléments vides soient représentés par la valeur indéfinie ou la chaîne vide respectivement. Les deux dernières alternatives sont un peu plus faciles à tester dans votre code qu'une table de hachage sans clés.

L'option contrôle également ce que XMLout() fait des valeurs indéfinies. Définir l'option sur undef fait que les valeurs indéfinies sont générées comme des éléments vides (plutôt que des attributs vides), et supprime également la génération d'avertissements concernant les valeurs indéfinies. Définir l'option sur une valeur vraie (par exemple, 1) fait que les valeurs indéfinies sont complètement ignorées lors de la sortie.

ValueAttr => [ noms ] # in - utile

Utilisez cette option pour traiter des éléments qui ont toujours un seul attribut et pas de contenu. Par exemple :

<opt>
  <colour value="red" />
  <size   value="XXL" />
</opt>

Définir "ValueAttr => [ 'value' ]" fera en sorte que le XML ci-dessus soit analysé comme :

{
  colour => 'red',
  size   => 'XXL'
}

au lieu de ceci (par défaut) :

{
  colour => { value => 'red' },
  size   => { value => 'XXL' }
}

Remarque : Cette forme de l'option ValueAttr n'est pas compatible avec XMLout() - puisque le nom de l'attribut est ignoré lors de l'analyse, le XML d'origine ne peut pas être reconstruit.

ValueAttr => { élément => attribut, ... } # in+out - utile

Cette forme (préférée) de l'option ValueAttr vous oblige à spécifier à la fois l'élément et le nom de l'attribut. C'est non seulement plus sûr, mais cela permet également de reconstruire le XML d'origine par XMLout().

Remarque : Vous ne voudrez probablement pas utiliser cette option et l'option NoAttr en même temps.

WarnOnInconsistentNums => 1 | 0 # in - utile

Si vous avez un XML mal formé qui contient des numéros de ligne incohérents (c'est-à-dire que les numéros de ligne fournis par l'analyseur ne sont pas strictement croissants), cette option fera en sorte que XMLin() émette un avertissement. Par défaut, aucun avertissement n'est émis.

WarnOnXMLDecl => 1 | 0 # in - utile

Par défaut, XMLin() émettra un avertissement si le document XML que vous lui donnez contient une déclaration XML. Cela peut être utile si vous recevez des données XML d'un tiers et que vous voulez vous assurer qu'elles sont conformes à la norme.

Définissez cette option sur 0 pour désactiver l'avertissement.

XMLDecl => 'chaîne' | 1 | 0 # out - utile

Cette option contrôle la génération d'une déclaration XML au début de la sortie. Les valeurs possibles sont :

0 - aucune déclaration XML ne sera générée.

1 - une déclaration XML par défaut sera générée (par exemple, <?xml version="1.0" encoding="UTF-8"?>).

'chaîne' - la chaîne spécifiée sera utilisée comme déclaration XML (par exemple, <?xml version="1.0" encoding="ISO-8859-1"?>).

XSIArrayType => 1 # in - rarement utilisé

Certains schémas XML utilisent des attributs de type xsi:type pour indiquer que certains éléments sont en fait des tableaux. Si vous rencontrez un tel XML, définir cette option sur 1 fera en sorte que ces éléments soient traités comme des tableaux Perl.

Variables => { nom => valeur } # en - pratique

Cette option permet d'étendre les variables dans le XML lors de la lecture du fichier. (il n'y a pas de mécanisme pour remettre les noms de variables si vous régénérez du XML en utilisant "XMLout").

Une 'variable' est tout texte de la forme "${nom}" qui apparaît dans la valeur d'un attribut ou dans le contenu textuel d'un élément. Si 'nom' correspond à une clé dans le hashref fourni, "${nom}" sera remplacé par la valeur correspondante du hashref. Si aucune clé correspondante n'est trouvée, la variable ne sera pas remplacée. Les noms doivent correspondre à l'expression régulière : "[\w.]+" (c'est-à-dire que seuls les caractères de 'mot' et les points sont autorisés).

VarAttr => 'nom_attr' # en - pratique

En plus des variables définies à l'aide de "Variables", cette option permet de définir des variables dans le XML. Une définition de variable consiste en un élément avec un attribut appelé 'nom_attr' (la valeur de l'option "VarAttr"). La valeur de l'attribut sera utilisée comme nom de variable et le contenu textuel de l'élément sera utilisé comme valeur. Une variable définie de cette manière remplacera une variable définie à l'aide de l'option "Variables". Par exemple :

XMLin( '<opt>
          <dir name="prefix">/usr/local/apache</dir>
          <dir name="exec_prefix">${prefix}</dir>
          <dir name="bindir">${exec_prefix}/bin</dir>
        </opt>',
       VarAttr => 'name', ContentKey => '-content'
      );

produit la structure de données suivante :

{
  dir => {
           prefix      => '/usr/local/apache',
           exec_prefix => '/usr/local/apache',
           bindir      => '/usr/local/apache/bin',
         }
}

XMLDecl => 1 ou XMLDecl => 'chaîne' # hors - pratique

Si vous souhaitez que la sortie de XMLout() commence par la déclaration XML optionnelle, définissez simplement l'option sur '1'. La déclaration XML par défaut est :

<?xml version='1.0' standalone='yes'?>

Si vous souhaitez une autre chaîne (par exemple pour déclarer une valeur d'encodage), définissez la valeur de cette option sur la chaîne complète requise.

INTERFACE OO OPTIONNELLE

L'interface procédurale est à la fois simple et pratique. Cependant, il y a plusieurs raisons pour lesquelles vous pourriez préférer utiliser l'interface orientée objet (OO) :

  • pour définir un ensemble de valeurs par défaut qui devraient être utilisées pour tous les appels ultérieurs à XMLin() ou XMLout()
  • pour remplacer des méthodes dans XML::Simple afin de fournir un comportement personnalisé

Les valeurs par défaut des options décrites ci-dessus ne conviendront probablement pas à tout le monde. L'interface OO vous permet de remplacer efficacement les valeurs par défaut de XML::Simple par vos valeurs préférées. Cela fonctionne comme suit :

Créez d'abord un objet analyseur XML::Simple avec vos valeurs par défaut préférées :

my $xs = XML::Simple->new(ForceArray => 1, KeepRoot => 1);

puis appelez XMLin() ou XMLout() en tant que méthode de cet objet :

my $ref = $xs->XMLin($xml);
my $xml = $xs->XMLout($ref);

Vous pouvez également spécifier des options lors des appels de méthode, et ces valeurs seront fusionnées avec les valeurs spécifiées lors de la création de l'objet. Les valeurs spécifiées dans un appel de méthode ont la priorité.

Note : lorsqu'elles sont appelées en tant que méthodes, les routines XMLin() et XMLout() peuvent être appelées sous les noms xml_in() ou xml_out(). Les noms de méthodes sont des alias, donc la seule différence est esthétique.

Méthodes d'analyse

Vous pouvez appeler explicitement l'une des méthodes suivantes plutôt que de vous fier à la méthode xml_in() pour déterminer automatiquement si la cible à analyser est une chaîne, un fichier ou un fichier ouvert :

parse_string(texte)
Fonctionne exactement comme la méthode xml_in(), mais suppose que le premier argument est une chaîne XML (ou une référence à un scalaire contenant une chaîne XML).
parse_file(nom_fichier)
Fonctionne exactement comme la méthode xml_in(), mais suppose que le premier argument est le nom d'un fichier contenant du XML.
parse_fh(descripteur_fichier)
Fonctionne exactement comme la méthode xml_in(), mais suppose que le premier argument est un descripteur de fichier à partir duquel on peut lire du XML.

Méthodes d'accroche

Vous pouvez créer votre propre classe qui hérite de XML::Simple et remplace certains comportements. Les méthodes suivantes peuvent fournir des 'crochets' utiles sur lesquels baser votre comportement modifié. Vous pourriez trouver d'autres méthodes non documentées en examinant la source, mais celles-ci peuvent être sujettes à des changements dans les futures versions.

new_xml_parser()
Cette méthode sera appelée lorsqu'un nouvel objet XML::Parser doit être construit (soit parce que XML::SAX n'est pas installé, soit parce que XML::Parser est préféré).
handle_options(direction, nom => valeur ...)
Cette méthode sera appelée lorsqu'une des méthodes d'analyse ou la méthode XMLout() est appelée. L'argument initial sera une chaîne (soit 'in' soit 'out') et les arguments restants seront des paires nom-valeur.
default_config_file()
Calcule et retourne le nom du fichier qui devrait être analysé si aucun nom de fichier n'est passé à XMLin() (par défaut : "$0.xml").
build_simple_tree(nom_fichier, chaîne)
Appelée depuis XMLin() ou l'une des méthodes d'analyse. Prend soit un nom de fichier comme premier argument, soit "undef" suivi d'une 'chaîne' comme deuxième argument. Retourne une structure de données arborescente simple. Vous pourriez remplacer cette méthode pour appliquer vos propres transformations avant que la structure de données ne soit retournée à l'appelant.
new_hashref()
Lorsque la structure de données 'arbre simple' est en cours de construction, cette méthode sera appelée pour créer les hashrefs anonymes requis.
sorted_keys(nom, hashref)
Appelée lorsque XMLout() traduit un hashref en XML. Cette routine retourne une liste de clés de hachage dans l'ordre dans lequel les attributs/éléments correspondants devraient apparaître dans la sortie.
escape_value(chaîne)
Appelée depuis XMLout(), prend une chaîne et retourne une copie de la chaîne avec les règles d'échappement de caractères XML appliquées.
escape_attr(chaîne)
Appelée depuis XMLout(), pour gérer les valeurs d'attributs. Par défaut, appelle simplement escape_value(), mais vous pouvez remplacer cette méthode si vous souhaitez que les attributs soient échappés différemment du contenu textuel.
numeric_escape(chaîne)
Appelée depuis escape_value(), pour gérer les caractères non-ASCII (en fonction de la valeur de l'option NumericEscape).
copy_hash(hashref, extra_key => valeur, ...)
Appelée depuis XMLout(), lors du 'dépliage' d'un hash de hashes en un tableau de hashes. Vous pourriez vouloir remplacer cette méthode si vous utilisez des hashes liés et que vous ne voulez pas qu'ils soient déliés.

Méthodes de cache

XML::Simple implémente trois schémas de mise en cache ('storable', 'memshare' et 'memcopy'). Vous pouvez implémenter un schéma de mise en cache personnalisé en implémentant deux méthodes - une pour lire depuis le cache et une pour écrire dedans.

Par exemple, vous pourriez implémenter un nouveau schéma 'dbm' qui stocke les structures de données mises en cache à l'aide du module MLDBM. Tout d'abord, vous ajouteriez une méthode cache_read_dbm() qui accepterait un nom de fichier à utiliser comme clé de recherche et retournerait une structure de données en cas de succès, ou undef en cas d'échec. Ensuite, vous implémenteriez une méthode cache_read_dbm() qui accepterait une structure de données et un nom de fichier.

Vous utiliseriez ce schéma de mise en cache en spécifiant l'option :

Cache => [ 'dbm' ]

MODE STRICT

Si vous importez les routines XML::Simple comme ceci :

use XML::Simple qw(:strict);

les erreurs courantes suivantes seront détectées et traitées comme des erreurs fatales :

  • Oubli de définir explicitement l'option "KeyAttr" - si vous n'avez pas envie de lire sur cette option, désactivez-la avec : KeyAttr => [ ]
  • Oubli de définir explicitement l'option "ForceArray" - si vous n'avez pas envie de lire sur cette option, définissez-la sur le mode le plus sûr avec : ForceArray => 1
  • Définition de ForceArray sur un tableau, mais oubli de lister tous les éléments du hash KeyAttr.
  • Erreur de données - KeyAttr est défini sur { part => 'partnum' } mais le XML contient un ou plusieurs éléments <part> sans attribut 'partnum' (ou élément imbriqué). Note : si le mode strict n'est pas défini mais que "use warnings;" est actif, cette condition déclenche un avertissement.
  • Erreur de données - comme ci-dessus, mais des valeurs non uniques sont présentes dans l'attribut clé (par exemple, plus d'un élément <part> avec le même partnum). Cela déclenchera également un avertissement si le mode strict n'est pas activé.
  • Erreur de données - comme ci-dessus, mais la valeur de l'attribut clé (par exemple, partnum) n'est pas une chaîne scalaire (en raison d'éléments imbriqués, etc.). Cela déclenchera également un avertissement si le mode strict n'est pas activé.

SUPPORT SAX

À partir de la version 1.08_01, XML::Simple inclut la prise en charge de SAX (la Simple API for XML) - spécifiquement SAX2.

Dans une application SAX typique, un analyseur XML (ou module 'driver' SAX) génère des événements SAX (début d'élément, données de caractères, fin d'élément, etc.) lorsqu'il analyse un document XML et qu'un module 'handler' traite les événements pour extraire les données requises. Ce modèle simple permet des possibilités intéressantes et puissantes :

  • Les applications écrites pour l'API SAX peuvent extraire des données d'énormes documents XML sans les surcoûts de mémoire d'une API DOM ou arborescente.
  • L'API SAX permet l'interchangeabilité des modules d'analyseurs ("plug and play") sans avoir à modifier votre code pour vous adapter à l'API d'un nouveau module. Un certain nombre d'analyseurs SAX sont disponibles avec des capacités allant de la portabilité extrême à des performances fulgurantes.
  • Un module 'filtre' SAX peut implémenter à la fois une interface de gestionnaire pour recevoir des données et une interface de générateur pour transmettre des données modifiées à un gestionnaire en aval. Les filtres peuvent être chaînés en 'pipelines'.
  • Un module de filtre pourrait diviser un flux de données pour diriger les données vers deux gestionnaires en aval ou plus.
  • La génération d'événements SAX n'est pas la prérogative exclusive des modules d'analyse XML. Par exemple, un module pourrait extraire des données d'une base de données relationnelle à l'aide de DBI et les transmettre à un pipeline SAX pour filtrage et formatage.

XML::Simple peut fonctionner à l'une ou l'autre extrémité d'un pipeline SAX. Par exemple, vous pouvez prendre une structure de données sous forme de hashref et la passer dans un pipeline SAX en utilisant l'option 'Handler' de XMLout() :

use XML::Simple;
use Some::SAX::Filter;
use XML::SAX::Writer;
my $ref = {
             ....   # vos données ici
          };
my $writer = XML::SAX::Writer->new();
my $filter = Some::SAX::Filter->new(Handler => $writer);
my $simple = XML::Simple->new(Handler => $filter);
$simple->XMLout($ref);

Vous pouvez également placer XML::Simple à l'extrémité opposée du pipeline pour tirer parti de la structure de données 'arbre' simple une fois que les données pertinentes ont été isolées par filtrage :

use XML::SAX;
use Some::SAX::Filter;
use XML::Simple;
my $simple = XML::Simple->new(ForceArray => 1, KeyAttr => ['partnum']);
my $filter = Some::SAX::Filter->new(Handler => $simple);
my $parser = XML::SAX::ParserFactory->parser(Handler => $filter);
my $ref = $parser->parse_uri('some_huge_file.xml');
print $ref->{part}->{'555-1234'};

Vous pouvez construire un filtre en utilisant un objet XML::Simple comme gestionnaire et en définissant son option DataHandler pour pointer vers une routine qui prend l'arbre résultant, le modifie et l'envoie sous forme d'événements SAX à un gestionnaire en aval :

my $writer = XML::SAX::Writer->new();
my $filter = XML::Simple->new(
               DataHandler => sub {
                                my $simple = shift;
                                my $data = shift;
                                # Modifier $data ici
                                $simple->XMLout($data, Handler => $writer);
                              }
             );
my $parser = XML::SAX::ParserFactory->parser(Handler => $filter);
$parser->parse_uri($filename);

Note : Dans ce dernier exemple, l'option 'Handler' a été spécifiée dans l'appel à XMLout() mais elle aurait pu également être spécifiée dans le constructeur.

ENVIRONNEMENT

Si vous ne vous souciez pas du module d'analyse utilisé par XML::Simple, ignorez complètement cette section (elle semble plus compliquée qu'elle ne l'est réellement).

XML::Simple utilisera par défaut un analyseur SAX s'il est disponible ou XML::Parser si SAX n'est pas disponible.

Vous pouvez dicter quel module d'analyse est utilisé en définissant soit la variable d'environnement 'XML_SIMPLE_PREFERRED_PARSER', soit la variable de paquetage $XML::Simple::PREFERRED_PARSER pour contenir le nom du module. Les règles suivantes sont utilisées :

  • La variable de paquetage a la priorité sur la variable d'environnement si les deux sont définies. Pour forcer XML::Simple à ignorer les paramètres d'environnement et à utiliser ses règles par défaut, vous pouvez définir la variable de paquetage sur une chaîne vide.
  • Si le 'parser préféré' est défini sur la chaîne 'XML::Parser', alors XML::Parser sera utilisé (ou XMLin() mourra si XML::Parser n'est pas installé).
  • Si le 'parser préféré' est défini sur une autre valeur, alors il est supposé être le nom d'un module d'analyse SAX et est passé à XML::SAX::ParserFactory. Si XML::SAX n'est pas installé, ou si le module d'analyse demandé n'est pas installé, alors XMLin() mourra.
  • Si le 'parser préféré' n'est pas du tout défini (l'état par défaut normal), une tentative sera faite pour charger XML::SAX. Si XML::SAX est installé, alors un module d'analyse sera sélectionné selon les règles normales de XML::SAX::ParserFactory (qui signifie généralement le dernier analyseur SAX installé).
  • Si le 'parser préféré' n'est pas défini et que XML::SAX n'est pas installé, alors XML::Parser sera utilisé. XMLin() mourra si XML::Parser n'est pas installé.

Note : La distribution XML::SAX inclut un analyseur XML entièrement écrit en Perl. Il est très portable mais pas très rapide. Vous devriez envisager d'installer XML::LibXML ou XML::SAX::Expat s'ils sont disponibles pour votre plateforme.

GESTION DES ERREURS

La norme XML est très claire sur la question des documents non conformes. Une erreur lors de l'analyse d'un seul élément (par exemple, une balise de fermeture manquante) doit entraîner le rejet de l'ensemble du document. XML::Simple mourra avec un message approprié s'il rencontre une erreur d'analyse.

Si mourir n'est pas approprié pour votre application, vous devriez organiser l'appel à XMLin() dans un bloc eval et rechercher les erreurs dans $@. par exemple :

my $config = eval { XMLin() };
PopUpMessage($@) if($@);

Notez qu'il existe une idée fausse courante selon laquelle l'utilisation de eval ralentira considérablement un script. Bien que cela puisse être vrai lorsque le code évalué est dans une chaîne, ce n'est pas vrai pour un code comme l'exemple ci-dessus.

EXEMPLES

Lorsque XMLin() lit le morceau de XML très simple suivant :

<opt username="testuser" password="frodo"></opt>

il renvoie la structure de données suivante :

{
  'username' => 'testuser',
  'password' => 'frodo'
}

Le résultat identique aurait pu être produit avec ce XML alternatif :

<opt username="testuser" password="frodo" />

Ou ceci (bien que voir l'option 'ForceArray' pour les variations) :

<opt>
  <username>testuser</username>
  <password>frodo</password>
</opt>

Les éléments imbriqués répétés sont représentés par des tableaux anonymes :

<opt>
  <person firstname="Joe" lastname="Smith">
    <email>joe@smith.com</email>
    <email>jsmith@yahoo.com</email>
  </person>
  <person firstname="Bob" lastname="Smith">
    <email>bob@smith.com</email>
  </person>
</opt>
{
  'person' => [
                {
                  'email' => [
                               'joe@smith.com',
                               'jsmith@yahoo.com'
                             ],
                  'firstname' => 'Joe',
                  'lastname' => 'Smith'
                },
                {
                  'email' => 'bob@smith.com',
                  'firstname' => 'Bob',
                  'lastname' => 'Smith'
                }
              ]
}

Les éléments imbriqués avec un attribut clé reconnu sont transformés (pliés) d'un tableau en une table indexée sur la valeur de cet attribut (voir l'option "KeyAttr") :

<opt>
  <person key="jsmith" firstname="Joe" lastname="Smith" />
  <person key="tsmith" firstname="Tom" lastname="Smith" />
  <person key="jbloggs" firstname="Joe" lastname="Bloggs" />
</opt>
{
  'person' => {
                'jbloggs' => {
                               'firstname' => 'Joe',
                               'lastname' => 'Bloggs'
                             },
                'tsmith' => {
                              'firstname' => 'Tom',
                              'lastname' => 'Smith'
                            },
                'jsmith' => {
                              'firstname' => 'Joe',
                              'lastname' => 'Smith'
                            }
              }
}

La balise <anon> peut être utilisée pour former des tableaux anonymes :

<opt>
  <head><anon>Col 1</anon><anon>Col 2</anon><anon>Col 3</anon></head>
  <data><anon>R1C1</anon><anon>R1C2</anon><anon>R1C3</anon></data>
  <data><anon>R2C1</anon><anon>R2C2</anon><anon>R2C3</anon></data>
  <data><anon>R3C1</anon><anon>R3C2</anon><anon>R3C3</anon></data>
</opt>
{
  'head' => [
              [ 'Col 1', 'Col 2', 'Col 3' ]
            ],
  'data' => [
              [ 'R1C1', 'R1C2', 'R1C3' ],
              [ 'R2C1', 'R2C2', 'R2C3' ],
              [ 'R3C1', 'R3C2', 'R3C3' ]
            ]
}

Les tableaux anonymes peuvent être imbriqués à des niveaux arbitraires et, à titre spécial, si les balises environnantes d'un document XML ne contiennent qu'un tableau anonyme, le tableau sera retourné directement au lieu de la table habituelle :

<opt>
  <anon><anon>Col 1</anon><anon>Col 2</anon></anon>
  <anon><anon>R1C1</anon><anon>R1C2</anon></anon>
  <anon><anon>R2C1</anon><anon>R2C2</anon></anon>
</opt>
t; [ [ 'Col 1', 'Col 2' ], [ 'R1C1', 'R1C2' ], [ 'R2C1', 'R2C2' ] ]

Les éléments qui ne contiennent que du contenu textuel seront simplement représentés comme une valeur scalaire. Lorsqu'un élément a à la fois des attributs et du contenu textuel, l'élément sera représenté comme un hashref avec le contenu textuel dans la clé 'content' (voir l'option "ContentKey") :

<opt>
  <one>first</one>
  <two attr="value">second</two>
</opt>
{
  'one' => 'first',
  'two' => { 'attr' => 'value', 'content' => 'second' }
}

Le contenu mixte (éléments qui contiennent à la fois du contenu textuel et des éléments imbriqués) ne sera pas représenté de manière utile - l'ordre des éléments et les espaces blancs significatifs seront perdus. Si vous avez besoin de travailler avec du contenu mixte, alors XML::Simple n'est pas le bon outil pour votre travail - consultez la section suivante.

OÙ ALLER À PARTIR D'ICI?

XML::Simple est capable de présenter une API simple car il fait certaines suppositions pour vous. Celles-ci incluent :

  • Vous ne vous intéressez pas au contenu textuel composé uniquement d'espaces blancs
  • Vous ne vous souciez pas que lorsque les choses sont chargées dans une hash, l'ordre soit perdu
  • Vous ne voulez pas d'un contrôle granulaire sur le formatage du XML généré
  • Vous n'utiliseriez jamais une clé de hash qui ne serait pas un nom d'élément XML légal
  • Vous n'avez pas besoin d'aide pour convertir entre différents encodages

Dans un projet XML sérieux, vous dépasserez probablement ces suppositions assez rapidement. Cette section du document offrait autrefois des conseils sur le choix d'une option plus puissante. Ces conseils ont maintenant été développés dans le document 'Perl-XML FAQ' que vous pouvez trouver à : http://perl-xml.sourceforge.net/faq/

Les conseils de la FAQ se résument à une explication rapide des parseurs basés sur des arbres par rapport aux parseurs basés sur des événements, puis recommandent :

Pour l'analyse basée sur des événements, utilisez SAX (ne cherchez pas à écrire de nouveau code pour l'API de gestionnaire d'XML::Parser - elle est obsolète).

Pour l'analyse basée sur des arbres, vous pouvez choisir entre l'approche 'Perlish' d'XML::Twig et des implémentations DOM plus basées sur des standards - de préférence une avec support XPath telle que XML::LibXML.

VOIR AUSSI

XML::Simple nécessite XML::Parser ou XML::SAX.

Pour générer des documents avec des espaces de noms, XML::NamespaceSupport est requis.

Les fonctions de mise en cache optionnelles nécessitent Storable.

Les réponses aux questions fréquemment posées sur XML::Simple sont fournies avec cette distribution sous le nom : XML::Simple::FAQ
