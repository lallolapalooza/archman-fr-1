NOM

XML::SAX::Intro - Une Introduction à l'analyse SAX avec Perl

Introduction

XML::SAX est une nouvelle façon de travailler avec les analyseurs XML sous Perl. Dans cet article, nous discuterons pourquoi vous devriez utiliser SAX, pourquoi vous devriez utiliser XML::SAX, et nous examinerons certains détails fins de l'implémentation. Le texte ci-dessous suppose une certaine familiarité avec l'analyse basée sur les rappels (callback) ou le flux (push), mais si vous n'êtes pas familier avec ces techniques, un bon point de départ est la série d'articles de Kip Hampton sur XML.com.

Remplacer XML::Parser

La méthode de facto pour analyser le XML sous Perl est d'utiliser XML::Parser de Larry Wall et Clark Cooper. Ce module est un wrapper Perl et XS autour de la bibliothèque d'analyse XML expat de James Clark. Ce fut un projet d'un succès immense, mais il souffre de quelques défauts plutôt majeurs. Premièrement, c'est une API propriétaire, conçue avant que l'API SAX ne soit conçue, ce qui signifie qu'elle n'est pas facilement remplaçable par d'autres analyseurs de flux. Deuxièmement, ses rappels sont des références à des sous-routines. Cela ne semble pas être un gros problème, mais conduit malheureusement à du code comme ceci :

sub handle_start {
  my ($e, $el, %attrs) = @_;
  if ($el eq 'foo') {
    $e->{inside_foo}++; # MAUVAIS ! $e est un objet XML::Parser::Expat.
  }
}

Comme vous pouvez le voir, nous utilisons l'objet $e pour conserver nos informations d'état, ce qui est une mauvaise idée car nous ne possédons pas cet objet - nous ne l'avons pas créé. C'est un objet interne de XML::Parser, qui se trouve être une référence de hachage. Nous pourrions trop facilement écraser les variables d'état internes de XML::Parser en utilisant cela, ou Clark pourrait le changer en une référence de tableau (pas qu'il le ferait, car cela casserait tellement de code, mais il le pourrait).

La seule façon actuelle avec XML::Parser de maintenir l'état en toute sécurité est d'utiliser une fermeture (closure):

my $state = MyState->new();
$parser->setHandlers(Start => sub { handle_start($state, @_) });

Cette fermeture capture la variable $state, qui est maintenant passée comme premier paramètre à votre rappel. Malheureusement, très peu de gens utilisent cette technique, car elle n'est pas documentée dans les fichiers POD de XML::Parser.

Une autre raison pour laquelle vous pourriez ne pas vouloir utiliser XML::Parser est que vous avez besoin d'une fonctionnalité qu'il ne fournit pas (comme la validation), ou vous pourriez avoir besoin d'utiliser une bibliothèque qui n'utilise pas expat, parce qu'elle n'est pas installée sur votre système, ou à cause d'un fournisseur d'accès à Internet restrictif. L'utilisation de SAX vous permet de contourner ces restrictions.

Introduction à SAX

SAX signifie Simple API for XML. Et simple, ça l'est vraiment. Construire un analyseur SAX et passer des événements aux gestionnaires se fait aussi simplement que :

use XML::SAX;
use MySAXHandler;

my $parser = XML::SAX::ParserFactory->parser(
      Handler => MySAXHandler->new
);

$parser->parse_uri("foo.xml");

Le concept important à saisir ici est que SAX utilise une classe fabrique appelée XML::SAX::ParserFactory pour créer une nouvelle instance d'analyseur. La raison en est que vous pouvez prendre en charge d'autres implémentations d'analyse sous-jacentes pour différents ensembles de fonctionnalités. C'est une chose qui a toujours cruellement manqué à XML::Parser.

Dans le code ci-dessus, nous voyons la méthode parse_uri utilisée, mais nous aurions tout aussi bien pu appeler parse_file, parse_string, ou parse(). Veuillez consulter XML::SAX::Base pour savoir ce que ces méthodes prennent comme paramètres, mais ne vous laissez pas berner en croyant que parse_file prend un nom de fichier. Non, il prend un descripteur de fichier, un glob, ou une sous-classe de IO::Handle. Attention.

SAX fonctionne de manière très similaire à la méthode de rappel par défaut de XML::Parser, sauf qu'il y a une différence majeure : plutôt que de définir des rappels individuels, vous créez une nouvelle classe dans laquelle recevoir les rappels. Chaque rappel est appelé comme un appel de méthode sur une instance de cette classe de gestionnaire. Un exemple démontrera mieux cela :

package MySAXHandler;
use base qw(XML::SAX::Base);

sub start_document {
  my ($self, $doc) = @_;
  # traite l'événement de début de document
}

sub start_element {
  my ($self, $el) = @_;
  # traite l'événement de début d'élément
}

Maintenant, lorsque nous instancions cela comme ci-dessus, et que nous analysons du XML avec ceci comme gestionnaire, les méthodes start_document et start_element seront appelées comme des appels de méthode, donc ce serait l'équivalent d'appeler directement :

$object->start_element($el);

Notez la différence avec le style d'appel de XML::Parser, qui appelle :

start_element($e, $name, %attribs);

C'est la différence entre les appels de fonction et les appels de méthode qui vous permet de créer des sous-classes de gestionnaires SAX, ce qui contribue à faire de SAX une solution puissante.

Comme vous pouvez le voir, contrairement à XML::Parser, nous devons définir un nouveau package pour faire notre traitement (il existe des astuces que vous pouvez utiliser pour rendre cela inutile, mais je laisserai les experts découvrir cela). Le plus grand avantage est que vous maintenez votre propre variable d'état ($self dans l'exemple ci-dessus), vous libérant ainsi des préoccupations énumérées ci-dessus. C'est également une amélioration en termes de maintenance - vous pouvez placer le code dans un fichier séparé si vous le souhaitez, et vos méthodes de rappel sont toujours appelées de la même manière, plutôt que d'avoir à choisir un nom approprié pour elles comme vous deviez le faire avec XML::Parser. C'est un avantage évident.

Les analyseurs SAX sont également très flexibles quant à la manière dont vous leur passez un gestionnaire. Vous pouvez utiliser un paramètre de constructeur comme nous l'avons vu ci-dessus, ou nous pouvons passer le gestionnaire directement dans l'appel à l'une des méthodes de parse :

$parser->parse(Handler => $handler, 
               Source => { SystemId => "foo.xml" });
# ou...
$parser->parse_file($fh, Handler => $handler);

Cette flexibilité permet d'utiliser un analyseur dans de nombreux scénarios différents tout au long de votre script (bien qu'il ne faille pas ressentir la pression d'utiliser cette méthode, car la construction de l'analyseur n'est généralement pas un processus coûteux en temps).

Paramètres des rappels

La seule autre chose que vous devez savoir pour comprendre le SAX de base est la structure des paramètres passés à chacun des rappels. Dans XML::Parser, tous les paramètres sont passés comme options multiples aux rappels, donc par exemple le rappel Start serait appelé comme my_start($e, $name, %attributes), et le rappel PI serait appelé comme my_processing_instruction($e, $target, $data). En SAX, chaque rappel reçoit une référence de hachage, contenant des entrées qui définissent notre "nœud". Les rappels clés et les structures qu'ils reçoivent sont :

start_element

Le gestionnaire start_element est appelé chaque fois qu'un analyseur rencontre une balise ouvrante. Il reçoit une structure d'élément composée de :

LocalName
Le nom de l'élément moins tout préfixe d'espace de noms avec lequel il peut être venu dans le document.
NamespaceURI
L'URI de l'espace de noms associé à cet élément, ou la chaîne vide pour aucun.
Attributes
Un ensemble d'attributs tel que décrit ci-dessous.
Name
Le nom de l'élément tel qu'il a été vu dans le document (c'est-à-dire en incluant tout préfixe qui lui est associé)
Prefix
Le préfixe utilisé pour qualifier l'espace de noms de cet élément, ou la chaîne vide si aucun.

Les Attributes sont une référence de hachage, indexée par ce que nous avons appelé la notation "James Clark". Cela signifie que le nom de l'attribut a été étendu pour inclure l'URI de l'espace de noms associé, et combiné comme {ns}name, où "ns" est l'URI de l'espace de noms étendu de l'attribut si et seulement si l'attribut avait un préfixe, et "name" est le LocalName de l'attribut.

La valeur de chaque entrée dans le hachage des attributs est une autre structure de hachage composée de :

LocalName
Le nom de l'attribut moins tout préfixe d'espace de noms avec lequel il peut être venu dans le document.
NamespaceURI
L'URI de l'espace de noms associé à cet attribut. Si l'attribut n'avait pas de préfixe, alors cela consiste uniquement en la chaîne vide.
Name
Le nom de l'attribut tel qu'il est apparu dans le document, inclu

Prefix
Le préfixe utilisé pour qualifier l'espace de noms de cet attribut, ou la chaîne vide si aucun.
Value
La valeur de l'attribut.

end_element

Le gestionnaire end_element est appelé soit lorsqu'un analyseur rencontre une balise fermante, soit après que start_element ait été appelé pour un élément vide (notez toutefois qu'un analyseur peut, s'il le souhaite, appeler characters avec une chaîne vide lorsqu'il rencontre un élément vide. Il n'y a aucun moyen simple en SAX de déterminer si l'analyseur a effectivement vu un élément vide, un début et une fin d'élément sans contenu).

Le gestionnaire end_element reçoit exactement la même structure que start_element, moins l'entrée Attributes. Il faut cependant noter qu'il ne doit pas s'agir d'une référence aux mêmes données que celles reçues par start_element, vous pouvez donc modifier les valeurs dans start_element, mais cela n'affectera pas les valeurs vues plus tard par end_element.

characters

La devolución de characters peut être appelée dans plusieurs circonstances. La plus évidente est lorsqu'on voit des données de caractères ordinaires dans le balisage. Mais elle est également appelée pour le texte dans une section CDATA, et est aussi appelée dans d'autres situations. Un analyseur SAX ne fait aucune garantie quant au nombre de fois où il peut appeler characters pour une étendue de texte dans un document XML - il peut appeler une fois, ou une fois pour chaque caractère du texte. Afin de contourner cela, il est souvent important pour le développeur SAX d'utiliser une technique de regroupement, où le texte est collecté et traité dans l'une des autres callbacks. Ce n'est pas toujours nécessaire, mais c'est une technique qui vaut la peine d'être apprise, que nous aborderons dans XML::SAX::Advanced (quand j'aurai le temps de l'écrire).

Le gestionnaire characters est appelé avec une structure très simple - une référence de hachage composée d'une seule entrée :

Data
Les données textuelles qui ont été reçues.

comment

La callback comment est appelée pour le texte des commentaires. Contrairement à characters(), la callback comment *doit* être invoquée une seule fois pour une chaîne de commentaire entière. Elle reçoit une seule structure simple - une référence de hachage contenant une seule entrée :

Data
Le texte du commentaire.

processing_instruction

Le gestionnaire d'instructions de traitement est appelé pour toutes les instructions de traitement du document. Notez que ces instructions de traitement peuvent apparaître avant l'élément racine du document, ou après celui-ci, ou n'importe où où le texte et les éléments apparaîtraient normalement dans le document, conformément à la spécification XML.

Le gestionnaire reçoit une structure contenant seulement deux entrées :

Target
La cible de l'instruction de traitement
Data
Les données textuelles de l'instruction de traitement. Peut être une chaîne vide pour une instruction de traitement qui n'a pas d'élément de données. Par exemple, <?wiggle?> est une instruction de traitement parfaitement valide.

Le bout de l'iceberg

Ce que nous avons discuté ci-dessus est vraiment le bout de l'iceberg SAX. Et jusqu'à présent, il semble qu'il n'y ait pas grand-chose d'intéressant dans SAX au-delà de ce que nous avons vu avec XML::Parser. Mais cela va beaucoup plus loin, je vous assure.

Ceux qui détestent le code orienté objet pour le plaisir de le faire pourraient penser ici que la création d'un nouveau paquet juste pour analyser quelque chose est une perte de temps alors qu'ils analysent des choses très bien jusqu'à présent en utilisant du code procédural. Mais il y a une raison à toute cette folie. Et cette raison, ce sont les filtres SAX.

Comme vous l'avez vu tout au début, pour informer l'analyseur de notre classe, nous lui passons une instance de notre classe comme Handler à l'analyseur. Mais imaginez maintenant ce qui se passerait si notre classe pouvait également accepter une option Handler, et simplement effectuer un traitement puis transmettre nos données plus loin ? C'est en quelques mots comment fonctionnent les filtres SAX. Ce sont des pipes Unix pour le 21ème siècle !

Il y a deux inconvénients à cela. Numéro 1 - écrire des filtres SAX peut être délicat. Si vous regardez dans le futur et lisez le tutoriel avancé que j'écris, vous verrez que Handler peut avoir plusieurs formes et tailles. Donc, s'assurer que votre filtre fait la bonne chose peut être délicat. Deuxièmement, la construction de chaînes de filtres complexes peut être difficile, et une simple réflexion nous dit que nous n'avons qu'une seule passe sur notre document, alors que nous en aurons souvent besoin de plus.

Heureusement, ces inconvénients ont été résolus avec la sortie de deux modules très intéressants. Ce qui est encore mieux, c'est que je n'ai écrit aucun d'entre eux !

Le premier module est XML::SAX::Base. C'est un module SAX VITAL qui sert de classe de base pour tous les analyseurs et filtres SAX. Il fournit une abstraction par rapport à l'appel des méthodes de gestionnaire, ce qui garantit que votre filtre ou analyseur fait la bonne chose, et il le fait RAPIDEMENT. Donc, si vous avez jamais besoin d'écrire un filtre SAX, ce qui est probablement le cas si vous traitez XML -> XML, ou XML -> HTML, alors vous devez l'écrire comme une sous-classe de XML::SAX::Base. Vraiment - c'est un conseil à ne pas négliger à la légère. Je n'entrerai pas dans les détails de l'écriture d'un filtre SAX ici. Kip Hampton, l'auteur de XML::SAX::Base, l'a bien couvert dans son article sur XML.com ici <URI>.

Pour construire des pipelines SAX, Barrie Slaymaker, un ancien hacker Perl dont vous avez probablement entendu parler ou utilisé les modules, a écrit un module très astucieux appelé XML::SAX::Machines. Celui-ci combine des modules de type filtre SAX vraiment astucieux avec une boîte à outils de construction de filtres qui facilite la création de pipelines. Mais avant de voir comment il facilite les choses, voyons d'abord à quel point il semble difficile de construire des pipelines de filtres SAX complexes.

use XML::SAX::ParserFactory;
use XML::Filter::Filter1;
use XML::Filter::Filter2;
use XML::SAX::Writer;

my $output_string;
my $writer = XML::SAX::Writer->new(Output => \$output_string);
my $filter2 = XML::SAX::Filter2->new(Handler => $writer);
my $filter1 = XML::SAX::Filter1->new(Handler => $filter2);
my $parser = XML::SAX::ParserFactory->parser(Handler => $filter1);

$parser->parse_uri("foo.xml");

C'est beaucoup plus facile avec XML::SAX::Machines :

use XML::SAX::Machines qw(Pipeline);

my $output_string;
my $parser = Pipeline(
      XML::SAX::Filter1 => XML::SAX::Filter2 => \$output_string
      );

$parser->parse_uri("foo.xml");

L'un des principaux avantages de XML::SAX::Machines est que les pipelines sont construits dans l'ordre naturel, plutôt que dans l'ordre inverse que nous avons vu avec la construction manuelle de pipelines. XML::SAX::Machines s'occupe de tous les détails internes de la construction de pipelines, vous fournissant à la fin juste un analyseur que vous pouvez utiliser (et vous pouvez réutiliser le même analyseur autant de fois que vous en avez besoin).

Juste un dernier conseil. Si jamais vous êtes bloqué et confus quant à ce qui est passé d'un filtre ou analyseur SAX à l'autre, alors Devel::TraceSAX vous viendra en aide. Ce plugin de débogueur Perl vous permettra de vider le flux d'événements SAX au fur et à mesure. L'utilisation est vraiment très simple, il suffit d'appeler votre script Perl qui utilise SAX comme suit :

$ perl -d:TraceSAX <scriptname>

Et de préférence redirigez la sortie vers un paginateur, tel que more ou less. La sortie est extrêmement verbeuse, mais devrait aider à éclaircir certains problèmes.
