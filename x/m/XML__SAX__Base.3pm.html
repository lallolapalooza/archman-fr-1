NOM

XML::SAX::Base - Classe de base pour les pilotes et filtres SAX

SYNTAXE

package MonFiltre;
use XML::SAX::Base;
@ISA = ('XML::SAX::Base');

DESCRIPTION

Ce module a une tâche très simple : servir de classe de base pour les pilotes et filtres PerlSAX. Son comportement par défaut est de passer l'entrée directement à la sortie sans modification. Il peut être utile d'utiliser ce module comme classe de base afin de ne pas avoir à implémenter, par exemple, la méthode de rappel (callback) characters().

Les principaux avantages qu'il offre sont la facilité de distribution des événements de la bonne manière (c'est-à-dire qu'il se charge de vérifier que le gestionnaire a implémenté cette méthode, ou a défini une AUTOLOAD), et la garantie que les filtres transmettront les événements qu'ils n'implémentent pas aux gestionnaires en aval qui pourraient néanmoins être intéressés par eux.

ÉCRIRE DES PILOTES ET FILTRES SAX

La référence de l'API Perl Sax se trouve à http://perl-xml.sourceforge.net/perl-sax/.

Écrire des filtres SAX est incroyablement facile : il suffit d'hériter de ce module et de définir les événements que vous souhaitez gérer. Une explication plus détaillée se trouve à http://www.xml.com/pub/a/2001/10/10/sax-filters.html.

Écrire des pilotes est tout aussi simple. La seule chose à laquelle vous devez prêter attention est de NE PAS appeler vous-même les événements (cela s'applique aussi aux filtres). Par exemple :

package MonFiltre;
use base qw(XML::SAX::Base);
sub start_element {
  my $self = shift;
  my $data = shift;
  # faire quelque chose
  $self->{Handler}->start_element($data); # MAUVAIS
}

L'exemple ci-dessus fonctionne bien en tant que tel : un exemple. Mais il présente plusieurs défauts : 1) il ne vérifie pas si le gestionnaire définit start_element. Peut-être qu'il ne veut pas voir cet événement, auquel cas vous ne devriez pas le déclencher (sinon cela provoquera une erreur). 2) il ne vérifie pas le ContentHandler puis le Handler (c'est-à-dire qu'il ne vérifie pas si l'utilisateur n'a pas demandé d'événements sur un gestionnaire spécifique, et sinon sur celui par défaut), 3) s'il vérifiait tout cela, non seulement le code serait fastidieux (voir le code source de ce module pour en avoir une idée) mais il devrait probablement vérifier pour un DocumentHandler (au cas où il s'agirait de SAX1) et pour les AUTOLOAD potentiellement définis dans tous ces paquets. Comme vous pouvez le constater, ce serait assez pénible. Au lieu de passer par là, rappelez-vous simplement d'utiliser un code similaire à celui ci-dessous à la place :

package MonFiltre;
use base qw(XML::SAX::Base);
sub start_element {
  my $self = shift;
  my $data = shift;
  # faire quelque chose pour filtrer
  $self->SUPER::start_element($data); # BON (et facile) !
}

De cette façon, une fois que vous avez fait votre travail, vous renvoyez la balle à XML::SAX::Base et il s'occupe de tous ces problèmes pour vous !

Notez que l'exemple ci-dessus ne s'applique pas uniquement aux filtres, les pilotes bénéficieront de la même fonctionnalité exacte.

MÉTHODES

Un certain nombre de méthodes sont définies dans cette classe dans le but d'hériter. Certaines n'ont probablement pas besoin d'être redéfinies (par exemple, parse_file), mais d'autres devraient clairement l'être (par exemple, parse). Les options pour ces méthodes sont décrites dans la spécification PerlSAX2 disponible à l'adresse http://cvs.sourceforge.net/cgi-bin/viewcvs.cgi/~checkout~/perl-xml/libxml-perl/doc/sax-2.0.html?rev=HEAD&content-type=text/html.

  • parse

    La méthode parse est le point d'entrée principal pour l'analyse des documents. En interne, la méthode parse détectera le type de "chose" que vous analysez et appellera la méthode appropriée dans votre classe d'implémentation. Voici le tableau de correspondance de ce qui se trouve dans les options Source (voir la spécification Perl SAX 2.0 pour la signification de ces valeurs) :

    Source Contient           parse() appelle
===============           =============
CharacterStream (*)       _parse_characterstream($stream, $options)
ByteStream                _parse_bytestream($stream, $options)
String                    _parse_string($string, $options)
SystemId                  _parse_systemid($string, $options)

    Notez cependant que ces méthodes peuvent ne pas être pertinentes si votre classe de pilote ne sert pas à analyser du XML. Un exemple pourrait être un pilote DBI qui génère du XML/SAX à partir d'une table de base de données. Si tel est le cas, vous voudrez probablement écrire votre propre méthode parse().

    Notez également que la Source peut contenir à la fois une entrée PublicId et une entrée Encoding. Pour y accéder, examinez $options->{Source} tel que passé à votre méthode.

    (*) Un CharacterStream est un handle de fichier qui ne nécessite aucune translation d'encodage. Ceci est implémenté comme un handle de fichier ordinaire et ne fonctionne qu'avec Perl 5.7.2 ou supérieur utilisant PerlIO. Pour obtenir un seul caractère, ou un certain nombre de caractères, utilisez la fonction de base Perl read(). Pour obtenir un seul octet (ou un certain nombre d'octets), vous pouvez utiliser sysread(). L'encodage du flux doit se trouver dans l'entrée Encoding pour la Source.

  • parse_file, parse_uri, parse_string

    Ce sont toutes des variations de commodité de parse(), et en fait, elles configurent simplement les options avant de l'appeler. Vous n'avez probablement pas besoin de les redéfinir.

  • get_options

    C'est une méthode de commodité pour obtenir les options dans le style SAX2, ou plus génériquement soit sous forme de tables de hachage (hashes), soit sous forme de références à des tables de hachage (hashes) (elle renvoie une référence à une table de hachage). Vous voudrez probablement utiliser cette méthode dans vos propres implémentations de parse() et de new().

  • get_feature, set_feature

    Celles-ci obtiennent et définissent simplement des fonctionnalités, et déclenchent les exceptions appropriées définies dans la spécification si nécessaire.

    Si votre sous-classe définit des fonctionnalités non définies dans celle-ci, vous devriez redéfinir ces méthodes de telle sorte qu'elles vérifient d'abord vos fonctionnalités, puis appellent les méthodes de la classe de base pour les fonctionnalités non définies par votre classe. Un exemple serait :

    sub get_feature {
    my $self = shift;
    my $feat = shift;
    if (exists $MY_FEATURES{$feat}) {
        # gérer la fonctionnalité de diverses manières
    }
    else {
        return $self->SUPER::get_feature($feat);
    }
}

    Actuellement, cette partie n'est pas implémentée.

  • set_handler

    Cette méthode prend un type de gestionnaire (Handler, ContentHandler, etc.) et un objet gestionnaire comme arguments, et modifie le gestionnaire actuel pour ce type de gestionnaire, tout en prenant soin de réinitialiser l'état interne qui doit l'être. Cela permet de changer un gestionnaire pendant l'analyse sans rencontrer de problèmes (le changer directement sur l'objet parseur provoquera très probablement des problèmes).

  • set_document_handler, set_content_handler, set_dtd_handler, set_lexical_handler, set_decl_handler, set_error_handler, set_entity_resolver

    Ce ne sont que de simples wrappers autour de la méthode précédente, et elles prennent un objet gestionnaire comme argument. En interne, elles appellent simplement set_handler avec les arguments corrects.

  • get_handler

    L'inverse de set_handler, cette méthode prend une chaîne optionnelle contenant un type de gestionnaire (DTDHandler, ContentHandler, etc. 'Handler' est utilisé si aucun type n'est passé). Elle renvoie une référence à l'objet qui implémente cette classe, ou undef si ce type de gestionnaire n'est pas défini pour le pilote/filtre actuel.

  • get_document_handler, get_content_handler, get_dtd_handler, get_lexical_handler, get_decl_handler, get_error_handler, get_entity_resolver

    Ce ne sont que de simples wrappers autour de la méthode get_handler(), et elles ne prennent aucun argument. En interne, elles appellent simplement get_handler avec le nom du type de gestionnaire correct.
