XML::Simple::FAQ - Foire aux questions concernant XML::Simple

Bases

À quoi devrais-je utiliser XML::Simple ?

À rien !

C'est aussi simple que ça.

Choisissez un meilleur module. Voir Perl XML::LibXML par l'exemple http://grantm.github.io/perl-libxml-by-example/ pour une introduction douce à XML::LibXML avec de nombreux exemples.

À quoi XML::Simple était-il destiné à être utilisé ?

XML::Simple est un module Perl qui a été initialement développé comme un outil pour lire et écrire des données de configuration au format XML. Vous pourriez l'utiliser pour d'autres usages impliquant le stockage et la récupération de données structurées en XML, mais ce serait probablement une expérience frustrante.

Pourquoi stocker des données de configuration en XML de toute façon ?

Cela semblait être une bonne idée à l'époque. Maintenant, j'utilise et recommande Config::General qui utilise un format similaire à celui utilisé par le serveur web Apache. Il est plus facile à lire que le XML tout en permettant des concepts avancés tels que les sections imbriquées.

Au moment où XML::Simple a été écrit, les avantages de l'utilisation du format XML pour les données de configuration étaient considérés comme incluant :

  • Utiliser des outils d'analyse XML existants demande moins de temps de développement, est plus facile et plus robuste que de développer votre propre code d'analyse de fichiers de configuration.
  • Le XML peut représenter des relations entre des morceaux de données, tels que l'imbrication de sections à des niveaux arbitraires (pas facilement faisable avec les fichiers .INI par exemple).
  • Le XML est essentiellement du texte, vous pouvez donc facilement éditer un fichier de configuration (plus facile que d'éditer le registre Win32).
  • Le XML fournit des solutions standard pour gérer les jeux de caractères et l'encodage au-delà du simple ASCII (important pour l'internationalisation).
  • S'il devient nécessaire de changer le format de votre fichier de configuration, il existe de nombreux outils disponibles pour effectuer des transformations sur les fichiers XML.
  • Le XML est une norme ouverte (le monde n'a pas besoin d'autres formats de fichiers binaires propriétaires).
  • Faire le pas supplémentaire de développer une DTD permet de valider le format des fichiers de configuration avant que votre programme ne les lise (non directement pris en charge par XML::Simple).
  • Combiner une DTD avec un bon éditeur XML peut vous donner un éditeur de configuration graphique avec un effort de codage minimal.

À quoi XML::Simple n'est-il pas bon ?

La principale limitation de XML::Simple est qu'il ne fonctionne pas avec le 'contenu mixte' (voir la question suivante). Si vous considérez que vos fichiers XML contiennent du texte balisé plutôt que des données structurées, vous devriez probablement utiliser un autre module.

Si vos documents XML source changent régulièrement, il est probable que vous rencontriez des échecs intermittents. En particulier, une mauvaise utilisation des options ForceArray et KeyAttr produira un code qui fonctionne lorsque vous obtenez une liste d'éléments portant le même nom, mais qui échoue lorsqu'il n'y a qu'un seul élément dans la liste. Ces types de problèmes peuvent être évités en n'utilisant pas XML::Simple en premier lieu.

Si vous travaillez avec de très gros fichiers XML, l'approche de XML::Simple consistant à représenter le fichier entier en mémoire sous forme d'une structure de données 'arbre' peut ne pas être appropriée.

Qu'est-ce que le contenu mixte ?

Considérez cet exemple XML :

<document>
  <para>Ceci est du contenu <em>mixte</em>.</para>
</document>

On dit que c'est du contenu mixte, car l'élément <para> contient à la fois des données caractères (contenu texte) et des éléments imbriqués.

Voici un autre exemple XML :

<person>
  <first_name>Joe</first_name>
  <last_name>Bloggs</last_name>
  <dob>25-Avril-1969</dob>
</person>

Ce deuxième exemple n'est généralement pas considéré comme du contenu mixte. Les éléments <first_name>, <last_name> et <dob> ne contiennent que des données caractères et l'élément <person> ne contient que des éléments imbriqués. (Note : Strictement parlant, les espaces blancs entre les éléments imbriqués sont des données caractères, mais ils sont ignorés par XML::Simple).

Pourquoi XML::Simple ne gère-t-il pas le contenu mixte ?

Parce que s'il le faisait, il ne serait plus simple :-)

Plus sérieusement, il existe de nombreux excellents modules qui vous permettent de travailler avec du contenu mixte de diverses manières. Gérer le contenu mixte correctement n'est pas facile et en ignorant ces problèmes, XML::Simple est capable de présenter une API sans courbe d'apprentissage abrupte.

Quels modules Perl gèrent le contenu mixte ?

Tous sauf XML::Simple :-)

Si vous cherchez une recommandation, je vous suggère de consulter la FAQ Perl-XML à l'adresse :

http://perl-xml.sourceforge.net/faq/

Installation

Comment installer XML::Simple ?

Si vous utilisez ActiveState Perl ou Strawberry Perl http://strawberryperl.com/, vous avez probablement déjà XML::Simple et n'avez donc pas besoin de l'installer du tout. Mais vous avez probablement aussi XML::LibXML, qui est un bien meilleur module, alors utilisez simplement celui-ci.

Si vous avez besoin d'installer XML::Simple, vous devrez d'abord installer un module d'analyse XML. Installez XML::Parser (que vous avez peut-être déjà) ou XML::SAX. Si vous installez les deux, XML::SAX sera utilisé par défaut.

Une fois que vous avez un analyseur installé...

Sur les systèmes Unix, essayez :

perl -MCPAN -e 'install XML::Simple'

Si cela ne fonctionne pas, téléchargez la dernière distribution depuis ftp://ftp.cpan.org/pub/CPAN/authors/id/G/GR/GRANTM , décompressez-la et exécutez ces commandes :

perl Makefile.PL
make
make test
make install

Sur Win32, si vous avez une version récente d'ActiveState Perl (618 ou meilleure), essayez cette commande :

ppm install XML::Simple

Si cela ne fonctionne pas, vous n'avez vraiment besoin que du fichier Simple.pm, alors extrayez-le du fichier .tar.gz (par exemple, en utilisant WinZIP) et enregistrez-le dans le répertoire \site\lib\XML sous votre installation Perl (typiquement C:\Perl).

J'essaie d'installer XML::Simple et 'make test' échoue

Le répertoire où vous avez décompressé XML::Simple est-il monté depuis un serveur de fichiers utilisant NFS, SMB ou un autre partage de fichiers réseau ? Si oui, cela peut causer des erreurs dans les scripts de test suivants :

3_Storable.t
4_MemShare.t
5_MemCopy.t

La suite de tests est conçue pour tester les conditions limites de toutes les fonctionnalités de XML::Simple et ces trois scripts testent les fonctions de mise en cache. Si XML::Simple est invité à analyser un fichier pour lequel il a une copie mise en cache d'une analyse précédente, il compare l'horodatage du fichier XML avec l'horodatage de la copie mise en cache. Si la copie mise en cache est *plus récente*, elle sera utilisée. Si la copie mise en cache est plus ancienne ou du même âge, le fichier est réanalysé. Les scripts de test seront confus par les systèmes de fichiers réseau si les horloges des systèmes client et serveur ne sont pas synchronisées (à la seconde près).

Si vous obtenez une erreur dans l'un de ces trois scripts de test, mais que vous n'avez pas l'intention d'utiliser les options de mise en cache (elles ne sont pas activées par défaut), alors allez-y et exécutez 'make install'. Si vous avez l'intention d'utiliser la mise en cache, essayez de décompresser la distribution sur un disque local et d'effectuer la construction/le test là-bas.

Il n'est probablement pas judicieux d'utiliser les options de mise en cache avec des systèmes de fichiers réseau en production. Si l'horloge du serveur de fichiers est en avance sur l'horloge locale, XML::Simple réanalysera les fichiers alors qu'il aurait pu utiliser la copie mise en cache. Cependant, si l'horloge locale est en avance sur l'horloge du serveur de fichiers et qu'un fichier est modifié immédiatement après avoir été mis en cache, l'ancienne copie mise en cache sera utilisée.

Pourquoi XML::Simple est-il si lent ?

Si vous trouvez que XML::Simple est très lent à lire du XML, la raison la plus probable est que vous avez installé XML::SAX mais aucun module analyseur SAX supplémentaire. La distribution XML::SAX inclut un analyseur XML écrit entièrement en Perl. Il est très portable mais pas très rapide. Pour de meilleures performances, installez XML::SAX::Expat ou XML::LibXML.

Utilisation

Comment utiliser XML::Simple ?

Si vous ne savez pas comment utiliser XML::Simple, la meilleure approche est d'apprendre plutôt à utiliser XML::LibXML à l'adresse http://grantm.github.io/perl-libxml-by-example/. Arrêtez de lire ce document et utilisez plutôt celui-ci.

Si vous êtes déterminé à utiliser XML::Simple, il est livré avec une documentation abondante, alors lisez-la.

Il y a tellement d'options, lesquelles dois-je vraiment connaître ?

Bien que vous puissiez vous en sortir sans utiliser aucune option, vous ne devriez même pas envisager d'utiliser XML::Simple en production tant que vous ne savez pas ce que font ces deux options :

  • forcearray
  • keyattr

La raison pour laquelle vous devez absolument les lire est que les valeurs par défaut de ces options vous piégeront si vous ne le faites pas. Bien que tout le monde s'accorde à dire que ces valeurs par défaut ne sont pas idéales, il n'y a pas de consensus sur la façon de les modifier. La réponse est donc de les lire (voir ci-dessous) et de choisir les valeurs qui vous conviennent.

Qu'est-ce que l'option forcearray ?

Considérez ce XML dans un fichier appelé ./person.xml :

<person>
  <first_name>Joe</first_name>
  <last_name>Bloggs</last_name>
  <hobbie>saut à l'élastique</hobbie>
  <hobbie>parachutisme</hobbie>
  <hobbie>tricot</hobbie>
</person>

Vous pourriez le lire avec cette ligne :

my $person = XMLin('./person.xml');

Ce qui vous donnerait une structure de données comme celle-ci :

$person = {
  'first_name' => 'Joe',
  'last_name'  => 'Bloggs',
  'hobbie'     => [ 'saut à l\'élastique', 'parachutisme', 'tricot' ]
};

Les éléments <first_name> et <last_name> sont représentés comme des valeurs scalaires simples auxquelles vous pourriez faire référence comme ceci :

print "$person->{first_name} $person->{last_name}\n";

Les éléments <hobbie> sont représentés comme un tableau - car il y en a plus d'un. Vous pourriez faire référence au premier comme ceci :

print $person->{hobbie}->[0], "\n";

Ou à tous comme ceci :

print join(', ', @{$person->{hobbie}} ), "\n";

Le hic, c'est que ces deux dernières lignes de code ne fonctionneront que pour les personnes qui ont plus d'un passe-temps. S'il n'y a qu'un seul élément <hobbie>, il sera représenté comme une valeur scalaire simple (comme <first_name> et <last_name>). Ce qui pourrait vous amener à écrire du code comme ceci :

if(ref($person->{hobbie})) {
  print join(', ', @{$person->{hobbie}} ), "\n";
}
else {
  print $person->{hobbie}, "\n";
}

Ne faites pas ça.

Une approche alternative consiste à définir l'option forcearray sur une valeur vraie :

my $person = XMLin('./person.xml', forcearray => 1);

Ce qui vous donnera une structure de données comme celle-ci :

$person = {
  'first_name' => [ 'Joe' ],
  'last_name'  => [ 'Bloggs' ],
  'hobbie'     => [ 'saut à l\'élastique', 'parachutisme', 'tricot' ]
};

Vous pouvez alors utiliser cette ligne pour faire référence à toute la liste des passe-temps, même s'il n'y en avait qu'un seul :

print join(', ', @{$person->{hobbie}} ), "\n";

L'inconvénient de cette approche est que les éléments <first_name> et <last_name> seront également toujours représentés comme des tableaux, même s'il n'y en aura jamais qu'un seul :

print "$person->{first_name}->[0] $person->{last_name}->[0]\n";

Cela pourrait être acceptable si vous modifiez le XML pour utiliser des attributs pour les choses qui seront toujours singulières et des éléments imbriqués pour les choses qui peuvent être plurielles :

<person first_name="Jane" last_name="Bloggs">
  <hobbie>maintenance de moto</hobbie>
</person>

D'un autre côté, si vous préférez ne pas utiliser d'attributs, vous pourriez spécifier que tous les éléments <hobbie> doivent toujours être représentés sous forme de tableaux et que tous les autres éléments imbriqués doivent être des valeurs scalaires simples, sauf s'il y en a plus d'un :

my $person = XMLin('./person.xml', forcearray => [ 'hobbie' ]);

L'option forcearray accepte une liste de noms d'éléments qui doivent toujours être forcés à une représentation de tableau :

forcearray => [ qw(hobbie qualification nom_enfant) ]

Consultez la page de manuel de XML::Simple pour plus d'informations.

Qu'est-ce que l'option keyattr ?

Considérez cet exemple de XML :

<catalog>
  <part partnum="1842334" desc="Bride haute pression" price="24.50" />
  <part partnum="9344675" desc="Joint fileté"      price="9.25" />
  <part partnum="5634896" desc="Rondelle basse tension"   price="12.00" />
</catalog>

Vous pourriez le charger avec ce code :

my $catalog = XMLin('./catalog.xml');

Ce qui renverrait une structure de données comme celle-ci :

$catalog = {
    'part' => [
        {
          'partnum' => '1842334',
          'desc'    => 'Bride haute pression',
          'price'   => '24.50'
        },
        {
          'partnum' => '9344675',
          'desc'    => 'Joint fileté',
          'price'   => '9.25'
        },
        {
          'partnum' => '5634896',
          'desc'    => 'Rondelle basse tension',
          'price'   => '12.00'
        }
    ]
};

Vous pourriez alors accéder à la description de la première pièce du catalogue avec ce code :

print $catalog->{part}->[0]->{desc}, "\n";

Cependant, si vous vouliez accéder à la description de la pièce avec le numéro de pièce "9344675", vous devriez coder une boucle comme celle-ci :

foreach my $part (@{$catalog->{part}}) {
  if($part->{partnum} eq '9344675') {
    print $part->{desc}, "\n";
    last;
  }
}

La connaissance que chaque élément <part> a un attribut partnum unique vous permet d'éliminer cette recherche. Vous pouvez transmettre cette connaissance à XML::Simple comme ceci :

my $catalog = XMLin($xml, keyattr => ['partnum']);

Ce qui renverra une structure de données comme celle-ci :

$catalog = {
  'part' => {
    '5634896' => { 'desc' => 'Rondelle basse tension',   'price' => '12.00' },
    '1842334' => { 'desc' => 'Bride haute pression', 'price' => '24.50' },
    '9344675' => { 'desc' => 'Joint fileté',      'price' => '9.25'  }
  }
};

XML::Simple a été capable de transformer $catalog->{part} d'un tableau (arrayref) en un hachage (hashref) (indexé par partnum). Cette transformation est appelée 'repli de tableau' (array folding).

Grâce à l'utilisation du repli de tableau, vous pouvez maintenant accéder directement à la description de la pièce que vous souhaitez :

print $catalog->{part}->{9344675}->{desc}, "\n";

L'option 'keyattr' permet également le repli de tableau lorsque la clé unique se trouve dans un élément imbriqué plutôt que dans un attribut. Par exemple :

<catalog>
  <part>
    <partnum>1842334</partnum>
    <desc>Bride haute pression</desc>
    <price>24.50</price>
  </part>
  <part>
    <partnum>9344675</partnum>
    <desc>Joint fileté</desc>
    <price>9.25</price>
  </part>
  <part>
    <partnum>5634896</partnum>
    <desc>Rondelle basse tension</desc>
    <price>12.00</price>
  </part>
</catalog>

Consultez la page de manuel de XML::Simple pour plus d'informations.

Alors quel est le piège avec 'keyattr' ?

Une chose à surveiller est que vous pourriez obtenir un repli de tableau même si vous ne fournissez pas l'option keyattr. La valeur par défaut de cette option est :

[ 'name', 'key', 'id']

Ce qui signifie que si vos éléments XML ont un attribut (ou un élément imbriqué) 'name', 'key' ou 'id', ils pourraient être regroupés sur ces valeurs. Cela signifie que vous pouvez profiter du repli de tableau simplement en choisissant judicieusement les noms d'attributs. D'un autre côté, si vous ne voulez vraiment aucun repli de tableau, vous devrez définir 'keyattr' sur une liste vide :

my $ref = XMLin($xml, keyattr => []);

Un deuxième 'piège' est que le repli de tableau ne fonctionne que sur les tableaux. Cela peut sembler évident, mais s'il n'y a qu'un seul enregistrement dans votre XML et que vous n'avez pas défini l'option 'forcearray', il ne sera pas représenté comme un tableau et, par conséquent, ne sera pas replié en un hachage. La morale est que si vous utilisez le repli de tableau, vous devriez toujours activer l'option forcearray.

Vous voudrez probablement être aussi spécifique que possible. Par exemple, la manière la plus sûre d'analyser l'exemple de <catalog> ci-dessus serait :

my $catalog = XMLin($xml, keyattr => { part => 'partnum'},
                          forcearray => ['part']);

En utilisant le hashref pour keyattr, vous pouvez spécifier que seuls les éléments <part> doivent être regroupés sur l'attribut 'partnum' (et que les éléments <part> ne doivent pas être regroupés sur tout autre attribut).

En fournissant une liste de noms d'éléments pour forcearray, vous vous assurez que le repli fonctionnera même s'il n'y a qu'un seul <part>. Vous vous assurez également que si la clé unique 'partnum' est fournie dans un élément imbriqué, cet élément ne sera pas non plus forcé à être un tableau.

Comment sais-je à quoi devrait ressembler ma structure de données ?

' >Comment savoir à quoi ressemble ma structure de données ?

Les règles sont assez simples :

  • chaque élément est représenté par une table de hachage
  • sauf s'il ne contient que du texte, auquel cas il sera une valeur scalaire simple
  • ou sauf s'il y a plus d'un élément du même nom, auquel cas ils seront représentés comme un tableau
  • sauf si vous avez activé le repliement de tableaux, auquel cas ils seront repliés dans une table de hachage
  • les éléments vides (pas de contenu texte et pas d'attributs) seront représentés soit par une table de hachage vide, une chaîne vide, soit par undef - selon la valeur de l'option 'suppressempty'.

En cas de doute, utilisez Data::Dumper, par exemple :

use XML::Simple;
use Data::Dumper;
my $ref = XMLin($xml);
print Dumper($ref);

Je reçois des avertissements « Use of uninitialized value »

Vous essayez probablement d'indexer une clé de table de hachage inexistante - essayez Data::Dumper.

Je reçois une erreur « Not an ARRAY reference »

Quelque chose que vous attendiez comme étant un tableau ne l'est pas. Les deux causes les plus probables sont que vous avez oublié d'utiliser 'forcearray' ou que le tableau a été replié dans une table de hachage - essayez Data::Dumper.

Je reçois une erreur « No such array field »

Quelque chose que vous attendiez comme étant une table de hachage est en fait un tableau. Peut-être que le repliement de tableau a échoué parce qu'un élément manquait l'attribut clé - essayez Data::Dumper.

Je reçois une erreur « Out of memory »

Quelque chose dans la structure de données n'est pas ce que vous attendez et Perl essaie peut-être sans succès d'autovivifier des choses - essayez Data::Dumper.

Si vous utilisez déjà Data::Dumper, essayez d'appeler Dumper() immédiatement après XMLin() - c'est-à-dire : avant de tenter d'accéder à quoi que ce soit dans la structure de données.

Mon ordre d'éléments est bouleversé

Si vous lisez un fichier XML avec XMLin() puis le réécrivez avec XMLout(), l'ordre des éléments sera probablement différent. (Cependant, si vous relisez le fichier avec XMLin(), vous obtiendrez la même structure de données Perl).

Le réarrangement se produit parce que XML::Simple utilise des tables de hachage pour stocker vos données et que les tables de hachage Perl n'ont pas vraiment d'ordre.

Il est possible qu'une future version de XML::Simple utilise Tie::IxHash pour stocker les données dans des tables de hachage qui conservent l'ordre. Cependant, cela ne corrigera pas tous les cas de perte d'ordre des éléments.

Si votre application est vraiment sensible à l'ordre des éléments, n'utilisez pas XML::Simple (et ne mettez pas de valeurs sensibles à l'ordre dans les attributs).

XML::Simple transforme les éléments imbriqués en attributs

Si vous lisez un fichier XML avec XMLin() puis le réécrivez avec XMLout(), certaines données qui étaient initialement stockées dans des éléments imbriqués peuvent se retrouver dans des attributs. (Cependant, si vous relisez le fichier avec XMLin(), vous obtiendrez la même structure de données Perl).

Il y a un certain nombre de façons dont vous pourriez gérer cela :

  • utilisez l'option 'forcearray' avec XMLin()
  • utilisez l'option 'noattr' avec XMLout()
  • acceptez-le
  • n'utilisez pas XML::Simple

Pourquoi XMLout() insère-t-il des éléments (ou attributs) <nom>?

Essayez de définir keyattr => [].

Lorsque vous appelez XMLin() pour lire du XML, l'option 'keyattr' contrôle si les tableaux sont 'repliés' en tables de hachage. De même, lorsque vous appelez XMLout(), l'option 'keyattr' contrôle si les tables de hachage sont 'dépliées' en tableaux. Comme décrit ci-dessus, 'keyattr' est activé par défaut.

Pourquoi les éléments vides sont-ils représentés par des tables de hachage vides?

Un élément est toujours représenté par une table de hachage sauf s'il ne contient que du texte, auquel cas il est représenté par une chaîne scalaire.

Si vous préférez que les éléments vides soient représentés par des chaînes vides ou par la valeur non définie, définissez l'option 'suppressempty' à '' ou undef respectivement.

Pourquoi ParserOpts est-il obsolète?

L'option "ParserOpts" est un vestige de l'époque où XML::Simple ne fonctionnait qu'avec l'API XML::Parser. Sa valeur est complètement ignorée si vous utilisez un analyseur SAX, donc écrire du code qui s'en appuyait vous empêcherait de profiter de SAX.

Même si vous utilisez XML::Parser, il est rarement nécessaire de passer des options à l'objet analyseur. Un certain nombre de personnes ont écrit pour dire qu'elles utilisent cette option pour définir l'option "ProtocolEncoding" de XML::Parser. Ne faites pas cela, c'est faux, FAUX, FAUX ! Corrigez le document XML pour qu'il soit bien formé et vous n'aurez aucun problème.

Cela dit, tant que XML::Simple continuera à prendre en charge l'API XML::Parser, cette option ne sera pas supprimée. Il n'y a actuellement aucun plan pour supprimer la prise en charge de l'API XML::Parser.
