NOM

XML::SAX::Base - Classe de base pour les drivers et filtres SAX

SYNTAXE

package MonFiltre;
use XML::SAX::Base;
@ISA = ('XML::SAX::Base');

DESCRIPTION

Ce module a une tâche très simple : servir de classe de base pour les drivers et les filtres PerlSAX. Son comportement par défaut est de transmettre l'entrée directement à la sortie sans modification. Il peut être utile d'utiliser ce module comme classe de base afin de ne pas avoir, par exemple, à implémenter le callback characters().

Les principaux avantages qu'il procure sont la facilité de distribution des événements de la bonne manière (c'est-à-dire qu'il s'occupe de vérifier que le gestionnaire a implémenté cette méthode, ou a défini un AUTOLOAD), et la garantie que les filtres transmettront les événements qu'ils n'implémentent pas aux gestionnaires en aval qui pourraient néanmoins y être intéressés.

ÉCRIRE DES DRIVERS ET FILTRES SAX

La référence de l'API Perl Sax est disponible à l'adresse : http://perl-xml.sourceforge.net/perl-sax/.

Écrire des filtres SAX est extrêmement facile : il suffit d'hériter de ce module et de définir les événements que vous souhaitez gérer. Une explication plus détaillée peut être trouvée à l'adresse : http://www.xml.com/pub/a/2001/10/10/sax-filters.html.

Écrire des drivers est tout aussi simple. La seule chose à laquelle vous devez prêter attention est de ne pas appeler les événements vous-même (ce qui s'applique aussi aux filtres). Par exemple :

package MonFiltre;
use base qw(XML::SAX::Base);
sub start_element {
  my $self = shift;
  my $data = shift;
  # faire quelque chose
  $self->{Handler}->start_element($data); # MAUVAIS
}

L'exemple ci-dessus fonctionne très bien en tant que tel : un exemple. Mais il présente plusieurs défauts : 1) il ne vérifie pas si le gestionnaire définit start_element. Peut-être qu'il ne souhaite pas voir cet événement, auquel cas vous ne devriez pas le déclencher (sinon il mourra). 2) il ne vérifie pas ContentHandler puis Handler (c'est-à-dire qu'il ne regarde pas si l'utilisateur n'a pas demandé d'événements sur un gestionnaire spécifique, et sinon sur celui par défaut), 3) s'il vérifiait tout cela, non seulement le code serait fastidieux (voir le code source de ce module pour avoir une idée) mais il faudrait aussi probablement vérifier DocumentHandler (au cas où ce serait SAX1) et les AUTOLOADs potentiellement définis dans tous ces packages. Comme vous pouvez le constater, ce serait assez pénible. Au lieu de cela, souvenez-vous simplement d'utiliser un code similaire au suivant :

package MonFiltre;
use base qw(XML::SAX::Base);
sub start_element {
  my $self = shift;
  my $data = shift;
  # faire quelque chose pour filtrer
  $self->SUPER::start_element($data); # BON (et facile) !
}

De cette façon, une fois que vous avez fait votre travail, vous renvoyez la balle à XML::SAX::Base et il s'occupe de tous ces problèmes pour vous !

Notez que l'exemple ci-dessus ne s'applique pas uniquement aux filtres, les drivers bénéficieront de la même fonctionnalité exacte.

MÉTHODES

Un certain nombre de méthodes sont définies dans cette classe dans le but d'hériter. Certaines n'ont probablement pas besoin d'être redéfinies (par exemple parse_file) mais d'autres devraient clairement l'être (par exemple parse). Les options pour ces méthodes sont décrites dans la spécification PerlSAX2 disponible à l'adresse : http://cvs.sourceforge.net/cgi-bin/viewcvs.cgi/~checkout~/perl-xml/libxml-perl/doc/sax-2.0.html?rev=HEAD&content-type=text/html.

  • parse

    La méthode parse est le point d'entrée principal pour l'analyse des documents. En interne, la méthode parse détectera quel type de « chose » vous analysez et appellera la méthode appropriée dans votre classe d'implémentation. Voici le tableau de correspondance de ce qui se trouve dans les options Source (voir la spécification Perl SAX 2.0 pour la signification de ces valeurs) :

    Source Contient           parse() appelle
===============           =============
CharacterStream (*)       _parse_characterstream($stream, $options)
ByteStream                _parse_bytestream($stream, $options)
String                    _parse_string($string, $options)
SystemId                  _parse_systemid($string, $options)

    Cependant, notez que ces méthodes peuvent ne pas être pertinentes si votre classe de driver n'est pas destinée à l'analyse XML. Un exemple pourrait être un driver DBI qui génère du XML/SAX à partir d'une table de base de données. Si tel est le cas, vous voudrez probablement écrire votre propre méthode parse().

    Notez également que la Source peut contenir à la fois une entrée PublicId et une entrée Encoding. Pour y accéder, examinez $options->{Source} tel que passé à votre méthode.

    (*) Un CharacterStream est un descripteur de fichier qui n'a pas besoin de traduction d'encodage. Ceci est implémenté comme un descripteur de fichier régulier et ne fonctionne que sous Perl 5.7.2 ou supérieur en utilisant PerlIO. Pour obtenir un seul caractère, ou un nombre de caractères, utilisez la fonction core Perl read(). Pour obtenir un seul octet (ou un nombre d'octets), vous pouvez utiliser sysread(). L'encodage du flux doit se trouver dans l'entrée Encoding de la Source.

  • parse_file, parse_uri, parse_string

    Ce sont toutes des variations pratiques de parse(), et en fait, elles configurent simplement les options avant de l'appeler. Vous n'avez probablement pas besoin de redéfinir celles-ci.

  • get_options

    Ceci est une méthode utilitaire pour obtenir les options dans le style SAX2, ou plus génériquement soit sous forme de tables associatives soit sous forme de références de tables associatives (elle retourne une référence de table associative). Vous voudrez probablement utiliser cette méthode dans vos propres implémentations de parse() et de new().

  • get_feature, set_feature

    Celles-ci obtiennent et définissent simplement des fonctionnalités, et lèvent les exceptions appropriées définies dans la spécification si nécessaire.

    Si votre sous-classe définit des fonctionnalités non définies ici, vous devriez redéfinir ces méthodes de manière à ce qu'elles vérifient d'abord vos fonctionnalités, puis appellent les méthodes de la classe de base pour les fonctionnalités non définies par votre classe. Un exemple serait :

    sub get_feature {
    my $self = shift;
    my $feat = shift;
    if (exists $MY_FEATURES{$feat}) {
        # gérer la fonctionnalité de diverses manières
    }
    else {
        return $self->SUPER::get_feature($feat);
    }
}

    Actuellement, cette partie n'est pas implémentée.

  • set_handler

    Cette méthode prend un type de gestionnaire (Handler, ContentHandler, etc.) et un objet gestionnaire comme arguments, et change le gestionnaire actuel pour ce type de gestionnaire, tout en s'occupant de réinitialiser l'état interne qui doit être réinitialisé. Cela permet de changer un gestionnaire pendant l'analyse sans rencontrer de problèmes (le changer directement sur l'objet analyseur provoquera très probablement des problèmes).

  • set_document_handler, set_content_handler, set_dtd_handler, set_lexical_handler, set_decl_handler, set_error_handler, set_entity_resolver

    Ce ne sont que de simples enveloppes de la méthode précédente, et elles prennent un objet gestionnaire comme argument. En interne, elles appellent simplement set_handler avec les arguments corrects.

  • get_handler

    L'inverse de set_handler, cette méthode prend une chaîne optionnelle contenant un type de gestionnaire (DTDHandler, ContentHandler, etc. 'Handler' est utilisé si aucun type n'est passé). Elle retourne une référence à l'objet qui implémente cette classe, ou undef si ce type de gestionnaire n'est pas défini pour le driver/filtre actuel.

  • get_document_handler, get_content_handler, get_dtd_handler, get_lexical_handler, get_decl_handler, get_error_handler, get_entity_resolver

    Ce ne sont que de simples enveloppes de la méthode get_handler(), et elles ne prennent aucun argument. En interne, elles appellent simplement get_handler avec le nom correct du type de gestionnaire.

XML::SAX::BuildSAXBase - Perl module

NAME

XML::SAX::BuildSAXBase - Base classes for building SAX drivers and filters

SYNOPSIS

  use XML::SAX::Base;
  
  package My::SAX::Driver;
  
  @ISA = qw(XML::SAX::Base);
  
  sub new {
    my $class = shift;
    my %params = @_;
    my $self = $class->SUPER::new(%params);
    # ... driver-specific initialization ...
    return $self;
  }
  
  # ... implement SAX driver methods ...
  
  package My::SAX::Filter;
  
  @ISA = qw(XML::SAX::Base);
  
  sub new {
    my $class = shift;
    my %params = @_;
    my $self = $class->SUPER::new(%params);
    # ... filter-specific initialization ...
    return $self;
  }
  
  # ... implement SAX filter methods ...

DESCRIPTION

This module provides base classes for implementing both SAX drivers and SAX filters. SAX drivers are responsible for parsing an XML document and sending SAX events to a handler. SAX filters are themselves handlers, but they also pass events along to another handler (which might be another filter or the final driver).

By inheriting from XML::SAX::Base, you get a framework that handles the boilerplate of SAX event passing, allowing you to focus on the specific logic of your driver or filter.

WRITING SAX DRIVERS AND FILTERS

To write a SAX driver or filter, you should:

  • Make your package inherit from XML::SAX::Base.
  • Implement the constructor (new) to accept any driver/filter-specific parameters and to call the parent constructor (SUPER::new) with the parameters intended for the SAX driver/filter interface (e.g., Handler, Source).
  • Implement the necessary SAX event handler methods as defined by the XML::SAX::DocumentHandler, XML::SAX::ErrorHandler, XML::SAX::DTDHandler, and XML::SAX::DeclHandler interfaces.

The base class XML::SAX::Base provides default implementations for many of the SAX event methods. These defaults typically just pass the event along to the next handler in the chain (if any). You only need to override the methods that your driver or filter needs to process.
