XML::LibXML::Simple(3) Documentation Perl fournie par les utilisateurs XML::LibXML::Simple(3)

NOM

XML::LibXML::Simple - Clone de XML::LibXML de XML::Simple::XMLin()

HIÉRARCHIE

XML::LibXML::Simple
  est un Exporter

SYNOPSIS

my $xml  = ...;  # nom de fichier, fh, chaîne, ou nœud XML::LibXML

Impératif :

use XML::LibXML::Simple   qw(XMLin);
my $data = XMLin $xml, %options;

Ou la manière orientée objet :

use XML::LibXML::Simple   ();
my $xs   = XML::LibXML::Simple->new(%options);
my $data = $xs->XMLin($xml, %options);

DESCRIPTION

Ce module est une réécriture directe de XML::Simple (par Grant McLean) pour utiliser l'analyseur XML::LibXML pour les structures XML, là où l'original utilise des analyseurs Perl ou SAX bruts.

Attention : ce module pense être intelligent. Vous risquez fortement de vous tirer une balle dans le pied avec cette auto-correction (DWIMmery). Lisez entièrement cette page de manuel au moins une fois avant de commencer à l'utiliser. Si votre XML est décrit dans un schéma ou un WSDL, utilisez alors XML::Compile pour un code maintenable.

MÉTHODES

Constructeurs

XML::LibXML::Simple->new(%options)
Instancie un objet, qui peut être utilisé pour appeler XMLin(). Vous pouvez fournir %options à ce constructeur (à réutiliser pour chaque appel à XMLin) et avec chaque appel de XMLin (à utiliser une fois).

Pour la description des %options, voir la section "DÉTAILS" de cette page de manuel.

Traducteurs

$obj->XMLin($xmldata, %options)
Pour $xmldata et la description des %options, voir la section "DÉTAILS" de cette page de manuel.

FONCTIONS

Les fonctions "XMLin" (exportée implicitement) et "xml_in" (exportée sur demande) appellent simplement "<XML::LibXML::Simple-"new->XMLin() >> avec les paramètres fournis.

DÉTAILS

Paramètre $xmldata

Comme premier paramètre de XMLin(), vous devez fournir le message XML à traduire en une structure Perl. Choisissez l'une des options suivantes :

Un nom de fichier
Si le nom de fichier ne contient pas de composantes de répertoire, XMLin() cherchera le fichier dans chaque répertoire du chemin de recherche (voir OPTIONS ci-dessous) et dans le répertoire courant. Exemple : 
$data = XMLin('/etc/params.xml', %options);
Un tiret (-)
Analyse depuis STDIN. 
$data = XMLin('-', %options);
undef
[déprécié] S'il n'y a pas de spécificateur XML, XMLin() cherchera dans le répertoire du script et dans chacun des répertoires du chemin de recherche un fichier portant le même nom que le script mais avec l'extension '.xml'. Note : si vous souhaitez spécifier des options, vous devez spécifier la valeur 'undef'. Ex : 
$data = XMLin(undef, ForceArray => 1);

Cette fonctionnalité est disponible pour des raisons de compatibilité descendante avec XML::Simple, mais elle est très sensible. Vous pouvez facilement tomber sur le mauvais fichier xml en entrée. N'utilisez pas cette option : utilisez toujours un nom de fichier explicite.

Une chaîne XML
Une chaîne contenant du XML (reconnaissable à la présence des caractères '<' et '>') sera analysée directement. Ex : 
$data = XMLin('<opt username="bob" password="flurp" />', %options);
Un objet IO::Handle
Dans ce cas, XML::LibXML::Parser lira directement les données XML depuis le fichier fourni. 
# $fh = IO::File->new('/etc/params.xml') or die;
open my $fh, '<:encoding(utf8)', '/etc/params.xml' or die;
$data = XMLin($fh, %options);
Un XML::LibXML::Document ou ::Element
[Non disponible dans XML::Simple] Lorsque vous avez un nœud XML::LibXML pré-analysé, vous pouvez le passer.

Paramètre %options

XML::LibXML::Simple prend en charge la plupart des options définies par XML::Simple, l'interface est donc assez compatible. Des changements mineurs s'appliquent. Cette explication est extraite de la page de manuel de XML::Simple.

  • consultez "ForceArray" car vous voudrez presque certainement l'activer
  • assurez-vous de savoir ce que fait l'option "KeyAttr" et quelle est sa valeur par défaut, car elle pourrait autrement vous surprendre.
  • les noms d'options ne sont pas sensibles à la casse, vous pouvez donc utiliser les versions en casse mixte indiquées ici ; vous pouvez ajouter des traits d'union entre les mots (ex: key_attr) si vous le souhaitez.

Par ordre alphabétique :

ContentKey => 'nom_clé' # rarement utilisé
Lorsque le contenu texte est analysé comme une valeur de hachage, cette option vous permet de spécifier un nom pour la clé de hachage afin de remplacer le 'content' par défaut. Ainsi, par exemple : 
XMLin('<opt one="1">Two</opt>', ContentKey => 'text')

analysera vers :

{ one => 1, text => 'Two' }

au lieu de :

{ one => 1, content => 'Two' }

Vous pouvez également préfixer votre nom de clé choisi avec un caractère '-' pour que XMLin() essaie un peu plus fort d'éliminer les clés 'content' inutiles après le pliage de tableau. Par exemple :

XMLin(
  '<opt><item name="one">First</item><item name="two">Second</item></opt>',
  KeyAttr => {item => 'name'},
  ForceArray => [ 'item' ],
  ContentKey => '-content'
)

analysera vers :

{
   item => {
    one =>  'First'
    two =>  'Second'
  }
}

plutôt que ceci (sans le '-') :

{
  item => {
    one => { content => 'First' }
    two => { content => 'Second' }
  }
}
ForceArray => 1 # important
Cette option doit être définie à '1' pour forcer les éléments imbriqués à être représentés sous forme de tableaux, même lorsqu'il n'y en a qu'un seul. Exemple, avec ForceArray activé, ce XML : 
<opt>
  <name>value</name>
</opt>

analyserait vers ceci :

{ name => [ 'value' ] }

au lieu de ceci (la valeur par défaut) :

{ name => 'value' }

Cette option est particulièrement utile si la structure de données doit probablement être réécrite en XML et que le comportement par défaut de remontée des éléments imbriqués uniques en attributs n'est pas désirable.

Si vous utilisez la fonctionnalité de pliage de tableau, vous devriez presque certainement activer cette option. Sinon, les éléments imbriqués uniques ne seront pas analysés en tableaux et ne seront donc pas candidats au pliage en hachage. (Étant donné que la valeur par défaut de 'KeyAttr' active le pliage de tableau, la valeur par défaut de cette option aurait également dû être activée).

ForceArray => [ noms ] # important
Cette forme alternative (et préférée) de l'option 'ForceArray' vous permet de spécifier une liste de noms d'éléments qui seront toujours forcés en représentation de tableau, plutôt que l'approche 'tout ou rien' ci-dessus.

Il est également possible d'inclure des expressions régulières compilées dans la liste -- tous les noms d'éléments qui correspondent au modèle seront forcés en tableaux. Si la liste ne contient qu'une seule expression régulière, il n'est pas nécessaire de l'entourer d'une référence de tableau. Ex :

ForceArray => qr/_list

$/
ForceContent => 1 # rarement utilisé
Lorsque XMLin() analyse des éléments qui ont un contenu textuel ainsi que des attributs, le contenu textuel doit être représenté comme une valeur de hachage plutôt qu'un simple scalaire. Cette option vous permet de forcer le contenu textuel à être toujours analysé comme une valeur de hachage, même en l'absence d'attributs. Par exemple : 
XMLin('<opt><x>texte1</x><y a="2">texte2</y></opt>', ForceContent => 1)

analysera en :

{
  x => {         content => 'texte1' },
  y => { a => 2, content => 'texte2' }
}

au lieu de :

{
  x => 'texte1',
  y => { 'a' => 2, 'content' => 'texte2' }
}
GroupTags => { balise de regroupement => balise groupée } # pratique
Vous pouvez utiliser cette option pour éliminer des niveaux d'indirection supplémentaires dans votre structure de données Perl. Par exemple, ce XML : 
 <opt>
  <searchpath>
    <dir>/usr/bin</dir>
    <dir>/usr/local/bin</dir>
    <dir>/usr/X11/bin</dir>
  </searchpath>
</opt>

Serait normalement lu dans une structure comme celle-ci :

{
  searchpath => {
     dir => [ '/usr/bin', '/usr/local/bin', '/usr/X11/bin' ]
  }
}

Mais lors de la lecture avec la valeur appropriée pour 'GroupTags' :

my $opt = XMLin($xml, GroupTags => { searchpath => 'dir' });

Elle renverra cette structure plus simple :

{
  searchpath => [ '/usr/bin', '/usr/local/bin', '/usr/X11/bin' ]
}

L'élément de regroupement ("<searchpath>" dans l'exemple) ne doit pas contenir d'attributs ou d'éléments autres que l'élément groupé.

Vous pouvez spécifier plusieurs correspondances 'élément de regroupement' à 'élément groupé' dans le même hashref. Si cette option est combinée avec "KeyAttr", le pliage de tableau se produira d'abord, puis les noms des éléments groupés seront éliminés.

HookNodes => CODE
Sélectionne les nœuds du document pour appliquer des astuces spéciales. Introduit dans [0.96], non disponible dans XML::Simple.

Lorsque cette option est fournie, la CODE sera appelée une fois que l'arbre DOM XML sera prêt à être transformé en Perl. Votre CODE doit renvoyer soit "undef" (rien à faire), soit un HASH qui mappe les valeurs de unique_key (voir la méthode "unique_key" de XML::LibXML::Node) vers des références CODE à appeler.

Une fois que le traducteur de XML en Perl atteint un nœud sélectionné, il appellera votre routine spécifique à ce nœud. Ce nœud déclencheur trouvé est le seul paramètre. Lorsque vous renvoyez "undef", le nœud ne sera pas trouvé dans le résultat final. Vous pouvez renvoyer n'importe quelle donnée (même le nœud lui-même) qui sera incluse dans le résultat final telle quelle, sous le nom du nœud d'origine.

Exemple :

my $out = XMLin $file, HookNodes => \&protect_html;
sub protect_html($$)
{   # $obj est l'objet XML::Compile::Simple instancié
    # $xml est un XML::LibXML::Element à transformer
    my ($obj, $xml) = @_;
    my %hooks;    # collecte la table des hooks
    # effectue une recherche xpath pour HTML
    my $xpc   = XML::LibXML::XPathContext->new($xml);
    my @nodes = $xpc->findNodes(...); #XXX
    @nodes or return undef;
    my $as_text = sub { $_[0]->toString(0) };  # sous forme de texte
    #  $as_node = sub { $_[0] };               # sous forme de nœud
    #  $skip    = sub { undef };               # pas du tout
    # le même comportement pour tous les nœuds xpath, dans cet exemple
    $hook{$_->unique_key} = $as_text
        for @nodes;

    \%hook;
}
KeepRoot => 1 # pratique
Dans sa tentative de renvoyer une structure de données exempte de détails superflus et de niveaux d'indirection inutiles, XMLin() ignore normalement le nom de l'élément racine. La définition de l'option 'KeepRoot' à '1' entraînera la conservation du nom de l'élément racine. Ainsi, après avoir exécuté ce code : 
$config = XMLin('<config tempdir="/tmp" />', KeepRoot => 1)

Vous pourrez référencer tempdir comme "$config->{config}->{tempdir}" au lieu de par défaut "$config->{tempdir}".

KeyAttr => [ liste ] # important
Cette option contrôle la fonctionnalité de 'pliage de tableau' qui transforme les éléments imbriqués d'un tableau en hachage. Elle contrôle également le 'dépliage' des hachages en tableaux.

Par exemple, ce XML :

<opt>
  <user login="grep" fullname="Gary R Epstein" />
  <user login="stty" fullname="Simon T Tyson" />
</opt>

Serait, par défaut, analysé comme suit :

{
  user => [
     { login    => 'grep',
       fullname => 'Gary R Epstein'
     },
     { login    => 'stty',
       fullname => 'Simon T Tyson'
     }
  ]
}

Si l'option 'KeyAttr => "login"' était utilisée pour spécifier que l'attribut 'login' est une clé, le même XML serait analysé comme suit :

{
  user => {
     stty => { fullname => 'Simon T Tyson' },
     grep => { fullname => 'Gary R Epstein' }
  }
}

Les noms des attributs clés doivent être fournis dans un arrayref s'il y en a plus d'un. XMLin() tentera de faire correspondre les noms d'attributs dans l'ordre spécifié.

Note 1 : La valeur par défaut pour 'KeyAttr' est "['name', 'key', 'id']". Si vous ne souhaitez pas de pliage à l'entrée ou de dépliage à la sortie, vous devez définir cette option à une liste vide pour désactiver la fonctionnalité.

Note 2 : Si vous souhaitez utiliser cette option, vous devriez également activer l'option "ForceArray". Sans 'ForceArray', un seul élément imbriqué sera replié en un scalaire plutôt qu'en un tableau et ne sera donc pas plié (car seuls les tableaux sont pliés).

KeyAttr => { liste } # important
Cette méthode alternative (et préférée) de spécification des attributs clés permet un contrôle plus fin sur les éléments qui sont pliés et sur quels attributs. Par exemple, l'option 'KeyAttr => { package => 'id' } entraînera le pliage de tous les éléments package sur l'attribut 'id'. Aucun autre élément possédant un attribut 'id' ne sera plié du tout.

Deux variations supplémentaires sont rendues possibles en préfixant un caractère '+' ou '-' au nom de l'attribut :

L'option 'KeyAttr => { user => "+login" }' entraînera ce XML :

<opt>
  <user login="grep" fullname="Gary R Epstein" />
  <user login="stty" fullname="Simon T Tyson" />
</opt>

à analyser en cette structure de données :

{
  user => {
     stty => {
        fullname => 'Simon T Tyson',
        login    => 'stty'
     },
     grep => {
        fullname => 'Gary R Epstein',
        login    => 'grep'
     }
  }
}

Le '+' indique que la valeur de l'attribut clé doit être copiée plutôt que déplacée vers la clé du hachage plié.

Un préfixe '-' produirait ce résultat :

{
  user => {
     stty => {
        fullname => 'Simon T Tyson',
        -login   => 'stty'
     },
     grep => {
        fullname => 'Gary R Epstein',
        -login    => 'grep'
     }
  }
}
NoAttr => 1 # pratique
Lorsqu'il est utilisé avec XMLin(), tous les attributs du XML seront ignorés.
NormaliseSpace => 0 | 1 | 2 # pratique
Cette option contrôle la manière dont les espaces blancs dans le contenu textuel sont gérés. Les valeurs reconnues pour l'option sont :
"0"
(par défaut) les espaces blancs sont transmis tels quels (sauf bien sûr pour la normalisation des espaces blancs dans les valeurs d'attributs qui est prescrite par la recommandation XML)
"1"
les espaces blancs sont normalisés dans toute valeur utilisée comme clé de hachage (normaliser signifie supprimer les espaces blancs en début et fin de chaîne et remplacer les séquences d'espaces blancs par un seul espace)
"2"
les espaces blancs sont normalisés dans tout le contenu textuel

Note : vous pouvez épeler cette option avec un 'z' si cela vous semble plus naturel.

Parser => OBJET
Vous pouvez passer votre propre objet XML::LibXML, au lieu qu'un objet soit créé pour vous. Ceci est utile lorsque vous avez besoin d'une configuration spécifique sur cet objet (Voir XML::LibXML::Parser) ou que vous avez implémenté votre propre extension à cet objet.

L'objet parser créé en interne est configuré en mode sécurisé. Lisez le manuel XML::LibXML::Parser concernant les problèmes de sécurité avec certains paramètres. La valeur par défaut est non sécurisée !

ParserOpts => HASH|TABLEAU
Passe des paramètres à la création d'un nouvel objet parser interne. Vous pouvez outrepasser les options qui créent un parser sécurisé. Il peut être plus lisible d'utiliser le paramètre "Parser".
SearchPath => [ liste ] # pratique
Si vous passez un nom de fichier à XMLin(), mais que le nom de fichier n'inclut pas de composant de répertoire, vous pouvez utiliser cette option pour spécifier quels répertoires doivent être recherchés pour trouver le fichier. Vous pourriez utiliser cette option pour rechercher d'abord dans le répertoire personnel de l'utilisateur, puis dans un répertoire global comme /etc.

Si un nom de fichier est fourni à XMLin() mais que SearchPath n'est pas défini, le fichier est supposé être dans le répertoire courant.

Si le premier paramètre de XMLin() est indéfini, le SearchPath par défaut ne contiendra que le répertoire dans lequel le script lui-même est situé. Sinon, le SearchPath par défaut sera vide.

SuppressEmpty => 1 | '' | undef
[0.99] Que faire avec les éléments vides (pas d'attributs et pas de contenu). Le comportement par défaut est de les représenter comme des hachages vides. Définir
ce option à une valeur vraie (par exemple : 1) fera que les éléments vides seront ignorés complètement. Définir l'option à 'undef' ou à la chaîne vide fera que les éléments vides seront représentés par la valeur indéfinie ou la chaîne vide respectivement.
ValueAttr => [ names ] # pratique
Utilisez cette option pour traiter les éléments qui ont toujours un attribut unique et aucun contenu. Par exemple : 
<opt>
  <colour value="red" />
  <size   value="XXL" />
</opt>

Définir "ValueAttr => [ 'value' ]" fera que le XML ci-dessus sera analysé comme suit :

{
  colour => 'red',
  size   => 'XXL'
}

au lieu de ceci (par défaut) :

{
  colour => { value => 'red' },
  size   => { value => 'XXL' }
}
NsExpand => 0 recommandé
Lorsque des espaces de noms sont utilisés, le comportement par défaut consiste à inclure le préfixe dans le nom de la clé. Cependant, c'est très dangereux : les préfixes peuvent être modifiés sans changer la signification du message XML. Par conséquent, vous pouvez mieux utiliser cette option "NsExpand". L'inconvénient, cependant, est que les étiquettes deviennent très longues.

Sans cette option :

<record xmlns:x="http://xyz">
  <x:field1>42</x:field1>
</record>
<record xmlns:y="http://xyz">
  <y:field1>42</y:field1>
</record>

se traduit par

{ 'x:field1' => 42 }
{ 'y:field1' => 42 }

mais les deux composants sources ont exactement le même sens. Lorsque "NsExpand" est utilisé, le résultat est :

{ '{http://xyz}field1' => 42 }
{ '{http://xyz}field1' => 42 }

Bien sûr, accéder à ces champs demande plus de travail. Il est recommandé de l'implémenter comme suit :

my $ns = 'http://xyz';
$data->{"{$ns}field1"};
NsStrip => 0 code négligé
[non disponible dans XML::Simple] Les espaces de noms sont très importants pour éviter les collisions de noms, mais ils sont un peu gênants. Pour le faire correctement, utilisez l'option "NsExpand". Pour le faire négligemment, utilisez "NsStrip". Avec cette option activée, l'exemple ci-dessus renverra 
{ field1 => 42 }
{ field1 => 42 }

EXEMPLES

Lorsque XMLin() lit le morceau de XML très simple suivant :

<opt username="testuser" password="frodo"></opt>

il renvoie la structure de données suivante :

{
  username => 'testuser',
  password => 'frodo'
}

Le résultat identique aurait pu être produit avec le XML alternatif suivant :

<opt username="testuser" password="frodo" />

Ou ceci (bien que voir l'option 'ForceArray' pour les variations) :

<opt>
  <username>testuser</username>
  <password>frodo</password>
</opt>

Les éléments imbriqués répétés sont représentés sous forme de tableaux anonymes :

<opt>
  <person firstname="Joe" lastname="Smith">
    <email>joe@smith.com</email>
    <email>jsmith@yahoo.com</email>
  </person>
  <person firstname="Bob" lastname="Smith">
    <email>bob@smith.com</email>
  </person>
</opt>
{
  person => [
    { email     => [ 'joe@smith.com', 'jsmith@yahoo.com' ],
      firstname => 'Joe',
      lastname  => 'Smith'
    },
    { email     => 'bob@smith.com',
      firstname => 'Bob',
      lastname  => 'Smith'
    }
  ]
}

Les éléments imbriqués avec un attribut clé reconnu sont transformés (pliés) d'un tableau en une table indexée sur la valeur de cet attribut (voir l'option "KeyAttr") :

<opt>
  <person key="jsmith" firstname="Joe" lastname="Smith" />
  <person key="tsmith" firstname="Tom" lastname="Smith" />
  <person key="jbloggs" firstname="Joe" lastname="Bloggs" />
</opt>
{
  person => {
     jbloggs => {
        firstname => 'Joe',
        lastname  => 'Bloggs'
     },
     tsmith  => {
        firstname => 'Tom',
        lastname  => 'Smith'
     },
     jsmith => {
        firstname => 'Joe',
        lastname => 'Smith'
     }
  }
}

La balise <anon> peut être utilisée pour former des tableaux anonymes :

<opt>
  <head><anon>Col 1</anon><anon>Col 2</anon><anon>Col 3</anon></head>
  <data><anon>R1C1</anon><anon>R1C2</anon><anon>R1C3</anon></data>
  <data><anon>R2C1</anon><anon>R2C2</anon><anon>R2C3</anon></data>
  <data><anon>R3C1</anon><anon>R3C2</anon><anon>R3C3</anon></data>
</opt>
{
  head => [ [ 'Col 1', 'Col 2', 'Col 3' ] ],
  data => [ [ 'R1C1', 'R1C2', 'R1C3' ],
            [ 'R2C1', 'R2C2', 'R2C3' ],
            [ 'R3C1', 'R3C2', 'R3C3' ]
          ]
}

Les tableaux anonymes peuvent être imbriqués à des niveaux arbitraires et, en particulier, si les balises environnantes d'un document XML ne contiennent qu'un tableau anonyme, la référence au tableau sera directement retournée au lieu de la référence habituelle à la table :

<opt>
  <anon><anon>Col 1</anon><anon>Col 2</anon></anon>
  <anon><anon>R1C1</anon><anon>R1C2</anon></anon>
  <anon><anon>R2C1</anon><anon>R2C2</anon></anon>
</opt>
[
  [ 'Col 1', 'Col 2' ],
  [ 'R1C1', 'R1C2' ],
  [ 'R2C1', 'R2C2' ]
]

Les éléments qui ne contiennent que du contenu textuel seront simplement représentés comme un scalaire. Lorsqu'un élément a à la fois des attributs et du contenu textuel, l'élément sera représenté comme une table indexée avec le contenu textuel dans la clé 'content' (voir l'option "ContentKey") :

<opt>
  <one>first</one>
  <two attr="value">second</two>
</opt>
{
  one => 'first',
  two => { attr => 'value', content => 'second' }
}

Le contenu mixte (éléments contenant à la fois du contenu textuel et des éléments imbriqués) ne sera pas représenté de manière utile - l'ordre des éléments et les espaces blancs significatifs seront perdus. Si vous avez besoin de travailler avec du contenu mixte, alors XML::Simple n'est pas le bon outil pour votre travail - consultez la section suivante.

Différences avec XML::Simple

En général, la sortie et les options sont équivalentes, bien que ce module présente quelques différences avec XML::Simple dont il faut être conscient.

seul XMLin() est supporté
Si vous voulez écrire du XML, utilisez un schéma (par exemple avec XML::Compile). N'essayez pas de créer du XML à la main ! Si vous pensez toujours en avoir besoin, jetez un œil à XMLout() tel qu'implémenté par XML::Simple ou l'un des innombrables systèmes de modèles.
pas d'option "variables"
Selon moi, vous devriez utiliser un système de modèles si vous souhaitez que des variables soient remplies dans l'entrée : ce n'est pas la tâche de ce module.
options ForceArray
Il existe quelques petites différences dans le résultat de l'option "forcearray", car XML::Simple semble se comporter de manière inconsistante.
hooks
XML::Simple ne supporte pas les hooks.
