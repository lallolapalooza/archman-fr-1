NOM

XML::Twig - Un module Perl pour traiter d'énormes documents XML en mode arbre.

SYNOPIS

Notez que cette documentation est destinée à servir de référence pour le module.

La documentation complète, y compris un tutoriel, des exemples, une version HTML plus facile à utiliser, une carte de référence rapide et une FAQ sont disponibles à l'adresse http://www.xmltwig.org/xmltwig.

Petits documents (chargés en mémoire sous forme d'arbre) :

my $twig=XML::Twig->new();    # crée le twig
$twig->parsefile( 'doc.xml'); # le construit
my_process( $twig);           # utilise les méthodes de twig pour le traiter
$twig->print;                 # affiche le twig

Grands documents (traités en mode flux/arbre combiné) :

# au maximum un div sera chargé en mémoire
my $twig=XML::Twig->new(
  twig_handlers =>
    { title   => sub { $_->set_tag( 'h2') }, # change les balises title en h2
                                             # $_ est l'élément courant
      para    => sub { $_->set_tag( 'p')  }, # change para en p
      hidden  => sub { $_->delete;       },  # supprime les éléments hidden
      list    => \&my_list_process,          # traite les éléments list
      div     => sub { $_[0]->flush;     },  # affiche et libère la mémoire
    },
  pretty_print => 'indented',                # la sortie sera joliment formatée
  empty_tags   => 'html',                    # affiche <empty_tag />
                       );
$twig->parsefile( 'my_big.xml');
sub my_list_process
  { my( $twig, $list)= @_;
    # ...
  }

Voir XML::Twig 101 pour d'autres façons d'utiliser le module, par exemple comme filtre.

DESCRIPTION

Ce module fournit un moyen de traiter les documents XML. Il est basé sur "XML::Parser".

Le module offre une interface arborescente au document, tout en vous permettant de sortir les parties qui ont été complètement traitées.

Il permet une utilisation minimale des ressources (CPU et mémoire) en construisant l'arbre uniquement pour les parties des documents qui nécessitent un traitement réel, grâce à l'utilisation des options "twig_roots " et "twig_print_outside_roots ". Les méthodes "finish " et "finish_print " contribuent également à augmenter les performances.

XML::Twig essaie de faciliter les choses simples, il fait donc de son mieux pour prendre en charge bon nombre des fonctionnalités (généralement) ennuyeuses (mais parfois nécessaires) qui accompagnent XML et XML::Parser.

OUTILS

XML::Twig est livré avec quelques utilitaires en ligne de commande :

xml_pp - joli-imprimeur XML

Joli-impression XML utilisant XML::Twig.

xml_grep - rechercher dans les fichiers XML des éléments spécifiques

"xml_grep" effectue une recherche dans les fichiers XML. Au lieu d'utiliser des expressions régulières, il utilise des expressions XPath (en fait, le sous-ensemble d'XPath pris en charge par XML::Twig).

xml_split - découper un gros fichier XML en plus petits morceaux

"xml_split" prend un fichier XML (vraisemblablement grand) et le divise en plusieurs fichiers plus petits, en fonction de divers critères (niveau dans l'arbre, taille ou une expression XPath).

xml_merge - fusionner les fichiers XML découpés avec xml_split

"xml_merge" prend plusieurs fichiers XML qui ont été découpés à l'aide de "xml_split" et recrée un seul fichier.

xml_spellcheck - vérifier l'orthographe des fichiers XML

"xml_spellcheck" vous permet de vérifier l'orthographe du contenu d'un fichier XML. Il extrait le texte (le contenu des éléments et éventuellement des attributs), appelle un correcteur orthographique dessus, puis recrée le document XML.

XML::Twig 101

XML::Twig peut être utilisé soit sur des documents XML "petits" (qui tiennent en mémoire), soit sur d'énormes documents en traitant des parties du document et en les affichant ou en les supprimant une fois qu'elles ont été traitées.

Chargement d'un document XML et son traitement

my $t= XML::Twig->new();
$t->parse( '<d><title>titre</title><para>p 1</para><para>p 2</para></d>');
my $root= $t->root;
$root->set_tag( 'html');              # change doc en html
$title= $root->first_child( 'title'); # obtient le titre
$title->set_tag( 'h1');               # le transforme en h1
my @para= $root->children( 'para');   # obtient les enfants para
foreach my $para (@para)
  { $para->set_tag( 'p'); }           # les transforme en p
$t->print;                            # affiche le document

D'autres méthodes utiles incluent :

att : "$elt->att( 'foo')" retourne l'attribut "foo" d'un élément,

set_att : "$elt->set_att( foo => "bar")" définit l'attribut "foo" à la valeur "bar",

next_sibling : "$elt->next_sibling" retourne le frère suivant dans le document (dans l'exemple "$title->next_sibling" est le premier "para", vous pouvez également (et devriez même) utiliser "$elt->next_sibling( 'para')" pour l'obtenir.

Le document peut également être transformé par l'utilisation des méthodes cut, copy, paste et move : "$title->cut; $title->paste( after => $p);" par exemple.

Et bien plus encore, voir XML::Twig::Elt.

Traitement d'un document XML morceau par morceau

L'une des forces de XML::Twig est qu'il vous permet de travailler avec des fichiers qui ne tiennent pas en mémoire. Stocker un document XML en mémoire sous forme d'arbre est assez coûteux en mémoire ; le facteur d'expansion étant souvent d'environ 10x.

Pour ce faire, vous pouvez définir des gestionnaires qui seront appelés une fois qu'un élément spécifique aura été complètement analysé (fermé). Dans ces gestionnaires, vous pouvez accéder à l'élément et le traiter comme bon vous semble, en utilisant la navigation et les méthodes cut/copy/paste, plus de nombreuses méthodes pratiques comme "prefix ". Une fois l'élément complètement traité, vous pouvez alors le "flush ", ce qui affiche l'élément et libère sa mémoire. Vous pouvez également le "purge " si vous n'avez pas besoin de l'afficher (si vous extrayez seulement des données du document, par exemple). Le gestionnaire sera appelé à nouveau une fois que le prochain élément pertinent aura été analysé.

my $t= XML::Twig->new( twig_handlers =>
                        { section => \&section,
                          para   => sub { $_->set_tag( 'p'); }
                        },
                     );
$t->parsefile( 'doc.xml');
# le gestionnaire est appelé une fois qu'une section est complètement analysée, c'est-à-dire lorsque
# la balise de fin pour section est trouvée, il reçoit le twig lui-même et
# l'élément (y compris tous ses sous-éléments) en arguments
sub section
  { my( $t, $section)= @_;      # arguments pour tous les twig_handlers
    $section->set_tag( 'div');  # change le nom de la balise
    # utilisons l'attribut nb comme préfixe pour le titre
    my $title= $section->first_child( 'title'); # trouve le titre
    my $nb= $title->att( 'nb'); # obtient l'attribut
    $title->prefix( "$nb - ");  # facile, non ?
    $section->flush;            # affiche la section et libère la mémoire
  }

Lorsqu'un gestionnaire est appelé, $_ contient l'élément correspondant au gestionnaire.

Vous pouvez déclencher h

et handler pour des conditions plus élaborées. Ce gestionnaire ne correspond qu'aux éléments "title" qui se trouvent dans des éléments "section" :

my $t= XML::Twig->new( twig_handlers =>
                         { 'section/title' => sub { $_->print } }
                     )
                ->parsefile( 'doc.xml');

Ici, "sub { $_->print }" imprime simplement l'élément courant.

Les gestionnaires peuvent également tester la présence ou le contenu des attributs :

my $t= XML::Twig->new( twig_handlers =>
                    { 'section[@level="1" or @force]' => sub { $_->print } }
                     );
                ->parsefile( 'doc.xml');

Vous pouvez également utiliser "start_tag_handlers " pour traiter un élément dès que sa balise ouvrante est trouvée.

Traitement de seulement certaines parties d'un document XML

Le mode "twig_roots" ne construit que les sous-arbres requis du document. Tout ce qui se trouve en dehors des racines de la brindille est ignoré :

my $t= XML::Twig->new(
     # la brindille n'inclura que la racine et les titres sélectionnés
         twig_roots   => { 'section/title' => \&print_n_purge,
                           'annex/title'   => \&print_n_purge
         }
                    );
$t->parsefile( 'doc.xml');
sub print_n_purge
  { my( $t, $elt)= @_;
    print $elt->text;    # imprime le texte (y compris les textes des sous-éléments)
    $t->purge;           # libère la mémoire
  }

Vous pouvez utiliser ce mode lorsque vous souhaitez traiter des parties d'un document mais que le reste ne vous intéresse pas et que vous ne souhaitez pas en payer le prix, que ce soit en temps ou en mémoire, pour construire l'arbre correspondant.

Construction d'un filtre XML

Vous pouvez combiner les options "twig_roots" et "twig_print_outside_roots" pour construire des filtres, qui vous permettent de modifier des éléments sélectionnés et de produire le reste du document tel quel.

Ceci convertirait les prix en $ en prix en Euros dans un document :

my $t= XML::Twig->new(
         twig_roots   => { 'price' => \&convert, },   # traite les prix
         twig_print_outside_roots => 1,               # imprime le reste
                    );
$t->parsefile( 'doc.xml');
sub convert
  { my( $t, $price)= @_;
    my $currency=  $price->att( 'currency');          # obtient la devise
    if( $currency eq 'USD')
      { $usd_price= $price->text;                     # obtient le prix
        # %rate est juste une table de conversion
        my $euro_price= $usd_price * $rate{usd2euro};
        $price->set_text( $euro_price);               # définit le nouveau prix
        $price->set_att( currency => 'EUR');          # n'oubliez pas celui-ci !
      }
    $price->print;                                    # imprime le prix
  }

XML::Twig et diverses versions de Perl, XML::Parser et expat :

XML::Twig est beaucoup plus sensible aux variations des versions de Perl, XML::Parser et expat qu'à l'OS, donc cela devrait couvrir des configurations raisonnables.

La "configuration recommandée" est perl 5.10.0+ (pour une bonne prise en charge Unicode), XML::Parser 2.31+, et expat 1.95.5+.

Consultez <http://testers.cpan.org/search?request=dist&dist=XML-Twig> pour les rapports des testeurs CPAN sur XML::Twig, qui listent toutes les configurations testées.

Un flux Atom des résultats des testeurs CPAN est disponible à l'adresse http://xmltwig.org/rss/twig_testers.rss.

Enfin :

XML::Twig ne fonctionne PAS avec expat 1.95.4.
XML::Twig ne fonctionne qu'avec XML::Parser 2.27 dans perl 5.10.0+.
Notez que je ne peux plus compiler XML::Parser 2.27, je ne peux donc pas garantir qu'il fonctionne toujours.
XML::Parser 2.28 ne fonctionne pas vraiment.

En cas de doute, mettez à jour expat, XML::Parser et Scalar::Util.

Enfin, pour certaines fonctionnalités optionnelles, XML::Twig dépend de modules supplémentaires. La liste complète, qui dépend quelque peu de la version de Perl que vous utilisez, est obtenue en exécutant "t/zz_dump_config.t".

Simplification du traitement XML

Espaces blancs
Les espaces blancs qui semblent non significatifs sont écartés. Ce comportement peut être contrôlé à l'aide des options "keep_spaces ", "keep_spaces_in " et "discard_spaces_in ".
Encodage
Vous pouvez spécifier que vous souhaitez que la sortie soit dans le même encodage que l'entrée (à condition d'avoir du XML valide, ce qui signifie que vous devez spécifier l'encodage soit dans le document, soit lors de la création de l'objet Twig) en utilisant l'option "keep_encoding ".

Vous pouvez également utiliser "output_encoding " pour convertir le format interne UTF-8 vers l'encodage requis.

Commentaires et Instructions de Traitement (PI)
Les commentaires et les PI peuvent être masqués du traitement, mais apparaître toujours dans la sortie (ils sont portés par l'élément "réel" le plus proche d'eux). Ou bien, ils peuvent être rendus disponibles pour le traitement en tant qu'éléments "#COMMENT" et "#PI".
Mise en forme esthétique
XML::Twig peut sortir le document en format esthétique pour qu'il soit plus facile à lire pour nous, humains.
Survivre à une mort prématurée
Les analyseurs XML sont censés réagir violemment lorsqu'ils reçoivent du XML incorrect. XML::Parser meurt simplement.

XML::Twig fournit les méthodes "safe_parse " et "safe_parsefile " qui encapsulent l'analyse dans un "eval" et renvoient soit la brindille analysée, soit 0 en cas d'échec.

Attributs privés
Les attributs dont le nom commence par # (illégal en XML !) ne seront pas affichés, vous pouvez donc les utiliser en toute sécurité pour stocker des valeurs temporaires pendant le traitement. Notez que vous pouvez stocker n'importe quoi dans un attribut privé, pas seulement du texte, c'est juste une variable Perl ordinaire, donc une référence à un objet ou une structure de données volumineuse est parfaitement acceptable.

CLASSES

XML::Twig utilise un nombre très limité de classes. Celles que vous êtes le plus susceptible d'utiliser sont "XML::Twig ", qui représente un document XML complet, y compris le document lui-même (la racine du document elle-même est "root "), ses gestionnaires, ses filtres d'entrée ou de sortie... L'autre classe principale est "XML::Twig::Elt ", qui modélise un élément XML. "Élément" ici a une définition très large : il peut s'agir d'un élément régulier, ou de texte stocké dans une balise "#PCDATA" (ou "#CDATA"), d'une entité (balise est "#ENT"), d'une instruction de traitement ("#PI"), ou d'un commentaire ("#COMMENT").

XML::Twig et XML::Twig::Elt sont les deux classes couramment utilisées.

Vous pourriez vouloir consulter l'option "elt_class " si vous souhaitez sous-classer "XML::Twig::Elt".

Les attributs sont simplement attachés à leur élément parent, ce ne sont pas des objets en soi. (Veuillez utiliser les méthodes fournies "att " et "set_att " pour y accéder, si vous y accédez comme à un hachage, alors votre code devient dépendant de l'implémentation et pourrait casser à l'avenir.)

D'autres classes rarement utilisées sont "XML::Twig::Entity_list " et "XML::Twig::Entity ".

Si vous utilisez "XML::Twig::XPath " au lieu de "XML::Twig", les éléments sont alors créés en tant que "XML::Twig::XPath::Elt ".

MÉTHODES

XML::Twig

Une brindille est une sous-classe de XML::Parser, donc toutes les méthodes de XML::Parser peuvent être appelées sur un objet brindille, y compris parse et parsefile. "setHandlers" en revanche ne peut pas être utilisé, voir "BUGS ".

new
C'est une méthode de classe, le constructeur pour XML::Twig. Les options sont passées sous forme de paires mot-clé-valeur. Les options reconnues sont les mêmes que celles de XML::Parser, plus quelques options spécifiques (en fait, beaucoup !) à XML::Twig.

Nouvelles options :

twig_handlers
Cet argument consiste en un hachage "{ expression =" \&handler}> où l'expression est une expression de type XPath (+ quelques autres).

Les expressions XPath sont limitées à l'utilisation des axes enfant et descendant (en effet, vous ne pouvez pas spécifier d'axe), et les prédicats ne peuvent pas être imbriqués. Vous pouvez utiliser la fonction "string", ou string(<tag>) (sauf dans les déclencheurs "twig_roots").

De plus, vous pouvez utiliser des expressions régulières (délimitées par des /) pour faire correspondre les valeurs d'attributs et de chaînes.

Exemples :

foo
foo/bar
foo//bar
/foo/bar
/foo//bar
/foo/bar[@att1 = "val1" and @att2 = "val2"]/baz[@a >= 1]
foo[string()=~ /^duh!+/]
/foo[string(bar)=~ /\d+/]/baz[@att != 3]

#CDATA peut être utilisé pour appeler un gestionnaire pour une balise CDATA. #COMMENT peut être utilisé pour appeler un gestionnaire pour les commentaires.

Quelques ajouts (

(non-XPath) expressions sont également fournies pour plus de commodité :

instructions de traitement
'?' ou '#PI' déclenche le gestionnaire pour toute instruction de traitement, et '?<cible>' ou '#PI <cible>' déclenche un gestionnaire pour une instruction de traitement avec la cible donnée (par exemple, '#PI xml-stylesheet').
niveau(<niveau>)
Déclenche le gestionnaire pour tout élément à ce niveau dans l'arbre (la racine est au niveau 1).
_tous_
Déclenche le gestionnaire pour tous les éléments de l'arbre.
_défaut_
Déclenche le gestionnaire pour chaque élément qui n'a pas d'autre gestionnaire.

Les gestionnaires sont évalués et mis en file d'attente par rapport au document d'entrée, puis exécutés. Les modifications apportées par un gestionnaire (telles que les changements de nom de balise, le déplacement ou l'enveloppement de l'élément - même dans les gestionnaires de balises de début) n'affectent pas les gestionnaires mis en file d'attente suivants, même si les modifications font que leur expression de déclenchement ne correspond plus. Il y a une exception : les attributs "privés" (dont les noms commencent par '#' et qui ne peuvent être créés que pendant le traitement, car ils ne sont pas XML valides) sont vérifiés par rapport à la branche actuelle.

Les gestionnaires sont déclenchés dans un ordre fixe, triés par leur type (expressions XPath d'abord, puis regexps, puis niveau), puis par le fait qu'ils spécifient un chemin complet (commençant à l'élément racine) ou non, puis par le nombre d'étapes dans l'expression, puis le nombre de prédicats, puis le nombre de tests dans les prédicats. Les gestionnaires dont la dernière étape ne spécifie pas d'étape ("foo/bar/*") sont déclenchés après les autres gestionnaires XPath. Enfin, les gestionnaires "_all_" sont déclenchés en dernier.

Important : Une fois qu'un gestionnaire a été déclenché, s'il renvoie 0, aucun autre gestionnaire n'est appelé, à l'exception du gestionnaire "_all_" qui est toujours appelé.

Si un gestionnaire renvoie une valeur vraie et que d'autres gestionnaires s'appliquent, le prochain gestionnaire applicable sera appelé. Répétez, rincez, faites mousser... L'exception à cette règle est lorsque l'option "do_not_chain_handlers" est définie, auquel cas seul le premier gestionnaire sera appelé.

Il est conseillé de retourner explicitement une courte valeur vraie (comme 1) des gestionnaires ; cela garantit que d'autres gestionnaires applicables sont appelés même si la dernière instruction du gestionnaire évalue à faux. Cela peut également accélérer le code en évitant que le résultat de la dernière instruction du code ne soit copié et transmis au code gérant les gestionnaires. Il peut vraiment être rentable d'avoir 1 au lieu d'une longue chaîne retournée.

Lorsque la balise fermante d'un élément est analysée, le gestionnaire correspondant est appelé avec deux arguments : la branche et l'"Element". La branche comprend l'arbre du document qui a été construit jusqu'à présent, l'élément est le sous-arbre complet de l'élément.

Étant donné que les gestionnaires ne sont appelés que lorsque la balise fermante de l'élément est trouvée, cela signifie que les gestionnaires des éléments internes sont appelés avant les gestionnaires des éléments externes.

$_ est également défini sur l'élément, il est donc facile d'écrire des gestionnaires en ligne comme :

para => sub { $_->set_tag( 'p'); }

Le texte est stocké dans des éléments dont le nom de balise est "#PCDATA" (en raison du contenu mixte, texte et sous-élément dans un élément, il n'y a aucun moyen de stocker le texte comme simple attribut de l'élément parent).

Attention : Si vous avez utilisé "purge" ou "flush" sur la branche, l'élément pourrait ne pas être complet : certains de ses enfants pourraient avoir été entièrement vidés ou purgés, et la balise de début pourrait même avoir été imprimée (par "flush") déjà, donc changer sa balise pourrait ne pas donner le résultat attendu.

racines de branche
Cet argument vous permet de construire l'arbre uniquement pour les éléments qui vous intéressent. 
Exemple : my $t= XML::Twig->new( twig_roots => { title => 1, subtitle => 1});
         $t->parsefile( fichier);
         my $t= XML::Twig->new( twig_roots => { 'section/title' => 1});
         $t->parsefile( fichier);

renvoie une branche contenant un document incluant uniquement les éléments "title" et "subtitle", en tant qu'enfants de l'élément racine.

Vous pouvez utiliser generic_attribute_condition, attribute_condition, full_path, partial_path, tag, tag_regexp, _default_ et _all_ pour déclencher la construction de la branche. string_condition et regexp_condition ne peuvent pas être utilisés car le contenu de l'élément, et la chaîne, n'ont pas encore été analysés lorsque la condition est vérifiée.

ATTENTION : Les chemins sont vérifiés pour le document. Même si l'option "twig_roots" est utilisée, ils seront vérifiés par rapport à l'arbre du document complet, pas à l'arbre virtuel créé par XML::Twig.

ATTENTION : Les éléments twig_roots ne doivent PAS être imbriqués, cela confondrait désespérément XML::Twig.

Note : Vous pouvez définir des gestionnaires (twig_handlers) en utilisant twig_roots
Exemple : my $t= XML::Twig->new( twig_roots =>
{ title => sub { $_[1]->print;},
subtitle => \&process_subtitle
}
);
$t->parsefile( fichier);

twig_print_outside_roots
À utiliser conjointement avec l'argument "twig_roots". Lorsqu'il est défini sur une valeur vraie, il imprime le document en dehors des éléments "twig_roots". 
Exemple : my $t= XML::Twig->new( twig_roots => { title => \&number_title },
                               twig_print_outside_roots => 1,
                              );
          $t->parsefile( fichier);
          { my $nb;
          sub number_title
            { my( $twig, $title);
              $nb++;
              $title->prefix( "$nb ");
              $title->print;
            }
          }

Cet exemple imprime le document en dehors de l'élément titre, appelle "number_title" pour chaque élément "title", l'imprime, puis reprend l'impression du document. La branche est construite uniquement pour les éléments "title".

Si la valeur est une référence à un descripteur de fichier, alors le document en dehors des éléments "twig_roots" sera envoyé à ce descripteur de fichier :

open( my $out, '>', 'out_file.xml') or die "impossible d'ouvrir out file.xml out_file:$!";
my $t= XML::Twig->new( twig_roots => { title => \&number_title },
                       # sortie par défaut vers $out
                       twig_print_outside_roots => $out,
                     );
       { my $nb;
         sub number_title
           { my( $twig, $title);
             $nb++;
             $title->prefix( "$nb ");
             $title->print( $out);    # vous devez imprimer vers \*OUT ici
           }
         }
gestionnaires de balises de début
Une table de hachage "<{ expression =" \&gestionnaire}>>. Définit les gestionnaires d'éléments qui sont appelés lorsque l'élément est ouvert (à la fin du gestionnaire "Start" de XML::Parser). Les gestionnaires sont appelés avec deux paramètres : la branche et l'élément. L'élément est vide à ce stade, mais ses attributs sont créés.

Vous pouvez utiliser generic_attribute_condition, attribute_condition, full_path, partial_path, tag, tag_regexp, _default_ et _all_ pour déclencher le gestionnaire.

string_condition et regexp_condition ne peuvent pas être utilisés car le contenu de l'élément, ainsi que la chaîne, n'ont pas encore été analysés lorsque la condition est vérifiée.

Les principales utilisations des gestionnaires de balises de début sont de changer le nom de la balise (vous devrez peut-être le faire dès que vous trouvez la balise ouverte si vous prévoyez de "flusher" la branche à un moment donné de l'élément, et de créer des attributs temporaires qui seront utilisés lors du traitement des sous-éléments avec des "twig_handlers" réguliers.

Vous devriez également l'utiliser pour changer les balises si vous utilisez "flush". Si vous changez la balise dans un "twig_handler" régulier, la balise de début pourrait déjà avoir été vidée.

Note : les gestionnaires "start_tag" peuvent être appelés en dehors des "twig_roots" si cet argument est utilisé, dans ce cas les gestionnaires sont appelés avec les arguments suivants : $t (la branche), $tag (la balise de l'élément) et %att (une table de hachage des attributs de l'élément).

Si l'argument "twig_print_outside_roots" est également utilisé, si le dernier gestionnaire appelé renvoie une valeur "vraie", alors la balise de début sera imprimée telle qu'elle apparaît dans le document original ; si le gestionnaire renvoie une valeur "fausse", alors la balise de début ne sera **pas** imprimée (vous pouvez donc imprimer vous-même une chaîne modifiée, par exemple).

Notez que vous pouvez utiliser la méthode ignore dans "start_tag_handlers" (et uniquement là).

gestionnaires de balises de fin
Une table de hachage "<{ expression =" \&gestionnaire}>>. Définit les gestionnaires d'éléments qui sont appelés lorsque l'élément est fermé (à la fin du gestionnaire "End" de XML::Parser). Les gestionnaires sont appelés avec deux paramètres : la branche et la balise de l'élément.

Les twig_handlers sont appelés lorsqu'un élément est complètement analysé, alors pourquoi avoir cette option redondante ? Il n'y a qu'une seule utilisation pour "end_tag_handlers" : lors de l'utilisation de l'option "twig_roots", pour déclencher un

handler pour un élément à l'extérieur des racines. C'est, par exemple, très utile pour numéroter les titres dans un document en utilisant des sections imbriquées :

my @no= (0);
my $no;
my $t= XML::Twig->new(
        start_tag_handlers =>
         { section => sub { $no[$#no]++; $no= join '.', @no; push @no, 0; } },
        twig_roots         =>
         { title   => sub { $_[1]->prefix( $no); $_[1]->print; } },
        end_tag_handlers   => { section => sub { pop @no;  } },
        twig_print_outside_roots => 1
                    );
 $t->parsefile( $file);

L'utilisation de l'argument "end_tag_handlers" sans "twig_roots" entraînera une erreur.

do_not_chain_handlers
Si cette option est définie sur une valeur vraie, alors un seul gestionnaire sera appelé pour chaque élément, même si plusieurs satisfont la condition.

Notez que le gestionnaire "_all_" est toujours appelé, quelle que soit cette option.

ignore_elts
Cette option vous permet d'ignorer des éléments lors de la construction de l'arbre. C'est utile dans les cas où vous ne pouvez pas utiliser "twig_roots" pour ignorer des éléments, par exemple si l'élément à ignorer est un frère d'éléments qui vous intéressent.

Exemple :

my $twig= XML::Twig->new( ignore_elts => { elt => 'discard' });
$twig->parsefile( 'doc.xml');

Ceci construira l'arbre complet pour le document, à l'exception de tous les éléments "elt" (et de leurs enfants) qui seront omis.

Les clés dans la table de hachage sont des déclencheurs, limités au même sous-ensemble que "start_tag_handlers ". Les valeurs peuvent être "discard" pour ignorer l'élément, "print" pour afficher l'élément tel quel, "string" pour stocker le texte des éléments ignorés (y compris le balisage) dans un champ de l'arbre : "$t->{twig_buffered_string}" ou une référence à un scalaire, auquel cas le texte des éléments ignorés (y compris le balisage) sera stocké dans le scalaire. Toute autre valeur sera traitée comme "discard".

char_handler
Une référence à une sous-routine qui sera appelée chaque fois que "#PCDATA" est trouvé.

La sous-routine reçoit la chaîne de caractères en argument et renvoie la chaîne modifiée :

# nous voulons toutes les chaînes en majuscules
sub my_char_handler
  { my( $text)= @_;
    $text= uc( $text);
    return $text;
  }
css_sel
Lorsque cette option est définie sur une valeur vraie, elle autorise les sélecteurs "tag.class" dans les gestionnaires.

Le point est un caractère valide dans les noms d'éléments, par exemple "div.header" est un nom XML tout à fait valide.

Mais comme XML::Twig est beaucoup utilisé pour traiter XHTML, et les dialectes basés sur HTML, il est assez pratique de pouvoir utiliser "div.header" pour déclencher une balise "div" avec une classe "header", au lieu de la plus lourde syntaxe "div[@class=~/\bheader\b/]".

Notez que la syntaxe "tag.class" est prise en charge dans les expressions de navigation, à moins que "css_sel" ne soit explicitement défini sur 0.

elt_class
Le nom d'une classe utilisée pour stocker les éléments. Cette classe doit hériter de "XML::Twig::Elt" (et par défaut, c'est "XML::Twig::Elt"). Cette option est utilisée pour sous-classer la classe d'élément et l'étendre avec de nouvelles méthodes.

Cette option est nécessaire car lors de l'analyse XML, les éléments sont créés par "XML::Twig" sans aucun contrôle de la part du code utilisateur.

keep_atts_order
Définir cette option sur une valeur vraie fait que la table de hachage des attributs est liée à un objet "Tie::IxHash". Cela signifie que "Tie::IxHash" doit être installé pour que cette option soit disponible. Cela signifie également que la table de hachage conserve son ordre, vous obtiendrez donc les attributs dans l'ordre. Cela permet de générer les attributs dans le même ordre qu'ils figuraient dans le document d'origine.
keep_encoding
C'est une option (légèrement ?) diabolique : si le document XML n'est pas encodé en UTF-8 et que vous voulez le conserver ainsi, alors définir keep_encoding utilisera la méthode original_string de "Expat" pour les caractères, conservant ainsi l'encodage d'origine, ainsi que les entités d'origine dans les chaînes.

Voir le fichier de test "t/test6.t" pour voir les résultats que vous pouvez attendre des différentes options d'encodage.

ATTENTION : Cette option n'est PAS utilisée lors de l'analyse avec le parseur non bloquant ("parse_start", "parse_more", méthodes parse_done) que vous ne devriez probablement pas utiliser de toute façon avec XML::Twig car ils sont totalement non testés !

output_encoding
Cette option génère un filtre de sortie utilisant "Encode", "Text::Iconv", ou "Unicode::Map8" et "Unicode::Strings", et définit l'encodage dans la déclaration XML. C'est le moyen le plus simple de gérer les encodages. Si vous avez besoin de fonctionnalités plus sophistiquées, voir "output_filter" ci-dessous.
output_filter
Cette option est utilisée pour convertir l'encodage des caractères du document de sortie. Elle reçoit soit une chaîne correspondant à un filtre prédéfini, soit une référence à une sous-routine. Le filtre sera appelé chaque fois qu'un document ou un élément est traité par les fonctions "print" ("print", "sprint", "flush").

Filtres prédéfinis :

latin1
Utilise soit "Encode", "Text::Iconv" ou "Unicode::Map8" et "Unicode::String" ou une expression régulière (qui ne fonctionne qu'avec XML::Parser 2.27), dans cet ordre, pour convertir tous les caractères en ISO-8859-15 (généralement latin1 est synonyme d'ISO-8859-1, mais en pratique il semble qu'ISO-8859-15, qui inclut le signe euro, soit plus utile et probablement ce que la plupart des gens veulent).
html
Effectue la même conversion que "latin1", plus l'encodage des entités en utilisant "HTML::Entities" (étonnamment, vous devrez avoir HTML::Entities installé pour qu'il soit disponible). Ceci ne devrait être utilisé que si les balises et les noms d'attributs sont en US-ASCII, sinon ils seront convertis et la sortie ne sera plus un XML valide.
safe
Convertit la sortie en ASCII (US) uniquement, plus les *entités de caractères* ("&#nnn;"). Ceci ne devrait être utilisé que si les balises et les noms d'attributs sont en US-ASCII, sinon ils seront convertis et la sortie ne sera plus un XML valide.
safe_hex
Identique à "safe" sauf que les entités de caractères sont en hexadécimal ("&#xnnn;").
encode_convert ($encoding)
Retourne une référence de sous-routine qui peut être utilisée pour convertir des chaînes utf8 en $encoding. Utilise "Encode". 
my $conv = XML::Twig::encode_convert( 'latin1');
my $t = XML::Twig->new(output_filter => $conv);
iconv_convert ($encoding)
Cette fonction est utilisée pour créer une sous-routine de filtre qui sera utilisée pour convertir les caractères vers l'encodage cible en utilisant "Text::Iconv" (qui doit être installé, voir la documentation du module et de la bibliothèque "iconv" pour savoir quels encodages sont disponibles sur votre système). 
my $conv = XML::Twig::iconv_convert( 'latin1');
my $t = XML::Twig->new(output_filter => $conv);
unicode_convert ($encoding)
Cette fonction est utilisée pour créer une sous-routine de filtre qui sera utilisée pour convertir les caractères vers l'encodage cible en utilisant "Unicode::Strings" et "Unicode::Map8" (qui doivent être installés, voir la documentation des modules pour savoir quels encodages sont disponibles sur votre système). 
my $conv = XML::Twig::unicode_convert( 'latin1');
my $t = XML::Twig->new(output_filter => $conv);

Les méthodes "text" et "att" n'utilisent pas le filtre, leur résultat est donc toujours en unicode.

Ces filtres prédéclarés sont basés sur des sous-routines qui peuvent être utilisées seules (comme "XML::Twig::foo").

html_encode ($string)
Utilise "HTML::Entities" pour encoder une chaîne utf8.
safe_encode ($string)
Utilise "Encode" pour encoder les caractères non-ascii de la chaîne au format "&#<nnnn>;".
safe_encode_hex ($string)
Utilise "Encode" pour encoder les caractères non-ascii de la chaîne
tring dans le format "&#x<nnnn>;".
regexp2latin1 ($string)
Utilise une expression régulière pour encoder une chaîne utf8 en latin 1 (ISO-8859-1).
output_text_filter
Identique à output_filter, sauf qu'il ne s'applique pas aux crochets et aux guillemets autour des valeurs d'attributs. Ceci est utile pour tous les filtres qui pourraient modifier l'étiquetage, essentiellement tout ce qui ne fait pas que changer l'encodage de la sortie. Les options "html", "safe" et "safe_hex" sont mieux utilisées avec cette option.
input_filter
Cette option est similaire à "output_filter" sauf que le filtre est appliqué aux caractères avant qu'ils ne soient stockés dans le twig, au moment de l'analyse.
remove_cdata
Définir cette option sur une valeur vraie forcera le twig à sortir les sections "#CDATA" comme des sections régulières (échappées) "#PCDATA".
parse_start_tag
Si vous utilisez l'option "keep_encoding", alors cette option peut être utilisée pour remplacer la fonction d'analyse par défaut. Vous devriez fournir un coderef (une référence à une sous-routine) comme argument. Cette sous-routine prend la balise d'origine (fournie par la méthode original_string() de XML::Parser::Expat) et retourne une balise et les attributs dans une hash (ou dans une liste nom_attribut/valeur_attribut).
no_xxe
Empêche l'analyse des entités externes.

Ceci est une fonctionnalité de sécurité, au cas où l'entrée XML ne serait pas fiable. Avec cette option définie sur une valeur vraie, la définition d'entités externes dans le document provoquera l'échec de l'analyse.

Ceci empêche une entité comme "<!ENTITY xxe PUBLIC "bar" "/etc/passwd">" de rendre le champ mot de passe disponible dans le document.

expand_external_ents
Lorsque cette option est utilisée, les entités externes (qui sont définies) sont développées lorsque le document est sorti en utilisant des fonctions "print" telles que "print ", "sprint ", "flush " et "xml_string ". Notez que dans le twig, l'entité sera stockée comme un élément avec une balise '"#ENT"', l'entité ne sera pas développée là, vous pourriez donc vouloir traiter les entités avant de la sortir.

Si une entité externe n'est pas disponible, alors l'analyse échouera.

Un cas spécial est lorsque la valeur de cette option est -1. Dans ce cas, une entité manquante ne fera pas mourir l'analyseur, mais son "name", "sysid" et "pubid" seront stockés dans le twig sous "$twig->{twig_missing_system_entities}" (une référence à un tableau de haches { name => <name>, sysid => <sysid>, pubid => <pubid> }). Oui, c'est un peu un hack, mais c'est utile dans certains cas.

load_DTD
Si cet argument est défini sur une valeur vraie, "parse" ou "parsefile" sur le twig chargeront les informations DTD. Ces informations pourront alors être accédées via le twig, dans un "DTD_handler" par exemple. Cela chargera même une DTD externe.

Les valeurs par défaut et fixes pour les attributs seront également remplies, basées sur la DTD.

Notez que pour ce faire, le module générera un fichier temporaire dans le répertoire courant. Si cela pose problème, faites-le moi savoir et j'ajouterai une option pour spécifier un répertoire alternatif.

Voir "Gestion des DTD" pour plus d'informations.

DTD_handler
Définit un gestionnaire qui sera appelé une fois que le doctype (et la DTD) auront été chargés, avec deux arguments : le twig et la DTD.
no_prolog
Ne sort pas de prologue (déclaration XML et DTD).
id
Cet argument optionnel donne le nom d'un attribut qui peut être utilisé comme ID dans le document. Les éléments dont l'ID est connu peuvent être accédés via la méthode elt_id. id vaut par défaut 'id'. Voir "BUGS ".
discard_spaces
Si cet argument optionnel est défini sur une valeur vraie, alors les espaces sont ignorés lorsqu'ils semblent non significatifs : les chaînes contenant uniquement des espaces et au moins un retour à la ligne sont ignorées. Cet argument est défini sur vrai par défaut.

L'algorithme exact pour supprimer les espaces est : les chaînes incluant uniquement des espaces (espaces \s de Perl) et au moins un \n juste avant une balise ouvrante ou fermante sont supprimées.

discard_all_spaces
Si cet argument est défini sur une valeur vraie, les espaces sont supprimés de manière plus agressive qu'avec "discard_spaces" : les chaînes ne contenant pas de \n sont également supprimées. Cette option convient aux XML orientés données.
keep_spaces
Si cet argument optionnel est défini sur une valeur vraie, alors tous les espaces dans le document sont conservés et stockés comme "#PCDATA".

Attention : L'ajout de cette option peut entraîner des changements dans le twig généré : les espaces précédemment ignorés pourraient se retrouver dans un nouvel élément texte. Voir la différence en appelant le code suivant avec 0 et 1 comme arguments :

perl -MXML::Twig -e'print XML::Twig->new( keep_spaces => shift)->parse( "<d> \n<e/></d>")->_dump'

"keep_spaces" et "discard_spaces" ne peuvent pas être définis en même temps.

discard_spaces_in
Cet argument définit "keep_spaces" sur vrai, mais amène le constructeur de twig à ignorer les espaces dans les éléments listés.

La syntaxe pour utiliser cet argument est :

XML::Twig->new( discard_spaces_in => [ 'elt1', 'elt2']);
keep_spaces_in
Cet argument définit "discard_spaces" sur vrai, mais amène le constructeur de twig à conserver les espaces dans les éléments listés.

La syntaxe pour utiliser cet argument est :

XML::Twig->new( keep_spaces_in => [ 'elt1', 'elt2']);

Attention : L'ajout de cette option peut entraîner des changements dans le twig généré : les espaces précédemment ignorés pourraient se retrouver dans un nouvel élément texte.

pretty_print
Définit la méthode d'impression soignée. Les valeurs sont '"none"' (par défaut), '"nsgmls"', '"nice"', '"indented"', '"indented_c"', '"indented_a"', '"indented_close_tag"', '"cvs"', '"wrapped"', '"record"' et '"record_c"'.

pretty_print formate :

none
Le document est sorti sous forme d'une seule chaîne de caractères, sans sauts de ligne sauf ceux trouvés dans les éléments texte.
nsgmls
Les sauts de ligne sont insérés à des endroits sûrs : c'est-à-dire à l'intérieur des balises, entre une balise et un attribut, entre les attributs et avant le > à la fin d'une balise.

C'est assez laid mais mieux que "none", et c'est très sûr, le document restera valide (conforme à sa DTD).

C'est ainsi que le parseur SGML "sgmls" divise les documents, d'où le nom.

nice
Cette option insère des sauts de ligne avant toute balise qui ne contient pas de texte (donc les éléments avec du contenu textuel ne sont pas coupés car le \n est significatif).

ATTENTION : Cette option laisse le document bien formé mais peut le rendre invalide (non conforme à sa DTD). Si vous avez des éléments déclarés comme :

<!ELEMENT foo (#PCDATA|bar)>

alors un élément "foo" incluant un élément "bar" sera imprimé comme :

<foo>
<bar>bar est juste pcdata</bar>
</foo>

C'est invalide, car le parseur prendra le saut de ligne après la balise "foo" comme un signe que l'élément contient du PCDATA, il mourra alors en trouvant la balise "bar". Cela peut être important pour vous ou pas, mais soyez-en conscient !

indented
Identique à "nice" (et avec le même avertissement) mais indente les éléments selon leur niveau.
indented_c
Identique à "indented", mais un peu plus compact : les balises de fermeture sont sur la même ligne que le texte précédent.
indented_close_tag
Identique à "indented", sauf que la balise de fermeture est également indentée, pour s'aligner avec les balises à l'intérieur de l'élément.
indented_a
Ceci formate les fichiers XML d'une manière conviviale pour le contrôle de version orienté ligne. Le format est décrit dans http://tinyurl.com/2kwscq (c'est un document Oracle avec un insanely long URL).

Notez que pour être totalement conforme à la « spécification », l'ordre des attributs ne doit pas être modifié. Ainsi, s'ils ne sont pas déjà triés par ordre alphabétique, vous devrez utiliser l'option "keep_atts_order ".

cvs
Identique à "indented_a ".
wrapped
Identique à "indented_c", mais les lignes sont retournées en utilisant Text::Wrap::wrap. La longueur par défaut des lignes est la valeur par défaut de $Text::Wrap::columns, et peut être modifiée en changeant cette variable.
record
Il s'agit d'un rendu visuel orienté enregistrement qui affiche les données par enregistrements, un champ par ligne (ce qui ressemble BEAUCOUP à "indented").
record_c
Abréviation de « record compact », un enregistrement par ligne.
empty_tags
Définit le style d'affichage des balises vides (‘"normal"’, ‘"html"’ ou ‘"expand"’).

"normal" affiche une balise vide ‘"<tag/>"’, "html" ajoute un espace ‘"<tag />"’ pour les éléments qui peuvent être vides en XHTML et "expand" affiche ‘"<tag></tag>"’.

quote
Définit le caractère de guillemet pour les attributs (‘"single"’ ou ‘"double"’).
escape_gt
Par défaut, XML::Twig n'échappe pas le caractère > dans sa sortie, car il n'est pas imposé par la spécification XML. Avec cette option activée, > est remplacé par "&gt;".
comments
Définit la manière dont les commentaires sont traités : ‘"drop"’ (par défaut), ‘"keep"’ ou ‘"process"’.

Options de traitement des commentaires :

drop
Supprime les commentaires ; ils ne sont ni lus, ni imprimés en sortie.
keep
Les commentaires sont chargés et apparaîtront en sortie ; ils ne sont pas accessibles dans le twig et n'interféreront pas avec le traitement.

Note : Les commentaires au milieu d'un élément de texte tels que :

<p>texte <!-- commentaire --> plus de texte --></p>

sont conservés à leur position d'origine dans le texte. L'utilisation des méthodes d'impression comme "print" ou "sprint" renverra les commentaires dans le texte. En revanche, utiliser "text" ou "field" ne le fera pas.

Toute utilisation de "set_pcdata" sur l'élément "#PCDATA" (directement ou par d'autres méthodes comme "set_content") supprimera le(s) commentaire(s).

process
Les commentaires sont chargés dans le twig et traités comme des éléments réguliers avec une valeur de "tag" de "#COMMENT". Cela peut interférer avec le traitement si vous vous attendez à ce que "$elt->{first_child}" soit un élément mais trouvez un commentaire à la place. La validation du schéma ne vous protégera pas, car les commentaires peuvent apparaître n'importe où. Vous pouvez utiliser "$elt->first_child( 'tag')" (ce qui est de toute façon une bonne habitude) pour obtenir ce que vous voulez.

Envisagez d'utiliser "process" si vous générez des événements SAX à partir de XML::Twig.

pi
Définit la manière dont les instructions de traitement (PI) sont traitées : ‘"drop"’, ‘"keep"’ (par défaut), ou ‘"process"’.

Notez que vous pouvez également définir des gestionnaires de PI dans l'option "twig_handlers" :

'?'       => \&handler
'?target' => \&handler2

Les gestionnaires seront appelés avec deux paramètres, le twig et l'élément PI si "pi" est défini sur "process", et avec trois, le twig, la cible et les données si "pi" est défini sur "keep". Bien sûr, ils ne seront pas appelés si "pi" est défini sur "drop".

Si "pi" est défini sur "keep", le gestionnaire doit retourner une chaîne qui sera utilisée telle quelle comme texte de la PI (elle doit ressembler à « "<?target data?>" » ou à une chaîne vide si vous voulez supprimer la PI),

Un seul gestionnaire sera appelé, "?target" ou "?" s'il n'y a pas de gestionnaire spécifique pour cette cible.

map_xmlns
Cette option prend en argument un hashref qui mappe des URI à des préfixes. Les préfixes dans le document seront remplacés par ceux de la table de correspondance. Les préfixes mis en correspondance peuvent (en fait doivent) être utilisés pour déclencher des gestionnaires, naviguer ou interroger le document.

Exemple :

my $t= XML::Twig->new( map_xmlns => {'http://www.w3.org/2000/svg' => "svg"},
                       twig_handlers =>
                         { 'svg:circle' => sub { $_->set_att( r => 20) } },
                       pretty_print => 'indented',
                     )
                ->parse( '<doc xmlns:gr="http://www.w3.org/2000/svg">
                            <gr:circle cx="10" cy="90" r="10"/>
                         </doc>'
                       )
                ->print;

Cela produira la sortie suivante :

<doc xmlns:svg="http://www.w3.org/2000/svg">
   <svg:circle cx="10" cy="90" r="20"/>
</doc>
keep_original_prefix
Lorsqu'elle est utilisée avec "map_xmlns ", cette option fait en sorte que "XML::Twig" utilise les préfixes d'espace de noms d'origine lors de la sortie d'un document. Les préfixes mis en correspondance sont toujours utilisés pour déclencher des gestionnaires et dans les méthodes de navigation et de requête. 
my $t= XML::Twig->new( map_xmlns => {'http://www.w3.org/2000/svg' => "svg"},
                       twig_handlers =>
                         { 'svg:circle' => sub { $_->set_att( r => 20) } },
                       keep_original_prefix => 1,
                       pretty_print => 'indented',
                     )
                ->parse( '<doc xmlns:gr="http://www.w3.org/2000/svg">
                            <gr:circle cx="10" cy="90" r="10"/>
                         </doc>'
                       )
                ->print;

Cela produit la sortie suivante :

<doc xmlns:gr="http://www.w3.org/2000/svg">
   <gr:circle cx="10" cy="90" r="20"/>
</doc>
original_uri ($prefix)
Appelée dans un gestionnaire, cette méthode renvoie l'URI lié au préfixe d'espace de noms dans le document d'origine.
index ($arrayref or $hashref)
Cette option crée des listes d'éléments spécifiques lors de l'analyse de l'XML. Elle prend en argument une référence soit à une liste d'expressions déclenchantes, soit à un hash nom => expression, et pour chacun, elle génère la liste des éléments qui correspondent à l'expression. La liste est accessible via la méthode "index ".

Exemple :

# Utilisation d'une référence de tableau
my $t= XML::Twig->new( index => [ 'div', 'table' ])
                ->parsefile( "foo.xml");
my $divs= $t->index( 'div');
my $first_div= $divs->[0];
my $last_table= $t->index( table => -1);
# Utilisation d'un hashref pour nommer les index
my $t= XML::Twig->new( index => { email => 'a[@href=~/^ \s*mailto:/]'})
                ->parsefile( "foo.xml");
my $last_emails= $t->index( email => -1);

Notez que l'index n'est pas maintenu après l'analyse. Si des éléments sont supprimés, renommés ou modifiés d'une autre manière pendant le traitement, l'index n'est PAS mis à jour. (Modifier l'élément id, en revanche, mettra à jour l'index).

att_accessors <liste de noms d'attributs>
Crée des méthodes qui donnent un accès direct aux attributs : 
my $t= XML::Twig->new( att_accessors => [ 'href', 'src'])
                ->parsefile( $file);
my $first_href= $t->first_elt( 'img')->src; # équivalent à ->att( 'src')
$t->first_elt( 'img')->src( 'new_logo.png') # change la valeur de l'attribut
elt_accessors
Crée des méthodes qui donnent un accès direct au premier élément enfant (en contexte scalaire) ou à la liste des éléments (en contexte de liste) :

La liste des accesseurs à créer peut être fournie de deux manières : dans un tableau, ou dans un hash alias => expression.

my $t=  XML::Twig->new( elt_accessors => [ 'head'])
                ->parsefile( $file);
my $title_text= $t->root->head->field( 'title');
# équivalent à $title_text= $t->root->first_child( 'head')->field( 'title');
my $t=  XML::Twig->new( elt_accessors => { warnings => 'p[@class="warning"]', d2 => 'div[2]'}, )
                ->parsefile( $file);
my $body= $t->first_elt( 'body');
my @warnings= $body->warnings; # équivalent à $body->children( 'p[@class="warning"]');
my $s2= $body->d2;             # équivalent à $body->first_child( 'div[2]')
field_accessors
Crée desméthodes qui donnent un accès direct au texte du premier élément enfant : 
my $t=  XML::Twig->new( field_accessors => [ 'h1'])

split_at ($offset)
Divise un texte (élément "#PCDATA" ou "#CDATA") en 2 à l'offset $offset, l'élément d'origine contient maintenant la première partie de la chaîne et un nouvel élément contient la partie droite. Le nouvel élément est retourné.

split ( $optional_regexp, $tag1, $atts1, $tag2, $atts2...)
Divise les descendants texte d'un élément en place, le texte est divisé en utilisant le $regexp, si l'expression régulière inclut () alors les séparateurs correspondants seront
englobé dans des éléments. $1 est englobé dans $tag1, avec les attributs $atts1 si $atts1 est donné (sous forme de hashref), $2 est englobé dans $tag2...

L'expression régulière peut être passée soit sous forme de chaîne, soit sous forme de "qr//", elle vaut par défaut \s+ tout comme la fonction intégrée "split" (mais ce serait un comportement assez inutile sans le paramètre $optional_tag).

subs_text ($regexp, $replace)
subs_text effectue une substitution de texte, similaire à l'opérateur " s///" de Perl.

$regexp doit être une regex Perl, créée avec l'opérateur "qr".

Retourne l'élément appelant.

$replace peut inclure "$1, $2"... de la $regexp. Il peut également être utilisé pour créer des éléments et des entités, en utilisant "&elt( tag => { att => val }, text)" (syntaxe similaire à "new ") et &ent( name).

Voici un exemple plutôt complexe :

$elt->subs_text( qr{(?<!do not )link to (http://([^\s,]*))},
                 'see &elt( a =>{ href => $1 }, $2)'
               );

Ceci remplace un texte comme link to http://www.xmltwig.org par see <a href="www.xmltwig.org">www.xmltwig.org</a>, mais pas do not link to....

Génération d'entités (ici remplacement des espaces par &nbsp;) :

$elt->subs_text( qr{ },'&ent( "&nbsp;")');

ou, en utilisant une variable :

my $ent="&nbsp;";
$elt->subs_text( qr{ },"&ent( '$ent')");

Notez que la substitution est toujours globale, comme en utilisant le modificateur "g" dans une substitution Perl, et qu'elle est effectuée sur tous les descendants textuels de l'élément.

Bug : dans la $regexp, vous ne pouvez utiliser que "\1", "\2"... si l'expression de remplacement n'inclut pas d'éléments ou d'attributs. par exemple :

$t->subs_text( qr/((t[aiou])\2)/, '$2');             # ok, remplace toto, tata, titi, tutu par to, ta, ti, tu

Renvoie une liste d'éléments satisfaisant à la requête $xpath. $xpath est une expression de type XPATH.

Un sous-ensemble de la syntaxe abrégée XPATH est couvert :

tag
tag[1]    (ou tout autre nombre positif)
tag[last()]
tag[@att]    (l'attribut existe pour l'élément)
tag[@att="val"]
tag[@att=~ /regexp/]

les expressions peuvent commencer par / (la recherche commence à la racine du document)
les expressions peuvent commencer par . (la recherche commence à l'élément courant)
// peut être utilisé pour obtenir tous les descendants au lieu des seuls enfants directs
* correspond à n'importe quel tag

Ainsi, les exemples suivants de la recommandation XPath http://www.w3.org/TR/xpath.html#path-abbrev fonctionnent :

para sélectionne les enfants de type element 'para' du nœud de contexte
* sélectionne tous les enfants de type element du nœud de contexte
para[1] sélectionne le premier enfant 'para' du nœud de contexte
para[last()] sélectionne le dernier enfant 'para' du nœud de contexte
*/para sélectionne tous les petits-enfants 'para' du nœud de contexte
/doc/chapter[5]/section[2] sélectionne la deuxième section du cinquième chapitre
   du document
chapter//para sélectionne les descendants 'para' des enfants 'chapter'
   du nœud de contexte
//para sélectionne tous les descendants 'para' de la racine du document et donc sélectionne
   tous les éléments 'para' du même document que le nœud de contexte
//olist/item sélectionne tous les éléments 'item' du même document que le
   nœud de contexte qui ont un parent 'olist'
.//para sélectionne les descendants 'para' du nœud de contexte
.. sélectionne le parent du nœud de contexte
para[@type="warning"] sélectionne tous les enfants 'para' du nœud de contexte qui ont
   un attribut type avec la valeur warning
employee[@secretary and @assistant] sélectionne tous les enfants 'employee' du
   nœud de contexte qui ont à la fois un attribut secretary et un attribut assistant

Les éléments sont renvoyés dans l'ordre du document.

Si $optional_offset est utilisé, alors un seul élément sera renvoyé – celui avec l'indice approprié dans la liste, en commençant à 0.

La mise entre guillemets et l'interpolation de variables peuvent être une source de problèmes lorsque la syntaxe Perl et la syntaxe XPATH entrent en collision, utilisez donc des mécanismes de citation alternatifs comme q ou qq (j'aime q{} et qq{} personnellement).

Voici quelques exemples supplémentaires pour vous aider à démarrer :

my $p1= "p1";
my $p2= "p2";
my @res= $t->get_xpath( qq{p[string( "$p1") ou string( "$p2")]});
my $a= "a1";
my @res= $t->get_xpath( qq{//*[@att="$a"]});
my $val= "a1";
my $exp= qq{//p[ \@att='$val']}; # vous devez utiliser \@ sinon vous obtiendrez un avertissement
my @res= $t->get_xpath( $exp);

Notez que les seuls délimiteurs d'expressions régulières pris en charge sont / et que vous devez échapper tous les / dans les expressions régulières ET dans les chaînes de caractères ordinaires.

XML::Twig ne fournit pas un support XPATH natif complet, mais vous pouvez utiliser "XML::Twig::XPath " pour obtenir "findnodes" afin d'utiliser "XML::XPath" comme moteur XPath avec une couverture complète de la spécification.

La plupart des fonctions de navigation acceptent une condition comme argument optionnel. Le premier élément (ou tous les éléments pour "children " ou "ancestors ") qui satisfait la condition est retourné.

La condition est une seule étape d'une expression XPath utilisant le sous-ensemble XPath défini par "get_xpath ". Les conditions supplémentaires sont :

La condition peut être :

#ELT
Retourne un "vrai" élément (pas un "#PCDATA", "#CDATA", class="Li">"#COMMENT", ou élément "#PI").
#TEXT
Retourne un élément "#PCDATA" ou "#CDATA".
expression régulière
Retourne un élément dont la balise correspond à l'expression régulière. L'expression régulière doit être créée avec "qr//".
référence de code
Applique le code, en passant l'élément courant comme argument. Si le code retourne vrai, alors l'élément est retourné. S'il retourne faux, alors le code est appliqué au prochain candidat.

XML::Twig::XPath

XML::Twig implémente un sous-ensemble de XPath à travers la méthode "get_xpath ".

Si vous souhaitez utiliser toute la puissance de XPath, vous pouvez utiliser "XML::Twig::XPath" à la place. Dans ce cas, "XML::Twig" utilise "XML::XPathEngine" ou "XML::XPath" pour exécuter des requêtes XPath. Vous avez toujours besoin de "XML::XPathEngine" ou "XML::XPath" installés pour pouvoir utiliser "XML::Twig::XPath".

Voir XML::XPathEngine ou XML::XPath pour plus d'informations.

EXEMPLES

Des exemples supplémentaires (et un tutoriel complet) peuvent être trouvés sur la Page XML::Twighttp://www.xmltwig.org/xmltwig/.

Pour comprendre ce que fait flush, appelez le script suivant avec un fichier XML et un nom d'élément comme arguments :

use XML::Twig;
my ($file, $elt)= @ARGV;
my $t= XML::Twig->new( twig_handlers =>
    { $elt => sub {$_[0]->flush; print "\n[flushed here]\n";} });
$t->parsefile( $file, ErrorContext => 2);
$t->flush;
print "\n";

Sous-classement de XML::Twig

Méthodes utiles :

elt_class
Afin de sous-classer "XML::Twig" vous devrez probablement aussi sous-classer "XML::Twig::Elt ". Utilisez l'option "elt_class" lorsque vous créez l'objet "XML::Twig" pour que les éléments soient créés dans une classe différente (qui devrait être une sous-classe de "XML::Twig::Elt".
add_options
Si vous héritez de la méthode new de "XML::Twig" mais souhaitez y ajouter des options supplémentaires, vous pouvez utiliser cette méthode pour éviter que XML::Twig n'émette des avertissements pour ces options supplémentaires.

Gestion des DTD

Il y a 3 possibilités ici. Ce sont :

Pas de DTD
Pas de doctype, pas d'informations DTD, pas d'informations sur les entités, le monde est simple...
DTD Interne

DTD

Internal DTD
Le document XML inclut une DTD interne, et peut-être des déclarations d'entités.

Si vous utilisez l'option load_DTD lors de la création du twig, les informations de la DTD et les déclarations d'entités seront accessibles.

La DTD et les déclarations d'entités seront "flush" (ou "print") telles quelles (si elles n'ont pas été modifiées) ou reconstruites (mal, les commentaires sont perdus, l'ordre n'est pas conservé, en raison de son contenu, cette DTD ne devrait être vue par personne) si elles ont été modifiées. Vous pouvez également les modifier directement en changeant le champ "$twig->{twig_doctype}->{internal}" (directement depuis XML::Parser, voir la documentation du gestionnaire "Doctype").

DTD Externe
Le document XML inclut une référence à une DTD externe, et peut-être des déclarations d'entités.

Si vous utilisez "load_DTD" lors de la création du twig, les informations de la DTD et les déclarations d'entités seront accessibles. Les déclarations d'entités seront "flush" (ou "print") telles quelles (si elles n'ont pas été modifiées) ou reconstruites (mal, les commentaires sont perdus, l'ordre n'est pas conservé).

Vous pouvez changer le doctype via la méthode "$twig->set_doctype" et imprimer la dtd via les méthodes "$twig->dtd_text" ou "$twig->dtd_print"
.

Si vous avez besoin de modifier la liste des entités, c'est probablement la façon la plus simple de le faire.

Flush

N'oubliez pas que les gestionnaires d'éléments sont appelés lorsque l'élément est FERMÉ, donc si vous avez des gestionnaires pour des éléments imbriqués, les gestionnaires internes seront appelés en premier. Cela rend, par exemple, plus difficile qu'il n'y paraît de numéroter des sections imbriquées (ou des clauses, ou des divs), car les titres des sections internes sont gérés avant les sections externes.

BUGS

segfault lors de l'analyse
Cela se produit lors de l'analyse de documents énormes, ou de nombreux petits documents, avec une version de Perl antérieure à 5.16.

Ceci est dû à un bug dans la façon dont les références faibles sont gérées dans Perl lui-même.

La solution est soit de passer à Perl 5.16 ou une version ultérieure ("perlbrew" est un excellent outil pour gérer plusieurs installations de perl sur la même machine).

Une autre façon, NON RECOMMANDÉE, de résoudre le problème est de désactiver les références faibles en écrivant "XML::Twig::_set_weakrefs( 0);" en haut du code. Ceci n'est totalement pas supporté et peut entraîner d'autres problèmes.

gestion des entités
En raison du comportement de XML::Parser, les entités non de base dans les valeurs d'attributs disparaissent si elles ne sont pas déclarées dans le document : "att="val&ent;"" sera transformé en "att => val", sauf si vous utilisez l'argument "keep_encoding" pour "XML::Twig->new".
gestion de la DTD
Les méthodes de gestion de la DTD sont assez buggées. Personne ne les utilise et il semble très difficile de les faire fonctionner dans tous les cas, y compris avec plusieurs versions légèrement incompatibles de XML::Parser et de libexpat.

En gros, vous pouvez lire la DTD, la sortir correctement, et mettre à jour les entités, mais pas beaucoup plus.

Utilisez donc XML::Twig avec des documents autonomes, ou avec des documents faisant référence à une DTD externe, mais ne vous attendez pas à ce qu'il analyse correctement, ni même à ce qu'il sorte la DTD.

liste des ID
La liste des ID n'est PAS mise à jour lorsque les éléments sont coupés ou supprimés.
change_gi
Cette méthode ne fonctionnera pas correctement si vous faites : 
$twig->change_gi( $old1, $new);
$twig->change_gi( $old2, $new);
$twig->change_gi( $new, $even_newer);
vérification de la validité des appels de méthode XML::Parser
XML::Twig devrait vraiment empêcher les appels à certaines méthodes XML::Parser, en particulier la méthode "setHandlers".
impression soignée
L'impression soignée (au moins en utilisant le style '"indented"') est difficile à obtenir correctement ! Seuls les éléments qui appartiennent au document seront correctement indentés. L'impression d'éléments qui n'appartiennent pas au twig rend impossible pour XML::Twig de déterminer leur profondeur, et donc leur niveau d'indentation.

Il y a aussi un bug inévitable lors de l'utilisation de "flush" et de l'impression soignée pour les éléments avec un contenu mixte qui commence par un élément imbriqué :

<elt><b>b</b>toto<b>bold</b></elt>
sera sorti comme
<elt>
  <b>b</b>toto<b>bold</b></elt>

si vous faites un flush du twig lorsque vous trouvez l'élément "<b>".

Modules alternatifs

XML::Twig n'est pas le seul module de traitement XML disponible sur CPAN (loin de là !).

L'alternative principale que je recommanderais est XML::LibXML.

Voici une comparaison rapide des 2 modules :

XML::LibXML, en fait "libxml2" sur lequel il est basé, respecte les normes et en implémente un bon nombre de manière plutôt stricte : XML, XPath, DOM, RelaxNG, j'oublie peut-être quelques-unes (XInclude ?). Il est rapide et plutôt économe en mémoire.

XML::Twig est plus ancien : quand j'ai commencé à l'écrire, XML::Parser/expat était le seul jeu disponible. Il implémente XML et c'est à peu près tout (plus un sous-ensemble de XPath, et vous pouvez utiliser XML::Twig::XPath si vous avez XML::XPathEngine installé pour un support complet). Il est plus lent et nécessite plus de mémoire pour un arbre complet que XML::LibXML. Le côté positif (oui, il y a un côté positif !) est qu'il vous permet de traiter un gros document par morceaux, vous permettant ainsi de traiter des documents qui ne pourraient pas être chargés en mémoire par XML::LibXML, et il offre beaucoup (et je dis BIEN BEAUCOUP !) de méthodes de plus haut niveau, pour tout, de l'ajout de structure au XML "bas niveau", aux raccourcis pour les conversions XHTML et plus encore. Il fait aussi beaucoup de choses intelligemment, en écartant les commentaires et les espaces blancs non significatifs mais en les préservant dans la sortie par exemple. Comme il ne respecte pas le DOM, il conduit également à un code généralement plus court qu'en XML::LibXML.

Au-delà des fonctionnalités pures des 2 modules, XML::LibXML semble être préféré par les "puristes XML", tandis que XML::Twig semble être plus utilisé par les Perl Hackers qui doivent traiter du XML. Comme vous l'avez noté, XML::Twig est également livré avec pas mal de documentation, mais je suis sûr que si vous demandez de l'aide concernant XML::LibXML ici ou sur Perlmonks, vous obtiendrez des réponses.

Notez qu'il m'est en fait assez difficile de comparer les 2 modules : d'une part, je connais XML::Twig sur le bout des doigts et je peux lui faire faire à peu près tout ce dont j'ai besoin (ou je l'améliore ;--), tandis que j'ai une connaissance très basique de XML::LibXML. Donc, en termes de fonctionnalités, je préférerais utiliser XML::Twig ;--). D'autre part, je suis painnellement conscient de certaines des lacunes, des bugs potentiels et du code franchement laid qui se cachent dans XML::Twig, même si vous ne serez probablement pas affecté par eux (sauf si, par exemple, vous avez besoin de modifier le DTD d'un document par programmation), alors que je n'ai pas beaucoup regardé XML::LibXML, il me semble donc toujours brillant et propre.

Cela dit, si vous avez besoin de traiter un document trop volumineux pour tenir en mémoire et que XML::Twig est trop lent pour vous, mon conseil à regret serait d'utiliser "brut" XML::Parser. Il ne sera pas aussi facile à utiliser que XML::Twig : en gros, avec XML::Twig, vous échangez une certaine vitesse (selon ce que vous faites, d'un facteur 3 à... zéro) contre la facilité d'utilisation, mais ce sera plus facile selon moi que d'utiliser SAX (bien que non standard), et à ce stade BEAUCOUP plus rapide (voir le dernier test à http://www.xmltwig.org/article/simple_benchmark/).
