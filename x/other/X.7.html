X(7) Manuel d'informations diverses X(7)

NOM

X - un système de fenêtrage portable et indépendant du réseau

APERÇU

Le système de fenêtrage X (X Window System) est un système de fenêtrage indépendant du réseau qui s'exécute sur une large gamme de machines informatiques et graphiques. Il devrait être relativement simple de compiler la distribution logicielle de la Fondation X.Org sur la plupart des systèmes conformes aux normes ANSI C et POSIX. Des implémentations commerciales sont également disponibles pour une large gamme de plateformes.

La Fondation X.Org demande que les noms suivants soient utilisés pour faire référence à ce logiciel :

X
Système de fenêtrage X
X Version 11
Système de fenêtrage X, Version 11
X11

X Window System est une marque commerciale de The Open Group.

DESCRIPTION

Les serveurs du système de fenêtrage X s'exécutent sur des ordinateurs dotés d'écrans bitmap. Le serveur distribue les entrées utilisateur et accepte les requêtes de sortie de divers programmes clients via une variété de canaux de communication interprocessus différents. Bien que le cas le plus courant soit que les programmes clients s'exécutent sur la même machine que le serveur, les clients peuvent également s'exécuter de manière transparente depuis d'autres machines (y compris des machines avec des architectures et des systèmes d'exploitation différents).

X prend en charge les sous-fenêtres hiérarchiques qui se chevauchent et les opérations de texte et de graphique, sur les écrans monochromes et couleur. Pour une explication complète des fonctions disponibles, consultez le manuel de Xlib - Interface C du langage X, la spécification du Protocole du système de fenêtrage X, le manuel de X Toolkit Intrinsics - Interface C du langage, et divers documents de boîtes à outils. Ces manuels, spécifications et documents peuvent être trouvés dans /usr/share/doc ou sur le site Web de la Fondation X.Org à l'adresse https://www.x.org/releases/current/doc/.

Le nombre de programmes utilisant X est assez important. Parmi les exemples de programmes fournis par la Fondation X.Org figurent : un émulateur de terminal, xterm ; un gestionnaire de fenêtres, twm ; un gestionnaire de composition, xcompmgr ; un gestionnaire d'affichage, xdm ; un programme de redirection de console, xconsole ; des utilitaires pour gérer les périphériques d'entrée et de sortie, xinput et xrandr ; des outils de liste et de manipulation de ressources, appres, editres ; des programmes de contrôle d'accès, xauth, xhost et iceauth ; des programmes de configuration des préférences utilisateur, transset, xrdb, xcmsdb, xset, xsetroot, xstdcmap et xmodmap ; des horloges, xclock et oclock ; des utilitaires d'affichage de polices, xfd et xfontsel ; des utilitaires pour lister des informations sur les affichages, les extensions et les ressources, xdpyinfo, xdriinfo, xvinfo, xwininfo, xlsclients, xprop, xlsatoms, xlsclients et xlsfonts ; des utilitaires de manipulation d'images d'écran, xwd, xwud et xmag ; un utilitaire de mesure de performance, x11perf ; un compilateur de polices, bdftopcf ; un serveur de polices et utilitaires associés, xfs, xfsinfo, fslsfonts, fstobdf ; un serveur d'affichage et utilitaires associés, Xserver, rgb, mkfontdir ; un gestionnaire de presse-papiers, xclipboard ; un compilateur de descriptions de clavier et utilitaires associés, xkbcomp, setxkbmap xkbprint, xkbbell, xkbevd, xkbvleds et xkbwatch ; un utilitaire pour terminer des clients, xkill ; et un utilitaire pour forcer le redessin de tout ou partie de l'écran, xrefresh.

De nombreux autres utilitaires, gestionnaires de fenêtres, jeux, boîtes à outils, etc. sont inclus en tant que paquets dans de nombreuses distributions de systèmes d'exploitation, ou sont disponibles sur Internet. Consultez votre administrateur système ou le gestionnaire de paquets de votre distribution pour plus de détails.

DÉMARRAGE

Il existe deux méthodes principales pour démarrer le serveur X et un ensemble initial d'applications clientes. La méthode particulière utilisée dépend du système d'exploitation sur lequel vous travaillez et si vous utilisez ou non d'autres systèmes de fenêtrage en plus de X.

Gestionnaire d'affichage
Si vous souhaitez que X soit toujours actif sur votre écran, votre administrateur système peut configurer votre machine pour utiliser un gestionnaire d'affichage tel que xdm, gdm ou kdm. Ce programme est généralement démarré par le système au moment du démarrage et prend en charge le maintien du serveur en cours d'exécution et la connexion des utilisateurs. Si vous utilisez l'un de ces gestionnaires d'affichage, vous verrez normalement une fenêtre à l'écran vous souhaitant la bienvenue sur le système et vous demandant vos informations de connexion. Tapez-les simplement comme vous le feriez sur un terminal normal. Si vous faites une erreur, le gestionnaire d'affichage affichera un message d'erreur et vous demandera de réessayer. Après vous être connecté avec succès, le gestionnaire d'affichage démarrera votre environnement X. La documentation du gestionnaire d'affichage que vous utilisez peut fournir plus de détails.
xinit (exécuté manuellement depuis le shell)
Les sites qui prennent en charge plus d'un système de fenêtrage peuvent choisir d'utiliser le programme xinit pour démarrer X manuellement. Si tel est le cas sur votre machine, votre administrateur système aura probablement fourni un programme nommé « x11 », « startx » ou « xstart » qui effectuera une initialisation spécifique au site (telle que le chargement de ressources par défaut pratiques, le lancement d'un gestionnaire de fenêtres, l'affichage d'une horloge et le lancement de plusieurs émulateurs de terminal) de manière agréable. Sinon, vous pouvez créer un tel script en utilisant le programme xinit. Cet utilitaire exécute simplement un programme spécifié par l'utilisateur pour démarrer le serveur, un autre pour démarrer les clients souhaités, puis attend que l'un d'eux se termine. Comme les deux programmes spécifiés par l'utilisateur (ou l'un d'eux) peuvent être un script shell, cela offre une flexibilité substantielle au détriment d'une interface agréable. Pour cette raison, xinit n'est pas destiné aux utilisateurs finaux.

NOMS D'AFFICHAGE

Du point de vue de l'utilisateur, chaque serveur X a un nom d'affichage de la forme :

nom_hôte:numéro_affichage.numéro_écran
ou
protocole/nom_hôte:numéro_affichage.numéro_écran

Ces informations sont utilisées par l'application pour déterminer comment elle doit se connecter au serveur et quel écran elle doit utiliser par défaut (sur les affichages avec plusieurs moniteurs) :

protocole
Le protocole spécifie le protocole à utiliser pour la communication. Les protocoles exacts pris en charge sont dépendants de la plateforme, mais les plus couramment pris en charge sont :
tcp TCP sur IPv4 ou IPv6
inet TCP uniquement sur IPv4
inet6 TCP uniquement sur IPv6
unix Sockets de domaine UNIX (même hôte uniquement)
local Méthode de connexion locale préférée par la plateforme
Si le protocole n'est pas spécifié, Xlib utilise le transport qu'il estime le plus efficace.
nom_hôte
Le nom_hôte spécifie le nom de la machine à laquelle l'affichage est physiquement connecté. Si le nom d'hôte n'est pas donné, une connexion à un serveur sur la même machine sera utilisée.
numéro_affichage
L'expression « affichage » est généralement utilisée pour désigner un ensemble de moniteurs qui partagent un ensemble commun de périphériques d'entrée (clavier, souris, tablette, etc.). La plupart des stations de travail n'ont généralement qu'un seul affichage. Les systèmes multi-utilisateurs plus grands, cependant, ont fréquemment plusieurs affichages afin que plusieurs personnes puissent effectuer des travaux graphiques en même temps. Pour éviter toute confusion, chaque affichage sur une machine se voit attribuer un numéro d'affichage (à partir de 0) lorsque le serveur X pour cet affichage est démarré. Le numéro d'affichage doit toujours être indiqué dans un nom d'affichage.
numéro_écran
Certains affichages partagent leurs périphériques d'entrée entre deux moniteurs ou plus. Ceux-ci peuvent être configurés comme un seul écran logique, ce qui permet aux fenêtres de se déplacer entre les écrans, ou comme des écrans individuels, chacun avec son propre ensemble de fenêtres. Si configuré de telle sorte que chaque moniteur ait son propre ensemble de fenêtres, chaque écran se voit attribuer un numéro d'écran (à partir de 0) lorsque
le X serveur pour cet affichage est démarré. Si le numéro d'écran n'est pas indiqué, l'écran 0 sera utilisé.

Sur les systèmes POSIX, le nom d'affichage par défaut est stocké dans votre variable d'environnement DISPLAY. Cette variable est automatiquement définie par l'émulateur de terminal xterm. Cependant, lorsque vous vous connectez à une autre machine sur un réseau, vous devrez peut-être définir manuellement DISPLAY pour pointer vers votre écran. Par exemple,

    % setenv DISPLAY myws:0
    $ DISPLAY=myws:0; export DISPLAY

Le programme ssh peut être utilisé pour démarrer un programme X sur une machine distante ; il définit automatiquement la variable DISPLAY correctement.

Enfin, la plupart des programmes X acceptent une option de ligne de commande -display nomdedisplay pour remplacer temporairement le contenu de DISPLAY. Ceci est le plus souvent utilisé pour afficher des fenêtres sur l'écran d'une autre personne ou dans le cadre d'une commande "shell à distance" pour démarrer un xterm pointant vers votre écran. Par exemple,

    % xeyes -display joesws:0 -geometry 1000x1000+0+0
    % rsh big xterm -display myws:0 -ls </dev/null &

Les serveurs X écoutent les connexions sur une variété de canaux de communication différents (flux d'octets réseau, mémoire partagée, etc.). Comme il peut y avoir plus d'une façon de contacter un serveur donné, le champ nommachine du nom d'affichage est utilisé pour déterminer le type de canal (également appelé couche de transport) à utiliser. Les serveurs X prennent généralement en charge les types de connexions suivants :

local

Le champ nommachine du nom d'affichage doit être la chaîne vide. Par exemple : :0, :1, et :0.1. Le transport local le plus efficace sera choisi.
TCP/IP

Le champ nommachine du nom d'affichage doit être le nom d'hôte ou l'adresse IP de la machine serveur. Les noms Internet complets, les noms abréviés, les adresses IPv4 et les adresses IPv6 sont tous autorisés. Par exemple : x.org:0, expo:0, [::1]:0, 198.112.45.11:0, bigmachine:1, et hydra:0.1.

CONNEXIONS LOCALES

Pour les systèmes d'exploitation qui prennent en charge les connexions locales autres que les sockets de domaine Unix (SVR3 et SVR4), il existe une liste intégrée spécifiant l'ordre dans lequel les connexions locales doivent être tentées. Cette liste peut être remplacée par la variable d'environnement XLOCAL décrite ci-dessous. Si le nom d'affichage indique qu'une connexion du meilleur choix doit être établie (par exemple, :0.0), chaque mécanisme de connexion est essayé jusqu'à ce qu'une connexion réussisse ou qu'il n'y ait plus de mécanismes disponibles.

La variable d'environnement XLOCAL doit contenir une liste d'un ou plusieurs des éléments suivants :

NAMED
PTS
SCO
UNIX

qui représentent respectivement les pipes de flux nommés SVR4, les pipes de flux de style ancien USL, les pipes de flux SCO XSight et les sockets de domaine Unix. Vous pouvez sélectionner un seul mécanisme (par exemple, XLOCAL=NAMED), ou une liste ordonnée (par exemple, XLOCAL="NAMED:PTS:SCO"). Cette variable remplace les valeurs par défaut intégrées. Pour SVR4, il est recommandé que NAMED soit la connexion de première préférence. Le réglage par défaut dépend de la plateforme.

Pour remplacer globalement les valeurs par défaut intégrées, vous devez définir (et exporter si vous utilisez sh ou ksh) XLOCAL globalement. Si vous utilisez startx(1) ou xinit(1), la définition doit être en haut de votre fichier .xinitrc. Si vous utilisez xdm(1), les définitions doivent être tôt dans le script /usr/lib/X11/xdm/Xsession.

CONTRÔLE D'ACCÈS

Un serveur X peut utiliser plusieurs types de contrôle d'accès. Les mécanismes fournis dans la Release 7 sont :

Accès par Hôte Contrôle d'accès simple basé sur l'hôte.
MIT-MAGIC-COOKIE-1 "Cookies" texte clair partagés.
XDM-AUTHORIZATION-1 Clés privées sécurisées basées sur DES.
SUN-DES-1 Basé sur le système rpc sécurisé de Sun.
Interprété par le Serveur Méthodes de contrôle d'accès dépendantes du serveur

Xdm initialise le contrôle d'accès pour le serveur et place également les informations d'autorisation dans un fichier accessible à l'utilisateur.

Normalement, la liste des hôtes à partir desquels les connexions sont toujours acceptées doit être vide, de sorte que seuls les clients qui sont explicitement autorisés puissent se connecter à l'écran. Lorsque vous ajoutez des entrées à la liste des hôtes (avec xhost), le serveur n'effectue plus d'autorisation sur les connexions provenant de ces machines. Soyez prudent avec cela.

Le fichier à partir duquel Xlib extrait les données d'autorisation peut être spécifié avec la variable d'environnement XAUTHORITY, et par défaut au fichier .Xauthority dans le répertoire personnel. Xdm utilise $HOME/.Xauthority et le créera ou fusionnera des enregistrements d'autorisation s'il existe déjà lorsqu'un utilisateur se connecte.

Si vous utilisez plusieurs machines et partagez un répertoire personnel commun sur toutes les machines au moyen d'un système de fichiers réseau, vous n'avez jamais vraiment à vous soucier des fichiers d'autorisation, le système devrait fonctionner correctement par défaut. Sinon, comme les fichiers d'autorisation sont indépendants de la machine, vous pouvez simplement copier les fichiers pour les partager. Pour gérer les fichiers d'autorisation, utilisez xauth. Ce programme vous permet d'extraire des enregistrements et de les insérer dans d'autres fichiers. En utilisant cela, vous pouvez envoyer des autorisations à des machines distantes lorsque vous vous connectez, si la machine distante ne partage pas un répertoire personnel commun avec votre machine locale. Notez que les informations d'autorisation transmises "en clair" via un système de fichiers réseau ou en utilisant ftp ou rcp peuvent être "volées" par un écouteur réseau, et peuvent ainsi permettre un accès non autorisé. Dans de nombreux environnements, ce niveau de sécurité n'est pas une préoccupation, mais s'il l'est, vous devez connaître la sémantique exacte des données d'autorisation particulières pour savoir si cela pose réellement un problème.

Pour plus d'informations sur le contrôle d'accès, consultez la page du manuel Xsecurity(7).

SPÉCIFICATIONS DE GÉOMÉTRIE

L'un des avantages de l'utilisation des systèmes de fenêtres au lieu des terminaux câblés est que les applications ne sont pas obligées d'être limitées à une taille ou un emplacement particulier sur l'écran. Bien que la disposition des fenêtres sur un écran soit contrôlée par le gestionnaire de fenêtres que l'utilisateur exécute (décrit ci-dessous), la plupart des programmes X acceptent un argument de ligne de commande de la forme -geometry LARGEURxHAUTEUR+DÉCALAGE_X+DÉCALAGE_Y (où LARGEUR, HAUTEUR, DÉCALAGE_X, et DÉCALAGE_Y sont des nombres) pour spécifier une taille et un emplacement préférés pour la fenêtre principale de cette application.

Les parties LARGEUR et HAUTEUR de la spécification de géométrie sont généralement mesurées en pixels ou en caractères, selon l'application. Les parties DÉCALAGE_X et DÉCALAGE_Y sont mesurées en pixels et sont utilisées pour spécifier la distance de la fenêtre par rapport aux bords gauche ou droit et supérieur et inférieur de l'écran, respectivement. Les deux types de décalages sont mesurés à partir du bord indiqué de l'écran jusqu'au bord correspondant de la fenêtre. Le décalage X peut être spécifié de la manière suivante :

+DÉCALAGE_X
Le bord gauche de la fenêtre doit être placé à DÉCALAGE_X pixels du bord gauche de l'écran (c'est-à-dire que la coordonnée X de l'origine de la fenêtre sera DÉCALAGE_X). DÉCALAGE_X peut être négatif, auquel cas le bord gauche de la fenêtre sera en dehors de l'écran.
-DÉCALAGE_X
Le bord droit de la fenêtre doit être placé à DÉCALAGE_X pixels du bord droit de l'écran. DÉCALAGE_X peut être négatif, auquel cas le bord droit de la fenêtre sera en dehors de l'écran.

Le décalage Y a des significations similaires :

+DÉCALAGE_Y
Le bord supérieur de la fenêtre doit être à DÉCALAGE_Y pixels du bord supérieur de l'écran (c'est-à-dire que la coordonnée Y de l'origine de la fenêtre sera DÉCALAGE_Y). DÉCALAGE_Y peut être négatif, auquel cas le bord supérieur de la fenêtre sera en dehors de l'écran.
-DÉCALAGE_Y
Le bord inférieur de la fenêtre doit être à DÉCALAGE_Y pixels du bord inférieur de l'écran. DÉCALAGE_Y peut être négatif, auquel cas le bord inférieur de la fenêtre sera en dehors de l'écran.

Les décalages doivent être donnés par paires ; en d'autres termes, pour spécifier soit DÉCALAGE_X soit DÉCALAGE_Y, les deux doivent être présents. Les fenêtres peuvent être placées dans les quatre coins de l'écran en utilisant les spécifications suivantes :

+0+0
coin supérieur gauche.
-0+0
coin supérieur droit.
-0-0
coin inférieur droit.
+0-0
coin inférieur gauche.

Dans les exemples suivants, un émulateur de terminal est placé à peu près au centre de l'écran et un moniteur de charge moyenne, une boîte aux lettres et une horloge sont placées dans le coin supérieur droit :

    xterm -fn 6x10 -geometry 80x24+30+200 &
    xclock -geometry 48x48-0+0 &
    xload -geometry 48x48-96+0 &
    xbiff -geometry 48x48-48+0 &

GESTIONNAIRES DE FENÊTRES

La disposition des fenêtres sur l'écran est contrôlée par des programmes spéciaux appelés gestionnaires de fenêtres. Bien que de nombreux gestionnaires de fenêtres honorent les spécifications de géométrie telles qu'elles sont données, d'autres peuvent choisir de les ignorer (obligeant l'utilisateur à dessiner explicitement la région de la fenêtre sur l'écran avec le pointeur, par exemple).

Étant donné que les gestionnaires de fenêtres sont des programmes clients réguliers (bien que complexes), une variété d'interfaces utilisateur différentes peuvent être construites. La X.Org Foundation fournit un gestionnaire de fenêtres nommé twm qui prend en charge les fenêtres superposées, les menus contextuels, les modèles d'entrée par point-et-clic ou par clic pour taper, les barres de titre, les belles icônes (et un gestionnaire d'icônes pour ceux qui n'aiment pas les fenêtres d'icônes séparées).

Consultez votre gestionnaire de paquets de distribution pour d'autres gestionnaires de fenêtres populaires.

NOMS DE POLICES

Les collections de caractères pour afficher du texte et des symboles dans X sont connues sous le nom de polices. Une police contient généralement des images qui partagent une apparence commune et qui ont un bel aspect ensemble (par exemple, une taille unique, une graisse, une inclinaison et un jeu de caractères). De même, les collections de polices basées sur une même police (les variations sont généralement appelées romain, gras, italique, gras italique, oblique et gras oblique) sont appelées familles.

Les polices existent dans différentes tailles. Le serveur X prend en charge les polices scalables, ce qui signifie i

Il est possible de créer une police de taille arbitraire à partir d'une seule source pour cette police. Le serveur prend en charge la mise à l'échelle de polices de type contour et de polices bitmap. La mise à l'échelle de polices de contour produit généralement des résultats significativement meilleurs que celle de polices bitmap.

Un serveur X peut obtenir des polices à partir de fichiers individuels stockés dans des répertoires du système de fichiers, ou à partir d'un ou plusieurs serveurs de polices, ou encore à partir d'un mélange de répertoires et de serveurs de polices. La liste des emplacements que le serveur recherche lors de la tentative de trouver une police est contrôlée par son chemin de polices. Bien que la plupart des installations choisissent d'avoir le serveur démarré avec tous les répertoires de polices couramment utilisés dans le chemin de polices, le chemin de polices peut être modifié à tout moment avec le programme xset. Cependant, il est important de se rappeler que les noms de répertoires se trouvent sur la machine du serveur, et non sur celle de l'application.

Les fichiers de polices bitmap sont généralement créés en compilant une description textuelle de police sous forme binaire, à l'aide de bdftopcf. Les bases de données de polices sont créées en exécutant le programme mkfontdir dans le répertoire contenant les versions source ou compilées des polices. Chaque fois que des polices sont ajoutées à un répertoire, mkfontdir doit être réexécuté afin que le serveur puisse trouver les nouvelles polices. Pour que le serveur relise la base de données des polices, réinitialisez le chemin de polices avec le programme xset. Par exemple, pour ajouter une police à un répertoire privé, les commandes suivantes pourraient être utilisées :

    % cp nouvellepolice.pcf ~/mespolices
    % mkfontdir ~/mespolices
    % xset fp rehash

Les programmes xfontsel et xlsfonts peuvent être utilisés pour parcourir les polices disponibles sur un serveur. Les noms de polices ont tendance à être assez longs car ils contiennent toutes les informations nécessaires pour identifier de manière unique des polices individuelles. Cependant, le serveur X prend en charge les jokers pour les noms de polices, de sorte que la spécification complète

    -adobe-courier-medium-r-normal--10-100-75-75-m-60-iso8859-1

pourrait être abrégée en :

    -*-courier-medium-r-normal--*-100-*-*-*-*-iso8859-1

Étant donné que le shell a également des significations spéciales pour * et ?, les noms de polices avec jokers doivent être mis entre guillemets :

    % xlsfonts -fn '-*-courier-medium-r-normal--*-100-*-*-*-*-*-*'

Le programme xlsfonts peut être utilisé pour lister toutes les polices qui correspondent à un modèle donné. Sans arguments, il liste toutes les polices disponibles. Cela listera généralement la même police dans de nombreuses tailles différentes. Pour voir uniquement les noms de polices de base scalables, essayez d'utiliser l'un des modèles suivants :

    -*-*-*-*-*-*-0-0-0-0-*-0-*-*
    -*-*-*-*-*-*-0-0-75-75-*-0-*-*
    -*-*-*-*-*-*-0-0-100-100-*-0-*-*

Pour convertir l'un des noms résultants en une police à une taille spécifique, remplacez l'un des deux premiers zéros par une valeur non nulle. Le champ contenant le premier zéro correspond à la taille en pixels ; remplacez-le par une hauteur spécifique en pixels pour nommer une police à cette taille. Alternativement, le champ contenant le deuxième zéro correspond à la taille en points ; remplacez-le par une taille spécifique en décipoints (il y a 722,7 décipoints par pouce) pour nommer une police à cette taille. Le dernier zéro est un champ de largeur moyenne, mesuré en dixièmes de pixels ; certains serveurs effectueront une mise à l'échelle anamorphique si cette valeur est spécifiée.

NOMS DE SERVEUR DE POLICES

L'une des formes suivantes peut être utilisée pour nommer un serveur de polices qui accepte les connexions TCP :

    tcp/nom_hote:port
    tcp/nom_hote:port/liste_catalogue

Le nom_hote spécifie le nom (ou l'adresse numérique décimale) de la machine sur laquelle le serveur de polices s'exécute. Le port est le port TCP décimal sur lequel le serveur de polices écoute les connexions. La liste_catalogue spécifie une liste de noms de catalogues, avec '+' comme séparateur.

Exemples : tcp/x.org:7100, tcp/198.112.45.11:7100/tous.

NOMS DE COULEUR

La plupart des applications offrent des moyens de personnaliser (généralement via des ressources ou des arguments de ligne de commande) les couleurs des divers éléments textuels et graphiques qu'elles affichent. Une couleur peut être spécifiée soit par un nom de couleur abstrait, soit par une spécification numérique de couleur. La spécification numérique peut identifier une couleur en termes dépendant du périphérique (RVB) ou indépendants du périphérique. Les chaînes de couleurs ne sont pas sensibles à la casse.

X prend en charge l'utilisation de noms de couleurs abstraits, par exemple, "rouge", "bleu". Une valeur pour ce nom abstrait est obtenue en recherchant une ou plusieurs bases de données de noms de couleurs. Xlib recherche d'abord zéro ou plusieurs bases de données côté client ; le nombre, l'emplacement et le contenu de ces bases de données dépendent de l'implémentation. Si le nom n'est pas trouvé, la couleur est recherchée dans la base de données du serveur X. La forme textuelle de cette base de données est couramment stockée dans le fichier /usr/share/X11/rgb.txt.

Une spécification numérique de couleur se compose d'un nom d'espace de couleurs et d'un ensemble de valeurs selon la syntaxe suivante :

    <nom_espace_couleur>:<valeur>/.../<valeur>

Une spécification de périphérique RVB est identifiée par le préfixe "rgb:" et a la syntaxe suivante :

    rgb:<rouge>/<vert>/<bleu>
        <rouge>, <vert>, <bleu> := h | hh | hhh | hhhh
        h := chiffres hexadécimaux simples

Notez que h indique la valeur mise à l'échelle sur 4 bits, hh la valeur mise à l'échelle sur 8 bits, hhh la valeur mise à l'échelle sur 12 bits, et hhhh la valeur mise à l'échelle sur 16 bits, respectivement. Ces valeurs sont transmises directement au serveur X et sont supposées être corrigées en gamma.

Les huit couleurs primaires peuvent être représentées comme suit :

noir rgb:0/0/0
rouge rgb:ffff/0/0
vert rgb:0/ffff/0
bleu rgb:0/0/ffff
jaune rgb:ffff/ffff/0
magenta rgb:ffff/0/ffff
cyan rgb:0/ffff/ffff
blanc rgb:ffff/ffff/ffff

Pour des raisons de compatibilité ascendante, une syntaxe plus ancienne pour le périphérique RVB est prise en charge, mais son utilisation continue n'est pas encouragée. La syntaxe est un caractère dièse initial suivi d'une spécification numérique, dans l'un des formats suivants :

#RVB (4 bits chacun)
#RRGGBB (8 bits chacun)
#RRRGGGBBB (12 bits chacun)
#RRRRGGGGBBBB (16 bits chacun)

Le R, G et B représentent des chiffres hexadécimaux simples. Lorsque moins de 16 bits chacun sont spécifiés, ils représentent les bits de poids fort de la valeur (contrairement à la syntaxe "rgb:", dans laquelle les valeurs sont mises à l'échelle). Par exemple, #3a7 est identique à #3000a0007000.

Une spécification d'intensité RVB est identifiée par le préfixe "rgbi:" et a la syntaxe suivante :

    rgbi:<rouge>/<vert>/<bleu>

Le rouge, le vert et le bleu sont des valeurs à virgule flottante comprises entre 0,0 et 1,0, inclus. Ils représentent des valeurs d'intensité linéaire, 1,0 indiquant l'intensité maximale, 0,5 la moitié de l'intensité, et ainsi de suite. Ces valeurs seront corrigées en gamma par Xlib avant d'être envoyées au serveur X. Le format d'entrée pour ces valeurs est un signe optionnel, une chaîne de chiffres contenant éventuellement un point décimal, et un champ d'exposant optionnel contenant un E ou un e suivi d'une chaîne d'entiers éventuellement signée.

Les spécifications de chaîne standard indépendantes du périphérique ont la syntaxe suivante :

CIEXYZ:<X>/<Y>/<Z> (aucun, 1, aucun)
CIEuvY:<u>/<v>/<Y> (~.6, ~.6, 1)
CIExyY:<x>/<y>/<Y> (~.75, ~.85, 1)
CIELab:<L>/<a>/<b> (100, aucun, aucun)
CIELuv:<L>/<u>/<v> (100, aucun, aucun)
TekHVC:<H>/<V>/<C> (360, 100, 100)

Toutes les valeurs (C, H, V, X, Y, Z, a, b, u, v, y, x) sont des valeurs à virgule flottante. Certaines valeurs sont contraintes d'être comprises entre zéro et une certaine borne supérieure ; les bornes supérieures sont indiquées entre parenthèses ci-dessus. La syntaxe de ces valeurs est un signe '+' ou '-' optionnel, une chaîne de chiffres contenant éventuellement un point décimal, et un champ d'exposant optionnel composé d'un 'E' ou d'un 'e' suivi d'un '+' ou '-' optionnel suivi d'une chaîne de chiffres.

Pour plus d'informations sur les couleurs indépendantes du périphérique, consultez le manuel de référence de Xlib.

CLAVIERS

Le modèle de clavier X est divisé en deux couches : des codes spécifiques au serveur (appelés keycodes) qui représentent les touches physiques, et des symboles indépendants du serveur (appelés keysyms) qui représentent les lettres ou les mots qui apparaissent sur les touches. Deux tables sont conservées dans le serveur pour convertir les keycodes en keysyms :

liste des modificateurs
Certaines touches (comme Maj, Ctrl et Verr Maj) sont appelées modificateurs et sont utilisées pour sélectionner différents symboles attachés à une seule touche (par exemple, Maj-a génère un A majuscule, et Ctrl-l génère un caractère de contrôle ^L). Le serveur conserve une liste de keycodes correspondant aux diverses touches modificatrices. Chaque fois qu'une touche est pressée ou relâchée, le serveur génère un événement qui contient le keycode de la touche indiquée ainsi qu'un masque spécifiant quelles touches modificatrices sont actuellement enfoncées. La plupart des serveurs configurent cette liste pour qu'elle contienne initialement les diverses touches Maj, Ctrl et Verr Maj du clavier.
table de mappage de clavier
Les applications traduisent les keycodes des événements et les masques de modificateurs en keysyms à l'aide d'une table de keysyms qui contient une ligne pour chaque keycode et une colonne pour divers états de modificateurs. Cette table est initialisée par le serveur pour correspondre aux conventions tyographiques normales. La sémantique exacte de la manière dont la table est interprétée pour produire des keysyms dépend du programme, des bibliothèques et de la méthode de saisie de langue utilisés, mais les conventions suivantes pour les quatre premiers keysyms de chaque ligne sont généralement respectées :

Les quatre premiers éléments de la liste sont divisés en deux groupes de keysyms. Le groupe 1 contient le premier et le deuxième keysyms ; le groupe 2 contient le troisième et le quatrième keysyms. Au sein de chaque groupe, si le premier élément est alphabétique et le second i

Le keysym spécial NoSymbol, alors le groupe est considéré comme équivalent à un groupe dans lequel le premier élément est la lettre minuscule et le second élément est la lettre majuscule.

La commutation entre les groupes est contrôlée par le keysym nommé MODE SWITCH, en attachant ce keysym à une touche et en attachant cette touche à l'un des modificateurs Mod1 à Mod5. Ce modificateur est appelé le « modificateur de groupe ». Le groupe 1 est utilisé lorsque le modificateur de groupe est désactivé, et le groupe 2 est utilisé lorsque le modificateur de groupe est activé.

Au sein d'un groupe, l'état du modificateur détermine quel keysym utiliser. Le premier keysym est utilisé lorsque les modificateurs Shift et Lock sont désactivés. Le second keysym est utilisé lorsque le modificateur Shift est activé, lorsque le modificateur Lock est activé et que le second keysym est alphabétique majuscule, ou lorsque le modificateur Lock est activé et est interprété comme ShiftLock. Sinon, lorsque le modificateur Lock est activé et est interprété comme CapsLock, l'état du modificateur Shift est d'abord appliqué pour sélectionner un keysym ; mais si ce keysym est alphabétique minuscule, le keysym majuscule correspondant est utilisé à la place.

OPTIONS

La plupart des programmes X tentent d'utiliser les mêmes noms pour les options et les arguments de la ligne de commande. Toutes les applications écrites avec les X Toolkit Intrinsics acceptent automatiquement les options suivantes :

-display display
Cette option spécifie le nom du serveur X à utiliser.
-geometry geometry
Cette option spécifie la taille et la position initiales de la fenêtre.
-bg couleur, -background couleur
L'une ou l'autre option spécifie la couleur à utiliser pour l'arrière-plan de la fenêtre.
-bd couleur, -bordercolor couleur
L'une ou l'autre option spécifie la couleur à utiliser pour la bordure de la fenêtre.
-bw nombre, -borderwidth nombre
L'une ou l'autre option spécifie la largeur en pixels de la bordure de la fenêtre.
-fg couleur, -foreground couleur
L'une ou l'autre option spécifie la couleur à utiliser pour le texte ou les graphiques.
-fn police, -font police
L'une ou l'autre option spécifie la police à utiliser pour afficher le texte.
-iconic

Cette option indique que l'utilisateur préférerait que les fenêtres de l'application ne soient pas initialement visibles, comme si les fenêtres avaient été immédiatement iconisées par l'utilisateur. Les gestionnaires de fenêtres peuvent choisir de ne pas honorer la demande de l'application.
-name

Cette option spécifie le nom sous lequel les ressources de l'application doivent être trouvées. Cette option est utile dans les alias de shell pour distinguer les invocations d'une application, sans avoir à créer de liens pour modifier le nom du fichier exécutable.
-rv, -reverse
L'une ou l'autre option indique que le programme doit simuler la vidéo inversée si possible, souvent en échangeant les couleurs de premier plan et d'arrière-plan. Tous les programmes ne prennent pas en charge cela ou ne l'implémentent pas correctement. Il est généralement utilisé uniquement sur les écrans monochromes.
+rv

Cette option indique que le programme ne doit pas simuler la vidéo inversée. Elle est utilisée pour remplacer les valeurs par défaut, car la vidéo inversée ne fonctionne pas toujours correctement.
-selectionTimeout
Cette option spécifie le délai en millisecondes dans lequel deux applications communicantes doivent se répondre pour une demande de sélection.
-synchronous
Cette option indique que les requêtes au serveur X doivent être envoyées de manière synchrone, au lieu d'asynchrone. Cette option spécifie le titre à utiliser pour cette fenêtre. Cette information est parfois utilisée par un gestionnaire de fenêtres pour fournir une sorte d'en-tête identifiant la fenêtre.

Cette option spécifie la langue, le territoire et le jeu de caractères à utiliser pour résoudre les noms de fichiers de ressources et autres.

Cette option spécifie un nom de ressource et une valeur pour remplacer les valeurs par défaut. Elle est également très utile pour définir des ressources qui n'ont pas d'arguments de ligne de commande explicites.

RESSOURCES

Pour faciliter l'adaptation des applications aux préférences personnelles, X fournit un mécanisme pour stocker des valeurs par défaut pour les ressources des programmes (par exemple, la couleur de fond, le titre de la fenêtre, etc.) qui est utilisé par les programmes qui utilisent des toolkits basés sur la bibliothèque X Toolkit Intrinsics libXt. (Les programmes utilisant les toolkits courants Gtk+ et Qt utilisent d'autres mécanismes de configuration.) Les ressources sont spécifiées sous forme de chaînes qui sont lues à partir de divers emplacements lorsqu'une application est exécutée. Les composants du programme sont nommés de manière hiérarchique, chaque nœud de la hiérarchie étant identifié par une classe et un nom d'instance. Au niveau supérieur se trouvent la classe et le nom d'instance de l'application elle-même. Par convention, le nom de classe de l'application est le même que le nom du programme, mais avec la première lettre capitalisée (par exemple, Bitmap ou Emacs), bien que certains programmes commençant par la lettre « x » capitalisent également la deuxième lettre pour des raisons historiques.

La syntaxe précise des ressources est la suivante :

ResourceLine    =       Comment | IncludeFile | ResourceSpec | <ligne vide>
Comment         =       "!" {<tout caractère sauf nul ou nouvelle ligne>}
IncludeFile     =       "#" WhiteSpace "include" WhiteSpace FileName WhiteSpace
FileName        =       <nom de fichier valide pour le système d'exploitation>
ResourceSpec    =       WhiteSpace ResourceName WhiteSpace ":" WhiteSpace Value
ResourceName    =       [Binding] {Component Binding} ComponentName
Binding         =       "." | "*"
WhiteSpace      =       {<espace> | <tabulation horizontale>}
Component       =       "?" | ComponentName
ComponentName   =       NameChar {NameChar}
NameChar        =       "a"-"z" | "A"-"Z" | "0"-"9" | "_" | "-"
Value           =       {<tout caractère sauf nul ou nouvelle ligne non échappée>}

Les éléments séparés par une barre verticale (|) sont des alternatives. Les accolades ({...}) indiquent zéro ou plusieurs répétitions des éléments contenus. Les crochets ([...]) indiquent que l'élément contenu est optionnel. Les guillemets ("...") sont utilisés autour des caractères littéraux.

Les lignes IncludeFile sont interprétées en remplaçant la ligne par le contenu du fichier spécifié. Le mot « include » doit être en minuscules. Le nom du fichier est interprété par rapport au répertoire du fichier dans lequel la ligne apparaît (par exemple, si le nom du fichier ne contient aucun répertoire ou contient une spécification de répertoire relative).

Si un ResourceName contient une séquence contiguë de deux caractères de liaison ou plus, la séquence sera remplacée par un seul caractère « . » si la séquence ne contient que des caractères « . », sinon la séquence sera remplacée par un seul caractère « * ».

Une base de données de ressources ne contient jamais plus d'une entrée pour un ResourceName donné. Si un fichier de ressources contient plusieurs lignes avec le même ResourceName, la dernière ligne du fichier est utilisée.

Tout caractère d'espacement avant ou après le nom ou le deux-points dans un ResourceSpec est ignoré. Pour permettre à une Value de commencer par un espace blanc, la séquence de deux caractères « \espace » (barre oblique inverse suivie d'un espace) est reconnue et remplacée par un caractère d'espace, et la séquence de deux caractères « \tab » (barre oblique inverse suivie d'une tabulation horizontale) est reconnue et remplacée par un caractère de tabulation horizontale. Pour permettre à une Value de contenir des caractères de nouvelle ligne intégrés, la séquence de deux caractères « \n » est reconnue et remplacée par un caractère de nouvelle ligne. Pour permettre à une Value d'être divisée sur plusieurs lignes dans un fichier texte, la séquence de deux caractères « \nouvelle ligne » (barre oblique inverse suivie d'une nouvelle ligne) est reconnue et supprimée de la valeur. Pour permettre à une Value de contenir des codes de caractères arbitraires, la séquence de quatre caractères « \nnn », où chaque n est un chiffre compris entre « 0 » et « 7 », est reconnue et remplacée par un seul octet contenant la valeur octale spécifiée par la séquence. Enfin, la séquence de deux caractères « \\ » est reconnue et remplacée par une seule barre oblique inverse.

Lorsqu'une application recherche la valeur d'une ressource, elle spécifie un chemin complet dans la hiérarchie, avec les noms de classe et d'instance. Cependant, les valeurs de ressources sont généralement fournies avec des noms et des classes partiellement spécifiés, en utilisant des constructions de correspondance de motifs. Un astérisque (*) est une liaison lâche et est utilisé pour représenter un nombre quelconque de composants intermédiaires, y compris aucun. Un point (.) est une liaison serrée et est utilisé pour séparer des composants immédiatement adjacents. Un point d'interrogation (?) est utilisé pour faire correspondre n'importe quel nom de composant ou classe unique. Une entrée de base de données ne peut pas se terminer par une liaison lâche ; le composant final (qui ne peut pas être « ? ») doit être spécifié. L'algorithme de recherche parcourt la base de données de ressources à la recherche de l'entrée qui correspond le plus étroitement (est la plus spécifique pour) le nom et la classe complets interrogés. Lorsque plusieurs entrées de base de données correspondent au nom et à la classe complets, des règles de précédence sont utilisées pour en sélectionner une seule.

Le nom et la classe complets sont analysés de gauche à droite (du niveau le plus élevé de la hiérarchie au plus bas), un composant à la fois. À chaque niveau, le composant et/ou la liaison correspondants de chaque entrée correspondante sont déterminés, et ces composants et liaisons correspondants sont comparés selon des règles de précédence. Chacune des règles est appliquée à chaque niveau, avant de passer au niveau suivant, jusqu'à ce qu'une règle sélectionne une seule entrée par rapport à toutes les autres. Les règles (par ordre de précédence) sont :

1.
Une entrée qui contient un composant correspondant (qu'il s'agisse d'un nom, d'une classe ou de « ? ») prend la précédence sur les entrées qui élident le niveau (c'est-à-dire les entrées qui correspondent au niveau dans une liaison lâche).
2.

PRIORITÉS

1.
Une entrée avec un nom correspondant a la priorité sur les entrées correspondant à une classe et les entrées qui correspondent en utilisant « ? ». Une entrée avec une classe correspondante a la priorité sur les entrées qui correspondent en utilisant « ? ».
2.

Les programmes basés sur X Toolkit Intrinsics obtiennent les ressources des sources suivantes (les autres programmes supportent généralement un sous-ensemble de ces sources) :

PROPRIÉTÉ RESOURCE_MANAGER DE LA FENÊTRE RACINE
Toutes les ressources globales qui devraient être disponibles pour les clients sur toutes les machines doivent être stockées dans la propriété RESOURCE_MANAGER sur la fenêtre racine du premier écran en utilisant le programme xrdb. Ceci est souvent pris en charge lorsque l'utilisateur démarre X via le gestionnaire d'affichage ou xinit.
PROPRIÉTÉ SCREEN_RESOURCES DE LA FENÊTRE RACINE
Toutes les ressources spécifiques à un écran donné (par exemple les couleurs) qui devraient être disponibles pour les clients sur toutes les machines doivent être stockées dans la propriété SCREEN_RESOURCES sur la fenêtre racine de cet écran. Le programme xrdb triera les ressources automatiquement et les placera dans RESOURCE_MANAGER ou SCREEN_RESOURCES, selon le cas.
fichiers spécifiques à l'application
Les répertoires nommés par la variable d'environnement XUSERFILESEARCHPATH ou la variable d'environnement XAPPLRESDIR (qui nomme un seul répertoire et devrait se terminer par un '/' sur les systèmes POSIX), plus les répertoires dans un emplacement standard (généralement sous /usr/share/X11/, mais cela peut être remplacé par la variable d'environnement XFILESEARCHPATH) sont recherchés pour les ressources spécifiques à l'application. Par exemple, les ressources par défaut des applications sont généralement conservées dans /usr/share/X11/app-defaults/. Voir le manuel X Toolkit Intrinsics - C Language Interface pour plus de détails.
XENVIRONMENT
Toutes les ressources spécifiques à l'utilisateur et à la machine peuvent être spécifiées en définissant la variable d'environnement XENVIRONMENT avec le nom d'un fichier de ressources à charger par toutes les applications. Si cette variable n'est pas définie, un fichier nommé $HOME/.Xdefaults-hostname est recherché à la place, où hostname est le nom de l'hôte sur lequel l'application s'exécute.
-xrm chaîne_de_ressources
Les ressources peuvent également être spécifiées depuis la ligne de commande. La chaîne_de_ressources est un nom et une valeur de ressource uniques comme indiqué ci-dessus. Notez que si la chaîne contient des caractères interprétés par le shell (par exemple, l'astérisque), ils doivent être entre guillemets. Un nombre quelconque d'arguments -xrm peut être donné sur la ligne de commande.

Les ressources des programmes sont organisées en groupes appelés classes, de sorte que des collections de ressources individuelles (chacune appelée instance) puissent être définies toutes à la fois. Par convention, le nom d'instance d'une ressource commence par une lettre minuscule et le nom de classe par une lettre majuscule. Les ressources de plusieurs mots sont concaténées avec la première lettre des mots suivants en majuscule. Les applications écrites avec le X Toolkit Intrinsics auront au moins les ressources suivantes :

background (classe Background)
Cette ressource spécifie la couleur à utiliser pour l'arrière-plan de la fenêtre.
borderWidth (classe BorderWidth)
Cette ressource spécifie la largeur en pixels de la bordure de la fenêtre.
borderColor (classe BorderColor)
Cette ressource spécifie la couleur à utiliser pour la bordure de la fenêtre.

La plupart des applications utilisant le X Toolkit Intrinsics ont également la ressource foreground (classe Foreground), qui spécifie la couleur à utiliser pour le texte et les graphiques à l'intérieur de la fenêtre.

DISPLAY
C'est la seule variable d'environnement obligatoire. Elle doit pointer vers un serveur X. Voir la section « Noms d'affichage » ci-dessus.

Elle doit pointer vers un fichier contenant des données d'autorisation. La valeur par défaut est $HOME/.Xauthority. Voir Xsecurity(7), xauth(1), xdm(1), Xau(3).

Elle doit pointer vers un fichier contenant des données d'autorisation. La valeur par défaut est $HOME/.ICEauthority.
LC_ALL, LC_CTYPE, LANG
La première valeur non vide parmi ces trois détermine la facette de locale actuelle pour la gestion des caractères, et en particulier le codage de texte par défaut. Voir locale(7), setlocale(3), locale(1).
XMODIFIERS
Cette variable peut être définie pour contenir des informations supplémentaires importantes pour le réglage de locale actuel. Typiquement définie à @im=<méthode-d'entrée> pour activer une méthode d'entrée particulière. Voir XSetLocaleModifiers(3).

    /usr/share/X11/%l/%T/%N%C%S:\

    /usr/share/X11/%l/%T/%N%S:\
    /usr/share/X11/%T/%N%S:\
    /usr/lib/X11/%L/%T/%N%C%S:\
    /usr/lib/X11/%l/%T/%N%C%S:\

Un modèle de chemin est transformé en chemin d'accès en substituant :

    %N => nom (nom de base) recherché

    $XAPPLRESDIR/%l/%N%C:\
    $XAPPLRESDIR/%N%C:\

    $XAPPLRESDIR/%L/%N:\
    $XAPPLRESDIR/%l/%N:\

    $HOME/%N

$XAPPLRESDIR est par défaut $HOME, voir ci-dessous.

Un modèle de chemin est transformé en chemin d'accès en substituant :

    %D => le chemin par défaut spécifique à l'implémentation
    %N => nom (nom de base) recherché
    %T => type (nom de répertoire) recherché
    %S => suffixe recherché
    %C => valeur de la ressource « customization »
          (classe « Customization »)
    %L => le nom de la locale
    %l => la langue de la locale (partie avant '_')
    %t => le territoire de la locale (partie après '_` mais avant '.')
    %c => l'encodage de la locale (partie après '.')
XAPPLRESDIR
Elle doit pointer vers un répertoire de base où l'utilisateur stocke les fichiers de ressources dépendant de l'application. La valeur par défaut est $HOME. Uniquement utilisé si XUSERFILESEARCHPATH n'est pas défini.
XKEYSYMDB
Elle doit pointer vers un fichier contenant des définitions de keysym non standard. La valeur par défaut est /usr/share/X11/XKeysymDB.
XCMSDB
Elle doit pointer vers un fichier de base de données de noms de couleurs. La valeur par défaut est /usr/lib/X11/Xcms.txt.

DIAGNOSTICS

Une grande variété de messages d'erreur est générée par divers programmes. Le gestionnaire d'erreurs par défaut dans Xlib (également utilisé par de nombreux kits d'outils) utilise des ressources standard pour construire des messages de diagnostic lorsque des erreurs se produisent. Les paramètres par défaut de ces messages sont généralement stockés dans /usr/share/X11/XErrorDB. Si ce fichier n'est pas présent, les messages d'erreur seront plutôt concis et cryptiques.

Lorsque les X Toolkit Intrinsics rencontrent des erreurs lors de la conversion de chaînes de ressources au format interne approprié, aucun message d'erreur n'est généralement imprimé. C'est pratique lorsqu'il est souhaitable d'avoir un ensemble de ressources pour une variété d'affichages (par exemple, couleur vs monochrome, beaucoup de polices vs très peu, etc.), bien que cela puisse poser des problèmes pour déterminer pourquoi une application échoue. Ce comportement peut être remplacé en définissant la ressource StringConversionWarnings.

Pour forcer les X Toolkit Intrinsics à imprimer toujours les messages d'erreur de conversion de chaîne, la ressource suivante doit être placée dans le fichier qui est chargé sur la propriété RESOURCE_MANAGER en utilisant le programme xrdb (souvent appelé .Xresources ou .Xres dans le répertoire personnel de l'utilisateur) :

    *StringConversionWarnings: on

Pour que les messages de conversion soient imprimés pour une application particulière uniquement, le nom d'instance approprié peut être placé avant l'astérisque :

    xterm*StringConversionWarnings: on
