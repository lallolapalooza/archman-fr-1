XS::Parse::Infix(3pm) Documentation Perl Contribuée par l'Utilisateur XS::Parse::Infix(3pm)

NOM

"XS::Parse::Infix" - Fonctions XS pour aider à l'analyse des opérateurs infixes

DESCRIPTION

Ce module fournit quelques fonctions XS pour aider à l'écriture de modules de syntaxe qui fournissent de nouveaux opérateurs infixes comme syntaxe perl, principalement pour les auteurs de plugins de syntaxe. Il est peu probable qu'il soit d'une grande utilité pour d'autres ; et il est très peu probable qu'il soit utile lors de l'écriture de code perl utilisant ces fonctions. Sauf si vous écrivez un plugin de syntaxe en utilisant XS, ce module n'est pas pour vous.

Ce module est également expérimental pour le moment, et la conception est encore en évolution et sujette à changement. Les versions ultérieures pourraient casser la compatibilité ABI, nécessitant des modifications ou du moins une reconstruction de tout module qui en dépend.

De plus, les endroits où cette fonctionnalité peut être utilisée sont relativement restreints. Le support des opérateurs infixes personnalisés tel qu'ajouté dans la version de développement de Perl "v5.37.7", et est donc présent dans Perl "v5.38.0".

De plus, les différents types de jetons "XPK_INFIX_*" de XS::Parse::Keyword peuvent interroger ce module, donc certaines syntaxes fournies par d'autres modules pourront être en mesure d'utiliser ces nouveaux opérateurs infixes.

Opérateurs Nommés Lexicalement vs. Globalement

Depuis la version 0.43, le mode de fonctionnement de ce module a changé. Depuis cette version, la méthode préférée de fonctionnement pour les opérateurs infixes est que le module qui les enregistre les crée avec un nom entièrement qualifié (c'est-à-dire incluant le nom du package qui les implémente). D'autres codes qui souhaitent importer l'opérateur peuvent alors lui fournir un nom local visible dans une portée. Cela agit comme un alias pour celui entièrement qualifié et enregistré. Le nom importé n'a pas besoin d'être le même dans différentes portées - cela permet aux opérateurs importés d'être renommés dans des portées spécifiques pour éviter les conflits de noms.

Les versions antérieures de ce module ne supportaient que les opérateurs qui ont un nom global qui peut ou non être activé dans les portées lexicales. Avec ce modèle, bien que la visibilité d'un opérateur puisse être contrôlée par portée, s'il est visible, il doit toujours avoir le même nom et ne peut pas être renommé pour éviter un conflit de noms.

À une future version de ce module, l'ancienne méthode pourra être supprimée, une fois que tous les modules CPAN existants auront été mis à jour vers le nouveau modèle.

CONSTANTES

HAVE_PL_INFIX_PLUGIN

if( XS::Parse::Infix::HAVE_PL_INFIX_PLUGIN ) { ... }

Cette constante est vraie si elle est construite sur un perl qui prend en charge le mécanisme d'extension "PL_infix_plugin", ce qui signifie que les opérateurs infixes personnalisés enregistrés auprès de ce module seront effectivement reconnus par l'analyseur perl.

Aucune version de production réelle de perl ne prend encore en charge cette fonctionnalité, mais voir ci-dessus pour les détails des versions de développement qui le font.

FONCTIONS PERL

apply_infix

$pkg->apply_infix( $on, $args, @infix );

Depuis la version 0.43.

Destiné à être appelé par les méthodes "import" et "unimport" d'un module qui implémente des opérateurs infixes. Ceci met en place les différentes clés requises dans le hash des indices lexicaux pour créer un alias lexical pour le(s) opérateur(s) demandé(s).

$on doit être une valeur vraie pour "import" ou une valeur fausse pour "unimport". $args doit être une référence vers le tableau des arguments, qui sera modifié pour extraire les valeurs reconnues, laissant derrière tout le reste non reconnu. @infix doit être une liste de noms d'opérateurs implémentés par le package d'importation, nommés par $pkg.

Après avoir appelé cette méthode, l'appelant doit inspecter les valeurs restantes dans le tableau des arguments, soit pour les traiter d'une autre manière, soit simplement pour se plaindre d'elles.

package Some::Infix::Module;
sub import
{
   my $pkg = shift;
   $pkg->XS::Parse::Infix::apply_infix( 1, \@_, qw( operator names here ) );
   die "Symboles non reconnus: @_" if @_;
}

Lorsque ce module est utilisé avec "use", les opérateurs nommés sont renommés à partir des noms entièrement qualifiés.

use Some::Infix::Module qw( operator );
my $z = $x operator $y;

À ce stade, le nom "operator" devient un alias lexical de "Some::Infix::Module::operator".

Chaque nom d'opérateur importé peut éventuellement être suivi d'options d'importation, fournies dans une référence de hash. Actuellement, la seule option nommée reconnue est "-as", qui permet au scope d'importation de fournir un nom différent pour l'opérateur importé, peut-être pour éviter des conflits de noms, ou pour la netteté.

use Some::Infix::Module operator => { -as => "myname" };
my $z = $x myname $y;  # invoque Some::Infix::Module::operator

FONCTIONS XS

boot_xs_parse_infix

void boot_xs_parse_infix(double ver);

Appelez cette fonction depuis votre section "BOOT" afin d'initialiser le module et les hooks d'analyse.

ver doit être soit 0, soit un nombre décimal pour l'exigence de version du module ; par exemple.

boot_xs_parse_infix(0.14);

parse_infix

bool parse_infix(enum XSParseInfixSelection select, struct XSParseInfixInfo **infop);

Depuis la version 0.27.

Cette fonction tente d'analyser la syntaxe d'un opérateur infixe à partir de la position actuelle de l'analyseur. Si elle réussit, elle remplit la variable pointée par infop avec un pointeur vers la structure d'informations réelle et renvoie "true". Si aucun opérateur approprié n'est trouvé, elle renvoie "false".

xs_parse_infix_new_op

OP *xs_parse_infix_new_op(const struct XSParseInfixInfo *info, U32 flags,
   OP *lhs, OP *rhs);

Cette fonction construit un nouveau fragment d'arbre d'opérations pour représenter l'invocation de l'opérateur infixe avec les opérandes donnés. Elle devrait être utilisée de la même manière que la fonction "newBINOP" du noyau de perl.

Le pointeur de structure "info" serait obtenu à partir du champ "infix" du résultat de l'invocation des différents types de jetons "XPK_INFIX_*" de "XS::Parse::Keyword", ou en appelant "parse_infix" directement.

register_xs_parse_infix

void register_xs_parse_infix(const char *opname,
   const struct XSParseInfixHooks *hooks, void *hookdata);

Cette fonction installe un ensemble de hooks d'analyse à associer au nom d'opérateur donné. Ce nouvel opérateur sera alors disponible via XS::Parse::Keyword par les différents types de jetons "XPK_INFIX_*", "parse_infix", ou pour le "PL_infix_plugin" du noyau de perl, si disponible.

Ces jetons produiront tous une structure d'informations, avec les champs suivants :

struct XSParseInfixInfo {
   const char *opname;
   OPCODE opcode;  /* pour les opérateurs intégrés, ou OP_CUSTOM pour 
                      ceux enregistrés de manière personnalisée */
   struct XSParseInfixHooks *hooks;
   void                     *hookdata;
   enum XSParseInfixClassification cls;  /* depuis la version 0.28 */
};

Si le nom de l'opérateur contient des caractères non ASCII, ils sont présumés être encodés en UTF-8. Cela sera important pour le déchiffrement.

Si opname contient une séquence double-point ("::"), elle est présumée

AMORCE DE PARSE

La structure "XSParseInfixHooks" fournit les champs suivants qui sont utilisés à diverses étapes de l'analyse syntaxique.

struct XSParseInfixHooks {
   U16 flags;
   U8 lhs_flags;
   U8 rhs_flags;
   enum XSParseInfixClassification cls;
   const char *wrapper_func_name;
   const char *permit_hintkey;
   bool (*permit)(pTHX_ void *hookdata);
   OP *(*new_op)(pTHX_ U32 flags, OP *lhs, OP *rhs, SV **parsedata, void *hookdata);
   OP *(*ppaddr)(pTHX);
   /* optionnel */
   void (*parse)(pTHX_ U32 flags, SV **parsedata, void *hookdata);
};

Drapeaux

Le champ "flags" donne des détails sur la manière de gérer l'opérateur dans son ensemble. Il doit s'agir d'un masque de bits des constantes suivantes, ou être laissé à zéro :

XPI_FLAG_LISTASSOC
Depuis la version 0.40.

Si défini, l'opérateur prend en charge la syntaxe n-aire associative par liste ; écrite sous la forme

OPERANDE op OPERANDE op OPERANDE op ...

Dans ce cas, l'opérateur personnalisé sera un LISTOP plutôt qu'un BINOP, et chaque opérande de la chaîne entière sera stocké comme enfant de celui-ci. La fonction de l'op devra savoir sur combien d'opérandes elle travaille. Il y a deux façons dont cela peut être indiqué, selon qu'il était connu au moment de la compilation.

Si le nombre d'opérandes est connu au moment de la compilation, le drapeau "OPf_STACKED" n'est pas défini, et le champ "op_private" indique le nombre d'expressions opérandes présentes.

Si le nombre n'est pas connu (par exemple, l'opérateur est utilisé comme corps d'une fonction enveloppante générée), le drapeau "OPf_STACKED" est défini. Le nombre d'arguments sera passé comme UV d'un SV supplémentaire qui est poussé en dernier sur la pile. La fonction de l'op devrait le dépiler en premier pour le découvrir.

Il est typique de commencer une fonction d'op associative par liste avec un code tel que :

int n = (PL_op->op_flags & OPf_STACKED) ? POPu : PL_op->op_private;

Si l'opérateur est associatif par liste, alors "lhs_flags" et "rhs_flags" doivent être égaux.

Les champs "lhs_flags" et "rhs_flags" donnent des détails sur la manière de gérer les opérandes de gauche et de droite, respectivement.

Il doit être défini à l'une des constantes suivantes, ou laissé à zéro :

XPI_OPERAND_TERM_LIST
L'opérande sera forcé dans un contexte de liste, en préservant "OP_PUSHMARK" au début. Cela signifie que la fonction ppfunc pour cet opérateur infixe devra faire un "POPMARK" pour le trouver.
XPI_OPERAND_LIST
Identique à ci-dessus.

Les versions plus anciennes fournissaient des constantes nommées "XPI_OPERAND_ARITH" et "XPI_OPERAND_TERM", mais elles étaient liées à une ancienne version de la branche principale de perl. Ces noms sont maintenant des alias de zéro et peuvent être supprimés du nouveau code.

De plus, les indicateurs de bits supplémentaires suivants sont définis :

XPI_OPERAND_ONLY_LOOK
Si défini, la fonction de l'opérateur promet qu'elle ne modifiera aucune de ses valeurs passées, ni ne permettra la fuite de pointeurs d'alias directs vers celles-ci via la valeur de retour ou d'autres emplacements.

Cet indicateur est facultatif ; l'omettre lorsqu'il est applicable ne changera aucun comportement observé. Le définir peut permettre d'effectuer certaines optimisations.

Actuellement, cet indicateur active simplement une optimisation dans le vérificateur d'appels pour les fonctions enveloppantes d'opérateurs infixes qui prennent des opérandes en forme de liste. Cette optimisation supprime une opération "OP_ANONLIST" qui créerait une référence de tableau anonyme temporaire pour les valeurs de ses opérandes, permettant une légère économie d'utilisation de mémoire et de temps CPU. Cette optimisation ne peut être effectuée en toute sécurité que si l'opérateur ne modifie pas ou ne conserve pas d'alias des arguments, sinon l'appelant pourrait voir des modifications inattendues ou des références de valeur aux valeurs passées.

L'étape de Sélection

Le champ "cls" donne une "classification" de l'opérateur, suggérant quel type d'opération il fournit. Ceci est utilisé comme filtre par les diverses macros de sélection de "XS::Parse::Keyword".

La classification doit être l'une des constantes "XPI_CLS_*" trouvées et décrites plus loin dans le fichier principal XSParseInfix.h.

L'étape "permit"

Par raccourci pour le cas courant, "permit_hintkey" peut pointer vers une chaîne à rechercher dans la table de hachage des indices. Si le nom de clé donné n'est pas trouvé dans la table de hachage des indices, alors le mot-clé n'est pas permis. Si la clé est présente, alors la fonction "permit" est appelée comme d'habitude.

Si le mot-clé n'est pas rejeté par une clé d'indice non trouvée dans la table de hachage des indices, la partie fonction de l'étape est appelée ensuite et doit inspecter si le mot-clé est permis à ce moment, peut-être en inspectant d'autres indices lexicaux, et ne retourner vrai que si le mot-clé est permis.

La chaîne et la fonction sont facultatives. L'une ou l'autre, ou les deux, peuvent être présentes. Si aucune n'est présente, alors le mot-clé est toujours permis - ce qui n'est probablement pas ce que vous vouliez faire.

L'étape "parse"

Si la fonction de crochet facultative "parse" est présente, elle est appelée immédiatement après que l'analyseur syntaxique a reconnu la présence de l'opérateur nommé lui-même, mais avant qu'il n'essaie de consommer le terme de droite. Cette fonction de crochet peut tenter une analyse syntaxique plus poussée, afin d'implémenter une syntaxe plus complexe comme les hyper-opérateurs.

Lorsqu'elle est invoquée, on lui passe un pointeur vers une variable de stockage de type "SV *". Elle est libre d'utiliser cette variable comme elle le souhaite pour stocker un résultat, qui sera ensuite rendu disponible à la fonction "new_op".

L'étape de Génération d'Opérateur

Si l'opérateur infixe doit être utilisé, alors l'un des champs "new_op" ou "ppaddr" explique comment créer un nouveau fragment d'arbre d'opérations.

Si "new_op" est défini, il sera utilisé, et on s'attend à ce qu'il retourne un fragment d'arbre d'opérations qui consomme les arguments LHS et RHS pour implémenter la sémantique de l'opérateur. Si l'étape facultative "parse" avait été présente auparavant, le pointeur "SV **" passé ici pointera vers le même stockage auquel "parse" avait eu accès auparavant, afin qu'il puisse récupérer les résultats.

Si "new_op" n'est pas présent, alors "ppaddr" sera utilisé à la place pour construire un nouveau BINOP ou LISTOP du type "OP_CUSTOM". Si une étape précédente "parse" avait stocké des résultats supplémentaires dans la variable "SV *", ils seront perdus ici.

La Fonction Enveloppante

De plus, si le champ "wrapper_func_name" est défini à une chaîne, cela donne le nom (entièrement qualifié) d'une fonction à générer dans le cadre de l'enregistrement de l'opérateur. Cette nouvelle fonction générée agira comme une enveloppe pour l'opérateur.

Pour les opérateurs dont le côté droit (RHS) est un scalaire, la fonction enveloppante est supposée prendre deux arguments scalaires simples. Le résultat de l'invocation de la fonction sur ces arguments sera déterminé en utilisant le code de l'opérateur.

$result = $lhs OP $rhs;
$result = WRAPPERFUNC( $lhs, $rhs );

Pour les opérateurs dont le côté droit (RHS) est une liste, la fonction enveloppante prend au moins un argument, peut-être plus. Le premier argument est le scalaire à gauche (LHS), et les arguments restants, quel que soit leur nombre, forment le côté droit (RHS) :

$result = $lhs OP @rhs;
$result = WRAPPERFUNC( $lhs, @rhs );

Pour les opérateurs qui prennent des listes des deux côtés (LHS et RHS), la fonction enveloppante prend deux arguments qui doivent être des références de tableau contenant les listes.

$result = @lhs OP @rhs;
$result = WRAPPERFUNC( \@lhs, \@rhs );

Cela crée une commodité pour accéder à l'opérateur à partir de perls qui ne prennent pas en charge "PL_infix_plugin".

Dans le cas des opérateurs scalaires infixes, la fonction enveloppante inclut également un vérificateur d'appels qui tente d'intégrer l'opérateur directement sur le site d'appel. Ainsi, dans les cas simples où la fonction est appelée directement sur exactement deux arguments scalaires (comme dans ce qui suit), aucun surcoût d'"ENTERSUB" ne sera engendré et l'arbre d'opérations généré sera identique à celui qui aurait été généré en utilisant directement la syntaxe d'opérateur infixe :

WRAPPERFUNC( $lhs, $rhs );
WRAPPERFUNC( $lhs, CONSTANT );
WRAPPERFUNC( $args[0], $args[1] );
WRAPPERFUNC( $lhs, scalar otherfunc() );

Le vérificateur est très pessimiste et ne réécrira que les appels pour lesquels il détermine que cela peut être fait en toute sécurité. Il ne réécrira aucune des formes suivantes :

WRAPPERFUNC( $onearg );            # pas assez d'arguments
WRAPPERFUNC( $x, $y, $z );         # trop d'arguments
WRAPPERFUNC( @args[0,1] );         # pas un scalaire
WRAPPERFUNC( $lhs, otherfunc() );  # pas un scalaire

La fonction enveloppante pour les opérateurs infixes qui prennent des listes des deux côtés a également un vérificateur d'appels qui tentera d'intégrer l'opérateur

en circonstances similaires. En plus des optimisations décrites ci-dessus pour les opérateurs scalaires, ce vérificateur insérera également un opérateur de référence de tableau et omettra le comportement de déréférencement qui en résulte. Ainsi, les deux lignes suivantes émettent le même optree, sans "OP_SREFGEN" ni "OP_RV2AV" :

@lhs OP @rhs;
WRAPPERFUNC( \@lhs, \@rhs );

Notez que techniquement, cette optimisation n'est pas strictement transparente dans le cas particulier où l'un des tableaux référencés est également le stockage sous-jacent d'une référence bénie, et que la classe de cet objet possède un surchargeur "@{}".

my @arr;
package SomeClass {
   use overload '@{}' => sub { return ["values", "go", "here"]; };
}
bless \@arr, "SomeClass";
# cela n'invoquera pas réellement l'opérateur de surcharge
WRAPPERFUNC( \@arr, [4, 5, 6] );

Comme ce cas particulier concerne la prise de références dupliquées vers la même variable de stockage sous-jacente d'un objet béni, il ne devrait pas affecter de code réel ; les objets normaux passés par référence à la fonction wrapper exécuteront leurs méthodes de surcharge comme d'habitude.

Le vérificateur d'appels pour les opérandes de liste peut facultativement supprimer également un op de type "OP_ANONLIST", qui est utilisé pour la construction de références d'arrays anonymes :

($u, $v, $w) OP ($x, $y, $z);
WRAPPERFUNC( [$u, $v, $w], [$x, $y, $z] );

Cette optimisation n'est effectuée que si l'opérateur a déclaré qu'il était sûr de le faire, via le drapeau "XPI_OPERAND_ONLY_LOOK".

Si une fonction du nom donné existe déjà au moment de l'enregistrement, elle sera laissée intacte et aucune nouvelle fonction wrapper ne sera créée. Cela permet au même opérateur infixe d'avoir plusieurs formes de son nom ; par exemple, pour permettre à la fois une translittération Unicode réelle et une translittération ASCII de secours du même opérateur. Le premier enregistrement créera la fonction wrapper ; le suivant l'ignorera car il serait par ailleurs identique.

Notez que lors de la génération d'un optree pour un appel de fonction wrapper, la fonction de hook "new_op" sera appelée avec un pointeur "NULL" pour le stockage des données d'analyse de type "SV *", car il n'y aura pas d'opportunité pour que le hook "parse" s'exécute dans ce cas.

DEPARSE

Ce module fonctionne avec B::Deparse afin de fournir automatiquement un support de déparessement pour les opérateurs infixes. Chaque opérateur infixe implémenté comme un op personnalisé (et donc avec le champ de hook "ppaddr" défini) aura une logique de déparessement ajoutée. Cela lui permettra de se déparesser soit vers la fonction wrapper nommée, soit vers la syntaxe de l'opérateur infixe si perl est activé avec "PL_infix_plugin" et que l'indice lexical approprié est activé au niveau du site d'appel.

Pour que cela fonctionne, il est important que votre opérateur personnalisé ne soit *pas* enregistré comme opérateur personnalisé à l'aide de la fonction Perl_register_custom_op(). Cet enregistrement sera effectué par "XS::Parse::Infix" lui-même au moment où l'opérateur infixe est enregistré.
