XS::Parse::Keyword(3pm) Documentation Perl fournie par l'utilisateur XS::Parse::Keyword(3pm)

NOM

"XS::Parse::Keyword" - Fonctions XS pour aider à l'analyse syntaxique de la syntaxe des mots-clés

DESCRIPTION

Ce module fournit certaines fonctions XS pour aider à l'écriture de modules de syntaxe qui fournissent une nouvelle syntaxe visible depuis Perl, principalement pour les auteurs de plugins de mots-clés utilisant le mécanisme de hook "PL_keyword_plugin". Il est peu probable qu'il soit d'une grande utilité pour d'autres ; et il est très peu probable qu'il soit utile lors de l'écriture de code Perl utilisant ces éléments. À moins que vous n'écriviez un plugin de mot-clé en utilisant XS, ce module n'est pas pour vous.

Ce module est également actuellement expérimental, et sa conception est toujours en évolution et sujette à changement. Les versions ultérieures peuvent casser la compatibilité ABI, nécessitant des modifications ou du moins une recompilation de tout module qui en dépend.

FONCTIONS XS

boot_xs_parse_keyword

void boot_xs_parse_keyword(double ver);

Appelez cette fonction depuis votre section "BOOT" afin d'initialiser le module et les hooks d'analyse.

ver doit être 0 ou un nombre décimal pour l'exigence de version du module ; par exemple :

boot_xs_parse_keyword(0.14);

register_xs_parse_keyword

void register_xs_parse_keyword(const char *keyword,
  const struct XSParseKeywordHooks *hooks, void *hookdata);

Cette fonction installe un ensemble de hooks d'analyse à associer au mot-clé donné. Un tel mot-clé sera alors automatiquement géré par un analyseur de mots-clés installé par "XS::Parse::Keyword" lui-même.

HOOKS D'ANALYSE

La structure "XSParseKeywordHooks" fournit les étapes de hook suivantes, qui sont invoquées dans l'ordre donné.

flags

Les drapeaux suivants sont définis :

"XPK_FLAG_EXPR"
La fonction d'analyse ou de construction est censée retourner "KEYWORD_PLUGIN_EXPR".
"XPK_FLAG_STMT"
La fonction d'analyse ou de construction est censée retourner "KEYWORD_PLUGIN_STMT".

Ces deux drapeaux sont principalement destinés à fournir des informations statiques au moment de l'enregistrement afin d'aider l'analyse statique ou d'autres tâches connexes à savoir quel type d'élément grammatical ce mot-clé produira.

"XPK_FLAG_AUTOSEMI"
La syntaxe forme une instruction complète, qui doit être suivie d'un point-virgule séparateur d'instruction (";"). Ce point-virgule est facultatif à la fin d'un bloc.

Le point-virgule, s'il est présent, sera consommé automatiquement.

"XPK_FLAG_BLOCKSCOPE"
L'ensemble du processus d'analyse et de construction sera encapsulé dans une paire d'appels block_start() et block_end(). Cela garantit que, par exemple, toutes les variables lexicales nouvellement introduites ne s'échappent pas de la portée de la syntaxe créée par le mot-clé.
"XPK_FLAG_PERMIT_LEXICAL"
Le mot-clé autorise un préfixe "my", pour que l'auteur indique qu'il doit avoir un effet lexical. Généralement, cela n'aurait de sens que pour les mots-clés qui déclarent une nouvelle entité nommée, où normalement l'entité de ce mot-clé est nommée dans la table des symboles à la place.

Au moment de l'"analyse" et de la "construction", ce fait sera indiqué par "PL_parser->in_my" étant défini à la valeur "KEY_my", plutôt que son zéro habituel.

Ce drapeau est ignoré silencieusement sur les versions de Perl antérieures à 5.16, car sur les versions antérieures, la solution de contournement de détection du préfixe "my" provoque des échecs d'analyse apparemment sans rapport dans utf8.pm.

L'étape "permit"

const char *permit_hintkey;
bool (*permit) (pTHX_ void *hookdata);

Appelée par le hook d'analyse de mot-clé installé qui est utilisé pour gérer les mots-clés enregistrés par "register_xs_parse_keyword".

En raccourci pour le cas courant, le "permit_hintkey" peut pointer vers une chaîne à rechercher dans la table des indices. Si le nom de clé donné n'est pas trouvé dans la table des indices, alors le mot-clé n'est pas autorisé. Si la clé est présente, alors la fonction "permit" est invoquée comme normal.

Si elle n'est pas rejetée par une clé d'indice qui n'a pas été trouvée dans la table des indices, la partie fonction de l'étape est appelée ensuite et doit inspecter si le mot-clé est autorisé à ce moment-là, peut-être en inspectant d'autres indices lexicaux, et retourner vrai seulement si le mot-clé est autorisé.

La chaîne et la fonction sont facultatives. L'une ou l'autre ou les deux peuvent être présentes. Si ni l'une ni l'autre n'est présente, alors le mot-clé est toujours autorisé - ce qui n'est probablement pas ce que vous vouliez faire.

L'étape "check"

void (*check)(pTHX_ void *hookdata);

Invoquée une fois que le mot-clé a été autorisé. S'il est présent, ce hook de fonction peut vérifier le contexte lexical environnant, l'état, ou d'autres informations et lancer une exception s'il n'est pas satisfait que le mot-clé doive s'appliquer à cet endroit.

L'étape "parse"

Cette étape est invoquée une fois que le mot-clé a été vérifié, et analyse réellement le texte entrant en une optree. Elle est implémentée en appelant le **premier** des pointeurs de fonction suivants qui n'est pas NULL. La fonction invoquée peut éventuellement construire une optree pour représenter la syntaxe analysée, et la placer dans la variable adressée par "out". Si elle ne le fait pas, une simple "OP_NULL" sera construite à sa place.

lex_read_space() est appelée avant et après l'invocation de cette étape, donc dans de nombreux cas simples, le hook de fonction n'a pas besoin de s'en préoccuper.

int (*parse)(pTHX_ OP **out, void *hookdata);

Si présent, cela doit consommer du texte du tampon de l'analyseur en invoquant les fonctions "lex_*" ou "parse_*" et finalement retourner une valeur de type "KEYWORD_PLUGIN_*".

C'est l'option la plus générique et la plus puissante, mais elle nécessite le plus de travail d'implémentation.

int (*build)(pTHX_ OP **out, XSParseKeywordPiece *args[], size_t nargs, void *hookdata);

Si "parse" n'est pas présent, ceci est appelé à la place après l'analyse d'une séquence d'arguments, dont les types sont donnés par le champ pieces ; qui devrait être un tableau terminé par zéro des types de pièces.

Cette alternative est quelque peu moins générique et puissante que de fournir soi-même "parse", mais implique beaucoup moins de travail d'analyse et est plus courte et plus facile à implémenter.

int (*build1)(pTHX_ OP **out, XSParseKeywordPiece *arg0, void *hookdata);

Si ni "parse" ni "build" ne sont présents, ceci est appelé comme une variante plus simple de "build" lorsqu'un seul argument est requis. Il prend son type du champ "piece1" à la place.

PIÈCES ET TYPES DE PIÈCES

Lors de l'utilisation des alternatives "build" ou "build1" pour la phase "parse", la syntaxe réelle est analysée automatiquement par ce module, conformément à la spécification donnée par le champ pieces ou piece1. Le résultat de cette étape d'analyse est placé dans le paramètre args ou arg0 de la fonction invoquée.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

, en utilisant un type "struct" composé des champs suivants :

typedef struct {
   union {
      OP *op;
      CV *cv;
      SV *sv;
      int i;
      struct {
         SV *name;
         SV *value;
      } attr;
      PADOFFSET padix;
      struct XSParseInfixInfo *infix;
   };
   int line;
} XSParseKeywordPiece;

Le champ de l'union anonyme qui est défini dépend du type de la pièce. Le champ line contient le numéro de ligne du fichier source où a commencé l'analyse de cette pièce.

Certains types de pièces sont "atomiques", dont la définition est autonome. D'autres sont structurels, définis en termes de pièces internes. Ensemble, ils forment une définition complète en forme d'arbre de la syntaxe que le mot-clé s'attend à trouver.

Les types atomiques fournissent généralement exactement un argument à la liste des args (à l'exception des correspondances littérales, qui ne fournissent rien). Les types structurels peuvent fournir un argument initial eux-mêmes, suivi d'une liste des valeurs de chaque sous-pièce qu'ils contenaient. Ainsi, bien que la structure de données définissant la forme syntaxique soit un arbre, les valeurs des arguments dans lesquelles elle analyse sont passées sous forme de tableau plat à la fonction "build".

Certains types structurels doivent être capables de déterminer si la syntaxe relative à une partie optionnelle de ceux-ci est présente ou non dans le texte source entrant. Dans ce cas, les pièces relatives à ces parties optionnelles doivent supporter le "sondage". Cette capacité est également notée ci-dessous.

Beaucoup des types de pièces atomiques ont une variante qui est optionnelle ; si l'entrée donnée ne ressemble pas à la syntaxe attendue pour le type de pièce, une version du type suffixée par "_OPT" produira alors "NULL" dans son pointeur de résultat.

Le type de chaque pièce doit être l'une des valeurs macro suivantes.

XPK_BLOCK

atomique, peut sonder, émet un op.

XPK_BLOCK

Un bloc de code délimité par des accolades est attendu, passé en tant qu'optree dans le champ op. Celui-ci sera analysé comme un bloc dans la portée de fonction actuelle.

Cela peut être sondé en vérifiant la présence d'un caractère d'accolade ouvrante ("{").

Soyez prudent lors de la définition de grammaires avec cela, car une accolade ouvrante est également un caractère valide pour commencer une expression de terme, par exemple. Étant donné le choix entre "XPK_BLOCK" et "XPK_TERMEXPR", l'un ou l'autre pourrait essayer de consommer du code tel que

{ 123, 456 }

XPK_BLOCK_VOIDCTX, XPK_BLOCK_SCALARCTX, XPK_BLOCK_LISTCTX

Variantes de "XPK_BLOCK" qui encapsulent une portée de contexte vide, scalaire ou de liste autour du bloc.

XPK_PREFIXED_BLOCK

structurel, émet un op.

XPK_PREFIXED_BLOCK(pieces ...)

Certaines pièces sont attendues, suivies d'un bloc de code délimité par des accolades, qui est passé en tant qu'optree dans le champ op. Les pièces de préfixe sont analysées en premier, et leurs résultats sont passés avant le bloc lui-même.

L'ensemble de la séquence, y compris les éléments de préfixe, est contenu dans une paire d'appels block_start() / block_end(). Cela permet aux pièces de préfixe d'introduire de nouveaux éléments dans la portée lexicale du bloc - par exemple, par l'utilisation de "XPK_LEXVAR_MY".

Un appel à intro_my() est automatiquement effectué à la fin des pièces de préfixe, avant l'analyse du bloc lui-même, garantissant que toutes les nouvelles variables lexicales sont maintenant visibles.

De plus, les types de pièces supplémentaires suivants sont reconnus ici :

XPK_SETUP
void setup(pTHX_ void *hookdata);
XPK_SETUP(&setup)

atomique, n'émet rien.

Ce type de pièce exécute une fonction donnée par pointeur. Typiquement, cette fonction peut être utilisée pour introduire un nouvel état lexical dans l'analyseur, ou d'une autre manière avoir un effet secondaire sur le contexte d'analyse du bloc à analyser.

XPK_PREFIXED_BLOCK_ENTERLEAVE

Une variante de "XPK_PREFIXED_BLOCK" qui encapsule supplémentairement toute l'opération d'analyse, y compris block_start(), block_end() et tous les appels aux fonctions "XPK_SETUP", dans une paire "ENTER"/"LEAVE".

Cela ne devrait pas faire de différence pour les pièces d'analyse standard fournies ici, mais peut être un comportement utile pour le code de la fonction de configuration, surtout s'il souhaite modifier l'état de l'analyseur et utiliser la pile sauvegardée pour s'assurer qu'elle est restaurée une fois l'analyse terminée.

XPK_ANONSUB

atomique, émet un cv.

Un bloc de code délimité par des accolades est attendu, et assemblé dans le corps d'une nouvelle sous-routine anonyme. Il sera passé en tant que CV de protosub dans le champ cv.

XPK_STAGED_ANONSUB

XPK_STAGED_ANONSUB(stages ...)

structurel, émet un cv.

Une variante de "XPK_ANONSUB" qui accepte des pointeurs de fonction supplémentaires à invoquer à divers points pendant l'analyse et la compilation. Ceux-ci peuvent être utilisés pour interrompre l'analyse normale d'une manière similaire à XS::Parse::Sublike, bien qu'actuellement un peu moins flexible.

La liste stages peut contenir des éléments des types suivants. Tous les stades ne doivent pas être présents, mais ceux qui le sont doivent être dans l'ordre suivant. Plusieurs copies de chaque stade sont permises ; elles sont invoquées dans l'ordre écrit, avec le code de l'analyseur se produisant entre-temps.

XPK_ANONSUB_PREPARE
XPK_ANONSUB_PREPARE(&callback)

atomique, n'émet rien.

Invoque la fonction de rappel avant start_subparse().

XPK_ANONSUB_START
XPK_ANONSUB_START(&callback)

atomique, n'émet rien.

Invoque la fonction de rappel après block_start() mais avant d'analyser le contenu réel du bloc.

XPK_ANONSUB_END
OP *op_wrapper_callback(pTHX_ OP *o, void *hookdata);
XPK_ANONSUB_END(&op_wrapper_callback)

atomique, n'émet rien.

Invoque la fonction de rappel après l'analyse du contenu du bloc mais avant d'appeler block_end(). La fonction de rappel peut modifier l'optree si nécessaire et en retourner un nouveau.

XPK_ANONSUB_WRAP
XPK_ANONSUB_WRAP(&op_wrapper_callback)

atomique, n'émet rien.

Invoque la fonction de rappel après block_end() mais avant de passer l'optree à newATTRSUB(). La fonction de rappel peut modifier l'optree si nécessaire et en retourner un nouveau.

XPK_ARITHEXPR. XPK_ARITHEXPR_OPT

atomique, émet un op.

XPK_ARITHEXPR

Une expression arithmétique est attendue, analysée à l'aide de parse_arithexpr(), et passée sous forme d'optree dans le champ op.

XPK_ARITHEXPR_VOIDCTX, XPK_ARITHEXPR_OPT

XPK_ARITHEXPR_SCALARCTX, XPK_ARITHEXPR_SCALARCTX_OPT

Variantes de "XPK_ARITHEXPR" qui placent l'expression dans un contexte vide ou scalaire.

XPK_TERMEXPR, XPK_TERMEXPR_OPT

atomique, émet un op.

XPK_TERMEXPR

Une expression de terme est attendue, analysée à l'aide de parse_termexpr(), et passée sous forme d'optree dans le champ op.

XPK_TERMEXPR_VOIDCTX, XPK_TERMEXPR_VOIDCTX

XPK_TERMEXPR_SCALARCTX, XPK_TERMEXPR_SCALARCTX_OPT

Variantes de "XPK_TERMEXPR" qui placent l'expression dans un contexte vide ou scalaire.

XPK_LISTEXPR, XPK_LISTEXPR_OPT

atomique, émet un op.

XPK_LISTEXPR

Une expression de liste est attendue, analysée à l'aide de parse_listexpr(), et passée sous forme d'optree dans le champ op.

XPK_LISTEXPR_LISTCTX, XPK_LISTEXPR_LISTCTX_OPT

Variante de "XPK_LISTEXPR" qui place l'expression dans un contexte de liste.

XPK_PREFIXED_TERMEXPR_ENTERLEAVE, XPK_PREFIXED_LISTEXPR_ENTERLEAVE

XPK_PREFIXED_TERMEXPR_ENTERLEAVE(pieces ...)
XPK_PREFIXED_LISTEXPR_ENTERLEAVE(pieces ...)

Variantes de "XPK_TERMEXPR" ou "XPK_LISTEXPR" qui attendent une séquence de pièces avant de parser une expression de terme, similaire à la façon dont "XPK_PREFIXED_BLOCK_ENTERLEAVE" fonctionne. L'opération entière est encapsulée dans une paire "ENTER"/"LEAVE".

Ceux-ci sont destinés uniquement à l'utilisation de pièces "XPK_SETUP" comme préfixes. Toutes autres pièces qui analysent une entrée réelle sont susceptibles de provoquer des grammaires excessivement complexes, subtiles ou carrément ambiguës, et doivent être évitées.

XPK_IDENT, XPK_IDENT_OPT

atomique, peut sonder, émet sv.

Un nom d'identifiant non qualifié est attendu, et passé sous forme de SV contenant un PV dans le champ sv. Un identifiant ne doit pas contenir de double deux-points ("::").

XPK_PACKAGENAME, XPK_PACKAGENAME_OPT

atomique, peut sonder, émet sv.

Un nom de package non qualifié est attendu, et passé sous forme de SV contenant un PV dans le champ sv. Un nom de package est similaire à un identifiant, sauf qu'il autorise les doubles deux-points au milieu.

XPK_LEXVARNAME

atomique, émet sv.

XPK_LEXVARNAME(kind)

Un nom de variable lexicale est attendu, et passé sous forme de SV contenant un PV dans le champ sv. L'argument "kind" spécifie quels types de variables sont autorisés, et doit être un masque de bits d'un ou plusieurs bits parmi "XPK_LEXVAR_SCALAR", "XPK_LEXVAR_ARRAY" et "XPK_LEXVAR_HASH". Un raccourci pratique, "XPK_LEXVAR_ANY", autorise les trois.

XPK_ATTRIBUTES

atomique, émet i suivi d'autres arguments.

Une liste d'attributs préfixés par ":" est attendue, dans le même format que les attributs de sous-routines ou de variables. Un préfixe optionnel ":" indique la présence d'attributs, puis un ou plusieurs d'entre eux sont analysés. Les attributs peuvent être optionnellement séparés par des ":" supplémentaires, mais ce n'est pas obligatoire.

Chaque attribut doit être un nom d'identifiant, suivi d'une valeur optionnelle encapsulée entre parenthèses. Les espaces blancs ne sont **PAS** autorisés entre le nom et la valeur, conformément aux règles d'analyse standard de Perl.

:attrname
:attrname(valeur)

Le champ i indique combien d'attributs ont été trouvés. Ce nombre d'arguments supplémentaires sont ensuite passés, chacun contenant deux SV dans les champs attr.name et attr.value. Ce nombre peut être zéro.

Il n'est pas considéré comme une erreur s'il n'y a pas d'attributs présents, ou si le deux-points optionnel est manquant. Dans ce cas, i sera défini à zéro.

XPK_VSTRING, XPK_VSTRING_OPT

atomique, peut sonder, émet sv.

Une chaîne de version est attendue, sous la forme "v1.234" incluant le caractère "v" initial. Elle est passée en tant qu'objet SV de version dans le champ sv.

XPK_LEXVAR

atomique, émet padix.

XPK_LEXVAR(kind)

Un nom de variable lexicale est attendu et recherché dans le pad actuel. L'indice de pad résultant est passé dans le champ padix. Aucune erreur ne se produit si la variable n'est pas trouvée ; la valeur "NOT_IN_PAD" est passée à la place.

Le paramètre "kind" spécifie quels types de variables sont autorisés, conformément à "XPK_LEXVARNAME".

XPK_LEXVAR_MY

atomique, émet padix.

XPK_LEXVAR_MY(kind)

Un nom de variable lexicale est attendu, ajouté au pad actuel comme s'il était spécifié dans une expression "my", et passé comme indice de pad dans le champ padix.

Le paramètre "kind" spécifie quels types de variables sont autorisés, conformément à "XPK_LEXVARNAME".

XPK_COMMA, XPK_COLON, XPK_EQUALS

atomique, peut sonder, n'émet rien.

Un caractère littéral (",", ":" ou "=") est attendu. Aucune valeur d'argument n'est passée.

XPK_AUTOSEMI

atomique, n'émet rien.

Un point-virgule littéral (";") servant de terminateur d'instruction est optionnellement attendu. Si le jeton suivant est une accolade fermante indiquant la fin d'un bloc, alors un point-virgule n'est pas requis. Si autre chose est rencontré, une erreur sera levée.

Ce type de pièce est identique à la spécification de "XPK_FLAG_AUTOSEMI". Il est utile de le placer à la fin d'une séquence qui fait partie d'un choix de syntaxe, où certaines formes indiquent une instruction se terminant par un point-virgule, tandis que d'autres peuvent se terminer par un bloc complet qui n'en a pas besoin.

XPK_INFIX_*

atomique, peut sonder, émet infix.

Un opérateur infixe tel que reconnu par XS::Parse::Infix. Le pointeur retourné pointe vers une structure allouée par "XS::Parse::Infix" décrivant l'opérateur.

Diverses versions de la macro sont fournies, chacune utilisant un filtre de sélection différent pour choisir certains opérateurs infixes disponibles :

XPK_INFIX_RELATION         // tout opérateur relationnel
XPK_INFIX_EQUALITY         // un opérateur d'égalité comme `==` ou `eq`
XPK_INFIX_MATCH_NOSMART    // tout opérateur de type "correspondance", sauf smartmatch
XPK_INFIX_MATCH_SMART      // XPK_INFIX_MATCH_NOSMART plus smartmatch

XPK_LITERAL

atomique, peut sonder, n'émet rien.

XPK_LITERAL("literal")

Une correspondance de chaîne littérale est attendue. Aucune valeur d'argument n'est passée.

Cette forme doit généralement être évitée autant que possible, car il est très facile de l'abuser pour créer des syntaxes qui confondent les humains et les outils de codage. Généralement, elle est réservée uniquement au premier composant d'une séquence "XPK_OPTIONAL" ou "XPK_REPEATED", pour fournir un "mot-clé secondaire" que cet élément répété peut rechercher.

XPK_KEYWORD

atomique, peut sonder, n'émet rien.

XPK_KEYWORD("keyword")

Une correspondance de chaîne littérale est attendue. Aucune valeur d'argument n'est passée.

Ceci est similaire à "XPK_LITERAL", sauf qu'il vérifie en plus que le caractère suivant n'est pas un caractère d'identifiant. Cela garantit que le comportement attendu de mot-clé est préservé. Par exemple, étant donné l'entrée "keyword", la pièce XPK_LITERAL("key") la ferait correspondre, tandis que XPK_KEYWORD("key") ne le ferait pas en raison du caractère "w" suivant.

XPK_INTRO_MY

atomique, n'émet rien.

Appelle immédiatement la fonction Perl de base intro_my(). Aucune entrée n'est consommée et aucune valeur de sortie n'est générée. Ceci est souvent utile après "XPK_LEXVAR_MY".

XPK_WARNING

atomique, n'émet rien.

XPK_WARNING("message ici")

Émet un avertissement en appelant la fonction Perl de base warn() sur la chaîne littérale donnée. Ceci est équivalent à appeler simplement warn() depuis la fonction de build, sauf qu'il est émis immédiatement au moment de l'analyse, donc la numérotation des lignes sera plus précise. De plus, en le plaçant dans le cadre d'une séquence optionnelle ou de choix, l'avertissement ne sera émis conditionnellement que si cette partie de la structure grammaticale est rencontrée.

XPK_WARNING_...

Plusieurs variantes de "XPK_WARNING" existent, conditionnées par l'activation de catégories d'avertissement particulières. Celles-ci sont susceptibles d'être utiles au moment de l'analyse :

XPK_WARNING_AMBIGUOUS
XPK_WARNING_DEPRECATED
XPK_WARNING_EXPERIMENTAL
XPK_WARNING_PRECEDENCE
XPK_WARNING_SYNTAX

XPK_SEQUENCE

structurel, peut supporter le sondage, n'émet rien.

XPK_SEQUENCE(pieces ...)

Un type structurel qui contient un certain nombre de pièces. Ceci est normalement équivalent à simplement placer les pièces en séquence à l'intérieur de leur propre conteneur, mais c'est utile à l'intérieur de "XPK_CHOICE" ou "XPK_TAGGEDCHOICE".

"XPK_SEQUENCE" supporte le sondage si sa première pièce contenue le fait ; c'est-à-dire qu'il est transparent au sondage.

XPK_OPTIONAL

structurel, émet i.

XPK_OPTIONAL(pieces ...)

Un type structurel qui attend de trouver ses pièces contenues, ou est satisfait de ne pas les trouver. Il passera un argument dont le champ i contient soit 1, soit 0, selon que le contenu a été trouvé ou non. Le premier type de pièce à l'intérieur doit supporter le sondage.

<

XPK_REPEATED

structural, émet i.

XPK_REPEATED(pieces ...)

Un type structurel qui s'attend à trouver zéro ou plusieurs répétitions de ses pièces contenues. Cela transmettra un argument dont le champ i contient le nombre de répétitions trouvées. Le premier type de pièce interne doit supporter la sonde (probe).

XPK_CHOICE

structural, peut sonder, émet i.

XPK_CHOICE(options ...)

Un type structurel qui s'attend à trouver une parmi plusieurs options alternatives. Une liste ordonnée de types est fournie, tous devant supporter la sonde. Cela transmettra un argument dont le champ i donne l'indice du premier choix qui a été accepté. La première option vaut 0.

Comme chacune des options est interprétée comme une alternative, et non une séquence, vous devriez utiliser "XPK_SEQUENCE" si une séquence de plusieurs éléments doit être considérée comme une seule alternative.

Ce n'est pas une erreur si aucun choix ne correspond. À ce moment-là, le champ i sera mis à -1.

Si vous avez besoin d'un message d'erreur dans ce cas, définissez le dernier choix comme étant de type "XPK_FAILURE". Cela provoquera l'affichage d'un message d'erreur à la place.

XPK_FAILURE("chaine de message")

XPK_TAGGEDCHOICE

structural, peut sonder, émet i.

XPK_TAGGEDCHOICE(choix, tag, ...)

Un type structurel similaire à "XPK_CHOICE", sauf que chaque type de choix est suivi d'un élément de type "XPK_TAG" qui donne un entier. C'est cette valeur entière, plutôt que l'indice positionnel du choix dans la liste, qui est transmise dans le champ i.

XPK_TAG(valeur)

Comme chacune des options est interprétée comme une alternative, et non une séquence, vous devriez utiliser "XPK_SEQUENCE" si une séquence de plusieurs éléments doit être considérée comme une seule alternative.

XPK_COMMALIST

structural, peut supporter la sonde, émet i.

XPK_COMMALIST(pieces ...)

Un type structurel qui s'attend à trouver une ou plusieurs répétitions de ses pièces contenues, séparées par des virgules littérales (","). Ceci est quelque peu similaire à "XPK_REPEATED", sauf qu'il faut au moins une copie, qu'il faut des virgules entre ses éléments, mais qu'il n'exige pas que la première pièce contenue supporte la sonde (la virgule elle-même suffit à indiquer une répétition).

Un "XPK_COMMALIST" supporte la sonde si sa première pièce contenue le fait; c'est-à-dire, est transparent à la sonde.

XPK_PARENS

structural, peut sonder, n'émet rien.

XPK_PARENS(pieces ...)

Un type structurel qui s'attend à trouver une séquence de pièces, toutes contenues entre parenthèses comme "( ... )". Cela ne transmettra aucun argument supplémentaire.

XPK_ARGS

structural, n'émet rien.

XPK_ARGS(pieces ...)

Un type structurel similaire à "XPK_PARENS", sauf que les parenthèses elles-mêmes sont optionnelles; un peu comme l'analyse des appels de fonctions connues par Perl.

Si des parenthèses sont rencontrées dans l'entrée, elles seront consommées par cette pièce et elle se comportera de manière identique à "XPK_PARENS". S'il n'y a pas de parenthèse ouvrante, cette pièce se comportera comme "XPK_SEQUENCE" et consommera toutes les pièces à l'intérieur, sans attendre de parenthèse fermante.

XPK_BRACKETS

structural, peut sonder, n'émet rien.

XPK_BRACKETS(pieces ...)

Un type structurel qui s'attend à trouver une séquence de pièces, toutes contenues entre crochets comme "[ ... ]". Cela ne transmettra aucun argument supplémentaire.

XPK_BRACES

structural, peut sonder, n'émet rien.

XPK_BRACES(pieces ...)

Un type structurel qui s'attend à trouver une séquence de pièces, toutes contenues entre accolades comme "{ ... }". Cela ne transmettra aucun argument supplémentaire.

Notez que ce n'est pas nécessaire de l'utiliser avec "XPK_BLOCK" ou "XPK_ANONSUB" ; ceux-ci consommeront déjà un ensemble d'accolades. Ceci est destiné à une syntaxe spéciale contrainte qui ne devrait pas simplement accepter un bloc arbitraire.

XPK_CHEVRONS

structural, peut sonder, n'émet rien.

XPK_CHEVRONS(pieces ...)

Un type structurel qui s'attend à trouver une séquence de pièces, toutes contenues entre chevrons comme "< ... >". Cela ne transmettra aucun argument supplémentaire.

N'oubliez pas que des expressions comme "a > b" sont des expressions de termes valides, de sorte que le contenu de ce contexte ne devrait pas permettre des expressions arbitraires, sinon le chevron fermant sera ambigu.

XPK_PARENS_OPT, XPK_BRACKETS_OPT, XPK_BRACES_OPT, XPK_CHEVRONS_OPT

structural, peut sonder, émet i.

XPK_PARENS_OPT(pieces ...)
XPK_BRACKETS_OPT(pieces ...)
XPK_BRACES_OPT(pieces ...)
XPK_CHEVERONS_OPT(pieces ...)

Chacune des quatre macros de structure contenues ci-dessus a une variante optionnelle, dont le nom est suffixé par "_OPT". Celles-ci transmettent un argument dont le champ i est soit vrai soit faux, indiquant si le contexte a été trouvé, suivi des valeurs du contexte lui-même.

C'est un raccourci pratique pour imbriquer le contexte dans une macro "XPK_OPTIONAL".

XPK_..._pieces

XPK_SEQUENCE_pieces(ptr)
XPK_OPTIONAL_pieces(ptr)
...

Pour chacune des macros "XPK_..." qui prend une liste de pièces de longueur variable, il existe une variante dont le nom se termine par "..._pieces", prenant directement un seul argument pointeur. Celui-ci doit pointer vers un tableau "const XSParseKeywordPieceType []" dont le dernier élément est l'élément zéro.

Normalement, le code C écrit à la main pour une grammaire fixe n'utiliserait pas ces formes, mais elles peuvent être utiles dans des cas générés dynamiquement.
