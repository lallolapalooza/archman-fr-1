X11::Protocol::Ext::DOUBLE_BUFFER(3) Documentation Perl fournie par l'utilisateur X11::Protocol::Ext::DOUBLE_BUFFER(3)

NOM

X11::Protocol::Ext::DOUBLE_BUFFER - Double buffering hors écran pour les fenêtres

SYNOPSIS

use X11::Protocol;
$X = X11::Protocol->new;
$X->init_extension('DOUBLE-BUFFER')
  or print "L'extension DOUBLE-BUFFER n'est pas disponible";

DESCRIPTION

L'extension DOUBLE-BUFFER permet à un programme de dessiner dans un "tampon arrière" hors écran sur une fenêtre et, une fois prêt, de le permuter avec le "tampon avant" visible par l'utilisateur. Un tampon arrière est un objet dessinable ayant la même taille, profondeur, visibilité, etc. que la fenêtre elle-même.

Dessiner hors écran puis permuter vers le visible est idéal pour des animations image par image fluides ou si certains dessins sont complexes ou mal implémentés et comportent des effacements ou des recouvrements qui clignoteraient s'ils étaient effectués directement sur la fenêtre.

Le dessin hors écran peut également être implémenté à l'aide d'un pixmap et copié dans la fenêtre, mais le serveur pourrait implémenter un tampon arrière de manière plus efficace. En particulier, le tampon arrière n'a besoin de contenir que les parties visibles d'une fenêtre, de sorte que la mémoire n'est pas utilisée pour les zones superposées.

Le serveur peut ne prendre en charge le double buffering que sur certains visuels. DbeGetVisualInfo() liste ceux qui sont pris en charge, ou vous pouvez simplement essayer de créer un tampon arrière pour une fenêtre et surveiller une réponse d'erreur.

Voir examples/dbe-swap.pl pour un programme simple dessinant avec le double buffering.

REQUETES

Les requêtes suivantes sont rendues disponibles avec un init_extension() par "EXTENSIONS" dans X11::Protocol.

my $bool = $X->init_extension('DOUBLE-BUFFER');
"($server_major, $server_minor) = $X->DbeGetVersion ($client_major, $client_minor)"
Négocie une version de protocole avec le serveur. $client_major et $client_minor sont ce que le client souhaite, les valeurs retournées $server_major et $server_minor sont ce que le serveur fera, ce qui peut être moins que demandé (mais pas plus).

Le code ici prend en charge la version 1.0 et négocie automatiquement au sein de init_extension(), donc une utilisation directe de DbeGetVersion() n'est pas nécessaire.

"$X->DbeAllocateBackBufferName ($window, $buffer, $action_hint)"
Crée $buffer (un nouveau XID) comme tampon arrière sur $window. $buffer est un objet dessinable et peut être utilisé avec toutes les opérations de dessin usuelles. 
my $buffer = $X->new_rsrc;
$X->DbeAllocateBackBufferName ($window, $buffer, 'Copied');

$action_hint est l'$action la plus probable dans les requêtes ultérieures de DbeSwapBuffers() (voir ci-dessous). Mais ce n'est qu'un indice et cela ne restreint pas ce qui peut être fait.

Si $window est déjà en double buffering, alors $buffer devient une autre référence à ce tampon arrière.

Si $window est détruit (DestroyWindow()), alors $buffer continue d'exister et devrait toujours être désalloué (ci-dessous), mais tenter d'y dessiner renvoie une réponse d'erreur de type "Resource".

"$X->DbeDellocateBackBufferName ($buffer)"
Désalloue $buffer et libère ce XID.

Si plusieurs requêtes DbeAllocateBackBufferName() ont été faites sur une fenêtre, alors tous les autres XID font toujours référence au tampon arrière de la fenêtre. Le tampon sous-jacent reste jusqu'à ce que tous les XID de tampon pour celui-ci soient désalloués.

"$X->DbeSwapBuffers ($window1,$action1, $window2,$action2,...)"
Permute les tampons avant et arrière sur chaque $window (XID) donné. Le tampon arrière devient visible et ce qui était le tampon avant devient le tampon arrière. 
$X->DbeSwapBuffers ($window1, 'Background',
                    $window2, 'Untouched');

Seul le contenu est permuté, les XID restent inchangés, donc $window est toujours la fenêtre avant visible et tous les XID $buffer associés sont toujours le tampon arrière.

Le contenu de chaque tampon arrière après permutation est contrôlé par l'$action correspondante pour chaque fenêtre (type chaîne "DbeSwapAction"),

 $action        contenu du nouveau tampon arrière
---------       ------------------------------
"Undefined"     contenu indéfini
"Background"    effacé avec l'arrière-plan de la fenêtre
"Untouched"     laissé tel quel (contenu visible précédent)
"Copied"        contenu de l'ancien tampon arrière (inchangé)

"Untouched" signifie que le contenu du tampon avant est permuté dans le tampon arrière sans modification.

"Copied" est comme si le contenu du tampon arrière était copié dans le tampon avant, rendant les deux identiques.

"$X->DbeBeginIdiom ()"
"$X->DbeEndIdiom ()"
Indique au serveur qu'une séquence d'opérations de permutation et/ou de dessin entre Begin et End pourrait être combinée de manière atomique pour une meilleure performance. Si le serveur ne reconnaît pas la séquence, il l'exécute séquentiellement comme d'habitude.

Si un DbeSwapBuffers() est dans l'idiome, il doit être la première requête, immédiatement après le Begin.

# permute puis efface le tampon arrière avec un motif GC
# aucune garantie qu'un serveur optimiserait cela !
$X->DbeBeginIdiom;
$X->DbeSwapBuffers ($window, 'Undefined');
$X->PolyFillRectangle ($buffer, $gc, [0,0,$width,$height]);
$X->DbeEndIdiom;

Il n'est pas nécessaire qu'il y ait une permutation dans un idiome. Par exemple, un CopyArea() de certaines parties du tampon arrière vers la fenêtre pourrait se trouver dans un Begin/End et pourrait éventuellement être optimisé par le serveur.

$X->DbeBeginIdiom;
$X->CopyArea ($buffer, $window,  # du tampon vers la fenêtre
              $gc, $x,$y,$width,$height, $dstx,$dsty);
# plus de choses...
$X->DbeEndIdiom;

L'idée des groupements d'idiomes est d'avoir un moyen flexible d'exprimer des opérations combinées, y compris des choses non encore imaginées, plutôt que d'ajouter des requêtes spécifiques au protocole. En principe, le serveur peut toujours optimiser les requêtes consécutives, mais cela dépend de leur arrivée ensemble au serveur. Un DbeBeginIdiom() est comme une permission au serveur de reporter l'exécution des requêtes et d'attendre, s'il le souhaite, de voir si ce qui suit peut être combiné.

"@infos = $X->DbeGetVisualInfo ($drawable1, $drawable2, ...)"
"@infos = $X->DbeGetVisualInfo ()"
Pour chaque $drawable, renvoie une liste des ID de visuels sur cet écran qui prennent en charge le double buffering. 
my ($info_aref_drawable1, $info_aref_drawable2)
  = $X->DbeGetVisualInfo ($drawable1, $drawable2);

Si aucun objet dessinable n'est donné, renvoie des informations sur chaque écran du serveur.

my @list_of_info_aref = $X->DbeGetVisualInfo ();

Chaque valeur renvoyée est une référence de tableau. Chaque référence de tableau contient une liste de paires ID de visuel et données de visuel,

# chaque $info_aref est
[ $visual_id1, [ $depth, $perflevel ],
  $visual_id2, [ $depth, $perflevel ],
  ...
]

$depth est la profondeur du visuel, la même que dans les informations du serveur "$X->{'visuals'}->{$visual_id}->{'depth'}".

$perflevel est un entier indiquant la qualité des performances du double buffering sur ce visuel. Une valeur plus élevée signifie des performances meilleures, mais le nombre lui-même n'a pas de signification et ne peut en particulier pas être comparé entre différents serveurs.

Si vous interrogez l'écran d'un seul objet dessinable, utilisez un contexte de liste comme suit. Le résultat en contexte scalaire n'est pas encore spécifié.

my ($info_aref) = $X->DbeGetVisualInfo ($X->root);

Le visuel et le niveau de performance sont des paires, ils peuvent donc être placés dans une table de hachage pour vérifier la prise en charge du double buffering sur un visuel donné,

my %hash = @$info_aref;   # paires $visualid => [$d,$p]
if ($hash{$my_visual_id}) {
  print "le double buffering est disponible sur my_visual_id\n";
}

X11::Protocol::Ext::DOUBLE_BUFFER(3pm) - Perl

NAME

X11::Protocol::Ext::DOUBLE_BUFFER - DBI extension for double buffering.

SYNOPSIS

    use X11::Protocol;
    use X11::Protocol::Ext::DOUBLE_BUFFER;
    my $X = X11::Protocol->new(...);
    $X->init_extension('DOUBLE_BUFFER') or die "DBE extension not available";
    my $buffer = $X->dbe_allocate_buffer(...);
    $X->dbe_choose_visual_info(...);
    $X->dbe_get_visual_info(...);
    $X->dbe_swap_buffers_attributes(...);
    $X->dbe_get_back_buffer_attributes(...);
    $X->dbe_destroy_buffer(...);
    $X->dbe_set_swap_interval(...);
    $X->dbe_get_swap_interval(...);
    $X->dbe_query_extension(...);

DESCRIPTION

This module implements the Double Buffer Extension (DBE) of the X Window System. This extension allows applications to perform single-buffered graphics operations into an off-screen pixmap, and then swap that pixmap with the on-screen pixmap in a single operation. This can be used to avoid flickering during screen updates.

The DBE extension is available on most modern X servers, but it is not part of the core X protocol. Therefore, you must explicitly initialize the extension using init_extension('DOUBLE_BUFFER') before using any of the DBE functions.

The module provides functions that correspond directly to the DBE protocol requests. These functions are available as methods on the $X object returned by X11::Protocol->new().

REQUESTS

dbe_allocate_buffer ($visual, $width, $height, $border_width, $depth)
Allocates a buffer that can be used for double buffering. The arguments are the same as for XCreateWindow().
dbe_choose_visual_info ($screen, $ளா_type, $ளா_flags, $ளா_attributes)
Chooses a visual that supports double buffering. The arguments are the same as for glXChooseVisual().
dbe_get_visual_info ($drawable)
Gets information about the double buffering capabilities of a drawable. This returns a list of hashes, where each hash represents a visual that supports double buffering. The keys in the hash are:
    "visual"           - the visual ID
    "depth"            - the depth of the visual
    "red_mask"         - the red color mask
    "green_mask"       - the green color mask
    "blue_mask"        - the blue color mask
    "colormap"         - the colormap ID
    "attributes"       - a list of attributes, e.g.
        "bufferable"       - true if this visual can be used for double buffering
        "swap_hint"        - true if this visual supports the swap hint

The return value $info_aref is a reference to an array of hashes.

It's important to use this function because some visuals might report themselves as supporting double buffering but might not have suitable performance level. If so the performance level might be compared to choose the best.

"List::Pairwise" has some grep and map functions for pair lists like the $info_aref.

See examples/dbe-info.pl for a simple program printing this info.

dbe_get_back_buffer_attributes ($buffer)
Return the window (an integer XID) which $buffer is for. If its target window has been destroyed (DestroyWindow()) then the return is "None".

ENUM TYPES

The following types are available for "$X->interp()" and "$X->num()", after init_extension().

DbeSwapAction
"Undefined"    0
"Background"   1
"Untouched"    2
"Copied">       3

For example,

my $num = $X->num("DbeSwapAction", "Background");
# sets $num to 2

BUGS

In some XFree86 3.x servers there was a bug in DbeGetVisualInfo() where the reply length was miscalculated, being bytes instead of CARD32s, resulting in a length value bigger than the actual data sent. The symptom is the client hangs waiting for data the length says should follow but which never does.

This affects all client code, including the Xlib XdbeGetVisualInfo() as used for instance by the "xdpyinfo" program.

Is there a good way to notice the problem? Probably not beyond looking at the server name and version and either forbidding the request or doing something nasty to the way handle_input() reads as a workaround.
