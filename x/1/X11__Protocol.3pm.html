NOM

X11::Protocol - Module Perl pour le protocole X Window System, version 11

SYNOPSIS

use X11::Protocol;
$x = X11::Protocol->new();
$win = $x->new_rsrc;
$x->CreateWindow($win, $x->root, 'InputOutput',
                 $x->root_depth, 'CopyFromParent',
                 ($x_coord, $y_coord), $width,
                 $height, $border_w);  
...

DESCRIPTION

X11::Protocol est une interface côté client pour le protocole X11 (voir X(1) pour des informations sur X11), permettant aux programmes Perl d'afficher des fenêtres et des graphiques sur les serveurs X11.

Une description complète du protocole dépasse le cadre de cette documentation ; pour des informations complètes, consultez le X Window System Protocol, X Version 11, disponible en Postscript ou en source *roff depuis "ftp://ftp.x.org", ou le Volume 0: X Protocol Reference Manual de la série de livres d'O'Reilly & Associates sur X (ISBN 1-56592-083-X, "http://www.oreilly.com"), qui contient la plupart des mêmes informations.

AVERTISSEMENT

``Le protocole contient de nombreux mécanismes de gestion qui ne sont pas destinés aux applications normales. Tous les mécanismes ne sont pas nécessaires pour construire une interface utilisateur particulière. Il est important de garder à l'esprit que le protocole est destiné à fournir des mécanismes, pas une politique.'' -- Robert W. Scheifler

MÉTHODES DE BASE

new

$x = X11::Protocol->new();
$x = X11::Protocol->new($display_name);
$x = X11::Protocol->new($connection);
$x = X11::Protocol->new($display_name, [$auth_type, $auth_data]);
$x = X11::Protocol->new($connection, [$auth_type, $auth_data]);

Ouvre une connexion à un serveur. $display_name doit être un nom d'affichage X, de la forme 'host:display_num.screen_num' ; si aucun argument n'est fourni, le contenu de la variable d'environnement DISPLAY est utilisé. Alternativement, une connexion pré-ouverte, d'une des classes X11::Protocol::Connection (voir X11::Protocol::Connection, X11::Protocol::Connection::FileHandle, X11::Protocol::Connection::Socket, X11::Protocol::Connection::UNIXFH, X11::Protocol::Connection::INETFH, X11::Protocol::Connection::UNIXSocket, X11::Protocol::Connection::INETSocket) peut être fournie. Les données d'authentification sont obtenues en utilisant X11::Auth ou le deuxième argument. Si l'affichage est spécifié par $display_name, plutôt que par $connection, un choose_screen() est également effectué, avec un défaut à l'écran 0 si le '.screen_num' du nom d'affichage n'est pas présent. Renvoie le nouvel objet protocole.

new_rsrc

$x->new_rsrc;

Renvoie un nouvel identifiant de ressource. Un ID de ressource unique est requis pour chaque objet que le serveur crée au nom du client : fenêtres, polices, curseurs, etc. (les ID sont choisis par le client plutôt que par le serveur pour des raisons d'efficacité -- le client n'a pas à attendre que le serveur accuse réception de la création avant de commencer à utiliser l'objet).

Notez que le nombre total d'ID de ressources disponibles, bien que grand, est fini. À partir de l'établissement d'une connexion, les ID de ressources sont alloués séquentiellement à partir d'une plage dont la taille dépend du serveur (communément 2**21, environ 2 millions). Si cette limite est atteinte et que le serveur ne prend pas en charge l'extension XC_MISC, les appels ultérieurs à new_rsrc échoueront. Si le serveur prend en charge cette extension, le module tentera de demander une nouvelle plage d'ID libres au serveur. Cela devrait permettre au programme de continuer, mais c'est une solution imparfaite, car avec le temps, l'ensemble des ID disponibles peut se fragmenter, nécessitant des demandes de plage aller-retour de plus en plus fréquentes du serveur. Pour les programmes de longue durée, la meilleure approche pourrait être de suivre les ID libres lorsque les ressources sont détruites. Dans la version actuelle, cependant, aucun support spécial n'est fourni pour cela.

handle_input

$x->handle_input;

Récupère un bloc d'informations du serveur et effectue quelque chose avec. S'il s'agit d'une erreur, elle est traitée à l'aide du gestionnaire de l'objet protocole ('error_handler' -- le défaut est de tuer le programme avec un message explicatif). S'il s'agit d'un événement, il est passé au gestionnaire d'événements choisi, ou mis dans une file d'attente si le gestionnaire est 'queue'. S'il s'agit d'une réponse à une requête, elle est sauvegardée en utilisant le hachage 'replies' de l'objet pour un traitement ultérieur.

atom_name

$name = $x->atom_name($atom);

Renvoie la chaîne de caractères correspondant à l'atome $atom. Ceci est similaire à la requête GetAtomName, mais met en cache le résultat pour des raisons d'efficacité.

atom

$atom = $x->atom($name);

L'opération inverse ; renvoie l'atome (numérique) correspondant à $name. Ceci est similaire à la requête InternAtom, mais met en cache le résultat.

choose_screen

$x->choose_screen($screen_num);

Indique que vous préférez utiliser un écran particulier de l'affichage. Les informations par écran, telles que 'root', 'width_in_pixels' et 'white_pixel', seront disponibles sous la forme

$x->{'root'}

au lieu de

$x->{'screens'}[$screen_num]{'root'}

CONSTANTES SYMBOLIQUES

Généralement, les constantes symboliques utilisées par le protocole, comme 'CopyFromParent' ou 'PieSlice', sont passées aux méthodes sous forme de chaînes de caractères et converties en nombres par le module. Leurs noms sont les mêmes que ceux de la spécification du protocole, y compris la casse, mais avec des tirets ('-') remplacés par des tirets bas ('_') pour un aspect plus Perl. Si vous souhaitez effectuer la conversion vous-même pour une raison quelconque, les méthodes suivantes sont disponibles :

num

$num = $x->num($type, $str)

Étant donné une chaîne représentant une constante et une chaîne spécifiant le type de constante, renvoie le nombre correspondant. $type doit être un nom comme 'VisualClass' ou 'GCLineStyle'. Si le nom n'est pas reconnu, il est renvoyé tel quel.

interp

$name = $x->interp($type, $num)

L'opération inverse ; étant donné un nombre et une chaîne spécifiant son type, renvoie une chaîne représentant la constante.

Vous pouvez désactiver interp() et l'interprétation interne des nombres par le module en définissant $x->{'do_interp'} à zéro. Bien sûr, ce n'est pas très utile, à moins que vous n'ayez vos propres définitions pour toutes les constantes.

INFORMATIONS DU SERVEUR

Au moment de la connexion, le serveur envoie une grande quantité d'informations à son sujet au client. Ces informations sont stockées dans l'objet protocole pour référence future. Elles peuvent être lues directement, comme

$x->{'release_number'}

ou, pour les vrais croyants de l'orienté objet, en utilisant une méthode :

$x->release_number

La méthode de méthode a également une forme à un argument pour définir des variables, mais elle n'est pas vraiment utile pour certaines des structures plus complexes.

request ```perl $x->request('CreateWindow', ...); $x->req('CreateWindow', ...); $x->CreateWindow(...); ``` Envoyer une requête de protocole au serveur et obtenir la réponse, le cas échéant. Pour les noms et informations sur les requêtes individuelles, voir ci-dessous et/ou le manuel de référence du protocole. ## robust_req ```perl $x->robust_req('CreateWindow', ...); ``` Similaire à request(), mais si le serveur renvoie une erreur, renvoie les informations d'erreur au lieu d'appeler le gestionnaire d'erreurs (qui par défaut se contente de planter). Si la requête réussit, renvoie une référence de tableau contenant ce que request() aurait renvoyé. Sinon, renvoie le type d'erreur, les codes d'opération majeurs et mineurs de la requête échouée, et les informations d'erreur supplémentaires, le cas échéant. Notez que même si la requête n'aurait normalement pas de réponse, cette méthode doit toujours attendre un temps aller-retour pour voir si une erreur s'est produite. Si les performances vous préoccupent, vous devriez concevoir votre gestion des erreurs pour qu'elle soit asynchrone. ## add_reply ```perl $x->add_reply($sequence_num, \$var); ``` Ajoute un espace réservé pour une réponse attendue au hachage 'replies' de l'objet. Lorsqu'une réponse numérotée $sequence_num arrive, elle sera stockée dans $var. ## delete_reply ```perl $x->delete_reply($sequence_num); ``` Supprime l'entrée dans 'replies' pour la réponse spécifiée. (Cela doit être fait après la réception de la réponse). ## send ```perl $x->send('CreateWindow', ...); ``` Envoie une requête, mais n'attend pas de réponse. Cette section ne contient qu'un bref résumé d'appel pour chaque requête; pour des descriptions complètes, voir la norme du protocole. L'ordre des arguments est généralement le même que celui indiqué dans la spécification, mais vous n'avez généralement pas à passer les longueurs des chaînes ou des tableaux, car perl s'en occupe. Les constantes symboliques sont généralement passées sous forme de chaînes. La plupart des réponses sont renvoyées sous forme de listes, mais lorsqu'il y a de nombreuses valeurs, un hachage est utilisé. Les parenthèses sont insérées dans les listes d'arguments pour plus de clarté, mais sont facultatives. Les requêtes sont listées dans l'ordre par code d'opération majeur, de sorte que les requêtes liées sont généralement proches les unes des autres. ÉVÉNEMENTS

Pour recevoir des événements, définissez d'abord l'attribut 'event_mask' sur une fenêtre pour indiquer quels types d'événements vous désirez (voir "pack_event_mask"). Ensuite, définissez 'event_handler' de l'objet protocole sur une référence de sous-routine qui gérera les événements. Alternativement, définissez 'event_handler' sur 'queue', et récupérez les événements en utilisant dequeue_event() ou next_event(). Dans les deux cas, les événements sont retournés sous forme de hachage. Par exemple, un événement MotionNotify typique pourrait ressembler à ceci:

%event = ('name' => 'MotionNotify', 'sequence_number' => 12,
          'state' => 0, 'event' => 58720256, 'root' => 43,
          'child' => None, 'same_screen' => 1, 'time' => 966080746,
          'detail' => 'Normal', 'event_x' => 10, 'event_y' => 3,
          'code' => 6, 'root_x' => 319, 'root_y' => 235)

pack_event_mask

$mask = $x->pack_event_mask('ButtonPress', 'KeyPress', 'Exposure');

Crée un masque d'événement (adapté comme 'event_mask' d'une fenêtre) à partir d'une liste de chaînes spécifiant les types d'événements.

unpack_event_mask

@event_types = $x->unpack_event_mask($mask);

L'opération inverse ; convertit un masque d'événement obtenu du serveur en une liste de noms de catégories d'événements.

dequeue_event

%event = $x->dequeue_event;

S'il y a un événement en attente dans la file d'attente, le retourne.

next_event

%event = $x->next_event;

Comme XNextEvent() de Xlib, cette fonction est équivalente à

$x->handle_input until %event = dequeue_event;

pack_event

$data = $x->pack_event(%event);

Étant donné un événement sous forme de hachage, le compresse en une chaîne. Ceci n'est utile qu'en tant qu'argument pour SendEvent().

unpack_event

%event = $x->unpack_event($data);

L'opération inverse ; étant donné les données brutes d'un événement (32 octets), le décompresse en forme de hachage. Normalement, cela est fait automatiquement.

EXTENSIONS

Les extensions de protocole ajoutent de nouvelles requêtes, types d'événements et types d'erreurs au protocole. Le support pour celles-ci est compartimenté dans des modules de la hiérarchie X11::Protocol::Ext::. Pour un exemple, voir X11::Protocol::Ext::SHAPE. Vous pouvez savoir si le module a chargé une extension en regardant

$x->{'ext'}{$extension_name}

Si l'extension a été initialisée, cette valeur sera une référence vers un tableau, [$major_request_number, $first_event_number, $first_error_number, $obj], où $obj est un objet contenant des informations privées à l'extension.

init_extension

$x->init_extension($name);

Initialise une extension : interroge le serveur pour trouver le numéro de requête de l'extension, puis charge le module correspondant. Retourne 0 si le serveur ne supporte pas l'extension nommée, ou si aucun module pour interfacer avec elle n'existe.

init_extensions

$x->init_extensions;

Initialise les extensions de protocole. Cela effectue une requête ListExtensions, puis appelle init_extension() pour chaque extension supportée par le serveur.

ÉCRITURE D'EXTENSIONS

En interne, le module X11::Protocol est piloté par des tables. Tout ce qu'une extension doit faire est d'ajouter de nouvelles entrées aux tables de l'objet protocole. Un module d'extension doit "use X11::Protocol", et doit définir une méthode new()

X11::Protocol::Ext::NAME
  ->new($x, $request_num, $event_num, $error_num)

où $x est l'objet protocole et $request_num, $event_num et $error_num sont les valeurs retournées par QueryExtension().

La méthode new() doit ajouter de nouveaux types de constantes comme

$x->{'ext_const'}{'ConstantType'} = ['Constant', 'Constant', ...]

et configurer les hachages de traduction nom vers numéro correspondants comme

$x->{'ext_const_num'}{'ConstantType'} =
  {make_num_hash($x->{'ext_const'}{'ConstantType'})}

Les noms d'événements vont dans

$x->{'ext_const'}{'Events'}[$event_number]

tandis que les spécifications pour le contenu des événements vont dans

$x->{'ext_event'}[$event_number]

chacun des éléments étant soit "[\&unpack_sub, \&pack_sub]", soit "[$pack_format, $field, $field, ...]", où chaque $field est 'name', "['name', 'const_type']", ou "['name', ['special_name_for_zero', 'special_name_for_one']]", où 'special_name_for_one' est facultatif.

Enfin,

$x->{'ext_request'}{$major_request_number}

devrait être un tableau de tableaux, chaque tableau étant soit "[$name, \&packit]", soit "[$name, \&packit, \&unpackit]", et

$x->{'ext_request_num'}{$request_name}

devrait être initialisé avec "[$minor_num, $major_num]" pour chaque requête que l'extension définit.

nes. For examples of code that does all of this, look at X11::Protocol::Ext::SHAPE.

X11::Protocol exports several functions that might be useful in extensions (note that these are not methods).

bourrage

$p = bourrage $x;

Étant donné un entier, calculez le nombre nécessaire pour l'arrondir au multiple de 4 le plus proche. Par exemple, bourrage(5) vaut 3.

remplir

$p = remplir $str;

Étant donné une chaîne de caractères, retournez le nombre d'octets supplémentaires nécessaires pour obtenir un multiple de 4. Équivalent à "bourrage(longueur($str))".

rembourre

$data = pack(rembourre($str), $str);

Retourne une chaîne de format, adaptée à pack(), pour une chaîne rembourrée à un multiple de 4 octets. Par exemple, "pack(rembourre('Hello'), 'Hello')" donne "Hello\0\0\0".

hexi

$str = hexi $n;

Formate un nombre en hexadécimal et ajoute un préfixe "0x".

fabriquer_hash_num

%hash = fabriquer_hash_num(['A', 'B', 'C']);

Étant donné une référence à une liste de chaînes de caractères, retourne un hash associant les chaînes à des nombres représentant leur position dans la liste, comme utilisé par "$x->{'ext_const_num'}".

BOGUES

Ce module est trop volumineux (~2500 lignes), trop lent (10 secondes pour se charger sur une machine lente), trop inefficace (les arguments des requêtes sont copiés plusieurs fois) et prend trop de mémoire (3000K pour basicwin).

Si vous avez plus de 65535 réponses en attente simultanément, les numéros de séquence peuvent entrer en collision.

Le protocole est trop complexe.
