NOM

REINDEX - reconstruire les index

SYNTAXE

REINDEX [ ( option [, ...] ) ] { INDEX | TABLE | SCHEMA } [ CONCURRENTLY ] nom
REINDEX [ ( option [, ...] ) ] { DATABASE | SYSTEM } [ CONCURRENTLY ] [ nom ]
où option peut être l'un des éléments suivants :
    CONCURRENTLY [ booléen ]
    TABLESPACE nouveau_tablespace
    VERBOSE [ booléen ]

DESCRIPTION

REINDEX reconstruit un index en utilisant les données stockées dans la table de l'index, en remplaçant l'ancienne copie de l'index. Il existe plusieurs scénarios pour utiliser REINDEX :

•Un index est devenu corrompu et ne contient plus de données valides. Bien que cela ne doive théoriquement jamais arriver, en pratique, les index peuvent être corrompus en raison de bugs logiciels ou de défaillances matérielles. REINDEX offre une méthode de récupération.
•Un index est devenu « gonflé » (« bloated »), c'est-à-dire qu'il contient de nombreuses pages vides ou presque vides. Cela peut se produire avec les index B-tree dans PostgreSQL dans certains modes d'accès peu courants. REINDEX permet de réduire l'espace utilisé par l'index en écrivant une nouvelle version de l'index sans les pages mortes. Voir la Section 24.2 pour plus d'informations.
•Vous avez modifié un paramètre de stockage (tel que fillfactor) pour un index et vous souhaitez vous assurer que le changement a été pleinement pris en compte.
•Si la création d'un index échoue avec l'option CONCURRENTLY, cet index reste « invalide ». De tels index sont inutiles, mais il peut être pratique d'utiliser REINDEX pour les reconstruire. Notez que seul REINDEX INDEX est capable d'effectuer une reconstruction concurrente sur un index invalide.

PARAMETRES

INDEX

Recrée l'index spécifié. Cette forme de REINDEX ne peut pas être exécutée à l'intérieur d'un bloc de transaction lorsqu'elle est utilisée avec un index partitionné.

TABLE

Recrée tous les index de la table spécifiée. Si la table a une table secondaire « TOAST », celle-ci est également reconstruite. Cette forme de REINDEX ne peut pas être exécutée à l'intérieur d'un bloc de transaction lorsqu'elle est utilisée avec une table partitionnée.

SCHEMA

Recrée tous les index du schéma spécifié. Si une table de ce schéma a une table secondaire « TOAST », celle-ci est également reconstruite. Les index sur les catalogues système partagés sont également traités. Cette forme de REINDEX ne peut pas être exécutée à l'intérieur d'un bloc de transaction.

DATABASE

Recrée tous les index dans la base de données actuelle, à l'exception des catalogues système. Les index sur les catalogues système ne sont pas traités. Cette forme de REINDEX ne peut pas être exécutée à l'intérieur d'un bloc de transaction.

SYSTEM

Recrée tous les index sur les catalogues système dans la base de données actuelle. Les index sur les catalogues système partagés sont inclus. Les index sur les tables utilisateur ne sont pas traités. Cette forme de REINDEX ne peut pas être exécutée à l'intérieur d'un bloc de transaction.

nom

Le nom de l'index, de la table ou de la base de données spécifique à reconstruire. Les noms d'index et de table peuvent être qualifiés par le schéma. Actuellement, REINDEX DATABASE et REINDEX SYSTEM ne peuvent reconstruire que la base de données actuelle. Leur paramètre est optionnel et doit correspondre au nom de la base de données actuelle.

CONCURRENTLY

Lorsque cette option est utilisée, PostgreSQL reconstruit l'index sans prendre de verrou qui empêcherait les insertions, mises à jour ou suppressions concurrentes sur la table ; tandis qu'une reconstruction d'index standard bloque les écritures (mais pas les lectures) sur la table jusqu'à ce qu'elle soit terminée. Il y a plusieurs avertissements à prendre en compte lors de l'utilisation de cette option — voir Reconstruire les index concurremment ci-dessous.

Pour les tables temporaires, REINDEX est toujours non concurrent, car aucune autre session ne peut y accéder, et la reconstruction non concurrente est moins coûteuse.

TABLESPACE

Spécifie que les index seront reconstruits sur un nouveau tablespace.

VERBOSE

Affiche un rapport de progression lors de la reconstruction de chaque index au niveau INFO.

booléen

Spécifie si l'option sélectionnée doit être activée ou désactivée. Vous pouvez écrire TRUE, ON, ou 1 pour activer l'option, et FALSE, OFF, ou 0 pour la désactiver. La valeur booléen peut également être omise, auquel cas TRUE est supposé.

nouveau_tablespace

Le tablespace où les index seront reconstruits.

NOTES

Si vous suspectez une corruption d'un index sur une table utilisateur, vous pouvez simplement reconstruire cet index, ou tous les index de la table, en utilisant REINDEX INDEX ou REINDEX TABLE.

Les choses sont plus compliquées si vous devez récupérer d'une corruption d'un index sur une table système. Dans ce cas, il est important que le système n'ait pas utilisé lui-même les index suspects. (En effet, dans ce type de scénario, vous pourriez constater que les processus serveur plantent immédiatement au démarrage, en raison de la dépendance vis-à-vis des index corrompus.) Pour récupérer en toute sécurité, le serveur doit être démarré avec l'option -P, qui l'empêche d'utiliser les index pour les recherches dans les catalogues système.

Une façon de procéder est d'arrêter le serveur et de démarrer un serveur PostgreSQL en mode mono-utilisateur avec l'option -P incluse dans sa ligne de commande. Ensuite, REINDEX DATABASE, REINDEX SYSTEM, REINDEX TABLE, ou REINDEX INDEX peuvent être exécutés, en fonction de la quantité que vous souhaitez reconstruire. En cas de doute, utilisez REINDEX SYSTEM pour sélectionner la reconstruction de tous les index système dans la base de données. Quittez ensuite la session du serveur en mode mono-utilisateur et redémarrez le serveur normal. Voir la page de référence postgres(1) pour plus d'informations sur la manière d'interagir avec l'interface du serveur mono-utilisateur.

Alternativement, une session serveur normale peut être démarrée avec -P inclus dans ses options de ligne de commande. La méthode pour le faire varie selon les clients, mais dans tous les clients basés sur libpq, il est possible de définir la variable d'environnement PGOPTIONS à -P avant de démarrer le client. Notez que, bien que cette méthode ne nécessite pas de verrouiller les autres clients, il peut toujours être judicieux d'empêcher d'autres utilisateurs de se connecter à la base de données endommagée tant que les réparations n'ont pas été effectuées.

REINDEX est similaire à un DROP et un RECREATE de l'index, en ce sens que le contenu de l'index est reconstruit à partir de zéro. Cependant, les considérations de verrouillage sont assez différentes. REINDEX verrouille les écritures mais pas les lectures de la table parente de l'index. Il prend également un verrou ACCESS EXCLUSIVE sur l'index spécifique traité, ce qui bloquera les lectures qui tentent d'utiliser cet index. En particulier, le planificateur de requêtes tente de prendre un verrou ACCESS SHARE sur chaque index de la table, quelle que soit la requête, et ainsi REINDEX bloque virtuellement toutes les requêtes sauf certaines requêtes préparées dont le plan a été mis en cache et qui n'utilisent pas cet index précis. En revanche, DROP INDEX prend momentanément un verrou ACCESS EXCLUSIVE sur la table parente, bloquant à la fois les écritures et les lectures. Le CREATE INDEX qui suit bloque les écritures mais pas les lectures ; comme l'index n'est pas présent, aucune lecture ne tentera de l'utiliser, ce qui signifie qu'il n'y aura pas de blocage, mais les lectures pourraient être forcées à effectuer des scans séquentiels coûteux.

Pendant que REINDEX s'exécute, le search_path est temporairement modifié en pg_catalog, pg_temp.

La reconstruction d'un index unique ou d'une table unique nécessite d'avoir le privilège MAINTAIN sur la table. Notez que, bien que REINDEX sur un index ou une table partitionnée nécessite d'avoir le privilège MAINTAIN sur la table partitionnée, de telles commandes ignorent les vérifications de privilèges lors du traitement des partitions individuelles. La reconstruction d'un schéma ou d'une base de données nécessite d'être propriétaire de ce schéma ou de cette base de données ou d'avoir les privilèges du rôle pg_maintain. Notez spécifiquement qu'il est ainsi possible pour des non-super-utilisateurs de reconstruire les index de tables appartenant à d'autres utilisateurs. Cependant, à titre d'exception spéciale, REINDEX DATABASE, REINDEX SCHEMA, et REINDEX SYSTEM ignoreront les index sur les catalogues partagés à moins que l'utilisateur n'ait le privilège MAINTAIN sur le catalogue.

La reconstruction des index partitionnés ou des tables partitionnées est prise en charge avec REINDEX INDEX ou REINDEX TABLE, respectivement. Chaque partition de la relation partitionnée spécifiée est reconstruite dans une transaction distincte. Ces commandes ne peuvent pas être utilisées à l'intérieur d'un bloc de transaction lorsqu'elles opèrent sur une table ou un index partitionné.

Lors de l'utilisation de la clause TABLESPACE avec REINDEX sur un index ou une table partitionné(e), seules les références aux tablespaces des partitions feuilles sont mises à jour. REINDEX

SYNTAXIS

REINDEX [INDEX | TABLE] [CONCURRENTLY] [INDEX | TABLE] ...

DESCRIPTION

La commande REINDEX reconstruit les index, et lorsqu'elle est utilisée avec l'option CONCURRENTLY, elle permet la reconstruction concurrente des index. La commande peut être utilisée avec les paramètres suivants :

Si SCHEMA, DATABASE ou SYSTEM est utilisé avec TABLESPACE, les relations système sont ignorées et un seul AVERTISSEMENT sera généré. Les index sur les tables TOAST sont reconstruits, mais pas déplacés vers le nouveau tablespace.

PARAMÈTRES

REINDEX [INDEX | TABLE] [CONCURRENTLY] [INDEX | TABLE] ...

NOTES

La reconstruction d'un index peut interférer avec le fonctionnement normal d'une base de données. Normalement, PostgreSQL verrouille la table dont l'index est reconstruit contre les écritures et effectue la construction complète de l'index avec une seule lecture de la table. D'autres transactions peuvent toujours lire la table, mais si elles tentent d'insérer, de mettre à jour ou de supprimer des lignes dans la table, elles seront bloquées jusqu'à ce que la reconstruction de l'index soit terminée. Cela pourrait avoir un effet grave si le système est une base de données de production active. Les tables très volumineuses peuvent prendre plusieurs heures à être indexées, et même pour les tables plus petites, une reconstruction d'index peut bloquer les écrivains pendant des périodes inacceptablement longues pour un système de production.

Les étapes suivantes se déroulent lors d'un reindex concurrent. Chaque étape est exécutée dans une transaction distincte. S'il y a plusieurs index à reconstruire, chaque étape parcourt tous les index avant de passer à l'étape suivante.

1. Une nouvelle définition d'index transitoire est ajoutée au catalogue pg_index. Cette définition sera utilisée pour remplacer l'ancien index. Un verrou SHARE UPDATE EXCLUSIVE au niveau de la session est pris sur les index en cours de reconstruction ainsi que sur leurs tables associées pour empêcher toute modification de schéma pendant le traitement.

2. Une première passe pour construire l'index est effectuée pour chaque nouvel index. Une fois l'index construit, son indicateur pg_index.indisready est mis à « vrai » pour le rendre prêt pour les insertions, le rendant visible aux autres sessions une fois que la transaction qui a effectué la construction est terminée. Cette étape est effectuée dans une transaction distincte pour chaque index.

3. Une deuxième passe est ensuite effectuée pour ajouter les tuples qui ont été ajoutés pendant que la première passe était en cours. Cette étape est également effectuée dans une transaction distincte pour chaque index.

4. Toutes les contraintes qui font référence à l'index sont modifiées pour faire référence à la nouvelle définition d'index, et les noms des index sont modifiés. À ce stade, pg_index.indisvalid est mis à « vrai » pour le nouvel index et à « faux » pour l'ancien, et une invalidation de cache est effectuée, provoquant l'invalidation de toutes les sessions qui référençaient l'ancien index.

5. Les anciens index ont leur indicateur pg_index.indisready mis à « faux » pour empêcher toute nouvelle insertion de tuple, après avoir attendu que les requêtes en cours qui pourraient faire référence à l'ancien index se terminent.

6. Les anciens index sont supprimés. Les verrous de session SHARE UPDATE EXCLUSIVE pour les index et la table sont libérés.

Si un problème survient lors de la reconstruction des index, telle qu'une violation d'unicité dans un index unique, la commande REINDEX échouera mais laissera derrière elle un nouvel index « invalide » en plus de celui préexistant. Cet index sera ignoré à des fins de requête car il pourrait être incomplet ; il consommera cependant toujours des surcoûts de mise à jour. La commande \d de psql signalera un tel index comme INVALID :

postgres=# \d tab
       Table "public.tab"
 Column |  Type   | Modifiers
--------+---------+-----------
 col    | integer |
Indexes:
    "idx" btree (col)
    "idx_ccnew" btree (col) INVALID

Si l'index marqué INVALID se termine par _ccnew, il correspond à l'index transitoire créé pendant l'opération concurrente, et la méthode de récupération recommandée est de le supprimer en utilisant DROP INDEX, puis de retenter REINDEX CONCURRENTLY. Si l'index invalide se termine plutôt par _ccold, il correspond à l'index d'origine qui n'a pas pu être supprimé ; la méthode de récupération recommandée est de simplement supprimer ledit index, car la reconstruction proprement dite a été réussie. Un nombre non nul peut être ajouté au suffixe des noms d'index invalides pour les maintenir uniques, comme _ccnew1, _ccold2, etc.

Les constructions d'index régulières permettent à d'autres constructions d'index régulières sur la même table de se produire simultanément, mais une seule construction d'index concurrente peut se produire sur une table à la fois. Dans les deux cas, aucun autre type de modification de schéma sur la table n'est autorisé pendant ce temps. Une autre différence est qu'une commande REINDEX TABLE ou REINDEX INDEX régulière peut être effectuée dans un bloc de transaction, mais REINDEX CONCURRENTLY ne le peut pas.

Comme toute transaction de longue durée, REINDEX sur une table peut affecter les tuples qui peuvent être supprimés par VACUUM concurrent sur toute autre table.

REINDEX SYSTEM ne prend pas en charge CONCURRENTLY car les catalogues système ne peuvent pas être réindexés de manière concurrente.

De plus, les index pour les contraintes d'exclusion ne peuvent pas être réindexés de manière concurrente. Si un tel index est nommé directement dans cette commande, une erreur est générée. Si une table ou une base de données avec des index de contrainte d'exclusion est réindexée de manière concurrente, ces index seront ignorés. (Il est possible de réindexer de tels index sans l'option CONCURRENTLY.)

Chaque backend exécutant REINDEX signalera sa progression dans la vue pg_stat_progress_create_index. Voir la section 27.4.4 pour plus de détails.

EXEMPLES

Reconstruire un index unique :

REINDEX INDEX mon_index ;

Reconstruire tous les index de la table ma_table :

REINDEX TABLE ma_table ;

Reconstruire les index d'une table, sans bloquer les opérations de lecture et d'écriture sur les relations impliquées pendant la reconstruction :

REINDEX TABLE CONCURRENTLY ma_table_cassee ;

COMPATIBILITÉ

Il n'y a pas de commande REINDEX dans la norme SQL.

VOIR AUSSI
