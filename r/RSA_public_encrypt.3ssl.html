RSA_PUBLIC_ENCRYPT(3ssl) OpenSSL RSA_PUBLIC_ENCRYPT(3ssl)

NOM

RSA_public_encrypt, RSA_private_decrypt - cryptographie RSA à clé publique

SYNOPSIS

#include <openssl/rsa.h>

Les fonctions suivantes sont dépréciées depuis OpenSSL 3.0 et peuvent être entièrement masquées en définissant OPENSSL_API_COMPAT avec une valeur de version appropriée, voir openssl_user_macros(7):

int RSA_public_encrypt(int flen, const unsigned char *from,
                       unsigned char *to, RSA *rsa, int padding);
int RSA_private_decrypt(int flen, const unsigned char *from,
                        unsigned char *to, RSA *rsa, int padding);

DESCRIPTION

Les deux fonctions décrites dans cette page sont dépréciées. Les applications devraient utiliser à la place EVP_PKEY_encrypt_init_ex(3), EVP_PKEY_encrypt(3), EVP_PKEY_decrypt_init_ex(3) et EVP_PKEY_decrypt(3).

RSA_public_encrypt() chiffre les flen octets de from (généralement une clé de session) en utilisant la clé publique rsa et stocke le texte chiffré dans to. to doit pointer vers RSA_size(rsa) octets de mémoire.

padding désigne l'un des modes suivants :

RSA_PKCS1_PADDING
Rembourrage PKCS #1 v1.5. C'est actuellement le mode le plus largement utilisé. Cependant, il est fortement recommandé d'utiliser RSA_PKCS1_OAEP_PADDING dans les nouvelles applications. VOIR L'AVERTISSEMENT CI-DESSOUS.
RSA_PKCS1_OAEP_PADDING
EME-OAEP tel que défini dans PKCS #1 v2.0 avec SHA-1, MGF1 et un paramètre d'encodage vide. Ce mode est recommandé pour toutes les nouvelles applications.
RSA_NO_PADDING
Chiffrement RSA brut. Ce mode ne doit être utilisé que pour implémenter des modes de rembourrage cryptographiquement valides dans le code de l'application. Le chiffrement direct de données utilisateur avec RSA n'est pas sécurisé.

Lors du chiffrement, flen ne doit pas être supérieur à RSA_size(rsa) - 11 pour les modes de rembourrage basés sur PKCS #1 v1.5, pas supérieur à RSA_size(rsa) - 42 pour RSA_PKCS1_OAEP_PADDING et égal à RSA_size(rsa) pour RSA_NO_PADDING. Lorsqu'un mode de rembourrage autre que RSA_NO_PADDING est utilisé, RSA_public_encrypt() inclura des octets aléatoires dans le texte chiffré et le texte chiffré sera donc différent à chaque fois, même si le texte clair et la clé publique sont exactement identiques. Le texte chiffré retourné dans to sera toujours complété par des zéros jusqu'à exactement RSA_size(rsa) octets. to et from peuvent se chevaucher.

RSA_private_decrypt() déchiffre les flen octets de from en utilisant la clé privée rsa et stocke le texte clair dans to. flen doit être égal à RSA_size(rsa) mais peut être plus petit, lorsqu'il y a des octets nuls en tête dans le texte chiffré. Ceux-ci ne sont pas importants et peuvent être supprimés, mais RSA_public_encrypt() ne le fait pas. to doit pointer vers une section mémoire suffisamment grande pour contenir les données décryptées maximales possibles (qui sont égales à RSA_size(rsa) pour RSA_NO_PADDING, RSA_size(rsa) - 11 pour les modes de rembourrage basés sur PKCS #1 v1.5 et RSA_size(rsa) - 42 pour RSA_PKCS1_OAEP_PADDING). padding est le mode de rembourrage qui a été utilisé pour chiffrer les données. to et from peuvent se chevaucher.

VALEURS DE RETOUR

RSA_public_encrypt() retourne la taille des données chiffrées (c'est-à-dire RSA_size(rsa)). RSA_private_decrypt() retourne la taille du texte clair récupéré. Une valeur de retour de 0 n'est pas une erreur et signifie seulement que le texte clair était vide.

En cas d'erreur, -1 est retourné ; les codes d'erreur peuvent être obtenus par ERR_get_error(3).

AVERTISSEMENTS

Les échecs de déchiffrement en mode RSA_PKCS1_PADDING révèlent des informations qui peuvent potentiellement être utilisées pour monter une attaque par oracle de remplissage de Bleichenbacher. C'est une faiblesse inhérente dans la conception du remplissage PKCS #1 v1.5. Préférez RSA_PKCS1_OAEP_PADDING.

Dans OpenSSL avant la version 3.2.0, la valeur de retour et la longueur de la valeur retournée pouvaient être utilisées pour monter l'attaque de Bleichenbacher. Depuis la version 3.2.0, le fournisseur par défaut dans OpenSSL ne retourne pas d'erreur lorsque les vérifications de remplissage échouent. Il génère plutôt un message aléatoire basé sur la clé privée utilisée et le texte chiffré fourni, de sorte que le code de l'application n'ait pas à implémenter une gestion des erreurs sécurisée par canal auxiliaire. Les applications qui veulent être sécurisées contre les attaques par canal auxiliaire avec des fournisseurs qui n'implémentent pas de rejet implicite doivent toujours gérer les valeurs retournées en utilisant un code exempt de canal auxiliaire. La gestion sans canal auxiliaire de la pile d'erreurs peut être effectuée en utilisant soit une paire d'appels inconditionnels ERR_set_mark(3) et ERR_pop_to_mark(3), soit en utilisant l'appel ERR_clear_error(3).

CONFORMITÉ

SSL, PKCS #1 v2.0
