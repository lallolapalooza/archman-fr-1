NOM

RlwrapFilter - Classe Perl pour les filtres rlwrap

SYNTAXE

use lib $ENV{RLWRAP_FILTERDIR};
use RlwrapFilter;
$filter = new RlwrapFilter;
$filter -> output_handler(sub {s/apple/orange/; $_}); # réécrire la sortie
$filter -> prompt_handler(\&pimp_the_prompt); # changer l'invite
$filter -> history_handler(sub {s/with password \w+/with password ****/; $_}); # garder les mots de passe hors de l'historique
$filter -> run;

DESCRIPTION

rlwrap (1) (https://github.com/hanslub42/rlwrap) est une petite utilitaire qui se place entre l'utilisateur et n'importe quelle commande de console, avec pour but d'apporter des capacités de readline (édition de ligne, récupération d'historique) aux commandes qui n'en ont pas.

Depuis la version 0.32, rlwrap peut utiliser des filtres pour scripter presque chaque aspect de votre interaction avec l'utilisateur : changement de l'historique, réécriture de la sortie et de l'entrée, appel d'un pager ou calcul de listes de mots de complétion à partir de l'entrée courante.

Les filtres peuvent être combinés dans un pipeline en utilisant le filtre spécial pipeline.

RlwrapFilter rend l'écriture de filtres rlwrap en Perl très simple. Un filtre a seulement besoin de créer un objet RlwrapFilter, de changer un ou deux de ses gestionnaires par défaut, puis d'appeler la méthode run.

Il existe également un module Python 3 appelé rlwrapfilter.py, distribué avec rlwrap, qui fournit une API presque identique à son homologue perl.

MÉTHODES PUBLIQUES

CONSTRUCTEUR

$f = new RlwrapFilter
$f = RlwrapFilter -> new(prompt_handler => sub {"Hi! > "}, minimal_rlwrap_version => "0.35", ...)
Retourne un nouvel objet RlwrapFilter.

DÉFINITION/OBTENTION DES GESTIONNAIRES

Les gestionnaires sont des rappels définis par l'utilisateur qui spécifient une ou plusieurs des méthodes d'un objet RlwrapFilter (handle_input, handle_prompt). Ils sont appelés depuis la méthode run en réponse à un message envoyé par rlwrap. Les messages se composent d'une étiquette indiquant quel gestionnaire doit être appelé (par exemple, TAG_INPUT, TAG_HISTORY) et du texte du message. En général, un filtre remplace seulement une ou deux méthodes.

CONVENTIONS D'APPEL

Dans de nombreux cas (par exemple, TAG_INPUT, TAG_OUTPUT, TAG_PROMPT), le texte du message est une chaîne simple. Votre gestionnaire est appelé avec le texte du message (c'est-à-dire l'entrée non filtrée, la sortie, l'invite) comme seul argument. Pour plus de commodité, $_ est défini sur la même valeur. Vous devez retourner le texte réécrit du message.

Certains gestionnaires (ceux pour TAG_COMPLETION et TAG_HOTKEY) sont un peu plus complexes : le texte du message (accessible via $_) est une liste de champs séparés par des tabulations ; ils sont appelés avec plusieurs arguments et évalués dans un contexte de liste.

Les gestionnaires sont appelés dans un ordre cyclique fixe : invite, complétion, historique, entrée, écho, sortie, invite, etc. Rlwrap peut toujours sauter un gestionnaire lorsqu'il est en mode direct ; d'un autre côté, les gestionnaires de complétion et de sortie peuvent être appelés plus d'une fois consécutivement. Si un gestionnaire est défini comme indéfini, le résultat est comme si le texte du message n'avait pas été réécrit (en fait, rlwrap sait quand cela se produit et le message ne sera pas envoyé).

Il est important de noter que le filtre, et donc tous ses gestionnaires, sont sautés lorsque command est en mode direct, c'est-à-dire lorsqu'il demande des touches individuelles (et aussi, pour des raisons de sécurité, lorsqu'il n'y a pas d'écho, par exemple, lorsqu'il demande un mot de passe). Si vous ne voulez pas que cela se produise, utilisez rlwrap -a pour forcer rlwrap à rester en mode readline et à appliquer le filtre à toute l'entrée et la sortie de command. Cela rendra les éditeurs et les pagers (qui répondent aux touches individuelles) inutilisables, sauf si vous utilisez l'option -N de rlwrap (uniquement sous Linux).

Les accesseurs/mutateurs pour les gestionnaires respectifs sont énumérés ci-dessous :

$handler = $f -> prompt_handler, $f -> prompt_handler(\&handler)
Le gestionnaire d'invite réécrit les invites et est appelé lorsque rlwrap décide qu'il est temps de « cuire » l'invite, par défaut après que la dernière sortie soit arrivée. Clairement, rlwrap ne peut pas lire dans les pensées de command, donc ce qui ressemble à une invite pour rlwrap peut être le début d'une ligne de sortie que command a mis un peu plus de temps à formuler. Si c'est un problème, spécifiez un temps de « cuisson » plus long avec l'option -w de rlwrap, utilisez la méthode prompts_are_never_empty ou « rejetez » l'invite (cf. la méthode prompt_rejected).
$handler = $f -> completion_handler, $f -> completion_handler(\&handler)
Le gestionnaire de complétion est appelé avec trois arguments : la ligne complète, le préfixe (mot partiel à compléter) et la liste des complétions propres à rlwrap. Vous devez retourner une liste (éventuellement modifiée) de complétions. À titre d'exemple, si l'utilisateur a tapé « She played for A<TAB> », le gestionnaire est appelé comme suit : 
myhandler("She played for A", "A", "Arsenal", "Arendal", "Anderlecht")

vous pouvez retourner une liste de clubs plus forts :

"Ajax", "AZ67", "Arnhem")

$handler = $f -> history_handler, $f -> history_handler(\&handler)
Chaque ligne d'entrée est envoyée à ce gestionnaire, la valeur renvoyée est ajoutée à l'historique de rlwrap. Retourner une valeur vide ou indéfinie gardera la ligne d'entrée hors de l'historique.
$handler = $f -> hotkey_handler, $f -> hotkey_handler(\&handler)
Si, lors de l'édition d'une ligne d'entrée, l'utilisateur appuie sur une touche qui est associée à « rlwrap_hotkey » dans .inputrc, le gestionnaire est appelé avec cinq arguments : la touche, le préfixe (partie de la ligne d'entrée actuelle avant le curseur), le reste de la ligne d'entrée (suffixe), l'historique sous forme de chaîne (« ligne 1\nligne 2\n...ligne N »), et la position dans l'historique. Vous devez retourner une liste similaire, à l'exception du premier élément qui sera imprimé dans la « zone d'écho » s'il diffère de la valeur d'origine.

Exemple : si la ligne d'entrée actuelle est « pea soup » (avec le curseur sur l'espace), et que l'utilisateur appuie sur CTRL+P, qui est associé à « rlwrap-hotkey » dans .inputrc, le gestionnaire est appelé comme suit :

my_handler("\0x10", "pea", " soup", "tomato soup\nasparagus..", 12) # 16 = CTRL-P

Si vous préférez le « cucumber soup », le gestionnaire devrait retourner :

("Mmmm!", "peanut", " soup", "asparagus..", 11)

après quoi la ligne d'entrée deviendra « peanut soup » (avec le curseur sur l'espace), la zone d'écho affichera « Mmmm! », et toute référence à des soupes inférieures sera supprimée de l'historique.

Si la ligne d'entrée se termine par un retour à la ligne, rlwrap acceptera immédiatement le résultat.

$handler = $f -> input_handler, $f -> input_handler(\&handler)
Chaque ligne d'entrée (qui peut contenir plusieurs lignes séparées par \n, lors de l'utilisation des papiers coupés) est envoyée à ce gestionnaire. La valeur renvoyée par le gestionnaire est écrite dans le pty (pseudo terminal) de command.
$handler = $f -> echo_handler, $f -> echo_handler(\&handler)
La première ligne de sortie lue à partir du pty de command est la ligne d'entrée échoée. Si votre gestionnaire d'entrée modifie la ligne d'entrée, la version modifiée sera affichée. Si vous ne voulez pas embrouiller l'utilisateur, utilisez un gestionnaire d'écho qui retourne votre entrée originale.

Si vous utilisez le mode multi-lignes de rlwrap, les lignes d'écho supplémentaires doivent être gérées par le gestionnaire de sortie.

$handler = $f -> output_handler, $f -> output_handler(\&handler)
Toute la sortie de command après la ligne d'écho est envoyée à ce gestionnaire (y compris les retours à la ligne). Ce gestionnaire peut être appelé plusieurs fois consécutivement, en fonction de la taille des appels write() de command et du comportement du système de planification. Par conséquent, votre gestionnaire doit être préparé à réécrire votre sortie en « morceaux » où vous n'avez même pas la garantie que le résultat est disponible.
morceaux contiennent des lignes entières ininterrompues.

Si vous souhaitez gérer la sortie entière de command en une seule fois, vous pouvez spécifier un gestionnaire de sortie qui renvoie une chaîne vide, puis utiliser $filter -> cumulative_output dans votre gestionnaire de prompt pour envoyer la sortie réécrite "hors bande" juste avant le prompt :

$filter -> output_handler(sub {""});
$filter -> prompt_handler(
              sub{ $filter -> send_output_oob(mysub($filter -> cumulative_output));
                   "Salut > "
                 });

Notez que lorsque rlwrap est exécuté en mode --multi-line, le gestionnaire d'écho ne traitera toujours que la première ligne d'écho. Le reste sera généralement renvoyé précédé d'un prompt de continuation ; il appartient au gestionnaire de sortie de décider quoi en faire.

$handler = $f -> signal_handler, $f -> signal_handler(\&handler)
Comme rlwrap est transparent aux signaux, les signaux sont transmis à command. Ce gestionnaire est appelé (sous la forme handler($signo)) pour les signaux SIGHUP, SIGINT, SIGQUIT, SIGTERM, SIGCONT, SIGUSR1, SIGUSR2 et SIGWINCH, avant que le signal ne soit délivré. Il reçoit ($signo en tant que chaîne de caractères) et doit le retourner. Le signal renvoyé est délivré à command ; renvoyer "0" pour ignorer totalement le signal. La sortie peut être écrite hors bande (à rlwrap) ou en mode furtif (à command, voir ci-dessous)
$handler = $f -> message_handler, $f -> message_handler(\&handler)
Ce gestionnaire est appelé (sous la forme handler($message, $tag)) pour chaque message entrant et chaque étiquette (y compris les étiquettes hors bande), avant tous les autres gestionnaires. Sa valeur de retour est ignorée, mais il peut être utile à des fins de journalisation et de débogage. Le $tag est un entier qui peut être converti en nom d'étiquette par la méthode 'tag2name'.

AUTRES METHODES

$f -> help_text("Usage...")
Définit le texte d'aide pour ce filtre. Il sera affiché par rlwrap -z <filtre>. La deuxième ligne du texte d'aide est utilisée par "rlwrap -z listing" ; elle doit être une courte description de ce que fait le filtre.
$f -> minimal_rlwrap_version("x.yy")
Arrête l'exécution sauf si la version de rlwrap est x.yy ou plus récente.
$dir = $f -> cwd
renvoie le nom du répertoire de travail courant de command. Ceci utilise le système de fichiers /proc et peut ne fonctionner que sur les systèmes linux récents (sur les anciens linux et Solaris, il renverra quelque chose comme "/proc/12345/cwd", utile pour trouver le contenu du répertoire de travail de command, mais pas son nom).
$text = $f -> cumulative_output
renvoie la sortie cumulative actuelle. Toute sortie (non traitée) est ajoutée à la sortie cumulative après l'appel du gestionnaire de sortie. La sortie cumulative commence sur une base propre avec chaque message OUTPUT qui suit directement un message INPUT (en ignorant les messages hors bande et les prompts rejetés).

Lorsque nécessaire (c'est-à-dire lorsque rlwrap est en mode "impatient"), le prompt est retiré de $filter->cumulative_output au moment où le gestionnaire de prompt est appelé.

$tag = $f -> previous_tag
L'étiquette du dernier message en bande précédent. Une étiquette est un entier entre 0 et 255, son nom peut être trouvé avec la méthode suivante :
$name = $f -> tag2name($tag)
Convertit l'étiquette (un entier) en son nom (par exemple "TAG_PROMPT").
$name = $f -> name2tag($tag)
Convertit un nom d'étiquette valide comme "TAG_PROMPT" en étiquette (un entier).
$f -> send_output_oob($text)
Demande à rlwrap d'afficher $text. $text est envoyé "hors bande" : rlwrap ne le verra qu'juste après avoir envoyé le message suivant au filtre.
$f -> send_ignore_oob($text)
Envoie un message hors bande TAG_IGNORE à rlwrap. rlwrap l'ignorera silencieusement, mais cela peut être utile lors du débogage de filtres.
$f -> tweak_readline_oob($readline_function, @parameters)
Envoie un message hors bande formaté spécialement afin de modifier readline (c'est-à-dire pour que rlwrap appelle une fonction readline ou définisse une variable readline). Voir la documentation GNU Readline pour plus de détails.

À l'heure actuelle, les tweaks suivants sont reconnus :

$filter -> tweak_readline_oob("rl_variable_bind", $rl_variable_name, $value);
# ... uniquement pour les variables readline liées comme celles de .inputrc
$filter -> tweak_readline_oob("rl_completer_word_break_characters", $chars);
$filter -> tweak_readline_oob("rl_completer_quote_characters", $chars);
$filter -> tweak_readline_oob("rl_filename_completion_desired", "0" ou "1");

Les paramètres ne doivent pas contenir de "::" (deux points consécutifs). Cette méthode peut être appelée à tout moment, même avant $filter -> run.

$f -> add_to_completion_list(@words)
$f -> remove_from_completion_list(@words)
Ajoute ou supprime définitivement les mots de @words de/de la liste de complétion de rlwrap.
$f -> cloak_and_dagger($question, $prompt, $timeout);
Envoie $question à l'entrée de command et lit tout ce qui revient jusqu'à ce que $prompt soit rencontré à la "fin du morceau", ou qu'aucun nouveau morceau n'arrive pendant $timeout secondes, selon ce qui arrive en premier. Renvoie la réponse (sans le $prompt final). rlwrap reste complètement inconscient de cette conversation ; elle n'apparaîtra même pas dans les journaux de débogage de rlwrap ou dans la sortie du filtre logger. D'où aussi :
$f -> cloak_and_dagger_verbose($verbosity)
Si $verbosity est évalué à une valeur vraie, demande à rlwrap d'afficher toutes les questions envoyées à command par la méthode "cloak_and_dagger", et les réponses de command. Par défaut, $verbosity = 0 ; le régler à 1 perturbera l'écran mais facilitera grandement l'utilisation (sinon assez délicate) de "cloak_and_dagger".
$self -> prompt_rejected
Un texte spécial ("_THIS_CANNOT_BE_A_PROMPT_") à renvoyer par un gestionnaire de prompt pour "rejeter" le prompt. Cela amènera rlwrap à ignorer le traitement du prompt. $self->previous_tag et $self->cumulative_output ne seront pas modifiés.
$text = $f -> prompts_are_never_empty($val)
Si $val est évalué à une valeur vraie, rejette automatiquement les prompts vides.
$f -> command_line
En contexte scalaire : la commande rlwrapped et ses arguments sous forme de chaîne ("commande -v bidule") ; en contexte liste : la même chose sous forme de liste ("commande", "-v", "bidule").
$f -> running_under_rlwrap
Indique si le filtre est exécuté par rlwrap, ou directement depuis la ligne de commande.
$f -> run
Démarre une boucle d'événements qui lit les messages de rlwrap depuis le tube d'entrée, appelle les gestionnaires appropriés et écrit le résultat dans le tube de sortie. Cette méthode ne retourne jamais.

PROTOCOLE BAS NIVEAU

rlwrap communique avec un filtre via des messages composés d'un octet d'étiquette (TAG_OUTPUT, TAG_PROMPT etc. - pour informer le filtre de ce qui est envoyé), d'un entier non signé de 32 bits contenant la longueur du message, du texte du message et d'une nouvelle ligne supplémentaire. Pour chaque message envoyé, rlwrap attend une réponse avec la même étiquette. Renvoyer une étiquette différente (en bande) est une erreur et tue instantanément rlwrap, bien que les filtres puissent précéder leur message de réponse avec des messages "hors bande" pour afficher du texte (TAG_OUTPUT_OUT_OF_BAND), signaler des erreurs (TAG_ERROR) et manipuler la liste des mots de complétion (TAG_ADD_TO_COMPLETION_LIST et TAG_REMOVE_FROM_COMPLETION_LIST). Les messages hors bande ne sont traités par rlwrap qu'juste après l'envoi du message en bande suivant - la communication avec le filtre est synchrone et pilotée par rlwrap.

Les messages sont reçus et envoyés via deux tubes. STDIN, STDOUT et STDERR sont toujours connectés au terminal de l'utilisateur, et vous pouvez les lire et les écrire directement, bien que cela puisse perturber l'écran et confondre l'utilisateur à moins d'être prudent. Un filtre peut même communiquer avec la commande rlwrapped derrière le dos de rlwrap (cf la méthode cloak_and_dagger()).

Le protocole utilise les étiquettes suivantes (les étiquettes > 128 sont hors bande) :

TAG_INPUT       0
TAG_OUTPUT      1
TAG_HISTORY     2
TAG_COMPLETION  3
TAG_PROMPT      4
TAG_HOTKEY      5
TAG_SIGNAL      6
TAG_WHAT_ARE_YOUR_INTERESTS     127
TAG_IGNORE                      251
TAG_ADD_TO_COMPLETION_LIST      252
TAG_REMOVE_FROM_COMPLETION_LIST 253
TAG_OUTPUT_OUT_OF_BAND          254
TAG_ERROR                       255

Pour voir comment cela fonctionne, vous pouvez espionner le protocole en utilisant le filtre logger.

Les constantes TAG_INPUT, ... sont exportées par le module RlwrapFilter.pm.

TAG_WHAT_ARE_YOUR_INTERESTS est seulement utilisé en interne, pour éviter l'échange de messages qui ne seront pas gérés par le filtre de toute façon. Il sera vu par le gestionnaire de messages général, et apparaîtra donc (exactement une fois, au démarrage du programme) dans la sortie par exemple du filtre logger.

SIGNALS

Comme STDIN est toujours connecté au terminal de l'utilisateur, on pourrait s'attendre à ce que le filtre reçoive SIGINT, SIGTERM, SIGTSTP directement du pilote de terminal si l'utilisateur appuie sur CTRL-C, CTRL-Z etc. Normalement, nous ne voulons pas cela - cela confondrait rlwrap, et l'utilisateur (qui pense parler directement à la commande rlwapped) voulait probablement que ces signaux soient envoyés à la commande elle-même. Pour cette raison, le filtre commence avec tous les signaux bloqués.

Les filtres qui interagissent avec le terminal de l'utilisateur (par exemple pour exécuter un paginateur) devraient débloquer des signaux comme SIGTERM, SIGWINCH.

DURÉE DE VIE DU FILTRE

Le filtre est démarré par rlwrap après command, et reste actif tant que rlwrap s'exécute. Les méthodes du filtre sont immédiatement utilisables. Lorsque command se termine, le filtre reste actif un peu plus longtemps pour traiter les derniers mots de command. Comme l'appel des méthodes cwd et cloak_and_dagger à ce moment fera mourir le filtre avec une erreur, il peut être conseillé d'encapsuler ces appels dans

n eval{}

Si un filtre appelle die(), il enverra un message TAG_ERROR (hors bande) à rlwrap avant de quitter. rlwrap signalera alors le message et quittera (juste après son prochain message en bande – les messages hors bande ne sont pas toujours traités immédiatement)

die() dans un eval() configure $@ comme d'habitude.

ENVIRONNEMENT

Avant d'appeler un filtre, rlwrap définit les variables d'environnement suivantes :

RLWRAP_FILTERDIR      répertoire où se trouvent RlwrapFilter.pm et la plupart des filtres (défini par rlwrap, peut être
                      remplacé par l'utilisateur avant d'appeler rlwrap)
PATH                  rlwrap ajoute automatiquement $RLWRAP_FILTERDIR au début du PATH du filtre
RLWRAP_VERSION        version de rlwrap (par exemple, "0.35")
RLWRAP_COMMAND_PID    identifiant du processus de la commande rlwrapped
RLWRAP_COMMAND_LINE   ligne de commande de la commande rlwrapped
RLWRAP_IMPATIENT      indique si rlwrap est en mode "impatient" (voir rlwrap (1)). En mode impatient,
                      l'invite candidate est filtrée par le gestionnaire de sortie (et affichée avant
                      d'être écrasée par l'invite cuisinée).
RLWRAP_INPUT_PIPE_FD  Descripteur de fichier du tube d'entrée. Pour usage interne uniquement
RLWRAP_OUTPUT_PIPE_FD Descripteur de fichier du tube de sortie. Pour usage interne uniquement
RLWRAP_MASTER_PTY_FD  Descripteur de fichier du pty de la commande.
RLWRAP_BREAK_CHARS    Les caractères que rlwrap considère comme des séparateurs de mots (voir l'option --break-chars dans rlwrap (1))
RLWRAP_DEBUG          La valeur de l'option --debug (-d) passée à rlwrap

DEBOGAGE DES FILTRES

Bien que RlwrapFilter.pm facilite l'écriture de filtres simples, leur débogage peut poser problème. Quelques astuces utiles :

ENREGISTREMENT

Lors de l'exécution d'un filtre, les messages entrants et sortants peuvent être enregistrés par le filtre logger, en utilisant un pipeline :

rlwrap -z 'pipeline logger incoming : my_filter : logger outgoing' command

EXECUTION SANS rlwrap

Lorsqu'ils sont appelés par rlwrap, les filtres reçoivent leur entrée de $RLWRAP_INPUT_PIPE_FD et écrivent leur sortie sur $RLWRAP_OUTPUT_PIPE_FD, et attendent et écrivent des messages composés d'un octet de balise, d'une longueur de 32 bits et du message propre. Ce n'est pas très utile lorsqu'on exécute un filtre directement depuis la ligne de commande (en dehors de rlwrap), même si nous définissons nous-mêmes les RLWRAP_*_FD.

Par conséquent, lorsqu'il est exécuté directement depuis la ligne de commande, un filtre attend des messages d'entrée sur son entrée standard de la forme

TAG_PROMPT monprompt >

(c'est-à-dire un nom de balise, un espace et un message suivi d'un retour à la ligne. Le message ne contiendra pas le retour à la ligne final) et il répondra de la même manière sur sa sortie standard. Bien sûr, rlwrap peut aider à éviter la saisie fastidieuse des noms de balises (et, pour plus de commodité, vous pouvez omettre le préfixe "TAG_" et taper le nom de la balise en minuscules)

rlwrap -i -f TAGNAMES -p -S "filtre > "  ./filtre_a_deboguer

Comme rlwrap ne peut pas insérer de TAB ni de retours à la ligne dans les lignes d'entrée, les filtres convertiront '\t' et '\n' en TAB et retour à la ligne lorsqu'ils seront exécutés directement depuis la ligne de commande.
