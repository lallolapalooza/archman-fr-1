NOM

VirtualBindings — Associations pour les événements virtuels de souris et de clavier

DESCRIPTION

Les pages de référence Motif décrivent les translations de touches en termes d'associations virtuelles, basées sur celles décrites dans le Guide de style Motif.

Associations pour les clés osf

Les chaînes de clés commençant par <osf> ne font pas partie du mappage clavier du serveur X. Au lieu de cela, ces clés sont produites côté client à l'exécution. Elles sont interprétées par la routine XmTranslateKey et sont utilisées par le gestionnaire de traduction lorsque le serveur livre un événement de touche réel. Pour chaque application, un mappage est maintenu entre les clés <osf> et les clés correspondant aux touches réelles. Ce mappage est basé sur des informations obtenues au démarrage de l'application à partir de l'une des sources suivantes, listées par ordre de priorité :

•
La ressource XmNdefaultVirtualBindings de Display.
•
Une propriété sur la fenêtre racine, qui peut être définie par mwm au démarrage, ou par le client xmbind, ou lors d'un démarrage antérieur d'une application Motif.
•
Le fichier .motifbind dans le répertoire personnel de l'utilisateur.
•
Un ensemble d'associations basé sur la chaîne du vendeur et éventuellement la version du vendeur du serveur X. Motif recherche ces associations en suivant les étapes suivantes :
0.
Si le fichier xmbind.alias existe dans le répertoire personnel de l'utilisateur, Motif recherche dans ce fichier un nom de chemin associé à la chaîne du vendeur ou à la chaîne du vendeur et à la version du vendeur. S'il trouve un tel nom de chemin et si ce fichier existe, Motif charge les associations contenues dans ce fichier.
1.
S'il n'a trouvé aucune association, Motif recherche ensuite le fichier xmbind.alias dans le répertoire spécifié par la variable d'environnement XMBINDDIR, si XMBINDDIR est définie, ou dans le répertoire /usr/lib/Xm/bindings si XMBINDDIR n'est pas définie. Si ce fichier existe, Motif le recherche pour trouver un nom de chemin associé à la chaîne du vendeur ou à la chaîne du vendeur et à la version du vendeur. S'il trouve un tel nom de chemin et si ce fichier existe, Motif charge les associations contenues dans ce fichier.
2.
S'il n'a toujours trouvé aucune association, Motif charge un ensemble d'associations de secours codées en dur.

Le fichier xmbind.alias contient zéro ou plusieurs lignes de la forme suivante :

"chaîne_vendeur[ version_vendeur]"    fichier_associations

où chaîne_vendeur est le nom du vendeur du serveur X tel que retourné par le client X xdpyinfo ou la fonction Xlib XServerVendor, et doit être entre guillemets doubles. Si version_vendeur est incluse, il s'agit du numéro de version du vendeur du serveur X tel que retourné par le client X xdpyinfo ou la fonction Xlib XVendorRelease, et doit également être contenue entre guillemets doubles, séparée par un espace de chaîne_vendeur. L'argument version_vendeur est fourni pour permettre la prise en charge des changements de matériel clavier d'un vendeur, en supposant que le vendeur incrémente le numéro de version pour signaler de tels changements. Alternativement, le vendeur peut simplement utiliser une chaîne de vendeur unique pour chaque clavier différent.

L'argument fichier_associations est le nom du chemin du fichier contenant les associations elles-mêmes. Il peut s'agir d'un chemin relatif ou absolu. S'il s'agit d'un chemin relatif, il est relatif à l'emplacement du fichier xmbind.alias.

Les lignes de commentaire dans le fichier xmbind.alias commencent par ! (point d'exclamation).

Les associations trouvées soit dans le fichier .motifbind, soit dans le mappage du vendeur sont placées dans une propriété sur la fenêtre racine. Cette propriété est utilisée pour déterminer les associations des applications Motif ultérieures.

Au démarrage, mwm tente de charger le fichier .motifbind dans le répertoire personnel de l'utilisateur. Si cela échoue, il charge les associations du vendeur comme décrit précédemment. Il place les associations qu'il charge dans une propriété sur la fenêtre racine pour être utilisées par les applications Motif ultérieures.

La fonction xmbind charge les associations à partir d'un fichier si ce fichier est spécifié sur la ligne de commande. Si aucun fichier n'est spécifié sur la ligne de commande, elle tente de charger le fichier .motifbind dans le répertoire personnel de l'utilisateur. Si cela échoue, elle charge les associations du vendeur comme décrit précédemment. Elle place les associations qu'elle charge dans une propriété sur la fenêtre racine pour être utilisées par les applications Motif ultérieures.

Le format de la spécification pour mapper les clés <osf> à des clés réelles est similaire à celui d'une spécification de translation d'événements. (Voir ci-dessous) La syntaxe est spécifiée (et ci-dessous) ici en notation EBNF en utilisant les conventions suivantes :

[a]    Signifie soit rien soit a
{a}    Signifie zéro ou plusieurs occurrences de a
(a|b)    Signifie soit a soit b.

Les terminaux sont entre guillemets doubles.

La syntaxe d'une spécification d'association de clé <osf> est la suivante :

binding_spec    =       {line "\n"} [line]
line            =       virtual_keysym ":" list_of_key_event
list_of_key_event=      key_event { "," key_event}
key_event       =       {modifier_name} "<Key>" actual_keysym
virtual_keysym  =       keysym
actual_keysym   =       keysym
keysym          =       Un nom de clé X11 valide qui est
                        mappé par XStringToKeysym

Comme pour les translations d'événements, les descriptions d'événements plus spécifiques doivent précéder les descriptions moins spécifiques. Par exemple, une description d'événement pour une touche avec un modificateur doit précéder une description pour la même touche sans le même modificateur.

Voici un exemple de spécification pour la ressource defaultVirtualBindings dans un fichier de ressources :

*defaultVirtualBindings: \
        osfBackSpace:       <Key>BackSpace       \n\
        osfInsert:       <Key>InsertChar      \n\
        osfDelete:       <Key>DeleteChar      \n\
...
        osfLeft:       <Key>left, Ctrl<Key>H

Le format d'un fichier .motifbind ou d'un fichier contenant les associations du vendeur est le même, à l'exception que la spécification de liaison pour chaque clé est placée sur une ligne distincte. La spécification précédente apparaît comme suit dans un fichier .motifbind ou de liaison du vendeur :

osfBackSpace:       <Key>BackSpace
osfInsert:       <Key>InsertChar
osfDelete:       <Key>DeleteChar
...
osfLeft:       <Key>left, Ctrl<Key>H

Changements dans la gestion des touches Majuscule

En conjonction avec le patch 24 de MIT X11R5, cette version de Motif introduit un changement dans la manière dont les touches impliquant le modificateur <Shift> sont traitées. Ce changement permet au pavé numérique d'être utilisé pour générer des nombres via les mécanismes standard de X. Étant donné que le comportement par défaut consiste maintenant à honorer les liaisons de carte de touches xmodmap, les traductions et les liaisons de touches virtuelles qui utilisent <Shift> peuvent se comporter différemment. Un symptôme courant est que les touches du pavé numérique et les touches de fonction non décalées (avec ou sans autres modificateurs) produisent les résultats attendus, mais les touches décalées non.

Pour obtenir l'ancien comportement, vous pouvez supprimer l'interprétation décalée des touches problématiques à l'aide de l'utilitaire xmodmap. Chaque entrée d'une table de carte de touches xmodmap contient jusqu'à quatre liaisons de keysym. Les deuxième et quatrième keysyms sont pour les touches décalées. Si une expression ne contient que deux keysyms, supprimez simplement le deuxième keysym. Si une entrée contient trois keysyms ou plus, remplacez le deuxième keysym par NoSymbol et supprimez le quatrième keysym.

Traductions d'actions

La syntaxe de la table de traduction utilisée par Motif est entièrement spécifiée dans la documentation des intrinsèques du toolkit X11R5. Pour une description complète de la syntaxe, et pour des instructions générales sur la rédaction ou la modification d'une table de traduction, veuillez vous référer à ce document. Un bref résumé du format de la table de traduction est cependant inclus ci-dessous.

La syntaxe est définie comme dans la spécification de la syntaxe de liaison ci-dessus. Les descriptions informelles sont contenues entre chevrons (<>).

TranslationTable=       [ directive ] { production }
directive       =       ( "#replace" | "#override" | "#augment") "\n"
production      =       lhs ":" rhs "\n"
lhs             =       ( event | keyseq) {"," ( event | keyseq) }
keyseq          =       """ keychar { keychar } """
keychar         =       ( "^" | "$" | "\\") <ISO Latin 1 character>
event           =       [ modifier_list ] "<" event_type ">" [ count ] {detail}
modifier_list   =       ( ["!"][":"] { modifier } | "None")
modifier        =       [ "~" ] ( "@" <keysym> | <name from table below>)
count           =       "(" <positive integer> [ "+" ] ")"
rhs             =       { action_name "(" [params] ")" }
params          =       string { "," string }

Le champ string n'a pas besoin d'être mis entre guillemets sauf s'il contient un espace ou une tabulation, ou une virgule, un saut de ligne ou une parenthèse. La liste entière des valeurs de chaîne composant le champ params sera passée à la routine d'action nommée.

Le champ details peut être utilisé pour spécifier un keysym qui identifiera un événement de touche particulier. Par exemple, <Key> est le nom d'un type d'événement, mais il doit être modifié par le champ details pour nommer un événement spécifique, tel que <Key>A.

Noms des modificateurs La liste des modificateurs, qui peut être vide, se compose d'une liste de touches modificatrices qui doivent être enfoncées avec la séquence de touches. Les touches modificatrices peuvent être abrégées par des lettres uniques, comme dans la liste suivante des modificateurs familiers :

s
Shift (Majuscule)
c ou ^
Ctrl (Control)
m ou $
Meta
a
Alt

D'autres modificateurs sont disponibles, tels que "Mod5" et "Button2." Ceux-ci n'ont pas d'abréviation (bien que les modificateurs "Button" puissent être abrégés en combinaison avec des événements, comme décrit ci-dessous). Si une liste de modificateurs est vide et n'est pas "None", cela signifie que la position des touches modificatrices n'a pas d'importance. Si des modificateurs sont listés, les touches désignées doivent être dans la position spécifiée, mais les touches modificatrices non listées sont sans importance. Si la liste commence

ns avec un point d'exclamation (!), cependant, les modificateurs non répertoriés peuvent ne pas être affirmés. De plus, si un nom de modificateur est précédé d'un tilde (~), la touche correspondante ne doit pas être enfoncée.

Si une liste de modificateurs commence par un deux-points (:), X essaie d'utiliser les modificateurs standard (Shift et Lock), s'ils sont présents, pour mapper le code de l'événement clavier en un keysym reconnu.

Types d'événements Ce sont quelques-uns des types d'événements reconnus.

Key ou KeyDown
Une touche du clavier a été enfoncée.
KeyUp
Une touche du clavier a été relâchée.
BtnDown
Un bouton de la souris a été enfoncé.
BtnUp
Un bouton de la souris a été relâché.
Motion
Le pointeur de la souris a bougé.
Enter
Le pointeur est entré dans la fenêtre du widget.
Leave
Le pointeur a quitté la fenêtre du widget.
FocusIn
Le widget a reçu le focus.
FocusOut
Le widget a perdu le focus.

Il existe quelques abréviations d'événements disponibles. Par exemple, <Btn1Motion> est en fait un événement « Motion », modifié avec le modificateur « Button1 » (Button1<Motion>). De même, <Btn3Up> est en fait un événement « BtnUp » avec le modificateur « Button3 ». Ces abréviations sont largement utilisées dans les tables de traduction Motif.
