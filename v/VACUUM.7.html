NOM

VACUUM - récupérer de l'espace et/ou analyser une base de données

SYNTAXE

VACUUM [ ( option [, ...] ) ] [ table_et_colonnes [, ...] ]
où option peut être l'une des suivantes :
    FULL [ booléen ]
    FREEZE [ booléen ]
    VERBOSE [ booléen ]
    ANALYZE [ booléen ]
    DISABLE_PAGE_SKIPPING [ booléen ]
    SKIP_LOCKED [ booléen ]
    INDEX_CLEANUP { AUTO | ON | OFF }
    PROCESS_MAIN [ booléen ]
    PROCESS_TOAST [ booléen ]
    TRUNCATE [ booléen ]
    PARALLEL entier
    SKIP_DATABASE_STATS [ booléen ]
    ONLY_DATABASE_STATS [ booléen ]
    BUFFER_USAGE_LIMIT taille
et table_et_colonnes est :
    [ ONLY ] nom_table [ * ] [ ( nom_colonne [, ...] ) ]

DESCRIPTION

VACUUM récupère l'espace occupé par les tuples morts. Dans le fonctionnement normal de PostgreSQL, les tuples supprimés ou obsolètes par une mise à jour ne sont pas physiquement retirés de leur table ; ils restent présents jusqu'à ce qu'un VACUUM soit effectué. Il est donc nécessaire d'effectuer périodiquement un VACUUM, en particulier sur les tables fréquemment mises à jour.

Sans liste de table_et_colonnes, VACUUM traite toutes les tables et vues matérialisées de la base de données actuelle que l'utilisateur actuel a la permission de vacuumiser. Avec une liste, VACUUM traite seulement cette ou ces tables.

VACUUM ANALYZE effectue un VACUUM puis un ANALYZE pour chaque table sélectionnée. C'est une combinaison pratique pour les scripts de maintenance de routine. Voir ANALYZE(7) pour plus de détails sur son traitement.

Un simple VACUUM (sans FULL) récupère simplement de l'espace et le rend disponible pour une réutilisation. Cette forme de la commande peut fonctionner en parallèle avec les lectures et écritures normales de la table, car un verrou exclusif n'est pas obtenu. Cependant, l'espace supplémentaire n'est pas retourné au système d'exploitation (dans la plupart des cas) ; il est simplement conservé pour être réutilisé au sein de la même table. Il permet également de tirer parti de plusieurs CPUs pour traiter les index. Cette fonctionnalité est connue sous le nom de vacuum parallèle. Pour désactiver cette fonctionnalité, on peut utiliser l'option PARALLEL et spécifier zéro workers parallèles. VACUUM FULL réécrit tout le contenu de la table dans un nouveau fichier disque sans espace supplémentaire, permettant de retourner l'espace inutilisé au système d'exploitation. Cette forme est beaucoup plus lente et nécessite un verrou ACCESS EXCLUSIVE sur chaque table pendant son traitement.

PARAMETRES

FULL

Sélectionne un vacuum « full », qui peut récupérer plus d'espace, mais prend beaucoup plus de temps et verrouille la table exclusivement. Cette méthode nécessite également de l'espace disque supplémentaire, car elle écrit une nouvelle copie de la table et ne libère l'ancienne copie qu'une fois l'opération terminée. Habituellement, elle ne devrait être utilisée que lorsqu'une quantité significative d'espace doit être récupérée depuis l'intérieur de la table.

FREEZE

Sélectionne un « gel » agressif des tuples. Spécifier FREEZE équivaut à effectuer un VACUUM avec les paramètres vacuum_freeze_min_age et vacuum_freeze_table_age définis à zéro. Le gel agressif est toujours effectué lors de la réécriture de la table, donc cette option est redondante lorsque FULL est spécifié.

VERBOSE

Affiche un rapport détaillé de l'activité du vacuum pour chaque table au niveau INFO.

ANALYZE

Met à jour les statistiques utilisées par le planificateur pour déterminer la manière la plus efficace d'exécuter une requête.

DISABLE_PAGE_SKIPPING

Normalement, VACUUM ignorera les pages en se basant sur la carte de visibilité. Les pages où tous les tuples sont connus pour être gelés peuvent toujours être ignorées, et celles où tous les tuples sont connus pour être visibles par toutes les transactions peuvent être ignorées sauf lors d'un vacuum agressif. De plus, sauf lors d'un vacuum agressif, certaines pages peuvent être ignorées afin d'éviter d'attendre que d'autres sessions aient fini de les utiliser. Cette option désactive tout comportement d'ignorance de page, et est destinée à être utilisée uniquement lorsque le contenu de la carte de visibilité est suspect, ce qui ne devrait arriver qu'en cas de problème matériel ou logiciel entraînant une corruption de la base de données.

SKIP_LOCKED

Spécifie que VACUUM n'attend pas la libération des verrous conflictuels lorsqu'il commence à travailler sur une relation : si une relation ne peut pas être verrouillée immédiatement sans attendre, la relation est ignorée. Notez que même avec cette option, VACUUM peut toujours bloquer lors de l'ouverture des index de la relation. De plus, VACUUM ANALYZE peut toujours bloquer lors de l'acquisition d'échantillons de lignes des partitions, des enfants d'héritage de table et de certains types de tables externes. Également, bien que VACUUM traite normalement toutes les partitions des tables partitionnées spécifiées, cette option entraînera l'ignorance de toutes les partitions par VACUUM s'il y a un verrouillage conflictuel sur la table partitionnée.

INDEX_CLEANUP

Normalement, VACUUM ignorera le vacuum d'index lorsqu'il y a très peu de tuples morts dans la table. Le coût de traitement de tous les index de la table devrait largement dépasser le bénéfice de la suppression des tuples d'index morts lorsque cela se produit. Cette option peut être utilisée pour forcer VACUUM à traiter les index lorsqu'il y a plus que zéro tuples morts. La valeur par défaut est AUTO, ce qui permet à VACUUM d'ignorer le vacuum d'index si nécessaire. Si INDEX_CLEANUP est réglé sur ON, VACUUM supprimera de manière conservatrice tous les tuples morts des index. Cela peut être utile pour la compatibilité descendante avec les versions antérieures de PostgreSQL où c'était le comportement standard.

INDEX_CLEANUP peut également être réglé sur OFF pour forcer VACUUM à ignorer toujours le vacuum d'index, même lorsqu'il y a beaucoup de tuples morts dans la table. Cela peut être utile lorsqu'il est nécessaire de faire exécuter VACUUM aussi rapidement que possible pour éviter un dépassement imminent des ID de transaction (voir la Section 24.1.5). Cependant, le mécanisme de sécurité anti-dépassement contrôlé par vacuum_failsafe_age se déclenchera généralement automatiquement pour éviter l'échec de dépassement des ID de transaction, et devrait être préféré. Si le nettoyage des index n'est pas effectué régulièrement, les performances peuvent en pâtir, car au fur et à mesure que la table est modifiée, les index accumuleront des tuples morts et la table elle-même accumulera des pointeurs de ligne morts qui ne pourront pas être supprimés tant que le nettoyage des index ne sera pas terminé.

Cette option n'a aucun effet sur les tables qui n'ont pas d'index et est ignorée si l'option FULL est utilisée. Elle n'a pas non plus d'effet sur le mécanisme de sécurité anti-dépassement des ID de transaction. Lorsqu'il est déclenché, il ignorera le vacuum d'index, même lorsque INDEX_CLEANUP est réglé sur ON.

PROCESS_MAIN

Spécifie que VACUUM doit tenter de traiter la relation principale. C'est généralement le comportement souhaité et c'est le défaut. Définir cette option à false peut être utile lorsqu'il est seulement nécessaire de vacuumiser la table TOAST correspondante d'une relation.

PROCESS_TOAST

Spécifie que VACUUM doit tenter de traiter la table TOAST correspondante pour chaque relation, si elle existe. C'est généralement le comportement souhaité et c'est le défaut. Définir cette option à false peut être utile lorsqu'il est seulement nécessaire de vacuumiser la relation principale. Cette option est requise lorsque l'option FULL est utilisée.

TRUNCATE

Spécifie que VACUUM doit tenter de tronquer toutes les pages vides à la fin de la table et de retourner l'espace disque pour les pages tronquées au système d'exploitation. C'est généralement le comportement souhaité et c'est le défaut à moins que vacuum_truncate ne soit réglé sur false ou que l'option vacuum_truncate n'ait été réglée sur false pour la table à vacuumiser. Définir cette option à false peut être utile pour éviter le verrou ACCESS EXCLUSIVE sur la table qu'exige la troncature. Cette option est ignorée si l'option FULL est utilisée.

PARALLEL

Effectue les phases de vacuum d'index et de nettoyage d'index de VACUUM en parallèle en utilisant entier workers en arrière-plan (pour les détails de chaque phase de vacuum, veuillez vous référer à la Table 27.46). Le nombre de workers utilisés pour effectuer l'opération est égal au nombre d'index sur la relation qui prennent en charge le vacuum parallèle, ce qui est limité par le nombre de workers spécifiés avec l'option PARALLEL le cas échéant, qui est à son tour limité par max_parallel_maintenance_workers. Un index peut participer au vacuum parallèle si et seulement si la taille de l'index est supérieure à min_parallel_index_scan_size. Veuillez noter qu'il n'est pas garanti que le nombre de workers parallèles spécifiés dans entier sera utilisé pendant l'exécution. Il est possible qu'un vacuum s'exécute avec moins de workers que spécifié, voire sans aucun worker. Un seul worker peut être utilisé par index. Les workers parallèles ne sont donc lancés que lorsqu'il y a au moins 2 index dans la table. Les workers pour le vacuum sont lancés avant le début de chaque phase et se terminent à la
t la fin de la phase. Ces comportements peuvent changer dans une future version. Cette option ne peut pas être utilisée avec l'option FULL.

SKIP_DATABASE_STATS

Spécifie que VACUUM doit ignorer la mise à jour des statistiques globales de la base de données concernant les XID non gelés les plus anciens. Normalement, VACUUM met à jour ces statistiques une fois à la fin de la commande. Cependant, cela peut prendre du temps dans une base de données avec un très grand nombre de tables, et cela n'aboutira à rien à moins que la table contenant le XID non gelé le plus ancien ne fasse partie de celles qui ont été vacuumées. De plus, si plusieurs commandes VACUUM sont émises en parallèle, une seule d'entre elles peut mettre à jour les statistiques globales de la base de données à la fois. Par conséquent, si une application a l'intention d'émettre une série de nombreuses commandes VACUUM, il peut être utile de définir cette option dans toutes ces commandes sauf la dernière; ou de la définir dans toutes les commandes et d'émettre séparément un VACUUM (ONLY_DATABASE_STATS) par la suite.

ONLY_DATABASE_STATS

Spécifie que VACUUM ne doit rien faire d'autre que de mettre à jour les statistiques globales de la base de données concernant les XID non gelés les plus anciens. Lorsque cette option est spécifiée, la liste table_and_columns doit être vide, et aucune autre option ne peut être activée à l'exception de VERBOSE.

BUFFER_USAGE_LIMIT

Spécifie la taille du tampon circulaire de la stratégie d'accès aux tampons pour VACUUM. Cette taille est utilisée pour calculer le nombre de tampons partagés qui seront réutilisés dans le cadre de cette stratégie. 0 désactive l'utilisation d'une stratégie d'accès aux tampons. Si ANALYZE est également spécifié, la valeur de BUFFER_USAGE_LIMIT est utilisée pour les étapes de vacuum et d'analyse. Cette option ne peut pas être utilisée avec l'option FULL sauf si ANALYZE est également spécifié. Lorsque cette option n'est pas spécifiée, VACUUM utilise la valeur de vacuum_buffer_usage_limit. Des paramètres plus élevés peuvent permettre à VACUUM de s'exécuter plus rapidement, mais un paramètre trop élevé peut entraîner l'éviction de trop d'autres pages utiles des tampons partagés. La valeur minimale est de 128 Ko et la valeur maximale est de 16 Go.

boolean

Spécifie si l'option sélectionnée doit être activée ou désactivée. Vous pouvez écrire TRUE, ON ou 1 pour activer l'option, et FALSE, OFF ou 0 pour la désactiver. La valeur boolean peut également être omise, auquel cas TRUE est supposé.

integer

Spécifie une valeur entière non négative passée à l'option sélectionnée.

size

Spécifie une quantité de mémoire en kilo-octets. Les tailles peuvent également être spécifiées sous forme de chaîne contenant la taille numérique suivie de l'une des unités de mémoire suivantes : B (octets), kB (kilo-octets), MB (méga-octets), GB (giga-octets) ou TB (téra-octets).

table_name

Le nom (éventuellement qualifié par un schéma) d'une table ou d'une vue matérialisée spécifique à vacuumer. Si ONLY est spécifié avant le nom de la table, seule cette table est vacuumée. Si ONLY n'est pas spécifié, la table et toutes ses tables filles d'héritage ou partitions (le cas échéant) sont également vacuumées. Optionnellement, * peut être spécifié après le nom de la table pour indiquer explicitement que les tables filles d'héritage (ou partitions) doivent être vacuumées.

column_name

Le nom d'une colonne spécifique à analyser. Par défaut, toutes les colonnes. Si une liste de colonnes est spécifiée, ANALYZE doit également être spécifié.

SORTIES

Lorsque VERBOSE est spécifié, VACUUM émet des messages de progression pour indiquer quelle table est en cours de traitement. Diverses statistiques sur les tables sont également imprimées.

NOTES

Pour vacuumer une table, il faut normalement avoir le privilège MAINTAIN sur la table. Cependant, les propriétaires de bases de données sont autorisés à vacuumer toutes les tables de leurs bases de données, à l'exception des catalogues partagés. VACUUM ignorera les tables pour lesquelles l'utilisateur appelant n'a pas la permission de vacuumer.

Pendant que VACUUM s'exécute, search_path est temporairement modifié en pg_catalog, pg_temp.

VACUUM ne peut pas être exécuté à l'intérieur d'un bloc de transaction.

Pour les tables avec des index GIN, VACUUM (sous quelque forme que ce soit) complète également toute insertion d'index en attente, en déplaçant les entrées d'index en attente vers les emplacements appropriés dans la structure principale de l'index GIN. Voir la section 65.4.4.1 pour plus de détails.

Nous recommandons que toutes les bases de données soient vacuumées régulièrement afin de supprimer les lignes mortes. PostgreSQL inclut une fonctionnalité "autovacuum" qui peut automatiser la maintenance de vacuum régulière. Pour plus d'informations sur le vacuum automatique et manuel, voir la section 24.1.

L'option FULL n'est pas recommandée pour une utilisation régulière, mais peut être utile dans des cas spéciaux. Un exemple est lorsque vous avez supprimé ou mis à jour la plupart des lignes d'une table et que vous souhaitez que la table rétrécisse physiquement pour occuper moins d'espace disque et permettre des scans de table plus rapides. VACUUM FULL rétrécira généralement la table plus qu'un simple VACUUM.

L'option PARALLEL est utilisée uniquement à des fins de vacuum. Si cette option est spécifiée avec l'option ANALYZE, elle n'a aucun effet sur ANALYZE.

VACUUM provoque une augmentation substantielle du trafic d'E/S, ce qui peut entraîner de mauvaises performances pour les autres sessions actives. Il est donc parfois conseillé d'utiliser la fonctionnalité de délai de vacuum basé sur le coût. Pour le vacuum parallèle, chaque travailleur dort proportionnellement au travail effectué par ce travailleur. Voir la section 19.10.2 pour plus de détails.

Chaque backend exécutant VACUUM sans l'option FULL signalera sa progression dans la vue pg_stat_progress_vacuum. Les backends exécutant VACUUM FULL signaleront leur progression dans la vue pg_stat_progress_cluster. Voir les sections 27.4.5 et 27.4.2 pour plus de détails.

EXEMPLES

Pour nettoyer une seule table onek, l'analyser pour l'optimiseur et imprimer un rapport détaillé de l'activité de vacuum :

VACUUM (VERBOSE, ANALYZE) onek;

COMPATIBILITÉ

Il n'y a pas d'instruction VACUUM dans la norme SQL.

La syntaxe suivante était utilisée avant la version 9.0 de PostgreSQL et est toujours prise en charge :

VACUUM [ FULL ] [ FREEZE ] [ VERBOSE ] [ ANALYZE ] [ table_and_columns [, ...] ]

Notez que dans cette syntaxe, les options doivent être spécifiées exactement dans l'ordre indiqué.
