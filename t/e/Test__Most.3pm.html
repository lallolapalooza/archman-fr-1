Test::Most(3) Documentation Perl fournie par les contributeurs Test::Most(3)

NOM

Test::Most - La plupart des fonctions et fonctionnalités de test couramment nécessaires.

VERSION

Version 0.38

SYNOPSIS

Au lieu de ceci :

use strict;
use warnings;
use Test::Exception 0.88;
use Test::Differences 0.500;
use Test::Deep 0.106;
use Test::Warn 0.11;
use Test::More tests => 42;

Vous tapez ceci :

use Test::Most tests => 42;

DESCRIPTION

Test::Most existe pour réduire le code répétitif et pour vous faciliter la vie en matière de tests. Nous fournissons un "guichet unique" pour la plupart des modules de test couramment utilisés. En fait, nous exigeons souvent les dernières versions afin que vous bénéficiiez des corrections de bugs via Test::Most et que vous n'ayez pas à mettre à jour ces modules séparément.

Ce module vous fournit les fonctions de test les plus couramment utilisées, tout en activant automatiquement strict et warning et en vous donnant un contrôle plus granulaire sur votre suite de tests.

use Test::Most tests => 4, 'die';
ok 1, 'Les appels normaux à ok() devraient réussir';
is 2, 2, '... tout comme tous les tests qui réussissent';
eq_or_diff [3], [4], '... mais les tests qui échouent devraient mourir';
ok 4, '... n'arrivera jamais ici';

Comme vous pouvez le constater, le test "eq_or_diff" échouera. Parce que 'die' est dans la liste d'importation, le programme de test s'arrêtera à ce point.

Si vous ne souhaitez pas activer strict et warnings, vous devez explicitement les désactiver. Ainsi, vous devez être explicite quant à ce que vous voulez et ne plus avoir à vous soucier de les oublier accidentellement.

use Test::Most tests => 4;
no strict;
no warnings;

EXPORT

Toutes les fonctions des modules suivants seront automatiquement exportées dans votre espace de noms :

  • Test::More
  • Test::Exception
  • Test::Differences
  • Test::Deep
  • Test::Warn

Les fonctions qui sont exportées *facultativement* depuis l'un de ces modules doivent être référencées par leur nom complètement qualifié :

Test::Deep::render_stack( $var, $stack );

FONCTIONS

Plusieurs autres fonctions sont également exportées automatiquement :

"die_on_fail"

die_on_fail;
is_deeply $foo, bar, '... nous lançons une exception si cela échoue';

Cette fonction, si appelée, fera en sorte que le programme de test lance une Test::Most::Exception, arrêtant effectivement le test.

"bail_on_fail"

bail_on_fail;
is_deeply $foo, bar, '... nous abandonnons si cela échoue';

Cette fonction, si appelée, entraînera l'abandon (BAIL_OUT()) de la suite de tests si des tests échouent après elle.

"restore_fail"

die_on_fail;
is_deeply $foo, bar, '... nous lançons une exception si cela échoue';
restore_fail;
cmp_bag(\@got, \@bag, '... nous ne lancerons pas d'exception si cela échoue';

Ceci restaure le comportement d'échec de test d'origine, de sorte que les tests ultérieurs ne lanceront plus d'exception ou n'abandonneront plus (BAIL_OUT()).

"set_failure_handler"

Si vous préférez un comportement différent de 'die_on_fail' ou 'bail_on_fail', vous pouvez définir votre propre gestionnaire d'échec :

set_failure_handler( sub {
    my $builder = shift;
    if ( $builder && $builder->{Test_Results}[-1] =~ /critical/ ) {
       send_admin_email("échec critique dans les tests");
    }
} );

Il reçoit l'instance "Test::Builder" comme seul argument.

Important : Notez que si le test qui échoue est le tout dernier test exécuté, $builder sera probablement indéfini. C'est un effet secondaire malheureux de la façon dont "Test::Builder" a été conçu.

"explain"

Similaire à note(), la sortie ne sera vue par l'utilisateur qu'en utilisant le commutateur "-v" avec "prove" ou en lisant le TAP brut.

Contrairement à note(), toute référence dans la liste des arguments est automatiquement développée à l'aide de "Data::Dumper". Ainsi, au lieu de ceci :

my $self = Some::Object->new($id);
use Data::Dumper;
explain 'Je viens d'être créé', Dumper($self);

Vous pouvez maintenant simplement faire ceci :

my $self = Some::Object->new($id);
explain 'Je viens d'être créé :  ', $self;

Cette sortie ressemblera à ceci :

Je viens d'être créé : bless( {
  'id' => 2,
  'stack' => []
}, 'Some::Object' )

Notez que la sortie "dumpered" a les variables "Data::Dumper" $Indent, "Sortkeys" et "Terse" toutes définies à la valeur 1 (un). Cela permet une sortie diagnostique beaucoup plus propre et ne peut actuellement pas être remplacé.

Notez que "explain" de Test::More agit différemment. Cet "explain" est équivalent à "note explain" dans Test::More.

"show"

Expérimental. Tout comme "explain", mais essaie également de vous montrer les noms des variables lexicales :

my $var   = 3;
my @array = qw/ foo bar /;
show $var, \@array;
__END__
$var = 3;
@array = [
    'foo',
    'bar'
];

Il affichera $VAR1, $VAR2 ... $VAR_N pour chaque variable dont il ne parvient pas à trouver le nom :

my @array = qw/ foo bar /;
show @array;
__END__
$VAR1 = 'foo';
$VAR2 = 'bar';

Notez que cela repose sur Data::Dumper::Names version 0.03 ou supérieure. Si ce n'est pas le cas, il affichera un avertissement et appellera explain à la place. De plus, il ne peut afficher les noms que pour les variables lexicales. Les variables globales telles que %ENV ou "%@" ne sont pas accessibles via PadWalker et ne peuvent donc pas être affichées. Il serait bon de trouver une solution de contournement pour cela.

"always_explain" et "always_show"

Ces fonctions sont identiques à "explain" et "show", mais comme la fonction "diag" de Test::More, elles émettront toujours une sortie, que vous soyez en mode verbeux ou non.

"all_done"

OBSOLÈTE. Utilisez la nouvelle fonction done_testing() (ajoutée dans Test::More depuis 0.87_01). à la place. Nous la laissons ici pour un long cycle de dépréciation. Après un certain temps, nous pourrions même commencer à avertir.

Si le plan est spécifié comme "defer_plan", vous pouvez appeler &all_done à la fin du test avec un nombre de tests optionnel. Cela vous permet de définir le plan sans connaître le plan avant d'exécuter les tests.

Si vous l'appelez sans nombre de tests, les tests échoueront toujours si vous n'atteignez pas la fin du test. Ceci est utile si vous ne souhaitez pas spécifier de plan mais que les tests se terminent de manière inattendue. Par exemple, ce qui suit *réussirait* avec "no_plan" mais échouerait avec "all_done".

use Test::More 'defer_plan';
ok 1;
exit;
ok 2;
all_done;

Voir "Plans différés" pour plus d'informations.

"timeit"

La fonctionnalité suivante ne sera exportée que sur demande :

"timeit"

Prototype : timeit(&;$)

Cette fonction émettra un avertissement si "Time::HiRes" n'est pas installé. Le test sera quand même exécuté, mais aucune information de temps ne sera affichée.

use Test::Most 'timeit';
timeit { is expensive_function(), $some_value, $message }
   "expensive_function()";
timeit { is expensive_function(), $some_value, $message };

"timeit" accepte une référence de code et un message optionnel. Après l'exécution du test, "explain" affichera le temps d'exécution de la fonction à l'aide de "Time::HiRes". Si un message est fourni, il sera formaté comme suit :

sprintf "$message: took %s seconds" => $time;

Sinon, il sera formaté comme suit :

sprintf "$filename line $line: took %s seconds" => $time;

DIE OU BAIL ON FAIL

Parfois, vous souhaitez que votre suite de tests lance une exception ou appelle BAIL_OUT() si un test échoue. Pour offrir une flexibilité maximale, il existe trois façons d'atteindre chacun de ces objectifs.

Liste d'importation

use Test::Most 'die', tests => 7;
use Test::Most qw< no_plan bail >;

Si "die" ou "bail" apparaît dans la liste d'importation, le programme de test/la suite lèvera une "Test::Most::Exception" ou appellera BAIL_OUT() respectivement lors de la première exécution d'un test échoué. L'appel de "restore_fail" dans le programme de test rétablira le comportement d'origine (ne pas lever d'exception ni appeler BAIL_OUT).

Fonctions

use Test::Most 'no_plan';
ok $bar, 'La suite de tests continuera si cela réussit';
die_on_fail;
is_deeply $foo, bar, '... nous lançons une exception si cela échoue';
restore_fail;
ok $baz, 'La suite de tests continuera si cela réussit';

Les fonctions "die_on_fail" et "bail_on_fail" définiront automatiquement le comportement souhaité en temps réel.

Variables d'environnement

DIE_ON_FAIL=1 prove t/
BAIL_ON_FAIL=1 prove t/

Si les variables d'environnement "DIE_ON_FAIL" ou "BAIL_ON_FAIL" sont vraies, tout test utilisant "Test::Most" lèvera une exception ou appellera BAIL_OUT en cas d'échec.

DIVERS

Moose

Ce module émettait autrefois un avertissement lors de l'utilisation de Moose :

Prototype mismatch: sub main::blessed ($) vs none

C'était parce que Test::Deep exportait une fonction blessed() par défaut, mais son prototype ne correspondait pas au prototype de Moose. La version de Test::Deep est maintenant exclue par défaut. Si vous souhaitez l'utiliser, vous pouvez appeler la version entièrement qualifiée ou la demander dans la ligne de commande :

use Test::Most 'blessed';

Remarque : Dans le cadre de la version 0.34, "reftype" est également exclu de la liste d'importation de "Test::Deep". Cela causait des problèmes aux utilisateurs tentant d'utiliser la fonction "reftype" de "Scalar::Util".

Exclusion de modules de test

Parfois, vous souhaitez exclure un module de test spécifique. Par exemple, lors de l'utilisation de Test::Deep avec Moose, il génère l'avertissement suivant :

Prototype mismatch: sub main::blessed ($) vs none

Vous pouvez l'exclure en ajoutant le module à la liste d'importation avec un signe moins :

use Test::Most tests => 42, '-Test::Deep';

Voir https://rt.cpan.org/Ticket/Display.html?id=54362 pour plus d'informations.

Exclusion de symboles de test

Parfois, vous ne souhaitez pas exclure un module de test complet, mais seulement un symbole qui pose problème. Vous pouvez exclure des symboles en spécifiant le symbole dans la liste d'importation avec un point d'exclamation :

use Test::Most tests => 42, '!throws_ok';

Plans différés

OBSOLÈTE et sera supprimé dans une future version de ce module. L'utilisation de "defer_plan" lèvera "carp(). Utilisez plutôt "done_testing() de Test::More.

use Test::Most qw<defer_plan>;
use My::Tests;
my $test_count = My::Tests->run;
all_done($test_count);

Parfois, il est difficile de connaître le plan au début, mais vous pouvez calculer le plan pendant que les tests s'exécutent. Par conséquent, vous souhaitez reporter le plan jusqu'à la fin des tests. En général, la meilleure chose que vous puissiez faire est :

use Test::More 'no_plan';
use My::Tests;
My::Tests->run;

Cependant, en faisant cela, "Test::Builder" affirme seulement que le nombre de tests que vous avez exécutés est le même que celui que vous attendiez. Jusqu'à présent, il n'y avait aucun moyen d'affirmer que le nombre de tests que vous attendiez est le même que celui que vous avez exécuté, à moins de le faire avant l'exécution des tests. Cela corrige ce problème.

Guichet unique

Généralement, nous exigeons les versions les plus stables de divers modules de test. Pourquoi ? Parce qu'ils ont des corrections de bugs et de nouvelles fonctionnalités. Vous ne voulez pas avoir à vous souvenir pourquoi vous les maintenez, alors nous publierons périodiquement de nouvelles versions de Test::Most juste pour les corrections de bugs.

"use ok"

Bien que le module Test::use::ok ait été demandé, nous ne l'incluons pas. C'est parce que "use_ok" est mal conçu, mais "Test::use::ok" est également mal conçu (et plus difficile à corriger). Voir http://use.perl.org/~Ovid/journal/39859 pour plus d'informations.

Si vous voulez tester si vous pouvez utiliser un module, utilisez-le. S'il échoue, le test échouera et c'est le résultat souhaité.

RATIONALE

Les gens veulent plus de contrôle sur leurs suites de tests. Parfois, lorsque vous voyez des centaines de tests échouer et réussir rapidement, vous voulez que la suite de tests s'arrête au premier échec. Ce module vous donne ce contrôle.

use Test::More 'no_plan';

"Pp">Parfois, vous ne connaissez pas le nombre de tests que vous allez exécuter lorsque vous utilisez "Test::More". La fonction plan() vous permet de retarder la spécification du plan, mais vous devez toujours l'appeler avant l'exécution des tests. Ceci est une erreur :

use Test::More;
my $tests = 0;
foreach my $test (
    my $count = run($test); # suppose que les tests sont en cours d'exécution
    $tests += $count;
}
plan($tests);

La solution consiste généralement à utiliser 'no_plan' et, une fois les tests terminés, "Test::Builder" définit simplement le plan au nombre de tests exécutés. Nous aimerions que le programmeur spécifie ce nombre au lieu de laisser "Test::Builder" le faire. Cependant, les internes de "Test::Builder" sont un peu difficiles à manipuler, nous retardons donc cette fonctionnalité.

Plus propre skip()

if ( $some_condition ) {
    skip $message, $num_tests;
}
else {
    # exécuter ces tests
}

Ce serait plus propre et je pourrais l'ajouter si suffisamment de personnes le souhaitent.

MISE EN GARDE

En raison de la façon dont Perl gère les arguments, et parce que les diagnostics ne font pas vraiment partie du Test Anything Protocol, ce qui se passe réellement en interne, c'est que nous notons qu'un test a échoué et nous levons une exception ou abandonnons dès que le prochain test est appelé (mais avant qu'il ne soit exécuté). Cela signifie que ses arguments sont automatiquement évalués avant que nous puissions agir :

use Test::Most qw<no_plan die>;
ok $foo, 'Mourir si cela échoue';
ok factorial(123456),
  '... mais attendez longtemps avant de lancer une exception';
