NOM

Test::Spec - Écrire des tests dans un style de spécification déclarative

SYNOPIS

use Test::Spec; # active automatiquement strict et warnings
describe "Un jour" => sub {
  my $jour;
  describe "dans une année bissextile" => sub {
    before each => sub {
      $jour = DateTime->new(year => 2000, month => 2, day => 28);
    };
    it "doit savoir que c'est une année bissextile" => sub {
      ok($jour->is_leap_year);
    };
    it "doit reconnaître le 29 fév." => sub {
      is($jour->add(days => 1)->day, 29);
    };
  };
  describe "pas dans une année bissextile" => sub {
    before each => sub {
      $jour = DateTime->new(year => 2001, month => 2, day => 28);
    };
    it "doit savoir que ce n'est pas une année bissextile" => sub {
      ok(!$jour->is_leap_year);
    };
    it "ne doit pas reconnaître le 29 fév." => sub {
      is($jour->add(days => 1)->day, 1);
    };
  };
};
runtests unless caller;
# Génère la sortie suivante :
# ok 1 - Un jour dans une année bissextile doit savoir que c'est une année bissextile
# ok 2 - Un jour dans une année bissextile doit reconnaître le 29 fév.
# ok 3 - Un jour pas dans une année bissextile doit savoir que ce n'est pas une année bissextile
# ok 4 - Un jour pas dans une année bissextile ne doit pas reconnaître le 29 fév.
# 1..4

DESCRIPTION

Ceci est un framework de test comportemental (BDD) pour le développement logiciel basé sur le comportement (BDD) en Perl. Les tests (également appelés exemples) sont nommés avec des chaînes de caractères au lieu de noms de sous-routines, ce qui réduit la fatigue du trait d'union pour vos doigts, avec le bénéfice secondaire que les rapports de test sont plus lisibles.

Ce module est inspiré de et emprunte à RSpec http://rspec.info/documentation, un outil BDD pour le langage de programmation Ruby.

EXPORTATIONS

Lorsqu'il est utilisé sans liste (c'est-à-dire "use Test::Spec;"), cette classe exportera :

  • Fonctions de définition de spécifications

    Ce sont les fonctions que vous utiliserez pour définir les comportements et exécuter vos tests : "describe", "it", "they", "before", "after", "runtests", "share", "shared_examples_for", "it_should_behave_like", et "spec_helper".

  • Les fonctions de mocks de Test::Spec::Mocks.
  • Tout ce que Test::More exporte normalement

    Cela inclut "ok", "is" et leurs semblables. Vous les utiliserez pour affirmer le bon comportement.

  • Tout ce que Test::Deep exporte normalement

    Les assertions plus complexes incluent "cmp_deeply".

  • Tout ce que "Test::Trap" exporte normalement

    La fonction "trap() permet de tester des comportements qui appellent "exit() et d'autres choses du genre. "Une évaluation de bloc dans ces contextes."

Si vous spécifiez une liste d'importation, seules les fonctions directement de "Test::Spec" (celles documentées ci-dessous) seront disponibles.

FONCTIONS

runtests
runtests(@patterns)
Exécute tous les exemples dont les descriptions correspondent à l'un des motifs d'expression régulière non sensibles à la casse dans @patterns. Si @patterns n'est pas défini, exécute tous les exemples. La variable d'environnement "SPEC" sera utilisée comme motif par défaut si elle est présente.

Si appelée comme une fonction (c'est-à-dire non comme un appel de méthode avec "->"), "runtests" détectera le package depuis lequel elle est appelée et exécutera les tests de ce package. Un idiome utile est :

runtests unless caller;

ce qui exécutera les exemples lorsque le fichier sera chargé comme un script (par exemple, en l'exécutant depuis la ligne de commande), mais pas lorsqu'il sera chargé comme un module (avec "require" ou "use").

describe DESCRIPTION => CODE
describe CODE
Définit un contexte de spécification dans lequel des exemples et d'autres descriptions peuvent être définis. Tous les exemples doivent se trouver dans un bloc "describe".
"describe" les blocs peuvent être imbriqués pour rendre vos tests plus lisibles.
Pour de grandes spécifications, les blocs "describe" peuvent vous éviter beaucoup de répétitions : 
describe "Un objet utilisateur" => sub {
  my $utilisateur;
  before sub {
    $utilisateur = User->new;
  };
  describe "venant d'un formulaire" => sub {
    before sub {
      $utilisateur->init_from_tree({ username => "bbill", ... });
    };
    it "doit lire ses attributs depuis le formulaire";
    describe "lors de la sauvegarde" => sub {
      it "doit exiger un nom d'utilisateur unique";
      it "doit exiger un mot de passe";
    };
  };
};

Le travail d'initialisation effectué dans chaque bloc "before" est passé d'un niveau à l'autre, vous n'aurez donc pas à appeler une fonction d'initialisation manuellement dans chaque test. Cela se fait automatiquement en fonction du contexte.

L'utilisation de blocs describe améliore la lisibilité sans exiger plus de technique.
Le nom du contexte sera inclus par défaut dans le rapport de succès/échec généré par les méthodes de test basées sur Test::Builder (par exemple, la fonction ok() de Test::More). Pour un exemple similaire : 
describe "Une hirondelle non chargée" => sub {
  it "a une vitesse de 11 mètres par seconde" => sub {
    is($hirondelle->airspeed, "11m/s");
  };
};

La sortie générée est :

ok 1 - Une hirondelle non chargée a une vitesse de 11 mètres par seconde

Comparez cela au cas de test suivant pour générer la même sortie :

sub unladen_swallow_airspeed : Test {
  is($swallow->airspeed, "11m/s",
     "Une hirondelle non chargée a une vitesse de 11 mètres par seconde");
}

"describe" les blocs sont exécutés dans l'ordre où ils sont définis. Les blocs "describe" portant le même nom sont autorisés. Ils ne se remplacent pas mutuellement, mais les blocs ultérieurs étendent le bloc existant du même nom.

context
Un alias pour describe().
xdescribe
Les blocs de spécification peuvent être désactivés en appelant "xdescribe" au lieu de describe(). Tous les exemples à l'intérieur d'un "xdescribe" sont signalés comme "# TODO (désactivé)", ce qui empêche Test::Harness/prove de les compter comme des échecs.
xcontext
Un alias pour xdescribe().
it SPÉCIFICATION => CODE
it CODE
it SPÉCIFICATION_TODO
Définit un exemple à tester. Bien que son nom soit un peu étrange, "it" permet une manière naturelle (à mon avis) de décrire le comportement attendu : 
describe "Un zoo captif de Buffalo Bill" => sub {
  it "met la pommade sur la peau" => sub {
    ...
  };
  it "met la pommade dans le récipient"; # TODO
};

Si aucun code de bloc n'est transmis, la spécification est présumée non implémentée et sera signalée comme &quo

t;TODO (non implémenté)" dans les résultats de test (voir "todo_skip" dans Test::Builder. Les tests TODO sont signalés comme ignorés, pas comme échoués.

they SPÉCIFICATION => CODE
they CODE
they TODO_SPÉCIFICATION
Un alias pour "it". Ceci est utile pour décrire le comportement d'un groupe d'éléments, de sorte que le verbe s'accorde avec le nom : 
describe "Captives of Buffalo Bill" => sub {
  they "put the lotion on their skin" => sub {
    ...
  };
  they "put the lotion in the basket"; # TODO
};
xit/xthey
Les exemples peuvent être désactivés en appelant xit()/xthey() au lieu de it()/they(). Ces exemples sont rapportés comme "# TODO (désactivé)", ce qui empêche Test::Harness/prove de les compter comme des échecs.
before each => CODE
before all => CODE
before CODE
Définit le code à exécuter avant l'exécution des tests dans le bloc describe actuel. Si "each" est spécifié, CODE sera réexécuté pour chaque test dans le contexte. Si "all" est spécifié, CODE ne sera exécuté qu'avant le premier test.

La valeur par défaut est "each", en raison de la logique présentée dans la documentation de RSpec :

"Il est très tentant d'utiliser before(:all) et after(:all) pour des situations où ce n'est pas approprié. before(:all) partage certains (mais pas tous) états entre plusieurs exemples. Cela signifie que les exemples deviennent liés ensemble, ce qui est un non absolu dans les tests. Vous ne devriez vraiment que jamais utiliser before(:all) pour mettre en place des choses qui sont des collaborateurs globaux, mais pas les choses que vous décrivez dans les exemples.

Les cas d'abus les plus courants sont l'accès à la base de données et/ou la configuration de fixtures. Chaque exemple qui accède à la base de données devrait commencer avec une ardoise vierge, sinon les exemples deviennent fragiles et perdent leur valeur avec de faux négatifs et, pire encore, de faux positifs."

(http://rspec.info/documentation/before_and_after.html)

Il n'y a aucune restriction sur le fait d'avoir plusieurs blocs before. Ils s'exécuteront séquentiellement dans leurs groupes respectifs "each" ou "all". Les blocs "before "all"" s'exécutent avant les blocs "before "each"".

after each => CODE
after all => CODE
after CODE
Comme "before", mais à l'envers. Exécute CODE après chaque test ou tous les tests, respectivement. La valeur par défaut est "each".

Les blocs "after "all"" s'exécutent *après* les blocs "after "each"".

around CODE
Définit le code à exécuter autour de l'exécution des tests dans le bloc describe actuel. Ce code doit appeler "yield".. 
our $var = 0;
describe "Something" => sub {
  around {
    local $var = 1;
    yield;
  };
  it "should have localized var" => sub {
    is $var, 1;
  };
};

Ce CODE s'exécutera autour de chaque exemple.

yield
Exécute les exemples dans le contexte du bloc "around".
shared_examples_for DESCRIPTION => CODE
Définit un groupe d'exemples qui peuvent être inclus ultérieurement dans les blocs "describe" ou d'autres blocs "shared_examples_for". Voir "Groupes d'exemples partagés".

Les noms de groupes d'exemples sont globaux, mais les groupes d'exemples peuvent être définis à n'importe quel niveau (c'est-à-dire qu'ils peuvent être définis dans le contexte global, ou à l'intérieur d'un bloc "describe").

my $browser;
shared_examples_for "all browsers" => sub {
  it "should open a URL" => sub { ok($browser->open("http://www.google.com/")) };
  ...
};
describe "Firefox" => sub {
  before all => sub { $browser = Firefox->new };
  it_should_behave_like "all browsers";
  it "should have firefox features";
};
describe "Safari" => sub {
  before all => sub { $browser = Safari->new };
  it_should_behave_like "all browsers";
  it "should have safari features";
};
it_should_behave_like DESCRIPTION
Affirme que l'élément actuellement testé réussit tous les tests du groupe d'exemples identifié par DESCRIPTION (ayant été précédemment défini avec un bloc "shared_examples_for"). En substance, cela équivaut à copier tous les tests du bloc "shared_examples_for" nommé dans le contexte actuel. Voir "Groupes d'exemples partagés" et shared_examples_for.
share %HASH
Enregistre %HASH pour partager des données entre les tests et les groupes d'exemples. Cela vous permet de partager des variables avec du code dans différentes portées lexicales sans avoir recours à l'utilisation de variables de paquet (c'est-à-dire globales) ou à d'autres astuces pour contourner les problèmes de portée.

Chaque hash qui est "share"d fait référence aux mêmes données. Le partage d'un hash rendra son contenu existant inaccessible, car il contiendra ensuite les mêmes données que tous les autres hashes partagés. Le résultat est que vous obtenez un hash avec une sémantique globale mais avec une portée lexicale (en supposant que %HASH est une variable lexicale).

Il y a plusieurs avantages à utiliser "share" par rapport à un hash global "régulier". Premièrement, vous n'avez pas à décider de quel paquet le hash appartiendra, ce qui est gênant lorsque vous avez des spécifications dans plusieurs paquets faisant référence aux mêmes exemples partagés. Vous n'avez pas non plus à encombrer vos exemples avec des deux-points pour les noms entièrement qualifiés. Par exemple, dans mon entreprise, nos spécifications vont dans la hiérarchie "ICA::TestCase", et "$ICA::TestCase::Some::Package::variable" est épuisant à la fois pour les yeux et pour les mains. Enfin, l'utilisation de "share" permet à "Test::Spec" de fournir cette fonctionnalité sans décider du nom de la variable pour vous (et donc potentiellement d'écraser l'une de vos variables).

share %vars;      # %vars fait maintenant référence au partage global
share my %vars;   # déclare et partage %vars en une seule étape
spec_helper FILESPEC
Charge le code source Perl dans "FILESPEC" dans le paquet de la spécification actuelle. Si "FILESPEC" est relatif (pas de barre oblique initiale), il est traité comme relatif au fichier de spécification (c'est-à-dire pas au script en cours d'exécution). Cela vous permet de garder les scripts d'aide près des spécifications dont ils ont besoin sans avoir à exercer vos compétences File::Spec dans vos spécifications. 
# dans foo/spec.t
spec_helper "helper.pl";          # charge foo/helper.pl
spec_helper "helpers/helper.pl";  # charge foo/helpers/helper.pl
spec_helper "/path/to/helper.pl"; # charge /path/to/helper.pl

Groupes d'exemples partagés

Cette fonctionnalité vient directement de RSpec, tout comme cette documentation :

Vous pouvez créer des groupes d'exemples partagés et inclure ces groupes dans d'autres groupes.

Supposons que vous ayez un comportement qui s'applique à toutes les éditions de votre produit, petites et grandes.

D'abord, extrayez le comportement "partagé" :

shared_examples_for "all editions" => sub {
  it "should behave like all editions" => sub {
    ...
  };
};

Ensuite, lorsque vous devez définir le comportement pour les éditions Large et Small, référencez le comportement partagé à l'aide de la fonction it_should_behave_like().

describe "SmallEdition" => sub {
  it_should_behave_like "all editions";
};
describe "LargeEdition" => sub {
  it_should_behave_like "all editions";
  it "should also behave like a large edition" => sub {
    ...
  };
};

"it_should_behave_like" recherchera un groupe d'exemples par sa chaîne de description, dans ce cas, "all editions".

Les groupes d'exemples partagés peuvent être inclus dans d'autres groupes partagés :

shared_examples_for "All Employees" => sub {
  it "should be payable" => sub {
    ...
  };
};
shared_examples_for "All Managers" => sub {
  it_should_behave_like "All Employees";
  it "should be bonusable" => sub {
    ...
  };
};
describe Officer => sub {
  it_should_behave_like "All Managers";
  it "should be optionable";
};
# génère :
ok 1 - Officer should be optionable
ok 2 - Officer should be bonusable
ok 3 - Officer should be payable

Refactorisation en fichiers

Si vous souhaitez factoriser des spécifications dans des fichiers séparés, les portées des variables peuvent être délicates. C'est particulièrement vrai si vous suivez le modèle recommandé et donnez à chaque spécification son propre nom de paquet. "Test::Spec" offre quelques fonctions qui facilitent considérablement ce processus : share et spec_helper.

Considérez l'exemple des navigateurs de "shared_examples_for". Une véritable spécification de navigateur serait longue, donc mettre les spécifications pour tous les navigateurs dans le même fichier serait une mauvaise idée. Créons donc "all_browsers.pl" pour les exemples partagés, et donnons à Safari et Firefox "safari.t" et "firefox.t", respectivement.

Test::Spec(3pm)

NAME

Test::Spec - RSpec-like testing framework for Perl

SYNOPSIS

    # foo.t
    use Test::Spec;
    describe "Foo" => sub {
      it "should do this" => sub {
        # test code
      };
      it "should do that" => sub {
        # test code
      };
    };
    # bar.t
    use Test::Spec;
    describe "Bar" => sub {
      it "should do something else" => sub {
        # test code
      };
    };

DESCRIPTION

Test::Spec is a testing framework that provides an RSpec-like syntax for writing tests in Perl. It aims to make tests more readable and maintainable by providing a clear structure for describing test cases and their expected behavior.

The core components of Test::Spec are:

  • describe: Used to group related tests under a common description.

  • it / it_should_behave_like: Used to define individual test cases or to include shared example groups.

  • before / after: Used to define setup and teardown code that runs before or after tests.

  • share: Used to declare variables that can be shared within a test suite.

  • spec_helper: Used to load shared helper files.

The following example demonstrates how to share test logic between different browser test files using "share" and "spec_helper".

# safari.t
package Testcase::Safari;
use Test::Spec;
spec_helper 'all_browsers.pl';
describe "Safari" => sub {
  share my %vars;
  before all => sub { $vars{browser} = Safari->new };
  it_should_behave_like "all browsers";
  it "should have safari features";
};
# firefox.t
package Testcase::Firefox;
use Test::Spec;
spec_helper 'all_browsers.pl';
describe "Firefox" => sub {
  share my %vars;
  before all => sub { $vars{browser} = Firefox->new };
  it_should_behave_like "all browsers";
  it "should have firefox features";
};
# in all_browsers.pl
shared_examples_for "all browsers" => sub {
  # doesn't have to be the same name!
  share my %t;
  it "should open a URL" => sub {
    ok $t{browser}->open("http://www.google.com/");
  };
  ...
};

Order of execution

This example, shamelessly adapted from the RSpec website, gives an overview of the order in which examples run, with particular attention to "before" and "after".

describe Thing => sub {
  before all => sub {
    # This is run once and only once, before all of the examples
    # and before any before("each") blocks.
  };
  before each => sub {
    # This is run before each example.
  };
  before sub {
    # "each" is the default, so this is the same as before("each")
  };
  it "should do stuff" => sub {
    ...
  };
  it "should do more stuff" => sub {
    ...
  };
  after each => sub {
    # this is run after each example
  };
  after sub {
    # "each" is the default, so this is the same as after("each")
  };
  after all => sub {
    # this is run once and only once after all of the examples
    # and after any after("each") blocks
  };
};
