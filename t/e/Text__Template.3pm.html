Text::Template(3) Documentation Perl fournie par l'utilisateur Text::Template(3)

NOM

Text::Template - Développe du texte de modèle avec du Perl embarqué

VERSION

version 1.61

SYNTAXE

use Text::Template;
$template = Text::Template->new(TYPE => 'FILE',  SOURCE => 'filename.tmpl');
$template = Text::Template->new(TYPE => 'ARRAY', SOURCE => [ ... ] );
$template = Text::Template->new(TYPE => 'FILEHANDLE', SOURCE => $fh );
$template = Text::Template->new(TYPE => 'STRING', SOURCE => '...' );
$template = Text::Template->new(PREPEND => q{use strict;}, ...);
# Utilise une syntaxe de fichier de modèle différente :
$template = Text::Template->new(DELIMITERS => [$open, $close], ...);
$recipient = 'Roi';
$text = $template->fill_in();  # Remplace `{$recipient}' par `Roi'
print $text;
$T::recipient = 'Josh';
$text = $template->fill_in(PACKAGE => T);
# Passe de nombreuses variables explicitement
$hash = { recipient => 'Abed-Nego',
          friends => [ 'moi', 'toi' ],
          enemies => { loathsome => 'Saruman',
                       fearsome => 'Sauron' },
        };
$text = $template->fill_in(HASH => $hash, ...);
# $recipient est Abed-Nego,
# @friends est ( 'moi', 'toi' ),
# %enemies est ( loathsome => ..., fearsome => ... )
# Appelle &callback en cas d'erreurs de programmation dans le modèle
$text = $template->fill_in(BROKEN => \&callback, BROKEN_ARG => $ref, ...);
# Évalue des fragments de programme dans un compartiment Safe avec des permissions restreintes
$text = $template->fill_in(SAFE => $compartment, ...);
# Imprime le texte résultant au lieu de le retourner
$success = $template->fill_in(OUTPUT => \*FILEHANDLE, ...);
# Analyse le modèle avec une syntaxe de fichier de modèle différente :
$text = $template->fill_in(DELIMITERS => [$open, $close], ...);
# Notez que cela est *plus rapide* que d'utiliser les délimiteurs par défaut
# Ajoute du code perl spécifié au début de chaque fragment avant l'évaluation :
$text = $template->fill_in(PREPEND => q{use strict 'vars';}, ...);
use Text::Template 'fill_in_string';
$text = fill_in_string( <<'EOM', PACKAGE => 'T', ...);
Cher {$recipient},
Payez-moi immédiatement.
       Amour, 
        G.V.
EOM
use Text::Template 'fill_in_file';
$text = fill_in_file($filename, ...);
# Tous les modèles auront toujours `use strict vars' attaché à tous les fragments
Text::Template->always_prepend(q{use strict 'vars';});

DESCRIPTION

Ceci est une bibliothèque pour générer des lettres types, construire des pages HTML ou remplir des modèles en général. Un « modèle » est un morceau de texte qui contient de petits programmes Perl intégrés ici et là. Lorsque vous « remplissez » un modèle, vous évaluez les petits programmes et les remplacez par leurs valeurs.

Vous pouvez stocker un modèle dans un fichier en dehors de votre programme. Les gens peuvent modifier le modèle sans modifier le programme. Vous pouvez séparer les détails de formatage du code principal et placer les parties de formatage du programme dans le modèle. Cela évite l'encombrement du code et encourage la séparation fonctionnelle.

Exemple

Voici un exemple de modèle, que nous supposerons stocké dans le fichier "formletter.tmpl" :

Cher {$title} {$lastname},
Nous avons été informés que vous êtes en retard pour votre
paiement de {$monthname[$last_paid_month]}. Veuillez envoyer
${sprintf("%.2f", $amount)} immédiatement, ou vos rotules pourraient
être inutilement mises en danger.
                Amour,
                Mark "Vizopteryx" Dominus

Le résultat du remplissage de ce modèle est une chaîne de caractères, qui pourrait ressembler à ceci :

Cher M. Smith,
Nous avons été informés que vous êtes en retard pour votre
paiement de Février. Veuillez envoyer
392.12 $ immédiatement, ou vos rotules pourraient
être inutilement mises en danger.
                Amour,
                Mark "Vizopteryx" Dominus

Voici un programme complet qui transforme le modèle d'exemple en le résultat d'exemple et l'affiche :

use Text::Template;
my $template = Text::Template->new(SOURCE => 'formletter.tmpl')
  or die "Impossible de construire le modèle : $Text::Template::ERROR";
my @monthname = qw(Janvier Février Mars Avril Mai Juin
                   Juillet Août Septembre Octobre Novembre Décembre);
my %vars = (title           => 'M.',
            firstname       => 'John',
            lastname        => 'Smith',
            last_paid_month => 1,   # Février
            amount          => 392.12,
            monthname       => \@monthname);
my $result = $template->fill_in(HASH => \%vars);
if (defined $result) { print $result }
else { die "Impossible de remplir le modèle : $Text::Template::ERROR" }

Philosophie

Lorsque les gens créent un module de modèle comme celui-ci, ils commencent presque toujours par inventer une syntaxe spéciale pour les substitutions. Par exemple, ils le construisent de sorte qu'une chaîne comme "%%VAR%%" soit remplacée par la valeur de $VAR. Ensuite, ils réalisent le besoin de formatage supplémentaire, ils ajoutent donc une syntaxe spéciale pour le formatage. Puis ils ont besoin d'une boucle, ils inventent donc une syntaxe de boucle. Assez rapidement, ils ont un nouveau petit langage de modèle.

Cette approche présente deux problèmes : Premièrement, leur petit langage est limité. Si vous avez besoin de faire quelque chose à quoi l'auteur n'a pas pensé, vous perdez. Deuxièmement : Qui veut apprendre un autre langage ? Vous connaissez déjà Perl, alors pourquoi ne pas l'utiliser ?

"Text::Template" les modèles sont programmés en Perl. Vous intégrez du code Perl dans votre modèle, avec "{" au début et "}" à la fin. Si vous voulez qu'une variable soit interpolée, écrivez-la comme vous le feriez en Perl. Si vous avez besoin de faire une boucle, vous pouvez utiliser n'importe quelle construction de boucle Perl. Toutes les fonctions intégrées de Perl sont disponibles.

Détails

Analyse du modèle

Le module "Text::Template" analyse la source du modèle. Une accolade ouvrante "{" commence un fragment de programme, qui se poursuit jusqu'à l'accolade fermante correspondante "}". Lorsque le modèle est rempli, les fragments de programme sont évalués, et chacun est remplacé par la valeur résultante pour générer le texte qui est retourné.

Une barre oblique inverse "\" devant une accolade (ou une autre barre oblique inverse devant une accolade) échappe son sens spécial. Le résultat du remplissage de ce modèle :

\{ La somme de 1 et 2 est {1+2}  \}

est

{ La somme de 1 et 2 est 3  }

Si vous avez une accolade non appariée, "Text::Template" retournera un code d'échec et un avertissement sur l'emplacement du problème. Les barres obliques inverses qui ne précèdent pas une accolade sont transmises inchangées. Si vous avez un modèle comme celui-ci :

{ "Chaîne se terminant par une nouvelle ligne.\n" }

La barre oblique inverse dans la chaîne est transmise à Perl inchangée, donc le "\n" se transforme réellement en une nouvelle ligne. Voir la note à la fin pour les détails sur le fonctionnement des barres obliques inverses. Le traitement des barres obliques inverses n'est *pas* effectué lorsque vous spécifiez des délimiteurs alternatifs avec l'option "DELIMITERS". (Voir « Délimiteurs alternatifs », ci-dessous.)

Chaque fragment de programme doit être une séquence d'instructions Perl, qui sont évaluées de manière habituelle. Le résultat de la dernière instruction exécutée sera évalué en contexte scalaire ; le résultat de cette instruction est une chaîne de caractères, qui est interpolée dans le modèle à la place du fragment de programme lui-même.

Les fragments sont évalués dans l'ordre, et les effets secondaires des fragments précédents persistent dans les fragments suivants :

{$x = @things; ''}Le Lord Grand Chambellan m'a obtenu {$x}
objets cette année.
{ $diff = $x - 17;
  $more = 'plus'
  if ($diff == 0) {
    $diff = 'aucun';
  } elsif ($diff < 0) {
    $more = 'moins';
  }
  '';
}
C'est {$diff} {$more} que ce qu'il m'a donné l'année dernière.

La valeur de $x définie sur la première ligne persistera dans le fragment suivant qui commence sur la troisième ligne, et les valeurs de $diff et $more définies dans le deuxième fragment persisteront et seront interpolées dans la dernière ligne. La sortie ressemblera à ceci :

Le Lord Grand Chambellan m'a obtenu 42
objets cette année.
C'est 25 de plus que ce qu'il m'a donné l'année dernière.

C'est toute la syntaxe qu'il y a.

La variable $OUT

le'>La variable $OUT

Il existe une astuce spéciale que vous pouvez utiliser dans un modèle. Voici la motivation : supposons que vous passiez un tableau, @items, dans le modèle, et que vous souhaitiez que le modèle génère une liste à puces avec un titre, comme ceci :

Voici une liste des choses que j'ai pour vous depuis 1907 :
  * Ivoire
  * Grands singes
  * Paons
  * ...

Une façon de procéder est d'utiliser un modèle comme celui-ci :

Voici une liste des choses que j'ai pour vous depuis 1907 :
{ my $blist = '';
  foreach $i (@items) {
      $blist .= qq{  * $i\n};
  }
  $blist;
}

Ici, nous construisons la liste dans une variable appelée $blist, que nous retournons à la fin. C'est un peu laborieux. Il existe un raccourci.

Dans les modèles, il existe une variable spéciale appelée $OUT. Tout ce que vous ajoutez à cette variable apparaîtra dans la sortie du modèle. De plus, si vous utilisez $OUT dans un fragment de programme, le comportement normal, qui consiste à remplacer le fragment par sa valeur de retour, est désactivé ; le fragment est plutôt remplacé par la valeur de $OUT. Cela signifie que vous pouvez écrire le modèle ci-dessus comme suit :

Voici une liste des choses que j'ai pour vous depuis 1907 :
{ foreach $i (@items) {
    $OUT .= "  * $i\n";
  }
}

$OUT est réinitialisé à la chaîne vide au début de chaque fragment de programme. Il est privé à "Text::Template", vous ne pouvez donc pas utiliser une variable nommée $OUT dans votre modèle sans invoquer le comportement spécial.

Remarques Générales

Toutes les fonctions de "Text::Template" retournent "undef" en cas d'échec, et définissent la variable $Text::Template::ERROR pour contenir une explication de ce qui s'est mal passé. Par exemple, si vous essayez de créer un modèle à partir d'un fichier qui n'existe pas, $Text::Template::ERROR contiendra quelque chose comme :

Impossible d'ouvrir le fichier xyz.tmpl : Aucun fichier ou dossier de ce type

"new"

$template = Text::Template->new( TYPE => ..., SOURCE => ... );

Cela crée et retourne un nouvel objet modèle. "new" retourne "undef" et définit $Text::Template::ERROR s'il ne parvient pas à créer l'objet modèle. "SOURCE" indique d'où proviendra le code source du modèle. "TYPE" indique de quel type d'objet est la source.

Le type de source le plus courant est un fichier :

Text::Template->new( TYPE => 'FILE', SOURCE => $filename );

Cela lit le modèle à partir du fichier spécifié. Le nom du fichier est ouvert avec la commande Perl "open", il peut donc s'agir d'un tube ou de tout autre élément logique avec "open".

Le "TYPE" peut également être "STRING", auquel cas la "SOURCE" doit être une chaîne de caractères :

Text::Template->new( TYPE => 'STRING',
                     SOURCE => "C'est le modèle réel !" );

Le "TYPE" peut être "ARRAY", auquel cas la source doit être une référence à un tableau de chaînes. La concaténation de ces chaînes constitue le modèle :

Text::Template->new( TYPE => 'ARRAY',
                         SOURCE => [ "C'est ", "le réel",
                                     " modèle !",
                                   ]
                   );

Le "TYPE" peut être "FILEHANDLE", auquel cas la source doit être un descripteur de fichier ouvert (tel que celui obtenu à partir des packages "FileHandle" ou "IO::*", ou un glob, ou une référence à un glob). Dans ce cas, "Text::Template" lira le texte du descripteur de fichier jusqu'à la fin du fichier, et ce texte est le modèle :

# Lire le code source du modèle depuis STDIN :
Text::Template->new ( TYPE => 'FILEHANDLE', 
                      SOURCE => \*STDIN  );

Si vous omettez l'attribut "TYPE", il est considéré comme "FILE". "SOURCE" est obligatoire. Si vous l'omettez, le programme s'arrêtera.

Les mots "TYPE" et "SOURCE" peuvent être orthographiés de l'une des manières suivantes :

TYPE     SOURCE
Type     Source
type     source
-TYPE    -SOURCE
-Type    -Source
-type    -source

Choisissez un style que vous aimez et tenez-vous-y.

"DELIMITERS"
Vous pouvez également ajouter une option "DELIMITERS". Si cette option est présente, sa valeur doit être une référence à un tableau de deux chaînes. La première chaîne est la chaîne qui signale le début de chaque fragment de programme, et la seconde chaîne est la chaîne qui signale la fin de chaque fragment de programme. Voir « Délimiteurs alternatifs », ci-dessous.
"ENCODING"
Vous pouvez également ajouter une option "ENCODING". Si cette option est présente, et que la "SOURCE" est un "FILE", alors les données seront décodées de l'encodage donné en utilisant le module Encode. Vous pouvez utiliser n'importe quel encodage qu'Encode reconnaît. Par exemple : 
Text::Template->new(
    TYPE     => 'FILE',
    ENCODING => 'UTF-8',
    SOURCE   => 'xyz.tmpl');
"UNTAINT"
Si votre programme s'exécute en mode taint, vous pourriez avoir des problèmes si vos modèles sont stockés dans des fichiers. Les données lues à partir de fichiers sont considérées comme « non fiables », et le mode taint ne vous permettra pas d'évaluer le code Perl du fichier. (Il craint qu'une personne malveillante n'ait falsifié le fichier.)

Dans certains environnements, cependant, les fichiers locaux sont fiables. Vous pouvez indiquer à "Text::Template" qu'un fichier donné est fiable en fournissant "UNTAINT => 1" dans l'appel à "new". Cela indiquera à "Text::Template" de désactiver les vérifications de taint sur le code du modèle provenant d'un fichier, tant que le nom du fichier lui-même est considéré comme fiable. Cela désactivera également les vérifications de taint sur le code du modèle provenant d'un descripteur de fichier. Lorsqu'il est utilisé avec "TYPE => 'string'" ou "TYPE => 'array'", il n'a aucun effet.

Voir perlsec pour des informations plus complètes sur le tainting.

Remerciements à Steve Palincsar, Gerard Vreeswijk et Dr. Christoph Baehr pour leur aide concernant cette fonctionnalité.

"PREPEND"
Cette option est transmise à l'appel "fill_in" à moins qu'elle ne soit remplacée dans les arguments de "fill_in". Voir la fonctionnalité "PREPEND" et l'utilisation de "strict" dans les modèles ci-dessous.
"BROKEN"
Cette option est transmise à l'appel "fill_in" à moins qu'elle ne soit remplacée dans les arguments de "fill_in". Voir "BROKEN" ci-dessous.

"compile"

$template->compile()

Charge tout le texte du modèle à partir de la source du modèle, l'analyse et le compile. En cas de succès, retourne vrai ; sinon, retourne faux et définit $Text::Template::ERROR. Si le modèle est déjà compilé, il retourne vrai et ne fait rien.

Vous n'avez généralement pas besoin d'appeler cette fonction, car "fill_in" (voir ci-dessous) compile le modèle s'il n'est pas déjà compilé.

S'il y a un argument à cette fonction, il doit s'agir d'une référence à un tableau contenant des chaînes de délimiteurs alternatives. Voir « Délimiteurs alternatifs », ci-dessous.

"fill_in"

$template->fill_in(OPTIONS);

Remplit un modèle. Retourne le texte résultant en cas de succès. Sinon, retourne "undef" et définit $Text::Template::ERROR.

Les OPTIONS sont une table de hachage, ou une liste de paires clé-valeur. Vous pouvez écrire les noms des clés dans l'un des six styles habituels comme ci-dessus ; cela signifie que là où ce manuel indique "PACKAGE" (par exemple), vous pouvez en fait utiliser n'importe lequel de ces :

PACKAGE Package package -PACKAGE -Package -package

Choisissez un style que vous aimez et tenez-vous-y. Les versions entièrement en minuscules peuvent générer des avertissements parasites concernant

Utilisation ambiguë de package => résolu en « package »

vous pourriez donc vouloir les éviter et utiliser les versions capitalisées.

Actuellement, il existe huit options légales : "PACKAGE", "BROKEN", "BROKEN_ARG", "FILENAME", "SAFE", "HASH", "OUTPUT" et "DELIMITERS".

"PACKAGE"
"PACKAGE" spécifie le nom d'un package dans lequel les fragments de programme doivent être évalués. La valeur par défaut est d'utiliser le package à partir duquel "fill_in" a été appelé. Par exemple, considérez ce modèle : 
La valeur de la variable x est {$x}.

Si vous utilisez "$template->fill_in(PACKAGE => 'R')", alors le $x dans le modèle est en fait remplacé par la valeur de $R::x. Si vous omettez l'option "PACKAGE", $x sera remplacé par la valeur de la variable $x dans le package qui a réellement appelé &q

information sur ce qui s'est mal passé.

La fonction "BROKEN" peut également utiliser "BROKEN_ARG" comme référence pour stocker un message d'erreur ou toute autre information qu'elle souhaite communiquer à l'appelant. Par exemple :

$error = '';
sub my_broken {
   my %args = @_;
   my $err_ref = $args{arg};
   ...
   $$err_ref = "Some error message";
   return undef;
}
$template->fill_in(
    BROKEN     => \&my_broken,
    BROKEN_ARG => \$error
);
if ($error) {
  die "It didn't work: $error";
}

Si l'un des fragments de programme du modèle échoue, il appellera la fonction "BROKEN", "my_broken", et lui passera "BROKEN_ARG", qui est une référence à $error. "my_broken" peut ainsi stocker un message d'erreur dans $error. Ensuite, la fonction qui a appelé "fill_in" peut voir si "my_broken" a laissé un message d'erreur à trouver, et agir en conséquence.

"FILENAME"
Si vous donnez à "fill_in" une option "FILENAME", alors c'est le nom du fichier d'où vous avez chargé la source du modèle. Cela n'affecte que le message d'erreur pour les erreurs de modèle. Si vous avez chargé le modèle depuis "foo.txt" par exemple, et que vous passez "foo.txt" comme paramètre "FILENAME", les erreurs ressembleront à "... at foo.txt line N" plutôt qu'à "... at template line N".

Notez que cela n'a RIEN à voir avec le chargement d'un modèle à partir du nom de fichier donné. Voir fill_in_file() pour cela.

Par exemple :

my $template = Text::Template->new(
    TYPE   => 'string',
    SOURCE => 'The value is {1/0}');
$template->fill_in(FILENAME => 'foo.txt') or die $Text::Template::ERROR;

mourra avec une erreur contenant

Illegal division by zero at at foo.txt line 1
"SAFE"
Si vous donnez à "fill_in" une option "SAFE", sa valeur doit être un objet compartiment sûr du package "Safe". Toute évaluation de fragments de programme sera effectuée dans ce compartiment. Voir Safe pour tous les détails sur de tels compartiments et comment restreindre les opérations qui peuvent y être effectuées.

Si vous utilisez l'option "PACKAGE" avec "SAFE", le package que vous spécifiez sera placé dans le compartiment sûr et l'évaluation se déroulera dans ce package comme d'habitude.

Sinon, le fonctionnement de "SAFE" est un peu différent de la valeur par défaut. Normalement, si vous ne spécifiez pas de package, l'évaluation des fragments de programme se fait dans le package depuis lequel le modèle a été appelé. Mais en mode "SAFE", l'évaluation se produit à l'intérieur du compartiment sûr et ne peut pas affecter le package appelant. Normalement, si vous utilisez "HASH" sans "PACKAGE", les variables de hachage sont importées dans un package privé et à usage unique. Mais si vous utilisez "HASH" et "SAFE" ensemble sans "PACKAGE", les variables de hachage seront simplement chargées dans l'espace de noms racine du compartiment "Safe".

"OUTPUT"
Si votre modèle va générer beaucoup de texte que vous allez simplement réimprimer de toute façon, vous pouvez économiser de la mémoire en faisant en sorte que "Text::Template" imprime le texte au fur et à mesure de sa génération au lieu de le transformer en une grande chaîne et de retourner cette chaîne. Si vous fournissez l'option "OUTPUT" à "fill_in", la valeur doit être un handle de fichier. Le texte généré sera imprimé sur ce handle de fichier au fur et à mesure de sa construction. Par exemple : 
$template->fill_in(OUTPUT => \*STDOUT, ...);

remplit le $template comme d'habitude, mais les résultats sont immédiatement imprimés sur STDOUT. Cela peut résulter en une sortie apparaissant plus rapidement qu'elle ne l'aurait fait autrement.

Si vous utilisez "OUTPUT", la valeur de retour de "fill_in" est toujours vraie en cas de succès et fausse en cas d'échec, mais le texte complet n'est pas retourné à l'appelant.

"PREPEND"
Vous pouvez avoir du code Perl ajouté automatiquement au début de chaque fragment de programme. Voir la section ""PREPEND" feature and using "strict" in templates" ci-dessous.
"DELIMITERS"
Si cette option est présente, sa valeur doit être une référence à une liste de deux chaînes. La première chaîne signale le début de chaque fragment de programme, et la seconde chaîne signale la fin de chaque fragment de programme. Voir "Alternative Delimiters", ci-dessous.

Si vous spécifiez "DELIMITERS" dans l'appel à "fill_in", ils outrepassent tous les délimiteurs que vous avez définis lors de la création de l'objet modèle avec "new".

Fonctions de commodité

"fill_this_in"

La manière de base de remplir un modèle est de créer un objet modèle, puis d'appeler "fill_in" dessus. Ceci est utile si vous voulez remplir le même modèle plusieurs fois.

Dans certains programmes, cela peut être encombrant. "fill_this_in" accepte une chaîne, qui contient le modèle, et une liste d'options, qui sont passées à "fill_in" comme ci-dessus. Elle construit l'objet modèle pour vous, le remplit comme spécifié, et retourne les résultats. Elle retourne "undef" et définit $Text::Template::ERROR si elle n'a pas pu générer de résultats.

Un exemple :

$Q::name = 'Donald';
$Q::amount = 141.61;
$Q::part = 'hyoid bone';
$text = Text::Template->fill_this_in( <<'EOM', PACKAGE => Q);
Dear {$name},
You owe me \\${sprintf('%.2f', $amount)}.
Pay or I will break your {$part}.
    Love,
    Grand Vizopteryx of Irkutsk.
EOM

Remarquez comment nous avons inclus le modèle en ligne dans le programme en utilisant un « here document » avec la notation "<<".

"fill_this_in" est une fonctionnalité obsolète. Elle n'est là que pour la compatibilité ascendante, et pourrait être supprimée dans une future version de "Text::Template". Vous devriez utiliser "fill_in_string" à la place. Elle est décrite dans la section suivante.

"fill_in_string"

Il est stupide que "fill_this_in" soit une méthode de classe. Elle aurait dû être simplement une fonction importée, de sorte que vous puissiez omettre le "Text::Template->" dans l'exemple ci-dessus. Mais j'ai fait l'erreur il y a quatre ans et il est trop tard pour la changer.

"fill_in_string" est exactement comme "fill_this_in" sauf qu'elle n'est pas une méthode et que vous pouvez omettre le "Text::Template->" et dire simplement

print fill_in_string(<<'EOM', ...);
Dear {$name},
  ...
EOM

Pour utiliser "fill_in_string", vous devez écrire

use Text::Template 'fill_in_string';

en haut de votre programme. Vous devriez probablement utiliser "fill_in_string" au lieu de "fill_this_in".

"fill_in_file"

Si vous importez "fill_in_file", vous pouvez dire

$text = fill_in_file(filename, ...);

Les "..." sont passés à "fill_in" comme ci-dessus. Le nom de fichier est le nom du fichier qui contient le modèle que vous voulez remplir. Il retourne le texte résultant, ou "undef", comme d'habitude.

Si vous allez remplir le même fichier plusieurs fois dans le même programme, vous devriez utiliser la séquence plus longue "new" / "fill_in" à la place. Elle sera beaucoup plus rapide car elle n'aura à lire et analyser le fichier qu'une seule fois.

Inclusion de fichiers dans les modèles

Les gens demandent toujours cela. « Pourquoi n'avez-vous pas de fonction d'inclusion ? » demandent-ils. La réponse courte est que c'est Perl, et Perl a déjà une fonction d'inclusion. Si vous la voulez, vous pouvez juste mettre

{qx{cat filename}}

dans votre modèle. Voilà.

*Q::include = \&Text::Template::_load_text;

Divers propos




variables "my"


Les utilisateurs sont souvent surpris quand ceci ne fonctionne pas :


my $recipient = 'The King';
my $text = fill_in_file('formletter.tmpl');


Le texte "The King" n’est pas inclus dans le formulaire. Pourquoi pas ? Parce que $recipient est une variable "my", et le but des variables "my" est d’être privées et accessibles seulement dans la portée dans laquelle elles sont déclarées. Le formulaire n’est pas dans cette portée, donc le formulaire ne peut pas voir $recipient.


Si ce n’est pas le comportement que vous souhaitez, n’utilisez pas "my". "my" signifie une variable privée, et dans ce cas vous ne voulez pas que la variable soit privée. Mettez les variables dans des variables de paquet dans un autre paquet, et utilisez l’option "PACKAGE" de "fill_in" :


$Q::recipient = $recipient;
my $text = fill_in_file('formletter.tmpl', PACKAGE => 'Q');


ou passez les noms et valeurs dans une hash avec l’option "HASH" :


my $text = fill_in_file('formletter.tmpl', HASH => { recipient => $recipient });






Problèmes de sécurité


Toutes les variables sont évaluées dans le paquet que vous spécifiez avec l’option "PACKAGE" de "fill_in". Si vous utilisez cette option et si vos formulaires ne font rien de particulièrement étrange, vous n’aurez pas à vous soucier que l’évaluation de petits bouts de programme se fasse dans le reste de votre programme et ne détruise quoi que ce soit.


Cependant, il n’y a vraiment aucun moyen (sauf si vous utilisez "Safe") de se protéger contre un formulaire qui dit :


{ $Important::Secret::Security::Enable = 0;
  # Désactiver les contrôles de sécurité dans ce programme
}


ou


{ $/ = "ho ho ho";   # Commencer à utiliser <FH>.
  # $/ est toujours une variable globale
}


ou même


{ system("rm -rf /") }


par conséquent, vous ne devriez pas remplir de formulaires à moins que vous ne sachiez ce qu’ils contiennent. Si vous êtes inquiet ou si vous ne pouvez pas faire confiance à celui qui a écrit le formulaire, utilisez l’option "SAFE".


Une dernière chose : les bouts de programme présentent un petit risque de sobrescrire des variables locales dans la fonction "fill_in". Ces variables ont des noms commençant par $fi_, donc si vous vous éloignez de ces noms, vous serez en sécurité. (Bien que si vous êtes un vrai magicien, vous pouvez les altérer délibérément pour des effets intéressants ; c’est comme ça que fonctionne $OUT.) Je peux corriger cela, mais cela ralentira le paquet, donc je préférerais ne pas le faire. Si vous êtes inquiet, envoyez-moi un message et je vous montrerai ce que vous devriez faire.






Délimiteurs alternatifs


Lorenzo Valdettaro a fait remarquer que si vous utilisez "Text::Template" pour générer des sorties TeX, le choix des accolades comme délimiteurs de bouts de code vous donne du fil à retordre. Depuis la version 1.20, vous pouvez changer le choix des délimiteurs pour autre chose que des accolades.


Entre-temps, l’option "DELIMITERS" de l’appel "new() ou "fill_in() vous permet de spécifier un ensemble alternatif de délimiteurs. Par exemple, si vous voulez que les bouts de code soient délimités par "[@--" et "--@]" au lieu de "{" et "}", utilisez :


... DELIMITERS => [ '[@--', '--@]' ], ...


Note : ces délimiteurs sont des chaînes littérales, pas des expressions régulières. (J’ai essayé avec des expressions régulières, mais cela a trop compliqué l’analyse lexicale.) Notez également que "DELIMITERS" désactive la signification spéciale de la barre oblique inverse, donc si vous voulez inclure les délimiteurs dans le texte littéral de votre fichier de formulaire, vous êtes mal parti — vous devez choisir des délimiteurs qui n’entrent pas en conflit avec ce que vous faites. Les chaînes de délimiteurs peuvent apparaître dans les bouts de code tant qu’ils sont correctement imbriqués. Cela signifie que si pour une raison quelconque vous devez avoir un bout de code qui mentionne l’un des délimiteurs, comme celui-ci :


[@--
    print "Oh non, un délimiteur : --@]\n"
--@]


vous pouvez le faire fonctionner avec ceci :


[@--
    # Délimiteur fictif dans un commentaire : [@--
    print "Oh non, un délimiteur : --@]\n"
--@]


Il peut être plus sûr de choisir des délimiteurs qui commencent par un caractère de nouvelle ligne.


Parce que l’analyse des formulaires est simplifiée sans échappement des barres obliques inverses, l’utilisation de délimiteurs alternatifs peut accélérer le processus d’analyse de 20-25%. Cela montre que mon choix initial de "{" et "}" était très mauvais.






Fonctionnalité "PREPEND" et utilisation de "strict" dans les formulaires


Supposons que vous souhaitiez utiliser "strict" dans vos formulaires pour détecter les variables non déclarées et autres cas. Mais chaque bout de code est un champ lexical différent, vous devez donc activer "strict" au début de chacun :


{ use strict;
  use vars '$foo';
  $foo = 14;
  ...
}
...
{ # j'ai oublié de mettre `use strict` ici
  my $result = $boo + 12;    # $boo est mal écrit et devrait être $foo
  # Aucune erreur n’est générée à propos de `$boo`
}


Parce que vous n’avez pas mis "use strict" au début du second bout de code, il n’était actif que dans le premier et aucun contrôle "strict" n’a été généré dans le second bout de code. Ensuite, vous avez mal orthographié $foo et l’erreur n’a pas été capturée.


La version 1.22 et supérieure de "Text::Template" a une nouvelle fonctionnalité pour faciliter cela. Vous pouvez spécifier que n’importe quel texte doit être automatiquement ajouté au début de chaque bout de code.


Lorsque vous faites un appel à "fill_in", vous pouvez spécifier l’option :


PREPEND => 'some perl statements here'


Les instructions sont ajoutées au début de chaque bout de code pour cet appel. Supposons que l’appel à "fill_in" incluait :


PREPEND => 'use strict;'


et que le formulaire ressemble à ceci :


{ use vars '$foo';
  $foo = 14;
  ...
}
...
{ my $result = $boo + 12;    # $boo est mal écrit et devrait être $foo
  ...
}


Le code dans le second bout de code échouera, car $boo n’a pas été déclaré. "use strict" a été imposé implicitement, même si vous ne l’avez pas explicitement écrit, car l’option "PREPEND" a ajouté le code pour vous.


Il y a trois autres façons de faire cela. Lorsque vous créez l’objet de formulaire avec "new", vous pouvez également spécifier l’option "PREPEND", dans laquelle les instructions sont ajoutées au début de chaque appel à "fill_in". Si l’appel à "fill_in" a sa propre option "PREPEND", celle-ci remplace l’option spécifiée lors de la création de l’objet. Enfin, vous pouvez appeler la méthode de classe :


Text::Template->always_prepend('perl statements');


Si vous faites cela, alors tout appel à "fill_in" pour n’importe quel formulaire ajoutera les instructions en tête de chaque bout de code, sauf lorsqu’elles sont remplacées par des options "PREPEND" de "new" ou "fill_in".


Une alternative à l’ajout de "use strict;" à l’option "PREPEND" est de passer STRICT => 1 lors de l’appel à "fill_in" avec l’option "HASH".


Supposons que l’appel à "fill_in" incluait les deux options :


HASH   => {$foo => ''} et
STRICT => 1


et que le formulaire ressemble à ceci :


{
  $foo = 14;
  ...
}
...
{ my $result = $boo + 12;    # $boo est mal écrit et devrait être $foo
  ...
}


Le code dans le second bout de code échouera, car $boo n’a pas été déclaré. "use strict" a été imposé implicitement, même si vous ne l’avez pas explicitement écrit, car l’option "STRICT" a ajouté le code pour vous. Toute variable référencée dans le formulaire qui ne figure pas dans l’option "HASH" sera une erreur.






Ajout en tête dans les classes dérivées


Cette section est technique et vous devriez la sauter lors des premières lectures.


Normalement, il y a trois endroits d’où le texte précédent peut provenir. Il peut provenir de l’option "PREPEND" de l’appel "fill_in", de l’option "PREPEND" de l’appel "new" qui a créé l’objet de formulaire, ou de l’argument de l’appel "always_prepend". L’option "PREPEND" de l’appel "fill_in" peut être utilisée pour empêcher le texte précédent d’être ajouté au bout de code. L’option "PREPEND" de l’appel "new" peut être utilisée pour empêcher le texte précédent d’être ajouté au bout de code. L’argument de l’appel "always_prepend" peut être utilisé pour empêcher le texte précédent d’être ajouté au bout de code.





>« Text::Template » recherche ces trois
    choses dans l'ordre et prend la première qu'elle trouve.


Dans une sous-classe de
     » Text::Template » , cette dernière possibilité est
    ambiguë. Supposons que  » S »  soit une sous-classe de
     » Text::Template » . Est-ce que


Text::Template->always_prepend(...);


affectera les objets de la classe
     » Derived »  ? La réponse est que vous pouvez avoir les deux. 


La valeur  » always_prepend »  pour
     » Text::Template »  est normalement stockée dans une
    variable de hachage nommée  » %GLOBAL_PREPEND »  sous la clé
     » Text::Template » . Lorsque
     » Text::Template »  recherche le texte à ajouter, il cherche d'abord dans l'objet template lui-même, et sinon, il cherche dans
     » $GLOBAL_PREPEND{class} où class est la classe à laquelle appartient l'objet template. S'il ne trouve aucune valeur, il cherche dans
     » $GLOBAL_PREPEND{'Text::Template'}. Cela signifie que les objets de la classe  » Derived »  *seront* affectés par


Text::Template->always_prepend(...);


 *à moins* qu'il n'y ait également un appel à


Derived->always_prepend(...);


Ainsi, lorsque vous concevez votre classe dérivée, vous pouvez faire en sorte que vos objets ignorent les appels à
     » Text::Template::always_prepend »  en plaçant simplement
     » Derived->always_prepend('') »  au début de votre module.


Bien sûr, il existe également un dernier recours : les templates prennent en charge une méthode
     » prepend_text »  qui est utilisée pour rechercher le texte approprié à ajouter au moment de
     » fill_in » . Votre classe dérivée peut remplacer cette méthode pour obtenir un effet arbitraire.

JavaScript

Jennifer D. St Clair demande :

> La plupart de mes pages contiennent du JavaScript et des feuilles de style.
> Comment changer l'identifiant du template ?

Jennifer s'inquiète que les accolades dans le JavaScript soient interprétées comme des délimiteurs des fragments de code Perl. Bien sûr, un désastre surviendra lorsque Perl essaiera de les évaluer comme s'il s'agissait de programmes Perl. Le meilleur choix est de trouver des chaînes de délimitation non ambiguës que vous pouvez utiliser dans votre template à la place des accolades, puis d'utiliser l'option  » DELIMITERS » . Cependant, si vous ne pouvez pas le faire pour une raison quelconque, il existe deux solutions simples :

1. Vous pouvez placer  » \ »  devant  » { » ,  » } » , ou  » \ »  pour supprimer leur signification spéciale. Ainsi, par exemple, au lieu de

if (br== "n3") {
    // etc.
}

vous pouvez écrire

if (br== "n3") \{
    // etc.
\}

et cela sortira du moteur de template comme vous le souhaitez.

Mais voici une autre méthode qui est probablement meilleure. Pour voir comment cela fonctionne, considérez d'abord ce qui se passe si vous mettez ceci dans un template :

{ 'foo' }

Comme c'est entre accolades, cela est évalué, et évidemment, cela se transformera en

foo

Alors voici l'astuce : en Perl,  » q{...} »  est la même chose que  » '...' » . Donc, si nous écrivions

{q{foo}}

cela se transformerait en

foo

Donc, pour votre JavaScript, écrivez simplement

{q{if (br== "n3") {
   // etc.
   }}
}

et cela sortira comme

if (br== "n3") {
    // etc.
}

ce qui est ce que vous voulez.

head2 Tais-toi !

Parfois, les gens essaient de mettre une section d'initialisation en haut de leurs templates, comme ceci :

{ ...
    $var = 17;
}

Ensuite, ils se plaignent parce qu'il y a un 17 en haut de la sortie qu'ils ne voulaient pas.

Rappelez-vous qu'un fragment de code est remplacé par sa propre valeur de retour, et qu'en Perl, la valeur de retour d'un bloc de code est la valeur de la dernière expression évaluée, qui dans ce cas est 17. Si cela ne le faisait pas, vous ne pourriez pas écrire  » {$recipient} »  et obtenir le destinataire rempli.

Pour empêcher le 17 d'apparaître dans la sortie, c'est très simple :

{ ...
    $var = 17;
    '';
}

Maintenant, la dernière expression évaluée renvoie une chaîne vide, qui est invisible. Si vous n'aimez pas la façon dont cela ressemble, utilisez

{ ...
    $var = 17;
    ($SILENTLY);
}

à la place. Vraisemblablement, $SILENTLY n'a pas de valeur, donc rien ne sera interpolé. C'est ce qu'on appelle une astuce.

Compatibilité

Tous les efforts ont été faits pour rendre ce module compatible avec les versions antérieures. Les seules exceptions connues sont les suivantes :

Le format de sortie de la sous-routine par défaut  » BROKEN »  a changé deux fois, le plus récemment entre les versions 1.31 et 1.40.

À partir de la version 1.10, la variable $OUT est réservée pour une signification spéciale. Si vous aviez des templates avant la version 1.10 qui utilisaient par hasard une variable nommée $OUT, vous devrez la changer pour utiliser une autre variable ou toutes sortes d'étrangetés en résulteront.

Entre les versions 0.1b et 1.00, le comportement du métacaractère \ a changé. En 0.1b, \\ était spécial partout, et le processeur de template le remplaçait toujours par une seule barre oblique inverse avant de passer le code à Perl pour évaluation. La règle est maintenant plus compliquée mais probablement plus pratique. Voir la section sur le traitement des barres obliques inverses ci-dessous pour une discussion complète.

Traitement des barres obliques inverses

Dans les versions bêta de  » Text::Template » , la barre oblique inverse était spéciale chaque fois qu'elle apparaissait avant une accolade ou une autre barre oblique inverse. Cela signifiait que tandis que  » { » \n » } »  générait effectivement un saut de ligne,  » { » \\ » } »  ne générait pas de barre oblique inverse, car le code passé à Perl pour évaluation était  » \ » , ce qui est une erreur de syntaxe. Si vous vouliez une barre oblique inverse, vous deviez écrire  » { » \\\\ » } » .

Dans les versions 1.00 à 1.10 de  » Text::Template » , il y avait un bug : la barre oblique inverse était spéciale partout. Dans ces versions,  » { » \n » } »  générait la lettre  » n » .

Le bug a été corrigé dans la version 1.11, mais je ne suis pas revenu à la règle exacte, car je n'aimais pas l'idée de devoir écrire  » { » \\\\ » } »  pour obtenir une barre oblique inverse. La règle est maintenant plus compliquée à retenir, mais probablement plus facile à utiliser. La règle est maintenant : les barres obliques inverses sont toujours transmises à Perl inchangées *sauf* si elles apparaissent dans une séquence comme  » \\\\\\{ »  ou  » \\\\\\} » . Dans ces contextes, elles sont spéciales ;  » \\ »  est remplacé par  » \ » , et  » \{ »  et  » \} »  signalent une accolade littérale.

Exemples :

\{ foo \}

n'est *pas* évalué, car la  » \ »  avant les accolades signale qu'elles doivent être prises littéralement. Le résultat dans la sortie ressemble à ceci :

{ foo }

Ceci est une erreur de syntaxe :

{ "foo}" }

car  » Text::Template »  pense que le code se termine à la première  » } » , puis s'énerve quand il voit la deuxième. Pour que cela fonctionne correctement, utilisez

{ "foo\}" }

Ceci passe  » foo} »  à Perl pour évaluation. Notez qu'il n'y a pas de  » \ »  dans le code évalué. Si vous voulez vraiment une  » \ »  dans le code évalué, utilisez

{ "foo\\\}" }

Ceci passe  » foo\} »  à Perl pour évaluation.

À partir de la version 1.20 de  » Text::Template » , le traitement des barres obliques inverses est désactivé si vous utilisez l'option  » DELIMITERS »  pour spécifier des chaînes de délimitation alternatives.

Une courte note sur $Text::Template::ERROR

Dans le passé, certaines personnes se sont inquiétées de « violer la frontière du paquetage » en examinant une variable à l'intérieur du paquetage  » Text::Template » . Ne vous sentez pas ainsi. $Text::Template::ERROR fait partie de l'interface publiée et officielle de ce paquetage. Il est parfaitement acceptable d'inspecter cette variable. L'interface ne changera pas.

Si cela vous dérange vraiment, vous pouvez importer une fonction appelée  » TTerror »  qui renvoie la valeur actuelle de la variable $ERROR. Vous pouvez donc dire :

use Text::Template 'TTerror';
my $template = Text::Template->new(SOURCE => $filename);
unless ($template) {
    my $err = TTerror;
    die "Couldn't make template: $err; aborting";
}

Je ne vois pas l'avantage par rapport à simplement faire ceci :

use Text::Template;
my $template = Text::Template->new(SOURCE => $filename)
    or die "Couldn't make template: $Text::Template::ERROR; aborting";

Mais si cela vous fait plaisir de le faire ainsi, allez-y.
