NOM

Test::Perl::Critic::Policy - Un framework pour tester vos politiques personnalisées

SYNTAXE

use Test::Perl::Critic::Policy qw< all_policies_ok >;
# En supposant que les fichiers .run se trouvent dans le répertoire 't'...
all_policies_ok()
# Ou si vos fichiers .run se trouvent dans un répertoire différent...
all_policies_ok( '-test-directory' => 'run' );
# Et si vous voulez juste exécuter des tests pour certaines politiques...
all_policies_ok( -policies => ['Some::Policy', 'Another::Policy'] );
# Si vous voulez que votre programme de test accepte des noms de politiques courts en tant que
# paramètres de ligne de commande...
#
# Vous pouvez ensuite tester une seule politique en exécutant
# "perl -Ilib t/policy-test.t My::Policy".
my %args = @ARGV ? ( -policies => [ @ARGV ] ) : ();
all_policies_ok(%args);

DESCRIPTION

Ce module fournit un framework pour tester fonctionnellement vos modules Perl::Critic::Policy personnalisés. Le test de politique implique généralement de lui fournir une chaîne de code Perl et de vérifier son comportement. Autrefois, ces chaînes de code Perl étaient mélangées directement dans le script de test. C'était nul.

SOUS-ROUTINES IMPORTABLES

all_policies_ok('-test-directory' => $path, -policies => \@policy_names)
Charge tous les fichiers *.run sous le "-test-directory" et exécute les tests. Si "-test-directory" n'est pas spécifié, il prend par défaut t/. "-policies" est une référence optionnelle à un tableau de noms de politiques abrégés. Si "-policies" est spécifié, seuls les tests pour les politiques qui correspondent à l'un des "m/$POLICY_NAME/imx" seront exécutés.

CRÉATION DES FICHIERS *.run

Tester une politique suit un schéma très simple :

* Nom de la politique
    * Nom du sous-test
    * Paramètres optionnels
    * Nombre d'échecs attendus
    * Exception optionnelle attendue
    * Nom de fichier optionnel pour le code

Chacun des sous-tests d'une politique est collecté dans un seul fichier .run, avec les propriétés de test sous forme de commentaires devant chaque bloc de code qui décrit comment nous attendons que Perl::Critic réagisse au code. Par exemple, disons que vous avez une politique appelée Variables::ProhibitVowels :

(Dans le fichier t/Variables/ProhibitVowels.run)
## name Basiques
## failures 1
## cut
my $vrbl_nm = 'foo';    # Bon nom, sans voyelles
my $wango = 12;         # Mauvais nom, prononçable
## name Parfois Y
## failures 1
## cut
my $yllw = 0;       # "y" n'est pas une voyelle ici
my $rhythm = 12;    # Mais ici c'en est une

Ce sont appelés des « sous-tests », et deux sont montrés ci-dessus. La beauté d'intégrer plusieurs sous-tests dans un fichier est que le fichier .run est lui-même un fichier Perl (principalement) valide, et non caché dans un HEREDOC, de sorte que la coloration syntaxique de votre éditeur fonctionne toujours, et il est beaucoup plus facile de travailler avec le code et le POD.

Si vous avez besoin de passer des paramètres de configuration pour votre sous-test, faites-le comme suit :

## parms { allow_y => '0' }

Notez que toutes les valeurs de ce hachage doivent être des chaînes car c'est ce que Perl::Critic vous remettra à partir d'un .perlcriticrc.

S'il s'agit d'un sous-test TODO (probablement à cause d'un coin bizarre de PPI que nous avons exercé et qu'Adam est en train de corriger, n'est-ce pas ?), alors faites une entrée "##TODO".

## TODO Devrait passer lorsque PPI 1.xxx sortira

Si le code est censé déclencher une exception dans la politique, indiquez-le comme suit :

## error 1

Si vous voulez tester le message d'erreur, marquez-le avec "/.../" pour indiquer un test like() :

## error /Impossible de charger Foo::Bar/

Si la politique que vous testez se soucie du nom de fichier du code, vous pouvez l'indiquer en utilisant "fcritique" comme suit (voir "fcritique" pour plus de détails) :

## filename lib/Foo/Bar.pm

La valeur de "parms" sera "eval"uée et passée à pcritique(), alors soyez prudent.

En général, un document de sous-test s'exécute à partir du "## cut" qui le commence jusqu'au prochain "## name" ou jusqu'à la fin du fichier. Dans de très rares circonstances, vous pourriez avoir besoin de terminer le document de test plus tôt. Un deuxième "## cut" le fera. Le seul besoin connu pour cela est dans t/Miscellanea/RequireRcsKeywords.run, où il est utilisé pour empêcher les mots-clés RCS dans le pied de page du fichier de produire des faux positifs ou négatifs dans le dernier test.

Notez que nulle part dans le fichier .run lui-même, vous ne spécifiez la politique que vous testez. C'est implicite dans le nom du fichier.
