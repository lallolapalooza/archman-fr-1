NOM

Template::Manual::Views - Vues de Template Toolkit (expérimental)

DESCRIPTION

Une vue est effectivement une collection de modèles et/ou de définitions de variables qui peuvent être passées comme une unité autonome. Elle représente une interface ou un style de présentation particulier pour d'autres objets ou éléments de données.

Vous pouvez utiliser des vues pour implémenter des « skins » personnalisés pour une application ou un ensemble de contenu. Vous pouvez les utiliser pour simplifier la présentation d'objets courants ou de types de données. Vous pouvez même les utiliser pour automatiser la présentation de structures complexes comme celles générées dans un "XML::DOM" ou similaire. Vous pouvez laisser un itérateur faire le parcours, et la vue fait la présentation. Voilà ! - vous avez un parcours indépendant et sans structure utilisant des modèles.

En général, les vues peuvent être utilisées de différentes manières pour accomplir différentes choses. Elles résolvent élégamment certains problèmes qui seraient difficiles ou compliqués à résoudre, et rendent faciles ce qui était auparavant difficile.

Pour l'instant, elles sont encore très expérimentales. La syntaxe des directives et l'API sous-jacente sont susceptibles de changer de manière significative dans la prochaine version ou deux. S'il vous plaît, soyez très prudent lorsque vous construisez vos solutions commerciales à un million de dollars basées sur cette fonctionnalité.

Vues comme collecteurs/fournisseurs de modèles

La directive "VIEW" commence une définition de vue et inclut un nom par lequel la vue peut être référencée. La définition de la vue continue jusqu'à la directive correspondante "END".

[% VIEW myview %]
   ...
[% END %]

La première fonction d'une vue est d'agir comme collecteur et fournisseur de modèles. La méthode include() peut être appelée sur une vue pour obtenir le même effet que la directive "INCLUDE". Le nom du modèle est passé comme premier argument, suivi de toute définition de variable locale pour le modèle.

[% myview.include('header', title='Le Titre') %]
# équivalent à
[% INCLUDE header  title='Le Titre' %]

Les vues acceptent plusieurs options de configuration qui peuvent être utilisées pour contrôler différents aspects de leur comportement. Les options "prefix" et "suffix" peuvent être spécifiées pour ajouter un préfixe et/ou un suffixe fixe au nom de chaque modèle.

[% VIEW myview
     prefix = 'my/'
     suffix = '.tt2' ;
   END
%]

Maintenant, l'appel

[% myview.include('header', title='Le Titre') %]

est équivalent à

[% INCLUDE my/header.tt2  title='Le Titre' %]

Les vues fournissent une méthode "AUTOLOAD" qui mappe les noms de méthodes à la méthode include(). Par conséquent, les éléments suivants sont tous équivalents :

[% myview.include('header', title='Bonjour le Monde') %]
[% myview.include_header(title='Bonjour le Monde') %]
[% myview.header(title='Bonjour le Monde') %]

Définitions de BLOCK locales

Une définition "VIEW" peut inclure des définitions "BLOCK" qui restent locales à la vue. Une demande d'un modèle particulier renverra un "BLOCK", s'il est défini, de préférence à tout autre modèle du même nom.

[% BLOCK foo %]
   block foo public
[% END %]
[% VIEW plain %]
   [% BLOCK foo %]
   block foo simple
   [% END %]
[% END %]
[% VIEW fancy %]
   [% BLOCK foo %]
   block foo fantaisiste
   [% END %]
[% END %]
[% INCLUDE foo %]       # block foo public
[% plain.foo %]         # block foo simple
[% fancy.foo %]         # block foo fantaisiste

En plus des définitions "BLOCK", une "VIEW" peut contenir toute autre directive de modèle. Le bloc de définition de "VIEW" entier est traité pour initialiser la vue, mais aucune sortie n'est générée (cela pourrait changer RSN - et sera stocké comme l'élément "output", accessible plus tard sous la forme "[% view.output %]"). Cependant, les directives ayant des effets secondaires, comme celles qui mettent à jour une variable, auront des conséquences notables.

Conservation de l'état des variables dans les vues

Les vues peuvent également être utilisées pour enregistrer les valeurs de toute variable existante, ou en créer de nouvelles au moment de la définition de la vue. Contrairement aux métadonnées simples ("META"), qui ne peuvent contenir que des valeurs de chaîne statiques, le bloc d'initialisation de la vue peut contenir n'importe quelle directive de modèle et générer n'importe quel type de sortie et/ou de données dynamiques.

[% VIEW my_web_site %]
   [% view.title   = title or 'Mon Super Site Web' %]
   [% view.author  = "$abw.name, $abw.email" %]
   [% view.sidebar = INCLUDE my/sidebar.tt2 %]
[% END %]

Remarque : Des données supplémentaires peuvent être spécifiées comme arguments à la directive "VIEW". Tout ce qui ne ressemble pas à un paramètre de configuration sera supposé être une donnée. Cela peut être un peu dangereux, car on ne sait jamais quand un nouveau paramètre de configuration sera ajouté qui pourrait interférer avec vos données.

[% VIEW my_web_site
        # options de configuration
        prefix = 'my/'
        # données supplémentaires
        title   = title or 'Mon Super Site Web'
        author  = "$abw.name, $abw.email"
        sidebar = INCLUDE my/sidebar.tt2
%]
   ...
[% END %]

En dehors de la définition de la vue, vous pouvez accéder aux variables de la vue comme suit :

[% my_web_site.title %]

Une caractéristique importante est l'équivalence des variables simples et des modèles. Vous pouvez implémenter l'élément de vue « title » comme une variable simple, un modèle défini dans un fichier externe, éventuellement avec un préfixe/suffixe ajouté automatiquement, ou comme une définition "BLOCK" locale au sein du bloc "%[ VIEW %] ... %] de la vue. Si vous utilisez la syntaxe ci-dessus, la vue fera le nécessaire pour renvoyer la sortie appropriée.

À la fin du bloc de définition de la vue "VIEW", la vue est fermée pour éviter que vous ne modifiiez accidentellement les valeurs de n'importe quelle variable. Si vous essayez de changer la valeur d'une variable après la fin du bloc de définition de la vue "VIEW", une erreur "view" sera levée.

[% TRY;
     my_web_site.title = 'Nouveau Titre';
   CATCH;
     error;
   END
%]

L'erreur ci-dessus sera rapportée comme suit :

erreur de vue - impossible de mettre à jour un élément dans une vue fermée : title

Il en va de même si vous passez un paramètre à une variable de vue. Ceci est interprété comme une tentative de mise à jour de la variable et le même avertissement sera levé.

[% my_web_site.title('Nouveau Titre') %]    # erreur de vue !

Vous pouvez définir le paramètre "silent" pour que la vue ignore ces paramètres et renvoie simplement la valeur de la variable.

[% VIEW my_web_site
        silent = 1
        title  = title or 'Mon Super Site Web'
        # ... ;
   END
%]
[% my_web_site.title('Blah Blah') %]   # Mon Super Site Web

Alternativement, vous pouvez spécifier qu'une vue n'est pas scellée, permettant la mise à jour des variables existantes et la définition de nouvelles variables.

[% VIEW my_web_site
        sealed = 0
        title  = title or 'Mon Super Site Web'
        # ... ;
   END
%]
[% my_web_site.title('Blah Blah') %]   # Blah Blah
[% my_web_site.title %]                # Blah Blah

Héritage, délégation et réutilisation

Les vues peuvent hériter de vues définies précédemment en utilisant le paramètre "base". Cet exemple montre comment une vue de base est définie qui applique un préfixe "view/default/" à tous les noms de modèles.

[% VIEW my.view.default
        prefix = 'view/default/';
   END
%]

Par conséquent, l'appel :

[% my.view.default.header(title='Bonjour le Monde') %]

est maintenant équivalent à :

[% INCLUDE view/default/header title='Bonjour le Monde' %]

defined which specifies the default view as a base.

[% VIEW my.view.fancy
        base   = my.view.default
        prefix = 'view/fancy/';
   END
%]

Now the directive:

[% my.view.fancy.header(title='Hello World') %]

will resolve to:

[% INCLUDE view/fancy/header title='Hello World' %]

or if that doesn't exist, it will be handled by the base view as:

[% INCLUDE view/default/header title='Hello World' %]

When a parent view is specified via the "base" parameter, the delegation of a view to its parent for fetching templates and accessing user defined variables is automatic. You can also implement your own inheritance, delegation or other reuse patterns by explicitly delegating to other views.

[% BLOCK foo %]
   public foo block
[% END %]
[% VIEW plain %]
   [% BLOCK foo %]
   <plain>[% PROCESS foo %]</plain>
   [% END %]
[% END %]
[% VIEW fancy %]
   [% BLOCK foo %]
   [% plain.foo | replace('plain', 'fancy') %]
   [% END %]
[% END %]
[% plain.foo %]     # <plain>public foo block</plain>
[% fancy.foo %]     # <fancy>public foo block</fancy>

Note that the regular "INCLUDE/PROCESS/WRAPPER" directives work entirely independently of views and will always get the original, unaltered template name rather than any local per-view definition.

Auto-référence

A reference to the view object under definition is available with the "VIEW ... END" block by its specified name and also by the special name '"view"' (similar to the "my $self = shift;" in a Perl method or the '"this"' pointer in C++, etc). The view is initially unsealed allowing any data items to be defined and updated within the "VIEW ... END" block. The view is automatically sealed at the end of the definition block, preventing any view data from being subsequently changed.

(NOTE: sealing should be optional. As well as sealing a view to prevent updates ("SEALED"), it should be possible to set an option in the view to allow external contexts to update existing variables ("UPDATE") or even create totally new view variables ("CREATE")).

[% VIEW fancy %]
   [% fancy.title  = 'My Fancy Title' %]
   [% fancy.author = 'Frank Open' %]
   [% fancy.col    = { bg => '#ffffff', bar => '#a0a0ff' } %]
[% END %]

or

[% VIEW fancy %]
   [% view.title  = 'My Fancy Title' %]
   [% view.author = 'Frank Open' %]
   [% view.col    = { bg => '#ffffff', bar => '#a0a0ff' } %]
[% END %]

It makes no real difference in this case if you refer to the view by its name, '"fancy"', or by the general name, '"view"'. Outside of the view block, however, you should always use the given name, '"fancy"':

[% fancy.title  %]
[% fancy.author %]
[% fancy.col.bg %]

The choice of given name or '"view"' is much more important when it comes to "BLOCK" definitions within a "VIEW". It is generally recommended that you use '"view"' inside a "VIEW" definition because this is guaranteed to be correctly defined at any point in the future when the block gets called. The original name of the view might have long since been changed or reused but the self-reference via '"view"' should always be intact and valid.

Take the following VIEW as an example:

[% VIEW foo %]
   [% view.title = 'Hello World' %]
   [% BLOCK header %]
   Title: [% view.title %]
   [% END %]
[% END %]

Even if we rename the view, or create a new "foo" variable, the header block still correctly accesses the "title" attribute of the view to which it belongs. Whenever a view "BLOCK" is processed, the "view" variable is always updated to contain the correct reference to the view object to which it belongs.

[% bar = foo %]
[% foo = { title => "New Foo" } %]  # no problem
[% bar.header %]                    # => Title: Hello World

Sauvegarde des références aux vues externes

When it comes to view inheritance, it's always a good idea to take a local copy of a parent or delegate view and store it as an attribute within the view for later use. This ensures that the correct view reference is always available, even if the external name of a view has been changed.

[% VIEW plain %]
   ...
[% END %]
[% VIEW fancy %]
   [% view.plain = plain %]
   [% BLOCK foo %]
   [% view.plain.foo | replace('plain', 'fancy') %]
   [% END %]
[% END %]
[% plain.foo %]         # => <plain>public foo block</plain>
[% plain = 'blah' %]    # no problem
[% fancy.foo %]         # => <fancy>public foo block</fancy>

Vues comme présentateurs de données

Another key role of a view is to act as a dispatcher to automatically apply the correct template to present a particular object or data item. This is handled via the print() method.

Here's an example:

[% VIEW foo %]
   [% BLOCK text %]
      Some text: [% item %]
   [% END %]
   [% BLOCK hash %]
      a hash:
      [% FOREACH key = item.keys.sort -%]
         [% key %] => [% item.$key %]
      [% END -%]
   [% END %]
   [% BLOCK list %]
      a list: [% item.sort.join(', ') %]
   [% END %]
[% END %]

We can now use the view to print text, hashes or lists. The print() method includes the right template depending on the typing of the argument (or arguments) passed.

[% some_text = 'I read the news today, oh boy.' %]
[% a_hash    = { house => 'Lords', hall => 'Albert' } %]
[% a_list    = [ 'sure', 'Nobody', 'really' ] %]
[% view.print(some_text) %]
                    # Some text: I read the news today, oh boy.
[% view.print(a_hash) %]
                    # a hash:
                         hall => Albert
                         house => Lords
[% view.print(a_list) %]
                    # a list: Nobody, really, sure

You can also provide templates to print objects of any other class. The class name is mapped to a template name with all non-word character sequences such as '"::"' converted to a single '"_"'.

[% VIEW foo %]
   [% BLOCK Foo_Bar %]
      a Foo::Bar object:
          thingies: [% view.print(item.thingies) %]
           doodahs: [% view.print(item.doodahs)  %]
   [% END %]
[% END %]
[% USE fubar = Foo::Bar(...) %]
[% foo.print(fubar) %]

Note how we use the view object to display various items within the objects ('"thingies"' and '"doodahs"'). We don't need to worry what kind of data these represent (text, list, hash, etc) because we can let the view worry about it, automatically mapping the data type to the correct template.

Views may define their own type => template map.

[% VIEW foo
     map = { TEXT  => 'plain_text',
             ARRAY => 'show_list',
             HASH  => 'show_hash',
             My::Module => 'template_name'
             default    => 'any_old_data'
           }
%]
    [% BLOCK plain_text %]
       ...
    [% END %]
    ...
[% END %]

They can also provide a "default" map entry, specified as part of the "map" hash or as a parameter by itself.

[% VIEW foo
     map     = { ... },
     default = 'whatever'
%]
   ...
[% END %]

or

[% VIEW foo %]
   [% view.map     = { ... }
      view.default = 'whatever'
   %]
   ...
[% END %]

The print() method provides one more piece of magic. If you pass it a reference to an object which provides a present() method, then the method will be called passing the view as an argument. This then gives any object a chance to determine how it should be presented via the view.

package Foo::Bar;
...
sub present {
    my ($self, $view) = @_;
    return "a Foo::Bar object:\n"
         . "thingies: " . $view->print($self->{ _THINGIES }) . "\n"
         . "doodahs: " . $view->print($self->{ _DOODAHS }) . "\n";
}

The object is free to delve deeply into its innards and mess around with its own private data, before presenting the relevant data via the view. In a more complex example, a present() method might walk part of a tree making calls back against the view to present different nodes within the tree. We may not want to expose the internal structure of the tree (because that would break encapsulation and make our presentation code dependant on it) but we want to have some way of walking the tree and presenting items found in a particular manner.

This is known as Structure Shy Traversal. Our view object doesn't require prior knowledge about the internal structure of any data set to be able to traverse it and present the data contained therein. The data items themselves, via the present() method, can implement the internal iterators to guide the view along the right path to presentation happiness.

The upshot is that you can use views to greatly simplify the display of data structures like "XML::DOM" trees. The documentation for the "Template::Plugin::XML::DOM" module contains an example of this. In essence, it looks something like this:

XML source:

<user name="Andy Wardley">
    <project id="iCan" title="iCan, but theyCan't"/>
    <project id="p45"  title="iDid, but theyDidn't"/>
</user>

TT View:

[% VIEW fancy %]
   [% BLOCK user %]
      User: [% item.name %]
            [% item.content(myview) %]
   [% END %]
   [% BLOCK project %]
        Project: [% project.id %] - [% project.name %]
   [% END %]
[% END %]

Generate view:

[% USE dom = XML.DOM %]
[% fancy.print(dom.parse(xml_source)) %]

Output:

User: Andy Wardley
  Project: iCan - iCan, but theyCan't
  Project: p45 - iDid, but th
