Test2::Manual::Tooling::Subtest(3perl) Guide du programmeur Perl Test2::Manual::Tooling::Subtest(3perl)

NOM

Test2::Manual::Tooling::Subtest - Comment implémenter un outil qui utilise les sous-tests.

DESCRIPTION

Les sous-tests sont un moyen agréable de rendre les événements liés visuellement et architecturalement distincts.

QUEL TYPE DE SOUS-TEST AI-JE BESOIN ?

Il existe 2 types de sous-tests. Le premier type concerne les sous-tests avec des coderefs fournis par l'utilisateur, tels que la fonction subtest() elle-même. Le second type concerne les sous-tests qui n'ont pas de coderefs fournis par l'utilisateur.

Alors, lequel des deux vous faut-il ? La réponse est simple : si vous allez permettre à l'utilisateur de définir le sous-test avec son propre bloc de code, vous avez le premier type, sinon vous avez le second.

Dans les deux cas, vous devrez toujours utiliser la même fonction d'API : "Test2::API::run_subtest".

SOUS-TEST AVEC CODEREF FOURNI PAR L'UTILISATEUR

Cet exemple émule la fonction "subtest".

use Test2::API qw/context run_subtest/;
sub my_subtest {
    my ($name, $code) = @_;
    # Comme tout autre outil, vous devez acquérir un contexte, sinon
    # les choses n'indiqueront pas le bon fichier et la bonne ligne.
    my $ctx = context();
    my $bool = run_subtest($name, $code);
    $ctx->release;
    return $bool;
}

Cela semble incroyablement simple... et ça l'est. run_subtest() fait tout le travail difficile pour vous. Cela émettra un événement Test2::Event::Subtest avec les résultats du sous-test. L'événement de sous-test lui-même rapportera le bon fichier et la bonne ligne grâce au contexte que vous avez acquis (même si cela ne semble pas être le cas).

run_subtest() peut accepter des arguments supplémentaires :

run_subtest($name, $code, \%params, @args);
@args
Cela vous permet de passer des arguments au bloc de code qui est exécuté.
\%params
C'est un hashref de paramètres. Actuellement, il y a 3 paramètres possibles :
buffered => $bool
Cela transformera le sous-test en sous-test mis en mémoire tampon de nouveau style. Ce type de sous-test est recommandé, mais pas par défaut.
inherit_trace => $bool
Ceci est utilisé pour les coderefs côté outil.
no_fork => $bool
réagit aux forks/threads à l'intérieur du sous-test lui-même. En général, il est peu probable que vous ayez besoin/vouliez ce paramètre.

SOUS-TEST AVEC CODEREF CÔTÉ OUTIL

Ceci est particulièrement utile si vous souhaitez transformer un outil qui encapsule d'autres outils en un sous-test. Pour cela, nous utiliserons l'outil que nous avons créé dans Test2::Manual::Tooling::Nesting.

use Test2::API qw/context run_subtest/;
sub check_class {
    my $class = shift;
    my $ctx = context();
    my $code = sub {
        my $obj = $class->new;
        is($obj->foo, 'foo', "got foo");
        is($obj->bar, 'bar', "got bar");
    };
    my $bool = run_subtest($class, $code, {buffered => 1, inherit_trace => 1});
    $ctx->release;
    return $bool;
}

La fonction run_subtest() fait tout le travail. Il nous suffit de donner à la fonction un nom, un coderef à exécuter et le paramètre "inherit_trace => 1". Le paramètre "buffered => 1" est facultatif, mais recommandé.

Le paramètre "inherit_trace" indique à l'outil de sous-test que les contextes acquis dans les outils imbriqués doivent utiliser la même trace que le sous-test lui-même. Pour les blocs de code fournis par l'utilisateur, vous n'utilisez pas inherit_trace car vous voulez que les erreurs soient signalées au fichier+ligne fourni par l'utilisateur.
