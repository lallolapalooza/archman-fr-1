Template::Manual::Directives - Directives de modèle

Accès et mise à jour des variables de modèle

GET

La directive "GET" récupère et affiche la valeur de la variable nommée.

[% GET foo %]

Le mot-clé "GET" est facultatif. Une variable peut être spécifiée seule dans une balise de directive.

[% foo %]

La variable peut avoir un nombre illimité d'éléments, chacun séparé par un point. Chaque élément peut avoir des arguments spécifiés entre parenthèses.

[% foo %]
[% bar.baz %]
[% biz.baz(10) %]
...etc...

Voir Template::Manual::Variables pour une discussion complète sur les variables de modèle.

Vous pouvez également spécifier des expressions en utilisant les opérateurs logiques ("and", "or", "not", "?", ":") et mathématiques ("+", "-", "*", "/", "%", "mod", "div").

[% template.title or default.title %]
[% score * 100 %]
[% order.nitems ? checkout(order.total) : 'aucun article' %]

L'opérateur "div" retourne le résultat entier de la division. Les opérateurs "%" et "mod" retournent le modulo (c'est-à-dire le reste) de la division.

[% 15 / 6 %]            # 2.5
[% 15 div 6 %]          # 2
[% 15 mod 6 %]          # 3

CALL

La directive "CALL" est similaire à "GET" pour évaluer la variable nommée, mais n'affiche pas le résultat retourné. Cela peut être utile lorsqu'une variable est liée à une sous-routine ou une méthode d'objet que vous souhaitez appeler mais dont la valeur retournée ne vous intéresse pas.

[% CALL dbi.disconnect %]
[% CALL inc_page_counter(page_count) %]

SET

La directive "SET" vous permet d'attribuer de nouvelles valeurs à des variables existantes ou de créer de nouvelles variables temporaires.

[% SET title = 'Bonjour le monde' %]

Le mot-clé "SET" est également facultatif.

[% title = 'Bonjour le monde' %]

Des variables peuvent se voir attribuer les valeurs d'autres variables, des nombres sans guillemets (2.718), du texte littéral (guillemets simples ') ou du texte entre guillemets (guillemets doubles "). Dans ce dernier cas, toute référence à une variable dans le texte sera interpolée lors de l'évaluation de la chaîne. Les variables doivent être précédées de "$", en utilisant des accolades pour délimiter explicitement le nom de la variable si nécessaire.

[% foo  = 'Foo'  %]               # valeur littérale 'Foo'
[% bar  =  foo   %]               # valeur de la variable 'foo'
[% cost = '$100' %]               # valeur littérale '$100'
[% item = "$bar: ${cost}.00" %]   # valeur "Foo: $100.00"

Plusieurs variables peuvent être assignées dans la même directive et sont évaluées dans l'ordre spécifié. Ainsi, ce qui précède aurait pu être écrit :

[% foo  = 'Foo'
   bar  = foo
   cost = '$100'
   item = "$bar: ${cost}.00"
%]

Des expressions simples peuvent également être utilisées, comme pour "GET".

[% dix    = 10
   vingt = 20
   trente = vingt + dix
   quarante  = 2 * vingt
   cinquante = 100 div 2
   six    = vingt mod 7
%]

Vous pouvez concaténer des chaînes en utilisant l'opérateur de soulignement '_'. En Perl 5, le point "." est utilisé pour la concaténation de chaînes, mais en Perl 6, comme dans Template Toolkit, le point "." sera utilisé comme opérateur d'appel de méthode et le soulignement "_" sera utilisé pour la concaténation de chaînes. Notez que l'opérateur doit être spécifié avec des espaces blancs environnants qui, comme le dit Larry, sont considérés comme une fonctionnalité :

[% copyright = '(C) Copyright' _ annee _ ' ' _ auteur %]

Vous pouvez, bien sûr, obtenir un effet similaire avec l'interpolation de chaînes entre guillemets doubles.

[% copyright = "(C) Copyright $annee $auteur" %]

DEFAULT

La directive "DEFAULT" est similaire à "SET" mais ne met à jour que les variables qui ne sont actuellement pas définies ou qui n'ont pas de valeur "vraie" (au sens de Perl).

[% DEFAULT
    nom = 'Jean Dupont'
    id   = 'jdupont'
%]

Cela peut être particulièrement utile dans des composants de modèle courants pour s'assurer que des valeurs par défaut sensées sont fournies pour des variables autrement indéfinies.

[% DEFAULT
   titre = 'Bonjour le monde'
   bgcol = '#ffffff'
%]
<html>
  <head>
    <title>[% titre %]</title>
  </head>
  <body bgcolor="[% bgcol %]">
    ...etc...

Traitement des fichiers et blocs de modèle

INSERT

La directive "INSERT" est utilisée pour insérer le contenu d'un fichier externe à la position actuelle.

[% INSERT monfichier %]

Aucune tentative n'est faite pour analyser ou traiter le fichier. Le contenu, y compris toute directive de modèle intégrée, est inséré intact.

Le nom de fichier spécifié doit être relatif à l'un des répertoires "INCLUDE_PATH". Les noms de fichiers absolus (c'est-à-dire commençant par "/") et relatifs (c'est-à-dire commençant par ".") peuvent être utilisés si les options "ABSOLUTE" et "RELATIVE" sont définies respectivement. Ces deux options sont désactivées par défaut.

my $template = Template->new({
    INCLUDE_PATH => '/ici:/là',
});
$template->process('monfichier');

monfichier:

[% INSERT foo %]            # recherche /ici/foo puis /là/foo
[% INSERT /etc/passwd %]    # erreur fichier : ABSOLUTE non défini
[% INSERT ../secret %]      # erreur fichier : RELATIVE non défini

Pour plus de commodité, le nom de fichier n'a pas besoin d'être entre guillemets tant qu'il ne contient que des caractères alphanumériques, des tirets bas, des points ou des barres obliques. Les noms contenant d'autres caractères doivent être mis entre guillemets.

[% INSERT misc/legalese.txt            %]
[% INSERT 'dos98/Program Files/stupid' %]

Pour évaluer une variable afin de spécifier un nom de fichier, vous devez explicitement la préfixer avec un "$" ou utiliser l'interpolation de chaîne entre guillemets doubles.

[% language = 'fr'
   legalese = 'misc/legalese.txt'
%]
[% INSERT $legalese %]              # misc/legalese.txt
[% INSERT "$language/$legalese" %]  # fr/misc/legalese.txt

Plusieurs fichiers peuvent être spécifiés en utilisant "+" comme délimiteur. Tous les fichiers doivent être des noms sans guillemets ou des chaînes entre guillemets. Toutes les variables doivent être interpolées dans des chaînes entre guillemets doubles.

[% INSERT legalese.txt + warning.txt %]
[% INSERT  "$legalese" + warning.txt %]  # nécessite des guillemets

INCLUDE

La directive "INCLUDE" est utilisée pour traiter et inclure la sortie d'un autre fichier ou bloc de modèle.

[% INCLUDE header %]

Si un "BLOCK" du nom spécifié est défini dans le même fichier, ou dans un fichier à partir duquel le modèle actuel a été appelé (c'est-à-dire un modèle parent), alors il sera utilisé de préférence à tout fichier du même nom.

[% INCLUDE table %]     # utilise le BLOCK défini ci-dessous
[% BLOCK table %]
   <table>
     ...
   </table>
[% END %]

Si une définition de "BLOCK" n'est pas actuellement visible, alors le nom du modèle doit être un fichier relatif à l'un des répertoires "INCLUDE_PATH", ou un nom de fichier absolu ou relatif si les options "ABSOLUTE"/"RELATIVE" sont activées de manière appropriée. Le

INCLUDE

La directive INCLUDE cite automatiquement le nom de fichier spécifié, comme décrit pour la directive INSERT.

Lorsqu'une variable contient le nom du template pour la directive INCLUDE, elle doit être explicitement précédée de $ ou être mise entre guillemets.

[% myheader = 'my/misc/header' %]
[% INCLUDE   myheader  %]           # 'myheader'
[% INCLUDE  $myheader  %]           # 'my/misc/header'
[% INCLUDE "$myheader" %]           # 'my/misc/header'

Toutes les directives de template contenues dans le fichier seront traitées de la même manière. Toutes les variables actuellement définies seront visibles et accessibles depuis le template inclus.

[% title = 'Hello World' %]
[% INCLUDE header %]
<body>
...

Le fichier header :

<html>
<title>[% title %]</title>

Sortie :

<html>
<title>Hello World</title>
<body>
...

Les définitions de variables locales peuvent être spécifiées après le nom du template, remplaçant temporairement toute variable existante. Les espaces blancs insignifiants sont ignorés dans les directives, ce qui permet d'ajouter des définitions de variables sur la même ligne, sur la suivante, ou réparties sur plusieurs lignes avec des commentaires, si vous le souhaitez.

[% INCLUDE table %]
[% INCLUDE table title="Active Projects" %]
[% INCLUDE table
     title   = "Active Projects"
     bgcolor = "#80ff00"    # chartreuse
     border  = 2
%]

La directive INCLUDE localise (c'est-à-dire copie) toutes les variables avant de traiter le template. Tout changement effectué dans le template inclus n'affectera pas les variables du template qui l'inclut.

[% foo = 10 %]
foo est à l'origine [% foo %]
[% INCLUDE bar %]
foo est toujours [% foo %]
[% BLOCK bar %]
   foo était [% foo %]
   [% foo = 20 %]
   foo est maintenant [% foo %]
[% END %]

Sortie :

foo est à l'origine 10
   foo était 10
   foo est maintenant 20
foo est toujours 10

Note technique : la localisation du stash (c'est-à-dire le processus par lequel les variables sont copiées avant une INCLUDE pour éviter d'être écrasées) n'est que superficielle. L'espace de noms supérieur (hash) est copié, mais aucune tentative n'est faite pour une copie profonde d'autres structures (hashes, tableaux, objets, etc.). Ainsi, une variable foo faisant référence à un hash sera copiée pour créer une nouvelle variable foo, mais pointant vers le même tableau de hashes. Par conséquent, si vous mettez à jour des variables composées (par exemple, foo.bar), vous changerez la copie originale, indépendamment de toute localisation de stash. Si vous ne vous souciez pas de préserver les valeurs des variables ou si vous avez confiance dans les templates que vous incluez, vous pourriez préférer utiliser la directive PROCESS, qui est plus rapide car elle n'effectue aucune localisation.

Vous pouvez spécifier des variables dotées comme variables locales pour une directive INCLUDE. Cependant, gardez à l'esprit qu'en raison des problèmes de localisation expliqués ci-dessus (si vous avez lu la note technique, vous voudrez peut-être la relire ou sauter cette section), les variables ne seront peut-être pas vraiment locales. Si le premier élément du nom de la variable fait déjà référence à un tableau de hashes, la mise à jour de la variable affectera la variable d'origine.

[% foo = {
       bar = 'Baz'
   }
%]
[% INCLUDE somefile foo.bar='Boz' %]
[% foo.bar %]           # Boz

Ce comportement peut être un peu imprévisible (et pourrait être amélioré dans une future version). Si vous savez ce que vous faites avec et que vous êtes sûr que les variables en question sont définies (ou non) comme vous vous y attendez, vous pouvez compter sur cette fonctionnalité pour mettre en œuvre des techniques d'échange global puissantes. Sinon, vous pourriez préférer l'éviter et passer des variables simples (sans points) en paramètres à INCLUDE et à d'autres directives similaires.

Si vous souhaitez traiter plusieurs templates en une seule fois, vous pouvez spécifier le nom de chacun (non cité ou cité, mais pas de variables $ citées) reliés par l'opérateur +. La directive INCLUDE les traitera alors dans l'ordre.

[% INCLUDE html/header + "site/$header" + site/menu
     title = "My Groovy Web Site"
%]

Le stash localisé, puis les templates spécifiés sont traités dans l'ordre, le tout dans le même contexte de variables. Cela le rend légèrement plus rapide que de spécifier plusieurs directives INCLUDE séparées (car le stash n'est cloné qu'une fois au lieu de n fois), mais ce n'est pas aussi sûr, car tout changement dans le premier fichier sera visible dans le second, le troisième, etc. Cela peut être ce que vous voulez, mais peut-être pas.

PROCESS

La directive PROCESS est similaire à INCLUDE, mais elle ne procède à aucune localisation de variables avant de traiter le template. Tout changement apporté aux variables dans le template inclus sera visible dans le template qui l'inclut.

[% foo = 10 %]
foo est [% foo %]
[% PROCESS bar %]
foo est [% foo %]
[% BLOCK bar %]
   [% foo = 20 %]
   foo a été changé en [% foo %]
[% END %]

Sortie :

foo est 10
   foo a été changé en 20
foo est 20

Les paramètres peuvent être spécifiés dans la directive PROCESS, mais ceux-ci deviennent également des changements visibles dans les valeurs actuelles des variables.

[% foo = 10 %]
foo est [% foo %]
[% PROCESS bar
   foo = 20
%]
foo est [% foo %]
[% BLOCK bar %]
   c'est bar, foo est [% foo %]
[% END %]

Sortie :

foo est 10
   c'est bar, foo est 20
foo est 20

La directive PROCESS est légèrement plus rapide que INCLUDE car elle évite la nécessité de localiser (c'est-à-dire copier) le stash avant de traiter le template. Comme avec INCLUDE et INSERT, le premier paramètre n'a pas besoin d'être cité s'il ne contient que des caractères alphanumériques, des traits d'union, des tirets ou des barres obliques. Un préfixe $ peut être utilisé explicitement pour indiquer une variable qui doit être interpolée pour fournir le nom du template :

[% myheader = 'my/misc/header' %]
[% PROCESS myheader %]              # 'myheader'
[% PROCESS $myheader %]              # 'my/misc/header'

Comme avec INCLUDE, plusieurs templates peuvent être spécifiés, séparés par +, et traités dans l'ordre.

[% PROCESS html/header + my/header %]

WRAPPER

Il est courant de vouloir ajouter des en-têtes et des pieds de page communs à des pages ou à des sections d'une page. Par exemple :

[% INCLUDE section/header
   title = 'Quantum Mechanics'
%]
   La mécanique quantique est un sujet très intéressant qui devrait être facilement abordable pour le profane pour le comprendre pleinement.
[% INCLUDE section/footer %]
[% INCLUDE section/header
   title = 'Desktop Nuclear Fusion for under $50'
%]
   Ceci décrit un appareil simple qui génère une électricité significative et durable à partir de l'eau du robinet ordinaire par le processus de fusion nucléaire.
[% INCLUDE section/footer %]

Les composants individuels des templates inclus peuvent ressembler à ceci :

section/header :

<p>
<h2>[% title %]</h2>

section/footer :

</p>

La directive WRAPPER fournit un moyen de simplifier cela. Elle englobe un bloc jusqu'à une directive END qui est traitée en premier pour produire une sortie. Celle-ci est passée au fichier template ou à la directive BLOCK sous le nom de variable `content`.

[% WRAPPER section
   title = 'Quantum Mechanics'
%]
   La mécanique quantique est un sujet très intéressant qui devrait être facilement abordable pour le profane pour le comprendre pleinement.
[% END %]
[% WRAPPER section
   title = 'Desktop Nuclear Fusion for under $50'
%]
   Ceci décrit un appareil simple qui génère une électricité significative et durable à partir de l'eau du robinet ordinaire par le processus de fusion nucléaire.
[% END %]

Le seul template 'section' peut alors être défini comme suit :

<h2>[% title %]</h2>
<p>
  [% content %]
</p>

Comme d'autres directives de bloc, elle peut être utilisée en notation d'effet secondaire :

[% INSERT legalese.txt WRAPPER big_bold_table %]

Il est également possible de spécifier plusieurs templates pour une directive WRAPPER. L'ordre de spécification indique les wrappers les plus externes aux plus internes. Par exemple, étant donné les définitions de bloc suivantes :

[% BLOCK bold   %]<b>[% content %]</b>[% END %]
[% BLOCK italic %]<i>[% content %]</i>[% END %]

la directive

[% WRAPPER bold+italic %]Hello World[% END %]

générerait la sortie suivante :

<b><i>Hello World</i></b>

BLOCK

La construction BLOCK...END peut être utilisée pour définir des blocs de composants de template qui peuvent être traités avec les directives INCLUDE, PROCESS et WRAPPER.

[% BLOCK tabrow %]
<tr>
  <td>[% name %]<td>
  <td>[% email %]</td>
</tr>
[% END %]
<table>
  [% PROCESS tabrow  name='Fred'  email='fred@nowhere.com' %]
  [% PROCESS tabrow  name='Alan'  email='alan@nowhere.com' %]
</table>

Une définition de bloc peut être utilisée avant qu'elle ne soit définie, à condition que la définition soit dans le même fichier. La définition du bloc elle-même ne produit aucune sortie.

[% PROCESS tmpblk %]
[% BLOCK tmpblk %] Ceci est OK [% END %]

Vous pouvez utiliser un bloc anonyme pour capturer la sortie d'un fragment de template.

[% julius = BLOCK %]
   Et l'esprit de César, méditant la vengeance,
   Avec Ate à ses côtés sort de l'enfer,
   Quelque chose dans ces confins avec une voix de roi
   Crie 'Havoc', et lâche le chien de guerre ;
   Que cette offense répugnante soit déchaînée
   Avec des serpents cadavéreux, pleurant pour être enterrés.
[% END %]

Comme un bloc nommé, il peut contenir toute autre directive de template qui sera traitée lors de la définition du bloc. La sortie du bloc peut être utilisée comme indiqué.

généré par le bloc est ensuite attribué à la variable "julius".

Des "BLOCK"s anonymes peuvent également être utilisés pour définir des macros de bloc. Le bloc englobant est traité à chaque appel de la macro.

[% MACRO locate BLOCK %]
   Le [% animal %] était assis sur le [% place %].
[% END %]
[% locate(animal='chat', place='tapis') %]    # Le chat était assis sur le tapis
[% locate(animal='chien', place='tronc') %]    # Le chien était assis sur le tronc

Traitement conditionnel

SI / SAUF SI / SINON SI / SINON

Les directives "SI" et "SAUF SI" peuvent être utilisées pour traiter ou ignorer un bloc en fonction d'une condition d'exécution.

[% SI frames %]
   [% INCLUDE cadres %]
[% END %]
[% SAUF SI mode_texte %]
   [% INCLUDE grandlogo %]
[% END %]

Plusieurs conditions peuvent être jointes avec des blocs "SINON SI" et/ou "SINON".

[% SI age < 10 %]
   Bonjour [% nom %], est-ce que ta mère sait que tu utilises son compte AOL ?
[% SINON SI age < 18 %]
   Désolé, tu n'es pas assez vieux pour entrer
   (et trop bête pour mentir sur ton âge)
[% SINON %]
   Bienvenue [% nom %].
[% END %]

Les opérateurs conditionnels et booléens suivants peuvent être utilisés :

== != < <= > >= && || ! et ou non

Les conditions peuvent être arbitrairement complexes et sont évaluées avec la même précédence qu'en Perl. Les parenthèses peuvent être utilisées pour déterminer explicitement l'ordre d'évaluation.

# exemple complexe ridiculement exagéré
[% SI (nom == 'admin' || uid <= 0) && mode == 'debug' %]
   Je suis confus.
[% SINON SI plus > moins %]
   C'est plus ou moins correct.
[% END %]

Les opérateurs "et", "ou" et "non" sont fournis comme alias pour "&&", "||" et "!", respectivement. Contrairement à Perl, qui traite "et", "ou" et "non" comme des versions séparées, de plus faible priorité, des autres opérateurs, Template Toolkit effectue une substitution directe de "et" pour "&&", et ainsi de suite. Cela signifie que "et", "ou" et "non" ont la même priorité d'opérateur que "&&", "||" et "!".

COMMUTATEUR / CAS

La construction "COMMUTATEUR" / "CAS" peut être utilisée pour effectuer un test conditionnel multi-voies. La directive "COMMUTATEUR" attend une expression qui est d'abord évaluée puis comparée à chaque instruction CASE tour à tour. Chaque directive "CAS" doit contenir une seule valeur ou une liste de valeurs qui doivent correspondre. "CAS" peut également être laissée vide ou écrite comme "[% CAS DÉFAUT %]" pour spécifier une correspondance par défaut. Seulement un "CAS" correspond, il n'y a pas de chute entre les instructions "CAS".

[% COMMUTATEUR mon_variable %]
[%   CAS 'valeur1' %]
       ...
[%   CAS ['valeur2', 'valeur3'] %]   # valeurs multiples
       ...
[%   CAS mes_hachages.clés %]            # idem
       ...
[%   CAS %]                        # par défaut
       ...
[% END %]

Traitement des boucles

POUR CHAQUE

La directive "POUR CHAQUE" itérera à travers les éléments d'une liste, traitant le bloc inclus pour chacun d'eux.

[% foo   = 'Foo'
   items = [ 'un', 'deux', 'trois' ]
%]
Choses :
[% POUR CHAQUE chose DANS [ foo 'Bar' "$foo Baz" ] %]
   * [% chose %]
[% END %]
Éléments :
[% POUR CHAQUE i DANS items %]
   * [% i %]
[% END %]
Trucs :
[% trucs = [ foo "$foo Bar" ] %]
[% POUR CHAQUE s DANS trucs %]
   * [% s %]
[% END %]

sortie :

Choses :
  * Foo
  * Bar
  * Foo Baz
Éléments :
  * un
  * deux
  * trois
Trucs :
  * Foo
  * Foo Bar

Vous pouvez également utiliser "=" au lieu de "DANS" si vous préférez.

[% POUR CHAQUE i = items %]

Lorsque la directive "POUR CHAQUE" est utilisée sans spécifier de variable cible, toutes les valeurs itérées qui sont des références de hachage seront automatiquement importées.

[% liste_utilisateurs = [
    { id => 'tom',   nom => 'Thomas'  },
    { id => 'dick',  nom => 'Richard'  },
    { id => 'larry', nom => 'Lawrence' },
   ]
%]
[% POUR CHAQUE utilisateur DANS liste_utilisateurs %]
   [% utilisateur.id %] [% utilisateur.nom %]
[% END %]

forme courte :

[% POUR CHAQUE liste_utilisateurs %]
   [% id %] [% nom %]
[% END %]

Notez que cette utilisation particulière crée un contexte de variable localisé pour empêcher les clés de hachage importées d'écraser les variables existantes. Les définitions importées et toutes les autres variables définies dans une telle boucle "POUR CHAQUE" seront perdues à la fin de la boucle, lorsque le contexte et les valeurs de variables précédents seront restaurés.

Cependant, en fonctionnement normal, la variable de boucle reste dans la portée après la fin de la boucle "POUR CHAQUE" (avertissement : écrasant toute variable précédemment dans la portée). Ceci est utile car la variable de boucle est secrètement un objet itérateur (voir ci-dessous) et peut être utilisée pour analyser la dernière entrée traitée par la boucle.

La directive "POUR CHAQUE" peut également être utilisée pour itérer sur les entrées d'un tableau de hachage. Chaque entrée du hachage est retournée dans l'ordre trié (basé sur la clé) sous forme de tableau de hachage contenant des éléments 'clé' et 'valeur'.

[% utilisateurs = {
     tom   => 'Thomas',
     dick  => 'Richard',
     larry => 'Lawrence',
   }
%]
[% POUR CHAQUE u DANS utilisateurs %]
   * [% u.clé %] : [% u.valeur %]
[% END %]

Sortie :

* dick : Richard
* larry : Lawrence
* tom : Thomas

La directive "SUIVANT" démarre la prochaine itération dans la boucle "POUR CHAQUE".

[% POUR CHAQUE utilisateur DANS liste_utilisateurs %]
   [% SUIVANT SI utilisateur.estinvité %]
   Nom : [% utilisateur.nom %]    Email : [% utilisateur.email %]
[% END %]

La directive "DERNIER" peut être utilisée pour quitter prématurément la boucle. "CASSÉ" est également fourni comme alias pour "DERNIER".

[% POUR CHAQUE résultat DANS résultats.nsort('score').reverse %]
   [% DERNIER SI résultat.score < 50 %]
   [% résultat.score %] : [% résultat.url %]
[% END %]

La directive "POUR CHAQUE" est implémentée à l'aide du module Template::Iterator. Une référence à l'objet itérateur pour une directive "POUR CHAQUE" est implicitement disponible dans la variable "boucle". Les méthodes suivantes peuvent être appelées sur l'itérateur "boucle".

taille()      nombre d'éléments dans la liste
max()       indice du dernier élément (taille - 1)
index()     indice de l'itération actuelle de 0 à max()
compteur()  compteur d'itération de 1 à taille() (c'est-à-dire index() + 1)
premier()     vrai si l'itération actuelle est la première
dernier()     vrai si l'itération actuelle est la dernière
précédent()  retourne l'élément précédent dans la liste
suivant()   retourne l'élément suivant dans la liste

Voir Template::Iterator pour plus de détails.

Exemple :

[% POUR CHAQUE élément DANS [ 'truc', 'machin', 'chose' ] -%]
   [%- "<ul>\n" SI boucle.premier %]
   <li>[% boucle.compteur %]/[% boucle.taille %] : [% élément %]
   [%- "</ul>\n" SI boucle.dernier %]
[% END %]

Sortie :

<ul>
<li>1/3 : truc
<li>2/3 : machin
<li>3/3 : chose
</ul>

Les boucles imbriquées fonctionneront comme prévu, la variable "boucle" faisant référence correctement à la boucle la plus interne et étant restaurée à toute valeur précédente (c'est-à-dire une boucle externe) à la fin de la boucle.

[% POUR CHAQUE groupe DANS liste_groupes;
     # boucle => itérateur de groupe
     "Groupes:\n" SI boucle.premier;
     POUR CHAQUE utilisateur DANS groupe.liste_utilisateurs;
        # boucle => itérateur d'utilisateur
        "$boucle.compteur : $utilisateur.nom\n";
     END;
     # boucle => itérateur de groupe
     "Fin des Groupes\n" SI boucle.dernier;
   END
%]

Le plugin "itérateur" peut également être utilisé pour créer explicitement un objet itérateur. Cela peut être utile dans les boucles imbriquées où vous devez conserver une référence à l'itérateur externe dans la boucle interne. Le plugin itérateur vous permet effectivement de créer un itérateur sous un nom autre que "boucle". Voir Template::Plugin::Iterator pour plus de détails.

[% UTILISER giter = itérateur(liste_groupes) %]
[% POUR CHAQUE groupe DANS giter %]
   [% POUR CHAQUE utilisateur DANS groupe.liste_utilisateurs %]
         utilisateur #[% boucle.compteur %] dans
         groupe [% giter.compteur %] est
         nommé [% utilisateur.nom %]
   [% END %]
[% END %]

TANT QUE

La directive "TANT QUE" peut être utilisée pour traiter de manière répétée un bloc de modèle tant qu'une expression conditionnelle s'évalue comme vraie. L'expression peut être arbitrairement complexe comme pour "SI" / "SAUF SI".

[% TANT QUE total < 100 %]
   ...
   [% total = calculer_nouveau_total %]
[% END %]

Une assignation peut être enfermée dans des parenthèses pour évaluer la valeur assignée.

[% TANT QUE (utilisateur = obtenir_prochain_enregistrement_utilisateur) %]
   [% utilisateur.nom %]
[% END %]

La directive "SUIVANT" peut être utilisée pour démarrer la prochaine itération d'une boucle "TANT QUE" et "CASSÉ" peut être utilisée pour sortir de la boucle, toutes deux comme pour "POUR CHAQUE".

Template Toolkit utilise un compteur de sécurité pour empêcher les boucles "TANT QUE" incontrôlables qui ne se termineraient pas autrement. Si la boucle dépasse 1000 itérations, une exception "undef" sera levée, rapportant l'erreur :

Boucle TANT QUE terminée (> 1000 itérations)

Le $Template::Directive::WHILE_MAX variable contrôle ce comportement et peut être réglé sur une valeur plus élevée si nécessaire.

Filtres, Plugins, Macros et Perl

FILTER

La directive "FILTER" peut être utilisée pour post-traiter la sortie d'un bloc. Un certain nombre de filtres standard sont fournis avec le Template Toolkit. Le filtre "html", par exemple, échappe les caractères '<', '>' et '&' pour les empêcher d'être interprétés comme des balises HTML ou des marqueurs d'entité.

[% FILTER html %]
   Le texte HTML peut contenir des caractères < et >
   qui doivent être convertis en entités HTML correctes.
[% END %]

sortie :

Le texte HTML peut contenir des caractères &lt; et &gt;
qui doivent être convertis en entités HTML correctes.

La directive "FILTER" peut également suivre diverses autres directives non-blocs. Par exemple :

[% INCLUDE mytext FILTER html %]

Le caractère "|" peut également être utilisé comme alias pour "FILTER".

[% INCLUDE mytext | html %]

Plusieurs filtres peuvent être chaînés et seront appelés séquentiellement.

[% INCLUDE mytext FILTER html FILTER html_para %]

ou

[% INCLUDE mytext | html | html_para %]

Les filtres se présentent en deux saveurs, connues sous le nom de 'statique' ou 'dynamique'. Un filtre statique est une simple sous-routine qui accepte une chaîne de caractères comme seul argument et retourne le texte modifié. Le filtre "html" est un exemple de filtre statique, implémenté comme suit :

sub html_filter {
    my $text = shift;
    for ($text) {
        s/&/&amp;/g;
        s/</&lt;/g;
        s/>/&gt;/g;
    }
    return $text;
}

Les filtres dynamiques peuvent accepter des arguments qui sont spécifiés lors de l'appel du filtre à partir d'un modèle. Le filtre "repeat" en est un exemple, acceptant un argument numérique qui spécifie le nombre de fois que le texte d'entrée doit être répété.

[% FILTER repeat(3) %]blah [% END %]

sortie :

blah blah blah

Ceux-ci sont implémentés comme des 'usines' de filtres. La sous-routine d'usine reçoit une référence vers l'objet Template::Context actuel ainsi que tous les arguments supplémentaires spécifiés. Elle doit ensuite retourner une référence de sous-routine (par exemple, une fermeture) qui implémente le filtre. L'usine de filtres "repeat" est implémentée comme ceci :

sub repeat_filter_factory {
    my ($context, $iter) = @_;
    $iter = 1 unless defined $iter;
    return sub {
        my $text = shift;
        $text = '' unless defined $text;
        return join('\n', $text) x $iter;
    }
}

L'option "FILTERS", décrite dans Template::Manual::Config, permet de définir des filtres personnalisés lors de l'instanciation d'un objet Template. La méthode define_filter() permet de définir d'autres filtres à tout moment.

Lors de l'utilisation d'un filtre, il est possible de lui assigner un alias pour une utilisation ultérieure. Ceci est particulièrement utile pour les filtres dynamiques que l'on souhaite réutiliser avec la même configuration.

[% FILTER echo = repeat(2) %]
Y a-t-il quelqu'un ?
[% END %]
[% FILTER echo %]
Mère, dois-je construire un mur ?
[% END %]

Sortie :

Y a-t-il quelqu'un ?
Y a-t-il quelqu'un ?
Mère, dois-je construire un mur ?
Mère, dois-je construire un mur ?

La directive "FILTER" met automatiquement entre guillemets le nom du filtre. Comme avec "INCLUDE" et autres, vous pouvez utiliser une variable pour fournir le nom du filtre, préfixé par "$".

[% myfilter = 'html' %]
[% FILTER $myfilter %]      # équivalent à [% FILTER html %]
   ...
[% END %]

Une variable de modèle peut également être utilisée pour définir une sous-routine de filtre statique. Cependant, le Template Toolkit appellera automatiquement toute sous-routine liée à une variable et utilisera la valeur retournée. Ainsi, l'exemple ci-dessus pourrait être implémenté comme suit :

my $vars = {
    myfilter => sub { return 'html' },
};

modèle :

[% FILTER $myfilter %]      # équivalent à [% FILTER html %]
   ...
[% END %]

Pour définir une variable de modèle qui s'évalue à une référence de sous-routine pouvant être utilisée par la directive "FILTER", vous devez créer une sous-routine qui, lorsqu'elle est appelée automatiquement par le Template Toolkit, retourne une autre référence de sous-routine qui peut ensuite être utilisée pour effectuer l'opération de filtrage. Notez que seuls les filtres statiques peuvent être implémentés de cette manière.

my $vars = {
    myfilter => sub { \&my_filter_sub },
};
sub my_filter_sub {
    my $text = shift;
    # faire quelque chose
    return $text;
}

modèle :

[% FILTER $myfilter %]
   ...
[% END %]

Alternativement, vous pouvez "blesser" une référence de sous-routine dans une classe (n'importe quelle classe fera l'affaire) pour tromper le Template Toolkit en lui faisant croire qu'il s'agit d'un objet plutôt que d'une sous-routine. Cela contournera alors la magie automatique "appeler une sous-routine pour retourner une valeur".

my $vars = {
    myfilter => bless(\&my_filter_sub, 'anything_you_like'),
};

modèle :

[% FILTER $myfilter %]
   ...
[% END %]

Les filtres liés aux variables de modèle restent locaux au contexte de variable dans lequel ils sont définis. C'est-à-dire, si vous définissez un filtre dans un bloc "PERL" au sein d'un modèle chargé via "INCLUDE", alors la définition du filtre n'existera que jusqu'à la fin de ce modèle, lorsque le cache sera dé-localisé, restaurant l'état précédent de la variable. Si vous souhaitez définir un filtre qui persiste pendant toute la durée de vie du processeur, ou définir des usines de filtres dynamiques supplémentaires, vous pouvez appeler la méthode define_filter() sur l'objet Template::Context actuel.

Voir Template::Manual::Filters pour une liste complète des filtres disponibles, leurs descriptions et exemples d'utilisation.

USE

La directive "USE" peut être utilisée pour charger et initialiser des modules d'extension "plugins".

[% USE myplugin %]

Un plugin est un module Perl régulier qui respecte une interface orientée objet particulière, lui permettant d'être chargé et utilisé automatiquement par le Template Toolkit. Pour plus de détails sur cette interface et des informations sur l'écriture de plugins, consultez Template::Plugin.

Un certain nombre de plugins standard sont inclus avec le Template Toolkit (voir ci-dessous et Template::Manual::Plugins). Les noms de ces plugins standard ne sont pas sensibles à la casse.

[% USE CGI   %]        # => Template::Plugin::CGI
[% USE Cgi   %]        # => Template::Plugin::CGI
[% USE cgi   %]        # => Template::Plugin::CGI

Vous pouvez également définir d'autres plugins en utilisant l'option "PLUGINS".

my $tt = Template->new({
    PLUGINS => {
        foo => 'My::Plugin::Foo',
        bar => 'My::Plugin::Bar',
    },
});

La convention recommandée est de spécifier ces noms de plugins en minuscules. Le Template Toolkit recherche d'abord une correspondance exacte sensible à la casse, puis essaie la conversion en minuscules du nom spécifié.

[% USE Foo %]      # recherche 'Foo' puis 'foo'

Si vous définissez tous vos "PLUGINS" avec des noms en minuscules, ils seront trouvés quelle que soit la manière dont l'utilisateur spécifie le nom dans la directive "USE". Si, en revanche, vous définissez vos "PLUGINS" avec des noms en majuscules ou mixtes, alors le nom spécifié dans la directive "USE" doit correspondre exactement à la casse.

Si le plugin n'est pas défini dans les plugins standard ($Template::Plugins::STD_PLUGINS) ni via l'option "PLUGINS", alors le "PLUGIN_BASE" est recherché.

Dans ce cas, le nom du plugin *est* sensible à la casse. Il est ajouté à chacun des espaces de noms de modules "PLUGIN_BASE" (par défaut : "Template::Plugin") pour construire un nom de module complet qu'il tente de localiser et de charger. Tous les points, '"."', dans le nom seront convertis en '"::"'.

[% USE MyPlugin %]     #  => Template::Plugin::MyPlugin
[% USE Foo.Bar  %]     #  => Template::Plugin::Foo::Bar

L'option "LOAD_PERL" (désactivée par défaut) offre un moyen supplémentaire par lequel des modules Perl externes peuvent être chargés. Si un module Perl régulier (c'est-à-dire pas un "Template::Plugin::*" ou un autre module relatif à un "PLUGIN_BASE") prend en charge une interface orientée objet et un constructeur new(), alors il peut être chargé et instancié automatiquement. L'exemple trivial suivant montre comment le module IO::File pourrait être utilisé.

[% USE file = IO.File('/tmp/mydata') %]
[% WHILE (line = file.getline) %]
   <!-- [% line %] -->
[% END %]

Tous les paramètres supplémentaires fournis entre parenthèses après le nom du plugin seront également passés au constructeur new(). Une référence vers l'objet Template::Context actuel est passée comme premier paramètre.

[% USE MyPlugin('foo', 123) %]

équivalent à :

Template::Plugin::MyPlugin->new($context, 'foo', 123);

La seule exception est lorsqu'un module est chargé via l'option "LOAD_PERL". Dans ce cas, la référence $context n'est *pas* passée au constructeur new(). Cela est basé sur l'hypothèse que le module est un module Perl régulier plutôt qu'un plugin Template Toolkit, donc il ne s'attend pas à une référence de contexte et ne saurait quoi en faire de toute façon.

Des paramètres nommés peuvent également être spécifiés. Ceux-ci sont regroupés dans une table de hachage qui est passée par référence comme dernier paramètre au constructeur, conformément à l'interface générale d'appel de code.

[% USE url('/cgi-bin/foo', mode='submit', debug=1) %]

équivalent à :

Template::Plugin::URL->new(
    $context,
    '/cgi-bin/foo'
    { mode => 'submit', debug => 1 }
);

Le plugin peut représenter n'importe quel type de données ; une simple variable, une table de hachage, une liste ou une référence de code, mais dans le cas général, ce sera une référence d'objet. Les méthodes peuvent être appelées sur l'objet (ou les membres pertinents du type de données spécifique) de la manière habituelle :

[% USE table(my
data, lignes=3) %] [% POUR TOUS les lignes IN tableau.lignes %] <tr> [% POUR TOUS les éléments IN lignes %] <td>[% élément %]</td> [% FIN %] </tr> [% FIN %]

Un nom alternatif peut être fourni pour le plugin afin qu'il puisse être référencé :

[% UTILISER scores = tableau(myscores, cols=5) %]
[% POUR TOUS les lignes IN scores.lignes %]
   ...
[% FIN %]

Vous pouvez utiliser cette approche pour créer plusieurs objets plugin avec des configurations différentes. Cet exemple montre comment le plugin format est utilisé pour créer des sous-routines liées à des variables pour formater du texte selon printf().

[% UTILISER bold = formater('<b>%s</b>') %]
[% UTILISER ital = formater('<i>%s</i>') %]
[% bold('Ceci est en gras')   %]
[% ital('Ceci est en italique') %]

Sortie :

<b>Ceci est en gras</b>
<i>Ceci est en italique</i>

Cet autre exemple montre comment le plugin URL peut être utilisé pour construire des URLs dynamiques à partir d'une partie de base et de paramètres de requête optionnels.

[% UTILISER mycgi = URL('/cgi-bin/foo.pl', debug=1) %]
<a href="[% mycgi %]">...
<a href="[% mycgi(mode='submit') %]"...

Sortie :

<a href="/cgi-bin/foo.pl?debug=1">...
<a href="/cgi-bin/foo.pl?mode=submit&debug=1">...

Le plugin CGI est un exemple de celui qui délègue à un autre module Perl. Dans ce cas, au module "CGI" de Lincoln Stein. Toutes les méthodes fournies par le module "CGI" sont disponibles via le plugin.

[% UTILISER CGI;
   CGI.debut_formulaire;
   CGI.groupe_cases_a_cocher( nom   = 'couleurs',
                       valeurs = [ 'rouge' 'vert' 'bleu' ] );
   CGI.menu_deroulant( nom   = 'elements',
                       valeurs = [ 'foo' 'bar' 'baz' ] );
   CGI.fin_formulaire
%]

Voir Template::Manual::Plugins pour plus d'informations sur les plugins distribués avec la boîte à outils ou disponibles sur CPAN.

MACRO

La directive "MACRO" vous permet de définir une directive ou un bloc de directives qui est ensuite évalué à chaque appel de la macro.

[% MACRO header INCLURE header %]

Appeler la macro comme suit :

[% header %]

est alors équivalent à :

[% INCLURE header %]

Les macros peuvent recevoir des paramètres nommés lors de leur appel. Ces valeurs restent locales à la macro.

[% header(titre='Bonjour le Monde') %]

équivalent à :

[% INCLURE header titre='Bonjour le Monde' %]

Une définition de "MACRO" peut inclure des noms de paramètres. Les valeurs passées aux macros sont alors mappées à ces variables locales. D'autres paramètres nommés peuvent suivre.

[% MACRO header(titre) INCLURE header %]
[% header('Bonjour le Monde') %]
[% header('Bonjour le Monde', bgcol='#123456') %]

équivalent à :

[% INCLURE header titre='Bonjour le Monde' %]
[% INCLURE header titre='Bonjour le Monde' bgcol='#123456' %]

Voici un autre exemple, définissant une macro pour afficher des nombres en groupes de 3 séparés par des virgules, en utilisant la méthode virtuelle chunk et join.

[% MACRO nombre(n) OBTENIR n.chunk(-3).join(',') %]
[% nombre(1234567) %]    # 1,234,567

Une "MACRO" peut précéder n'importe quelle directive et doit être conforme à la structure de la directive.

[% MACRO header SI frames %]
   [% INCLURE frames/header %]
[% SINON %]
   [% INCLURE header %]
[% FIN %]
[% header %]

Une "MACRO" peut également être définie comme un "BLOCK" anonyme. Le bloc sera évalué à chaque appel de la macro.

[% MACRO header BLOCK %]
   ...contenu...
[% FIN %]
[% header %]

Si vous avez l'option "EVAL_PERL" activée, vous pouvez même définir une "MACRO" comme un bloc "PERL" (voir ci-dessous) :

[% MACRO triple(n) PERL %]
     mon $n = $stash->get('n');
     imprimer $n * 3;
[% FIN -%]

PERL

(pour le lecteur avancé)

La directive "PERL" est utilisée pour marquer le début d'un bloc contenant du code Perl pour évaluation. L'option "EVAL_PERL" doit être activée pour que le code Perl soit évalué, sinon une exception "perl" sera levée avec le message '"EVAL_PERL non défini"'.

Le code Perl est évalué dans le package "Template::Perl". La variable du package $context contient une référence à l'objet Template::Context actuel. Cela peut être utilisé pour accéder aux fonctionnalités de la boîte à outils Template pour traiter d'autres templates, charger des plugins, des filtres, etc. Voir Template::Context pour plus de détails.

[% PERL %]
   imprimer $context->inclure('monfichier');
[% FIN %]

La variable $stash contient une référence à l'objet stash de haut niveau qui gère les variables du template. Via cela, les valeurs des variables peuvent être récupérées et mises à jour. Voir Template::Stash pour plus de détails.

[% PERL %]
   $stash->set(foo => 'bar');
   imprimer "valeur de foo : ", $stash->get('foo');
[% FIN %]

Sortie :

valeur de foo : bar

La sortie est générée à partir du bloc "PERL" en appelant print(). Notez que le handle "Template::Perl::PERLOUT" est sélectionné (lié à un tampon de sortie) au lieu de "STDOUT".

[% PERL %]
   imprimer "foo\n";                           # OK
   imprimer PERLOUT "bar\n";                   # OK, identique à ci-dessus
   imprimer Template::Perl::PERLOUT "baz\n";   # OK, identique à ci-dessus
   imprimer STDOUT "qux\n";                    # INCORRECT !
[% FIN %]

Le bloc "PERL" peut contenir d'autres directives de template. Celles-ci sont traitées avant que le code Perl ne soit évalué.

[% nom = 'Fred Smith' %]
[% PERL %]
   imprimer "[% nom %]\n";
[% FIN %]

Ainsi, le code Perl dans l'exemple ci-dessus est évalué comme suit :

imprimer "Fred Smith\n";

Des exceptions peuvent être levées depuis des blocs "PERL" en utilisant die(). Elles seront correctement capturées par des blocs "TRY" enveloppants.

[% TRY %]
   [% PERL %]
      die "rien pour vivre\n";
   [% FIN %]
[% CATCH %]
   erreur : [% erreur.info %]
[% FIN %]

sortie :
erreur : rien pour vivre

RAWPERL

(pour le lecteur très avancé)

L'analyseur Template Toolkit lit un template source et génère le texte d'une sous-routine Perl en sortie. Il utilise ensuite eval() pour l'évaluer en une référence de sous-routine. Cette sous-routine est ensuite appelée pour traiter le template, en passant une référence à l'objet Template::Context actuel à travers lequel les fonctionnalités de la boîte à outils Template peuvent être accessibles. La référence de la sous-routine peut être mise en cache, permettant de traiter le template de manière répétée sans nécessiter d'analyse supplémentaire.

Par exemple, un template tel que :

[% TRAITER  header %]
Le [% animal %] s'est assis sur le [% lieu %]
[% TRAITER  footer %]

est converti en la définition de sous-routine Perl suivante :

sous {
    mon $contexte = décalage;
    mon $virement   = $contexte->virement;
    mon $sortie  = '';
    mon $erreur;
    eval { BLOC : {
        $sortie .=  $contexte->traiter('header');
        $sortie .=  "Le ";
        $sortie .=  $virement->obtenir('animal');
        $sortie .=  " s'est assis sur le ";
        $sortie .=  $virement->obtenir('lieu');
        $sortie .=  $contexte->traiter('footer');
        $sortie .=  "\n";
    } };
    si ($@) {
        $erreur = $contexte->capturer($@, \$sortie);
        mourir $erreur sauf si $erreur->type eq 'retour';
    }
    retour $sortie;
}

Pour examiner le code Perl généré, comme dans l'exemple ci-dessus, définissez la variable du package $Template::Parser::DEBUG à n'importe quelle valeur vraie. Vous pouvez également définir la variable $Template::Directive::PRETTY à vraie pour que le code soit formaté de manière lisible pour une consommation humaine. Le code source de chaque sous-routine de template générée sera imprimé sur "STDERR" lors de la compilation (c'est-à-dire la première fois qu'un template est utilisé).

$Template::Parser::DEBUG = 1;
$Template::Directive::PRETTY = 1;
$template->traiter($fichier, $vars)
    || mourir $template->erreur(), "\n";

La construction "PERL" ... "END" permet d'intégrer du code Perl dans un template lorsque l'option "EVAL_PERL" est définie. Il est évalué à "l'exécution" en utilisant eval() chaque fois que la sous-routine du template est appelée. Ceci est intrinsèquement flexible, mais pas aussi efficace qu'il pourrait l'être, surtout dans un environnement serveur persistant où un template peut être traité de nombreuses fois.

La directive "RAWPERL" vous permet d'écrire du code Perl qui est intégré directement dans le texte de la sous-routine Perl générée. Il est évalué une fois au moment de la compilation et est stocké sous forme de cache dans le cadre de la sous-routine compilée du template. Cela rend les blocs "RAWPERL" plus efficaces que les blocs "PERL".

L'inconvénient est que vous devez coder beaucoup plus près du métal. Par exemple, dans un bloc "PERL" vous pouvez appeler print() pour générer une sortie. Les blocs "RAWPERL" n'offrent pas un tel luxe. Le code est inséré directement dans le texte de la sous-routine générée et doit se conformer à la convention d'ajout à la variable $output.

[% TRAITER  header %]
[% RAWPERL %]
   $output .= "Une sortie\n";
   ...
   $output .= "Une autre sortie\n";
[% FIN %]

La section critique de la sous-routine générée pour cet exemple ressemblerait alors à quelque chose comme :

...
eval { BLOC : {
    $output .=  $contexte->traiter('header');
    $output .=  "\n";
    $output .= "Une sortie\n";
    ...
    $output .= "Une autre sortie\n";
    $output .=  "\n";
} };
...

Comme pour les blocs "PERL", les références $context et $stash sont prédéfinies et disponibles pour utilisation dans le code "RAWPERL".

Gestion des Exceptions et Contrôle de Flux

ESSAI / LANCER / ATTTRAPER / FINAL

ESSAI / LANCER / ATTTRAPER / FINAL

(matériel plus avancé)

Le Template Toolkit prend en charge la gestion des exceptions imbriquées et entièrement fonctionnelle. La directive "ESSAI" introduit une portée de gestion des exceptions qui se poursuit jusqu'à la directive "FIN" correspondante. Toute erreur survenant dans ce bloc sera interceptée et pourra être gérée par l'un des blocs "ATTTRAPER" définis.

[% ESSAI %]
   ...blablabla...
   [% APPEL somecode %]
   ...etc...
   [% INCLURE someblock %]
   ...et ainsi de suite...
[% ATTTRAPER %]
   Une erreur s'est produite !
[% FIN %]

Les erreurs sont émises comme des exceptions (objets de la classe "Template::Exception") qui contiennent deux champs :

  • "type"
  • "info"

Le champ "type" est utilisé pour indiquer le type d'erreur qui s'est produit. Il s'agit d'une chaîne de caractères simple pouvant contenir des lettres, des chiffres, des '_' ou des '.'. Le champ "info" contient des informations sur l'erreur indiquant ce qui s'est réellement passé. Dans un bloc "ATTTRAPER", l'objet d'exception est attribué à la variable "erreur". Vous pouvez accéder directement aux champs "type" et "info".

[% mydsn = 'dbi:MySQL:foobar' %]
...
[% ESSAI %]
   [% UTILISER DBI(mydsn) %]
[% ATTTRAPER %]
   ERREUR ! Type : [% erreur.type %]
          Informations : [% erreur.info %]
[% FIN %]

Sortie (en supposant une base de données inexistante appelée '"foobar"') :

ERREUR ! Type : DBI
        Informations : Base de données 'foobar' non trouvée

La variable "erreur" peut également être spécifiée seule et renverra une chaîne de la forme ""$type erreur - $info"".

...
[% ATTTRAPER %]
ERREUR : [% erreur %]
[% FIN %]

Sortie :

ERREUR : erreur DBI - Base de données 'foobar' non trouvée

Chaque bloc "ATTTRAPER" peut être spécifié avec un type d'erreur spécifique indiquant le type d'erreur qu'il doit intercepter. Plusieurs blocs "ATTTRAPER" peuvent être fournis pour gérer différents types d'exceptions qui peuvent être levées dans le bloc "ESSAI". Un bloc "ATTTRAPER" spécifié sans type, comme dans l'exemple précédent, est un gestionnaire par défaut qui interceptera toute exception non interceptée d'un autre type. Cela peut également être spécifié comme "[% ATTTRAPER PAR DEFAUT %]".

[% ESSAI %]
   [% INCLURE myfile %]
   [% UTILISER DBI(mydsn) %]
   [% APPEL somecode %]
[% ATTTRAPER file %]
   Erreur de fichier ! [% erreur.info %]
[% ATTTRAPER DBI %]
   [% INCLURE database/error.html %]
[% ATTTRAPER %]
   [% erreur %]
[% FIN %]

N'oubliez pas que vous pouvez spécifier plusieurs directives dans une seule balise, chacune étant séparée par un ';'. Ainsi, l'exemple précédent peut être écrit de manière plus concise comme suit :

[% ESSAI;
       INCLURE myfile;
       UTILISER DBI(mydsn);
       APPEL somecode;
   ATTTRAPER file;
       "Erreur de fichier ! $erreur.info";
   ATTTRAPER DBI;
       INCLURE database/error.html;
   ATTTRAPER;
       erreur;
   FIN
%]

Le plugin "DBI" lève des exceptions de type "DBI" (au cas où ce ne serait pas déjà évident). L'autre type spécifique d'exception intercepté ici est de type "file".

Une exception "file" est automatiquement levée par le Template Toolkit lorsqu'il ne parvient pas à trouver un fichier, ou échoue à charger, analyser ou traiter un fichier qui a été demandé par une directive comme "INCLURE", "TRAITER", "INSERER" ou "ENVELOPPER". Si "myfile" ne peut pas être trouvé dans l'exemple précédent, la directive "[% INCLURE myfile %]" lèvera une exception "file" qui sera ensuite interceptée par le bloc "[% ATTTRAPER file %]". La sortie générée serait :

Erreur de fichier ! myfile: introuvable

Note : L'option "PAR DEFAUT" (désactivée par défaut) permet de spécifier un fichier par défaut à utiliser chaque fois qu'un fichier de modèle ne peut pas être trouvé. Cela empêche les exceptions de fichier d'être levées lorsqu'un fichier inexistant est demandé (sauf, bien sûr, si le fichier "PAR DEFAUT" que vous spécifiez n'existe pas). Les exceptions rencontrées après que le fichier ait été trouvé (c'est-à-dire les erreurs de lecture, d'analyse) sont levées comme des exceptions de fichier comme d'habitude.

Les exceptions non interceptées (c'est-à-dire si le bloc "ESSAI" n'a pas de gestionnaire "ATTTRAPER" spécifique ou par défaut) peuvent être interceptées en émettant des blocs "ESSAI" qui peuvent être imbriqués indéfiniment entre plusieurs modèles. Si l'exception n'est capturée à aucun niveau, l'exécution s'arrête et la méthode process() de Template renvoie une valeur fausse à l'appelant. L'objet Template::Exception pertinent peut être récupéré via la méthode error().

[% ESSAI %]
   ...
   [% ESSAI %]
      [% INCLURE $user.header %]
   [% ATTTRAPER file %]
      [% INCLURE header %]
   [% FIN %]
   ...
[% ATTTRAPER DBI %]
   [% INCLURE database/error.html %]
[% FIN %]

Dans cet exemple, le bloc "ESSAI" interne est utilisé pour s'assurer que la première directive "INCLURE" fonctionne comme prévu. Nous utilisons une variable pour fournir le nom du modèle que nous voulons inclure, "user.header", et il est possible que cela contienne le nom d'un modèle inexistant, ou un modèle qui contient des directives de modèle invalides. Si la directive "INCLURE" échoue avec une exception "file", nous interceptons cette exception dans le bloc interne et incluons à la place le fichier par défaut "header". Toute erreur "DBI" survenant dans la portée du bloc "ESSAI" externe sera interceptée dans le bloc "ATTTRAPER" correspondant, entraînant le traitement du modèle "database/error.html". Notez que les modèles inclus héritent de toutes les variables actuellement définies dans le modèle. Par conséquent, ces fichiers d'erreur peuvent accéder à la variable "erreur" pour récupérer des informations sur l'exception actuellement interceptée. Par exemple, le modèle "database/error.html" pourrait ressembler à ceci :

<h2>Erreur de base de données</h2>
Une erreur de base de données s'est produite : [% erreur.info %]

Vous pouvez également spécifier un bloc "FINAL". Celui-ci est toujours traité indépendamment du résultat des blocs "ESSAI" et/ou "ATTTRAPER". Si une exception n'est pas interceptée, le bloc "FINAL" est traité avant de passer au bloc supérieur ou de retourner à l'appelant.

[% ESSAI %]
   ...
[% ATTTRAPER this %]
   ...
[% ATTTRAPER that %]
   ...
[% FINAL %]
   Tout est terminé !
[% FIN %]

La sortie du bloc "ESSAI" est conservée intacte jusqu'à ce qu'une exception se produise. Par exemple, ce modèle génère la sortie suivante :

This gets printed
culinary delights: carrots

Le bloc "EFFACER" peut être utilisé dans un bloc "ATTTRAPER" ou "FINAL" pour effacer toute sortie créée dans le bloc "ESSAI".

[% ESSAI %]
   This gets printed
   [% LANCER food 'carrots' %]
   This doesn't
[% ATTTRAPER food %]
   [% EFFACER %]
   culinary delights: [% erreur.info %]
[% FIN %]

Sortie :

culinary delights: carrots

Les types d'exception sont vus hiérarchiquement, chaque niveau étant séparé par l'opérateur familier du point. Une exception "DBI.connect" est un type d'exception "DBI" plus spécifique. De même, une exception "example.error.barf" est un type d'exception "example.error" plus spécifique, qui est à son tour également un type d'exception "example".

Un gestionnaire d'exception "ATTTRAPER" spécifiant un type général (tel que "DBI" ou "example.error") interceptera également des types plus spécifiques ayant le même préfixe, à condition qu'aucun gestionnaire plus spécifique ne soit défini. Notez que l'ordre dans lequel les gestionnaires d'exception "ATTTRAPER" sont définis n'a pas d'importance ; un gestionnaire plus spécifique interceptera toujours une exception de préférence à un gestionnaire plus général ou par défaut.

[% ESSAI %]
   ...
[% ATTTRAPER DBI ;
     INCLURE database/error.html ;
   ATTTRAPER DBI.connect ;
     INCLURE database/connect.html ;
   ATTTRAPER ;
     INCLURE error.html ;
   FIN
%]

Dans cet exemple, une exception "DBI.connect" a son propre gestionnaire, un bloc "DBI" plus général est utilisé pour toutes les exceptions "DBI" ou "DBI.*", et un gestionnaire par défaut intercepte tout le reste.

Les exceptions peuvent être levées dans un modèle en utilisant la directive "LANCER". Le premier paramètre est le type d'exception, qui n'a pas besoin d'être cité (mais peut l'être, car il est le même que "INCLURE"), suivi du message pertinent qui peut être n'importe quelle valeur régulière, telle qu'une chaîne citée, une variable, etc.

[% LANCER food "Ingrédients manquants : $recipe.error" %]
[% LANCER user.login 'aucun id utilisateur : veuillez vous connecter' %]
[% LANCER $myerror.type "Mon Erreur : $myerror.info" %]

Vous pouvez également spécifier des paramètres positionnels ou nommés supplémentaires à la directive "LANCER" si vous souhaitez passer plus d'un simple message sous forme de champ d'erreur "info".

[% LANCER food 'oeufs' 'farine' msg='Ingrédients manquants' %]

Dans ce cas, le champ "info" de l'exception sera un tableau associatif avec les arguments nommés et un élément "args" contenant une liste des arguments positionnels.

Directives

The Template Toolkit provides a number of directives for controlling the flow and behaviour of template processing.

TRY

The "TRY" directive can be used to wrap blocks of template code in an exception handler. Any exceptions (errors) thrown during the processing of the code within the "TRY" block can be caught by an associated "CATCH" block.

The "TRY" directive must be followed by a "CATCH" directive or an "END" directive.

Template:
  [% TRY %]
     Some processing...
     [% USE some.plugin %]
     ...
  [% CATCH %]
     An error occurred: [% error %]
  [% END %]

If the "TRY" block completes without throwing any exceptions, then the "CATCH" block is skipped.

The "CATCH" directive can be specified with a type parameter, which is used to match the type of the exception being thrown. If the type matches, or if no type is specified, then the "CATCH" block is executed.

Template:
  [% TRY %]
     ...
  [% CATCH user.login ;
        'Login failed: ' _ error.info ;
     END
  %]
  [% CATCH db.error ;
        'Database error: ' _ error.info ;
     END
  %]
  [% CATCH ;
        'An unexpected error occurred: ' _ error ;
     END
  %]
  [% END %]

When an exception is caught, the error object is made available in the template under the variable name "error". This object is an instance of the Template::Exception class.

The exception object has the following attributes:

type
The exception type, as a string. This is typically in the format "category.subcategory", e.g. "user.login" or "db.error".
info
Additional information about the error. This can be a string or a reference to any Perl data structure (hash, array, object, etc.).
args
A reference to an array containing the positional arguments passed to the exception constructor. This is a convenience shortcut for accessing "info" if it is an array reference.

For example, if an exception is thrown using:

die Template::Exception->new('food.missing',
                            'Ingredients missing',
                            ['eggs', 'flour']);

The exception object can be accessed in the template as follows:

Template:
  [% TRY %]
     ...
  [% CATCH food.missing ;
        'Missing: ' _ error.info _ ' (' _ error.args.join(', ') _ ')';
     END
  %]
  [% END %]

Output:

Missing: Ingredients missing (eggs, flour)

The "info" attribute can also be accessed directly via numerical indexes in the "args" array:

[% error.info.0 %]   # same as [% error.info.args.0 %]

Exceptions can also be thrown from Perl code which you've bound to template variables, or defined as a plugin or other extension. To raise an exception, call die() passing a reference to a Template::Exception object as the argument. This will then be caught by any enclosing "TRY" blocks from where the code was called.

use Template::Exception;
...
my $vars = {
    foo => sub {
        # ... do something ...
        die Template::Exception->new('myerr.naughty',
                                     'Bad, bad error');
    },
};

Template:

[% TRY %]
   [% foo %]
[% CATCH myerr ;
     "Error: $error" ;
   END
%]

Output:

Error: myerr.naughty error - Bad, bad error

The "info" field can also be a reference to another object or data structure, if required.

die Template::Exception->new('myerror', {
    module => 'foo.pl',
    errors => [ 'bad permissions', 'naughty boy' ],
});

Later, in a template:

[% TRY %]
   ...
[% CATCH myerror %]
   [% error.info.errors.size or 'no';
      error.info.errors.size == 1 ? ' error' : ' errors' %]
   in [% error.info.module %]:
      [% error.info.errors.join(', ') %].
[% END %]

Generating the output:

2 errors in foo.pl:
   bad permissions, naughty boy.

You can also call die() with a single string, as is common in much existing Perl code. This will automatically be converted to an exception of the '"undef"' type (that's the literal string '"undef"', not the undefined value). If the string isn't terminated with a newline then Perl will append the familiar " at $file line $line" message.

sub foo {
    # ... do something ...
    die "I'm sorry, Dave, I can't do that\n";
}

If you're writing a plugin, or some extension code that has the current Template::Context in scope (you can safely skip this section if this means nothing to you) then you can also raise an exception by calling the context throw() method. You can pass it an Template::Exception object reference, a pair of "($type, $info)" parameters or just an $info string to create an exception of '"undef"' type.

$context->throw($e);            # exception object
$context->throw('Denied');      # 'undef' type
$context->throw('user.passwd', 'Bad Password');

NEXT

The "NEXT" directive can be used to start the next iteration of a "FOREACH" or "WHILE" loop.

[% FOREACH user IN users %]
   [% NEXT IF user.isguest %]
   Name: [% user.name %]    Email: [% user.email %]
[% END %]

LAST

The "LAST" directive can be used to prematurely exit a "FOREACH" or "WHILE" loop.

[% FOREACH user IN users %]
   Name: [% user.name %]    Email: [% user.email %]
   [% LAST IF some.condition %]
[% END %]

"BREAK" can also be used as an alias for "LAST".

RETURN

The "RETURN" directive can be used to stop processing the current template and return to the template from which it was called, resuming processing at the point immediately after the "INCLUDE", "PROCESS" or "WRAPPER" directive. If there is no enclosing template then the Template process() method will return to the calling code with a true value.

Before
[% INCLUDE half_wit %]
After
[% BLOCK half_wit %]
This is just half...
[% RETURN %]
...a complete block
[% END %]

Output:

Before
This is just half...
After

STOP

The "STOP" directive can be used to indicate that the processor should stop gracefully without processing any more of the template document. This is a planned stop and the Template process() method will return a true value to the caller. This indicates that the template was processed successfully according to the directives within it.

[% IF something.terrible.happened %]
   [% INCLUDE fatal/error.html %]
   [% STOP %]
[% END %]
[% TRY %]
   [% USE DBI(mydsn) %]
   ...
[% CATCH DBI.connect %]
   <h1>Cannot connect to the database: [% error.info %]</h1>
   <p>
     We apologise for the inconvenience.
   </p>
   [% INCLUDE footer %]
   [% STOP %]
[% END %]

CLEAR

The "CLEAR" directive can be used to clear the output buffer for the current enclosing block. It is most commonly used to clear the output generated from a "TRY" block up to the point where the error occurred.

[% TRY %]
   blah blah blah            # this is normally left intact
   [% THROW some 'error' %]  # up to the point of error
   ...
[% CATCH %]
   [% CLEAR %]               # clear the TRY output
   [% error %]               # print error string
[% END %]

Miscellaneous

META

The "META" directive allows simple metadata items to be defined within a template. These are evaluated when the template is parsed and as such may only contain simple values (e.g. it's not possible to interpolate other variables values into "META" variables).

[% META
   title   = 'The Cat in the Hat'
   author  = 'Dr. Seuss'
   version = 1.23
%]

The "template" variable contains a reference to the main template being processed. These metadata items may be retrieved as attributes of the template.

<h1>[% template.title %]</h1>
<h2>[% template.author %]</h2>

The "name" and "modtime" metadata items are automatically defined for each template to contain its name and modification time in seconds since the epoch.

[% USE date %]              # use Date plugin to format time
...
[% template.name %] last modified
at [% date.format(template.modtime) %]

The "PRE_PROCESS" and "POST_PROCESS" options allow common headers and footers to be added to all templates. The "template" reference is correctly defined when these templates are processed, allowing headers and footers to reference metadata items from the main template.

$template = Template->new({
    PRE_PROCESS  => 'header',
    POST_PROCESS => 'footer',
});
$template->process('cat_in_hat');

header:

<html>
  <head>
    <title>[% template.title %]</title>
  </head>
  <body>

cat_in_hat:

[% META
     title   = 'The Cat in the Hat'
     author  = 'Dr. Seuss'
     version = 1.23
     year    = 2000
%]
    The cat in the hat sat on the mat.

footer:

    <hr>
    &copy; [% template.year %] [% template.author %]
  </body>
</html>

The output generated from the above example is:

<html>
  <head>
    <title>The Cat in the Hat</title>
  </head>
  <body>
    The cat in the hat sat on the mat.
    <hr>
    &copy; 2000 Dr. Seuss
  </body>
</html>

TAGS

The "TAGS" directive can be used to set the "START_TAG" and "END_TAG" values on a per-template file basis.

[% TAGS <+ +> %]
<+ INCLUDE header +>

The TAGS directive may also be used to set a named "TAG_STYLE"

[% TAGS html %]
<!-- INCLUDE header -->

See the TAGS and TAG_STYLE configuration options for further details.

DEBUG

The "DEBUG" directive can be used to enable or disable directive debug messages within a template. The "DEBUG" configuration option must be set to include "DEBUG_DIRS" for the "DEBUG" directives to have any effect. If "DEBUG_DIRS" is not set then the parser will automatically ignore and remove any "DEBUG" directives.

The "DEBUG" directive can be used with an "on" or "off" parameter to enable or disable directive debugging messages from that point forward. When enabled, the output of each directive in the generated output will be prefixed by a comment indicate the file, line and original directive text.

[% DEBUG on %]
directive debugging is on (assuming DEBUG option is set true)
[% DEBUG off %]
directive debugging is off

The "format" parameter can be used to change the format of the debugging message.

[% DEBUG format '<!-- $file line $line : [% $text %] -->' %]
