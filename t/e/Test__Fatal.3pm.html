Test::Fatal(3) Documentation Perl fournie par l'utilisateur Test::Fatal(3)

NOM

Test::Fatal - assistants incroyablement simples pour tester du code avec des exceptions

VERSION

version 0.018

SYNOPSIS

use Test::More;
use Test::Fatal;
use System::Under::Test qw(might_die);
is(
  exception { might_die; },
  undef,
  "le code a vécu",
);
like(
  exception { might_die; },
  qr/il s'avère qu'il est mort/,
  "le code est mort comme prévu",
);
isa_ok(
  exception { might_die; },
  'Exception::Whatever',
  'l'exception levée',
);

DESCRIPTION

Test::Fatal est une alternative au populaire Test::Exception. Il fait beaucoup moins, mais devrait permettre une plus grande flexibilité pour tester du code lançant des exceptions avec à peu près la même quantité de frappe.

Il exporte une seule routine par défaut : "exception".

Attention ! "exception" ne manipule intentionnellement pas la pile d'appels. Les fonctions de test écrites par l'utilisateur qui utilisent "exception" doivent faire attention à éviter les faux positifs si les exceptions utilisent des traces de pile qui montrent les arguments. Pour une approche plus magique impliquant la redéfinition globale de "caller", voir Test::Exception.

VERSION PERL

Cette bibliothèque devrait fonctionner sur des perl lancées il y a longtemps. Elle devrait fonctionner sur n'importe quelle version de perl lancée au cours des cinq dernières années.

Bien qu'elle puisse fonctionner sur des versions plus anciennes de perl, aucune garantie n'est donnée que la version minimale requise ne sera pas augmentée. La version peut être augmentée pour quelque raison que ce soit, et aucune promesse n'est faite que des correctifs seront acceptés pour abaisser la version minimale requise de perl.

FONCTIONS

exception

my $exception = exception { ... };

"exception" prend un bloc de code nu et retourne l'exception levée par ce bloc. Si aucune exception n'a été levée, elle retourne undef.

Attention ! Si le bloc aboutit à une exception fausse non bénie, comme 0 ou la chaîne vide, Test::Fatal mourra lui-même. Étant donné que l'un ou l'autre de ces cas indique un problème sérieux avec le système sous test, ce comportement est considéré comme une fonctionnalité. Notez que ce problème n'est connu que pour se produire sur les perl avant 5.14.

Faites preuve de prudence si vous devez tester ces conditions : encapsuler "exception { ... }" dans un bloc ok() ne vous donnera pas le résultat escompté, alors assurez-vous d'utiliser is() à la place. Vous pouvez également utiliser directement le mécanisme try/catch de Try::Tiny, le système de gestion des exceptions sous-jacent de Test::Fatal.

Notez qu'il n'y a aucune assertion TAP effectuée. En d'autres termes, aucune ligne "ok" ou "not ok" n'est émise. Il vous appartient d'utiliser le reste de "exception" dans un test existant comme "ok", "isa_ok", "is", etc. Ou vous pouvez souhaiter utiliser les enveloppes "dies_ok" et "lives_ok", qui fournissent une sortie TAP.

"exception" ne modifie *pas* la pile présentée au bloc appelé, ce qui signifie que si l'exception retournée a une trace de pile, elle inclura des cadres entre le code appelant "exception" et la chose lançant l'exception. Ceci est considéré comme une fonctionnalité car cela évite le mécanisme parfois capricieux de "Sub::Uplevel".

Attention ! Ce n'est pas une bonne idée :

sub exception_like(&$;$) {
    my ($code, $pattern, $name) = @_;
    like( &exception($code), $pattern, $name );
}
exception_like(sub { }, qr/foo/, 'foo apparaît dans l'exception');

Si le code dans les "..." va lancer une trace de pile avec les arguments de chaque sous-routine dans sa pile d'appels (par exemple via "Carp::confess", le nom du test, "foo apparaît dans l'exception" sera lui-même correspondant par l'expression régulière. Écrivez plutôt ceci :

like( exception { ... }, qr/foo/, 'foo apparaît dans l'exception' );

Si vous voulez vraiment une fonction de test qui transmet le nom du test, enveloppez les arguments dans une référence de tableau pour cacher le texte littéral d'une trace de pile :

sub exception_like(&$) {
    my ($code, $args) = @_;
    my ($pattern, $name) = @$args;
    like( &exception($code), $pattern, $name );
}
exception_like(sub { }, [ qr/foo/, 'foo apparaît dans l'exception' ] );

Pour aider à éviter le problème où le motif est vu dans l'exception à cause de la pile d'appels, $Carp::MaxArgNums est localement défini à -1 lorsque le bloc de code est appelé. Si vous ne le souhaitez vraiment pas, définissez-le à nouveau à la valeur de votre choix au début du bloc de code. Évidemment, cette solution n'affecte pas toutes les façons possibles dont les arguments des sous-routines dans la pile d'appels pourraient "teinter" le test. L'intention ici est d'empêcher certains faux succès de la part de personnes qui n'ont pas lu la documentation. Votre punition pour l'avoir lue est que vous devez considérer si vous devez faire quelque chose à ce sujet.

Attention : Une dernière mauvaise idée :

isnt( exception { ... }, undef, "mon code est mort !");

Il est vrai que cela teste que votre code est mort, mais vous devriez vraiment tester qu'il est mort pour la bonne raison. Par exemple, si vous faites une erreur non liée dans le bloc, comme utiliser le mauvais déréférencement, votre test réussira même si le code à tester n'est pas réellement exécuté du tout. Si vous attendez une exception inspectable avec un identifiant ou une classe, testez cela. Si vous attendez une exception sous forme de chaîne, envisagez d'utiliser "like".

succès

try {
  should_live;
} catch {
  fail("boo, nous sommes morts");
} success {
  pass("hourra, nous avons vécu");
};

"success", exporté uniquement sur demande, est un assistant de Try::Tiny avec des sémantiques identiques à "finally", mais le corps du bloc ne sera exécuté que si le bloc "try" s'est exécuté sans erreur.

Bien que presque tous les tests d'exception nécessaires puissent être effectués avec "exception", les blocs de succès peuvent parfois aider à organiser des tests complexes.

dies_ok

lives_ok

Exportées uniquement sur demande, ces deux fonctions exécutent un bloc de code donné et fournissent une sortie TAP indiquant si elles ont lancé ou non une exception. Celles-ci offrent un chemin de mise à niveau facile pour remplacer les tests unitaires existants basés sur "Test::Exception".

RJBS ne suggère pas d'utiliser cela sauf par commodité lors du portage de tests pour utiliser la routine "exception" de Test::Fatal.

use Test::More tests => 2;
use Test::Fatal qw(dies_ok lives_ok);
dies_ok { die "j'ai échoué" } 'code qui échoue';
lives_ok { return "je suis toujours en vie" } 'code qui n'échoue pas';

Test::Fatal(3pm) — Arch manual pages

NAME

Test::Fatal - Tests that code dies or fails

VERSION

This document describes version 0.018 of Test::Fatal.

SYNOPSIS

use Test::More tests => 5;
use Test::Fatal;

# Test that code dies with a specific exception
my $exception = lives_and_diag { die "oops" };
ok($exception =~ /oops/, "die message was correct");

# Test that code dies with an exception object
use MooseX::Exception;
my $error = MyException->new(message => "it failed");
is(dies_ok { $error->throw }, $error, "dies_ok dies with the correct exception");

# Test that code dies with an exception object whose message matches
dies_and_diag { MyException->new(message => "it failed")->throw };

# Test that code dies with an exception object whose message matches a regex
dies_and_diag { MyException->new(message => "it failed")->throw }, qr/failed/;

# Test that code dies with an exception object whose class matches
dies_and_diag { MyException->new(message => "it failed")->throw }, qr/failed/, MyException;

# Test that code dies with an exception object whose class is a subclass
dies_and_diag { MyException->new(message => "it failed")->throw }, qr/failed/, qr/^MyException\b/;

# Test that code doesn't die
isnt_die { print "hello" };

# Test that code doesn't die, and report diag output
isnt_die_diag { print "hello" };

# Test that code doesn't die, and report diag output with a message
isnt_die_diag { print "hello" }, "this code should not die";

# Test that code doesn't die, and report diag output with a message and output
isnt_die_diag { print "hello" }, "this code should not die", "hello\n";

# Test that code doesn't die, and report diag output with a message and output,
# and output is a regex
isnt_die_diag { print "hello" }, "this code should not die", qr/hello/;

# Test that code doesn't die, and report diag output with a message and output,
# and output is a regex, and output is a subclass
isnt_die_diag { print "hello" }, "this code should not die", qr/hello/, qr/^hello\b/;

# Test that code doesn't die, and report diag output with a message and output,
# and output is a regex, and output is a subclass, and output is a class
isnt_die_diag { print "hello" }, "this code should not die", qr/hello/, qr/^hello\b/, qr/^hello\b/;

DESCRIPTION

This module provides functions for testing code that is expected to die, or is not expected to die.

This module is a wrapper around Test::Builder::Module.

lives_and_diag

This function runs the code in the block. If the code dies, it returns the exception object. If the code does not die, it fails the test and reports diagnostics.

lives_and_ok

This function runs the code in the block. If the code dies, it returns the exception object. If the code does not die, it fails the test and reports diagnostics.

dies_ok

This function runs the code in the block. If the code dies, it returns the exception object. If the code does not die, it fails the test and reports diagnostics.

dies_and_diag

This function runs the code in the block. If the code dies, it returns the exception object. If the code does not die, it fails the test and reports diagnostics.

isnt_die

This function runs the code in the block. If the code does not die, it passes the test. If the code dies, it fails the test and reports diagnostics.

isnt_die_diag

This function runs the code in the block. If the code does not die, it passes the test. If the code dies, it fails the test and reports diagnostics.

PERL VERSION

This module is tested with Perl 5.8.1, and should be compatible with Perl 5.6.0 and later.
