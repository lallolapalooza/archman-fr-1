Test::More(3perl) Guide du programmeur Perl Test::More(3perl)

NOM

Test::More - encore un framework pour écrire des scripts de test

SYNOPSIS

use Test::More tests => 23;
# ou
use Test::More skip_all => $raison;
# ou
use Test::More;   # voir done_testing()
require_ok( 'Some::Module' );
# Diverses façons de dire "ok"
ok($got eq $expected, $nom_test);
is  ($got, $expected, $nom_test);
isnt($got, $expected, $nom_test);
# Plutôt que d'afficher STDERR "# voici ce qui s'est mal passé\n"
diag("voici ce qui s'est mal passé");
like  ($got, qr/attendu/, $nom_test);
unlike($got, qr/attendu/, $nom_test);
cmp_ok($got, '==', $expected, $nom_test);
is_deeply($structure_complexe_obtenue, $structure_complexe_attendue, $nom_test);
SKIP: {
    skip $pourquoi, $combien_de_fois unless $avons_la_fonctionnalite;
    ok( foo(),       $nom_test );
    is( foo(42), 23, $nom_test );
};
TODO: {
    local $TODO = $pourquoi;
    ok( foo(),       $nom_test );
    is( foo(42), 23, $nom_test );
};
can_ok($module, @methods);
isa_ok($objet, $classe);
pass($nom_test);
fail($nom_test);
BAIL_OUT($pourquoi);
# NON IMPLÉMENTÉ !!!
my @status = Test::More::status;

DESCRIPTION

ARRÊTEZ ! Si vous débutez dans l'écriture de tests, jetez un œil à Test2::Suite d'abord.

Ceci est un remplacement direct de Test::Simple auquel vous pouvez passer une fois que vous avez pris le coup de main des tests de base.

Le but de ce module est de fournir une large gamme d'utilitaires de test. Diverses façons de dire "ok" avec de meilleurs diagnostics, des facilités pour sauter des tests, tester des fonctionnalités futures et comparer des structures de données compliquées. Bien que vous puissiez faire presque n'importe quoi avec une simple fonction ok(), elle ne fournit pas une bonne sortie de diagnostic.

J'adore quand un plan se prépare

Avant toute chose, vous avez besoin d'un plan de test. Cela déclare essentiellement combien de tests votre script va exécuter pour se protéger contre les échecs prématurés.

La façon préférée de faire cela est de déclarer un plan lorsque vous faites "use Test::More".

use Test::More tests => 23;

Il y a des cas où vous ne saurez pas à l'avance combien de tests votre script va exécuter. Dans ce cas, vous pouvez déclarer vos tests à la fin.

use Test::More;
... exécutez vos tests ...
done_testing( $nombre_de_tests_exécutés );

NOTE done_testing() ne doit jamais être appelée dans un bloc "END { ... }".

Parfois, vous ne savez vraiment pas combien de tests ont été exécutés, ou c'est trop difficile à calculer. Auquel cas, vous pouvez omettre $nombre_de_tests_exécutés.

Dans certains cas, vous voudrez sauter complètement un script de test entier.

use Test::More skip_all => $raison_du_saut;

Votre script déclarera un saut avec la raison pour laquelle vous avez sauté et quittera immédiatement avec un zéro (succès). Voir Test::Harness pour les détails.

Si vous voulez contrôler quelles fonctions Test::More exportera, vous devez utiliser l'option 'import'. Par exemple, pour tout importer sauf 'fail', vous feriez :

use Test::More tests => 23, import => ['!fail'];

Alternativement, vous pouvez utiliser la fonction plan(). Utile lorsque vous devez calculer le nombre de tests.

use Test::More;
plan tests => keys %Stuff * 3;

ou pour décider de lancer ou non les tests :

use Test::More;
if( $^O eq 'MacOS' ) {
    plan skip_all => 'Test non pertinent sur MacOS';
}
else {
    plan tests => 42;
}
done_testing
done_testing();
done_testing($nombre_de_tests);

Si vous ne savez pas combien de tests vous allez exécuter, vous pouvez émettre le plan une fois que vous avez terminé d'exécuter les tests.

$nombre_de_tests est la même chose que plan(), c'est le nombre de tests que vous vous attendiez à exécuter. Vous pouvez omettre cela, auquel cas le nombre de tests exécutés n'a pas d'importance, juste le fait que vos tests se sont terminés.

Ceci est plus sûr que et remplace le plan "no_plan".

Note : Vous ne devez jamais placer done_testing() à l'intérieur d'un bloc "END { ... }". Le plan est là pour assurer que votre test ne se termine pas avant que les tests ne soient terminés. Si vous utilisez un bloc END, vous contournez complètement cette protection.

Noms des tests

Par convention, chaque test est attribué un numéro dans l'ordre. Ceci est largement fait automatiquement pour vous. Cependant, il est souvent très utile d'attribuer un nom à chaque test. Que préféreriez-vous voir :

ok 4
not ok 5
ok 6

ou

ok 4 - exponentielle simple
not ok 5 - exponentielle simple
ok 6 - force == masse * accélération

Le dernier donne une idée de ce qui a échoué. Cela facilite également la recherche du test dans votre script, il suffit de rechercher "exponentielle simple".

Toutes les fonctions de test prennent un argument de nom. Il est facultatif, mais il est fortement suggéré de l'utiliser.

Je vais bien, tu vas mal.

Le but principal de ce module est d'afficher soit "ok #", soit "not ok #" selon que le test a réussi ou échoué. Tout le reste n'est que du bonus.

Toutes les fonctions suivantes affichent "ok" ou "not ok" selon que le test a réussi ou échoué. Elles retournent toutes également vrai ou faux, respectivement.

ok
ok($got eq $expected, $nom_test);

Ceci évalue simplement toute expression ("$got eq $expected" n'est qu'un simple exemple) et utilise cela pour déterminer si le test a réussi ou échoué. Une expression vraie réussit, une fausse échoue. Très simple.

Par exemple :

ok( $exp{9} == 81,                   'exponentielle simple' );
ok( Film->can('db_Main'),            'set_db()' );
ok( $p->tests == 4,                  'a vu les tests' );
ok( !grep(!defined $_, @items),      'tous les éléments sont définis' );

(Mnémonique : "Ceci est ok.")

$nom_test est une description très courte du test qui sera affichée. Cela permet de trouver très facilement un test dans votre script lorsqu'il échoue et donne aux autres une idée de vos intentions. $nom_test est facultatif, mais nous en encourageons **vivement** l'utilisation.

Si un ok() échoue, il produira quelques diagnostics :

not ok 18 - mucus suffisant
#   Failed test 'mucus suffisant'
#   in foo.t at line 42.

C'est la même chose que la routine ok() de Test::Simple.

is
isnt
is  ( $got, $expected, $nom_test );
isnt( $got, $expected, $nom_test );

Similaire à ok(), is() et isnt() comparent leurs deux arguments avec "eq" et "ne" respectivement et utilisent le résultat pour déterminer si le test a réussi ou échoué. Donc ceux-ci :

# La réponse ultime est-elle 42 ?
is( ultimate_answer(), 42,          "Sens de la vie" );
# $foo n'est pas vide
isnt( $foo, '',     "Obtenu du foo" );

sont similaires à ceux-ci :

ok( ultimate_answer() eq 42,        "Sens de la vie" );
ok( $foo ne '',     "Obtenu du foo" );

"undef" ne correspondra jamais qu'à "undef". Vous pouvez donc tester une valeur contre "undef" comme ceci :

is($not_defined, undef, "non défini comme prévu");

(Mnémonique : "Ceci est cela." "Ceci n'est pas cela.")

Alors pourquoi les utiliser ? Ils produisent de meilleurs diagnostics en cas d'échec. ok() ne peut pas savoir ce que vous testez (au-delà du nom), mais is() et isnt() savent quel était le test et pourquoi il a échoué. Par exemple ce test :

my $foo =
'gaufre'; mon $bar = 'yarblokos'; is( $foo, $bar, 'Est-ce que foo est la même chose que bar ?' );

Produira quelque chose comme ceci :

not ok 17 - Est-ce que foo est la même chose que bar ?
#   Failed test 'Est-ce que foo est la même chose que bar ?'
#   dans foo.t à la ligne 139.
#          obtenu: 'gaufre'
#     attendu: 'yarblokos'

Vous pouvez ainsi comprendre ce qui n'a pas fonctionné sans relancer le test.

Il est encouragé d'utiliser is() et isnt() plutôt que ok() lorsque possible, cependant ne soyez pas tenté de les utiliser pour savoir si quelque chose est vrai ou faux !

# XXX MAUVAIS !
is( exists $brooklyn{tree}, 1, 'Un arbre pousse à Brooklyn' );

Cela ne vérifie pas si "exists $brooklyn{tree}" est vrai, cela vérifie si cela retourne 1. Très différent. Des mises en garde similaires existent pour false et 0. Dans ces cas, utilisez ok().

ok( exists $brooklyn{tree},    'Un arbre pousse à Brooklyn' );

Un appel simple à isnt() ne fournit généralement pas un test fort, mais il y a des cas où l'on ne peut pas dire grand-chose de plus sur une valeur que le fait qu'elle est différente d'une autre valeur :

new_ok $obj, "Foo";
my $clone = $obj->clone;
isa_ok $obj, "Foo", "Foo->clone";
isnt $obj, $clone, "clone() produit un objet différent";

Historiquement, nous supportions une fonction "isn't()" comme alias de isnt(), cependant dans Perl 5.37.9, le support de l'apostrophe comme séparateur de package a été déprécié et dans Perl 5.42.0, le support de celui-ci sera complètement supprimé. Par conséquent, l'utilisation de "isn't()" est également dépréciée et produira des avertissements lors de son utilisation, à moins que les avertissements 'deprecated' ne soient spécifiquement désactivés dans le scope où elle est utilisée. Il est fortement conseillé de migrer vers l'utilisation de isnt() à la place.

like
like( $got, qr/attendu/, $test_name );

Similaire à ok(), like() fait correspondre $got à l'expression régulière "qr/attendu/".

Donc ceci :

like($got, qr/attendu/, 'ceci est comme cela');

est similaire à :

ok( $got =~ m/attendu/, 'ceci est comme cela');

(Mnémonique : « Ceci est comme cela ».)

Le deuxième argument est une expression régulière. Il peut être donné comme une référence d'expression régulière (c'est-à-dire "qr//") ou (pour une meilleure compatibilité avec les anciennes versions de Perl) comme une chaîne qui ressemble à une expression régulière (les délimiteurs alternatifs ne sont actuellement pas pris en charge) :

like( $got, '/attendu/', 'ceci est comme cela' );

Les options de l'expression régulière peuvent être placées à la fin ('/attendu/i').

Ses avantages par rapport à ok() sont similaires à ceux de is() et isnt(). Meilleures diagnostics en cas d'échec.

unlike
unlike( $got, qr/attendu/, $test_name );

Fonctionne exactement comme like(), seulement elle vérifie si $got **ne correspond pas** au motif donné.

cmp_ok
cmp_ok( $got, $op, $expected, $test_name );

À mi-chemin entre ok() et is() se trouve cmp_ok(). Cela vous permet de comparer deux arguments en utilisant n'importe quel opérateur binaire de Perl. Le test réussit si la comparaison est vraie et échoue sinon.

# ok( $got eq $expected );
cmp_ok( $got, 'eq', $expected, 'ceci eq cela' );
# ok( $got == $expected );
cmp_ok( $got, '==', $expected, 'ceci == cela' );
# ok( $got && $expected );
cmp_ok( $got, '&&', $expected, 'ceci && cela' );
...etc...

Son avantage par rapport à ok() est qu'en cas d'échec du test, vous saurez quels étaient $got et $expected :

not ok 1
#   Failed test in foo.t à la ligne 12.
#     '23'
#         &&
#     undef

C'est aussi utile dans les cas où vous comparez des nombres et que l'utilisation de is() avec "eq" interférerait :

cmp_ok( $big_hairy_number, '==', $another_big_hairy_number );

C'est particulièrement utile lors de la comparaison de relations supérieur ou inférieur entre des valeurs :

cmp_ok( $some_value, '<=', $upper_limit );
can_ok
can_ok($module, @methods);
can_ok($object, @methods);

Vérifie si le $module ou $object peut exécuter ces @methods (fonctionne aussi avec les fonctions).

can_ok('Foo', qw(ceci cela quoi que ce soit));

équivaut presque exactement à dire :

ok( Foo->can('ceci') && 
    Foo->can('cela') && 
    Foo->can('quoi que ce soit') 
  );

sauf que vous tapez moins et que l'interface est meilleure. Utile pour tester rapidement une interface.

Peu importe le nombre de @methods que vous vérifiez, un seul appel à can_ok() compte comme un test. Si vous souhaitez le contraire, utilisez :

foreach my $meth (@methods) {
    can_ok('Foo', $meth);
}
isa_ok
isa_ok($object,   $class, $object_name);
isa_ok($subclass, $class, $object_name);
isa_ok($ref,      $type,  $ref_name);

Vérifie si le "$object->isa($class)" donné est vrai. Vérifie également que l'objet a été défini en premier lieu. Utile pour ce genre de chose :

my $obj = Some::Module->new;
isa_ok( $obj, 'Some::Module' );

où vous devriez autrement écrire

my $obj = Some::Module->new;
ok( defined $obj && $obj->isa('Some::Module') );

pour éviter que votre script de test n'explose.

Vous pouvez également tester une classe pour vous assurer qu'elle a le bon ancêtre :

isa_ok( 'Vole', 'Rodent' );

Cela fonctionne aussi avec les références :

isa_ok( $array_ref, 'ARRAY' );

Les diagnostics de ce test se réfèrent normalement juste à « l'objet ». Si vous souhaitez qu'ils soient plus spécifiques, vous pouvez fournir un $object_name (par exemple, « Client test »).

new_ok
my $obj = new_ok( $class );
my $obj = new_ok( $class => \@args );
my $obj = new_ok( $class => \@args, $object_name );

Une fonction de commodité qui combine la création d'un objet et l'appel à isa_ok() sur cet objet.

C'est essentiellement équivalent à :

my $obj = $class->new(@args);
isa_ok $obj, $class, $object_name;

Si @args n'est pas fourni, une liste vide sera utilisée.

Cette fonction ne fonctionne que sur new() et suppose que new() retournera un seul objet qui est $class.

subtest
subtest $name => \&code, @args;

subtest() exécute le &code comme son propre petit test avec son propre plan et son propre résultat. Le test principal compte cela comme un seul test en utilisant le résultat de l'ensemble du sous-test pour déterminer s'il est ok ou not ok.

Par exemple...

use Test::More tests => 3;

pass("Premier test");
subtest 'Un exemple de sous-test' => sub {
    plan tests => 2;
    pass("Ceci est un sous-test");
    pass("Celui-ci aussi");
};
pass("Troisième test");

Cela produirait.

1..3
ok 1 - Premier test
    # Subtest: Un exemple de sous-test
    1..2
    ok 1 - Ceci est un sous-test
    ok 2 - Celui-ci aussi
ok 2 - Un exemple de sous-test
ok 3 - Troisième test

Un sous-test peut appeler "skip_all". Aucun test ne sera exécuté, mais le sous-test est considéré comme un saut.

subtest 'skippy' => sub {
    plan skip_all => 'parce que j'ai dit que oui';
    pass('ce test ne sera jamais exécuté');
};

Retourne vrai si le sous-test a réussi, faux sinon.

En raison de la façon dont fonctionnent les sous-tests, vous pouvez omettre un plan si vous le souhaitez. Cela ajoute un done_testing() implicite à la fin de votre sous-test. Les deux sous-tests suivants sont équivalents :

subtest 'sous-test avec done_testing() implicite', sub {
    ok 1, 'les sous-tests avec un done testing implicite devraient fonctionner';
    ok 1, '... et supporter plus d\'un test';
    ok 1, '... peu importe combien de tests sont exécutés';
};
subtest 'sous-test avec done_testing() explicite', sub {
    ok 1, 'les sous-tests avec un done testing explicite devraient fonctionner';
    ok 1, '... et supporter plus d\'un test';
    ok 1, '... peu importe combien de tests sont exécutés';
    done_testing();
};

Les arguments supplémentaires donnés à "subtest" sont passés au callback. Par exemple :

sub my_subtest {
    my $range = shift;
    ...
}
for my $range (1, 10, 100, 1000) {
    subtest "test de la plage $range", \&my_subtest, $range;
}
pass
fail
pass($test_name);
fail($test_name);

Parfois, vous voulez simplement dire que les tests ont réussi. Le cas le plus fréquent est lorsque vous avez une condition compliquée qu'il est difficile d'intégrer dans un ok(). Dans ce cas, vous pouvez simplement utiliser pass() (pour déclarer le test comme ok) ou fail (pour not ok). Ce sont des synonymes de ok(1) et ok(0).

Utilisez-les très, très, très rarement.

Tests de modules

Parfois, vous voulez tester si un module, ou une liste de modules, peut être chargé avec succès. Par exemple, vous voudrez souvent un premier test qui charge simplement tous les modules de la distribution pour vous assurer qu'ils fonctionnent avant de passer à des tests plus compliqués.

Chargement des modules

Pour de tels usages, nous avons "use_ok" et "require_ok".

require_ok
require_ok($module);
require_ok($file);

Tente de "require" le module ou le fichier donné par $module ou $file. Si le chargement réussit, le test passe. Si le chargement échoue, il affiche l'erreur de chargement.

"require_ok" tente de deviner si l'entrée est un nom de module ou un nom de fichier.

Aucune exception ne sera levée si le chargement échoue.

# require Some::Module
require_ok "Some::Module";
# require "Some/File.pl";
require_ok "Some/File.pl";
# arrêtez les tests si l'un de vos modules ne charge pas
for my $module (@module) {
    require_ok $module or BAIL_OUT "Impossible de charger $module";
}
use_ok
BEGIN { use_ok($module); }
BEGIN { use_ok($module, @imports); }

Similaire à "require_ok", mais charge le module et non les fichiers.

Si vous voulez simplement tester qu'un module peut être chargé, utilisez "require_ok".

Si vous voulez simplement charger un module dans un test, nous vous recommandons d'utiliser directement "use". Cela provoquera l'arrêt du test.

Il est recommandé d'exécuter use_ok() dans un bloc BEGIN afin que ses fonctions soient exportées au moment de la compilation et que les prototypes soient respectés.

Si @imports sont fournis, ils sont transmis au use. Ainsi, ceci :

BEGIN { use_ok('Some::Module', qw(foo bar)) }

est équivalent à :

use Some::Module qw(foo bar);

Les numéros de version peuvent être vérifiés comme ceci :

# similaire à "use Some::Module 1.02"
BEGIN { use_ok('Some::Module', 1.02) }

N'essayez pas de faire ceci :

BEGIN {
    use_ok('Some::Module');
    ...code qui dépend de l'utilisation...
    ...fait ce qui se passe au moment de la compilation...
}

car le concept de « moment de compilation » est relatif. Vous voudrez plutôt :

BEGIN { use_ok('Some::Module') }
BEGIN { ...code qui dépend de l'utilisation... }

Si vous voulez l'équivalent de "use Foo ()", c'est-à-dire charger un module mais ne pas importer quoi que ce soit, utilisez "require_ok".

BEGIN { require_ok "Foo" }

Structures de données complexes

Tout n'est pas une simple comparaison ou une expression régulière. Parfois, vous devez vérifier si deux structures de données sont équivalentes. Pour ces cas, Test::More offre plusieurs fonctions utiles.

NOTE Je ne suis pas sûr de ce qui se passera avec les handles de fichier.

is_deeply
is_deeply( $got, $expected, $test_name );

Similaire à is(), sauf que si $got et $expected sont des références, il effectue une comparaison profonde, parcourant chaque structure de données pour voir si elles sont équivalentes. Si les structures sont différentes, il affichera l'endroit où elles commencent à diverger.

is_deeply compare les valeurs déréférencées des références ; les références elles-mêmes (sauf leur type) sont ignorées. Cela signifie que des aspects tels que le blessing et les ties ne sont pas considérés comme différents.

is_deeply a actuellement une gestion très limitée des références de fonction et des références globales. Il vérifie uniquement si elles ont le même objet référencé. Cela pourrait être amélioré à l'avenir.

Test::Differences et Test::Deep offrent des fonctionnalités plus approfondies dans ce domaine.

NOTE is_deeply a des limitations lors de la comparaison de chaînes et de références :

my $path = path('.');
my $hash = {};
is_deeply( $path, "$path" ); # ok
is_deeply( $hash, "$hash" ); # échoue

Cela se produit car is_deeply déréférence tous les arguments sans condition. Il est probablement préférable de ne pas utiliser is_deeply avec des surcharges. Cela ne sera pas corrigé pour des raisons de compatibilité descendante. Si vous souhaitez un meilleur outil pour cela, consultez Test2::Suite, en particulier Test2::Tools::Compare, qui possède une fonction is() qui fonctionne comme is_deeply avec des améliorations.

Diagnostics

Si vous choisissez la bonne fonction de test, vous aurez généralement une bonne idée de ce qui a échoué lorsque le test a échoué. Cependant, parfois, cela ne fonctionne pas ainsi. C'est pourquoi nous avons ici des moyens d'écrire vos propres messages de diagnostic qui sont plus sûrs que de simplement faire "print STDERR".

diag
diag(@diagnostic_message);

Affiche un message de diagnostic dont on garantit qu'il n'interférera pas avec la sortie du test. Similaire à "print", @diagnostic_message sera simplement concaténé.

Retourne false, afin de préserver l'échec.

Utile pour ceci :

ok( grep(/foo/, @users), "Il y a un utilisateur foo" ) or
    diag("Comme il n'y a pas de foo, vérifiez que /etc/bar est correctement configuré");

qui produirait :

not ok 42 - Il y a un utilisateur foo
#   Failed test 'Il y a un utilisateur foo'
#   in foo.t at line 52.
# Comme il n'y a pas de foo, vérifiez que /etc/bar est correctement configuré.

Vous pouvez vous souvenir de "ok() or diag()" avec le moyen mnémotechnique open() or die().

NOTE Le format exact du message de diagnostic est encore en cours d'évolution, mais il est garanti que ce que vous émettez n'interférera pas avec le test.

note
note(@diagnostic_message);

Similaire à diag(), mais le message ne sera pas affiché lorsque le test est exécuté par un harness. Il ne sera affiché que dans le flux TAP verbeux.

Utile pour placer des notes qui pourraient être utiles au débogage, mais qui n'indiquent pas un problème.

note("Le fichier temporaire est $tempfile");
explain
my @dump = explain @diagnostic_message;

Affiche le contenu de toute référence dans un format lisible. Vous voudrez généralement le passer à "note" ou "diag".

Utile pour des choses comme...

is_deeply($have, $want) || diag explain $have;

ou

note explain \%args;
Some::Class->method(%args);

Tests conditionnels

Parfois, lors de l'exécution d'un test sous certaines conditions, le script de test peut échouer. Une certaine fonction ou méthode n'est pas implémentée (comme fork() sous Mac OS), une ressource n'est pas disponible (comme une connexion Internet) ou un module n'est pas disponible. Dans ces cas, il est nécessaire de sauter des tests ou de déclarer qu'ils devraient échouer mais fonctionneront à l'avenir (un test de type todo).

Pour plus de détails sur le mécanisme de saut et de todo, consultez Test::Harness.

La façon dont Test::More gère cela est avec un bloc nommé. Essentiellement, un bloc de test qui peut être sauté ou converti en todo. Il est préférable si je vous le montre...

SKIP: BLOCK
SKIP: {
    skip $why, $how_many if $condition;
    ...le code de test s'exécute normalement ici...
}

Déclare un bloc de test qui pourrait être sauté, avec $how_many tests, $why et sous quelle $condition les sauter. Un exemple est le plus facile à illustrer :

SKIP: {
    eval { require HTML::Lint };
    skip "HTML::Lint non installé", 2 if $@;
    my $lint = new HTML::Lint;
    isa_ok( $lint, "HTML::Lint" );
    $lint->parse( $html );
    is( $lint->errors, 0, "Pas d'erreurs HTML" );
}

Si l'utilisateur n'a pas HTML::Lint installé, le bloc de code complet ne sera pas exécuté. Test::More affichera des ok spéciaux que Test::Harness interprète comme des tests sautés, mais qui réussissent.

Il est important que $how_many reflète correctement le nombre de tests dans le bloc SKIP afin que le nombre de tests exécutés corresponde à votre plan. Si votre plan est "no_plan", $how_many est facultatif et est utilisé par défaut comme 1.

Il est tout à fait sûr d'imbriquer des blocs SKIP. Chaque bloc SKIP doit avoir une étiquette "SKIP", sinon Test::More ne pourra pas faire sa magie.

Ne sautez pas les tests qui échouent à cause d'un bug dans votre programme, ou parce que vous n'avez pas encore de code écrit. Pour cela, utilisez TODO. Lisez plus bas.

TODO: BLOCK
TODO: {
    local $TODO = $why if $condition;
    ...le code de test s'exécute normalement ici...
}

Déclare un bloc de tests dont vous vous attendez à ce qu'ils échouent, avec $why. Peut-être parce que vous n'avez pas résolu un bug ou que vous n'avez pas terminé une nouvelle fonctionnalité :

TODO: {
    local $TODO = "URI::Geller non terminé";
    my $card = "Huit de trèfle";
    is( URI::Geller->your_card, $card, 'Est-ce VOTRE carte ?' );
    my $spoon;
    URI::Geller->bend_spoon;
    is( $spoon, 'bent', "Gauchisme de cuillère, ce qui est original" );
}

Avec un bloc todo, les tests internes sont censés échouer. Test::More exécute normalement les tests, mais affiche des signaux spéciaux indiquant qu'ils sont "todo". Test::Harness interprétera les échecs comme des ok. Si quelque chose échoue, vous devriez avoir un todo.

Sinon, il le signalera comme un succès inattendu. Vous saurez alors que la tâche que vous aviez à faire est terminée et vous pourrez supprimer le marqueur TODO.

L'avantage des tests TODO, par rapport au simple commentaire d'un bloc de tests, est qu'ils constituent une liste TODO programmatique. Vous savez quelle quantité de travail reste à faire, vous êtes au courant des bugs existants et vous saurez immédiatement quand ils seront corrigés.

Une fois qu'un test TODO commence à réussir, déplacez-le simplement hors du bloc. Lorsque le bloc est vide, supprimez-le.

Notez que si vous laissez $TODO non défini ou indéfini, Test::More signalera les échecs normalement. Cela peut être utile pour marquer les tests comme étant censés échouer uniquement dans certaines conditions, par exemple :

TODO: {
    local $TODO = "$^O ne fonctionne pas encore. :(";
    ...
}
todo_skip
TODO: {
    todo_skip $pourquoi, $combien if $condition;
    ...code de test normal...
}

Avec les tests TODO, il est préférable que les tests s'exécutent réellement. Ainsi, vous saurez quand ils commenceront à passer. Parfois, ce n'est pas possible. Souvent, un test défaillant peut faire planter tout le programme ou le bloquer, même à l'intérieur d'un "eval BLOCK" avec et en utilisant "alarm". Dans ces cas extrêmes, vous n'avez d'autre choix que de sauter complètement les tests défectueux.

La syntaxe et le comportement sont similaires à ceux d'un "SKIP: BLOCK", à la différence près que les tests seront marqués comme échoués mais TODO. Test::Harness les interprétera comme passant.

Quand utiliser SKIP par rapport à TODO ?
Si c'est quelque chose que l'utilisateur pourrait ne pas être en mesure de faire, utilisez SKIP. Cela inclut les modules optionnels qui ne sont pas installés, l'exécution sous un système d'exploitation qui ne dispose pas de certaines fonctionnalités (comme fork() ou les liens symboliques), ou peut-être qu'une connexion Internet est nécessaire et qu'elle n'est pas disponible.

Si c'est quelque chose que le programmeur n'a pas encore fait, utilisez TODO. Ceci est destiné à tout code que vous n'avez pas encore écrit, ou à des bugs que vous n'avez pas encore corrigés, mais pour lesquels vous souhaitez mettre des tests dans votre script de test (toujours une bonne idée).

Contrôle des tests

BAIL_OUT
BAIL_OUT($raison);

Indique au système de test que les choses vont si mal que tous les tests devraient être interrompus. Cela inclut l'exécution de tout script de test supplémentaire.

Ceci est généralement utilisé lorsque les tests ne peuvent pas continuer, par exemple si un module critique échoue à la compilation ou si un utilitaire externe nécessaire n'est pas disponible, comme une connexion à une base de données qui échoue.

Le test se terminera avec le code 255.

Pour un contrôle encore meilleur, regardez Test::Most.

Fonctions de comparaison déconseillées

L'utilisation des fonctions suivantes est déconseillée car elles ne sont pas réellement des fonctions de test et ne produisent aucun diagnostic pour aider à comprendre ce qui s'est mal passé. Elles ont été écrites avant l'existence de is_deeply() car je n'arrivais pas à afficher une différence utile entre deux structures de données arbitraires.

Ces fonctions sont généralement utilisées à l'intérieur d'un ok().

ok( eq_array(\@got, \@expected) );

is_deeply() peut faire cela mieux et avec des diagnostics.

is_deeply( \@got, \@expected );

Elles pourraient être dépréciées dans les versions futures.

eq_array
my $is_eq = eq_array(\@got, \@expected);

Vérifie si deux tableaux sont équivalents. Il s'agit d'une vérification approfondie, donc les structures à plusieurs niveaux sont gérées correctement.

eq_hash
my $is_eq = eq_hash(\%got, \%expected);

Détermine si les deux hachages contiennent les mêmes clés et valeurs. Il s'agit d'une vérification approfondie.

eq_set
my $is_eq = eq_set(\@got, \@expected);

Similaire à eq_array(), sauf que l'ordre des éléments n'est pas important. Il s'agit d'une vérification approfondie, mais l'absence d'importance de l'ordre ne s'applique qu'au niveau supérieur.

ok( eq_set(\@got, \@expected) );

Il est préférable de l'écrire ainsi :

is_deeply( [sort @got], [sort @expected] );

NOTE Par accident historique, ce n'est pas une véritable comparaison d'ensembles. Bien que l'ordre des éléments n'ait pas d'importance, les éléments dupliqués en ont.

NOTE eq_set() ne sait pas comment gérer les références au niveau supérieur. L'exemple suivant est une comparaison qui pourrait ne pas fonctionner :

eq_set([\1, \2], [\2, \1]);

Test::Deep contient des fonctions de comparaison d'ensembles bien meilleures.

Extension et intégration de Test::More

Parfois, l'interface Test::More n'est pas tout à fait suffisante. Heureusement, Test::More est construit sur Test::Builder, qui fournit un backend unique et unifié que toute bibliothèque de test peut utiliser. Cela signifie que deux bibliothèques de test qui utilisent toutes deux Test::Builder peuvent être utilisées ensemble dans le même programme.

Si vous souhaitez simplement apporter quelques modifications au comportement des tests, vous pouvez accéder à l'objet Test::Builder sous-jacent comme ceci :

builder
my $test_builder = Test::More->builder;

Retourne l'objet Test::Builder sous-jacent à Test::More pour que vous puissiez jouer avec.

CODES DE SORTIE

Si tous vos tests ont réussi, Test::Builder se terminera avec zéro (ce qui est normal). Si quelque chose a échoué, il se terminera avec le nombre d'échecs. Si vous exécutez moins (ou plus) de tests que prévu, les tests manquants (ou supplémentaires) seront considérés comme des échecs. Si aucun test n'a jamais été exécuté, Test::Builder émettra un avertissement et se terminera avec 255. Si le test est décédé, même après avoir terminé avec succès tous ses tests, il sera toujours considéré comme un échec et se terminera avec 255.

Les codes de sortie sont donc...

0                   tous les tests réussis
255                 le test est décédé ou tous les tests sont réussis mais le nombre incorrect de tests a été exécuté
tout autre nombre    le nombre d'échecs (y compris les tests manquants ou supplémentaires)

Si vous échouez à plus de 254 tests, cela sera signalé comme 254.

NOTE Ce comportement pourrait disparaître dans les versions futures.

COMPATIBILITÉ

Test::More fonctionne avec des versions de Perl aussi anciennes que 5.8.1.

Le support des threads n'est pas très fiable avant la version 5.10.1, mais c'est parce que les threads ne sont pas très fiables avant la version 5.10.1.

Bien que Test::More soit un module de base dans les versions de Perl depuis 5.6.2, Test::More a évolué depuis, et toutes les fonctionnalités auxquelles vous êtes habitué ne seront pas présentes dans la version livrée de Test::More. Si vous écrivez un module, n'oubliez pas d'indiquer dans les métadonnées de votre package la version minimale de Test::More que vous exigez. Par exemple, si vous souhaitez utiliser done_testing() mais que vous souhaitez que votre script de test s'exécute sur Perl 5.10.0, vous devrez explicitement exiger Test::More > 0.88.

Les jalons clés des fonctionnalités comprennent :

sous-tests
Les sous-tests ont été publiés dans Test::More 0.94, qui est livré avec Perl 5.12.0. Les sous-tests n'appelaient pas implicitement done_testing() avant la version 0.96 ; le premier Perl avec cette correction était Perl 5.14.0 avec la version 0.98.
done_testing()
Ceci a été publié dans Test::More 0.88 et a été livré pour la première fois avec Perl dans la version 5.10.1 dans le cadre de Test::More 0.92.
cmp_ok()
Bien que cmp_ok() ait été introduit dans la version 0.40, la version 0.86 a corrigé un bug important pour le rendre sûr pour les objets surchargés ; la correction a été livrée pour la première fois avec Perl dans la version 5.10.1 dans le cadre de Test::More 0.92.
new_ok() note() et explain()
Ceux-ci ont été publiés dans Test::More 0.82, et ont été livrés pour la première fois avec Perl dans la version 5.10.1 dans le cadre de Test::More 0.92.

Il existe un historique complet des versions dans le fichier Changes, et les versions de Test::More incluses en tant que cœur peuvent être trouvées en utilisant Module::CoreList :

$ corelist -a Test::More

CAVEATS et NOTES

UTF-8 / "Caractère large dans l'impression"
Si vous utilisez UTF-8 ou d'autres caractères non ASCII avec Test::More, vous pourriez recevoir un avertissement "Wide character in print". L'utilisation de "binmode STDOUT, ":utf8"" ne le résoudra pas. Test::Builder (qui alimente Test::More) duplique STDOUT et STDERR. Ainsi, toute modification apportée à ceux-ci, y compris la modification de leurs disciplines de sortie, ne sera pas vue par Test::More.

Une solution consiste à appliquer des encodages à STDOUT et STDERR dès que possible et avant que Test::More (ou tout autre module de test) ne se charge.

use open ':std', ':encoding(UTF-8)';
use Test::More;

Une solution plus directe consiste à modifier les flux de fichiers utilisés par Test::Builder.

my $builder = Test::More->builder;
binmode $builder->output,         ":encoding(UTF-8)";
binmode $builder->failure_output, ":encoding(UTF-8)";
binmode $builder->todo_output,    ":encoding(UTF-8)";
Objets surchargés
Les objets surchargés en chaîne sont comparés en tant que chaînes (ou dans le cas de cmp_ok(), chaînes ou nombres selon ce qui convient à l'opérateur de comparaison). Cela empêche Test::More de pénétrer l'interface d'un objet, permettant de meilleurs tests en boîte noire. Donc, si une fonction commence à retourner des objets surchargés au lieu de chaînes nues, vos tests ne remarqueront pas la différence. C'est une bonne chose.

Cependant, cela signifie que des fonctions comme is_deeply() ne peuvent pas être utilisées pour tester les détails internes

Test::More(3perl)

Perl interface to a test suite

NAME

Test::More - Another testing module suite

SYNOPSIS

    use Test::More tests => 12; # Number of tests to run
    use Test::More;             # Number of tests to run is guessed

    ok( $condition, $name );
    is( $got, $expected, $name );
    isnt( $got, $expected, $name );
    cmp_ok( $got, $operator, $expected, $name );
    ne( $got, $expected, $name );
    like( $string, $regex, $name );
    unlike( $string, $regex, $name );
    can_ok( $module, $methods );
    use_ok( $module );

    # For testing modules
    require Module;
    Module->import();
    ok( Module->can_load(), 'Module can be loaded' );
    subtest 'Test my subroutine' => sub {
        my $result = my_subroutine();
        is( $result, 'expected value' );
        done_testing();
    };

DESCRIPTION

This module is intended to be a successor to Test.pm. It provides a set of testing routines that are simpler to learn, quicker to use and less prone to error than Test.pm.

See the synopsis for the most common routines.

See CAVEATS and NOTES for important information about using Test::More.

EXIT CODES

Test::More exits with 0 on success and non-zero on failure.

COMPATIBILITY

Test::More is compatible with Test.pm. You can drop Test::More in place of Test.pm and your tests should continue to work.

CAVEATS and NOTES

Floating Point Comparisons
Do not use is() to compare floating point numbers. Due to the nature of floating point arithmetic, direct comparisons are often unreliable. Use cmp_ok() with an appropriate operator (like ~=) instead.
Complex Data Structures
Testing complex data structures (e.g. nested arrays and hashes) can be tedious with Test::More's basic routines. You may wish to investigate Test::Deep, which provides more flexible testing functions for complex data structures.
Threads
Test::More will only be aware of threads if "use threads" has been done before Test::More is loaded. This is ok: 
use threads;
use Test::More;

This may cause problems:

use Test::More
use threads;

5.8.1 and above are supported. Anything below that has too many bugs.

HISTORY

This is a case of convergent evolution with Joshua Pritikin's Test module. I was largely unaware of its existence when I'd first written my own ok() routines. This module exists because I can't figure out how to easily wedge test names into Test's interface (along with a few other problems).

The goal here is to have a testing utility that's simple to learn, quick to use and difficult to trip yourself up with while still providing more flexibility than the existing Test.pm. As such, the names of the most common routines are kept tiny, special cases and magic side-effects are kept to a minimum. WYSIWYG.
