Test2::Event(3perl) Manuel des développeurs Perl Test2::Event(3perl)

Nom

Test2::Event - Classe de base pour les événements

Description

Classe de base pour tous les objets événement qui sont passés autour de Test2.

Synopsis

package Test2::Event::MyEvent;
use strict;
use warnings;
# Ceci fera de notre classe une sous-classe d'événement (obligatoire)
use base 'Test2::Event';
# Ajouter des accesseurs (optionnel)
# Vous n'êtes pas obligé d'utiliser HashBase, vous pouvez utiliser n'importe quel outil objet que vous voulez, ou vous pouvez créer vos propres accesseurs.
use Test2::Util::HashBase qw/foo bar baz/;
# Utilisez ceci si vous voulez que l'ancien API soit écrit pour vous, pour que cela fonctionne, vous aurez besoin d'implémenter la méthode facet_data().
use Test2::Util::Facets2Legacy;
# Opportunité d'initialiser quelques valeurs par défaut
sub init {
    my $self = shift;
    # Il n'y a pas d'autres arguments dans @_ 
    $self->set_foo('xxx') unless defined $self->foo;
    ...
}
# C'est la nouvelle façon de transmettre des données à Test2
sub facet_data {
    my $self = shift;
    # Récupérer les facettes communes comme 'about', 'trace', 'amnesty', et 'meta'
    my $facet_data = $self->common_facet_data();
    # Est-ce que vous faites une assertion ?
    $facet_data->{assert} = {pass => 1, details => 'mon assertion'};
    ...
    return $facet_data;
}
1;

Méthodes

Général

$trace = $e->trace
Obtient un instantané de la facette Test2::EventFacet::Trace tel qu'il était lorsque cet événement a été généré
$bool_or_undef = $e->related($e2)
Vérifie si 2 événements sont liés. Liés dans ce cas signifie que leurs traces partagent une signification, ce qui indique qu'ils ont été créés avec le même contexte (ou du moins par des contextes partageant un ID, ce qui est la même chose, à moins que quelqu'un ne fasse quelque chose de très mal).

Ceci peut être utilisé pour lier plusieurs événements générés par le même programme. Par exemple, un test raté comme "ok(0, "fail"" produira 2 événements, l'un étant un Test2::Event::Ok, l'autre un Test2::Event::Diag, les deux étant liés, car ils ont été créés dans le même contexte et par le même programme initial (bien que plusieurs programmes puissent avoir été dans le programme initial).

Ceci retournera "undef" si la relation ne peut pas être vérifiée, ce qui se produit si l'un ou l'autre des événements a une trace incomplète ou indéfinie. Ceci retournera 0 si les traces sont complètes mais ne correspondent pas. 1 sera retourné s'il y a une correspondance.

$e->add_amnesty({tag => $TAG, details => $DETAILS});
Ceci peut être utilisé pour ajouter de l'amnistie à cet événement. L'amnistie n'affecte que les assertions qui échouent, mais certains formateurs peuvent l'afficher pour les assertions qui réussissent, voire pour les non-assertions.

L'amnistie empêche qu'une assertion échouée ne fasse planter l'ensemble du test. En d'autres termes, elle marque un échec comme étant attendu et permis.

Note : C'est ainsi que le "TODO" est implémenté, c'est-à-dire "amnistie" avec le tag "TODO". Les détails sont la raison pour laquelle le TODO.

$uuid = $e->uuid
Si le marquage UUID est activé (voir Test::API), tout événement qui est passé par un hub sera marqué avec un UUID. Un nouvel événement ne sera pas marqué dans la plupart des cas.
$class = $e->load_facet($name)
Cette méthode est utilisée pour charger une facette par nom (ou clé). Elle tentera de charger la classe de la facette, et si elle réussit, retournera la classe qui a été chargée. Si elle échoue, elle retournera "undef". Elle met en cache le résultat au niveau de la classe pour que les appels suivants soient plus rapides.

Le paramètre $name doit être la clé utilisée pour accéder à la facette dans une table de facettes. Par exemple, la facette d'assertion a la clé 'assert', la facette d'informations a 'info', et la facette d'erreurs a 'errors'. Vous pouvez inclure ou omettre le 's' à la fin du nom, et la méthode est suffisamment intelligente pour essayer les deux, en vérifiant d'abord ce que vous avez fourni, et si elle ne le trouve pas, elle ajoutera ou supprimera le 's' et réessaiera.

@classes = $e->FACET_TYPES()
@classes = Test2::Event->FACET_TYPES()
Ceci retourne une liste de toutes les facettes qui ont été chargées en utilisant la méthode load_facet(). Ceci ne retourne aucune classe qui n'a pas été chargée, ou qui a été chargée directement sans appel à load_facet().

Note : Les facettes de type de base sont automatiquement chargées et remplies dans cette liste.

Nouvel API

$hashref = $e->common_facet_data();
Ceci peut être utilisé par les sous-classes pour générer un hashref de données de facette initial. Il remplira le hashref avec la trace, les métadonnées, l'amnistie et l'informations sur. Ces facettes sont presque toujours produites de la même manière pour tous les événements.
$hashref = $e->facet_data()
Si vous ne surchargez pas cette méthode, l'implémentation par défaut tentera de générer les données de facette à partir de l'ancien API. Cette génération est limitée à ce que l'ancien API peut fournir. Il est recommandé de surcharger cette méthode et d'écrire explicitement les données de facette.
$hashref = $e->facets()
Ceci prend le hashref de facet_data() et le bénit dans la classe correspondante "Test2::EventFacet::*". Si la classe ne peut pas être trouvée pour une facette, elle est passée sans modification.
@errors = $e->validate_facet_data();
@errors = $e->validate_facet_data(%params);
@errors = $e->validate_facet_data(\%facets, %params);
@errors = Test2::Event->validate_facet_data(%params);
@errors = Test2::Event->validate_facet_data(\%facets, %params);
Cette méthode validera les données de facette et retournera une liste d'erreurs. S'il n'y a pas d'erreurs, elle retournera une liste vide.

Elle peut être appelée en tant que méthode objet sans arguments, auquel cas la méthode facet_data() sera appelée pour obtenir les données de facette à valider.

Lorsqu'elle est appelée en tant que méthode objet, l'argument "\%facet_data" peut être omis.

Lorsqu'elle est appelée en tant que méthode de classe, l'argument "\%facet_data" est requis.

Les arguments restants seront absorbés dans une table %params.

Un seul paramètre est actuellement défini :

require_facet_class => $BOOL
Si défini à vrai (par défaut à faux), ceci rejettera toute facette pour laquelle la classe ne peut pas être trouvée. Par défaut, les facettes sans classe sont supposées être personnalisées et sont ignorées.

QU'EST-CE QUE LES FACETTES ?

Les facettes sont la manière dont les événements transmettent leur intention aux internes de Test2 et aux formateurs. Un événement sans facettes n'aura aucun effet intentionnel sur l'état général du test, et ne sera affiché dans presque aucun formateur, sauf peut-être pour indiquer qu'un événement de type inconnu a été vu.

Les facettes sont produites par la sous-routine facet_data(), que vous devriez presque toujours surcharger. facet_data() est censé retourner un hashref où chaque clé est le type de facette et la valeur sont les données pour cette facette, ou un tableau de hashrefs. Certaines facettes doivent être définies comme de simples hashrefs, d'autres comme des tableaux de hashrefs, et elles n'autorisent pas les deux.

facet_data() NE DOIT PAS bénir les données qu'il retourne, le hashref principal et les hashrefs de facette imbriqués DOIVENT être nus. Cependant, les éléments à l'intérieur de chaque facette peuvent être bénis. Les données retournées par cette méthode doivent également être des copies des données internes pour éviter les modifications accidentelles de l'état.

facets() prend les données de facet_data() et les bénit dans les classes "Test2::EventFacet::*". Ceci est rarement utilisé, mais les packages EventFacet sont principalement pour la commodité et la documentation. Les classes EventFacet ne sont pas utilisées en interne, mais les données directes sont utilisées.

Voici une liste des types de facettes par package. Les packages ne sont pas utilisés en interne, mais sont utilisés comme...

Conservez toute la structure du fichier.

Note : Chaque type unique de facette a le champ 'details'. Ce champ est toujours destiné à la consommation humaine et, lorsqu'il est fourni, doit expliquer le "pourquoi" de la facette. Tous les autres champs sont spécifiques à la facette.

about => {...}
Test2::EventFacet::About

Ceci contient des informations sur l'événement lui-même, comme le nom du paquet d'événement. Le champ "details" pour cette facette est un résumé général de l'événement.

assert => {...}
Test2::EventFacet::Assert

Cette facette est utilisée si une assertion a été faite. Le champ "details" de cette facette est la description de l'assertion.

control => {...}
Test2::EventFacet::Control

Cette facette est utilisée pour indiquer à Test2::Event::Hub des actions spéciales que l'événement doit provoquer. Des choses comme arrêter tous les tests, terminer le test actuel, etc. Dans cette facette, le champ "details" explique pourquoi toute action spéciale a été entreprise.

Note : C'est ainsi que le débranchement est implémenté.

meta => {...}
Test2::EventFacet::Meta

La facette meta contient toutes les métadonnées attachées à l'événement. Dans ce cas, le champ "details" n'a pas de signification particulière, mais il peut être présent si quelque chose a défini le champ 'details' dans l'événement.

parent => {...}
Test2::EventFacet::Parent

Cette facette contient des événements imbriqués et des détails similaires pour les sous-tests. Dans cette facette, le champ "details" sera généralement le nom du sous-test.

plan => {...}
Test2::EventFacet::Plan

Cette facette indique au système qu'un plan a été défini. Le champ "details" de celle-ci est normalement vide, mais lorsqu'il est présent, il explique pourquoi le plan est ainsi, c'est plus utile si le plan est de tout ignorer.

trace => {...}
Test2::EventFacet::Trace

Cette facette contient des informations relatives à quand et où l'événement a été généré. C'est ainsi que le fichier de test et le numéro de ligne d'un échec sont connus. Cette facette peut également vous aider à savoir si des tests sont liés.

Dans cette facette, le champ "details" remplace le message « échec à test_file.t ligne 42. » fourni dans un échec d'assertion.

amnesty => [{...}, ...]
Test2::EventFacet::Amnesty

La facette amnesty est une liste plutôt qu'un élément unique, c'est important car l'amnistie peut provenir de plusieurs sources à la fois.

Pour chaque instance d'amnistie, le champ "details" explique pourquoi l'amnistie a été accordée.

Note : En dehors des formateurs, l'amnistie sert uniquement à excuser une assertion ratée.

errors => [{...}, ...]
Test2::EventFacet::Error

La facette errors est une liste plutôt qu'un élément unique, n'importe quel nombre d'erreurs peut être listé. Dans cette facette, le champ "details" décrit l'erreur, ou peut contenir le message d'erreur lui-même (comme une exception). En Perl, les exceptions peuvent être des objets sérialisés, donc les données de cette facette peuvent contenir des éléments imbriqués qui sont sérialisés.

Toutes les erreurs ne sont pas considérées comme catastrophiques, il y a un champ "fail" qui doit être défini pour qu'une erreur provoque l'échec du test.

Note : Cette facette est unique car le nom du champ est 'errors' tandis que le package est 'Error'. C'est parce qu'il s'agit du seul type de facette qui est à la fois une liste et a un nom où le pluriel n'est pas le même que le singulier. Cela peut prêter à confusion, mais je le trouve moins confus que l'alternative.

info => [{...}, ...]
Test2::EventFacet::Info

La facette info est une liste plutôt qu'un élément unique, n'importe quelle quantité d'informations supplémentaires peut être attachée à un événement. Certaines informations peuvent être des diagnostics critiques, d'autres peuvent être de simples commentaires, cela est déterminé par le drapeau "debug".

Pour cette facette, le champ "details" est l'info elle-même. Cette info peut être une chaîne de caractères ou une structure de données à afficher. C'est l'un des rares types de facettes qui peuvent contenir des éléments sérialisés.

API OBSOLÈTE

$bool = $e->causes_fail
Renvoie vrai si cet événement doit entraîner un échec du test. Généralement, cela devrait être faux.
$bool = $e->increments_count
Doit être vrai si cet événement doit incrémenter le compteur de tests.
$e->callback($hub)
Si votre événement nécessite des effets supplémentaires sur Test2::Hub, vous pouvez remplacer cette méthode.

Ceci est appelé AVANT que votre événement ne soit envoyé au formateur.

$num = $e->nested
Si cet événement est imbriqué dans d'autres événements, cela devrait être la profondeur d'imbrication. (Ceci est principalement pour les sous-tests)
$bool = $e->global
Définissez ceci sur vrai si votre événement est global, c'est-à-dire que tous les threads et processus doivent le voir indépendamment de quand ou où il est généré. Ce n'est pas une chose courante, elle est utilisée pour le débranchement et le saut de tous pour terminer le test.
$code = $e->terminate
Ceci est appelé APRÈS que votre événement ait été envoyé au formateur. Cela devrait normalement renvoyer undef, ne changez que si votre événement doit provoquer la sortie immédiate du test.

Si vous voulez que votre événement provoque la sortie du test, vous devez renvoyer le code de sortie ici. Le code de sortie 0 signifie succès, tout autre nombre signifie échec.

Ceci est utilisé par Test2::Event::Plan pour sortir avec 0 lorsque le plan est 'skip_all'. Ceci est également utilisé par Test2::Event:Bail pour forcer la sortie du test avec un échec.

Ceci est appelé après que l'événement a été envoyé au formateur pour s'assurer que l'événement est vu et compris.

$msg = $e->summary
On s'attend à ce que ce soit un résumé lisible par l'homme de l'événement. Idéalement, ce devrait être une seule ligne, mais vous pouvez utiliser plusieurs lignes si nécessaire. Ceci est destiné à la consommation humaine. Vous n'avez pas besoin de le rendre facile pour les machines.

Par défaut, il renvoie simplement le nom du package de l'événement.

($count, $directive, $reason) = $e->sets_plan()
Vérifie si cet événement définit le plan de test. Renvoie une liste vide si ce n'est pas le cas. S'il le fait, renvoie une liste de 1 à 3 éléments dans l'ordre : compteur de tests attendu, directive de test, raison de la directive.
$bool = $e->diagnostics
Vrai si l'événement contient des informations de diagnostic. Ceci est utile car un harness non-verbeux peut choisir de masquer les événements qui n'entrent pas dans cette catégorie. Certains formateurs peuvent choisir d'envoyer ceux-ci à STDERR au lieu de STDOUT pour s'assurer qu'ils sont vus.
$bool = $e->no_display
Faux par défaut. Ceci renverra vrai pour les événements qui ne doivent pas être affichés par les formateurs.
$id = $e->in_subtest
Si l'événement est à l'intérieur d'un sous-test, il devrait avoir l'ID du sous-test.
$id = $e->subtest_id
Si l'événement est un événement de fin de sous-test, il devrait contenir l'ID du sous-test.

MÉTADONNÉES TIERS

Cet objet consomme Test2::Util::ExternalMeta qui fournit un moyen cohérent d'attacher des métadonnées aux instances de cette classe. Il est utile pour les outils, les plugins et autres extensions.
