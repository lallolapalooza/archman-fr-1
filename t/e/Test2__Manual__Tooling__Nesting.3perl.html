Test2::Manual::Tooling::Nesting(3perl) Guide de référence des programmeurs Perl Test2::Manual::Tooling::Nesting(3perl)

NOM

Test2::Manual::Tooling::Nesting - Tutoriel pour utiliser d'autres outils au sein des vôtres.

DESCRIPTION

Parfois, vous vous retrouvez à écrire le même modèle de test encore et encore. Dans de tels cas, vous pourriez vouloir encapsuler la logique dans une nouvelle fonction de test qui appelle plusieurs outils ensemble. Cela semble assez facile, mais peut causer des maux de tête si ce n'est pas fait correctement.

MANIÈRE NAÏVE

Disons que vous vous retrouvez à écrire le même modèle de test encore et encore pour plusieurs objets :

my $obj1 = $class1->new;
is($obj1->foo, 'foo', "got foo");
is($obj1->bar, 'bar', "got bar");
my $obj2 = $class1->new;
is($obj2->foo, 'foo', "got foo");
is($obj2->bar, 'bar', "got bar");
... 10 fois de plus pour les classes 2-12

La manière naïve de faire cela est d'écrire une fonction check_class() comme ceci :

sub check_class {
    my $class = shift;
    my $obj = $class->new;
    is($obj->foo, 'foo', "got foo");
    is($obj->bar, 'bar', "got bar");
}
check_class($class1);
check_class($class2);
check_class($class3);
...

Cela semblera fonctionner correctement, et vous pourriez ne pas remarquer de problèmes, tant que les tests réussissent.

QU'EST-CE QUI NE VA PAS ?

Les problèmes avec l'approche naïve deviennent évidents si les choses commencent à échouer. Les diagnostics qui vous indiquent quel fichier et quelle ligne l'échec s'est produit seront incorrects. L'échec sera signalé à la ligne à l'intérieur de "check_class", et non à la ligne où check_class() a été appelée. C'est un problème car cela vous laisse sans idée de quelle classe échoue.

COMMENT RÉPARER ?

Heureusement, c'est extrêmement facile à réparer. Vous devez obtenir un objet de contexte au début de votre fonction, et le libérer à la fin... oui, c'est aussi simple que ça.

use Test2::API qw/context/;
sub check_class {
    my $class = shift;
    my $ctx = context();
    my $obj = $class->new;
    is($obj->foo, 'foo', "got foo");
    is($obj->bar, 'bar', "got bar");
    $ctx->release;
}

Voyez, c'était facile. Avec ces 2 lignes supplémentaires, nous avons maintenant un rapport de fichier+ligne correct. Les outils imbriqués trouveront le contexte que nous avons acquis ici, et sauront utiliser ses numéros de fichier et de ligne.

L'ANCIENNE MANIÈRE (NE LE FAITES PLUS MAINTENANT)

Avec Test::Builder, il y avait une variable globale appelée $Test::Builder::Level qui aidait à résoudre ce problème :

sub check_class {
    my $class = shift;
    local $Test::Builder::Level = $Test::Builder::Level + 1;
    my $obj = $class->new;
    is($obj->foo, 'foo', "got foo");
    is($obj->bar, 'bar', "got bar");
}

Cette variable fonctionnait assez bien (et fonctionnera toujours), mais elle n'était pas très découvrable. Un autre problème avec cette variable est qu'elle devient encombrante si vous avez une structure de code plus profondément imbriquée appelant les outils imbriqués, vous pourriez avoir besoin de compter les cadres de pile, et espérer qu'ils ne changent jamais en raison d'un module tiers. La solution de contexte n'a pas de tels inconvénients.
