Test::Tester(3perl) Guide de référence des programmeurs Perl Test::Tester(3perl)

NOM

Test::Tester - Facilite le test des modules de test construits avec Test::Builder

SYNTAXE

use Test::Tester tests => 6;
use Test::MyStyle;
check_test(
  sub {
    is_mystyle_eq("this", "that", "not eq");
  },
  {
    ok => 0, # attendre cet échec
    name => "not eq",
    diag => "Expected: 'this'\nGot: 'that'",
  }
);

ou

use Test::Tester tests => 6;
use Test::MyStyle;
check_test(
  sub {
    is_mystyle_qr("this", "that", "not matching");
  },
  {
    ok => 0, # attendre cet échec
    name => "not matching",
    diag => qr/Expected: 'this'\s+Got: 'that'/,
  }
);

ou

use Test::Tester;
use Test::More tests => 3;
use Test::MyStyle;
my ($premature, @results) = run_tests(
  sub {
    is_database_alive("dbname");
  }
);
# maintenant utiliser Test::More::like pour vérifier la sortie diagnostique
like($results[0]->{diag}, "/^Database ping took \\d+ seconds$", "diag");

DESCRIPTION

Si vous avez écrit un module de test basé sur Test::Builder, Test::Tester vous permet de le tester avec un minimum d'effort.

COMMENT UTILISER (LA FAÇON FACILE)

À partir de la version 0.08, Test::Tester ne vous oblige plus à inclure quoi que ce soit de spécial dans vos modules de test. Tout ce que vous avez à faire est

use Test::Tester;

dans votre script de test **avant** tout autre module basé sur Test::Builder, et c'est parti.

D'autres modules basés sur Test::Builder peuvent être utilisés pour aider aux tests. En fait, vous pouvez même utiliser des fonctions de votre module pour tester d'autres fonctions du même module (bien que cela soit possible, ce n'est probablement pas une bonne idée, si votre module a des bugs, l'utiliser pour se tester lui-même pourrait donner de mauvaises réponses).

La façon la plus simple de tester est de faire quelque chose comme

check_test(
  sub { is_mystyle_eq("this", "that", "not eq") },
  {
    ok => 0, # nous attendons que le test échoue
    name => "not eq",
    diag => "Expected: 'this'\nGot: 'that'",
  }
);

cela exécutera le test is_mystyle_eq, capturera ses résultats et vérifiera qu'ils sont conformes aux attentes.

Vous pourriez avoir besoin d'examiner les résultats des tests d'une manière plus flexible. Par exemple, la sortie diagnostique peut être assez longue ou complexe, ou elle peut impliquer quelque chose que vous ne pouvez pas prédire à l'avance, comme un horodatage. Dans ce cas, vous pouvez obtenir un accès direct aux résultats des tests :

my ($premature, @results) = run_tests(
  sub {
    is_database_alive("dbname");
  }
);
like($result[0]->{diag}, "/^Database ping took \\d+ seconds$", "diag");

ou

check_test(
  sub { is_mystyle_qr("this", "that", "not matching") },
  {
    ok => 0, # nous attendons que le test échoue
    name => "not matching",
    diag => qr/Expected: 'this'\s+Got: 'that'/,
  }
);

Nous ne pouvons pas prédire combien de temps le ping de la base de données prendra, nous utilisons donc le test like() de Test::More pour vérifier que la chaîne diagnostique est de la bonne forme.

COMMENT UTILISER (LA FAÇON DIFFICLE)

Ceci est là uniquement pour des raisons de compatibilité ascendante

Faites en sorte que votre module utilise l'objet Test::Tester::Capture au lieu de celui de Test::Builder. Comment faire cela dépend de votre module, mais en supposant que votre module conserve l'objet Test::Builder dans $Test et que toutes vos routines de test y accèdent via $Test, alors fournir une fonction similaire à celle-ci

sub set_builder
{
  $Test = shift;
}

devrait permettre à vos scripts de test de faire

Test::YourModule::set_builder(Test::Tester->capture);

et après cela, tous les tests à l'intérieur de votre module seront capturés.

RÉSULTATS DES TESTS

Le résultat de chaque test est capturé dans une table de hachage. Ces tables de hachage sont les mêmes que celles retournées par Test::Builder->details, mais avec quelques champs supplémentaires.

Ces champs sont documentés dans Test::Builder dans la fonction details()

ok
Le test a-t-il réussi ?
actual_ok
Le test a-t-il vraiment réussi ? C'est-à-dire, le succès vient-il de Test::Builder->ok() ou a-t-il réussi parce que c'était un test TODO ?
name
Le nom fourni pour le test.
type
Quel type de test ? Les possibilités incluent skip, todo, etc. Voir Test::Builder pour plus de détails.
reason
La raison du skip, todo, etc. Voir Test::Builder pour plus de détails.

Ces champs sont exclusifs à Test::Tester.

diag
Tous les diagnostics qui ont été affichés pour le test. Ceci inclut seulement les diagnostics affichés **après** la déclaration du résultat du test.

Notez que Test::Builder garantit que tous les diagnostics se terminent par un \n et que dans les versions précédentes de Test::Tester, il était essentiel que vous ayez le \n final dans vos diagnostics attendus. À partir de la version 0.10, Test::Tester ajoutera le \n si vous l'avez oublié. Il n'ajoutera pas de \n si vous n'attendez aucun diagnostic. Voir ci-dessous pour de l'aide à la recherche de problèmes difficiles à identifier liés aux espaces et aux tabulations.

depth
Cela vous permet de vérifier que votre module de test définit la bonne valeur pour $Test::Builder::Level et donc donne le bon nom de fichier et numéro de ligne lorsqu'un test échoue. Il est calculé en examinant caller() et $Test::Builder::Level. Il doit compter le nombre de sous-routines avant de sauter dans la fonction que vous testez. Donc, par exemple dans 
run_tests( sub { my_test_function("a", "b") } );

la profondeur doit être 1 et dans

sub deeper { my_test_function("a", "b") }
run_tests(sub { deeper() });

la profondeur doit être 2, c'est-à-dire 1 pour le sub {} et un pour deeper(). Cela peut sembler un peu complexe, mais si vos tests ressemblent aux exemples simples de ce document, vous n'avez pas à vous en soucier car la profondeur sera toujours de 1 et c'est ce que Test::Tester attend par défaut.

Note : si vous ne spécifiez pas de valeur pour la profondeur dans check_test(), elle est automatiquement comparée à 1. Si vous voulez vraiment ignorer le test de profondeur, passez undef.

Note : la profondeur ne sera pas calculée correctement pour les tests qui s'exécutent à partir d'un gestionnaire de signaux ou d'un bloc END ou de tout autre endroit qui masque la pile d'appels.

Certaines des fonctions de Test::Tester retournent des tableaux de ces tables de hachage, tout comme Test::Builder->details. C'est-à-dire que la table de hachage pour le premier test sera l'élément d'indice 1 du tableau (pas 0). L'élément 0 ne sera pas une table de hachage, ce sera une chaîne contenant toute sortie diagnostique qui est intervenue avant les premiers résultats de test. Ceci devrait généralement être vide. Si ce n'est pas le cas, cela signifie que quelque chose a produit des diagnostics avant que les résultats des tests ne soient affichés.

ESPACES ET TABULATIONS

Les apparences peuvent être trompeuses, surtout lorsqu'il s'agit de vide. Si vous vous grattez la tête en essayant de comprendre pourquoi Test::Tester dit que vos diagnostics sont faux alors qu'ils semblent parfaits, la réponse est probablement les espaces blancs. À partir de la version 0.10, Test::Tester entoure les valeurs de diag attendues et obtenues de guillemets simples pour faciliter la détection des espaces blancs de fin. Donc dans cet exemple

# Diag obtenu (5 octets) :
# 'abcd '
# Diag attendu (4 octets) :
# 'abcd'

il est tout à fait clair qu'il y a un espace à la fin de la première chaîne. Une autre façon de résoudre ce problème est d'utiliser la couleur et l'inversion de vidéo sur un terminal ANSI. Voir ci-dessous COLOUR si vous le souhaitez.

Malheureusement, cela ne suffit parfois pas. Ni la couleur ni les guillemets ne vous aideront avec des problèmes impliquant des tabulations, d'autres caractères non imprimables et certains types de problèmes inhérents à Unicode. Pour y remédier, vous pouvez basculer Test::Tester dans un mode dans lequel tous les caractères « délicats » sont affichés sous forme de \{xx}. Les caractères délicats sont ceux

NOMBRE

Test::Tester - Module de test avec capture des résultats de test

SINTAXIS

use Test::Tester;

DESCRIPCIÓN

Test::Tester est un module Perl qui capture les résultats des tests et fournit un moyen d'exécuter des tests avec une sortie détaillée. Il permet l'exécution de sous-routines de test et l'enregistrement des résultats des tests, y compris la possibilité d'activer ou de désactiver des fonctionnalités spécifiques telles que la gestion des codes ASCII et la sortie couleur.

CÓMO USAR (LA FORMA FÁCIL)

La façon la plus simple d'utiliser Test::Tester est d'appeler run_tests() avec une sous-routine de test. Cette méthode capture automatiquement tous les résultats des tests et fournit des diagnostics pour toute divergence constatée.

CÓMO USAR (LA FORMA DIFÍCIL)

Pour utiliser Test::Tester de manière plus contrôlée, vous pouvez appeler check_tests() avec une sous-routine de test et un tableau de résultats attendus. Cette méthode combine les fonctionnalités de run_tests() et cmp_tests() pour vérifier les résultats des tests et fournir des diagnostics.

RESULTADOS DE PRUEBA

Test::Tester capture les résultats des tests et fournit des diagnostics pour toute divergence constatée. Les résultats peuvent être examinés à l'aide de la variable $premature, qui contient la sortie de diagnostic avant le premier test, et @results, qui est un tableau de hachages de résultats de test.

ESPACIOS Y TABULADORES

Test::Tester permet la gestion des codes ASCII inférieurs à 33 ou supérieurs à 126. Cela rend la sortie plus difficile à lire mais beaucoup plus facile à trouver des différences subtiles entre les chaînes de caractères. Pour activer ce mode, vous pouvez soit appeler show_space() dans votre script de test, soit définir la variable d'environnement "TESTTESTERSPACE" sur une valeur vraie. L'exemple ci-dessus ressemblerait alors à ceci :

# Got diag (5 bytes):
# abcd\x{20}
# Expected diag (4 bytes):
# abcd

COLORES

Si vous préférez utiliser la couleur comme moyen de trouver des caractères d'espacement difficiles, vous pouvez définir la variable d'environnement "TESTTESTCOLOUR" sur une paire de couleurs séparées par des virgules, la première pour le premier plan, la seconde pour l'arrière-plan. Par exemple, "white,red" affichera du texte blanc sur fond rouge. Cela nécessite le module Term::ANSIColor. Vous pouvez spécifier n'importe quelle couleur acceptable pour la fonction Term::ANSIColor::color.

Si vous écrivez « colour » différemment, ce n'est pas un problème. La variable "TESTTESTERCOLOR" fonctionne également (si les deux sont définies, l'orthographe britannique l'emporte).

FUNCIONES EXPORTADAS

($premature, @results) = run_tests(\&test_sub)

\&test_sub est une référence à une sous-routine.

run_tests exécute la sous-routine dans $test_sub et capture les résultats de tous les tests qu'elle contient. Vous pouvez exécuter plus d'un test dans cette sous-routine si vous le souhaitez.

$premature est une chaîne de caractères contenant tout message de diagnostic antérieur au premier test.

@results est un tableau de hachages de résultats de test.

cmp_result(\%result, \%expect,$name)

\%result est une référence à un hachage de résultat de test.

\%expect est une référence à un hachage de valeurs attendues pour le résultat du test.

cmp_result compare le résultat avec les valeurs attendues. S'il trouve des différences, il affiche des diagnostics. Vous pouvez omettre n'importe quel champ du résultat attendu et cmp_result n'effectuera pas la comparaison de ce champ.

cmp_results(\@results, \@expects,$name)

\@results est une référence à un tableau de résultats de test.

\@expects est une référence à un tableau de références de hachages.

cmp_results vérifie que les résultats correspondent aux résultats attendus et, en cas de différences, affiche des diagnostics. Il vérifie d'abord que le nombre d'éléments dans \@results et \@expects est le même. Ensuite, il parcourt chaque résultat en le comparant au résultat attendu, comme dans cmp_result() ci-dessus.

($premature, @results) = check_tests(\&test_sub, \@expects,$name)

\&test_sub est une référence à une sous-routine.

\@expect est une référence à un tableau de références de hachages qui sont les résultats de test attendus.

check_tests combine run_tests et cmp_tests en un seul appel. Il vérifie également si les tests sont morts à un moment donné.

Il renvoie les mêmes valeurs que run_tests, de sorte que vous puissiez examiner davantage les résultats des tests si nécessaire.

($premature, @results) = check_test(\&test_sub, \%expect,$name)

\&test_sub est une référence à une sous-routine.

\%expect est une référence à un hachage de valeurs attendues pour le résultat du test.

check_test est un wrapper autour de check_tests. Il combine run_tests et cmp_tests en un seul appel, vérifiant si le test est mort. Il suppose qu'un seul test est exécuté à l'intérieur de \&test_sub et inclut un test pour s'en assurer.

Il renvoie les mêmes valeurs que run_tests, de sorte que vous puissiez examiner davantage les résultats des tests si nécessaire.

show_space()

Active l'échappement des caractères comme décrit dans la section ESPACES ET TABULATEURS.

CÓMO FUNCIONA

Normalement, un module de test (appelons-le Test:MyStyle) appelle Test::Builder->new pour obtenir l'objet Test::Builder. Test::MyStyle appelle des méthodes sur cet objet pour enregistrer des informations sur les résultats des tests. Lorsque Test::Tester est chargé, il remplace la méthode new() de Test::Builder par une qui renvoie un objet Test::Tester::Delegate. La plupart du temps, cet objet se comporte comme le véritable objet Test::Builder. Toutes les méthodes appelées sont déléguées au véritable objet Test::Builder afin que tout fonctionne parfaitement. Cependant, une fois que nous entrons en mode test, les appels de méthode ne sont plus transmis au véritable objet Test::Builder, mais vont à l'objet Test::Tester::Capture. Cet objet ressemble exactement au véritable objet Test::Builder, sauf qu'au lieu de produire des résultats de test et des diagnostics, il enregistre simplement toutes les informations pour une analyse ultérieure.

ADVERTENCIAS

La prise en charge de l'appel de Test::Builder->note est minimale. Elle est implémentée comme un stub vide, de sorte que les modules qui l'utilisent ne planteront pas mais les appels ne seront pas enregistrés à des fins de test comme les autres. Patchs bienvenus.

VER TAMBIÉN

Test::Builder la source de la qualité des tests. Test::Builder::Tester pour une approche alternative du problème abordé par Test::Tester - capture les chaînes de caractères produites par Test::Builder. Cela signifie que vous ne pouvez pas obtenir d'accès séparé aux informations individuelles et que vous devez prédire exactement ce que votre test produira.
