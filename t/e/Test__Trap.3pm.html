Test::Trap(3) Documentation Perl fournie par l'utilisateur Test::Trap(3)

NOM

Test::Trap - Intercepter les codes de sortie, exceptions, sorties, etc.

VERSION

Version 0.3.5

SYNOPIS

use Test::More;
use Test::Trap;
my @r = trap { some_code(@some_parameters) };
is ( $trap->exit, 1, 'On attend que &some_code$exit avec 1' );
is ( $trap->stdout, '', 'On n\'attend pas de STDOUT' );
like ( $trap->stderr, qr/^Mauvais parametres; sortie\b/, 'On attend des avertissements.' );

DESCRIPTION

Principalement (mais pas exclusivement) pour une utilisation dans les scripts de test : Un bloc eval amélioré, configurable et extensible, mais qui intercepte par défaut les exceptions (Perl), les sorties (Perl) sur STDOUT, STDERR, les avertissements, les codes de sortie potentiels et les valeurs de retour des blocs de code testés.

Les valeurs collectées par la dernière interception peuvent ensuite être interrogées ou testées via un objet d'interception spécial.

EXPORT

Une fonction et un scalaire peuvent être exportés sous n'importe quel nom. La fonction (par défaut nommée "trap") est analogue au eval() en bloc, et le scalaire (par défaut nommé $trap) est l'analogue correspondant à $@.

Optionnellement, vous pouvez spécifier les couches de l'interception exportée. Les couches peuvent être spécifiées par leur nom, avec un sigil deux-points. Plusieurs couches peuvent être données dans une liste, ou simplement concaténées comme ":flow:stderr:warn".

(Pour l'utilisateur avancé, vous pouvez également spécifier des implémentations de couches anonymes - c'est-à-dire une sous-routine appropriée.)

Voir ci-dessous pour une liste des couches intégrées, dont la plupart sont activées par défaut. Notez, enfin, que l'ordre des couches est important : la couche :raw est toujours en bas (tout ce qui est en dessous est ignoré), et toutes les autres couches de "contrôle de flux" utilisées devraient y être placées.

FONCTION

trap BLOC

Cette fonction peut être exportée sous n'importe quel nom, mais par défaut, elle s'appelle "trap".

Par défaut, elle intercepte les exceptions (comme l'évaluation de bloc), mais aussi les sorties et les codes de sortie, les retours et les valeurs de retour, le contexte, et les sorties (Perl) sur STDOUT ou STDERR, ainsi que les avertissements. Toutes les informations interceptées peuvent être interrogées via l'objet d'interception, qui est par défaut exporté sous le nom $trap, mais peut être exporté sous n'importe quel nom.

La valeur retournée par "trap" imite celle retournée par "eval" : Si le BLOC devait échouer ou sortir, elle retourne une valeur indéfinie en contexte scalaire ou une liste vide en contexte liste ; sinon, elle retourne ce que le BLOC retournerait dans le contexte donné (également disponible en tant que valeurs de retour interceptées).

COUCHES D'INTERCEPTION

Ce que la fonction "trap" intercepte exactement dépend des couches de l'interception. Il est possible d'en enregistrer d'autres (voir Test::Trap::Builder), mais les couches suivantes sont prédéfinies par ce module :

:raw

La seule couche terminale intégrée, à laquelle le traitement des couches s'arrête, et l'appel réel du code utilisateur est effectué. En cas de succès, elle collecte la ou les valeurs de retour dans le contexte approprié. Appliquer la couche :raw sur une interception supprimera à toutes fins utiles toutes les couches inférieures.

:die

La couche qui émule l'évaluation de bloc, interceptant les exceptions normales.

:exit

La troisième couche de "contrôle de flux", capturant les codes de sortie si quelque chose utilise dans la portée dynamique de l'interception appelle CORE::GLOBAL::exit(). (Voir CAVEATS ci-dessous pour plus d'informations.)

:flow

Un raccourci pour :raw:die:exit (qui applique effectivement les trois couches à l'interception). Puisque cela inclut :raw, c'est également terminal : Appliquer :flow sur une interception supprimera effectivement toutes les couches inférieures.

:stdout, :stderr

Couches interceptant la sortie Perl sur STDOUT et STDERR, respectivement.

:stdout(perlio), :stderr(perlio)

Comme ci-dessus, mais en spécifiant une stratégie de capture utilisant PerlIO::scalar. Si cette stratégie n'est pas disponible (typiquement si PerlIO ne l'est pas), c'est une erreur. Voir "STRATÉGIES DE CAPTURE".

:stdout(tempfile), :stderr(tempfile)

Comme ci-dessus, mais en spécifiant une stratégie de capture utilisant File::Temp. Notez que c'est la stratégie par défaut, à moins que la couche :output() ne soit utilisée pour définir un autre défaut. Voir "STRATÉGIES DE CAPTURE".

:stdout(a;b;c), :stderr(a,b,c)

(La syntaxe avec virgules ou points-virgules est autorisée, ainsi que n'importe quel nombre de noms dans la liste.) Comme ci-dessus, mais en spécifiant la stratégie de capture par le premier nom existant parmi a, b, et c. Si aucune stratégie de ce type n'est trouvée, c'est une erreur. Voir "STRATÉGIES DE CAPTURE".

:warn

Une couche qui intercepte les avertissements, avec un teedage supplémentaire : Si STDERR est ouvert, elle affichera également les avertissements là. (Cette sortie peut être interceptée par la couche :stderr, qu'elle soit au-dessus ou en dessous de la couche :warn.)

:default

Un raccourci pour :raw:die:exit:stdout:stderr:warn (qui applique effectivement les six couches à l'interception). Puisque cela inclut :raw, c'est également terminal : Appliquer :default sur une interception supprimera effectivement toutes les couches inférieures.

L'autre propriété intéressante de :default est qu'il s'agit de ce avec quoi chaque interception commence : Pour ne pas inclure les six couches qui composent :default, vous devez appliquer une couche terminale (telle que :raw ou :flow) sur l'interception.

:on_fail(m)

Une couche (non-défaut, non-interception) qui installe une méthode de rappel (par nom) m à exécuter en cas d'échec de test. Pour exécuter la méthode "diag_all" à chaque échec de test :

use Test::Trap qw/ :on_fail(diag_all) /;

:void, :scalar, :list

Ces couches (non-défaut, non-interception) feront en sorte que le code utilisateur intercepté soit exécuté dans un contexte void, scalaire ou liste, respectivement. (Par défaut, l'interception propage le contexte, c'est-à-dire qu'elle exécute le code dans le contexte où se trouve l'interception elle-même.)

Si plus d'une de ces couches sont appliquées à l'interception, la plus profonde (c'est-à-dire la plus à gauche) a la priorité :

use Test::Trap qw/ :scalar:void:list /;
trap { 42, 13 };
$trap->return_is_deeply( [ 13 ], 'Virgule scalaire.' );

:output(a;b;c)

Une couche (non-défaut, non-interception) qui définit la stratégie de capture par défaut pour toutes les couches d'interception de sortie (":stdout", ":stderr", ou d'autres définies de manière similaire) situées en dessous.

use Test::Trap qw/ :output(systemsafe) /;
trap { system echo => 'Bonjour Unix!' }; # intercepté !
use Test::Trap qw/ :flow:stderr:output(systemsafe):stdout /;
trap { system echo => 'Bonjour Unix!' }; # *pas* intercepté !
trap { system q/ echo 'Bonjour Unix!' >&2 / }; # intercepté !

Voir "STRATÉGIES DE CAPTURE".

STRATÉGIES DE CAPTURE

La manière dont la sortie est interceptée dépend de la stratégie de capture utilisée. Il est possible d'en enregistrer d'autres (voir Test::Trap::Builder), mais les stratégies suivantes sont prédéfinies

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

-défini par ce module :

tempfile

La stratégie de capture par défaut, fournie par Test::Trap::Builder::TempFile, dans laquelle la sortie est temporairement redirigée vers (et relue depuis) un fichier temporaire.

tempfile-preserve

Une variante de la stratégie de capture fournie par Test::Trap::Builder::TempFile, dans laquelle les descripteurs utilisés pour écrire et lire du fichier temporaire sont tous deux binmodés avec les mêmes couches perlio que les descripteurs de sortie piégés avaient initialement.

Attention : Si le descripteur a des couches perlio personnalisées, elles peuvent (ou non) ne pas s'appliquer aux descripteurs de lecture et d'écriture du fichier temporaire.

systemsafe

Une stratégie de capture fournie par Test::Trap::Builder::SystemSafe, similaire à la stratégie par défaut, sauf qu'elle sort sur des descripteurs de fichiers avec les mêmes descripteurs de fichiers que ceux du descripteur de sortie piégé avaient initialement, et peut donc être utilisée pour piéger la sortie de processus débranchés, y compris system().

Cette stratégie peut être « sûre » par rapport aux processus débranchés, mais elle est fragile. D'une part, elle ne fonctionne qu'avec des descripteurs qui ont des descripteurs de fichiers « réels ». D'autre part, elle dépend de la disponibilité des descripteurs de fichiers d'origine après leur fermeture. (Si des gestionnaires de signaux ou des threads ouvrent des fichiers, ils ne seront peut-être pas disponibles.) Et elle peut échouer d'autres manières. Mais par rapport aux processus débranchés, les autres stratégies prédéfinies échoueront silencieusement à piéger, tout comme des stratégies similaires et simples. Celle-ci, lorsqu'elle ne plante pas, piégera cette sortie.

systemsafe-preserve

Une variante de la stratégie de capture fournie par Test::Trap::Builder::SystemSafe, dans laquelle les descripteurs utilisés pour écrire et lire du fichier temporaire sont tous deux binmodés avec les mêmes couches perlio que les descripteurs de sortie piégés avaient initialement.

Attention : Si le descripteur a des couches perlio personnalisées, elles peuvent (ou non) ne pas s'appliquer aux descripteurs de lecture et d'écriture du fichier temporaire.

perlio

Une stratégie de capture fournie par Test::Trap::Builder::PerlIO, dans laquelle la sortie est temporairement redirigée vers un fichier en mémoire via PerlIO::scalar.

Si PerlIO::scalar n'est pas disponible, cette stratégie ne l'est pas non plus.

ACCESSEURS DE RÉSULTATS

Les méthodes suivantes peuvent être appelées sur les objets pièges après qu'un piège a été déclenché, et accèdent au résultat de l'exécution.

Toute propriété sera undef si elle n'a pas été effectivement piégée – que ce soit parce qu'il n'y a pas de couche pour les piéger ou parce que le contrôle de flux les a contournées. (S'il existe une couche de piégeage active et réussie, les chaînes vides et les tableaux vides piégés seront bien sûr définis.)

Lorsque les propriétés sont définies, leurs valeurs seront les suivantes :

leaveby

Une chaîne indiquant comment le piège s'est terminé : "return", "die", ou "exit".

die

L'exception, si le dernier piège en a levé une.

exit

Le code de sortie, si le dernier piège a tenté de se terminer (par le biais de &CORE::GLOBAL::exit du piège uniquement ; voir « CAVEATS »).

return [INDEX ...]

Retourne undef si le dernier piège ne s'est pas terminé par un retour ; sinon, retourne trois vues différentes du tableau de retour :

  • si aucun INDEX n'est passé, retourne une référence au tableau (NB ! un tableau vide d'indices est considéré comme « aucun index »)
  • si appelé avec au moins un INDEX dans un contexte scalaire, retourne l'élément du tableau indexé par le premier INDEX (ignorant les autres)
  • si appelé avec au moins un INDEX dans un contexte de liste, retourne la tranche du tableau par ces indices

Note : Le tableau ne contiendra qu'une seule valeur si le piège a été déclenché dans un contexte scalaire, et sera vide s'il était dans un contexte vide.

stdout, stderr

La sortie capturée sur les descripteurs de fichiers respectifs.

warn [INDEX]

Retourne undef si le dernier piège n'avait pas de couche de capture d'avertissements ; sinon, retourne trois vues différentes du tableau d'avertissements :

  • si aucun INDEX n'est passé, retourne une référence au tableau (NB ! un tableau vide d'indices est considéré comme « aucun index »)
  • si appelé avec au moins un INDEX dans un contexte scalaire, retourne l'élément du tableau indexé par le premier INDEX (ignorant les autres)
  • si appelé avec au moins un INDEX dans un contexte de liste, retourne la tranche du tableau par ces indices

wantarray

Le contexte dans lequel le dernier code piégé a été appelé. (Par défaut, un contexte propagé, mais les couches peuvent remplacer cela.)

list, scalar, void

Vrai si le dernier code piégé a été appelé dans le contexte indiqué. (Par défaut, le code sera appelé dans un contexte propagé, mais les couches peuvent remplacer cela.)

TESTS DE RÉSULTATS

Pour chaque accesseur, un certain nombre de méthodes de test standard pratiques sont également disponibles. Par défaut, il s'agit de quelques tests standard de Test::More, plus le test "nok" (un test "ok" nié). Tout cela par commodité :

ACCESSEUR_ok [INDEX,] NOM_TEST

ACCESSEUR_nok [INDEX,] NOM_TEST

ACCESSEUR_is [INDEX,] SCALAR, NOM_TEST

ACCESSEUR_isnt [INDEX,] SCALAR, NOM_TEST

ACCESSEUR_isa_ok [INDEX,] SCALAR, NOM_INVOCANT

ACCESSEUR_like [INDEX,] REGEX, NOM_TEST

ACCESSEUR_unlike [INDEX,] REGEX, NOM_TEST

ACCESSEUR_is_deeply STRUCTURE, NOM_TEST

INDEX n'est pas facultatif : Il est requis pour les accesseurs de tableaux (comme "return" et "warn"), et interdit pour les accesseurs scalaires. Notez que le test "is_deeply" n'accepte pas d'index. Même pour les accesseurs de tableaux, il opère sur l'ensemble du tableau.

Pour plus de commodité et de clarté, les tests sur un accesseur de contrôle de flux ( "return", "die", "exit", ou tout autre que vous définissez vous-même) testeront d'abord si le piège a été quitté par le biais du mécanisme de contrôle de flux en question, et échoueront avec des diagnostics appropriés sinon.

did_die, did_exit, did_return

Commodités : Teste si le piège a été quitté par le biais du mécanisme de contrôle de flux en question. Similaire à leaveby_is('die') etc., mais avec de meilleurs diagnostics et une vérification orthographique (à l'exécution).

quiet

Commodité : Réussit si une sortie de longueur nulle a été capturée sur STDOUT et STDERR, et génère de meilleurs diagnostics sinon.

UTILITAIRES

diag_all

Affiche un message de diagnostic (comme pour « diag » dans Test::More) consistant en un vidage (en code Perl, comme pour Data::Dump) de l'objet piège.

diag_all_once

Comme « diag_all », sauf si cette instance de l'objet piège a déjà été diag_all_once'd, le message de diagnostic consistera à la place en la chaîne "(comme ci-dessus)".

Cela pourrait être utile avec la couche "on_fail" :

use Test::Trap qw/ :on_fail(diag_all_once) /;

CAVEATS

Ce module doit être chargé avant que tout code contenant des exit() à piéger ne soit compilé. Tout exit() déjà compilé ne pourra pas être piégé et mettra fin au programme de toute façon.

Ce module remplace &CORE::GLOBAL::exit, il peut donc ne pas fonctionner correctement (voire pas du tout) en présence d'un autre code remplaçant &CORE::GLOBAL::exit. Plus précisément : ce module installe son propre exit() à l'entrée du bloc, et ne restaure le précédent, le cas échéant, qu'à la sortie du bloc.

Si vous utilisez fork() dans la portée dynamique d'un piège, sachez que la couche :exit (par défaut) de ce piège ne piège pas les exit() dans les enfants, mais les transmet au gestionnaire externe. Si vous y réfléchissez, c'est probablement ce que vous voudrez dans la plupart des cas.

Notez que la couche :exit (par défaut) ne piège que les appels à &CORE::GLOBAL::exit (et les appels exit() nus qui se compilent en cela). Elle ne tente pas de piéger CORE::exit(), POSIX::_exit(), exec(), les exceptions non piégées de die(), ni les segfaults. Elle ne tente pas non plus de piéger quoi que ce soit d'autre qui pourrait terminer le programme. Le piège est un eval de bloc sur stéroïdes – pas le dernier eval de bloc de Krypton !

Ce module piège les avertissements en utilisant $SIG{__WARN__}, il peut donc ne pas fonctionner correctement (voire pas du tout) en présence d'un autre code définissant ce gestionnaire. Plus précisément : ce module installe son propre gestionnaire __WARN__ à l'entrée du bloc, et restaure le précédent, le cas échéant, uniquement à la sortie du bloc.

Les gestionnaires :stdout et :stderr (par défaut) ne piégeront pas la sortie de system

() appels.

Threads ? Aucune idée. Cela pourrait même fonctionner correctement.
