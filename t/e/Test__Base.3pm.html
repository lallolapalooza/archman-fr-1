Test::Base(3) Documentation Perl fournie par l'utilisateur Test::Base(3)

NOM

Test::Base - Un framework de tests basé sur les données

SYNTAXE

Un nouveau module de test :

# lib/MyProject/Test.pm
package MyProject::Test;
use Test::Base -Base;
use MyProject;
package MyProject::Test::Filter;
use Test::Base::Filter -base;
sub my_filter {
    return MyProject->do_something(shift);
}

Un exemple de test :

# t/sample.t
use MyProject::Test;
plan tests => 1 * blocks;
run_is input => 'expected';
sub local_filter {
    s/my/your/;
}
__END__
=== Test one (le nom du test)
--- input my_filter local_filter
my
input
lines
--- expected
expected
output
=== Test two
Ceci est une description optionnelle
de ce test particulier.
--- input my_filter
other
input
lines
--- expected
other expected
output

DESCRIPTION

Les tests sont généralement la partie laide de la création de modules Perl. Perl vous donne une manière standard d'exécuter des tests avec Test::Harness, et des primitives de test de base avec Test::More. Après cela, vous êtes à peu près seul pour développer un framework et une philosophie de test. Test::More vous encourage à créer votre propre framework en sous-classant Test::Builder, mais ce n'est pas trivial.

Test::Base vous offre un moyen d'écrire votre propre classe de base de framework de test qui *est* triviale. En fait, c'est aussi simple que deux lignes :

package MyTestFramework;
use Test::Base -Base;

Un module appelé "MyTestFramework.pm" contenant ces deux lignes, donnera toute la puissance de Test::More et toute la puissance de Test::Base à chaque fichier de test qui l'utilise. Au fur et à mesure que vous augmentez les capacités de "MyTestFramework", vos tests auront également toute cette puissance.

"MyTestFramework" devient un endroit où vous pouvez placer tous vos éléments de test réutilisables. Lorsque vous écrivez des tests, vous verrez des motifs et des duplications, et vous pourrez les « remonter » dans "MyTestFramework". Bien sûr, vous n'avez pas besoin de sous-classer Test::Base du tout. Vous pouvez l'utiliser directement dans de nombreuses applications, y compris partout où vous utiliseriez Test::More.

Test::Base se concentre sur l'offre de motifs réutilisables basés sur les données, afin que vous puissiez écrire des tests avec un minimum de code. Au cœur de tous les tests, vous avez des entrées, des processus et des sorties attendues. Test::Base offre des moyens clairs pour exprimer vos données d'entrée et de sortie attendues, afin que vous puissiez consacrer votre

temps à vous concentrer sur ceux-ci plutôt que sur le squelette de votre code.

FONCTIONS EXPORTÉES

Test::Base étend Test::More et exporte toutes ses fonctions. Vous pouvez donc fondamentalement écrire vos tests comme avec Test::More. Test::Base exporte également de nombreuses fonctions propres :

"is(actual, expected, [test-name])"
C'est l'équivalent de la fonction "is" de Test::More avec une subtilité intéressante. Si vos résultats réels et attendus diffèrent et que la sortie est multiligne, cette fonction vous montrera un format de diff unifié de la sortie. Considérez l'avantage lorsque vous recherchez le caractère unique différent dans des centaines de lignes de sortie !

La sortie de diff nécessite le module optionnel "Text::Diff" du CPAN. Si vous n'avez pas ce module, la fonction is() vous donnera simplement une sortie normale de Test::More. Pour désactiver complètement le diff, définissez la variable d'environnement "TEST_SHOW_NO_DIFFS" (ou $ENV{TEST_SHOW_NO_DIFFS}) sur une valeur vraie. Vous pouvez également appeler la fonction "no_diff" comme raccourci.

blocks( [nom-section-données] )
La fonction la plus importante est "blocks". En contexte de liste, elle renvoie une liste d'objets "Test::Base::Block" générés à partir de la spécification de test dans la section "DATA" de votre fichier de test. En contexte scalaire, elle renvoie le nombre d'objets. Ceci est utile pour calculer votre plan Test::More.

Chaque objet Test::Base::Block a des méthodes qui correspondent aux noms des sections de données de cet objet. Il existe également une méthode "name" et une méthode "description" pour accéder à ces parties du bloc si elles étaient spécifiées.

La fonction "blocks" peut prendre un argument unique facultatif, qui indique de ne renvoyer que les blocs contenant une section de données nommée particulière. Sinon, "blocks" renvoie tous les blocs.

my @all_of_my_blocks = blocks;
my @just_the_foo_blocks = blocks('foo');
next_block()
Vous pouvez utiliser la fonction next_block pour itérer sur tous les blocs. 
while (my $block = next_block) {
    ...
}

Elle renvoie undef après que tous les blocs aient été parcourus. Elle peut ensuite être appelée à nouveau pour réitérer.

first_block()
Renvoie le premier bloc ou undef s'il n'y en a aucun. Elle réinitialise l'itérateur pour la fonction "next_block".
run(&subroutine)
Il existe de nombreuses façons d'écrire vos tests. Vous pouvez référencer chaque bloc individuellement ou vous pouvez boucler sur tous les blocs et effectuer une opération commune. La fonction "run" fait la boucle pour vous, donc tout ce que vous avez à faire est de lui passer un bloc de code à exécuter pour chaque bloc.

La fonction "run" prend une sous-routine comme argument et appelle la sous-routine une fois pour chaque bloc de la spécification. Elle passe l'objet de bloc actuel à la sous-routine.

run {
    my $block = shift;
    is(process($block->foo), $block->bar, $block->name);
};
"run_is([nom_données1, nom_données2])"
Souvent, vous voulez simplement vérifier si deux sections de données sont équivalentes dans chaque bloc, probablement après avoir été traitées par un ou plusieurs filtres. Avec la fonction "run_is", vous pouvez simplement passer les noms de deux sections de données qui existent dans chaque bloc, et elle bouclera sur chaque bloc en comparant les deux sections. 
run_is 'foo', 'bar';

Si aucune section de données n'est donnée, "run_is" essaiera de les détecter automatiquement.

NOTE : Test::Base ignorera silencieusement tous les blocs qui ne contiennent pas
les deux sections.

"is_deep($data1, $data2, $test_name)"
Comme "is_deeply" de Test::More, mais utilise le module plus correct Test::Deep.
"run_is_deeply([nom_données1, nom_données2])"
Comme "run_is_deeply", mais utilise "is_deep" qui utilise le plus correct Test::Deep.
"run_is_deeply([nom_données1, nom_données2])"
Comme "run_is", mais utilise "is_deeply" pour la comparaison de structures de données complexes.
"run_is_deeply([nom_données1, nom_données2])"
Comme "run_is_deeply", mais utilise "is_deep" qui utilise le plus correct Test::Deep.
"run_like([nom_données, regexp | nom_données]);"
La fonction "run_like" est similaire à "run_is", sauf que le deuxième argument est une expression régulière. L'expression régulière peut être un objet "qr{}" ou une section de données qui a été filtrée en une expression régulière. 
run_like 'foo', qr{<html.*};
run_like 'foo', 'match';
"run_unlike([nom_données, regexp | nom_données]);"
La fonction "run_unlike" est similaire à "run_like", sauf qu'elle fait le contraire. 
run_unlike 'foo', qr{<html.*};
run_unlike 'foo', 'no_match';
"run_compare(nom_données1, nom_données2)"
La fonction "run_compare" est similaire aux fonctions "run_is", "run_is_deeply" et "run_like" al

SPÉCIFICATION DE TEST

Test::Base vous permet de spécifier vos données de test dans un fichier externe, la section DATA de votre programme, ou dans une variable scalaire contenant l'intégralité du texte d'entrée.

Une spécification de test est une série de lignes de texte. Chaque test (ou bloc) est séparé par une ligne contenant le délimiteur de bloc et un "nom" de test facultatif. Chaque bloc est ensuite divisé en sections nommées par une ligne contenant le délimiteur de données et le nom de la section de données. Une "description" du test peut apparaître sur des lignes après le délimiteur de bloc mais avant la première section de données.

Voici la structure de base d'une spécification :

=== <nom du bloc 1>
<lignes optionnelles de description du bloc>
--- <nom de section de données 1> <filtre-1> <filtre-2> <filtre-n>
<lignes de données de test>
--- <nom de section de données 2> <filtre-1> <filtre-2> <filtre-n>
<lignes de données de test>
--- <nom de section de données n> <filtre-1> <filtre-2> <filtre-n>
<lignes de données de test>
=== <nom du bloc 2>
<lignes optionnelles de description du bloc>
--- <nom de section de données 1> <filtre-1> <filtre-2> <filtre-n>
<lignes de données de test>
--- <nom de section de données 2> <filtre-1> <filtre-2> <filtre-n>
<lignes de données de test>
--- <nom de section de données n> <filtre-1> <filtre-2> <filtre-n>
<lignes de données de test>

Voici un exemple de code :

use Test::Base;
delimiters qw(### :::);
# code de test ici
__END__
### Test Un
Nous voulons voir si foo et bar
sont réellement égaux...
::: foo
une ligne de foo
une autre ligne de foo
::: bar
une ligne de bar
une autre ligne de bar
### Test Deux
::: foo
une ligne de foo
une autre ligne de foo
::: bar
une ligne de bar
une autre ligne de bar
::: baz
une ligne de baz
une autre ligne de baz

Cet exemple spécifie deux blocs. Les deux ont des sections de données foo et bar. Le second bloc a un composant baz. Le délimiteur de bloc est "###" et le délimiteur de données est ":::".

Le délimiteur de bloc par défaut est "===" et le délimiteur de données par défaut est "---".

Il existe quelques noms de section de données spéciaux aux fins de contrôle :

--- SKIP
--- ONLY
--- LAST

Un bloc avec une section SKIP provoque l'ignorance du test. Ceci est utile pour désactiver temporairement un test.

Un bloc avec une section ONLY provoque l'utilisation de ce seul bloc. Ceci est utile lorsque vous vous concentrez sur la réussite d'un seul test. S'il y a plus d'un bloc avec ONLY, le premier sera choisi.

Étant donné que ONLY est très utile pour le débogage et que vous oubliez parfois de supprimer le flag ONLY avant de le commiter dans le VCS ou de le téléverser sur CPAN, Test::Base vous donne par défaut un message de diagnostic disant Je suis tombé sur ONLY... peut-être êtes-vous en train de déboguer ?. Si cela ne vous plaît pas, utilisez "no_diag_on_only".

Un bloc avec une section LAST fait de ce bloc le dernier de la spécification. Tous les blocs suivants sont ignorés.

FILTRES

La vraie puissance de l'écriture de tests avec Test::Base vient de ses capacités de filtrage. Test::Base est livré avec un ensemble croissant de filtres génériques utiles que vous pouvez chaîner et appliquer à divers blocs de test. Cela signifie que vous pouvez spécifier la sérialisation des blocs de test de la manière la plus lisible que vous trouviez, et que les filtres la traduiront en ce dont vous avez réellement besoin pour un test. Il est facile d'écrire vos propres filtres.

Test::Base vous permet de spécifier une liste de filtres pour chaque section de données de chaque bloc. Les filtres par défaut sont "norm" et "trim". Ces filtres seront appliqués (dans l'ordre) aux données après qu'elles aient été analysées à partir de la spécification et avant qu'elles ne soient définies sur l'objet Test::Base::Block.

Vous pouvez ajouter à la liste des filtres par défaut avec la fonction "filters". Vous pouvez spécifier des filtres supplémentaires à un bloc spécifique en les plaçant après le nom de la section sur une ligne de délimiteur de données.

Exemple :

use Test::Base;
filters qw(foo bar);
filters { perl => 'strict' };
sub upper { uc(shift) }
__END__
=== Test un
--- foo trim chomp upper
...
--- bar -norm
...
--- perl eval dumper
my @foo = map {
    - $_;
} 1..10;
\ @foo;

Placer un "-" avant un filtre sur une ligne de délimiteur désactive ce filtre.

Scalaire vs Liste

Chaque filtre peut prendre un scalaire ou une liste et retourner un scalaire ou une liste. Comme les filtres s'alignent les uns sur les autres, il est important de savoir quels filtres attendent quel type d'entrée et quel type de sortie ils retournent.

Par exemple, considérez la liste de filtres suivante :

norm trim lines chomp array dumper eval

Les données commencent toujours comme une seule chaîne scalaire. "norm" prend un scalaire et retourne un scalaire. "trim" prend une liste et retourne une liste, mais un scalaire est valablement une liste. "lines" prend un scalaire et retourne une liste. "chomp" prend une liste et retourne une liste. "array" prend une liste et retourne un scalaire (un référence anonyme de liste contenant les éléments de la liste). "dumper" prend une liste et retourne un scalaire. "eval" prend un scalaire et crée une liste.

Une liste avec exactement un élément fonctionne bien comme entrée d'un filtre qui nécessite un scalaire, mais toute autre liste provoquera une exception. Un scalaire dans un contexte de liste est considéré comme une liste d'un élément.

Les méthodes d'accès aux données des blocs retournent une liste de valeurs lorsqu'elles sont utilisées dans un contexte de liste, et le premier élément de la liste dans un contexte scalaire. C'est généralement le "bon" comportement, mais soyez-en conscient.

Les Filtres Standards

Test::Base est livré avec un grand ensemble de filtres standard. Ceux-ci se trouvent dans le module "Test::Base::Filter". Voir Test::Base::Filter pour une liste et une description de ces filtres.

Créer vos propres Filtres

Créer des extensions de filtres est très simple. Vous pouvez écrire une fonction dans l'espace de nom du module "main", ou une méthode dans le module "Test::Base::Filter" ou une de ses sous-classes. Dans tous les cas, le texte et tous les arguments supplémentaires vous seront passés, et vous retournerez toutes les valeurs que vous souhaitez.

Voici un exemple explicatif :

use Test::Base;
filters 'foo', 'bar=xyz';
sub foo {
    transform(shift);
}
sub Test::Base::Filter::bar {
    my $self = shift;       # L'objet Test::Base::Filter
    my $data = shift;
    my $args = $self->current_arguments;
    my $current_block = shift;
    ...
}

NOM

Test::Base - Facile à utiliser, basé sur des blocs de test Perl

SYNOPSIS

 use Test::Base;
 # Utilisation de la spécification de test par défaut
 plan tests => MyTests->run_spec('t/mytests.t');
 # Utilisation d'une spécification de test personnalisée
 plan tests => MyTests->run_spec('t/mytests.t',
     spec_string => $my_test_data,
     delimiters => [qw(--- ===)],
 );
 # Utilisation des filtres
 package MyTests;
 use Test::Base;
 sub filter1 {
     my ($self, $data) = @_;
     return 'filtered:' . $data;
 }
 # Utilisation de la spécification de test par défaut
 plan tests => MyTests->run_spec('t/mytests.t',
     filters => [qw(filter1)]
 );
 # Utilisation d'une spécification de test personnalisée
 plan tests => MyTests->run_spec('t/mytests.t',
     spec_string => $my_test_data,
     filters => [qw(filter1)]
 );

DESCRIPTION

Test::Base est un module d'aide aux tests qui permet de définir des données de test et des procédures de test dans un fichier de test Perl unique. Il vous permet de séparer vos données de test de votre code de test d'une manière très pratique.

Il interprète la spécification de test comme une série de "blocs". Chaque bloc peut contenir des données de test et un sous-programme de test associé. Les blocs sont séparés par des délimiteurs personnalisables.

Test::Base prend en charge les filtres, qui sont des sous-programmes qui peuvent transformer les données d'entrée avant qu'elles ne soient traitées par le sous-programme de test associé.

FONCTIONS EXPORTÉES

Test::Base exporte les fonctions suivantes dans l'espace de noms principal :

plan_tests
Planifie les tests en utilisant les informations du ou des blocs Test::Base.
run_spec
Exécute la spécification de test. Prend le nom d'un fichier de spécification de test comme premier argument. Les arguments suivants sont des paires clé-valeur pour spécifier des options telles que "spec_string", "delimiters", et "filters".

SPÉCIFICATION DE TEST

Une spécification de test est un fichier ou une chaîne de caractères contenant des blocs de données de test. Chaque bloc est défini par des délimiteurs personnalisables.

Voici un exemple de spécification de test :

  --- Bloc 1 ---
  name: Simple test
  description: This is a simple test case.
  input:
      - 1
      - 2
      - 3
  expected: 6

  --- Bloc 2 ---
  name: Another test
  input: "hello"
  expected: "olleh"

Les blocs sont séparés par des délimiteurs. Par défaut, le délimiteur est "---". Vous pouvez spécifier des délimiteurs personnalisés à l'aide de l'argument "delimiters" dans "run_spec".

Chaque bloc peut avoir les sections suivantes :

  • name : Un nom court facultatif pour le bloc.

  • description : Une description facultative plus longue du bloc.

  • input : Les données d'entrée pour le bloc.

  • expected : Les données attendues pour le bloc.

Les sections peuvent être spécifiées dans n'importe quel ordre, sauf que description doit précéder la première section de données (par exemple, input ou expected).

Les données de test peuvent être des chaînes de caractères, des nombres ou des tableaux Perl. Test::Base tentera d'analyser les données au format YAML.

FILTRES

Les filtres sont des sous-programmes qui peuvent être utilisés pour modifier les données d'entrée avant qu'elles ne soient transmises au sous-programme de test associé. Ils sont utiles pour effectuer des transformations courantes sur vos données de test.

Vous pouvez spécifier une liste de filtres à appliquer à un bloc en utilisant l'argument "filters" dans "run_spec".

Les filtres sont appelés dans l'ordre spécifié. Chaque filtre reçoit les données du bloc comme argument et doit renvoyer les données transformées.

Voici un exemple de définition et d'utilisation d'un filtre :

 package MyTests;
 use Test::Base;

 sub filter_uppercase {
     my ($self, $data) = @_;
     return uc($data);
 }

 sub filter_reverse {
     my ($self, $data) = @_;
     return scalar reverse split //, $data;
 }

 plan tests => MyTests->run_spec('t/mytests.t',
     filters => [qw(filter_uppercase filter_reverse)]
 );

Dans cet exemple, les données d'entrée seront d'abord converties en majuscules, puis inversées.

Si vous utilisez l'interface de méthode pour un filtre, vous pouvez accéder aux internes du bloc en appelant la méthode "block" sur l'objet filtre.

Normalement, vous utiliserez probablement juste l'interface fonctionnelle, bien que tous les filtres intégrés soient des méthodes.

Notez que les filtres définis dans l'espace de noms "main" peuvent ressembler à ceci :

 sub filter9 {
     s/foo/bar/;
 }

puisque Test::Base transforme automatiquement la chaîne d'entrée dans la variable $_ et vérifie la valeur de retour de la fonction pour voir si elle ressemble à un nombre. Si vous devez définir un filtre qui ne renvoie qu'un seul nombre, faites-le dans un espace de noms différent en tant que méthode. Ces filtres ne permettent pas la transformation simpliste de $_.

OO

Test::Base a une belle interface fonctionnelle pour une utilisation simple. Sous le capot, tout est orienté objet. Un objet Test::Base par défaut est créé et toutes les fonctions ne sont en réalité que des appels de méthodes sur cet objet.

Cela signifie que si vous avez besoin de faire des choses complexes, vous pouvez également utiliser tout le matériel orienté objet. Créez simplement de nouveaux objets Test::Base et utilisez les fonctions comme des méthodes.

 use Test::Base;
 my $blocks1 = Test::Base->new;
 my $blocks2 = Test::Base->new;
 $blocks1->delimiters(qw(!!! @@@))->spec_file('test1.txt');
 $blocks2->delimiters(qw(### $$$))->spec_string($test_data);
 plan tests => $blocks1->blocks + $blocks2->blocks;
 # ... etc

LA CLASSE "TEST::BASE::BLOCK"

Dans Test::Base, les blocs sont exposés en tant qu'objets Test::Base::Block. Cette section répertorie les méthodes qui peuvent être appelées sur un objet Test::Base::Block. Bien sûr, chaque nom de section de données est également disponible en tant que méthode.

name()
Il s'agit de la courte description facultative d'un bloc, spécifiée sur la ligne du séparateur de bloc.
description()
Il s'agit d'une longue description facultative du bloc. C'est le texte provenant de l'espace entre le séparateur de bloc et la première section de données.
seq_num()
Retourne un numéro de séquence pour ce bloc. Les numéros de séquence commencent à 1.
blocks_object()
Retourne l'objet Test::Base qui possède ce bloc.
run_filters()
Exécute les filtres sur les sections de données des blocs. Vous n'avez pas besoin d'utiliser cette méthode, sauf si vous avez également utilisé la fonction "filters_delay".
is_filtered()
Retourne vrai si les filtres ont déjà été exécutés pour ce bloc.
original_values()
Retourne une table de hachage des valeurs originales, non filtrées, de chaque section de données.

SOUS-CLASSEMENT

L'une des meilleures choses à propos de Test::Base est qu'il est facile de le sous-classer. Ceci est très important, car dans votre projet personnel, vous voudrez probablement étendre Test::Base avec vos propres filtres et d'autres éléments réutilisables de votre framework de test.

Voici un exemple de sous-classe :

 package MyTestStuff;
 use Test::Base -Base;
 our @EXPORT = qw(some_func);
 sub some_func {
     (my ($self), @_) = find_my_self(@_);
     ...
 }
 package MyTestStuff::Block;
 use base 'Test::Base::Block';
 sub desc {
     $self->description(@_);
 }
 package MyTestStuff::Filter;
 use base 'Test::Base::Filter';
 sub upper {
     $self->assert_scalar(@_);
     uc(shift);
 }

Notez que vous n'avez pas à ré-exporter toutes les fonctions de Test::Base. Cela se fait automatiquement, grâce à la puissance de Spiffy.

La première ligne de "some_func" lui permet d'être appelée comme fonction ou comme méthode dans le code de test.

SUPPORT DE DISTRIBUTION

Vous pourriez penser que vous ne voulez pas utiliser Test::Base dans vos modules, car cela ajoute une dépendance d'installation. N'ayez crainte. Module::Install::TestBase s'en charge.

Écrivez simplement un Makefile.PL qui ressemble à ceci :

 use inc::Module::Install;
 name            'Foo';
 all_from        'lib/Foo.pm';
 use_test_base;
 WriteAll;

La ligne avec "use_test_base" regroupera automatiquement tout le code dont l'utilisateur a besoin pour exécuter des tests basés sur Test::Base.

AUTRES FONCTIONNALITÉS INTÉRESSANTES

Test::Base ajoute automatiquement :

 use strict;
 use warnings;

à tous vos scripts de test et sous-classes Test::Base. Une fonctionnalité Spiffy en effet.

HISTORIQUE

Ce module a commencé sa vie avec le nom horrible et ridicule "Test::Chunks". Il a été renommé en "Test::Base" dans l'espoir qu'il serait vu comme le module très utile qu'il est devenu. Si vous passez de "Test::Chunks" à "Test::Base", substituez simplement le concept et l'utilisation de "chunks" à "blocks".
