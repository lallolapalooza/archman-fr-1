DESCRIPTION

Le module "Text::BibTeX::Structure" fournit deux classes qui constituent la base du "module de structure" de btOOL. Ce système permet de définir et d'appliquer des structures de bases de données dans des fichiers BibTeX, et offre une syntaxe élégante de techniques orientées objet avec des structures de bases de données de style BibTeX. Ce qui est décrit ici n'est ni particulièrement profond ni complexe ; tout programmeur familier avec la programmation orientée objet devrait pouvoir suivre. Il y a cependant un certain jargon inventé qui est utilisé, alors gardez cela à l'esprit.

Une structure de base de données, dans le langage de btOOL, est simplement un ensemble de types d'entrées autorisés et de règles de champs pour chaque type d'entrée. Actuellement, il existe trois types de règles qui s'appliquent aux champs : certains champs sont requis, c'est-à-dire qu'ils doivent être présents dans chaque entrée d'un type donné ; d'autres sont optionnels, c'est-à-dire qu'ils peuvent être présents et seront utilisés s'ils le sont ; d'autres encore appartiennent à des ensembles de contraintes, qui sont expliqués dans "Listes de champs et ensembles de contraintes" ci-dessous.

Une structure bTOOL est implémentée par deux classes : la classe de structure et la classe d'entrée structurée. La première définit tout ce qui s'applique à la structure dans son ensemble (types d'entrées autorisés et règles de champs). La seconde fournit des méthodes qui opèrent sur des entrées individuelles qui doivent (ou sont censées) respecter la structure. Les deux classes fournies par le module "Text::BibTeX::Structure" sont "Text::BibTeX::Structure" et "Text::BibTeX::StructuredEntry" ; celles-ci servent de classes de base pour, respectivement, toutes les classes de structure et toutes les classes d'entrée structurées. Une structure canonique est fournie en exemple avec btOOL : la structure "Bib", qui (via les classes "BibStructure" et "BibEntry") fournit la même fonctionnalité que les fichiers de style BibTeX standard 0.99. On s'attend à ce que d'autres programmeurs écrivent de nouvelles structures bibliographiques, potentiellement dérivées de la structure "Bib", pour émuler une partie de la fonctionnalité disponible via des fichiers de style BibTeX tiers.

Le but de cette page de manuel est de décrire le système complet du module de structure. Il s'adresse principalement aux programmeurs souhaitant implémenter une nouvelle structure de base de données pour les fichiers BibTeX avec une syntaxe BibTeX ; si vous êtes intéressé par les règles spécifiques pour la structure BibTeX "Bib", consultez "Text::BibTeX::Bib".

Remarque : dans cette page de manuel, le préfixe "Text::BibTeX" est supprimé des noms de modules et de classes, sauf si cela est nécessaire.

CLASSES DE STRUCTURE

Les classes de structure ont deux rôles : définir la liste des types d'entrées autorisés et les règles de champs, et gérer les options de structure.

Listes de champs et ensembles de contraintes

Les listes de champs et les ensembles de contraintes définissent la structure de la base de données pour un type d'entrée spécifique : c'est-à-dire qu'ils spécifient les règles qu'une entrée doit suivre pour satisfaire la structure (en supposant que l'entrée est d'un type autorisé). Il existe trois composantes dans les règles de champs pour chaque type d'entrée : une liste de champs requis, une liste de champs optionnels et des contraintes de champs. Les champs requis et optionnels devraient être évidents pour toute personne familiarisée avec BibTeX : tous les champs requis doivent être présents, et les champs optionnels qui sont présents auront une signification pour la structure. (Une interprétation stricte où tout champ non mentionné dans la définition officielle est désactivé pourrait être envisagée ; cela irait à l'encontre de l'esprit ouvert des bases de données BibTeX, mais pourrait être utile dans certaines applications où un niveau de contrôle plus strict est souhaité. Actuellement, btOOL n'offre pas cette option.)

Les contraintes de champs capturent la relation "l'un ou l'autre, mais pas les deux" présente dans certaines entrées de type des spécifications standard BibTeX. La plupart de la documentation BibTeX passe sous silence la distinction entre les champs mutuellement contraints et les champs requis/optionnels. Par exemple, l'un des types d'entrées standard est "book", et "author" ou "editor" apparaissent dans la liste des champs requis pour ce type. La signification en est qu'une entrée de type "book" doit avoir soit le champ "author" soit "editor", mais pas les deux. De même, les champs "volume" ou "number" sont listés sous l'en-tête des champs optionnels pour les entrées de type "book" ; il serait plus précis de dire que chaque entrée "book" peut avoir l'un de ces champs, ou aucun, mais pas les deux.

btOOL tente de clarifier cette situation en créant une troisième catégorie de champs, à savoir ceux qui sont mutuellement contraints. Par exemple, selon btOOL, les champs "author" et "editor" n'apparaissent pas dans la liste des champs requis pour le type "inbook" ; à la place, une contrainte de champ est créée pour exprimer cette relation :

[1, 1, ['author', 'editor']]

C'est-à-dire qu'une contrainte de champ est une référence à une liste de trois éléments. Le dernier élément est une référence à la contrainte de champ, la liste des champs auxquels la contrainte s'applique. (Ceci est appelé un ensemble, mais c'est un peu inexact, car il y a des conditions où l'ordre des champs est important - voir la méthode "check_field_constraints" dans "MÉTHODES 2 : CLASSE D'ENTRÉE STRUCTURÉE".) Les deux premiers éléments sont le nombre minimum et maximum de champs de la liste de champs de contrainte qui doivent être présents pour qu'une entrée satisfasse la contrainte. Cette contrainte exprime ainsi qu'il doit y avoir exactement un ("author" et "editor") des champs dans une entrée "book".

La contrainte "l'un ou l'autre, mais pas les deux" appliquée aux champs "volume" et "number" des entrées de type "book" est exprimée légèrement différemment :

[0, 1, ['volume', 'number']]

C'est-à-dire que 0 ou 1, mais pas les deux, des champs "volume" et "number" peuvent être présents.

Il est important de noter que la vérification et l'approche des contraintes de champs sont basées uniquement sur le décompte des champs d'un ensemble qui sont réellement présents ; ce mécanisme ne peut pas capturer des relations telles que "x doit être présent si y l'est".

Les obligations imposées à la classe de structure réelle sont simples : elle doit fournir une méthode "describe_entry" qui établit une structure de données attrayante décrivant les types d'entrées autorisés et toutes les règles de champs pour ces types. La classe "Structure" fournit des méthodes (héritées par une classe de structure spécifique) pour aider à créer cette structure de données de manière cohérente et contrôlée. Par exemple, la méthode "describe_structure" dans la classe "BibStructure" (émulant BibTeX 0.99) est assez simple :

L'un de ces appels à la méthode "set_fields" définit les règles pour les entrées de type "book" :

$self->set_fields ('book',
                   [qw(title publisher year)],
                   [qw(series address edition month note)],
                   [1, 1, [qw(author editor)]],
                   [0, 1, [qw(volume number)]]);

La première liste de champs est la liste des champs requis, et la seconde est la liste des champs optionnels. Un nombre quelconque de contraintes de champs peut suivre la liste des champs optionnels ; dans ce cas, il y en a deux, une pour chacune des contraintes ("author"/"editor" et "volume"/"number") décrites ci-dessus. À aucun moment une liste de types autorisés n'est explicitement fournie ; plutôt, chaque appel à "set_fields" ajoute un type autorisé de plus.

Les nouveaux modules de structure qui dérivent de modules existants utiliseront probablement la méthode "add_fields" (et éventuellement "add_constraints") pour augmenter un type d'entrée existant. L'ajout de nouveaux types doit cependant se faire avec "set_fields".

Options de structure

L'autre responsabilité des classes de structure est de gérer les options de structure. Ce sont des valeurs scalaires qui permettent à l'utilisateur de personnaliser le comportement de la classe de structure et de la classe d'entrée structurée. Par exemple, on pourrait avoir une option pour activer la "structure étendue", qui pourrait ajouter un ensemble de nouveaux types d'entrée et de nouveaux champs. (Dans ce cas, la méthode "describe_entry" devrait prêter attention à cette option et modifier son comportement en conséquence.) Ou, on pourrait avoir des options pour contrôler comment la classe d'entrée structurée trie ou formate les entrées (pour les structures de bibliographie telles que "Bib").

La manière simple de gérer les options de structure est de fournir deux méthodes, "known_option" et "default_option". Celles-ci retournent, respectivement, si une option donnée est supportée, et quelle est sa valeur par défaut. (Si votre structure ne supporte aucune option, vous pouvez simplement hériter de ces méthodes de la classe "Structure". La méthode par défaut "known_option" retourne faux pour toutes les options, et sa compagne "default_option" plante avec une erreur "option inconnue".)

Une fois que "known_option" et "default_option" sont fournies, la classe de structure peut se reposer et hériter des méthodes plus visibles "set_options" et "get_options" de la classe "Structure". Ce sont les méthodes réellement utilisées pour modifier/interroger les options, et elles seront utilisées par les programmes d'application pour personnaliser le comportement du module de structure, et par le module de structure lui-même pour prêter attention aux souhaits de l'utilisateur.

Les options devraient généralement avoir des valeurs purement chaînes de caractères, de sorte que la méthode générique set_options n'ait pas à analyser les chaînes fournies par l'utilisateur en une structure compliquée. Cependant, "set_options" accepte n'importe quelle valeur scalaire, donc si le module de structure documente clairement ses exigences, le programme d'application pourrait fournir une structure qui répond à ses besoins. Gardez à l'esprit que cela nécessite une coopération entre l'application et le module de structure ; le code intermédiaire dans "Text::BibTeX::Structure" ne sait rien du format ou de la syntaxe des options de votre structure, et quel que soit le scalaire que l'application passe via "set_options" sera stocké pour que votre module le récupère via "get_options".

À titre d'exemple, la structure "Bib" supporte un certain nombre d'options de "balisage" qui permettent aux applications de contrôler le langage de balisage utilisé pour formater les entrées bibliographiques. Ces options sont naturellement groupées, car les commandes de formatage dans les langages de balisage doivent généralement être activées et désactivées. La structure "Bib" attend donc des références à des listes à deux éléments pour les options de balisage ; pour spécifier l'emphase de style LaTeX 2e pour les titres de livres, une application telle que "btformat" définirait l'option "btitle_mkup" comme suit :

$structure->set_options (btitle_mkup => ['\emph{', '}']);

D'autres options pour d'autres structures pourraient avoir une structure plus compliquée, mais il appartient à la classe de structure de documenter et de faire respecter cela.

CLASSES D'ENTRÉES STRUCTURÉES

Une classe d'entrée structurée définit le comportement des entrées individuelles sous le régime d'une structure de base de données particulière. C'est la raison d'être de toute structure de base de données : la classe de structure établit simplement les règles pour que les entrées se conforment à la structure, mais la classe d'entrée structurée fournit les méthodes qui opèrent réellement sur les entrées individuelles. Comme cela est totalement ouvert, les exigences d'une classe d'entrée structurée sont beaucoup moins rigides que pour une classe de structure. En fait, toutes les exigences d'une classe d'entrée structurée peuvent être satisfaites simplement en héritant de "Text::BibTeX::StructuredEntry", l'autre classe fournie par le module "Text::BibTeX::Structure". (Pour mémoire, ces exigences sont : une classe d'entrée structurée doit fournir les méthodes de parsing/requête/manipulation d'entrée de la classe "Entry", et elle doit fournir les méthodes "check", "coerce" et "silently_coerce" de la classe "StructuredEntry". Puisque "StructuredEntry" hérite de "Entry", ces deux exigences sont satisfaites "gratuitement" par les classes d'entrée structurées qui héritent de "Text::BibTeX::StructuredEntry", donc naturellement c'est la voie recommandée !)

Il n'y a délibérément pas d'autres méthodes requises des classes d'entrée structurées. Une application particulière (par exemple "btformat" pour les structures de bibliographie) requerra certaines méthodes, mais il appartient à l'application et au module de structure de déterminer les exigences par le biais de la documentation.

INTERACTIONS DE CLASSES

L'imposition d'une structure de base de données à vos entrées déclenche une réaction en chaîne d'interactions entre diverses classes de la bibliothèque "Text::BibTeX" qui devraient être transparentes quand tout va bien. Cela pourrait être déroutant si les choses tournent mal et que vous devez vous frayer un chemin à travers plusieurs niveaux de programme d'application, les classes principales de "Text::BibTeX" et un module de structure.

La justification de ce comportement compliqué est qu'il vous permet d'écrire des programmes qui utiliseront un module structuré particulier sans connaître le nom de la structure lors de l'écriture du programme. Ainsi, l'utilisateur peut fournir une structure de base de données, et finalement les objets d'entrée que vous manipulez seront bénis dans une classe fournie par le module de structure. Un bref exemple illustrera cela.

Typiquement, un programme basé sur "Text::BibTeX" est basé autour d'un noyau de code comme celui-ci :

$bibfile = Text::BibTeX::File->new("foo.bib");
while ($entry = Text::BibTeX::Entry->new($bibfile))
{
   # traiter $entry
}

Dans ce cas, rien de spécial ne se passe en coulisses : l'objet $bibfile est béni dans la classe "Text::BibTeX::File", et $entry est béni dans "Text::BibTeX::Entry". C'est le comportement conventionnel des classes Perl, mais ce n'est pas le seul comportement possible. Supposons maintenant que $bibfile est censé se conformer à une structure de base de données spécifiée par $structure (probablement une valeur fournie par l'utilisateur, et donc inconnue au moment de la compilation) :

$bibfile = Text::BibTeX::File->new("foo.bib");
$bibfile->set_structure ($structure);
while ($entry = Text::BibTeX::Entry->new($bibfile))
{
   # traiter $entry
}

Beaucoup de choses se passent en coulisses avec l'appel à la méthode "set_structure" de $bibfile. Premièrement, un nouvel objet de structure est créé à partir de $structure. Le nom de la structure implique le nom d'un module Perl — le module de structure — qui est "require"'d par le constructeur "Structure". (La principale conséquence de cela est que toute erreur de compilation dans votre module de structure ne sera révélée que lorsqu'un appel à "Text::BibTeX::File::set_structure" ou "Text::BibTeX::Structure::new" tentera de le charger.)

Rappelez-vous que la première responsabilité d'un module de structure est de définir une classe de structure. L'"objet de structure" créé par l'appel de la méthode "set_structure" est en fait un objet de cette classe ; c'est le premier trucage — l'objet de structure (caché en coulisses) est béni dans une classe dont le nom n'est connu qu'à l'exécution.

Maintenant, le comportement du constructeur "Text::BibTeX::Entry::new" change subtilement : au lieu de retourner un objet béni dans la classe "Text::BibTeX::Entry" comme on pourrait s'y attendre d'après le code, l'objet est béni dans la classe d'entrée structurée associée à $structure.

Méthodes optionnelles

option_connue (OPTION)
Retourne false. Ceci est principalement destiné à l'utilisation par des structures dérivées qui n'ont pas d'options et, par conséquent, n'ont pas besoin de fournir leur propre méthode "option_connue". Les structures qui proposent réellement des options doivent remplacer cette méthode ; elle doit retourner true si OPTION est une option supportée.
option_par_defaut (OPTION)
Crée un crash avec un message "option inconnue". Encore une fois, ceci est principalement destiné à l'utilisation par les classes de structure dérivées qui ne proposent pas réellement d'options. Les structures qui gèrent les options doivent remplacer cette méthode ; chaque option gérée par "option_connue" doit avoir une valeur par défaut (qui peut juste être "undef") qui est retournée par "option_par_defaut". Votre méthode "options_par_defaut" devrait planter en cas d'option inconnue, peut-être en appelant "SUPER::option_par_defaut" (afin d'assurer des messages d'erreur cohérents). Par exemple : 
sub option_par_defaut
{
   my ($self, $option) = @_;
   return $options_par_defaut{$option}
      if exists $options_par_defaut{$option};
   $self->SUPER::option_par_defaut ($option);   # crash
}

La valeur par défaut d'une option est retournée par "get_options" lorsque cette option n'a pas été explicitement définie avec "set_options".

MÉTHODES 2 : CLASSE DE BASE STRUCTUREDENTRY

L'autre classe fournie par le module "Structure" est "StructuredEntry", la classe de base pour toutes les classes d'entrées structurées. Cette classe hérite de "Entry", donc toutes ses méthodes de requête/manipulation d'entrée sont disponibles. "StructuredEntry" ajoute des méthodes pour vérifier qu'une entrée est conforme à la structure de base de données définie par une classe de structure.

Il n'est logique que "StructuredEntry" soit utilisé comme classe de base ; vous ne créeriez jamais d'objets "StructuredEntry" autonomes. La raison superficielle est que seules des classes d'entrées structurées particulières ont une classe de structure associée, "StructuredEntry" seul ne dispose d'aucune information sur les types autorisés, les champs requis, etc. Pour une compréhension plus approfondie, consultez "INTERACTIONS DE CLASSE" ci-dessus.

Étant donné que "StructuredEntry" dérive de "Entry", il fonctionne naturellement sur les entrées BibTeX. Par conséquent, les descriptions suivantes font référence à "l'entrée" --- c'est juste l'objet (l'entrée) sur lequel on opère. Notez que ces méthodes sont présentées dans l'ordre ascendant, c'est-à-dire que les méthodes que vous utiliserez le plus probablement --- "vérifier", "coercer", et "coercer_silencieusement" sont en bas. Lors d'une première lecture, vous voudrez probablement sauter directement à celles-ci pour un résumé rapide.

structure ()
Retourne l'objet qui définit la structure à laquelle l'entrée est censée se conformer. Il s'agira d'une instantiation d'une classe de structure, et elle existe principalement pour que les méthodes de vérification/coercition puissent interroger la structure sur les types et les champs qu'elle reconnaît. Si, pour une raison quelconque, vous souhaitiez interroger la structure d'une entrée sur la validité du type "foo", vous pourriez faire ceci : 
# supposer que $entry est un objet d'une classe d'entrée structurée, c'est-à-dire
# qu'il hérite de Text::BibTeX::StructuredEntry
$structure = $entry->structure;
$foo_connu = $structure->type_connu ('foo');
verifier_type ([WARN])
Retourne true si l'entrée a un type valide selon sa structure. Si WARN est vrai, alors un type invalide entraîne l'impression d'un avertissement.
verifier_champs_requis ([WARN [, COERCE]])
Vérifie que tous les champs requis sont présents dans l'entrée. Si WARN est vrai, alors un avertissement est imprimé pour chaque champ manquant. Si COERCE est vrai, alors les champs manquants sont définis sur une chaîne vide.

Ceci n'est généralement pas utilisé par d'autres codes ; voir les méthodes "verifier" et "coercer" ci-dessous.

verifier_contraintes_champs ([WARN [, COERCE]])
Vérifie que l'entrée est conforme à toutes les contraintes de champs imposées par sa structure. Rappelez-vous qu'une contrainte de champ se compose d'une liste de champs et d'un nombre minimum et maximum de ces champs qui doivent être présents dans une entrée. Pour chaque contrainte, "verifier_contraintes_champs" compte simplement combien de champs de l'ensemble de champs de la contrainte sont présents. Si ce compte tombe en dessous du minimum ou au-dessus du maximum pour cette contrainte et que WARN est vrai, un avertissement est émis. En général, cet avertissement est de la forme "entre x et y des champs foo, bar et baz doivent être présents". Les cas les plus courants sont traités spécialement pour générer des messages d'avertissement plus utiles et conviviaux.

Si COERCE est vrai, alors l'entrée est modifiée pour la forcer à se conformer à toutes les contraintes de champs. La manière dont cela est fait dépend de la question de savoir si la violation résulte d'un manque de champs présents dans l'entrée, ou d'un excès de champs présents. Dans le premier cas, juste assez de champs sont ajoutés (sous forme de chaînes vides) pour répondre aux exigences de la contrainte ; dans le second cas, les champs sont supprimés. Les champs à ajouter ou à supprimer sont contrôlés par l'ordre des champs dans la liste des champs de la contrainte.

Un exemple devrait clarifier cela. Par exemple, une contrainte de champ spécifiant qu'exactement un de "auteur" ou "editeur" doit apparaître dans une entrée ressemblerait à ceci :

[1, 1, ['auteur', 'editeur']]

Supposons que l'entrée suivante soit analysée et qu'elle doive se conformer à cette structure :

@inbook{inconnu:1997a,
  title = "Un chapitre de livre non attribué",
  booktitle = "Un livre non édité",
  publisher = "Foo, Bar \& Compagnie",
  year = 1997
}

Si "verifier_contraintes_champs" est appelé sur cette méthode avec COERCE vrai (ce qui est fait par n'importe laquelle des méthodes "verification_complete", "coercer", et "coercer_silencieusement"), alors le champ "auteur" est défini sur une chaîne vide. (Nous parcourons la liste des champs de l'ensemble de champs de la contrainte dans l'ordre -- puisque "auteur" est le premier champ manquant, nous le fournissons ; une fois cela fait, l'entrée est maintenant conforme à la contrainte "auteur"/"editeur", nous avons donc terminé.)

Cependant, si la même structure était appliquée à cette entrée :

@inbook{smith:1997a,
  author = "John Smith",
  editor = "Fred Jones",
  ...
}

alors le champ "editeur" serait supprimé. Dans ce cas, nous autorisons le premier champ de l'ensemble de champs de la contrainte --- "auteur". Puisque un seul champ de l'ensemble peut être présent, tous les champs après le premier sont en violation, ils sont donc supprimés.

Encore une fois, cette méthode n'est généralement pas utilisée par d'autres codes ; elle est plutôt appelée par "verification_complete" et ses amis ci-dessous.

verification_complete ([WARN [, COERCE]])
Retourne true si le type et les champs d'une entrée sont tous valides. C'est-à-dire qu'elle appelle "verifier_type", "verifier_champs_requis", et "verifier_contraintes_champs" ; si toutes retournent true, alors "verification_complete" retourne true. WARN et COERCE sont simplement transmis aux trois méthodes "verifier_*" : le premier contrôle l'impression des avertissements, et le second décide si nous devons modifier l'entrée pour la forcer à se conformer.
verifier ()
Vérifie que l'entrée est conforme aux exigences de sa structure de base de données associée : le type doit être connu, tous les champs requis doivent être présents, et toutes les contraintes de champ doivent être respectées. Voir "check_type", "check_required_fields", et "check_field_constraints" pour plus de détails.

Appeler "check" revient au même que d'appeler "full_check" avec WARN vrai et COERCE faux.

coerce ()
Identique à "check", sauf que les entrées sont coercées pour être conformes à la structure de base de données - c'est-à-dire qu'il est identique à "full_check" avec WARN et COERCE vrais.
silently_coerce ()
Identique à "coerce", sauf que les avertissements ne sont pas affichés - c'est-à-dire qu'il est identique à "full_check" avec WARN faux et COERCE vrai.
