Test2::Manual::Anatomy::EndToEnd(3perl) Manuel du programmeur Perl Test2::Manual::Anatomy::EndToEnd(3perl)

NOM

Test2::Manual::Anatomy::EndToEnd - Vue d'ensemble de Test2 depuis le chargement jusqu'à la fin d'un script de test.

DESCRIPTION

Voici une vue d'ensemble de tout ce qui se passe depuis le chargement de Test2 jusqu'à la fin d'un script de test.

Que se passe-t-il lorsque je charge l'API ?

use Test2::API qw/context/
Une instance singleton de Test2::API::Instance est créée.
Vous n'avez pas accès à cela, c'est un détail d'implémentation.
Plusieurs fonctions de l'API sont définies qui utilisent l'instance singleton.
Vous pouvez importer ces fonctions, ou les utiliser directement.
Quoi ?
Attendez...

L'API fait le moins possible. À ce stade, quelque chose peut encore changer le formateur, charger Test2::IPC, ou avoir des effets globaux qui doivent être effectués avant la création de la première instance de Test2::API::Context. Une fois la première instance de Test2::API::Context créée, l'API sera finalisée.

Voir « Que se passe-t-il lorsque j'obtiens un contexte ? » pour plus d'informations.

Que se passe-t-il lorsque j'utilise un outil ?

Cette section couvre le flux de base que tous les outils, tels que ok(), doivent suivre.

sub ok($$) {
    my ($bool, $name) = @_;
    my $ctx = context();
    my $event = $ctx->send_event('Ok', pass => $bool, name => $name);
    ...
    $ctx->release;
    return $bool;
}
ok(1, "1 est vrai");
Une fonction outil est exécutée.
ok(1, "1 est vrai");
L'outil obtient un objet contexte.
my $ctx = context();

Voir « Que se passe-t-il lorsque j'obtiens un contexte ? » pour plus d'informations.

L'outil utilise l'objet contexte pour créer, envoyer et retourner des événements.
Voir « Que se passe-t-il lorsque j'envoie un événement ? » pour plus d'informations. 
my $event = $ctx->send_event('Ok', pass => $bool, name => $name);
Lorsqu'il a terminé, l'outil doit libérer le contexte.
Voir « Que se passe-t-il lorsque je libère un contexte ? » pour plus d'informations. 
$ctx->release();
L'outil retourne.
return $bool;

Que se passe-t-il lorsque j'obtiens un contexte ?

my $ctx = context();

Ces actions ne se produisent pas nécessairement exactement dans cet ordre, mais c'est un détail d'implémentation. Aux fins de ce document, cet ordre est utilisé pour aider le lecteur à comprendre le flux.

$!, $@, $? et $^E sont capturés et conservés.
Test2 s'assure de préserver les valeurs de $!, $@, $? et $^E afin que les outils de test ne modifient pas ces variables de manière inattendue. Elles sont capturées en premier afin de pouvoir être restaurées plus tard.
L'état de l'API passe à 'loaded'.
L'état 'loaded' signifie que des outils de test ont déjà commencé à s'exécuter. C'est important car certains plugins doivent être activés avant que toute épreuve ne soit exécutée. Ce changement d'état ne se produit que la première fois qu'un contexte est obtenu, et peut déclencher certains hooks définis par des plugins.
Le hub actuel est trouvé.
Un contexte est attaché au hub actuel. S'il n'y a pas de hub actuel, le hub racine est initialisé. Cela démarre également la pile de hubs si nécessaire.
Les hooks d'acquisition de contexte sont déclenchés.
Il est possible de créer des hooks globaux ou spécifiques au hub qui se déclenchent lors de l'acquisition d'un contexte ; ces hooks sont déclenchés maintenant. Ces hooks sont déclenchés même s'il existe déjà un contexte.
Tout contexte existant est trouvé.
Si le hub actuel a déjà un contexte, une copie de celui-ci sera utilisée au lieu d'un contexte entièrement nouveau. Ceci est important car cela permet aux outils imbriqués d'hériter du contexte utilisé par les outils parents.
La profondeur de la pile est mesurée.
Test2 s'assure qu'il n'y a pas d'erreurs dans la façon dont le contexte est utilisé. La profondeur de la pile est utilisée pour y parvenir. S'il existe un contexte, sa profondeur sera comparée à celle trouvée ici. Si l'ancien contexte a la même profondeur ou une profondeur inférieure, cela indique qu'un outil est défectueux et n'a pas nettoyé son contexte lorsqu'il a terminé, ce qui entraînera le nettoyage de l'ancien contexte et l'émission d'un avertissement.
Un nouveau contexte est créé (s'il n'y en a pas d'existant).
S'il n'y a pas de contexte existant, un nouveau contexte est créé en utilisant les données collectées précédemment.
Les hooks d'initialisation de contexte sont déclenchés (s'il n'y en a pas d'existant).
Si un nouveau contexte a été créé, les hooks de création de contexte sont déclenchés.
$!, $@, $?, et $^E sont restaurés.
On s'assure que ces valeurs n'ont pas été modifiées à ce stade afin que les changements qui ont été effectués n'affectent rien d'autre. Ceci est fait au cas où quelque chose aurait accidentellement changé ces valeurs dans le contexte de construction.
Le contexte est retourné.
Vous avez un brillant nouvel objet contexte ou une copie du contexte existant.

Que se passe-t-il lorsque j'envoie un événement ?

my $event = $ctx->send_event('Ok', pass => $bool, name => $name);
Le module Test2::Event::Ok est chargé.
La méthode send_event() de Test2::Event::Ok est chargée automatiquement. Normalement, send_event() suppose que le premier argument est une classe d'événement sans le préfixe Test2::Event::, qu'elle ajoute pour vous. Si vous souhaitez utiliser une classe d'événement dans un espace de noms différent, vous pouvez préfixer le nom de la classe avec un + pour indiquer que vous fournissez un nom de classe entièrement qualifié : 
my $event = $ctx->send_event('+Fully::Qualified::Event', pass => $bool, name => $name);
Une nouvelle instance de Test2::Event::Ok est créée.
L'objet événement est instancié en utilisant les paramètres fournis.
L'objet événement est envoyé au hub.
Le hub prend le contrôle à partir d'ici.
Le hub fait passer l'événement à travers tous les filtres.
Les filtres peuvent modifier ou supprimer les événements. Les filtres sont exécutés en premier, avant que l'événement ne modifie l'état global des tests.
L'état global des tests est mis à jour pour refléter l'événement.
Si l'événement affecte le compteur de tests, le compteur est incrémenté. Si l'événement provoque un échec, le compteur d'échecs est incrémenté. L'état global peut être affecté de diverses autres manières.
L'événement est envoyé au formateur.
Après la mise à jour de l'état, le hub enverra l'événement au formateur pour le rendu. C'est là que le TAP est normalement généré.
L'événement est envoyé à tous les auditeurs.
Il existe n'importe quel nombre d'auditeurs qui agissent lors du traitement des événements. Cela se produit maintenant.

Que se passe-t-il lorsque je libère un contexte ?

$ctx->release;
Le clone de contexte actuel est libéré.
Si votre outil est imbriqué, la libération détruira simplement la copie du contexte, rien d'autre ne se produira.

Tous les événements IPC en attente seront élagués.
Si l'IPC est activé, un élagage final aura lieu.
Les hooks de suivi sont exécutés
Les hooks de suivi sont un moyen d'exécuter des actions lorsqu'un hub est terminé. Ceci est utile pour ajouter des tâches de nettoyage ou des tests finaux à la fin d'un test.
Le contexte est effacé
Les données de contexte principales sont effacées, permettant au prochain outil de créer un nouveau contexte. Ceci est important car le prochain outil aura très probablement un nouveau numéro de ligne.
$!, $@, $?, et $^E sont restaurés
Lorsqu'un outil Test2 est terminé, il restaure $@, $!, $? et $^E pour éviter les actions à distance.

QUE SE PASSE-T-IL QUAND J'UTILISE done_testing()?

done_testing();
Tous les événements IPC en attente seront élagués.
Si l'IPC est activé, un élagage final aura lieu.
Les hooks de suivi sont exécutés
Les hooks de suivi sont un moyen d'exécuter des actions lorsqu'un hub est terminé. Ceci est utile pour ajouter des tâches de nettoyage ou des tests finaux à la fin d'un test.
L'événement de plan final est généré et traité.
L'événement de plan final sera produit en utilisant le nombre de tests actuel comme nombre de tests planifiés.
Le hub actuel est finalisé.
Cela marquera le hub comme terminé et n'autorisera pas le traitement de nouveaux événements.

QUE SE PASSE-T-IL QUAND UN SCRIPT DE TEST EST TERMINÉ?

Test2 a certains comportements qu'il exécute dans un bloc "END { ... }" après que les tests soient terminés. Ce bloc de fin effectue quelques vérifications finales pour vous avertir si quelque chose s'est mal passé. Ce bloc de fin définit également la valeur de sortie du script.

Les versions de l'API sont vérifiées.
Un avertissement sera produit si Test::Builder est chargé, mais a une version différente de Test2::API. Cette situation peut se produire si vous rétrogradez vers une distribution Test-Simple plus ancienne, et c'est une mauvaise situation.
Tous les objets de contexte restants sont nettoyés.
S'il reste des objets de contexte, ils devront être nettoyés. Un contexte restant n'est jamais une bonne chose et nécessite généralement un avertissement. Un contexte restant pourrait également résulter d'une exception lancée qui termine le script. Test2 est assez bon pour remarquer cela et ne pas avertir dans ces cas, car l'avertissement ne serait qu'un bruit.
Les processus enfants reçoivent un événement 'en attente'.
Si l'IPC est actif, un événement en attente est envoyé à tous les processus enfants.
Le script attendra que tous les processus et/ou threads enfants se terminent.
Cela se produit uniquement lorsque l'IPC est chargé, mais que Test::Builder ne l'est pas. Ce comportement est utile, mais briserait la compatibilité pour les tests hérités.
La pile des hubs est nettoyée.
Tous les hubs sont finalisés en partant du haut. Les hubs restants sont généralement une mauvaise chose, un avertissement est donc produit s'il en est trouvé.
Le hub racine est finalisé.
Cette étape est une opération nulle si done_testing() a été utilisé. Si nécessaire, cela marquera le hub racine comme terminé.
Les rappels de sortie sont appelés.
C'est une occasion pour les plugins de modifier la valeur de sortie finale du script.
La valeur de sortie du script ($?) est définie.
Si le test a rencontré des échecs, celle-ci sera définie sur une valeur non nulle. Si possible, elle sera définie sur le nombre d'échecs, ou 255 si le nombre est supérieur à 255 (la valeur maximale autorisée).
Diagnostics de modules cassés
Test2 est conscient de nombreux modules qui ont été cassés par la sortie de Test2. À ce stade, le script vérifiera si des modules connus comme cassés ont été chargés et vous avertira s'ils l'ont été.

Remarque : Cela ne se produit que s'il y a eu des échecs de test. Aucun avertissement de module cassé n'est produit en cas de succès.
