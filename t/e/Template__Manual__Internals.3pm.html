Nom

Template::Manual::Internals - Internes de Template Toolkit

Introduction

Cette section de la documentation est destinée aux développeurs qui souhaitent en savoir plus sur le fonctionnement interne de Template Toolkit afin de l'étendre ou de l'adapter à leurs besoins.

Si cela ne vous concerne pas, vous n'avez probablement pas besoin de lire ceci. Il n'y a pas de test après.

De l'extérieur vers l'intérieur

Le module Template est simplement un module de façade qui crée et utilise un objet Template::Service et envoie le résultat là où vous le souhaitez (par défaut, "STDOUT" ou peut-être un fichier, une variable, etc.). Le module Apache::Template (disponible séparément sur CPAN) est une autre façade. Il crée un objet Template::Service::Apache, appelle les fonctions nécessaires et envoie le résultat à un objet Apache::Request correspondant.

Ces modules de façade servent en réalité uniquement à gérer les spécificités de l'environnement dans lequel ils sont utilisés. Le module Apache::Template, par exemple, gère les spécificités d'Apache::Request et la configuration via le fichier httpd.conf. Le module de façade régulier de Template gère le "STDOUT", les références de variables, etc. Pour le reste, c'est Template::Service (ou une de ses dérivées) qui fait le travail.

Le module Template::Service offre un service de livraison de modèles de haute qualité, avec des fonctionnalités, un accord de niveau de service et une garantie de remboursement de 30 jours sans conditions. "Passez un bon moment, tout le temps", telle est notre devise.

Au niveau inférieur de Template Toolkit, il y a beaucoup de détails complexes dont nous n'avons pas à nous soucier la plupart du temps. Des choses comme les modèles introuvables, les erreurs d'analyse, les exceptions non interceptées, les modules de plugins manquants ou les dépendances, etc. Le module Template::Service cache tout cela et donne une impression de simplicité de l'extérieur. Il offre des fonctionnalités supplémentaires telles que "PRE_PROCESS", "PROCESS" et "POST_PROCESS", ainsi que le mécanisme de gestion des erreurs via "ERROR". Vous demandez au module de traiter un modèle, et il s'occupe de tout pour vous. Le module Template::Service::Apache va un peu plus loin, ajoutant quelques en-têtes supplémentaires à un objet Apache::Request, définissant quelques variables de modèle supplémentaires, et ainsi de suite.

En général, le travail d'un service est simplement une question de planification et d'attribution. Il reçoit une requête sous la forme d'un appel à sa méthode process() et planifie le modèle nommé spécifié comme argument, et potentiellement plusieurs autres modèles ("PRE_PROCESS", etc.) à traiter dans l'ordre. Il ne traite pas réellement les modèles, mais appelle plutôt la méthode process() sur un objet Template::Context.

Template::Context est le moteur d'exécution de Template Toolkit - le module qui rassemble tout au niveau inférieur de Template Toolkit et qui effectue la majeure partie du travail, bien que par délégation créative à divers modules d'aide conviviaux.

Étant donné un nom de modèle (ou peut-être une référence à un scalaire ou un descripteur de fichier), la méthode process() du contexte doit charger et compiler, ou obtenir une copie mise en cache d'un modèle précédemment compilé, correspondant à ce nom. Il le fait en appelant une liste d'un ou plusieurs objets Template::Provider (les "LOAD_TEMPLATES" de la famille) qui peuvent s'engager avec un objet Template::Parser pour convertir les fichiers source en code Perl exécutable (mais nous y reviendrons plus tard).

Heureusement, toute cette complexité est cachée derrière une simple méthode template(). Vous l'appelez en passant un nom de modèle comme argument, et il renvoie un modèle compilé sous la forme d'un objet Template::Document, ou lance une exception.

Un Template::Document est un objet enveloppant léger autour d'une sous-routine Perl compilée d'un modèle. La classe implémente une méthode process() qui effectue un peu de nettoyage, puis appelle la sous-routine du modèle. Elle définit également les métadonnées du modèle (définies dans les directives "[% META ... %]") et possède une méthode block() qui renvoie une table de hachage de toute définition de "[% BLOCK xxxx %]" trouvée dans le code source du modèle.

Ainsi, le contexte obtient un modèle compilé via sa propre méthode template() et se prépare à le traiter. Il met d'abord à jour le stash (l'endroit où les variables de modèle sont définies - nous y reviendrons bientôt) pour définir toute définition de variable de modèle spécifiée comme deuxième argument par une référence à un tableau associatif. Il appelle ensuite la méthode process() du document, en passant une référence à lui-même, l'objet contexte, comme argument. Ce faisant, il se fournit lui-même comme un objet sur lequel les fonctions de code de modèle peuvent faire des rappels pour accéder aux ressources d'exécution et aux fonctionnalités de Template Toolkit.

Ce que nous voulons dire ici, c'est que non seulement vous recevez des appels de l'extérieur, c'est-à-dire ceux provenant du code utilisateur appelant la méthode process() sur un objet Template, mais aussi des appels de l'intérieur, c'est-à-dire ceux provenant des directives de modèle de la forme "[% PROCESS template %]".

De l'intérieur vers l'extérieur

Pour mieux comprendre ce qui se passe à ces niveaux inférieurs, nous devons examiner à quoi ressemble un modèle compilé. En fait, un modèle compilé n'est qu'une sous-routine Perl ordinaire. Voici un exemple très simple.

sub my_compiled_template {
    return "This is a compiled template.\n";
}

Vous ne le verrez pas ainsi à moins de l'avoir écrit vous-même, mais c'est tout à fait valide. Toutes les sous-routines d'un modèle ne doivent faire qu'une seule chose : renvoyer une sortie (qui peut être vide, bien sûr). Si, pour une raison quelconque, elles ne peuvent pas le faire, elles devraient lever une exception via la méthode die().

sub my_todo_template {
    die "This template not yet implemented\n";
}

Si vous voulez être plus créatif, vous pouvez lever une exception sous la forme d'un objet Template::Exception. Un objet d'exception est en fait un conteneur de calcul pour les champs "type" et "info".

sub my_soliloquy_template {
    die (Template::Exception->new('yorrick', 'Fellow of infinite jest'));
}

Supervision du Template Toolkit

Vous êtes encouragé à apporter des modifications au Template Toolkit. Si vous trouvez un bug qui nécessite une correction, si vous avez une idée pour une fonctionnalité manquante ou si vous souhaitez traiter un élément de la liste TODO, n'hésitez pas à le faire !

Si vous envisagez quelque chose de non trivial, il est conseillé de soulever la question sur la liste de diffusion afin de comprendre l'état actuel des choses, de vérifier si quelqu'un y travaille déjà, et ainsi de suite.

Le référentiel de code du Template Toolkit est hébergé sur GitHub.

https://github.com/abw/Template2

Clonez le référentiel, apportez vos modifications, commitez-les, puis soumettez une demande de tirage (pull request).

Une fois que vous avez apporté vos modifications, n'oubliez pas de mettre à jour la suite de tests en ajoutant des tests supplémentaires à l'un des scripts existants dans le sous-répertoire "t", ou en ajoutant un nouveau script de test. Et bien sûr, exécutez "make test" pour vous assurer que tous les tests passent avec votre nouveau code.

N'oubliez pas que tout fichier que vous ajoutez doit également figurer dans le MANIFEST. L'exécution de "make manifest" s'en chargera pour vous, mais vous devez vous assurer qu'aucun fichier temporaire n'y est également ajouté.

La documentation est souvent négligée, mais elle est aussi importante que le code. Si vous ajoutez un nouveau module, par exemple un module de plugin, il est acceptable d'inclure la documentation POD avec le module, mais s'il vous plaît écrivez-la dans un seul bloc à la fin du fichier, après le code (voir n'importe quel module "Template::*" pour un exemple). C'est un sujet religieux, bien que je sache que j'ai une forte aversion pour la documentation POD intercalée dans le code. À mon humble avis, cela rend à la fois le code et la documentation plus difficiles à lire (le même problème que l'inclusion de Perl dans du HTML).

Ensuite, ajoutez une ligne au fichier Changes décrivant brièvement ce que vous avez fait. Il n'est pas nécessaire d'entrer dans les détails ici (sauf pour le message de commit, les commentaires dans le code ou la documentation le cas échéant).

Vous devez également vous assurer d'ajouter votre nom au fichier "lib/Template/Manual/Credits.pod" (s'il n'y est pas déjà).

Ensuite, faites votre commit et soumettez une demande de tirage.

NOM

Template::Manual::Internals - Détails internes du Template Toolkit

Introduction

Ce document décrit certaines des structures de données et des mécanismes internes utilisés par le Template Toolkit.

Il est destiné aux programmeurs qui souhaitent étendre le comportement du moteur ou comprendre comment il fonctionne en interne.

De l'extérieur vers l'intérieur

La plupart des interactions avec le Template Toolkit se font via l'objet Template.

Les objets Template::Context sont utilisés pour stocker les configurations, les filtres, les variables, etc. Ils sont généralement créés et gérés par l'objet Template.

Les objets Template::Parser sont responsables de l'analyse du code de template en une structure interne d'opérations ou de « blocs ».

Les objets Template::Provider sont utilisés pour localiser et récupérer les fichiers de templates.

Les objets Template::Grammar définissent la syntaxe du langage de template.

De l'intérieur vers l'extérieur

Lorsqu'une directive PROCESS est rencontrée, l'objet Template::Context est responsable de l'invocation du bloc de code approprié.

Le moteur utilise une approche basée sur des blocs pour le rendu. Les blocs peuvent être imbriqués les uns dans les autres.

Les variables sont gérées dans des piles, ce qui permet un comportement de portée local.

Hacking sur le Template Toolkit

Pour modifier le comportement du Template Toolkit, vous pouvez créer de nouveaux filtres, des variables, des fournisseurs, des analyseurs, des grammaires ou des blocs.

Les nouveaux blocs peuvent être implémentés en tant que sous-classes de Template::Block.

Les filtres peuvent être implémentés en tant que sous-classes de Template::Filter.

Pour ajouter un nouveau fournisseur, vous devez implémenter la méthode fetch().

Consultez la documentation spécifique pour chaque composant pour plus de détails.
