Test2::API(3perl) Guide de référence du programmeur Perl Test2::API(3perl)

NOM

Test2::API - Interface principale pour l'écriture d'outils de test basés sur Test2.

***NOTE INTERNE***

Les détails internes de ce paquet sont susceptibles d'être modifiés à tout moment ! Les méthodes publiques fournies ne changeront pas de manière incompatible avec les versions précédentes (une fois qu'une version stable sera disponible), mais les détails de mise en œuvre sous-jacents pourraient l'être. Ne cassez pas l'encapsulation ici !

Actuellement, l'implémentation consiste à créer une seule instance de l'objet Test2::API::Instance. Toutes les méthodes de classe délèguent à l'instance unique. Il n'y a pas d'accès public au singleton, et c'est intentionnel. Les méthodes de classe fournies par ce paquet constituent la seule fonctionnalité exposée publiquement.

Ceci est fait principalement pour éviter les problèmes rencontrés par Test::Builder en exposant son singleton. Nous ne voulons pas que quelqu'un remplace ce singleton, le rebless, ou manipule directement ses détails internes. Si vous avez besoin de faire quelque chose et que vous ne le pouvez pas en raison des restrictions imposées ici, veuillez le signaler comme un problème. Si possible, nous créerons un moyen pour vous de mettre en œuvre votre fonctionnalité sans exposer ce qui ne devrait pas l'être.

DESCRIPTION

Ce paquet exporte toutes les fonctions nécessaires pour écrire et/ou vérifier des outils de test. En utilisant ces blocs de construction, vous pouvez commencer à écrire des outils de test très rapidement. Vous disposez également d'outils qui vous aident à tester les outils que vous écrivez.

EXEMPLE D'EMPLOI

ÉCRIRE UN OUTIL

La méthode context() est votre interface principale dans le framework Test2.

package My::Ok;
use Test2::API qw/context/;
our @EXPORT = qw/my_ok/;
use base 'Exporter';
# Similaire à ok() de Test::More
sub my_ok($;$) {
    my ($bool, $name) = @_;
    my $ctx = context(); # Obtenir un contexte
    $ctx->ok($bool, $name);
    $ctx->release; # Libérer le contexte
    return $bool;
}

Voir Test2::API::Context pour une liste des méthodes disponibles sur l'objet contexte.

TESTER VOS OUTILS

L'outil "intercept { ... }" vous permet d'intercepter temporairement tous les événements générés par le système de test :

use Test2::API qw/intercept/;
use My::Ok qw/my_ok/;
my $events = intercept {
    # Ces événements ne sont pas affichés
    my_ok(1, "réussite");
    my_ok(0, "échec");
};

Depuis la version 1.302178, ceci retourne maintenant un tableau référencé qui est également une instance de Test2::API::InterceptResult. Voir la documentation de Test2::API::InterceptResult pour savoir comment l'utiliser au mieux.

EXPORTATIONS API PRINCIPALE

Toutes les exportations sont optionnelles. Vous devez spécifier les subs à importer.

use Test2::API qw/context intercept run_subtest/;

C'est la liste des exportations les plus couramment nécessaires. Si vous écrivez simplement un outil, alors c'est probablement tout ce dont vous avez besoin. Si vous avez besoin de quelque chose et que vous ne le trouvez pas ici, vous pouvez également consulter la section "AUTRES EXPORTATIONS API".

Ces exportations n'ont pas le préfixe 'test2_' en raison de leur importance/fréquence. Les exportations dans la section "AUTRES EXPORTATIONS API" ont le préfixe 'test2_' pour s'assurer qu'elles se distinguent.

context(...)

Utilisation :

$ctx = context()
$ctx = context(%params)

La fonction context() retournera toujours le contexte actuel. S'il y a déjà un contexte actif, il sera retourné. S'il n'y a pas de contexte actif, un sera généré. Lorsqu'un contexte est généré, il utilisera par défaut le fichier et le numéro de ligne d'où la sous-routine en cours d'exécution a été appelée.

Veuillez consulter "DÉTAILS CRITIQUES" dans Test2::API::Context pour connaître les règles importantes concernant ce que vous pouvez et ne pouvez pas faire avec un contexte une fois qu'il est obtenu.

Note Cette fonction lèvera une exception si vous ignorez l'objet contexte qu'elle retourne.

Note Sur les Perl 5.14+, une vérification de profondeur est utilisée pour s'assurer qu'il n'y a pas de fuites de contexte. Cela ne peut pas être fait en toute sécurité sur les anciennes versions de Perl en raison de https://rt.perl.org/Public/Bug/Display.html?id=127774 Vous pouvez l'activer de force soit en définissant "$ENV{T2_CHECK_DEPTH} = 1", soit "$Test2::API::DO_DEPTH_CHECK = 1" AVANT de charger Test2::API.

PARAMÈTRES OPTIONNELS

Tous les paramètres de "context" sont facultatifs.

level => $int
Si vous devez obtenir un contexte dans une sous-routine plus profonde que votre point d'entrée, vous pouvez l'utiliser pour lui indiquer le nombre de cadres de pile SUPPLÉMENTAIRES à remonter. Si cette option n'est pas fournie, la valeur par défaut de 0 est utilisée. 
sub third_party_tool {
    my $sub = shift;
    ... # N'obtient pas de contexte
    $sub->();
    ...
}
third_party_tool(sub {
    my $ctx = context(level => 1);
    ...
    $ctx->release;
});
wrapped => $int
Utilisez ceci si vous avez besoin d'écrire votre propre outil qui encapsule un appel à context() dans le but qu'il retourne un objet contexte. 
sub my_context {
    my %params = ( wrapped => 0, @_ );
    $params{wrapped}++;
    my $ctx = context(%params);
    ...
    return $ctx;
}
sub my_tool {
    my $ctx = my_context();
    ...
    $ctx->release;
}

Si vous ne faites pas cela, les outils que vous appelez et qui vérifient également un contexte remarqueront que le contexte qu'ils ont saisi a été créé à la même profondeur de pile, ce qui déclenchera des mesures de protection qui vous avertiront et détruiront le contexte existant.

stack => $stack
Normalement, context() examine la pile du hub global. Si vous maintenez votre propre instance de Test2::API::Stack, vous pouvez la passer pour qu'elle soit utilisée à la place de la pile globale.
hub => $hub
Utilisez ce paramètre si vous souhaitez obtenir le contexte pour un hub spécifique au lieu de celui qui se trouve au sommet de la pile.
on_init => sub { ... }
Cela vous permet de fournir une sous-routine de rappel qui sera appelée UNIQUEMENT si votre appel à context() a généré un nouveau contexte. Le rappel NE SERA PAS appelé si context() retourne un contexte existant. Le seul argument passé au rappel sera l'objet contexte lui-même. 
sub foo {
    my $ctx = context(on_init => sub { 'sera exécuté' });
    my $inner = sub {
        # Ce rappel ne s'exécute pas car nous obtenons le contexte existant
        # de notre sous-routine parente.
        my $ctx = context(on_init => sub { 'NE SERA PAS exécuté' });
        $ctx->release;
    }
    $inner->();
    $ctx->release;
}
on_release => sub { ... }
Cela vous permet de fournir une sous-routine de rappel qui sera appelée lorsque l'instance de contexte sera libérée. Ce rappel sera ajouté au contexte retourné même si un contexte existant est retourné. Si plusieurs appels à context ajoutent des rappels, tous seront appelés dans l'ordre inverse lorsque le contexte sera finalement libéré. 
sub foo {
    my $ctx = context(on_release => sub { 'sera exécuté en deuxième' });
    my $inner = sub {
        my $ctx = context(on_release => sub { 'sera exécuté en premier' });
        # Aucun des deux rappels ne s'exécute lors de cette libération

release($;$)

Utilisation:

release $ctx;
release $ctx, ...;

Ceci est conçu comme un raccourci qui vous permet de libérer votre contexte et de retourner une valeur en une seule instruction. Cette fonction obtiendra votre contexte, et une valeur de retour optionnelle. Elle libérera votre contexte, puis retournera votre valeur. Le contexte scalaire est toujours supposé.

sub tool {
    my $ctx = context();
    ...
    return release $ctx, 1;
}

Cet outil est plus utile lorsque vous souhaitez retourner la valeur que vous obtenez en appelant une fonction qui doit voir le contexte actuel :

my $ctx = context();
my $out = some_tool(...);
$ctx->release;
return $out;

Nous pouvons combiner les 3 dernières lignes de ce qui précède comme suit :

my $ctx = context();
release $ctx, some_tool(...);

context_do(&;@)

Utilisation:

sub my_tool {
    context_do {
        my $ctx = shift;
        my (@args) = @_;
        $ctx->ok(1, "pass");
        ...
        # Pas besoin d'appeler $ctx->release, c'est fait pour vous à la sortie de portée.
    } @_;
}

Utiliser ceci à l'intérieur de votre outil de test s'occupe de beaucoup de code répétitif pour vous. Il garantit qu'un contexte est acquis. Il capture et relance toute exception. Il garantit que le contexte est libéré lorsque vous avez terminé. Il préserve le contexte d'appel de sous-routine (liste, scalaire, vide).

C'est la manière la plus sûre d'écrire un outil de test. Les deux seuls inconvénients sont une légère diminution des performances et une indentation supplémentaire dans votre source. Si l'indentation est un problème pour vous, vous pouvez jeter un œil à la section suivante.

no_context(&;$)

Utilisation:

no_context { ... };
no_context { ... } $hid;
sub my_tool(&) {
    my $code = shift;
    my $ctx = context();
    ...
    no_context {
        # Les choses ici ne verront pas notre contexte actuel, elles en obtiennent un nouveau.
        $code->();
    };
    ...
    $ctx->release;
};

Cet outil masquera un contexte pour le bloc de code fourni. Cela signifie que tous les outils exécutés à l'intérieur du bloc recevront un contexte complètement nouveau s'ils en acquièrent un. Le nouveau contexte sera hérité par les outils imbriqués en dessous de celui qui l'a acquis.

Cela masquera normalement le contexte actuel pour le hub supérieur. Si vous avez besoin de masquer le contexte pour un hub différent, vous pouvez passer le paramètre optionnel $hid.

intercept(&)

Utilisation:

my $events = intercept {
    ok(1, "pass");
    ok(0, "fail");
    ...
};

Cette fonction prend un bloc de code comme seul argument, et elle a un prototype. Elle exécutera le bloc de code, interceptant tous les événements générés au cours du processus. Elle retournera une référence de tableau avec tous les objets événementiels générés. Tous les événements doivent être des sous-classes de Test2::Event.

À partir de la version 1.302178, le tableau d'événements retourné est béni en tant qu'instance de Test2::API::InterceptResult. Test2::API::InterceptResult fournit une interface utile pour filtrer et/ou inspecter la liste des événements dans l'ensemble, ou les événements individuels au sein de la liste.

Ceci est destiné à vous aider à tester votre code de test. Ceci n'est pas destiné aux personnes qui écrivent simplement des tests.

run_subtest(...)

Utilisation:

run_subtest($NAME, \&CODE, $BUFFERED, @ARGS)
# ou
run_subtest($NAME, \&CODE, \%PARAMS, @ARGS)

Ceci exécutera le bloc de code fourni avec les arguments dans @args. Ce bloc de code sera exécuté comme un sous-test. Un sous-test est un état de test isolé qui est condensé en un seul événement Test2::Event::Subtest, qui contient tous les événements générés à l'intérieur du sous-test.

ARGUMENTS:

$NAME
Le nom du sous-test.
\&CODE
Le code à exécuter dans le sous-test.
$BUFFERED ou \%PARAMS
Si c'est un scalaire simple, il sera traité comme un booléen pour le paramètre 'buffered'. Si c'est une référence de hachage, il sera utilisé comme un paramètre de hachage. Le hachage de paramètres sera utilisé pour la construction du hub (avec les clés spécifiées supprimées).

Clés qui sont supprimées et utilisées par run_subtest :

'buffered' => $bool
Active/désactive le statut tamponné.
'inherit_trace' => $bool
Normalement, le hub de sous-test est empilé et le sous-test est autorisé à générer son propre contexte racine pour le hub. Lorsque ce paramètre est activé, un contexte racine est créé pour le hub qui partage la même trace que le contexte actuel.

Définissez ceci sur vrai si votre outil produit des sous-tests sans sous-routines spécifiées par l'utilisateur.

'no_fork' => $bool
Par défaut désactivé. Normalement, le forkage à l'intérieur d'un sous-test provoquera effectivement le forkage du sous-test, résultant en 2 événements de sous-test finaux. Ce paramètre désactivera ce comportement, seul le processus/thread d'origine retournera un événement de sous-test final.
@ARGS
Tous les arguments supplémentaires que vous souhaitez passer au code du sous-test.

TAMPONNÉ VS NON TAMPONNÉ (OU EN FLUX)

Normalement, tous les événements à l'intérieur et à l'extérieur d'un sous-test sont envoyés au formateur immédiatement par le hub. Il est parfois souhaitable de retarder l'envoi des événements à l'intérieur d'un sous-test jusqu'à ce que le sous-test soit terminé. Cela dépend généralement du formateur utilisé.

Les choses non affectées par ce drapeau
Dans les deux cas, les événements sont générés et stockés dans un tableau. Ce tableau est éventuellement utilisé pour remplir l'attribut "subevents" sur l'événement Test2::Event::Subtest qui est généré à la fin du sous-test. Ce drapeau n'a aucun effet sur cette partie ; cela se produit toujours.

À la fin du sous-test, l'événement final Test2::Event::Subtest est envoyé au formateur.

Les choses qui sont affectées par ce drapeau
L'attribut "buffered" de l'événement Test2::Event::Subtest sera défini sur la valeur de ce drapeau. Cela signifie que tout formateur, écouteur, etc. qui examine l'événement saura s'il a été tamponné.
Les choses qui dépendent du formateur
Les événements à l'intérieur d'un sous-test tamponné peuvent ou non être envoyés au formateur au fur et à mesure qu'ils se produisent. Si un formateur ne spécifie pas, le défaut est de **NE PAS ENVOYER** les événements au fur et à mesure de leur génération, au lieu de cela, le formateur peut les récupérer de l'attribut "subevents".

Un formateur peut spécifier en implémentant la méthode hide_buffered(). Si cette méthode retourne vrai, alors les événements générés à l'intérieur d'un sous-test tamponné ne seront pas envoyés indépendamment de l'événement de sous-test final.

Un exemple de la façon dont cela est utilisé est le formateur Test2::Formatter::TAP. Pour les sous-tests non tamponnés, les événements sont rendus au fur et à mesure de leur génération. À la fin du sous-test, l'événement de sous-test final est rendu, mais l'attribut "subevents" est ignoré. Pour les sous-tests tamponnés, le contraire se produit, les événements NE SONT PAS rendus au fur et à mesure de leur génération, au lieu de cela, l'attribut "subevents" est utilisé pour les rendre tous en une seule fois. Ceci est utile lors de l'exécution de tests de sous-tests en parallèle, car sans cela, la sortie des sous-tests serait entrelacée.

AUTRES EXPORTATIONS API

Les exportations dans cette section ne sont généralement pas nécessaires. Toutes ont le préfixe 'test2_' pour aider à les faire ressortir. Vous devriez regarder la section "EXPORTATIONS API PRINCIPALES" avant de regarder ici. Cette section est celle où "Un grand pouvoir implique une grande responsabilité". Il est possible de casser gravement les choses si vous ne faites pas attention avec celles-ci.

Toutes les exportations sont facultatives. Vous devez indiquer celles que vous souhaitez au moment de l'importation :

use Test2::API qw/test2_init_done .../;

ETAT STATUT ET INITIALISATION

Ceux-ci fournissent un accès à l'état interne et aux instances d'objets.

$bool = test2_init_done()
Ceci retournera vrai si les instances de pile et d'IPC ont déjà été initialisées. Il retournera faux si elles ne l'ont pas été. L'initialisation se fait le plus tard possible. Elle se produit dès qu'un outil demande l'instance IPC, le formateur, ou la pile.
$bool = test2_load_done()
Ceci retournera simplement la valeur booléenne du drapeau chargé. Si Test2 a terminé le chargement, ce sera vrai, sinon faux. Le chargement est considéré comme complet la première fois qu'un outil demande un contexte.
test2_set_is_end()
test2_set_is_end($bool)
Ceci est utilisé pour basculer la croyance de Test2 que la phase FIN est déjà commencée. Sans arguments, cela le définira sur vrai. Avec des arguments, cela le définira sur la valeur du premier argument.

Ceci est utilisé pour empêcher l'utilisation de caller() dans les blocs FIN, ce qui peut provoquer des segfaults. Ceci n'est nécessaire que dans certains environnements persistants qui peuvent avoir plusieurs phases FIN.

$bool = test2_get_is_end()
Vérifie si Test2 croit être dans la phase FIN.
$stack = test2_stack()
Ceci retournera l'instance globale de Test2::API::Stack. Si elle n'a pas encore été initialisée, elle sera initialisée maintenant.
$bool = test2_is_testing_done()
Ceci retournera vrai si les tests sont terminés et qu'aucun autre événement ne doit être envoyé. Ceci est utile dans des choses comme les gestionnaires d'avertissement où vous pourriez vouloir transformer les avertissements en événements, mais avez besoin qu'ils agissent comme des avertissements normaux lorsque les tests sont terminés.

GESTION DES AVERTISSEMENTS

$SIG{__WARN__} = sub { ... }
$SIG{__WARN__} = sub {
    my ($warning) = @_;
    if (test2_is_testing_done()) {
        warn @_;
    }
    else {
        my $ctx = context();
        ...
        $ctx->release
    }
}
test2_ipc_disable
Désactiver l'IPC.
$bool = test2_ipc_disabled
Vérifier si l'IPC est désactivé.
test2_ipc_wait_enable()
test2_ipc_wait_disable()
$bool = test2_ipc_wait_enabled()
Celles-ci peuvent être utilisées pour activer ou désactiver l'attente IPC, ou pour vérifier la valeur actuelle du drapeau.

L'attente est désactivée par défaut. L'attente entraînera le blocage du processus parent/de thread jusqu'à ce que tous les processus enfants/threads soient terminés avant de se terminer. Vous ne voudrez presque jamais désactiver cette fonction.

$bool = test2_no_wait()
test2_no_wait($bool)
DÉCONSEILLÉ : Cette interface est confuse, il est préférable d'utiliser test2_ipc_wait_enable(), test2_ipc_wait_disable() et test2_ipc_wait_enabled().

Celle-ci peut être utilisée pour obtenir/définir l'état de non-attente. L'attente est activée par défaut. L'attente entraînera le blocage du processus parent/de thread jusqu'à ce que tous les processus enfants/threads soient terminés avant de se terminer. Vous ne voudrez presque jamais désactiver cette fonction.

$fh = test2_stdout()
$fh = test2_stderr()
Ces fonctions retournent les descripteurs de fichiers vers lesquels la sortie des tests doit être écrite. Elles sont principalement utiles lorsque vous écrivez un formateur personnalisé et du code qui transforme les événements en sortie (TAP, etc.). Elles retourneront une copie de l'original, quel que soit l'état du test en cours, STDOUT et STDERR seront identiques.
test2_reset_io()
Recrée les descripteurs de fichiers internes retournés par test2_stdout() et test2_stderr() à partir du STDOUT et STDERR actuels. Vous ne devriez pas en avoir besoin sauf dans des situations très inhabituelles (par exemple, lorsque vous testez un nouveau formateur et que vous voulez avoir le contrôle sur l'endroit où la sortie du formateur est envoyée).

ACCROCHAGES DE COMPORTEMENT

Ce sont les points d'accroche qui permettent d'ajouter un comportement personnalisé aux actions entreprises par Test2 et les outils qui en dépendent.

test2_add_callback_exit(sub { ... })
Celle-ci peut être utilisée pour ajouter une fonction de rappel qui sera appelée après la fin de tous les tests. Il est trop tard pour ajouter de nouveaux résultats, l'utilisation principale de cette fonction de rappel est la définition du code de sortie. 
test2_add_callback_exit(
    sub {
        my ($context, $exit, \$new_exit) = @_;
        ...
    }
);

Le $context passé sera une instance de Test2::API::Context. L'argument $exit sera le code de sortie original avant toute modification. $$new_exit est une référence au nouveau code de sortie. Vous pouvez le modifier pour changer le code de sortie. Veuillez noter que $$new_exit peut déjà être différent de $exit

test2_add_callback_post_load(sub { ... })
Ajouter une fonction de rappel qui sera exécutée lorsque Test2 aura fini de se charger. Cela signifie que la fonction de rappel sera exécutée une fois, la première fois qu'un contexte est obtenu. Si Test2 a déjà fini de se charger, la fonction de rappel s'exécutera immédiatement.
test2_add_callback_testing_done(sub { ... })
Ceci ajoute votre coderef comme un suivi au hub racine une fois que Test2 a fini de se charger.

Ceci est essentiellement une aide pour faire ce qui suit :

test2_add_callback_post_load(sub {
    my $stack = test2_stack();
    $stack->top; # Assurez-vous d'avoir un hub
    my ($hub) = Test2::API::test2_stack->all;
    $hub->set_active(1);
    $hub->follow_up(sub { ... }); # <-- Votre coderef ici
});
test2_add_callback_context_acquire(sub { ... })
Ajouter une fonction de rappel qui sera exécutée chaque fois que quelqu'un essaie d'acquérir un contexte. Ceci sera exécuté sur chaque appel à context(). Un seul argument sera reçu, une référence aux paramètres utilisés pour construire le contexte. C'est votre chance de modifier les paramètres en modifiant directement le hash. 
test2_add_callback_context_acquire(sub {
    my $params = shift;
    $params->{level}++;
});

Ceci est une fonction API très dangereuse. S'il vous plaît, ne l'utilisez pas sauf si vous en avez besoin. Elle est là pour Test::Builder et la compatibilité descendante. Elle manipule directement le hash au lieu d'en retourner un nouveau pour des raisons de performance.

test2_add_callback_context_init(sub { ... })
Ajouter une fonction de rappel qui sera exécutée chaque fois qu'un nouveau contexte est créé. La fonction de rappel recevra le nouveau contexte comme son seul argument.
test2_add_callback_context_release(sub { ... })
Ajouter une fonction de rappel qui sera exécutée chaque fois qu'un contexte est libéré. La fonction de rappel recevra le contexte libéré comme son seul argument.
test2_add_callback_pre_subtest(sub { ... })
Ajouter une fonction de rappel qui sera exécutée chaque fois qu'une sous-test est sur le point d'être exécutée. La fonction de rappel recevra le nom de la sous-test, le coderef et tous les arguments.
@list = test2_list_context_acquire_callbacks()
Retourne toutes les références de fonctions de rappel d'acquisition de contexte.
@list = test2_list_context_init_callbacks()
Retourne toutes les références de fonctions de rappel d'initialisation de contexte.
@list = test2_list_context_release_callbacks()
Retourne toutes les références de fonctions de rappel de libération de contexte.
@list = test2_list_exit_callbacks()
Retourne toutes les références de fonctions de rappel de sortie.
@list = test2_list_post_load_callbacks()
Retourne toutes les références de fonctions de rappel de post-chargement.
@list = test2_list_pre_subtest_callbacks()
Retourne toutes les références de fonctions de rappel de pré-sous-test.
test2_add_uuid_via(sub { ... })
$sub = test2_add_uuid_via()
Ceci vous permet de fournir un générateur d'UUID. Si des UUID sont fournis, ils seront ajoutés à tous les événements, hubs et contextes. Il est utile pour le stockage, le suivi et la liaison de ces objets.

Le sous-programme que vous fournissez doit toujours retourner un identifiant unique. La plupart des objets s'attendent à une chaîne UUID, bien que rien dans Test2::API ne l'impose.

Le sous-programme recevra exactement 1 argument, le type d'objet qui doit être étiqueté 'context', 'hub' ou 'event'. À l'avenir, d'autres objets pourraient être étiquetés, auquel cas de nouvelles chaînes seront passées. Celles-ci sont informatives, vous pouvez les ignorer (et vous devriez presque toujours le faire).

test2_add_pending_diag($diag)
test2_add_pending_diag($diag1, $diag2)
Ajouter un message de diagnostic qui sera émis la prochaine fois qu'un contexte dans lequel une défaillance s'est produite sera libéré.

Ceci peut également être pensé comme suit : « Si le prochain bit entraîne une affirmation échouée, ajoutez ce message de diagnostic ».

@diags = test2_get_pending_diags()
Obtenir tous les messages de diagnostic en attente actuels.
@diags = test2_clear_pending_diags()
Effacer tous les messages de diagnostic en attente, en les retournant.

Ceux-ci permettent d'accéder aux internes du système IPC ou de les spécifier.

$bool = test2_has_ipc()
Vérifier si l'IPC est actif.
$ipc = test2_ipc()
Ceci retournera le pilote Test2::IPC global instancié. S'il n'a pas encore été initialisé, il l'initialisera maintenant.
test2_ipc_add_driver($DRIVER)
Ajouter un pilote IPC à la liste. Ceci ajoutera le pilote au début de la liste.
@drivers = test2_ipc_drivers()
Obtenir la liste des pilotes IPC.
$bool = test2_ipc_polling()
Vérifier si le polling est actif.
test2_ipc_enable_polling()
Activer le polling. Chaque fois qu'un contexte est créé, les événements des autres processus et threads seront retirés.
test2_ipc_disable_polling()
Désactiver le polling IPC.
test2_ipc_enable_shm()
Ancien, ceci est actuellement un no-op qui retourne 0;
test2_ipc_set_pending($uniq_val)
Indiquer aux autres processus et événements qu'il y a un événement en attente. $uniq_val doit être une valeur unique non générée par d'autres threads/processus.

Remarque : Après avoir appelé test2_ipc_get_pending(), il retournera 1. Ceci est intentionnel et ne peut pas être évité.

$pending = test2_ipc_get_pending()
Retourne -1 s'il n'y a aucun moyen de vérifier (nous supposons que oui).

Retourne 0 s'il n'y a (très probablement) aucun événement en attente.

Retourne 1 s'il y a (probablement) des événements en attente. Lors du retour, il est réinitialisé, rien d'autre ne pourra voir qu'il y avait des événements en attente.

Test2::API(3pm)

NAME

Test2::API - The main API for Test2

***INTERNALS NOTE***

This module is designed to be the main entry point for Test2 modules. It exports very little, and relies on other modules to do the actual work. This is intentional.

It is possible for Test2 to be run without any modules being loaded at all. In this case, the defaults will be used. The primary reason for this is that Test2 is designed to be a foundation for other testing modules. Many testing modules will export their own subroutines and may not even require Test2::API to be explicitly required. However, for those that do, this module serves as the primary API.

DESCRIPTION

This module provides the main interface to the Test2 testing framework. It allows you to configure the core components of the framework, such as the formatter and the IPC system.

SYNOPSIS

    use Test2::API;
    use Test2::Bundle::More;

    ok 1, 'This is a test';

    # Accessing configuration
    my $timeout = test2_ipc_set_timeout( 60 );
    my $formatter = test2_formatter;
    test2_formatter_set('My::Custom::Formatter');

ENVIRONMENT VARIABLES

The following environment variables can be used to configure Test2:

T2_FORMATTER
Specifies the formatter to use. This can be a short name (e.g., TAP) or a fully qualified module name (e.g., +My::Formatter).
T2_DEBUG
Enable debugging output for Test2.

MAIN API EXPORTS

This module exports the following subroutines:

test2_ipc_set_timeout($timeout)
Get/Set the timeout value for the IPC system. This timeout is how long the IPC system will wait for child processes and threads to finish before aborting.

The default value is 30 seconds.

MANAGING FORMATTERS

These let you access, or specify, the formatters that can/should be used.

$formatter = test2_formatter
This will return the global formatter class. This is not an instance. By default the formatter is set to Test2::Formatter::TAP.

You can override this default using the "T2_FORMATTER" environment variable.

Normally 'Test2::Formatter::' is prefixed to the value in the environment variable:

$ T2_FORMATTER='TAP' perl test.t     # Use the Test2::Formatter::TAP formatter
$ T2_FORMATTER='Foo' perl test.t     # Use the Test2::Formatter::Foo formatter

If you want to specify a full module name you use the '+' prefix:

$ T2_FORMATTER='+Foo::Bar' perl test.t     # Use the Foo::Bar formatter
test2_formatter_set($class_or_instance)
Set the global formatter class. This can only be set once. Note: This will override anything specified in the 'T2_FORMATTER' environment variable.
@formatters = test2_formatters()
Get a list of all loaded formatters.
test2_formatter_add($class_or_instance)
Add a formatter to the list. Last formatter added is used at initialization. If this is called after initialization a warning will be issued.

TIME STAMPS

You can enable or disable timestamps in trace facets. They are disabled by default for compatibility and performance reasons.

test2_enable_trace_stamps()
Enable stamps in traces.
test2_disable_trace_stamps()
Disable stamps in traces.
$bool = test2_trace_stamps_enabled()
Check status of trace stamps.
