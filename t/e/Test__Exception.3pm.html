NOM

Test::Exception - Tests de code utilisant des exceptions

SYNTAXE

use Test::More tests => 5;
use Test::Exception;
# ou si vous n'avez pas besoin de Test::More
use Test::Exception tests => 5;
# puis...
# Vérifier que l'exception sérialisée correspond à une regex donnée
throws_ok { $foo->method } qr/division by zero/, 'zero caught okay';
# Vérifier qu'une exception de la classe donnée (ou dérivée) est levée
throws_ok { $foo->method } 'Error::Simple', 'simple error thrown';

# tous les méthodes de Test::Exception préservent l'état de $@, donc vous pouvez faire des choses comme ceci après throws_ok et dies_ok
like $@, 'what the stringified exception should look like';
# Vérifier que quelque chose a échoué - peu importe pourquoi
dies_ok { $foo->method } 'expecting to die';
# Vérifier que quelque chose n'a pas échoué
lives_ok { $foo->method } 'expecting to live';
# Vérifier qu'un test s'exécute sans exception
lives_and { is $foo->method, 42 } 'method is 42';

# ou si vous n'aimez pas les fonctions prototypées

throws_ok( sub { $foo->method }, qr/division by zero/,
    'zero caught okay' );
throws_ok( sub { $foo->method }, 'Error::Simple', 
    'simple error thrown' );
dies_ok( sub { $foo->method }, 'expecting to die' );
lives_ok( sub { $foo->method }, 'expecting to live' );
lives_and( sub { is $foo->method, 42 }, 'method is 42' );

DESCRIPTION

Ce module offre quelques méthodes pratiques pour tester du code qui utilise des exceptions. Il est construit avec Test::Builder et s'intègre bien avec Test::More et ses amis.

Si vous n'êtes pas familier avec Test::More, ce serait le moment de jeter un œil.

Vous pouvez spécifier le plan de test lors de l'utilisation de "use Test::Exception" dans le même fichier que "use Test::More". Voir Test::More pour plus de détails.

NOTE : Test::Exception ne vérifie que les exceptions. Il ignore les autres méthodes d'arrêt de programme, y compris exit(). Si vous avez un exit() dans le code évalué, Test::Exception ne le capturera avec aucune de ses fonctions de test.

NOTE : Ce module utilise Sub::Uplevel et s'appuie sur la surcharge de "CORE::GLOBAL::caller" pour masquer vos blocs de test de la pile d'appels. Si cela vous préoccupe, le module Test::Fatal offre une alternative plus minimaliste.

throws_ok
Teste qu'une exception spécifique est levée. throws_ok() a deux formes : 
throws_ok BLOCK REGEX, TEST_DESCRIPTION
throws_ok BLOCK CLASS, TEST_DESCRIPTION

Dans la première forme, le test réussit si l'exception sérialisée correspond à l'expression régulière donnée. Par exemple :

throws_ok { read_file( 'unreadable' ) } qr/No file/, 'no file';

Si votre perl ne supporte pas "qr//", vous pouvez aussi passer une chaîne qui se comporte comme une expression régulière, par exemple :

throws_ok { read_file( 'unreadable' ) } '/No file/', 'no file';

La deuxième forme de throws_ok() réussit si l'exception est de la même classe que celle donnée, ou d'une classe dérivée de celle-ci. Par exemple :

throws_ok { $foo->bar } "Error::Simple", 'simple error';

Cela ne réussira que si la méthode "bar" lève une exception Error::Simple, ou une exception dérivée d'une exception Error::Simple.

Vous pouvez obtenir le même effet en passant un objet de l'exception que vous souhaitez voir. Ce qui suit est équivalent à l'exemple précédent :

my $SIMPLE = Error::Simple->new;
throws_ok { $foo->bar } $SIMPLE, 'simple error';

Si un test throws_ok() échoue, des messages de diagnostic appropriés sont produits. Par exemple :

not ok 3 - simple error
#     Failed test (test.t at line 48)
#     expecting: Error::Simple exception
#     found: normal exit

Comme toutes les fonctions de Test::Exception, vous pouvez éviter les prototypes en passant explicitement une sous-routine :

throws_ok( sub {$foo->bar}, "Error::Simple", 'simple error' );

Une valeur vraie est retournée si le test réussit, et fausse sinon. À la sortie, $@ garantit être la cause de la mort (s'il y en a une).

Si une description optionnelle de l'exception n'est pas fournie, la description de l'exception est utilisée.

NOTE : N'oubliez pas que lorsque vous utilisez "die $string_without_a_trailing_newline", Perl ajoute automatiquement le numéro de ligne courant, le numéro de ligne d'entrée et un saut de ligne. Cela fera partie de la chaîne à laquelle les expressions régulières de throws_ok correspondent.

dies_ok
Vérifie qu'un bloc de code s'arrête, au lieu de retourner normalement. Par exemple : 
sub div {
    my ( $a, $b ) = @_;
    return $a / $b;
};
dies_ok { div( 1, 0 ) } 'divide by zero detected';
# ou si vous n'aimez pas les fonctions prototypées
dies_ok( sub { div( 1, 0 ) }, 'divide by zero detected' );

Une valeur vraie est retournée si le test réussit, et fausse sinon. À la sortie, $@ garantit être la cause de la mort (s'il y en a une).

Note : Ce test réussira si le code s'arrête pour une raison quelconque. Si vous êtes préoccupé par la raison, il serait plus sage d'écrire un test plus spécifique en utilisant throws_ok().

La description du test est optionnelle, mais recommandée.

lives_ok
Vérifie qu'un bloc de code ne s'arrête pas. Cela permet à votre script de test de continuer, au lieu d'être abandonné si une exception inattendue se produit. Par exemple : 
sub read_file {
    my $file = shift;
    local $/;
    open my $fh, '<', $file or die "open failed ($!)\n";
    $file = <FILE>;
    return $file;
};
my $file;
lives_ok { $file = read_file('test.txt') } 'file read';
# ou si vous n'aimez pas les fonctions prototypées
lives_ok( sub { $file = read_file('test.txt') }, 'file read' );

Si un test lives_ok() échoue, des messages de diagnostic appropriés sont produits. Par exemple :

not ok 1 - file read
#     Failed test (test.t at line 15)
#     died: open failed (No such file or directory)

Une valeur vraie est retournée si le test réussit, et fausse sinon. À la sortie, $@ garantit être la cause de la mort (s'il y en a une).

La description du test est optionnelle, mais recommandée.

lives_and
Exerce un test qui pourrait lancer une exception. Par exemple, au lieu de faire : 
my $file;
lives_ok { $file = read_file('answer.txt') } 'read_file worked';
is $file, "42", 'answer was 42';

Vous pouvez utiliser lives_and() comme ceci :

lives_and { is read_file('answer.txt'), "42" } 'answer is 42';
# ou si vous n'aimez pas les fonctions prototypées
lives_and(sub {is read_file('answer.txt'), "42"}, 'answer is 42');

C'est la même chose que de faire :

is read_file('answer.txt'), "42\n", 'answer is 42';

sauf que si read_file('answer.txt') s'arrête, vous obtenez le même type d'erreur que lives_ok()

not ok 1 - answer is 42
#     Failed test (test.t at line 15)
#     died: open failed (No such file or directory)

Une valeur vraie est retournée si le test réussit, et fausse sinon. À la sortie, $@ garantit être la cause de la mort (s'il y en a une).

La description du test est optionnelle, mais recommandée.

IGNORER LES TESTS TEST::EXCEPTION

Parfois, nous voulons utiliser les tests de Test::Exception dans un ensemble de tests, mais nous ne voulons pas forcer les utilisateurs à avoir Test::Exception installé. Une façon de faire cela est d'ignorer les tests si Test::Exception n'est pas présent. Vous pouvez faire cela avec un code similaire à ceci :

use strict;
use warnings;
use Test::More;

BEGIN {
    eval "use Test::Exception";
    plan skipAll => "Test::Exception required" if $@;
}

plan tests => 2;
# ... tests qui ont besoin de Test::Exception ...

Note : nous chargeons Test::Exception dans un bloc "BEGIN", garantissant que les prototypes des sous-routines sont prêts avant que le reste du script de test ne soit compilé.
