Test::Builder(3perl) Guide du programmeur Perl Test::Builder(3perl)

NOM

Test::Builder - Backend pour la création de bibliothèques de test

SYNOPIS

package My::Test::Module;
use base 'Test::Builder::Module';
my $CLASS = __PACKAGE__;
sub ok {
    my($test, $name) = @_;
    my $tb = $CLASS->builder;
    $tb->ok($test, $name);
}

DESCRIPTION

Test::Simple et Test::More se sont avérés être des modules de test populaires, mais ils ne sont pas toujours assez flexibles. Test::Builder fournit un bloc de construction sur lequel écrire vos propres bibliothèques de test qui peuvent travailler ensemble.

Construction

new
my $Test = Test::Builder->new;

Retourne un objet Test::Builder représentant l'état actuel du test.

Puisque vous n'exécutez qu'un seul test par programme, "new" retourne toujours le même objet Test::Builder. Peu importe combien de fois vous appelez new(), vous obtenez le même objet. Ceci est appelé un singleton. C'est fait pour que plusieurs modules partagent des informations globales comme le compteur de tests et où la sortie des tests va.

Si vous voulez un objet Test::Builder complètement nouveau, différent du singleton, utilisez "create".

create
my $Test = Test::Builder->create;

Ok, il peut donc y avoir plus d'un objet Test::Builder et c'est comme ça que vous l'obtenez. Vous pourriez l'utiliser à la place de new() si vous testez un module basé sur Test::Builder, mais sinon vous voudrez probablement "new".

NOTE : l'implémentation n'est pas complète. "level", par exemple, est toujours partagé par tous les objets Test::Builder, même ceux créés avec cette méthode. De plus, le nom de la méthode peut changer à l'avenir.

subtest
$builder->subtest($name, \&subtests, @args);

Voir la documentation de "subtest" dans Test::More.

"subtest" accepte également, optionnellement, des arguments qui seront passés à la référence des sous-tests.

name
diag $builder->name;

Retourne le nom du constructeur actuel. Les constructeurs de niveau supérieur utilisent par défaut $0 (le nom de l'exécutable). Les constructeurs enfants sont nommés via la méthode "child". Si aucun nom n'est fourni, il sera nommé "Enfant de $parent->name".

reset
$Test->reset;

Réinitialise le singleton Test::Builder à son état d'origine. Utile principalement pour les tests exécutés dans des environnements persistants où le même test peut être exécuté plusieurs fois dans le même processus.

Configuration des tests

Ces méthodes servent à configurer les tests et à déclarer combien il y en a. Vous ne voudrez généralement appeler qu'une seule de ces méthodes.

plan
$Test->plan('no_plan');
$Test->plan( skip_all => $reason );
$Test->plan( tests => $num_tests );

Un moyen pratique de configurer vos tests. Appelez cette méthode et Test::Builder affichera les en-têtes appropriés et effectuera les actions appropriées.

Si vous appelez plan(), n'appelez aucune des autres méthodes ci-dessous.

expected_tests
my $max = $Test->expected_tests;
$Test->expected_tests($max);

Récupère/définit le nombre de tests que nous nous attendons à ce que ce test exécute et imprime les en-têtes appropriés.

no_plan
$Test->no_plan;

Déclare que ce test exécutera un nombre indéterminé de tests.

done_testing
$Test->done_testing();
$Test->done_testing($num_tests);

Déclare que vous avez terminé les tests, qu'aucun test supplémentaire ne sera exécuté après ce point.

Si un plan n'a pas encore été émis, il le fera.

$num_tests est le nombre de tests que vous aviez prévu d'exécuter. Si un plan numéroté a déjà été déclaré et si cela contredit, un test échoué sera exécuté pour refléter l'erreur de planification. Si "no_plan" a été déclaré, cela l'écrasera.

Si done_testing() est appelé deux fois, le deuxième appel générera un test échoué.

Si $num_tests est omis, le nombre de tests exécutés sera utilisé, comme pour no_plan.

done_testing() est, en effet, utilisé quand vous voudriez utiliser "no_plan", mais en plus sûr. Vous l'utiliseriez comme ceci :

$Test->ok($a == $b);
$Test->done_testing();

Ou pour planifier un nombre variable de tests :

for my $test (@tests) {
    $Test->ok($test);
}
$Test->done_testing(scalar @tests);
has_plan
$plan = $Test->has_plan

Découvrez si un plan a été défini. $plan est soit "undef" (aucun plan n'a été défini), "no_plan" (nombre indéterminé de tests) soit un entier (le nombre de tests attendus).

skip_all
$Test->skip_all;
$Test->skip_all($reason);

Ignore tous les tests, en utilisant la raison fournie $reason. Quitte immédiatement avec 0.

exported_to
my $pack = $Test->exported_to;
$Test->exported_to($pack);

Indique à Test::Builder dans quel paquet vous avez exporté vos fonctions.

Cette méthode n'est pas très utile car les modules qui partagent le même objet Test::Builder pourraient être exportés vers différents paquets et seul le dernier sera honoré.

Exécution des tests

Ceux-ci exécutent réellement les tests, de manière analogue aux fonctions de Test::More.

Ils retournent tous vrai si le test a réussi, faux si le test a échoué.

$name est toujours facultatif.

ok
$Test->ok($test, $name);

Votre test de base. Réussit si $test est vrai, échoue si $test est faux. Comme le ok() de Test::Simple.

is_eq
$Test->is_eq($got, $expected, $name);

Comme le is() de Test::More. Vérifie si "$got eq $expected". C'est la version chaîne.

"undef" ne correspond jamais qu'à un autre "undef".

is_num
$Test->is_num($got, $expected, $name);

Comme le is() de Test::More. Vérifie si "$got == $expected". C'est la version numérique.

"undef" ne correspond jamais qu'à un autre "undef".

isnt_eq
$Test->isnt_eq($got, $dont_expect, $name);

Comme le isnt() de Test::More. Vérifie

cks si "$got ne $dont_expect". C'est la version chaîne.

isnt_num
$Test->isnt_num($got, $dont_expect, $name);

Comme isnt() de Test::More. Vérifie si "$got ne $dont_expect". C'est la version numérique.

like
$Test->like($thing, qr/$regex/, $name);
$Test->like($thing, '/$regex/', $name);

Comme like() de Test::More. Vérifie si $thing correspond à l'$regex donnée.

unlike
$Test->unlike($thing, qr/$regex/, $name);
$Test->unlike($thing, '/$regex/', $name);

Comme unlike() de Test::More. Vérifie si $thing **ne correspond pas** à l'$regex donnée.

cmp_ok
$Test->cmp_ok($thing, $type, $that, $name);

Fonctionne exactement comme cmp_ok() de Test::More.

$Test->cmp_ok($big_num, '!=', $other_big_num);

Autres Méthodes de Test

Ce sont des méthodes utilisées lors de l'écriture d'un test mais qui ne sont pas des tests elles-mêmes.

BAIL_OUT
$Test->BAIL_OUT($reason);

Indique à Test::Harness que les choses vont si mal que tous les tests doivent s'arrêter. Cela inclut l'exécution de scripts de test supplémentaires.

Il se terminera avec le code 255.

skip
$Test->skip;
$Test->skip($why);

Ignore le test courant, en signalant $why.

todo_skip
$Test->todo_skip;
$Test->todo_skip($why);

Comme skip(), mais il déclarera le test comme échoué et TODO. Similaire à

print "not ok $tnum # TODO $why\n";

Méthodes utilitaires de construction de tests

Ces méthodes sont utiles lors de l'écriture de vos propres méthodes de test.

maybe_regex
$Test->maybe_regex(qr/$regex/);
$Test->maybe_regex('/$regex/');

Cette méthode était utile à l'époque où Test::Builder fonctionnait sur des Perls avant 5.6 qui n'avaient pas qr//. Maintenant, elle est assez inutile.

Méthode de commodité pour construire des fonctions de test qui acceptent des expressions régulières comme arguments.

Prend une expression régulière entre guillemets produite par "qr//", ou une chaîne représentant une expression régulière.

Retourne une valeur Perl qui peut être utilisée à la place de l'expression régulière correspondante, ou "undef" si son argument n'est pas reconnu.

Par exemple, une version de like(), sans les messages de diagnostic utiles, pourrait s'écrire comme suit :

sub laconic_like {
    my ($self, $thing, $regex, $name) = @_;
    my $usable_regex = $self->maybe_regex($regex);
    die "expecting regex, found '$regex'\n"
        unless $usable_regex;
    $self->ok($thing =~ m/$usable_regex/, $name);
}
is_fh
my $is_fh = $Test->is_fh($thing);

Détermine si le $thing donné peut être utilisé comme handle de fichier.

Style de Test

level
$Test->level($how_high);

À quelle hauteur dans la pile d'appels $Test doit chercher lors de la signalisation de l'échec d'un test.

Par défaut à 1.

La définition de $Test::Builder::Level outrepasse. Ceci est généralement utile localisé :

sub my_ok {
    my $test = shift;
    local $Test::Builder::Level = $Test::Builder::Level + 1;
    $TB->ok($test);
}

Pour être courtois envers d'autres fonctions qui encapsulent les vôtres, vous voudrez généralement incrémenter $Level plutôt que de le définir à une constante.

use_numbers
$Test->use_numbers($on_or_off);

Indique si le test doit afficher des numéros. C'est-à-dire, si vrai :

ok 1
ok 2
ok 3

ou ceci si faux

ok
ok
ok

Le plus utile lorsque vous ne pouvez pas dépendre de l'ordre de sortie des tests, comme en cas de threads ou de fork.

Par défaut à activé.

no_diag
$Test->no_diag($no_diag);

Si réglé à vrai, aucun diagnostic ne sera imprimé. Cela inclut les appels à diag().

no_ending
$Test->no_ending($no_ending);

Normalement, Test::Builder effectue des diagnostics supplémentaires lorsque le test se termine. Il modifie également le code de sortie comme décrit ci-dessous.

Si ceci est vrai, rien de tout cela ne sera fait.

no_header
$Test->no_header($no_header);

Si réglé à vrai, aucun en-tête "1..N" ne sera imprimé.

Sortie

Contrôle où va la sortie du test.

Il est acceptable que votre test modifie où STDOUT et STDERR pointent, les paramètres de sortie par défaut de Test::Builder ne seront pas affectés.

diag
$Test->diag(@msgs);

Imprime les @msgs donnés. Comme "print", les arguments sont simplement joints.

Normalement, il utilise le handle failure_output(), mais s'il s'agit d'un test TODO, le handle todo_output() est utilisé.

La sortie sera indentée et marquée avec un # afin de ne pas interférer avec la sortie du test. Une nouvelle ligne sera ajoutée à la fin s'il n'y en a pas déjà une.

Nous encourageons l'utilisation de ceci plutôt que d'appeler print directement.

Retourne faux. Pourquoi ? Parce que diag() est souvent utilisé conjointement avec un test échoué ("ok() || diag()") il "transmet" l'échec.

return ok(...) || diag(...);
note
$Test->note(@msgs);

Comme diag(), mais il imprime sur le handle output() et ne sera donc normalement pas vu par l'utilisateur sauf en mode verbeux.

explain
my @dump = $Test->explain(@msgs);

Videra le contenu de toute référence dans un format lisible par l'homme. Pratique pour des choses comme...

is_deeply($have, $want) || diag explain $have;

ou

is_deeply($have, $want) || note explain $have;
output
failure_output
todo_output
my $filehandle = $Test->output;
$Test->output($filehandle);
$Test->output($filename);
$Test->output(\$scalar);

Ces méthodes contrôlent où Test::Builder imprimera sa sortie. Elles acceptent soit un $filehandle ouvert, un $filename à ouvrir et écrire, soit une référence à un $scalar à ajouter. Elles retourneront toujours un $filehandle.

output est l'endroit où va la sortie normale des tests "ok/not ok".

Par défaut à STDOUT.

failure_output est l'endroit où va la sortie de diagnostic en cas d'échec de test et les appels à diag(). Elle n'est normalement pas lue par Test::Harness et est plutôt affichée à l'utilisateur.

Par défaut à STDERR.

"todo_output" est utilisé à la place de failure_output() pour les diagnostics d'un test TODO échoué. Ceux-ci ne seront pas vus par l'utilisateur.

Par défaut à STDOUT.

reset_outputs
$tb->reset_outputs;

Réinitialise tous les handles de sortie à leurs valeurs par défaut.

carp
$tb->carp(@message);

Avertit avec @message, mais le message semblera provenir de l'endroit où la fonction de test d'origine a été appelée ("$tb->caller").

croak
$tb->croak(@message);

Mort avec @message, mais le message semblera provenir de l'endroit où la fonction de test d'origine a été appelée ("$tb->caller").

Statut et Infos du Test

no_log_results

Test::Builder

La classe Test::Builder vous donne les outils pour créer vos propres modules de test.

Elle est très utilisée par les modules de test populaires tels que Test::Simple, Test::More, Test::Exception et Test::Differences.

METHODS

new
my $Test = Test::Builder->new;

Crée un nouvel objet Test::Builder. Si vous utilisez les modules de test de haut niveau, vous n'aurez généralement pas besoin d'appeler cette méthode directement.

level
my $level = $Test->level;
$Test->level($num);

Gère le niveau de profondeur de la pile d'appels. La plupart des utilisateurs n'auront pas à modifier ceci. Les tests de haut niveau comme Test::More le font pour vous.

no_log_results
Test::Builder->new->no_log_results();

Désactive l'impression des résultats des tests sur la sortie standard. Vous pourriez vouloir utiliser cela si vous exécutez suffisamment de tests pour remplir toute la mémoire disponible.

Il n'y a aucun moyen de le réactiver.

current_test
my $curr_test = $Test->current_test;
$Test->current_test($num);

Récupère/définit le numéro du test courant. Vous ne devriez généralement pas avoir à le définir.

Si vous avancez, les détails des tests manquants sont remplis comme 'inconnu'. Si vous reculez, les détails des tests intermédiaires sont supprimés. Vous pouvez effacer l'historique si vous le souhaitez vraiment.

is_passing
my $ok = $builder->is_passing;

Indique si la suite de tests est actuellement réussie.

Plus formellement, elle sera fausse si quelque chose s'est produit qui rend impossible la réussite de la suite de tests. Vraie sinon.

Par exemple, si aucun test n'a été exécuté, is_passing() sera vrai car même si une suite sans tests est un échec, vous pouvez y ajouter un test réussi et commencer à réussir.

Ne réfléchissez pas trop.

summary
my @tests = $Test->summary;

Un résumé simple des tests jusqu'à présent. Vrai pour réussite, faux pour échec. Il s'agit d'une réussite/échec logique, donc les TODO sont considérés comme des réussites.

Bien sûr, le test n° 1 est $tests[0], etc.

details
my @tests = $Test->details;

Comme summary(), mais avec beaucoup plus de détails.

$tests[$test_num - 1] =
        { 'ok'       => le test est-il considéré comme une réussite ?
          actual_ok  => a-t-il littéralement dit 'ok' ou 'not ok' ?
          name       => nom du test (le cas échéant)
          type       => type de test (le cas échéant, voir ci-dessous).
          reason     => raison pour ce qui précède (le cas échéant)
        };

'ok' est vrai si Test::Harness considère le test comme une réussite.

'actual_ok' reflète si le test a littéralement imprimé 'ok' ou 'not ok'. Ceci est utile pour examiner le résultat des tests 'todo'.

'name' est le nom du test.

'type' indique s'il s'agissait d'un test spécial. Les tests normaux ont un type de ''. Le type peut être l'un des suivants :

skip        voir skip()
todo        voir todo()
todo_skip   voir todo_skip()
unknown     voir ci-dessous

Parfois, le compteur de tests de Test::Builder est incrémenté sans qu'il imprime de sortie de test, par exemple, lorsque current_test() est modifié. Dans ces cas, Test::Builder ne connaît pas le résultat du test, donc son type est 'unknown'. Les détails de ces tests sont remplis. Ils sont considérés comme ok, mais le nom et actual_ok sont laissés "undef".

Par exemple, "not ok 23 - hole count # TODO insufficient donuts" donnerait la structure suivante :

$tests[22] =    # 23 - 1, car les tableaux commencent à 0.
  { ok        => 1,   # logiquement, le test a réussi car il est todo
    actual_ok => 0,   # en termes absolus, il a échoué
    name      => 'hole count',
    type      => 'todo',
    reason    => 'insufficient donuts'
  };
todo
my $todo_reason = $Test->todo;
my $todo_reason = $Test->todo($pack);

Si les tests courants sont considérés comme "TODO", la raison, le cas échéant, sera retournée. Cette raison peut provenir d'une variable $TODO ou du dernier appel à todo_start().

Comme un test TODO n'a pas besoin de raison, cette fonction peut retourner une chaîne vide même à l'intérieur d'un bloc TODO. Utilisez "$Test->in_todo" pour déterminer si vous êtes actuellement à l'intérieur d'un bloc TODO.

todo() concerne la recherche du bon paquet pour rechercher $TODO. Il est assez bon pour deviner le bon paquet à examiner. Il recherche d'abord l'appelant en se basant sur "$Level + 1", car todo() est généralement appelé à l'intérieur d'une fonction de test. En dernier recours, il utilisera exported_to().

Parfois, il y a une confusion quant à l'endroit où todo() devrait rechercher la variable $TODO. Si vous voulez être sûr, dites-lui explicitement quel $pack utiliser.

find_TODO
my $todo_reason = $Test->find_TODO();
my $todo_reason = $Test->find_TODO($pack);

Comme todo(), mais ne retourne que la valeur de $TODO en ignorant todo_start().

Peut également être utilisé pour définir $TODO à une nouvelle valeur tout en retournant l'ancienne valeur :

my $old_reason = $Test->find_TODO($pack, 1, $new_reason);
in_todo
my $in_todo = $Test->in_todo;

Retourne vrai si le test est actuellement dans un bloc TODO.

todo_start
$Test->todo_start();
$Test->todo_start($message);

Cette méthode vous permet de déclarer tous les tests suivants comme tests TODO, jusqu'à ce que la méthode "todo_end" ait été appelée.

La syntaxe "TODO:" et $TODO est généralement assez bonne pour déterminer si nous sommes dans un test TODO ou non. Cependant, il est souvent impossible de le déterminer (par exemple, lorsque nous voulons utiliser $TODO mais que les tests sont exécutés dans d'autres paquets qui ne peuvent pas être déduits à l'avance).

Notez que vous pouvez utiliser cela pour imbriquer des tests "todo" :

$Test->todo_start('working on this');
# beaucoup de code
$Test->todo_start('working on that');
# plus de code
$Test->todo_end;
$Test->todo_end;

Ce n'est généralement pas recommandé, mais les grands systèmes de test ont souvent des besoins internes étranges.

Nous avons essayé de faire en sorte que cela fonctionne également avec la syntaxe TODO:, mais ce n'est pas garanti et son utilisation est également déconseillée :

TODO: {
    local $TODO = 'We have work to do!';
    $Test->todo_start('working on this');
    # beaucoup de code
    $Test->todo_start('working on that');
    # plus de code
    $Test->todo_end;
    $Test->todo_end;
}

Choisissez un style de "TODO" pour être sûr.

"todo_end"
$Test->todo_end;

Arrête d'exécuter les tests comme tests "TODO". Cette méthode est fatale si elle est appelée sans un appel préalable à la méthode "todo_start".

caller
my $package = $Test->caller;
my($pack, $file, $line) = $Test->caller;
my($pack, $file, $line) = $Test->caller($height);

Comme la fonction normale caller(), sauf qu'elle rapporte selon votre level().

$height sera ajouté au level().

Si caller() sort du haut de la pile, il rapporte le contexte le plus élevé.

CODES DE SORTIE

Si tous vos tests ont réussi, Test::Builder se terminera avec zéro (ce qui est normal). Si quelque chose a échoué, il se terminera avec le nombre d'échecs. Si vous exécutez moins (ou plus) de tests que prévu, les tests manquants (ou supplémentaires) seront considérés comme des échecs. Si aucun test n'a jamais été exécuté, Test::Builder émettra un avertissement et se terminera avec 255. Si le test est mort, même après avoir terminé avec succès tous ses tests, il sera toujours considéré comme un échec et se terminera avec 255.

Les codes de sortie sont donc...

0                   tous les tests réussis
255                 le test est mort ou tous les tests ont réussi mais le mauvais nombre de tests a été exécuté
tout autre nombre    combien ont échoué (y compris les tests manquants ou supplémentaires)

Si vous échouez à plus de 254 tests, cela sera rapporté comme 254.

THREADS

Dans perl 5.8.1 et versions ultérieures, Test::Builder est thread-safe. Le numéro de test est partagé par tous les threads. Cela signifie que si un thread définit le numéro de test en utilisant current_test(), tous les autres threads seront affectés.

Bien que les versions antérieures à 5.8.1 aient des threads, elles contiennent trop de bogues pour être prises en charge.

Test::Builder n'est thread-aware que si threads.pm est chargé *avant* Test::Builder.

Vous pouvez désactiver directement le support des threads avec l'une des options suivantes :

$ENV{T2_NO_IPC} = 1

ou

no Test2::IPC;

ou

Test2::API::test2_ipc_disable()

MÉMOIRE

Un hachage informatif, accessible via details(), est stocké pour chaque test que vous effectuez. Ainsi, l'utilisation de la mémoire augmente linéairement avec chaque exécution de test. Bien que cela ne pose pas de problème pour la plupart des suites de tests, cela peut devenir un problème si vous effectuez des tests combinatoires importants (centaines de milliers à millions) dans la même exécution.

Dans de tels cas, il est conseillé soit de diviser le fichier de test en fichiers plus petits, soit d'utiliser une approche inverse, en effectuant des comparaisons "normales" (code) et en déclenchant fail() si quelque chose ne va pas.

Les futures versions de Test::Builder auront un moyen de désactiver l'historique.

EXEMPLES

CPAN peut fournir les meilleurs exemples. Test::Simple, Test::More, Test::Exception et Test::Differences utilisent tous Test::Builder.
