Test::Trap::Builder(3) Documentation Perl fournie par l'utilisateur Test::Trap::Builder(3)

NOM

Test::Trap::Builder - Backend pour la construction de pièges de test

VERSION

Version 0.3.5

SYNOPSIS

package My::Test::Trap;
use Test::Trap::Builder;
my $B = Test::Trap::Builder->new;
$B->layer( $layer_name => \&layer_implementation );
$B->accessor( simple => [ $layer_name ] );
$B->multi_layer( $multi_name => @names );
$B->test( $test_name => 'trap, predicate, name', \&test_function );

DESCRIPTION

Test::Trap ne capture ni ne teste tout ce que vous pourriez vouloir capturer ou tester. Ainsi, Test::Trap::Builder fournit des méthodes pour écrire vos propres couches de capture, vos accesseurs et vos callbacks de test -- de préférence pour une utilisation avec vos propres modules (trappeurs).

Notez que les couches sont des méthodes avec des noms modifiés (les noms sont préfixés par "layer:"), et sont donc héritées comme toute autre méthode, tandis que les accesseurs sont des méthodes ordinaires. Pendant ce temps, les callbacks de test ne sont pas référencés dans la table des symboles par eux-mêmes, mais seulement en combinaison avec des accesseurs, toutes les méthodes de la forme ACCESSEUR_TEST.

EXPORTS

Les trappeurs ne devraient pas hériter de Test::Trap::Builder, mais peuvent importer quelques méthodes pratiques pour être utilisées dans la construction du piège. Ne les utilisez pas comme méthodes de Test::Trap::Builder -- elles sont destinées à être des méthodes d'objets piège. (Si vous héritez d'un autre trappeur, vous n'avez pas besoin, et ne devriez probablement pas, les importer vous-même -- vous devriez hériter de ces méthodes comme de toutes les autres.)

Les trappeurs peuvent importer n'importe lequel de ces méthodes, ou toutes par le biais de la balise ":methods".

Les couches devraient être implémentées comme des méthodes, et bien qu'elles n'aient pas besoin d'appeler elles-mêmes ces méthodes pratiques, cela rend probablement le code plus lisible que toute alternative. De même, les callbacks de test peuvent utiliser des méthodes pratiques pour un code plus lisible.

Bien sûr, certaines méthodes pratiques peuvent également être utiles dans des méthodes plus génériques manipulant des objets piège ou constructeur.

Prop [PACKAGE]

Une méthode retournant une référence vers une table de hachage, contenant les propriétés attachées au package (par défaut celui de l'appelant) pour l'objet piège (courant). Actuellement, Test::Trap::Builder définit les propriétés suivantes :

couches
Pendant que le piège se déclenche, la file des couches restantes. Habituellement définie par la méthode "trap" et consommée par la méthode "Next".
nettoyage
Pendant que le piège se déclenche, la file des actions de nettoyage restantes. Habituellement accumulée par la méthode "Teardown" et invoquée par la méthode "trap".
code
Le code utilisateur piégé. Habituellement défini par la méthode "trap" et invoqué par la méthode "Run".
exception
Une exception interne. Habituellement définie via la méthode "Exception" et examinée par la méthode "trap".
on_test_failure
Un callback invoqué par la méthode "TestFailure". Les couches en particulier pourraient vouloir le définir.
test_accessor
Le nom et (optionnellement) l'index de l'accesseur, dont le contenu est en cours de test. Mieux accédé via la méthode "TestAccessor", et habituellement défini par les méthodes "test" et "accessor", mais si vous écrivez vos propres tests ou accesseurs directement, vous pourriez avoir besoin de le définir. Peut-être.

Soyez correct : Traitez les propriétés attachées d'un autre module comme vous traiteriez les variables globales d'un autre module. Ne les utilisez pas sauf si documenté.

Exemple :

# dans une couche, définition du callback pour TestFailure :
$self->Prop('Test::Trap::Builder')->{on_test_failure} = \&mydiag;

DESTROY

Cela nettoie les propriétés attachées lorsque l'objet piège est détruit. N'essayez pas de créer un trappeur qui n'appelle pas cela ; il sera confus.

Si votre trappeur a besoin de son propre "DESTROY", assurez-vous qu'il appelle aussi celui-ci :

sub DESTROY {
  my $self = shift;
  # faites votre chose
  $self->Test::Trap::Builder::DESTROY;
  # et d'autres choses
}

Run

Une couche terminante devrait appeler cette méthode pour exécuter le code utilisateur. Ne devrait être appelée que dans un contexte dynamique dans lequel les couches sont appliquées.

Next

Chaque couche non terminante devrait appeler cette méthode (ou un équivalent) pour passer à la couche suivante. Ne devrait être appelée que dans un contexte dynamique dans lequel les couches sont appliquées. Notez que cette méthode n'a pas besoin de retourner, donc toute action de nettoyage devrait probablement être enregistrée avec la méthode Teardown (voir ci-dessous).

Teardown SUBS

Si votre couche souhaite nettoyer sa configuration, elle peut utiliser cette méthode pour enregistrer n'importe quel nombre d'actions de nettoyage, qui seront exécutées (dans l'ordre inverse d'enregistrement) une fois que le code utilisateur aura été exécuté. Ne devrait être appelée que dans un contexte dynamique dans lequel les couches sont appliquées.

TestAccessor

Retourne une chaîne de la forme "NOM(INDEX)", où NOM et INDEX sont le nom de l'accesseur et l'index (le cas échéant) en cours de test. Ne devrait être appelée que dans le contexte dynamique des callbacks de test.

Ceci est destiné au diagnostic :

diag( sprintf 'Expected %s in %s; got %s',
      $expected, $self->TestAccessor, dump($got),
    );

TestFailure

Exécute la propriété attachée "on_test_failure" (le cas échéant) sur l'objet piège. Si vous écrivez des tests non enregistrés, vous pourriez vouloir inclure (une variation de) cet appel :

$ok or $self->TestFailure;

Exception STRINGS

Les implémentations de couches peuvent rencontrer des situations exceptionnelles, dans lesquelles elles veulent que le piège entier échoue. Malheureusement, une autre couche peut capturer des exceptions ordinaires, vous avez donc besoin d'une sorte de magie pour lancer une exception non capturable. C'est une façon pratique.

Ne devrait être appelée que dans un contexte dynamique dans lequel les couches sont appliquées.

Note : La méthode Exception ne fonctionnera pas si elle est appelée en dehors du flux de contrôle régulier, comme dans une méthode DESTROY ou un gestionnaire de signal. Si quelque chose de ce genre se produit, CORE::exit sera appelé avec un code de sortie de 8.

Note : Les appels directs à la méthode Exception dans des fermetures peuvent créer des références circulaires et donc des fuites. Pour éviter cela, récupérez une "ExceptionFunction" et appelez-la depuis la fermeture à la place.

ExceptionFunction

Cette méthode retourne une fonction qui peut être appelée avec le même effet que l'appel de la méthode "Exception", permettant aux fermetures de lancer des exceptions sans créer de références circulaires en englobant l'objet piège lui-même.

Pour illustrer :

# ceci va créer une chaîne de référence circulaire :
# l'objet piège a une collection de propriétés a une fermeture de nettoyage a l'objet piège
$self->Teardown($_) for sub {
  do_stuff() or $self->Exception("Stuff didn't work.");
};
# ceci va briser la chaîne de référence circulaire :
# la fermeture de nettoyage n'a plus l'objet piège
$Exception = $self->ExceptionFunction;
$self->Teardown($_) for sub {
  do_things() or $Exception->("Things didn't work.");
};

MÉTHODES

new

Retourne un objet singleton. Ne vous attendez pas à ce que ce module fonctionne avec une instance d'objet différente de cette classe.

trap TRAPPER, GLOBREF, LAYERARRAYREF, CODE

Implémente un piège pour le module TRAPPER, appliquant les couches de LAYERARRAYREF, piégeant divers résultats du CODE utilisateur, et stockant l'objet piège dans la fente scalaire de GLOBREF.

Dans la plupart des cas, le trappeur devrait exporter commodément une fonction appelant cette méthode.

layer NAME, CODE

Enregistre une couche par NAME auprès du trappeur appelant. Lorsque la couche est appliquée, le CODE sera invoqué sur l'objet piège en cours de construction, sans arguments, et devrait appeler la méthode Next() ou Run() ou un équivalent.

output_layer NAME, GLOBREF

Enregistre (par NAME et auprès du trappeur appelant) une couche pour piéger la sortie sur le descripteur de fichier de GLOBREF, en utilisant également NAME comme nom d'attribut.

capture_strategy NAME, [CODE]

Lorsqu'elle est appelée avec deux arguments, enregistre (par NAME et globalement) une stratégie pour les couches de piège de sortie. Lorsqu'elle est appelée avec un seul argument, recherche et retourne la stratégie enregistrée par NAME (ou undef).

Lorsqu'une couche utilisant cette stratégie est appliquée, le CODE sera appelé sur l'objet piège, avec le nom de la couche et le fileno et le globref du descripteur de sortie comme arguments.

output_layer_backend SPEC

Alias de compatibilité ascendante de ce qui précède.

first_capture_strategy SPEC

Lorsque SPEC est vide, retourne simplement.

Lorsque SPEC est une chaîne de noms séparés par des virgules ou des points-virgules, itère sur les noms, retournant la première stratégie qu'elle trouve. Lance une exception si aucune stratégie n'est trouvée par l'un de ces noms.

first_output_layer_backend SPEC

Alias de compatibilité ascendante de ce qui précède.

multi_layer NAME, LAYERS

Enregistre (par NAME) une couche qui empile simplement un certain nombre d'autres LAYERS sur la pile des couches. Si l'un des LAYERS n'est ni une méthode anonyme ni le nom d'une couche enregistrée auprès de l'appelant ou d'un trappeur dont il hérite, une exception est levée.

layer_implementation TRAPPER, LAYERS

Retourne les sous-routines qui implémentent les LAYERS demandés. Si l'un des LAYERS n'est ni une méthode anonyme ni le nom d'une couche enregistrée auprès du TRAPPER ou dont il hérite, une exception est levée.

accessor NAMED_ARGS

Génère et enregistre un nombre quelconque d'accesseurs selon les NAMED_ARGS, et génère également les méthodes de test appropriées pour ces accesseurs (voir ci-dessous).

Les arguments nommés suivants sont reconnus :

is_leaveby
Si vrai, les méthodes de test généreront de meilleurs diagnostics si le piège n'a pas été quitté comme spécifié. De plus, une méthode de test spéciale did_ACCESSOR sera générée (sauf si elle est déjà présente), passant simplement tant que le piège a été quitté comme spécifié.
is_array
Si vrai, les accesseurs simples seront intelligents quant au contexte et aux arguments, retournant un arrayref sans argument (dans n'importe quel contexte), une tranche de tableau en contexte de liste (avec n'importe quel nombre d'arguments), et l'élément indexé par le premier argument sinon.
simple
Doit être une référence à un tableau de noms d'accesseurs. Pour chaque nom, un accesseur (en supposant un objet piège basé sur un hash avec les noms d'accesseurs comme clés), sera généré et enregistré.
flexible
Doit être une référence à un hash. Pour chaque paire, un nom et une implémentation, un accesseur est généré et enregistré.

test NAME, ARGSPEC, CODE

Enregistre une fonction de rappel de test par NAME et auprès du trappeur appelant.

Les trappeurs héritent des fonctions de rappel de test comme des méthodes (bien qu'elles ne soient pas implémentées comme telles ; ne vous attendez pas à les trouver dans la table des symboles).

Les méthodes de test de la forme ACCESSOR_TEST seront rendues disponibles (directement ou par héritage) à chaque trappeur qui enregistre ou hérite à la fois de l'accesseur nommé ACCESSOR et du test nommé TEST.

(Plus en détail, la méthode sera générée dans chaque trappeur qui (1) enregistre à la fois le test et l'accesseur, ou (2) enregistre l'un et hérite de l'autre.)

Lorsque la méthode de test est appelée, toute condition implicite de 'leaveby' sera testée en premier, et si elle réussit (ou s'il n'y en avait pas), le CODE est appelé avec des arguments selon les mots trouvés dans la chaîne ARGSPEC :

trap
L'objet piège.
entirety
La valeur de retour de ACCESSOR lorsqu'elle est appelée sans argument.
element
La valeur de retour de ACCESSOR lorsqu'elle est appelée avec un index, si applicable (c'est-à-dire pour les accesseurs de tableau). L'index n'est pas applicable aux accesseurs scalaires, donc ceux-ci sont toujours appelés sans index.

L'index, le cas échéant, sera pris parmi les arguments de la méthode de test.

predicate
Ce que la valeur de retour de ACCESSOR doit être testée (provenant des arguments de la méthode de test). (Il peut y avoir un nombre fixe de prédicats.)
name
Le nom du test (provenant des arguments de la méthode de test).

EXEMPLE

Un exemple complet, implémentant une couche timeout (dépendante de la présence de Time::HiRes::ualarm), une couche simpletee (imprimant le stdout/stderr piégé dans les descripteurs de fichiers originaux après que le piège a été déclenché), et un modèle de méthode de test cmp_ok :

package My::Test::Trap;
use base 'Test::Trap'; # à titre d'exemple
use Test::Trap::Builder;
my $B = Test::Trap::Builder->new;
# exemple (couche:timeout):
use Time::HiRes qw/ualarm/;
$B->layer( timeout => $_ ) for sub {
  my $self = shift;
  eval {
    local $SIG{ALRM} = sub {
      $self->{timeout} = 1; # simple vérité
      $SIG{ALRM} = sub {die};
      die;
    };
    ualarm 1000, 1; # une seconde maximum, puis mourir de manière répétée !
    $self->Next;
  };
  alarm 0;
  if ($self->{timeout}) {
    $self->{leaveby} = 'timeout';
    delete $self->{$_} for qw/ die exit return /;
  }
};
$B->accessor( is_leaveby => 1,
              simple => ['timeout'],
            );
# exemple (couche:simpletee):
$B->layer( simpletee => $_ ) for sub {
  my $self = shift;
  for (qw/ stdout stderr /) {
    exists $self->{$_} or $self->Exception("Trop tard pour 'tee' $_");
  }
  $self->Teardown($_) for sub {
    print STDOUT $self->{stdout} if exists $self->{stdout};
    print STDERR $self->{stderr} if exists $self->{stderr};
  };
  $self->Next;
};
# pas d'accesseur pour cette couche
$B->multi_layer( flow => qw/ raw die exit timeout / );
$B->multi_layer( default => qw/ flow stdout stderr warn simpletee / );
$B->test_method( cmp_ok => 1, 2, \&Test::More::cmp_ok );

CAVEATS

L'interface de ce module est susceptible de rester quelque peu fluctuante pendant encore un certain temps.

Les différentes stratégies pour les couches de piège de sortie ont leurs propres caveats ; voir Test::Trap::Builder::Tempfile, Test::Trap::Builder::PerlIO, Test::Trap::Builder::SystemSafe.

L'héritage multiple n'est pas (encore ?) entièrement pris en charge. Si un parent a enregistré une fonction de rappel de test "X" et qu'un autre a enregistré un accesseur "Y", la méthode de test "Y_X" ne sera pas générée.

Threads ? Aucune idée. Cela pourrait même fonctionner correctement.
