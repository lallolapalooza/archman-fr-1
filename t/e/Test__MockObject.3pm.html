Test::MockObject(3) Documentation contribuée par Perl Test::MockObject(3)

NOM

Test::MockObject - Extension Perl pour émuler des interfaces difficiles

SYNTAXE

use Test::MockObject;
my $mock = Test::MockObject->new();
$mock->set_true( 'somemethod' );
ok( $mock->somemethod() );
$mock->set_true( 'veritas')
     ->set_false( 'ficta' )
     ->set_series( 'amicae', 'Sunny', 'Kylie', 'Bella' );

DESCRIPTION

Il s'agit d'un programme simple qui n'utilise pas d'autres modules, et ceux-ci sont facilement testables. Plus souvent, tester un programme complet implique de falsifier les entrées d'un autre module, en essayant d'obtenir la bonne sortie de quelque chose que vous ne testez pas complètement.

Les tests sont beaucoup plus faciles lorsque vous pouvez contrôler l'environnement complet. Avec Test::MockObject, vous pouvez vous en approcher beaucoup plus.

Test::MockObject permet de créer des objets qui se conforment à des interfaces spécifiques avec très peu de code. Vous n'avez pas à réimplémenter le comportement, seulement les entrées et les sorties.

ATTENTION IMPORTANTES

Avant d'utiliser pleinement vos pouvoirs de test, considérez trois avertissements :

  • Il est possible d'écrire des tests unitaires très détaillés qui réussissent même lorsque vos tests d'intégration peuvent échouer. Tester les composants séparément n'excuse pas le fait de ne pas avoir à tout tester ensemble.
  • Si vous avez seulement besoin de mocker quelques éléments d'un module existant, considérez Test::MockObject::Extends.
  • Si le code à tester génère des erreurs inhabituelles concernant les types, utilisez l'option "-debug" lorsque vous utilisez "Test::MockObject" ou "Test::MockObject::Extends". Cela charge à la fois "UNIVERSAL::isa" et "UNIVERSAL::can" pour un débogage supplémentaire sur l'utilisation incorrecte des deux méthodes du package UNIVERSAL. (Ce comportement était auparavant activé par défaut, mais cela était probablement un obstacle pour CPAN.)

EXPORT

Aucun.

MÉTHODES

La chose la plus importante qu'un objet mock puisse faire est de se conformer suffisamment à une interface. Par exemple, si vous testez quelque chose qui dépend de CGI.pm, il peut être plus facile de créer un objet mock qui renvoie des résultats contrôlés à certains moments que de falsifier l'entrée de la chaîne de requête.

Les bases

•
"new" - Crée un nouvel objet mock. Par défaut, il s'agit d'une référence de hachage. Vous pouvez passer une référence pour la « bloquer ».

my $mock_array  = Test::MockObject->new( [] );
my $mock_scalar = Test::MockObject->new( \( my $scalar ) );
my $mock_code   = Test::MockObject->new( sub {} );
my $mock_glob   = Test::MockObject->new( \*GLOB );

Mise en place des mocks

Votre objet mock est presque inutile s'il ne sait pas ce qu'il doit mocker. Cela se fait en installant des méthodes. Vous contrôlez la sortie de ces méthodes mockées. En outre, toute méthode mockée est enregistrée. Vous pouvez savoir non seulement ce qui a été appelé, mais aussi quels arguments ont été passés. Veuillez noter que vous ne pouvez pas enregistrer les appels à des méthodes non mockées. Celles-ci sont autorisées, bien que Test::MockObject les capture. Ceci est considéré comme une fonctionnalité, bien qu'elle puisse être désactivée à l'avenir.

Comme mentionné dans l'exemple ci-dessus, il est possible de chaîner ces appels. Grâces à Piers Cawley (CPAN RT #1249), cette fonctionnalité a été introduite dans la version 0.09. Le code de test est plus court !

  • "mock(name, coderef [, name2, coderef2, ...])" - Ajoute un ou plusieurs coderefs à un objet. Cela permet au code d'appeler les méthodes nommées sur l'objet. Par exemple, ce code :

    my $mock = Test::MockObject->new();
$mock->mock( 'fluorinate',
    sub { 'impurifying precious bodily fluids' } );
print $mock->fluorinate;

    imprimera un message d'avertissement utile. Veuillez noter que les méthodes sont ajoutées à un objet à la fois et non à la classe. (Il y a une petite similitude avec le langage Self ou le module Class::Prototyped.)

    Cette méthode constitue la base de la plupart des avantages de Test::MockObject.

    Note : cette méthode s'appelait auparavant add(). En raison de son ambiguïté, elle a maintenant un nom différent. Pour la compatibilité avec les versions antérieures, add() est disponible, bien que la version 0.07 l'ait déprécié. Bien qu'il essaie de faire ce que vous voulez, je fais peu de garanties.

  • "fake_module(module_name), [ subname =" coderef, ... ]

    Note : voir Test::MockModule pour une alternative (et meilleure) à ceci.

    Ment à Perl qu'il a déjà chargé un module du nom spécifié. C'est utile lorsque vous voulez mocker un module réel et éviter que le module réel n'interfère avec le fakery comique. Si vous mockez Regexp::English, par exemple :

    $mock->fake_module( 'Regexp::English' );

    Il s'agit à la fois d'une méthode de classe et d'une méthode d'objet. Faites attention, cela doit se produire avant que le module réel ne soit chargé. Soit enveloppez-le dans un bloc BEGIN avant un use ou require, soit placez-le avant un appel use_ok() ou require_ok().

    Vous pouvez également ajouter des sous-routines à ce module mocké en les passant sous forme de paires nom => coderef à fake_module(). C'est utile si vous voulez tester une importation :

    my $import;
$mock->fake_module(
    'Regexp::English',
    import => sub { $import = caller }
);
use_ok( 'Regexp::Esperanto' );
is( $import, 'Regexp::Esperanto',
    'Regexp::Esperanto devrait utiliser() Regexp::English' );

    Si vous utilisez fake_module() pour mocker un module qui existe déjà en mémoire — un module que vous avez déjà chargé, mais sans passer de sous-routines à mocker — cette méthode lèvera une exception. Cela se produit parce que si vous appelez le constructeur plus tard, vous n'obtiendrez probablement pas un objet mock et vous seriez confus.

  • "fake_new(module_name)"

    Note : voir Test::MockObject::Extends pour une meilleure alternative à cette méthode.

    Fournit un constructeur factice pour le module donné qui renvoie l'objet mock actuel. Utilisé en conjonction avec fake_module(), vous pouvez forcer le module testé à fonctionner avec l'objet mock.

    $mock->fake_module( 'CGI' );
$mock->fake_new( 'CGI' );
use_ok( 'Some::Module' );
my $s = Some::Module->new();
is( $s->{_cgi}, $mock,
    'new() devrait créer et stocker un nouvel objet CGI' );
  • "set_always(name, value)"

    Ajoute une méthode du nom spécifié qui renvoie toujours la valeur spécifiée.

  • "set_true(name_1, name_2, ... name_n)"

    Ajoute une méthode du nom spécifié qui renvoie toujours une valeur vraie. Cela peut prendre une liste de noms.

  • "set_false(name_1, name_2, ... name_n)"

    Ajoute une méthode du nom spécifié qui renvoie toujours une valeur fausse. (Puisqu'elle installe une sous-routine vide, la valeur sera fausse dans les contextes scalaire et liste.) Cela peut prendre une liste de noms.

  • can( $nom_methode )

    Retourne une référence à une sous-routine si cet objet mocké peut gérer la méthode nommée, sinon retourne false.

  • isa( $nom_classe )

    Retourne vrai si l'objet invoqué mocke une classe spécifique. Vous devez avoir utilisé set_isa() auparavant.

  • called(nom)

    Vérifie si quelque chose a invoqué une méthode nommée sur l'objet. Retourne une valeur booléenne. L'implémentation actuelle n'est pas particulièrement évolutive, utilisez donc ceci avec précaution si vous avez besoin de rechercher des milliers d'appels.

  • clear()

    Efface l'enregistrement interne de tous les appels aux méthodes de l'objet. Il est utile de le faire souvent. Notez que cela n'affecte pas les méthodes mockées, seulement toutes les méthodes appelées à ce moment-là.

    Il est utile de clear() les méthodes entre des séries de tests. Cela permet de faciliter l'appel à next_method() sans avoir à sauter par-dessus les appels des derniers testeurs.

  • "next_call([ position ])"

    Retourne le nom et la liste des arguments de la prochaine méthode mockée dans la liste d'appels, en contexte de liste. En contexte scalaire, retourne seulement le nom de la méthode. Il y a deux choses importantes à propos de cette méthode. Premièrement, elle commence au début de la liste d'appels. Si votre code s'exécute comme ceci :

    $mock->set_true( 'foo' );
$mock->set_true( 'bar' );
$mock->set_true( 'baz' );
$mock->foo();
$mock->bar( 3, 4 );
$mock->foo( 1, 2 );

    Alors, vous pourriez voir une sortie comme :

    my ($name, $args) = $mock->next_call();
print "$name (@$args)";
# imprime 'foo'
$name = $mock->next_call();
print $name;
# imprime 'bar'
($name, $args) = $mock->next_call();
print "$name (@$args)";
# imprime 'foo 1 2'

    Si vous passez un nombre optionnel comme argument position, la méthode saute cette quantité d'appels, retournant les données de la dernière étape sautée. 

    $mock->foo();
$mock->bar();
$mock->baz();
$name = $mock->next_call();
print $name;
# imprime 'foo'
$name = $mock->next_call( 2 );
print $name
# imprime 'baz'

    Lorsqu'elle atteint la fin de la liste, elle retourne undef. C'est probablement la méthode la plus pratique du module, mais pour des raisons de complétude et de compatibilité (il faut un peu de temps pour atteindre l'état de paresse ultime !), il existe plusieurs autres méthodes.

  • call_pos(position)

    Retourne le nom de la méthode appelée à la position spécifiée de l'objet. Utile si vous avez besoin de tester l'ordre des appels. Par exemple :

    Some::Function( $mock );
is( $mock->call_pos(1),  'setup',
    'Function() should first call setup()' );
is( $mock->call_pos(-1), 'end',
    '... and last call end()' );

    Les positions peuvent être positives ou négatives. Veuillez noter que la première position est en fait 1. (Cela pourrait changer à l'avenir. Je reconsidérerais cela, mais je suis ouvert.)

  • call_args(position)

    Retourne une liste des arguments passés à la méthode appelée à la position appropriée. En suivant le test précédent, vous pourriez dire :

    is( ($mock->call_args(1))[0], $mock,
    '... passing the object to setup()' );
is( scalar $mock->call_args(-1), 0,
    '... and no args to end()' );
  • "call_args_pos(appel position, argument position)"

    Retourne l'argument à la position spécifiée pour la méthode appelée à la position spécifiée. On pourrait réécrire le premier test de l'exemple final comme :

    is( $mock->call_args_pos(1, 1), $mock,
    '... passing the object to setup()');
  • "call_args_string(position , [ séparateur ])"

    Retourne une version string des arguments à la position spécifiée. Si aucun séparateur n'est spécifié, ils ne seront pas séparés. Ceci peut être utilisé comme :

    is( $mock->call_args_string(1), "$mock initialize",
    '... passing object, initialize as arguments' );
  • "called_ok(nom méthode, [ nom test ])"

    Teste si une méthode du nom spécifié a été appelée sur l'objet. Ceci et les méthodes suivantes utilisent Test::Builder, donc elles s'intègrent bien avec une suite de tests construite sur Test::Simple, Test::More ou toute autre chose compatible :

    $mock->foo();
$mock->called_ok( 'foo' );

    Un nom de test par défaut est fourni.

  • "called_pos_ok(position , nom méthode, [ nom test ])"

    Teste si la méthode nommée a été appelée à la position spécifiée. Un nom de test par défaut est fourni.

  • "called_args_pos_is(position méthode, position argument, attendu, [ nom test ])"

    Teste si l'argument à la position appropriée de la méthode à la position spécifiée est égal à une valeur spécifiée. Un nom de test par défaut est fourni, bien qu'il soit génériquement peu descriptif.

  • "called_args_string_is(position méthode, séparateur, attendu, [ nom test ])"

    Concatène tous les arguments d'une méthode à la position appropriée et les compare à une chaîne spécifiée. Un nom de test génériquement faible est fourni par défaut. Vous pouvez faire beaucoup mieux.

  • check_class_loaded( $nom_classe )

    Tente de déterminer si vous avez une classe du nom donné chargée et compilée. Retourne vrai ou faux.

Journalisation

Test::MockObject journalise par défaut tous les appels aux méthodes mockées. Parfois, vous ne voulez pas le faire. Pour empêcher la journalisation de tous les appels à une méthode donnée, préfixez le nom de la méthode avec "-" lorsque vous la mockez.

C'est-à-dire :

$mock->set_true( '-foo', 'bar' );

définit le mock à la fois pour foo() et bar(), provoquant le retour de vrai pour les deux. Cependant, l'objet ne journalise que les appels à bar(), pas à foo(). Pour journaliser à nouveau foo(), mockez-le simplement sans le préfixe "-" :

$mock->set_true( 'foo' );

Le $mock journalisera tous les appels suivants à foo() à nouveau.

Héritage

Il existe deux méthodes pour l'héritage :

  • "dispatch_mocked_method( $nom_methode, @_ )"

    Cette méthode détermine comment appeler une méthode (nommée $nom_methode) non disponible dans cette classe. Elle contrôle également la journalisation. Vous pourriez la trouver utile ou non, mais je l'utilise pour Test::MockObject::Extends.

  • "log_call( $nom_methode, @_ )"

    Cette méthode enregistre l'appel de la méthode nommée et ses arguments.
