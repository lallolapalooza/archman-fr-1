NOM

Test::Spec::Mocks - Plugin de simulation d'objets pour Test::Spec

SYNTAXE

use Test::Spec;
use base qw(Test::Spec);
use My::RSS::Tool;    # c'est ce que nous testons
use LWP::UserAgent;
describe "RSS tool" => sub {
  it "should fetch and parse an RSS feed" => sub {
    my $xml = load_rss_fixture();
    LWP::Simple->expects('get')->returns($xml);
    # appelle LWP::Simple::get, mais retourne notre $xml à la place
    my @stories = My::RSS::Tool->run;
    is_deeply(\@stories, load_stories_fixture());
  };
};

DESCRIPTION

Test::Spec::Mocks est un plugin pour Test::Spec qui fournit des capacités de mocking et de stubbing d'objets, de méthodes individuelles et de sous-routines simples sur des instances d'objets et des classes. Ce module est inspiré et emprunte largement à Mocha, une bibliothèque pour le langage de programmation Ruby. Mocha elle-même est inspirée de JMock.

Les objets mocks permettent de simuler le comportement d'objets réels, tout en fournissant des résultats cohérents et répétables. Ceci est très utile lorsque vous devez tester une fonction dont les résultats dépendent d'un facteur externe normalement incontrôlable (comme l'heure de la journée). Les mocks permettent également de tester votre code de manière isolée, un principe du test unitaire.

Il existe de nombreuses autres raisons pour lesquelles les objets mocks peuvent être utiles. Consultez l'article sur les objets mocks de http://en.wikipedia.org/wiki/Mock_object sur Wikipedia pour de nombreux autres exemples et une couverture plus approfondie de la philosophie derrière le mocking d'objets.

Écosystème

Test::Spec::Mocks ne peut actuellement être utilisé qu'à l'intérieur de tests construits avec le framework BDD Test::Spec.

Terminologie

Familiarisez-vous avec ces termes:

  • Objet stub

    Un objet stub est un objet créé spécifiquement pour retourner des réponses préenregistrées pour un ensemble spécifique de méthodes. Ceux-ci sont créés avec la fonction stub.

  • Objet mock

    Les objets mocks sont similaires aux objets stubs, mais sont programmés avec des réponses préparées et des attentes quant à la manière dont ils seront appelés. Si les attentes ne sont pas satisfaites, ils lèvent une exception pour indiquer que le test a échoué. Les objets mocks sont créés avec la fonction mock.

  • Méthode stubbée

    Les méthodes stubbées remplacent temporairement des méthodes existantes sur une classe ou une instance d'objet. Ceci est utile lorsque vous souhaitez uniquement remplacer un sous-ensemble du comportement d'un objet ou d'une classe. Par exemple, vous pourriez vouloir remplacer la méthode "do" d'un descripteur de fichier DBI afin qu'elle ne modifie pas votre base de données, tout en ayant besoin que le descripteur de fichier réponde normalement à la méthode "quote". Vous stubberez les méthodes en utilisant la méthode stubs.

  • Méthode mockée

    Si vous avez lu jusqu'ici, cela ne vous surprendra pas. Les méthodes mockées sont comme les méthodes stubbées, mais elles s'accompagnent d'attentes qui lèveront une exception si elles ne sont pas satisfaites. Par exemple, vous pouvez mocker une méthode "save" sur un objet pour vous assurer qu'elle est appelée par le code que vous testez, tout en empêchant les données d'être réellement enregistrées sur disque lors de votre test. Utilisez la méthode expects pour créer des méthodes mockées.

  • "stub", "mock"

    Selon le contexte, ces termes peuvent faire référence respectivement aux objets et méthodes stubbées, ou aux objets et méthodes mockées.

Utilisation d'objets stub (stubs anonymes)

Parfois, le code que vous testez nécessite que vous lui passiez un objet qui respecte une interface spécifique. Par exemple, vous testez une bibliothèque de création d'invites de console, mais vous ne voulez pas qu'une personne réelle se tienne prête à taper des réponses dans la console. La bibliothèque nécessite un objet qui retourne une chaîne lorsque la méthode "read_line" est appelée.

Vous pourriez créer une classe spécifiquement pour retourner des entrées de console de test. Mais pourquoi faire cela ? Vous pouvez créer un objet stub en une seule ligne :

describe "An Asker" => sub {
  my $asker = Asker->new;
  it "returns true when a yes_or_no question is answered 'yes'" => sub {
    my $console_stub = stub(read_line => "yes");
    # $console_stub->read_line retourne "yes"
    ok( $asker->yes_or_no($console_stub, "Am I awesome?") );
  };
  it "returns false when a yes_or_no question is answered 'no'" => sub {
    my $console_stub = stub(read_line => "no");
    ok( ! $asker->yes_or_no($console_stub, "Am I second best?") );
  };
};

Les stubs peuvent également accepter des références de sous-routines. C'est utile lorsque le comportement que vous devez imiter est un peu plus complexe.

it "keeps asking until it gets an answer" => sub {
  my @answers = (undef, "yes");
  my $console_stub = stub(read_line => sub { shift @answers });
  # lorsque console_stub est appelé la première fois, il retourne undef
  # la deuxième fois, il retourne "yes"
  ok( $asker->yes_or_no($console_stub, "Do I smell nice?") );
};

Utilisation d'objets mock

Si vous souhaitez aller plus loin dans vos tests, vous pouvez utiliser des objets mocks au lieu d'objets stubs. Les mocks garantissent que les méthodes que vous attendez d'être appelées le sont effectivement. Si ce n'est pas le cas, le mock lèvera une exception qui entraînera l'échec de votre test.

Dans cet exemple, nous vérifions que "read_line" est appelée une seule fois (par défaut pour les mocks).

it "returns true when a yes_or_no question is answered 'yes'" => sub {
  my $console_mock = mock();
  $console_mock->expects('read_line')
               ->returns("yes");
  # $console_mock->read_line retourne "yes"
  ok( $asker->yes_or_no($console_mock, "Am I awesome?") );
};

Si la méthode "yes_or_no" de Asker n'appelle pas "read_line" sur notre mock exactement une fois, le test échouera avec un message tel que :

expected read_line to be called exactly 1 time, but it was called 0 times

Vous pouvez spécifier combien de fois votre mock doit être appelé avec "exactly" :

it "keeps asking until it gets an answer" => sub {
  my @answers = (undef, "yes");
  my $console_mock = mock();
  $console_mock->expects('read_line')
               ->returns(sub { shift @answers })
               ->exactly(2);
  # lorsque console_mock est appelé la première fois, il retourne undef
  # la deuxième fois, il retourne "yes"
  ok( $asker->yes_or_no($console_mock, "Do I smell nice?") );
};

Si vous souhaitez quelque chose de plus flexible que "exactly", vous pouvez choisir parmi "at_least", "at_most", "any_number" et d'autres. Voir "MÉTHODES D'AJUSTEMENT D'ATTENTE".

Stubbing de méthodes

Parfois, vous souhaitez remplacer seulement un petit sous-ensemble du comportement d'un objet.

describe "The old audit system" => sub {
  my $dbh;
  before sub { $dbh = SomeExternalClass->get_dbh };
  it "executes the expected sql" => sub {
    my $sql;
    $dbh->stubs(do => sub { $sql = shift; return 1 });
    # $dbh->do("foo") définit maintenant $sql à "foo"
    # $dbh->quote fait toujours ce qu'il faisait normalement
    audit_event($dbh, "server crash, oh noes!!");
    like( $sql, qr/insert into audit_event.*'server crash, oh noes!!!'/ );
  };
};

Vous pouvez également stubber des méthodes de classe :

# 1977-05-26T14:11:55
my $event_datetime = DateTime->new(from_epoch => 0xdeafcab);
it "should tag each audit event with the current time" => sub {
  DateTime->stubs('now' => sub { $event_datetime });
  is( audit_timestamp(), '19770526.141155' );
};

CONSTRUCTEURS

stub()
stub($nom_methode => $resultat, ...)
stub($nom_methode => sub { $resultat }, ...)
stub({ $nom_methode => $resultat, ... })
Retourne un nouvel objet stub anonyme. Prend une liste de paires $nom_methode/$resultat ou une référence vers un hachage contenant les mêmes. Chaque $nom_methode listé est stubbé pour retourner la valeur associée ($resultat); ou si la valeur est une référence de sous-routine, elle est stubbée en place (la sous-routine devient la méthode).

Exemples:

# Un objet vide sans méthodes.
# Donne une réponse vraie à ref() et blessed().
my $vide = stub();
# Réponses statiques à width() et height():
my $rect = stub(width => 5, height => 5);
# Réponse dynamique à area():
my $rayon = 1.0;
my $cercle_stub = stub(area => sub { PI * $rayon * $rayon });

Vous pouvez aussi stubber plus de méthodes, comme avec tout autre objet:

my $rect = stub(width => 5, height => 5);
$rect->stubs(area => sub { my $self = shift; $self->width * $self->height });
$truc->stubs($nom_methode)
$truc->stubs($nom_methode => $resultat)
$truc->stubs($nom_methode => sub { $resultat })
$truc->stubs({ $nom_methode => $resultat })
Stubbe une ou plusieurs méthodes sur une classe ou une instance existante, $truc.

Si un seul argument (non haché) est passé, il est interprété comme un nom de méthode. La valeur de retour de la méthode stubbée sera "undef".

Sinon, les arguments sont une liste de paires $nom_methode et $resultat, soit sous forme de liste plate, soit sous forme de référence de hachage. Chaque méthode est installée sur $truc et retourne le résultat spécifié. Si le résultat est une référence de sous-routine, elle sera appelée à chaque invocation de la méthode.

mock()
Retourne un nouvel objet mock vide et anonyme, adapté pour mocker des méthodes avec expects(). 
my $rect = mock();
$rect->expects('area')->returns(100);
$truc->expects($methode)
Installe une méthode mock nommée $methode sur la classe ou l'objet $truc et retourne un objet Test::Spec::Mocks::Expectation, que vous pouvez utiliser pour définir la valeur de retour avec returns() et d'autres attentes. Par défaut, la méthode est attendue à être appelée at_least_once.

Si l'attente n'est pas satisfaite avant que l'exemple englobant ne soit terminé, la méthode mockée lèvera une exception qui ressemblera à quelque chose comme:

expected foo to be called exactly 1 time, but it was called 0 times

METHODES DE REGULATION DES ATTENTES

Ce sont des méthodes de la classe Test::Spec::Mocks::Expectation, que vous obtiendrez en appelant expects() sur une classe ou une instance d'objet.

returns( $resultat )
returns( @resultats )
returns( \&callback )
Configure la méthode mockée pour retourner le résultat spécifié lors de son appel. Si une référence de sous-routine est passée, la sous-routine sera exécutée lorsque la méthode est appelée, et le résultat est la valeur de retour. 
$rect->expects('height')->returns(5);
# $rect->height ==> 5
@points = ( [0,0], [1,0], [1,1], [1,0] );
$rect->expects('points')->returns(@points);
# (@p = $rect->points) ==> ( [0,0], [1,0], [1,1], [1,0] )
# ($p = $rect->points) ==> 4
@points = ( [0,0], [1,0], [1,1], [1,0] );
$rect->expects('next_point')->returns(sub { shift @points });
# $rect->next_point ==> [0,0]
# $rect->next_point ==> [1,0]
# ...
exactly($N)
Configure la méthode mockée de telle sorte qu'elle doit être appelée exactement $N fois.
never
Configure la méthode mockée de telle sorte qu'elle ne doit jamais être appelée.
once
Configure la méthode mockée de telle sorte qu'elle doit être appelée exactement une fois.
at_least($N)
Configure la méthode mockée de telle sorte qu'elle doit être appelée au moins $N fois.
at_least_once
Configure la méthode mockée de telle sorte qu'elle doit être appelée au moins 1 fois. C'est juste du sucre syntaxique pour at_least(1).
at_most($N)
Configure la méthode mockée de telle sorte qu'elle ne doit pas être appelée plus de $N fois.
at_most_once
Configure la méthode mockée de telle sorte qu'elle doit être appelée zéro ou 1 fois.
maybe
Un alias pour "at_most_once".
any_number
Configure la méthode mockée de telle sorte qu'elle peut être appelée zéro ou plusieurs fois.
times
Un no-op de sucre syntaxique: 
$io->expects('print')->exactly(3)->times;

Cette méthode est en alpha et pourrait changer dans une future version.

with(@arguments) / with_eq(@arguments)
Configure la méthode mockée de telle sorte qu'elle doit être appelée avec les arguments spécifiés. Les arguments seront comparés en utilisant l'opérateur "eq", donc cela fonctionne pour la plupart des valeurs scalaires sans problème. Si vous voulez vérifier des objets ici, ils doivent être la même instance exacte ou vous devez surcharger l'opérateur "eq" pour fournir le comportement désiré.
with_deep(@arguments)
Similaire à "with_eq", sauf que les arguments sont comparés en utilisant Test::Deep : les scalaires sont comparés par valeur, les tableaux et les hachages doivent avoir les mêmes éléments et les références doivent être bénies dans la même classe. 
$cache->expects('set')
      ->with_deep($customer_id, { name => $customer_name });

Utilisez les fonctions de comparaison de Test::Deep pour plus de flexibilité:

use Test::Deep::NoTest ();
$s3->expects('put')
   ->with_deep('test-bucket', 'my-doc', Test::Deep::ignore());
raises($exception)
Configure la méthode mockée de telle sorte qu'elle lève $exception lors de son appel.

AUTRES METHODES D'ATTENTE

verify
Permet de vérifier manuellement que l'attente a été satisfaite. Si l'attente n'a pas été satisfaite, la méthode meurt avec un message d'erreur contenant les détails de l'échec. Retourne vrai sinon.
problems
Si l'attente n'a pas été satisfaite, retourne une liste de chaînes décrivant les problèmes. Sinon, retourne une liste vide.

PROBLEMES CONNUS

Fuites de mémoire
En raison de la manière dont les objets mockés ("stubs", "stub", "expects", et "mock") sont intégrés dans le runtime Test::Spec, ils fuiront de la mémoire. Il n'est pas recommandé d'utiliser les mocks de Test::Spec dans un programme de longue durée.

Patchs bienvenus.

VOIR AUSSI

Il existe d'autres systèmes de mocking moins élaborés pour Perl, notamment Test::MockObject et Test::MockObject::Extends.

Ce module est un plugin pour Test::Spec. Il est inspiré par Mocha http://mocha.rubyforge.org/.

L'article Wikipédia sur les objets mock http://en.wikipedia.org/wiki/Mock_object est très informatif.
