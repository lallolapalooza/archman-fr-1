Template::Tutorial::Web - Générer du contenu Web à l'aide de la Template Toolkit

Vue d'ensemble

Ce document de tutoriel fournit une introduction à la Template Toolkit et démontre certaines des façons typiques dont elle peut être utilisée pour générer du contenu Web. Il couvre la génération de pages statiques à partir de modèles à l'aide des scripts tpage et ttree, puis montre la génération de contenu dynamique à l'aide de scripts CGI et de gestionnaires Apache/mod_perl.

Diverses fonctionnalités de la Template Toolkit sont introduites et décrites brièvement, puis expliquées par des exemples. Pour plus d'informations, consultez Template, Template::Manual et les différentes sections correspondantes. Par exemple :

perldoc Template                    # Utilisation du module Template.pm
perldoc Template::Manual            # Index du manuel
perldoc Template::Manual::Config    # Par ex. options de configuration

La documentation est également disponible au format HTML pour être lue en ligne, ou téléchargée depuis le site Web de la Template Toolkit :

http://template-toolkit.org/docs/

Introduction

La Template Toolkit est un ensemble de modules Perl qui implémentent collectivement un système de traitement de modèles.

Un modèle est un document texte contenant des balises spéciales intégrées. Par défaut, la Template Toolkit utilise '"[%"' et '"%]"' pour délimiter le début et la fin d'une balise. Voici un exemple :

[% INCLUDE header %]

Gens de [% planet %], votre attention s'il vous plaît.

Ceci est [% captain %] du
Conseil Galactique de Planification Hyperspatiale.

Comme vous le savez sans doute, les plans
de développement des régions périphériques
de la Galaxie nécessitent la construction
d'une voie express hyperspatiale à travers votre
système stellaire, et malheureusement votre planète
est parmi celles prévues pour la destruction.

Le processus prendra un peu moins de
[% time %].

Merci.

[% INCLUDE footer %]

Les balises peuvent contenir de simples *variables* (comme "planet" et "captain") et des *directives* plus complexes qui commencent par un mot-clé en majuscule (comme "INCLUDE"). Une directive est une instruction qui indique au processeur de modèle d'effectuer une action, comme le traitement d'un autre modèle ("header" et "footer" dans cet exemple) et l'insertion de la sortie dans le modèle actuel. En fait, les variables simples que nous avons mentionnées sont en fait des directives *GET*, mais le mot-clé "GET" est facultatif.

Gens de [% planet %], votre attention s'il vous plaît.      # forme courte
Gens de [% GET planet %], votre attention s'il vous plaît.  # forme longue

Les autres directives incluent "SET" pour définir une valeur de variable (le mot-clé "SET" est également facultatif), "FOREACH" pour parcourir une liste de valeurs, et "IF", "UNLESS", "ELSIF" et "ELSE" pour déclarer des blocs conditionnels.

La Template Toolkit traite tous les fichiers *texte* de la même manière, quel que soit le type de contenu qu'ils contiennent. Vous pouvez donc utiliser TT pour générer HTML, XML, CSS, Javascript, Perl, RTF, LaTeX ou tout autre format textuel. Dans ce tutoriel, cependant, nous nous concentrerons sur la génération de HTML pour les pages Web.

Génération de contenu Web statique

Voici un exemple de modèle utilisé pour générer un document HTML.

[%  INCLUDE header
      title = 'Ceci est un exemple HTML';

    pages = [
      { url   = 'http://foo.org'
        title = 'The Foo Organisation' 
      }
      { url   = 'http://bar.org'
        title = 'The Bar Organisation' 
      }
    ]
%]
   <h1>Quelques liens intéressants</h1>
   <ul>
[%  FOREACH page IN pages %]
     <li><a href="[% page.url %]">[% page.title %]</a>
[%  END %]
   </ul>

[% INCLUDE footer %]

Cet exemple montre comment la directive "INCLUDE" est utilisée pour charger et traiter des fichiers de modèle distincts '"header"' et '"footer"', en incluant la sortie dans le document actuel. Ces fichiers pourraient ressembler à ceci :

header :

<html>
  <head>
    <title>[% title %]</title>
  </head>
  <body>

footer :

    <div class="copyright">
      &copy; Copyright 2007 Arthur Dent
    </div>
  </body>
</html>

L'exemple utilise également la directive "FOREACH" pour parcourir la liste '"pages"' afin de construire un tableau de liens. Dans cet exemple, nous avons défini cette liste dans le modèle pour contenir un certain nombre de références de hachage, chacune contenant un membre '"url"' et '"title"'. La directive "FOREACH" parcourt la liste, attribuant '"page"' à chaque élément (dans ce cas, des références de hachage). Les directives "[% page.url %]" et "[% page.title %]" accèdent ensuite aux valeurs individuelles dans les hachages et les insèrent dans le document.

Utilisation de tpage

Après avoir créé un fichier modèle, nous pouvons maintenant le traiter pour générer une sortie réelle. La manière la plus rapide et la plus simple de le faire est d'utiliser le script tpage. Il est fourni dans le cadre de la Template Toolkit et doit être installé dans votre répertoire Perl bin habituel.

En supposant que vous ayez enregistré votre fichier modèle sous le nom de example.html, vous exécuteriez la commande :

$ tpage example.html

Cela traitera le fichier modèle, envoyant la sortie à "STDOUT" (c'est-à-dire qu'elle défilera sur votre écran). Vous voudrez peut-être rediriger la sortie vers un fichier, mais faites attention à ne pas spécifier le même nom que le fichier modèle, sinon vous l'écraserez. Vous pourriez vouloir utiliser un préfixe pour vos modèles (par exemple, '".tt"') et un autre (par exemple, '".html"') pour les fichiers de sortie.

$ tpage example.tt > example.html

Ou vous pouvez rediriger la sortie vers un autre répertoire. Par exemple :

$ tpage templates/example.tt > html/example.html

La sortie générée ressemblerait à ceci :

<html>
  <head>
    <title>Ceci est un exemple HTML</title>
  </head>
  <body>
    <h1>Quelques liens intéressants</h1>
    <ul>
      <li><a href="http://foo.org">The Foo Organsiation</a>
      <li><a href="http://bar.org">The Bar Organsiation</a>
    </ul>
    <div class="copyright">
      &copy; Copyright 2007 Arthur Dent
    </div>
  </body>
</html>

Les fichiers de modèle *header* et *footer* ont été inclus (en supposant que vous les avez créés et qu'ils se trouvent dans le répertoire actuel) et les données de lien ont été intégrées dans une liste HTML.

Utilisation de ttree

Le script tpage vous offre un moyen simple et facile de traiter un seul modèle sans avoir à écrire de code Perl. Le script <ttree:Template::Tools::ttree>, également distribué dans le cadre de la Template Toolkit, offre un moyen plus flexible de traiter un certain nombre de documents modèles en une seule fois.

ttree Usage

The ttree script processes a hierarchy of template files from a source directory ("src") and writes the output to a destination directory ("dest"). It uses Template Toolkit to process the files and can be configured via a .ttreerc file in your home directory.

The configuration file can specify various options, including:

  • "src": The source directory containing template files.
  • "dest": The destination directory for processed files.
  • "lib": A library directory for template includes (e.g., headers, footers).
  • "verbose": Enables verbose output.
  • "recurse": Processes files in subdirectories.
  • "ignore": Regular expressions to exclude files from processing.
  • "accept": Regular expressions to explicitly include files.
  • "copy": Regular expressions for files to be copied directly without processing.
  • "cfg": Directory to store additional configuration files.
  • Template Toolkit options like "interpolate", "pre_process", "post_chomp", etc.

You can specify processing options (such as "verbose" and "recurse") and provide regular expressions to match files that you don't want to process ("ignore", "accept") or should be copied instead of being processed as templates ("copy").

An example .ttreerc file is shown here:

$HOME/.ttreerc:

verbose
recurse

# this is where I keep other ttree config files
cfg = ~/.ttree

src  = ~/websrc/src
lib  = ~/websrc/lib
dest = ~/public_html/test

ignore = \b(CVS|RCS)\b
ignore = ^#

You can create many different configuration files and store them in the directory specified in the "cfg" option, shown above. You then add the "-f filename" option to "ttree" to have it read that file.

When you run the script, it compares all the files in the "src" directory (including those in sub-directories if the "recurse" option is set), with those in the "dest" directory. If the destination file doesn't exist or has an earlier modification time than the corresponding source file, then the source will be processed with the output written to the destination file. The "-a" option forces all files to be processed, regardless of modification times.

The script doesn't process any of the files in the "lib" directory, but it does add it to the "INCLUDE_PATH" for the template processor so that it can locate these files via an "INCLUDE", "PROCESS" or "WRAPPER" directive. Thus, the "lib" directory is an excellent place to keep template elements such as header, footers, etc., that aren't complete documents in their own right.

You can also specify various Template Toolkit options from the configuration file. Consult the ttree documentation and help summary ("ttree -h") for full details. e.g.

$HOME/.ttreerc:

pre_process = config
interpolate
post_chomp

The "pre_process" option allows you to specify a template file which should be processed before each file. Unsurprisingly, there's also a "post_process" option to add a template after each file. In the fragment above, we have specified that the "config" template should be used as a prefix template. We can create this file in the "lib" directory and use it to define some common variables, including those web page links we defined earlier and might want to re-use in other templates. We could also include an HTML header, title, or menu bar in this file which would then be prepended to each and every template file, but for now we'll keep all that in a separate "header" file.

$lib/config:

[% root     = '~/abw'
   home     = "$root/index.html"
   images   = "$root/images"
   email    = 'abw@wardley.org'
   graphics = 1
   webpages = [
     { url => 'http://foo.org', title => 'The Foo Organsiation' }
     { url => 'http://bar.org', title => 'The Bar Organsiation' }
   ]
%]

Assuming you've created or copied the "header" and "footer" files from the earlier example into your "lib" directory, you can now start to create web pages like the following in your "src" directory and process them with "ttree".

$src/newpage.html:

[% INCLUDE header
   title = 'Another Template Toolkit Test Page'
%]

    <a href="[% home %]">Home</a>
    <a href="mailto:[% email %]">Email</a>

[% IF graphics %]
    <img src="[% images %]/logo.gif" align=right width=60 height=40>
[% END %]

[% INCLUDE footer %]

Here we've shown how pre-defined variables can be used as flags to enable certain feature (e.g. "graphics") and to specify common items such as an email address and URL's for the home page, images directory and so on. This approach allows you to define these values once so that they're consistent across all pages and can easily be changed to new values.

When you run ttree, you should see output similar to the following (assuming you have the verbose flag set).

 ttree 2.9 (Template Toolkit version 2.20)

      Source: /home/abw/websrc/src
 Destination: /home/abw/public_html/test
Include Path: [ /home/abw/websrc/lib ]
      Ignore: [ \b(CVS|RCS)\b, ^# ]
        Copy: [  ]
      Accept: [ * ]

 + newpage.html

The "+" in front of the "newpage.html" filename shows that the file was processed, with the output being written to the destination directory. If you run the same command again, you'll see the following line displayed instead showing a "-" and giving a reason why the file wasn't processed.

- newpage.html                     (not modified)

It has detected a "newpage.html" in the destination directory which is more recent than that in the source directory and so hasn't bothered to waste time re-processing it. To force all files to be processed, use the "-a" option. You can also specify one or more filenames as command line arguments to "ttree":

tpage newpage.html

This is what the destination page looks like.

$dest/newpage.html:

<html>
  <head>
    <title>Another Template Toolkit Test Page</title>
  </head>
  <body>

    <a href="~/abw/index.html">Home</a>
    <a href="mailto:abw@wardley.org">Email me</a>
    <img src="~/abw/images/logo.gif" align=right width=60 height=40>

    <div class="copyright">
      &copy; Copyright 2007 Arthur Dent
    </div>
  </body>
</html>

You can add as many documents as you like to the "src" directory and "ttree" will apply the same process to them all. In this way, it is possible to build an entire tree of static content for a web site with a single command. The added benefit is that you can be assured of consistency in links, header style, or whatever else you choose to implement in terms of common templates elements or variables.

Génération de Contenu Dynamique via un Script CGI

Le module Template fournit une interface simple au Template Toolkit pour une utilisation dans les scripts CGI et les gestionnaires Apache/mod_perl. Il suffit d'"use" le module Template, de créer une instance d'objet avec la méthode new(), puis d'appeler la méthode process() sur l'objet, en passant le nom du fichier modèle comme paramètre. Le second paramètre passé est une référence à un tableau associatif de variables que nous voulons rendre disponibles au modèle :

#!/usr/bin/perl
use strict;
use warnings;
use Template;

my $file = 'src/greeting.html';
my $vars = {
   message  => "Hello World\n"
};

my $template = Template->new();

$template->process($file, $vars)
    || die "Template process failed: ", $template->error(), "\n";

Pour que nos scripts fonctionnent avec les mêmes fichiers modèles que nos exemples précédents, nous pouvons ajouter quelques options de configuration au constructeur pour lui parler de notre environnement :

my $template->new({
    # où trouver les fichiers modèles
    INCLUDE_PATH => ['/home/abw/websrc/src', '/home/abw/websrc/lib'],
    # pré-traiter lib/config pour définir des valeurs supplémentaires
    PRE_PROCESS  => 'config',
});

Notez qu'ici nous spécifions le fichier "config" comme une option "PRE_PROCESS". Cela signifie que les modèles que nous traitons peuvent utiliser les mêmes variables globales que celles définies précédemment pour nos pages statiques. Nous n'avons pas à reproduire leurs définitions dans ce script. Cependant, nous pouvons fournir des données et des fonctionnalités supplémentaires spécifiques à ce script via le tableau associatif de variables que nous passons à la méthode process().

Ces entrées dans ce tableau peuvent contenir du texte simple ou d'autres valeurs, des références à des listes, d'autres tableaux associatifs, des sous-routines ou des objets. Le Template Toolkit appliquera automatiquement la procédure correcte pour accéder à ces différents types lorsque vous utilisez les variables dans un modèle.

Voici un exemple plus détaillé à examiner. Parmi les différentes variables de modèle que nous définissons dans $vars, nous créons une référence à un objet CGI et une sous-routine get_user_projects().

#!/usr/bin/perl
use strict;
use warnings;
use Template;
use CGI;

$| = 1;
print "Content-type: text/html\n\n";

my $file = 'userinfo.html';
my $vars = {
    'version'  => 3.14,
    'days'     => [ qw( mon tue wed thu fri sat sun ) ],
    'worklist' => \&get_user_projects,
    'cgi'      => CGI->new(),
    'me'       => {
        'id'     => 'abw',
        'name'   => 'Andy Wardley',
    },
};

sub get_user_projects {
    my $user = shift;
    my @projects = ...   # faire quelque chose pour récupérer les données
    return \@projects;
}

my $template = Template->new({
    INCLUDE_PATH => '/home/abw/websrc/src:/home/abw/websrc/lib',
    PRE_PROCESS  => 'config',
});

$template->process($file, $vars)
    || die $template->error();

Voici un exemple de fichier modèle que nous pourrions créer pour générer la sortie de ce script.

$src/userinfo.html:

[% INCLUDE header
   title = 'Template Toolkit CGI Test'
%]

<a href="mailto:[% email %]">Email [% me.name %]</a>

<p>This is version [% version %]</p>

<h3>Projects</h3>
<ul>
[% FOREACH project IN worklist(me.id) %]
   <li> <a href="[% project.url %]">[% project.name %]</a>
[% END %]
</ul>

[% INCLUDE footer %]

Cet exemple montre comment nous avons séparé l'implémentation Perl (code) de la présentation (HTML). Cela les rend non seulement plus faciles à maintenir isolément, mais permet également la réutilisation de

Garder toute la structure de fichiers. des éléments tels que les en-têtes et les pieds de page, entre autres. En utilisant un modèle pour créer la sortie de vos scripts CGI, vous pouvez leur donner la même cohérence que les pages statiques construites à l'aide de ttree ou d'autres moyens. De plus, nous pouvons modifier notre script pour qu'il traite l'un des différents modèles en fonction de certaines conditions. Un script CGI pour gérer une base d'utilisateurs, par exemple, pourrait traiter un modèle pour afficher un formulaire vierge pour les nouveaux utilisateurs, le même formulaire avec certaines valeurs par défaut pour mettre à jour un enregistrement d'utilisateur existant, un autre modèle pour lister tous les utilisateurs du système, et ainsi de suite. Vous pouvez utiliser toutes les fonctionnalités Perl que vous écrivez pour implémenter la logique de votre application, puis choisir un ou plusieurs modèles pour générer la sortie souhaitée en fonction de l'état de l'application. ### Génération de contenu dynamique via un gestionnaire Apache/Mod_Perl **NOTE :** Le module Apache::Template est disponible sur CPAN et offre une interface simple et conviviale pour le Template Toolkit d'Apache/mod_perl. Bien qu'basique, il implémente presque tout ce qui est décrit ci-dessous, évitant ainsi la nécessité d'écrire votre propre gestionnaire. Cependant, dans de nombreux cas, vous devrez écrire votre propre gestionnaire pour personnaliser le traitement en fonction de vos besoins, et cette section montrera comment commencer. Le module Template peut être utilisé à partir d'un gestionnaire Apache/mod_perl. Voici un exemple de fichier de configuration Apache typique : ```perl PerlModule CGI; PerlModule Template PerlModule MyOrg::Apache::User PerlSetVar websrc_root /home/abw/websrc SetHandler perl-script PerlHandler MyOrg::Apache::User ``` Cela définit un emplacement appelé `/user/bin` auquel toutes les requêtes sont dirigées vers la méthode `handler()` de la classe `MyOrg::Apache::User`. Cette classe pourrait ressembler à ceci : ```perl package MyOrg::Apache::User; use strict; use Apache::Constants qw( :common ); use Template; use CGI; our $VERSION = 1.59; sub handler { my $r = shift; my $websrc = $r->dir_config('websrc_root') or return fail($r, SERVER_ERROR, '"'websrc_root' not specified'); my $template = Template->new({ INCLUDE_PATH => "$websrc/src/user:$websrc/lib", PRE_PROCESS => 'config', OUTPUT => $r, # direct output to Apache request }); my $params = { uri => $r->uri, cgi => CGI->new, }; # use the path_info to determine which template file to process my $file = $r->path_info; $file =~ s[^/][]; $r->content_type('text/html'); $r->send_http_header; $template->process($file, $params) || return fail($r, SERVER_ERROR, $template->error()); return OK; } sub fail { my ($r, $status, $message) = @_; $r->log_reason($message, $r->filename); return $status; } ``` Le gestionnaire accepte la requête et l'utilise pour déterminer la valeur de `$websrc_root` à partir du fichier de configuration. Cette valeur est ensuite utilisée pour définir un `INCLUDE_PATH` pour un nouvel objet Template. L'URI est extrait de la requête et un objet CGI est créé. Ceux-ci sont tous deux définis comme variables de template. Le nom du fichier modèle lui-même est pris de la partie de l'URL qui se trouve après l'élément `PATH_INFO` de la requête. Dans ce cas, ce serait la partie de l'URL après `/user/bin`, par exemple, pour `/user/bin/edit`, le fichier modèle serait `edit` situé dans `$websrc/src/user`. Les en-têtes sont envoyés et le fichier modèle est traité. Toute la sortie est envoyée directement à la méthode `print()` de l'objet de requête Apache. ### Utilisation de plugins pour étendre les fonctionnalités Comme nous l'avons déjà montré, il est possible de lier des données et des fonctions Perl avec des variables de modèle lors de la création de contenu dynamique via un script CGI ou un processus Apache/mod_perl. Le Template Toolkit prend également en charge une interface de plugins qui permet de définir des données et/ou des fonctionnalités supplémentaires dans un module séparé, puis de le charger et de l'utiliser avec la directive `USE`. L'avantage principal de cette approche est que vous pouvez charger l'extension dans n'importe quel document de modèle, même ceux qui sont traités statiquement par `tpage` ou `ttree`. Vous n'avez pas besoin d'écrire un wrapper Perl pour charger explicitement le module et le rendre disponible dans le stash. Nous allons démontrer ces principes en utilisant le plugin `DBI` écrit par Simon Matthews (disponible sur CPAN). Vous pouvez créer ce modèle dans votre répertoire `src` et le traiter avec `ttree` pour voir les résultats. Bien sûr, cet exemple dépend de l'existence d'une base de données SQL appropriée, mais vous devriez pouvoir l'adapter à vos ressources, ou au moins l'utiliser comme exemple de ce qui est possible. ```html [% INCLUDE header title = 'User Info' %] [% USE DBI('dbi:mSQL:mydbname') %] [% FOREACH user IN DBI.query('SELECT * FROM user ORDER BY id') %] [% END %]
User ID Name Email
[% user.id %] [% user.name %] [% user.email %]
[% INCLUDE footer %] ``` Un plugin est simplement un module Perl situé à un emplacement connu et conforme à une norme connue, permettant au Template Toolkit de le trouver et de le charger automatiquement. Vous pouvez créer votre propre plugin en héritant de la classe `Template::Plugin`. Voici un exemple qui définit des données ( `foo` et `people`) ainsi qu'une méthode d'objet ( `bar`). Nous appellerons le plugin `FooBar` faute de mieux et nous le créerons dans la classe `MyOrg::Template::Plugin::FooBar`. Nous ajoutons un `MyOrg` à la classe `Template::Plugin::*` pour éviter les conflits avec les plugins existants. ```perl package MyOrg::Template::Plugin::FooBar; use base 'Template::Plugin' our $VERSION = 1.23; sub new { my ($class, $context, @params) = @_; bless { _CONTEXT => $context, foo => 25, people => [ 'tom', 'dick', 'harry' ], }, $class; } sub bar { my ($self, @params) = @_; # ...do something... return $some_value; } ``` Le constructeur du plugin `new()` reçoit le nom de la classe comme premier paramètre, ce qui est habituel en Perl, suivi d'une référence à un objet `Template::Context`. Ne vous inquiétez pas trop à ce sujet, mais sachez qu'il s'agit de l'objet de traitement principal du Template Toolkit. Il fournit un accès à la fonctionnalité du processeur et certains plugins peuvent avoir besoin de communiquer avec lui. Nous ne le ferons pas maintenant, mais nous le conserverons dans le membre `_CONTEXT`. Le soulignement initial indique que cet élément est privé et que le Template Toolkit n'essaiera pas d'y accéder. Les autres membres définis, `foo` et `people`, sont des données ordinaires qui seront présentées aux modèles utilisant ce plugin. Après la référence au contexte, tous les paramètres supplémentaires spécifiés avec la directive `USE` sont transmis, tels que le paramètre de source, `dbi:mSQL:mydbname`, que nous avons utilisé dans l'exemple précédent. Si vous ne pouvez pas ou ne pouvez pas l'installer à son emplacement habituel pour vos modules Perl (probablement parce que vous n'avez pas les droits nécessaires), vous pouvez définir la variable d'environnement `PERL5LIB` pour spécifier un autre emplacement. Si vous utilisez `ttree`, vous pouvez ajouter la ligne suivante à votre fichier de configuration : ``` $HOME/.ttreerc: perl5lib = /path/to/modules ``` Une configuration supplémentaire doit être ajoutée pour indiquer à l'outil le nouveau nom de package que nous utilisons pour nos plugins : ``` $HOME/.ttreerc: plugin_base = 'MyOrg::Template::Plugin' ``` Si vous écrivez du code Perl pour contrôler directement les modules Template, cette valeur peut être transmise comme paramètre de configuration lors de la création du module. ```perl use Template; my $template = Template->new({ PLUGIN_BASE => 'MyOrg::Template::Plugin' }); ``` Nous pouvons maintenant créer un modèle qui utilise ce plugin : ```html [% INCLUDE header title = 'FooBar Plugin Test' %] [% USE FooBar %] Valeurs disponibles à partir de ce plugin : [% FooBar.foo %] [% FooBar.bar %] Utilisateurs définis dans la liste 'people' : [% FOREACH uid = FooBar.people %] * [% uid %] [% END %] [% INCLUDE footer %] ``` Les éléments `foo`, `bar` et `people` du plugin `FooBar` sont automatiquement résolus en données correspondantes ou en appels de méthode de l'objet sous-jacent. En utilisant cette approche, il est possible de créer une fonctionnalité d'application dans un seul module qui peut ensuite être chargé et utilisé dans n'importe quel modèle. L'interface simple entre les directives de modèle et les objets de plugin permet de construire un contenu dynamique complexe à partir de quelques documents de modèle simples sans connaître l'implémentation sous-jacente. ### AUTEUR Andy Wardley http://wardley.org/ ### DROITS D'AUTEUR Copyright (C) 1996-2007 Andy Wardley.
