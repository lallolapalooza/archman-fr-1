NOM

Test::Warn - Extension Perl pour tester les méthodes produisant des avertissements

SYNOPIS

use Test::Warn;
warning_is    {foo(-dri => "/")} "Unknown Parameter 'dri'", "dri != dir donne un avertissement";
warnings_are  {bar(1,1)} ["Width very small", "Height very small"];
warning_is    {add(2,2)} undef, "Aucun avertissement pour calc 2+2"; # ou
warnings_are  {add(2,2)} [],    "Aucun avertissement pour calc 2+2"; # celui qui se lit mieux :-)
warning_like  {foo(-dri => "/")} qr/unknown param/i, "un test de paramètre inconnu";
warnings_like {bar(1,1)} [qr/width.*small/i, qr/height.*small/i];
warning_is    {foo()} {carped => "didn't find the right parameters"};
warnings_like {foo()} [qr/undefined/,qr/undefined/,{carped => qr/no result/i}];
warning_like {foo(undef)}                 'uninitialized';
warning_like {bar(file => '/etc/passwd')} 'io';
warning_like {eval q/"$x"; $x;/}
             [qw/void uninitialized/],
             "quelques avertissements à la compilation";
warnings_exist {...} [qr/expected warning/], "L'avertissement attendu est lancé";

DESCRIPTION

Un bon style de programmation en Perl exige beaucoup de tests de régression diversifiés.

Ce module fournit quelques méthodes pratiques pour tester le code basé sur les avertissements.

Si vous n'êtes pas encore familier avec la page man Test::More, c'est le moment d'y jeter un coup d'œil.

FONCTIONS

warning_is BLOC CHAINE, NOM_TEST
Teste que le BLOC donne exactement l'avertissement spécifié une seule fois.

Le test échoue si le BLOC produit plus d'un avertissement ou aucun avertissement. Si la chaîne est indéfinie (undef), le test réussit si le BLOC ne produit aucun avertissement.

Une autre façon de dire qu'il n'y a pas d'avertissement dans le bloc est :

warnings_are {foo()} [], "pas d'avertissement"

Si vous voulez tester un avertissement donné par Carp, vous devez écrire quelque chose comme :

warning_is {carp "msg"} {carped => 'msg'}, "Test d'un avertissement carpé";

Le test échouera si un avertissement "normal" est trouvé à la place d'un avertissement "carpé".

Note : "warn "foo"" imprimerait quelque chose comme "foo at -e line 1". Cette méthode ignore tout ce qui suit "at". Ainsi, pour correspondre à cet avertissement, vous devriez appeler "warning_is {warn "foo"} "foo", "Foo a réussi"". Si vous avez besoin de tester un avertissement à une ligne exacte, essayez quelque chose comme :

warning_like {warn "foo"} qr/at XYZ.dat line 5/

Les messages d'avertissement avec une nouvelle ligne à la fin (comme "warn "foo\n"") ne produisent pas le message "at -e line 1" par Perl. Jusqu'à Test::Warn 0.30, de tels avertissements n'étaient pas pris en charge par "warning_is {warn "foo\n"} "foo\n"". À partir de la version 0.31, ils sont pris en charge, mais également marqués comme expérimentaux.

warning_is() et warnings_are() sont uniquement des alias de la même méthode. Vous pourriez donc aussi écrire "warning_is {foo()} [], "pas d'avertissement"" ou quelque chose de similaire.

J'ai décidé de donner deux noms de méthode à la même fonctionnalité pour améliorer la lisibilité.

Une valeur vraie est retournée si le test réussit, faux sinon.

Le nom du test est facultatif, mais recommandé.

warnings_are BLOC TABLEAU_REF, NOM_TEST
Teste si le BLOC produit exactement les avertissements spécifiés. Le test échoue si les avertissements du BLOC ne sont pas exactement ceux du TABLEAU_REF. Si le TABLEAU_REF est égal à "[]", le test réussit si le BLOC ne produit aucun avertissement.

Veuillez lire également les notes relatives à warning_is() car ces méthodes ne sont que des alias.

Si vous souhaitez plusieurs tests pour les avertissements carpeés, essayez ceci :

warnings_are {carp "c1"; carp "c2"} {carped => ['c1','c2'];

ou

warnings_are {foo()} ["Avertissement 1", {carped => ["Carp 1", "Carp 2"]}, "Avertissement 2"];

Notez que "{carped => ...}" doit toujours être une référence de hachage.

warning_like BLOC REGEXP, NOM_TEST
Teste que le BLOC produit exactement un avertissement et qu'il peut être mis en correspondance par l'expression régulière donnée.

Si la chaîne est indéfinie (undef), le test réussit si le BLOC ne produit aucun avertissement.

L'EXPRESSION_REGULIERE est mise en correspondance avec toute la ligne d'avertissement, qui a généralement la forme "WARNING at __FILE__ line __LINE__". Vous pouvez donc tester un avertissement dans le fichier "Foo.pm" à la ligne 5 avec :

warning_like {bar()} qr/at Foo.pm line 5/, "Nom du test"

Je ne sais pas si cela a du sens de faire un tel test :-(

Cependant, vous devez vous attendre à ce qu'une correspondance avec 'at', 'file', '\d' ou similaire réussisse toujours.

Considérez "qr/^foo/" si vous voulez tester l'avertissement "foo something" dans le fichier foo.pl.

Vous pouvez également écrire l'expression régulière sous forme de chaîne comme "/.../" au lieu d'utiliser la syntaxe "qr/.../".

Notez que les barres obliques sont importantes dans la chaîne, car les chaînes sans barres obliques sont réservées aux catégories d'avertissement (pour correspondre aux catégories d'avertissement comme indiqué dans la page man perllexwarn).

Similaire à warning_is() et warnings_are(), vous pouvez tester les avertissements via "carp" avec :

warning_like {bar()} {carped => qr/bar called too early/i};

Similaire à warning_is() et warnings_are(),

warning_like() et warnings_like() ne sont que des alias des mêmes méthodes.

Une valeur vraie est retournée si le test réussit, faux sinon.

Le nom du test est facultatif, mais recommandé.

warning_like BLOC CHAINE, NOM_TEST
Teste si un BLOC produit exactement un avertissement de la catégorie passée.

Les catégories sont regroupées dans un arbre, comme exprimé dans perllexwarn. Voir également "BUGS AND LIMITATIONS".

Grâce au regroupement en arbre, il est possible de tester simplement un avertissement 'io', au lieu de tester un avertissement 'closed|exec|layer|newline|pipe|unopened'.

Notez que les avertissements survenant à la compilation ne peuvent être capturés que dans un bloc eval. Donc

warning_like {eval q/"$x"; $x;/}
              [qw/void uninitialized/],
              "quelques avertissements à la compilation";

fonctionnera, alors que cela ne fonctionnerait pas sans l'eval.

Notez qu'il n'est pas encore possible de tester des catégories personnalisées, créées avec warnings::register.

warnings_like BLOC TABLEAU_REF, NOM_TEST
Teste si le BLOC produit exactement le nombre d'avertissements spécifiés, dans l'ordre défini.

Veuillez lire également les notes relatives à warning_like() car ces méthodes ne sont que des alias.

Similaire à warnings_are(), vous pouvez tester plusieurs avertissements via "carp" et également des catégories d'avertissement :

warnings_like {foo()}
              [qr/avertissement bar/,
               qr/avertissement bar/,
               {carped => qr/avertissement bar/i},
               'io'
              ],
              "J'espère que vous n'aurez jamais à écrire un test pour autant d'avertissements :-)";

NOM

Test::Warn

SYNTAXE

Test::Warn est un module Perl qui vous permet de tester les avertissements dans votre code. Il fournit des méthodes pour vérifier des avertissements spécifiques, comme "warning_is", "warnings_are", "warning_like", et "warnings_like", et supporte également la vérification de l'existence d'avertissements sans correspondre à une regex/catégorie.

DESCRIPTION

Le module fournit des méthodes pour vérifier des avertissements spécifiques dans votre code. Il vous permet de tester si certains avertissements sont générés, et il peut également vérifier si des avertissements existent sans correspondre à une regex/catégorie. Ceci est utile lorsque vous voulez simplement vous assurer que des avertissements spécifiques ont été générés, et que vous ne vous souciez pas des autres avertissements dans le même bloc de code.

BOGUES ET LIMITATIONS

La vérification de catégorie se fait comme "qr/category_name/". Dans certains cas, cela fonctionne, comme pour la catégorie 'uninitialized'. Pour 'utf8', cela ne fonctionne pas. Perl n'a pas de liste d'avertissements, il n'est donc pas possible d'en générer une pour "Test::Warn".

Si vous souhaitez ajouter un avertissement à une catégorie, envoyez une pull request. Les modifications devraient être apportées à %warnings_in_category. Vous devriez examiner le code source de Perl pour vérifier à quoi ressemble exactement l'avertissement.

Veuillez noter que les avertissements contenant des sauts de ligne sont très gênants. La seule façon raisonnable de les gérer est d'utiliser les méthodes "warning_like" ou "warnings_like". La raison est qu'il n'y a aucun moyen vraiment sûr de distinguer les avertissements avec des sauts de ligne d'une trace de pile.

Si une méthode a son propre gestionnaire d'avertissement, qui écrase $SIG{__WARN__}, mes méthodes de test d'avertissement ne recevront pas ces avertissements.

La méthode "warning_like BLOCK CATEGORY, TEST_NAME" n'est pas entièrement testée. Veuillez en tenir compte si vous utilisez ce style d'appel, et signalez tout bogue que vous trouvez.

Avertissements en XS

Comme décrit dans https://rt.cpan.org/Ticket/Display.html?id=42070&results=3c71d1b101a730e185691657f3b02f21 ou https://github.com/hanfried/test-warn/issues/1 les avertissements XS pourraient ne pas être capturés.
