Test(3perl) Manuel de référence pour développeurs Perl Test(3perl)

NOM

Test - fournit un framework simple pour écrire des scripts de test

SYNOPIS

use strict;
use Test;
# utiliser un bloc BEGIN pour imprimer notre plan avant que MyModule ne soit chargé
BEGIN { plan tests => 14, todo => [3,4] }
# charger votre module...
use MyModule;
# Notes utiles. Toutes les lignes de commentaire doivent commencer par un #.
print "# Je teste MyModule version $MyModule::VERSION\n";
ok(0); # échec
ok(1); # succès
ok(0); # ok, échec attendu (voir la liste des échecs ci-dessus)
ok(1); # succès inattendu !
ok(0,1);             # échec : '0' ne vaut pas '1'
ok('broke','fixed'); # échec : 'broke' ne vaut pas 'fixed'
ok('fixed','fixed'); # succès : 'fixed' est égal à 'fixed'
ok('fixed',qr/x/);   # succès : 'fixed' correspond à qr/x/
ok(sub { 1+1 }, 2);  # succès : '2' est égal à '2'
ok(sub { 1+1 }, 3);  # échec : '2' ne vaut pas '3'
my @list = (0,0);
ok @list, 3, "\@list=".join(',',@list);      # notes supplémentaires
ok 'segmentation fault', '/(?i)success/';    # correspondance regex
skip(
  $^O =~ m/MSWin/ ? "Sauter si MSWin" : 0,  # faut-il sauter ?
  $foo, $bar  # arguments similaires à ok(...)
);
skip(
  $^O =~ m/MSWin/ ? 0 : "Sauter si non MSWin",  # faut-il sauter ?
  $foo, $bar  # arguments similaires à ok(...)
);

DESCRIPTION

Ce module simplifie la tâche d'écriture de fichiers de test pour les modules Perl, de telle sorte que leur sortie soit dans le format attendu par Test::Harness.

GUIDE DE DÉMARRAGE RAPIDE

Pour écrire un test pour votre nouveau module (probablement incomplet), créez un nouveau fichier appelé t/test.t (dans un nouveau dossier t). Si vous avez plusieurs fichiers de test, pour tester les fonctionnalités de « foo », « bar » et « baz », vous pouvez nommer vos fichiers t/foo.t, t/bar.t et t/baz.t.

FONCTIONS

Ce module définit trois fonctions publiques, plan(...), ok(...) et skip(...). Par défaut, elles sont toutes exportées par le "use Test;".

plan(...)
BEGIN { plan %theplan; }

Ce devrait être la première chose que vous faites dans votre script de test. Il déclare votre plan de test, combien il y en a, si certains peuvent échouer, et ainsi de suite.

L'utilisation typique est simplement :

use Test;
BEGIN { plan tests => 23 }

Voici les éléments que vous pouvez placer dans les paramètres de plan :

"tests => nombre"
Le nombre de tests dans votre script. Cela correspond à tous les appels ok() et skip().
"todo => [1,5,14]"
Une référence à une liste de tests qui peuvent échouer. Voir « TESTS EN COURS ».
"onfail => sub { ... }"
"onfail => \&some_sub"
Une référence à une sous-routine qui sera exécutée à la fin du script de test, si un des tests échoue. Voir « ONFAIL ».

Vous devez appeler plan(...) une et une seule fois. Vous devez l'appeler dans un bloc "BEGIN {...}", comme ceci :

BEGIN { plan tests => 23 }
ok(...)
ok(1 + 1 == 2);
ok($have, $expect);
ok($have, $expect, $diagnostics);

Cette fonction est la raison d'être de "Test". C'est la fonction de base qui imprime « "ok" » ou « "not ok" », avec le numéro de test actuel. (C'est ce que "Test::Harness" attend.)

Dans son utilisation la plus basique, ok(...) prend simplement une seule expression scalaire. Si sa valeur est vraie, le test réussit ; si elle est fausse, il échoue. Exemples :

# Exemples de ok(scalaires)
ok( 1 + 1 == 2 );           # réussit si 1 + 1 == 2
ok( $foo =~ /bar/ );        # réussit si $foo contient 'bar'
ok( baz($x + $y) eq 'Armondo' );    # réussit si baz($x + $y) renvoie
                                    # 'Armondo'
ok( @a == @b );             # réussit si @a et @b ont la même longueur
                            # et les mêmes éléments

L'expression est évaluée en contexte scalaire. Ainsi, ce qui suit fonctionnera :

ok( @stuff );                       # réussit si @stuff a des éléments
                                    # quelconques
ok( !grep !defined $_, @stuff );    # réussit si tout dans @stuff est défini.

Un cas spécial est si l'expression est une référence de sous-routine (au format "sub {...}" ou "\&foo"). Dans ce cas, elle est exécutée et sa valeur (vraie ou fausse) détermine si le test réussit ou échoue. Par exemple :

ok( sub {   # Vérifier si le sleep fonctionne au moins de manière passable
  my $start_time = time;
  sleep 5;
  time() - $start_time  >= 4
});

Dans sa forme à deux arguments, "ok(arg1, arg2)" compare les deux valeurs scalaires pour voir si elles sont égales. Elles correspondent si les deux sont indéfinies, ou si arg2 est une regex qui correspond à arg1, ou si elles se comparent de manière égale avec "eq".

# Exemple de ok(scalaires, scalaire)
ok( "this", "that" );               # ne réussit pas, 'this' ne vaut pas 'that'
ok( "", undef );                    # ne réussit pas, "" est défini

Le deuxième argument est considéré comme une regex s'il s'agit d'un objet regex ou d'une chaîne qui ressemble à une regex. Les objets regex sont créés avec l'opérateur "qr// dans les versions récentes de Perl. Une chaîne est considérée comme une regex si ses premiers et derniers caractères sont « / », ou si le premier caractère est « m » et ses deux derniers caractères sont tous deux des caractères non alphanumériques non blancs. Ces règles de regex

Exemples de regex :

ok( 'JaffO', '/Jaff/' );    # réussit, 'JaffO' =~ /Jaff/
ok( 'JaffO', 'm|Jaff|' );   # réussit, 'JaffO' =~ m|Jaff|
ok( 'JaffO', qr/Jaff/ );    # réussit, 'JaffO' =~ qr/Jaff/;
ok( 'JaffO', '/(?i)jaff/ ); # réussit, 'JaffO' =~ /jaff/i;

Si l'un (ou les deux) est une référence de sous-routine, elle est exécutée et sa valeur est utilisée pour la comparaison. Par exemple :

ok sub {
    open(OUT, '>', 'x.dat') || die $!;
    print OUT "\x{e000}";
    close OUT;
    my $bytecount = -s 'x.dat';
    unlink 'x.dat' or warn "Impossible de supprimer : $!";
    return $bytecount;
  },
  4
;

Le test ci-dessus passe deux valeurs à "ok(arg1, arg2)" — la première est un coderef, et la seconde est le nombre 4. Avant que "ok" ne les compare, le coderef est appelé, et sa valeur de retour est utilisée comme valeur réelle de ce paramètre. En supposant que $bytecount renvoie 4, "ok" teste "4 eq 4". Puisqu'il est vrai, ce test réussit.

Enfin, vous pouvez ajouter un troisième argument optionnel, dans "ok(arg1,arg2, note)", où note est une valeur de chaîne qui sera imprimée si le test échoue. Cela devrait être une information utile sur le test, expliquant pourquoi il échoue, et/ou une description du test. Par exemple :

ok( grep($_ eq 'something unique', @stuff), 1,
    "Something that should be unique isn't!\n".
    '@stuff = '.join ', ', @stuff
  );

Cependant, une note ne peut pas être utilisée avec le style d'appel ok(...) à un seul argument. C'est-à-dire, si vous essayez "ok(arg1, note)", "Test" interprétera cela comme "ok(arg1, arg2)", et échouera probablement sur "arg1 eq arg2". C'est pourquoi le texte de la note est pertinent.

ok( grep($_ eq 'something unique', @stuff), 1,
    "Something that should be unique isn't!\n".
    '@stuff = '.join ', ', @stuff
  );

Bien qu'une note ne puisse pas être utilisée avec le style d'appel ok(...) à un seul argument, c'est-à-dire si vous essayez "ok(arg1, note)", "Test" interprétera cela comme "ok(arg1, arg2)", et échouera probablement sur "arg1 eq arg2". C'est pourquoi le texte de la note est pertinent.

TESTS EN COURS

Pour marquer une preuve comme étant « en cours », ou « attendue à échouer », vous pouvez passer un tableau de numéros de tests à plan() comme argument todo.

BEGIN { plan tests => 10, todo => [3, 7, 8] }

Si le test numéro 3, 7 ou 8 échoue, cela ne sera pas signalé comme un échec du test en cours. Cela sera signalé comme « TODO ». Si l'un de ces tests réussit, cela sera signalé comme un « succès inattendu ».

Ceci est utile pour les erreurs connues que vous n'avez pas encore résolues. Une fois que vous avez résolu le problème, vous pouvez retirer le numéro de test de la liste todo.

ONFAIL

Si une preuve échoue, vous pouvez passer une référence de sous-routine à plan() comme argument onfail. Cette sous-routine sera appelée juste avant que le script de test ne se termine, et elle recevra comme argument une référence à un tableau de toutes les preuves qui ont échoué.

BEGIN { plan tests => 2, onfail => \&my_handler }
sub my_handler {
  my ($failed_tests) = @_;
  print "Oh non, les tests suivants ont échoué : @$failed_tests\n";
  # Je pourrais envoyer un email, ou faire autre chose ici.
}

TYPES DE TESTS

  • TESTS NORMAUX

    Ces tests sont censés réussir. Généralement, la plupart ou la totalité de vos tests appartiennent à cette catégorie. Si un test normal ne réussit pas, cela signifie que quelque chose ne va pas.

  • TESTS IGNORÉS

    La fonction skip(...) est destinée aux tests qui peuvent ou non être exécutés, en fonction de la disponibilité de fonctionnalités spécifiques à la plateforme. Le premier argument devrait s'évaluer à vrai (pensez « oui, veuillez ignorer ») si la fonctionnalité requise n'est pas disponible. Après le premier argument, skip(...) fonctionne exactement de la même manière que ok(...).

  • TESTS À FAIRE (TODO)

    Les tests TODO sont conçus pour maintenir une liste TODO exécutable. Ces tests sont censés échouer. Si un test TODO réussit, alors la fonctionnalité en question ne devrait plus être sur la liste TODO, n'est-ce pas ?

    Les packages NE DOIVENT PAS être publiés avec des tests TODO réussis. Dès qu'un test TODO commence à fonctionner, il doit être promu au rang de test normal, et la nouvelle fonctionnalité fonctionnelle doit être documentée dans les notes de publication ou dans le journal des modifications.

ONFAIL

BEGIN { plan test => 4, onfail => sub { warn "APPELLEZ LE 911!" } }

Bien que les échecs de tests devraient suffire, des diagnostics supplémentaires peuvent être déclenchés à la fin d'une série de tests. "onfail" reçoit un tableau de références de hash qui décrivent chaque échec de test. Chaque hash contiendra au moins les champs suivants : "package", "repetition", et "result". (Vous ne devriez pas vous fier à la présence d'autres champs.) Si le test avait une valeur attendue ou une chaîne de diagnostic (ou « note »), celles-ci seront également incluses.

Le crochet facultatif "onfail" pourrait être utilisé simplement pour imprimer la version de votre package et/ou la manière de signaler les problèmes. Il pourrait également être utilisé pour générer des diagnostics extrêmement sophistiqués pour un échec de test particulièrement bizarre. Cependant, ce n'est pas une panacée. Les plantages de noyau ou d'autres erreurs irrécupérables empêchent l'exécution du crochet "onfail". (Il est exécuté dans un bloc "END".) De plus, "onfail" est probablement excessif dans la plupart des cas. (Votre code de test doit être plus simple que le code qu'il teste, n'est-ce pas ?)

BOGUES et MISES EN GARDE

  • La gestion spéciale des chaînes qui ressemblent à des expressions régulières par ok(...) peut également entraîner un comportement inattendu. Un innocent : 
    ok( $fileglob, '/path/to/some/*stuff/' );

    échouera, car Test.pm considère le deuxième argument comme une expression régulière ! Le mieux est d'utiliser la forme à un seul argument :

    ok( $fileglob eq '/path/to/some/*stuff/' );
  • L'utilisation de la chaîne "eq" par ok(...) peut parfois causer des problèmes étranges lors de la comparaison de nombres, surtout si vous convertissez une chaîne en nombre : 
    $foo = "1.0";
ok( $foo, 1 );      # pas ok, "1.0" ne eq 1

    Le mieux est d'utiliser la forme à un seul argument :

    ok( $foo == 1 );    # ok "1.0" == 1
  • Comme vous l'avez peut-être déduit de la documentation et des exemples ci-dessus, le prototype de "ok" est "($;$$)" (et, incidemment, celui de "skip" est "($;$$$)"). Cela signifie, par exemple, que vous pouvez faire "ok @foo, @bar" pour comparer la taille des deux tableaux. Mais ne vous laissez pas tromper en pensant que "ok @foo, @bar" signifie une comparaison du contenu de deux tableaux – vous comparez seulement le nombre d'éléments de chacun. Il est si facile de faire cette erreur en lisant "ok @foo, @bar" que vous pourriez vouloir être très explicite à ce sujet, et écrire plutôt ok scalar(@foo), scalar(@bar).
  • Ceci ne fait presque certainement pas ce que vous attendez : 
    ok $thingy->can('some_method');

    Pourquoi ? Parce que "can" renvoie une référence de code pour signifier « oui, il peut (et la méthode est celle-ci...) », et ensuite "ok" voit une référence de code et pense que vous passez une fonction qu'il doit appeler et considérer la vérité de son résultat ! C'est-à-dire, tout comme :

    ok $thingy->can('some_method')->();

    Ce que vous voulez probablement à la place, c'est ceci :

    ok $thingy->can('some_method') && 1;

    Si "can" renvoie faux, alors cela est passé à "ok". S'il renvoie vrai, alors l'expression plus grande "$thingy->can('some_method') && 1" renvoie 1, que "ok" voit comme un simple signal de succès, comme vous vous y attendriez.

  • La syntaxe de "skip" est à peu près la seule possible, mais elle reste assez confuse. Commencez simplement par les exemples ci-dessus et tout ira bien.

    De plus, les utilisateurs peuvent s'attendre à ceci :

    skip $unless_mswin, foo($bar), baz($quux);

    à ne pas évaluer foo($bar) et baz($quux) lorsque le test est ignoré. Mais en réalité, ils sont évalués, mais "skip" ne s'embête pas à les comparer si $unless_mswin est vrai.

    Vous pourriez faire ceci :

    skip $unless_mswin, sub{foo($bar)}, sub{baz($quux)};

    Mais ce n'est pas très joli. Vous trouverez peut-être plus simple ou plus clair à long terme de simplement faire des choses comme ceci :

    if( $^O =~ m/MSWin/ ) {
  print "# Yay, nous sommes sous $^O\n";
  ok foo($bar), baz($quux);
  ok thing($whatever), baz($stuff);
  ok blorp($quux, $whatever);
  ok foo($barzbarz), thang($quux);
} else {
  print "# Feh, nous sommes sous $^O. Regardez-moi ignorer quelques tests...\n";
  for(1 .. 4) { skip "Ignorer sauf sous MSWin" }
}

    Mais soyez tout à fait sûr que "ok" est appelé exactement autant de fois dans le premier bloc que "skip" est appelé dans le second bloc.

ENVIRONNEMENT

Si la variable d'environnement "PERL_TEST_DIFF" est définie, elle sera utilisée comme commande pour comparer les résultats multilignes inattendus. Si vous avez GNU diff installé, vous pourriez vouloir définir "PERL_TEST_DIFF" à "diff -u". Si vous n'avez pas de programme approprié, vous pourriez installer le module "Text::Diff" puis définir "PERL_TEST_DIFF" à "perl -MText::Diff -e 'print diff(@ARGV)'". Si

"PERL_TEST_DIFF" n'est pas défini mais le module "Algorithm::Diff" est disponible, alors il sera utilisé pour afficher les différences dans les sorties multilignes.
