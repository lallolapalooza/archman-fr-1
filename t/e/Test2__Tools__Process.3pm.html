Test2::Tools::Process(3) Documentation Perl fournie par l'utilisateur Test2::Tools::Process(3)

NOM

Test2::Tools::Process - Tests unitaires pour le code qui appelle exit, exec, system ou qx()

VERSION

version 0.07

SYNOPIS

use Test2::V0 -no_srand => 1;
use Test2::Tools::Process;

process {
  system 'foo', 'bar';
} [
  # vérifier que le premier appel système est à
  # une commande foo avec n'importe quels arguments
  proc_event(system => array {
    item 'foo';
    etc;
  }, sub {
    # simuler la commande foo
    my($proc, @args) = @_;
    note "commande faux bar : @args";
    # simuler une sortie normale
    $proc->exit(0);
  }),
];

process {
  exit 2;
  note 'pas exécuté';
} [
  # peut utiliser n'importe quels contrôles Test2 sur le statut de sortie
  proc_event(exit => match qr/^[2-3]$/),
];

process {
  exit 4;
} [
  # ou vous pouvez simplement vérifier que le statut de sortie correspond numériquement
  proc_event(exit => 4),
];

process {
  exit 5;
} [
  # ou simplement vérifier que nous avons appelé exit.
  proc_event('exit'),
];

process {
  exec 'foo bar';
  exec 'baz';
  note 'pas exécuté';
} [
  # émuler le premier exec comme échoué
  proc_event(exec => match qr/^foo\b/, sub {
    my($return, @command) = @_;
    $! = 2;
    return 0;
  }),
  # le second exec sera émuler comme réussi
  proc_event('exec'),
];

# intercepter simplement `exit`
is intercept_exit { exit 10 }, 10;

# intercepter simplement `exec`
is intercept_exec { exec 'foo', 'bar', 'baz' }, ['foo','bar','baz'];

done_testing;

DESCRIPTION

Cet ensemble d'outils de test est destiné à écrire des tests unitaires pour du code qui interagit avec d'autres processus sans utiliser de vrais processus qui pourraient avoir des effets secondaires indésirables. Il vous permet également de tester du code qui interrompt le flux du programme sans réellement terminer votre test. Jusqu'à présent, il vous permet de tester et/ou de simuler "exit", "exec", "system", "readpipe" et "qx//". D'autres tests liés aux processus seront ajoutés à l'avenir.

Ce module emprunte quelques idées à Test::Exit. En particulier, il n'utilise pas d'exceptions pour simuler "exit" ou "exec", vous pouvez donc tester librement du code qui les appelle dans un "eval".

FONCTIONS

process

my $ok = process { ... } \@events, $test_name;
my $ok = process { ... } \@events;
my $ok = process { ... } $test_name;
my $ok = process { ... };

Exécute le bloc, interceptant les appels "exit", "exec", "system", "readpipe" et "qx//". Les appels sont ensuite comparés à "\@events" en tant qu'événements de processus attendus. Voir "proc_event" ci-dessous pour définir des événements individuels, et le synopsis ci-dessus pour des exemples.

named_signal

my $signame = named_signal $name;

Étant donné un nom de signal sous forme de chaîne comme "KILL", cela renverra le numéro de signal entier. Cela lancera une exception si $name est invalide.

intercept_exit

my $status = intercept_exit { ... };

Intercepte tous les appels c<exit> à l'intérieur du bloc et renvoie le statut de sortie. Renvoie "undef" s'il n'y a pas eu d'appels "exec".

intercept_exec

my $arrayref = intercept_exec { ... };

Intercepte tous les appels "exec" à l'intérieur du bloc et renvoie la ligne de commande qui lui a été passée. Renvoie "undef" s'il n'y a pas eu d'appels "exec".

VERIFICATIONS

proc_event

process { ... } [
  proc_event($type => $check, $callback),
  proc_event($type => $check),
  proc_event($type => $callback),
  proc_event($type),

  # vérifications de résultats supplémentaires pour les événements `system`
  proc_event('system' => $check, \%result_check, $callback),
  proc_event('system' => \%result_check, $callback),
  proc_event('system' => $check, \%result_check),
  proc_event('system' => \%result_check),
];

La fonction "proc_event" crée un événement de processus, avec une vérification et un rappel optionnels. La façon dont $check fonctionne dépend du $type. Si aucun $check n'est fourni, il vérifiera seulement que le $type correspond. En raison de leur nature, les événements "exit" et "exec" sont émules. Les événements "system" effectueront réellement un appel système, à moins qu'un $callback ne soit fourni.

exit
Un événement de processus pour un appel "exit". La vérification porte sur la valeur de statut passée à "exit". Cette valeur sera toujours un entier. Si aucune valeur de statut n'a été passée à "exit", 0 sera utilisée comme valeur de statut.

Si aucun rappel n'est fourni, un "exit" sera émule en terminant le bloc de processus sans exécuter plus de code. Le reste du test se poursuivra.

proc_event( exit => sub {
  my($proc, $status) = @_;
  $proc->terminate;
});

Le rappel prend un objet $proc et une valeur $status. Normalement, "exit" ne devrait jamais retourner, donc ce que vous voulez faire est d'appeler la méthode "terminate" sur l'objet $proc.

exec
Un événement de processus pour un appel "exec". La vérification porte sur la commande passée à "exec". Si "exec" est appelé avec un seul argument, ce sera une chaîne, sinon ce sera une référence de tableau. De cette façon, vous pouvez différencier les modes SCALAR et LIST de "exec".

Si aucun rappel n'est fourni, un appel "exec" (réussi) sera émule en terminant le bloc de processus sans exécuter plus de code. Le reste du test se poursuivra.

proc_event( exec => sub {
  my($proc, @command) = @_;
  ...;
});

Le rappel prend un objet $proc et les arguments passés à "exec" sous forme de @command. Vous pouvez émuler un appel "exec" échoué en utilisant la méthode "errno" sur l'objet $proc :

proc_event( exec => sub {
  my($proc, @command) = @_;
  $proc->errno(2); # c'est la valeur errno
});

Pour émuler un appel "exec" réussi, vous voulez simplement vous souvenir d'appeler la méthode "terminate" sur l'objet $proc.

proc_event( exec => sub {
  my($proc, @command) = @_;
  $proc->terminate;
});
system
Un événement de processus pour "system", "piperead" et "qx//". La première vérification (comme avec "exec") porte sur la chaîne de commande passée à "system". La seconde est une référence de hachage avec des vérifications de résultats.
status

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

proc_event( system => { status => $check } );

Le statut de terminaison normal. C'est généralement la valeur passée à "exit" dans le programme appelé. Typiquement, un programme qui a réussi retournera zéro (0) et un programme qui a échoué retournera une valeur non nulle.

errno
proc_event( system => { errno => $check } );

La valeur "errno" ou $! si l'appel système a échoué. Le plus souvent, cela concerne des noms de commandes incorrects, mais cela pourrait être autre chose comme un manque de mémoire ou d'autres ressources système.

signal
proc_event( system => { signal => $check } );

Défini si le processus a été tué par un signal.

Une seule vérification devrait être incluse car une seule de ces options est généralement valide. Si vous ne fournissez pas cette vérification, elle vérifiera que le code de statut est zéro uniquement.

Par défaut, l'appel système réel sera effectué, mais si vous fournissez une fonction de rappel, vous pouvez simuler des commandes, ce qui est utile dans les tests unitaires de votre script sans avoir à appeler des programmes externes qui pourraient avoir des effets secondaires indésirables.

proc_event( system => sub {
  my($proc, @command) = @_;
  ...
});

Comme l'événement "exec", @command contient la commande complète passée à l'appel "system". Vous pouvez utiliser l'objet $proc pour simuler l'un des trois résultats différents :

exit
$proc->exit($status);
$proc->exit;

Sortir avec le statut donné. Un statut de zéro (0) sera utilisé s'il n'est pas fourni. Si aucun résultat n'est spécifié dans la fonction de rappel, un statut de zéro (0) sera également utilisé.

signal
$proc->signal($signal);

Terminer avec le signal donné. $signal peut être soit une valeur entière (auquel cas aucune validation qu'il s'agisse d'un signal réel n'est effectuée), soit un nom de signal sous forme de chaîne comme "KILL", "HUP" ou tout signal pris en charge par votre système d'exploitation. Si vous fournissez un nom de signal invalide, une exception sera levée.

proc_event( system => { signal => 9 } => sub {
  my($proc, @args) = @_;
  $proc->signal('KILL');
});

Notez que lorsque vous tuez l'un de ces faux processus avec un signal, vous voudrez mettre à jour la vérification du signal attendu, comme dans l'exemple ci-dessus.

errno
$proc->errno($errno);

Simuler un appel "system" échoué. Le plus souvent, "system" échoue si la commande n'est pas trouvée. Le $errno passé doit être une valeur "errno" valide. Sur mon système, 2 est le code d'erreur pour « commande introuvable ». Exemple :

proc_event( system => { errno => number(2) } => sub {
  my($proc, @args) = @_;
  $proc->errno(2);
});
type
my $type = $proc->type;

Retourne "system" ou "readpipe" en fonction de la fonction Perl qui a déclenché l'appel système.

CAVEATS

L'émulation de "exit" n'appelle pas les rappels "END" ni d'autres destructeurs, car vous ne terminez pas réellement le processus.

Ce module installe des gestionnaires pour "exec", "exit", "system" et "readpipe", dans l'espace de noms "CORE::GLOBAL", donc si votre code installe également des gestionnaires là-bas, les choses pourraient ne pas fonctionner.

Ce module n'est apparemment pas compatible avec IPC::Run3. Utilisez plutôt Capture::Tiny, qui est mieux maintenu à mon avis.

VOIR AUSSI

Test::Exit
Émulation simple de "exit" pour les tests. La version la plus récente ne repose pas sur des exceptions.
Test::Exec
Comme Test::Exit, mais pour "exec"
Test::Mock::Cmd
Fournit une interface pour simuler "system", "qx" et "exec".
