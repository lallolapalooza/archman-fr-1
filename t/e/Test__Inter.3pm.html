Test::Inter(3) Documentation Perl fournie par l'utilisateur Test::Inter(3)

NOM

Test::Inter - framework pour des scripts de test interactifs plus lisibles

DESCRIPTION

Ceci est un autre framework pour écrire des scripts de test. Une grande partie de la syntaxe est vaguement inspirée de Test::More, et Test::Inter possède la plupart de ses fonctionnalités, mais ce n'est pas un remplacement direct.

Test::More (et d'autres frameworks de test existants) souffrent de deux faiblesses, qui m'ont empêché de les utiliser jusqu'à présent :

Aucun n'offre la possibilité d'accéder à des tests spécifiques
de manière raisonnablement interactive, principalement à des fins de
débogage
Aucun n'offre la possibilité d'écrire les tests dans
le format qui rendrait les tests les plus lisibles

La façon dont j'écris et utilise les scripts de test, les modules Test::* existants ne sont pas aussi utiles qu'ils pourraient l'être.

Les scripts de test écrits à l'aide de Test::More fonctionnent bien lorsqu'ils sont exécutés dans le cadre de la suite de tests, mais le débogage d'un test individuel nécessite des étapes supplémentaires, et les tests eux-mêmes ne sont pas aussi lisibles qu'ils devraient l'être.

EXÉCUTION INTERACTIVE

Une exigence que j'ai d'un framework de test est la capacité d'interagir avec lui.

Je fais la plupart de mon débogage à l'aide de scripts de test. Lorsque je trouve un bug, j'écris un cas de test pour celui-ci (généralement en l'ajoutant à un script de test existant) puis je le débogue à l'aide du script de test. Ensuite, je laisse le test là pour m'assurer que le bug ne revienne pas (espérons-le).

Puisque j'utilise les scripts de test de manière très interactive (souvent dans le débogueur), je veux pouvoir faire trivialement ce qui suit :

Accès facile à un test ou des tests spécifiques
Je voudrais pouvoir exécuter un seul test, ou un sous-ensemble de tests.
Définir facilement des points d'arrêt dans le débogueur
Définir un point d'arrêt dans le débogueur pour exécuter jusqu'au début du N-ième test est l'une des tâches les plus courantes que je veux faire lorsque je débogue un test échoué.

Pour illustrer le premier point, dans Test::More, une série de tests pourrait être spécifiée dans un script de test comme montré dans l'exemple suivant (numéros de ligne ajoutés pour plus de commodité) :

...
100:  # test 1
101:  $result = func("apples","bushels");
102:  is($result, "enough");
103:
104:  # test 2
105:  $result = func("grapefruit","tons");
106:  is($result, "enough");
107:
108:  # test 3
109:  $result = func("oranges","boatloads");
110:  is($result, "insufficient");
111:
112:  # tests 4-6
113:  foreach my $arg (qw(pears plums pineapple)) {
114:    $result = func($arg,"boxes");
115:    is($result, "enough");
116:  }
...

Supposons que vous ayez exécuté la suite de tests et que le test 3 ait échoué. Pour le déboguer, vous devez ouvrir le script de test, trouver le 3ème test et définir le point d'arrêt approprié. Dans ce cas, vous voudrez vous arrêter à la ligne 109.

Aucune de ces étapes n'est impossible bien sûr, mais il faudra un certain temps pour y parvenir. Cela devient plus difficile lorsqu'il y a beaucoup de tests (imaginez que vous vouliez tester le 117ème test au lieu du 3ème) ou lorsque les tests sont encapsulés dans des boucles, intégrés dans des sous-programmes, ou des situations similaires.

Par exemple, que se passe-t-il si c'est le 5ème test qui échoue dans l'exemple ci-dessus. Maintenant, le point d'arrêt sera conditionnel, vous devrez donc non seulement trouver la ligne, mais aussi la condition de l'état approprié pendant ce test. Dans ce cas, vous devez vous arrêter à la ligne 114 lorsque $arg est 'plums'.

Ne serait-il pas beaucoup mieux de définir un point d'arrêt dans `func` lorsque le N-ième test est atteint ? Avec Test::Inter, vous le pouvez.

Donc, pour le script ci-dessus, les commandes de débogueur que vous utiliseriez pour déboguer le 3ème test sont :

Test::More :   b 109
Test::Inter:   b func ($::TI_NUM==3)

et le 5ème test sont :

Test::More :   b 114  ($arg eq 'plums')
Test::Inter:   b func ($::TI_NUM==5)

Il serait également agréable de pouvoir sauter les deux premiers tests... peut-être qu'ils prennent beaucoup de temps à s'exécuter, et que je veux me mettre tout de suite au travail sur le test 3. Vous pouvez le faire facilement aussi en définissant la variable $::TI_START.

Il existe d'autres variables qui peuvent être utilisées pour spécifier quel test ou quels tests exécuter, décrites dans la section "VARIABLES DE TEST::INTER" ci-dessous.

L'autre chose que je veux faire lorsque j'exécute les scripts de test de manière interactive est de voir plus d'informations qui aideront à déboguer un test échoué.

Ceci peut être contrôlé avec des variables telles que TI_QUIET, TI_MODE, et TI_WIDTH décrites ci-dessous dans la section "VARIABLES DE TEST::INTER".

TESTS LISIBLES

L'autre fonctionnalité que je voulais dans une suite de tests est la possibilité de définir les tests dans un format qui est naturel et lisible POUR LES TESTS. Dans presque tous les cas, il est préférable de considérer un script de test comme composé de deux parties distinctes : une partie script et une partie test.

La partie script d'un script de test est la partie la moins importante ! Elle est généralement assez triviale, nécessite rarement d'être modifiée, et n'est pas le point central du script de test.

La partie tests du script EST la partie importante, et ceux-ci devraient être exprimés dans une forme qui leur est naturelle, facile à maintenir, facile à lire, et facile à modifier, et aucun de ces aspects ne devrait impliquer de modifier la partie script du script de test en général. Parce que le contenu des tests est la partie importante du script, l'accent doit être mis sur leur lisibilité, même au détriment de la partie script. En règle générale, si la partie script du script de test obscurcit les tests d'une quelconque manière, ce n'est pas écrit correctement !

La solution à cela est bien comprise, et est commune à de nombreux autres systèmes où vous mélangez deux "langages". La tâche de spécifier correctement à la fois les tests et le script de test est pratiquement identique à la tâche de créer un script PHP qui consiste en un mélange de PHP et de HTML, ou la tâche de créer un fichier de modèle utilisant un système de modèle où le fichier consiste en un mélange de texte à afficher et de commandes de modèle. Il est bien compris dans chacun de ces cas que plus les deux "langages" sont entrelacés, moins ils sont lisibles, et plus il est difficile de les maintenir. Plus vous êtes capable de les séparer, plus ils sont faciles à lire et à maintenir.

Autant que possible, je veux que les tests soient écrits dans une sorte de format texte qui peut être facilement vu et modifié (généralement sous forme de tableau simple) sans commandes perl entremêlées. Je veux la liberté de définir les tests dans une section (une longue chaîne, la section DATA, ou même dans un fichier séparé) qui est facilement lisible. Cela peut nécessiter de l'analyser, mais cela rend la maintenance des tests considérablement plus facile.

Cette flexibilité rend beaucoup plus facile la lecture des tests (par opposition au script) qui est le contenu fondamental d'un script de test.

En regardant à nouveau l'exemple de script de test, vous pouvez voir qu'il y a beaucoup trop de code perl entremêlé avec les tests.

Il est difficile de lire les tests individuellement dans ce script car il y a trop de code perl parmi eux, et pratiquement impossible de les regarder dans leur ensemble.

Il est vrai qu'en regardant cet exemple particulier, il est très simple... mais le script N'EST PAS le contenu qui vous intéresse (et gardez à l'esprit que de nombreux scripts de test ne sont pas aussi simples). Le VRAI contenu de ce script sont les tests, qui consistent en les arguments de la fonction et le résultat attendu. Bien qu'il ne soit pas impossible de voir chacun d'eux dans le script ci-dessus, ce n'est pas dans un format propice à l'étude des tests, et encore moins à l'examen de la liste des tests dans son ensemble.

Maintenant, regardez une manière alternative de spécifier les tests à l'aide de ce module :

$tests = "
  apples     bushels   => enough
  grapefruit tons      => enough
  oranges    boatloads => insufficient
  pears      boxes     => enough
  plums      boxes     => enough
  pineapple  boxes     => enough
";
$o->tests(tests => $tests,
          func  => \&func);

Ici, il est facile de voir la liste des tests, et ajouter des tests supplémentaires est un jeu d'enfant.

CRÉATION D'UN TEST

Ce module prend en charge un certain nombre de méthodes pour définir des tests, vous pouvez donc utiliser celle qui est la plus pratique (y compris les méthodes identiques à Test::More si c'est vraiment la meilleure méthode).

Chaque test peut avoir plusieurs informations :

Une

DESCRIPTION

This module provides a framework for writing tests. You can use it to test both your own modules and your scripts.

The primary design goal of this module is to make it easy for you to write tests that will be useful to you. And it has been designed with the following features in mind:

Un nom
Chaque test se voit automatiquement attribuer un numéro, mais il peut être utile de spécifier un nom de test (qui est en fait une courte description du test). Chaque fois qu'un résultat de test est rapporté, le nom sera donné (s'il en a été spécifié un).

Le nom ne peut pas contenir de caractère '#'.

Le nom est complètement facultatif, mais il peut servir à rendre les résultats plus lisibles.

Un résultat attendu
Afin de tester quelque chose, vous devez savoir quel résultat était attendu (ou dans certains cas, quel résultat n'était PAS attendu).
Une fonction et des arguments OU un résultat
Vous devez également connaître les résultats auxquels vous comparez les résultats attendus.

Cela peut être obtenu en travaillant simplement avec un ensemble de résultats, ou un nom de fonction et un ensemble d'arguments à lui passer.

Conditions
Il est utile de pouvoir spécifier des informations d'état au début de la suite de tests (par exemple, pour voir si certaines fonctionnalités sont disponibles), et certains tests ne peuvent être exécutés que si ces conditions sont remplies.

Si aucune condition n'est définie pour un test, il sera toujours exécuté.

Tests TODO
Certains tests peuvent être marqués comme tests 'todo'. Ce sont des tests qui sont autorisés à échouer (ce qui signifie qu'ils ont été mis en place pour une fonctionnalité non encore implémentée). Comme il est attendu que le test échouera, la suite de tests réussira toujours, même si ces tests échouent.

Les tests seront toujours exécutés et s'ils réussissent, un message sera émis indiquant que la fonctionnalité est maintenant implémentée et que les tests devraient être promus à l'état non-todo.

MÉTHODES DE BASE

new
$o = new Test::Inter [$name] [%options];

Cela crée un nouveau framework de test. Plusieurs options peuvent être utilisées pour spécifier quels tests sont exécutés, comment ils sont exécutés, et quel résultat est donné.

L'ensemble du script de test peut être nommé en passant $name.

Toutes les options peuvent être définies de quatre manières différentes.

Premièrement, vous pouvez passer une table de hachage de paires OPT = VAL en dans la méthode new. Ainsi, pour définir l'option start, la table de hachage %options contiendrait :

start => VALEUR

Deuxièmement, vous pouvez définir une variable d'environnement. Cela remplacera toute valeur passée de la première manière. La variable d'environnement est nommée TI_XXX où XXX est l'option entièrement capitalisée. Donc :

$ENV{TI_START} = VALEUR

La troisième méthode, qui remplace les deux précédentes, consiste à définir une variable globale. Elle est également nommée TI_XXX dans l'espace de noms principal, donc pour la définir ainsi, définissez :

$::TI_START = VALEUR

La dernière méthode consiste à appeler l'une des méthodes ci-dessous et celles-ci remplacent toutes les autres méthodes.

Chacune des options autorisées est décrite ci-dessous dans les méthodes de base suivantes :

start
end
testnum
plan
abort
quiet
mode
skip_all
width
use_lib
version
$o->version();

Retourne la version du module.

encoding
$o->encoding($encoding);

$encoding est toute valeur pouvant être passée comme encodage à la fonction Encode::decode de Perl.

Utilisez ceci si vos chaînes de test contiennent des caractères dans d'autres encodages.

start
$o = new Test::Inter 'start' => $N;
$o->start($N)

Pour définir le test avec lequel vous souhaitez commencer, définissez l'option start comme décrit dans la méthode new ci-dessus.

Lorsque le test de départ est défini, la plupart des tests numérotés inférieurs à N sont complètement ignorés. Si les tests sont exécutés silencieusement (voir la méthode quiet ci-dessous), rien n'est imprimé pour ces tests. Sinon, un message de saut est imprimé.

Une classe de tests EST toujours exécutée. Les tests exécutés à l'aide des méthodes require_ok ou use_ok (pour tester le chargement des modules) sont toujours exécutés.

Si aucune valeur (ou une valeur de 0) n'est utilisée, les tests commencent à partir du premier test.

end
$o = new Test::Inter 'end' => $M;
$o->end($M);

Pour définir le test avec lequel vous souhaitez terminer, définissez l'option end comme décrit dans la méthode new ci-dessus.

Lorsque le test de fin est défini, tous les tests numérotés supérieurs à M sont complètement ignorés. Si les tests sont exécutés silencieusement (voir la méthode quiet ci-dessous), rien n'est imprimé pour ces tests. Sinon, un message de saut est imprimé.

Si aucune valeur n'est donnée, elle est par défaut à 0 (ce qui signifie que tous les tests restants sont exécutés).

testnum
$o = new Test::Inter 'testnum' => $N;
$o->testnum($N);

Pour exécuter un seul test, définissez l'option testnum comme décrit dans la méthode new ci-dessus.

C'est équivalent à définir à la fois les tests de début et de fin sur $N.

plan
done_testing
$o = new Test::Inter 'plan' => $N;
$o->plan($n);
$o->done_testing();
$o->done_testing($n);

L'API TAP (le 'langage' utilisé pour exécuter une séquence de tests et voir lesquels ont échoué et lesquels ont réussi) nécessite une déclaration du nombre de tests qui devraient être exécutés.

Cette déclaration peut apparaître au début de la suite de tests, ou à la fin.

Si vous connaissez à l'avance combien de tests doivent s'exécuter dans le script de test, vous pouvez définir l'option plan comme décrit dans la méthode new ci-dessus avec le nombre de tests.

Si vous savez combien de tests doivent s'exécuter à la fin du script de test, vous pouvez passer un entier non nul à la méthode done_testing.

Fréquemment, vous ne vous souciez pas vraiment du nombre de tests dans le script (surtout si de nouveaux tests sont ajoutés régulièrement). Dans ce cas, vous devez toujours inclure une déclaration indiquant que le nombre de tests attendus est le nombre de tests exécutés. Pour ce faire, appelez la méthode done_testing sans argument.

NOTE : si la méthode plan est utilisée, elle DOIT être utilisée avant que des tests ne soient exécutés (y compris ceux qui testent le chargement de modules). Si la méthode done_testing est utilisée, elle DOIT être appelée après l'exécution de tous les tests. Vous devez spécifier un plan ou utiliser une déclaration done_testing, mais vous ne pouvez pas faire les deux.

Il n'est PAS strictement nécessaire de définir un plan si le script n'est exécuté qu'en mode interactif, donc si pour une raison quelconque ce module est utilisé pour des scripts de test qui ne font pas partie d'une suite de tests Perl standard, les déclarations de plan et de done_testing sont facultatives. En fait, le script s'exécutera très bien sans elles... mais un installateur Perl rapportera un échec dans la suite de tests.

abort
$o = new Test::Inter 'abort' => 0/1/2;
$o->abort(0/1/2);

Pour définir comment vous souhaitez qu'un échec soit traité, définissez l'option abort comme décrit dans la méthode new ci-dessus. L'option abort peut prendre une valeur de 0, 1 ou 2.

Si elle est définie sur 1, le script de test s'exécutera sans modification jusqu'à ce qu'un test échoue. À ce moment-là, tous les tests restants seront ignorés. Si elle est définie sur 2, le script de test s'exécutera jusqu'à ce qu'un test échoue, auquel cas il se terminera avec un code d'erreur de 1. Avec une valeur de 0, les tests échoués seront rapportés, mais le script continuera.

Dans les deux cas, les tests todo ne déclencheront PAS le comportement d'abandon.

quiet
$o = new Test::Inter 'quiet' => 0/1/2;
$o->quiet(0/1/2);

Pour définir comment vous souhaitez que les échecs soient rapportés, définissez l'option quiet comme décrit dans la méthode new ci-dessus. L'option quiet peut prendre une valeur de 0, 1 ou 2.

Si elle est définie sur 0 (par défaut), toutes les informations seront imprimées. Si elle est définie sur 1, certaines informations facultatives ne seront pas imprimées. Si elle est définie sur 2, toutes les informations facultatives ne seront pas imprimées.

mode
$o = new Test::Inter 'mode' => MODE;
$o->mode(MODE);

Les scripts Test::Inter peuvent être exécutés soit en mode interactif, soit dans le cadre d'une suite de tests avec des comportements différents. Pour sélectionner le mode, définissez l'option mode comme décrit dans la méthode new ci-dessus. L'option mode peut prendre une valeur de 'inter' ou 'test'.

Lorsqu'il est exécuté en mode test, il imprime les résultats en utilisant la grammaire TAP (c'est-à-dire 'ok 1', 'not ok 3', etc.).

Lorsqu'il est exécuté en mode interactif, il imprime les résultats dans un format plus lisible par l'homme.

width
$o = new Test::Inter 'width' => WIDTH;
$o->width(WIDTH);

L'option width peut être définie comme décrit dans la méthode new ci-dessus.

WIDTH est la largeur du terminal (pour l'impression des informations sur les tests échoués). Elle est par défaut à 80, mais elle peut être définie sur n'importe quelle largeur (et les lignes plus longues que cela sont tronquées). Si WIDTH est défini sur 0, aucune troncature n'est effectuée.

use_lib
$o = new Test::Inter 'use_lib' => VALUE;
$o->use_lib(VALUE);
$o->use_lib();

Par défaut, la bibliothèque incluse dans la distribution du module sera ajoutée au chemin de recherche des modules, donc une ligne 'use MODULE' devrait trouver la version stockée dans cette distribution de module.

Si VALUE est défini sur 'off', le chemin de recherche ne sera pas modifié automatiquement.

Vous pouvez ajouter le chemin de la bibliothèque plus tard en appelant :

$o->use_lib('on');
$o->use_lib();

Note : les deux appels doivent être utilisés. Le premier définit l'option, le second modifie effectivement le chemin de recherche.

skip_all
$o->skip_all($reason);

Pour ignorer tous les tests, vous pouvez appeler la méthode skip_all avec une raison facultative.

skip_all 
$o = new Test::Inter 'skip_all' => REASON;
$o->skip_all(REASON);

The skip_all option can be set as described in the new method above.

If this option is set, the whole test script will be skipped for the given reason. This operation must be performed before running any tests and before setting any plan number.

The skip_all option can be called at any time during the script (i.e. after tests have been run). In this case, all remaining scripts will be skipped.

$o->skip_all(REASON,FEATURE,FEATURE,...);
$o->skip_all('',FEATURE,FEATURE,...);

This code will skip all tests (or all remaining ones) unless all of the FEATUREs are available. REASON can be entered as an empty string and the reason for skipping will be a message about the lack of the FEATURE.

feature
$o->feature($feature,$val);

This defines a FEATURE. If $val is non-zero, the FEATURE is available. Otherwise, it is not.

diag
note
$o->diag($message);
$o->note($message);

Both methods print an optional message. Messages printed with the "note" method are always optional and are omitted if quiet is set to 1 or 2. Messages printed with the "diag" method are optional and are not printed if quiet is set to 2, but are printed if quiet is set to 1.

testdir
$o->testdir();
$o->testdir('mod');
$o->testdir('lib');

Sometimes, it may be necessary to know the directory where Test::Inter gets some of its information. By default, the directory containing the tests is returned, but if the optional argument 'mod' is included, the path to the distribution directory (which must include both a 'lib' and a 't' directory) is returned. If the argument 'lib' is included, the directory where the libraries are stored is returned.

METHODS FOR LOADING MODULES

Test scripts may load other modules (using perl "use" or "require" statements). There are three different modes for performing this operation, which determine how it is performed.

required
By default, this option is used to check that a module is necessary for all tests in the test script.

The loading of the module is treated as a test in the test suite. The test is to determine if the module is available and can be loaded. If it can be loaded, it is considered successful. If it cannot be loaded, it is reported as failed.

In the result of a failed test, all remaining tests will be skipped automatically (except for tests that load modules).

feature
In the feature mode, the loading of the module is not treated as a test (i.e., an "ok" or "not ok" will not be printed). Instead, a FEATURE (with the same name as the module) will be set, which can be used to determine if other tests should be run or not.
forbid
In some rare cases, we may wish to discard that a module is present, but make it fail if it is. This is the opposite of the required mode.

Successful loading of the module is treated as a failing test. In case of failure, all remaining tests will be skipped.

The available methods are:

require_ok
$o->require_ok($module [,$mode]);

This method is used to load a module with Perl's "require" function. If $mode is not passed, the default mode (required) is used to check for the module's existence.

If $mode is passed, it must be the string 'forbid' or 'feature'.

If $mode is passed as 'feature', a FEATURE named $module will be set if the module can be loaded.

use_ok
$o->use_ok(@args [,$mode]);

This method is used to load a module with "use" or check the Perl version.

BEGIN { $o->use_ok('5.010'); }
BEGIN { $o->use_ok('Some::Module'); }
BEGIN { $o->use_ok('Some::Module',2.05); }
BEGIN { $o->use_ok('Some::Module','foo','bar'); }
BEGIN { $o->use_ok('Some::Module',2.05,'foo','bar'); }

These are equivalent to:

use 5.010;
use Some::Module;
use Some::Module 2.05;
use Some::Module qw(foo bar);
use Some::Module 2.05 qw(foo bar);

Placing the use_ok call in a BEGIN block allows importing functions at compile time and correctly honoring prototypes. You will also need to load the Test::Inter module and create the object in a BEGIN block.

The $mode acts the same as in the require_ok method.

METHODS FOR RUNNING TESTS

There are several methods for running tests. The ok, is, and isnt methods are included for those already accustomed to Test::More and wishing to maintain the same test script format. The tests method is the recommended method although it utilizes the full power of this module.

ok
$o->ok(TESTS);

A test run with ok examines the result and if the evaluation is 0 (or false), it fails. If it is non-zero (or true), it passes.

These tests do not require specifying expected results. If expected results are specified, they are compared with the obtained results and, if they differ, a diagnostic message will be printed, but the test will still pass or fail based solely on the actual result.

These tests require a single result and zero or one expected.

To run a single test, you can use any of the following:

$o->ok();          # always passes
$o->ok($result);
$o->ok($result,$name);
$o->ok($result,$expected,$name);
$o->ok(\&func);
$o->ok(\&func,$name);
$o->ok(\&func,$expected,$name);
$o->ok(\&func,\@args);
$o->ok(\&func,\@args,$name);
$o->ok(\&func,\@args,$expected,$name);

If $result is a scalar, the test passes if $result is true. If $result is a list reference, the test passes if the list contains at least one defined value. If $result is a hash reference, the test passes if the hash contains at least one key with an undefined ("undef") value.

If an expected value is passed and the result does not match, a diagnostic warning message will be printed, even if the test passes.

is
isnt
$o->is(TESTS);
$o->isnt(TESTS);

A test run with is examines the result and tests if it is identical to an expected result. If so, the test passes. Otherwise, it fails. In case of failure, the obtained and expected results will be displayed.

A test run with isnt examines the result and tests if the obtained result is different from an expected result. If it is different, the test passes. Otherwise, it fails.

The is method can be called in several ways:

$o->is($result,$expected);
$o->is($result,$expected,$name);
$o->is(\&func,$expected);
$o->is(\&func,$expected,$name);
$o->is(\&func,\@args,$expected);
$o->is(\&func,\@args,$expected,$name);

The isnt method can be called in exactly the same way.

As with the ok method, the result can be a scalar, a hash, or a list. If it is a hash or a list, the entire structure must match the expected value.

tests
$o->tests($opt=>$val, $opt=>$val, ...)

The available options are described in the following section.

file
$o->file($func,$input,$outputdir,$expected,$name [,@args]);

Sometimes, it is easier to store the input, output, and expected output of a test in a text file. In this case, each line of output is treated as an individual test, so the output and expected output must match exactly.

The $func is a reference to a function that produces a temporary output file.

If $input is specified, it is the name of the input file. If it is empty, no input file is used. The input file can be fully specified or be relative to the test directory.

If $outputdir is passed, it is the directory where the output file will be written. It can be fully specified or be relative to the test directory. If $outputdir is empty, the temporary file is created in the test directory.

UTILISATION DE LA MÉTHODE TESTS

La plupart des tests (à l'exception de ceux qui chargent un module) sont censés être exécutés en utilisant la méthode de tests nommée comme suit :

$o->tests(%options);

Les options suivantes sont disponibles :

name
name => NAME

Ceci définit le nom de cet ensemble de tests. Tous les tests auront le même nom.

tests
func
expected
Pour spécifier un ensemble de tests, vous devez soit spécifier une fonction et une liste d'arguments, soit une liste de résultats.

Spécifier la fonction et la liste d'arguments peut se faire en utilisant la paire :

func  => \&FUNCTION
tests => TESTS

Si l'option func n'est pas définie, tests contient une liste de résultats.

Une liste de résultats attendus peut également être fournie. Ceux-ci peuvent être inclus dans l'option

tests => TESTS

ou inclus séparément sous la forme :

expected => RESULTS

La manière de spécifier ceux-ci est couverte dans la section suivante SPÉCIFICATION DES TESTS.

feature
disable
feature => [FEATURE1, FEATURE2, ...]
disable => [FEATURE1, FEATURE2, ...]

L'ensemble de tests par défaut qui est exécuté est déterminé en utilisant les méthodes start, end et skip_all discutées précédemment. En utilisant ces méthodes, une liste de tests est obtenue et ceux-ci sont censés être exécutés.

Les options feature et disable modifient la liste.

Si l'option feature est incluse, les tests donnés dans cet appel ne seront exécutés que si toutes les caractéristiques listées sont disponibles.

Si l'option disable est incluse, les tests seront exécutés à moins qu'une des caractéristiques listées ne soit disponible.

skip
skip => REASON

Saute ces tests pour la raison donnée.

todo
todo => 0/1

Définir ceci à 1 indique que ces tests sont autorisés à échouer. Cela représente une fonctionnalité qui n'est pas encore implémentée.

Si les tests réussissent, un message sera imprimé informant le développeur que les tests sont prêts à être promus pour une utilisation actuelle.

SPÉCIFICATION DES TESTS

Un ensemble de tests peut être spécifié de deux manières différentes. Les tests peuvent être écrits dans un format très simple ou stockés sous forme de liste.

Démontrer comment cela peut être fait est mieux par un exemple, alors supposons qu'il existe une fonction (func) qui prend deux arguments et renvoie une seule valeur. Supposons que le résultat attendu (et le résultat réel) de trois ensembles d'arguments différents est :

Entrée   Sortie Attendue  Sortie Réelle
-----   -------------  -------------
1,2     a              a
3,4     b              x
5,6     c              c

(donc dans ce cas, le premier et le troisième test réussissent, mais le second échoue).

Spécifier ces tests sous forme de listes pourrait se faire ainsi :

$o->tests(
   func     => \&func,
   tests   => [ [1,2], [3,4], [5,6] ],
   expected => [ [a],   [b],   [c] ],
);

Ici, les tests sont stockés sous forme de liste, et chaque élément de la liste contient une référence à la liste des arguments.

Si l'option func n'est pas passée, l'option tests est définie comme une liste de résultats à comparer aux résultats attendus, donc ce qui suit est équivalent à ce qui précède :

$o->tests(
   tests   => [ [a],   [x],   [c] ],
   expected => [ [a],   [b],   [c] ],
);

Si un argument (ou résultat actuel) ou un résultat attendu n'est qu'une seule valeur, il peut être entré comme un scalaire au lieu d'une référence de tableau, donc ce qui suit est également équivalent :

$o->tests(
   func     => \&func,
   tests   => [ [1,2], [3,4], [5,6] ],
   expected => [ a,     b,     [c] ],
);

La seule exception est si la valeur est juste une référence de tableau. Dans ce cas, elle doit être incluse comme une référence. En d'autres termes, si vous avez un seul test et que la valeur attendue pour ce test est une référence de tableau, elle doit être passée comme :

expected => [ [ \@r ] ]

Pas comme :

expected => [ \@r ]

L'inclusion d'un ensemble de résultats attendus est facultative. Si aucun résultat n'est passé, cela est traité comme si les résultats étaient passés à la méthode ok (c'est-à-dire, s'ils renvoient quelque chose de vrai, ils réussissent, sinon ils échouent).

La deuxième manière de spécifier les tests est sous forme de chaîne. La chaîne est une chaîne multiligne où chaque test est séparé par une ligne vide. Les commentaires (lignes commençant par #) sont autorisés et sont ignorés. Les espaces blancs au début et à la fin de la ligne sont ignorés.

La chaîne peut inclure les résultats directement, ou les résultats peuvent être passés séparément. Par exemple, les lignes suivantes donnent les mêmes ensembles de tests que l'exemple précédent :

$o->tests(
   func     => \&func,
   tests   => "
                # Test 1
                1 2 => a
                # Test 2
                3 4 => b
                5 6 => c
               ",
);
$o->tests(
   func     => \&func,
   tests   => "
                1 2
                3 4
                5 6
               ",
    expected => [ [a], [b], [c] ]
);
$o->tests(
   func     => \&func,
   tests   => [ [1,2], [3,4], [5,6] ],
    expected => "
                a
                b
                c
               ",
);
$o->tests(
   func     => \&func,
   tests   => "
                1 2
                3 4
                5 6
               ",
    expected => "
                a
                b
                c
               ",
);

Les résultats attendus peuvent consister uniquement en un ensemble de résultats (dans ce cas, il doit être passé sous forme de liste de références). Dans ce cas, tous les tests sont censés produire les mêmes résultats.

Par conséquent, les lignes suivantes sont équivalentes :

$o->tests(
   func     => \&func,
   tests   => "
                1 2 => a b
                3 4 => a b
                5 6 => a b
               ",
);
$o->tests(
   func     => \&func,
   tests   => "
                1 2
                3 4
                5 6
               ",
    expected => [ [a, b] ],
);
$o->tests(
   func     => \&func,
   tests   => "
                1 2
                3 4
                5 6
               ",
    expected => "a b",
);

Le nombre de valeurs attendues doit être de 1 (c'est-à-dire que tous les tests sont censés produire la même valeur) ou exactement le même nombre que le nombre de tests.

Le parseur est en fait assez puissant et peut gérer des tests multilignes, des chaînes entre guillemets et des structures imbriquées.

Le test peut être divisé en n'importe quel nombre de lignes, tant qu'il n'y a pas de ligne complètement vide (qui signale la fin du test), donc les lignes suivantes sont équivalentes :

tests => "a b c",
tests => "a b
          c",

Les arguments (ou résultats attendus) peuvent inclure des structures de données. Par exemple, les lignes suivantes sont équivalentes :

tests => "[ a b ] { a 1 b 2 }"
tests => [ [ [a,b], { a=>1, b=>2 } ] ]

L'espace est facultatif, mais il y a une exception. Un élément doit se terminer par un type de délimiteur, donc la ligne suivante échouera :

tests => "[a b][c d]"

Le premier élément (la référence de tableau [a b]) doit être séparé du deuxième élément par le délimiteur (qui est l'espace blanc dans ce cas), il doit donc être écrit comme :

tests => "[a b] [c d]"

Bien que les parenthèses soient facultatives, elles peuvent rendre la lecture plus facile et permettre d'utiliser autre chose que l'espace blanc comme délimiteur. Puisque les parenthèses sont ignorées, une chaîne comme BAq()' est également ignorée, n'utilisez donc pas de parenthèses vides.

Si le caractère immédiatement après l'ouverture d'une parenthèse, d'un crochet ou d'une accolade est un caractère de ponctuation, alors il est utilisé comme délimiteur à la place de l'espace blanc. Par exemple, les lignes suivantes sont toutes équivalentes :

[ a b c ]
[a b c]
[, a,b,c ]
[, a, b, c ]

Un délimiteur est un seul caractère, et les lignes suivantes ne peuvent pas être utilisées comme délimiteur :

tout caractère ouvrant/fermant () [] {}'
guillemets simples ou doubles
tout caractère alphanumérique
underscore

L'espace (y compris les espaces blancs) autour du délimiteur est ignoré, donc la ligne suivante est valide :

[, a,
   b,
   c ]

Deux délimiteurs consécutifs ou un délimiteur à la fin produisent une chaîne vide.

"(,a,b,)" => (a, b, '')
"(,a,,b)" => (a, '', b)

Les références de hachage peuvent être spécifiées en utilisant des accolades et sont équivalentes à :

{ a 1 b 2 }
{, a,1,b,2 }
{, a,1,b,2, }

Note : S'il y a un nombre pair d'éléments, le délimiteur final est ignoré, ou s'il y a une chaîne vide, le délimiteur final est ignoré.

Les structures imbriquées sont autorisées :

"[ [1 2] [3 4] ]"

$o->tests(
   func     => \&func,
   tests   => "a [ b c ] { d 1 e 2 } =&g

NAME

Test::Inter - A module for writing interactive tests in perl

DESCRIPTION

This module is designed to make it easier to write interactive tests in perl. The module allows you to write your tests in a human-readable format that can be easily understood and modified by anyone.

The module provides a flexible way to define and run tests, allowing you to specify arguments, expected results, and even custom functions to be called during the test execution.

INTERACTIVE EXECUTION

Tests are run interactively by default. This means that after each test is executed, the user is prompted to indicate whether the test passed or failed. This allows for manual verification of test results.

$ ./my_test_script.t
test 1... ok? [y/n] y
test 2... ok? [y/n] n
test 3... ok? [y/n] y
...

READABLE TESTS

The tests themselves are written in a format that is designed to be readable. Each test is defined as a string, which is then parsed by the module. This allows for a concise and clear representation of the tests.

my $tests = q(
    test 1: Does this work?
        arg1: hello
        arg2: world
    test 2: Does that work?
        arg1: foo
        arg2: bar
);

CREATING A TEST

You create tests by calling the tests method of the Test::Inter object. The arguments to this method are a series of hashes, where each hash represents a single test.

Each test hash can contain the following keys:

name
The name of the test (optional).
func
A reference to a subroutine that will be called to perform the test. If this is not provided, the test will be considered to be a simple comparison.
args
An array reference containing the arguments to be passed to the test function.
tests
An array reference containing the data to be tested. Each element in this array can be a simple value, an array reference, or a hash reference.
results
An array reference containing the expected results for each test case. The structure of this array should mirror the structure of the tests argument.

Example:

$o->tests(
    name => 'Test 1',
    func => \&my_test_function,
    args => [ 'arg1', 'arg2' ],
    tests => [
        [ 'a', [ 'b', 'c' ], { d => 1, e => 2 } ],
    ],
    results => [
        [ 'x', [ 'y', 'z' ], { f => 3, g => 4 } ],
    ],
);

BASE METHODS

The following methods are available from the base Test::Inter class:

new()
Creates a new Test::Inter object.
load_modules()
Loads the specified modules.
run_tests()
Runs the tests defined in the object.
tests()
Defines the tests to be run.

METHODS FOR LOADING MODULES

The load_modules() method can be used to load any perl modules that your tests may depend on. The method takes a list of module names as arguments.

$o->load_modules( 'Test::More', 'Data::Dumper' );

METHODS FOR RUNNING TEST

The run_tests() method executes all the tests that have been defined using the tests() method.

USING THE TESTS METHOD

The tests() method is used to define the tests that will be executed. It takes a hash reference as an argument, where the keys specify the test parameters and the values specify the test data.

The tests() method can be called multiple times to add more tests to the test suite.

$o->tests(
    name => 'Test 1',
    tests => [ 'hello', 'world' ],
    results => [ 'goodbye', 'universe' ],
);
$o->tests(
    name => 'Test 2',
    tests => [ 1, 2, 3 ],
    results => [ 4, 5, 6 ],
);

SPECIFYING THE TESTS

The tests themselves can be specified in a variety of ways. The most common way is to provide a list of values that will be passed to the test function.

$o->tests(
   func     => \&func,
   tests    => [ [a, [b,c], {d=>1,e=>2}] ],
   results  => [ [x,y] ],
);

Any single value can be surrounded by single or double quotes in order to include the delimiter. So:

"(, a,'b,c',e )"

is equivalent to:

"( a b,c e )"

Any single value can be the string '__undef__' which will be turned into an actual undef. If the value is '__blank__' it is turned into an empty string (''), though it can also be specified as '' directly. Any value can have an embedded newline by including a __nl__ in the value, but the value must be written on a single line.

Expected results are separated from arguments by ' => '.

TEST::INTER VARIABLES

To summarize the information above, the following variables are used by Test::Inter. Each variable can be set in two different ways: as an environment variable and as a perl variable in the main namespace.

For example, the TI_END variable can be set as:

$::TI_END
$ENV{TI_END}

The following variables can be used to define which tests are run:

TI_START
Set this to define the test you want to start with.

Example: If you have a perl test script and you want to start running it at test 12, run the following shell commands:

TI_START=12
./my_test_script.t
TI_END
Set this to define the test you want to end with.
TI_TESTNUM
Set this to run only a single test

There is also a variable TI_NUM (available only as $::TI_NUM) which is set automatically by Test::Inter to be the test currently being run.

The following variables control what is output from the tests, and how it is formatted:

TI_QUIET
How verbose the test script is. Values are 0 (most verbose) to 2 (least verbose).
TI_MODE
How the output is formatted. Values are 'inter' (interactive mode) or 'test' (test suite mode). Interactive mode is easier to read. Test mode is for running as part of a test suite.
TI_WIDTH
The width of the terminal.

The following variables control how some tests are run:

TI_NOCLEAN
When running a file test, the temporary output file will not be removed if this is set.

HISTORY

The history of this module dates back to 1996 when I needed to write a test suite for my Date::Manip module. At that time, none of the Test::* modules currently available in CPAN existed (the earliest ones didn't come along until 1998), so I was left completely on my own writing my test scripts.

I wrote a very basic version of my test framework which allowed me to write all of the tests as a string, it would parse the string, count the tests, and then run them.

Over the years, the functionality I wanted grew, and periodically, I'd go back and reexamine other Test frameworks (primarily Test::More) to see if I could replace my framework with an existing module... and I've always found them wanting, and chosen to extend my existing framework instead.

As I've written other modules, I've wanted to use the framework in them too, so I've always just copied it in, but this is obviously tedious and error prone. I'm not sure why it took me so long... but in 2010, I finally decided it was time to rework the framework in a module form.

I loosely based my module on Test::More. I like the functionality of that module, and wanted most of it (and I plan on adding more in future versions). So this module uses some similar syntax to Test::More (though it allows a great deal more flexibility in how the tests are specified).

One thing to note is that I may have been able to write this module as an extension to Test::More, but after looking into that possibility, I decided that it would be faster to not do that. I did "borrow" a couple of routines from it (though they've been modified quite heavily) as a starting point for a few of the functions in this module, and I thank the authors of Test::More for their work.
