Test2::Manual::Anatomy::Event(3perl) Guide de référence des programmeurs Perl Test2::Manual::Anatomy::Event(3perl)

NOM

Test2::Manual::Anatomy::Event - Les internes des événements

DESCRIPTION

Les événements sont la manière dont les outils affectent l'état global et transmettent des informations au système de gestion des tests ou à la personne qui exécute les tests.

HISTORIQUE

Avant de continuer, il est important que vous connaissiez l'historique des événements. Initialement, il y avait une API d'événements, et un événement implémentait cette API pour produire un effet. Cette API s'est avérée verbeuse et inflexible. Récemment, le système de 'facettes' a été introduit, et il compense les lacunes et l'inflexibilité de l'ancienne API.

Tous les événements doivent toujours implémenter l'ancienne API, mais cela peut être largement automatisé si vous utilisez efficacement le système de facettes. De même, les facettes essentielles peuvent souvent être déduites à partir d'événements qui implémentent uniquement l'ancienne API, bien que leurs informations puissent être moins complètes.

L'OBJET ÉVÉNEMENT

Tous les objets événements doivent hériter de Test2::Event. Si vous héritez de cette classe de base et implémentez correctement l'ancienne API, les facettes seront générées gratuitement pour vous. D'autre part, vous pouvez hériter de celle-ci et importer également Test2::Util::Facets2Legacy, qui s'appuiera alors sur vos données de facettes et en déduira l'ancienne API.

Tous les nouveaux événements "DOIVENT" implémenter les deux API, d'une manière ou d'une autre. Une manière courante de le faire est de simplement implémenter les deux API directement dans votre événement.

Voici un bon modèle pour un nouvel événement :

package Test2::Event::Mine;
use strict;
use warnings;
use parent 'Test2::Event';
use Test2::Util::Facets2Legacy ':ALL';
sub facet_data {
    my $self = shift;
    # Ajoute les facettes 'about', 'amnesty', et 'trace'
    my $out = $self->common_facet_data;
    # Ajoutez toutes les facettes supplémentaires au hashref $out
    ...
    return $out;
}
1;

L'API DES FACETTES

La nouvelle API est une méthode unique : facet_data(). Cette méthode doit retourner un hashref où chaque clé est spécifique à un type de facette, et la valeur est soit un hashref de facette, soit un tableau de hashrefs. Certaines facettes "DOIVENT" être des hashrefs seuls, d'autres "DOIVENT" être des hashrefs à l'intérieur d'un arrayref.

Les types de facettes *standard* sont les suivants :

assert => {details => $name, pass => $bool, no_debug => $bool, number => $maybe_int}
Documenté dans Test2::EventFacet::Assert. Un événement ne peut en avoir qu'un seul.

La clé 'details' est le nom de l'assertion.

La clé 'pass' indique une assertion réussie ou échouée.

La clé 'no_debug' indique à tout système de gestion ou formatteur que des diagnostics ne doivent pas être ajoutés automatiquement à une assertion échouée (utilisé lorsqu'il existe des diagnostics personnalisés à la place).

La clé 'number' est pour l'usage du système de gestion, ne la définissez jamais vous-même.

about => {details => $string, no_display => $bool, package => $pkg}
Documenté dans Test2::EventFacet::About. Un événement ne peut en avoir qu'un seul.

'details' est une chaîne lisible par l'homme décrivant l'événement global.

'no_display' signifie qu'un formatteur/système de gestion doit masquer l'événement.

'package' est le package de l'événement que la facette décrit (c'est-à-dire : Test2::Event::Ok)

amnesty => [{details => $string, tag => $short_string, inherited => $bool}]
Documenté dans Test2::EventFacet::Amnesty. Un événement peut en avoir plusieurs.

Cet événement est la manière dont les choses comme 'todo' sont implémentées. L'amnistie empêche une assertion échouée de provoquer un échec global des tests.

'details' est une description lisible par l'homme expliquant pourquoi l'échec se voit accorder une amnistie (par exemple : la raison du 'todo')

'tag' est une chaîne courte lisible par l'homme, ou une catégorie pour l'amnistie. C'est généralement 'TODO' ou 'SKIP'.

'inherited' est vrai si l'amnistie a été appliquée dans un contexte parent (vrai si ce test est exécuté dans un sous-test marqué comme todo).

control => {details => $string, global => $bool, terminate => $maybe_int, halt => $bool, has_callback => $bool, encoding => $enc}
Documenté dans Test2::EventFacet::Control. Un événement peut en avoir un.

Cette facette est utilisée pour appliquer un comportement supplémentaire lorsque l'événement est traité.

'details' est une explication lisible par l'homme pour le comportement.

'global' vrai si cet événement doit être transmis et traité par tous les hubs, partout. (bail-out utilise ceci)

'terminate' ceci devrait être soit undef, soit un entier. Lorsqu'il est défini, cela provoquera la sortie du test avec le code de sortie spécifique.

'halt' est utilisé pour signaler à tout système de gestion qu'aucun autre fichier de test ne doit être exécuté (bail-out utilise ceci).

'has_callback' est défini sur vrai si l'événement a une sous-routine de rappel définie.

'encoding' utilisé pour indiquer au formateur quel encodage utiliser.

errors => [{details => $string, tag => $short_string, fail => $bool}]
Documenté dans Test2::EventFacet::Error. Un événement peut en avoir plusieurs.

'details' est une explication lisible par l'homme de l'erreur.

'tag' est une courte catégorie lisible par l'homme pour l'erreur.

'fail' est vrai si l'erreur doit provoquer un échec du test. Si c'est faux, l'erreur est simplement informative, mais pas fatale.

info => [{details => $string, tag => $short_string, debug => $bool, important => $bool}]
Documenté dans Test2::EventFacet::Info. Un événement peut en avoir plusieurs.

C'est ainsi que diag et note sont implémentés.

'details' message lisible par l'homme.

'tag' courte catégorie pour le message, comme 'diag' ou 'note'.

'debug' est vrai si le message est de nature diagnostique, c'est la principale différence entre une note et un diagnostic.

'important' est vrai si le message n'est pas un diagnostic, mais qu'il est important de l'afficher de toute façon. Ceci est principalement utilisé pour communiquer avec un système de gestion.

parent => {details => $string, hid => $hid, children => [...], buffered => 1}
Documenté dans Test2::EventFacet::Parent. Un événement peut en avoir un.

Ceci est utilisé par les sous-tests.

'details' nom lisible par l'homme du sous-test.

'hid' identifiant du hub du sous-test.

'children' un arrayref contenant les instances de facet_data de tous les événements enfants.

'buffered' vrai s'il s'agissait d'un sous-test mis en mémoire tampon.

plan => {details => $string, count => $int, skip => $bool, none => $bool}
Documenté dans Test2::EventFacet::Plan. Un événement peut en avoir un.

'details' est une chaîne lisible par l'homme décrivant le plan (par exemple, pourquoi un test est sauté)

'count' est le nombre d'assertions attendues (0 pour le saut)

'skip' est vrai si le plan est de sauter le test.

'none' utilisé pour le plan 'no_plan' de Test::More.

trace => {details => $string, frame => [$pkg, $file, $line, $sub], pid => $int, tid => $int, cid => $cid, hid => $hid, nested => $int, buffered => $bool}
Documenté dans Test2::EventFacet::Trace. Un événement peut en avoir un.

C'est ainsi que les informations de débogage sont suivies. Ceci est extrait de l'objet contexte au moment de la création de l'événement.

'details' message de débogage lisible par l'homme (sinon généré à partir du frame)

'frame' les 4 premiers champs retournés par caller : "[$package, $file, $line, $subname]".

'pid' l'identifiant du processus dans lequel l'événement a été créé.

'tid' le thread dans lequel l'événement a été créé.

'cid' l'identifiant du contexte utilisé pour créer l'événement.

'hid' l'identifiant du hub auquel l'événement a été envoyé.

'nest' profondeur d'imbrication du sous-test de l'événement.

'buffered' est vrai si l'événement a été généré à l'intérieur d'un sous-test mis en mémoire tampon.

FACETTES PERSONNALISÉES

Vous pouvez écrire vos propres types de facettes, il suffit d'ajouter une nouvelle clé à la hash et de la remplir. La règle générale est que tout code qui voit des facettes doit ignorer celles qu'il ne comprend pas.

Vous pouvez éventuellement créer un paquet pour documenter vos facettes personnalisées. Le paquet doit être un objet valide et peut avoir des méthodes supplémentaires pour aider à travailler avec votre facette.

package Test2::EventFacet::MyFacet;
use parent 'Test2::EventFacet';
sub facet_key { 'myfacet' }
sub is_list { 0 }
1;

Votre paquet de facette doit toujours être sous l'espace de noms Test2::EventFacet:: si vous voulez que les outils le trouvent automatiquement. La dernière partie du nom de l'espace doit être le nom non pluriel de votre facette, avec seulement le premier mot en majuscule.

$string = $facet_class->facet_key
La clé de votre facette doit être la même que la dernière partie de l'espace de noms, mais en minuscules. Vous pouvez ajouter un 's' à la clé si votre facette est de type liste.
$bool = $facet_class->is_list
True si un événement doit placer ces facettes dans une liste : 
{ myfacet => [{}, {}] }

False si un événement ne peut avoir qu'une seule de ce type de facette à la fois :

{ myfacet => {} }

EXEMPLES

La facette assert n'est pas une liste, donc son implémentation ressemblerait à ceci :

package Test2::EventFacet::Assert;
sub facet_key { 'assert' }
sub is_list { 0 }

La facette amnesty est une liste, mais n'a pas besoin d'un 's' ajouté pour être plurielle :

package Test2::EventFacet::Amnesty;
sub facet_key { 'amnesty' }
sub is_list { 1 }

La facette error est une liste, et l'ajout de 's' rend error pluriel. Cela signifie que le nom du paquet est '::Error', mais la clé est 'errors'.

package Test2::EventFacet::Error;
sub facet_key { 'errors' }
sub is_list { 1 }

Note2: En pratique, la plupart des outils ignorent les paquets de facettes et travaillent directement avec les données de la facette dans leur structure. C'est par conception et recommandé. Les données de facette sont conçues pour être fréquemment sérialisées et échangées. Lorsqu'il s'agit de facettes, les données sont importantes, les classes et les méthodes ne le sont pas.

L'ANCIENNE API

L'ancienne API était simplement un ensemble de méthodes que vous deviez implémenter :

$bool = $e->causes_fail
Retourne true si cet événement doit entraîner un échec de test. En général, cela devrait être false.
$bool = $e->increments_count
Vous devez retourner true si cet événement doit provoquer une augmentation du compteur de tests.
$e->callback($hub)
Si votre événement doit avoir des effets supplémentaires sur le Test2::Hub, vous pouvez remplacer cette méthode.

Cette méthode est appelée AVANT que l'événement ne soit passé au formateur.

$num = $e->nested
Si cet événement se trouve à l'intérieur d'autres événements, il doit indiquer le niveau d'imbrication. (Ceci est principalement pour les sous-tests)
$bool = $e->global
Définissez ceci sur true si votre événement est global, c'est-à-dire que tous les threads et processus doivent le voir, où qu'il soit généré. Ce n'est pas courant, mais est utilisé pour les sorties de test avec bail-out et skip_all.
$code = $e->terminate
Ceci est appelé APRÈS que l'événement ait été passé au formateur. Il devrait normalement retourner undef, mais ne changez que si l'événement doit faire se terminer le test immédiatement.

Si vous voulez que l'événement provoque la fin du test, vous devriez retourner le code de sortie ici. Un code de sortie de 0 signifie succès, tout autre nombre signifie échec.

Ceci est utilisé par Test2::Event::Plan pour sortir avec 0 lorsque le plan est 'skip_all'. Il est également utilisé par Test2::Event:Bail pour forcer la fin du test avec un échec.

Ceci est appelé après que l'événement ait été envoyé au formateur pour s'assurer que l'événement soit vu et compris.

$msg = $e->summary
Ceci est utilisé comme un résumé humain de l'événement. Vous devriez idéalement avoir un résumé d'une ligne, mais vous pouvez en utiliser plusieurs si nécessaire. Ceci est utilisé pour la consommation humaine. Vous n'avez pas besoin de le rendre facile pour les machines.

Par défaut, il renvoie simplement le nom du paquet de l'événement.

($count, $directive, $reason) = $e->sets_plan()
Vérifie si cet événement définit le plan de test. Renverra une liste vide s'il ne le fait pas. S'il le fait, il renverra une liste de 1 à 3 éléments dans l'ordre : le nombre de tests attendus, la directive, la raison de la directive.
$bool = $e->diagnostics
True si l'événement contient des informations de diagnostic. Ceci est utile car un système de test non verbeux peut choisir de masquer les événements qui ne relèvent pas de cette catégorie. Certains formateurs peuvent choisir d'envoyer ceux-ci à STDERR au lieu de STDOUT pour s'assurer qu'ils sont vus.
$bool = $e->no_display
False par défaut. Ceci renverra true pour les événements qui ne doivent pas être affichés par les formateurs.
