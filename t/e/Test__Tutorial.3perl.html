Test::Tutorial(3perl) Manuel de référence Perl Test::Tutorial(3perl)

NOM

Test::Tutorial - Un tutoriel sur la manière d'écrire des tests vraiment basiques

DESCRIPTION

AHHHHHHH !!!! PAS DE TESTS ! TOUT LE CONTRAIRE DE TESTER ! Battez-moi, frappez-moi dans le dos, emmenez-moi à Détroit, mais ne me faites pas écrire de tests !

*sniff*

De plus, je ne sais pas comment écrire ces choses.

Est-ce vous ? Écrire des tests est-il tout simplement à la hauteur d'écrire de la documentation et de vous faire arracher les ongles ? Avez-vous ouvert un test et lu

######## nous commençons avec un peu de mystère

et avez décidé que c'était suffisant pour vous ?

C'est bien, ça arrive. Nous avons tous vécu ce mystère. Et voici les astuces...

NOIX ET BOULONS DES TESTS.

Voici le programme de test le plus basique.

#!/usr/bin/perl -w
print "1..1\n";
print 1 + 1 == 2 ? "ok 1\n" : "not ok 1\n";

Parce que 1 + 1 font 2, il imprime :

1..1
ok 1

Ce que cela dit, c'est : 1..1 "J'attends d'exécuter un test." [1] "ok 1" "Le premier test a réussi." Et c'est toute la magie du test. Votre unité de test de base est ok. Pour chaque chose que vous testez, vous imprimez un "ok". Simple. Test::Harness interprète les résultats de vos tests pour déterminer si vous avez réussi ou échoué (plus d'informations plus tard).

Écrire autant de `print` rapidement devient fastidieux. Heureusement, il existe Test::Simple. Il a une fonction, ok().

#!/usr/bin/perl -w
use Test::Simple tests => 1;
ok( 1 + 1 == 2 );

Cela fait la même chose que le code précédent. ok() est la base du test Perl, et nous l'utiliserons à la place d'écrire le nôtre à partir de maintenant. Si ok() reçoit une valeur vraie, le test réussit. Faux, il échoue.

#!/usr/bin/perl -w
use Test::Simple tests => 2;
ok( 1 + 1 == 2 );
ok( 2 + 2 == 5 );

D'où vient :

1..2
ok 1
not ok 2
#     Test échoué (test.pl ligne 5)
#     Il semble qu'il y ait 1 test échoué sur 2.

1..2 "J'attends d'exécuter deux tests." Ce numéro est un *plan*. Il aide à s'assurer que votre programme de test a terminé tout et n'est pas mort ou n'a pas sauté certains tests. "ok 1" "Le premier test a réussi." "not ok 2" "Le second test a échoué." Test::Simple aide à imprimer quelques commentaires supplémentaires sur vos tests.

Ce n'est pas magique. Voyez, aidez-moi. Prenons un exemple de test d'un module. Pour notre exemple, nous allons tester un module de date, Date::ICal. Il est sur CPAN, alors téléchargez une copie et continuez. [2]

OÙ COMMENCER ?

C'est la partie la plus difficile du test, où commencer ? Les gens se sentent souvent submergés par l'ampleur apparente du travail de test d'un module complet. Le meilleur endroit pour commencer est par le début. Date::ICal est un module orienté objet, et cela signifie que vous commencez par créer un objet. Testez new().

#!/usr/bin/perl -w
# suppose que ces deux lignes sont dans tous les exemples suivants
use strict;
use warnings;
use Test::Simple tests => 2;
use Date::ICal;
my $ical = Date::ICal->new;         # créer un objet
ok( defined $ical );                # vérifier que quelque chose a été renvoyé
ok( $ical->isa('Date::ICal') );     # et que c'est la bonne classe

Exécutez cela et vous devriez obtenir :

1..2
ok 1
ok 2

Félicitations ! Vous avez écrit votre premier test utile !

NOMS

Cette sortie n'est pas très descriptive, n'est-ce pas ? Quand vous avez deux tests, vous pouvez savoir que c'est le #2, mais que se passe-t-il si vous avez 102 tests ?

Chaque test peut recevoir un nom descriptif comme deuxième argument à ok().

use Test::Simple tests => 2;
ok( defined $ical,              'new() a renvoyé quelque chose' );
ok( $ical->isa('Date::ICal'),   "et c'est la bonne classe" );

Maintenant, vous verrez :

1..2
ok 1 - new() a renvoyé quelque chose
ok 2 - et c'est la bonne classe

TESTER LE MANUEL

La manière la plus simple de construire une bonne suite de tests est simplement de tester ce que le manuel dit qu'il fait. [3] Extrayons une partie de ce qui se trouve dans le "SYNOPSIS" de Date::ICal et testons que tout fonctionne.

#!/usr/bin/perl -w
use Test::Simple tests => 8;
use Date::ICal;
$ical = Date::ICal->new( year => 1964, month => 10, day => 16,
                         hour => 16,   min   => 12, sec => 47,
                         tz   => '0530' );
ok( defined $ical,            'new() a renvoyé quelque chose' );
ok( $ical->isa('Date::ICal'), "et c'est la bonne classe" );
ok( $ical->sec   == 47,       'sec()' );
ok( $ical->min   == 12,       'min()' );
ok( $ical->hour  == 16,       'hour()' );
ok( $ical->day   == 17,       'day()' );
ok( $ical->month == 10,       'month()' );
ok( $ical->year  == 1964,     'year()' );

Exécutez cela et vous obtiendrez :

1..8
ok 1 - new() a renvoyé quelque chose
ok 2 - et c'est la bonne classe
ok 3 - sec()
ok 4 - min()
ok 5 - hour()
not ok 6 - day()
#     Test échoué (- ligne 16)
ok 7 - month()
ok 8 - year()
#     Il semble qu'il y ait 1 test échoué sur 8.

Hé, un échec ! [4] Test::Simple a aidé à nous dire à quelle ligne l'échec s'est produit, mais pas beaucoup plus. Nous nous attendions à obtenir 17, mais nous ne l'avons pas fait. Qu'avons-nous obtenu ? Je ne sais pas. Vous pouvez réexécuter le test dans le débogueur ou ajouter quelques lignes d'impression pour le découvrir.

Au lieu d'utiliser Test::Simple, passez à Test::More. Test::More fait tout ce que fait Test::Simple et plus encore ! En fait, Test::More fait les choses *exactement* comme Test::Simple. Vous pouvez remplacer complètement Test::Simple et mettre Test::More à sa place. C'est ce que nous allons faire.

Test::More fait plus que Test::Simple. La différence la plus importante maintenant est qu'il fournit des moyens plus informatifs de dire "ok". Bien que vous puissiez écrire presque n'importe quel test avec un ok() générique, il ne peut pas vous dire ce qui n'a pas fonctionné. La fonction is() vous permet de déclarer que quelque chose doit être égal à autre chose :

use Test::More tests => 8;
use Date::ICal;
$ical = Date::ICal->new( year => 1964, month => 10, day => 16,
                         hour => 16,   min   => 12, sec => 47,
                         tz   => '0530' );
ok( defined $ical,            'new() a renvoyé quelque chose' );
ok( $ical->isa('Date::ICal'), "et c'est la bonne classe" );
is( $ical->sec,     47,       'sec()' );
is( $ical->min,     12,       'min()' );
is( $ical->hour,    16,       'hour()' );
is( $ical->day,     17,       'day()' );
is( $ical->month,   10,       'month()' );
is( $ical->year,    1964,     'year()' );

"Est-ce que "$ical->sec" est 47 ?" "Est-ce que "$ical->min" est 12 ?" Avec is() en place, vous obtenez plus d'informations :

1..8
ok 1 - new() a renvoyé quelque chose
ok 2 - et c'est la bonne classe
ok 3 - sec()
ok 4 - min()
ok 5 - hour()
not ok 6 - day()
#     Test échoué (- ligne 16)
#          got: '16'
#     attendu: '17'
ok 7 - month()
ok 8 - year()
#     Il semble qu'il y ait 1 test échoué sur 8.

Ah. "$ical->day" a renvoyé 16, mais nous attendions 17. Un rapide coup d'œil montre que le code fonctionne bien, mais nous avons commis une erreur en écrivant les tests. Passez à :

is( $ical->day,     16,       'day()' );

... et tout fonctionne.

Tout test qui est "ceci est égal à cela" utilise is(). Il fonctionne également avec les tableaux. Le test s'exécute toujours en contexte scalaire, vous pouvez donc tester combien d'éléments se trouvent dans un tableau de cette manière. [5]

is( @foo, 5, 'foo a 5 éléments' );

CERTAINS TESTS SONT INCORRECTS

Cela génère une leçon très importante. Le code a des bugs. Les tests sont du code. Par conséquent, les tests ont aussi des bugs. Un test échoué peut signifier un bug dans le code, mais vous ne devez pas écarter la possibilité que le test lui-même soit défectueux.

Inversement, vous ne devez pas être tenté de déclarer immédiatement qu'un test est défectueux simplement parce que vous avez du mal à trouver le bug. invalider un test peut être un bug dans le code, mais vous ne devriez pas manquer de considérer la possibilité que le test soit défectueux.

tester n'est pas quelque chose à prendre à la légère, et ne l'utilisez pas comme échappatoire pour éviter le travail.

Tester beaucoup de valeurs

Nous allons vouloir tester beaucoup de dates ici, en essayant de piéger le code avec de nombreux cas limites différents. Fonctionne-t-il avant 1970 ? Après 2038 ? Avant 1904 ? Les années après 10 000 lui posent-elles problème ? Gère-t-il correctement les années bissextiles ? Nous pourrions continuer à répéter le code ci-dessus, ou nous pourrions mettre en place une petite boucle try/expect.

use Test::More tests => 32;
use Date::ICal;
my %ICal_Dates = (
        # Une chaîne ICal     Et l'année, le mois, le jour
        #                    l'heure, la minute et la seconde attendues.
        '19971024T120000' =>    # d'après la documentation.
                            [ 1997, 10, 24, 12,  0,  0 ],
        '20390123T232832' =>    # après l'époque Unix
                            [ 2039,  1, 23, 23, 28, 32 ],
        '19671225T000000' =>    # avant l'époque Unix
                            [ 1967, 12, 25,  0,  0,  0 ],
        '18990505T232323' =>    # avant l'époque MacOS
                            [ 1899,  5,  5, 23, 23, 23 ],
);
while( my($ical_str, $expect) = each %ICal_Dates ) {
    my $ical = Date::ICal->new( ical => $ical_str );
    ok( defined $ical,            "new(ical => '$ical_str')" );
    ok( $ical->isa('Date::ICal'), "  et c'est la bonne classe" );
    is( $ical->year,    $expect->[0],     '  year()'  );
    is( $ical->month,   $expect->[1],     '  month()' );
    is( $ical->day,     $expect->[2],     '  day()'   );
    is( $ical->hour,    $expect->[3],     '  hour()'  );
    is( $ical->min,     $expect->[4],     '  min()'   );
    is( $ical->sec,     $expect->[5],     '  sec()'   );
}

Nous pouvons maintenant tester des lots de dates en les ajoutant simplement à %ICal_Dates. Maintenant qu'il est moins laborieux de tester avec plus de dates, vous serez enclin à en ajouter davantage au fur et à mesure que vous y penserez. Le seul problème est que chaque fois que nous en ajoutons, nous devons continuer à ajuster la ligne "use Test::More tests => ##". Cela peut rapidement devenir ennuyeux. Il existe des moyens de mieux faire fonctionner cela.

Premièrement, nous pouvons calculer le plan dynamiquement en utilisant la fonction plan().

use Test::More;
use Date::ICal;
my %ICal_Dates = (
    ...idem que précédemment...
);
# Pour chaque clé du hash, nous exécutons 8 tests.
plan tests => keys(%ICal_Dates) * 8;
...et ensuite vos tests...

Pour être encore plus flexible, utilisez "done_testing". Cela signifie que nous exécutons simplement quelques tests, nous ne savons pas combien. [6]

use Test::More;   # au lieu de tests => 32
... # tests ici
done_testing();   # atteint la fin en toute sécurité

Si vous ne spécifiez pas de plan, Test::More s'attend à voir done_testing() avant que votre programme ne se termine. Il vous avertira si vous l'oubliez. Vous pouvez donner à done_testing() un nombre facultatif de tests que vous vous attendiez à exécuter, et si le nombre exécuté diffère, Test::More vous donnera un autre type d'avertissement.

Noms informatifs

Regardez la ligne :

ok( defined $ical,            "new(ical => '$ical_str')" );

Nous avons ajouté plus de détails sur ce que nous testons et sur la chaîne ICal elle-même que nous essayons d'utiliser dans le nom. Vous obtenez donc des résultats comme :

ok 25 - new(ical => '19971024T120000')
ok 26 -   et c'est la bonne classe
ok 27 -   year()
ok 28 -   month()
ok 29 -   day()
ok 30 -   hour()
ok 31 -   min()
ok 32 -   sec()

Si quelque chose échoue, vous saurez lequel et cela facilitera la recherche du problème. Essayez de mettre un peu d'informations de débogage dans les noms de tests.

Décrivez ce que les tests testent, pour faciliter le débogage d'un test échoué pour vous ou pour la prochaine personne qui exécutera votre test.

Sauter des tests

En explorant les tests existants de Date::ICal, j'ai trouvé ceci dans t/01sanity.t [7]

#!/usr/bin/perl -w
use Test::More tests => 7;
use Date::ICal;
# Assurez-vous que le temps d'époque est géré de manière saine.
my $t1 = Date::ICal->new( epoch => 0 );
is( $t1->epoch, 0,          "Temps d'époque de 0" );
# XXX Cela ne fonctionnera que sur les systèmes Unix.
is( $t1->ical, '19700101Z', "  époque vers Ical" );
is( $t1->year,  1970,       "  year()"  );
is( $t1->month, 1,          "  month()" );
is( $t1->day,   1,          "  day()"   );
# comme les tests ci-dessus, mais en commençant par ical au lieu de epoch
my $t2 = Date::ICal->new( ical => '19700101Z' );
is( $t2->ical, '19700101Z', "Début de l'époque en notation ICal" );
is( $t2->epoch, 0,          "  et retour à ICal" );

Le début de l'époque est différent sur la plupart des systèmes d'exploitation non-Unix [8]. Même si Perl lisse les différences la plupart du temps, certains ports le font différemment. MacPerl est un exemple qui me vient à l'esprit. [9] Plutôt que de mettre un commentaire dans le test et d'espérer que quelqu'un lise le test lors du débogage de l'échec, nous pouvons explicitement dire que cela ne fonctionnera jamais et sauter le test.

use Test::More tests => 7;
use Date::ICal;
# Assurez-vous que le temps d'époque est géré de manière saine.
my $t1 = Date::ICal->new( epoch => 0 );
is( $t1->epoch, 0,          "Temps d'époque de 0" );
SKIP: {
    skip('epoch to ICal not working on Mac OS', 6)
        if $^O eq 'MacOS';
    is( $t1->ical, '19700101Z', "  époque vers Ical" );
    is( $t1->year,  1970,       "  year()"  );
    is( $t1->month, 1,          "  month()" );
    is( $t1->day,   1,          "  day()"   );
    # comme les tests ci-dessus, mais en commençant par ical au lieu de epoch
    my $t2 = Date::ICal->new( ical => '19700101Z' );
    is( $t2->ical, '19700101Z', "Début de l'époque en notation ICal" );
    is( $t2->epoch, 0,          "  et retour à ICal" );
}

Un peu de magie se produit ici. Lors de l'exécution sur autre chose que MacOS, tous les tests s'exécutent normalement. Mais sur MacOS, skip() fait que tout le contenu du bloc SKIP est ignoré. Il ne s'exécute jamais. Au lieu de cela, skip() imprime une sortie spéciale qui indique à Test::Harness que les tests ont été sautés.

1..7
ok 1 - Temps d'époque de 0
ok 2 # skip epoch to ICal not working on MacOS
ok 3 # skip epoch to ICal not working on MacOS
ok 4 # skip epoch to ICal not working on MacOS
ok 5 # skip epoch to ICal not working on MacOS
ok 6 # skip epoch to ICal not working on MacOS
ok 7 # skip epoch to ICal not working on MacOS

Cela signifie que vos tests n'échoueront pas sur MacOS. Cela signifie moins d'e-mails des utilisateurs de MacPerl vous informant des tests échoués dont vous savez qu'ils ne fonctionneront jamais. Vous devez faire attention avec les tests sautés. Ce sont pour les tests qui ne fonctionnent pas et qui ne fonctionneront *jamais*. Ce n'est pas pour sauter des bugs réels (nous y reviendrons dans un moment).

Les tests sont complètement et entièrement sautés. [10] Cela fonctionnera.

SKIP: {
    skip("Je ne veux pas mourir !");
    die, die, die, die, die;
}

Tests Todo

En parcourant la page de manuel de Date::ICal, j'ai trouvé ceci :

ical
    $ical_string = $ical->ical;
Récupère ou définit la date sur l'objet, en utilisant n'importe quelle chaîne de date/heure ICal valide.

"Récupère ou définit". Hmm. Je n'ai pas vu de test pour utiliser ical() pour définir la date dans la suite de tests de Date::ICal. Alors j'en ai écrit un :

use Test::More tests => 1;
use Date::ICal;
my $ical = Date::ICal->new;
$ical->ical('20201231Z');
is( $ical->ical, '20201231Z',   'Définition via ical()' );

Exécutez cela. J'ai vu :

1..1
not ok 1 - Définition via ical()
#     Failed test (- at line 6)
#          got: '20010814T233649Z'
#     expected: '20201231Z'
# Looks like you failed 1 tests of 1.

Oups ! Il semble que ce ne soit pas implémenté. Supposons que vous n'ayez pas le temps de corriger cela. [11] Normalement, vous commenteriez simplement le test et mettriez une note dans une liste de choses à faire quelque part. Au lieu de cela, indiquez explicitement "ce test échouera" en l'entourant d'un bloc "TODO" :

use Test::More tests => 1;
TODO: {
    local $TODO = 'ical($ical) not yet implemented';
    my $ical = Date::ICal->new;
    $ical->ical('20201231Z');
    is( $ical->ical, '20201231Z',   'Définition via ical()' );
}

Maintenant, lorsque vous exécutez, c'est un peu différent :

1..1
not ok 1 - Définition via ical() # TODO ical($ical) not yet implemented
#          got: '20010822T201551Z'
#     expected: '20201231Z'

Test::More ne dit pas "Looks like you failed 1 tests of 1". Ce '# TODO' indique à Test::Harness "ceci est censé échouer" et il traite un échec comme un test réussi. Vous pouvez écrire des tests avant même d'avoir corrigé le code sous-jacent.

Si un test TODO réussit, Test::Harness le signalera comme "UNEXPECTEDLY SUCCEEDED". Lorsque cela se produit, supprimez le bloc TODO avec "local $TODO" et transformez-le en un vrai test.

Tester avec le mode taint.

Le mode Taint est une chose étrange. C'est la plus globale de toutes les fonctionnalités globales. Une fois que vous l'activez, il affecte *tout* le code de votre programme et *tous* les modules utilisés (et tous les modules qu'ils utilisent). Si une seule partie du code n'est pas propre au mode taint, tout explose. Dans cet esprit, il est très important de s'assurer que votre module fonctionne en mode taint.

Il est très simple d'exécuter vos tests en mode taint. Il suffit d'ajouter un "-T" à la ligne "#!". Test::Harness lira les commutateurs dans "#!" et les utilisera pour exécuter vos tests.

#!/usr/bin/perl -Tw
...testez normalement ici...

Lorsque vous dites "make test", il s'exécutera avec le mode taint activé.
