Test2::API::InterceptResult(3perl) Guide du programmeur Perl Test2::API::InterceptResult(3perl)

NOM

Test2::API::InterceptResult - Représentation d'une liste d'événements.

DESCRIPTION

Cette classe représente une liste d'événements, normalement obtenus à l'aide de intercept() de Test2::API.

Cette classe est destinée aux personnes qui souhaitent vérifier les résultats des outils de test qu'ils écrivent.

Cette classe fournit des méthodes pour normaliser, résumer ou mapper la liste d'événements. La sortie de ces opérations facilite grandement la vérification de vos outils de test et des événements qu'ils génèrent. Dans la plupart des cas, cela vous épargne d'avoir besoin d'une compréhension approfondie du modèle événement/facette.

SYNOPSIS

Habituellement, vous obtenez une instance de cette classe lorsque vous utilisez intercept() de Test2::API.

use Test2::V0;
use Test2::API qw/intercept/;
my $events = intercept {
    ok(1, "pass");
    ok(0, "fail");
    todo "broken" => sub { ok(0, "fixme") };
    plan 3;
};
# C'est généralement la construction la plus utile
# squash_info() fusionne les assertions et les diagnostics qui sont associés
#   (et retourne une nouvelle instance avec les modifications)
# flatten() condense les données de facette dans les détails clés pour chaque événement
#   (et retourne ces structures dans un tableau)
is(
    $events->squash_info->flatten(),
    [
        {
            causes_failure => 0,
            name => 'pass',
            pass => 1,
            trace_file => 'xxx.t',
            trace_line => 5,
        },
        {
            causes_failure => 1,
            name => 'fail',
            pass => 0,
            trace_file => 'xxx.t',
            trace_line => 6,
            # Il peut y avoir plus d'un message de diagnostic, donc c'est
            # toujours un tableau lorsqu'il est présent.
            diag => ["Failed test 'fail'\nat xxx.t line 6."],
        },
        {
            causes_failure => 0,
            name => 'fixme',
            pass => 0,
            trace_file => 'xxx.t',
            trace_line => 7,
            # Il peut y avoir plus d'un message de diagnostic ou raison de todo
            # donc ce sont toujours des tableaux lorsqu'ils sont présents.
            todo => ['broken'],
            # Le message Diag a été transformé en note car l'assertion était
            # TODO
            note => ["Failed test 'fixme'\nat xxx.t line 7."],
        },
        {
            causes_failure => 0,
            plan => 3,
            trace_file => 'xxx.t',
            trace_line => 8,
        },
    ],
    "Les événements aplatis correspondent à nos attentes"
);

Voir Test2::API::InterceptResult::Event pour une description complète de ce que flatten() fournit pour chaque événement.

MÉTHODES

Veuillez noter qu'aucune méthode ne modifie l'instance originale à moins qu'il ne soit demandé de le faire.

CONSTRUCTION

$events = Test2::API::InterceptResult->new(@EVENTS)
$events = Test2::API::InterceptResult->new_from_ref(\@EVENTS)
Ces méthodes créent une nouvelle instance de Test2::API::InterceptResult à partir des événements donnés.

Dans la première forme, un nouvel objet "blessed" est retourné. Dans la forme 'new_from_ref', la référence que vous passez est directement "blessed".

Ces deux méthodes lèveront une exception si elles sont appelées dans un contexte vide (void). C'est principalement important pour les méthodes de 'filtrage' listées ci-dessous qui retournent normalement une nouvelle instance ; elles lèvent une exception dans de tels cas car cela signifie probablement que quelqu'un avait l'intention de filtrer l'original sur place.

$clone = $events->clone()
Crée une copie de l'instance originale des événements. Notez qu'il s'agit d'une copie profonde, toute la structure est dupliquée. Utilise "dclone" de Storable pour réaliser la copie profonde.

NORMALISATION

@events = $events->event_list
Retourne tous les événements sous forme de liste.
$hub = $events->hub
Retourne une nouvelle instance de Test2::Hub qui a traité tous les événements contenus dans l'instance. Cela vous donne un moyen simple d'inspecter les changements d'état causés par vos événements.
$state = $events->state
Retourne un résumé de l'état d'un hub après le traitement de tous les événements. 
{
    count        => 2,      # Nombre d'assertions effectuées
    failed       => 1,      # Nombre d'échecs de tests rencontrés
    is_passing   => 0,      # Booléen, vrai si le test passerait
                            # après le traitement des événements.
    plan         => 2,      # Plan, soit un nombre, undef, 'SKIP', ou 'NO PLAN'
    follows_plan => 1,      # Vrai s'il y a un plan et qu'il a été suivi.
                            # Faux si le plan et les assertions ne correspondent pas,
                            # undef s'il n'y avait pas de plan dans la liste d'événements.
    bailed_out   => undef,  # undef sauf s'il y a eu un bail-out dans les
                            # événements, auquel cas ce sera une chaîne
                            # expliquant pourquoi il y a eu un bail-out, si aucune
                            # raison n'a été donnée, ce sera simplement défini à
                            # vrai (1).
    skip_reason  => undef,  # S'il y a eu un skip_all, cela donnera la
                            # raison.
}
$new = $events->upgrade
$events->upgrade(in_place => $BOOL)
Note : Ceci retourne normalement une nouvelle instance, laissant l'original inchangé. Si vous l'appelez dans un contexte vide (void), cela lèvera une exception. Si vous voulez modifier l'original, vous devez passer l'option "in_place => 1". Vous pouvez appeler cela dans un contexte vide lorsque vous demandez une modification sur place. La forme sur place retourne l'instance modifiée afin que vous puissiez chaîner les méthodes.

Cela créera une copie de la liste où tous les événements auront été convertis en instances de Test2::API::InterceptResult::Event. C'est extrêmement utile car Test2::API::InterceptResult::Event fournit une bien meilleure interface pour travailler avec les événements. Cela vous permet d'éviter de penser aux anciens types d'événements.

Cela signifie également que vos tests sur la liste ne seront pas fragiles si l'outil que vous testez change aléatoirement le type d'événements qu'il génère (par exemple, passer de Test2::Event::Ok à Test2::Event::Pass, les deux font des assertions et les deux seront normalisés en instances de Test2::API::InterceptResult::Event identiques (ou suffisamment proches)).

En réalité, vous voulez presque toujours cela, la seule raison pour laquelle ce n'est pas fait automatiquement est de garantir la rétrocompatibilité de l'outil intercept().

$new = $events->squash_info
$events->squash_info(in_place => $BOOL)
Note : Ceci retourne normalement une nouvelle instance, laissant l'original inchangé. Si vous l'appelez dans un contexte vide (void), cela lèvera une exception. Si vous voulez modifier l'original, vous devez passer l'option "in_place => 1". Vous pouvez appeler cela dans un contexte vide lorsque vous demandez une modification sur place. La forme sur place retourne l'instance modifiée afin que vous puissiez chaîner les méthodes.

Note : Tous les événements de la nouvelle instance ou de l'instance modifiée seront convertis en instances de Test2::API::InterceptResult::Event. Il n'y a aucun moyen d'éviter cela, l'opération de squash nécessite la classe d'événement améliorée.

Test::More et de nombreux autres outils hérités envoyaient des notes, des diagnostics et des assertions comme événements séparés. Un sous-test dans Test::More envoyait une note avec le nom du sous-test, l'assertion du sous-test, puis un événement de diagnostic si le sous-test échouait. Cette méthode normalisera les choses en fusionnant la note et le diagnostic dans le même événement que le sous-test (ceci est différent de les placer dans le sous-test, ce qui n'est pas ce qui se passe).

FILTRAGE

Note : Ces méthodes retournent normalement de nouvelles instances, laissant les originales inchangées. Si vous les appelez dans un contexte vide (void), elles lèveront des exceptions. Si vous voulez modifier les originales, vous devez passer l'option "in_place => 1". Vous pouvez appeler ces méthodes dans un contexte vide lorsque vous demandez une modification sur place. Les formes sur place retournent l'instance modifiée afin que vous puissiez chaîner les méthodes.

MÉTHODES

$events->grep($CALL, %PARAMS)
Ceci est essentiellement : 
Test2::API::InterceptResult->new(
    grep { $_->$CALL( @{$PARAMS{args}} ) } $self->event_list,
);

Note : que $CALL est appelée sur une version mise à niveau de l'événement, bien que les événements retournés soient les originaux, pas ceux mis à niveau.

$CALL peut être soit le nom d'une méthode sur Test2::API::InterceptResult::Event, soit un coderef.

$events->asserts(%PARAMS)
Ceci est essentiellement : 
$events->grep(has_assert => @{$PARAMS{args}})

Il retourne une nouvelle instance contenant uniquement les événements qui ont fait des assertions.

$events->subtests(%PARAMS)
Ceci est essentiellement : 
$events->grep(has_subtest => @{$PARAMS{args}})

Il retourne une nouvelle instance contenant uniquement les événements qui ont des sous-tests.

$events->diags(%PARAMS)
Ceci est essentiellement : 
$events->grep(has_diags => @{$PARAMS{args}})

Il retourne une nouvelle instance contenant uniquement les événements qui ont des diagnostics.

$events->notes(%PARAMS)
Ceci est essentiellement : 
$events->grep(has_notes => @{$PARAMS{args}})

Il retourne une nouvelle instance contenant uniquement les événements qui ont des notes.

$events->errors(%PARAMS)
Note : Les erreurs NE SONT PAS des assertions échouées. Les assertions échouées sont une chose différente.

Ceci est essentiellement :

$events->grep(has_errors => @{$PARAMS{args}})

Il retourne une nouvelle instance contenant uniquement les événements qui ont des erreurs.

$events->plans(%PARAMS)
Ceci est essentiellement : 
$events->grep(has_plan => @{$PARAMS{args}})

Il retourne une nouvelle instance contenant uniquement les événements qui ont défini le plan.

$events->causes_fail(%PARAMS)
$events->causes_failure(%PARAMS)
Ceci est essentiellement : 
$events->grep(causes_fail    => @{$PARAMS{args}})
$events->grep(causes_failure => @{$PARAMS{args}})

Note : causes_fail() et causes_failure() sont des alias l'un de l'autre dans les événements, donc ces méthodes sont effectivement des alias ici aussi.

Il retourne une nouvelle instance contenant uniquement les événements qui causent un échec.

MAPPING

Ces méthodes retournent **TOUJOURS** un arrayref.

Note : Aucune méthode sur Test2::API::InterceptResult::Event ne modifie l'événement de quelque manière que ce soit.

Notes importantes sur les événements :

Test2::API::InterceptResult::Event a été spécialement conçu pour être utilisé dans les listes d'événements. La plupart des méthodes qui ne sont pas applicables à un événement donné retourneront une liste vide, vous n'avez donc normalement pas à vous soucier des valeurs "undef" indésirables ou des exceptions levées. Mapper sur les méthodes d'événement est une utilisation prévue, donc cela fonctionne bien pour produire des listes.

Exceptions à la règle :

Certaines méthodes comme "causes_fail" retournent toujours un booléen vrai ou faux pour tous les événements. Toute méthode préfixée par "the_" transmet l'intention que l'événement doit avoir exactement 1 de quelque chose, donc celles-ci lèveront une exception lorsque cette condition n'est pas remplie.

$arrayref = $events->map($CALL, %PARAMS)
Ceci est essentiellement : 
[ map { $_->$CALL(@{ $PARAMS{args} }) } $events->upgrade->event_list ];

$CALL peut être soit le nom d'une méthode sur Test2::API::InterceptResult::Event, soit un coderef.

$arrayref = $events->flatten(%PARAMS)
Ceci est essentiellement :
