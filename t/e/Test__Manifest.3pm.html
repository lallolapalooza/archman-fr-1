NAME

Test::Manifest - interagir avec un fichier t/test_manifest

SYNOPSIS

# dans Makefile.PL
eval "use Test::Manifest 2.00";
# dans Build.PL
my $class = do {
        if( eval 'use Test::Manifest 2.00; 1' ) {
                Test::Manifest->get_module_build_subclass;
                }
        else {
                'Module::Build';
                }
        };
my $build = $class->new( ... )
# dans le fichier t/test_manifest, listez les tests que vous voulez
# exécuter dans l'ordre où vous voulez les exécuter

DESCRIPTION

"Test::Harness" suppose que vous voulez exécuter tous les fichiers .t du répertoire t/ dans l'ordre alphabétique lors de "make test" ou "./Build test", sauf indication contraire. Cela conduit à des schémas de nommage intéressants pour les fichiers de test afin de les obtenir dans l'ordre souhaité. Ces noms intéressants se fossilisent lorsqu'ils sont intégrés dans le système de contrôle de version, et deviennent encore plus intéressants à mesure que de nouveaux tests apparaissent.

"Test::Manifest" remplace l'ordre par défaut des fichiers de test. Au lieu d'exécuter tous les fichiers t/*.t dans l'ordre alphabétique, il recherche dans le fichier t/test_manifest pour savoir quels tests vous voulez exécuter et dans quel ordre. Il construit la bonne valeur pour le système de construction afin qu'il fasse la bonne chose.

Dans t/test_manifest, listez simplement les tests que vous voulez exécuter. Leur ordre dans le fichier est l'ordre dans lequel ils s'exécutent. Vous pouvez commenter les lignes avec un "#", tout comme en Perl, et "Test::Manifest" supprimera les espaces blancs en début et fin de chaque ligne. Il vérifie également que le fichier spécifié se trouve bien dans le répertoire t/. Si le fichier n'existe pas, il n'ajoute pas son nom à la liste des fichiers de test à exécuter et émet un avertissement.

Facultativement, vous pouvez ajouter un nombre après le nom du test dans test_manifest pour définir des ensembles de tests. Voir "get_t_files" pour plus d'informations.

ExtUtils::MakeMaker

Pour remplacer le comportement de l'ordre des tests dans "MakeMaker", "Test::Manifest" s'insère dans l'étape "test_via_harness" en fournissant son propre exécuteur de tests. Dans "Makefile.PL", vous n'avez qu'à charger "Test::Manifest" avant d'appeler "WriteMakefile". Pour le rendre facultatif, chargez-le dans un eval :

eval "use Test::Manifest";

Module::Build

Remplacer des parties de "Module::Build" est plus délicat si vous voulez utiliser le mécanisme de sous-classe et toujours rendre "Test::Manifest" facultatif. Si vous pouvez charger "Test::Manifest" (version 2.00 ou ultérieure), "Test::Manifest" peut créer la sous-classe pour vous.

my $class = do {
        if( eval 'use Test::Manifest 2.00; 1' ) {
                Test::Manifest->get_module_build_subclass;
                }
        else {
                'Module::Build' # si Test::Manifest n'est pas là
                }
        };
$class->new( ... );
$class->create_build_file;

C'est un peu problématique lorsque vous avez déjà votre propre sous-classe. "Test::Manifest" remplace "find_test_files", vous pouvez donc obtenir juste ce code à ajouter à votre propre chaîne de code de sous-classe :

my $code = eval 'use Test::Manifest 2.00; 1'
                ?
        Test::Manifest->get_module_build_code_string
                :
        '';
my $class = Module::Build->subclass(
        ...,
        code => "$code\n...votre chaîne de code de sous-classe...",
        );

Méthodes de classe

get_module_build_subclass
Pour "Module::Build" uniquement.

Retourne une sous-classe de "Module::Build" qui remplace "find_test_files". Si vous voulez avoir votre propre sous-classe "Module::Build" et toujours utiliser "Test::Manifest", vous pouvez obtenir juste la chaîne de code avec "get_module_build_code_string".

get_module_build_code_string
Pour "Module::Build" uniquement.

Retourne le "find_test_files" remplacé sous forme de code Perl dans une chaîne adaptée à la clé "code" dans "Module::Build-"subclass()>. Vous pouvez l'ajouter à d'autres parties que vous remplacez ou étendez.

Voir "Module::Build::Base::find_test_files" pour voir l'implémentation de base.

Fonctions

run_t_manifest( TEST_VERBOSE, INST_LIB, INST_ARCHLIB, TEST_LEVEL )
Pour "MakeMaker" uniquement. Vous n'avez pas à vous en soucier au niveau utilisateur.

Exécute tous les fichiers de t/test_manifest via "Test::Harness:runtests" dans l'ordre où ils apparaissent dans le fichier. Ceci est inséré automatiquement

eval "use Test::Manifest";
get_t_files( [LEVEL] )
En contexte scalaire, il retourne une chaîne unique que vous pouvez utiliser directement dans WriteMakefile(). En contexte de liste, il retourne une liste des fichiers qu'il a trouvés dans t/test_manifest.

Si un fichier t/test_manifest n'existe pas, get_t_files() ne retourne rien.

get_t_files() vous avertit s'il ne trouve pas t/test_manifest, ou si les entrées commencent par t/. Il ignore les lignes vides et supprime les commentaires style Perl du fichier.

Chaque ligne dans t/test_manifest peut avoir trois parties : le nom du test, le niveau de test (un nombre flottant) et un commentaire. Par défaut, le niveau de test est 1.

test_name.t 2  # Exécute ceci uniquement pour les tests de niveau 2

Sans argument, get_t_files() retourne tous les fichiers de test qu'il trouve. Avec un argument qui est vrai (donc on ne peut pas utiliser 0 comme niveau) et qui est un nombre, il ignore les tests dont le niveau est supérieur à cet argument. Vous pouvez alors définir des ensembles de tests et choisir un ensemble à exécuter. Par exemple, vous pourriez créer un ensemble pour les utilisateurs finaux, mais ajouter également un ensemble pour des tests plus approfondis pour les développeurs.

Expérimentalement, vous pouvez inclure une commande pour extraire les noms de tests d'un autre fichier. La commande commence par un ";" pour la distinguer d'un vrai nom de fichier. Le nom du fichier (actuellement) est relatif au répertoire de travail courant, contrairement aux noms de fichiers, qui sont relatifs à "t/". Les noms de fichiers dans le fichier inclus sont toujours relatifs à "t/".

;include t/file_with_other_test_names.txt

Également expérimentalement, vous pouvez empêcher "Test::Manifest" de lire des noms de fichiers avec la directive ";skip". "Test::Manifest" ignorera les noms de fichiers jusqu'à la directive ";unskip" (ou la fin du fichier) :

run_this1
;skip
skip_this
;unskip
run_this2

Pour sélectionner des ensembles de tests, spécifiez le niveau dans la variable d'environnement "TEST_LEVEL" :

make test # exécute tous les tests quel que soit le niveau
make test TEST_LEVEL=2  # exécute tous les tests de niveau 2 et inférieur

À terme, cela deviendra une option pour Build.PL :

./Build test --testlevel=2  # Pas encore supporté
