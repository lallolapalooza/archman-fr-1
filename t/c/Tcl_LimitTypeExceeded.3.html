ARGUMENTS

Tcl_Interp *interp (entrée)
L'interpréteur auquel la limite gérée s'applique ou dont les limites seront vérifiées.
int type (entrée)
Le type de limite auquel l'opération se réfère. Doit être soit TCL_LIMIT_COMMANDS soit TCL_LIMIT_TIME.
int commandLimit (entrée)
Le nombre maximal de commandes (tel que rapporté par info cmdcount) qui peuvent être exécutées dans l'interpréteur.
Tcl_Time *timeLimitPtr (entrée/sortie)
Un pointeur vers une structure qui recevra la nouvelle limite de temps (depuis Tcl_LimitSetTime) ou écrira la limite actuelle (depuis Tcl_LimitGetTime).
int granularity (entrée)
Un diviseur indiquant à quelle fréquence une limite doit réellement être vérifiée. Doit être au moins 1.
Tcl_LimitHandlerProc *handlerProc (entrée)
La fonction à appeler lorsqu'une limite est dépassée. Si le handlerProc supprime ou augmente la limite pendant son exécution, l'interpréteur limité sera autorisé à continuer le traitement après le retour du gestionnaire. De nombreux gestionnaires peuvent être associés à une même limite d'interpréteur ; leur ordre d'exécution n'est pas défini et ils doivent être identifiés par handlerProc et clientData lors de leur suppression.
ClientData clientData (entrée)
Une valeur de pointeur arbitraire utilisée pour passer un contexte à la fonction handlerProc.
Tcl_LimitHandlerDeleteProc *deleteProc (entrée)
La fonction à appeler lorsqu'un gestionnaire est supprimé. Peut être NULL si le clientData ne nécessite pas de suppression.

DESCRIPTION

Le système de limites de temps de Tcl permet un contrôle étroit sur le temps d'utilisation d'un script et est utile dans les cas où un programme est divisé en plusieurs parties, dont certaines sont plus fiables que d'autres (par exemple, les serveurs web).

Chaque interpréteur peut avoir une limite de temps d'exécution et une limite de commandes qu'il peut exécuter. Étant donné que la vérification de ces limites peut être coûteuse (en particulier la limite de temps), chaque limite a également une politique de granularité, qui est un diviseur pour un compte interne de points dans le noyau où une vérification peut être effectuée (ce qui se produit juste avant l'exécution d'une commande et à une fréquence non spécifiée entre les exécutions de commandes, qui peut se produire dans des boucles vides while).

Le composant final du moteur de limites est un mécanisme de notification qui permet d'être informé lorsqu'une limite a été dépassée. Ces notifications peuvent simplement fournir une journalisation, ou elles peuvent allouer plus de ressources à l'interpréteur pour lui permettre de continuer à traiter plus longtemps.

Lorsqu'une limite est dépassée (et que les callbacks ont été exécutés ; l'ordre d'exécution des callbacks n'est pas défini), l'exécution dans l'interpréteur limité est arrêtée en levant une erreur et en définissant un drapeau qui empêche la commande catch dans cet interpréteur de capturer cette erreur. C'est le contexte qui a initié l'exécution dans cet interpréteur (généralement l'interpréteur principal) qui doit gérer l'erreur.

API DE VÉRIFICATION DES LIMITES

Pour vérifier les limites de ressources d'un interpréteur, appelez Tcl_LimitCheck, qui renvoie TCL_OK si la limite n'a pas été dépassée (après traitement des callbacks) et TCL_ERROR si la limite a été dépassée (auquel cas un message d'erreur sera également placé dans le résultat de l'interpréteur). Cette fonction ne doit être appelée que lorsque Tcl_LimitReady renvoie une valeur non nulle afin que la politique de granularité soit appliquée. Cette API est conçue pour être utilisée de manière similaire à Tcl_AsyncReady et Tcl_AsyncInvoke.

Lorsque vous écrivez du code qui peut se comporter comme catch par rapport aux erreurs, vous ne devez capturer une erreur que si Tcl_LimitExceeded renvoie zéro. Si elle renvoie une valeur non nulle, l'interpréteur est dans un état de limite dépassée et les erreurs doivent être autorisées à se propager au contexte d'appel. Vous pouvez également vérifier si un type particulier de limite a été dépassé en utilisant Tcl_LimitTypeExceeded.

CONFIGURATION DES LIMITES

Pour vérifier si une limite a été définie (mais pas si elle a réellement été dépassée) dans un interpréteur, appelez Tcl_LimitTypeEnabled avec le type de limite que vous souhaitez vérifier. Pour activer une limite, appelez Tcl_LimitTypeSet, et pour désactiver une limite, appelez Tcl_LimitTypeReset.

Le niveau d'une limite de commandes peut être défini avec Tcl_LimitSetCommands et récupéré avec Tcl_LimitGetCommands. De même, pour une limite de temps, elle peut être définie avec Tcl_LimitSetTime et récupérée avec Tcl_LimitGetTime, mais avec cette API, la limite de temps est copiée depuis et vers la structure Tcl_Time vers laquelle pointe l'argument timeLimitPtr.

Le grain de vérification d'une limite peut être défini avec Tcl_LimitSetGranularity et récupéré avec Tcl_LimitGetGranularity. Vous devez noter que les grains doivent être positifs.

GESTION DES CALLBACKS

Pour ajouter un callback à appeler lorsqu'une limite est dépassée, appelez Tcl_LimitAddHandler. L'argument handlerProc décrit la fonction qui sera appelée ; elle devrait avoir le prototype suivant :

typedef void Tcl_LimitHandlerProc(
        ClientData clientData,
        Tcl_Interp *interp);

L'argument clientData de la fonction de gestionnaire sera ce qui a été passé à l'argument clientData de Tcl_LimitAddHandler, et interp est l'interpréteur dont la limite a été dépassée.

L'argument deleteProc de Tcl_LimitAddHandler est une fonction à appeler pour supprimer la valeur de clientData. Il peut s'agir de TCL_STATIC ou de NULL s' aucune action de suppression n'est requise, ou de TCL_DYNAMIC s'il suffit de libérer la structure avec Tcl_Free. Sinon, il doit faire référence à une fonction ayant le prototype suivant :

typedef void Tcl_LimitHandlerDeleteProc(
        ClientData clientData);

Un gestionnaire de limite peut être supprimé avec Tcl_LimitRemoveHandler ; le gestionnaire supprimé sera le premier trouvé (parmi les gestionnaires ajoutés avec Tcl_LimitAddHandler) ayant exactement les mêmes arguments type, handlerProc et clientData. Cette fonction appelle toujours le deleteProc sur le clientData (sauf si le deleteProc était NULL ou TCL_STATIC).
