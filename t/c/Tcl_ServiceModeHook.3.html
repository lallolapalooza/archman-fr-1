INTRODUCTION

Les interfaces décrites ici sont utilisées pour personnaliser la boucle d'événements de Tcl. Les deux personnalisations les plus courantes consistent à ajouter de nouvelles sources d'événements et à joindre la boucle d'événements Tcl à une autre boucle d'événements, comme celle fournie par une application dans laquelle Tcl est intégrée. Chacune de ces tâches est décrite dans une section distincte.

Les procédures de ce manuel sont les éléments constitutifs du notificateur Tcl. Le notificateur est la couche la plus basse du mécanisme d'événements de Tcl. Il se compose de trois éléments :

[1]
Sources d'événements : elles représentent les moyens par lesquels les événements peuvent être générés. Par exemple, il existe une source d'événements de minuteur qui implémente la procédure Tcl_CreateTimerHandler et la commande after, et une source d'événements de fichier qui implémente la procédure Tcl_CreateFileHandler sur les systèmes Unix. Une source d'événements doit collaborer avec le notificateur pour détecter les événements aux bons moments, les enregistrer dans la file d'attente d'événements, et finalement notifier le logiciel de plus haut niveau que des événements se sont produits. Les procédures Tcl_CreateEventSource, Tcl_DeleteEventSource, Tcl_SetMaxBlockTime, Tcl_QueueEvent et Tcl_DeleteEvents sont principalement utilisées par les sources d'événements.
[2]
La file d'attente d'événements : pour les applications non multithread, il existe une seule file d'attente pour l'application qui contient les événements détectés mais pas encore traités. Les sources d'événements placent les événements dans la file d'attente afin qu'ils puissent être traités dans l'ordre pendant la boucle d'événements. La file d'attente d'événements assure une discipline équitable de traitement des événements, de sorte qu'aucune source d'événements ne puisse gêner les autres. Elle permet également de conserver des événements pour un traitement ultérieur. Les applications multithread fonctionnent de manière similaire, mais il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. Tcl_QueueEvent est utilisé (principalement par les sources d'événements) pour ajouter des événements à la file d'attente d'événements et Tcl_DeleteEvents pour supprimer des événements de la file d'attente sans les traiter. Dans une application multithread, Tcl_QueueEvent ajoute un événement à la file d'attente du thread actuel, et Tcl_ThreadQueueEvent ajoute un événement à la file d'attente d'un thread spécifique.
[3]
La boucle d'événements : pour détecter et traiter les événements, l'application entre dans une boucle qui attend les événements, les place dans la file d'attente d'événements, puis les traite. La plupart des applications le font en appelant la procédure Tcl_DoOneEvent, qui est décrite dans un manuel distinct.

La plupart des applications Tcl n'ont pas besoin de se soucier des détails internes du notificateur Tcl. Cependant, le notificateur est maintenant suffisamment flexible pour être réaffecté à une nouvelle plateforme ou pour être utilisé avec une boucle d'événements externe (telle que la boucle d'événements Motif lorsque Tcl est intégrée dans une application Motif). Les procédures Tcl_WaitForEvent et Tcl_SetTimer sont normalement implémentées par Tcl, mais peuvent être remplacées par de nouvelles versions pour réaffecter le notificateur (les procédures Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler et Tcl_DeleteFileHandler doivent également être remplacées ; voir CRÉATION D'UN NOUVEAU NOTIFICATEUR pour plus de détails). Les procédures Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode et Tcl_SetServiceMode sont fournies pour aider à connecter la boucle d'événements Tcl à une boucle d'événements externe comme celle de Motif.

BASES DU NOTIFICATEUR

La façon la plus simple de comprendre le fonctionnement du notificateur est de considérer ce qui se passe lorsque Tcl_DoOneEvent est appelée. Tcl_DoOneEvent reçoit un argument flags qui indique quel type d'événements peut être traité et s'il faut ou non bloquer si aucun événement n'est prêt. Tcl_DoOneEvent fait ce qui suit :

[1]
Vérifier la file d'attente d'événements pour voir s'il y a des événements qui peuvent être servis. S'il y en a, le premier événement possible est servi, retiré de la file d'attente et retourné. Cela est fait en appelant Tcl_ServiceEvent et en lui passant l'argument flags.
[2]
Se préparer à bloquer en attendant un événement. Pour ce faire, Tcl_DoOneEvent appelle une procédure setup sur chaque source d'événements. La source d'événements effectuera l'initialisation spécifique à la source d'événements et pourra éventuellement appeler Tcl_SetMaxBlockTime pour limiter le temps pendant lequel Tcl_WaitForEvent sera bloqué si aucun nouvel événement ne se produit.
[3]
Appeler Tcl_WaitForEvent. Cette procédure est implémentée différemment selon les plateformes ; elle attend un événement en fonction des informations fournies par les sources d'événements. Elle peut entraîner le blocage de l'application si timePtr spécifie un intervalle différent de 0. Tcl_WaitForEvent retourne lorsqu'un événement s'est produit, tel qu'un fichier devenant lisible ou l'expiration de l'intervalle donné par timePtr. S'il n'y a pas d'événements pour lesquels Tcl_WaitForEvent doit attendre, et qu'il est donc bloqué indéfiniment, il retourne immédiatement et Tcl_DoOneEvent retourne 0.
[4]
Appeler une procédure check sur chaque source d'événements. La procédure check détermine s'il y a des événements intéressant cette source. S'il y en a, les événements sont ajoutés à la file d'attente d'événements.
[5]
Vérifier t
Mantén toda la estructura del archivo.
Vérifiez s'il existe des événements en attente qui peuvent être traités. S'ils sont trouvés, traitez le premier événement possible, retirez-le du tampon et revenez.
Vérifiez s'il existe des callbacks inactifs en attente. S'ils sont trouvés, appelez-les tous et revenez.
Retourne 0 pour indiquer qu'aucun événement n'est prêt, ou revenez à l'étape [2] si l'appelant a demandé un blocage.

CRÉATION D'UNE NOUVELLE SOURCE D'ÉVÉNEMENTS

Une source d'événements se compose de trois procédures appelées par le gestionnaire, plus des procédures C supplémentaires qui sont appelées par le code appelant pour organiser les callbacks d'événements. Les trois procédures appelées par le gestionnaire comprennent les procédures de configuration et de vérification décrites ci-dessus, plus une procédure supplémentaire qui est appelée lorsqu'un événement est retiré du tampon pour être traité.

La procédure Tcl_CreateEventSource crée une nouvelle source d'événements. Ses arguments spécifient les procédures de configuration et de vérification de la source d'événements. SetupProc doit correspondre au prototype suivant :

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

L'argument clientData sera le même que l'argument clientData de la procédure Tcl_CreateEventSource ; il est généralement utilisé pour pointer vers des informations privées gérées par la source d'événements. L'argument flags sera le même que l'argument flags passé à Tcl_DoOneEvent, sauf qu'il ne sera jamais 0 (Tcl_DoOneEvent remplace 0 par TCL_ALL_EVENTS). Flags indique quels types d'événements doivent être pris en compte ; si le bit correspondant à cette source d'événements n'est pas activé, la source d'événements doit revenir immédiatement sans rien faire. Par exemple, la source d'événements vérifie le bit TCL_FILE_EVENTS.

Le travail de la procédure SetupProc est d'assurer que l'application se réveille lorsque des événements du type souhaité se produisent. Ceci est généralement fait de manière dépendante de la plateforme. Par exemple, sous Unix, une source d'événements pourrait appeler Tcl_CreateFileHandler ; sous Windows, elle pourrait demander une notification avec un événement Windows. Pour les sources d'événements de type minuterie, telles que les événements temporels ou tout événement interrogé, la source d'événements peut appeler Tcl_SetMaxBlockTime pour forcer l'application à se réveiller après un délai spécifié, même s'il n'y a pas d'événements. Si aucune source d'événements n'appelle Tcl_SetMaxBlockTime, Tcl_WaitForEvent attendra suffisamment longtemps pour qu'un événement se produise ; sinon, elle n'attendra que le temps le plus court spécifié par l'une des sources d'événements dans Tcl_SetMaxBlockTime. Si une source d'événements sait qu'elle a déjà des événements prêts à être signalés, elle peut demander un temps de blocage nul. Par exemple, la procédure de configuration de la source d'événements X vérifie s'il y a déjà des événements dans la file d'attente. S'il y en a, elle appelle Tcl_SetMaxBlockTime avec un temps de blocage nul afin que Tcl_WaitForEvent ne bloque pas s'il n'y a pas de nouvelles données sur la connexion X. L'argument timePtr de Tcl_WaitForEvent pointe vers une structure décrivant un intervalle de temps en secondes et microsecondes :

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

Le champ usec doit être inférieur à 1000000.

Les informations fournies à Tcl_SetMaxBlockTime ne sont utilisées que pour le prochain appel à Tcl_WaitForEvent ; elles sont ignorées après le retour de Tcl_WaitForEvent. La prochaine fois qu'une attente d'événement sera effectuée, chaque procédure de configuration des sources d'événements sera à nouveau appelée, et elles pourront spécifier de nouvelles données pour cette attente d'événement.

Si l'application utilise une boucle d'événements externe au lieu de Tcl_DoOneEvent, les sources d'événements peuvent avoir besoin d'appeler Tcl_SetMaxBlockTime à d'autres moments. Par exemple, si un nouveau gestionnaire d'événements qui a besoin d'interroger des événements est enregistré, la source d'événements peut appeler Tcl_SetMaxBlockTime pour définir un temps de blocage nul, forçant la boucle d'événements externe à appeler Tcl. Dans ce cas, Tcl_SetMaxBlockTime appelle Tcl_SetTimer avec l'intervalle le plus court vu depuis le dernier appel à Tcl_DoOneEvent ou Tcl_ServiceAll.

En plus de la procédure générale Tcl_SetMaxBlockTime, d'autres procédures spécifiques à la plateforme peuvent être disponibles pour le setupProc, si des informations supplémentaires sont nécessaires par Tcl_WaitForEvent sur cette plateforme. Par exemple, sur les systèmes Unix, l'interface Tcl_CreateFileHandler peut être utilisée pour attendre des événements de fichier.

La deuxième procédure fournie par chaque source d'événements est sa procédure de vérification, indiquée par l'argument checkProc de Tcl_CreateEventSource. CheckProc doit correspondre au prototype suivant :

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Les arguments de cette procédure sont les mêmes que ceux de setupProc. CheckProc est appelée par Tcl_DoOneEvent après avoir attendu des événements. On suppose qu'au moins une source d'événements est prête à mettre un événement en file d'attente. Tcl_DoOneEvent appelle chaque source d'événements dans l'ordre, de sorte que toutes aient une chance de mettre en file d'attente tout événement prêt. La procédure de vérification fait deux choses. Premièrement, elle doit vérifier s'il y a des événements qui sont devenus actifs. Différentes sources d'événements le font différemment.

Si une source d'événements détecte un événement intéressant, elle doit ajouter l'événement à la file d'attente des événements de Tcl. Pour ce faire, la source d'événements appelle Tcl_QueueEvent. L'argument evPtr est un pointeur vers une structure allouée dynamiquement qui contient l'événement (voir ci-dessous pour plus d'informations sur la gestion de la mémoire). Chaque source d'événements peut définir sa propre structure d'événement avec des informations pertinentes pour cette source d'événements. Cependant, le premier élément de la structure doit être une structure de type Tcl_Event, et l'adresse de cette structure est utilisée lors de la communication entre la source d'événements et le reste du gestionnaire. Un Tcl_Event a la définition suivante :

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La source d'événements doit remplir le champ proc de la structure avant d'appeler Tcl_QueueEvent. Le nextPtr est utilisé pour lier les événements dans la file d'attente et ne doit pas être modifié par la source d'événements.

Un événement peut être ajouté à la file d'attente dans l'une des trois positions, selon l'argument position de Tcl_QueueEvent :

TCL_QUEUE_TAIL
Ajoute l'événement à la fin de la file d'attente, de sorte que tous les autres événements en attente soient traités en premier. C'est presque toujours la meilleure position pour les nouveaux événements.
TCL_QUEUE_HEAD
Ajoute l'événement au début de la file d'attente, de sorte qu'il soit traité avant tout autre événement dans la file d'attente.
TCL_QUEUE_MARK
Ajoute l'événement au début de la file d'attente, à moins qu'il n'y ait d'autres événements au début de la file d'attente dont la position est TCL_QUEUE_MARK ; si c'est le cas, ajoute le nouvel événement juste après tous les autres événements TCL_QUEUE_MARK. Cette valeur de position est utilisée pour insérer une séquence ordonnée d'événements au début de la file d'attente, comme une série d'événements Enter et Leave synthétisés lors d'une opération d'enregistrement ou de désenregistrement dans Tk.

Lorsqu'un événement de la file d'attente doit être traité (étapes 1 et 4 ci-dessus), Tcl_ServiceEvent appellera le proc spécifié dans la première structure Tcl_Event qui a été mise en file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

Le premier argument du proc est un pointeur vers l'événement, qui sera le même que le premier argument de l'appel à Tcl_QueueEvent qui a ajouté l'événement à la file d'attente. Le deuxième argument du proc est le flags pour l'appel actuel à Tcl_ServiceEvent ; ceci est utilisé par la source d'événements pour revenir immédiatement si ses événements ne sont pas pertinents.

Il incombe au proc de traiter l'événement, généralement en appelant une ou plusieurs commandes Tcl ou callbacks C. Une fois que la source d'événements a terminé de traiter l'événement, elle retourne 1 pour indiquer que l'événement peut être retiré de la file d'attente. Si, pour une raison quelconque, la source d'événements décide que l'événement ne peut pas être traité pour le moment, elle peut retourner 0 pour indiquer que l'événement doit être différé pour être traité plus tard ; dans ce cas, Tcl_ServiceEvent passera à l'événement suivant dans la file d'attente et essaiera de le traiter. Il existe plusieurs raisons pour lesquelles une source d'événements pourrait différer un événement. Une possibilité est que les événements de ce type soient exclus par l'argument flags. Par exemple, la source d'événements de fichier retourne toujours 0 si le bit TCL_FILE_EVENTS n'est pas activé dans flags. Un autre exemple de report d'événements se produit dans Tk si Tk_RestrictEvents a été appelé pour reporter certains types d'événements de fenêtre.

Lorsque proc retourne 1, Tcl_ServiceEvent retirera l'événement de la file d'attente et libérera son stockage. Vous devez noter que le stockage d'un événement doit être alloué par la source d'événements (en utilisant Tcl_Alloc ou la macro Tcl ckalloc) avant d'appeler Tcl_QueueEvent, mais il sera libéré par Tcl_ServiceEvent, et non par la source d'événements.

Les applications multithreads fonctionnent de manière similaire, à moins qu'il n'y ait une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. Appeler Tcl_QueueEvent dans une application multithread ajoute un événement à la file d'attente du thread actuel. Pour ajouter un événement à la file d'attente d'un autre thread, utilisez Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent accepte comme argument un Tcl_ThreadId, qui identifie un thread unique dans une application Tcl. Pour obtenir le Tcl_ThreadId du thread actuel, utilisez la procédure Tcl_GetCurrentThread. (Un thread devrait passer cet identifiant à d'autres threads afin qu'ils puissent ajouter des événements à sa file d'attente.) Après avoir ajouté un événement à la file d'attente d'un autre thread, vous devez généralement appeler Tcl_ThreadAlert pour "réveiller" le gestionnaire du thread afin de l'alerter du nouvel événement.

Tcl_DeleteEvents peut être utilisé explicitement pour supprimer un ou plusieurs événements de la file d'attente des événements. Tcl_DeleteEvents appelle le proc pour chaque événement dans la file d'attente, supprimant ceux dont la procédure retourne 1. Les événements dont la procédure retourne 0 restent dans la file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

L'argument clientData sera le même que l'argument clientData de la procédure Tcl_DeleteE

vents; il est typiquement utilisé pour pointer vers des informations privées gérées par la source d'événements. Le evPtr pointera vers l'événement suivant dans la file d'attente.

Tcl_DeleteEventSource supprime une source d'événements. Les arguments setupProc, checkProc et clientData doivent correspondre exactement à ceux fournis à Tcl_CreateEventSource pour que la source d'événements soit supprimée. Si aucune source de ce type n'existe, Tcl_DeleteEventSource n'a aucun effet.

CRÉER UN NOUVEAU NOTIFICATEUR

Le notificateur est constitué de toutes les procédures décrites dans cette entrée de manuel, plus Tcl_DoOneEvent et Tcl_Sleep, qui sont disponibles sur toutes les plateformes, et Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont spécifiques à Unix. La plupart de ces procédures sont génériques, dans le sens où elles sont identiques pour tous les notificateurs. Cependant, aucune des procédures n'est indépendante du notificateur : Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler et Tcl_ServiceModeHook. Pour supporter une nouvelle plateforme ou pour intégrer Tcl à une boucle d'événements spécifique à une application, vous devez écrire de nouvelles versions de ces procédures.

Tcl_InitNotifier initialise l'état du notificateur et retourne un handle vers l'état du notificateur. Tcl appelle cette procédure lors de l'initialisation d'un interpréteur Tcl. De même, Tcl_FinalizeNotifier arrête le notificateur et est appelée par Tcl_Finalize lors de l'arrêt d'un interpréteur Tcl.

Tcl_WaitForEvent est la procédure la plus bas niveau du notificateur ; elle est responsable de l'attente d'un événement « intéressant » qui se produit ou de l'expiration d'un délai donné. Avant que Tcl_WaitForEvent ne soit invoquée, chacune des procédures de configuration des sources d'événements aura été appelée. L'argument timePtr de Tcl_WaitForEvent donne le temps maximum d'attente bloquante pour un événement, basé sur les appels à Tcl_SetMaxBlockTime effectués par les procédures de configuration et sur d'autres informations (telles que le bit TCL_DONT_WAIT dans flags).

Idéalement, Tcl_WaitForEvent ne devrait attendre qu'un événement ; elle ne devrait pas réellement traiter l'événement de quelque manière que ce soit. Plus tard, les sources d'événements traiteront les événements bruts et créeront des Tcl_Events dans la file d'attente d'événements dans leurs procédures checkProc. Cependant, sur certaines plateformes (comme Windows) ce n'est pas possible ; les événements peuvent être traités dans Tcl_WaitForEvent, y compris la mise en file d'attente de Tcl_Events et plus encore (par exemple, des callbacks pour les widgets natifs peuvent être invoqués). La valeur de retour de Tcl_WaitForEvent doit être 0, 1 ou -1. Sur les plateformes comme Windows où les événements sont traités dans Tcl_WaitForEvent, une valeur de retour de 1 signifie qu'il peut y avoir d'autres événements en attente qui n'ont pas été traités. C'est un signe pour l'appelant qu'il doit rappeler Tcl_WaitForEvent s'il veut que tous les événements en attente soient traités. Une valeur de retour de 0 signifie qu'appeler à nouveau Tcl_WaitForEvent n'aura aucun effet : soit c'est une plateforme où Tcl_WaitForEvent ne fait qu'attendre sans traiter aucun événement, soit Tcl_WaitForEvent sait avec certitude qu'il n'y a pas d'événements supplémentaires à traiter (par exemple, elle est revenue parce que le temps a expiré). Enfin, une valeur de retour de -1 signifie que la boucle d'événements n'est plus opérationnelle et que l'application devrait probablement se dérouler et se terminer. Sous Windows, cela se produit lorsqu'un message WM_QUIT est reçu ; sous Unix, cela se produit lorsque Tcl_WaitForEvent aurait attendu éternellement car il n'y avait pas de sources d'événements actives et que le délai était infini.

Tcl_AlertNotifier est utilisé dans les applications multithreadées pour permettre à n'importe quel thread de « réveiller » le notificateur pour l'alerter de nouveaux événements dans sa file d'attente. Tcl_AlertNotifier nécessite comme argument le handle du notificateur retourné par Tcl_InitNotifier.

Si le notificateur doit être utilisé avec une boucle d'événements externe, il doit également supporter l'interface Tcl_SetTimer. Tcl_SetTimer est invoqué par Tcl_SetMaxBlockTime chaque fois que le temps de blocage maximum a été réduit. Tcl_SetTimer doit organiser la boucle d'événements externe pour qu'elle appelle Tcl_ServiceAll après l'intervalle spécifié même si aucun événement ne s'est produit. Cette interface est nécessaire car Tcl_WaitForEvent n'est pas invoqué en présence d'une boucle d'événements externe. Si le notificateur ne doit être utilisé qu'à partir de Tcl_DoOneEvent, alors Tcl_SetTimer n'a pas besoin de faire quoi que ce soit.

Tcl_ServiceModeHook est appelé par la partie indépendante de la plateforme du notificateur lorsque le code client effectue un appel à Tcl_SetServiceMode. Ce hook est fourni pour supporter les systèmes d'exploitation qui nécessitent un traitement d'événements spécial lorsque l'application est dans une boucle modale (le notificateur Windows, par exemple, utilise ce hook pour créer une fenêtre de communication).

Sur les systèmes Unix, la source d'événements de fichier nécessite également le support du notificateur. La source d'événements de fichier est constituée des procédures Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont décrites dans la page de manuel Tcl_CreateFileHandler.

Les interfaces Tcl_Sleep et Tcl_DoOneEvent sont décrites dans leurs pages de manuel respectives.

Le moyen le plus simple de créer un nouveau notificateur est de consulter le code d'un notificateur existant, tel que les fichiers unix/tclUnixNotfy.c ou win/tclWinNotify.c dans la distribution source de Tcl.

REMPLACER LE NOTIFICATEUR

Un notificateur écrit selon les conventions ci-dessus peut également être installé dans un processus en cours d'exécution à la place du notificateur standard. Ce mécanisme est utilisé pour qu'un seul exécutable puisse être utilisé (avec le notificateur standard) comme programme autonome et réutilisé (avec un notificateur de remplacement dans une extension chargeable) comme extension d'un autre programme, tel qu'un plugin de navigateur Web.

Pour ce faire, l'extension effectue un appel à Tcl_SetNotifier en passant un pointeur vers une structure de données Tcl_NotifierProcs. La structure a la disposition suivante :

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Suite à l'appel à Tcl_SetNotifier, les pointeurs fournis dans la structure Tcl_NotifierProcs remplacent tout notificateur qui avait été installé dans le processus.

Il est extraordinairement imprudent de remplacer un notificateur en cours d'exécution. Normalement, Tcl_SetNotifier doit être appelé au moment de l'initialisation du processus, avant le premier appel à Tcl_InitNotifier.

BOUCLES D'ÉVÉNEMENTS EXTERNES

Les interfaces du notificateur sont conçues de manière à ce que Tcl puisse être intégrée dans des applications qui ont leurs propres boucles d'événements privées. Dans ce cas, l'application n'appelle pas Tcl_DoOneEvent sauf en cas de boucles d'événements récursives telles que les appels aux commandes Tcl update ou vwait. La majeure partie du temps est passée dans la boucle d'événements externe de l'application. Dans ce cas, le notificateur doit organiser la boucle d'événements externe pour qu'elle rappelle Tcl lorsque quelque chose se produit sur les différentes sources d'événements Tcl. Ces rappels doivent organiser l'ajout des événements Tcl appropriés dans la file d'attente d'événements Tcl.

Étant donné que la boucle d'événements externe n'appelle pas Tcl_DoOneEvent régulièrement, il incombe au notificateur d'organiser l'appel à Tcl_ServiceEvent chaque fois que des événements sont en attente dans la file d'attente d'événements Tcl. Le moyen le plus simple de le faire est d'invoquer Tcl_ServiceAll à la fin de chaque rappel de la boucle d'événements externe. Cela garantira que toutes les sources d'événements sont interrogées, que tous les événements mis en file d'attente sont traités et que tous les gestionnaires inactifs en attente sont traités avant de rendre le contrôle à l'application. De plus, les sources d'événements qui ont besoin d'interroger les événements peuvent appeler Tcl_SetMaxBlockTime pour forcer la boucle d'événements externe à appeler Tcl même si aucun événement n'est disponible dans la file d'attente système d'événements.

Comme effet secondaire du traitement des événements détectés dans la boucle d'événements externe principale, Tcl peut invoquer Tcl_DoOneEvent pour démarrer une boucle d'événements récursive dans des commandes comme vwait. Tcl_DoOneEvent invoquera la boucle d'événements externe, ce qui entraînera des rappels comme décrit dans le paragraphe précédent, ce qui entraînera des appels à Tcl_ServiceAll. Cependant, dans ces cas, il est indésirable de traiter les événements dans Tcl_ServiceAll. Le traitement des événements là-bas est inutile car le contrôle retournera immédiatement à la boucle d'événements externe et donc à Tcl_DoOneEvent, qui peut traiter les événements elle-même. De plus, Tcl_DoOneEvent est censé traiter un seul événement, tandis que Tcl_ServiceAll traite normalement tous les événements en attente. Pour gérer cette situation, Tcl_DoOneEvent définit un drapeau pour Tcl_ServiceAll qui lui fait retourner sans traiter aucun événement. Ce drapeau est appelé le mode de service ; Tcl_DoOneEvent le restaure à sa valeur précédente avant de retourner.

Dans certains cas, cependant, il peut être nécessaire que Tcl_ServiceAll traite les événements même lorsqu'il a été invoqué par Tcl_DoOneEvent. Cela se produit lorsqu'il existe une autre boucle d'événements récursive invoquée via un gestionnaire d'événements appelé par Tcl_DoOneEvent (tel qu'un composant d'un widget natif). Dans ce cas, Tcl_DoOneEvent peut ne pas avoir la possibilité de traiter les événements, donc Tcl_ServiceAll doit tous les traiter. Toute boucle d'événements récursive qui appelle une boucle d'événements externe plutôt que Tcl_DoOneEvent doit réinitialiser le mode de service afin que tous les événements soient traités dans Tcl_ServiceAll. Ceci est fait en invoquant la procédure Tcl_SetServiceMode. Si Tcl_SetServiceMode reçoit TCL_SERVICE_NONE, alors les appels à Tcl_ServiceAll retourneront immédiatement sans traiter aucun événement. Si Tcl_SetServiceMode reçoit TCL_SERVICE_ALL, alors les appels à Tcl_ServiceAll se comporteront normalement. Tcl_SetServiceMode retourne la valeur précédente du mode de service, qui doit être restaurée à la sortie de la boucle récursive. Tcl_GetServiceMode retourne la valeur actuelle du mode de service.
