INTRODUCTION

Les interfaces décrites ici sont utilisées pour personnaliser la boucle d'événements Tcl. Les deux personnalisations les plus courantes sont l'ajout de nouvelles sources d'événements et la fusion de la boucle d'événements Tcl avec une autre boucle d'événements, telle que celle fournie par une application dans laquelle Tcl est intégré. Chacune de ces tâches est décrite dans une section distincte ci-dessous.

Les procédures de cette entrée de manuel sont les éléments constitutifs de la construction du notifier d'événements Tcl. Le notifier d'événements est la couche la plus basse du mécanisme d'événements Tcl. Il se compose de trois éléments :

[1]
Sources d'événements : elles représentent les moyens par lesquels des événements peuvent être générés. Par exemple, il existe une source d'événements de minuterie qui implémente la procédure Tcl_CreateTimerHandler et la commande after, et il existe une source d'événements de fichier qui implémente la procédure Tcl_CreateFileHandler sur les systèmes Unix. Une source d'événements doit fonctionner avec le notifier pour détecter les événements aux moments opportuns, les enregistrer dans la file d'attente des événements et informer finalement le logiciel de niveau supérieur qu'ils se sont produits. Les procédures Tcl_CreateEventSource, Tcl_DeleteEventSource, Tcl_SetMaxBlockTime, Tcl_QueueEvent et Tcl_DeleteEvents sont principalement utilisées par les sources d'événements.
[2]
La file d'attente d'événements : pour les applications non multithread, il existe une seule file d'attente pour l'ensemble de l'application, contenant les événements qui ont été détectés mais pas encore traités. Les sources d'événements placent les événements dans la file d'attente afin qu'ils puissent être traités dans l'ordre à des moments appropriés pendant la boucle d'événements. La file d'attente d'événements garantit une discipline équitable de traitement des événements, de sorte qu'aucune source d'événements ne puisse affamer les autres. Elle permet également de sauvegarder des événements pour un traitement ultérieur. Les applications multithread fonctionnent de manière similaire, sauf qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. Tcl_QueueEvent est utilisée (principalement par les sources d'événements) pour ajouter des événements à la file d'attente des événements et Tcl_DeleteEvents est utilisée pour supprimer des événements de la file d'attente sans les traiter. Dans une application multithread, Tcl_QueueEvent ajoute un événement à la file d'attente du thread courant, et Tcl_ThreadQueueEvent ajoute un événement à la file d'attente d'un thread spécifique.
[3]
La boucle d'événements : pour détecter et traiter les événements, l'application entre dans une boucle qui attend que des événements se produisent, les place dans la file d'attente des événements, puis les traite. La plupart des applications le feront en appelant la procédure Tcl_DoOneEvent, qui est décrite dans une entrée de manuel séparée.

La plupart des applications Tcl n'ont pas besoin de se soucier des détails internes du notifier Tcl. Cependant, le notifier est maintenant suffisamment flexible pour être redirigé soit vers une nouvelle plateforme, soit pour utiliser une boucle d'événements externe (telle que la boucle d'événements Motif, lorsque Tcl est intégré dans une application Motif). Les procédures Tcl_WaitForEvent et Tcl_SetTimer sont normalement implémentées par Tcl, mais peuvent être remplacées par de nouvelles versions pour rediriger le notifier (les procédures Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler et Tcl_DeleteFileHandler doivent également être remplacées ; voir CRÉATION D'UN NOUVEAU NOTIFIER ci-dessous pour plus de détails). Les procédures Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode et Tcl_SetServiceMode sont fournies pour aider à connecter la boucle d'événements Tcl à une boucle d'événements externe telle que celle de Motif.

BASES DU NOTIFIER

La manière la plus simple de comprendre le fonctionnement du notifier est de considérer ce qui se passe lorsque Tcl_DoOneEvent est appelée. Tcl_DoOneEvent reçoit un argument flags qui indique quels types d'événements peuvent être traités et s'il faut bloquer s'il n'y a pas d'événements prêts. Tcl_DoOneEvent effectue les actions suivantes :

[1]
Vérifie la file d'attente des événements pour voir si elle contient des événements pouvant être traités. Si c'est le cas, traite le premier événement possible, le retire de la file d'attente et retourne. Elle le fait en appelant Tcl_ServiceEvent et en lui passant l'argument flags.
[2]
Se prépare à bloquer pour un événement. Pour ce faire, Tcl_DoOneEvent appelle une procédure de préparation dans chaque source d'événements. La source d'événements effectuera l'initialisation spécifique à la source d'événements et appellera éventuellement Tcl_SetMaxBlockTime pour limiter la durée pendant laquelle Tcl_WaitForEvent bloquera si aucun nouvel événement ne se produit.
[3]
Appelle Tcl_WaitForEvent. Cette procédure est implémentée différemment selon les plateformes ; elle attend qu'un événement se produise, en se basant sur les informations fournies par les sources d'événements. Elle peut provoquer le blocage de l'application si timePtr spécifie un intervalle autre que 0. Tcl_WaitForEvent retourne lorsqu'un événement s'est produit, tel qu'un fichier devenu lisible ou l'expiration de l'intervalle spécifié par timePtr. S'il n'y a aucun événement pour lequel Tcl_WaitForEvent puisse attendre, de sorte qu'elle bloquerait indéfiniment, alors elle retourne immédiatement et Tcl_DoOneEvent retourne 0.
[4]
Appelle une procédure de vérification dans chaque source d'événements. La procédure de vérification détermine si des événements intéressant cette source se sont produits. Si c'est le cas, les événements sont ajoutés à la file d'attente des événements.
[5]
Vérifie la file

CRÉATION D'UNE NOUVELLE SOURCE D'ÉVÉNEMENTS

Une source d'événements se compose de trois procédures appelées par le dispatching, plus des procédures C supplémentaires appelées par du code de niveau supérieur pour organiser les rappels d'événements basés sur le temps. Les trois procédures appelées par le dispatching incluent les procédures de configuration et de vérification décrites précédemment, plus une procédure supplémentaire appelée lorsqu'un événement est retiré de la file d'attente des événements pour être traité.

La procédure Tcl_CreateEventSource crée une nouvelle source d'événements. Ses arguments spécifient les procédures de configuration et de vérification pour la source d'événements. SetupProc doit correspondre au prototype suivant :

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

L'argument clientData sera le même que l'argument clientData de Tcl_CreateEventSource ; il est généralement utilisé pour pointer vers des informations privées gérées par la source d'événements. L'argument flags sera le même que l'argument flags passé à Tcl_DoOneEvent, sauf qu'il ne sera jamais 0 (Tcl_DoOneEvent remplace 0 par TCL_ALL_EVENTS). Flags indique quels types d'événements doivent être considérés ; si le bit correspondant à cette source d'événements n'est pas défini, la source d'événements doit retourner immédiatement sans effectuer aucune action. Par exemple, la source d'événements de fichiers vérifie le bit TCL_FILE_EVENTS.

La procédure SetupProc doit s'assurer que l'application est surveillée lorsque des événements du type souhaité se produisent. Ceci est généralement effectué de manière spécifique à la plateforme. Par exemple, sous Unix, une source d'événements pourrait appeler Tcl_CreateFileHandler ; sous Windows, elle pourrait demander une notification avec un événement Windows. Pour les sources d'événements basées sur des délais, comme les événements temporels ou tout événement interrogé, la source d'événements peut appeler Tcl_SetMaxBlockTime pour forcer l'application à surveiller après un délai spécifié même s'il n'y a pas d'événements. Si aucune source d'événements n'appelle Tcl_SetMaxBlockTime, Tcl_WaitForEvent attendra aussi longtemps que nécessaire pour qu'un événement se produise ; sinon, elle n'attendra que le délai le plus court passé à Tcl_SetMaxBlockTime par l'une des sources d'événements. Si la source d'événements sait qu'elle a déjà des événements prêts à signaler, elle peut demander un temps de blocage maximal de 0. Par exemple, la procédure de configuration de la source d'événements X vérifie s'il y a déjà des événements en file d'attente. S'il y en a, elle appelle Tcl_SetMaxBlockTime avec un temps de blocage de 0 afin que Tcl_WaitForEvent ne se bloque pas s'il n'y a pas de nouvelles données sur la connexion X. L'argument timePtr de Tcl_WaitForEvent pointe vers une structure décrivant un intervalle de temps en secondes et microsecondes :

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

Le champ usec doit être inférieur à 1 000 000.

Les informations fournies à Tcl_SetMaxBlockTime sont utilisées uniquement pour le prochain appel à Tcl_WaitForEvent ; elles sont ignorées après le retour de Tcl_WaitForEvent. La prochaine fois qu'une attente d'événement aura lieu, chaque procédure de configuration des sources d'événements sera appelée à nouveau, et elles pourront spécifier de nouvelles informations pour cette attente d'événement.

Si l'application utilise une boucle d'événements externe au lieu de Tcl_DoOneEvent, les sources d'événements peuvent avoir besoin d'appeler Tcl_SetMaxBlockTime à d'autres moments. Par exemple, si un nouveau gestionnaire d'événements qui doit être interrogé est enregistré, la source d'événements peut appeler Tcl_SetMaxBlockTime pour définir un temps de blocage de 0, forçant la boucle d'événements externe à appeler Tcl. Dans ce cas, Tcl_SetMaxBlockTime appelle Tcl_SetTimer avec le délai le plus court vu depuis le dernier appel à Tcl_DoOneEvent ou Tcl_ServiceAll.

En plus de la procédure générique Tcl_SetMaxBlockTime, d'autres procédures spécifiques à la plateforme peuvent être disponibles pour le setupProc, si des informations supplémentaires sont nécessaires à Tcl_WaitForEvent sur cette plateforme. Par exemple, sur les systèmes Unix, l'interface Tcl_CreateFileHandler peut être utilisée pour attendre les événements de fichier.

La deuxième procédure fournie par chaque source d'événements est sa procédure de vérification, indiquée par l'argument checkProc de Tcl_CreateEventSource. CheckProc doit correspondre au prototype suivant :

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Les arguments de cette procédure sont les mêmes que ceux de setupProc. CheckProc est appelé par Tcl_DoOneEvent après l'attente des événements. Bien qu'au moins une des sources d'événements soit préparée pour mettre en file d'attente un événement, Tcl_DoOneEvent appelle chaque source d'événements dans l'ordre, permettant à tous les événements prêts d'être mis en file d'attente. La procédure de vérification doit faire deux choses. Premièrement, elle doit vérifier s'il y a des événements qui se sont déclenchés. Différentes sources d'événements le font de différentes manières.

Si une source d'événements détecte un événement intéressant, elle doit ajouter l'événement à la file d'attente de Tcl. Pour ce faire, la source d'événements appelle Tcl_QueueEvent. L'argument evPtr est un pointeur vers une structure allouée dynamiquement qui contient l'événement (voir plus loin pour les problèmes de gestion de la mémoire). Chaque source d'événements peut définir sa propre structure d'événement avec les informations pertinentes pour cette source d'événements. Cependant, le premier membre de la structure doit être une structure de type Tcl_Event, et le pointeur vers cette structure est utilisé lors de la communication entre la source d'événements et le reste du dispatching. Une Tcl_Event a la définition suivante :

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La source d'événements doit remplir le champ proc de la structure avant d'appeler Tcl_QueueEvent. Le nextPtr est utilisé pour chaîner les événements dans la file d'attente et ne doit pas être modifié par la source d'événements.

Un événement peut être ajouté à la file d'attente dans l'une des trois positions, en fonction de l'argument position de Tcl_QueueEvent :

TCL_QUEUE_TAIL
Ajoute l'événement à la fin de la file d'attente, de sorte que tous les événements en attente soient traités en premier. C'est presque toujours la bonne position pour les nouveaux événements.
TCL_QUEUE_HEAD
Ajoute l'événement au début de la file d'attente, de sorte qu'il soit traité avant les autres événements dans la file d'attente.
TCL_QUEUE_MARK
Ajoute l'événement au début de la file d'attente, à moins qu'il n'y ait d'autres événements au début avec la position TCL_QUEUE_MARK. Si c'est le cas, le nouvel événement est ajouté juste après tous les événements TCL_QUEUE_MARK existants. Cette valeur de position est utilisée pour insérer une séquence ordonnée d'événements au début de la file d'attente, comme une série d'événements Enter et Leave générés lors d'une opération de capture ou de libération dans Tk.

Lorsqu'il est temps de traiter un événement de la file d'attente (étapes 1 et 4 ci-dessus), Tcl_ServiceEvent appellera le proc spécifié dans la première structure Tcl_Event qui a été mise en file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

Le premier argument de proc est un pointeur vers l'événement, qui sera le même que le premier argument de l'appel à Tcl_QueueEvent qui a ajouté l'événement à la file d'attente. Le deuxième argument de proc est le flags de l'appel actuel à Tcl_ServiceEvent ; il est utilisé par la source d'événements pour retourner immédiatement si ses événements ne sont pas pertinents.

Il incombe à proc de traiter l'événement, en appelant généralement une ou plusieurs commandes Tcl ou des rappels de niveau C. Une fois que la source d'événements a fini de traiter l'événement, elle retourne 1 pour indiquer que l'événement peut être retiré de la file d'attente. Si, pour une raison quelconque, la source d'événements décide que l'événement ne peut pas être traité à ce moment-là, elle peut retourner 0 pour indiquer que l'événement doit être différé à une date ultérieure. Dans ce cas, Tcl_ServiceEvent passera à l'événement suivant dans la file d'attente et tentera de le traiter. Il existe plusieurs raisons pour lesquelles une source d'événements pourrait différer un événement. Une possibilité est que les événements de ce type soient exclus par l'argument flags. Par exemple, la source d'événements de fichier retourne toujours 0 si le bit TCL_FILE_EVENTS n'est pas défini dans flags. Un autre exemple de report d'événements se produit dans Tk lorsque Tk_RestrictEvents a été appelé pour reporter certains types d'événements de fenêtre.

Lorsque proc retourne 1, Tcl_ServiceEvent retirera l'événement de la file d'attente et libérera son espace mémoire. Il convient de noter que l'espace mémoire d'un événement doit être alloué par la source d'événements (en utilisant Tcl_Alloc ou la macro Tcl ckalloc) avant d'appeler Tcl_QueueEvent, mais il sera libéré par Tcl_ServiceEvent, et non par la source d'événements.

Les applications multithreadées fonctionnent de manière similaire, mais il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. L'appel à Tcl_QueueEvent dans une application multithreadée ajoute un événement à la file d'attente du thread courant. Pour ajouter un événement à la file d'attente d'un autre thread, utilisez Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent accepte comme argument un Tcl_ThreadId, qui identifie de manière unique un thread dans une application Tcl. Pour obtenir le Tcl_ThreadId du thread courant, utilisez la procédure Tcl_GetCurrentThread. (Un thread devrait passer cet identifiant à d'autres threads afin qu'ils puissent ajouter des événements à sa file d'attente.) Après avoir ajouté un événement à la file d'attente d'un autre thread, il est généralement nécessaire d'appeler Tcl_ThreadAlert pour "réveiller" ce thread et l'alerter du nouvel événement.

Tcl_DeleteEvents peut être utilisé explicitement pour supprimer un ou plusieurs événements de la file d'attente des événements. Tcl_DeleteEvents appelle le proc pour chaque événement dans la file d'attente, en supprimant ceux dont la procédure retourne 1. Les événements dont la procédure retourne 0 restent dans la file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

L'argument clientData sera le même que l'argument clientData de Tcl_DeleteEvents ;

b> ; il est typiquement utilisé pour pointer vers des informations privées gérées par la source d'événements. Le evPtr pointera vers l'événement suivant dans la file d'attente.

Tcl_DeleteEventSource supprime une source d'événements. Les arguments setupProc, checkProc et clientData doivent correspondre exactement à ceux fournis à Tcl_CreateEventSource pour que la source d'événements soit supprimée. Si aucune source de ce type n'existe, Tcl_DeleteEventSource n'a aucun effet.

CRÉATION D'UN NOUVEAU NOTIFIER

Le notifier est constitué de toutes les procédures décrites dans cette entrée de manuel, plus Tcl_DoOneEvent et Tcl_Sleep, qui sont disponibles sur toutes les plateformes, et Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont spécifiques à Unix. La plupart de ces procédures sont génériques, en ce sens qu'elles sont les mêmes pour tous les notifiers. Cependant, aucune des procédures n'est indépendante du notifier : Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler et Tcl_ServiceModeHook. Pour prendre en charge une nouvelle plateforme ou pour intégrer Tcl avec une boucle d'événements spécifique à une application, vous devez écrire de nouvelles versions de ces procédures.

Tcl_InitNotifier initialise l'état du notifier et retourne un handle vers l'état du notifier. Tcl appelle cette procédure lors de l'initialisation d'un interpréteur Tcl. De même, Tcl_FinalizeNotifier arrête le notifier et est appelée par Tcl_Finalize lors de l'arrêt d'un interpréteur Tcl.

Tcl_WaitForEvent est la procédure de plus bas niveau dans le notifier ; elle est responsable de l'attente d'un événement “intéressant” ou de l'expiration d'un délai donné. Avant que Tcl_WaitForEvent ne soit invoquée, chaque procédure de configuration des sources d'événements aura été appelée. L'argument timePtr de Tcl_WaitForEvent donne le temps maximal de blocage pour un événement, basé sur les appels à Tcl_SetMaxBlockTime effectués par les procédures de configuration et sur d'autres informations (comme le bit TCL_DONT_WAIT dans flags).

Idéalement, Tcl_WaitForEvent ne devrait attendre qu'un événement se produise ; elle ne devrait pas réellement traiter l'événement de quelque manière que ce soit. Plus tard, les sources d'événements traiteront les événements bruts et créeront des Tcl_Events dans la file d'événements dans leurs procédures checkProc. Cependant, sur certaines plateformes (comme Windows), cela n'est pas possible ; les événements peuvent être traités dans Tcl_WaitForEvent, y compris la mise en file d'attente de Tcl_Events et plus encore (par exemple, des rappels pour les widgets natifs peuvent être invoqués). La valeur de retour de Tcl_WaitForEvent doit être 0, 1 ou -1. Sur les plateformes comme Windows où les événements sont traités dans Tcl_WaitForEvent, une valeur de retour de 1 signifie qu'il peut y avoir encore des événements en attente qui n'ont pas été traités. C'est un signe pour l'appelant qu'il doit appeler à nouveau Tcl_WaitForEvent s'il veut que tous les événements en attente soient traités. Une valeur de retour de 0 signifie que l'appel à nouveau de Tcl_WaitForEvent n'aura aucun effet : soit c'est une plateforme où Tcl_WaitForEvent attend seulement sans traiter d'événements, soit Tcl_WaitForEvent sait avec certitude qu'il n'y a pas d'événements supplémentaires à traiter (par exemple, elle est revenue parce que le temps s'est écoulé). Enfin, une valeur de retour de -1 signifie que la boucle d'événements n'est plus opérationnelle et que l'application devrait probablement se dérouler et se terminer. Sous Windows, cela se produit lorsqu'un message WM_QUIT est reçu ; sous Unix, cela se produit lorsque Tcl_WaitForEvent aurait attendu indéfiniment car il n'y avait pas de sources d'événements actives et que le délai était infini.

Tcl_AlertNotifier est utilisé dans les applications multithreads pour permettre à n'importe quel thread de “réveiller” le notifier pour l'alerter de nouveaux événements dans sa file d'attente. Tcl_AlertNotifier nécessite en argument le handle du notifier retourné par Tcl_InitNotifier.

Si le notifier doit être utilisé avec une boucle d'événements externe, il doit également prendre en charge l'interface Tcl_SetTimer. Tcl_SetTimer est appelée par Tcl_SetMaxBlockTime chaque fois que le temps de blocage maximal a été réduit. Tcl_SetTimer doit faire en sorte que la boucle d'événements externe appelle Tcl_ServiceAll après l'intervalle spécifié, même si aucun événement ne s'est produit. Cette interface est nécessaire car Tcl_WaitForEvent n'est pas appelée lorsqu'il y a une boucle d'événements externe. Si le notifier ne doit être utilisé qu'à partir de Tcl_DoOneEvent, alors Tcl_SetTimer n'a pas besoin de faire quoi que ce soit.

Tcl_ServiceModeHook est appelée par la partie indépendante de la plateforme du notifier lorsque le code client appelle Tcl_SetServiceMode. Ce hook est fourni pour prendre en charge les systèmes d'exploitation qui nécessitent une gestion spéciale des événements lorsque l'application est dans une boucle modale (le notifier Windows, par exemple, utilise ce hook pour créer une fenêtre de communication).

Sur les systèmes Unix, la source d'événements de fichier a également besoin du support du notifier. La source d'événements de fichier est composée des procédures Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont décrites dans la page de manuel de Tcl_CreateFileHandler.

Les interfaces Tcl_Sleep et Tcl_DoOneEvent sont décrites dans leurs pages de manuel respectives.

La manière la plus simple de créer un nouveau notifier est de consulter le code d'un notifier existant, tel que les fichiers unix/tclUnixNotfy.c ou win/tclWinNotify.c dans la distribution source de Tcl.

REMPLACEMENT DU NOTIFIER

Un notifier qui a été écrit selon les conventions ci-dessus peut également être installé dans un processus en cours d'exécution à la place du notifier standard. Ce mécanisme est utilisé pour qu'un seul exécutable puisse être utilisé (avec le notifier standard) comme programme autonome et réutilisé (avec un notifier de remplacement dans une extension chargeable) comme extension d'un autre programme, tel qu'un plugin de navigateur Web.

Pour ce faire, l'extension appelle Tcl_SetNotifier en passant un pointeur vers une structure de données Tcl_NotifierProcs. La structure a la disposition suivante :

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Après l'appel à Tcl_SetNotifier, les pointeurs fournis dans la structure Tcl_NotifierProcs remplacent tout notifier qui avait été installé dans le processus.

Il est extraordinairement imprudent de remplacer un notifier en cours d'exécution. Normalement, Tcl_SetNotifier doit être appelé au moment de l'initialisation du processus, avant le premier appel à Tcl_InitNotifier.

BOUCLES D'ÉVÉNEMENTS EXTERNES

Les interfaces du notifier sont conçues pour que Tcl puisse être intégré dans des applications qui ont leurs propres boucles d'événements privées. Dans ce cas, l'application n'appelle pas Tcl_DoOneEvent, sauf dans le cas de boucles d'événements récursives telles que les appels aux commandes Tcl update ou vwait. La plupart du temps est passé dans la boucle d'événements externe de l'application. Dans ce cas, le notifier doit faire en sorte que la boucle d'événements externe rappelle Tcl lorsque quelque chose se produit sur les diverses sources d'événements Tcl. Ces rappels doivent organiser la mise en place des événements Tcl appropriés dans la file d'événements Tcl.

Étant donné que la boucle d'événements externe n'appelle pas Tcl_DoOneEvent régulièrement, il incombe au notifier de faire en sorte que Tcl_ServiceEvent soit appelé chaque fois que des événements sont en attente dans la file d'événements Tcl. Le moyen le plus simple de le faire est d'invoquer Tcl_ServiceAll à la fin de chaque rappel de la boucle d'événements externe. Cela garantira que toutes les sources d'événements sont interrogées, que tous les événements mis en file d'attente sont traités et que tous les gestionnaires inactifs en attente sont traités avant de restituer le contrôle à l'application. De plus, les sources d'événements qui doivent interroger les événements peuvent appeler Tcl_SetMaxBlockTime pour forcer la boucle d'événements externe à appeler Tcl même si aucun événement n'est disponible dans la file d'événements système.

En tant qu'effet secondaire du traitement des événements détectés dans la boucle d'événements externe principale, Tcl peut invoquer Tcl_DoOneEvent pour démarrer une boucle d'événements récursive dans des commandes comme vwait. Tcl_DoOneEvent appellera la boucle d'événements externe, ce qui entraînera des rappels comme décrit dans le paragraphe précédent, ce qui entraînera des appels à Tcl_ServiceAll. Cependant, dans ces cas, il est indésirable de traiter les événements dans Tcl_ServiceAll. Le traitement des événements là est inutile car le contrôle reviendra immédiatement à la boucle d'événements externe et donc à Tcl_DoOneEvent, qui peut traiter les événements elle-même. De plus, Tcl_DoOneEvent est censé ne traiter qu'un seul événement, tandis que Tcl_ServiceAll traite normalement tous les événements en attente. Pour gérer cette situation, Tcl_DoOneEvent définit un indicateur pour Tcl_ServiceAll qui lui fait retourner sans traiter d'événements. Cet indicateur est appelé le mode de service ; Tcl_DoOneEvent le restaure à sa valeur précédente avant de retourner.

Dans certains cas, cependant, il peut être nécessaire que Tcl_ServiceAll traite les événements même lorsqu'il a été invoqué par Tcl_DoOneEvent. Cela se produit lorsqu'il existe une autre boucle d'événements récursive invoquée via un gestionnaire d'événements appelé par Tcl_DoOneEvent (tel qu'un qui fait partie d'un widget natif). Dans ce cas, Tcl_DoOneEvent peut ne pas avoir la chance de traiter les événements, donc Tcl_ServiceAll doit tous les traiter. Toute boucle d'événements récursive qui appelle une boucle d'événements externe plutôt que Tcl_DoOneEvent doit réinitialiser le mode de service afin que tous les événements soient traités dans Tcl_ServiceAll. Cela se fait en invoquant la procédure Tcl_SetServiceMode. Si Tcl_SetServiceMode reçoit TCL_SERVICE_NONE, alors les appels à Tcl_ServiceAll retourneront immédiatement sans traiter d'événements. Si Tcl_SetServiceMode reçoit TCL_SERVICE_ALL, alors les appels à Tcl_ServiceAll se comporteront normalement. Tcl_SetServiceMode retourne la valeur précédente du mode de service, qui doit être restaurée lorsque la boucle récursive se termine. Tcl_GetServiceMode retourne la valeur actuelle du mode de service.

Pendant que le système de la machine à sous est un simulateur, il fonctionne aussi comme un démon de fond qui envoie des événements à un processus qui est le cœur de l 'application. Pour des raisons de performance, le notificateur ne génère pas d'événements qui ne sont pas nécessaires.

Il existe une sous-routine où l'on peut avoir une machine à sous qui envoie des notifications pour tous les événements possibles. Cette sous-routine est appelée "notifier", et on la trouve dans les fichiers `notifier.py` et `notifier_test.py`.

La commande `python -m notifier` lance le démon. La commande `python -m notifier -h` affiche les options de ligne de commande disponibles.

Notifier Basics

Le notificateur est une sous-routine de démon qui fait deux choses :

  1. Il est conscient des jeux qui sont joués sur la machine à sous.
  2. Il envoie une notification à chaque fois qu'un événement se produit dans ces jeux.

Il est également conçu pour être remplacé par des implémentations personnalisées. Par exemple, une machine à sous de jeu plus complexe pourrait devoir envoyer des notifications plus détaillées que celles qui sont actuellement prises en charge.

Voici un aperçu rapide de la façon dont le notificateur est utilisé :

Pour créer une nouvelle source d'événements, vous devez créer une nouvelle classe qui hérite de `EventSource`. Cette classe doit implémenter les méthodes suivantes :

  • `__init__(self, name)` : Initialise la nouvelle source d'événements.
  • `emit(self, event_name, data=None)` : Émet un nouvel événement.

Une fois que vous avez créé votre nouvelle source d'événements, vous pouvez l'enregistrer auprès du notificateur. Pour ce faire, vous devez créer une nouvelle classe qui hérite de `Notifier`. Cette classe doit implémenter les méthodes suivantes :

  • `__init__(self, event_sources)` : Initialise le notificateur.
  • `notify(self, event_name, data=None)` : Reçoit une notification d'un événement.

Enfin, vous pouvez remplacer le notificateur par votre propre implémentation. Pour ce faire, vous devez créer une nouvelle classe qui hérite de `Notifier`. Cette classe doit implémenter les méthodes suivantes :

  • `__init__(self, event_sources)` : Initialise le notificateur.
  • `notify(self, event_name, data=None)` : Reçoit une notification d'un événement.

Création d'une nouvelle source d'événements

Pour créer une nouvelle source d'événements, vous devez créer une nouvelle classe qui hérite de `EventSource`. Cette classe doit implémenter les méthodes suivantes :

  • `__init__(self, name)` : Initialise la nouvelle source d'événements.
  • `emit(self, event_name, data=None)` : Émet un nouvel événement.

Voici un exemple de création d'une nouvelle source d'événements : 


class MyEventSource(EventSource):
    def __init__(self, name):
        super().__init__(name)

    def emit(self, event_name, data=None):
        print(f"Événement émis : {event_name} avec des données : {data}")

Création d'un nouveau notificateur

Pour créer un nouveau notificateur, vous devez créer une nouvelle classe qui hérite de `Notifier`. Cette classe doit implémenter les méthodes suivantes :

  • `__init__(self, event_sources)` : Initialise le notificateur.
  • `notify(self, event_name, data=None)` : Reçoit une notification d'un événement.

Voici un exemple de création d'un nouveau notificateur : 


class MyNotifier(Notifier):
    def __init__(self, event_sources):
        super().__init__(event_sources)

    def notify(self, event_name, data=None):
        print(f"Notification reçue : {event_name} avec des données : {data}")

Remplacement du notificateur

Pour remplacer le notificateur par votre propre implémentation, vous devez créer une nouvelle classe qui hérite de `Notifier`. Cette classe doit implémenter les méthodes suivantes :

  • `__init__(self, event_sources)` : Initialise le notificateur.
  • `notify(self, event_name, data=None)` : Reçoit une notification d'un événement.

Voici un exemple de remplacement du notificateur : 


class MyCustomNotifier(Notifier):
    def __init__(self, event_sources):
        super().__init__(event_sources)

    def notify(self, event_name, data=None):
        print(f"Notification personnalisée reçue : {event_name} avec des données : {data}")

# Utilisation du notificateur personnalisé
notifier = MyCustomNotifier(event_sources)

Boucles d'événements externes

Le notificateur peut être utilisé avec des boucles d'événements externes. Pour ce faire, vous devez créer une nouvelle classe qui hérite de `Notifier`. Cette classe doit implémenter les méthodes suivantes :

  • `__init__(self, event_sources)` : Initialise le notificateur.
  • `notify(self, event_name, data=None)` : Reçoit une notification d'un événement.

Voici un exemple d'utilisation du notificateur avec une boucle d'événements externe : 


import asyncio

class MyExternalEventLoopNotifier(Notifier):
    def __init__(self, event_sources):
        super().__init__(event_sources)

    def notify(self, event_name, data=None):
        asyncio.get_event_loop().call_soon_threadsafe(
            print, f"Notification reçue dans la boucle d'événements externe : {event_name} avec des données : {data}"
        )

# Utilisation du notificateur avec une boucle d'événements externe
loop = asyncio.get_event_loop()
notifier = MyExternalEventLoopNotifier(event_sources)
