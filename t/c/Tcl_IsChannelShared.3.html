ARGUMENTS

Pointe vers une structure contenant les points d'accès aux fonctions qui peuvent être appelées pour effectuer des opérations d'entrée/sortie sur le canal.

Le nom du canal, par exemple, "file3"; ne peut pas être utilisé par d'autres canaux. Peut être NULL, auquel cas le canal est créé sans nom. Si le canal créé est affecté à l'un des canaux standard (stdin, stdout ou stderr), le nom attribué sera le nom du canal standard.

Valeur arbitraire d'un seul octet associée à ce canal. Cette valeur est transmise aux fonctions dans typePtr lorsqu'elles sont appelées.

DESCRIPTION

Tcl utilise une architecture de canaux à deux niveaux. Elle offre une couche générique pour permettre aux programmes C et Tcl d'effectuer des entrées/sorties en utilisant les mêmes API pour divers fichiers, périphériques, sockets, etc. Les API C génériques sont décrites dans la page de manuel de Tcl_OpenFileChannel.

La couche inférieure fournit des pilotes de canaux spécifiques pour chaque type de périphérique pris en charge sur chaque plateforme. Cette section décrit les API C utilisées pour communiquer entre la couche générique et les pilotes de canaux spécifiques. Elle explique également comment de nouveaux types de canaux peuvent être ajoutés en implémentant de nouveaux pilotes de canaux.

Les pilotes de canaux consistent en plusieurs composants : Premièrement, chaque pilote de canal fournit une structure Tcl_ChannelType qui contient des pointeurs vers les fonctions implémentant les opérations utilisées par la couche générique pour communiquer avec le pilote de canal. La structure Tcl_ChannelType et les fonctions auxquelles elle fait référence sont décrites dans la section TCL_CHANNELTYPE, ci-dessous.

Deuxièmement, les pilotes de canaux fournissent généralement une commande Tcl pour créer des instances de ce type de canal. Par exemple, la commande Tcl open crée des canaux utilisant les pilotes de canaux de fichiers et de commandes, et la commande Tcl socket crée des canaux utilisant les protocoles de sockets TCP pour les communications réseau.

Troisièmement, un pilote de canal fournit éventuellement une fonction C pour créer des instances de ce type de canal. Par exemple, Tcl_OpenFileChannel ouvre un canal utilisant le pilote de canal de fichier, et Tcl_OpenTcpClient ouvre un canal utilisant le protocole réseau TCP. Ces fonctions de création utilisent généralement Tcl_CreateChannel en interne pour ouvrir le canal.

Pour ajouter un nouveau type de canal, vous devez implémenter une API C ou une commande Tcl qui ouvre un canal en appelant Tcl_CreateChannel. Lorsque votre pilote appelle Tcl_CreateChannel, il passe un Tcl_ChannelType qui décrit les procédures d'entrée/sortie de votre pilote. La couche générique appellera ensuite les fonctions référencées dans cette structure pour effectuer des opérations sur le canal.

Tcl_CreateChannel ouvre un nouveau canal et lui associe les valeurs de typePtr et instanceData. Le canal est ouvert dans le mode indiqué par mask. Pour une discussion sur les pilotes de canaux, leurs opérations et la structure Tcl_ChannelType, voir la section TCL_CHANNELTYPE, ci-dessous.

Tcl_CreateChannel interagit avec le code qui gère les canaux standard. Une fois qu'un canal standard a été initialisé par un appel à Tcl_GetStdChannel ou Tcl_SetStdChannel, la fermeture de ce canal entraînera le prochain appel à Tcl_CreateChannel pour créer le nouveau canal comme canal standard également. Voir Tcl_StandardChannels pour une discussion générale sur les canaux standard et le comportement de la bibliothèque Tcl à leur égard.

Tcl_GetChannelInstanceData renvoie les données d'instance associées au canal dans channel. C'est la même valeur que l'argument instanceData dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelType renvoie un pointeur vers la structure Tcl_ChannelType utilisée par le canal dans l'argument channel. C'est la même valeur que l'argument typePtr dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelName renvoie une chaîne contenant le nom associé au canal, ou NULL si l'argument channelName de Tcl_CreateChannel était NULL.

Tcl_GetChannelHandle place le handle du système d'exploitation associé à channel pour la direction donnée dans handlePtr.

TCL_CHANNELTYPE

Un pilote de canal fournit une structure Tcl_ChannelType qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un canal; ces opérations sont appelées au besoin par la couche générique. La structure a été versionnée à partir de Tcl 8.3.2/8.4 pour corriger un problème avec les pilotes de canaux bloquants. Consultez la section OLD CHANNEL TYPES pour plus de détails sur l'ancienne structure.

La structure Tcl_ChannelType contient les champs suivants:

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Il n'est pas nécessaire de fournir des implémentations pour toutes les opérations sur les canaux. Celles qui ne sont pas nécessaires peuvent être définies sur NULL dans la structure: blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc, et close2Proc, ainsi que flushProc, handlerProc, threadActionProc, et truncateProc. D'autres fonctions qui ne peuvent pas être implémentées de manière significative doivent retourner EINVAL lorsqu'elles sont appelées, pour indiquer que les opérations qu'elles représentent ne sont pas disponibles. Il convient également de noter que wideSeekProc peut être NULL si seekProc l'est.

L'utilisateur doit uniquement utiliser cette structure pour l'instanciation de Tcl_ChannelType. Lorsqu'il fait référence à des champs d'une structure Tcl_ChannelType, les fonctions suivantes doivent être utilisées pour obtenir les valeurs: Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, et Tcl_ChannelFlushProc, ou Tcl_ChannelHandlerProc.

La modification des structures a été faite de telle sorte que les types de canaux standard soient compatibles au niveau binaire. Cependant, les types de canaux utilisant des canaux bloquants (c'est-à-dire TLS, Trf) ont des versions qui correspondent à ce changement, car le code plus ancien pour les canaux bloquants présentait des problèmes.

TYPENAME

Le champ typeName contient une chaîne terminée par un caractère nul identifiant le type de périphérique implémenté par ce pilote, par exemple, file ou socket.

Cette valeur peut être obtenue avec Tcl_ChannelName, qui renvoie un pointeur vers la chaîne.

VERSION

Le champ version doit être défini sur la version de la structure dont vous avez besoin. TCL_CHANNEL_VERSION_2 est le minimum recommandé. TCL_CHANNEL_VERSION_3 doit être défini pour spécifier le champ wideSeekProc. TCL_CHANNEL_VERSION_4 doit être défini pour spécifier le champ threadActionProc (inclut wideSeekProc). TCL_CHANNEL_VERSION_5 doit être défini pour spécifier les champs truncateProc (inclut wideSeekProc et threadActionProc). Si aucun de ces éléments n'est défini, il est supposé que ce Tcl_ChannelType a la structure originale. Consultez OLD CHANNEL TYPES pour plus de détails. Bien que Tcl reconnaisse et fonctionne avec chacune de ces structures, les canaux bloquants doivent avoir au moins TCL_CHANNEL_VERSION_2 pour fonctionner correctement.

Cette valeur peut être obtenue avec Tcl_ChannelVersion, qui renvoie l'un de TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 ou TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

Le champ blockModeProc contient l'adresse d'une fonction appelée par la couche générique pour définir le mode bloquant et non bloquant sur le périphérique. BlockModeProc doit correspondre au prototype suivant:

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

instanceData est le même que la valeur fournie à Tcl_CreateChannel lors de la création de ce canal. L'argument mode est soit TCL_MODE_BLOCKING, soit TCL_MODE_NONBLOCKING pour définir le périphérique en mode bloquant ou non bloquant. La fonction doit retourner zéro si l'opération a réussi, ou un code d'erreur POSIX non nul si l'opération a échoué.

Si l'opération réussit, la fonction peut modifier le instanceData fourni pour enregistrer que le canal est passé en mode bloquant ou non bloquant et implémenter le comportement bloquant ou non bloquant. Pour certains types de périphériques, le comportement bloquant et non bloquant peut être implémenté par le système d'exploitation sous le périphérique; pour d'autres types de périphériques, le comportement doit être émulé dans le pilote de canal.

Cette valeur peut être obtenue avec Tcl_ChannelBlockModeProc, qui renvoie un pointeur vers la fonction.

Un pilote de canal qui ne fournit pas de blockModeProc doit être très prudent. Il doit informer la couche générique du mode bloquant acceptable pour lui, et il doit le documenter pour l'utilisateur, de sorte que le mode bloquant du canal ne soit pas changé à une valeur inacceptable. Toute confusion ici pourrait conduire l'interpréteur à une (fausse et difficile à trouver) collision.

CLOSEPROC ET CLOSE2PROC

Le champ closeProc contient l'adresse d'une fonction appelée par la couche générique pour nettoyer les informations relatives au pilote lorsque le canal est fermé. CloseProc doit correspondre au prototype suivant:

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

instanceData est le même que la valeur fournie à Tcl_CreateChannel lors de la création de ce canal. La fonction doit libérer toute mémoire conservée par le pilote de canal pour ce canal, et fermer les périphériques d'entrée et de sortie encapsulés par ce canal. Avant d'appeler cette fonction, toutes les données de sortie en attente ont été vidées du périphérique. Aucune autre opération du pilote ne sera appelée après l'appel de closeProc. Si l'opération de fermeture réussit, la procédure s'exécutera.

devrait retourner zéro ; sinon, elle devrait retourner un code d'erreur POSIX non nul. De plus, si une erreur survient et que interp n'est pas NULL, la procédure doit stocker un message d'erreur dans le résultat de l'interpréteur.

Alternativement, les canaux qui prennent en charge la fermeture indépendante des côtés lecture et écriture peuvent définir closeProc sur TCL_CLOSE2PROC et définir close2Proc sur l'adresse d'une fonction qui correspond au prototype suivant :

typedef int Tcl_DriverClose2Proc(
        ClientData instanceData,
        Tcl_Interp *interp,
        int flags);

Le close2Proc sera appelé avec flags défini sur une combinaison OR de TCL_CLOSE_READ ou TCL_CLOSE_WRITE pour indiquer que le pilote doit fermer le côté lecture et/ou écriture du canal. Le pilote de canal peut être invoqué pour effectuer des opérations supplémentaires sur le canal après l'appel de close2Proc pour fermer un ou les deux côtés du canal. Si flags est 0 (zéro), le pilote doit fermer le canal de la manière décrite ci-dessus pour closeProc. Aucune opération supplémentaire ne sera appelée sur cette instance après l'appel de close2Proc avec tous les indicateurs effacés. Dans tous les cas, la fonction close2Proc doit retourner zéro si l'opération de fermeture a réussi ; sinon, elle doit retourner un code d'erreur POSIX non nul. De plus, si une erreur survient et que interp n'est pas NULL, la procédure doit stocker un message d'erreur dans le résultat de l'interpréteur.

Les valeurs closeProc et close2Proc peuvent être récupérées avec Tcl_ChannelCloseProc ou Tcl_ChannelClose2Proc, qui retournent un pointeur vers la fonction respective.

INPUTPROC

Le champ inputProc contient l'adresse d'une fonction appelée par la couche générique pour lire des données du fichier ou de l'appareil et les stocker dans un tampon interne. InputProc doit correspondre au prototype suivant :

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

InstanceData est la même que la valeur passée à Tcl_CreateChannel lors de la création du canal. L'argument buf pointe vers un tableau d'octets dans lequel stocker les entrées de l'appareil, et l'argument bufSize indique combien d'octets sont disponibles à buf.

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générique. Si une erreur survient, la fonction doit définir la variable à un code d'erreur POSIX qui identifie l'erreur qui s'est produite.

La fonction doit lire les données de l'appareil d'entrée encapsulé par le canal et les stocker dans buf. En cas de succès, la fonction doit retourner un entier non négatif indiquant combien d'octets ont été lus de l'appareil d'entrée et stockés dans buf. En cas d'erreur, la fonction doit retourner -1. Si une erreur survient après que certaines données aient été lues de l'appareil, ces données sont perdues.

Si inputProc peut déterminer que l'appareil d'entrée a des données disponibles mais moins que ce qui est demandé par l'argument bufSize, la fonction ne doit tenter de lire que la quantité de données disponibles et retourner sans bloquer. Si l'appareil d'entrée n'a absolument aucune donnée disponible et que le canal est en mode non bloquant, la fonction doit retourner une erreur EAGAIN. Si l'appareil d'entrée n'a absolument aucune donnée disponible et que le canal est en mode bloquant, la fonction doit bloquer le moins de temps possible jusqu'à ce qu'au moins un octet de données puisse être lu de l'appareil ; ensuite, elle doit retourner autant de données qu'elle peut lire sans bloquer.

Cette valeur peut être récupérée avec Tcl_ChannelInputProc, qui retourne un pointeur vers la fonction.

OUTPUTPROC

Le champ outputProc contient l'adresse d'une fonction appelée par la couche générique pour transférer des données d'un tampon interne vers l'appareil de sortie. OutputProc doit correspondre au prototype suivant :

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData est la même que la valeur passée à Tcl_CreateChannel lors de la création du canal. L'argument buf contient un tableau d'octets à écrire sur l'appareil, et l'argument toWrite indique combien d'octets doivent être écrits à partir de l'argument buf.

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générique. Si une erreur survient, la fonction doit définir cette variable à un code d'erreur POSIX qui identifie l'erreur.

La fonction doit écrire les données de buf sur l'appareil de sortie encapsulé par le canal. En cas de succès, la fonction doit retourner un entier non négatif indiquant combien d'octets ont été écrits sur l'appareil de sortie. La valeur de retour est normalement identique à toWrite, mais peut être inférieure dans certains cas, par exemple si l'opération de sortie est interrompue par un signal. Si une erreur survient, la fonction doit retourner -1. En cas d'erreur, certaines données peuvent avoir été écrites sur l'appareil.

Si le canal est non bloquant et que l'appareil de sortie ne peut absolument absorber aucune donnée, la fonction doit retourner -1 avec une erreur EAGAIN sans écrire aucune donnée.

Cette valeur peut être récupérée avec Tcl_ChannelOutputProc, qui retourne un pointeur vers la fonction.

SEEKPROC ET WIDESEEKPROC

Le champ seekProc contient l'adresse d'une fonction appelée par la couche générique pour déplacer le point d'accès auquel les opérations d'entrée ou de sortie ultérieures seront appliquées. SeekProc doit correspondre au prototype suivant :

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

L'argument instanceData est le même que la valeur donnée à Tcl_CreateChannel lors de la création de ce canal. Offset et seekMode ont la même signification que pour la procédure Tcl_Seek (décrite dans l'entrée de manuel de Tcl_OpenFileChannel).

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générique pour retourner les valeurs errno de la fonction. La fonction doit définir cette variable à un code d'erreur POSIX si une erreur survient. La fonction doit stocker un code d'erreur EINVAL si le type de canal n'implémente pas le positionnement.

La valeur de retour est le nouveau point d'accès ou -1 en cas d'erreur. Si une erreur est survenue, la fonction ne doit pas déplacer le point d'accès.

S'il existe un champ seekProc non NULL, le champ wideSeekProc peut contenir l'adresse d'une fonction alternative à utiliser qui gère les décalages étendus (c'est-à-dire supérieurs à 32 bits), permettant ainsi les positionnements dans des fichiers supérieurs à 2 Go. Le wideSeekProc sera appelé de préférence au seekProc, mais les deux doivent être définis si le wideSeekProc est défini. WideSeekProc doit correspondre au prototype suivant :

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

Les arguments et les valeurs de retour signifient la même chose qu'avec seekProc ci-dessus, à la différence que le type des décalages et le type de retour sont différents.

La valeur seekProc peut être récupérée avec Tcl_ChannelSeekProc, qui retourne un pointeur vers la fonction, et de manière similaire, le wideSeekProc peut être récupéré avec Tcl_ChannelWideSeekProc.

SETOPTIONPROC

Le champ setOptionProc contient l'adresse d'une fonction appelée par la couche générique pour définir une option spécifique au type de canal sur un canal. setOptionProc doit correspondre au prototype suivant :

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

optionName est le nom d'une option à définir, et newValue est la nouvelle valeur de cette option, sous forme de chaîne. InstanceData est la même que la valeur donnée à Tcl_CreateChannel lors de la création de ce canal. La fonction doit effectuer toute action spécifique au type de canal requise pour implémenter la nouvelle valeur de l'option.

Certaines options sont gérées par le code générique et cette fonction n'est jamais appelée pour les définir, par exemple -blockmode. D'autres options sont spécifiques à chaque type de canal et la procédure setOptionProc du pilote de canal sera appelée pour les implémenter. Le champ setOptionProc peut être NULL, ce qui indique que ce type de canal ne prend en charge aucune option spécifique au type.

Si la valeur de l'option est modifiée avec succès à la nouvelle valeur, la fonction retourne TCL_OK. Elle doit appeler Tcl_BadChannelOption qui elle-même retourne TCL_ERROR si optionName n'est pas reconnu. Si newValue spécifie une valeur pour l'option qui n'est pas prise en charge ou si une erreur d'appel système survient, la fonction doit laisser un message d'erreur dans le résultat de interp si interp n'est pas NULL. La fonction doit également appeler Tcl_SetErrno pour stocker un code d'erreur POSIX approprié.

Cette valeur peut être récupérée avec Tcl_ChannelSetOptionProc, qui retourne un pointeur vers la fonction.

GETOPTIONPROC

Le champ getOptionProc contient l'adresse d'une fonction appelée par la couche générique pour obtenir la valeur d'une option spécifique au type de canal sur un canal. getOptionProc doit correspondre au prototype suivant :

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        Tcl_DString *optionValue);

OptionName est le nom d'une option prise en charge par ce type de canal. Si le nom de l'option n'est pas NULL, la fonction stocke sa valeur actuelle, sous forme de chaîne, dans la chaîne dynamique Tcl optionValue. Si optionName est NULL, la fonction stocke dans optionValue une liste alternée de toutes les options prises en charge et de leurs valeurs actuelles. En cas de succès, la fonction retourne TCL_OK. WATCHPROC

Le champ watchProc contient l'adresse d'une fonction appelée par la couche générale de canal pour initialiser le mécanisme de notification des événements d'intérêt sur ce canal. WatchProc doit correspondre au prototype suivant :

typedef void Tcl_DriverWatchProc(
        ClientData instanceData,
        int mask);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument mask est une combinaison OR de TCL_READABLE, TCL_WRITABLE et TCL_EXCEPTION ; il indique les événements pour lesquels l'appelant souhaite être notifié sur ce canal.

La fonction doit initialiser des mécanismes spécifiques au type de périphérique pour être notifiée lorsqu'un événement d'intérêt est présent sur le canal. Lorsqu'un ou plusieurs des événements désignés se produisent sur le canal, le pilote de canal est responsable d'appeler Tcl_NotifyChannel pour informer le module général de canal. Le pilote doit veiller à ne pas bloquer d'autres pilotes de canal ou sources de callbacks en appelant Tcl_NotifyChannel trop fréquemment. L'équité peut être assurée en utilisant la file d'attente d'événements de Tcl pour permettre à l'événement de canal d'être planifié séquentiellement avec d'autres événements. Voir la description de Tcl_QueueEvent pour plus de détails sur la façon de planifier un événement.

Cette valeur peut être récupérée avec Tcl_ChannelWatchProc, qui renvoie un pointeur vers la fonction.

GETHANDLEPROC

Le champ getHandleProc contient l'adresse d'une fonction appelée par la couche générale de canal pour récupérer un handle spécifique au périphérique à partir du canal. GetHandleProc doit correspondre au prototype suivant :

typedef int Tcl_DriverGetHandleProc(
        ClientData instanceData,
        int direction,
        ClientData *handlePtr);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument direction est TCL_READABLE pour récupérer le handle utilisé pour l'entrée, ou TCL_WRITABLE pour récupérer le handle utilisé pour la sortie.

Si l'implémentation du canal a des handles spécifiques, la fonction doit récupérer le handle approprié associé au canal en fonction de l'argument direction. Le handle doit être stocké à l'emplacement référencé par handlePtr, et TCL_OK doit être retourné. Si le canal n'est pas ouvert pour la direction spécifiée, ou si l'implémentation du canal n'utilise pas de handles spécifiques, la fonction doit retourner TCL_ERROR.

Cette valeur peut être récupérée avec Tcl_ChannelGetHandleProc, qui renvoie un pointeur vers la fonction.

FLUSHPROC

Le champ flushProc est actuellement réservé pour une utilisation future. Il doit être défini à NULL. FlushProc doit correspondre au prototype suivant :

typedef int Tcl_DriverFlushProc(
        ClientData instanceData);

Cette valeur peut être récupérée avec Tcl_ChannelFlushProc, qui renvoie un pointeur vers la fonction.

HANDLERPROC

Le champ handlerProc contient l'adresse d'une fonction appelée par la couche générale de canal pour notifier le canal qu'un événement s'est produit. Il doit être défini pour les pilotes de canal empilés qui souhaitent être notifiés des événements qui se produisent sur le canal sous-jacent (canal empilé). HandlerProc doit correspondre au prototype suivant :

typedef int Tcl_DriverHandlerProc(
        ClientData instanceData,
        int interestMask);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. interestMask est une combinaison OR de TCL_READABLE ou TCL_WRITABLE ; il indique quel type d'événement s'est produit sur ce canal.

Cette valeur peut être récupérée avec Tcl_ChannelHandlerProc, qui renvoie un pointeur vers la fonction.

THREADACTIONPROC

Le champ threadActionProc contient l'adresse de la fonction appelée par la couche générale de canal lorsqu'un canal est créé, fermé ou déplacé vers un autre thread, c'est-à-dire lorsque l'état spécifique au thread du pilote pourrait avoir besoin d'être initialisé ou mis à jour. Il peut être NULL. L'action TCL_CHANNEL_THREAD_REMOVE est utilisée pour notifier au pilote qu'il doit mettre à jour ou supprimer toute donnée spécifique au thread qu'il pourrait détenir pour le canal.

L'action TCL_CHANNEL_THREAD_INSERT est utilisée pour notifier au pilote qu'il doit mettre à jour ou initialiser toute donnée spécifique au thread qu'il pourrait détenir en utilisant le thread actuel comme associé. Voir Tcl_CutChannel et Tcl_SpliceChannel pour plus de détails.

typedef void Tcl_DriverThreadActionProc(
        ClientData instanceData,
        int action);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal.

Ces valeurs peuvent être récupérées avec Tcl_ChannelThreadActionProc, qui renvoie un pointeur vers la fonction.

TRUNCATEPROC

Le champ truncateProc contient l'adresse de la fonction appelée par la couche générale de canal lorsqu'un canal est tronqué à une longueur spécifique. Il peut être NULL.

typedef int Tcl_DriverTruncateProc(
        ClientData instanceData,
        Tcl_WideInt length);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal, et length est la nouvelle longueur du fichier sous-jacent, qui ne doit pas être négative. Le résultat doit être 0 en cas de succès ou un code d'erreur (approprié pour une utilisation avec Tcl_SetErrno) en cas d'échec.

Ces valeurs peuvent être récupérées avec Tcl_ChannelTruncateProc, qui renvoie un pointeur vers la fonction.

TCL_BADCHANNELOPTION

Cette procédure génère un message d'erreur "mauvaise option" dans un interpréteur (optionnel). Elle est utilisée par les pilotes de canal lorsqu'une option de réglage/obtention invalide est demandée. Son but est de concaténer la liste des options génériques à celle des options spécifiques et de factoriser le message d'erreur des options génériques.

Retourne toujours TCL_ERROR.

Un message d'erreur est généré dans la valeur de résultat de interp pour indiquer qu'une commande a été appelée avec une option invalide. Le message a la forme :

    mauvaise option "blah" : devrait être l'une des
    <...options génériques...>+<...options spécifiques...>
par exemple : 
    mauvaise option "-blah" : devrait être l'une de -blocking,
    -buffering, -buffersize, -eofchar, -translation,
    -peername, ou -sockname
lorsqu'elle est appelée avec optionList égal à "peername sockname".

"blah" est l'argument optionName et " <options spécifiques>" est une liste de mots spécifiques séparés par des espaces. La fonction prend soin d'insérer des traits d'union avant chaque option, des virgules après, et un "ou" avant la dernière option.

ANCIENS TYPES DE CANAUX

La structure originale (8.3.1 et versions antérieures) de Tcl_ChannelType contient les champs suivants :

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
} Tcl_ChannelType;

Bien qu'il soit possible de créer des canaux avec la structure ci-dessus, le code interne du canal déterminera la version. Il est essentiel d'utiliser la nouvelle structure Tcl_ChannelType si un pilote de canal empilé est créé, en raison de problèmes dans l'implémentation précédente des canaux empilés (de 8.2.0 à 8.3.1).

Avant 8.4.0 (c'est-à-dire pendant les dernières versions de 8.3 et le début du cycle de développement de 8.4), la structure Tcl_ChannelType contenait les champs suivants :

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_ChannelTypeVersion version;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Lorsque la structure ci-dessus est enregistrée comme type de canal, le champ version doit toujours être TCL_CHANNEL_VERSION_2.
