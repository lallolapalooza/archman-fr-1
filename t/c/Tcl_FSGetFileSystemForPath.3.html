DESCRIPTION

Hay varias razones por las que se llaman a las funciones de la API Tcl_FS (por ejemplo, Tcl_FSAccess y Tcl_FSStat) en lugar de llamar a funciones del nivel del sistema como access y stat. Primero, funcionan de forma multiplataforma, por lo que una extensión que llame a estas funciones debería funcionar sin modificaciones en Unix y Windows. Segundo, la implementación de algunas de estas funciones en Windows corrige algunos errores en las llamadas al nivel del sistema. Tercero, estas llamadas manejan cualquier conversión de rutas de tipo "Utf a plataforma nativa" que pueda ser requerida (y pueden cachear los resultados de estas conversiones para mayor eficiencia en llamadas posteriores). Cuarto, y probablemente más importante, todas estas funciones son "conscientes del sistema de archivos virtual" (virtual filesystem aware). Cualquier sistema de archivos virtual (VFS, por su abreviatura) registrado (a través de Tcl_FSRegister) puede redirigir el acceso a archivos a medios alternativos o métodos de acceso. Esto significa que todas estas funciones (y por tanto los comandos Tcl correspondientes como file, glob, pwd, cd, open, etc.) pueden operar sobre "archivos" que no son archivos nativos en el sistema de archivos nativo. Esto también significa que cualquier extensión Tcl que acceda al sistema de archivos (FS, por su abreviatura) a través de esta API será automáticamente "consciente del sistema de archivos virtual". Claro está, si una extensión accede directamente al sistema de archivos nativo (a través de APIs específicas del sistema, por ejemplo), Tcl no puede interceptar tales llamadas.

Si se han registrado adecuadamente los sistemas de archivos VFS, los "archivos" pueden ser remotos (por ejemplo, situados en un servidor FTP remoto) o archivados (por ejemplo, ubicados dentro de un archivo ZIP). Estos sistemas de archivos registrados ofrecen una tabla de búsqueda de funciones para implementar parte o toda la funcionalidad mencionada aquí. Por último, las llamadas a Tcl_FSStat y Tcl_FSLstat abstraen de lo que el buffer struct stat realmente es, permitiendo que el mismo código se use tanto en sistemas con como sin soporte para archivos mayores de 2 GB.

La API Tcl_FS está orientada a Tcl_Obj y puede cachear representaciones internas y otros strings relacionados con rutas (por ejemplo, el directorio actual). Un efecto secundario de esto es que no debe pasar valores con un contador de referencias cero a ninguna de estas funciones. Si se hiciera así, podría causar errores de memoria (en algunos casos, el código del sistema de archivos podría descartar una referencia al valor pasado y, por lo tanto, uno no debe asumir que después de cualquier llamada a estas funciones, el valor todavía tenga un contador de referencias cero - podría haber sido incrementado). O, en el caso de un error directo de segmentación (o error de acceso a memoria), debido a que el valor se libera durante el manejo complejo de la normalización y absolutización de rutas para el sistema de archivos. La lección práctica a aprender es que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

es incorrecto y puede causar errores de memoria. El path debe incrementar su contador de referencias antes de pasarlo, o decrementarlo. Por eso, los valores con un contador de referencias cero se consideran no válidos como rutas del sistema de archivos y llamar a cualquier función de API de Tcl_FS con tales valores no generará ninguna acción.

FUNCIONES DE LA API Tcl_FS

Tcl_FSCopyFile intenta copiar el archivo dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas indicadas están en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función de copia de archivo del sistema de archivos. De lo contrario, devuelve -1 y establece el valor global errno a EXDEV (código POSIX que indica un cruce de dispositivo).

Tcl_FSCopyDirectory intenta copiar el directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas indicadas están en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función de copia de directorio del sistema de archivos. De lo contrario, devuelve -1 y establece el valor global errno a EXDEV (código POSIX que indica un cruce de dispositivo).

Tcl_FSCreateDirectory intenta crear el directorio dado por pathPtr llamando a la función de creación de directorio del sistema de archivos que lo posee.

Tcl_FSDeleteFile intenta eliminar el archivo dado por pathPtr llamando a la función de eliminación de archivo del sistema de archivos que lo posee.

Tcl_FSRemoveDirectory intenta eliminar el directorio dado por pathPtr llamando a la función de eliminación de directorio del sistema de archivos que lo posee.

Tcl_FSRenameFile intenta renombrar el archivo o directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas indicadas están en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función de renombrar archivo del sistema de archivos. De lo contrario, devuelve -1 y establece el valor global errno a EXDEV (código POSIX que indica un cruce de dispositivo).

Tcl_FSListVolumes llama a cada sistema de archivos que tiene una función de listado de volúmenes no NULL y les pide a estos sistemas de archivos que devuelvan su lista de volúmenes raíz. Acumula los valores devueltos en una lista que se devuelve al llamador (con un contador de referencias 0).

Tcl_FSEvalFileEx lee el contenido del archivo dado por pathPtr usando el esquema de codificación identificado por encodingName y evalúa su contenido como un script Tcl. Devuelve la misma información que Tcl_EvalObjEx. Si encodingName es NULL, se usa el esquema de codificación del sistema para leer el contenido del archivo. Si el archivo no se puede leer, se devuelve un error Tcl que describe por qué no se pudo leer el archivo. El carácter de fin de archivo para archivos es \x1A (^Z) para todos los sistemas. Si quieres usar \x1A en código para comparaciones de strings, puedes usarlo, que se sustituirá correctamente por el intérprete Tcl en ^Z. Tcl_FSEvalFile es una versión más simple de Tcl_FSEvalFileEx que siempre usa el esquema de codificación del sistema al leer el archivo.

Tcl_FSLoadFile carga dinámicamente un archivo binario en memoria y devuelve las direcciones de dos procedimientos dentro de ese archivo, si están definidos. La función apropiada para el sistema de archivos al que pertenece pathPtr será llamada. Si ese sistema de archivos no implementa esta función (la mayoría de los sistemas de archivos virtuales no lo harán debido a las limitaciones del sistema al cargar código binario), Tcl intentará copiar el archivo a un directorio temporal y cargar ese archivo temporal. Tcl_FSUnloadFile revierte esta operación, pidiendo al proceso que elimine la biblioteca indicada por el loadHandle del proceso. Ten en cuenta que, a diferencia del comando unload, esto no da a la biblioteca ninguna oportunidad de limpieza.

Ambas funciones anteriores devuelven un código de finalización Tcl estándar. Si ocurre un error, se deja un mensaje de error en el resultado del interp.

El token proporcionado a través de la variable indicada por loadHandlePtr puede ser utilizado con Tcl_FindSymbol.

Tcl_FSMatchInDirectory es utilizada por el código de globbing para buscar en un directorio todos los archivos que coinciden con un patrón dado. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El valor de retorno es un resultado Tcl estándar que indica si ocurrió un error en el globbing. Los mensajes de error se colocan en interp (a menos que interp sea NULL, lo cual está permitido), pero los buenos resultados se colocan en resultPtr dado.

Ten en cuenta que el código de glob implementa patrones recursivos internamente, por lo que esta función solo recibirá patrones simples, que pueden ser emparejados usando la lógica de string match. Para manejar la recursión, Tcl llamará a esta función con frecuencia pidiendo solo directorios para ser devueltos. Un caso especial de ser llamado con un patrón NULL indica que la ruta solo necesita ser verificada por el tipo correcto.

Tcl_FSLink reemplaza la versión de biblioteca de readlink, y la extiende para soportar la creación de enlaces. Se llamará a la función apropiada para el sistema de archivos al que pertenece linkNamePtr.

Si toPtr es NULL, se realiza una acción de lectura de enlace. El resultado es un Tcl_Obj que especifica el contenido del enlace simbólico dado por linkNamePtr, o NULL si el enlace no pudo ser leído. El resultado es propiedad del llamador, que debería llamar a Tcl_DecrRefCount cuando el resultado ya no sea necesario. Si toPtr no es NULL, Tcl debería crear un enlace de uno de los tipos pasados en el flag linkAction. Este flag es una combinación OR de TCL_CREATE_SYMBOLIC_LINK y TCL_CREATE_HARD_LINK. Donde existe una elección (es decir, se pasan más de un flag), la convención de Tcl es preferir los enlaces simbólicos. Cuando se crea un enlace con éxito, el valor de retorno debería ser toPtr (que por lo tanto ya es propiedad del llamador). Si no tiene éxito, se devuelve NULL.

Tcl_FSLstat llena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesitas ningún derecho de acceso al archivo para obtener esta información, pero necesitas derechos de búsqueda para todos los directorios nombrados en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, inodo (siempre 0 en Windows), modo de privilegios, nlink (siempre 1 en Windows), id de usuario (siempre 0 en Windows), id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño,

temps d'accès, temps de modification et temps de changement de métadonnées. Voir PORTABLE STAT RESULT API pour une description de la façon d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSLstat renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé, et aucune information de stat n'est fournie.

Tcl_FSUtime remplace la version de bibliothèque de utime.

Ceci renvoie 0 en cas de succès et -1 en cas d'erreur (conformément à la documentation de utime). En cas de succès, la fonction mettra à jour les valeurs "atime" et "mtime" du fichier donné.

Tcl_FSFileAttrsGet implémente l'accès en lecture pour la sous-commande file attributes, qui peut être interceptée. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

Si le résultat est TCL_OK, alors une valeur a été placée dans objPtrRef, qui ne sera valide que temporairement (sauf si Tcl_IncrRefCount est appelé).

Tcl_FSFileAttrsSet implémente l'accès en écriture pour la sous-commande file attributes, qui peut être interceptée. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

Tcl_FSFileAttrStrings implémente une partie de la sous-commande file attributes, qui peut être interceptée. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La procédure appelée peut soit renvoyer un tableau de chaînes, soit renvoyer NULL et placer une liste Tcl dans objPtrRef donné. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer de conserver un compteur de références pour la valeur.

Tcl_FSAccess vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est pathname. Si pathname est un lien symbolique sous Unix, alors les permissions du fichier auquel ce lien symbolique fait référence sont testées.

En cas de succès (toutes les permissions demandées accordées), zéro est renvoyé. En cas d'erreur (au moins un bit dans le mode demandait une permission qui est refusée, ou une autre erreur s'est produite), -1 est renvoyé.

Tcl_FSStat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de parcours sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf comprend des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le temps du dernier accès, le temps de la dernière modification et le temps du dernier changement de métadonnées. Voir PORTABLE STAT RESULT API pour une description de la façon d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSStat renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé, et aucune information de stat n'est fournie.

Tcl_FSOpenFileChannel ouvre un fichier spécifié par pathPtr et renvoie un descripteur de canal qui peut être utilisé pour effectuer des opérations d'entrée et de sortie sur le fichier. Cette API est basée sur la procédure fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier. En cas d'erreur lors de l'ouverture du canal, Tcl_FSOpenFileChannel renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannel laisse un message d'erreur dans le résultat de interp après toute erreur.

Le canal nouvellement créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez Tcl_RegisterChannel. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, l'acte de création du nouveau canal l'assigne également comme remplacement du canal standard.

Tcl_FSGetCwd remplace la version de bibliothèque de getcwd.

Il renvoie le répertoire de travail courant de la bibliothèque Tcl. Celui-ci peut être différent du répertoire de travail de la plateforme native, ce qui se produit lorsque le répertoire de travail courant n'est pas dans le système de fichiers natif.

Le résultat est un pointeur vers un Tcl_Obj spécifiant le répertoire courant, ou NULL si le répertoire courant n'a pas pu être déterminé. Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de interp.

Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compteur de références doit être décrémenté. Ceci est nécessaire pour des raisons de sécurité des threads, afin de permettre à plusieurs threads d'accéder à cette fonction et aux fonctions connexes, tout en garantissant que les résultats sont toujours valides.

Tcl_FSChdir remplace la version de bibliothèque de chdir. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl se rabattra sur une combinaison de stat et access pour vérifier si le répertoire existe et possède les permissions appropriées.

Pour les résultats, voir la documentation de chdir. En cas de succès, nous conservons un enregistrement du chemin réussi dans cwdPathPtr pour les appels ultérieurs à Tcl_FSGetCwd.

Tcl_FSPathSeparator renvoie le caractère séparateur à utiliser pour l'élément le plus spécifique du chemin spécifié par pathPtr (c'est-à-dire la dernière partie du chemin).

Le séparateur est renvoyé sous forme de Tcl_Obj contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est renvoyé.

Tcl_FSJoinPath prend le Tcl_Obj donné, qui doit être une liste valide (qui est autorisée à avoir un compteur de références de zéro), et renvoie la valeur du chemin donnée en considérant les elements premiers éléments comme des segments de chemin valides (chaque segment de chemin peut être un chemin complet, un chemin partiel ou simplement un seul répertoire ou nom de fichier possible). Si un segment de chemin est en fait un chemin absolu, alors tous les segments de chemin précédents sont ignorés. Si elements est inférieur à 0, nous utilisons la liste entière.

Il est possible que la valeur renvoyée soit en fait un élément de la liste donnée, donc l'appelant doit veiller à incrémenter le compteur de références du résultat avant de libérer la liste.

La valeur renvoyée, généralement avec un compteur de références de zéro (mais elle peut être partagée dans certaines conditions), contient le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. En particulier, la valeur renvoyée peut être un élément de la liste donnée, donc la libération de la liste peut libérer la valeur prématurément si aucun compteur de références n'a été pris. Si le nombre d'éléments est zéro, alors la valeur renvoyée sera un Tcl_Obj de chaîne vide.

Tcl_FSSplitPath prend le Tcl_Obj donné, qui devrait être un chemin valide, et renvoie une valeur de liste Tcl contenant chaque segment de ce chemin comme élément. Il renvoie une valeur de liste avec un compteur de références de zéro. Si le lenPtr passé n'est pas NULL, la variable vers laquelle il pointe sera mise à jour pour contenir le nombre d'éléments dans la liste renvoyée.

Tcl_FSEqualPaths teste si les deux chemins donnés représentent le même objet système de fichiers. Il renvoie 1 si les chemins sont égaux et 0 s'ils sont différents. Si l'un des chemins est NULL, 0 est toujours renvoyé.

Tcl_FSGetNormalizedPath tente d'extraire du Tcl_Obj donné une représentation de chemin normalisée unique, dont la valeur chaîne peut être utilisée comme identifiant unique du fichier.

Il renvoie la valeur du chemin normalisé, détenue par Tcl, ou NULL si le chemin était invalide ou n'a pas pu être converti avec succès. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère sur ces représentations en interne), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques puisse ne pas être la version la plus conviviale d'un chemin. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle de pathPtr passé (sauf si c'est un chemin relatif, auquel cas la valeur du chemin normalisé peut être libérée à tout moment lorsque le cwd change) - l'appelant peut bien sûr incrémenter le compteur de références s'il souhaite conserver une copie plus longtemps.

Tcl_FSJoinToPath prend la valeur donnée, qui devrait généralement être un chemin valide ou NULL, et y joint le tableau de segments de chemin fournis.

Renvoie une valeur, généralement avec un compteur de références de zéro (mais elle peut être partagée dans certaines conditions), contenant le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. Si l'une des valeurs passées à cette fonction (pathPtr ou éléments de path) a un compteur de références de zéro, elle sera libérée lorsque cette fonction renverra.

Tcl_FSConvertToPathType essaie de convertir le Tcl_Obj donné en un type de chemin Tcl valide, en tenant compte du fait que le cwd a pu changer même si cette valeur est déjà censée être du bon type. Le nom de fichier peut commencer par "~" (pour indiquer le répertoire personnel de l'utilisateur courant) ou "~<utilisateur>" (pour indiquer le répertoire personnel de n'importe quel utilisateur).

Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers courants), alors TCL_OK est renvoyé. Sinon, TCL_ERROR est renvoyé, et un message d'erreur peut être laissé dans l'interpréteur.

Tcl_FSGetInternalRep extrait la représentation interne d'une valeur de chemin donnée, dans le système de fichiers donné. Si la valeur du chemin appartient à un système de fichiers différent, nous renvoyons NULL. Si la représentation interne est actuellement NULL, nous tentons de la générer en appelant Tcl_FSCreateInternalRepProc du système de fichiers.

Renvoie NULL ou une représentation de chemin interne valide. Cette représentation interne est mise en cache, de sorte que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires.

Tcl_FSGetTranslatedPath tente d'extraire le chemin traduit du Tcl_Obj donné.

Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), elle est renvoyée. Sinon, NULL sera renvoyé, et un message d'erreur peut être laissé dans l'interpréteur. Un chemin "traduit" est un chemin qui ne contient aucune séquence "~" ou "~utilisateur" (celles-ci ont été développées dans leur représentation actuelle dans le système de fichiers). La valeur renvoyée est détenue par l'appelant, qui doit la stocker ou appeler Tcl_DecrRefCount pour s'assurer que la mémoire est libérée. Cette fonction a peu d'utilité pratique, et Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des besoins.

Tcl_FSGetNormalizedPath realiza algo así como el reverso de las conversiones usuales de obj→path→nativerep. Si algún código obtiene una ruta en forma nativa (de, por ejemplo, readlink o un diálogo nativo), y esa ruta debe usarse en el nivel Tcl, entonces llamar a esta función es una forma eficiente de crear el valor correspondiente de tipo ruta.

El valor resultante es un valor puro "ruta", que recibirá una representación en formato UTF-8 solo si es requerida por algún código Tcl.

Tcl_FSGetNativePath se usa para el sistema de archivos nativo de Win/Unix, permitiendo fácilmente recuperar la representación nativa (char* o TCHAR*) de una ruta. Esta función es un wrapper conveniente al Tcl_FSGetInternalRep. Podría ser deseable en el futuro tener representaciones no basadas en strings (por ejemplo, en macOS, una representación usando un estructura FSRef de fileSpec sería probablemente más eficiente). En Windows, una representación completa en Unicode permite rutas de longitud ilimitada. Actualmente, la representación es simplemente una cadena de caracteres que puede contener la ruta relativa o una ruta absoluta normalizada en la codificación nativa (condiciones complejas determinan cuál de estas se proporcionará, así que ninguno puede recaudarse sin conocer la ruta de forma absoluta). Si necesitas una ruta nativa que debe ser absoluta, deberías pedir la versión nativa de una ruta normalizada. Si por algún motivo se necesita una versión no absoluta, no normalizada de la ruta, esa debe construirse por separado (por ejemplo, usando Tcl_FSGetTranslatedPath).

La representación nativa se caché para que llamadas repetidas a esta función no requieran conversión adicional. El valor devuelto es todos los que pertenecen a Tcl y tiene un vida útil equivalente a la del pathPtr pasado (a menos que ese sea una ruta relativa, en cuyo caso la representación nativa puede ser liberada cualquier vez que cambie el cwd).

Tcl_FSFileSystemInfo devuelve un valor de lista con dos elementos. El primer elemento es el nombre del sistema de archivos (por ejemplo, "native", "vfs", "zip", "prowrap", etc.), y el segundo es el tipo de la ruta dada dentro de ese sistema de archivos (depende del sistema de archivos). El segundo elemento puede ser vacío si el sistema de archivos no proporciona una categorización adicional de archivos.

Un valor de lista válido se devuelve, a menos que la ruta no sea reconocida, en cualquiera de los casos se devuelve NULL.

Tcl_FSGetFileSystemForPath devuelve un puntero al Tcl_Filesystem que acepta esta ruta como válida.

Si ningún sistema de archivos acepta esta ruta, se devuelve NULL.

Tcl_FSGetPathType determina si la ruta dada es relativa al directorio actual, relativa al volumen actual o absoluta.

Devuelve uno de TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE o TCL_PATH_VOLUME_RELATIVE.

THE VIRTUAL FILESYSTEM API

Un sistema de archivos proporciona un Tcl_Filesystem que contiene punteros a funciones que implementan las diversas operaciones en un sistema de archivos; estas operaciones se invocan según sea necesario por el capaz generico, lo cual generalmente ocurre a través de las funciones mencionadas anteriormente.

Los estructuras Tcl_Filesystem se manipulan mediante los siguientes métodos.

Tcl_FSRegister toma un puntero a una estructura de sistema de archivos y un dato opcional asociado con ese sistema de archivos. Al llamar a esta función, Tcl atará el sistema de archivos a la lista de sistemas de archivos conocidos, lo que lo hace funcional inmediatamente. Tcl no verifica si el mismo sistema de archivos se registra múltiples veces (y en general no es buen idea). TCL_OK será devuelto.

Tcl_FSUnregister elimina el sistema de archivos dado de la lista de sistemas de archivos conocidos, si es conocido, y devuelve TCL_OK. Si el sistema de archivos no está actualmente registrado, se devuelve TCL_ERROR.

Tcl_FSData devolverá el clienteData asociado con el sistema de archivos dado, si éste está registrado. De lo contrario, devolverá NULL.

Tcl_FSMountsChanged se utiliza para informar a la núcleo de Tcl que la lista de puntos de montaje para el sistema de archivos dado (ya registrado) ha cambiado, y que así las representaciones de archivos cachadas pueden estar ya no correctas.

Las muchas funciones en esta estructura se dividen en tres categorías: funciones de infraestructura (bulk de las cuales casi todas deben ser implementadas), funciones operativas (que deben ser implementadas si se proporciona un sistema de archivos completo), y funciones eficientes (que solo deben ser implementadas si pueden hacerse eficientemente, o si tienen efectos secundarios que sean necesarios por el sistema de archivos; Tcl tiene emulaciones menos eficientes que puede usar como alternativa). Es importante notar que, en la versión actual de Tcl, la mayoría de estos fallbacks solo se utilizan para manejar comandos iniciados en Tcl, no en C. Esto significa que, si se emite una orden de renombrar en Tcl y los sistemas de archivos relevantes no implementan su Tcl_FSRenameFileProc, el núcleo de Tcl se basa en combinaciones de otras funciones de sistema de archivos (usará Tcl_FSCopyFileProc seguido por Tcl_FSDeleteFileProc, y si Tcl_FSCopyFileProc no está implementado, hay un fallback adicional). Sin embargo, si se emite una orden de Tcl_FSRenameFileProc en el nivel C, no ocurre tal fallback. Esto es true a menos que las últimas cuatro entradas en la tabla de sistemas de archivos ( lstat, load, getcwd y chdir ) tengan fallbacks en el nivel C.

Cualquier función que tome nombres de ruta en formato Tcl_Obj debe usarlos en formato UTF-8. La infraestructura del API de conversión es diseñada para soportar la conversión eficiente y cachada de estos caminos UTF-8 en otras representaciones nativas.

PROCÉDURE CHEMIN DANS SYSTÈME DE FICHIERS

Le champ pathInFilesystemProc contient l'adresse d'une fonction appelée pour déterminer si une valeur de chemin donnée appartient ou non à ce système de fichiers. Tcl mettra simultanément en cache le fait que ce chemin appartient à ce système de fichiers. De tels caches sont invalidés lorsque des structures de systèmes de fichiers sont ajoutées ou supprimées de la liste interne des systèmes de fichiers connus de Tcl.

PROCÉDURE NORMALISER CHEMIN

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations textuelles pour la même valeur de chemin. Dans Tcl, chaque « chemin » doit avoir une seule représentation textuelle « normalisée » unique. Selon le système de fichiers, il peut y avoir plus d'une représentation textuelle non normalisée qui fait référence à ce chemin (par exemple, un chemin relatif, un chemin avec une casse différente si le système de fichiers ne tient pas compte de la casse, un chemin contenant une référence à un répertoire personnel tel que « ~ », un chemin contenant des liens symboliques, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être converti en la valeur à laquelle il pointe (mais sa casse ou d'autres aspects doivent être rendus uniques). Tous les autres composants du chemin doivent être convertis à partir de liens symboliques. Cette unique exception est requise pour être conforme aux sémantiques de Tcl avec file delete, file rename, file copy opérant sur des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint soit au début du chemin (c'est-à-dire zéro), à la fin du chemin, soit à un séparateur de fichier intermédiaire dans le chemin. Elle ne pointera jamais vers une autre position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS DU SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui est censé être utilisé avec l'ensemble complet des commandes Tcl standard doit implémenter toutes ces fonctions. Si certaines d'entre elles ne sont pas implémentées, certaines commandes Tcl peuvent échouer lors de l'opération sur des chemins appartenant à ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques n'a pas besoin d'implémenter la fonction readlink, etc. Le noyau Tcl s'attend à ce que les systèmes de fichiers se comportent de cette manière).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La Tcl_FSStatProc remplit la structure stat statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure stat inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'identifiant utilisateur (toujours 0 sous Windows), l'identifiant de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification, et l'heure du dernier changement de métadonnées.

Si le fichier représenté par pathPtr existe, la Tcl_FSStatProc retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné, et aucune information stat n'est donnée.

PROCÉDURE ACCÈS

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent crucialement (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est dans pathPtr. Si le nom de chemin fait référence à un lien symbolique, alors les permissions du fichier auquel ce lien symbolique fait référence doivent être testées.

En cas de succès (toutes les permissions demandées accordées), zéro est retourné. En cas d'erreur (au moins un bit dans mode demandait une permission refusée, ou une autre erreur s'est produite), -1 est retourné.

NNELPROC'>OPENFILECHANNELPROC

Fonction pour traiter un appel à Tcl_FSOpenFileChannel. Doit être implémentée pour tout système de fichiers raisonnable, car toutes les opérations qui nécessitent l'ouverture ou l'accès au contenu d'un fichier l'utiliseront (par exemple, open, encoding, et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et retourne un descripteur de canal qui peut être utilisé pour effectuer des entrées et des sorties sur le fichier. Cette API est basée sur la procédure fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles de la commande Tcl open lors de l'ouverture d'un fichier, où l'argument mode est une combinaison des indicateurs POSIX O_RDONLY, O_WRONLY, etc. Si une erreur survient lors de l'ouverture du canal, Tcl_FSOpenFileChannelProc retourne NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le nouveau canal créé ne doit pas être enregistré dans l'interpréteur fourni par un Tcl_FSOpenFileChannelProc ; cette tâche incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, la création du nouveau canal l'attribue également comme remplacement du canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, les fonctionnalités glob et de copie récursive manqueront dans le système de fichiers (et cela peut avoir un impact sur des commandes comme encoding names qui utilisent des fonctionnalités glob en interne).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit retourner tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au motif donné et conformément à la spécification de types. Il y a deux façons dont cette fonction peut être appelée. Si pattern est NULL, alors pathPtr est une spécification de chemin complet d'un seul fichier ou répertoire qui doit être vérifié pour son existence et son type correct. Sinon, pathPtr est un répertoire, dont le contenu doit être recherché par la fonction pour trouver des fichiers ou des répertoires du type correct. Dans les deux cas, on peut supposer que pathPtr n'est ni NULL ni vide. Il n'est pas actuellement documenté si pathPtr aura ou non un séparateur de fichier à la fin, donc le code doit être flexible aux deux possibilités.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le processus de correspondance. Les messages d'erreur sont placés dans interp, à moins que interp ne soit NULL auquel cas aucun message d'erreur ne doit être généré ; en cas de résultat TCL_OK, les résultats doivent être ajoutés à la valeur de resultPtr donnée (qui peut être supposée être une liste Tcl valide et non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (cela signifie généralement qu'il s'agira de spécifications de chemin absolu). Notez que si aucune correspondance n'est trouvée, cela conduit simplement à un résultat vide ; les erreurs ne sont signalées que pour des problèmes réels de fichiers ou de système de fichiers qui peuvent survenir pendant le processus de correspondance.

La structure Tcl_GlobTypeData passée dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Type mac acceptable */
    Tcl_Obj *macType;
    /* Créateur mac acceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de traiter correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT sont vrais (et en particulier lorsque les autres indicateurs sont faux). Dans le premier de ces cas, la fonction doit lister les répertoires contenus. Tcl utilise cela pour implémenter le globbing récursif, il est donc essentiel que les systèmes de fichiers implémentent correctement la correspondance des répertoires. Dans le second de ces cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage qui se trouvent dans le pathPtr donné (et dans ce cas, pathPtr n'a pas besoin de se trouver dans le même système de fichiers - différent de tous les autres cas où cette fonction est appelée). Le support de ceci est critique si Tcl doit avoir des transitions transparentes entre les systèmes de fichiers.

UTIMEPROC

Fonction pour traiter un appel à Tcl_FSUtime. Nécessaire pour permettre la définition (pas la lecture) des horodatages avec file mtime, file atime et l'implémentation open-r/open-w/fcopy de file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les horodatages d'accès et de modification du fichier spécifié par pathPtr doivent être modifiés aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec le système utime.

LINKPROC

Fonction pour traiter un appel à Tcl_FSLink. Ne doit être implémentée que si le système de fichiers prend en charge les liens, et peut sinon être NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est invitée à lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant (et son compteur de références doit donc être incrémenté avant d'être retourné). Tous les appelants doivent appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'est plus nécessaire. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Le résultat dans ce cas doit être toPtr si le lien a réussi et NULL sinon. Dans ce cas, le résultat n'appartient pas à l'appelant (c'est-à-dire qu'aucune manipulation du compteur de références des deux côtés n'est nécessaire). Voir la documentation de Tcl_FSLink pour l'interprétation correcte des indicateurs linkAction.

LISTVOLUMESPROC

Fonction pour lister tous les volumes de système de fichiers ajoutés par ce système de fichiers. Ne doit être implémentée que si le système de fichiers ajoute des volumes à la tête du système de fichiers, afin qu'ils puissent être retournés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste de volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. La valeur du résultat est considérée comme appartenant au système de fichiers (pas au cœur de Tcl), mais doit avoir un compteur de références pour Tcl. Tcl utilisera le contenu de la liste puis décrémentera ce compteur de références. Cela permet aux systèmes de fichiers de choisir s'ils souhaitent réellement conserver une liste "globale" de volumes ou non (sinon, ils génèrent la liste à la volée et la passent à Tcl avec un compteur de références de 1 puis oublient la liste, sinon, ils incrémentent simplement le compteur de références de leur liste globale et la passent à Tcl qui copiera le contenu puis décrémentera le compteur pour revenir à son état précédent).

Par conséquent, Tcl considère les valeurs de retour de ce proc comme étant en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne supportera pas la commande file attributes. Cela permet d'attacher des informations supplémentaires arbitraires aux fichiers dans le système de fichiers. Si elle n'est pas implémentée, il n'est pas nécessaire d'implémenter les méthodes get et set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La fonction appelée peut soit retourner un tableau de chaînes, soit retourner NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer qu'il retourne une valeur avec un compteur de références d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsGet, utilisé par file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Retourne un code de retour Tcl standard. La valeur d'attribut récupérée, qui correspond à l'élément index dans la liste retournée par Tcl_FSFileAttrStringsProc, est un Tcl_Obj placé dans objPtrRef (si TCL_OK a été retourné) et aura probablement un compteur de références de zéro. Dans tous les cas, nous devons soit le stocker quelque part (par exemple, le résultat Tcl), soit incrémenter/décrémenter son compteur de références pour s'assurer qu'il est correctement libéré.

EFFICACITÉ DU SYSTÈME DE FICHIERS

Ces fonctions ne doivent pas être implémentées pour un système de fichiers particulier, car le noyau dispose d'une implémentation de secours. Voir chaque description individuelle pour les conséquences de laisser le champ NULL.

LSTATPROC

Fonction pour traiter un appel à Tcl_FSLstat. Si elle n'est pas implémentée, Tcl tentera d'utiliser le statProc défini précédemment. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut faire la différence entre les appels stat et lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le comportement de cette fonction est très similaire à celui de Tcl_FSStatProc défini précédemment, sauf lorsqu'il est appliqué à un lien symbolique, auquel cas il renvoie des informations sur le lien, et non sur le fichier cible.

COPYFILEPROC

Fonction pour traiter un appel à Tcl_FSCopyFile. Si elle n'est pas implémentée, Tcl utilisera un mécanisme de copie basé sur open-r, open-w et fcopy. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat standard Tcl indiquant si une erreur s'est produite pendant le processus de copie. Il convient de noter que destPathPtr est le nom du fichier qui devrait devenir la copie de srcPathPtr. Ce n'est jamais le nom d'un répertoire dans lequel srcPathPtr peut être copié (c'est-à-dire que la fonction est beaucoup plus simple que le sous-commande file copy au niveau Tcl). Il convient de noter que si le système de fichiers prend en charge les liens symboliques, Tcl appellera cette fonction et non copyDirectoryProc lorsque cela est nécessaire pour les copier (même s'il s'agit de liens symboliques vers des répertoires). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de file copy, appeler Tcl_SetErrno(EXDEV) et renvoyer un résultat différent de TCL_OK amènera Tcl à utiliser ses mécanismes de secours standard.

RENAMEFILEPROC

Fonction pour traiter un appel à Tcl_FSRenameFile. Si elle n'est pas implémentée, Tcl utilisera un mécanisme de copie et de suppression. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat standard Tcl indiquant si une erreur s'est produite pendant le processus de renommage. Si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de file rename, appeler Tcl_SetErrno(EXDEV) et renvoyer un résultat différent de TCL_OK amènera Tcl à utiliser ses mécanismes de secours standard.

COPYDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSCopyDirectory. Si elle n'est pas implémentée, Tcl utilisera un mécanisme de création de répertoires récursif basé sur file mkdir et file copy. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

La valeur de retour est un résultat standard Tcl indiquant si une erreur s'est produite pendant le processus de copie. En cas d'erreur, le nom du fichier ou du répertoire qui a causé l'erreur doit être placé dans errorPtr. Il convient de noter que destPathPtr est le nom du répertoire qui devrait devenir le miroir de srcPathPtr. Ce n'est pas le nom d'un répertoire dans lequel srcPathPtr peut être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande file copy au niveau Tcl). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de copier des répertoires, appeler Tcl_SetErrno(EXDEV) et renvoyer un résultat différent de TCL_OK amènera Tcl à utiliser ses mécanismes de secours standard.

LOADFILEPROC

Fonction pour traiter un appel à Tcl_FSLoadFile. Si elle n'est pas implémentée, Tcl utilisera un mécanisme de copie vers un fichier temporaire suivi d'un appel à Tcl_FSLoadFile sur ce fichier temporaire. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut charger du code directement, ou s'il peut simplement renvoyer TCL_ERROR pour désactiver la fonctionnalité de chargement sur ce système de fichiers.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Renvoie un code de complétion standard Tcl. En cas d'erreur, un message d'erreur est laissé dans le résultat de l'interp. La fonction charge dynamiquement un fichier de code binaire en mémoire. En cas de succès, handlePtr doit être rempli avec un jeton pour le fichier chargé dynamiquement, et unloadProcPtr doit être rempli avec l'adresse d'une procédure. La procédure de déchargement est appelée avec le Tcl_LoadHandle donné comme seul paramètre lorsque Tcl a besoin de décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle renvoyé est actuellement un jeton qui peut être utilisé dans le TclpFindSymbol privé pour accéder aux fonctions du nouveau code. Chaque système de fichiers peut définir le Tcl_LoadHandle comme requis. Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de charger des fichiers, appeler Tcl_SetErrno(EXDEV) et renvoyer un résultat différent de TCL_OK amènera Tcl à utiliser ses mécanismes de secours standard.
