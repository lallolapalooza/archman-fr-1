DESCRIPTION

Il existe plusieurs raisons d'appeler les fonctions de l'API Tcl_FS (par ex. Tcl_FSAccess et Tcl_FSStat) plutôt que d'appeler directement des fonctions de niveau système comme access et stat. Premièrement, elles fonctionneront sur différentes plateformes, donc une extension qui les appelle devrait fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige certains bugs dans les appels de niveau système. Troisièmement, ces appels de fonction gèrent les conversions de chemin « Utf vers natif de la plateforme » qui peuvent être nécessaires (et peuvent mettre en cache les résultats de telles conversions pour une plus grande efficacité lors des appels ultérieurs). Quatrièmement, et peut-être le plus important, toutes ces fonctions sont « conscientes du système de fichiers virtuel » (VFS pour faire court). Tout système de fichiers virtuel (VFS) qui a été enregistré (via Tcl_FSRegister) peut réacheminer l'accès aux fichiers vers des supports ou des méthodes d'accès alternatifs. Cela signifie que toutes ces fonctions (et donc les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent fonctionner sur des « fichiers » qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS pour faire court) via cette API est automatiquement « consciente du système de fichiers virtuel ». Bien sûr, si une extension accède directement au système de fichiers natif (via des API spécifiques à la plateforme, par exemple), Tcl ne peut pas intercepter de tels appels.

Si des VFS appropriés ont été enregistrés, les « fichiers » peuvent, pour donner deux exemples, être distants (par ex. situés sur un serveur ftp distant) ou archivés (par ex. se trouvant à l'intérieur d'une archive .zip). De tels systèmes de fichiers enregistrés fournissent une table de correspondance de fonctions pour implémenter tout ou partie de la fonctionnalité listée ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat masquent la déclaration réelle du tampon « struct stat », permettant d'utiliser le même code sur les systèmes prenant en charge les fichiers de plus de 2 Go et ceux qui n'en prennent pas en charge.

L'API Tcl_FS est basée sur Tcl_Obj et peut mettre en cache des représentations internes et d'autres chaînes liées aux chemins (par ex. le répertoire de travail courant). Une conséquence est qu'il ne faut pas passer de valeurs avec un compteur de références de zéro à aucune de ces fonctions. Si de tels appels étaient traités, ils pourraient entraîner des fuites de mémoire (dans certaines circonstances, le code du système de fichiers peut souhaiter conserver une référence à la valeur transmise, et il ne faut donc pas supposer qu'après le retour de l'un de ces appels, la valeur a toujours un compteur de références de zéro - il peut avoir été incrémenté) ou un crash de segmentation direct (ou une autre erreur d'accès mémoire) en raison de la libération de la valeur au cours de la manipulation complexe de valeurs requise pour s'assurer que le chemin est entièrement normalisé et absolu pour la détermination du système de fichiers. La leçon pratique à en tirer est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect, et peut causer des erreurs de mémoire. Le compteur de références de path doit être incrémenté avant de le passer, ou décrémenté. Pour cette raison, les valeurs avec un compteur de références de zéro sont considérées comme des chemins de système de fichiers non valides et tout appel à une fonction de l'API Tcl_FS avec une telle valeur n'aura aucun effet.

FONCTIONS API FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno à l'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno à l'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction « créer répertoire » du système de fichiers propriétaire.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction « supprimer fichier » du système de fichiers propriétaire.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction « supprimer répertoire » du système de fichiers propriétaire.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « renommer fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno à l'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction « lister volumes » non NULL et leur demande de retourner leur liste de volumes racine. Elle accumule les valeurs de retour dans une liste qui est retournée à l'appelant (avec un compteur de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant l'encodage identifié par encodingName et évalue son contenu comme un script Tcl. Elle retourne les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, l'encodage système est utilisé pour lire le contenu du fichier. Si le fichier n'a pas pu être lu, une erreur Tcl est retournée pour expliquer pourquoi le fichier n'a pas pu être lu. Le caractère de fin de fichier pour les fichiers est « \x1A » (^Z) pour toutes les plateformes. Si vous avez besoin d'un « ^Z » dans le code pour la comparaison de chaînes, vous pouvez utiliser « \x1A », qui sera substitué en toute sécurité par l'interpréteur Tcl en « ^Z ». Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours l'encodage système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier de code binaire en mémoire et retourne les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas, en raison des limitations du système d'exploitation dans le chargement dynamique de code binaire), Tcl tentera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile inverse l'opération, demandant que la bibliothèque indiquée par loadHandle soit supprimée du processus. Notez que, contrairement à la commande unload, cela ne donne pas à la bibliothèque la possibilité de se nettoyer.

Les deux fonctions ci-dessus retournent un code d'achèvement Tcl standard. Si une erreur se produit, un message d'erreur est laissé dans le résultat de interp.

Le jeton fourni via la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de glob pour rechercher dans un répertoire tous les fichiers qui correspondent à un modèle donné. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du glob. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Notez que le code glob implémente les motifs récursifs en interne, de sorte que cette fonction ne recevra que des motifs simples, qui peuvent être mis en correspondance en utilisant la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment en demandant uniquement que les répertoires soient retournés. Un cas spécial où elle est appelée avec un motif NULL indique que le chemin doit être vérifié uniquement pour le type correct.

Tcl_FSLink remplace la version bibliothèque de readlink, et l'étend pour prendre en charge la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr sera appelée.

Si toPtr est NULL, une action de « lecture de lien » est effectuée. Le résultat est un Tcl_Obj spécifiant le contenu du lien symbolique donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant, qui devrait appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl doit créer un lien d'un des types passés dans l'indicateur linkAction. Cet indicateur est une combinaison par OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'un choix existe (c'est-à-dire plus d'un indicateur est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur de retour doit être toPtr (qui appartient donc déjà à l'appelant). En cas d'échec, NULL est retourné.

Tcl_FSLstat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez besoin d'aucun droit d'accès au fichier pour obtenir ces informations, mais vous avez besoin des droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf contient des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, la dernière acce

Temps d'accès, temps de dernière modification et temps de dernière modification des métadonnées. Voir **API DE RÉSULTAT DE STATISTIQUES PORTABLES** pour une description de la manière d'écrire du code portable pour allouer et accéder à la structure *Tcl_StatBuf*. Si *chemin* existe, **Tcl_FSLstat** renvoie 0 et la structure de statistiques est remplie de données. Sinon, -1 est renvoyé, et aucune information de statistiques n'est fournie. **Tcl_FSUtime** remplace la version de la bibliothèque de utime. Cela renvoie 0 en cas de succès et -1 en cas d'erreur (conformément à la documentation de **utime**). En cas de succès, la fonction mettra à jour les valeurs « atime » et « mtime » du fichier donné. **Tcl_FSFileAttrsGet** implémente l'accès en lecture pour la sous-commande **file attributes** hookable. La fonction appropriée pour le système de fichiers auquel appartient *pathPtr* sera appelée. Si le résultat est **TCL_OK**, alors une valeur a été placée dans *objPtrRef*, qui ne sera valide que temporairement (sauf si **Tcl_IncrRefCount** est appelée). **Tcl_FSFileAttrsSet** implémente l'accès en écriture pour la sous-commande **file attributes** hookable. La fonction appropriée pour le système de fichiers auquel appartient *pathPtr* sera appelée. **Tcl_FSFileAttrStrings** implémente une partie de la sous-commande **file attributes** hookable. La fonction appropriée pour le système de fichiers auquel appartient *pathPtr* sera appelée. La procédure appelée peut soit renvoyer un tableau de chaînes, soit renvoyer NULL et placer une liste Tcl dans *objPtrRef* donné. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être éliminée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être éliminée, le système de fichiers doit s'assurer qu'il conserve un compteur de références pour la valeur. **Tcl_FSAccess** vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est *pathname*. Si *pathname* est un lien symbolique sur Unix, alors les permissions du fichier auquel ce lien symbolique fait référence sont testées. En cas de succès (toutes les permissions demandées sont accordées), zéro est renvoyé. En cas d'erreur (au moins un bit dans le mode demandé pour une permission refusée, ou une autre erreur s'est produite), -1 est renvoyé. **Tcl_FSStat** remplit la structure *Tcl_StatBuf* *statPtr* avec des informations sur le fichier spécifié. Vous n'avez besoin d'aucun droit d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure *Tcl_StatBuf* inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le temps du dernier accès, le temps de la dernière modification et le temps de la dernière modification des métadonnées. Voir **API DE RÉSULTAT DE STATISTIQUES PORTABLES** pour une description de la manière d'écrire du code portable pour allouer et accéder à la structure *Tcl_StatBuf*. Si *chemin* existe, **Tcl_FSStat** renvoie 0 et la structure de statistiques est remplie de données. Sinon, -1 est renvoyé, et aucune information de statistiques n'est fournie. **Tcl_FSOpenFileChannel** ouvre un fichier spécifié par *pathPtr* et renvoie un handle de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est basée sur la procédure **fopen** de la bibliothèque d'entrée/sortie standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl **open** lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, **Tcl_FSOpenFileChannel** renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec **Tcl_GetErrno**. De plus, si *interp* n'est pas NULL, **Tcl_FSOpenFileChannel** laisse un message d'erreur dans le résultat de *interp* après toute erreur. Le canal nouvellement créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez **Tcl_RegisterChannel**. Si l'un des canaux standard, **stdin**, **stdout** ou **stderr** a été précédemment fermé, la création du nouveau canal l'attribue également comme remplaçant du canal standard. **Tcl_FSGetCwd** remplace la version de la bibliothèque de **getcwd**. Il renvoie le répertoire de travail courant de la bibliothèque Tcl. Cela peut être différent du répertoire de travail courant de la plateforme native, ce qui se produit lorsque le répertoire de travail courant n'est pas dans le système de fichiers natif. Le résultat est un pointeur vers un Tcl_Obj spécifiant le répertoire courant, ou NULL si le répertoire courant n'a pas pu être déterminé. Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de *interp*. Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compteur de références doit être décrémenté. Ceci est nécessaire pour des raisons de sécurité des threads, afin de permettre à plusieurs threads d'accéder à cette fonction et aux fonctions connexes, tout en garantissant que les résultats sont toujours valides. **Tcl_FSChdir** remplace la version de la bibliothèque de **chdir**. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl se rabattra sur une combinaison de **stat** et **access** pour vérifier si le répertoire existe et a les permissions appropriées. Pour les résultats, voir la documentation de **chdir**. En cas de succès, nous conservons un enregistrement du chemin réussi dans *cwdPathPtr* pour les appels ultérieurs à **Tcl_FSGetCwd**. **Tcl_FSPathSeparator** renvoie le caractère séparateur à utiliser pour l'élément le plus spécifique du chemin spécifié par *pathPtr* (c'est-à-dire la dernière partie du chemin). Le séparateur est renvoyé sous forme de Tcl_Obj contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est renvoyé. **Tcl_FSJoinPath** prend le Tcl_Obj donné, qui doit être une liste valide (qui peut avoir un compteur de références de zéro), et renvoie la valeur du chemin donnée en considérant les *elements* premiers éléments comme des segments de chemin valides (chaque segment de chemin peut être un chemin complet, un chemin partiel ou juste un seul répertoire ou nom de fichier possible). Si un segment de chemin est en fait un chemin absolu, tous les segments de chemin précédents sont supprimés. Si *elements* est inférieur à 0, nous utilisons toute la liste. Il est possible que la valeur renvoyée soit en fait un élément de la liste donnée, donc l'appelant doit faire attention à incrémenter le compteur de références du résultat avant de libérer la liste. La valeur renvoyée, généralement avec un compteur de références de zéro (mais elle peut être partagée dans certaines conditions), contient le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. En particulier, la valeur renvoyée pourrait être un élément de la liste donnée, donc la libération de la liste pourrait libérer la valeur prématurément si aucun compteur de références n'a été pris. Si le nombre d'éléments est zéro, alors la valeur renvoyée sera un Tcl_Obj de chaîne vide. **Tcl_FSSplitPath** prend le Tcl_Obj donné, qui devrait être un chemin valide, et renvoie une valeur de liste Tcl contenant chaque segment de ce chemin comme un élément. Il renvoie une valeur de liste avec un compteur de références de zéro. Si le *lenPtr* passé n'est pas NULL, la variable à laquelle il pointe sera mise à jour pour contenir le nombre d'éléments dans la liste renvoyée. **Tcl_FSEqualPaths** teste si les deux chemins donnés représentent le même objet de système de fichiers. Il renvoie 1 si les chemins sont égaux et 0 s'ils sont différents. Si l'un des chemins est NULL, 0 est toujours renvoyé. **Tcl_FSGetNormalizedPath** tente d'extraire du Tcl_Obj donné une représentation de chemin normalisée unique, dont la valeur de chaîne peut être utilisée comme identifiant unique du fichier. Il renvoie la valeur du chemin normalisé, détenue par Tcl, ou NULL si le chemin était invalide ou ne pouvait pas être converti avec succès. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère sur ces représentations en interne), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques puisse ne pas être la version la plus conviviale d'un chemin. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle de *pathPtr* passé (sauf si c'est un chemin relatif, auquel cas la valeur du chemin normalisé peut être libérée à tout moment où le cwd change) - l'appelant peut bien sûr incrémenter le compteur de références s'il souhaite conserver une copie plus longtemps. **Tcl_FSJoinToPath** prend la valeur donnée, qui devrait généralement être un chemin valide ou NULL, et lui joint le tableau de segments de chemin donnés. Renvoie une valeur, généralement avec un compteur de références de zéro (mais elle peut être partagée dans certaines conditions), contenant le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. Si l'une des valeurs passées à cette fonction (*pathPtr* ou éléments de *path*) a un compteur de références de zéro, elle sera libérée lorsque cette fonction renverra. **Tcl_FSConvertToPathType** essaie de convertir le Tcl_Obj donné en un type de chemin Tcl valide, en tenant compte du fait que le cwd peut avoir changé même si cette valeur est déjà censée être du bon type. Le nom de fichier peut commencer par « ~ » (pour indiquer le répertoire personnel de l'utilisateur courant) ou « ~<utilisateur> » (pour indiquer le répertoire personnel de n'importe quel utilisateur). Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), alors **TCL_OK** est renvoyé. Sinon, **TCL_ERROR** est renvoyé, et un message d'erreur peut être laissé dans l'interpréteur. **Tcl_FSGetInternalRep** extrait la représentation interne d'une valeur de chemin donnée, dans le système de fichiers donné. Si la valeur du chemin appartient à un système de fichiers différent, nous renvoyons NULL. Si la représentation interne est actuellement NULL, nous tentons de la générer, en appelant **Tcl_FSCreateInternalRepProc** du système de fichiers. Renvoie NULL ou une représentation de chemin interne valide. Cette représentation interne est mise en cache, de sorte que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. **Tcl_FSGetTranslatedPath** tente d'extraire le chemin traduit du Tcl_Obj donné. Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), elle est renvoyée. Sinon, NULL sera renvoyé, et un message d'erreur peut être laissé dans l'interpréteur. Un chemin « traduit » est un chemin qui ne contient pas de séquences « ~ » ou « ~utilisateur » (celles-ci ont été développées dans leur représentation actuelle dans le système de fichiers). La valeur renvoyée est détenue par l'appelant, qui doit la stocker ou appeler **Tcl_DecrRefCount** pour s'assurer que la mémoire est libérée. Cette fonction a peu d'utilité pratique, et **Tcl_FSGetNormalizedPath** ou **Tcl_FSGetNativePath** sont généralement de meilleures fonctions à utiliser pour la plupart des besoins. **Tcl_FSGetTranslatedStringPath** fait la même chose que **Tcl_FSGetTranslatedPath**, mais renvoie une chaîne de caractères ou NULL. La chaîne renvoyée est allouée dynamiquement.nd détenu par l'appelant, qui doit le stocker ou appeler ckfree pour s'assurer qu'il est libéré. Encore une fois, Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des usages.

Tcl_FSNewNativePath effectue quelque chose comme l'inverse des conversions habituelles obj->path->reprétation native. Si un code récupère un chemin sous forme native (depuis, par exemple, readlink ou une boîte de dialogue native), et que ce chemin doit être utilisé au niveau Tcl, alors l'appel de cette fonction est un moyen efficace de créer le type de valeur de chemin approprié.

La valeur résultante est une valeur de « chemin » pure, qui ne recevra une représentation sous forme de chaîne UTF-8 que si cela est requis par du code Tcl.

Tcl_FSGetNativePath est destiné à être utilisé par les systèmes de fichiers natifs Win/Unix, de sorte qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un wrapper pratique autour de Tcl_FSGetInternalRep. Il peut être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes (par exemple, sur macOS, une représentation utilisant une structure FSRef de fileSpec serait probablement plus efficace). Sous Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Actuellement, la représentation est simplement une chaîne de caractères qui peut contenir soit le chemin relatif, soit un chemin absolu normalisé complet dans l'encodage natif (des conditions complexes dictent lequel de ceux-ci sera fourni, donc aucun ne peut être fiable, sauf si le chemin est connu pour être absolu). Si vous avez besoin d'un chemin natif qui doit être absolu, vous devriez alors demander la version native d'un chemin normalisé. Si pour une raison quelconque une version non absolue et non normalisée du chemin est nécessaire, cela doit être construit séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache afin que les appels répétés à cette fonction n'entraînent pas de conversions supplémentaires. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle du pathPtr passé (sauf si il s'agit d'un chemin relatif, auquel cas la représentation native peut être libérée à tout moment où le cwd change).

Tcl_FSFileSystemInfo retourne une liste de deux éléments. Le premier élément est le nom du système de fichiers (par exemple, « natif », « vfs », « zip », ou « prowrap », peut-être), et le second est le type particulier du chemin donné dans ce système de fichiers (qui dépend du système de fichiers). Le second élément peut être vide si le système de fichiers ne fournit pas de catégorisation supplémentaire des fichiers.

Une valeur de liste valide est retournée, sauf si la valeur du chemin n'est pas reconnue, auquel cas NULL sera retourné.

Tcl_FSGetFileSystemForPath retourne un pointeur vers le Tcl_Filesystem qui accepte ce chemin comme valide.

Si aucun système de fichiers n'accepte le chemin, NULL est retourné.

Tcl_FSGetPathType détermine si le chemin donné est relatif au répertoire courant, relatif au volume courant, ou absolu.

Il retourne l'un de TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, ou TCL_PATH_VOLUME_RELATIVE

API DU SYSTÈME DE FICHIERS VIRTUEL

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions qui implémentent les diverses opérations sur un système de fichiers ; ces opérations sont invoquées au besoin par la couche générique, ce qui se produit généralement par le biais des fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un élément de données facultatif à associer à ce système de fichiers. Lors de l'appel de cette fonction, Tcl attachera le système de fichiers à la liste des systèmes de fichiers connus, et il deviendra pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera retourné.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et retourne TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est retourné.

Tcl_FSData retournera le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il retournera NULL.

Tcl_FSMountsChanged est utilisé pour informer le cœur de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

LA STRUCTURE TCL_FILESYSTEM

La structure Tcl_Filesystem contient les champs suivants :

typedef struct Tcl_Filesystem {
    const char *typeName;
    int structureLength;
    Tcl_FSVersion version;
    Tcl_FSPathInFilesystemProc *pathInFilesystemProc;
    Tcl_FSDupInternalRepProc *dupInternalRepProc;
    Tcl_FSFreeInternalRepProc *freeInternalRepProc;
    Tcl_FSInternalToNormalizedProc *internalToNormalizedProc;
    Tcl_FSCreateInternalRepProc *createInternalRepProc;
    Tcl_FSNormalizePathProc *normalizePathProc;
    Tcl_FSFilesystemPathTypeProc *filesystemPathTypeProc;
    Tcl_FSFilesystemSeparatorProc *filesystemSeparatorProc;
    Tcl_FSStatProc *statProc;
    Tcl_FSAccessProc *accessProc;
    Tcl_FSOpenFileChannelProc *openFileChannelProc;
    Tcl_FSMatchInDirectoryProc *matchInDirectoryProc;
    Tcl_FSUtimeProc *utimeProc;
    Tcl_FSLinkProc *linkProc;
    Tcl_FSListVolumesProc *listVolumesProc;
    Tcl_FSFileAttrStringsProc *fileAttrStringsProc;
    Tcl_FSFileAttrsGetProc *fileAttrsGetProc;
    Tcl_FSFileAttrsSetProc *fileAttrsSetProc;
    Tcl_FSCreateDirectoryProc *createDirectoryProc;
    Tcl_FSRemoveDirectoryProc *removeDirectoryProc;
    Tcl_FSDeleteFileProc *deleteFileProc;
    Tcl_FSCopyFileProc *copyFileProc;
    Tcl_FSRenameFileProc *renameFileProc;
    Tcl_FSCopyDirectoryProc *copyDirectoryProc;
    Tcl_FSLstatProc *lstatProc;
    Tcl_FSLoadFileProc *loadFileProc;
    Tcl_FSGetCwdProc *getCwdProc;
    Tcl_FSChdirProc *chdirProc;
} Tcl_Filesystem;

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche de système de fichiers générique pour effectuer la gamme complète d'actions liées au système de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (presque toutes doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni) et fonctions d'efficacité (qui n'ont besoin d'être implémentées que si elles peuvent l'être efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces replis ne sont utilisés que pour gérer les commandes initiées en Tcl, pas en C. Ce que cela signifie, c'est que si une commande de renommage de fichier est émise en Tcl, et que le(s) système(s) de fichiers pertinent(s) n'implémentent pas leur Tcl_FSRenameFileProc, le cœur de Tcl se rabattra sur une combinaison d'autres fonctions de système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a un repli supplémentaire). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun de ces replis ne se produit. Ceci est vrai sauf pour les quatre dernières entrées du tableau de système de fichiers (lstat, load, getcwd et chdir) pour lesquels des replis se produisent en effet au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme Tcl_Obj les prennent sous forme UTF-8. L'API d'infrastructure du système de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

STRUCTURE DU SYSTÈME DE FICHIERS

Ces champs contiennent des informations de base sur la structure du système de fichiers et les adresses des fonctions utilisées pour associer un système de fichiers particulier à un chemin de fichier, et pour gérer le traitement interne des représentations de chemin, par exemple la copie et la libération de ces représentations.

NOM DU TYPE

Le champ typeName contient une chaîne terminée par un caractère nul qui identifie le type du système de fichiers implémenté, par exemple « natif », « zip » ou « vfs ».

LONGUEUR DE LA STRUCTURE

Le champ structureLength est généralement implémenté comme sizeof(Tcl_Filesystem), et est là pour permettre une meilleure compatibilité ascendante binaire si la taille de la structure change dans une future version de Tcl.

VERSION

Le champ version doit être défini à TCL_FILESYSTEM_VERSION_1.

PROC_CHEMIN_DANS_SYSTÈME_DE_FICHIERS

Le champ pathInFilesystemProc contient l'adresse d'une fonction qui est appelée pour déterminer si une valeur de chemin donnée appartient à ce système de fichiers ou non. Tcl n'appellera les autres fonctions du système de fichiers qu'avec un chemin pour lequel cette fonction a retourné TCL_OK. Si le chemin n'appartient pas, -1 doit être retourné (le comportement de Tcl pour toute autre valeur de retour n'est pas défini). Si TCL_OK est retourné, alors le paramètre de sortie optionnel clientDataPtr peut être utilisé pour retourner une représentation interne (spécifique au système de fichiers) du chemin, qui sera mise en cache dans la valeur du chemin, et pourra être récupérée efficacement par les autres fonctions du système de fichiers. Tcl mettra simultanément en cache le fait que ce chemin appartient à ce système de fichiers. De tels caches sont invalidés lorsque des structures de système de fichiers sont ajoutées ou retirées de la liste interne de Tcl des systèmes de fichiers connus.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROC_COPIER_REPRÉSENTATION_INTERNE

Cette fonction crée une copie de la représentation interne d'un chemin, et est appelée lorsque Tcl doit dupliquer une valeur de chemin. Si elle est NULL, Tcl ne copiera simplement pas la représentation interne, qui pourra alors devoir être régénérée plus tard.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

PROC_LIBÉRER_REPRÉSENTATION_INTERNE

Libère la représentation interne. Ceci doit être implémenté si les représentations internes nécessitent une libération (c'est-à-dire si de la mémoire est allouée lors de la génération d'une représentation interne), mais peut sinon être NULL.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

PROC_INTERNE_VERS_NORMALISÉ

Fonction pour convertir une représentation interne en un chemin normalisé. Nécessaire uniquement si le système de fichiers crée des valeurs de chemin pures sans représentation textuelle/de chemin. La valeur de retour est une valeur Tcl dont la représentation textuelle est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

PROC_CRÉER_REPRÉSENTATION_INTERNE

Fonction pour prendre une valeur de chemin, calculer une représentation interne pour celle-ci, et stocker cette représentation native dans la valeur. Peut être NULL si les chemins n'ont pas de représentation interne, ou si Tcl_FSPathInFilesystemProc pour ce système de fichiers crée toujours immédiatement une représentation interne pour les chemins qu'il accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

PROC_NORMALISER_CHEMIN

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations textuelles pour la même valeur de chemin. Dans Tcl, chaque « chemin » doit avoir une unique représentation textuelle « normalisée ». Selon le système de fichiers, il peut y avoir plus d'une représentation textuelle non normalisée qui fait référence à ce chemin (par exemple, un chemin relatif, un chemin avec une casse différente si le système de fichiers ne tient pas compte de la casse, un chemin contenant une référence à un répertoire personnel comme « ~ », un chemin contenant des liens symboliques, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être converti en la valeur à laquelle il pointe (mais sa casse ou d'autres aspects doivent être rendus uniques). Tous les autres composants du chemin doivent être convertis à partir des liens symboliques. Cette exception est nécessaire pour s'accorder avec la sémantique de Tcl pour les opérations file delete, file rename, file copy sur les liens symboliques. Cette fonction peut être appelée avec nextCheckpoint soit au début du chemin (c'est-à-dire zéro), soit à la fin du chemin, soit à n'importe quel séparateur de fichier intermédiaire dans le chemin. Elle ne pointera jamais vers une autre position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS DU SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions qui sont appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui est censé être utilisé avec l'ensemble complet des commandes Tcl standard doit implémenter toutes ces fonctions. Si certaines d'entre elles ne sont pas implémentées, certaines commandes Tcl peuvent échouer lors de l'opération sur des chemins dans ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques n'a pas besoin d'implémenter la fonction readlink, etc. Le noyau Tcl s'attend à ce que les systèmes de fichiers se comportent de cette manière).

PROC_TYPE_CHEMIN_SYSTÈME_DE_FICHIERS

Fonction pour déterminer le type d'un chemin dans ce système de fichiers. Peut être NULL, auquel cas aucune information de type ne sera disponible pour les utilisateurs du système de fichiers. Le « type » est uniquement utilisé à des fins d'information, et doit être retourné comme la représentation textuelle de l'objet Tcl retourné. Une valeur typique pourrait être « réseau », « zip » ou « ftp ». L'objet Tcl résultat appartient au système de fichiers, Tcl incrémentera donc le compteur de références de cette valeur s'il souhaite en conserver une référence.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

PROC_SÉPARATEUR_SYSTÈME_DE_FICHIERS

Fonction pour retourner le(s) caractère(s) séparateur(s) pour ce système de fichiers. Ceci n'a besoin d'être implémenté que si le système de fichiers souhaite utiliser un séparateur différent de la chaîne standard « / ». Entre autres utilisations, il est retourné par la commande file separator. La valeur de retour doit être une valeur avec un compteur de références de zéro.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

PROC_STAT

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes au niveau Tcl en dépendent crucialement (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le Tcl_FSStatProc remplit la structure stat statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure stat inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le temps du dernier accès, le temps de la dernière modification, et le temps du dernier changement de métadonnées.

Si le fichier représenté par pathPtr existe, le Tcl_FSStatProc retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné, et aucune information stat n'est donnée.

PROC_ACCÈS

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes au niveau Tcl en dépendent crucialement (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

Le Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est dans pathPtr. Si le chemin fait référence à un lien symbolique, alors les permissions du fichier auquel ce lien symbolique fait référence doivent être testées.

En cas de succès (toutes les permissions demandées accordées), zéro est retourné. En cas d'erreur (au moins un bit dans mode demandait une permission refusée, ou une autre erreur s'est produite), -1 est retourné.

PROC_OUVRIR_CANAL_FICHIER

Fonction pour traiter un appel Tcl_FSOpenFileChannel. C'est une fonction d'interface pour les opérations de lecture/écriture de fichiers de base.

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_Obj *channelTypePtr,
        const char *openMode,
        ClientData passed);
OPENFILECHANNELPROC

Fonction pour traiter un appel à Tcl_FSOpenFileChannel. Elle doit être implémentée pour tout système de fichiers raisonnable, car toute opération nécessitant l'ouverture ou l'accès au contenu d'un fichier utilisera cette fonction (par exemple, open, encoding et de nombreuses commandes Tk).

  
typedef Tcl_Channel Tcl_FSOpenFileChannelProc(  
        Tcl_Interp *interp,  
        Tcl_Obj *pathPtr,  
        int mode,  
        int permissions);

La Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et renvoie un handle de canal qui peut être utilisé pour effectuer des lectures et des écritures dans le fichier. Cette API est modelée sur la fonction fopen de la bibliothèque d'entrée/sortie standard Unix. La signification et le symbole de tous les arguments sont similaires à ceux des commandes Tcl open lors de l'ouverture d'un fichier, où le mode est une combinaison des indicateurs POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannelProc renvoie NULL et enregistre un code d'erreur POSIX qui peut être obtenu avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le nouveau canal créé ne doit pas être enregistré auprès de l'interpréteur par Tcl_FSOpenFileChannelProc; ce travail incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standards, stdin, stdout ou stderr a été précédemment fermé, la création du nouveau canal l'affecte également comme canaux standards.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, la fonctionnalité de glob et de copie récursive sera absente du système de fichiers (et cela peut affecter des commandes comme encoding names qui utilisent la fonctionnalité de glob).

  
typedef int Tcl_FSMatchInDirectoryProc(  
        Tcl_Interp *interp,  
        Tcl_Obj *resultPtr,  
        Tcl_Obj *pathPtr,  
        const char *pattern,  
        Tcl_GlobTypeData *types);

La fonction doit renvoyer tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au motif donné et satisfont la spécification de types. Cette fonction peut être appelée de deux manières. Si pattern est NULL, pathPtr est une spécification complète d'un fichier ou répertoire unique qui doit être vérifié quant à son existence et son type. Sinon, pathPtr est un répertoire dont les entrées doivent être recherchées pour trouver des fichiers ou répertoires du type correct. Dans tous les cas, pathPtr est supposé être non NULL et non vide. Il n'est pas documenté actuellement si pathPtr aura un séparateur de fichier à la fin, le code doit donc être flexible aux deux possibilités.

La valeur de retour est un résultat standard Tcl indiquant si une erreur s'est produite pendant le processus de correspondance. Les messages d'erreur sont placés dans interp, à moins que interp ne soit NULL, auquel cas aucun message d'erreur n'est généré. En cas de résultat TCL_OK, les résultats doivent être ajoutés à la valeur donnée dans resultPtr (qui est supposée être une liste Tcl non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (ce qui signifie généralement qu'il s'agit de spécifications de chemin absolues). Note : si aucune correspondance n'est trouvée, un résultat vide est généré; seules des erreurs réelles de fichier ou de système de fichiers survenant pendant le processus de correspondance signalent des erreurs.

Le Tcl_GlobTypeData passé dans le paramètre types contient les champs suivants :

  
typedef struct Tcl_GlobTypeData {  
    /* Correspond à bcdpfls comme dans 'find -t' */  
    int type;  
    /* Correspond aux permissions de fichier */  
    int perm;  
    /* Type MAC accepté */  
    Tcl_Obj *macType;  
    /* Créateur MAC accepté */  
    Tcl_Obj *macCreator;  
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de traiter correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types & TCL_GLOB_TYPE_DIR est vrai ou lorsque types->types & TCL_GLOB_TYPE_MOUNT est vrai (et en particulier lorsque les autres indicateurs sont faux). Dans le premier cas, la fonction doit lister les répertoires contenus. Tcl utilise cela pour implémenter le globbing récursif, il est donc essentiel que les systèmes de fichiers implémentent correctement la correspondance de répertoires. Dans le second cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage rencontrés dans pathPtr (et dans ce cas, pathPtr n'a pas besoin d'être à l'intérieur du même système de fichiers - contrairement à tous les autres cas où cette fonction est appelée). Le support pour cela est critique si Tcl doit avoir des transitions douces entre les systèmes de fichiers.

UTIMEPROC

Fonction pour traiter un appel à Tcl_FSUtime. Elle est requise pour permettre la configuration (pas la lecture) des temps de modification et d'accès aux fichiers, et l'implémentation de la fonction de copie de fichiers de open-r/open-w/fcopy.

  
typedef int Tcl_FSUtimeProc(  
        Tcl_Obj *pathPtr,  
        struct utimbuf *tval);

Les temps d'accès et de modification du fichier spécifié par pathPtr doivent être modifiés aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec la fonction système utime.

LINKPROC

Fonction pour traiter un appel à Tcl_FSLink. Elle doit être implémentée uniquement si le système de fichiers prend en charge les liens, et peut être NULL.

  
typedef Tcl_Obj *Tcl_FSLinkProc(  
        Tcl_Obj *linkNamePtr,  
        Tcl_Obj *toPtr,  
        int linkAction);

Si toPtr est NULL, la fonction est sollicitée pour lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien ne peut pas être lu. Le résultat appartient à l'appelant (et par conséquent, son compteur de références doit être incrémenté avant d'être renvoyé). Tout appelant doit appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'en a plus besoin. Si toPtr n'est pas NULL, la fonction doit essayer de créer un lien. Dans ce cas, le résultat doit être toPtr si le lien a réussi et NULL sinon. Dans ce cas, le résultat n'appartient pas à l'appelant (c'est-à-dire qu'il n'y a pas de manipulation des compteurs de références des deux côtés). Voir la documentation de Tcl_FSLink pour l'interprétation correcte des indicateurs de linkAction.

LISTVOLUMESPROC

Fonction pour lister les volumes du système de fichiers ajoutés par ce système de fichiers. Elle doit être implémentée uniquement si le système de fichiers ajoute des volumes au début du système de fichiers, afin qu'ils puissent être renvoyés par file volumes.

  
typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste de volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) s'il n'y a pas de volumes fournis. La valeur de retour est considérée comme la propriété du système de fichiers (pas de Tcl), mais elle doit avoir un comptage de références pour Tcl. Tcl utilisera le contenu de la liste, puis décrémentera le comptage de références. Cela permet aux systèmes de fichiers de choisir s'ils veulent maintenir une liste globale de volumes ou non (si non, ils génèrent la liste à la volée et la passent à Tcl avec un comptage de références de 1, puis oublient la liste; si oui, alors ils incrémentent le comptage de références de leur liste globale et la passent à Tcl qui copie le contenu puis décrémente le compteur de références pour le ramener à sa valeur initiale).

Par conséquent, Tcl considère les valeurs de retour de cette proc comme étant lues et non modifiables.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne prendra pas en charge la commande file attributes. Cela permet des informations supplémentaires arbitraires sur les fichiers du système de fichiers. Si elle n'est pas implémentée, les méthodes get et set n'ont pas besoin d'être implémentées.

  
typedef const char *const *Tcl_FSFileAttrStringsProc(  
        Tcl_Obj *pathPtr,  
        Tcl_Obj **objPtrRef);

La fonction peut renvoyer un tableau de chaînes ou, alternativement, renvoyer NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Après avoir terminé l'utilisation, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être détruite par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si elle ne doit pas être détruite, le système de fichiers doit garantir qu'il renvoie une valeur avec un compteur de références d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsGet, utilisée par file attributes.

  
typedef int Tcl_FSFileAttrsGetProc(  
        Tcl_Interp *interp,  
        int index,  
        Tcl_Obj *pathPtr,  
        Tcl_Obj **objPtrRef);

Renvoie un code de retour Tcl standard. La valeur de la propriété de l'attribut récupéré, correspondant à l'élément d'indice index dans la liste renvoyée par Tcl_FSFileAttrStringsProc, est placée dans objPtrRef (si TCL_OK a été renvoyé) et aura probablement un compteur de références de zéro. Même ainsi, nous devons stocker cette valeur (par exemple, dans le résultat Tcl) ou incrémenter/décrémenter son compteur de références pour garantir qu'elle est correctement libérée.

FILEATTRSSETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsSet, utilisée par file attributes. Si le système de fichiers est en lecture seule, cette fonction n'a pas besoin d'être implémentée.

  
typedef int Tcl_FSFileAttrsSetProc(  
        Tcl_Interp *interp,  
        int index,  
        Tcl_Obj *pathPtr,  
        Tcl_Obj *objPtr);

La valeur de la propriété de l'attribut pour la index-ième entrée dans la liste renvoyée par Tcl_FSFileAttrStringsProc doit être définie sur l'objPtr donné.

CREATEDIRECTORYPROC

Fonction pour créer des répertoires sur un système de fichiers. Si le système de fichiers ne prend pas en charge les liens, cette fonction n'a pas besoin d'être implémentée.

  
typedef int Tcl_FSCreateDirectoryProc(  
        Tcl_Interp *interp,  
        Tcl_Obj *pathPtr,  
        int action);

La fonction doit créer un répertoire au chemin spécifié par pathPtr selon l'action. La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur.
