DESCRIPTION

Il existe plusieurs raisons pour lesquelles les fonctions de l'API Tcl_FS (par exemple, Tcl_FSAccess et Tcl_FSStat) sont appelées au lieu d'appeler directement des fonctions de niveau système telles que access et stat. Premièrement, ces fonctions fonctionneront de manière inter-plateformes, de sorte que toute extension qui les appelle doit fonctionner sans modification sous Unix et Windows. Deuxièmement, l'implémentation de certaines de ces fonctions sous Windows corrige certains bugs dans les appels de niveau système. Troisièmement, ces appels gèrent toute conversion de chemin de type "UTF vers plateforme native" qui pourrait être nécessaire (et peuvent mettre en cache les résultats de ces conversions pour plus d'efficacité lors des appels ultérieurs). Quatrièmement, et peut-être le plus important, toutes ces fonctions sont "conscientes des fichiers virtuels". Tout système de fichiers virtuel (VFS en abrégé) enregistré (via Tcl_FSRegister) peut rediriger l'accès aux fichiers vers des supports ou des méthodes d'accès alternatifs. Cela signifie que toutes ces fonctions (et par conséquent les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent fonctionner avec des fichiers qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS en abrégé) via cette API devient automatiquement "consciente des fichiers virtuels". Bien sûr, si une extension accède directement au système de fichiers natif (via des API spécifiques au système, par exemple), alors Tcl ne peut pas intercepter de tels appels.

Si les VFS ont été correctement enregistrés, les "fichiers" peuvent être, par exemple, distants (comme s'ils étaient situés sur un serveur ftp distant) ou archivés (comme s'ils étaient situés dans un fichier .zip). Ces VFS enregistrés fournissent un ensemble de fonctions pour implémenter tout ou partie de la fonctionnalité mentionnée ici. Enfin, les appels à Tcl_FSStat et Tcl_FSLstat abstraient le contenu du buffer struct stat, permettant d'utiliser le même code sur des systèmes avec et sans support pour les fichiers de plus de 2 Go.

L'API Tcl_FS est "typée" comme Tcl_Obj et peut mettre en cache des représentations internes et d'autres chaînes de caractères liées aux chemins (par exemple, le répertoire courant). Un effet secondaire est qu'il ne faut pas passer à n'importe quelle fonction ces valeurs avec un compteur de références nul. Si elles étaient traitées ainsi, elles pourraient provoquer des fuites de mémoire (dans certains cas, le code du système de fichiers pourrait abandonner une référence à la valeur passée, et par conséquent, il ne faut pas supposer qu'après n'importe quel appel à ces fonctions, la valeur ait un compteur de références nul - il pourrait avoir été incrémenté). Ou encore, elles pourraient provoquer un échec de segmentation (ou une autre erreur d'accès mémoire) parce que la valeur a été libérée lors d'une manipulation complexe de valeurs pour normaliser et rendre absolu le chemin. La leçon pratique à retenir est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect et peut entraîner des erreurs de mémoire. Le path doit avoir son compteur de références incrémenté avant d'être passé, ou décrémenté. Pour cette raison, les valeurs avec un compteur de références nul sont considérées comme invalides en tant que chemins de système de fichiers et tout appel à une fonction de l'API Tcl_FS avec ces valeurs n'entraînera aucune action.

FS API FUNCTIONS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés sont sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction de copie de fichier du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la valeur globale C de errno à EXDEV (code POSIX indiquant un "léger" cross-link).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés sont sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction de copie de répertoire du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la valeur globale C de errno à EXDEV (code POSIX indiquant un "léger" cross-link).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction de création de répertoire du système de fichiers qui le possède.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction de suppression de fichier du système de fichiers qui le possède.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction de suppression de répertoire du système de fichiers qui le possède.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés sont sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction de renommage de fichier du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la valeur globale C de errno à EXDEV (code POSIX indiquant un "léger" cross-link).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction "lister les volumes" non nulle et leur demande de renvoyer leur liste de volumes racines. Elle accumule les valeurs renvoyées dans une liste qui est renvoyée à l'appelant (avec un compteur de références 0).

Tcl_FSEvalFileEx lit le contenu du fichier donné par pathPtr en utilisant le code d'encodage identifié par encodingName et évalue son contenu comme un script Tcl. Elle renvoie les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, l'encodage du système est utilisé pour lire le contenu du fichier. Si le fichier ne peut pas être lu, une erreur Tcl est renvoyée pour décrire pourquoi il ne peut pas être lu. Le caractère EOF pour les fichiers est \x1A (^Z) pour tous les systèmes. Si vous voulez avoir ^Z dans un code de comparaison de chaînes, vous pouvez utiliser \x1A, qui sera probablement remplacé par l'interpréteur Tcl comme ^Z. Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours l'encodage du système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier binaire en mémoire et renvoie les adresses de deux procédures à l'intérieur de ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas en raison des limitations du système pour le chargement de code binaire), Tcl tentera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile annule cette opération, en demandant que le livre indiqué par loadHandle soit supprimé du processus. Notez que, contrairement à la commande unload, cela ne donne aucune chance au livre de se nettoyer.

Les deux fonctions mentionnées ci-dessus renvoient un code de complétion Tcl standard. Si une erreur se produit, un message d'erreur est laissé dans le résultat de l'interp.

Le jeton fourni par la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher tous les fichiers qui correspondent à un motif donné dans un répertoire. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La valeur renvoyée est un résultat Tcl standard indiquant s'il y a eu une erreur dans le globbing. Les messages d'erreur sont placés dans l'interp (sauf si l'interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans le resultPtr donné.

Notez que le code de glob implémente des motifs récursifs en interne, de sorte que cette fonction ne recevra que des motifs simples, qui peuvent être mis en correspondance avec la logique de string match. Pour gérer la récursivité, Tcl appellera cette fonction fréquemment en demandant uniquement aux répertoires d'être renvoyés. Une exception spéciale consistant à être appelée avec un motif nul indique que le chemin doit simplement être vérifié pour le bon type.

Tcl_FSLink remplace la version de la bibliothèque de readlink et l'étend pour supporter la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr sera appelée.

Si toPtr est NULL, une action de "lecture de lien" sera effectuée. Le résultat est un objet Tcl spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien ne peut pas être lu. Le résultat est tout ce qui doit être pris en compte par l'appelant, qui doit appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl doit créer un lien de l'un des types de liens passés dans le linkAction de l'indicateur. Cet indicateur est une combinaison OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. S'il y a un choix (c'est-à-dire que plus d'un indicateur est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur renvoyée devrait être toPtr (il est donc déjà sous la responsabilité de l'appelant). S'il ne peut pas être créé, NULL est renvoyé.

Toutes les structures de fichiers sont conservées. Temps d'accès ST, temps de dernière modification et dernier changement de métadonnées. Si le _path_ existe, **Tcl_FSLstat** renvoie 0 et la structure _statPtr_ est remplie de données. Sinon, elle renvoie -1 et aucune donnée de stat n'est fournie. **Tcl_FSUtime** remplace la version de la bibliothèque de la fonction _utime_. Elle renvoie 0 en cas de succès et -1 en cas d'erreur (conformément à la documentation de **utime**). En cas de succès, elle met à jour les valeurs **atime** et **mtime** d'un fichier donné. **Tcl_FSFileAttrsGet** implémente l'accès en lecture pour le sous-commande **file attributes** du hookable **file** du système de fichiers. La fonction appropriée, en fonction du système de fichiers auquel appartient _pathPtr_, est appelée. Si le résultat est **TCL_OK**, une valeur est placée dans _objPtrRef_, qui ne sera valide que temporairement (sauf si **Tcl_IncrRefCount** est appelé). **Tcl_FSFileAttrsSet** implémente l'accès en écriture pour le sous-commande **file attributes** du hookable **file** du système de fichiers. La fonction appropriée, en fonction du système de fichiers auquel appartient _pathPtr_, est appelée. **Tcl_FSFileAttrStrings** implémente une partie du sous-commande **file attributes** du hookable **file** du système de fichiers. La fonction appropriée, en fonction du système de fichiers auquel appartient _pathPtr_, est appelée. La procédure appelée peut renvoyer un tableau de chaînes, ou renvoyer NULL et placer une liste Tcl dans _objPtrRef_. Tcl prendra cette liste et incrémentera son compteur de références avant de l'utiliser. Lorsqu'elle aura fini de l'utiliser, elle décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, son compteur de références doit être égal à zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer qu'elle conserve un compteur de références à sa valeur. **Tcl_FSAccess** vérifie si le processus serait autorisé à lire, écrire ou tester l'existence d'un fichier (ou objet de système de fichiers) dont le nom est _pathname_. Si _pathname_ est un lien symbolique sous Unix, les permissions du fichier auquel ce lien symbolique fait référence sont testées. En cas de succès (toutes les permissions demandées), renvoie 0. En cas d'erreur (au moins un bit du mode demandé est refusé ou une autre erreur s'est produite), renvoie -1. **Tcl_FSStat** remplit la structure _Tcl_StatBuf_ avec des informations sur le fichier spécifié. Aucun droit d'accès au fichier n'est requis pour obtenir ces informations, mais des droits de parcours sont nécessaires pour tous les répertoires mentionnés dans le chemin menant au fichier. La structure _Tcl_StatBuf_ comprend des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nlink (toujours 1 sous Windows), l'identifiant utilisateur (toujours 0 sous Windows), l'identifiant groupe (toujours 0 sous Windows), le rdev (identique au périphérique sous Windows), la taille, le temps d'accès le plus récent, le temps de dernière modification et le dernier changement de métadonnées. Voir l'**API PORTABLE STAT RESULT** pour une description sur la façon d'écrire du code portable pour héberger et accéder à la structure _Tcl_StatBuf_. Si _path_ existe, **Tcl_FSStat** renvoie 0 et la structure _statPtr_ est remplie de données. Sinon, elle renvoie -1 et aucune donnée de stat n'est fournie. **Tcl_FSOpenFileChannel** ouvre un fichier spécifié par _pathPtr_ et renvoie un handle de canal qui peut être utilisé pour lire et écrire dans le fichier. Cette API est calquée sur la fonction _fopen_ de la bibliothèque d'entrée/sortie standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles de la commande _open_ de Tcl lors de l'ouverture de fichiers. Si une erreur se produit lors de l'ouverture du canal, **Tcl_FSOpenFileChannel** renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec **Tcl_GetErrno**. De plus, si _interp_ n'est pas NULL, **Tcl_FSOpenFileChannel** laisse un message d'erreur dans le résultat de _interp_'s après toute erreur. Le canal nouvellement créé n'est pas enregistré auprès de l'interpréteur fourni ; pour l'enregistrer, utilisez **Tcl_RegisterChannel**. Si l'un des canaux standard, **stdin**, **stdout** ou **stderr**, a été précédemment fermé, l'acte de création du nouveau canal l'attribue également comme substitut du canal standard. **Tcl_FSGetCwd** remplace la version de la bibliothèque de la fonction **getcwd**. Elle renvoie le répertoire de travail actuel de la bibliothèque Tcl. Cela peut être différent du répertoire de travail natif, ce qui se produit lorsque le répertoire de travail actuel ne se trouve pas dans le système de fichiers natif. Le résultat est un pointeur vers un _Tcl_Obj_ spécifiant le répertoire actuel, ou NULL si le répertoire ne peut pas être déterminé. Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de _interp_'s. Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'en a plus besoin, ce compteur doit être décrémenté. Ceci est nécessaire pour la sécurité multithread, pour permettre à plusieurs threads d'accéder à cette fonction et à d'autres tout en garantissant que les résultats sont toujours valides. **Tcl_FSChdir** remplace la version de la bibliothèque de la fonction **chdir**. Le chemin est normalisé puis transmis au système de fichiers qui le revendique. Si ce système n'implémente pas cette fonction, Tcl s'appuie sur une combinaison de **stat** et **access** pour vérifier si le répertoire existe et a les permissions appropriées. Pour les résultats, voir la documentation de **chdir**. En cas de succès, un enregistrement du chemin réussi est conservé dans _cwdPathPtr_ pour les appels ultérieurs à **Tcl_FSGetCwd**. **Tcl_FSPathSeparator** renvoie le caractère séparateur pour l'élément le plus spécifique du chemin spécifié par _pathPtr_ (c'est-à-dire le dernier segment du chemin). Le séparateur est renvoyé sous la forme d'un _Tcl_Obj_ contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est renvoyé. **Tcl_FSJoinPath** prend le _Tcl_Obj_ donné, qui doit être une liste valide (permettant d'avoir un compteur de références égal à zéro), et renvoie la valeur du chemin donnée en considérant les _elements_ premiers comme des segments de chemin valides (chaque segment peut être un chemin complet, un chemin partiel ou juste un répertoire ou un nom de fichier). Si un segment de chemin est effectivement un chemin absolu, tous les segments précédents sont ignorés. Si _elements_ est inférieur à 0, l'entier complet est utilisé. Il est possible que la valeur renvoyée soit effectivement un élément de la liste donnée, de sorte que l'appelant doit faire attention à incrémenter le compteur de références du résultat avant de libérer la liste. La valeur renvoyée, généralement avec un compteur de références égal à zéro (mais pouvant être partagée sous certaines conditions), contient le chemin concaténé. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. En particulier, la valeur renvoyée peut être un élément de la liste donnée, de sorte que la libération de la liste pourrait libérer prématurément la valeur si aucun compteur de références n'a été pris. Si le nombre d'éléments est zéro, la valeur renvoyée sera une chaîne vide _Tcl_Obj_. **Tcl_FSSplitPath** prend le _Tcl_Obj_ donné, qui devrait être un chemin valide, et renvoie une valeur de liste contenant chaque segment de ce chemin comme élément. Elle renvoie une valeur de liste avec un compteur de références égal à zéro. Si le _lenPtr_ passé n'est pas NULL, la variable pointée est mise à jour avec le nombre d'éléments dans la valeur renvoyée. **Tcl_FSEqualPaths** teste si les deux chemins donnés représentent le même objet de système de fichiers. Elle renvoie 1 s'ils sont égaux, 0 s'ils sont différents. Si l'un des chemins est NULL, elle renvoie toujours 0. **Tcl_FSGetNormalizedPath** tente d'extraire une représentation normalisée unique du chemin donné, dont la valeur de chaîne peut être utilisée comme identifiant unique du fichier. Elle renvoie le chemin normalisé, détenu par Tcl, ou NULL si le chemin était invalide ou n'a pas pu être converti avec succès. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère en interne sur ces représentations), bien que le résultat lorsque le système de fichiers contient plusieurs liens symboliques ne sera pas la version la plus conviviale d'un chemin. La valeur renvoyée est détenue par Tcl et a une durée de vie équivalente à celle de _pathPtr_ passé (sauf s'il s'agit d'un chemin relatif, auquel cas le chemin normalisé peut être libéré à tout moment lorsque le cwd change) - l'appelant peut incrémenter le compteur de références s'il le souhaite pour conserver une copie plus longue. **Tcl_FSJoinToPath** prend la valeur donnée, qui est généralement un chemin valide ou NULL, et joint les segments de chemin donnés. Elle renvoie une valeur, généralement avec un compteur de références égal à zéro (mais pouvant être partagée sous certaines conditions), qui contient le chemin joint. L'appelant doit incrémenter le compteur de références avant de l'utiliser. Si l'une des valeurs passées à cette fonction (_pathPtr_ ou les éléments _path_) a un compteur de références égal à zéro, elles seront libérées lorsque cette fonction retournera. **Tcl_FSConvertToPathType** tente de convertir le _Tcl_Obj_ donné en un type de chemin valide, en tenant compte du fait que le cwd pourrait avoir changé même si cette valeur est déjà du type attendu. Le nom de fichier peut commencer par ~ (pour indiquer le répertoire utilisateur actuel) ou ~ (pour indiquer le répertoire de n'importe quel utilisateur). Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), **TCL_OK** est renvoyé. Sinon, **TCL_ERROR** est renvoyé, et un message d'erreur peut être laissé dans l'interpréteur. **Tcl_FSGetInternalRep** extrait la représentation interne d'une valeur de chemin donnée dans un système de fichiers spécifique. Si la valeur de chemin appartient à un système de fichiers différent, elle renvoie NULL. Si la représentation interne est actuellement NULL, elle tente de la générer en appelant le **Tcl_FSCreateInternalRepProc** du système de fichiers. Elle renvoie NULL ou une représentation de chemin interne valide. Cette représentation interne est mise en cache, de sorte que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. **Tcl_FSGetTranslatedPath** tente d'extraire un chemin traduit à partir du _Tcl_Obj_ donné. Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), la valeur est renvoyée. Sinon, elle renvoie NULL et peut laisser un message d'erreur dans l'interpréteur. Un chemin traduit est un chemin qui ne contient aucune séquence de ~ (ou ~utilisateur) (celles-ci ont été développées en leur représentation actuelle dans le système de fichiers). La valeur renvoyée est la propriété de l'appelant, qui doit la stocker ou appeler **Tcl_DecrRefCount** pour s'assurer que la mémoire est libérée. Cette fonction a peu d'utilité pratique, et **Tcl_FSGetNormalizedPath** ou **Tcl_FSGetNativePath** sont généralement des fonctions plus utiles à ces fins. **Tcl_FSGetTranslatedStringPath** fait la même chose que **Tcl_FSGetTranslatedPath**, mais renvoie une chaîne ou NULL. La chaîne renvoyée est allouée dynamiquement. cated et appartenant à l'appelant, qui doit le stocker ou appeler ckfree pour s'assurer qu'il est libéré. Encore une fois, Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des usages.

Tcl_FSNewNativePath effectue quelque chose comme l'inverse des conversions habituelles obj->path->nativerep. Si un code récupère un chemin sous forme native (à partir, par exemple, de readlink ou d'une boîte de dialogue native), et que ce chemin doit être utilisé au niveau Tcl, alors appeler cette fonction est un moyen efficace de créer le type de valeur de chemin approprié.

La valeur résultante est une valeur de "chemin" pure, qui ne recevra une représentation en chaîne UTF-8 que si cela est requis par du code Tcl.

Tcl_FSGetNativePath est destiné à être utilisé par les systèmes de fichiers natifs Win/Unix, afin qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un wrapper pratique autour de Tcl_FSGetInternalRep. Il peut être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes (par exemple, sur macOS, une représentation utilisant une structure FSRef de fileSpec serait probablement plus efficace). Sous Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Actuellement, la représentation est simplement une chaîne de caractères qui peut contenir soit le chemin relatif, soit un chemin absolu normalisé complet dans l'encodage natif (des conditions complexes déterminent lequel de ceux-ci sera fourni, de sorte qu'aucun ne peut être garanti, à moins que le chemin ne soit connu pour être absolu). Si vous avez besoin d'un chemin natif qui doit être absolu, vous devriez demander la version native d'un chemin normalisé. Si, pour une raison quelconque, une version non absolue et non normalisée du chemin est nécessaire, celle-ci doit être construite séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache afin que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. La valeur de retour appartient à Tcl et a une durée de vie équivalente à celle du pathPtr passé en argument (sauf si il s'agit d'un chemin relatif, auquel cas la représentation native peut être libérée à tout moment où le cwd change).

Tcl_FSFileSystemInfo renvoie une liste de deux éléments. Le premier élément est le nom du système de fichiers (par exemple, "native", "vfs", "zip" ou "prowrap", peut-être), et le second est le type particulier du chemin donné dans ce système de fichiers (qui dépend du système de fichiers). Le second élément peut être vide si le système de fichiers ne fournit pas de catégorisation supplémentaire des fichiers.

Une valeur de liste valide est renvoyée, sauf si la valeur du chemin n'est pas reconnue, auquel cas NULL sera renvoyé.

Tcl_FSGetFileSystemForPath renvoie un pointeur vers le Tcl_Filesystem qui accepte ce chemin comme valide.

Si aucun système de fichiers n'accepte le chemin, NULL est renvoyé.

Tcl_FSGetPathType détermine si le chemin donné est relatif au répertoire courant, relatif au volume courant, ou absolu.

Il renvoie l'une des valeurs TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, ou TCL_PATH_VOLUME_RELATIVE

L'API DU SYSTÈME DE FICHIERS VIRTUEL

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions qui implémentent les différentes opérations sur un système de fichiers ; ces opérations sont invoquées au besoin par la couche générique, ce qui se produit généralement via les fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un morceau de données facultatif à associer à ce système de fichiers. En appelant cette fonction, Tcl attachera le système de fichiers à la liste des systèmes de fichiers connus, et il deviendra pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera renvoyé.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et renvoie TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est renvoyé.

Tcl_FSData renverra le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il renverra NULL.

Tcl_FSMountsChanged est utilisé pour informer le noyau de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche de système de fichiers générique pour effectuer la gamme complète d'actions liées au système de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (dont la plupart doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni) et fonctions d'efficacité (qui n'ont besoin d'être implémentées que si elles peuvent être effectuées efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces solutions de secours ne sont utilisées que pour gérer les commandes initiées dans Tcl, pas dans C. Cela signifie que si une commande file rename est émise dans Tcl, et que les systèmes de fichiers concernés n'implémentent pas leur Tcl_FSRenameFileProc, le noyau Tcl se rabattra plutôt sur une combinaison d'autres fonctions de système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a une autre solution de secours). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucune solution de secours de ce type ne se produit. Ceci est vrai sauf pour les quatre dernières entrées de la table des systèmes de fichiers (lstat, load, getcwd et chdir) pour lesquelles des solutions de secours se produisent en fait au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme Tcl_Obj prennent ces noms sous forme UTF-8. L'API d'infrastructure des systèmes de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

INFRASTRUCTURE DU SYSTÈME DE FICHIERS

Ces champs contiennent des informations de base sur la structure du système de fichiers et les adresses des fonctions utilisées pour associer un système de fichiers particulier à un chemin de fichier, et pour gérer la représentation interne des chemins, par exemple la copie et la libération de ces représentations.

TYPE NOM

Le champ typeName contient une chaîne de caractères terminée par un octet nul qui identifie le type du système de fichiers implémenté, par exemple “natif”, “zip” ou “vfs”.

LONGUEUR STRUCTURE

Le champ structureLength est généralement implémenté comme sizeof(Tcl_Filesystem), et est là pour permettre une compatibilité binaire ascendante plus facile si la taille de la structure change dans une future version de Tcl.

VERSION

Le champ version doit être défini à TCL_FILESYSTEM_VERSION_1.

PROCÉDURE PATHINFILESYSTEMPROC

Le champ pathInFilesystemProc contient l'adresse d'une fonction qui est appelée pour déterminer si une valeur de chemin donnée appartient à ce système de fichiers ou non. Tcl appellera le reste des fonctions du système de fichiers uniquement avec un chemin pour lequel cette fonction a retourné TCL_OK. Si le chemin n'appartient pas, -1 doit être retourné (le comportement de Tcl pour toute autre valeur de retour n'est pas défini). Si TCL_OK est retourné, alors le paramètre de sortie optionnel clientDataPtr peut être utilisé pour retourner une représentation interne (spécifique au système de fichiers) du chemin, qui sera mise en cache à l'intérieur de la valeur du chemin, et pourra être récupérée efficacement par les autres fonctions du système de fichiers. Tcl mettra simultanément en cache le fait que ce chemin appartient à ce système de fichiers. De tels caches sont invalidés lorsque des structures de systèmes de fichiers sont ajoutées ou retirées de la liste interne de Tcl des systèmes de fichiers connus.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROCÉDURE DUPINTERNALREPPROC

Cette fonction crée une copie de la représentation interne d'un chemin, et est appelée lorsque Tcl a besoin de dupliquer une valeur de chemin. Si elle est NULL, Tcl ne copiera tout simplement pas la représentation interne, qui peut alors devoir être régénérée plus tard.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

PROCÉDURE FREEINTERNALREPPROC

Libère la représentation interne. Ceci doit être implémenté si les représentations internes nécessitent une libération (c'est-à-dire si de la mémoire est allouée lorsqu'une représentation interne est générée), mais peut sinon être NULL.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

PROCÉDURE INTERNALTONORMALIZEDPROC

Fonction pour convertir une représentation interne en un chemin normalisé. Requise uniquement si le système de fichiers crée des valeurs de chemin pures sans représentation textuelle/de chemin. La valeur de retour est une valeur Tcl dont la représentation textuelle est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

PROCÉDURE CREATEINTERNALREPPROC

Fonction pour prendre une valeur de chemin, calculer une représentation interne pour celle-ci, et stocker cette représentation native dans la valeur. Peut être NULL si les chemins n'ont pas de représentation interne, ou si la procédure Tcl_FSPathInFilesystemProc pour ce système de fichiers crée toujours immédiatement une représentation interne pour les chemins qu'elle accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

PROCÉDURE NORMALIZEPATHPROC

Fonction pour normaliser un chemin. Devrait être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations textuelles pour la même valeur de chemin. Dans Tcl, chaque “chemin” doit avoir une seule représentation textuelle “normalisée” unique. Selon le système de fichiers, il peut y avoir plus d'une représentation textuelle non normalisée qui se réfère à ce chemin (par exemple, un chemin relatif, un chemin avec une casse de caractères différente si le système de fichiers ne fait pas la distinction de casse, un chemin contenant une référence à un répertoire personnel tel que “~”, un chemin contenant des liens symboliques, etc.). Si le tout dernier composant du chemin est un lien symbolique, il ne doit pas être converti en la valeur vers laquelle il pointe (mais sa casse ou d'autres aspects doivent être rendus uniques). Tous les autres composants du chemin doivent être convertis à partir des liens symboliques. Cette seule exception est requise pour être conforme aux sémantiques de Tcl avec file delete, file rename, file copy opérant sur des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint soit au début du chemin (c'est-à-dire zéro), soit à la fin du chemin, soit à n'importe quel séparateur de fichier intermédiaire dans le chemin. Elle ne pointera jamais vers une autre position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS DU SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions qui sont appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui doit être utilisé avec l'ensemble complet des commandes standard de Tcl doit implémenter toutes ces opérations. Si certaines ne sont pas implémentées, certaines commandes Tcl peuvent échouer lors de l'opération sur des chemins appartenant à ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques n'a pas besoin d'implémenter la fonction readlink, etc. Le noyau Tcl s'attend à ce que les systèmes de fichiers se comportent de cette manière).

PROCÉDURE FILESYSTEMPATHTYPEPROC

Fonction pour déterminer le type d'un chemin dans ce système de fichiers. Peut être NULL, auquel cas aucune information de type ne sera disponible pour les utilisateurs du système de fichiers. Le “type” est utilisé uniquement à des fins d'information, et doit être retourné comme représentation textuelle de l'objet Tcl retourné. Une valeur de retour typique pourrait être “réseau”, “zip” ou “ftp”. L'objet Tcl résultant est la propriété du système de fichiers et Tcl incrémentera le compteur de références de cette valeur s'il souhaite en conserver une référence.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

PROCÉDURE FILESYSTEMSEPARATORPROC

Fonction pour retourner le(s) caractère(s) séparateur(s) pour ce système de fichiers. Ceci n'a besoin d'être implémenté que si le système de fichiers souhaite utiliser un séparateur différent de la chaîne standard “/”. Entre autres utilisations, il est retourné par la commande file separator. La valeur de retour doit être une valeur avec un compteur de références de zéro.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

PROCÉDURE STATPROC

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes au niveau Tcl en dépendent crucialement (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La procédure Tcl_FSStatProc remplit la structure stat statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure stat inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification et l'heure du dernier changement de métadonnées.

Si le fichier représenté par pathPtr existe, la procédure Tcl_FSStatProc retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné, et aucune information de stat n'est donnée.

PROCÉDURE ACCESSPROC

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes au niveau Tcl en dépendent crucialement (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La procédure Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est dans pathPtr. Si le nom de chemin fait référence à un lien symbolique, alors les permissions du fichier auquel ce lien symbolique fait référence doivent être testées.

En cas de succès (toutes les permissions demandées accordées), zéro est retourné. En cas d'erreur (au moins un bit dans mode demandait une permission refusée, ou une autre erreur s'est produite), -1 est retourné.

PROCÉDURE OPENFILECHANNELPROC

OPENFILECHANNELPROC

Fonction pour traiter un appel Tcl_FSOpenFileChannel. Doit être implémentée pour tout système de fichiers raisonnable, car toutes les opérations qui nécessitent l'ouverture ou l'accès au contenu d'un fichier l'utiliseront (par exemple, open, encoding, et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

La Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et retourne un descripteur de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est calquée sur la procédure fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles fournies dans la commande Tcl open lors de l'ouverture d'un fichier, où l'argument mode est une combinaison des indicateurs POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, la Tcl_FSOpenFileChannelProc retourne NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, la Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le nouveau canal créé ne doit pas être enregistré dans l'interpréteur fourni par une Tcl_FSOpenFileChannelProc ; cette tâche incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr, était précédemment fermé, l'acte de création du nouveau canal l'assigne également comme remplacement du canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, la fonctionnalité de glob et de copie récursive manquera dans le système de fichiers (et cela peut impacter des commandes comme encoding names qui utilisent la fonctionnalité de glob en interne).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit retourner tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au modèle donné et qui respectent la spécification types donnée. Il existe deux manières dont cette fonction peut être appelée. Si pattern est NULL, alors pathPtr est une spécification de chemin complet d'un seul fichier ou répertoire qui doit être vérifié pour son existence et son type correct. Sinon, pathPtr est un répertoire, dont le contenu doit être recherché par la fonction pour trouver les fichiers ou répertoires qui ont le type correct. Dans les deux cas, on peut supposer que pathPtr n'est ni NULL ni vide. Il n'est actuellement pas documenté si pathPtr aura ou non un séparateur de fichier à la fin, donc le code doit être flexible pour les deux possibilités.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le processus de mise en correspondance. Les messages d'erreur sont placés dans interp, sauf si interp est NULL, auquel cas aucun message d'erreur ne doit être généré ; en cas de résultat TCL_OK, les résultats doivent être ajoutés à la valeur resultPtr donnée (qui peut être supposée être une liste Tcl valide non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (cela signifie généralement qu'il s'agira de spécifications de chemin absolu). Notez que si aucune correspondance n'est trouvée, cela conduit simplement à un résultat vide ; les erreurs ne sont signalées que pour les problèmes réels de fichiers ou de systèmes de fichiers qui peuvent survenir pendant le processus de mise en correspondance.

La structure Tcl_GlobTypeData passée dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Type Mac acceptable */
    Tcl_Obj *macType;
    /* Créateur Mac acceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de traiter correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT sont vrais (et en particulier lorsque les autres indicateurs sont faux). Dans le premier de ces cas, la fonction doit lister les répertoires contenus. Tcl utilise cela pour implémenter le globbing récursif, il est donc essentiel que les systèmes de fichiers implémentent correctement la correspondance des répertoires. Dans le second de ces cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage qui se trouvent dans le pathPtr donné (et dans ce cas, pathPtr n'a pas besoin de se trouver dans le même système de fichiers - différent de tous les autres cas où cette fonction est appelée). Le support pour cela est essentiel si Tcl veut avoir des transitions transparentes entre différents systèmes de fichiers.

UTIMEPROC

Fonction pour traiter un appel Tcl_FSUtime. Requise pour permettre la définition (pas la lecture) des temps avec file mtime, file atime et l'implémentation open-r/open-w/fcopy de file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les temps d'accès et de modification du fichier spécifié par pathPtr doivent être modifiés pour correspondre aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec utime du système.

LINKPROC

Fonction pour traiter un appel Tcl_FSLink. Ne devrait être implémentée que si le système de fichiers prend en charge les liens, et peut sinon être NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est invitée à lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat est la propriété de l'appelant (et doit donc voir son compteur de références incrémenté avant d'être retourné). Tous les appelants doivent appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'est plus nécessaire. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Le résultat dans ce cas doit être toPtr si le lien a réussi et NULL sinon. Dans ce cas, le résultat n'est pas la propriété de l'appelant (c'est-à-dire qu'aucune manipulation de compteur de références des deux côtés n'est nécessaire). Voir la documentation de Tcl_FSLink pour l'interprétation correcte des indicateurs linkAction.

LISTVOLUMESPROC

Fonction pour lister tous les volumes de système de fichiers ajoutés par ce système de fichiers. Ne devrait être implémentée que si le système de fichiers ajoute des volumes en tête du système de fichiers, afin qu'ils puissent être retournés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste des volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. La valeur du résultat est considérée comme appartenant au système de fichiers (et non au cœur de Tcl), mais un compteur de références doit lui être attribué pour Tcl. Tcl utilisera le contenu de la liste, puis décrémentera ce compteur de références. Cela permet aux systèmes de fichiers de choisir s'ils souhaitent réellement conserver une liste « globale » de volumes ou non (sinon, ils génèrent la liste à la volée et la transmettent à Tcl avec un compteur de références de 1, puis oublient la liste ; sinon, ils incrémentent simplement le compteur de références de leur liste globale et la transmettent à Tcl qui copiera le contenu, puis décrémentera le compteur pour le ramener à son état précédent).

Par conséquent, Tcl considère les valeurs de retour de cette procédure comme étant en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne prendra pas en charge la commande file attributes. Cela permet de joindre des informations supplémentaires arbitraires aux fichiers dans le système de fichiers. Si elle n'est pas implémentée, il n'est pas nécessaire d'implémenter les méthodes get et set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La fonction appelée peut soit retourner un tableau de chaînes, soit retourner NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer qu'il retourne une valeur avec un compteur de références d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel Tcl_FSFileAttrsGet, utilisé par file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Retourne un code de retour Tcl standard. La valeur d'attribut récupérée, qui correspond à l'élément d'indice index dans la liste retournée par la Tcl_FSFileAttrStringsProc, est un Tcl_Obj placé dans objPtrRef (si TCL_OK a été retourné) et aura probablement un compteur de références de zéro. Dans tous les cas, nous devons soit le stocker quelque part (par exemple, le résultat Tcl), soit incrémenter/décrémenter son compteur de références pour assurer sa libération correcte.

FILEATTRSSETPROC

Fonction pour traiter un appel Tcl_FSFileAttrsSet, utilisé par file attributes. Si le système de fichiers est en lecture seule, il n'est pas nécessaire de l'implémenter.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

La valeur d'attribut de l'élément d'indice index dans la liste retournée par la Tcl_FSFileAttrStringsProc doit être définie sur l'objPtr donné.

REMOVEDIRECTORYPROC

typedef int Tcl_FSRemoveDirectoryProc(

Ces fonctions n'ont pas besoin d'être implémentées pour un système de fichiers particulier car le noyau dispose d'une implémentation de secours disponible. Voir la description individuelle de chaque champ pour les conséquences de laisser le champ NULL.

LSTATPROC

Fonction pour traiter un appel à Tcl_FSLstat. Si elle n'est pas implémentée, Tcl tentera d'utiliser la procédure statProc définie ci-dessus à la place. Par conséquent, elle n'a besoin d'être implémentée que si un système de fichiers peut différencier les appels stat et lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le comportement de cette fonction est très similaire à celui de Tcl_FSStatProc défini ci-dessus, sauf que si elle est appliquée à un lien symbolique, elle renvoie des informations sur le lien, et non sur le fichier cible.

COPYFILEPROC

Fonction pour traiter un appel à Tcl_FSCopyFile. Si elle n'est pas implémentée, Tcl utilisera open-r, open-w et fcopy comme mécanisme de copie. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de copie. Notez que destPathPtr est le nom du fichier qui doit devenir la copie de srcPathPtr. Ce n'est jamais le nom d'un répertoire dans lequel srcPathPtr pourrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande Tcl de niveau file copy). Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non copyDirectoryProc lorsqu'il est nécessaire de les copier (même s'il s'agit de liens symboliques vers des répertoires). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file copy, appeler Tcl_SetErrno(EXDEV) et renvoyer un résultat non-TCL_OK indiquera à Tcl d'utiliser ses mécanismes de secours standard.

RENAMEFILEPROC

Fonction pour traiter un appel à Tcl_FSRenameFile. Si elle n'est pas implémentée, Tcl utilisera un mécanisme de copie et de suppression. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de renommage. Si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file rename, appeler Tcl_SetErrno(EXDEV) et renvoyer un résultat non-TCL_OK indiquera à Tcl d'utiliser ses mécanismes de secours standard.

COPYDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSCopyDirectory. Si elle n'est pas implémentée, Tcl utilisera un mécanisme récursif de file mkdir, file copy. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de copie. Si une erreur se produit, le nom du fichier ou du répertoire qui a causé l'erreur doit être placé dans errorPtr. Notez que destPathPtr est le nom du répertoire qui doit devenir l'image miroir de srcPathPtr. Ce n'est pas le nom d'un répertoire dans lequel srcPathPtr devrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande Tcl de niveau file copy). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de copie de répertoire, appeler Tcl_SetErrno(EXDEV) et renvoyer un résultat non-TCL_OK indiquera à Tcl d'utiliser ses mécanismes de secours standard.

LOADFILEPROC

Fonction pour traiter un appel à Tcl_FSLoadFile. Si elle n'est pas implémentée, Tcl utilisera une copie vers un fichier temporaire natif suivie d'un Tcl_FSLoadFile sur cette copie temporaire. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut charger du code directement, ou si elle peut être implémentée simplement pour renvoyer TCL_ERROR afin de désactiver complètement la fonctionnalité de chargement dans ce système de fichiers.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Renvoie un code de complétion Tcl standard. En cas d'erreur, un message d'erreur est laissé dans le résultat de interp. La fonction charge dynamiquement un fichier de code binaire en mémoire. En cas de chargement réussi, handlePtr doit être rempli avec un jeton pour le fichier chargé dynamiquement, et unloadProcPtr doit être rempli avec l'adresse d'une procédure. La procédure de déchargement sera appelée avec le Tcl_LoadHandle donné comme seul paramètre lorsque Tcl aura besoin de décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle renvoyé est actuellement un jeton qui peut être utilisé dans le TclpFindSymbol privé pour accéder aux fonctions du nouveau code. Chaque système de fichiers est libre de définir le Tcl_LoadHandle comme il l'exige. Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de chargement de fichier, appeler Tcl_SetErrno(EXDEV) et renvoyer un résultat non-TCL_OK indiquera à Tcl d'utiliser ses mécanismes de secours standard.

UNLOADFILEPROC

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Fonction pour traiter un appel à Tcl_FSGetCwd. La plupart des systèmes de fichiers n'ont pas besoin de l'implémenter. Elle ne sera généralement appelée qu'une seule fois, si getcwd est appelé avant chdir. Peut être NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si le système de fichiers prend en charge une notion native d'un répertoire de travail courant (qui pourrait peut-être changer indépendamment de Tcl), cette fonction devrait renvoyer ce répertoire courant comme résultat, ou NULL si le répertoire courant n'a pas pu être déterminé (par exemple, l'utilisateur n'a pas les permissions appropriées sur le répertoire courant). Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de interp.

CHDIRPROC

Fonction pour traiter un appel à Tcl_FSChdir. Si les systèmes de fichiers ne l'implémentent pas, elle sera émulée par une série de vérifications d'accès aux répertoires. Sinon, les systèmes de fichiers virtuels qui l'implémentent doivent seulement répondre avec un résultat positif si pathPtr est un répertoire valide et accessible dans leur système de fichiers. Ils n'ont pas besoin de mémoriser le résultat, car celui-ci sera automatiquement mémorisé pour être utilisé par Tcl_FSGetCwd. Les systèmes de fichiers réels doivent effectuer l'action correcte (c'est-à-dire appeler l'API système chdir appropriée).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

Le Tcl_FSChdirProc change le répertoire de travail courant de l'application à la valeur spécifiée dans pathPtr. La fonction renvoie -1 en cas d'erreur ou 0 en cas de succès.
