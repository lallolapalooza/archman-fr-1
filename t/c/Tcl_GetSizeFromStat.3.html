DESCRIPTION

Il existe plusieurs raisons d'appeler les fonctions de l'API Tcl_FS (par exemple, Tcl_FSAccess et Tcl_FSStat) plutôt que d'appeler directement des fonctions de niveau système comme access et stat. Premièrement, elles fonctionneront sur différentes plateformes, donc une extension qui les appelle devrait fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige certains bogues dans les appels de niveau système. Troisièmement, ces appels de fonction traitent les conversions de chemin « Utf vers natif de la plateforme » qui peuvent être nécessaires (et peuvent mettre en cache les résultats de telles conversions pour une plus grande efficacité lors d'appels ultérieurs). Quatrièmement, et peut-être le plus important, toutes ces fonctions sont « conscientes des systèmes de fichiers virtuels » (VFS pour faire court). Tout système de fichiers virtuel (VFS) qui a été enregistré (via Tcl_FSRegister) peut rediriger l'accès aux fichiers vers des supports ou des méthodes d'accès alternatifs. Cela signifie que toutes ces fonctions (et donc les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent opérer sur des « fichiers » qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS pour faire court) via cette API est automatiquement « consciente des systèmes de fichiers virtuels ». Bien entendu, si une extension accède directement au système de fichiers natif (via des API spécifiques à la plateforme, par exemple), Tcl ne peut pas intercepter de tels appels.

Si des VFS appropriés ont été enregistrés, les « fichiers » peuvent, pour donner deux exemples, être distants (par exemple, situés sur un serveur ftp distant) ou archivés (par exemple, se trouvant à l'intérieur d'une archive .zip). De tels systèmes de fichiers enregistrés fournissent une table de correspondance de fonctions pour implémenter tout ou partie de la fonctionnalité énumérée ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat abstraient la structure du tampon « struct stat », permettant d'utiliser le même code sur les systèmes qui supportent les fichiers de plus de 2 Go et ceux qui ne le supportent pas.

L'API Tcl_FS est basée sur Tcl_Obj et peut mettre en cache des représentations internes et d'autres chaînes relatives aux chemins (par exemple, le répertoire de travail courant). Un effet secondaire de ceci est qu'il ne faut pas passer de valeurs avec un nombre de références nul à l'une de ces fonctions. Si de tels appels étaient gérés, ils pourraient entraîner des fuites de mémoire (dans certaines circonstances, le code du système de fichiers peut souhaiter conserver une référence à la valeur transmise, et il ne faut donc pas supposer qu'après le retour de l'un de ces appels, la valeur a toujours un nombre de références nul - il peut avoir été incrémenté) ou un plantage de segmentation direct (ou une autre erreur d'accès mémoire) en raison de la libération de la valeur en cours de la manipulation complexe de valeurs requise pour garantir que le chemin est entièrement normalisé et absolu pour la détermination du système de fichiers. La leçon pratique à en tirer est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect et peut provoquer des erreurs de mémoire. Le nombre de références de path doit être incrémenté avant de le passer, ou décrémenté. Pour cette raison, les valeurs avec un nombre de références nul ne sont pas considérées comme des chemins de système de fichiers valides et l'appel de toute fonction de l'API Tcl_FS avec une telle valeur n'entraînera aucune action.

FONCTIONS DE L'API FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno sur le code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno sur le code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction « créer un répertoire » du système de fichiers propriétaire.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction « supprimer un fichier » du système de fichiers propriétaire.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction « supprimer un répertoire » du système de fichiers propriétaire.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « renommer un fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno sur le code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction « lister les volumes » non-NULL et leur demande de renvoyer leur liste de volumes racines. Elle accumule les valeurs de retour dans une liste qui est renvoyée à l'appelant (avec un nombre de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant le codage identifié par encodingName et évalue son contenu comme un script Tcl. Elle renvoie les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, le codage système est utilisé pour lire le contenu du fichier. Si le fichier n'a pas pu être lu, une erreur Tcl est renvoyée pour décrire pourquoi le fichier n'a pas pu être lu. Le caractère de fin de fichier (eofchar) pour les fichiers est « \x1A » (^Z) pour toutes les plateformes. Si vous avez besoin d'un « ^Z » dans une chaîne pour une comparaison, vous pouvez utiliser « \x1A », qui sera substitué en toute sécurité par l'interpréteur Tcl en « ^Z ». Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours le codage système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier de code binaire en mémoire et renvoie les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas, en raison des limitations du système d'exploitation en matière de chargement dynamique de code binaire), Tcl tentera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile inverse l'opération, demandant que la bibliothèque indiquée par loadHandle soit retirée du processus. Notez que, contrairement à la commande unload, cela ne donne aucune opportunité à la bibliothèque de se nettoyer.

Les deux fonctions ci-dessus renvoient un code d'achèvement Tcl standard. En cas d'erreur, un message d'erreur est laissé dans le résultat de l'interp.

Le jeton fourni via la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisée par le code de globbing pour rechercher dans un répertoire tous les fichiers qui correspondent à un modèle donné. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le globbing. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Notez que le code glob implémente les modèles récursifs en interne, donc cette fonction ne recevra que des modèles simples, qui peuvent être mis en correspondance en utilisant la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment en demandant uniquement le retour des répertoires. Un cas spécial où elle est appelée avec un modèle NULL indique que le chemin doit être vérifié uniquement pour le type correct.

Tcl_FSLink remplace la version bibliothèque de readlink, et l'étend pour supporter la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr sera appelée.

Si toPtr est NULL, une action « lire le lien » est effectuée. Le résultat est un Tcl_Obj spécifiant le contenu du lien symbolique donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant, qui devrait appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl doit créer un lien d'un des types passés dans l'indicateur linkAction. Cet indicateur est une combinaison OU de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'un choix existe (c'est-à-dire plus d'un indicateur est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur de retour doit être toPtr (qui appartient donc déjà à l'appelant). En cas d'échec, NULL est renvoyé.

Tcl_FSLstat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de parcours sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (nlink, toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID groupe (toujours 0 sous Windows), le périphérique rdev (identique au périphérique sous Windows), la taille, la dernière a

Conservez toute la structure du fichier. Accès au temps de création, au temps de dernière modification et au temps de dernière mise à jour des métadonnées. Voir PORTABLE STAT RESULT API pour une description de la manière d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf. Si path existe, Tcl_FSLstat renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé, et aucune donnée de stat n'est fournie. Tcl_FSUtime remplace la version de la bibliothèque de utime. Elle renvoie 0 en cas de succès et -1 en cas d'erreur (comme décrit dans la documentation utime). En cas de succès, la fonction mettra à jour les valeurs atime et mtime d'un fichier donné. Tcl_FSFileAttrsGet implémente l'accès en lecture pour la sous-commande file attributes de la commande hookable file. La fonction appropriée pour le système de fichiers auquel appartient pathPtr est appelée. Si le résultat est TCL_OK, une valeur a été placée dans objPtrRef, qui ne sera valable que temporairement (jusqu'à ce que Tcl_IncrRefCount soit appelé). Tcl_FSFileAttrsSet implémente l'accès en écriture pour la sous-commande file attributes de la commande hookable file. La fonction appropriée pour le système de fichiers auquel appartient pathPtr est appelée. Tcl_FSFileAttrStrings implémente une partie de la sous-commande file attributes de la commande hookable file. La fonction appropriée pour le système de fichiers auquel appartient pathPtr est appelée. La procédure appelée peut renvoyer un tableau de chaînes ou, à la place, renvoyer NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et augmentera d'abord son compteur de références avant de l'utiliser. Une fois son utilisation terminée, Tcl diminuera sa référence. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si elle ne doit pas être supprimée, le système de fichiers doit s'assurer de maintenir un compteur de références sur la valeur. Tcl_FSAccess vérifie si le processus serait autorisé à lire, écrire ou tester l'existence d'un fichier (ou d'un autre objet du système de fichiers) dont le nom est pathname. Si pathname est un lien symbolique sous Unix, la permission du fichier référencé par ce lien symbolique est testée. En cas de succès (toutes les permissions demandées), 0 est renvoyé. En cas d'erreur (au moins un des bits du mode demandé est refusé, ou une autre erreur s'est produite), -1 est renvoyé. Tcl_FSStat remplit la structure Tcl_StatBuf avec des informations sur le fichier spécifié. Aucun droit d'accès au fichier n'est requis pour obtenir ces informations, mais des droits de recherche sont requis dans tous les répertoires mentionnés dans le chemin du fichier. La structure Tcl_StatBuf inclut des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'UID (toujours 0 sous Windows), le GID (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le temps de dernier accès, le temps de modification et le temps de mise à jour des métadonnées. Voir PORTABLE STAT RESULT API pour une description de la manière d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf. Si path existe, Tcl_FSStat renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé, et aucune donnée de stat n'est fournie. Tcl_FSOpenFileChannel ouvre un fichier spécifié par pathPtr et renvoie un handle de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est calquée sur la procédure fopen de la bibliothèque d'entrée/sortie standard d'Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannel renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannel laisse un message d'erreur dans le résultat de interp après toute erreur. Le canal nouvellement créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez Tcl_RegisterChannel. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, l'action de création du nouveau canal l'assigne également en remplacement du canal standard. Tcl_FSGetCwd remplace la version de la fonction getcwd de la bibliothèque. Elle renvoie le répertoire de travail actuel de la bibliothèque Tcl. Cela peut différer du répertoire de travail natif, ce qui se produit lorsque le répertoire de travail actuel n'est pas dans le système de fichiers natif. Le résultat est un pointeur vers un Tcl_Obj spécifiant le répertoire actuel, ou NULL si le répertoire n'a pas pu être déterminé. Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de interp. Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, il faut décrémenter son compteur de références. Ceci est nécessaire pour la sécurité multi-thread, afin que plusieurs threads puissent accéder à cette fonction et à des fonctions connexes, tout en conservant toujours des résultats valides. Tcl_FSChdir remplace la version de la fonction chdir de la bibliothèque. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si le système de fichiers n'implémente pas cette fonction, Tcl se rabat sur une combinaison de stat et access pour vérifier si le répertoire existe et a les permissions appropriées. Pour les résultats, voir la documentation de chdir. En cas de succès, un enregistrement du chemin réussi est sauvegardé dans cwdPathPtr pour les appels ultérieurs à Tcl_FSGetCwd. Tcl_FSPathSeparator renvoie le caractère séparateur pour l'élément le plus spécifique du chemin spécifié par pathPtr (c'est-à-dire la dernière partie du chemin). Le séparateur est renvoyé sous forme de Tcl_Obj avec une chaîne de longueur 1. Si le chemin est invalide, NULL est renvoyé. Tcl_FSJoinPath prend le Tcl_Obj donné, qui doit être une liste valide (qui peut avoir un compteur de références de zéro), et renvoie la valeur de chemin en considérant les elements premiers éléments comme des segments de chemin valides (chaque segment peut être un chemin complet, un segment partiel ou simplement un nom de répertoire ou de fichier). Si un segment est effectivement un chemin absolu, tous les segments précédents sont ignorés. Si elements est inférieur à 0, nous utilisons toute la liste. Il est possible que la valeur renvoyée soit effectivement un élément de la liste donnée, donc l'appelant doit faire attention à incrémenter le compteur de références du résultat avant de libérer la liste. La valeur renvoyée, généralement avec un compteur de références de zéro (mais pouvant être partagée dans certaines conditions), contient le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. En particulier, la valeur renvoyée peut être un élément de la liste donnée, donc libérer la liste pourrait libérer prématurément la valeur si aucune référence n'a été prise. Si le nombre d'éléments est zéro, la valeur renvoyée sera un Tcl_Obj de chaîne vide. Tcl_FSSplitPath prend le Tcl_Obj donné, qui doit être un chemin valide, et renvoie une valeur de liste avec chaque segment du chemin comme élément. Elle renvoie une valeur de liste avec un compteur de références de zéro. Si lenPtr n'est pas NULL, la variable qui y pointe sera mise à jour avec le nombre d'éléments dans la valeur de liste renvoyée. Tcl_FSEqualPaths teste si les deux chemins donnés représentent le même objet du système de fichiers. Elle renvoie 1 s'ils sont égaux, 0 s'ils sont différents. Si l'un des chemins est NULL, 0 est toujours renvoyé. Tcl_FSGetNormalizedPath tente d'extraire une représentation normalisée unique du chemin donné, dont la valeur de chaîne peut être utilisée comme identifiant unique du fichier. Renvoie le chemin normalisé, appartenant à Tcl, ou NULL si le chemin était invalide ou n'a pas pu être converti. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère sur ces représentations en interne), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques ne sera pas la version la plus conviviale d'un chemin. La valeur renvoyée appartient à Tcl et a une durée de vie équivalente à celle de pathPtr (sauf s'il s'agit d'un chemin relatif, auquel cas la valeur normalisée peut être libérée dès que le cwd change) - l'appelant peut incrémenter le compteur de références s'il le souhaite pour conserver une copie plus longue. Tcl_FSJoinToPath prend la valeur donnée, qui devrait généralement être un chemin valide ou NULL, et la joint au tableau de segments de chemins donnés. Renvoie une valeur, généralement avec un compteur de références de zéro (mais pouvant être partagée dans certaines conditions), avec le chemin joint. L'appelant doit incrémenter le compteur de références avant de l'utiliser. Si l'une des valeurs passées à cette fonction (pathPtr ou les éléments de path) a un compteur de références de zéro, elle sera libérée une fois cette fonction terminée. Tcl_FSConvertToPathType tente de convertir le Tcl_Obj donné en un type de chemin valide, en tenant compte du fait que le cwd peut avoir changé même si cette valeur est déjà du bon type. Le nom de fichier peut commencer par ~ (pour indiquer le répertoire utilisateur actuel) ou ~ (pour indiquer le répertoire de n'importe quel utilisateur). Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), TCL_OK est renvoyé. Sinon, TCL_ERROR est renvoyé, et un message d'erreur peut être laissé dans l'interpréteur. Tcl_FSGetInternalRep extrait la représentation interne d'une valeur de chemin donnée dans le système de fichiers donné. Si la valeur de chemin appartient à un système de fichiers différent, NULL est renvoyé. Si la représentation interne est actuellement NULL, on tente de la générer en appelant Tcl_FSCreateInternalRepProc du système de fichiers. Renvoie NULL ou une représentation valide du chemin interne. Cette représentation interne est mise en cache, de sorte que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. Tcl_FSGetTranslatedPath tente d'extraire le chemin traduit du Tcl_Obj donné. Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), la valeur est renvoyée. Sinon, NULL est renvoyé, et un message d'erreur peut être laissé dans l'interpréteur. Un chemin traduit est celui qui ne contient aucun ~ ou ~utilisateur (ceux-ci ont été développés dans leur représentation actuelle dans le système de fichiers). La valeur renvoyée appartient à l'appelant, qui doit stocker la valeur ou appeler Tcl_DecrRefCount pour s'assurer que la mémoire est libérée. Cette fonction est d'une utilité pratique limitée, et Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement des fonctions plus appropriées pour la plupart des utilisations. Tcl_FSGetTranslatedStringPath fait la même chose que Tcl_FSGetTranslatedPath, mais renvoie une chaîne ou NULL. La chaîne renvoyée est allouée dynamiquement.

API DES SYSTÈMES DE FICHIERS VIRTUELS

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un système de fichiers; ces opérations sont invoquées au besoin par la couche générique, ce qui se produit généralement via les fonctions énumérées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un morceau de données optionnel à associer à ce système de fichiers. En appelant cette fonction, Tcl attachera le système de fichiers à la liste des systèmes de fichiers connus, et il deviendra pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera renvoyé.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et renvoie TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est renvoyé.

Tcl_FSData renverra le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il renverra NULL.

Tcl_FSMountsChanged est utilisé pour informer le cœur de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche générique du système de fichiers pour effectuer la gamme complète d'actions liées au système de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories: fonctions d'infrastructure (dont la plupart doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni) et fonctions d'efficacité (qui n'ont besoin d'être implémentées que si elles peuvent être réalisées efficacement, ou si elles ont des effets secondaires requis par le système de fichiers; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces remplacements ne sont utilisés que pour gérer les commandes initiées dans Tcl, pas dans C. Cela signifie que si une commande file rename est émise dans Tcl, et que le(s) système(s) de fichiers pertinent(s) n'implémente(nt) pas leur Tcl_FSRenameFileProc, le cœur de Tcl se rabattra sur une combinaison d'autres fonctions du système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a un autre mécanisme de secours). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun de ces mécanismes de secours ne se produit. Ceci est vrai sauf pour les quatre dernières entrées du tableau du système de fichiers (lstat, load, getcwd et chdir) pour lesquelles des mécanismes de secours se produisent en fait au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme de Tcl_Obj les prennent sous forme UTF-8. L'API d'infrastructure du système de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

NORMALIZEPATHPROC

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations de chaînes pour le même chemin. Dans Tcl, chaque path doit avoir une représentation unique normalisée de chaîne. Selon le système de fichiers, il peut y avoir plus d'une représentation non normalisée qui fait référence au même chemin (par exemple, un chemin relatif, un chemin avec une casse différente si le système de fichiers ne respecte pas la casse, un chemin contenant une référence à un répertoire personnel comme ~, un chemin contenant des liens symboliques, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être transformé en la valeur vers laquelle il pointe (mais sa casse ou d'autres aspects doivent être uniques). Tous les autres composants du chemin doivent être transformés à partir des liens symboliques. Cette exception est nécessaire pour correspondre à la sémantique de Tcl pour les opérations file delete, file rename, file copy avec des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint au début du chemin (c'est-à-dire zéro), à la fin du chemin, ou à n'importe quel séparateur de fichier intermédiaire dans le chemin. Elle ne sera jamais dirigée vers une position arbitraire autre dans le chemin. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS DU SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent des adresses de fonctions qui sont utilisées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui est censé être utilisé avec l'ensemble complet des commandes Tcl doit implémenter toutes ces fonctions. Si certaines d'entre elles ne sont pas implémentées, certaines commandes Tcl peuvent échouer lors de l'opération sur des chemins appartenant à ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques ne devrait pas implémenter la fonction readlink, etc. Le noyau de Tcl s'attend à ce que les systèmes de fichiers se comportent de cette manière).

Le type est utilisé uniquement à des fins informatives et doit être retourné comme la représentation chaîne de l'objet Tcl Tcl_Obj retourné. Une valeur typique pourrait être networked, zip ou ftp. Le résultat de la fonction Tcl_FSFilesystemPathTypeProc appartient au système de fichiers et Tcl incrémentera donc le compteur de références de la valeur si elle le souhaite.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

Fonction pour retourner le caractère séparateur de ce système de fichiers. Cette fonction ne doit être implémentée que si le système de fichiers souhaite utiliser un séparateur différent de la chaîne standard /. Entre autres utilisations, elle est retournée par la commande file separator. La valeur retournée doit avoir un compteur de références égal à zéro.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

STATPROC

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent de manière cruciale (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La fonction Tcl_FSStatProc remplit la structure statPtr avec des informations sur le fichier spécifié. Aucun accès à ce fichier n'est nécessaire pour obtenir ces informations, mais le droit de recherche sur tous les répertoires mentionnés dans le chemin menant au fichier est nécessaire. La structure de stat comprend des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode des privilèges, le nombre de liens (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), le rdev (identique au périphérique sous Windows), la taille, la dernière date d'accès, la dernière date de modification et la dernière date de modification des métadonnées.

Si le fichier représenté par pathPtr existe, le Tcl_FSStatProc retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné et aucune information de stat n'est fournie.

ACCESSPROC

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent de manière cruciale (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La fonction Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est dans pathPtr. Si le nom de chemin fait référence à un lien symbolique, les permissions du fichier auquel ce lien symbolique fait référence doivent être testées.

En cas de succès (toutes les permissions demandées ont été accordées), 0 est retourné. En cas d'erreur (au moins un bit dans mode demandait une permission qui n'a pas pu être accordée, ou une autre erreur s'est produite), -1 est retourné.

OPENFILECHANNELPROC

Fonction pour traiter un appel Tcl_FSOpenFileChannel. Doit être implémentée pour tout système de fichiers raisonnable, car toutes les opérations qui nécessitent l'ouverture ou l'accès au contenu d'un fichier l'utiliseront (par exemple, open, encoding et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

Le Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et retourne un descripteur de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est calquée sur la procédure fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier, où l'argument mode est une combinaison des indicateurs POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, le Tcl_FSOpenFileChannelProc retourne NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, le Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le nouveau canal créé ne doit pas être enregistré dans l'interpréteur fourni par un Tcl_FSOpenFileChannelProc ; cette tâche incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, la création du nouveau canal l'attribue également comme remplacement du canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, les fonctionnalités de glob et de copie récursive manqueront dans le système de fichiers (et cela pourrait affecter des commandes comme encoding names qui utilisent la fonctionnalité de glob en interne).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit retourner tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au modèle donné et qui sont conformes à la spécification types donnée. Il existe deux façons dont cette fonction peut être appelée. Si pattern est NULL, alors pathPtr est une spécification de chemin complet d'un seul fichier ou répertoire qui doit être vérifié pour son existence et son type correct. Sinon, pathPtr est un répertoire, dont le contenu la fonction doit rechercher des fichiers ou des répertoires du type correct. Dans les deux cas, on peut supposer que pathPtr n'est ni NULL ni vide. Il n'est pas documenté actuellement si pathPtr aura ou non un séparateur de fichier à sa fin, le code doit donc être flexible aux deux possibilités.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du processus de correspondance. Les messages d'erreur sont placés dans interp, sauf si interp est NULL, auquel cas aucun message d'erreur ne doit être généré ; sur un résultat TCL_OK, les résultats doivent être ajoutés à la valeur de resultPtr donnée (qui peut être supposée être une liste Tcl valide non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (cela signifie généralement qu'il s'agira de spécifications de chemin absolu). Notez que si aucune correspondance n'est trouvée, cela conduit simplement à un résultat vide ; les erreurs ne sont signalées que pour les problèmes réels de fichiers ou de systèmes de fichiers qui peuvent survenir pendant le processus de correspondance.

La structure Tcl_GlobTypeData passée dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichiers */
    int perm;
    /* Type mac acceptable */
    Tcl_Obj *macType;
    /* Créateur mac acceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de gérer correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT sont vrais (et en particulier lorsque les autres indicateurs sont faux). Dans le premier de ces cas, la fonction doit lister les répertoires contenus. Tcl utilise cela pour implémenter le glob récursif, il est donc essentiel que les systèmes de fichiers implémentent correctement la correspondance des répertoires. Dans le second de ces cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage qui se trouvent dans pathPtr donné (et dans ce cas, pathPtr n'a pas besoin de se trouver dans le même système de fichiers - différent de tous les autres cas dans lesquels cette fonction est appelée). Le support pour cela est essentiel si Tcl veut avoir des transitions transparentes entre un système de fichiers et un autre.

UTIMEPROC

Fonction pour traiter un appel Tcl_FSUtime. Nécessaire pour permettre la définition (pas la lecture) des heures avec file mtime, file atime et l'implémentation open-r/open-w/fcopy de file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les heures d'accès et de modification du fichier spécifié par pathPtr doivent être modifiées pour correspondre aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec la fonction système utime.

LINKPROC

Fonction pour traiter un appel Tcl_FSLink. Doit être implémentée uniquement si le système de fichiers prend en charge les liens, et peut sinon être NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est invitée à lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant (et son compteur de références doit donc être incrémenté avant d'être retourné). Tous les appelants doivent appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'est plus nécessaire. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Le résultat dans ce cas doit être toPtr si le lien a réussi et NULL sinon. Dans ce cas, le résultat n'appartient pas à l'appelant (c'est-à-dire qu'aucune manipulation du compteur de références des deux côtés n'est nécessaire). Voir la documentation de Tcl_FSLink pour l'interprétation correcte des indicateurs linkAction.

LISTVOLUMESPROC

Fonction pour lister les volumes de système de fichiers ajoutés par ce système de fichiers. Doit être implémentée uniquement si le système de fichiers ajoute des volumes en tête du système de fichiers, afin qu'ils puissent être retournés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste de volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. La valeur de résultat est considérée comme appartenant au système de fichiers (et non au cœur de Tcl), mais doit se voir attribuer un compteur de références pour Tcl. Tcl utilisera le contenu de la liste, puis décrémentera ce compteur de références. Cela permet aux systèmes de fichiers de choisir s'ils souhaitent réellement conserver une liste "globale" de volumes ou non (si ce n'est pas le cas, ils génèrent la liste à la volée et la transmettent à Tcl avec un compteur de références de 1, puis oublient la liste ; si oui, ils incrémentent simplement le compteur de références de leur liste globale et la transmettent à Tcl qui en copiera le contenu, puis décrémentera le compteur pour le ramener à sa valeur initiale).

Par conséquent, Tcl considère les valeurs de retour de cette procédure comme étant en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne prendra pas en charge la commande file attributes. Cela permet d'attacher des informations supplémentaires arbitraires aux fichiers du système de fichiers. Si elle n'est pas implémentée, il n'est pas nécessaire d'implémenter les méthodes get et set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La fonction appelée peut soit retourner un tableau de chaînes, soit retourner NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer qu'il retourne une valeur avec un compteur de références d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel Tcl_FSFileAttrsGet, utilisé par file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Retourne un code de retour Tcl standard. La valeur d'attribut récupérée, qui correspond à l'élément d'indice index dans la liste retournée par Tcl_FSFileAttrStringsProc, est un Tcl_Obj placé dans objPtrRef (si TCL_OK a été retourné) et aura probablement un compteur de références de zéro. Dans tous les cas, nous devons soit le stocker quelque part (par exemple, le résultat Tcl), soit incrémenter/décrémenter son compteur de références pour s'assurer qu'il est correctement libéré.

FILEATTRSSETPROC

Fonction pour traiter un appel Tcl_FSFileAttrsSet, utilisé par file attributes. Si le système de fichiers est en lecture seule, il n'est pas nécessaire de l'implémenter.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

La valeur d'attribut de l'élément d'indice index dans la liste retournée par le Tcl_FSFileAttrStringsProc doit être définie sur objPtr donné.

TCL_FILESYSTEM PROCEDURES

The Tcl file system interface provides a framework for extending Tcl to handle filesystems other than the native one. The core Tcl interpreter handles the actual interpretation of file-related commands (like open, read, write, file, etc.). When a command that accesses the filesystem is invoked, Tcl determines which filesystem the path belongs to and then calls the appropriate procedure in that filesystem's implementation.

A filesystem is described by a Tcl_FS structure. This structure contains pointers to procedures that implement the various filesystem operations. The following are the procedures that can be part of a filesystem implementation:

OPENPROC

Function to process a Tcl_FSOpenFileChannel call. Must be implemented for any filesystem that wishes to support opening files.

typedef Tcl_Channel Tcl_FSOpenProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_Obj *options);

The function should attempt to open the file specified by pathPtr with the given options. The options are a list of key-value pairs, e.g. {read w binary}. On success, it returns a Tcl channel handle; otherwise, it returns NULL and leaves an error message in the interpreter's result.

CLOSEPROC

Function to process a Tcl_FSClose call. Must be implemented if openProc is implemented.

typedef int Tcl_FSCloseProc(
        Tcl_Channel chan);

Should close the channel chan. Returns 0 on success, -1 on error.

READPROC

Function to process a Tcl_FSRead call. Must be implemented if files are to be read.

typedef int Tcl_FSReadProc(
        Tcl_Channel chan,
        char *buf,
        int toRead,
        Tcl_Obj **errorPtr);

Reads up to toRead bytes from channel chan into buffer buf. Returns the number of bytes actually read, or -1 on error. If an error occurs, the name of the file or directory which caused the error should be placed in errorPtr.

WRITEPROC

Function to process a Tcl_FSWrite call. Must be implemented if files are to be written.

typedef int Tcl_FSWriteProc(
        Tcl_Channel chan,
        char *buf,
        int toWrite,
        Tcl_Obj **errorPtr);

Writes up to toWrite bytes from buffer buf to channel chan. Returns the number of bytes actually written, or -1 on error. If an error occurs, the name of the file or directory which caused the error should be placed in errorPtr.

GETCHANNAMEPROC

Function to process a Tcl_FSGetChannelName call. Should be implemented for all filesystems that implement openProc.

typedef Tcl_Obj *Tcl_FSGetChannelNameProc(
        Tcl_Channel chan);

Returns the name of the channel. This is usually the original pathname used to open the channel.

GETCHANOPTIONSPROC

Function to process a Tcl_FSGetChannelOptions call. May be NULL.

typedef Tcl_Obj *Tcl_FSGetChannelOptionsProc(
        Tcl_Channel chan);

Returns a list of options that were used to open the channel.

SEEKPROC

Function to process a Tcl_FSSeek call. May be NULL.

typedef Tcl_WideInt Tcl_FSSeekProc(
        Tcl_Channel chan,
        Tcl_WideInt offset,
        int seekMode);

Reposition the internal read/write position of channel chan. Returns the resulting offset from the beginning of the file, or -1 on error.

EOFPROC

Function to process a Tcl_FSEof call. May be NULL.

typedef int Tcl_FSEofProc(
        Tcl_Channel chan);

Returns true if the next read from channel chan will return end-of-file.

IOERRORPROC

Function to process a Tcl_FSLastError call. May be NULL.

typedef Tcl_Obj *Tcl_FSIoErrorProc(
        Tcl_Channel chan);

Returns the last error that occurred on channel chan.

STATPROC

Function to process a Tcl_FSStat call. Must be implemented for any filesystem that is not read-only.

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Fills the buffer statPtr with information about the file at pathPtr. Returns 0 on success, -1 on error.

CREATEDIRECTORYPROC

Function to process a Tcl_FSCreateDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, a new directory should have been added to the filesystem in the location specified by pathPtr.

REMOVEDIRECTORYPROC

Function to process a Tcl_FSRemoveDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the directory specified by pathPtr should have been removed from the filesystem. If the recursive flag is given, then a non-empty directory should be deleted without error. If this flag is not given, then and the directory is non-empty a POSIX “EEXIST” error should be signaled. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr.

DELETEFILEPROC

Function to process a Tcl_FSDeleteFile call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the file specified by pathPtr should have been removed from the filesystem. Note that, if the filesystem supports symbolic links, Tcl will always call this function and not Tcl_FSRemoveDirectoryProc when needed to delete them (even if they are symbolic links to directories).

FILESYSTEM EFFICIENCY

These functions need not be implemented for a particular filesystem because the core has a fallback implementation available. See each individual description for the consequences of leaving the field NULL.

LSTATPROC

Function to process a Tcl_FSLstat call. If not implemented, Tcl will attempt to use the statProc defined above instead. Therefore it need only be implemented if a filesystem can differentiate between stat and lstat calls.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

The behavior of this function is very similar to that of the Tcl_FSStatProc defined above, except that if it is applied to a symbolic link, it returns information about the link, not about the target file.

COPYFILEPROC

Function to process a Tcl_FSCopyFile call. If not implemented Tcl will fall back on open-r, open-w and fcopy as a copying mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. Note that, destPathPtr is the name of the file which should become the copy of srcPathPtr. It is never the name of a directory into which srcPathPtr could be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Note that, if the filesystem supports symbolic links, Tcl will always call this function and not copyDirectoryProc when needed to copy them (even if they are symbolic links to directories). Finally, if the filesystem determines it cannot support the file copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

RENAMEFILEPROC

Function to process a Tcl_FSRenameFile call. If not implemented, Tcl will fall back on a copy and delete mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the renaming process. If the filesystem determines it cannot support the file rename action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

COPYDIRECTORYPROC

Function to process a Tcl_FSCopyDirectory call. If not implemented, Tcl will fall back on a recursive file mkdir, file copy mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr. Note that, destPathPtr is the name of the directory-name which should become the mirror-image of srcPathPtr. It is not the name of a directory into which srcPathPtr should be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Finally, if the filesystem determines it cannot support the directory copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

LOADFILEPROC

Function to process a Tcl_FSLoadFile call. If not implemented, Tcl will fall back on a copy to native-temp followed by a Tcl_FSLoadFile on that temporary copy. Therefore it need only be implemented if the filesystem can load code directly, or it can be implemented simply to return TCL_ERROR to disable load functionality in this filesystem entirely.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Returns a standard Tcl completion code. If an error occurs, an error message is left in the interp's result. The function dynamically loads a binary code file into memory. On a successful load, the handlePtr should be filled with a token for the dynamically loaded file, and the unloadProcPtr should be filled in with the address of a procedure. The unload procedure will be called with the given Tcl_LoadHandle as its only parameter when Tcl needs to unload the file. For example, for the native filesystem, the Tcl_LoadHandle returned is currently a token which can be used in the private TclpFindSymbol to access functions in the new code. Each filesystem is free to define the Tcl_LoadHandle as it requires. Finally, if the filesystem determines it cannot support the file load action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

UNLOADFILEPROC

Function to unload a previously successfully loaded file. If load was implemented, then this should also be implemented, if there is any cleanup action required.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Function to process a Tcl_FSGetCwd call. Most filesystems need not implement this. It will usually only be called once, if getcwd is called before chdir. May be NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

If the filesystem supports a native notion of a current working directory (which might perhaps change independent of Tcl), this function should return that cwd as the result, or NULL if the current directory could not be determined (e.g. the user does not have appropriate permissions on the cwd directory). If NULL is returned, an error message is left in the interp's result.

CHDIRPROC

Function to process a Tcl_FSChdir call. If filesystems do not implement this, it will be emulated by a series of directory access checks. Otherwise, virtual filesystems which do implement it need only respond with a positive return result if the pathPtr is a valid, accessible directory in their filesystem. They need not remember the result, since that will be automatically remembered for use by Tcl_FSGetCwd. Real filesystems should carry out the correct action (i.e. call the correct system chdir API).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

The Tcl_FSChdirProc changes the applications current working directory to the value specified in pathPtr. The function returns -1 on error or 0 on success.
