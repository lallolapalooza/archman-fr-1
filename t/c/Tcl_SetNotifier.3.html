ARGUMENTS

Procédure à appeler pour préparer l'attente d'événements dans Tcl_DoOneEvent.
Tcl_EventCheckProc *checkProc (in)
Procédure pour Tcl_DoOneEvent à appeler après avoir attendu des événements. Elle vérifie si des événements sont présents et, le cas échéant, les met dans la file d'attente.

Valeur arbitraire d'un mot unique transmise à setupProc, checkProc ou deleteProc.
const Tcl_Time *timePtr (in)
Indique le temps maximal d'attente d'un événement. Il est spécifié comme un intervalle (combien de temps attendre), et non comme un temps absolu (quand se réveiller). Si le pointeur passé à Tcl_WaitForEvent est NULL, cela signifie qu'il n'y a pas de limite d'attente : il attend indéfiniment si nécessaire.
Tcl_Event *evPtr (in)
Un événement à ajouter à la file d'attente des événements. Le stockage de l'événement doit avoir été alloué par l'utilisateur avec Tcl_Alloc ou ckalloc.
Tcl_QueuePosition position (in)
Où le nouvel événement est ajouté dans la file d'attente : TCL_QUEUE_TAIL, TCL_QUEUE_HEAD ou TCL_QUEUE_MARK.
Tcl_ThreadId threadId (in)
Identifiant unique d'un thread.
Tcl_EventDeleteProc *deleteProc (in)
Procédure à appeler pour chaque événement conservé dans Tcl_DeleteEvents.

Indique si les événements doivent être traités par Tcl_ServiceAll. Doit être l'une des valeurs TCL_SERVICE_NONE ou TCL_SERVICE_ALL.

structure de pointeurs de procédures de notification à remplacer. Voir REPLACING THE NOTIFIER pour les détails.

INTRODUCTION

Les interfaces décrites ici sont utilisées pour personnaliser la boucle d'événements de Tcl. Les deux configurations les plus courantes sont l'ajout de nouvelles sources d'événements et la fusion de la boucle d'événements de Tcl avec une autre boucle d'événements, telle que celle fournie par une application dans laquelle Tcl est intégrée. Chaque tâche est décrite dans une section distincte.

Les procédures de cette page de manuel sont les blocs de construction du notificateur Tcl. Le notificateur est la couche la plus basse du mécanisme d'événements de Tcl. Il se compose de trois éléments :

[1]
Sources d'événements : représentent les moyens par lesquels les événements peuvent être générés. Par exemple, il existe une source d'événements de type temporisateur qui implémente la procédure Tcl_CreateTimerHandler et la commande after, et une source d'événements de type fichier qui implémente la procédure Tcl_CreateFileHandler sur les systèmes Unix. Une source d'événements doit travailler avec le notificateur pour détecter les événements au bon moment, les enregistrer dans la file d'attente des événements et, éventuellement, informer le logiciel de niveau supérieur qu'ils se sont produits. Les procédures Tcl_CreateEventSource, Tcl_DeleteEventSource et Tcl_SetMaxBlockTime, Tcl_QueueEvent et Tcl_DeleteEvents sont principalement utilisées par les sources d'événements.
[2]
File d'attente d'événements : pour les applications non multithreadées, il existe une seule file d'attente pour l'application qui contient les événements détectés mais pas encore traités. Les sources d'événements placent les événements dans la file d'attente afin qu'ils puissent être traités dans l'ordre lors de la boucle d'événements appropriée. La file d'attente d'événements garantit une gestion équitable des événements, de sorte qu'aucune source d'événements ne peut suralimenter les autres. Elle permet également de sauvegarder des événements pour les traiter ultérieurement. Les applications multithreadées fonctionnent de manière similaire, sauf qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. Tcl_QueueEvent est utilisé (principalement par les sources d'événements) pour ajouter des événements à la file d'attente des événements, et Tcl_DeleteEvents est utilisé pour supprimer des événements de la file d'attente sans les traiter. Dans une application multithreadée, Tcl_QueueEvent ajoute un événement à la file d'attente du thread actuel, et Tcl_ThreadQueueEvent ajoute un événement à une file d'attente dans un thread spécifique.
[3]
Boucle d'événements : pour détecter et traiter les événements, l'application entre dans une boucle qui attend que les événements se produisent, les met dans la file d'attente, puis les traite. La plupart des applications le feront en appelant la procédure Tcl_DoOneEvent, décrite dans une entrée de manuel séparée.

La plupart des applications Tcl n'ont pas à se soucier des détails internes du notificateur Tcl. Cependant, le notificateur est maintenant suffisamment flexible pour être porté sur une nouvelle plateforme ou pour utiliser une boucle d'événements externe (comme la boucle d'événements Motif lorsque Tcl s'exécute dans une application Motif). Les procédures Tcl_WaitForEvent et Tcl_SetTimer sont normalement implémentées par Tcl, mais peuvent être remplacées par de nouvelles versions pour porter le notificateur (Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler et Tcl_DeleteFileHandler doivent également être remplacées ; voir CREATING A NEW NOTIFIER pour plus de détails). Les procédures Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode et Tcl_SetServiceMode sont fournies pour aider à connecter la boucle d'événements Tcl à une boucle d'événements externe telle que celle de Motif.

BASES DU NOTIFICATEUR

La manière la plus simple de comprendre le fonctionnement du notificateur est de considérer ce qui se passe lorsqu'on appelle Tcl_DoOneEvent. Tcl_DoOneEvent reçoit un argument flags qui indique quel type d'événements peut être traité et s'il faut se bloquer si aucun événement n'est prêt. Tcl_DoOneEvent effectue les opérations suivantes :

[1]
Elle vérifie la file d'attente des événements pour voir s'il y a des événements à traiter. S'il y en a, le premier événement possible est traité, retiré de la file d'attente et retourné. Elle le fait en appelant Tcl_ServiceEvent et en passant l'argument flags.
[2]
Elle se prépare à se bloquer en attendant un événement. Pour ce faire, Tcl_DoOneEvent appelle une procédure setup sur chaque source d'événements. La source d'événements effectuera l'initialisation spécifique à la source d'événements et pourra éventuellement appeler Tcl_SetMaxBlockTime pour limiter le temps pendant lequel Tcl_WaitForEvent sera bloquée si aucun nouvel événement ne se produit.
[3]
Elle appelle Tcl_WaitForEvent. Cette procédure est implémentée différemment selon les plateformes ; elle attend un événement en fonction des informations fournies par les sources d'événements. Elle peut entraîner le blocage de l'application si timePtr spécifie un intervalle différent de 0. Tcl_WaitForEvent retourne lorsqu'un événement s'est produit, tel qu'un fichier est devenu lisible ou que l'intervalle spécifié par timePtr a expiré. S'il n'y a aucun événement pour que Tcl_WaitForEvent attende, et qu'elle serait donc bloquée éternellement, elle retourne immédiatement et Tcl_DoOneEvent retourne 0.
[4]
Elle appelle une procédure check sur chaque source d'événements. La procédure check détermine si un événement intéressant pour cette source s'est produit. Si c'est le cas, les événements sont ajoutés à la file d'attente des événements.
[5]
Elle vérifie l'état de la file d'attente des événements.
vent pour voir s'il contient des événements pouvant être traités. Si c'est le cas, traiter le premier événement possible, le supprimer de la file d'attente et revenir.
[6]
Vérifier s'il existe des rappels inactifs en attente. Si c'est le cas, les invoquer tous et revenir.
[7]
Retourner 0 pour indiquer qu'aucun événement n'était prêt, ou revenir à l'étape [2] si un blocage a été demandé par l'appelant.

CRÉATION D'UNE NOUVELLE SOURCE D'ÉVÉNEMENTS

Une source d'événements se compose de trois procédures invoquées par le notificateur, plus des procédures C supplémentaires qui sont invoquées par le code de niveau supérieur pour organiser les rappels pilotés par événements. Les trois procédures appelées par le notificateur comprennent les procédures de configuration et de vérification décrites ci-dessus, plus une procédure supplémentaire qui est invoquée lorsqu'un événement est retiré de la file d'attente d'événements pour traitement.

La procédure Tcl_CreateEventSource crée une nouvelle source d'événements. Ses arguments spécifient la procédure de configuration et la procédure de vérification pour la source d'événements. SetupProc doit correspondre au prototype suivant :

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

L'argument clientData sera le même que l'argument clientData passé à Tcl_CreateEventSource ; il est généralement utilisé pour pointer vers des informations privées gérées par la source d'événements. L'argument flags sera le même que l'argument flags passé à Tcl_DoOneEvent sauf qu'il ne sera jamais 0 (Tcl_DoOneEvent remplace 0 par TCL_ALL_EVENTS). Flags indique quels types d'événements doivent être pris en compte ; si le bit correspondant à cette source d'événements n'est pas défini, la source d'événements doit revenir immédiatement sans rien faire. Par exemple, la source d'événements de fichier vérifie le bit TCL_FILE_EVENTS.

Le travail de SetupProc est de s'assurer que l'application se réveille lorsque des événements du type désiré se produisent. Ceci est généralement fait d'une manière dépendante de la plateforme. Par exemple, sous Unix, une source d'événements peut appeler Tcl_CreateFileHandler ; sous Windows, elle peut demander une notification avec un événement Windows. Pour les sources d'événements pilotées par minuteur, telles que les événements de minuteur ou tout événement interrogé, la source d'événements peut appeler Tcl_SetMaxBlockTime pour forcer l'application à se réveiller après un délai spécifié, même si aucun événement ne s'est produit. Si aucune source d'événements n'appelle Tcl_SetMaxBlockTime, alors Tcl_WaitForEvent attendra aussi longtemps que nécessaire qu'un événement se produise ; sinon, il attendra seulement aussi longtemps que l'intervalle le plus court passé à Tcl_SetMaxBlockTime par l'une des sources d'événements. Si une source d'événements sait qu'elle a déjà des événements prêts à être signalés, elle peut demander un temps de blocage nul. Par exemple, la procédure de configuration pour la source d'événements X vérifie s'il y a déjà des événements dans la file d'attente. S'il y en a, elle appelle Tcl_SetMaxBlockTime avec un temps de blocage de 0 afin que Tcl_WaitForEvent ne bloque pas s'il n'y a pas de nouvelles données sur la connexion X. L'argument timePtr de Tcl_WaitForEvent pointe vers une structure qui décrit un intervalle de temps en secondes et en microsecondes :

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

Le champ usec doit être inférieur à 1000000.

Les informations fournies à Tcl_SetMaxBlockTime ne sont utilisées que pour le prochain appel à Tcl_WaitForEvent ; elles sont supprimées après le retour de Tcl_WaitForEvent. La prochaine fois qu'une attente d'événement est effectuée, chacune des procédures de configuration des sources d'événements sera de nouveau appelée, et elles pourront spécifier de nouvelles informations pour cette attente d'événement.

Si l'application utilise une boucle d'événements externe plutôt que Tcl_DoOneEvent, les sources d'événements peuvent avoir besoin d'appeler Tcl_SetMaxBlockTime à d'autres moments. Par exemple, si un nouveau gestionnaire d'événements est enregistré qui nécessite d'interroger les événements, la source d'événements peut appeler Tcl_SetMaxBlockTime pour définir le temps de blocage à zéro afin de forcer la boucle d'événements externe à appeler Tcl. Dans ce cas, Tcl_SetMaxBlockTime invoque Tcl_SetTimer avec l'intervalle le plus court vu depuis le dernier appel à Tcl_DoOneEvent ou Tcl_ServiceAll.

En plus de la procédure générique Tcl_SetMaxBlockTime, d'autres procédures spécifiques à la plateforme peuvent également être disponibles pour setupProc, s'il existe des informations supplémentaires nécessaires à Tcl_WaitForEvent sur cette plateforme. Par exemple, sur les systèmes Unix, l'interface Tcl_CreateFileHandler peut être utilisée pour attendre les événements de fichier.

La deuxième procédure fournie par chaque source d'événements est sa procédure de vérification, indiquée par l'argument checkProc passé à Tcl_CreateEventSource. CheckProc doit correspondre au prototype suivant :

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Les arguments de cette procédure sont les mêmes que ceux de setupProc. CheckProc est invoquée par Tcl_DoOneEvent après qu'elle ait attendu les événements. On suppose qu'au moins une source d'événements est maintenant préparée à mettre un événement en file d'attente. Tcl_DoOneEvent appelle chaque source d'événements à tour de rôle, afin qu'elles aient toutes une chance de mettre en file d'attente tous les événements qui sont prêts. La procédure de vérification fait deux choses. Premièrement, elle doit vérifier si des événements se sont déclenchés. Différentes sources d'événements le font de différentes manières.

Si la procédure de vérification d'une source d'événements détecte un événement intéressant, elle doit ajouter l'événement à la file d'attente d'événements de Tcl. Pour ce faire, la source d'événements appelle Tcl_QueueEvent. L'argument evPtr est un pointeur vers une structure allouée dynamiquement contenant l'événement (voir ci-dessous pour plus d'informations sur les problèmes de gestion de la mémoire). Chaque source d'événements peut définir sa propre structure d'événement avec les informations pertinentes pour cette source d'événements. Cependant, le premier élément de la structure doit être une structure de type Tcl_Event, et l'adresse de cette structure est utilisée lors de la communication entre la source d'événements et le reste du notificateur. Un Tcl_Event a la définition suivante :

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La source d'événements doit remplir le champ proc de l'événement avant d'appeler Tcl_QueueEvent. Le champ nextPtr est utilisé pour lier les événements dans la file d'attente et ne doit pas être modifié par la source d'événements.

Un événement peut être ajouté à la file d'attente à l'une des trois positions, en fonction de l'argument position passé à Tcl_QueueEvent :

TCL_QUEUE_TAIL
Ajouter l'événement à la fin de la file d'attente, de sorte que tous les autres événements en attente soient traités en premier. C'est presque toujours la bonne position pour les nouveaux événements.
TCL_QUEUE_HEAD
Ajouter l'événement au début de la file d'attente, de sorte qu'il soit traité avant tous les autres événements mis en file d'attente.
TCL_QUEUE_MARK
Ajouter l'événement au début de la file d'attente, à moins qu'il n'y ait d'autres événements au début dont la position est TCL_QUEUE_MARK ; si c'est le cas, ajouter le nouvel événement juste après tous les autres événements TCL_QUEUE_MARK. Cette valeur de position est utilisée pour insérer une séquence ordonnée d'événements au début de la file d'attente, tels qu'une série d'événements Enter et Leave synthétisés lors d'une opération de grab ou ungrab dans Tk.

Lorsqu'il est temps de traiter un événement de la file d'attente (étapes 1 et 4 ci-dessus), Tcl_ServiceEvent invoquera la procédure proc spécifiée dans la première structure Tcl_Event mise en file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

Le premier argument de proc est un pointeur vers l'événement, qui sera le même que le premier argument de l'appel Tcl_QueueEvent qui a ajouté l'événement à la file d'attente. Le second argument de proc est l'argument flags de l'appel actuel à Tcl_ServiceEvent ; il est utilisé par la source d'événements pour revenir immédiatement si ses événements ne sont pas pertinents.

Il appartient à proc de gérer l'événement, généralement en invoquant une ou plusieurs commandes Tcl ou des rappels au niveau C. Une fois que la source d'événements a fini de gérer l'événement, elle retourne 1 pour indiquer que l'événement peut être retiré de la file d'attente. Si, pour une raison quelconque, la source d'événements décide que l'événement ne peut pas être traité à ce moment-là, elle peut retourner 0 pour indiquer que l'événement doit être différé pour un traitement ultérieur ; dans ce cas, Tcl_ServiceEvent passera à l'événement suivant dans la file d'attente et tentera de le traiter. Il existe plusieurs raisons pour lesquelles une source d'événements peut différer un événement. Une possibilité est que les événements de ce type soient exclus par l'argument flags. Par exemple, la source d'événements de fichier retournera toujours 0 si le bit TCL_FILE_EVENTS n'est pas défini dans flags. Un autre exemple de report d'événements se produit dans Tk si Tk_RestrictEvents a été invoqué pour reporter certains types d'événements de fenêtre.

Lorsque proc retourne 1, Tcl_ServiceEvent retirera l'événement de la file d'attente d'événements et libérera son stockage. Notez que le stockage pour un événement doit être alloué par la source d'événements (en utilisant Tcl_Alloc ou la macro Tcl ckalloc) avant d'appeler Tcl_QueueEvent, mais il sera libéré par Tcl_ServiceEvent, et non par la source d'événements.

Les applications multithread fonctionnent de manière similaire, sauf qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. L'appel de Tcl_QueueEvent dans une application multithread ajoute un événement à la file d'attente du thread actuel. Pour ajouter un événement à la file d'attente d'un autre thread, utilisez Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent accepte comme argument un argument Tcl_ThreadId, qui identifie de manière unique un thread dans une application Tcl. Pour obtenir le Tcl_ThreadId du thread actuel, utilisez la procédure Tcl_GetCurrentThread. (Un thread devrait ensuite passer cet identifiant à d'autres threads pour que ces derniers puissent ajouter des événements à sa file d'attente.) Après avoir ajouté un événement à la file d'attente d'un autre thread, vous devez généralement appeler Tcl_ThreadAlert pour « réveiller » le notificateur de ce thread afin de l'alerter du nouvel événement.

Tcl_DeleteEvents peut être utilisé pour supprimer explicitement un ou plusieurs événements de la file d'attente d'événements. Tcl_DeleteEvents appelle proc pour chaque événement dans la file d'attente, supprimant ceux pour lesquels la procédure retourne 1. Les événements pour lesquels la procédure retourne 0 restent dans la file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

L'argument clientData sera le même que l'argument clientData passé à Tcl_DeleteEvent

CRÉER UN NOUVEAU NOTIFICATEUR

Le notificateur se compose de toutes les procédures décrites dans ce manuel, plus Tcl_DoOneEvent et Tcl_Sleep, qui sont disponibles sur toutes les plateformes, et Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont spécifiques à Unix. La plupart de ces procédures sont génériques, car elles sont identiques pour tous les notificateurs. Cependant, aucune des procédures n'est dépendante du notificateur : Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler et Tcl_ServiceModeHook. Pour prendre en charge un nouveau système d'exploitation ou intégrer Tcl avec une boucle d'événements spécifique à un programme, vous devez écrire de nouvelles versions de ces procédures.

Tcl_InitNotifier initialise l'état du notificateur et renvoie un handle vers l'état du notificateur. Tcl appelle cette procédure lors de l'initialisation d'un interpréteur Tcl. De même, Tcl_FinalizeNotifier désactive le notificateur et est appelée par Tcl_Finalize lors de la fermeture d'un interpréteur Tcl.

Tcl_WaitForEvent est la procédure la plus basse du notificateur ; elle est responsable de l'attente d'un événement "intéressant" ou d'un temps donné. Avant d'invoquer Tcl_WaitForEvent, chaque procédure de source d'événement aura été invoquée. L'argument timePtr de Tcl_WaitForEvent donne le temps de blocage maximum pour un événement, basé sur les appels à Tcl_SetMaxBlockTime effectués par les procédures de configuration et d'autres informations (comme le bit TCL_DONT_WAIT dans flags).

Idéalement, Tcl_WaitForEvent ne devrait attendre qu'un événement ; elle ne devrait pas le traiter d'une quelconque manière. Ensuite, les notificateurs traiteront les événements bruts et créeront des Tcl_Events dans la file d'attente des événements dans leurs procédures checkProc. Cependant, sur certains systèmes d'exploitation (comme Windows), cela n'est pas possible ; les événements peuvent être traités dans Tcl_WaitForEvent, y compris la mise en file d'attente des Tcl_Events et plus encore (par exemple, les callbacks des widgets natifs). La valeur renvoyée par Tcl_WaitForEvent doit être 0, 1 ou -1. Sur les systèmes d'exploitation comme Windows où les événements sont traités dans Tcl_WaitForEvent, une valeur de retour de 1 signifie qu'il y a des événements en attente qui n'ont pas été traités. C'est un signal à l'appelant qui doit réinvoquer Tcl_WaitForEvent s'il souhaite traiter tous les événements en attente. Une valeur de retour de 0 signifie que l'invocation répétée de Tcl_WaitForEvent n'a aucun effet : il peut s'agir d'un système d'exploitation où Tcl_WaitForEvent attend simplement sans traiter d'événements, ou Tcl_WaitForEvent sait avec certitude qu'il n'y a pas d'événements supplémentaires à traiter (par exemple, la valeur a été renvoyée car le temps est écoulé). Enfin, une valeur de retour de -1 signifie que la boucle d'événements n'est plus opérationnelle et que l'application doit se démonter et se terminer. Sous Windows, cela se produit lorsqu'un message WM_QUIT est reçu ; sous Unix, cela se produit lorsque Tcl_WaitForEvent attendrait éternellement en raison de l'absence de sources d'événements actives et que le délai d'attente était infini.

Tcl_AlertNotifier est utilisé dans les applications multithreadées pour permettre à n'importe quel thread de "réveiller" le notificateur pour l'alerter de nouveaux événements dans sa file d'attente. Tcl_AlertNotifier nécessite comme argument le handle du notificateur renvoyé par Tcl_InitNotifier.

Si le notificateur doit être utilisé avec une boucle d'événements externe, il doit également prendre en charge l'interface Tcl_SetTimer. Tcl_SetTimer est appelée par Tcl_SetMaxBlockTime lorsqu'un temps de blocage maximal a été réduit. Tcl_SetTimer doit organiser que la boucle d'événements externe appelle Tcl_ServiceAll après un intervalle spécifié, même si aucun événement ne s'est produit. Cette interface est nécessaire car Tcl_WaitForEvent n'est pas appelée lorsqu'il y a une boucle d'événements externe. Si le notificateur doit uniquement être utilisé à partir de Tcl_DoOneEvent, Tcl_SetTimer n'a rien à faire.

Tcl_ServiceModeHook est appelée par la partie indépendante du notificateur lorsque le code client appelle Tcl_SetServiceMode. Ce hook est fourni pour prendre en charge les systèmes d'exploitation qui nécessitent une gestion spéciale des événements lorsque l'application est dans une boucle modale (comme le notificateur de Windows, par exemple, utilise ce hook pour créer une fenêtre de communication).

Sur les systèmes Unix, le notificateur de fichiers nécessite également un support du notificateur. Le notificateur de fichiers se compose des procédures Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont décrites sur la page de manuel de Tcl_CreateFileHandler.

Les interfaces de Tcl_Sleep et Tcl_DoOneEvent sont décrites dans leurs pages de manuel respectives.

La manière la plus simple de créer un nouveau notificateur est de consulter le code d'un notificateur existant, par exemple dans les fichiers unix/tclUnixNotfy.c ou win/tclWinNotify.c dans la distribution du code Tcl.

REMPLACER LE NOTIFICATEUR

Un notificateur qui a été écrit selon les conventions ci-dessus peut également être installé dans un processus en cours d'exécution à la place du notificateur standard. Ce mécanisme est utilisé pour qu'un seul exécutable puisse être utilisé (avec le notificateur standard) comme programme autonome et puisse être réutilisé (avec un notificateur remplacé dans une extension chargeable) comme extension d'un autre programme, tel qu'un plugin de navigateur web.

Pour ce faire, l'extension appelle Tcl_SetNotifier, en passant un pointeur vers une structure Tcl_NotifierProcs. La structure a la disposition suivante :

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Après l'appel à Tcl_SetNotifier, les pointeurs donnés dans la structure Tcl_NotifierProcs remplacent tout notificateur qui avait été installé dans le processus.

Il est extrêmement déconseillé de remplacer un notificateur en cours d'exécution. Normalement, Tcl_SetNotifier devrait être appelé avant la première invocation de Tcl_InitNotifier.

BOUCLES D'ÉVÉNEMENTS EXTERNES

Les interfaces du notificateur sont conçues pour que Tcl puisse s'intégrer dans des applications qui ont leurs propres boucles d'événements privées. Dans ce cas, l'application n'appelle pas Tcl_DoOneEvent sauf dans le cas de boucles d'événements récursives, telles que les appels à des commandes comme update ou vwait. La majeure partie du temps est consacrée à la boucle d'événements externe de l'application. Dans ce cas, le notificateur doit organiser que la boucle d'événements externe rappelle Tcl lorsqu'un événement se produit dans les sources d'événements Tcl. Ces callbacks doivent organiser que les événements Tcl appropriés soient placés dans la file d'attente des événements Tcl.

Étant donné que la boucle d'événements externe n'appelle pas Tcl_DoOneEvent régulièrement, c'est le notificateur qui doit organiser l'invocation de Tcl_ServiceEvent lorsqu'il y a des événements en attente dans la file d'attente des événements Tcl. La manière la plus simple de le faire est d'appeler Tcl_ServiceAll à la fin de chaque callback de la boucle d'événements externe. Cela garantira que tous les événements des sources d'événements sont inspectés, que les événements mis en file d'attente sont servis et que les gestionnaires d'inactivité sont traités avant de rendre le contrôle à l'application. De plus, les événements qui nécessitent une inspection peuvent appeler Tcl_SetMaxBlockTime pour forcer la boucle d'événements externe à appeler Tcl même s'il n'y a pas d'événements dans la file d'attente des événements système.

En conséquence des événements détectés dans la boucle d'événements externe principale, Tcl peut appeler Tcl_DoOneEvent pour démarrer une boucle d'événements récursive dans des commandes comme vwait. Tcl_DoOneEvent appelle la boucle d'événements externe, ce qui entraînera des callbacks comme décrit dans le paragraphe précédent, ce qui entraînera des appels à Tcl_ServiceAll. Cependant, dans ces cas, il n'est pas souhaitable de traiter les événements dans Tcl_ServiceAll. Le traitement des événements là-bas est inutile car le contrôle reviendra immédiatement à la boucle d'événements externe et, par conséquent, à Tcl_DoOneEvent, qui peut servir les événements. De plus, Tcl_DoOneEvent est destiné à servir un seul événement, tandis que Tcl_ServiceAll sert normalement tous les événements en attente. Pour gérer cette situation, Tcl_DoOneEvent définit un drapeau dans Tcl_ServiceAll qui lui indique de ne traiter aucun événement, faisant que Tcl_ServiceAll renvoie sans traiter aucun événement. Ce drapeau est appelé le *mode de service* ; Tcl_DoOneEvent le restaurera à sa valeur précédente avant de se rendre.

Dans certains cas, cependant, il peut être nécessaire que Tcl_ServiceAll traite les événements même s'il a été appelé depuis Tcl_DoOneEvent. Cela se produit lorsqu'il y a une autre boucle d'événements récursive invoquée par un gestionnaire d'événements appelé par Tcl_DoOneEvent (comme celui qui fait partie d'un widget natif). Dans ce cas, Tcl_DoOneEvent peut ne pas avoir l'occasion de servir les événements, donc Tcl_ServiceAll doit les servir tous. Toute boucle d'événements récursive qui appelle une boucle d'événements externe au lieu de Tcl_DoOneEvent doit réinitialiser le mode de service afin que tous les événements soient traités dans Tcl_ServiceAll. Cela est fait en appelant la procédure Tcl_SetServiceMode. Si Tcl_SetServiceMode est passé TCL_SERVICE_NONE, alors les appels à Tcl_ServiceAll renverront immédiatement sans traiter aucun événement. Si Tcl_SetServiceMode est passé TCL_SERVICE_ALL, alors les appels à Tcl_ServiceAll se comporteront normalement. Tcl_SetServiceMode renvoie la valeur précédente du mode de service, qui doit être restaurée lorsque la boucle d'événements récursive se termine. Tcl_GetServiceMode renvoie la valeur actuelle du mode de service.
