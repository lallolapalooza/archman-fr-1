DESCRIPTION

Il y a plusieurs raisons d'appeler les fonctions de l'API Tcl_FS (par exemple, Tcl_FSAccess et Tcl_FSStat) plutôt que d'appeler directement des fonctions de niveau système comme access et stat. Premièrement, elles fonctionneront de manière multiplateforme, donc une extension qui les appelle devrait fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige certains bogues dans les appels de niveau système. Troisièmement, ces appels de fonction gèrent toutes les conversions de chemin « Utf vers natif de plateforme » qui peuvent être nécessaires (et peuvent mettre en cache les résultats de telles conversions pour une plus grande efficacité lors des appels ultérieurs). Quatrièmement, et peut-être le plus important, toutes ces fonctions sont « conscientes des systèmes de fichiers virtuels ». Tout système de fichiers virtuel (VFS pour faire court) qui a été enregistré (via Tcl_FSRegister) peut rediriger l'accès aux fichiers vers des supports ou des méthodes d'accès alternatifs. Cela signifie que toutes ces fonctions (et donc les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent fonctionner sur des « fichiers » qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS pour faire court) via cette API est automatiquement « consciente des systèmes de fichiers virtuels ». Bien sûr, si une extension accède au système de fichiers natif directement (via des API spécifiques à la plateforme, par exemple), Tcl ne peut pas intercepter de tels appels.

Si des VFS appropriés ont été enregistrés, les « fichiers » peuvent, pour donner deux exemples, être distants (par exemple, situés sur un serveur ftp distant) ou archivés (par exemple, se trouvant à l'intérieur d'une archive .zip). De tels systèmes de fichiers enregistrés fournissent une table de correspondance de fonctions pour implémenter tout ou partie de la fonctionnalité énumérée ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat abstraient la façon dont le tampon « struct stat » est réellement déclaré, permettant d'utiliser le même code aussi bien sur les systèmes avec que sans prise en charge des fichiers de plus de 2 Go. taille.

L'API Tcl_FS est basée sur Tcl_Obj et peut mettre en cache des représentations internes et d'autres chaînes de caractères liées aux chemins (par exemple, le répertoire de travail actuel). Un effet secondaire est qu'il ne faut pas passer de valeurs avec un compteur de références de zéro à l'une de ces fonctions. Si de tels appels étaient traités, ils pourraient entraîner des fuites de mémoire (dans certaines circonstances, le code du système de fichiers peut souhaiter conserver une référence à la valeur passée, et il ne faut donc pas supposer qu'après le retour de l'un de ces appels, la valeur a toujours un compteur de références de zéro - il pourrait avoir été incrémenté) ou un segmentation fault direct (ou une autre erreur d'accès mémoire) en raison de la libération de la valeur au milieu de la manipulation complexe de valeurs requise pour garantir que le chemin est entièrement normalisé et absolu pour la détermination du système de fichiers. La leçon pratique à en tirer est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect et peut causer des erreurs de mémoire. Le compteur de références de path doit être incrémenté avant d'être passé, ou décrémenté. Pour cette raison, les valeurs avec un compteur de références de zéro ne sont pas considérées comme des chemins de système de fichiers valides et l'appel de toute fonction de l'API Tcl_FS avec une telle valeur n'entraînera aucune action.

FONCTIONS API FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno sur le code d'erreur POSIX « EXDEV » (qui signifie un « lien inter-domaines »).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno sur le code d'erreur POSIX « EXDEV » (qui signifie un « lien inter-domaines »).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction « créer un répertoire » du système de fichiers propriétaire.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction « supprimer un fichier » du système de fichiers propriétaire.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction « supprimer un répertoire » du système de fichiers propriétaire.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr en nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « renommer le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno sur le code d'erreur POSIX « EXDEV » (qui signifie un « lien inter-domaines »).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction « lister les volumes » non NULL et leur demande de retourner leur liste de volumes racine. Elle accumule les valeurs de retour dans une liste qui est renvoyée à l'appelant (avec un compteur de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant l'encodage identifié par encodingName et évalue son contenu comme un script Tcl. Elle renvoie les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, l'encodage système est utilisé pour lire le contenu du fichier. Si le fichier n'a pas pu être lu, une erreur Tcl est renvoyée pour décrire pourquoi le fichier n'a pas pu être lu. Le caractère de fin de fichier (eofchar) pour les fichiers est « \x1A » (^Z) pour toutes les plateformes. Si vous avez besoin d'un « ^Z » dans le code pour la comparaison de chaînes, vous pouvez utiliser « \x1A », qui sera substitué en toute sécurité par l'interpréteur Tcl en « ^Z ». Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours l'encodage système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier de code binaire en mémoire et renvoie les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas, en raison des limitations du système d'exploitation dans le chargement dynamique de code binaire), Tcl tentera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile inverse l'opération, demandant que la bibliothèque indiquée par loadHandle soit retirée du processus. Notez qu'à la différence de la commande unload, cela ne donne à la bibliothèque aucune possibilité de nettoyage.

Les deux fonctions ci-dessus renvoient un code d'achèvement Tcl standard. Si une erreur se produit, un message d'erreur est laissé dans le résultat de l'interp.

Le jeton fourni via la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher dans un répertoire tous les fichiers qui correspondent à un modèle donné. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le globbing. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Notez que le code glob implémente les modèles récursifs en interne, de sorte que cette fonction ne recevra jamais que des modèles simples, qui peuvent être mis en correspondance en utilisant la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment en demandant uniquement le retour des répertoires. Un cas spécial où elle est appelée avec un modèle NULL indique que le chemin doit être vérifié uniquement pour le bon type.

Tcl_FSLink remplace la version bibliothèque de readlink, et l'étend pour supporter la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr sera appelée.

Si toPtr est NULL, une action « lire le lien » est effectuée. Le résultat est un Tcl_Obj spécifiant le contenu du lien symbolique donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat est détenu par l'appelant, qui devrait appeler Tcl_DecrRefCount lorsqu'il n'a plus besoin du résultat. Si toPtr n'est pas NULL, Tcl doit créer un lien de l'un des types passés dans le drapeau linkAction. Ce drapeau est une combinaison OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'un choix existe (c'est-à-dire que plus d'un drapeau est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur de retour doit être toPtr (qui est donc déjà détenu par l'appelant). En cas d'échec, NULL est renvoyé.

Tcl_FSLstat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de parcours sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (nlink, toujours 1 sous Windows), l'identifiant utilisateur (toujours 0 sous Windows), l'identifiant de groupe (toujours 0 sous Windows), le périphérique rdev (identique au périphérique sous Windows), la taille, le dernier

t d'accès, heure de dernière modification et heure de dernière modification des métadonnées. Voir API PORTABLE STAT RESULT pour une description de la manière d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSLstat retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné et aucune information de stat n'est fournie.

Tcl_FSUtime remplace la version de bibliothèque de utime.

Ceci retourne 0 en cas de succès et -1 en cas d'erreur (conformément à la documentation utime). En cas de succès, la fonction mettra à jour les valeurs “atime” et “mtime” du fichier spécifié.

Tcl_FSFileAttrsGet implémente l'accès en lecture pour la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel pathPtr appartient sera appelée.

Si le résultat est TCL_OK, alors une valeur a été placée dans objPtrRef, qui ne sera valide que temporairement (sauf si Tcl_IncrRefCount est appelé).

Tcl_FSFileAttrsSet implémente l'accès en écriture pour la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel pathPtr appartient sera appelée.

Tcl_FSFileAttrStrings implémente une partie de la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel pathPtr appartient sera appelée.

La procédure appelée peut soit retourner un tableau de chaînes, soit retourner NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et augmentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl diminuera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl lorsqu'elle n'est plus utilisée, elle devrait avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer de conserver un compteur de références pour la valeur.

Tcl_FSAccess vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est pathname. Si pathname est un lien symbolique sur Unix, alors les permissions du fichier auquel ce lien symbolique fait référence sont testées.

En cas de succès (toutes les permissions demandées accordées), zéro est retourné. En cas d'erreur (au moins un bit dans mode demandait une permission refusée, ou une autre erreur s'est produite), -1 est retourné.

Tcl_FSStat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf contient des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification et l'heure de la dernière modification des métadonnées. Voir API PORTABLE STAT RESULT pour une description de la manière d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSStat retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné et aucune information de stat n'est fournie.

Tcl_FSOpenFileChannel ouvre un fichier spécifié par pathPtr et retourne un descripteur de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est calquée sur la procédure fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannel retourne NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannel laisse un message d'erreur dans le résultat de interp après toute erreur.

Le nouveau canal créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez Tcl_RegisterChannel. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, l'acte de création du nouveau canal l'assigne également en tant que remplacement du canal standard.

Tcl_FSGetCwd remplace la version de bibliothèque de getcwd.

Il retourne le répertoire de travail actuel de la bibliothèque Tcl. Celui-ci peut être différent du répertoire de travail de la plateforme native, ce qui se produit lorsque le répertoire de travail actuel n'est pas dans le système de fichiers natif.

Le résultat est un pointeur vers un Tcl_Obj spécifiant le répertoire courant, ou NULL si le répertoire courant n'a pas pu être déterminé. Si NULL est retourné, un message d'erreur est laissé dans le résultat de interp.

Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compteur de références doit être décrémenté. Ceci est nécessaire pour des raisons de sécurité des threads, afin de permettre à plusieurs threads d'accéder à cette fonction et aux fonctions connexes, tout en garantissant que les résultats sont toujours valides.

Tcl_FSChdir remplace la version de bibliothèque de chdir. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl se rabattra sur une combinaison de stat et access pour vérifier si le répertoire existe et a les permissions appropriées.

Pour les résultats, voir la documentation de chdir. En cas de succès, nous conservons un enregistrement du chemin réussi dans cwdPathPtr pour les appels ultérieurs à Tcl_FSGetCwd.

Tcl_FSPathSeparator retourne le caractère séparateur à utiliser pour l'élément le plus spécifique du chemin spécifié par pathPtr (c'est-à-dire la dernière partie du chemin).

Le séparateur est retourné sous forme de Tcl_Obj contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est retourné.

Tcl_FSJoinPath prend le Tcl_Obj donné, qui doit être une liste valide (qui est autorisée à avoir un compteur de références de zéro), et retourne la valeur du chemin donnée en considérant les elements premiers éléments comme des segments de chemin valides (chaque segment de chemin peut être un chemin complet, un chemin partiel ou juste un seul répertoire ou nom de fichier possible). Si un segment de chemin est en fait un chemin absolu, alors tous les segments de chemin précédents sont écartés. Si elements est inférieur à 0, nous utilisons la liste entière.

Il est possible que la valeur retournée soit en fait un élément de la liste donnée, donc l'appelant doit faire attention à incrémenter le compteur de références du résultat avant de libérer la liste.

La valeur retournée, généralement avec un compteur de références de zéro (mais elle peut être partagée dans certaines conditions), contient le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. En particulier, la valeur retournée peut être un élément de la liste donnée, donc libérer la liste pourrait libérer la valeur prématurément si aucun compteur de références n'a été pris. Si le nombre d'éléments est zéro, alors la valeur retournée sera un Tcl_Obj de chaîne vide.

Tcl_FSSplitPath prend le Tcl_Obj donné, qui devrait être un chemin valide, et retourne une valeur de liste Tcl contenant chaque segment de ce chemin comme un élément. Il retourne une valeur de liste avec un compteur de références de zéro. Si lenPtr passé est non NULL, la variable à laquelle il pointe sera mise à jour pour contenir le nombre d'éléments dans la liste retournée.

Tcl_FSEqualPaths teste si les deux chemins donnés représentent le même objet de système de fichiers. Il retourne 1 si les chemins sont égaux et 0 s'ils sont différents. Si l'un des chemins est NULL, 0 est toujours retourné.

Tcl_FSGetNormalizedPath tente d'extraire du Tcl_Obj donné une représentation de chemin normalisée unique, dont la valeur de chaîne peut être utilisée comme identifiant unique pour le fichier.

Il retourne la valeur du chemin normalisé, détenue par Tcl, ou NULL si le chemin était invalide ou n'a pas pu être converti avec succès. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère sur ces représentations en interne), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques puisse ne pas être la version la plus conviviale d'un chemin. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle de pathPtr passé (sauf si c'est un chemin relatif, auquel cas la valeur du chemin normalisé peut être libérée à tout moment où le cwd change) - l'appelant peut bien sûr incrémenter le compteur de références s'il souhaite conserver une copie plus longtemps.

Tcl_FSJoinToPath prend la valeur donnée, qui devrait généralement être un chemin valide ou NULL, et y joint le tableau de segments de chemin donnés.

Retourne une valeur, généralement avec un compteur de références de zéro (mais elle peut être partagée dans certaines conditions), contenant le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. Si l'une des valeurs passées à cette fonction (pathPtr ou éléments de path) a un compteur de références de zéro, elle sera libérée lorsque cette fonction retournera.

Tcl_FSConvertToPathType essaie de convertir le Tcl_Obj donné en un type de chemin Tcl valide, en tenant compte du fait que le cwd peut avoir changé même si cette valeur est déjà censée être du bon type. Le nom de fichier peut commencer par “~” (pour indiquer le répertoire personnel de l'utilisateur courant) ou “~<utilisateur>” (pour indiquer le répertoire personnel d'un utilisateur quelconque).

Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), alors TCL_OK est retourné. Sinon, TCL_ERROR est retourné, et un message d'erreur peut être laissé dans l'interpréteur.

Tcl_FSGetInternalRep extrait la représentation interne d'une valeur de chemin donnée, dans le système de fichiers donné. Si la valeur du chemin appartient à un système de fichiers différent, nous retournons NULL. Si la représentation interne est actuellement NULL, nous tentons de la générer, en appelant Tcl_FSCreateInternalRepProc du système de fichiers.

Retourne NULL ou une représentation de chemin interne valide. Cette représentation interne est mise en cache, de sorte que les appels répétés à cette fonction ne nécessiteront pas de conversions supplémentaires.

Tcl_FSGetTranslatedPath tente d'extraire le chemin traduit du Tcl_Obj donné.

Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), alors elle est retournée. Sinon, NULL sera retourné, et un message d'erreur peut être laissé dans l'interpréteur. Un chemin “traduit” est un chemin qui ne contient aucune séquence “~” ou “~utilisateur” (celles-ci ont été développées dans leur représentation actuelle dans le système de fichiers). La valeur retournée est détenue par l'appelant, qui doit la stocker ou appeler Tcl_DecrRefCount pour s'assurer que la mémoire est libérée. Cette fonction est d'une utilité pratique limitée, et Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des usages.

Tcl_FSGetTranslatedStringPath fait la même chose que Tcl_FSGetTranslatedPath, mais retourne une chaîne de caractères ou NULL. La chaîne retournée est allouée dynamiquement

L'API DU SYSTÈME DE FICHIERS VIRTUEL

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un système de fichiers ; ces opérations sont invoquées au besoin par la capacité générale, qui se produit généralement par le biais des fonctions mentionnées ci-dessus.

Les structures Tcl_Filesystem sont manipulées par les méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et des données facultatives associées à cette structure. En appelant cette fonction, Tcl associera le système de fichiers à la liste des systèmes de fichiers connus et le rendra immédiatement fonctionnel. Tcl ne vérifie pas si le même système de fichiers a été enregistré plusieurs fois (et ce n'est généralement pas une bonne idée). TCL_OK sera renvoyé.

Tcl_FSUnregister supprime la structure donnée de la liste des systèmes de fichiers connus, si elle est enregistrée, et renvoie TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR sera renvoyé.

Tcl_FSData renverra le clientData associé au système de fichiers donné, s'il est enregistré. Sinon, il renverra NULL.

Tcl_FSMountsChanged est utilisé pour informer le noyau de Tcl que les points de montage du système de fichiers donné (déjà enregistré) ont changé, et que les représentations mises en cache des fichiers peuvent maintenant être inadéquates.

LA STRUCTURE TCL_FILESYSTEM

La structure Tcl_Filesystem contient les champs suivants :

    const char *typeName;
    int structureLength;
    Tcl_FSVersion version;
    Tcl_FSPathInFilesystemProc *pathInFilesystemProc;
    Tcl_FSDupInternalRepProc *dupInternalRepProc;
    Tcl_FSFreeInternalRepProc *freeInternalRepProc;
    Tcl_FSInternalToNormalizedProc *internalToNormalizedProc;
    Tcl_FSCreateInternalRepProc *createInternalRepProc;
    Tcl_FSNormalizePathProc *normalizePathProc;
    Tcl_FSFilesystemPathTypeProc *filesystemPathTypeProc;
    Tcl_FSFilesystemSeparatorProc *filesystemSeparatorProc;
    Tcl_FSStatProc *statProc;
    Tcl_FSAccessProc *accessProc;
    Tcl_FSOpenFileChannelProc *openFileChannelProc;
    Tcl_FSMatchInDirectoryProc *matchInDirectoryProc;
    Tcl_FSUtimeProc *utimeProc;
    Tcl_FSLinkProc *linkProc;
    Tcl_FSListVolumesProc *listVolumesProc;
    Tcl_FSFileAttrStringsProc *fileAttrStringsProc;
    Tcl_FSFileAttrsGetProc *fileAttrsGetProc;
    Tcl_FSFileAttrsSetProc *fileAttrsSetProc;
    Tcl_FSCreateDirectoryProc *createDirectoryProc;
    Tcl_FSRemoveDirectoryProc *removeDirectoryProc;
    Tcl_FSDeleteFileProc *deleteFileProc;
    Tcl_FSCopyFileProc *copyFileProc;
    Tcl_FSRenameFileProc *renameFileProc;
    Tcl_FSCopyDirectoryProc *copyDirectoryProc;
    Tcl_FSLstatProc *lstatProc;
    Tcl_FSLoadFileProc *loadFileProc;
    Tcl_FSGetCwdProc *getCwdProc;
    Tcl_FSChdirProc *chdirProc;
} Tcl_Filesystem;

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, tous les autres champs contiennent des adresses de fonctions qui sont invoquées par la capacité générale pour effectuer un large éventail d'actions liées au système de fichiers.

Les fonctions mentionnées dans cette structure sont divisées en trois catégories : fonctions d'infrastructure (la plupart doivent être implémentées, au-delà de presque toutes les autres), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni) et fonctions d'efficacité (qui ne doivent être implémentées que si elles peuvent être effectuées efficacement, ou si elles ont des effets secondaires nécessaires au système de fichiers ; Tcl dispose d'émulations plus lentes auxquelles il peut recourir). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces rappels ne sont utilisés que pour gérer les commandes initiées dans Tcl, pas dans C. Cela signifie que, si une instruction de renommage de fichier est émise dans Tcl, et que les systèmes de fichiers concernés n'implémentent pas leur Tcl_FSRenameFileProc, le noyau de Tcl se basera sur une combinaison d'autres fonctions du système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a un rappel supplémentaire). Cependant, si une instruction Tcl_FSRenameFileProc est émise au niveau C, ce mécanisme de secours ne se produit pas. Ceci est vrai, à l'exception des quatre derniers éléments du tableau du système de fichiers (lstat, load, getcwd et chdir), pour lesquels les mécanismes de secours se produisent effectivement au niveau C.

Toute fonction qui accepte des noms de répertoire au format Tcl_Obj les acceptera sous forme d'UTF-8. L'API d'infrastructure du système de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers des représentations natives.

INFRASTRUCTURE DU SYSTÈME DE FICHIERS

Ces champs contiennent des informations de base sur la structure du système de fichiers et les adresses des fonctions utilisées pour associer un système de fichiers donné à une valeur de chemin et pour gérer la représentation interne des chemins, par exemple, pour copier et libérer de telles représentations.

NOM DU TYPE

Le champ typeName contient une chaîne terminée par null qui identifie le type du système de fichiers implémenté, par exemple, « native », « zip » ou « vfs ».

LONGUEUR DE LA STRUCTURE

Le champ structureLength est généralement implémenté comme sizeof(Tcl_Filesystem), et il est là pour permettre une compatibilité binaire plus facile dans les futures versions de Tcl si la taille de la structure change.

VERSION

Le champ version doit être défini à TCL_FILESYSTEM_VERSION_1.

PROCÉDURE DE CHEMIN DANS LE SYSTÈME DE FICHIERS

Le champ pathInFilesystemProc contient l'adresse d'une fonction qui est appelée pour déterminer si une valeur de chemin donnée appartient à ce système de fichiers. Tcl n'appellera les autres fonctions du système de fichiers qu'avec un chemin pour lequel cette fonction a renvoyé TCL_OK. Si le chemin n'appartient pas, -1 sera renvoyé (le comportement de Tcl pour toute autre valeur de retour n'est pas défini). Si TCL_OK est renvoyé, le paramètre de sortie clientDataPtr peut être utilisé pour renvoyer une représentation interne (spécifique au système de fichiers) du chemin, qui sera stockée dans la valeur du chemin et pourra être récupérée efficacement par d'autres fonctions du système de fichiers à partir d'autres systèmes de fichiers. Tcl mettra également en cache le fait que ce chemin appartient à ce système de fichiers. Ces caches seront invalidés lorsque des systèmes de fichiers seront ajoutés ou supprimés de la liste interne des systèmes de fichiers connus de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROCÉDURE DE DUPLICATION DE REPRÉSENTATION INTERNE

Cette fonction crée une copie de la représentation interne d'un chemin et est appelée lorsque Tcl a besoin de dupliquer une valeur de chemin. Si elle est NULL, Tcl ne copiera pas la représentation interne, qui pourrait alors être nécessaire plus tard.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

PROCÉDURE DE LIBÉRATION DE REPRÉSENTATION INTERNE

Libère la représentation interne. Doit être implémentée si les représentations internes nécessitent une libération (c'est-à-dire si de la mémoire est allouée lors de la création d'une représentation interne), mais peut être NULL sinon.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

PROCÉDURE DE CONVERSION DE REPRÉSENTATION INTERNE EN REPRÉSENTATION NORMALISÉE

Procédure pour convertir la représentation interne en un chemin normalisé. N'est requise que si le système de fichiers crée des valeurs de chemin pures sans représentation chaîne/branche. La valeur renvoyée est un objet Tcl dont la représentation chaîne est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

PROCÉDURE DE CRÉATION DE REPRÉSENTATION INTERNE

Procédure pour prendre une valeur de chemin et calculer une représentation interne pour celle-ci, et stocker cette représentation native dans la valeur. Peut être NULL si les chemins n'ont pas de représentation interne, ou si le Tcl_FSPathInFilesystemProc pour ce système de fichiers crée toujours immédiatement une représentation interne pour les chemins qu'il accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

PROCÉDURE DE NORMALISATION DE CHEMIN

Procédure pour normaliser un chemin. Doit être implémentée par tous les systèmes de fichiers qui peuvent avoir plusieurs représentations de chaînes pour la même valeur de chemin. Dans Tcl, chaque chemin doit avoir une seule représentation canonique « normalisée ». Selon le système de fichiers, il peut y avoir plus d'une représentation de chaîne non normalisée qui se réfère à ce chemin (par exemple, un chemin relatif, un chemin avec une casse différente si le système de fichiers est insensible à la casse, un chemin contenant une référence à un répertoire personnel comme ~, un chemin contenant des liens symboliques, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être résolu en la valeur vers laquelle il pointe, mais sa casse ou d'autres aspects doivent être uniques. Tous les autres composants du chemin doivent être résolus à partir des liens symboliques. Cette exception est nécessaire pour s'aligner sur le comportement de Tcl avec les commandes file, delete, rename, copy sur les liens symboliques. Cette procédure peut être appelée avec nextCheckpoint au début du chemin (c'est-à-dire zéro), à la fin du chemin, ou à n'importe quel séparateur de fichier intermédiaire dans le chemin. Elle ne sera pas appelée à une autre position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémenteur peut supposer que le chemin depuis le début jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS DU SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions qui sont appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers destiné à être utilisé avec l'ensemble complet des commandes Tcl doit implémenter toutes ces fonctions. Si certaines d'entre elles ne sont pas implémentées, certaines commandes Tcl peuvent échouer lors de l'opération sur des chemins dans ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne doit pas implémenter les quatre dernières fonctions et un système de fichiers qui ne prend pas en charge les liens symboliques ne doit pas implémenter la fonction readlink, etc. Le noyau de Tcl s'attend à ce que les systèmes de fichiers se comportent ainsi).

PROCÉDURE DE TYPE DE CHEMIN DU SYSTÈME DE FICHIERS

Procédure pour déterminer le type d'un chemin dans ce système de fichiers. Peut être NULL, auquel cas aucune information de type ne sera affichée aux utilisateurs du système de fichiers. Le type est utilisé uniquement à des fins d'information, et doit être renvoyé comme représentation chaîne de l'objet Tcl_Obj renvoyé. Une valeur typique pourrait être "networked", "zip" ou "ftp". L'objet Tcl résultant est considéré comme appartenant au système de fichiers, Tcl incrémentera donc le compteur de références de cette valeur si elle le souhaite.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

PROCÉDURE DE SÉPARATEUR DE SYSTÈME DE FICHIERS

Procédure pour renvoyer le caractère séparateur de ce système de fichiers. Ne doit être implémentée que si le système de fichiers souhaite utiliser un séparateur autre que le standard « / ». Entre autres utilisations, elle est renvoyée par la commande file separator. La valeur renvoyée devrait avoir un compteur de références de zéro.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

PROCÉDURE STAT

Procédure pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes Tcl en dépendent crucialement (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La procédure Tcl_FSStatProc remplit la structure statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche pour tous les répertoires nommés dans le chemin menant au fichier. La structure de statistiques comprend des informations sur le périphérique, l'inœud (0 sous Windows), le mode des privilèges, le nlink (1 sous Windows), l'identifiant de l'utilisateur (0 sous Windows), l'identifiant du groupe (0 sous Windows), le rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification et l'heure du dernier changement de métadonnées.

Si le fichier représenté par pathPtr existe, Tcl_FSStatProc renvoie 0 et la structure de statistiques est remplie de données. Sinon, -1 est renvoyé et aucune information de statistiques n'est fournie.

PROCÉDURE D'ACCÈS

Procédure pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes Tcl en dépendent crucialement (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La procédure Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom se trouve dans pathPtr. Si le chemin fait référence à un lien symbolique, les autorisations du fichier auquel ce lien symbolique fait référence doivent être vérifiées.

En cas de succès (toutes les autorisations demandées ont été accordées), 0 est renvoyé. En cas d'erreur (au moins un bit du mode demandé est refusé, ou une autre erreur s'est produite), -1 est renvoyé.

PROCÉDURE D'OUVERTURE DE CANAL DE FICHIER

Procédure pour traiter un appel Tcl_FSOpenFileChannel. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes Tcl en dépendent crucialement (par exemple, file exists, file readable).

typedef int Tcl_FSOpenFileChannelProc(
        Tcl_Obj *pathPtr,
        int mode);

La procédure Tcl_FSOpenFileChannelProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom se trouve dans pathPtr. Si le chemin fait référence à un lien symbolique, les autorisations du fichier auquel ce lien symbolique fait référence doivent être vérifiées.

En cas de succès (toutes les autorisations demandées ont été accordées), 0 est renvoyé. En cas d'erreur (au moins un bit du mode demandé est refusé, ou une autre erreur s'est produite), -1 est renvoyé.

OPENFILECHANNELPROC

Fonction pour traiter un appel à Tcl_FSOpenFileChannel. Elle doit être implémentée pour tout système de fichiers raisonnable, car toute opération qui nécessite l'ouverture ou l'accès au contenu d'un fichier utilisera cette fonction (par exemple, open, encoding, et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

La Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et retourne un handle de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est modelée d'après la fonction fopen de la bibliothèque d'E/S standard POSIX. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier, où le mode est une combinaison des drapeaux POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannelProc retourne NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le canal créé doit être enregistré auprès de l'interpréteur fourni par Tcl_FSOpenFileChannelProc ; le travail d'enregistrement incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standards, stdin, stdout ou stderr, a été précédemment fermé, la création du nouveau canal l'assigne également en remplacement des canaux standards.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, la fonctionnalité de globbing et de copie récursive sera absente du système de fichiers (et cela peut affecter des commandes comme encoding names qui utilisent la fonctionnalité de globbing).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit retourner tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au modèle donné et qui satisfont la spécification types. Cette fonction peut être appelée de deux manières. Si pattern est NULL, pathPtr est une spécification complète d'un fichier ou d'un répertoire dont l'existence et le type doivent être vérifiés. Sinon, pathPtr est un répertoire et la fonction doit rechercher des fichiers ou des répertoires dont les types sont corrects. Dans tous les cas, pathPtr est supposé ne pas être nul et non vide. Il n'est actuellement pas documenté si pathPtr se termine par un séparateur de fichier, le code doit donc être flexible aux deux cas.

La valeur de retour est un résultat standard de Tcl indiquant si une erreur s'est produite pendant le processus de correspondance. Les messages d'erreur sont placés dans interp, sauf si interp est NULL, auquel cas aucun message d'erreur n'est généré. En cas de résultat TCL_OK, les résultats doivent être ajoutés à la valeur resultPtr fournie (qui est supposée être une liste Tcl non partagée). Les correspondances supplémentaires dans resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (ce qui indique généralement qu'il s'agira de spécifications de chemin absolu). Remarque : s'il n'y a pas de correspondance, un résultat vide est retourné ; les erreurs ne sont signalées que pour les problèmes réels de fichier ou de système de fichiers qui peuvent survenir pendant le processus de correspondance.

Le Tcl_GlobTypeData passé dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Type mac accepté */
    Tcl_Obj *macType;
    /* Créateur mac accepté */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il existe deux cas spécifiques qui sont importants à gérer correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types est & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT est vrai (et en particulier lorsque les autres drapeaux sont faux). Dans le premier cas, la fonction doit lister les répertoires contenus. Tcl utilise cela pour implémenter le globbing récursif, il est donc crucial que les systèmes de fichiers implémentent correctement la correspondance des répertoires. Dans le second cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage trouvés dans le répertoire donné (pathPtr), et dans ce cas, pathPtr n'a pas besoin d'être dans le même système de fichiers (contrairement à d'autres cas où cette fonction est appelée). Le support de cela est critique si Tcl doit avoir des transitions fluides entre les systèmes de fichiers.

UTIMEPROC

Fonction pour traiter un appel à Tcl_FSUtime. Elle est obligatoire pour permettre l'ajustement (pas la lecture) des heures de dernière modification et de dernier accès sur les fichiers, ainsi que pour implémenter l'opération de copie de fichiers (open-r/open-w/fcopy).

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les heures d'accès et de modification des fichiers spécifiés par pathPtr doivent être modifiées pour correspondre aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec le système utime.

LINKPROC

Fonction pour traiter un appel à Tcl_FSLink. Elle ne doit être implémentée que si le système de fichiers prend en charge les liens, et dans le cas contraire, elle peut être NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est appelée pour lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient entièrement à l'appelant (et doit donc voir son compteur de références incrémenté avant d'être retourné). Tout appelant doit appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'en a plus besoin. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Dans ce cas, le résultat doit être toPtr si la création du lien a réussi et NULL sinon. Dans ce cas, le résultat n'appartient pas à l'appelant (c'est-à-dire qu'aucune manipulation du compteur de références n'est nécessaire des deux côtés). Voir la documentation de Tcl_FSLink pour l'interprétation correcte des drapeaux de linkAction.

LISTVOLUMESPROC

Fonction pour lister tous les volumes du système de fichiers ajoutés par ce système de fichiers. Elle ne doit être implémentée que si le système de fichiers ajoute des volumes en tête du système de fichiers, afin qu'ils puissent être retournés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste de volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) s'il n'y a pas de volumes fournis. La valeur de retour est considérée comme appartenant au système de fichiers (pas au noyau Tcl), mais doit se voir attribuer un compteur de références pour Tcl. Tcl utilisera le contenu de la liste puis décrémentera ce compteur. Cela permet aux systèmes de fichiers de choisir s'ils souhaitent réellement maintenir une liste globale de volumes ou non (si ce n'est pas le cas, ils généreront la liste à la volée et la passeront à Tcl avec un compteur de références de 1, puis oublieront la liste ; si c'est le cas, ils incrémenteront simplement le compteur de références de leur liste globale et la passeront à Tcl, qui copiera le contenu puis décrémentera le compteur pour le ramener à son état initial).

Par conséquent, Tcl considère les valeurs de retour de cette proc comme étant en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne supportera pas la commande file attributes. Cela permet d'attacher des informations supplémentaires arbitraires aux fichiers du système de fichiers. Si elle n'est pas implémentée, il n'est pas nécessaire d'implémenter les méthodes get et set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La fonction peut retourner un tableau de chaînes, ou elle peut retourner NULL et placer une liste Tcl dans le objPtrRef fourni. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Après avoir terminé son utilisation, Tcl décrémentera son propre compteur de références. Par conséquent, si la liste doit être disposée par Tcl une fois qu'il a terminé, elle doit avoir un compteur de références de zéro, et si elle ne doit pas être disposée, le système de fichiers doit s'assurer qu'il retourne une valeur avec un compteur de références d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsGet, utilisé par file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Retourne un code de retour standard. La valeur de l'attribut récupéré, qui correspond à l'élément d'indice index dans la liste retournée par Tcl_FSFileAttrStringsProc, est placée dans objPtrRef (si TCL_OK a été retourné). Cette valeur aura probablement un compteur de références de zéro. Par conséquent, dans tous les cas, nous devons stocker cette valeur quelque part (par exemple, dans le résultat Tcl) ou incrémenter/décrémenter son compteur de références pour garantir qu'elle est correctement libérée.

FILEATTRSSETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsSet, utilisé par file attributes. Si le système de fichiers est en lecture seule, il n'est pas nécessaire de l'implémenter.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

La valeur de l'attribut de l'élément d'indice index dans la liste retournée par Tcl_FSFileAttrStringsProc doit être définie sur l'objet objPtr fourni.

CREATEDIRECTORYPROC

Fonction pour créer un répertoire dans le système de fichiers. Elle ne doit être implémentée que si le système de fichiers permet la création de répertoires, et dans le cas contraire, elle peut être NULL.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode);

La fonction crée un répertoire dans le système de fichiers spécifié par pathPtr avec le mode donné.

Tcl_FSCmd » Tcl_FS » Tcl_FSProvider » Tcl_FSUnion » Tcl_FSCreateDirectory » CREATEDIRECTORYPROC

CREATEDIRECTORYPROC

Function to process a Tcl_FSCreateDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, a new directory should have been added to the filesystem in the location specified by pathPtr.

REMOVEDIRECTORYPROC

Function to process a Tcl_FSRemoveDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the directory specified by pathPtr should have been removed from the filesystem. If the recursive flag is given, then a non-empty directory should be deleted without error. If this flag is not given, then and the directory is non-empty a POSIX “EEXIST” error should be signaled. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr.

DELETEFILEPROC

Function to process a Tcl_FSDeleteFile call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the file specified by pathPtr should have been removed from the filesystem. Note that, if the filesystem supports symbolic links, Tcl will always call this function and not Tcl_FSRemoveDirectoryProc when needed to delete them (even if they are symbolic links to directories).

FILESYSTEM EFFICIENCY

These functions need not be implemented for a particular filesystem because the core has a fallback implementation available. See each individual description for the consequences of leaving the field NULL.

LSTATPROC

Function to process a Tcl_FSLstat call. If not implemented, Tcl will attempt to use the statProc defined above instead. Therefore it need only be implemented if a filesystem can differentiate between stat and lstat calls.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

The behavior of this function is very similar to that of the Tcl_FSStatProc defined above, except that if it is applied to a symbolic link, it returns information about the link, not about the target file.

COPYFILEPROC

Function to process a Tcl_FSCopyFile call. If not implemented Tcl will fall back on open-r, open-w and fcopy as a copying mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. Note that, destPathPtr is the name of the file which should become the copy of srcPathPtr. It is never the name of a directory into which srcPathPtr could be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Note that, if the filesystem supports symbolic links, Tcl will always call this function and not copyDirectoryProc when needed to copy them (even if they are symbolic links to directories). Finally, if the filesystem determines it cannot support the file copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

RENAMEFILEPROC

Function to process a Tcl_FSRenameFile call. If not implemented, Tcl will fall back on a copy and delete mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the renaming process. If the filesystem determines it cannot support the file rename action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

COPYDIRECTORYPROC

Function to process a Tcl_FSCopyDirectory call. If not implemented, Tcl will fall back on a recursive file mkdir, file copy mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr. Note that, destPathPtr is the name of the directory-name which should become the mirror-image of srcPathPtr. It is not the name of a directory into which srcPathPtr should be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Finally, if the filesystem determines it cannot support the directory copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

LOADFILEPROC

Function to process a Tcl_FSLoadFile call. If not implemented, Tcl will fall back on a copy to native-temp followed by a Tcl_FSLoadFile on that temporary copy. Therefore it need only be implemented if the filesystem can load code directly, or it can be implemented simply to return TCL_ERROR to disable load functionality in this filesystem entirely.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Returns a standard Tcl completion code. If an error occurs, an error message is left in the interp's result. The function dynamically loads a binary code file into memory. On a successful load, the handlePtr should be filled with a token for the dynamically loaded file, and the unloadProcPtr should be filled in with the address of a procedure. The unload procedure will be called with the given Tcl_LoadHandle as its only parameter when Tcl needs to unload the file. For example, for the native filesystem, the Tcl_LoadHandle returned is currently a token which can be used in the private TclpFindSymbol to access functions in the new code. Each filesystem is free to define the Tcl_LoadHandle as it requires. Finally, if the filesystem determines it cannot support the file load action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

UNLOADFILEPROC

Function to unload a previously successfully loaded file. If load was implemented, then this should also be implemented, if there is any cleanup action required.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Function to process a Tcl_FSGetCwd call. Most filesystems need not implement this. It will usually only be called once, if getcwd is called before chdir. May be NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

If the filesystem supports a native notion of a current working directory (which might perhaps change independent of Tcl), this function should return that cwd as the result, or NULL if the current directory could not be determined (e.g. the user does not have appropriate permissions on the cwd directory). If NULL is returned, an error message is left in the interp's result.

CHDIRPROC

Function to process a Tcl_FSChdir call. If filesystems do not implement this, it will be emulated by a series of directory access checks. Otherwise, virtual filesystems which do implement it need only respond with a positive return result if the pathPtr is a valid, accessible directory in their filesystem. They need not remember the result, since that will be automatically remembered for use by Tcl_FSGetCwd. Real filesystems should carry out the correct action (i.e. call the correct system chdir API).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

The Tcl_FSChdirProc changes the applications current working directory to the value specified in pathPtr. The function returns -1 on error or 0 on success.
