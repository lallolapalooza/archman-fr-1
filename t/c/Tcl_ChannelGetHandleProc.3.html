DESCRIPTION

Tcl utilise une architecture de canaux à deux niveaux. Il fournit une couche générale pour permettre aux programmes C et Tcl d'effectuer des entrées et des sorties en utilisant les mêmes API pour divers fichiers, périphériques, sockets, etc. Les API C générales sont décrites dans l'entrée de manuel de Tcl_OpenFileChannel.

La couche inférieure fournit des pilotes de canaux spécifiques à chaque type de périphérique pris en charge sur chaque plateforme. Cette entrée de manuel décrit les API C qui communiquent entre la couche générale et les pilotes de canaux spécifiques. Elle explique également comment de nouveaux types de canaux peuvent être ajoutés en implémentant de nouveaux pilotes de canaux.

Les pilotes de canaux consistent en plusieurs composants : Premièrement, chaque pilote de canal fournit une structure Tcl_ChannelType qui contient des pointeurs vers des fonctions implémentant les diverses opérations utilisées par la couche générale pour communiquer avec le pilote de canal. La structure Tcl_ChannelType et les fonctions référencées par celle-ci sont décrites dans la section TCL_CHANNELTYPE, ci-dessous.

Deuxièmement, les pilotes de canaux fournissent généralement une commande Tcl pour créer des instances de ce type de canal. Par exemple, la commande Tcl open crée des canaux qui utilisent les pilotes de fichiers et de commandes, et la commande Tcl socket crée des canaux qui utilisent les protocoles réseau TCP.

Troisièmement, un pilote de canal fournit éventuellement une fonction C pour ouvrir des instances de ce type de canal. Par exemple, Tcl_OpenFileChannel ouvre un canal utilisant le pilote de fichier, et Tcl_OpenTcpClient ouvre un canal utilisant le protocole réseau TCP. Ces fonctions de création utilisent généralement Tcl_CreateChannel en interne pour ouvrir le canal.

Pour ajouter un nouveau type de canal, vous devez implémenter une API C ou une commande Tcl qui ouvre un canal en appelant Tcl_CreateChannel. Lorsque votre pilote appelle Tcl_CreateChannel, il passe une structure Tcl_ChannelType décrivant les procédures d'entrée et de sortie de votre pilote. La couche générale invoque ensuite les fonctions référencées dans cette structure pour effectuer des opérations sur le canal.

Tcl_CreateChannel ouvre un nouveau canal et lui associe typePtr et instanceData. Le canal est ouvert dans le mode indiqué par mask. Pour une discussion sur les pilotes de canaux, leurs opérations et la structure Tcl_ChannelType, voir la section TCL_CHANNELTYPE, ci-dessous.

Tcl_CreateChannel interagit avec le code qui gère les canaux standard. Une fois qu'un canal standard a été initialisé par un appel à Tcl_GetStdChannel ou un appel à Tcl_SetStdChannel, la fermeture de ce canal fera que le prochain appel à Tcl_CreateChannel créera le nouveau canal en tant que nouveau canal standard. Voir Tcl_StandardChannels pour un traitement général des canaux standard et le comportement de la bibliothèque Tcl à leur égard.

Tcl_GetChannelInstanceData renvoie les données d'instance associées au canal dans channel. Ceci est le même que l'argument instanceData dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelType renvoie un pointeur vers la structure Tcl_ChannelType utilisée par le canal dans l'argument channel. Ceci est le même que l'argument typePtr dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelName renvoie une chaîne contenant le nom associé au canal, ou NULL si l'argument channelName de Tcl_CreateChannel était NULL.

Tcl_GetChannelHandle place le handle du système d'exploitation associé à channel pour la direction donnée dans handlePtr.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

lieu spécifié par handlePtr et retourne TCL_OK. Si le canal n'a pas de descripteur de périphérique pour la direction spécifiée, alors TCL_ERROR est retourné à la place. Différents pilotes de canaux retourneront différents types de descripteurs. Référez-vous aux entrées du manuel pour chaque pilote afin de déterminer le type de descripteur retourné.

Tcl_GetChannelThread retourne l'identifiant du thread gérant actuellement le channel spécifié. Ceci permet aux pilotes de canaux d'envoyer leurs événements de fichiers à la file d'événements correcte, même pour un cœur multi-threadé.

Tcl_GetChannelMode retourne une combinaison OR-de TCL_READABLE et TCL_WRITABLE, indiquant si le canal est ouvert en lecture et/ou en écriture.

Tcl_GetChannelBufferSize retourne la taille, en octets, des tampons alloués pour stocker les entrées ou sorties dans le channel. Si la valeur n'a pas été définie par un appel antérieur à Tcl_SetChannelBufferSize, décrit ci-dessous, alors la valeur par défaut de 4096 est retournée.

Tcl_SetChannelBufferSize définit la taille, en octets, des tampons qui seront alloués lors des opérations ultérieures sur le canal pour stocker les entrées ou sorties. L'argument size doit être compris entre un et un million, permettant des tampons de un octet à un million d'octets. Si size est en dehors de cette plage, Tcl_SetChannelBufferSize définit la taille du tampon à 4096.

Tcl_NotifyChannel est appelée par un pilote de canal pour indiquer à la couche générique que les événements spécifiés par mask se sont produits sur le canal. Les pilotes de canaux sont responsables de l'invocation de cette fonction chaque fois que les gestionnaires de canaux doivent être appelés pour le canal (ou que d'autres tâches en attente, comme une vidange d'écriture, doivent être effectuées). Voir WATCHPROC ci-dessous pour plus de détails.

Tcl_BadChannelOption est appelée à partir du setOptionProc ou getOptionProc spécifique du pilote pour générer un message d'erreur complet.

Tcl_ChannelBuffered retourne le nombre d'octets d'entrée actuellement en tampon dans le tampon interne (zone de retour en arrière) du canal lui-même. Il ne rapporte pas les données dans les tampons globaux pour la pile de canaux dont le canal fourni fait partie.

Tcl_IsChannelShared vérifie le compteur de références du channel spécifié et retourne si le channel était partagé entre plusieurs interpréteurs (résultat == 1) ou non (résultat == 0).

Tcl_IsChannelRegistered vérifie si le channel spécifié est enregistré dans l'interpréteur donné (résultat == 1) ou non (résultat == 0).

Tcl_IsChannelExisting vérifie si un canal portant le nom spécifié est enregistré dans la liste globale (par thread) de tous les canaux (résultat == 1) ou non (résultat == 0).

Tcl_CutChannel retire le channel spécifié de la liste globale (par thread) de tous les canaux (du thread actuel). L'application à un canal toujours enregistré dans un interpréteur n'est pas autorisée. Notifie également le pilote si la version Tcl_ChannelType est TCL_CHANNEL_VERSION_4 (ou supérieure) et que Tcl_DriverThreadActionProc est définie pour celui-ci.

Tcl_SpliceChannel ajoute le channel spécifié à la liste globale (par thread) de tous les canaux (du thread actuel). L'application à un canal enregistré dans un interpréteur n'est pas autorisée. Notifie également le pilote si la version Tcl_ChannelType est TCL_CHANNEL_VERSION_4 (ou supérieure) et que Tcl_DriverThreadActionProc est définie pour celui-ci.

Tcl_ClearChannelHandlers retire tous les gestionnaires de canaux et les scripts d'événements associés au channel spécifié, arrêtant ainsi tout traitement d'événements pour ce canal.

TCL_CHANNELTYPE

Un pilote de canal fournit une structure Tcl_ChannelType qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un canal ; ces opérations sont appelées au besoin par la couche générique. La structure a été versionnée à partir de Tcl 8.3.2/8.4 pour corriger un problème avec les canaux empilés. Voir la section OLD CHANNEL TYPES ci-dessous pour plus de détails sur l'ancienne structure.

La structure Tcl_ChannelType contient les champs suivants :

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Il n'est pas nécessaire de fournir des implémentations pour toutes les opérations de canal. Celles qui ne sont pas nécessaires peuvent être mises à NULL dans la structure : blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc et close2Proc, en plus de flushProc, handlerProc, threadActionProc et truncateProc. D'autres fonctions qui ne peuvent pas être implémentées de manière significative devraient retourner EINVAL lorsqu'elles sont appelées, pour indiquer que les opérations qu'elles représentent ne sont pas disponibles. Notez également que wideSeekProc peut être NULL si seekProc l'est.

L'utilisateur ne devrait utiliser que la structure ci-dessus pour l'instanciation de Tcl_ChannelType. Lors de la référence aux champs d'une structure Tcl_ChannelType, les fonctions suivantes devraient être utilisées pour obtenir les valeurs : Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc ou Tcl_ChannelHandlerProc.

La modification des structures a été faite de manière à ce que les types de canaux standard soient binaires compatibles. Cependant, les types de canaux qui utilisent des canaux empilés (c'est-à-dire TLS, Trf) ont de nouvelles versions pour correspondre au changement ci-dessus, car le code précédent pour les canaux empilés avait des problèmes.

TYPENAME

Le champ typeName contient une chaîne terminée par null qui identifie le type de périphérique implémenté par ce pilote, par exemple, file ou socket.

Cette valeur peut être récupérée avec Tcl_ChannelName, qui retourne un pointeur vers la chaîne.

VERSION

Le champ version doit être défini sur la version de la structure dont vous avez besoin. TCL_CHANNEL_VERSION_2 est le minimum recommandé. TCL_CHANNEL_VERSION_3 doit être défini pour spécifier le membre wideSeekProc. TCL_CHANNEL_VERSION_4 doit être défini pour spécifier le membre threadActionProc (inclut wideSeekProc). TCL_CHANNEL_VERSION_5 doit être défini pour spécifier le membre truncateProc (inclut wideSeekProc et threadActionProc). S'il n'est défini sur aucune de ces valeurs, alors ce Tcl_ChannelType est supposé avoir la structure d'origine. Voir OLD CHANNEL TYPES pour plus de détails. Bien que Tcl reconnaisse et fonctionne avec les deux structures, les canaux empilés doivent être au moins de version TCL_CHANNEL_VERSION_2 pour fonctionner correctement.

Cette valeur peut être récupérée avec Tcl_ChannelVersion, qui retourne l'une des valeurs TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 ou TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

Le champ blockModeProc contient l'adresse d'une fonction appelée par la couche générique pour définir le mode bloquant et non bloquant sur le périphérique. BlockModeProc doit correspondre au prototype suivant :

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

instanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument mode est soit TCL_MODE_BLOCKING, soit TCL_MODE_NONBLOCKING pour définir le périphérique en mode bloquant ou non bloquant. La fonction doit retourner zéro si l'opération a réussi, ou un code d'erreur POSIX non nul si l'opération a échoué.

Si l'opération réussit, la fonction peut modifier le instanceData fourni pour enregistrer que le canal est entré en mode bloquant ou non bloquant et pour implémenter le comportement bloquant ou non bloquant. Pour certains types de périphériques, le comportement bloquant et non bloquant peut être implémenté par le système d'exploitation sous-jacent ; pour d'autres types de périphériques, le comportement doit être émulé dans le pilote de canal.

Cette valeur peut être récupérée avec Tcl_ChannelBlockModeProc, qui retourne un pointeur vers la fonction.

Un pilote de canal qui **ne** fournit **pas** de blockModeProc doit être très, très prudent. Il doit indiquer exactement à la couche générique quel mode de blocage lui convient, et cela doit également être documenté pour l'utilisateur afin que le mode de blocage du canal ne soit pas modifié à une valeur inacceptable. Toute confusion ici peut entraîner un interblocage (sans véritable cause et difficile à trouver) de l'interpréteur.

CLOSEPROC ET CLOSE2PROC

Le champ closeProc contient l'adresse d'une fonction appelée par la couche générique pour nettoyer les informations relatives au pilote lors de la fermeture du canal. CloseProc doit correspondre au prototype suivant :

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

L'argument instanceData est la même valeur que celle fournie à Tcl_CreateChannel lors de la création du canal. La fonction doit libérer toute mémoire conservée par le pilote de canal pour ce canal, et fermer les périphériques d'entrée et de sortie encapsulés par ce canal. Toutes les sorties en file d'attente auront été vidées vers le périphérique avant que cette fonction ne soit appelée, et aucune autre opération de pilote ne sera invoquée sur cette instance après l'appel de closeProc. Si l'opération de fermeture réussit, la procédure

Maintenir toute la structure du fichier. La procédure doit retourner zéro ; sinon, elle doit retourner un code d'erreur POSIX non nul. De plus, si une erreur se produit et que interp n'est pas NULL, la procédure doit stocker un message d'erreur dans le résultat de l'interpréteur. Alternativement, les canaux qui supportent la fermeture des parties lecture et écriture indépendamment peuvent définir closeProc à TCL_CLOSE2PROC et close2Proc à l'adresse d'une fonction correspondant au prototype suivant : ```c typedef int Tcl_DriverClose2Proc( ClientData instanceData, Tcl_Interp *interp, int flags); ``` Le close2Proc sera appelé avec flags défini comme un OR de TCL_CLOSE_READ ou TCL_CLOSE_WRITE, indiquant que le canal doit fermer la partie lecture et/ou écriture du canal. Le pilote de canal peut être invoqué pour effectuer des opérations supplémentaires sur le canal après que close2Proc ait fermé une ou les deux parties du canal. Si flags est 0 (zéro), le pilote doit fermer le canal selon le mode décrit ci-dessus pour closeProc. Aucune opération supplémentaire ne sera effectuée sur cette instance après que close2Proc ait été appelé avec tous les flags effacés. Dans tous les cas, le close2Proc doit retourner zéro si l'opération de fermeture a réussi, sinon il doit retourner un code d'erreur POSIX non nul. De plus, si une erreur se produit et que interp n'est pas NULL, la procédure doit stocker un message d'erreur dans le résultat de l'interpréteur. Les valeurs de closeProc et close2Proc peuvent être récupérées via Tcl_ChannelCloseProc ou Tcl_ChannelClose2Proc, qui renvoient un pointeur vers la fonction correspondante. --- **Section 2. Ss**

INPUTPROC

Le champ inputProc contient l'adresse d'une fonction appelée par la couche générale pour lire des données depuis le périphérique ou le fichier et les stocker dans un tampon interne. InputProc doit correspondre au prototype suivant : ```c typedef int Tcl_DriverInputProc( ClientData instanceData, char *buf, int bufSize, int *errorCodePtr); ``` InstanceData est la même que la valeur passée à Tcl_CreateChannel lors de la création du canal. L'argument buf pointe vers un tableau d'octets dans lequel les données d'entrée du périphérique seront stockées, et l'argument bufSize indique combien d'octets sont disponibles dans buf. L'argument errorCodePtr pointe vers une variable entière fournie par la couche générale. Si une erreur se produit, la fonction doit définir cette variable avec un code d'erreur POSIX qui identifie l'erreur. La fonction doit lire les données du périphérique encapsulé par le canal et les stocker dans buf. En cas de succès, elle doit retourner un nombre non négatif indiquant combien d'octets ont été lus depuis le périphérique et stockés dans buf. En cas d'erreur, elle doit retourner -1. Si une erreur se produit après que des données aient été lues depuis le périphérique, ces données seront perdues. Si inputProc peut déterminer que le périphérique a des données disponibles mais moins que ce qui est demandé par l'argument bufSize, la fonction doit tenter de lire uniquement la quantité de données disponible et retourner sans bloquer. Si le périphérique n'a pas de données disponibles et que le canal est en mode non bloquant, la fonction doit retourner une erreur EAGAIN. Si le périphérique n'a pas de données disponibles et que le canal est en mode bloquant, la fonction doit bloquer pour la durée la plus courte possible jusqu'à ce qu'au moins un octet puisse être lu depuis le périphérique, puis retourner le plus grand nombre d'octets possible sans bloquer. Cette valeur peut être récupérée via Tcl_ChannelInputProc, qui renvoie un pointeur vers la fonction. --- **Section 2. Ss**

OUTPUTPROC

Le champ outputProc contient l'adresse d'une fonction appelée par la couche générale pour transférer des données d'un tampon interne vers le périphérique de sortie. OutputProc doit correspondre au prototype suivant : ```c typedef int Tcl_DriverOutputProc( ClientData instanceData, const char *buf, int toWrite, int *errorCodePtr); ``` InstanceData est la même que la valeur passée à Tcl_CreateChannel lors de la création du canal. L'argument buf contient un tableau d'octets qui sera écrit sur le périphérique, et l'argument toWrite indique combien d'octets seront écrits à partir de l'argument buf. L'argument errorCodePtr pointe vers une variable entière fournie par la couche générale. Si une erreur se produit, la fonction doit définir cette variable avec un code d'erreur POSIX qui identifie l'erreur. La fonction doit écrire les données dans buf sur le périphérique de sortie encapsulé par le canal. En cas de succès, elle doit retourner un nombre non négatif indiquant combien d'octets ont été écrits sur le périphérique de sortie. La valeur retournée est normalement la même que toWrite, mais peut être inférieure dans certains cas, comme lorsque l'opération de sortie est interrompue par un signal. Si une erreur se produit, la fonction doit retourner -1. En cas d'erreur, certaines données peuvent avoir été écrites sur le périphérique. Si le canal est en mode non bloquant et que le périphérique ne peut absorber aucune donnée, la fonction doit retourner -1 avec une erreur EAGAIN sans écrire aucune donnée. Cette valeur peut être récupérée via Tcl_ChannelOutputProc, qui renvoie un pointeur vers la fonction. --- **Section 2. Ss**

SEEKPROC ET WIDESEEKPROC

Le champ seekProc contient l'adresse d'une fonction appelée par la couche générale pour déplacer le point d'accès auquel les prochaines opérations d'entrée ou de sortie seront appliquées. SeekProc doit correspondre au prototype suivant : ```c typedef int Tcl_DriverSeekProc( ClientData instanceData, long offset, int seekMode, int *errorCodePtr); ``` L'argument instanceData est le même que la valeur passée à Tcl_CreateChannel lors de la création de ce canal. Offset et seekMode ont la même signification que dans la fonction Tcl_Seek (décrite dans le manuel de Tcl_OpenFileChannel). L'argument errorCodePtr pointe vers une variable entière fournie par la couche générale pour renvoyer les valeurs errno de la fonction. La fonction doit définir cette variable avec un code d'erreur POSIX si une erreur se produit. La fonction doit stocker un code d'erreur EINVAL si le type de canal n'implémente pas le positionnement. La valeur retournée est le nouveau point d'accès ou -1 en cas d'erreur. Si une erreur se produit, la fonction ne doit pas déplacer le point d'accès. S'il y a un champ non NULL de seekProc, le champ wideSeekProc peut contenir l'adresse d'une fonction alternative qui gère les décalages (c'est-à-dire plus grands que 32 bits), permettant des positions dans des fichiers supérieurs à 2 Go. Le wideSeekProc est appelé de préférence au seekProc, mais les deux doivent être définis si le wideSeekProc est défini. WideSeekProc doit correspondre au prototype suivant : ```c typedef Tcl_WideInt Tcl_DriverWideSeekProc( ClientData instanceData, Tcl_WideInt offset, int seekMode, int *errorCodePtr); ``` Les arguments et les valeurs retournées sont les mêmes que pour seekProc, sauf que le type de décalage et le type retourné sont différents. La valeur de seekProc peut être récupérée via Tcl_ChannelSeekProc, qui renvoie un pointeur vers la fonction, et la valeur de wideSeekProc peut être récupérée via Tcl_ChannelWideSeekProc. --- **Section 2. Ss**

SETOPTIONPROC

Le champ setOptionProc contient l'adresse d'une fonction appelée par la couche générale pour définir une option spécifique au type de canal sur un canal. setOptionProc doit correspondre au prototype suivant : ```c typedef int Tcl_DriverSetOptionProc( ClientData instanceData, Tcl_Interp *interp, const char *optionName, const char *newValue); ``` optionName est le nom d'une option à définir, et newValue est la nouvelle valeur de cette option, sous forme de chaîne. instanceData est la même que la valeur passée à Tcl_CreateChannel lors de la création de ce canal. La fonction doit effectuer toute action spécifique au type de canal nécessaire pour implémenter la nouvelle valeur de l'option. Certaines options sont gérées par la couche générale et cette fonction n'est pas appelée pour les définir, par exemple, -blockmode. Les options spécifiques à chaque type de canal sont implémentées par la procédure setOptionProc du pilote du canal. Le champ setOptionProc peut être NULL, ce qui indique que ce type de canal ne supporte pas d'options spécifiques. Si la valeur de l'option est correctement modifiée à sa nouvelle valeur, la fonction retourne TCL_OK. Elle doit appeler Tcl_BadChannelOption, qui retourne TCL_ERROR si le optionName n'est pas reconnu. Si newValue spécifie une valeur non supportée ou si une erreur se produit lors d'un appel système, la fonction doit laisser un message d'erreur dans le résultat de interp si interp n'est pas NULL. La fonction doit également appeler Tcl_SetErrno pour stocker un code d'erreur POSIX approprié. Cette valeur peut être récupérée via Tcl_ChannelSetOptionProc, qui renvoie un pointeur vers la fonction. --- **Section 2. Ss**

GETOPTIONPROC

Le champ getOptionProc contient l'adresse d'une fonction appelée par la couche générale pour obtenir la valeur d'une option spécifique au type de canal sur un canal. getOptionProc doit correspondre au prototype suivant : ```c typedef int Tcl_DriverGetOptionProc( ClientData instanceData, Tcl_Interp *interp, const char *optionName, Tcl_DString *optionValue); ``` OptionName est le nom d'une option supportée par ce type de canal. Si le nom de l'option n'est pas NULL, la fonction stocke sa valeur actuelle (sous forme de chaîne) dans la chaîne dynamique Tcl optionValue. Si optionName est NULL, la fonction stocke dans optionValue une liste alternative de toutes les options supportées et de leurs valeurs actuelles. En cas de succès, la fonction retourne TCL_OK. Elle doit appeler Tcl_BadChannelOption, qui retourne TCL_ERROR si le optionName n'est pas reconnu. Si newValue spécifie une valeur non supportée ou si une erreur se produit lors d'un appel système, la fonction doit laisser un message d'erreur dans le résultat de interp si interp n'est pas NULL. La fonction doit également appeler Tcl_SetErrno pour stocker un code d'erreur POSIX approprié. Cette valeur peut être récupérée via Tcl_ChannelGetOptionProc, qui renvoie un pointeur vers la fonction.

WATCHPROC

Le champ watchProc contient l'adresse d'une fonction appelée par la couche générale pour initialiser le mécanisme de notification des événements d'intérêt sur ce canal. WatchProc doit correspondre au prototype suivant :

typedef void Tcl_DriverWatchProc(
        ClientData instanceData,
        int mask);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument mask est une combinaison OU de TCL_READABLE, TCL_WRITABLE et TCL_EXCEPTION ; il indique les événements pour lesquels l'appelant souhaite être notifié sur ce canal.

La fonction doit initialiser les mécanismes spécifiques au type de périphérique pour notifier lorsqu'un événement d'intérêt est présent sur le canal. Lorsque un ou plusieurs des événements désignés se produisent sur le canal, le pilote de canal doit appeler Tcl_NotifyChannel pour informer le module général de canal. Le pilote doit éviter de bloquer d'autres pilotes de canal ou sources de callbacks en appelant Tcl_NotifyChannel trop fréquemment. L'équité peut être assurée en utilisant la file d'attente d'événements de Tcl pour permettre à l'événement de canal d'être mis en file d'attente séquentiellement avec d'autres événements. Voir la description de Tcl_QueueEvent pour plus de détails sur la mise en file d'attente d'un événement.

Cette valeur peut être récupérée avec Tcl_ChannelWatchProc, qui renvoie un pointeur vers la fonction.

GETHANDLEPROC

Le champ getHandleProc contient l'adresse d'une fonction appelée par la couche générale pour récupérer un handle de canal spécifique. GetHandleProc doit correspondre au prototype suivant :

typedef int Tcl_DriverGetHandleProc(
        ClientData instanceData,
        int direction,
        ClientData *handlePtr);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument direction est TCL_READABLE pour récupérer le handle utilisé pour l'entrée, ou TCL_WRITABLE pour récupérer le handle utilisé pour la sortie.

Si l'implémentation du canal a des handles spécifiques, la fonction doit récupérer le handle approprié en fonction de l'argument direction. Le handle doit être stocké à l'emplacement référencé par handlePtr, et TCL_OK doit être renvoyé. Si le canal n'est pas ouvert pour la direction spécifiée, ou si l'implémentation du canal n'utilise pas de handles spécifiques, la fonction doit renvoyer TCL_ERROR.

Cette valeur peut être récupérée avec Tcl_ChannelGetHandleProc, qui renvoie un pointeur vers la fonction.

FLUSHPROC

Le champ flushProc est réservé pour une utilisation future et doit être défini à NULL. FlushProc doit correspondre au prototype suivant :

typedef int Tcl_DriverFlushProc(
        ClientData instanceData);

Cette valeur peut être récupérée avec Tcl_ChannelFlushProc, qui renvoie un pointeur vers la fonction.

HANDLERPROC

Le champ handlerProc contient l'adresse d'une fonction appelée par la couche générale pour notifier au canal qu'un événement s'est produit. Il doit être défini pour les pilotes de canal empilés qui souhaitent être notifiés des événements se produisant sur le canal (empilé). HandlerProc doit correspondre au prototype suivant :

typedef int Tcl_DriverHandlerProc(
        ClientData instanceData,
        int interestMask);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument interestMask est une combinaison OU de TCL_READABLE ou TCL_WRITABLE ; il indique le type d'événement qui s'est produit sur ce canal.

Cette valeur peut être récupérée avec Tcl_ChannelHandlerProc, qui renvoie un pointeur vers la fonction.

THREADACTIONPROC

Le champ threadActionProc contient l'adresse de la fonction appelée par la couche générale lorsqu'un canal est créé, fermé, ou est sur le point d'être déplacé vers un autre thread, c'est-à-dire lorsque l'état spécifique au thread du pilote peut avoir été initialisé ou mis à jour. Il peut être NULL. L'action TCL_CHANNEL_THREAD_REMOVE est utilisée pour notifier au pilote qu'il doit mettre à jour ou supprimer toute donnée spécifique au thread qu'il pourrait détenir pour le canal.

L'action TCL_CHANNEL_THREAD_INSERT est utilisée pour notifier au pilote qu'il doit mettre à jour ou initialiser toute donnée spécifique au thread qu'il pourrait détenir en utilisant le thread actuel comme associé. Voir Tcl_CutChannel et Tcl_SpliceChannel pour plus de détails.

typedef void Tcl_DriverThreadActionProc(
        ClientData instanceData,
        int action);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal.

Ces valeurs peuvent être récupérées avec Tcl_ChannelThreadActionProc, qui renvoie un pointeur vers la fonction.

TRUNCATEPROC

Le champ truncateProc contient l'adresse de la fonction appelée par la couche générale lorsqu'un canal est tronqué à une longueur spécifiée. Il peut être NULL.

typedef int Tcl_DriverTruncateProc(
        ClientData instanceData,
        Tcl_WideInt length);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal, et length est la nouvelle longueur du fichier sous-jacent, qui ne doit pas être négative. Le résultat doit être 0 en cas de succès ou un code d'erreur (approprié pour être utilisé avec Tcl_SetErrno) en cas d'échec.

Ces valeurs peuvent être récupérées avec Tcl_ChannelTruncateProc, qui renvoie un pointeur vers la fonction.

TCL_BADCHANNELOPTION

Cette procédure génère un message d'erreur "bad option" dans un interpréteur (optionnel). Elle est utilisée par les pilotes de canal lorsqu'une option Set/Get invalide est demandée. Son but est de concaténer la liste des options génériques à la liste spécifique et de factoriser le message d'erreur des options génériques.

Retourne toujours TCL_ERROR.

Un message d'erreur est généré dans la valeur du résultat de interp pour indiquer qu'une commande a été appelée avec une option invalide. Le message a la forme :

    mauvaise option "blah" : devrait être l'un des
    <...options génériques...>+<...options spécifiques...>
par exemple : 
    mauvaise option "-blah" : devrait être l'un des -blocking,
    -buffering, -buffersize, -eofchar, -translation,
    -peername, ou -sockname
lorsqu'elle est appelée avec optionList égal à "peername sockname".

"blah" est l'argument optionName et " <options spécifiques>" est une liste d'options spécifiques séparées par des espaces. La fonction s'occupe d'insérer des traits d'union devant chaque option, des virgules après, et un "ou" avant la dernière option.

ANCIENS TYPES DE CANAUX

La structure originale (8.3.1 et versions antérieures) Tcl_ChannelType contient les champs suivants :

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
} Tcl_ChannelType;

Il est toujours possible de créer un canal avec la structure précédente. Le code interne du canal déterminera la version. Il est essentiel d'utiliser la nouvelle structure Tcl_ChannelType si vous créez un pilote de canal empilé, en raison de problèmes avec l'implémentation précédente des canaux empilés (8.2.0 à 8.3.1).

Avant 8.4.0 (c'est-à-dire pendant les versions ultérieures de 8.3 et une partie précoce du cycle de développement de 8.4), la structure Tcl_ChannelType comportait les champs suivants :

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_ChannelTypeVersion version;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Lorsque la structure précédente est enregistrée en tant que type de canal, le champ version doit toujours être TCL_CHANNEL_VERSION_2.
