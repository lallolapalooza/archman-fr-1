DESCRIPTION

Il y a plusieurs raisons pour lesquelles les fonctions de l'API Tcl_FS (par exemple, Tcl_FSAccess et Tcl_FSStat) sont appelées plutôt que des appels directs aux fonctions système comme access et stat. Premièrement, ces fonctions fonctionneront sur toutes les plateformes, de sorte qu'une extension qui appelle ces fonctions devrait fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation de certaines de ces fonctions sous Windows corrige certains bugs dans les appels système. Troisièmement, ces appels de fonctions gèrent toute conversion de chemins de type UTF-8 vers natif qui pourrait être nécessaire (et peuvent mettre en cache les résultats de telles conversions pour une efficacité accrue lors d'appels ultérieurs). Quatrièmement, et probablement le plus important, toutes ces fonctions sont « conscientes des fichiers virtuels ». Tout système de fichiers virtuel (VFS en abrégé) enregistré (via Tcl_FSRegister) peut rediriger l'accès aux fichiers vers des médias ou des méthodes alternatifs. Cela signifie que toutes ces fonctions (et donc les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent fonctionner sur des fichiers qui ne sont pas des fichiers natifs sur le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS en abrégé) via cette API est automatiquement « consciente des fichiers virtuels ». Bien sûr, si une extension accède directement au système de fichiers natif (via des API spécifiques à la plateforme), alors Tcl ne peut pas intercepter de tels appels.

Si des VFS ont été correctement enregistrés, les « fichiers » peuvent être distants (par exemple, situés sur un serveur FTP distant) ou archivés (par exemple, situés à l'intérieur d'un fichier .zip). De tels systèmes de fichiers enregistrés fournissent une table de fonctions pour implémenter tout ou partie de la fonctionnalité mentionnée ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat abstraient ce qui est réellement déclaré comme struct stat dans le tampon, permettant d'utiliser le même code sur des systèmes avec et sans prise en charge de fichiers de plus de 2 Go.

L'API Tcl_FS est « typée » en Tcl_Obj et peut mettre en cache des représentations internes et d'autres chaînes liées aux chemins (par exemple, le répertoire courant). Un effet secondaire de cela est que des valeurs avec un compteur de références nul ne peuvent pas être passées à l'une quelconque de ces fonctions. Si de tels appels étaient gérés, ils pourraient causer des fuites de mémoire (dans certains cas, le code du système de fichiers pourrait ignorer une référence à la valeur passée et ainsi, on ne supposerait pas qu'après tout appel à ces fonctions, la valeur ait un compteur de références nul - elle pourrait avoir été incrémentée). Ou, ils pourraient causer un échec de segmentation (ou une autre erreur d'accès à la mémoire) car la valeur serait libérée pendant la manipulation complexe des valeurs pour s'assurer que le chemin est normalisé et absolu pour le système de fichiers. La leçon pratique à retenir de ceci est que :

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect et pourrait causer des erreurs de mémoire. Le path doit incrémenter son compteur de références avant d'être passé, ou le décrémenter. Pour cette raison, les valeurs avec un compteur de références nul sont considérées comme invalides en tant que chemins de système de fichiers et tout appel à une fonction de l'API Tcl_FS avec une telle valeur n'entraînera aucune action.

FONCTIONS DE L'API Tcl_FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés se trouvent sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la méthode de copie de fichier du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la valeur de errno globale C à EXDEV (code POSIX indiquant un lien croisé).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés se trouvent sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la méthode de copie de répertoire du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la valeur de errno globale C à EXDEV (code POSIX indiquant un lien croisé).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la méthode de création de répertoire du système de fichiers qui le possède.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la méthode de suppression de fichier du système de fichiers qui le possède.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la méthode de suppression de répertoire du système de fichiers qui le possède.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés se trouvent sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la méthode de renommage de fichier du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la valeur de errno globale C à EXDEV (code POSIX indiquant un lien croisé).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une méthode list volumes non nulle et demande à ces systèmes de renvoyer leur liste de volumes racine. Il accumule les valeurs renvoyées dans une liste qui est renvoyée à l'appelant (avec un compteur de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant le codage identifié par encodingName et évalue son contenu comme un script Tcl. Il renvoie les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, le codage du système est utilisé pour lire le contenu du fichier. Si le fichier n'a pas pu être lu, une erreur Tcl décrivant pourquoi le fichier n'a pas pu être lu est renvoyée. Le caractère de fin de fichier pour les fichiers est \x1A (^Z) pour tous les systèmes. Si vous souhaitez utiliser ^Z dans le code pour des comparaisons de chaînes, vous pouvez utiliser \x1A, qui sera très probablement substitué par l'interpréteur Tcl à ^Z. Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx, qui utilise toujours le codage du système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier binaire en mémoire et renvoie les adresses de deux procédures dans le fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr est appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne l'implémenteront pas en raison des limitations du système d'exploitation pour charger du code binaire), Tcl tentera de copier le fichier vers un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile annule cette opération, demandant que la bibliothèque indiquée par loadHandle soit déchargée du processus. Notez que, contrairement à la commande unload, cela ne donne aucune possibilité à la bibliothèque de faire du nettoyage.

Les deux fonctions ci-dessus renvoient un code d'achèvement standard de Tcl. Si une erreur se produit, un message d'erreur est laissé dans le résultat de interp.

Le jeton fourni par la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher tous les fichiers correspondant à un modèle donné dans un répertoire. La fonction appropriée pour le système de fichiers auquel appartient pathPtr est appelée.

La valeur renvoyée est un résultat standard de Tcl indiquant si une erreur s'est produite pendant le globbing. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr fourni.

Note : Le code glob implémente des modèles récursifs en interne, de sorte que cette fonction ne recevra que des modèles simples, qui peuvent être mis en correspondance en utilisant la logique de string match. Pour gérer la récursivité, Tcl appellera cette fonction fréquemment en demandant uniquement aux répertoires de renvoyer. Un cas spécial est d'être appelé avec un modèle nul indiquant que le chemin doit être vérifié uniquement pour le bon type.

Tcl_FSLink remplace la version de la bibliothèque de readlink et l'étend pour prendre en charge la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr est appelée.

Si toPtr est NULL, une action de « lecture de lien » est effectuée. Le résultat est un objet Tcl spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient entièrement à l'appelant, qui doit appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl doit créer un lien d'un des types passés dans le drapeau linkAction. Ce drapeau est une combinaison OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'il existe un choix (c'est-à-dire que plus d'un drapeau est spécifié), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur renvoyée doit être toPtr (qui appartient donc déjà à l'appelant). Si la création échoue, NULL est renvoyé.

Tcl_FSLstat remplit la structure Tcl_StatBuf avec des informations sur le fichier spécifié par statPtr. Vous n'avez pas besoin des permissions d'accès au fichier pour obtenir ces informations, mais vous avez besoin des permissions de parcours pour chaque répertoire mentionné dans le chemin d'accès au fichier. La structure Tcl_StatBuf contient des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), le rdev (identique au périphérique sous Windows), la taille, le dernier accès

Si le *path* existe, **Tcl_FSLstat** retourne 0 et la structure *statPtr* est remplie de données. Sinon, elle retourne -1 et aucune information de statistique n'est fournie. **Tcl_FSUtime** remplace la version de la bibliothèque *utime*. Elle retourne 0 en cas de succès et -1 en cas d'erreur (comme décrit dans le document **utime**). En cas de succès, elle met à jour les valeurs *atime* et *mtime* du fichier donné. **Tcl_FSFileAttrsGet** implémente l'accès en lecture pour le sous-commande **file attributes** de la commande hookable **file**. La fonction appropriée pour le système de fichiers auquel appartient *pathPtr* est appelée. Si le résultat est **TCL_OK**, une valeur est placée dans *objPtrRef*, qui ne sera valide que temporairement (jusqu'à ce que **Tcl_IncrRefCount** soit appelée). **Tcl_FSFileAttrsSet** implémente l'accès en écriture pour le sous-commande **file attributes** de la commande hookable **file**. La fonction appropriée pour le système de fichiers auquel appartient *pathPtr* est appelée. **Tcl_FSFileAttrStrings** implémente une partie du sous-commande **file attributes** de la commande hookable **file**. La fonction appropriée pour le système de fichiers auquel appartient *pathPtr* est appelée. La procédure appelée peut retourner un tableau de chaînes ou, alternativement, retourner NULL et placer une liste Tcl dans *objPtrRef*. Tcl prendra cette liste, incrémentera sa référence avant de l'utiliser. Lorsqu'elle aura fini de l'utiliser, elle décrémentera sa référence. Par conséquent, si la liste doit être libérée par Tcl lorsqu'elle aura terminé, elle doit avoir un compteur de références de zéro, et si elle ne doit pas être libérée, le système de fichiers doit s'assurer de maintenir un compteur de références sur la valeur. **Tcl_FSAccess** vérifie si le processus serait autorisé à lire, écrire ou tester l'existence d'un fichier (ou d'un objet système de fichiers) dont le nom est *pathname*. Si *pathname* est un lien symbolique sous Unix, les permissions du fichier référencé par ce lien symbolique sont testées. En cas de succès (toutes les permissions demandées), retourne 0. En cas d'erreur (au moins un bit dans le mode demandé est refusé ou une autre erreur se produit), retourne -1. **Tcl_FSStat** remplit la structure *Tcl_StatBuf* avec des informations sur le fichier spécifié. Aucun droit d'accès au fichier n'est requis pour obtenir ces informations, mais des droits de recherche sont requis sur tous les répertoires mentionnés dans le chemin vers le fichier. La structure *Tcl_StatBuf* inclut des informations sur le périphérique, l'inode (0 sous Windows), le mode de privilège, le nombre de liens (1 sous Windows), l'ID utilisateur (0 sous Windows), l'ID groupe (0 sous Windows), le rdev (identique au périphérique sous Windows), la taille, le dernier temps d'accès, le dernier temps de modification et le dernier temps de changement de métadonnées. Voir **PORTABLE STAT RESULT API** pour une description de la façon d'écrire du code portable pour attribuer et accéder à la structure *Tcl_StatBuf*. Si *path* existe, **Tcl_FSStat** retourne 0 et la structure *statPtr* est remplie de données. Sinon, elle retourne -1 et aucune information de statistique n'est fournie. **Tcl_FSOpenFileChannel** ouvre un fichier spécifié par *pathPtr* et retourne un handle de canal qui peut être utilisé pour effectuer des opérations de lecture et d'écriture sur le fichier. Cette API est similaire à la fonction **fopen** de la bibliothèque d'entrée/sortie standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande **open** de Tcl lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, **Tcl_FSOpenFileChannel** retourne NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec **Tcl_GetErrno**. De plus, si *interp* n'est pas NULL, **Tcl_FSOpenFileChannel** laisse un message d'erreur dans le résultat de *interp* après toute erreur. Le nouveau canal n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, il faut utiliser **Tcl_RegisterChannel**. Si l'un des canaux standard, **stdin**, **stdout** ou **stderr**, avait été précédemment fermé, l'action de création du nouveau canal l'assigne également en remplacement des canaux standard. **Tcl_FSGetCwd** remplace la version de la bibliothèque **getcwd**. Retourne le répertoire de travail actuel de la bibliothèque Tcl. Celui-ci peut être différent du répertoire de travail natif, ce qui se produit lorsque le répertoire de travail actuel n'est pas dans le système de fichiers natif. Le résultat est un pointeur vers un objet Tcl spécifiant le répertoire actuel, ou NULL si le répertoire ne peut pas être déterminé. Si NULL est retourné, un message d'erreur est laissé dans le résultat de *interp*. Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, il doit être décrémenté. Ceci est nécessaire pour la sécurité multithread, afin que plusieurs threads puissent accéder à cette fonction et aux fonctions connexes, tout en garantissant que les résultats sont toujours valides. **Tcl_FSChdir** remplace la version de la bibliothèque **chdir**. Le chemin est normalisé et passé au système de fichiers qui le revendique. Si le système de fichiers n'implémente pas cette fonction, Tcl se rabat sur une combinaison de **stat** et **access** pour vérifier si le répertoire existe et a les permissions appropriées. Pour les résultats, voir le document **chdir**. En cas de succès, un enregistrement du chemin réussi est conservé dans *cwdPathPtr* pour les appels ultérieurs à **Tcl_FSGetCwd**. **Tcl_FSPathSeparator** retourne le caractère séparateur pour l'élément le plus spécifique du chemin spécifié par *pathPtr* (c'est-à-dire la dernière partie du chemin). Le séparateur est retourné sous forme d'objet Tcl contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est retourné. **Tcl_FSJoinPath** prend l'objet Tcl donné, qui doit être une liste valide (pouvant avoir un compteur de références de zéro), et retourne la valeur du chemin en considérant les *elements* premiers éléments comme des segments de chemin valides (chaque segment peut être un chemin absolu, un chemin partiel ou simplement un nom de répertoire ou de fichier). Si un segment est effectivement un chemin absolu, tous les segments précédents sont écartés. Si *elements* est inférieur à 0, l'entier complet est utilisé. Il est possible que la valeur retournée soit en fait un élément de la liste donnée, l'utilisateur doit donc veiller à incrémenter le compteur de références du résultat avant de libérer la liste. La valeur retournée, typiquement avec un compteur de références de zéro (mais peut être partagée dans certaines conditions), contient le chemin joint. L'utilisateur doit ajouter un compteur de références à la valeur avant de l'utiliser. En particulier, la valeur retournée peut être un élément de la liste donnée, de sorte que la libération de la liste pourrait libérer prématurément la valeur si aucun compteur de références n'a été pris. Si le nombre d'éléments est zéro, la valeur retournée sera une chaîne vide Tcl_Obj. **Tcl_FSSplitPath** prend l'objet Tcl donné, qui doit être un chemin valide, et retourne une valeur Tcl liste avec chaque segment du chemin comme élément. Elle retourne une valeur liste avec un compteur de références de zéro. Si le *lenPtr* passé n'est pas NULL, la variable qu'il pointe sera mise à jour pour contenir le nombre d'éléments dans la valeur retournée. **Tcl_FSEqualPaths** teste si les deux chemins donnés représentent le même objet système de fichiers. Retourne 1 s'ils sont égaux, 0 s'ils sont différents. Si l'un des chemins est NULL, retourne toujours 0. **Tcl_FSGetNormalizedPath** tente d'extraire du chemin donné une représentation normalisée unique, dont la valeur chaîne peut être utilisée comme identifiant unique pour le fichier. Retourne le chemin normalisé, détenu par Tcl, ou NULL si le chemin était invalide ou n'a pas pu être converti correctement. L'extraction des chemins absolus et normalisés est très efficace (car le système de fichiers opère en interne sur ces représentations), bien que le résultat lorsqu'un système de fichiers contient de nombreux liens symboliques ne sera pas la version la plus conviviale d'un chemin. La valeur retournée est détenue par Tcl et a une durée de vie équivalente à celle de *pathPtr* passé (sauf s'il s'agit d'un chemin relatif, auquel cas la valeur normalisée peut être libérée à chaque changement du cwd) - l'utilisateur peut incrémenter le compteur de références s'il le souhaite pour conserver une copie plus longue. **Tcl_FSJoinToPath** prend la valeur donnée, qui doit généralement être un chemin valide ou NULL, et joint les chemins de segments donnés. Retourne une valeur, typiquement avec un compteur de références de zéro (mais peut être partagée dans certaines conditions), qui contient le chemin joint. L'utilisateur doit ajouter un compteur de références à la valeur avant de l'utiliser. Si l'une des valeurs passées à cette fonction (*pathPtr* ou éléments *path*) a un compteur de références de zéro, elle sera libérée lorsque cette fonction retournera. **Tcl_FSConvertToPathType** tente de convertir l'objet Tcl donné en un type de chemin valide, en tenant compte du fait que le cwd pourrait avoir changé même si cette valeur est déjà du bon type. Le nom du fichier peut commencer par ~ (pour indiquer le répertoire utilisateur courant) ou ~ (pour indiquer le répertoire de n'importe quel utilisateur). Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide sur l'un des systèmes de fichiers actuels), retourne **TCL_OK**. Sinon, retourne **TCL_ERROR**, et peut laisser un message d'erreur dans l'interpréteur. **Tcl_FSGetInternalRep** extrait la représentation interne d'une valeur de chemin donnée, dans le système de fichiers donné. Si la valeur du chemin appartient à un système de fichiers différent, elle retourne NULL. Si la représentation interne actuelle est NULL, elle essaie de la générer en appelant **Tcl_FSCreateInternalRepProc** du système de fichiers. Retourne NULL ou une représentation valide du chemin interne. Cette représentation interne est mise en cache, de sorte que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. **Tcl_FSGetTranslatedPath** tente d'extraire un chemin traduit de l'objet Tcl donné. Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), la valeur est retournée. Sinon, NULL est retourné, et un message d'erreur peut être laissé dans l'interpréteur. Un chemin traduit est un chemin qui ne contient pas de ~ ou de ~utilisateur (ceux-ci ont été développés en leur représentation courante dans le système de fichiers). La valeur retournée appartient à l'utilisateur, qui doit soit la stocker, soit appeler **Tcl_DecrRefCount** pour s'assurer que la mémoire est libérée. Cette fonction est d'une utilité pratique limitée, et **Tcl_FSGetNormalizedPath** ou **Tcl_FSGetNativePath** sont des fonctions plus appropriées pour la plupart des cas. **Tcl_FSGetTranslatedStringPath** fait la même chose que **Tcl_FSGetTranslatedPath**, mais retourne une chaîne ou NULL. La chaîne retournée est allouée dynamiquement et propriété de l'appelant, qui doit la stocker ou appeler ckfree pour s'assurer qu'elle est libérée. Encore une fois, Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des usages.

Tcl_FSNewNativePath effectue quelque chose comme l'inverse des conversions usuelles obj->path->nativerep. Si un code récupère un chemin sous forme native (par exemple, de readlink ou d'une boîte de dialogue native), et que ce chemin doit être utilisé au niveau Tcl, alors appeler cette fonction est un moyen efficace de créer le type de valeur de chemin approprié.

La valeur résultante est une valeur de type "chemin" pure, qui ne recevra une représentation de chaîne UTF-8 que si cela est requis par un code Tcl quelconque.

Tcl_FSGetNativePath est destiné à être utilisé par les systèmes de fichiers natifs Win/Unix, afin qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un wrapper de commodité autour de Tcl_FSGetInternalRep. Il pourrait être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes (par exemple, sur macOS, une représentation utilisant une structure FSRef de fileSpec serait probablement plus efficace). Sous Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Actuellement, la représentation est simplement une chaîne de caractères qui peut contenir soit le chemin relatif, soit un chemin absolu normalisé complet dans l'encodage natif (des conditions complexes dictent lequel de ceux-ci sera fourni, donc aucun ne peut être garanti, sauf si le chemin est connu pour être absolu). Si vous avez besoin d'un chemin natif qui doit être absolu, vous devriez demander la version native d'un chemin normalisé. Si, pour une raison quelconque, une version du chemin non absolue et non normalisée est nécessaire, elle doit être construite séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache de sorte que les appels répétés à cette fonction n'entraînent pas de conversions supplémentaires. La valeur de retour est la propriété de Tcl et a une durée de vie équivalente à celle du pathPtr passé (sauf si il s'agit d'un chemin relatif, auquel cas la représentation native peut être libérée à tout moment lorsque le cwd change).

Tcl_FSFileSystemInfo renvoie une liste de deux éléments. Le premier élément est le nom du système de fichiers (par exemple, "native", "vfs", "zip", ou "prowrap", peut-être), et le second est le type particulier du chemin donné dans ce système de fichiers (qui dépend du système de fichiers). Le second élément peut être vide si le système de fichiers ne fournit pas de catégorisation supplémentaire des fichiers.

Une valeur de liste valide est renvoyée, sauf si la valeur du chemin n'est pas reconnue, auquel cas NULL sera renvoyé.

Tcl_FSGetFileSystemForPath renvoie un pointeur vers le Tcl_Filesystem qui accepte ce chemin comme valide.

Si aucun système de fichiers n'accepte le chemin, NULL est renvoyé.

Tcl_FSGetPathType détermine si le chemin donné est relatif au répertoire courant, relatif au volume courant, ou absolu.

Il renvoie l'une des valeurs TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, ou TCL_PATH_VOLUME_RELATIVE

L'API DU SYSTÈME DE FICHIERS VIRTUEL

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un système de fichiers ; ces opérations sont appelées au besoin par la couche générique, ce qui se produit généralement par le biais des fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un morceau de données optionnel à associer à ce système de fichiers. Lors de l'appel de cette fonction, Tcl attachera le système de fichiers à la liste des systèmes de fichiers connus, et il deviendra pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera renvoyé.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et renvoie TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est renvoyé.

Tcl_FSData renverra le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il renverra NULL.

Tcl_FSMountsChanged est utilisé pour informer le noyau de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (presque toutes doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni) et fonctions d'efficacité (qui ne doivent être implémentées que si elles peuvent être réalisées efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces remplacements ne sont utilisés que pour gérer les commandes initiées dans Tcl, pas dans C. Cela signifie que si une commande file rename est émise dans Tcl, et que le(s) système(s) de fichiers pertinent(s) n'implémente(nt) pas leur Tcl_FSRenameFileProc, le noyau de Tcl se rabattra alors sur une combinaison d'autres fonctions du système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y aura un nouveau remplacement). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun remplacement de ce type ne se produit. Ceci est vrai sauf pour les quatre dernières entrées de la table des systèmes de fichiers (lstat, load, getcwd et chdir) pour lesquelles des remplacements se produisent effectivement au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme Tcl_Obj prennent ces noms sous forme UTF-8. L'API de l'infrastructure du système de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

INFRASTRUCTURE DU SYSTÈME DE FICHIERS

Ces champs contiennent des informations de base sur la structure du système de fichiers et les adresses des fonctions utilisées pour associer un système de fichiers particulier à un chemin d'accès, et pour gérer le traitement interne des représentations de chemin, par exemple la copie et la libération de ces représentations.

TYPENAME

Le champ typeName contient une chaîne de caractères terminée par un caractère nul qui identifie le type du système de fichiers implémenté, par exemple « natif », « zip » ou « vfs ».

STRUCTURE LENGTH

Le champ structureLength est généralement implémenté comme sizeof(Tcl_Filesystem), et sert à permettre une meilleure compatibilité binaire descendante si la taille de la structure change dans une future version de Tcl.

VERSION

Le champ version doit être défini à TCL_FILESYSTEM_VERSION_1.

PATHINFILESYSTEMPROC

Le champ pathInFilesystemProc contient l'adresse d'une fonction qui est appelée pour déterminer si une valeur de chemin donnée appartient ou non à ce système de fichiers. Tcl n'appellera les autres fonctions du système de fichiers qu'avec un chemin pour lequel cette fonction a renvoyé TCL_OK. Si le chemin n'appartient pas, -1 doit être renvoyé (le comportement de Tcl pour toute autre valeur de retour n'est pas défini). Si TCL_OK est renvoyé, le paramètre de sortie facultatif clientDataPtr peut être utilisé pour renvoyer une représentation interne (spécifique au système de fichiers) du chemin, qui sera mise en cache dans la valeur du chemin, et pourra être récupérée efficacement par les autres fonctions du système de fichiers. Tcl mettra simultanément en cache le fait que ce chemin appartient à ce système de fichiers. De tels caches sont invalidés lorsque des structures de systèmes de fichiers sont ajoutées ou supprimées de la liste interne des systèmes de fichiers connus de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

DUPINTERNALREPPROC

Cette fonction crée une copie de la représentation interne d'un chemin, et est appelée lorsque Tcl doit dupliquer une valeur de chemin. Si elle est NULL, Tcl ne copiera simplement pas la représentation interne, qui pourrait alors devoir être régénérée plus tard.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

FREEINTERNALREPPROC

Libère la représentation interne. Ceci doit être implémenté si des représentations internes nécessitent une libération (c'est-à-dire si de la mémoire est allouée lors de la génération d'une représentation interne), mais peut sinon être NULL.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

INTERNALTONORMALIZEDPROC

Fonction pour convertir une représentation interne en un chemin normalisé. Requise uniquement si le système de fichiers crée des valeurs de chemin pures sans représentation textuelle/de chemin. La valeur de retour est une valeur Tcl dont la représentation textuelle est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

CREATEINTERNALREPPROC

Fonction pour prendre une valeur de chemin, calculer une représentation interne pour celle-ci, et stocker cette représentation native dans la valeur. Peut être NULL si les chemins n'ont pas de représentation interne, ou si le Tcl_FSPathInFilesystemProc pour ce système de fichiers crée toujours immédiatement une représentation interne pour les chemins qu'il accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

NORMALIZEPATHPROC

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations textuelles pour la même valeur de chemin. Dans Tcl, chaque « chemin » doit avoir une seule représentation textuelle « normalisée » unique. Selon le système de fichiers, il peut y avoir plus d'une représentation textuelle non normalisée qui fait référence à ce chemin (par exemple, un chemin relatif, un chemin avec une casse de caractères différente si le système de fichiers ne distingue pas la casse, un chemin contenant une référence à un répertoire personnel tel que « ~ », un chemin contenant des liens symboliques, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être converti en la valeur qu'il pointe (mais sa casse ou d'autres aspects doivent être rendus uniques). Tous les autres composants de chemin doivent être convertis à partir de liens symboliques. Cette exception est nécessaire pour être cohérent avec la sémantique de Tcl pour les opérations file delete, file rename, file copy sur des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint soit au début du chemin (c'est-à-dire zéro), soit à la fin du chemin, soit à un séparateur de fichier intermédiaire dans le chemin. Elle ne pointera jamais vers une autre position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS DU SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions qui sont appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui est censé être utilisé avec l'ensemble complet des commandes Tcl standard doit implémenter toutes ces fonctions. Si certaines d'entre elles ne sont pas implémentées, certaines commandes Tcl peuvent échouer lors de l'opération sur des chemins appartenant à ce système de fichiers. Cependant, cela peut être souhaitable dans certains cas (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques n'a pas besoin d'implémenter la fonction readlink, etc. Le cœur de Tcl s'attend à ce que les systèmes de fichiers se comportent de cette manière).

Une valeur typique pourrait être « réseau », « zip » ou « ftp ». L'objet Tcl résultant appartient au système de fichiers et Tcl incrémentera donc le compteur de références de cette valeur s'il souhaite en conserver une référence.

STATPROC

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes au niveau Tcl en dépendent de manière cruciale (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La fonction Tcl_FSStatProc remplit la structure stat statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure stat inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), le rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification et l'heure de la dernière modification des métadonnées.

Si le fichier représenté par pathPtr existe, la fonction Tcl_FSStatProc renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé, et aucune information stat n'est fournie.

ACCESSPROC

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes au niveau Tcl en dépendent de manière cruciale (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La fonction Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est dans pathPtr. Si le nom de chemin fait référence à un lien symbolique, alors les permissions du fichier auquel ce lien symbolique fait référence doivent être testées.

En cas de succès (toutes les permissions demandées accordées), zéro est renvoyé. En cas d'erreur (au moins un bit dans mode demandait une permission refusée, ou une autre erreur s'est produite), -1 est renvoyé.

ENFILECHANNELPROC

Fonction pour traiter un appel à Tcl_FSOpenFileChannel. Doit être implémentée pour tout système de fichiers raisonnable, car toutes les opérations qui nécessitent l'ouverture ou l'accès au contenu d'un fichier l'utiliseront (par exemple, open, encoding, et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

La fonction Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et retourne un descripteur de canal qui peut être utilisé pour effectuer des entrées et des sorties sur le fichier. Cette API est basée sur la procédure fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier, où l'argument mode est une combinaison des indicateurs POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannelProc retourne NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le nouveau canal créé ne doit pas être enregistré dans l'interpréteur fourni par un Tcl_FSOpenFileChannelProc ; cette tâche incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr a été fermé précédemment, la création du nouveau canal lui assigne également le rôle de remplacement du canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, les fonctionnalités de glob et de copie récursive seront manquantes dans le système de fichiers (et cela peut affecter des commandes comme encoding names qui utilisent la fonctionnalité de glob en interne).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit retourner tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au modèle donné et qui respectent la spécification types fournie. Il y a deux façons dont cette fonction peut être appelée. Si pattern est NULL, alors pathPtr est une spécification de chemin complet d'un seul fichier ou répertoire qui doit être vérifié pour son existence et son type correct. Sinon, pathPtr est un répertoire, dont la fonction doit rechercher le contenu pour trouver les fichiers ou répertoires du bon type. Dans les deux cas, on peut supposer que pathPtr n'est ni NULL ni vide. Il n'est pas actuellement documenté si pathPtr se termine par un séparateur de fichier ou non, donc le code doit être flexible aux deux possibilités.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le processus de correspondance. Les messages d'erreur sont placés dans interp, sauf si interp est NULL, auquel cas aucun message d'erreur n'a besoin d'être généré ; en cas de résultat TCL_OK, les résultats doivent être ajoutés à la valeur donnée de resultPtr (qui peut être supposée être une liste Tcl valide et non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (cela signifie généralement qu'elles seront des spécifications de chemin absolu). Notez que si aucune correspondance n'est trouvée, cela conduit simplement à un résultat vide ; les erreurs ne sont signalées que pour les problèmes réels de fichier ou de système de fichiers qui peuvent survenir pendant le processus de correspondance.

La structure Tcl_GlobTypeData passée dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Type Mac acceptable */
    Tcl_Obj *macType;
    /* Créateur Mac acceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qui sont importants à gérer correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT sont vrais (et en particulier lorsque les autres indicateurs sont faux). Dans le premier de ces cas, la fonction doit lister les répertoires contenus. Tcl utilise cela pour implémenter le globbing récursif, il est donc crucial que les systèmes de fichiers implémentent correctement la correspondance des répertoires. Dans le second cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage qui se trouvent dans le pathPtr donné (et dans ce cas, pathPtr n'a pas besoin de se trouver dans le même système de fichiers - différent de tous les autres cas où cette fonction est appelée). Le support pour ceci est critique si Tcl veut avoir des transitions transparentes entre les systèmes de fichiers.

UTIMEPROC

Fonction pour traiter un appel à Tcl_FSUtime. Nécessaire pour permettre la définition (pas la lecture) des heures avec file mtime, file atime et l'implémentation open-r/open-w/fcopy de file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les heures d'accès et de modification du fichier spécifié par pathPtr doivent être modifiées pour correspondre aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec la fonction système utime.

LINKPROC

Fonction pour traiter un appel à Tcl_FSLink. Ne doit être implémentée que si le système de fichiers supporte les liens, et peut sinon être NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est invitée à lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat est possédé par l'appelant (et devrait donc avoir son compteur de références incrémenté avant d'être retourné). Tous les appelants doivent appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'est plus nécessaire. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Le résultat dans ce cas doit être toPtr si le lien a réussi et NULL sinon. Dans ce cas, le résultat n'est pas possédé par l'appelant (c'est-à-dire qu'aucun manipulation de compteur de références des deux côtés n'est nécessaire). Voir la documentation de Tcl_FSLink pour l'interprétation correcte des indicateurs linkAction.

LISTVOLUMESPROC

Fonction pour lister les volumes de systèmes de fichiers ajoutés par ce système de fichiers. Ne doit être implémentée que si le système de fichiers ajoute des volumes à la tête du système de fichiers, afin qu'ils puissent être retournés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste de volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. La valeur de retour est considérée comme appartenant au système de fichiers (pas au cœur de Tcl), mais doit avoir un compteur de références pour Tcl. Tcl utilisera le contenu de la liste puis décrémentera ce compteur de références. Cela permet aux systèmes de fichiers de choisir s'ils veulent réellement conserver une liste « globale » de volumes ou non (sinon, ils génèrent la liste à la volée et la passent à Tcl avec un compteur de références de 1, puis oublient la liste ; s'ils le veulent, ils incrémentent simplement le compteur de références de leur liste globale et la passent à Tcl, qui copiera le contenu puis décrémentera le compteur pour le ramener à son état initial).

Par conséquent, Tcl considère les valeurs de retour de ce proc comme en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne supportera pas la commande file attributes. Cela permet de joindre des informations supplémentaires arbitraires aux fichiers dans le système de fichiers. Si elle n'est pas implémentée, il n'est pas nécessaire d'implémenter les méthodes get et set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La fonction appelée peut soit retourner un tableau de chaînes, soit retourner NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer de retourner une valeur avec un compteur de références d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsGet, utilisé par file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Retourne un code de retour Tcl standard. La valeur d'attribut récupérée, qui correspond à l'élément d'index index dans la liste retournée par Tcl_FSFileAttrStringsProc, est un Tcl_Obj placé dans objPtrRef (si TCL_OK a été retourné) et aura probablement un compteur de références de zéro. Dans tous les cas, nous devons soit le stocker quelque part (par exemple, le résultat Tcl), soit incrémenter/décrémenter son compteur de références pour assurer sa libération correcte.

FILEATTRSSETPROC

Fonction pour traiter un appel Tcl_FSCopyFile. Si elle n'est pas implémentée, Tcl se rabattra sur open-r, open-w et fcopy comme mécanisme de copie. Elle ne doit donc être implémentée que si le système de fichiers peut effectuer cette opération plus efficacement.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

Fonction pour traiter un appel Tcl_FSLoadFile. Si elle n'est pas implémentée, Tcl se rabattra sur une copie vers un fichier temporaire, suivie d'un Tcl_FSLoadFile sur ce fichier temporaire.         Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,

La procédure de déchargement est appelée avec le Tcl_LoadHandle donné comme seul argument lorsque Tcl a besoin de décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle renvoyé est actuellement un jeton qui peut être utilisé dans le TclpFindSymbol privé pour accéder aux fonctions du nouveau code. Chaque système de fichiers peut définir le Tcl_LoadHandle selon ses besoins. Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de chargement de fichiers, l'appel à Tcl_SetErrno(EXDEV) et le renvoi d'un résultat autre que TCL_OK amèneront Tcl à utiliser ses mécanismes de secours standard.
