INTRODUCTION

Ces routines convertissent entre la représentation interne des caractères de Tcl, UTF-8, et les représentations de caractères utilisées par divers systèmes d'exploitation ou systèmes de fichiers, tels que Unicode, ASCII ou Shift-JIS. Lors de l'opération sur des chaînes, comme l'obtention des noms de fichiers ou l'affichage de caractères à l'aide de polices internationales, les chaînes doivent être traduites dans un ou potentiellement plusieurs formats que les divers appels système peuvent utiliser. Par exemple, sur un poste de travail Unix japonais, un utilisateur pourrait obtenir un nom de fichier représenté dans l'encodage de fichier EUC-JP, puis traduire les caractères vers l'encodage de police jisx0208 afin d'afficher le nom de fichier dans un widget Tk. Le but du package d'encodage est d'aider à combler le fossé de traduction. UTF-8 fournit une zone de transit intermédiaire pour tous les divers encodages. Dans l'exemple ci-dessus, le texte serait traduit en UTF-8 à partir de l'encodage de fichier que le système d'exploitation utilise. Ensuite, il serait traduit de UTF-8 vers l'encodage de police dont les routines d'affichage ont besoin.

Certains encodages de base sont compilés dans Tcl. D'autres peuvent être définis par l'utilisateur ou chargés dynamiquement à partir de fichiers d'encodage d'une manière indépendante de la plateforme.

DESCRIPTION

Tcl_GetEncoding trouve un encodage étant donné son nom. Le nom peut faire référence à un encodage Tcl intégré, à un encodage défini par l'utilisateur enregistré en appelant Tcl_CreateEncoding, ou à un fichier d'encodage chargeable dynamiquement. La valeur de retour est un jeton qui représente l'encodage et peut être utilisé dans des appels ultérieurs à des procédures telles que Tcl_GetEncodingName, Tcl_FreeEncoding, et Tcl_UtfToExternal. Si le nom ne fait référence à aucun encodage connu ou chargeable, NULL est retourné et un message d'erreur est renvoyé dans interp.

Le package d'encodage maintient une base de données de tous les encodages actuellement en cours d'utilisation. La première fois que name est rencontré, Tcl_GetEncoding retourne un encodage avec un compteur de références de 1. Si le même nom est demandé plusieurs fois, alors le compteur de références pour cet encodage est incrémenté sans la surcharge d'allocation d'un nouvel encodage et de toutes ses structures de données associées.

Lorsqu'un encodage n'est plus nécessaire, Tcl_FreeEncoding doit être appelé pour le libérer. Lorsqu'un encodage n'est plus utilisé nulle part (c'est-à-dire qu'il a été libéré autant de fois qu'il a été obtenu), Tcl_FreeEncoding libérera tout le stockage utilisé par l'encodage et le supprimera de la base de données.

Tcl_GetEncodingFromObj traite la représentation sous forme de chaîne de objPtr comme un nom d'encodage, et trouve un encodage portant ce nom, tout comme le fait Tcl_GetEncoding. De manière similaire à Tcl_GetEncoding, l'appelant doit appeler Tcl_FreeEncoding sur le jeton d'encodage résultant lorsque ce jeton ne sera plus utilisé.

Tcl_ExternalToUtfDString convertit un tampon source src de l'encodage spécifié encoding en UTF-8. Les octets convertis sont stockés dans dstPtr, qui est terminé par le caractère nul de l'encodage spécifique. L'appelant doit éventuellement appeler Tcl_DStringFree pour libérer toute information stockée dans dstPtr. Lors de la conversion, si l'un des caractères du tampon source ne peut pas être représenté dans l'encodage de destination, un caractère par défaut sera utilisé. La valeur renvoyée est un pointeur vers la valeur stockée dans le DString.

Tcl_ExternalToUtf convertit un tampon source src de l'encodage spécifié encoding en UTF-8. Jusqu'à srcLen octets du tampon source sont convertis, et jusqu'à dstLen octets sont stockés dans dst. Dans tous les cas, *srcReadPtr est rempli avec le nombre d'octets convertis à partir de src, et *dstWrotePtr est rempli avec le nombre d'octets stockés dans dst. La valeur renvoyée est l'une des suivantes :

TCL_OK
Tous les octets de src ont été convertis.
TCL_CONVERT_NOSPACE
Le tampon de destination n'était pas suffisant pour toutes les données converties ; autant de caractères que possible ont été convertis.
TCL_CONVERT_MULTIBYTE
Les quelques derniers octets du tampon source étaient le début d'une séquence multi-octets, mais plus d'octets étaient nécessaires pour compléter cette séquence. Un appel ultérieur à la procédure de conversion doit passer un tampon contenant les octets non convertis qui sont encore dans src plus quelques octets supplémentaires du flux d'entrée pour convertir correctement la séquence multi-octets qui a été divisée.
TCL_CONVERT_SYNTAX
Le tampon source contenait une séquence de caractères invalide. Cela peut se produire si le flux d'entrée a été corrompu ou si la méthode d'encodage a été mal identifiée.
TCL_CONVERT_UNKNOWN
Le tampon source contenait un caractère qui ne pouvait pas être représenté dans l'encodage de destination et TCL_ENCODING_STOPONERROR avait été spécifié.

Tcl_UtfToExternalDString convertit un tampon source src de UTF-8 dans l'encodage spécifié encoding. Les octets convertis sont stockés dans dstPtr, qui est terminé par le caractère nul de l'encodage spécifique. L'appelant doit éventuellement appeler Tcl_DStringFree pour libérer toute information stockée dans dstPtr. Lors de la conversion, si l'un des caractères du tampon source ne peut pas être représenté dans l'encodage de destination, un caractère par défaut sera utilisé. La valeur renvoyée est un pointeur vers la valeur stockée dans le DString.

Tcl_UtfToExternal convertit un tampon source src de UTF-8 dans l'encodage spécifié encoding. Jusqu'à srcLen octets du tampon source sont convertis, et jusqu'à dstLen octets sont stockés dans dst. Dans tous les cas, *srcReadPtr est rempli avec le nombre d'octets convertis à partir de src, et *dstWrotePtr est rempli avec le nombre d'octets stockés dans dst. Les valeurs renvoyées sont les mêmes que pour Tcl_ExternalToUtf.

Tcl_WinUtfToTChar et Tcl_WinTCharToUtf sont des fonctions utilitaires uniquement pour Windows qui convertissent entre UTF-8 et les chaînes Windows basées sur le type TCHAR, qui est par commodité un caractère Unicode sous Windows NT.

Tcl_GetEncodingName est approximativement l'inverse de Tcl_GetEncoding. Étant donné un encodage encoding, la valeur renvoyée est l'argument name qui a été utilisé pour créer l'encodage. La chaîne renvoyée par Tcl_GetEncodingName n'est garantie de persister que jusqu'à ce que l'encodage encoding soit supprimé. L'appelant ne doit pas modifier cette chaîne.

Tcl_SetSystemEncoding définit l'encodage par défaut qui doit être utilisé lorsque l'utilisateur passe une valeur nulle pour l'argument encoding à toute fonction d'encodage. Si name est nul, l'encodage système est réinitialisé à l'encodage par défaut, binary. Si le nom ne fait pas référence à un encodage connu ou chargeable, TCL_ERROR est renvoyé et un message d'erreur est laissé dans interp. Sinon, cette procédure incrémente le compteur de références du nouvel encodage système, décrémente le compteur de références de l'ancien encodage, et renvoie TCL_OK.

Tcl_GetEncodingNameFromEnvironment fournit un moyen pour la bibliothèque Tcl de signaler le nom de l'encodage qu'elle pense être correct pour être utilisé comme encodage système, basé sur les appels système et l'examen de l'environnement approprié à la plateforme. Elle reçoit bufPtr, un pointeur vers un Tcl_DString initialisé ou libéré, et y écrit le nom de l'encodage. La valeur renvoyée est la valeur de Tcl_DStringValue.

Tcl_GetEncodingNames définit le résultat interp en une liste composée des noms de tous les encodages définis ou chargeables dynamiquement, en recherchant dans le chemin d'encodage spécifié par Tcl_SetDefaultEncodingDir. Cette procédure ne garantit pas que les fichiers chargeables dynamiquement contiennent des données valides, mais seulement qu'ils existent.

Tcl_CreateEncoding définit un nouvel encodage et enregistre les procédures C qui sont appelées pour convertir entre cet encodage et UTF-8. Les encodages créés par Tcl_CreateEncoding sont ensuite visibles dans la base de données utilisée par Tcl_GetEncoding. De manière similaire à Tcl_GetEncoding, la valeur renvoyée est un jeton représentant l'encodage et pouvant être utilisé dans les appels ultérieurs à d'autres fonctions d'encodage. Tcl_CreateEncoding renvoie un encodage avec un compteur de références de 1. Si un encodage avec le nom spécifié name existe déjà, son entrée dans la base de données est remplacée par le nouvel encodage ; le jeton de l'ancien encodage reste valide et continue de se comporter comme auparavant, mais les utilisateurs du nouveau jeton appellent désormais les nouvelles procédures d'encodage.

L'argument typePtr de Tcl_CreateEncoding contient des informations sur le nom de l'encodage et les procédures qui seront appelées pour convertir entre cet encodage et UTF-8. Il est défini comme suit :

typedef struct Tcl_EncodingType {
    const char *encodingName;
    Tcl_EncodingConvertProc *toUtfProc;
    Tcl_EncodingConvertProc *fromUtfProc;
    Tcl_EncodingFreeProc *freeProc;
    ClientData clientData;
    int nullSize;
} Tcl_EncodingType;

encodingName fournit un nom pour l'encodage, par lequel il peut être référencé dans d'autres procédures telles que Tcl_GetEncoding. toUtfProc fait référence à une procédure de rappel à invoquer pour convertir du texte de cet encodage vers UTF-8. fromUtfProc fait référence à une procédure de rappel à invoquer pour convertir du texte d'UTF-8 vers cet encodage. freeProc fait référence à une procédure de rappel à invoquer lorsque cet encodage est supprimé. Le champ freeProc peut être nul. clientData contient une valeur de type mot arbitraire passée aux procédures toUtfProc, fromUtfProc et freeProc lorsqu'elles sont appelées. Généralement, il s'agit d'un pointeur vers un ensemble de données contenant des informations spécifiques à l'encodage, qui peuvent être utilisées par les procédures de rappel. Par exemple, deux encodages très similaires comme ascii et macRoman peuvent utiliser la même procédure de rappel, mais utilisent des valeurs clientData différentes pour contrôler leur comportement. nullSize spécifie le nombre d'octets nuls qui signifient la fin de la chaîne dans cet encodage. Il doit être de 1 (pour les encodages d'un octet ou multi-octets comme ASCII ou Shift-JIS) ou 2 (pour les encodages de deux octets comme Unicode). Les encodages de taille constante avec 3 octets ou plus par caractère (comme CNS11643) ne sont pas pris en charge.

Les procédures de rappel toUtfProc et fromUtfProc doivent correspondre au type Tcl_EncodingConvertProc :

typedef int Tcl_EncodingConvertProc(
        ClientData clientData,
        const char *src,
        int srcLen,
        int flags,
        Tcl_EncodingState *statePtr,
        char *dst,
        int dstLen,
        int *srcReadPtr,
        int *dstWrotePtr,
        int *dstCharsPtr);

Les procédures toUtfProc et fromUtfProc sont appelées par Tcl_ExternalToUtf ou Tcl_UtfToExternal pour effectuer la conversion réelle. Le paramètre clientData de ces procédures est le même que le champ clientData spécifié dans Tcl_CreateEncoding lors de la création de l'encodage. Les arguments restants aux procédures de rappel sont les mêmes que les arguments, documentés ci-dessus, pour Tcl_ExternalToUtf ou Tcl_UtfToExternal, à l'exception des points suivants. Si l'argument srcLen de l'une de ces fonctions de haut niveau est négatif, la valeur passée à la procédure de rappel sera la longueur appropriée de l'encodage source src. Si l'un des arguments srcReadPtr, dstWrotePtr, ou dstCharsPtr de l'une de ces fonctions de haut niveau est nul, la valeur correspondante passée à la procédure de rappel sera un emplacement non nul.

La procédure de rappel freeProc, si elle n'est pas nulle, doit correspondre au type Tcl_EncodingFreeProc :

typedef void Tcl_EncodingFreeProc(
        ClientData clientData);

Cette fonction freeProc est appelée lorsque l'encodage est supprimé. Le paramètre clientData est le même que le champ clientData spécifié dans Tcl_CreateEncoding lors de la création de l'encodage.

Tcl_GetEncodingSearchPath et Tcl_SetEncodingSearchPath sont appelés pour accéder et configurer la liste des répertoires système où rechercher les fichiers de données d'encodage. La valeur renvoyée par Tcl_GetEncodingSearchPath est la valeur stockée par le dernier appel réussi à Tcl_SetEncodingSearchPath. Si aucun appel à Tcl_SetEncodingSearchPath n'a été effectué, Tcl calculera une valeur initiale basée sur l'environnement. Il existe un chemin de recherche d'encodage pour l'ensemble du processus, partagé par tous les threads du processus.

Tcl_SetEncodingSearchPath stocke searchPath et renvoie TCL_OK, sauf si searchPath n'est pas une liste Tcl valide, auquel cas TCL_ERROR est renvoyé. Les éléments de searchPath sont les mêmes que les arguments, documentés ci-dessus, pour Tcl_ExternalToUtf ou Tcl_UtfToExternal, à l'exception du fait que l'argument srcLen peut être négatif.

INTRODUCTION

Tcl has built-in support for Unicode, and can convert strings between Unicode and various other character encodings. This man page describes the interface for manipulating encodings. Encodings are loaded dynamically from encoding files stored in directories specified by the searchPath.

DESCRIPTION

The primary mechanism for Tcl to handle character encodings is through dynamically loadable encoding files. These files contain tables and/or rules for converting between Unicode and the external encoding. Tcl searches for these files in directories specified by the searchPath.

The searchPath is a list of directory names. Tcl searches the searchPath in order, looking for a file named encoding.enc in each directory. The first file found is loaded. If an encoding is not found in any of the directories in the searchPath, Tcl will then attempt to load it from the default system encoding directory (if one is configured).

The function Tcl_SetEncodingSearchPath sets the searchPath for the interpreter. The searchPath argument is an array of strings, each string being a path to a directory. The last element of the array must be NULL. The function Tcl_GetEncodingSearchPath retrieves the current searchPath and stores it in the location pointed to by searchPathPtr. The caller is responsible for freeing the memory allocated for the search path.

Note that directories in the searchPath are not verified as existing readable filesystem directories. When searching for encoding data files takes place, and non-existent or non-readable filesystem directories on the searchPath are silently ignored.

Tcl_GetDefaultEncodingDir and Tcl_SetDefaultEncodingDir are obsolete interfaces best replaced with calls to Tcl_GetEncodingSearchPath and Tcl_SetEncodingSearchPath. They are called to access and set the first element of the searchPath list. Since Tcl searches searchPath for encoding data files in list order, these routines establish the “default” directory in which to find encoding data files.

ENCODING FILES

Space would prohibit precompiling into Tcl every possible encoding algorithm, so many encodings are stored on disk as dynamically-loadable encoding files. This behavior also allows the user to create additional encoding files that can be loaded using the same mechanism. These encoding files contain information about the tables and/or escape sequences used to map between an external encoding and Unicode. The external encoding may consist of single-byte, multi-byte, or double-byte characters.

Each dynamically-loadable encoding is represented as a text file. The initial line of the file, beginning with a “#” symbol, is a comment that provides a human-readable description of the file. The next line identifies the type of encoding file. It can be one of the following letters:

[1] S
A single-byte encoding, where one character is always one byte long in the encoding. An example is iso8859-1, used by many European languages.
[2] D
A double-byte encoding, where one character is always two bytes long in the encoding. An example is big5, used for Chinese text.
[3] M
A multi-byte encoding, where one character may be either one or two bytes long. Certain bytes are lead bytes, indicating that another byte must follow and that together the two bytes represent one character. Other bytes are not lead bytes and represent themselves. An example is shiftjis, used by many Japanese computers.
[4] E
An escape-sequence encoding, specifying that certain sequences of bytes do not represent characters, but commands that describe how following bytes should be interpreted.

The rest of the lines in the file depend on the type.

Cases [1], [2], and [3] are collectively referred to as table-based encoding files. The lines in a table-based encoding file are in the same format as this example taken from the shiftjis encoding (this is not the complete file):

The third line of the file is three numbers. The first number is the fallback character (in base 16) to use when converting from UTF-8 to this encoding. The second number is a 1 if this file represents the encoding for a symbol font, or 0 otherwise. The last number (in base 10) is how many pages of data follow.

Subsequent lines in the example above are pages that describe how to map from the encoding into 2-byte Unicode. The first line in a page identifies the page number. Following it are 256 double-byte numbers, arranged as 16 rows of 16 numbers. Given a character in the encoding, the high byte of that character is used to select which page, and the low byte of that character is used as an index to select one of the double-byte numbers in that page - the value obtained being the corresponding Unicode character. By examination of the example above, one can see that the characters 0x7E and 0x8163 in shiftjis map to 203E and 2026 in Unicode, respectively.

Following the first page will be all the other pages, each in the same format as the first: one number identifying the page followed by 256 double-byte Unicode characters. If a character in the encoding maps to the Unicode character 0000, it means that the character does not actually exist. If all characters on a page would map to 0000, that page can be omitted.

Case [4] is the escape-sequence encoding file. The lines in an this type of file are in the same format as this example taken from the iso2022-jp encoding:

# Encoding file: iso2022-jp, escape-driven
E
init		{}
final		{}
iso8859-1	\x1b(B
jis0201		\x1b(J
jis0208		\x1b$@
jis0208		\x1b$B
jis0212		\x1b$(D
gb2312		\x1b$A
ksc5601		\x1b$(C

In the file, the first column represents an option and the second column is the associated value. init is a string to emit or expect before the first character is converted, while final is a string to emit or expect after the last character. All other options are names of table-based encodings; the associated value is the escape-sequence that marks that encoding. Tcl syntax is used for the values; in the above example, for instance, “{}” represents the empty string and “\x1b” represents character 27.

When Tcl_GetEncoding encounters an encoding name that has not been loaded, it attempts to load an encoding file called name.enc from the encoding subdirectory of each directory that Tcl searches for its script library. If the encoding file exists, but is malformed, an error message will be left in interp.
