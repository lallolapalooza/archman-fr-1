Une combinaison OR de TCL_READABLE, TCL_WRITABLE et TCL_EXCEPTION indiquant les événements qui se sont produits sur ce canal.

DESCRIPTION

Tcl utilise une architecture de canaux à deux couches. Elle fournit une couche supérieure générique pour permettre aux programmes C et Tcl d'effectuer des entrées et sorties en utilisant les mêmes API pour une variété de fichiers, périphériques, sockets, etc. Les API C génériques sont décrites dans la page de manuel de Tcl_OpenFileChannel.

La couche inférieure fournit des pilotes de canaux spécifiques à chaque type pour chaque type de périphérique supporté sur chaque plateforme. Cette page de manuel décrit les API C utilisées pour communiquer entre la couche générique et les pilotes de canaux spécifiques au type. Elle explique également comment de nouveaux types de canaux peuvent être ajoutés en fournissant de nouveaux pilotes de canaux.

Les pilotes de canaux se composent de plusieurs composants : Premièrement, chaque pilote de canal fournit une structure Tcl_ChannelType contenant des pointeurs vers les fonctions implémentant les différentes opérations utilisées par la couche générique pour communiquer avec le pilote de canal. La structure Tcl_ChannelType et les fonctions auxquelles elle fait référence sont décrites dans la section TCL_CHANNELTYPE, ci-dessous.

Deuxièmement, les pilotes de canaux fournissent généralement une commande Tcl pour créer des instances de ce type de canal. Par exemple, la commande Tcl open crée des canaux qui utilisent les pilotes de canaux de fichier et de commande, et la commande Tcl socket crée des canaux qui utilisent des sockets TCP pour la communication réseau.

Troisièmement, un pilote de canal fournit éventuellement une fonction C pour ouvrir des instances de canaux de ce type. Par exemple, Tcl_OpenFileChannel ouvre un canal qui utilise le pilote de canal de fichier, et Tcl_OpenTcpClient ouvre un canal qui utilise le protocole réseau TCP. Ces fonctions de création utilisent généralement Tcl_CreateChannel en interne pour ouvrir le canal.

Pour ajouter un nouveau type de canal, vous devez implémenter une API C ou une commande Tcl qui ouvre un canal en invoquant Tcl_CreateChannel. Lorsque votre pilote appelle Tcl_CreateChannel, il passe une structure Tcl_ChannelType décrivant les procédures d'E/S du pilote. La couche générique invoquera alors les fonctions référencées dans cette structure pour effectuer des opérations sur le canal.

Tcl_CreateChannel ouvre un nouveau canal et lui associe les arguments typePtr et instanceData fournis. Le canal est ouvert dans le mode indiqué par mask. Pour une discussion sur les pilotes de canaux, leurs opérations et la structure Tcl_ChannelType, voir la section TCL_CHANNELTYPE, ci-dessous.

Tcl_CreateChannel interagit avec le code gérant les canaux standards. Une fois qu'un canal standard a été initialisé soit par un appel à Tcl_GetStdChannel soit par un appel à Tcl_SetStdChannel, la fermeture de ce canal standard provoquera le prochain appel à Tcl_CreateChannel pour faire du nouveau canal le nouveau canal standard également. Voir Tcl_StandardChannels pour une discussion générale sur les canaux standards et le comportement de la bibliothèque Tcl à leur égard.

Tcl_GetChannelInstanceData renvoie les données d'instance associées au canal dans channel. C'est la même valeur que l'argument instanceData dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelType renvoie un pointeur vers la structure Tcl_ChannelType utilisée par le canal dans l'argument channel. C'est la même valeur que l'argument typePtr dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelName renvoie une chaîne contenant le nom associé au canal, ou NULL si l'argument channelName de Tcl_CreateChannel était NULL.

location specified by handlePtr and returns TCL_OK. If the channel does not have a device handle for the specified direction, then TCL_ERROR is returned instead. Different channel drivers will return different types of handle. Refer to the manual entries for each driver to determine what type of handle is returned.

Tcl_GetChannelThread returns the id of the thread currently managing the specified channel. This allows channel drivers to send their file events to the correct event queue even for a multi-threaded core.

Tcl_GetChannelMode returns an OR-ed combination of TCL_READABLE and TCL_WRITABLE, indicating whether the channel is open for input and output.

Tcl_GetChannelBufferSize returns the size, in bytes, of buffers allocated to store input or output in channel. If the value was not set by a previous call to Tcl_SetChannelBufferSize, described below, then the default value of 4096 is returned.

Tcl_SetChannelBufferSize sets the size, in bytes, of buffers that will be allocated in subsequent operations on the channel to store input or output. The size argument should be between one and one million, allowing buffers of one byte to one million bytes. If size is outside this range, Tcl_SetChannelBufferSize sets the buffer size to 4096.

Tcl_NotifyChannel is called by a channel driver to indicate to the generic layer that the events specified by mask have occurred on the channel. Channel drivers are responsible for invoking this function whenever the channel handlers need to be called for the channel (or other pending tasks like a write flush should be performed). See WATCHPROC below for more details.

Tcl_BadChannelOption is called from driver specific setOptionProc or getOptionProc to generate a complete error message.

Tcl_ChannelBuffered returns the number of bytes of input currently buffered in the internal buffer (push back area) of the channel itself. It does not report about the data in the overall buffers for the stack of channels the supplied channel is part of.

Tcl_IsChannelShared checks the refcount of the specified channel and returns whether the channel was shared among multiple interpreters (result == 1) or not (result == 0).

Tcl_IsChannelRegistered checks whether the specified channel is registered in the given interpreter (result == 1) or not (result == 0).

Tcl_IsChannelExisting checks whether a channel with the specified name is registered in the (thread)-global list of all channels (result == 1) or not (result == 0).

Tcl_CutChannel removes the specified channel from the (thread)global list of all channels (of the current thread). Application to a channel still registered in some interpreter is not allowed. Also notifies the driver if the Tcl_ChannelType version is TCL_CHANNEL_VERSION_4 (or higher), and Tcl_DriverThreadActionProc is defined for it.

Tcl_SpliceChannel adds the specified channel to the (thread)global list of all channels (of the current thread). Application to a channel registered in some interpreter is not allowed. Also notifies the driver if the Tcl_ChannelType version is TCL_CHANNEL_VERSION_4 (or higher), and Tcl_DriverThreadActionProc is defined for it.

Tcl_ClearChannelHandlers removes all channel handlers and event scripts associated with the specified channel, thus shutting down all event processing for this channel.

TCL_CHANNELTYPE

Un pilote de canal fournit une structure Tcl_ChannelType qui contient des pointeurs vers des fonctions qui implémentent les diverses opérations sur un canal ; ces opérations sont appelées si nécessaire par la couche générique. La structure a été versionnée à partir de Tcl 8.3.2/8.4 pour corriger un problème avec les pilotes de canaux empilés. Voir la section ANCIENS TYPES DE CANAUX ci-dessous pour plus de détails sur l'ancienne structure.

La structure Tcl_ChannelType contient les champs suivants :

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Il n'est pas nécessaire de fournir des implémentations pour toutes les opérations de canal. Celles qui ne sont pas nécessaires peuvent être mises à NULL dans la structure : blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc, et close2Proc, en plus de flushProc, handlerProc, threadActionProc, et truncateProc. D'autres fonctions qui ne peuvent pas être implémentées de manière significative devraient retourner EINVAL lorsqu'elles sont appelées, pour indiquer que les opérations qu'elles représentent ne sont pas disponibles. Notez également que wideSeekProc peut être NULL si seekProc l'est.

L'utilisateur ne doit utiliser que la structure ci-dessus pour l'instanciation de Tcl_ChannelType. Lors de la référence aux champs d'une structure Tcl_ChannelType, les fonctions suivantes doivent être utilisées pour obtenir les valeurs : Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc, ou Tcl_ChannelHandlerProc.

La modification des structures a été faite de telle sorte que les types de canaux standards sont binaires compatibles. Cependant, les types de canaux qui utilisent des canaux empilés (c'est-à-dire TLS, Trf) ont de nouvelles versions pour correspondre au changement ci-dessus car le code précédent pour les canaux empilés présentait des problèmes.

TYPENAME

Le champ typeName contient une chaîne terminée par un caractère nul qui identifie le type de l'appareil implémenté par ce pilote, par exemple file ou socket.

Cette valeur peut être récupérée avec Tcl_ChannelName, qui renvoie un pointeur vers la chaîne.

VERSION

Le champ version doit être défini sur la version de la structure dont vous avez besoin. TCL_CHANNEL_VERSION_2 est le minimum recommandé. TCL_CHANNEL_VERSION_3 doit être défini pour spécifier le membre wideSeekProc. TCL_CHANNEL_VERSION_4 doit être défini pour spécifier le membre threadActionProc (inclut wideSeekProc). TCL_CHANNEL_VERSION_5 doit être défini pour spécifier les membres truncateProc (inclut wideSeekProc et threadActionProc). S'il n'est défini sur aucune de ces valeurs, alors ce Tcl_ChannelType est supposé avoir la structure d'origine. Voir ANCIENS TYPES DE CANAUX pour plus de détails. Bien que Tcl reconnaisse et fonctionne avec les deux structures, les canaux empilés doivent être au moins de TCL_CHANNEL_VERSION_2 pour fonctionner correctement.

Cette valeur peut être récupérée avec Tcl_ChannelVersion, qui renvoie l'une des valeurs TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 ou TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

Le champ blockModeProc contient l'adresse d'une fonction appelée par la couche générique pour définir le mode bloquant et non bloquant sur le périphérique. BlockModeProc doit correspondre au prototype suivant :

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

Le instanceData est le même que la valeur passée à Tcl_CreateChannel lors de la création de ce canal. L'argument mode est soit TCL_MODE_BLOCKING, soit TCL_MODE_NONBLOCKING pour définir le périphérique en mode bloquant ou non bloquant. La fonction doit retourner zéro si l'opération a réussi, ou un code d'erreur POSIX non nul si l'opération a échoué.

Si l'opération réussit, la fonction peut modifier le instanceData fourni pour enregistrer que le canal est entré en mode bloquant ou non bloquant et pour implémenter le comportement bloquant ou non bloquant. Pour certains types de périphériques, le comportement bloquant et non bloquant peut être implémenté par le système d'exploitation sous-jacent ; pour d'autres types de périphériques, le comportement doit être émulé dans le pilote de canal.

Cette valeur peut être récupérée avec Tcl_ChannelBlockModeProc, qui renvoie un pointeur vers la fonction.

Un pilote de canal qui ne fournit pas de blockModeProc doit être très, très prudent. Il doit indiquer à la couche générique exactement quel mode de blocage lui convient, et cela doit également être documenté pour l'utilisateur afin que le mode de blocage du canal ne soit pas modifié à une valeur inacceptable. Toute confusion ici peut conduire l'interpréteur à une impasse (sans objet et difficile à trouver).

CLOSEPROC ET CLOSE2PROC

Le champ closeProc contient l'adresse d'une fonction appelée par la couche générique pour nettoyer les informations spécifiques au pilote lors de la fermeture du canal. CloseProc doit correspondre au prototype suivant :

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

L'argument instanceData est le même que la valeur fournie à Tcl_CreateChannel lors de la création du canal. La fonction doit libérer toute mémoire maintenue par le pilote de canal pour ce canal, et fermer les périphériques d'entrée et de sortie encapsulés par ce canal. Toute sortie mise en file d'attente aura été vidée vers le périphérique avant que cette fonction ne soit appelée, et aucune autre opération de pilote ne sera invoquée sur cette instance après l'appel de closeProc. Si l'opération de fermeture réussit, la procédure

ure doit retourner zéro ; sinon, elle doit retourner un code d'erreur POSIX non nul. De plus, si une erreur se produit et que interp n'est pas NULL, la procédure doit stocker un message d'erreur dans le résultat de l'interpréteur.

Alternativement, les canaux qui permettent de fermer indépendamment les côtés lecture et écriture peuvent définir closeProc sur TCL_CLOSE2PROC et définir close2Proc sur l'adresse d'une fonction qui correspond au prototype suivant :

typedef int Tcl_DriverClose2Proc(
        ClientData instanceData,
        Tcl_Interp *interp,
        int flags);

Le close2Proc sera appelé avec flags défini sur une combinaison OR'ée de TCL_CLOSE_READ ou TCL_CLOSE_WRITE pour indiquer que le pilote doit fermer le côté lecture et/ou écriture du canal. Le pilote de canal peut être appelé pour effectuer des opérations supplémentaires sur le canal après l'appel de close2Proc pour fermer un ou les deux côtés du canal. Si flags est 0 (zéro), le pilote doit fermer le canal de la manière décrite ci-dessus pour closeProc. Aucune opération supplémentaire ne sera invoquée sur cette instance après l'appel de close2Proc avec tous les drapeaux effacés. Dans tous les cas, la fonction close2Proc doit retourner zéro si l'opération de fermeture a réussi ; sinon, elle doit retourner un code d'erreur POSIX non nul. De plus, si une erreur se produit et que interp n'est pas NULL, la procédure doit stocker un message d'erreur dans le résultat de l'interpréteur.

Les valeurs closeProc et close2Proc peuvent être récupérées avec Tcl_ChannelCloseProc ou Tcl_ChannelClose2Proc, qui retournent un pointeur vers la fonction respective.

INPUTPROC

Le champ inputProc contient l'adresse d'une fonction appelée par la couche générique pour lire les données du fichier ou de l'appareil et les stocker dans un tampon interne. InputProc doit correspondre au prototype suivant :

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création du canal. L'argument buf pointe vers un tableau d'octets dans lequel stocker les entrées de l'appareil, et l'argument bufSize indique le nombre d'octets disponibles dans buf.

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générique. Si une erreur se produit, la fonction doit définir la variable à un code d'erreur POSIX qui identifie l'erreur qui s'est produite.

La fonction doit lire les données du périphérique d'entrée encapsulé par le canal et les stocker dans buf. En cas de succès, la fonction doit retourner un entier non négatif indiquant le nombre d'octets lus depuis le périphérique d'entrée et stockés dans buf. En cas d'erreur, la fonction doit retourner -1. Si une erreur se produit après qu'une partie des données ait été lue depuis le périphérique, ces données sont perdues.

Si inputProc peut déterminer que le périphérique d'entrée dispose de données disponibles mais moins que ce qui est demandé par l'argument bufSize, la fonction ne doit tenter de lire que la quantité de données disponible et retourner sans bloquer. Si le périphérique d'entrée n'a absolument aucune donnée disponible et que le canal est en mode non bloquant, la fonction doit retourner une erreur EAGAIN. Si le périphérique d'entrée n'a absolument aucune donnée disponible et que le canal est en mode bloquant, la fonction doit bloquer pendant la durée la plus courte possible jusqu'à ce qu'au moins un octet de données puisse être lu depuis le périphérique ; ensuite, elle doit retourner autant de données qu'elle peut lire sans bloquer.

Cette valeur peut être récupérée avec Tcl_ChannelInputProc, qui retourne un pointeur vers la fonction.

OUTPUTPROC

Le champ outputProc contient l'adresse d'une fonction appelée par la couche générique pour transférer des données d'un tampon interne vers le périphérique de sortie. OutputProc doit correspondre au prototype suivant :

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création du canal. L'argument buf contient un tableau d'octets à écrire sur le périphérique, et l'argument toWrite indique le nombre d'octets à écrire à partir de l'argument buf.

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générique. Si une erreur se produit, la fonction doit définir cette variable à un code d'erreur POSIX qui identifie l'erreur.

La fonction doit écrire les données présentes dans buf sur le périphérique de sortie encapsulé par le canal. En cas de succès, la fonction doit retourner un entier non négatif indiquant le nombre d'octets écrits sur le périphérique de sortie. La valeur de retour est normalement la même que toWrite, mais peut être inférieure dans certains cas, par exemple si l'opération de sortie est interrompue par un signal. Si une erreur se produit, la fonction doit retourner -1. En cas d'erreur, certaines données peuvent avoir été écrites sur le périphérique.

Si le canal est non bloquant et que le périphérique de sortie est incapable d'absorber la moindre donnée, la fonction doit retourner -1 avec une erreur EAGAIN sans écrire de données.

Cette valeur peut être récupérée avec Tcl_ChannelOutputProc, qui retourne un pointeur vers la fonction.

SEEKPROC ET WIDESEEKPROC

Le champ seekProc contient l'adresse d'une fonction appelée par la couche générique pour déplacer le point d'accès auquel les opérations d'entrée ou de sortie ultérieures seront appliquées. SeekProc doit correspondre au prototype suivant :

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

L'argument instanceData est la même valeur que celle donnée à Tcl_CreateChannel lors de la création de ce canal. Offset et seekMode ont la même signification que pour la procédure Tcl_Seek (décrite dans l'entrée de manuel de Tcl_OpenFileChannel).

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générique pour retourner les valeurs errno de la fonction. La fonction doit définir cette variable à un code d'erreur POSIX si une erreur se produit. La fonction doit stocker un code d'erreur EINVAL si le type de canal n'implémente pas le déplacement.

La valeur de retour est le nouveau point d'accès ou -1 en cas d'erreur. Si une erreur s'est produite, la fonction ne doit pas déplacer le point d'accès.

S'il existe un champ seekProc non NULL, le champ wideSeekProc peut contenir l'adresse d'une fonction alternative à utiliser qui gère les décalages larges (c'est-à-dire supérieurs à 32 bits), permettant ainsi les déplacements dans des fichiers de plus de 2 Go. Le wideSeekProc sera appelé de préférence au seekProc, mais les deux doivent être définis si le wideSeekProc est défini. WideSeekProc doit correspondre au prototype suivant :

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

Les arguments et les valeurs de retour signifient la même chose qu'avec seekProc ci-dessus, sauf que le type des décalages et le type de retour sont différents.

La valeur seekProc peut être récupérée avec Tcl_ChannelSeekProc, qui retourne un pointeur vers la fonction, et de même, le wideSeekProc peut être récupéré avec Tcl_ChannelWideSeekProc.

SETOPTIONPROC

Le champ setOptionProc contient l'adresse d'une fonction appelée par la couche générique pour définir une option spécifique au type de canal sur un canal. setOptionProc doit correspondre au prototype suivant :

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

optionName est le nom d'une option à définir, et newValue est la nouvelle valeur de cette option, sous forme de chaîne. instanceData est la même valeur que celle donnée à Tcl_CreateChannel lors de la création de ce canal. La fonction doit effectuer l'action spécifique au type de canal requise pour implémenter la nouvelle valeur de l'option.

Certaines options sont gérées par le code générique et cette fonction n'est jamais appelée pour les définir, par exemple -blockmode. D'autres options sont spécifiques à chaque type de canal et la procédure setOptionProc du pilote de canal sera appelée pour les implémenter. Le champ setOptionProc peut être NULL, ce qui indique que ce type de canal ne prend en charge aucune option spécifique au type.

Si la valeur de l'option est modifiée avec succès vers la nouvelle valeur, la fonction retourne TCL_OK. Elle doit appeler Tcl_BadChannelOption, qui retourne elle-même TCL_ERROR si le nom de l'option optionName n'est pas reconnu. Si newValue spécifie une valeur pour l'option qui n'est pas prise en charge ou si une erreur d'appel système se produit, la fonction doit laisser un message d'erreur dans le résultat de interp si interp n'est pas NULL. La fonction doit également appeler Tcl_SetErrno pour stocker un code d'erreur POSIX approprié.

Cette valeur peut être récupérée avec Tcl_ChannelSetOptionProc, qui retourne un pointeur vers la fonction.

GETOPTIONPROC

Le champ getOptionProc contient l'adresse d'une fonction appelée par la couche générique pour obtenir la valeur d'une option spécifique au type de canal sur un canal. getOptionProc doit correspondre au prototype suivant :

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        Tcl_DString *optionValue);

OptionName est le nom d'une option prise en charge par ce type de canal. Si le nom de l'option n'est pas NULL, la fonction stocke sa valeur actuelle, sous forme de chaîne, dans la chaîne dynamique Tcl optionValue. Si optionName est NULL, la fonction stocke dans optionValue une liste alternée de toutes les options prises en charge et de leurs valeurs actuelles. En cas de succès, la fonction retourne TCL_OK. Elle doit appeler Tcl_BadChannelOption, qui retourne elle-même TCL_ERROR si le nom de l'option op

WATCHPROC

Le champ watchProc contient l'adresse d'une fonction appelée par la couche générale pour initialiser le mécanisme de notification des événements d'intérêt sur ce canal. WatchProc doit correspondre au prototype suivant :

typedef void Tcl_DriverWatchProc(
        ClientData instanceData,
        int mask);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument mask est une combinaison OR de TCL_READABLE, TCL_WRITABLE et TCL_EXCEPTION ; il indique les événements pour lesquels l'appelant souhaite être notifié sur ce canal.

La fonction doit initialiser des mécanismes spécifiques au type de périphérique pour notifier lorsqu'un événement d'intérêt est présent sur le canal. Lorsqu'un événement d'intérêt se produit sur le canal, le pilote de canal doit appeler Tcl_NotifyChannel pour informer le module de canal général. Le pilote doit éviter que d'autres pilotes de canal ou sources de rappels ne se bloquent en appelant Tcl_NotifyChannel trop fréquemment. L'équité peut être garantie en appelant la file d'événements de Tcl, permettant à l'événement de canal d'être planifié séquentiellement avec d'autres événements. Voir la description de Tcl_QueueEvent pour les détails sur la planification d'un événement.

Cette valeur peut être récupérée avec Tcl_ChannelWatchProc, qui renvoie une adresse à la fonction.

GETHANDLEPROC

Le champ getHandleProc contient l'adresse d'une fonction appelée par la couche générale pour récupérer un descripteur spécifique au canal. GetHandleProc doit correspondre au prototype suivant :

typedef int Tcl_DriverGetHandleProc(
        ClientData instanceData,
        int direction,
        ClientData *handlePtr);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument direction est TCL_READABLE pour récupérer le descripteur utilisé pour l'entrée, ou TCL_WRITABLE pour récupérer le descripteur utilisé pour la sortie.

Si l'implémentation du canal a des descripteurs spécifiques, la fonction doit récupérer le descripteur approprié en fonction de l'argument direction. Le descripteur doit être stocké à l'emplacement indiqué par handlePtr, et TCL_OK doit être renvoyé. Si le canal n'est pas ouvert pour la direction spécifiée, ou si l'implémentation du canal n'utilise pas de descripteurs spécifiques, la fonction doit renvoyer TCL_ERROR.

Cette valeur peut être récupérée avec Tcl_ChannelGetHandleProc, qui renvoie une adresse à la fonction.

FLUSHPROC

Le champ flushProc est actuellement réservé pour une utilisation future. Il doit être défini à NULL. FlushProc doit correspondre au prototype suivant :

typedef int Tcl_DriverFlushProc(
        ClientData instanceData);

Cette valeur peut être récupérée avec Tcl_ChannelFlushProc, qui renvoie une adresse à la fonction.

HANDLERPROC

Le champ handlerProc contient l'adresse d'une fonction appelée par la couche générale pour notifier le canal qu'un événement s'est produit. Il doit être défini pour les pilotes de canal empilés qui souhaitent être notifiés des événements se produisant sur le canal sous-jacent (empilé). HandlerProc doit correspondre au prototype suivant :

typedef int Tcl_DriverHandlerProc(
        ClientData instanceData,
        int interestMask);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. InterestMask est une combinaison OR de TCL_READABLE ou TCL_WRITABLE ; il indique le type d'événement qui s'est produit sur ce canal.

Cette valeur peut être récupérée avec Tcl_ChannelHandlerProc, qui renvoie une adresse à la fonction.

THREADACTIONPROC

Le champ threadActionProc contient l'adresse de la fonction appelée par la couche générale lorsqu'un canal est créé, fermé ou déplacé vers un autre thread, c'est-à-dire lorsque l'état spécifique au thread du pilote peut devoir être initialisé ou mis à jour. Il peut être NULL. L'action TCL_CHANNEL_THREAD_REMOVE est utilisée pour notifier au pilote qu'il doit mettre à jour ou supprimer toutes les données spécifiques au thread qu'il conserve pour le canal.

L'action TCL_CHANNEL_THREAD_INSERT est utilisée pour notifier au pilote qu'il doit mettre à jour ou initialiser toutes les données spécifiques au thread qu'il conserve en utilisant le thread actuel comme associé. Voir Tcl_CutChannel et Tcl_SpliceChannel pour plus de détails.

typedef void Tcl_DriverThreadActionProc(
        ClientData instanceData,
        int action);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal.

Ces valeurs peuvent être récupérées avec Tcl_ChannelThreadActionProc, qui renvoie une adresse à la fonction.

TRUNCATEPROC

Le champ truncateProc contient l'adresse de la fonction appelée par la couche générale lorsqu'un canal est tronqué à une longueur spécifiée. Il peut être NULL.

typedef int Tcl_DriverTruncateProc(
        ClientData instanceData,
        Tcl_WideInt length);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal, et length est la nouvelle longueur du fichier sous-jacent, qui ne doit pas être négative. Le résultat doit être 0 en cas de succès ou un code d'erreur (approprié pour l'utilisation avec Tcl_SetErrno) en cas d'échec.

Ces valeurs peuvent être récupérées avec Tcl_ChannelTruncateProc, qui renvoie une adresse à la fonction.

TCL_BADCHANNELOPTION

Cette procédure génère un message d'erreur "mauvaise option" dans un interpréteur (optionnel). Elle est utilisée par les pilotes de canal lorsqu'une option invalide est demandée. Son but est de concaténer la liste des options génériques à la liste spécifique et de factoriser le message d'erreur des options génériques.

Renvoie toujours TCL_ERROR.

Un message d'erreur est généré dans la valeur de résultat de interp pour indiquer qu'une instruction a été appelée avec une option invalide. Le message est de la forme :

    mauvaise option "blah" : devrait être l'une des
    <...options génériques...>+<...options spécifiques...>
par exemple : 
    mauvaise option "-blah" : devrait être l'une des -blocking,
    -buffering, -buffersize, -eofchar, -translation,
    -peername, ou -sockname
lorsqu'elle est appelée avec optionList égal à "peername sockname".

"blah" est l'argument optionName et " <options spécifiques>" est une liste de mots spécifiques séparés par des espaces. La fonction s'occupe d'insérer des tirets avant chaque option, des virgules après et un "ou" avant la dernière option.

OLD CHANNEL TYPES

La structure originale (8.3.1 et versions antérieures) contient les champs suivants :

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
} Tcl_ChannelType;

Bien qu'il soit possible de créer des canaux avec la structure mentionnée, le code interne du canal déterminera la version. Il est essentiel d'utiliser la nouvelle structure Tcl_ChannelType si vous créez un pilote de canal empilé en raison de problèmes dans l'implémentation précédente des canaux empilés (8.2.0 à 8.3.1).

Avant 8.4.0 (c'est-à-dire pendant les dernières versions de 8.3 et une partie du début du cycle de développement de 8.4), la structure Tcl_ChannelType comportait les champs suivants :

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_ChannelTypeVersion version;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Lorsque la structure précédente est enregistrée comme type de canal, le champ version doit toujours être TCL_CHANNEL_VERSION_2.
