DESCRIPTION

Le mécanisme de canaux Tcl fournit un mécanisme indépendant des périphériques et indépendant de la plateforme pour effectuer des opérations d'entrée et de sortie mises en tampon sur une variété de types de fichiers, de sockets et de périphériques. Le mécanisme de canaux est extensible aux nouveaux types de canaux, en fournissant un pilote de canal de bas niveau pour le nouveau type ; l'interface du pilote de canal est décrite dans l'entrée de manuel de Tcl_CreateChannel. Le mécanisme de canaux fournit un schéma de mise en tampon calqué sur les E/S standard d'Unix, et il permet également les E/S non bloquantes sur les canaux.

Les procédures décrites dans cette entrée de manuel comprennent les API C de la couche générique de l'architecture des canaux. Pour une description de l'architecture des pilotes de canaux et de la manière d'implémenter des pilotes de canaux pour de nouveaux types de canaux, consultez l'entrée de manuel de Tcl_CreateChannel.

TCL_OPENFILECHANNEL

Tcl_OpenFileChannel ouvre un fichier spécifié par fileName et renvoie un handle de canal qui peut être utilisé pour lire et écrire dans le fichier. Cette API est calquée sur la fonction fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande open de Tcl lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, Tcl_OpenFileChannel renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_OpenFileChannel laisse un message d'erreur dans le résultat de interp après toute erreur. Depuis Tcl 8.4, la valeur basée sur l'API Tcl_FSOpenFileChannel doit être utilisée de préférence à Tcl_OpenFileChannel dans tous les cas.

Le canal nouvellement créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, il faut utiliser Tcl_RegisterChannel, décrit ci-dessous. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, la création du nouveau canal l'affecte également comme remplacement du canal standard.

TCL_OPENCOMMANDCHANNEL

Tcl_OpenCommandChannel fournit une interface de niveau C pour les fonctionnalités des commandes exec et open. Il crée une séquence de sous-processus spécifiés par les arguments argv et argc et renvoie un canal qui peut être utilisé pour communiquer avec ces sous-processus. L'argument flags indique le type de communication que vous aurez avec le pipeline de commandes.

Si le flag TCL_STDIN est défini, le canal d'entrée standard du premier sous-processus est lié au canal : écrire dans le canal fournit l'entrée au sous-processus. Si le flag TCL_STDIN n'est pas défini, le canal d'entrée standard du premier sous-processus sera le même que le canal d'entrée standard de cette application. Si le flag TCL_STDOUT est défini, la sortie standard des derniers sous-processus peut être lue à partir du canal ; sinon, elle est envoyée à la sortie standard de cette application. Si le flag TCL_STDERR est défini, la sortie d'erreur standard de tous les sous-processus est renvoyée au canal et génère une erreur lorsque le canal est fermé ; sinon, elle est envoyée à la sortie d'erreur standard de cette application. Si le flag TCL_ENFORCE_MODE n'est pas défini, les arguments argc et argv peuvent rediriger les handles standards pour remplacer les flags TCL_STDIN, TCL_STDOUT et TCL_STDERR ; s'il est défini, il s'agit d'une erreur si argc et argv tentent de remplacer les canaux standards pour lesquels TCL_STDIN, TCL_STDOUT et TCL_STDERR ont été définis.

Si une erreur se produit lors de l'ouverture du canal, Tcl_OpenCommandChannel renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, Tcl_OpenCommandChannel laisse un message d'erreur dans le résultat de l'interpréteur. interp ne peut pas être NULL.

Le canal nouvellement créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, il faut utiliser Tcl_RegisterChannel, décrit ci-dessous. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, la création du nouveau canal l'affecte également comme remplacement du canal standard.

TCL_MAKEFILECHANNEL

Tcl_MakeFileChannel crée un Tcl_Channel à partir d'un handle de fichier existant et spécifique à la plateforme. Le canal nouvellement créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, il faut utiliser Tcl_RegisterChannel, décrit ci-dessous. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, la création du nouveau canal l'affecte également comme remplacement du canal standard.

TCL_GETCHANNEL

Tcl_GetChannel renvoie un canal étant donné le channelName utilisé pour le créer avec Tcl_CreateChannel et un pointeur vers l'interpréteur dans interp. Si aucun canal enregistré n'existe dans cet interpréteur sous ce nom, la procédure renvoie NULL. Si l'argument modePtr n'est pas NULL, il pointe vers une variable entière qui recevra une combinaison OR de TCL_READABLE et TCL_WRITABLE indiquant si le canal est ouvert en lecture et en écriture.

Tcl_GetChannelNames et Tcl_GetChannelNamesEx écrivent les noms des canaux enregistrés dans le résultat de l'interpréteur sous forme de liste. Tcl_GetChannelNamesEx filtrera ces noms selon le pattern. Si pattern est NULL, aucun filtrage ne sera effectué. La valeur de retour est TCL_OK s'il n'y a pas eu d'erreurs lors de l'écriture dans le résultat, sinon TCL_ERROR, et le message d'erreur est laissé dans le résultat de l'interpréteur.

TCL_REGISTERCHANNEL

Tcl_RegisterChannel ajoute un canal à la collection de canaux accessibles dans interp. Après cet appel, les programmes Tcl exécutés dans cet interpréteur peuvent faire référence au canal par le nom donné lors de l'appel à Tcl_CreateChannel. Après cet appel, le canal devient la propriété de l'interpréteur, et l'utilisateur doit éviter d'appeler Tcl_Close sur le canal ; le canal est fermé automatiquement lorsqu'il est désenregistré de l'interpréteur.

Le code exécuté en dehors de tout interpréteur peut appeler Tcl_RegisterChannel avec interp comme NULL, indiquant qu'il souhaite conserver une référence à ce canal. Par la suite, le canal peut être enregistré dans un interpréteur Tcl et ne sera fermé que lorsque les appels correspondants à Tcl_UnregisterChannel auront été effectués. Cela permet à un code non associé à un interpréteur de conserver une référence à un canal également enregistré dans un interpréteur Tcl.

Cette procédure interagit avec le code qui gère les canaux standards. Si aucun canal standard n'est initialisé avant le premier appel à Tcl_RegisterChannel, ils seront initialisés par cet appel. Voir Tcl_StandardChannels pour une généralité sur les canaux standards et le comportement de la bibliothèque Tcl à leur égard.

TCL_UNREGISTERCHANNEL

Tcl_UnregisterChannel supprime un canal de la collection de canaux accessibles dans interp. Après cet appel, les programmes Tcl ne pourront plus utiliser le nom du canal pour y faire référence dans cet interpréteur. Si cette opération supprime la dernière référence au canal dans n'importe quel interpréteur, le canal est également fermé et détruit.

Le code non associé à un interpréteur peut appeler Tcl_UnregisterChannel avec interp comme NULL, indiquant à Tcl qu'il ne conserve plus de référence à ce canal. S'il s'agit de la dernière référence, le canal est fermé. Tcl_UnregisterChannel est très similaire à Tcl_DetachChannel sauf qu'il ferme également le canal s'il n'y a plus de références à celui-ci.

TCL_DETACHCHANNEL

Tcl_DetachChannel supprime un canal de la collection de canaux accessibles dans interp. Après cet appel, les programmes Tcl ne pourront plus utiliser le nom du canal pour y faire référence dans cet interpréteur. Au-delà de cela, cette commande n'a aucun effet supplémentaire. Elle ne peut pas être utilisée sur les canaux standards (stdout, stderr, stdin), et renverra TCL_ERROR si on lui passe l'un de ces canaux.

Le code non associé à un interpréteur peut appeler Tcl_DetachChannel avec interp comme NULL, indiquant à Tcl qu'il ne conserve plus de référence à ce canal. S'il s'agit de la dernière référence, il n'est pas fermé comme avec Tcl_UnregisterChannel.

TCL_ISSTANDARDCHANNEL

Tcl_IsStandardChannel teste si un canal est l'un des trois canaux standards, stdin, stdout ou stderr. Si c'est le cas, il renvoie 1, sinon 0.

Aucune tentative n'est faite pour vérifier si le canal donné ou les canaux standards sont initialisés ou valides.

TCL_CLOSE

Tcl_Close détruit le canal channel, qui doit désigner un canal actuellement ouvert. Le canal ne doit pas être enregistré dans un interpréteur lorsque Tcl_Close est appelé. La sortie bufferisée est écrite sur le périphérique de sortie du canal avant sa destruction, et toute entrée bufferisée est supprimée. S'il s'agit d'un canal bloquant, l'appelant ne retourne pas tant que toutes les données bufferisées n'ont pas été envoyées à la sortie du canal. S'il s'agit d'un canal non bloquant et qu'il y a des données bufferisées qui ne peuvent pas être écrites sans bloquer, l'appelant retourne immédiatement ; la sortie est envoyée en arrière-plan et le canal est fermé lorsque toutes les données bufferisées ont été envoyées. Dans ce cas, les erreurs lors du nettoyage ne sont pas signalées.

Si le canal a été fermé avec succès, Tcl_Close renvoie TCL_OK. Si une erreur se produit, Tcl_Close renvoie TCL_ERROR et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. Si le canal est fermé de manière synchrone et qu'une erreur se produit lors de la fermeture et que interp n'est pas NULL, un message d'erreur est laissé dans le résultat de l'interpréteur.

Note : il n'est pas sûr d'appeler Tcl_Close sur un canal enregistré avec Tcl_RegisterChannel ; voir la documentation de Tcl_RegisterChannel pour plus de détails. Si le canal a été donné comme chan dans un appel à Tcl_RegisterChannel, vous devez utiliser Tcl_UnregisterChannel, qui appelle Tcl_Close en interne lorsque tous les appels à Tcl_RegisterChannel ont été mis en correspondance avec des appels à Tcl_UnregisterChannel.

TCL_READCHARS ET TCL_READ

Tcl_ReadChars consomme des octets du channel, les convertit en UTF-8 selon le codage du canal et stocke les données produites dans la représentation de readObjPtr. La valeur de retour de Tcl_ReadChars est le nombre de caractères, jusqu'à charsToRead, qui ont été stockés dans readObjPtr. Si une erreur se produit lors de la lecture, la valeur de retour est -1 et Tcl_ReadChars enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno.

TCL_READCHARS, TCL_READOBJ, ET TCL_READ

La valeur -1 pour rsToRead causera à la commande de lire tous les caractères actuellement disponibles (sans blocage) ou tout jusqu'à l'EOF (mode bloquant).

La valeur de retour peut être inférieure à la valeur à lire, indiquant que moins de données que demandé étaient disponibles. C'est ce qu'on appelle une lecture courte. En mode bloquant, cela ne peut arriver qu'à une fin de fichier. En mode non bloquant, une lecture courte peut également se produire s'il n'y a pas assez d'entrée disponible actuellement : Tcl_ReadChars retourne un compte court plutôt que d'attendre plus de données.

Si le canal est en mode bloquant, une valeur de retour de zéro indique une condition de fin de fichier. Si le canal est en mode non bloquant, une valeur de retour de zéro indique soit qu'aucune entrée n'est disponible actuellement, soit une condition de fin de fichier. Utilisez Tcl_Eof et Tcl_InputBlocked pour savoir laquelle de ces conditions s'est réellement produite.

Tcl_ReadChars traduit les diverses représentations de fin de ligne en la représentation interne canonique \n selon le mode de reconnaissance de fin de ligne actuel. La reconnaissance de fin de ligne et les divers modes spécifiques à la plateforme sont décrits dans l'entrée de manuel de la commande Tcl fconfigure.

En tant qu'optimisation des performances, lors de la lecture à partir d'un canal avec l'encodage binary, les octets ne sont pas convertis en UTF-8 lorsqu'ils sont lus. Au lieu de cela, ils sont stockés dans la représentation interne de readObjPtr en tant que valeur de tableau d'octets. La représentation de chaîne de cette valeur ne sera construite que si elle est nécessaire (par exemple, en raison d'un appel à Tcl_GetStringFromObj). De cette façon, des données orientées octets peuvent être lues à partir d'un canal, manipulées en appelant Tcl_GetByteArrayFromObj et les fonctions associées, puis écrites dans un canal sans le coût de la conversion vers ou depuis UTF-8.

Tcl_Read est similaire à Tcl_ReadChars, sauf qu'il ne fait pas de conversions d'encodage, quel que soit l'encodage du canal. Il est déprécié et existe pour des raisons de compatibilité ascendante avec les extensions Tcl non internationalisées. Il consomme des octets du channel et les stocke dans readBuf, en effectuant des traductions de fin de ligne au passage. La valeur de retour de Tcl_Read est le nombre d'octets, jusqu'à bytesToRead, écrits dans readBuf. Le tampon produit par Tcl_Read n'est pas terminé par null. Son contenu est valide à partir de la position zéro jusqu'à, mais sans inclure, la position indiquée par la valeur de retour.

Tcl_ReadRaw est identique à Tcl_Read mais ne compense pas l'empilement. Alors que Tcl_Read (et les autres fonctions de l'API) obtiennent toujours leurs données du canal le plus haut dans la pile dont le canal fourni fait partie, Tcl_ReadRaw ne le fait pas. Ainsi, cette fonction est uniquement utilisable pour les pilotes de canaux transformationnels, c'est-à-dire les pilotes utilisés au milieu d'une pile de canaux, pour déplacer les données du canal inférieur dans la transformation.

TCL_GETSOBJ ET TCL_GETS

Tcl_GetsObj consomme des octets du channel, convertissant les octets en UTF-8 en fonction de l'encodage du canal, jusqu'à ce qu'une ligne complète d'entrée ait été vue. Si l'encodage du canal est binary, chaque octet lu du canal est traité comme un caractère Unicode individuel. Tous les caractères de la ligne, à l'exception du ou des caractères de fin de ligne terminaux, sont ajoutés à la représentation de chaîne de lineObjPtr. Le ou les caractères de fin de ligne sont lus et rejetés.

Si une ligne a été lue avec succès, la valeur de retour est supérieure ou égale à zéro et indique le nombre d'octets stockés dans lineObjPtr. Si une erreur se produit, Tcl_GetsObj retourne -1 et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. Tcl_GetsObj retourne également -1 si la fin du fichier est atteinte ; la procédure Tcl_Eof peut être utilisée pour distinguer une erreur d'une condition de fin de fichier.

Si le canal est en mode non bloquant, la valeur de retour peut également être -1 s'il n'y avait pas de données disponibles ou si les données disponibles ne contenaient pas de caractère de fin de ligne. Lorsque -1 est retourné, la procédure Tcl_InputBlocked peut être appelée pour déterminer si le canal est bloqué en raison de l'indisponibilité des entrées.

Tcl_Gets est identique à Tcl_GetsObj sauf que les caractères résultants sont ajoutés à la chaîne dynamique fournie par lineRead plutôt qu'à une valeur Tcl.

TCL_UNGETS

Tcl_Ungets est utilisé pour ajouter des données à la file d'attente d'entrée d'un canal, à la tête ou à la queue de la file. Le pointeur input pointe vers les données à ajouter. La longueur de l'entrée à ajouter est donnée par inputLen. Une valeur non nulle de addAtEnd indique que les données doivent être ajoutées à la fin de la file ; sinon, elles seront ajoutées au début de la file. Si channel a un EOF "collant" réglé, aucune donnée ne sera ajoutée à la file d'attente d'entrée. Tcl_Ungets retourne inputLen ou -1 si une erreur se produit.

TCL_WRITECHARS, TCL_WRITEOBJ, ET TCL_WRITE

Tcl_WriteChars accepte bytesToWrite octets de données caractères à charBuf. Les caractères UTF-8 dans le tampon sont convertis vers l'encodage du canal et mis en file d'attente pour la sortie vers channel. Si bytesToWrite est négatif, Tcl_WriteChars s'attend à ce que charBuf soit terminé par null et il sort tout jusqu'à la null.

Les données mises en file d'attente pour la sortie peuvent ne pas apparaître immédiatement sur le périphérique de sortie, en raison de la mise en mémoire tampon interne. Si les données doivent apparaître immédiatement, appelez Tcl_Flush après l'appel à Tcl_WriteChars, ou définissez l'option -buffering sur le canal à none. Si vous souhaitez que les données apparaissent dès qu'une ligne complète est acceptée pour la sortie, définissez l'option -buffering sur le canal en mode line.

La valeur de retour de Tcl_WriteChars est un compte du nombre d'octets qui ont été acceptés pour la sortie vers le canal. C'est soit supérieur à zéro pour indiquer le succès, soit -1 pour indiquer qu'une erreur s'est produite. Si une erreur se produit, Tcl_WriteChars enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno.

Les caractères de nouvelle ligne dans les données de sortie sont traduits en séquences de fin de ligne spécifiques à la plateforme selon l'option -translation pour le canal. Ceci est fait même si le canal n'a pas d'encodage.

Tcl_WriteObj est similaire à Tcl_WriteChars sauf qu'il accepte une valeur Tcl dont le contenu sera sorti vers le canal. Les caractères UTF-8 dans la représentation de chaîne de writeObjPtr sont convertis vers l'encodage du canal et mis en file d'attente pour la sortie vers channel. En tant qu'optimisation des performances, lors de l'écriture sur un canal avec l'encodage binary, les caractères UTF-8 ne sont pas convertis lors de leur écriture. Au lieu de cela, les octets dans la représentation interne de writeObjPtr en tant que valeur de tableau d'octets sont écrits sur le canal. La représentation de tableau d'octets de la valeur sera construite si nécessaire. De cette façon, des données orientées octets peuvent être lues à partir d'un canal, manipulées en appelant Tcl_GetByteArrayFromObj et les fonctions associées, puis écrites dans un canal sans le coût de la conversion vers ou depuis UTF-8.

Tcl_Write est similaire à Tcl_WriteChars sauf qu'il ne fait pas de conversions d'encodage, quel que soit l'encodage du canal. Il est déprécié et existe pour des raisons de compatibilité ascendante avec les extensions Tcl non internationalisées. Il accepte bytesToWrite octets de données à byteBuf et les met en file d'attente pour la sortie vers channel. Si bytesToWrite est négatif, Tcl_Write s'attend à ce que byteBuf soit terminé par null et il sort tout jusqu'à la null.

Tcl_WriteRaw est identique à Tcl_Write mais ne compense pas l'empilement. Alors que Tcl_Write (et les autres fonctions de l'API) alimentent toujours leur entrée dans le canal le plus haut dans la pile dont le canal fourni fait partie, Tcl_WriteRaw ne le fait pas. Ainsi, cette fonction est uniquement utilisable pour les pilotes de canaux transformationnels, c'est-à-dire les pilotes utilisés au milieu d'une pile de canaux, pour déplacer les données de la transformation vers le canal inférieur.

TCL_FLUSH

Tcl_Flush provoque l'écriture de toutes les données de sortie tamponnées pour channel vers son fichier ou périphérique sous-jacent dès que possible. Si le canal est en mode bloquant, l'appel ne retourne pas tant que toutes les données tamponnées n'ont pas été envoyées au canal ou qu'une erreur ne s'est pas produite. L'appel retourne immédiatement si le canal n'est pas bloquant ; il démarre une vidange en arrière-plan qui écrira les données tamponnées vers le canal éventuellement, aussi vite que le canal peut les absorber.

La valeur de retour est normalement TCL_OK. Si une erreur se produit, Tcl_Flush retourne TCL_ERROR et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno.

TCL_SEEK

Tcl_Seek déplace le point d'accès dans channel où les données ultérieures seront lues ou écrites. La sortie tamponnée est vidée vers le canal et l'entrée tamponnée est rejetée, avant l'opération de recherche.

Tcl_Seek retourne normalement le nouveau point d'accès. Si une erreur se produit, Tcl_Seek retourne -1 et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. Après une erreur, le point d'accès peut avoir été déplacé ou non.

TCL_TELL

Tcl_Tell retourne le point d'accès actuel pour un canal. La valeur retournée est -1 si le canal ne prend pas en charge la recherche.

TCL_TRUNCATECHANNEL

Tcl_TruncateChannel tronque le fichier sous-jacent de channel à une longueur donnée de length octets. Il retourne TCL_OK si l'opération a réussi, et TCL_ERROR sinon.

TCL_GETCHANNELOPTION

Tcl_GetChannelOption récupère, dans optionValue, la valeur d'une des options actuellement en vigueur pour un canal, ou une liste de toutes les options et leurs valeurs. L'argument channel identifie le canal pour lequel interroger une option ou récupérer toutes les options et leurs valeurs. Si optionName n'est pas NULL, c'est le nom de l'option à interroger ; la valeur de l'option est copiée dans la chaîne dynamique Tcl désignée par optionValue. Si optionName est NULL, la fonction stocke une liste alternée de noms d'options et de leurs valeurs dans optionValue.

, en utilisant une série d'appels à Tcl_DStringAppendElement. Les différentes options préexistantes et leurs valeurs possibles sont décrites dans la page de manuel de la commande Tcl fconfigure. D'autres options peuvent être ajoutées par chaque type de canal. Ces options spécifiques au type de canal sont décrites dans la page de manuel de la commande Tcl qui crée un canal de ce type ; par exemple, les options supplémentaires pour les canaux basés sur TCP sont décrites dans la page de manuel de la commande Tcl socket. La procédure renvoie normalement TCL_OK. Si une erreur se produit, elle renvoie TCL_ERROR et appelle Tcl_SetErrno pour stocker un code d'erreur POSIX approprié.

TCL_SETCHANNELOPTION

Tcl_SetChannelOption définit une nouvelle valeur newValue pour une option optionName sur le channel. La procédure renvoie normalement TCL_OK. Si une erreur se produit, elle renvoie TCL_ERROR ; de plus, si interp n'est pas NULL, Tcl_SetChannelOption laisse un message d'erreur dans le résultat de l'interpréteur.

TCL_EOF

Tcl_Eof renvoie une valeur non nulle si channel a rencontré une fin de fichier lors de la dernière opération d'entrée.

TCL_INPUTBLOCKED

Tcl_InputBlocked renvoie une valeur non nulle si channel est en mode non bloquant et que la dernière opération d'entrée a renvoyé moins de données que demandé car il n'y avait pas suffisamment de données disponibles. L'appel renvoie toujours zéro si le canal est en mode bloquant.

TCL_INPUTBUFFERED

Tcl_InputBuffered renvoie le nombre d'octets d'entrée actuellement mis en mémoire tampon dans les tampons internes pour un canal. Si le canal n'est pas ouvert en lecture, cette fonction renvoie toujours zéro.

TCL_OUTPUTBUFFERED

Tcl_OutputBuffered renvoie le nombre d'octets de sortie actuellement mis en mémoire tampon dans les tampons internes pour un canal. Si le canal n'est pas ouvert en écriture, cette fonction renvoie toujours zéro.

PLATFORM ISSUES

Les descripteurs renvoyés par Tcl_GetChannelHandle dépendent de la plateforme et du type de canal. Sur les plateformes Unix, le descripteur est toujours un descripteur de fichier Unix tel que renvoyé par l'appel système open. Sur les plateformes Windows, le descripteur est un HANDLE de fichier lorsque le canal a été créé avec Tcl_OpenFileChannel, Tcl_OpenCommandChannel, ou Tcl_MakeFileChannel. D'autres types de canaux peuvent renvoyer un type de descripteur différent sur les plateformes Windows.
