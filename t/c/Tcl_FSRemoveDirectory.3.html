FONCTIONS DE L'API FS

Tcl_FSCopyFile tente de copier le fichier spécifié par srcPathPtr vers le nom de fichier spécifié par destPathPtr. Si les deux chemins spécifiés se trouvent sur le même système de fichiers (déterminé par Tcl_FSGetFileSystemForPath), la fonction de copie de fichier du système de fichiers est appelée. Sinon, elle renvoie -1 et définit la valeur globale de la variable C errno à EXDEV (indiquant un lien croisé).

Tcl_FSCopyDirectory tente de copier le répertoire spécifié par srcPathPtr vers le nom de fichier spécifié par destPathPtr. Si les deux chemins spécifiés se trouvent sur le même système de fichiers (déterminé par Tcl_FSGetFileSystemForPath), la fonction de copie de répertoire du système de fichiers est appelée. Sinon, elle renvoie -1 et définit la valeur globale de la variable C errno à EXDEV (indiquant un lien croisé).

Tcl_FSCreateDirectory tente de créer le répertoire spécifié par pathPtr en appelant la fonction de création de répertoire du système de fichiers propriétaire.

Tcl_FSDeleteFile tente de supprimer le fichier spécifié par pathPtr en appelant la fonction de suppression de fichier du système de fichiers.

Tcl_FSRemoveDirectory tente de supprimer le répertoire spécifié par pathPtr en appelant la fonction de suppression de répertoire du système de fichiers.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire spécifié par srcPathPtr vers le nom de fichier spécifié par destPathPtr. Si les deux chemins spécifiés se trouvent sur le même système de fichiers (déterminé par Tcl_FSGetFileSystemForPath), la fonction de renommage de fichier du système de fichiers est appelée. Sinon, elle renvoie -1 et définit la valeur globale de la variable C errno à EXDEV (indiquant un lien croisé).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction de listage de volumes non nulle et lui demande de renvoyer sa liste de volumes racines. Elle accumule les valeurs renvoyées dans une liste qui est renvoyée à l'appelant (avec un compteur de références de 0).

Tcl_FSEvalFileEx lit le fichier spécifié par pathPtr en utilisant le jeu de caractères identifié par encodingName et évalue son contenu comme un script Tcl. Elle renvoie les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, le jeu de caractères du système est utilisé pour lire le contenu du fichier. Si le fichier n'a pas pu être lu, une erreur Tcl est renvoyée pour décrire pourquoi le fichier n'a pas pu être lu. Le caractère de fin de fichier pour les fichiers est \x1A (^Z) pour tous les systèmes. Si vous voulez utiliser \x1A dans des comparaisons de chaînes, vous pouvez le faire, il sera sûrement remplacé par l'interpréteur Tcl par \x1A. Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours le jeu de caractères du système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement le code binaire d'un fichier en mémoire et renvoie les adresses de deux procédures dans le fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel pathPtr appartient est appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes virtuels ne l'implémentent pas en raison des limitations du système d'exploitation lors du chargement de code binaire), Tcl tente de copier le fichier vers un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile annule cette opération, demandant au processus de supprimer la bibliothèque indiquée par loadHandle. Notez que, contrairement à la commande unload, cela ne donne pas à la bibliothèque la possibilité de nettoyer.

Les deux fonctions ci-dessus renvoient un code d'achèvement Tcl standard. En cas d'erreur, un message d'erreur est placé dans le résultat de interp.

Le jeton fourni par la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher tous les fichiers correspondant à un modèle donné dans un répertoire. La fonction appropriée pour le système de fichiers auquel pathPtr appartient est appelée.

La valeur renvoyée est un résultat Tcl standard indiquant s'il y a eu une erreur dans le globbing. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Remarque : Le code de glob implémente des modèles récursifs en interne, de sorte que cette fonction ne sera appelée qu'avec des modèles simples, qui peuvent être mis en correspondance à l'aide de la logique de string match. Pour gérer la récursion, Tcl appelle cette fonction fréquemment en demandant uniquement aux répertoires de renvoyer. Un cas spécial d'appel avec un modèle nul indique que le chemin doit uniquement être vérifié pour le bon type.

Tcl_FSLink remplace la version de la bibliothèque de readlink et étend la fonctionnalité pour créer des liens. La fonction appropriée pour le système de fichiers auquel linkNamePtr appartient est appelée.

Si toPtr est NULL, une action de lecture de lien est effectuée. Le résultat est un objet Tcl spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient entièrement à l'appelant, qui doit appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl doit créer un lien d'un des types passés dans linkAction. Ce drapeau est une combinaison OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'il y a un choix (c'est-à-dire plus d'un drapeau est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur renvoyée doit être toPtr (qui appartient déjà à l'appelant). S'il ne peut pas être créé, NULL est renvoyé.

Tcl_FSLstat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Aucun droit d'accès au fichier n'est requis pour obtenir ces informations, mais des droits de recherche sur tous les répertoires mentionnés dans le chemin menant au fichier sont requis. La structure Tcl_StatBuf inclut des informations sur le périphérique, l'inode (0 sous Windows), le mode de privilège, le nombre de liens (1 sous Windows), l'UID (0 sous Windows), le GID (0 sous Windows), le rdev (identique au périphérique sous Windows), la taille, la dernière

Conservez la structure de fichiers. Accès en temps, temps de modification et dernier changement de métadonnées. Voir PORTABLE STAT RESULT API pour une description de la manière d'écrire du code portable pour distribuer et accéder à la structure Tcl_StatBuf. Si path existe, Tcl_FSLstat renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé et aucune donnée stat n'est fournie. Tcl_FSUtime remplace la version de la bibliothèque utime. Ceci renvoie 0 en cas de succès et -1 en cas d'erreur (comme décrit dans la documentation de utime). En cas de succès, la fonction mettra à jour les valeurs atime et mtime du fichier donné. Tcl_FSFileAttrsGet implémente l'accès en lecture pour le sous-commande file attributes du file hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si le résultat est TCL_OK, une valeur est placée dans objPtrRef, qui ne sera valide que temporairement (sauf si Tcl_IncrRefCount est appelé). Tcl_FSFileAttrsSet implémente l'accès en écriture pour le sous-commande file attributes du file hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Tcl_FSFileAttrStrings implémente une partie du sous-commande file attributes du file hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. La procédure appelante peut renvoyer un tableau de chaînes ou, à la place, renvoyer NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et augmentera son compteur de références avant de l'utiliser. Après utilisation, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être libérée par Tcl à la fin, son compteur de références doit être égal à zéro, et si elle ne doit pas être libérée, le système de fichiers doit s'assurer de maintenir le compteur de références à la valeur. Tcl_FSAccess vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou objet de système de fichiers) dont le nom est pathname. Si pathname est un lien symbolique sous Unix, les permissions du fichier référencé par ce lien symbolique sont testées. En cas de succès (toutes les permissions demandées), 0 est renvoyé. En cas d'erreur (au moins un bit du mode demandé est refusé ou une autre erreur s'est produite), -1 est renvoyé. Tcl_FSStat remplit la structure Tcl_StatBuf avec des informations sur le fichier spécifié. Aucun droit d'accès au fichier n'est requis pour obtenir ces informations, mais des droits de parcours sont requis sur tous les répertoires mentionnés dans le chemin d'accès au fichier. La structure Tcl_StatBuf comprend des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le temps d'accès, le temps de modification et le temps de changement de métadonnées. Voir PORTABLE STAT RESULT API pour une description de la manière d'écrire du code portable pour distribuer et accéder à la structure Tcl_StatBuf. Si path existe, Tcl_FSStat renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé et aucune donnée stat n'est fournie. Tcl_FSOpenFileChannel ouvre un fichier spécifié par pathPtr et renvoie un descripteur de canal qui peut être utilisé pour les opérations d'entrée et de sortie sur le fichier. Cette API est basée sur la procédure fopen de la bibliothèque d'entrée/sortie standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles des commandes Tcl open lors de l'ouverture d'un fichier. En cas d'erreur lors de l'ouverture du canal, Tcl_FSOpenFileChannel renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannel laisse un message d'erreur dans le résultat de interp après toute erreur. Le nouveau canal créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez Tcl_RegisterChannel. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, l'action de création du nouveau canal l'affecte également en remplacement des canaux standard. Tcl_FSGetCwd remplace la version de la bibliothèque getcwd. Renvoie le répertoire de travail courant de la bibliothèque Tcl. Cela peut être différent du répertoire de travail natif, ce qui se produit lorsque le répertoire de travail courant n'est pas dans le système de fichiers natif. Le résultat est un pointeur vers un Tcl_Obj spécifiant le répertoire courant, ou NULL si le répertoire ne peut pas être déterminé. Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de interp. Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compteur doit être décrémenté. Ceci est nécessaire pour la sécurité multi-threading, permettant à plusieurs threads d'accéder à cette fonction et aux fonctions associées, tout en garantissant que les résultats sont toujours valides. Tcl_FSChdir remplace la version de la bibliothèque chdir. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si ce système n'implémente pas cette fonction, Tcl s'appuie sur une combinaison de stat et access pour vérifier si le répertoire existe et a les permissions appropriées. Pour les résultats, voir la documentation de chdir. En cas de succès, un enregistrement du chemin réussi est sauvegardé dans cwdPathPtr pour les appels ultérieurs à Tcl_FSGetCwd. Tcl_FSPathSeparator renvoie le caractère séparateur à utiliser pour l'élément le plus spécifique du chemin spécifié par pathPtr (c'est-à-dire le dernier segment du chemin). Le séparateur est renvoyé sous forme de Tcl_Obj avec une chaîne de longueur 1. Si le chemin est invalide, NULL est renvoyé. Tcl_FSJoinPath prend le Tcl_Obj donné, qui doit être une liste valide (qui peut avoir un compteur de références de zéro), et renvoie la valeur du chemin en considérant les elements premiers éléments comme des segments de chemin valides (chaque segment peut être un chemin complet, un chemin partiel ou juste un répertoire ou un nom de fichier). Si un segment de chemin est effectivement un chemin absolu, tous les segments précédents sont ignorés. Si elements est inférieur à 0, nous utilisons la liste entière. Il est possible que la valeur renvoyée soit en fait un élément de la liste donnée, de sorte que l'appelant doit incrémenter le compteur de références de la valeur avant de libérer la liste. La valeur renvoyée, généralement avec un compteur de références de zéro (mais peut être partagée dans certaines conditions), contient le chemin concaténé. L'appelant doit incrémenter le compteur de références de la valeur avant de l'utiliser. En particulier, la valeur renvoyée peut être un élément de la liste donnée, de sorte que la libération de la liste pourrait libérer la valeur prématurément si un compteur de références n'a pas été pris. Si le nombre d'éléments est zéro, la valeur renvoyée sera une chaîne vide Tcl_Obj. Tcl_FSSplitPath prend le Tcl_Obj donné, qui devrait être un chemin valide, et renvoie une valeur Tcl de type liste avec chaque segment de ce chemin comme élément. Renvoie une valeur de type liste avec un compteur de références de zéro. Si lenPtr n'est pas NULL, la variable pointée sera mise à jour avec le nombre d'éléments dans la valeur de liste renvoyée. Tcl_FSGetEqualPaths teste si les deux chemins donnés représentent le même objet de système de fichiers. Renvoie 1 s'ils sont égaux, 0 s'ils sont différents. Si l'un des chemins est NULL, renvoie toujours 0. Tcl_FSGetNormalizedPath tente d'extraire une représentation normalisée unique du chemin donné, dont la valeur de chaîne peut être utilisée comme identifiant unique du fichier. Renvoie la valeur du chemin normalisé, propriété de Tcl, ou NULL si le chemin était invalide ou n'a pas pu être converti. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère en interne avec ces représentations), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques ne sera pas la version la plus conviviale d'un chemin. La valeur renvoyée est propriété de Tcl et a une durée de vie équivalente à celle du pathPtr passé (sauf s'il s'agit d'un chemin relatif, auquel cas le chemin normalisé peut être libéré à chaque fois que le cwd change) - l'appelant peut incrémenter le compteur de références s'il le souhaite pour conserver une copie plus longue. Tcl_FSJoinToPath prend la valeur donnée, qui est généralement un chemin valide ou NULL, et joint le tableau de segments de chemin donnés. Renvoie une valeur, généralement avec un compteur de références de zéro (mais peut être partagée dans certaines conditions), contenant le chemin joint. L'appelant doit incrémenter le compteur de références de la valeur avant de l'utiliser. Si l'une des valeurs passées à cette fonction (pathPtr ou éléments de path) a un compteur de références de zéro, elle sera libérée lorsque cette fonction renverra. Tcl_FSConvertToPathType tente de convertir le Tcl_Obj donné en un type de chemin valide, en tenant compte du fait que le cwd peut avoir changé même si cette valeur est déjà du type correct. Le nom du fichier peut commencer par ~ (pour indiquer le répertoire utilisateur courant) ou ~ (pour indiquer le répertoire de n'importe quel utilisateur). Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), TCL_OK est renvoyé. Sinon, TCL_ERROR est renvoyé, et un message d'erreur peut se trouver dans l'interpréteur. Tcl_FSGetInternalRep extrait la représentation interne d'une valeur de chemin donnée dans le système de fichiers donné. Si la valeur de chemin appartient à un système de fichiers différent, NULL est renvoyé. Si la représentation interne actuelle est NULL, on tente de la générer en appelant Tcl_FSCreateInternalRepProc du système de fichiers. Renvoie NULL ou une représentation valide du chemin interne. Cette représentation est mise en cache, de sorte que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. Tcl_FSGetTranslatedPath tente d'extraire le chemin traduit à partir du Tcl_Obj donné. Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), la valeur est renvoyée. Sinon, NULL est renvoyé et un message d'erreur peut se trouver dans l'interpréteur. Un chemin traduit est un chemin qui ne contient pas ~ ou ~utilisateur (ceux-ci ont été développés dans leur représentation actuelle dans le système de fichiers). La valeur renvoyée est la propriété de l'appelant, qui doit stocker la valeur ou appeler Tcl_DecrRefCount pour assurer la libération de la mémoire. Cette fonction a peu d'utilité pratique, et Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement des fonctions plus appropriées pour la plupart des usages. Tcl_FSGetTranslatedStringPath fait la même chose que Tcl_FSGetTranslatedPath, mais renvoie une chaîne ou NULL. La chaîne renvoyée est allouée dynamiquement. ted et détenu par l'appelant, qui doit le stocker ou appeler ckfree pour s'assurer qu'il est libéré. Encore une fois, Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des usages.

Tcl_FSNewNativePath effectue quelque chose comme l'inverse des conversions habituelles obj->chemin->représentation native. Si un code récupère un chemin sous forme native (par exemple, depuis readlink ou une boîte de dialogue native), et que ce chemin doit être utilisé au niveau Tcl, alors appeler cette fonction est un moyen efficace de créer le type de valeur de chemin approprié.

La valeur résultante est une valeur de « chemin » pure, qui ne recevra une représentation de chaîne UTF-8 que si cela est requis par du code Tcl.

Tcl_FSGetNativePath est destiné à être utilisé par les systèmes de fichiers natifs Win/Unix, afin qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un wrapper pratique autour de Tcl_FSGetInternalRep. Il peut être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes (par exemple, sur macOS, une représentation utilisant une structure FSRef de fileSpec serait probablement plus efficace). Sous Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Actuellement, la représentation est simplement une chaîne de caractères qui peut contenir soit le chemin relatif, soit un chemin normalisé complet et absolu dans l'encodage natif (des conditions complexes dictent lequel de ceux-ci sera fourni, de sorte qu'aucun ne peut être fiable, sauf si le chemin est connu pour être absolu). Si vous avez besoin d'un chemin natif qui doit être absolu, vous devriez demander la version native d'un chemin normalisé. Si pour une raison quelconque une version non absolue et non normalisée du chemin est nécessaire, celle-ci doit être construite séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache afin que les appels répétés à cette fonction n'entraînent pas de conversions supplémentaires. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle du pathPtr passé en argument (sauf si il s'agit d'un chemin relatif, auquel cas la représentation native peut être libérée à tout moment où le cwd change).

Tcl_FSFileSystemInfo renvoie une liste de deux éléments. Le premier élément est le nom du système de fichiers (par exemple, « native », « vfs », « zip », ou « prowrap », peut-être), et le second est le type particulier du chemin donné dans ce système de fichiers (qui dépend du système de fichiers). Le second élément peut être vide si le système de fichiers ne fournit pas de catégorisation supplémentaire des fichiers.

Une valeur de liste valide est retournée, sauf si la valeur du chemin n'est pas reconnue, auquel cas NULL sera retourné.

Tcl_FSGetFileSystemForPath renvoie un pointeur vers le Tcl_Filesystem qui accepte ce chemin comme valide.

Si aucun système de fichiers n'accepte le chemin, NULL est retourné.

Tcl_FSGetPathType détermine si le chemin donné est relatif au répertoire courant, relatif au volume courant, ou absolu.

Il renvoie l'une des valeurs TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, ou TCL_PATH_VOLUME_RELATIVE.

L'API DES SYSTÈMES DE FICHIERS VIRTUELS

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un système de fichiers ; ces opérations sont invoquées au besoin par la couche générique, ce qui se produit généralement par le biais des fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un morceau de données optionnel à associer à ce système de fichiers. En appelant cette fonction, Tcl attachera le système de fichiers à la liste des systèmes de fichiers connus, et il deviendra pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera retourné.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et renvoie TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est retourné.

Tcl_FSData renverra le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il renverra NULL.

Tcl_FSMountsChanged est utilisé pour informer le noyau de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche générique du système de fichiers pour effectuer toute la gamme des actions liées au système de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (dont la quasi-totalité doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni) et fonctions d'efficacité (qui ne doivent être implémentées que si elles peuvent l'être de manière efficace, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces remplacements ne sont utilisés que pour gérer les commandes initiées en Tcl, et non en C. Cela signifie que si une commande file rename est émise en Tcl, et que les systèmes de fichiers concernés n'implémentent pas leur Tcl_FSRenameFileProc, le noyau de Tcl se rabattra sur une combinaison d'autres fonctions de système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a un autre remplacement). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun de ces remplacements ne se produit. Ceci est vrai sauf pour les quatre dernières entrées dans la table du système de fichiers (lstat, load, getcwd et chdir) pour lesquelles des remplacements se produisent en fait au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme de Tcl_Obj les prennent sous forme UTF-8. L'API d'infrastructure des systèmes de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

INFRASTRUCTURE DU SYSTÈME DE FICHIERS

Ces champs contiennent des informations de base sur la structure du système de fichiers et les adresses des fonctions utilisées pour associer un système de fichiers particulier à un chemin de fichier, et pour gérer la gestion interne des représentations de chemins, par exemple la copie et la libération de ces représentations.

NOM DU TYPE

Le champ typeName contient une chaîne terminée par un nul qui identifie le type du système de fichiers implémenté, par exemple « natif », « zip » ou « vfs ».

LONGUEUR DE LA STRUCTURE

Le champ structureLength est généralement implémenté comme sizeof(Tcl_Filesystem), et est là pour permettre une compatibilité binaire descendante plus facile si la taille de la structure change dans une future version de Tcl.

VERSION

Le champ version doit être défini à TCL_FILESYSTEM_VERSION_1.

PROCÉDURE PATHINFILESYSTEM

Le champ pathInFilesystemProc contient l'adresse d'une fonction appelée pour déterminer si une valeur de chemin donnée appartient à ce système de fichiers ou non. Tcl appellera les autres fonctions du système de fichiers uniquement avec un chemin pour lequel cette fonction a renvoyé TCL_OK. Si le chemin n'appartient pas, -1 doit être retourné (le comportement de Tcl pour toute autre valeur de retour n'est pas défini). Si TCL_OK est retourné, alors le paramètre de sortie optionnel clientDataPtr peut être utilisé pour retourner une représentation interne (spécifique au système de fichiers) du chemin, qui sera mise en cache dans la valeur du chemin, et pourra être récupérée efficacement par les autres fonctions du système de fichiers. Tcl mettra simultanément en cache le fait que ce chemin appartient à ce système de fichiers. Ces caches sont invalidés lorsque des structures de système de fichiers sont ajoutées ou supprimées de la liste interne de Tcl des systèmes de fichiers connus.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROCÉDURE DUPINTERNALREP

Cette fonction crée une copie de la représentation interne d'un chemin, et est appelée lorsque Tcl a besoin de dupliquer une valeur de chemin. Si elle est NULL, Tcl ne copiera pas simplement la représentation interne, qui devra alors être régénérée plus tard.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

PROCÉDURE FREEINTERNALREP

Libère la représentation interne. Ceci doit être implémenté si des représentations internes nécessitent une libération (c'est-à-dire si de la mémoire est allouée lors de la génération d'une représentation interne), mais peut sinon être NULL.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

PROCÉDURE INTERNALTONORMALIZED

Fonction pour convertir la représentation interne en un chemin normalisé. Uniquement requis si le système de fichiers crée des valeurs de chemin pures sans représentation de chaîne/chemin. La valeur de retour est une valeur Tcl dont la représentation de chaîne est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

PROCÉDURE CREATEINTERNALREP

Fonction pour prendre une valeur de chemin, calculer une représentation interne pour celle-ci, et stocker cette représentation native dans la valeur. Peut être NULL si les chemins n'ont pas de représentation interne, ou si la Tcl_FSPathInFilesystemProc pour ce système de fichiers crée immédiatement une représentation interne pour les chemins qu'elle accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

PROCÉDURE NORMALIZEPATH

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations de chaîne pour la même valeur de chemin. Dans Tcl, chaque « chemin » doit avoir une seule représentation de chaîne « normalisée » unique. Selon le système de fichiers, il peut y avoir plus d'une représentation de chaîne non normalisée qui fait référence à ce chemin (par exemple, un chemin relatif, un chemin avec une casse différente si le système de fichiers ne respecte pas la casse, un chemin contenant une référence à un répertoire personnel comme « ~ », un chemin contenant des liens symboliques, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être converti en la valeur qu'il pointe (mais sa casse ou d'autres aspects doivent être rendus uniques). Tous les autres composants de chemin doivent être convertis à partir de liens symboliques. Cette unique exception est requise pour être conforme aux sémantiques de Tcl avec file delete, file rename, file copy opérant sur des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint soit au début du chemin (c'est-à-dire zéro), soit à la fin du chemin, soit à un séparateur de fichier intermédiaire dans le chemin. Elle ne pointera jamais vers une autre position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS DU SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions qui sont appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui est censé être utilisé avec l'ensemble complet des commandes Tcl standard doit implémenter toutes ces fonctions. Si certaines d'entre elles ne sont pas implémentées, certaines commandes Tcl peuvent échouer lors de l'opération sur des chemins appartenant à ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques n'a pas besoin d'implémenter la fonction readlink, etc. Le noyau Tcl s'attend à ce que les systèmes de fichiers se comportent de cette manière).

PROCÉDURE FILESYSTEMPATHTYPE

Fonction pour déterminer le type d'un chemin dans ce système de fichiers. Peut être NULL, auquel cas aucune information de type ne sera disponible pour les utilisateurs du système de fichiers. Le « type » est utilisé uniquement à des fins d'information, et doit être retourné comme la représentation de chaîne de l'objet Tcl retourné. Une valeur de retour typique pourrait être « réseau », « zip » ou « ftp ». L'objet Tcl résultant est détenu par le système de fichiers et Tcl incrémentera donc le compteur de références de cette valeur s'il souhaite en conserver une référence.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

PROCÉDURE FILESYSTEMSEPARATOR

Fonction pour retourner le(s) caractère(s) séparateur(s) pour ce système de fichiers. Ceci n'a besoin d'être implémenté que si le système de fichiers souhaite utiliser un séparateur différent de la chaîne standard « / ». Entre autres utilisations, il est retourné par la commande file separator. La valeur de retour doit être un objet avec un compteur de références nul.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

PROCÉDURE STAT

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes au niveau Tcl en dépendent de manière cruciale (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La Tcl_FSStatProc remplit la structure stat statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure stat inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification, et l'heure du dernier changement de métadonnées.

Si le fichier représenté par pathPtr existe, la Tcl_FSStatProc renvoie 0 et la structure stat est remplie de données. Sinon, -1 est retourné, et aucune information de stat n'est donnée.

PROCÉDURE ACCESS

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes au niveau Tcl en dépendent de manière cruciale (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est dans pathPtr. Si le nom de chemin fait référence à un lien symbolique, alors les permissions du fichier auquel ce lien symbolique fait référence doivent être testées.

En cas de succès (toutes les permissions demandées accordées), zéro est retourné. En cas d'erreur (au moins un bit dans mode demandait une permission refusée, ou une autre erreur s'est produite), -1 est retourné.

PROCÉDURE OPENFILECHANNEL

ROC'>OPENFILECHANNELPROC

Fonction pour traiter un appel Tcl_FSOpenFileChannel. Elle doit être implémentée pour tout système de fichiers raisonnable, car toute opération qui nécessite l'ouverture ou l'accès au contenu d'un fichier utilisera cette fonction (par exemple, open, encoding et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

Le Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et renvoie un descripteur de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est modelée d'après la procédure fopen de la bibliothèque d'entrée/sortie standard POSIX. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier, où l'argument mode est une combinaison des indicateurs POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, le Tcl_FSOpenFileChannelProc renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas nul, le Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le canal nouvellement créé doit être enregistré dans l'interpréteur fourni par un Tcl_FSOpenFileChannelProc; ce travail incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, l'action de création du nouveau canal l'assigne également comme remplacement des canaux standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, la fonctionnalité de glob et de copie récursive sera perdue dans le système de fichiers (et cela peut affecter des commandes comme encoding names qui utilisent la fonctionnalité de glob).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit renvoyer tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au modèle donné et satisfont la spécification types. Il existe deux manières dont cette fonction peut être appelée. Si pattern est NULL, pathPtr est une spécification complète d'un fichier ou d'un répertoire qui doit être vérifié pour son existence et son type correct. Sinon, pathPtr est un répertoire et la fonction doit rechercher des fichiers ou des répertoires dont les types sont corrects. Dans tous les cas, pathPtr peut être supposé non nul et non vide. Il n'est actuellement pas documenté si pathPtr aura un séparateur de fichier à la fin ou non, de sorte que le code doit être flexible aux deux possibilités.

La valeur de retour est un résultat standard Tcl indiquant si une erreur s'est produite dans le processus de mise en correspondance. Les messages d'erreur sont placés dans interp, à moins que interp ne soit NULL, auquel cas aucun message d'erreur ne doit être généré. Si le résultat est TCL_OK, les résultats doivent être ajoutés à la valeur donnée resultPtr (qui peut être supposée être une liste Tcl non partagée). Les éléments ajoutés à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (ce qui implique généralement qu'il s'agira de spécifications de chemin absolu). Note: s'il n'y a pas de correspondances, un résultat vide est simplement obtenu; les erreurs ne sont signalées que pour les problèmes réels de fichier ou de système de fichiers qui peuvent survenir pendant le processus de mise en correspondance.

La structure Tcl_GlobTypeData fournie dans le paramètre types contient les champs suivants:

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Type mac acceptable */
    Tcl_Obj *macType;
    /* Créateur mac acceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de gérer correctement, tous deux lorsque types n'est pas nul. Les deux cas sont lorsque types->types est TCL_GLOB_TYPE_DIR ou TCL_GLOB_TYPE_MOUNT (et en particulier lorsque les autres indicateurs sont faux). Dans le premier de ces cas, la fonction doit lister les répertoires contenus. Tcl utilise cette fonction pour implémenter le globbing récursif, il est donc essentiel que les systèmes de fichiers implémentent correctement la mise en correspondance des répertoires. Dans le second de ces cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage qui se trouvent dans le répertoire donné par pathPtr (et dans ce cas, pathPtr ne doit pas se trouver dans le même système de fichiers - contrairement à tous les autres cas où cette fonction est appelée). Le support pour cela est critique si Tcl doit avoir des transitions douces entre différents systèmes de fichiers.

UTIMEPROC

Fonction pour traiter un appel Tcl_FSUtime. Elle est requise pour permettre la définition (pas la lecture) des temps avec file mtime, file atime et l'implémentation de file copy de open-r/open-w/fcopy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les temps d'accès et de modification des fichiers spécifiés par pathPtr doivent être modifiés aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec le système utime.

LINKPROC

Fonction pour traiter un appel Tcl_FSLink. Elle doit être implémentée uniquement si le système de fichiers prend en charge les liens, et peut être NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est interrogée pour lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien ne peut pas être lu. Le résultat appartient à l'appelant (et doit donc incrémenter son compteur de références avant d'être renvoyé). Tout appelant doit appeler Tcl_DecrRefCount sur ce résultat lorsqu'il ne l'utilise plus. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Dans ce cas, le résultat doit être toPtr si le lien a réussi et NULL dans le cas contraire. Dans ce cas, le résultat n'appartient pas à l'appelant (c'est-à-dire qu'aucune manipulation du compteur de références ne sera effectuée des deux côtés). Consultez la documentation de Tcl_FSLink pour l'interprétation correcte des indicateurs de linkAction.

LISTVOLUMESPROC

Fonction pour lister tous les volumes de système de fichiers ajoutés par ce système de fichiers. Elle doit être implémentée uniquement si le système de fichiers ajoute des volumes au début du système de fichiers, permettant ainsi qu'ils soient renvoyés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste de volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. La valeur de retour est considérée comme appartenant au système de fichiers (pas au cœur de Tcl), mais doit se voir attribuer un compteur de références pour Tcl. Tcl utilisera le contenu de la liste, puis décrémentera le compteur de références. Cela permet aux systèmes de fichiers de décider s'ils souhaitent conserver une liste globale de volumes ou non (si non, ils génèrent la liste à la volée et la passent à Tcl avec un compteur de références de 1 puis oublient la liste, si oui, alors ils incrémentent le compteur de références de leur liste globale et la passent à Tcl qui copie le contenu puis décrémente le compteur de références là où il était).

Par conséquent, Tcl considère les valeurs de retour de cette procédure comme en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne prendra pas en charge la commande file attributes. Cela permet d'ajouter des informations arbitraires supplémentaires aux fichiers du système de fichiers. Si elle n'est pas implémentée, les méthodes get et set n'ont pas besoin d'être implémentées.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La fonction appelée peut renvoyer un tableau de chaînes, ou elle peut renvoyer NULL et placer une liste Tcl dans le objPtrRef donné. Tcl prendra cette liste et incrémentera son compteur de références avant de l'utiliser. Une fois son utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être libérée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si elle ne doit pas être libérée, le système de fichiers doit garantir qu'il renvoie une valeur avec un compteur de références d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel Tcl_FSFileAttrsGet, utilisé par file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Renvoie un code de retour standard Tcl. La valeur de l'attribut récupéré, qui correspond à l'élément d'indice index dans la liste renvoyée par Tcl_FSFileAttrStringsProc, est placée dans objPtrRef (si TCL_OK a été renvoyé) et aura probablement un compteur de références de zéro. Soit nous devons le stocker quelque part (par exemple, le résultat Tcl), soit incrémenter/décrémenter son compteur de références pour assurer sa libération correcte.

FILEATTRSSETPROC

Fonction pour traiter un appel Tcl_FSFileAttrsSet, utilisé par file attributes. Si le système de fichiers est en lecture seule, cette fonction n'a pas besoin d'être implémentée.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

L'attribut de la valeur de l'élément d'indice index dans la liste renvoyée par Tcl_FSFileAttrStringsProc doit être défini sur le objPtr donné.

CREATEDIRECTORYPROC

Fonction pour créer un répertoire dans le système de fichiers. Elle doit être implémentée si le système de fichiers prend en charge les répertoires, sinon elle peut être NULL.

PROC

Fonction pour traiter un appel à Tcl_FSCreateDirectory. Doit être implémentée, sauf si le FS est en lecture seule.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

La valeur de retour est un résultat standard Tcl indiquant si une erreur s'est produite pendant le traitement. Si cela réussit, un nouveau répertoire aurait dû être créé à l'emplacement spécifié par pathPtr.

REMOVEDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSRemoveDirectory. Doit être implémentée, sauf si le FS est en lecture seule.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

La valeur de retour est un résultat standard Tcl indiquant si une erreur s'est produite pendant le traitement. Si cela réussit, le répertoire spécifié par pathPtr aurait dû être supprimé du système de fichiers. Si l'indicateur recursive est donné, un répertoire non vide aurait dû être supprimé sans erreur. Si cet indicateur n'est pas donné, et que le répertoire est non vide, une erreur POSIX "EEXIST" aurait dû être signalée. Si une erreur se produit, le nom du fichier ou du répertoire ayant causé l'erreur devrait se trouver dans errorPtr.

DELETEFILEPROC

Fonction pour traiter un appel à Tcl_FSDeleteFile. Doit être implémentée, sauf si le FS est en lecture seule.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

La valeur de retour est un résultat standard Tcl indiquant si une erreur s'est produite pendant le traitement. Si cela réussit, le fichier spécifié par pathPtr aurait dû être supprimé du système de fichiers. Il convient de noter que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non Tcl_FSRemoveDirectoryProc lorsque cela est nécessaire pour les supprimer (même s'il s'agit de liens symboliques vers des répertoires).

FILESYSTEM EFFICIENCY

Ces fonctions ne doivent pas être implémentées pour un système de fichiers donné, car le noyau dispose d'une implémentation de secours disponible. Voir chaque description individuelle pour les conséquences de laisser le champ vide.

LSTATPROC

Fonction pour traiter un appel à Tcl_FSLstat. Si elle n'est pas implémentée, Tcl tentera d'utiliser le statProc défini précédemment. Elle ne doit donc être implémentée que si le système de fichiers peut faire la distinction entre les appels stat et lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le comportement de cette fonction est très similaire à celui de la Tcl_FSStatProc définie précédemment, sauf lorsqu'elle s'applique à un lien symbolique, auquel cas elle renvoie des informations sur le lien, et non sur le fichier cible.

COPYFILEPROC

Fonction pour traiter un appel à Tcl_FSCopyFile. Si elle n'est pas implémentée, Tcl se rabattra sur un mécanisme de copie utilisant open-r, open-w et fcopy. Elle ne doit donc être implémentée que si le système de fichiers peut effectuer cette opération plus efficacement.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat standard Tcl indiquant si une erreur s'est produite pendant la copie. Notez que destPathPtr est le nom du fichier qui doit devenir la copie de srcPathPtr. Il ne s'agit jamais du nom d'un répertoire dans lequel srcPathPtr pourrait être copié (c'est-à-dire que le fonctionnement est beaucoup plus simple que la sous-commande file copy du niveau Tcl). Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non copyDirectoryProc lorsque cela est nécessaire pour les copier (même s'il s'agit de liens symboliques vers des répertoires). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge le mécanisme de copie de fichiers, en appelant Tcl_SetErrno(EXDEV) et en renvoyant un résultat autre que TCL_OK, il indiquera à Tcl d'utiliser ses mécanismes de secours standard.

RENAMEFILEPROC

Fonction pour traiter un appel à Tcl_FSRenameFile. Si elle n'est pas implémentée, Tcl se rabattra sur une copie et une suppression. Elle ne doit donc être implémentée que si le système de fichiers peut effectuer cette opération plus efficacement.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat standard Tcl indiquant si une erreur s'est produite pendant le processus de renommage. Si le système de fichiers détermine qu'il ne peut pas prendre en charge le mécanisme de renommage de fichiers, en appelant Tcl_SetErrno(EXDEV) et en renvoyant un résultat autre que TCL_OK, il indiquera à Tcl d'utiliser ses mécanismes de secours standard.

COPYDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSCopyDirectory. Si elle n'est pas implémentée, Tcl se rabattra sur un mécanisme de récursion file mkdir, file copy. Elle ne doit donc être implémentée que si le système de fichiers peut effectuer cette opération plus efficacement.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

La valeur de retour est un résultat standard Tcl indiquant si une erreur s'est produite pendant le processus de copie. Si une erreur se produit, le nom du fichier ou du répertoire ayant causé l'erreur devrait se trouver dans errorPtr. Notez que destPathPtr est le nom du répertoire qui doit devenir l'image copiée de srcPathPtr. Il ne s'agit jamais du nom d'un répertoire dans lequel srcPathPtr pourrait être copié (c'est-à-dire que le fonctionnement est beaucoup plus simple que la sous-commande file copy du niveau Tcl). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge le mécanisme de copie de répertoires, en appelant Tcl_SetErrno(EXDEV) et en renvoyant un résultat autre que TCL_OK, il indiquera à Tcl d'utiliser ses mécanismes de secours standard.

LOADFILEPROC

Fonction pour traiter un appel à Tcl_FSLoadFile. Si elle n'est pas implémentée, Tcl se rabattra sur une copie vers un fichier temporaire, puis sur Tcl_FSLoadFile sur ce fichier temporaire. Elle ne doit donc être implémentée que si le système de fichiers peut charger du code directement, ou peut être implémentée en renvoyant simplement TCL_ERROR pour désactiver la fonctionnalité de chargement sur ce système de fichiers.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Renvoie un code de complétion standard Tcl. Si une erreur se produit, un message d'erreur est laissé dans le résultat de l'interp. La fonction charge dynamiquement un fichier de code binaire en mémoire. En cas de chargement réussi, handlePtr doit être rempli avec un jeton pour le fichier chargé dynamiquement, et unloadProcPtr doit être rempli avec l'adresse d'une procédure. La procédure de déchargement sera appelée avec le Tcl_LoadHandle donné comme seul paramètre lorsque Tcl aura besoin de décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle renvoyé est actuellement un jeton qui peut être utilisé dans le TclpFindSymbol privé pour accéder aux fonctions du nouveau code. Chaque système de fichiers peut définir le Tcl_LoadHandle selon ses besoins. Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge le mécanisme de chargement de fichiers, en appelant Tcl_SetErrno(EXDEV) et en renvoyant un résultat autre que TCL_OK, il indiquera à Tcl d'utiliser ses mécanismes de secours standard.

UNLOADFILEPROC

Fonction pour décharger un fichier qui a été précédemment chargé. Si le chargement a été implémenté, celui-ci doit également l'être, s'il y a une action de nettoyage requise.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Fonction pour traiter un appel à Tcl_FSGetCwd. La plupart des systèmes de fichiers traditionnels n'ont pas besoin de l'implémenter. Elle est généralement appelée une seule fois, si getcwd est appelé avant chdir. Elle peut être NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si le système de fichiers prend en charge une notation native du répertoire de travail (qui pourrait changer indépendamment de Tcl), cette fonction devrait renvoyer ce cwd comme résultat, ou NULL si le répertoire de travail n'a pas pu être déterminé (par exemple, l'utilisateur n'a pas les autorisations appropriées dans le répertoire de travail). Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de l'interp.

CHDIRPROC

Fonction pour traiter un appel à Tcl_FSChdir. Si les systèmes de fichiers ne l'implémentent pas, elle sera émulée par une série de vérifications d'accès aux répertoires. Sinon, les systèmes de fichiers qui implémentent cette fonctionnalité ne devraient renvoyer un résultat positif que si pathPtr est un répertoire valide et accessible sur leur système de fichiers. Ils ne doivent pas se souvenir du résultat, car celui-ci sera automatiquement retenu par Tcl_FSGetCwd. Les systèmes de fichiers réels doivent effectuer l'action correcte (c'est-à-dire appeler l'API chdir correspondante du système).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

La Tcl_FSChdirProc change le répertoire de travail actuel de l'application vers la valeur spécifiée dans pathPtr. La fonction renvoie -1 en cas d'erreur ou 0 en cas de succès.
