DESCRIPTION

Il y a plusieurs raisons d'appeler les fonctions de l'API Tcl_FS (par ex., Tcl_FSAccess et Tcl_FSStat) plutôt que d'appeler directement des fonctions de niveau système comme access et stat. Premièrement, elles fonctionneront sur plusieurs plateformes, donc une extension qui les appelle devrait fonctionner sans modification sous Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige certains bugs dans les appels de niveau système. Troisièmement, ces appels de fonction traitent toute conversion de chemin « Utf vers natif de la plateforme » qui pourrait être nécessaire (et peuvent mettre en cache les résultats de ces conversions pour une plus grande efficacité lors des appels ultérieurs). Quatrièmement, et peut-être le plus important, toutes ces fonctions sont « conscientes des systèmes de fichiers virtuels » (VFS pour faire court). Tout système de fichiers virtuel (VFS) qui a été enregistré (via Tcl_FSRegister) peut rediriger l'accès aux fichiers vers des supports ou des méthodes d'accès alternatives. Cela signifie que toutes ces fonctions (et donc les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent opérer sur des « fichiers » qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS pour faire court) via cette API est automatiquement « consciente des systèmes de fichiers virtuels ». Bien sûr, si une extension accède directement au système de fichiers natif (via des API spécifiques à la plateforme, par exemple), alors Tcl ne peut pas intercepter de tels appels.

Si des VFS appropriés ont été enregistrés, les « fichiers » peuvent, pour donner deux exemples, être distants (par ex., situés sur un serveur ftp distant) ou archivés (par ex., se trouvant à l'intérieur d'une archive .zip). De tels systèmes de fichiers enregistrés fournissent une table de recherche de fonctions pour implémenter tout ou partie des fonctionnalités énumérées ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat abstraient le contenu du buffer « struct stat », ce qui permet d'utiliser le même code aussi bien sur les systèmes qui prennent en charge les fichiers de plus de 2 Go que sur ceux qui n'en prennent pas en charge.

L'API Tcl_FS est transformée en Tcl_Obj et peut mettre en cache les représentations internes et autres chaînes relatives aux chemins (par ex., le répertoire de travail courant). Une conséquence est qu'il ne faut pas passer de valeurs avec un compteur de références de zéro à aucune de ces fonctions. Si de tels appels étaient traités, ils pourraient entraîner des fuites de mémoire (dans certaines circonstances, le code du système de fichiers peut souhaiter conserver une référence à la valeur passée, et il ne faut donc pas supposer qu'après le retour de l'un de ces appels, la valeur a toujours un compteur de références de zéro - il peut avoir été incrémenté) ou une faute de segmentation directe (ou une autre erreur d'accès à la mémoire) due à la libération de la valeur pendant la manipulation complexe de la valeur nécessaire pour s'assurer que le chemin est entièrement normalisé et absolu pour la détermination du système de fichiers. La leçon pratique à en tirer est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect, et peut causer des erreurs de mémoire. Le chemin path doit avoir son compteur de références incrémenté avant d'être passé, ou avant d'être décrémenté. Pour cette raison, les valeurs avec un compteur de références de zéro sont considérées comme n'étant pas des chemins de système de fichiers valides et l'appel de toute fonction API Tcl_FS avec une telle valeur n'entraînera aucune action.

FONCTIONS DE L'API FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno au code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno au code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction « créer répertoire » du système de fichiers propriétaire.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction « supprimer fichier » du système de fichiers propriétaire.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction « supprimer répertoire » du système de fichiers propriétaire.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr en le nommant destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « renommer fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno au code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction « lister volumes » non NULL et leur demande de retourner leur liste de volumes racines. Elle accumule les valeurs de retour dans une liste qui est renvoyée à l'appelant (avec un compteur de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant l'encodage identifié par encodingName et évalue son contenu comme un script Tcl. Elle retourne les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, l'encodage système est utilisé pour lire le contenu du fichier. Si le fichier n'a pas pu être lu, une erreur Tcl est renvoyée pour décrire pourquoi le fichier n'a pas pu être lu. Le caractère de fin de fichier pour les fichiers est « \x1A » (^Z) pour toutes les plateformes. Si vous avez besoin d'un « ^Z » dans le code pour une comparaison de chaînes, vous pouvez utiliser « \x1A », qui sera substitué en toute sécurité par l'interpréteur Tcl en « ^Z ». Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours l'encodage système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier de code binaire en mémoire et retourne les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas, en raison des limitations du système d'exploitation pour charger dynamiquement du code binaire), Tcl tentera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile inverse l'opération, demandant que la bibliothèque indiquée par loadHandle soit retirée du processus. Notez que, contrairement à la commande unload, cela ne donne aucune opportunité à la bibliothèque de faire du nettoyage.

Les deux fonctions ci-dessus retournent un code de complétion Tcl standard. Si une erreur se produit, un message d'erreur est laissé dans le résultat de l' interp.

Le jeton fourni via la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher dans un répertoire tous les fichiers qui correspondent à un motif donné. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du globbing. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Notez que le code glob implémente les motifs récursifs en interne, donc cette fonction ne recevra jamais que des motifs simples, qui peuvent être mis en correspondance en utilisant la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment en demandant uniquement le retour des répertoires. Un cas spécial d'appel avec un motif NULL indique que le chemin doit uniquement être vérifié pour le type correct.

Tcl_FSLink remplace la version bibliothèque de readlink, et l'étend pour prendre en charge la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr sera appelée.

Si toPtr est NULL, une action « lire le lien » est effectuée. Le résultat est un Tcl_Obj spécifiant le contenu du lien symbolique donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant, qui devrait appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl devrait créer un lien d'un des types passés dans le drapeau linkAction. Ce drapeau est une combinaison OU de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'un choix existe (c'est-à-dire plus d'un drapeau est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur de retour doit être toPtr (qui appartient donc déjà à l'appelant). En cas d'échec, NULL est retourné.

Tcl_FSLstat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez besoin d'aucun droit d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. Sinon, il renvoie -1 et aucune donnée statistique n'est donnée. **Tcl_FSUtime** remplace la version de la bibliothèque de utime. La fonction appropriée pour le système de fichiers auquel appartient pathPtr est appelée. La procédure appelée peut renvoyer un tableau de chaînes ou, alternativement, renvoyer NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et augmentera d'abord son compteur de références avant de l'utiliser. Une fois son utilisation terminée, Tcl diminuera son compteur de références. Par conséquent, si la liste doit être libérée par Tcl lorsqu'elle a terminé, elle doit avoir un compteur de références égal à zéro, et si elle ne doit pas être libérée, le système de fichiers doit s'assurer qu'il maintient un compteur de références à la valeur. **Tcl_FSAccess** vérifie si le processus serait autorisé à lire, écrire ou tester l'existence d'un fichier (ou objet de système de fichiers) dont le nom est pathname. Si pathname est un lien symbolique sous Unix, les permissions du fichier référencé par ce lien symbolique sont testées. En cas de succès (toutes les permissions demandées ont été accordées), il renvoie 0. En cas d'erreur (au moins un bit dans le mode demandé est refusé ou une autre erreur se produit), il renvoie -1. **Tcl_FSStat** remplit la structure Tcl_StatBuf avec des informations sur le fichier spécifié. Aucun droit d'accès au fichier n'est requis pour obtenir ces informations, mais des droits de recherche sont requis pour tous les répertoires mentionnés dans le chemin vers le fichier. La structure Tcl_StatBuf inclut des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID groupe (toujours 0 sous Windows), le rdev (identique au périphérique sous Windows), la taille, le temps d'accès le plus récent, le temps de modification le plus récent et le temps de dernière modification des métadonnées. Voir **PORTABLE STAT RESULT API** pour une description de la façon d'écrire du code portable pour mapper et accéder à la structure Tcl_StatBuf. Si path existe, **Tcl_FSStat** renvoie 0 et la structure statPtr est remplie de données. Sinon, il renvoie -1 et aucune donnée statistique n'est donnée. **Tcl_FSOpenFileChannel** ouvre un fichier spécifié par pathPtr et renvoie un descripteur de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est calquée sur la fonction fopen de la bibliothèque d'entrée/sortie standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles de la commande Tcl **open** lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, **Tcl_FSOpenFileChannel** renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec **Tcl_GetErrno**. De plus, si interp n'est pas NULL, **Tcl_FSOpenFileChannel** laisse un message d'erreur dans le résultat de interp après toute erreur. Le nouveau canal créé n'est pas enregistré auprès de l'interpréteur fourni ; pour l'enregistrer, utilisez **Tcl_RegisterChannel**. Si l'un des canaux standard, **stdin**, **stdout** ou **stderr**, a été précédemment fermé, l'action de créer le nouveau canal lui attribue également comme substitut des canaux standard. **Tcl_FSGetCwd** remplace la version de la bibliothèque de **getcwd**. Elle renvoie le répertoire de travail actuel de la bibliothèque Tcl. Cela peut différer du répertoire de travail natif, ce qui se produit lorsque le répertoire de travail actuel ne se trouve pas dans le système de fichiers natif. Le résultat est un pointeur vers un objet Tcl Tcl_Obj spécifiant le répertoire actuel, ou NULL s'il n'a pas été possible de déterminer le répertoire. Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de interp. Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compteur de références doit être décrémenté. Ceci est nécessaire pour la sécurité des threads, afin que plusieurs threads puissent accéder à cette fonction et aux fonctions associées, garantissant ainsi que les résultats sont toujours valides. **Tcl_FSChdir** remplace la version de la bibliothèque de **chdir**. Le chemin est normalisé puis transmis au système de fichiers qui le réclame. Si ce système de fichiers n'implémente pas cette fonction, Tcl s'appuie sur une combinaison de **stat** et **access** pour vérifier si le répertoire existe et possède les permissions appropriées. Pour les résultats, voir la documentation de **chdir**. En cas de succès, nous conservons un enregistrement du chemin réussi dans cwdPathPtr pour les appels ultérieurs à **Tcl_FSGetCwd**. **Tcl_FSPathSeparator** renvoie le caractère séparateur à utiliser pour l'élément le plus spécifique du chemin spécifié par pathPtr (c'est-à-dire le dernier élément du chemin). Le séparateur est renvoyé sous la forme d'un objet Tcl contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est renvoyé. **Tcl_FSJoinPath** prend l'objet Tcl donné, qui doit être une liste valide (il peut avoir un compteur de références de zéro), et renvoie la valeur du chemin en considérant les elements premiers comme des segments de chemin valides (chaque segment peut être un chemin absolu, un chemin partiel ou simplement un nom de répertoire ou de fichier). Si un segment de chemin est effectivement un chemin absolu, tous les segments précédents sont ignorés. Si elements est inférieur à 0, nous utilisons l'entier complet. Il est possible que la valeur renvoyée soit en fait un élément de la liste donnée, par conséquent l'appelant doit faire attention à incrémenter le compteur de références du résultat avant de libérer la liste. La valeur renvoyée, typiquement avec un compteur de références de zéro (mais elle pourrait être partagée dans certaines conditions), contient le chemin joint. L'appelant doit incrémenter le compteur de références de la valeur avant de l'utiliser. Si le nombre d'éléments est zéro, la valeur renvoyée sera une chaîne vide Tcl_Obj. **Tcl_FSSplitPath** prend l'objet Tcl donné, qui doit être un chemin valide, et renvoie une valeur de liste contenant chaque segment de ce chemin comme élément. Elle renvoie une valeur de liste avec un compteur de références de zéro. Si le lenPtr passé n'est pas NULL, la variable pointée est mise à jour pour contenir le nombre d'éléments dans la valeur de liste renvoyée. **Tcl_FSEqualPaths** teste si les deux chemins donnés représentent le même objet de système de fichiers. Elle renvoie 1 si les chemins sont égaux, 0 s'ils sont différents. Si l'un des chemins est NULL, elle renvoie toujours 0. **Tcl_FSGetNormalizedPath** tente d'extraire une représentation normalisée unique du chemin donné, dont la valeur de chaîne peut être utilisée comme identifiant unique pour le fichier. Elle renvoie le chemin normalisé, propriété de Tcl, ou NULL si le chemin était invalide ou n'a pas pu être correctement converti. L'extraction des chemins absolus et normaux est très efficace (car le système de fichiers opère en interne sur ces représentations), bien que le résultat lorsqu'il contient plusieurs liens symboliques ne sera pas la version la plus conviviale d'un chemin. La valeur renvoyée est propriété de Tcl et a une durée de vie équivalente à celle de pathPtr passé (sauf s'il s'agit d'un chemin relatif, auquel cas la valeur normalisée peut être libérée à chaque changement de cwd) - l'appelant peut incrémenter le compteur de références s'il le souhaite pour conserver une copie plus longtemps. **Tcl_FSJoinToPath** prend la valeur donnée, qui doit généralement être un chemin valide ou NULL, et joint les segments de chemin donnés. Elle renvoie une valeur, typiquement avec un compteur de références de zéro (mais elle pourrait être partagée dans certaines conditions), contenant le chemin joint. L'appelant doit incrémenter le compteur de références de la valeur avant de l'utiliser. Si l'une des valeurs passées à cette fonction (pathPtr ou éléments path) a un compteur de références de zéro, elles seront libérées lorsque cette fonction renverra. **Tcl_FSConvertToPathType** tente de convertir l'objet Tcl donné en un type de chemin valide, en tenant compte du fait que le cwd a pu changer même si cette valeur est déjà censée être du bon type. Le nom de fichier peut commencer par "~" (pour indiquer le répertoire de l'utilisateur actuel) ou "~" (pour indiquer le répertoire de n'importe quel utilisateur). Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), **TCL_OK** est renvoyé. Sinon, **TCL_ERROR** est renvoyé, et un message d'erreur peut se trouver dans l'interpréteur. **Tcl_FSGetInternalRep** extrait la représentation interne d'une valeur de chemin donnée dans un système de fichiers spécifique. Si la valeur du chemin appartient à un système de fichiers différent, elle renvoie NULL. Si la représentation interne est actuellement NULL, elle tente de la générer en appelant la fonction Tcl_FSCreateInternalRepProc du système de fichiers. Elle renvoie NULL ou une représentation valide du chemin interne. Cette représentation interne est mise en cache, de sorte que des appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. **Tcl_FSGetTranslatedPath** tente d'extraire le chemin traduit à partir de l'objet Tcl donné. Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), la valeur est renvoyée. Sinon, NULL est renvoyé et un message d'erreur peut se trouver dans l'interpréteur. Un chemin traduit est un chemin qui ne contient aucun élément "~" (ceux-ci ont été développés dans leur représentation actuelle dans le système de fichiers). La valeur renvoyée est la propriété de l'appelant, qui doit la stocker ou appeler **Tcl_DecrRefCount** pour s'assurer que la mémoire est libérée. Cette fonction a peu d'utilité pratique, et **Tcl_FSGetNormalizedPath** ou **Tcl_FSGetNativePath** sont généralement des fonctions plus utiles pour de nombreux usages. **Tcl_FSGetTranslatedStringPath** fait la même chose que **Tcl_FSGetTranslatedPath**, mais renvoie une chaîne ou NULL. La chaîne renvoyée est allouée dynamiquement. nd appartenant à l'appelant, qui doit le stocker ou appeler ckfree pour s'assurer qu'il est libéré. Encore une fois, Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des usages.

Tcl_FSNewNativePath effectue quelque chose comme l'inverse des conversions habituelles obj->path->nativerep. Si un code récupère un chemin sous forme native (depuis, par exemple, readlink ou une boîte de dialogue native), et que ce chemin doit être utilisé au niveau Tcl, alors appeler cette fonction est un moyen efficace de créer le type de valeur de chemin approprié.

La valeur résultante est une valeur de type « chemin » pur, qui ne recevra une représentation sous forme de chaîne UTF-8 que si cela est requis par un code Tcl.

Tcl_FSGetNativePath est destiné à être utilisé par les systèmes de fichiers natifs Win/Unix, afin qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un wrapper pratique autour de Tcl_FSGetInternalRep. Il pourrait être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes (par exemple, sur macOS, une représentation utilisant une structure FSRef de fileSpec serait probablement plus efficace). Sous Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Actuellement, la représentation est simplement une chaîne de caractères qui peut contenir le chemin relatif ou un chemin normalisé complet et absolu dans le codage natif (des conditions complexes dictent lequel de ceux-ci sera fourni, donc aucun ne peut être fiable, sauf si le chemin est connu pour être absolu). Si vous avez besoin d'un chemin natif qui doit être absolu, vous devriez demander la version native d'un chemin normalisé. Si, pour une raison quelconque, une version non absolue et non normalisée du chemin est nécessaire, cela doit être construit séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache afin que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle du pathPtr passé (sauf s'il s'agit d'un chemin relatif, auquel cas la représentation native peut être libérée à tout moment où le cwd change).

Tcl_FSFileSystemInfo renvoie une liste de deux éléments. Le premier élément est le nom du système de fichiers (par exemple, « native », « vfs », « zip », ou « prowrap », peut-être), et le second est le type particulier du chemin donné au sein de ce système de fichiers (qui dépend du système de fichiers). Le second élément peut être vide si le système de fichiers ne fournit pas de catégorisation supplémentaire de fichiers.

Une valeur de liste valide est renvoyée, sauf si la valeur du chemin n'est pas reconnue, auquel cas NULL sera renvoyé.

Tcl_FSGetFileSystemForPath renvoie un pointeur vers le Tcl_Filesystem qui accepte ce chemin comme valide.

Si aucun système de fichiers n'accepte le chemin, NULL est renvoyé.

Tcl_FSGetPathType détermine si le chemin donné est relatif au répertoire courant, relatif au volume courant, ou absolu.

Il renvoie l'une des valeurs TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, ou TCL_PATH_VOLUME_RELATIVE

API DU SYSTÈME DE FICHIERS VIRTUEL

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un système de fichiers ; ces opérations sont invoquées au besoin par la couche générique, ce qui se produit généralement par le biais des fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un morceau de données facultatif à associer à ce système de fichiers. En appelant cette fonction, Tcl attachera le système de fichiers à la liste des systèmes de fichiers connus, et il deviendra pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera renvoyé.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et renvoie TCL_OK. Si le système de fichiers n'est actuellement pas enregistré, TCL_ERROR est renvoyé.

Tcl_FSData renverra le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il renverra NULL.

Tcl_FSMountsChanged est utilisé pour informer le cœur de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

La structure Tcl_Filesystem contient les champs suivants :

    Tcl_FSCreateInternalRepProc *createInternalRepProc;

    Tcl_FSFilesystemPathTypeProc *filesystemPathTypeProc;
    Tcl_FSFilesystemSeparatorProc *filesystemSeparatorProc;
    Tcl_FSStatProc *statProc;
    Tcl_FSAccessProc *accessProc;
    Tcl_FSOpenFileChannelProc *openFileChannelProc;
    Tcl_FSMatchInDirectoryProc *matchInDirectoryProc;
    Tcl_FSUtimeProc *utimeProc;
    Tcl_FSLinkProc *linkProc;
    Tcl_FSListVolumesProc *listVolumesProc;
    Tcl_FSFileAttrStringsProc *fileAttrStringsProc;
    Tcl_FSFileAttrsGetProc *fileAttrsGetProc;
    Tcl_FSFileAttrsSetProc *fileAttrsSetProc;
    Tcl_FSCreateDirectoryProc *createDirectoryProc;
    Tcl_FSRemoveDirectoryProc *removeDirectoryProc;

    Tcl_FSCopyFileProc *copyFileProc;
    Tcl_FSRenameFileProc *renameFileProc;
    Tcl_FSCopyDirectoryProc *copyDirectoryProc;

    Tcl_FSChdirProc *chdirProc;

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche générique du système de fichiers pour effectuer l'ensemble complet des actions liées au système de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (la quasi-totalité d'entre elles doit être implémentée), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni), et fonctions d'efficacité (qui doivent seulement être implémentées si elles peuvent l'être efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces solutions de repli ne sont utilisées que pour gérer les commandes initiées dans Tcl, et non en C. Cela signifie que si une commande file rename est émise dans Tcl, et que les systèmes de fichiers pertinents n'implémentent pas leur Tcl_FSRenameFileProc, le cœur de Tcl utilisera une combinaison d'autres fonctions du système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a une autre solution de repli). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun de ces replis ne se produit. Ceci est vrai sauf pour les quatre dernières entrées du tableau des systèmes de fichiers (lstat, load, getcwd et chdir) pour lesquelles des replis se produisent effectivement au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme Tcl_Obj les prennent sous forme UTF-8. L'API d'infrastructure des systèmes de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

INFRASTRUCTURE DU SYSTÈME DE FICHIERS

Ces champs contiennent des informations de base sur la structure du système de fichiers et des adresses de fonctions utilisées pour associer un système de fichiers donné à un chemin de fichier, et pour gérer la représentation interne des chemins, par exemple, copier et libérer ces représentations.

TYPENAME

Le champ typeName contient une chaîne terminée par NULL qui identifie le type du système de fichiers implémenté, par exemple, native, zip ou vfs.

STRUCTURE_LENGTH

Le champ structureLength est généralement implémenté comme sizeof(Tcl_Filesystem), et il est là pour permettre une compatibilité binaire plus facile si la taille de la structure change dans une future version de Tcl.

VERSION

Le champ version doit être défini sur TCL_FILESYSTEM_VERSION_1.

PATHINFILESYSTEMPROC

Le champ pathInFilesystemProc contient l'adresse d'une fonction qui est appelée pour déterminer si une valeur de chemin donnée appartient à ce système de fichiers ou non. Tcl appellera uniquement le reste des fonctions du système de fichiers avec un chemin pour lequel cette fonction renvoie TCL_OK. Si le chemin n'appartient pas, -1 doit être renvoyé (le comportement de Tcl pour toute autre valeur renvoyée n'est pas défini). Si TCL_OK est renvoyé, alors le paramètre de sortie optionnel clientDataPtr peut être utilisé pour renvoyer une représentation interne (spécifique au système de fichiers) du chemin, qui sera stockée dans la valeur du chemin et pourra être récupérée efficacement par d'autres fonctions de système de fichiers. Tcl stockera simultanément l'information que ce chemin appartient à ce système de fichiers. De telles caches sont invalidées lorsque les systèmes de fichiers sont ajoutés ou supprimés de la liste interne des systèmes de fichiers connus de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

DUPINTERNALREPPROC

Cette fonction crée une copie de la représentation interne d'un chemin et est appelée lorsque Tcl a besoin de dupliquer une valeur de chemin. Si elle est NULL, Tcl ne copiera tout simplement pas la représentation interne, qui devra peut-être être régénérée plus tard.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

FREEINTERNALREPPROC

Libère la représentation interne. Doit être implémentée si la représentation interne doit être libérée (c'est-à-dire si de la mémoire a été allouée lors de la génération d'une représentation interne), mais peut être NULL sinon.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

INTERNALTONORMALIZEDPROC

Fonction pour convertir la représentation interne en un chemin normalisé. Elle n'est requise que si le système de fichiers crée des valeurs de chemin pures sans aucune représentation de chaîne ou de chemin. La valeur renvoyée est une valeur Tcl dont la représentation string est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

CREATEINTERNALREPPROC

Fonction pour prendre une valeur de chemin et calculer une représentation interne pour celle-ci, et stocker cette représentation native dans la valeur. Peut être NULL si les chemins n'ont pas de représentation interne, ou si le Tcl_FSPathInFilesystemProc pour ce système de fichiers crée toujours immédiatement une représentation interne pour les chemins qu'il accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

NORMALIZEPATHPROC

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations de chaîne pour la même valeur de chemin. Dans Tcl, chaque path doit avoir une représentation de chaîne normalisée unique. Selon le système de fichiers, il peut y avoir plus d'une représentation de chaîne non normalisée qui fait référence au même chemin (par exemple, un chemin relatif, un chemin avec une casse différente si le système de fichiers est insensible à la casse, un chemin contenant un lien symbolique, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être résolu en la valeur vers laquelle il pointe (mais sa casse ou d'autres aspects doivent être uniques). Tous les autres composants du chemin doivent être résolus à partir des liens symboliques. Cette exception est nécessaire pour être cohérent avec la sémantique de Tcl pour file delete, file rename, file copy lors de la manipulation des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint au début du chemin (c'est-à-dire zéro), à la fin du chemin, ou à n'importe quel point séparateur de fichier intermédiaire. Elle ne pointera jamais vers une position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS DU SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent des adresses de fonctions qui sont appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui devrait être utilisé avec l'ensemble complet des commandes Tcl doit implémenter toutes celles-ci. Si certaines d'entre elles ne sont pas implémentées, certaines commandes Tcl peuvent échouer lors de l'opération sur des chemins appartenant à ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques ne devrait pas implémenter la fonction readlink, etc. Le cœur de Tcl s'attend à ce que les systèmes de fichiers se comportent de cette manière).

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(

STATPROC

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent crucialement (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La fonction Tcl_FSStatProc remplit la structure statPtr avec des informations sur le fichier spécifié. Aucun droit d'accès au fichier n'est requis pour obtenir ces informations, mais des droits de parcours sont requis pour tous les répertoires mentionnés dans le chemin menant au fichier. La structure stat inclut des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (toujours 1 sous Windows), l'UID (toujours 0 sous Windows), le GID (toujours 0 sous Windows), le rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification et l'heure du dernier changement de métadonnées.

Si le fichier représenté par pathPtr existe, Tcl_FSStatProc renvoie 0 et la structure statPtr est remplie de données. Sinon, -1 est renvoyé et aucune information de stat n'est donnée.

ACCESSPROC

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent crucialement (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La fonction Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet de système de fichiers) dont le nom est dans pathPtr. Si le nom de chemin fait référence à un lien symbolique, alors les droits d'accès du fichier auquel ce lien symbolique fait référence doivent être vérifiés.

En cas de succès (tous les droits demandés sont accordés), 0 est renvoyé. En cas d'erreur (au moins un bit dans mode demande un droit refusé, ou une autre erreur se produit), -1 est renvoyé.

OPENFILECHANNELPROC

Fonction pour traiter un appel à Tcl_FSOpenFileChannel. Doit être implémentée pour tout système de fichiers raisonnable, car toutes les opérations qui nécessitent l'ouverture ou l'accès au contenu d'un fichier l'utiliseront (par ex. open, encoding, et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

Le Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et renvoie un descripteur de canal qui peut être utilisé pour effectuer des opérations d'entrée et de sortie sur le fichier. Cette API est calquée sur la procédure fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier, où l'argument mode est une combinaison des indicateurs POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, le Tcl_FSOpenFileChannelProc renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, le Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le nouveau canal créé ne doit pas être enregistré dans l'interpréteur fourni par un Tcl_FSOpenFileChannelProc ; cette tâche incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, la création du nouveau canal lui assigne également comme remplacement du canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, la fonctionnalité de glob et de copie récursive sera manquante dans le système de fichiers (et cela peut impacter les commandes comme encoding names qui utilisent en interne la fonctionnalité de glob).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit renvoyer tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au modèle donné et qui respectent la spécification des types fournie. Il y a deux façons dont cette fonction peut être appelée. Si pattern est NULL, alors pathPtr est une spécification de chemin complet d'un seul fichier ou répertoire qui doit être vérifié pour son existence et son type correct. Sinon, pathPtr est un répertoire, dont le contenu doit être recherché par la fonction pour trouver des fichiers ou des répertoires du type correct. Dans les deux cas, on peut supposer que pathPtr n'est ni NULL ni vide. Il n'est actuellement pas documenté si pathPtr aura ou non un séparateur de fichier à la fin, donc le code doit être flexible aux deux possibilités.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de correspondance. Les messages d'erreur sont placés dans interp, sauf si interp est NULL, auquel cas aucun message d'erreur ne doit être généré ; en cas de résultat TCL_OK, les résultats doivent être ajoutés à la valeur resultPtr donnée (qui peut être supposée être une liste Tcl valide non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (cela signifie généralement qu'il s'agira de spécifications de chemin absolu). Notez que si aucune correspondance n'est trouvée, cela conduit simplement à un résultat vide ; les erreurs ne sont signalées que pour les problèmes réels de fichiers ou de système de fichiers qui peuvent survenir pendant le processus de correspondance.

La structure Tcl_GlobTypeData passée dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions du fichier */
    int perm;
    /* Type Mac acceptable */
    Tcl_Obj *macType;
    /* Créateur Mac acceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de traiter correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT sont vrais (et en particulier lorsque les autres indicateurs sont faux). Dans le premier de ces cas, la fonction doit lister les répertoires contenus. Tcl utilise cela pour implémenter le globbing récursif, il est donc essentiel que les systèmes de fichiers implémentent correctement la correspondance de répertoires. Dans le second de ces cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage qui se trouvent dans le pathPtr donné (et dans ce cas, pathPtr n'a pas besoin de se trouver dans le même système de fichiers - différent de tous les autres cas où cette fonction est appelée). Le support pour cela est essentiel si Tcl veut avoir des transitions transparentes entre un système de fichiers et un autre.

UTIMEPROC

Fonction pour traiter un appel à Tcl_FSUtime. Requis pour permettre la définition (pas la lecture) des heures avec file mtime, file atime et l'implémentation open-r/open-w/fcopy de file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les heures d'accès et de modification du fichier spécifié par pathPtr doivent être modifiées pour correspondre aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec la fonction système utime.

LINKPROC

Fonction pour traiter un appel à Tcl_FSLink. Ne doit être implémentée que si le système de fichiers prend en charge les liens, et peut sinon être NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est invitée à lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant (et son compteur de références doit donc être incrémenté avant d'être renvoyé). Tous les appelants doivent appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'est plus nécessaire. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Le résultat dans ce cas doit être toPtr si le lien a réussi et NULL sinon. Dans ce cas, le résultat n'appartient pas à l'appelant (c'est-à-dire qu'aucune manipulation de compteur de références des deux côtés n'est nécessaire). Voir la documentation de Tcl_FSLink pour l'interprétation correcte des indicateurs linkAction.

LISTVOLUMESPROC

Fonction pour lister les volumes de systèmes de fichiers ajoutés par ce système de fichiers. Doit être implémentée uniquement si le système de fichiers ajoute des volumes en tête de la hiérarchie du système de fichiers, afin qu'ils puissent être retournés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste de volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. La valeur de retour est considérée comme appartenant au système de fichiers (pas au cœur de Tcl), mais un compteur de références doit lui être attribué pour Tcl. Tcl utilisera le contenu de la liste et décrémentera ensuite ce compteur de références. Cela permet aux systèmes de fichiers de choisir s'ils souhaitent réellement conserver une liste « globale » de volumes ou non (si ce n'est pas le cas, ils génèrent la liste à la volée et la transmettent à Tcl avec un compteur de références de 1, puis oublient la liste ; si oui, ils incrémentent simplement le compteur de références de leur liste globale et la transmettent à Tcl qui en copiera le contenu puis décrémentera le compteur pour revenir à sa valeur précédente).

Par conséquent, Tcl considère les valeurs de retour de cette proc comme étant en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne prendra pas en charge la commande file attributes. Cela permet d'attacher des informations supplémentaires arbitraires aux fichiers dans le système de fichiers. Si elle n'est pas implémentée, il n'est pas nécessaire d'implémenter les méthodes get et set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La fonction appelée peut soit renvoyer un tableau de chaînes, soit renvoyer NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer qu'il renvoie une valeur avec un compteur de références d'au moins un.

FILESYSTEM EFFICIENCY

Ces fonctions ne doivent pas être implémentées pour un système de fichiers particulier, car le noyau dispose d'une implémentation de secours. Voir chaque description individuelle pour les conséquences de laisser les champs NULL.

LSTATPROC

Fonction pour traiter un appel à Tcl_FSLstat. Si elle n'est pas implémentée, Tcl tentera d'utiliser le statProc précédemment défini. Par conséquent, elle ne devrait être implémentée que si le système de fichiers peut différencier les appels stat et lstat.

typedef int Tcl_FSLstatProc(
                Tcl_Obj *pathPtr,
                Tcl_StatBuf *statPtr);

Le comportement de cette fonction est très similaire à celui de Tcl_FSStatProc précédemment défini, sauf qu'elle s'applique à un lien symbolique, auquel cas elle renvoie des informations sur le lien, et non sur le fichier cible.

COPYFILEPROC

Fonction pour traiter un appel à Tcl_FSCopyFile. Si elle n'est pas implémentée, Tcl se rabattra sur le mode open-r, open-w et fcopy comme mécanisme de copie. Par conséquent, elle ne devrait être implémentée que si le système de fichiers peut effectuer cette opération plus efficacement.

typedef int Tcl_FSCopyFileProc(
                Tcl_Obj *srcPathPtr,
                Tcl_Obj *destPathPtr);

La valeur de retour est un code de résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de copie. Il faut noter que destPathPtr est le nom du fichier qui devrait devenir la copie de srcPathPtr. Ce ne sera jamais le nom d'un répertoire dans lequel srcPathPtr peut être copié (c'est-à-dire que le fonctionnement est beaucoup plus simple que le sous-commande file copy du niveau Tcl). Il faut noter que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera cette fonction et non copyDirectoryProc lorsque cela est nécessaire pour les copier (même s'ils sont des liens symboliques vers des répertoires). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de copie de fichiers, en appelant Tcl_SetErrno(EXDEV) et en renvoyant un résultat autre que TCL_OK, cela indiquera à Tcl d'utiliser ses mécanismes de secours standard.

Fonction pour traiter un appel à Tcl_FSRenameFile. Si elle n'est pas implémentée, Tcl se rabattra sur un mécanisme de copie et de suppression. Par conséquent, elle ne devrait être implémentée que si le système de fichiers peut effectuer cette opération plus efficacement.

typedef int Tcl_FSRenameFileProc(
                Tcl_Obj *srcPathPtr,

Par conséquent, elle ne devrait être implémentée que si le système de fichiers peut charger du code directement, ou si elle peut être implémentée simplement pour renvoyer TCL_ERROR afin de désactiver la fonctionnalité de chargement sur ce système de fichiers.

Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de chargement de fichiers, en appelant Tcl_SetErrno(EXDEV) et en renvoyant un résultat autre que TCL_OK, cela indiquera à Tcl d'utiliser ses mécanismes de secours standard.
