Interpréteur à utiliser pour la gestion des erreurs, ou NULL si aucune gestion d'erreur n'est souhaitée.
const char *name (en entrée)
Nom de l'encodage à charger.
Tcl_Encoding encoding (en entrée)
L'encodage à interroger, libérer ou utiliser pour la conversion de texte. Si encoding est NULL, l'encodage système courant est utilisé.
Tcl_Obj *objPtr (en entrée)
Nom de l'encodage pour lequel obtenir un jeton.
Tcl_Encoding *encodingPtr (en sortie)
Pointe vers le stockage où le jeton d'encodage doit être écrit.
const char *src (en entrée)
Pour les fonctions Tcl_ExternalToUtf, un tableau d'octets dans l'encodage spécifié qui doit être converti en UTF-8. Pour les fonctions Tcl_UtfToExternal et Tcl_WinUtfToTChar, un tableau de caractères UTF-8 à convertir dans l'encodage spécifié.
const TCHAR *tsrc (en entrée)
Un tableau de caractères Windows TCHAR à convertir en UTF-8.
int srcLen (en entrée)
Longueur de src ou tsrc en octets. Si la longueur est négative, la longueur spécifique à l'encodage de la chaîne est utilisée.
Tcl_DString *dstPtr (en sortie)
Pointeur vers une Tcl_DString non initialisée ou libérée dans laquelle le résultat converti sera stocké.
int flags (en entrée)
Divers bits de drapeau mis en OR. TCL_ENCODING_START signifie que le tampon source est le premier bloc d'un flux d'entrée (potentiellement multi-blocs), indiquant à la routine de conversion de réinitialiser à un état initial et d'effectuer toute initialisation nécessaire avant que le premier octet ne soit converti. TCL_ENCODING_END signifie que le tampon source est le dernier bloc d'un flux d'entrée (potentiellement multi-blocs), indiquant à la routine de conversion d'effectuer toute finalisation nécessaire après la conversion du dernier octet, puis de se réinitialiser à un état initial. TCL_ENCODING_STOPONERROR signifie que la routine de conversion doit retourner immédiatement après avoir lu un caractère source qui n'existe pas dans l'encodage cible ; sinon, un caractère de repli par défaut sera automatiquement substitué.
Tcl_EncodingState *statePtr (en entrée/sortie)
Utilisé lors de la conversion d'un flux d'octets (généralement long ou de longueur indéfinie) morceau par morceau. La routine de conversion stocke son état actuel dans *statePtr après la conversion de src (le tampon contenant le morceau courant) ; ces informations d'état doivent être renvoyées lors de la conversion du morceau suivant du flux afin que la routine de conversion sache dans quel état elle s'est arrêtée à la fin du dernier morceau. Peut être NULL, auquel cas la valeur spécifiée pour flags est ignorée et le tampon source est supposé contenir la chaîne complète à convertir.
char *dst (en sortie)
Tampon dans lequel le résultat converti sera stocké. Pas plus de dstLen octets seront stockés dans dst.
int dstLen (en entrée)
La longueur maximale du tampon de sortie dst en octets.
int *srcReadPtr (en sortie)
Rempli avec le nombre d'octets de src qui ont été effectivement convertis. Cela peut être inférieur à la longueur source d'origine s'il y a eu un problème lors de la conversion de certains caractères source. Peut être NULL.
int *dstWrotePtr (en sortie)
Rempli avec le nombre d'octets qui ont été effectivement stockés dans le tampon de sortie suite à la conversion. Peut être NULL.
int *dstCharsPtr (en sortie)
Rempli avec le nombre de caractères qui correspondent au nombre d'octets stockés dans le tampon de sortie. Peut être NULL.
Tcl_DString *bufPtr (en sortie)

INTRODUCTION

Ces routines convertissent entre la représentation interne des caractères de Tcl, UTF-8, et les représentations de caractères utilisées par divers systèmes d'exploitation ou systèmes de fichiers, tels que Unicode, ASCII ou Shift-JIS. Lors de l'opération sur des chaînes, comme l'obtention des noms de fichiers ou l'affichage de caractères à l'aide de polices internationales, les chaînes doivent être traduites dans un ou plusieurs formats que les divers appels système peuvent utiliser. Par exemple, sur un poste de travail Unix japonais, un utilisateur peut obtenir un nom de fichier représenté dans l'encodage de fichier EUC-JP, puis traduire les caractères dans l'encodage de police jisx0208 afin d'afficher le nom de fichier dans un widget Tk. Le but du package d'encodage est d'aider à combler le fossé de traduction. UTF-8 fournit une zone de transit intermédiaire pour tous les différents encodages. Dans l'exemple ci-dessus, le texte serait traduit en UTF-8 à partir de l'encodage de fichier utilisé par le système d'exploitation. Ensuite, il serait traduit d'UTF-8 vers l'encodage de police requis par les routines d'affichage.

Certains encodages de base sont compilés dans Tcl. D'autres peuvent être définis par l'utilisateur ou chargés dynamiquement à partir de fichiers d'encodage d'une manière indépendante de la plateforme.

DESCRIPTION

Tcl_GetEncoding recherche un encodage donné son name. Le nom peut faire référence à un encodage Tcl intégré, à un encodage défini par l'utilisateur enregistré en appelant Tcl_CreateEncoding, ou à un fichier d'encodage chargeable dynamiquement. La valeur de retour est un jeton qui représente l'encodage et peut être utilisé dans des appels ultérieurs à des procédures telles que Tcl_GetEncodingName, Tcl_FreeEncoding et Tcl_UtfToExternal. Si le nom ne fait référence à aucun encodage connu ou chargeable, NULL est retourné et un message d'erreur est retourné dans interp.

Le package d'encodage maintient une base de données de tous les encodages actuellement en usage. La première fois que name est vu, Tcl_GetEncoding renvoie un encodage avec un compteur de références de 1. Si le même name est demandé plusieurs fois, le compteur de références pour cet encodage est incrémenté sans le surcoût d'allocation d'un nouvel encodage et de toutes ses structures de données associées.

Lorsqu'un encoding n'est plus nécessaire, Tcl_FreeEncoding doit être appelé pour le libérer. Lorsqu'un encoding n'est plus utilisé nulle part (c'est-à-dire qu'il a été libéré autant de fois qu'il a été obtenu), Tcl_FreeEncoding libérera tout le stockage utilisé par l'encodage et le supprimera de la base de données.

Tcl_GetEncodingFromObj traite la représentation sous forme de chaîne de objPtr comme un nom d'encodage, et recherche un encodage portant ce nom, tout comme le fait Tcl_GetEncoding. Toda la estructura del archivo. El valor `encodingPtr` es el que se encarga de la codificación, y el valor `TCL_OK` se devuelve. Si no se encuentra ninguna codificación correspondiente, se devuelve `TCL_ERROR` y no se realiza ningún escribimiento en `*encodingPtr`. Así como con `Tcl_GetEncoding`, el llamador debe llamar a `Tcl_FreeEncoding` sobre el token de codificación resultante cuando este ya no se utilizará.

Tcl_ExternalToUtfDString convierte un buffer fuente `src` de la codificación especificada `encoding` en UTF-8. Los bytes convertidos se almacenan en `dstPtr`, que se termina con el carácter nulo específico para la codificación. El llamador debe llamar a `Tcl_DStringFree` para liberar cualquier información almacenada en `dstPtr`. Cuando se convierte, si algún carácter en el buffer fuente no puede representarse en la codificación objetivo, se usa un carácter de reemplazo por defecto. El valor devuelto es un puntero al valor almacenado en el DString.

Tcl_ExternalToUtf convierte un buffer fuente `src` de la codificación especificada `encoding` en UTF-8. Se convierten hasta `srcLen` bytes del buffer fuente y se almacenan hasta `dstLen` bytes en `dst`. En todos los casos, `*srcReadPtr` se llena con el número de bytes que se convirtieron con éxito desde `src`, y `*dstWrotePtr` se llena con el número de bytes que se almacenaron en `dst`. El valor devuelto es uno de los siguientes:

TCL_OK
Todos los bytes de `src` se convirtieron.
TCL_CONVERT_NOSPACE
El buffer de destino no es suficiente para almacenar todos los datos convertidos; se convirtieron tantos caracteres como pudieron, aunque el espacio fuera insuficiente.
TCL_CONVERT_MULTIBYTE
Los últimos bytes del buffer fuente eran el inicio de una secuencia de múltiples bytes, pero se necesitaban más bytes para completar esta secuencia. Una llamada posterior a la rutina de conversión debe pasar un buffer que contenga los bytes no convertidos que quedan en `src` más algunos bytes adicionales de la fuente para convertir correctamente la secuencia que había sido dividida previamente.
TCL_CONVERT_SYNTAX
El buffer fuente contuvo una secuencia de caracteres inválida. Esto puede ocurrir si el flujo de entrada ha sido dañado o si el método de codificación de entrada fue mal identificado.
TCL_CONVERT_UNKNOWN
El buffer fuente contuvo un carácter que no se puede representar en la codificación objetivo y `TCL_ENCODING_STOPONERROR` fue especificado.

Tcl_UtfToExternalDString convierte un buffer fuente `src` de UTF-8 en la codificación especificada `encoding`. Los bytes convertidos se almacenan en `dstPtr`, que se termina con el carácter nulo específico para la codificación. El llamador debe llamar a `Tcl_DStringFree` para liberar cualquier información almacenada en `dstPtr`. Cuando se convierte, si algún carácter en el buffer fuente no puede representarse en la codificación objetivo, se usa un carácter de reemplazo por defecto. El valor devuelto es un puntero al valor almacenado en el DString.

Tcl_UtfToExternal convierte un buffer fuente `src` de UTF-8 en la codificación especificada `encoding`. Se convierten hasta `srcLen` bytes del buffer fuente y se almacenan hasta `dstLen` bytes en `dst`. En todos los casos, `*srcReadPtr` se llena con el número de bytes que se convirtieron con éxito desde `src`, y `*dstWrotePtr` se llena con el número de bytes que se almacenaron en `dst`. Los valores devueltos son los mismos que los de `Tcl_ExternalToUtf`.

Tcl_WinUtfToTChar y Tcl_WinTCharToUtf son funciones de conveniencia para convertir entre UTF-8 y strings de Windows basadas en el tipo TCHAR, que por conveniencia es un carácter Unicode en Windows NT.

Tcl_GetEncodingName es aproximadamente el inverso de `Tcl_GetEncoding`. Dado un `encoding`, el valor devuelto es el `name` que se utilizó para crear la codificación. El string devuelto por `Tcl_GetEncodingName` solo es garantizado para persistir hasta que el `encoding` sea eliminado. El llamador debe no modificar este string.

Tcl_SetSystemEncoding establece la codificación por defecto que se debe usar cuando el usuario pasa un valor nulo para el argumento `encoding` a cualquier función de codificación. Si `name` es nulo, la codificación del sistema es reestablecida al codificador por defecto, `binary`. Si el nombre no se refiere a ninguna codificación conocida o cargable, se devuelve `TCL_ERROR` y un mensaje de error se deja en `interp`. De otro modo, este procedimiento incrementa el contador de referencia de la nueva codificación del sistema, decrementa el contador de referencia de la codificación antigua del sistema, y devuelve `TCL_OK`.

Tcl_GetEncodingNameFromEnvironment proporciona un medio para que la librería Tcl reporte el nombre de la codificación que cree creer es el correcto para ser la codificación del sistema, basado en llamadas de sistema y examen del entorno adecuado para la plataforma. acepta `bufPtr`, un puntero a un `Tcl_DString` no inicializado o liberado, y escribe el nombre de la codificación en él. El valor devuelto es el valor de `Tcl_DStringValue`.

Tcl_GetEncodingNames establece el resultado `interp` como una lista que incluye los nombres de todas las codificaciones definidas o dinámicamente cargables, buscando en la ruta de codificaciones especificada por `Tcl_SetDefaultEncodingDir`. Este procedimiento no garantiza que los archivos dinámicamente cargables contengan datos válidos, pero solo garantiza que existan.

Tcl_CreateEncoding define una nueva codificación y registra los procedimientos C que se llaman cuando se convierte entre esta codificación y UTF-8. Las codificaciones creadas por `Tcl_CreateEncoding` son visibles en la base de datos usada por `Tcl_GetEncoding`. De manera similar a `Tcl_GetEncoding`, el valor devuelto es un token que representa la codificación y puede usarse en llamadas posteriores a otras funciones de codificación. `Tcl_CreateEncoding` devuelve una codificación con un contador de referencia de 1. Si una codificación con el nombre especificado ya existe, su registro en la base de datos se reemplaza con la nueva codificación; el token de la codificación antigua permanece válido y continúa a comportarse como antes, pero los usuarios del nuevo token ahora llamarán las procedimientos de codificación nuevas.

El argumento `typePtr` de `Tcl_CreateEncoding` contiene información sobre el nombre de la codificación y los procedimientos que se llaman cuando se convierte entre esta codificación y UTF-8. Se define como: 

typedef struct Tcl_EncodingType {
    const char *encodingName;
    Tcl_EncodingConvertProc *toUtfProc;
    Tcl_EncodingConvertProc *fromUtfProc;
    Tcl_EncodingFreeProc *freeProc;
    ClientData clientData;
    int nullSize;
} Tcl_EncodingType;

El `encodingName` proporciona un nombre para la codificación, mediante el cual se puede referir en otras procedimientos como `Tcl_GetEncoding`. El `toUtfProc` se refiere a un procedimiento de callback para convertir texto de esta codificación a UTF-8. El `fromUtfProc` se refiere a un procedimiento de callback para convertir texto de UTF-8 a esta codificación. El `freeProc` se refiere a un procedimiento de callback para invocar cuando se elimina esta codificación. El campo `freeProc` puede ser `NULL`. El `clientData` contiene un valor de una palabra arbitraria pasado a `toUtfProc`, `fromUtfProc` y `freeProc` cuando se les llama. Por lo general, este es un puntero a un estructura de datos que contiene información específica de codificación que puede usarse por los procedimientos de callback. Por ejemplo, dos codificaciones muy similares como `ascii` y `macRoman` pueden usar el mismo procedimiento de callback, pero usan valores diferentes de `clientData` para controlar su comportamiento. El `nullSize` especifica el número de bytes nulos que indican el fin de cadena en esta codificación. Debe ser `1` (para codificaciones de solo un byte o multi-byte como ASCII o Shift-JIS) o `2` (para codificaciones de dos bytes como Unicode). Las codificaciones constantes con 3 o más bytes por carácter (como CNS11643) no son aceptadas.

Los procedimientos de callback `toUtfProc` y `fromUtfProc` deben corresponder al tipo `Tcl_EncodingConvertProc:` 

typedef int Tcl_EncodingConvertProc(
        ClientData clientData,
        const char *src,
        int srcLen,
        int flags,
        Tcl_EncodingState *statePtr,
        char *dst,
        int dstLen,
        int *srcReadPtr,
        int *dstWrotePtr,
        int *dstCharsPtr);

Los procedimientos de callback `toUtfProc` y `fromUtfProc` se llaman por `Tcl_ExternalToUtf` o `Tcl_UtfToExternal` para realizar la conversión real. El parámetro `clientData` de estos procedimientos es el mismo que el campo `clientData` especificado en `Tcl_CreateEncoding` cuando se creó la codificación. Los argumentos restantes de los procedimientos de callback son los mismos que los argumentos, documentados en el inicio, de `Tcl_ExternalToUtf` o `Tcl_UtfToExternal`, con las siguientes excepciones. Si el argumento `srcLen` de una de estas funciones de nivel alto es negativo, el valor pasado al procedimiento de callback será el largo adecuado de `src` para la codificación. Si algún de los argumentos `srcReadPtr`, `dstWrotePtr` o `dstCharsPtr` de una de estas funciones de nivel alto es `NULL`, el valor correspondiente pasado al procedimiento de callback será una ubicación no nula.

El procedimiento de callback `freeProc`, si no es `NULL`, debe corresponder al tipo `Tcl_EncodingFreeProc:` 

typedef void Tcl_EncodingFreeProc(
        ClientData clientData);

Este `freeProc` se llama cuando se elimina la codificación. El parámetro `clientData` es el mismo que el campo `clientData` especificado en `Tcl_CreateEncoding` cuando se creó la codificación.

Tcl_GetEncodingSearchPath y Tcl_SetEncodingSearchPath se llaman para acceder y establecer la lista de carpetas de directorios de archivos de datos de codificación.

El valor devuelto por `Tcl_GetEncodingSearchPath` es el valor almacenado por la última llamada exitosa a `Tcl_SetEncodingSearchPath`. Si no se han realizado llamadas a `Tcl_SetEncodingSearchPath`, Tcl calculará un valor inicial basado en el entorno. Hay una ruta de búsqueda de codificación para el proceso completo, compartida por todos los hilos del proceso.

Tcl_SetEncodingSearchPath almacena `searchPath` y devuelve `TCL_OK`, excepto si `searchPath` no es una lista válida de Tcl, en cuyo caso se devuelve `TCL_ERROR`. Los elementos de `searchPath` se procesan como se describe en `Tcl_SetEncodingSearchPath`.

SYNOPIS

Tcl_GetDefaultEncodingDir et Tcl_SetDefaultEncodingDir sont des interfaces obsolètes qu'il est préférable de remplacer par des appels à Tcl_GetEncodingSearchPath et Tcl_SetEncodingSearchPath. Elles sont appelées pour accéder et définir le premier élément de la liste searchPath. Comme Tcl recherche dans searchPath les fichiers de données d'encodage dans l'ordre de la liste, ces routines établissent le répertoire "par défaut" dans lequel trouver les fichiers de données d'encodage.

INTRODUCTION

L'espace interdirait la pré-compilation de tous les algorithmes d'encodage possibles dans Tcl, de sorte que de nombreux encodages sont stockés sur disque sous forme de fichiers d'encodage chargeables dynamiquement. Ce comportement permet également à l'utilisateur de créer des fichiers d'encodage supplémentaires qui peuvent être chargés en utilisant le même mécanisme. Ces fichiers d'encodage contiennent des informations sur les tables et/ou les séquences d'échappement utilisées pour faire la correspondance entre un encodage externe et Unicode. L'encodage externe peut être constitué de caractères sur un octet, plusieurs octets ou deux octets.

Chaque encodage chargeable dynamiquement est représenté par un fichier texte. La première ligne du fichier, commençant par un symbole #, est un commentaire qui fournit une description lisible par l'homme du fichier. La ligne suivante identifie le type de fichier d'encodage. Il peut s'agir de l'une des lettres suivantes :

[1] S
Un encodage sur un octet, où un caractère a toujours une longueur d'un octet dans l'encodage. Un exemple est l'iso8859-1, utilisé par de nombreuses langues européennes.
[2] D
Un encodage sur deux octets, où un caractère a toujours une longueur de deux octets dans l'encodage. Un exemple est le big5, utilisé pour le texte chinois.
[3] M
Un encodage multi-octets, où un caractère peut avoir une longueur d'un ou deux octets. Certains octets sont des octets de tête, indiquant qu'un autre octet doit suivre et que les deux octets ensemble représentent un caractère. D'autres octets ne sont pas des octets de tête et se représentent eux-mêmes. Un exemple est le shiftjis, utilisé par de nombreux ordinateurs japonais.
[4] E
Un encodage à séquence d'échappement, spécifiant que certaines séquences d'octets ne représentent pas des caractères, mais des commandes qui décrivent comment les octets suivants doivent être interprétés.

Le reste des lignes du fichier dépend du type.

Les cas [1], [2] et [3] sont collectivement appelés fichiers d'encodage basés sur des tables. Les lignes d'un fichier d'encodage basé sur des tables sont au même format que cet exemple tiré de l'encodage shiftjis (ce n'est pas le fichier complet) :

Les lignes de ces types d'encodage sont des séries de nombres hexadécimaux représentant des octets de code. Les lignes commençant par un caractère hexadécimal représentent la table de codage. Chaque paire de nombres hexadécimaux représente la valeur Unicode d'un caractère. La position de la paire dans le fichier détermine l'octet (ou la paire d'octets) qui correspond à ce caractère Unicode. Par exemple, la première ligne de la table du fichier ci-dessus est :

0000000100020003000400050006000700080009000A000B000C000D000E000F

Cela signifie que l'octet 00 correspond au caractère Unicode U+0000, l'octet 01 correspond à U+0001, et ainsi de suite. Pour un encodage sur un octet, il y a 256 octets de code dans le fichier (00-FF). Pour un encodage sur deux octets, il y a 256 * 256 paires d'octets de code.

Pour les encodages multi-octets, les lignes avant la table de codage sont utilisées pour spécifier les octets de tête. L'encodage shiftjis a également une première ligne, `003F 0 40`, qui spécifie que l'octet de code `0x3F` mappe vers l'Unicode `U+0040` et qu'il n'est pas un octet de tête. Les octets de tête sont spécifiés comme une liste d'octets de début et de fin. Dans l'exemple shiftjis, les octets de tête sont compris entre `0x81` et `0x9F` et entre `0xE0` et `0xFC`. Cela signifie que si Tcl rencontre un octet dans ces plages, il suppose qu'il s'agit d'un octet de tête et qu'il doit lire l'octet suivant pour former un caractère complet.

Les fichiers d'encodage de type 'E' sont différents. Ils ne contiennent pas de table de mappage dans le même format. Au lieu de cela, ils contiennent des informations sur les séquences d'échappement qui indiquent comment les octets suivants doivent être interprétés. Ces fichiers sont utilisés pour des encodages plus complexes qui ne peuvent pas être représentés par de simples tables, tels que certains encodages de terminaux ou de protocoles.
