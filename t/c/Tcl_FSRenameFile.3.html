DESCRIPTION

Il y a plusieurs raisons pour lesquelles les fonctions de l'API Tcl_FS (par exemple, Tcl_FSAccess et Tcl_FSStat) sont appelées au lieu d'appeler directement les fonctions de niveau système comme access et stat. Premièrement, ces fonctions sont multiplateformes, donc toute extension utilisant ces fonctions devrait fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation de certaines de ces fonctions sous Windows corrige certains bugs dans les appels de niveau système. Troisièmement, ces appels de fonctions traitent toute conversion de chemin de type « UTF-8 vers plateforme native » qui pourrait être nécessaire (et qui peut mettre en cache les résultats de ces conversions pour une plus grande efficacité lors des appels ultérieurs). Quatrièmement, et probablement le plus important, toutes ces fonctions sont « conscientes des systèmes de fichiers virtuels ». Tout système de fichiers virtuel (VFS) enregistré (via Tcl_FSRegister) peut rediriger l'accès aux fichiers vers des supports ou des méthodes alternatifs. Cela signifie que toutes ces fonctions (et donc les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent fonctionner sur des « fichiers » qui ne sont pas des fichiers natifs sur le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS) via cette API est automatiquement considérée comme « consciente des systèmes de fichiers virtuels ». Évidemment, si une extension accède directement au système de fichiers natif (via des API spécifiques au système, par exemple), Tcl ne peut pas intercepter de tels appels.

Si les systèmes de fichiers virtuels ont été correctement enregistrés, les « fichiers » peuvent être distants (par exemple, situés sur un serveur FTP distant) ou archivés (par exemple, situés dans un fichier ZIP). De tels systèmes enregistrés fournissent une table de fonctions pour implémenter tout ou partie des fonctions mentionnées ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat abstraient le tampon struct stat qui est réellement déclaré, permettant d'utiliser le même code sur des systèmes avec et sans prise en charge de fichiers de plus de 2 Go.

L'API Tcl_FS est basée sur Tcl_Obj et peut mettre en cache des représentations internes et d'autres chaînes liées aux chemins (par exemple, le répertoire courant). Un effet secondaire est qu'il ne faut pas passer à ces fonctions des valeurs dont le compteur de références est nul. Si tel était le cas, il pourrait y avoir des erreurs de mémoire (dans certains cas, le code du système de fichiers pourrait supprimer une référence à la valeur passée et donc ne pas supposer qu'après tout appel à ces fonctions, la valeur a un compteur de références nul - il aurait pu être incrémenté). Ou il pourrait y avoir un échec de segmentation (ou une erreur d'accès mémoire) parce que la valeur est libérée pendant la manipulation complexe de la valeur pour garantir que le chemin est normalisé et absolu pour le système de fichiers. La leçon pratique à retenir est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect et peut causer des erreurs de mémoire. Le path doit voir son compteur de références incrémenté avant d'être passé, ou décrémenté. Pour cette raison, les valeurs dont le compteur de références est nul sont considérées comme invalides comme chemins de système de fichiers et tout appel à une fonction de l'API Tcl_FS avec une telle valeur ne produit aucune action.

FONCTIONS DE L'API Tcl_FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés sont sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction de copie de fichier du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la variable globale errno à EXDEV (ce qui signifie un lien croisé).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés sont sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction de copie de répertoire du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la variable globale errno à EXDEV (ce qui signifie un lien croisé).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction de création de répertoire du système de fichiers qui le possède.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction de suppression de fichier du système de fichiers qui le possède.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction de suppression de répertoire du système de fichiers qui le possède.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés sont sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction de renommage de fichier du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la variable globale errno à EXDEV (ce qui signifie un lien croisé).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction list volumes non nulle et leur demande de renvoyer leur liste de volumes racine. Elle accumule les valeurs renvoyées dans une liste qui est renvoyée à l'appelant (avec un compteur de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant le code d'encodage identifié par encodingName et évalue son contenu comme un script Tcl. Elle renvoie les mêmes informations que Tcl_EvalObjEx. Si encodingName est nul, l'encodage du système est utilisé pour lire le contenu du fichier. Si le fichier ne peut pas être lu, un message d'erreur Tcl est renvoyé pour décrire pourquoi le fichier ne peut pas être lu. Le caractère de fin de fichier pour les fichiers est \x1A (^Z) pour toutes les plateformes. Si vous avez besoin d'un ^Z dans le code de comparaison de chaînes, vous pouvez utiliser \x1A, qui sera probablement remplacé par l'interpréteur Tcl par ^Z. Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours l'encodage du système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier binaire en mémoire et renvoie les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr est appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes virtuels ne l'implémenteront pas en raison des limitations du système sur le chargement dynamique de code binaire), Tcl essaiera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile inverse cette opération, demandant que la bibliothèque indiquée par loadHandle soit déchargée du processus. Notez que, contrairement à la commande unload, cela ne donne aucune chance à la bibliothèque de nettoyage.

Les deux fonctions ci-dessus renvoient un code de complétion standard de Tcl. Si une erreur se produit, un message d'erreur est laissé dans le résultat de l'interp.

Le jeton fourni par la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour trouver tous les fichiers correspondant à un motif donné dans un répertoire. La fonction appropriée pour le système de fichiers auquel appartient pathPtr est appelée.

La valeur renvoyée est un résultat standard de Tcl indiquant si une erreur s'est produite pendant le globbing. Les messages d'erreur sont placés dans l'interp (sauf si l'interp est nul, ce qui est autorisé), mais les bons résultats sont placés dans le resultPtr donné.

Notez que le code de glob implémente les motifs récursifs en interne, donc cette fonction ne recevra que des motifs simples, qui peuvent être mis en correspondance avec la logique de string match. Pour gérer la récursivité, Tcl appellera cette fonction fréquemment en demandant seulement aux répertoires de renvoyer. Un cas spécial d'appel avec un motif nul indique que le chemin doit être vérifié uniquement pour le bon type.

Tcl_FSLink remplace la version de bibliothèque de readlink et l'étend pour prendre en charge la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr est appelée.

Si toPtr est nul, une action « lire le lien » est effectuée. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien ne peut pas être lu. Le résultat appartient à l'appelant, qui doit appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas nul, Tcl doit créer un lien d'un des types passés dans linkAction. Ce drapeau est une combinaison OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'il y a un choix (c'est-à-dire plus d'un drapeau est passé), la convention de Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur renvoyée doit être toPtr (elle appartient donc déjà à l'appelant). En cas d'échec, NULL est renvoyé.

Tcl_FSLstat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Aucun droit de lecture de fichier n'est nécessaire pour obtenir ces informations, mais les droits de lecture de tous les répertoires mentionnés dans le chemin menant au fichier sont nécessaires. La structure Tcl_StatBuf contient des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode des privilèges, le nlink (toujours 1 sous Windows), l'UID (toujours 0 sous Windows), le GID (toujours 0 sous Windows), le rdev (identique au périphérique sous Windows), la taille, le dernier accès.

au moment, heure de dernière modification et heure de dernière modification des métadonnées. Voir PORTABLE STAT RESULT API pour une description sur la façon d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf. Si path existe, Tcl_FSLstat retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné, et aucune information de stat n'est fournie. Tcl_FSUtime remplace la version de la bibliothèque de utime. Ceci retourne 0 en cas de succès et -1 en cas d'erreur (conformément à la documentation de utime). En cas de succès, la fonction mettra à jour les valeurs « atime » et « mtime » du fichier donné. Tcl_FSFileAttrsGet implémente l'accès en lecture pour la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si le résultat est TCL_OK, alors une valeur a été placée dans objPtrRef, qui ne sera valide que temporairement (à moins que Tcl_IncrRefCount ne soit appelée). Tcl_FSFileAttrsSet implémente l'accès en écriture pour la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Tcl_FSFileAttrStrings implémente une partie de la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. La procédure appelée peut soit retourner un tableau de chaînes, soit retourner NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. À la fin de cette utilisation, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer qu'il conserve un compteur de références pour la valeur. Tcl_FSAccess vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet de système de fichiers) dont le nom est pathname. Si pathname est un lien symbolique sur Unix, alors les permissions du fichier auquel ce lien symbolique fait référence sont testées. En cas de succès (toutes les permissions demandées sont accordées), zéro est retourné. En cas d'erreur (au moins un bit dans le mode demandé une permission qui est refusée, ou une autre erreur s'est produite), -1 est retourné. Tcl_FSStat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf comprend des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'identifiant utilisateur (toujours 0 sous Windows), l'identifiant de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification et l'heure de la dernière modification des métadonnées. Voir PORTABLE STAT RESULT API pour une description sur la façon d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf. Si path existe, Tcl_FSStat retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné, et aucune information de stat n'est fournie. Tcl_FSOpenFileChannel ouvre un fichier spécifié par pathPtr et retourne un descripteur de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est basée sur la procédure fopen de la bibliothèque standard d'E/S Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannel retourne NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannel laisse un message d'erreur dans le résultat de interp après toute erreur. Le canal nouvellement créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez Tcl_RegisterChannel. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, la création du nouveau canal l'assigne également comme remplacement du canal standard. Tcl_FSGetCwd remplace la version de la bibliothèque de getcwd. Il retourne le répertoire de travail courant de la bibliothèque Tcl. Cela peut être différent du répertoire de travail du système natif, ce qui se produit lorsque le répertoire de travail courant n'est pas dans le système de fichiers natif. Le résultat est un pointeur vers un Tcl_Obj spécifiant le répertoire courant, ou NULL si le répertoire courant n'a pas pu être déterminé. Si NULL est retourné, un message d'erreur est laissé dans le résultat de interp. Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compteur de références doit être décrémenté. Ceci est nécessaire pour des raisons de sécurité des threads, pour permettre à plusieurs threads d'accéder à cette fonction et aux fonctions associées, tout en garantissant que les résultats sont toujours valides. Tcl_FSChdir remplace la version de la bibliothèque de chdir. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl se rabattra sur une combinaison de stat et access pour vérifier si le répertoire existe et a les permissions appropriées. Pour les résultats, voir la documentation de chdir. En cas de succès, nous conservons un enregistrement du chemin réussi dans cwdPathPtr pour les appels ultérieurs à Tcl_FSGetCwd. Tcl_FSPathSeparator retourne le caractère séparateur à utiliser pour l'élément le plus spécifique du chemin spécifié par pathPtr (c'est-à-dire la dernière partie du chemin). Le séparateur est retourné sous forme de Tcl_Obj contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est retourné. Tcl_FSJoinPath prend le Tcl_Obj donné, qui doit être une liste valide (qui est autorisée à avoir un compteur de références de zéro), et retourne la valeur du chemin donnée en considérant les elements premiers éléments comme des segments de chemin valides (chaque segment de chemin peut être un chemin complet, un chemin partiel ou juste un nom de répertoire ou de fichier unique possible). Si un segment de chemin est en fait un chemin absolu, alors tous les segments de chemin précédents sont rejetés. Si elements est inférieur à 0, nous utilisons toute la liste. Il est possible que la valeur retournée soit en fait un élément de la liste donnée, l'appelant doit donc faire attention à incrémenter le compteur de références du résultat avant de libérer la liste. La valeur retournée, généralement avec un compteur de références de zéro (mais elle peut être partagée dans certaines conditions), contient le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. En particulier, la valeur retournée peut être un élément de la liste donnée, donc la libération de la liste pourrait libérer la valeur prématurément si aucun compteur de références n'a été pris. Si le nombre d'éléments est zéro, alors la valeur retournée sera un Tcl_Obj de chaîne vide. Tcl_FSSplitPath prend le Tcl_Obj donné, qui devrait être un chemin valide, et retourne une valeur de liste Tcl contenant chaque segment de ce chemin comme élément. Il retourne une valeur de liste avec un compteur de références de zéro. Si le lenPtr passé n'est pas NULL, la variable à laquelle il pointe sera mise à jour pour contenir le nombre d'éléments dans la liste retournée. Tcl_FSEqualPaths teste si les deux chemins donnés représentent le même objet de système de fichiers. Il retourne 1 si les chemins sont égaux et 0 s'ils sont différents. Si l'un des chemins est NULL, 0 est toujours retourné. Tcl_FSGetNormalizedPath tente d'extraire du Tcl_Obj donné une représentation de chemin normalisée unique, dont la valeur de chaîne peut être utilisée comme identifiant unique pour le fichier. Il retourne la valeur du chemin normalisé, détenue par Tcl, ou NULL si le chemin était invalide ou ne pouvait pas être converti avec succès. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère en interne sur ces représentations), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques puisse ne pas être la version la plus conviviale d'un chemin. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle de pathPtr passé (sauf si c'est un chemin relatif, auquel cas la valeur du chemin normalisé peut être libérée à tout moment lorsque le cwd change) - l'appelant peut bien sûr incrémenter le compteur de références s'il souhaite conserver une copie plus longtemps. Tcl_FSJoinToPath prend la valeur donnée, qui devrait généralement être un chemin valide ou NULL, et y joint le tableau de segments de chemin donnés. Retourne une valeur, généralement avec un compteur de références de zéro (mais elle peut être partagée dans certaines conditions), contenant le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. Si l'une des valeurs passées à cette fonction (pathPtr ou éléments de path) a un compteur de références de zéro, elles seront libérées lorsque cette fonction retournera. Tcl_FSConvertToPathType essaie de convertir le Tcl_Obj donné en un type de chemin Tcl valide, en tenant compte du fait que le cwd peut avoir changé même si cette valeur est déjà censée être du bon type. Le nom de fichier peut commencer par « ~ » (pour indiquer le répertoire personnel de l'utilisateur courant) ou « ~ » (pour indiquer le répertoire personnel de n'importe quel utilisateur). Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), alors TCL_OK est retourné. Sinon, TCL_ERROR est retourné, et un message d'erreur peut être laissé dans l'interpréteur. Tcl_FSGetInternalRep extrait la représentation interne d'une valeur de chemin donnée, dans le système de fichiers donné. Si la valeur du chemin appartient à un système de fichiers différent, nous retournons NULL. Si la représentation interne est actuellement NULL, nous essayons de la générer, en appelant le Tcl_FSCreateInternalRepProc du système de fichiers. Retourne NULL ou une représentation de chemin interne valide. Cette représentation interne est mise en cache, de sorte que les appels répétés à cette fonction ne nécessiteront pas de conversions supplémentaires. Tcl_FSGetTranslatedPath tente d'extraire le chemin traduit du Tcl_Obj donné. Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), elle est retournée. Sinon, NULL sera retourné, et un message d'erreur peut être laissé dans l'interpréteur. Un chemin « traduit » est un chemin qui ne contient aucune séquence « ~ » ou « ~utilisateur » (celles-ci ont été développées dans leur représentation actuelle dans le système de fichiers). La valeur retournée est détenue par l'appelant, qui doit la stocker ou appeler Tcl_DecrRefCount pour s'assurer que la mémoire est libérée. Cette fonction a peu d'utilité pratique, et Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des usages. Tcl_FSGetTranslatedStringPath fait la même chose que Tcl_FSGetTranslatedPath, mais retourne une chaîne de caractères ou NULL. La chaîne retournée est allouée dynamiquement.

API DU SYSTÈME DE FICHIERS VIRTUEL

Un système de fichiers fournit une Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un système de fichiers ; ces opérations sont appelées au besoin par la couche générique, ce qui se produit généralement via les fonctions listées ci-dessus.

Les Tcl_Filesystem sont manipulés en utilisant les méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et des données optionnelles associées à ce système de fichiers. En appelant cette fonction, Tcl ajoute le système de fichiers à la liste des systèmes de fichiers connus, et il devient immédiatement fonctionnel. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne idée). TCL_OK est retourné.

Tcl_FSUnregister supprime le système de fichiers donné de la liste des systèmes de fichiers connus, s'il est enregistré, et retourne TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est retourné.

Tcl_FSData retourne le clientData associé au système de fichiers donné, s'il est enregistré. Sinon, il retourne NULL.

Tcl_FSMountsChanged est utilisé pour informer le noyau Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations mises en cache des fichiers peuvent maintenant être inaccessibles.

À l'exception des trois premiers champs de cette structure, qui contiennent des éléments simples, tous les autres contiennent des adresses de fonctions appelées par la couche générique du système de fichiers pour effectuer la gamme complète d'actions liées au système de fichiers.

Les fonctions dans cette structure sont divisées en trois catégories : fonctions d'infrastructure (la plupart desquelles doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni), et fonctions d'efficacité (qui ne doivent être implémentées que si cela peut être fait efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl a des émulations moins efficaces qui peuvent s'y rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces solutions de repli ne sont utilisées que pour gérer les commandes initiées en Tcl, pas en C. Cela signifie que si une instruction de renommage de fichier est émise en Tcl, et que les systèmes de fichiers concernés n'implémentent pas leur Tcl_FSRenameFileProc, le noyau Tcl se rabattra sur une combinaison d'autres fonctions du système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a une solution de repli supplémentaire). Cependant, si une instruction Tcl_FSRenameFileProc est émise au niveau C, aucune solution de repli ne se produit. Ceci est vrai sauf pour les quatre derniers éléments du tableau du système de fichiers (lstat, load, getcwd et chdir), pour lesquels les solutions de repli se produisent réellement au niveau C.

Toute fonction qui prend des noms de fichiers sous forme de Tcl_Obj les prend au format UTF-8. L'API d'infrastructure du système de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers des représentations natives.

INFRASTRUCTURE DU SYSTÈME DE FICHIERS

Ces champs contiennent des informations de base sur la structure du système de fichiers et les adresses des fonctions utilisées pour associer un système de fichiers particulier à un chemin de fichier, ainsi que pour gérer les représentations internes des chemins, par exemple pour les copier et les libérer.

TYPENAME

Le champ typeName contient une chaîne terminée par null identifiant le type du système de fichiers implémenté, par exemple « native », « zip » ou « vfs ».

TAILLE STRUCTURE

Le champ structureLength est généralement implémenté comme sizeof(Tcl_Filesystem), et est là pour permettre une compatibilité binaire ascendante plus facile si la taille de la structure change dans une future version de Tcl.

VERSION

Le champ version doit être défini sur TCL_FILESYSTEM_VERSION_1.

PROC_CHEMIN_DANS_SYSTÈME_DE_FICHIERS

Le champ pathInFilesystemProc contient l'adresse d'une fonction qui est appelée pour déterminer si une valeur de chemin donnée appartient ou non à ce système de fichiers. Tcl appellera le reste des fonctions du système de fichiers uniquement avec un chemin pour lequel cette fonction a renvoyé TCL_OK. Si le chemin n'appartient pas, -1 doit être renvoyé (le comportement de Tcl pour toute autre valeur de retour n'est pas défini). Si TCL_OK est renvoyé, alors le paramètre de sortie optionnel clientDataPtr peut être utilisé pour renvoyer une représentation interne (spécifique au système de fichiers) du chemin, qui sera mise en cache dans la valeur du chemin, et pourra être récupérée efficacement par les autres fonctions du système de fichiers. Tcl mettra simultanément en cache le fait que ce chemin appartient à ce système de fichiers. De tels caches sont invalidés lorsque des structures de systèmes de fichiers sont ajoutées ou supprimées de la liste interne de Tcl des systèmes de fichiers connus.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROC_DUPLICATION_REP_INTERNE

Cette fonction crée une copie de la représentation interne d'un chemin, et est appelée lorsque Tcl doit dupliquer une valeur de chemin. Si NULL, Tcl ne copiera tout simplement pas la représentation interne, qui pourra alors devoir être régénérée plus tard.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

PROC_LIBÉRATION_REP_INTERNE

Libère la représentation interne. Ceci doit être implémenté si des représentations internes nécessitent une libération (c'est-à-dire si de la mémoire est allouée lors de la génération d'une représentation interne), mais peut sinon être NULL.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

PROC_INTERNE_VERS_NORMALISÉ

Fonction pour convertir une représentation interne en un chemin normalisé. Seulement requis si le système de fichiers crée des valeurs de chemin pures sans représentation textuelle/de chemin. La valeur de retour est une valeur Tcl dont la représentation textuelle est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

PROC_CRÉATION_REP_INTERNE

Fonction pour prendre une valeur de chemin, calculer une représentation interne pour celle-ci, et stocker cette représentation native dans la valeur. Peut être NULL si les chemins n'ont pas de représentation interne, ou si le Tcl_FSPathInFilesystemProc pour ce système de fichiers crée toujours immédiatement une représentation interne pour les chemins qu'il accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

PROC_NORMALISATION_CHEMIN

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations textuelles pour la même valeur de chemin. Dans Tcl, chaque « chemin » doit avoir une unique représentation textuelle « normalisée ». Selon le système de fichiers, il peut y avoir plus d'une représentation textuelle non normalisée qui fait référence à ce chemin (par exemple, un chemin relatif, un chemin avec une casse de caractères différente si le système de fichiers est insensible à la casse, un chemin contenant une référence à un répertoire personnel tel que « ~ », un chemin contenant des liens symboliques, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être converti en la valeur à laquelle il pointe (mais sa casse ou d'autres aspects doivent être rendus uniques). Tous les autres composants du chemin doivent être convertis à partir de liens symboliques. Cette seule exception est requise pour être conforme aux sémantiques de Tcl avec file delete, file rename, file copy opérant sur des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint soit au début du chemin (c'est-à-dire zéro), soit à la fin du chemin, soit à un séparateur de fichier intermédiaire dans le chemin. Elle ne pointera jamais vers une autre position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS DU SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions qui sont appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui est censé être utilisé avec l'ensemble complet des commandes Tcl standard doit implémenter toutes ces fonctions. Si certaines d'entre elles ne sont pas implémentées, certaines commandes Tcl peuvent échouer lors de l'opération sur les chemins de ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne supporte pas les liens symboliques n'a pas besoin d'implémenter la fonction readlink, etc. Le cœur de Tcl s'attend à ce que les systèmes de fichiers se comportent de cette manière).

PROC_TYPE_CHEMIN_SYSTÈME_DE_FICHIERS

Fonction pour déterminer le type d'un chemin dans ce système de fichiers. Peut être NULL, auquel cas aucune information de type ne sera disponible pour les utilisateurs du système de fichiers. Le « type » est utilisé uniquement à des fins d'information, et doit être renvoyé comme la représentation textuelle de l'objet Tcl renvoyé. Une valeur de retour typique pourrait être « networked », « zip » ou « ftp ». L'objet Tcl résultant appartient au système de fichiers et Tcl incrémentera donc le compteur de références de cette valeur s'il souhaite en conserver une référence.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

PROC_SÉPARATEUR_SYSTÈME_DE_FICHIERS

Fonction pour renvoyer le(s) caractère(s) séparateur(s) pour ce système de fichiers. Ceci n'a besoin d'être implémenté que si le système de fichiers souhaite utiliser un séparateur différent de la chaîne standard « / ». Entre autres utilisations, il est renvoyé par la commande file separator. La valeur de retour doit être une valeur avec un compteur de références de zéro.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

PROC_STAT

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent crucialement (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le Tcl_FSStatProc remplit la structure stat statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure stat inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'identifiant utilisateur (toujours 0 sous Windows), l'identifiant groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le temps du dernier accès, le temps de la dernière modification, et le temps du dernier changement de métadonnées.

Si le fichier représenté par pathPtr existe, le Tcl_FSStatProc renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé, et aucune information de stat n'est fournie.

PROC_ACCÈS

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent crucialement (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

Le Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est dans pathPtr. Si le nom de chemin fait référence à un lien symbolique, alors les permissions du fichier auquel ce lien symbolique fait référence doivent être testées.

En cas de succès (toutes les permissions demandées accordées), zéro est renvoyé. En cas d'erreur (au moins un bit dans mode demandait une permission refusée, ou une autre erreur s'est produite), -1 est renvoyé.

OPENFILECHANNELPROC

Fonction pour traiter un appel Tcl_FSOpenFileChannel. Doit être implémentée pour tout système de fichiers raisonnable, car toutes les opérations qui nécessitent l'ouverture ou l'accès au contenu d'un fichier l'utiliseront (par exemple, open, encoding et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

Le Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et retourne un descripteur de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est calquée sur la procédure fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier, où l'argument mode est une combinaison des drapeaux POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannelProc retourne NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le nouveau canal créé ne doit pas être enregistré dans l'interpréteur fourni par un Tcl_FSOpenFileChannelProc ; cette tâche incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr était précédemment fermé, la création du nouveau canal l'assigne également en remplacement du canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, les fonctionnalités de glob et de copie récursive manqueront dans le système de fichiers (et cela peut avoir un impact sur des commandes comme encoding names qui utilisent en interne la fonctionnalité de glob).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit retourner tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au motif donné et respectent la spécification types fournie. Il y a deux façons dont cette fonction peut être appelée. Si pattern est NULL, alors pathPtr est une spécification de chemin complet d'un seul fichier ou répertoire qui doit être vérifié pour son existence et son type correct. Sinon, pathPtr est un répertoire, dont le contenu doit être recherché par la fonction pour trouver des fichiers ou des répertoires du type correct. Dans les deux cas, on peut supposer que pathPtr n'est ni NULL ni vide. Il n'est pas actuellement documenté si pathPtr aura un séparateur de fichier à sa fin ou non, donc le code doit être flexible aux deux possibilités.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le processus de correspondance. Les messages d'erreur sont placés dans interp, sauf si interp est NULL, auquel cas aucun message d'erreur ne doit être généré ; en cas de résultat TCL_OK, les résultats doivent être ajoutés à la valeur donnée de resultPtr (qui peut être supposée être une liste Tcl valide non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (cela signifie généralement qu'elles seront des spécifications de chemin absolu). Notez que si aucune correspondance n'est trouvée, cela conduit simplement à un résultat vide ; les erreurs ne sont signalées que pour les problèmes réels de fichier ou de système de fichiers qui peuvent survenir pendant le processus de correspondance.

La structure Tcl_GlobTypeData passée dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Type Mac acceptable */
    Tcl_Obj *macType;
    /* Créateur Mac acceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de gérer correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT sont vrais (et en particulier lorsque les autres drapeaux sont faux). Dans le premier de ces cas, la fonction doit lister les répertoires contenus. Tcl utilise cela pour implémenter le globbing récursif, il est donc crucial que les systèmes de fichiers implémentent correctement la correspondance des répertoires. Dans le second de ces cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage qui se trouvent dans le pathPtr donné (et dans ce cas, pathPtr n'a pas besoin de se trouver dans le même système de fichiers - différent de tous les autres cas où cette fonction est appelée). Le support pour cela est crucial si Tcl veut avoir des transitions transparentes d'un système de fichiers à un autre.

UTIMEPROC

Fonction pour traiter un appel Tcl_FSUtime. Nécessaire pour permettre la définition (pas la lecture) des temps avec file mtime, file atime et l'implémentation open-r/open-w/fcopy de file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les temps d'accès et de modification du fichier spécifié par pathPtr doivent être modifiés aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec l'appel système utime.

LINKPROC

Fonction pour traiter un appel Tcl_FSLink. Ne doit être implémentée que si le système de fichiers prend en charge les liens, et peut sinon être NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est invitée à lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat est détenu par l'appelant (et doit donc voir son compteur de références incrémenté avant d'être retourné). Tous les appelants doivent appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'est plus nécessaire. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Le résultat dans ce cas doit être toPtr si le lien a réussi et NULL sinon. Dans ce cas, le résultat n'est pas détenu par l'appelant (c'est-à-dire qu'aucune manipulation de compteur de références des deux côtés n'est nécessaire). Voir la documentation de Tcl_FSLink pour l'interprétation correcte des drapeaux linkAction.

LISTVOLUMESPROC

Fonction pour lister tous les volumes de systèmes de fichiers ajoutés par ce système de fichiers. Ne doit être implémentée que si le système de fichiers ajoute des volumes en tête de la hiérarchie des systèmes de fichiers, afin qu'ils puissent être retournés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste des volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. La valeur du résultat est considérée comme détenue par le système de fichiers (pas par le cœur de Tcl), mais doit se voir attribuer un compteur de références pour Tcl. Tcl utilisera le contenu de la liste puis décrémentera ce compteur de références. Cela permet aux systèmes de fichiers de choisir s'ils souhaitent réellement conserver une liste « globale » de volumes ou non (sinon, ils génèrent la liste à la volée et la passent à Tcl avec un compteur de références de 1, puis oublient la liste ; si oui, alors ils incrémentent simplement le compteur de références de leur liste globale et la passent à Tcl qui copiera le contenu, puis décrémentera le compte jusqu'à son état précédent).

Par conséquent, Tcl considère les valeurs de retour de ce proc comme étant en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne supportera pas la commande file attributes. Cela permet d'attacher des informations supplémentaires arbitraires aux fichiers dans le système de fichiers. Si elle n'est pas implémentée, il n'est pas nécessaire d'implémenter les méthodes get et set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La fonction appelée peut soit retourner un tableau de chaînes, soit retourner NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. À la fin de cette utilisation, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle devrait avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer de retourner une valeur avec un compteur de références d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel Tcl_FSFileAttrsGet, utilisé par file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Retourne un code de retour Tcl standard. La valeur d'attribut récupérée, qui correspond à l'élément d'index index dans la liste retournée par Tcl_FSFileAttrStringsProc, est un Tcl_Obj placé dans objPtrRef (si TCL_OK a été retourné) et aura probablement un compteur de références de zéro. Dans tous les cas, nous devons soit le stocker quelque part (par exemple, le résultat Tcl), soit incrémenter/décrémenter son compteur de références pour s'assurer qu'il est correctement libéré.

FILEATTRSSETPROC

Fonction pour traiter un appel Tcl_FSFileAttrsSet, utilisé par file attributes. Si le système de fichiers est en lecture seule, il n'est pas nécessaire de l'implémenter.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

La valeur d'attribut de l'élément d'index index dans la liste retournée par Tcl_FSFileAttrStringsProc doit être définie sur le objPtr donné.

CREATEDIRECTORYPROC

EFFICACITÉ DU SYSTÈME DE FICHIERS

Ces fonctions n'ont pas besoin d'être implémentées pour un système de fichiers particulier car le cœur dispose d'une implémentation de secours disponible. Voir la description individuelle de chacune pour les conséquences de laisser le champ à NULL.

LSTATPROC

Fonction pour traiter un appel Tcl_FSLstat. Si elle n'est pas implémentée, Tcl tentera d'utiliser la procédure statProc définie ci-dessus à la place. Par conséquent, elle ne doit être implémentée que si un système de fichiers peut différencier les appels stat et lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le comportement de cette fonction est très similaire à celui de Tcl_FSStatProc défini ci-dessus, sauf que si elle est appliquée à un lien symbolique, elle renvoie des informations sur le lien, et non sur le fichier cible.

COPYFILEPROC

Fonction pour traiter un appel Tcl_FSCopyFile. Si elle n'est pas implémentée, Tcl utilisera open-r, open-w et fcopy comme mécanisme de copie. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de copie. Notez que destPathPtr est le nom du fichier qui doit devenir la copie de srcPathPtr. Ce n'est jamais le nom d'un répertoire dans lequel srcPathPtr pourrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande file copy au niveau Tcl). Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non copyDirectoryProc lorsqu'il est nécessaire de les copier (même s'il s'agit de liens symboliques vers des répertoires). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file copy, l'appel à Tcl_SetErrno(EXDEV) et le renvoi d'un résultat non-TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

RENAMEFILEPROC

Fonction pour traiter un appel Tcl_FSRenameFile. Si elle n'est pas implémentée, Tcl utilisera un mécanisme de copie et de suppression. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de renommage. Si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file rename, l'appel à Tcl_SetErrno(EXDEV) et le renvoi d'un résultat non-TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

COPYDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSCopyDirectory. Si elle n'est pas implémentée, Tcl utilisera un mécanisme récursif de file mkdir et file copy. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de copie. Si une erreur se produit, le nom du fichier ou du répertoire qui a causé l'erreur doit être placé dans errorPtr. Notez que destPathPtr est le nom du répertoire qui doit devenir le miroir de srcPathPtr. Ce n'est pas le nom d'un répertoire dans lequel srcPathPtr devrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande file copy au niveau Tcl). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de copie de répertoire, l'appel à Tcl_SetErrno(EXDEV) et le renvoi d'un résultat non-TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

LOADFILEPROC

Fonction pour traiter un appel Tcl_FSLoadFile. Si elle n'est pas implémentée, Tcl utilisera une copie vers un fichier temporaire natif suivie d'un Tcl_FSLoadFile sur cette copie temporaire. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut charger du code directement, ou si elle peut être implémentée simplement pour renvoyer TCL_ERROR afin de désactiver complètement la fonctionnalité de chargement dans ce système de fichiers.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Renvoie un code d'achèvement Tcl standard. En cas d'erreur, un message d'erreur est laissé dans le résultat de l'interp. La fonction charge dynamiquement un fichier de code binaire en mémoire. En cas de chargement réussi, handlePtr doit être rempli avec un jeton pour le fichier chargé dynamiquement, et unloadProcPtr doit être rempli avec l'adresse d'une procédure. La procédure de déchargement sera appelée avec Tcl_LoadHandle donné comme seul paramètre lorsque Tcl aura besoin de décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle renvoyé est actuellement un jeton qui peut être utilisé dans le TclpFindSymbol privé pour accéder aux fonctions du nouveau code. Chaque système de fichiers est libre de définir le Tcl_LoadHandle comme il l'entend. Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de chargement de fichier, l'appel à Tcl_SetErrno(EXDEV) et le renvoi d'un résultat non-TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

UNLOADFILEPROC

Fonction pour décharger un fichier précédemment chargé avec succès. Si le chargement a été implémenté, alors celui-ci doit également l'être, s'il y a une action de nettoyage requise.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Fonction pour traiter un appel Tcl_FSGetCwd. La plupart des systèmes de fichiers n'ont pas besoin de l'implémenter. Elle ne sera généralement appelée qu'une seule fois, si getcwd est appelé avant chdir. Peut être NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si le système de fichiers prend en charge une notion native d'un répertoire de travail actuel (qui pourrait peut-être changer indépendamment de Tcl), cette fonction doit renvoyer ce répertoire de travail comme résultat, ou NULL si le répertoire actuel n'a pas pu être déterminé (par exemple, l'utilisateur n'a pas les permissions appropriées sur le répertoire actuel). Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de l'interp.

CHDIRPROC

Fonction pour traiter un appel Tcl_FSChdir. Si les systèmes de fichiers n'implémentent pas cela, cela sera émulé par une série de vérifications d'accès aux répertoires. Sinon, les systèmes de fichiers virtuels qui l'implémentent n'ont qu'à répondre avec un résultat positif si pathPtr est un répertoire valide et accessible dans leur système de fichiers. Ils n'ont pas besoin de mémoriser le résultat, car celui-ci sera automatiquement mémorisé pour être utilisé par Tcl_FSGetCwd. Les systèmes de fichiers réels doivent effectuer l'action correcte (c'est-à-dire appeler l'API système chdir correcte).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

Le Tcl_FSChdirProc change le répertoire de travail actuel de l'application pour la valeur spécifiée dans pathPtr. La fonction renvoie -1 en cas d'erreur ou 0 en cas de succès.
