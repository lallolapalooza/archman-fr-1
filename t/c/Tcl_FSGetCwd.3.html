DESCRIPTION

Il y a plusieurs raisons pour lesquelles les fonctions de l'API Tcl_FS (par exemple, Tcl_FSAccess et Tcl_FSStat) sont appelées au lieu d'appeler directement des fonctions système telles que access et stat. Premièrement, ces fonctions sont multiplateformes, donc toute extension qui les appelle doit fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige des bogues dans les appels système. Troisièmement, ces appels de fonction gèrent toute conversion de chemin d'accès de type "Utf vers natif" qui pourrait être nécessaire (et peuvent mettre en cache les résultats de telles conversions pour une meilleure efficacité lors d'appels ultérieurs). Quatrièmement, et probablement le plus important, toutes ces fonctions sont "conscientes des systèmes de fichiers virtuels" (VFS abrégé). Tout VFS (VFS abrégé) enregistré (via Tcl_FSRegister) peut réorienter l'accès aux fichiers vers des supports ou des méthodes alternatives. Cela signifie que toutes ces fonctions (et donc les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent fonctionner sur des "fichiers" qui ne sont pas des fichiers natifs sur le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS abrégé) via cette API est considérée comme "consciente des systèmes de fichiers virtuels". Évidemment, si une extension accède directement au système de fichiers natif (via des API spécifiques au système, par exemple), Tcl ne peut pas intercepter de tels appels.

Si des VFS ont été correctement enregistrés, les "fichiers" peuvent, par exemple, être distants (comme s'ils étaient situés sur un serveur ftp distant) ou archivés (comme s'ils étaient situés dans un fichier .zip). Ces systèmes de fichiers enregistrés fournissent une table de fonctions pour implémenter tout ou partie des fonctions mentionnées ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat font abstraction de ce qui est réellement déclaré comme le tampon struct stat, permettant ainsi au même code d'être utilisé sur des systèmes avec ou sans prise en charge des fichiers de plus de 2 Go.

L'API Tcl_FS est encapsulée dans Tcl_Obj et peut mettre en cache les représentations internes et autres chaînes de caractères liées aux chemins d'accès (par exemple, le répertoire courant). Un effet secondaire de ceci est qu'il ne faut pas passer de valeurs avec un compteur de références nul à ces fonctions. Si de tels appels étaient gérés, ils pourraient provoquer des erreurs de mémoire (dans certains cas, le code du système de fichiers pourrait décrémenter une référence à la valeur passée et donc ne pas supposer qu'après un appel à ces fonctions, la valeur ait toujours un compteur de références nul - il pourrait avoir été incrémenté). Ou ils pourraient également provoquer une erreur de segmentation (ou une autre erreur d'accès mémoire) car la valeur aurait été libérée pendant le processus complexe de manipulation des valeurs pour garantir que le chemin est normalisé et absolu pour le système de fichiers. La leçon pratique à retenir est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect et peut provoquer des erreurs de mémoire. Le path doit voir son compteur de références incrémenté avant d'être passé, ou décrémenté. Pour cette raison, les valeurs avec un compteur de références nul sont considérées comme invalides en tant que chemins de système de fichiers et tout appel à une fonction API Tcl_FS avec de telles valeurs n'entraînera aucune action.

FONCTIONS DE L'API FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés sont sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction "copie de fichier" du système de fichiers est appelée. Sinon, elle renvoie -1 et définit la variable globale errno à EXDEV (qui indique un lien croisé).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés sont sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction "copie de répertoire" du système de fichiers est appelée. Sinon, elle renvoie -1 et définit la variable globale errno à EXDEV (qui indique un lien croisé).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction "création de répertoire" du système de fichiers propriétaire.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction "suppression de fichier" du système de fichiers.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction "suppression de répertoire" du système de fichiers.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés sont sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction "renommer fichier" du système de fichiers est appelée. Sinon, elle renvoie -1 et définit la variable globale errno à EXDEV (qui indique un lien croisé).

Tcl_FSListVolumes appelle chaque système de fichiers ayant une fonction "lister volumes" non nulle et leur demande de renvoyer leur liste de volumes racines. Elle agrège les valeurs renvoyées dans une liste qui est renvoyée à l'appelant (avec un compteur de références nul).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant le schéma de codage identifié par encodingName et évalue son contenu comme un script Tcl. Elle renvoie les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, le schéma de codage du système est utilisé pour lire le contenu du fichier. Si le fichier ne peut pas être lu, une erreur Tcl est renvoyée pour décrire pourquoi le fichier ne peut pas être lu. Le caractère EOF pour les fichiers est \x1A (^Z) pour tous les systèmes. Si vous voulez utiliser ^Z dans du code pour des comparaisons de chaînes, vous pouvez utiliser \x1A, qui sera probablement substitué par l'interpréteur Tcl par ^Z. Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx, qui utilise toujours le schéma de codage du système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier binaire en mémoire et renvoie les adresses de deux procédures dans le fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr est appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas, en raison des limitations du système sur le chargement de code binaire), Tcl tentera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile annule cette opération, demandant au processus de supprimer la bibliothèque indiquée par loadHandle de l'exécution. Notez que, contrairement à la commande unload, cette opération ne donne aucune opportunité à la bibliothèque de faire du nettoyage.

les deux fonctions ci-dessus renvoient un code d'achèvement standard Tcl. En cas d'erreur, un message d'erreur est laissé dans le résultat de interp.

Le jeton fourni par la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher tous les fichiers qui correspondent à un modèle donné dans un répertoire. La fonction appropriée pour le système de fichiers auquel appartient pathPtr est appelée.

La valeur renvoyée est un code de résultat standard Tcl indiquant si une erreur s'est produite pendant le globbing. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Note : le code de glob implémente les motifs récursifs en interne, cette fonction ne recevra donc que des motifs simples, qui peuvent être mis en correspondance en utilisant la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment en demandant uniquement des répertoires à renvoyer. Un cas spécial d'appel avec un modèle nul indique que le chemin doit être vérifié uniquement pour le bon type.

Tcl_FSLink remplace la version linguistique de lecture de readlink et étend sa fonctionnalité pour la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr est appelée.

Si toPtr est NULL, une action de "lecture de lien" est effectuée. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien ne peut pas être lu. Le résultat est entièrement la propriété de l'appelant, qui doit appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl doit créer un lien d'un des types passés dans linkAction. Ce drapeau est une combinaison OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'il y a un choix (c'est-à-dire que plus d'un drapeau est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur renvoyée doit être toPtr (qui appartient déjà à l'appelant). S'il ne peut pas être créé, NULL est renvoyé.

Tcl_FSLstat remplit la structure Tcl_StatBuf avec des informations sur le fichier spécifié par statPtr. Aucun droit d'accès au fichier n'est requis pour obtenir ces informations, mais le droit de lecture est requis pour tous les répertoires mentionnés dans le chemin menant au fichier. La structure Tcl_StatBuf contient des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), le rdev (identique au périphérique sous Windows), la taille, la date du dernier accès.

t, dernière heure de modification et dernière heure de changement de métadonnées. Voir PORTABLE STAT RESULT API pour une description de la manière d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSLstat renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé et aucune information stat n'est fournie.

Tcl_FSUtime remplace la version bibliothèque de utime.

Renvoie 0 en cas de succès et -1 en cas d'erreur (conformément à la documentation de utime). En cas de succès, la fonction mettra à jour les valeurs "atime" et "mtime" du fichier donné.

Tcl_FSFileAttrsGet implémente l'accès en lecture pour la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

Si le résultat est TCL_OK, une valeur a été placée dans objPtrRef, qui ne sera valable que temporairement (sauf si Tcl_IncrRefCount est appelée).

Tcl_FSFileAttrsSet implémente l'accès en écriture pour la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

Tcl_FSFileAttrStrings implémente une partie de la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La procédure appelée peut soit renvoyer un tableau de chaînes, soit renvoyer NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer qu'il conserve un compteur de références de la valeur.

Tcl_FSAccess vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est pathname. Si pathname est un lien symbolique sous Unix, les autorisations du fichier référencé par ce lien symbolique sont testées.

En cas de succès (toutes les autorisations demandées sont accordées), zéro est renvoyé. En cas d'erreur (au moins un bit dans le mode demandé pour une autorisation refusée, ou une autre erreur s'est produite), -1 est renvoyé.

Tcl_FSStat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (nlink) (toujours 1 sous Windows), l'identifiant utilisateur (uid) (toujours 0 sous Windows), l'identifiant groupe (gid) (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification et l'heure du dernier changement de métadonnées. Voir PORTABLE STAT RESULT API pour une description de la manière d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSStat renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé et aucune information stat n'est fournie.

Tcl_FSOpenFileChannel ouvre un fichier spécifié par pathPtr et renvoie un handle de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est basée sur la procédure fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles de la commande Tcl open lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannel renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannel laisse un message d'erreur dans le résultat de interp après toute erreur.

Le canal nouvellement créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez Tcl_RegisterChannel. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, l'acte de création du nouveau canal l'assigne également comme remplacement du canal standard.

Tcl_FSGetCwd remplace la version bibliothèque de getcwd.

Renvoie le répertoire de travail actuel de la bibliothèque Tcl. Cela peut être différent du répertoire de travail de la plateforme native, ce qui se produit lorsque le répertoire de travail actuel n'est pas dans le système de fichiers natif.

Le résultat est un pointeur vers un Tcl_Obj spécifiant le répertoire courant, ou NULL si le répertoire courant n'a pas pu être déterminé. Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de interp.

Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compteur de références doit être décrémenté. Ceci est nécessaire pour des raisons de sécurité des threads, afin de permettre à plusieurs threads d'accéder à cette fonction et aux fonctions associées, tout en garantissant que les résultats sont toujours valides.

Tcl_FSChdir remplace la version bibliothèque de chdir. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl se rabattra sur une combinaison de stat et access pour vérifier si le répertoire existe et a les autorisations appropriées.

Pour les résultats, voir la documentation de chdir. En cas de succès, nous conservons un enregistrement du chemin réussi dans cwdPathPtr pour les appels ultérieurs à Tcl_FSGetCwd.

Le séparateur est renvoyé sous forme de Tcl_Obj contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est renvoyé.

La valeur renvoyée, généralement avec un compteur de références de zéro (mais elle peut être partagée dans certaines conditions), contient le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. En particulier, la valeur renvoyée peut être un élément de la liste donnée, donc libérer la liste pourrait libérer la valeur prématurément si aucun compteur de références n'a été pris. LA API DU SYSTÈME DE FICHIERS VIRTUEL

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un système de fichiers ; ces opérations sont invoquées au besoin par la couche générale, généralement par le biais des fonctions mentionnées ci-dessus.

Les structures Tcl_Filesystem sont manipulées par les méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et des données optionnelles associées à cette structure. En appelant cette fonction, Tcl ajoute la structure du système de fichiers à la liste des systèmes de fichiers connus, et elle devient immédiatement fonctionnelle. Tcl ne vérifie pas si la même structure de système de fichiers est enregistrée plusieurs fois (et en général, ce n'est pas une bonne pratique). TCL_OK est retourné.

Tcl_FSUnregister retire la structure donnée de la liste des systèmes de fichiers connus, si elle est connue, et retourne TCL_OK. Si la structure n'est pas actuellement enregistrée, TCL_ERROR est retourné.

Tcl_FSData retourne le clientData associé à la structure de système de fichiers donnée, si cette structure est enregistrée. Sinon, il retourne NULL.

Tcl_FSMountsChanged informe le noyau de Tcl que les points de montage pour le système de fichiers donné (déjà enregistré) ont changé, et que les représentations mises en cache des fichiers peuvent alors ne plus être correctes.

Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun recours de ce type ne se produit. Ceci est vrai sauf pour les quatre derniers enregistrements de la table du système de fichiers (lstat, load, getcwd et chdir), pour lesquels des recours se produisent réellement au niveau C.

PROCÉDURE DE CHEMIN DANS LE SYSTÈME DE FICHIERS

Le champ pathInFilesystemProc contient l'adresse d'une fonction qui est appelée pour déterminer si une valeur de chemin donnée appartient à ce système de fichiers ou non. Si le chemin n'appartient pas, -1 sera renvoyé (le comportement de Tcl pour toute autre valeur de retour n'est pas défini). Si TCL_OK est renvoyé, le paramètre de sortie clientDataPtr peut être utilisé pour renvoyer une représentation interne (spécifique au système de fichiers) du chemin, qui sera mise en cache dans la valeur du chemin et peut être récupérée efficacement par d'autres procédures du système de fichiers. Tcl mettra également en cache le fait que ce chemin appartient à ce système de fichiers. De tels caches sont invalidés lorsque les structures de système de fichiers sont ajoutées ou supprimées de la liste interne des systèmes de fichiers connus de Tcl.

        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROCÉDURE DE NORMALISATION DE CHEMIN

Fonction pour normaliser un chemin. Elle doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations de chaîne pour le même chemin. Dans Tcl, chaque chemin doit avoir une représentation normalisée unique. Selon le système de fichiers, il peut y avoir plus d'une représentation de chaîne non normalisée qui se réfère au même chemin (par exemple, un chemin relatif, un chemin avec une casse de caractères différente si le système de fichiers est insensible à la casse, un chemin contenant une référence à un répertoire personnel comme ~, un chemin contenant des liens symboliques, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être développé en la valeur vers laquelle il pointe, mais sa casse ou d'autres aspects doivent être uniques. Tous les autres composants du chemin doivent être développés à partir des liens symboliques. Cette exception est requise pour s'aligner sur le comportement de Tcl pour les opérations sur les liens symboliques de file delete, file rename, file copy. Cette fonction peut être appelée avec nextCheckpoint au début du chemin (c'est-à-dire 0), à la fin du chemin, ou à tout séparateur de fichier intermédiaire dans le chemin. Elle ne sera pas appelée pour une position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémenteur peut supposer que le chemin jusqu'au séparateur inclus est connu et normalisé.

        int nextCheckpoint);

Les champs de cette section de la structure contiennent des adresses de fonctions qui sont utilisées pour effectuer les opérations de base du système de fichiers. Fonction pour traiter un appel Tcl_FSStat. Elle doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent de manière cruciale (par exemple, file atime, file isdirectory, file size, glob).

Le Tcl_FSStatProc remplit la structure de statistiques statPtr avec des informations sur le fichier spécifié. Fonction pour traiter un appel Tcl_FSAccess. Elle doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent de manière cruciale (par exemple, file exists, file readable).

        Tcl_Obj *pathPtr,

Le Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est dans pathPtr. En cas de succès (toutes les autorisations demandées sont accordées), 0 est renvoyé. En cas d'erreur (au moins un bit dans le mode demandé indique une autorisation refusée, ou une autre erreur s'est produite), -1 est renvoyé.

Fonction pour traiter un appel à Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, le fonctionnement du glob et de la copie récursive sera manquant dans le système de fichiers (et cela peut affecter des commandes comme encoding names qui utilisent la fonctionnalité de glob).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit renvoyer tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au modèle donné et qui correspondent à la spécification types. Il existe deux façons dont cette fonction peut être appelée. Si pattern est NULL, pathPtr est une spécification complète d'un seul fichier ou répertoire qui doit être vérifiée en termes d'existence et de type. Sinon, pathPtr est un répertoire, et la fonction doit rechercher des fichiers ou des répertoires dont le type est correct. Dans tous les cas, pathPtr peut être supposé non nul et non vide. Il n'est pas documenté si pathPtr aura un séparateur de fichier à la fin, donc le code doit être flexible pour les deux cas.

La valeur de retour est un résultat standard de Tcl indiquant si une erreur s'est produite pendant le processus de correspondance. Les messages d'erreur sont placés dans interp, sauf si interp est NULL, auquel cas aucun message d'erreur n'est généré ; en cas de résultat TCL_OK, les résultats doivent être ajoutés à la valeur donnée dans resultPtr (qui peut être supposée être une liste Tcl non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (cela signifie généralement qu'il s'agira de spécifications de chemin absolu). Note : s'il n'y a pas de correspondances, cela conduit simplement à un résultat vide ; seules les erreurs réelles de fichier ou de système de fichiers qui peuvent survenir pendant le processus de correspondance sont signalées.

La structure Tcl_GlobTypeData passée dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Types mac acceptés */
    Tcl_Obj *macType;
    /* Créateurs mac acceptés */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de gérer correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types est TRUE et que TCL_GLOB_TYPE_DIR ou TCL_GLOB_TYPE_MOUNT est TRUE (et en particulier lorsque d'autres indicateurs sont faux). Dans le premier cas, la fonction doit énumérer les répertoires conteneurs. Tcl l'utilise pour implémenter le globbing récursif, il est donc essentiel que les systèmes de fichiers implémentent correctement la correspondance des répertoires. Dans le second cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit énumérer les points de montage qui se trouvent dans le répertoire donné par pathPtr (et dans ce cas, pathPtr n'a pas besoin d'être dans le même système de fichiers - contrairement aux autres cas où cette fonction est appelée). Le support de cela est essentiel si Tcl veut avoir des transitions fluides entre les systèmes de fichiers.

UTIMEPROC

Fonction pour traiter un appel à Tcl_FSUtime. Elle est requise pour permettre la définition (pas la lecture) des temps de modification et d'accès des fichiers, ainsi que pour l'implémentation de l'opération de copie de fichiers (open-r/open-w/fcopy).

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les temps d'accès et de modification des fichiers spécifiés par pathPtr doivent être modifiés aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec le système utime.

LINKPROC

Fonction pour traiter un appel à Tcl_FSLink. Elle doit être implémentée uniquement si le système de fichiers prend en charge les liens, sinon elle peut être NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est invitée à lire le contenu d'un lien. Le résultat est un Tcl_Obj qui spécifie le contenu du lien donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant (et doit donc incrémenter son compteur de références avant d'être renvoyé). Tout appelant doit appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'en a plus besoin. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Le résultat dans ce cas doit être toPtr si le lien a réussi et NULL dans le cas contraire. Dans ce cas, le résultat n'appartient pas à l'appelant (c'est-à-dire qu'aucune manipulation de compteur de références ne sera effectuée des deux côtés). Voir la documentation de Tcl_FSLink pour l'interprétation correcte des indicateurs linkAction.

LISTVOLUMESPROC

Fonction pour lister les volumes de système de fichiers ajoutés par ce système de fichiers. Elle doit être implémentée uniquement si le système de fichiers ajoute des volumes en tête du système de fichiers, afin qu'ils puissent être renvoyés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste de volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. La valeur du résultat est considérée comme appartenant au système de fichiers (pas au noyau Tcl), mais elle doit être dotée d'un compteur de références pour Tcl. Tcl utilisera le contenu de la liste, puis décrémentera ce compteur de références. Cela permet aux systèmes de fichiers de choisir s'ils veulent réellement conserver une "liste globale" de volumes ou non (sinon, ils génèrent la liste à la volée et la passent à Tcl avec un compteur de références de 1, puis oublient la liste ; si oui, alors ils incrémentent simplement le compteur de références de leur liste globale et la passent à Tcl qui copie les contenus, puis décrémente le compteur de références d'où elle a commencé).

Par conséquent, Tcl considère les valeurs de retour de cette proc comme étant en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne prendra pas en charge la commande file attributes. Cela permet d'ajouter des informations arbitraires aux fichiers du système de fichiers. Si elle n'est pas implémentée, il n'est pas nécessaire d'implémenter les méthodes get et set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La fonction peut renvoyer un tableau de chaînes de caractères ou, à la place, renvoyer NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être détruite par Tcl lorsqu'elle est terminée, elle doit avoir un compteur de références de zéro, et si elle ne doit pas être détruite, le système de fichiers doit s'assurer qu'il renvoie une valeur avec un compteur de références d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsGet, utilisé par la commande file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Renvoie un code de retour standard. La valeur de l'index donné dans la liste renvoyée par Tcl_FSFileAttrStringsProc est un Tcl_Obj placé dans objPtrRef (si TCL_OK a été renvoyé) et aura probablement un compteur de références de zéro. Dans tous les cas, nous devons stocker cette valeur (par exemple, dans le résultat de Tcl) ou incrémenter/décrémenter son compteur de références pour nous assurer qu'elle sera correctement libérée.

FILEATTRSSETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsSet, utilisé par la commande file attributes. Si le système de fichiers est en lecture seule, il n'est pas nécessaire de l'implémenter.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

La valeur de l'index donné dans la liste renvoyée par Tcl_FSFileAttrStringsProc doit être définie sur objPtr donné.

CREATEDIRECTORYPROC

Fonction pour créer des répertoires dans le système de fichiers. Elle doit être implémentée si le système de fichiers prend en charge les répertoires, sinon elle peut être NULL.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode);

Cette fonction crée un répertoire dans le système de fichiers spécifié par pathPtr avec le mode donné.

ATEDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSCreateDirectory. Doit être implémentée sauf si le FS est en lecture seule.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du traitement. En cas de succès, un nouveau répertoire aurait dû être ajouté au système de fichiers à l'emplacement spécifié par pathPtr.

REMOVEDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSRemoveDirectory. Doit être implémentée sauf si le FS est en lecture seule.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du traitement. En cas de succès, le répertoire spécifié par pathPtr aurait dû être supprimé du système de fichiers. Si le drapeau recursive est donné, alors un répertoire non vide doit être supprimé sans erreur. Si ce drapeau n'est pas donné et que le répertoire est non vide, une erreur POSIX «EEXIST» doit être signalée. Si une erreur se produit, le nom du fichier ou du répertoire qui a causé l'erreur doit être placé dans errorPtr.

DELETEFILEPROC

Fonction pour traiter un appel Tcl_FSDeleteFile. Doit être implémentée sauf si le FS est en lecture seule.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du traitement. En cas de succès, le fichier spécifié par pathPtr aurait dû être supprimé du système de fichiers. Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non Tcl_FSRemoveDirectoryProc lorsqu'il est nécessaire de les supprimer (même s'il s'agit de liens symboliques vers des répertoires).

EFFICACITÉ DU SYSTÈME DE FICHIERS

Ces fonctions n'ont pas besoin d'être implémentées pour un système de fichiers particulier, car le noyau dispose d'une implémentation de secours disponible. Voir chaque description individuelle pour les conséquences de laisser le champ NULL.

LSTATPROC

Fonction pour traiter un appel Tcl_FSLstat. Si elle n'est pas implémentée, Tcl tentera d'utiliser la procédure statProc définie ci-dessus à la place. Par conséquent, elle n'a besoin d'être implémentée que si un système de fichiers peut différencier les appels stat et lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le comportement de cette fonction est très similaire à celui de Tcl_FSStatProc défini ci-dessus, sauf que si elle est appliquée à un lien symbolique, elle renvoie des informations sur le lien, et non sur le fichier cible.

COPYFILEPROC

Fonction pour traiter un appel Tcl_FSCopyFile. Si elle n'est pas implémentée, Tcl utilisera open-r, open-w et fcopy comme mécanisme de copie. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du processus de copie. Notez que destPathPtr est le nom du fichier qui deviendra la copie de srcPathPtr. Ce n'est jamais le nom d'un répertoire dans lequel srcPathPtr pourrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande de niveau Tcl file copy). Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non copyDirectoryProc lorsqu'il est nécessaire de les copier (même s'il s'agit de liens symboliques vers des répertoires). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file copy, appeler Tcl_SetErrno(EXDEV) et renvoyer un résultat non-TCL_OK indiquera à Tcl d'utiliser ses mécanismes de secours standard.

RENAMEFILEPROC

Fonction pour traiter un appel Tcl_FSRenameFile. Si elle n'est pas implémentée, Tcl utilisera un mécanisme de copie et suppression. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du processus de renommage. Si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file rename, appeler Tcl_SetErrno(EXDEV) et renvoyer un résultat non-TCL_OK indiquera à Tcl d'utiliser ses mécanismes de secours standard.

COPYDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSCopyDirectory. Si elle n'est pas implémentée, Tcl utilisera un mécanisme récursif de file mkdir, file copy. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du processus de copie. Si une erreur se produit, le nom du fichier ou du répertoire qui a causé l'erreur doit être placé dans errorPtr. Notez que destPathPtr est le nom du répertoire qui devrait devenir l'image miroir de srcPathPtr. Ce n'est pas le nom d'un répertoire dans lequel srcPathPtr devrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande de niveau Tcl file copy). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de copie de répertoire, appeler Tcl_SetErrno(EXDEV) et renvoyer un résultat non-TCL_OK indiquera à Tcl d'utiliser ses mécanismes de secours standard.

LOADFILEPROC

Fonction pour traiter un appel Tcl_FSLoadFile. Si elle n'est pas implémentée, Tcl utilisera une copie vers un fichier temporaire natif suivie d'un appel Tcl_FSLoadFile sur cette copie temporaire. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut charger du code directement, ou elle peut être implémentée simplement pour retourner TCL_ERROR afin de désactiver complètement la fonctionnalité de chargement dans ce système de fichiers.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Renvoie un code de complétion Tcl standard. Si une erreur se produit, un message d'erreur est laissé dans le résultat de l'interp. La fonction charge dynamiquement un fichier de code binaire en mémoire. En cas de chargement réussi, handlePtr doit être rempli avec un jeton pour le fichier chargé dynamiquement, et unloadProcPtr doit être rempli avec l'adresse d'une procédure. La procédure de déchargement sera appelée avec le Tcl_LoadHandle donné comme seul paramètre lorsque Tcl aura besoin de décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle renvoyé est actuellement un jeton qui peut être utilisé dans la fonction privée TclpFindSymbol pour accéder aux fonctions du nouveau code. Chaque système de fichiers est libre de définir Tcl_LoadHandle comme il le souhaite. Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de chargement de fichier, appeler Tcl_SetErrno(EXDEV) et renvoyer un résultat non-TCL_OK indiquera à Tcl d'utiliser ses mécanismes de secours standard.

UNLOADFILEPROC

Fonction pour décharger un fichier précédemment chargé avec succès. Si le chargement a été implémenté, alors cela devrait également être implémenté, s'il y a une action de nettoyage requise.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Fonction pour traiter un appel Tcl_FSGetCwd. La plupart des systèmes de fichiers n'ont pas besoin de l'implémenter. Elle sera généralement appelée une seule fois, si getcwd est appelé avant chdir. Peut être NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si le système de fichiers prend en charge une notion native de répertoire de travail actuel (qui pourrait éventuellement changer indépendamment de Tcl), cette fonction devrait renvoyer ce répertoire comme résultat, ou NULL si le répertoire actuel n'a pas pu être déterminé (par exemple, l'utilisateur n'a pas les autorisations appropriées sur le répertoire actuel). Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de l'interp.

CHDIRPROC

Fonction pour traiter un appel Tcl_FSChdir. Si les systèmes de fichiers ne l'implémentent pas, elle sera émulée par une série de vérifications d'accès aux répertoires. Sinon, les systèmes de fichiers virtuels qui l'implémentent doivent seulement répondre par un résultat positif si pathPtr est un répertoire valide et accessible dans leur système de fichiers. Ils n'ont pas besoin de mémoriser le résultat, car celui-ci sera automatiquement mémorisé pour être utilisé par Tcl_FSGetCwd. Les systèmes de fichiers réels doivent effectuer l'action correcte (c'est-à-dire appeler la bonne API système chdir).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

La Tcl_FSChdirProc change le répertoire de travail actuel de l'application vers la valeur spécifiée dans pathPtr. La fonction renvoie -1 en cas d'erreur ou 0 en cas de succès.
