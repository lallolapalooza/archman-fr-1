DESCRIPTION

Tcl utilise une architecture de canaux à deux couches. Elle fournit une couche supérieure générique pour permettre aux programmes C et Tcl d'effectuer des entrées et sorties en utilisant les mêmes API pour une variété de fichiers, de périphériques, de sockets, etc. Les API C génériques sont décrites dans la page de manuel de Tcl_OpenFileChannel.

La couche inférieure fournit des pilotes de canaux spécifiques au type pour chaque type de périphérique supporté sur chaque plateforme. Cette page de manuel décrit les API C utilisées pour communiquer entre la couche générique et les pilotes de canaux spécifiques au type. Elle explique également comment de nouveaux types de canaux peuvent être ajoutés en fournissant de nouveaux pilotes de canaux.

Les pilotes de canaux se composent d'un certain nombre de composants : Premièrement, chaque pilote de canal fournit une structure Tcl_ChannelType contenant des pointeurs vers des fonctions implémentant les diverses opérations utilisées par la couche générique pour communiquer avec le pilote de canal. La structure Tcl_ChannelType et les fonctions référencées par celle-ci sont décrites dans la section TCL_CHANNELTYPE, ci-dessous.

Deuxièmement, les pilotes de canaux fournissent généralement une commande Tcl pour créer des instances de ce type de canal. Par exemple, la commande Tcl open crée des canaux qui utilisent les pilotes de canaux de fichiers et de commandes, et la commande Tcl socket crée des canaux qui utilisent des sockets TCP pour la communication réseau.

Troisièmement, un pilote de canal fournit éventuellement une fonction C pour ouvrir des instances de canal de ce type. Par exemple, Tcl_OpenFileChannel ouvre un canal qui utilise le pilote de canal de fichier, et Tcl_OpenTcpClient ouvre un canal qui utilise le protocole réseau TCP. Ces fonctions de création utilisent généralement Tcl_CreateChannel en interne pour ouvrir le canal.

Pour ajouter un nouveau type de canal, vous devez implémenter une API C ou une commande Tcl qui ouvre un canal en appelant Tcl_CreateChannel. Lorsque votre pilote appelle Tcl_CreateChannel, il lui passe une structure Tcl_ChannelType décrivant les procédures d'E/S du pilote. La couche générique invoquera alors les fonctions référencées dans cette structure pour effectuer des opérations sur le canal.

Tcl_CreateChannel ouvre un nouveau canal et y associe les informations typePtr et instanceData fournies. Le canal est ouvert dans le mode indiqué par mask. Pour une discussion sur les pilotes de canaux, leurs opérations et la structure Tcl_ChannelType, voir la section TCL_CHANNELTYPE, ci-dessous.

Tcl_CreateChannel interagit avec le code gérant les canaux standard. Une fois qu'un canal standard a été initialisé soit par un appel à Tcl_GetStdChannel, soit par un appel à Tcl_SetStdChannel, la fermeture de ce canal standard entraînera la prochaine invocation de Tcl_CreateChannel pour faire également du nouveau canal le nouveau canal standard. Voir Tcl_StandardChannels pour un traité général sur les canaux standard et le comportement de la bibliothèque Tcl à leur égard.

Tcl_GetChannelInstanceData renvoie les données d'instance associées au canal dans channel. Ceci est identique à l'argument instanceData dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelType renvoie un pointeur vers la structure Tcl_ChannelType utilisée par le canal dans l'argument channel. Ceci est identique à l'argument typePtr dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelName renvoie une chaîne contenant le nom associé au canal, ou NULL si l'argument channelName de Tcl_CreateChannel était NULL.

Tcl_GetChannelHandle place la poignée de périphérique spécifique au système d'exploitation associée à channel pour la direction donnée dans

TCL_CHANNELTYPE

Un pilote de canal fournit une structure Tcl_ChannelType qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un canal ; ces opérations sont invoquées selon les besoins par la couche générique. La structure a été versionnée à partir de Tcl 8.3.2/8.4 pour corriger un problème dans les pilotes de canaux bloquants. Consultez la section OLD CHANNEL TYPES pour plus de détails sur l'ancienne structure.

La structure Tcl_ChannelType contient les champs suivants :

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Il n'est pas nécessaire de fournir des implémentations pour toutes les opérations de canal. Celles qui ne sont pas nécessaires peuvent être définies sur NULL dans la structure : blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc, et close2Proc, en plus de flushProc, handlerProc, threadActionProc, et truncateProc. Les fonctions qui ne peuvent pas être implémentées de manière significative doivent renvoyer EINVAL lorsqu'elles sont appelées, indiquant que les opérations représentées ne sont pas disponibles. Il convient également de noter que wideSeekProc peut être NULL si seekProc l'est.

L'utilisateur doit utiliser la structure ci-dessus uniquement pour l'instanciation de Tcl_ChannelType. Lors de la référence aux champs d'une structure Tcl_ChannelType, les fonctions suivantes doivent être utilisées pour obtenir les valeurs : Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc, ou Tcl_ChannelHandlerProc.

Le changement dans les structures a été effectué de manière à ce que les types de canaux standard soient binaires compatibles. Cependant, les types de canaux utilisant des canaux bloquants (c'est-à-dire TLS, Trf) ont de nouvelles versions pour correspondre au changement ci-dessus, car le code précédent pour les canaux bloquants présentait des problèmes.

TYPENAME

Le champ typeName contient une chaîne terminée par NULL qui identifie le type de périphérique implémenté par ce pilote, par exemple, file ou socket.

Cette valeur peut être obtenue avec Tcl_ChannelName, qui renvoie un pointeur vers la chaîne.

VERSION

Le champ version doit être défini sur la version de la structure requise. TCL_CHANNEL_VERSION_2 est le minimum recommandé. TCL_CHANNEL_VERSION_3 doit être défini pour spécifier le membre wideSeekProc. TCL_CHANNEL_VERSION_4 doit être défini pour spécifier le membre threadActionProc (inclut wideSeekProc). TCL_CHANNEL_VERSION_5 doit être défini pour spécifier les membres truncateProc (inclut wideSeekProc et threadActionProc). S'il n'est pas défini sur l'une de ces valeurs, il est supposé que le Tcl_ChannelType a la structure d'origine. Consultez OLD CHANNEL TYPES pour plus de détails. Bien que Tcl reconnaisse et fonctionne avec l'une de ces structures, les canaux bloquants doivent être au moins TCL_CHANNEL_VERSION_2 pour fonctionner correctement.

Cette valeur peut être obtenue avec Tcl_ChannelVersion, qui renvoie l'une des valeurs TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 ou TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

Le champ blockModeProc contient l'adresse d'une fonction appelée par la couche générique pour définir le mode bloquant et non bloquant du périphérique. BlockModeProc doit correspondre au prototype suivant :

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

instanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument mode est soit TCL_MODE_BLOCKING, soit TCL_MODE_NONBLOCKING pour définir le périphérique en mode bloquant ou non bloquant. La fonction doit renvoyer zéro si l'opération a réussi, ou un code d'erreur POSIX non nul si l'opération a échoué.

Si l'opération réussit, la fonction peut modifier le instanceData fourni pour enregistrer que le canal est passé en mode bloquant ou non bloquant et implémenter le comportement bloquant ou non bloquant. Pour certains types de périphériques, le comportement bloquant et non bloquant peut être implémenté par le système d'exploitation sous-jacent ; pour d'autres types de périphériques, le comportement doit être émulé dans le pilote de canal.

Cette valeur peut être obtenue avec Tcl_ChannelBlockModeProc, qui renvoie un pointeur vers la fonction.

Un pilote de canal qui ne fournit pas de blockModeProc doit être très prudent. Il doit indiquer à la couche générique quel mode bloquant est acceptable pour lui, et il doit documenter cela pour l'utilisateur de manière à ce que le mode bloquant du canal ne soit pas modifié à une valeur inacceptable. Toute confusion à cet égard pourrait entraîner un blocage (factice et difficile à trouver) de l'interpréteur.

CLOSEPROC ET CLOSE2PROC

Le champ closeProc contient l'adresse d'une fonction appelée par la couche générique pour nettoyer les informations relatives au pilote lorsque le canal est fermé. CloseProc doit correspondre au prototype suivant :

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

L'argument instanceData est la même valeur que celle fournie à Tcl_CreateChannel lors de la création du canal. La fonction doit libérer toute mémoire allouée par le pilote de canal pour ce canal, et fermer les périphériques d'entrée et de sortie encapsulés par ce canal. Avant d'appeler cette fonction, toute sortie mise en mémoire tampon aura été vidée vers le périphérique. Aucune autre opération du pilote ne sera appelée après l'appel à closeProc. Si l'opération de fermeture réussit, la procédure

Mantén toda la estructura del archivo.

INPUTPROC

Le champ inputProc contient l'adresse d'une fonction appelée par la couche générale pour lire des données d'un fichier ou d'un périphérique et les stocker dans un tampon interne. InputProc doit correspondre au prototype suivant :

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

InstanceData est la même que la valeur passée à Tcl_CreateChannel lors de la création du canal. L'argument buf pointe vers un tableau d'octets dans lequel l'entrée du périphérique sera stockée, et l'argument bufSize indique combien d'octets sont disponibles dans buf.

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générale. Si une erreur se produit, la fonction doit définir cette valeur sur un code d'erreur POSIX qui identifie l'erreur.

La fonction doit lire les données du périphérique encapsulé par le canal et les stocker dans buf. En cas de succès, la fonction doit retourner un nombre non négatif indiquant combien d'octets ont été lus du périphérique et stockés dans buf. En cas d'erreur, la fonction doit retourner -1. Si une erreur se produit après que certains octets aient été lus du périphérique, ces données sont perdues.

Si inputProc peut déterminer que le périphérique a des données disponibles mais moins que ce qui est demandé par l'argument bufSize, la fonction doit essayer de lire uniquement ce qui est disponible et retourner sans bloquer. Si le périphérique n'a pas de données disponibles et que le canal est en mode non bloquant, la fonction doit retourner une erreur EAGAIN. Si le périphérique n'a pas de données disponibles et que le canal est en mode bloquant, la fonction doit bloquer jusqu'à ce qu'au moins un octet puisse être lu du périphérique, puis retourner les données qui peuvent être lues sans bloquer.

Cette valeur peut être obtenue avec Tcl_ChannelInputProc, qui retourne un pointeur vers la fonction.

OUTPUTPROC

Le champ outputProc contient l'adresse d'une fonction appelée par la couche générale pour transférer des données d'un tampon interne vers le périphérique de sortie. OutputProc doit correspondre au prototype suivant :

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData est la même que la valeur passée à Tcl_CreateChannel lors de la création du canal. L'argument buf contient un tableau d'octets à écrire dans le périphérique, et l'argument toWrite indique combien d'octets seront écrits à partir de l'argument buf.

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générale. Si une erreur se produit, la fonction doit définir cette valeur sur un code d'erreur POSIX qui identifie l'erreur.

La fonction doit écrire les données dans buf dans le périphérique de sortie encapsulé par le canal. En cas de succès, la fonction doit retourner un nombre non négatif indiquant combien d'octets ont été écrits dans le périphérique de sortie. La valeur de retour est généralement la même que toWrite, mais peut être inférieure dans certains cas, par exemple si l'opération de sortie est interrompue par un signal. En cas d'erreur, la fonction doit retourner -1. En cas d'erreur, certaines données peuvent avoir été écrites dans le périphérique.

Si le canal est en mode non bloquant et que le périphérique de sortie ne peut absorber aucune donnée, la fonction doit retourner -1 avec une erreur EAGAIN sans écrire aucune donnée.

Cette valeur peut être obtenue avec Tcl_ChannelOutputProc, qui retourne un pointeur vers la fonction.

SEEKPROC AND WIDESEEKPROC

Le champ seekProc contient l'adresse d'une fonction appelée par la couche générale pour déplacer le point d'accès auquel les opérations d'entrée ou de sortie ultérieures seront appliquées. SeekProc doit correspondre au prototype suivant :

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

L'argument instanceData est le même que la valeur donnée à Tcl_CreateChannel lors de la création de ce canal. Offset et seekMode ont la même signification que dans la procédure Tcl_Seek (décrite dans le manuel de Tcl_OpenFileChannel).

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générale pour retourner les valeurs errno de la fonction. La fonction doit définir cette valeur sur un code d'erreur POSIX si une erreur se produit. La fonction doit stocker un code EINVAL dans cet argument si le type de canal n'implémente pas la possibilité de rechercher.

La valeur de retour est le nouveau point d'accès ou -1 en cas d'erreur. En cas d'erreur, la fonction ne doit pas déplacer le point d'accès.

S'il existe un champ non nul de seekProc, le champ wideSeekProc peut contenir l'adresse d'une fonction alternative qui gère les décalages de déplacement (c'est-à-dire, supérieurs à 32 bits), permettant de rechercher dans des fichiers de plus de 2 Go. La fonction wideSeekProc sera appelée de préférence à seekProc, mais les deux doivent être définis si wideSeekProc est défini. WideSeekProc doit correspondre au prototype suivant :

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

Les arguments et les valeurs de retour ont la même signification qu'avec seekProc, sauf que le type de décalage et le type de retour sont différents.

Le champ seekProc peut être obtenu avec Tcl_ChannelSeekProc, qui retourne un pointeur vers la fonction, et de manière similaire, le champ wideSeekProc peut être obtenu avec Tcl_ChannelWideSeekProc.

SETOPTIONPROC

Le champ setOptionProc contient l'adresse d'une fonction appelée par la couche générale pour définir une option spécifique au type de canal sur un canal. setOptionProc doit correspondre au prototype suivant :

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

optionName est le nom d'une option qui peut être définie, et newValue est la nouvelle valeur de cette option, sous forme de chaîne. instanceData est la même que la valeur donnée à Tcl_CreateChannel lors de la création de ce canal. La fonction doit effectuer l'action spécifique au type de canal pour implémenter la nouvelle valeur de l'option.

Certaines options sont gérées par le code général et cette fonction n'est jamais appelée pour les définir, par exemple, -blockmode. D'autres options sont spécifiques à chaque type de canal et la fonction setOptionProc du pilote du canal est appelée pour les implémenter. Le champ setOptionProc peut être nul, indiquant que ce type de canal ne prend pas en charge les options spécifiques au type.

Si la valeur de l'option est correctement modifiée à sa nouvelle valeur, la fonction retourne TCL_OK. Elle doit appeler Tcl_BadChannelOption, qui retourne TCL_ERROR si optionName n'est pas reconnu. Si newValue spécifie une valeur non prise en charge ou si une erreur se produit lors d'un appel système, la fonction doit laisser un message d'erreur dans le résultat de interp si interp n'est pas nul. La fonction doit également appeler Tcl_SetErrno pour stocker un code d'erreur POSIX approprié.

Cette valeur peut être obtenue avec Tcl_ChannelSetOptionProc, qui retourne un pointeur vers la fonction.

GETOPTIONPROC

Le champ getOptionProc contient l'adresse d'une fonction appelée par la couche générale pour obtenir la valeur d'une option spécifique au type de canal sur un canal. getOptionProc doit correspondre au prototype suivant :

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        Tcl_DString *optionValue);

OptionName est le nom d'une option prise en charge par ce type de canal. Si le nom de l'option n'est pas nul, la fonction stocke sa valeur actuelle, sous forme de chaîne, dans le string Tcl dynamique optionValue. Si optionName est nul, la fonction stocke dans optionValue une liste alternée de toutes les options prises en charge et de leurs valeurs actuelles. En cas de succès, la fonction retourne TCL_OK. Elle doit appeler Tcl_BadChannelOption, qui retourne TCL_ERROR si optionName n'est pas reconnu. Si newValue spécifie une valeur non prise en charge ou si une erreur se produit lors d'un appel système, la fonction doit laisser un message d'erreur dans le résultat de interp si interp n'est pas nul. La fonction doit également appeler Tcl_SetErrno pour stocker un code d'erreur POSIX approprié.

Cette valeur peut être obtenue avec Tcl_ChannelGetOptionProc, qui retourne un pointeur vers la fonction.

* Name est non reconnu. Si une erreur d'appel système se produit, la fonction doit laisser un message d'erreur dans le résultat de interp si interp n'est pas NULL. La fonction doit également appeler Tcl_SetErrno pour stocker un code d'erreur POSIX approprié.

Certaines options sont gérées par le code générique et cette fonction n'est jamais appelée pour récupérer leur valeur, par exemple -blockmode. D'autres options sont spécifiques à chaque type de canal et la procédure getOptionProc du pilote de canal sera appelée pour les implémenter. Le champ getOptionProc peut être NULL, ce qui indique que ce type de canal ne prend en charge aucune option spécifique au type.

Cette valeur peut être récupérée avec Tcl_ChannelGetOptionProc, qui renvoie un pointeur vers la fonction.

WATCHPROC

Le champ watchProc contient l'adresse d'une fonction appelée par la couche générique pour initialiser le mécanisme de notification d'événements afin de détecter les événements d'intérêt sur ce canal. WatchProc doit correspondre au prototype suivant :

typedef void Tcl_DriverWatchProc(
        ClientData instanceData,
        int mask);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument mask est une combinaison OR de TCL_READABLE, TCL_WRITABLE et TCL_EXCEPTION ; il indique les événements que l'appelant souhaite surveiller sur ce canal.

La fonction doit initialiser des mécanismes spécifiques au type de périphérique pour détecter quand un événement d'intérêt est présent sur le canal. Lorsqu'un ou plusieurs des événements désignés se produisent sur le canal, le pilote de canal est responsable de l'appel de Tcl_NotifyChannel pour informer le module de canal générique. Le pilote doit veiller à ne pas affamer d'autres pilotes de canal ou sources de rappels en appelant Tcl_NotifyChannel trop fréquemment. L'équité peut être assurée en utilisant la file d'attente d'événements de Tcl pour permettre à l'événement du canal d'être planifié séquentiellement avec d'autres événements. Voir la description de Tcl_QueueEvent pour plus de détails sur la façon de mettre un événement en file d'attente.

Cette valeur peut être récupérée avec Tcl_ChannelWatchProc, qui renvoie un pointeur vers la fonction.

GETHANDLEPROC

Le champ getHandleProc contient l'adresse d'une fonction appelée par la couche générique pour récupérer un descripteur spécifique au périphérique à partir du canal. GetHandleProc doit correspondre au prototype suivant :

typedef int Tcl_DriverGetHandleProc(
        ClientData instanceData,
        int direction,
        ClientData *handlePtr);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument direction est soit TCL_READABLE pour récupérer le descripteur utilisé pour l'entrée, soit TCL_WRITABLE pour récupérer le descripteur utilisé pour la sortie.

Si l'implémentation du canal a des descripteurs spécifiques au périphérique, la fonction doit récupérer le descripteur approprié associé au canal, selon l'argument direction. Le descripteur doit être stocké à l'emplacement référencé par handlePtr, et TCL_OK doit être renvoyé. Si le canal n'est pas ouvert pour la direction spécifiée, ou si l'implémentation du canal n'utilise pas de descripteurs de périphérique, la fonction doit renvoyer TCL_ERROR.

Cette valeur peut être récupérée avec Tcl_ChannelGetHandleProc, qui renvoie un pointeur vers la fonction.

FLUSHPROC

Le champ flushProc est actuellement réservé pour une utilisation future. Il doit être défini à NULL. FlushProc doit correspondre au prototype suivant :

typedef int Tcl_DriverFlushProc(
        ClientData instanceData);

Cette valeur peut être récupérée avec Tcl_ChannelFlushProc, qui renvoie un pointeur vers la fonction.

HANDLERPROC

Le champ handlerProc contient l'adresse d'une fonction appelée par la couche générique pour notifier le canal qu'un événement s'est produit. Il doit être défini pour les pilotes de canal empilés qui souhaitent être notifiés des événements qui se produisent sur le canal sous-jacent (empilé). HandlerProc doit correspondre au prototype suivant :

typedef int Tcl_DriverHandlerProc(
        ClientData instanceData,
        int interestMask);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. Le interestMask est une combinaison OR de TCL_READABLE ou TCL_WRITABLE ; il indique quel type d'événement s'est produit sur ce canal.

Cette valeur peut être récupérée avec Tcl_ChannelHandlerProc, qui renvoie un pointeur vers la fonction.

THREADACTIONPROC

Le champ threadActionProc contient l'adresse de la fonction appelée par la couche générique lorsqu'un canal est créé, fermé ou qu'il va être déplacé vers un thread différent, c'est-à-dire chaque fois que l'état du pilote spécifique au thread pourrait devoir être initialisé ou mis à jour. Il peut être NULL. L'action TCL_CHANNEL_THREAD_REMOVE est utilisée pour notifier au pilote qu'il doit mettre à jour ou supprimer toute donnée spécifique au thread qu'il pourrait maintenir pour le canal.

L'action TCL_CHANNEL_THREAD_INSERT est utilisée pour notifier au pilote qu'il doit mettre à jour ou initialiser toute donnée spécifique au thread qu'il pourrait maintenir en utilisant le thread appelant comme associé. Voir Tcl_CutChannel et Tcl_SpliceChannel pour plus de détails.

typedef void Tcl_DriverThreadActionProc(
        ClientData instanceData,
        int action);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal.

Ces valeurs peuvent être récupérées avec Tcl_ChannelThreadActionProc, qui renvoie un pointeur vers la fonction.

TRUNCATEPROC

Le champ truncateProc contient l'adresse de la fonction appelée par la couche générique lorsqu'un canal est tronqué à une certaine longueur. Il peut être NULL.

typedef int Tcl_DriverTruncateProc(
        ClientData instanceData,
        Tcl_WideInt length);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal, et length est la nouvelle longueur du fichier sous-jacent, qui ne doit pas être négative. Le résultat doit être 0 en cas de succès ou un code errno (adapté à une utilisation avec Tcl_SetErrno) en cas d'échec.

Ces valeurs peuvent être récupérées avec Tcl_ChannelTruncateProc, qui renvoie un pointeur vers la fonction.

TCL_BADCHANNELOPTION

Cette procédure génère un message d'erreur “mauvaise option” dans un interpréteur (optionnel). Elle est utilisée par les pilotes de canal lorsqu'une option Set/Get invalide est demandée. Son but est de concaténer la liste des options génériques aux options spécifiques et de factoriser la chaîne de message d'erreur des options génériques.

Elle renvoie toujours TCL_ERROR

Un message d'erreur est généré dans la valeur de résultat d'interp pour indiquer qu'une commande a été invoquée avec une mauvaise option. Le message a la forme

    mauvaise option "blah" : devrait être l'une de
    <...options génériques...>+<...options spécifiques...>
vous obtenez par exemple : 
    mauvaise option "-blah" : devrait être l'une de -blocking,
    -buffering, -buffersize, -eofchar, -translation,
    -peername, ou -sockname
lorsque l'appel est effectué avec optionList égal à “peername sockname”

“blah” est l'argument optionName et “<options spécifiques>” est une liste d'options spécifiques séparées par des espaces. La fonction prend soin d'insérer des signes moins avant chaque option, des virgules après, et un “ou” avant la dernière option.

TYPES DE CANAUX OBSOLÈTES

La structure Tcl_ChannelType originale (version 8.3.1 et antérieures) contient les champs suivants :

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
} Tcl_ChannelType;

Il est toujours possible de créer des canaux avec la structure ci-dessus. Le code interne des canaux déterminera la version. Il est impératif d'utiliser la nouvelle structure Tcl_ChannelType si vous créez un pilote de canal empilé, en raison de problèmes avec l'implémentation précédente des canaux empilés (dans les versions 8.2.0 à 8.3.1).

Avant la version 8.4.0 (c'est-à-dire lors des dernières versions de 8.3 et la première partie du cycle de développement de 8.4), la structure Tcl_ChannelType contenait les champs suivants :

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_ChannelTypeVersion version;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Lorsque la structure ci-dessus est enregistrée en tant que type de canal, le champ version doit toujours être TCL_CHANNEL_VERSION_2.
