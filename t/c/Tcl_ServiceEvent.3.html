INTRODUCTION

Les interfaces décrites ici sont utilisées pour personnaliser la boucle d'événements Tcl. Les deux personnalisations les plus courantes sont l'ajout de nouvelles sources d'événements et la fusion de la boucle d'événements Tcl avec une autre boucle d'événements, comme celle fournie par une application dans laquelle Tcl est intégré. Chacune de ces tâches est décrite dans une section distincte ci-dessous.

Les procédures de cette entrée de manuel sont les éléments de base sur lesquels le gestionnaire d'événements Tcl est construit. Le gestionnaire d'événements est la couche la plus basse du mécanisme d'événements Tcl. Il se compose de trois éléments :

[1]
Sources d'événements : celles-ci représentent les moyens par lesquels les événements peuvent être générés. Par exemple, il existe une source d'événements de temporisation qui implémente la procédure Tcl_CreateTimerHandler et la commande after, et il existe une source d'événements de fichiers qui implémente la procédure Tcl_CreateFileHandler sur les systèmes Unix. Une source d'événements doit fonctionner avec le gestionnaire d'événements pour détecter les événements aux moments opportuns, les enregistrer dans la file d'attente d'événements et notifier ultérieurement le logiciel de niveau supérieur qu'ils se sont produits. Les procédures Tcl_CreateEventSource, Tcl_DeleteEventSource, et Tcl_SetMaxBlockTime, Tcl_QueueEvent, et Tcl_DeleteEvents sont principalement utilisées par les sources d'événements.
[2]
La file d'attente d'événements : pour les applications non multithread, il existe une seule file d'attente pour l'ensemble de l'application, contenant les événements qui ont été détectés mais pas encore traités. Les sources d'événements placent les événements dans la file d'attente afin qu'ils puissent être traités dans l'ordre à des moments appropriés pendant la boucle d'événements. La file d'attente d'événements garantit une discipline équitable de traitement des événements, de sorte qu'aucune source d'événements ne puisse affamer les autres. Elle permet également de sauvegarder les événements pour un traitement ultérieur. Les applications multithread fonctionnent de manière similaire, à l'exception du fait qu'il existe une file d'attente d'événements distincte pour chaque fil d'exécution contenant un interpréteur Tcl. Tcl_QueueEvent est utilisée (principalement par les sources d'événements) pour ajouter des événements à la file d'attente d'événements et Tcl_DeleteEvents est utilisée pour supprimer des événements de la file d'attente sans les traiter. Dans une application multithread, Tcl_QueueEvent ajoute un événement à la file d'attente du fil d'exécution courant, et Tcl_ThreadQueueEvent ajoute un événement à la file d'attente d'un fil d'exécution spécifique.
[3]
La boucle d'événements : afin de détecter et de traiter les événements, l'application entre dans une boucle qui attend que les événements se produisent, les place dans la file d'attente d'événements, puis les traite. La plupart des applications le font en appelant la procédure Tcl_DoOneEvent, qui est décrite dans une entrée de manuel séparée.

La plupart des applications Tcl n'ont pas besoin de se soucier des détails internes du gestionnaire d'événements Tcl. Cependant, le gestionnaire d'événements est maintenant suffisamment flexible pour être redirigé soit vers une nouvelle plateforme, soit pour utiliser une boucle d'événements externe (telle que la boucle d'événements Motif, lorsque Tcl est intégré dans une application Motif). Les procédures Tcl_WaitForEvent et Tcl_SetTimer sont normalement implémentées par Tcl, mais peuvent être remplacées par de nouvelles versions pour rediriger le gestionnaire d'événements (les procédures Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler, et Tcl_DeleteFileHandler doivent également être remplacées ; voir CRÉATION D'UN NOUVEAU GESTIONNAIRE D'ÉVÉNEMENTS ci-dessous pour plus de détails). Les procédures Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode, et Tcl_SetServiceMode sont fournies pour aider à connecter la boucle d'événements Tcl à une boucle d'événements externe telle que celle de Motif.

BASES DU GESTIONNAIRE D'ÉVÉNEMENTS

Le moyen le plus simple de comprendre le fonctionnement du gestionnaire d'événements est d'examiner ce qui se passe lorsque Tcl_DoOneEvent est appelé. Tcl_DoOneEvent reçoit un argument flags qui indique quels types d'événements peuvent être traités et s'il faut bloquer ou non s'il n'y a pas d'événements prêts. Tcl_DoOneEvent effectue les opérations suivantes :

[1]
Vérifie la file d'attente d'événements pour voir si elle contient des événements pouvant être traités. Si c'est le cas, traite le premier événement possible, le retire de la file d'attente et retourne. Pour ce faire, elle appelle Tcl_ServiceEvent et lui passe l'argument flags.
[2]
Prépare le blocage pour un événement. Pour ce faire, Tcl_DoOneEvent invoque une procédure setup dans chaque source d'événements. La source d'événements effectuera l'initialisation spécifique à la source d'événements et appellera éventuellement Tcl_SetMaxBlockTime pour limiter la durée pendant laquelle Tcl_WaitForEvent bloquera si aucun nouvel événement ne se produit.
[3]
Appelle Tcl_WaitForEvent. Cette procédure est implémentée différemment selon les plateformes ; elle attend qu'un événement se produise, en se basant sur les informations fournies par les sources d'événements. Elle peut provoquer le blocage de l'application si timePtr spécifie un intervalle différent de 0. Tcl_WaitForEvent retourne lorsque quelque chose s'est produit, comme un fichier devenu lisible ou l'expiration de l'intervalle donné par timePtr. S'il n'y a aucun événement pour Tcl_WaitForEvent à attendre, de sorte qu'elle bloquerait indéfiniment, alors elle retourne immédiatement et Tcl_DoOneEvent retourne 0.
[4]
Appelle une procédure check dans chaque source d'événements. La procédure check détermine si des événements intéressants pour cette source se sont produits. Si c'est le cas, les événements sont ajoutés à la file d'attente d'événements.

CRÉATION D'UNE NOUVELLE SOURCE D'ÉVÉNEMENTS

Une source d'événements se compose de trois procédures qui sont appelées par le multiplexeur, plus des procédures C supplémentaires qui sont appelées par le code de niveau supérieur pour organiser les rappels d'événements orientés événement. Les trois procédures appelées par le multiplexeur consistent en les procédures de configuration et de vérification décrites ci-dessus, plus une procédure supplémentaire qui est appelée lorsqu'un événement est retiré de la file d'attente des événements pour être traité.

La procédure Tcl_CreateEventSource crée une nouvelle source d'événements. Ses arguments spécifient la procédure de configuration et la procédure de vérification pour la source d'événements. SetupProc doit correspondre au prototype suivant :

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

L'argument clientData sera le même que l'argument clientData de Tcl_CreateEventSource ; il est généralement utilisé pour pointer vers des informations privées gérées par la source d'événements. L'argument flags sera le même que l'argument flags passé à Tcl_DoOneEvent, sauf s'il est 0 (auquel cas TCL_ALL_EVENTS est retourné). Flags indique quels types d'événements doivent être pris en compte ; si le bit correspondant à cette source d'événements n'est pas défini, la source d'événements devrait retourner immédiatement sans rien faire. Par exemple, la source d'événements de fichiers vérifie le bit TCL_FILE_EVENTS.

Le SetupProc a pour but de s'assurer que l'application se réveille lorsque des événements du type souhaité se produisent. Ceci est généralement fait d'une manière dépendante de la plateforme. Par exemple, sous Unix, une source d'événements pourrait appeler Tcl_CreateFileHandler ; sous Windows, elle pourrait demander une notification avec un événement Windows. Pour les sources d'événements contrôlées par des minuteries, telles que les événements temporels ou tout événement interrogé, la source d'événements peut appeler Tcl_SetMaxBlockTime pour forcer l'application à se réveiller après un temps spécifié, même s'il n'y a pas d'événements. Si aucune source d'événements n'appelle Tcl_SetMaxBlockTime, Tcl_WaitForEvent attendra suffisamment longtemps pour qu'un événement se produise ; sinon, il n'attendra que la durée de l'intervalle le plus court spécifié par l'une des sources d'événements. Si une source d'événements sait qu'elle a déjà des événements prêts à signaler, elle peut demander un temps d'attente maximal nul. Par exemple, la procédure de configuration de la source d'événements X vérifie s'il y a déjà des événements en file d'attente. S'il y en a, elle appelle Tcl_SetMaxBlockTime avec un temps d'attente maximal nul afin que Tcl_WaitForEvent ne se bloque pas s'il n'y a pas de nouvelles données sur la connexion X. L'argument timePtr de Tcl_WaitForEvent pointe vers une structure décrivant un intervalle de temps en secondes et microsecondes :

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

Le champ usec doit être inférieur à 1000000.

Les informations fournies à Tcl_SetMaxBlockTime ne sont utilisées que pour le prochain appel à Tcl_WaitForEvent ; elles sont supprimées après le retour de Tcl_WaitForEvent. La prochaine fois qu'une attente d'événement sera effectuée, chaque procédure de configuration des sources d'événements sera à nouveau appelée, et elles pourront spécifier de nouvelles données pour cette attente d'événement.

Si l'application utilise une boucle d'événements externe au lieu de Tcl_DoOneEvent, les sources d'événements peuvent avoir besoin d'appeler Tcl_SetMaxBlockTime à d'autres moments. Par exemple, si un nouveau gestionnaire d'événements est enregistré qui doit surveiller les événements, la source d'événements peut appeler Tcl_SetMaxBlockTime pour définir un temps d'attente maximal nul, forçant la boucle d'événements externe à appeler Tcl. Dans ce cas, Tcl_SetMaxBlockTime appelle Tcl_SetTimer avec l'intervalle le plus court vu depuis le dernier appel à Tcl_DoOneEvent ou Tcl_ServiceAll.

En plus de la procédure générale Tcl_SetMaxBlockTime, d'autres procédures spécifiques à la plateforme peuvent également être disponibles pour le setupProc, si des informations supplémentaires sont nécessaires à Tcl_WaitForEvent sur cette plateforme. Par exemple, sur les systèmes Unix, l'interface Tcl_CreateFileHandler peut être utilisée pour attendre les événements de fichiers.

La deuxième procédure fournie par chaque source d'événements est sa procédure de vérification, indiquée par l'argument checkProc de Tcl_CreateEventSource. CheckProc doit correspondre au prototype suivant :

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Les arguments de cette procédure sont les mêmes que ceux de setupProc. CheckProc est appelé par Tcl_DoOneEvent après qu'il a attendu les événements. On suppose qu'au moins une source d'événements est prête à mettre un événement en file d'attente. Tcl_DoOneEvent appelle chaque source d'événements à tour de rôle, de sorte que toutes aient une chance de mettre en file d'attente tous les événements qui sont prêts. La procédure de vérification fait deux choses. Premièrement, elle doit vérifier s'il y a des événements qui ont été déclenchés. Les différentes sources d'événements le font différemment.

Si une source d'événements détecte un événement intéressant, elle doit ajouter l'événement à la file d'attente d'événements de Tcl. Pour ce faire, la source d'événements appelle Tcl_QueueEvent. L'argument evPtr est un pointeur vers une structure allouée dynamiquement qui contient l'événement (voir plus loin pour les problèmes de gestion de la mémoire). Chaque source d'événements peut définir sa propre structure d'événement avec des informations pertinentes pour cette source d'événements. Cependant, le premier membre de la structure doit être une structure de type Tcl_Event, et le pointeur vers cette structure est utilisé lors de la communication entre la source d'événements et le reste du multiplexeur. Un Tcl_Event a la définition suivante :

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La source d'événements doit remplir le champ proc de la structure avant d'appeler Tcl_QueueEvent. Le nextPtr est utilisé pour lier les événements dans la file d'attente et ne doit pas être modifié par la source d'événements.

Un événement peut être ajouté à la file d'attente dans l'une des trois positions, en fonction de l'argument position de Tcl_QueueEvent :

TCL_QUEUE_TAIL
Ajouter l'événement à la fin de la file d'attente, de sorte que tous les autres événements en attente soient traités en premier. C'est presque toujours la meilleure position pour les nouveaux événements.
TCL_QUEUE_HEAD
Ajouter l'événement au début de la file d'attente, de sorte qu'il soit traité avant tous les autres événements dans la file d'attente.
TCL_QUEUE_MARK
Ajouter l'événement au début de la file d'attente, sauf s'il y a d'autres événements au début de la file d'attente avec la position TCL_QUEUE_MARK ; si c'est le cas, ajouter le nouvel événement juste après tous les autres événements TCL_QUEUE_MARK. Cette valeur de position est utilisée pour insérer une séquence ordonnée d'événements au début de la file d'attente, comme une série d'événements Enter et Leave synthétisés lors d'une opération de capture ou de libération de capture dans Tk.

Lorsqu'il est temps de traiter un événement de la file d'attente (étapes 1 et 4 ci-dessus), Tcl_ServiceEvent appellera le proc spécifié dans la première structure Tcl_Event qui a été mise en file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

Le premier argument de proc est un pointeur vers l'événement, qui sera le même que le premier argument de l'appel à Tcl_QueueEvent qui a ajouté l'événement à la file d'attente. Le deuxième argument de proc est le flags de l'appel actuel à Tcl_ServiceEvent ; il est utilisé par la source d'événements pour retourner immédiatement si ses événements ne sont pas pertinents.

Il incombe à proc de traiter l'événement, en appelant généralement une ou plusieurs commandes Tcl ou des rappels de niveau C. Une fois que la source d'événements a fini de traiter l'événement, elle renvoie 1 pour indiquer que l'événement peut être retiré de la file d'attente. Si, pour une raison quelconque, la source d'événements décide que l'événement ne peut pas être traité à ce moment-là, elle peut renvoyer 0 pour indiquer que l'événement doit être différé pour être traité plus tard ; dans ce cas, Tcl_ServiceEvent passe à l'événement suivant dans la file d'attente et tente de le traiter. Il existe plusieurs raisons pour lesquelles une source d'événements pourrait différer un événement. Une possibilité est que les événements de ce type soient exclus par l'argument flags. Par exemple, la source d'événements de fichiers renvoie toujours 0 si le bit TCL_FILE_EVENTS n'est pas défini dans flags. Un autre exemple de report d'événements se produit dans Tk lorsque Tk_RestrictEvents a été appelé pour restreindre certains types d'événements de fenêtre.

Lorsque proc renvoie 1, Tcl_ServiceEvent retirera l'événement de la file d'attente des événements et libérera son stockage. Vous devez noter que le stockage d'un événement doit être alloué par la source d'événements (en utilisant Tcl_Alloc ou la macro Tcl ckalloc) avant d'appeler Tcl_QueueEvent, mais il sera libéré par Tcl_ServiceEvent, et non par la source d'événements.

Les applications multithread fonctionnent de manière similaire, à la différence qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. Appeler Tcl_QueueEvent dans une application multithread ajoute un événement à la file d'attente de ce thread. Pour ajouter un événement à la file d'attente d'un autre thread, utilisez Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent accepte comme argument un Tcl_ThreadId, qui identifie de manière unique un thread dans une application Tcl. Pour obtenir le Tcl_ThreadId du thread actuel, utilisez la procédure Tcl_GetCurrentThread. (Un thread devrait alors passer cet identifiant à d'autres threads afin qu'ils puissent ajouter des événements à sa file d'attente.) Après avoir ajouté un événement à la file d'attente d'un autre thread, vous devez généralement appeler Tcl_ThreadAlert pour "réveiller" le multiplexeur de ce thread afin de l'alerter du nouvel événement.

Tcl_DeleteEvents peut être utilisé explicitement pour supprimer un ou plusieurs événements de la file d'attente des événements. Tcl_DeleteEvents appelle le proc pour chaque événement de la file d'attente, supprimant ceux dont la procédure renvoie 1. Les événements dont la procédure renvoie 0 sont conservés dans la file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

L'argument clientData sera le même que l'argument clientData de Tcl_DeleteEven

ts ; il est généralement utilisé pour pointer vers des informations privées gérées par la source d'événements. Le pointeur evPtr pointera vers l'événement suivant dans la file d'attente.

Tcl_DeleteEventSource supprime une source d'événements. Les arguments setupProc, checkProc et clientData doivent correspondre exactement à ceux fournis à Tcl_CreateEventSource pour que la source d'événements soit supprimée. Si aucune source de ce type n'existe, Tcl_DeleteEventSource n'a aucun effet.

CRÉATION D'UN NOUVEAU NOTIFICATEUR

Le notificateur se compose de toutes les procédures décrites dans cet article de manuel, plus Tcl_DoOneEvent et Tcl_Sleep, qui sont disponibles sur toutes les plateformes, et Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont spécifiques à Unix. La plupart de ces procédures sont génériques, dans le sens où elles sont identiques pour tous les notificateurs. Cependant, aucune des procédures n'est indépendante du notificateur : Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler et Tcl_ServiceModeHook. Pour prendre en charge une nouvelle plateforme ou pour intégrer Tcl à une boucle d'événements spécifique à une application, vous devez écrire de nouvelles versions de ces procédures.

Tcl_InitNotifier initialise l'état du notificateur et renvoie un handle vers l'état du notificateur. Tcl appelle cette procédure lors de l'initialisation d'un interpréteur Tcl. De même, Tcl_FinalizeNotifier arrête le notificateur et est appelée par Tcl_Finalize lors de l'arrêt d'un interpréteur Tcl.

Tcl_WaitForEvent est la procédure de plus bas niveau du notificateur ; elle est responsable de l'attente d'un événement « intéressant » ou de l'expiration d'un délai donné. Avant que Tcl_WaitForEvent ne soit appelée, chaque procédure de configuration des sources d'événements aura été appelée. L'argument timePtr de Tcl_WaitForEvent donne le temps maximum de blocage pour un événement, basé sur les appels à Tcl_SetMaxBlockTime effectués par les procédures de configuration et sur d'autres informations (telles que le bit TCL_DONT_WAIT dans flags).

Idéalement, Tcl_WaitForEvent ne devrait qu'attendre qu'un événement se produise ; elle ne devrait pas vraiment traiter l'événement de quelque manière que ce soit. Plus tard, les sources d'événements traiteront les événements bruts et créeront des Tcl_Events dans la file d'attente d'événements dans leurs procédures checkProc. Cependant, sur certaines plateformes (comme Windows), cela n'est pas possible ; les événements peuvent être traités dans Tcl_WaitForEvent, y compris la mise en file d'attente des Tcl_Events et plus encore (par exemple, des rappels pour les widgets natifs peuvent être invoqués). La valeur de retour de Tcl_WaitForEvent doit être 0, 1 ou -1. Sur les plateformes comme Windows où les événements sont traités dans Tcl_WaitForEvent, une valeur de retour de 1 signifie qu'il peut y avoir encore d'autres événements en attente qui n'ont pas été traités. C'est un signe pour l'appelant qu'il doit appeler à nouveau Tcl_WaitForEvent s'il veut que tous les événements en attente soient traités. Une valeur de retour de 0 signifie qu'un nouvel appel à Tcl_WaitForEvent n'aura aucun effet : soit c'est une plateforme où Tcl_WaitForEvent ne fait qu'attendre sans traiter d'événements, soit Tcl_WaitForEvent sait avec certitude qu'il n'y a pas d'événements supplémentaires à traiter (par exemple, elle est retournée parce que le temps est écoulé). Enfin, une valeur de retour de -1 signifie que la boucle d'événements n'est plus opérationnelle et que l'application devrait probablement se dérouler et se terminer. Sous Windows, cela se produit lorsqu'un message WM_QUIT est reçu ; sous Unix, cela se produit lorsque Tcl_WaitForEvent attendrait éternellement car il n'y avait pas de sources d'événements actives et que le délai d'attente était infini.

Tcl_AlertNotifier est utilisé dans les applications multithread pour permettre à n'importe quel thread de « réveiller » le notificateur afin de l'alerter de nouveaux événements dans sa file d'attente. Tcl_AlertNotifier nécessite comme argument le handle du notificateur renvoyé par Tcl_InitNotifier.

Si le notificateur sera utilisé avec une boucle d'événements externe, il doit également prendre en charge l'interface Tcl_SetTimer. Tcl_SetTimer est appelée par Tcl_SetMaxBlockTime chaque fois que le temps de blocage maximum a été réduit. Tcl_SetTimer doit organiser pour que la boucle d'événements externe appelle Tcl_ServiceAll après l'intervalle spécifié, même si aucun événement ne s'est produit. Cette interface est nécessaire car Tcl_WaitForEvent n'est pas appelée lorsqu'il y a une boucle d'événements externe. Si le notificateur ne sera utilisé qu'à partir de Tcl_DoOneEvent, alors Tcl_SetTimer n'a pas besoin de faire quoi que ce soit.

Tcl_ServiceModeHook est appelée par la partie indépendante de la plateforme du notificateur lorsque le code client appelle Tcl_SetServiceMode. Ce hook est fourni pour prendre en charge les systèmes d'exploitation qui nécessitent une gestion spéciale des événements lorsque l'application est dans une boucle modale (le notificateur Windows, par exemple, utilise ce hook pour créer une fenêtre de communication).

Sur les systèmes Unix, la source d'événements de fichier nécessite également le support du notificateur. La source d'événements de fichier se compose des procédures Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont décrites dans la page de manuel de Tcl_CreateFileHandler.

Les interfaces Tcl_Sleep et Tcl_DoOneEvent sont décrites dans leurs pages de manuel respectives.

Le moyen le plus simple de créer un nouveau notificateur est de regarder le code d'un notificateur existant, tel que les fichiers unix/tclUnixNotfy.c ou win/tclWinNotify.c dans la distribution source de Tcl.

REMPLACEMENT DU NOTIFICATEUR

Un notificateur écrit conformément aux conventions ci-dessus peut également être installé dans un processus en cours d'exécution à la place du notificateur standard. Ce mécanisme est utilisé de manière à ce qu'un seul exécutable puisse être utilisé (avec le notificateur standard) comme programme autonome et réutilisé (avec un notificateur de remplacement dans une extension chargeable) comme extension d'un autre programme, tel qu'un plugin de navigateur Web.

Pour ce faire, l'extension appelle Tcl_SetNotifier en lui passant un pointeur vers une structure de données Tcl_NotifierProcs. La structure a la disposition suivante :

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Suite à l'appel à Tcl_SetNotifier, les pointeurs fournis dans la structure Tcl_NotifierProcs remplacent tout notificateur qui avait été installé dans le processus.

Il est extraordinairement déconseillé de remplacer un notificateur en cours d'exécution. Normalement, Tcl_SetNotifier devrait être appelé au moment de l'initialisation du processus, avant le premier appel à Tcl_InitNotifier.

BOUCLES D'ÉVÉNEMENTS EXTERNES

Les interfaces du notificateur sont conçues de manière à ce que Tcl puisse être intégrée dans des applications qui ont leurs propres boucles d'événements privées. Dans ce cas, l'application n'appelle pas Tcl_DoOneEvent, sauf dans le cas de boucles d'événements récursives telles que les appels aux commandes Tcl update ou vwait. La plupart du temps est passé dans la boucle d'événements externe de l'application. Dans ce cas, le notificateur doit organiser pour que la boucle d'événements externe rappelle Tcl lorsque quelque chose se produit sur les différentes sources d'événements Tcl. Ces rappels doivent organiser pour que des événements Tcl appropriés soient placés dans la file d'attente d'événements Tcl.

Étant donné que la boucle d'événements externe n'appelle pas Tcl_DoOneEvent régulièrement, il incombe au notificateur d'organiser pour que Tcl_ServiceEvent soit appelée chaque fois que des événements sont en attente dans la file d'attente d'événements Tcl. Le moyen le plus simple de le faire est d'appeler Tcl_ServiceAll à la fin de chaque rappel provenant de la boucle d'événements externe. Cela garantira que toutes les sources d'événements sont sondées, que tous les événements mis en file d'attente sont traités et que tous les gestionnaires d'inactivité en attente sont traités avant de rendre le contrôle à l'application. De plus, les sources d'événements qui doivent sonder les événements peuvent appeler Tcl_SetMaxBlockTime pour forcer la boucle d'événements externe à appeler Tcl même si aucun événement n'est disponible dans la file d'attente d'événements système.

En tant qu'effet secondaire du traitement des événements détectés dans la boucle d'événements externe principale, Tcl peut appeler Tcl_DoOneEvent pour démarrer une boucle d'événements récursive dans des commandes comme vwait. Tcl_DoOneEvent appellera la boucle d'événements externe, ce qui entraînera des rappels comme décrit dans le paragraphe précédent, ce qui entraînera des appels à Tcl_ServiceAll. Cependant, dans ces cas, il est indésirable de traiter les événements dans Tcl_ServiceAll. Le traitement des événements là-bas est inutile car le contrôle reviendra immédiatement à la boucle d'événements externe et donc à Tcl_DoOneEvent, qui peut traiter les événements elle-même. De plus, Tcl_DoOneEvent est censé ne traiter qu'un seul événement, tandis que Tcl_ServiceAll traite normalement tous les événements en attente. Pour gérer cette situation, Tcl_DoOneEvent définit un drapeau pour Tcl_ServiceAll qui le fait retourner sans traiter d'événements. Ce drapeau est appelé le *mode de service* ; Tcl_DoOneEvent le rétablit à sa valeur précédente avant de retourner.

Dans certains cas, cependant, il peut être nécessaire que Tcl_ServiceAll traite des événements même lorsqu'il a été appelé depuis Tcl_DoOneEvent. Cela se produit lorsqu'il existe une autre boucle d'événements récursive invoquée via un gestionnaire d'événements appelé par Tcl_DoOneEvent (comme celui qui fait partie d'un widget natif). Dans ce cas, Tcl_DoOneEvent peut ne pas avoir la chance de traiter les événements, donc Tcl_ServiceAll doit les traiter tous. Toute boucle d'événements récursive qui appelle une boucle d'événements externe plutôt que Tcl_DoOneEvent doit réinitialiser le mode de service afin que tous les événements soient traités dans Tcl_ServiceAll. Ceci est fait en appelant la procédure Tcl_SetServiceMode. Si Tcl_SetServiceMode est appelé avec TCL_SERVICE_NONE, les appels à Tcl_ServiceAll retourneront immédiatement sans traiter d'événements. Si Tcl_SetServiceMode est appelé avec TCL_SERVICE_ALL, les appels à Tcl_ServiceAll se comporteront normalement. Tcl_SetServiceMode renvoie la valeur précédente du mode de service, qui doit être restaurée à la sortie de la boucle récursive. Tcl_GetServiceMode renvoie la valeur actuelle du mode de service.
