DESCRIPTION

Il y a plusieurs raisons d'appeler les fonctions de l'API Tcl_FS (par exemple, Tcl_FSAccess et Tcl_FSStat) plutôt que d'appeler directement des fonctions de niveau système comme access et stat. Premièrement, elles fonctionnent sur plusieurs plateformes, donc une extension qui les appelle devrait fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige certains bugs dans les appels de niveau système. Troisièmement, ces appels de fonction gèrent les conversions de chemins “Utf vers natif de la plateforme” qui peuvent être requises (et peuvent mettre en cache les résultats de telles conversions pour une plus grande efficacité lors des appels ultérieurs). Quatrièmement, et peut-être le plus important, toutes ces fonctions sont “conscientes du système de fichiers virtuel”. Tout système de fichiers virtuel (VFS pour short) qui a été enregistré (via Tcl_FSRegister) peut réacheminer l'accès aux fichiers vers des supports ou des méthodes d'accès alternatifs. Cela signifie que toutes ces fonctions (et donc les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent opérer sur des “fichiers” qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS pour short) via cette API est automatiquement “consciente du système de fichiers virtuel”. Bien sûr, si une extension accède directement au système de fichiers natif (via des API spécifiques à la plateforme, par exemple), alors Tcl ne peut pas intercepter de tels appels.

Si des VFS appropriés ont été enregistrés, les “fichiers” peuvent, pour donner deux exemples, être distants (par exemple, situés sur un serveur ftp distant) ou archivés (par exemple, se trouvant à l'intérieur d'une archive .zip). De tels systèmes de fichiers enregistrés fournissent une table de recherche de fonctions pour implémenter tout ou partie de la fonctionnalité listée ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat font abstraction de la déclaration du tampon “struct stat”, permettant d'utiliser le même code sur les systèmes avec et sans prise en charge des fichiers de plus de 2 Go.

L'API Tcl_FS est basée sur Tcl_Obj et peut mettre en cache des représentations internes et d'autres chaînes liées aux chemins (par exemple, le répertoire de travail courant). Une conséquence est qu'il ne faut pas passer de valeurs avec un compteur de références de zéro à aucune de ces fonctions. Si de tels appels étaient traités, ils pourraient entraîner des fuites de mémoire (dans certaines circonstances, le code du système de fichiers peut souhaiter conserver une référence à la valeur passée, et il ne faut donc pas supposer qu'après le retour de l'un de ces appels, la valeur a toujours un compteur de références de zéro - il peut avoir été incrémenté) ou un défaut de segmentation direct (ou une autre erreur d'accès mémoire) en raison de la libération de la valeur au cours de la manipulation complexe de valeurs requise pour s'assurer que le chemin est entièrement normalisé et absolu pour la détermination du système de fichiers. La leçon pratique à en tirer est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect et peut causer des erreurs de mémoire. La référence du path doit être incrémentée avant d'être passée, ou décrémentée. Pour cette raison, les valeurs avec un compteur de références de zéro ne sont pas considérées comme des chemins de système de fichiers valides et l'appel de toute fonction API Tcl_FS avec une telle valeur n'entraînera aucune action.

FONCTIONS DE L'API FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), alors la fonction “copier fichier” de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno sur le code d'erreur POSIX “EXDEV” (qui signifie un “lien inter-domaines”).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), alors la fonction “copier fichier” de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno sur le code d'erreur POSIX “EXDEV” (qui signifie un “lien inter-domaines”).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction “créer répertoire” du système de fichiers propriétaire.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction “supprimer fichier” du système de fichiers propriétaire.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction “supprimer répertoire” du système de fichiers propriétaire.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr en le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), alors la fonction “renommer fichier” de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno sur le code d'erreur POSIX “EXDEV” (qui signifie un “lien inter-domaines”).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction “lister volumes” non NULL et leur demande de retourner leur liste de volumes racines. Elle accumule les valeurs de retour dans une liste qui est retournée à l'appelant (avec un compteur de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant le codage identifié par encodingName et évalue son contenu comme un script Tcl. Elle retourne les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, le codage système est utilisé pour lire le contenu du fichier. Si le fichier n'a pas pu être lu, une erreur Tcl est retournée pour décrire pourquoi le fichier n'a pas pu être lu. Le caractère de fin de fichier (eofchar) pour les fichiers est “\x1A” (^Z) pour toutes les plateformes. Si vous avez besoin d'un “^Z” dans le code pour une comparaison de chaînes, vous pouvez utiliser “\x1A”, qui sera sûrement substitué par l'interpréteur Tcl en “^Z”. Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours le codage système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier de code binaire en mémoire et retourne les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas, en raison des limitations du système d'exploitation dans le chargement dynamique de code binaire), Tcl tentera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile inverse l'opération, demandant que la bibliothèque indiquée par loadHandle soit retirée du processus. Notez que, contrairement à la commande unload, cela ne donne à la bibliothèque aucune opportunité de nettoyage.

Les deux fonctions ci-dessus retournent un code de complétion Tcl standard. En cas d'erreur, un message d'erreur est laissé dans le résultat de l'interp.

Le jeton fourni via la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher dans un répertoire tous les fichiers qui correspondent à un modèle donné. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du globbing. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Notez que le code glob implémente les motifs récursifs en interne, donc cette fonction ne recevra jamais que des motifs simples, qui peuvent être mis en correspondance en utilisant la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment en demandant uniquement que des répertoires soient retournés. Un cas spécial d'appel avec un motif NULL indique que le chemin doit être vérifié uniquement pour le type correct.

Tcl_FSLink remplace la version de bibliothèque de readlink, et l'étend pour prendre en charge la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr sera appelée.

Si toPtr est NULL, une action de “lecture de lien” est effectuée. Le résultat est un Tcl_Obj spécifiant le contenu du lien symbolique donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat est détenu par l'appelant, qui devrait appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl devrait créer un lien d'un des types passés dans le drapeau linkAction. Ce drapeau est une combinaison OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'un choix existe (c'est-à-dire que plus d'un drapeau est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur de retour doit être toPtr (qui est donc déjà détenu par l'appelant). En cas d'échec, NULL est retourné.

Tcl_FSLstat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (toujours 1 sous Windows), l'ID d'utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), le périphérique de destination (rdev) (identique au périphérique sous Windows), la taille, la dernière

t accéder au moment de l'accès, au moment de la dernière modification et au moment de la dernière modification des métadonnées. Voir API PORTABLE POUR LE RÉSULTAT DE STAT pour une description de la façon d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSLstat retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné, et aucune information stat n'est fournie.

Tcl_FSUtime remplace la version bibliothèque de utime.

Ceci retourne 0 en cas de succès et -1 en cas d'erreur (conformément à la documentation de utime). En cas de succès, la fonction mettra à jour les valeurs "atime" et "mtime" du fichier donné.

Tcl_FSFileAttrsGet implémente l'accès en lecture pour la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

Si le résultat est TCL_OK, alors une valeur a été placée dans objPtrRef, qui ne sera valide que temporairement (à moins que Tcl_IncrRefCount ne soit appelée).

Tcl_FSFileAttrsSet implémente l'accès en écriture pour la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

Tcl_FSFileAttrStrings implémente une partie de la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La procédure appelée peut soit retourner un tableau de chaînes, soit retourner NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. À la fin de cette utilisation, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer qu'il conserve un compteur de références à la valeur.

Tcl_FSAccess vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est pathname. Si pathname est un lien symbolique sous Unix, alors les permissions du fichier auquel ce lien symbolique fait référence sont testées.

En cas de succès (toutes les permissions demandées accordées), zéro est retourné. En cas d'erreur (au moins un bit dans mode demandé une permission qui est refusée, ou une autre erreur s'est produite), -1 est retourné.

Tcl_FSStat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le dernier accès, la dernière modification et le dernier changement de métadonnées. Voir API PORTABLE POUR LE RÉSULTAT DE STAT pour une description de la façon d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSStat retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné, et aucune information stat n'est fournie.

Tcl_FSOpenFileChannel ouvre un fichier spécifié par pathPtr et retourne un descripteur de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est basée sur la procédure fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannel retourne NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannel laisse un message d'erreur dans le résultat de interp après toute erreur.

Le canal nouvellement créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez Tcl_RegisterChannel. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, l'acte de création du nouveau canal l'assigne également en tant que remplacement du canal standard.

Tcl_FSGetCwd remplace la version bibliothèque de getcwd.

Il retourne le répertoire de travail courant de la bibliothèque Tcl. Cela peut être différent du répertoire de travail courant de la plateforme native, ce qui se produit lorsque le répertoire de travail courant n'est pas dans le système de fichiers natif.

Le résultat est un pointeur vers un Tcl_Obj spécifiant le répertoire courant, ou NULL si le répertoire courant n'a pas pu être déterminé. Si NULL est retourné, un message d'erreur est laissé dans le résultat de l'interpréteur interp.

Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compteur de références doit être décrémenté. Ceci est nécessaire pour la thread-safety, pour permettre à plusieurs threads d'accéder à cette fonction et aux fonctions associées, tout en garantissant que les résultats sont toujours valides.

Tcl_FSChdir remplace la version bibliothèque de chdir. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl se rabattra sur une combinaison de stat et access pour vérifier si le répertoire existe et a les permissions appropriées.

Pour les résultats, voir la documentation de chdir. En cas de succès, nous conservons un enregistrement du chemin réussi dans cwdPathPtr pour les appels ultérieurs à Tcl_FSGetCwd.

Tcl_FSPathSeparator retourne le caractère séparateur à utiliser pour l'élément le plus spécifique du chemin spécifié par pathPtr (c'est-à-dire la dernière partie du chemin).

Le séparateur est retourné sous forme de Tcl_Obj contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est retourné.

Tcl_FSJoinPath prend le Tcl_Obj donné, qui doit être une liste valide (autorisée à avoir un compteur de références nul), et retourne la valeur du chemin donnée en considérant les elements premiers éléments comme des segments de chemin valides (chaque segment de chemin peut être un chemin complet, un chemin partiel ou juste un seul répertoire ou nom de fichier possible). Si un segment de chemin est effectivement un chemin absolu, tous les segments de chemin précédents sont rejetés. Si elements est inférieur à 0, nous utilisons la liste entière.

Il est possible que la valeur retournée soit effectivement un élément de la liste donnée, donc l'appelant doit faire attention à incrémenter le compteur de références du résultat avant de libérer la liste.

La valeur retournée, généralement avec un compteur de références de zéro (mais elle peut être partagée dans certaines conditions), contient le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. En particulier, la valeur retournée peut être un élément de la liste donnée, donc la libération de la liste pourrait libérer la valeur prématurément si aucun compteur de références n'a été pris. Si le nombre d'éléments est zéro, alors la valeur retournée sera un Tcl_Obj chaîne vide.

Tcl_FSSplitPath prend le Tcl_Obj donné, qui devrait être un chemin valide, et retourne une valeur de liste Tcl contenant chaque segment de ce chemin comme un élément. Il retourne une valeur de liste avec un compteur de références de zéro. Si lenPtr passé n'est pas NULL, la variable à laquelle il pointe sera mise à jour pour contenir le nombre d'éléments dans la liste retournée.

Tcl_FSEqualPaths teste si les deux chemins donnés représentent le même objet de système de fichiers. Il retourne 1 si les chemins sont égaux, et 0 s'ils sont différents. Si l'un des chemins est NULL, 0 est toujours retourné.

Tcl_FSGetNormalizedPath tente d'extraire du Tcl_Obj donné une représentation de chemin normalisée unique, dont la valeur chaîne peut être utilisée comme identifiant unique du fichier.

Il retourne la valeur du chemin normalisé, détenue par Tcl, ou NULL si le chemin était invalide ou n'a pas pu être converti avec succès. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère sur ces représentations en interne), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques ne soit pas la version la plus conviviale d'un chemin. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle du pathPtr passé (sauf s'il s'agit d'un chemin relatif, auquel cas la valeur du chemin normalisé peut être libérée à tout moment où le cwd change) - l'appelant peut bien sûr incrémenter le compteur de références s'il souhaite conserver une copie plus longtemps.

Tcl_FSJoinToPath prend la valeur donnée, qui devrait généralement être un chemin valide ou NULL, et y joint le tableau de segments de chemin donnés.

Retourne une valeur, généralement avec un compteur de références nul (mais elle peut être partagée dans certaines conditions), contenant le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. Si l'une des valeurs passées à cette fonction (pathPtr ou éléments de path) a un compteur de références nul, elle sera libérée lorsque cette fonction retournera.

Tcl_FSConvertToPathType essaie de convertir le Tcl_Obj donné en un type de chemin Tcl valide, en tenant compte du fait que le cwd peut avoir changé même si cette valeur est déjà censée être du bon type. Le nom de fichier peut commencer par "~" (pour indiquer le répertoire personnel de l'utilisateur courant) ou "~<utilisateur>" (pour indiquer le répertoire personnel de n'importe quel utilisateur).

Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), alors TCL_OK est retourné. Sinon, TCL_ERROR est retourné, et un message d'erreur peut être laissé dans l'interpréteur.

Tcl_FSGetInternalRep extrait la représentation interne d'une valeur de chemin donnée, dans le système de fichiers donné. Si la valeur du chemin appartient à un système de fichiers différent, nous retournons NULL. Si la représentation interne est actuellement NULL, nous tentons de la générer, en appelant Tcl_FSCreateInternalRepProc du système de fichiers.

Retourne NULL ou une représentation de chemin interne valide. Cette représentation interne est mise en cache, de sorte que les appels répétés à cette fonction ne nécessiteront pas de conversions supplémentaires.

Tcl_FSGetTranslatedPath tente d'extraire le chemin traduit du Tcl_Obj donné.

Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), elle est retournée. Sinon, NULL sera retourné, et un message d'erreur peut être laissé dans l'interpréteur. Un chemin "traduit" est un chemin qui ne contient pas de séquences "~" ou "~utilisateur" (celles-ci ont été développées en leur représentation actuelle dans le système de fichiers). La valeur retournée est détenue par l'appelant, qui doit la stocker ou appeler Tcl_DecrRefCount pour s'assurer que la mémoire est libérée. Cette fonction a peu d'utilité pratique, et Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des besoins.

Tcl_FSGetTranslatedStringPath fait la même chose que Tcl_FSGetTranslatedPath, mais retourne une chaîne de caractères ou NULL. La chaîne retournée est allouée dynamiquement

édité et détenu par l'appelant, qui doit le stocker ou appeler ckfree pour s'assurer qu'il est libéré. Encore une fois, Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des usages.

Tcl_FSNewNativePath effectue quelque chose comme l'inverse des conversions obj->chemin->représentationnative habituelles. Si un code récupère un chemin sous forme native (depuis, par exemple, readlink ou une boîte de dialogue native), et que ce chemin doit être utilisé au niveau Tcl, alors appeler cette fonction est un moyen efficace de créer le type de valeur de chemin approprié.

La valeur résultante est une valeur pure de type « chemin », qui ne recevra une représentation textuelle UTF-8 que si cela est requis par du code Tcl.

Tcl_FSGetNativePath est destiné à être utilisé par les systèmes de fichiers natifs Win/Unix, afin qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un wrapper de commodité autour de Tcl_FSGetInternalRep. Il pourrait être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes de caractères (par exemple, sur macOS, une représentation utilisant une structure FSRef de fileSpec serait probablement plus efficace). Sous Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Actuellement, la représentation est simplement une chaîne de caractères qui peut contenir soit le chemin relatif, soit un chemin normalisé complet et absolu dans l'encodage natif (des conditions complexes dictent lequel de ceux-ci sera fourni, donc aucun ne peut être garanti, sauf si le chemin est connu pour être absolu). Si vous avez besoin d'un chemin natif qui doit être absolu, alors vous devriez demander la version native d'un chemin normalisé. Si, pour une raison quelconque, une version non absolue et non normalisée du chemin est nécessaire, celle-ci doit être construite séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache afin que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle du pathPtr passé en argument (sauf si il s'agit d'un chemin relatif, auquel cas la représentation native peut être libérée à tout moment où le répertoire courant change).

Tcl_FSFileSystemInfo renvoie une liste de deux éléments. Le premier élément est le nom du système de fichiers (par exemple, « native », « vfs », « zip », ou « prowrap », éventuellement), et le second est le type particulier du chemin donné au sein de ce système de fichiers (qui dépend du système de fichiers). Le second élément peut être vide si le système de fichiers ne fournit pas de catégorisation supplémentaire des fichiers.

Une valeur de liste valide est renvoyée, à moins que la valeur du chemin ne soit pas reconnue, auquel cas NULL sera renvoyé.

Tcl_FSGetFileSystemForPath renvoie un pointeur vers le Tcl_Filesystem qui accepte ce chemin comme valide.

Si aucun système de fichiers n'accepte le chemin, NULL est renvoyé.

Tcl_FSGetPathType détermine si le chemin donné est relatif au répertoire courant, relatif au volume courant, ou absolu.

Il renvoie l'une des valeurs TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, ou TCL_PATH_VOLUME_RELATIVE

L'API DU SYSTÈME DE FICHIERS VIRTUEL

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un système de fichiers ; ces opérations sont invoquées au besoin par la couche générique, ce qui se produit généralement via les fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées en utilisant les méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un morceau de données facultatif à associer à ce système de fichiers. En appelant cette fonction, Tcl attachera le système de fichiers à la liste des systèmes de fichiers connus, et il deviendra pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera renvoyé.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et renvoie TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est renvoyé.

Tcl_FSData renverra le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il renverra NULL.

Tcl_FSMountsChanged est utilisé pour informer le noyau de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

LA STRUCTURE Tcl_Filesystem

La structure Tcl_Filesystem contient les champs suivants :

    const char *typeName;
    int structureLength;
    Tcl_FSVersion version;
    Tcl_FSPathInFilesystemProc *pathInFilesystemProc;
    Tcl_FSDupInternalRepProc *dupInternalRepProc;
    Tcl_FSFreeInternalRepProc *freeInternalRepProc;
    Tcl_FSInternalToNormalizedProc *internalToNormalizedProc;
    Tcl_FSCreateInternalRepProc *createInternalRepProc;
    Tcl_FSNormalizePathProc *normalizePathProc;
    Tcl_FSFilesystemPathTypeProc *filesystemPathTypeProc;
    Tcl_FSFilesystemSeparatorProc *filesystemSeparatorProc;
    Tcl_FSStatProc *statProc;
    Tcl_FSAccessProc *accessProc;
    Tcl_FSOpenFileChannelProc *openFileChannelProc;
    Tcl_FSMatchInDirectoryProc *matchInDirectoryProc;
    Tcl_FSUtimeProc *utimeProc;
    Tcl_FSLinkProc *linkProc;
    Tcl_FSListVolumesProc *listVolumesProc;
    Tcl_FSFileAttrStringsProc *fileAttrStringsProc;
    Tcl_FSFileAttrsGetProc *fileAttrsGetProc;
    Tcl_FSFileAttrsSetProc *fileAttrsSetProc;
    Tcl_FSCreateDirectoryProc *createDirectoryProc;
    Tcl_FSRemoveDirectoryProc *removeDirectoryProc;
    Tcl_FSDeleteFileProc *deleteFileProc;
    Tcl_FSCopyFileProc *copyFileProc;
    Tcl_FSRenameFileProc *renameFileProc;
    Tcl_FSCopyDirectoryProc *copyDirectoryProc;

    Tcl_FSLoadFileProc *loadFileProc;
    Tcl_FSGetCwdProc *getCwdProc;
    Tcl_FSChdirProc *chdirProc;

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche générique du système de fichiers pour effectuer la gamme complète des actions liées au système de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (dont presque toutes doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni), et fonctions d'efficacité (qui n'ont besoin d'être implémentées que si elles peuvent être faites efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces substitutions ne sont utilisées que pour gérer les commandes initiées dans Tcl, pas dans C. Cela signifie que, si une commande file rename est émise dans Tcl, et que le(s) système(s) de fichiers pertinent(s) n'implémente(nt) pas leur Tcl_FSRenameFileProc, le noyau de Tcl se rabattra sur une combinaison d'autres fonctions de système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a une autre substitution). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucune substitution de ce type ne se produit. Ceci est vrai sauf pour les quatre dernières entrées de la table des systèmes de fichiers (lstat, load, getcwd et chdir) pour lesquelles des substitutions se produisent en fait au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme Tcl_Obj les prennent sous forme UTF-8. L'API d'infrastructure des systèmes de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

    /* Pas de copie de fichier ; utiliser le mécanisme de substitution du noyau */
    NULL,
    /* Pas de renommage de fichier ; utiliser le mécanisme de substitution du noyau
mechanism */ NULL, /* Pas de répertoire de copie ; utiliser le mécanisme de secours du noyau */ NULL, /* Le noyau utilisera stat pour lstat */ NULL, /* Pas de chargement ; utiliser le mécanisme de secours du noyau */ NULL, /* Nous n'avons pas besoin de getcwd ou chdir ; la valeur interne * du noyau est suffisante */ NULL, NULL };

INFRASTRUCTURE DU SYSTÈME DE FICHIERS

Ces champs contiennent des informations de base sur la structure du système de fichiers et les adresses des fonctions utilisées pour associer un système de fichiers particulier à un chemin de fichier, et pour gérer le traitement interne des représentations de chemin, par exemple la copie et la libération de ces représentations.

TYPE NOM

Le champ typeName contient une chaîne de caractères terminée par un caractère nul qui identifie le type du système de fichiers implémenté, par exemple « natif », « zip » ou « vfs ».

LONGUEUR STRUCTURE

Le champ structureLength est généralement implémenté comme sizeof(Tcl_Filesystem), et est là pour permettre une meilleure compatibilité descendante binaire si la taille de la structure change dans une future version de Tcl.

VERSION

Le champ version doit être défini sur TCL_FILESYSTEM_VERSION_1.

PROCÉDURE CHEMIN DANS SYSTÈME DE FICHIERS

Le champ pathInFilesystemProc contient l'adresse d'une fonction qui est appelée pour déterminer si une valeur de chemin donnée appartient à ce système de fichiers ou non. Tcl n'appellera les autres fonctions du système de fichiers qu'avec un chemin pour lequel cette fonction a retourné TCL_OK. Si le chemin n'appartient pas, -1 doit être retourné (le comportement de Tcl pour toute autre valeur de retour n'est pas défini). Si TCL_OK est retourné, alors le paramètre de sortie optionnel clientDataPtr peut être utilisé pour retourner une représentation interne (spécifique au système de fichiers) du chemin, qui sera mise en cache dans la valeur du chemin, et pourra être récupérée efficacement par les autres fonctions du système de fichiers. Tcl mettra simultanément en cache le fait que ce chemin appartient à ce système de fichiers. Ces caches sont invalidés lorsque les structures de système de fichiers sont ajoutées ou supprimées de la liste interne des systèmes de fichiers connus de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROCÉDURE DUPLICATION REPRÉSENTATION INTERNE

Cette fonction crée une copie de la représentation interne d'un chemin, et est appelée lorsque Tcl a besoin de dupliquer une valeur de chemin. Si elle est NULL, Tcl ne copiera simplement pas la représentation interne, qui pourra alors devoir être régénérée ultérieurement.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

PROCÉDURE LIBÉRATION REPRÉSENTATION INTERNE

Libère la représentation interne. Cela doit être implémenté si les représentations internes nécessitent d'être libérées (c'est-à-dire si de la mémoire est allouée lors de la génération d'une représentation interne), mais peut sinon être NULL.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

PROCÉDURE INTERNE VERS NORMALISÉE

Fonction pour convertir une représentation interne en un chemin normalisé. Requis uniquement si le système de fichiers crée des valeurs de chemin pures sans représentation textuelle/de chemin. La valeur de retour est une valeur Tcl dont la représentation textuelle est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

PROCÉDURE CRÉATION REPRÉSENTATION INTERNE

Fonction pour prendre une valeur de chemin, calculer une représentation interne pour celle-ci, et stocker cette représentation native dans la valeur. Peut être NULL si les chemins n'ont pas de représentation interne, ou si la procédure Tcl_FSPathInFilesystemProc pour ce système de fichiers crée toujours immédiatement une représentation interne pour les chemins qu'elle accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

PROCÉDURE NORMALISATION CHEMIN

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations textuelles pour la même valeur de chemin. Dans Tcl, chaque « chemin » doit avoir une seule représentation textuelle « normalisée » unique. Selon le système de fichiers, il peut y avoir plus d'une représentation textuelle non normalisée qui se réfère à ce chemin (par exemple, un chemin relatif, un chemin avec une casse de caractères différente si le système de fichiers ne respecte pas la casse, un chemin contenant une référence à un répertoire personnel comme « ~ », un chemin contenant des liens symboliques, etc.). Si le tout dernier composant du chemin est un lien symbolique, il ne doit pas être converti en la valeur à laquelle il pointe (mais sa casse ou d'autres aspects doivent être rendus uniques). Tous les autres composants du chemin doivent être convertis à partir de liens symboliques. Cette seule exception est requise pour être cohérente avec la sémantique de Tcl pour les opérations file delete, file rename, file copy sur les liens symboliques. Cette fonction peut être appelée avec nextCheckpoint soit au début du chemin (c'est-à-dire zéro), soit à la fin du chemin, soit à un séparateur de fichier intermédiaire dans le chemin. Elle ne pointera jamais vers une autre position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS SUR SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions appelées pour effectuer les opérations de base sur le système de fichiers. Un système de fichiers qui doit être utilisé avec l'ensemble complet des commandes Tcl standard doit implémenter toutes ces opérations. Si certaines d'entre elles ne sont pas implémentées, certaines commandes Tcl peuvent échouer lors de l'opération sur des chemins dans ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques n'a pas besoin d'implémenter la fonction readlink, etc. Le noyau Tcl attend des systèmes de fichiers qu'ils se comportent de cette manière).

PROCÉDURE TYPE CHEMIN SYSTÈME DE FICHIERS

Fonction pour déterminer le type d'un chemin dans ce système de fichiers. Peut être NULL, auquel cas aucune information de type ne sera disponible pour les utilisateurs du système de fichiers. Le « type » est utilisé uniquement à des fins d'information, et doit être retourné comme la représentation textuelle du Tcl_Obj retourné. Une valeur de retour typique pourrait être « réseau », « zip » ou « ftp ». L'objet Tcl résultat est détenu par le système de fichiers, Tcl incrémentera donc le compteur de références de cette valeur s'il souhaite conserver une référence à celle-ci.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

PROCÉDURE SÉPARATEUR SYSTÈME DE FICHIERS

Fonction pour retourner le(s) caractère(s) séparateur(s) pour ce système de fichiers. Ceci n'a besoin d'être implémenté que si le système de fichiers souhaite utiliser un séparateur différent de la chaîne standard « / ». Entre autres utilisations, il est retourné par la commande file separator. La valeur de retour doit être une valeur avec un compteur de références de zéro.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

PROCÉDURE STAT

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes au niveau Tcl en dépendent crucialement (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La procédure Tcl_FSStatProc remplit la structure stat statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure stat inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification, et l'heure du dernier changement de métadonnées.

Si le fichier représenté par pathPtr existe, la procédure Tcl_FSStatProc retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné, et aucune information de stat n'est donnée.

PROCÉDURE ACCÈS

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes au niveau Tcl en dépendent crucialement (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La procédure Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est dans pathPtr. Si le nom de chemin fait référence à un lien symbolique, alors les permissions du fichier auquel ce lien symbolique fait référence doivent être testées.

En cas de succès (toutes les permissions demandées accordées), zéro est retourné. En cas d'erreur (au moins un bit dans mode demandait une permission refusée, ou une autre erreur s'est produite), -1 est retourné.

PROCÉDURE OUVERTURE CANAL FICHIER

OPENFILECHANNELPROC

Fonction pour traiter un appel à Tcl_FSOpenFileChannel. Elle doit être implémentée pour tout système de fichiers raisonnable, car toute opération qui nécessite l'ouverture ou l'accès au contenu d'un fichier utilisera cette fonction (par exemple, open, encoding et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

La fonction Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et retourne un handle de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est calquée sur la fonction fopen de la bibliothèque d'entrée/sortie standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier, où mode est une combinaison des indicateurs POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannelProc retourne NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas nul, Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le nouveau canal ne doit pas être enregistré auprès de l'interpréteur fourni par Tcl_FSOpenFileChannelProc ; ce travail incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr, a été précédemment fermé, l'action de création du nouveau canal l'assigne également comme canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, la fonctionnalité de globbing et de copie récursive sera perdue pour le système de fichiers (et cela peut affecter des commandes comme encoding names qui utilisent la fonctionnalité de globbing).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit retourner tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au motif donné et qui correspondent à la spécification types. Il y a deux façons dont cette fonction peut être appelée. Si pattern est NULL, pathPtr est une spécification complète d'un fichier ou d'un répertoire unique qui doit être vérifié pour son existence et son type correct. Sinon, pathPtr est un répertoire et la fonction doit rechercher des fichiers ou des répertoires dont le type est correct. Dans tous les cas, on peut supposer que pathPtr n'est ni nul ni vide. Il n'est actuellement pas documenté si pathPtr aura un séparateur de fichier à la fin, le code doit donc être flexible pour les deux possibilités.

La valeur de retour est un résultat standard de Tcl indiquant si une erreur s'est produite pendant le processus de correspondance. Les messages d'erreur sont placés dans interp, à moins que interp ne soit NULL, auquel cas aucun message d'erreur ne sera généré ; en cas de résultat TCL_OK, les correspondances doivent être ajoutées à la valeur resultPtr fournie (qui peut être considérée comme une liste Tcl non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (ce qui signifie généralement qu'il s'agira de spécifications de chemin absolu). Remarque : s'il n'y a pas de correspondances, cela se traduit par un résultat vide ; seules les erreurs réelles de fichiers ou de systèmes de fichiers qui peuvent survenir pendant le processus de correspondance sont signalées.

Le Tcl_GlobTypeData fourni dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Type mac accepté */
    Tcl_Obj *macType;
    /* Créateur mac accepté */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de gérer correctement, tous deux lorsque types n'est pas nul. Les deux cas sont lorsque types->types & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT sont vrais (et en particulier lorsque les autres indicateurs sont faux). Dans le premier de ces cas, la fonction doit lister les répertoires correspondants. Tcl utilise cela pour implémenter le globbing récursif, il est donc crucial que les systèmes de fichiers implémentent correctement la correspondance des répertoires. Dans le second de ces cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage qui se trouvent dans pathPtr (et dans ce cas, pathPtr n'a pas besoin de se trouver dans le même système de fichiers - contrairement à tous les autres cas où cette fonction est appelée). Le support pour cela est critique si Tcl veut avoir des transitions fluides entre différents systèmes de fichiers.

UTIMEPROC

Fonction pour traiter un appel à Tcl_FSUtime. Elle est requise pour permettre la mise à jour (pas la lecture) des temps de modification et d'accès d'un fichier, ainsi que pour implémenter les fonctions de copie de fichiers file copy (open-r, open-w, fcopy).

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les temps d'accès et de modification du fichier spécifié par pathPtr doivent être modifiés aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec la fonction système utime.

LINKPROC

Fonction pour traiter un appel à Tcl_FSLink. Elle ne doit être implémentée que si le système de fichiers prend en charge les liens, et sinon elle peut être NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est sollicitée pour lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien ne peut pas être lu. Le résultat est contrôlé par l'appelant (et doit donc voir son compteur de références incrémenté avant d'être retourné). Tout appelant doit appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'en a plus besoin. Si toPtr n'est pas NULL, la fonction doit essayer de créer un lien. Dans ce cas, le résultat doit être toPtr si le lien a réussi et NULL dans le cas contraire. Dans ce cas, le résultat n'est pas contrôlé par l'appelant (c'est-à-dire qu'aucune manipulation de compteur de références n'est effectuée des deux côtés). Voir la documentation de Tcl_FSLink pour l'interprétation correcte des indicateurs linkAction.

LISTVOLUMESPROC

Fonction pour lister tous les volumes de système de fichiers ajoutés par ce système de fichiers. Elle ne doit être implémentée que si le système de fichiers ajoute des volumes au début du système de fichiers, afin qu'ils puissent être retournés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste de volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. La valeur du résultat est considérée comme contrôlée par le système (pas par le cœur de Tcl), mais elle doit se voir attribuer un compteur de références pour Tcl. Tcl utilisera le contenu de la liste, puis décrémentera ce compteur de références. Cela permet aux systèmes de fichiers de choisir s'ils veulent réellement conserver une liste globale de volumes (sinon, ils génèrent la liste à la volée et la passent à Tcl avec un compteur de références de 1, puis oublient la liste ; si oui, ils incrémentent simplement le compteur de références de leur liste globale et la passent à Tcl qui copie le contenu, puis décrémente le compteur de références de l'endroit où il se trouvait).

Par conséquent, Tcl considère les valeurs retournées par cette proc comme étant en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne prendra pas en charge la commande file attributes. Cela permet d'ajouter des informations arbitraires aux fichiers du système de fichiers. Si elle n'est pas implémentée, il n'est pas nécessaire d'implémenter les méthodes get et set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La fonction peut retourner un tableau de chaînes, ou elle peut retourner NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois son utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être disposée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si elle ne doit pas être disposée, le système de fichiers doit s'assurer de retourner une valeur avec un compteur de références d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsGet, utilisé par file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Retourne un code de retour standard Tcl. La valeur de la propriété d'index donné dans la liste retournée par Tcl_FSFileAttrStringsProc est un Tcl_Obj placé dans objPtrRef (si le code de retour était TCL_OK), et aura probablement un compteur de références de zéro. Qu'il soit retourné tel quel, nous devons stocker la valeur quelque part (par exemple, dans le résultat de Tcl), ou incrémenter/décrémenter son compteur de références pour assurer sa libération appropriée.

FILEATTRSSETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsSet, utilisé par file attributes. Si le système de fichiers est en lecture seule, il n'est pas nécessaire de l'implémenter.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

La valeur de la propriété d'index donné dans la liste retournée par Tcl_FSFileAttrStringsProc doit être définie sur objPtr fourni.

CREATEDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSCreateDirectory. Elle doit être implémentée, sauf si le FS est en lecture seule.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

La valeur de retour est un code de complétion standard de Tcl indiquant si une erreur s'est produite pendant le processus. En cas de succès, un nouveau répertoire doit avoir été ajouté au système de fichiers à l'emplacement spécifié par pathPtr.

REMOVEDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSRemoveDirectory. Elle doit être implémentée, sauf si le FS est en lecture seule.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

La valeur de retour est un code de complétion standard de Tcl indiquant si une erreur s'est produite pendant le processus. En cas de succès, le répertoire spécifié par pathPtr doit avoir été supprimé du système de fichiers. Si l'indicateur recursive est donné, un répertoire non vide doit être supprimé sans erreur. Si cet indicateur n'est pas donné, une erreur POSIX "EEXIST" doit être générée si le répertoire n'est pas vide. En cas d'erreur, le nom du fichier ou du répertoire qui a causé l'erreur doit se trouver dans errorPtr.

DELETEFILEPROC

Fonction pour traiter un appel à Tcl_FSDeleteFile. Elle doit être implémentée, sauf si le FS est en lecture seule.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

La valeur de retour est un code de complétion standard de Tcl indiquant si une erreur s'est produite pendant le processus. En cas de succès, le fichier spécifié par pathPtr doit avoir été supprimé du système de fichiers. Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non Tcl_FSRemoveDirectoryProc lorsqu'il est nécessaire de les supprimer (même s'ils sont des liens symboliques vers des répertoires).

EFFICACITÉ DU SYSTÈME DE FICHIERS

Ces fonctions ne doivent pas être implémentées pour un système de fichiers donné car le noyau dispose d'une implémentation de secours disponible. Voir chaque description individuelle pour les conséquences de laisser le champ NULL.

LSTATPROC

Fonction pour traiter un appel à Tcl_FSLstat. Si elle n'est pas implémentée, Tcl tentera d'utiliser la statProc définie ci-dessus. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut différencier les appels stat et lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le comportement de cette fonction est très similaire à celui de la Tcl_FSStatProc définie ci-dessus, sauf que si elle s'applique à un lien symbolique, elle renvoie des informations sur le lien, et non sur le fichier auquel il pointe.

COPYFILEPROC

Fonction pour traiter un appel à Tcl_FSCopyFile. Si elle n'est pas implémentée, Tcl utilisera le mécanisme open-r, open-w et fcopy comme copieur. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un code de complétion standard de Tcl indiquant si une erreur s'est produite pendant le processus de copie. Notez que, destPathPtr est le nom du fichier qui doit devenir une copie de srcPathPtr. Ce n'est jamais le nom d'un répertoire dans lequel srcPathPtr peut être copié (c'est-à-dire que la fonction est beaucoup plus simple que le sous-commande de niveau Tcl file copy). Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non copyDirectoryProc lorsqu'il est nécessaire de les copier (même s'ils sont des liens symboliques vers des répertoires). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file copy, en appelant Tcl_SetErrno(EXDEV) et en retournant un résultat non TCL_OK, Tcl utilisera ses mécanismes de secours standard.

RENAMEFILEPROC

Fonction pour traiter un appel à Tcl_FSRenameFile. Si elle n'est pas implémentée, Tcl utilisera un mécanisme de copie et de suppression. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un code de complétion standard de Tcl indiquant si une erreur s'est produite pendant le processus de renommage. Si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file rename, en appelant Tcl_SetErrno(EXDEV) et en retournant un résultat non TCL_OK, Tcl utilisera ses mécanismes de secours standard.

COPYDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSCopyDirectory. Si elle n'est pas implémentée, Tcl utilisera un mécanisme récursif de file mkdir, file copy comme copieur. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

La valeur de retour est un code de complétion standard de Tcl indiquant si une erreur s'est produite pendant le processus de copie. En cas d'erreur, le nom du fichier ou du répertoire qui a causé l'erreur doit se trouver dans errorPtr. Notez que, destPathPtr est le nom du répertoire qui doit devenir une image de copie de srcPathPtr. Ce n'est pas le nom d'un répertoire dans lequel srcPathPtr peut être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande de niveau Tcl file copy). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de copie de répertoires, en appelant Tcl_SetErrno(EXDEV) et en retournant un résultat non TCL_OK, Tcl utilisera ses mécanismes de secours standard.

LOADFILEPROC

Fonction pour traiter un appel à Tcl_FSLoadFile. Si elle n'est pas implémentée, Tcl utilisera une copie dans un fichier temporaire suivie d'un appel à Tcl_FSLoadFile sur ce fichier temporaire. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut charger du code directement, ou peut être simplement implémentée pour renvoyer TCL_ERROR afin de désactiver la fonctionnalité de chargement sur ce système de fichiers.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Renvoie un code de complétion standard de Tcl. En cas d'erreur, un message d'erreur est laissé dans le résultat de l'interp. La fonction charge dynamiquement un fichier binaire en mémoire. En cas de succès, handlePtr doit être rempli avec un jeton pour le fichier chargé dynamiquement, et unloadProcPtr doit être rempli avec l'adresse d'une procédure. La procédure de déchargement sera appelée avec le Tcl_LoadHandle donné comme seul paramètre lorsque Tcl doit décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle retourné est actuellement un jeton qui peut être utilisé dans le TclpFindSymbol privé pour accéder aux fonctions du nouveau code. Chaque système de fichiers peut définir le Tcl_LoadHandle selon ses besoins. Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de chargement de fichier, en appelant Tcl_SetErrno(EXDEV) et en retournant un résultat non TCL_OK, Tcl utilisera ses mécanismes de secours standard.

UNLOADFILEPROC

Fonction pour décharger un fichier qui a été précédemment chargé avec succès. Si le chargement a été implémenté, cette fonction doit également l'être s'il y a des actions de nettoyage nécessaires.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Fonction pour traiter un appel à Tcl_FSGetCwd. La plupart des systèmes de fichiers courants n'ont pas besoin d'implémenter cette fonction. Elle est souvent appelée une fois, si getcwd est appelé avant chdir. Elle peut être NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si le système de fichiers prend en charge une notation de répertoire de travail native (qui pourrait changer indépendamment de Tcl), cette fonction doit renvoyer ce répertoire de travail comme résultat, ou NULL si le répertoire de travail ne peut pas être déterminé (par exemple, l'utilisateur n'a pas les permissions appropriées dans le répertoire de travail). Si NULL est retourné, un message d'erreur est laissé dans le résultat de l'interp.

CHDIRPROC

Fonction pour traiter un appel à Tcl_FSChdir. Si les systèmes de fichiers n'implémentent pas cette fonction, elle est émulée par une série de vérifications d'accès aux répertoires. Sinon, les systèmes virtuels qui l'implémentent ne doivent renvoyer un résultat positif que si pathPtr est un répertoire valide et accessible sur leur système de fichiers. Ils ne doivent pas se souvenir du résultat, car celui-ci sera automatiquement mémorisé par Tcl_FSGetCwd. Les implémentations réelles doivent effectuer l'action correcte (c'est-à-dire appeler l'API chdir appropriée du système d'exploitation).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

La fonction Tcl_FSChdirProc change le répertoire de travail actuel de l'application vers la valeur spécifiée dans pathPtr. La fonction renvoie -1 en cas d'erreur ou 0 en cas de succès.
