DESCRIPTION

Il existe plusieurs raisons d'appeler les fonctions de l'API Tcl_FS (par exemple, Tcl_FSAccess et Tcl_FSStat) plutôt que d'appeler directement des fonctions de niveau système comme access et stat. Premièrement, elles fonctionnent sur plusieurs plateformes, de sorte qu'une extension qui les appelle devrait fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige certains bogues dans les appels de niveau système. Troisièmement, ces appels de fonction traitent les conversions de chemins "Utf vers natif de la plateforme" qui peuvent être nécessaires (et peuvent mettre en cache les résultats de ces conversions pour une plus grande efficacité lors des appels ultérieurs). Quatrièmement, et peut-être le plus important, toutes ces fonctions sont "conscientes du système de fichiers virtuel". Tout système de fichiers virtuel (VFS pour faire court) qui a été enregistré (via Tcl_FSRegister) peut rediriger l'accès aux fichiers vers des supports ou des méthodes d'accès alternatifs. Cela signifie que toutes ces fonctions (et par conséquent les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent opérer sur des "fichiers" qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS pour faire court) via cette API est automatiquement "consciente du système de fichiers virtuel". Bien sûr, si une extension accède directement au système de fichiers natif (via des API spécifiques à la plateforme, par exemple), Tcl ne peut pas intercepter de tels appels.

Si des VFS appropriés ont été enregistrés, les "fichiers" peuvent, pour donner deux exemples, être distants (par exemple, situés sur un serveur ftp distant) ou archivés (par exemple, se trouvant à l'intérieur d'une archive .zip). Ces systèmes de fichiers enregistrés fournissent une table de correspondance de fonctions pour implémenter tout ou partie de la fonctionnalité répertoriée ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat abstrait la déclaration du tampon "struct stat", permettant d'utiliser le même code sur les systèmes avec et sans prise en charge des fichiers de plus de 2 Go. La structure Tcl_StatBuf inclut des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (toujours 1 sous Windows), l'identifiant utilisateur (toujours 0 sous Windows), l'identifiant de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, l.

L'API Tcl_FS est basée sur Tcl_Obj et peut mettre en cache des représentations internes et d'autres chaînes liées aux chemins (par exemple, le répertoire de travail actuel). Un effet secondaire est qu'il ne faut pas passer de valeurs avec un compteur de références nul à l'une de ces fonctions. Si de tels appels étaient traités, ils pourraient entraîner des fuites de mémoire (dans certaines circonstances, le code du système de fichiers peut souhaiter conserver une référence à la valeur passée, et il ne faut donc pas supposer qu'après le retour de l'un de ces appels, la valeur a toujours un compteur de références nul - il peut avoir été incrémenté) ou un crash de segmentation direct (ou une autre erreur d'accès mémoire) en raison de la libération de la valeur en cours de manipulation complexe de valeur requise pour garantir que le chemin est complètement normalisé et absolu pour la détermination du système de fichiers. La leçon pratique à en tirer est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect et peut causer des erreurs de mémoire. Le compteur de références de path doit être incrémenté avant de le passer, ou décrémenté. Pour cette raison, les valeurs ayant un compteur de références nul ne sont pas considérées comme des chemins de système de fichiers valides et tout appel à une fonction de l'API Tcl_FS avec une telle valeur n'entraînera aucune action.

FONCTIONS DE L'API FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction "copie de fichier" de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno sur le code d'erreur POSIX "EXDEV" (qui signifie "lien inter-domaines").

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction "copie de fichier" de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno sur le code d'erreur POSIX "EXDEV" (qui signifie "lien inter-domaines").

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction "créer un répertoire" du système de fichiers propriétaire.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction "supprimer un fichier" du système de fichiers propriétaire.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction "supprimer un répertoire" du système de fichiers propriétaire.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction "renommer un fichier" de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno sur le code d'erreur POSIX "EXDEV" (qui signifie "lien inter-domaines").

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction "lister les volumes" non NULL et leur demande de retourner leur liste de volumes racines. Elle accumule les valeurs de retour dans une liste qui est renvoyée à l'appelant (avec un compteur de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant l'encodage identifié par encodingName et évalue son contenu comme un script Tcl. Elle renvoie les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, l'encodage système est utilisé pour lire le contenu du fichier. Si le fichier n'a pas pu être lu, une erreur Tcl est renvoyée pour expliquer pourquoi il n'a pas pu être lu. Le caractère eof pour les fichiers est "\x1A" (^Z) pour toutes les plateformes. Si vous avez besoin d'un "^Z" dans le code pour la comparaison de chaînes, vous pouvez utiliser "\x1A", qui sera substitué en toute sécurité par l'interpréteur Tcl en "^Z". Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours l'encodage système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier de code binaire en mémoire et renvoie les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas, en raison des limitations du système d'exploitation pour le chargement dynamique de code binaire), Tcl tentera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile inverse l'opération, demandant que la bibliothèque indiquée par loadHandle soit retirée du processus. Notez que, contrairement à la commande unload, cela ne donne à la bibliothèque aucune possibilité de nettoyage.

Les deux fonctions ci-dessus renvoient un code de complétion Tcl standard. Si une erreur se produit, un message d'erreur est laissé dans le résultat de l'interp.

Le jeton fourni via la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de glob pour rechercher dans un répertoire tous les fichiers qui correspondent à un modèle donné. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le glob. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Notez que le code glob implémente les modèles récursifs en interne, de sorte que cette fonction ne sera jamais appelée qu'avec des modèles simples, qui peuvent être comparés à l'aide de la logique de string match. Pour gérer la récursivité, Tcl appellera cette fonction fréquemment en demandant uniquement le retour des répertoires. Un cas spécial où elle est appelée avec un modèle NULL indique que le chemin doit être vérifié uniquement pour le bon type.

Tcl_FSLink remplace la version bibliothèque de readlink, et l'étend pour prendre en charge la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr sera appelée.

Si toPtr est NULL, une action de "lecture de lien" est effectuée. Le résultat est un Tcl_Obj spécifiant le contenu du lien symbolique donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant, qui doit appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl doit créer un lien d'un des types passés dans l'indicateur linkAction. Cet indicateur est une combinaison OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'un choix existe (c'est-à-dire que plus d'un indicateur est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur de retour doit être toPtr (qui appartient donc déjà à l'appelant). En cas d'échec, NULL est renvoyé.

Tcl_FSLstat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf comprend des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, l.

L'appel de procédure peut retourner un tableau de chaînes de caractères ou, à la place, retourner NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera son compteur de référence avant de l'utiliser. Une fois son utilisation terminée, Tcl décrémentera son compteur de référence. Par conséquent, si la liste doit être libérée par Tcl une fois terminée, elle doit avoir un compteur de référence égal à zéro, et si elle ne doit pas être libérée, le système de fichiers doit s'assurer de conserver un compteur de référence sur la valeur. Tcl_FSAccess vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est pathname. Si pathname est un lien symbolique sous Unix, les permissions du fichier auquel ce lien symbolique fait référence seront testées. En cas de succès (toutes les permissions demandées), 0 est retourné. En cas d'erreur (au moins un bit du mode demandé est refusé, ou une autre erreur se produit), -1 est retourné. Tcl_FSStat remplit la structure Tcl_StatBuf avec des informations sur le fichier spécifié. Aucun droit d'accès au fichier n'est requis pour obtenir ces informations, mais des droits de recherche sont requis dans tous les répertoires mentionnés dans le chemin d'accès au fichier. La structure Tcl_StatBuf comprend des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode des privilèges, le nombre de liens (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID groupe (toujours 0 sous Windows), le rdev (égal au périphérique sous Windows), la taille, le temps du dernier accès, le temps de la dernière modification et le temps du dernier changement de métadonnées. Voir PORTABLE STAT RESULT API pour une description sur la façon d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf. Si le path existe, Tcl_FSStat retourne 0 et la structure statPtr est remplie de données. Sinon, il retourne -1 et aucune information de statistiques n'est fournie. Tcl_FSOpenFileChannel ouvre un fichier spécifié par pathPtr et retourne un handle de canal qui peut être utilisé pour effectuer des entrées et sorties dans le fichier. Cette API est un modèle de la fonction fopen de la bibliothèque d'entrée/sortie du système Unix. La syntaxe et la signification des arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannel retourne NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannel laisse un message d'erreur dans le résultat de interp après toute erreur. Le canal nouvellement créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez Tcl_RegisterChannel. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, l'action de création du nouveau canal l'assigne également comme substitut du canal standard correspondant. Tcl_FSGetCwd remplace la version de la fonction getcwd de la bibliothèque. Retourne le répertoire de travail actuel de la bibliothèque Tcl. Cela peut être différent du répertoire de travail natif, lorsque le répertoire de travail actuel n'est pas dans le système de fichiers natif. Le résultat est un pointeur vers un objet Tcl Tcl_Obj spécifiant le répertoire actuel, ou NULL si le répertoire actuel ne peut pas être déterminé. Si NULL est retourné, un message d'erreur est laissé dans le résultat de interp. Le résultat a déjà son compteur de référence incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compteur de référence doit être décrémenté. Ceci est nécessaire pour la sécurité des threads, afin que plusieurs threads puissent accéder à cette fonction et aux fonctions associées, tout en garantissant que les résultats sont toujours valides. Tcl_FSChdir remplace la version de la fonction chdir de la bibliothèque. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl se rabat sur une combinaison de stat et access pour vérifier si le répertoire existe et possède les permissions adéquates. Pour les résultats, voir la documentation de chdir. En cas de succès, un enregistrement du chemin réussi est conservé dans cwdPathPtr pour les appels ultérieurs à Tcl_FSGetCwd. Tcl_FSPathSeparator retourne le caractère séparateur pour l'élément le plus spécifique du chemin spécifié par pathPtr (c'est-à-dire le dernier segment du chemin). Le séparateur est retourné sous forme d'objet Tcl avec une chaîne de longueur 1. Si le chemin est invalide, NULL est retourné. Tcl_FSJoinPath prend l'objet Tcl donné, qui doit être une liste valide (qui peut avoir un compteur de référence zéro), et retourne la valeur du chemin en considérant les elements premiers éléments comme des segments de chemin valides (chaque segment peut être un chemin complet, un chemin partiel ou juste un nom de répertoire ou de fichier). Si un segment de chemin est réellement un chemin absolu, tous les segments précédents sont ignorés. Si elements est inférieur à 0, l'entier complet est utilisé. Il est possible que la valeur retournée soit réellement un élément de la liste donnée, le chargeur doit donc faire attention à incrémenter le compteur de référence de la valeur avant de libérer la liste. La valeur retournée, généralement avec un compteur de référence de zéro (mais pouvant être partagée sous certaines conditions), contient le chemin joint. L'appelant doit ajouter un compteur de référence à la valeur avant de l'utiliser. En particulier, la valeur retournée pourrait être un élément de la liste donnée, donc la libération de la liste pourrait libérer la valeur prématurément si aucun compteur de référence n'a été pris. Si le nombre d'éléments est zéro, la valeur retournée sera une chaîne vide Tcl_Obj. Tcl_FSSplitPath prend l'objet Tcl donné, qui devrait être un chemin valide, et retourne une valeur de liste Tcl contenant chaque segment de ce chemin comme élément. Il retourne une valeur de liste avec un compteur de référence de zéro. Si le lenPtr passé n'est pas NULL, la variable pointée sera mise à jour pour contenir le nombre d'éléments dans la liste retournée. Tcl_FSEqualPaths teste si les deux chemins donnés représentent le même objet de système de fichiers. Il retourne 1 s'ils sont égaux, 0 s'ils sont différents. Si l'un des chemins est NULL, 0 est toujours retourné. Tcl_FSGetNormalizedPath tente d'extraire d'un objet Tcl une représentation normalisée unique, dont la valeur de chaîne peut être utilisée comme identifiant unique pour le fichier. Retourne la représentation normalisée du chemin, propriété de Tcl, ou NULL si le chemin était invalide ou n'a pas pu être converti avec succès. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère en interne sur ces représentations), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques ne soit pas nécessairement la version la plus conviviale d'un chemin. La valeur retournée est propriété de Tcl et a une durée de vie équivalente à celle du pathPtr passé (sauf si c'est un chemin relatif, auquel cas la valeur normalisée peut être libérée dès que le cwd change) - l'appelant peut incrémenter le compteur de référence s'il le souhaite pour conserver une copie plus longtemps. Tcl_FSJoinToPath prend la valeur donnée, qui devrait généralement être un chemin valide ou NULL, et la joint avec le tableau de segments de chemin donnés. Retourne une valeur, généralement avec un compteur de référence de zéro (mais pouvant être partagée sous certaines conditions), contenant le chemin joint. L'appelant doit ajouter un compteur de référence à la valeur avant de l'utiliser. Si l'une des valeurs passées à cette fonction (pathPtr ou éléments de path) a un compteur de référence de zéro, celles-ci seront libérées lorsque cette fonction retournera la valeur. Tcl_FSConvertToPathType tente de convertir l'objet Tcl donné en un type de chemin valide, en tenant compte que le cwd a pu changer même si cette valeur est déjà du bon type. Le nom du fichier peut commencer par ~ (pour indiquer le répertoire utilisateur actuel) ou ~ (pour indiquer le répertoire de n'importe quel utilisateur). Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), TCL_OK est retourné. Sinon, TCL_ERROR est retourné, et un message d'erreur peut être laissé dans l'interpréteur. Tcl_FSGetInternalRep extrait la représentation interne d'une valeur de chemin donnée dans le système de fichiers spécifié. Si la valeur du chemin appartient à un système de fichiers différent, NULL est retourné. Si la représentation interne est actuellement NULL, il tente de la générer en appelant le Tcl_FSCreateInternalRepProc du système de fichiers. Retourne NULL ou une représentation valide du chemin interne. Cette représentation interne est mise en cache, donc les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. Tcl_FSGetTranslatedPath tente d'extraire le chemin traduit à partir de l'objet Tcl donné. Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), la valeur est retournée. Sinon, NULL est retourné, et un message d'erreur peut être laissé dans l'interpréteur. Un chemin traduit est un chemin qui ne contient pas ~ ou ~utilisateur (ceux-ci ont été développés en leur représentation actuelle dans le système de fichiers). La valeur retournée est la propriété de l'appelant, qui doit la conserver ou appeler Tcl_DecrRefCount pour s'assurer que l'espace est libéré. Cette fonction a peu d'utilité pratique, et Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement des fonctions plus utiles pour de nombreux usages. Tcl_FSGetTranslatedStringPath fait la même chose que Tcl_FSGetTranslatedPath, mais retourne une chaîne ou NULL. La chaîne retournée est dynamique et Situé et détenu par l'appelant, qui doit le stocker ou appeler ckfree pour s'assurer qu'il est libéré. Encore une fois, Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des besoins.

Tcl_FSNewNativePath effectue quelque chose comme l'inverse des conversions habituelles obj->path->représentation native. Si un code récupère un chemin sous forme native (depuis, par exemple, readlink ou une boîte de dialogue native), et que ce chemin doit être utilisé au niveau Tcl, alors appeler cette fonction est un moyen efficace de créer le type de valeur de chemin approprié.

La valeur résultante est une valeur de type « chemin » pure, qui ne recevra une représentation sous forme de chaîne UTF-8 que si cela est requis par un certain code Tcl.

Tcl_FSGetNativePath est destiné à être utilisé par les systèmes de fichiers natifs Win/Unix, de sorte qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un wrapper de commodité autour de Tcl_FSGetInternalRep. Il peut être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes (par exemple, sur macOS, une représentation utilisant une structure FSRef de fileSpec serait probablement plus efficace). Sous Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Actuellement, la représentation est simplement une chaîne de caractères qui peut contenir soit le chemin relatif, soit un chemin absolu et normalisé dans le codage natif (des conditions complexes dictent lequel de ceux-ci sera fourni, donc aucun ne peut être garanti, sauf si le chemin est connu pour être absolu). Si vous avez besoin d'un chemin natif qui doit être absolu, vous devriez demander la version native d'un chemin normalisé. Si pour une raison quelconque une version non absolue et non normalisée du chemin est nécessaire, cela doit être construit séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache de sorte que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle du *pathPtr* passé (sauf s'il s'agit d'un chemin relatif, auquel cas la représentation native peut être libérée à tout moment où le cwd change).

Tcl_FSFileSystemInfo renvoie une liste de deux éléments. Le premier élément est le nom du système de fichiers (par exemple, « natif », « vfs », « zip », ou « prowrap », peut-être), et le second est le type particulier du chemin donné dans ce système de fichiers (qui dépend du système de fichiers). Le second élément peut être vide si le système de fichiers ne fournit pas de catégorisation supplémentaire des fichiers.

Une valeur de liste valide est renvoyée, sauf si la valeur du chemin n'est pas reconnue, auquel cas NULL sera renvoyé.

Tcl_FSGetFileSystemForPath renvoie un pointeur vers le Tcl_Filesystem qui accepte ce chemin comme valide.

Si aucun système de fichiers n'accepte le chemin, NULL est renvoyé.

Tcl_FSGetPathType détermine si le chemin donné est relatif au répertoire courant, relatif au volume courant, ou absolu.

Il renvoie l'un des TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, ou TCL_PATH_VOLUME_RELATIVE

API DES SYSTÈMES DE FICHIERS VIRTUELS

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un système de fichiers ; ces opérations sont invoquées au besoin par la couche générique, ce qui se produit généralement via les fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et une donnée optionnelle à associer à ce système de fichiers. Lors de l'appel de cette fonction, Tcl attachera le système de fichiers à la liste des systèmes de fichiers connus, et il deviendra pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera renvoyé.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et renvoie TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est renvoyé.

Tcl_FSData renverra le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il renverra NULL.

Tcl_FSMountsChanged est utilisé pour informer le cœur de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

LA STRUCTURE TCL_FILESYSTEM

La structure Tcl_Filesystem contient les champs suivants :

typedef struct Tcl_Filesystem {
    const char *typeName;
    int structureLength;
    Tcl_FSVersion version;
    Tcl_FSPathInFilesystemProc *pathInFilesystemProc;
    Tcl_FSDupInternalRepProc *dupInternalRepProc;
    Tcl_FSFreeInternalRepProc *freeInternalRepProc;
    Tcl_FSInternalToNormalizedProc *internalToNormalizedProc;
    Tcl_FSCreateInternalRepProc *createInternalRepProc;
    Tcl_FSNormalizePathProc *normalizePathProc;
    Tcl_FSFilesystemPathTypeProc *filesystemPathTypeProc;
    Tcl_FSFilesystemSeparatorProc *filesystemSeparatorProc;
    Tcl_FSStatProc *statProc;
    Tcl_FSAccessProc *accessProc;
    Tcl_FSOpenFileChannelProc *openFileChannelProc;
    Tcl_FSMatchInDirectoryProc *matchInDirectoryProc;
    Tcl_FSUtimeProc *utimeProc;
    Tcl_FSLinkProc *linkProc;
    Tcl_FSListVolumesProc *listVolumesProc;
    Tcl_FSFileAttrStringsProc *fileAttrStringsProc;
    Tcl_FSFileAttrsGetProc *fileAttrsGetProc;
    Tcl_FSFileAttrsSetProc *fileAttrsSetProc;
    Tcl_FSCreateDirectoryProc *createDirectoryProc;
    Tcl_FSRemoveDirectoryProc *removeDirectoryProc;
    Tcl_FSDeleteFileProc *deleteFileProc;
    Tcl_FSCopyFileProc *copyFileProc;
    Tcl_FSRenameFileProc *renameFileProc;
    Tcl_FSCopyDirectoryProc *copyDirectoryProc;
    Tcl_FSLstatProc *lstatProc;
    Tcl_FSLoadFileProc *loadFileProc;
    Tcl_FSGetCwdProc *getCwdProc;
    Tcl_FSChdirProc *chdirProc;
} Tcl_Filesystem;

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche générique du système de fichiers pour effectuer la gamme complète d'actions liées aux systèmes de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (dont la quasi-totalité doit être implémentée), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni) et fonctions d'efficacité (qui ne doivent être implémentées que si elles peuvent l'être efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces substitutions ne sont utilisées que pour gérer les commandes initiées dans Tcl, pas dans C. Ce que cela signifie, c'est que si une commande file rename est émise dans Tcl, et que les systèmes de fichiers pertinents n'implémentent pas leur *Tcl_FSRenameFileProc*, le cœur de Tcl se rabattra alors sur une combinaison d'autres fonctions de système de fichiers (il utilisera *Tcl_FSCopyFileProc* suivi de *Tcl_FSDeleteFileProc*, et si *Tcl_FSCopyFileProc* n'est pas implémenté, il y aura une autre substitution). Cependant, si une commande *Tcl_FSRenameFileProc* est émise au niveau C, aucune de ces substitutions ne se produit. Il en est ainsi sauf pour les quatre dernières entrées du tableau des systèmes de fichiers (*lstat*, *load*, *getcwd* et *chdir*) pour lesquelles des substitutions se produisent effectivement au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme Tcl_Obj prennent ces noms sous forme UTF-8. L'API d'infrastructure du système de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

INFRASTRUCTURE DU SYSTÈME DE FICHIERS

Ces champs contiennent des informations de base sur la structure du système de fichiers et les adresses des fonctions utilisées pour associer un système de fichiers particulier à un chemin de fichier, et pour gérer le traitement interne des représentations de chemin, par exemple la copie et la libération de ces représentations.

NOM DU TYPE

Le champ typeName contient une chaîne de caractères terminée par null qui identifie le type du système de fichiers implémenté, par exemple “native”, “zip” ou “vfs”.

LONGUEUR DE LA STRUCTURE

Le champ structureLength est généralement implémenté comme sizeof(Tcl_Filesystem), et est là pour permettre une meilleure compatibilité ascendante binaire si la taille de la structure change dans une future version de Tcl.

VERSION

Le champ version doit être défini sur TCL_FILESYSTEM_VERSION_1.

PROCÉDURE CHEMIN DANS SYSTÈME DE FICHIERS

Le champ pathInFilesystemProc contient l'adresse d'une fonction qui est appelée pour déterminer si une valeur de chemin donnée appartient à ce système de fichiers ou non. Tcl n'appellera les autres fonctions du système de fichiers qu'avec un chemin pour lequel cette fonction a renvoyé TCL_OK. Si le chemin n'appartient pas, -1 doit être renvoyé (le comportement de Tcl pour toute autre valeur de retour n'est pas défini). Si TCL_OK est renvoyé, alors le paramètre de sortie optionnel clientDataPtr peut être utilisé pour renvoyer une représentation interne (spécifique au système de fichiers) du chemin, qui sera mise en cache dans la valeur du chemin, et pourra être récupérée efficacement par les autres fonctions du système de fichiers. Tcl mettra simultanément en cache le fait que ce chemin appartient à ce système de fichiers. Ces caches sont invalidés lorsque les structures de système de fichiers sont ajoutées ou supprimées de la liste interne des systèmes de fichiers connus de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROCÉDURE DUPLICATION REPRÉSENTATION INTERNE

Cette fonction crée une copie de la représentation interne d'un chemin et est appelée lorsque Tcl a besoin de dupliquer une valeur de chemin. Si elle est nulle, Tcl ne copiera tout simplement pas la représentation interne, qui pourra alors devoir être régénérée plus tard.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

PROCÉDURE LIBÉRATION REPRÉSENTATION INTERNE

Libère la représentation interne. Ceci doit être implémenté si les représentations internes nécessitent une libération (c'est-à-dire si de la mémoire est allouée lorsqu'une représentation interne est générée), mais peut sinon être nulle.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

PROCÉDURE INTERNE VERS NORMALISÉ

Fonction pour convertir la représentation interne en un chemin normalisé. Nécessaire uniquement si le système de fichiers crée des valeurs de chemin pures sans représentation textuelle/chemin. La valeur de retour est une valeur Tcl dont la représentation textuelle est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

PROCÉDURE CRÉATION REPRÉSENTATION INTERNE

Fonction pour prendre une valeur de chemin, calculer une représentation interne pour celle-ci, et stocker cette représentation native dans la valeur. Peut être nulle si les chemins n'ont pas de représentation interne, ou si la fonction Tcl_FSPathInFilesystemProc pour ce système de fichiers crée toujours immédiatement une représentation interne pour les chemins qu'elle accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

PROCÉDURE NORMALISATION CHEMIN

Fonction pour normaliser un chemin. Devrait être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations textuelles pour la même valeur de chemin. Dans Tcl, chaque “chemin” doit avoir une représentation textuelle “normalisée” unique. Selon le système de fichiers, il peut y avoir plus d'une représentation textuelle non normalisée qui fait référence à ce chemin (par exemple, un chemin relatif, un chemin avec une casse de caractères différente si le système de fichiers ne distingue pas la casse, un chemin contenant une référence à un répertoire personnel tel que “~”, un chemin contenant des liens symboliques, etc.). Si le tout dernier composant du chemin est un lien symbolique, il ne doit pas être converti en la valeur qu'il pointe (mais sa casse ou d'autres aspects doivent être rendus uniques). Tous les autres composants du chemin doivent être convertis à partir de liens symboliques. Cette unique exception est nécessaire pour être conforme aux sémantiques de Tcl avec file delete, file rename, file copy opérant sur des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint soit au début du chemin (c'est-à-dire zéro), soit à la fin du chemin, soit à un séparateur de fichier intermédiaire dans le chemin. Il ne pointera jamais vers une autre position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS DU SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui est censé être utilisé avec l'ensemble complet des commandes standard de Tcl doit implémenter toutes celles-ci. Si certaines d'entre elles ne sont pas implémentées, certaines commandes Tcl peuvent échouer lors de l'opération sur des chemins appartenant à ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques n'a pas besoin d'implémenter la fonction readlink, etc. Le noyau Tcl s'attend à ce que les systèmes de fichiers se comportent de cette manière).

PROCÉDURE TYPE CHEMIN SYSTÈME DE FICHIERS

Fonction pour déterminer le type d'un chemin dans ce système de fichiers. Peut être nulle, auquel cas aucune information de type ne sera disponible pour les utilisateurs du système de fichiers. Le “type” est utilisé uniquement à des fins d'information, et doit être renvoyé comme la représentation textuelle de l'objet Tcl renvoyé. Une valeur de retour typique pourrait être “networked”, “zip” ou “ftp”. L'objet Tcl résultant est la propriété du système de fichiers et Tcl incrémentera donc le compteur de références de cette valeur s'il souhaite en conserver une référence.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(

PROCÉDURE STAT

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes au niveau Tcl en dépendent crucialement (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La fonction Tcl_FSStatProc remplit la structure stat statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure stat inclut des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification et l'heure de la dernière modification des métadonnées.

Si le fichier représenté par pathPtr existe, la fonction Tcl_FSStatProc renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé et aucune information de stat n'est fournie.

PROCÉDURE ACCÈS

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes au niveau Tcl en dépendent crucialement (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La fonction Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est dans pathPtr. Si le nom de chemin fait référence à un lien symbolique, alors les permissions du fichier auquel fait référence ce lien symbolique doivent être testées.

En cas de succès (toutes les permissions demandées accordées), zéro est renvoyé. En cas d'erreur (au moins un bit dans mode demandait une permission qui est refusée, ou une autre erreur s'est produite), -1 est renvoyé.

PROCÉDURE OUVRIR CANAL FICHIER

OPENFILECHANNELPROC

Fonction pour traiter un appel à Tcl_FSOpenFileChannel. Elle doit être implémentée pour tout système de fichiers raisonnable, car toute opération qui nécessite l'ouverture ou l'accès au contenu d'un fichier utilisera cette fonction (par exemple, open, encoding, et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

La Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et renvoie un descripteur de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est modelée d'après la fonction fopen de la bibliothèque d'entrée/sortie standard Unix. La syntaxe et la signification des arguments sont similaires à celles données dans la commande Tcl open, où mode est une combinaison des drapeaux POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, la Tcl_FSOpenFileChannelProc renvoie NULL et enregistre un code d'erreur POSIX qui peut être obtenu avec Tcl_GetErrno. De plus, si interp n'est pas nul, la Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le canal nouvellement créé ne doit pas être enregistré dans l'interpréteur par une Tcl_FSOpenFileChannelProc ; ce travail incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, l'action de créer le nouveau canal l'assigne également comme remplacement du canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, la fonctionnalité de glob et de copie récursive sera manquante dans le système de fichiers (et cela peut affecter des commandes comme encoding names qui utilisent la fonctionnalité de glob).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit renvoyer tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au modèle donné et satisfont la spécification types. La fonction peut être appelée de deux manières. Si pattern est NULL, pathPtr est une spécification complète d'un fichier ou d'un répertoire qui doit être vérifié pour son existence et son type. Sinon, pathPtr est un répertoire, et la fonction doit rechercher des fichiers ou des répertoires du type correct. Dans tous les cas, pathPtr peut être supposé à la fois non nul et non vide. Il n'est pas documenté si pathPtr a un séparateur de fichier à la fin, donc le code doit être flexible aux deux possibilités.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de correspondance. Les messages d'erreur sont placés dans interp, sauf si interp est NULL, auquel cas aucun message d'erreur n'est généré ; en cas de résultat TCL_OK, les résultats doivent être ajoutés à la valeur resultPtr donnée (qui peut être supposée être une liste Tcl non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (ce qui indique généralement qu'il s'agira de spécifications de chemin absolu). Remarque : si aucune correspondance n'est trouvée, un résultat vide est simplement produit ; les erreurs ne sont signalées que pour les problèmes réels de fichiers ou de systèmes de fichiers qui peuvent survenir pendant le processus de correspondance.

La structure Tcl_GlobTypeData passée dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Types mac acceptés */
    Tcl_Obj *macType;
    /* Créateurs mac acceptés */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de gérer correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT sont vrais (et en particulier lorsque les autres drapeaux sont faux). Dans le premier cas, la fonction doit énumérer les répertoires contenus. Tcl utilise cela pour implémenter le globbing récursif, il est donc essentiel que les systèmes de fichiers implémentent correctement la correspondance de répertoires. Dans le second cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit énumérer les points de montage trouvés dans le répertoire donné par pathPtr (et dans ce cas, pathPtr n'a pas besoin d'être dans le même système de fichiers - contrairement à tous les autres cas où cette fonction est appelée). Le support pour cela est essentiel si Tcl doit effectuer des transitions fluides entre les systèmes de fichiers.

UTIMEPROC

Fonction pour traiter un appel à Tcl_FSUtime. Elle est nécessaire pour permettre la configuration (pas la lecture) des dates de dernière modification et de dernier accès d'un fichier, ainsi que pour l'implémentation de file copy avec open-r/open-w/fcopy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les dates d'accès et de modification du fichier spécifié par pathPtr doivent être changées aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec le système utime.

LINKPROC

Fonction pour traiter un appel à Tcl_FSLink. Elle doit être implémentée uniquement si le système de fichiers supporte les liens, et peut être NULL dans les autres cas.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est sollicitée pour lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien ne peut être lu. Le résultat est la responsabilité de l'appelant (et doit donc voir son compteur de références incrémenté avant d'être renvoyé). Tout appelant doit appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'en a plus besoin. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Dans ce cas, le résultat doit être toPtr si le lien a réussi et NULL sinon. Dans ce cas, le résultat n'est pas la responsabilité de l'appelant (c'est-à-dire qu'aucune manipulation du compteur de références n'est nécessaire des deux côtés). Voir la documentation de Tcl_FSLink pour interpréter correctement les drapeaux de linkAction.

LISTVOLUMESPROC

Fonction pour lister tous les volumes de systèmes de fichiers ajoutés par ce système de fichiers. Elle ne doit être implémentée que si le système de fichiers ajoute des volumes en tête du système de fichiers, afin qu'ils puissent être renvoyés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste de volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. La valeur de retour est considérée comme appartenant au système de fichiers (pas au cœur de Tcl), mais doit se voir attribuer un compteur de références pour Tcl. Tcl utilisera le contenu de la liste, puis décrémentera ce compteur de références. Cela permet aux systèmes de fichiers de choisir s'ils veulent réellement conserver une "liste globale" de volumes ou non (si c'est le cas, ils génèrent la liste en temps réel et la transmettent à Tcl avec un compteur de références de 1, puis oublient la liste ; si non, ils incrémentent simplement le compteur de références de leur liste globale et la transmettent à Tcl qui copiera le contenu puis décrémentera le compteur pour le ramener à son état initial).

Par conséquent, Tcl considère les valeurs de retour de cette proc comme en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne supportera pas la commande file attributes. Cela permet d'ajouter des informations arbitraires supplémentaires aux fichiers dans le système de fichiers. Si elle n'est pas implémentée, les méthodes get et set n'ont pas besoin d'être implémentées.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

L'appel peut renvoyer un tableau de chaînes, ou peut renvoyer NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Après avoir fini de l'utiliser, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être libérée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si elle ne doit pas être libérée, le système de fichiers doit garantir qu'il renvoie une valeur avec un compteur de références d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsGet, utilisé par file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Renvoie un code de retour standard. La valeur de la propriété de l'attribut obtenue, correspondant à l'élément d'indice index dans la liste renvoyée par la fonction Tcl_FSFileAttrStringsProc, est placée dans objPtrRef (si TCL_OK a été renvoyé). Cette valeur est probablement de référence zéro. Quel que soit le cas, nous devons la stocker quelque part (par exemple, dans le résultat Tcl), ou incrémenter/décrémenter son compteur de références pour assurer sa libération appropriée.

FILEATTRSSETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsSet, utilisé par file attributes. Si le système de fichiers est en lecture seule, il n'est pas nécessaire de l'implémenter.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

La propriété de la valeur de l'élément d'indice index dans la liste renvoyée par la fonction Tcl_FSFileAttrStringsProc doit être définie à la valeur donnée par objPtr.

CREATEDIRECTORYPROC

Fonction pour créer un répertoire dans le système de fichiers. La procédure est indiquée ci-dessous.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode);

La fonction doit créer un répertoire avec le mode donné. Si le mode est TCL_FS_CREATE_DIR, un répertoire doit être créé et un descripteur de canal doit être renvoyé. Si le mode est TCL_FS_CREATE_FILE, un fichier doit être créé et un descripteur de canal doit être renvoyé. Si le mode est TCL_FS_CREATE_LINK, un lien doit être créé et un descripteur de canal doit être renvoyé.

DESCRIPTION

Tcl fournit une interface abstraite pour interagir avec le système de fichiers. Cette interface permet aux applications Tcl d'utiliser différents systèmes de fichiers virtuels (VFS) comme s'ils étaient le système de fichiers natif. L'implémentation principale de cette interface est généralement le système de fichiers natif, mais d'autres systèmes de fichiers peuvent être greffés dessus.

Les fonctions listées ici sont des pointeurs de fonction qui composent la structure Tcl_Filesystem. Chaque système de fichiers enregistré auprès de Tcl fournit une telle structure, contenant des pointeurs vers des fonctions qui implémentent les opérations de base du système de fichiers.

Les fonctions de l'API du système de fichiers Tcl sont généralement appelées par les commandes Tcl de haut niveau comme file, open, source, load, etc. L'application Tcl n'appelle généralement pas directement ces fonctions de bas niveau, mais elles sont cruciales pour l'implémentation de l'interface du système de fichiers.

OPÉRATIONS DE LECTURE SEULE

Ces fonctions sont utilisées pour lire des informations du système de fichiers. Elles doivent être implémentées par tous les systèmes de fichiers, y compris ceux qui sont en lecture seule.

STATPROC

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée par tous les systèmes de fichiers.

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statBuf);

La fonction remplit la structure statBuf avec des informations sur le fichier ou le répertoire spécifié par pathPtr. La valeur de retour est un code de résultat Tcl standard indiquant si une erreur s'est produite.

ACCESSPROC

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée par tous les systèmes de fichiers.

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La fonction vérifie les permissions d'accès spécifiées par mode (par exemple, R_OK, W_OK, X_OK) pour le chemin spécifié par pathPtr. La valeur de retour est un code de résultat Tcl standard.

OPENFILEPROC

Fonction pour traiter un appel Tcl_FSOpenFile. Doit être implémentée par tous les systèmes de fichiers qui peuvent ouvrir des fichiers pour la lecture ou l'écriture.

typedef Tcl_Obj *Tcl_FSOpenFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_Obj *flagsPtr);

La fonction ouvre le fichier spécifié par pathPtr avec les indicateurs spécifiés par flagsPtr et renvoie un objet Tcl représentant le canal ouvert. Si une erreur se produit, elle renvoie NULL et laisse un message d'erreur dans le résultat de l'interpréteur.

OPENPIPEPROC

Fonction pour traiter un appel Tcl_FSOpenPipe. Permet d'ouvrir des canaux de type pipe.

typedef int Tcl_FSOpenPipeProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int bufferSize,
        Tcl_Channel *chanPtr);

Ouvre un pipe associé au chemin spécifié. Les arguments mode et bufferSize contrôlent le comportement du pipe. Le canal résultant est placé dans chanPtr. La valeur de retour est un code de résultat Tcl standard.

CLOSEPROC

Fonction pour traiter un appel Tcl_FSClose. Doit être implémentée par tous les systèmes de fichiers qui prennent en charge l'ouverture de fichiers.

typedef int Tcl_FSCloseProc(
        Tcl_Channel chan);

Ferme le canal spécifié par chan. La valeur de retour est un code de résultat Tcl standard.

COPYPROC

Fonction pour traiter un appel Tcl_FSCopy. Utilisée pour copier le contenu d'un canal à un autre.

typedef int Tcl_FSCopyProc(
        Tcl_Channel srcChan,
        Tcl_Channel destChan);

Copie le contenu du canal source srcChan vers le canal de destination destChan. La valeur de retour est un code de résultat Tcl standard.

COMPANYNAMEPROC

Fonction pour obtenir le nom canonique d'un chemin. Utile pour les systèmes de fichiers qui ont des représentations de chemins multiples.

typedef Tcl_Obj *Tcl_FSCompanyNameProc(
        Tcl_Obj *pathPtr);

Renvoie un objet Tcl contenant le nom canonique du chemin spécifié par pathPtr. Peut être NULL si le nom canonique ne peut pas être déterminé ou si cette fonctionnalité n'est pas prise en charge.

OPÉRATIONS DÉJÀ IMPLEMENTÉES

Ces fonctions sont implémentées par le système de fichiers natif de Tcl. Elles n'ont pas besoin d'être implémentées à moins que le système de fichiers ne puisse offrir une implémentation plus efficace ou différente.

CREATEDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSCreateDirectory. Doit être implémentée sauf si le système de fichiers est en lecture seule.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

La valeur de retour est un code de résultat Tcl standard indiquant si une erreur s'est produite dans le processus. En cas de succès, un nouveau répertoire devrait avoir été ajouté au système de fichiers à l'emplacement spécifié par pathPtr.

REMOVEDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSRemoveDirectory. Doit être implémentée sauf si le système de fichiers est en lecture seule.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

La valeur de retour est un code de résultat Tcl standard indiquant si une erreur s'est produite dans le processus. En cas de succès, le répertoire spécifié par pathPtr devrait avoir été supprimé du système de fichiers. Si l'indicateur recursive est donné, alors un répertoire non vide devrait être supprimé sans erreur. Si cet indicateur n'est pas donné et que le répertoire est non vide, une erreur POSIX "EEXIST" devrait être signalée. Si une erreur se produit, le nom du fichier ou du répertoire qui a causé l'erreur doit être placé dans errorPtr.

DELETEFILEPROC

Fonction pour traiter un appel Tcl_FSDeleteFile. Doit être implémentée sauf si le système de fichiers est en lecture seule.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

La valeur de retour est un code de résultat Tcl standard indiquant si une erreur s'est produite dans le processus. En cas de succès, le fichier spécifié par pathPtr devrait avoir été supprimé du système de fichiers. Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non Tcl_FSRemoveDirectoryProc lorsqu'il est nécessaire de les supprimer (même s'il s'agit de liens symboliques vers des répertoires).

EFFICACITÉ DU SYSTÈME DE FICHIERS

Ces fonctions n'ont pas besoin d'être implémentées pour un système de fichiers particulier car le cœur de Tcl dispose d'une implémentation de secours. Voir la description de chaque fonction individuelle pour les conséquences de laisser le champ à NULL.

LSTATPROC

Fonction pour traiter un appel Tcl_FSLstat. Si elle n'est pas implémentée, Tcl tentera d'utiliser la fonction statProc définie ci-dessus à la place. Par conséquent, elle n'a besoin d'être implémentée que si un système de fichiers peut différencier les appels stat et lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le comportement de cette fonction est très similaire à celui de Tcl_FSStatProc défini ci-dessus, sauf que si elle est appliquée à un lien symbolique, elle renvoie des informations sur le lien, et non sur le fichier cible.

COPYFILEPROC

Fonction pour traiter un appel Tcl_FSCopyFile. Si elle n'est pas implémentée, Tcl utilisera un mécanisme de copie basé sur open-r, open-w et fcopy. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un code de résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de copie. Notez que destPathPtr est le nom du fichier qui doit devenir la copie de srcPathPtr. Ce n'est jamais le nom d'un répertoire dans lequel srcPathPtr pourrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande Tcl de haut niveau file copy). Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non copyDirectoryProc lorsqu'il est nécessaire de les copier (même s'il s'agit de liens symboliques vers des répertoires). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file copy, l'appel de Tcl_SetErrno(EXDEV) et le retour d'un résultat non TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standards.

RENAMEFILEPROC

Fonction pour traiter un appel Tcl_FSRenameFile. Si elle n'est pas implémentée, Tcl utilisera un mécanisme de copie et de suppression. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un code de résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de renommage. Si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file rename, l'appel de Tcl_SetErrno(EXDEV) et le retour d'un résultat non TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standards.

COPYDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSCopyDirectory. Si elle n'est pas implémentée, Tcl utilisera un mécanisme récursif de file mkdir et file copy. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

La valeur de retour est un code de résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de copie. Si une erreur se produit, le nom du fichier ou du répertoire qui a causé l'erreur doit être placé dans errorPtr. Notez que destPathPtr est le nom du répertoire qui doit devenir le miroir de srcPathPtr. Ce n'est pas le nom d'un répertoire dans lequel srcPathPtr doit être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande Tcl de haut niveau file copy). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de copie de répertoire, l'appel de Tcl_SetErrno(EXDEV) et le retour d'un résultat non TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standards.

LOADFILEPROC

Fonction pour traiter un appel Tcl_FSLoadFile. Si elle n'est pas implémentée, Tcl utilisera une copie vers un fichier temporaire natif suivie d'un appel Tcl_FSLoadFile sur cette copie temporaire. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut charger du code directement, ou si elle peut être implémentée simplement pour retourner TCL_ERROR afin de désactiver complètement la fonctionnalité de chargement dans ce système de fichiers.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Renvoie un code de complétion Tcl standard. En cas d'erreur, un message d'erreur est laissé dans le résultat de l'interpréteur. La fonction charge dynamiquement un fichier de code binaire en mémoire. En cas de chargement réussi, handlePtr doit être rempli avec un jeton pour le fichier chargé dynamiquement, et unloadProcPtr doit être rempli avec l'adresse d'une procédure. La procédure de déchargement sera appelée avec le Tcl_LoadHandle donné comme seul paramètre lorsque Tcl aura besoin de décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle renvoyé est actuellement un jeton qui peut être utilisé dans le TclpFindSymbol privé pour accéder aux fonctions du nouveau code. Chaque système de fichiers est libre de définir le Tcl_LoadHandle selon ses besoins. Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de chargement de fichier, l'appel de Tcl_SetErrno(EXDEV) et le retour d'un résultat non TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standards.

UNLOADFILEPROC

Fonction pour décharger un fichier précédemment chargé avec succès. Si le chargement a été implémenté, alors celui-ci doit également l'être, s'il y a une action de nettoyage requise.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Fonction pour traiter un appel Tcl_FSGetCwd. La plupart des systèmes de fichiers n'ont pas besoin de l'implémenter. Elle ne sera généralement appelée qu'une seule fois, si getcwd est appelé avant chdir. Peut être NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si le système de fichiers prend en charge une notion native de répertoire de travail courant (qui pourrait peut-être changer indépendamment de Tcl), cette fonction doit renvoyer ce répertoire courant comme résultat, ou NULL si le répertoire courant n'a pas pu être déterminé (par exemple, l'utilisateur n'a pas les permissions appropriées sur le répertoire courant). Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de l'interpréteur.

CHDIRPROC

Fonction pour traiter un appel Tcl_FSChdir. Si les systèmes de fichiers n'implémentent pas cela, cela sera émulé par une série de vérifications d'accès aux répertoires. Sinon, les systèmes de fichiers virtuels qui l'implémentent n'ont besoin de répondre avec un résultat positif que si pathPtr est un répertoire valide et accessible dans leur système de fichiers. Ils n'ont pas besoin de mémoriser le résultat, car celui-ci sera automatiquement mémorisé pour une utilisation par Tcl_FSGetCwd. Les systèmes de fichiers réels doivent effectuer l'action correcte (c'est-à-dire appeler la bonne API système chdir).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

Le Tcl_FSChdirProc change le répertoire de travail courant de l'application pour la valeur spécifiée dans pathPtr. La fonction renvoie -1 en cas d'erreur ou 0 en cas de succès.
