INTRODUCTION

Les interfaces décrites ici sont utilisées pour personnaliser la boucle d'événements Tcl. Les deux personnalisations les plus courantes sont l'ajout de nouvelles sources d'événements et la fusion de la boucle d'événements de Tcl avec une autre boucle d'événements, telle que celle fournie par une application dans laquelle Tcl est intégrée. Chacune de ces tâches est décrite dans une section distincte ci-dessous.

Les procédures de cette entrée de manuel sont les éléments de base à partir desquels le notifier d'événements Tcl est construit. Le notifier d'événements est la couche la plus basse du mécanisme d'événements Tcl. Il se compose de trois choses :

[1]
Sources d'événements : celles-ci représentent les moyens par lesquels les événements peuvent être générés. Par exemple, il existe une source d'événements de minuterie qui implémente la procédure Tcl_CreateTimerHandler et la commande after, et il existe une source d'événements de fichier qui implémente la procédure Tcl_CreateFileHandler sur les systèmes Unix. Une source d'événements doit travailler avec le notifier pour détecter les événements aux moments opportuns, les enregistrer dans la file d'attente des événements et, finalement, notifier le logiciel de niveau supérieur qu'ils se sont produits. Les procédures Tcl_CreateEventSource, Tcl_DeleteEventSource, Tcl_SetMaxBlockTime, Tcl_QueueEvent, et Tcl_DeleteEvents sont principalement utilisées par les sources d'événements.
[2]
La file d'attente des événements : pour les applications non multithread, il existe une seule file pour l'ensemble de l'application, contenant les événements qui ont été détectés mais pas encore traités. Les sources d'événements placent les événements dans la file d'attente afin qu'ils puissent être traités en ordre à des moments appropriés pendant la boucle d'événements. La file d'attente des événements garantit une discipline équitable de traitement des événements, de sorte qu'aucune source d'événements ne puisse affamer les autres. Elle permet également de sauvegarder des événements pour un traitement ultérieur. Les applications multithread fonctionnent de manière similaire, sauf qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. Tcl_QueueEvent est utilisé (principalement par les sources d'événements) pour ajouter des événements à la file d'attente des événements et Tcl_DeleteEvents est utilisé pour supprimer des événements de la file d'attente sans les traiter. Dans une application multithread, Tcl_QueueEvent ajoute un événement à la file d'attente du thread courant, et Tcl_ThreadQueueEvent ajoute un événement à la file d'attente d'un thread spécifique.
[3]
La boucle d'événements : pour détecter et traiter les événements, l'application entre dans une boucle qui attend que les événements se produisent, les place dans la file d'attente des événements, puis les traite. La plupart des applications le feront en appelant la procédure Tcl_DoOneEvent, qui est décrite dans une entrée de manuel séparée.

La plupart des applications Tcl n'ont pas besoin de se soucier des détails internes du notifier Tcl. Cependant, le notifier est maintenant suffisamment flexible pour être redéployé soit pour une nouvelle plateforme, soit pour utiliser une boucle d'événements externe (telle que la boucle d'événements Motif, lorsque Tcl est intégrée dans une application Motif). Les procédures Tcl_WaitForEvent et Tcl_SetTimer sont normalement implémentées par Tcl, mais peuvent être remplacées par de nouvelles versions pour redéployer le notifier (Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler, et Tcl_DeleteFileHandler doivent également être remplacées ; voir CRÉATION D'UN NOUVEAU NOTIFIER ci-dessous pour plus de détails). Les procédures Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode, et Tcl_SetServiceMode sont fournies pour aider à connecter la boucle d'événements de Tcl à une boucle d'événements externe telle que celle de Motif.

BASES DU NOTIFIER

La manière la plus simple de comprendre le fonctionnement du notifier est d'examiner ce qui se passe lorsque Tcl_DoOneEvent est appelée. Tcl_DoOneEvent reçoit un argument flags qui indique quel type d'événements peut être traité et s'il faut bloquer s'il n'y a pas d'événements prêts. Tcl_DoOneEvent effectue les actions suivantes :

[1]
Vérifie la file d'attente des événements pour voir si elle contient des événements qui peuvent être traités. Si c'est le cas, traite le premier événement possible, le retire de la file d'attente et retourne. Pour ce faire, elle appelle Tcl_ServiceEvent et lui passe l'argument flags.
[2]
Prépare à bloquer pour un événement. Pour ce faire, Tcl_DoOneEvent invoque une procédure setup dans chaque source d'événements. La source d'événements effectuera l'initialisation spécifique à la source d'événements et appellera éventuellement Tcl_SetMaxBlockTime pour limiter la durée pendant laquelle Tcl_WaitForEvent bloquera si aucun nouvel événement ne se produit.
[3]
Appelle Tcl_WaitForEvent. Cette procédure est implémentée différemment selon les plateformes ; elle attend qu'un événement se produise, en se basant sur les informations fournies par les sources d'événements. Elle peut entraîner le blocage de l'application si timePtr spécifie un intervalle différent de 0. Tcl_WaitForEvent retourne lorsqu'un événement s'est produit, tel qu'un fichier devenant lisible ou l'expiration de l'intervalle donné par timePtr. S'il n'y a aucun événement pour Tcl_WaitForEvent à attendre, de sorte qu'elle bloquerait indéfiniment, elle retourne immédiatement et Tcl_DoOneEvent retourne 0.
[4]
Appelle une procédure check dans chaque source d'événements. La procédure check détermine si des événements intéressant cette source se sont produits. Si c'est le cas, les événements sont ajoutés à la file d'attente des événements.
[5]
Vérifie le file d'attente d'événements.

CRÉATION D'UNE NOUVELLE SOURCE D'ÉVÉNEMENTS

Une source d'événements se compose de trois procédures appelées par le gestionnaire, plus des procédures C supplémentaires qui sont appelées par du code de niveau supérieur pour organiser les callbacks d'événements basés sur le temps. Les trois procédures appelées par le gestionnaire consistent en les procédures de configuration et de vérification décrites ci-dessus, plus une procédure supplémentaire qui est appelée lorsqu'un événement est retiré de la file d'attente des événements pour être traité.

La procédure Tcl_CreateEventSource crée une nouvelle source d'événements. Ses arguments spécifient les procédures de configuration et de vérification de l'événement. SetupProc doit correspondre au prototype suivant :

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

L'argument clientData sera le même que l'argument clientData de la procédure Tcl_CreateEventSource ; il est généralement utilisé pour pointer vers des informations privées gérées par la source d'événements. L'argument flags sera le même que l'argument flags passé à Tcl_DoOneEvent, sauf s'il est de 0 (Tcl_DoOneEvent remplace 0 par TCL_ALL_EVENTS). Flags indique quels types d'événements doivent être pris en compte ; si le bit correspondant à cette source d'événements n'est pas actif, la source d'événements doit retourner immédiatement sans rien faire. Par exemple, la source d'événements de fichier vérifie le bit TCL_FILE_EVENTS.

Le SetupProc doit s'assurer que l'application se réveille lorsque des événements du type désiré se produisent. Ceci est généralement effectué de manière dépendante de la plateforme. Par exemple, sous Unix, une source d'événements pourrait appeler Tcl_CreateFileHandler ; sous Windows, elle pourrait demander une notification avec un événement Windows. Pour les sources d'événements basées sur des minuteurs, comme les événements de minuteur ou tout événement sondé, la source d'événements peut appeler Tcl_SetMaxBlockTime pour forcer l'application à se réveiller après un temps spécifié, même si aucun événement ne s'est produit. Si aucune source d'événements n'appelle Tcl_SetMaxBlockTime, Tcl_WaitForEvent attendra suffisamment longtemps pour qu'un événement se produise ; sinon, il n'attendra que jusqu'à l'intervalle le plus court spécifié par l'une des sources d'événements. Si une source d'événements sait qu'elle a déjà des événements prêts à être signalés, elle peut demander un temps de blocage nul. Par exemple, la procédure de configuration de la source d'événements X vérifie s'il y a déjà des événements enregistrés. S'il y en a, elle appelle Tcl_SetMaxBlockTime avec un temps de blocage nul afin que Tcl_WaitForEvent ne se bloque pas s'il n'y a pas de nouvelles données sur la connexion X. L'argument timePtr de Tcl_WaitForEvent pointe vers une structure décrivant un intervalle de temps en secondes et microsecondes :

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

Le champ usec doit être inférieur à 1000000.

Les informations fournies à Tcl_SetMaxBlockTime sont utilisées uniquement pour le prochain appel à Tcl_WaitForEvent ; elles sont supprimées après le retour de Tcl_WaitForEvent. La prochaine fois qu'une attente d'événements sera effectuée, chaque procédure de configuration des sources d'événements sera appelée à nouveau, et elles pourront spécifier de nouvelles informations pour cette attente d'événement.

Si l'application utilise une boucle d'événements externe au lieu de Tcl_DoOneEvent, les sources d'événements peuvent avoir besoin d'appeler Tcl_SetMaxBlockTime à d'autres moments. Par exemple, si un nouveau gestionnaire d'événements qui doit être sondé est enregistré, la source d'événements peut appeler Tcl_SetMaxBlockTime pour définir un temps de blocage nul, forçant la boucle d'événements externe à appeler Tcl. Dans ce cas, Tcl_SetMaxBlockTime invoque Tcl_SetTimer avec l'intervalle le plus court vu depuis le dernier appel à Tcl_DoOneEvent ou Tcl_ServiceAll.

En plus de la procédure générique Tcl_SetMaxBlockTime, d'autres procédures spécifiques à la plateforme peuvent également être disponibles pour setupProc, si des informations supplémentaires sont nécessaires à Tcl_WaitForEvent sur cette plateforme. Par exemple, sur les systèmes Unix, l'interface Tcl_CreateFileHandler peut être utilisée pour attendre les événements de fichier.

La deuxième procédure fournie par chaque source d'événements est sa procédure de vérification, indiquée par l'argument checkProc de la procédure Tcl_CreateEventSource. CheckProc doit correspondre au prototype suivant :

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Les arguments de cette procédure sont les mêmes que ceux de setupProc. CheckProc est invoqué par Tcl_DoOneEvent après avoir attendu les événements. Bien qu'au moins une source d'événements soit prête à mettre en file d'attente un événement, Tcl_DoOneEvent appelle chaque source d'événements dans l'ordre, de sorte que toutes aient la possibilité de mettre en file d'attente tout événement prêt. La procédure de vérification effectue deux tâches. Premièrement, elle doit vérifier s'il y a des événements qui se sont déclenchés. Différentes sources d'événements le font différemment.

Si une source d'événements détecte un événement intéressant, elle doit ajouter l'événement à la file d'attente des événements Tcl. Pour ce faire, la source d'événements appelle Tcl_QueueEvent. L'argument evPtr est un pointeur vers une structure allouée dynamiquement qui contient l'événement (voir plus loin pour les problèmes de gestion de la mémoire). Chaque source d'événements peut définir sa propre structure d'événement avec toute information pertinente pour cette source d'événements. Cependant, le premier élément de la structure doit être une structure de type Tcl_Event, et l'adresse de cette structure est utilisée lors des communications entre la source d'événements et le reste du gestionnaire. Un Tcl_Event a la définition suivante :

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La source d'événements doit remplir le champ proc de la structure avant d'appeler Tcl_QueueEvent. Le nextPtr est utilisé pour lier les événements dans la file d'attente et ne doit pas être modifié par la source d'événements.

Un événement peut être ajouté à la file d'attente à l'une des trois positions, en fonction de l'argument position de Tcl_QueueEvent :

TCL_QUEUE_TAIL
Ajouter l'événement à la fin de la file d'attente, de sorte que tous les événements en attente soient traités en premier. C'est presque toujours la bonne position pour les nouveaux événements.
TCL_QUEUE_HEAD
Ajouter l'événement au début de la file d'attente, de sorte qu'il soit traité avant tous les autres événements dans la file d'attente.
TCL_QUEUE_MARK
Ajouter l'événement au début de la file d'attente, sauf s'il y a d'autres événements au début dont la position est TCL_QUEUE_MARK ; si c'est le cas, ajouter le nouvel événement juste après tous les autres événements TCL_QUEUE_MARK. Cette valeur de position est utilisée pour insérer une séquence ordonnée d'événements au début de la file d'attente, comme une série d'événements Enter et Leave synthétisés lors d'une opération de saisie ou de relâchement dans Tk.

Lorsque le moment est venu de traiter un événement de la file d'attente (étapes 1 et 4 ci-dessus), Tcl_ServiceEvent appellera le proc spécifié dans la première structure Tcl_Event qui a été mise en file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

Le premier argument du proc est un pointeur vers l'événement, qui sera le même que le premier argument de l'appel à Tcl_QueueEvent qui a ajouté l'événement à la file d'attente. Le deuxième argument du proc est le flags de l'appel actuel à Tcl_ServiceEvent ; il est utilisé par la source d'événements pour retourner immédiatement si ses événements ne sont pas pertinents.

Il incombe au proc de gérer l'événement, généralement en invoquant une ou plusieurs commandes Tcl ou des callbacks de niveau C. Une fois que la source d'événements a fini de gérer l'événement, elle retourne 1 pour indiquer que l'événement peut être retiré de la file d'attente. Si pour une raison quelconque la source d'événements décide que l'événement ne peut pas être traité à ce moment-là, elle peut retourner 0 pour indiquer que l'événement doit être différé pour plus tard. Dans ce cas, Tcl_ServiceEvent passera à l'événement suivant dans la file d'attente et tentera de le traiter. Il existe plusieurs raisons pour lesquelles une source d'événements pourrait différer un événement. Une possibilité est que les événements de ce type soient exclus par l'argument flags. Par exemple, la source d'événements de fichier retournera toujours 0 si le bit TCL_FILE_EVENTS n'est pas actif dans flags. Un autre exemple de report d'événements se produit dans Tk si Tk_RestrictEvents a été appelé pour reporter certains types d'événements de fenêtre.

Lorsque proc retourne 1, Tcl_ServiceEvent retirera l'événement de la file d'attente et libérera son stockage. Il convient de noter que le stockage d'un événement doit être alloué par la source d'événements (en utilisant Tcl_Alloc ou la macro Tcl ckalloc) avant d'appeler Tcl_QueueEvent, mais il sera libéré par Tcl_ServiceEvent, et non par la source d'événements.

Les applications multithreads fonctionnent de manière similaire, sauf qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. Appeler Tcl_QueueEvent dans une application multithread ajoute un événement à la file d'attente du thread actuel. Pour ajouter un événement à la file d'attente d'un autre thread, utilisez Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent accepte comme argument un Tcl_ThreadId, qui identifie de manière unique un thread dans une application Tcl. Pour obtenir le Tcl_ThreadId du thread actuel, utilisez la procédure Tcl_GetCurrentThread. (Un thread doit alors passer cet identifiant à d'autres threads afin qu'ils puissent ajouter des événements à sa file d'attente.) Après avoir ajouté un événement à la file d'attente d'un autre thread, il est généralement nécessaire d'appeler Tcl_ThreadAlert pour "réveiller" ce thread et le notifier du nouvel événement.

Tcl_DeleteEvents peut être utilisé explicitement pour supprimer un ou plusieurs événements de la file d'attente des événements. Tcl_DeleteEvents appelle le proc pour chaque événement dans la file d'attente, supprimant ceux dont la procédure retourne 1. Les événements dont la procédure retourne 0 sont conservés dans la file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

L'argument clientData sera le même que l'argument clientData de l'appel à Tcl_DeleteEvents ;

; est généralement utilisé pour cibler des informations privées gérées par la source d'événements. Le pointeur evPtr pointera vers l'événement suivant dans la file d'attente des événements.

Tcl_DeleteEventSource supprime une source d'événements. Les arguments setupProc, checkProc et clientData doivent correspondre exactement à ceux fournis à Tcl_CreateEventSource pour que la source d'événements soit supprimée. S'il n'existe pas de telle source, Tcl_DeleteEventSource n'a aucun effet.

CRÉER UN NOUVEAU NOTIFICATEUR

Le notificateur se compose de toutes les procédures décrites dans ce manuel, plus Tcl_DoOneEvent et Tcl_Sleep, disponibles sur toutes les plateformes, et Tcl_CreateFileHandler et Tcl_DeleteFileHandler, spécifiques à Unix. La plupart de ces procédures sont générales, dans le sens où elles sont identiques pour tous les notificateurs. Cependant, aucune des procédures n'est indépendante du notificateur : Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler et Tcl_ServiceModeHook. Pour prendre en charge un nouveau système d'exploitation ou intégrer Tcl à une boucle d'événements spécifique à une application, vous devez écrire de nouvelles versions de ces procédures.

Tcl_InitNotifier initialise l'état du notificateur et renvoie un handle vers l'état du notificateur. Tcl appelle cette procédure lors de l'initialisation d'un interpréteur Tcl. De même, Tcl_FinalizeNotifier arrête le notificateur et est appelée par Tcl_Finalize lors de la finalisation d'un interpréteur Tcl.

Tcl_WaitForEvent est la procédure de plus bas niveau du notificateur ; elle est responsable de l'attente d'un événement « intéressant » ou d'un temps donné. Avant que Tcl_WaitForEvent ne soit invoquée, chacune des procédures de configuration des sources d'événements sera invoquée. L'argument timePtr de la procédure Tcl_WaitForEvent donne le temps de blocage maximal pour un événement, basé sur les appels à Tcl_SetMaxBlockTime effectués par les procédures de configuration et d'autres informations (par exemple, le bit TCL_DONT_WAIT dans flags).

Idéalement, Tcl_WaitForEvent ne devrait attendre qu'un seul événement ; elle ne devrait pas réellement traiter l'événement de quelque manière que ce soit. Ensuite, les sources d'événements traiteront les événements bruts et créeront des Tcl_Events dans la file d'attente des événements dans leurs procédures checkProc. Cependant, sur certains systèmes d'exploitation (comme Windows), ce n'est pas possible ; les événements peuvent être traités dans Tcl_WaitForEvent, y compris la mise en file d'attente des Tcl_Events et plus encore (par exemple, les rappels pour les widgets natifs). La valeur de retour de Tcl_WaitForEvent doit être 0, 1 ou -1. Sur les plateformes comme Windows où les événements sont traités dans Tcl_WaitForEvent, une valeur de retour de 1 indique qu'il peut y avoir d'autres événements en attente qui n'ont pas été traités. C'est une indication à l'appelant qu'il doit appeler à nouveau Tcl_WaitForEvent pour traiter tous les événements en attente. Une valeur de retour de 0 indique que l'appel répété de Tcl_WaitForEvent n'aura aucun effet : il peut s'agir d'un système d'exploitation où Tcl_WaitForEvent attend simplement sans traiter les événements, ou Tcl_WaitForEvent sait avec certitude qu'il n'y a plus d'événements à traiter (par exemple, le temps est écoulé). Enfin, une valeur de retour de -1 indique que la boucle d'événements n'est plus opérationnelle et que l'application devrait se désassembler et se terminer. Sous Windows, cela se produit lorsqu'un message WM_QUIT est reçu ; sous Unix, lorsque Tcl_WaitForEvent attend indéfiniment car il n'y a pas de sources d'événements actives et que le délai d'attente est infini).

Tcl_AlertNotifier est utilisé dans les applications multithread pour permettre à n'importe quel thread de « réveiller » le notificateur afin de l'alerter de nouveaux événements dans sa file d'attente. Tcl_AlertNotifier nécessite comme argument le handle du notificateur renvoyé par Tcl_InitNotifier.

Si le notificateur doit être utilisé avec une boucle d'événements externe, il doit également prendre en charge l'interface de Tcl_SetTimer. Tcl_SetTimer est appelée par Tcl_SetMaxBlockTime lorsqu'une réduction du temps de blocage maximal a été effectuée. Tcl_SetTimer doit organiser la boucle d'événements externe pour qu'elle appelle Tcl_ServiceAll même si aucun événement ne s'est produit. Cette interface est nécessaire car Tcl_WaitForEvent n'est pas appelée lorsqu'il existe une boucle d'événements externe. Si le notificateur doit uniquement être appelé depuis Tcl_DoOneEvent, alors Tcl_SetTimer n'a rien à faire.

Tcl_ServiceModeHook est appelée par la partie indépendante du notificateur lorsque le code client appelle Tcl_SetServiceMode. Ce hook est fourni pour prendre en charge les systèmes d'exploitation qui nécessitent une gestion spéciale des événements lorsque l'application est dans une boucle modale (par exemple, le notificateur Windows utilise ce hook pour créer une fenêtre de communication).

Sur les systèmes Unix, les sources d'événements de fichiers nécessitent également le support du notificateur. Les sources d'événements de fichiers se composent des procédures Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont décrites sur la page de manuel de Tcl_CreateFileHandler.

Les interfaces de Tcl_Sleep et Tcl_DoOneEvent sont décrites dans leurs pages de manuel respectives.

Le moyen le plus simple de créer un nouveau notificateur est d'examiner le code d'un notificateur existant, par exemple dans les fichiers unix/tclUnixNotfy.c ou win/tclWinNotify.c dans la distribution du code source de Tcl.

REMPLACER LE NOTIFICATEUR

Un notificateur écrit selon les conventions ci-dessus peut également être installé dans un processus déjà en cours d'exécution pour remplacer le notificateur standard. Ce mécanisme est utilisé pour qu'un seul exécutable puisse être utilisé (avec le notificateur standard) comme programme autonome et réutilisé (en tant qu'extension d'un autre programme, comme un plugin de navigateur Web).

Pour ce faire, l'extension appelle Tcl_SetNotifier, en passant un pointeur vers une structure Tcl_NotifierProcs. La structure a la disposition suivante :

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Après l'appel à Tcl_SetNotifier, les pointeurs fournis dans la structure Tcl_NotifierProcs remplacent ce qui avait été installé dans le processus.

Il est inhabituellement inapproprié de remplacer un notificateur déjà en cours d'exécution. Normalement, Tcl_SetNotifier devrait être appelé avant le premier appel à Tcl_InitNotifier.

BOUCLES D'ÉVÉNEMENTS EXTERNES

Les interfaces de notificateur sont conçues pour que Tcl puisse être intégré dans des applications qui ont leurs propres boucles d'événements privées. Dans ce cas, l'application n'appelle pas Tcl_DoOneEvent, sauf dans les cas de boucles d'événements récursives, comme les appels aux commandes Tcl update ou vwait. La majeure partie du temps est consacrée à la boucle d'événements externe de l'application. Dans ce cas, le notificateur doit organiser la boucle d'événements externe pour qu'elle rappelle Tcl lorsque des événements se produisent dans les sources d'événements Tcl. Ces rappels doivent organiser la mise en file d'attente d'événements appropriés dans la file d'attente des événements Tcl.

Étant donné que la boucle d'événements externe n'appelle pas régulièrement Tcl_DoOneEvent, il est de la responsabilité du notificateur d'organiser l'appel à Tcl_ServiceEvent lorsqu'il y a des événements en attente dans la file d'attente des événements Tcl. Le moyen le plus simple de le faire est d'appeler Tcl_ServiceAll à la fin de chaque rappel de la boucle d'événements externe. Cela garantira que toutes les sources d'événements sont interrogées, que les événements mis en file d'attente sont traités et que les gestionnaires inactifs sont traités avant de redonner le contrôle à l'application. De plus, les sources d'événements qui nécessitent une interrogation d'événements peuvent appeler Tcl_SetMaxBlockTime pour forcer la boucle d'événements externe à rappeler Tcl même s'il n'y a pas d'événements disponibles dans la file d'attente des événements système.

En tant qu'effet secondaire du traitement des événements détectés dans la boucle d'événements externe principale, Tcl peut appeler Tcl_DoOneEvent pour démarrer une boucle d'événements récursive dans des commandes comme vwait. Tcl_DoOneEvent appellera la boucle d'événements externe, ce qui entraînera des rappels comme décrit ci-dessus, qui entraîneront des appels à Tcl_ServiceAll. Cependant, dans ces cas, il est souhaitable de ne pas servir d'événements dans Tcl_ServiceAll. Servir des événements là est inutile car le contrôle sera immédiatement rendu à la boucle d'événements externe, et donc à Tcl_DoOneEvent, qui peut servir les événements lui-même. De plus, Tcl_DoOneEvent est conçu pour servir un seul événement, tandis que Tcl_ServiceAll sert normalement tous les événements en attente. Pour gérer cette situation, Tcl_DoOneEvent définit un drapeau pour Tcl_ServiceAll qui fait que ce dernier renvoie sans servir d'événements. Ce drapeau est appelé le mode de service ; Tcl_DoOneEvent le restaure à sa valeur précédente avant de renvoyer. Dans certains cas, cependant, il peut être nécessaire que Tcl_ServiceAll serve des événements même lorsqu'il a été appelé depuis Tcl_DoOneEvent. Cela se produit lorsqu'il existe une autre boucle d'événements récursive appelée par un gestionnaire d'événements appelé par Tcl_DoOneEvent (comme une faisant partie d'un widget natif). Dans ce cas, Tcl_DoOneEvent pourrait ne pas avoir l'occasion de servir des événements, de sorte que Tcl_ServiceAll doit tous les servir. Toute boucle d'événements récursive qui appelle une boucle d'événements externe au lieu de Tcl_DoOneEvent doit réinitialiser le mode de service afin que tous les événements soient traités dans Tcl_ServiceAll. Ceci est réalisé en appelant la procédure Tcl_SetServiceMode. Si Tcl_SetServiceMode reçoit TCL_SERVICE_NONE, les appels à Tcl_ServiceAll renverront immédiatement sans traiter aucun événement. Si Tcl_SetServiceMode reçoit TCL_SERVICE_ALL, les appels à Tcl_ServiceAll se comporteront normalement. Tcl_SetServiceMode renvoie la valeur précédente du mode de service, qui doit être restaurée lorsque la boucle d'événements récursive se termine. Tcl_GetServiceMode renvoie la valeur actuelle du mode de service.
