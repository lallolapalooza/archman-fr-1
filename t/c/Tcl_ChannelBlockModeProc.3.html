DESCRIPTION

Tcl utilise une architecture de canaux à deux niveaux. Il offre un niveau général pour permettre aux programmes C et Tcl d'effectuer des entrées et sorties en utilisant les mêmes API pour une variété de fichiers, périphériques, sockets, etc. Les API C du niveau général sont décrites dans la page de manuel Tcl_OpenFileChannel.

Le niveau inférieur fournit des pilotes de canaux spécifiques à chaque type de périphérique supporté sur chaque plateforme. Cette page de manuel décrit les API qui communiquent entre le niveau général et les pilotes de canaux spécifiques. Elle explique également comment de nouveaux types de canaux peuvent être ajoutés en fournissant de nouveaux pilotes de canaux.

Les pilotes de canaux consistent en plusieurs composants : Premièrement, chaque pilote de canal fournit une structure Tcl_ChannelType qui contient des pointeurs vers les procédures implémentant les différentes opérations utilisées par le niveau général pour communiquer avec le pilote de canal. La structure Tcl_ChannelType et les procédures référencées par elle sont décrites dans la section TCL_CHANNELTYPE, ci-dessous.

Deuxièmement, les pilotes de canaux fournissent généralement une commande Tcl pour créer des instances de ce type de canal. Par exemple, la commande Tcl open crée des canaux qui utilisent les pilotes de canaux de fichiers et de commandes, et la commande Tcl socket crée des canaux qui utilisent les protocoles réseau TCP.

Troisièmement, un pilote de canal fournit éventuellement une fonction C pour ouvrir des instances de ce type de canal. Par exemple, Tcl_OpenFileChannel ouvre un canal qui utilise le pilote de canal de fichier, et Tcl_OpenTcpClient ouvre un canal qui utilise le protocole réseau TCP. Ces fonctions de création utilisent généralement Tcl_CreateChannel en interne pour ouvrir le canal.

Pour ajouter un nouveau type de canal, vous devez implémenter une API C ou une commande Tcl qui ouvre un canal en appelant Tcl_CreateChannel. Lorsque votre pilote appelle Tcl_CreateChannel, il passe une structure Tcl_ChannelType qui décrit les procédures d'entrée/sortie de votre pilote. Le niveau général invoquera ensuite les procédures référencées dans cette structure pour effectuer des opérations sur le canal.

Tcl_CreateChannel ouvre un nouveau canal et associe typePtr et instanceData à celui-ci. Le canal est ouvert dans le mode indiqué par mask. Pour une discussion sur les pilotes de canaux, leurs opérations et la structure Tcl_ChannelType, voir la section TCL_CHANNELTYPE, ci-dessous.

Tcl_CreateChannel interagit avec le code qui gère les canaux standards. Une fois qu'un canal standard a été initialisé par un appel à Tcl_GetStdChannel ou Tcl_SetStdChannel, la fermeture de ce canal entraînera la prochaine invocation de Tcl_CreateChannel à recréer le canal comme canal standard. Voir Tcl_StandardChannels pour une généralisation sur les canaux standards et le comportement de la bibliothèque Tcl à leur égard.

Tcl_GetChannelInstanceData renvoie les données d'instanciation associées au canal dans channel. Ceci est identique à l'argument instanceData dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelType renvoie un pointeur vers la structure Tcl_ChannelType utilisée par le canal dans l'argument channel. Ceci est identique à l'argument typePtr dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelName renvoie une chaîne contenant le nom associé au canal, ou NULL si l'argument channelName de Tcl_CreateChannel était NULL.

Tcl_GetChannelHandle place le handle de périphérique du système d'exploitation associé à channel pour la direction donnée dans handlePtr.

Tcl_GetChannelThread renvoie l'identifiant du thread gérant actuellement le canal spécifié. Cela permet aux pilotes de canal d'envoyer leurs événements de fichier à la file d'attente d'événements correcte, même pour un noyau multi-thread.

Tcl_GetChannelMode renvoie une combinaison OR de TCL_READABLE et TCL_WRITABLE, indiquant si le canal est ouvert en lecture et en écriture.

Tcl_GetChannelBufferSize renvoie la taille, en octets, des tampons alloués pour stocker les entrées ou les sorties dans channel. Si la valeur n'a pas été définie par un appel précédent à Tcl_SetChannelBufferSize, décrit ci-dessous, alors la valeur par défaut de 4096 est retournée.

Tcl_SetChannelBufferSize définit la taille, en octets, des tampons qui seront alloués lors des opérations ultérieures sur le canal pour stocker les entrées ou les sorties. L'argument size doit être compris entre un et un million, permettant des tampons d'un octet à un million d'octets. Les pilotes de canal sont responsables de l'appel de cette fonction chaque fois que les gestionnaires de canal doivent être appelés pour le canal (ou que d'autres tâches en attente, comme la vidange d'une écriture, doivent être effectuées). Voir WATCHPROC ci-dessous pour plus de détails.

Tcl_BadChannelOption est appelée à partir du setOptionProc ou getOptionProc spécifique au pilote pour générer un message d'erreur complet.

Tcl_ChannelBuffered renvoie le nombre d'octets d'entrée actuellement mis en tampon dans le tampon interne (zone de rappel) du canal lui-même. Il ne rapporte pas les données dans les tampons globaux de la pile de canaux dont fait partie le canal fourni.

Tcl_IsChannelShared vérifie le compteur de références du channel spécifié et renvoie si le channel était partagé entre plusieurs interpréteurs (résultat == 1) ou non (résultat == 0).

Tcl_IsChannelRegistered vérifie si le channel spécifié est enregistré dans l'interpréteur interp donné (résultat == 1) ou non (résultat == 0).

Tcl_IsChannelExisting vérifie si un canal portant le nom spécifié est enregistré dans la liste globale (par thread) de tous les canaux (résultat == 1) ou non (résultat == 0).

Tcl_CutChannel supprime le channel spécifié de la liste globale (par thread) de tous les canaux (du thread courant). L'application à un canal toujours enregistré dans un interpréteur n'est pas autorisée. Notifie également le pilote si la version de Tcl_ChannelType est TCL_CHANNEL_VERSION_4 (ou supérieure) et si Tcl_DriverThreadActionProc est définie pour celui-ci.

Tcl_SpliceChannel ajoute le channel spécifié à la liste globale (par thread) de tous les canaux (du thread courant). L'application à un canal enregistré dans un interpréteur n'est pas autorisée. Notifie également le pilote si la version de Tcl_ChannelType est TCL_CHANNEL_VERSION_4 (ou supérieure) et si Tcl_DriverThreadActionProc est définie pour celui-ci.

Tcl_ClearChannelHandlers supprime tous les gestionnaires de canal et les scripts d'événements associés au channel spécifié, fermant ainsi tout traitement d'événements pour ce canal.

TCL_CHANNELTYPE

Un pilote de canal fournit une structure Tcl_ChannelType qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un canal ; ces opérations sont appelées si nécessaire par la couche générique. La structure a été versionnée à partir de Tcl 8.3.2/8.4 pour corriger un problème avec les canaux empilés. Voir la section OLD CHANNEL TYPES ci-dessous pour les détails sur l'ancienne structure.

La structure Tcl_ChannelType contient les champs suivants :

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Il n'est pas nécessaire de fournir des implémentations pour toutes les opérations de canal. Celles qui ne sont pas nécessaires peuvent être mises à NULL dans la structure : blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc, et close2Proc, en plus de flushProc, handlerProc, threadActionProc, et truncateProc. D'autres fonctions qui ne peuvent pas être implémentées de manière significative doivent renvoyer EINVAL lorsqu'elles sont appelées, pour indiquer que les opérations qu'elles représentent ne sont pas disponibles. Notez également que wideSeekProc peut être NULL si seekProc l'est.

L'utilisateur ne doit utiliser que la structure ci-dessus pour l'instanciation de Tcl_ChannelType. Lors de la référence aux champs d'une structure Tcl_ChannelType, les fonctions suivantes doivent être utilisées pour obtenir les valeurs : Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc, ou Tcl_ChannelHandlerProc.

La modification des structures a été faite de manière à ce que les types de canaux standard soient binaires compatibles. Cependant, les types de canaux qui utilisent des canaux empilés (c'est-à-dire TLS, Trf) ont de nouvelles versions pour correspondre à la modification ci-dessus, car le code précédent pour les canaux empilés avait des problèmes.

TYPENAME

Le champ typeName contient une chaîne terminée par un nul qui identifie le type du périphérique implémenté par ce pilote, par exemple file ou socket.

Cette valeur peut être récupérée avec Tcl_ChannelName, qui renvoie un pointeur vers la chaîne.

VERSION

Le champ version doit être défini sur la version de la structure dont vous avez besoin. TCL_CHANNEL_VERSION_2 est le minimum recommandé. TCL_CHANNEL_VERSION_3 doit être défini pour spécifier le membre wideSeekProc. TCL_CHANNEL_VERSION_4 doit être défini pour spécifier le membre threadActionProc (inclut wideSeekProc). TCL_CHANNEL_VERSION_5 doit être défini pour spécifier le membre truncateProc (inclut wideSeekProc et threadActionProc). S'il n'est défini sur aucun de ceux-ci, alors ce Tcl_ChannelType est supposé avoir la structure originale. Voir OLD CHANNEL TYPES pour plus de détails. Bien que Tcl reconnaisse et fonctionne avec les deux structures, les canaux empilés doivent être au moins de version TCL_CHANNEL_VERSION_2 pour fonctionner correctement.

Cette valeur peut être récupérée avec Tcl_ChannelVersion, qui renvoie l'une des valeurs suivantes : TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 ou TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

Le champ blockModeProc contient l'adresse d'une fonction appelée par la couche générique pour définir le mode bloquant et non bloquant sur le périphérique. BlockModeProc doit correspondre au prototype suivant :

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

instanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument mode est soit TCL_MODE_BLOCKING, soit TCL_MODE_NONBLOCKING pour mettre le périphérique en mode bloquant ou non bloquant. La fonction doit renvoyer zéro si l'opération a réussi, ou un code d'erreur POSIX non nul si l'opération a échoué.

Si l'opération réussit, la fonction peut modifier instanceData fourni pour enregistrer que le canal est entré en mode bloquant ou non bloquant et pour implémenter le comportement bloquant ou non bloquant. Pour certains types de périphériques, le comportement bloquant et non bloquant peut être implémenté par le système d'exploitation sous-jacent ; pour d'autres types de périphériques, le comportement doit être émulé dans le pilote de canal.

Cette valeur peut être récupérée avec Tcl_ChannelBlockModeProc, qui renvoie un pointeur vers la fonction.

Un pilote de canal qui ne fournit **pas** de blockModeProc doit être très, très prudent. Il doit indiquer à la couche générique quel mode bloquant lui est acceptable, et documenter cela également pour l'utilisateur afin que le mode bloquant du canal ne soit pas modifié à une valeur inacceptable. Toute confusion ici peut entraîner l'interpréteur dans un interblocage (interne et difficile à trouver).

CLOSEPROC ET CLOSE2PROC

Le champ closeProc contient l'adresse d'une fonction appelée par la couche générique pour nettoyer les informations liées au pilote lorsque le canal est fermé. CloseProc doit correspondre au prototype suivant :

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

L'argument instanceData est la même valeur que celle fournie à Tcl_CreateChannel lors de la création du canal. La fonction doit libérer toute mémoire gérée par le pilote de canal pour ce canal et fermer les périphériques d'entrée et de sortie encapsulés par ce canal. Toutes les sorties en file d'attente auront été vidées vers le périphérique avant que cette fonction ne soit appelée, et aucune autre opération de pilote ne sera invoquée sur cette instance après l'appel de closeProc. Si l'opération de fermeture réussit, la procédure

ure doit retourner zéro; sinon, elle doit retourner un code d'erreur POSIX non nul. De plus, si une erreur se produit et que interp n'est pas NULL, la procédure doit stocker un message d'erreur dans le résultat de l'interpréteur.

Alternativement, les canaux qui prennent en charge la fermeture des côtés de lecture et d'écriture indépendamment peuvent définir closeProc sur TCL_CLOSE2PROC et close2Proc sur l'adresse d'une fonction qui correspond au prototype suivant :

typedef int Tcl_DriverClose2Proc(
        ClientData instanceData,
        Tcl_Interp *interp,
        int flags);

Le close2Proc sera appelé avec flags défini sur une combinaison OR de TCL_CLOSE_READ ou TCL_CLOSE_WRITE pour indiquer que le pilote doit fermer le côté lecture et/ou écriture du canal. Le pilote de canal peut être appelé pour effectuer des opérations supplémentaires sur le canal après que close2Proc ait été appelé pour fermer un ou les deux côtés du canal. Si flags est 0 (zéro), le pilote doit fermer le canal de la manière décrite ci-dessus pour closeProc. Aucune opération supplémentaire ne sera appelée sur cette instance après que close2Proc ait été appelé avec tous les indicateurs effacés. Dans tous les cas, la fonction close2Proc doit retourner zéro si l'opération de fermeture a réussi ; sinon, elle doit retourner un code d'erreur POSIX non nul. De plus, si une erreur se produit et que interp n'est pas NULL, la procédure doit stocker un message d'erreur dans le résultat de l'interpréteur.

Les valeurs closeProc et close2Proc peuvent être récupérées avec Tcl_ChannelCloseProc ou Tcl_ChannelClose2Proc, qui retournent un pointeur vers la fonction respective.

INPUTPROC

Le champ inputProc contient l'adresse d'une fonction appelée par la couche générique pour lire des données du fichier ou du périphérique et les stocker dans un tampon interne. InputProc doit correspondre au prototype suivant :

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création du canal. L'argument buf pointe vers un tableau d'octets dans lequel stocker les entrées du périphérique, et l'argument bufSize indique combien d'octets sont disponibles à buf.

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générique. Si une erreur se produit, la fonction doit définir la variable à un code d'erreur POSIX qui identifie l'erreur qui s'est produite.

La fonction doit lire des données du périphérique d'entrée encapsulé par le canal et les stocker à buf. En cas de succès, la fonction doit retourner un entier non négatif indiquant combien d'octets ont été lus du périphérique d'entrée et stockés à buf. En cas d'erreur, la fonction doit retourner -1. Si une erreur se produit après que certaines données aient été lues du périphérique, ces données sont perdues.

Si inputProc peut déterminer que le périphérique d'entrée a des données disponibles mais moins que demandé par l'argument bufSize, la fonction ne doit tenter de lire que la quantité de données disponible et retourner sans bloquer. Si le périphérique d'entrée n'a aucune donnée disponible et que le canal est en mode non bloquant, la fonction doit retourner une erreur EAGAIN. Si le périphérique d'entrée n'a aucune donnée disponible et que le canal est en mode bloquant, la fonction doit se bloquer pendant la plus courte durée possible jusqu'à ce qu'au moins un octet de données puisse être lu du périphérique ; ensuite, elle doit retourner autant de données qu'elle peut lire sans bloquer.

Cette valeur peut être récupérée avec Tcl_ChannelInputProc, qui retourne un pointeur vers la fonction.

OUTPUTPROC

Le champ outputProc contient l'adresse d'une fonction appelée par la couche générique pour transférer des données d'un tampon interne vers le périphérique de sortie. OutputProc doit correspondre au prototype suivant :

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création du canal. L'argument buf contient un tableau d'octets à écrire sur le périphérique, et l'argument toWrite indique combien d'octets doivent être écrits à partir de l'argument buf.

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générique. Si une erreur se produit, la fonction doit définir cette variable à un code d'erreur POSIX qui identifie l'erreur.

La fonction doit écrire les données à buf sur le périphérique de sortie encapsulé par le canal. En cas de succès, la fonction doit retourner un entier non négatif indiquant combien d'octets ont été écrits sur le périphérique de sortie. La valeur de retour est normalement la même que toWrite, mais peut être inférieure dans certains cas, par exemple si l'opération de sortie est interrompue par un signal. Si une erreur se produit, la fonction doit retourner -1. En cas d'erreur, certaines données peuvent avoir été écrites sur le périphérique.

Si le canal est non bloquant et que le périphérique de sortie ne peut absorber aucune donnée, la fonction doit retourner -1 avec une erreur EAGAIN sans écrire aucune donnée.

Cette valeur peut être récupérée avec Tcl_ChannelOutputProc, qui retourne un pointeur vers la fonction.

SEEKPROC ET WIDESEEKPROC

Le champ seekProc contient l'adresse d'une fonction appelée par la couche générique pour déplacer le point d'accès auquel les opérations d'entrée ou de sortie ultérieures seront appliquées. SeekProc doit correspondre au prototype suivant :

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

L'argument instanceData est la même valeur que celle donnée à Tcl_CreateChannel lors de la création de ce canal. Offset et seekMode ont la même signification que pour la procédure Tcl_Seek (décrite dans l'entrée de manuel de Tcl_OpenFileChannel).

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générique pour retourner les valeurs errno de la fonction. La fonction doit définir cette variable à un code d'erreur POSIX si une erreur se produit. La fonction doit stocker un code d'erreur EINVAL si le type de canal n'implémente pas le déplacement.

La valeur de retour est le nouveau point d'accès ou -1 en cas d'erreur. Si une erreur s'est produite, la fonction ne doit pas déplacer le point d'accès.

S'il existe un champ seekProc non NULL, le champ wideSeekProc peut contenir l'adresse d'une fonction alternative à utiliser qui gère les décalages larges (c'est-à-dire supérieurs à 32 bits), permettant ainsi les déplacements dans des fichiers supérieurs à 2 Go. Le wideSeekProc sera appelé de préférence au seekProc, mais les deux doivent être définis si le wideSeekProc est défini. WideSeekProc doit correspondre au prototype suivant :

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

Les arguments et les valeurs de retour signifient la même chose qu'avec seekProc ci-dessus, à l'exception du type des décalages et du type de retour qui sont différents.

La valeur seekProc peut être récupérée avec Tcl_ChannelSeekProc, qui retourne un pointeur vers la fonction, et de manière similaire, le wideSeekProc peut être récupéré avec Tcl_ChannelWideSeekProc.

SETOPTIONPROC

Le champ setOptionProc contient l'adresse d'une fonction appelée par la couche générique pour définir une option spécifique au type de canal sur un canal. setOptionProc doit correspondre au prototype suivant :

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

optionName est le nom d'une option à définir, et newValue est la nouvelle valeur de cette option, sous forme de chaîne. InstanceData est la même valeur que celle donnée à Tcl_CreateChannel lors de la création de ce canal. La fonction doit effectuer toute action spécifique au type de canal requise pour implémenter la nouvelle valeur de l'option.

Certaines options sont gérées par le code générique et cette fonction n'est jamais appelée pour les définir, par exemple -blockmode. D'autres options sont spécifiques à chaque type de canal et la procédure setOptionProc du pilote de canal sera appelée pour les implémenter. Le champ setOptionProc peut être NULL, ce qui indique que ce type de canal ne prend en charge aucune option spécifique au type.

Si la valeur de l'option est modifiée avec succès à la nouvelle valeur, la fonction retourne TCL_OK. Elle doit appeler Tcl_BadChannelOption qui retourne elle-même TCL_ERROR si optionName n'est pas reconnu. Si newValue spécifie une valeur pour l'option qui n'est pas prise en charge ou si une erreur d'appel système se produit, la fonction doit laisser un message d'erreur dans le résultat de interp si interp n'est pas NULL. La fonction doit également appeler Tcl_SetErrno pour stocker un code d'erreur POSIX approprié.

Cette valeur peut être récupérée avec Tcl_ChannelSetOptionProc, qui retourne un pointeur vers la fonction.

GETOPTIONPROC

Le champ getOptionProc contient l'adresse d'une fonction appelée par la couche générique pour obtenir la valeur d'une option spécifique au type de canal sur un canal. getOptionProc doit correspondre au prototype suivant :

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        Tcl_DString *optionValue);

OptionName est le nom d'une option prise en charge par ce type de canal. Si le nom de l'option n'est pas NULL, la fonction stocke sa valeur actuelle, sous forme de chaîne, dans la chaîne dynamique Tcl optionValue. Si optionName est NULL, la fonction stocke dans optionValue une liste alternée de toutes les options prises en charge et de leurs valeurs actuelles. En cas de succès, la fonction retourne TCL_OK. WATCHPROC

Le champ watchProc contient l'adresse d'une fonction appelée par la couche générique pour initialiser le mécanisme de notification des événements d'intérêt sur ce canal. WatchProc doit correspondre au prototype suivant:

typedef void Tcl_DriverWatchProc(
        ClientData instanceData,
        int mask);

Le instanceData est le même que la valeur passée à Tcl_CreateChannel lors de la création de ce canal. L'argument mask est une combinaison OR de TCL_READABLE, TCL_WRITABLE et TCL_EXCEPTION; il indique les événements pour lesquels l'appelant souhaite être notifié sur ce canal.

La fonction doit initialiser des mécanismes spécifiques au type de périphérique pour signaler quand un événement d'intérêt est présent sur le canal. Lorsqu'un événement d'intérêt se produit sur le canal, le pilote de canal doit appeler Tcl_NotifyChannel pour informer le module de canal générique. Le pilote doit éviter que d'autres pilotes de canal ou sources de rappels ne se bloquent en appelant Tcl_NotifyChannel trop fréquemment. L'équité peut être assurée en utilisant la file d'attente d'événements de Tcl pour permettre à l'événement de canal d'être programmé en séquence avec d'autres événements. Voir la description de Tcl_QueueEvent pour plus de détails sur la programmation d'un événement.

Cette valeur peut être récupérée via Tcl_ChannelWatchProc, qui renvoie une adresse à la fonction.

GETHANDLEPROC

Le champ getHandleProc contient l'adresse d'une fonction appelée par la couche générique pour récupérer un handle spécifique au canal. GetHandleProc doit correspondre au prototype suivant:

typedef int Tcl_DriverGetHandleProc(
        ClientData instanceData,
        int direction,
        ClientData *handlePtr);

InstanceData est le même que la valeur passée à Tcl_CreateChannel lors de la création de ce canal. L'argument direction est TCL_READABLE pour récupérer le handle utilisé pour l'entrée, ou TCL_WRITABLE pour récupérer le handle utilisé pour la sortie.

Si l'implémentation du canal possède des handles spécifiques, la fonction doit récupérer le handle approprié en fonction de l'argument direction. Le handle doit être stocké à l'emplacement référencé par handlePtr, et TCL_OK doit être renvoyé. Si le canal n'est pas ouvert pour la direction spécifiée, ou si l'implémentation du canal n'utilise pas de handles spécifiques, la fonction doit renvoyer TCL_ERROR.

Cette valeur peut être récupérée via Tcl_ChannelGetHandleProc, qui renvoie une adresse à la fonction.

FLUSHPROC

Le champ flushProc est réservé pour les fonctions futures. Il doit être défini à NULL. FlushProc doit correspondre au prototype suivant:

typedef int Tcl_DriverFlushProc(
        ClientData instanceData);

Cette valeur peut être récupérée via Tcl_ChannelFlushProc, qui renvoie une adresse à la fonction.

HANDLERPROC

Le champ handlerProc contient l'adresse d'une fonction appelée par la couche générique pour informer le canal qu'un événement s'est produit. Il doit être défini pour les pilotes de canal empilés qui souhaitent être informés des événements sur le canal sous-jacent (empilé). HandlerProc doit correspondre au prototype suivant:

typedef int Tcl_DriverHandlerProc(
        ClientData instanceData,
        int interestMask);

InstanceData est le même que la valeur passée à Tcl_CreateChannel lors de la création de ce canal. Le interestMask est une combinaison OR de TCL_READABLE ou TCL_WRITABLE; il indique le type d'événement qui s'est produit sur ce canal.

Cette valeur peut être récupérée via Tcl_ChannelHandlerProc, qui renvoie une adresse à la fonction.

THREADACTIONPROC

Le champ threadActionProc contient l'adresse de la fonction appelée par la couche générique lors de la création d'un canal, de la fermeture d'un canal ou du déplacement vers un thread différent, c'est-à-dire lorsque l'état spécifique au thread du pilote peut nécessiter d'être initialisé ou mis à jour. Il peut être NULL. L'action TCL_CHANNEL_THREAD_REMOVE est utilisée pour informer le pilote qu'il doit mettre à jour ou supprimer toute donnée spécifique au thread qu'il maintient pour le canal.

L'action TCL_CHANNEL_THREAD_INSERT est utilisée pour informer le pilote qu'il doit mettre à jour ou initialiser toute donnée spécifique au thread qu'il maintient en utilisant le thread actuel comme associé. Voir Tcl_CutChannel et Tcl_SpliceChannel pour plus de détails.

typedef void Tcl_DriverThreadActionProc(
        ClientData instanceData,
        int action);

InstanceData est le même que la valeur passée à Tcl_CreateChannel lors de la création de ce canal.

Ces valeurs peuvent être récupérées via Tcl_ChannelThreadActionProc, qui renvoie une adresse à la fonction.

TRUNCATEPROC

Le champ truncateProc contient l'adresse de la fonction appelée par la couche générique lorsqu'un canal est tronqué à une certaine longueur. Il peut être NULL.

typedef int Tcl_DriverTruncateProc(
        ClientData instanceData,
        Tcl_WideInt length);

InstanceData est le même que la valeur passée à Tcl_CreateChannel lors de la création de ce canal, et length est la nouvelle longueur du fichier sous-jacent, qui ne doit pas être négative. Le résultat doit être 0 en cas de succès ou un code d'erreur (approprié pour être utilisé avec Tcl_SetErrno) en cas d'échec.

Ces valeurs peuvent être récupérées via Tcl_ChannelTruncateProc, qui renvoie une adresse à la fonction.

TCL_BADCHANNELOPTION

Cette procédure génère un message d'erreur "mauvaise option" dans un interpréteur (optionnel). Elle est utilisée par les pilotes de canal lorsqu'une option invalide est demandée. Son but est de concaténer la liste des options génériques à la liste des options spécifiques et de factoriser le message d'erreur des options génériques.

Renvoie toujours TCL_ERROR.

Un message d'erreur est généré dans la valeur de résultat de interp pour indiquer qu'une commande a été invoquée avec une option invalide. Le message a la forme

    bad option "blah": should be one of
    <...generic options...>+<...specific options...>
comme obtenu par exemple: 
    bad option "-blah": should be one of -blocking,
    -buffering, -buffersize, -eofchar, -translation,
    -peername, or -sockname
lorsqu'elle est appelée avec optionList égal à "peername sockname".

"blah" est l'argument optionName et "<specific options>" est une liste de mots d'options spécifiques séparés par des espaces. La fonction prend soin d'insérer des tirets avant chaque option, des virgules après et un "or" avant la dernière option.

OLD CHANNEL TYPES

La structure originale (8.3.1 et versions antérieures) Tcl_ChannelType contient les champs suivants:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
} Tcl_ChannelType;

Bien qu'il soit possible de créer un canal avec la structure ci-dessus, le code interne du canal déterminera la version. Il est essentiel d'utiliser la nouvelle structure Tcl_ChannelType si vous créez un pilote de canal empilé en raison de problèmes avec l'implémentation précédente des canaux empilés (8.2.0 à 8.3.1).

Avant 8.4.0 (c'est-à-dire, pendant les dernières versions de 8.3 et la première partie du cycle de développement de 8.4), la structure Tcl_ChannelType contenait les champs suivants:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_ChannelTypeVersion version;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Lorsque cette structure est enregistrée comme type de canal, le champ version doit toujours être TCL_CHANNEL_VERSION_2.
