ARGUMENTS

Tcl_Interp *interp (in)
Interpréteur auquel la limite gérée s'applique ou dont les limites doivent être vérifiées.
int type (in)
Le type de limite auquel l'opération se réfère. Il doit s'agir de TCL_LIMIT_COMMANDS ou TCL_LIMIT_TIME.
int commandLimit (in)
Le nombre maximum de commandes (tel que rapporté par info cmdcount) qui peuvent être exécutées dans l'interpréteur.
Tcl_Time *timeLimitPtr (in/out)
Un pointeur vers une structure qui contiendra la nouvelle limite de temps lue (Tcl_LimitSetTime) ou la limite de temps actuelle écrite (Tcl_LimitGetTime).
int granularity (in)
Un diviseur indiquant combien de temps doit s'écouler entre les vérifications d'une limite spécifique. Doit être au moins 1.
Tcl_LimitHandlerProc *handlerProc (in)
Fonction à appeler lorsqu'une limite est dépassée. Si le handlerProc supprime ou augmente la limite pendant son exécution, l'interpréteur limité sera autorisé à continuer le traitement après le retour du gestionnaire. Plusieurs gestionnaires peuvent être associés au même interpréteur limité ; l'ordre d'exécution n'est pas défini et ils doivent être identifiés par handlerProc et clientData lors de leur suppression.
ClientData clientData (in)
Une donnée de type mot arbitraire utilisée pour transmettre le contexte à la fonction handlerProc.
Tcl_LimitHandlerDeleteProc *deleteProc (in)
Fonction à appeler lorsqu'un gestionnaire est supprimé. Peut être NULL si le clientData ne nécessite pas de suppression.

DESCRIPTION

Le système de limites de temps pour l'interpréteur Tcl permet un contrôle précis sur le temps qu'un script peut utiliser et est utile dans les cas où un programme est divisé en plusieurs parties, dont certaines sont plus fiables que d'autres (par exemple, les serveurs d'applications Web).

Chaque interpréteur peut avoir une limite de temps d'exécution et une limite de commandes qu'il peut exécuter. Étant donné que le contrôle de ces limites peut potentiellement être coûteux (en particulier la limite de temps), chaque limite a également une politique de granularité, qui est un diviseur pour un compte interne de points où une vérification peut être effectuée (ce qui se produit immédiatement avant l'exécution d'une commande et à une fréquence indéterminée entre les exécutions de commandes, ce qui peut se produire dans des boucles while vides).

La partie finale du moteur de limites est un schéma de rappels qui permet des notifications lorsqu'une limite est dépassée. Ces rappels peuvent simplement fournir un enregistrement, ou ils peuvent allouer plus de ressources à l'interpréteur pour lui permettre de continuer à traiter plus longtemps.

Lorsqu'une limite est dépassée (et que les rappels ont été exécutés ; l'ordre d'exécution des rappels n'est pas défini), le traitement dans l'interpréteur limité est arrêté en lançant une erreur et en définissant un indicateur qui empêche l'instruction catch dans cet interpréteur de capturer cette erreur. Il incombe au contexte qui a initié le traitement dans cet interpréteur (généralement l'interpréteur principal) de gérer l'erreur.

API DE VÉRIFICATION DES LIMITES

Pour vérifier les limites de ressources dans un interpréteur, appelez Tcl_LimitCheck, qui renvoie TCL_OK si la limite n'a pas été dépassée (après traitement des rappels) et TCL_ERROR si la limite a été dépassée (auquel cas un message d'erreur est également placé dans le résultat de l'interpréteur). Cette fonction ne doit être appelée que lorsque Tcl_LimitReady renvoie une valeur non nulle afin que la politique de granularité soit exécutée. Cette API est conçue pour être similaire en utilisation à Tcl_AsyncReady et Tcl_AsyncInvoke.

Lorsque vous écrivez du code qui pourrait se comporter comme catch en ce qui concerne les erreurs, vous ne devez capturer une erreur que si Tcl_LimitExceeded renvoie zéro. S'il renvoie une valeur non nulle, l'interpréteur est dans un état de limite dépassée et les erreurs doivent être propagées au contexte d'appel. Vous pouvez également vérifier si un type particulier de limite a été dépassé en utilisant Tcl_LimitTypeExceeded.

CONFIGURATION DES LIMITES

Pour vérifier si une limite a été définie (mais pas nécessairement dépassée) dans un interpréteur, appelez Tcl_LimitTypeEnabled avec le type de limite que vous souhaitez vérifier. Pour activer une limite, appelez Tcl_LimitTypeSet et pour désactiver une limite, appelez Tcl_LimitTypeReset.

Le niveau d'une limite de commandes peut être défini à l'aide de Tcl_LimitSetCommands et récupéré à l'aide de Tcl_LimitGetCommands. De même, pour une limite de temps, elle peut être définie à l'aide de Tcl_LimitSetTime et Tcl_LimitGetTime, mais avec cette API, la limite de temps est copiée de la structure Tcl_Time vers laquelle pointe l'argument timeLimitPtr.

Le degré de granularité d'une limite peut être défini à l'aide de Tcl_LimitSetGranularity et récupéré à l'aide de Tcl_LimitGetGranularity. Vous devez vous rappeler que les granularités doivent toujours être positives.

RAPPELS DE LIMITES

Pour ajouter un rappel de gestionnaire à appeler lorsqu'une limite est dépassée, appelez Tcl_LimitAddHandler. L'argument handlerProc décrit la fonction à appeler ; il doit avoir le prototype suivant :

typedef void Tcl_LimitHandlerProc(
        ClientData clientData,
        Tcl_Interp *interp);

L'argument clientData de la fonction de gestionnaire sera ce qui a été passé à l'argument clientData de Tcl_LimitAddHandler, et interp est l'interpréteur dont la limite a été dépassée.

L'argument deleteProc de Tcl_LimitAddHandler est une fonction à appeler pour supprimer la valeur de clientData. Il peut s'agir de TCL_STATIC ou NULL s'aucune action de suppression n'est nécessaire, ou TCL_DYNAMIC si seule la libération de la structure avec Tcl_Free est nécessaire. Sinon, il doit faire référence à une fonction ayant le prototype suivant :

typedef void Tcl_LimitHandlerDeleteProc(
        ClientData clientData);

Un gestionnaire de limite peut être supprimé en utilisant Tcl_LimitRemoveHandler ; le gestionnaire supprimé sera le premier trouvé (parmi les gestionnaires ajoutés avec Tcl_LimitAddHandler) avec exactement les mêmes arguments type, handlerProc et clientData. Cette fonction appelle toujours le deleteProc sur le clientData (sauf si le deleteProc est NULL ou TCL_STATIC).
