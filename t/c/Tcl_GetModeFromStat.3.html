DESCRIPTION

Il y a plusieurs raisons d'appeler les fonctions de l'API Tcl_FS (par ex. Tcl_FSAccess et Tcl_FSStat) plutôt que d'appeler directement des fonctions de niveau système comme access et stat. Premièrement, elles fonctionnent sur plusieurs plateformes, donc une extension qui les appelle devrait fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige certains bugs dans les appels de niveau système. Troisièmement, ces appels de fonction gèrent les conversions de chemin "Utf vers natif de la plateforme" qui peuvent être nécessaires (et peuvent mettre en cache les résultats de telles conversions pour une plus grande efficacité lors d'appels ultérieurs). Quatrièmement, et peut-être le plus important, toutes ces fonctions sont "conscientes du système de fichiers virtuel". Tout système de fichiers virtuel (VFS pour faire court) qui a été enregistré (via Tcl_FSRegister) peut rediriger l'accès aux fichiers vers des supports ou des méthodes d'accès alternatives. Cela signifie que toutes ces fonctions (et donc les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent opérer sur des "fichiers" qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS pour faire court) via cette API est automatiquement "consciente du système de fichiers virtuel". Bien sûr, si une extension accède directement au système de fichiers natif (via des API spécifiques à la plateforme, par exemple), Tcl ne peut pas intercepter de tels appels.

Si les VFS appropriés ont été enregistrés, les "fichiers" peuvent, pour donner deux exemples, être distants (par ex. situés sur un serveur ftp distant) ou archivés (par ex. situés à l'intérieur d'une archive .zip). De tels systèmes de fichiers enregistrés fournissent une table de correspondance de fonctions pour implémenter tout ou partie de la fonctionnalité listée ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat abstrait ce qu'est réellement le tampon "struct stat", permettant d'utiliser le même code à la fois sur les systèmes qui prennent en charge les fichiers de plus de 2 Go et sur ceux qui n'en prennent pas en charge.

L'API Tcl_FS est basée sur Tcl_Obj et peut mettre en cache des représentations internes et d'autres chaînes relatives aux chemins (par ex. le répertoire de travail courant). Un effet secondaire de ceci est qu'il ne faut pas passer de valeurs avec un compteur de références de zéro à aucune de ces fonctions. Si de tels appels étaient traités, ils pourraient entraîner des fuites de mémoire (dans certaines circonstances, le code du système de fichiers peut souhaiter conserver une référence à la valeur passée, et il ne faut donc pas supposer qu'après le retour de l'un de ces appels, la valeur a toujours un compteur de références de zéro - il peut avoir été incrémenté) ou un segmentation fault direct (ou autre erreur d'accès mémoire) en raison de la libération de la valeur en cours de manipulation complexe de valeur nécessaire pour garantir que le chemin est entièrement normalisé et absolu pour la détermination du système de fichiers. La leçon pratique à tirer de ceci est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect, et peut causer des erreurs de mémoire. Le compteur de références de path doit être incrémenté avant d'être passé, ou décrémenté. Pour cette raison, les valeurs avec un compteur de références de zéro sont considérées comme des chemins de système de fichiers invalides et l'appel de toute fonction de l'API Tcl_FS avec une telle valeur n'aura aucun effet.

FONCTIONS DE L'API FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction "copier fichier" de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno au code d'erreur POSIX "EXDEV" (qui signifie "lien cross-domain").

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction "copier fichier" de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno au code d'erreur POSIX "EXDEV" (qui signifie "lien cross-domain").

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction "créer répertoire" du système de fichiers propriétaire.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction "supprimer fichier" du système de fichiers propriétaire.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction "supprimer répertoire" du système de fichiers propriétaire.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction "renommer fichier" de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno au code d'erreur POSIX "EXDEV" (qui signifie "lien cross-domain").

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction "lister volumes" non-NULL et leur demande de retourner leur liste de volumes racine. Elle accumule les valeurs de retour dans une liste qui est retournée à l'appelant (avec un compteur de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant l'encodage identifié par encodingName et évalue son contenu comme un script Tcl. Elle retourne les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, l'encodage système est utilisé pour lire le contenu du fichier. Si le fichier n'a pas pu être lu, une erreur Tcl est retournée pour décrire pourquoi le fichier n'a pas pu être lu. Le caractère de fin de fichier (eofchar) pour les fichiers est "\x1A" (^Z) pour toutes les plateformes. Si vous avez besoin d'un "^Z" dans le code pour une comparaison de chaînes, vous pouvez utiliser "\x1A", qui sera substitué en toute sécurité par l'interpréteur Tcl en "^Z". Tcl_FSEvalFile est une version simplifiée de Tcl_FSEvalFileEx qui utilise toujours l'encodage système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier binaire en mémoire et retourne les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas, en raison des limitations du système d'exploitation dans le chargement dynamique de code binaire), Tcl tentera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile inverse l'opération, demandant que la bibliothèque indiquée par loadHandle soit retirée du processus. Notez que, contrairement à la commande unload, cela ne donne pas à la bibliothèque aucune opportunité de nettoyage.

Les deux fonctions ci-dessus retournent un code de complétion Tcl standard. En cas d'erreur, un message d'erreur est laissé dans le résultat de l'interpréteur (interp). Le jeton fourni via la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher dans un répertoire tous les fichiers qui correspondent à un motif donné. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le globbing. Les messages d'erreur sont placés dans l'interpréteur (sauf si l'interpréteur est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Notez que le code glob implémente les motifs récursifs en interne, donc cette fonction ne recevra que des motifs simples, qui peuvent être mis en correspondance en utilisant la logique de string match. Pour gérer la récursivité, Tcl appellera cette fonction fréquemment en demandant uniquement le retour des répertoires. Un cas spécial où elle est appelée avec un motif NULL indique que le chemin doit être vérifié uniquement pour le type correct.

Tcl_FSLink remplace la version bibliothèque de readlink, et l'étend pour supporter la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr sera appelée.

Si toPtr est NULL, une action de "lire le lien" est effectuée. Le résultat est un Tcl_Obj spécifiant le contenu du lien symbolique donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat est la propriété de l'appelant, qui devrait appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl devrait créer un lien d'un des types passés dans le drapeau linkAction. Ce drapeau est une combinaison OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Là où un choix existe (c'est-à-dire plus d'un drapeau est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur de retour devrait être toPtr (qui est donc déjà la propriété de l'appelant). En cas d'échec, NULL est retourné.

Tcl_FSLstat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (nlink, toujours 1 sous Windows), l'identifiant utilisateur (user id, toujours 0 sous Windows), l'identifiant groupe (group id, toujours 0 sous Windows), le périphérique réel (rdev, identique au périphérique sous Windows), la taille, la dernière a

temps d'accès, heure de dernière modification et heure de dernière modification des métadonnées. Voir PORTABLE STAT RESULT API pour une description de la façon d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSLstat retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné, et aucune information stat n'est fournie.

Tcl_FSUtime remplace la version bibliothèque de utime.

Retourne 0 en cas de succès et -1 en cas d'erreur (conformément à la documentation utime). En cas de succès, la fonction mettra à jour les valeurs « atime » et « mtime » du fichier donné.

Tcl_FSFileAttrsGet implémente l'accès en lecture pour la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

Si le résultat est TCL_OK, alors une valeur a été placée dans objPtrRef, qui ne sera valide que temporairement (sauf si Tcl_IncrRefCount est appelée).

Tcl_FSFileAttrsSet implémente l'accès en écriture pour la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

Tcl_FSFileAttrStrings implémente une partie de la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La procédure appelée peut soit retourner un tableau de chaînes, soit retourner NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle devrait avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer qu'il conserve un compteur de références pour la valeur.

Tcl_FSAccess vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou autre objet du système de fichiers) dont le nom est pathname. Si pathname est un lien symbolique sous Unix, les permissions du fichier auquel ce lien symbolique fait référence sont testées.

En cas de succès (toutes les permissions demandées accordées), zéro est retourné. En cas d'erreur (au moins un bit dans le mode demandé pour une permission refusée, ou une autre erreur s'est produite), -1 est retourné.

Tcl_FSStat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le temps de dernier accès, le temps de dernière modification et le temps de dernière modification des métadonnées. Voir PORTABLE STAT RESULT API pour une description de la façon d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSStat retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné, et aucune information stat n'est fournie.

Tcl_FSOpenFileChannel ouvre un fichier spécifié par pathPtr et retourne un handle de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est modelée sur la procédure fopen de la bibliothèque standard d'E/S Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannel retourne NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannel laisse un message d'erreur dans le résultat de interp après toute erreur.

Le canal nouvellement créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez Tcl_RegisterChannel. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, l'acte de création du nouveau canal l'assigne également comme remplacement pour le canal standard.

Tcl_FSGetCwd remplace la version bibliothèque de getcwd.

Retourne le répertoire de travail courant de la bibliothèque Tcl. Celui-ci peut être différent du répertoire de travail de la plateforme native, ce qui se produit lorsque le répertoire de travail courant n'est pas dans le système de fichiers natif.

Le résultat est un pointeur vers un Tcl_Obj spécifiant le répertoire courant, ou NULL si le répertoire courant n'a pas pu être déterminé. Si NULL est retourné, un message d'erreur est laissé dans le résultat de interp.

Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compteur de références doit être décrémenté. Ceci est nécessaire pour des raisons de sécurité des threads, pour permettre à plusieurs threads d'accéder à cette fonction et aux fonctions associées, tout en garantissant que les résultats sont toujours valides.

Tcl_FSChdir remplace la version bibliothèque de chdir. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl se rabattra sur une combinaison de stat et access pour vérifier si le répertoire existe et a les permissions appropriées.

Pour les résultats, voir la documentation chdir. En cas de succès, nous conservons une trace du chemin réussi dans cwdPathPtr pour les appels ultérieurs à Tcl_FSGetCwd.

Tcl_FSPathSeparator retourne le caractère séparateur à utiliser pour l'élément le plus spécifique du chemin spécifié par pathPtr (c'est-à-dire la dernière partie du chemin).

Le séparateur est retourné sous forme de Tcl_Obj contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est retourné.

Tcl_FSJoinPath prend le Tcl_Obj donné, qui doit être une liste valide (qui est autorisée à avoir un compteur de références de zéro), et retourne la valeur du chemin donnée en considérant les elements premiers éléments comme des segments de chemin valides (chaque segment de chemin peut être un chemin complet, un chemin partiel ou juste un nom de répertoire ou de fichier possible). Si un segment de chemin est en fait un chemin absolu, alors tous les segments de chemin précédents sont discardés. Si elements est inférieur à 0, nous utilisons la liste entière.

Il est possible que la valeur retournée soit en fait un élément de la liste donnée, l'appelant doit donc faire attention à incrémenter le compteur de références du résultat avant de libérer la liste.

La valeur retournée, typiquement avec un compteur de références de zéro (mais elle pourrait être partagée dans certaines conditions), contient le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. En particulier, la valeur retournée pourrait être un élément de la liste donnée, donc libérer la liste pourrait libérer la valeur prématurément si aucun compteur de références n'a été pris. Si le nombre d'éléments est zéro, alors la valeur retournée sera un Tcl_Obj de chaîne vide.

Tcl_FSSplitPath prend le Tcl_Obj donné, qui devrait être un chemin valide, et retourne une valeur de liste Tcl contenant chaque segment de ce chemin comme un élément. Elle retourne une valeur de liste avec un compteur de références de zéro. Si lenPtr passé est non NULL, la variable à laquelle il pointe sera mise à jour pour contenir le nombre d'éléments dans la liste retournée.

Tcl_FSEqualPaths teste si les deux chemins donnés représentent le même objet du système de fichiers. Il retourne 1 si les chemins sont égaux, et 0 s'ils sont différents. Si l'un des chemins est NULL, 0 est toujours retourné.

Tcl_FSGetNormalizedPath tente d'extraire du Tcl_Obj donné une représentation unique et normalisée du chemin, dont la valeur de chaîne peut être utilisée comme identifiant unique du fichier.

Il retourne la valeur du chemin normalisé, détenue par Tcl, ou NULL si le chemin était invalide ou ne pouvait pas être converti avec succès. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère sur ces représentations en interne), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques puisse ne pas être la version la plus conviviale d'un chemin. La valeur retournée est détenue par Tcl et a une durée de vie équivalente à celle de pathPtr passé (sauf si c'est un chemin relatif, auquel cas la valeur du chemin normalisé peut être libérée à chaque changement de cwd) - l'appelant peut bien sûr incrémenter le compteur de références s'il souhaite conserver une copie plus longtemps.

Tcl_FSJoinToPath prend la valeur donnée, qui devrait généralement être un chemin valide ou NULL, et y joint le tableau de segments de chemin donnés.

Retourne une valeur, typiquement avec un compteur de références de zéro (mais elle pourrait être partagée dans certaines conditions), contenant le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. Si l'une des valeurs passées à cette fonction (pathPtr ou éléments de path) a un compteur de références de zéro, elle sera libérée lorsque cette fonction retournera.

Tcl_FSConvertToPathType essaie de convertir le Tcl_Obj donné en un type de chemin Tcl valide, en tenant compte du fait que le cwd a pu changer même si cette valeur est déjà censée être du bon type. Le nom de fichier peut commencer par « ~ » (pour indiquer le répertoire personnel de l'utilisateur courant) ou « ~<utilisateur> » (pour indiquer le répertoire personnel de n'importe quel utilisateur).

Si la conversion réussit (c'est-à-dire si la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), alors TCL_OK est retourné. Sinon, TCL_ERROR est retourné, et un message d'erreur peut être laissé dans l'interpréteur.

Tcl_FSGetInternalRep extrait la représentation interne d'une valeur de chemin donnée, dans le système de fichiers donné. Si la valeur du chemin appartient à un système de fichiers différent, nous retournons NULL. Si la représentation interne est actuellement NULL, nous essayons de la générer, en appelant Tcl_FSCreateInternalRepProc du système de fichiers.

Retourne NULL ou une représentation interne de chemin valide. Cette représentation interne est mise en cache, de sorte que les appels répétés à cette fonction ne nécessiteront pas de conversions supplémentaires.

Tcl_FSGetTranslatedPath tente d'extraire le chemin traduit du Tcl_Obj donné.

Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), elle est retournée. Sinon, NULL sera retourné, et un message d'erreur peut être laissé dans l'interpréteur. Un chemin « traduit » est un chemin qui ne contient pas de séquences « ~ » ou « ~utilisateur » (celles-ci ont été développées dans leur représentation actuelle dans le système de fichiers). La valeur retournée est détenue par l'appelant, qui doit la stocker ou appeler Tcl_DecrRefCount pour s'assurer que la mémoire est libérée. Cette fonction a peu d'utilité pratique, et Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des besoins.

Tcl_FSGetTranslatedStringPath fait la même chose que Tcl_FSGetTranslatedPath, mais retourne une chaîne de caractères ou NULL. La chaîne retournée est allouée dynamiquement

d et appartient à l'appelant, qui doit le stocker ou appeler ckfree pour s'assurer qu'il est libéré. Encore une fois, Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des objectifs.

Tcl_FSNewNativePath effectue quelque chose comme l'inverse des conversions habituelles obj->path->nativerep. Si un code récupère un chemin sous forme native (provenant, par exemple, de readlink ou d'une boîte de dialogue native), et que ce chemin doit être utilisé au niveau Tcl, alors appeler cette fonction est un moyen efficace de créer le type de valeur de chemin approprié.

La valeur résultante est une valeur de type « chemin » pure, qui ne recevra une représentation sous forme de chaîne UTF-8 que si cela est requis par un code Tcl.

Tcl_FSGetNativePath est destiné à être utilisé par les systèmes de fichiers natifs Win/Unix, afin qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un wrapper de commodité autour de Tcl_FSGetInternalRep. Il peut être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes (par exemple, sur macOS, une représentation utilisant une structure fileSpec de FSRef serait probablement plus efficace). Sur Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Actuellement, la représentation est simplement une chaîne de caractères qui peut contenir soit le chemin relatif, soit un chemin absolu normalisé complet dans le codage natif (des conditions complexes dictent lequel de ceux-ci sera fourni, de sorte qu'aucun ne peut être garanti, à moins que le chemin ne soit connu pour être absolu). Si vous avez besoin d'un chemin natif qui doit être absolu, vous devriez demander la version native d'un chemin normalisé. Si pour une raison quelconque une version non absolue et non normalisée du chemin est nécessaire, elle doit être construite séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache de sorte que les appels répétés à cette fonction n'entraînent pas de conversions supplémentaires. La valeur de retour appartient à Tcl et a une durée de vie équivalente à celle du pathPtr passé (sauf s'il s'agit d'un chemin relatif, auquel cas la représentation native peut être libérée à tout moment lorsque le cwd change).

Tcl_FSFileSystemInfo renvoie une liste de deux éléments. Le premier élément est le nom du système de fichiers (par exemple, « native », « vfs », « zip », ou « prowrap », potentiellement), et le second est le type particulier du chemin donné au sein de ce système de fichiers (qui dépend du système de fichiers). Le second élément peut être vide si le système de fichiers ne fournit pas de catégorisation supplémentaire des fichiers.

Une valeur de liste valide est renvoyée, sauf si la valeur du chemin n'est pas reconnue, auquel cas NULL sera renvoyé.

Tcl_FSGetFileSystemForPath renvoie un pointeur vers le Tcl_Filesystem qui accepte ce chemin comme valide.

Si aucun système de fichiers n'accepte le chemin, NULL est renvoyé.

Tcl_FSGetPathType détermine si le chemin donné est relatif au répertoire courant, relatif au volume courant, ou absolu.

Il renvoie l'une des valeurs TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, ou TCL_PATH_VOLUME_RELATIVE

L'API DU SYSTÈME DE FICHIERS VIRTUELS

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un système de fichiers ; ces opérations sont invoquées au besoin par la couche générique, ce qui se produit généralement via les fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un élément de données facultatif à associer à ce système de fichiers. Lors de l'appel de cette fonction, Tcl attache le système de fichiers à la liste des systèmes de fichiers connus, et il devient pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera renvoyé.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et renvoie TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est renvoyé.

Tcl_FSData renvoie le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il renvoie NULL.

Tcl_FSMountsChanged est utilisé pour informer le noyau de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (dont la plupart doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni) et fonctions d'efficacité (qui n'ont besoin d'être implémentées que si elles peuvent l'être efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces solutions de repli ne sont utilisées que pour gérer les commandes initiées dans Tcl, pas dans C. Cela signifie que si une commande file rename est émise dans Tcl, et que le(s) système(s) de fichiers pertinent(s) n'implémentent pas leur Tcl_FSRenameFileProc, le noyau de Tcl se rabattra sur une combinaison d'autres fonctions du système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a une autre solution de repli). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun de ces rabattements ne se produit. Ceci est vrai sauf pour les quatre dernières entrées du tableau des systèmes de fichiers (lstat, load, getcwd et chdir) pour lesquelles des rabattements se produisent effectivement au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme de Tcl_Obj les prennent sous forme UTF-8. L'API d'infrastructure du système de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

Fonction pour traiter un appel Tcl_FSOpenFileChannel. Doit être implémentée pour tout système de fichiers raisonnable, car toutes les opérations qui nécessitent l'ouverture ou l'accès au contenu d'un fichier l'utiliseront (par exemple, open, encoding et de nombreuses commandes Tk).

La fonction doit renvoyer tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au motif donné et respectent la spécification de types donnée. Il y a deux façons dont cette fonction peut être appelée. Si pattern est NULL, alors pathPtr est une spécification de chemin complet d'un seul fichier ou répertoire qui doit être vérifié pour son existence et son type correct. Sinon, pathPtr est un répertoire, dont le contenu la fonction doit rechercher les fichiers ou répertoires qui ont le type correct. Dans les deux cas, pathPtr peut être supposé être non NULL et non vide. Il n'est pas actuellement documenté si pathPtr aura ou non un séparateur de fichier à la fin, donc le code doit être flexible aux deux possibilités.

Le résultat est détenu par l'appelant (et doit donc avoir son compteur de références incrémenté avant d'être renvoyé). Tous les appelants doivent appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'est plus nécessaire. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Le résultat dans ce cas doit être toPtr si le lien a réussi et NULL sinon. Dans ce cas, le résultat n'est pas détenu par l'appelant (c'est-à-dire qu'aucune manipulation de compteur de références des deux côtés n'est nécessaire). Voir la documentation de Tcl_FSLink pour l'interprétation correcte des indicateurs linkAction.

Le résultat doit être une liste de volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. Tcl utilisera le contenu de la liste et décrémentera ensuite ce compteur de références. Cela permet aux systèmes de fichiers de choisir s'ils souhaitent réellement conserver une liste « globale » de volumes ou non (sinon, ils génèrent la liste à la volée et la transmettent à Tcl avec un compteur de références de 1 et oublient ensuite la liste ; sinon, ils incrémentent simplement le compteur de références de leur liste globale et la transmettent à Tcl qui copiera le contenu puis décrémentera le compteur pour revenir à son état précédent).

REMOVEDIRECTORYPROC

typedef int Tcl_FSRemoveDirectoryProc(

FILESYSTEM EFFICIENCY

Ces fonctions n'ont pas besoin d'être implémentées pour un système de fichiers particulier car le noyau dispose d'une implémentation de secours disponible. Voir chaque description individuelle pour les conséquences de laisser le champ NULL.

LSTATPROC

Fonction pour traiter un appel à Tcl_FSLstat. Si elle n'est pas implémentée, Tcl essaiera d'utiliser statProc défini précédemment. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut faire la distinction entre les appels stat et lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le comportement de cette fonction est très similaire à celui de Tcl_FSStatProc défini précédemment, sauf que si elle s'applique à un lien symbolique, elle renvoie des informations sur le lien, et non sur le fichier cible.

COPYFILEPROC

Fonction pour traiter un appel à Tcl_FSCopyFile. Si elle n'est pas implémentée, Tcl utilisera open-r, open-w et fcopy comme mécanisme de copie. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un code de retour standard de Tcl indiquant si une erreur s'est produite pendant la copie. Notez que destPathPtr est le nom du fichier qui doit devenir une copie de srcPathPtr. Ce n'est jamais le nom d'un répertoire dans lequel srcPathPtr peut être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande file copy au niveau Tcl). Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non copyDirectoryProc lorsque cela est nécessaire pour les copier (même s'ils sont des liens symboliques vers des répertoires). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file copy, l'appel à Tcl_SetErrno(EXDEV) et le renvoi d'un résultat autre que TCL_OK indiquent à Tcl d'utiliser ses mécanismes de secours standard.

RENAMEFILEPROC

Fonction pour traiter un appel à Tcl_FSRenameFile. Si elle n'est pas implémentée, Tcl utilisera un mécanisme de copie et de suppression. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un code de retour standard de Tcl indiquant si une erreur s'est produite pendant le processus de renommage. Si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file rename, l'appel à Tcl_SetErrno(EXDEV) et le renvoi d'un résultat autre que TCL_OK indiquent à Tcl d'utiliser ses mécanismes de secours standard.

COPYDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSCopyDirectory. Si elle n'est pas implémentée, Tcl utilisera un mécanisme récursif de file mkdir, file copy. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

La valeur de retour est un code de retour standard de Tcl indiquant si une erreur s'est produite pendant le processus de copie. Si une erreur se produit, le nom du fichier ou du répertoire qui a causé l'erreur doit se trouver dans errorPtr. Notez que destPathPtr est le nom du répertoire qui doit devenir une image de srcPathPtr. Ce n'est pas le nom d'un répertoire dans lequel srcPathPtr peut être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande file copy au niveau Tcl). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de copie de répertoire, l'appel à Tcl_SetErrno(EXDEV) et le renvoi d'un résultat autre que TCL_OK indiquent à Tcl d'utiliser ses mécanismes de secours standard.

LOADFILEPROC

Fonction pour traiter un appel à Tcl_FSLoadFile. Si elle n'est pas implémentée, Tcl utilisera une copie vers un fichier temporaire, suivie d'un appel à Tcl_FSLoadFile sur ce fichier temporaire. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut charger du code directement, ou si elle peut être implémentée simplement en renvoyant TCL_ERROR pour désactiver la fonctionnalité de chargement sur ce système de fichiers.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Renvoie un code de complétion standard de Tcl. En cas d'erreur, un message d'erreur se trouve dans le résultat de interp. La fonction charge dynamiquement un fichier de code binaire en mémoire. En cas de succès, handlePtr doit être rempli avec un jeton pour le fichier chargé dynamiquement, et unloadProcPtr doit être rempli avec l'adresse d'une procédure. La procédure de déchargement sera appelée avec le Tcl_LoadHandle donné comme seul paramètre lorsque Tcl aura besoin de décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle renvoyé est actuellement un jeton qui peut être utilisé dans TclpFindSymbol pour accéder aux fonctions du nouveau code. Chaque système de fichiers peut définir le Tcl_LoadHandle comme il le souhaite. Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de chargement de fichier, l'appel à Tcl_SetErrno(EXDEV) et le renvoi d'un résultat autre que TCL_OK indiquent à Tcl d'utiliser ses mécanismes de secours standard.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Fonction pour traiter un appel à Tcl_FSGetCwd. La plupart des systèmes de fichiers n'ont pas besoin de l'implémenter. Elle est généralement appelée une fois, si getcwd est appelé avant chdir. Elle peut être NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si le système de fichiers prend en charge un concept natif de répertoire de travail courant (qui peut changer indépendamment de Tcl), cette fonction devrait renvoyer ce cwd en tant que résultat, ou NULL si le répertoire de travail courant ne peut pas être déterminé (par exemple, l'utilisateur n'a pas les permissions appropriées dans le répertoire cwd). Si NULL est renvoyé, un message d'erreur se trouve dans le résultat de interp.

CHDIRPROC

Fonction pour traiter un appel à Tcl_FSChdir. Si les systèmes de fichiers n'implémentent pas celle-ci, elle est émule par une série de vérifications d'accès aux répertoires. Autrement, les systèmes virtuels qui l'implémentent ne devraient renvoyer qu'un résultat positif si pathPtr est un répertoire valide et accessible dans leur système de fichiers. Ils ne devraient pas mémoriser le résultat, car ce résultat sera automatiquement mémorisé par Tcl_FSGetCwd. Les systèmes de fichiers réels devraient effectuer l'action correcte (c'est-à-dire appeler l'API chdir correspondante du système).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

La fonction Tcl_FSChdirProc change le répertoire de travail courant de l'application vers la valeur spécifiée dans pathPtr. La fonction renvoie -1 en cas d'erreur ou 0 en cas de succès.
