DESCRIPTION

Il y a plusieurs raisons d'appeler les fonctions de l'API Tcl_FS (par exemple, Tcl_FSAccess et Tcl_FSStat) plutôt que d'appeler directement des fonctions de niveau système comme access et stat. Premièrement, elles fonctionnent sur différentes plates-formes, de sorte qu'une extension qui les appelle devrait fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige des bugs dans les appels de niveau système. Troisièmement, ces appels de fonction gèrent les conversions de chemin « Utf vers natif de la plate-forme » qui peuvent être nécessaires (et peuvent mettre en cache les résultats de telles conversions pour une plus grande efficacité lors des appels ultérieurs). Quatrièmement, et peut-être le plus important, toutes ces fonctions sont « conscientes du système de fichiers virtuel ». Tout système de fichiers virtuel (VFS pour faire court) qui a été enregistré (via Tcl_FSRegister) peut réacheminer l'accès aux fichiers vers des supports ou des méthodes d'accès alternatifs. Cela signifie que toutes ces fonctions (et donc les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent fonctionner sur des « fichiers » qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS pour faire court) via cette API est automatiquement « consciente du système de fichiers virtuel ». Bien sûr, si une extension accède directement au système de fichiers natif (via des API spécifiques à la plate-forme, par exemple), Tcl ne peut pas intercepter de tels appels.

Si des VFS appropriés ont été enregistrés, les « fichiers » peuvent, pour donner deux exemples, être distants (par exemple, situés sur un serveur ftp distant) ou archivés (par exemple, se trouvant à l'intérieur d'une archive .zip). De tels systèmes de fichiers enregistrés fournissent une table de correspondance de fonctions pour implémenter tout ou partie de la fonctionnalité énumérée ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat s'abstrait du contenu du tampon « struct stat », permettant d'utiliser le même code à la fois sur les systèmes avec et sans prise en charge des fichiers de plus de 2 Go. taille.

L'API Tcl_FS est « Tcl_Obj-ifiée » et peut mettre en cache des représentations internes et d'autres chaînes liées aux chemins (par exemple, le répertoire de travail actuel). Un effet secondaire est qu'il ne faut pas passer de valeurs avec un compteur de références de zéro à l'une de ces fonctions. Si de tels appels étaient gérés, ils pourraient entraîner des fuites de mémoire (dans certaines circonstances, le code du système de fichiers peut souhaiter conserver une référence à la valeur passée, et il ne faut donc pas supposer qu'après le retour de l'un de ces appels, la valeur a toujours un compteur de références de zéro - il peut avoir été incrémenté) ou un segmentation fault direct (ou autre erreur d'accès à la mémoire) en raison de la libération de la valeur en cours de manipulation complexe de valeur requise pour garantir que le chemin est entièrement normalisé et absolu pour la détermination du système de fichiers. La leçon pratique à retenir est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect et peut causer des erreurs de mémoire. Le path doit avoir son compteur de références incrémenté avant d'être passé, ou décrémenté. Pour cette raison, les valeurs avec un compteur de références de zéro ne sont pas considérées comme des chemins de système de fichiers valides et tout appel à une fonction de l'API Tcl_FS avec une telle valeur n'entraînera aucune action.

FONCTIONS DE L'API FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable C globale errno sur le code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable C globale errno sur le code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction « créer un répertoire » du système de fichiers propriétaire.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction « supprimer un fichier » du système de fichiers propriétaire.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction « supprimer un répertoire » du système de fichiers propriétaire.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr en le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « renommer un fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable C globale errno sur le code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction « lister les volumes » non NULL et leur demande de retourner leur liste de volumes racine. Elle accumule les valeurs de retour dans une liste qui est retournée à l'appelant (avec un compteur de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant le codage identifié par encodingName et évalue son contenu comme un script Tcl. Elle retourne les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, le codage système est utilisé pour lire le contenu du fichier. Si le fichier n'a pas pu être lu, une erreur Tcl est retournée pour décrire pourquoi le fichier n'a pas pu être lu. Le caractère de fin de fichier est « \x1A » (^Z) pour toutes les plateformes. Si vous avez besoin d'un « ^Z » dans une chaîne pour comparaison, vous pouvez utiliser « \x1A », qui sera remplacé en toute sécurité par l'interpréteur Tcl en « ^Z ». Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours le codage système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier de code binaire en mémoire et retourne les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas, en raison des limitations du système d'exploitation dans le chargement dynamique de code binaire), Tcl tentera de copier le fichier vers un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile inverse l'opération, demandant que la bibliothèque indiquée par loadHandle soit supprimée du processus. Notez que, contrairement à la commande unload, cela ne donne aucune possibilité à la bibliothèque de nettoyage.

Les deux fonctions ci-dessus retournent un code d'achèvement Tcl standard. En cas d'erreur, un message d'erreur est laissé dans le résultat de interp.

Le jeton fourni via la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher dans un répertoire tous les fichiers qui correspondent à un modèle donné. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le globbing. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr.

Notez que le code glob implémente les modèles récursifs en interne, donc cette fonction ne recevra jamais que des modèles simples, qui peuvent être mis en correspondance en utilisant la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment en demandant uniquement que les répertoires soient retournés. Un cas spécial est d'être appelé avec un modèle NULL, indiquant que le chemin doit être vérifié uniquement pour le type correct.

Tcl_FSLink remplace la version bibliothèque de readlink, et l'étend pour prendre en charge la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr sera appelée.

Si toPtr est NULL, une action de « lecture de lien » est effectuée. Le résultat est un Tcl_Obj spécifiant le contenu du lien symbolique donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant, qui devrait appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl doit créer un lien d'un des types passés dans le drapeau linkAction. Ce drapeau est une combinaison OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'un choix existe (c'est-à-dire que plus d'un drapeau est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur de retour doit être toPtr (qui appartient donc déjà à l'appelant). En cas d'échec, NULL est retourné.

Tcl_FSAccess verifica si el proceso sería permitido a leer, escribir o testear la existencia de un archivo (o objeto de sistema de archivos) cuyo nombre es pathname. Si pathname es un enlace simbólico en Unix, se testan los permisos del archivo referido por este enlace simbólico. En caso de éxito (todas las permisos solicitadas se han concedido), se devuelve 0. En caso de error (al menos un bit en el modo solicitado es un permiso denegado, o se produjo otro error), se devuelve -1. Tcl_FSStat rellena el Tcl_StatBuf estructura statPtr con información sobre el archivo especificado. No se requieren derechos de acceso al archivo para obtener esta información, pero sí se requieren derechos de búsqueda en todos los directorios mencionados en la ruta que lleva al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, el inodo (siempre 0 en Windows), el modo de privilegio, el nlink (siempre 1 en Windows), el usuario id (siempre 0 en Windows), el grupo id (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), el tamaño, el tiempo de acceso más reciente, el tiempo de modificación más reciente y el tiempo de cambio de metadatos más reciente. Si path existe, Tcl_FSStat devuelve 0 y la estructura de estadísticas es rellenada con datos. De lo contrario, -1 es devuelto y no se dan datos de estadísticas. Tcl_FSOpenFileChannel abre un archivo especificado por pathPtr y devuelve un handle de canal que puede usarse para realizar entrada y salida en el archivo. Esta API está modelada después de la función fopen del biblioteca de I/O estándar Unix. El sintaxis y significado de todos los argumentos son similares a los dados en la comandos open de Tcl cuando se abre un archivo. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannel devuelve NULL y registra un código de error POSIX que puede ser recuperado con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannel deja un mensaje de error en interp's result después de cualquier error. El canal creado se registra en el interpretador proporcionado; para registrarlo, use Tcl_RegisterChannel. Si uno de los canales estándar, stdin, stdout o stderr fue previamente cerrado, la acción de crear el nuevo canal también lo asigna como sustituto del canal estándar. Tcl_FSGetCwd reemplaza la versión del biblioteca de getcwd. Devuelve el directorio de trabajo actual de la biblioteca Tcl. Este puede ser diferente al directorio de trabajo nativo, que ocurre cuando el directorio de trabajo actual no está en el sistema de archivos nativo. El resultado es un puntero a un Tcl_Obj especificando el directorio actual, o NULL si no se pudo determinar el directorio. Si se devuelve NULL, un mensaje de error se deja en interp's result. El resultado ya tiene su referencia count incrementada para el llamador. Cuando no es más necesario, ese reference count debe ser decrementado. Esto es necesario para la seguridad multi-threaded, para permitir múltiples hilos acceder a esta y funciones relacionadas, asegurando que los resultados siempre sean válidos. Tcl_FSChdir reemplaza la versión del biblioteca de chdir. El camino se normaliza y luego pasa a el sistema de archivos que lo reclama. Si ese sistema de archivos no implementa esta función, Tcl cae en una combinación de stat y access para verificar si el directorio existe y tiene permisos adecuados. Para los resultados, vea la documentación de chdir. Si es exitoso, se registra un registro de la ruta exitosa en cwdPathPtr para llamadas posteriores a Tcl_FSGetCwd. Tcl_FSPathSeparator devuelve el carácter de separador para el elemento más específico de la ruta especificada por pathPtr (es decir, el último parte de la ruta). El separador se devuelve como un Tcl_Obj conteniendo una cadena de longitud 1. Si la ruta es inválida, se devuelve NULL. Tcl_FSJoinPath toma el dado Tcl_Obj, que debe ser un lista válida (que permite tener un referencia count de cero), y devuelve el valor de ruta obtenido considerando los primeros elements elementos como segmentos válidos de ruta (cada segmento puede ser una ruta completa, una ruta parcial o solo un nombre posible de directorio o archivo). Si cualquier segmento de ruta es realmente una ruta absoluta, todos los segmentos previos son descartados. Si elements es menor que 0, usamos el todo el list. Es posible que el valor devuelto sea realmente un elemento del list dado, por lo que el llamador debe ser cuidadoso al incrementar la referencia count del valor antes de liberar el list. El valor devuelto, típicamente con una referencia count de cero (pero podría ser compartido en ciertas condiciones), contiene la ruta unida. El llamador debe agregar una referencia count al valor antes de usarlo. En particular, el valor devuelto podría ser un elemento del list dado, por lo que liberar el list podría liberar el valor prematuramente si no se ha tomado una referencia count. Si el número de elementos es cero, el valor devuelto será una cadena vacía Tcl_Obj. Tcl_FSSplitPath toma el dado Tcl_Obj, que debe ser una ruta válida, y devuelve un valor de lista con cada segmento de esa ruta como elemento. Devuelve un valor de lista con una referencia count de cero. Si el lenPtr pasado es no NULL, el variable que señala es actualizado para contener el número de elementos en el valor de lista devuelto. Tcl_FSEqualPaths prueba si las dos rutas dadas representan el mismo objeto de sistema de archivos. Devuelve 1 si las rutas son iguales, 0 si son diferentes. Si cualquiera de las rutas es NULL, se devuelve 0 siempre. Tcl_FSGetNormalizedPath intenta extraer de la ruta dada una representación normalizada única, cuyo valor de cadena puede usarse como un identificador único para el archivo. Devuelve la ruta normalizada, propiedad de Tcl, o NULL si la ruta era inválida o no pudo ser convertida con éxito. La extracción de rutas absolutas y normalizadas es muy eficiente (porque el sistema de archivos opera en estas representaciones internamente), aunque el resultado cuando el sistema de archivos contiene muchos enlaces simbólicos no necesariamente sea la versión más amigable de una ruta. El valor devuelto es propiedad de Tcl y tiene una vida útil equivalente a la del pathPtr pasado (excepto si es una ruta relativa, en la cual caso el valor normalizado puede ser liberado cualquier vez que cambie el cwd) - el llamador puede incrementar la referencia count si lo desea para mantener una copia más tiempo. Tcl_FSJoinToPath toma el valor dado, que suele ser una ruta válida o NULL, y une con el array de segmentos de rutas dados. Devuelve un valor, típicamente con una referencia count de cero (pero podría ser compartido en ciertas condiciones), conteniendo la ruta unida. El llamador debe agregar una referencia count al valor antes de usarlo. Si alguno de los valores pasados a esta función (pathPtr o path elementos) tiene una referencia count de cero, ellos se liberarán cuando esta función devuelva. Tcl_FSConvertToPathType intenta convertir el dado Tcl_Obj a un tipo de ruta válida, considerando que el cwd podría haber cambiado incluso si este valor ya se suponía de tipo correcto. El nombre del archivo puede comenzar con ~ (para indicar el directorio de usuario actual) o ~ (para indicar cualquier directorio de usuario). Si la conversión es exitosa (es decir, el valor es una ruta válida en una de las actualizaciones de sistemas de archivos), se devuelve TCL_OK. De lo contrario se devuelve TCL_ERROR, y un mensaje de error puede dejar en el interpretador. Tcl_FSGetInternalRep extrae la representación interna de un valor de ruta dado en un sistema de archivos específico. Si el valor de ruta pertenece a un sistema de archivos diferente, se devuelve NULL. Si la representación interna es actualmente NULL, se intenta generarla llamando a Tcl_FSCreateInternalRepProc del sistema de archivos. Devuelve NULL o una representación válida de la ruta interna. Esta representación interna es cachada, por lo que llamadas repetidas a esta función no requieren conversiones adicionales. Tcl_FSGetTranslatedPath intenta extraer la ruta traducida del dado Tcl_Obj. Si la traducción es exitosa (es decir, el valor es una ruta válida), se devuelve el valor. De lo contrario se devuelve NULL, y un mensaje de error puede dejar en el interpretador. Una ruta traducida es una que contiene ninguna secuencia de ~ (es decir, no contiene ~ o ~user) (estas han sido expandidas a su representación actual en el sistema de archivos). El valor devuelto es propiedad del llamador, que debe almacenarlo o llamar Tcl_DecrRefCount para asegurar que la memoria se libere. Esta función es de poca utilidad práctica, y Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath son usualmente mejores funciones para usar en la mayoría de los casos. Tcl_FSGetTranslatedStringPath realiza lo mismo que Tcl_FSGetTranslatedPath, pero devuelve una cadena de caracteres o NULL. El string devuelto es dinámicamente alojado.ated et appartient à l'appelant, qui doit le stocker ou appeler ckfree pour s'assurer qu'il est libéré. Encore une fois, Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des usages.

Tcl_FSNewNativePath effectue quelque chose comme l'inverse des conversions habituelles obj->chemin->représentation native. Si un code récupère un chemin sous forme native (depuis, par exemple, readlink ou une boîte de dialogue native), et que ce chemin doit être utilisé au niveau Tcl, alors l'appel de cette fonction est un moyen efficace de créer le type de valeur de chemin approprié.

La valeur résultante est une valeur de type "chemin" pure, qui ne recevra une représentation sous forme de chaîne UTF-8 que si cela est requis par du code Tcl.

Tcl_FSGetNativePath est destiné à être utilisé par les systèmes de fichiers natifs Win/Unix, afin qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un wrapper pratique autour de Tcl_FSGetInternalRep. Il pourrait être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes (par exemple, sur macOS, une représentation utilisant une structure FSRef pour fileSpec serait probablement plus efficace). Sous Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Actuellement, la représentation est simplement une chaîne de caractères qui peut contenir soit le chemin relatif, soit un chemin normalisé complet et absolu dans l'encodage natif (des conditions complexes dictent lequel de ceux-ci sera fourni, donc aucun ne peut être garanti, sauf si le chemin est connu pour être absolu). Si vous avez besoin d'un chemin natif qui doit être absolu, alors vous devriez demander la version native d'un chemin normalisé. Si, pour une raison quelconque, une version non absolue et non normalisée du chemin est nécessaire, elle doit être construite séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache afin que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle du pathPtr passé en argument (sauf si c'est un chemin relatif, auquel cas la représentation native peut être libérée à chaque changement du cwd).

Tcl_FSFileSystemInfo renvoie une liste de deux éléments. Le premier élément est le nom du système de fichiers (par exemple, "native", "vfs", "zip", ou "prowrap", peut-être), et le second est le type particulier du chemin donné dans ce système de fichiers (qui dépend du système de fichiers). Le second élément peut être vide si le système de fichiers ne fournit pas de catégorisation supplémentaire des fichiers.

Une valeur de liste valide est retournée, sauf si la valeur du chemin n'est pas reconnue, auquel cas NULL sera retourné.

Tcl_FSGetFileSystemForPath renvoie un pointeur vers le Tcl_Filesystem qui accepte ce chemin comme valide.

Si aucun système de fichiers n'accepte le chemin, NULL est retourné.

Tcl_FSGetPathType détermine si le chemin donné est relatif au répertoire courant, relatif au volume courant, ou absolu.

Il renvoie l'une des valeurs TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, ou TCL_PATH_VOLUME_RELATIVE

L'API DU SYSTÈME DE FICHIERS VIRTUEL

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions qui implémentent les diverses opérations sur un système de fichiers ; ces opérations sont invoquées si nécessaire par la couche générique, ce qui se produit généralement via les fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un morceau de données optionnel à associer à ce système de fichiers. Lors de l'appel de cette fonction, Tcl attachera le système de fichiers à la liste des systèmes de fichiers connus, et il deviendra pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera retourné.

Tcl_FSUnregister retire la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et retourne TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est retourné.

Tcl_FSData renverra le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il renverra NULL.

Tcl_FSMountsChanged est utilisé pour informer le noyau de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche de système de fichiers générique pour effectuer la gamme complète d'actions liées au système de fichiers.

Les nombreuses fonctions de cette structure sont divisées en trois catégories : fonctions d'infrastructure (dont la plupart doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni) et fonctions d'efficacité (qui n'ont besoin d'être implémentées que si elles peuvent être faites efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces replis ne sont utilisés que pour gérer les commandes initiées en Tcl, pas en C. Cela signifie que si une commande file rename est émise en Tcl, et que le(s) système(s) de fichiers pertinent(s) n'implémentent pas leur Tcl_FSRenameFileProc, le noyau de Tcl se rabattra sur une combinaison d'autres fonctions de système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a un repli supplémentaire). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun de ces replis ne se produit. Ceci est vrai sauf pour les quatre dernières entrées de la table des systèmes de fichiers (lstat, load, getcwd et chdir) pour lesquelles des replis se produisent effectivement au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme de Tcl_Obj les prennent sous forme UTF-8. L'API d'infrastructure des systèmes de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

PROCÉDURE DE CHEMIN DANS SYSTÈME DE FICHIERS

Le champ pathInFilesystemProc contient l'adresse d'une fonction qui est appelée pour déterminer si une valeur de chemin donnée appartient à ce système de fichiers ou non. Tcl n'appellera le reste des fonctions du système de fichiers que lorsque la valeur du chemin aura retourné TCL_OK dans cette fonction. Si le chemin n'appartient pas, -1 doit être retourné (le comportement de Tcl pour d'autres valeurs de retour n'est pas défini). Si TCL_OK est retourné, alors le paramètre optionnel clientDataPtr peut être utilisé pour retourner une représentation interne (spécifique au système de fichiers) du chemin, qui sera mise en cache dans la valeur du chemin, et pourra être récupérée efficacement par d'autres fonctions du système de fichiers à partir de celui-ci. Tcl mettra simultanément en cache le fait que ce chemin appartient à ce système de fichiers. Ces caches sont invalidés lorsque les structures de systèmes de fichiers sont ajoutées ou supprimées de la liste interne des systèmes de fichiers connus de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROCÉDURE DE DUPLICATION DE REPRÉSENTATION INTERNE

Cette fonction génère une copie de la représentation interne d'un chemin et est appelée lorsque Tcl a besoin de dupliquer une valeur de chemin. Si elle est NULL, Tcl ne copiera pas la représentation interne, qui pourrait alors avoir besoin d'être générée plus tard.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

PROCÉDURE DE LIBÉRATION DE REPRÉSENTATION INTERNE

Libère la représentation interne. Doit être implémentée si la représentation interne a besoin d'être libérée (c'est-à-dire si de la mémoire est allouée lors de la génération d'une représentation interne), mais peut être NULL sinon.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

PROCÉDURE DE CONVERSION DE L'INTERNE AU NORMALISÉ

Fonction pour convertir une représentation interne en un chemin normalisé. Ceci est nécessaire si le système de fichiers crée des valeurs de chemin pures sans représentation chaîne/chemin. La valeur retournée est une valeur Tcl dont la représentation chaîne est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

PROCÉDURE DE CRÉATION DE REPRÉSENTATION INTERNE

Fonction pour prendre une valeur de chemin et calculer une représentation interne pour celle-ci, et stocker cette représentation native dans la valeur. Peut être NULL si les chemins n'ont pas de représentation interne, ou si le Tcl_FSPathInFilesystemProc du système de fichiers génère toujours immédiatement une représentation interne pour les chemins qu'il accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

PROCÉDURE DE NORMALISATION DE CHEMIN

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations de chaîne pour une même valeur de chemin. Dans Tcl, chaque chemin "path" doit avoir une représentation unique "normalisée". Selon le système de fichiers, il peut y avoir plus d'une représentation de chaîne non normalisée faisant référence à ce chemin (par exemple, un chemin relatif, un chemin avec une casse différente si le système de fichiers ne fait pas de distinction de casse, un chemin contenant un lien symbolique, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être résolu en la valeur vers laquelle il pointe, mais sa casse ou d'autres aspects doivent être uniques. Tous les autres composants du chemin doivent être résolus à partir des liens symboliques. Cette exception est nécessaire pour correspondre à la sémantique de Tcl pour la commande file, delete, file rename, file copy lors du traitement des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint au début du chemin (c'est-à-dire zéro), à la fin du chemin, ou à n'importe quel séparateur de fichier intermédiaire dans le chemin. Elle ne pointera jamais vers une position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémenteur peut supposer que le chemin depuis le début jusqu'au séparateur inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS DU SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent des adresses de fonctions qui sont appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers destiné à être utilisé avec l'ensemble complet des commandes standard de Tcl doit implémenter toutes ces opérations. Si certaines ne sont pas implémentées, certaines commandes Tcl peuvent échouer lorsqu'elles opèrent sur des chemins appartenant à ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers ne supportant pas les liens symboliques ne devrait pas implémenter la fonction readlink, etc. Le noyau de Tcl attend que les systèmes de fichiers se comportent ainsi).

PROCÉDURE DE TYPE DE CHEMIN DU SYSTÈME DE FICHIERS

Fonction pour déterminer le type de chemin dans ce système de fichiers. Peut être NULL, auquel cas aucune information de type ne sera disponible pour les utilisateurs du système de fichiers. Le type est utilisé uniquement à des fins d'information, et doit être retourné sous forme de représentation chaîne du Tcl_Obj retourné. Une valeur typique pourrait être networked, zip ou ftp. Le Tcl_Obj résultant appartient au système de fichiers, Tcl incrémentera donc le compteur de références de cette valeur s'il le souhaite.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

PROCÉDURE DE SÉPARATEUR DE SYSTÈME DE FICHIERS

Fonction pour retourner le caractère séparateur pour ce système de fichiers. Cette fonction ne doit être implémentée que si le système de fichiers souhaite utiliser un séparateur différent du standard /. Entre autres utilisations, elle est retournée par la commande file separator. La valeur retournée doit avoir un compteur de références égal à zéro.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

PROCÉDURE STAT

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent de manière cruciale (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La fonction Tcl_FSStatProc remplit la structure statPtr avec des informations sur le fichier spécifié. Elle n'a pas besoin de droits d'accès au fichier pour obtenir ces informations, mais elle a besoin de droits de parcours pour tous les répertoires nommés dans le chemin menant au fichier. La structure stat inclut des informations sur le périphérique, l'inœud (toujours 0 sous Windows), le mode de privilège, le nlink (toujours 1 sous Windows), l'UID (toujours 0 sous Windows), le GID (toujours 0 sous Windows), le rdev (identique au périphérique sous Windows), la taille, la dernière date d'accès, la dernière date de modification, et la dernière date de modification des métadonnées.

Si le fichier représenté par pathPtr existe, Tcl_FSStatProc retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné et aucune information stat n'est fournie.

PROCÉDURE D'ACCÈS

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent de manière cruciale (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La fonction Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est dans pathPtr. Si le chemin fait référence à un lien symbolique, les permissions du fichier auquel ce lien symbolique fait référence doivent être testées.

En cas de succès (toutes les permissions demandées ont été accordées), 0 est retourné. En cas d'erreur (au moins un bit dans mode a demandé une permission refusée, ou une autre erreur s'est produite), -1 est retourné.

PROCÉDURE D'OUVERTURE DE CANAL DE FICHIER

Fonction pour traiter un appel Tcl_FSOpenFileChannel. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent de manière cruciale (par exemple, file exists, file readable).

typedef int Tcl_FSOpenFileChannelProc(
        Tcl_Obj *pathPtr,
        int mode);

OPENFILECHANNELPROC

Fonction pour traiter un appel à Tcl_FSOpenFileChannel. Elle doit être implémentée pour tout système de fichiers raisonnable, car toute opération qui nécessite d'ouvrir ou d'accéder au contenu d'un fichier utilisera cette fonction (par exemple, open, encoding et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

La fonction Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et renvoie un handle de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est modélisée d'après la fonction fopen de la bibliothèque d'E/S standard POSIX. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier, où l'argument mode est une combinaison des drapeaux POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannelProc renvoie NULL et enregistre un code d'erreur POSIX qui peut être obtenu avec Tcl_GetErrno. De plus, si interp n'est pas nul, Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le canal nouvellement créé ne doit pas être enregistré dans l'interpréteur fourni par Tcl_FSOpenFileChannelProc ; ce travail incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, la création du nouveau canal l'assigne également comme canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, la fonctionnalité de glob et de copie récursive ne sera pas disponible dans le système de fichiers (et cela peut affecter des commandes comme encoding names qui utilisent la fonctionnalité de glob).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit renvoyer tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au motif donné et satisfont la spécification de types. Cette fonction peut être appelée de deux manières. Si pattern est NULL, pathPtr est une spécification complète d'un fichier ou d'un répertoire qui doit être vérifié pour son existence et son type correct. Sinon, pathPtr est un répertoire et la fonction doit rechercher des fichiers ou des répertoires du bon type. Dans tous les cas, pathPtr peut être supposé comme étant à la fois non nul et non vide. Il n'est pas documenté actuellement si pathPtr se termine par un séparateur de fichier ou non, le code doit donc être flexible aux deux possibilités.

La valeur de retour est un résultat standard Tcl indiquant si une erreur s'est produite pendant le processus de correspondance. Les messages d'erreur sont placés dans interp, sauf si interp est nul auquel cas aucun message d'erreur n'est généré ; dans un résultat TCL_OK, les résultats doivent être ajoutés à la valeur resultPtr fournie (qui peut être supposée être une liste Tcl non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (ce qui signifie généralement qu'il s'agira de spécifications de chemin absolu). Remarque : s'il n'y a pas de correspondances, cela conduit simplement à un résultat vide ; seules les erreurs réelles de fichiers ou de système de fichiers qui peuvent survenir pendant le processus de correspondance sont signalées.

Le Tcl_GlobTypeData fourni dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Type mac accepté */
    Tcl_Obj *macType;
    /* Créateur mac accepté */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de gérer correctement, tous deux lorsque types n'est pas nul. Les deux cas sont lorsque types->types est & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT est vrai (et en particulier lorsque les autres drapeaux sont faux). Dans le premier cas, la fonction doit énumérer les répertoires contenus. Tcl utilise cette fonction pour implémenter le globbing récursif, il est donc crucial que les systèmes de fichiers implémentent correctement la correspondance de répertoires. Dans le second cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit énumérer les points de montage trouvés dans le répertoire donné par pathPtr (et dans ce cas, pathPtr n'a pas besoin d'être dans le même système de fichiers - contrairement à d'autres cas où cette fonction est appelée). La prise en charge de cela est critique si Tcl doit permettre des transitions douces entre les systèmes de fichiers.

UTIMEPROC

Fonction pour traiter un appel à Tcl_FSUtime. Elle est requise pour permettre la définition (pas la lecture) des temps de dernière modification et de dernier accès du fichier, et l'implémentation de la copie de fichiers de type open-r/open-w/fcopy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les heures d'accès et de modification du fichier spécifié par pathPtr doivent être modifiées aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec la fonction système utime.

LINKPROC

Fonction pour traiter un appel à Tcl_FSLink. Elle ne doit être implémentée que si le système de fichiers prend en charge les liens, et peut être nulle dans le cas contraire.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est sollicitée pour lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien ne peut pas être lu. Le résultat appartient à l'appelant (et doit donc voir son compteur de références incrémenté avant d'être retourné). Tout appelant doit appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'en a plus besoin. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Dans ce cas, le résultat doit être toPtr si le lien a réussi et NULL dans le cas contraire. Dans ce cas, le résultat n'appartient pas à l'appelant (c'est-à-dire qu'il n'y a pas de manipulation de compteur de références des deux côtés). Voir la documentation de Tcl_FSLink pour l'interprétation correcte du paramètre linkAction.

LISTVOLUMESPROC

Fonction pour énumérer tous les volumes du système de fichiers ajoutés par ce système de fichiers. Elle ne doit être implémentée que si le système de fichiers ajoute des volumes en tête du système de fichiers, de sorte qu'ils puissent être renvoyés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste des volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) s'il n'y a pas de volumes fournis. La valeur de retour est considérée comme appartenant au système de fichiers (pas au noyau Tcl), mais doit se voir attribuer un compteur de références pour Tcl. Tcl utilisera le contenu de la liste puis décrémentera le compteur de références. Cela permet aux systèmes de fichiers de choisir s'ils souhaitent réellement conserver une liste globale de volumes ou non (s'ils ne le font pas, ils génèrent la liste à la volée et la transmettent à Tcl avec un compteur de références de 1 puis oublient la liste, s'ils le font, alors ils incrémentent simplement le compteur de références de leur liste globale et la transmettent à Tcl qui copiera le contenu puis décrémentera le compteur de références de là où il était).

Par conséquent, Tcl considère les valeurs de retour de cette fonction comme étant en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour énumérer toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne prendra pas en charge la commande file attributes. Cela permet d'associer des informations supplémentaires arbitraires aux fichiers du système de fichiers. Si elle n'est pas implémentée, il n'est pas nécessaire d'implémenter les méthodes get et set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La fonction peut renvoyer un tableau de chaînes ou, à la place, renvoyer NULL et placer une liste Tcl dans le objPtrRef fourni. Tcl prendra cette liste et incrémentera son compteur de références avant de l'utiliser. Après avoir terminé son utilisation, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être libérée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si elle ne doit pas être libérée, le système de fichiers doit s'assurer qu'il renvoie une valeur avec un compteur de références d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsGet, utilisée par la commande file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Renvoie un code de retour standard Tcl. La valeur de la chaîne d'attribut récupérée, qui correspond à l'élément d'indice index dans la liste renvoyée par Tcl_FSFileAttrStringsProc, est placée dans objPtrRef (si TCL_OK a été renvoyé), et aura probablement un compteur de références de zéro. Quoi qu'il en soit, nous devons stocker cette valeur quelque part (par exemple, dans le résultat Tcl) ou incrémenter/désencombrer son compteur de références pour assurer sa libération correcte.

FILEATTRSSETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsSet, utilisée par la commande file attributes. Si le système de fichiers est en lecture seule, il n'est pas nécessaire de l'implémenter.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

La valeur d'attribut de l'élément d'indice index dans la liste renvoyée par Tcl_FSFileAttrStringsProc doit être définie sur l'objet objPtr fourni.

OPÉRATIONS REQUISES

Les systèmes de fichiers doivent implémenter au moins les opérations suivantes pour être considérés comme fonctionnels :

STATPROC

Fonction pour traiter un appel Tcl_FSStat. Devrait être implémenté par tous les systèmes de fichiers non en lecture seule.

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus. Si l'opération réussit, `statPtr` est rempli avec les informations de statut du fichier spécifié par `pathPtr`.

ACCESSPROC

Fonction pour traiter un appel Tcl_FSAccess. Devrait être implémenté par tous les systèmes de fichiers non en lecture seule.

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus. Si l'opération réussit, elle vérifie si le fichier spécifié par `pathPtr` existe et si les permissions spécifiées par `mode` sont accordées.

OPENPROC

Fonction pour traiter un appel Tcl_FSOpen. Devrait être implémenté par tous les systèmes de fichiers non en lecture seule.

typedef int Tcl_FSOpenProc(
        Tcl_Obj *pathPtr,
        int mode,
        Tcl_Channel *chanPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus. Si l'opération réussit, le fichier spécifié par `pathPtr` est ouvert avec le mode spécifié, et un handle de canal est placé dans `chanPtr`.

CONVERTPATHINCONTEXTPROC

Fonction pour traiter un appel Tcl_FSConvertPathInContext. Devrait être implémenté par tous les systèmes de fichiers qui supportent des chemins relatifs ou qui nécessitent une conversion spécifique.

typedef Tcl_Obj *Tcl_FSConvertPathInContextProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj *contextPathPtr);

La fonction convertit un chemin donné (`pathPtr`) en un chemin absolu en utilisant un chemin de contexte (`contextPathPtr`). Si la conversion réussit, un nouveau chemin est retourné. Sinon, NULL est retourné et un message d'erreur est laissé dans le résultat de l'interpréteur.

PATHFROMSTRINGPROC

Fonction pour traiter un appel Tcl_FSPathFromString. Devrait être implémenté par tous les systèmes de fichiers pour permettre la conversion de chaînes de caractères en chemins.

typedef Tcl_Obj *Tcl_FSPathFromStringProc(
        const char *string);

La fonction convertit une chaîne de caractères représentant un chemin en un objet Tcl représentant ce chemin. Si la conversion réussit, un pointeur vers l'objet chemin est retourné. Sinon, NULL est retourné et un message d'erreur est laissé dans le résultat de l'interpréteur.

STRINGFROMPATHPROC

Fonction pour traiter un appel Tcl_FSStringFromPath. Devrait être implémenté par tous les systèmes de fichiers pour permettre la conversion de chemins en chaînes de caractères.

typedef const char *Tcl_FSStringFromPathProc(
        Tcl_Obj *pathPtr);

La fonction convertit un objet Tcl représentant un chemin en une chaîne de caractères. La chaîne retournée est valide jusqu'à la prochaine gestion d'événements Tcl. Si `pathPtr` n'est pas un chemin valide, NULL est retourné.

CREATEDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSCreateDirectory. Devrait être implémenté sauf si le système de fichiers est en lecture seule.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus. En cas de succès, un nouveau répertoire devrait avoir été ajouté au système de fichiers à l'emplacement spécifié par pathPtr.

REMOVEDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSRemoveDirectory. Devrait être implémenté sauf si le système de fichiers est en lecture seule.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus. En cas de succès, le répertoire spécifié par pathPtr devrait avoir été supprimé du système de fichiers. Si l'indicateur recursive est donné, alors un répertoire non vide doit être supprimé sans erreur. Si cet indicateur n'est pas donné et que le répertoire est non vide, une erreur POSIX « EEXIST » doit être signalée. Si une erreur se produit, le nom du fichier ou du répertoire qui a causé l'erreur doit être placé dans errorPtr.

DELETEFILEPROC

Fonction pour traiter un appel Tcl_FSDeleteFile. Devrait être implémenté sauf si le système de fichiers est en lecture seule.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus. En cas de succès, le fichier spécifié par pathPtr devrait avoir été supprimé du système de fichiers. Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non Tcl_FSRemoveDirectoryProc lorsque cela est nécessaire pour les supprimer (même s'il s'agit de liens symboliques vers des répertoires).

FILESYSTEM EFFICIENCY

Ces fonctions n'ont pas besoin d'être implémentées pour un système de fichiers particulier car le noyau dispose d'une implémentation de secours disponible. Voir la description individuelle de chaque fonction pour les conséquences de laisser le champ à NULL.

LSTATPROC

Fonction pour traiter un appel Tcl_FSLstat. Si elle n'est pas implémentée, Tcl tentera d'utiliser le statProc défini ci-dessus à la place. Par conséquent, elle n'a besoin d'être implémentée que si un système de fichiers peut différencier les appels stat et lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le comportement de cette fonction est très similaire à celui de Tcl_FSStatProc défini ci-dessus, sauf que si elle est appliquée à un lien symbolique, elle renvoie des informations sur le lien, et non sur le fichier cible.

COPYFILEPROC

Fonction pour traiter un appel Tcl_FSCopyFile. Si elle n'est pas implémentée, Tcl utilisera open-r, open-w et fcopy comme mécanisme de copie. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de copie. Notez que destPathPtr est le nom du fichier qui deviendra la copie de srcPathPtr. Ce n'est jamais le nom d'un répertoire dans lequel srcPathPtr pourrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande Tcl de niveau file copy). Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non copyDirectoryProc lorsqu'il est nécessaire de les copier (même s'il s'agit de liens symboliques vers des répertoires). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file copy, appeler Tcl_SetErrno(EXDEV) et retourner un résultat différent de TCL_OK indiquera à Tcl d'utiliser ses mécanismes de secours standards.

RENAMEFILEPROC

Fonction pour traiter un appel Tcl_FSRenameFile. Si elle n'est pas implémentée, Tcl utilisera un mécanisme de copie et de suppression. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de renommage. Si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file rename, appeler Tcl_SetErrno(EXDEV) et retourner un résultat différent de TCL_OK indiquera à Tcl d'utiliser ses mécanismes de secours standards.

COPYDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSCopyDirectory. Si elle n'est pas implémentée, Tcl utilisera un mécanisme récursif de file mkdir et file copy. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de copie. Si une erreur se produit, le nom du fichier ou du répertoire qui a causé l'erreur doit être placé dans errorPtr. Notez que destPathPtr est le nom du répertoire qui deviendra l'image miroir de srcPathPtr. Ce n'est pas le nom d'un répertoire dans lequel srcPathPtr devrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande Tcl de niveau file copy). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de copie de répertoire, appeler Tcl_SetErrno(EXDEV) et retourner un résultat différent de TCL_OK indiquera à Tcl d'utiliser ses mécanismes de secours standards.

LOADFILEPROC

Fonction pour traiter un appel Tcl_FSLoadFile. Si elle n'est pas implémentée, Tcl utilisera une copie vers un fichier temporaire natif suivie d'un Tcl_FSLoadFile sur cette copie temporaire. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut charger du code directement, ou si elle peut être implémentée simplement pour renvoyer TCL_ERROR afin de désactiver complètement la fonctionnalité de chargement dans ce système de fichiers.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Renvoie un code de complétion Tcl standard. En cas d'erreur, un message d'erreur est laissé dans le résultat de l'interp. La fonction charge dynamiquement un fichier de code binaire en mémoire. En cas de chargement réussi, handlePtr doit être rempli avec un jeton pour le fichier chargé dynamiquement, et unloadProcPtr doit être rempli avec l'adresse d'une procédure. La procédure de déchargement sera appelée avec le Tcl_LoadHandle donné comme seul paramètre lorsque Tcl devra décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle retourné est actuellement un jeton qui peut être utilisé dans le TclpFindSymbol privé pour accéder aux fonctions du nouveau code. Chaque système de fichiers est libre de définir le Tcl_LoadHandle comme il le souhaite. Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de chargement de fichier, appeler Tcl_SetErrno(EXDEV) et retourner un résultat différent de TCL_OK indiquera à Tcl d'utiliser ses mécanismes de secours standards.

UNLOADFILEPROC

Fonction pour décharger un fichier précédemment chargé avec succès. Si le chargement a été implémenté, alors celui-ci doit également être implémenté, s'il y a une action de nettoyage requise.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Fonction pour traiter un appel Tcl_FSGetCwd. La plupart des systèmes de fichiers n'ont pas besoin de l'implémenter. Elle ne sera généralement appelée qu'une seule fois, si getcwd est appelé avant chdir. Peut être NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si le système de fichiers prend en charge une notion native de répertoire de travail courant (qui pourrait potentiellement changer indépendamment de Tcl), cette fonction doit retourner ce répertoire de travail courant comme résultat, ou NULL si le répertoire courant n'a pas pu être déterminé (par exemple, si l'utilisateur n'a pas les permissions appropriées sur le répertoire courant). Si NULL est retourné, un message d'erreur est laissé dans le résultat de interp.

CHDIRPROC

Fonction pour traiter un appel Tcl_FSChdir. Si les systèmes de fichiers ne l'implémentent pas, elle sera émulée par une série de vérifications d'accès aux répertoires. Sinon, les systèmes de fichiers virtuels qui l'implémentent doivent seulement répondre avec un résultat positif si pathPtr est un répertoire valide et accessible dans leur système de fichiers. Ils n'ont pas besoin de mémoriser le résultat, car celui-ci sera automatiquement mémorisé pour être utilisé par Tcl_FSGetCwd. Les systèmes de fichiers réels doivent effectuer l'action correcte (c'est-à-dire appeler l'API système chdir correcte).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

Le Tcl_FSChdirProc change le répertoire de travail courant de l'application pour la valeur spécifiée dans pathPtr. La fonction renvoie -1 en cas d'erreur ou 0 en cas de succès.
