Tcl_AsyncDelete(3) Procédures de bibliothèque Tcl Tcl_AsyncDelete(3)

NOM

Tcl_AsyncDelete, Tcl_AyncMark, Tcl_AyncInvoke, Tcl_AyncCreate, Tcl_AyncReady - gestion des événements asynchrones

SYNTAXE

#include <tcl.h>

Tcl_AyncHandler
Tcl_AyncCreate(proc, clientData)

void
Tcl_AyncMark(async)

int
Tcl_AyncInvoke(interp, code)

void
Tcl_AyncDelete(async)

int
Tcl_AyncReady()

ARGUMENTS

Tcl_AyncProc *proc (entrée)
Procédure à invoquer pour gérer un événement asynchrone.
ClientData clientData (entrée)
Valeur d'un octet à passer à proc.
Tcl_AyncHandler async (entrée)
Jeton pour le gestionnaire d'événement asynchrone.
Tcl_Interp *interp (entrée)
Interpréteur Tcl dans lequel la commande était en cours d'évaluation lorsque le gestionnaire a été invoqué, ou NULL si le gestionnaire a été invoqué sans interpréteur actif.
int code (entrée)
Code de sortie de la commande qui s'est terminée dans interp, ou 0 si interp est NULL.

DESCRIPTION

Ces fonctions fournissent un mécanisme sûr pour gérer les événements asynchrones tels que les signaux. Si un événement tel qu'un signal se produit pendant l'évaluation d'un script Tcl, il n'est pas sûr de prendre des mesures substantielles pour le traiter. Par exemple, il n'est pas sûr d'évaluer un script Tcl car l'interpréteur peut être en train d'évaluer un script ; il peut ne pas être sûr d'allouer de la mémoire, car l'allocation de mémoire pourrait être en cours lorsque l'événement s'est produit. La seule façon sûre est de marquer un indicateur signalant que l'événement s'est produit, puis de le gérer plus tard lorsque le monde est dans un état propre, par exemple après la fin de la commande actuelle.

Tcl_AyncCreate, Tcl_AyncDelete et Tcl_AyncReady sont thread-safe. Ils accèdent et/ou définissent une structure de données de thread s'ils sont compilés avec --enable-threads. Le jeton créé par Tcl_AyncCreate contient les informations de thread nécessaires sur le thread qui a été appelé afin que Tcl_AyncMark(token) ne retourne que le thread d'origine dans le gestionnaire asynchrone.

Tcl_AyncCreate crée un gestionnaire asynchrone et renvoie un jeton pour celui-ci. Le gestionnaire asynchrone doit être créé avant toute occurrence d'un événement asynchrone qui tente de le gérer (il n'est pas sûr de créer un gestionnaire au moment d'un événement). Lorsqu'un événement asynchrone se produit, le code qui détecte l'événement (tel qu'un gestionnaire de signaux) doit appeler Tcl_AyncMark avec le jeton du gestionnaire. Tcl_AyncMark marquera le gestionnaire comme prêt à être exécuté, mais ne l'invoquera pas immédiatement. Tcl appellera le proc associé au gestionnaire plus tard, lorsque le monde sera dans un état sûr, et proc pourra alors exécuter les actions associées à l'événement asynchrone. Le proc doit avoir des arguments et des résultats correspondant au type Tcl_AyncProc :

typedef int Tcl_AyncProc(
        ClientData clientData,
        Tcl_Interp *interp,
        int code);

Le clientData sera le même que le clientData passé à Tcl_AyncCreate lors de la création du gestionnaire. Si proc est invoqué juste après la fin d'une commande dans un interpréteur, alors interp identifiera l'interpréteur dans lequel la commande a été évaluée et code sera le code de sortie de cette commande. Le résultat de la commande sera présent dans le résultat de l'interpréteur. Lorsque proc retourne, ce qu'il laisse dans le résultat de l'interpréteur sera renvoyé comme résultat de la commande et la valeur entière renvoyée par proc sera utilisée comme nouveau code de sortie de la commande.

Il est également possible que proc soit invoqué lorsqu'aucun interpréteur n'est actif. Cela peut se produire, par exemple, si un événement asynchrone se produit pendant que l'application attend une entrée interactive ou un événement X. Dans ce cas, interp sera NULL et code sera 0, et la valeur renvoyée par proc sera ignorée.

La fonction Tcl_AyncInvoke est appelée pour invoquer tous les gestionnaires prêts. La fonction Tcl_AyncReady renvoie une valeur non nulle lorsqu'il y a des gestionnaires asynchrones prêts ; elle peut être utilisée pour éviter les appels à Tcl_AyncInvoke lorsqu'aucun gestionnaire n'est prêt. Tcl appelle Tcl_AyncReady après chaque commande évaluée et appelle Tcl_AyncInvoke si nécessaire. Les applications peuvent également appeler Tcl_AyncInvoke à des moments intéressants pour leur application. Par exemple, le gestionnaire d'événements de Tcl appelle Tcl_AyncReady après chaque événement et appelle Tcl_AyncInvoke si nécessaire. Les arguments interp et code de Tcl_AyncInvoke ont la même signification que pour proc : ils identifient l'interpréteur actif, s'il existe, et le code de sortie de la commande qui s'est terminée.

Tcl_AyncDelete supprime un gestionnaire asynchrone afin que son proc ne soit jamais invoqué à nouveau. Un gestionnaire peut être supprimé même s'il est prêt, et il ne sera toujours pas invoqué.

Si plusieurs gestionnaires deviennent prêts en même temps, les gestionnaires sont invoqués dans l'ordre dans lequel ils ont été créés (le gestionnaire le plus ancien en premier). Les valeurs de code et le résultat de l'interpréteur des gestionnaires ultérieurs reflètent les valeurs renvoyées par les gestionnaires précédents, de sorte que le gestionnaire le plus récent a le dernier mot sur le résultat de l'interpréteur et le code de sortie. Si de nouveaux gestionnaires deviennent prêts pendant que les gestionnaires sont en cours d'exécution, Tcl_AyncInvoke les invoquera tous ; à chaque étape, il invoque le gestionnaire de priorité la plus élevée (le plus ancien) qui est prêt, répétant ce processus jusqu'à ce qu'il n'y ait plus de gestionnaires prêts.

AVERTISSEMENT

Il est presque toujours une mauvaise idée pour un gestionnaire d'événements asynchrones de modifier le résultat de l'interpréteur ou de renvoyer un code différent de l'argument code du gestionnaire. Ce type de comportement peut déclencher un décalage dans l'exécution des scripts de manière subtile et entraîner des bugs difficiles à trouver. Si un gestionnaire d'événements asynchrones doit évaluer des scripts Tcl, il doit d'abord sauvegarder l'état de l'interpréteur en appelant Tcl_SaveInterpState, en passant l'argument code. Lorsque le gestionnaire asynchrone est terminé, il doit restaurer l'état de l'interpréteur en appelant Tcl_RestoreInterpState, puis renvoyer l'argument code.
