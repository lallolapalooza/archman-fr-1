DESCRIPTION

Il y a plusieurs raisons d'appeler les fonctions de l'API Tcl_FS (par exemple, Tcl_FSAccess et Tcl_FSStat) plutôt que d'appeler directement des fonctions de niveau système comme access et stat. Premièrement, elles fonctionneront sur plusieurs plates-formes, donc une extension qui les appelle devrait fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige certains bogues dans les appels de niveau système. Troisièmement, ces appels de fonction traitent les conversions de chemins « Utf vers natif de la plate-forme » qui peuvent être nécessaires (et peuvent mettre en cache les résultats de telles conversions pour une plus grande efficacité lors des appels ultérieurs). Quatrièmement, et peut-être le plus important, toutes ces fonctions sont « conscientes du système de fichiers virtuel » (VFS pour court). Tout système de fichiers virtuel (VFS pour court) qui a été enregistré (via Tcl_FSRegister) peut réacheminer l'accès aux fichiers vers des supports ou des méthodes d'accès alternatifs. Cela signifie que toutes ces fonctions (et donc les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent opérer sur des « fichiers » qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS pour court) via cette API est automatiquement « consciente du système de fichiers virtuel ». Bien sûr, si une extension accède directement au système de fichiers natif (via des API spécifiques à la plate-forme, par exemple), Tcl ne peut pas intercepter de tels appels.

Si des VFS appropriés ont été enregistrés, les « fichiers » peuvent, pour donner deux exemples, être distants (par exemple, situés sur un serveur ftp distant) ou archivés (par exemple, se trouvant à l'intérieur d'une archive .zip). De tels systèmes de fichiers enregistrés fournissent une table de recherche de fonctions pour implémenter tout ou partie des fonctionnalités énumérées ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat abstraient la déclaration du tampon « struct stat », permettant d'utiliser le même code sur les systèmes avec et sans prise en charge des fichiers de plus de 2 Go.

L'API Tcl_FS est transformée en Tcl_Obj et peut mettre en cache des représentations internes et d'autres chaînes liées aux chemins (par exemple, le répertoire de travail actuel). Un effet secondaire est qu'il ne faut pas passer de valeurs avec un compteur de références de zéro à l'une de ces fonctions. Si de tels appels étaient traités, ils pourraient entraîner des fuites de mémoire (dans certaines circonstances, le code du système de fichiers peut souhaiter conserver une référence à la valeur passée, et il ne faut donc pas supposer qu'après le retour de l'un de ces appels, la valeur a toujours un compteur de références de zéro - il peut avoir été incrémenté) ou un défaut de segmentation direct (ou une autre erreur d'accès mémoire) en raison de la libération de la valeur pendant la manipulation complexe de la valeur requise pour s'assurer que le chemin est entièrement normalisé et absolu pour la détermination du système de fichiers. La leçon pratique à en tirer est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect, et peut causer des erreurs de mémoire. La référence du chemin path doit être incrémentée avant d'être passée, ou décrémentée. Pour cette raison, les valeurs avec un compteur de références de zéro ne sont pas considérées comme des chemins de système de fichiers valides et l'appel de toute fonction de l'API Tcl_FS avec une telle valeur n'entraînera aucune action.

FONCTIONS DE L'API FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno au code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno au code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction « créer un répertoire » du système de fichiers propriétaire.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction « supprimer un fichier » du système de fichiers propriétaire.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction « supprimer un répertoire » du système de fichiers propriétaire.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « renommer un fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno au code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction « lister les volumes » non NULL et leur demande de renvoyer leur liste de volumes racines. Elle accumule les valeurs de retour dans une liste qui est renvoyée à l'appelant (avec un compteur de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant l'encodage identifié par encodingName et évalue son contenu comme un script Tcl. Elle renvoie les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, l'encodage système est utilisé pour lire le contenu du fichier. Si le fichier n'a pas pu être lu, une erreur Tcl est renvoyée pour décrire pourquoi le fichier n'a pas pu être lu. Le caractère eof pour les fichiers est « \x1A » (^Z) pour toutes les plates-formes. Si vous avez besoin d'un « ^Z » dans le code pour une comparaison de chaînes, vous pouvez utiliser « \x1A », qui sera safely substitué par l'interpréteur Tcl en « ^Z ». Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours l'encodage système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier de code binaire en mémoire et renvoie les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas, en raison des limitations du système d'exploitation dans le chargement dynamique de code binaire), Tcl tentera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile inverse l'opération, demandant que la bibliothèque indiquée par loadHandle soit retirée du processus. Notez que, contrairement à la commande unload, cela ne donne à la bibliothèque aucune possibilité de nettoyage.

Les deux fonctions ci-dessus renvoient un code de complétion Tcl standard. Si une erreur se produit, un message d'erreur est laissé dans le résultat de l'interp.

Le jeton fourni via la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher dans un répertoire tous les fichiers qui correspondent à un motif donné. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le globbing. Les messages d'erreur sont placés dans l'interpréteur (sauf si l'interpréteur est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Notez que le code glob implémente les motifs récursifs en interne, donc cette fonction ne recevra jamais que des motifs simples, qui peuvent être mis en correspondance en utilisant la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment en demandant uniquement le retour des répertoires. Un cas spécial d'appel avec un motif NULL indique que le chemin doit uniquement être vérifié pour le type correct.

Tcl_FSLink remplace la version bibliothèque de readlink, et l'étend pour prendre en charge la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr sera appelée.

Si toPtr est NULL, une action « lire le lien » est effectuée. Le résultat est un Tcl_Obj spécifiant le contenu du lien symbolique donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant, qui devrait appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl devrait créer un lien d'un des types passés dans l'indicateur linkAction. Cet indicateur est une combinaison OU de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'un choix existe (c'est-à-dire que plus d'un indicateur est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur de retour doit être toPtr (qui appartient donc déjà à l'appelant). En cas d'échec, NULL est renvoyé.

Tcl_FSLstat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le dernier accès

temps de dernière modification, et temps de dernière modification des métadonnées. Voir **PORTABLE STAT RESULT API** pour une description de la manière d'écrire du code portable pour allouer et accéder à la structure *Tcl_StatBuf*. Si *path* existe, **Tcl_FSLstat** renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé, et aucune information de stat n'est fournie. **Tcl_FSUtime** remplace la version de bibliothèque de utime. Ceci renvoie 0 en cas de succès et -1 en cas d'erreur (conformément à la documentation de **utime**). En cas de succès, la fonction mettra à jour les valeurs « atime » et « mtime » du fichier donné. **Tcl_FSFileAttrsGet** implémente l'accès en lecture pour la sous-commande hookable **file attributes**. La fonction appropriée pour le système de fichiers auquel appartient *pathPtr* sera appelée. Si le résultat est **TCL_OK**, une valeur a été placée dans *objPtrRef*, qui ne sera valide que temporairement (sauf si **Tcl_IncrRefCount** est appelée). **Tcl_FSFileAttrsSet** implémente l'accès en écriture pour la sous-commande hookable **file attributes**. La fonction appropriée pour le système de fichiers auquel appartient *pathPtr* sera appelée. **Tcl_FSFileAttrStrings** implémente une partie de la sous-commande hookable **file attributes**. La fonction appropriée pour le système de fichiers auquel appartient *pathPtr* sera appelée. La procédure appelée peut soit renvoyer un tableau de chaînes, soit renvoyer NULL et placer une liste Tcl dans *objPtrRef*. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer qu'il conserve un compteur de références à la valeur. **Tcl_FSAccess** vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est *pathname*. Si *pathname* est un lien symbolique sous Unix, les permissions du fichier auquel ce lien symbolique fait référence sont testées. En cas de succès (toutes les permissions demandées accordées), zéro est renvoyé. En cas d'erreur (au moins un bit dans le mode demandait une permission refusée, ou une autre erreur s'est produite), -1 est renvoyé. **Tcl_FSStat** remplit la structure *Tcl_StatBuf* *statPtr* avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure *Tcl_StatBuf* inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le temps de dernier accès, le temps de dernière modification et le temps de dernière modification des métadonnées. Voir **PORTABLE STAT RESULT API** pour une description de la manière d'écrire du code portable pour allouer et accéder à la structure *Tcl_StatBuf*. Si *path* existe, **Tcl_FSStat** renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé, et aucune information de stat n'est fournie. **Tcl_FSOpenFileChannel** ouvre un fichier spécifié par *pathPtr* et renvoie un handle de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est calquée sur la procédure **fopen** de la bibliothèque d'entrée/sortie standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl **open** lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, **Tcl_FSOpenFileChannel** renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec **Tcl_GetErrno**. De plus, si *interp* n'est pas NULL, **Tcl_FSOpenFileChannel** laisse un message d'erreur dans le résultat de *interp* après toute erreur. Le canal nouvellement créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez **Tcl_RegisterChannel**. Si l'un des canaux standard, **stdin**, **stdout** ou **stderr**, a été précédemment fermé, la création du nouveau canal l'assigne également comme remplacement du canal standard. **Tcl_FSGetCwd** remplace la version de bibliothèque de **getcwd**. Il renvoie le répertoire de travail courant de la bibliothèque Tcl. Il peut être différent du répertoire de travail courant de la plateforme native, ce qui se produit lorsque le répertoire de travail courant ne se trouve pas dans le système de fichiers natif. Le résultat est un pointeur vers un Tcl_Obj spécifiant le répertoire courant, ou NULL si le répertoire courant n'a pas pu être déterminé. Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de *interp*. Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compteur de références doit être décrémenté. Ceci est nécessaire pour des raisons de sécurité des threads, pour permettre à plusieurs threads d'accéder à cette fonction et aux fonctions associées, tout en garantissant que les résultats sont toujours valides. **Tcl_FSChdir** remplace la version de bibliothèque de **chdir**. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl utilisera une combinaison de **stat** et **access** pour vérifier si le répertoire existe et possède les autorisations appropriées. Pour les résultats, voir la documentation de **chdir**. En cas de succès, nous conservons un enregistrement du chemin réussi dans *cwdPathPtr* pour les appels ultérieurs à **Tcl_FSGetCwd**. **Tcl_FSPathSeparator** renvoie le caractère séparateur à utiliser pour l'élément le plus spécifique du chemin spécifié par *pathPtr* (c'est-à-dire la dernière partie du chemin). Le séparateur est renvoyé sous forme de Tcl_Obj contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est renvoyé. **Tcl_FSJoinPath** prend le Tcl_Obj donné, qui doit être une liste valide (autorisée à avoir un compteur de références de zéro), et renvoie la valeur du chemin donnée en considérant les *elements* premiers éléments comme des segments de chemin valides (chaque segment de chemin peut être un chemin complet, un chemin partiel ou simplement un seul répertoire ou nom de fichier possible). Si un segment de chemin est en fait un chemin absolu, tous les segments de chemin précédents sont ignorés. Si *elements* est inférieur à 0, nous utilisons la liste entière. Il est possible que la valeur renvoyée soit en fait un élément de la liste donnée, donc l'appelant doit faire attention à incrémenter le compteur de références du résultat avant de libérer la liste. La valeur renvoyée, généralement avec un compteur de références de zéro (mais elle pourrait être partagée dans certaines conditions), contient le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. En particulier, la valeur renvoyée pourrait être un élément de la liste donnée, donc la libération de la liste pourrait libérer la valeur prématurément si aucun compteur de références n'a été pris. Si le nombre d'éléments est zéro, la valeur renvoyée sera un Tcl_Obj de chaîne vide. **Tcl_FSSplitPath** prend le Tcl_Obj donné, qui devrait être un chemin valide, et renvoie une valeur de liste Tcl contenant chaque segment de ce chemin comme élément. Elle renvoie une valeur de liste avec un compteur de références de zéro. Si *lenPtr* passé n'est pas NULL, la variable à laquelle il pointe sera mise à jour pour contenir le nombre d'éléments dans la liste renvoyée. **Tcl_FSEqualPaths** teste si les deux chemins donnés représentent le même objet du système de fichiers. Il renvoie 1 si les chemins sont égaux, et 0 s'ils sont différents. Si l'un des chemins est NULL, 0 est toujours renvoyé. **Tcl_FSGetNormalizedPath** tente d'extraire du Tcl_Obj donné une représentation de chemin normalisée unique, dont la valeur de chaîne peut être utilisée comme identifiant unique du fichier. Il renvoie la valeur du chemin normalisé, détenue par Tcl, ou NULL si le chemin était invalide ou n'a pas pu être converti avec succès. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère en interne sur ces représentations), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques puisse ne pas être la version la plus conviviale d'un chemin. La valeur renvoyée est détenue par Tcl et a une durée de vie équivalente à celle de *pathPtr* passé (sauf si c'est un chemin relatif, auquel cas la valeur du chemin normalisé peut être libérée à tout moment où le cwd change) - l'appelant peut bien sûr incrémenter le compteur de références s'il souhaite conserver une copie plus longtemps. **Tcl_FSJoinToPath** prend la valeur donnée, qui devrait généralement être un chemin valide ou NULL, et y joint le tableau de segments de chemin donnés. Renvoie une valeur, généralement avec un compteur de références de zéro (mais elle pourrait être partagée dans certaines conditions), contenant le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. Si l'une des valeurs passées à cette fonction (*pathPtr* ou éléments de *path*) a un compteur de références de zéro, elles seront libérées lorsque cette fonction renverra. **Tcl_FSConvertToPathType** essaie de convertir le Tcl_Obj donné en un type de chemin Tcl valide, en tenant compte du fait que le cwd peut avoir changé même si cette valeur est déjà censée être du bon type. Le nom de fichier peut commencer par « ~ » (pour indiquer le répertoire personnel de l'utilisateur courant) ou « ~<utilisateur> » (pour indiquer le répertoire personnel de n'importe quel utilisateur). Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), alors **TCL_OK** est renvoyé. Sinon, **TCL_ERROR** est renvoyé, et un message d'erreur peut être laissé dans l'interpréteur. **Tcl_FSGetInternalRep** extrait la représentation interne d'une valeur de chemin donnée, dans le système de fichiers donné. Si la valeur du chemin appartient à un système de fichiers différent, nous renvoyons NULL. Si la représentation interne est actuellement NULL, nous tentons de la générer, en appelant **Tcl_FSCreateInternalRepProc** du système de fichiers. Renvoie NULL ou une représentation de chemin interne valide. Cette représentation interne est mise en cache, de sorte que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. **Tcl_FSGetTranslatedPath** tente d'extraire le chemin traduit du Tcl_Obj donné. Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), elle est renvoyée. Sinon, NULL sera renvoyé, et un message d'erreur peut être laissé dans l'interpréteur. Un chemin « traduit » est un chemin qui ne contient aucune séquence « ~ » ou « ~utilisateur » (celles-ci ont été développées en leur représentation actuelle dans le système de fichiers). La valeur renvoyée est détenue par l'appelant, qui doit la stocker ou appeler **Tcl_DecrRefCount** pour s'assurer que la mémoire est libérée. Cette fonction a peu d'utilité pratique, et **Tcl_FSGetNormalizedPath** ou **Tcl_FSGetNativePath** sont généralement de meilleures fonctions à utiliser pour la plupart des cas. **Tcl_FSGetTranslatedStringPath** fait la même chose que **Tcl_FSGetTranslatedPath**, mais renvoie une chaîne de caractères ou NULL. La chaîne renvoyée est allouée dynamiquementet détenue par l'appelant, qui doit la stocker ou appeler ckfree pour s'assurer qu'elle est libérée. Encore une fois, Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement des fonctions mieux adaptées à la plupart des usages.

Tcl_FSNewNativePath effectue quelque chose comme l'inverse des conversions habituelles obj->path->nativerep. Si un code récupère un chemin sous forme native (par exemple, à partir de readlink ou d'une boîte de dialogue native), et que ce chemin doit être utilisé au niveau Tcl, alors appeler cette fonction est un moyen efficace de créer le type de valeur de chemin approprié.

La valeur résultante est une valeur de « chemin » pure, qui ne recevra une représentation sous forme de chaîne UTF-8 que si cela est requis par un code Tcl.

Tcl_FSGetNativePath est destiné aux systèmes de fichiers natifs Win/Unix, afin qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un wrapper pratique autour de Tcl_FSGetInternalRep. Il pourrait être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes (par exemple, sur macOS, une représentation utilisant une structure FSRef de fileSpec serait probablement plus efficace). Sous Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Actuellement, la représentation est simplement une chaîne de caractères qui peut contenir soit le chemin relatif, soit un chemin normalisé complet et absolu dans le codage natif (des conditions complexes dictent lequel de ceux-ci sera fourni, de sorte qu'aucun ne peut être fiable, à moins que le chemin ne soit connu pour être absolu). Si vous avez besoin d'un chemin natif qui doit être absolu, vous devez demander la version native d'un chemin normalisé. Si, pour une raison quelconque, une version non absolue et non normalisée du chemin est nécessaire, cela doit être construit séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache afin que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle du pathPtr passé (sauf si c'est un chemin relatif, auquel cas la représentation native peut être libérée à tout moment où le cwd change).

Tcl_FSFileSystemInfo renvoie une liste de deux éléments. Le premier élément est le nom du système de fichiers (par exemple, « native », « vfs », « zip », ou « prowrap », peut-être), et le second est le type particulier du chemin donné dans ce système de fichiers (qui dépend du système de fichiers). Le second élément peut être vide si le système de fichiers ne fournit pas de catégorisation supplémentaire des fichiers.

Une valeur de liste valide est retournée, à moins que la valeur du chemin ne soit pas reconnue, auquel cas NULL sera retourné.

Tcl_FSGetFileSystemForPath renvoie un pointeur vers le Tcl_Filesystem qui accepte ce chemin comme valide.

Si aucun système de fichiers n'accepte le chemin, NULL est retourné.

Tcl_FSGetPathType détermine si le chemin donné est relatif au répertoire courant, relatif au volume courant, ou absolu.

Il retourne l'un des TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, ou TCL_PATH_VOLUME_RELATIVE

L'API DU SYSTÈME DE FICHIERS VIRTUEL

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un système de fichiers ; ces opérations sont appelées selon les besoins par la couche générique, ce qui se produit généralement via les fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un élément de données optionnel à associer à ce système de fichiers. Lors de l'appel de cette fonction, Tcl attache le système de fichiers à la liste des systèmes de fichiers connus, et il devient pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera retourné.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et retourne TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est retourné.

Tcl_FSData retournera le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il retournera NULL.

Tcl_FSMountsChanged est utilisé pour informer le noyau de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche générique du système de fichiers pour effectuer toute la gamme des actions relatives au système de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (dont presque toutes doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni), et fonctions d'efficacité (qui n'ont besoin d'être implémentées que si elles peuvent l'être efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces solutions de secours ne sont utilisées que pour gérer les commandes initiées en Tcl, pas en C. Cela signifie que si une commande file rename est émise en Tcl, et que le(s) système(s) de fichiers concerné(s) n'implémente pas son Tcl_FSRenameFileProc, le noyau de Tcl utilisera alors une combinaison d'autres fonctions du système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a un autre recours). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun recours de ce type ne se produit. Ceci est vrai sauf pour les quatre dernières entrées du tableau des systèmes de fichiers (lstat, load, getcwd et chdir) pour lesquelles des recours se produisent effectivement au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme Tcl_Obj prennent ces noms sous forme UTF-8. L'API de l'infrastructure du système de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

PROCÉDURE DE DÉTERMINATION DU SYSTÈME DE FICHIERS DU CHEMIN

Le champ pathInFilesystemProc contient l'adresse d'une fonction qui est appelée pour déterminer si une valeur de chemin donnée appartient à ce système de fichiers ou non. Tcl n'appellera les fonctions restantes du système de fichiers qu'avec un chemin pour lequel cette fonction a renvoyé TCL_OK. Si le chemin n'appartient pas, -1 doit être renvoyé (le comportement de Tcl pour toute autre valeur renvoyée n'est pas défini). Si TCL_OK est renvoyé, alors le paramètre de sortie optionnel clientDataPtr peut être utilisé pour renvoyer une représentation interne (spécifique au système de fichiers) du chemin, qui sera stockée dans la valeur du chemin, et pourra être récupérée efficacement par d'autres fonctions du système de fichiers. Tcl mettra simultanément en cache l'information selon laquelle ce chemin appartient à ce système de fichiers. De tels caches sont invalidés lorsque les structures de systèmes de fichiers sont ajoutées ou supprimées de la liste interne des systèmes de fichiers connus de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROCÉDURE DE DUPLICATION DE LA REPRÉSENTATION INTERNE

Cette fonction crée une copie de la représentation interne d'un chemin et est appelée lorsque Tcl a besoin de dupliquer une valeur de chemin. Si elle est NULL, Tcl ne copiera pas la représentation interne, ce qui pourrait être nécessaire après la copie.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

PROCÉDURE DE LIBÉRATION DE LA REPRÉSENTATION INTERNE

Libère la représentation interne. Doit être implémentée si la représentation interne doit être libérée (c'est-à-dire si de la mémoire a été allouée lors de la création d'une représentation interne), mais peut être NULL sinon.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

PROCÉDURE DE CONVERSION DE L'INTERNE EN NORMALISÉ

Fonction pour convertir une représentation interne en un chemin normalisé. N'est nécessaire que si le système de fichiers crée des valeurs de chemin pures sans représentation chaîne/chemin. La valeur renvoyée est un objet Tcl dont la représentation chaîne est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

PROCÉDURE DE CRÉATION DE LA REPRÉSENTATION INTERNE

Fonction pour calculer une représentation interne d'une valeur de chemin et la stocker dans la valeur. Peut être NULL si les chemins n'ont pas de représentation interne, ou si le Tcl_FSPathInFilesystemProc pour ce système de fichiers crée toujours directement une représentation interne pour les chemins qu'il accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

PROCÉDURE DE NORMALISATION DU CHEMIN

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui ont plusieurs représentations de chaîne pour le même chemin de valeur. Dans Tcl, chaque chemin doit avoir une seule représentation normalisée unique. Selon le système de fichiers, il peut y avoir plus d'une représentation de chaîne non normalisée faisant référence à ce chemin (par exemple, un chemin relatif, un chemin avec une casse différente si le système de fichiers ne respecte pas la casse, un chemin contenant une référence à un répertoire utilisateur comme ~, un chemin contenant des liens symboliques, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être résolu en sa valeur (mais sa casse ou d'autres aspects doivent être uniques). Tous les autres composants du chemin doivent être résolus à partir des liens symboliques. Cette exception est nécessaire pour s'aligner sur la sémantique de Tcl pour les commandes telles que file delete, file rename, file copy sur des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint au début du chemin (c'est-à-dire zéro), à la fin du chemin, ou à tout délimiteur de fichier intermédiaire dans le chemin. Elle ne sera pas appelée à toute autre position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémenteur peut supposer que le chemin jusqu'au délimiteur inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS DU SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions qui sont appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui est censé être utilisé avec l'ensemble complet des commandes Tcl doit implémenter toutes ces fonctions. Si l'une d'elles n'est pas implémentée, certaines commandes Tcl peuvent échouer lors de l'opération sur des chemins dans ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques ne devrait pas implémenter la fonction readlink, etc. Le noyau Tcl s'attend à ce que les systèmes de fichiers agissent de cette manière).

PROCÉDURE DE TYPE DE CHEMIN DU SYSTÈME DE FICHIERS

OPENFILECHANNELPROC

Fonction pour traiter un appel à Tcl_FSOpenFileChannel. Elle doit être implémentée pour tout système de fichiers raisonnable, car toute opération nécessitant l'ouverture ou l'accès au contenu d'un fichier utilisera cette fonction (par exemple, open, encoding et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

La Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et renvoie un descripteur de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est calquée sur la fonction fopen de la bibliothèque d'entrée/sortie standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier, où l'argument mode est une combinaison des drapeaux POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, la Tcl_FSOpenFileChannelProc renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas nul, la Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le canal créé ne doit pas être enregistré dans l'interpréteur fourni par une Tcl_FSOpenFileChannelProc ; ce travail incombe à l'appelant Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, la création du nouveau canal l'attribue également en remplacement du canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, la fonctionnalité de glob et de copie récursive sera perdue dans le système de fichiers (et cela peut affecter des commandes telles que encoding names qui utilisent la fonctionnalité de glob).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit renvoyer tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au motif donné et qui correspondent à la spécification types. Cette fonction peut être appelée de deux manières. Si pattern est NULL, pathPtr spécifie un chemin complet d'un fichier ou d'un répertoire dont il faut vérifier l'existence et le type. Sinon, pathPtr est un répertoire et la fonction doit rechercher des fichiers ou des répertoires du bon type. Dans tous les cas, pathPtr sera supposé non nul et non vide. Il n'est pas documenté si pathPtr a un séparateur de fichier à la fin de sa chaîne, le code doit donc être flexible aux deux possibilités.

La valeur de retour est un résultat standard de Tcl indiquant si une erreur s'est produite pendant le processus de mise en correspondance. Les messages d'erreur sont placés dans interp, sauf si interp est NULL, auquel cas aucun message d'erreur n'est généré. Dans un résultat TCL_OK, les résultats doivent être ajoutés à la valeur resultPtr fournie (qui sera supposée être une liste Tcl valide et non partagée). Les résultats ajoutés à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (ce qui signifie généralement qu'il s'agira de spécifications de chemin absolu). Remarque : s'il n'y a pas de correspondances, un résultat vide est obtenu ; seules les erreurs réelles de fichier ou de système de fichiers qui peuvent survenir pendant le processus de mise en correspondance sont signalées.

La structure Tcl_GlobTypeData passée dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Corresponds to bcdpfls as in 'find -t' */
    int type;
    /* Corresponds to file permissions */
    int perm;
    /* Acceptable mac type */
    Tcl_Obj *macType;
    /* Acceptable mac creator */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de gérer correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT sont vrais (et en particulier lorsque les autres drapeaux sont faux). Dans le premier cas, la fonction doit lister les répertoires contenus. Tcl utilise cela pour implémenter le globbing récursif, il est donc essentiel que les systèmes de fichiers implémentent correctement la mise en correspondance des répertoires. Dans le second cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage qui se trouvent dans le pathPtr donné (et dans ce cas, pathPtr n'a pas besoin d'être dans le même système de fichiers - contrairement à tous les autres cas où cette fonction est appelée). Le support de ceci est essentiel si Tcl doit avoir des transitions douces entre les systèmes de fichiers.

LINKPROC

Fonction pour traiter un appel à Tcl_FSLink. Elle ne doit être implémentée que si le système de fichiers prend en charge les liens, et peut sinon être NULL.

Fonction pour lister les volumes du système de fichiers ajoutés par ce système de fichiers. Elle ne doit être implémentée que si le système de fichiers ajoute des volumes au début du système de fichiers, afin qu'ils puissent être renvoyés par file volumes.

        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du processus de copie. Notez que destPathPtr est le nom du fichier qui deviendra la copie de srcPathPtr. Ce n'est jamais le nom d'un répertoire dans lequel srcPathPtr pourrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande Tcl de niveau file copy). Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non copyDirectoryProc lorsqu'il est nécessaire de les copier (même s'il s'agit de liens symboliques vers des répertoires). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file copy, l'appel à Tcl_SetErrno(EXDEV) et le retour d'un résultat différent de TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

RENAMEFILEPROC

Fonction pour traiter un appel à Tcl_FSRenameFile. Si non implémentée, Tcl utilisera un mécanisme de copie et de suppression. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du processus de renommage. Si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file rename, l'appel à Tcl_SetErrno(EXDEV) et le retour d'un résultat différent de TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

COPYDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSCopyDirectory. Si non implémentée, Tcl utilisera un mécanisme récursif de file mkdir, file copy. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du processus de copie. Si une erreur se produit, le nom du fichier ou du répertoire qui a causé l'erreur devrait être placé dans errorPtr. Notez que destPathPtr est le nom du répertoire qui devrait devenir l'image miroir de srcPathPtr. Ce n'est pas le nom d'un répertoire dans lequel srcPathPtr devrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande Tcl de niveau file copy). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de copie de répertoire, l'appel à Tcl_SetErrno(EXDEV) et le retour d'un résultat différent de TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

LOADFILEPROC

Fonction pour traiter un appel à Tcl_FSLoadFile. Si non implémentée, Tcl utilisera une copie vers un fichier temporaire natif suivie d'un Tcl_FSLoadFile sur cette copie temporaire. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut charger du code directement, ou si elle peut être implémentée simplement pour renvoyer TCL_ERROR afin de désactiver complètement la fonctionnalité de chargement dans ce système de fichiers.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Renvoie un code de complétion Tcl standard. En cas d'erreur, un message d'erreur est laissé dans le résultat de l'interp. La fonction charge dynamiquement un fichier de code binaire en mémoire. En cas de chargement réussi, handlePtr doit être rempli avec un jeton pour le fichier chargé dynamiquement, et unloadProcPtr doit être rempli avec l'adresse d'une procédure. La procédure de déchargement sera appelée avec Tcl_LoadHandle comme seul paramètre lorsque Tcl aura besoin de décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle renvoyé est actuellement un jeton qui peut être utilisé dans TclpFindSymbol privé pour accéder aux fonctions du nouveau code. Chaque système de fichiers est libre de définir le Tcl_LoadHandle comme il l'entend. Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de chargement de fichier, l'appel à Tcl_SetErrno(EXDEV) et le retour d'un résultat différent de TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

UNLOADFILEPROC

Fonction pour décharger un fichier précédemment chargé avec succès. Si le chargement a été implémenté, alors celui-ci devrait également être implémenté, s'il y a des actions de nettoyage requises.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Fonction pour traiter un appel à Tcl_FSGetCwd. La plupart des systèmes de fichiers n'ont pas besoin de l'implémenter. Elle ne sera généralement appelée qu'une seule fois, si getcwd est appelé avant chdir. Peut être NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si le système de fichiers prend en charge une notion native de répertoire de travail courant (qui pourrait potentiellement changer indépendamment de Tcl), cette fonction devrait renvoyer ce répertoire courant comme résultat, ou NULL si le répertoire courant n'a pas pu être déterminé (par exemple, si l'utilisateur n'a pas les permissions appropriées sur le répertoire courant). Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de l'interp.

CHDIRPROC

Fonction pour traiter un appel à Tcl_FSChdir. Si les systèmes de fichiers ne l'implémentent pas, elle sera émulée par une série de vérifications d'accès aux répertoires. Sinon, les systèmes de fichiers virtuels qui l'implémentent n'ont qu'à répondre avec un résultat positif si pathPtr est un répertoire valide et accessible dans leur système de fichiers. Ils n'ont pas besoin de mémoriser le résultat, car celui-ci sera automatiquement mémorisé pour être utilisé par Tcl_FSGetCwd. Les systèmes de fichiers réels devraient effectuer l'action correcte (c'est-à-dire appeler l'API système chdir correcte).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

Le Tcl_FSChdirProc change le répertoire de travail courant de l'application pour la valeur spécifiée dans pathPtr. La fonction renvoie -1 en cas d'erreur ou 0 en cas de succès.
