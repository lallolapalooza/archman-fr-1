INTRODUCTION

Ces routines convertissent entre la représentation interne de caractères de Tcl, UTF-8, et les représentations de caractères utilisées par divers systèmes d'exploitation ou systèmes de fichiers, tels que Unicode, ASCII ou Shift-JIS. Lors de l'opération sur des chaînes de caractères, telles que l'obtention de noms de fichiers ou l'affichage de caractères à l'aide de polices internationales, les chaînes doivent être traduites dans un ou potentiellement plusieurs formats que les divers appels système peuvent utiliser. Par exemple, sur une station de travail Unix japonaise, un utilisateur pourrait obtenir un nom de fichier représenté dans l'encodage de fichier EUC-JP, puis traduire les caractères dans l'encodage de police jisx0208 afin d'afficher le nom de fichier dans un widget Tk. Le but du package d'encodage est d'aider à combler l'écart de traduction. UTF-8 fournit une zone de transit intermédiaire pour tous les divers encodages. Dans l'exemple ci-dessus, le texte serait traduit en UTF-8 à partir de l'encodage de fichier utilisé par le système d'exploitation. Ensuite, il serait traduit de l'UTF-8 vers l'encodage de police requis par les routines d'affichage.

Certains encodages de base sont intégrés à Tcl. D'autres peuvent être définis par l'utilisateur ou chargés dynamiquement à partir de fichiers d'encodage d'une manière indépendante de la plateforme.

DESCRIPTION

Tcl_GetEncoding trouve un encodage étant donné son name. Le nom peut faire référence à un encodage Tcl intégré, un encodage défini par l'utilisateur enregistré en appelant Tcl_CreateEncoding, ou un fichier d'encodage chargeable dynamiquement. La valeur de retour est un jeton qui représente l'encodage et peut être utilisé dans des appels ultérieurs à des procédures telles que Tcl_GetEncodingName, Tcl_FreeEncoding et Tcl_UtfToExternal. Si le nom ne fait référence à aucun encodage connu ou chargeable, NULL est retourné et un message d'erreur est retourné dans interp.

Le package d'encodage maintient une base de données de tous les encodages actuellement en cours d'utilisation. La première fois que name est vu, Tcl_GetEncoding retourne un encodage avec un compteur de références de 1. Si le même name est demandé plusieurs fois, le compteur de références pour cet encodage est incrémenté sans le surcoût de l'allocation d'un nouvel encodage et de toutes ses structures de données associées.

Lorsqu'un encoding n'est plus nécessaire, Tcl_FreeEncoding doit être appelé pour le libérer. Lorsqu'un encoding n'est plus utilisé nulle part (c'est-à-dire qu'il a été libéré autant de fois qu'il a été obtenu), Tcl_FreeEncoding libérera tout le stockage utilisé par l'encodage et le supprimera de la base de données.

Tcl_GetEncodingFromObj traite la représentation sous forme de chaîne de objPtr comme un nom d'encodage, et trouve un encodage avec ce nom, tout comme le fait Tcl_GetEncoding. Lorsqu'un encodage est trouvé, il est mis en cache dans la valeur objPtr pour référence future, le jeton Tcl_Encoding est écrit dans le stockage pointe

Tout comme avec Tcl_GetEncoding, l'appelant doit appeler Tcl_FreeEncoding sur le jeton d'encodage résultant lorsque ce jeton ne sera plus utilisé.

Tcl_ExternalToUtfDString convertit un tampon source src de l'encodage spécifié vers UTF-8. Les octets convertis sont stockés dans dstPtr, qui est ensuite terminé par un caractère nul. L'appelant doit éventuellement appeler Tcl_DStringFree pour libérer toute information stockée dans dstPtr. Lors de la conversion, si l'un des caractères du tampon source ne peut être représenté dans l'encodage de destination, un caractère de repli par défaut sera utilisé. La valeur de retour est un pointeur vers la valeur stockée dans le DString.

Tcl_ExternalToUtf convertit un tampon source src de l'encodage spécifié vers UTF-8. Jusqu'à srcLen octets sont convertis depuis le tampon source et jusqu'à dstLen octets convertis sont stockés dans dst. Dans tous les cas, *srcReadPtr est rempli avec le nombre d'octets qui ont été convertis avec succès depuis src et *dstWrotePtr est rempli avec le nombre correspondant d'octets qui ont été stockés dans dst. La valeur de retour est l'une des suivantes :

TCL_OK
Tous les octets de src ont été convertis.
TCL_CONVERT_NOSPACE
Le tampon de destination n'était pas assez grand pour toutes les données converties ; cependant, autant de caractères que possible ont été convertis.
TCL_CONVERT_MULTIBYTE
Les derniers octets du tampon source étaient le début d'une séquence multi-octets, mais des octets supplémentaires étaient nécessaires pour compléter cette séquence. Un appel ultérieur à la routine de conversion devrait passer un tampon contenant les octets non convertis qui restaient dans src plus quelques octets supplémentaires du flux source pour convertir correctement la séquence multi-octets précédemment divisée.
TCL_CONVERT_SYNTAX
Le tampon source contenait une séquence de caractères invalide. Cela peut se produire si le flux d'entrée a été endommagé ou si la méthode d'encodage d'entrée a été mal identifiée.
TCL_CONVERT_UNKNOWN
Le tampon source contenait un caractère qui ne pouvait pas être représenté dans l'encodage de destination et TCL_ENCODING_STOPONERROR a été spécifié.

Tcl_UtfToExternalDString convertit un tampon source src d'UTF-8 vers l'encodage spécifié. Les octets convertis sont stockés dans dstPtr, qui est ensuite terminé par un caractère nul spécifique à l'encodage. L'appelant doit éventuellement appeler Tcl_DStringFree pour libérer toute information stockée dans dstPtr. Lors de la conversion, si l'un des caractères du tampon source ne peut être représenté dans l'encodage de destination, un caractère de repli par défaut sera utilisé. La valeur de retour est un pointeur vers la valeur stockée dans le DString.

Tcl_UtfToExternal convertit un tampon source src d'UTF-8 vers l'encodage spécifié. Jusqu'à srcLen octets sont convertis depuis le tampon source et jusqu'à dstLen octets convertis sont stockés dans dst. Dans tous les cas, *srcReadPtr est rempli avec le nombre d'octets qui ont été convertis avec succès depuis src et *dstWrotePtr est rempli avec le nombre correspondant d'octets qui ont été stockés dans dst. Les valeurs de retour sont les mêmes que celles pour Tcl_ExternalToUtf.

Tcl_WinUtfToTChar et Tcl_WinTCharToUtf sont des fonctions utilitaires propres à Windows pour convertir entre UTF-8 et les chaînes de caractères Windows basées sur le type TCHAR qui est par convention un caractère Unicode sur Windows NT.

Tcl_GetEncodingName est à peu près l'inverse de Tcl_GetEncoding. Étant donné un encoding, la valeur de retour est l'argument name qui a été utilisé pour créer l'encodage. La chaîne retournée par Tcl_GetEncodingName n'est garantie de persister que jusqu'à ce que l'encodage soit supprimé. L'appelant ne doit pas modifier cette chaîne.

Tcl_SetSystemEncoding définit l'encodage par défaut qui doit être utilisé chaque fois que l'utilisateur passe une valeur NULL pour l'argument encoding à l'une des autres fonctions d'encodage. Si name est NULL, l'encodage système est réinitialisé à l'encodage système par défaut, binary. Si le nom ne fait pas référence à un encodage connu ou chargeable, TCL_ERROR est retourné et un message d'erreur est laissé dans interp. Sinon, cette procédure incrémente le compteur de références du nouvel encodage système, décrémente le compteur de références de l'ancien encodage système et retourne TCL_OK.

Tcl_GetEncodingNameFromEnvironment fournit un moyen pour la bibliothèque Tcl de signaler le nom de l'encodage qu'elle considère comme correct à utiliser comme encodage système, basé sur des appels système et l'examen de l'environnement adapté à la plateforme. Elle accepte bufPtr, un pointeur vers un Tcl_DString non initialisé ou libéré, et y écrit le nom de l'encodage. La valeur Tcl_DStringValue est retournée.

Tcl_GetEncodingNames définit le résultat de interp en une liste composée des noms de tous les encodages qui sont actuellement définis ou qui peuvent être chargés dynamiquement, en recherchant dans le chemin d'encodage spécifié par Tcl_SetDefaultEncodingDir. Cette procédure ne garantit pas que les fichiers d'encodage chargeables dynamiquement contiennent des données valides, mais seulement qu'ils existent.

Tcl_CreateEncoding définit un nouvel encodage et enregistre les procédures C qui sont appelées pour convertir entre l'encodage et UTF-8. Les encodages créés par Tcl_CreateEncoding sont ensuite visibles dans la base de données utilisée par Tcl_GetEncoding. Tout comme avec la procédure Tcl_GetEncoding, la valeur de retour est un jeton qui représente l'encodage et peut être utilisé dans les appels ultérieurs à d'autres fonctions d'encodage. Tcl_CreateEncoding retourne un encodage avec un compteur de références de 1. Si un encodage avec le nom spécifié existe déjà, son entrée dans la base de données est remplacée par le nouvel encodage ; le jeton de l'ancien encodage restera valide et continuera de se comporter comme avant, mais les utilisateurs du nouveau jeton appelleront désormais les nouvelles procédures d'encodage.

L'argument typePtr à Tcl_CreateEncoding contient des informations sur le nom de l'encodage et les procédures qui seront appelées pour convertir entre cet encodage et UTF-8. Il est défini comme suit :

typedef struct Tcl_EncodingType {
    const char *encodingName;
    Tcl_EncodingConvertProc *toUtfProc;
    Tcl_EncodingConvertProc *fromUtfProc;
    Tcl_EncodingFreeProc *freeProc;
    ClientData clientData;
    int nullSize;
} Tcl_EncodingType;

L'encodingName fournit un nom textuel pour l'encodage, par lequel il peut être référencé dans d'autres procédures telles que Tcl_GetEncoding. Le toUtfProc fait référence à une procédure de rappel à invoquer pour convertir du texte de cet encodage vers UTF-8. Le fromUtfProc fait référence à une procédure de rappel à invoquer pour convertir du texte d'UTF-8 vers cet encodage. Le freeProc fait référence à une procédure de rappel à invoquer lorsque cet encodage est supprimé. Le champ freeProc peut être NULL. Le clientData contient une valeur arbitraire d'un mot passée aux procédures toUtfProc, fromUtfProc, et freeProc chaque fois qu'elles sont appelées. Typiquement, il s'agit d'un pointeur vers une structure de données contenant des informations spécifiques à l'encodage qui peuvent être utilisées par les procédures de rappel. Par exemple, deux encodages très similaires tels que ascii et macRoman peuvent utiliser la même procédure de rappel, mais utiliser des valeurs différentes de clientData pour contrôler son comportement. Le nullSize spécifie le nombre d'octets nuls qui signifient la fin de la chaîne dans cet encodage. Il doit être de 1 (pour les encodages mono-octet ou multi-octets comme ASCII ou Shift-JIS) ou de 2 (pour les encodages bi-octets comme Unicode). Les encodages de taille constante avec 3 octets ou plus par caractère (comme CNS11643) ne sont pas acceptés.

Les procédures de rappel toUtfProc et fromUtfProc doivent correspondre au type Tcl_EncodingConvertProc :

typedef int Tcl_EncodingConvertProc(
        ClientData clientData,
        const char *src,
        int srcLen,
        int flags,
        Tcl_EncodingState *statePtr,
        char *dst,
        int dstLen,
        int *srcReadPtr,
        int *dstWrotePtr,
        int *dstCharsPtr);

Les procédures toUtfProc et fromUtfProc sont appelées par la famille de fonctions Tcl_ExternalToUtf ou Tcl_UtfToExternal pour effectuer la conversion réelle. Le paramètre clientData à ces procédures est le même que le champ clientData spécifié à Tcl_CreateEncoding lors de la création de l'encodage. Les arguments restants aux procédures de rappel sont les mêmes que les arguments, documentés en haut, de Tcl_ExternalToUtf ou Tcl_UtfToExternal, avec les exceptions suivantes. Si l'argument srcLen à l'une de ces fonctions de haut niveau est négatif, la valeur passée à la procédure de rappel sera la longueur de chaîne spécifique à l'encodage appropriée de src. Si l'un des arguments srcReadPtr, dstWrotePtr, ou dstCharsPtr à l'une des fonctions de haut niveau est NULL, la valeur correspondante passée à la procédure de rappel sera un emplacement non NULL.

La procédure de rappel freeProc, si elle n'est pas NULL, doit correspondre au type Tcl_EncodingFreeProc :

typedef void Tcl_EncodingFreeProc(
        ClientData clientData);

Cette fonction freeProc est appelée lorsque l'encodage est supprimé. Le paramètre clientData est le même que le champ clientData spécifié à Tcl_CreateEncoding lors de la création de l'encodage.

Tcl_GetEncodingSearchPath et Tcl_SetEncodingSearchPath sont appelés pour accéder et définir la liste des répertoires du système de fichiers dans lesquels rechercher les fichiers de données d'encodage.

La valeur retournée par Tcl_GetEncodingSearchPath est la valeur stockée par le dernier appel réussi à Tcl_SetEncodingSearchPath. Si aucun appel à Tcl_SetEncodingSearchPath n'a eu lieu, Tcl calculera une valeur initiale basée sur l'environnement. Il existe un seul chemin de recherche d'encodage pour l'ensemble du processus, partagé par tous les threads du processus.

INTRODUCTION

The Tcl library provides support for Unicode through its internal representation, called Tcl_UniChar. Many operating systems, notably Windows, use UTF-16 as their native representation for Unicode. These procedures provide a bridge between Tcl’s internal UTF-8 representation and the Windows UTF-16 representation.

DESCRIPTION

These routines perform conversions between Tcl’s internal UTF-8 representation and the UTF-16 representation used by the Windows operating system. A Tcl_UniChar is a 16-bit unsigned integer type. Tcl itself uses UTF-8 strings internally, which are sequences of 8-bit bytes that can represent any Unicode character. UTF-16 strings are sequences of 16-bit units. Some Unicode characters require two 16-bit units (a surrogate pair) to represent them in UTF-16.

Tcl_WinUtfToTChar converts a string in UTF-8 encoding to a string in UTF-16 encoding. The utf argument is a pointer to the UTF-8 string, and length is its length in bytes. The converted string is written to the buffer pointed to by tchar, and tcharLen is the maximum number of Tcl_UniChars to store in that buffer. If the conversion is successful, the number of bytes consumed from the utf string is stored in the location pointed to by charsConsumed, if not NULL. The function returns the number of Tcl_UniChars written to the tchar buffer. If the conversion fails because the tchar buffer is too small, the function returns -1 and leaves the number of bytes consumed in charsConsumed. If the conversion fails for any other reason (e.g., invalid UTF-8 input), the function returns -1 and leaves 0 in charsConsumed.

Tcl_WinTCharToUtf converts a string in UTF-16 encoding to a string in UTF-8 encoding. The tchar argument is a pointer to the UTF-16 string, and length is its length in Tcl_UniChars. The converted string is written to the buffer pointed to by utf, and utfLen is the maximum number of bytes to store in that buffer. If the conversion is successful, the number of Tcl_UniChars consumed from the tchar string is stored in the location pointed to by charsConsumed, if not NULL. The function returns the number of bytes written to the utf buffer. If the conversion fails because the utf buffer is too small, the function returns -1 and leaves the number of Tcl_UniChars consumed in charsConsumed. If the conversion fails for any other reason (e.g., invalid UTF-16 input), the function returns -1 and leaves 0 in charsConsumed.

Note that these functions are intended for use on Windows systems. They use the Windows API calls WideCharToMultiByte and MultiByteToWideChar to perform the conversions.

The Tcl library maintains a list of directories where it searches for encoding data files. This list is called the searchPath. Calls to Tcl_GetEncodingSearchPath and Tcl_SetEncodingSearchPath may be used to get and set this list. The directories in the searchPath list are searched in order. Encoding data files that are not found are silently ignored. Directories are not verified as existing readable filesystem directories. When searching for encoding data files takes place, and non-existent or non-readable filesystem directories on the searchPath are silently ignored.

Tcl_GetDefaultEncodingDir and Tcl_SetDefaultEncodingDir are obsolete interfaces best replaced with calls to Tcl_GetEncodingSearchPath and Tcl_SetEncodingSearchPath. They are called to access and set the first element of the searchPath list. Since Tcl searches searchPath for encoding data files in list order, these routines establish the “default” directory in which to find encoding data files.

ENCODING FILES

Space would prohibit precompiling into Tcl every possible encoding algorithm, so many encodings are stored on disk as dynamically-loadable encoding files. This behavior also allows the user to create additional encoding files that can be loaded using the same mechanism. These encoding files contain information about the tables and/or escape sequences used to map between an external encoding and Unicode. The external encoding may consist of single-byte, multi-byte, or double-byte characters.

Each dynamically-loadable encoding is represented as a text file. The initial line of the file, beginning with a “#” symbol, is a comment that provides a human-readable description of the file. The next line identifies the type of encoding file. It can be one of the following letters:

[1] S
A single-byte encoding, where one character is always one byte long in the encoding. An example is iso8859-1, used by many European languages.
[2] D
A double-byte encoding, where one character is always two bytes long in the encoding. An example is big5, used for Chinese text.
[3] M
A multi-byte encoding, where one character may be either one or two bytes long. Certain bytes are lead bytes, indicating that another byte must follow and that together the two bytes represent one character. Other bytes are not lead bytes and represent themselves. An example is shiftjis, used by many Japanese computers.
[4] E
An escape-sequence encoding, specifying that certain sequences of bytes do not represent characters, but commands that describe how following bytes should be interpreted.

The rest of the lines in the file depend on the type.

Cases [1], [2], and [3] are collectively referred to as table-based encoding files. The lines in a table-based encoding file are in the same format as this example taken from the shiftjis encoding (this is not the complete file):

The third line of the file is three numbers. The first number is the fallback character (in base 16) to use when converting from UTF-8 to this encoding. The second number is a 1 if this file represents the encoding for a symbol font, or 0 otherwise. The last number (in base 10) is how many pages of data follow.

Subsequent lines in the example above are pages that describe how to map from the encoding into 2-byte Unicode. The first line in a page identifies the page number. Following it are 256 double-byte numbers, arranged as 16 rows of 16 numbers. Given a character in the encoding, the high byte of that character is used to select which page, and the low byte of that character is used as an index to select one of the double-byte numbers in that page - the value obtained being the corresponding Unicode character. By examination of the example above, one can see that the characters 0x7E and 0x8163 in shiftjis map to 203E and 2026 in Unicode, respectively.

Following the first page will be all the other pages, each in the same format as the first: one number identifying the page followed by 256 double-byte Unicode characters. If a character in the encoding maps to the Unicode character 0000, it means that the character does not actually exist. If all characters on a page would map to 0000, that page can be omitted.

Case [4] is the escape-sequence encoding file. The lines in an this type of file are in the same format as this example taken from the iso2022-jp encoding:

# Encoding file: iso2022-jp, escape-driven
E
init		{}
final		{}
iso8859-1	\x1b(B
jis0201		\x1b(J
jis0208		\x1b$@
jis0208		\x1b$B
jis0212		\x1b$(D
gb2312		\x1b$A
ksc5601		\x1b$(C

In the file, the first column represents an option and the second column is the associated value. init is a string to emit or expect before the first character is converted, while final is a string to emit or expect after the last character. All other options are names of table-based encodings; the associated value is the escape-sequence that marks that encoding. Tcl syntax is used for the values; in the above example, for instance, “{}” represents the empty string and “\x1b” represents character 27.

When Tcl_GetEncoding encounters an encoding name that has not been loaded, it attempts to load an encoding file called name.enc from the encoding subdirectory of each directory that Tcl searches for its script library. If the encoding file exists, but is malformed, an error message will be left in interp.
