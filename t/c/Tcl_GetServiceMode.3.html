INTRODUCTION

Les interfaces décrites ici sont utilisées pour personnaliser la boucle d'événements Tcl. Les deux personnalisations les plus courantes sont d'ajouter de nouvelles sources d'événements et de fusionner la boucle d'événements Tcl avec une autre boucle d'événements, telle que celle fournie par une application dans laquelle Tcl est intégrée. Chacune de ces tâches est décrite dans une section distincte ci-dessous.

Les procédures de cette entrée de manuel sont les éléments constitutifs de la construction du notificateur d'événements Tcl. Le notificateur d'événements est la couche la plus basse du mécanisme d'événements Tcl. Il se compose de trois choses :

[1]
Sources d'événements : celles-ci représentent les moyens par lesquels les événements peuvent être générés. Par exemple, il existe une source d'événements de minuteur qui implémente la procédure Tcl_CreateTimerHandler et la commande after, et il existe une source d'événements de fichier qui implémente la procédure Tcl_CreateFileHandler sur les systèmes Unix. Une source d'événements doit travailler avec le notificateur pour détecter les événements aux bons moments, les enregistrer sur la file d'attente des événements et informer finalement le logiciel de niveau supérieur qu'ils se sont produits. Les procédures Tcl_CreateEventSource, Tcl_DeleteEventSource, Tcl_SetMaxBlockTime, Tcl_QueueEvent et Tcl_DeleteEvents sont principalement utilisées par les sources d'événements.
[2]
La file d'attente des événements : pour les applications non multithread, il existe une seule file pour toute l'application, contenant les événements qui ont été détectés mais pas encore traités. Les sources d'événements placent les événements dans la file d'attente afin qu'ils puissent être traités en ordre à des moments appropriés pendant la boucle d'événements. La file d'attente des événements garantit une discipline équitable de gestion des événements, de sorte qu'aucune source d'événements ne puisse affamer les autres. Elle permet également de sauvegarder des événements pour un traitement ultérieur. Les applications multithread fonctionnent de manière similaire, sauf qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. Tcl_QueueEvent est utilisée (principalement par les sources d'événements) pour ajouter des événements à la file d'attente des événements et Tcl_DeleteEvents est utilisée pour supprimer des événements de la file d'attente sans les traiter. Dans une application multithread, Tcl_QueueEvent ajoute un événement à la file d'attente du thread courant, et Tcl_ThreadQueueEvent ajoute un événement à une file d'attente dans un thread spécifique.
[3]
La boucle d'événements : afin de détecter et de traiter les événements, l'application entre dans une boucle qui attend que les événements se produisent, les place dans la file d'attente des événements, puis les traite. La plupart des applications le feront en appelant la procédure Tcl_DoOneEvent, qui est décrite dans une entrée de manuel séparée.

La plupart des applications Tcl n'ont pas besoin de se soucier des détails internes du notificateur Tcl. Cependant, le notificateur est maintenant suffisamment flexible pour être redirigé soit vers une nouvelle plateforme, soit pour utiliser une boucle d'événements externe (telle que la boucle d'événements Motif, lorsque Tcl est intégrée dans une application Motif). Les procédures Tcl_WaitForEvent et Tcl_SetTimer sont normalement implémentées par Tcl, mais peuvent être remplacées par de nouvelles versions pour rediriger le notificateur (Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler et Tcl_DeleteFileHandler doivent également être remplacées ; voir CRÉER UN NOUVEAU NOTIFICATEUR ci-dessous pour plus de détails). Les procédures Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode et Tcl_SetServiceMode sont fournies pour aider à connecter la boucle d'événements Tcl à une boucle d'événements externe telle que celle de Motif.

BASES DU NOTIFICATEUR

Le moyen le plus simple de comprendre le fonctionnement du notificateur est de considérer ce qui se passe lorsque Tcl_DoOneEvent est appelé. Tcl_DoOneEvent reçoit un argument flags qui indique quels types d'événements peuvent être traités et s'il faut bloquer si aucun événement n'est prêt. Tcl_DoOneEvent effectue les opérations suivantes :

[1]
Vérifier la file d'attente des événements pour voir si elle contient des événements pouvant être traités. Si c'est le cas, traiter le premier événement possible, le retirer de la file d'attente et retourner. Pour ce faire, elle appelle Tcl_ServiceEvent et lui passe l'argument flags.
[2]
Se préparer à bloquer pour un événement. Pour ce faire, Tcl_DoOneEvent invoque une procédure setup dans chaque source d'événements. La source d'événements effectuera l'initialisation spécifique à la source d'événements et pourra appeler Tcl_SetMaxBlockTime pour limiter la durée pendant laquelle Tcl_WaitForEvent bloquera si aucun nouvel événement ne se produit.
[3]
Appeler Tcl_WaitForEvent. Cette procédure est implémentée différemment selon les plates-formes ; elle attend qu'un événement se produise, en fonction des informations fournies par les sources d'événements. Elle peut provoquer le blocage de l'application si timePtr spécifie un intervalle différent de 0. Tcl_WaitForEvent retourne lorsque quelque chose s'est produit, comme un fichier devenant lisible ou l'expiration de l'intervalle donné par timePtr. S'il n'y a aucun événement pour Tcl_WaitForEvent à attendre, de sorte qu'elle bloquerait indéfiniment, alors elle retourne immédiatement et Tcl_DoOneEvent retourne 0.
[4]
Appeler une procédure check dans chaque source d'événements. La procédure check détermine si des événements intéressant cette source se sont produits. Le cas échéant, les événements sont ajoutés à la file d'attente des événements.
[5]
Vérifier th
e file d'attente d'événements pour voir s'il contient des événements qui peuvent être servis. Si c'est le cas, servir le premier événement possible, le supprimer de la file d'attente et retourner.
[6]
Vérifier s'il y a des rappels inactifs en attente. Si c'est le cas, les invoquer tous et retourner.
[7]
Soit retourner 0 pour indiquer qu'aucun événement n'était prêt, soit retourner à l'étape [2] si l'appelant a demandé un blocage.

CRÉATION D'UNE NOUVELLE SOURCE D'ÉVÉNEMENTS

Une source d'événements se compose de trois procédures invoquées par le notificateur, plus des procédures C supplémentaires qui sont invoquées par du code de plus haut niveau pour organiser des rappels pilotés par les événements. Les trois procédures appelées par le notificateur comprennent les procédures de configuration et de vérification décrites ci-dessus, plus une procédure supplémentaire qui est invoquée lorsqu'un événement est retiré de la file d'attente d'événements pour être servi.

La procédure Tcl_CreateEventSource crée une nouvelle source d'événements. Ses arguments spécifient la procédure de configuration et la procédure de vérification pour la source d'événements. SetupProc doit correspondre au prototype suivant :

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

L'argument clientData sera le même que l'argument clientData passé à Tcl_CreateEventSource ; il est généralement utilisé pour pointer vers des informations privées gérées par la source d'événements. L'argument flags sera le même que l'argument flags passé à Tcl_DoOneEvent, sauf qu'il ne sera jamais 0 (Tcl_DoOneEvent remplace 0 par TCL_ALL_EVENTS). Flags indique quels types d'événements doivent être pris en compte ; si le bit correspondant à cette source d'événements n'est pas défini, la source d'événements doit retourner immédiatement sans rien faire. Par exemple, la source d'événements de fichier vérifie le bit TCL_FILE_EVENTS.

Le rôle de SetupProc est de s'assurer que l'application se réveille lorsque des événements du type souhaité se produisent. Ceci est généralement fait d'une manière dépendante de la plateforme. Par exemple, sous Unix, une source d'événements peut appeler Tcl_CreateFileHandler ; sous Windows, elle peut demander une notification via un événement Windows. Pour les sources d'événements pilotées par le temps, comme les événements de minuterie ou tout événement interrogé, la source d'événements peut appeler Tcl_SetMaxBlockTime pour forcer l'application à se réveiller après un temps spécifié, même si aucun événement ne s'est produit. Si aucune source d'événements n'appelle Tcl_SetMaxBlockTime, alors Tcl_WaitForEvent attendra aussi longtemps que nécessaire pour qu'un événement se produise ; sinon, il n'attendra que la durée de l'intervalle le plus court passé à Tcl_SetMaxBlockTime par l'une des sources d'événements. Si une source d'événements sait qu'elle a déjà des événements prêts à signaler, elle peut demander un temps de blocage nul. Par exemple, la procédure de configuration de la source d'événements X vérifie s'il y a déjà des événements dans la file d'attente. S'il y en a, elle appelle Tcl_SetMaxBlockTime avec un temps de blocage de 0 afin que Tcl_WaitForEvent ne bloque pas s'il n'y a pas de nouvelles données sur la connexion X. L'argument timePtr de Tcl_WaitForEvent pointe vers une structure qui décrit un intervalle de temps en secondes et en microsecondes :

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

Le champ usec doit être inférieur à 1000000.

Les informations fournies à Tcl_SetMaxBlockTime sont uniquement utilisées pour le prochain appel à Tcl_WaitForEvent ; elles sontDiscardées après le retour de Tcl_WaitForEvent. La prochaine fois qu'une attente d'événement sera effectuée, les procédures de configuration de chacune des sources d'événements seront à nouveau appelées, et elles pourront spécifier de nouvelles informations pour cette attente d'événement.

Si l'application utilise une boucle d'événements externe au lieu de Tcl_DoOneEvent, les sources d'événements peuvent avoir besoin d'appeler Tcl_SetMaxBlockTime à d'autres moments. Par exemple, si un nouveau gestionnaire d'événements est enregistré qui doit interroger les événements, la source d'événements peut appeler Tcl_SetMaxBlockTime pour définir le temps de blocage à zéro afin de forcer la boucle d'événements externe à appeler Tcl. Dans ce cas, Tcl_SetMaxBlockTime invoque Tcl_SetTimer avec l'intervalle le plus court vu depuis le dernier appel à Tcl_DoOneEvent ou Tcl_ServiceAll.

En plus de la procédure générique Tcl_SetMaxBlockTime, d'autres procédures spécifiques à la plateforme peuvent également être disponibles pour setupProc, s'il existe des informations supplémentaires nécessaires à Tcl_WaitForEvent sur cette plateforme. Par exemple, sur les systèmes Unix, l'interface Tcl_CreateFileHandler peut être utilisée pour attendre des événements de fichier.

La deuxième procédure fournie par chaque source d'événements est sa procédure de vérification, indiquée par l'argument checkProc de Tcl_CreateEventSource. CheckProc doit correspondre au prototype suivant :

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Les arguments de cette procédure sont les mêmes que ceux de setupProc. CheckProc est invoqué par Tcl_DoOneEvent après qu'il ait attendu des événements. Vraisemblablement, au moins une source d'événements est maintenant prête à mettre un événement en file d'attente. Tcl_DoOneEvent appelle chaque source d'événements à tour de rôle, afin qu'elles aient toutes une chance de mettre en file d'attente les événements qui sont prêts. La procédure de vérification fait deux choses. Premièrement, elle doit vérifier si des événements se sont déclenchés. Différentes sources d'événements le font de différentes manières.

Si la procédure de vérification d'une source d'événements détecte un événement intéressant, elle doit ajouter l'événement à la file d'attente d'événements de Tcl. Pour ce faire, la source d'événements appelle Tcl_QueueEvent. L'argument evPtr est un pointeur vers une structure allouée dynamiquement contenant l'événement (voir ci-dessous pour plus d'informations sur les problèmes de gestion de la mémoire). Chaque source d'événements peut définir sa propre structure d'événement avec les informations pertinentes pour cette source d'événements. Cependant, le premier élément de la structure doit être une structure de type Tcl_Event, et l'adresse de cette structure est utilisée lors de la communication entre la source d'événements et le reste du notificateur. Un Tcl_Event a la définition suivante :

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La source d'événements doit remplir le champ proc de l'événement avant d'appeler Tcl_QueueEvent. Le champ nextPtr est utilisé pour lier les événements dans la file d'attente et ne doit pas être modifié par la source d'événements.

Un événement peut être ajouté à la file d'attente à l'une des trois positions, en fonction de l'argument position de Tcl_QueueEvent :

TCL_QUEUE_TAIL
Ajouter l'événement à la fin de la file d'attente, de sorte que tous les autres événements en attente soient servis en premier. C'est presque toujours le bon endroit pour les nouveaux événements.
TCL_QUEUE_HEAD
Ajouter l'événement au début de la file d'attente, de sorte qu'il soit servi avant tous les autres événements en file d'attente.
TCL_QUEUE_MARK
Ajouter l'événement au début de la file d'attente, sauf s'il y a d'autres événements au début dont la position est TCL_QUEUE_MARK ; si c'est le cas, ajouter le nouvel événement juste après tous les autres événements TCL_QUEUE_MARK. Cette valeur de position est utilisée pour insérer une séquence ordonnée d'événements au début de la file d'attente, telle qu'une série d'événements Enter et Leave synthétisés lors d'une opération de saisie ou de libération dans Tk.

Lorsqu'il est temps de traiter un événement de la file d'attente (étapes 1 et 4 ci-dessus), Tcl_ServiceEvent invoquera le proc spécifié dans la première structure Tcl_Event mise en file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

Le premier argument de proc est un pointeur vers l'événement, qui sera le même que le premier argument de l'appel Tcl_QueueEvent qui a ajouté l'événement à la file d'attente. Le second argument de proc est l'argument flags de l'appel actuel à Tcl_ServiceEvent ; il est utilisé par la source d'événements pour retourner immédiatement si ses événements ne sont pas pertinents.

Il appartient à proc de gérer l'événement, généralement en invoquant une ou plusieurs commandes Tcl ou des rappels au niveau C. Une fois que la source d'événements a fini de gérer l'événement, elle retourne 1 pour indiquer que l'événement peut être retiré de la file d'attente. Si, pour une raison quelconque, la source d'événements décide que l'événement ne peut pas être traité pour le moment, elle peut retourner 0 pour indiquer que l'événement doit être reporté pour un traitement ultérieur ; dans ce cas, Tcl_ServiceEvent passera à l'événement suivant dans la file d'attente et tentera de le servir. Il y a plusieurs raisons pour lesquelles une source d'événements pourrait reporter un événement. Une possibilité est que les événements de ce type soient exclus par l'argument flags. Par exemple, la source d'événements de fichier retournera toujours 0 si le bit TCL_FILE_EVENTS n'est pas défini dans flags. Un autre exemple de report d'événements se produit dans Tk si Tk_RestrictEvents a été invoqué pour reporter certains types d'événements de fenêtre.

Lorsque proc retourne 1, Tcl_ServiceEvent retire l'événement de la file d'attente d'événements et libère son stockage. Notez que le stockage d'un événement doit être alloué par la source d'événements (en utilisant Tcl_Alloc ou la macro Tcl ckalloc) avant d'appeler Tcl_QueueEvent, mais il sera libéré par Tcl_ServiceEvent, et non par la source d'événements.

Les applications multithread fonctionnent de manière similaire, à la différence près qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. L'appel de Tcl_QueueEvent dans une application multithread ajoute un événement à la file d'attente du thread courant. Pour ajouter un événement à la file d'attente d'un autre thread, utilisez Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent accepte comme argument un argument Tcl_ThreadId, qui identifie de manière unique un thread dans une application Tcl. Pour obtenir le Tcl_ThreadId du thread courant, utilisez la procédure Tcl_GetCurrentThread. (Un thread devrait alors passer cet identifiant à d'autres threads pour que ces threads puissent ajouter des événements à sa file d'attente.) Après avoir ajouté un événement à la file d'attente d'un autre thread, vous devez généralement appeler Tcl_ThreadAlert pour « réveiller » le notificateur de ce thread et l'alerter du nouvel événement.

Tcl_DeleteEvents peut être utilisé pour supprimer explicitement un ou plusieurs événements de la file d'attente d'événements. Tcl_DeleteEvents appelle proc pour chaque événement dans la file d'attente, supprimant ceux pour lesquels la procédure retourne 1. Les événements pour lesquels la procédure retourne 0 restent dans la file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

L'argument clientData sera le même que l'argument clientData de Tcl_DeleteEv

CRÉATION D'UN NOUVEAU NOTIFICATEUR

Le notificateur se compose de toutes les procédures décrites dans ce manuel, plus Tcl_DoOneEvent et Tcl_Sleep, qui sont disponibles sur tous les systèmes d'exploitation, et Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont spécifiques à Unix. Beaucoup de ces procédures sont génériques, dans le sens qu'elles sont identiques pour tous les notificateurs. Cependant, aucune des procédures n'est indépendante du notificateur : Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler et Tcl_ServiceModeHook. Pour prendre en charge un nouveau système d'exploitation ou intégrer Tcl à une boucle d'événements spécifique à une application, vous devez écrire de nouvelles versions de ces procédures.

Tcl_InitNotifier initialise l'état du notificateur et renvoie un pointeur vers l'état du notificateur. Tcl appelle cette procédure lorsqu'il démarre un interpréteur Tcl. De même, Tcl_FinalizeNotifier arrête le notificateur et est appelée par Tcl_Finalize lors de la finalisation d'un interpréteur Tcl.

Tcl_WaitForEvent est la procédure la plus bas niveau du notificateur ; elle est responsable de l'attente d'un événement « intéressant » ou d'un délai donné. Avant que Tcl_WaitForEvent ne soit appelée, chaque procédure de source d'événements sera invoquée. L'argument timePtr de Tcl_WaitForEvent donne le temps maximal pendant lequel il bloquera en attendant un événement, en fonction des appels à Tcl_SetMaxBlockTime effectués par les procédures de configuration et d'autres informations (comme le bit TCL_DONT_WAIT dans flags).

Idéalement, Tcl_WaitForEvent devrait simplement attendre qu'un événement se produise ; elle ne devrait en aucun cas traiter l'événement. Par la suite, les événements des sources d'événements seront traités et des Tcl_Events seront créés dans la file d'attente des événements de leurs checkProc respectives. Cependant, sur certains systèmes d'exploitation (comme Windows), cela n'est pas possible ; les événements peuvent être traités dans Tcl_WaitForEvent, y compris la mise en file d'attente des Tcl_Events et plus encore (par exemple, les rappels pour les widgets natifs peuvent être invoqués). La valeur de retour de Tcl_WaitForEvent doit être 0, 1 ou -1. Sur les systèmes d'exploitation comme Windows, où les événements sont traités dans Tcl_WaitForEvent, une valeur de retour de 1 indique qu'il pourrait y avoir d'autres événements en attente non traités. Ceci est un indicateur pour l'appelant qu'il doit rappeler Tcl_WaitForEvent pour traiter tous les événements en attente. Une valeur de retour de 0 indique qu'un nouvel appel à Tcl_WaitForEvent n'aura aucun effet : il peut s'agir d'un système d'exploitation où Tcl_WaitForEvent attend simplement sans traiter les événements, ou Tcl_WaitForEvent sait avec certitude qu'il n'y a plus d'événements à traiter (par exemple, le temps est écoulé). Enfin, une valeur de retour de -1 indique que la boucle d'événements n'est plus opérationnelle et que le programme doit s'arrêter et se terminer. Sous Windows, cela se produit lors de la réception d'un message WM_QUIT ; sous Unix, cela se produit lorsque Tcl_WaitForEvent attendrait éternellement car il n'y a pas de sources d'événements actives et que le délai d'attente est infini.

Tcl_AlertNotifier est utilisé dans les applications multithread pour permettre à n'importe quel thread de « réveiller » le notificateur afin de l'alerter de nouveaux événements dans sa file d'attente. Tcl_AlertNotifier nécessite le pointeur vers le notificateur renvoyé par Tcl_InitNotifier comme argument.

Si le notificateur doit être utilisé avec une boucle d'événements externe, il doit également prendre en charge l'interface Tcl_SetTimer. Tcl_SetTimer est appelée par Tcl_SetMaxBlockTime chaque fois que le temps de blocage maximal a été réduit. Tcl_SetTimer doit organiser la boucle d'événements externe pour qu'elle appelle Tcl_ServiceAll même si aucun événement ne s'est produit. Cette interface est nécessaire car Tcl_WaitForEvent n'est pas appelée lorsqu'il y a une boucle d'événements externe. Si le notificateur doit uniquement être appelé depuis Tcl_DoOneEvent, Tcl_SetTimer ne doit rien faire.

Tcl_ServiceModeHook est appelée par la partie indépendante du notificateur lorsque le code client appelle Tcl_SetServiceMode. Ce hook est fourni pour prendre en charge les systèmes d'exploitation qui nécessitent un traitement spécial des événements lorsque l'application est dans une boucle modale (par exemple, le notificateur Windows utilise ce hook pour créer une fenêtre de communication).

Sur les systèmes Unix, une prise en charge du notificateur est également nécessaire pour la source d'événements basée sur les fichiers. La source d'événements basée sur les fichiers se compose des procédures Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont décrites dans la page de manuel de Tcl_CreateFileHandler.

Les interfaces de Tcl_Sleep et Tcl_DoOneEvent sont décrites dans leurs pages de manuel respectives.

La manière la plus simple de créer un nouveau notificateur est d'étudier le code d'un notificateur existant, par exemple dans les fichiers unix/tclUnixNotfy.c ou win/tclWinNotify.c dans la distribution du code source de Tcl.

REMPLACER LE NOTIFICATEUR

Un notificateur écrit selon les conventions ci-dessus peut également être installé dans un processus déjà en cours d'exécution à la place du notificateur standard. Ce mécanisme est utilisé de sorte qu'un seul exécutable puisse être utilisé (avec le notificateur standard) comme programme autonome et être réutilisé (comme une extension d'un autre programme, comme un plugin de navigateur Web).

Pour ce faire, l'extension appelle Tcl_SetNotifier, en passant un pointeur vers une structure Tcl_NotifierProcs. La structure a le format suivant :

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Après l'appel à Tcl_SetNotifier, les pointeurs de la structure Tcl_NotifierProcs remplacent tout notificateur qui a été installé dans le processus.

Il est très inhabituel de remplacer un notificateur déjà en cours d'exécution. Normalement, Tcl_SetNotifier devrait être appelé avant le premier appel à Tcl_InitNotifier.

BOUCLES D'ÉVÉNEMENTS EXTERNES

Les interfaces du notificateur sont conçues de manière à ce que Tcl puisse s'intégrer dans des applications qui ont leurs propres boucles d'événements privées. Dans ce cas, l'application n'appelle pas Tcl_DoOneEvent, sauf en cas de boucles d'événements récursives, comme les appels aux commandes Tcl update ou vwait. La plupart du temps est consacrée à la boucle d'événements externe de l'application. Dans ce cas, le notificateur doit organiser la boucle d'événements externe pour rappeler Tcl lorsqu'il y a un événement dans les sources d'événements Tcl. Ces rappels doivent organiser le placement des événements appropriés dans la file d'attente des événements Tcl.

Suite au traitement des événements détectés dans la boucle d'événements externe principale, Tcl peut appeler Tcl_DoOneEvent pour démarrer une boucle d'événements récursive dans des commandes telles que vwait. Tcl_DoOneEvent appelle la boucle d'événements externe, ce qui entraîne des rappels comme décrit précédemment, qui à leur tour entraînent des appels à Tcl_ServiceAll. Cependant, dans ces cas, il est préjudiciable de traiter les événements dans Tcl_ServiceAll. Le traitement des événements là-bas est inutile car le contrôle reviendra immédiatement à la boucle d'événements externe, et donc à Tcl_DoOneEvent, qui peut traiter les événements lui-même. De plus, Tcl_DoOneEvent est destiné à ne traiter qu'un seul événement, tandis que Tcl_ServiceAll traite normalement tous les événements en attente. Pour gérer cette situation, Tcl_DoOneEvent définit un indicateur dans Tcl_ServiceAll qui lui indique de ne traiter aucun événement. Cet indicateur est appelé le mode de service ; Tcl_DoOneEvent le restaure à sa valeur précédente avant de renvoyer.

Dans certains cas, cependant, il peut être nécessaire que Tcl_ServiceAll traite les événements même s'il a été appelé depuis Tcl_DoOneEvent. Cela se produit lorsqu'une autre boucle d'événements récursive est appelée via un gestionnaire d'événements appelé par Tcl_DoOneEvent (comme celui qui fait partie d'un widget natif). Dans ce cas, Tcl_DoOneEvent peut ne pas avoir l'occasion de traiter les événements, de sorte que Tcl_ServiceAll doit tous les traiter. Toute boucle d'événements récursive qui appelle une boucle d'événements externe au lieu de Tcl_DoOneEvent doit réinitialiser le mode de service afin que tous les événements soient traités par Tcl_ServiceAll. Ceci est réalisé en appelant la procédure Tcl_SetServiceMode. Si Tcl_SetServiceMode reçoit TCL_SERVICE_NONE, les appels à Tcl_ServiceAll renverront immédiatement sans traiter d'événements. Si Tcl_SetServiceMode reçoit TCL_SERVICE_ALL, les appels à Tcl_ServiceAll se comporteront normalement. Tcl_SetServiceMode renvoie la valeur précédente du mode de service, qui doit être restaurée une fois la boucle d'événements récursive terminée. Tcl_GetServiceMode renvoie la valeur actuelle du mode de service.
