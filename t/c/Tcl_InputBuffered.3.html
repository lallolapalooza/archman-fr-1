DESCRIPTION

Le mécanisme de canal Tcl fournit un mécanisme indépendant de la plateforme et des périphériques pour effectuer des opérations d'entrée et de sortie bufferisées sur divers types de fichiers, sockets et périphériques. Le mécanisme de canal est extensible à de nouveaux types de canaux, via un pilote de canal de bas niveau pour le nouveau type ; l'interface du pilote de canal est décrite dans la page de manuel de Tcl_CreateChannel. Le mécanisme de canal fournit un schéma de bufferisation calqué sur les entrées standard Unix, et permet également des opérations non bloquantes sur les canaux.

Les procédures décrites dans ce manuel sont les API C de la couche générale de l'architecture de canal. Pour une description de l'architecture du pilote de canal et comment implémenter des pilotes de canal pour de nouveaux types de canaux, voir la page de manuel de Tcl_CreateChannel.

FILECHANNEL'>TCL_OPENFILECHANNEL

Tcl_OpenFileChannel ouvre un fichier spécifié par fileName et renvoie un handle de canal qui peut être utilisé pour effectuer des entrées et des sorties sur le fichier. Cette API est modelée sur la procédure fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, Tcl_OpenFileChannel renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_OpenFileChannel laisse un message d'erreur dans le résultat de interp après toute erreur. Depuis Tcl 8.4, l'API basée sur la valeur Tcl_FSOpenFileChannel doit être utilisée de préférence à Tcl_OpenFileChannel dans la mesure du possible.

Le nouveau canal créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez Tcl_RegisterChannel, décrit ci-dessous. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, l'acte de création du nouveau canal l'assigne également en remplacement du canal standard.

TCL_OPENCOMMANDCHANNEL

Tcl_OpenCommandChannel fournit une interface de niveau C aux fonctions des commandes exec et open. Elle crée une séquence de sous-processus spécifiés par les arguments argv et argc et renvoie un canal qui peut être utilisé pour communiquer avec ces sous-processus. L'argument flags indique quel type de communication existera avec le pipeline de commandes.

Si le drapeau TCL_STDIN est défini, l'entrée standard du premier sous-processus sera liée au canal : écrire dans le canal fournira des données au sous-processus. Si TCL_STDIN n'est pas défini, alors l'entrée standard du premier sous-processus sera la même que l'entrée standard de cette application. Si TCL_STDOUT est défini, la sortie standard du dernier sous-processus pourra être lue à partir du canal ; sinon, elle ira à la sortie standard de cette application. Si TCL_STDERR est défini, la sortie de l'erreur standard pour tous les sous-processus est renvoyée au canal et résulte en une erreur lors de la fermeture du canal ; sinon, elle va à l'erreur standard de cette application. Si TCL_ENFORCE_MODE n'est pas défini, alors argc et argv peuvent rediriger les descripteurs stdio pour outrepasser TCL_STDIN, TCL_STDOUT et TCL_STDERR ; s'il est défini, alors c'est une erreur pour argc et argv d'outrepasser les canaux stdio pour lesquels TCL_STDIN, TCL_STDOUT et TCL_STDERR ont été définis.

Si une erreur se produit lors de l'ouverture du canal, Tcl_OpenCommandChannel renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, Tcl_OpenCommandChannel laisse un message d'erreur dans le résultat de l'interpréteur. interp ne peut pas être NULL.

Le nouveau canal créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez Tcl_RegisterChannel, décrit ci-dessous. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, l'acte de création du nouveau canal l'assigne également en remplacement du canal standard.

TCL_MAKEFILECHANNEL

Tcl_MakeFileChannel crée un Tcl_Channel à partir d'un handle de fichier existant et spécifique à la plateforme. Le nouveau canal créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez Tcl_RegisterChannel, décrit ci-dessous. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, l'acte de création du nouveau canal l'assigne également en remplacement du canal standard.

TCL_GETCHANNEL

Tcl_GetChannel renvoie un canal étant donné le channelName utilisé pour le créer avec Tcl_CreateChannel et un pointeur vers un interpréteur Tcl dans interp. Si un canal de ce nom n'est pas enregistré dans cet interpréteur, la procédure renvoie NULL. Si l'argument modePtr n'est pas NULL, il pointe vers une variable entière qui recevra une combinaison OR de TCL_READABLE et TCL_WRITABLE décrivant si le canal est ouvert en lecture et en écriture.

Tcl_GetChannelNames et Tcl_GetChannelNamesEx écrivent les noms des canaux enregistrés dans le résultat de l'interpréteur sous forme de liste. Tcl_GetChannelNamesEx filtrera ces noms en fonction du pattern. Si pattern est NULL, alors aucun filtrage ne sera effectué. La valeur de retour est TCL_OK si aucune erreur ne s'est produite lors de l'écriture dans le résultat, sinon c'est TCL_ERROR, et le message d'erreur est laissé dans le résultat de l'interpréteur.

TCL_REGISTERCHANNEL

Tcl_RegisterChannel ajoute un canal à l'ensemble des canaux accessibles dans interp. Après cet appel, les programmes Tcl exécutant dans cet interpréteur peuvent faire référence au canal dans les opérations d'entrée ou de sortie en utilisant le nom donné dans l'appel à Tcl_CreateChannel. Après cet appel, le canal devient la propriété de l'interpréteur, et l'appelant ne doit pas appeler Tcl_Close pour le canal ; le canal sera fermé automatiquement lorsqu'il sera désenregistré de l'interpréteur.

Le code exécuté en dehors de tout interpréteur Tcl peut appeler Tcl_RegisterChannel avec interp comme NULL, pour indiquer qu'il souhaite détenir une référence à ce canal. Par la suite, le canal peut être enregistré dans un interpréteur Tcl et il ne sera fermé que lorsque le nombre correspondant d'appels à Tcl_UnregisterChannel aura été effectué. Cela permet au code exécuté en dehors de tout interpréteur de détenir en toute sécurité une référence à un canal qui est également enregistré dans un interpréteur Tcl.

Cette procédure interagit avec le code gérant les canaux standard. Si aucun canal standard n'a été initialisé avant le premier appel à Tcl_RegisterChannel, ils seront initialisés par cet appel. Voir Tcl_StandardChannels pour un traité général sur les canaux standard et le comportement de la bibliothèque Tcl à leur égard.

TCL_UNREGISTERCHANNEL

Tcl_UnregisterChannel retire un canal de l'ensemble des canaux accessibles dans interp. Après cet appel, les programmes Tcl ne pourront plus utiliser le nom du canal pour faire référence au canal dans cet interpréteur. Si cette opération a supprimé la dernière inscription du canal dans un interpréteur, le canal est également fermé et détruit.

Le code non associé à un interpréteur Tcl peut appeler Tcl_UnregisterChannel avec interp comme NULL, pour indiquer à Tcl qu'il ne détient plus de référence à ce canal. S'il s'agit de la dernière référence au canal, il sera alors fermé. Tcl_UnregisterChannel est très similaire à Tcl_DetachChannel, sauf qu'il fermera également le canal s'il n'y a plus de références à celui-ci.

TCL_DETACHCHANNEL

Tcl_DetachChannel retire un canal de l'ensemble des canaux accessibles dans interp. Après cet appel, les programmes Tcl ne pourront plus utiliser le nom du canal pour faire référence au canal dans cet interpréteur. Au-delà de cela, cette commande n'a aucun autre effet. Elle ne peut pas être utilisée sur les canaux standard (stdout, stderr, stdin) et renverra TCL_ERROR si on lui passe l'un de ces canaux.

Le code non associé à un interpréteur Tcl peut appeler Tcl_DetachChannel avec interp comme NULL, pour indiquer à Tcl qu'il ne détient plus de référence à ce canal. S'il s'agit de la dernière référence au canal, contrairement à Tcl_UnregisterChannel, il ne sera pas fermé.

TCL_ISSTANDARDCHANNEL

Tcl_IsStandardChannel teste si un canal est l'un des trois canaux standard, stdin, stdout ou stderr. Si c'est le cas, il renvoie 1, sinon 0.

Aucune tentative n'est faite pour vérifier si le canal donné ou les canaux standard sont initialisés ou valides autrement.

TCL_CLOSE

Tcl_Close détruit le canal channel, qui doit désigner un canal actuellement ouvert. Le canal ne doit pas être enregistré dans un interpréteur lors de l'appel à Tcl_Close. Les sorties mises en tampon sont vidées vers le périphérique de sortie du canal avant la destruction du canal, et toute entrée mise en tampon est rejetée. Si c'est un canal bloquant, l'appel ne renvoie pas tant que toutes les données mises en tampon n'ont pas été envoyées avec succès au périphérique de sortie du canal. Si c'est un canal non bloquant et qu'il y a des sorties mises en tampon qui ne peuvent pas être écrites sans bloquer, l'appel renvoie immédiatement ; la sortie est vidée en arrière-plan et le canal sera fermé une fois que toutes les données mises en tampon auront été sorties. Dans ce cas, les erreurs lors du vidage ne sont pas signalées.

Si le canal a été fermé avec succès, Tcl_Close renvoie TCL_OK. Si une erreur se produit, Tcl_Close renvoie TCL_ERROR et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. Si le canal est fermé de manière synchrone et qu'une erreur se produit lors de la fermeture du canal et que interp n'est pas NULL, un message d'erreur est laissé dans le résultat de l'interpréteur.

Note : il n'est pas sûr d'appeler Tcl_Close sur un canal qui a été enregistré en utilisant Tcl_RegisterChannel ; voir la documentation de Tcl_RegisterChannel, ci-dessus, pour les détails. Si le canal a déjà été donné comme argument chan dans un appel à Tcl_RegisterChannel, vous devriez plutôt utiliser Tcl_UnregisterChannel, qui appellera en interne Tcl_Close lorsque tous les appels à Tcl_RegisterChannel auront été égalés par les appels correspondants à Tcl_UnregisterChannel.

TCL_READCHARS ET TCL_READ

Tcl_ReadChars consomme des octets du channel, convertissant les octets en UTF-8 en fonction de l'encodage du canal et stockant les données produites dans la représentation de chaîne de readObjPtr. La valeur de retour de Tcl_ReadChars est le nombre de caractères, jusqu'à charsToRead, qui ont été stockés dans readObjPtr. Si une erreur se produit lors de la lecture, la valeur de retour est -1 et Tcl_ReadChars enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno.

Définir charsT

TCL_READCHARS, TCL_READOBJ, ET TCL_READ

Le paramètre charsToRead à Tcl_ReadChars spécifie le nombre maximal de caractères à lire. Une valeur de -1 pour charsToRead amènera la commande à lire tous les caractères actuellement disponibles (mode non bloquant) ou tout jusqu'à la fin de fichier (mode bloquant).

La valeur de retour peut être inférieure à la valeur à lire, indiquant que moins de données que demandé étaient disponibles. Ceci est appelé une lecture courte. En mode bloquant, cela ne peut arriver qu'à la fin du fichier. En mode non bloquant, une lecture courte peut aussi se produire s'il n'y a pas assez d'entrée actuellement disponible : Tcl_ReadChars renvoie un compte court plutôt que d'attendre plus de données.

Si le canal est en mode bloquant, une valeur de retour de zéro indique une condition de fin de fichier. Si le canal est en mode non bloquant, une valeur de retour de zéro indique soit qu'aucune entrée n'est actuellement disponible, soit une condition de fin de fichier. Utilisez Tcl_Eof et Tcl_InputBlocked pour savoir laquelle de ces conditions s'est réellement produite.

Tcl_ReadChars traduit les diverses représentations de fin de ligne en la représentation interne canonique \n conformément au mode de reconnaissance de fin de ligne actuel. La reconnaissance de fin de ligne et les divers modes spécifiques à la plateforme sont décrits dans l'entrée de manuel de la commande Tcl fconfigure.

Par optimisation des performances, lors de la lecture à partir d'un canal avec le codage binary, les octets ne sont pas convertis en UTF-8 lorsqu'ils sont lus. Au lieu de cela, ils sont stockés dans la représentation interne de readObjPtr sous forme de valeur de tableau d'octets. La représentation chaîne de cette valeur ne sera construite que si elle est nécessaire (par exemple, en raison d'un appel à Tcl_GetStringFromObj). De cette manière, des données orientées octets peuvent être lues à partir d'un canal, manipulées en appelant Tcl_GetByteArrayFromObj et les fonctions associées, puis écrites dans un canal sans la dépense de conversion vers ou depuis UTF-8.

Tcl_Read est similaire à Tcl_ReadChars, sauf qu'elle n'effectue pas de conversions d'encodage, indépendamment de l'encodage du canal. Elle est obsolète et existe pour la compatibilité ascendante avec les extensions Tcl non internationalisées. Elle consomme des octets du channel et les stocke dans readBuf, en effectuant des traductions de fin de ligne en cours de route. La valeur de retour de Tcl_Read est le nombre d'octets, jusqu'à bytesToRead, écrits dans readBuf. Le tampon produit par Tcl_Read n'est pas terminé par un caractère nul. Son contenu est valide à partir de la position zéro jusqu'à, mais sans inclure, la position indiquée par la valeur de retour.

Tcl_ReadRaw est identique à Tcl_Read mais ne compense pas l'empilement. Alors que Tcl_Read (et les autres fonctions de l'API) obtiennent toujours leurs données du canal le plus haut dans la pile dont le canal fourni fait partie, Tcl_ReadRaw ne le fait pas. Ainsi, cette fonction est uniquement utilisable pour les pilotes de canaux transformationnels, c'est-à-dire les pilotes utilisés au milieu d'une pile de canaux, pour déplacer les données du canal inférieur dans la transformation.

TCL_GETSOBJ ET TCL_GETS

Tcl_GetsObj consomme des octets du channel, convertissant les octets en UTF-8 en fonction de l'encodage du canal, jusqu'à ce qu'une ligne complète d'entrée ait été vue. Si l'encodage du canal est binary, chaque octet lu du canal est traité comme un caractère Unicode individuel. Tous les caractères de la ligne, à l'exception des caractères de fin de ligne terminaux, sont ajoutés à la représentation chaîne de lineObjPtr. Les caractères de fin de ligne sont lus et ignorés.

Si une ligne a été lue avec succès, la valeur de retour est supérieure ou égale à zéro et indique le nombre d'octets stockés dans lineObjPtr. En cas d'erreur, Tcl_GetsObj renvoie -1 et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. Tcl_GetsObj renvoie également -1 si la fin du fichier est atteinte ; la procédure Tcl_Eof peut être utilisée pour distinguer une erreur d'une condition de fin de fichier.

Si le canal est en mode non bloquant, la valeur de retour peut également être -1 si aucune donnée n'était disponible ou si les données disponibles ne contiennent pas de caractère de fin de ligne. Lorsque -1 est retourné, la procédure Tcl_InputBlocked peut être appelée pour déterminer si le canal est bloqué en raison de l'indisponibilité des entrées.

Tcl_Gets est identique à Tcl_GetsObj sauf que les caractères résultants sont ajoutés à la chaîne dynamique fournie par lineRead plutôt qu'à une valeur Tcl.

TCL_UNGETS

Tcl_Ungets est utilisé pour ajouter des données à la file d'attente d'entrée d'un canal, soit à la tête, soit à la queue de la file. Le pointeur input pointe vers les données à ajouter. La longueur des données à ajouter est donnée par inputLen. Une valeur non nulle de addAtEnd indique que les données doivent être ajoutées à la fin de la file ; sinon, elles seront ajoutées au début de la file. Si channel a un EOF "collant" défini, aucune donnée ne sera ajoutée à la file d'attente d'entrée. Tcl_Ungets renvoie inputLen ou -1 en cas d'erreur.

TCL_WRITECHARS, TCL_WRITEOBJ, ET TCL_WRITE

Tcl_WriteChars accepte bytesToWrite octets de données caractères à charBuf. Les caractères UTF-8 dans le tampon sont convertis selon l'encodage du canal et mis en file d'attente pour la sortie vers channel. Si bytesToWrite est négatif, Tcl_WriteChars attend que charBuf soit terminé par un caractère nul et affiche tout jusqu'au caractère nul.

Les données mises en file d'attente pour la sortie peuvent ne pas apparaître sur le périphérique de sortie immédiatement, en raison de la mise en tampon interne. Si les données doivent apparaître immédiatement, appelez Tcl_Flush après l'appel à Tcl_WriteChars, ou définissez l'option -buffering sur le canal à none. Si vous souhaitez que les données apparaissent dès qu'une ligne complète est acceptée pour la sortie, définissez l'option -buffering sur le canal en mode line.

La valeur de retour de Tcl_WriteChars est un compte du nombre d'octets qui ont été acceptés pour la sortie vers le canal. Il s'agit soit d'un nombre supérieur à zéro pour indiquer le succès, soit de -1 pour indiquer qu'une erreur s'est produite. En cas d'erreur, Tcl_WriteChars enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno.

Les caractères de nouvelle ligne dans les données de sortie sont traduits en séquences de fin de ligne spécifiques à la plateforme conformément à l'option -translation du canal. Ceci est fait même si le canal n'a pas d'encodage.

Tcl_WriteObj est similaire à Tcl_WriteChars sauf qu'il accepte une valeur Tcl dont le contenu sera sorti sur le canal. Les caractères UTF-8 dans la représentation chaîne de writeObjPtr sont convertis selon l'encodage du canal et mis en file d'attente pour la sortie vers channel. Par optimisation des performances, lors de l'écriture sur un canal avec l'encodage binary, les caractères UTF-8 ne sont pas convertis lorsqu'ils sont écrits. Au lieu de cela, les octets dans la représentation interne de writeObjPtr sous forme de valeur de tableau d'octets sont écrits dans le canal. La représentation de tableau d'octets de la valeur sera construite si elle est nécessaire. De cette manière, des données orientées octets peuvent être lues à partir d'un canal, manipulées en appelant Tcl_GetByteArrayFromObj et les fonctions associées, puis écrites dans un canal sans la dépense de conversion vers ou depuis UTF-8.

Tcl_Write est similaire à Tcl_WriteChars sauf qu'elle n'effectue pas de conversions d'encodage, indépendamment de l'encodage du canal. Elle est obsolète et existe pour la compatibilité ascendante avec les extensions Tcl non internationalisées. Elle accepte bytesToWrite octets de données à byteBuf et les met en file d'attente pour la sortie vers channel. Si bytesToWrite est négatif, Tcl_Write attend que byteBuf soit terminé par un caractère nul et affiche tout jusqu'au caractère nul.

Tcl_WriteRaw est identique à Tcl_Write mais ne compense pas l'empilement. Alors que Tcl_Write (et les autres fonctions de l'API) alimentent toujours leur entrée dans le canal le plus haut de la pile dont le canal fourni fait partie, Tcl_WriteRaw ne le fait pas. Ainsi, cette fonction est uniquement utilisable pour les pilotes de canaux transformationnels, c'est-à-dire les pilotes utilisés au milieu d'une pile de canaux, pour déplacer les données de la transformation vers le canal inférieur.

TCL_FLUSH

Tcl_Flush provoque l'écriture de toutes les données de sortie tamponnées pour channel dans son fichier ou périphérique sous-jacent dès que possible. Si le canal est en mode bloquant, l'appel ne retourne pas tant que toutes les données tamponnées n'ont pas été envoyées au canal ou qu'une erreur ne s'est pas produite. L'appel retourne immédiatement si le canal est non bloquant ; il démarre une vidange en arrière-plan qui écrira les données tamponnées dans le canal éventuellement, aussi rapidement que le canal est capable de les absorber.

La valeur de retour est normalement TCL_OK. En cas d'erreur, Tcl_Flush renvoie TCL_ERROR et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno.

TCL_SEEK

Tcl_Seek déplace le point d'accès dans channel où les données ultérieures seront lues ou écrites. La sortie tamponnée est vidée vers le canal et l'entrée tamponnée estDiscardée, avant l'opération de recherche.

Tcl_Seek renvoie normalement le nouveau point d'accès. En cas d'erreur, Tcl_Seek renvoie -1 et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. Après une erreur, le point d'accès peut avoir été déplacé ou non.

TCL_TELL

Tcl_Tell renvoie le point d'accès actuel pour un canal. La valeur renvoyée est -1 si le canal ne prend pas en charge la recherche.

TCL_TRUNCATECHANNEL

Tcl_TruncateChannel tronque le fichier sous-jacent de channel à une longueur donnée de length octets. Il renvoie TCL_OK si l'opération a réussi, et TCL_ERROR sinon.

TCL_GETCHANNELOPTION

Tcl_GetChannelOption récupère, dans optionValue, la valeur d'une des options actuellement en vigueur pour un canal, ou une liste de toutes les options et leurs valeurs. L'argument channel identifie le canal pour lequel interroger une option ou récupérer toutes les options et leurs valeurs. Si optionName n'est pas NULL, c'est le nom de l'option à interroger ; la valeur de l'option est copiée dans la chaîne dynamique Tcl désignée par optionValue. Si optionName est NULL, la fonction stocke une liste alternée de noms d'options et leurs valeurs dans optionValue.

TCL_GETCHANNELOPTION

Tcl_GetChannelOption retrieves the value of optionName for channel. The value is placed in the interpreter's result using a series of calls to Tcl_DStringAppendElement. The various preexisting options and their possible values are described in the manual entry for the Tcl fconfigure command. Other options can be added by each channel type. These channel type specific options are described in the manual entry for the Tcl command that creates a channel of that type; for example, the additional options for TCP-based channels are described in the manual entry for the Tcl socket command. The procedure normally returns TCL_OK. If an error occurs, it returns TCL_ERROR and calls Tcl_SetErrno to store an appropriate POSIX error code.

TCL_SETCHANNELOPTION

Tcl_SetChannelOption sets a new value newValue for an option optionName on channel. The procedure normally returns TCL_OK. If an error occurs, it returns TCL_ERROR; in addition, if interp is non-NULL, Tcl_SetChannelOption leaves an error message in the interpreter's result.

TCL_EOF

Tcl_Eof returns a nonzero value if channel encountered an end of file during the last input operation.

TCL_INPUTBLOCKED

Tcl_InputBlocked returns a nonzero value if channel is in nonblocking mode and the last input operation returned less data than requested because there was insufficient data available. The call always returns zero if the channel is in blocking mode.

TCL_INPUTBUFFERED

Tcl_InputBuffered returns the number of bytes of input currently buffered in the internal buffers for a channel. If the channel is not open for reading, this function always returns zero.

TCL_OUTPUTBUFFERED

Tcl_OutputBuffered returns the number of bytes of output currently buffered in the internal buffers for a channel. If the channel is not open for writing, this function always returns zero.

PLATFORM ISSUES

The handles returned from Tcl_GetChannelHandle depend on the platform and the channel type. On Unix platforms, the handle is always a Unix file descriptor as returned from the open system call. On Windows platforms, the handle is a file HANDLE when the channel was created with Tcl_OpenFileChannel, Tcl_OpenCommandChannel, or Tcl_MakeFileChannel. Other channel types may return a different type of handle on Windows platforms.
