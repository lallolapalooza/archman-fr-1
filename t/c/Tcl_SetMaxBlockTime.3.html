INTRODUCTION

Les interfaces décrites ici sont utilisées pour personnaliser la boucle d'événements de Tcl. Les deux personnalisations les plus courantes sont l'ajout de nouvelles sources d'événements et la jonction de la boucle d'événements de Tcl avec une autre boucle d'événements, par exemple, celle fournie par une application dans laquelle Tcl est intégrée. Chacune de ces tâches est décrite dans une section distincte.

Les procédures mentionnées dans cette page de manuel sont les éléments de base à partir desquels le notificateur Tcl est construit. Le notificateur d'événements est la couche la plus basse du mécanisme d'événements Tcl. Il est composé de trois éléments :

[1]
Sources d'événements : représentent les moyens par lesquels les événements peuvent être générés. Par exemple, il existe une source d'événements qui implémente la procédure Tcl_CreateTimerHandler et la commande after, et il existe une source d'événements qui implémente la procédure Tcl_CreateFileHandler sur les systèmes Unix. Une source d'événements doit fonctionner avec le notificateur pour détecter les événements aux bons moments, les enregistrer dans la file d'attente des événements et enfin notifier le logiciel de niveau supérieur qu'ils se sont produits. Les procédures Tcl_CreateEventSource, Tcl_DeleteEventSource et Tcl_SetMaxBlockTime, Tcl_QueueEvent et Tcl_DeleteEvents sont principalement utilisées par les sources d'événements.
[2]
La file d'attente d'événements : pour les applications non multithreadées, il existe une seule file d'attente pour l'application qui contient les événements détectés mais pas encore traités. Les sources d'événements placent les événements dans la file d'attente afin qu'ils puissent être traités au bon moment pendant la boucle d'événements. La file d'attente d'événements garantit une discipline équitable dans le traitement des événements, de sorte qu'aucune source d'événements ne puisse devancer les autres. Elle permet également de mettre en mémoire tampon les événements pour qu'ils soient traités à un moment ultérieur. Les applications multithreadées fonctionnent de manière similaire, sauf qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. Tcl_QueueEvent est utilisée (principalement par les sources d'événements) pour ajouter des événements à la file d'attente d'événements et Tcl_DeleteEvents est utilisée pour supprimer des événements de la file d'attente sans les traiter. Dans une application multithreadée, Tcl_QueueEvent ajoute un événement à la file d'attente du thread actuel, et Tcl_ThreadQueueEvent ajoute un événement à une file d'attente spécifique d'un thread.
[3]
La boucle d'événements : pour détecter et traiter les événements, l'application entre dans une boucle qui attend les événements, les place dans la file d'attente et les traite. La plupart des applications le font en appelant la procédure Tcl_DoOneEvent, qui est décrite dans un manuel séparé.

La plupart des applications Tcl n'ont pas à se soucier des détails internes du notificateur Tcl. Cependant, le notificateur est maintenant suffisamment flexible pour être reconfiguré pour une nouvelle plateforme ou pour utiliser une boucle d'événements externe (comme la boucle d'événements Motif lorsque Tcl est intégrée dans une application Motif). Les procédures Tcl_WaitForEvent et Tcl_SetTimer sont normalement implémentées par Tcl, mais peuvent être remplacées par de nouvelles versions pour reconfigurer le notificateur (les procédures Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler et Tcl_DeleteFileHandler doivent également être remplacées ; voir CRÉATION D'UN NOUVEAU NOTIFICATEUR pour plus de détails). Les procédures Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode et Tcl_SetServiceMode sont fournies pour aider à connecter la boucle d'événements Tcl à une boucle d'événements externe comme celle de Motif.

BASES DU NOTIFICATEUR

La façon la plus simple de comprendre le fonctionnement du notificateur est de considérer ce qui se passe lorsque Tcl_DoOneEvent est appelée. Tcl_DoOneEvent reçoit un argument flags qui indique quels types d'événements peuvent être traités et s'il faut bloquer s'il n'y a pas d'événements prêts. Tcl_DoOneEvent fait ce qui suit :

[1]
Elle vérifie la file d'attente des événements pour voir s'il y a des événements qui peuvent être traités. Si c'est le cas, elle traite le premier événement possible, le retire de la file d'attente et retourne. Elle le fait en appelant Tcl_ServiceEvent et en lui passant l'argument flags.
[2]
Elle se prépare à bloquer pour un événement. Pour ce faire, Tcl_DoOneEvent appelle une procédure setup sur chaque source d'événements. La source d'événements effectuera l'initialisation spécifique à la source d'événements et, éventuellement, appellera Tcl_SetMaxBlockTime pour limiter le temps pendant lequel Tcl_WaitForEvent sera bloquée s'il n'y a pas de nouveaux événements.
[3]
Elle appelle Tcl_WaitForEvent. Cette procédure est implémentée différemment selon les plateformes ; elle attend un événement, sur la base des informations fournies par les sources d'événements. Elle peut provoquer le blocage de l'application si timePtr spécifie une durée autre que 0. Tcl_WaitForEvent retourne lorsqu'un événement s'est produit, comme un fichier devenant lisible ou lorsque la durée spécifiée par timePtr a expiré. S'il n'y a pas d'événements pour lesquels Tcl_WaitForEvent puisse attendre, c'est-à-dire qu'elle serait bloquée indéfiniment, elle retourne immédiatement et Tcl_DoOneEvent retourne 0.
[4]
Elle appelle une procédure check sur chaque source d'événements. La procédure check détermine s'il y a des événements qui intéressent cette source. Si c'est le cas, les événements sont ajoutés à la file d'attente des événements.
[5]
Elle vérifie l'exécution de Tcl_ServiceEvent pour s'assurer que les événements d'intérêt se sont produits. S'il y a des événements, ils sont ajoutés à la file d'attente des événements.

CRÉATION D'UNE NOUVELLE SOURCE D'ÉVÉNEMENTS

Une source d'événements se compose de trois procédures invoquées par le notificateur, plus des procédures C supplémentaires qui sont invoquées par le code de plus haut niveau pour organiser des rappels pilotés par les événements. Les trois procédures appelées par le notificateur consistent en les procédures de configuration et de vérification décrites ci-dessus, plus une procédure supplémentaire qui est invoquée lorsqu'un événement est retiré de la file d'attente d'événements pour être traité.

La procédure Tcl_CreateEventSource crée une nouvelle source d'événements. Ses arguments spécifient la procédure de configuration et la procédure de vérification pour la source d'événements. SetupProc doit correspondre au prototype suivant :

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

L'argument clientData sera le même que l'argument clientData de Tcl_CreateEventSource ; il est généralement utilisé pour pointer vers des informations privées gérées par la source d'événements. L'argument flags sera le même que l'argument flags passé à Tcl_DoOneEvent sauf qu'il ne sera jamais 0 (Tcl_DoOneEvent remplace 0 par TCL_ALL_EVENTS). Flags indique quels types d'événements doivent être considérés ; si le bit correspondant à cette source d'événements n'est pas défini, la source d'événements doit retourner immédiatement sans rien faire. Par exemple, la source d'événements de fichier vérifie le bit TCL_FILE_EVENTS.

Le rôle de SetupProc est de s'assurer que l'application se réveille lorsque des événements du type désiré se produisent. Ceci est généralement fait d'une manière dépendante de la plateforme. Par exemple, sous Unix, une source d'événements peut appeler Tcl_CreateFileHandler ; sous Windows, elle peut demander une notification avec un événement Windows. Pour les sources d'événements pilotées par le temps, telles que les événements de temporisation ou tout événement interrogé, la source d'événements peut appeler Tcl_SetMaxBlockTime pour forcer l'application à se réveiller après un temps spécifié, même si aucun événement ne s'est produit. Si aucune source d'événements n'appelle Tcl_SetMaxBlockTime, alors Tcl_WaitForEvent attendra autant que nécessaire qu'un événement se produise ; sinon, elle n'attendra que le temps le plus court passé à Tcl_SetMaxBlockTime par l'une des sources d'événements. Si une source d'événements sait qu'elle a déjà des événements prêts à être signalés, elle peut demander un temps de blocage nul. Par exemple, la procédure de configuration de la source d'événements X vérifie s'il y a déjà des événements dans la file d'attente. S'il y en a, elle appelle Tcl_SetMaxBlockTime avec un temps de blocage de 0 afin que Tcl_WaitForEvent ne bloque pas s'il n'y a pas de nouvelles données sur la connexion X. L'argument timePtr de Tcl_WaitForEvent pointe vers une structure qui décrit un intervalle de temps en secondes et en microsecondes :

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

Le champ usec doit être inférieur à 1000000.

Les informations fournies à Tcl_SetMaxBlockTime ne sont utilisées que pour le prochain appel à Tcl_WaitForEvent ; elles sont ignorées après le retour de Tcl_WaitForEvent. La prochaine fois qu'une attente d'événement sera effectuée, les procédures de configuration de chacune des sources d'événements seront à nouveau appelées, et elles pourront spécifier de nouvelles informations pour cette attente d'événement.

Si l'application utilise une boucle d'événements externe plutôt que Tcl_DoOneEvent, les sources d'événements peuvent avoir besoin d'appeler Tcl_SetMaxBlockTime à d'autres moments. Par exemple, si un nouveau gestionnaire d'événements est enregistré qui a besoin d'interroger les événements, la source d'événements peut appeler Tcl_SetMaxBlockTime pour définir le temps de blocage à zéro afin de forcer la boucle d'événements externe à appeler Tcl. Dans ce cas, Tcl_SetMaxBlockTime invoque Tcl_SetTimer avec l'intervalle le plus court vu depuis le dernier appel à Tcl_DoOneEvent ou Tcl_ServiceAll.

En plus de la procédure générique Tcl_SetMaxBlockTime, d'autres procédures spécifiques à la plateforme peuvent également être disponibles pour setupProc, s'il y a des informations supplémentaires nécessaires à Tcl_WaitForEvent sur cette plateforme. Par exemple, sur les systèmes Unix, l'interface Tcl_CreateFileHandler peut être utilisée pour attendre les événements de fichier.

La deuxième procédure fournie par chaque source d'événements est sa procédure de vérification, indiquée par l'argument checkProc de Tcl_CreateEventSource. CheckProc doit correspondre au prototype suivant :

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Les arguments de cette procédure sont les mêmes que ceux de setupProc. CheckProc est invoqué par Tcl_DoOneEvent après qu'il a attendu les événements. Vraisemblablement, au moins une source d'événements est maintenant prête à mettre un événement en file d'attente. Tcl_DoOneEvent appelle chaque source d'événements tour à tour, afin qu'elles aient toutes une chance de mettre en file d'attente tous les événements qui sont prêts. La procédure de vérification fait deux choses. Premièrement, elle doit vérifier si des événements se sont déclenchés. Différentes sources d'événements le font de différentes manières.

Si la procédure de vérification d'une source d'événements détecte un événement intéressant, elle doit ajouter l'événement à la file d'attente d'événements de Tcl. Pour ce faire, la source d'événements appelle Tcl_QueueEvent. L'argument evPtr est un pointeur vers une structure allouée dynamiquement contenant l'événement (voir ci-dessous pour plus d'informations sur les problèmes de gestion de la mémoire). Chaque source d'événements peut définir sa propre structure d'événement avec les informations pertinentes pour cette source d'événements. Cependant, le premier élément de la structure doit être une structure de type Tcl_Event, et l'adresse de cette structure est utilisée lors de la communication entre la source d'événements et le reste du notificateur. Une Tcl_Event a la définition suivante :

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La source d'événements doit remplir le champ proc de l'événement avant d'appeler Tcl_QueueEvent. Le champ nextPtr est utilisé pour relier les événements dans la file d'attente et ne doit pas être modifié par la source d'événements.

Un événement peut être ajouté à la file d'attente à l'une des trois positions, en fonction de l'argument position de Tcl_QueueEvent :

TCL_QUEUE_TAIL
Ajouter l'événement à la fin de la file d'attente, de sorte que tous les autres événements en attente soient traités en premier. C'est presque toujours le bon endroit pour les nouveaux événements.
TCL_QUEUE_HEAD
Ajouter l'événement au début de la file d'attente, de sorte qu'il soit traité avant tous les autres événements mis en file d'attente.
TCL_QUEUE_MARK
Ajouter l'événement au début de la file d'attente, à moins qu'il n'y ait d'autres événements au début dont la position est TCL_QUEUE_MARK ; dans ce cas, ajouter le nouvel événement juste après tous les autres événements TCL_QUEUE_MARK. Cette valeur de position est utilisée pour insérer une séquence ordonnée d'événements au début de la file d'attente, telle qu'une série d'événements Enter et Leave synthétisés lors d'une opération de saisie ou de libération dans Tk.

Lorsqu'il est temps de gérer un événement de la file d'attente (étapes 1 et 4 ci-dessus), Tcl_ServiceEvent invoquera le proc spécifié dans la première structure Tcl_Event mise en file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

Le premier argument de proc est un pointeur vers l'événement, qui sera le même que le premier argument de l'appel Tcl_QueueEvent qui a ajouté l'événement à la file d'attente. Le deuxième argument de proc est l'argument flags de l'appel actuel à Tcl_ServiceEvent ; il est utilisé par la source d'événements pour retourner immédiatement si ses événements ne sont pas pertinents.

Il appartient à proc de gérer l'événement, généralement en invoquant une ou plusieurs commandes Tcl ou des rappels au niveau C. Une fois que la source d'événements a fini de traiter l'événement, elle retourne 1 pour indiquer que l'événement peut être retiré de la file d'attente. Si, pour une raison quelconque, la source d'événements décide que l'événement ne peut pas être traité pour le moment, elle peut retourner 0 pour indiquer que l'événement doit être différé pour un traitement ultérieur ; dans ce cas, Tcl_ServiceEvent passera à l'événement suivant dans la file d'attente et tentera de le traiter. Il y a plusieurs raisons pour lesquelles une source d'événements pourrait différer un événement. Une possibilité est que les événements de ce type sont exclus par l'argument flags. Par exemple, la source d'événements de fichier retournera toujours 0 si le bit TCL_FILE_EVENTS n'est pas défini dans flags. Un autre exemple de report d'événements se produit dans Tk si Tk_RestrictEvents a été invoqué pour reporter certains types d'événements de fenêtre.

Lorsque proc retourne 1, Tcl_ServiceEvent retirera l'événement de la file d'attente d'événements et libérera son stockage. Notez que le stockage d'un événement doit être alloué par la source d'événements (en utilisant Tcl_Alloc ou la macro Tcl ckalloc) avant d'appeler Tcl_QueueEvent, mais il sera libéré par Tcl_ServiceEvent, et non par la source d'événements.

Les applications multithread fonctionnent de manière similaire, sauf qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. L'appel à Tcl_QueueEvent dans une application multithread ajoute un événement à la file d'attente du thread courant. Pour ajouter un événement à la file d'attente d'un autre thread, utilisez Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent accepte comme argument un argument Tcl_ThreadId, qui identifie de manière unique un thread dans une application Tcl. Pour obtenir le Tcl_ThreadId du thread courant, utilisez la procédure Tcl_GetCurrentThread. (Un thread devrait alors passer cet identifiant à d'autres threads pour que ces threads puissent ajouter des événements à sa file d'attente.) Après avoir ajouté un événement à la file d'attente d'un autre thread, vous devez généralement appeler Tcl_ThreadAlert pour « réveiller » le notificateur de ce thread et l'alerter du nouvel événement.

Tcl_DeleteEvents peut être utilisé pour retirer explicitement un ou plusieurs événements de la file d'attente d'événements. Tcl_DeleteEvents appelle proc pour chaque événement dans la file d'attente, en supprimant ceux pour lesquels la procédure retourne 1. Les événements pour lesquels la procédure retourne 0 restent dans la file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

L'argument clientData sera le même que l'argument clientData de Tcl_DeleteE

CRÉATION D'UN NOUVEAU NOTIFICATEUR

Le notificateur comprend toutes les procédures décrites dans ce manuel, ainsi que Tcl_DoOneEvent et Tcl_Sleep, qui sont disponibles sur toutes les plateformes, et Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont spécifiques à Unix. La plupart de ces procédures sont génériques, dans le sens où elles sont identiques pour tous les notificateurs. Cependant, aucune d'entre elles n'est indépendante du notificateur : Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler et Tcl_ServiceModeHook. Pour prendre en charge un nouveau système d'exploitation ou intégrer Tcl à une boucle d'événements spécifique à une application, vous devez écrire de nouvelles versions de ces procédures.

Tcl_InitNotifier initialise l'état du notificateur et renvoie un handle vers cet état. Tcl appelle cette procédure lors de l'initialisation d'un environnement Tcl. De même, Tcl_FinalizeNotifier désactive le notificateur et est appelée par Tcl_Finalize lors de la finalisation d'un environnement Tcl.

Tcl_WaitForEvent est la procédure la plus bas niveau du notificateur ; elle est responsable de l'attente d'un événement « intéressant » ou d'un délai donné. Avant que Tcl_WaitForEvent ne soit appelée, chaque procédure de source d'événement aura été appelée. L'argument timePtr de Tcl_WaitForEvent spécifie le temps maximum pendant lequel bloquer sur un événement, basé sur les appels à Tcl_SetMaxBlockTime effectués par les procédures de configuration et d'autres informations (comme le bit TCL_DONT_WAIT dans flags).

Idéalement, Tcl_WaitForEvent ne devrait attendre qu'un événement ; elle ne devrait traiter l'événement d'aucune manière. Ensuite, les événements des sources d'événements seront traités par les notificateurs et des Tcl_Events seront créés dans la file d'attente des événements de leur checkProc. Cependant, sur certains systèmes (comme Windows), ce n'est pas possible ; les événements peuvent être traités dans Tcl_WaitForEvent, y compris la mise en file d'attente de Tcl_Events et plus encore (par exemple, les rappels pour les widgets natifs). La valeur de retour de Tcl_WaitForEvent doit être 0, 1 ou -1. Sur les plateformes comme Windows où les événements sont traités dans Tcl_WaitForEvent, une valeur de retour de 1 indique qu'il pourrait y avoir d'autres événements en attente qui n'ont pas été traités. C'est un signal pour l'appelant qu'il doit rappeler Tcl_WaitForEvent pour traiter tous les événements en attente. Une valeur de retour de 0 indique que le rappel de Tcl_WaitForEvent n'aura aucun effet : il peut s'agir d'un système où Tcl_WaitForEvent attend seulement sans traiter d'événement, ou Tcl_WaitForEvent sait avec certitude qu'il n'y a plus d'événements en attente (par exemple, le temps est écoulé). Enfin, une valeur de retour de -1 indique que la boucle d'événements n'est plus opérationnelle et que l'application doit se terminer proprement. Sous Windows, cela se produit lorsqu'un message WM_QUIT est reçu ; sous Unix, cela se produit lorsque Tcl_WaitForEvent attend indéfiniment car il n'y a pas de sources d'événements actives et que le temps est infini.

Tcl_AlertNotifier est utilisé dans les applications multithread pour permettre à n'importe quel thread de « réveiller » le notificateur afin de l'alerter de nouveaux événements dans sa file d'attente. Tcl_AlertNotifier nécessite comme argument le handle du notificateur renvoyé par Tcl_InitNotifier.

Si le notificateur doit être utilisé avec une boucle d'événements externe, il doit également prendre en charge l'interface Tcl_SetTimer. Tcl_SetTimer est appelée par Tcl_SetMaxBlockTime lorsque le temps de blocage maximal a été réduit. Tcl_SetTimer doit organiser la boucle d'événements externe pour appeler Tcl_ServiceAll même s'il n'y a pas d'événements. Cette interface est nécessaire car Tcl_WaitForEvent n'est pas appelée lorsqu'il existe une boucle d'événements externe. Si le notificateur ne sera utilisé qu'à partir de Tcl_DoOneEvent, alors Tcl_SetTimer ne doit rien faire.

Tcl_ServiceModeHook est appelée par la partie indépendante du notificateur lorsque le code client appelle Tcl_SetServiceMode. Ce hook est fourni pour prendre en charge les opérations du système d'exploitation qui nécessitent une gestion spéciale des événements lorsque l'application est dans une boucle modale (par exemple, le notificateur Windows utilise ce hook pour créer une fenêtre de communication).

Sur les systèmes Unix, le notificateur de fichiers nécessite également un support de notification. Le notificateur de fichiers comprend les procédures Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont décrites dans la page de manuel de Tcl_CreateFileHandler.

Les interfaces de Tcl_Sleep et Tcl_DoOneEvent sont décrites dans leurs pages de manuel respectives.

Le moyen le plus simple de créer un nouveau notificateur est d'étudier le code d'un notificateur existant, comme dans les fichiers unix/tclUnixNotfy.c ou win/tclWinNotify.c de la distribution du code source de Tcl.

REMPLACEMENT DU NOTIFICATEUR

Un notificateur écrit selon les conventions ci-dessus peut également être installé dans un processus en cours d'exécution pour remplacer le notificateur standard. Ce mécanisme est utilisé pour qu'un seul exécutable puisse être utilisé (avec le notificateur standard) comme un programme autonome et réutilisé (avec un notificateur remplacé dans une extension chargeable) comme une extension d'un autre programme, tel qu'un plugin de navigateur web.

Pour ce faire, l'extension appelle Tcl_SetNotifier en passant un pointeur vers une structure Tcl_NotifierProcs. La structure a la disposition suivante :

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Après l'appel à Tcl_SetNotifier, les pointeurs indiqués dans la structure Tcl_NotifierProcs remplacent ce qui avait été installé dans le processus.

Il est exceptionnellement inutile de remplacer un notificateur en cours d'exécution. Normalement, Tcl_SetNotifier doit être appelée avant le premier appel à Tcl_InitNotifier dans le processus.

BOUCLES D'ÉVÉNEMENTS EXTERNES

Les interfaces du notificateur sont conçues pour que Tcl puisse être intégré dans des applications qui ont leurs propres boucles d'événements privées. Dans ce cas, l'application n'appelle pas Tcl_DoOneEvent sauf dans le cas de boucles d'événements récursives, telles que les appels aux commandes Tcl update ou vwait. La majeure partie du temps est consacrée aux boucles d'événements externes de l'application. Dans ce cas, le notificateur doit organiser la boucle d'événements externe pour qu'elle fasse référence à Tcl lorsqu'un événement se produit dans les sources d'événements Tcl. Ces rappels doivent organiser le placement d'événements appropriés dans la file d'attente des événements de Tcl.

Par effet secondaire du traitement des événements détectés dans la boucle d'événements externe principale, Tcl peut appeler Tcl_DoOneEvent pour démarrer une boucle d'événements récursive dans des commandes comme vwait. Tcl_DoOneEvent appelle la boucle d'événements externe, ce qui entraîne des rappels comme décrit ci-dessus, ce qui entraîne des appels à Tcl_ServiceAll. Cependant, dans ces cas, le service d'événements dans Tcl_ServiceAll doit être évité. Le service d'événements là est inutile car le contrôle sera immédiatement rendu à la boucle d'événements externe et donc à Tcl_DoOneEvent, qui peut servir les événements lui-même. De plus, Tcl_DoOneEvent est destiné à ne servir qu'un seul événement, tandis que Tcl_ServiceAll sert normalement tous les événements en attente. Pour gérer cette situation, Tcl_DoOneEvent définit un drapeau pour Tcl_ServiceAll qui lui indique de ne pas servir d'événements, d'où le nom de ce drapeau : le mode de service ; Tcl_DoOneEvent le restaure à sa valeur précédente avant de retourner.

Dans certains cas, il peut être nécessaire que Tcl_ServiceAll serve des événements même si elle a été appelée par Tcl_DoOneEvent. Cela se produit lorsqu'il existe une autre boucle d'événements récursive appelée par un gestionnaire d'événements appelé par Tcl_DoOneEvent (comme celui qui fait partie d'un widget natif). Dans ce cas, Tcl_DoOneEvent peut ne pas avoir l'occasion de servir les événements, de sorte que Tcl_ServiceAll doit tous les servir. Toute boucle d'événements récursive qui appelle une boucle d'événements externe au lieu de Tcl_DoOneEvent doit réinitialiser le mode de service afin que tous les événements soient traités dans Tcl_ServiceAll. Ceci est réalisé en appelant la procédure Tcl_SetServiceMode. Si Tcl_SetServiceMode reçoit TCL_SERVICE_NONE, alors les appels à Tcl_ServiceAll retourneront immédiatement sans traiter aucun événement. Si Tcl_SetServiceMode reçoit TCL_SERVICE_ALL, alors les appels à Tcl_ServiceAll se comporteront normalement. Tcl_SetServiceMode renvoie la valeur précédente du mode de service, qui doit être restaurée lorsque la boucle d'événements récursive se termine. Tcl_GetServiceMode renvoie la valeur actuelle du mode de service.

MOTS-CLÉS

Tcl_Notifier - Documentation Tcl

Tcl_Notifier

Tcl_Notifier est une primitive du noyau Tcl qui permet aux extensions d'intégrer des sources d'événements personnalisées dans la boucle d'événements Tcl. Il fournit un mécanisme pour enregistrer et désenregistrer des sources d'événements, ainsi que pour attendre et gérer ces événements.

Les principaux composants du système de notification Tcl sont :

  • Notifier : L'objet central qui gère le système de notification. Il contient une liste de toutes les sources d'événements enregistrées et une boucle d'événements qui attend les événements.
  • Source d'événement : Un objet qui représente une source d'événements externe, telle qu'un descripteur de fichier, un timer ou un événement de maintenance. Les sources d'événements sont enregistrées auprès du Notifier, qui les surveille ensuite pour les événements.
  • File d'attente d'événements : Une file d'attente où les événements entrants sont stockés en attendant d'être traités par la boucle d'événements.
  • Gestionnaire d'événements : Une fonction de rappel qui est appelée lorsqu'un événement spécifique se produit pour une source d'événement enregistrée.

Le Notifier est implémenté en tant que singleton, ce qui signifie qu'il n'y a qu'une seule instance du Notifier dans une application Tcl. Cela garantit une gestion cohérente des événements dans toute l'application.

Les sources d'événements peuvent être de différents types, notamment :

  • Descripteurs de fichier : Événements liés à la lecture ou à l'écriture sur des descripteurs de fichier.
  • Timers : Événements qui se déclenchent après un délai spécifié.
  • Oisiveté : Événements qui se déclenchent lorsque le système est inactif pendant une période spécifiée.
  • Mode de service : Événements qui se déclenchent lorsque le système passe en mode de service.
  • Threads : Événements liés à l'activité des threads.

Les extensions Tcl peuvent utiliser l'API Tcl_Notifier pour créer et gérer leurs propres sources d'événements personnalisées, permettant une intégration transparente avec la boucle d'événements Tcl. Cela permet aux extensions de répondre aux événements externes sans avoir à gérer leur propre boucle d'événements complexe.

L'API Tcl_Notifier fournit des fonctions pour :

  • Obtenir l'instance Notifier actuelle.
  • Enregistrer et désenregistrer des sources d'événements.
  • Ajouter et supprimer des gestionnaires d'événements pour des sources d'événements spécifiques.
  • Démarrer et arrêter la boucle d'événements.
  • Traiter les événements et déclencher les gestionnaires d'événements appropriés.

En utilisant Tcl_Notifier, les développeurs peuvent améliorer les performances et la réactivité de leurs applications Tcl en gérant efficacement les événements externes et en les intégrant à la boucle d'événements Tcl principale.
