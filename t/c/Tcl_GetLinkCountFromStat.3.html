DESCRIPTION

Il y a plusieurs raisons d'appeler les fonctions API Tcl_FS (par exemple, Tcl_FSAccess et Tcl_FSStat) plutôt que d'appeler directement des fonctions de niveau système comme access et stat. Premièrement, elles fonctionnent sur plusieurs plateformes, donc une extension qui les appelle devrait fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige certains bogues dans les appels de niveau système. Troisièmement, ces appels de fonction gèrent toutes les conversions de chemin « Utf vers natif de la plateforme » qui peuvent être nécessaires (et peuvent mettre en cache les résultats de telles conversions pour une plus grande efficacité lors des appels ultérieurs). Quatrièmement, et peut-être le plus important, toutes ces fonctions sont « conscientes du système de fichiers virtuel » (VFS). Tout système de fichiers virtuel (VFS en abrégé) qui a été enregistré (via Tcl_FSRegister) peut rediriger l'accès aux fichiers vers des supports ou des méthodes d'accès alternatifs. Cela signifie que toutes ces fonctions (et par conséquent les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent opérer sur des « fichiers » qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS en abrégé) via cette API est automatiquement « consciente du système de fichiers virtuel ». Bien sûr, si une extension accède directement au système de fichiers natif (par exemple, via des API spécifiques à la plateforme), Tcl ne peut pas intercepter de tels appels.

Si des VFS appropriés ont été enregistrés, les « fichiers » peuvent, pour donner deux exemples, être distants (par exemple, situés sur un serveur ftp distant) ou archivés (par exemple, se trouvant à l'intérieur d'une archive .zip). De tels systèmes de fichiers enregistrés fournissent une table de correspondance de fonctions pour implémenter tout ou partie de la fonctionnalité listée ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat abstraient la déclaration du tampon « struct stat », permettant d'utiliser le même code sur les systèmes avec et sans prise en charge de fichiers de plus de 2 Go.

L'API Tcl_FS est basée sur Tcl_Obj et peut mettre en cache des représentations internes et d'autres chaînes liées aux chemins (par exemple, le répertoire de travail courant). Un effet secondaire est qu'il ne faut pas passer de valeurs avec un compteur de références de zéro à l'une de ces fonctions. Si de tels appels étaient gérés, ils pourraient entraîner des fuites de mémoire (dans certaines circonstances, le code du système de fichiers peut souhaiter conserver une référence à la valeur passée, et il ne faut donc pas supposer qu'après le retour de l'un de ces appels, la valeur a toujours un compteur de références de zéro - il peut avoir été incrémenté) ou un segmentation fault direct (ou une autre erreur d'accès mémoire) due à la libération de la valeur à mi-chemin de la manipulation complexe de la valeur requise pour s'assurer que le chemin est entièrement normalisé et absolu pour la détermination du système de fichiers. La leçon pratique à retenir est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect et peut causer des erreurs de mémoire. Le compteur de références de path doit être incrémenté avant de le passer, ou décrémenté. Pour cette raison, les valeurs avec un compteur de références de zéro ne sont pas considérées comme des chemins de système de fichiers valides et l'appel de toute fonction API Tcl_FS avec une telle valeur n'entraînera aucune action.

FONCTIONS API FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno à la code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno au code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction « créer un répertoire » du système de fichiers propriétaire.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction « supprimer un fichier » du système de fichiers propriétaire.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction « supprimer un répertoire » du système de fichiers propriétaire.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « renommer un fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno au code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction « lister les volumes » non-NULL et leur demande de renvoyer leur liste de volumes racine. Elle accumule les valeurs de retour dans une liste qui est renvoyée à l'appelant (avec un compteur de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant l'encodage identifié par encodingName et évalue son contenu en tant que script Tcl. Elle renvoie les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, l'encodage système est utilisé pour lire le contenu du fichier. Si le fichier n'a pas pu être lu, une erreur Tcl est renvoyée pour décrire pourquoi le fichier n'a pas pu être lu. Le caractère de fin de fichier est « \x1A » (^Z) pour toutes les plateformes. Si vous avez besoin d'un « ^Z » dans une chaîne pour une comparaison, vous pouvez utiliser « \x1A », qui sera substitué en toute sécurité par l'interpréteur Tcl en « ^Z ». Tcl_FSEvalFile est une version simplifiée de Tcl_FSEvalFileEx qui utilise toujours l'encodage système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier de code binaire en mémoire et renvoie les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas, en raison des limitations de l'OS pour le chargement dynamique de code binaire), Tcl tentera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile inverse l'opération, demandant que la bibliothèque indiquée par loadHandle soit retirée du processus. Notez que, contrairement à la commande unload, cela ne donne pas à la bibliothèque de possibilité de nettoyage.

Les deux fonctions ci-dessus renvoient un code de complétion Tcl standard. En cas d'erreur, un message d'erreur est laissé dans le résultat de l'interp.

Le jeton fourni via la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher dans un répertoire tous les fichiers qui correspondent à un modèle donné. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le globbing. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Notez que le code glob implémente les modèles récursifs en interne, de sorte que cette fonction ne recevra que des modèles simples, qui peuvent être mis en correspondance en utilisant la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment en demandant uniquement le retour des répertoires. Un cas particulier est d'être appelé avec un modèle NULL, ce qui indique que le chemin doit seulement être vérifié pour le bon type.

Tcl_FSLink remplace la version de bibliothèque de readlink, et l'étend pour prendre en charge la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr sera appelée.

Si toPtr est NULL, une action « lire le lien » est effectuée. Le résultat est un Tcl_Obj spécifiant le contenu du lien symbolique donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant, qui doit appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl doit créer un lien de l'un des types passés dans le drapeau linkAction. Ce drapeau est une combinaison OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'il existe un choix (c'est-à-dire que plus d'un drapeau est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur de retour doit être toPtr (qui appartient donc déjà à l'appelant). En cas d'échec, NULL est renvoyé.

Si l'un des canaux standard, **stdin**, **stdout** ou **stderr**, a été précédemment fermé, l'action de création du nouveau canal l'assigne également comme substitut des canaux standard. **Tcl_FSGetCwd** remplace la version de la bibliothèque de **getcwd**. Elle renvoie le répertoire de travail actuel de la bibliothèque Tcl. Cela peut être différent du répertoire de travail natif, qui est défini lorsque le répertoire de travail actuel n'est pas dans le système de fichiers natif. Le résultat est un pointeur vers un *Tcl_Obj* spécifiant le répertoire actuel, ou NULL si le répertoire ne peut pas être déterminé. Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de *interp*. Le résultat a déjà son compte de référence augmenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compte de référence doit être diminué. Ceci est nécessaire pour la sécurité des threads, afin que plusieurs threads puissent accéder à cette fonction et aux fonctions associées tout en garantissant que les résultats sont toujours valides. **Tcl_FSChdir** remplace la version de la bibliothèque de **chdir**. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl se rabattra sur une combinaison de **stat** et **access** pour vérifier si le répertoire existe et a les permissions appropriées. Pour les résultats, voir la documentation de **chdir**. En cas de succès, nous conservons une trace du chemin réussi dans *cwdPathPtr* pour les appels ultérieurs à **Tcl_FSGetCwd**. **Tcl_FSPathSeparator** renvoie le caractère séparateur à utiliser pour l'élément le plus spécifique du chemin spécifié par *pathPtr* (c'est-à-dire la dernière partie du chemin). Le séparateur est renvoyé comme un *Tcl_Obj* contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est renvoyé. **Tcl_FSJoinPath** prend le *Tcl_Obj* donné, qui doit être une liste valide (permettant d'avoir un compte de référence de zéro), et renvoie la valeur du chemin en considérant les *elements* premiers éléments comme des segments de chemin valides (chaque segment peut être un chemin complet, un chemin partiel ou juste un nom de répertoire ou de fichier). Si un segment est réellement un chemin absolu, tous les segments précédents sont ignorés. Si *elements* est inférieur à 0, nous utilisons toute la liste. Il est possible que la valeur renvoyée soit réellement un élément de la liste donnée, donc l'appelant doit être prudent en augmentant le compte de référence du résultat avant de libérer la liste. La valeur renvoyée, typiquement avec un compte de référence de zéro (mais pourrait être partagée dans certains cas), contient le chemin combiné. L'appelant doit augmenter le compte de référence avant de l'utiliser. En particulier, la valeur renvoyée pourrait être un élément de la liste donnée, donc libérer la liste pourrait libérer prématurément la valeur si aucun compte de référence n'a été pris. Si le nombre d'éléments est zéro, la valeur renvoyée sera un *Tcl_Obj* de chaîne vide. **Tcl_FSSplitPath** prend le *Tcl_Obj* donné, qui doit être un chemin valide, et renvoie une valeur de liste contenant chaque segment de ce chemin comme élément. Elle renvoie une valeur de liste avec un compte de référence de zéro. Si le *lenPtr* passé n'est pas NULL, la variable pointée est mise à jour pour contenir le nombre d'éléments dans la valeur de liste renvoyée. **Tcl_FSEqualPaths** teste si deux chemins donnés représentent le même objet de système de fichiers. Elle renvoie 1 si les chemins sont égaux, 0 s'ils sont différents. Si l'un des chemins est NULL, 0 est toujours renvoyé. **Tcl_FSGetNormalizedPath** tente d'extraire d'un *Tcl_Obj* donné une représentation normalisée unique, dont la valeur de chaîne peut être utilisée comme identifiant unique pour le fichier. Elle renvoie la représentation normalisée du chemin, appartenant à Tcl, ou NULL si le chemin était invalide ou n'a pas pu être correctement converti. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère sur ces représentations en interne), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques ne soit pas la version la plus conviviale d'un chemin. La valeur de retour appartient à Tcl et a une durée de vie équivalente à celle du *pathPtr* passé (sauf si c'est un chemin relatif, auquel cas la valeur normalisée peut être libérée à tout moment que le cwd change) - l'appelant peut augmenter le compte de référence s'il le souhaite pour conserver une copie plus longtemps. **Tcl_FSJoinToPath** prend la valeur donnée, qui est généralement un chemin valide ou NULL, et combine les segments de chemin donnés. Elle renvoie une valeur, typiquement avec un compte de référence de zéro (mais pourrait être partagée dans certains cas), contenant le chemin combiné. L'appelant doit augmenter le compte de référence avant de l'utiliser. Si une valeur passée à cette fonction (*pathPtr* ou éléments de *path*) a un compte de référence de zéro, elle sera libérée lorsque cette fonction retournera. **Tcl_FSConvertToPathType** tente de convertir le *Tcl_Obj* donné en un type de chemin valide, en tenant compte du fait que le cwd pourrait avoir changé même si cette valeur est déjà supposée être du bon type. Le nom de fichier peut commencer par ~ (pour indiquer le répertoire utilisateur actuel) ou ~ (pour indiquer le répertoire de n'importe quel utilisateur). Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), **TCL_OK** est renvoyé. Sinon, **TCL_ERROR** est renvoyé, et un message d'erreur peut être laissé dans l'interpréteur. **Tcl_FSGetInternalRep** extrait la représentation interne d'une valeur de chemin donnée dans le système de fichiers donné. Si la valeur du chemin appartient à un système de fichiers différent, nous renvoyons NULL. Si la représentation interne est actuellement NULL, nous essayons de la générer en appelant le **Tcl_FSCreateInternalRepProc** du système de fichiers. Elle renvoie NULL ou une représentation valide du chemin interne. Cette représentation interne est mise en cache, de sorte que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. **Tcl_FSGetTranslatedPath** tente d'extraire le chemin traduit à partir du *Tcl_Obj* donné. Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), la valeur est renvoyée. Sinon, NULL est renvoyé, et un message d'erreur peut être laissé dans l'interpréteur. Un chemin traduit est celui qui ne contient aucun ~ ou ~utilisateur (ceux-ci ont été développés dans leur représentation actuelle dans le système de fichiers). La valeur renvoyée appartient à l'appelant, qui doit la stocker ou appeler **Tcl_DecrRefCount** pour garantir la libération de la mémoire. Cette fonction a une utilité pratique limitée, et **Tcl_FSGetNormalizedPath** ou **Tcl_FSGetNativePath** sont généralement des fonctions plus appropriées à ces fins. **Tcl_FSGetTranslatedStringPath** fait la même chose que **Tcl_FSGetTranslatedPath**, mais renvoie une chaîne ou NULL. API DES SYSTÈMES DE FICHIERS VIRTUELS

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un système de fichiers ; ces opérations sont invoquées au besoin par la couche générique, ce qui se produit généralement par le biais des fonctions énumérées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un élément de données optionnel à associer à ce système de fichiers. Lors de l'appel de cette fonction, Tcl attachera le système de fichiers à la liste des systèmes de fichiers connus, et il deviendra pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera renvoyé.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et renvoie TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est renvoyé.

Tcl_FSData renverra le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il renverra NULL.

Tcl_FSMountsChanged est utilisé pour informer le cœur de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

    Tcl_FSStatProc *statProc;
    Tcl_FSAccessProc *accessProc;
    Tcl_FSOpenFileChannelProc *openFileChannelProc;
    Tcl_FSMatchInDirectoryProc *matchInDirectoryProc;
    Tcl_FSUtimeProc *utimeProc;
    Tcl_FSLinkProc *linkProc;
    Tcl_FSListVolumesProc *listVolumesProc;
    Tcl_FSFileAttrStringsProc *fileAttrStringsProc;
    Tcl_FSFileAttrsGetProc *fileAttrsGetProc;
    Tcl_FSFileAttrsSetProc *fileAttrsSetProc;

    Tcl_FSChdirProc *chdirProc;

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche générique des systèmes de fichiers pour effectuer la gamme complète d'actions liées aux systèmes de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (la quasi-totalité doit être implémentée), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni) et fonctions d'efficacité (qui doivent seulement être implémentées si elles peuvent l'être efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl a des émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces solutions de repli ne sont utilisées que pour gérer les commandes initiées dans Tcl, pas dans C. Cela signifie que si une commande file rename est émise dans Tcl, et que les systèmes de fichiers concernés n'implémentent pas leur Tcl_FSRenameFileProc, le cœur de Tcl se rabattra sur une combinaison d'autres fonctions de système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y aura une autre solution de repli). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun de ces replis ne se produit. Il en va de même pour les quatre dernières entrées du tableau des systèmes de fichiers (lstat, load, getcwd et chdir) pour lesquelles des replis se produisent effectivement au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme de Tcl_Obj les prennent sous forme UTF-8. L'API d'infrastructure des systèmes de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

INFRASTRUCTURE DU SYSTÈME DE FICHIERS

Ces champs contiennent des informations de base sur la structure du système de fichiers et les adresses des fonctions utilisées pour associer un système de fichiers particulier à un chemin de fichier, et pour gérer la gestion interne des représentations de chemins, par exemple la copie et la libération de ces représentations.

TYPENAME

Le champ typeName contient une chaîne de caractères terminée par un octet nul qui identifie le type du système de fichiers implémenté, par exemple “native”, “zip” ou “vfs”.

TAILLE DE LA STRUCTURE

Le champ structureLength est généralement implémenté comme sizeof(Tcl_Filesystem), et est là pour permettre une meilleure compatibilité ascendante binaire si la taille de la structure change dans une future version de Tcl.

VERSION

Le champ version doit être défini sur TCL_FILESYSTEM_VERSION_1.

PATHINFILESYSTEMPROC

Le champ pathInFilesystemProc contient l'adresse d'une fonction qui est appelée pour déterminer si une valeur de chemin donnée appartient ou non à ce système de fichiers. Tcl n'appellera les autres fonctions du système de fichiers qu'avec un chemin pour lequel cette fonction a retourné TCL_OK. Si le chemin n'appartient pas, -1 doit être retourné (le comportement de Tcl pour toute autre valeur de retour n'est pas défini). Si TCL_OK est retourné, alors le paramètre de sortie optionnel clientDataPtr peut être utilisé pour retourner une représentation interne (spécifique au système de fichiers) du chemin, qui sera mise en cache dans la valeur du chemin, et pourra être récupérée efficacement par les autres fonctions du système de fichiers. Tcl mettra simultanément en cache le fait que ce chemin appartient à ce système de fichiers. Ces caches sont invalidés lorsque des structures de systèmes de fichiers sont ajoutées ou supprimées de la liste interne des systèmes de fichiers connus de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

DUPINTERNALREPPROC

Cette fonction crée une copie de la représentation interne d'un chemin, et est appelée lorsque Tcl a besoin de dupliquer une valeur de chemin. Si NULL, Tcl ne copiera simplement pas la représentation interne, qui devra alors être régénérée plus tard.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

FREEINTERNALREPPROC

Libère la représentation interne. Cela doit être implémenté si des représentations internes doivent être libérées (c'est-à-dire si de la mémoire est allouée lors de la génération d'une représentation interne), mais peut sinon être NULL.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

INTERNALTONORMALIZEDPROC

Fonction pour convertir une représentation interne en un chemin normalisé. Uniquement requis si le système de fichiers crée des valeurs de chemin pures sans représentation de chaîne/chemin. La valeur de retour est une valeur Tcl dont la représentation de chaîne est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

CREATEINTERNALREPPROC

Fonction pour prendre une valeur de chemin, calculer une représentation interne pour celle-ci, et stocker cette représentation native dans la valeur. Peut être NULL si les chemins n'ont pas de représentation interne, ou si le Tcl_FSPathInFilesystemProc pour ce système de fichiers crée toujours immédiatement une représentation interne pour les chemins qu'il accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

NORMALIZEPATHPROC

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations de chaînes pour la même valeur de chemin. Dans Tcl, chaque “chemin” doit avoir une unique “représentation de chaîne normalisée”. Selon le système de fichiers, il peut y avoir plus d'une représentation de chaîne non normalisée qui fait référence à ce chemin (par exemple, un chemin relatif, un chemin avec une casse de caractères différente si le système de fichiers ne fait pas la distinction, un chemin contenant une référence à un répertoire personnel comme “~”, un chemin contenant des liens symboliques, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être converti en la valeur à laquelle il pointe (mais sa casse ou d'autres aspects doivent être rendus uniques). Tous les autres composants du chemin doivent être convertis à partir des liens symboliques. Cette seule exception est nécessaire pour s'aligner sur la sémantique de Tcl avec les commandes file delete, file rename, file copy opérant sur des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint soit au début du chemin (c'est-à-dire zéro), soit à la fin du chemin, soit à tout séparateur de fichier intermédiaire dans le chemin. Elle ne pointira jamais vers une autre position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS DU SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions qui sont appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui est censé être utilisé avec l'ensemble complet des commandes Tcl standard doit implémenter toutes ces fonctions. Si certaines ne sont pas implémentées, certaines commandes Tcl peuvent échouer lorsqu'elles opèrent sur des chemins de ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques n'a pas besoin d'implémenter la fonction readlink, etc. Le noyau Tcl s'attend à ce que les systèmes de fichiers se comportent de cette manière).

FILESYSTEMPATHTYPEPROC

Fonction pour déterminer le type d'un chemin dans ce système de fichiers. Peut être NULL, auquel cas aucune information de type ne sera disponible pour les utilisateurs du système de fichiers. Le “type” est utilisé à des fins informatifs uniquement, et doit être retourné comme la représentation de chaîne de l'objet Tcl retourné. Une valeur de retour typique pourrait être “networked”, “zip” ou “ftp”. L'objet Tcl résultant appartient au système de fichiers et donc Tcl incrémentera le compteur de références de cette valeur s'il souhaite en conserver une référence.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

FILESYSTEMSEPARATORPROC

Fonction pour retourner le(s) caractère(s) séparateur(s) pour ce système de fichiers. Cela n'a besoin d'être implémenté que si le système de fichiers souhaite utiliser un séparateur différent de la chaîne standard “/”. Entre autres utilisations, il est retourné par la commande file separator. La valeur de retour doit être une valeur avec un compteur de références de zéro.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

STATPROC

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent de manière cruciale (par exemple, file atime, file isdir, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le Tcl_FSStatProc remplit la structure stat statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche pour tous les répertoires nommés dans le chemin menant au fichier. La structure stat comprend des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification et l'heure de la dernière modification des métadonnées.

Si le fichier représenté par pathPtr existe, le Tcl_FSStatProc retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné, et aucune information de stat n'est donnée.

ACCESSPROC

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent de manière cruciale (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

Le Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est dans pathPtr. Si le nom de chemin fait référence à un lien symbolique, alors les permissions du fichier auquel ce lien symbolique fait référence doivent être testées.

En cas de succès (toutes les permissions demandées accordées), zéro est retourné. En cas d'erreur (au moins un bit dans le mode demandait une permission qui est refusée, ou une autre erreur s'est produite), -1 est retourné.

OPENFILECHANNELPROC

Fonction pour traiter un appel Tcl_FSOpenFileChannel. Elle doit être implémentée pour tout système de fichiers raisonnable, car toute opération qui nécessite l'ouverture ou l'accès au contenu d'un fichier utilisera cette fonction (par exemple, open, encoding et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

La Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et renvoie un descripteur de canal qui peut être utilisé pour lire et écrire dans le fichier. Cette API est calquée sur la fonction fopen de la bibliothèque d'entrée/sortie standard Unix. La syntaxe et la signification des arguments sont similaires à celles fournies dans la commande Tcl open lors de l'ouverture d'un fichier, où le mode est une combinaison des indicateurs POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, la Tcl_FSOpenFileChannelProc renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, la Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le canal créé doit être enregistré auprès de l'interpréteur fourni par une Tcl_FSOpenFileChannelProc ; ce travail incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr, a été précédemment fermé, l'action de création du nouveau canal l'assigne également comme substitut du canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, la fonctionnalité de globbing et de copie récursive manquera dans le système de fichiers (et cela peut affecter des commandes comme encoding names qui utilisent la fonctionnalité de globbing).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit renvoyer tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au modèle donné et qui correspondent au schéma types spécifié. Il y a deux façons dont cette fonction peut être appelée. Si pattern est NULL, pathPtr est une spécification complète d'un fichier ou d'un répertoire dont l'existence et le type doivent être vérifiés. Sinon, pathPtr est un répertoire, et la fonction doit rechercher des fichiers ou des répertoires du bon type. Dans tous les cas, pathPtr peut être supposé non nul et non vide. Bien qu'il ne soit pas documenté si pathPtr a un séparateur de fichier à sa fin, le code doit être flexible pour les deux possibilités.

La valeur de retour est un résultat standard de Tcl indiquant si une erreur s'est produite pendant le processus de correspondance. Les messages d'erreur sont placés dans interp, à moins que interp ne soit NULL, auquel cas aucun message d'erreur ne sera généré ; en cas de résultat TCL_OK, les résultats doivent être ajoutés à la valeur resultPtr donnée (qui est supposée être une liste Tcl non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (ce qui signifie généralement qu'il s'agira de spécifications de chemin absolu). Remarque : s'il n'y a pas de correspondances, cela conduit simplement à un résultat vide ; seules les erreurs sont signalées pour les problèmes réels de fichier ou de système de fichiers qui peuvent survenir pendant le processus de correspondance.

Le Tcl_GlobTypeData passé dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Corresponds to bcdpfls as in 'find -t' */
    int type;
    /* Corresponds to file permissions */
    int perm;
    /* Acceptable mac type */
    Tcl_Obj *macType;
    /* Acceptable mac creator */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de gérer correctement, tous deux lorsque types n'est pas nul. Les deux cas sont lorsque types->types est TCL_GLOB_TYPE_DIR ou TCL_GLOB_TYPE_MOUNT (et en particulier lorsque les autres indicateurs sont faux). Dans le premier de ces cas, la fonction doit lister les répertoires comptés. Tcl utilise cette fonction pour implémenter le globbing récursif, il est donc essentiel que les systèmes de fichiers implémentent correctement la correspondance de répertoires. Dans le second de ces cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage trouvés dans le répertoire donné par pathPtr (et dans ce cas, pathPtr n'a pas besoin d'être dans le même système de fichiers - contrairement à tous les autres cas où cette fonction est appelée). Le support pour ce cas est critique si Tcl doit avoir des transitions fluides entre différents systèmes de fichiers.

UTIMEPROC

Fonction pour traiter un appel Tcl_FSUtime. Elle est requise pour permettre la mise à jour (pas la lecture) des horodatages de fichiers avec file mtime, file atime et l'implémentation de la copie de fichiers de open-r/open-w/fcopy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les heures d'accès et de modification des fichiers spécifiés par pathPtr doivent être modifiées aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec le système utime.

LINKPROC

Fonction pour traiter un appel Tcl_FSLink. Elle doit être implémentée uniquement si le système de fichiers prend en charge les liens, et peut être NULL dans le cas contraire.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est appelée pour lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient entièrement à l'appelant (et doit donc incrémenter son compte de références avant d'être renvoyé). Tout appelant doit appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'en a plus besoin. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Le résultat dans ce cas doit être toPtr si la création du lien a réussi et NULL dans le cas contraire. Dans ce cas, le résultat n'appartient pas à l'appelant (c'est-à-dire qu'il n'y a aucune manipulation de références des deux côtés). Voir la documentation de Tcl_FSLink pour interpréter correctement les indicateurs de linkAction.

LISTVOLUMESPROC

Fonction pour lister tous les volumes de systèmes de fichiers ajoutés par ce système de fichiers. Elle doit être implémentée uniquement si le système de fichiers ajoute des volumes au début du système de fichiers, afin qu'ils puissent être renvoyés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste de volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'a été fourni. La valeur de retour est considérée comme appartenant au système de fichiers (pas au noyau Tcl), mais doit recevoir un compte de références pour Tcl. Tcl utilisera le contenu de la liste, puis décrémentera ce compte de références. Cela permet aux systèmes de fichiers de choisir s'ils veulent réellement conserver une liste globale de volumes ou non (si non, générer la liste à la volée et la passer à Tcl avec un compte de références de 1, puis oublier la liste ; si oui, alors simplement incrémenter le compte de références de leur liste globale et la passer à Tcl qui copiera le contenu puis décrémentera le compteur pour le ramener à son état précédent).

Par conséquent, Tcl considère les valeurs de retour de cette proc comme étant en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne prendra pas en charge la fonctionnalité file attributes. Cela permet d'ajouter des informations arbitraires aux fichiers du système de fichiers. Si elle n'est pas implémentée, les méthodes get et set n'ont pas besoin d'être implémentées.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

L'appel de la fonction peut renvoyer un tableau de chaînes ou, à la place, renvoyer NULL et placer une liste Tcl dans le objPtrRef donné. Tcl prendra cette liste et incrémentera d'abord son compte de références avant de l'utiliser. Une fois son utilisation terminée, Tcl décrémentera son compte de références. Par conséquent, si la liste doit être détruite par Tcl lorsqu'elle est terminée, elle doit avoir un compte de références de zéro, et si la liste ne doit pas être détruite, le système de fichiers doit garantir qu'il renvoie une valeur avec un compte de références d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel Tcl_FSFileAttrsGet, utilisé par file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Renvoie un code de retour standard de Tcl. La valeur de l'attribut récupéré, correspondant à l'élément index-ième dans la liste renvoyée par Tcl_FSFileAttrStringsProc, est placée dans objPtrRef (si TCL_OK a été renvoyé) et aura probablement un compte de références de zéro. Dans tous les cas, nous devons stocker cette valeur quelque part (par exemple, dans le résultat de Tcl), ou incrémenter/décrémenter son compte de références pour garantir qu'elle sera détruite correctement.

FILEATTRSSETPROC

Fonction pour traiter un appel Tcl_FSFileAttrsSet, utilisé par file attributes. Si le système de fichiers est en lecture seule, cette fonction n'a pas besoin d'être implémentée.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

La valeur de l'attribut pour l'élément index-ième dans la liste renvoyée par Tcl_FSFileAttrStringsProc doit être définie sur objPtr donné.

CREATEDIRECTORYPROC

Fonction pour créer un répertoire dans le système de fichiers. Elle doit être implémentée si le système de fichiers ajoute des volumes au début du système de fichiers.

FILESYSTEM FUNCTIONS

Las siguientes funciones son las correspondientes a las llamadas de Tcl file. Deben ser implementadas por los sistemas de archivos si desean ser compatibles con el manejo de archivos y directorios por parte de Tcl.

CREATEDIRECTORYPROC

Función para procesar una llamada Tcl_FSCreateDirectory. Debe implementarse a menos que el sistema de archivos sea de solo lectura.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error durante el procesamiento. Si tiene éxito, se debería haber añadido una nueva carpeta al sistema de archivos en la ubicación especificada por pathPtr.

REMOVEDIRECTORYPROC

Función para procesar una llamada Tcl_FSRemoveDirectory. Debe implementarse a menos que el sistema de archivos sea de solo lectura.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error durante el procesamiento. Si tiene éxito, la carpeta especificada por pathPtr debería haber sido eliminada del sistema de archivos. Si se proporciona el indicador recursive, una carpeta no vacía debería haber sido eliminada sin error. Si el indicador no se proporciona y la carpeta no está vacía, se debería generar un error POSIX "EEXIST". Si ocurre un error, el nombre del archivo o carpeta que causó el error debería estar en errorPtr.

DELETEFILEPROC

Función para procesar una llamada Tcl_FSDeleteFile. Debe implementarse a menos que el sistema de archivos sea de solo lectura.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error durante el procesamiento. Si tiene éxito, el archivo especificado por pathPtr debería haber sido eliminado del sistema de archivos. Tenga en cuenta que, si el sistema de archivos admite enlaces simbólicos, Tcl llamará a esta función y no a Tcl_FSRemoveDirectoryProc cuando sea necesario eliminarlos (incluso si son enlaces simbólicos a directorios).

FILESYSTEM EFFICIENCY

Estas funciones no necesitan ser implementadas para un sistema de archivos determinado, ya que el núcleo tiene una implementación de respaldo disponible. Consulte cada descripción individual para conocer las consecuencias de dejar el campo en NULL.

LSTATPROC

Función para procesar una llamada Tcl_FSLstat. Si no se implementa, Tcl intentará usar statProc definido anteriormente. Por lo tanto, solo debe implementarse si el sistema de archivos puede diferenciar entre las llamadas stat y lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

El comportamiento de esta función es muy similar al de Tcl_FSStatProc definido anteriormente, excepto que si se aplica a un enlace simbólico, devuelve información sobre el enlace, no sobre el archivo de destino.

COPYFILEPROC

Función para procesar una llamada Tcl_FSCopyFile. Si no se implementa, Tcl recurrirá al mecanismo de open-r, open-w y fcopy para realizar la copia. Por lo tanto, solo debe implementarse si el sistema de archivos puede realizar esta acción de manera más eficiente.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error durante el proceso de copia. Tenga en cuenta que destPathPtr es el nombre del archivo que se convertirá en la copia de srcPathPtr. No es el nombre de un directorio en el que se pueda copiar srcPathPtr (es decir, la función es mucho más simple que el subcomando file copy en el nivel Tcl). Tenga en cuenta que, si el sistema de archivos admite enlaces simbólicos, Tcl llamará a esta función y no a copyDirectoryProc cuando sea necesario copiarlos (incluso si son enlaces simbólicos a directorios). Finalmente, si el sistema de archivos determina que no puede admitir la acción de copiar archivos, se llamará a Tcl_SetErrno(EXDEV) y se devolverá un resultado que no sea TCL_OK para que Tcl utilice sus mecanismos de respaldo estándar.

RENAMEFILEPROC

Función para procesar una llamada Tcl_FSRenameFile. Si no se implementa, Tcl recurrirá a un mecanismo de copia y eliminación. Por lo tanto, solo debe implementarse si el sistema de archivos puede realizar esta acción de manera más eficiente.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error durante el proceso de renombrado. Si el sistema de archivos determina que no puede admitir la acción de renombrado, se llamará a Tcl_SetErrno(EXDEV) y se devolverá un resultado que no sea TCL_OK para que Tcl utilice sus mecanismos de respaldo estándar.

COPYDIRECTORYPROC

Función para procesar una llamada Tcl_FSCopyDirectory. Si no se implementa, Tcl recurrirá a un mecanismo recursivo de file mkdir, file copy. Por lo tanto, solo debe implementarse si el sistema de archivos puede realizar esta acción de manera más eficiente.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error durante el proceso de copia. Si ocurre un error, el nombre del archivo o carpeta que causó el error debería estar en errorPtr. Tenga en cuenta que destPathPtr es el nombre de la carpeta que se convertirá en el espejo de srcPathPtr. No es el nombre de un directorio en el que se pueda copiar srcPathPtr (es decir, la función es mucho más simple que el subcomando file copy en el nivel Tcl). Finalmente, si el sistema de archivos determina que no puede admitir la acción de copiar directorios, se llamará a Tcl_SetErrno(EXDEV) y se devolverá un resultado que no sea TCL_OK para que Tcl utilice sus mecanismos de respaldo estándar.

LOADFILEPROC

Función para procesar una llamada Tcl_FSLoadFile. Si no se implementa, Tcl recurrirá a una copia a un archivo temporal, seguido de una llamada a Tcl_FSLoadFile en ese archivo temporal. Por lo tanto, solo debe implementarse si el sistema de archivos puede cargar el código directamente, o puede implementarse simplemente para devolver TCL_ERROR para desactivar la funcionalidad de carga en este sistema de archivos.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Devuelve un código de finalización estándar de Tcl. Si hay un error, se deja un mensaje de error en el resultado del interp. La función carga dinámicamente un archivo de código binario en memoria. En caso de éxito, handlePtr debe rellenarse con un token para el archivo cargado dinámicamente, y unloadProcPtr debe rellenarse con la dirección de un procedimiento. El procedimiento de descarga se llamará con el Tcl_LoadHandle dado como único parámetro cuando Tcl necesite descargar el archivo. Por ejemplo, para el sistema de archivos nativo, el Tcl_LoadHandle devuelto es actualmente un token que se puede utilizar en el TclpFindSymbol privado para acceder a funciones del nuevo código. Cada sistema de archivos puede definir el Tcl_LoadHandle como lo requiera. Finalmente, si el sistema de archivos determina que no puede admitir la acción de carga de archivos, se llamará a Tcl_SetErrno(EXDEV) y se devolverá un resultado que no sea TCL_OK para que Tcl utilice sus mecanismos de respaldo estándar.

UNLOADFILEPROC

Función para descargar un archivo que fue previamente cargado con éxito. Si se implementó la carga, esta también debe implementarse si hay alguna acción de limpieza necesaria.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Función para procesar una llamada Tcl_FSGetCwd. La mayoría de los sistemas de archivos no necesitan implementar esto. A veces se llama una vez, si getcwd se llama antes de chdir. Puede ser NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si el sistema de archivos admite una noción nativa de directorio de trabajo (que podría cambiar independientemente de Tcl), esta función debería devolver ese cwd como resultado, o NULL si el directorio de trabajo no se puede determinar (por ejemplo, el usuario no tiene permisos adecuados en el directorio cwd). Si se devuelve NULL, se deja un mensaje de error en el resultado del interp.

CHDIRPROC

Función para procesar una llamada Tcl_FSChdir. Si los sistemas de archivos no implementan esto, se emulará mediante una serie de comprobaciones de acceso a directorios. De lo contrario, los sistemas de archivos que implementan esto deben responder con un resultado positivo si pathPtr es un directorio válido y accesible en su sistema de archivos. No deben recordar el resultado, ya que ese será recordado automáticamente por Tcl_FSGetCwd. Las implementaciones reales deberían realizar la acción correcta (es decir, llamar a la API de sistema chdir correspondiente).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

La función Tcl_FSChdirProc cambia el directorio de trabajo de la aplicación al valor especificado en pathPtr. La función devuelve -1 en caso de error o 0 en caso de éxito.
