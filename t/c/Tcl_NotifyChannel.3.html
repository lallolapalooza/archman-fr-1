DESCRIPTION

Tcl utilise une architecture de canaux à deux couches. Elle fournit une couche générique supérieure pour permettre aux programmes C et Tcl d'effectuer des entrées et sorties en utilisant les mêmes API pour une variété de fichiers, périphériques, sockets, etc. Les API C génériques sont décrites dans l'entrée de manuel de Tcl_OpenFileChannel.

La couche inférieure fournit des pilotes de canaux spécifiques au type pour chaque type de périphérique supporté sur chaque plateforme. Cette entrée de manuel décrit les API C utilisées pour communiquer entre la couche générique et les pilotes de canaux spécifiques au type. Elle explique également comment de nouveaux types de canaux peuvent être ajoutés en fournissant de nouveaux pilotes de canaux.

Les pilotes de canaux se composent de plusieurs composants : Premièrement, chaque pilote de canal fournit une structure Tcl_ChannelType contenant des pointeurs vers des fonctions implémentant les diverses opérations utilisées par la couche générique pour communiquer avec le pilote de canal. La structure Tcl_ChannelType et les fonctions auxquelles elle fait référence sont décrites dans la section TCL_CHANNELTYPE, ci-dessous.

Deuxièmement, les pilotes de canaux fournissent généralement une commande Tcl pour créer des instances de ce type de canal. Par exemple, la commande Tcl open crée des canaux qui utilisent les pilotes de canaux de fichier et de commande, et la commande Tcl socket crée des canaux qui utilisent des sockets TCP pour la communication réseau.

Troisièmement, un pilote de canal fournit éventuellement une fonction C pour ouvrir des instances de canaux de ce type. Par exemple, Tcl_OpenFileChannel ouvre un canal qui utilise le pilote de canal de fichier, et Tcl_OpenTcpClient ouvre un canal qui utilise le protocole réseau TCP. Ces fonctions de création utilisent généralement Tcl_CreateChannel en interne pour ouvrir le canal.

Pour ajouter un nouveau type de canal, vous devez implémenter une API C ou une commande Tcl qui ouvre un canal en appelant Tcl_CreateChannel. Lorsque votre pilote appelle Tcl_CreateChannel, il lui passe une structure Tcl_ChannelType décrivant les procédures d'E/S du pilote. La couche générique invoquera alors les fonctions référencées dans cette structure pour effectuer des opérations sur le canal.

Tcl_CreateChannel ouvre un nouveau canal et lui associe les éléments typePtr et instanceData fournis. Le canal est ouvert dans le mode indiqué par mask. Pour une discussion sur les pilotes de canaux, leurs opérations et la structure Tcl_ChannelType, voir la section TCL_CHANNELTYPE, ci-dessous.

Tcl_CreateChannel interagit avec le code gérant les canaux standards. Une fois qu'un canal standard a été initialisé soit par un appel à Tcl_GetStdChannel soit par un appel à Tcl_SetStdChannel, la fermeture de ce canal standard provoquera le prochain appel à Tcl_CreateChannel pour faire également du nouveau canal le nouveau canal standard. Voir Tcl_StandardChannels pour un traité général sur les canaux standards et le comportement de la bibliothèque Tcl à leur égard.

Tcl_GetChannelInstanceData renvoie les données d'instance associées au canal dans channel. Ceci est identique à l'argument instanceData dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelType renvoie un pointeur vers la structure Tcl_ChannelType utilisée par le canal dans l'argument channel. Ceci est identique à l'argument typePtr dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelName renvoie une chaîne contenant le nom associé au canal, ou NULL si l'argument channelName de Tcl_CreateChannel était NULL.

Tcl_GetChannelHandle place le descripteur de périphérique spécifique au système d'exploitation associé à channel pour la direction donnée dans l;

FONCTIONS DE CANAL

Les fonctions suivantes sont disponibles pour manipuler les canaux Tcl.

Tcl_GetChannelHandle renvoie le descripteur de périphérique sous-jacent pour le canal spécifié dans la direction donnée. La valeur sera un descripteur de périphérique valide pour la direction spécifiée et sera stockée dans la localisation indiquée par handlePtr, et la fonction renvoie TCL_OK. Si le canal n'a pas de descripteur de périphérique pour la direction spécifiée, alors TCL_ERROR est retourné à la place. Différents pilotes de canal renverront différents types de descripteurs. Référez-vous aux entrées du manuel pour chaque pilote afin de déterminer le type de descripteur retourné.

Tcl_GetChannelThread renvoie l'identifiant du thread qui gère actuellement le channel spécifié. Cela permet aux pilotes de canal d'envoyer leurs événements de fichier à la file d'attente d'événements correcte, même pour un noyau multi-thread.

Tcl_GetChannelMode renvoie une combinaison OR de TCL_READABLE et TCL_WRITABLE, indiquant si le canal est ouvert en lecture et en écriture.

Tcl_GetChannelBufferSize renvoie la taille, en octets, des tampons alloués pour stocker les entrées ou sorties dans le channel. Si la valeur n'a pas été définie par un appel précédent à Tcl_SetChannelBufferSize, décrit ci-dessous, alors la valeur par défaut de 4096 est retournée.

Tcl_SetChannelBufferSize définit la taille, en octets, des tampons qui seront alloués lors des opérations ultérieures sur le canal pour stocker les entrées ou sorties. L'argument size doit être compris entre un et un million, permettant des tampons d'un octet à un million d'octets. Si size est en dehors de cette plage, Tcl_SetChannelBufferSize définit la taille du tampon à 4096.

Tcl_NotifyChannel est appelé par un pilote de canal pour indiquer à la couche générique que les événements spécifiés par mask se sont produits sur le canal. Les pilotes de canal sont responsables de l'invocation de cette fonction chaque fois que les gestionnaires de canal doivent être appelés pour le canal (ou que d'autres tâches en attente, comme la vidange d'une écriture, doivent être effectuées). Voir WATCHPROC ci-dessous pour plus de détails.

Tcl_BadChannelOption est appelée à partir de setOptionProc ou getOptionProc spécifiques au pilote pour générer un message d'erreur complet.

Tcl_ChannelBuffered renvoie le nombre d'octets d'entrée actuellement mis en mémoire tampon dans le tampon interne (zone de repoussage) du canal lui-même. Il ne signale pas les données dans les tampons globaux de la pile de canaux dont le canal fourni fait partie.

Tcl_IsChannelShared vérifie le compteur de références du channel spécifié et renvoie si le channel était partagé entre plusieurs interpréteurs (résultat == 1) ou non (résultat == 0).

Tcl_IsChannelRegistered vérifie si le channel spécifié est enregistré dans l'interpréteur interp donné (résultat == 1) ou non (résultat == 0).

Tcl_IsChannelExisting vérifie si un canal portant le nom spécifié est enregistré dans la liste globale (par thread) de tous les canaux (résultat == 1) ou non (résultat == 0).

Tcl_CutChannel retire le channel spécifié de la liste globale (par thread) de tous les canaux (du thread courant). L'application à un canal encore enregistré dans un interpréteur n'est pas autorisée. Notifie également le pilote si la version de Tcl_ChannelType est TCL_CHANNEL_VERSION_4 (ou supérieure), et si Tcl_DriverThreadActionProc est défini pour elle.

Tcl_SpliceChannel ajoute le channel spécifié à la liste globale (par thread) de tous les canaux (du thread courant). L'application à un canal enregistré dans un interpréteur n'est pas autorisée. Notifie également le pilote si la version de Tcl_ChannelType est TCL_CHANNEL_VERSION_4 (ou supérieure), et si Tcl_DriverThreadActionProc est défini pour elle.

Tcl_ClearChannelHandlers supprime tous les gestionnaires de canal et scripts d'événements associés au channel spécifié, interrompant ainsi tout traitement d'événements pour ce canal.

TCL_CHANNELTYPE

Un pilote de canal fournit une structure Tcl_ChannelType qui contient des pointeurs vers les fonctions qui implémentent les diverses opérations sur un canal ; ces opérations sont invoquées au besoin par la couche générique. La structure a été versionnée à partir de Tcl 8.3.2/8.4 pour corriger un problème avec les pilotes de canal empilés. Voir la section OLD CHANNEL TYPES ci-dessous pour les détails sur l'ancienne structure.

La structure Tcl_ChannelType contient les champs suivants :

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Il n'est pas nécessaire de fournir des implémentations pour toutes les opérations sur les canaux. Celles qui ne sont pas nécessaires peuvent être définies à NULL dans la structure : blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc, et close2Proc, en plus de flushProc, handlerProc, threadActionProc, et truncateProc. D'autres fonctions qui ne peuvent pas être implémentées de manière significative devraient renvoyer EINVAL lorsqu'elles sont appelées, pour indiquer que les opérations qu'elles représentent ne sont pas disponibles. Notez également que wideSeekProc peut être NULL si seekProc l'est.

L'utilisateur ne devrait utiliser que la structure ci-dessus pour l'instanciation de Tcl_ChannelType. Lors de la référence aux champs d'une structure Tcl_ChannelType, les fonctions suivantes doivent être utilisées pour obtenir les valeurs : Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc, ou Tcl_ChannelHandlerProc.

La modification des structures a été faite de manière à ce que les types de canaux standard soient compatibles au niveau binaire. Cependant, les types de canaux qui utilisent des canaux empilés (c'est-à-dire TLS, Trf) ont de nouvelles versions pour correspondre au changement ci-dessus, car le code précédent pour les canaux empilés présentait des problèmes.

TYPENAME

Le champ typeName contient une chaîne terminée par un octet nul qui identifie le type de périphérique implémenté par ce pilote, par exemple file ou socket.

Cette valeur peut être récupérée avec Tcl_ChannelName, qui renvoie un pointeur vers la chaîne.

VERSION

Le champ version doit être défini sur la version de la structure dont vous avez besoin. TCL_CHANNEL_VERSION_2 est le minimum recommandé. TCL_CHANNEL_VERSION_3 doit être défini pour spécifier le membre wideSeekProc. TCL_CHANNEL_VERSION_4 doit être défini pour spécifier le membre threadActionProc (inclut wideSeekProc). TCL_CHANNEL_VERSION_5 doit être défini pour spécifier le membre truncateProc (inclut wideSeekProc et threadActionProc). S'il n'est défini sur aucune de ces valeurs, alors ce Tcl_ChannelType est supposé avoir la structure d'origine. Voir OLD CHANNEL TYPES pour plus de détails. Bien que Tcl reconnaisse et fonctionne avec les deux structures, les canaux empilés doivent être au moins de TCL_CHANNEL_VERSION_2 pour fonctionner correctement.

Cette valeur peut être récupérée avec Tcl_ChannelVersion, qui renvoie l'une des valeurs TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 ou TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

Le champ blockModeProc contient l'adresse d'une fonction appelée par la couche générique pour définir le mode bloquant et non bloquant sur le périphérique. BlockModeProc doit correspondre au prototype suivant :

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

L'argument instanceData est le même que la valeur passée à Tcl_CreateChannel lors de la création de ce canal. L'argument mode est soit TCL_MODE_BLOCKING soit TCL_MODE_NONBLOCKING pour définir le périphérique en mode bloquant ou non bloquant. La fonction doit renvoyer zéro si l'opération a réussi, ou un code d'erreur POSIX non nul si l'opération a échoué.

Si l'opération réussit, la fonction peut modifier l' instanceData fourni pour enregistrer que le canal est passé en mode bloquant ou non bloquant et pour implémenter le comportement bloquant ou non bloquant. Pour certains types de périphériques, le comportement bloquant et non bloquant peut être implémenté par le système d'exploitation sous-jacent ; pour d'autres types de périphériques, le comportement doit être émulé dans le pilote de canal.

Cette valeur peut être récupérée avec Tcl_ChannelBlockModeProc, qui renvoie un pointeur vers la fonction.

Un pilote de canal qui ne fournit pas de blockModeProc doit être très, très prudent. Il doit indiquer précisément à la couche générique quel mode de blocage lui convient, et cela doit également être documenté pour l'utilisateur afin que le mode de blocage du canal ne soit pas modifié à une valeur inacceptable. Toute confusion ici peut entraîner l'interpréteur dans une impasse (factice et difficile à trouver).

INPUTPROC

Le champ inputProc contient l'adresse d'une fonction appelée par la couche générique pour lire des données à partir d'un périphérique ou d'un fichier et les stocker dans un tampon interne. InputProc doit correspondre au prototype suivant :

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création du canal. L'argument buf pointe vers un tableau d'octets dans lequel l'entrée du périphérique sera stockée, et l'argument bufSize indique combien d'octets sont disponibles dans buf.

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générique. Si une erreur se produit, la fonction doit définir cette variable à un code d'erreur POSIX identifiant l'erreur.

La fonction doit lire les données du périphérique encapsulé par le canal et les stocker dans buf. En cas de succès, la fonction doit retourner un nombre non négatif indiquant combien d'octets ont été lus à partir du périphérique et stockés dans buf. En cas d'erreur, la fonction doit retourner -1. Si une erreur se produit après la lecture de certaines données du périphérique, ces données seront perdues.

Si inputProc peut déterminer que le périphérique d'entrée a des données disponibles mais moins que ce qui est demandé par l'argument bufSize, la fonction doit tenter de lire uniquement la quantité de données disponible et retourner sans bloquer. Si le périphérique d'entrée n'a pas de données disponibles et que le canal est en mode non bloquant, la fonction doit retourner une erreur EAGAIN. Si le périphérique d'entrée n'a pas de données disponibles et que le canal est en mode bloquant, la fonction doit bloquer pendant la plus courte durée possible jusqu'à ce qu'au moins un octet puisse être lu à partir du périphérique, puis retourner le nombre maximum de données qui peuvent être lues sans bloquer.

Cette valeur peut être récupérée avec Tcl_ChannelInputProc, qui retourne un pointeur vers la fonction.

OUTPUTPROC

Le champ outputProc contient l'adresse d'une fonction appelée par la couche générique pour transférer des données d'un tampon interne vers le périphérique de sortie. OutputProc doit correspondre au prototype suivant :

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création du canal. L'argument buf contient un tableau d'octets à écrire dans le périphérique, et l'argument toWrite indique combien d'octets seront écrits à partir de l'argument buf.

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générique pour retourner la valeur de errno. Si une erreur se produit, la fonction doit définir cette variable à un code d'erreur POSIX identifiant l'erreur.

La fonction doit écrire les données dans buf dans le périphérique de sortie encapsulé par le canal. En cas de succès, la fonction doit retourner un nombre non négatif indiquant combien d'octets ont été écrits dans le périphérique de sortie. La valeur de retour est normalement la même que toWrite, mais peut être plus petite dans certains cas, par exemple si l'opération de sortie est interrompue par un signal. Si une erreur se produit, la fonction doit retourner -1. En cas d'erreur, certaines données pourraient avoir été écrites dans le périphérique.

Si le canal est en mode non bloquant et que le périphérique de sortie ne peut pas absorber de données, la fonction doit retourner -1 avec une erreur EAGAIN sans écrire de données.

Cette valeur peut être récupérée avec Tcl_ChannelOutputProc, qui retourne un pointeur vers la fonction.

SEEKPROC ET WIDESEEKPROC

Le champ seekProc contient l'adresse d'une fonction appelée par la couche générique pour déplacer le point d'accès auquel les futures opérations d'entrée ou de sortie seront appliquées. SeekProc doit correspondre au prototype suivant :

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

InstanceData est la même valeur que celle donnée à Tcl_CreateChannel lors de la création de ce canal. Offset et seekMode ont la même signification que dans la fonction Tcl_Seek (description dans le manuel de Tcl_OpenFileChannel).

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générique pour retourner la valeur de errno. Si une erreur se produit, la fonction doit définir cette variable à un code d'erreur POSIX identifiant l'erreur. La fonction doit stocker un code EINVAL si le type de canal n'implémente pas la recherche.

La valeur de retour est le nouveau point d'accès ou -1 en cas d'erreur. Si une erreur se produit, la fonction ne doit pas déplacer le point d'accès.

Si un champ non nul seekProc existe, le champ wideSeekProc peut contenir l'adresse d'une fonction alternative qui gère les décalages (c'est-à-dire les valeurs supérieures à 32 bits), permettant de se déplacer dans des fichiers de plus de 2 Go. La fonction wideSeekProc est appelée de préférence à seekProc, mais les deux doivent être définies si wideSeekProc est définie. WideSeekProc doit correspondre au prototype suivant :

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

Les arguments et les valeurs de retour sont les mêmes qu'avec seekProc, sauf que le type de décalage et le type de retour sont différents.

Le champ seekProc peut être récupéré avec Tcl_ChannelSeekProc, qui retourne un pointeur vers la fonction, et le champ wideSeekProc peut être récupéré avec Tcl_ChannelWideSeekProc.

SETOPTIONPROC

Le champ setOptionProc contient l'adresse d'une fonction appelée par la couche générique pour définir une option spécifique au type de canal sur un canal. setOptionProc doit correspondre au prototype suivant :

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

optionName est le nom d'une option à définir, et newValue est la nouvelle valeur pour cette option, sous forme de chaîne. InstanceData est la même valeur que celle donnée à Tcl_CreateChannel lors de la création de ce canal. La fonction doit effectuer toute action spécifique au type de canal nécessaire pour implémenter la nouvelle valeur de l'option.

Certaines options sont gérées par le code générique et cette fonction n'est jamais appelée pour les définir, par exemple, -blockmode. D'autres options sont spécifiques à chaque type de canal et la fonction setOptionProc du pilote du canal est appelée pour les implémenter. Le champ setOptionProc peut être nul, ce qui indique que ce type de canal ne prend pas en charge d'options spécifiques.

Si la valeur de l'option est correctement modifiée à la nouvelle valeur, la fonction retourne TCL_OK. Elle doit appeler Tcl_BadChannelOption, qui à son tour retourne TCL_ERROR si optionName n'est pas reconnu. Si newValue spécifie une valeur non prise en charge ou si une erreur se produit lors d'un appel système, la fonction doit laisser un message d'erreur dans le résultat de interp si interp n'est pas nul. La fonction doit également appeler Tcl_SetErrno pour stocker un code d'erreur POSIX approprié.

Cette valeur peut être récupérée avec Tcl_ChannelSetOptionProc, qui retourne un pointeur vers la fonction.

GETOPTIONPROC

Le champ getOptionProc contient l'adresse d'une fonction appelée par la couche générique pour obtenir la valeur d'une option spécifique au type de canal sur un canal. getOptionProc doit correspondre au prototype suivant :

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        Tcl_DString *optionValue);

OptionName est le nom d'une option prise en charge par ce type de canal. Si le nom de l'option n'est pas NULL, la fonction stocke sa valeur actuelle, sous forme de chaîne, dans la chaîne dynamique Tcl optionValue. Si optionName est NULL, la fonction stocke dans optionValue une liste alternative de toutes les options prises en charge et de leurs valeurs actuelles. En cas de succès, la fonction retourne TCL_OK. Elle doit appeler Tcl_BadChannelOption, qui à son tour retourne TCL_ERROR si optionName n'est pas reconnu. Si newValue spécifie une valeur pour l'option qui n'est pas prise en charge ou si une erreur se produit lors d'un appel système, la fonction doit laisser un message d'erreur dans le résultat de interp si interp n'est pas nul. La fonction doit également appeler Tcl_SetErrno pour stocker un code d'erreur POSIX approprié.

Cette valeur peut être récupérée avec Tcl_ChannelGetOptionProc, qui retourne un pointeur vers la fonction.

WATCHPROC

Le champ watchProc contient l'adresse d'une fonction appelée par le gestionnaire de canal générique pour initialiser le mécanisme de notification des événements d'intérêt sur ce canal. WatchProc doit correspondre au prototype suivant :

typedef void Tcl_DriverWatchProc(
        ClientData instanceData,
        int mask);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument mask est une combinaison OU de TCL_READABLE, TCL_WRITABLE et TCL_EXCEPTION ; il indique les événements dont l'utilisateur souhaite être informé sur ce canal.

La fonction doit initialiser les mécanismes spécifiques au type de périphérique pour être avertie lorsqu'un événement d'intérêt est présent sur le canal. Lorsque un ou plusieurs des événements désignés se produisent sur le canal, le pilote de canal est responsable d'appeler Tcl_NotifyChannel pour informer le module de canal générique. Le pilote doit éviter de bloquer les autres pilotes de canal ou les sources de rappel en appelant Tcl_NotifyChannel trop fréquemment. L'équité peut être assurée en utilisant la file d'attente d'événements de Tcl pour permettre à l'événement de canal d'être programmé séquentiellement avec d'autres événements. Voir la description de Tcl_QueueEvent pour plus de détails sur la programmation d'un événement.

Cette valeur peut être récupérée avec Tcl_ChannelWatchProc, qui retourne un pointeur vers la fonction.

GETHANDLEPROC

Le champ getHandleProc contient l'adresse d'une fonction appelée par le gestionnaire de canal générique pour récupérer un handle spécifique au canal. GetHandleProc doit correspondre au prototype suivant :

typedef int Tcl_DriverGetHandleProc(
        ClientData instanceData,
        int direction,
        ClientData *handlePtr);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument direction est TCL_READABLE pour récupérer le handle utilisé pour l'entrée, ou TCL_WRITABLE pour récupérer le handle utilisé pour la sortie.

Si l'implémentation du canal a des handles spécifiques, la fonction doit récupérer le handle approprié en fonction de l'argument direction. Le handle doit être stocké à l'emplacement pointé par handlePtr, et TCL_OK doit être retourné. Si le canal n'est pas ouvert pour la direction spécifiée, ou si l'implémentation du canal n'utilise pas de handles spécifiques, la fonction doit retourner TCL_ERROR.

Cette valeur peut être récupérée avec Tcl_ChannelGetHandleProc, qui retourne un pointeur vers la fonction.

FLUSHPROC

Le champ flushProc est réservé pour des utilisations futures et doit être défini à NULL. FlushProc doit correspondre au prototype suivant :

typedef int Tcl_DriverFlushProc(
        ClientData instanceData);

Cette valeur peut être récupérée avec Tcl_ChannelFlushProc, qui retourne un pointeur vers la fonction.

HANDLERPROC

Le champ handlerProc contient l'adresse d'une fonction appelée par le gestionnaire de canal générique pour informer le canal qu'un événement s'est produit. Il doit être défini pour les pilotes de canal empilés qui souhaitent être informés des événements se produisant sur le canal sous-jacent (empilé). HandlerProc doit correspondre au prototype suivant :

typedef int Tcl_DriverHandlerProc(
        ClientData instanceData,
        int interestMask);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. InterestMask est une combinaison OU de TCL_READABLE ou TCL_WRITABLE ; il indique quel type d'événement s'est produit sur ce canal.

Cette valeur peut être récupérée avec Tcl_ChannelHandlerProc, qui retourne un pointeur vers la fonction.

THREADACTIONPROC

Le champ threadActionProc contient l'adresse de la fonction appelée par le gestionnaire de canal générique lorsque un canal est créé, fermé, ou est sur le point d'être déplacé vers un autre thread, c'est-à-dire lorsque l'état spécifique au thread du pilote pourrait devoir être initialisé ou mis à jour. Il peut être NULL. L'action TCL_CHANNEL_THREAD_REMOVE est utilisée pour informer le pilote qu'il doit mettre à jour ou supprimer toute donnée spécifique au thread qu'il pourrait conserver pour le canal.

L'action TCL_CHANNEL_THREAD_INSERT est utilisée pour informer le pilote qu'il doit mettre à jour ou initialiser toute donnée spécifique au thread qu'il pourrait conserver en utilisant le thread actuel comme associé. Voir Tcl_CutChannel et Tcl_SpliceChannel pour plus de détails.

typedef void Tcl_DriverThreadActionProc(
        ClientData instanceData,
        int action);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal.

Ces valeurs peuvent être récupérées avec Tcl_ChannelThreadActionProc, qui retourne un pointeur vers la fonction.

TRUNCATEPROC

Le champ truncateProc contient l'adresse de la fonction appelée par le gestionnaire de canal générique lorsqu'un canal est tronqué à une certaine longueur. Il peut être NULL.

typedef int Tcl_DriverTruncateProc(
        ClientData instanceData,
        Tcl_WideInt length);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal, et length est la nouvelle longueur du fichier sous-jacent, qui ne doit pas être négative. Le résultat doit être 0 en cas de succès ou un code d'erreur (suffisant pour être utilisé avec Tcl_SetErrno) en cas d'échec.

Ces valeurs peuvent être récupérées avec Tcl_ChannelTruncateProc, qui retourne un pointeur vers la fonction.

TCL_BADCHANNELOPTION

Cette procédure génère un message d'erreur "mauvaise option" dans un interpréteur (optionnel). Elle est utilisée par les pilotes de canal lorsqu'une option invalide est demandée. Son but est de concaténer la liste des options génériques à la liste spécifique et de factoriser le message d'erreur des options génériques.

Retourne toujours TCL_ERROR.

Un message d'erreur est généré dans la valeur de résultat de interp pour indiquer qu'une commande a été appelée avec une option invalide. Le message a la forme :

    mauvaise option "blah" : devrait être l'une des
    <...options génériques...>+<...options spécifiques...>
par exemple : 
    mauvaise option "-blah" : devrait être l'une des -blocking,
    -buffering, -buffersize, -eofchar, -translation,
    -peername, ou -sockname
lorsqu'elle est appelée avec optionList égale à "peername sockname".

"blah" est l'argument optionName et "<options spécifiques>" est une liste de mots spécifiques séparés par des espaces. La fonction prend soin d'insérer des signes négatifs avant chaque option, des virgules après et un "ou" avant la dernière option.

OLD CHANNEL TYPES

La structure originale (8.3.1 et versions antérieures) Tcl_ChannelType contenait les champs suivants :

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
} Tcl_ChannelType;

Bien qu'il soit possible de créer des canaux avec la structure ci-dessus, le code interne du canal déterminera la version. Il est essentiel d'utiliser la nouvelle structure Tcl_ChannelType si vous créez un pilote de canal empilé, en raison de problèmes dans l'ancienne implémentation des canaux empilés (8.2.0 à 8.3.1).

Avant 8.4.0 (c'est-à-dire, pendant les dernières versions de 8.3 et le début du cycle de développement de 8.4), la structure Tcl_ChannelType comportait les champs suivants :

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_ChannelTypeVersion version;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Lorsque la structure ci-dessus est enregistrée comme type de canal, le champ version doit toujours être TCL_CHANNEL_VERSION_2.
