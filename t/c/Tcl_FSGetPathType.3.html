DESCRIPTION

Il existe plusieurs raisons pour lesquelles les fonctions de l'API Tcl_FS (par exemple, Tcl_FSAccess et Tcl_FSStat) sont appelées plutôt que les fonctions système comme access et stat directement. Premièrement, ces fonctions sont inter-plateformes, de sorte qu'une extension qui appelle ces fonctions devrait fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige certains bugs dans les appels système. Troisièmement, ces appels de fonction gèrent toute conversion de chemin entre "UTF-8" et le système natif qui pourrait être nécessaire (et peuvent mettre en cache les résultats de ces conversions pour une plus grande efficacité lors d'appels ultérieurs). Quatrièmement, et c'est probablement le plus important, toutes ces fonctions sont "conscientes des fichiers virtuels". Tout système de fichiers virtuel (VFS) enregistré (via Tcl_FSRegister) peut rediriger les opérations d'accès aux fichiers vers des supports ou des méthodes alternatifs. Cela signifie que toutes ces fonctions (et par conséquent les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent fonctionner sur des fichiers qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS) via cette API est automatiquement "consciente des fichiers virtuels". Naturellement, si une extension accède directement au système de fichiers natif (via des API spécifiques au système, par exemple), Tcl ne peut pas intercepter de tels appels.

Si des VFS ont été correctement enregistrés, les fichiers peuvent, par exemple, être distants (par exemple, situés sur un serveur FTP distant) ou archivés (par exemple, situés dans un fichier .zip). Ces systèmes de fichiers enregistrés fournissent une table de fonctions de recherche pour implémenter tout ou partie des fonctionnalités mentionnées ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat abstraient le contenu du tampon struct stat, permettant au même code d'être utilisé à la fois sur des systèmes avec et sans prise en charge des fichiers de plus de 2 Go.

L'API Tcl_FS est Tcl_Obj-ifiée et peut mettre en cache des représentations internes et d'autres chaînes liées aux chemins (par exemple, le répertoire courant). Un effet secondaire de cela est qu'il ne faut pas passer à l'une de ces fonctions une valeur avec un compteur de références égal à zéro. Si de tels appels avaient été traités, ils pourraient causer des erreurs de mémoire (dans certains cas, le code du système de fichiers pourrait supprimer une référence à une telle valeur, il ne faut donc pas supposer qu'après l'un de ces appels, la valeur a toujours un compteur de références égal à zéro - il pourrait avoir été incrémenté). Ou, si la valeur est libérée lors d'une manipulation complexe de valeurs pour s'assurer que le chemin est normalisé et absolu, cela pourrait provoquer un échec de segmentation (ou une erreur d'accès à la mémoire) car la valeur a été libérée au milieu du processus. La leçon pratique à retenir est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect et pourrait entraîner des erreurs de mémoire. Le path doit incrémenter son compteur de références avant de le passer, ou le décrémenter. Pour cette raison, les valeurs avec un compteur de références égal à zéro sont considérées comme invalides en tant que chemins du système de fichiers et tout appel à une fonction de l'API Tcl_FS avec de telles valeurs ne provoquera aucune action.

FONCTIONS DE L'API Tcl_FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés se trouvent sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction de copie de fichier du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la variable globale errno sur le code POSIX EXDEV (qui indique une connexion inter-domaines).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés se trouvent sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction de copie de répertoire du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la variable globale errno sur le code POSIX EXDEV (qui indique une connexion inter-domaines).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction de création de répertoire du système de fichiers qui possède le répertoire.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction de suppression de fichier du système de fichiers.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction de suppression de répertoire du système de fichiers.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés se trouvent sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction de renommage de fichier du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la variable globale errno sur le code POSIX EXDEV (qui indique une connexion inter-domaines).

Tcl_FSListVolumes appelle chaque système de fichiers ayant une fonction list volumes non nulle et lui demande de renvoyer sa liste de volumes racines. Elle accumule les valeurs renvoyées dans une liste qui est renvoyée à l'appelant (avec un compteur de références à zéro).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant le codage identifié par encodingName et évalue son contenu comme un script Tcl. Elle renvoie les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, le codage système est utilisé pour lire le contenu du fichier. Si le fichier ne peut pas être lu, un message d'erreur Tcl est renvoyé pour décrire pourquoi le fichier n'a pas pu être lu. Le caractère de fin de fichier pour les fichiers est \x1A ( ^Z ) pour tous les systèmes. Si vous souhaitez utiliser \x1A dans du code pour des comparaisons de chaînes, vous pouvez l'utiliser, il sera probablement substitué par l'interpréteur Tcl comme \x1A. Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours le codage système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier de code binaire en mémoire et renvoie les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel pathPtr appartient sera appelée. Si ce système de fichiers n'implémente pas cette fonction (bien que de nombreux systèmes virtuels ne le feront pas en raison des limitations de chargement de code dynamique du système d'exploitation), Tcl tentera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile annule cette opération, demandant au processus de supprimer la bibliothèque indiquée par loadHandle de la mémoire. Notez que, contrairement à la commande unload, celle-ci ne donne aucune chance à la bibliothèque de se nettoyer.

Ces deux fonctions renvoient un code de complétion standard Tcl. En cas d'erreur, un message d'erreur est placé dans le résultat de interp.

Le jeton fourni par la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour trouver tous les fichiers qui correspondent à un modèle donné dans un répertoire. La fonction appropriée pour le système de fichiers auquel pathPtr appartient sera appelée.

La valeur renvoyée est un résultat standard Tcl indiquant si une erreur s'est produite lors du globbing. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Notez que le code glob implémente des modèles récursifs en interne, de sorte que cette fonction ne sera appelée qu'avec des modèles simples, qui peuvent être mis en correspondance en utilisant la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment, demandant uniquement des répertoires à renvoyer. Un cas spécial d'appel avec un modèle nul indique que le chemin doit seulement être vérifié pour le bon type.

Tcl_FSLink remplace la version bibliothèque de readlink et l'étend pour prendre en charge la création de liens. La fonction appropriée pour le système de fichiers auquel linkNamePtr appartient sera appelée.

Si toPtr est NULL, une action "lire le lien" sera effectuée. Le résultat est un objet Tcl spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat est tout ce pour quoi il faut appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl doit créer un lien de l'un des types passés dans linkAction. Ce drapeau est une combinaison OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'il y a un choix (c'est-à-dire que plus d'un drapeau est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur renvoyée devrait être toPtr (il est donc déjà la propriété de l'appelant). En cas d'échec, NULL est renvoyé.

Tcl_FSLstat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Aucun droit d'accès au fichier n'est requis pour obtenir ces informations, mais des droits de recherche sont requis pour tous les répertoires mentionnés dans le chemin du fichier. La structure Tcl_StatBuf comprend des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'UID (toujours 0 sous Windows), le GID (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le dernier accès et le type de fichier.

Il est temps, heure de la dernière modification et heure de la dernière modification des métadonnées. Voir PORTABLE STAT RESULT API pour une description de la façon d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSLstat renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé, et aucune information de stat n'est fournie.

Tcl_FSUtime remplace la version bibliothèque de utime.

Ceci renvoie 0 en cas de succès et -1 en cas d'erreur (conformément à la documentation de utime). En cas de succès, la fonction mettra à jour les valeurs « atime » et « mtime » du fichier fourni.

Tcl_FSFileAttrsGet implémente l'accès en lecture pour la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

Si le résultat est TCL_OK, alors une valeur a été placée dans objPtrRef, qui ne sera valide que temporairement (sauf si Tcl_IncrRefCount est appelée).

Tcl_FSFileAttrsSet implémente l'accès en écriture pour la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

Tcl_FSFileAttrStrings implémente une partie de la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La procédure appelée peut soit renvoyer un tableau de chaînes, soit renvoyer NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer qu'il conserve un compteur de références sur la valeur.

Tcl_FSAccess vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est pathname. Si pathname est un lien symbolique sous Unix, alors les permissions du fichier auquel ce lien symbolique fait référence sont testées.

En cas de succès (toutes les permissions demandées sont accordées), zéro est renvoyé. En cas d'erreur (au moins un bit dans mode demandait une permission refusée, ou une autre erreur s'est produite), -1 est renvoyé.

Tcl_FSStat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche pour tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf comprend des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification et l'heure de la dernière modification des métadonnées. Voir PORTABLE STAT RESULT API pour une description de la façon d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSStat renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé, et aucune information de stat n'est fournie.

Tcl_FSOpenFileChannel ouvre un fichier spécifié par pathPtr et renvoie un handle de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est basée sur la procédure fopen de la bibliothèque d'entrée/sortie standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles de la commande Tcl open lors de l'ouverture d'un fichier. En cas d'erreur lors de l'ouverture du canal, Tcl_FSOpenFileChannel renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannel laisse un message d'erreur dans le résultat de interp après toute erreur.

Le canal nouvellement créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez Tcl_RegisterChannel. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, la création du nouveau canal l'assigne également comme remplacement du canal standard.

Tcl_FSGetCwd remplace la version bibliothèque de getcwd.

Il renvoie le répertoire de travail actuel de la bibliothèque Tcl. Celui-ci peut être différent du répertoire de travail de la plateforme native, ce qui se produit lorsque le répertoire de travail actuel ne se trouve pas dans le système de fichiers natif.

Le résultat est un pointeur vers un Tcl_Obj spécifiant le répertoire courant, ou NULL si le répertoire courant n'a pas pu être déterminé. Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de l'interpréteur interp.

Le résultat a déjà vu son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compteur de références doit être décrémenté. Ceci est nécessaire pour des raisons de sécurité des threads, afin de permettre à plusieurs threads d'accéder à cette fonction et aux fonctions associées, tout en garantissant que les résultats sont toujours valides.

Tcl_FSChdir remplace la version bibliothèque de chdir. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl utilisera une combinaison de stat et access pour vérifier si le répertoire existe et a les permissions appropriées.

Pour les résultats, voir la documentation de chdir. En cas de succès, nous conservons un enregistrement du chemin réussi dans cwdPathPtr pour les appels ultérieurs à Tcl_FSGetCwd.

Tcl_FSPathSeparator renvoie le caractère séparateur à utiliser pour l'élément le plus spécifique du chemin spécifié par pathPtr (c'est-à-dire la dernière partie du chemin).

Le séparateur est renvoyé sous forme de Tcl_Obj contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est renvoyé.

Tcl_FSJoinPath prend le Tcl_Obj donné, qui doit être une liste valide (autorisée à avoir un compteur de références de zéro), et renvoie la valeur du chemin donnée en considérant les elements premiers éléments comme des segments de chemin valides (chaque segment de chemin peut être un chemin complet, un chemin partiel ou juste un seul répertoire ou nom de fichier possible). Si un segment de chemin est en fait un chemin absolu, alors tous les segments de chemin précédents sont ignorés. Si elements est inférieur à 0, nous utilisons la liste entière.

Il est possible que la valeur renvoyée soit en fait un élément de la liste donnée, l'appelant doit donc veiller à incrémenter le compteur de références du résultat avant de libérer la liste.

La valeur renvoyée, généralement avec un compteur de références de zéro (mais elle peut être partagée dans certaines conditions), contient le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. En particulier, la valeur renvoyée peut être un élément de la liste donnée, donc la libération de la liste peut libérer prématurément la valeur si aucun compteur de références n'a été pris. Si le nombre d'éléments est zéro, alors la valeur renvoyée sera un Tcl_Obj de chaîne vide.

Tcl_FSSplitPath prend le Tcl_Obj donné, qui devrait être un chemin valide, et renvoie une valeur de liste Tcl contenant chaque segment de ce chemin comme élément. Il renvoie une valeur de liste avec un compteur de références de zéro. Si le lenPtr passé n'est pas NULL, la variable à laquelle il pointe sera mise à jour pour contenir le nombre d'éléments dans la liste renvoyée.

Tcl_FSEqualPaths teste si les deux chemins donnés représentent le même objet du système de fichiers. Il renvoie 1 si les chemins sont égaux et 0 s'ils sont différents. Si l'un des chemins est NULL, 0 est toujours renvoyé.

Tcl_FSGetNormalizedPath tente d'extraire du Tcl_Obj donné une représentation unique de chemin normalisé, dont la valeur de chaîne peut être utilisée comme identifiant unique du fichier.

Il renvoie la valeur du chemin normalisé, détenue par Tcl, ou NULL si le chemin était invalide ou n'a pas pu être converti avec succès. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère en interne sur ces représentations), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques puisse ne pas être la version la plus conviviale d'un chemin. La valeur renvoyée est détenue par Tcl et a une durée de vie équivalente à celle du pathPtr passé (sauf si c'est un chemin relatif, auquel cas la valeur du chemin normalisé peut être libérée à tout moment où le cwd change) - l'appelant peut bien sûr incrémenter le compteur de références s'il souhaite conserver une copie plus longtemps.

Tcl_FSJoinToPath prend la valeur donnée, qui devrait généralement être un chemin valide ou NULL, et y joint le tableau de segments de chemin donnés.

Renvoie une valeur, généralement avec un compteur de références de zéro (mais elle peut être partagée dans certaines conditions), contenant le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. Si l'une des valeurs passées à cette fonction (pathPtr ou éléments de path) a un compteur de références de zéro, elle sera libérée lorsque cette fonction renverra.

Tcl_FSConvertToPathType essaie de convertir le Tcl_Obj donné en un type de chemin Tcl valide, en tenant compte du fait que le cwd a pu changer même si cette valeur est déjà censée être du bon type. Le nom de fichier peut commencer par « ~ » (pour indiquer le répertoire personnel de l'utilisateur actuel) ou « ~<utilisateur> » (pour indiquer le répertoire personnel de n'importe quel utilisateur).

Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), alors TCL_OK est renvoyé. Sinon, TCL_ERROR est renvoyé, et un message d'erreur peut être laissé dans l'interpréteur.

Tcl_FSGetInternalRep extrait la représentation interne d'une valeur de chemin donnée, dans le système de fichiers donné. Si la valeur du chemin appartient à un système de fichiers différent, nous renvoyons NULL. Si la représentation interne est actuellement NULL, nous essayons de la générer, en appelant Tcl_FSCreateInternalRepProc du système de fichiers.

Renvoie NULL ou une représentation de chemin interne valide. Cette représentation interne est mise en cache, de sorte que les appels répétés à cette fonction ne nécessiteront pas de conversions supplémentaires.

Tcl_FSGetTranslatedPath tente d'extraire le chemin traduit du Tcl_Obj donné.

Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), elle est renvoyée. Sinon, NULL sera renvoyé, et un message d'erreur peut être laissé dans l'interpréteur. Un chemin « traduit » est un chemin qui ne contient pas de séquences « ~ » ou « ~utilisateur » (celles-ci ont été développées pour leur représentation actuelle dans le système de fichiers). La valeur renvoyée appartient à l'appelant, qui doit la stocker ou appeler Tcl_DecrRefCount pour s'assurer que la mémoire est libérée. Cette fonction est d'une utilité pratique limitée, et Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des usages.

Tcl_FSGetTranslatedStringPath fait la même chose que Tcl_FSGetTranslatedPath, mais renvoie une chaîne de caractères ou NULL. La chaîne renvoyée est allouée dynamiquement

et détenu par l'appelant, qui doit le stocker ou appeler ckfree pour s'assurer qu'il est libéré. Encore une fois, Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des usages.

Tcl_FSNewNativePath effectue quelque chose comme l'inverse des conversions habituelles obj->chemin->représentation native. Si un code récupère un chemin sous forme native (depuis, par exemple, readlink ou une boîte de dialogue native), et que ce chemin doit être utilisé au niveau Tcl, alors appeler cette fonction est un moyen efficace de créer le type de valeur de chemin approprié.

La valeur résultante est une valeur de type "chemin" pure, qui ne recevra une représentation sous forme de chaîne UTF-8 que si cela est requis par un code Tcl.

Tcl_FSGetNativePath est destiné à être utilisé par les systèmes de fichiers natifs Win/Unix, afin qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un wrapper de commodité autour de Tcl_FSGetInternalRep. Il pourrait être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes (par exemple, sur macOS, une représentation utilisant une structure FSRef de fileSpec serait probablement plus efficace). Sous Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Actuellement, la représentation est simplement une chaîne de caractères qui peut contenir soit le chemin relatif, soit un chemin absolu normalisé complet dans l'encodage natif (des conditions complexes dictent lequel de ceux-ci sera fourni, donc aucun ne peut être garanti, à moins que le chemin ne soit connu pour être absolu). Si vous avez besoin d'un chemin natif qui doit être absolu, vous devriez demander la version native d'un chemin normalisé. Si, pour une raison quelconque, une version non absolue et non normalisée du chemin est nécessaire, elle doit être construite séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache de sorte que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle du pathPtr passé en argument (sauf s'il s'agit d'un chemin relatif, auquel cas la représentation native peut être libérée à tout moment où le cwd change).

Tcl_FSFileSystemInfo renvoie une liste de deux éléments. Le premier élément est le nom du système de fichiers (par exemple, « native », « vfs », « zip », ou « prowrap », peut-être), et le second est le type particulier du chemin donné dans ce système de fichiers (qui dépend du système de fichiers). Le second élément peut être vide si le système de fichiers ne fournit pas de catégorisation supplémentaire des fichiers.

Une valeur de liste valide est renvoyée, sauf si la valeur du chemin n'est pas reconnue, auquel cas NULL sera renvoyé.

Tcl_FSGetFileSystemForPath renvoie un pointeur vers le Tcl_Filesystem qui accepte ce chemin comme valide.

Si aucun système de fichiers n'accepte le chemin, NULL est renvoyé.

Tcl_FSGetPathType détermine si le chemin donné est relatif au répertoire courant, relatif au volume courant, ou absolu.

Il renvoie l'une des valeurs TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, ou TCL_PATH_VOLUME_RELATIVE.

API DU SYSTÈME DE FICHIERS VIRTUEL

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les différentes opérations sur un système de fichiers ; ces opérations sont invoquées si nécessaire par la couche générique, ce qui se produit généralement par le biais des fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un morceau de données optionnel à associer à ce système de fichiers. Lors de l'appel de cette fonction, Tcl attachera le système de fichiers à la liste des systèmes de fichiers connus, et il deviendra pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera renvoyé.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et renvoie TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est renvoyé.

Tcl_FSData renverra le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il renverra NULL.

Tcl_FSMountsChanged est utilisé pour informer le cœur de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

LA STRUCTURE TCL_FILESYSTEM

La structure Tcl_Filesystem contient les champs suivants :

typedef struct Tcl_Filesystem {
    const char *typeName;
    int structureLength;
    Tcl_FSVersion version;
    Tcl_FSPathInFilesystemProc *pathInFilesystemProc;
    Tcl_FSDupInternalRepProc *dupInternalRepProc;
    Tcl_FSFreeInternalRepProc *freeInternalRepProc;
    Tcl_FSInternalToNormalizedProc *internalToNormalizedProc;
    Tcl_FSCreateInternalRepProc *createInternalRepProc;
    Tcl_FSNormalizePathProc *normalizePathProc;
    Tcl_FSFilesystemPathTypeProc *filesystemPathTypeProc;
    Tcl_FSFilesystemSeparatorProc *filesystemSeparatorProc;
    Tcl_FSStatProc *statProc;
    Tcl_FSAccessProc *accessProc;
    Tcl_FSOpenFileChannelProc *openFileChannelProc;
    Tcl_FSMatchInDirectoryProc *matchInDirectoryProc;
    Tcl_FSUtimeProc *utimeProc;
    Tcl_FSLinkProc *linkProc;
    Tcl_FSListVolumesProc *listVolumesProc;
    Tcl_FSFileAttrStringsProc *fileAttrStringsProc;
    Tcl_FSFileAttrsGetProc *fileAttrsGetProc;
    Tcl_FSFileAttrsSetProc *fileAttrsSetProc;
    Tcl_FSCreateDirectoryProc *createDirectoryProc;
    Tcl_FSRemoveDirectoryProc *removeDirectoryProc;
    Tcl_FSDeleteFileProc *deleteFileProc;
    Tcl_FSCopyFileProc *copyFileProc;
    Tcl_FSRenameFileProc *renameFileProc;
    Tcl_FSCopyDirectoryProc *copyDirectoryProc;
    Tcl_FSLstatProc *lstatProc;
    Tcl_FSLoadFileProc *loadFileProc;
    Tcl_FSGetCwdProc *getCwdProc;
    Tcl_FSChdirProc *chdirProc;
} Tcl_Filesystem;

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche générique du système de fichiers pour effectuer la gamme complète des actions liées au système de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (dont la plupart doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni), et fonctions d'efficacité (qui ne doivent être implémentées que si elles peuvent l'être efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces solutions de repli ne sont utilisées que pour gérer les commandes initiées en Tcl, pas en C. Cela signifie que si une commande file rename est émise en Tcl, et que les systèmes de fichiers pertinents n'implémentent pas leur Tcl_FSRenameFileProc, le cœur de Tcl se rabattra sur une combinaison d'autres fonctions de système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a un autre recours). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun de ces recours ne se produit. Ceci est vrai sauf pour les quatre dernières entrées de la table des systèmes de fichiers (lstat, load, getcwd et chdir) pour lesquelles des recours se produisent effectivement au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme Tcl_Obj les prennent sous forme UTF-8. L'API d'infrastructure des systèmes de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

INFRASTRUCTURE DU SYSTÈME DE FICHIERS

Ces champs contiennent des informations de base sur la structure du système de fichiers et les adresses des fonctions utilisées pour associer un système de fichiers particulier à un chemin d'accès, et pour gérer la représentation interne des chemins, par exemple leur copie et leur libération.

NOM DU TYPE

Le champ typeName contient une chaîne terminée par un nul qui identifie le type du système de fichiers implémenté, par exemple « natif », « zip » ou « vfs ».

LONGUEUR STRUCTURE

Le champ structureLength est généralement implémenté comme sizeof(Tcl_Filesystem), et sert à permettre une rétrocompatibilité binaire plus facile si la taille de la structure change dans une future version de Tcl.

VERSION

Le champ version doit être défini à TCL_FILESYSTEM_VERSION_1.

PROC_CHEMIN_DANS_SYSTÈME_FICHIERS

Le champ pathInFilesystemProc contient l'adresse d'une fonction appelée pour déterminer si une valeur de chemin donnée appartient à ce système de fichiers ou non. Tcl n'appellera les autres fonctions du système de fichiers qu'avec un chemin pour lequel cette fonction a retourné TCL_OK. Si le chemin n'appartient pas, -1 doit être retourné (le comportement de Tcl pour toute autre valeur de retour n'est pas défini). Si TCL_OK est retourné, alors le paramètre optionnel de sortie clientDataPtr peut être utilisé pour retourner une représentation interne (spécifique au système de fichiers) du chemin, qui sera mise en cache dans la valeur du chemin, et pourra être récupérée efficacement par les autres fonctions du système de fichiers. Tcl mettra simultanément en cache le fait que ce chemin appartient à ce système de fichiers. De tels caches sont invalidés lorsque des structures de systèmes de fichiers sont ajoutées ou supprimées de la liste interne des systèmes de fichiers connus de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROC_DUPLICATION_REPÉRÉE_INTERNE

Cette fonction crée une copie de la représentation interne d'un chemin, et est appelée lorsque Tcl a besoin de dupliquer une valeur de chemin. Si elle est NULL, Tcl ne copiera tout simplement pas la représentation interne, qui pourrait alors devoir être régénérée plus tard.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

PROC_LIBÉRATION_REPÉRÉE_INTERNE

Libère la représentation interne. Ceci doit être implémenté si les représentations internes nécessitent une libération (c'est-à-dire si de la mémoire est allouée lors de la génération d'une représentation interne), mais peut sinon être NULL.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

PROC_INTERNE_VERS_NORMALISÉ

Fonction pour convertir une représentation interne en un chemin normalisé. Nécessaire uniquement si le système de fichiers crée des valeurs de chemin pures sans représentation textuelle/de chemin. La valeur de retour est une valeur Tcl dont la représentation textuelle est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

PROC_CRÉATION_REPÉRÉE_INTERNE

Fonction pour prendre une valeur de chemin, calculer une représentation interne pour celle-ci, et stocker cette représentation native dans la valeur. Peut être NULL si les chemins n'ont pas de représentation interne, ou si le Tcl_FSPathInFilesystemProc pour ce système de fichiers crée toujours immédiatement une représentation interne pour les chemins qu'il accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

PROC_NORMALISATION_CHEMIN

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations textuelles pour la même valeur de chemin. Dans Tcl, chaque « chemin » doit avoir une représentation textuelle unique « normalisée ». Selon le système de fichiers, il peut y avoir plus d'une représentation textuelle non normalisée qui fait référence à ce chemin (par exemple, un chemin relatif, un chemin avec une casse de caractères différente si le système de fichiers ne respecte pas la casse, un chemin contenant une référence à un répertoire personnel tel que « ~ », un chemin contenant des liens symboliques, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être converti en la valeur qu'il pointe (mais sa casse ou d'autres aspects doivent être rendus uniques). Tous les autres composants du chemin doivent être convertis depuis les liens symboliques. Cette seule exception est requise pour être conforme aux sémantiques de Tcl avec file delete, file rename, file copy opérant sur les liens symboliques. Cette fonction peut être appelée avec nextCheckpoint soit au début du chemin (c'est-à-dire zéro), soit à la fin du chemin, soit à un séparateur de fichier intermédiaire dans le chemin. Elle ne pointera jamais vers une autre position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS DU SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui est censé être utilisé avec l'ensemble complet des commandes Tcl standard doit implémenter toutes celles-ci. Si certaines ne sont pas implémentées, certaines commandes Tcl peuvent échouer lors de l'opération sur des chemins appartenant à ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques n'a pas besoin d'implémenter la fonction readlink, etc. Le noyau Tcl s'attend à ce que les systèmes de fichiers se comportent de cette manière).

PROC_TYPE_CHEMIN_SYSTÈME_FICHIERS

Fonction pour déterminer le type d'un chemin dans ce système de fichiers. Peut être NULL, auquel cas aucune information de type ne sera disponible pour les utilisateurs du système de fichiers. Le « type » est uniquement utilisé à des fins d'information, et doit être retourné comme la représentation textuelle du Tcl_Obj retourné. Une valeur de retour typique pourrait être « en réseau », « zip » ou « ftp ». L'objet Tcl résultant appartient au système de fichiers et Tcl incrémentera donc le compteur de références de cette valeur s'il souhaite en conserver une référence.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

PROC_SÉPARATEUR_SYSTÈME_FICHIERS

Fonction pour retourner le ou les caractères séparateurs pour ce système de fichiers. Ceci n'a besoin d'être implémenté que si le système de fichiers souhaite utiliser un séparateur différent de la chaîne standard « / ». Entre autres utilisations, il est retourné par la commande file separator. La valeur de retour doit être une valeur avec un compteur de références de zéro.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

PROC_STAT

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes au niveau Tcl en dépendent crucialement (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le Tcl_FSStatProc remplit la structure stat statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure stat inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'identifiant utilisateur (toujours 0 sous Windows), l'identifiant de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le temps du dernier accès, le temps de la dernière modification, et le temps du dernier changement de métadonnées.

Si le fichier représenté par pathPtr existe, le Tcl_FSStatProc retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné, et aucune information de stat n'est donnée.

PROC_ACCÈS

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes au niveau Tcl en dépendent crucialement (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

Le Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est dans pathPtr. Si le chemin fait référence à un lien symbolique, alors les permissions du fichier auquel ce lien symbolique fait référence doivent être testées.

En cas de succès (toutes les permissions demandées accordées), zéro est retourné. En cas d'erreur (au moins un bit dans mode demandait une permission refusée, ou une autre erreur s'est produite), -1 est retourné.

PROC_CANAL_OUVERTURE_FICHIER

Fonction pour traiter un appel Tcl_FSOpenFileChannel.

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        const char *mode,
        int permissions);

OPENFILECHANNELPROC

Fonction pour traiter un appel à Tcl_FSOpenFileChannel. Elle doit être implémentée pour tout système de fichiers raisonnable, car toute opération qui nécessite d'ouvrir ou d'accéder au contenu d'un fichier utilisera cette fonction (par exemple, open, encoding et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

La Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et renvoie un handle de canal qui peut être utilisé pour effectuer des entrées/sorties sur le fichier. Cette API est calquée sur la fonction fopen des bibliothèques standard d'E/S POSIX. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier, où l'argument mode est une combinaison des drapeaux POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannelProc renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le canal nouvellement créé ne doit pas être enregistré dans l'interpréteur fourni par Tcl_FSOpenFileChannelProc ; le travail d'enregistrement incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr, a été précédemment fermé, l'action de création du nouveau canal l'attribue également en tant que substitut du canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, la fonctionnalité de globbing et de copie récursive dans le système de fichiers sera perdue (et cela peut affecter des commandes comme encoding names qui utilisent la fonctionnalité de globbing en interne).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit renvoyer tous les fichiers ou répertoires (ou autres objets de système de fichiers) qui correspondent au modèle donné et qui correspondent à la spécification types donnée. Il y a deux façons dont cette fonction peut être appelée. Si pattern est NULL, pathPtr est une spécification complète d'un fichier ou d'un répertoire dont il faut vérifier l'existence et le type. Sinon, pathPtr est un répertoire et la fonction doit rechercher des fichiers ou des répertoires du type correct. Dans tous les cas, pathPtr peut être supposé non NULL et non vide. Il n'est pas actuellement documenté si pathPtr aura un séparateur de fichier à la fin de son nom, le code doit donc être flexible aux deux possibilités.

La valeur de retour est un résultat standard de Tcl indiquant si une erreur s'est produite pendant le processus de mise en correspondance. Les messages d'erreur sont placés dans interp, sauf si interp est NULL, auquel cas aucun message d'erreur n'est généré ; en cas de résultat TCL_OK, les résultats doivent être ajoutés à la valeur donnée dans resultPtr (qui peut être supposée être une liste Tcl non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (ce qui signifie généralement qu'il s'agira de spécifications de chemin absolu). Notez que s'il n'y a pas de correspondances, cela conduit simplement à un résultat vide ; seules les erreurs réelles de fichier ou de système de fichiers qui peuvent survenir pendant le processus de mise en correspondance sont signalées.

La structure Tcl_GlobTypeData passée dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Type mac accepté */
    Tcl_Obj *macType;
    /* Créateur mac accepté */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de gérer correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT sont vrais (et en particulier lorsque les autres drapeaux sont faux). Dans le premier cas, la fonction doit lister les répertoires contenus. Tcl l'utilise pour implémenter le globbing récursif, il est donc crucial que les systèmes de fichiers implémentent correctement la correspondance des répertoires. Dans le second cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage qui se trouvent dans le répertoire donné par pathPtr (et dans ce cas, pathPtr n'a pas besoin d'être à l'intérieur du même système de fichiers - contrairement à tous les autres cas où cette fonction est appelée). Le support de cela est crucial si Tcl veut avoir des transitions fluides entre les systèmes de fichiers.

UTIMEPROC

Fonction pour traiter un appel à Tcl_FSUtime. Elle est requise pour permettre la configuration (pas la lecture) des temps de dernier accès (file mtime), de dernière modification (file atime) et l'implémentation de file copy (open-r, open-w, fcopy).

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les temps d'accès et de modification du fichier spécifié par pathPtr doivent être changés aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec le système utime.

LINKPROC

Fonction pour traiter un appel à Tcl_FSLink. Elle ne doit être implémentée que si le système de fichiers prend en charge les liens, et peut être NULL dans d'autres cas.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est appelée pour lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien ne peut pas être lu. Le résultat appartient entièrement à l'appelant (et doit donc incrémenter son compteur de références avant de le renvoyer). Tout appelant doit appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'en a plus besoin. Si toPtr n'est pas NULL, la fonction doit essayer de créer un lien. Le résultat dans ce cas doit être toPtr si le lien a réussi et NULL dans le cas contraire. Dans ce cas, le résultat n'appartient pas à l'appelant (c'est-à-dire qu'il n'y a aucune manipulation du compteur de références des deux côtés). Voir la documentation de Tcl_FSLink pour l'interprétation correcte des drapeaux de linkAction.

LISTVOLUMESPROC

Fonction pour lister tous les volumes du système de fichiers ajoutés par ce système de fichiers. Elle ne doit être implémentée que si le système de fichiers ajoute des volumes au début du système de fichiers, afin qu'ils puissent être renvoyés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste de volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. La valeur de retour est considérée comme appartenant au système de fichiers (pas au cœur de Tcl), mais Tcl lui attribue un compteur de références. Tcl utilisera le contenu de la liste puis décrémentera ce compteur de références. Cela permet aux systèmes de fichiers de choisir s'ils veulent réellement conserver une "liste globale" de volumes ou non (si non, générer la liste à la volée et la passer à Tcl avec un compteur de références de 1 puis oublier la liste ; si oui, alors incrémenter le compteur de références de leur liste globale et la passer à Tcl qui copiera le contenu puis décrémentera le compteur de références d'où elle provenait).

Par conséquent, Tcl considère les valeurs de retour de cette proc comme étant en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne prendra pas en charge l'instruction file attributes. Cela permet de joindre des informations arbitraires aux fichiers du système de fichiers. Si elle n'est pas implémentée, les méthodes get et set n'ont pas besoin d'être implémentées.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La fonction peut renvoyer un tableau de chaînes ou, alternativement, renvoyer NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois son utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être disposée par Tcl lorsqu'elle est terminée, elle doit avoir un compteur de références de zéro, et si elle ne doit pas être disposée, le système de fichiers doit garantir qu'il renvoie une valeur avec un compteur de références d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsGet, utilisée par file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Renvoie un code de retour standard. La valeur de la propriété d'attribut récupérée, qui correspond à l'élément d'indice index dans la liste renvoyée par Tcl_FSFileAttrStringsProc, est placée dans objPtrRef (si TCL_OK a été renvoyé), et aura probablement un compteur de références de zéro. Dans tous les cas, vous devez stocker cette valeur quelque part (par exemple, dans le résultat de Tcl), ou incrémenter/décrémenter son compteur de références pour vous assurer qu'elle est correctement libérée.

FILEATTRSSETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsSet, utilisée par file attributes. Si le système de fichiers est en lecture seule, cette fonction n'a pas besoin d'être implémentée.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

La propriété de la valeur d'indice index dans la liste renvoyée par Tcl_FSFileAttrStringsProc doit être définie sur la valeur donnée par objPtr.

CREATEDIRECTORYPROC

Fonction pour créer un répertoire dans le système de fichiers. Elle doit être implémentée si le système de fichiers prend en charge les répertoires, sinon elle peut être NULL.

typedef int Tcl_FSCreateDirectoryProc(

CREATEDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSCreateDirectory. Elle doit être implémentée à moins que le système de fichiers ne soit en lecture seule.

typedef int Tcl_FSCreateDirectoryProc(
                        Tcl_Obj *pathPtr);

REMOVEDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSRemoveDirectory. Elle doit être implémentée à moins que le système de fichiers ne soit en lecture seule.

typedef int Tcl_FSRemoveDirectoryProc(

                        int recursive,
                        Tcl_Obj **errorPtr);

La valeur de retour est un résultat standard de Tcl indiquant si une erreur s'est produite pendant le traitement. En cas de succès, le répertoire spécifié par pathPtr doit avoir été supprimé du système de fichiers. Si recursive est donné, un répertoire non vide doit être supprimé sans erreur. Si ce drapeau n'est pas donné, une erreur POSIX "EEXIST" doit être générée si le répertoire est non vide. En cas d'erreur, le nom du fichier ou du répertoire qui a causé l'erreur doit être placé dans errorPtr.

DELETEFILEPROC

Fonction pour traiter un appel Tcl_FSDeleteFile. Elle doit être implémentée à moins que le système de fichiers ne soit en lecture seule.

typedef int Tcl_FSDeleteFileProc(
                        Tcl_Obj *pathPtr);

La valeur de retour est un résultat standard de Tcl indiquant si une erreur s'est produite pendant le traitement. En cas de succès, le fichier spécifié par pathPtr doit avoir été supprimé du système de fichiers. Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non Tcl_FSRemoveDirectoryProc lorsqu'il est nécessaire de les supprimer (même s'il s'agit de liens symboliques vers des répertoires).

FILESYSTEM EFFICIENCY

Ces fonctions n'ont pas besoin d'être implémentées pour un système de fichiers donné car le noyau dispose d'une implémentation de secours. Voir chaque description individuelle pour les conséquences de laisser le champ vide.

LSTATPROC

Fonction pour traiter un appel Tcl_FSLstat. Si elle n'est pas implémentée, Tcl tentera d'utiliser le statProc défini ci-dessus. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut faire la distinction entre les appels stat et lstat.

typedef int Tcl_FSLstatProc(
                        Tcl_Obj *pathPtr,
                        Tcl_StatBuf *statPtr);

Le comportement de cette fonction est très similaire à celui de Tcl_FSStatProc défini ci-dessus, sauf que si elle s'applique à un lien symbolique, elle renvoie des informations sur le lien, et non sur le fichier cible.

COPYFILEPROC

Fonction pour traiter un appel Tcl_FSCopyFile. Si elle n'est pas implémentée, Tcl utilisera open-r, open-w et fcopy comme mécanisme de copie. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyFileProc(
                        Tcl_Obj *srcPathPtr,
                        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat standard de Tcl indiquant si une erreur s'est produite pendant le processus de copie. Notez que destPathPtr est le nom du fichier qui doit devenir la copie de srcPathPtr. Ce n'est jamais le nom d'un répertoire dans lequel srcPathPtr pourrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande file copy au niveau Tcl). Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non copyDirectoryProc lorsqu'il est nécessaire de les copier (même s'il s'agit de liens symboliques vers des répertoires). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de copie de fichiers, l'appel à Tcl_SetErrno(EXDEV) et le renvoi d'un résultat autre que TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

RENAMEFILEPROC

Fonction pour traiter un appel Tcl_FSRenameFile. Si elle n'est pas implémentée, Tcl utilisera une copie suivie d'une suppression. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSRenameFileProc(
                        Tcl_Obj *srcPathPtr,
                        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat standard de Tcl indiquant si une erreur s'est produite pendant le processus de renommage. Si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de file rename, l'appel à Tcl_SetErrno(EXDEV) et le renvoi d'un résultat autre que TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

COPYDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSCopyDirectory. Si elle n'est pas implémentée, Tcl utilisera un mécanisme récursif de file mkdir, file copy. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyDirectoryProc(
                        Tcl_Obj *srcPathPtr,
                        Tcl_Obj *destPathPtr,
                        Tcl_Obj **errorPtr);

La valeur de retour est un résultat standard de Tcl indiquant si une erreur s'est produite pendant le processus de copie. En cas d'erreur, le nom du fichier ou du répertoire qui a causé l'erreur doit être placé dans errorPtr. Notez que destPathPtr est le nom du répertoire qui doit devenir le miroir de srcPathPtr. Ce n'est jamais le nom d'un répertoire dans lequel srcPathPtr pourrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande file copy au niveau Tcl). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de copie de répertoires, l'appel à Tcl_SetErrno(EXDEV) et le renvoi d'un résultat autre que TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

LOADFILEPROC

Fonction pour traiter un appel Tcl_FSLoadFile. Si elle n'est pas implémentée, Tcl utilisera une copie vers un fichier temporaire natif suivie d'un Tcl_FSLoadFile sur cette copie. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut charger du code directement, ou peut être simplement implémentée pour renvoyer TCL_ERROR afin de désactiver le chargement de fichiers sur ce système de fichiers.

typedef int Tcl_FSLoadFileProc(
                        Tcl_Interp *interp,
                        Tcl_Obj *pathPtr,
                        Tcl_LoadHandle *handlePtr,
                        Tcl_FSUnloadFileProc *unloadProcPtr);

Renvoie un code de complétion standard Tcl. En cas d'erreur, un message d'erreur est laissé dans le résultat de l'interp. La fonction charge dynamiquement un fichier binaire en mémoire. En cas de succès, handlePtr doit être rempli avec un jeton pour le fichier chargé dynamiquement, et unloadProcPtr doit être rempli avec l'adresse d'une fonction. La fonction de déchargement sera appelée avec le Tcl_LoadHandle donné comme seul paramètre lorsque Tcl aura besoin de décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle renvoyé est actuellement un jeton qui peut être utilisé dans le TclpFindSymbol privé pour accéder aux fonctions du nouveau code. Chaque système de fichiers peut définir le Tcl_LoadHandle comme il convient. Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de chargement de fichiers, l'appel à Tcl_SetErrno(EXDEV) et le renvoi d'un résultat autre que TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

UNLOADFILEPROC

Fonction pour décharger un fichier qui a été précédemment chargé avec succès. Si le chargement a été implémenté, celle-ci doit également être implémentée s'il y a une action de nettoyage requise.

typedef void Tcl_FSUnloadFileProc(
                        Tcl_LoadHandle loadHandle);

GETCWDPROC

Fonction pour traiter un appel Tcl_FSGetCwd. La plupart des systèmes de fichiers n'ont pas besoin de l'implémenter. Elle peut être NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
                        Tcl_Interp *interp);

Si le système de fichiers prend en charge une notion native de répertoire de travail courant (qui pourrait changer indépendamment de Tcl), cette fonction doit renvoyer ce répertoire de travail courant sous forme de résultat, ou NULL si le répertoire de travail courant ne peut pas être déterminé (par exemple, l'utilisateur n'a pas les permissions appropriées sur le répertoire de travail courant). Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de l'interp.

CHDIRPROC

Fonction pour traiter un appel Tcl_FSChdir. Si les systèmes de fichiers ne l'implémentent pas, elle est émulée par une série de vérifications d'accès aux répertoires. Sinon, les systèmes de fichiers qui l'implémentent ne doivent renvoyer un résultat positif que si pathPtr est un répertoire valide et accessible sur leur système de fichiers. Ils ne doivent pas mémoriser le résultat, car cela sera automatiquement mémorisé par Tcl_FSGetCwd. Les systèmes de fichiers réels doivent effectuer l'action correcte (c'est-à-dire appeler l'API système correspondant chdir).

typedef int Tcl_FSChdirProc(
                        Tcl_Obj *pathPtr);

La Tcl_FSChdirProc change le répertoire de travail actuel de l'application pour la valeur spécifiée dans pathPtr. La fonction renvoie -1 en cas d'erreur ou 0 en cas de succès.
