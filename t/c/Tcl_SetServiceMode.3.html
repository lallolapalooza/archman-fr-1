INTRODUCTION

Les interfaces décrites ici sont utilisées pour personnaliser la boucle d'événements Tcl. Les deux personnalisations les plus courantes sont l'ajout de nouvelles sources d'événements et la fusion de la boucle d'événements Tcl avec une autre boucle d'événements, telle que celle fournie par une application dans laquelle Tcl est intégrée. Chacune de ces tâches est décrite dans une section distincte ci-dessous.

Les procédures de cette entrée manuelle sont les éléments constitutifs à partir desquels le notificateur d'événements Tcl est construit. Le notificateur d'événements est la couche la plus basse du mécanisme d'événements Tcl. Il se compose de trois choses :

[1]
Sources d'événements : celles-ci représentent les moyens par lesquels les événements peuvent être générés. Par exemple, il existe une source d'événements de minuteur qui implémente la procédure Tcl_CreateTimerHandler et la commande after, et il existe une source d'événements de fichier qui implémente la procédure Tcl_CreateFileHandler sur les systèmes Unix. Une source d'événements doit travailler avec le notificateur pour détecter les événements aux moments opportuns, les enregistrer dans la file d'attente des événements et informer éventuellement le logiciel de niveau supérieur qu'ils se sont produits. Les procédures Tcl_CreateEventSource, Tcl_DeleteEventSource, et Tcl_SetMaxBlockTime, Tcl_QueueEvent, et Tcl_DeleteEvents sont principalement utilisées par les sources d'événements.
[2]
La file d'attente d'événements : pour les applications non multithreadées, il existe une seule file d'attente pour toute l'application, contenant les événements qui ont été détectés mais pas encore traités. Les sources d'événements placent les événements dans la file d'attente afin qu'ils puissent être traités dans l'ordre à des moments appropriés pendant la boucle d'événements. La file d'attente d'événements garantit une discipline équitable de traitement des événements, de sorte qu'aucune source d'événement ne puisse affamer les autres. Elle permet également de sauvegarder les événements pour un traitement ultérieur. Les applications multithreadées fonctionnent de manière similaire, sauf qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. Tcl_QueueEvent est utilisé (principalement par les sources d'événements) pour ajouter des événements à la file d'attente des événements et Tcl_DeleteEvents est utilisé pour supprimer des événements de la file d'attente sans les traiter. Dans une application multithreadée, Tcl_QueueEvent ajoute un événement à la file d'attente du thread courant, et Tcl_ThreadQueueEvent ajoute un événement à une file d'attente dans un thread spécifique.
[3]
La boucle d'événements : pour détecter et traiter les événements, l'application entre dans une boucle qui attend que les événements se produisent, les place dans la file d'attente des événements, puis les traite. La plupart des applications le feront en appelant la procédure Tcl_DoOneEvent, qui est décrite dans une entrée manuelle distincte.

La plupart des applications Tcl n'ont pas à se soucier des détails internes du notificateur Tcl. Cependant, le notificateur dispose désormais de suffisamment de flexibilité pour être redirigé soit vers une nouvelle plateforme, soit pour utiliser une boucle d'événements externe (telle que la boucle d'événements Motif, lorsque Tcl est intégrée dans une application Motif). Les procédures Tcl_WaitForEvent et Tcl_SetTimer sont normalement implémentées par Tcl, mais peuvent être remplacées par de nouvelles versions pour rediriger le notificateur (Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler, et Tcl_DeleteFileHandler doivent également être remplacées ; voir CRÉER UN NOUVEAU NOTIFICATEUR ci-dessous pour plus de détails). Les procédures Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode, et Tcl_SetServiceMode sont fournies pour aider à connecter la boucle d'événements Tcl à une boucle d'événements externe telle que celle de Motif.

BASES DU NOTIFICATEUR

La manière la plus simple de comprendre le fonctionnement du notificateur est d'examiner ce qui se passe lorsque Tcl_DoOneEvent est appelée. Tcl_DoOneEvent reçoit un argument flags qui indique quels types d'événements peuvent être traités et s'il faut bloquer si aucun événement n'est prêt. Tcl_DoOneEvent effectue les actions suivantes :

[1]
Vérifie la file d'attente des événements pour voir si elle contient des événements qui peuvent être traités. Si c'est le cas, traite le premier événement possible, le retire de la file d'attente et retourne. Pour ce faire, elle appelle Tcl_ServiceEvent et lui passe l'argument flags.
[2]
Se prépare à bloquer pour un événement. Pour ce faire, Tcl_DoOneEvent invoque une procédure setup dans chaque source d'événements. La source d'événements effectuera l'initialisation spécifique à la source d'événements et appellera éventuellement Tcl_SetMaxBlockTime pour limiter la durée pendant laquelle Tcl_WaitForEvent bloquera si aucun nouvel événement ne se produit.
[3]
Appelle Tcl_WaitForEvent. Cette procédure est implémentée différemment selon les plateformes ; elle attend qu'un événement se produise, en fonction des informations fournies par les sources d'événements. Elle peut provoquer le blocage de l'application si timePtr spécifie un intervalle autre que 0. Tcl_WaitForEvent retourne lorsqu'un événement s'est produit, tel qu'un fichier devenant lisible ou l'expiration de l'intervalle spécifié par timePtr. S'il n'y a aucun événement pour Tcl_WaitForEvent à attendre, de sorte qu'elle bloquerait indéfiniment, elle retourne immédiatement et Tcl_DoOneEvent retourne 0.
[4]
Appelle une procédure check dans chaque source d'événements. La procédure check détermine si des événements d'intérêt pour cette source se sont produits. Si c'est le cas, les événements sont ajoutés à la file d'attente des événements.
[5]
Vérifie la
file d'attente d'événements pour voir s'il contient des événements qui peuvent être traités. Si c'est le cas, traiter le premier événement possible, le supprimer de la file d'attente et retourner.
[6]
Vérifier s'il y a des rappels inactifs en attente. Si c'est le cas, invoquer tous ces rappels et retourner.
[7]
Retourner 0 pour indiquer qu'aucun événement n'était prêt, ou revenir à l'étape [2] si le blocage a été demandé par l'appelant.

CRÉATION D'UNE NOUVELLE SOURCE D'ÉVÉNEMENT

Une source d'événements se compose de trois procédures invoquées par le répartiteur, plus des procédures C supplémentaires qui sont invoquées par du code de niveau supérieur pour organiser des rappels pilotés par les événements. Les trois procédures appelées par le répartiteur comprennent les procédures de configuration et de vérification décrites ci-dessus, plus une procédure supplémentaire qui est invoquée lorsqu'un événement est retiré de la file d'attente d'événements pour traitement.

La procédure Tcl_CreateEventSource crée une nouvelle source d'événements. Ses arguments spécifient la procédure de configuration et la procédure de vérification pour la source d'événements. SetupProc doit correspondre au prototype suivant :

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

L'argument clientData sera le même que l'argument clientData passé à Tcl_CreateEventSource ; il est typiquement utilisé pour pointer vers des informations privées gérées par la source d'événements. L'argument flags sera le même que l'argument flags passé à Tcl_DoOneEvent, sauf qu'il ne sera jamais 0 (Tcl_DoOneEvent remplace 0 par TCL_ALL_EVENTS). Flags indique quels types d'événements doivent être pris en compte ; si le bit correspondant à cette source d'événements n'est pas défini, la source d'événements doit retourner immédiatement sans rien faire. Par exemple, la source d'événements de fichier vérifie le bit TCL_FILE_EVENTS.

Le rôle de SetupProc est de s'assurer que l'application se réveille lorsque des événements du type souhaité se produisent. Ceci est typiquement fait d'une manière dépendante de la plateforme. Par exemple, sous Unix, une source d'événements peut appeler Tcl_CreateFileHandler ; sous Windows, elle peut demander une notification avec un événement Windows. Pour les sources d'événements pilotées par minuterie, telles que les événements de minuterie ou tout événement interrogé, la source d'événements peut appeler Tcl_SetMaxBlockTime pour forcer l'application à se réveiller après un délai spécifié, même si aucun événement ne s'est produit. Si aucune source d'événements n'appelle Tcl_SetMaxBlockTime, alors Tcl_WaitForEvent attendra aussi longtemps que nécessaire pour qu'un événement se produise ; sinon, elle n'attendra que la durée de l'intervalle le plus court passé à Tcl_SetMaxBlockTime par l'une des sources d'événements. Si une source d'événements sait qu'elle a déjà des événements prêts à être signalés, elle peut demander un temps de blocage nul. Par exemple, la procédure de configuration de la source d'événements X vérifie s'il y a déjà des événements mis en file d'attente. S'il y en a, elle appelle Tcl_SetMaxBlockTime avec un temps de blocage de 0 afin que Tcl_WaitForEvent ne bloque pas s'il n'y a pas de nouvelles données sur la connexion X. L'argument timePtr de Tcl_WaitForEvent pointe vers une structure qui décrit un intervalle de temps en secondes et en microsecondes :

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

Le champ usec doit être inférieur à 1000000.

Les informations fournies à Tcl_SetMaxBlockTime ne sont utilisées que pour le prochain appel à Tcl_WaitForEvent ; elles sont supprimées après le retour de Tcl_WaitForEvent. La prochaine fois qu'une attente d'événement sera effectuée, chacune des procédures de configuration des sources d'événements sera à nouveau appelée, et elles pourront spécifier de nouvelles informations pour cette attente d'événement.

Si l'application utilise une boucle d'événements externe plutôt que Tcl_DoOneEvent, les sources d'événements peuvent avoir besoin d'appeler Tcl_SetMaxBlockTime à d'autres moments. Par exemple, si un nouveau gestionnaire d'événements est enregistré qui doit interroger les événements, la source d'événements peut appeler Tcl_SetMaxBlockTime pour définir le temps de blocage à zéro afin de forcer la boucle d'événements externe à appeler Tcl. Dans ce cas, Tcl_SetMaxBlockTime invoque Tcl_SetTimer avec l'intervalle le plus court vu depuis le dernier appel à Tcl_DoOneEvent ou Tcl_ServiceAll.

En plus de la procédure générique Tcl_SetMaxBlockTime, d'autres procédures spécifiques à la plateforme peuvent également être disponibles pour setupProc, s'il existe des informations supplémentaires nécessaires à Tcl_WaitForEvent sur cette plateforme. Par exemple, sur les systèmes Unix, l'interface Tcl_CreateFileHandler peut être utilisée pour attendre les événements de fichier.

La deuxième procédure fournie par chaque source d'événements est sa procédure de vérification, indiquée par l'argument checkProc de Tcl_CreateEventSource. CheckProc doit correspondre au prototype suivant :

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Les arguments de cette procédure sont les mêmes que ceux de setupProc. CheckProc est invoqué par Tcl_DoOneEvent après qu'elle a attendu des événements. Vraisemblablement, au moins une source d'événements est maintenant préparée à mettre en file d'attente un événement. Tcl_DoOneEvent appelle chaque source d'événements à tour de rôle, leur donnant ainsi une chance de mettre en file d'attente tous les événements qui sont prêts. La procédure de vérification fait deux choses. Premièrement, elle doit vérifier si des événements se sont déclenchés. Différentes sources d'événements font cela de différentes manières.

Si la procédure de vérification d'une source d'événements détecte un événement intéressant, elle doit ajouter l'événement à la file d'attente d'événements de Tcl. Pour ce faire, la source d'événements appelle Tcl_QueueEvent. L'argument evPtr est un pointeur vers une structure allouée dynamiquement contenant l'événement (voir ci-dessous pour plus d'informations sur les problèmes de gestion de la mémoire). Chaque source d'événements peut définir sa propre structure d'événement avec toutes les informations pertinentes pour cette source d'événements. Cependant, le premier élément de la structure doit être une structure de type Tcl_Event, et l'adresse de cette structure est utilisée lors de la communication entre la source d'événements et le reste du répartiteur. Un Tcl_Event a la définition suivante :

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La source d'événements doit remplir le champ proc de l'événement avant d'appeler Tcl_QueueEvent. Le champ nextPtr est utilisé pour lier les événements dans la file d'attente et ne doit pas être modifié par la source d'événements.

Un événement peut être ajouté à la file d'attente à l'une des trois positions, en fonction de l'argument position de Tcl_QueueEvent :

TCL_QUEUE_TAIL
Ajoute l'événement à la fin de la file d'attente, de sorte que tous les autres événements en attente soient traités en premier. C'est presque toujours la bonne place pour les nouveaux événements.
TCL_QUEUE_HEAD
Ajoute l'événement au début de la file d'attente, de sorte qu'il soit traité avant tous les autres événements mis en file d'attente.
TCL_QUEUE_MARK
Ajoute l'événement au début de la file d'attente, à moins qu'il n'y ait d'autres événements au début dont la position est TCL_QUEUE_MARK ; si c'est le cas, ajoute le nouvel événement juste après tous les autres événements TCL_QUEUE_MARK. Cette valeur de position est utilisée pour insérer une séquence ordonnée d'événements au début de la file d'attente, tels qu'une série d'événements Enter et Leave synthétisés lors d'une opération de capture (grab) ou de libération (ungrab) dans Tk.

Lorsqu'il est temps de traiter un événement de la file d'attente (étapes 1 et 4 ci-dessus), Tcl_ServiceEvent invoquera la procédure proc spécifiée dans la première structure Tcl_Event mise en file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

Le premier argument de proc est un pointeur vers l'événement, qui sera le même que le premier argument de l'appel à Tcl_QueueEvent qui a ajouté l'événement à la file d'attente. Le second argument de proc est l'argument flags pour l'appel actuel à Tcl_ServiceEvent ; ceci est utilisé par la source d'événements pour retourner immédiatement si ses événements ne sont pas pertinents.

Il appartient à proc de gérer l'événement, typiquement en invoquant une ou plusieurs commandes Tcl ou des rappels au niveau C. Une fois que la source d'événements a fini de gérer l'événement, elle retourne 1 pour indiquer que l'événement peut être retiré de la file d'attente. Si pour une raison quelconque la source d'événements décide que l'événement ne peut pas être traité à ce moment-là, elle peut retourner 0 pour indiquer que l'événement doit être différé pour un traitement ultérieur ; dans ce cas, Tcl_ServiceEvent passera à l'événement suivant dans la file d'attente et tentera de le traiter. Il y a plusieurs raisons pour lesquelles une source d'événements pourrait différer un événement. Une possibilité est que les événements de ce type soient exclus par l'argument flags. Par exemple, la source d'événements de fichier retournera toujours 0 si le bit TCL_FILE_EVENTS n'est pas défini dans flags. Un autre exemple de différé d'événements se produit dans Tk si Tk_RestrictEvents a été invoqué pour différer certains types d'événements de fenêtre.

Lorsque proc retourne 1, Tcl_ServiceEvent retirera l'événement de la file d'attente d'événements et libérera sa mémoire. Notez que la mémoire pour un événement doit être allouée par la source d'événements (en utilisant Tcl_Alloc ou la macro Tcl ckalloc) avant d'appeler Tcl_QueueEvent, mais elle sera libérée par Tcl_ServiceEvent, et non par la source d'événements.

Les applications multithread fonctionnent de manière similaire, sauf qu'il existe une file d'attente d'événements séparée pour chaque thread contenant un interpréteur Tcl. L'appel de Tcl_QueueEvent dans une application multithread ajoute un événement à la file d'attente du thread courant. Pour ajouter un événement à la file d'attente d'un autre thread, utilisez Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent accepte comme argument un argument Tcl_ThreadId, qui identifie de manière unique un thread dans une application Tcl. Pour obtenir le Tcl_ThreadId du thread courant, utilisez la procédure Tcl_GetCurrentThread. (Un thread devrait alors passer cet identifiant à d'autres threads pour que ceux-ci puissent ajouter des événements à sa file d'attente.) Après avoir ajouté un événement à la file d'attente d'un autre thread, vous devez ensuite généralement appeler Tcl_ThreadAlert pour « réveiller » le répartiteur de ce thread afin de le notifier du nouvel événement.

Tcl_DeleteEvents peut être utilisé pour supprimer explicitement un ou plusieurs événements de la file d'attente d'événements. Tcl_DeleteEvents appelle proc pour chaque événement dans la file d'attente, supprimant ceux pour lesquels la procédure retourne 1. Les événements pour lesquels la procédure retourne 0 restent dans la file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

L'argument clientData sera le même que l'argument clientData passé à Tcl_DeleteEv

CRÉATION D'UN NOUVEAU NOTIFICATEUR

Le notificateur inclut toutes les procédures décrites dans ce manuel, plus Tcl_DoOneEvent et Tcl_Sleep, disponibles sur toutes les plateformes, et Tcl_CreateFileHandler et Tcl_DeleteFileHandler, spécifiques à Unix. La plupart de ces procédures sont génériques, car elles sont identiques pour tous les notificateurs. Cependant, aucune des procédures n'est dépendante du notificateur : Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler et Tcl_ServiceModeHook. Pour prendre en charge un nouveau système d'exploitation ou intégrer Tcl avec une boucle d'événements spécifique à une application, vous devez écrire de nouvelles versions de ces procédures.

Tcl_InitNotifier initialise l'état du notificateur et renvoie un handle vers l'état du notificateur. Tcl appelle cette procédure lors de l'initialisation d'un environnement Tcl. De même, Tcl_FinalizeNotifier finalise le notificateur, et est appelée par Tcl_Finalize lors de la finalisation d'un environnement Tcl.

Tcl_WaitForEvent est la procédure la plus bas niveau du notificateur ; elle est responsable de l'attente d'un événement « intéressant » ou d'un délai donné. Avant que Tcl_WaitForEvent ne soit invoquée, chaque procédure de source d'événements aura été appelée. L'argument timePtr de Tcl_WaitForEvent indique le temps maximum pouvant être attendu pour un événement, basé sur les appels à Tcl_SetMaxBlockTime effectués par les procédures de configuration et sur d'autres informations (comme le bit TCL_DONT_WAIT dans flags).

Idéalement, Tcl_WaitForEvent ne devrait attendre qu'un événement ; elle ne devrait pas le traiter du tout. Les notificateurs traiteront ensuite les événements bruts et créeront des Tcl_Events dans la file d'attente des événements de leurs checkProc. Cependant, sur certains systèmes (comme Windows), cela n'est pas possible ; les événements peuvent être traités dans Tcl_WaitForEvent, y compris la mise en file d'attente des Tcl_Events et plus encore (par exemple, les callbacks pour les widgets natifs). La valeur de retour de Tcl_WaitForEvent doit être 0, 1 ou -1. Sur les plateformes comme Windows, où les événements sont traités dans Tcl_WaitForEvent, une valeur de retour de 1 signifie qu'il peut y avoir d'autres événements en attente non traités. C'est un signal pour l'appelant qu'il doit rappeler Tcl_WaitForEvent pour traiter tous les événements en attente. Une valeur de retour de 0 indique que rappeler Tcl_WaitForEvent n'aura aucun effet : il peut s'agir d'un système où Tcl_WaitForEvent attend simplement sans traiter les événements, ou Tcl_WaitForEvent sait avec certitude qu'il n'y a plus d'événements en attente (par exemple, en raison du temps écoulé). Enfin, une valeur de retour de -1 signifie que la boucle d'événements n'est plus opérationnelle et que l'application doit se débarrasser et se terminer. Sous Windows, cela se produit lorsqu'un message WM_QUIT est reçu ; sous Unix, lorsque Tcl_WaitForEvent attend éternellement en raison du manque de sources d'événements actives et que le délai d'attente est infini).

Tcl_AlertNotifier est utilisé dans les applications multithreadées pour permettre à n'importe quel thread de « réveiller » le notificateur afin de l'alerter de nouveaux événements dans sa file d'attente. Tcl_AlertNotifier nécessite comme argument le handle du notificateur renvoyé par Tcl_InitNotifier.

Si le notificateur doit être utilisé avec une boucle d'événements externe, il doit également prendre en charge l'interface de Tcl_SetTimer. Tcl_SetTimer est appelé par Tcl_SetMaxBlockTime lorsque le temps de blocage maximal a été réduit. Tcl_SetTimer doit organiser que la boucle d'événements externe appelle Tcl_ServiceAll même si aucun événement ne s'est produit. Cette interface est nécessaire car Tcl_WaitForEvent n'est pas appelée lorsqu'il y a une boucle d'événements externe. Si le notificateur ne doit être utilisé qu'à partir de Tcl_DoOneEvent, alors Tcl_SetTimer ne doit rien faire.

Tcl_ServiceModeHook est appelé par la partie indépendante du notificateur lorsque le code client appelle Tcl_SetServiceMode. Ce hook est fourni pour prendre en charge les opérations des systèmes d'exploitation qui nécessitent un traitement spécial des événements lorsque l'application est dans une boucle d'événements modale (comme le notificateur Windows, par exemple, utilise ce hook pour créer une fenêtre de communication).

Sur les systèmes Unix, les sources d'événements de fichiers nécessitent également le support du notificateur. Les sources d'événements de fichiers se composent des procédures Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont décrites dans la page de manuel de Tcl_CreateFileHandler.

Les interfaces de Tcl_Sleep et Tcl_DoOneEvent sont décrites dans leurs pages de manuel respectives.

La manière la plus simple de créer un nouveau notificateur est d'examiner le code d'un notificateur existant, par exemple dans les fichiers unix/tclUnixNotfy.c ou win/tclWinNotify.c dans la distribution du code source de Tcl.

REMPLACEMENT DU NOTIFICATEUR

Un notificateur écrit selon les conventions ci-dessus peut également être installé dans un processus déjà en cours d'exécution à la place du notificateur standard. Ce mécanisme est utilisé pour qu'un seul exécutable puisse être utilisé (avec le notificateur standard) comme programme autonome et être réutilisé (avec un notificateur remplacé dans une extension chargeable) comme une extension d'un autre programme, comme un plugin de navigateur Web.

Pour ce faire, l'extension appelle Tcl_SetNotifier, en passant un pointeur vers une structure Tcl_NotifierProcs. La structure a la disposition suivante :

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Après avoir appelé Tcl_SetNotifier, les pointeurs de la structure Tcl_NotifierProcs remplacent tout notificateur qui a été installé dans le processus.

Il est exceptionnellement mauvais de remplacer un notificateur en cours d'exécution. Normalement, Tcl_SetNotifier doit être appelé avant le premier appel à Tcl_InitNotifier.

BOUCLES D'ÉVÉNEMENTS EXTERNES

Les interfaces du notificateur sont conçues pour que Tcl puisse être intégré dans des applications qui ont leurs propres boucles d'événements privées. Dans ce cas, l'application n'appelle pas Tcl_DoOneEvent sauf dans des cas récursifs, comme les appels aux commandes Tcl update ou vwait. La majeure partie du temps est passée dans la boucle d'événements externe de l'application. Dans ce cas, le notificateur doit organiser que la boucle d'événements externe s'appelle elle-même lorsqu'un événement se produit sur l'une des sources d'événements Tcl. Ces callbacks doivent organiser que les événements Tcl appropriés soient placés dans la file d'attente des événements Tcl.

En conséquence du traitement des événements détectés dans la boucle d'événements externe principale, Tcl peut appeler Tcl_DoOneEvent pour initier une boucle d'événements récursive dans des commandes comme vwait. Tcl_DoOneEvent appelle la boucle d'événements externe, ce qui entraîne des callbacks comme décrit dans la section précédente, qui aboutissent à des appels à Tcl_ServiceAll. Cependant, dans ces cas, il est inapproprié de servir les événements dans Tcl_ServiceAll. Servir les événements là est inutile car le contrôle est immédiatement renvoyé à la boucle d'événements externe, donc le contrôle est renvoyé à Tcl_DoOneEvent, qui peut servir les événements. De plus, Tcl_DoOneEvent est conçu pour servir un seul événement, tandis que Tcl_ServiceAll sert normalement tous les événements en attente. Pour gérer cette situation, Tcl_DoOneEvent définit un drapeau pour Tcl_ServiceAll qui le fait retourner sans servir d'événements. Ce drapeau s'appelle le mode de service ; Tcl_DoOneEvent le restaure à sa valeur précédente avant de retourner.

Dans certains cas, il peut être nécessaire de servir les événements même si Tcl_ServiceAll a été appelé à partir de Tcl_DoOneEvent. Cela se produit lorsqu'une autre boucle d'événements récursive est invoquée via un gestionnaire d'événements appelé par Tcl_DoOneEvent (comme un faisant partie d'un widget natif). Dans ce cas, Tcl_DoOneEvent pourrait ne pas avoir l'occasion de servir les événements, donc Tcl_ServiceAll doit les servir tous. Toute boucle d'événements récursive qui appelle une boucle d'événements externe au lieu de Tcl_DoOneEvent doit réinitialiser le mode de service afin que tous les événements soient traités dans Tcl_ServiceAll. Cela est réalisé en appelant la procédure Tcl_SetServiceMode. Si Tcl_SetServiceMode se voit passer TCL_SERVICE_NONE, alors les appels à Tcl_ServiceAll retourneront immédiatement sans traiter aucun événement. Si Tcl_SetServiceMode se voit passer TCL_SERVICE_ALL, alors les appels à Tcl_ServiceAll se comporteront normalement. Tcl_SetServiceMode renvoie la valeur précédente du mode de service, qui doit être restaurée lorsque la boucle d'événements récursive se termine. Tcl_GetServiceMode renvoie la valeur actuelle du mode de service.

#include <tcl.h>

  • TCL_SERVICE_ALL : Traite tous les événements en attente.

INTRODUCTION

Le gestionnaire d'événements Tcl est le mécanisme par lequel Tcl gère les événements d'entrée provenant de diverses sources, telles que les entrées de clavier, les événements de la souris, les événements de temporisation, les événements de fichier, etc. Le gestionnaire d'événements Tcl est responsable de la surveillance de ces sources d'événements et de la notification des gestionnaires d'événements appropriés lorsque des événements se produisent.

La fonction Tcl_SetServiceMode permet aux développeurs de contrôler le comportement du gestionnaire d'événements Tcl en spécifiant le mode de service. Le mode de service détermine quels types d'événements le gestionnaire d'événements traitera.

BASES DU GESTIONNAIRE D'ÉVÉNEMENTS

Le gestionnaire d'événements Tcl fonctionne selon une boucle événementielle. La boucle événementielle est responsable de la vérification continue des événements en attente provenant de diverses sources d'événements. Lorsqu'un événement se produit, il est placé dans la file d'attente des événements. La boucle événementielle extrait ensuite les événements de la file d'attente et les traite.

Les sources d'événements sont les mécanismes qui génèrent des événements. Les sources d'événements courantes dans Tcl incluent :

  • Événements de fichier : se produisent lorsque des données sont disponibles sur un descripteur de fichier, ou lorsqu'un descripteur de fichier devient prêt pour l'écriture.
  • Événements de temporisation : se produisent après un délai spécifié.
  • Événements de service : se produisent lorsque le système est inactif (idle).
  • Événements d'entrée utilisateur : tels que les frappes de touches et les mouvements de souris.

La file d'attente des événements est une structure de données qui stocke les événements en attente d'être traités. Les événements sont ajoutés à la file d'attente au fur et à mesure de leur production et retirés de la file d'attente pour traitement dans l'ordre où ils ont été reçus (FIFO).

CRÉER UNE NOUVELLE SOURCE D'ÉVÉNEMENTS

Pour créer une nouvelle source d'événements dans Tcl, vous devez enregistrer une nouvelle source d'événements auprès du gestionnaire d'événements Tcl. Cela implique généralement la création d'une structure Tcl_EventHandle et son enregistrement à l'aide de la fonction Tcl_CreateFileHandler ou d'une fonction similaire pour d'autres types d'événements.

La structure Tcl_EventHandle contient des informations sur la source de l'événement, telles que le descripteur de fichier associé ou l'identifiant de la temporisation. Elle contient également un pointeur vers une fonction de rappel qui sera appelée lorsque l'événement se produira.

CRÉER UN NOUVEAU GESTIONNAIRE D'ÉVÉNEMENTS

Dans la plupart des cas, vous n'avez pas besoin de créer un nouveau gestionnaire d'événements. Tcl fournit un gestionnaire d'événements par défaut qui gère la plupart des besoins. Cependant, si vous avez des exigences spécifiques ou si vous intégrez Tcl dans une application existante avec sa propre boucle événementielle, vous pourriez avoir besoin de créer un gestionnaire d'événements personnalisé.

La création d'un gestionnaire d'événements personnalisé implique la mise en œuvre de la logique de la boucle événementielle et l'intégration avec le système de gestion d'événements Tcl. Cela peut être une tâche complexe qui nécessite une compréhension approfondie du fonctionnement interne de Tcl.

REMPLACER LE GESTIONNAIRE D'ÉVÉNEMENTS

Il est possible de remplacer le gestionnaire d'événements Tcl par défaut par une implémentation personnalisée. Cela peut être utile dans des scénarios où Tcl est intégré dans une application existante qui possède déjà sa propre boucle événementielle. En remplaçant le gestionnaire d'événements, vous pouvez vous assurer que Tcl s'intègre de manière transparente avec la boucle événementielle de l'application.

Le remplacement du gestionnaire d'événements implique généralement l'utilisation de fonctions telles que Tcl_SetEventLoopProc pour enregistrer votre propre procédure de boucle événementielle. Votre procédure de boucle événementielle personnalisée sera responsable de la surveillance des événements et de leur transmission au système de gestion d'événements Tcl pour traitement.

BOUCLES D'ÉVÉNEMENTS EXTERNES

Tcl peut être intégré dans des applications qui ont leurs propres boucles d'événements externes. Dans de tels cas, Tcl doit être configuré pour fonctionner avec la boucle d'événements externe au lieu d'utiliser sa propre boucle événementielle par défaut. Cela peut être réalisé en configurant Tcl pour exécuter des événements dans le cadre de la boucle d'événements externe.

Lors de l'utilisation de boucles d'événements externes, il est important de s'assurer que Tcl est correctement initialisé et que les gestionnaires d'événements Tcl sont enregistrés auprès de la boucle d'événements externe. Cela garantit que les événements Tcl sont traités en temps voulu et que Tcl interagit correctement avec le reste de l'application.
