DESCRIPTION

Il y a plusieurs raisons d'appeler les fonctions de l'API Tcl_FS (par ex., Tcl_FSAccess et Tcl_FSStat) plutôt que d'appeler directement des fonctions de niveau système comme access et stat. Premièrement, elles fonctionneront sur plusieurs plateformes, donc une extension qui les appelle devrait fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige certains bugs dans les appels de niveau système. Troisièmement, ces appels de fonction gèrent toutes les conversions de chemin « Utf vers natif de la plateforme » qui peuvent être requises (et peuvent mettre en cache les résultats de ces conversions pour une plus grande efficacité lors des appels ultérieurs). Quatrièmement, et peut-être le plus important, toutes ces fonctions sont « conscientes des systèmes de fichiers virtuels ». Tout système de fichiers virtuel (VFS pour faire court) qui a été enregistré (via Tcl_FSRegister) peut rediriger l'accès aux fichiers vers des supports ou des méthodes d'accès alternatifs. Cela signifie que toutes ces fonctions (et donc les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent fonctionner sur des « fichiers » qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS pour faire court) via cette API est automatiquement « consciente des systèmes de fichiers virtuels ». Bien sûr, si une extension accède directement au système de fichiers natif (via des API spécifiques à la plateforme, par exemple), Tcl ne peut pas intercepter de tels appels.

Si des VFS appropriés ont été enregistrés, les « fichiers » peuvent, pour donner deux exemples, être distants (par ex., situés sur un serveur ftp distant) ou archivés (par ex., à l'intérieur d'une archive .zip). De tels systèmes de fichiers enregistrés fournissent une table de correspondance de fonctions pour implémenter tout ou partie de la fonctionnalité listée ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat abstraient le contenu du tampon « struct stat », permettant d'utiliser le même code sur les systèmes avec et sans prise en charge de fichiers de plus de 2 Go.

L'API Tcl_FS est basée sur Tcl_Obj et peut mettre en cache des représentations internes et d'autres chaînes liées aux chemins (par ex., le répertoire de travail actuel). Un effet secondaire de ceci est qu'il ne faut pas passer de valeurs avec un compteur de références de zéro à aucune de ces fonctions. Si de tels appels étaient traités, ils pourraient entraîner des fuites de mémoire (dans certaines circonstances, le code du système de fichiers peut souhaiter conserver une référence à la valeur passée, et donc il ne faut pas supposer qu'après le retour de l'un de ces appels, la valeur ait toujours un compteur de références de zéro - il peut avoir été incrémenté) ou une segmentation fault directe (ou une autre erreur d'accès mémoire) due à la libération de la valeur au cours de la manipulation complexe de la valeur requise pour garantir que le chemin est entièrement normalisé et absolu pour la détermination du système de fichiers. La leçon pratique à retenir de ceci est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect, et peut causer des erreurs mémoire. Le compteur de références de path doit être incrémenté avant d'être passé, ou décrémenté. Pour cette raison, les valeurs avec un compteur de références de zéro sont considérées comme n'étant pas des chemins de système de fichiers valides et l'appel à toute fonction de l'API Tcl_FS avec une telle valeur n'entraînera aucune action.

FONCTIONS DE L'API FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), alors la fonction « copier le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno à l'erreur POSIX « EXDEV » (qui signifie un « lien inter-domaines »).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), alors la fonction « copier le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno à l'erreur POSIX « EXDEV » (qui signifie un « lien inter-domaines »).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction « créer un répertoire » du système de fichiers propriétaire.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction « supprimer un fichier » du système de fichiers propriétaire.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction « supprimer un répertoire » du système de fichiers propriétaire.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr en le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), alors la fonction « renommer un fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable globale C errno à l'erreur POSIX « EXDEV » (qui signifie un « lien inter-domaines »).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction « lister les volumes » non NULL et leur demande de renvoyer leur liste de volumes racine. Elle accumule les valeurs de retour dans une liste qui est renvoyée à l'appelant (avec un compteur de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant l'encodage identifié par encodingName et évalue son contenu comme un script Tcl. Elle renvoie les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, l'encodage système est utilisé pour lire le contenu du fichier. Si le fichier n'a pas pu être lu, une erreur Tcl est renvoyée pour décrire pourquoi le fichier n'a pas pu être lu. Le caractère de fin de fichier pour les fichiers est « \x1A » (^Z) pour toutes les plateformes. Si vous avez besoin d'un « ^Z » dans le code pour une comparaison de chaînes, vous pouvez utiliser « \x1A », qui sera substitué en toute sécurité par l'interpréteur Tcl en « ^Z ». Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours l'encodage système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier de code binaire en mémoire et renvoie les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas, en raison des limitations du système d'exploitation pour charger dynamiquement du code binaire), Tcl tentera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile inverse l'opération, demandant que la bibliothèque indiquée par loadHandle soit retirée du processus. Notez que, contrairement à la commande unload, cela ne donne aucune opportunité à la bibliothèque de faire du nettoyage.

Les deux fonctions ci-dessus renvoient un code d'achèvement Tcl standard. Si une erreur se produit, un message d'erreur est laissé dans le résultat de l'interp.

Le jeton fourni via la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher dans un répertoire tous les fichiers qui correspondent à un modèle donné. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le globbing. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Notez que le code glob implémente les motifs récursifs en interne, donc cette fonction ne sera jamais appelée qu'avec des motifs simples, qui peuvent être mis en correspondance en utilisant la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment en demandant uniquement aux répertoires d'être retournés. Un cas spécial d'appel avec un motif NULL indique que le chemin doit être vérifié uniquement pour le type correct.

Tcl_FSLink remplace la version bibliothèque de readlink, et l'étend pour prendre en charge la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr sera appelée.

Si toPtr est NULL, une action « lire un lien » est effectuée. Le résultat est un Tcl_Obj spécifiant le contenu du lien symbolique donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant, qui devrait appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl doit créer un lien d'un des types passés dans le drapeau linkAction. Ce drapeau est une combinaison OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'un choix existe (c'est-à-dire plus d'un drapeau est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur de retour doit être toPtr (qui appartient donc déjà à l'appelant). En cas d'échec, NULL est retourné.

Tcl_FSLstat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf comprend des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le dernier accès au moment

E, temps de modification, et temps de changement des métadonnées. Voir PORTABLE STAT RESULT API pour une description de la manière d'écrire du code portable pour héberger et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSLstat renvoie 0 et la structure statPtr est remplie de données. Sinon, -1 est renvoyé et aucune information statistique n'est fournie.

Tcl_FSUtime remplace la version de la bibliothèque de utime.

Celle-ci renvoie 0 en cas de succès et -1 en cas d'erreur (conformément à la documentation de utime). En cas de succès, la fonction met à jour les valeurs atime et mtime du fichier donné.

Tcl_FSFileAttrsGet implémente l'accès en lecture pour le sous-commande file attributes de la pile de la file hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

Si le résultat est TCL_OK, une valeur a été placée dans objPtrRef, qui ne sera valide que temporairement (à moins que Tcl_IncrRefCount ne soit appelée).

Tcl_FSFileAttrsSet implémente l'accès en écriture pour le sous-commande file attributes de la pile de la file hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

Tcl_FSFileAttrStrings implémente une partie du sous-commande file attributes de la pile de la file hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

L'appel de procédure peut renvoyer un tableau de chaînes ou, à la place, renvoyer NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. À la fin de son utilisation, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être libérée par Tcl à la fin, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être libérée, le système de fichiers doit s'assurer qu'il conserve une référence à la valeur.

Tcl_FSAccess vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet de système de fichiers) dont le nom est pathname. Si pathname est un lien symbolique sous Unix, les permissions du fichier auquel ce lien symbolique renvoie sont testées.

En cas de succès (toutes les permissions demandées), 0 est renvoyé. En cas d'erreur (au moins un bit dans le mode demandé n'est pas autorisé ou une autre erreur se produit), -1 est renvoyé.

Tcl_FSStat remplit la structure Tcl_StatBuf avec des informations sur le fichier spécifié. Aucun droit d'accès au fichier n'est requis pour obtenir ces informations, mais des droits de recherche sont requis pour tous les répertoires mentionnés dans le chemin vers le fichier. La structure Tcl_StatBuf inclut des informations sur le périphérique, l'inode (0 sous Windows), le mode de privilège, le nombre de liens (1 sous Windows), l'UID (0 sous Windows), le GID (0 sous Windows), le rdev (identique au périphérique sous Windows), la taille, le dernier temps d'accès, le dernier temps de modification et le dernier temps de changement des métadonnées. Voir PORTABLE STAT RESULT API pour une description de la manière d'écrire du code portable pour héberger et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSStat renvoie 0 et la structure statPtr est remplie de données. Sinon, -1 est renvoyé et aucune information statistique n'est fournie.

Tcl_FSOpenFileChannel ouvre un fichier spécifié par pathPtr et renvoie un handle de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est calquée sur la fonction fopen de la bibliothèque d'entrée/sortie standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans les commandes Tcl open lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannel renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannel laisse un message d'erreur dans le résultat de interp après toute erreur.

Le canal nouvellement créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez Tcl_RegisterChannel. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, l'action de création du nouveau canal l'assigne également en remplacement du canal standard.

Tcl_FSGetCwd remplace la version de la bibliothèque de getcwd.

Renvoie le répertoire de travail actuel de la bibliothèque Tcl. Celui-ci peut être différent du répertoire de travail natif, lorsque le répertoire de travail actuel ne se trouve pas dans le système de fichiers natif.

Le résultat est un pointeur vers un objet Tcl Tcl_Obj spécifiant le répertoire actuel, ou NULL si le répertoire n'a pas pu être déterminé. Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de interp.

Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'en a plus besoin, ce compteur de références doit être décrémenté. Ceci est nécessaire pour la sécurité multi-thread, afin que plusieurs threads puissent accéder à cette fonction et aux fonctions associées, tout en s'assurant que les résultats sont toujours valides.

Tcl_FSChdir remplace la version de la bibliothèque de chdir. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl se rabat sur un ensemble de stat et access pour vérifier si le répertoire existe et a les permissions appropriées.

Pour les résultats, voir la documentation de chdir. En cas de succès, nous conservons un enregistrement du chemin réussi dans cwdPathPtr pour les appels ultérieurs à Tcl_FSGetCwd.

Tcl_FSPathSeparator renvoie le caractère séparateur utilisé pour l'élément le plus spécifique du chemin spécifié par pathPtr (c'est-à-dire, le dernier segment du chemin).

Le séparateur est renvoyé sous forme d'objet Tcl contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est renvoyé.

Tcl_FSJoinPath prend l'objet donné, qui doit être une liste valide (une référence de zéro est acceptée), et renvoie la valeur du chemin en considérant les premiers elements comme des segments de chemin valides (chaque segment peut être un chemin complet, un chemin partiel ou juste un nom de répertoire ou de fichier). Si un segment du chemin est effectivement un chemin absolu, alors tous les segments précédents sont ignorés. Si elements est inférieur à 0, nous utilisons l'entier complet.

Il est possible que la valeur renvoyée soit effectivement un élément de la liste donnée, donc l'appelant doit faire attention à incrémenter le compteur de références de la valeur avant de libérer la liste.

La valeur renvoyée, typiquement avec un compteur de références de zéro (mais elle pourrait être partagée dans certaines conditions), contient le chemin joint. L'appelant doit incrémenter le compteur de références avant de l'utiliser. En particulier, la valeur renvoyée pourrait être un élément de la liste donnée, donc la libération de la liste pourrait libérer la valeur prématurément si aucune référence n'a été prise. Si le nombre d'éléments est zéro, la valeur renvoyée sera une chaîne vide Tcl_Obj.

Tcl_FSSplitPath prend l'objet donné, qui doit être un chemin valide, et renvoie une valeur de liste contenant chaque segment de ce chemin comme élément. Il renvoie une valeur de liste avec un compteur de références de zéro. Si le lenPtr passé n'est pas NULL, la variable pointée sera mise à jour pour contenir le nombre d'éléments dans la valeur de liste renvoyée.

Tcl_FSEqualPaths teste si les deux chemins donnés représentent le même objet de système de fichiers. Il renvoie 1 s'ils sont égaux et 0 s'ils sont différents. Si l'un des chemins est NULL, 0 est toujours renvoyé.

Tcl_FSGetNormalizedPath tente d'extraire une représentation unique et normalisée d'un chemin donné, dont la valeur chaîne peut être utilisée comme identifiant unique du fichier.

Renvoie la valeur de chemin normalisée, propriété de Tcl, ou NULL si le chemin était invalide ou n'a pas pu être correctement converti. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère avec ces représentations en interne), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques ne soit pas la version la plus conviviale d'un chemin. La valeur renvoyée est la propriété de Tcl et a une durée de vie équivalente à celle de pathPtr passé (sauf s'il s'agit d'un chemin relatif, auquel cas la valeur normalisée peut être libérée à tout moment où le cwd change) - l'appelant peut incrémenter le compteur de références s'il le souhaite pour conserver une copie plus longtemps.

Tcl_FSJoinToPath prend la valeur donnée, qui devrait généralement être un chemin valide ou NULL, et la joint avec le tableau de segments de chemins donnés.

Renvoie une valeur, typiquement avec un compteur de références de zéro (mais elle pourrait être partagée dans certaines conditions), contenant le chemin joint. L'appelant doit incrémenter le compteur de références avant de l'utiliser. Si l'une des valeurs passées à cette fonction (pathPtr ou éléments de path) a un compteur de références de zéro, elles seront libérées lorsque cette fonction renverra la valeur.

Tcl_FSConvertToPathType tente de convertir l'objet Tcl donné en un type de chemin valide, en tenant compte du fait que le cwd pourrait avoir changé même si cette valeur est déjà du bon type. Le nom de fichier peut commencer par ~ (pour indiquer le répertoire utilisateur actuel) ou ~ (pour indiquer le répertoire de n'importe quel utilisateur).

Si la conversion réussit (c'est-à-dire, la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), TCL_OK est renvoyé. Sinon, TCL_ERROR est renvoyé, et il peut y avoir un message d'erreur dans l'interpréteur.

Tcl_FSGetInternalRep extrait la représentation interne d'une valeur de chemin donnée, dans le système de fichiers donné. Si la valeur de chemin appartient à un système de fichiers différent, NULL est renvoyé. Si la représentation interne est actuellement NULL, une tentative est faite pour la générer en appelant la fonction Tcl_FSCreateInternalRepProc du système de fichiers.

Renvoie NULL ou une représentation valide d'un chemin interne. Cette représentation interne est mise en cache, de sorte que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires.

Tcl_FSGetTranslatedPath tente d'extraire le chemin traduit à partir de l'objet Tcl donné.

Si la traduction réussit (c'est-à-dire, la valeur est un chemin valide), la valeur est renvoyée. Sinon, NULL est renvoyé, et il peut y avoir un message d'erreur dans l'interpréteur. Une route traduite est celle qui ne contient pas ~ ou ~user (ceux-ci ont été développés en leur représentation actuelle dans le système de fichiers). La valeur renvoyée est la propriété de l'appelant, qui doit stocker la valeur ou appeler Tcl_DecrRefCount pour s'assurer que la mémoire est libérée. Cette fonction a peu d'utilité pratique, et Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement des améliorations à utiliser dans plus d'occasions.

Tcl_FSGetTranslatedStringPath fait la même chose que Tcl_FSGetTranslatedPath, mais renvoie une chaîne ou NULL. La chaîne renvoyée est allouée dynamiquement et est la propriété de Tcl_Obj.

ed par l'appelant, qui doit le stocker ou appeler ckfree pour s'assurer qu'il est libéré. Encore une fois, Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des usages.

Tcl_FSNewNativePath effectue quelque chose comme l'inverse des conversions habituelles obj->chemin->représentation native. Si un code récupère un chemin sous forme native (provenant, par exemple, de readlink ou d'une boîte de dialogue native), et que ce chemin doit être utilisé au niveau Tcl, alors appeler cette fonction est un moyen efficace de créer le type de valeur de chemin approprié.

La valeur résultante est une valeur de type « chemin » pure, qui ne recevra une représentation sous forme de chaîne UTF-8 que si cela est requis par un code Tcl.

Tcl_FSGetNativePath est destiné à être utilisé par les systèmes de fichiers natifs Win/Unix, de sorte qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un enrobage de commodité autour de Tcl_FSGetInternalRep. Il pourrait être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes (par exemple, sur macOS, une représentation utilisant une structure fileSpec de FSRef serait probablement plus efficace). Sous Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Actuellement, la représentation est simplement une chaîne de caractères qui peut contenir soit le chemin relatif, soit un chemin normalisé complet et absolu dans l'encodage natif (des conditions complexes dictent lequel de ceux-ci sera fourni, donc aucun ne peut être fiable, sauf si le chemin est connu pour être absolu). Si vous avez besoin d'un chemin natif qui doit être absolu, alors vous devriez demander la version native d'un chemin normalisé. Si, pour une raison quelconque, une version non absolue et non normalisée du chemin est nécessaire, cela doit être construit séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache de sorte que les appels répétés à cette fonction n'entraînent pas de conversions supplémentaires. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle du pathPtr passé (sauf s'il s'agit d'un chemin relatif, auquel cas la représentation native peut être libérée à tout moment où le cwd change).

Tcl_FSFileSystemInfo renvoie une liste de deux éléments. Le premier élément est le nom du système de fichiers (par exemple, « natif », « vfs », « zip », ou « prowrap », peut-être), et le second est le type particulier du chemin donné au sein de ce système de fichiers (qui dépend du système de fichiers). Le second élément peut être vide si le système de fichiers ne fournit pas de catégorisation supplémentaire des fichiers.

Une valeur de liste valide est renvoyée, sauf si la valeur du chemin n'est pas reconnue, auquel cas NULL sera renvoyé.

Tcl_FSGetFileSystemForPath renvoie un pointeur vers le Tcl_Filesystem qui accepte ce chemin comme valide.

Si aucun système de fichiers n'accepte le chemin, NULL est renvoyé.

Tcl_FSGetPathType détermine si le chemin donné est relatif au répertoire courant, relatif au volume courant, ou absolu.

Il renvoie l'une des valeurs TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, ou TCL_PATH_VOLUME_RELATIVE

L'API DU SYSTÈME DE FICHIERS VIRTUEL

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un système de fichiers ; ces opérations sont invoquées au besoin par la couche générique, ce qui se produit généralement via les fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un morceau de données optionnel à associer à ce système de fichiers. En appelant cette fonction, Tcl attachera le système de fichiers à la liste des systèmes de fichiers connus, et il deviendra pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera renvoyé.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et renvoie TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est renvoyé.

Tcl_FSData renverra le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il renverra NULL.

Tcl_FSMountsChanged est utilisé pour informer le cœur de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche de système de fichiers générique pour effectuer l'ensemble complet des actions liées au système de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (presque toutes doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni), et fonctions d'efficacité (qui n'ont besoin d'être implémentées que si elles peuvent l'être efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces solutions de repli ne sont utilisées que pour gérer les commandes initiées dans Tcl, pas en C. Cela signifie que si une commande file rename est émise en Tcl, et que le(s) système(s) de fichiers pertinent(s) n'implémentent pas leur Tcl_FSRenameFileProc, le noyau de Tcl se rabattra sur une combinaison d'autres fonctions de système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a un autre repli). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun repli de ce type ne se produit. Ceci est vrai sauf pour les quatre dernières entrées du tableau de systèmes de fichiers (lstat, load, getcwd et chdir) pour lesquels des replis se produisent effectivement au niveau C.

Toutes les fonctions qui prennent des noms de chemins sous forme Tcl_Obj prennent ces noms sous forme UTF-8. L'API d'infrastructure des systèmes de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

INFRASTRUCTURE SYSTÈME DE FICHIERS

Ces champs contiennent des informations de base sur la structure du système de fichiers et les adresses des fonctions utilisées pour associer un système de fichiers particulier à un chemin de fichier, et pour gérer en interne les représentations de chemins, par exemple en copiant et en libérant ces représentations.

TYPE NOM

Le champ typeName contient une chaîne de caractères terminée par un caractère nul qui identifie le type du système de fichiers implémenté, par exemple “natif”, “zip” ou “vfs”.

LONGUEUR STRUCTURE

Le champ structureLength est généralement implémenté comme sizeof(Tcl_Filesystem), et il est là pour permettre une meilleure compatibilité ascendante binaire si la taille de la structure change dans une future version de Tcl.

VERSION

Le champ version doit être défini sur TCL_FILESYSTEM_VERSION_1.

PROCÉDURE CHEMIN DANS SYSTÈME DE FICHIERS

Le champ pathInFilesystemProc contient l'adresse d'une fonction qui est appelée pour déterminer si une valeur de chemin donnée appartient à ce système de fichiers ou non. Tcl n'appellera les autres fonctions du système de fichiers qu'avec un chemin pour lequel cette fonction a renvoyé TCL_OK. Si le chemin n'appartient pas, -1 doit être renvoyé (le comportement de Tcl pour toute autre valeur de retour n'est pas défini). Si TCL_OK est renvoyé, alors le paramètre de sortie optionnel clientDataPtr peut être utilisé pour renvoyer une représentation interne (spécifique au système de fichiers) du chemin, qui sera mise en cache à l'intérieur de la valeur du chemin, et pourra être récupérée efficacement par les autres fonctions du système de fichiers. Tcl mettra simultanément en cache le fait que ce chemin appartient à ce système de fichiers. Ces caches sont invalidés lorsque des structures de système de fichiers sont ajoutées ou supprimées de la liste interne des systèmes de fichiers connus de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROCÉDURE DUPLIQUER REPRÉSENTATION INTERNE

Cette fonction crée une copie de la représentation interne d'un chemin et est appelée lorsque Tcl a besoin de dupliquer une valeur de chemin. Si elle est NULL, Tcl ne copiera tout simplement pas la représentation interne, qui devra alors peut-être être régénérée plus tard.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

PROCÉDURE LIBÉRER REPRÉSENTATION INTERNE

Libère la représentation interne. Cela doit être implémenté si les représentations internes doivent être libérées (c'est-à-dire si de la mémoire est allouée lors de la génération d'une représentation interne), mais peut sinon être NULL.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

PROCÉDURE INTERNE VERS NORMALISÉE

Fonction pour convertir la représentation interne en un chemin normalisé. Uniquement requise si le système de fichiers crée des valeurs de chemin pures sans représentation textuelle/de chemin. La valeur de retour est une valeur Tcl dont la représentation textuelle est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

PROCÉDURE CRÉER REPRÉSENTATION INTERNE

Fonction pour prendre une valeur de chemin, calculer une représentation interne pour celle-ci, et stocker cette représentation native dans la valeur. Peut être NULL si les chemins n'ont pas de représentation interne, ou si la Tcl_FSPathInFilesystemProc pour ce système de fichiers crée toujours immédiatement une représentation interne pour les chemins qu'elle accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

PROCÉDURE NORMALISER CHEMIN

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations textuelles pour la même valeur de chemin. Dans Tcl, chaque “chemin” doit avoir une seule représentation textuelle “normalisée” unique. Selon le système de fichiers, il peut y avoir plus d'une représentation textuelle non normalisée qui fait référence à ce chemin (par exemple, un chemin relatif, un chemin avec une casse différente si le système de fichiers ne tient pas compte de la casse, un chemin contenant une référence à un répertoire personnel comme “~”, un chemin contenant des liens symboliques, etc.). Si le tout dernier composant du chemin est un lien symbolique, il ne doit pas être converti en la valeur à laquelle il pointe (mais sa casse ou d'autres aspects doivent être rendus uniques). Tous les autres composants du chemin doivent être convertis à partir de liens symboliques. Cette seule exception est nécessaire pour être conforme aux sémantiques de Tcl avec file delete, file rename, file copy opérant sur des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint soit au début du chemin (c'est-à-dire zéro), soit à la fin du chemin, soit à un séparateur de fichier intermédiaire dans le chemin. Elle ne pointera jamais vers une autre position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions qui sont appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui devrait être utilisé avec l'ensemble complet des commandes Tcl standard doit implémenter toutes ces opérations. Si certaines d'entre elles ne sont pas implémentées, certaines commandes Tcl peuvent échouer lors de l'opération sur des chemins appartenant à ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques n'a pas besoin d'implémenter la fonction readlink, etc. Le cœur de Tcl s'attend à ce que les systèmes de fichiers se comportent de cette manière).

PROCÉDURE TYPE CHEMIN SYSTÈME DE FICHIERS

MATCHINDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, les fonctionnalités de glob et de copie récursive manqueront dans le système de fichiers (et cela peut affecter des commandes comme encoding names qui utilisent la fonctionnalité de glob en interne).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit renvoyer tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au modèle donné et sont conformes à la spécification types donnée. Il y a deux façons dont cette fonction peut être appelée. Si pattern est NULL, alors pathPtr est une spécification de chemin complet d'un seul fichier ou répertoire qui doit être vérifié pour son existence et son type correct. Sinon, pathPtr est un répertoire, dont le contenu doit être recherché par la fonction pour trouver les fichiers ou répertoires du type correct. Dans les deux cas, on peut supposer que pathPtr n'est ni NULL ni vide. Il n'est actuellement pas documenté si pathPtr aura ou non un séparateur de fichier à sa fin, donc le code doit être flexible aux deux possibilités.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le processus de correspondance. Les messages d'erreur sont placés dans interp, à moins que interp ne soit NULL, auquel cas aucun message d'erreur ne doit être généré ; en cas de résultat TCL_OK, les résultats doivent être ajoutés à la valeur resultPtr donnée (qui peut être supposée être une liste Tcl valide non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (cela signifie généralement qu'il s'agira de spécifications de chemins absolus). Notez que si aucune correspondance n'est trouvée, cela conduit simplement à un résultat vide ; les erreurs ne sont signalées que pour les problèmes réels de fichiers ou de systèmes de fichiers qui peuvent survenir pendant le processus de correspondance.

La structure Tcl_GlobTypeData passée dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Type Mac acceptable */
    Tcl_Obj *macType;
    /* Créateur Mac acceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qui sont importants à gérer correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT sont vrais (et en particulier lorsque les autres indicateurs sont faux). Dans le premier de ces cas, la fonction doit lister les répertoires contenus. Tcl utilise ceci pour implémenter le globbing récursif, il est donc essentiel que les systèmes de fichiers implémentent correctement la correspondance des répertoires. Dans le second de ces cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage qui se trouvent dans le pathPtr donné (et dans ce cas, pathPtr n'a pas besoin de se trouver dans le même système de fichiers - différent de tous les autres cas où cette fonction est appelée). Le support pour cela est essentiel si Tcl veut avoir des transitions transparentes entre un système de fichiers et un autre.

DESCRIPTION

These are the procedure formats for the file system interface functions that Tcl uses to implement its virtual file system (VFS) layer. These functions are not normally called directly by Tcl application code. Instead, they are invoked by Tcl's built-in file system commands such as file, open, load, etc. when operating on filenames that have been registered with Tcl's VFS layer.

A filesystem is registered with Tcl by the Tcl_FSInit function. This function takes a pointer to a Tcl_FS structure which contains pointers to the functions that implement the filesystem operations. The filesystem is also given a name, by which it may be referred to in pathnames. For example, a filesystem named "memfs" might handle pathnames like "memfs1:/myfile.txt".

STATPROC

Function to process a Tcl_FSStat call. This function is optional for filesystems that do not support the stat system call directly. If this field is NULL, Tcl will attempt to call the lstatProc (defined below) to get file information. If both are NULL, then Tcl_FSStat will fail with an error.

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

The function should fill the buffer pointed to by statPtr with file status information for the file specified by pathPtr. The return value is a standard Tcl result indicating whether an error occurred in the process. On success, statPtr will contain the file status. If this function is called on a symbolic link, it returns information about the file pointed to by the link.

CREATEDIRECTORYPROC

Function to process a Tcl_FSCreateDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, a new directory should have been added to the filesystem in the location specified by pathPtr.

REMOVEDIRECTORYPROC

Function to process a Tcl_FSRemoveDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the directory specified by pathPtr should have been removed from the filesystem. If the recursive flag is given, then a non-empty directory should be deleted without error. If this flag is not given, then and the directory is non-empty a POSIX “EEXIST” error should be signaled. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr.

DELETEFILEPROC

Function to process a Tcl_FSDeleteFile call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the file specified by pathPtr should have been removed from the filesystem. Note that, if the filesystem supports symbolic links, Tcl will always call this function and not Tcl_FSRemoveDirectoryProc when needed to delete them (even if they are symbolic links to directories).

FILESYSTEM EFFICIENCY

These functions need not be implemented for a particular filesystem because the core has a fallback implementation available. See each individual description for the consequences of leaving the field NULL.

LSTATPROC

Function to process a Tcl_FSLstat call. If not implemented, Tcl will attempt to use the statProc defined above instead. Therefore it need only be implemented if a filesystem can differentiate between stat and lstat calls.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

The behavior of this function is very similar to that of the Tcl_FSStatProc defined above, except that if it is applied to a symbolic link, it returns information about the link, not about the target file.

COPYFILEPROC

Function to process a Tcl_FSCopyFile call. If not implemented Tcl will fall back on open-r, open-w and fcopy as a copying mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. Note that, destPathPtr is the name of the file which should become the copy of srcPathPtr. It is never the name of a directory into which srcPathPtr could be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Note that, if the filesystem supports symbolic links, Tcl will always call this function and not copyDirectoryProc when needed to copy them (even if they are symbolic links to directories). Finally, if the filesystem determines it cannot support the file copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

RENAMEFILEPROC

Function to process a Tcl_FSRenameFile call. If not implemented, Tcl will fall back on a copy and delete mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the renaming process. If the filesystem determines it cannot support the file rename action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

COPYDIRECTORYPROC

Function to process a Tcl_FSCopyDirectory call. If not implemented, Tcl will fall back on a recursive file mkdir, file copy mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr. Note that, destPathPtr is the name of the directory-name which should become the mirror-image of srcPathPtr. It is not the name of a directory into which srcPathPtr should be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Finally, if the filesystem determines it cannot support the directory copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

LOADFILEPROC

Function to process a Tcl_FSLoadFile call. If not implemented, Tcl will fall back on a copy to native-temp followed by a Tcl_FSLoadFile on that temporary copy. Therefore it need only be implemented if the filesystem can load code directly, or it can be implemented simply to return TCL_ERROR to disable load functionality in this filesystem entirely.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc **unloadProcPtr);

Returns a standard Tcl completion code. If an error occurs, an error message is left in the interp's result. The function dynamically loads a binary code file into memory. On a successful load, the handlePtr should be filled with a token for the dynamically loaded file, and the unloadProcPtr should be filled in with the address of a procedure. The unload procedure will be called with the given Tcl_LoadHandle as its only parameter when Tcl needs to unload the file. For example, for the native filesystem, the Tcl_LoadHandle returned is currently a token which can be used in the private TclpFindSymbol to access functions in the new code. Each filesystem is free to define the Tcl_LoadHandle as it requires. Finally, if the filesystem determines it cannot support the file load action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

UNLOADFILEPROC

Function to unload a previously successfully loaded file. If load was implemented, then this should also be implemented, if there is any cleanup action required.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Function to process a Tcl_FSGetCwd call. Most filesystems need not implement this. It will usually only be called once, if getcwd is called before chdir. May be NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

If the filesystem supports a native notion of a current working directory (which might perhaps change independent of Tcl), this function should return that cwd as the result, or NULL if the current directory could not be determined (e.g. the user does not have appropriate permissions on the cwd directory). If NULL is returned, an error message is left in the interp's result.

CHDIRPROC

Function to process a Tcl_FSChdir call. If filesystems do not implement this, it will be emulated by a series of directory access checks. Otherwise, virtual filesystems which do implement it need only respond with a positive return result if the pathPtr is a valid, accessible directory in their filesystem. They need not remember the result, since that will be automatically remembered for use by Tcl_FSGetCwd. Real filesystems should carry out the correct action (i.e. call the correct system chdir API).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

The Tcl_FSChdirProc changes the applications current working directory to the value specified in pathPtr. The function returns -1 on error or 0 on success.
