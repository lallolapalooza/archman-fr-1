INTRODUCTION

Les interfaces décrites ici sont utilisées pour personnaliser la boucle d'événements de Tcl. Les deux modifications les plus courantes sont l'ajout de nouvelles sources d'événements et la fusion de la boucle d'événements de Tcl avec une autre boucle d'événements, telle qu'une fournie par une application dans laquelle Tcl est intégré. Chacune de ces tâches est décrite dans une section distincte.

Les procédures de ce manuel sont les éléments de base sur lesquels le notificateur d'événements de Tcl est construit. Le notificateur d'événements est la couche la plus basse du mécanisme d'événements de Tcl. Il se compose de trois éléments :

[1]
Les sources d'événements : elles représentent les moyens par lesquels des événements peuvent être générés. Par exemple, il existe une source d'événements de type temporisateur qui implémente Tcl_CreateTimerHandler et la commande after, et il existe une source d'événements de type fichier qui implémente Tcl_CreateFileHandler sur les systèmes Unix. Une source d'événements doit travailler avec le notificateur pour détecter les événements aux bons moments, les enregistrer dans la file d'attente des événements et, finalement, avertir le logiciel de niveau supérieur qu'ils se sont produits. Les procédures Tcl_CreateEventSource, Tcl_DeleteEventSource et Tcl_SetMaxBlockTime, Tcl_QueueEvent et Tcl_DeleteEvents sont principalement utilisées par les sources d'événements.
[2]
La file d'attente des événements : pour les applications non multithread, il existe une seule file d'attente pour l'application entière, qui contient les événements détectés mais pas encore traités. Les sources d'événements placent les événements dans la file d'attente afin qu'ils puissent être traités au moment approprié pendant la boucle d'événements. La file d'attente des événements garantit une discipline de traitement des événements juste, de sorte qu'aucun thread ne puisse supplanter les autres. Elle permet également de mettre en attente des événements pour un traitement ultérieur. Les applications multithread fonctionnent de manière similaire, sauf qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. Tcl_QueueEvent est utilisée (principalement par les sources d'événements) pour ajouter des événements à la file d'attente des événements et Tcl_DeleteEvents est utilisée pour supprimer des événements de la file d'attente sans les traiter. Dans une application multithread, Tcl_QueueEvent ajoute un événement à la file d'attente du thread courant, et Tcl_ThreadQueueEvent ajoute un événement à une file d'attente dans un thread spécifique.
[3]
La boucle d'événements : pour détecter et traiter les événements, l'application entre dans une boucle qui attend les événements, les place dans la file d'attente des événements, puis les traite. La plupart des applications Tcl le feront en appelant la procédure Tcl_DoOneEvent, qui est décrite dans une entrée de manuel.

La plupart des applications Tcl n'ont pas à se soucier des détails internes du notificateur de Tcl. Cependant, le notificateur est maintenant suffisamment flexible pour être adapté à une nouvelle plateforme ou pour utiliser une boucle d'événements externe (comme la boucle d'événements Motif lorsque Tcl est intégré dans une application Motif). Les procédures Tcl_WaitForEvent et Tcl_SetTimer sont normalement implémentées par Tcl, mais peuvent être remplacées par de nouvelles versions pour adapter le notificateur (les procédures Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler et Tcl_DeleteFileHandler doivent également être remplacées ; voir CRÉATION D'UN NOUVEAU NOTIFICATEUR pour les détails). Les procédures Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode et Tcl_SetServiceMode sont fournies pour aider à connecter la boucle d'événements de Tcl à une boucle d'événements externe telle que celle de Motif.

BASES DU NOTIFICATEUR

La façon la plus simple de comprendre le fonctionnement du notificateur est de considérer ce qui se passe lorsqu'on appelle Tcl_DoOneEvent. Tcl_DoOneEvent reçoit un argument flags qui indique quel type d'événements peut être traité et s'il doit bloquer s'il n'y a pas d'événements prêts. Tcl_DoOneEvent fait ce qui suit :

[1]
Il vérifie la file d'attente des événements pour voir s'il y a des événements qui peuvent être servis. Si c'est le cas, le premier événement possible est servi, retiré de la file d'attente et renvoyé. Il fait cela en appelant Tcl_ServiceEvent et en lui passant l'argument flags.
[2]
Il se prépare à bloquer pour un événement. Pour ce faire, Tcl_DoOneEvent appelle une procédure d'initialisation dans chaque source d'événements. La source d'événements effectuera l'initialisation spécifique à la source d'événements et pourra éventuellement appeler Tcl_SetMaxBlockTime pour limiter le temps pendant lequel Tcl_WaitForEvent bloquera s'il n'y a pas de nouveaux événements.
[3]
Il appelle Tcl_WaitForEvent. Cette procédure est implémentée différemment sur différentes plateformes ; elle attend un événement en fonction des informations fournies par les sources d'événements. Elle peut entraîner le blocage de l'application si timePtr spécifie un intervalle différent de 0. Tcl_WaitForEvent renvoie lorsque quelque chose s'est produit, par exemple un fichier est devenu lisible ou l'intervalle spécifié par timePtr a expiré. S'il n'y a aucun événement pour Tcl_WaitForEvent à attendre, elle renvoie immédiatement et Tcl_DoOneEvent renvoie 0.
[4]
Il appelle une procédure de vérification dans chaque source d'événements. La procédure de vérification détermine si des événements qui intéressent cette source se sont produits. Si c'est le cas, les événements sont ajoutés à la file d'attente des événements.

CRÉATION D'UNE NOUVELLE SOURCE D'ÉVÉNEMENTS

Une source d'événements se compose de trois procédures qui sont appelées par le multiplexeur, plus des procédures C supplémentaires qui sont appelées par du code de plus haut niveau pour organiser les rappels d'événements. Les trois procédures appelées par le multiplexeur comprennent les procédures de configuration et de vérification décrites ci-dessus, plus une procédure supplémentaire qui est appelée lorsqu'un événement est retiré de la file d'attente des événements pour être traité.

La procédure Tcl_CreateEventSource crée une nouvelle source d'événements. Ses arguments spécifient les procédures de configuration et de vérification de la source d'événements. SetupProc doit correspondre au prototype suivant :

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

L'argument clientData sera le même que l'argument clientData de la procédure Tcl_CreateEventSource ; il est généralement utilisé pour pointer vers des informations privées gérées par la source d'événements. L'argument flags sera le même que l'argument flags passé à Tcl_DoOneEvent, sauf qu'il ne sera jamais 0 (Tcl_DoOneEvent remplace 0 par TCL_ALL_EVENTS). Flags indique quels types d'événements doivent être pris en compte ; si le bit correspondant à cette source d'événements n'est pas activé, la source d'événements doit retourner immédiatement sans rien faire. Par exemple, la source d'événements de fichiers vérifie le bit TCL_FILE_EVENTS.

SetupProc doit garantir que le programme ne se bloque pas lorsque des événements du type souhaité se produisent. Ceci est généralement fait de manière dépendante de la plateforme. Par exemple, sous Unix, une source d'événements pourrait appeler Tcl_CreateFileHandler ; sous Windows, elle pourrait demander des notifications avec un événement Windows. Pour les sources d'événements basées sur le temps, comme les événements de minuterie ou tout événement interrogé, la source d'événements peut appeler Tcl_SetMaxBlockTime pour forcer le programme à se réveiller même si aucun événement ne s'est produit. Si aucune source d'événements n'appelle Tcl_SetMaxBlockTime, Tcl_WaitForEvent attendra aussi longtemps que nécessaire pour qu'un événement se produise ; sinon, il n'attendra que la durée la plus courte entre les appels à Tcl_SetMaxBlockTime d'une des sources d'événements. Si une source d'événements sait qu'elle a déjà des événements prêts à être signalés, elle peut demander un temps de blocage maximal de zéro. Par exemple, la procédure de configuration de la source d'événements X vérifie s'il y a déjà des événements dans la file d'attente. S'il y en a, elle appelle Tcl_SetMaxBlockTime avec un temps de blocage maximal de zéro afin que Tcl_WaitForEvent ne se bloque pas s'il n'y a pas de nouvelles données sur la connexion X. L'argument timePtr de Tcl_WaitForEvent pointe vers une structure décrivant un intervalle de temps en secondes et microsecondes :

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

Le champ usec doit être inférieur à 1000000.

Les informations fournies à Tcl_SetMaxBlockTime ne sont utilisées que pour le prochain appel à Tcl_WaitForEvent ; elles sont supprimées après le retour de Tcl_WaitForEvent. La prochaine fois qu'une attente d'événement sera effectuée, chaque procédure de configuration des sources d'événements sera rappelée, et elles pourront spécifier de nouvelles informations pour cette attente d'événement.

Si le programme utilise une boucle d'événements externe au lieu de Tcl_DoOneEvent, les sources d'événements peuvent avoir besoin d'appeler Tcl_SetMaxBlockTime à d'autres moments. Par exemple, si un nouveau gestionnaire d'événements est enregistré qui doit surveiller les événements, la source d'événements peut appeler Tcl_SetMaxBlockTime pour définir un temps de blocage maximal de zéro afin de forcer la boucle d'événements externe à appeler Tcl. Dans ce cas, Tcl_SetMaxBlockTime appelle Tcl_SetTimer avec l'intervalle le plus court vu depuis le dernier appel à Tcl_DoOneEvent ou Tcl_ServiceAll.

En plus de la procédure générale Tcl_SetMaxBlockTime, d'autres procédures spécifiques à la plateforme peuvent également être disponibles pour setupProc, si des informations supplémentaires sont nécessaires à Tcl_WaitForEvent sur cette plateforme. Par exemple, sur les systèmes Unix, l'interface Tcl_CreateFileHandler peut être utilisée pour attendre des événements de fichier.

La deuxième procédure fournie par chaque source d'événements est sa procédure de vérification, indiquée par l'argument checkProc de Tcl_CreateEventSource. CheckProc doit correspondre au prototype suivant :

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Les arguments de cette procédure sont les mêmes que ceux de setupProc. CheckProc est appelé par Tcl_DoOneEvent après qu'il a attendu les événements. Il est supposé qu'au moins une source d'événements est prête à mettre des événements en file d'attente. Tcl_DoOneEvent appelle chaque source d'événements dans l'ordre, donc toutes ont la possibilité de mettre en file d'attente les événements qui sont prêts. La procédure de vérification fait deux choses. Premièrement, elle doit voir s'il y a des événements qui se sont produits. Différentes sources d'événements le font différemment.

Si la procédure de vérification d'une source d'événements détecte un événement intéressant, elle doit ajouter l'événement à la file d'attente des événements de Tcl. Pour ce faire, la source d'événements appelle Tcl_QueueEvent. L'argument evPtr est un pointeur vers une structure allouée dynamiquement qui contient l'événement (voir ci-dessous pour les questions de gestion de la mémoire). Chaque source d'événements peut définir sa propre structure d'événement avec des informations pertinentes pour cette source d'événements. Cependant, le premier membre de la structure doit être une structure de type Tcl_Event, et l'adresse de cette structure est utilisée lorsqu'on communique entre la source d'événements et le reste du multiplexeur. Une Tcl_Event a la définition suivante :

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La source d'événements doit remplir le champ proc de la structure avant d'appeler Tcl_QueueEvent. nextPtr est utilisé pour lier les événements dans la file d'attente et ne doit pas être modifié par la source d'événements.

Un événement peut être ajouté à la file d'attente dans l'une des trois positions, en fonction de l'argument position de Tcl_QueueEvent :

TCL_QUEUE_TAIL
Ajouter l'événement à la fin de la file d'attente, de sorte que tous les événements en attente soient traités en premier. C'est presque toujours la bonne position pour les nouveaux événements.
TCL_QUEUE_HEAD
Ajouter l'événement au début de la file d'attente, de sorte qu'il soit traité avant tous les autres événements en attente.
TCL_QUEUE_MARK
Ajouter l'événement au début de la file d'attente, à moins qu'il n'y ait d'autres événements au début avec la position TCL_QUEUE_MARK ; si c'est le cas, ajouter le nouvel événement juste après tous les autres événements TCL_QUEUE_MARK. Cette valeur de position est utilisée pour insérer une séquence ordonnée d'événements au début de la file d'attente, comme une série d'événements Enter et Leave synthétisés lors d'une opération de grappage ou de dégrapage dans Tk.

Lorsqu'il est temps de traiter un événement de la file d'attente (étapes 1 et 4 ci-dessus), Tcl_ServiceEvent appellera la procédure proc spécifiée dans le premier Tcl_Event de la file. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

Le premier argument de proc est un pointeur vers l'événement, qui sera le même que le premier argument de l'appel à Tcl_QueueEvent qui a ajouté l'événement à la file d'attente. Le deuxième argument de proc est l'argument flags de l'appel actuel à Tcl_ServiceEvent ; il est utilisé par la source d'événements pour retourner immédiatement si ses événements ne sont pas pertinents.

Il incombe à proc de traiter l'événement, généralement en appelant une ou plusieurs commandes Tcl ou des rappels de niveau C. Une fois que la source d'événements a terminé de traiter l'événement, elle retourne 1, indiquant que l'événement peut être retiré de la file d'attente. Si pour une raison quelconque la source d'événements décide que l'événement ne peut pas être traité pour le moment, elle peut retourner 0 pour indiquer que l'événement doit être différé pour un traitement ultérieur ; dans ce cas, Tcl_ServiceEvent passera à la prochaine entrée de la file d'attente et tentera de la traiter. Il existe plusieurs raisons pour lesquelles une source d'événements pourrait différer un événement. Une possibilité est que les événements de ce type soient exclus par l'argument flags. Par exemple, la source d'événements de fichiers retournera toujours 0 si le bit TCL_FILE_EVENTS n'est pas activé dans flags. Un autre exemple de report d'événements se produit dans Tk si Tk_RestrictEvents a été appelé pour reporter certains types d'événements de fenêtre.

Lorsque proc retourne 1, Tcl_ServiceEvent retirera l'événement de la file d'attente et libérera sa mémoire. Il convient de noter que la mémoire de l'événement doit être allouée par la source d'événements (en utilisant Tcl_Alloc ou la macro Tcl ckalloc) avant d'appeler Tcl_QueueEvent, mais elle sera libérée par Tcl_ServiceEvent, et non par la source d'événements.

Les applications multithreadées fonctionnent de manière similaire, à la différence qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. L'appel à Tcl_QueueEvent dans une application multithreadée ajoute un événement à la file d'attente du thread actuel. Pour ajouter un événement à la file d'attente d'un autre thread, utilisez Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent accepte comme argument un identifiant de thread Tcl, qui identifie de manière unique un thread dans une application Tcl. Pour obtenir l'identifiant de thread Tcl_ThreadId du thread actuel, utilisez la procédure Tcl_GetCurrentThread. (Un thread devrait alors passer cet identifiant à d'autres threads afin qu'ils puissent ajouter des événements à sa file d'attente.) Après avoir ajouté un événement à la file d'attente d'un autre thread, vous devrez généralement appeler Tcl_ThreadAlert pour "réveiller" ce thread et le notifier du nouvel événement.

Tcl_DeleteEvents peut être utilisé pour supprimer explicitement un ou plusieurs événements de la file d'attente des événements. Tcl_DeleteEvents appelle la procédure proc pour chaque événement dans la file d'attente, supprimant ceux dont la procédure retourne 1. Les événements dont la procédure retourne 0 restent dans la file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

L'argument clientData sera le même que l'argument clientData de l'appel à Tcl_DeleteEvent ; il est généralement utilisé pour pointer vers des informations privées gérées par la source d'événements. La procédure proc est appelée pour chaque événement dans la file d'attente, et si la procédure retourne 1, l'événement est supprimé. Les événements dont la procédure retourne 0 restent dans la file d'attente.

Tcl_DeleteEventSource supprime une source d'événements. Les arguments setupProc, checkProc et clientData doivent correspondre exactement à ceux fournis à Tcl_CreateEventSource pour que la source d'événements soit supprimée. Si aucune source de ce type n'existe, Tcl_DeleteEventSource n'a aucun effet.

CRÉATION D'UN NOUVEAU NOTIFICATEUR

Le notificateur comprend toutes les procédures décrites dans cette entrée de manuel, ainsi que Tcl_DoOneEvent et Tcl_Sleep, qui sont disponibles sur toutes les plateformes, et Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont spécifiques à Unix. La plupart de ces procédures sont génériques, dans le sens où elles sont les mêmes pour tous les notificateurs. Cependant, aucune des procédures n'est dépendante du notificateur : Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler et Tcl_ServiceModeHook. Pour supporter une nouvelle plateforme ou pour intégrer Tcl avec une boucle d'événements spécifique à une application, vous devez écrire de nouvelles versions de ces procédures.

Tcl_InitNotifier initialise l'état du notificateur et renvoie un handle vers l'état du notificateur. Tcl appelle cette procédure lors de l'initialisation d'un interpréteur Tcl. De même, Tcl_FinalizeNotifier arrête le notificateur et est appelée par Tcl_Finalize lors de l'arrêt d'un interpréteur Tcl.

Tcl_WaitForEvent est la procédure de plus bas niveau du notificateur ; elle est responsable de l'attente d'un événement « intéressant » ou de l'expiration d'un temps donné. Avant que Tcl_WaitForEvent ne soit appelée, chacune des procédures d'initialisation des sources d'événements aura été appelée. L'argument timePtr de Tcl_WaitForEvent donne le temps maximum de blocage pour un événement, basé sur les appels à Tcl_SetMaxBlockTime effectués par les procédures d'initialisation et sur d'autres informations (telles que le bit TCL_DONT_WAIT dans flags).

Idéalement, Tcl_WaitForEvent ne devrait qu'attendre qu'un événement se produise ; elle ne devrait pas réellement traiter l'événement d'aucune manière. Plus tard, les sources d'événements traiteront les événements bruts et créeront des Tcl_Events dans la file d'attente d'événements dans leurs procédures checkProc. Cependant, sur certaines plateformes (comme Windows), cela n'est pas possible ; les événements peuvent être traités dans Tcl_WaitForEvent, y compris la mise en file d'attente de Tcl_Events et plus encore (par exemple, des rappels pour les widgets natifs peuvent être invoqués). La valeur de retour de Tcl_WaitForEvent doit être 0, 1 ou -1. Sur les plateformes comme Windows où les événements sont traités dans Tcl_WaitForEvent, une valeur de retour de 1 signifie qu'il peut y avoir d'autres événements en attente qui n'ont pas été traités. C'est un signe pour l'appelant qu'il doit rappeler Tcl_WaitForEvent s'il veut que tous les événements en attente soient traités. Une valeur de retour de 0 signifie que rappeler Tcl_WaitForEvent n'aura aucun effet : soit c'est une plateforme où Tcl_WaitForEvent n'attend que sans traiter d'événements, soit Tcl_WaitForEvent sait avec certitude qu'il n'y a pas d'événements supplémentaires à traiter (par exemple, elle est revenue parce que le temps s'est écoulé). Enfin, une valeur de retour de -1 signifie que la boucle d'événements n'est plus opérationnelle et que l'application devrait probablement se dérouler et se terminer. Sous Windows, cela se produit lorsqu'un message WM_QUIT est reçu ; sous Unix, cela se produit lorsque Tcl_WaitForEvent aurait attendu éternellement car il n'y avait pas de sources d'événements actives et que le délai d'attente était infini.

Tcl_AlertNotifier est utilisé dans les applications multithreads pour permettre à n'importe quel thread de « réveiller » le notificateur pour l'alerter de nouveaux événements dans sa file d'attente. Tcl_AlertNotifier nécessite comme argument le handle du notificateur renvoyé par Tcl_InitNotifier.

Si le notificateur doit être utilisé avec une boucle d'événements externe, alors il doit également supporter l'interface Tcl_SetTimer. Tcl_SetTimer est appelée par Tcl_SetMaxBlockTime chaque fois que le temps de blocage maximal a été réduit. Tcl_SetTimer doit organiser pour que la boucle d'événements externe appelle Tcl_ServiceAll après l'intervalle spécifié, même si aucun événement ne s'est produit. Cette interface est nécessaire car Tcl_WaitForEvent n'est pas appelée lorsqu'il y a une boucle d'événements externe. Si le notificateur ne sera utilisé qu'à partir de Tcl_DoOneEvent, alors Tcl_SetTimer n'a rien à faire.

Tcl_ServiceModeHook est appelée par la partie indépendante de la plateforme du notificateur lorsque le code client effectue un appel à Tcl_SetServiceMode. Ce crochet est fourni pour supporter les systèmes d'exploitation qui nécessitent une gestion spéciale des événements lorsque l'application est dans une boucle modale (le notificateur Windows, par exemple, utilise ce crochet pour créer une fenêtre de communication).

Sur les systèmes Unix, la source d'événements de fichiers a également besoin du support du notificateur. La source d'événements de fichiers comprend les procédures Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont décrites dans la page de manuel de Tcl_CreateFileHandler.

Les interfaces Tcl_Sleep et Tcl_DoOneEvent sont décrites dans leurs pages de manuel respectives.

La manière la plus simple de créer un nouveau notificateur est de regarder le code d'un notificateur existant, tel que les fichiers unix/tclUnixNotfy.c ou win/tclWinNotify.c dans la distribution source de Tcl.

REMPLACEMENT DU NOTIFICATEUR

Un notificateur qui a été écrit selon les conventions ci-dessus peut également être installé dans un processus en cours d'exécution à la place du notificateur standard. Ce mécanisme est utilisé pour qu'un seul exécutable puisse être utilisé (avec le notificateur standard) comme programme autonome et être réutilisé (avec un notificateur de remplacement dans une extension chargeable) comme extension à un autre programme, tel qu'un plugin de navigateur Web.

Pour ce faire, l'extension effectue un appel à Tcl_SetNotifier en passant un pointeur vers une structure de données Tcl_NotifierProcs. La structure a la disposition suivante :

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Suite à l'appel à Tcl_SetNotifier, les pointeurs fournis dans la structure Tcl_NotifierProcs remplacent tout notificateur qui aurait été installé dans le processus.

Il est extraordinairement déconseillé de remplacer un notificateur en cours d'exécution. Normalement, Tcl_SetNotifier devrait être appelée au moment de l'initialisation du processus, avant le premier appel à Tcl_InitNotifier.

BOUCLES D'ÉVÉNEMENTS EXTERNES

Les interfaces de notificateur sont conçues de manière à ce que Tcl puisse être intégré dans des applications qui ont leurs propres boucles d'événements privées. Dans ce cas, l'application n'appelle pas Tcl_DoOneEvent sauf en cas de boucles d'événements récursives telles que les appels aux commandes Tcl update ou vwait. La plupart du temps est passé dans la boucle d'événements externe de l'application. Dans ce cas, le notificateur doit s'arranger pour que la boucle d'événements externe rappelle Tcl lorsque quelque chose se passe sur les diverses sources d'événements Tcl. Ces rappels devraient organiser pour que des événements Tcl appropriés soient placés dans la file d'attente d'événements Tcl.

Étant donné que la boucle d'événements externe n'appelle pas Tcl_DoOneEvent régulièrement, il incombe au notificateur de s'assurer que Tcl_ServiceEvent est appelée chaque fois que des événements sont en attente dans la file d'attente d'événements Tcl. La manière la plus simple de le faire est d'invoquer Tcl_ServiceAll à la fin de chaque rappel de la boucle d'événements externe. Cela garantira que toutes les sources d'événements sont sondées, que tous les événements mis en file d'attente sont traités et que tous les gestionnaires inactifs en attente sont traités avant de renvoyer le contrôle à l'application. De plus, les sources d'événements qui doivent sonder les événements peuvent appeler Tcl_SetMaxBlockTime pour forcer la boucle d'événements externe à appeler Tcl, même si aucun événement n'est disponible dans la file d'attente d'événements système.

En tant qu'effet secondaire du traitement des événements détectés dans la boucle d'événements externe principale, Tcl peut invoquer Tcl_DoOneEvent pour démarrer une boucle d'événements récursive dans des commandes comme vwait. Tcl_DoOneEvent invoquera la boucle d'événements externe, ce qui entraînera des rappels comme décrit dans le paragraphe précédent, ce qui entraînera des appels à Tcl_ServiceAll. Cependant, dans ces cas, il est indésirable de traiter les événements dans Tcl_ServiceAll. Le traitement des événements là est inutile car le contrôle retournera immédiatement à la boucle d'événements externe et donc à Tcl_DoOneEvent, qui peut traiter les événements elle-même. De plus, Tcl_DoOneEvent est censé traiter un seul événement, tandis que Tcl_ServiceAll traite normalement tous les événements en attente. Pour gérer cette situation, Tcl_DoOneEvent définit un indicateur pour Tcl_ServiceAll qui le fait retourner sans traiter aucun événement. Cet indicateur est appelé le mode de service ; Tcl_DoOneEvent le restaure à sa valeur précédente avant de retourner. Dans certains cas, cependant, il peut être nécessaire que Tcl_ServiceAll traite les événements même lorsqu'il a été invoqué à partir de Tcl_DoOneEvent. Cela se produit lorsqu'il y a une autre boucle d'événements récursive invoquée via un gestionnaire d'événements appelé par Tcl_DoOneEvent (comme celui qui fait partie d'un widget natif). Dans ce cas, Tcl_DoOneEvent peut ne pas avoir la possibilité de traiter les événements, donc Tcl_ServiceAll doit les traiter tous. Toute boucle d'événements récursive qui appelle une boucle d'événements externe plutôt que Tcl_DoOneEvent doit réinitialiser le mode de service afin que tous les événements soient traités dans Tcl_ServiceAll. Ceci est fait en invoquant la procédure Tcl_SetServiceMode. Si Tcl_SetServiceMode reçoit TCL_SERVICE_NONE, alors les appels à Tcl_ServiceAll retourneront immédiatement sans traiter aucun événement. Si Tcl_SetServiceMode reçoit TCL_SERVICE_ALL, alors les appels à Tcl_ServiceAll se comporteront normalement. Tcl_SetServiceMode renvoie la valeur précédente du mode de service, qui doit être restaurée lorsque la boucle récursive se termine. Tcl_GetServiceMode renvoie la valeur actuelle du mode de service.
