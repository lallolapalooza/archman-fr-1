ARGUMENTS

Tcl_Interp *interp (entrée)
Interpréteur auquel s'applique la limite gérée ou dont les limites seront vérifiées.
int type (entrée)
Le type de limite auquel l'opération fait référence. Ce doit être soit TCL_LIMIT_COMMANDS soit TCL_LIMIT_TIME.
int commandLimit (entrée)
Le nombre maximum de commandes (tel que rapporté par info cmdcount) qui peuvent être exécutées dans l'interpréteur.
Tcl_Time *timeLimitPtr (entrée/sortie)
Un pointeur vers une structure qui contiendra soit la nouvelle limite de temps lue (Tcl_LimitSetTime) soit la limite de temps actuelle écrite (Tcl_LimitGetTime).
int granularity (entrée)
Diviseur qui indique à quelle fréquence une limite particulière doit réellement être vérifiée. Doit être au moins 1.
Tcl_LimitHandlerProc *handlerProc (entrée)
Fonction à appeler lorsqu'une limite particulière est dépassée. Si le handlerProc supprime ou augmente la limite pendant son traitement, l'interpréteur limité sera autorisé à continuer son traitement après le retour du gestionnaire. De nombreux gestionnaires peuvent être attachés à la même limite d'interpréteur; leur ordre d'exécution n'est pas défini, et ils doivent être identifiés par handlerProc et clientData lors de leur suppression.
ClientData clientData (entrée)
Mot arbitraire de la taille d'un pointeur utilisé pour passer un contexte à la fonction handlerProc.
Tcl_LimitHandlerDeleteProc *deleteProc (entrée)
Fonction à appeler chaque fois qu'un gestionnaire est supprimé. Peut être NULL si le clientData ne nécessite aucune suppression.

DESCRIPTION

Le sous-système de limites de ressources de Tcl permet un contrôle précis du temps de calcul qu'un script peut utiliser, et est utile pour les cas où un programme est divisé en plusieurs parties dont certaines sont plus fiables que d'autres (par exemple, les serveurs d'applications web).

Chaque interpréteur peut avoir une limite sur le temps réel d'exécution et une limite sur le nombre de commandes que l'interpréteur peut exécuter. Puisque la vérification de ces limites peut être coûteuse (en particulier la limite de temps), chaque limite a également une granularité de vérification, qui est un diviseur pour un compteur interne du nombre de points dans le noyau où une vérification peut être effectuée (qui se produit juste avant l'exécution d'une commande et à une fréquence non spécifiée entre les commandes en cours d'exécution, ce qui peut se produire dans des boucles while au corps vide).

Le composant final du moteur de limites est un schéma de rappel qui permet des notifications lorsque une limite a été dépassée. Ces rappels peuvent simplement fournir une journalisation, ou peuvent allouer plus de ressources à l'interpréteur pour lui permettre de continuer le traitement plus longtemps.

Lorsqu'une limite est dépassée (et que les rappels ont été exécutés; l'ordre d'exécution des rappels n'est pas spécifié), l'exécution dans l'interpréteur limité est arrêtée en levant une erreur et en définissant un drapeau qui empêche la commande catch de cet interpréteur de piéger cette erreur. Il appartient au contexte qui a lancé l'exécution dans cet interpréteur (généralement l'interpréteur principal) de gérer l'erreur.

API DE VÉRIFICATION DES LIMITES

Pour vérifier les limites de ressources d'un interpréteur, appelez Tcl_LimitCheck, qui renvoie TCL_OK si la limite n'a pas été dépassée (après traitement des rappels) et TCL_ERROR si la limite a été dépassée (auquel cas un message d'erreur est également placé dans le résultat de l'interpréteur). Cette fonction ne devrait être appelée que lorsque Tcl_LimitReady renvoie une valeur non nulle afin que la politique de granularité soit appliquée. Cette API est conçue pour être similaire en utilisation à Tcl_AsyncReady et Tcl_AsyncInvoke.

Lors de la rédaction de code qui peut se comporter comme catch par rapport aux erreurs, vous ne devriez piéger une erreur que si Tcl_LimitExceeded renvoie zéro. Si elle renvoie une valeur non nulle, l'interpréteur est dans un état de limite dépassée et les erreurs devraient être autorisées à se propager au contexte appelant. Vous pouvez également vérifier si un type de limite particulier a été dépassé en utilisant Tcl_LimitTypeExceeded.

CONFIGURATION DES LIMITES

Pour vérifier si une limite a été définie (mais pas si elle a effectivement été dépassée) sur un interpréteur, appelez Tcl_LimitTypeEnabled avec le type de limite que vous souhaitez vérifier. Pour activer une limite particulière, appelez Tcl_LimitTypeSet, et pour désactiver une limite, appelez Tcl_LimitTypeReset.

Le niveau d'une limite de commande peut être défini à l'aide de Tcl_LimitSetCommands et récupéré à l'aide de Tcl_LimitGetCommands. De même pour une limite de temps avec Tcl_LimitSetTime et Tcl_LimitGetTime respectivement, mais avec cette API, la limite de temps est copiée depuis et vers la structure Tcl_Time vers laquelle pointe l'argument timeLimitPtr.

La granularité de vérification d'une limite particulière peut être définie à l'aide de Tcl_LimitSetGranularity et récupérée à l'aide de Tcl_LimitGetGranularity. Notez que les granularités doivent toujours être positives.

RAPPELS DE LIMITES

Pour ajouter un rappel de gestionnaire à invoquer lorsqu'une limite est dépassée, appelez Tcl_LimitAddHandler. L'argument handlerProc décrit la fonction qui sera effectivement appelée; elle doit avoir le prototype suivant :

typedef void Tcl_LimitHandlerProc(
        ClientData clientData,
        Tcl_Interp *interp);

L'argument clientData du gestionnaire sera celui passé à l'argument clientData de Tcl_LimitAddHandler, et interp est l'interpréteur dont la limite a été dépassée.

L'argument deleteProc de Tcl_LimitAddHandler est une fonction à appeler pour supprimer la valeur clientData. Il peut être TCL_STATIC ou NULL si aucune action de suppression n'est nécessaire, ou TCL_DYNAMIC si tout ce qui est nécessaire est de libérer la structure avec Tcl_Free. Sinon, il doit faire référence à une fonction ayant le prototype suivant :

typedef void Tcl_LimitHandlerDeleteProc(
        ClientData clientData);

Un gestionnaire de limite peut être supprimé en utilisant Tcl_LimitRemoveHandler; le gestionnaire supprimé sera le premier trouvé (parmi les gestionnaires ajoutés avec Tcl_LimitAddHandler) avec des arguments type, handlerProc et clientData exactement correspondants. Cette fonction invoque toujours le deleteProc sur le clientData (sauf si le deleteProc était NULL ou TCL_STATIC).
