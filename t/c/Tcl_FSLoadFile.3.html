DESCRIPTION

Il y a plusieurs raisons d'appeler les fonctions de l'API Tcl_FS (par exemple, Tcl_FSAccess et Tcl_FSStat) plutôt que d'appeler directement des fonctions de niveau système comme access et stat. Premièrement, elles fonctionneront de manière multiplateforme, donc une extension qui les appelle devrait fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige certains bugs dans les appels de niveau système. Troisièmement, ces appels de fonction traitent toutes les conversions de chemin « Utf vers natif de la plateforme » qui peuvent être nécessaires (et peuvent mettre en cache les résultats de ces conversions pour une plus grande efficacité lors des appels ultérieurs). Quatrièmement, et peut-être le plus important, toutes ces fonctions sont « conscientes des systèmes de fichiers virtuels ». Tout système de fichiers virtuel (VFS pour faire court) qui a été enregistré (via Tcl_FSRegister) peut rediriger l'accès aux fichiers vers des médias ou des méthodes d'accès alternatifs. Cela signifie que toutes ces fonctions (et donc les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent opérer sur des « fichiers » qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS pour faire court) via cette API est automatiquement « consciente des systèmes de fichiers virtuels ». Bien sûr, si une extension accède directement au système de fichiers natif (via des API spécifiques à la plateforme, par exemple), Tcl ne peut pas intercepter de tels appels.

Si des VFS appropriés ont été enregistrés, les « fichiers » peuvent, pour donner deux exemples, être distants (par exemple, situés sur un serveur ftp distant) ou archivés (par exemple, se trouvant à l'intérieur d'une archive .zip). De tels systèmes de fichiers enregistrés fournissent une table de correspondance de fonctions pour implémenter tout ou partie de la fonctionnalité répertoriée ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat abstraient la déclaration du tampon « struct stat », permettant d'utiliser le même code sur les systèmes avec et sans prise en charge des fichiers de plus de 2 Go.

L'API Tcl_FS est « Tcl_Obj »-ifiée et peut mettre en cache des représentations internes et d'autres chaînes liées aux chemins (par exemple, le répertoire de travail courant). Un effet secondaire est qu'il ne faut pas passer de valeurs avec un nombre de références de zéro à l'une de ces fonctions. Si de tels appels étaient traités, ils pourraient entraîner des fuites de mémoire (dans certaines circonstances, le code du système de fichiers peut souhaiter conserver une référence à la valeur passée, et il ne faut donc pas supposer qu'après le retour de l'un de ces appels, la valeur a toujours un nombre de références de zéro - il peut avoir été incrémenté) ou un défaut de segmentation direct (ou une autre erreur d'accès à la mémoire) en raison de la libération de la valeur à mi-chemin de la manipulation complexe de valeurs requise pour s'assurer que le chemin est entièrement normalisé et absolu pour la détermination du système de fichiers. La leçon pratique à en tirer est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect, et peut causer des erreurs de mémoire. Le path doit avoir son nombre de références incrémenté avant d'être passé, ou décrémenté. Pour cette raison, les valeurs avec un nombre de références de zéro sont considérées comme des chemins de système de fichiers invalides et l'appel de toute fonction de l'API Tcl_FS avec une telle valeur ne produira aucune action.

FONCTIONS API FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable C globale errno sur le code d'erreur POSIX « EXDEV » (qui signifie un « lien inter-domaines »).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable C globale errno sur le code d'erreur POSIX « EXDEV » (qui signifie un « lien inter-domaines »).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction « créer un répertoire » du système de fichiers propriétaire.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction « supprimer un fichier » du système de fichiers propriétaire.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction « supprimer un répertoire » du système de fichiers propriétaire.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « renommer le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable C globale errno sur le code d'erreur POSIX « EXDEV » (qui signifie un « lien inter-domaines »).

Tcl_FSListVolumes appelle chaque système de fichiers ayant une fonction « lister les volumes » non NULL et leur demande de retourner leur liste de volumes racines. Elle accumule les valeurs de retour dans une liste qui est retournée à l'appelant (avec un nombre de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant l'encodage identifié par encodingName et évalue son contenu comme un script Tcl. Elle retourne les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, l'encodage système est utilisé pour lire le contenu du fichier. Si le fichier n'a pas pu être lu, une erreur Tcl est retournée pour décrire pourquoi le fichier n'a pas pu être lu. Le caractère de fin de fichier (eofchar) est « \x1A » (^Z) pour toutes les plateformes. Si vous avez besoin d'un « ^Z » dans le code pour la comparaison de chaînes, vous pouvez utiliser « \x1A », qui sera substitué en toute sécurité par l'interpréteur Tcl en « ^Z ». Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours l'encodage système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier de code binaire en mémoire et retourne les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas, en raison des limitations de l'OS dans le chargement dynamique de code binaire), Tcl tentera de copier le fichier vers un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile inverse l'opération, demandant que la bibliothèque indiquée par loadHandle soit retirée du processus. Notez que, contrairement à la commande unload, cela ne donne aucune opportunité à la bibliothèque de faire du nettoyage.

Les deux fonctions ci-dessus retournent un code de complétion Tcl standard. Si une erreur se produit, un message d'erreur est laissé dans le résultat de l'interp.

Le jeton fourni via la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher dans un répertoire tous les fichiers qui correspondent à un modèle donné. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le globbing. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Notez que le code glob implémente les motifs récursifs en interne, donc cette fonction ne recevra que des motifs simples, qui peuvent être mis en correspondance en utilisant la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment en demandant uniquement que les répertoires soient retournés. Un cas spécial d'appel avec un modèle NULL indique que le chemin doit être vérifié uniquement pour le type correct.

Tcl_FSLink remplace la version bibliothèque de readlink, et l'étend pour prendre en charge la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr sera appelée.

Si toPtr est NULL, une action « lire le lien » est effectuée. Le résultat est un Tcl_Obj spécifiant le contenu du lien symbolique donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant, qui devrait appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl devrait créer un lien d'un des types passés dans l'indicateur linkAction. Cet indicateur est une combinaison OU de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Là où un choix existe (c'est-à-dire plus d'un indicateur est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur de retour doit être toPtr (qui appartient donc déjà à l'appelant). En cas d'échec, NULL est retourné.

Tcl_FSLstat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf contient des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le dernier accès

Structure de fichier. Temps, temps de modification et temps de changement de métadonnées. Voir PORTABLE STAT RESULT API pour une description sur la façon d'écrire du code portable pour la distribution et l'accès à la structure Tcl_StatBuf. Si path existe, Tcl_FSLstat renvoie 0 et la structure statPtr est remplie de données. Sinon, elle renvoie -1 et aucune donnée de stat n'est fournie. Tcl_FSUtime remplace la version de la bibliothèque de utime. Celle-ci renvoie 0 en cas de succès et -1 en cas d'erreur (conformément à la documentation utime). En cas de succès, la fonction met à jour les valeurs atime et mtime du fichier donné. Tcl_FSFileAttrsGet implémente l'accès en lecture pour la sous-commande file attributes de file. La fonction appropriée pour le système de fichiers auquel appartient pathPtr est appelée. Si le résultat est TCL_OK, une valeur est placée dans objPtrRef, qui ne sera valide que temporairement (sauf si Tcl_IncrRefCount est appelée). Tcl_FSFileAttrsSet implémente l'accès en écriture pour la sous-commande file attributes de file. La fonction appropriée pour le système de fichiers auquel appartient pathPtr est appelée. Tcl_FSFileAttrStrings implémente une partie de la sous-commande file attributes de file. La fonction appropriée pour le système de fichiers auquel appartient pathPtr est appelée. La procédure appelée peut renvoyer un tableau de chaînes ou, à la place, renvoyer NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et augmentera son compteur de références avant de l'utiliser. Une fois son utilisation terminée, Tcl diminuera son compteur de références. Par conséquent, si la liste doit être détruite par Tcl à la fin, elle doit avoir un compteur de références de zéro, et si elle ne doit pas être détruite, le système de fichiers doit s'assurer qu'il conserve un compteur de références sur la valeur. Tcl_FSAccess vérifie si le processus serait autorisé à lire, écrire ou tester l'existence d'un fichier (ou objet de système de fichiers) dont le nom est pathname. Si pathname est un lien symbolique sous Unix, les permissions du fichier auquel ce lien symbolique fait référence sont testées. En cas de succès (toutes les permissions demandées), renvoie 0. En cas d'erreur (au moins un bit du mode demandé est refusé ou une autre erreur se produit), renvoie -1. Tcl_FSStat remplit la structure Tcl_StatBuf avec des informations sur le fichier spécifié. Aucun droit d'accès au fichier n'est requis pour obtenir ces informations, mais des droits de parcours sont requis sur tous les répertoires mentionnés dans le chemin menant au fichier. La structure Tcl_StatBuf inclut des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le temps d'accès, le temps de modification et le temps de changement de métadonnées. Voir PORTABLE STAT RESULT API pour une description sur la façon d'écrire du code portable pour la distribution et l'accès à la structure Tcl_StatBuf. Si path existe, Tcl_FSStat renvoie 0 et la structure statPtr est remplie de données. Sinon, elle renvoie -1 et aucune donnée de stat n'est fournie. Tcl_FSOpenFileChannel ouvre un fichier spécifié par pathPtr et renvoie un handle de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est un modèle de la procédure fopen de la bibliothèque d'entrée/sortie standard Unix. La syntaxe et la signification des arguments sont similaires à celles de la commande open de Tcl lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannel renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas nul, Tcl_FSOpenFileChannel laisse un message d'erreur dans le résultat de interp après toute erreur. Le nouveau canal n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez Tcl_RegisterChannel. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, l'action de création du nouveau canal l'assigne également comme substitut du canal standard. Tcl_FSGetCwd remplace la version de getcwd de la bibliothèque. Elle renvoie le répertoire de travail actuel de la bibliothèque Tcl. Celui-ci peut être différent du répertoire de travail natif, ce qui se produit lorsque le répertoire de travail actuel n'est pas dans le système de fichiers natif. Le résultat est un pointeur vers un Tcl_Obj spécifiant le répertoire actuel, ou NULL si le répertoire ne peut pas être déterminé. Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de interp. Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compteur de références doit être décrémenté. Ceci est nécessaire pour la sécurité multi-threads, afin que plusieurs threads puissent accéder à cette fonction et aux fonctions associées, garantissant que les résultats sont toujours valides. Tcl_FSChdir remplace la version de chdir de la bibliothèque. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl s'appuie sur une combinaison de stat et access pour vérifier si le répertoire existe et a les permissions appropriées. Pour les résultats, voir la documentation de chdir. En cas de succès, un enregistrement du chemin réussi est conservé dans cwdPathPtr pour les appels ultérieurs à Tcl_FSGetCwd. Tcl_FSPathSeparator renvoie le caractère séparateur pour l'élément le plus spécifique du chemin spécifié par pathPtr (c'est-à-dire, le dernier fragment du chemin). Le séparateur est renvoyé sous la forme d'un Tcl_Obj contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est renvoyé. Tcl_FSJoinPath prend le Tcl_Obj donné, qui doit être une liste valide (qui peut avoir un compteur de références de zéro), et renvoie la valeur du chemin en considérant les elements premiers comme des segments de chemin valides (chaque segment peut être un chemin complet, un fragment de chemin ou un seul répertoire ou nom de fichier). Si un segment de chemin est en fait un chemin absolu, les segments précédents sont supprimés. Si elements est inférieur à 0, la liste entière est utilisée. Il est possible que la valeur renvoyée soit en fait un élément de la liste donnée, par conséquent l'appelant doit incrémenter le compteur de références du résultat avant de libérer la liste. La valeur renvoyée, typiquement avec un compteur de références de zéro (mais qui pourrait être partagée dans certaines conditions), contient le chemin joint. L'appelant doit incrémenter le compteur de références de la valeur avant de l'utiliser. En particulier, la valeur renvoyée pourrait être un élément de la liste donnée, par conséquent la libération de la liste pourrait libérer la valeur prématurément si un compteur de références n'a pas été pris. Si le nombre d'éléments est zéro, la valeur renvoyée sera une chaîne vide Tcl_Obj. Tcl_FSSplitPath prend le Tcl_Obj donné, qui doit être un chemin valide, et renvoie une valeur de liste avec chaque segment du chemin comme élément. Elle renvoie une valeur de liste avec un compteur de références de zéro. Si le lenPtr passé n'est pas nul, la variable pointée sera mise à jour avec le nombre d'éléments dans la liste renvoyée. Tcl_FSEqualPaths teste si les deux chemins donnés représentent le même objet de système de fichiers. Elle renvoie 1 s'ils sont égaux, 0 s'ils sont différents. Si l'un des chemins est NULL, elle renvoie toujours 0. Tcl_FSGetNormalizedPath tente d'extraire une représentation normalisée unique du chemin donné, dont la valeur chaîne peut être utilisée comme identifiant unique pour le fichier. Elle renvoie le chemin normalisé, détenu par Tcl, ou NULL si le chemin était invalide ou n'a pas pu être converti correctement. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère en interne sur ces représentations), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques ne soit pas la version la plus conviviale d'un chemin. La valeur renvoyée est détenue par Tcl et a une durée de vie équivalente à celle du pathPtr passé (sauf si c'est un chemin relatif, auquel cas le chemin normalisé peut être libéré à tout moment où le cwd change) - l'appelant peut incrémenter le compteur de références s'il le souhaite pour conserver une copie plus longtemps. Tcl_FSJoinToPath prend la valeur donnée, qui est généralement un chemin valide ou NULL, et joint les segments de chemin donnés. Elle renvoie une valeur, typiquement avec un compteur de références de zéro (mais qui pourrait être partagée dans certaines conditions), contenant le chemin joint. L'appelant doit incrémenter le compteur de références de la valeur avant de l'utiliser. Si une valeur passée à cette fonction (pathPtr ou éléments de path) a un compteur de références de zéro, elle sera libérée lorsque cette fonction renverra. Tcl_FSConvertToPathType tente de convertir la valeur Tcl donnée en un type de chemin valide, en tenant compte du fait que le cwd a pu changer même si cette valeur est déjà supposée être du bon type. Le nom de fichier peut commencer par ~ (pour indiquer le répertoire utilisateur actuel) ou ~ (pour indiquer le répertoire de n'importe quel utilisateur). Si la conversion réussit (c'est-à-dire, la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), elle renvoie TCL_OK. Sinon, elle renvoie TCL_ERROR, et peut laisser un message d'erreur dans l'interpréteur. Tcl_FSGetInternalRep extrait la représentation interne d'une valeur de chemin donnée dans le système de fichiers spécifié. Si la valeur appartient à un système de fichiers différent, elle renvoie NULL. Si la représentation interne est actuellement NULL, elle tente de la générer en appelant Tcl_FSCreateInternalRepProc du système de fichiers. Elle renvoie NULL ou une représentation valide du chemin interne. Cette représentation interne est mise en cache, donc des appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. Tcl_FSGetTranslatedPath tente d'extraire le chemin traduit de la valeur Tcl donnée. Si la traduction réussit (c'est-à-dire, la valeur est un chemin valide), elle est renvoyée. Sinon, elle renvoie NULL et peut laisser un message d'erreur dans l'interpréteur. Un chemin traduit ne contient aucun ~ ni ~utilisateur (ceux-ci ont été étendus à leur représentation actuelle dans le système de fichiers). La valeur renvoyée est détenue par l'appelant, qui doit la conserver ou appeler Tcl_DecrRefCount pour s'assurer que la mémoire est libérée. Cette fonction n'a pas d'utilité pratique et Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont normalement des fonctions plus appropriées pour de nombreuses utilisations. Tcl_FSGetTranslatedStringPath fait la même chose que Tcl_FSGetTranslatedPath, mais renvoie une chaîne ou NULL. La chaîne renvoyée est allouée dynamiquement et possédé par l'appelant, qui doit le stocker ou appeler ckfree pour s'assurer qu'il est libéré. Encore une fois, Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des besoins.

Tcl_FSNewNativePath effectue quelque chose comme l'inverse des conversions habituelles obj->path->nativerep. Si un code récupère un chemin sous forme native (depuis, par exemple, readlink ou une boîte de dialogue native), et que ce chemin doit être utilisé au niveau Tcl, alors appeler cette fonction est un moyen efficace de créer le type de valeur de chemin approprié.

La valeur résultante est une valeur de type « chemin » pure, qui ne recevra une représentation sous forme de chaîne UTF-8 que si cela est requis par un code Tcl.

Tcl_FSGetNativePath est destiné aux systèmes de fichiers natifs Win/Unix, afin qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un wrapper pratique autour de Tcl_FSGetInternalRep. Il pourrait être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes (par exemple, sur macOS, une représentation utilisant une spécification de fichier de structure FSRef serait probablement plus efficace). Sous Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Actuellement, la représentation est simplement une chaîne de caractères qui peut contenir soit le chemin relatif, soit un chemin complet, absolu et normalisé dans le codage natif (des conditions complexes dictent lequel de ceux-ci sera fourni, donc aucun ne peut être fiable, sauf si le chemin est connu pour être absolu). Si vous avez besoin d'un chemin natif qui doit être absolu, vous devriez demander la version native d'un chemin normalisé. Si pour une raison quelconque une version non absolue et non normalisée du chemin est nécessaire, celle-ci doit être construite séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache afin que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. La valeur de retour appartient à Tcl et a une durée de vie équivalente à celle du pathPtr passé (sauf s'il s'agit d'un chemin relatif, auquel cas la représentation native peut être libérée à tout moment lorsque le répertoire courant change).

Tcl_FSFileSystemInfo renvoie une liste de deux éléments. Le premier élément est le nom du système de fichiers (par exemple, « native », « vfs », « zip », ou « prowrap », peut-être), et le second est le type particulier du chemin donné au sein de ce système de fichiers (qui dépend du système de fichiers). Le second élément peut être vide si le système de fichiers ne fournit pas de catégorisation supplémentaire des fichiers.

Une valeur de liste valide est retournée, sauf si la valeur du chemin n'est pas reconnue, auquel cas NULL sera retourné.

Tcl_FSGetFileSystemForPath renvoie un pointeur vers le Tcl_Filesystem qui accepte ce chemin comme valide.

Si aucun système de fichiers n'accepte le chemin, NULL est retourné.

Tcl_FSGetPathType détermine si le chemin donné est relatif au répertoire courant, relatif au volume courant, ou absolu.

Il renvoie l'une des valeurs TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, ou TCL_PATH_VOLUME_RELATIVE

L'API DES SYSTÈMES DE FICHIERS VIRTUELS

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un système de fichiers ; ces opérations sont invoquées si nécessaire par la couche générique, ce qui se produit généralement via les fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un élément de données facultatif à associer à ce système de fichiers. Lors de l'appel de cette fonction, Tcl attachera le système de fichiers à la liste des systèmes de fichiers connus, et il deviendra pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera retourné.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et renvoie TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est retourné.

Tcl_FSData renverra le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il renverra NULL.

Tcl_FSMountsChanged est utilisé pour informer le noyau de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

LA STRUCTURE TCL_FILESYSTEM

La structure Tcl_Filesystem contient les champs suivants :

    const char *typeName;
    int structureLength;
    Tcl_FSVersion version;
    Tcl_FSPathInFilesystemProc *pathInFilesystemProc;
    Tcl_FSDupInternalRepProc *dupInternalRepProc;
    Tcl_FSFreeInternalRepProc *freeInternalRepProc;
    Tcl_FSInternalToNormalizedProc *internalToNormalizedProc;
    Tcl_FSCreateInternalRepProc *createInternalRepProc;
    Tcl_FSNormalizePathProc *normalizePathProc;
    Tcl_FSFilesystemPathTypeProc *filesystemPathTypeProc;
    Tcl_FSFilesystemSeparatorProc *filesystemSeparatorProc;
    Tcl_FSStatProc *statProc;
    Tcl_FSAccessProc *accessProc;
    Tcl_FSOpenFileChannelProc *openFileChannelProc;
    Tcl_FSMatchInDirectoryProc *matchInDirectoryProc;
    Tcl_FSUtimeProc *utimeProc;
    Tcl_FSLinkProc *linkProc;
    Tcl_FSListVolumesProc *listVolumesProc;
    Tcl_FSFileAttrStringsProc *fileAttrStringsProc;
    Tcl_FSFileAttrsGetProc *fileAttrsGetProc;
    Tcl_FSFileAttrsSetProc *fileAttrsSetProc;
    Tcl_FSCreateDirectoryProc *createDirectoryProc;
    Tcl_FSRemoveDirectoryProc *removeDirectoryProc;
    Tcl_FSDeleteFileProc *deleteFileProc;
    Tcl_FSCopyFileProc *copyFileProc;
    Tcl_FSRenameFileProc *renameFileProc;
    Tcl_FSCopyDirectoryProc *copyDirectoryProc;
    Tcl_FSLstatProc *lstatProc;
    Tcl_FSLoadFileProc *loadFileProc;
    Tcl_FSGetCwdProc *getCwdProc;
    Tcl_FSChdirProc *chdirProc;
} Tcl_Filesystem;

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche générique du système de fichiers pour effectuer la gamme complète d'actions liées au système de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (presque toutes doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni), et fonctions d'efficacité (qui ne doivent être implémentées que si elles peuvent l'être efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces replis ne sont utilisés que pour gérer les commandes initiées dans Tcl, pas dans C. Cela signifie que si une commande file rename est émise dans Tcl, et que les systèmes de fichiers pertinents n'implémentent pas leur Tcl_FSRenameFileProc, le noyau de Tcl se rabattra alors sur une combinaison d'autres fonctions de système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a un repli supplémentaire). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun de ces replis ne se produit. Ceci est vrai sauf pour les quatre dernières entrées du tableau des systèmes de fichiers (lstat, load, getcwd et chdir) pour lesquelles des replis se produisent effectivement au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme Tcl_Obj les prennent sous forme UTF-8. L'API de l'infrastructure des systèmes de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

INFRASTRUCTURE DU SYSTÈME DE FICHIERS

Ces champs contiennent des informations de base sur la structure du système de fichiers et les adresses des fonctions utilisées pour associer un système de fichiers donné à un chemin de fichier, et pour gérer la représentation interne des chemins de fichier, par exemple, en copiant et en libérant ces représentations.

NOM DU TYPE

Le champ typeName contient une chaîne terminée par null qui identifie le type de système de fichiers implémenté, par exemple, native, zip ou vfs.

LONGUEUR DE LA STRUCTURE

Le champ structureLength est généralement implémenté comme sizeof(Tcl_Filesystem), et il est là pour permettre une compatibilité binaire plus facile si la taille de la structure change dans une future version de Tcl.

VERSION

Le champ version doit être défini sur TCL_FILESYSTEM_VERSION_1.

PROCÉDURE_CHEMIN_DANS_SYSTÈME_DE_FICHIERS

Le champ pathInFilesystemProc contient l'adresse d'une fonction qui est appelée pour déterminer si une valeur de chemin donnée appartient à ce système de fichiers ou non. Tcl n'appellera les autres fonctions du système de fichiers qu'avec un chemin pour lequel cette fonction a renvoyé TCL_OK. Si le chemin n'appartient pas, -1 doit être renvoyé (le comportement de Tcl pour toute autre valeur de retour n'est pas défini). Si TCL_OK est renvoyé, alors le paramètre de sortie optionnel clientDataPtr peut être utilisé pour renvoyer une représentation interne (spécifique au système de fichiers) du chemin, qui sera mise en cache dans la valeur du chemin et pourra être récupérée efficacement par d'autres fonctions du système de fichiers. Tcl mettra également en cache simultanément que ce chemin appartient à ce système de fichiers. Ces caches sont invalidés lorsque les structures de systèmes de fichiers sont ajoutées ou supprimées de la liste interne des systèmes de fichiers connus de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROCÉDURE_DUPLICATION_REPRÉSENTATION_INTERNE

Cette fonction crée une copie de la représentation interne d'un chemin et est appelée lorsque Tcl a besoin de dupliquer une valeur de chemin. Si elle est NULL, Tcl ne copiera tout simplement pas la représentation interne, qui devra peut-être être régénérée plus tard.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

PROCÉDURE_LIBÉRATION_REPRÉSENTATION_INTERNE

Libère la représentation interne. Doit être implémentée si la représentation interne doit être libérée (c'est-à-dire si de la mémoire est allouée lors de la génération d'une représentation interne), mais peut être NULL sinon.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

PROCÉDURE_INTÉRNE_VERS_NORMALISÉ

Fonction pour convertir une représentation interne en un chemin normalisé. N'est requise que si le système de fichiers crée des valeurs pures sans représentation de chaîne ou de chemin. La valeur renvoyée est un objet Tcl dont la représentation de chaîne est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

PROCÉDURE_CRÉATION_REPRÉSENTATION_INTERNE

Fonction pour prendre une valeur de chemin et calculer une représentation interne pour celle-ci, et stocker cette représentation native dans la valeur. Peut être NULL si les chemins n'ont pas de représentation interne, ou si le Tcl_FSPathInFilesystemProc du système de fichiers crée toujours immédiatement une représentation interne pour les chemins qu'il accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

PROCÉDURE_NORMALISATION_CHEMIN

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations de chaîne pour le même chemin. Dans Tcl, chaque chemin doit avoir une représentation normalisée unique. Selon le système de fichiers, il peut y avoir plus d'une représentation non normalisée faisant référence au même chemin (par exemple, un chemin relatif, un chemin avec une casse différente si le système de fichiers est insensible à la casse, un chemin contenant un lien symbolique, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être déréférencé vers la valeur pointée (mais sa casse ou d'autres aspects doivent être rendus uniques). Tous les autres composants du chemin doivent être déréférencés depuis les liens symboliques. Cette exception est nécessaire pour s'aligner avec le comportement de Tcl pour file delete, file rename, file copy avec des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint au début du chemin (c'est-à-dire zéro), à la fin du chemin, ou à n'importe quel séparateur de fichier intermédiaire dans le chemin. Elle ne sera jamais pointée vers une position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémenteur peut supposer que le chemin jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS DU SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions qui sont appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui est censé être utilisé avec l'ensemble complet des commandes Tcl standard doit implémenter toutes ces opérations. Si certaines d'entre elles ne sont pas implémentées, certaines commandes Tcl peuvent échouer lorsqu'elles opèrent sur des chemins de ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques ne devrait pas implémenter la fonction readlink, etc. Le noyau Tcl s'attend à ce que les systèmes de fichiers se comportent ainsi).

PROCÉDURE_TYPE_CHEMIN_SYSTÈME_DE_FICHIERS

Fonction pour déterminer le type d'un chemin dans ce système de fichiers. Peut être NULL, dans ce cas, aucune information de type ne serait disponible pour les utilisateurs de ce système de fichiers. Le type est utilisé uniquement à des fins informatives et doit être renvoyé sous forme de représentation de chaîne de l'objet Tcl renvoyé. Une valeur typique pourrait être networked, zip ou ftp. L'objet Tcl résultant appartient au système de fichiers et Tcl incrémentera donc le compteur de références de la valeur si désiré.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

PROCÉDURE_SÉPARATEUR_SYSTÈME_DE_FICHIERS

Fonction pour renvoyer le caractère séparateur pour ce système de fichiers. Ne doit être implémentée que si le système de fichiers souhaite utiliser un séparateur différent de celui standard /. Entre autres utilisations, elle est renvoyée par la commande file separator. La valeur renvoyée doit avoir un compteur de références de zéro.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

PROCÉDURE_STAT

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent de manière cruciale (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La fonction Tcl_FSStatProc remplira la structure statPtr avec des informations sur le fichier spécifié. Aucun droit sur le fichier n'est requis pour obtenir ces informations, mais des droits de recherche sont requis pour tous les répertoires mentionnés dans le chemin menant à ce fichier. La structure stat inclut des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le dernier accès, la dernière modification et la dernière modification des métadonnées.

Si le fichier représenté par pathPtr existe, le Tcl_FSStatProc renvoie 0 et la structure stat est remplie de données. Sinon, il renvoie -1 et aucune information de stat n'est fournie.

PROCÉDURE_ACCÈS

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent de manière cruciale (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La fonction Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom se trouve dans pathPtr. Si le chemin fait référence à un lien symbolique, il doit tester les permissions du fichier auquel ce lien symbolique fait référence.

En cas de succès (toutes les permissions demandées sont accordées), 0 est renvoyé. En cas d'échec (au moins un bit dans mode demandait une permission refusée, ou une autre erreur s'est produite), -1 est renvoyé.

PROCÉDURE_OUVERTURE_CANAL_FICHIER

Fonction pour traiter un appel Tcl_FSOpenFileChannel. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent de manière cruciale (par exemple, file exists, file readable).

ENFILECHANNELPROC

Fonction pour traiter un appel à Tcl_FSOpenFileChannel. Elle doit être implémentée pour tout système de fichiers raisonnable, car toute opération qui nécessite l'ouverture ou l'accès au contenu d'un fichier utilisera cette fonction (par exemple, open, encoding et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

La Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et retourne un handle de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est calquée sur la fonction fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier, où le mode est une combinaison des indicateurs POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, la Tcl_FSOpenFileChannelProc retourne NULL et enregistre un code d'erreur POSIX qui peut être obtenu avec Tcl_GetErrno. De plus, si interp n'est pas NULL, la Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le nouveau canal ne doit pas être enregistré dans l'interpréteur fourni par une Tcl_FSOpenFileChannelProc ; le travail d'enregistrement incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standards, stdin, stdout ou stderr, était précédemment fermé, la création du nouveau canal l'attribue également comme canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, le fonctionnement de glob et de copie récursive sera perdu dans le système de fichiers (et cela peut affecter des commandes comme encoding names qui utilisent la fonction glob en interne).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit retourner tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au modèle donné et satisfont la spécification des paramètres types. Cette fonction peut être appelée de deux manières. Si pattern est NULL, pathPtr est une spécification complète d'un fichier ou d'un répertoire dont il faut vérifier l'existence et le type. Sinon, pathPtr est un répertoire, et la fonction doit rechercher des fichiers ou des répertoires dont le type est correct. Dans tous les cas, pathPtr peut être supposé non NULL et non vide. Il n'est actuellement pas documenté si pathPtr a un séparateur de fichier à la fin, donc le code doit être flexible dans les deux cas.

La valeur de retour est un résultat standard de Tcl indiquant si une erreur s'est produite pendant le processus de correspondance. Les messages d'erreur sont placés dans interp, sauf si interp est NULL, auquel cas aucun message d'erreur n'est généré ; dans un résultat TCL_OK, les résultats doivent être ajoutés à la valeur resultPtr fournie (qui peut être supposée être une liste valide sans référence partagée). Les éléments ajoutés à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (ce qui signifie généralement qu'il s'agira de spécifications de chemin absolues). Il convient de noter que s'il n'y a pas de correspondances, le résultat est vide ; seules les erreurs réelles de fichier ou de système de fichiers qui pourraient survenir pendant le processus de correspondance sont signalées.

La structure Tcl_GlobTypeData passée dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Type mac accepté */
    Tcl_Obj *macType;
    /* Créateur mac accepté */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de gérer correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types est TCL_GLOB_TYPE_DIR ou TCL_GLOB_TYPE_MOUNT (et en particulier lorsque les autres indicateurs sont faux). Dans le premier cas, la fonction doit lister les répertoires contenus. Tcl utilise cela pour implémenter le globbing récursif, il est donc crucial que les systèmes de fichiers implémentent correctement la correspondance des répertoires. Dans le second cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage qui se trouvent dans le répertoire spécifié par pathPtr (et dans ce cas, pathPtr ne doit pas être dans le même système de fichiers - contrairement à tous les autres cas où cette fonction est appelée). Le support pour cela est critique si Tcl doit avoir des transitions douces entre les systèmes de fichiers.

UTIMEPROC

Fonction pour traiter un appel à Tcl_FSUtime. Elle est requise pour permettre la mise à jour (pas la lecture) des temps de dernière modification et de dernier accès d'un fichier, ainsi que pour l'implémentation des commandes de copie de fichiers file copy (open-r, open-w, fcopy).

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les temps d'accès et de modification du fichier spécifié par pathPtr doivent être changés aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec le système utime.

LINKPROC

Fonction pour traiter un appel à Tcl_FSLink. Elle ne doit être implémentée que si le système de fichiers prend en charge les liens, et dans le cas contraire, elle peut être NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est interrogée sur le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien ne peut pas être lu. Le résultat appartient à l'appelant (et doit donc voir son compteur de références incrémenté avant d'être retourné). Tout appelant doit appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'en a plus besoin. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Dans ce cas, le résultat doit être toPtr si le lien a réussi et NULL dans le cas contraire. Dans ce cas, le résultat n'appartient pas à l'appelant (c'est-à-dire qu'aucune manipulation de compteur de références n'est effectuée des deux côtés). Voir la documentation de Tcl_FSLink pour l'interprétation correcte des indicateurs linkAction.

LISTVOLUMESPROC

Fonction pour lister tous les volumes de système de fichiers ajoutés par ce système de fichiers. Elle ne doit être implémentée que si le système de fichiers ajoute des volumes au début du système de fichiers, afin qu'ils puissent être retournés avec file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste des volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. La valeur du résultat est considérée comme appartenant au système de fichiers (pas au noyau Tcl), mais elle doit se voir attribuer un compteur de références pour Tcl. Tcl utilisera le contenu de la liste, puis décrémentera ce compteur de références. Cela permet aux systèmes de fichiers de décider s'ils veulent réellement conserver une liste globale de volumes ou non (si ce n'est pas le cas, ils génèrent la liste à la volée et la passent à Tcl avec un compteur de références de 1, puis oublient la liste ; si c'est le cas, ils incrémentent le compteur de références de leur liste globale et la passent à Tcl qui copiera le contenu puis décrémentera le compteur de références là où il était).

Par conséquent, Tcl considère les valeurs de retour de cette proc comme en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne supportera pas la commande file attributes. Cela permet d'attacher des informations arbitraires aux fichiers du système de fichiers. Si elle n'est pas implémentée, il n'est pas nécessaire d'implémenter les méthodes get et set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La fonction appelée peut retourner un tableau de chaînes ou retourner NULL et placer une liste Tcl dans le objPtrRef fourni. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Après utilisation, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être détruite par Tcl lorsqu'elle est terminée, elle doit avoir un compteur de références de zéro, et si elle ne doit pas être détruite, le système de fichiers doit s'assurer qu'il retourne une valeur avec un compteur de références d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsGet, utilisée par la commande file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Retourne un code de retour standard de Tcl. La valeur de la chaîne d'attribut obtenue, correspondant à l'élément d'indice index dans la liste retournée par Tcl_FSFileAttrStringsProc, est placée dans objPtrRef (si TCL_OK a été retourné) et aura probablement un compteur de références de zéro. Dans tous les cas, nous devons stocker cette valeur (par exemple, dans le résultat de Tcl) ou incrémenter/décrémenter son compteur de références pour assurer sa libération correcte.

FILEATTRSSETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsSet, utilisée par la commande file attributes. Si le système de fichiers est en lecture seule, il n'est pas nécessaire de l'implémenter.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

La valeur d'attribut de l'élément d'indice index dans la liste retournée par Tcl_FSFileAttrStringsProc doit être définie sur le objPtr donné.

CREATEDIRECTORYPROC

Fonction pour créer un répertoire dans le système de fichiers. Cette procédure doit être implémentée si le système de fichiers prend en charge les répertoires, sinon elle peut être NULL.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode);

La fonction doit créer un répertoire dans le système de fichiers spécifié par pathPtr avec le mode donné.

REATEDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSCreateDirectory. Doit être implémentée sauf si le FS est en lecture seule.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus. En cas de succès, un nouveau répertoire devrait avoir été ajouté au système de fichiers à l'emplacement spécifié par pathPtr.

REMOVEDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSRemoveDirectory. Doit être implémentée sauf si le FS est en lecture seule.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus. En cas de succès, le répertoire spécifié par pathPtr devrait avoir été supprimé du système de fichiers. Si le drapeau recursive est donné, alors un répertoire non vide doit être supprimé sans erreur. Si ce drapeau n'est pas donné et que le répertoire est non vide, une erreur POSIX "EEXIST" devrait être signalée. Si une erreur se produit, le nom du fichier ou du répertoire qui a causé l'erreur doit être placé dans errorPtr.

DELETEFILEPROC

Fonction pour traiter un appel Tcl_FSDeleteFile. Doit être implémentée sauf si le FS est en lecture seule.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus. En cas de succès, le fichier spécifié par pathPtr devrait avoir été supprimé du système de fichiers. Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non Tcl_FSRemoveDirectoryProc lorsque cela est nécessaire pour les supprimer (même s'il s'agit de liens symboliques vers des répertoires).

EFFICACITÉ DU SYSTÈME DE FICHIERS

Ces fonctions n'ont pas besoin d'être implémentées pour un système de fichiers particulier car le noyau dispose d'une implémentation de secours disponible. Voir chaque description individuelle pour les conséquences de laisser le champ NULL.

LSTATPROC

Fonction pour traiter un appel Tcl_FSLstat. Si elle n'est pas implémentée, Tcl tentera d'utiliser la statProc définie ci-dessus à la place. Par conséquent, elle n'a besoin d'être implémentée que si un système de fichiers peut faire la distinction entre les appels stat et lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le comportement de cette fonction est très similaire à celui de Tcl_FSStatProc défini ci-dessus, sauf que si elle est appliquée à un lien symbolique, elle renvoie des informations sur le lien, et non sur le fichier cible.

COPYFILEPROC

Fonction pour traiter un appel Tcl_FSCopyFile. Si elle n'est pas implémentée, Tcl utilisera open-r, open-w et fcopy comme mécanisme de copie. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de copie. Notez que destPathPtr est le nom du fichier qui deviendra la copie de srcPathPtr. Ce n'est jamais le nom d'un répertoire dans lequel srcPathPtr pourrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande file copy au niveau Tcl). Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non copyDirectoryProc lorsque cela est nécessaire pour les copier (même s'il s'agit de liens symboliques vers des répertoires). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file copy, l'appel de Tcl_SetErrno(EXDEV) et le renvoi d'un résultat non-TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standards.

RENAMEFILEPROC

Fonction pour traiter un appel Tcl_FSRenameFile. Si elle n'est pas implémentée, Tcl utilisera un mécanisme de copie et de suppression. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de renommage. Si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file rename, l'appel de Tcl_SetErrno(EXDEV) et le renvoi d'un résultat non-TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standards.

COPYDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSCopyDirectory. Si elle n'est pas implémentée, Tcl utilisera un mécanisme récursif file mkdir, file copy. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de copie. Si une erreur se produit, le nom du fichier ou du répertoire qui a causé l'erreur doit être placé dans errorPtr. Notez que destPathPtr est le nom du répertoire qui deviendra le miroir de srcPathPtr. Ce n'est pas le nom d'un répertoire dans lequel srcPathPtr devrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande file copy au niveau Tcl). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de copie de répertoire, l'appel de Tcl_SetErrno(EXDEV) et le renvoi d'un résultat non-TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standards.

LOADFILEPROC

Fonction pour traiter un appel Tcl_FSLoadFile. Si elle n'est pas implémentée, Tcl utilisera une copie vers un fichier temporaire natif suivie d'un Tcl_FSLoadFile sur cette copie temporaire. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut charger du code directement, ou si elle peut être implémentée simplement pour renvoyer TCL_ERROR afin de désactiver complètement la fonctionnalité de chargement dans ce système de fichiers.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Renvoie un code d'achèvement Tcl standard. Si une erreur se produit, un message d'erreur est laissé dans le résultat de interp. La fonction charge dynamiquement un fichier de code binaire en mémoire. En cas de chargement réussi, handlePtr doit être rempli avec un jeton pour le fichier chargé dynamiquement, et unloadProcPtr doit être rempli avec l'adresse d'une procédure. La procédure de déchargement sera appelée avec le Tcl_LoadHandle donné comme seul paramètre lorsque Tcl aura besoin de décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle renvoyé est actuellement un jeton qui peut être utilisé dans le TclpFindSymbol privé pour accéder aux fonctions du nouveau code. Chaque système de fichiers est libre de définir le Tcl_LoadHandle comme il convient. Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de chargement de fichier, l'appel de Tcl_SetErrno(EXDEV) et le renvoi d'un résultat non-TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standards.

UNLOADFILEPROC

Fonction pour décharger un fichier précédemment chargé avec succès. Si le chargement a été implémenté, alors ceci devrait également être implémenté, s'il y a une action de nettoyage requise.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Fonction pour traiter un appel Tcl_FSGetCwd. La plupart des systèmes de fichiers n'ont pas besoin d'implémenter ceci. Il sera généralement appelé une seule fois, si getcwd est appelé avant chdir. Peut être NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si le système de fichiers prend en charge une notion native de répertoire de travail courant (qui pourrait peut-être changer indépendamment de Tcl), cette fonction devrait renvoyer ce répertoire de travail courant sous forme de résultat, ou NULL si le répertoire courant n'a pas pu être déterminé (par exemple, l'utilisateur n'a pas les permissions appropriées sur le répertoire courant). Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de interp.

CHDIRPROC

Fonction pour traiter un appel Tcl_FSChdir. Si les systèmes de fichiers n'implémentent pas cela, cela sera émulé par une série de vérifications d'accès aux répertoires. Sinon, les systèmes de fichiers virtuels qui l'implémentent n'ont qu'à répondre par un résultat positif si pathPtr est un répertoire valide et accessible dans leur système de fichiers. Ils n'ont pas besoin de se souvenir du résultat, car celui-ci sera automatiquement mémorisé pour être utilisé par Tcl_FSGetCwd. Les systèmes de fichiers réels devraient effectuer l'action correcte (c'est-à-dire appeler l'API système chdir correcte).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

Le Tcl_FSChdirProc change le répertoire de travail courant de l'application à la valeur spécifiée dans pathPtr. La fonction renvoie -1 en cas d'erreur ou 0 en cas de succès.
