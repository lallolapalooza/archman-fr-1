DESCRIPTION

Il y a plusieurs raisons pour lesquelles les fonctions API Tcl_FS (par exemple, Tcl_FSAccess et Tcl_FSStat) sont appelées au lieu d'appeler directement des fonctions de niveau système comme access et stat. Premièrement, elles fonctionnent de manière multiplateforme, de sorte qu'une extension appelant ces fonctions devrait fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige certains bugs dans les appels de niveau système. Troisièmement, ces appels de fonctions gèrent toute conversion de chemins d'UTF-8 en chemins natifs qui pourrait être nécessaire (et peuvent mettre en cache les résultats de ces conversions pour une plus grande efficacité lors d'appels ultérieurs). Quatrièmement, et c'est peut-être le plus important, toutes ces fonctions sont "compatibles avec les systèmes de fichiers virtuels" (virtual filesystem aware). Tout système de fichiers virtuel (VFS en abrégé) enregistré (via Tcl_FSRegister) peut rediriger l'accès aux fichiers vers des supports ou des méthodes alternatifs. Cela signifie que toutes ces fonctions (et par conséquent les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent opérer sur des fichiers qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS en abrégé) via cette API est automatiquement "compatible avec les systèmes de fichiers virtuels". Bien sûr, si une extension accède directement au système de fichiers natif (via des API spécifiques au système, par exemple), alors Tcl ne peut pas intercepter de tels appels.

Si des VFS ont été correctement enregistrés, les fichiers peuvent être, par exemple, distants (comme situés sur un serveur ftp distant) ou archivés (comme situés à l'intérieur d'une archive .zip). Les systèmes de fichiers enregistrés fournissent une table de fonctions qui implémentent tout ou partie des fonctionnalités mentionnées ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat abstraient le contenu du buffer struct stat tel qu'il est réellement déclaré, permettant d'utiliser le même code sur des systèmes avec ou sans prise en charge de fichiers de plus de 2 Go.

L'API Tcl_FS est objectivée par Tcl_Obj et peut mettre en cache des représentations internes et d'autres chaînes liées aux chemins (par exemple, le répertoire courant). Un effet secondaire de ceci est que vous ne devez pas passer de valeurs avec un compteur de références nul à l'une de ces fonctions. Si de tels appels étaient effectués, cela pourrait provoquer des erreurs de mémoire (dans certains cas, le code du système de fichiers pourrait supprimer une référence à la valeur passée, donc vous ne pouvez pas supposer qu'après un appel à ces fonctions la valeur aura toujours un compteur de références nul - elle pourrait avoir été incrémentée). Ou bien, cela pourrait provoquer un segment de faute (ou une autre erreur d'accès à la mémoire) parce que la valeur a été libérée pendant la manipulation complexe des valeurs pour s'assurer que le chemin est normalisé et absolu pour le système de fichiers. La leçon pratique à retenir est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est une mauvaise pratique et peut causer des erreurs de mémoire. Le path doit incrémenter son compteur de références avant d'être passé, ou le décrémenter. Pour cette raison, les valeurs avec un compteur de références nul sont considérées comme invalides en tant que chemins de système de fichiers et l'appel à toute fonction API Tcl_FS avec de telles valeurs n'entraînera aucune action.

FONCTIONS API Tcl_FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés se trouvent sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction de copie de fichier du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la valeur globale errno sur EXDEV (code POSIX indiquant un lien inter-domaines).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés se trouvent sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction de copie de répertoire du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la valeur globale errno sur EXDEV (code POSIX indiquant un lien inter-domaines).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction de création de répertoire du système de fichiers qui le possède.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction de suppression de fichier du système de fichiers qui le possède.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction de suppression de répertoire du système de fichiers qui le possède.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés se trouvent sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction de renommage de fichier du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la valeur globale errno sur EXDEV (code POSIX indiquant un lien inter-domaines).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une méthode de liste de volumes non nulle et lui demande de renvoyer sa liste de volumes racine. Elle accumule les valeurs renvoyées dans une liste qui est renvoyée à l'appelant (avec un compteur de références à 0).

Tcl_FSEvalFileEx lit le contenu du fichier donné par pathPtr en utilisant le codage identifié par encodingName et évalue son contenu en tant que script Tcl. Elle renvoie les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, le codage du système est utilisé pour lire le contenu du fichier. Si le fichier ne peut pas être lu, une erreur Tcl décrivant pourquoi le fichier n'a pas pu être lu est renvoyée. Le caractère EOF pour les fichiers est \x1A (^Z) pour tous les systèmes. Si vous avez besoin d'un ^Z dans le code pour des comparaisons de chaînes, vous pouvez utiliser \x1A, qui sera probablement substitué par l'interpréteur Tcl en ^Z. Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours le codage du système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier binaire en mémoire et renvoie les adresses de deux procédures dans le fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr est appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas en raison des limitations du système d'exploitation sur le chargement de code binaire), Tcl essaie de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile annule cette opération, demandant que la bibliothèque indiquée par loadHandle soit supprimée du processus. Notez que, contrairement à la commande unload, cela ne donne aucune chance à la bibliothèque de nettoyage.

Les deux fonctions ci-dessus renvoient un code de complétion standard Tcl. Si une erreur se produit, un message d'erreur est laissé dans le résultat de l'interp.

Le jeton fourni par la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher tous les fichiers correspondant à un modèle donné dans un répertoire. La fonction appropriée pour le système de fichiers auquel appartient pathPtr est appelée.

La valeur renvoyée est un résultat standard Tcl indiquant s'il y a eu une erreur de globbing. Les messages d'erreur sont placés dans l'interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans le resultPtr donné.

Notez que le code de glob implémente les modèles récursifs en interne, de sorte que cette fonction ne reçoit que des modèles simples, qui peuvent correspondre à la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment en demandant uniquement aux répertoires de renvoyer. Un cas spécial d'appel avec un modèle nul indique que le chemin doit uniquement être vérifié pour le bon type.

Tcl_FSLink remplace la version de la bibliothèque de readlink et l'étend pour prendre en charge la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr est appelée.

Si toPtr est NULL, une action "lire le lien" est effectuée. Le résultat est un objet Tcl spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant, qui doit appeler Tcl_DecrRefCount lorsqu'il n'a plus besoin du résultat. Si toPtr n'est pas NULL, Tcl doit créer un lien de l'un des types passés dans le drapeau linkAction. Ce drapeau est une combinaison OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'il y a un choix (c'est-à-dire plus d'un drapeau est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur renvoyée doit être toPtr (il appartient donc déjà à l'appelant). S'il échoue, NULL est renvoyé.

Tcl_FSLstat remplit la structure statPtr Tcl_StatBuf avec des informations sur le fichier spécifié. Aucun droit d'accès au fichier n'est requis pour obtenir ces informations, mais les droits de recherche sont requis sur tous les répertoires mentionnés dans le chemin menant au fichier. La structure Tcl_StatBuf comprend des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le dernier accès.

Tcl_FSNewNativePath effectue quelque chose comme l'inverse des conversions habituelles obj->path->nativerep. La valeur résultante est une valeur de type "chemin" pure, qui ne recevra une représentation sous forme de chaîne UTF-8 que si cela est requis par un code Tcl.

Tcl_FSGetNativePath est destiné à être utilisé par les systèmes de fichiers natifs Win/Unix, afin qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un wrapper pratique autour de Tcl_FSGetInternalRep. Il peut être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes (par exemple, sur macOS, une représentation utilisant une structure FSRef de fileSpec serait probablement plus efficace). Sous Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Si vous avez besoin d'un chemin natif qui doit être absolu, vous devriez demander la version native d'un chemin normalisé. Si, pour une raison quelconque, une version non absolue et non normalisée du chemin est nécessaire, celle-ci doit être construite séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache afin que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle du pathPtr passé (sauf si c'est un chemin relatif, auquel cas la représentation native peut être libérée à tout moment où le cwd change).

Si aucun système de fichiers n'accepte le chemin, NULL est renvoyé.

L'API DU SYSTÈME DE FICHIERS VIRTUELS

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions qui implémentent les diverses opérations sur un système de fichiers ; ces opérations sont invoquées au besoin par la couche générique, ce qui se produit généralement via les fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées en utilisant les méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et une donnée optionnelle à associer à ce système de fichiers. Lors de l'appel de cette fonction, Tcl attache le système de fichiers à la liste des systèmes de fichiers connus, et il devient pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera renvoyé.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et renvoie TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est renvoyé.

Tcl_FSData renverra le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il renverra NULL.

Tcl_FSMountsChanged est utilisé pour informer le noyau Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent par conséquent ne plus être correctes.

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche générique du système de fichiers pour effectuer la gamme complète des actions liées aux systèmes de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (dont presque toutes doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni), et fonctions d'efficacité (qui n'ont besoin d'être implémentées que si elles peuvent l'être efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose de simulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces substitutions ne sont utilisées que pour gérer les commandes initiées dans Tcl, pas dans C. Cela signifie que si une commande file rename est émise dans Tcl, et que le(s) système(s) de fichiers concerné(s) n'implémentent pas leur Tcl_FSRenameFileProc, le noyau Tcl se rabattra au lieu de cela sur une combinaison d'autres fonctions du système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y aura une autre substitution). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucune de ces substitutions ne se produit. Ceci est vrai sauf pour les quatre dernières entrées du tableau des systèmes de fichiers (lstat, load, getcwd et chdir) pour lesquelles des substitutions se produisent en effet au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme de Tcl_Obj prennent ces noms sous forme UTF-8. L'API d'infrastructure du système de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

INFRASTRUCTURE DU SYSTÈME DE FICHIERS

Ces champs contiennent des informations de base sur la structure du système de fichiers et des adresses de fonctions qui sont utilisées pour associer une valeur de chemin donnée à un système de fichiers, et pour gérer la représentation interne des chemins, par exemple, en copiant et en libérant de telles représentations.

NOM DU TYPE

Le champ typeName contient une chaîne terminée par NULL qui identifie le type de système de fichiers implémenté, par exemple, native, zip ou vfs.

LONGUEUR DE LA STRUCTURE

Le champ structureLength est généralement implémenté comme sizeof(Tcl_Filesystem), et il est là pour permettre la compatibilité binaire ascendante en cas de changements de taille de la structure dans une nouvelle version de Tcl.

VERSION

Le champ version doit être défini à TCL_FILESYSTEM_VERSION_1.

PROCÉDURE PATHINFILESYSTEM

Le champ pathInFilesystemProc contient l'adresse d'une fonction qui est appelée pour déterminer si une valeur de chemin donnée appartient à ce système de fichiers ou non. Tcl n'appellera les fonctions de système de fichiers restantes qu'avec une valeur de chemin pour laquelle cette fonction a renvoyé TCL_OK. Si le chemin n'appartient pas, -1 doit être renvoyé (le comportement de Tcl pour toute autre valeur renvoyée n'est pas défini). Si TCL_OK est renvoyé, alors le paramètre de sortie optionnel clientDataPtr peut être utilisé pour renvoyer une représentation interne (c'est-à-dire spécifique au système de fichiers) du chemin, qui sera stockée dans la valeur du chemin et pourra être récupérée efficacement par d'autres fonctions du système de fichiers. Tcl stockera simultanément l'information que ce chemin appartient à ce système de fichiers. De telles caches sont invalidées lorsque les systèmes de fichiers sont ajoutés ou supprimés de la liste interne des systèmes de fichiers connus de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROCÉDURE DUPINTERNALREP

Cette fonction crée une copie de la représentation interne d'une valeur de chemin et est appelée lorsque Tcl a besoin de dupliquer une valeur de chemin. Si elle est NULL, Tcl ne copiera pas la représentation interne, qui pourrait alors devoir être régénérée.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

PROCÉDURE FREEINTERNALREP

Libère la représentation interne. Doit être implémentée si la libération des représentations internes est nécessaire (c'est-à-dire si de la mémoire est allouée lors de la génération d'une représentation interne), mais peut être NULL dans d'autres cas.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

PROCÉDURE INTERNALTONORMALIZED

Fonction pour convertir une représentation interne en un chemin normalisé. N'est requise que si le système de fichiers crée des valeurs de chemin pures sans représentation chaîne/page. La valeur renvoyée est une valeur Tcl dont la représentation chaîne est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

PROCÉDURE CREATEINTERNALREP

Fonction pour calculer une représentation interne d'une valeur de chemin et la stocker dans la valeur. Peut être NULL si les valeurs de chemin n'ont pas de représentation interne, ou si le Tcl_FSPathInFilesystemProc de ce système de fichiers crée toujours immédiatement une représentation interne pour les valeurs de chemin qu'il accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

PROCÉDURE NORMALIZEPATH

Fonction pour normaliser une valeur de chemin. Doit être implémentée pour tous les systèmes de fichiers qui ont plusieurs représentations de chaîne pour la même valeur de chemin. Dans Tcl, chaque path doit avoir une représentation normalized unique. Selon le système de fichiers, il peut y avoir plus d'une représentation unnormalized qui fait référence au même chemin (par exemple, un chemin relatif, un chemin avec une casse différente si le système de fichiers ne tient pas compte de la casse, un chemin avec une référence au répertoire personnel comme ~, un chemin avec des liens symboliques, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être converti en la valeur qu'il pointe, mais sa casse ou d'autres aspects doivent être uniques. Tous les autres composants du chemin doivent être convertis à partir de liens symboliques. Cette exception est nécessaire pour correspondre au comportement de Tcl pour file delete, file rename, file copy avec des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint au début du chemin (c'est-à-dire zéro), à la fin du chemin, ou à n'importe quel séparateur de fichier intermédiaire dans le chemin. Elle ne fera pas référence à un autre point arbitraire du chemin. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS SUR LE SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent des adresses de fonctions qui sont utilisées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui est censé être utilisé avec l'ensemble complet de commandes Tcl doit implémenter toutes ces fonctions. Si l'une d'entre elles n'est pas implémentée, certaines commandes Tcl peuvent échouer lors de l'opération sur les chemins de ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques ne devrait pas implémenter la fonction readlink, etc. Le noyau Tcl s'attend à ce que les systèmes de fichiers se comportent de cette manière).

PROCÉDURE FILESYSTEMPATHTYPE

Fonction pour déterminer le type d'une valeur de chemin dans ce système de fichiers. Peut être NULL, auquel cas aucune information de type ne sera fournie à l'utilisateur du système de fichiers. Le type est utilisé uniquement à des fins d'information et doit être renvoyé comme la représentation de chaîne de Tcl_Obj renvoyé. Une valeur de retour typique pourrait être networked, zip ou ftp. Le résultat Tcl_Obj appartient au système de fichiers et Tcl incrémentera donc le compteur de références de la valeur si elle le souhaite.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

PROCÉDURE FILESYSTEMSEPARATOR

Fonction pour renvoyer le caractère séparateur de ce système de fichiers. Ceci n'est implémenté que si le système de fichiers souhaite utiliser un séparateur différent du standard /. Entre autres utilisations, elle est renvoyée par la commande file separator. La valeur renvoyée doit avoir un compteur de références de zéro.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

PROCÉDURE STAT

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent de manière cruciale (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La fonction Tcl_FSStatProc remplit la structure de données statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche pour tous les répertoires mentionnés dans le chemin vers le fichier. La structure de données comprend des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), le rdev (identique au périphérique sous Windows), la taille, la dernière date d'accès, la dernière date de modification et la dernière date de modification des métadonnées.

Si le fichier représenté par pathPtr existe, Tcl_FSStatProc renvoie 0 et la structure de données est remplie de données. Sinon, -1 est renvoyé et aucune donnée de stat n'est fournie.

typedef int Tcl_FSAccessProc(

Fonction pour traiter un appel à Tcl_FSOpenFileChannel. Doit être implémentée pour tout système de fichiers raisonnable, car toutes les opérations qui nécessitent l'ouverture ou l'accès au contenu d'un fichier l'utiliseront (par exemple, open, encoding et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

La fonction Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et renvoie un descripteur de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est modelée sur la procédure fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier, où l'argument mode est une combinaison des indicateurs POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannelProc renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le nouveau canal créé ne doit pas être enregistré dans l'interpréteur fourni par une Tcl_FSOpenFileChannelProc; cette tâche incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr**, a été précédemment fermé, l'acte de création du nouveau canal l'assigne également comme remplacement du canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, la fonctionnalité de glob et de copie récursive sera manquante dans le système de fichiers (et cela peut affecter des commandes comme encoding names qui utilisent la fonctionnalité de glob en interne).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit renvoyer tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au motif donné et qui correspondent à la spécification types fournie. Il y a deux façons dont cette fonction peut être appelée. Si pattern est NULL, alors pathPtr est une spécification de chemin complet d'un seul fichier ou répertoire qui doit être vérifié pour son existence et son type correct. Sinon, pathPtr est un répertoire, dont le contenu la fonction doit rechercher les fichiers ou répertoires qui ont le type correct. Dans les deux cas, on peut supposer que pathPtr n'est ni NULL ni vide. Il n'est pas actuellement documenté si pathPtr aura un séparateur de fichier à sa fin ou non, donc le code doit être flexible pour les deux possibilités.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le processus de mise en correspondance. Les messages d'erreur sont placés dans interp, sauf si interp est NULL, auquel cas aucun message d'erreur ne doit être généré ; lors d'un résultat TCL_OK, les résultats doivent être ajoutés à la valeur de resultPtr donnée (qui peut être supposée être une liste Tcl valide non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (cela signifie généralement qu'il s'agira de spécifications de chemin absolu). Notez que si aucune correspondance n'est trouvée, cela conduit simplement à un résultat vide ; les erreurs ne sont signalées que pour les problèmes réels de fichier ou de système de fichiers qui peuvent survenir pendant le processus de mise en correspondance.

La structure Tcl_GlobTypeData passée dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Type Mac acceptable */
    Tcl_Obj *macType;
    /* Créateur Mac acceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de gérer correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT sont vrais (et en particulier lorsque les autres indicateurs sont faux). Dans le premier de ces cas, la fonction doit lister les répertoires contenus. Tcl utilise cela pour implémenter le globbing récursif, il est donc crucial que les systèmes de fichiers implémentent correctement la mise en correspondance des répertoires. Dans le second de ces cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage qui se trouvent dans le pathPtr donné (et dans ce cas, pathPtr n'a pas besoin de se trouver dans le même système de fichiers - différent de tous les autres cas où cette fonction est appelée). Le support pour cela est critique si Tcl doit avoir des transitions transparentes entre un système de fichiers et un autre.

LISTVOLUMESPROC

Fonction pour lister les volumes de système de fichiers ajoutés par ce système de fichiers. Doit être implémentée uniquement si le système de fichiers ajoute des volumes en tête du système de fichiers, afin qu'ils puissent être retournés par file volumes.

Cela permet aux systèmes de fichiers de choisir s'ils souhaitent effectivement conserver une liste "globale" de volumes ou non (sinon, ils génèrent la liste à la volée et la passent à Tcl avec un compteur de références de 1, puis oublient la liste ; si oui, alors ils incrémentent simplement le compteur de références de leur liste globale et la passent à Tcl qui copiera le contenu, puis décrémentera le compteur pour revenir à son état initial).
