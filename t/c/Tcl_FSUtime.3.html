DESCRIPTION

Il y a plusieurs raisons d'appeler les fonctions de l'API Tcl_FS (par exemple, Tcl_FSAccess et Tcl_FSStat) plutôt que d'appeler directement des fonctions de niveau système comme access et stat. Premièrement, elles fonctionneront sur plusieurs plateformes, donc une extension qui les appelle devrait fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige certains bugs dans les appels de niveau système. Troisièmement, ces appels de fonction gèrent les conversions de chemins de « Utf vers natif de la plateforme » qui peuvent être nécessaires (et peuvent mettre en cache les résultats de ces conversions pour une plus grande efficacité lors des appels ultérieurs). Quatrièmement, et peut-être le plus important, toutes ces fonctions sont « conscientes des systèmes de fichiers virtuels ». Tout système de fichiers virtuel (VFS pour raccourci) qui a été enregistré (via Tcl_FSRegister) peut réacheminer l'accès aux fichiers vers des supports ou des méthodes d'accès alternatifs. Cela signifie que toutes ces fonctions (et donc les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent fonctionner sur des « fichiers » qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS pour raccourci) via cette API est automatiquement « consciente des systèmes de fichiers virtuels ». Bien sûr, si une extension accède au système de fichiers natif directement (via des API spécifiques à la plateforme, par exemple), Tcl ne peut pas intercepter de tels appels.

Si des VFS appropriés ont été enregistrés, les « fichiers » peuvent, pour donner deux exemples, être distants (par exemple, situés sur un serveur ftp distant) ou archivés (par exemple, se trouvant à l'intérieur d'une archive .zip). De tels systèmes de fichiers enregistrés fournissent une table de correspondance de fonctions pour implémenter tout ou partie de la fonctionnalité listée ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat abstraient le contenu du tampon « struct stat », permettant d'utiliser le même code sur les systèmes qui prennent en charge les fichiers de plus de 2 Go et ceux qui n'en prennent pas en charge.

L'API Tcl_FS est « Tcl_Obj-ifiée » et peut mettre en cache des représentations internes et d'autres chaînes liées aux chemins (par exemple, le répertoire de travail actuel). Un effet secondaire est qu'il ne faut pas passer de valeurs avec un compteur de références de zéro à aucune de ces fonctions. Si de tels appels étaient traités, ils pourraient entraîner des fuites de mémoire (dans certaines circonstances, le code du système de fichiers peut souhaiter conserver une référence à la valeur passée, et il ne faut donc pas supposer qu'après le retour de l'un de ces appels, la valeur a toujours un compteur de références de zéro - il peut avoir été incrémenté) ou un échec de segmentation direct (ou une autre erreur d'accès à la mémoire) en raison de la libération de la valeur à mi-chemin de la manipulation complexe de valeurs requise pour s'assurer que le chemin est entièrement normalisé et absolu pour la détermination du système de fichiers. La leçon pratique à en tirer est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect et peut provoquer des erreurs de mémoire. La référence de path doit être incrémentée avant de la passer, ou décrémentée. Pour cette raison, les valeurs avec un compteur de références de zéro ne sont pas considérées comme des chemins de système de fichiers valides et tout appel à une fonction de l'API Tcl_FS avec une telle valeur n'aura aucun effet.

FONCTIONS DE L'API FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable C globale errno sur le code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable C globale errno sur le code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction « créer répertoire » du système de fichiers propriétaire.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction « supprimer fichier » du système de fichiers propriétaire.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction « supprimer répertoire » du système de fichiers propriétaire.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « renommer fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la variable C globale errno sur le code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction « lister les volumes » non NULL et leur demande de renvoyer leur liste de volumes racine. Elle accumule les valeurs de retour dans une liste qui est renvoyée à l'appelant (avec un compteur de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant le codage identifié par encodingName et évalue son contenu comme un script Tcl. Elle renvoie les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, le codage système est utilisé pour lire le contenu du fichier. Si le fichier n'a pas pu être lu, une erreur Tcl est renvoyée pour décrire pourquoi le fichier n'a pas pu être lu. Le caractère fin de fichier pour les fichiers est « \x1A » (^Z) pour toutes les plateformes. Si vous avez besoin d'un « ^Z » dans le code pour une comparaison de chaînes, vous pouvez utiliser « \x1A », qui sera substitué en toute sécurité par l'interpréteur Tcl en « ^Z ». Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours le codage système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier de code binaire en mémoire et renvoie les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas, en raison des limitations du système d'exploitation dans le chargement dynamique de code binaire), Tcl tentera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile inverse l'opération, demandant que la bibliothèque indiquée par loadHandle soit supprimée du processus. Notez que, contrairement à la commande unload, cela ne donne pas à la bibliothèque la possibilité de nettoyer.

Les deux fonctions ci-dessus renvoient un code d'achèvement Tcl standard. Si une erreur se produit, un message d'erreur est laissé dans le résultat de l'interp.

Le jeton fourni via la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher dans un répertoire tous les fichiers qui correspondent à un modèle donné. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le globbing. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Notez que le code glob implémente les motifs récursifs en interne, de sorte que cette fonction ne recevra jamais que des motifs simples, qui peuvent être mis en correspondance en utilisant la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment en demandant uniquement le retour des répertoires. Un cas spécial où elle est appelée avec un motif NULL indique que le chemin doit être vérifié uniquement pour le type correct.

Tcl_FSLink remplace la version bibliothèque de readlink, et l'étend pour prendre en charge la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr sera appelée.

Si toPtr est NULL, une action de « lecture de lien » est effectuée. Le résultat est un Tcl_Obj spécifiant le contenu du lien symbolique donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant, qui devrait appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl devrait créer un lien d'un des types passés dans l'indicateur linkAction. Cet indicateur est une combinaison OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'un choix existe (c'est-à-dire que plus d'un indicateur est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur de retour doit être toPtr (qui appartient donc déjà à l'appelant). En cas d'échec, NULL est renvoyé.

Tcl_FSLstat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, la dernière heure d'accès (ce qui suit ...)

Gardez toute la structure du fichier. Si le fichier `path` existe, `Tcl_FSLstat` renvoie 0 et la structure `statPtr` est remplie de données. Sinon, il renvoie -1 et aucune information de stat n'est fournie. `Tcl_FSUtime` remplace la version du système de fichiers de `utime`. Il renvoie 0 en cas de succès et -1 en cas d'erreur (comme dans la documentation de `utime`). En cas de succès, la fonction met à jour les valeurs `atime` et `mtime` du fichier donné. `Tcl_FSFileAttrsGet` implémente l'accès en lecture pour la sous-commande `file` `attributes` des sous-commandes hookables. La fonction appropriée pour le système de fichiers auquel appartient `pathPtr` est appelée. Si le résultat est `TCL_OK`, une valeur est placée dans `objPtrRef`, qui ne sera valide que temporairement (jusqu'à ce que `Tcl_IncrRefCount` soit appelé). `Tcl_FSFileAttrsSet` implémente l'accès en écriture pour la sous-commande `file` `attributes` des sous-commandes hookables. La fonction appropriée pour le système de fichiers auquel appartient `pathPtr` est appelée. `Tcl_FSFileAttrStrings` implémente une partie de la sous-commande `file` `attributes` des sous-commandes hookables. La fonction appropriée pour le système de fichiers auquel appartient `pathPtr` est appelée. L'appel de procédure peut renvoyer un tableau de chaînes ou, à la place, renvoyer `NULL` et placer une liste Tcl dans `objPtrRef`. Tcl prendra cette liste et incrémentera son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera le compteur de références. Par conséquent, si la liste doit être détruite par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si elle ne doit pas être détruite, le système de fichiers doit garantir qu'il maintient un compteur de références à cette valeur. `Tcl_FSAccess` vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est `pathname`. Si `pathname` est un lien symbolique sous Unix, les permissions du fichier auquel ce lien symbolique renvoie sont testées. En cas de succès (toutes les permissions demandées), 0 est renvoyé. En cas d'erreur (au moins un bit dans `mode` demandé est refusé ou une autre erreur s'est produite), -1 est renvoyé. `Tcl_FSStat` remplit la structure `Tcl_StatBuf` avec des informations sur le fichier spécifié. Aucun droit d'accès au fichier n'est requis pour obtenir ces informations, mais des droits de recherche sont requis dans tous les répertoires mentionnés dans le chemin vers le fichier. La structure `Tcl_StatBuf` inclut des informations sur le périphérique, l'inode (0 sous Windows), le mode de privilège, le nombre de liens (1 sous Windows), l'ID utilisateur (0 sous Windows), l'ID de groupe (0 sous Windows), `rdev` (identique au périphérique sous Windows), la taille, la dernière fois d'accès, la dernière fois de modification et la dernière fois de changement de métadonnées d'état. Voir PORTABLE STAT RESULT API pour une description de la manière d'écrire du code portable pour stocker et accéder à la structure `Tcl_StatBuf`. Si `path` existe, `Tcl_FSStat` renvoie 0 et la structure `statPtr` est remplie de données. Sinon, il renvoie -1 et aucune information de stat n'est fournie. `Tcl_FSOpenFileChannel` ouvre un fichier spécifié par `pathPtr` et renvoie un handle de canal qui peut être utilisé pour les opérations d'entrée et de sortie sur le fichier. Cette API est un modèle de la fonction `fopen` de la bibliothèque d'entrée/sortie standard Unix. La syntaxe et la signification des arguments sont similaires à celles de la commande `open` de Tcl lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, `Tcl_FSOpenFileChannel` renvoie `NULL` et enregistre un code d'erreur POSIX qui peut être récupéré avec `Tcl_GetErrno`. De plus, si `interp` n'est pas `NULL`, `Tcl_FSOpenFileChannel` laisse un message d'erreur dans le résultat de `interp` après toute erreur. Le canal nouvellement créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez `Tcl_RegisterChannel`. Si l'un des canaux standard, `stdin`, `stdout` ou `stderr`, a été précédemment fermé, l'action de création du nouveau canal l'assigne également comme substitut du canal standard. `Tcl_FSGetCwd` remplace la version du système de fichiers de `getcwd`. Renvoie le répertoire courant de la librairie Tcl. Cela peut être différent du répertoire de travail natif, ce qui se produit lorsque le répertoire courant n'est pas dans le système de fichiers natif. Le résultat est un pointeur vers un objet Tcl spécifiant le répertoire courant, ou `NULL` si le répertoire ne peut être déterminé. Si `NULL` est renvoyé, un message d'erreur est laissé dans le résultat de `interp`. Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsque vous n'en avez plus besoin, ce compteur doit être décrémenté. Ceci est nécessaire pour des raisons de sécurité multithread, afin de permettre à plusieurs threads d'accéder à ces fonctions et à leurs fonctions associées, tout en garantissant que les résultats sont toujours valides. `Tcl_FSChdir` remplace la version du système de fichiers de `chdir`. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl se rabat sur une combinaison de `stat` et `access` pour vérifier si le répertoire existe et a les permissions appropriées. Pour les résultats, voir la documentation de `chdir`. En cas de succès, un enregistrement du chemin réussi est enregistré dans `cwdPathPtr` pour les appels ultérieurs à `Tcl_FSGetCwd`. `Tcl_FSPathSeparator` renvoie le caractère séparateur utilisé pour l'élément le plus spécifique du chemin spécifié par `pathPtr` (c'est-à-dire la dernière partie du chemin). Le séparateur est renvoyé sous la forme d'un objet Tcl contenant une chaîne de longueur 1. Si le chemin est invalide, il renvoie `NULL`. `Tcl_FSJoinPath` prend l'objet Tcl, qui doit être une liste valide (qui permet d'avoir un compteur de références de zéro), et renvoie la valeur du chemin donné en considérant les `elements` premiers éléments comme des segments de chemin valides (chaque segment peut être un chemin complet, un chemin partiel ou juste un nom de répertoire ou de fichier). Si un segment est réellement un chemin absolu, tous les segments précédents sont ignorés. Si `elements` est inférieur à 0, la liste entière est utilisée. Il est possible que la valeur renvoyée soit réellement un élément de la liste donnée, donc l'appelant doit faire attention à incrémenter le compteur de références du résultat avant de libérer la liste. La valeur renvoyée, typiquement avec un compteur de références de zéro (mais pourrait être partagée dans certaines conditions), contient le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. En particulier, la valeur renvoyée pourrait être un élément de la liste donnée, donc libérer la liste pourrait libérer la valeur prématurément si un compteur de références n'a pas été pris. Si le nombre d'éléments est zéro, la valeur renvoyée sera une chaîne vide `Tcl_Obj`. `Tcl_FSSplitPath` prend l'objet Tcl, qui devrait être un chemin valide, et renvoie une valeur de liste Tcl contenant chaque segment du chemin comme élément. Renvoie une valeur de liste avec un compteur de références de zéro. Si le `lenPtr` passé n'est pas `NULL`, la variable indiquant le nombre d'éléments dans la valeur de liste est mise à jour. `Tcl_FSEqualPaths` teste si deux chemins donnés représentent le même objet de système de fichiers. Renvoie 1 s'ils sont égaux, 0 s'ils sont différents. Si l'un des chemins est `NULL`, il renvoie toujours 0. `Tcl_FSGetNormalizedPath` tente d'extraire d'un objet Tcl une représentation normalisée unique, dont la valeur de chaîne peut être utilisée comme identifiant unique pour le fichier. Renvoie la représentation normalisée du chemin, propriété de Tcl, ou `NULL` si le chemin était invalide ou n'a pas pu être converti. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère en interne sur ces représentations), bien que le résultat lorsque le système de fichiers contient plusieurs liens symboliques ne soit pas la version la plus conviviale d'un chemin. La valeur renvoyée est la propriété de Tcl et a une durée de vie équivalente à celle du `pathPtr` passé (sauf s'il s'agit d'un chemin relatif, auquel cas la valeur normalisée peut être libérée à chaque fois que le cwd change) - l'appelant peut incrémenter le compteur de références s'il le souhaite pour conserver une copie plus longue. `Tcl_FSJoinToPath` prend la valeur donnée, qui est généralement un chemin valide ou `NULL`, et la joint à l'ensemble des segments de chemin donnés. Renvoie une valeur, typiquement avec un compteur de références de zéro (mais pourrait être partagée dans certaines conditions), contenant le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. Si l'une des valeurs passées à cette fonction (`pathPtr` ou éléments de `path`) a un compteur de références de zéro, elle sera libérée lorsque cette fonction renverra. `Tcl_FSConvertToPathType` tente de convertir l'objet Tcl donné en un type de chemin valide, en tenant compte du fait que le cwd peut avoir changé même si cette valeur est déjà du bon type. Le nom de fichier peut commencer par `~` (pour indiquer le répertoire utilisateur courant) ou `~` (pour indiquer le répertoire de n'importe quel utilisateur). Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), `TCL_OK` est renvoyé. Sinon, `TCL_ERROR` est renvoyé, et un message d'erreur peut être dans l'interpréteur. `Tcl_FSGetInternalRep` extrait la représentation interne d'une valeur de chemin donnée dans un système de fichiers spécifié. Si la valeur du chemin appartient à un système de fichiers différent, il renvoie `NULL`. Si la représentation interne est actuellement `NULL`, il tente de la générer en appelant la fonction `Tcl_FSCreateInternalRepProc` du système de fichiers. Renvoie `NULL` ou une représentation interne de chemin valide. Cette représentation interne est mise en cache, donc les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. `Tcl_FSGetTranslatedPath` tente d'extraire le chemin traduit de l'objet Tcl donné. Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), la valeur est renvoyée. Sinon, il renvoie `NULL`, et un message d'erreur peut être dans l'interpréteur. Un chemin traduit est celui qui ne contient aucune séquence de `~` ou `~user` (celles-ci ont été développées en leur représentation actuelle dans le système de fichiers). La valeur renvoyée est la propriété de l'appelant, qui doit la stocker ou appeler `Tcl_DecrRefCount` pour s'assurer que la mémoire est libérée. Cette fonction a peu d'utilité pratique, et `Tcl_FSGetNormalizedPath` ou `Tcl_FSGetNativePath` sont généralement des fonctions plus appropriées pour de nombreuses utilisations. `Tcl_FSGetTranslatedStringPath` fait la même chose que `Tcl_FSGetTranslatedPath`, mais renvoie une chaîne ou `NULL`. La chaîne renvoyée est allouée dynamiquement et doit être stockée ou `Tcl_DecrRefCount` doit être appelé pour s'assurer que la mémoire est libérée. Cette fonction a peu d'utilité pratique, et `Tcl_FSGetNormalizedPath` ou `Tcl_FSGetNativePath` sont généralement des fonctions plus appropriées pour de nombreuses utilisations. par l'appelant, qui doit la stocker ou appeler ckfree pour s'assurer qu'elle est libérée. Encore une fois, Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des usages.

Tcl_FSNewNativePath effectue une opération qui est un peu l'inverse des conversions habituelles obj->path->nativerep. Si un code récupère un chemin sous forme native (provenant par exemple de readlink ou d'une boîte de dialogue native), et que ce chemin doit être utilisé au niveau Tcl, alors appeler cette fonction est un moyen efficace de créer le type de valeur de chemin approprié.

La valeur résultante est une valeur de type « chemin » pure, qui ne recevra une représentation sous forme de chaîne UTF-8 que si cela est requis par un code Tcl.

Tcl_FSGetNativePath est destiné à être utilisé par les systèmes de fichiers natifs Win/Unix, afin qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un wrapper de commodité autour de Tcl_FSGetInternalRep. Il pourrait être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes (par exemple, sur macOS, une représentation utilisant une structure FSRef de fileSpec serait probablement plus efficace). Sous Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Actuellement, la représentation est simplement une chaîne de caractères qui peut contenir soit le chemin relatif, soit un chemin absolu normalisé complet dans l'encodage natif (des conditions complexes dictent lequel de ces deux sera fourni, donc aucun des deux ne peut être utilisé de manière fiable, sauf si le chemin est connu pour être absolu). Si vous avez besoin d'un chemin natif qui doit être absolu, alors vous devriez demander la version native d'un chemin normalisé. Si, pour une raison quelconque, une version non absolue et non normalisée du chemin est nécessaire, celle-ci doit être construite séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache de sorte que les appels répétés à cette fonction n'entraînent pas de conversions supplémentaires. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle du pathPtr passé en argument (sauf si c'est un chemin relatif, auquel cas la représentation native peut être libérée à tout moment où le cwd change).

Tcl_FSFileSystemInfo retourne une liste de deux éléments. Le premier élément est le nom du système de fichiers (par exemple, « native », « vfs », « zip », ou « prowrap », potentiellement), et le second est le type particulier du chemin donné au sein de ce système de fichiers (qui dépend du système de fichiers). Le second élément peut être vide si le système de fichiers ne fournit pas de catégorisation supplémentaire des fichiers.

Une valeur de liste valide est retournée, sauf si la valeur du chemin n'est pas reconnue, auquel cas NULL sera retourné.

Tcl_FSGetFileSystemForPath retourne un pointeur vers le Tcl_Filesystem qui accepte ce chemin comme valide.

Si aucun système de fichiers n'accepte le chemin, NULL est retourné.

Tcl_FSGetPathType détermine si le chemin donné est relatif au répertoire courant, relatif au volume courant, ou absolu.

Il retourne l'une des valeurs TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, ou TCL_PATH_VOLUME_RELATIVE

L'API DU SYSTÈME DE FICHIERS VIRTUEL

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un système de fichiers ; ces opérations sont invoquées au besoin par la couche générique, ce qui se produit généralement via les fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un morceau de données optionnel à associer à ce système de fichiers. Lors de l'appel de cette fonction, Tcl attachera le système de fichiers à la liste des systèmes de fichiers connus, et il deviendra pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera retourné.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et retourne TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est retourné.

Tcl_FSData retournera le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il retournera NULL.

Tcl_FSMountsChanged est utilisé pour informer le noyau de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche générique du système de fichiers pour effectuer la gamme complète d'actions liées au système de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (dont la plupart doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni), et fonctions d'efficacité (qui ne doivent être implémentées que si elles peuvent l'être efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces solutions de repli ne sont utilisées que pour gérer les commandes initiées dans Tcl, pas dans C. Ce que cela signifie, c'est que si une commande file rename est émise dans Tcl, et que les systèmes de fichiers pertinents n'implémentent pas leur Tcl_FSRenameFileProc, le noyau de Tcl se rabattra sur une combinaison d'autres fonctions de système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a un autre repli). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun de ces replis ne se produit. Ceci est vrai à l'exception des quatre dernières entrées de la table des systèmes de fichiers (lstat, load, getcwd et chdir) pour lesquelles des replis se produisent effectivement au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme de Tcl_Obj les prennent dans la forme UTF-8. L'API de l'infrastructure du système de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

INFRASTRUCTURE DU SYSTÈME DE FICHIERS

Ces champs contiennent des informations de base sur la structure du système de fichiers et les adresses des fonctions qui sont utilisées pour associer un système de fichiers particulier à un chemin de fichier, et pour gérer le traitement interne des représentations de chemins, par exemple la copie et la libération de ces représentations.

TYPENAME

Le champ typeName contient une chaîne de caractères terminée par null qui identifie le type du système de fichiers implémenté, par exemple « native », « zip » ou « vfs ».

STRUCTURE LENGTH

Le champ structureLength est généralement implémenté comme sizeof(Tcl_Filesystem), et sert à permettre une compatibilité binaire rétroactive plus facile si la taille de la structure change dans une future version de Tcl.

VERSION

Le champ version doit être défini à TCL_FILESYSTEM_VERSION_1.

PATHINFILESYSTEMPROC

Le champ pathInFilesystemProc contient l'adresse d'une fonction qui est appelée pour déterminer si une valeur de chemin donnée appartient à ce système de fichiers ou non. Tcl n'appellera les autres fonctions du système de fichiers qu'avec un chemin pour lequel cette fonction a retourné TCL_OK. Si le chemin n'appartient pas, -1 doit être retourné (le comportement de Tcl pour toute autre valeur de retour n'est pas défini). Si TCL_OK est retourné, alors le paramètre de sortie optionnel clientDataPtr peut être utilisé pour retourner une représentation interne (spécifique au système de fichiers) du chemin, qui sera mise en cache dans la valeur du chemin, et pourra être récupérée efficacement par les autres fonctions du système de fichiers. Tcl mettra en cache simultanément le fait que ce chemin appartient à ce système de fichiers. De tels caches sont invalidés lorsque des structures de systèmes de fichiers sont ajoutées ou supprimées de la liste interne des systèmes de fichiers connus de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

DUPINTERNALREPPROC

Cette fonction crée une copie de la représentation interne d'un chemin et est appelée lorsque Tcl doit dupliquer une valeur de chemin. Si elle est NULL, Tcl ne copiera tout simplement pas la représentation interne, qui devra alors être régénérée plus tard.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

FREEINTERNALREPPROC

Libère la représentation interne. Cela doit être implémenté si des représentations internes doivent être libérées (c'est-à-dire si de la mémoire est allouée lors de la génération d'une représentation interne), mais peut sinon être NULL.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

INTERNALTONORMALIZEDPROC

Fonction pour convertir la représentation interne en un chemin normalisé. Uniquement nécessaire si le système de fichiers crée des valeurs de chemin pures sans représentation textuelle/de chemin. La valeur de retour est une valeur Tcl dont la représentation textuelle est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

CREATEINTERNALREPPROC

Fonction pour prendre une valeur de chemin, calculer une représentation interne pour celle-ci, et stocker cette représentation native dans la valeur. Peut être NULL si les chemins n'ont pas de représentation interne, ou si le Tcl_FSPathInFilesystemProc pour ce système de fichiers crée toujours immédiatement une représentation interne pour les chemins qu'il accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

NORMALIZEPATHPROC

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations textuelles pour la même valeur de chemin. Dans Tcl, chaque « chemin » doit avoir une représentation textuelle « normalisée » unique. Selon le système de fichiers, il peut y avoir plus d'une représentation textuelle non normalisée qui fait référence à ce chemin (par exemple, un chemin relatif, un chemin avec une casse de caractère différente si le système de fichiers n'est pas sensible à la casse, un chemin contenant une référence à un répertoire personnel comme « ~ », un chemin contenant des liens symboliques, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être converti en la valeur à laquelle il pointe (mais sa casse ou d'autres aspects doivent être rendus uniques). Tous les autres composants du chemin doivent être convertis à partir de liens symboliques. Cette seule exception est nécessaire pour être conforme aux sémantiques de Tcl avec file delete, file rename, file copy opérant sur des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint soit au début du chemin (c'est-à-dire zéro), à la fin du chemin, soit à tout séparateur de fichier intermédiaire dans le chemin. Elle ne pointera jamais vers une autre position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS DU SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions qui sont appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui s'attend à être utilisé avec l'ensemble complet des commandes Tcl standard doit implémenter toutes ces fonctions. Si certaines d'entre elles ne sont pas implémentées, certaines commandes Tcl peuvent échouer lors de l'opération sur des chemins appartenant à ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques n'a pas besoin d'implémenter la fonction readlink, etc. Le noyau Tcl s'attend à ce que les systèmes de fichiers se comportent de cette manière).

FILESYSTEMPATHTYPEPROC

Fonction pour déterminer le type d'un chemin dans ce système de fichiers. Peut être NULL, auquel cas aucune information de type ne sera disponible pour les utilisateurs du système de fichiers. Le « type » est utilisé uniquement à des fins d'information, et doit être retourné comme représentation textuelle du Tcl_Obj retourné. Une valeur de retour typique pourrait être « networked », « zip » ou « ftp ». L'objet Tcl résultant appartient au système de fichiers et Tcl incrémentera donc le compteur de références de cette valeur s'il souhaite en conserver une référence.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

FILESYSTEMSEPARATORPROC

Fonction pour retourner le(s) caractère(s) séparateur(s) pour ce système de fichiers. Cela n'a besoin d'être implémenté que si le système de fichiers souhaite utiliser un séparateur différent de la chaîne standard « / ». Entre autres utilisations, il est retourné par la commande file separator. La valeur de retour doit être une valeur avec un compteur de références de zéro.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

STATPROC

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent crucialement (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le Tcl_FSStatProc remplit la structure stat statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure stat inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification et l'heure du dernier changement de métadonnées.

Si le fichier représenté par pathPtr existe, le Tcl_FSStatProc retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné, et aucune information de stat n'est donnée.

ACCESSPROC

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent crucialement (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

Le Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est dans pathPtr. Si le nom de chemin fait référence à un lien symbolique, alors les permissions du fichier auquel ce lien symbolique fait référence doivent être testées.

En cas de succès (toutes les permissions demandées accordées), zéro est retourné. En cas d'erreur (au moins un bit dans mode demandait une permission refusée, ou une autre erreur s'est produite), -1 est retourné.

OPENFILECHANNELPROC

ILECHANNELPROC

Fonction pour traiter un appel Tcl_FSOpenFileChannel. Doit être implémentée pour tout système de fichiers raisonnable, car toutes les opérations qui nécessitent d'ouvrir ou d'accéder au contenu d'un fichier l'utiliseront (par exemple, open, encoding et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

Le Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et retourne un descripteur de canal qui peut être utilisé pour effectuer des entrées et des sorties sur le fichier. Cette API est modelée sur la procédure fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier, où l'argument mode est une combinaison des indicateurs POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, le Tcl_FSOpenFileChannelProc retourne NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, le Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat d'interp après toute erreur.

Le nouveau canal créé ne doit pas être enregistré dans l'interpréteur fourni par un Tcl_FSOpenFileChannelProc ; cette tâche incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, la création du nouveau canal l'assigne également comme remplacement du canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, alors la fonctionnalité de glob et de copie récursive manquera dans le système de fichiers (et cela peut avoir un impact sur des commandes comme encoding names qui utilisent la fonctionnalité de glob en interne).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit retourner tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au modèle donné et conformément à la spécification des types fournie. Il y a deux façons dont cette fonction peut être appelée. Si pattern est NULL, alors pathPtr est une spécification de chemin complet d'un seul fichier ou répertoire qui doit être vérifié pour son existence et son type correct. Sinon, pathPtr est un répertoire, dont le contenu doit être recherché par la fonction pour trouver des fichiers ou des répertoires du type correct. Dans les deux cas, on peut supposer que pathPtr n'est ni NULL ni vide. Il n'est pas actuellement documenté si pathPtr aura ou non un séparateur de fichier à sa fin, donc le code doit être flexible aux deux possibilités.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du processus de correspondance. Les messages d'erreur sont placés dans interp, à moins que interp ne soit NULL, auquel cas aucun message d'erreur n'a besoin d'être généré ; lors d'un résultat TCL_OK, les résultats doivent être ajoutés à la valeur d'resultPtr donnée (qui peut être supposée être une liste Tcl valide non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (cela signifie généralement qu'elles seront des spécifications de chemin absolu). Notez que si aucune correspondance n'est trouvée, cela conduit simplement à un résultat vide ; les erreurs ne sont signalées que pour les problèmes réels de fichiers ou de système de fichiers qui peuvent survenir pendant le processus de correspondance.

La structure Tcl_GlobTypeData passée dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions du fichier */
    int perm;
    /* Type Mac acceptable */
    Tcl_Obj *macType;
    /* Créateur Mac acceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qui sont importants à gérer correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT sont vrais (et en particulier lorsque les autres indicateurs sont faux). Dans le premier de ces cas, la fonction doit lister les répertoires contenus. Tcl utilise cela pour implémenter le globbing récursif, il est donc essentiel que les systèmes de fichiers implémentent correctement la correspondance des répertoires. Dans le second de ces cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage qui se trouvent dans le pathPtr donné (et dans ce cas, pathPtr n'a pas besoin d'être situé dans le même système de fichiers, contrairement à tous les autres cas où cette fonction est appelée). La prise en charge de cela est essentielle si Tcl doit avoir des transitions transparentes d'un système de fichiers à un autre.

UTIMEPROC

Fonction pour traiter un appel Tcl_FSUtime. Nécessaire pour permettre la définition (pas la lecture) des heures avec file mtime, file atime et l'implémentation d'ouverture-r/ouverture-w/fcopy de file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les heures d'accès et de modification du fichier spécifié par pathPtr doivent être modifiées pour correspondre aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec le utime du système.

LINKPROC

Fonction pour traiter un appel Tcl_FSLink. Ne devrait être implémentée que si le système de fichiers prend en charge les liens, et peut sinon être NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est invitée à lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant (et son compteur de références doit donc être incrémenté avant d'être retourné). Tout appelant doit appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'est plus nécessaire. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Le résultat dans ce cas doit être toPtr si le lien a réussi et NULL sinon. Dans ce cas, le résultat n'appartient pas à l'appelant (c'est-à-dire qu'aucune manipulation de compteur de références des deux côtés n'est nécessaire). Voir la documentation de Tcl_FSLink pour l'interprétation correcte des indicateurs linkAction.

LISTVOLUMESPROC

Fonction pour lister les volumes de systèmes de fichiers ajoutés par ce système de fichiers. Ne devrait être implémentée que si le système de fichiers ajoute des volumes en tête du système de fichiers, afin qu'ils puissent être retournés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste de volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. La valeur de résultat est considérée comme appartenant au système de fichiers (pas au noyau Tcl), mais un compteur de références doit lui être donné pour Tcl. Tcl utilisera le contenu de la liste puis décrémentera ce compteur de références. Cela permet aux systèmes de fichiers de choisir s'ils souhaitent effectivement conserver une liste « globale » de volumes ou non (sinon, ils génèrent la liste à la volée et la transmettent à Tcl avec un compteur de références de 1, puis oublient la liste, sinon, ils incrémentent simplement le compteur de références de leur liste globale et la transmettent à Tcl qui en copiera le contenu puis décrémentera le compteur pour revenir à son état initial).

Par conséquent, Tcl considère les valeurs de retour de ce proc comme étant en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne prendra pas en charge la commande file attributes. Cela permet d'attacher des informations supplémentaires arbitraires aux fichiers dans le système de fichiers. Si elle n'est pas implémentée, il n'est pas nécessaire d'implémenter les méthodes get et set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La fonction appelée peut soit retourner un tableau de chaînes, soit retourner NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. À la fin de cette utilisation, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer qu'il retourne une valeur avec un compteur de références d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel Tcl_FSFileAttrsGet, utilisé par file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Retourne un code de retour Tcl standard. La valeur d'attribut récupérée, qui correspond à l'élément d'index index dans la liste retournée par Tcl_FSFileAttrStringsProc, est un Tcl_Obj placé dans objPtrRef (si TCL_OK a été retourné) et aura probablement un compteur de références de zéro. Dans tous les cas, nous devons soit le stocker quelque part (par exemple, le résultat Tcl), soit incrémenter/décrémenter son compteur de références pour s'assurer qu'il est correctement libéré.

FILEATTRSSETPROC

Fonction pour traiter un appel Tcl_FSFileAttrsSet, utilisé par file attributes. Si le système de fichiers est en lecture seule, il n'est pas nécessaire de l'implémenter.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,

LSTATPROC

Fonction pour traiter un appel à Tcl_FSLstat. Si elle n'est pas implémentée, Tcl essaiera d'utiliser la statProc définie précédemment. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut faire la distinction entre les appels stat et lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le comportement de cette fonction est très similaire à celui de la Tcl_FSStatProc définie précédemment, sauf que si elle s'applique à un lien symbolique, elle renvoie des informations sur le lien, et non sur le fichier auquel il pointe.

COPYFILEPROC

Fonction pour traiter un appel à Tcl_FSCopyFile. Si elle n'est pas implémentée, Tcl se rabattra sur l'émulation de open-r, open-w et fcopy comme mécanisme de copie. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de copie. Il faut noter que destPathPtr est le nom du fichier qui doit devenir la copie de srcPathPtr. Ce n'est jamais le nom d'un répertoire dans lequel srcPathPtr peut être copié (c'est-à-dire que le fonctionnement est beaucoup plus simple que la sous-commande file copy du niveau Tcl). Il faut noter que, si le système de fichiers supporte les liens symboliques, Tcl appellera cette fonction et non la copyDirectoryProc lorsqu'il est nécessaire de les copier (même s'il s'agit de liens symboliques vers des répertoires). Enfin, si le système de fichiers détermine qu'il ne peut pas supporter l'action de copie de fichiers, appeler Tcl_SetErrno(EXDEV) et retourner un résultat autre que TCL_OK amènera Tcl à utiliser ses mécanismes d'émulation standard.

RENAMEFILEPROC

Fonction pour traiter un appel à Tcl_FSRenameFile. Si elle n'est pas implémentée, Tcl se rabattra sur une émulation de copie et de suppression. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de renommage. Si le système de fichiers détermine qu'il ne peut pas supporter l'action de renommage de fichiers, appeler Tcl_SetErrno(EXDEV) et retourner un résultat autre que TCL_OK amènera Tcl à utiliser ses mécanismes d'émulation standard.

COPYDIRECTORYPROC

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,

        Tcl_Obj **errorPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de copie. En cas d'erreur, le nom du fichier ou du répertoire qui a causé l'erreur doit être placé dans errorPtr. Il faut noter que destPathPtr est le nom du répertoire qui doit devenir l'image du répertoire srcPathPtr. Ce n'est jamais le nom d'un répertoire dans lequel srcPathPtr devrait être copié (c'est-à-dire que le fonctionnement est beaucoup plus simple que la sous-commande file copy du niveau Tcl). LOADFILEPROC

Fonction pour traiter un appel à Tcl_FSLoadFile. Si elle n'est pas implémentée, Tcl se rabattra sur une copie vers un fichier temporaire suivie d'un appel à Tcl_FSLoadFile sur ce fichier temporaire. Par conséquent, elle ne doit être implémentée que si le système de fichiers peut charger du code directement, ou si elle peut simplement retourner TCL_ERROR pour désactiver la fonctionnalité de chargement sur ce système de fichiers.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Retourne un code de complétion Tcl standard. En cas d'erreur, un message d'erreur est laissé dans le résultat de l'interp. La fonction charge dynamiquement un fichier binaire en mémoire. En cas de succès, handlePtr doit contenir un jeton pour le fichier chargé dynamiquement, et unloadProcPtr doit contenir l'adresse d'une procédure. La procédure de déchargement sera appelée avec le Tcl_LoadHandle donné comme seul paramètre lorsque Tcl devra décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle retourné est actuellement un jeton qui peut être utilisé dans le TclpFindSymbol privé pour accéder aux fonctions du nouveau code. Chaque système de fichiers peut définir le Tcl_LoadHandle comme il l'entend. Enfin, si le système de fichiers détermine qu'il ne peut pas supporter l'action de chargement de fichiers, appeler Tcl_SetErrno(EXDEV) et retourner un résultat autre que TCL_OK amènera Tcl à utiliser ses mécanismes d'émulation standard.

UNLOADFILEPROC

Fonction pour décharger un fichier qui a été précédemment chargé avec succès. Si le chargement a été implémenté, celui-ci doit également être implémenté s'il y a des actions de nettoyage nécessaires.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Fonction pour traiter un appel à Tcl_FSGetCwd. Plusieurs systèmes de fichiers n'ont pas besoin de l'implémenter. Généralement, elle est appelée une fois, si getcwd est appelé avant chdir. Elle peut être NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si le système de fichiers prend en charge une notation native du répertoire de travail actuel (qui peut changer indépendamment de Tcl), cette fonction devrait renvoyer ce cwd comme résultat, ou NULL si le répertoire de travail actuel ne peut pas être déterminé (par exemple, l'utilisateur n'a pas les permissions appropriées dans le répertoire cwd). Si NULL est retourné, un message d'erreur est laissé dans le résultat de l'interp.

CHDIRPROC

Fonction pour traiter un appel à Tcl_FSChdir. Si les systèmes de fichiers n'implémentent pas celle-ci, elle sera émulée par une série de vérifications d'accès aux répertoires. Autrement, les systèmes de fichiers qui l'implémentent doivent répondre avec un résultat positif si pathPtr est un répertoire valide et accessible sur leur système de fichiers. Ils ne doivent pas se souvenir du résultat, car celui-ci sera automatiquement rappelé par Tcl_FSGetCwd. Les systèmes de fichiers réels doivent effectuer l'action correcte (c'est-à-dire appeler l'API chdir correspondante du système d'exploitation).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

La Tcl_FSChdirProc change le répertoire de travail actuel de l'application vers la valeur spécifiée dans pathPtr. La fonction retourne -1 en cas d'erreur ou 0 en cas de succès.
