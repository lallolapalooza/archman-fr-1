DESCRIPTION

Le système de fichiers Tcl implémente un certain nombre de procédures qui permettent aux programmes Tcl de manipuler des fichiers et des répertoires d'une manière indépendante du système de fichiers sous-jacent. Elles sont disponibles pour toutes les applications Tcl.

Les systèmes de fichiers sont inscrits dans le noyau Tcl à l'aide de la procédure Tcl_FSRegister. La structure de système de fichiers fournie par la procédure Tcl_FSRegister est utilisée pour enregistrer les procédures spécifiques au système de fichiers pour l'implémentation du système de fichiers.

Une seule structure Tcl_Filesystem peut être enregistrée pour chaque système de fichiers. Lorsque cette structure est supprimée du noyau Tcl, la procédure Tcl_FSUnregister est utilisée.

Les applications Tcl utilisent généralement ces procédures via les commandes Tcl natives qui fournissent des interfaces pour manipuler des fichiers et des répertoires. La bibliothèque Tcl fournit des implémentations par défaut pour un certain nombre d'entre elles.

DESCRIPTION

Il y a plusieurs raisons d'appeler les fonctions de l'API Tcl_FS (par exemple, Tcl_FSAccess et Tcl_FSStat) plutôt que d'appeler directement des fonctions de niveau système comme access et stat. Premièrement, elles fonctionneront sur plusieurs plateformes, donc une extension qui les appelle devrait fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige des bogues dans les appels de niveau système. Troisièmement, ces appels de fonction gèrent toutes les conversions de chemin « Utf vers natif de la plateforme » qui peuvent être nécessaires (et peuvent mettre en cache les résultats de ces conversions pour une plus grande efficacité lors des appels ultérieurs). Quatrièmement, et c'est peut-être le plus important, toutes ces fonctions sont « conscientes du système de fichiers virtuel ». Tout système de fichiers virtuel (VFS pour faire court) qui a été enregistré (via Tcl_FSRegister) peut rediriger l'accès aux fichiers vers des supports ou des méthodes d'accès alternatifs. Cela signifie que toutes ces fonctions (et par conséquent les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent opérer sur des « fichiers » qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS pour faire court) via cette API est automatiquement « consciente du système de fichiers virtuel ». Bien sûr, si une extension accède directement au système de fichiers natif (via des API spécifiques à la plateforme, par exemple), Tcl ne peut pas intercepter de tels appels.

Si des VFS appropriés ont été enregistrés, les « fichiers » peuvent, pour donner deux exemples, être distants (par exemple, situés sur un serveur ftp distant) ou archivés (par exemple, se trouvant à l'intérieur d'une archive .zip). De tels systèmes de fichiers enregistrés fournissent une table de correspondance de fonctions pour implémenter tout ou partie des fonctionnalités énumérées ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat s'affranchissent de la déclaration du tampon « struct stat », permettant d'utiliser le même code sur les systèmes qui prennent en charge les fichiers de plus de 2 Go et ceux qui ne le font pas.

L'API Tcl_FS est basée sur Tcl_Obj et peut mettre en cache des représentations internes et d'autres chaînes liées aux chemins (par exemple, le répertoire de travail actuel). Une conséquence est qu'il ne faut pas passer de valeurs avec un nombre de références de zéro à l'une de ces fonctions. Si de tels appels étaient traités, ils pourraient entraîner des fuites de mémoire (dans certaines circonstances, le code du système de fichiers peut souhaiter conserver une référence à la valeur passée, et il ne faut donc pas supposer qu'après le retour de l'un de ces appels, la valeur a toujours un nombre de références de zéro - il pourrait avoir été incrémenté) ou un segmentation fault direct (ou une autre erreur d'accès mémoire) en raison de la libération de la valeur au milieu de la manipulation complexe de valeurs requise pour s'assurer que le chemin est entièrement normalisé et absolu pour la détermination du système de fichiers. La leçon pratique à en tirer est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect et peut causer des erreurs de mémoire. Le nombre de références de path doit être incrémenté avant de le passer, ou décrémenté. Pour cette raison, les valeurs avec un nombre de références de zéro ne sont pas considérées comme des chemins de système de fichiers valides et tout appel à une fonction de l'API Tcl_FS avec une telle valeur n'aura aucun effet.

FONCTIONS DE L'API FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno au code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier le fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno au code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction « créer un répertoire » du système de fichiers propriétaire.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction « supprimer un fichier » du système de fichiers propriétaire.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction « supprimer un répertoire » du système de fichiers propriétaire.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « renommer un fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno au code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction « lister les volumes » non-NULL et leur demande de retourner leur liste de volumes racines. Elle accumule les valeurs de retour dans une liste qui est retournée à l'appelant (avec un nombre de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant l'encodage identifié par encodingName et évalue son contenu comme un script Tcl. Elle retourne les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, l'encodage système est utilisé pour lire le contenu du fichier. Si le fichier n'a pas pu être lu, une erreur Tcl est retournée pour décrire pourquoi le fichier n'a pas pu être lu. Le caractère de fin de fichier (eofchar) est « \x1A » (^Z) pour toutes les plateformes. Si vous avez besoin d'un « ^Z » dans le code pour la comparaison de chaînes, vous pouvez utiliser « \x1A », qui sera remplacé en toute sécurité par l'interpréteur Tcl par « ^Z ». Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours l'encodage système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier de code binaire en mémoire et retourne les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas, en raison des limitations du système d'exploitation pour le chargement dynamique de code binaire), Tcl tentera de copier le fichier vers un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile inverse l'opération, demandant que la bibliothèque indiquée par loadHandle soit retirée du processus. Notez que, contrairement à la commande unload, cela ne donne aucune opportunité à la bibliothèque de nettoyer.

Les deux fonctions ci-dessus retournent un code d'achèvement Tcl standard. En cas d'erreur, un message d'erreur est laissé dans le résultat de l'interp.

Le jeton fourni via la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher dans un répertoire tous les fichiers qui correspondent à un modèle donné. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le globbing. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Notez que le code glob implémente les modèles récursifs en interne, donc cette fonction ne recevra que des modèles simples, qui peuvent être mis en correspondance en utilisant la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment en demandant uniquement des répertoires à retourner. Un cas spécial, lorsqu'elle est appelée avec un modèle NULL, indique que le chemin doit uniquement être vérifié pour le bon type.

Tcl_FSLink remplace la version de bibliothèque de readlink, et l'étend pour prendre en charge la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr sera appelée.

Si toPtr est NULL, une action « lire un lien » est effectuée. Le résultat est un Tcl_Obj spécifiant le contenu du lien symbolique donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant, qui devrait appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl doit créer un lien d'un des types passés dans le drapeau linkAction. Ce drapeau est une combinaison OU de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Lorsqu'un choix existe (c'est-à-dire que plus d'un drapeau est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur de retour devrait être toPtr (qui appartient donc déjà à l'appelant). En cas d'échec, NULL est retourné.

Tcl_FSLstat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf contient des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, la dernière a

temps d'accès, de dernière modification et de dernière modification des métadonnées temps. Voir PORTABLE STAT RESULT API pour une description de la façon d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSLstat renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé, et aucune information stat n'est fournie.

Tcl_FSUtime remplace la version de la bibliothèque de utime.

Cette fonction renvoie 0 en cas de succès et -1 en cas d'erreur (conformément à la documentation de utime). En cas de succès, la fonction mettra à jour les valeurs "atime" et "mtime" du fichier donné.

Tcl_FSFileAttrsGet implémente l'accès en lecture pour la commande d'attributs de file qui peut être interceptée. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

Si le résultat est TCL_OK, une valeur a été placée dans objPtrRef, qui ne sera valide que temporairement (sauf si Tcl_IncrRefCount est appelée).

Tcl_FSFileAttrsSet implémente l'accès en écriture pour la commande d'attributs de file qui peut être interceptée. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

Tcl_FSFileAttrStrings implémente une partie de la commande d'attributs de file qui peut être interceptée. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La procédure appelée peut soit renvoyer un tableau de chaînes de caractères, soit renvoyer NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer qu'il conserve un compteur de références pour la valeur.

Tcl_FSAccess vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet de système de fichiers) dont le nom est pathname. Si pathname est un lien symbolique sur Unix, les permissions du fichier référencé par ce lien symbolique sont testées.

En cas de succès (toutes les permissions demandées accordées), zéro est renvoyé. En cas d'erreur (au moins un bit dans mode a demandé une permission qui est refusée, ou une autre erreur s'est produite), -1 est renvoyé.

Tcl_FSStat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche pour tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'identifiant utilisateur (toujours 0 sous Windows), l'identifiant groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le temps de dernier accès, le temps de dernière modification et le temps de dernière modification des métadonnées. Voir PORTABLE STAT RESULT API pour une description de la façon d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSStat renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé, et aucune information stat n'est fournie.

Tcl_FSOpenFileChannel ouvre un fichier spécifié par pathPtr et renvoie un descripteur de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est basée sur la procédure fopen de la bibliothèque standard d'E/S de Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannel renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannel laisse un message d'erreur dans le résultat de interp après toute erreur.

Le canal nouvellement créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez Tcl_RegisterChannel. Si l'un des canaux standards, stdin, stdout ou stderr a été précédemment fermé, l'acte de création du nouveau canal l'assigne également comme remplacement du canal standard.

Tcl_FSGetCwd remplace la version de la bibliothèque de getcwd.

Elle renvoie le répertoire de travail actuel de la bibliothèque Tcl. Il peut être différent du répertoire de travail de la plateforme native, ce qui se produit lorsque le répertoire de travail actuel n'est pas dans le système de fichiers natif.

Le résultat est un pointeur vers un Tcl_Obj spécifiant le répertoire actuel, ou NULL si le répertoire actuel n'a pas pu être déterminé. Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de l'interpréteur.

Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compteur de références doit être décrémenté. Ceci est nécessaire pour la sécurité des threads, afin de permettre à plusieurs threads d'accéder à cette fonction et aux fonctions associées, tout en garantissant que les résultats sont toujours valides.

Tcl_FSChdir remplace la version de la bibliothèque de chdir. Le chemin est normalisé, puis passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl se rabattra sur une combinaison de stat et access pour vérifier si le répertoire existe et possède les permissions appropriées.

Pour les résultats, voir la documentation de chdir. En cas de succès, nous conservons un enregistrement du chemin réussi dans cwdPathPtr pour les appels ultérieurs à Tcl_FSGetCwd.

Tcl_FSPathSeparator renvoie le caractère séparateur à utiliser pour l'élément le plus spécifique du chemin spécifié par pathPtr (c'est-à-dire la dernière partie du chemin).

Le séparateur est renvoyé sous forme de Tcl_Obj contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est renvoyé.

Tcl_FSJoinPath prend le Tcl_Obj donné, qui doit être une liste valide (qui est autorisée à avoir un compteur de références de zéro), et renvoie la valeur du chemin en considérant les elements premiers éléments comme des segments de chemin valides (chaque segment de chemin peut être un chemin complet, un chemin partiel ou juste un seul répertoire ou nom de fichier possible). Si un segment de chemin est en fait un chemin absolu, alors tous les segments de chemin précédents sont supprimés. Si elements est inférieur à 0, nous utilisons toute la liste.

Il est possible que la valeur renvoyée soit en fait un élément de la liste donnée, de sorte que l'appelant doit faire attention à incrémenter le compteur de références du résultat avant de libérer la liste.

La valeur renvoyée, généralement avec un compteur de références de zéro (mais elle peut être partagée dans certaines conditions), contient le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. En particulier, la valeur renvoyée peut être un élément de la liste donnée, de sorte que la libération de la liste peut libérer prématurément la valeur si aucun compteur de références n'a été pris. Si le nombre d'éléments est zéro, alors la valeur renvoyée sera un Tcl_Obj de chaîne vide.

Tcl_FSSplitPath prend le Tcl_Obj donné, qui devrait être un chemin valide, et renvoie une valeur de liste Tcl contenant chaque segment de ce chemin comme élément. Elle renvoie une valeur de liste avec un compteur de références de zéro. Si le lenPtr passé n'est pas NULL, la variable vers laquelle il pointe sera mise à jour pour contenir le nombre d'éléments dans la liste renvoyée.

Tcl_FSEqualPaths teste si les deux chemins donnés représentent le même objet de système de fichiers. Elle renvoie 1 si les chemins sont égaux, et 0 s'ils sont différents. Si l'un des chemins est NULL, 0 est toujours renvoyé.

Tcl_FSGetNormalizedPath tente d'extraire du Tcl_Obj donné une représentation unique de chemin normalisé, dont la valeur de chaîne peut être utilisée comme identifiant unique du fichier.

Elle renvoie la valeur du chemin normalisé, détenue par Tcl, ou NULL si le chemin était invalide ou ne pouvait pas être converti avec succès. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère sur ces représentations en interne), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques ne soit pas la version la plus conviviale d'un chemin. La valeur renvoyée est détenue par Tcl et a une durée de vie équivalente à celle de pathPtr passé (sauf s'il s'agit d'un chemin relatif, auquel cas la valeur du chemin normalisé peut être libérée à chaque changement de cwd) - l'appelant peut bien sûr incrémenter le compteur de références s'il souhaite conserver une copie plus longtemps.

Tcl_FSJoinToPath prend la valeur donnée, qui devrait généralement être un chemin valide ou NULL, et y joint le tableau de segments de chemin donnés.

Renvoie une valeur, généralement avec un compteur de références de zéro (mais elle peut être partagée dans certaines conditions), contenant le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. Si l'une des valeurs passées à cette fonction (pathPtr ou les éléments de path) a un compteur de références de zéro, elle sera libérée lorsque cette fonction renverra.

Tcl_FSConvertToPathType essaie de convertir le Tcl_Obj donné en un type de chemin Tcl valide, en tenant compte du fait que le cwd peut avoir changé même si cette valeur est déjà censée être du bon type. Le nom de fichier peut commencer par "~" (pour indiquer le répertoire personnel de l'utilisateur actuel) ou "~" (pour indiquer le répertoire personnel de n'importe quel utilisateur).

Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), alors TCL_OK est renvoyé. Sinon, TCL_ERROR est renvoyé, et un message d'erreur peut être laissé dans l'interpréteur.

Tcl_FSGetInternalRep extrait la représentation interne d'une valeur de chemin donnée, dans le système de fichiers donné. Si la valeur du chemin appartient à un système de fichiers différent, nous renvoyons NULL. Si la représentation interne est actuellement NULL, nous tentons de la générer, en appelant Tcl_FSCreateInternalRepProc du système de fichiers.

Renvoie NULL ou une représentation interne de chemin valide. Cette représentation interne est mise en cache, de sorte que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires.

Tcl_FSGetTranslatedPath tente d'extraire le chemin traduit du Tcl_Obj donné.

Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), alors elle est renvoyée. Sinon, NULL sera renvoyé, et un message d'erreur peut être laissé dans l'interpréteur. Un chemin "traduit" est un chemin qui ne contient pas de séquences "~" ou "~utilisateur" (celles-ci ont été développées vers leur représentation actuelle dans le système de fichiers). La valeur renvoyée est détenue par l'appelant, qui doit la stocker ou appeler Tcl_DecrRefCount pour s'assurer que la mémoire est libérée. Cette fonction a peu d'utilité pratique, et Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement des fonctions plus utiles à utiliser pour la plupart des cas.

Tcl_FSGetTranslatedStringPath fait la même chose que Tcl_FSGetTranslatedPath, mais renvoie une chaîne de caractères ou NULL. La chaîne renvoyée est allouée dynamiquement

d et appartient à l'appelant, qui doit le stocker ou appeler ckfree pour s'assurer qu'il est libéré. Encore une fois, Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des objectifs.

Tcl_FSNewNativePath effectue quelque chose comme l'inverse des conversions usuelles obj->path->nativerep. Si un code récupère un chemin sous forme native (à partir de, par exemple, readlink ou d'une boîte de dialogue native), et que ce chemin doit être utilisé au niveau Tcl, alors appeler cette fonction est un moyen efficace de créer le type de valeur de chemin approprié.

La valeur résultante est une valeur pure de « chemin », qui ne recevra une représentation sous forme de chaîne UTF-8 que si cela est requis par un code Tcl.

Tcl_FSGetNativePath est destiné à être utilisé par les systèmes de fichiers natifs Win/Unix, afin qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un wrapper de commodité autour de Tcl_FSGetInternalRep. Il peut être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes (par exemple, sur macOS, une représentation utilisant une structure FSRef de fileSpec serait probablement plus efficace). Sous Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Actuellement, la représentation est simplement une chaîne de caractères qui peut contenir le chemin relatif ou un chemin absolu normalisé complet dans le codage natif (des conditions complexes dictent lequel de ceux-ci sera fourni, de sorte qu'aucun ne peut être utilisé avec certitude, à moins que le chemin ne soit connu pour être absolu). Si vous avez besoin d'un chemin natif qui doit être absolu, vous devez demander la version native d'un chemin normalisé. Si, pour une raison quelconque, une version non absolue et non normalisée du chemin est nécessaire, cela doit être construit séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache afin que les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. La valeur de retour appartient à Tcl et a une durée de vie équivalente à celle du pathPtr passé (sauf si il s'agit d'un chemin relatif, auquel cas la représentation native peut être libérée à tout moment lorsque le cwd change).

Tcl_FSFileSystemInfo renvoie une liste de deux éléments. Le premier élément est le nom du système de fichiers (par exemple, « natif », « vfs », « zip », ou « prowrap », peut-être), et le second est le type particulier du chemin donné dans ce système de fichiers (qui dépend du système de fichiers). Le second élément peut être vide si le système de fichiers ne fournit pas de catégorisation supplémentaire des fichiers.

Une valeur de liste valide est renvoyée, à moins que la valeur du chemin ne soit pas reconnue, auquel cas NULL sera renvoyé.

Tcl_FSGetFileSystemForPath renvoie un pointeur vers le Tcl_Filesystem qui accepte ce chemin comme valide.

Si aucun système de fichiers n'accepte le chemin, NULL est renvoyé.

Tcl_FSGetPathType détermine si le chemin donné est relatif au répertoire courant, relatif au volume courant, ou absolu.

Il renvoie l'un des TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, ou TCL_PATH_VOLUME_RELATIVE

L'API DES SYSTÈMES DE FICHIERS VIRTUELS

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions qui implémentent les différentes opérations sur un système de fichiers ; ces opérations sont invoquées si nécessaire par la couche générique, ce qui se produit généralement par le biais des fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un élément de données optionnel à associer à ce système de fichiers. En appelant cette fonction, Tcl attachera le système de fichiers à la liste des systèmes de fichiers connus, et il deviendra pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera renvoyé.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et renvoie TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est renvoyé.

Tcl_FSData renverra le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il renverra NULL.

Tcl_FSMountsChanged est utilisé pour informer le cœur de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche générique du système de fichiers pour effectuer toute la gamme des actions liées au système de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (dont presque toutes doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni) et fonctions d'efficacité (qui ne doivent être implémentées que si elles peuvent être effectuées efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces solutions de repli ne sont utilisées que pour gérer les commandes initiées en Tcl, pas en C. Ce que cela signifie, c'est que si une commande file rename est émise en Tcl, et que les systèmes de fichiers pertinents n'implémentent pas leur Tcl_FSRenameFileProc, le cœur de Tcl se rabattra sur une combinaison d'autres fonctions de système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a une autre solution de repli). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun de ces replis ne se produit. Ceci est vrai sauf pour les quatre dernières entrées du tableau des systèmes de fichiers (lstat, load, getcwd et chdir) pour lesquelles des replis se produisent en fait au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme Tcl_Obj les prennent sous forme UTF-8. L'API d'infrastructure du système de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

PROC_NORMALISER_CHEMIN

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations de chaîne pour le même chemin. Dans Tcl, chaque chemin doit avoir une seule représentation normalisée unique. Selon le système de fichiers, il peut y avoir plus d'une représentation de chaîne non normalisée qui fait référence au même chemin (par exemple, un chemin relatif, un chemin avec une casse différente si le système de fichiers ne distingue pas la casse, un chemin contenant un lien symbolique comme ~, un chemin contenant des liens symboliques, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être résolu en la valeur vers laquelle il pointe, mais sa casse ou d'autres aspects doivent être rendus uniques. Tous les autres composants du chemin doivent être résolus à partir des liens symboliques. Cette exception est nécessaire pour correspondre à la sémantique de Tcl avec file, delete, file rename, file copy avec des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint au début du chemin (c'est-à-dire zéro), à la fin du chemin, ou à n'importe quel délimiteur de fichier intermédiaire dans le chemin. Elle ne doit pas se diriger vers une position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémenteur peut supposer que le chemin jusqu'au délimiteur inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS DU SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui s'attend à utiliser l'ensemble complet des commandes Tcl doit implémenter toutes ces fonctions. Si certaines d'entre elles ne sont pas implémentées, certaines commandes Tcl peuvent échouer lorsqu'elles opèrent sur des chemins dans ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques ne devrait pas implémenter la fonction readlink, etc. Le noyau Tcl s'attend à ce que les systèmes de fichiers agissent de cette manière).

PROC_TYPE_CHEMIN_SYSTEME_FICHIERS

Fonction pour déterminer le type d'un chemin dans ce système de fichiers. Peut être NULL, auquel cas aucune information de type n'est disponible pour les utilisateurs du système de fichiers. Le type est utilisé uniquement à des fins d'information, et doit être retourné sous forme de représentation chaîne de l'objet Tcl retourné. Une valeur typique pourrait être networked, zip ou ftp. L'objet Tcl résultant appartient au système de fichiers et Tcl incrémentera donc le compteur de références de la valeur si elle le souhaite.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

PROC_SEPARATEUR_SYSTEME_FICHIERS

Fonction pour retourner le caractère séparateur du système de fichiers. Ne doit être implémentée que si le système de fichiers souhaite utiliser un séparateur autre que le / standard. Entre autres utilisations, il est retourné par la commande file separator. La valeur retournée doit avoir un compteur de références nul.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

PROC_STAT

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent de manière cruciale (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La fonction Tcl_FSStatProc remplira la structure statPtr avec des informations sur le fichier spécifié. Aucun droit de lecture, d'écriture ou de test des droits sur les répertoires mentionnés dans le chemin pointant vers le fichier n'est requis. La structure stat inclut des informations sur le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, le nombre de liens (toujours 1 sous Windows), l'UID (toujours 0 sous Windows), le GID (toujours 0 sous Windows), le rdev (identique au périphérique sous Windows), la taille, la dernière date d'accès, la dernière date de modification et la dernière date de changement de métadonnées.

Si le fichier représenté par pathPtr existe, Tcl_FSStatProc retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné et aucune donnée stat n'est fournie.

PROC_ACCES

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent de manière cruciale (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La fonction Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est dans pathPtr. Si le chemin fait référence à un lien symbolique, les droits d'accès du fichier vers lequel pointe ce lien symbolique doivent être testés.

En cas de succès (tous les droits demandés sont accordés), 0 est retourné. En cas d'erreur (au moins un bit dans mode demandant un droit qui ne peut être accordé, ou une autre erreur s'est produite), -1 est retourné.

Fonction pour traiter un appel Tcl_FSOpenFileChannel. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent de manière cruciale (par exemple, file open, file close).

typedef int Tcl_FSOpenFileChannelProc(
        Tcl_Obj *pathPtr,
        int mode);

La fonction Tcl_FSOpenFileChannelProc vérifie si le processus serait autorisé à ouvrir le canal de fichier (ou tout autre objet du système de fichiers) dont le nom est dans pathPtr. Si le chemin fait référence à un lien symbolique, les droits d'accès du fichier vers lequel pointe ce lien symbolique doivent être testés.

En cas de succès (tous les droits demandés sont accordés), 0 est retourné. En cas d'erreur (au moins un bit dans mode demandant un droit qui ne peut être accordé, ou une autre erreur s'est produite), -1 est retourné.

OPENFILECHANNELPROC

Fonction pour traiter un appel à Tcl_FSOpenFileChannel. Elle doit être implémentée pour tout système de fichiers raisonnable, car toute opération nécessitant l'ouverture ou l'accès au contenu d'un fichier utilisera cette fonction (par exemple, open, encoding et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

La Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et renvoie un descripteur de canal qui peut être utilisé pour effectuer des entrées/sorties sur le fichier. Cette API est calquée sur la fonction fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification des arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier, où le mode est une combinaison des indicateurs POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannelProc renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le canal créé doit être enregistré dans l'interpréteur fourni par Tcl_FSOpenFileChannelProc par l'utilisateur; le travail d'enregistrement incombe à Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr, a été précédemment fermé, l'acte de création du nouveau canal l'assigne également comme substitut du canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel à Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, la fonctionnalité de glob et de copie récursive ne sera pas disponible dans le système de fichiers (et cela peut affecter des commandes comme encoding names qui utilisent la fonctionnalité de glob).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit renvoyer tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au modèle donné et qui satisfont la spécification types. Cette fonction peut être appelée de deux manières. Si pattern est NULL, pathPtr est une spécification complète d'un fichier ou d'un répertoire qui doit être vérifié pour son existence et son type. Sinon, pathPtr est un répertoire, et la fonction doit rechercher des fichiers ou des répertoires du type correct. Dans tous les cas, pathPtr peut être considéré comme non NULL et non vide. Bien qu'il ne soit pas documenté si pathPtr aura un séparateur de fichier à la fin, le code doit être flexible pour les deux possibilités.

La valeur de retour est un résultat standard de Tcl indiquant si une erreur s'est produite pendant le processus de correspondance. Les messages d'erreur sont placés dans interp, à moins que interp ne soit NULL, auquel cas aucun message d'erreur n'est généré. Si le résultat est TCL_OK, les résultats doivent être ajoutés à la valeur donnée dans resultPtr (qui peut être considéré comme une liste Tcl non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (ce qui indique généralement qu'il s'agit de spécifications de chemin absolu). Remarque : s'il n'y a pas de correspondances, cela implique simplement un résultat vide; seules des erreurs réelles de fichier ou de système de fichiers qui peuvent survenir pendant le processus de correspondance sont signalées.

Le Tcl_GlobTypeData passé dans le paramètre types contient les champs suivants:

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Type mac accepté */
    Tcl_Obj *macType;
    /* Créateur mac accepté */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qui sont importants à gérer correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types est TCL_GLOB_TYPE_DIR ou TCL_GLOB_TYPE_MOUNT (et en particulier lorsque les autres indicateurs sont faux). Dans le premier cas, la fonction doit lister les répertoires contenus. Tcl utilise cela pour implémenter le globbing récursif, il est donc crucial que les systèmes de fichiers implémentent correctement la correspondance de répertoires. Dans le second cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage trouvés dans le pathPtr donné (et dans ce cas, pathPtr n'a pas besoin d'être sur le même système de fichiers - contrairement à d'autres cas où cette fonction est appelée). Le support pour cela est crucial si Tcl veut avoir des transitions fluides entre différents systèmes de fichiers.

UTIMEPROC

Fonction pour traiter un appel à Tcl_FSUtime. Elle est requise pour permettre la configuration (pas la lecture) des temps de dernier accès et de création de fichiers, ainsi que l'implémentation de l'opération de copie de fichiers (open-r/open-w/fcopy).

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les temps d'accès et de modification des fichiers spécifiés par pathPtr doivent être changés aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec le système utime.

LINKPROC

Fonction pour traiter un appel à Tcl_FSLink. Elle ne doit être implémentée que si le système de fichiers supporte les liens, et peut être NULL dans le cas contraire.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est appelée pour lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien ne peut pas être lu. Le résultat est entièrement la propriété de l'appelant (et donc sa référence doit être incrémentée avant d'être renvoyée). Tout appelant devra appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'en aura plus besoin. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Le résultat dans ce cas doit être toPtr si le lien a réussi et NULL dans le cas contraire. Dans ce cas, le résultat n'est pas la propriété de l'appelant (c'est-à-dire qu'aucune manipulation de compteur de références n'est nécessaire des deux côtés). Consultez la documentation de Tcl_FSLink pour interpréter correctement les indicateurs de linkAction.

LISTVOLUMESPROC

Fonction pour lister tous les volumes de système de fichiers ajoutés par ce système de fichiers. Elle ne doit être implémentée que si le système de fichiers ajoute des volumes au début du système de fichiers, afin qu'ils puissent être renvoyés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste de volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. La valeur de retour est considérée comme la propriété du système de fichiers (et non du cœur de Tcl), mais sa référence doit être incrémentée pour Tcl. Tcl utilisera le contenu de la liste, puis décrémentera la référence. Cela permet aux systèmes de fichiers de choisir s'ils veulent réellement conserver une liste globale de volumes ou non (si ce n'est pas le cas, ils génèrent la liste à la volée et la donnent à Tcl avec une référence de 1, puis oublient la liste; si c'est le cas, ils incrémentent la référence de leur liste globale et la donnent à Tcl qui copiera le contenu, puis décrémentera la référence de là où elle était).

Par conséquent, Tcl considère les valeurs retournées par cette procédure comme étant en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister tous les strings d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne supportera pas la commande file attributes. Cela permet d'ajouter des informations arbitraires supplémentaires aux fichiers du système de fichiers. Si elle n'est pas implémentée, les méthodes get et set n'ont pas besoin d'être implémentées.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La fonction peut renvoyer un tableau de strings, ou elle peut renvoyer NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord sa référence avant de l'utiliser. Après avoir terminé son utilisation, Tcl décrémentera sa référence. Par conséquent, si la liste doit être disposée par Tcl une fois terminée, elle doit avoir une référence de zéro, et si elle ne doit pas être disposée, le système de fichiers doit garantir qu'il renvoie une valeur avec une référence d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsGet, utilisée par file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Renvoie un code de retour standard de Tcl. La valeur de l'attribut obtenu, qui correspond à l'élément index de la liste renvoyée par Tcl_FSFileAttrStringsProc, est placée dans objPtrRef (si TCL_OK a été renvoyé et est susceptible d'avoir une référence de zéro). Dans tous les cas, nous devons stocker la valeur quelque part (par exemple, dans le résultat de Tcl), ou incrémenter/décrémenter sa référence pour garantir qu'elle sera correctement libérée.

FILEATTRSSETPROC

Fonction pour traiter un appel à Tcl_FSFileAttrsSet, utilisée par file attributes. Si le système de fichiers est en lecture seule, il n'est pas nécessaire de l'implémenter.

typedef int Tcl_FSFileAttrsSetProc(

        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

La valeur de l'attribut pour l'élément index dans la liste renvoyée par Tcl_FSFileAttrStringsProc doit être définie sur l'objet objPtr donné.

typedef int Tcl_FSCreateDirectoryProc(

EFFACITÉ DU SYSTÈME DE FICHIERS

Ces fonctions n'ont pas besoin d'être implémentées pour un système de fichiers particulier car le cœur dispose d'une implémentation de secours disponible. Voir chaque description individuelle pour les conséquences de laisser le champ à NULL.

LSTATPROC

Fonction pour traiter un appel Tcl_FSLstat. Si elle n'est pas implémentée, Tcl tentera d'utiliser statProc défini ci-dessus à la place. Par conséquent, elle n'a besoin d'être implémentée que si un système de fichiers peut faire la différence entre les appels stat et lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le comportement de cette fonction est très similaire à celui de Tcl_FSStatProc défini ci-dessus, sauf que si elle est appliquée à un lien symbolique, elle renvoie des informations sur le lien, et non sur le fichier cible.

COPIERFICHIERPROC

Fonction pour traiter un appel Tcl_FSCopyFile. Si elle n'est pas implémentée, Tcl utilisera open-r, open-w et fcopy comme mécanisme de copie. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du processus de copie. Notez que destPathPtr est le nom du fichier qui deviendra la copie de srcPathPtr. Ce n'est jamais le nom d'un répertoire dans lequel srcPathPtr pourrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande file copy au niveau Tcl). Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non copyDirectoryProc lorsqu'il est nécessaire de les copier (même s'il s'agit de liens symboliques vers des répertoires). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file copy, l'appel à Tcl_SetErrno(EXDEV) et le retour d'un résultat non-TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

RENOMMERFICHIERPROC

Fonction pour traiter un appel Tcl_FSRenameFile. Si elle n'est pas implémentée, Tcl utilisera un mécanisme de copie et suppression. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du processus de renommage. Si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file rename, l'appel à Tcl_SetErrno(EXDEV) et le retour d'un résultat non-TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

COPIERANNUAIREPROC

Fonction pour traiter un appel Tcl_FSCopyDirectory. Si elle n'est pas implémentée, Tcl utilisera un mécanisme récursif file mkdir, file copy. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du processus de copie. Si une erreur se produit, le nom du fichier ou du répertoire qui a causé l'erreur doit être placé dans errorPtr. Notez que destPathPtr est le nom du répertoire qui deviendra l'image miroir de srcPathPtr. Ce n'est pas le nom d'un répertoire dans lequel srcPathPtr pourrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande file copy au niveau Tcl). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de copie de répertoire, l'appel à Tcl_SetErrno(EXDEV) et le retour d'un résultat non-TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

CHARGERFICHIERPROC

Fonction pour traiter un appel Tcl_FSLoadFile. Si elle n'est pas implémentée, Tcl utilisera une copie vers un fichier temporaire natif suivie d'un appel Tcl_FSLoadFile sur cette copie temporaire. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut charger du code directement, ou si elle peut être implémentée simplement pour retourner TCL_ERROR afin de désactiver complètement la fonctionnalité de chargement dans ce système de fichiers.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Retourne un code de complétion Tcl standard. En cas d'erreur, un message d'erreur est laissé dans le résultat de l'interp. La fonction charge dynamiquement un fichier de code binaire en mémoire. En cas de succès du chargement, handlePtr doit être rempli avec un jeton pour le fichier chargé dynamiquement, et unloadProcPtr doit être rempli avec l'adresse d'une procédure. La procédure de déchargement sera appelée avec le Tcl_LoadHandle donné comme seul paramètre lorsque Tcl aura besoin de décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle retourné est actuellement un jeton qui peut être utilisé dans le TclpFindSymbol privé pour accéder aux fonctions du nouveau code. Chaque système de fichiers est libre de définir le Tcl_LoadHandle comme il l'entend. Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de chargement de fichier, l'appel à Tcl_SetErrno(EXDEV) et le retour d'un résultat non-TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

OBTENIRCWDPROC

Fonction pour traiter un appel Tcl_FSGetCwd. La plupart des systèmes de fichiers n'ont pas besoin de l'implémenter. Elle ne sera généralement appelée qu'une seule fois, si getcwd est appelé avant chdir. Peut être NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(

Si le système de fichiers prend en charge une notion native de répertoire de travail courant (qui pourrait peut-être changer indépendamment de Tcl), cette fonction doit renvoyer ce répertoire courant comme résultat, ou NULL si le répertoire courant n'a pas pu être déterminé (par exemple, l'utilisateur n'a pas les permissions appropriées sur le répertoire courant). CHANGERANNUAIREPROC

Fonction pour traiter un appel Tcl_FSChdir. Si les systèmes de fichiers ne l'implémentent pas, elle sera émulée par une série de vérifications d'accès aux répertoires.
