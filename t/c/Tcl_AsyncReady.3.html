Tcl_AsyncCreate(3) Procédures de la bibliothèque Tcl Tcl_AsyncCreate(3)

NAME

Tcl_AsyncCreate, Tcl_AsyncMark, Tcl_AsyncInvoke, Tcl_AsyncDelete, Tcl_AsyncReady - gestion des événements asynchrones

SYNOPSIS

#include <tcl.h>

Tcl_AsyncHandler
Tcl_AsyncCreate(proc, clientData)

void
Tcl_AsyncMark(async)

int
Tcl_AsyncInvoke(interp, code)

void
Tcl_AsyncDelete(async)

int
Tcl_AsyncReady()

ARGUMENTS

Tcl_AsyncProc *proc (in)
Procédure à invoquer pour gérer un événement asynchrone.
ClientData clientData (in)
Valeur d'un octet à passer à proc.
Tcl_AsyncHandler async (in)
Jeton pour le gestionnaire d'événements asynchrones.
Tcl_Interp *interp (in)
Interpréteur Tcl sur lequel la commande est en cours d'évaluation lors de l'appel du gestionnaire, ou NULL si le gestionnaire est appelé sans interpréteur actif.
int code (in)
Code de retour de la commande qui s'est terminée dans interp, ou 0 si interp est NULL.

DESCRIPTION

Ces fonctions fournissent un mécanisme sûr pour gérer des événements asynchrones tels que les signaux. Si un événement tel qu'un signal se produit pendant l'évaluation d'un script Tcl, il n'est pas sûr d'effectuer des actions substantielles pour le traiter. Par exemple, il n'est pas sûr d'évaluer un script Tcl, car l'interpréteur pourrait être en train d'évaluer un autre script ; il peut ne pas être sûr d'allouer de la mémoire, car une allocation de mémoire pourrait être en cours lorsque l'événement s'est produit. La seule façon sûre est de marquer un drapeau indiquant que l'événement s'est produit, puis de le gérer lorsque le monde est dans un état propre, par exemple après que la commande Tcl actuelle soit terminée.

Tcl_AsyncCreate, Tcl_AsyncDelete et Tcl_AsyncReady sont thread-safe. Ils accèdent et/ou définissent une structure de données de thread dans le cas d'un noyau construit avec --enable-threads. Le jeton créé par Tcl_AsyncCreate contient les informations nécessaires sur le thread à partir duquel l'appel a été effectué, de sorte qu'en appelant Tcl_AsyncMark(token), seul le thread d'origine sera renvoyé dans le gestionnaire asynchrone.

Tcl_AsyncCreate crée un gestionnaire asynchrone et renvoie un jeton pour celui-ci. Le gestionnaire asynchrone doit être créé avant toute occurrence d'un événement asynchrone qui tente de le gérer (il n'est pas sûr de créer un gestionnaire au moment d'une occurrence). Lorsqu'un événement asynchrone se produit, le code qui détecte l'événement (par exemple, un gestionnaire de signaux) doit appeler Tcl_AsyncMark avec le jeton du gestionnaire. Tcl_AsyncMark marquera le gestionnaire comme prêt à être exécuté, mais ne l'invoquera pas immédiatement. Tcl appellera le proc associé au gestionnaire plus tard, lorsque le monde sera dans un état sûr, et proc pourra alors effectuer les actions associées à l'événement asynchrone. Proc doit avoir les arguments et le résultat correspondant au type Tcl_AsyncProc :

typedef int Tcl_AsyncProc(
        ClientData clientData,
        Tcl_Interp *interp,
        int code);

Le clientData sera le même que le clientData passé à Tcl_AsyncCreate lors de la création du gestionnaire. Si proc est invoqué juste après la fin d'une commande dans un interpréteur, alors interp identifiera l'interpréteur dans lequel la commande a été évaluée et code sera le code de retour renvoyé par cette commande. Le résultat de la commande sera présent dans le résultat de l'interpréteur. Lorsque proc retourne, ce qu'il a laissé dans le résultat de l'interpréteur sera renvoyé comme résultat de la commande, et la valeur renvoyée par proc sera utilisée comme nouveau code de retour de la commande.

Il est également possible que proc soit invoqué lorsqu'aucun interpréteur n'est actif. Cela peut se produire, par exemple, si un événement asynchrone se produit pendant que l'application attend des entrées interactives ou un événement X. Dans ce cas, interp sera NULL et code sera 0, et la valeur renvoyée par proc sera ignorée.

La fonction Tcl_AsyncInvoke est appelée pour invoquer tous les gestionnaires qui sont prêts. La fonction Tcl_AsyncReady renverra une valeur non nulle lorsqu'il y aura des gestionnaires asynchrones prêts ; elle peut être utilisée pour éviter d'appeler Tcl_AsyncInvoke lorsqu'aucun gestionnaire n'est prêt. Tcl appelle Tcl_AsyncReady après chaque évaluation de commande et appelle Tcl_AsyncInvoke si nécessaire. Les applications peuvent également appeler Tcl_AsyncInvoke à des moments intéressants pour l'application. Par exemple, le gestionnaire d'événements de Tcl appelle Tcl_AsyncReady après chaque événement et appelle Tcl_AsyncInvoke si nécessaire. Les arguments interp et code de Tcl_AsyncInvoke ont la même signification que pour proc : ils identifient l'interpréteur actif, le cas échéant, et le code de retour de la commande qui s'est terminée.

Tcl_AsyncDelete supprime un gestionnaire asynchrone de sorte que son proc ne soit jamais invoqué à nouveau. Un gestionnaire peut être supprimé même s'il est prêt, et il ne sera toujours pas invoqué.

Si plusieurs gestionnaires sont activés en même temps, ils sont invoqués dans l'ordre où ils ont été créés (le premier, le plus ancien, en premier). Les valeurs de code et le résultat de l'interpréteur pour les gestionnaires ultérieurs reflètent les valeurs renvoyées par les gestionnaires précédents, de sorte que le gestionnaire le plus récemment créé a le dernier mot sur le résultat de l'interpréteur et le code de retour. Si de nouveaux gestionnaires deviennent prêts pendant que les gestionnaires sont en cours d'exécution, Tcl_AsyncInvoke les invoquera tous ; à chaque étape, il invoque le gestionnaire le plus prioritaire (le plus ancien) qui est prêt, répétant cela jusqu'à ce qu'il n'y ait plus de gestionnaires prêts.

AVERTISSEMENT

Il est presque toujours mauvais qu'un gestionnaire d'événements asynchrones modifie le résultat de l'interpréteur ou renvoie un code différent de l'argument code du gestionnaire. Ce type de comportement peut perturber subtilement l'exécution des scripts et provoquer des erreurs difficiles à trouver. Si un gestionnaire d'événements asynchrones doit évaluer des scripts Tcl, il doit d'abord sauvegarder l'état de l'interpréteur en appelant Tcl_SaveInterpState, en passant l'argument code. Ensuite, lorsque le gestionnaire asynchrone est terminé, il doit restaurer l'état de l'interpréteur en appelant Tcl_RestoreInterpState, puis renvoyer la valeur de l'argument code.
