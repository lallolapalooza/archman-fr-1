ARGUMENTS

Tcl_Interp *interp (in)
Interpréteur à utiliser pour la signalisation des erreurs, ou NULL si aucune signalisation d'erreur n'est souhaitée.
const char *name (in)
Nom de l'encodage à charger.
Tcl_Encoding encoding (in)
L'encodage à interroger, libérer ou utiliser pour convertir du texte. Si encoding est NULL, l'encodage système actuel est utilisé.
Tcl_Obj *objPtr (in)
Nom de l'encodage pour lequel obtenir un jeton.
Tcl_Encoding *encodingPtr (out)
Pointeur vers l'espace mémoire où le jeton d'encodage doit être écrit.
const char *src (in)
Pour les fonctions Tcl_ExternalToUtf, un tableau d'octets dans l'encodage spécifié qui doit être converti en UTF-8. Pour les fonctions Tcl_UtfToExternal et Tcl_WinUtfToTChar, un tableau de caractères UTF-8 à convertir dans l'encodage spécifié.
const TCHAR *tsrc (in)
Un tableau de caractères Windows TCHAR à convertir en UTF-8.
int srcLen (in)
Longueur de src ou tsrc en octets. Si la longueur est négative, la longueur spécifique à l'encodage de la chaîne est utilisée.
Tcl_DString *dstPtr (out)
Pointeur vers une Tcl_DString non initialisée ou libérée dans laquelle le résultat converti sera stocké.
int flags (in)
Divers bits de drapeau combinés par OR. TCL_ENCODING_START signifie que le tampon source est le premier bloc d'un flux d'entrée (potentiellement multi-blocs), indiquant à la routine de conversion de réinitialiser à un état initial et d'effectuer toute initialisation nécessaire avant la conversion du premier octet. TCL_ENCODING_END signifie que le tampon source est le dernier bloc d'un flux d'entrée (potentiellement multi-blocs), indiquant à la routine de conversion d'effectuer toute finalisation nécessaire après la conversion du dernier octet, puis de réinitialiser à un état initial. TCL_ENCODING_STOPONERROR signifie que la routine de conversion doit retourner immédiatement à la lecture d'un caractère source qui n'existe pas dans l'encodage cible ; sinon, un caractère de remplacement par défaut sera automatiquement substitué.
Tcl_EncodingState *statePtr (in/out)
Utilisé lors de la conversion d'un flux d'octets (généralement long ou de longueur indéfinie) morceau par morceau. La routine de conversion stocke son état actuel dans *statePtr après la conversion de src (le tampon contenant le morceau actuel) ; ces informations d'état doivent être renvoyées lors de la conversion du morceau suivant du flux afin que la routine de conversion sache dans quel état elle s'est arrêtée à la fin du morceau précédent. Peut être NULL, auquel cas la valeur spécifiée pour flags est ignorée et le tampon source est supposé contenir la chaîne complète à convertir.
char *dst (out)
Tampon dans lequel le résultat converti sera stocké. Pas plus de dstLen octets seront stockés dans dst.
int dstLen (in)
La longueur maximale du tampon de sortie dst en octets.
int *srcReadPtr (out)
Rempli avec le nombre d'octets de src qui ont été effectivement convertis. Cela peut être inférieur à la longueur source d'origine s'il y a eu un problème de conversion de certains caractères source. Peut être NULL.
int *dstWrotePtr (out)
Rempli avec le nombre d'octets qui ont été effectivement stockés dans le tampon de sortie suite à la conversion. Peut être NULL.
int *dstCharsPtr (out)
Rempli avec le nombre de caractères correspondant au nombre d'octets stockés dans le tampon de sortie. Peut être NULL.
Tcl_DString *bufPtr (out)
Espace mémoire pour le nom d'encodage système prescrit.
const Tcl_EncodingType *typePtr (in)
Structure définissant un nouveau type d'encodage.

Liste des répertoires du système de fichiers dans lesquels rechercher les fichiers de données d'encodage.
const char *path (in)
Un chemin vers l'emplacement du fichier d'encodage.

INTRODUCTION

Ces routines convertissent entre la représentation interne des caractères de Tcl, UTF-8, et les représentations de caractères utilisées par divers systèmes d'exploitation ou systèmes de fichiers, tels que Unicode, ASCII, ou Shift-JIS. Lors de l'opération sur des chaînes, comme l'obtention des noms de fichiers ou l'affichage de caractères à l'aide de polices internationales, les chaînes doivent être traduites dans un ou potentiellement plusieurs formats que les différents appels système peuvent utiliser. Par exemple, sur un poste de travail Unix japonais, un utilisateur pourrait obtenir un nom de fichier représenté dans l'encodage de fichier EUC-JP, puis traduire les caractères dans l'encodage de police jisx0208 afin d'afficher le nom de fichier dans un widget Tk. Le but du paquet d'encodage est d'aider à combler le fossé de traduction. UTF-8 fournit une zone de transit intermédiaire pour tous les différents encodages. Dans l'exemple ci-dessus, le texte serait traduit en UTF-8 à partir de l'encodage de fichier utilisé par le système d'exploitation. Ensuite, il serait traduit de UTF-8 vers l'encodage de police requis par les routines d'affichage.

Certains encodages de base sont compilés dans Tcl. D'autres peuvent être définis par l'utilisateur ou chargés dynamiquement à partir de fichiers d'encodage d'une manière indépendante de la plateforme.

DESCRIPTION

Tcl_GetEncoding recherche un encodage en utilisant son name. Le nom peut faire référence à un encodage Tcl intégré, un encodage défini par l'utilisateur enregistré en appelant Tcl_CreateEncoding, ou un fichier d'encodage chargeable dynamiquement. La valeur de retour est un jeton qui représente l'encodage et peut être utilisé dans des appels ultérieurs à des procédures telles que Tcl_GetEncodingName, Tcl_FreeEncoding et Tcl_UtfToExternal. Si le nom ne fait référence à aucun encodage connu ou chargeable, NULL est retourné et un message d'erreur est retourné dans interp.

Le paquet d'encodage maintient une base de données de tous les encodages actuellement en cours d'utilisation. La première fois que name est vu, Tcl_GetEncoding retourne un encodage avec un compteur de références de 1. Si le même name est demandé plusieurs fois, alors le compteur de références pour cet encodage est incrémenté sans la surcharge de l'allocation d'un nouvel encodage et de toutes ses structures de données associées.

Lorsqu'un encoding n'est plus nécessaire, Tcl_FreeEncoding doit être appelé pour le libérer. Lorsqu'un encoding n'est plus utilisé nulle part (c'est-à-dire qu'il a été libéré autant de fois qu'il a été obtenu), Tcl_FreeEncoding libérera tout l'espace mémoire utilisé par l'encodage et le supprimera de la base de données.

Tcl_GetEncodingFromObj traite la représentation sous forme de chaîne de objPtr comme un nom d'encodage, et trouve un encodage portant ce nom, tout comme le fait Tcl_GetEncoding. Lorsqu'un encodage est trouvé, il est mis en cache dans la valeur objPtr pour référence future, le jeton Tcl_Encoding est écrit dans l'espace mémoire

Mantener toda la estructura del archivo. El valor TCL_OK se devuelve cuando se refiere al encodingPtr especificado. Si no existe ningún tipo de codificación, se devuelve TCL_ERROR y no se realiza ninguna escritura en *encodingPtr. Esto es similar al caso de Tcl_GetEncoding, y el usuario debe llamar a Tcl_FreeEncoding sobre el token de codificación resultante cuando ya no lo utilizará.

Tcl_ExternalToUtfDString convierte un búfer fuente src de la codificación especificada a UTF-8. Los bytes convertidos se almacenan en dstPtr, que luego se termina con el carácter nulo adecuado de la codificación. El usuario debe llamar finalmente a Tcl_DStringFree para liberar cualquier información almacenada en dstPtr. Cuando se realiza la conversión, si algún carácter en el búfer fuente no puede representarse en la codificación de destino, se utiliza un carácter de reemplazo por defecto. El valor devuelto es un puntero al valor almacenado en el DString.

Tcl_ExternalToUtf convierte un búfer fuente src de la codificación especificada a UTF-8. Se convierten hasta srcLen bytes del búfer fuente y hasta dstLen bytes se almacenan en dst. En cualquier caso, *srcReadPtr se llena con el número de bytes convertidos de src y *dstWrotePtr con el número de bytes almacenados en dst. El valor devuelto es uno de los siguientes:

TCL_OK
Todo el contenido de src fue convertido.
TCL_CONVERT_NOSPACE
El búfer de destino no fue suficiente para almacenar todos los datos convertidos; se convirtieron los caracteres que podían caber aunque no todos.
TCL_CONVERT_MULTIBYTE
Los últimos bytes del búfer fuente eran el inicio de una secuencia multibyte, pero se necesitaban más bytes para completarla. Una llamada posterior al convertidor debe pasar un búfer con los bytes no convertidos que quedan en src más algunos bytes de la fuente para completar la secuencia anteriormente dividida.
TCL_CONVERT_SYNTAX
El búfer fuente contenía una secuencia de caracteres inválida. Esto puede ocurrir si el flujo de entrada ha sido dañado o si el método de codificación fue mal identificado.
TCL_CONVERT_UNKNOWN
El búfer fuente contenía un carácter que no podía representarse en la codificación de destino y TCL_ENCODING_STOPONERROR fue especificado.

Tcl_UtfToExternalDString convierte un búfer fuente src de UTF-8 a la codificación especificada. Los bytes convertidos se almacenan en dstPtr, que luego se termina con el carácter nulo adecuado de la codificación. El usuario debe llamar finalmente a Tcl_DStringFree para liberar cualquier información almacenada en dstPtr. Cuando se realiza la conversión, si algún carácter en el búfer fuente no puede representarse en la codificación de destino, se utiliza un carácter de reemplazo por defecto. El valor devuelto es un puntero al valor almacenado en el DString.

Tcl_UtfToExternal convierte un búfer fuente src de UTF-8 a la codificación especificada. Se convierten hasta srcLen bytes del búfer fuente y hasta dstLen bytes se almacenan en dst. En cualquier caso, *srcReadPtr se llena con el número de bytes convertidos de src y *dstWrotePtr con el número de bytes almacenados en dst. Los valores devueltos son los mismos que los de Tcl_ExternalToUtf.

Tcl_WinUtfToTChar y Tcl_WinTCharToUtf son funciones de soporte para convertir entre UTF-8 y cadenas de Windows basadas en el tipo TCHAR, el cual es en general un carácter Unicode en Windows NT.

Tcl_GetEncodingName es aproximadamente la inversa de Tcl_GetEncoding. Dado un encoding, el valor devuelto es el argumento name utilizado para crear la codificación. La cadena devuelta por Tcl_GetEncodingName solo se garantiza que persista hasta que el encoding sea eliminado. El usuario no debe modificar esta cadena.

Tcl_SetSystemEncoding establece la codificación por defecto que se utilizará cuando el usuario pasa un valor nulo para el argumento encoding a cualquier función de codificación. Si name es nulo, la codificación del sistema se restablece a la codificación por defecto del sistema, binary. Si el nombre no se refiere a ninguna codificación conocida o cargable, se devuelve TCL_ERROR y un mensaje de error se deja en interp. De lo contrario, este procedimiento incrementa el contador de referencias de la nueva codificación del sistema, decrementa el contador de referencias de la antigua codificación del sistema y devuelve TCL_OK.

Tcl_GetEncodingNameFromEnvironment proporciona un medio para que la biblioteca Tcl informe el nombre de la codificación que cree ser el correcto para ser usado como codificación del sistema, basándose en llamadas de sistema y examinación del entorno adecuado para la plataforma. Recibe bufPtr, un puntero a un Tcl_DString no inicializado o liberado, y escribe el nombre de la codificación en él. El valor devuelto es el Tcl_DStringValue.

Tcl_GetEncodingNames establece el resultado interp a una lista que contiene los nombres de todas las codificaciones definidas o dinámicamente cargables, buscando en la ruta de codificaciones especificada por Tcl_SetDefaultEncodingDir. Este procedimiento no garantiza que los archivos dinámicamente cargables contengan datos válidos, pero solo asegura que existan.

Tcl_CreateEncoding define una nueva codificación y registra los procedimientos C que se llaman para convertir entre la codificación y UTF-8. Las codificaciones creadas con Tcl_CreateEncoding son visibles en la base de datos utilizada por Tcl_GetEncoding. Al igual que con Tcl_GetEncoding, el valor devuelto es un token que representa la codificación y puede usarse en llamadas posteriores a otras funciones de codificación. Tcl_CreateEncoding devuelve una codificación con un contador de referencias de 1. Si ya existe una entrada en la base de datos con el nombre especificado, su entrada se reemplaza con la nueva codificación; el token del sistema antiguo seguirá siendo válido y continuará comportándose como antes, pero los usuarios del nuevo token llamarán ahora a los procedimientos de la nueva codificación.

El argumento typePtr de Tcl_CreateEncoding contiene información sobre el nombre de la codificación y los procedimientos que se llaman para convertir entre esta codificación y UTF-8. Está definido como:

typedef struct Tcl_EncodingType {
    const char *encodingName;
    Tcl_EncodingConvertProc *toUtfProc;
    Tcl_EncodingConvertProc *fromUtfProc;
    Tcl_EncodingFreeProc *freeProc;
    ClientData clientData;
    int nullSize;
} Tcl_EncodingType;

El encodingName proporciona un nombre para la codificación, por el cual se puede referir en otros procedimientos como Tcl_GetEncoding. El toUtfProc se refiere a un procedimiento de callback para convertir texto de esta codificación a UTF-8. El fromUtfProc se refiere a un procedimiento de callback para convertir texto de UTF-8 a esta codificación. El freeProc se refiere a un procedimiento de callback para invocar cuando se elimina la codificación. El campo freeProc puede ser nulo. El clientData contiene un valor arbitrario de una palabra utilizada por toUtfProc, fromUtfProc y freeProc cuando se llaman. Generalmente, es un puntero a una estructura que contiene información específica de la codificación que puede ser utilizada por los procedimientos de callback. Por ejemplo, dos codificaciones muy similares como ascii y macRoman pueden usar el mismo procedimiento de callback, pero usan valores diferentes de clientData para controlar su comportamiento. El nullSize especifica el número de ceros que significan el fin de cadena en esta codificación. Debe ser 1 (para codificaciones de un solo byte o multibyte como ASCII o Shift-JIS) o 2 (para codificaciones de dos bytes como Unicode). Las codificaciones con 3 o más bytes por carácter (como CNS11643) no son aceptadas.

Los procedimientos de callback toUtfProc y fromUtfProc deben coincidir con el tipo Tcl_EncodingConvertProc:

typedef int Tcl_EncodingConvertProc(
        ClientData clientData,
        const char *src,
        int srcLen,
        int flags,
        Tcl_EncodingState *statePtr,
        char *dst,
        int dstLen,
        int *srcReadPtr,
        int *dstWrotePtr,
        int *dstCharsPtr);

Los procedimientos de callback toUtfProc y fromUtfProc son llamados por Tcl_ExternalToUtf o Tcl_UtfToExternal para realizar la conversión real. El parámetro clientData de estos procedimientos es el mismo que el clientData especificado en Tcl_CreateEncoding cuando se creó la codificación. Los argumentos restantes de los procedimientos de callback son los mismos que los argumentos, documentados arriba, de Tcl_ExternalToUtf o Tcl_UtfToExternal, con las siguientes excepciones. Si el argumento srcLen de una de estas funciones de nivel alto es negativo, el valor pasado al procedimiento de callback será la longitud adecuada de la codificación de src. Si alguno de los argumentos srcReadPtr, dstWrotePtr o dstCharsPtr de una de estas funciones de nivel alto es nulo, el valor pasado al procedimiento de callback será una ubicación no nula.

El procedimiento de callback freeProc, si no es nulo, debe coincidir con el tipo Tcl_EncodingFreeProc:

typedef void Tcl_EncodingFreeProc(
        ClientData clientData);

Este freeProc se llama cuando se elimina la codificación. El parámetro clientData es el mismo que el clientData especificado en Tcl_CreateEncoding cuando se creó la codificación.

Tcl_GetEncodingSearchPath y Tcl_SetEncodingSearchPath se llaman para acceder y establecer la lista de carpetas de directorios de archivos de datos de codificación. El valor devuelto por Tcl_GetEncodingSearchPath es el valor almacenado por la última llamada exitosa a Tcl_SetEncodingSearchPath. Si no se han realizado llamadas a Tcl_SetEncodingSearchPath, Tcl calculará un valor inicial basado en el entorno. Hay una ruta de búsqueda de codificación única para el proceso completo, compartida por todos los hilos del proceso.

Tcl_SetEncodingSearchPath almacena searchPath y devuelve TCL_OK, excepto si searchPath no es una lista válida de Tcl, en cuyo caso se devuelve TCL_ERROR. Los elementos de searchPath se procesan como se explica en el texto anterior, con la siguiente excepción: si el argumento searchPath es un valor nulo, se devuelve TCL_ERROR. El valor devuelto es el mismo que el de Tcl_GetEncodingSearchPath.

INTRODUCTION

Les fonctions Tcl_GetDefaultEncodingDir et Tcl_GetEncodingSearchPath sont des interfaces obsolètes qui devraient être remplacées par des appels à Tcl_GetDefaultEncodingDir et Tcl_GetEncodingSearchPath. Elles sont appelées pour accéder et définir le premier élément de la liste searchPath. Comme Tcl recherche les fichiers de données d'encodage dans searchPath dans l'ordre de la liste, ces routines établissent le répertoire "par défaut" dans lequel trouver les fichiers de données d'encodage.

DESCRIPTION

L'espace interdirait de précompiler dans Tcl tous les algorithmes d'encodage possibles, de sorte que de nombreux encodages sont stockés sur disque sous forme de fichiers d'encodage chargeables dynamiquement. Ce comportement permet également à l'utilisateur de créer des fichiers d'encodage supplémentaires qui peuvent être chargés en utilisant le même mécanisme. Ces fichiers d'encodage contiennent des informations sur les tables et/ou les séquences d'échappement utilisées pour mapper entre un encodage externe et Unicode. L'encodage externe peut être constitué de caractères sur un, plusieurs ou deux octets.

Chaque encodage chargeable dynamiquement est représenté par un fichier texte. La ligne initiale du fichier, commençant par un symbole #, est un commentaire qui fournit une description lisible par l'homme du fichier. La ligne suivante identifie le type de fichier d'encodage. Il peut s'agir de l'une des lettres suivantes :

[1] S
Un encodage sur un octet, où un caractère est toujours d'un octet dans l'encodage. Un exemple est iso8859-1, utilisé par de nombreuses langues européennes.
[2] D
Un encodage sur deux octets, où un caractère est toujours de deux octets dans l'encodage. Un exemple est big5, utilisé pour le texte chinois.
[3] M
Un encodage multi-octets, où un caractère peut être d'un ou deux octets. Certains octets sont des octets de tête, indiquant qu'un autre octet doit suivre et que les deux octets représentent un caractère. D'autres octets ne sont pas des octets de tête et se représentent eux-mêmes. Un exemple est shiftjis, utilisé par de nombreux ordinateurs japonais.
[4] E
Un encodage par séquence d'échappement, spécifiant que certaines séquences d'octets ne représentent pas des caractères, mais des commandes décrivant comment les octets suivants doivent être interprétés.

Le reste des lignes du fichier dépend du type.

Les cas [1], [2] et [3] sont collectivement appelés fichiers d'encodage basés sur des tables. Les lignes d'un fichier d'encodage basé sur des tables sont dans le même format que cet exemple tiré de l'encodage shiftjis (ce n'est pas le fichier complet) :

La troisième ligne du fichier est composée de trois nombres. Le premier nombre est le caractère de repli (en base 16) à utiliser lors de la conversion de UTF-8 vers cet encodage. Le deuxième nombre est 1 si ce fichier représente l'encodage d'une police de symboles, ou 0 sinon. Le dernier nombre (en base 10) indique combien de pages de données suivent.

Les lignes suivantes dans l'exemple ci-dessus sont des pages qui décrivent comment mapper de l'encodage vers Unicode sur 2 octets. La première ligne d'une page identifie le numéro de la page. Elle est suivie de 256 nombres sur 2 octets, arrangés en 16 lignes de 16 nombres. Étant donné un caractère dans l'encodage, l'octet de poids fort de ce caractère est utilisé pour sélectionner la page, et l'octet de poids faible de ce caractère est utilisé comme indice pour sélectionner l'un des nombres sur 2 octets de cette page - la valeur obtenue étant le caractère Unicode correspondant. Par examen de l'exemple ci-dessus, on peut voir que les caractères 0x7E et 0x8163 en shiftjis correspondent respectivement à 203E et 2026 en Unicode.

Après la première page suivront toutes les autres pages, chacune dans le même format que la première : un nombre identifiant la page suivi de 256 caractères Unicode sur 2 octets. Si un caractère de l'encodage correspond au caractère Unicode 0000, cela signifie que le caractère n'existe pas réellement. Si tous les caractères d'une page correspondent à 0000, cette page peut être omise.

Le cas [4] est le fichier d'encodage par séquence d'échappement. Les lignes de ce type de fichier sont dans le même format que cet exemple tiré de l'encodage iso2022-jp :

# Fichier d'encodage : iso2022-jp, piloté par séquence d'échappement
E
init		{}
final		{}
iso8859-1	\x1b(B
jis0201		\x1b(J
jis0208		\x1b$@
jis0208		\x1b$B
jis0212		\x1b$(D
gb2312		\x1b$A
ksc5601		\x1b$(C

Dans le fichier, la première colonne représente une option et la deuxième colonne est la valeur associée. init est une chaîne à émettre ou à attendre avant la conversion du premier caractère, tandis que final est une chaîne à émettre ou à attendre après le dernier caractère. Toutes les autres options sont des noms d'encodages basés sur des tables ; la valeur associée est la séquence d'échappement qui marque cet encodage. La syntaxe Tcl est utilisée pour les valeurs ; dans l'exemple ci-dessus, { } représente la chaîne vide et \x1b représente le caractère 27.

Lorsque Tcl_GetEncoding rencontre un nom d'encodage qui n'a pas été chargé, il tente de charger un fichier d'encodage nommé name.enc depuis le sous-répertoire d'encodage de chaque répertoire que Tcl utilise pour sa bibliothèque de scripts. Si le fichier d'encodage existe, mais est malformé, un message d'erreur sera laissé dans interp.

MOTS CLES

utf, encoding, convert

SYNTAXE

Tcl_GetDefaultEncodingDir, Tcl_GetEncodingSearchPath

ARGUMENTS

name, searchPath

INTRODUCTION

Les fonctions Tcl_GetDefaultEncodingDir et Tcl_GetEncodingSearchPath sont des interfaces obsolètes qui devraient être remplacées par des appels à Tcl_GetDefaultEncodingDir et Tcl_GetEncodingSearchPath. Elles sont appelées pour accéder et définir le premier élément de la liste searchPath. Comme Tcl recherche les fichiers de données d'encodage dans searchPath dans l'ordre de la liste, ces routines établissent le répertoire "par défaut" dans lequel trouver les fichiers de données d'encodage.

DESCRIPTION

L'espace interdirait de précompiler dans Tcl tous les algorithmes d'encodage possibles, de sorte que de nombreux encodages sont stockés sur disque sous forme de fichiers d'encodage chargeables dynamiquement. Ce comportement permet également à l'utilisateur de créer des fichiers d'encodage supplémentaires qui peuvent être chargés en utilisant le même mécanisme. Ces fichiers d'encodage contiennent des informations sur les tables et/ou les séquences d'échappement utilisées pour mapper entre un encodage externe et Unicode. L'encodage externe peut être constitué de caractères sur un, plusieurs ou deux octets.

Chaque encodage chargeable dynamiquement est représenté par un fichier texte. La ligne initiale du fichier, commençant par un symbole #, est un commentaire qui fournit une description lisible par l'homme du fichier. La ligne suivante identifie le type de fichier d'encodage. Il peut s'agir de l'une des lettres suivantes :

[1] S
Un encodage sur un octet, où un caractère est toujours d'un octet dans l'encodage. Un exemple est iso8859-1, utilisé par de nombreuses langues européennes.
[2] D
Un encodage sur deux octets, où un caractère est toujours de deux octets dans l'encodage. Un exemple est big5, utilisé pour le texte chinois.
[3] M
Un encodage multi-octets, où un caractère peut être d'un ou deux octets. Certains octets sont des octets de tête, indiquant qu'un autre octet doit suivre et que les deux octets représentent un caractère. D'autres octets ne sont pas des octets de tête et se représentent eux-mêmes. Un exemple est shiftjis, utilisé par de nombreux ordinateurs japonais.
[4] E
Un encodage par séquence d'échappement, spécifiant que certaines séquences d'octets ne représentent pas des caractères, mais des commandes décrivant comment les octets suivants doivent être interprétés.

Le reste des lignes du fichier dépend du type.

Les cas [1], [2] et [3] sont collectivement appelés fichiers d'encodage basés sur des tables. Les lignes d'un fichier d'encodage basé sur des tables sont dans le même format que cet exemple tiré de l'encodage shiftjis (ce n'est pas le fichier complet) :

# Fichier d'encodage : shiftjis, multi-octets
M
003F 0 40
00
0000000100020
