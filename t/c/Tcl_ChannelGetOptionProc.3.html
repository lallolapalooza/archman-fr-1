ARGUMENTS

const Tcl_ChannelType *typePtr (in)
Pointeur vers une structure contenant les points de procédure qui peuvent être utilisés pour effectuer des opérations d'entrée et de sortie sur le canal.
const char *channelName (in)
Le nom de ce canal, tel que file3; il ne doit pas être utilisé par aucun autre canal. Peut être NULL, auquel cas le canal est créé sans nom. Si le canal créé est assigné à l'un des canaux standards (stdin, stdout ou stderr), le nom assigné au canal sera le nom du canal standard.
ClientData instanceData (in)
Valeur arbitraire d'un seul octet associée à ce canal. Cette valeur est passée aux procédures de typePtr lorsqu'elles sont appelées.
int mask (in)
Une combinaison OR de TCL_READABLE et TCL_WRITABLE indiquant si le canal est en lecture et en écriture.
Tcl_Channel channel (in)
Le canal sur lequel opérer.
int direction (in)
TCL_READABLE signifie que le handle d'entrée est souhaité ; TCL_WRITABLE signifie que le handle de sortie est souhaité.
ClientData *handlePtr (out)
Le pointeur vers l'emplacement où le handle souhaité du système d'exploitation doit être stocké.
int size (in)
La taille, en octets, des tampons à allouer sur ce canal.
int mask (in)
Une combinaison OR de TCL_READABLE, TCL_WRITABLE et TCL_EXCEPTION indiquant les événements qui se sont produits sur ce canal.
Tcl_Interp *interp (in)
Interpréteur actuel. (peut être NULL)
const char *optionName (in)
Nom de l'option invalide.
const char *optionList (in)
Liste d'options (mots séparés par des espaces, sans le préfixe -) qui sont ajoutés à la liste des options standard. Peut être NULL pour des messages d'erreur standards uniquement.

DESCRIPTION

Tcl utilise une architecture de canaux à deux niveaux. Elle fournit un niveau supérieur générique pour permettre aux programmes C et Tcl d'effectuer des entrées et des sorties en utilisant les mêmes API pour divers fichiers, périphériques, sockets, etc. Les API C génériques sont décrites dans la page de manuel de Tcl_OpenFileChannel.

Le niveau inférieur fournit des pilotes de canal spécifiques à chaque type de périphérique pris en charge sur chaque plateforme. Cette page de manuel décrit les API C qui communiquent entre le niveau générique et les pilotes de canal spécifiques. Elle explique également comment de nouveaux types de canaux peuvent être ajoutés en implémentant de nouveaux pilotes de canal.

Les pilotes de canal se composent de plusieurs composants : Premièrement, chaque pilote de canal fournit une structure Tcl_ChannelType qui contient des pointeurs vers les procédures qui implémentent les diverses opérations utilisées par le niveau générique pour communiquer avec le pilote de canal. La structure Tcl_ChannelType et les procédures auxquelles elle fait référence sont décrites dans la section TCL_CHANNELTYPE, ci-dessous.

Deuxièmement, les pilotes de canal fournissent généralement une commande Tcl pour créer des instances de ce type de canal. Par exemple, la commande Tcl open crée des canaux qui utilisent les pilotes de fichier et de commande, et la commande Tcl socket crée des canaux qui utilisent les protocoles réseau TCP.

Troisièmement, un pilote de canal fournit éventuellement une fonction C pour ouvrir des instances de ce type de canal. Par exemple, Tcl_OpenFileChannel ouvre un canal utilisant le pilote de fichier, et Tcl_OpenTcpClient ouvre un canal utilisant le protocole réseau TCP. Ces fonctions de création utilisent généralement Tcl_CreateChannel en interne pour ouvrir le canal.

Pour ajouter un nouveau type de canal, vous devez implémenter une API C ou une commande Tcl qui ouvre un canal en appelant Tcl_CreateChannel. Lorsque votre pilote appelle Tcl_CreateChannel, il passe une structure Tcl_ChannelType qui décrit les procédures d'entrée et de sortie de votre pilote. Le niveau générique appelle ensuite les procédures référencées dans cette structure pour effectuer des opérations sur le canal.

Tcl_CreateChannel ouvre un nouveau canal et lui associe typePtr et instanceData. Le canal est ouvert dans le mode indiqué par mask. Pour une discussion sur les pilotes de canal, leurs opérations et la structure Tcl_ChannelType, voir la section TCL_CHANNELTYPE, ci-dessous.

Tcl_CreateChannel interagit avec le code qui gère les canaux standards. Une fois qu'un canal standard a été initialisé par un appel à Tcl_GetStdChannel ou un appel à Tcl_SetStdChannel, la fermeture de ce canal entraînera la prochaine invocation de Tcl_CreateChannel pour faire de ce canal le nouveau canal standard également. Voir Tcl_StandardChannels pour un traitement général des canaux standards et du comportement de la bibliothèque Tcl à leur égard.

Tcl_GetChannelInstanceData renvoie les données d'instanciation associées au canal dans channel. Il s'agit de la même valeur que l'argument instanceData dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelType renvoie un pointeur vers la structure Tcl_ChannelType utilisée par le canal dans l'argument channel. Il s'agit de la même valeur que l'argument typePtr dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelName renvoie une chaîne contenant le nom associé au canal, ou NULL si l'argument channelName de Tcl_CreateChannel était NULL.

Tcl_GetChannelHandle place le handle du système d'exploitation associé à channel pour la direction donnée dans handlePtr.

TCL_CHANNELTYPE

Un pilote de canal fournit une structure Tcl_ChannelType qui contient des pointeurs vers des fonctions implémentant les différentes opérations sur un canal ; ces opérations sont appelées au besoin par la couche générique. La structure a été versionnée à partir de Tcl 8.3.2/8.4 pour corriger un problème avec les pilotes de canaux bloquants. Voir la section OLD CHANNEL TYPES pour plus de détails sur l'ancienne structure.

La structure Tcl_ChannelType contient les champs suivants :

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Il n'est pas nécessaire de fournir des implémentations pour toutes les opérations de canal. Celles qui ne sont pas nécessaires peuvent être définies à NULL dans la structure : blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc, et close2Proc, en plus de flushProc, handlerProc, threadActionProc, et truncateProc. Les autres fonctions qui ne peuvent pas être implémentées de manière significative doivent retourner EINVAL lorsqu'elles sont appelées, indiquant que les opérations représentées ne sont pas disponibles. Il convient également de noter que wideSeekProc peut être NULL si seekProc ne l'est pas.

L'utilisateur ne doit utiliser que cette structure pour l'instanciation de Tcl_ChannelType. Lors de la référence aux champs d'une structure Tcl_ChannelType, les fonctions suivantes doivent être utilisées pour obtenir les valeurs : Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc, ou Tcl_ChannelHandlerProc.

La modification de la structure a été faite de telle sorte que les types de canaux standard soient compatibles au niveau binaire. Cependant, les types de canaux utilisant des canaux bloquants (c'est-à-dire TLS, Trf) ont de nouvelles versions qui correspondent à ce changement, car l'ancien code des canaux bloquants présentait des problèmes.

TYPENAME

Le champ typeName contient une chaîne terminée par null qui identifie le type de périphérique implémenté par ce pilote, par exemple, file ou socket.

Cette valeur peut être obtenue avec Tcl_ChannelName, qui renvoie un pointeur vers la chaîne.

VERSION

Le champ version doit être défini sur la version de la structure requise. TCL_CHANNEL_VERSION_2 est le minimum recommandé. TCL_CHANNEL_VERSION_3 doit être défini pour spécifier le membre wideSeekProc. TCL_CHANNEL_VERSION_4 doit être défini pour spécifier le membre threadActionProc (inclut wideSeekProc). TCL_CHANNEL_VERSION_5 doit être défini pour spécifier les membres truncateProc (inclut wideSeekProc et threadActionProc). Si aucun de ceux-ci n'est défini, on suppose que Tcl_ChannelType a la structure d'origine. Voir OLD CHANNEL TYPES pour plus de détails. Bien que Tcl reconnaisse et fonctionne avec chacune de ces structures, les canaux bloquants doivent avoir au moins TCL_CHANNEL_VERSION_2 pour fonctionner correctement.

Cette valeur peut être obtenue avec Tcl_ChannelVersion, qui renvoie l'une des valeurs TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 ou TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

Le champ blockModeProc contient l'adresse d'une fonction appelée par la couche générique pour définir le mode bloquant et non bloquant sur le périphérique. BlockModeProc doit correspondre au prototype suivant :

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

instanceData est le même que la valeur passée à Tcl_CreateChannel lors de la création de ce canal. L'argument mode est soit TCL_MODE_BLOCKING, soit TCL_MODE_NONBLOCKING pour définir le périphérique en mode bloquant ou non bloquant. La fonction doit retourner zéro si l'opération a réussi, ou un code d'erreur POSIX non nul si l'opération a échoué.

Si l'opération réussit, la fonction peut modifier le instanceData fourni pour enregistrer que le canal est passé en mode bloquant ou non bloquant et pour implémenter le comportement bloquant ou non bloquant. Pour certains types de périphériques, le comportement bloquant et non bloquant peut être implémenté par le système d'exploitation sous le périphérique ; pour d'autres types de périphériques, le comportement doit être émulé dans le pilote de canal.

Cette valeur peut être obtenue avec Tcl_ChannelBlockModeProc, qui renvoie un pointeur vers la fonction.

Un pilote de canal qui ne fournit pas de blockModeProc doit être très prudent. Il doit indiquer exactement quel mode bloquant lui convient, et doit le documenter pour l'utilisateur afin que le mode bloquant du canal ne soit pas changé à une valeur inacceptable. Toute confusion à cet égard peut entraîner un blocage (faux et difficile à trouver) de l'interprète.

CLOSEPROC ET CLOSE2PROC

Le champ closeProc contient l'adresse d'une fonction appelée par la couche générique pour nettoyer les informations relatives au pilote lorsque le canal est fermé. CloseProc doit correspondre au prototype suivant :

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

instanceData est le même que la valeur fournie à Tcl_CreateChannel lors de la création du canal. La fonction doit libérer toute mémoire conservée par le pilote de canal pour ce canal, et fermer les périphériques d'entrée et de sortie encapsulés par ce canal. Avant que cette fonction ne soit appelée, toutes les données de sortie accumulées ont été vidées vers le périphérique. Après l'appel de closeProc, aucune autre opération du pilote ne sera appelée sur cette instance. Si l'opération de fermeture réussit, la fonction continue.

Mantén toda la estructura del archivo.

La valeur de closeProc et close2Proc peut être récupérée avec Tcl_ChannelCloseProc ou Tcl_ChannelClose2Proc, qui renvoient un pointeur vers la fonction respective.

Le close2Proc est appelé avec flags définis à un OU de TCL_CLOSE_READ ou TCL_CLOSE_WRITE pour indiquer que le pilote doit fermer le côté lecture et/ou écriture du canal. Le pilote de canal peut être appelé pour effectuer des opérations supplémentaires sur le canal après que close2Proc ait fermé une ou les deux parties du canal. Si flags est 0 (zéro), le pilote doit fermer le canal comme décrit pour closeProc. Aucune autre opération ne sera appelée sur cette instance après l'exécution de close2Proc avec tous les flags effacés. Dans tous les cas, le close2Proc doit retourner zéro si l'opération de fermeture a réussi ; sinon, il doit retourner un code d'erreur POSIX non nul. De plus, si une erreur se produit et que interp n'est pas NULL, la procédure doit stocker un message d'erreur dans le résultat de l'interpréteur.

La valeur de closeProc et close2Proc peut être récupérée avec Tcl_ChannelCloseProc ou Tcl_ChannelClose2Proc, qui renvoient un pointeur vers la fonction respective.

INPUTPROC

La valeur de inputProc contient l'adresse d'une fonction appelée par la couche générique pour lire des données depuis le périphérique ou le fichier et les stocker dans un tampon interne. InputProc doit correspondre au prototype suivant :

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

InstanceData est la même que la valeur passée à Tcl_CreateChannel lors de la création du canal. L'argument buf pointe vers un tableau d'octets dans lequel les données d'entrée du périphérique seront stockées, et l'argument bufSize indique combien d'octets sont disponibles dans buf.

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générique. Si une erreur se produit, la fonction doit définir cette valeur à un code d'erreur POSIX identifiant l'erreur.

La fonction doit lire les données du périphérique encapsulé par le canal et les stocker dans buf. En cas de succès, la fonction doit retourner un nombre non négatif indiquant combien d'octets ont été lus depuis le périphérique et stockés dans buf. En cas d'erreur, la fonction doit retourner -1. Si une erreur se produit après la lecture de certaines données depuis le périphérique, ces données sont perdues.

Si inputProc peut déterminer que le périphérique d'entrée dispose de données disponibles mais moins que ce qui est demandé par l'argument bufSize, la fonction doit tenter de lire uniquement la quantité de données disponible et retourner sans bloquer. Si le périphérique d'entrée n'a pas de données disponibles et que le canal est en mode non bloquant, la fonction doit retourner une erreur EAGAIN. Si le périphérique d'entrée n'a pas de données disponibles et que le canal est en mode bloquant, la fonction doit bloquer pendant la période la plus courte possible jusqu'à ce qu'au moins un octet puisse être lu depuis le périphérique ; elle retournera ensuite toutes les données qu'elle peut lire sans bloquer.

Cette valeur peut être récupérée avec Tcl_ChannelInputProc, qui retourne un pointeur vers la fonction.

OUTPUTPROC

La valeur de outputProc contient l'adresse d'une fonction appelée par la couche générique pour transférer des données du tampon interne vers le périphérique de sortie. OutputProc doit correspondre au prototype suivant :

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData est la même que la valeur passée à Tcl_CreateChannel lors de la création du canal. L'argument buf contient un tableau d'octets qui sera écrit sur le périphérique, et l'argument toWrite indique combien d'octets seront écrits depuis l'argument buf.

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générique. Si une erreur se produit, la fonction doit définir cette valeur à un code d'erreur POSIX identifiant l'erreur.

La fonction doit écrire les données dans buf sur le périphérique de sortie encapsulé par le canal. En cas de succès, la fonction doit retourner un nombre non négatif indiquant combien d'octets ont été écrits sur le périphérique de sortie. La valeur de retour est normalement la même que toWrite, mais peut être inférieure dans certains cas, comme lorsque l'opération de sortie est interrompue par un signal. En cas d'erreur, la fonction doit retourner -1. En cas d'erreur, certaines données peuvent avoir été écrites sur le périphérique.

Si le canal est en mode non bloquant et que le périphérique de sortie ne peut absorber aucune donnée, la fonction doit retourner -1 avec une erreur EAGAIN sans écrire aucune donnée.

Cette valeur peut être récupérée avec Tcl_ChannelOutputProc, qui retourne un pointeur vers la fonction.

SEEKPROC ET WIDESEEKPROC

La valeur de seekProc contient l'adresse d'une fonction appelée par la couche générique pour déplacer le point d'accès auquel les opérations de lecture ou d'écriture suivantes s'appliqueront. SeekProc doit correspondre au prototype suivant :

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

L'argument instanceData est le même que la valeur passée à Tcl_CreateChannel lors de la création de ce canal. Offset et seekMode ont la même signification que dans la fonction Tcl_Seek (mentionnée dans le manuel de Tcl_OpenFileChannel).

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générique pour renvoyer les valeurs errno de la fonction. La fonction doit définir cette valeur à un code d'erreur POSIX si une erreur se produit. La fonction doit stocker un code EINVAL dans cet argument si le type de canal n'implémente pas la recherche.

La valeur de retour est le nouveau point d'accès ou -1 en cas d'erreur. Si une erreur se produit, la fonction ne doit pas déplacer le point d'accès.

Si un seekProc non NULL existe, le wideSeekProc peut contenir l'adresse d'une fonction alternative qui gère les décalages larges (c'est-à-dire, supérieurs à 32 bits), permettant de rechercher dans des fichiers supérieurs à 2 Go. Le wideSeekProc est appelé avant le seekProc, mais les deux doivent être définis si wideSeekProc est défini. WideSeekProc doit correspondre au prototype suivant :

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

Les arguments et les valeurs de retour sont les mêmes que pour seekProc, sauf que le type du décalage et le type de retour sont différents.

La valeur de seekProc peut être récupérée avec Tcl_ChannelSeekProc, qui retourne un pointeur vers la fonction, et de manière similaire, la valeur de wideSeekProc peut être récupérée avec Tcl_ChannelWideSeekProc.

SETOPTIONPROC

La valeur de setOptionProc contient l'adresse d'une fonction appelée par la couche générique pour définir une option spécifique au type de canal sur un canal. setOptionProc doit correspondre au prototype suivant :

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

optionName est le nom d'une option à définir, et newValue est la nouvelle valeur pour cette option, sous forme de chaîne. instanceData est la même que la valeur passée à Tcl_CreateChannel lors de la création de ce canal. La fonction doit effectuer toute action spécifique au type de canal nécessaire pour implémenter la nouvelle valeur de l'option.

Certaines options sont gérées par le code générique et cette fonction n'est jamais appelée pour les définir, comme -blockmode. D'autres options sont spécifiques à chaque type de canal et la fonction setOptionProc du pilote de canal est appelée pour les implémenter. La valeur de setOptionProc peut être NULL, indiquant que ce type de canal ne prend pas en charge d'options spécifiques au type.

Si la valeur de l'option est modifiée avec succès à la nouvelle valeur, la fonction retourne TCL_OK. Elle devrait appeler Tcl_BadChannelOption, qui retourne elle-même TCL_ERROR si le optionName n'est pas reconnu. Si newValue spécifie une valeur non prise en charge ou si une erreur se produit lors d'un appel système, la fonction doit laisser un message d'erreur dans le résultat de interp si interp n'est pas NULL. La fonction doit également appeler Tcl_SetErrno pour stocker un code d'erreur POSIX approprié.

Cette valeur peut être récupérée avec Tcl_ChannelSetOptionProc, qui retourne un pointeur vers la fonction.

GETOPTIONPROC

La valeur de getOptionProc contient l'adresse d'une fonction appelée par la couche générique pour obtenir la valeur d'une option spécifique au type de canal sur un canal. getOptionProc doit correspondre au prototype suivant :

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        Tcl_DString *optionValue);

OptionName est le nom d'une option prise en charge par ce type de canal. Si le nom de l'option n'est pas NULL, la fonction stocke sa valeur actuelle, sous forme de chaîne, dans la chaîne dynamique Tcl optionValue. Si optionName est NULL, la fonction stocke dans optionValue une liste alternative de toutes les options prises en charge et de leurs valeurs actuelles. En cas de succès, la fonction retourne TCL_OK. Elle devrait appeler Tcl_BadChannelOption, qui retourne elle-même TCL_ERROR si le optionName n'est pas reconnu. Si newValue spécifie une valeur pour l'option qui n'est pas prise en charge ou si une erreur se produit lors d'un appel système, la fonction doit laisser un message d'erreur dans le résultat de interp si interp n'est pas NULL. La fonction doit également appeler Tcl_SetErrno pour stocker un code d'erreur POSIX approprié.

Cette valeur peut être récupérée avec Tcl_ChannelGetOptionProc, qui retourne un pointeur vers la fonction.

WATCHPROC

Le champ watchProc contient l'adresse d'une fonction appelée par la couche générique pour initialiser le mécanisme de notification des événements d'intérêt sur ce canal. WatchProc doit correspondre au prototype suivant :

typedef void Tcl_DriverWatchProc(
        ClientData instanceData,
        int mask);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument mask est une combinaison OR de TCL_READABLE, TCL_WRITABLE et TCL_EXCEPTION ; il indique les événements pour lesquels l'appelant souhaite être notifié sur ce canal.

La fonction doit initialiser des mécanismes spécifiques au type de périphérique pour la notification lorsqu'un événement d'intérêt est présent sur le canal. Lorsqu'un événement d'intérêt se produit sur le canal, le pilote de canal est responsable d'appeler Tcl_NotifyChannel pour informer le module de canal générique. Le pilote doit éviter d'épuiser les autres pilotes de canal ou sources de callbacks en appelant Tcl_NotifyChannel trop fréquemment. L'équité peut être assurée en utilisant la file d'attente d'événements de Tcl pour permettre à l'événement du canal d'être planifié séquentiellement avec d'autres événements. Voir la description de Tcl_QueueEvent pour plus de détails sur la planification d'un événement.

Cette valeur peut être obtenue avec Tcl_ChannelWatchProc, qui renvoie l'adresse de la fonction.

GETHANDLEPROC

Le champ getHandleProc contient l'adresse d'une fonction appelée par la couche générique pour récupérer un handle spécifique au canal. GetHandleProc doit correspondre au prototype suivant :

typedef int Tcl_DriverGetHandleProc(
        ClientData instanceData,
        int direction,
        ClientData *handlePtr);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument direction est TCL_READABLE pour récupérer le handle utilisé pour l'entrée, ou TCL_WRITABLE pour récupérer le handle utilisé pour la sortie.

Si l'implémentation du canal a des handles spécifiques, la fonction doit récupérer le handle approprié en fonction de l'argument direction. Le handle doit être stocké à l'emplacement référencé par handlePtr, et TCL_OK doit être retourné. Si le canal n'est pas ouvert pour la direction spécifiée ou si l'implémentation du canal n'utilise pas de handles spécifiques, la fonction doit retourner TCL_ERROR.

Cette valeur peut être obtenue avec Tcl_ChannelGetHandleProc, qui renvoie l'adresse de la fonction.

FLUSHPROC

Le champ flushProc est actuellement réservé pour une utilisation future. Il doit être défini à NULL. FlushProc doit correspondre au prototype suivant :

typedef int Tcl_DriverFlushProc(
        ClientData instanceData);

Cette valeur peut être obtenue avec Tcl_ChannelFlushProc, qui renvoie l'adresse de la fonction.

HANDLERPROC

Le champ handlerProc contient l'adresse d'une fonction appelée par la couche générique pour notifier le canal qu'un événement s'est produit. Il doit être défini pour les pilotes de canaux empilés qui souhaitent être notifiés des événements sur le canal sous-jacent (canal empilé). HandlerProc doit correspondre au prototype suivant :

typedef int Tcl_DriverHandlerProc(
        ClientData instanceData,
        int interestMask);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. InterestMask est une combinaison OR de TCL_READABLE ou TCL_WRITABLE ; il indique le type d'événement qui s'est produit sur ce canal.

Cette valeur peut être obtenue avec Tcl_ChannelHandlerProc, qui renvoie l'adresse de la fonction.

THREADACTIONPROC

Le champ threadActionProc contient l'adresse de la fonction appelée par la couche générique lorsqu'un canal est créé, fermé ou déplacé vers un autre thread, c'est-à-dire lorsque l'état spécifique au thread du pilote peut devoir être initialisé ou mis à jour. Il peut être NULL. L'action TCL_CHANNEL_THREAD_REMOVE est utilisée pour notifier au pilote qu'il doit mettre à jour ou supprimer toute donnée spécifique au thread qu'il pourrait conserver pour le canal.

L'action TCL_CHANNEL_THREAD_INSERT est utilisée pour notifier au pilote qu'il doit mettre à jour ou initialiser toute donnée spécifique au thread qu'il pourrait conserver en utilisant le thread actuel comme associé. Voir Tcl_CutChannel et Tcl_SpliceChannel pour plus de détails.

typedef void Tcl_DriverThreadActionProc(
        ClientData instanceData,
        int action);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal.

Ces valeurs peuvent être obtenues avec Tcl_ChannelThreadActionProc, qui renvoie l'adresse de la fonction.

TRUNCATEPROC

Le champ truncateProc contient l'adresse de la fonction appelée par la couche générique lorsqu'un canal est tronqué à une longueur spécifiée. Il peut être NULL.

typedef int Tcl_DriverTruncateProc(
        ClientData instanceData,
        Tcl_WideInt length);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal, et length est la nouvelle longueur du fichier sous-jacent, qui ne doit pas être négative. Le résultat doit être 0 en cas de succès ou un code d'erreur (applicable avec Tcl_SetErrno) en cas d'échec.

Ces valeurs peuvent être obtenues avec Tcl_ChannelTruncateProc, qui renvoie l'adresse de la fonction.

TCL_BADCHANNELOPTION

Cette procédure génère un message d'erreur "mauvaise option" sur un interpréteur (optionnel). Elle est utilisée par les pilotes de canaux lorsqu'une option invalide est demandée. Son but est de concaténer la liste des options génériques avec celles spécifiques et de factoriser la chaîne du message d'erreur générique.

Retourne toujours TCL_ERROR.

Un message d'erreur est généré dans la valeur de résultat de interp pour indiquer qu'une commande a été invoquée avec une option incorrecte. Le message est de la forme :

    mauvaise option "blah" : devrait être l'une des
    <...options génériques...>+<...options spécifiques...>
par exemple : 
    mauvaise option "-blah" : devrait être l'une des -blocking,
    -buffering, -buffersize, -eofchar, -translation,
    -peername, ou -sockname
lorsqu'elle est appelée avec optionList égal à "peername sockname".

"blah" est l'argument optionName et "<options spécifiques>" est une liste de mots séparés par des espaces. La fonction se charge d'insérer des tirets avant chaque option, des virgules après et un "ou" avant la dernière option.

TYPES DE CANAUX OBSOLÈTES

La structure d'origine (Tcl_ChannelType pour les versions 8.3.1 et antérieures) contenait les champs suivants :

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
} Tcl_ChannelType;

Bien qu'il soit toujours possible de créer un canal avec la structure ci-dessus, le code interne du canal déterminera la version. Il est essentiel d'utiliser la nouvelle structure Tcl_ChannelType si un pilote de canal empilé est créé en raison de problèmes dans l'implémentation précédente des canaux empilés (de 8.2.0 à 8.3.1).

Avant 8.4.0 (c'est-à-dire pendant les versions ultérieures de 8.3 et le début du cycle de développement de 8.4), la structure Tcl_ChannelType contenait les champs suivants :

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_ChannelTypeVersion version;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Lorsque la structure ci-dessus est enregistrée comme type de canal, le champ version doit toujours être TCL_CHANNEL_VERSION_2.
