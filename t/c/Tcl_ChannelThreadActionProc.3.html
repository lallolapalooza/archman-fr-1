ARGUMENTS

const Tcl_ChannelType *typePtr (in)
Pointe vers une structure contenant les adresses des procédures qui peuvent être appelées pour effectuer des opérations d'E/S et autres sur le canal.
const char *channelName (in)
Le nom de ce canal, par exemple file3 ; ne doit être utilisé par aucun autre canal. Peut être NULL, auquel cas le canal est créé sans nom. Si le canal créé est attribué à l'un des canaux standard ( stdin, stdout ou stderr), le nom du canal attribué sera le nom du canal standard.
ClientData instanceData (in)
Valeur arbitraire d'un mot à associer à ce canal. Cette valeur est transmise aux procédures dans typePtr lorsqu'elles sont invoquées.
int mask (in)
Combinaison OU de TCL_READABLE et TCL_WRITABLE pour indiquer si un canal est lisible et/ou écrivable.
Tcl_Channel channel (in)
Le canal sur lequel opérer.
int direction (in)
TCL_READABLE signifie que le handle d'entrée est requis ; TCL_WRITABLE signifie que le handle de sortie est requis.
ClientData *handlePtr (out)
Pointe vers l'emplacement où le handle spécifique au système d'exploitation doit être stocké.
int size (in)
La taille, en octets, des tampons à allouer dans ce canal.
int mask (in)
Une combinaison OU de TCL_READABLE, TCL_WRITABLE et TCL_EXCEPTION qui indique les événements qui se sont produits sur ce canal.
Tcl_Interp *interp (in)
Interpréteur courant. (peut être NULL)
const char *optionName (in)
Nom de l'option invalide.
const char *optionList (in)
Liste d'options spécifiques (mots séparés par des espaces, sans le tiret « - ») à ajouter à la liste standard des options génériques. Peut être NULL pour le message d'erreur des options génériques uniquement.

DESCRIPTION

Tcl utilise une architecture de canaux à deux niveaux. Il fournit une couche supérieure générique pour permettre aux programmes C et Tcl d'effectuer des entrées et des sorties en utilisant les mêmes API pour une variété de fichiers, appareils, sockets, etc. Les API C génériques sont décrites dans l'entrée du manuel pour Tcl_OpenFileChannel.

La couche inférieure fournit des pilotes de canaux spécifiques au type pour chaque type d'appareil pris en charge sur chaque plateforme. Cette entrée de manuel décrit les API C utilisées pour communiquer entre la couche générique et les pilotes de canaux spécifiques au type. Elle explique également comment de nouveaux types de canaux peuvent être ajoutés en fournissant de nouveaux pilotes de canaux.

Les pilotes de canaux se composent d'un certain nombre de composants : Premièrement, chaque pilote de canal fournit une structure Tcl_ChannelType contenant des pointeurs vers des fonctions implémentant les diverses opérations utilisées par la couche générique pour communiquer avec le pilote de canal. La structure Tcl_ChannelType et les fonctions auxquelles elle fait référence sont décrites dans la section TCL_CHANNELTYPE, ci-dessous.

Deuxièmement, les pilotes de canaux fournissent généralement une commande Tcl pour créer des instances de ce type de canal. Par exemple, la commande Tcl open crée des canaux qui utilisent les pilotes de canaux de fichiers et de commandes, et la commande Tcl socket crée des canaux qui utilisent des sockets TCP pour la communication réseau.

Troisièmement, un pilote de canal fournit éventuellement une fonction C pour ouvrir des instances de canal de ce type. Par exemple, Tcl_OpenFileChannel ouvre un canal qui utilise le pilote de canal de fichier, et Tcl_OpenTcpClient ouvre un canal qui utilise le protocole réseau TCP. Ces fonctions de création utilisent généralement Tcl_CreateChannel en interne pour ouvrir le canal.

Pour ajouter un nouveau type de canal, vous devez implémenter une API C ou une commande Tcl qui ouvre un canal en appelant Tcl_CreateChannel. Lorsque votre pilote appelle Tcl_CreateChannel, il passe une structure Tcl_ChannelType décrivant les procédures d'E/S du pilote. La couche générique invoquera alors les fonctions référencées dans cette structure pour effectuer des opérations sur le canal.

Tcl_CreateChannel ouvre un nouveau canal et y associe typePtr et instanceData fournis. Le canal est ouvert dans le mode indiqué par mask. Pour une discussion sur les pilotes de canaux, leurs opérations et la structure Tcl_ChannelType, voir la section TCL_CHANNELTYPE, ci-dessous.

Tcl_CreateChannel interagit avec le code gérant les canaux standard. Une fois qu'un canal standard a été initialisé soit par un appel à Tcl_GetStdChannel, soit par un appel à Tcl_SetStdChannel, la fermeture de ce canal standard entraînera l'appel suivant à Tcl_CreateChannel pour faire du nouveau canal le nouveau canal standard également. Voir Tcl_StandardChannels pour un traité général sur les canaux standard et le comportement de la bibliothèque Tcl à leur égard.

Tcl_GetChannelInstanceData renvoie les données d'instance associées au canal dans channel. Ceci est identique à l'argument instanceData dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelType renvoie un pointeur vers la structure Tcl_ChannelType utilisée par le canal dans l'argument channel. Ceci est identique à l'argument typePtr dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelName renvoie une chaîne contenant le nom associé au canal, ou NULL si l'argument channelName de Tcl_CreateChannel était NULL.

Mantén la estructura del archivo. El archivo especificado por handlePtr devuelve TCL_OK. Si el canal no tiene un handle para la dirección especificada, se devuelve TCL_ERROR. Diferentes drivers de canal devuelven diferentes tipos de handles. Consulta las entradas del manual para cada driver para determinar qué tipo de handle se devuelve. Tcl_GetChannelThread devuelve el identificador del hilo que gestiona el canal especificado. Esto permite a los drivers de canal enviar sus eventos de archivo a la cola de eventos correcta incluso en un núcleo multi-hilo. Tcl_GetChannelMode devuelve una combinación OR de TCL_READABLE y TCL_WRITABLE, indicando si el canal está abierto para entrada y salida. Tcl_GetChannelBufferSize devuelve el tamaño, en bytes, de los buffers asignados para almacenar entrada o salida en el canal channel. Si el valor no fue establecido previamente por una llamada a Tcl_SetChannelBufferSize, se devuelve el valor por defecto de 4096. Tcl_SetChannelBufferSize establece el tamaño, en bytes, de los buffers que se asignarán en operaciones posteriores en el canal para almacenar entrada o salida. El argumento size debe estar entre 1 y 1 millón, permitiendo buffers de 1 byte a 1 millón de bytes. Si size está fuera de este rango, Tcl_SetChannelBufferSize establece el tamaño de los buffers en 4096. Tcl_NotifyChannel se llama por un driver de canal para indicar a la capa genérica que los eventos especificados por mask han ocurrido en el canal. Los drivers de canal son responsables de invocar esta función cuando los handlers de canal necesiten ser llamados para el canal (o tareas pendientes como una escritura pendiente deban realizarse). Consulta WATCHPROC para más detalles. Tcl_BadChannelOption se llama desde setOptionProc o getOptionProc específicos de los drivers para generar un mensaje de error completo. Tcl_ChannelBuffered devuelve el número de bytes de entrada actualmente bufferizados en el buffer interno (área de push back) del canal. No reporta sobre los datos en los buffers globales para los canales del stack que el canal especificado es parte. Tcl_IsChannelShared verifica el refcount del canal especificado y devuelve si el canal fue compartido entre múltiples intérpretes (resultado == 1) o no (resultado == 0). Tcl_IsChannelRegistered verifica si el canal especificado está registrado en el interp (resultado == 1) o no (resultado == 0). Tcl_IsChannelExisting verifica si un canal con el nombre especificado está registrado en la lista global de canales (del hilo) (resultado == 1) o no (resultado == 0). Tcl_CutChannel elimina el canal especificado de la lista global de canales (de la hilera actual). La aplicación a un canal registrado en algún intérprete no está permitida. También notifica al driver si el Tcl_ChannelType del canal es TCL_CHANNEL_VERSION_4 (o superior) y si Tcl_DriverThreadActionProc está definido. Tcl_SpliceChannel agrega el canal especificado a la lista global de canales (de la hilera actual). La aplicación a un canal registrado en algún intérprete no está permitida. También notifica al driver si el Tcl_ChannelType del canal es TCL_CHANNEL_VERSION_4 (o superior) y si Tcl_DriverThreadActionProc está definido. Tcl_ClearChannelHandlers elimina todos los handlers de canal y scripts de eventos asociados al canal especificado, así como la desactivación de todo el procesamiento de eventos para este canal.

TCL_CHANNELTYPE

Un driver de canal proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las operaciones variadas en un canal; estas operaciones se invocan cuando sea necesario por la capa genérica. La estructura fue versionada desde Tcl 8.3.2/8.4 para corregir un problema con los drivers de canal estacados. Consulta la sección OLD CHANNEL TYPES para detalles sobre la antigua estructura.

La estructura Tcl_ChannelType contiene los siguientes campos:

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

No es necesario proporcionar implementaciones para todas las operaciones de canal. Las que no son necesarias pueden ser establecidas a NULL en la estructura: blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc, y close2Proc, además de flushProc, handlerProc, threadActionProc, y truncateProc. Otras funciones que no pueden implementarse de forma significativa deberían devolver EINVAL cuando se llamen, indicando que las operaciones representadas no están disponibles. También es importante notar que wideSeekProc puede ser NULL si seekProc lo es.

El usuario debe utilizar solo la estructura mencionada para la instanciación de Tcl_ChannelType. Cuando se refieran a campos de una estructura Tcl_ChannelType, deben usar las siguientes funciones para obtener los valores: Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc, o Tcl_ChannelHandlerProc.

La modificación de las estructuras se realizó de tal manera que los tipos de canal estándar sean compatibles binariamente. Sin embargo, los tipos de canal que usan canales estacados (es decir, TLS, Trf) tienen nuevas versiones para corresponder a este cambio, ya que el código anterior para canales estacados tenía problemas.

TYPENAME

El campo typeName contiene una cadena terminada en nulo que identifica el tipo de dispositivo implementado por este driver, por ejemplo, file o socket.

Este valor puede obtenerse con Tcl_ChannelName, que devuelve un puntero a la cadena.

VERSION

El campo version debe establecerse a la versión de la estructura que requieres. TCL_CHANNEL_VERSION_2 es la versión mínima recomendada. TCL_CHANNEL_VERSION_3 debe establecerse para especificar el miembro wideSeekProc. TCL_CHANNEL_VERSION_4 debe establecerse para especificar el miembro threadActionProc (incluye wideSeekProc). TCL_CHANNEL_VERSION_5 debe establecerse para especificar los miembros truncateProc (incluye wideSeekProc y threadActionProc). Si no se establece ninguno de estos, se asume que esta Tcl_ChannelType tiene la estructura original. Consulta OLD CHANNEL TYPES para más detalles. Aunque Tcl reconocerá y funcionará con cualquiera de estas estructuras, los canales estacados deben ser de al menos TCL_CHANNEL_VERSION_2 para funcionar correctamente.

Este valor puede obtenerse con Tcl_ChannelVersion, que devuelve uno de TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 o TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

El campo blockModeProc contiene la dirección de una función llamada por la capa genérica para establecer el modo bloqueante y no bloqueante del dispositivo. BlockModeProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

El instanceData es el mismo que el valor proporcionado al llamar a Tcl_CreateChannel cuando este canal fue creado. El argumento mode es either TCL_MODE_BLOCKING o TCL_MODE_NONBLOCKING para establecer el dispositivo en modo bloqueante o no bloqueante. La función debe devolver cero si la operación fue exitosa, o un código de error POSIX no cero si la operación falló.

Si la operación es exitosa, la función puede modificar el valor proporcionado instanceData para registrar que el canal entró en modo bloqueante o no bloqueante y para implementar el comportamiento bloqueante o no bloqueante. Para algunos tipos de dispositivos, el comportamiento bloqueante y no bloqueante puede implementarse por el sistema operativo subyacente; para otros tipos de dispositivos, el comportamiento debe emularse en el driver de canal.

Este valor puede obtenerse con Tcl_ChannelBlockModeProc, que devuelve un puntero a la función.

Un driver de canal que no proporciona un blockModeProc debe ser muy cuidadoso. Debe indicar exactamente qué modo bloqueante es aceptable para él, y debería documentar esto para el usuario, para que el modo bloqueante del canal no cambie a un valor inaceptable. Cualquier confusión aquí puede llevar a un (oscuro y difícil de encontrar) deadlock del intérprete.

CLOSEPROC Y CLOSE2PROC

El campo closeProc contiene la dirección de una función llamada por la capa genérica para limpiar información relacionada con el driver cuando el canal es cerrado. CloseProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

El argumento instanceData es el mismo que el valor proporcionado al llamar a Tcl_CreateChannel cuando el canal fue creado. La función debe liberar cualquier almacenamiento mantenido por el driver de canal para este canal y cerrar los dispositivos de entrada y salida encapsulados por este canal. Antes de que esta función sea invocada, todos los datos de salida pendientes se han estado limpiando en el dispositivo. Después de invocar closeProc, no se invocarán más operaciones del driver en esta instancia. Si la operación de cierre es exitosa, la función debe devolver 0. Si la operación de cierre falla, debe devolver un código de error POSIX no cero.

Este valor puede obtenerse con Tcl_ChannelCloseProc, que devuelve un puntero a la función.

El campo close2Proc es una versión más nueva del closeProc. Si está presente, se llama en lugar de closeProc. Se invoca cuando el refcount del canal llega a cero. Close2Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverClose2Proc(
        ClientData instanceData,
        Tcl_Interp *interp);

El instanceData es el mismo que el valor proporcionado al llamar a Tcl_CreateChannel cuando este canal fue creado. La función debe liberar cualquier almacenamiento mantenido por el driver de canal para este canal y cerrar los dispositivos de entrada y salida encapsulados por este canal. Antes de que esta función sea invocada, todos los datos de salida pendientes se han estado limpiando en el dispositivo. Después de invocar close2Proc, no se invocarán más operaciones del driver en esta instancia. Si la operación de cierre es exitosa, la función debe devolver 0. Si la operación de cierre falla, debe devolver un código de error POSIX no cero.

Este valor puede obtenerse con Tcl_ChannelClose2Proc, que devuelve un puntero a la función.

INPUTPROC

Le champ inputProc contient l'adresse d'une fonction appelée par la couche générale pour lire les données du fichier ou du périphérique et les stocker dans un tampon interne. InputProc doit correspondre au prototype suivant :

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

Le instanceData est la même que la valeur passée à Tcl_CreateChannel lors de la création du canal. L'argument buf pointe vers un tableau d'octets dans lequel les données du périphérique seront stockées, et l'argument bufSize indique le nombre d'octets disponibles dans buf.

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générale. Si une erreur se produit, la fonction doit définir cette variable à un code d'erreur POSIX qui identifie l'erreur.

La fonction doit lire les données du périphérique encapsulé par le canal et les stocker dans buf. En cas de succès, la fonction doit retourner un nombre non négatif indiquant le nombre d'octets lus à partir du périphérique et stockés dans buf. En cas d'erreur, la fonction doit retourner -1. Si une erreur se produit après la lecture de certaines données du périphérique, ces données seront perdues.

Si inputProc peut déterminer que le périphérique d'entrée a des données disponibles mais moins que ce qui est demandé par l'argument bufSize, la fonction ne doit tenter de lire que la quantité de données disponible et retourner sans bloquer. Si le périphérique d'entrée n'a pas de données disponibles et que le canal est en mode non bloquant, la fonction doit retourner l'erreur EAGAIN. Si le périphérique d'entrée n'a pas de données disponibles et que le canal est en mode bloquant, la fonction doit bloquer le moins de temps possible jusqu'à ce qu'au moins un octet puisse être lu à partir du périphérique, puis retourner les données qui peuvent être lues sans bloquer.

Cette valeur peut être récupérée avec Tcl_ChannelInputProc, qui retourne un pointeur vers la fonction.

OUTPUTPROC

Le champ outputProc contient l'adresse d'une fonction appelée par la couche générale pour transférer les données d'un tampon interne vers le périphérique de sortie. OutputProc doit correspondre au prototype suivant :

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

Le instanceData est la même que la valeur passée à Tcl_CreateChannel lors de la création du canal. L'argument buf contient un tableau d'octets à écrire sur le périphérique, et l'argument toWrite indique le nombre d'octets à écrire à partir de l'argument buf.

L'argument errorCodePtr pointe vers une variable entière fournie par la couche générale pour retourner les valeurs de errno à partir de la fonction. La fonction doit définir cette variable à un code d'erreur POSIX si une erreur se produit. La fonction doit stocker un code EINVAL si le type de canal n'implémente pas la recherche.

La fonction doit écrire les données dans buf sur le périphérique de sortie encapsulé par le canal. En cas de succès, la fonction doit retourner un nombre non négatif indiquant le nombre d'octets écrits sur le périphérique de sortie. La valeur de retour est généralement la même que toWrite, mais peut être inférieure dans certains cas, par exemple si l'opération de sortie est interrompue par un signal. Si une erreur se produit, la fonction doit retourner -1. En cas d'erreur, certaines données peuvent avoir été écrites sur le périphérique.

Si le canal est en mode non bloquant et que le périphérique de sortie ne peut absorber aucune donnée, la fonction doit retourner -1 avec l'erreur EAGAIN sans écrire aucune donnée.

Cette valeur peut être récupérée avec Tcl_ChannelOutputProc, qui retourne un pointeur vers la fonction.

SEEKPROC ET WIDESEEKPROC

Le champ seekProc contient l'adresse d'une fonction appelée par la couche générale pour déplacer le point d'accès auquel les opérations d'entrée ou de sortie ultérieures s'appliqueront. SeekProc doit correspondre au prototype suivant :

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

Le instanceData est le même que la valeur donnée à Tcl_CreateChannel lors de la création de ce canal. Offset et seekMode ont la même signification que pour la procédure Tcl_Seek (décrite dans le manuel de Tcl_OpenFileChannel).

Le errorCodePtr pointe vers une variable entière fournie par la couche générale pour retourner les valeurs de errno à partir de la fonction. La fonction doit définir cette variable à un code d'erreur POSIX si une erreur se produit. La fonction doit stocker un code EINVAL si le type de canal n'implémente pas la recherche.

La valeur de retour est le nouveau point d'accès ou -1 en cas d'erreur. Si une erreur s'est produite, la fonction ne doit pas déplacer le point d'accès.

S'il existe un seekProc non nul, le champ wideSeekProc peut contenir l'adresse d'une fonction alternative qui gère les décalages larges (c'est-à-dire supérieurs à 32 bits), permettant de rechercher dans des fichiers de plus de 2 Go. La fonction wideSeekProc est appelée de préférence à seekProc, mais les deux doivent être définis si wideSeekProc est défini. WideSeekProc doit correspondre au prototype suivant :

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

Les arguments et les valeurs de retour sont les mêmes qu'avec seekProc, sauf que le type de décalage et le type de retour sont différents.

Le champ seekProc peut être récupéré avec Tcl_ChannelSeekProc, qui retourne un pointeur vers la fonction, et le champ wideSeekProc peut être récupéré avec Tcl_ChannelWideSeekProc.

SETOPTIONPROC

Le champ setOptionProc contient l'adresse d'une fonction appelée par la couche générale pour définir une option spécifique au type de canal sur un canal. setOptionProc doit correspondre au prototype suivant :

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

Le optionName est le nom d'une option à définir, et newValue est la nouvelle valeur pour cette option, sous forme de chaîne. Le instanceData est le même que la valeur donnée à Tcl_CreateChannel lors de la création de ce canal. La fonction doit effectuer toute action spécifique au type de canal nécessaire pour implémenter la nouvelle valeur de l'option.

Certaines options sont gérées par le code général et cette fonction n'est jamais appelée pour les définir, comme -blockmode. D'autres types d'options sont spécifiques à chaque type de canal et la fonction setOptionProc du pilote du canal est appelée pour les implémenter. Le champ setOptionProc peut être NUL, ce qui indique que ce type de canal ne prend pas en charge les options spécifiques.

Si la valeur de l'option est modifiée avec succès à sa nouvelle valeur, la fonction retourne TCL_OK. Elle doit appeler Tcl_BadChannelOption, qui retourne à son tour TCL_ERROR si le optionName n'est pas reconnu. Si newValue spécifie une valeur non prise en charge ou si une erreur se produit lors d'un appel système, la fonction doit stocker un message d'erreur dans le résultat de interp si interp n'est pas nul. La fonction doit également appeler Tcl_SetErrno pour stocker un code d'erreur POSIX approprié.

Cette valeur peut être récupérée avec Tcl_ChannelSetOptionProc, qui retourne un pointeur vers la fonction.

GETOPTIONPROC

Le champ getOptionProc contient l'adresse d'une fonction appelée par la couche générale pour obtenir la valeur d'une option spécifique au type de canal sur un canal. getOptionProc doit correspondre au prototype suivant :

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        Tcl_DString *optionValue);

Le optionName est le nom d'une option prise en charge par ce type de canal. Si le nom de l'option n'est pas nul, la fonction stocke sa valeur actuelle (sous forme de chaîne) dans le string dynamique Tcl optionValue. Si optionName est nul, la fonction stocke dans optionValue une liste alternée de toutes les options prises en charge et de leurs valeurs actuelles. En cas de succès, la fonction retourne TCL_OK. Elle doit appeler Tcl_BadChannelOption, qui retourne à son tour TCL_ERROR si le optionName n'est pas reconnu. Si newValue spécifie une valeur pour l'option qui n'est pas prise en charge ou si une erreur se produit lors d'un appel système, la fonction doit stocker un message d'erreur dans le résultat de interp si interp n'est pas nul. La fonction doit également appeler Tcl_SetErrno pour stocker un code d'erreur POSIX approprié.

Cette valeur peut être récupérée avec Tcl_ChannelGetOptionProc, qui retourne un pointeur vers la fonction.

>optionName est non reconnu. Si une erreur d'appel système se produit, la fonction doit laisser un message d'erreur dans le résultat de interp si interp n'est pas NULL. La fonction doit également appeler Tcl_SetErrno pour stocker un code d'erreur POSIX approprié.

Certaines options sont gérées par le code générique et cette fonction n'est jamais appelée pour récupérer leur valeur, par exemple -blockmode. D'autres options sont spécifiques à chaque type de canal et la procédure getOptionProc du pilote de canal sera appelée pour les implémenter. Le champ getOptionProc peut être NULL, ce qui indique que ce type de canal ne prend en charge aucune option spécifique au type.

Cette valeur peut être récupérée avec Tcl_ChannelGetOptionProc, qui renvoie un pointeur vers la fonction.

WATCHPROC

Le champ watchProc contient l'adresse d'une fonction appelée par la couche générique pour initialiser le mécanisme de notification d'événements afin de détecter les événements d'intérêt sur ce canal. WatchProc doit correspondre au prototype suivant :

typedef void Tcl_DriverWatchProc(
        ClientData instanceData,
        int mask);

Le instanceData est le même que la valeur passée à Tcl_CreateChannel lors de la création de ce canal. L'argument mask est une combinaison OR de TCL_READABLE, TCL_WRITABLE et TCL_EXCEPTION ; il indique les événements que l'appelant souhaite détecter sur ce canal.

La fonction doit initialiser des mécanismes spécifiques au type d'appareil pour détecter quand un événement d'intérêt est présent sur le canal. Lorsque un ou plusieurs des événements désignés se produisent sur le canal, le pilote de canal est responsable de l'appel de Tcl_NotifyChannel pour informer le module de canal générique. Le pilote doit veiller à ne pas affamer d'autres pilotes de canal ou sources de callbacks en appelant Tcl_NotifyChannel trop fréquemment. L'équité peut être assurée en utilisant la file d'événements Tcl pour permettre à l'événement du canal d'être planifié en séquence avec d'autres événements. Voir la description de Tcl_QueueEvent pour plus de détails sur la façon de mettre un événement en file d'attente.

Cette valeur peut être récupérée avec Tcl_ChannelWatchProc, qui renvoie un pointeur vers la fonction.

GETHANDLEPROC

Le champ getHandleProc contient l'adresse d'une fonction appelée par la couche générique pour récupérer un descripteur spécifique à l'appareil à partir du canal. GetHandleProc doit correspondre au prototype suivant :

typedef int Tcl_DriverGetHandleProc(
        ClientData instanceData,
        int direction,
        ClientData *handlePtr);

InstanceData est le même que la valeur passée à Tcl_CreateChannel lors de la création de ce canal. L'argument direction est soit TCL_READABLE pour récupérer le descripteur utilisé pour l'entrée, soit TCL_WRITABLE pour récupérer le descripteur utilisé pour la sortie.

Si l'implémentation du canal a des descripteurs spécifiques à l'appareil, la fonction doit récupérer le descripteur approprié associé au canal, conformément à l'argument direction. Le descripteur doit être stocké à l'emplacement référencé par handlePtr, et TCL_OK doit être retourné. Si le canal n'est pas ouvert pour la direction spécifiée, ou si l'implémentation du canal n'utilise pas de descripteurs d'appareil, la fonction doit retourner TCL_ERROR.

Cette valeur peut être récupérée avec Tcl_ChannelGetHandleProc, qui renvoie un pointeur vers la fonction.

FLUSHPROC

Le champ flushProc est actuellement réservé pour une utilisation future. Il doit être défini à NULL. FlushProc doit correspondre au prototype suivant :

typedef int Tcl_DriverFlushProc(
        ClientData instanceData);

Cette valeur peut être récupérée avec Tcl_ChannelFlushProc, qui renvoie un pointeur vers la fonction.

HANDLERPROC

Le champ handlerProc contient l'adresse d'une fonction appelée par la couche générique pour notifier le canal qu'un événement s'est produit. Il doit être défini pour les pilotes de canaux empilés qui souhaitent être informés des événements se produisant sur le canal sous-jacent (empilé). HandlerProc doit correspondre au prototype suivant :

typedef int Tcl_DriverHandlerProc(
        ClientData instanceData,
        int interestMask);

InstanceData est le même que la valeur passée à Tcl_CreateChannel lors de la création de ce canal. Le interestMask est une combinaison OR de TCL_READABLE ou TCL_WRITABLE ; il indique quel type d'événement s'est produit sur ce canal.

Cette valeur peut être récupérée avec Tcl_ChannelHandlerProc, qui renvoie un pointeur vers la fonction.

THREADACTIONPROC

Le champ threadActionProc contient l'adresse de la fonction appelée par la couche générique lorsqu'un canal est créé, fermé ou sur le point de passer à un autre thread, c'est-à-dire chaque fois que l'état du pilote spécifique au thread pourrait avoir besoin d'être initialisé ou mis à jour. Il peut être NULL. L'action TCL_CHANNEL_THREAD_REMOVE est utilisée pour notifier au pilote qu'il doit mettre à jour ou supprimer toute donnée spécifique au thread qu'il pourrait maintenir pour le canal.

L'action TCL_CHANNEL_THREAD_INSERT est utilisée pour notifier au pilote qu'il doit mettre à jour ou initialiser toute donnée spécifique au thread qu'il pourrait maintenir en utilisant le thread appelant comme associé. Voir Tcl_CutChannel et Tcl_SpliceChannel pour plus de détails.

typedef void Tcl_DriverThreadActionProc(
        ClientData instanceData,
        int action);

InstanceData est le même que la valeur passée à Tcl_CreateChannel lors de la création de ce canal.

Ces valeurs peuvent être récupérées avec Tcl_ChannelThreadActionProc, qui renvoie un pointeur vers la fonction.

TRUNCATEPROC

Le champ truncateProc contient l'adresse de la fonction appelée par la couche générique lorsqu'un canal est tronqué à une certaine longueur. Il peut être NULL.

typedef int Tcl_DriverTruncateProc(
        ClientData instanceData,
        Tcl_WideInt length);

InstanceData est le même que la valeur passée à Tcl_CreateChannel lors de la création de ce canal, et length est la nouvelle longueur du fichier sous-jacent, qui ne doit pas être négative. Le résultat doit être 0 en cas de succès ou un code errno (approprié pour être utilisé avec Tcl_SetErrno) en cas d'échec.

Ces valeurs peuvent être récupérées avec Tcl_ChannelTruncateProc, qui renvoie un pointeur vers la fonction.

TCL_BADCHANNELOPTION

Cette procédure génère un message d'erreur « mauvaise option » dans un interpréteur (optionnel). Elle est utilisée par les pilotes de canaux lorsqu'une option de mise à jour/récupération invalide est demandée. Son but est de concaténer la liste des options génériques aux options spécifiques et de factoriser le message d'erreur des options génériques.

Elle retourne toujours TCL_ERROR

Un message d'erreur est généré dans la valeur de résultat de interp pour indiquer qu'une commande a été appelée avec une mauvaise option. Le message a la forme

    bad option "blah": should be one of
    <...generic options...>+<...specific options...>
ainsi vous obtenez par exemple : 
    bad option "-blah": should be one of -blocking,
    -buffering, -buffersize, -eofchar, -translation,
    -peername, or -sockname
lorsqu'elle est appelée avec optionList égal à « peername sockname »

“blah” est l'argument optionName et “<specific options>” est une liste d'options spécifiques séparées par des espaces. La fonction prend soin d'insérer des signes moins avant chaque option, des virgules après, et un “or” avant la dernière option.

OLD CHANNEL TYPES

La structure Tcl_ChannelType originale (8.3.1 et versions antérieures) contient les champs suivants :

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
} Tcl_ChannelType;

Il est toujours possible de créer des canaux avec la structure ci-dessus. Le code interne du canal déterminera la version. Il est impératif d'utiliser la nouvelle structure Tcl_ChannelType si vous créez un pilote de canal empilé, en raison de problèmes avec l'implémentation précédente des canaux empilés (dans les versions 8.2.0 à 8.3.1).

Avant la version 8.4.0 (c'est-à-dire lors des dernières versions de 8.3 et la première partie du cycle de développement de 8.4), la structure Tcl_ChannelType contenait les champs suivants :

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_ChannelTypeVersion version;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Lorsque la structure ci-dessus est enregistrée comme type de canal, le champ version doit toujours être TCL_CHANNEL_VERSION_2.
