DESCRIPTION

Il y a plusieurs raisons d'appeler les fonctions de l'API Tcl_FS (par ex. Tcl_FSAccess et Tcl_FSStat) plutôt que d'appeler directement des fonctions système comme access et stat. Premièrement, elles fonctionnent sur plusieurs plateformes, donc une extension qui les appelle devrait fonctionner sans modification sous Unix et Windows. Deuxièmement, l'implémentation Windows de certaines de ces fonctions corrige des bogues dans les appels système. Troisièmement, ces appels de fonction gèrent les conversions de chemin « Utf vers natif de la plateforme » qui peuvent être nécessaires (et peuvent mettre en cache les résultats de telles conversions pour une plus grande efficacité lors des appels ultérieurs). Quatrièmement, et c'est peut-être le plus important, toutes ces fonctions sont « conscientes des systèmes de fichiers virtuels ». Tout système de fichiers virtuel (VFS pour faire court) qui a été enregistré (via Tcl_FSRegister) peut réacheminer l'accès aux fichiers vers des supports ou des méthodes d'accès alternatives. Cela signifie que toutes ces fonctions (et donc les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent opérer sur des « fichiers » qui ne sont pas des fichiers natifs dans le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS pour faire court) via cette API est automatiquement « consciente des systèmes de fichiers virtuels ». Bien sûr, si une extension accède directement au système de fichiers natif (via des API spécifiques à la plateforme, par exemple), Tcl ne peut pas intercepter de tels appels.

Si des VFS appropriés ont été enregistrés, les « fichiers » peuvent, pour donner deux exemples, être distants (par ex. situés sur un serveur ftp distant) ou archivés (par ex. se trouvant à l'intérieur d'une archive .zip). De tels systèmes de fichiers enregistrés fournissent une table de correspondance de fonctions pour implémenter tout ou partie de la fonctionnalité listée ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat s'abstrayent de la déclaration du buffer « struct stat », permettant d'utiliser le même code sur les systèmes qui supportent les fichiers de plus de 2 Go et ceux qui ne le supportent pas.

L'API Tcl_FS est « Tcl_Obj » et peut mettre en cache des représentations internes et d'autres chaînes liées aux chemins (par ex. le répertoire de travail courant). Une conséquence de cela est qu'il ne faut pas passer de valeurs avec un compteur de références de zéro à l'une de ces fonctions. Si de tels appels étaient traités, ils pourraient entraîner des fuites de mémoire (dans certaines circonstances, le code du système de fichiers peut souhaiter conserver une référence à la valeur passée, et donc on ne doit pas supposer qu'après le retour de l'un de ces appels, la valeur ait toujours un compteur de références de zéro - il peut avoir été incrémenté) ou un segment de faute direct (ou une autre erreur d'accès mémoire) en raison de la libération de la valeur pendant la manipulation complexe de la valeur requise pour s'assurer que le chemin est entièrement normalisé et absolu pour la détermination du système de fichiers. La leçon pratique à retenir est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect et peut provoquer des erreurs de mémoire. Le path doit avoir son compteur de références incrémenté avant d'être passé, ou avant d'être décrémenté. Pour cette raison, les valeurs avec un compteur de références de zéro sont considérées comme des chemins de système de fichiers invalides et l'appel de toute fonction de l'API Tcl_FS avec une telle valeur n'entraînera aucune action.

FONCTIONS DE L'API FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno au code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « copier fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno au code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction « créer répertoire » du système de fichiers propriétaire.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction « supprimer fichier » du système de fichiers propriétaire.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction « supprimer répertoire » du système de fichiers propriétaire.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le nom de chemin donné par destPathPtr. Si les deux chemins donnés se trouvent dans le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction « renommer fichier » de ce système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction retourne -1 et définit la variable globale C errno au code d'erreur POSIX « EXDEV » (qui signifie « lien inter-domaines »).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction « lister les volumes » non NULL et leur demande de retourner leur liste de volumes racines. Elle accumule les valeurs de retour dans une liste qui est retournée à l'appelant (avec un compteur de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant l'encodage identifié par encodingName et évalue son contenu comme un script Tcl. Elle retourne les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, l'encodage système est utilisé pour lire le contenu du fichier. Si le fichier n'a pas pu être lu, une erreur Tcl est retournée pour décrire pourquoi le fichier n'a pas pu être lu. Le caractère de fin de fichier (eofchar) est « \x1A » (^Z) pour toutes les plateformes. Si vous avez besoin d'un « ^Z » dans le code pour la comparaison de chaînes, vous pouvez utiliser « \x1A », qui sera substitué en toute sécurité par l'interpréteur Tcl en « ^Z ». Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours l'encodage système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier de code binaire en mémoire et retourne les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas, en raison des limitations du système d'exploitation dans le chargement dynamique de code binaire), Tcl tentera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile inverse l'opération, demandant que la bibliothèque indiquée par loadHandle soit supprimée du processus. Notez que, contrairement à la commande unload, cela ne donne aucune opportunité à la bibliothèque de nettoyer.

Les deux fonctions ci-dessus retournent un code d'achèvement Tcl standard. En cas d'erreur, un message d'erreur est laissé dans le résultat de l'interp.

Le jeton fourni via la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher dans un répertoire tous les fichiers qui correspondent à un modèle donné. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du globbing. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Notez que le code glob implémente les modèles récursifs en interne, donc cette fonction ne recevra jamais que des modèles simples, qui peuvent être mis en correspondance en utilisant la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment en demandant seulement que des répertoires soient retournés. Un cas spécial d'appel avec un modèle NULL indique que le chemin doit être vérifié uniquement pour le type correct.

Tcl_FSLink remplace la version bibliothèque de readlink, et l'étend pour supporter la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr sera appelée.

Si toPtr est NULL, une action de « lire le lien » est effectuée. Le résultat est un Tcl_Obj spécifiant le contenu du lien symbolique donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat est possédé par l'appelant, qui devrait appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl doit créer un lien d'un des types passés dans l'indicateur linkAction. Cet indicateur est une combinaison OR'ée de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. Là où un choix existe (c'est-à-dire plus d'un indicateur est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur de retour doit être toPtr (qui est donc déjà possédé par l'appelant). En cas d'échec, NULL est retourné.

Tcl_FSLstat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de parcours pour tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf contient des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, le dernier accès

time, last modification time, et last metadata change time. Voir PORTABLE STAT RESULT API pour une description de la manière d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSLstat renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé, et aucune information de stat n'est fournie.

Tcl_FSUtime remplace la version bibliothèque de utime.

Renvoie 0 en cas de succès et -1 en cas d'erreur (conformément à la documentation de utime). En cas de succès, la fonction mettra à jour les valeurs "atime" et "mtime" du fichier donné.

Tcl_FSFileAttrsGet implémente l'accès en lecture pour la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

Si le résultat est TCL_OK, alors une valeur a été placée dans objPtrRef, qui ne sera valable que temporairement (sauf si Tcl_IncrRefCount est appelé).

Tcl_FSFileAttrsSet implémente l'accès en écriture pour la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

Tcl_FSFileAttrStrings implémente une partie de la sous-commande file attributes hookable. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La procédure appelée peut soit renvoyer un tableau de chaînes, soit renvoyer NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl lorsqu'elle n'est plus nécessaire, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer de conserver un compteur de références de la valeur.

Tcl_FSAccess vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet de système de fichiers) dont le nom est pathname. Si pathname est un lien symbolique sous Unix, alors les permissions du fichier auquel ce lien symbolique fait référence sont testées.

En cas de succès (toutes les permissions demandées accordées), zéro est renvoyé. En cas d'erreur (au moins un bit dans mode a demandé une permission qui est refusée, ou une autre erreur s'est produite), -1 est renvoyé.

Tcl_FSStat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure Tcl_StatBuf inclut des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification et l'heure du dernier changement de métadonnées. Voir PORTABLE STAT RESULT API pour une description de la manière d'écrire du code portable pour allouer et accéder à la structure Tcl_StatBuf.

Si path existe, Tcl_FSStat renvoie 0 et la structure stat est remplie de données. Sinon, -1 est renvoyé, et aucune information de stat n'est fournie.

Tcl_FSOpenFileChannel ouvre un fichier spécifié par pathPtr et renvoie un handle de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est basée sur la procédure fopen de la bibliothèque d'entrée/sortie standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, Tcl_FSOpenFileChannel renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, Tcl_FSOpenFileChannel laisse un message d'erreur dans le résultat de interp après toute erreur.

Le nouveau canal créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez Tcl_RegisterChannel. Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, l'acte de création du nouveau canal l'assigne également comme remplacement du canal standard.

Tcl_FSGetCwd remplace la version bibliothèque de getcwd.

Renvoie le répertoire de travail actuel de la bibliothèque Tcl. Celui-ci peut être différent du répertoire de travail de la plateforme native, ce qui se produit lorsque le répertoire de travail actuel ne se trouve pas dans le système de fichiers natif.

Le résultat est un pointeur vers un Tcl_Obj spécifiant le répertoire courant, ou NULL si le répertoire courant n'a pas pu être déterminé. Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de interp.

Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compteur de références doit être décrémenté. Ceci est nécessaire pour des raisons de sécurité des threads, pour permettre à plusieurs threads d'accéder à cette fonction et aux fonctions connexes, tout en garantissant que les résultats sont toujours valides.

Tcl_FSChdir remplace la version bibliothèque de chdir. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl utilisera une combinaison de stat et access pour vérifier si le répertoire existe et possède les permissions appropriées.

Pour les résultats, voir la documentation de chdir. En cas de succès, nous conservons un enregistrement du chemin réussi dans cwdPathPtr pour les appels ultérieurs à Tcl_FSGetCwd.

Tcl_FSPathSeparator renvoie le caractère séparateur à utiliser pour l'élément le plus spécifique du chemin spécifié par pathPtr (c'est-à-dire la dernière partie du chemin).

Le séparateur est renvoyé sous forme de Tcl_Obj contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est renvoyé.

Tcl_FSJoinPath prend le Tcl_Obj donné, qui doit être une liste valide (qui est autorisée à avoir un compteur de références de zéro), et renvoie la valeur du chemin en considérant les elements premiers éléments comme des segments de chemin valides (chaque segment de chemin peut être un chemin complet, un chemin partiel ou juste un seul nom de répertoire ou de fichier possible). Si un segment de chemin est en fait un chemin absolu, alors tous les segments de chemin précédents sont ignorés. Si elements est inférieur à 0, nous utilisons toute la liste.

Il est possible que la valeur renvoyée soit en fait un élément de la liste donnée, donc l'appelant doit faire attention à incrémenter le compteur de références du résultat avant de libérer la liste.

La valeur renvoyée, généralement avec un compteur de références de zéro (mais elle pourrait être partagée dans certaines conditions), contient le chemin combiné. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. En particulier, la valeur renvoyée peut être un élément de la liste donnée, donc la libération de la liste pourrait libérer la valeur prématurément si aucun compteur de références n'a été pris. Si le nombre d'éléments est zéro, alors la valeur renvoyée sera un Tcl_Obj à chaîne vide.

Tcl_FSSplitPath prend le Tcl_Obj donné, qui devrait être un chemin valide, et renvoie une valeur de liste Tcl contenant chaque segment de ce chemin comme élément. Elle renvoie une valeur de liste avec un compteur de références de zéro. Si le lenPtr passé est non NULL, la variable à laquelle il pointe sera mise à jour pour contenir le nombre d'éléments dans la liste renvoyée.

Tcl_FSEqualPaths teste si les deux chemins donnés représentent le même objet de système de fichiers. Elle renvoie 1 si les chemins sont égaux, et 0 s'ils sont différents. Si l'un des chemins est NULL, 0 est toujours renvoyé.

Tcl_FSGetNormalizedPath tente d'extraire du Tcl_Obj donné une représentation de chemin normalisée unique, dont la valeur de chaîne peut être utilisée comme identifiant unique du fichier.

Elle renvoie la valeur du chemin normalisé, détenue par Tcl, ou NULL si le chemin était invalide ou n'a pas pu être converti avec succès. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère sur ces représentations en interne), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques puisse ne pas être la version la plus conviviale d'un chemin. La valeur renvoyée est détenue par Tcl et a une durée de vie équivalente à celle du pathPtr passé (sauf si celui-ci est un chemin relatif, auquel cas la valeur du chemin normalisé peut être libérée à tout moment lorsque le cwd change) - l'appelant peut bien sûr incrémenter le compteur de références s'il souhaite conserver une copie plus longtemps.

Tcl_FSJoinToPath prend la valeur donnée, qui devrait généralement être un chemin valide ou NULL, et y joint le tableau de segments de chemin donnés.

Renvoie une valeur, généralement avec un compteur de références de zéro (mais elle pourrait être partagée dans certaines conditions), contenant le chemin combiné. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. Si l'une des valeurs passées à cette fonction (pathPtr ou éléments de path) a un compteur de références de zéro, elles seront libérées lorsque cette fonction retournera.

Tcl_FSConvertToPathType essaie de convertir le Tcl_Obj donné en un type de chemin Tcl valide, en tenant compte du fait que le cwd peut avoir changé même si cette valeur est déjà censée être du bon type. Le nom de fichier peut commencer par "~" (pour indiquer le répertoire personnel de l'utilisateur actuel) ou "~<utilisateur>" (pour indiquer le répertoire personnel de n'importe quel utilisateur).

Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), alors TCL_OK est renvoyé. Sinon, TCL_ERROR est renvoyé, et un message d'erreur peut être laissé dans l'interpréteur.

L'API DU SYSTÈME DE FICHIERS VIRTUELS

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions qui implémentent les différentes opérations sur un système de fichiers ; ces opérations sont invoquées au besoin par la couche générique, ce qui se produit généralement via les fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un élément de données facultatif à associer à ce système de fichiers. Lors de l'appel de cette fonction, Tcl attachera le système de fichiers à la liste des systèmes de fichiers connus, et il deviendra pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera retourné.

Tcl_FSUnregister retire la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et retourne TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est retourné.

Tcl_FSData retournera le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il retournera NULL.

Tcl_FSMountsChanged est utilisé pour informer le noyau de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche générique du système de fichiers pour effectuer la gamme complète des actions liées au système de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (dont presque toutes doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni), et fonctions d'efficacité (qui n'ont besoin d'être implémentées que si elles peuvent l'être efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces solutions de repli ne sont utilisées que pour gérer les commandes initiées dans Tcl, pas dans C. Cela signifie que si une commande file rename est émise dans Tcl, et que les systèmes de fichiers pertinents n'implémentent pas leur Tcl_FSRenameFileProc, le noyau de Tcl se rabattra sur une combinaison d'autres fonctions du système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a un autre repli). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun repli de ce type ne se produit. C'est vrai, sauf pour les quatre dernières entrées du tableau des systèmes de fichiers (lstat, load, getcwd et chdir) pour lesquelles des replis se produisent effectivement au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme d'objet Tcl les prennent en forme UTF-8. L'API de l'infrastructure du système de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

INFRASTRUCTURE DE SYSTÈME DE FICHIERS

Ces champs contiennent des informations de base sur la structure du système de fichiers et les adresses des fonctions utilisées pour associer un système de fichiers particulier à un chemin de fichier, et pour gérer la gestion interne des représentations de chemin, par exemple la copie et la libération de ces représentations.

NOM DU TYPE

Le champ typeName contient une chaîne terminée par un nul qui identifie le type de système de fichiers implémenté, par exemple “native”, “zip” ou “vfs”.

LONGUEUR DE LA STRUCTURE

Le champ structureLength est généralement implémenté comme sizeof(Tcl_Filesystem), et est là pour permettre une compatibilité binaire ascendante plus facile si la taille de la structure change dans une future version de Tcl.

VERSION

Le champ version doit être défini sur TCL_FILESYSTEM_VERSION_1.

PROCÉDURE CHEMIN DANS SYSTÈME DE FICHIERS

Le champ pathInFilesystemProc contient l'adresse d'une fonction qui est appelée pour déterminer si une valeur de chemin donnée appartient à ce système de fichiers ou non. Tcl n'appellera les autres fonctions du système de fichiers qu'avec un chemin pour lequel cette fonction a retourné TCL_OK. Si le chemin n'appartient pas, -1 doit être retourné (le comportement de Tcl pour toute autre valeur de retour n'est pas défini). Si TCL_OK est retourné, alors le paramètre de sortie optionnel clientDataPtr peut être utilisé pour retourner une représentation interne (spécifique au système de fichiers) du chemin, qui sera mise en cache à l'intérieur de la valeur du chemin, et pourra être récupérée efficacement par les autres fonctions du système de fichiers. Tcl mettra simultanément en cache le fait que ce chemin appartient à ce système de fichiers. Ces caches sont invalidés lorsque des structures de système de fichiers sont ajoutées ou retirées de la liste interne des systèmes de fichiers connus de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROCÉDURE COPIER REPRÉSENTATION INTERNE

Cette fonction crée une copie de la représentation interne d'un chemin, et est appelée lorsque Tcl doit dupliquer une valeur de chemin. Si elle est NULL, Tcl ne copiera tout simplement pas la représentation interne, qui devra alors être régénérée plus tard.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

PROCÉDURE LIBÉRER REPRÉSENTATION INTERNE

Libère la représentation interne. Ceci doit être implémenté si des représentations internes nécessitent une libération (c'est-à-dire si de la mémoire est allouée lors de la génération d'une représentation interne), mais peut sinon être NULL.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

PROCÉDURE INTERNE VERS NORMALISÉ

Fonction pour convertir la représentation interne en un chemin normalisé. Seulement requis si le système de fichiers crée des valeurs de chemin pures sans représentation textuelle/de chemin. La valeur de retour est une valeur Tcl dont la représentation textuelle est le chemin normalisé.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

PROCÉDURE CRÉER REPRÉSENTATION INTERNE

Fonction pour prendre une valeur de chemin, calculer une représentation interne pour celle-ci, et stocker cette représentation native dans la valeur. Peut être NULL si les chemins n'ont pas de représentation interne, ou si la Tcl_FSPathInFilesystemProc pour ce système de fichiers crée toujours immédiatement une représentation interne pour les chemins qu'elle accepte.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

PROCÉDURE NORMALISER CHEMIN

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations textuelles pour la même valeur de chemin. Dans Tcl, chaque “chemin” doit avoir une seule représentation textuelle “normalisée” unique. Selon le système de fichiers, il peut y avoir plus d'une représentation textuelle non normalisée qui se réfère à ce chemin (par exemple, un chemin relatif, un chemin avec une casse de caractères différente si le système de fichiers est insensible à la casse, un chemin contenant une référence à un répertoire personnel comme “~”, un chemin contenant des liens symboliques, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être converti en la valeur à laquelle il pointe (mais sa casse ou d'autres aspects doivent être rendus uniques). Tous les autres composants du chemin doivent être convertis à partir des liens symboliques. Cette seule exception est requise pour s'accorder avec la sémantique de Tcl pour file delete, file rename, file copy opérant sur des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint soit au début du chemin (c'est-à-dire zéro), soit à la fin du chemin, soit à un séparateur de fichier intermédiaire dans le chemin. Elle ne pointera jamais vers une autre position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions qui sont appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui doit être utilisé avec l'ensemble complet des commandes Tcl standard doit implémenter toutes ces fonctions. Si certaines ne sont pas implémentées, certaines commandes Tcl peuvent échouer lors de l'opération sur des chemins appartenant à ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques n'a pas besoin d'implémenter la fonction readlink, etc. Le noyau Tcl s'attend à ce que les systèmes de fichiers se comportent de cette manière).

Fonction pour déterminer le type d'un chemin dans ce système de fichiers. Peut être NULL, auquel cas aucune information de type ne sera disponible pour les utilisateurs du système de fichiers. Le “type” est utilisé uniquement à des fins d'information, et doit être retourné comme la représentation textuelle de Tcl_Obj qui est retourné. Une valeur typique de retour pourrait être “networked”, “zip” ou “ftp”. Tcl incrémentera le compteur de références de cette valeur s'il souhaite conserver une référence à celle-ci, car l'objet Tcl résultant est la propriété du système de fichiers.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

PROCÉDURE SÉPARATEUR SYSTÈME DE FICHIERS

Fonction pour retourner le(s) caractère(s) séparateur(s) pour ce système de fichiers. Ceci n'a besoin d'être implémenté que si le système de fichiers souhaite utiliser un séparateur différent de la chaîne standard “/”. Entre autres utilisations, il est retourné par la commande file separator. La valeur de retour doit être une valeur avec un compteur de références de zéro.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

PROCÉDURE STAT

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes au niveau Tcl en dépendent crucialement (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La Tcl_FSStatProc remplit la structure stat statPtr avec des informations sur le fichier spécifié. Vous n'avez pas besoin de droits d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure stat inclut des informations concernant le périphérique, l'i-node (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'identifiant utilisateur (toujours 0 sous Windows), l'identifiant de groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification, et l'heure du dernier changement de métadonnées.

Si le fichier représenté par pathPtr existe, la Tcl_FSStatProc retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné, et aucune information stat n'est donnée.

PROCÉDURE ACCÈS

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes au niveau Tcl en dépendent crucialement (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est dans pathPtr. Si le nom de chemin fait référence à un lien symbolique, alors les permissions du fichier auquel ce lien symbolique fait référence doivent être testées.

En cas de succès (toutes les permissions demandées accordées), zéro est retourné. En cas d'erreur (au moins un bit dans mode demandait une permission refusée, ou une autre erreur s'est produite), -1 est retourné.

Fonction pour traiter un appel Tcl_FSOpenFileChannel. Cette fonction est nécessaire pour que les commandes Tcl telles que puts, read, gets, etc. puissent fonctionner avec des chemins appartenant à ce système de fichiers. Si ce champ est NULL, ces commandes échoueront.

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(

ENFILECHANNELPROC

Fonction pour traiter un appel Tcl_FSOpenFileChannel. Doit être implémentée pour tout système de fichiers raisonnable, car toutes les opérations qui nécessitent l'ouverture ou l'accès au contenu d'un fichier l'utiliseront (par exemple, open, encoding et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

Le Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et retourne un descripteur de canal qui peut être utilisé pour effectuer des entrées et des sorties sur le fichier. Cette API est basée sur la procédure fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier, où l'argument mode est une combinaison des drapeaux POSIX O_RDONLY, O_WRONLY, etc. Si une erreur survient lors de l'ouverture du canal, le Tcl_FSOpenFileChannelProc retourne NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, le Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le canal nouvellement créé ne doit pas être enregistré dans l'interpréteur fourni par un Tcl_FSOpenFileChannelProc ; cette tâche incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, la création du nouveau canal l'assigne également en remplacement du canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, la fonctionnalité de glob et de copie récursive sera absente du système de fichiers (et cela peut impacter des commandes comme encoding names qui utilisent la fonctionnalité de glob en interne).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit retourner tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au motif donné et respectent la spécification types. Il y a deux façons dont cette fonction peut être appelée. Si pattern est NULL, alors pathPtr est une spécification de chemin complet d'un seul fichier ou répertoire qui doit être vérifié pour son existence et son type correct. Sinon, pathPtr est un répertoire, dont le contenu doit être recherché par la fonction pour trouver des fichiers ou des répertoires du type correct. Dans les deux cas, on peut supposer que pathPtr n'est ni NULL ni vide. Il n'est pas actuellement documenté si pathPtr aura ou non un séparateur de fichier à sa fin, donc le code doit être flexible aux deux possibilités.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le processus de correspondance. Les messages d'erreur sont placés dans interp, sauf si interp est NULL auquel cas aucun message d'erreur n'a besoin d'être généré ; sur un résultat TCL_OK, les résultats doivent être ajoutés à la valeur resultPtr donnée (qui peut être supposée être une liste Tcl valide et non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (cela signifie généralement qu'elles seront des spécifications de chemin absolu). Notez que si aucune correspondance n'est trouvée, cela conduit simplement à un résultat vide ; les erreurs ne sont signalées que pour les problèmes réels de fichier ou de système de fichiers qui peuvent survenir pendant le processus de correspondance.

La structure Tcl_GlobTypeData passée dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Type Mac acceptable */
    Tcl_Obj *macType;
    /* Créateur Mac acceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de gérer correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT sont vrais (et en particulier lorsque les autres drapeaux sont faux). Dans le premier de ces cas, la fonction doit lister les répertoires contenus. Tcl utilise cela pour implémenter le glob récursif, il est donc essentiel que les systèmes de fichiers implémentent correctement la correspondance de répertoires. Dans le second de ces cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage qui se trouvent dans le pathPtr donné (et dans ce cas, pathPtr n'a pas besoin de se trouver dans le même système de fichiers - différent de tous les autres cas où cette fonction est appelée). La prise en charge de cela est essentielle si Tcl veut avoir des transitions transparentes entre différents systèmes de fichiers.

LINKPROC

Fonction pour traiter un appel Tcl_FSLink. Ne doit être implémentée que si le système de fichiers prend en charge les liens, et peut sinon être NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est priée de lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat appartient à l'appelant (et devrait donc avoir son compteur de références incrémenté avant d'être retourné). Tous les appelants doivent appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'est plus nécessaire. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Le résultat dans ce cas doit être toPtr si le lien a réussi et NULL sinon. Dans ce cas, le résultat n'appartient pas à l'appelant (c'est-à-dire qu'aucune manipulation du compteur de références des deux côtés n'est nécessaire). Voir la documentation de Tcl_FSLink pour l'interprétation correcte des drapeaux linkAction.

LISTVOLUMESPROC

Fonction pour lister les volumes de systèmes de fichiers ajoutés par ce système de fichiers. Doit être implémentée uniquement si le système de fichiers ajoute des volumes en tête du système de fichiers, afin qu'ils puissent être retournés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste des volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. La valeur de résultat est considérée comme appartenant au système de fichiers (pas au cœur de Tcl), mais doit avoir un compteur de références pour Tcl. Tcl utilisera le contenu de la liste puis décrémentera ce compteur de références. Cela permet aux systèmes de fichiers de choisir s'ils souhaitent réellement conserver une liste « globale » de volumes ou non (sinon, ils génèrent la liste à la volée et la passent à Tcl avec un compteur de références de 1, puis oublient la liste ; sinon, ils incrémentent simplement le compteur de références de leur liste globale et la passent à Tcl qui copiera le contenu puis décrémentera le compteur pour revenir à son état précédent).

Par conséquent, Tcl considère les valeurs de retour de ce proc comme étant en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne prendra pas en charge la commande file attributes. Cela permet d'attacher des informations supplémentaires arbitraires aux fichiers du système de fichiers. Si elle n'est pas implémentée, il n'est pas nécessaire d'implémenter les méthodes get et set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La fonction appelée peut soit retourner un tableau de chaînes, soit retourner NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer qu'il retourne une valeur avec un compteur de références d'au moins un.

FILEATTRSGETPROC

Retourne un code de retour Tcl standard. La valeur d'attribut récupérée, qui correspond à l'élément d'indice index dans la liste retournée par Tcl_FSFileAttrStringsProc, est un Tcl_Obj placé dans objPtrRef (si TCL_OK a été retourné) et aura probablement un compteur de références de zéro. Dans tous les cas, nous devons soit le stocker quelque part (par exemple, dans le résultat Tcl), soit incrémenter/décrémenter son compteur de références pour garantir sa libération appropriée.

Fonction pour traiter un appel Tcl_FSLoadFile. Si elle n'est pas implémentée, Tcl utilisera une copie vers un fichier temporaire natif suivie d'un Tcl_FSLoadFile sur cette copie temporaire. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut charger du code directement, ou elle peut être implémentée simplement pour renvoyer TCL_ERROR afin de désactiver complètement la fonctionnalité de chargement dans ce système de fichiers.

        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

La procédure de déchargement sera appelée avec Tcl_LoadHandle donné comme seul paramètre lorsque Tcl aura besoin de décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle renvoyé est actuellement un jeton qui peut être utilisé dans le TclpFindSymbol privé pour accéder aux fonctions du nouveau code. Chaque système de fichiers est libre de définir le Tcl_LoadHandle comme il l'exige. Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de chargement de fichier, appeler Tcl_SetErrno(EXDEV) et renvoyer un résultat non-TCL_OK indiquera à Tcl d'utiliser ses mécanismes de secours standards.
