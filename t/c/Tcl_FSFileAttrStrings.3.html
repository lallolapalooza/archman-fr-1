DESCRIPTION

Il existe plusieurs raisons pour lesquelles les fonctions Tcl_FS (comme Tcl_FSAccess et Tcl_FSStat) sont appelées au lieu d'appels directs aux fonctions système comme access et stat. Premièrement, ces fonctions sont multiplateformes, de sorte que toute extension qui les utilise doit fonctionner sans modification sous Unix et Windows. Deuxièmement, l'implémentation de certaines de ces fonctions sous Windows corrige certains bogues dans les appels système. Troisièmement, ces appels gèrent les conversions de chemins d'UTF-8 vers la plateforme native, qui peuvent être nécessaires (et peuvent mettre en cache les résultats de telles conversions pour une efficacité accrue lors d'appels ultérieurs). Quatrièmement, et probablement le plus important, toutes ces fonctions sont « conscientes des systèmes de fichiers virtuels ». Tout système de fichiers virtuel (VFS) enregistré via Tcl_FSRegister peut réorienter l'accès aux fichiers vers des supports ou des méthodes alternatives. Cela signifie que toutes ces fonctions (et par conséquent les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent fonctionner avec des « fichiers » qui ne sont pas des fichiers natifs dans le système de fichiers. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS) via cette API est considérée comme « consciente des systèmes de fichiers virtuels ». Évidemment, si une extension accède directement au système de fichiers natif (par exemple via des API spécifiques au système), Tcl ne peut pas intercepter de tels appels.

Si des systèmes de fichiers virtuels ont été correctement enregistrés, les « fichiers » peuvent, par exemple, être distants (par exemple, situés sur un serveur FTP distant) ou archivés (par exemple, situés à l'intérieur d'une archive ZIP). De tels systèmes de fichiers virtuels enregistrés fournissent une table de fonctions pour implémenter tout ou partie des fonctionnalités mentionnées ici. Enfin, les appels Tcl_FSStat et Tcl_FSLstat abstraient le contenu du buffer struct stat, permettant d'utiliser le même code sur des systèmes avec et sans prise en charge de fichiers de plus de 2 Go.

L'API Tcl_FS est basée sur Tcl_Obj et peut mettre en cache des représentations internes et d'autres chaînes liées aux chemins (par exemple, le répertoire courant). Une conséquence en est qu'il ne faut pas passer de valeurs avec un compteur de références nul à l'une de ces fonctions. Si de tels appels étaient effectués, cela pourrait entraîner des erreurs de mémoire (dans certains cas, le code système pourrait supprimer une référence à la valeur passée, vous ne devez donc pas supposer qu'après tout appel à ces fonctions, la valeur aura un compteur de références nul). Ou, dans d'autres cas, cela pourrait entraîner une erreur de segmentation (ou une autre erreur d'accès mémoire) car la valeur a été libérée pendant la manipulation complexe de la valeur pour s'assurer que le chemin est normalisé et absolu pour le système de fichiers. La leçon pratique à retenir est que :

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect et peut entraîner des erreurs de mémoire. Le path doit incrémenter son compteur de références avant d'être passé, ou le décrémenter. Pour cette raison, les valeurs avec un compteur de références nul sont considérées comme invalides comme chemins du système de fichiers et tout appel à une fonction de l'API Tcl_FS avec de telles valeurs n'entraînera aucune action.

FONCTIONS DE L'API FS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés sont sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction de copie de fichier du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la valeur globale d'errno sur EXDEV (code POSIX indiquant un lien croisé).

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés sont sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction de copie de répertoire du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la valeur globale d'errno sur EXDEV (code POSIX indiquant un lien croisé).

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction de création de répertoire du système de fichiers qui le possède.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction de suppression de fichier du système de fichiers.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction de suppression de répertoire du système de fichiers.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés sont sur le même système de fichiers (selon Tcl_FSGetFileSystemForPath), la fonction de renommage de fichier du système de fichiers est appelée (si elle n'est pas NULL). Sinon, la fonction renvoie -1 et définit la valeur globale d'errno sur EXDEV (code POSIX indiquant un lien croisé).

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction list volumes non NULL et lui demande de renvoyer sa liste de volumes racine. Il accumule les valeurs renvoyées dans une liste qui est renvoyée à l'appelant (avec un compteur de références de 0).

Tcl_FSEvalFileEx lit le fichier donné par pathPtr en utilisant le jeu de caractères identifié par encodingName et évalue son contenu comme un script Tcl. Elle renvoie les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, le jeu de caractères système est utilisé pour lire le contenu du fichier. Si le fichier ne peut pas être lu, une erreur Tcl décrivant pourquoi il ne peut pas être lu est renvoyée. Le caractère de fin de fichier pour les fichiers est \x1A (^Z) pour tous les systèmes. Si vous souhaitez utiliser ^Z dans le code pour des comparaisons de chaînes, vous pouvez utiliser \x1A, qui sera correctement substitué par l'interpréteur Tcl en ^Z. Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours le jeu de caractères système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier binaire en mémoire et renvoie les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr est appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne l'implémenteront pas en raison des limitations du système d'exploitation sur le chargement dynamique de code binaire), Tcl tentera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile annule cette opération, demandant au processus de supprimer la bibliothèque identifiée par loadHandle de l'exécution. Notez que, comme avec la commande unload, cette opération ne donne pas à la bibliothèque la possibilité de faire du nettoyage.

Les deux fonctions mentionnées renvoient un code d'achèvement Tcl standard. Si une erreur se produit, un message d'erreur est laissé dans le résultat de l'interp.

Le jeton fourni via la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour trouver tous les fichiers correspondant à un modèle donné dans un répertoire. La fonction appropriée pour le système de fichiers auquel appartient pathPtr est appelée.

La valeur renvoyée est un résultat Tcl standard indiquant si une erreur s'est produite pendant le processus de globbing. Les messages d'erreur sont placés dans l'interp (sauf si l'interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans le resultPtr donné.

Note : Le code de glob implémente les modèles récursifs en interne, donc cette fonction ne recevra que des modèles simples, qui peuvent correspondre à la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment, ne demandant que des répertoires à renvoyer. Un cas spécial d'appel avec un modèle NULL indique que le chemin doit uniquement être vérifié pour le bon type.

Tcl_FSLink remplace la version readlink de la bibliothèque et l'étend pour prendre en charge la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr est appelée.

Si toPtr est NULL, une action de « lecture de lien » est effectuée. Le résultat est un objet Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien ne peut pas être lu. Le résultat appartient à l'utilisateur, qui doit appeler Tcl_DecrRefCount lorsqu'il n'a plus besoin du résultat. Si toPtr n'est pas NULL, Tcl doit créer un lien d'un des types passés dans le drapeau linkAction. Ce drapeau est une combinaison OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. S'il y a un choix entre plusieurs drapeaux (c'est-à-dire que plus d'un drapeau est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur renvoyée doit être toPtr (qui appartient déjà à l'utilisateur). S'il ne peut pas être créé, NULL est renvoyé.

Tcl_FSLstat remplit la structure Tcl_StatBuf avec des informations sur le fichier spécifié. Aucun droit d'accès au fichier n'est requis pour obtenir ces informations, mais des droits de parcours sont requis dans tous les répertoires mentionnés dans le chemin menant au fichier. La structure Tcl_StatBuf contient des informations sur le périphérique, l'inœud (toujours 0 sous Windows), le mode des privilèges, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, la dernière

access, heure de dernière modification et heure de dernier changement de métadonnées. Voir **PORTABLE STAT RESULT API** pour une description de la manière d'écrire du code portable pour allouer et accéder à la structure *Tcl_StatBuf*. Si *path* existe, **Tcl_FSLstat** retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné, et aucune information de stat n'est fournie. **Tcl_FSUtime** remplace la version de la bibliothèque de utime. Ceci retourne 0 en cas de succès et -1 en cas d'erreur (conformément à la documentation de **utime**). En cas de succès, la fonction mettra à jour les valeurs « atime » et « mtime » du fichier donné. **Tcl_FSFileAttrsGet** implémente l'accès en lecture pour la sous-commande **file attributes** hookable. La fonction appropriée pour le système de fichiers auquel *pathPtr* appartient sera appelée. Si le résultat est **TCL_OK**, alors une valeur a été placée dans *objPtrRef*, qui ne sera valide que temporairement (sauf si **Tcl_IncrRefCount** est appelé). **Tcl_FSFileAttrsSet** implémente l'accès en écriture pour la sous-commande **file attributes** hookable. La fonction appropriée pour le système de fichiers auquel *pathPtr* appartient sera appelée. **Tcl_FSFileAttrStrings** implémente une partie de la sous-commande **file attributes** hookable. La fonction appropriée pour le système de fichiers auquel *pathPtr* appartient sera appelée. La procédure appelée peut soit retourner un tableau de chaînes de caractères, soit retourner NULL et placer une liste Tcl dans *objPtrRef*. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer qu'il conserve un compteur de références à la valeur. **Tcl_FSAccess** vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou d'un autre objet du système de fichiers) dont le nom est *pathname*. Si *pathname* est un lien symbolique sous Unix, alors les permissions du fichier auquel ce lien symbolique fait référence sont testées. En cas de succès (toutes les permissions demandées accordées), zéro est retourné. En cas d'erreur (au moins un bit dans mode demandait une permission qui est refusée, ou une autre erreur s'est produite), -1 est retourné. **Tcl_FSStat** remplit la structure *Tcl_StatBuf* *statPtr* avec des informations sur le fichier spécifié. Vous n'avez besoin d'aucun droit d'accès au fichier pour obtenir ces informations, mais vous avez besoin de droits de recherche sur tous les répertoires nommés dans le chemin menant au fichier. La structure *Tcl_StatBuf* comprend des informations concernant le périphérique, l'inode (toujours 0 sous Windows), le mode de privilège, nlink (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification et l'heure du dernier changement de métadonnées. Voir **PORTABLE STAT RESULT API** pour une description de la manière d'écrire du code portable pour allouer et accéder à la structure *Tcl_StatBuf*. Si *path* existe, **Tcl_FSStat** retourne 0 et la structure stat est remplie de données. Sinon, -1 est retourné, et aucune information de stat n'est fournie. **Tcl_FSOpenFileChannel** ouvre un fichier spécifié par *pathPtr* et retourne un handle de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est modelée sur la procédure **fopen** de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl **open** lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, **Tcl_FSOpenFileChannel** retourne NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec **Tcl_GetErrno**. De plus, si *interp* n'est pas NULL, **Tcl_FSOpenFileChannel** laisse un message d'erreur dans le résultat de *interp* après toute erreur. Le nouveau canal créé n'est pas enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez **Tcl_RegisterChannel**. Si l'un des canaux standard, **stdin**, **stdout** ou **stderr**, a été précédemment fermé, la création du nouveau canal l'attribue également comme remplacement du canal standard. **Tcl_FSGetCwd** remplace la version de la bibliothèque de **getcwd**. Il retourne le répertoire de travail courant de la bibliothèque Tcl. Cela peut être différent du répertoire de travail courant de la plateforme native, ce qui se produit lorsque le répertoire de travail courant ne se trouve pas dans le système de fichiers natif. Le résultat est un pointeur vers un Tcl_Obj spécifiant le répertoire courant, ou NULL si le répertoire courant n'a pas pu être déterminé. Si NULL est retourné, un message d'erreur est laissé dans le résultat de *interp*. Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compteur de références doit être décrémenté. Ceci est nécessaire pour des raisons de thread-safety, pour permettre à plusieurs threads d'accéder à cette fonction et aux fonctions associées, tout en garantissant que les résultats sont toujours valides. **Tcl_FSChdir** remplace la version de la bibliothèque de **chdir**. Le chemin est normalisé puis passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl se rabattra sur une combinaison de **stat** et **access** pour vérifier si le répertoire existe et a les permissions appropriées. Pour les résultats, voir la documentation de **chdir**. En cas de succès, nous conservons un enregistrement du chemin réussi dans *cwdPathPtr* pour les appels ultérieurs à **Tcl_FSGetCwd**. **Tcl_FSPathSeparator** retourne le caractère séparateur à utiliser pour l'élément le plus spécifique du chemin spécifié par *pathPtr* (c'est-à-dire la dernière partie du chemin). Le séparateur est retourné sous forme de Tcl_Obj contenant une chaîne de longueur 1. Si le chemin est invalide, NULL est retourné. **Tcl_FSJoinPath** prend le Tcl_Obj donné, qui doit être une liste valide (autorisée à avoir un compteur de références de zéro), et retourne la valeur du chemin donnée en considérant les *elements* premiers éléments comme des segments de chemin valides (chaque segment de chemin peut être un chemin complet, un chemin partiel ou juste un nom de répertoire ou de fichier possible). Si un segment de chemin est en fait un chemin absolu, alors tous les segments de chemin précédents sont ignorés. Si *elements* est inférieur à 0, nous utilisons la liste entière. Il est possible que la valeur retournée soit en fait un élément de la liste donnée, donc l'appelant doit veiller à incrémenter le compteur de références du résultat avant de libérer la liste. La valeur retournée, généralement avec un compteur de références de zéro (mais elle peut être partagée dans certaines conditions), contient le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. En particulier, la valeur retournée peut être un élément de la liste donnée, donc la libération de la liste pourrait libérer la valeur prématurément si aucun compteur de références n'a été pris. Si le nombre d'éléments est zéro, alors la valeur retournée sera un Tcl_Obj de chaîne vide. **Tcl_FSSplitPath** prend le Tcl_Obj donné, qui devrait être un chemin valide, et retourne une valeur de liste Tcl contenant chaque segment de ce chemin comme élément. Il retourne une valeur de liste avec un compteur de références de zéro. Si *lenPtr* passé n'est pas NULL, la variable à laquelle il pointe sera mise à jour pour contenir le nombre d'éléments dans la liste retournée. **Tcl_FSEqualPaths** teste si les deux chemins donnés représentent le même objet système de fichiers. Il retourne 1 si les chemins sont égaux et 0 s'ils sont différents. Si l'un des chemins est NULL, 0 est toujours retourné. **Tcl_FSGetNormalizedPath** tente d'extraire du Tcl_Obj donné une représentation unique de chemin normalisé, dont la valeur de chaîne peut être utilisée comme identifiant unique du fichier. Il retourne la valeur du chemin normalisé, détenue par Tcl, ou NULL si le chemin était invalide ou ne pouvait pas être converti avec succès. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère en interne sur ces représentations), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques puisse ne pas être la version la plus conviviale d'un chemin. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle du *pathPtr* passé (sauf si c'est un chemin relatif, auquel cas la valeur du chemin normalisé peut être libérée à tout moment où le cwd change) - l'appelant peut bien sûr incrémenter le compteur de références s'il souhaite conserver une copie plus longtemps. **Tcl_FSJoinToPath** prend la valeur donnée, qui devrait généralement être un chemin valide ou NULL, et y joint le tableau de segments de chemin donnés. Retourne une valeur, généralement avec un compteur de références de zéro (mais elle peut être partagée dans certaines conditions), contenant le chemin joint. L'appelant doit ajouter un compteur de références à la valeur avant de l'utiliser. Si l'une des valeurs passées à cette fonction (*pathPtr* ou éléments de *path*) a un compteur de références de zéro, elle sera libérée lorsque cette fonction retournera. **Tcl_FSConvertToPathType** essaie de convertir le Tcl_Obj donné en un type de chemin Tcl valide, en tenant compte du fait que le cwd peut avoir changé même si cette valeur est déjà censée être du bon type. Le nom de fichier peut commencer par « ~ » (pour indiquer le répertoire personnel de l'utilisateur courant) ou « ~<utilisateur> » (pour indiquer le répertoire personnel de n'importe quel utilisateur). Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), alors **TCL_OK** est retourné. Sinon, **TCL_ERROR** est retourné, et un message d'erreur peut être laissé dans l'interpréteur. **Tcl_FSGetInternalRep** extrait la représentation interne d'une valeur de chemin donnée, dans le système de fichiers donné. Si la valeur du chemin appartient à un système de fichiers différent, nous retournons NULL. Si la représentation interne est actuellement NULL, nous tentons de la générer, en appelant **Tcl_FSCreateInternalRepProc** du système de fichiers. Retourne NULL ou une représentation de chemin interne valide. Cette représentation interne est mise en cache, de sorte que les appels répétés à cette fonction ne nécessiteront pas de conversions supplémentaires. **Tcl_FSGetTranslatedPath** tente d'extraire le chemin traduit du Tcl_Obj donné. Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), alors elle est retournée. Sinon, NULL sera retourné, et un message d'erreur peut être laissé dans l'interpréteur. Un chemin « traduit » est un chemin qui ne contient pas de séquences « ~ » ou « ~utilisateur » (celles-ci ont été développées dans leur représentation actuelle dans le système de fichiers). La valeur retournée est détenue par l'appelant, qui doit la stocker ou appeler **Tcl_DecrRefCount** pour s'assurer que la mémoire est libérée. Cette fonction est d'une utilité pratique limitée, et **Tcl_FSGetNormalizedPath** ou **Tcl_FSGetNativePath** sont généralement de meilleures fonctions à utiliser pour la plupart des besoins. **Tcl_FSGetTranslatedStringPath** fait la même chose que **Tcl_FSGetTranslatedPath**, mais retourne une chaîne de caractères ou NULL. La chaîne retournée est dynamiquement allouéeted et détenu par l'appelant, qui doit le stocker ou appeler ckfree pour s'assurer qu'il est libéré. Encore une fois, Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des usages.

Tcl_FSNewNativePath effectue quelque chose comme l'inverse des conversions objet->chemin->représentation_native habituelles. Si un code récupère un chemin sous forme native (depuis, par exemple, readlink ou une boîte de dialogue native), et que ce chemin doit être utilisé au niveau Tcl, alors appeler cette fonction est un moyen efficace de créer le type de valeur de chemin approprié.

La valeur résultante est une valeur de « chemin » pure, qui ne recevra une représentation sous forme de chaîne UTF-8 que si cela est requis par un code Tcl.

Tcl_FSGetNativePath est destiné à être utilisé par les systèmes de fichiers natifs Win/Unix, afin qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un wrapper de commodité autour de Tcl_FSGetInternalRep. Il pourrait être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes (par exemple, sur macOS, une représentation utilisant une structure FSRef de fileSpec serait probablement plus efficace). Sous Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Actuellement, la représentation est simplement une chaîne de caractères qui peut contenir soit le chemin relatif, soit un chemin complet, absolu et normalisé dans le codage natif (des conditions complexes dictent lequel de ceux-ci sera fourni, donc aucun ne peut être garanti, sauf si le chemin est connu pour être absolu). Si vous avez besoin d'un chemin natif qui doit être absolu, vous devriez demander la version native d'un chemin normalisé. Si pour une raison quelconque une version non absolue et non normalisée du chemin est nécessaire, cela doit être construit séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache de sorte que les appels répétés à cette fonction n'entraînent pas de conversions supplémentaires. La valeur de retour est détenue par Tcl et a une durée de vie équivalente à celle du pathPtr passé en argument (sauf si celui-ci est un chemin relatif, auquel cas la représentation native peut être libérée à tout moment lorsque le cwd change).

Tcl_FSFileSystemInfo renvoie une liste de deux éléments. Le premier élément est le nom du système de fichiers (par exemple, « native », « vfs », « zip », ou « prowrap », peut-être), et le second est le type particulier du chemin donné au sein de ce système de fichiers (qui dépend du système de fichiers). Le second élément peut être vide si le système de fichiers ne fournit pas de catégorisation supplémentaire des fichiers.

Une valeur de liste valide est retournée, sauf si la valeur du chemin n'est pas reconnue, auquel cas NULL sera retourné.

Tcl_FSGetFileSystemForPath renvoie un pointeur vers le Tcl_Filesystem qui accepte ce chemin comme valide.

Si aucun système de fichiers n'accepte le chemin, NULL est retourné.

Tcl_FSGetPathType détermine si le chemin donné est relatif au répertoire courant, relatif au volume courant, ou absolu.

Il renvoie l'une des valeurs TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE ou TCL_PATH_VOLUME_RELATIVE.

API DU SYSTÈME DE FICHIERS VIRTUEL

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un système de fichiers ; ces opérations sont invoquées au besoin par la couche générique, ce qui se produit généralement par le biais des fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un élément de données facultatif à associer à ce système de fichiers. Lors de l'appel de cette fonction, Tcl attache le système de fichiers à la liste des systèmes de fichiers connus, et il devient pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera retourné.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et renvoie TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est retourné.

Tcl_FSData renverra le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il renverra NULL.

Tcl_FSMountsChanged est utilisé pour informer le cœur de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent par conséquent ne plus être correctes.

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche générique du système de fichiers pour effectuer la gamme complète des actions liées au système de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (dont la plupart doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni) et fonctions d'efficacité (qui ne doivent être implémentées que si elles peuvent être réalisées efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces solutions de repli ne sont utilisées que pour gérer les commandes initiées dans Tcl, pas dans C. Cela signifie que, si une commande file rename est émise dans Tcl, et que les systèmes de fichiers pertinents n'implémentent pas leur Tcl_FSRenameFileProc, le cœur de Tcl se rabattra sur une combinaison d'autres fonctions de système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a une solution de repli supplémentaire). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun de ces replis ne se produit. Ceci est vrai sauf pour les quatre dernières entrées de la table des systèmes de fichiers (lstat, load, getcwd et chdir) pour lesquelles des replis se produisent en effet au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme Tcl_Obj les prennent sous forme UTF-8. L'API d'infrastructure du système de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

INFRASTRUCTURE DE SYSTÈME DE FICHIERS

Ces champs contiennent des informations de base sur la structure du système de fichiers et les adresses des fonctions utilisées pour associer un système de fichiers particulier à un chemin de fichier, et pour gérer le traitement interne des représentations de chemins, par exemple la copie et la libération de telles représentations.

TYPENAME

Le champ typeName contient une chaîne terminée par null qui identifie le type du système de fichiers implémenté, par exemple “natif”, “zip” ou “vfs”.

LONGUEUR STRUCTURE

Le champ structureLength est généralement implémenté comme sizeof(Tcl_Filesystem), et est là pour permettre une compatibilité binaire ascendante plus facile si la taille de la structure change dans une future version de Tcl.

VERSION

Le champ version doit être défini à TCL_FILESYSTEM_VERSION_1.

PROCÉDURE_CHEMIN_DANS_SYSTÈME_DE_FICHIERS

Le champ pathInFilesystemProc contient l'adresse d'une fonction appelée pour déterminer si une valeur de chemin donnée appartient à ce système de fichiers ou non. Tcl n'appellera les autres fonctions du système de fichiers qu'avec un chemin pour lequel cette fonction a retourné TCL_OK. Si le chemin n'appartient pas, -1 doit être retourné (le comportement de Tcl pour toute autre valeur de retour n'est pas défini). Si TCL_OK est retourné, alors le paramètre de sortie optionnel clientDataPtr peut être utilisé pour retourner une représentation interne (spécifique au système de fichiers) du chemin, qui sera mise en cache dans la valeur du chemin, et pourra être récupérée efficacement par les autres fonctions du système de fichiers. Tcl mettra simultanément en cache le fait que ce chemin appartient à ce système de fichiers. De tels caches sont invalidés lorsque des structures de système de fichiers sont ajoutées ou supprimées de la liste interne de Tcl des systèmes de fichiers connus.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROCÉDURE_NORMALISER_CHEMIN

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations textuelles pour la même valeur de chemin. Dans Tcl, chaque « chemin » doit avoir une seule représentation textuelle « normalisée » unique. Selon le système de fichiers, il peut y avoir plus d'une représentation textuelle non normalisée qui fait référence à ce chemin (par exemple, un chemin relatif, un chemin avec une casse de caractères différente si le système de fichiers ne distingue pas la casse, un chemin contenant une référence à un répertoire personnel tel que “~”, un chemin contenant des liens symboliques, etc.). Si le tout dernier composant du chemin est un lien symbolique, il ne doit pas être converti en la valeur à laquelle il pointe (mais sa casse ou d'autres aspects doivent être rendus uniques). Tous les autres composants du chemin doivent être convertis depuis des liens symboliques. Cette unique exception est requise pour être en accord avec la sémantique de Tcl concernant file delete, file rename, file copy opérant sur des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint soit au début du chemin (c'est-à-dire zéro), soit à la fin du chemin, soit à un séparateur de fichier intermédiaire dans le chemin. Elle ne pointera jamais vers une autre position arbitraire dans le chemin. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

ROC'>OPENFILECHANNELPROC

Fonction pour traiter un appel Tcl_FSOpenFileChannel. Doit être implémentée pour tout système de fichiers raisonnable, car toutes les opérations qui nécessitent l'ouverture ou l'accès au contenu d'un fichier l'utiliseront (par exemple, les commandes open, encoding, et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

Le Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et renvoie un handle de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est modelée sur la procédure fopen de la bibliothèque d'entrées/sorties standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier, où l'argument mode est une combinaison des indicateurs POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, le Tcl_FSOpenFileChannelProc renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, le Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le nouveau canal créé ne doit pas être enregistré dans l'interpréteur fourni par un Tcl_FSOpenFileChannelProc ; cette tâche incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr était précédemment fermé, l'acte de création du nouveau canal l'attribue également comme remplacement du canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, alors la fonctionnalité glob et la copie récursive manqueront dans le système de fichiers (et cela peut affecter des commandes comme encoding names qui utilisent la fonctionnalité glob en interne).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit renvoyer tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au modèle donné et qui respectent la spécification types fournie. Il y a deux façons dont cette fonction peut être appelée. Si pattern est NULL, alors pathPtr est une spécification de chemin complet d'un seul fichier ou répertoire qui doit être vérifié pour son existence et son type correct. Sinon, pathPtr est un répertoire, dont le contenu doit être recherché par la fonction pour trouver des fichiers ou des répertoires du type correct. Dans les deux cas, pathPtr peut être supposé être non NULL et non vide. Il n'est pas actuellement documenté si pathPtr aura ou non un séparateur de fichier à la fin, donc le code doit être flexible aux deux possibilités.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le processus de correspondance. Les messages d'erreur sont placés dans interp, sauf si interp est NULL auquel cas aucun message d'erreur ne doit être généré ; en cas de résultat TCL_OK, les résultats doivent être ajoutés à la valeur resultPtr donnée (qui peut être supposée être une liste Tcl valide et non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (cela signifie généralement qu'il s'agira de spécifications de chemin absolu). Notez que si aucune correspondance n'est trouvée, cela conduit simplement à un résultat vide ; les erreurs ne sont signalées que pour les problèmes réels de fichier ou de système de fichiers qui peuvent survenir pendant le processus de correspondance.

La structure Tcl_GlobTypeData passée dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Type Mac acceptable */
    Tcl_Obj *macType;
    /* Créateur Mac acceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qu'il est important de traiter correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT sont vrais (et en particulier lorsque les autres indicateurs sont faux). Dans le premier de ces cas, la fonction doit lister les répertoires contenus. Tcl utilise cela pour implémenter le globbing récursif, il est donc essentiel que les systèmes de fichiers implémentent correctement la correspondance des répertoires. Dans le second de ces cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage qui se trouvent dans le pathPtr donné (et dans ce cas, pathPtr n'a pas besoin de se trouver dans le même système de fichiers - différent de tous les autres cas où cette fonction est appelée). Le support pour cela est essentiel si Tcl veut avoir des transitions transparentes d'un système de fichiers à un autre.

LINKPROC

Fonction pour traiter un appel Tcl_FSLink. Ne doit être implémentée que si le système de fichiers prend en charge les liens, et peut sinon être NULL.

        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,

Si toPtr est NULL, la fonction est invitée à lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. LISTVOLUMESPROC

Fonction pour lister tous les volumes du système de fichiers ajoutés par ce système de fichiers. Ne doit être implémentée que si le système de fichiers ajoute des volumes en tête du système de fichiers, afin qu'ils puissent être retournés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste des volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. La valeur du résultat est considérée comme appartenant au système de fichiers (pas au cœur de Tcl), mais un compteur de références doit être fourni pour Tcl. Tcl utilisera le contenu de la liste, puis décrémentera ce compteur de références. Cela permet aux systèmes de fichiers de choisir s'ils souhaitent réellement conserver une liste « globale » de volumes ou non (sinon, ils génèrent la liste à la volée et la passent à Tcl avec un compteur de références de 1, puis oublient la liste ; si oui, ils incrémentent simplement le compteur de références de leur liste globale et la passent à Tcl qui copiera le contenu, puis décrémentera le compteur pour le ramener à son état précédent).

Par conséquent, Tcl considère les valeurs de retour de ce proc comme étant en lecture seule.

Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de copie de répertoires, l'appel à Tcl_SetErrno(EXDEV) et le renvoi d'un code autre que TCL_OK amèneront Tcl à utiliser ses mécanismes de repli standard.

LOADFILEPROC

Fonction pour traiter un appel à Tcl_FSLoadFile. Si elle n'est pas implémentée, Tcl se rabattra sur la copie vers un fichier temporaire, suivie d'un appel à Tcl_FSLoadFile sur ce fichier temporaire. Elle ne doit donc être implémentée que si le système de fichiers peut charger du code directement, ou peut simplement être implémentée en renvoyant TCL_ERROR pour désactiver la fonctionnalité de chargement sur ce système de fichiers.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Renvoie un code de complexité Tcl standard. En cas d'erreur, un message d'erreur est laissé dans le résultat de l'interp. La fonction charge dynamiquement un fichier binaire en mémoire. En cas de succès, handlePtr doit être rempli avec un jeton pour le fichier chargé dynamiquement, et unloadProcPtr doit être rempli avec l'adresse d'une procédure. La procédure de déchargement est appelée avec le Tcl_LoadHandle donné comme seul paramètre lorsque Tcl doit décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle renvoyé est actuellement un jeton qui peut être utilisé dans le TclpFindSymbol privé pour accéder aux fonctions du nouveau code. Chaque système de fichiers peut définir le Tcl_LoadHandle selon ses besoins. Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de chargement de fichier, l'appel à Tcl_SetErrno(EXDEV) et le renvoi d'un code autre que TCL_OK amèneront Tcl à utiliser ses mécanismes de repli standard.

UNLOADFILEPROC

Fonction pour décharger un fichier qui a été précédemment chargé avec succès. Si le chargement a été implémenté, celui-ci doit également l'être, s'il y a des actions de nettoyage nécessaires.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Fonction pour traiter un appel à Tcl_FSGetCwd. La plupart des systèmes de fichiers n'ont pas besoin de l'implémenter. Elle est généralement appelée une fois, si getcwd est appelé avant chdir. Elle peut être NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si le système de fichiers prend en charge une notion native de répertoire de travail (qui peut changer indépendamment de Tcl), cette fonction doit renvoyer ce répertoire de travail sous forme de résultat, ou NULL si le répertoire de travail ne peut pas être déterminé (par exemple, l'utilisateur n'a pas les permissions appropriées sur le répertoire cwd). Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de l'interp.

CHDIRPROC

Fonction pour traiter un appel à Tcl_FSChdir. Si les systèmes de fichiers n'implémentent pas celle-ci, elle sera émulée par une série de vérifications d'accès aux répertoires. Sinon, les systèmes de fichiers qui implémentent cette fonction ne doivent renvoyer un résultat positif que si pathPtr est un répertoire valide et accessible dans leur système de fichiers. Ils ne doivent pas se souvenir du résultat, car ce résultat sera automatiquement mémorisé par Tcl_FSGetCwd. Les systèmes de fichiers réels doivent effectuer l'action correcte (c'est-à-dire appeler l'API chdir correspondante du système).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

La fonction Tcl_FSChdirProc change le répertoire de travail actuel du programme vers la valeur spécifiée dans pathPtr. La fonction renvoie -1 en cas d'erreur ou 0 en cas de succès.
