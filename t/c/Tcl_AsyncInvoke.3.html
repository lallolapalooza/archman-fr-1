Tcl_AsyncCreate(3) Procédures de la bibliothèque Tcl Tcl_AsyncCreate(3)

NOM

Tcl_AsyncCreate, Tcl_AsyncMark, Tcl_AsyncInvoke, Tcl_AsyncDelete, Tcl_AsyncReady - gérer les événements asynchrones

SYNOPSIS

#include <tcl.h>

Tcl_AsyncHandler
Tcl_AsyncCreate(proc, clientData)

void
Tcl_AsyncMark(async)

int
Tcl_AsyncInvoke(interp, code)

void
Tcl_AsyncDelete(async)

int
Tcl_AsyncReady()

ARGUMENTS

Tcl_AsyncProc *proc (entrée)
Procédure à appeler pour gérer un événement asynchrone.
ClientData clientData (entrée)
Valeur d'un mot à passer à proc.
Tcl_AsyncHandler async (entrée)
Jeton pour le gestionnaire d'événements asynchrones.
Tcl_Interp *interp (entrée)
Interpréteur Tcl dans lequel une commande était en cours d'évaluation lors de l'invocation du gestionnaire, ou NULL si le gestionnaire a été invoqué alors qu'aucun interpréteur n'était actif.
int code (entrée)
Code d'achèvement de la commande qui vient de se terminer dans interp, ou 0 si interp est NULL.

DESCRIPTION

Ces procédures fournissent un mécanisme sûr pour gérer les événements asynchrones tels que les signaux. Si un événement tel qu'un signal se produit pendant l'évaluation d'un script Tcl, il n'est pas sûr de prendre des mesures substantielles pour traiter l'événement. Par exemple, il n'est pas sûr d'évaluer un script Tcl car l'interpréteur pourrait être déjà en train d'évaluer un script ; il peut même ne pas être sûr d'allouer de la mémoire, car une allocation de mémoire pourrait être en cours lorsque l'événement se produit. La seule approche sûre consiste à définir un indicateur indiquant que l'événement s'est produit, puis à gérer l'événement plus tard, lorsque le monde est revenu à un état propre, par exemple après l'achèvement de la commande Tcl en cours.

Tcl_AsyncCreate, Tcl_AsyncDelete, et Tcl_AsyncReady sont sensibles aux threads. Ils accèdent et/ou définissent une structure de données spécifique au thread en cas de compilation du noyau avec --enable-threads. Le jeton créé par Tcl_AsyncCreate contient les informations de thread nécessaires dans lesquelles il a été appelé, de sorte que l'appel de Tcl_AsyncMark(token) ne redirige vers le gestionnaire asynchrone que le thread d'origine.

Tcl_AsyncCreate crée un gestionnaire asynchrone et renvoie un jeton pour celui-ci. Le gestionnaire asynchrone doit être créé avant toute occurrence de l'événement asynchrone qu'il est censé gérer (il n'est pas sûr de créer un gestionnaire au moment d'un événement). Lorsqu'un événement asynchrone se produit, le code qui détecte l'événement (tel qu'un gestionnaire de signal) devrait appeler Tcl_AsyncMark avec le jeton du gestionnaire. Tcl_AsyncMark marquera le gestionnaire comme prêt à être exécuté, mais n'invoquera pas le gestionnaire immédiatement. Tcl appellera le proc associé au gestionnaire plus tard, lorsque le monde sera dans un état sûr, et proc pourra alors effectuer les actions associées à l'événement asynchrone. Proc doit avoir des arguments et un résultat qui correspondent au type Tcl_AsyncProc :

typedef int Tcl_AsyncProc(
        ClientData clientData,
        Tcl_Interp *interp,
        int code);

Le clientData sera le même que l'argument clientData passé à Tcl_AsyncCreate lors de la création du gestionnaire. Si proc est appelé juste après l'exécution d'une commande dans un interpréteur, alors interp identifiera l'interpréteur dans lequel la commande a été évaluée et code sera le code d'achèvement renvoyé par cette commande. Le résultat de la commande sera présent dans le résultat de l'interpréteur. Lorsque proc renvoie, ce qu'il laisse dans le résultat de l'interpréteur sera renvoyé comme résultat de la commande et la valeur entière renvoyée par proc sera utilisée comme nouveau code d'achèvement pour la commande.

Il est également possible que proc soit appelé lorsqu'aucun interpréteur n'est actif. Cela peut se produire, par exemple, si un événement asynchrone se produit pendant que l'application attend une entrée interactive ou un événement X. Dans ce cas, interp sera NULL et code sera 0, et la valeur de retour de proc sera ignorée.

La procédure Tcl_AsyncInvoke est appelée pour invoquer tous les gestionnaires qui sont prêts. La procédure Tcl_AsyncReady renverra une valeur non nulle chaque fois que des gestionnaires asynchrones seront prêts ; elle peut être vérifiée pour éviter les appels à Tcl_AsyncInvoke quand il n'y a pas de gestionnaires prêts. Tcl appelle Tcl_AsyncReady après chaque commande évaluée et appelle Tcl_AsyncInvoke si nécessaire. Les applications peuvent également appeler Tcl_AsyncInvoke à des moments intéressants pour cette application. Par exemple, le gestionnaire d'événements de Tcl appelle Tcl_AsyncReady après chaque événement et appelle Tcl_AsyncInvoke si nécessaire. Les arguments interp et code pour Tcl_AsyncInvoke ont la même signification que pour proc : ils identifient l'interpréteur actif, le cas échéant, et le code d'achèvement de la commande qui vient de se terminer.

Tcl_AsyncDelete supprime un gestionnaire asynchrone afin que son proc ne soit jamais appelé à nouveau. Un gestionnaire peut être supprimé même s'il est prêt, et il ne sera toujours pas appelé.

Si plusieurs gestionnaires deviennent actifs en même temps, les gestionnaires sont appelés dans l'ordre où ils ont été créés (le gestionnaire le plus ancien en premier). Le code et le résultat de l'interpréteur pour les gestionnaires ultérieurs reflètent les valeurs renvoyées par les gestionnaires précédents, de sorte que le gestionnaire créé le plus récemment ait le dernier mot concernant le résultat de l'interpréteur et le code d'achèvement. Si de nouveaux gestionnaires deviennent prêts pendant que les gestionnaires sont en cours d'exécution, Tcl_AsyncInvoke les appellera tous ; à chaque point, il invoquera le gestionnaire prêt de priorité la plus élevée (le plus ancien), répétant cela encore et encore jusqu'à ce qu'il n'y ait plus de gestionnaires prêts.

AVERTISSEMENT

Il est presque toujours déconseillé pour un gestionnaire d'événements asynchrones de modifier le résultat de l'interpréteur ou de renvoyer un code différent de son argument code. Ce type de comportement peut perturber l'exécution des scripts de manière subtile et entraîner des bugs extrêmement difficiles à traquer. Si un gestionnaire d'événements asynchrones doit évaluer des scripts Tcl, il devrait d'abord sauvegarder l'état de l'interpréteur en appelant Tcl_SaveInterpState, en passant l'argument code. Lorsque le gestionnaire asynchrone a terminé, il devrait restaurer l'état de l'interpréteur en appelant Tcl_RestoreInterpState, puis renvoyer l'argument code.
