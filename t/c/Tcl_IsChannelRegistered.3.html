DESCRIPTION

Tcl utilise une architecture de canaux à deux couches. Il fournit une couche générale permettant aux programmes C et Tcl d'effectuer des entrées et sorties en utilisant les mêmes API pour divers fichiers, périphériques, sockets, etc. Les API C générales sont décrites dans le manuel de Tcl_OpenFileChannel.

La couche inférieure fournit des pilotes de canaux spécifiques à chaque type de périphérique pris en charge sur chaque plateforme. Ce manuel décrit les API C utilisées entre la couche générale et les pilotes de canaux spécifiques. Il explique également comment de nouveaux types de canaux peuvent être ajoutés en implémentant de nouveaux pilotes de canaux.

Les pilotes de canaux se composent de plusieurs composants : Premièrement, chaque pilote de canal fournit une structure Tcl_ChannelType qui contient des pointeurs vers les procédures implémentant les opérations utilisées par la couche générale pour communiquer avec le pilote de canal. La structure Tcl_ChannelType et les procédures auxquelles elle fait référence sont décrites dans la section TCL_CHANNELTYPE, ci-dessous.

Deuxièmement, les pilotes de canaux fournissent généralement une commande Tcl pour créer des instances de ce type de canal. Par exemple, la commande Tcl open crée des canaux qui utilisent les pilotes de canaux de fichiers et de commandes, et la commande Tcl socket crée des canaux qui utilisent les protocoles réseau TCP.

Troisièmement, un pilote de canal fournit éventuellement une fonction C pour ouvrir des instances de ce type de canal. Par exemple, Tcl_OpenFileChannel ouvre un canal qui utilise le pilote de canal de fichier, et Tcl_OpenTcpClient ouvre un canal qui utilise le protocole réseau TCP. Ces fonctions de création utilisent généralement Tcl_CreateChannel en interne pour ouvrir le canal.

Pour ajouter un nouveau type de canal, vous devez implémenter une API C ou une commande Tcl qui ouvre un canal en appelant Tcl_CreateChannel. Lorsque votre pilote appelle Tcl_CreateChannel, il transmet une structure Tcl_ChannelType décrivant les procédures d'E/S de votre pilote. La couche générale appellera ensuite les procédures référencées dans cette structure pour effectuer des opérations sur le canal.

Tcl_CreateChannel ouvre un nouveau canal et associe les valeurs de typePtr et instanceData à celui-ci. Le canal est ouvert dans le mode indiqué par mask. Pour une discussion sur les pilotes de canaux, leurs opérations et la structure Tcl_ChannelType, voir la section TCL_CHANNELTYPE, ci-dessous.

Tcl_CreateChannel interagit avec le code qui gère les canaux standard. Une fois qu'un canal standard a été initialisé par un appel à Tcl_GetStdChannel ou un appel à Tcl_SetStdChannel, la fermeture de ce canal entraînera le prochain appel à Tcl_CreateChannel pour faire du nouveau canal le nouveau canal standard. Consultez Tcl_StandardChannels pour un aperçu des canaux standard et du comportement de la bibliothèque Tcl à leur égard.

Tcl_GetChannelInstanceData renvoie les données d'instance associées au canal dans channel. Il s'agit de la même valeur que l'argument instanceData dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelType renvoie un pointeur vers la structure Tcl_ChannelType utilisée par le canal dans l'argument channel. Il s'agit de la même valeur que l'argument typePtr dans l'appel à Tcl_CreateChannel qui a créé ce canal.

Tcl_GetChannelName renvoie une chaîne contenant le nom associé au canal, ou NULL si l'argument channelName de Tcl_CreateChannel était NULL.

Tcl_GetChannelHandle place le handle du système d'exploitation associé à channel pour la direction donnée dans handlePtr.

L'exemple suivant montre comment Tcl_CreateChannel peut être utilisé pour créer un canal :

int main() {
    Tcl_Channel *channel;
    Tcl_ChannelType *typePtr;
    ClientData instanceData;
    int mask;
    channel = Tcl_CreateChannel(&typePtr, "file3", instanceData, TCL_READABLE | TCL_WRITABLE);
    // ... rest of the code ...
}

Tcl_GetChannelThread retourne l'identifiant du thread gérant actuellement le channel spécifié. Ceci permet aux pilotes de canal d'envoyer leurs événements de fichier à la file d'événements correcte, même pour un cœur multi-thread.

Tcl_GetChannelMode retourne une combinaison OR de TCL_READABLE et TCL_WRITABLE, indiquant si le canal est ouvert en entrée et en sortie.

Tcl_GetChannelBufferSize retourne la taille, en octets, des tampons alloués pour stocker l'entrée ou la sortie dans le channel. Si la valeur n'a pas été définie par un appel antérieur à Tcl_SetChannelBufferSize, décrit ci-dessous, alors la valeur par défaut de 4096 est retournée.

Tcl_SetChannelBufferSize définit la taille, en octets, des tampons qui seront alloués lors des opérations ultérieures sur le canal pour stocker l'entrée ou la sortie. L'argument size doit être compris entre un et un million, permettant des tampons de un octet à un million d'octets. Si size est en dehors de cette plage, Tcl_SetChannelBufferSize définit la taille du tampon à 4096.

Tcl_NotifyChannel est appelée par un pilote de canal pour indiquer à la couche générique que les événements spécifiés par mask se sont produits sur le canal. Les pilotes de canal sont responsables de l'invocation de cette fonction chaque fois que les gestionnaires de canal doivent être appelés pour le canal (ou que d'autres tâches en attente, comme la vidange d'écriture, doivent être effectuées). Voir WATCHPROC ci-dessous pour plus de détails.

Tcl_BadChannelOption est appelée depuis le setOptionProc ou getOptionProc spécifique au pilote pour générer un message d'erreur complet.

Tcl_ChannelBuffered retourne le nombre d'octets d'entrée actuellement mis en mémoire tampon dans le tampon interne (zone de retour en arrière) du canal lui-même. Il ne signale pas les données dans les tampons globaux de la pile de canaux dont fait partie le canal fourni.

Tcl_IsChannelShared vérifie le compteur de références du channel spécifié et retourne si le channel était partagé entre plusieurs interpréteurs (résultat == 1) ou non (résultat == 0).

Tcl_IsChannelRegistered vérifie si le channel spécifié est enregistré dans l'interpréteur interp donné (résultat == 1) ou non (résultat == 0).

Tcl_IsChannelExisting vérifie si un canal portant le nom spécifié est enregistré dans la liste globale (de thread) de tous les canaux (résultat == 1) ou non (résultat == 0).

Tcl_CutChannel supprime le channel spécifié de la liste globale (de thread) de tous les canaux (du thread courant). L'application à un canal toujours enregistré dans un interpréteur n'est pas autorisée. Notifie également le pilote si la version de Tcl_ChannelType est TCL_CHANNEL_VERSION_4 (ou supérieure), et Tcl_DriverThreadActionProc est définie pour celui-ci.

Tcl_SpliceChannel ajoute le channel spécifié à la liste globale (de thread) de tous les canaux (du thread courant). L'application à un canal enregistré dans un interpréteur n'est pas autorisée. Notifie également le pilote si la version de Tcl_ChannelType est TCL_CHANNEL_VERSION_4 (ou supérieure), et Tcl_DriverThreadActionProc est définie pour celui-ci.

Tcl_ClearChannelHandlers supprime tous les gestionnaires de canal et scripts d'événements associés au channel spécifié, fermant ainsi tout traitement d'événements pour ce canal.

TCL_CHANNELTYPE

Un pilote de canal fournit une structure Tcl_ChannelType qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un canal ; ces opérations sont invoquées si nécessaire par la couche générique. La structure a été versionnée à partir de Tcl 8.3.2/8.4 pour corriger un problème avec les pilotes de canaux empilés. Voir la section OLD CHANNEL TYPES ci-dessous pour plus de détails sur l'ancienne structure.

La structure Tcl_ChannelType contient les champs suivants :

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Il n'est pas nécessaire de fournir des implémentations pour toutes les opérations de canal. Celles qui ne sont pas nécessaires peuvent être mises à NULL dans la structure : blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc, et close2Proc, en plus de flushProc, handlerProc, threadActionProc, et truncateProc. D'autres fonctions qui ne peuvent pas être implémentées de manière significative devraient retourner EINVAL lorsqu'elles sont appelées, pour indiquer que les opérations qu'elles représentent ne sont pas disponibles. Notez également que wideSeekProc peut être NULL si seekProc l'est.

L'utilisateur ne doit utiliser que la structure ci-dessus pour l'instanciation de Tcl_ChannelType. Lors de la référence aux champs d'une structure Tcl_ChannelType, les fonctions suivantes doivent être utilisées pour obtenir les valeurs : Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc, ou Tcl_ChannelHandlerProc.

La modification des structures a été effectuée de telle sorte que les types de canaux standard soient binaires compatibles. Cependant, les types de canaux qui utilisent des canaux empilés (c'est-à-dire TLS, Trf) ont de nouvelles versions pour correspondre au changement ci-dessus car le code précédent pour les canaux empilés avait des problèmes.

TYPENAME

Le champ typeName contient une chaîne terminée par un null qui identifie le type du périphérique implémenté par ce pilote, par exemple file ou socket.

Cette valeur peut être récupérée avec Tcl_ChannelName, qui retourne un pointeur vers la chaîne.

VERSION

Le champ version doit être défini sur la version de la structure dont vous avez besoin. TCL_CHANNEL_VERSION_2 est le minimum recommandé. TCL_CHANNEL_VERSION_3 doit être défini pour spécifier le membre wideSeekProc. TCL_CHANNEL_VERSION_4 doit être défini pour spécifier le membre threadActionProc (inclut wideSeekProc). TCL_CHANNEL_VERSION_5 doit être défini pour spécifier les membres truncateProc (inclut wideSeekProc et threadActionProc). S'il n'est défini sur aucune de ces valeurs, alors cette Tcl_ChannelType est supposée avoir la structure originale. Voir OLD CHANNEL TYPES pour plus de détails. Bien que Tcl reconnaisse et fonctionne avec les deux structures, les canaux empilés doivent être d'au moins TCL_CHANNEL_VERSION_2 pour fonctionner correctement.

Cette valeur peut être récupérée avec Tcl_ChannelVersion, qui retourne l'une des valeurs TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 ou TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

Le champ blockModeProc contient l'adresse d'une fonction appelée par la couche générique pour définir le mode bloquant et non bloquant sur le périphérique. BlockModeProc doit correspondre au prototype suivant :

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

Le instanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument mode est soit TCL_MODE_BLOCKING soit TCL_MODE_NONBLOCKING pour définir le périphérique en mode bloquant ou non bloquant. La fonction doit retourner zéro si l'opération a réussi, ou un code d'erreur POSIX non nul si l'opération a échoué.

Si l'opération réussit, la fonction peut modifier le instanceData fourni pour enregistrer que le canal est entré en mode bloquant ou non bloquant et pour implémenter le comportement bloquant ou non bloquant. Pour certains types de périphériques, le comportement bloquant et non bloquant peut être implémenté par le système d'exploitation sous-jacent ; pour d'autres types de périphériques, le comportement doit être émulé dans le pilote de canal.

Cette valeur peut être récupérée avec Tcl_ChannelBlockModeProc, qui retourne un pointeur vers la fonction.

Un pilote de canal qui ne fournit pas de blockModeProc doit être très, très prudent. Il doit indiquer à la couche générique exactement quel mode de blocage lui convient, et doit également le documenter pour l'utilisateur afin que le mode de blocage du canal ne soit pas changé à une valeur inacceptable. Toute confusion ici peut conduire l'interpréteur à une impasse (fausse et difficile à trouver).

CLOSEPROC ET CLOSE2PROC

Le champ closeProc contient l'adresse d'une fonction appelée par la couche générique pour nettoyer les informations liées au pilote lorsque le canal est fermé. CloseProc doit correspondre au prototype suivant :

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

L'argument instanceData est la même valeur que celle fournie à Tcl_CreateChannel lors de la création du canal. La fonction doit libérer toute mémoire maintenue par le pilote de canal pour ce canal, et fermer les périphériques d'entrée et de sortie encapsulés par ce canal. Toute sortie mise en file d'attente aura été vidée vers le périphérique avant que cette fonction ne soit appelée, et aucune autre opération de pilote ne sera invoquée sur cette instance après l'appel de la closeProc. Conservez toute la structure du fichier. La valeur de `re` doit retourner zéro en cas de succès, sinon un code d'erreur POSIX non nul. De plus, si une erreur se produit et que `interp` n'est pas `NULL`, la procédure doit stocker un message d'erreur dans le résultat de l'interpréteur. Alternativement, les canaux qui prennent en charge la fermeture indépendante des côtés lecture et écriture peuvent définir `closeProc` sur `TCL_CLOSE2PROC` et `close2Proc` sur l'adresse d'une fonction qui correspond au schéma de prototype suivant : ```c typedef int Tcl_DriverClose2Proc( ClientData instanceData, Tcl_Interp *interp, int flags); ``` Le `close2Proc` sera appelé avec `flags` défini sur un OR de `TCL_CLOSE_READ` ou `TCL_CLOSE_WRITE`, indiquant que le pilote doit fermer le côté lecture et/ou écriture du canal. Le pilote de canal peut être appelé pour effectuer des opérations supplémentaires sur le canal après que `close2Proc` a fermé une ou deux parties du canal. Si `flags` est `0`, le pilote doit fermer le canal dans le mode décrit ci-dessus pour `closeProc`. Aucune autre opération ne sera invoquée sur cette instance après l'appel de `close2Proc` avec tous les flags effacés. Dans tous les cas, le `close2Proc` doit retourner zéro si l'opération de fermeture a réussi ; sinon, il doit retourner un code d'erreur POSIX non nul. De plus, si une erreur se produit et que `interp` n'est pas `NULL`, la procédure doit stocker un message d'erreur dans le résultat de l'interpréteur. Les valeurs de `closeProc` et `close2Proc` peuvent être récupérées avec `Tcl_ChannelCloseProc` ou `Tcl_ChannelClose2Proc`, qui retournent un pointeur vers la fonction correspondante. ### INPUTPROC Le champ `inputProc` contient l'adresse d'une fonction appelée par la couche générique pour lire des données d'un périphérique ou d'un fichier et les stocker dans un tampon interne. `inputProc` doit correspondre au schéma de prototype suivant : ```c typedef int Tcl_DriverInputProc( ClientData instanceData, char *buf, int bufSize, int *errorCodePtr); ``` `instanceData` est la même valeur que celle passée à `Tcl_CreateChannel` lors de la création du canal. L'argument `buf` pointe vers un tableau d'octets dans lequel l'entrée du périphérique sera stockée, et `bufSize` indique combien d'octets sont disponibles dans `buf`. L'argument `errorCodePtr` pointe vers une variable entière fournie par la couche générique. Si une erreur se produit, la fonction doit définir cette valeur sur un code d'erreur POSIX qui identifie l'erreur. La fonction doit lire les données du périphérique encapsulé par le canal et les stocker dans `buf`. En cas de succès, elle doit retourner un nombre non négatif indiquant combien d'octets ont été lus du périphérique et stockés dans `buf`. En cas d'erreur, elle doit retourner -1. Si une erreur se produit après que certaines données ont été lues du périphérique, ces données seront perdues. Si `inputProc` peut déterminer que des données sont disponibles pour le périphérique mais moins que ce qui est demandé par `bufSize`, la fonction ne doit tenter de lire que ce qui est disponible et retourner sans bloquer. Si le périphérique n'a pas de données disponibles et que le canal est en mode non bloquant, la fonction doit retourner une erreur `EAGAIN`. Si le périphérique n'a pas de données disponibles et que le canal est en mode bloquant, la fonction doit bloquer le plus longtemps possible jusqu'à ce qu'au moins un octet puisse être lu du périphérique, puis retourner le maximum de données qu'elle peut lire sans bloquer. Cette valeur peut être récupérée avec `Tcl_ChannelInputProc`, qui retourne un pointeur vers la fonction. ### OUTPUTPROC Le champ `outputProc` contient l'adresse d'une fonction appelée par la couche générique pour transférer des données d'un tampon interne vers le périphérique de sortie. `outputProc` doit correspondre au schéma de prototype suivant : ```c typedef int Tcl_DriverOutputProc( ClientData instanceData, const char *buf, int toWrite, int *errorCodePtr); ``` `instanceData` est la même valeur que celle passée à `Tcl_CreateChannel` lors de la création du canal. L'argument `buf` contient un tableau d'octets qui sera écrit sur le périphérique, et `toWrite` indique combien d'octets seront écrits à partir de l'argument `buf`. `errorCodePtr` pointe vers une variable entière fournie par la couche générique. Si une erreur se produit, la fonction doit définir cette valeur sur un code d'erreur POSIX qui identifie l'erreur. La fonction doit écrire les données dans `buf` sur le périphérique de sortie encapsulé par le canal. En cas de succès, elle doit retourner un nombre non négatif indiquant combien d'octets ont été écrits sur le périphérique de sortie. La valeur de retour est normalement la même que `toWrite`, mais elle peut être inférieure dans certains cas, par exemple lorsque l'opération de sortie est interrompue par un signal. Si une erreur se produit, la fonction doit retourner -1. En cas d'erreur, certaines données pourraient avoir été écrites sur le périphérique. Si le canal est en mode non bloquant et que le périphérique de sortie ne peut pas absorber de données, la fonction doit retourner -1 avec une erreur `EAGAIN` sans écrire de données. Cette valeur peut être récupérée avec `Tcl_ChannelOutputProc`, qui retourne un pointeur vers la fonction. ### SEEKPROC_Y_WIDESEEKPROC Le champ `seekProc` contient l'adresse d'une fonction appelée par la couche générique pour déplacer le point d'accès auquel les futures opérations d'entrée ou de sortie seront appliquées. `seekProc` doit correspondre au schéma de prototype suivant : ```c typedef int Tcl_DriverSeekProc( ClientData instanceData, long offset, int seekMode, int *errorCodePtr); ``` `instanceData` est la même valeur que celle passée à `Tcl_CreateChannel` lors de la création de ce canal. `offset` et `seekMode` ont la même signification que dans la fonction `Tcl_Seek` (mentionnée dans le manuel de `Tcl_OpenFileChannel`). `errorCodePtr` pointe vers une variable entière fournie par la couche générique pour retourner les valeurs de `errno`. Si une erreur se produit, la fonction doit définir cette valeur sur un code d'erreur POSIX. Si le canal n'implémente pas le déplacement de point d'accès, `errorCodePtr` doit avoir la valeur `EINVAL`. La valeur de retour est le nouveau point d'accès ou -1 en cas d'erreur. Si une erreur se produit, la fonction ne doit pas déplacer le point d'accès. S'il existe un champ `seekProc` non nul, le champ `wideSeekProc` peut contenir l'adresse d'une fonction alternative qui gère les décalages (c'est-à-dire plus grands que 32 bits), permettant les décalages dans des fichiers de plus de 2 Go. La fonction `wideSeekProc` est appelée de préférence à `seekProc`, mais les deux doivent être définis si `wideSeekProc` est défini. `WideSeekProc` doit correspondre au schéma de prototype suivant : ```c typedef Tcl_WideInt Tcl_DriverWideSeekProc( ClientData instanceData, Tcl_WideInt offset, int seekMode, int *errorCodePtr); ``` Les arguments et les valeurs de retour ont la même signification qu'avec `seekProc`, à l'exception du type des décalages et du type de retour qui sont différents. La valeur `seekProc` peut être récupérée avec `Tcl_ChannelSeekProc`, qui retourne un pointeur vers la fonction, et la valeur `wideSeekProc` peut être récupérée avec `Tcl_ChannelWideSeekProc`. ### SETOPTIONPROC Le champ `setOptionProc` contient l'adresse d'une fonction appelée par la couche générique pour configurer une option spécifique au type de canal sur un canal. `setOptionProc` doit correspondre au schéma de prototype suivant : ```c typedef int Tcl_DriverSetOptionProc( ClientData instanceData, Tcl_Interp *interp, const char *optionName, const char *newValue); ``` `optionName` est le nom d'une option à configurer, et `newValue` est la nouvelle valeur de l'option, sous forme de chaîne. `instanceData` est la même valeur que celle passée à `Tcl_CreateChannel` lors de la création de ce canal. La fonction doit effectuer l'action spécifique au type de canal pour implémenter la nouvelle valeur de l'option. Certaines options sont gérées par la couche générique et cette fonction n'est jamais appelée pour les configurer, comme `-blockmode`. D'autres options sont spécifiques au type de canal, et la fonction `setOptionProc` du pilote de canal est appelée pour les implémenter. Le champ `setOptionProc` peut être `NULL`, ce qui indique que ce type de canal ne prend pas en charge d'options spécifiques au type. Si la valeur de l'option est correctement modifiée à sa nouvelle valeur, la fonction retourne `TCL_OK`. Elle doit appeler `Tcl_BadChannelOption`, qui retourne `TCL_ERROR` si le nom de l'option est inconnu. Si `newValue` spécifie une valeur non prise en charge ou si une erreur se produit dans un appel système, la fonction doit stocker un message d'erreur dans le résultat de `interp` si `interp` n'est pas `NULL`. La fonction doit également appeler `Tcl_SetErrno` pour stocker un code d'erreur POSIX approprié. Cette valeur peut être récupérée avec `Tcl_ChannelSetOptionProc`, qui retourne un pointeur vers la fonction. ### GETOPTIONPROC Le champ `getOptionProc` contient l'adresse d'une fonction appelée par la couche générique pour obtenir la valeur d'une option spécifique au type de canal sur un canal. `getOptionProc` doit correspondre au schéma de prototype suivant : ```c typedef int Tcl_DriverGetOptionProc( ClientData instanceData, Tcl_Interp *interp, const char *optionName, Tcl_DString *optionValue); ``` `optionName` est le nom d'une option prise en charge par ce type de canal. Si le nom de l'option n'est pas `NULL`, la fonction stocke la valeur actuelle de l'option sous forme de chaîne dans la chaîne dynamique Tcl `optionValue`. Si le nom de l'option est `NULL`, la fonction stocke une liste alternative des options prises en charge et de leurs valeurs actuelles dans `optionValue`. En cas de succès, la fonction retourne `TCL_OK`. Elle doit appeler `Tcl_BadChannelOption`, qui retourne `TCL_ERROR` si le nom de l'option est inconnu. Si `newValue` spécifie une valeur non prise en charge ou si une erreur se produit dans un appel système, la fonction doit stocker un message d'erreur dans le résultat de `interp` si `interp` n'est pas `NULL`. La fonction doit également appeler `Tcl_SetErrno` pour stocker un code d'erreur POSIX approprié. Cette valeur peut être récupérée avec `Tcl_ChannelGetOptionProc`, qui retourne un pointeur vers la fonction.

WATCHPROC

Le champ watchProc contient l'adresse d'une fonction appelée par la couche générale pour initialiser le mécanisme de notification d'événements d'intérêt sur ce canal. WatchProc doit correspondre au prototype suivant :

typedef void Tcl_DriverWatchProc(
        ClientData instanceData,
        int mask);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument mask est une combinaison OR de TCL_READABLE, TCL_WRITABLE, et TCL_EXCEPTION ; il indique les événements dont l'appelant souhaite être notifié sur ce canal.

La fonction doit initialiser les mécanismes spécifiques au type de périphérique pour notifier lorsqu'un événement d'intérêt est présent sur le canal. Lorsqu'un événement d'intérêt se produit sur le canal, le pilote de canal doit appeler Tcl_NotifyChannel pour informer la couche générale des canaux. Le pilote doit éviter que d'autres pilotes de canaux ou sources de callbacks ne soient bloqués en appelant Tcl_NotifyChannel trop fréquemment. L'équité peut être assurée en utilisant la file d'événements de Tcl pour permettre à l'événement de canal d'être planifié séquentiellement avec d'autres événements. Voir la description de Tcl_QueueEvent pour plus de détails sur la planification d'un événement.

Cette valeur peut être récupérée avec Tcl_ChannelWatchProc, qui renvoie l'adresse de la fonction.

GETHANDLEPROC

Le champ getHandleProc contient l'adresse d'une fonction appelée par la couche générale pour récupérer un handle spécifique au canal. GetHandleProc doit correspondre au prototype suivant :

typedef int Tcl_DriverGetHandleProc(
        ClientData instanceData,
        int direction,
        ClientData *handlePtr);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument direction est TCL_READABLE pour récupérer le handle utilisé pour l'entrée, ou TCL_WRITABLE pour récupérer le handle utilisé pour la sortie.

Si l'implémentation du canal a des handles spécifiques, la fonction doit récupérer le handle approprié en fonction de l'argument direction. Le handle doit être stocké à l'emplacement référencé par handlePtr, et TCL_OK doit être retourné. Si le canal n'est pas ouvert pour la direction spécifiée, ou si l'implémentation du canal n'utilise pas de handles spécifiques, la fonction doit retourner TCL_ERROR.

Cette valeur peut être récupérée avec Tcl_ChannelGetHandleProc, qui renvoie l'adresse de la fonction.

FLUSHPROC

Le champ flushProc est réservé pour une utilisation future. Il doit être défini à NULL. FlushProc doit correspondre au prototype suivant :

typedef int Tcl_DriverFlushProc(
        ClientData instanceData);

Cette valeur peut être récupérée avec Tcl_ChannelFlushProc, qui renvoie l'adresse de la fonction.

HANDLERPROC

Le champ handlerProc contient l'adresse d'une fonction appelée par la couche générale pour notifier au pilote de canal qu'un événement s'est produit. Il doit être défini pour les pilotes de canaux empilés qui souhaitent être notifiés des événements se produisant sur le canal sous-jacent (empilé). HandlerProc doit correspondre au prototype suivant :

typedef int Tcl_DriverHandlerProc(
        ClientData instanceData,
        int interestMask);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal. L'argument interestMask est une combinaison OR de TCL_READABLE ou TCL_WRITABLE ; il indique le type d'événement qui s'est produit sur ce canal.

Cette valeur peut être récupérée avec Tcl_ChannelHandlerProc, qui renvoie l'adresse de la fonction.

THREADACTIONPROC

Le champ threadActionProc contient l'adresse de la fonction appelée par la couche générale lorsqu'un canal est créé, fermé ou déplacé vers un autre thread, c'est-à-dire lorsque l'état spécifique au thread du pilote peut devoir être initialisé ou mis à jour. Il peut être NULL. L'action TCL_CHANNEL_THREAD_REMOVE est utilisée pour notifier au pilote qu'il doit mettre à jour ou supprimer toute donnée spécifique au thread qu'il pourrait détenir pour le canal.

L'action TCL_CHANNEL_THREAD_INSERT est utilisée pour notifier au pilote qu'il doit mettre à jour ou initialiser toute donnée spécifique au thread qu'il pourrait détenir en utilisant le thread appelant comme association. Voir Tcl_CutChannel et Tcl_SpliceChannel pour plus de détails.

typedef void Tcl_DriverThreadActionProc(
        ClientData instanceData,
        int action);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal.

Ces valeurs peuvent être récupérées avec Tcl_ChannelThreadActionProc, qui renvoie l'adresse de la fonction.

TRUNCATEPROC

Le champ truncateProc contient l'adresse de la fonction appelée par la couche générale lorsqu'un canal est tronqué à une longueur spécifiée. Il peut être NULL.

typedef int Tcl_DriverTruncateProc(
        ClientData instanceData,
        Tcl_WideInt length);

InstanceData est la même valeur que celle passée à Tcl_CreateChannel lors de la création de ce canal, et length est la nouvelle longueur du fichier sous-jacent, qui ne doit pas être négative. Le résultat doit être 0 en cas de succès, ou un code d'erreur (modifiable pour être utilisé avec Tcl_SetErrno) en cas d'échec.

Ces valeurs peuvent être récupérées avec Tcl_ChannelTruncateProc, qui renvoie l'adresse de la fonction.

TCL_BADCHANNELOPTION

Cette procédure génère un message d'erreur "mauvaise option" dans un interpréteur (optionnel). Elle est utilisée par les pilotes de canaux lorsqu'une option invalide est demandée. Son but est de concaténer la liste des options génériques avec les options spécifiques et de factoriser le message d'erreur des options génériques.

Elle retourne toujours TCL_ERROR.

Un message d'erreur est généré dans la valeur de résultat de interp pour indiquer qu'une commande a été appelée avec une option invalide. Le message a la forme :

    bad option "blah": should be one of
    <...generic options...>+<...specific options...>
par exemple : 
    bad option "-blah": should be one of -blocking,
    -buffering, -buffersize, -eofchar, -translation,
    -peername, or -sockname
lorsqu'elle est appelée avec optionList égal à "peername sockname".

"blah" est l'argument optionName, et "<specific options>" est une liste séparée par des espaces d'options spécifiques. La fonction s'assure d'insérer des tirets avant chaque option, des virgules après et un "or" avant la dernière option.

OLD CHANNEL TYPES

La structure Tcl_ChannelType originale (8.3.1 et versions antérieures) contenait les champs suivants :

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
} Tcl_ChannelType;

Bien qu'il soit possible de créer des canaux avec la structure ci-dessus, le code interne du canal déterminera la version. Il est essentiel d'utiliser la nouvelle structure Tcl_ChannelType si vous créez un pilote de canal empilé en raison de problèmes avec l'implémentation précédente des canaux empilés (8.2.0 à 8.3.1).

Avant 8.4.0 (c'est-à-dire, pendant les versions ultérieures de 8.3 et le début du cycle de développement de 8.4), la structure Tcl_ChannelType contenait les champs suivants :

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_ChannelTypeVersion version;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Lorsque la structure ci-dessus est enregistrée comme type de canal, le champ version doit toujours être TCL_CHANNEL_VERSION_2.

typedef void Tcl_DriverDeleteProc(

Tcl_IsChannelRegistered(3) - Tcl

Tcl_IsChannelRegistered(3) - Tcl

NOM

Tcl_IsChannelRegistered - enregistre un type de canal.

SYNOPSIS

#include <tcl.h>

int
Tcl_IsChannelRegistered(interp, typeName)
Tcl_Interp *interp;
const char *typeName;

ARGUMENTS

interp
Interpréteur Tcl.
typeName
Nom du type de canal à vérifier.

DESCRIPTION

La fonction Tcl_IsChannelRegistered vérifie si un type de canal nommé typeName est actuellement enregistré dans l'interpréteur interp. Elle renvoie 1 si le type est enregistré, et 0 sinon.

Cette fonction est utile pour vérifier si un nouveau type de canal peut être enregistré sans conflit, ou pour déterminer si un canal existant appartient à un type particulier.

TCL_CHANNELTYPE

La structure Tcl_ChannelType définit le comportement d'un type de canal. Elle contient des pointeurs vers des fonctions qui implémentent les différentes opérations sur les canaux, telles que la lecture, l'écriture, la fermeture, etc.

Lorsqu'un nouveau type de canal est implémenté, sa structure Tcl_ChannelType doit être enregistrée auprès de Tcl en utilisant Tcl_CreateChannelType. Cette fonction prend un pointeur vers l'interpréteur et un pointeur vers la structure Tcl_ChannelType comme arguments.

TCL_BADCHANNELOPTION

La constante TCL_BADCHANNELOPTION est une valeur spéciale qui peut être retournée par certaines fonctions de gestion de canaux Tcl pour indiquer une option invalide. Par exemple, si une commande tente de définir une option sur un canal qui n'est pas supportée par ce type de canal, TCL_BADCHANNELOPTION pourrait être retournée.

OLD CHANNEL TYPES

Les anciens types de canaux ne sont plus recommandés. Il est préférable d'utiliser les nouveaux types de canaux, qui offrent plus de flexibilité et de fonctionnalités. Cependant, pour des raisons de compatibilité descendante, Tcl prend toujours en charge les anciens types de canaux. Il est possible de migrer les anciens types de canaux vers les nouveaux en implémentant les fonctions appropriées.
