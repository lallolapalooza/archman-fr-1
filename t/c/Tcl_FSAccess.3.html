DESCRIPTION

Hay varias razones por las que las funciones de API de Tcl_FS (por ejemplo, Tcl_FSAccess y Tcl_FSStat) se llaman en lugar de llamar directamente a funciones del sistema como access y stat. Primero, estas funcionarán de forma multiplataforma, por lo que una extensión que llame a estas funciones debería funcionar sin modificaciones tanto en Unix como en Windows. Segundo, la implementación de algunas de estas funciones en Windows corrige algunos fallos en las llamadas al sistema. Tercero, estas llamadas manejan cualquier conversión de ruta de tipo "Utf a plataforma nativa" que pueda ser necesaria (y pueden almacenar en caché los resultados de estas conversiones para una mayor eficiencia en llamadas posteriores). Cuarto, y quizás lo más importante, todas estas funciones son "conscientes del sistema virtual". Cualquier sistema virtual (VFS, por sus siglas en inglés) registrado (a través de Tcl_FSRegister) puede redirigir el acceso a archivos a medios o métodos alternativos. Esto significa que todas estas funciones (y, por lo tanto, los comandos file, glob, pwd, cd, open, etc. de Tcl correspondientes) pueden operar sobre archivos que no son archivos nativos en el sistema de archivos nativo. Esto también significa que cualquier extensión Tcl que acceda al sistema de archivos (FS, por sus siglas en inglés) a través de esta API será automáticamente "consciente del sistema virtual". Claramente, si una extensión accede directamente al sistema de archivos nativo (a través de APIs específicas de plataforma), entonces Tcl no puede interceptar tales llamadas.

Si se han registrado adecuadamente los sistemas VFS, los archivos pueden, por ejemplo, ser remotos (como si estuvieran en un servidor FTP remoto) o archivados (como si estuvieran dentro de un archivo .zip). Estos sistemas registrados proporcionan un mapa de funciones para implementar parte o toda la funcionalidad mencionada aquí. Finalmente, las llamadas Tcl_FSStat y Tcl_FSLstat abstraen lo que realmente se declara como struct stat en el búfer, lo que permite que el mismo código se utilice tanto en sistemas con como sin soporte para archivos de más de 2 GB.

La API Tcl_FS está basada en Tcl_Obj y puede almacenar en caché representaciones internas y otras cadenas relacionadas con rutas (por ejemplo, el directorio actual). Un efecto secundario de esto es que no se deben pasar a estas funciones valores con un contador de referencias cero. Si se hubieran manejado tales llamadas, podrían causar fugas de memoria (en ciertos casos, el código del sistema de archivos podría descartar una referencia al valor pasado, y por lo tanto se debe asumir que después de cualquiera de estas llamadas, el valor aún no tiene un contador de referencias cero - podría haber sido incrementado). O bien, podría causar un fallo de segmentación (u otro error de acceso a memoria) debido a que el valor se ha liberado durante la manipulación compleja de valores que garantiza que la ruta esté normalizada y sea absoluta para el sistema de archivos. La lección práctica a aprender es que:

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

es malo y podría causar errores de memoria. El path debe incrementar su contador de referencias antes de pasarlo, o disminuirlo. Por esta razón, los valores con un contador de referencias cero se consideran no válidos como rutas del sistema de archivos y cualquier llamada a una función de API de Tcl_FS con tal valor no realizará ninguna acción.

FUNCIONES DE LA API Tcl_FS

Tcl_FSCopyFile intenta copiar el archivo dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas están en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función de copia del sistema de archivos. De lo contrario, la función devuelve -1 y establece el valor global de errno en C a los códigos de error EXDEV (que significa enlace cruzado).

Tcl_FSCopyDirectory intenta copiar el directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas están en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función de copia del sistema de archivos. De lo contrario, la función devuelve -1 y establece el valor global de errno en C a los códigos de error EXDEV (que significa enlace cruzado).

Tcl_FSCreateDirectory intenta crear el directorio dado por pathPtr llamando a la función de creación del sistema de archivos que lo posee.

Tcl_FSDeleteFile intenta eliminar el archivo dado por pathPtr llamando a la función de eliminación del sistema de archivos.

Tcl_FSRemoveDirectory intenta eliminar el directorio dado por pathPtr llamando a la función de eliminación del sistema de archivos.

Tcl_FSRenameFile intenta renombrar el archivo o directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas están en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función de renombrado del sistema de archivos. De lo contrario, la función devuelve -1 y establece el valor global de errno en C a los códigos de error EXDEV (que significa enlace cruzado).

Tcl_FSListVolumes llama a cada sistema de archivos que tenga una función list volumes no NULL y les pide que devuelvan su lista de volúmenes raíz. Acumula los valores devueltos en una lista que se devuelve al llamador (con un contador de referencias de 0).

Tcl_FSEvalFileEx lee el archivo dado por pathPtr usando la codificación identificada por encodingName y evalúa su contenido como un script Tcl. Devuelve la misma información que Tcl_EvalObjEx. Si encodingName es NULL, se usa la codificación del sistema para leer el contenido del archivo. Si el archivo no se puede leer, se devuelve un error Tcl que describe por qué no se puede leer el archivo. El carácter EOF para los archivos es \x1A ( ^Z ) para todos los sistemas. Si deseas usar \x1A en código para comparaciones de cadenas, puedes hacerlo, ya que se sustituirá por \x1A en el intérprete Tcl. Tcl_FSEvalFile es una versión más simple de Tcl_FSEvalFileEx que siempre usa la codificación del sistema al leer el archivo.

Tcl_FSLoadFile carga dinámicamente un archivo binario en memoria y devuelve las direcciones de dos procedimientos dentro de ese archivo, si están definidos. Se llama a la función adecuada para el sistema de archivos al que pertenece pathPtr. Si ese sistema de archivos no implementa esta función (la mayoría de los sistemas virtuales no lo harán, debido a las limitaciones de carga de código en el sistema operativo), Tcl intentará copiar el archivo a un directorio temporal y cargar ese archivo temporal. Tcl_FSUnloadFile revierte esta operación, pidiendo que se elimine de la memoria el cargador indicado por loadHandle. Nota que, a diferencia del comando unload, esto no da al cargador ninguna oportunidad de limpieza.

Ambas funciones anteriores devuelven un código de finalización estándar de Tcl. Si ocurre un error, se deja un mensaje de error en el resultado del interp.

El token proporcionado por la variable indicada por loadHandlePtr puede usarse con Tcl_FindSymbol.

Tcl_FSMatchInDirectory es utilizada por el código de globbing para encontrar todos los archivos que coincidan con un patrón dado en un directorio. Se llama a la función adecuada para el sistema de archivos al que pertenece pathPtr.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error durante el globbing. Los mensajes de error se colocan en el interp (a menos que interp sea NULL, lo cual está permitido), pero los resultados exitosos se colocan en el resultPtr dado.

Nota: el código de glob implementa internamente patrones recursivos, por lo que esta función solo será llamada con patrones simples, que pueden coincidir utilizando la lógica de string match. Para manejar la recursión, Tcl llamará a esta función frecuentemente pidiendo solo directorios para devolver. Un caso especial de llamada con un patrón nulo indica que la ruta solo debe ser verificada para el tipo correcto.

Tcl_FSLink reemplaza la versión de la biblioteca de readlink y la extiende para soportar la creación de enlaces. Se llama a la función adecuada para el sistema de archivos al que pertenece linkNamePtr.

Si toPtr es NULL, se realiza una acción de "leer enlace". El resultado es un objeto Tcl que especifica el contenido del enlace dado por linkNamePtr, o NULL si el enlace no pudo ser leído. El resultado es propiedad del llamador, que debe llamar a Tcl_DecrRefCount cuando el resultado ya no sea necesario. Si toPtr no es NULL, Tcl debería crear un enlace de uno de los tipos pasados en linkAction. Este flag es una combinación OR de TCL_CREATE_SYMBOLIC_LINK y TCL_CREATE_HARD_LINK. Cuando existe una elección (es decir, se pasan más de un flag), la convención de Tcl es preferir enlaces simbólicos. Cuando se crea un enlace correctamente, el valor devuelto debería ser toPtr (que ya es propiedad del llamador). Si falla, se devuelve NULL.

Conservez toute la structure du fichier. Si le fichier *path* existe, *Tcl_FSLstat* renvoie 0 et la structure *Tcl_StatBuf* est remplie de données. Sinon, -1 est renvoyé et aucune donnée statistique n'est fournie. *Tcl_FSUtime* remplace la version de la bibliothèque de la fonction *utime*. Cette fonction renvoie 0 en cas de succès et -1 en cas d'erreur (comme dans la documentation de *utime*). En cas de succès, la fonction mettra à jour les valeurs *atime* et *mtime* du fichier donné. *Tcl_FSFileAttrsGet* implémente l'accès aux attributs de la sous-commande *file* de *Tcl_FileAttrs*. La fonction appropriée pour le système de fichiers auquel appartient *pathPtr* est appelée. Si le résultat est *TCL_OK*, une valeur est placée dans *objPtrRef*, qui ne sera valable que temporairement (sauf si *Tcl_IncrRefCount* est appelé). *Tcl_FSFileAttrsSet* implémente l'accès en écriture pour la sous-commande *file* de *Tcl_FileAttrs*. La fonction appropriée pour le système de fichiers auquel appartient *pathPtr* est appelée. *Tcl_FSFileAttrStrings* implémente une partie de la sous-commande *file* de *Tcl_FileAttrs*. La fonction appropriée pour le système de fichiers auquel appartient *pathPtr* est appelée. La procédure appelée peut renvoyer une liste de chaînes, ou elle peut renvoyer NULL et placer une liste Tcl dans *objPtrRef*. Tcl incrémentera sa référence avant de l'utiliser. Une fois son utilisation terminée, elle diminuera sa référence. Par conséquent, si la liste doit être libérée par Tcl, elle doit avoir un compteur de référence de zéro, et si elle ne doit pas être libérée, le système de fichiers doit garantir qu'il conserve la référence. *Tcl_FSAccess* vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou de l'objet du système de fichiers) dont le nom est *pathname*. Si *pathname* est un lien symbolique sous Unix, les permissions du fichier auquel ce lien symbolique fait référence sont testées. En cas de succès (toutes les permissions demandées), 0 est renvoyé. En cas d'erreur (au moins un bit dans le mode demandé est refusé ou une autre erreur se produit), -1 est renvoyé. *Tcl_FSStat* remplit la structure *Tcl_StatBuf* avec des informations sur le fichier spécifié. Aucun accès au fichier n'est nécessaire pour obtenir ces informations, mais le droit de parcourir tous les répertoires mentionnés dans le chemin du fichier est nécessaire. La structure *Tcl_StatBuf* inclut des informations sur le périphérique, l'inode (0 sous Windows), le mode de privilège, le nlink (1 sous Windows), l'UID (0 sous Windows), le GID (0 sous Windows), le rdev (identique au périphérique sous Windows), la taille, le temps d'accès, le temps de modification et le temps de changement des métadonnées. Voir **PORTABLE STAT RESULT API** pour une description de la manière d'écrire du code portable pour attribuer et accéder à la structure *Tcl_StatBuf*. Si le fichier *path* existe, *Tcl_FSStat* renvoie 0 et la structure *Tcl_StatBuf* est remplie de données. Sinon, -1 est renvoyé et aucune donnée statistique n'est fournie. *Tcl_FSOpenFileChannel* ouvre un fichier spécifié par *pathPtr* et renvoie un descripteur de canal qui peut être utilisé pour effectuer des entrées et sorties sur le fichier. Cette API est calquée sur la fonction *fopen* de la bibliothèque d'entrée/sortie standard Unix. La syntaxe et la signification des arguments sont similaires à celles données dans les commandes *open* de Tcl lors de l'ouverture d'un fichier. Si une erreur se produit lors de l'ouverture du canal, *Tcl_FSOpenFileChannel* renvoie NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec *Tcl_GetErrno*. De plus, si *interp* n'est pas NULL, *Tcl_FSOpenFileChannel* laisse un message d'erreur dans le résultat de *interp* après toute erreur. Le canal créé est enregistré dans l'interpréteur fourni ; pour l'enregistrer, utilisez *Tcl_RegisterChannel*. Si l'un des canaux standard, tel que *stdin*, *stdout* ou *stderr*, a été précédemment fermé, l'acte de création du nouveau canal l'assigne également comme substitut du canal standard correspondant. *Tcl_FSGetCwd* remplace la version de la bibliothèque de la fonction *getcwd*. Renvoie le répertoire de travail de la bibliothèque Tcl. Cela peut être différent du répertoire de travail natif, ce qui se produit lorsque le répertoire de travail actuel n'est pas dans le système de fichiers natif. Le résultat est un pointeur vers un objet Tcl (*Tcl_Obj*) spécifiant le répertoire actuel, ou NULL s'il ne peut pas être déterminé. Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de *interp*. Le résultat a déjà son compteur de références incrémenté pour l'appelant. Lorsqu'il n'est plus nécessaire, ce compteur de références doit être décrémenté. Ceci est nécessaire pour la sécurité des threads, afin que plusieurs threads puissent accéder à cette fonction et à des fonctions connexes, en s'assurant toujours que les résultats sont valides. *Tcl_FSChdir* remplace la version de la bibliothèque de la fonction *chdir*. Le chemin est normalisé et passé au système de fichiers qui le revendique. Si ce système de fichiers n'implémente pas cette fonction, Tcl se rabat sur une combinaison de *stat* et *access* pour vérifier si le répertoire existe et a les permissions appropriées. Pour les résultats, voir la documentation de *chdir*. En cas de succès, le chemin réussi est enregistré dans *cwdPathPtr* pour les appels ultérieurs à *Tcl_FSGetCwd*. *Tcl_FSPathSeparator* renvoie le caractère séparateur pour l'élément le plus spécifique du chemin spécifié par *pathPtr* (c'est-à-dire la dernière partie du chemin). Le séparateur est renvoyé sous la forme d'un objet Tcl (*Tcl_Obj*) avec une chaîne de longueur 1. Si le chemin est invalide, NULL est renvoyé. *Tcl_FSJoinPath* prend l'objet Tcl donné, qui doit être une liste valide (permettant d'avoir un compteur de références de zéro), et renvoie la valeur du chemin en considérant les *elements* premiers éléments comme des segments de chemin valides (chaque segment peut être un chemin complet, un chemin partiel ou juste un nom de répertoire ou de fichier). Si un segment est réellement un chemin absolu, tous les segments précédents sont ignorés. Si *elements* est inférieur à 0, la liste entière est utilisée. Il est possible que la valeur renvoyée soit réellement un élément de la liste donnée, l'appelant doit donc incrémenter le compteur de références du résultat avant de libérer la liste. La valeur renvoyée, qui a généralement un compteur de références de zéro (mais pourrait être partagée dans certaines conditions), contient le chemin concaténé. L'appelant doit incrémenter le compteur de références avant de l'utiliser. En particulier, la valeur renvoyée pourrait être un élément de la liste donnée, donc la libération de la liste pourrait libérer la valeur prématurément si un compteur de références n'a pas été pris. Si le nombre d'éléments est zéro, la valeur renvoyée sera une chaîne vide (*Tcl_Obj*) avec une valeur de chaîne. *Tcl_FSSplitPath* prend l'objet Tcl donné, qui doit être un chemin valide, et renvoie une valeur de liste avec chaque segment de ce chemin comme élément. La valeur renvoyée a un compteur de références de zéro. Si le *lenPtr* passé n'est pas NULL, la variable pointée est mise à jour pour contenir le nombre d'éléments dans la valeur renvoyée. *Tcl_FSEqualPaths* teste si deux chemins donnés représentent le même objet du système de fichiers. Renvoie 1 si les chemins sont égaux, 0 s'ils sont différents. Si l'un des chemins est NULL, 0 est toujours renvoyé. *Tcl_FSGetNormalizedPath* tente d'extraire une représentation normalisée unique du chemin donné, dont la valeur de chaîne peut être utilisée comme identifiant unique du fichier. Renvoie le chemin normalisé, détenu par Tcl, ou NULL si le chemin était invalide ou n'a pas pu être converti correctement. L'extraction de chemins absolus et normalisés est très efficace (car le système de fichiers opère en interne sur ces représentations), bien que le résultat lorsque le système de fichiers contient de nombreux liens symboliques ne soit pas nécessairement la version la plus conviviale d'un chemin. La valeur renvoyée est détenue par Tcl et a une durée de vie équivalente à celle de *pathPtr* passé (sauf s'il s'agit d'un chemin relatif, auquel cas la valeur normalisée peut être libérée chaque fois que le cwd change) - l'appelant peut incrémenter le compteur de références s'il le souhaite pour conserver une copie plus longtemps. *Tcl_FSJoinToPath* prend la valeur donnée, qui devrait être un chemin valide ou NULL, et joint les chemins de segments donnés. Renvoie une valeur, typiquement avec un compteur de références de zéro (mais pourrait être partagée dans certaines conditions), avec le chemin concaténé. L'appelant doit incrémenter le compteur de références de la valeur avant de l'utiliser. Si l'une des valeurs passées à cette fonction (*pathPtr* ou éléments de *path*) a un compteur de références de zéro, elles seront libérées lorsque cette fonction renverra. *Tcl_FSConvertToPathType* tente de convertir l'objet Tcl donné en un type de chemin Tcl valide, en considérant que le cwd pourrait avoir changé même si cette valeur semble déjà être du bon type. Le nom du fichier peut commencer par *~* (pour indiquer le répertoire utilisateur actuel) ou *~* (pour indiquer le répertoire de n'importe quel utilisateur). Si la conversion réussit (c'est-à-dire que la valeur est un chemin valide dans l'un des systèmes de fichiers actuels), *TCL_OK* est renvoyé. Sinon, *TCL_ERROR* est renvoyé, et il peut y avoir un message d'erreur dans l'interpréteur. *Tcl_FSGetInternalRep* extrait la représentation interne d'une valeur de chemin donnée, dans le système de fichiers donné. Si la valeur de chemin appartient à un système de fichiers différent, NULL est renvoyé. Si la représentation interne est actuellement NULL, on tente de la générer en appelant la fonction *Tcl_FSCreateInternalRepProc* du système de fichiers. Renvoie NULL ou une représentation valide de la représentation interne du chemin. Cette représentation interne est mise en cache, donc les appels répétés à cette fonction ne nécessitent pas de conversions supplémentaires. *Tcl_FSGetTranslatedPath* tente d'extraire un chemin traduit de l'objet Tcl donné. Si la traduction réussit (c'est-à-dire que la valeur est un chemin valide), la valeur est renvoyée. Sinon, NULL est renvoyé et il peut y avoir un message d'erreur dans l'interpréteur. Un chemin traduit ne contient aucune séquence de *~* (celles-ci ont été développées en leur représentation actuelle dans le système de fichiers). La valeur renvoyée est détenue par l'appelant, qui doit la stocker ou appeler *Tcl_DecrRefCount* pour s'assurer que la mémoire est libérée. Cette fonction a peu d'utilité pratique, et *Tcl_FSGetNormalizedPath* ou *Tcl_FSGetNativePath* sont des fonctions plus appropriées pour de nombreuses utilisations. *Tcl_FSGetTranslatedStringPath* fait la même chose que *Tcl_FSGetTranslatedPath*, mais renvoie une chaîne ou NULL. La chaîne renvoyée est allouée dynamiquement et doit être libérée avec *Tcl_DecrRefCount*. Cette fonction a peu d'utilité pratique, et *Tcl_FSGetNormalizedPath* ou *Tcl_FSGetNativePath* sont des fonctions plus appropriées pour de nombreuses utilisations. wned par l'appelant, qui doit le stocker ou appeler ckfree pour s'assurer qu'il est libéré. Encore une fois, Tcl_FSGetNormalizedPath ou Tcl_FSGetNativePath sont généralement de meilleures fonctions à utiliser pour la plupart des usages.

Tcl_FSNewNativePath effectue quelque chose comme l'inverse des conversions habituelles obj->chemin->représentation native. Si un code récupère un chemin sous forme native (depuis, par exemple, readlink ou une boîte de dialogue native), et que ce chemin doit être utilisé au niveau Tcl, alors appeler cette fonction est un moyen efficace de créer le type de valeur de chemin approprié.

La valeur résultante est une valeur "chemin" pure, qui ne recevra une représentation sous forme de chaîne UTF-8 que si cela est requis par un code Tcl.

Tcl_FSGetNativePath est destiné à être utilisé par les systèmes de fichiers natifs Win/Unix, afin qu'ils puissent facilement récupérer la représentation native (char* ou TCHAR*) d'un chemin. Cette fonction est un wrapper pratique autour de Tcl_FSGetInternalRep. Il pourrait être souhaitable à l'avenir d'avoir des représentations natives non basées sur des chaînes (par exemple, sur macOS, une représentation utilisant une structure fileSpec de FSRef serait probablement plus efficace). Sous Windows, une représentation Unicode complète permettrait des chemins de longueur illimitée. Actuellement, la représentation est simplement une chaîne de caractères qui peut contenir soit le chemin relatif, soit un chemin absolu normalisé complet dans le codage natif (des conditions complexes dictent lequel de ces éléments sera fourni, donc aucun ne peut être garanti, à moins que le chemin ne soit connu pour être absolu). Si vous avez besoin d'un chemin natif qui doit être absolu, vous devriez demander la version native d'un chemin normalisé. Si, pour une raison quelconque, une version non absolue et non normalisée du chemin est nécessaire, elle doit être construite séparément (par exemple, en utilisant Tcl_FSGetTranslatedPath).

La représentation native est mise en cache de sorte que les appels répétés à cette fonction n'entraînent pas de conversions supplémentaires. La valeur de retour appartient à Tcl et a une durée de vie équivalente à celle du pathPtr passé (sauf si c'est un chemin relatif, auquel cas la représentation native peut être libérée à tout moment lorsque le cwd change).

Tcl_FSFileSystemInfo renvoie une liste de deux éléments. Le premier élément est le nom du système de fichiers (par exemple, "natif", "vfs", "zip", ou "prowrap", peut-être), et le second est le type particulier du chemin donné dans ce système de fichiers (qui dépend du système de fichiers). Le second élément peut être vide si le système de fichiers ne fournit pas de catégorisation supplémentaire des fichiers.

Une valeur de liste valide est renvoyée, à moins que la valeur du chemin ne soit pas reconnue, auquel cas NULL sera renvoyé.

Tcl_FSGetFileSystemForPath renvoie un pointeur vers le Tcl_Filesystem qui accepte ce chemin comme valide.

Si aucun système de fichiers n'accepte le chemin, NULL est renvoyé.

API DES SYSTÈMES DE FICHIERS VIRTUELS

Un système de fichiers fournit une structure Tcl_Filesystem qui contient des pointeurs vers des fonctions implémentant les diverses opérations sur un système de fichiers ; ces opérations sont invoquées selon les besoins par la couche générique, ce qui se produit généralement via les fonctions listées ci-dessus.

Les structures Tcl_Filesystem sont manipulées à l'aide des méthodes suivantes.

Tcl_FSRegister prend un pointeur vers une structure de système de fichiers et un élément de données facultatif à associer à ce système de fichiers. Lors de l'appel de cette fonction, Tcl attache le système de fichiers à la liste des systèmes de fichiers connus, et il devient pleinement fonctionnel immédiatement. Tcl ne vérifie pas si le même système de fichiers est enregistré plusieurs fois (et en général, ce n'est pas une bonne chose à faire). TCL_OK sera renvoyé.

Tcl_FSUnregister supprime la structure de système de fichiers donnée de la liste des systèmes de fichiers connus, si elle est connue, et renvoie TCL_OK. Si le système de fichiers n'est pas actuellement enregistré, TCL_ERROR est renvoyé.

Tcl_FSData renvoie le clientData associé au système de fichiers donné, si ce système de fichiers est enregistré. Sinon, il renvoie NULL.

Tcl_FSMountsChanged est utilisé pour informer le noyau de Tcl que l'ensemble des points de montage pour le système de fichiers donné (déjà enregistré) a changé, et que les représentations de fichiers mises en cache peuvent donc ne plus être correctes.

À l'exception des trois premiers champs de cette structure qui contiennent des éléments de données simples, toutes les entrées contiennent des adresses de fonctions appelées par la couche générique du système de fichiers pour effectuer la gamme complète d'actions liées au système de fichiers.

Les nombreuses fonctions de cette structure sont réparties en trois catégories : fonctions d'infrastructure (dont presque toutes doivent être implémentées), fonctions opérationnelles (qui doivent être implémentées si un système de fichiers complet est fourni), et fonctions d'efficacité (qui n'ont besoin d'être implémentées que si elles peuvent être réalisées efficacement, ou si elles ont des effets secondaires requis par le système de fichiers ; Tcl dispose d'émulations moins efficaces sur lesquelles il peut se rabattre). Il est important de noter que, dans la version actuelle de Tcl, la plupart de ces solutions de repli ne sont utilisées que pour gérer les commandes initiées dans Tcl, pas dans C. Cela signifie que si une commande file rename est émise dans Tcl, et que les systèmes de fichiers pertinents n'implémentent pas leur Tcl_FSRenameFileProc, le noyau de Tcl se rabattra sur une combinaison d'autres fonctions de système de fichiers (il utilisera Tcl_FSCopyFileProc suivi de Tcl_FSDeleteFileProc, et si Tcl_FSCopyFileProc n'est pas implémenté, il y a un autre repli). Cependant, si une commande Tcl_FSRenameFileProc est émise au niveau C, aucun de ces replis ne se produit. Ceci est vrai à l'exception des quatre dernières entrées de la table des systèmes de fichiers (lstat, load, getcwd et chdir) pour lesquelles des replis se produisent en fait au niveau C.

Toutes les fonctions qui prennent des noms de chemin sous forme Tcl_Obj prennent ces noms sous forme UTF-8. L'API de l'infrastructure des systèmes de fichiers est conçue pour prendre en charge la conversion efficace et mise en cache de ces chemins UTF-8 vers d'autres représentations natives.

PROCÉDURE DE CHEMIN DANS SYSTÈME DE FICHIERS

Le champ procédure de chemin dans système de fichiers contient l'adresse d'une fonction qui est appelée pour déterminer si un chemin donné appartient à ce système de fichiers ou non. Si TCL_OK est retourné, le paramètre de sortie facultatif clientDataPtr peut être utilisé pour retourner une représentation interne (spécifique au système de fichiers) du chemin, qui sera stockée dans la valeur du chemin et pourra être récupérée efficacement par d'autres fonctions de système de fichiers de Tcl. Tcl stockera simultanément l'information que ce chemin appartient à ce système de fichiers. Ces caches sont invalidées lorsque des systèmes de fichiers sont ajoutés ou retirés de la liste interne des systèmes de fichiers connus de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

PROCÉDURE DE NORMALISATION DE CHEMIN

Fonction pour normaliser un chemin. Doit être implémentée pour tous les systèmes de fichiers qui peuvent avoir plusieurs représentations string pour le même chemin. Dans Tcl, chaque chemin doit avoir une unique représentation normalisée. Selon le système de fichiers, il peut y avoir plus d'une représentation string non normalisée pointant vers le même chemin (par exemple, un chemin relatif, un chemin avec une casse différente si le système de fichiers est insensible à la casse, un chemin contenant une référence au répertoire utilisateur comme ~, un chemin contenant des liens symboliques, etc.). Si le dernier composant du chemin est un lien symbolique, il ne doit pas être résolu en la valeur vers laquelle il pointe (mais sa casse ou d'autres aspects doivent être uniques). Tous les autres composants du chemin doivent être résolus à partir des liens symboliques. Cette exception est nécessaire pour correspondre aux significations de Tcl pour la commande file, delete, rename, copy avec des liens symboliques. Cette fonction peut être appelée avec nextCheckpoint au début du chemin (c'est-à-dire zéro), à la fin du chemin, ou à n'importe quel point séparateur de fichier intermédiaire. Aucun autre point arbitraire du chemin ne sera sollicité. Dans le dernier des trois cas valides, l'implémentation peut supposer que le chemin jusqu'au séparateur de fichier inclus est connu et normalisé.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPÉRATIONS SYSTÈME DE FICHIERS

Les champs de cette section de la structure contiennent les adresses des fonctions qui sont appelées pour effectuer les opérations de base du système de fichiers. Un système de fichiers qui est censé être utilisé avec l'ensemble complet des commandes standard Tcl doit implémenter toutes ces opérations. Si certaines d'entre elles ne sont pas implémentées, certaines commandes Tcl peuvent échouer lors de l'opération sur des chemins dans ce système de fichiers. Cependant, dans certains cas, cela peut être souhaitable (par exemple, un système de fichiers en lecture seule ne devrait pas implémenter les quatre dernières fonctions, et un système de fichiers qui ne prend pas en charge les liens symboliques ne devrait pas implémenter la fonction readlink, etc. Le noyau Tcl s'attend à ce que les systèmes de fichiers se comportent ainsi).

Le type est uniquement utilisé à des fins d'information et doit être retourné comme représentation string de l'objet Tcl retourné. Une valeur de retour typique pourrait être networked, zip ou ftp. Le résultat de Tcl appartient au système de fichiers et Tcl incrémentera donc le compteur de références de la valeur s'il souhaite la conserver.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

Fonction pour retourner le caractère séparateur pour ce système de fichiers. Ceci n'est nécessaire que si le système de fichiers souhaite utiliser un séparateur différent de la chaîne standard /. Entre autres utilisations, il est retourné par la commande file separator. La valeur retournée doit avoir un compteur de références de zéro.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

PROCÉDURE STAT

Fonction pour traiter un appel Tcl_FSStat. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent crucialement (par exemple, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La fonction Tcl_FSStatProc remplit la structure statPtr avec des informations sur le fichier spécifié. Aucun droit de lecture, d'écriture ou de test d'existence du fichier (ou autre objet du système de fichiers) dont le nom est dans pathPtr n'est nécessaire. Cependant, les droits de parcours sont nécessaires dans tous les répertoires mentionnés dans le chemin menant au fichier. La structure stat comprend des informations sur le périphérique, l'inœud (toujours 0 sous Windows), le mode des privilèges, le nombre de liens (toujours 1 sous Windows), l'ID utilisateur (toujours 0 sous Windows), l'ID groupe (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, l'heure du dernier accès, l'heure de la dernière modification et l'heure du dernier changement de métadonnées.

Si le fichier représenté par pathPtr existe, le Tcl_FSStatProc retourne 0 et la structure stat est remplie de données. Sinon, il retourne -1 et aucune information de stat n'est fournie.

PROCÉDURE D'ACCÈS

Fonction pour traiter un appel Tcl_FSAccess. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent crucialement (par exemple, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La fonction Tcl_FSAccessProc vérifie si le processus serait autorisé à lire, écrire ou tester l'existence du fichier (ou autre objet du système de fichiers) dont le nom est dans pathPtr. Si le nom du chemin fait référence à un lien symbolique, les permissions du fichier auquel ce lien symbolique fait référence doivent être vérifiées.

En cas de succès (toutes les permissions demandées sont accordées), 0 est retourné. En cas d'erreur (au moins un bit dans mode demande une permission refusée, ou une autre erreur se produit), -1 est retourné.

PROCÉDURE D'OUVERTURE DE CANAL DE FICHIER

Fonction pour traiter un appel Tcl_FSOpenFileChannel. Doit être implémentée pour tout système de fichiers raisonnable, car de nombreuses commandes de niveau Tcl en dépendent crucialement (par exemple, file open, file close, file read, file write, file exists).

FILECHANNELPROC

Fonction pour traiter un appel Tcl_FSOpenFileChannel. Doit être implémentée pour tout système de fichiers raisonnable, car toutes les opérations qui nécessitent d'ouvrir ou d'accéder au contenu d'un fichier l'utiliseront (par exemple, open, encoding, et de nombreuses commandes Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

Le Tcl_FSOpenFileChannelProc ouvre un fichier spécifié par pathPtr et retourne un handle de canal qui peut être utilisé pour effectuer des entrées et des sorties sur le fichier. Cette API est basée sur la procédure fopen de la bibliothèque d'E/S standard Unix. La syntaxe et la signification de tous les arguments sont similaires à celles données dans la commande Tcl open lors de l'ouverture d'un fichier, où l'argument mode est une combinaison des indicateurs POSIX O_RDONLY, O_WRONLY, etc. Si une erreur se produit lors de l'ouverture du canal, le Tcl_FSOpenFileChannelProc retourne NULL et enregistre un code d'erreur POSIX qui peut être récupéré avec Tcl_GetErrno. De plus, si interp n'est pas NULL, le Tcl_FSOpenFileChannelProc laisse un message d'erreur dans le résultat de interp après toute erreur.

Le nouveau canal créé ne doit pas être enregistré dans l'interpréteur fourni par un Tcl_FSOpenFileChannelProc ; cette tâche incombe à l'appelant de Tcl_FSOpenFileChannel (si nécessaire). Si l'un des canaux standard, stdin, stdout ou stderr a été précédemment fermé, l'acte de créer le nouveau canal lui assigne également en tant que remplacement du canal standard.

MATCHINDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSMatchInDirectory. Si elle n'est pas implémentée, alors la fonctionnalité glob et copie récursive manquera dans le système de fichiers (et cela peut avoir un impact sur les commandes comme encoding names qui utilisent la fonctionnalité glob en interne).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La fonction doit retourner tous les fichiers ou répertoires (ou autres objets du système de fichiers) qui correspondent au modèle donné et sont conformes à la spécification des types donnée. Il y a deux façons dont cette fonction peut être appelée. Si pattern est NULL, alors pathPtr est une spécification de chemin complet d'un seul fichier ou répertoire qui doit être vérifié pour son existence et son type correct. Sinon, pathPtr est un répertoire, dont le contenu la fonction doit rechercher des fichiers ou répertoires ayant le type correct. Dans les deux cas, on peut supposer que pathPtr n'est ni NULL ni vide. Il n'est pas actuellement documenté si pathPtr aura ou non un séparateur de fichier à sa fin, donc le code doit être flexible aux deux possibilités.

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite dans le processus de correspondance. Les messages d'erreur sont placés dans interp, sauf si interp est NULL auquel cas aucun message d'erreur n'a besoin d'être généré ; en cas de résultat TCL_OK, les résultats doivent être ajoutés à la valeur de resultPtr donnée (qui peut être supposée être une liste Tcl valide et non partagée). Les correspondances ajoutées à resultPtr doivent inclure tout préfixe de chemin donné dans pathPtr (cela signifie généralement qu'il s'agira de spécifications de chemin absolu). Notez que si aucune correspondance n'est trouvée, cela conduit simplement à un résultat vide ; les erreurs ne sont signalées que pour les problèmes de fichier ou de système de fichiers réels qui peuvent survenir pendant le processus de correspondance.

La structure Tcl_GlobTypeData passée dans le paramètre types contient les champs suivants :

typedef struct Tcl_GlobTypeData {
    /* Correspond à bcdpfls comme dans 'find -t' */
    int type;
    /* Correspond aux permissions de fichier */
    int perm;
    /* Type Mac acceptable */
    Tcl_Obj *macType;
    /* Créateur Mac acceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Il y a deux cas spécifiques qui sont importants à gérer correctement, tous deux lorsque types n'est pas NULL. Les deux cas sont lorsque types->types & TCL_GLOB_TYPE_DIR ou types->types & TCL_GLOB_TYPE_MOUNT sont vrais (et en particulier lorsque les autres indicateurs sont faux). Dans le premier de ces cas, la fonction doit lister les répertoires contenus. Tcl utilise cela pour implémenter le globbing récursif, il est donc essentiel que les systèmes de fichiers implémentent correctement la correspondance de répertoire. Dans le second de ces cas, avec TCL_GLOB_TYPE_MOUNT, le système de fichiers doit lister les points de montage qui se trouvent dans le pathPtr donné (et dans ce cas, pathPtr n'a pas besoin de se trouver dans le même système de fichiers - différent de tous les autres cas où cette fonction est appelée). Le support pour cela est critique si Tcl doit avoir des transitions transparentes entre un système de fichiers et un autre.

UTIMEPROC

Fonction pour traiter un appel Tcl_FSUtime. Nécessaire pour permettre la définition (pas la lecture) des temps avec file mtime, file atime et l'implémentation open-r/open-w/fcopy de file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Les temps d'accès et de modification du fichier spécifié par pathPtr doivent être modifiés pour correspondre aux valeurs données dans la structure tval.

La valeur de retour doit être 0 en cas de succès et -1 en cas d'erreur, comme avec la fonction système utime.

LINKPROC

Fonction pour traiter un appel Tcl_FSLink. Doit être implémentée uniquement si le système de fichiers prend en charge les liens, et peut sinon être NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr est NULL, la fonction est invitée à lire le contenu d'un lien. Le résultat est un Tcl_Obj spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien n'a pas pu être lu. Le résultat est détenu par l'appelant (et doit donc voir son compteur de références incrémenté avant d'être retourné). Tous les appelants doivent appeler Tcl_DecrRefCount sur ce résultat lorsqu'il n'est plus nécessaire. Si toPtr n'est pas NULL, la fonction doit tenter de créer un lien. Le résultat dans ce cas doit être toPtr si le lien a réussi et NULL sinon. Dans ce cas, le résultat n'est pas détenu par l'appelant (c'est-à-dire qu'aucune manipulation de compteur de référence des deux côtés n'est nécessaire). Voir la documentation de Tcl_FSLink pour l'interprétation correcte des indicateurs linkAction.

LISTVOLUMESPROC

Fonction pour lister tous les volumes de système de fichiers ajoutés par ce système de fichiers. Doit être implémentée uniquement si le système de fichiers ajoute des volumes en tête du système de fichiers, afin qu'ils puissent être retournés par file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

Le résultat doit être une liste de volumes ajoutés par ce système de fichiers, ou NULL (ou une liste vide) si aucun volume n'est fourni. La valeur de résultat est considérée comme détenue par le système de fichiers (pas par le cœur de Tcl), mais doit se voir attribuer un compteur de références pour Tcl. Tcl utilisera le contenu de la liste, puis décrémentera ce compteur de références. Cela permet aux systèmes de fichiers de choisir s'ils souhaitent réellement conserver une liste « globale » de volumes ou non (sinon, ils génèrent la liste à la volée et la transmettent à Tcl avec un compteur de références de 1, puis oublient la liste ; sinon, ils incrémentent simplement le compteur de références de leur liste globale et la transmettent à Tcl qui copiera le contenu, puis décrémentera le compte pour revenir à sa valeur d'origine).

Par conséquent, Tcl considère que les valeurs de retour de ce proc sont en lecture seule.

FILEATTRSTRINGSPROC

Fonction pour lister toutes les chaînes d'attributs qui sont valides pour ce système de fichiers. Si elle n'est pas implémentée, le système de fichiers ne prendra pas en charge la commande file attributes. Cela permet de joindre des informations arbitraires supplémentaires aux fichiers du système de fichiers. Si elle n'est pas implémentée, il n'est pas nécessaire d'implémenter les méthodes get et set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La fonction appelée peut soit retourner un tableau de chaînes, soit retourner NULL et placer une liste Tcl dans objPtrRef. Tcl prendra cette liste et incrémentera d'abord son compteur de références avant de l'utiliser. Une fois cette utilisation terminée, Tcl décrémentera son compteur de références. Par conséquent, si la liste doit être supprimée par Tcl une fois terminée, elle doit avoir un compteur de références de zéro, et si la liste ne doit pas être supprimée, le système de fichiers doit s'assurer qu'il retourne une valeur avec un compteur de références d'au moins un.

FILEATTRSGETPROC

Fonction pour traiter un appel Tcl_FSFileAttrsGet, utilisé par file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Retourne un code de retour Tcl standard. La valeur d'attribut récupérée, qui correspond à l'élément d'indice index dans la liste retournée par Tcl_FSFileAttrStringsProc, est un Tcl_Obj placé dans objPtrRef (si TCL_OK a été retourné) et est susceptible d'avoir un compteur de références de zéro. Dans les deux cas, nous devons soit le stocker quelque part (par exemple, le résultat Tcl), soit incrémenter/décrémenter son compteur de références pour s'assurer qu'il est correctement libéré.

FILEATTRSSETPROC

Fonction pour traiter un appel Tcl_FSFileAttrsSet, utilisé par file attributes. Si le système de fichiers est en lecture seule, il n'est pas nécessaire de l'implémenter.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

La valeur d'attribut de l'élément d'indice index dans la liste retournée par le Tcl_FSFileAttrStringsProc doit être définie sur le objPtr donné.

EFFICACITÉ DU SYSTÈME DE FICHIERS

Ces fonctions n'ont pas besoin d'être implémentées pour un système de fichiers particulier car le cœur de Tcl dispose d'une implémentation de secours. Voir la description individuelle de chaque fonction pour connaître les conséquences de laisser le champ à NULL.

LSTATPROC

Fonction pour traiter un appel Tcl_FSLstat. Si elle n'est pas implémentée, Tcl tentera d'utiliser la statProc définie ci-dessus à la place. Par conséquent, elle n'a besoin d'être implémentée que si un système de fichiers peut différencier les appels stat et lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Le comportement de cette fonction est très similaire à celui de la Tcl_FSStatProc définie ci-dessus, sauf que si elle est appliquée à un lien symbolique, elle renvoie des informations sur le lien, et non sur le fichier cible.

COPYFILEPROC

Fonction pour traiter un appel Tcl_FSCopyFile. Si elle n'est pas implémentée, Tcl utilisera open en lecture, open en écriture et fcopy comme mécanisme de copie. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du processus de copie. Notez que destPathPtr est le nom du fichier qui deviendra la copie de srcPathPtr. Ce n'est jamais le nom d'un répertoire dans lequel srcPathPtr pourrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande file copy au niveau Tcl). Notez que, si le système de fichiers prend en charge les liens symboliques, Tcl appellera toujours cette fonction et non copyDirectoryProc lorsque cela est nécessaire pour les copier (même s'il s'agit de liens symboliques vers des répertoires). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file copy, l'appel de Tcl_SetErrno(EXDEV) et le renvoi d'un résultat non TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

RENAMEFILEPROC

Fonction pour traiter un appel Tcl_FSRenameFile. Si elle n'est pas implémentée, Tcl utilisera un mécanisme de copie et de suppression comme secours. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du processus de renommage. Si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action file rename, l'appel de Tcl_SetErrno(EXDEV) et le renvoi d'un résultat non TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

COPYDIRECTORYPROC

Fonction pour traiter un appel Tcl_FSCopyDirectory. Si elle n'est pas implémentée, Tcl utilisera un mécanisme récursif de file mkdir et file copy comme secours. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut effectuer cette action plus efficacement.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

La valeur de retour est un résultat Tcl standard indiquant si une erreur s'est produite lors du processus de copie. Si une erreur se produit, le nom du fichier ou du répertoire qui a causé l'erreur doit être placé dans errorPtr. Notez que destPathPtr est le nom du répertoire qui deviendra le reflet de srcPathPtr. Ce n'est pas le nom d'un répertoire dans lequel srcPathPtr devrait être copié (c'est-à-dire que la fonction est beaucoup plus simple que la sous-commande file copy au niveau Tcl). Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de copie de répertoire, l'appel de Tcl_SetErrno(EXDEV) et le renvoi d'un résultat non TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

LOADFILEPROC

Fonction pour traiter un appel Tcl_FSLoadFile. Si elle n'est pas implémentée, Tcl utilisera une copie vers un fichier temporaire natif, suivie d'un appel Tcl_FSLoadFile sur cette copie temporaire. Par conséquent, elle n'a besoin d'être implémentée que si le système de fichiers peut charger du code directement, ou si elle peut être implémentée simplement pour renvoyer TCL_ERROR afin de désactiver complètement la fonctionnalité de chargement dans ce système de fichiers.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Renvoie un code d'achèvement Tcl standard. Si une erreur se produit, un message d'erreur est laissé dans le résultat de l'interpréteur. La fonction charge dynamiquement un fichier de code binaire en mémoire. En cas de succès du chargement, handlePtr doit être rempli avec un jeton pour le fichier chargé dynamiquement, et unloadProcPtr doit être rempli avec l'adresse d'une procédure. La procédure de déchargement sera appelée avec le Tcl_LoadHandle donné comme seul paramètre lorsque Tcl aura besoin de décharger le fichier. Par exemple, pour le système de fichiers natif, le Tcl_LoadHandle renvoyé est actuellement un jeton qui peut être utilisé dans le TclpFindSymbol privé pour accéder aux fonctions du nouveau code. Chaque système de fichiers est libre de définir le Tcl_LoadHandle comme il le souhaite. Enfin, si le système de fichiers détermine qu'il ne peut pas prendre en charge l'action de chargement de fichier, l'appel de Tcl_SetErrno(EXDEV) et le renvoi d'un résultat non TCL_OK indiqueront à Tcl d'utiliser ses mécanismes de secours standard.

GETCWDPROC

Fonction pour traiter un appel Tcl_FSGetCwd. La plupart des systèmes de fichiers n'ont pas besoin de l'implémenter. Elle ne sera généralement appelée qu'une seule fois, si getcwd est appelé avant chdir. Peut être NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si le système de fichiers prend en charge une notion native de répertoire de travail courant (qui pourrait éventuellement changer indépendamment de Tcl), cette fonction doit renvoyer ce répertoire courant comme résultat, ou NULL si le répertoire courant n'a pas pu être déterminé (par exemple, si l'utilisateur n'a pas les permissions appropriées sur le répertoire courant). Si NULL est renvoyé, un message d'erreur est laissé dans le résultat de l'interpréteur.

CHDIRPROC

Fonction pour traiter un appel Tcl_FSChdir. Si les systèmes de fichiers ne l'implémentent pas, elle sera émulée par une série de vérifications d'accès aux répertoires. Sinon, les systèmes de fichiers virtuels qui l'implémentent doivent seulement répondre avec un résultat positif si pathPtr est un répertoire valide et accessible dans leur système de fichiers. Ils n'ont pas besoin de mémoriser le résultat, car celui-ci sera automatiquement mémorisé pour être utilisé par Tcl_FSGetCwd. Les systèmes de fichiers réels devraient effectuer l'action correcte (c'est-à-dire appeler l'API système chdir correcte).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

La Tcl_FSChdirProc change le répertoire de travail courant de l'application pour la valeur spécifiée dans pathPtr. La fonction renvoie -1 en cas d'erreur ou 0 en cas de succès.
