INTRODUCTION

Les interfaces décrites ici sont utilisées pour personnaliser la boucle d'événements de Tcl. Les deux personnalisations les plus courantes sont l'ajout de nouvelles sources d'événements et la fusion de la boucle d'événements de Tcl avec une autre boucle d'événements, telle que celle fournie par une application dans laquelle Tcl est intégrée. Chacune de ces tâches est décrite dans une section distincte ci-dessous.

Les procédures de cette entrée de manuel sont les éléments de base qui composent le notifier d'événements Tcl. Le notifier d'événements est la couche la plus basse du mécanisme d'événements de Tcl. Il se compose de trois éléments :

[1]
Sources d'événements : elles représentent les moyens par lesquels des événements peuvent être générés. Par exemple, il existe une source d'événements de minuterie qui implémente la procédure Tcl_CreateTimerHandler et la commande after, et il existe une source d'événements de fichier qui implémente la procédure Tcl_CreateFileHandler sur les systèmes Unix. Une source d'événements doit fonctionner avec le notifier pour détecter les événements aux moments opportuns, les enregistrer dans la file d'attente des événements et, finalement, notifier le logiciel de niveau supérieur qu'ils se sont produits. Les procédures Tcl_CreateEventSource, Tcl_DeleteEventSource, Tcl_SetMaxBlockTime, Tcl_QueueEvent et Tcl_DeleteEvents sont principalement utilisées par les sources d'événements.
[2]
La file d'attente d'événements : pour les applications non multithread, il existe une file d'attente unique pour toute l'application, contenant les événements qui ont été détectés mais pas encore traités. Les sources d'événements placent les événements dans la file d'attente afin qu'ils puissent être traités dans l'ordre aux moments appropriés pendant la boucle d'événements. La file d'attente d'événements garantit une discipline équitable de traitement des événements, de sorte qu'aucune source d'événements ne puisse affamer les autres. Elle permet également de sauvegarder les événements pour un traitement ultérieur. Les applications multithread fonctionnent de manière similaire, sauf qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. Tcl_QueueEvent est utilisée (principalement par les sources d'événements) pour ajouter des événements à la file d'attente des événements et Tcl_DeleteEvents est utilisée pour supprimer des événements de la file d'attente sans les traiter. Dans une application multithread, Tcl_QueueEvent ajoute un événement à la file d'attente du thread courant, et Tcl_ThreadQueueEvent ajoute un événement à la file d'attente d'un thread spécifique.
[3]
La boucle d'événements : afin de détecter et de traiter les événements, l'application entre dans une boucle qui attend que les événements se produisent, les place dans la file d'attente d'événements, puis les traite. La plupart des applications le feront en appelant la procédure Tcl_DoOneEvent, qui est décrite dans une entrée de manuel distincte.

La plupart des applications Tcl n'ont pas besoin de se préoccuper des détails internes du notifier Tcl. Cependant, le notifier est maintenant suffisamment flexible pour être redéployé soit pour une nouvelle plateforme, soit pour utiliser une boucle d'événements externe (telle que la boucle d'événements Motif, lorsque Tcl est intégrée dans une application Motif). Les procédures Tcl_WaitForEvent et Tcl_SetTimer sont normalement implémentées par Tcl, mais peuvent être remplacées par de nouvelles versions pour redéployer le notifier (Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler et Tcl_DeleteFileHandler doivent également être remplacées ; voir CRÉATION D'UN NOUVEAU NOTIFIER ci-dessous pour plus de détails). Les procédures Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode et Tcl_SetServiceMode sont fournies pour aider à connecter la boucle d'événements de Tcl à une boucle d'événements externe telle que celle de Motif.

BASES DU NOTIFIER

La façon la plus simple de comprendre le fonctionnement du notifier est d'examiner ce qui se passe lorsque Tcl_DoOneEvent est appelé. Tcl_DoOneEvent reçoit un argument flags qui indique quels types d'événements peuvent être traités et s'il faut bloquer si aucun événement n'est prêt. Tcl_DoOneEvent effectue les opérations suivantes :

[1]
Vérifie la file d'attente d'événements pour voir si elle contient des événements pouvant être traités. Si c'est le cas, il traite le premier événement possible, le retire de la file d'attente et retourne. Pour ce faire, il appelle Tcl_ServiceEvent et lui passe l'argument flags.
[2]
Prépare à bloquer pour un événement. Pour ce faire, Tcl_DoOneEvent appelle une procédure setup dans chaque source d'événements. La source d'événements effectuera une initialisation spécifique à la source d'événements et pourra appeler Tcl_SetMaxBlockTime pour limiter la durée pendant laquelle Tcl_WaitForEvent bloquera si aucun nouvel événement ne se produit.
[3]
Appelle Tcl_WaitForEvent. Cette procédure est implémentée différemment selon les plates-formes ; elle attend qu'un événement se produise, en se basant sur les informations fournies par les sources d'événements. Elle peut amener l'application à se bloquer si timePtr spécifie un intervalle autre que 0. Tcl_WaitForEvent retourne lorsqu'un événement s'est produit, tel qu'un fichier devenant lisible ou l'expiration de l'intervalle donné par timePtr. S'il n'y a aucun événement pour lequel Tcl_WaitForEvent doit attendre, de sorte qu'il bloquerait indéfiniment, alors il retourne immédiatement et Tcl_DoOneEvent retourne 0.
[4]
Appelle une procédure check dans chaque source d'événements. La procédure check détermine si des événements intéressant cette source se sont produits. Si c'est le cas, les événements sont ajoutés à la file d'attente d'événements.
[5]
Vérifie
la file d'attente d'événements pour voir si elle contient des événements pouvant être traités. Si c'est le cas, traiter le premier événement possible, le supprimer de la file d'attente et revenir.
[6]
Vérifier s'il y a des rappels inactifs en attente. Si c'est le cas, les invoquer tous et revenir.
[7]
Soit retourner 0 pour indiquer qu'aucun événement n'était prêt, soit revenir à l'étape [2] si la mise en attente a été demandée par l'appelant.

CRÉATION D'UNE NOUVELLE SOURCE D'ÉVÉNEMENTS

Une source d'événements se compose de trois procédures invoquées par le notificateur, plus des procédures C supplémentaires qui sont invoquées par le code de niveau supérieur pour organiser des rappels pilotés par les événements. Les trois procédures appelées par le notificateur comprennent les procédures de configuration et de vérification décrites ci-dessus, plus une procédure supplémentaire qui est invoquée lorsqu'un événement est retiré de la file d'attente d'événements pour être traité.

La procédure Tcl_CreateEventSource crée une nouvelle source d'événements. Ses arguments spécifient la procédure de configuration et la procédure de vérification pour la source d'événements. SetupProc doit correspondre au prototype suivant :

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

L'argument clientData sera le même que l'argument clientData passé à Tcl_CreateEventSource ; il est généralement utilisé pour pointer vers des informations privées gérées par la source d'événements. L'argument flags sera le même que l'argument flags passé à Tcl_DoOneEvent à ceci près qu'il ne sera jamais 0 (Tcl_DoOneEvent remplace 0 par TCL_ALL_EVENTS). Flags indique quels types d'événements doivent être pris en compte ; si le bit correspondant à cette source d'événements n'est pas défini, la source d'événements doit revenir immédiatement sans rien faire. Par exemple, la source d'événements de fichier vérifie le bit TCL_FILE_EVENTS.

Le rôle de SetupProc est de s'assurer que l'application se réveille lorsque des événements du type souhaité se produisent. Ceci est généralement fait d'une manière dépendante de la plateforme. Par exemple, sous Unix, une source d'événements pourrait appeler Tcl_CreateFileHandler ; sous Windows, elle pourrait demander une notification avec un événement Windows. Pour les sources d'événements pilotées par minuteur telles que les événements de minuteur ou tout événement interrogé, la source d'événements peut appeler Tcl_SetMaxBlockTime pour forcer l'application à se réveiller après un temps spécifié même si aucun événement ne s'est produit. Si aucune source d'événements n'appelle Tcl_SetMaxBlockTime, alors Tcl_WaitForEvent attendra autant que nécessaire qu'un événement se produise ; sinon, il attendra seulement aussi longtemps que l'intervalle le plus court passé à Tcl_SetMaxBlockTime par l'une des sources d'événements. Si une source d'événements sait qu'elle a déjà des événements prêts à être signalés, elle peut demander un temps de blocage nul. Par exemple, la procédure de configuration de la source d'événements X vérifie s'il y a déjà des événements dans la file d'attente. S'il y en a, elle appelle Tcl_SetMaxBlockTime avec un temps de blocage de 0 afin que Tcl_WaitForEvent ne bloque pas s'il n'y a pas de nouvelles données sur la connexion X. L'argument timePtr de Tcl_WaitForEvent pointe vers une structure qui décrit un intervalle de temps en secondes et microsecondes :

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

Le champ usec doit être inférieur à 1000000.

Les informations fournies à Tcl_SetMaxBlockTime ne sont utilisées que pour le prochain appel à Tcl_WaitForEvent ; elles sont supprimées après le retour de Tcl_WaitForEvent. La prochaine fois qu'une attente d'événement sera effectuée, les procédures de configuration de chacune des sources d'événements seront à nouveau appelées, et elles pourront spécifier de nouvelles informations pour cette attente d'événement.

Si l'application utilise une boucle d'événements externe plutôt que Tcl_DoOneEvent, les sources d'événements peuvent avoir besoin d'appeler Tcl_SetMaxBlockTime à d'autres moments. Par exemple, si un nouveau gestionnaire d'événements est enregistré qui doit interroger les événements, la source d'événements peut appeler Tcl_SetMaxBlockTime pour définir le temps de blocage à zéro afin de forcer la boucle d'événements externe à appeler Tcl. Dans ce cas, Tcl_SetMaxBlockTime invoque Tcl_SetTimer avec l'intervalle le plus court vu depuis le dernier appel à Tcl_DoOneEvent ou Tcl_ServiceAll.

En plus de la procédure générique Tcl_SetMaxBlockTime, d'autres procédures spécifiques à la plateforme peuvent également être disponibles pour setupProc, s'il existe des informations supplémentaires nécessaires à Tcl_WaitForEvent sur cette plateforme. Par exemple, sur les systèmes Unix, l'interface Tcl_CreateFileHandler peut être utilisée pour attendre les événements de fichier.

La deuxième procédure fournie par chaque source d'événements est sa procédure de vérification, indiquée par l'argument checkProc de Tcl_CreateEventSource. CheckProc doit correspondre au prototype suivant :

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Les arguments de cette procédure sont les mêmes que ceux de setupProc. CheckProc est invoquée par Tcl_DoOneEvent après qu'elle ait attendu les événements. Vraisemblablement, au moins une source d'événements est maintenant prête à mettre un événement en file d'attente. Tcl_DoOneEvent appelle chaque source d'événements à tour de rôle, afin qu'elles aient toutes une chance de mettre en file d'attente tous les événements qui sont prêts. La procédure de vérification fait deux choses. Premièrement, elle doit vérifier si des événements se sont déclenchés. Différentes sources d'événements le font de différentes manières.

Si la procédure de vérification d'une source d'événements détecte un événement intéressant, elle doit ajouter l'événement à la file d'attente d'événements de Tcl. Pour ce faire, la source d'événements appelle Tcl_QueueEvent. L'argument evPtr est un pointeur vers une structure allouée dynamiquement contenant l'événement (voir ci-dessous pour plus d'informations sur la gestion de la mémoire). Chaque source d'événements peut définir sa propre structure d'événement avec les informations pertinentes pour cette source d'événements. Cependant, le premier élément de la structure doit être une structure de type Tcl_Event, et l'adresse de cette structure est utilisée lors de la communication entre la source d'événements et le reste du notificateur. Un Tcl_Event a la définition suivante :

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La source d'événements doit remplir le champ proc de l'événement avant d'appeler Tcl_QueueEvent. Le champ nextPtr est utilisé pour relier les événements dans la file d'attente et ne doit pas être modifié par la source d'événements.

Un événement peut être ajouté à la file d'attente à l'une des trois positions, en fonction de l'argument position de Tcl_QueueEvent :

TCL_QUEUE_TAIL
Ajoute l'événement à la fin de la file d'attente, de sorte que tous les autres événements en attente soient traités en premier. C'est presque toujours le bon endroit pour les nouveaux événements.
TCL_QUEUE_HEAD
Ajoute l'événement au début de la file d'attente, de sorte qu'il soit traité avant tous les autres événements mis en file d'attente.
TCL_QUEUE_MARK
Ajoute l'événement au début de la file d'attente, à moins qu'il n'y ait d'autres événements au début dont la position est TCL_QUEUE_MARK ; si c'est le cas, ajoute le nouvel événement juste après tous les autres événements TCL_QUEUE_MARK. Cette valeur de position est utilisée pour insérer une séquence ordonnée d'événements au début de la file d'attente, telle qu'une série d'événements Entrée et Sortie synthétisés lors d'une opération de capture ou de libération dans Tk.

Lorsque le moment est venu de traiter un événement de la file d'attente (étapes 1 et 4 ci-dessus), Tcl_ServiceEvent invoquera la procédure proc spécifiée dans la première structure Tcl_Event mise en file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

Le premier argument de proc est un pointeur vers l'événement, qui sera le même que le premier argument de l'appel Tcl_QueueEvent qui a ajouté l'événement à la file d'attente. Le second argument de proc est l'argument flags de l'appel actuel à Tcl_ServiceEvent ; il est utilisé par la source d'événements pour revenir immédiatement si ses événements ne sont pas pertinents.

Il appartient à proc de gérer l'événement, généralement en invoquant une ou plusieurs commandes Tcl ou des rappels au niveau C. Une fois que la source d'événements a fini de gérer l'événement, elle retourne 1 pour indiquer que l'événement peut être retiré de la file d'attente. Si, pour une raison quelconque, la source d'événements décide que l'événement ne peut pas être géré pour le moment, elle peut retourner 0 pour indiquer que l'événement doit être différé pour un traitement ultérieur ; dans ce cas, Tcl_ServiceEvent passera à l'événement suivant dans la file d'attente et tentera de le traiter. Il y a plusieurs raisons pour lesquelles une source d'événements pourrait différer un événement. Une possibilité est que les événements de ce type soient exclus par l'argument flags. Par exemple, la source d'événements de fichier retournera toujours 0 si le bit TCL_FILE_EVENTS n'est pas défini dans flags. Un autre exemple de report d'événements se produit dans Tk si Tk_RestrictEvents a été invoqué pour reporter certains types d'événements de fenêtre.

Lorsque proc retourne 1, Tcl_ServiceEvent retire l'événement de la file d'attente d'événements et libère son stockage. Notez que le stockage d'un événement doit être alloué par la source d'événements (en utilisant Tcl_Alloc ou la macro Tcl ckalloc) avant d'appeler Tcl_QueueEvent, mais il sera libéré par Tcl_ServiceEvent, et non par la source d'événements.

Les applications multithread fonctionnent de manière similaire, sauf qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. L'appel de Tcl_QueueEvent dans une application multithread ajoute un événement à la file d'attente du thread courant. Pour ajouter un événement à la file d'attente d'un autre thread, utilisez Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent accepte comme argument un argument Tcl_ThreadId, qui identifie de manière unique un thread dans une application Tcl. Pour obtenir le Tcl_ThreadId du thread courant, utilisez la procédure Tcl_GetCurrentThread. (Un thread devrait alors passer cet identifiant à d'autres threads pour que ces threads puissent ajouter des événements à sa file d'attente.) Après avoir ajouté un événement à la file d'attente d'un autre thread, vous devez généralement appeler Tcl_ThreadAlert pour « réveiller » le notificateur de ce thread afin de l'alerter du nouvel événement.

Tcl_DeleteEvents peut être utilisé pour supprimer explicitement un ou plusieurs événements de la file d'attente d'événements. Tcl_DeleteEvents appelle proc pour chaque événement dans la file d'attente, supprimant ceux pour lesquels la procédure retourne 1. Les événements pour lesquels la procédure retourne 0 restent dans la file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

L'argument clientData sera le même que l'argument clientData passé à Tcl_DeleteÉvénements ; il est généralement utilisé pour pointer vers des informations privées gérées par la source d'événements. Le pointeur evPtr pointera vers l'événement suivant dans la file d'attente.

Tcl_DeleteEventSource supprime une source d'événements. Les arguments setupProc, checkProc et clientData doivent correspondre exactement à ceux fournis à Tcl_CreateEventSource pour que la source d'événements soit supprimée. Si aucune source de ce type n'existe, Tcl_DeleteEventSource n'a aucun effet.

CRÉATION D'UNE NOUVELLE PROCÉDURE DE NOTIFICATION

La procédure de notification se compose de toutes les procédures décrites dans cette entrée de manuel, plus Tcl_DoOneEvent et Tcl_Sleep, qui sont disponibles sur toutes les plateformes, et Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont spécifiques à Unix. La plupart de ces procédures sont génériques, en ce sens qu'elles sont les mêmes pour toutes les procédures de notification. Cependant, aucune des procédures n'est dépendante de la procédure de notification : Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler et Tcl_ServiceModeHook. Pour prendre en charge une nouvelle plateforme ou pour intégrer Tcl à une boucle d'événements spécifique à une application, vous devez écrire de nouvelles versions de ces procédures.

Tcl_InitNotifier initialise l'état de la procédure de notification et renvoie un handle vers l'état de la procédure de notification. Tcl appelle cette procédure lors de l'initialisation d'un interpréteur Tcl. De même, Tcl_FinalizeNotifier arrête la procédure de notification et est appelée par Tcl_Finalize lors de l'arrêt d'un interpréteur Tcl.

Tcl_WaitForEvent est la procédure de plus bas niveau dans la procédure de notification ; elle est responsable de l'attente d'un événement « intéressant » ou de l'expiration d'un délai donné. Avant que Tcl_WaitForEvent ne soit invoquée, la procédure de configuration de chaque source d'événements aura été invoquée. L'argument timePtr de Tcl_WaitForEvent donne le temps maximum de blocage pour un événement, basé sur les appels à Tcl_SetMaxBlockTime effectués par les procédures de configuration et sur d'autres informations (telles que le bit TCL_DONT_WAIT dans flags).

Idéalement, Tcl_WaitForEvent ne devrait attendre qu'un événement ; elle ne devrait en aucun cas traiter l'événement. Plus tard, les sources d'événements traiteront les événements bruts et créeront des Tcl_Events dans la file d'attente d'événements dans leurs procédures checkProc. Cependant, sur certaines plateformes (comme Windows), cela n'est pas possible ; les événements peuvent être traités dans Tcl_WaitForEvent, y compris la mise en file d'attente de Tcl_Events et plus encore (par exemple, des rappels pour des widgets natifs peuvent être invoqués). La valeur de retour de Tcl_WaitForEvent doit être 0, 1 ou -1. Sur les plateformes comme Windows où les événements sont traités dans Tcl_WaitForEvent, une valeur de retour de 1 signifie qu'il peut y avoir d'autres événements en attente qui n'ont pas été traités. C'est un signe pour l'appelant qu'il doit rappeler Tcl_WaitForEvent s'il veut que tous les événements en attente soient traités. Une valeur de retour de 0 signifie qu'un rappel à Tcl_WaitForEvent n'aura aucun effet : soit c'est une plateforme où Tcl_WaitForEvent attend seulement sans traiter aucun événement, soit Tcl_WaitForEvent sait avec certitude qu'il n'y a pas d'événements supplémentaires à traiter (par exemple, elle est retournée parce que le temps s'est écoulé). Enfin, une valeur de retour de -1 signifie que la boucle d'événements n'est plus opérationnelle et que l'application devrait probablement se terminer. Sous Windows, cela se produit lorsqu'un message WM_QUIT est reçu ; sous Unix, cela se produit lorsque Tcl_WaitForEvent attendrait indéfiniment car il n'y avait pas de sources d'événements actives et que le délai d'attente était infini.

Tcl_AlertNotifier est utilisé dans les applications multithread pour permettre à n'importe quel thread de « réveiller » la procédure de notification pour l'alerter de nouveaux événements dans sa file d'attente. Tcl_AlertNotifier nécessite en argument le handle de la procédure de notification renvoyé par Tcl_InitNotifier.

Si la procédure de notification doit être utilisée avec une boucle d'événements externe, alors elle doit également prendre en charge l'interface Tcl_SetTimer. Tcl_SetTimer est invoquée par Tcl_SetMaxBlockTime chaque fois que le temps de blocage maximal a été réduit. Tcl_SetTimer doit organiser la boucle d'événements externe pour qu'elle invoque Tcl_ServiceAll après l'intervalle spécifié, même si aucun événement ne s'est produit. Cette interface est nécessaire car Tcl_WaitForEvent n'est pas invoquée lorsqu'il existe une boucle d'événements externe. Si la procédure de notification ne doit être utilisée qu'à partir de Tcl_DoOneEvent, alors Tcl_SetTimer n'a rien à faire.

Tcl_ServiceModeHook est appelée par la partie indépendante de la plateforme de la procédure de notification lorsque le code client appelle Tcl_SetServiceMode. Ce hook est fourni pour prendre en charge les systèmes d'exploitation qui nécessitent une gestion spéciale des événements lorsque l'application est dans une boucle modale (la procédure de notification Windows, par exemple, utilise ce hook pour créer une fenêtre de communication).

Sur les systèmes Unix, la source d'événements de fichier nécessite également le support de la procédure de notification. La source d'événements de fichier se compose des procédures Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont décrites dans la page de manuel de Tcl_CreateFileHandler.

Les interfaces Tcl_Sleep et Tcl_DoOneEvent sont décrites dans leurs pages de manuel respectives.

Le moyen le plus simple de créer une nouvelle procédure de notification est de consulter le code d'une procédure de notification existante, telle que les fichiers unix/tclUnixNotfy.c ou win/tclWinNotify.c dans la distribution source de Tcl.

REMPLACEMENT DE LA PROCÉDURE DE NOTIFICATION

Une procédure de notification écrite selon les conventions ci-dessus peut également être installée dans un processus en cours à la place de la procédure de notification standard. Ce mécanisme est utilisé de sorte qu'un exécutable unique puisse être utilisé (avec la procédure de notification standard) comme programme autonome et réutilisé (avec une procédure de notification de remplacement dans une extension chargeable) comme extension d'un autre programme, tel qu'un plugin de navigateur Web.

Pour ce faire, l'extension appelle Tcl_SetNotifier en lui transmettant un pointeur vers une structure de données Tcl_NotifierProcs. La structure a la disposition suivante :

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Après l'appel à Tcl_SetNotifier, les pointeurs fournis dans la structure Tcl_NotifierProcs remplacent toute procédure de notification qui avait été installée dans le processus.

Il est extraordinairement déconseillé de remplacer une procédure de notification en cours d'exécution. Normalement, Tcl_SetNotifier doit être appelé au moment de l'initialisation du processus, avant le premier appel à Tcl_InitNotifier.

BOUCLES D'ÉVÉNEMENTS EXTERNES

Les interfaces de procédure de notification sont conçues pour que Tcl puisse être intégrée dans des applications qui ont leurs propres boucles d'événements privées. Dans ce cas, l'application n'appelle pas Tcl_DoOneEvent sauf dans le cas de boucles d'événements récursives telles que les appels aux commandes Tcl update ou vwait. La majorité du temps est passée dans la boucle d'événements externe de l'application. Dans ce cas, la procédure de notification doit s'arranger pour que la boucle d'événements externe rappelle Tcl lorsque quelque chose se produit sur les différentes sources d'événements Tcl. Ces rappels doivent organiser la mise en place des événements Tcl appropriés dans la file d'attente d'événements Tcl.

Étant donné que la boucle d'événements externe n'appelle pas Tcl_DoOneEvent régulièrement, il incombe à la procédure de notification de faire en sorte que Tcl_ServiceEvent soit appelée chaque fois qu'il y a des événements en attente dans la file d'attente d'événements Tcl. Le moyen le plus simple d'y parvenir est d'invoquer Tcl_ServiceAll à la fin de chaque rappel de la boucle d'événements externe. Cela garantira que toutes les sources d'événements sont interrogées, que tous les événements mis en file d'attente sont traités et que tous les gestionnaires d'inactivité en attente sont traités avant de rendre le contrôle à l'application. De plus, les sources d'événements qui doivent interroger les événements peuvent appeler Tcl_SetMaxBlockTime pour forcer la boucle d'événements externe à appeler Tcl, même si aucun événement n'est disponible dans la file d'attente d'événements système.

En raison du traitement des événements détectés dans la boucle d'événements externe principale, Tcl peut invoquer Tcl_DoOneEvent pour démarrer une boucle d'événements récursive dans des commandes telles que vwait. Tcl_DoOneEvent invoquera la boucle d'événements externe, ce qui entraînera des rappels comme décrit dans le paragraphe précédent, ce qui entraînera des appels à Tcl_ServiceAll. Cependant, dans ces cas, il est indésirable de traiter les événements dans Tcl_ServiceAll. Le traitement des événements là-bas est inutile car le contrôle reviendra immédiatement à la boucle d'événements externe et donc à Tcl_DoOneEvent, qui peut traiter les événements elle-même. De plus, Tcl_DoOneEvent est censé traiter un seul événement, tandis que Tcl_ServiceAll traite normalement tous les événements en attente. Pour gérer cette situation, Tcl_DoOneEvent définit un indicateur pour Tcl_ServiceAll qui lui fait retourner sans traiter aucun événement. Cet indicateur est appelé le « mode de service » ; Tcl_DoOneEvent le restaure à sa valeur précédente avant de retourner.

Dans certains cas, cependant, il peut être nécessaire pour Tcl_ServiceAll de traiter les événements même lorsqu'elle a été appelée depuis Tcl_DoOneEvent. Cela se produit lorsqu'il existe une autre boucle d'événements récursive invoquée via un gestionnaire d'événements appelé par Tcl_DoOneEvent (tel qu'un composant d'un widget natif). Dans ce cas, Tcl_DoOneEvent peut ne pas avoir la possibilité de traiter les événements, donc Tcl_ServiceAll doit tous les traiter. Toute boucle d'événements récursive qui appelle une boucle d'événements externe plutôt que Tcl_DoOneEvent doit réinitialiser le mode de service afin que tous les événements soient traités dans Tcl_ServiceAll. Ceci est fait en invoquant la procédure Tcl_SetServiceMode. Si Tcl_SetServiceMode est passé TCL_SERVICE_NONE, alors les appels à Tcl_ServiceAll retourneront immédiatement sans traiter aucun événement. Si Tcl_SetServiceMode est passé TCL_SERVICE_ALL, alors les appels à Tcl_ServiceAll se comporteront normalement. Tcl_SetServiceMode renvoie la valeur précédente du mode de service, qui doit être restaurée lorsque la boucle récursive se termine. Tcl_GetServiceMode renvoie la valeur actuelle du mode de service.

INTRODUCTION

Tcl prend en charge les threads, les mutex, les conditions, les canaux, les événements et les files d'attente d'événements.

BASES DU NOTIFICATEUR

Le concept de base est que Tcl gère une liste de descripteurs de fichiers et d'autres sources d'événements, et les utilise pour déterminer quand rappeler les gestionnaires d'événements appropriés. C'est ce que fait la boucle d'événements principale dans l'interpréteur Tcl.

CRÉER UNE NOUVELLE SOURCE D'ÉVÉNEMENTS

Une nouvelle source d'événements peut être créée en utilisant Tcl_MakeFile, Tcl_MakeResource, Tcl_MakePipe, Tcl_MakeTimer ou Tcl_MakeEventSource.

Tcl_MakeFile: Crée une nouvelle source d'événements à partir d'un descripteur de fichier.

Tcl_MakeResource: Crée une nouvelle source d'événements à partir d'une ressource nommée.

Tcl_MakePipe: Crée une nouvelle source d'événements à partir d'un tuyau.

Tcl_MakeTimer: Crée une nouvelle source d'événements à partir d'une minuterie.

Tcl_MakeEventSource: Crée une nouvelle source d'événements à partir d'un type de canal.

CRÉER UN NOUVEAU NOTIFICATEUR

Un nouveau notificateur peut être créé en utilisant Tcl_EventSourceQueue, Tcl_EventSourceSock, Tcl_EventSourceTimer, Tcl_EventSourceIdle ou Tcl_EventSourceServiceMode.

Tcl_EventSourceQueue: Met en file d'attente un événement pour une source d'événements.

Tcl_EventSourceSock: Définit un descripteur de fichier pour une source d'événements.

Tcl_EventSourceTimer: Définit une minuterie pour une source d'événements.

Tcl_EventSourceIdle: Définit un événement inactif pour une source d'événements.

Tcl_EventSourceServiceMode: Définit le mode de service pour une source d'événements.

REMPLACER LE NOTIFICATEUR

Le notificateur par défaut peut être remplacé en utilisant Tcl_EventSourceThread.

BOUCLES D'ÉVÉNEMENTS EXTERNES

Tcl prend en charge l'intégration avec des boucles d'événements externes. Cela permet à Tcl d'être utilisé dans des environnements où une boucle d'événements existe déjà, tels que les applications GUI.
