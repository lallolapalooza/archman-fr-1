INTRODUCTION

Les interfaces décrites ici sont utilisées pour personnaliser la boucle d'événements Tcl. Les deux personnalisations les plus courantes sont l'ajout de nouvelles sources d'événements et la fusion de la boucle d'événements Tcl avec une autre boucle d'événements, telle qu'une boucle fournie par une application dans laquelle Tcl est incorporé. Chacune de ces tâches est décrite dans une section distincte ci-dessous.

Les procédures de cette entrée manuelle sont les éléments constitutifs de la construction du notifier Tcl. Le notifier d'événements est la couche la plus basse du mécanisme d'événements Tcl. Il se compose de trois éléments :

[1]
Sources d'événements : celles-ci représentent les moyens par lesquels les événements peuvent être générés. Par exemple, il existe une source d'événements de minuteur qui implémente la procédure Tcl_CreateTimerHandler et la commande after, et il existe une source d'événements de fichier qui implémente la procédure Tcl_CreateFileHandler sur les systèmes Unix. Une source d'événements doit fonctionner avec le notifier pour détecter les événements aux bons moments, les enregistrer dans la file d'attente des événements et notifier finalement le logiciel de niveau supérieur qu'ils se sont produits. Les procédures Tcl_CreateEventSource, Tcl_DeleteEventSource, et Tcl_SetMaxBlockTime, Tcl_QueueEvent, et Tcl_DeleteEvents sont principalement utilisées par les sources d'événements.
[2]
La file d'attente d'événements : pour les applications non multithread, il existe une seule file d'attente pour l'ensemble de l'application, contenant les événements qui ont été détectés mais pas encore traités. Les sources d'événements placent des événements dans la file d'attente afin qu'ils puissent être traités dans l'ordre à des moments appropriés pendant la boucle d'événements. La file d'attente d'événements garantit une discipline équitable de traitement des événements, de sorte qu'aucune source d'événements ne puisse affamer les autres. Elle permet également de sauvegarder les événements pour un traitement ultérieur. Les applications multithread fonctionnent de manière similaire, sauf qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. Tcl_QueueEvent est utilisé (principalement par les sources d'événements) pour ajouter des événements à la file d'attente d'événements et Tcl_DeleteEvents est utilisé pour supprimer des événements de la file d'attente sans les traiter. Dans une application multithread, Tcl_QueueEvent ajoute un événement à la file d'attente du thread courant, et Tcl_ThreadQueueEvent ajoute un événement à une file d'attente dans un thread spécifique.
[3]
La boucle d'événements : pour détecter et traiter les événements, l'application entre dans une boucle qui attend que les événements se produisent, les place dans la file d'attente d'événements, puis les traite. La plupart des applications le feront en appelant la procédure Tcl_DoOneEvent, qui est décrite dans une entrée manuelle distincte.

La plupart des applications Tcl n'ont pas besoin de se soucier des détails internes du notifier Tcl. Cependant, le notifier est désormais suffisamment flexible pour être redirigé soit vers une nouvelle plateforme, soit pour utiliser une boucle d'événements externe (telle que la boucle d'événements Motif, lorsque Tcl est incorporé dans une application Motif). Les procédures Tcl_WaitForEvent et Tcl_SetTimer sont normalement implémentées par Tcl, mais peuvent être remplacées par de nouvelles versions pour rediriger le notifier (les procédures Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler, et Tcl_DeleteFileHandler doivent également être remplacées ; voir CRÉATION D'UN NOUVEAU NOTIFIER ci-dessous pour plus de détails). Les procédures Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode, et Tcl_SetServiceMode sont fournies pour aider à connecter la boucle d'événements Tcl à une boucle d'événements externe telle que celle de Motif.

BASES DU NOTIFIER

Le moyen le plus simple de comprendre le fonctionnement du notifier est de considérer ce qui se passe lorsque Tcl_DoOneEvent est appelé. Tcl_DoOneEvent reçoit un argument flags qui indique quels types d'événements peuvent être traités et s'il faut bloquer s'il n'y a pas d'événements prêts. Tcl_DoOneEvent effectue les actions suivantes :

[1]
Vérifie la file d'attente d'événements pour voir si elle contient des événements pouvant être traités. Si c'est le cas, il traite le premier événement possible, le retire de la file d'attente et renvoie. Il le fait en appelant Tcl_ServiceEvent et en passant l'argument flags.
[2]
Prépare le blocage pour un événement. Pour ce faire, Tcl_DoOneEvent invoque une procédure de configuration dans chaque source d'événements. La source d'événements effectuera une initialisation spécifique à la source d'événements et pourra appeler Tcl_SetMaxBlockTime pour limiter la durée pendant laquelle Tcl_WaitForEvent bloquera si aucun nouvel événement ne se produit.
[3]
Appelle Tcl_WaitForEvent. Cette procédure est implémentée différemment selon les plates-formes ; elle attend qu'un événement se produise, en fonction des informations fournies par les sources d'événements. Elle peut entraîner le blocage de l'application si timePtr spécifie un intervalle différent de 0. Tcl_WaitForEvent renvoie lorsque quelque chose s'est produit, comme un fichier devenant lisible ou l'expiration de l'intervalle donné par timePtr. S'il n'y a pas d'événements pour lesquels Tcl_WaitForEvent doit attendre, de sorte qu'il bloquerait indéfiniment, alors il renvoie immédiatement et Tcl_DoOneEvent renvoie 0.
[4]
Appelle une procédure de vérification dans chaque source d'événements. La procédure de vérification détermine si des événements intéressants pour cette source se sont produits. Si c'est le cas, les événements sont ajoutés à la file d'attente d'événements.
[5]
Vérifie le
file d'attente d'événements pour voir s'il contient des événements pouvant être servis. Si c'est le cas, servir le premier événement possible, le retirer de la file d'attente et revenir.
[6]
Vérifier s'il y a des rappels inactifs en attente. Si c'est le cas, les invoquer tous et revenir.
[7]
Soit retourner 0 pour indiquer qu'aucun événement n'était prêt, soit revenir à l'étape [2] si le blocage a été demandé par l'appelant.

CRÉATION D'UNE NOUVELLE SOURCE D'ÉVÉNEMENTS

Une source d'événements se compose de trois procédures invoquées par le notificateur, plus des procédures C supplémentaires qui sont invoquées par le code de niveau supérieur pour organiser des rappels pilotés par événements. Les trois procédures appelées par le notificateur comprennent les procédures de configuration et de vérification décrites ci-dessus, plus une procédure supplémentaire qui est invoquée lorsqu'un événement est retiré de la file d'attente d'événements pour être servi.

La procédure Tcl_CreateEventSource crée une nouvelle source d'événements. Ses arguments spécifient la procédure de configuration et la procédure de vérification pour la source d'événements. SetupProc doit correspondre au prototype suivant :

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

L'argument clientData sera le même que l'argument clientData passé à Tcl_CreateEventSource ; il est généralement utilisé pour pointer vers des informations privées gérées par la source d'événements. L'argument flags sera le même que l'argument flags passé à Tcl_DoOneEvent sauf qu'il ne sera jamais 0 (Tcl_DoOneEvent remplace 0 par TCL_ALL_EVENTS). Flags indique quels types d'événements doivent être considérés ; si le bit correspondant à cette source d'événements n'est pas défini, la source d'événements doit revenir immédiatement sans rien faire. Par exemple, la source d'événements de fichier vérifie le bit TCL_FILE_EVENTS.

Le travail de SetupProc est de s'assurer que l'application se réveille lorsque des événements du type souhaité se produisent. Ceci est généralement fait de manière dépendante de la plateforme. Par exemple, sous Unix, une source d'événements pourrait appeler Tcl_CreateFileHandler ; sous Windows, elle pourrait demander une notification avec un événement Windows. Pour les sources d'événements pilotées par minuterie, telles que les événements de minuterie ou tout événement interrogé, la source d'événements peut appeler Tcl_SetMaxBlockTime pour forcer l'application à se réveiller après un temps spécifié même si aucun événement ne s'est produit. Si aucune source d'événements n'appelle Tcl_SetMaxBlockTime, alors Tcl_WaitForEvent attendra aussi longtemps que nécessaire qu'un événement se produise ; sinon, elle n'attendra que le temps le plus court passé à Tcl_SetMaxBlockTime par l'une des sources d'événements. Si une source d'événements sait qu'elle a déjà des événements prêts à signaler, elle peut demander un temps de blocage maximal nul. Par exemple, la procédure de configuration de la source d'événements X vérifie s'il y a déjà des événements mis en file d'attente. S'il y en a, elle appelle Tcl_SetMaxBlockTime avec un temps de blocage de 0 afin que Tcl_WaitForEvent ne bloque pas s'il n'y a pas de nouvelles données sur la connexion X. L'argument timePtr de Tcl_WaitForEvent pointe vers une structure qui décrit un intervalle de temps en secondes et microsecondes :

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

Le champ usec doit être inférieur à 1000000.

Les informations fournies à Tcl_SetMaxBlockTime ne sont utilisées que pour le prochain appel à Tcl_WaitForEvent ; elles sont supprimées après le retour de Tcl_WaitForEvent. La prochaine fois qu'une attente d'événement sera effectuée, chacune des procédures de configuration des sources d'événements sera à nouveau appelée, et elles pourront spécifier de nouvelles informations pour cette attente d'événement.

Si l'application utilise une boucle d'événements externe plutôt que Tcl_DoOneEvent, les sources d'événements peuvent avoir besoin d'appeler Tcl_SetMaxBlockTime à d'autres moments. Par exemple, si un nouveau gestionnaire d'événements est enregistré qui nécessite d'interroger les événements, la source d'événements peut appeler Tcl_SetMaxBlockTime pour définir le temps de blocage à zéro afin de forcer la boucle d'événements externe à appeler Tcl. Dans ce cas, Tcl_SetMaxBlockTime invoque Tcl_SetTimer avec l'intervalle le plus court vu depuis le dernier appel à Tcl_DoOneEvent ou Tcl_ServiceAll.

En plus de la procédure générique Tcl_SetMaxBlockTime, d'autres procédures spécifiques à la plateforme peuvent également être disponibles pour setupProc, s'il y a des informations supplémentaires nécessaires à Tcl_WaitForEvent sur cette plateforme. Par exemple, sur les systèmes Unix, l'interface Tcl_CreateFileHandler peut être utilisée pour attendre des événements de fichier.

La deuxième procédure fournie par chaque source d'événements est sa procédure de vérification, indiquée par l'argument checkProc de Tcl_CreateEventSource. CheckProc doit correspondre au prototype suivant :

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Les arguments de cette procédure sont les mêmes que ceux de setupProc. CheckProc est invoqué par Tcl_DoOneEvent après qu'il ait attendu des événements. On suppose qu'au moins une source d'événements est maintenant prête à mettre un événement en file d'attente. Tcl_DoOneEvent appelle chaque source d'événements à tour de rôle, afin qu'elles aient toutes une chance de mettre en file d'attente tous les événements qui sont prêts. La procédure de vérification fait deux choses. Premièrement, elle doit vérifier si des événements se sont déclenchés. Différentes sources d'événements le font de différentes manières.

Si la procédure de vérification d'une source d'événements détecte un événement intéressant, elle doit ajouter l'événement à la file d'attente d'événements de Tcl. Pour ce faire, la source d'événements appelle Tcl_QueueEvent. L'argument evPtr est un pointeur vers une structure allouée dynamiquement contenant l'événement (voir ci-dessous pour plus d'informations sur les problèmes de gestion de la mémoire). Chaque source d'événements peut définir sa propre structure d'événement avec les informations pertinentes pour cette source d'événements. Cependant, le premier élément de la structure doit être une structure de type Tcl_Event, et l'adresse de cette structure est utilisée pour la communication entre la source d'événements et le reste du notificateur. Un Tcl_Event a la définition suivante :

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La source d'événements doit remplir le champ proc de l'événement avant d'appeler Tcl_QueueEvent. Le champ nextPtr est utilisé pour lier les événements dans la file d'attente et ne doit pas être modifié par la source d'événements.

Un événement peut être ajouté à la file d'attente à l'une des trois positions, en fonction de l'argument position de Tcl_QueueEvent :

TCL_QUEUE_TAIL
Ajouter l'événement à la fin de la file d'attente, de sorte que tous les autres événements en attente soient servis en premier. C'est presque toujours la bonne position pour les nouveaux événements.
TCL_QUEUE_HEAD
Ajouter l'événement au début de la file d'attente, de sorte qu'il soit servi avant tous les autres événements mis en file d'attente.
TCL_QUEUE_MARK
Ajouter l'événement au début de la file d'attente, sauf s'il y a d'autres événements au début dont la position est TCL_QUEUE_MARK ; si c'est le cas, ajouter le nouvel événement juste après tous les autres événements TCL_QUEUE_MARK. Cette valeur de position est utilisée pour insérer une séquence ordonnée d'événements au début de la file d'attente, comme une série d'événements Enter et Leave synthétisés lors d'une opération de saisie ou de libération dans Tk.

Lorsqu'il est temps de traiter un événement de la file d'attente (étapes 1 et 4 ci-dessus), Tcl_ServiceEvent invoquera le proc spécifié dans la première Tcl_Event mise en file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

Le premier argument de proc est un pointeur vers l'événement, qui sera le même que le premier argument de l'appel Tcl_QueueEvent qui a ajouté l'événement à la file d'attente. Le deuxième argument de proc est l'argument flags pour l'appel actuel de Tcl_ServiceEvent ; ceci est utilisé par la source d'événements pour revenir immédiatement si ses événements ne sont pas pertinents.

Il appartient à proc de gérer l'événement, généralement en invoquant une ou plusieurs commandes Tcl ou des rappels au niveau C. Une fois que la source d'événements a terminé le traitement de l'événement, elle retourne 1 pour indiquer que l'événement peut être retiré de la file d'attente. Si, pour une raison quelconque, la source d'événements décide que l'événement ne peut pas être traité à ce moment-là, elle peut retourner 0 pour indiquer que l'événement doit être différé pour un traitement ultérieur ; dans ce cas, Tcl_ServiceEvent passera à l'événement suivant dans la file d'attente et tentera de le servir. Il y a plusieurs raisons pour lesquelles une source d'événements pourrait différer un événement. Une possibilité est que les événements de ce type soient exclus par l'argument flags. Par exemple, la source d'événements de fichier retournera toujours 0 si le bit TCL_FILE_EVENTS n'est pas défini dans flags. Un autre exemple de report d'événements se produit dans Tk si Tk_RestrictEvents a été invoqué pour reporter certains types d'événements de fenêtre.

Lorsque proc retourne 1, Tcl_ServiceEvent retirera l'événement de la file d'attente d'événements et libérera sa mémoire. Notez que la mémoire d'un événement doit être allouée par la source d'événements (en utilisant Tcl_Alloc ou la macro Tcl ckalloc) avant d'appeler Tcl_QueueEvent, mais elle sera libérée par Tcl_ServiceEvent, et non par la source d'événements.

Les applications multithread fonctionnent de manière similaire, sauf qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. Appeler Tcl_QueueEvent dans une application multithread ajoute un événement à la file d'attente du thread actuel. Pour ajouter un événement à la file d'attente d'un autre thread, utilisez Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent accepte comme argument un argument Tcl_ThreadId, qui identifie de manière unique un thread dans une application Tcl. Pour obtenir le Tcl_ThreadId du thread actuel, utilisez la procédure Tcl_GetCurrentThread. (Un thread devrait alors passer cet identifiant à d'autres threads pour que ces derniers puissent ajouter des événements à sa file d'attente.) Après avoir ajouté un événement à la file d'attente d'un autre thread, vous devez généralement appeler Tcl_ThreadAlert pour « réveiller » le notificateur de ce thread afin de l'alerter du nouvel événement.

Tcl_DeleteEvents peut être utilisé pour retirer explicitement un ou plusieurs événements de la file d'attente d'événements. Tcl_DeleteEvents appelle proc pour chaque événement dans la file d'attente, en supprimant ceux pour lesquels la procédure retourne 1. Les événements pour lesquels la procédure retourne 0 sont laissés dans la file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

L'argument clientData sera le même que l'argument clientData de Tcl_DeleteEven

CRÉATION D'UN NOUVEAU NOTIFICATEUR

Le notificateur se compose de toutes les procédures décrites dans ce manuel, plus Tcl_DoOneEvent et Tcl_Sleep, disponibles sur toutes les plateformes, et Tcl_CreateFileHandler et Tcl_DeleteFileHandler, spécifiques à Unix. La plupart de ces procédures sont génériques, car elles sont identiques pour tous les notificateurs. Cependant, aucune d'entre elles ne dépend du notificateur : Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler et Tcl_ServiceModeHook. Pour prendre en charge un nouveau système d'exploitation ou intégrer Tcl à une boucle d'événements spécifique à une application, vous devez écrire de nouvelles versions de ces procédures.

Tcl_InitNotifier initialise l'état du notificateur et renvoie un handle vers l'état du notificateur. Tcl appelle cette procédure lors de l'initialisation d'un interpréteur Tcl. De même, Tcl_FinalizeNotifier désactive le notificateur, et est appelée par Tcl_Finalize lors de la fermeture d'un interpréteur Tcl.

Tcl_WaitForEvent est la procédure la plus bas niveau du notificateur ; elle est responsable de l'attente d'un événement "intéressant" ou de l'attente pendant une durée donnée. Avant que Tcl_WaitForEvent ne soit invoquée, chaque procédure de source d'événement sera invoquée. L'argument timePtr de Tcl_WaitForEvent donne le temps de blocage maximum pour un événement, basé sur les appels à Tcl_SetMaxBlockTime effectués par les procédures de configuration et sur d'autres informations (comme le bit TCL_DONT_WAIT dans flags).

Idéalement, Tcl_WaitForEvent ne devrait attendre qu'un seul événement ; elle ne doit pas le traiter d'une quelconque manière. Par la suite, les événements des sources d'événement seront traités dans leurs procédures checkProc, créant des Tcl_Events dans la file d'attente des événements. Cependant, sur certaines plateformes (comme Windows), ce n'est pas possible ; les événements peuvent être traités dans Tcl_WaitForEvent, y compris la file d'attente des Tcl_Events et plus encore (par exemple, les callbacks pour les widgets natifs). La valeur renvoyée par Tcl_WaitForEvent doit être 0, 1 ou -1. Sur les plateformes comme Windows, où les événements sont traités dans Tcl_WaitForEvent, une valeur de retour de 1 signifie qu'il peut y avoir d'autres événements en attente qui n'ont pas été traités. C'est un indicateur pour l'appelant qu'il doit appeler à nouveau Tcl_WaitForEvent pour traiter tous les événements en attente. Une valeur de retour de 0 signifie qu'appeler à nouveau Tcl_WaitForEvent n'aura aucun effet : il peut s'agir d'un système d'exploitation où Tcl_WaitForEvent attend simplement sans traiter les événements, ou Tcl_WaitForEvent sait avec certitude qu'il n'y a plus d'événements en attente (par exemple, en raison du temps écoulé). Enfin, une valeur de retour de -1 signifie que la boucle d'événements n'est plus opérationnelle et que l'application doit se débarrasser et se terminer. Cela se produit lorsqu'un message WM_QUIT est reçu sous Windows, et lorsque Tcl_WaitForEvent attend éternellement sous Unix car il n'y a pas de sources d'événements actives et que le timeout est infini).

Tcl_AlertNotifier est utilisé dans les applications multithread pour permettre à n'importe quel thread de "réveiller" le notificateur afin de lui signaler de nouveaux événements dans sa file d'attente. Tcl_AlertNotifier nécessite comme argument le handle du notificateur renvoyé par Tcl_InitNotifier.

Si le notificateur doit être utilisé avec une boucle d'événements externe, il doit également prendre en charge l'interface Tcl_SetTimer. Tcl_SetTimer est appelée par Tcl_SetMaxBlockTime lorsque le temps de blocage maximum a été réduit. Tcl_SetTimer doit s'assurer que la boucle d'événements externe appelle Tcl_ServiceAll après l'intervalle spécifié, même si aucun événement ne s'est produit. Cette interface est nécessaire car Tcl_WaitForEvent n'est pas appelée lorsqu'il y a une boucle d'événements externe. Si le notificateur ne doit être utilisé qu'à partir de Tcl_DoOneEvent, Tcl_SetTimer ne doit rien faire.

Tcl_ServiceModeHook est appelée par la partie indépendante du notificateur lorsque le code client appelle Tcl_SetServiceMode. Cette hook est fournie pour prendre en charge les systèmes d'exploitation qui nécessitent une gestion spéciale des événements lorsque l'application est dans une boucle modale (par exemple, le notificateur Windows utilise cette hook pour créer une fenêtre de communication).

Sur les systèmes Unix, les sources d'événements basées sur des fichiers nécessitent également le support du notificateur. Les sources d'événements consistent en les procédures Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont décrites dans la page de manuel de Tcl_CreateFileHandler.

Les interfaces Tcl_Sleep et Tcl_DoOneEvent sont décrites dans leurs pages de manuel respectives.

La manière la plus simple de créer un nouveau notificateur est d'examiner le code d'un notificateur existant, comme dans les fichiers unix/tclUnixNotfy.c ou win/tclWinNotify.c dans la distribution du code source de Tcl.

REMPLACEMENT DU NOTIFICATEUR

Un notificateur écrit selon les conventions ci-dessus peut également être installé dans un processus en cours d'exécution à la place du notificateur standard. Cette mécanique est utilisée pour qu'un seul exécutable puisse être utilisé (avec le notificateur standard) comme programme autonome et réutilisé (avec un notificateur remplacé dans une extension chargeable) comme extension d'un autre programme, comme un plugin de navigateur web.

Pour y parvenir, l'extension appelle Tcl_SetNotifier, en passant un pointeur vers une structure Tcl_NotifierProcs. Cette structure a la disposition suivante :

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Après l'appel à Tcl_SetNotifier, les pointeurs fournis dans la structure Tcl_NotifierProcs remplacent ce qui avait été précédemment installé dans le processus.

Il est extrêmement inutile de remplacer un notificateur en cours d'exécution. Normalement, Tcl_SetNotifier doit être appelé avant le premier appel à Tcl_InitNotifier lors de l'initialisation du processus.

BOUCLES D'ÉVÉNEMENTS EXTERNES

Les interfaces du notificateur sont conçues pour que Tcl puisse s'intégrer dans des applications qui ont leurs propres boucles d'événements privées. Dans ce cas, l'application n'appelle pas Tcl_DoOneEvent, sauf dans des cas tels que des boucles d'événements récursives, comme les appels aux commandes Tcl update ou vwait. La majeure partie du temps est consacrée à la boucle d'événements externe de l'application. Dans ce cas, le notificateur doit s'assurer que la boucle d'événements externe appelle Tcl_ServiceEvent lorsqu'un événement se produit sur l'une des sources d'événements de Tcl. Ces callbacks doivent s'assurer que les événements appropriés sont placés dans la file d'attente des événements de Tcl.

En conséquence des événements détectés dans la boucle d'événements externe principale, Tcl peut appeler Tcl_DoOneEvent pour initier une boucle d'événements récursive dans des commandes comme vwait. Tcl_DoOneEvent appellera la boucle d'événements externe, ce qui entraînera des callbacks comme décrit ci-dessus, qui à leur tour entraîneront des appels à Tcl_ServiceAll. Cependant, dans ces cas, aucun événement ne doit être traité dans Tcl_ServiceAll. Le traitement là-bas est inutile car le contrôle sera immédiatement rendu à la boucle d'événements externe, donc rendu à Tcl_DoOneEvent, qui peut traiter les événements lui-même. De plus, Tcl_DoOneEvent est conçu pour traiter un seul événement, tandis que Tcl_ServiceAll traite normalement tous les événements en attente. Pour gérer cette situation, Tcl_DoOneEvent définit un indicateur pour Tcl_ServiceAll qui fait que ce dernier renvoie sans traiter d'événement. Cet indicateur est appelé le mode de service ; Tcl_DoOneEvent le restaure à sa valeur précédente avant de renvoyer.

Dans certains cas, il peut être nécessaire que Tcl_ServiceAll s'exécute même s'il a été appelé depuis Tcl_DoOneEvent. Cela se produit lorsqu'une autre boucle d'événements récursive est appelée via un gestionnaire d'événements appelé par Tcl_DoOneEvent (comme celui qui fait partie d'un widget natif). Dans ce cas, Tcl_DoOneEvent pourrait ne pas avoir l'occasion de traiter les événements, donc Tcl_ServiceAll doit traiter tous les événements. Toute boucle d'événements récursive qui appelle une boucle d'événements externe au lieu de Tcl_DoOneEvent doit réinitialiser le mode de service afin que tous les événements soient traités dans Tcl_ServiceAll. Ceci est réalisé en appelant la procédure Tcl_SetServiceMode. Si Tcl_SetServiceMode est passé TCL_SERVICE_NONE, alors les appels à Tcl_ServiceAll renverront immédiatement sans traiter d'événement. Si Tcl_SetServiceMode est passé TCL_SERVICE_ALL, alors les appels à Tcl_ServiceAll se comporteront normalement. Tcl_SetServiceMode renvoie la valeur précédente du mode de service, qui doit être restaurée lorsque la boucle d'événements récursive se termine. Tcl_GetServiceMode renvoie la valeur actuelle du mode de service.
