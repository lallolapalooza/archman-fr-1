INTRODUCTION

Les interfaces décrites ici sont utilisées pour personnaliser la boucle d'événements Tcl. Les deux personnalisations les plus courantes consistent à ajouter de nouvelles sources d'événements et à fusionner la boucle d'événements Tcl avec une autre boucle d'événements, telle que celle fournie par une application dans laquelle Tcl est intégrée. Chacune de ces tâches est décrite dans une section distincte ci-dessous.

Les procédures de cette entrée de manuel sont les éléments constitutifs de la boucle de notification d'événements Tcl. La boucle de notification d'événements est la couche la plus basse du mécanisme d'événements Tcl. Elle se compose de trois éléments :

[1]
Sources d'événements : celles-ci représentent les moyens par lesquels des événements peuvent être générés. Par exemple, il existe une source d'événements de minuteur qui implémente la procédure Tcl_CreateTimerHandler et la commande after, et il existe une source d'événements de fichier qui implémente la procédure Tcl_CreateFileHandler sur les systèmes Unix. Une source d'événements doit fonctionner avec le gestionnaire de notification pour détecter les événements aux bons moments, les enregistrer dans la file d'attente d'événements et informer finalement le logiciel de niveau supérieur qu'ils se sont produits. Les procédures Tcl_CreateEventSource, Tcl_DeleteEventSource et Tcl_SetMaxBlockTime, Tcl_QueueEvent, et Tcl_DeleteEvents sont principalement utilisées par les sources d'événements.
[2]
La file d'attente d'événements : pour les applications non multithread, il existe une seule file pour toute l'application, contenant les événements qui ont été détectés mais pas encore traités. Les sources d'événements placent les événements dans la file d'attente afin qu'ils puissent être traités dans l'ordre aux moments appropriés pendant la boucle d'événements. La file d'attente d'événements garantit une discipline équitable de traitement des événements, de sorte qu'aucune source d'événement ne puisse affamer les autres. Elle permet également de sauvegarder les événements pour un traitement ultérieur. Les applications multithread fonctionnent de manière similaire, à la différence qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. Tcl_QueueEvent est utilisé (principalement par les sources d'événements) pour ajouter des événements à la file d'attente d'événements et Tcl_DeleteEvents est utilisé pour supprimer des événements de la file d'attente sans les traiter. Dans une application multithread, Tcl_QueueEvent ajoute un événement à la file d'attente du thread courant, et Tcl_ThreadQueueEvent ajoute un événement à une file d'attente dans un thread spécifique.
[3]
La boucle d'événements : afin de détecter et de traiter les événements, l'application entre dans une boucle qui attend que les événements se produisent, les place dans la file d'attente d'événements, puis les traite. La plupart des applications le feront en appelant la procédure Tcl_DoOneEvent, qui est décrite dans une entrée de manuel distincte.

La plupart des applications Tcl n'ont pas besoin de se soucier des détails internes du gestionnaire de notification Tcl. Cependant, le gestionnaire de notification est maintenant suffisamment flexible pour être redirigé soit vers une nouvelle plateforme, soit pour utiliser une boucle d'événements externe (telle que la boucle d'événements Motif, lorsque Tcl est intégrée dans une application Motif). Les procédures Tcl_WaitForEvent et Tcl_SetTimer sont normalement implémentées par Tcl, mais peuvent être remplacées par de nouvelles versions pour rediriger le gestionnaire de notification (Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler, et Tcl_DeleteFileHandler doivent également être remplacées ; voir CRÉATION D'UN NOUVEAU GESTIONNAIRE DE NOTIFICATION ci-dessous pour plus de détails). Les procédures Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode, et Tcl_SetServiceMode sont fournies pour aider à connecter la boucle d'événements Tcl à une boucle d'événements externe telle que celle de Motif.

BASES DU GESTIONNAIRE DE NOTIFICATION

La façon la plus simple de comprendre le fonctionnement du gestionnaire de notification est de considérer ce qui se passe lorsque Tcl_DoOneEvent est appelée. Tcl_DoOneEvent reçoit un argument flags qui indique quels types d'événements peuvent être traités et s'il faut bloquer ou non si aucun événement n'est prêt. Tcl_DoOneEvent effectue les actions suivantes :

[1]
Vérifie la file d'attente d'événements pour voir si elle contient des événements pouvant être traités. Si c'est le cas, traite le premier événement possible, le retire de la file d'attente et retourne. Pour ce faire, elle appelle Tcl_ServiceEvent et passe l'argument flags.
[2]
Prépare le blocage pour un événement. Pour ce faire, Tcl_DoOneEvent invoque une procédure setup dans chaque source d'événements. La source d'événements effectuera l'initialisation spécifique à la source d'événements et pourra appeler Tcl_SetMaxBlockTime pour limiter la durée pendant laquelle Tcl_WaitForEvent bloquera si aucun nouvel événement ne se produit.
[3]
Appelle Tcl_WaitForEvent. Cette procédure est implémentée différemment selon les plateformes ; elle attend qu'un événement se produise, en se basant sur les informations fournies par les sources d'événements. Elle peut entraîner le blocage de l'application si timePtr spécifie un intervalle différent de 0. Tcl_WaitForEvent retourne lorsqu'un événement s'est produit, tel qu'un fichier devenant lisible ou l'expiration de l'intervalle donné par timePtr. S'il n'y a aucun événement pour lequel Tcl_WaitForEvent doit attendre, de sorte qu'elle bloquerait indéfiniment, alors elle retourne immédiatement et Tcl_DoOneEvent retourne 0.
[4]
Appelle une procédure check dans chaque source d'événements. La procédure check détermine si des événements intéressants pour cette source se sont produits. Si c'est le cas, les événements sont ajoutés à la file d'attente d'événements.
[5]
Vérifie la file d'attente d'événements pour voir si elle contient des événements qui peuvent être traités. Si c'est le cas, elle appelle Tcl_ServiceEvent et retourne 1, sinon elle retourne 0.

CRÉER UNE NOUVELLE SOURCE D'ÉVÉNEMENTS

Une source d'événements se compose de trois procédures invoquées par le gestionnaire d'événements, plus des procédures C supplémentaires qui sont invoquées par le code de niveau supérieur pour organiser les rappels d'événements basés sur des événements. Les trois procédures invoquées par le gestionnaire d'événements consistent en les procédures de configuration et de vérification décrites précédemment, plus une procédure supplémentaire qui est invoquée lorsqu'un événement est retiré de la file d'attente des événements pour traitement.

La procédure Tcl_CreateEventSource crée une nouvelle source d'événements. Ses arguments spécifient les procédures de configuration et de vérification pour la source d'événements. SetupProc doit correspondre au prototype suivant :

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

L'argument clientData sera le même que l'argument clientData de Tcl_CreateEventSource ; il est généralement utilisé pour pointer vers des informations privées gérées par la source d'événements. L'argument flags sera le même que l'argument flags passé à Tcl_DoOneEvent, sauf s'il est 0 (auquel cas Tcl_DoOneEvent remplace 0 par TCL_ALL_EVENTS). Flags indique quels types d'événements doivent être pris en compte ; si le bit correspondant à cette source d'événements n'est pas défini, la source d'événements doit retourner immédiatement sans rien faire. Par exemple, la source d'événements de fichier vérifie le bit TCL_FILE_EVENTS.

SetupProc doit s'assurer que l'application est réveillée lorsque des événements du type désiré se produisent. Ceci est généralement fait de manière dépendante de la plateforme. Par exemple, sous Unix, une source d'événements pourrait appeler Tcl_CreateFileHandler ; sous Windows, elle pourrait demander une notification avec un événement Windows. Pour les sources d'événements basées sur des minuteries, comme les événements temporels ou tout événement sondé, la source d'événements peut appeler Tcl_SetMaxBlockTime pour forcer l'application à se réveiller après un temps spécifié, même s'il n'y a pas d'événements. Si aucune source d'événements n'appelle Tcl_SetMaxBlockTime, Tcl_WaitForEvent attendra autant que nécessaire qu'un événement se produise ; sinon, elle n'attendra que l'intervalle le plus court entre les appels à Tcl_SetMaxBlockTime effectués par l'une des sources d'événements. Si la source d'événements sait qu'elle a déjà des événements prêts à signaler, elle peut demander un temps de blocage maximal de zéro. Par exemple, la procédure de configuration de l'événement X vérifie s'il y a déjà des événements en file d'attente. S'il y en a, elle appelle Tcl_SetMaxBlockTime avec un temps de blocage maximal nul afin que Tcl_WaitForEvent ne se bloque pas s'il n'y a pas de nouvelles données sur la connexion X. L'argument timePtr de Tcl_WaitForEvent pointe vers une structure décrivant un intervalle de temps en secondes et microsecondes :

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

Le champ usec doit être inférieur à 1 000 000.

Les informations fournies à Tcl_SetMaxBlockTime ne sont utilisées que pour le prochain appel à Tcl_WaitForEvent ; elles sont ignorées après le retour de Tcl_WaitForEvent. La prochaine fois qu'une attente d'événements sera effectuée, chaque procédure de configuration des sources d'événements sera réinvoquée, et elles pourront spécifier de nouvelles données pour cette attente d'événements.

Si l'application utilise une boucle d'événements externe au lieu de Tcl_DoOneEvent, les sources d'événements peuvent avoir besoin d'appeler Tcl_SetMaxBlockTime à d'autres moments. Par exemple, si un nouveau gestionnaire d'événements est enregistré qui doit surveiller des événements, la source d'événements peut appeler Tcl_SetMaxBlockTime pour définir un temps de blocage maximal nul, forçant ainsi la boucle d'événements externe à appeler Tcl. Dans ce cas, Tcl_SetMaxBlockTime appelle Tcl_SetTimer avec l'intervalle le plus court vu depuis le dernier appel à Tcl_DoOneEvent ou Tcl_ServiceAll.

En plus de la procédure générale Tcl_SetMaxBlockTime, d'autres procédures spécifiques à la plateforme peuvent être disponibles pour setupProc, si des informations supplémentaires sont nécessaires à Tcl_WaitForEvent sur cette plateforme. Par exemple, sur les systèmes Unix, l'interface Tcl_CreateFileHandler peut être utilisée pour attendre des événements de fichier.

La deuxième procédure fournie par chaque source d'événements est sa procédure de vérification, indiquée par l'argument checkProc de Tcl_CreateEventSource. CheckProc doit correspondre au prototype suivant :

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Les arguments de cette procédure sont les mêmes que ceux de setupProc. CheckProc est appelée par Tcl_DoOneEvent après qu'elle a attendu les événements. On suppose qu'au moins une source d'événements est prête à placer un événement dans la file d'attente. Tcl_DoOneEvent appelle chaque source d'événements dans l'ordre, de sorte que toutes aient une chance de placer les événements prêts. La procédure de vérification fait deux choses. Premièrement, elle doit vérifier s'il y a des événements qui se sont produits. Différentes sources d'événements le font différemment.

Si une source d'événements détecte un événement intéressant, elle doit ajouter l'événement à la file d'attente Tcl. Pour ce faire, la source d'événements appelle Tcl_QueueEvent. L'argument evPtr est un pointeur vers une structure allouée dynamiquement qui contient l'événement (voir ci-dessous pour plus d'informations sur la gestion de la mémoire). Chaque source d'événements peut définir sa propre structure d'événement avec des informations pertinentes pour cette source d'événements. Cependant, le premier élément de la structure doit être une structure de type Tcl_Event, et le pointeur vers cette structure est utilisé lors de la communication entre la source d'événements et le reste du gestionnaire d'événements. Un Tcl_Event a la définition suivante :

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La source d'événements doit remplir le champ proc de la structure d'événement avant d'appeler Tcl_QueueEvent. Le nextPtr est utilisé pour chaîner les événements dans la file d'attente et ne doit pas être modifié par la source d'événements.

Un événement peut être ajouté à la file d'attente dans l'une des trois positions, selon l'argument position de Tcl_QueueEvent :

TCL_QUEUE_TAIL
Ajouter l'événement à la fin de la file d'attente, de sorte que tous les événements en attente soient traités en premier. C'est presque toujours l'endroit approprié pour les nouveaux événements.
TCL_QUEUE_HEAD
Ajouter l'événement au début de la file d'attente, de sorte qu'il soit traité avant tous les autres événements dans la file d'attente.
TCL_QUEUE_MARK
Ajouter l'événement au début de la file d'attente, sauf s'il y a d'autres événements au début de la file d'attente qui ont la position TCL_QUEUE_MARK ; si c'est le cas, ajouter le nouvel événement juste après tous les autres événements TCL_QUEUE_MARK. Cette valeur de position est utilisée pour insérer une séquence ordonnée d'événements au début de la file d'attente, comme une série d'événements Enter et Leave synthétisés lors d'une opération de capture ou de libération dans Tk.

Lorsqu'il est temps de traiter un événement de la file d'attente (étapes 1 et 4 ci-dessus), Tcl_ServiceEvent invoquera le proc spécifié dans la première structure de Tcl_Event qui se trouve dans la file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

Le premier argument de proc est un pointeur vers l'événement, qui sera le même que le premier argument de l'appel à Tcl_QueueEvent qui a ajouté l'événement à la file d'attente. Le deuxième argument de proc est l'argument flags de l'appel actuel à Tcl_ServiceEvent ; celui-ci est utilisé par la source d'événements pour retourner immédiatement si ses événements ne sont pas pertinents.

Il incombe à proc de gérer l'événement, généralement en invoquant une ou plusieurs commandes Tcl ou des rappels de niveau C. Une fois que la source d'événements a terminé de gérer l'événement, elle retourne 1 pour indiquer que l'événement peut être retiré de la file d'attente. Si pour une raison quelconque la source d'événements décide que l'événement ne peut pas être traité à ce moment-là, elle peut retourner 0 pour indiquer que l'événement doit être différé pour être traité plus tard ; dans ce cas, Tcl_ServiceEvent passe à la prochaine entrée de la file d'attente et tente de la traiter. Il existe plusieurs raisons pour lesquelles une source d'événements pourrait différer un événement. Une possibilité est que les événements de ce type soient exclus par l'argument flags. Par exemple, la source d'événements de fichier retourne toujours 0 si le bit TCL_FILE_EVENTS n'est pas défini dans flags. Un autre exemple de décalage d'événements se produit dans Tk si Tk_RestrictEvents a été invoqué pour décaler certains types d'événements de fenêtre.

Lorsque proc retourne 1, Tcl_ServiceEvent retirera l'événement de la file d'attente des événements et libérera son stockage. Vous devez noter que le stockage d'un événement doit être alloué par la source d'événements (en utilisant Tcl_Alloc ou la macro Tcl ckalloc) avant d'appeler Tcl_QueueEvent, mais il sera libéré par Tcl_ServiceEvent, et non par la source d'événements.

Les applications multithreadées fonctionnent de manière similaire, à ceci près qu'il existe une file d'attente d'événements distincte pour chaque thread contenant un interpréteur Tcl. Appeler Tcl_QueueEvent dans les applications multithreadées ajoute un événement à la file d'attente du thread actuel. Pour ajouter un événement à la file d'attente d'un autre thread, utilisez Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent accepte comme argument un Tcl_ThreadId, qui identifie de manière unique un thread dans une application Tcl. Pour obtenir le Tcl_ThreadId du thread actuel, utilisez la procédure Tcl_GetCurrentThread. (Un thread devrait alors passer cet identifiant à d'autres threads afin qu'ils puissent ajouter des événements à sa file d'attente.) Après avoir ajouté un événement à la file d'attente d'un autre thread, il faut généralement appeler Tcl_ThreadAlert pour "réveiller" le gestionnaire d'événements de ce thread afin de l'alerter du nouvel événement.

Tcl_DeleteEvents peut être utilisé explicitement pour supprimer un ou plusieurs événements de la file d'attente des événements. Tcl_DeleteEvents appelle le proc pour chaque événement dans la file d'attente, supprimant ceux qui retournent 1. Les événements qui retournent 0 sont conservés dans la file d'attente. Proc doit correspondre au prototype suivant :

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

L'argument clientData sera le même que l'argument clientData de Tcl_DeleteEvent ; il est généralement utilisé pour pointer vers des informations privées gérées par la source d'événements.

ts ; il est typiquement utilisé pour pointer vers des informations privées gérées par la source d'événement. Le pointeur evPtr pointera vers l'événement suivant dans la file d'attente.

Tcl_DeleteEventSource supprime une source d'événement. Les arguments setupProc, checkProc et clientData doivent correspondre exactement à ceux fournis à Tcl_CreateEventSource pour que la source d'événement soit supprimée. Si aucune source de ce type n'existe, Tcl_DeleteEventSource n'a aucun effet.

CRÉATION D'UN NOUVEAU NOTIFIER

Le notifier se compose de toutes les procédures décrites dans cette entrée de manuel, plus Tcl_DoOneEvent et Tcl_Sleep, qui sont disponibles sur toutes les plateformes, et Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont spécifiques à Unix. La plupart de ces procédures sont génériques, dans le sens où elles sont identiques pour tous les notifiers. Cependant, aucune des procédures n'est indépendante du notifier : Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler et Tcl_ServiceModeHook. Pour prendre en charge une nouvelle plateforme ou pour intégrer Tcl à une boucle d'événements spécifique à une application, vous devez écrire de nouvelles versions de ces procédures.

Tcl_InitNotifier initialise l'état du notifier et renvoie un handle vers l'état du notifier. Tcl appelle cette procédure lors de l'initialisation d'un interpréteur Tcl. De même, Tcl_FinalizeNotifier arrête le notifier et est appelé par Tcl_Finalize lors de l'arrêt d'un interpréteur Tcl.

Tcl_WaitForEvent est la procédure la plus bas niveau du notifier ; elle est responsable de l'attente d'un événement « intéressant » ou de l'expiration d'un délai donné. Avant que Tcl_WaitForEvent ne soit invoqué, chacune des procédures de configuration des sources d'événements aura été appelée. L'argument timePtr à Tcl_WaitForEvent donne le temps maximum de blocage pour un événement, basé sur les appels à Tcl_SetMaxBlockTime effectués par les procédures de configuration et sur d'autres informations (telles que le bit TCL_DONT_WAIT dans flags).

Idéalement, Tcl_WaitForEvent ne devrait attendre qu'un événement se produise ; il ne devrait pas traiter l'événement de quelque manière que ce soit. Plus tard, les sources d'événements traiteront les événements bruts et créeront des Tcl_Events dans la file d'attente d'événements dans leurs procédures checkProc. Cependant, sur certaines plateformes (comme Windows), ce n'est pas possible ; les événements peuvent être traités dans Tcl_WaitForEvent, y compris la mise en file d'attente de Tcl_Events et plus encore (par exemple, des callbacks pour des widgets natifs peuvent être invoqués). La valeur de retour de Tcl_WaitForEvent doit être 0, 1 ou -1. Sur les plateformes comme Windows où les événements sont traités dans Tcl_WaitForEvent, une valeur de retour de 1 signifie qu'il peut y avoir encore des événements en attente qui n'ont pas été traités. C'est un signe pour l'appelant qu'il doit appeler à nouveau Tcl_WaitForEvent s'il souhaite que tous les événements en attente soient traités. Une valeur de retour de 0 signifie qu'un nouvel appel à Tcl_WaitForEvent n'aura aucun effet : soit c'est une plateforme où Tcl_WaitForEvent attend simplement sans traiter d'événements, soit Tcl_WaitForEvent sait avec certitude qu'il n'y a pas d'événements supplémentaires à traiter (par exemple, il est revenu parce que le temps s'est écoulé). Enfin, une valeur de retour de -1 signifie que la boucle d'événements n'est plus opérationnelle et que l'application devrait probablement se terminer. Sous Windows, cela se produit lorsqu'un message WM_QUIT est reçu ; sous Unix, cela se produit lorsque Tcl_WaitForEvent aurait attendu éternellement car il n'y avait pas de sources d'événements actives et le délai d'attente était infini.

Tcl_AlertNotifier est utilisé dans les applications multithreadées pour permettre à n'importe quel thread de « réveiller » le notifier afin de l'alerter de nouveaux événements dans sa file d'attente. Tcl_AlertNotifier nécessite en argument le handle du notifier renvoyé par Tcl_InitNotifier.

Si le notifier doit être utilisé avec une boucle d'événements externe, il doit également prendre en charge l'interface Tcl_SetTimer. Tcl_SetTimer est appelé par Tcl_SetMaxBlockTime chaque fois que le temps de blocage maximum a été réduit. Tcl_SetTimer doit organiser la boucle d'événements externe pour qu'elle appelle Tcl_ServiceAll après l'intervalle spécifié, même si aucun événement ne s'est produit. Cette interface est nécessaire car Tcl_WaitForEvent n'est pas appelé lorsqu'il y a une boucle d'événements externe. Si le notifier doit uniquement être utilisé à partir de Tcl_DoOneEvent, alors Tcl_SetTimer n'a pas besoin de faire quoi que ce soit.

Tcl_ServiceModeHook est appelé par la partie indépendante de la plateforme du notifier lorsque le code client effectue un appel à Tcl_SetServiceMode. Ce hook est fourni pour prendre en charge les systèmes d'exploitation qui nécessitent une gestion spéciale des événements lorsque l'application est dans une boucle modale (le notifier Windows, par exemple, utilise ce hook pour créer une fenêtre de communication).

Sur les systèmes Unix, la source d'événements de fichier nécessite également le support du notifier. La source d'événements de fichier se compose des procédures Tcl_CreateFileHandler et Tcl_DeleteFileHandler, qui sont décrites dans la page de manuel Tcl_CreateFileHandler.

Les interfaces Tcl_Sleep et Tcl_DoOneEvent sont décrites dans leurs pages de manuel respectives.

La manière la plus simple de créer un nouveau notifier est de consulter le code d'un notifier existant, tel que les fichiers unix/tclUnixNotfy.c ou win/tclWinNotify.c dans la distribution source de Tcl.

REMPLACEMENT DU NOTIFIER

Un notifier qui a été écrit conformément aux conventions ci-dessus peut également être installé dans un processus en cours d'exécution à la place du notifier standard. Ce mécanisme est utilisé de telle sorte qu'un exécutable unique puisse être utilisé (avec le notifier standard) comme programme autonome et réutilisé (avec un notifier de remplacement dans une extension chargeable) comme extension à un autre programme, tel qu'un plugin de navigateur Web.

Pour ce faire, l'extension effectue un appel à Tcl_SetNotifier en passant un pointeur vers une structure de données Tcl_NotifierProcs. La structure a la disposition suivante :

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Suite à l'appel à Tcl_SetNotifier, les pointeurs fournis dans la structure Tcl_NotifierProcs remplacent tout notifier qui avait été installé dans le processus.

Il est extraordinairement imprudent de remplacer un notifier en cours d'exécution. Normalement, Tcl_SetNotifier doit être appelé au moment de l'initialisation du processus, avant le premier appel à Tcl_InitNotifier.

BOUCLES D'ÉVÉNEMENTS EXTERNES

Les interfaces du notifier sont conçues pour que Tcl puisse être embarqué dans des applications qui ont leurs propres boucles d'événements privées. Dans ce cas, l'application n'appelle pas Tcl_DoOneEvent sauf dans le cas de boucles d'événements récursives telles que les appels aux commandes Tcl update ou vwait. La plupart du temps est passé dans la boucle d'événements externe de l'application. Dans ce cas, le notifier doit organiser la boucle d'événements externe pour qu'elle rappelle Tcl lorsque quelque chose se produit sur les différentes sources d'événements Tcl. Ces rappels doivent organiser la mise en place des événements Tcl appropriés dans la file d'attente d'événements Tcl.

Étant donné que la boucle d'événements externe n'appelle pas Tcl_DoOneEvent régulièrement, il incombe au notifier d'organiser l'appel de Tcl_ServiceEvent chaque fois qu'il y a des événements en attente dans la file d'attente d'événements Tcl. Le moyen le plus simple de le faire est d'invoquer Tcl_ServiceAll à la fin de chaque rappel de la boucle d'événements externe. Cela garantira que toutes les sources d'événements sont interrogées, que tous les événements mis en file d'attente sont traités et que tous les gestionnaires inactifs en attente sont traités avant de redonner le contrôle à l'application. En outre, les sources d'événements qui doivent interroger les événements peuvent appeler Tcl_SetMaxBlockTime pour forcer la boucle d'événements externe à appeler Tcl même si aucun événement n'est disponible dans la file d'attente d'événements du système.

En tant qu'effet secondaire du traitement des événements détectés dans la boucle d'événements externe principale, Tcl peut invoquer Tcl_DoOneEvent pour démarrer une boucle d'événements récursive dans des commandes comme vwait. Tcl_DoOneEvent invoquera la boucle d'événements externe, ce qui entraînera des rappels comme décrit dans le paragraphe précédent, ce qui entraînera des appels à Tcl_ServiceAll. Cependant, dans ces cas, il est indésirable de traiter les événements dans Tcl_ServiceAll. Le traitement des événements là est inutile car le contrôle reviendra immédiatement à la boucle d'événements externe et donc à Tcl_DoOneEvent, qui peut traiter les événements elle-même. De plus, Tcl_DoOneEvent est censé traiter un seul événement, tandis que Tcl_ServiceAll traite normalement tous les événements en attente. Pour gérer cette situation, Tcl_DoOneEvent définit un indicateur pour Tcl_ServiceAll qui lui fait retourner sans traiter d'événements. Cet indicateur est appelé le *mode de service* ; Tcl_DoOneEvent le rétablira à sa valeur précédente avant de retourner.

Dans certains cas, cependant, il peut être nécessaire que Tcl_ServiceAll traite les événements même lorsqu'il a été invoqué à partir de Tcl_DoOneEvent. Cela se produit lorsqu'il y a encore une autre boucle d'événements récursive invoquée via un gestionnaire d'événements appelé par Tcl_DoOneEvent (tel qu'un qui fait partie d'un widget natif). Dans ce cas, Tcl_DoOneEvent peut ne pas avoir la possibilité de traiter les événements, donc Tcl_ServiceAll doit tous les traiter. Toute boucle d'événements récursive qui appelle une boucle d'événements externe au lieu de Tcl_DoOneEvent doit réinitialiser le mode de service afin que tous les événements soient traités dans Tcl_ServiceAll. Ceci est fait en appelant la procédure Tcl_SetServiceMode. Si Tcl_SetServiceMode est passé TCL_SERVICE_NONE, alors les appels à Tcl_ServiceAll retourneront immédiatement sans traiter d'événements. Si Tcl_SetServiceMode est passé TCL_SERVICE_ALL, alors les appels à Tcl_ServiceAll se comporteront normalement. Tcl_SetServiceMode renvoie la valeur précédente du mode de service, qui doit être restaurée à la sortie de la boucle récursive. Tcl_GetServiceMode renvoie la valeur actuelle du mode de service.

Tcl_DeleteEvents.3 — Documentation Tcl

Tcl_DeleteEvents

Supprime des événements de la boucle d'événements

SYNOPSE

#include <tcl.h>

void
Tcl_DeleteEvents(
    Tcl_Event *eventsToRemove
);

ARGUMENTS

eventsToRemove (in)
Un pointeur vers une liste chaînée d'événements à supprimer de la file d'attente d'événements. Les événements doivent avoir été créés par Tcl_AddEventToQueue. La liste chaînée doit se terminer par un pointeur NULL.

INTRODUCTION

La procédure Tcl_DeleteEvents est utilisée pour supprimer un ou plusieurs événements de la file d'attente d'événements de Tcl. Ceci est utile lorsque vous n'avez plus besoin qu'un événement soit traité, par exemple, lorsque vous supprimez une source d'événements ou que vous annulez une opération asynchrone.

COMMENT ÇA MARCHE

Lorsque vous ajoutez un événement à la file d'attente d'événements de Tcl en utilisant Tcl_AddEventToQueue, l'événement est placé dans une liste chaînée interne. Tcl_DeleteEvents prend en paramètre un pointeur vers la tête d'une liste chaînée d'événements que vous souhaitez supprimer. Il parcourt cette liste et supprime chaque événement spécifié de la file d'attente d'événements principale de Tcl.

Il est important de noter que Tcl_DeleteEvents ne libère pas la mémoire allouée pour les événements supprimés. Vous êtes responsable de libérer la mémoire de vos propres structures d'événements après qu'ils aient été supprimés de la file d'attente et traités, ou après qu'ils aient été retirés de la file d'attente par Tcl_DeleteEvents s'ils n'ont jamais été traités.

EXEMPLES

Voici un exemple simple de suppression d'un seul événement de la file d'attente : 

Tcl_Event *myEventPtr = ...; // Obtenez un pointeur vers l'événement à supprimer
Tcl_Event eventList[2];

eventList[0] = *myEventPtr;
eventList[1].proc = NULL; // Marque la fin de la liste

Tcl_DeleteEvents(eventList);
// Maintenant, myEventPtr n'est plus dans la file d'attente d'événements.
// Vous êtes responsable de libérer la mémoire de myEventPtr si nécessaire.

Pour supprimer plusieurs événements : 

Tcl_Event *event1 = ...;
Tcl_Event *event2 = ...;
Tcl_Event eventList[3];

eventList[0] = *event1;
eventList[1] = *event2;
eventList[2].proc = NULL; // Marque la fin de la liste

Tcl_DeleteEvents(eventList);
// event1 et event2 ne sont plus dans la file d'attente.
