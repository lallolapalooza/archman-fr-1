TAP::Harness(3perl) Guide du programmeur Perl TAP::Harness(3perl)

NOM

TAP::Harness - Exécuter des scripts de test avec statistiques

VERSION

Version 3.50

DESCRIPTION

Ceci est un simple appareil de test qui permet d'exécuter des tests et d'agréger automatiquement les résultats et de les afficher sur STDOUT.

SYNOPIS

use TAP::Harness;
my $harness = TAP::Harness->new( \%args );
$harness->runtests(@tests);

MÉTHODES

Méthodes de classe

"new"

my %args = (
   verbosity => 1,
   lib     => [ 'lib', 'blib/lib', 'blib/arch' ],
)
my $harness = TAP::Harness->new( \%args );

Le constructeur renvoie un nouvel objet "TAP::Harness". Il accepte un hashref optionnel dont les clés autorisées sont :

  • "verbosity"

    Définit le niveau de verbosité :

     1   verbose        Affiche les résultats de chaque test sur STDOUT.
 0   normal
-1   quiet          Supprime une partie de la sortie des tests (principalement les échecs
                    pendant l'exécution des tests).
-2   really quiet   Supprime tout sauf le résumé des tests.
-3   silent         Supprime tout.
  • "timer"

    Ajoute le temps d'exécution de chaque test à la sortie. Utilise Time::HiRes si disponible.

  • "failures"

    Affiche les échecs de tests (ceci est une opération nulle si "verbose" est sélectionné).

  • "comments"

    Affiche les commentaires de tests (ceci est une opération nulle si "verbose" est sélectionné).

  • "show_count"

    Met à jour le compteur de tests en cours pendant l'exécution.

  • "normalize"

    Mis à une valeur vraie pour normaliser le TAP qui est émis dans les modes verbeux.

  • "lib"

    Accepte une valeur scalaire ou une référence de tableau de valeurs scalaires indiquant quels chemins pour les bibliothèques autorisées doivent être inclus si des tests Perl sont exécutés. Naturellement, cela n'a de sens que dans le contexte de tests écrits en Perl.

  • "switches"

    Accepte une valeur scalaire ou une référence de tableau de valeurs scalaires indiquant quels commutateurs doivent être inclus si des tests Perl sont exécutés. Naturellement, cela n'a de sens que dans le contexte de tests écrits en Perl.

  • "test_args"

    Une référence à un tableau d'arguments de style @INC à passer à chaque programme de test.

    test_args => ['foo', 'bar'],

    si vous souhaitez passer des arguments différents à chaque test, vous devriez passer une table d'associations (hashref) de tableaux, indexée par l'alias de chaque test :

    test_args => {
  mon_test    => ['foo', 'bar'],
  autre_test => ['baz'],
}
  • "color"

    Tente de produire une sortie en couleur.

  • "exec"

    Généralement, les tests Perl sont exécutés via ceci. Cependant, tout ce qui produit du TAP est acceptable. Vous pouvez utiliser cet argument pour spécifier le nom du programme (et les commutateurs optionnels) pour exécuter vos tests :

    exec => ['/usr/bin/ruby', '-w']

    Vous pouvez également passer une référence de sous-routine afin de déterminer et de renvoyer le programme approprié à exécuter en fonction d'un script de test donné. La référence de sous-routine doit attendre l'objet TAP::Harness lui-même comme premier argument, et le nom de fichier comme second argument. Elle doit renvoyer une référence de tableau contenant la commande à exécuter et incluant le nom du fichier de test. Elle peut également simplement renvoyer "undef", auquel cas TAP::Harness se rabattra sur l'exécution du script de test en Perl :

    exec => sub {
    my ( $harness, $test_file ) = @_;
    # Laisser les tests Perl s'exécuter.
    return undef if $test_file =~ /[.]t$/;
    return [ qw( /usr/bin/ruby -w ), $test_file ]
      if $test_file =~ /[.]rb$/;
  }

    Si la sous-routine renvoie un scalaire avec un saut de ligne ou un descripteur de fichier, il sera interprété comme du TAP brut ou comme un flux TAP, respectivement.

  • "merge"

    Si "merge" est vrai, l'appareil créera des analyseurs qui fusionnent STDOUT et STDERR ensemble pour tous les processus qu'ils démarrent.

  • "sources"

    NOUVEAU depuis la version 3.18.

    Si défini, "sources" doit être un hashref contenant les noms des TAP::Parser::SourceHandlers à charger et/ou configurer. Les valeurs sont un hash de configuration qui sera accessible aux gestionnaires de source via "config_for" dans TAP::Parser::Source.

    Par exemple :

    sources => {
  Perl => { exec => '/path/to/custom/perl' },
  File => { extensions => [ '.tap', '.txt' ] },
  MyCustom => { some => 'config' },
}

    Le paramètre "sources" affecte la manière dont les paramètres "source", "tap" et "exec" sont gérés.

    Pour plus de détails, voir le paramètre "sources" dans "new" dans TAP::Parser, TAP::Parser::Source, et TAP::Parser::IteratorFactory.

  • "aggregator_class"

    Le nom de la classe à utiliser pour agréger les résultats des tests. La valeur par défaut est TAP::Parser::Aggregator.

  • "version"

    NOUVEAU depuis la version 3.22.

    Suppose cette version TAP pour TAP::Parser au lieu de la version TAP par défaut 12.

  • "formatter_class"

    Le nom de la classe à utiliser pour formater la sortie. La valeur par défaut est TAP::Formatter::Console, ou TAP::Formatter::File si la sortie n'est pas un TTY.

  • "multiplexer_class"

    Le nom de la classe à utiliser pour multiplexer les tests lors des tests parallèles. La valeur par défaut est TAP::Parser::Multiplexer.

  • "parser_class"

    Le nom de la classe à utiliser pour analyser le TAP. La valeur par défaut est TAP::Parser.

  • "scheduler_class"

    Le nom de la classe à utiliser pour planifier l'exécution des tests. La valeur par défaut est TAP::Parser::Scheduler.

  • "formatter"

    Si défini, "formatter" doit être un objet capable de formater la sortie TAP. Voir TAP::Formatter::Console pour un exemple.

  • "errors"

    Si des erreurs d'analyse sont trouvées dans la sortie TAP, une note sera faite dans le rapport de résumé. Pour voir toutes les erreurs d'analyse, définissez cet argument sur vrai :

    errors => 1
  • "directives"

    Si défini sur une valeur vraie, seuls les résultats de test avec des directives seront affichés. Ceci remplace d'autres paramètres tels que "verbose" ou "failures".

  • "ignore_exit"

    Si défini sur une valeur vraie, demande à "TAP::Parser" d'ignorer le statut de sortie et d'attente des scripts de test.

  • "jobs"

    Le nombre maximum de tests parallèles à exécuter à la fois. Quels tests peuvent être exécutés en parallèle est contrôlé par "rules". La valeur par défaut est d'exécuter un seul test à la fois.

  • "rules"

    Une référence à une table d'associations (hashref) de règles qui contrôlent quels tests peuvent être exécutés en parallèle. Si aucune règle n'est déclarée et que CPAN::Meta::YAML est disponible, "TAP::Harness" tente de charger les règles à partir d'un fichier YAML spécifié par le paramètre "rulesfile". Si aucun fichier de règles n'existe, la valeur par défaut est que tous les tests sont éligibles pour être exécutés en parallèle.

# Exécute tous les tests en séquence, sauf ceux commençant par "p"
$harness->rules({
    par => 't/p*.t'

# Fichier YAML équivalent
---

    seq => [
              { seq => 't/p*.t' },
              { par => '**'     },
           ],
});
# Fichier YAML équivalent

    - par: **
# Exécute certains tests de démarrage en séquence, puis certains tests parallèles, puis certains

$harness->rules({
    seq => [
        { seq => 't/startup/*.t' },
        { par => ['t/a/*.t','t/b/*.t','t/c/*.t'], }
        { seq => 't/shutdown/*.t' },
    ],
});
# Fichier YAML équivalent
---
seq:
    - seq: t/startup/*.t
    - par:
        - t/a/*.t
        - t/b/*.t
        - t/c/*.t
    - seq: t/shutdown/*.t

Il s'agit d'une fonctionnalité expérimentale et l'interface peut changer.

  • "rulesfiles"

    Spécifie où trouver un fichier YAML de règles de planification de tests. Si non fourni, il recherche un fichier par défaut à utiliser. Il recherche d'abord un fichier spécifié dans la variable d'environnement "HARNESS_RULESFILE", puis il recherche testrules.yml puis t/testrules.yml.

  • "stdout"

    Un descripteur de fichier pour capturer la sortie standard.

  • "trap"

    Tente d'afficher des informations récapitulatives si l'exécution est interrompue par SIGINT (Ctrl-C).

    • Toutes les clés pour lesquelles la valeur est "undef" seront ignorées.

    Méthodes d'instance

    "runtests"

    $harness->runtests(@tests);

    Accepte un tableau de @tests à exécuter. Il devrait généralement s'agir des noms de fichiers de test, mais ce n'est pas obligatoire. Chaque élément de @tests sera passé à TAP::Parser::new() en tant que "source". Voir TAP::Parser pour plus d'informations.

    Il est possible de fournir des alias qui seront affichés à la place du nom du test en fournissant le test comme référence à un tableau contenant "[ $test, $alias ]" :

    $harness->runtests( [ 't/foo.t', 'Foo Une fois' ],
                    [ 't/foo.t', 'Foo Deux fois' ] );

    Normalement, il est une erreur de tenter d'exécuter le même test deux fois. Les alias vous permettent de surmonter cette limitation en donnant un nom unique à chaque exécution du test.

    Les tests seront exécutés dans l'ordre où ils sont trouvés.

    Si la variable d'environnement "PERL_TEST_HARNESS_DUMP_TAP" est définie, elle doit nommer un répertoire dans lequel une copie du TAP brut pour chaque test sera écrite. Le TAP est écrit dans des fichiers nommés pour chaque test. Des sous-répertoires seront créés si nécessaire.

    Retourne un TAP::Parser::Aggregator contenant les résultats des tests.

    "summary"

    $harness->summary( $aggregator );

    Affiche le résumé d'un TAP::Parser::Aggregator.

    "aggregate_tests"

    $harness->aggregate_tests( $aggregate, @tests );

    Exécute les tests nommés et affiche un résumé des résultats. Les tests seront exécutés dans l'ordre où ils sont trouvés.

    Les résultats des tests seront ajoutés à l'agrégateur fourni TAP::Parser::Aggregator. "aggregate_tests" peut être appelé plusieurs fois pour exécuter plusieurs ensembles de tests. Plusieurs instances de "Test::Harness" peuvent être utilisées pour passer des résultats à un seul agrégateur afin que différentes parties d'une suite de tests complexe puissent être exécutées à l'aide de différents paramètres de "TAP::Harness". Ceci est utile, par exemple, lorsque certains tests doivent s'exécuter en parallèle mais que d'autres ne conviennent pas à une exécution parallèle.

    my $formatter   = TAP::Formatter::Console->new;
my $ser_harness = TAP::Harness->new( { formatter => $formatter } );
my $par_harness = TAP::Harness->new(
    {   formatter => $formatter,
        jobs      => 9
    }
);
my $aggregator = TAP::Parser::Aggregator->new;
$aggregator->start();
$ser_harness->aggregate_tests( $aggregator, @ser_tests );
$par_harness->aggregate_tests( $aggregator, @par_tests );
$aggregator->stop();
$formatter->summary($aggregator);

    Notez que pour des exigences de test plus simples, il sera souvent possible de remplacer le code ci-dessus par un seul appel à "runtests".

    Chaque élément du tableau @tests est soit :

    • le nom source d'un test à exécuter
    • une référence à un tableau [ nom source, nom d'affichage ]

    Dans le cas d'une suite de tests Perl, les *noms sources* sont généralement simplement les noms de fichiers des scripts de test à exécuter.

    Lorsque vous fournissez un nom d'affichage distinct, il devient possible d'exécuter un test plus d'une fois ; le nom d'affichage est effectivement l'alias par lequel le test est connu dans le système. Le système ne se soucie pas s'il exécute le même test plus d'une fois lorsque chaque invocation utilise un nom différent.

    "make_scheduler"

    Appelé par le système lorsque celui-ci a besoin de créer un TAP::Parser::Scheduler. Surchargez dans une sous-classe pour fournir un planificateur alternatif. "make_scheduler" reçoit la liste des tests passée à "aggregate_tests".

    "jobs"

    Obtient ou définit le nombre d'exécutions de tests concurrentes gérées par le système. Par défaut, cette valeur est de 1 ; pour les tests parallèles, elle doit être définie plus haut.

    "make_parser"

    Crée une nouvelle session d'analyseur et de formatage d'affichage. Typiquement utilisé et/ou surchargé dans les sous-classes.

    my ( $parser, $session ) = $harness->make_parser;

    "finish_parser"

    Termine l'utilisation d'un analyseur. Typiquement utilisé et/ou surchargé dans les sous-classes. L'analyseur n'est pas détruit à la suite de cela.

    CONFIGURATION

    "TAP::Harness" est conçu pour être facile à configurer.

    Plugins

    "TAP::Parser" plugins permettent de modifier la façon dont le TAP est *entré* et *sorti* de l'analyseur.

    Les TAP::Parser::SourceHandlers gèrent l'*entrée* du TAP. Vous pouvez les configurer et charger des gestionnaires personnalisés en utilisant le paramètre "sources" pour "new".

    Les TAP::Formatters gèrent la *sortie* du TAP. Vous pouvez charger des formateurs personnalisés en utilisant le paramètre "formatter_class" pour "new". Pour configurer un formateur, vous devez actuellement l'instancier en dehors de TAP::Harness et le passer avec le paramètre "formatter" à "new". Cela *pourrait* être résolu en ajoutant un paramètre *formatters* à "new" à l'avenir.

    "Module::Build"

    Module::Build version 0.30 prend en charge "TAP::Harness".

    Pour charger les plugins "TAP::Harness", vous devrez utiliser le paramètre "tap_harness_args" pour "new", typiquement depuis votre "Build.PL". Par exemple :

    Module::Build->new(
    module_name        => 'MyApp',
    test_file_exts     => [qw(.t .tap .txt)],
    use_tap_harness    => 1,
    tap_harness_args   => {
        sources => {
            MyCustom => {},
            File => {
                extensions => ['.tap', '.txt'],
            },
        },
        formatter_class => 'TAP::Formatter::HTML',
    },
    build_requires     => {
        'Module::Build' => '0.30',
        'TAP::Harness'  => '3.18',
    },
)->create_build_script;

    Voir "new"

    "ExtUtils::MakeMaker"

    ExtUtils::MakeMaker ne prend pas en charge TAP::Harness par défaut.

    "prove"

    prove prend en charge les plugins "TAP::Harness" et possède son propre système de plugins. Voir "FORMATTERS" dans prove, "SOURCE HANDLERS" dans prove et App::Prove pour plus de détails.

    ÉCRIRE DES PLUGINS

    Si vous ne pouvez pas configurer "TAP::Harness" pour faire ce que vous voulez, et que vous ne trouvez pas de plugin existant, envisagez d'en écrire un.

    Les deux principaux cas d'utilisation pris en charge par TAP::Harness pour les plugins sont l'*entrée* et la *sortie* :

    Personnaliser comment le TAP est entré dans l'analyseur
    Pour ce faire, vous pouvez soit étendre un TAP::Parser::SourceHandler existant, soit écrire le vôtre. C'est une API assez simple, et ils peuvent être chargés et configurés à l'aide du paramètre "sources" à "new".
    Personnaliser comment les résultats du TAP sont générés par l'analyseur
    Pour ce faire, vous pouvez soit étendre un TAP::Formatter existant, soit écrire le vôtre. L'écriture de formateurs est un peu plus complexe que l'écriture d'un SourceHandler, car vous devrez comprendre l'API TAP::Parser. Un bon point de départ est de comprendre le fonctionnement de "aggregate_tests".

    Les formateurs personnalisés peuvent être chargés et configurés en utilisant le paramètre "formatter_class" à "new".

    SOUS-CLASSEMENT

    Si vous ne parvenez pas à configurer "TAP::Harness" pour faire exactement ce que vous voulez, et écrire un p TAP::Harness(3pm)

    TAP::Harness(3pm)

    NOM

    TAP::Harness - Un greffon de test de base pour l'API TAP

    VERSION

    1.000

    DESCRIPTION

    TAP::Harness est une classe qui exécute des tests en Perl à l'aide du protocole TAP (Test::Harness).

    Il est conçu pour être le greffon par défaut pour l'utilitaire "prove". Bien qu'il puisse être utilisé directement, il est beaucoup plus couramment utilisé via l'utilitaire "prove".

    SYNOPSIS

        use TAP::Harness;
    my $harness = TAP::Harness->new({
        jobs => 4,
        # ... d'autres options
    });
    $harness->runtests(@tests);

    MÉTHODES

    Voici les méthodes que vous pourriez souhaiter substituer si vous souhaitez sous-classer "TAP::Harness".

    "new"
    "runtests"
    "summary"

    CONFIGURATION

    Lorsque vous sous-classez TAP::Harness, vous pouvez fournir votre propre méthode "new". Elle devrait accepter un seul argument, un hachage de configuration. L'hachage de configuration est basé sur celui utilisé par TAP::Parser, mais peut avoir des clés supplémentaires.

    Les clés courantes incluent:

    "jobs"
    Le nombre de tests parallèles à exécuter.
    "execdir"
    Le répertoire à partir duquel exécuter les tests.
    "merge"
    Un hachage de spécification de greffon pour fusionner les sorties.
    "lib"
    Un tableau de chemins à ajouter à "@INC".
    "script_args"
    Un tableau d'arguments à passer à chaque script de test.

    ÉCRITURE DE GREFFONS

    Si l'extension du greffon n'est pas une option, envisagez de l'étendre. Il est conçu pour être (principalement) facile à sous-classer, bien que les cas où la sous-classification est nécessaire devraient être rares.

    REMPLACEMENT

    Si vous aimez l'utilitaire "prove" et TAP::Parser mais que vous voulez votre propre greffon, tout ce que vous avez à faire est d'en écrire un et de fournir les méthodes "new" et "runtests". Vous pouvez ensuite utiliser l'utilitaire "prove" comme ceci:

    prove --harness My::Test::Harness

    Notez que bien que "prove" accepte une liste de tests (ou d'éléments à tester), "new" a un ensemble d'arguments assez riche. Vous voudrez probablement lire attentivement ce code pour voir comment tous ces arguments sont utilisés.
