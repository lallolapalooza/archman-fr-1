NOM

SELECT, TABLE, WITH — récupérer des lignes d'une table ou d'une vue

SYNTAXE

[ WITH [ RECURSIVE ] requete_with [, ...] ]
SELECT [ ALL | DISTINCT [ ON ( expression [, ...] ) ] ]
    [ { * | expression [ [ AS ] nom_sortie ] } [, ...] ]
    [ FROM element_from [, ...] ]
    [ WHERE condition ]
    [ GROUP BY [ ALL | DISTINCT ] element_groupement [, ...] ]
    [ HAVING condition ]
    [ WINDOW nom_fenetre AS ( definition_fenetre ) [, ...] ]
    [ { UNION | INTERSECT | EXCEPT } [ ALL | DISTINCT ] select ]
    [ ORDER BY expression [ ASC | DESC | USING operateur ] [ NULLS { FIRST | LAST } ] [, ...] ]
    [ LIMIT { nombre | ALL } ]
    [ OFFSET debut [ ROW | ROWS ] ]
    [ FETCH { FIRST | NEXT } [ nombre ] { ROW | ROWS } { ONLY | WITH TIES } ]
    [ FOR { UPDATE | NO KEY UPDATE | SHARE | KEY SHARE } [ OF reference_from [, ...] ] [ NOWAIT | SKIP LOCKED ] [...] ]
où element_from peut être l'un des suivants :
    [ ONLY ] nom_table [ * ] [ [ AS ] alias [ ( alias_colonne [, ...] ) ] ]
                [ TABLESAMPLE methode_echantillonnage ( argument [, ...] ) [ REPEATABLE ( graine ) ] ]
    [ LATERAL ] ( select ) [ [ AS ] alias [ ( alias_colonne [, ...] ) ] ]
    nom_requete_with [ [ AS ] alias [ ( alias_colonne [, ...] ) ] ]
    [ LATERAL ] nom_fonction ( [ argument [, ...] ] )
                [ WITH ORDINALITY ] [ [ AS ] alias [ ( alias_colonne [, ...] ) ] ]
    [ LATERAL ] nom_fonction ( [ argument [, ...] ] ) [ AS ] alias ( definition_colonne [, ...] )
    [ LATERAL ] nom_fonction ( [ argument [, ...] ] ) AS ( definition_colonne [, ...] )
    [ LATERAL ] ROWS FROM( nom_fonction ( [ argument [, ...] ] ) [ AS ( definition_colonne [, ...] ) ] [, ...] )
                [ WITH ORDINALITY ] [ [ AS ] alias [ ( alias_colonne [, ...] ) ] ]
    element_from type_jointure element_from { ON condition_jointure | USING ( colonne_jointure [, ...] ) [ AS alias_using_jointure ] }
    element_from NATURAL type_jointure element_from
    element_from CROSS JOIN element_from
et element_groupement peut être l'un des suivants :
    ( )
    expression
    ( expression [, ...] )
    ROLLUP ( { expression | ( expression [, ...] ) } [, ...] )
    CUBE ( { expression | ( expression [, ...] ) } [, ...] )
    GROUPING SETS ( element_groupement [, ...] )
et requete_with est :
    nom_requete_with [ ( nom_colonne [, ...] ) ] AS [ [ NOT ] MATERIALIZED ] ( select | values | insert | update | delete | merge )
        [ SEARCH { BREADTH | DEPTH } FIRST BY nom_colonne [, ...] SET nom_colonne_seq_recherche ]
        [ CYCLE nom_colonne [, ...] SET nom_colonne_marque_cycle [ TO valeur_marque_cycle DEFAULT valeur_par_defaut_marque_cycle ] USING nom_colonne_chemin_cycle ]
TABLE [ ONLY ] nom_table [ * ]

DESCRIPTION

SELECT récupère des lignes à partir de zéro ou plusieurs tables. Le traitement général de SELECT est le suivant :

1.Toutes les requêtes de la liste WITH sont calculées. Elles servent effectivement de tables temporaires qui peuvent être référencées dans la liste FROM. Une requête WITH référencée plus d'une fois dans FROM n'est calculée qu'une seule fois, sauf indication contraire avec NOT MATERIALIZED. (Voir Clause WITH ci-dessous.)
2.Tous les éléments de la liste FROM sont calculés. (Chaque élément de la liste FROM est une table réelle ou virtuelle.) Si plusieurs éléments sont spécifiés dans la liste FROM, ils sont combinés par produit cartésien. (Voir Clause FROM ci-dessous.)
3.Si la clause WHERE est spécifiée, toutes les lignes qui ne satisfont pas à la condition sont éliminées de la sortie. (Voir Clause WHERE ci-dessous.)
4.Si la clause GROUP BY est spécifiée, ou s'il y a des appels de fonctions d'agrégation, la sortie est regroupée en groupes de lignes qui correspondent sur une ou plusieurs valeurs, et les résultats des fonctions d'agrégation sont calculés. Si la clause HAVING est présente, elle élimine les groupes qui ne satisfont pas à la condition donnée. (Voir Clause GROUP BY et Clause HAVING ci-dessous.) Bien que les colonnes de sortie de la requête soient nominalement calculées à l'étape suivante, elles peuvent également être référencées (par nom ou numéro ordinal) dans la clause GROUP BY.
5.Les lignes de sortie réelles sont calculées en utilisant les expressions de sortie SELECT pour chaque ligne ou groupe de lignes sélectionné. (Voir Liste SELECT ci-dessous.)
6.SELECT DISTINCT élimine les lignes dupliquées du résultat. SELECT DISTINCT ON élimine les lignes qui correspondent sur toutes les expressions spécifiées. SELECT ALL (par défaut) renvoie toutes les lignes candidates, y compris les doublons. (Voir Clause DISTINCT ci-dessous.)
7.En utilisant les opérateurs UNION, INTERSECT et EXCEPT, la sortie de plusieurs instructions SELECT peut être combinée pour former un seul ensemble de résultats. L'opérateur UNION renvoie toutes les lignes qui sont dans un ou les deux ensembles de résultats. L'opérateur INTERSECT renvoie toutes les lignes qui sont strictement dans les deux ensembles de résultats. L'opérateur EXCEPT renvoie les lignes qui sont dans le premier ensemble de résultats mais pas dans le second. Dans les trois cas, les lignes dupliquées sont éliminées à moins que ALL ne soit spécifié. Le mot-clé DISTINCT peut être ajouté pour spécifier explicitement l'élimination des lignes dupliquées. Notez que DISTINCT est le comportement par défaut ici, même si ALL est le défaut pour SELECT lui-même. (Voir Clause UNION, Clause INTERSECT et Clause EXCEPT ci-dessous.)
8.Si la clause ORDER BY est spécifiée, les lignes renvoyées sont triées dans l'ordre spécifié. Si ORDER BY n'est pas donné, les lignes sont renvoyées dans l'ordre le plus rapide que le système trouve pour les produire. (Voir Clause ORDER BY ci-dessous.)
9.Si les clauses LIMIT (ou FETCH FIRST) ou OFFSET sont spécifiées, l'instruction SELECT ne renvoie qu'un sous-ensemble des lignes de résultat. (Voir Clause LIMIT ci-dessous.)
10.Si FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE ou FOR KEY SHARE est spécifié, l'instruction SELECT verrouille les lignes sélectionnées contre les mises à jour concurrentes. (Voir La Clause de Verrouillage ci-dessous.)

Vous devez avoir le privilège SELECT sur chaque colonne utilisée dans une commande SELECT. L'utilisation de FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE ou FOR KEY SHARE nécessite également le privilège UPDATE (pour au moins une colonne de chaque table ainsi sélectionnée).

PARAMÈTRES

Clause WITH

La clause WITH permet de spécifier une ou plusieurs sous-requêtes qui peuvent être référencées par nom dans la requête principale. Les sous-requêtes agissent effectivement comme des tables temporaires ou des vues pour la durée de la requête principale. Chaque sous-requête peut être une instruction SELECT, TABLE, VALUES, INSERT, UPDATE, DELETE ou MERGE. Lors de l'écriture d'une instruction de modification de données (INSERT, UPDATE, DELETE ou MERGE) dans WITH, il est courant d'inclure une clause RETURNING. C'est la sortie de RETURNING, pas la table sous-jacente que l'instruction modifie, qui forme la table temporaire lue par la requête principale. Si RETURNING est omis, l'instruction est toujours exécutée, mais elle ne produit aucune sortie et ne peut donc pas être référencée comme une table par la requête principale.

Un nom (sans qualification de schéma) doit être spécifié pour chaque requête WITH. Facultativement, une liste de noms de colonnes peut être spécifiée ; si elle est omise, les noms de colonnes sont déduits de la sous-requête.

Si RECURSIVE est spécifié, il permet à une sous-requête SELECT de se référencer elle-même par son nom. Une telle sous-requête doit avoir la forme

terme_non_recursif UNION [ ALL | DISTINCT ] terme_recursif

où la référence récursive de soi doit apparaître du côté droit de l'UNION. Une seule référence récursive de soi est autorisée par requête. Les instructions de modification de données récursives ne sont pas prises en charge, mais vous pouvez utiliser les résultats d'une requête SELECT récursive dans une instruction de modification de données. Voir Section 7.8 pour un exemple.

Un autre effet de RECURSIVE est que les requêtes WITH n'ont pas besoin d'être ordonnées : une requête peut en référencer une autre qui se trouve plus loin dans la liste. (Cependant, les références circulaires, ou la récursion mutuelle, ne sont pas implémentées.) Sans RECURSIVE, les requêtes WITH ne peuvent référencer que des requêtes WITH sœurs qui sont antérieures dans la liste WITH.

Lorsqu'il y a plusieurs requêtes dans la clause WITH, RECURSIVE ne doit être écrit qu'une seule fois, immédiatement après WITH. Il s'applique à toutes les requêtes de la clause WITH, bien qu'il n'ait aucun effet sur les requêtes qui n'utilisent pas de récursion ou de références avant.

SQL Syntax

SELECT Statement

The SELECT statement is the most common type of SQL query. It retrieves data from one or more tables.

The general form of a SELECT statement is:

[ WITH [ RECURSIVE ] with_query [, ...] ]
SELECT [ DISTINCT [ ON ( expression [, ...] ) ] ]
    [ * | expression [ [ AS ] output_name ] [, ...] ]
[ FROM from_item [, ...] ]
[ WHERE filter_clause ]
[ GROUP BY expression [, ...] ]
[ HAVING filter_clause ]
[ ORDER BY expression [ ASC | DESC | FIRST | LAST ] [, ...] ]
[ LIMIT count [ OFFSET start ] ]
[ OFFSET start [ LIMIT count ] ]
[ FETCH { FIRST | NEXT } [ count ] { ROWS | ROW } [ ONLY ] ]
[ FOR UPDATE [ OF table_name [, ...] ] [ NOWAIT | SKIP LOCKED ] ]

where from_item can be a table, joined table, or VALUES list.

WITH Clause

The optional WITH clause allows you to write a series of preparatory queries that you can then reference by name in a subsequent query. The queries in the WITH clause can refer to each other and to the base table of the command. Thus, the WITH clause provides a way to break down complex queries into simpler, more readable logical parts.

The general form of a WITH clause is:

WITH [ RECURSIVE ] with_query_name ( column_name [, ...] ) AS (
    query
)
[, with_query_name ( column_name [, ...] ) AS (
    query
)
...]

and the main query follows the WITH clause.

A WITH query that is referenced multiple times is only executed once per invocation of the main query. This feature makes it possible to use a WITH query to avoid redundant computation, though it also means that the effects of the WITH query cannot be seen by other parts of the main query, other than by reading its output. (See Section 7.8.3 for more details.)

If the keyword RECURSIVE is specified, this enables a SELECT statement that can reference itself. A recursive query is typically used to process hierarchical or graph-structured data. For example, the following query finds all the subordinates of a particular employee:

WITH RECURSIVE subordinates AS (
    SELECT employee_id, name, manager_id
    FROM employees
    WHERE employee_id = 1
  UNION
    SELECT e.employee_id, e.name, e.manager_id
    FROM employees e
    JOIN subordinates s ON s.employee_id = e.manager_id
)
SELECT * FROM subordinates;

The optional SEARCH clause is used to control the order in which rows are traversed in a recursive query. The supplied column name list specifies the row key that is to be used for keeping track of visited rows. A column named search_seq_col_name will be added to the result column list of the WITH query. This column can be ordered by in the outer query to achieve the respective ordering. See Section 7.8.2.1 for examples.

The optional CYCLE clause is used to detect cycles in recursive queries. The supplied column name list specifies the row key that is to be used for keeping track of visited rows. A column named cycle_mark_col_name will be added to the result column list of the WITH query. This column will be set to cycle_mark_value when a cycle has been detected, else to cycle_mark_default. Furthermore, processing of the recursive union will stop when a cycle has been detected. cycle_mark_value and cycle_mark_default must be constants and they must be coercible to a common data type, and the data type must have an inequality operator. (The SQL standard requires that they be Boolean constants or character strings, but PostgreSQL does not require that.) By default, TRUE and FALSE (of type boolean) are used. Furthermore, a column named cycle_path_col_name will be added to the result column list of the WITH query. This column is used internally for tracking visited rows. See Section 7.8.2.2 for examples.

Both the SEARCH and the CYCLE clause are only valid for recursive WITH queries. The with_query must be a UNION (or UNION ALL) of two SELECT (or equivalent) commands (no nested UNIONs). If both clauses are used, the column added by the SEARCH clause appears before the columns added by the CYCLE clause.

The primary query and the WITH queries are all (notionally) executed at the same time. This implies that the effects of a data-modifying statement in WITH cannot be seen from other parts of the query, other than by reading its RETURNING output. If two such data-modifying statements attempt to modify the same row, the results are unspecified.

A key property of WITH queries is that they are normally evaluated only once per execution of the primary query, even if the primary query refers to them more than once. In particular, data-modifying statements are guaranteed to be executed once and only once, regardless of whether the primary query reads all or any of their output.

However, a WITH query can be marked NOT MATERIALIZED to remove this guarantee. In that case, the WITH query can be folded into the primary query much as though it were a simple sub-SELECT in the primary query's FROM clause. This results in duplicate computations if the primary query refers to that WITH query more than once; but if each such use requires only a few rows of the WITH query's total output, NOT MATERIALIZED can provide a net savings by allowing the queries to be optimized jointly. NOT MATERIALIZED is ignored if it is attached to a WITH query that is recursive or is not side-effect-free (i.e., is not a plain SELECT containing no volatile functions).

By default, a side-effect-free WITH query is folded into the primary query if it is used exactly once in the primary query's FROM clause. This allows joint optimization of the two query levels in situations where that should be semantically invisible. However, such folding can be prevented by marking the WITH query as MATERIALIZED. That might be useful, for example, if the WITH query is being used as an optimization fence to prevent the planner from choosing a bad plan. PostgreSQL versions before v12 never did such folding, so queries written for older versions might rely on WITH to act as an optimization fence.

See Section 7.8 for additional information.

FROM Clause

The FROM clause specifies one or more source tables for the SELECT. If multiple sources are specified, the result is the Cartesian product (cross join) of all the sources. But usually qualification conditions are added (via WHERE) to restrict the returned rows to a small subset of the Cartesian product.

The FROM clause can contain the following elements:

table_name

The name (optionally schema-qualified) of an existing table or view. If ONLY is specified before the table name, only that table is scanned. If ONLY is not specified, the table and all its descendant tables (if any) are scanned. Optionally, * can be specified after the table name to explicitly indicate that descendant tables are included.

alias

A substitute name for the FROM item containing the alias. An alias is used for brevity or to eliminate ambiguity for self-joins (where the same table is scanned multiple times). When an alias is provided, it completely hides the actual name of the table or function; for example given FROM foo AS f, the remainder of the SELECT must refer to this FROM item as f not foo. If an alias is written, a column alias list can also be written to provide substitute names for one or more columns of the table.

TABLESAMPLE sampling_method ( argument [, ...] ) [ REPEATABLE ( seed ) ]

A TABLESAMPLE clause after a table_name indicates that the specified sampling_method should be used to retrieve a subset of the rows in that table. This sampling precedes the application of any other filters such as WHERE clauses. The standard PostgreSQL distribution includes two sampling methods, BERNOULLI and SYSTEM, and other sampling methods can be installed in the database via extensions.

The BERNOULLI and SYSTEM sampling methods each accept a single argument which is the fraction of the table to sample, expressed as a percentage between 0 and 100. This argument can be any real-valued expression. (Other sampling methods might accept more or different arguments.) These two methods each return a randomly-chosen sample of the table that will contain approximately the specified percentage of the table's rows. The BERNOULLI method scans the whole table and selects or ignores individual rows independently with the specified probability. The SYSTEM method does block-level sampling with each block having the specified chance of being selected; all rows in each selected block are returned. The SYSTEM method is significantly faster than the BERNOULLI method when small sampling percentages are specified, but it may return a less-random sample of the table as a result of clustering effects.

The optional REPEATABLE clause specifies a seed number or expression to use for generating random numbers within the sampling method. The seed value can be any non-null floating-point value. Two queries that specify the same seed and argument values will select the same sample of the table, if the table has not been changed meanwhile. But different seed values will usually produce different samples. If REPEATABLE is not given then a new random sample is selected for each query, based upon a system-generated seed. Note that some add-on sampling methods do not accept REPEATABLE, and will always produce new samples on each use.

select

A sub-SELECT can appear in the FROM clause. This acts as though its output were created as a temporary table for the duration of this single SELECT command. Note that the sub-SELECT must be surrounded by parentheses, and an alias can be provided in the same way as for a table. A VALUES command can also be used here.

with_query_name

A WITH query is referenced by writing its name, just as though the query's name were a table name. (In fact, the WITH query hides any real table of the same name for the purposes of the primary query. If necessary, you can refer to a real table of the same name by schema-qualifying the table's name.) An alias can be provided in the same way as for a table.

function_name

Function calls can appear in the FROM clause. (This is especially useful for functions that return result sets, but any function can be used.) This acts as though the function's output were created as a temporary table for the duration of this single SELECT command. If the function's result type is composite (including the case of a function with multiple OUT parameters), each attribute becomes a separate column in the implicit table.

When the optional WITH ORDINALITY clause is added to the function call, an additional column of type bigint will be appended to the function's result column(s). This column numbers the rows of the function's result set, starting from 1. By default, this column is named ordinality.

An alias can be provided in the same way as for a table. If an alias is written, a column alias list can also be written to provide substitute names for one or more attributes of the function's composite return type, including the ordinality column if present.

Multiple function calls can be combined into a single FROM-clause item by surrounding them with ROWS FROM( ... ). The output of such an item is the concatenation of the first row from each function, then the second row from each function, etc. If some of the functions produce fewer rows than others, null values are substituted for the missing data, so that the total number of rows returned is always the same as for the function that produced the most rows.

If the function has been defined as returning the record data type, then an alias or the key word AS must be present, followed by a column definition list in the form ( column_name data_type [, ... ]). The column definition list must match the actual number and types of columns returned by the function.

When using the ROWS FROM( ... ) syntax, if one of the functions requires a column definition list, it's preferred to put the column definition list after the function call inside ROWS FROM( ... ). A column definition list can be placed after the ROWS FROM( ... ) construct only if there's just a single function and no WITH ORDINALITY clause.

To use ORDINALITY together with a column definition list, you must use the ROWS FROM( ... ) syntax and put the column definition list inside ROWS FROM( ... ).

join_type

One of
•[ INNER ] JOIN
•LEFT [ OUTER ] JOIN
•RIGHT [ OUTER ] JOIN
•FULL [ OUTER ] JOIN

For the INNER and OUTER join types, a join condition must be specified, namely exactly one of ON join_condition, USING (join_column [, ...]), or NATURAL. See below for the meaning.

A JOIN clause combines two FROM items, which for convenience we will refer to as “tables”, though in reality they can be any type of FROM item. Use parentheses if necessary to determine the order of nesting. In the absence of parentheses, JOINs nest left-to-right. In any case JOIN binds more tightly than the commas separating FROM-list items. All the JOIN options are just a notati

FULL OUTER JOIN renvoie toutes les lignes jointes, plus une ligne pour chaque ligne de la table de gauche non correspondante (étendues avec des valeurs nulles à droite), plus une ligne pour chaque ligne de la table de droite non correspondante (étendues avec des valeurs nulles à gauche).

ON condition_jointure

condition_jointure est une expression résultant en une valeur de type booléen (similaire à une clause WHERE) qui spécifie quelles lignes d'une jointure sont considérées comme correspondantes.

USING ( colonne_jointure [, ...] ) [ AS alias_jointure_using ]

Une clause de la forme USING ( a, b, ... ) est un raccourci pour ON table_gauche.a = table_droite.a ET table_gauche.b = table_droite.b .... De plus, USING implique que seule une des paires de colonnes équivalentes sera incluse dans la sortie de la jointure, et non les deux.

Si un nom alias_jointure_using est spécifié, il fournit un alias de table pour les colonnes de jointure. Seules les colonnes de jointure listées dans la clause USING sont adressables par ce nom. Contrairement à un alias régulier, cela ne masque pas les noms des tables jointes du reste de la requête. Contrairement également à un alias régulier, vous ne pouvez pas écrire une liste d'alias de colonnes — les noms de sortie des colonnes de jointure sont les mêmes que ceux qui apparaissent dans la liste USING.

NATURAL

NATURAL est un raccourci pour une liste USING qui mentionne toutes les colonnes des deux tables qui ont des noms correspondants. S'il n'y a pas de noms de colonnes communs, NATURAL est équivalent à ON TRUE.

CROSS JOIN

CROSS JOIN est équivalent à INNER JOIN ON (TRUE), c'est-à-dire qu'aucune ligne n'est supprimée par qualification. Ils produisent un simple produit cartésien, le même résultat que celui obtenu en listant les deux tables au niveau supérieur de FROM, mais restreint par la condition de jointure (le cas échéant).

LATERAL

Le mot-clé LATERAL peut précéder un sous-SELECT FROM item. Cela permet au sous-SELECT de faire référence à des colonnes d'éléments FROM qui apparaissent avant lui dans la liste FROM. (Sans LATERAL, chaque sous-SELECT est évalué indépendamment et ne peut donc pas faire référence à d'autres éléments FROM.)

LATERAL peut également précéder un appel de fonction FROM item, mais dans ce cas, il s'agit d'un bruit, car l'expression de la fonction peut faire référence à des éléments FROM précédents dans tous les cas.

Un élément LATERAL peut apparaître au niveau supérieur de la liste FROM, ou à l'intérieur d'un arbre de JOIN. Dans ce dernier cas, il peut également faire référence à tous les éléments qui se trouvent du côté gauche d'une JOIN dont il est du côté droit.

Lorsque un élément FROM contient des références croisées LATERAL, l'évaluation procède comme suit : pour chaque ligne de l'élément FROM fournissant la (les) colonne(s) référencée(s) en croix, ou l'ensemble de lignes de plusieurs éléments FROM fournissant les colonnes, l'élément LATERAL est évalué en utilisant les valeurs de la ligne ou de l'ensemble de lignes de ces colonnes. Les lignes résultantes sont jointes comme d'habitude avec les lignes à partir desquelles elles ont été calculées. Ceci est répété pour chaque ligne ou ensemble de lignes des tables sources de colonnes.

Les tables sources de colonnes doivent être jointes par INNER ou LEFT JOIN à l'élément LATERAL, sinon il n'y aurait pas d'ensemble bien défini de lignes à partir desquelles calculer chaque ensemble de lignes pour l'élément LATERAL. Ainsi, bien qu'une construction telle que X RIGHT JOIN LATERAL Y soit syntaxiquement valide, elle n'est pas autorisée pour que Y fasse référence à X.

Clause WHERE

La clause WHERE optionnelle a la forme générale

WHERE condition

où condition est une expression qui évalue à un résultat de type booléen. Toute ligne qui ne satisfait pas cette condition sera éliminée de la sortie. Une ligne satisfait la condition si elle renvoie vrai lorsque les valeurs de ligne réelles sont substituées à toutes les références de variable.

Clause GROUP BY

La clause GROUP BY optionnelle a la forme générale

GROUP BY [ ALL | DISTINCT ] élément_groupement [, ...]

GROUP BY condensera en une seule ligne toutes les lignes sélectionnées qui partagent les mêmes valeurs pour les expressions groupées. Une expression utilisée à l'intérieur d'un élément_groupement peut être un nom de colonne d'entrée, ou le nom ou le numéro ordinal d'une colonne de sortie (élément de la liste SELECT), ou une expression arbitraire formée à partir des valeurs des colonnes d'entrée. En cas d'ambiguïté, un nom GROUP BY sera interprété comme un nom de colonne d'entrée plutôt qu'un nom de colonne de sortie.

Si GROUPING SETS, ROLLUP ou CUBE sont présents en tant qu'éléments de groupement, alors la clause GROUP BY dans son ensemble définit un certain nombre d'ensembles de groupement indépendants. L'effet est équivalent à la construction d'un UNION ALL entre des sous-requêtes avec les ensembles de groupement individuels comme leurs clauses GROUP BY. La clause DISTINCT optionnelle supprime les ensembles dupliqués avant le traitement ; elle ne transforme pas l'UNION ALL en UNION DISTINCT. Pour plus de détails sur le traitement des ensembles de groupement, voir la Section 7.2.4.

Les fonctions d'agrégation, si elles sont utilisées, sont calculées sur toutes les lignes constituant chaque groupe, produisant une valeur distincte pour chaque groupe. (S'il y a des fonctions d'agrégation mais pas de clause GROUP BY, la requête est traitée comme ayant un seul groupe comprenant toutes les lignes sélectionnées.) L'ensemble des lignes alimentant chaque fonction d'agrégation peut être filtré davantage en ajoutant une clause FILTER à l'appel de la fonction d'agrégation ; voir la Section 4.2.7 pour plus d'informations. Lorsqu'une clause FILTER est présente, seules les lignes qui la satisfont sont incluses dans l'entrée de cette fonction d'agrégation.

Lorsque GROUP BY est présent, ou que des fonctions d'agrégation sont présentes, il n'est pas valide pour les expressions de la liste SELECT de faire référence à des colonnes non groupées sauf dans les fonctions d'agrégation ou lorsque la colonne non groupée dépend fonctionnellement des colonnes groupées, car il y aurait sinon plus d'une valeur possible à retourner pour une colonne non groupée. Une dépendance fonctionnelle existe si les colonnes groupées (ou un sous-ensemble de celles-ci) constituent la clé primaire de la table contenant la colonne non groupée.

Gardez à l'esprit que toutes les fonctions d'agrégation sont évaluées avant l'évaluation de toute expression « scalaire » dans la clause HAVING ou la liste SELECT. Cela signifie que, par exemple, une expression CASE ne peut pas être utilisée pour ignorer l'évaluation d'une fonction d'agrégation ; voir la Section 4.2.14.

Actuellement, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE et FOR KEY SHARE ne peuvent pas être spécifiés avec GROUP BY.

Clause HAVING

La clause HAVING optionnelle a la forme générale

HAVING condition

où condition est la même que celle spécifiée pour la clause WHERE.

HAVING élimine les lignes de groupe qui ne satisfont pas la condition. HAVING est différent de WHERE : WHERE filtre les lignes individuelles avant l'application de GROUP BY, tandis que HAVING filtre les lignes de groupe créées par GROUP BY. Chaque colonne référencée dans condition doit référencer sans ambiguïté une colonne de groupement, sauf si la référence apparaît dans une fonction d'agrégation ou si la colonne non groupée dépend fonctionnellement des colonnes de groupement.

La présence de HAVING transforme une requête en une requête groupée même s'il n'y a pas de clause GROUP BY. C'est la même chose qui se produit lorsque la requête contient des fonctions d'agrégation mais pas de clause GROUP BY. Toutes les lignes sélectionnées sont considérées comme formant un seul groupe, et la liste SELECT et la clause HAVING ne peuvent référencer des colonnes de table qu'à partir de fonctions d'agrégation. Une telle requête émettra une seule ligne si la condition HAVING est vraie, zéro ligne si elle est fausse.

Actuellement, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE et FOR KEY SHARE ne peuvent pas être spécifiés avec HAVING.

Clause WINDOW

La clause WINDOW optionnelle a la forme générale

WINDOW nom_fenetre AS ( definition_fenetre ) [, ...]

où nom_fenetre est un nom qui peut être référencé depuis des clauses OVER ou des définitions de fenêtre ultérieures, et definition_fenetre est

[ nom_fenetre_existant ]
[ PARTITION BY expression [, ...] ]
[ ORDER BY expression [ ASC | DESC | USING operateur ] [ NULLS { FIRST | LAST } ] [, ...] ]
[ clause_cadre ]

Si un nom_fenetre_existant est spécifié, il doit faire référence à une entrée antérieure dans la liste WINDOW ; la nouvelle fenêtre copie sa clause de partitionnement de cette entrée, ainsi que sa clause de tri le cas échéant. Dans ce cas, la nouvelle fenêtre ne peut pas spécifier sa propre clause PARTITION BY, et elle ne peut spécifier ORDER BY que si la fenêtre copiée n'en a pas. La nouvelle fenêtre utilise toujours sa propre clause de cadre ; la fenêtre copiée ne doit pas spécifier de clause de cadre.

Les éléments de la liste PARTITION BY sont interprétés de la même manière que les éléments d'une clause GROUP BY, à la différence qu'il s'agit toujours d'expressions simples et jamais du nom ou du numéro d'une colonne de sortie. Une autre différence est que ces expressions peuvent contenir des appels de fonction d'agrégation, qui ne sont pas autorisés dans une clause GROUP BY régulière. Ils sont autorisés ici car le fenêtrage se produit après le groupement et l'agrégation.

De même, les éléments de la liste ORDER BY sont interprétés de la même manière que les éléments d'une clause ORDER BY au niveau de l'instruction, à la différence que les expressions sont toujours prises comme des expressions simples et jamais comme le nom ou le numéro d'une colonne de sortie.

La clause_cadre optionnelle définit le cadre de fenêtre pour les fonctions de fenêtre qui dépendent du cadre (pas toutes). Le cadre de fenêtre est un ensemble de lignes liées pour chaque ligne de la requête (appelée la ligne courante). La clause_cadre peut être l'une des suivantes :

{ RANGE | ROWS | GROUPS } debut_cadre [ exclusion_cadre ]
{ RANGE | ROWS | GROUPS } BETWEEN debut_cadre AND fin_cadre [ exclusion_cadre ]

où debut_cadre et fin_cadre peuvent être l'un des suivants :

Liste SELECT

La liste SELECT (entre les mots-clés SELECT et FROM) spécifie les expressions qui forment les lignes de sortie de l'instruction SELECT. Les expressions peuvent (et le font habituellement) faire référence à des colonnes calculées dans la clause FROM.

Tout comme dans une table, chaque colonne de sortie d'un SELECT a un nom. Dans un simple SELECT, ce nom est simplement utilisé pour étiqueter la colonne pour l'affichage, mais lorsque le SELECT est une sous-requête d'une requête plus grande, le nom est vu par la requête plus grande comme le nom de colonne de la table virtuelle produite par la sous-requête. Pour spécifier le nom à utiliser pour une colonne de sortie, écrivez AS nom_sortie après l'expression de la colonne. (Vous pouvez omettre AS, mais seulement si le nom de sortie désiré ne correspond à aucun mot-clé PostgreSQL (voir l'Annexe C). Pour vous protéger contre de possibles ajouts futurs de mots-clés, il est recommandé d'écrire toujours AS ou de mettre le nom de sortie entre guillemets doubles.) Si vous ne spécifiez pas de nom de colonne, un nom est choisi automatiquement par PostgreSQL. Si l'expression de la colonne est une simple référence de colonne, alors le nom choisi est le même que le nom de cette colonne. Dans des cas plus complexes, un nom de fonction ou de type peut être utilisé, ou le système peut se rabattre sur un nom généré comme ?column?.

Le nom d'une colonne de sortie peut être utilisé pour faire référence à la valeur de la colonne dans les clauses ORDER BY et GROUP BY, mais pas dans les clauses WHERE ou HAVING ; vous devez y écrire l'expression à la place.

Au lieu d'une expression, * peut être écrit dans la liste de sortie comme un raccourci pour toutes les colonnes des lignes sélectionnées. De plus, vous pouvez écrire nom_table.* comme un raccourci pour les colonnes provenant uniquement de cette table. Dans ces cas, il n'est pas possible de spécifier de nouveaux noms avec AS ; les noms des colonnes de sortie seront les mêmes que les noms des colonnes de la table.

Selon la norme SQL, les expressions de la liste de sortie doivent être calculées avant d'appliquer DISTINCT, ORDER BY ou LIMIT. C'est évidemment nécessaire lors de l'utilisation de DISTINCT, car sinon il n'est pas clair quelles valeurs sont rendues distinctes. Cependant, dans de nombreux cas, il est pratique que les expressions de sortie soient calculées après ORDER BY et LIMIT ; en particulier si la liste de sortie contient des fonctions volatiles ou coûteuses. Avec ce comportement, l'ordre des évaluations des fonctions est plus intuitif et il n'y aura pas d'évaluations correspondant à des lignes qui n'apparaissent jamais dans la sortie. PostgreSQL évaluera effectivement les expressions de sortie après le tri et la limitation, tant que ces expressions ne sont pas référencées dans DISTINCT, ORDER BY ou GROUP BY. (Comme contre-exemple, SELECT f(x) FROM tab ORDER BY 1 doit clairement évaluer f(x) avant le tri.) Les expressions de sortie contenant des fonctions renvoyant un ensemble sont effectivement évaluées après le tri et avant la limitation, de sorte que LIMIT agisse pour couper la sortie d'une fonction renvoyant un ensemble.


Note

Les versions de PostgreSQL antérieures à 9.6 ne garantissaient pas le moment de l'évaluation des expressions de sortie par rapport au tri et à la limitation ; cela dépendait de la forme du plan de requête choisi.

Clause DISTINCT

Si SELECT DISTINCT est spécifié, toutes les lignes dupliquées sont supprimées de l'ensemble des résultats (une ligne est conservée pour chaque groupe de doublons). SELECT ALL spécifie le contraire : toutes les lignes sont conservées ; c'est le comportement par défaut.

SELECT DISTINCT ON ( expression [, ...] ) ne conserve que la première ligne de chaque ensemble de lignes où les expressions données sont égales. Les expressions DISTINCT ON sont interprétées en utilisant les mêmes règles que pour ORDER BY (voir ci-dessus). Notez que la « première ligne » de chaque ensemble est imprévisible à moins que ORDER BY ne soit utilisé pour garantir que la ligne souhaitée apparaît en premier. Par exemple :

SELECT DISTINCT ON (location) location, time, report
    FROM weather_reports
    ORDER BY location, time DESC;

récupère le rapport météorologique le plus récent pour chaque emplacement. Mais si nous n'avions pas utilisé ORDER BY pour forcer l'ordre décroissant des valeurs de temps pour chaque emplacement, nous aurions obtenu un rapport d'une heure imprévisible pour chaque emplacement.

L'expression (les expressions) DISTINCT ON doit correspondre à la (aux) expression(s) ORDER BY la (les) plus à gauche. La clause ORDER BY contiendra normalement des expressions supplémentaires qui déterminent la priorité souhaitée des lignes au sein de chaque groupe DISTINCT ON.

Actuellement, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE et FOR KEY SHARE ne peuvent pas être spécifiés avec DISTINCT.

Clause UNION

La clause UNION a cette forme générale :

instruction_select UNION [ ALL | DISTINCT ] instruction_select

instruction_select est toute instruction SELECT sans clause ORDER BY, LIMIT, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE ou FOR KEY SHARE. (ORDER BY et LIMIT peuvent être attachés à une sous-expression si elle est entourée de parenthèses. Sans parenthèses, ces clauses s'appliqueront au résultat de l'UNION, et non à l'expression d'entrée de droite.)

L'opérateur UNION calcule l'union des ensembles des lignes retournées par les instructions SELECT impliquées. Une ligne fait partie de l'union de deux ensembles de résultats si elle apparaît dans au moins l'un des ensembles de résultats. Les deux instructions SELECT qui représentent les opérandes directs de l'UNION doivent produire le même nombre de colonnes, et les colonnes correspondantes doivent être de types de données compatibles.

Le résultat de UNION ne contient aucune ligne dupliquée, sauf si l'option ALL est spécifiée. ALL empêche l'élimination des doublons. (Par conséquent, UNION ALL est généralement beaucoup plus rapide que UNION ; utilisez ALL lorsque vous le pouvez.) DISTINCT peut être écrit pour spécifier explicitement le comportement par défaut d'élimination des lignes dupliquées.

Plusieurs opérateurs UNION dans la même instruction SELECT sont évalués de gauche à droite, sauf indication contraire par des parenthèses.

Actuellement, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE et FOR KEY SHARE ne peuvent être spécifiés ni pour un résultat UNION, ni pour aucune entrée d'un UNION.

Clause INTERSECT

La clause INTERSECT a cette forme générale :

instruction_select INTERSECT [ ALL | DISTINCT ] instruction_select

instruction_select est toute instruction SELECT

Clause INTERSECT

La clause INTERSECT a la forme générale suivante :

instruction_select INTERSECT [ ALL | DISTINCT ] instruction_select

Chaque instruction_select est une instruction SELECT qui ne doit pas contenir de clause ORDER BY, LIMIT, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE ou FOR KEY SHARE.

L'opérateur INTERSECT calcule l'intersection des ensembles des lignes renvoyées par les instructions SELECT impliquées. Une ligne fait partie de l'intersection de deux ensembles de résultats si elle apparaît dans les deux ensembles de résultats.

Le résultat d'INTERSECT ne contient pas de lignes dupliquées à moins que l'option ALL ne soit spécifiée. Avec ALL, une ligne qui a m doublons dans la table de gauche et n doublons dans la table de droite apparaîtra min(m,n) fois dans l'ensemble de résultats. DISTINCT peut être utilisé pour spécifier explicitement le comportement par défaut d'élimination des lignes dupliquées.

Plusieurs opérateurs INTERSECT dans la même instruction SELECT sont évalués de gauche à droite, à moins que les parenthèses n'en décident autrement. INTERSECT a une priorité plus élevée qu'UNION. Autrement dit, A UNION B INTERSECT C sera interprété comme A UNION (B INTERSECT C).

Actuellement, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE et FOR KEY SHARE ne peuvent être spécifiés ni pour un résultat d'INTERSECT ni pour une entrée d'INTERSECT.

Clause EXCEPT

La clause EXCEPT a la forme générale suivante :

instruction_select EXCEPT [ ALL | DISTINCT ] instruction_select

instruction_select est toute instruction SELECT sans clause ORDER BY, LIMIT, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE ou FOR KEY SHARE.

L'opérateur EXCEPT calcule l'ensemble des lignes qui se trouvent dans le résultat de l'instruction SELECT de gauche mais pas dans le résultat de celle de droite.

Le résultat d'EXCEPT ne contient pas de lignes dupliquées à moins que l'option ALL ne soit spécifiée. Avec ALL, une ligne qui a m doublons dans la table de gauche et n doublons dans la table de droite apparaîtra max(m-n,0) fois dans l'ensemble de résultats. DISTINCT peut être utilisé pour spécifier explicitement le comportement par défaut d'élimination des lignes dupliquées.

Plusieurs opérateurs EXCEPT dans la même instruction SELECT sont évalués de gauche à droite, à moins que les parenthèses n'en décident autrement. EXCEPT a la même priorité qu'UNION.

Actuellement, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE et FOR KEY SHARE ne peuvent être spécifiés ni pour un résultat d'EXCEPT ni pour une entrée d'EXCEPT.

Clause ORDER BY

La clause ORDER BY optionnelle a la forme générale suivante :

ORDER BY expression [ ASC | DESC | USING opérateur ] [ NULLS { FIRST | LAST } ] [, ...]

La clause ORDER BY entraîne le tri des lignes de résultat selon l'expression (ou les expressions) spécifiée(s). Si deux lignes sont égales selon l'expression la plus à gauche, elles sont comparées selon l'expression suivante et ainsi de suite. Si elles sont égales selon toutes les expressions spécifiées, elles sont renvoyées dans un ordre dépendant de l'implémentation.

Chaque expression peut être le nom ou le numéro ordinal d'une colonne de sortie (élément de la liste SELECT), ou une expression arbitraire formée à partir des valeurs des colonnes d'entrée.

Le numéro ordinal fait référence à la position ordinale (de gauche à droite) de la colonne de sortie. Cette fonctionnalité permet de définir un ordre basé sur une colonne qui n'a pas de nom unique. Ce n'est jamais absolument nécessaire car il est toujours possible d'attribuer un nom à une colonne de sortie en utilisant la clause AS.

Il est également possible d'utiliser des expressions arbitraires dans la clause ORDER BY, y compris des colonnes qui n'apparaissent pas dans la liste de sortie SELECT. Ainsi, l'instruction suivante est valide :

SELECT name FROM distributors ORDER BY code;

Une limitation de cette fonctionnalité est qu'une clause ORDER BY s'appliquant au résultat d'une clause UNION, INTERSECT ou EXCEPT ne peut spécifier que le nom ou le numéro d'une colonne de sortie, pas une expression.

Si une expression ORDER BY est un nom simple qui correspond à la fois à un nom de colonne de sortie et à un nom de colonne d'entrée, ORDER BY l'interprétera comme le nom de colonne de sortie. C'est l'inverse du choix que fera GROUP BY dans la même situation. Cette incohérence est introduite pour être compatible avec la norme SQL.

Optionnellement, vous pouvez ajouter le mot-clé ASC (ascendant) ou DESC (descendant) après chaque expression dans la clause ORDER BY. Si non spécifié, ASC est supposé par défaut. Alternativement, un nom d'opérateur de tri spécifique peut être spécifié dans la clause USING. Un opérateur de tri doit être un membre inférieur ou supérieur d'une famille d'opérateurs B-tree. ASC est généralement équivalent à USING < et DESC est généralement équivalent à USING >. (Mais le créateur d'un type de données défini par l'utilisateur peut définir exactement quel est l'ordre de tri par défaut, et cela peut correspondre à des opérateurs portant d'autres noms.)

Si NULLS LAST est spécifié, les valeurs nulles sont triées après toutes les valeurs non nulles ; si NULLS FIRST est spécifié, les valeurs nulles sont triées avant toutes les valeurs non nulles. Si aucune des deux options n'est spécifiée, le comportement par défaut est NULLS LAST lorsque ASC est spécifié ou implicite, et NULLS FIRST lorsque DESC est spécifié (ainsi, par défaut, les nuls sont considérés comme plus grands que les non-nuls). Lorsque USING est spécifié, l'ordre des nuls par défaut dépend du fait que l'opérateur soit un opérateur de type « inférieur à » ou « supérieur à ».

Notez que les options de tri ne s'appliquent qu'à l'expression qui les suit ; par exemple, ORDER BY x, y DESC ne signifie pas la même chose que ORDER BY x DESC, y DESC.

Les données de type chaîne de caractères sont triées selon le classement qui s'applique à la colonne triée. Cela peut être remplacé si nécessaire en incluant une clause COLLATE dans l'expression, par exemple ORDER BY mycolumn COLLATE "en_US". Pour plus d'informations, voir la Section 4.2.10 et la Section 23.2.

Clause LIMIT

La clause LIMIT comprend deux sous-clauses indépendantes :

LIMIT { nombre | ALL }
OFFSET début

Le paramètre nombre spécifie le nombre maximum de lignes à renvoyer, tandis que début spécifie le nombre de lignes à ignorer avant de commencer à renvoyer des lignes. Lorsque les deux sont spécifiés, début lignes sont ignorées avant de commencer à compter les nombre lignes à renvoyer.

Si l'expression nombre évalue à NULL, elle est traitée comme LIMIT ALL, c'est-à-dire aucune limite. Si début évalue à NULL, il est traité comme OFFSET 0.

SQL:2008 a introduit une syntaxe différente pour obtenir le même résultat, que PostgreSQL prend également en charge. C'est :

OFFSET début { ROW | ROWS }
FETCH { FIRST | NEXT } [ nombre ] { ROW | ROWS } { ONLY | WITH TIES }

Dans cette syntaxe, la valeur début ou nombre est obligatoirement une constante littérale, un paramètre ou un nom de variable selon la norme ; en tant qu'extension PostgreSQL, d'autres expressions sont autorisées, mais devront généralement être entourées de parenthèses pour éviter toute ambiguïté. Si nombre est omis dans une clause FETCH, il vaut 1 par défaut. L'option WITH TIES est utilisée pour renvoyer toutes les lignes supplémentaires qui font égalité pour la dernière place dans l'ensemble de résultats selon la clause ORDER BY ; ORDER BY est obligatoire dans ce cas, et SKIP LOCKED n'est pas autorisé. ROW et ROWS ainsi que FIRST et NEXT sont des mots superflus qui n'influencent pas les effets de ces clauses. Selon la norme, la clause OFFSET doit précéder la clause FETCH si les deux sont présentes ; mais PostgreSQL est plus souple et autorise les deux ordres.

Lors de l'utilisation de LIMIT, il est conseillé d'utiliser une clause ORDER BY qui contraint les lignes de résultat à un ordre unique. Sinon, vous obtiendrez un sous-ensemble imprévisible des lignes de la requête — vous pourriez demander les dixième à vingtième lignes, mais dixième à vingtième dans quel ordre ? Vous ne saurez quel ordre sauf si vous spécifiez ORDER BY.

Le planificateur de requêtes prend en compte LIMIT lors de la génération d'un plan de requête, de sorte que vous obtiendrez très probablement des plans différents (produisant des ordres de lignes différents) en fonction de ce que vous utilisez pour LIMIT et OFFSET. Ainsi, utiliser différentes valeurs de LIMIT/OFFSET pour sélectionner différents sous-ensembles d'un résultat de requête donnera des résultats incohérents sauf si vous imposez un ordre de résultat prévisible avec ORDER BY. Ce n'est pas un bug ; c'est une conséquence inhérente du fait que SQL ne garantit pas de renvoyer les résultats d'une requête dans un ordre particulier, sauf si ORDER BY est utilisé pour contraindre l'ordre.

Il est même possible que des exécutions répétées de la même requête LIMIT renvoient des sous-ensembles différents des lignes d'une table, s'il n'y a pas d'ORDER BY pour imposer la sélection d'un sous-ensemble déterministe. Encore une fois, ce n'est pas un bug ; le caractère déterministe des résultats n'est tout simplement pas garanti dans un tel cas.

La Clause de Verrouillage

FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE et FOR KEY SHARE sont des clauses de verrouillage ; elles affectent la manière dont SELECT verrouille les lignes lorsqu'elles sont obtenues de la table.

La clause de verrouillage a la forme générale

FOR force_verrouillage [ OF référence_source [, ...] ] [ NOWAIT | SKIP LOCKED ]

où force_verrouillage peut être l'une des options suivantes :

UPDATE
NO KEY UPDATE
SHARE
KEY SHARE

référence_source doit être un alias de table ou un nom de table non caché référencé dans la clause FROM. Pour plus d'informations sur chaque mode de verrouillage de ligne, reportez-vous à la Section 13.3.2.

Pour empêcher l'opération d'attendre que d'autres transactions soient validées, utilisez l'option NOWAIT ou SKIP LOCKED. Avec NOWAIT, l'instruction signale une erreur, plutôt que d'attendre, si une ligne sélectionnée ne peut pas être verrouillée immédiatement. Avec SKIP LOCKED, les lignes sélectionnées qui ne peuvent pas être verrouillées immédiatement sont ignorées. Ignorer les lignes verrouillées fournit une vue incohérente des données, donc ce n'est pas adapté à un usage général, mais cela peut être utilisé pour éviter la contention de verrouillage avec plusieurs consommateurs accédant à une table de type file d'attente. Notez que NOWAIT et SKIP LOCKED s'appliquent uniquement aux verrouillages de ligne — le verrouillage de table requis ROW SHARE est toujours pris de manière ordinaire (voir le Chapitre 13). Vous pouvez utiliser LOCK avec l'option NOWAIT en premier, si vous avez besoin d'acquérir le verrouillage de table sans attendre.

Si des tables spécifiques sont nommées dans une clause de verrouillage, alors seules les lignes provenant de ces tables sont verrouillées ; toutes les autres tables utilisées dans le SELECT sont simplement lues comme d'habitude. Une clause de verrouillage sans liste de tables affecte toutes les tables utilisées dans l'instruction. Si une clause de verrouillage est appliquée à une vue ou une sous-requête, elle affecte toutes les tables utilisées dans la vue ou la sous-requête. Cependant, ces clauses ne s'appliquent pas aux requêtes WITH référencées par la requête principale. Si vous souhaitez qu'un verrouillage de ligne se produise dans une requête WITH, spécifiez une clause de verrouillage dans la requête WITH.

Plusieurs clauses de verrouillage peuvent être écrites

ten si nécessaire pour spécifier un comportement de verrouillage différent pour différentes tables. Si la même table est mentionnée (ou affectée implicitement) par plus d'une clause de verrouillage, alors elle est traitée comme si elle n'était spécifiée que par la plus forte. De même, une table est traitée comme NOWAIT si cela est spécifié dans l'une des clauses qui la concernent. Sinon, elle est traitée comme SKIP LOCKED si cela est spécifié dans l'une des clauses qui la concernent.

Les clauses de verrouillage ne peuvent pas être utilisées dans des contextes où les lignes renvoyées ne peuvent pas être clairement identifiées avec des lignes de table individuelles ; par exemple, elles ne peuvent pas être utilisées avec l'agrégation.

Lorsqu'une clause de verrouillage apparaît au niveau supérieur d'une requête SELECT, les lignes qui sont verrouillées sont exactement celles qui sont renvoyées par la requête ; dans le cas d'une requête de jointure, les lignes verrouillées sont celles qui contribuent aux lignes de jointure renvoyées. De plus, les lignes qui satisfaisaient les conditions de la requête au moment de l'instantané de la requête seront verrouillées, bien qu'elles ne soient pas renvoyées si elles ont été mises à jour après l'instantané et ne satisfont plus les conditions de la requête. Si une LIMIT est utilisée, le verrouillage s'arrête une fois que suffisamment de lignes ont été renvoyées pour satisfaire la limite (mais notez que les lignes ignorées par OFFSET seront verrouillées). De même, si une clause de verrouillage est utilisée dans la requête d'un curseur, seules les lignes réellement récupérées ou franchies par le curseur seront verrouillées.

Lorsqu'une clause de verrouillage apparaît dans une sous-requête SELECT, les lignes verrouillées sont celles renvoyées à la requête externe par la sous-requête. Cela peut impliquer moins de lignes que ce que laisserait supposer une inspection de la sous-requête seule, car les conditions de la requête externe peuvent être utilisées pour optimiser l'exécution de la sous-requête. Par exemple,

SELECT * FROM (SELECT * FROM mytable FOR UPDATE) ss WHERE col1 = 5;

verrouillera uniquement les lignes ayant col1 = 5, même si cette condition n'est pas textuellement incluse dans la sous-requête.

Les versions précédentes ne parvenaient pas à préserver un verrou qui est mis à niveau par un savepoint ultérieur. Par exemple, ce code :

BEGIN;
SELECT * FROM mytable WHERE key = 1 FOR UPDATE;
SAVEPOINT s;
UPDATE mytable SET ... WHERE key = 1;
ROLLBACK TO s;

ne parviendrait pas à préserver le verrou FOR UPDATE après le ROLLBACK TO. Ceci a été corrigé dans la version 9.3.


Attention

Il est possible qu'une commande SELECT exécutée au niveau d'isolation de transaction READ COMMITTED et utilisant ORDER BY et une clause de verrouillage renvoie des lignes dans le désordre. C'est parce que ORDER BY est appliqué en premier. La commande trie le résultat, mais peut ensuite se bloquer en essayant d'obtenir un verrou sur une ou plusieurs des lignes. Une fois que le SELECT est débloqué, certaines des valeurs des colonnes de tri peuvent avoir été modifiées, ce qui fait que ces lignes semblent être dans le désordre (bien qu'elles soient dans l'ordre par rapport aux valeurs des colonnes d'origine). Cela peut être contourné si nécessaire en plaçant la clause FOR UPDATE/SHARE dans une sous-requête, par exemple

SELECT * FROM (SELECT * FROM mytable FOR UPDATE) ss ORDER BY column1;

Notez que cela entraînera le verrouillage de toutes les lignes de mytable, alors que FOR UPDATE au niveau supérieur ne verrouillerait que les lignes effectivement renvoyées. Cela peut entraîner une différence de performance significative, en particulier si ORDER BY est combiné avec LIMIT ou d'autres restrictions. Cette technique n'est donc recommandée que si des mises à jour concurrentes des colonnes de tri sont attendues et qu'un résultat strictement trié est requis.

Aux niveaux d'isolation de transaction REPEATABLE READ ou SERIALIZABLE, cela provoquerait une erreur de sérialisation (avec un SQLSTATE de '40001'), il n'y a donc aucune possibilité de recevoir des lignes dans le désordre sous ces niveaux d'isolation.

La commande

TABLE nom

est équivalente à

SELECT * FROM nom

Elle peut être utilisée comme commande de haut niveau ou comme variante syntaxique économisant de l'espace dans certaines parties de requêtes complexes. Seules les clauses WITH, UNION, INTERSECT, EXCEPT, ORDER BY, LIMIT, OFFSET, FETCH et FOR de verrouillage peuvent être utilisées avec TABLE ; la clause WHERE et toute forme d'agrégation ne peuvent pas être utilisées.

EXEMPLES

Pour joindre la table films avec la table distributeurs :

SELECT f.title, f.did, d.name, f.date_prod, f.kind
    FROM distributors d JOIN films f USING (did);
       title       | did |     name     | date_prod  |   kind
-------------------+-----+--------------+------------+----------
 The Third Man     | 101 | British Lion | 1949-12-23 | Drama
 The African Queen | 101 | British Lion | 1951-08-11 | Romantic
 ...

Pour additionner la colonne len de tous les films et regrouper les résultats par type :

SELECT kind, sum(len) AS total FROM films GROUP BY kind;
   kind   | total
----------+-------
 Action   | 07:34
 Comedy   | 02:58
 Drama    | 14:28
 Musical  | 06:42
 Romantic | 04:38

Pour additionner la colonne len de tous les films, regrouper les résultats par type et afficher les totaux de ces groupes qui sont inférieurs à 5 heures :

SELECT kind, sum(len) AS total
    FROM films
    GROUP BY kind
    HAVING sum(len) < interval '5 hours';
   kind   | total
----------+-------
 Comedy   | 02:58
 Romantic | 04:38

SELECT * FROM distributors ORDER BY name;
SELECT * FROM distributors ORDER BY 2;

L'exemple suivant montre comment obtenir l'union des tables distributeurs et acteurs, en limitant les résultats à ceux qui commencent par la lettre W dans chaque table. Seules les lignes distinctes sont souhaitées, donc le mot-clé ALL est omis.

distributors:               actors:
 did |     name              id |     name
-----+--------------        ----+----------------

 112 | Warner Bros.           3 | Walter Matthau
 ...                         ...
SELECT distributors.name
    FROM distributors
    WHERE distributors.name LIKE 'W%'
UNION
SELECT actors.name
    FROM actors
    WHERE actors.name LIKE 'W%';

Cet exemple montre comment utiliser une fonction dans la clause FROM, avec et sans liste de définition de colonnes :

CREATE FUNCTION distributors(int) RETURNS SETOF distributors AS $$
    SELECT * FROM distributors WHERE did = $1;
$$ LANGUAGE SQL;
SELECT * FROM distributors(111);
 did |    name
-----+-------------
 111 | Walt Disney
CREATE FUNCTION distributors_2(int) RETURNS SETOF record AS $$
    SELECT * FROM distributors WHERE did = $1;
$$ LANGUAGE SQL;
SELECT * FROM distributors_2(111) AS (f1 int, f2 text);
 f1  |     f2
-----+-------------
 111 | Walt Disney

Voici un exemple de fonction avec une colonne d'ordinalité ajoutée :

SELECT * FROM unnest(ARRAY['a','b','c','d','e','f']) WITH ORDINALITY;
 unnest | ordinality
--------+----------
 a      |        1
 b      |        2
 c      |        3
 d      |        4
 e      |        5
 f      |        6
(6 rows)

Cet exemple montre comment utiliser une clause WITH simple :

WITH t AS (
    SELECT random() as x FROM generate_series(1, 3)
  )
SELECT * FROM t
UNION ALL
SELECT * FROM t;
         x
--------------------
  0.534150459803641
  0.520092216785997
 0.0735620250925422
  0.534150459803641
  0.520092216785997
 0.0735620250925422

Notez que la requête WITH a été évaluée une seule fois, de sorte que nous avons obtenu deux ensembles des mêmes trois valeurs aléatoires.

Cet exemple utilise WITH RECURSIVE pour trouver tous les subordonnés (directs ou indirects) de l'employé Mary, et leur niveau d'indirectité, à partir d'une table qui ne montre que les subordonnés directs :

WITH RECURSIVE employee_recursive(distance, employee_name, manager_name) AS (
    SELECT 1, employee_name, manager_name
    FROM employee
    WHERE manager_name = 'Mary'
  UNION ALL
    SELECT er.distance + 1, e.employee_name, e.manager_name
    FROM employee_recursive er, employee e
    WHERE er.employee_name = e.manager_name
  )
SELECT distance, employee_name FROM employee_recursive;

Notez la forme typique des requêtes récursives : une condition initiale, suivie de UNION, suivie de la partie récursive de la requête. Assurez-vous que la partie récursive de la requête ne renverra éventuellement aucun tuple, sinon la requête bouclera indéfiniment. (Voir la section 7.8 pour plus d'exemples.)

Cet exemple utilise LATERAL pour appliquer une fonction renvoyant un ensemble get_product_names() pour chaque ligne de la table manufacturers :

SELECT m.name AS mname, pname
FROM manufacturers m, LATERAL get_product_names(m.id) pname;

Les fabricants n'ayant actuellement aucun produit n'apparaîtraient pas dans le résultat, car il s'agit d'une jointure interne. Si nous souhaitions inclure les noms de tels fabricants dans le résultat, nous pourrions faire :

SELECT m.name AS mname, pname
FROM manufacturers m LEFT JOIN LATERAL get_product_names(m.id) pname ON true;

COMPATIBILITÉ

Bien sûr, l'instruction SELECT est compatible avec la norme SQL. Mais il existe des extensions et des fonctionnalités manquantes.

Clauses FROM omises

PostgreSQL permet d'omettre la clause FROM. Elle est utilisée de manière simple pour calculer les résultats d'expressions simples :

SELECT 2+2;
 ?column?
----------
        4

Certaines autres bases de données SQL ne peuvent pas le faire sauf en introduisant une table factice d'une ligne à partir de laquelle faire le SELECT.

Listes SELECT vides

La liste des expressions de sortie après SELECT peut être vide, produisant une table résultat de zéro colonne. Ce n'est pas une syntaxe valide selon la norme SQL. PostgreSQL l'autorise pour être cohérent avec l'autorisation des tables de zéro colonne. Cependant, une liste vide n'est pas autorisée lorsque DISTINCT est utilisé.

Omission du mot-clé AS

Dans la norme SQL, le mot-clé optionnel AS

Omission des alias de sous-SELECT dans FROM

Conformément à la norme SQL, un sous-SELECT dans la liste FROM doit avoir un alias. Dans PostgreSQL, cet alias peut être omis.

ONLY et Héritage

La norme SQL exige des parenthèses autour du nom de la table lors de l'utilisation de ONLY, par exemple SELECT * FROM ONLY (tab1), ONLY (tab2) WHERE ... PostgreSQL considère ces parenthèses comme facultatives.

PostgreSQL permet d'écrire un astérisque à la fin pour spécifier explicitement le comportement non-ONLY d'inclure les tables filles. La norme ne le permet pas.

(Ces points s'appliquent également à toutes les commandes SQL qui prennent en charge l'option ONLY).

Clause TABLESAMPLE : Restrictions

La clause TABLESAMPLE est actuellement acceptée uniquement sur les tables régulières et les vues matérialisées. Conformément à la norme SQL, elle devrait pouvoir être appliquée à tout élément de FROM.

Appels de fonctions dans FROM

PostgreSQL permet d'écrire un appel de fonction directement comme membre de la liste FROM. Conformément à la norme SQL, il faudrait enfermer cet appel dans un sous-SELECT ; c'est-à-dire que la syntaxe FROM func(...) alias est à peu près équivalente à FROM LATERAL (SELECT func(...)) alias. Notez que LATERAL est considéré comme implicite ; cela est dû au fait que la norme exige le sens LATERAL pour un élément UNNEST() dans FROM. PostgreSQL traite UNNEST() de manière similaire aux autres fonctions retournant des ensembles.

Espace de noms disponible pour GROUP BY et ORDER BY

Selon la norme SQL-92, une clause ORDER BY ne peut utiliser que des noms de colonnes de sortie ou des nombres, tandis qu'une clause GROUP BY ne peut utiliser que des expressions basées sur des noms de colonnes d'entrée. PostgreSQL étend chacune de ces clauses pour permettre également l'autre option (bien qu'il utilise l'interprétation standard en cas d'ambiguïté). PostgreSQL permet également aux deux clauses de spécifier des expressions arbitraires. Notez que les noms apparaissant dans une expression seront toujours interprétés comme des noms de colonnes d'entrée, et non de sortie.

SQL:1999 et les versions ultérieures utilisent une définition légèrement différente, qui n'est pas entièrement compatible avec SQL-92. Dans la plupart des cas, cependant, PostgreSQL interprétera une expression ORDER BY ou GROUP BY de la même manière que SQL:1999.

Dépendances fonctionnelles

PostgreSQL ne reconnaît une dépendance fonctionnelle (permettant d'omettre des colonnes dans GROUP BY) que lorsque le nom de la table principale est inclus dans la liste GROUP BY. La norme SQL spécifie des conditions supplémentaires qui doivent être reconnues.

LIMIT et OFFSET

Les clauses LIMIT et OFFSET sont une syntaxe spécifique à PostgreSQL, également utilisée par MySQL. La norme SQL:2008 a introduit les clauses OFFSET ... FETCH {FIRST|NEXT} ... pour la même fonctionnalité, comme illustré dans la clause LIMIT. Cette syntaxe est également utilisée par IBM DB2. (Les applications écrites pour Oracle utilisent souvent une solution de contournement avec la colonne rownum générée automatiquement, qui n'est pas disponible dans PostgreSQL pour implémenter les effets de ces clauses.)

FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE, FOR KEY SHARE

Bien que FOR UPDATE apparaisse dans la norme SQL, la norme ne l'autorise que comme une option de DECLARE CURSOR. PostgreSQL l'autorise dans n'importe quel SELECT et dans les sous-SELECTs, bien que ce soit une extension. Les variantes FOR NO KEY UPDATE, FOR SHARE et FOR KEY SHARE, ainsi que les options NOWAIT et SKIP LOCKED, n'apparaissent pas dans la norme.

Instructions de modification de données dans WITH

PostgreSQL permet d'utiliser INSERT, UPDATE, DELETE et MERGE comme requêtes WITH. Ceci n'est pas présent dans la norme SQL.

Clauses non standard

DISTINCT ON ( ... ) est une extension de la norme SQL.

ROWS FROM( ... ) est une extension de la norme SQL.

Les options MATERIALIZED et NOT MATERIALIZED de WITH sont une extension de la norme SQL.
