TAP::Harness::Beyond(3perl) Manuel de référence pour développeurs Perl TAP::Harness::Beyond(3perl)

NAME

Test::Harness::Beyond - Au-delà de make test

Au-delà de make test

Test::Harness est responsable de l'exécution des scripts de test, de l'analyse de leur sortie et du rapport des succès ou échecs. Lorsque j'écris make test (ou ./Build test) pour un module, Test::Harness est généralement utilisé pour exécuter les tests (tous les modules n'utilisent pas Test::Harness mais la plupart le font).

Pour explorer certaines des fonctionnalités de Test::Harness, je dois passer de make test à la commande prove (qui est fournie avec Test::Harness). Pour les exemples suivants, j'aurai également besoin d'une version récente de Test::Harness installée; 3.14 est la version actuelle que j'ai.

Pour les exemples que je vais présenter, je suppose que nous travaillons avec une distribution de module Perl normale. Spécifiquement, je suppose que lors de l'exécution de make ou ./Build, le code du module déjà compilé et prêt à être installé se trouve dans ./blib/lib et ./blib/arch, et qu'il existe un répertoire nommé 't' qui contient nos tests. Test::Harness n'est pas figé à cette configuration, mais cela m'aide à éviter d'expliquer où se trouvent les fichiers pour chaque exemple.

Je reviens à prove; comme make test, il exécute un ensemble de tests - mais il offre plus de contrôle sur les tests qui sont exécutés, dans quel ordre et comment les résultats sont rapportés. Généralement, make test exécute tous les scripts de test situés dans le répertoire 't'. Pour faire la même chose avec prove, j'écris :

prove -rb t

Les options ici sont -r pour parcourir récursivement tous les répertoires sous 't' et -b qui ajoute ./blib/lib et ./blib/arch au chemin d'inclusion de Perl de sorte que les tests puissent trouver le code qu'ils testent. Si je teste un module dont une version antérieure est déjà installée, je dois faire attention au chemin d'inclusion pour m'assurer que je n'exécute pas mes tests contre la version installée, mais contre la nouvelle sur laquelle je travaille.

Contrairement à make test, taper prove ne reconstruit pas automatiquement mon module. Si j'oublie de faire make avant d'exécuter prove, je testerai contre d'anciennes versions de ces fichiers - ce qui conduira inévitablement à la confusion. Ce que je fais, c'est prendre l'habitude de taper :

make && prove -rb t

ou - si je n'ai pas de code XS qui nécessite une compilation, j'utilise les modules sous lib :

prove -Ilib -r t

Jusqu'à présent, je n'ai rien montré que make test ne fasse pas. Corrigeons cela.

État enregistré

Si j'ai des tests échoués dans une suite de tests composée de plus de quelques scripts et qui prend plus de quelques secondes à s'exécuter, il est fastidieux de répéter l'exécution de la suite de tests pour chaque problème que je rencontre.

Je peux dire à prove de n'exécuter que les tests qui échouent comme ceci :

prove -b t/this_fails.t t/so_does_this.t

Cela accélère les choses, mais je dois noter quels tests échouent et m'assurer de les exécuter. Au lieu de cela, je peux utiliser l'option --state de prove pour qu'il garde une trace des tests qui échouent pour moi. D'abord, j'exécute un cycle complet de la suite de tests et je dis à prove de sauvegarder les résultats :

prove -rb --state=save t

Cela enregistre un résumé lisible par machine de l'exécution des tests dans un fichier nommé '.prove' dans le répertoire courant. Si j'ai des échecs, je peux ensuite n'exécuter que les tests qui échouent comme ceci :

prove -b --state=failed

Je peux aussi dire à prove de sauvegarder à nouveau les résultats pour mettre à jour sa compréhension de quels tests échouent :

prove -b --state=failed,save

Dès qu'un de mes tests qui échoue passe, il est retiré de la liste des tests échoués. Finalement, je corrige tous les problèmes et prove n'aura plus de tests échoués à exécuter :

Files=0, Tests=0, 0 wallclock secs ( 0.00 usr + 0.00 sys = 0.00 CPU)
Result: NOTESTS

Pendant que je travaille sur une partie spécifique de mon module, il est probable que les tests qui couvrent ce code échouent. Je voudrais exécuter la suite de tests complète mais accorder la priorité à ces tests "chauds". Je peux dire à prove de faire cela :

prove -rb --state=hot,save t

Tous les tests seront exécutés, mais ceux qui ont échoué le plus récemment seront exécutés en premier. S'il n'y a pas eu de tests échoués depuis que j'ai commencé à sauvegarder l'état, tous les tests seront exécutés dans leur ordre normal. Cela combine une couverture de test complète avec une notification précoce des échecs.

L'option --state de prove prend en charge un certain nombre d'options ; par exemple, pour exécuter d'abord les tests qui ont échoué, suivis des tests restants triés par date de script de test - et pour sauvegarder les résultats - je peux utiliser :

prove -rb --state=failed,new,save t

Consultez la documentation de prove (tapez prove --man) pour une liste complète des options d'état.

Lorsque je dis à prove de sauvegarder l'état, il écrit un fichier nommé '.prove' ('_prove' sous Windows) dans le répertoire courant. C'est un document YAML, il est donc facile d'écrire des outils personnalisés qui fonctionnent avec l'état de test sauvegardé - mais le format n'est pas officiellement documenté, il pourrait donc changer (très) bientôt sans préavis.

Tests parallèles

Si mes tests prennent trop de temps à s'exécuter, je peux les accélérer en exécutant plusieurs scripts de test en parallèle. Ceci est particulièrement efficace si les tests sont liés aux E/S ou si j'ai plusieurs cœurs de processeur. Je dis à prove d'exécuter mes tests en parallèle comme ceci :

prove -rb -j 9 t

L'option -j active les tests parallèles ; le nombre qui suit est le nombre maximum de tests à exécuter en parallèle. Parfois, des tests qui réussissent lors d'une exécution séquentielle peuvent échouer lors d'une exécution parallèle. Par exemple, si deux scripts de test différents utilisent le même fichier temporaire ou tentent d'écouter sur le même socket, ils auront des problèmes lors de l'exécution parallèle. Si je vois des échecs inattendus, je dois examiner mes tests pour voir lesquels accaparent des ressources communes et renommer les fichiers temporaires ou ajouter des verrous si nécessaire.

Pour obtenir le maximum de performances, je veux que les scripts de test qui prennent le plus de temps à s'exécuter soient exécutés en premier - sinon j'attendrai que le test qui prend près d'une minute se termine après que tous les autres soient terminés. Je peux utiliser l'option --state pour exécuter les tests de manière décroissante en termes de lenteur :

prove -rb -j 9 --state=slow,save t

Tests non-Perl

Le protocole de test (TAP) n'est pas réservé à Perl. Toutes sortes de langages peuvent être utilisés pour écrire des tests qui produisent du TAP. Il existe des bibliothèques de test basées sur TAP pour C, C++, PHP, Python et bien d'autres. Si je ne trouve pas de bibliothèque TAP pour mon langage préféré, il est facile de générer une sortie TAP valide. Cela ressemble à ceci :

1..3 
ok 1 - init OK 
ok 2 - opened file 
not ok 3 - appended to file

La première ligne est le plan - elle spécifie le nombre de tests que je vais exécuter, il est donc facile de vérifier que le script de test n'a pas terminé avant d'avoir exécuté toutes les tests attendus. Les lignes suivantes sont les résultats des tests - 'ok' pour succès, 'not ok' pour échec. Chaque test a un numéro et, facultativement, une description. Et c'est tout. Tout langage capable de produire une sortie similaire sur STDOUT peut être utilisé pour écrire des tests.

Récemment, j'ai ravivé mon intérêt pour Forth, qui date d'il y a vingt ans. Clairement, j'ai une tendance à l'autosatisfaction que même Perl ne peut satisfaire. Je veux écrire des tests en Forth et les exécuter en utilisant prove (vous pouvez trouver mes expériences gforth TAP sur https://svn.hexten.net/andy/Forth/Testing/). Je peux utiliser l'option --exec de prove pour exécuter les tests avec gforth comme ceci :

prove -r --exec gforth t

Alternativement, si le langage utilisé pour écrire mes tests permet une ligne shebang, je peux l'utiliser pour spécifier l'interpréteur. Voici un exemple écrit en PHP :

#!/usr/bin/php 
<?php
  print "1..2\n"; 
  print "ok 1\n"; 
  print "not ok 2\n";
?>

Si je le sauvegarde sous t/phptest.t, la ligne shebang garantira qu'il s'exécute correctement avec tous mes autres tests.

Mélanger les choses

Des dépendances subtiles entre les programmes de test peuvent masquer des problèmes - par exemple, un test précédent pourrait ne pas supprimer un fichier temporaire qui affecte le comportement d'un test ultérieur. Pour trouver ce type de problème, j'utilise les options --shuffle et --reverse de prove pour exécuter mes tests dans un ordre aléatoire ou inversé.

Créer mon propre outil

Si j'ai besoin d'une fonctionnalité que prove ne fournit pas, je peux facilement créer la mienne.

Normalement, vous voudrez modifier la façon dont TAP obtient son entrée et la sortie du parseur. App::Prove prend en charge

TAP::Harness::Beyond - Perl manual

NAME

TAP::Harness::Beyond - More advanced TAP::Harness usage

Beyond make test

The test suite for a Perl distribution is represented as a set of TAP (Test Anything Protocol) files. The harness that runs them is typically Test::Harness, which is a compatibility wrapper around TAP::Harness. For new applications I should use TAP::Harness directly.

The harness runs the tests, and then parses, analyses and presents the results. By subclassing TAP::Harness I can customise many aspects of the test run.

For example, I want to log my test results in a database so I can track them over time. To do this I override the summary method in TAP::Harness. I start with a simple prototype that dumps the results as a YAML document:

  package My::TAP::Harness;
  use base 'TAP::Harness';
  use YAML;
  sub summary {
    my ( $self, $aggregate ) = @_; 
    print Dump( $aggregate );
    $self->SUPER::summary( $aggregate );
  }
  1;

I need to tell prove to use my My::TAP::Harness. If My::TAP::Harness is on Perl's @INC include path I can

  prove --harness=My::TAP::Harness -rb t

If I don't have My::TAP::Harness installed on @INC I need to provide the correct path to perl when I run prove:

  perl -Ilib `which prove` --harness=My::TAP::Harness -rb t

I can incorporate these options into my own version of prove. It's pretty simple. Most of the work of prove is handled by App::Prove. The important code in prove is just:

  use App::Prove;
  my $app = App::Prove->new; 
  $app->process_args(@ARGV); 
  exit( $app->run ? 0 : 1 );

If I write a subclass of App::Prove I can customise any aspect of the test runner while inheriting all of prove's behaviour. Here's myprove:

  #!/usr/bin/env perl
  use lib qw( lib );      # Add ./lib to @INC
  use App::Prove;
  my $app = App::Prove->new;
  # Use custom TAP::Harness subclass
  $app->harness( 'My::TAP::Harness' );
  $app->process_args( @ARGV );
  exit( $app->run ? 0 : 1 );

Now I can run my tests like this

  ./myprove -rb t

Deeper Customisation

Now that I know how to subclass and replace TAP::Harness I can replace any other part of the harness. To do that I need to know which classes are responsible for which functionality. Here's a brief guided tour; the default class for each component is shown in parentheses. Normally any replacements I write will be subclasses of these default classes.

When I run my tests TAP::Harness creates a scheduler (TAP::Parser::Scheduler) to work out the running order for the tests, an aggregator (TAP::Parser::Aggregator) to collect and analyse the test results and a formatter (TAP::Formatter::Console) to display those results.

If I'm running my tests in parallel there may also be a multiplexer (TAP::Parser::Multiplexer) - the component that allows multiple tests to run simultaneously.

Once it has created those helpers TAP::Harness starts running the tests. For each test it creates a new parser (TAP::Parser) which is responsible for running the test script and parsing its output.

To replace any of these components I call one of these harness methods with the name of the replacement class:

  aggregator_class 
  formatter_class 
  multiplexer_class 
  parser_class
  scheduler_class

For example, to replace the aggregator I would

  $harness->aggregator_class( 'My::Aggregator' );

Alternately I can supply the names of my substitute classes to the TAP::Harness constructor:

  my $harness = TAP::Harness->new(
    { aggregator_class => 'My::Aggregator' }
  );

If I need to reach even deeper into the internals of the harness I can replace the classes that TAP::Parser uses to execute test scripts and tokenise their output. Before running a test script TAP::Parser creates a grammar (TAP::Parser::Grammar) to decode the raw TAP into tokens, a result factory (TAP::Parser::ResultFactory) to turn the decoded TAP results into objects and, depending on whether it's running a test script or reading TAP from a file, scalar or array a source or an iterator (TAP::Parser::IteratorFactory).

Each of these objects may be replaced by calling one of these parser methods:

  source_class
  perl_source_class 
  grammar_class 
  iterator_factory_class
  result_factory_class

Callbacks

As an alternative to subclassing the components I need to change I can attach callbacks to the default classes. TAP::Harness exposes these callbacks:

  parser_args      Tweak the parameters used to create the parser 
  made_parser      Just made a new parser 
  before_runtests  About to run tests 
  after_runtests   Have run all tests 
  after_test       Have run an individual test script

TAP::Parser also supports callbacks; bailout, comment, plan, test, unknown, version and yaml are called for the corresponding TAP result types, ALL is called for all results, ELSE is called for all results for which a named callback is not installed and EOF is called once at the end of each TAP stream.

To install a callback I pass the name of the callback and a subroutine reference to TAP::Harness or TAP::Parser's callback method:

  $harness->callback( after_test => sub {
    my ( $script, $desc, $parser ) = @_;
  } );

I can also pass callbacks to the constructor:

  my $harness = TAP::Harness->new({
    callbacks => {
            after_test => sub {
        my ( $script, $desc, $parser ) = @_; 
        # Do something interesting here
            }
    }
  });

When it comes to altering the behaviour of the test harness there's more than one way to do it. Which way is best depends on my requirements. In general if I only want to observe test execution without changing the harness' behaviour (for example to log test results to a database) I choose callbacks. If I want to make the harness behave differently subclassing gives me more control.

Parsing TAP

Perhaps I don't need a complete test harness. If I already have a TAP test log that I need to parse all I need is TAP::Parser and the various classes it depends upon. Here's the code I need to run a test and parse its TAP output

  use TAP::Parser;
  my $parser = TAP::Parser->new( { source => 't/simple.t' } );
  while ( my $result = $parser->next ) {
    print $result->as_string, "\n";
  }

Alternately I can pass an open filehandle as source and have the parser read from that rather than attempting to run a test script:

  open my $tap, '<', 'tests.tap' 
    or die "Can't read TAP transcript ($!)\n"; 
  my $parser = TAP::Parser->new( { source => $tap } );
  while ( my $result = $parser->next ) {
    print $result->as_string, "\n";
  }

This approach is useful if I need to convert my TAP based test results into some other representation. See TAP::Convert::TET (http://search.cpan.org/dist/TAP-Convert-TET/) for an example of this approach.

Getting Support

The Test::Harness developers hang out on the tapx-dev mailing list[1]. For discussion of general, language independent TAP issues there's the tap-l[2] list. Finally there's a wiki dedicated to the Test Anything Protocol[3]. Contributions to the wiki, patches and suggestions are all welcome.
