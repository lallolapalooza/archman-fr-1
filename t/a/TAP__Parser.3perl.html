TAP::Parser(3perl) Manuel du développeur Perl TAP::Parser(3perl)

NOM

TAP::Parser - Analyse la sortie TAP

VERSION

Version 3.50

SYNOPIS

use TAP::Parser;
my $parser = TAP::Parser->new( { source => $source } );
while ( my $result = $parser->next ) {
    print $result->as_string;
}

DESCRIPTION

« TAP::Parser » est conçu pour produire une analyse correcte des résultats TAP. Pour un exemple de la façon d'exécuter des tests à l'aide de ce module, consultez les exemples simples de harnesses dans « examples/ ».

Il existe un wiki dédié au protocole de test TAP :

http://testanything.org

Cela inclut le Cookbook de TAP::Parser :

http://testanything.org/testing-with-tap/perl/tap::parser-cookbook.html

MÉTHODES

Méthodes de classe

« new »

my $parser = TAP::Parser->new(\%args);

Renvoie un nouvel objet « TAP::Parser ».

Les arguments doivent être un hashref avec l'une des clés suivantes :

  • "source"

    CHANGÉ en 3.18

    C'est la méthode préférée pour passer l'entrée au constructeur.

    Le "source" est utilisé pour créer un objet TAP::Parser::Source qui est passé à l'iterateur_factory_class, qui à son tour détermine comment gérer la source et en crée un TAP::Parser::Iterator. L'itérateur est utilisé par l'analyseur pour lire le flux TAP.

    Pour configurer le IteratorFactory, utilisez le paramètre "sources" ci-dessous.

    Remarque : "source", "tap" et "exec" sont mutuellement exclusifs.

  • "tap"

    CHANGÉ en 3.18

    La valeur doit être la sortie TAP complète.

    Le "tap" est utilisé pour créer un objet TAP::Parser::Source qui est passé à l'iterateur_factory_class, qui à son tour détermine comment gérer la source et en crée un TAP::Parser::Iterator. L'itérateur est utilisé par l'analyseur pour lire le flux TAP.

    Pour configurer le IteratorFactory, utilisez le paramètre "sources" ci-dessous.

    Remarque : "source", "tap" et "exec" sont mutuellement exclusifs.

  • "exec"

    Vous devez passer une référence de tableau.

    Le tableau exec est utilisé pour créer un objet TAP::Parser::Source qui est passé à l'iterateur_factory_class, qui à son tour détermine comment gérer la source et en crée un TAP::Parser::Iterator. L'itérateur est utilisé par l'analyseur pour lire le flux TAP.

    Par défaut, TAP::Parser::SourceHandler::Executable crée un TAP::Parser::Iterator::Process pour gérer la source. Celui-ci passe le tableau de chaînes de caractères en tant qu'arguments à IPC::Open3::open3 :

    exec => [ '/usr/bin/ruby', 't/my_test.rb' ]

    Si certains "test_args" sont donnés, ils sont ajoutés à la fin de la liste des arguments de la commande.

    Pour configurer le IteratorFactory, utilisez le paramètre "sources" ci-dessous.

    Remarque : "source", "tap" et "exec" sont mutuellement exclusifs.

Les clés suivantes sont facultatives.

  • "sources"

    NOUVEAU en 3.18.

    S'il est défini, "sources" doit être un hashref contenant les noms des TAP::Parser::SourceHandler à charger et/ou configurer. Les valeurs sont un hash de configuration qui est accessible via "config_for" dans TAP::Parser::Source.

    Par exemple :

    sources => {
  Perl => { exec => '/path/to/custom/perl' },
  File => { extensions => [ '.tap', '.txt' ] },
  MyCustom => { some => 'config' },
}

    Cela amènera "TAP::Parser" à passer la configuration personnalisée à deux des gestionnaires préinstallés - TAP::Parser::SourceHandler::Perl, TAP::Parser::SourceHandler::File - et tentera de charger la classe "MyCustom". Voir "load_handlers" dans TAP::Parser::IteratorFactory pour plus de détails.

    Le paramètre "sources" affecte la façon dont les paramètres "source", "tap" et "exec" sont gérés.

    Voir TAP::Parser::IteratorFactory, TAP::Parser::SourceHandler et leurs sous-classes pour plus de détails.

  • "callback"

    S'il est présenté, chaque callback correspondant à un type de résultat donné sera appelé avec le résultat comme argument si la méthode "run" est utilisée :

    my %callbacks = (
    test    => \&test_callback,
    plan    => \&plan_callback,
    comment => \&comment_callback,
    bailout => \&bailout_callback,
    unknown => \&unknown_callback,
);
my $aggregator = TAP::Parser::Aggregator->new;
for my $file ( @test_files ) {
    my $parser = TAP::Parser->new(
        {
            source    => $file,
            callbacks => \%callbacks,
        }
    );
    $parser->run;
    $aggregator->add( $file, $parser );
}
  • "switches"

    Si un fichier Perl est utilisé comme source, des options facultatives peuvent être transmises qui seront utilisées lors de l'invocation de l'exécutable perl.

    my $parser = TAP::Parser->new( {
    source   => $test_file,
    switches => [ '-Ilib' ],
} );
  • "test_args"

    Est utilisé en conjonction avec les paramètres "source" et "exec" pour fournir une référence de tableau d'arguments de style @ARGV au programme de test.

  • "spool"

    Si un descripteur de fichier est passé, il écrira une copie de tous les TAP analysés dans ce descripteur.

  • "merge"

    S'il est faux, STDERR n'est pas capturé (bien qu'il soit envoyé à STDOUT pour le maintenir synchronisé.)

    S'il est vrai, STDERR et STDOUT sont le même descripteur de fichier. Cela peut causer des problèmes si STDERR contient quelque chose qui ressemble au format TAP, mais permet une synchronisation exacte.

    Les détails de ce comportement peuvent dépendre du système et peuvent changer à l'avenir.

  • "grammar_class"

    Cette option a été introduite pour vous permettre de personnaliser facilement la classe de grammaire que l'analyseur devrait utiliser. La valeur par défaut est TAP::Parser::Grammar.

    Voir également "make_grammar".

  • "result_factory_class"

    Cette option a été introduite pour vous permettre de personnaliser facilement la classe de fabrique de résultats que l'analyseur devrait utiliser. La valeur par défaut est TAP::Parser::ResultFactory.

    Voir également "make_result".

  • "iterator_factory_class"

    CHANGEMENT en 3.18

    Cette option a été introduite pour vous permettre de personnaliser facilement la classe de fabrique d'itérateurs que l'analyseur devrait utiliser. La valeur par défaut est TAP::Parser::IteratorFactory.

NAME

TAP::Parser - parse Test Anything Protocol (TAP) output

SYNOPSIS

    use TAP::Parser;

    # Read from a file
    my $parser = TAP::Parser->new( { source => 't/basic.t' } );

    # Read from a filehandle
    open my $fh, '<', 't/basic.t' or die $!;
    my $parser = TAP::Parser->new( { source => $fh } );

    # Read from a string
    my $parser = TAP::Parser->new( { source => '... TAP ...' } );

    # Parse it all
    my $results = $parser->run;

    # Parse one at a time
    while ( my $result = $parser->next ) {
        # ... do something with $result ...
    }

    # Use callbacks
    my $parser = TAP::Parser->new( {
        source   => 't/basic.t',
        callback => sub {
            my $result = shift;
            print $result->as_string;
        },
    } );
    $parser->run;

DESCRIPTION

This module parses Test Anything Protocol (TAP) output. It can read from files, filehandles, or strings, and then either yield results one by one or call a callback for each result.

See TAP::Parser::SourceHandler documentation for details on what can be used for the source argument.

METHODS

new

my $parser = TAP::Parser->new( $args );
my $parser = TAP::Parser->new( $source );

Instantiates a new TAP::Parser object. The $args or $source argument is required.

If $args is a string or a filehandle it's treated as the source argument.

Supported arguments include:

source
The data to parse. This can be a filename (string), a filehandle, or an arrayref of strings (one string per line).
callback
A callback sub to be called for each result. The result object is passed as the first argument to the callback.
callback_self
An object to be used as the invocant for the callback sub. If this is used, the callback will be called like $self->callback(@args). If it's not used, the callback will be called like callback(@args).
merge
A boolean indicating whether or not to merge STDERR into STDOUT. Default is false.
merge_to
A filehandle to print to if merge is true. If this is not specified, STDERR will be printed to the original STDERR.
grammar_class
The class to use for parsing the TAP. Defaults to TAP::Parser::Grammar.
result_factory_class
The class to use for creating result objects. Defaults to TAP::Parser::ResultFactory.
iterator_factory_class
The class to use for creating iterator objects. Defaults to TAP::Parser::IteratorFactory.
strict
If true, will cause the parser to die if it encounters any non-TAP output.
warnings
If true, will cause the parser to die if it encounters any warnings.

next

my $result = $parser->next;

This method returns the results of the parsing, one result at a time. Note that it is destructive. You can't rewind and examine previous results.

If callbacks are used, they will be issued before this call returns.

Each result returned is a subclass of TAP::Parser::Result. See that module and related classes for more information on how to use them.

run

$parser->run;

This method merely runs the parser and parses all of the TAP.

make_grammar

Make a new TAP::Parser::Grammar object and return it. Passes through any arguments given.

The grammar_class can be customized, as described in new.

make_result

Make a new TAP::Parser::Result object using the parser's TAP::Parser::ResultFactory, and return it. Passes through any arguments given.

The result_factory_class can be customized, as described in new.

make_iterator_factory

NEW to 3.18.

Make a new TAP::Parser::IteratorFactory object and return it. Passes through any arguments given.

iterator_factory_class can be customized, as described in new.

INDIVIDUAL RESULTS

If you've read this far in the docs, you've seen this:

while ( my $result = $parser->next ) {
    print $result->as_string;
}

Each result returned is a TAP::Parser::Result subclass, referred to as result types.

Result types

Basically, you fetch individual results from the TAP. The six types, with examples of each, are as follows:

  • Version 
    TAP version 12
  • Plan 
    1..42
  • Pragma 
    pragma +strict
  • Test 
    ok 3 - We should start with some foobar!
  • Comment 
    # Hope we don't use up the foobar.
  • Bailout 
    Bail out!  We ran out of foobar!
  • Unknown 
    ... yo, this ain't TAP! ...

Each result fetched is a result object of a different type. There are common methods to each result object and different types may have methods unique to their type. Sometimes a type method may be overridden in a subclass, but its use is guaranteed to be identical.

Common type methods

type

Returns the type of result, such as comment or test.

as_string

Prints a string representation of the token. This might not be the exact output, however. Tests will have test numbers added if not present, TODO and SKIP directives will be capitalized and, in general, things will be cleaned up. If you need the original text for the token, see the raw method.

raw

Returns the original line of text which was parsed.

is_plan

Indicates whether or not this is the test plan line.

is_test

Indicates whether or not this is a test line.

is_comment

Indicates whether or not this is a comment. Comments will generally only appear in the TAP stream if STDERR is merged to STDOUT. See the merge option.

is_bailout

Indicates whether or not this is bailout line.

is_yaml

Indicates whether or not the current item is a YAML block.

is_unknown

Indicates whether or not the current line could be parsed.

is_ok

if ( $result->is_ok ) { ... }

Reports whether or not a given result has passed. Anything which is not a test result returns true. This is merely provided as a convenient shortcut which allows you to do this:

my $parser = TAP::Parser->new( { source => $source } );
while ( my $result = $parser->next ) {
    # only print failing results
    print $result->as_string unless $result->is_ok;
}

"plan" methods

if ( $result->is_plan ) { ... }

If the above evaluates as true, the following methods will be available on the $result object.

plan

if ( $result->is_plan ) {
   print $result->plan;
}

This is merely a synonym for as_string.

directive

my $directive = $result->directive;

If a SKIP directive is included with the plan, this method will return it.

1..0 # SKIP: why bother?

explanation

my $explanation = $result->explanation;

If a SKIP directive was included with the plan, this method will return the explanation, if any.

"pragma" methods

if ( $result->is_pragma ) { ... }

If the above evaluates as true, the following methods will be available on the $result object.

pragmas

Returns a list of pragmas each of which is a + or - followed by the pragma name.

"comment" methods

if ( $result->is_comment ) { ... }

If the above evaluates as true, the following methods will be available on the $result object.

comment

if ( $result->is_comment ) {
    my $comment = $result->comment;
    print "I have something to say:  $comment";
}

"bailout" methods

if ( $result->is_bailout ) { ... }

If the above evaluates as true, the following methods will be available on the $result object.

explanation

if ( $result->is_bailout ) {
    my $explanation = $result->explanation;
    print "We bailed out because ($explanation)";
}

If, and only if, a token is a bailout token, you can get an "explanation" via this method. The explanation is the text after the mystical "Bail out!" words which appear in the tap output.

"unknown" methods

if ( $result->is_unknown ) { ... }

There are no unique methods for unknown results.

"test" methods

if ( $result->is_test ) { ... }

If the above evaluates as true, the following methods will be available on the $result object.

ok

my $ok = $result->ok;

Returns the literal text of the ok or not ok status.

number

my $test_number = $result->number;

Returns the number of the test, even if the original TAP output did not supply that number.

description

my $description = $result->description;

Returns the description of the test, if any. This is the portion after the test number but before the directive.

directive

my $directive = $result->directive;

Returns either TODO or SKIP if either directive was present for a test line.

explanation

my $explanation = $result->explanation;

If a test had either a TODO or SKIP directive, this method will return the accompanying explanation, if present.

not ok 17 - 'Pigs can fly' # TODO not enough acid

For the above line, the explanation is not enough acid.

is_ok

if ( $result->is_ok ) { ... }

Returns a boolean value indicating whether or not the test passed. Remember that for TODO tests, the test always passes.

Note: this was formerly passed. The latter method is deprecated and will issue a warning.

is_actual_ok

if ( $result->is_actual_ok ) { ... }

Returns a boolean value indicating whether or not the test passed, regardless of its TODO status.

Note: this was formerly actual_passed. The latter method is deprecated and will issue a warning.

Méthodes de contrôle du résultat

"is_unplanned"

if ( $test->is_unplanned ) { ... }

Si un numéro de test est supérieur au nombre de tests planifiés, cette méthode renverra vrai. Les tests non planifiés renverront *toujours* faux pour "is_ok", que le test "has_todo" (voir TAP::Parser::Result::Test pour plus d'informations à ce sujet).

"has_skip"

if ( $result->has_skip ) { ... }

Retourne une valeur booléenne indiquant si ce test avait une directive SKIP.

"has_todo"

if ( $result->has_todo ) { ... }

Retourne une valeur booléenne indiquant si ce test avait une directive TODO.

Notez que les tests TODO réussissent *toujours*. Si vous avez besoin de savoir s'ils ont réellement réussi, vérifiez la méthode "is_actual_ok".

"in_todo"

if ( $parser->in_todo ) { ... }

Vrai tant que le résultat le plus récent était un TODO. Devient vrai avant que le résultat TODO ne soit retourné et reste vrai jusqu'à juste avant que le prochain test non-TODO ne soit retourné.

RÉSULTATS TOTAUX

Après avoir analysé le TAP, de nombreuses méthodes sont disponibles pour vous permettre d'examiner les résultats et de déterminer ce qui est significatif pour vous.

Résultats individuels

Ces résultats font référence aux tests individuels qui sont exécutés.

"passed"

my @passed = $parser->passed; # les numéros de test qui ont réussi
my $passed = $parser->passed; # le nombre de tests qui ont réussi

Cette méthode vous indique quels tests (ou combien) ont réussi. Si un test a échoué mais avait une directive TODO, il sera compté comme un test réussi.

"failed"

my @failed = $parser->failed; # les numéros de test qui ont échoué
my $failed = $parser->failed; # le nombre de tests qui ont échoué

Cette méthode vous indique quels tests (ou combien) ont échoué. Si un test a réussi mais avait une directive TODO, il ne sera **PAS** compté comme un test échoué.

"actual_passed"

# les numéros de test qui ont réellement réussi
my @actual_passed = $parser->actual_passed;
# le nombre de tests qui ont réellement réussi
my $actual_passed = $parser->actual_passed;

Cette méthode vous indique quels tests (ou combien) ont réellement réussi, indépendamment de la présence ou non d'une directive TODO.

"actual_ok"

Cette méthode est un synonyme de "actual_passed".

"actual_failed"

# les numéros de test qui ont réellement échoué
my @actual_failed = $parser->actual_failed;
# le nombre de tests qui ont réellement échoué
my $actual_failed = $parser->actual_failed;

Cette méthode vous indique quels tests (ou combien) ont réellement échoué, indépendamment de la présence ou non d'une directive TODO.

"todo"

my @todo = $parser->todo; # les numéros de test avec des directives todo
my $todo = $parser->todo; # le nombre de tests avec des directives todo

Cette méthode vous indique quels tests (ou combien) avaient des directives TODO.

"todo_passed"

# les numéros de test qui ont inopinément réussi
my @todo_passed = $parser->todo_passed;
# le nombre de tests qui ont inopinément réussi
my $todo_passed = $parser->todo_passed;

Cette méthode vous indique quels tests (ou combien) ont réellement réussi mais étaient déclarés comme tests "TODO".

"todo_failed"

# déprécié en faveur de 'todo_passed'. Cette méthode était horriblement mal nommée.

C'était une méthode mal nommée. Elle indique quels tests TODO ont réussi inopinément. Elle émettra maintenant un avertissement et appellera "todo_passed".

"skipped"

my @skipped = $parser->skipped; # les numéros de test avec des directives SKIP
my $skipped = $parser->skipped; # le nombre de tests avec des directives SKIP

Cette méthode vous indique quels tests (ou combien) avaient des directives SKIP.

Pragma

"pragma"

Obtient ou définit un pragma. Pour obtenir l'état d'un pragma :

if ( $p->pragma('strict') ) {
    # être strict
}

Pour définir l'état d'un pragma :

$p->pragma('strict', 1); # activer le mode strict

"pragmas"

Obtient une liste de tous les pragmas actuellement activés :

my @pragmas_enabled = $p->pragmas;

Résultats synthétiques

Ces résultats sont des informations "méta" sur les résultats totaux d'un programme de test individuel.

"plan"

my $plan = $parser->plan;

Retourne le plan de test, s'il est trouvé.

"good_plan"

Obsolète. Utilisez "is_good_plan" à la place.

"is_good_plan"

if ( $parser->is_good_plan ) { ... }

Retourne une valeur booléenne indiquant si le nombre de tests planifiés correspond ou non au nombre de tests exécutés.

Note : ceci était anciennement "good_plan". Cette dernière méthode est obsolète et émettra un avertissement.

Et puisque nous en parlons...

"tests_planned"

print $parser->tests_planned;

Retourne le nombre de tests planifiés, selon le plan. Par exemple, un plan de '1..17' signifiera que 17 tests étaient planifiés.

"tests_run"

print $parser->tests_run;

Retourne le nombre de tests qui ont réellement été exécutés. Espérons que cela correspondra au nombre de "$parser->tests_planned".

"skip_all"

Retourne une valeur vraie (en fait, la raison du saut) si tous les tests ont été ignorés.

"start_time"

Retourne le temps réel lors de la création du Parseur.

"end_time"

Retourne le temps réel lors de la fin de la lecture de l'entrée TAP.

"start_times"

Retourne les temps CPU (comme "times" dans perlfunc) lors de la création du Parseur.

"end_times"

Retourne les temps CPU (comme "times" dans perlfunc) lors de la fin de la lecture de l'entrée TAP.

"has_problems"

if ( $parser->has_problems ) {
    ...
}

C'est une méthode "tout-en-un" qui renvoie vrai si des tests ont actuellement échoué, si des tests TODO ont réussi inopinément, ou si des erreurs d'analyse se sont produites.

"version"

$parser->version;

Une fois l'analyse terminée, ceci retournera le numéro de version du TAP analysé. Les numéros de version ont été introduits avec la version 13 de TAP, donc s'il n'y a pas de numéro de version trouvé, la version 12 est supposée.

"exit"

$parser->exit;

Une fois l'analyse terminée, ceci retournera le code de sortie. Si le parseur a exécuté un exécutable, il retournera le code de sortie de l'exécutable.

"wait"

$parser->wait;

Une fois l'analyse terminée, ceci retournera le statut d'attente. Si le parseur a exécuté un exécutable, il retournera le statut d'attente de l'exécutable. Sinon, ceci retourne simplement le statut de "exit".

"ignore_exit"

$parser->ignore_exit(1);

Indique au parseur d'ignorer le code de sortie du test lors de la détermination de la réussite du test. Normalement, les tests avec un code de sortie non nul sont considérés comme ayant échoué même si tous les tests individuels ont réussi. Dans les cas où il n'est pas possible de contrôler la valeur de sortie du script de test, utilisez cette option pour l'ignorer.

"parse_errors"

my @errors = $parser->parse_errors; # les erreurs du parseur
my $errors = $parser->parse_errors; # le nombre d'erreurs d'analyse

Heureusement, toutes les sorties TAP sont parfaites. Dans le cas contraire, cette méthode retournera les erreurs du parseur. Notez qu'une ligne incorrecte que le parseur ne reconnaît pas n'est **pas** une erreur. Cela permet à ce parseur de gérer les versions futures de TAP. Les éléments suivants sont toutes des erreurs TAP signalées par le parseur :

  • Plan mal placé

    Le plan (par exemple, '1..5'), doit apparaître uniquement au début ou à la fin de la sortie TAP.

  • Pas de plan

    Il faut un plan !

  • Plusieurs plans 
    1..3
ok 1 - fichier d'entrée ouvert
not ok 2 - première ligne de l'entrée valide # todo certaines données
ok 3 lecture du reste du fichier
1..3

    C'est ça. Très drôle. Ne faites pas ça.

  • Numéros de test hors séquence 
    1..3
ok 1 - fichier d'entrée ouvert
not ok 2 - première ligne de l'entrée valide # todo certaines données
ok 2 lecture du reste du fichier

    La dernière ligne de test ci-dessus devrait avoir le numéro '3' au lieu de '2'.

    Notez qu'il est parfaitement acceptable que certaines lignes aient des numéros de test et d'autres non. Cependant, lorsqu'un numéro de test est trouvé, il doit être en séquence. Ce qui suit est également une erreur :

    1..3
ok 1 - fichier d'entrée ouvert
not ok - première ligne de l'entrée valide # todo certaines données
ok 2 lecture du reste du fichier

    Mais ce n'est pas le cas :

    1..3
ok  - fichier d'entrée ouvert
not ok - première ligne de l'entrée valide # todo certaines données
ok 3 lecture du reste du fichier

"get_select_handles"

Obtenir une liste de descripteurs de fichiers qui peuvent être passés à "select" pour déterminer la disponibilité de ce parseur.

"delete_spool"

Supprimer et retourner le spool.

my $fh = $parser->delete_spool;

CALLBACKS

Comme mentionné précédemment, une clé "callback" peut être ajoutée au constructeur de "TAP::Parser". Si elle est présente, chaque callback correspondant à un type de résultat donné sera appelé avec le résultat comme argument si la méthode "run" est utilisée. Le callback est censé être une référence de sous-routine (ou une sous-routine anonyme) qui est invoquée avec le résultat du parseur comme son argument.

my %callbacks = (
    test    => \&test_callback,
    plan    => \&plan_callback,
    comment => \&comment_callback,
    bailout => \&bailout_callback,
    unknown => \&unknown_callback,
);
my $aggregator = TAP::Parser::Aggregator->new;
for my $file ( @test_files ) {
    my $parser = TAP::Parser->new(
        {
            source    => $file,
            callbacks => \%callbacks,
        }
    );
    $parser->run;
    $aggregator->add( $file, $parser );
}

Les callbacks peuvent également être ajoutés comme ceci :

$parser->callback( test => \&test_callback );
$parser->callback( plan => \&plan_callback );

Les clés suivantes sont autorisées pour les callbacks. Ces clés sont sensibles à la casse.

  • "test"

    Invoqué si "$result->is_test" retourne vrai.

  • "version"

    Invoqué si "$result->is_version" retourne vrai.

  • "plan"

    Invoqué si "$result->is_plan" retourne vrai.

  • "comment"

    Invoqué si "$result->is_comment" retourne vrai.

  • "bailout"

    Invoqué si "$result->is_unknown" retourne vrai.

  • "yaml"

    Invoqué si "$result->is_yaml" retourne vrai.

  • "unknown"

    Invoqué si "$result->is_unknown" retourne vrai.

  • "ELSE"

    Si un résultat n'a pas de callback défini pour lui, ce callback sera invoqué. Ainsi, si tous les types de résultats précédents sont spécifiés comme callbacks, ce callback ne sera jamais invoqué.

  • "ALL"

    Ce callback sera toujours invoqué et cela se produira pour chaque résultat après qu'un des callbacks ci-dessus ait été invoqué. Par exemple, si Term::ANSIColor est chargé, vous pourriez utiliser ce qui suit pour colorer votre sortie de test :

    my %callbacks = (
    test => sub {
        my $test = shift;
        if ( $test->is_ok && not $test->directive ) {
            # test normal réussi
            print color 'green';
        }
        elsif ( !$test->is_ok ) {    # même s'il est TODO
            print color 'white on_red';
        }
        elsif ( $test->has_skip ) {
            print color 'white on_blue';
        }
        elsif ( $test->has_todo ) {
            print color 'white';
        }
    },
    ELSE => sub {
        # plan, commentaire, et ainsi de suite (tout ce qui n'est pas une ligne de test)
        print color 'black on_white';
    },
    ALL => sub {
        # maintenant, affichez-les
        print shift->as_string;
        print color 'reset';
        print "\n";
    },
);
  • "EOF"

    Invoqué lorsqu'il n'y a plus de lignes à analyser. Puisqu'il n'y a pas d'objet TAP::Parser::Result associé, l'objet "TAP::Parser" est passé à la place.

GRAMMAIRE TAP

Si vous recherchez une grammaire EBNF, consultez TAP::Parser::Grammar.

COMPATIBILITÉ ASCENDANTE

La liste Perl-QA a tenté d'assurer la compatibilité ascendante avec Test::Harness. Cependant, il existe quelques différences mineures.

Différences

  • Plans TODO

    Une caractéristique peu connue de Test::Harness était qu'elle prenait en charge les listes TODO dans le plan :

    1..2 todo 2
ok 1 - Nous avons décollé
not ok 2 - Appareil anti-gravité activé

    Sous Test::Harness, le test numéro 2 aurait réussi car il était listé comme un test TODO sur la ligne du plan. Cependant, nous n'avons connaissance de personne n'utilisant réellement cette fonctionnalité et la codification en dur des numéros de test est déconseillée car il est très facile d'ajouter un test et de casser la séquence des numéros de test. Cela rend les suites de tests très fragiles. Au lieu de cela, il convient d'utiliser ce qui suit :

    1..2
ok 1 - Nous avons décollé
not ok 2 - Appareil anti-gravité activé # TODO
  • Tests 'manquants'

    Cela arrive rarement, mais parfois une 'harness' peut rencontrer des 'tests manquants :

    ok 1
ok 2
ok 15
ok 16
ok 17

    Test::Harness aurait signalé les tests 3 à 14 comme ayant échoué. Pour "TAP::Parser", ces tests ne sont pas considérés comme échoués car ils n'ont jamais été exécutés. Ils sont signalés comme des erreurs d'analyse (tests hors séquence).

SOUS-CLASSEMENT

Si vous trouvez que vous avez besoin de fournir une fonctionnalité personnalisée (comme vous l'auriez fait avec Test::Harness::Straps), vous avez de la chance : "TAP::Parser" et ses amis sont conçus pour être facilement intégrés et/ou sous-classés.

Avant de commencer, il est important de connaître quelques éléments :

1.
Tous les objets "TAP::*" héritent de TAP::Object.
2.
De nombreuses classes "TAP::*" ont une section SUBCLASSING pour vous guider.
3.
Notez que "TAP::Parser" est conçu pour être le "créateur" central - c'est-à-dire qu'il est responsable de la création de la plupart des nouveaux objets dans l'espace de noms "TAP::Parser::*".

Cela vous permet d'avoir un point unique pour configurer les sous-classes à utiliser, ce qui signifie que dans de nombreux cas, vous constaterez que vous n'avez besoin de sous-classer qu'un des composants du parseur.

L'exception à cette règle concerne les SourceHandlers et les Iterators, mais ceux-ci sont tous deux créés avec un IteratorFactory personnalisable.

4.
En sous-classant, vous pourriez finir par remplacer des méthodes non documentées. Ce n'est pas nécessairement une mauvaise chose, mais soyez averti que les méthodes non documentées peuvent changer sans préavis d'une version à l'autre - nous ne pouvons pas garantir la compatibilité ascendante. Si une méthode documentée doit être modifiée, elle sera d'abord dépréciée, puis modifiée dans une version ultérieure.

Composants du Parseur

Sources

Un parseur TAP consomme l'entrée d'une seule source brute de TAP, qui peut provenir de n'importe où (un fichier, un exécutable, une base de données, un descripteur d'E/S, une URI, etc.). La source est regroupée dans un objet TAP::Parser::Source qui collecte des métadonnées à son sujet. Le parseur utilise ensuite un TAP::Parser::IteratorFactory pour déterminer quel TAP::Parser::SourceHandler utiliser pour transformer la source brute en un flux de TAP au moyen d'"Iterators".

Si vous souhaitez simplement que "TAP::Parser" gère une nouvelle source de TAP, vous n'avez probablement pas besoin de sous-classer "TAP::Parser" lui-même. Au lieu de cela, vous devrez créer une nouvelle classe TAP::Parser::SourceHandler, et simplement l'intégrer au parseur en utilisant le paramètre sources de "new". Avant de commencer à en écrire une, lisez TAP::Parser::IteratorFactory pour avoir une idée du fonctionnement du système.

Si vous trouvez que vous avez vraiment besoin d'utiliser votre propre fabrique d'itérateurs, vous pouvez toujours le faire sans sous-classer "TAP::Parser" en définissant "iterator_factory_class".

Si vous avez juste besoin de personnaliser les objets lors de leur création, sous-classez TAP::Parser et remplacez "make_iterator_factory".

Notez que "make_source" et "make_perl_source" ont été dépréciés et sont maintenant supprimés.

Iterateurs

Un parseur TAP utilise des itérateurs pour parcourir le flux de TAP lu à partir de la source qui lui a été donnée. Il existe quelques types d'itérateurs disponibles par défaut, tous sous-classes de TAP::Parser::Iterator. Le choix de l'itérateur à utiliser est la responsabilité de la fabrique d'itérateurs, bien qu'elle délègue simplement au Source Handler qu'elle utilise.

Si vous écrivez votre propre TAP::Parser::SourceHandler, vous pourriez avoir besoin de créer vos propres itérateurs également. Si c'est le cas, vous devrez sous-classer TAP::Parser::Iterator.

Notez que "make_iterator" a été déprécié et est maintenant supprimé.

Résultats

Un parseur TAP crée des TAP::Parser::Results lors de son parcours du flux d'entrée. Il existe pas mal de types de résultats disponibles ; le choix de la classe à utiliser est la responsabilité de la fabrique de résultats.

Pour créer vos propres types de résultats, vous avez deux options :

Option 1
Sous-classez TAP::Parser::Result et enregistrez votre nouveau type/classe de résultat auprès de la TAP::Parser::ResultFactory par défaut.
Option 2
Sous-classez TAP::Parser::ResultFactory elle-même et implémentez votre propre logique de création de TAP::Parser::Result. Ensuite, vous devrez personnaliser la classe utilisée par votre parseur en définissant le paramètre "result_factory_class". Voir "new" pour plus de détails.

Si vous avez besoin de personnaliser les objets lors de leur création, sous-classez

TAP::Parser et remplacez "make_result".

Grammaire

TAP::Parser::Grammar est le cœur de l'analyseur. Il convertit en jetons le flux TAP d'entrée et produit des résultats. Si vous avez besoin de personnaliser son comportement, vous devriez probablement vous familiariser d'abord avec le code source. Assez de leçons.

Héritez de TAP::Parser::Grammar et personnalisez votre analyseur en définissant le paramètre "grammar_class". Voir "new" pour plus de détails.

Si vous avez besoin de personnaliser les objets lors de leur création, héritez de TAP::Parser et remplacez "make_grammar"
